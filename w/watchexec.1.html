NOM

watchexec - Exécute des commandes lorsque les fichiers surveillés changent

SYNTAXE

watchexec [--manual] [--completions] [--only-emit-events] [--shell] [-n ] [-E|--env] [--no-process-group] [--wrap-process] [--stop-signal] [--stop-timeout] [--delay-run] [--workdir] [--socket] [-o|--on-busy-update] [-r|--restart] [-s|--signal] [--map-signal] [-d|--debounce] [--stdin-quit] [-p|--postpone] [--poll] [--emit-events-to] [-w|--watch] [-W|--watch-non-recursive] [-F|--watch-file] [--no-vcs-ignore] [--no-project-ignore] [--no-global-ignore] [--no-default-ignore] [--no-discover-ignore] [--ignore-nothing] [-e|--exts] [-f|--filter] [--filter-file] [--project-origin] [-j|--filter-prog] [-i|--ignore] [--ignore-file] [--fs-events] [--no-meta] [-v|--verbose]... [--log-file] [--print-events] [-c|--clear] [-N|--notify] [--color] [--timings] [-q|--quiet] [--bell] [-h|--help] [-V|--version] [COMMANDE]

DESCRIPTION

Exécute des commandes lorsque les fichiers surveillés changent.

Surveille récursivement le répertoire courant pour détecter des changements, exécute la commande lorsqu'un changement dans le système de fichiers est détecté (parmi d'autres sources d'événements). Par défaut, watchexec utilise des mécanismes efficaces au niveau du noyau pour surveiller les changements.

Au démarrage, la commande spécifiée est exécutée une fois, et watchexec commence à surveiller les changements.

Exemples:

Reconstruire un projet lorsque les fichiers sources changent:

$ watchexec make

Surveiller tous les fichiers HTML, CSS et JavaScript pour les changements:

$ watchexec -e html,css,js make

Exécuter les tests lorsque les fichiers sources changent, en effaçant l'écran à chaque fois:

$ watchexec -c make test

Lancer et redémarrer un serveur Node.js:

$ watchexec -r node app.js

Surveiller les répertoires lib et src pour les changements, en reconstruisant à chaque fois:

$ watchexec -w lib -w src make

OPTIONS

--manual
Afficher la page de manuel

Ceci affiche la page de manuel pour Watchexec, si la sortie est un terminal et que le programme 'man' est disponible. Sinon, la page de manuel est imprimée sur stdout au format ROFF (adapté pour être écrit dans un fichier watchexec.1).

--completions=SHELL
Générer un script de complétion de shell

Fournit un script de complétion ou une configuration pour le shell donné. Si Watchexec n'est pas distribué avec des complétions pré-générées, vous pouvez l'utiliser pour les générer vous-même.

Shells supportés : bash, elvish, fish, nu, powershell, zsh.

--only-emit-events
Émettre uniquement les événements vers stdout, ne pas exécuter de commandes.

C'est une option de commodité pour utiliser Watchexec comme un surveillant de fichiers, sans exécuter de commandes. C'est presque équivalent à utiliser `cat` comme commande, sauf qu'il ne lancera pas de nouveau processus pour chaque événement.

Cette option implique `--emit-events-to=json-stdio`; vous pouvez également utiliser le mode texte en spécifiant `--emit-events-to=stdio`.

-h, --help
Afficher l'aide (voir un résumé avec '-h')
-V, --version
Afficher la version
[COMMANDE]
Commande (programme et arguments) à exécuter lors des changements

Elle est exécutée lorsque les événements passent les filtres et la période de temporisation (et une fois au démarrage, sauf si '--postpone' est donné). Si vous passez des drapeaux à la commande, vous devriez séparer avec -- bien que ce ne soit pas strictement requis.

Exemples:

$ watchexec -w src npm run build

$ watchexec -w src -- rsync -a src dest

Soyez prudent lorsque vous utilisez des jokers ou d'autres expansions de shell dans la commande. Votre shell peut les développer avant de les passer à Watchexec, et les résultats peuvent ne pas être ceux attendus. Comparez:

$ watchexec echo src/*.rs

$ watchexec echo 'src/*.rs'

$ watchexec --shell=none echo 'src/*.rs'

Le comportement dépend de la valeur de '--shell': pour tous sauf 'none', chaque partie de la commande est jointe en une seule chaîne avec un seul caractère espace ASCII, et donnée au shell comme décrit dans l'aide de '--shell'. Pour 'none', chaque élément distinct de la commande est passé comme convention execvp(3): le premier argument est le programme, en tant que chemin ou recherché dans la variable d'environnement 'PATH', le reste sont les arguments.

COMMANDE

--shell=SHELL
Utiliser un shell différent

Par défaut, Watchexec utilisera '$SHELL' s'il est défini ou un défaut de 'sh' sur les systèmes Unix, et soit 'pwsh', 'powershell', ou 'cmd' (CMD.EXE) sous Windows, selon le shell détecté par Watchexec.

Avec cette option, vous pouvez outrepasser cela et utiliser un shell différent, par exemple un avec plus de fonctionnalités ou un qui possède vos alias et fonctions personnalisés.

Si la valeur contient des espaces, elle est analysée comme une ligne de commande, et le premier mot est utilisé comme programme shell, avec le reste comme arguments du shell.

La commande est exécutée avec le drapeau '-c' (sauf pour 'cmd' sous Windows, où c'est '/C').

La valeur spéciale 'none' peut être utilisée pour désactiver totalement l'utilisation du shell. Dans ce cas, la commande fournie à Watchexec sera analysée, le premier mot étant l'exécutable et le reste étant les arguments, et exécutée directement. Notez que cette analyse est rudimentaire et peut ne pas fonctionner comme prévu dans tous les cas.

Utiliser 'none' est un peu plus efficace et peut permettre une interprétation plus stricte de l'entrée, mais cela signifie également que vous ne pouvez pas utiliser les fonctionnalités du shell comme le globbing, la redirection, le contrôle de flux, la logique, ou les pipes.

Exemples:

Utiliser sans shell:

$ watchexec -n -- zsh -x -o shwordsplit scr

Utiliser avec PowerShell Core:

$ watchexec --shell=pwsh -- Test-Connection localhost

Utiliser avec CMD.exe:

$ watchexec --shell=cmd -- dir

Utiliser avec un shell Unix différent:

$ watchexec --shell=bash -- 'echo $BASH_VERSION'

Utiliser avec un shell Unix et des options:

$ watchexec --shell='zsh -x -o shwordsplit' -- scr

-n
Raccourci pour '--shell=none'
-E, --env=CLE=VALEUR
Ajouter des variables d'environnement à la commande

C'est une option de commodité pour définir des variables d'environnement pour la commande, sans les définir pour le processus Watchexec lui-même.

Utilisez la syntaxe clé=valeur. Plusieurs variables peuvent être définies en répétant l'option.

--no-process-group
Ne pas utiliser de groupe de processus

Par défaut, Watchexec exécutera la commande dans un groupe de processus, afin que les signaux et les terminaisons soient envoyés à tous les processus du groupe. Parfois, ce n'est pas ce que vous voulez, et vous pouvez désactiver ce comportement avec cette option.

Obsolète, utilisez '--wrap-process=none' à la place.

--wrap-process=MODE [défaut: group]
Configurer comment le processus est encapsulé

Par défaut, Watchexec exécutera la commande dans une session sur Mac, dans un groupe de processus sous Unix, et dans un Job Object sous Windows.

Certains programmes Unix préfèrent s'exécuter dans une session, tandis que d'autres ne fonctionnent pas dans un groupe de processus.

Utilisez 'group' pour utiliser un groupe de processus, 'session' pour utiliser une session de processus, et 'none' pour exécuter la commande directement. Sous Windows, 'group' ou 'session' utiliseront un Job Object.

Watchexec Documentation

OPTIONS

--fail-fast
Fail immediately on error

By default, Watchexec will continue running even if the command it is managing exits with a non-zero status code. This option changes that, so that Watchexec will exit immediately if the command fails.

This is useful for build systems where you want to stop immediately if a compilation fails, for example.

--signal=SIGNAL
Signal to send to the command

This is used by 'signal' and 'restart' modes of '--on-busy-update' (unless '--stop-signal' is provided). The default on unix is "SIGTERM".

See the long documentation for '--stop-signal' for syntax.

--trace=FILE
Trace filesystem events

This option saves a trace of all filesystem events to the specified file. This can be invaluable for debugging issues where Watchexec doesn't seem to be reacting to changes as expected.

The format of the trace file is JSON, and each event is logged with its type, path, and timestamp.

If you find you need to specify this frequently for different kinds of programs, file an issue at https://github.com/watchexec/watchexec/issues. As errors of this nature are hard to debug and can be highly environment-dependent, reports from *multiple affected people* are more likely to be actioned promptly. Ask your friends/colleagues!

--stop-signal=SIGNAL
Signal to send to stop the command

This is used by 'restart' and 'signal' modes of '--on-busy-update' (unless '--signal' is provided). The restart behaviour is to send the signal, wait for the command to exit, and if it hasn't exited after some time (see '--timeout-stop'), forcefully terminate it.

The default on unix is "SIGTERM".

Input is parsed as a full signal name (like "SIGTERM"), a short signal name (like "TERM"), or a signal number (like "15"). All input is case-insensitive.

On Windows this option is technically supported but only supports the "KILL" event, as Watchexec cannot yet deliver other events. Windows doesn't have signals as such; instead it has termination (here called "KILL" or "STOP") and "CTRL+C", "CTRL+BREAK", and "CTRL+CLOSE" events. For portability the unix signals "SIGKILL", "SIGINT", "SIGTERM", and "SIGHUP" are respectively mapped to these.

--stop-timeout=TIMEOUT
Time to wait for the command to exit gracefully

This is used by the 'restart' mode of '--on-busy-update'. After the graceful stop signal is sent, Watchexec will wait for the command to exit. If it hasn't exited after this time, it is forcefully terminated.

Takes a unit-less value in seconds, or a time span value such as "5min 20s". Providing a unit-less value is deprecated and will warn; it will be an error in the future.

The default is 10 seconds. Set to 0 to immediately force-kill the command.

This has no practical effect on Windows as the command is always forcefully terminated; see '--stop-signal' for why.

--delay-run=DURATION
Sleep before running the command

This option will cause Watchexec to sleep for the specified amount of time before running the command, after an event is detected. This is like using "sleep 5 && command" in a shell, but portable and slightly more efficient.

Takes a unit-less value in seconds, or a time span value such as "2min 5s". Providing a unit-less value is deprecated and will warn; it will be an error in the future.

--workdir=DIRECTORY
Set the working directory

By default, the working directory of the command is the working directory of Watchexec. You can change that with this option. Note that paths may be less intuitive to use with this.

--socket=PORT
Provide a socket to the command

This implements the systemd socket-passing protocol, like with `systemfd`: sockets are opened from the watchexec process, and then passed to the commands it runs. This lets you keep sockets open and avoid address reuse issues or dropping packets.

This option can be supplied multiple times, to open multiple sockets.

The value can be either of `PORT` (opens a TCP listening socket at that port), `HOST:PORT` (specify a host IP address; IPv6 addresses can be specified `[bracketed]`), `TYPE::PORT` or `TYPE::HOST:PORT` (specify a socket type, `tcp` / `udp`).

This integration only provides basic support, if you want more control you should use the `systemfd` tool from https://github.com/mitsuhiko/systemfd, upon which this is based. The syntax here and the spawning behaviour is identical to `systemfd`, and both watchexec and systemfd are compatible implementations of the systemd socket-activation protocol.

Watchexec does _not_ set the `LISTEN_PID` variable on unix, which means any child process of your command could accidentally bind to the sockets, unless the `LISTEN_*` variables are removed from the environment.

EVENTS

-o, --on-busy-update=MODE
What to do when receiving events while the command is running

Default is to 'do-nothing', which ignores events while the command is running, so that changes that occur due to the command are ignored, like compilation outputs. You can also use 'queue' which will run the command once again when the current run has finished if any events occur while it's running, or 'restart', which terminates the running command and starts a new one. Finally, there's 'signal', which only sends a signal; this can be useful with programs that can reload their configuration without a full restart.

The signal can be specified with the '--signal' option.

-r, --restart
Restart the process if it's still running

This is a shorthand for '--on-busy-update=restart'.

-s, --signal=SIGNAL
Send a signal to the process when it's still running

Specify a signal to send to the process when it's still running. This implies '--on-busy-update=signal'; otherwise the signal used when that mode is 'restart' is controlled by '--stop-signal'.

See the long documentation for '--stop-signal' for syntax.

Signals are not supported on Windows at the moment, and will always be overridden to 'kill'. See '--stop-signal' for more on Windows "signals".

--map-signal=SIGNAL:SIGNAL
Translate signals from the OS to signals to send to the command

Takes a pair of signal names, separated by a colon, such as "TERM:INT" to map SIGTERM to SIGINT. The first signal is the one received by watchexec, and the second is the one sent to the command. The second can be omitted to discard the first signal, such as "TERM:" to not do anything on SIGTERM.

If SIGINT or SIGTERM are mapped, then they no longer quit Watchexec. Besides making it hard to quit Watchexec itself, this is useful to send pass a Ctrl-C to the command without also terminating Watchexec and the underlying program with it, e.g. with "INT:INT".

This option can be specified multiple times to map multiple signals.

Signal syntax is case-insensitive for short names (like "TERM", "USR2") and long names (like "SIGKILL", "SIGHUP"). Signal numbers are also supported (like "15", "31"). On Windows, the forms "STOP", "CTRL+C", and "CTRL+BREAK" are also supported to receive, but Watchexec cannot yet deliver other "signals" than a STOP.

-d, --debounce=TIMEOUT
Time to wait for new events before taking action

When an event is received, Watchexec will wait for up to this amount of time before handling it (such as running the command). This is essential as what you might perceive as a single change may actually emit many events, and without this behaviour, Watchexec would run much too often. Additionally, it's not infrequent that file writes are not atomic, and each write may emit an event, so this is a good way to avoid running a command while a file is partially written.

An alternative use is to set a high value (like "30min" or longer), to save power or bandwidth on intensive tasks, like an ad-hoc backup script. In those use cases, note that every accumulated event will build up in memory.

Takes a unit-less value in milliseconds, or a time span value such as "5sec 20ms". Providing a unit-less value is deprecated and will warn; it will be an error in the future.

The default is 50 milliseconds. Setting to 0 is highly discouraged.

--stdin-quit
Exit when stdin closes

This watches the stdin file descriptor for EOF, and exits Watchexec gracefully when it is closed. This is used by some process managers to avoid leaving zombie processes around.

-p, --postpone
Wait until first change before running command

By default, Watchexec will run the command once immediately. With this option, it will instead wait until an event is detected before running the command as normal.

--poll=INTERVAL
Poll for filesystem changes

By default, and where available, Watchexec uses the operating system's native file system watching capabilities. This option disables that and instead uses a polling mechanism, which is less efficient but can work around issues with some file systems (like network shares) or edge cases.

Optionally takes a unit-less value in milliseconds, or a time span value such as "2s 500ms", to use as the polling interval. If not specified, the default is 30 seconds. Providing a unit-less value is deprecated and will warn; it will be an error in the future.

Aliased as '--force-poll'.

ÉMETTEURS D'ÉVÉNEMENTS

-e, --event=MODE
Specify how events are emitted

When filesystem events occur, Watchexec needs to know which path changed. This can be tricky, as some events might occur without a clear path attached (like signals or key events), some events might indicate a file was modified without knowing which one, and rename events might be difficult to interpret. It's not always possible to know which path is the old or new one for "half" renames (only the original, only the new), "unknown" renames (the change was a rename, but whether it was the old or new is unknown), renames might split across two debounce boundaries, and so on.

This option controls where that information is emitted. It defaults to 'none', which doesn't emit event information at all. The other options are 'environment' (deprecated), 'stdio', 'file', 'json-stdio', and 'json-file'.

The 'stdio' and 'file' modes are text-based: 'stdio' writes absolute paths to the stdin of the command, one per line, each prefixed with `create:`, `remove:`, `rename:`, `modify:`, or `other:`, then closes the handle; 'file' writes the same thing to a temporary file, and its path is given with the $WATCHEXEC_EVENTS_FILE environment variable.

There are also two JSON modes, which are based on JSON objects and can represent the full set of events Watchexec handles. Here's an example of a folder being created on Linux:

```json
{
"tags": [
{
"kind": "path",
"absolute": "/home/user/your/new-folder",
"filetype": "dir"
},
{
"kind": "fs",
"simple": "create",
"full": "Create(Folder)"
},
{
"kind": "source",
"source": "filesystem",
}
],
"metadata": {
"notify-backend": "inotify"
}
} ```

The fields are as follows:


- `tags`, structured event data.
- `tags[].kind`, which can be:
* 'path', along with:
+ `absolute`, an absolute path.
+ `filetype`, a file type if known ('dir', 'file', 'symlink', 'other').
* 'fs':
+ `simple`, the "simple" event type ('access', 'create', 'modify', 'remove', or 'other').
+ `full`, the "full" event type, which is too complex to fully describe here, but looks like 'General(Precise(Specific))'.
* 'source', along with:
+ `source`, the source of the event ('filesystem', 'keyboard', 'mouse', 'os', 'time', 'internal').
* 'keyboard', along with:
+ `keycode`. Currently only the value 'eof' is supported.
* 'process', for events caused by processes:
+ `pid`, the process ID.
* 'signal', for signals sent to Watchexec:
+ `signal`, the normalised signal name ('hangup', 'interrupt', 'quit', 'terminate', 'user1', 'user2').
* 'completion', for when a command ends:
+ `disposition`, the exit disposition ('success', 'error', 'signal', 'stop', 'exception', 'continued').
+ `code`, the exit, signal, stop, or exception code.
- `metadata`, additional information about the event.

The 'json-stdio' mode will emit JSON events to the standard input of the command, one per line, then close stdin. The 'json-file' mode will create a temporary file, write the events to it, and provide the path to the file with the $WATCHEXEC_EVENTS_FILE environment variable.

Finally, the 'environment' mode was the default until 2.0. It sets environment variables with the paths of the affected files, for filesystem events:

$WATCHEXEC_COMMON_PATH is set to the longest common path of all of the below variables, and so should be prepended to each path to obtain the full/real path. Then:


- $WATCHEXEC_CREATED_PATH is set when files/folders were created
- $WATCHEXEC_REMOVED_PATH is set when files/folders were removed
- $WATCHEXEC_RENAMED_PATH is set when files/folders were renamed
- $WATCHEXEC_WRITTEN_PATH is set when files/folders were modified
- $WATCHEXEC_META_CHANGED_PATH is set when files/folders' metadata were modified
- $WATCHEXEC_OTHERWISE_CHANGED_PATH is set for every other kind of pathed event

Multiple paths are separated by the system path separator, ';' on Windows and ':' on unix. Within each variable, paths are deduplicated and sorted in binary order (i.e. neither Unicode nor locale aware).

This is the legacy mode, is deprecated, and will be removed in the future. The environment is a very restricted space, while also limited in what it can usefully represent. Large numbers of files will either cause the environment to be truncated, or may error or crash the process entirely. The $WATCHEXEC_COMMON_PATH is also unintuitive, as demonstrated by the multiple confused queries that have landed in my inbox over the years.

FILTRAGE

-w, --watch=CHEMIN
Surveiller un fichier ou un répertoire spécifique

Par défaut, Watchexec surveille le répertoire courant.

Lorsque vous surveillez un seul fichier, il est souvent préférable de surveiller le répertoire contenant plutôt que de filtrer sur le nom du fichier. Certains éditeurs peuvent remplacer le fichier par un nouveau lors de la sauvegarde, et certaines plateformes peuvent ne pas détecter cela ou d'autres modifications.

Au démarrage, Watchexec résout une "origine de projet" à partir des chemins surveillés. Voir l'aide de '--project-origin' pour plus d'informations.

Cette option peut être spécifiée plusieurs fois pour surveiller plusieurs fichiers ou répertoires.

La valeur spéciale '/dev/null', fournie comme seul chemin surveillé, amènera Watchexec à ne surveiller aucun chemin. D'autres sources d'événements (comme les signaux ou les événements clavier) peuvent toujours être utilisées.

-W, --watch-non-recursive=CHEMIN
Surveiller un répertoire spécifique, de manière non récursive

Contrairement à '-w', les répertoires surveillés avec cette option ne sont pas parcourus de manière récursive.

Cette option peut être spécifiée plusieurs fois pour surveiller plusieurs répertoires de manière non récursive.

-F, --watch-file=CHEMIN
Surveiller les fichiers et répertoires à partir d'un fichier

Chaque ligne du fichier sera interprétée comme si elle était fournie à '-w'.

Pour des utilisations plus complexes (comme la surveillance non récursive), utilisez la capacité de fichier d'arguments : construisez un fichier contenant les options de ligne de commande et passez-le à watchexec avec `@chemin/vers/fichier_arguments`.

La valeur spéciale '-' lira depuis STDIN ; ceci est incompatible avec '--stdin-quit'.

--no-vcs-ignore
Ne pas charger les fichiers .gitignore

Parmi d'autres fichiers d'exclusion de VCS, comme pour Mercurial, Subversion, Bazaar, DARCS, Fossil. Notez que Watchexec détectera lequel de ceux-ci est utilisé, le cas échéant, et ne chargera que les fichiers pertinents. Les fichiers globaux (comme '~/.gitignore') et locaux (comme '.gitignore') sont pris en compte.

Cette option est utile si vous souhaitez surveiller des fichiers qui sont ignorés par Git.

--no-project-ignore
Ne pas charger les ignorés locaux du projet

Ceci désactive le chargement des fichiers d'ignorés locaux du projet, tels que '.gitignore' ou '.ignore' dans le projet surveillé. Ceci est contrasté avec '--no-vcs-ignore', qui désactive le chargement des fichiers d'ignorés Git et autres VCS, et avec '--no-global-ignore', qui désactive le chargement des fichiers d'ignorés globaux ou utilisateur, comme '~/.gitignore' ou '~/.config/watchexec/ignore'.

Fichiers d'ignorés de projet pris en charge :


- Git : .gitignore à la racine du projet et dans les sous-répertoires, .git/info/exclude, et le fichier pointé par `core.excludesFile` dans .git/config.
- Mercurial : .hgignore à la racine du projet et dans les sous-répertoires.
- Bazaar : .bzrignore à la racine du projet.
- Darcs : _darcs/prefs/boring
- Fossil : .fossil-settings/ignore-glob
- Ripgrep/Watchexec/générique : .ignore à la racine du projet et dans les sous-répertoires.

Les fichiers d'ignorés VCS (Git, Mercurial, Bazaar, Darcs, Fossil) ne sont utilisés que si le VCS correspondant est détecté comme étant utilisé pour le projet/l'origine. Par exemple, un .bzrignore dans un dépôt Git sera rejeté.

--no-global-ignore
Ne pas charger les ignorés globaux

Ceci désactive le chargement des fichiers d'ignorés globaux ou utilisateur, tels que '~/.gitignore', '~/.config/watchexec/ignore', ou '%APPDATA%\Bazzar\2.0\ignore'. Contraste avec '--no-vcs-ignore' et '--no-project-ignore'.

Fichiers d'ignorés globaux pris en charge


- Git (si core.excludesFile est défini) : le fichier à ce chemin
- Git (sinon) : le premier trouvé parmi $XDG_CONFIG_HOME/git/ignore, %APPDATA%/.gitignore, %USERPROFILE%/.gitignore, $HOME/.config/git/ignore, $HOME/.gitignore.
- Bazaar : le premier trouvé parmi %APPDATA%/Bazzar/2.0/ignore, $HOME/.bazaar/ignore.
- Watchexec : le premier trouvé parmi $XDG_CONFIG_HOME/watchexec/ignore, %APPDATA%/watchexec/ignore, %USERPROFILE%/.watchexec/ignore, $HOME/.watchexec/ignore.

Comme pour les fichiers de projet, les fichiers globaux Git et Bazaar ne seront utilisés que pour le VCS correspondant tel qu'utilisé dans le projet.

--no-default-ignore
Ne pas utiliser les ignorés par défaut internes

Watchexec dispose d'un ensemble de modèles d'ignorés par défaut, tels que les fichiers d'échange d'éditeur, `*.pyc`, `*.pyo`, `.DS_Store`, `.bzr`, `_darcs`, `.fossil-settings`, `.git`, `.hg`, `.pijul`, `.svn`, et les fichiers journaux de Watchexec.

--no-discover-ignore
Ne pas découvrir du tout les fichiers d'ignorés

Ceci est un raccourci pour '--no-global-ignore', '--no-vcs-ignore', '--no-project-ignore', mais encore plus efficace car il ignorera tous les mécanismes de découverte d'ignorés dès le départ.

Notez que les ignorés par défaut sont toujours chargés, voir '--no-default-ignore'.

Ceci est un raccourci pour '--no-discover-ignore', '--no-

'.

Notez que les ignorés chargés explicitement via d'autres options de ligne de commande, tels que '--ignore' ou '--ignore-file', seront toujours utilisés.

-e, --exts=EXTENSIONS
Extensions de nom de fichier pour filtrer

Ceci est un filtre rapide pour n'émettre des événements que pour les fichiers avec les extensions données. Les extensions peuvent être données avec ou sans le point initial (par exemple, 'js' ou '.js'). Plusieurs extensions peuvent être données en répétant l'option ou en les séparant par des virgules.

-f, --filter=PATTERN
Motifs de nom de fichier pour filtrer

Fournissez un motif de type glob, et seuls les événements pour les fichiers correspondant au motif seront émis. Plusieurs motifs peuvent être donnés en répétant l'option. Les événements qui ne proviennent pas de fichiers (par exemple, signaux, événements clavier) passeront intacts.

--filter-file=PATH
Fichiers pour charger les filtres

Fournissez un chemin vers un fichier contenant des filtres, un par ligne. Les lignes vides et les lignes commençant par '#' sont ignorées. Utilise le même format de motif que l'option '--filter'.

Ceci peut également être utilisé via la variable d'environnement $WATCHEXEC_FILTER_FILES.

--project-origin=DIRECTORY
Définir l'origine du projet

Watchexec tentera de découvrir l'"origine" (ou la "racine") du projet en recherchant une variété de marqueurs, tels que des fichiers ou des motifs de répertoire. Il fait de son mieux mais se trompe parfois, et vous pouvez outrepasser cela avec cette option.

L'origine du projet est utilisée pour déterminer le chemin de certains fichiers d'ignorés, quel VCS est utilisé, la signification d'un '/' initial dans les motifs de filtrage, et peut-être plus à l'avenir.

Lorsqu'elle est définie, Watchexec n'essaiera pas de rechercher, ce qui peut être significativement plus rapide.

-j, --filter-prog=EXPRESSION
Programmes de filtrage.

Fournissez vos propres programmes de filtrage personnalisés en syntaxe jaq (similaire à jq). Les programmes reçoivent un événement dans le même format que celui décrit dans '--emit-events-to' et doivent renvoyer une valeur booléenne. Les programmes invalides feront échouer le démarrage de watchexec ; utilisez '-v' pour voir les erreurs d'exécution du programme.

En plus de la bibliothèque standard jaq, watchexec ajoute quelques définitions de filtre personnalisées :

- 'path | file_meta' renvoie les métadonnées du fichier ou null si le fichier n'existe pas.

- 'path | file_size' renvoie la taille du fichier à l'emplacement path, ou null s'il n'existe pas.

- 'path | file_read(bytes)' renvoie une chaîne avec les n premiers octets du fichier à l'emplacement path. Si le fichier est plus petit que n octets, le fichier entier est renvoyé. Il n'y a pas de filtre pour lire le fichier entier en une seule fois afin d'encourager la limitation de la quantité de données lues et traitées.

- 'string | hash', et 'path | file_hash' renvoient le hachage de la chaîne ou du fichier à l'emplacement path. Aucune garantie n'est faite concernant l'algorithme utilisé : considérez-le comme une valeur opaque.

- 'any | kv_store(key)', 'kv_fetch(key)', et 'kv_clear' fournissent un simple magasin clé-valeur. Les données sont conservées en mémoire uniquement, il n'y a pas de persistance. La cohérence n'est pas garantie.

- 'any | printout', 'any | printerr', et 'any | log(level)' afficheront ou enregistreront toute valeur donnée sur stdout, stderr, ou le log (niveaux = error, warn, info, debug, trace), et transmettront la valeur (ainsi '[1] | log("debug") | .[]' produira un '1' et enregistrera '[1]').

Tout filtrage effectué avec de tels programmes, et en particulier ceux utilisant l'accès kv ou au système de fichiers, est beaucoup plus lent que les autres méthodes de filtrage. Si le filtrage est trop lent, les événements s'accumuleront et ralentiront watchexec. Soyez prudent lors de la conception de vos filtres.

Si l'argument de cette option commence par '@', le reste de l'argument est considéré comme le chemin d'un fichier contenant un programme jaq.

Les programmes Jaq sont exécutés dans l'ordre, après tous les autres filtres, et s'arrêtent prématurément : si un filtre (jaq ou non) rejette un événement, l'exécution s'arrête là, et aucun autre filtre n'est exécuté. De plus, ils s'arrêtent après avoir affiché la première valeur, vous voudrez donc utiliser 'any' ou 'all' lors de l'itération, sinon seul le premier élément sera traité, ce qui peut être assez déroutant !

Trouvez des programmes contribués par les utilisateurs ou soumettez les vôtres utiles sur https://github.com/watchexec/watchexec/discussions/592.

## Exemples :

Filtre d'ignoré par expression régulière sur les chemins :

'all(.tags[] | select(.kind == "path"); .absolute | test("[.]test[.]js$")) | not'

Autoriser tout événement qui crée un fichier :

'any(.tags[] | select(.kind == "fs"); .simple == "create")'

Autoriser les événements qui touchent des fichiers exécutables :

'any(.tags[] | select(.kind == "path" && .filetype == "file"); .absolute | metadata | .executable)'

Ignorer les fichiers qui commencent par des shebangs :

'any(.tags[] | select(.kind == "path" && .filetype == "file"); .absolute | read(2) == "#!") | not'

-i, --ignore=PATTERN
Motifs de nom de fichier à ignorer

Fournissez un motif de type glob, et les événements pour les fichiers correspondant au motif seront exclus. Plusieurs motifs peuvent être donnés en répétant l'option. Les événements qui ne proviennent pas de fichiers (par exemple, signaux, événements clavier) passeront intacts.

--ignore-file=PATH
Fichiers pour charger les ignorés

Fournissez un chemin vers un fichier contenant des ignorés, un par ligne. Les lignes vides et les lignes commençant par '#' sont ignorées. Utilise le même format de motif que l'option '--ignore'.

Ceci peut également être utilisé via la variable d'environnement $WATCHEXEC_IGNORE_FILES.

--fs-events=EVENTS
Événements du système de fichiers pour filtrer

Ceci est un filtre rapide pour n'émettre des événements que pour les types de changements du système de fichiers donnés. Choisissez parmi 'access', 'create', 'remove', 'rename', 'modify', 'metadata'. Plusieurs types peuvent être donnés en répétant l'option ou en les séparant par des virgules. Par défaut, il s'agit de tous les types sauf 'access'.

Ceci peut appliquer un filtrage au niveau du noyau lorsque possible, ce qui peut être plus efficace, mais peut être plus déroutant lors de la lecture des logs.

--no-meta
Ne pas émettre d'événements fs pour les changements de métadonnées

Ceci est un raccourci pour '--fs-events create,remove,rename,modify'. L'utiliser en conjonction avec l'option '--fs-events' n'a pas de sens et n'est pas autorisé.

DÉBOGAGE

-v, --verbose
Définir le niveau de log de diagnostic

Ceci active la journalisation de diagnostic, utile pour enquêter sur des bugs ou pour mieux comprendre des filtres défectueux ou des événements "manquants". Utilisez plusieurs fois pour augmenter la verbeuxité.

Va jusqu'à '-vvvv'. Lors de la soumission de rapports de bugs, utilisez un niveau de log '-vvv' par défaut.

Vous voudrez peut-être l'utiliser avec '--log-file' pour éviter de polluer votre terminal.

Définir $WATCHEXEC_LOG fonctionne également, et a la priorité, mais n'est pas recommandé. Cependant, utiliser $WATCHEXEC_LOG est le seul moyen d'obtenir des logs avant que ces options ne soient analysées.

--log-file=PATH
Écrire les logs de diagnostic dans un fichier

Ceci écrit les logs de diagnostic dans un fichier, au lieu du terminal, au format JSON. Si aucun niveau de log n'a été spécifié auparavant, celui-ci sera défini sur '-vvv'.

Si aucun chemin n'est fourni, la valeur par défaut est le répertoire courant. Notez qu'avec '--ignore-nothing', les événements d'écriture dans le log seront probablement capturés par Watchexec, provoquant une boucle ; préférez définir un chemin en dehors du répertoire surveillé.

Si le chemin fourni est un répertoire, un fichier sera créé dans ce répertoire. Le nom du fichier sera la date et l'heure actuelles, au format 'watchexec.YYYY-MM-DDTHH-MM-SSZ.log'.

--print-events
Afficher les événements qui déclenchent des actions

Ceci affiche les événements qui ont déclenché l'action lors de son traitement (après détection), sous une forme lisible par l'homme. Ceci est utile pour le débogage des filtres.

Utilisez '-vvv' à la place lorsque vous avez besoin de plus d'informations de diagnostic.

SORTIE

-c, --clear=MODE
Effacer l'écran avant d'exécuter la commande

Si cela n'efface pas complètement l'écran, essayez '--clear=reset'.

-N, --notify
Alerter au démarrage et à la fin des commandes

Avec cela, Watchexec émettra une notification de bureau lorsqu'une commande démarre et se termine, sur les plateformes prises en charge. Sur les plateformes non prises en charge, il peut silencieusement ne rien faire, ou enregistrer un avertissement.

--color=MODE [défaut : auto]
Quand utiliser les couleurs du terminal

Définir la variable d'environnement `NO_COLOR` à n'importe quelle valeur est équivalent à `--color=never`.

--timings
Afficher combien de temps la commande a pris pour s'exécuter

Cela peut ne pas être totalement précis, car cela inclut une certaine surcharge de Watchexec lui-même. Utilisez l'utilitaire `time`, des minuteurs de haute précision ou des outils de benchmarking pour des résultats plus précis.

-q, --quiet
Ne pas afficher les messages de démarrage et d'arrêt

Par défaut, Watchexec affichera un message lors du démarrage et de l'arrêt de la commande. Cette option désactive ce comportement, de sorte que seule la sortie de la commande, les avertissements et les erreurs seront affichés.

--bell
Sonner la cloche du terminal à la fin de la commande

NAME

watchexec — a general-purpose file watcher that executes commands when files change

SYNOPSIS

watchexec [OPTIONS] [COMMAND]

DESCRIPTION

watchexec is a command-line tool that watches for file changes in the current directory (or specified paths) and runs a command when a change is detected.

It is designed to be simple, fast, and highly configurable. It can be used for tasks like automatically recompiling code, refreshing web pages, or running tests whenever source files are modified.

OPTIONS

-h, --help
Show help message and exit.
-v, --version
Show version and exit.
-w, --watch PATH
Watch the given path (file or directory). Can be used multiple times. Defaults to current directory.
-i, --ignore PATTERN
Ignore files matching the given glob pattern. Can be used multiple times. Defaults to ignoring hidden files and the .git directory.
-e, --ext EXTENSION
Watch files with the given extension. Defaults to watching all files.
-d, --debounce MILLISECONDS
Set the debounce interval in milliseconds. This prevents rapid re-triggering of the command if multiple files change quickly. Defaults to 50ms.
-p, --poll
Use polling instead of filesystem events. This can be useful on systems where filesystem events are unreliable.
-f, --force
Execute the command immediately on startup, even if no files have changed.
-s, --signal SIGNAL
Send the specified signal to the command instead of SIGTERM when it needs to be restarted. Defaults to SIGTERM.
-k, --kill
Kill the command process when changes are detected, instead of restarting it.
-t, --once
Exit after the first command execution, even if more changes occur.
--filter FILE
Load filtering rules from a file.
--templates FILE
Load event templates from a file.
--no-ignore
Do not use the default ignore patterns.
--log-file FILE
Write logs to the specified file.
--log-level LEVEL
Set the log level (e.g., debug, info, warn, error).
--argfile FILE
Use the specified file as an argument file. Arguments are read one per line and inserted in place of the file argument. Further arguments on the CLI will override or add onto those in the file.

Didn't expect this much output? Use the short '-h' flag to get short help.

COMMAND

The command to execute when files change. If no command is provided, watchexec will simply print the detected changes.

The command can use environment variables to access information about the detected changes, such as:

WATCHEXEC_EVENT_FILE_NAME
The name of the file that triggered the event.
WATCHEXEC_EVENT_PATH
The full path of the file that triggered the event.
WATCHEXEC_EVENT_TYPE
The type of event (e.g., `modify`, `create`, `delete`).
WATCHEXEC_EVENTS_COUNT
The number of events that occurred.

EVENTS

watchexec watches for the following filesystem events:

  • `create`: A file or directory was created.
  • `delete`: A file or directory was deleted.
  • `modify`: A file's content was modified.
  • `rename`: A file or directory was renamed.

FILTERING

By default, watchexec ignores hidden files (those starting with a dot) and the contents of the .git directory. You can customize this behavior using the -i flag or by providing a filter file with the --filter option.

Filter patterns use glob syntax.

DEBUGGING

To enable debug logging, use the --log-level debug option.

OUTPUT

By default, watchexec outputs logs and command output to standard error. Use the --log-file option to redirect logs to a file.

Use @argfile as first argument to load arguments from the file 'argfile' (one argument per line) which will be inserted in place of the @argfile (further arguments on the CLI will override or add onto those in the file).

Didn't expect this much output? Use the short '-h' flag to get short help.
