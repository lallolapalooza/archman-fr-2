Paquet: wimlib

Licences: custom

WIMCAPTURE(1) Commandes utilisateur WIMCAPTURE(1)

NOM

wimcapture, wimappend - Capturer ou ajouter une image WIM

SYNTAXE

wimcapture SOURCE WIMFILE [NOM_IMAGE  [DESC_IMAGE]] [OPTION...]
wimappend SOURCE WIMFILE [NOM_IMAGE  [DESC_IMAGE]] [OPTION...]

DESCRIPTION

Les commandes wimcapture (équivalemment : wimlib-imagex capture) et wimappend (équivalemment : wimlib-imagex append) créent ("capturent") une nouvelle image Windows Imaging (WIM). wimcapture crée une nouvelle archive WIM WIMFILE pour contenir la nouvelle image, tandis que wimappend ajoute l'image à l'archive WIM existante WIMFILE (ou avec --create, en la créant si nécessaire).

SOURCE spécifie l'emplacement des fichiers à partir desquels créer l'image WIM. Si SOURCE est un répertoire ou un lien symbolique pointant vers un répertoire, alors l'image est capturée à partir de ce répertoire conformément à CAPTURE DE RÉPERTOIRE (UNIX) ou CAPTURE DE RÉPERTOIRE (WINDOWS). Alternativement, si --source-list est spécifié, alors SOURCE est interprété comme un fichier contenant une liste de fichiers et de répertoires à inclure dans l'image. Toujours alternativement, si SOURCE est un périphérique bloc UNIX, alors une image est capturée à partir du volume NTFS qu'il contient conformément à CAPTURE DE VOLUME NTFS (UNIX).

NOM_IMAGE et DESC_IMAGE spécifient le nom et la description à donner à la nouvelle image. Si NOM_IMAGE n'est pas spécifié, il prend par défaut le composant nom de fichier de SOURCE, en ajoutant un suffixe unique si nécessaire. Sinon, NOM_IMAGE doit être soit un nom non déjà utilisé par une image dans WIMFILE, soit la chaîne vide pour créer une image sans nom. Si DESC_IMAGE n'est pas spécifié, la nouvelle image n'a pas de description.

Si WIMFILE est spécifié comme "-", alors l'option --pipable est supposée et une WIM pipable est écrite en sortie standard (il s'agit d'une extension de wimlib).

CAPTURE DE RÉPERTOIRE (UNIX)

Sur les systèmes de type UNIX, si SOURCE spécifie un répertoire ou un lien symbolique vers un répertoire, alors l'image WIM sera capturée à partir de ce répertoire. Le répertoire peut être sur n'importe quel type de système de fichiers, et les points de montage sont suivis. Dans ce mode, les types d'informations suivants sont capturés :

•
Répertoires et fichiers réguliers, et le contenu des fichiers réguliers
•
Liens physiques
•
Liens symboliques (traduits de manière sans perte en points d'analyse sous Windows)
•
Dates de dernière modification (mtime) et de dernier accès (atime) avec une granularité de 100 nanosecondes
•
Les fichiers qui semblent être épars seront marqués comme tels, mais leur contenu complet sera toujours stocké, soumis à la compression habituelle.
•
Avec --unix-data : permissions de fichiers UNIX standard (propriétaire, groupe et mode)
•
Avec --unix-data : nœuds de périphériques, tubes nommés et sockets
•
Avec --unix-data : attributs étendus (Linux uniquement)

Il n'y a pas de prise en charge pour stocker les dates de dernière modification d'état (ctime), ni les informations de lien physique pour les liens symboliques (chaque lien symbolique sera stocké comme un fichier distinct). De plus, les noms de fichiers et les cibles de liens symboliques qui ne sont pas en UTF-8 valide avec l'ajout de points de code de substitution ne sont pas pris en charge. Notez que si vous avez un système de fichiers contenant des noms de fichiers dans un autre encodage multibyte, tel que l'ISO-8859-1, et que vous souhaitez l'archiver avec wimlib, vous pourrez peut-être le monter avec une option qui fait que ses noms de fichiers soient présentés en UTF-8.

CAPTURE DE VOLUME NTFS (UNIX)

Sur les systèmes de type UNIX, SOURCE peut également être spécifié comme un périphérique bloc (par exemple /dev/sda3) contenant un volume NTFS non monté. Dans ce mode, wimcapture utilise libntfs-3g pour capturer une image WIM à partir du répertoire racine du volume NTFS. Dans ce mode, autant de données et métadonnées que possible sont capturées, y compris les métadonnées spécifiques à NTFS et à Windows :

•
Tous les flux de données de tous les fichiers non chiffrés, y compris le flux de données sans nom ainsi que tous les flux de données nommés.
•
Points d'analyse. Voir POINTS D'ANALYSE ET LIENS SYMBOLIQUES pour plus de détails.
•
Horodatages de création, d'accès et de modification de fichiers et répertoires, utilisant la résolution native de NTFS de 100 nanosecondes.
•
Descripteurs de sécurité Windows, y compris tous les composants (propriétaire, groupe, DACL et SACL).
•
Attributs de fichiers DOS/Windows.
•
Tous les noms de tous les fichiers, y compris les noms dans l'espace de noms Win32, l'espace de noms DOS, l'espace de noms Win32+DOS et l'espace de noms POSIX. Cela inclut les liens physiques.
•
Identifiants d'objet.

Cependant, les principales limitations de ce mode sont :

•
Les fichiers chiffrés sont exclus.
•
Les attributs étendus (EA) ne sont pas encore stockés.
•
Les fichiers épars seront marqués comme tels, mais leur contenu complet sera toujours stocké, soumis à la compression habituelle.
•
Certains types de points d'analyse sont transparentement déréférencés par Windows mais pas par NTFS-3G. Voir POINTS D'ANALYSE ET LIENS SYMBOLIQUES.

Notez que ce mode utilise libntfs-3g directement, sans passer par le pilote ntfs-3g(8). Par conséquent, il n'y a pas de prise en charge spéciale pour capturer une image WIM à partir d'un répertoire sur lequel un système de fichiers NTFS a été monté à l'aide de ntfs-3g(8) ; vous devez d'abord le démonter. Il n'y a pas non plus de prise en charge pour capturer un sous-répertoire du volume NTFS ; vous ne pouvez capturer que le volume complet.

CAPTURE DE RÉPERTOIRE (WINDOWS)

Sous Windows, wimcapture et wimappend prennent en charge nativement les données spécifiques à Windows et à NTFS. Ils agissent donc de manière similaire aux commandes correspondantes d'ImageX ou de DISM de Microsoft. Pour de meilleurs résultats, le répertoire capturé doit être sur un volume NTFS et le programme doit être exécuté avec des privilèges d'administrateur ; cependant, les systèmes de fichiers non-NTFS et l'exécution sans privilèges d'administrateur sont également pris en charge, sous réserve de limitations.

Sous Windows, wimcapture et wimappend tentent de capturer autant de données et de métadonnées que possible, y compris :

•
Tous les flux de données de tous les fichiers.
•
Points d'analyse, si pris en charge par le système de fichiers source. Voir POINTS D'ANALYSE ET LIENS SYMBOLIQUES pour plus de détails.
•
Horodatages de création, d'accès et de modification de fichiers et de répertoires. Ceux-ci sont stockés avec la résolution d'horodatage native de Windows de 100 nanosecondes.
•
Descripteurs de sécurité, si pris en charge par le système de fichiers source et si --no-acls n'est pas spécifié. Remarque : lorsque vous ne vous exécutez pas en tant qu'administrateur, les descripteurs de sécurité peuvent être capturés partiellement seulement (voir --strict-acls).
•
Attributs de fichiers, y compris caché, épars, compressé, chiffré, etc. Les fichiers chiffrés seront stockés sous forme chiffrée plutôt qu'en texte brut. Les fichiers transparentement compressés seront lus décompressés et stockés sous réserve de la propre compression du WIM. Il n'y a pas de traitement spécial pour stocker les fichiers épars, mais ils compresseront probablement en une petite taille.
•
Noms DOS (8.3) des fichiers ; cependant, l'échec de leur lecture n'est pas considéré comme une condition d'erreur.
•
Liens physiques, si pris en charge par le système de fichiers source.
•
Identifiants d'objet, si pris en charge par le système de fichiers source.
•
Attributs étendus (EA), si pris en charge par le système de fichiers source.

POINTS D'ANALYSE ET LIENS SYMBOLIQUES

Un "lien symbolique" (ou "symlink") est un fichier spécial qui "pointe vers" un autre fichier ou répertoire. Sous Windows, un "point d'analyse" est une généralisation d'un lien symbolique qui permet de rediriger l'accès à un fichier ou répertoire d'une manière plus complexe. Windows utilise les points d'analyse pour implémenter les liens symboliques et les utilise parfois pour diverses autres fonctionnalités. Le comportement par défaut de wimcapture est que les points de réanalyse et les liens symboliques ne sont *pas* déréférencés, ce qui signifie que les points de réanalyse ou les liens symboliques eux-mêmes sont stockés dans l'archive plutôt que les fichiers ou les données auxquels ils pointent. Il existe une option --dereference, mais elle n'est actuellement prise en charge que par la version UNIX de wimcapture sur les systèmes de fichiers UNIX (elle n'est pas encore implémentée pour les systèmes de fichiers Windows).

Windows traite également certains types de points de réanalyse de manière spéciale. Par exemple, les applications Windows lisant des fichiers dédupliqués, basés sur WIM ou compressés par le système voient toujours les données déréférencées, même si elles demandent le contraire. Par conséquent, wimcapture sous Windows stockera ces fichiers déréférencés, et non comme des points de réanalyse. Mais wimcapture sous UNIX en mode NTFS-3G ne peut pas déréférencer ces fichiers et les stockera comme des points de réanalyse à la place. Cette différence peut être significative dans certaines situations, par exemple lors de la capture de fichiers dédupliqués qui, pour être lisibles après extraction, nécessitent que le magasin de blocs soit également présent.

OPTIONS

--boot
Marque la nouvelle image comme l'image "amorçable" du WIM. L'image "amorçable" est l'image que le chargeur de démarrage Windows utilisera lors du chargement de Windows PE à partir du WIM.
--check
Inclut des informations d'intégrité supplémentaires dans le fichier WIM résultant. Avec wimappend, vérifie également l'intégrité du WIM avant d'y ajouter des données. Vérifie également l'intégrité de tous les WIM spécifiés par --update-of et/ou --delta-from.
--include-integrity
Inclut des informations d'intégrité supplémentaires dans le fichier WIM résultant, c'est-à-dire comme --check mais sans aucune vérification préalable.
--compress=TYPE[:LEVEL]
Avec wimcapture, utilise le format de compression spécifié dans le nouveau fichier WIM. TYPE peut être "none", "XPRESS" (alias : "fast"), "LZX" (alias : "maximum"), ou "LZMS" (alias : "recovery"). TYPE est insensible à la casse. La valeur par défaut est "LZX".
Vous pouvez éventuellement spécifier également un entier pour le niveau de compression LEVEL. Le niveau de compression spécifie l'effort que l'algorithme de compression pour le TYPE de compression spécifié consacrera à la compression des données. Les valeurs sont mises à l'échelle de sorte que 20 représente une compression rapide, 50 une compression moyenne et 100 une compression élevée. Cependant, vous pouvez choisir n'importe quelle valeur et pas seulement ces valeurs particulières. La valeur par défaut est 50.
Cette option affecte uniquement le type de compression utilisé dans les ressources WIM non solides. Si vous créez un WIM solide (en utilisant l'option --solid), vous voudrez probablement utiliser --solid-compress à la place.
Soyez prudent si vous choisissez la compression LZMS. Elle n'est pas compatible avec wimlib avant la v1.6.0, WIMGAPI avant Windows 8, DISM avant Windows 8.1, et 7-Zip avant la v15.12. Notez également que le choix de la compression LZMS n'implique pas automatiquement la compression en mode solide, comme c'est le cas avec DISM. Utilisez --solid si vous souhaitez créer un WIM solide, ou un fichier "ESD".
--chunk-size=SIZE
Avec wimcapture, utilise une taille de bloc de compression de SIZE octets. Une taille de bloc de compression plus grande permet un meilleur ratio de compression. wimlib prend en charge différentes tailles de bloc en fonction du type de compression :
•
XPRESS : 4K, 8K, 16K, 32K, 64K
•
LZX : 32K, 64K, 128K, 256K, 512K, 1M, 2M
•
LZMS : 32K, 64K, 128K, 256K, 512K, 1M, 2M, 4M, 8M, 16M, 32M, 64M, 128M, 256M, 512M, 1G
Vous pouvez fournir le nombre complet (par exemple, 32768), ou utiliser l'un des suffixes K, M ou G. KiB, MiB et GiB sont également acceptés.
Cette option affecte uniquement la taille de bloc utilisée dans les ressources WIM non solides. Si vous créez un WIM solide (en utilisant l'option --solid), vous voudrez probablement utiliser --solid-chunk-size à la place.
Utilisez cette option avec prudence si la compatibilité avec les logiciels WIM de Microsoft est souhaitée, car leur logiciel a un support limité pour les tailles de bloc non par défaut.
--solid
Avec wimcapture, crée un fichier WIM "solide" qui compresse les fichiers ensemble plutôt qu'indépendamment. Cela entraîne un ratio de compression significativement meilleur, mais au prix d'une compression lente avec une utilisation très élevée de la mémoire, d'une compatibilité réduite et d'un accès aléatoire lent au fichier WIM résultant.
Par défaut, cela active la compression LZMS solide, créant ainsi un fichier équivalent à celui créé avec l'option /compress:recovery de DISM. Ces fichiers sont également appelés "fichiers ESD" et ont été pris en charge pour la première fois par WIMGAPI sous Windows 8, par DISM sous Windows 8.1 et par 7-Zip 15.12.
--solid-compress=TYPE[:LEVEL]
Similaire à --compress, mais définit le type de compression utilisé dans les ressources solides. La valeur par défaut est la compression LZMS. Cette option n'a d'effet que lorsque --solid est également spécifié.
--solid-chunk-size=SIZE
Similaire à --chunk-size, mais définit la taille de bloc utilisée dans les ressources solides. La valeur par défaut, en supposant la compression LZMS, est 64MiB (67108864) ; cela nécessite environ 640MiB de mémoire par thread. Cette option n'a d'effet que lorsque --solid est également spécifié. Remarque : les logiciels WIM de Microsoft ne sont pas compatibles avec les tailles de bloc LZMS supérieures à 64MiB.
--threads=NUM_THREADS
Nombre de threads à utiliser pour la compression des données. Défaut : autodétection (nombre de processeurs disponibles).
--rebuild
Avec wimappend, reconstruit l'intégralité du WIM au lieu d'ajouter les nouvelles données à la fin. La reconstruction du WIM est plus lente, mais permet d'économiser de l'espace qui autrement serait laissé comme un trou dans le WIM. Voir également wimoptimize(1).
--flags=EDITIONID
Spécifie une chaîne à utiliser dans l'élément <FLAGS> des données XML pour la nouvelle image.
--image-property NAME=VALUE
Attribue une propriété arbitraire à la nouvelle image dans le document XML du WIM. VALUE est la chaîne à définir comme valeur de la propriété. NAME est le nom de la propriété de l'image, par exemple "NAME", "DESCRIPTION" ou "TOTALBYTES". Le nom peut contenir des barres obliques pour indiquer un élément XML imbriqué ; par exemple, "WINDOWS/VERSION/BUILD" indique l'élément BUILD imbriqué dans l'élément VERSION imbriqué dans l'élément WINDOWS. Un nombre entre crochets peut être utilisé pour indiquer l'un des plusieurs éléments de même nom ; par exemple, "WINDOWS/LANGUAGES/LANGUAGE[2]" indique le deuxième élément "LANGUAGE" imbriqué dans l'élément "WINDOWS/LANGUAGES". Lors de l'ajout d'une liste d'éléments de cette manière, ils doivent être spécifiés dans l'ordre séquentiel. Notez que les noms d'éléments sont sensibles à la casse. Cette option peut être spécifiée plusieurs fois.
--dereference
(Systèmes de type UNIX uniquement) Suit les liens symboliques et archive les fichiers auxquels ils pointent, plutôt que d'archiver les liens eux-mêmes.
--config=FILE
Spécifie un fichier de configuration (codé UTF-8 ou UTF-16LE ; ASCII brut fonctionne également) pour la capture de la nouvelle image. Le fichier de configuration spécifie les fichiers qui doivent être traités spécialement pendant la capture de l'image.
Le format du fichier de configuration est de style INI ; c'est-à-dire qu'il est organisé en sections entre crochets. Actuellement, les sections suivantes sont reconnues :
•
[ExclusionList] --- contient une liste de motifs de chemin à exclure de la capture. Si un répertoire correspond, le répertoire et son contenu sont exclus.
•
[ExclusionException] --- contient une liste de motifs de chemin à inclure, même si le fichier ou le répertoire correspond également à un motif dans [ExclusionList]. Si un répertoire correspond, tout son contenu est également inclus. Les fichiers ou répertoires *dans* un répertoire exclu par [ExclusionList] peuvent même être inclus en utilisant cela, bien que cela ne fonctionne actuellement que pour les motifs absolus (ceux qui commencent par "/" ou "\") ; par exemple, "/dir/file" peut être inclus alors que "/dir" peut être exclu, mais l'inclusion de "file" ne fonctionnera pas dans ce cas.
•
[PrepopulateList] --- cela n'affecte pas la capture, mais si l'image est appliquée plus tard avec --wimboot, il s'agit de motifs de fichiers qui seront extraits normalement, et non comme des "fichiers pointeurs" WIMBoot. Si un répertoire correspond, tous les fichiers et sous-répertoires sont également mis en correspondance de manière récursive.
Les motifs de chemin peuvent contenir les métacaractères '*' et '?'. Les motifs relatifs (par exemple, *.mp3) correspondent au nom d'un fichier dans n'importe quel répertoire. Les motifs absolus (par exemple, /dir/file) sont traités comme des chemins commençant par le répertoire principal capturé, ou la racine du volume NTFS en mode de capture de volume NTFS. N'utilisez pas de lettres de lecteur dans les chemins ; elles seront ignorées. Les séparateurs de chemin peuvent être des barres obliques ou des barres obliques inversées.
Les lignes commençant par les caractères '#' ou ';' sont traitées comme des commentaires et ignorées. Les motifs contenant des espaces blancs n'ont pas besoin d'être mis entre guillemets ; cependant, s'ils le sont, les guillemets doubles et simples sont acceptés.
Si cette option n'est pas spécifiée, le fichier de configuration par défaut suivant est utilisé :
[ExclusionList]
\$ntfs.log
\hiberfil.sys
\pagefile.sys
\swapfile.sys
\System Volume Information
\RECYCLER
\$RECYCLE.BIN
\$Recycle.Bin
\Windows\CSC
Cependant, un comportement spécial s'applique si --wimboot est également spécifié. Par défaut, avec --wimboot spécifié, le fichier Windows/System32/WimBoo
tCompress.ini dans le répertoire capturé sera utilisé comme fichier de configuration. Cependant, cela peut être remplacé en utilisant --config ; et cela provoque également l'enregistrement du fichier de configuration spécifié dans l'image WIM sous le nom Windows/System32/WimBootCompress.ini, remplaçant tout ce qui pourrait être présent sur le système de fichiers.
--unix-data
(Systèmes de type UNIX uniquement) Stocker les métadonnées et fichiers spéciaux spécifiques à UNIX. Cela inclut : les permissions de fichiers UNIX standard (propriétaire, groupe et mode) ; les nœuds de périphériques, les tubes nommés et les sockets ; et les attributs étendus (Linux uniquement). Ces informations peuvent être restaurées ultérieurement par wimapply avec l'option --unix-data.
Les informations spécifiques à UNIX sont ignorées par le logiciel WIM de Microsoft et par la version Windows de wimlib.
--no-acls
Ne pas capturer les descripteurs de sécurité des fichiers.
--strict-acls
Échouer immédiatement si le descripteur de sécurité complet d'un fichier ne peut pas être lu. Sous Windows, le comportement par défaut sans cette option est d'abord d'essayer d'omettre le SACL du descripteur de sécurité, puis d'essayer d'omettre complètement le descripteur de sécurité. Le but est de capturer autant de données que possible sans toujours exiger des privilèges d'administrateur. Cependant, si vous souhaitez que tous les descripteurs de sécurité soient capturés exactement, vous pouvez souhaiter fournir cette option, bien que l'administrateur devrait avoir la permission de tout lire de toute façon.
--rpfix, --norpfix
Définir s'il faut corriger ou non les cibles des liens symboliques absolus (points de redirection dans la terminologie Windows). Lorsqu'il est activé (--rpfix), les liens symboliques absolus qui pointent à l'intérieur de l'arborescence de répertoires capturée seront ajustés pour être absolus par rapport à la racine de l'arborescence de répertoires capturée. Lorsqu'il est désactivé (--norpfix), les liens symboliques absolus seront capturés tels quels.
Le comportement par défaut de wimcapture est équivalent à --rpfix. Le comportement par défaut de wimappend est équivalent à --rpfix si des corrections de points de redirection ont été effectuées précédemment sur WIMFILE, sinon --norpfix.
Dans le cas d'une capture multi-source, (--source-list spécifié), passer --norpfix est recommandé. Sinon, les corrections de points de redirection seront désactivées sur toutes les sources de capture destinées à des emplacements non-racine dans l'image WIM, tandis que les sources de capture destinées à la racine WIM recevront le comportement par défaut du paragraphe précédent.
--source-list
wimcapture et wimappend prennent en charge la création d'une image WIM à partir de plusieurs fichiers ou répertoires distincts. Lorsque --source-list est spécifié, l'argument SOURCE spécifie le nom d'un fichier texte, dont chaque ligne est soit 1 ou 2 chemins de fichiers séparés par des espaces. Le premier chemin de fichier, la source, spécifie le chemin d'un fichier ou d'un répertoire à capturer dans l'image WIM. Il peut être absolu ou relatif au répertoire de travail actuel. Le second chemin de fichier, s'il est fourni, est la cible et spécifie le chemin dans l'image WIM où ce fichier ou répertoire sera enregistré. Les barres obliques de début et de fin dans la cible sont ignorées, sauf si elle est entièrement composée de barres obliques (par exemple, "/"), ce qui indique que le répertoire doit devenir la racine de l'image WIM. S'il est omis, la chaîne cible par défaut est la même que la chaîne source.
Un exemple de fichier de liste de sources est le suivant :
# Créer l'image WIM à partir du répertoire 'winpe'
winpe	/
# Envoyer le répertoire 'overlay' vers '/overlay' dans l'image WIM
overlay	/overlay
# Superposer un répertoire séparé directement sur la racine de l'image WIM.
/data/stuff	/
Les sous-répertoires dans le WIM sont créés si nécessaire. Plusieurs répertoires sources peuvent partager la même cible, ce qui implique une superposition. Dans le cas où cela entraînerait l'ajout d'un fichier non-répertoire dans l'image WIM plusieurs fois, la dernière version (telle qu'indiquée dans le fichier de liste des sources) remplace toute version antérieure.
Les chemins de fichiers contenant des espaces peuvent être mis entre guillemets simples ou doubles. Les guillemets ne peuvent pas être échappés.
Les lignes ne contenant que des espaces et les lignes commençant par '#' précédées d'espaces optionnels sont ignorées.
À titre spécial, si SOURCE est "-", la liste des sources est lue à partir de l'entrée standard plutôt que d'un fichier externe.
Le mode de capture de volume NTFS sur les systèmes de type UNIX ne peut pas être utilisé avec --source-list, car seule la capture d'un volume NTFS complet est prise en charge.
--pipable
Avec wimcapture, créez un WIM "pipable" spécifique à wimlib qui peut être capturé et appliqué entièrement séquentiellement. Si WIMFILE est spécifié comme "-", alors le WIM pipable est écrit directement sur la sortie standard ; sinon, il est écrit sur disque comme d'habitude. L'image dans le WIM pipable peut plus tard être appliquée avec wimapply, soit depuis le disque, soit depuis l'entrée standard. Une utilisation typique des WIM pipables pourrait impliquer de diffuser l'image WIM vers un serveur distant lors de sa capture et/ou de diffuser l'image WIM depuis un serveur distant lors de son application.
Généralement, toutes les commandes wimlib-imagex fonctionnent sur les WIM pipables et non pipables. wimoptimize et wimexport peuvent également être utilisés pour convertir entre WIM pipables et non pipables. Cependant, il existe quelques limitations des WIM pipables :
•
Les WIM pipables sont une extension de wimlib qui ne sont *pas* compatibles avec le logiciel WIM de Microsoft ou avec d'autres programmes tels que 7-Zip.
•
En utilisant wimappend, plusieurs images peuvent être ajoutées à un WIM pipable. Ceci est pris en charge, bien que moins efficace que de le faire avec des WIM non pipables car un WIM pipable est entièrement reconstruit à chaque fois qu'il est ajouté ; et lors du piping d'un tel WIM vers wimapply pour extraire une image, certaines données inutiles seront envoyées sur le pipe.
•
Bien qu'une image WIM pipable puisse être mise à jour à l'aide de wimupdate, cela nécessite une reconstruction complète du fichier WIM, ce qui le rend moins efficace que la mise à jour d'un WIM non pipable.
•
Les WIM pipables solides ne sont pas encore pris en charge.
--not-pipable
Avec wimappend, reconstruire le fichier WIM au format non pipable (régulier). Cette option n'est utile que si vous ajoutez une image à un WIM pipable (voir --pipable) que vous souhaitez plutôt au format non pipable. Notez que wimoptimize(1) peut également être utilisé pour convertir entre WIM non pipables et pipables.
--update-of=[WIMFILE:]IMAGE
Indiquer que l'image capturée ou ajoutée à partir de SOURCE est en grande partie identique à l'image existante IMAGE dans WIMFILE, mais capturée à un moment ultérieur, potentiellement avec quelques modifications entre-temps. Ceci est conçu pour être utilisé dans les sauvegardes incrémentielles du même système de fichiers ou de la même arborescence de répertoires. IMAGE peut être un index basé sur 1 ou le nom d'une image existante dans WIMFILE. Il peut également s'agir d'un entier négatif pour indexer à rebours dans les images (par exemple, -1 signifie la dernière image existante dans WIMFILE).
Lorsque cette option est fournie, la capture ou l'ajout de la nouvelle image sera optimisé en ne lisant pas les fichiers qui, sur la base des métadonnées telles que les horodatages, semblent ne pas avoir été modifiés depuis leur archivage dans l'image existante IMAGE. Sans manipulation des horodatages, cette option n'affecte que les performances et ne modifie pas l'image WIM résultante (mais voir la note ci-dessous).
Comme indiqué, la syntaxe complète de l'argument de cette option est de spécifier le fichier WIM, deux points, et l'image ; par exemple, "--update-of mywim.wim:1". Cependant, le fichier WIM et les deux points peuvent être omis si --delta-from est spécifié exactement une fois, auquel cas le WIM par défaut est celui spécifié dans --delta-from, ou si l'opération est wimappend plutôt que wimcapture, auquel cas le WIM par défaut est celui auquel l'ajout est fait.
Note : dans la version Windows de wimlib, il a été observé que le mode --update-of n'est pas complètement fiable pour détecter les changements dans le contenu des fichiers, provoquant parfois l'archivage des anciens contenus de quelques fichiers plutôt que les contenus actuels. La cause de ce problème est que Windows ne met pas immédiatement à jour l'horodatage de dernière modification d'un fichier après chaque écriture dans ce fichier. Malheureusement, il n'existe aucun moyen connu pour les applications comme wimlib de contourner automatiquement ce bug. Des solutions manuelles sont possibles ; théoriquement, toute action qui provoque la fermeture des fichiers problématiques, comme le redémarrage des applications ou de l'ordinateur lui-même, devrait entraîner la mise à jour des horodatages des fichiers. Notez également que wimlib compare les tailles de fichiers ainsi que les horodatages pour déterminer si un fichier a changé, ce qui contribue à rendre le problème moins probable ; et le problème ne se produit pas sur d'autres systèmes d'exploitation tels que Linux qui maintiennent correctement les horodatages de dernière modification des fichiers.
--delta-from=WIMFILE
Capturer ou ajouter la nouvelle image comme un "delta" à partir de WIMFILE. Toute donnée de fichier qui devrait normalement être archivée dans le WIM nouveau ou mis à jour est omise si elle est déjà présente dans le WIMFILE sur lequel le delta est basé. Le WIM résultant contiendra toujours une copie complète des métadonnées de l'image, mais il s'agit généralement d'une petite fraction de la taille totale d'un WIM.
Cette option peut être spécifiée plusieurs fois, auquel cas le WIM delta résultant ne contiendra que les données de fichiers qui ne sont présentes dans aucun des WIM de base spécifiés.
Pour opérer sur le WIM delta résultant avec d'autres commandes telles que wimapply, vous devez spécifier le WIM delta comme fichier WIM sur lequel opérer, mais également référencer le(s) WIM de base en utilisant l'option --ref. Attention : pour conserver le bon fonctionnement du WIM delta, vous ne pouvez ajouter, pas supprimer, des fichiers et des images au(x) WIM de base après la capture
wimcapture(1) — wimlib 1.14.4

OPTIONS

--delta-from
When creating a WIM file, capture changes relative to a base WIM file. This makes the new WIM file a "delta" WIM, which is smaller than a full WIM, but requires the base WIM to be present when applying the delta WIM. This option may be specified multiple times if the delta is to be computed relative to multiple base WIMs. If multiple base WIMs are specified, the delta is computed relative to the last one specified. The first base WIM specified is used to initialize the capture, and subsequent base WIMs are used to refine the delta.
--delta-from may be combined with --update-of to increase the speed of capturing a delta WIM.
As an example, consider the following backup and restore sequence:
(initial backup)
$ wimcapture /some/directory bkup-base.wim
(some days later, create second backup as delta from first)
$ wimcapture /some/directory bkup-2013-08-20.dwm \
	--update-of bkup-base.wim:-1 --delta-from bkup-base.wim
(restoring the second backup)
$ wimapply bkup-2013-08-20.dwm --ref=bkup-base.wim 1 \
	/some/directory
However, note that as an alternative to the above sequence that used a delta WIM, the second backup could have simply been appended to the WIM as new image using wimappend. Delta WIMs should be used only if it's desired to base the backups or images on a separate, large file that is rarely modified.
--delta-from is supported by both wimcapture and wimappend.
Delta WIMs are compatible with Microsoft's WIM software. For example, you can use the /ref option of ImageX to reference the base WIM(s), similar to above.
Additional note: wimlib is generalized enough that you can in fact combine --pipable and --delta-from to create pipable delta WIMs. In such cases, the base WIM(s) must be captured as pipable as well as the delta WIM, and when applying an image, the base WIM(s) must be sent over the pipe after the delta WIM.
--wimboot
Mark the image as WIMBoot-compatible. See Microsoft's documentation for more information about WIMBoot. With wimcapture this option will set the compression type to XPRESS and the chunk size to 4096 bytes; these can, however, still be overridden through the --compress and --chunk-size parameters, respectively. In addition, this option will set the configuration file to SOURCE\Windows\System32\WimBootCompress.ini if present and accessible; however, this may still be overridden through the --config parameter.
--unsafe-compact
With wimappend, compact the WIM archive in-place and append any new data, eliminating "holes". This is efficient, but in general this option should not be used because a failed or interrupted compaction will corrupt the WIM archive. For more information, see the documentation for this option to wimoptimize(1).
--snapshot
Create a temporary filesystem snapshot of the source directory and capture the files from it. Currently, this option is only supported on Windows, where it uses the Volume Shadow Copy Service (VSS). Using this option, you can create a consistent backup of the system volume of a running Windows system without running into problems with locked files. For the VSS snapshot to be successfully created, wimlib-imagex must be run as an Administrator, and it cannot be run in WoW64 mode (i.e. if Windows is 64-bit, then wimlib-imagex must be 64-bit as well).
--create
With wimappend, if the WIM file doesn't exist yet, then create it (like wimcapture).

NOTES

wimappend does not support appending an image to a split WIM.

Except when using --unsafe-compact, it is safe to abort a wimappend command partway through; however, after doing this, it is recommended to run wimoptimize to remove any data that was appended to the physical WIM file but not yet incorporated into the structure of the WIM, unless the WIM was being fully rebuilt (e.g. with --rebuild), in which case you should delete the temporary file left over.

wimlib-imagex creates WIMs compatible with Microsoft's software (WIMGAPI, ImageX, DISM), with some caveats:

•
With wimlib-imagex on UNIX-like systems, it is possible to create a WIM image containing files with names differing only in case, or files with names containing the characters ':', '*', '?', '"', '<', '>', '|', or '\', which are valid on POSIX-compliant filesystems but not Windows. Be warned that such files will not be extracted by default by the Windows version of wimlib-imagex, and (even worse) Microsoft's ImageX can be confused by such names and quit extracting the image partway through.
•
Pipable WIMs are incompatible with Microsoft's software. Pipable WIMs are created only if WIMFILE was specified as "-" (standard output) or if the --pipable flag was specified.
•
WIMs captured with a non-default chunk size (with the --chunk-size option) or as solid archives (with the --solid option) or with LZMS compression (with --compress=LZMS or --compress=recovery) have varying levels of compatibility with Microsoft's software. Generally, more recent versions of Microsoft's software are more compatible.

EXAMPLES

First example: Create a new WIM 'mywim.wim' with LZX ("maximum") compression that will contain a captured image of the directory tree 'somedir'. Note that the image name need not be specified and will default to 'somedir':

wimcapture somedir mywim.wim

Next, append the image of a different directory tree to the WIM created above:

wimappend anotherdir mywim.wim

Easy enough, and the above examples of imaging directory trees work on both UNIX-like systems and Windows. Next, capture a WIM with several non-default options, including XPRESS ("fast") compression, extra integrity information, no messing with absolute symbolic links, and an image name and description:

wimcapture somedir mywim.wim --compress=fast \

--check --norpfix "Some Name" "Some Description"

On a UNIX-like system, capture a full NTFS volume into a new WIM using the NTFS VOLUME CAPTURE (UNIX) mode, and name the image "Windows 7":

wimcapture /dev/sda2 windows7.wim "Windows 7"

or, on Windows, to capture a full NTFS volume you instead need to specify the root directory of the mounted volume, for example:

wimcapture E:\ windows7.wim "Windows 7"

Same as UNIX example above, but capture the WIM in the wimlib-specific "pipable" format that can be piped to wimapply:

wimcapture /dev/sda2 windows7.wim "Windows 7" --pipable

Same as above, but instead of writing the pipable WIM to the file "windows7.wim", write it directly to standard output through a pipe into some other program "someprog", which could, for example, be a program or script that streams the data to a server:

wimcapture /dev/sda2 - "Windows 7" | someprog
