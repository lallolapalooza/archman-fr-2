NOM

Wget - Le téléchargeur réseau non interactif.

SYNTAXE

wget [option]... [URL]...

DESCRIPTION

GNU Wget est un utilitaire libre pour télécharger des fichiers du Web de manière non interactive. Il prend en charge les protocoles HTTP, HTTPS et FTP, ainsi que la récupération via des proxys HTTP.

Wget est non interactif, ce qui signifie qu'il peut fonctionner en arrière-plan, sans que l'utilisateur ne soit connecté. Cela vous permet de lancer une récupération et de vous déconnecter du système, laissant Wget terminer le travail. En revanche, la plupart des navigateurs Web nécessitent la présence constante de l'utilisateur, ce qui peut être un obstacle majeur lors du transfert de grandes quantités de données.

Wget peut suivre les liens dans les pages HTML, XHTML et CSS, pour créer des versions locales de sites Web distants, recréant entièrement la structure de répertoires du site d'origine. Ceci est parfois appelé "téléchargement récursif". Pendant ce processus, Wget respecte le Robot Exclusion Standard (/robots.txt). Wget peut être instruit pour convertir les liens dans les fichiers téléchargés afin qu'ils pointent vers les fichiers locaux, pour une consultation hors ligne.

Wget a été conçu pour être robuste sur des connexions réseau lentes ou instables ; si un téléchargement échoue en raison d'un problème réseau, il continuera à réessayer jusqu'à ce que le fichier entier ait été récupéré. Si le serveur prend en charge la reprise, il demandera au serveur de continuer le téléchargement à partir de l'endroit où il s'est arrêté.

OPTIONS

Syntaxe des options

Puisque Wget utilise GNU getopt pour traiter les arguments de la ligne de commande, chaque option a une forme longue en plus de sa forme courte. Les options longues sont plus pratiques à retenir, mais prennent plus de temps à taper. Vous pouvez mélanger librement différents styles d'options, ou spécifier les options après les arguments de la ligne de commande. Ainsi, vous pouvez écrire :

wget -r --tries=10 http://fly.srk.fer.hr/ -o log

L'espace entre l'option acceptant un argument et l'argument peut être omis. Au lieu de -o log, vous pouvez écrire -olog.

Vous pouvez grouper plusieurs options qui ne nécessitent pas d'arguments, comme :

wget -drc <URL>

Ceci est complètement équivalent à :

wget -d -r -c <URL>

Comme les options peuvent être spécifiées après les arguments, vous pouvez les terminer par --. Ainsi, le suivant essaiera de télécharger l'URL -x, en rapportant l'échec à log :

wget -o log -- -x

Les options qui acceptent des listes séparées par des virgules respectent toutes la convention selon laquelle la spécification d'une liste vide efface sa valeur. Ceci peut être utile pour effacer les paramètres de .wgetrc. Par exemple, si votre .wgetrc définit "exclude_directories" à /cgi-bin, l'exemple suivant la réinitialisera d'abord, puis la définira pour exclure /~nobody et /~somebody. Vous pouvez également effacer les listes dans .wgetrc.

wget -X "" -X /~nobody,/~somebody

La plupart des options qui n'acceptent pas d'arguments sont des options booléennes, ainsi nommées car leur état peut être capturé par une variable oui-ou-non ("booléenne"). Par exemple, --follow-ftp indique à Wget de suivre les liens FTP depuis les fichiers HTML et, d'autre part, --no-glob lui indique de ne pas effectuer de globbing de fichiers sur les URL FTP. Une option booléenne est soit affirmative, soit négative (commençant par --no). Toutes ces options partagent plusieurs propriétés.

Sauf indication contraire, il est supposé que le comportement par défaut est l'opposé de ce que fait l'option. Par exemple, l'existence documentée de --follow-ftp suppose que le défaut est de ne pas suivre les liens FTP depuis les pages HTML.

Les options affirmatives peuvent être niées en préfixant --no- au nom de l'option ; les options négatives peuvent être niées en omettant le préfixe --no-. Cela peut sembler superflu - si le défaut pour une option affirmative est de ne rien faire, alors pourquoi fournir un moyen de l'activer explicitement ? Mais le fichier de démarrage peut effectivement changer le défaut. Par exemple, utiliser "follow_ftp = on" dans .wgetrc fait que Wget suit les liens FTP par défaut, et utiliser --no-follow-ftp est le seul moyen de restaurer le défaut d'usine depuis la ligne de commande.

Options de démarrage de base

-V
--version
Affiche la version de Wget.
-h
--help
Imprime un message d'aide décrivant toutes les options de ligne de commande de Wget.
-b
--background
Passe en arrière-plan immédiatement après le démarrage. Si aucun fichier de sortie n'est spécifié via -o, la sortie est redirigée vers wget-log.
-e commande
--execute commande
Exécute commande comme si elle faisait partie de .wgetrc. Une commande ainsi invoquée sera exécutée après les commandes dans .wgetrc, prenant ainsi la priorité sur elles. Si vous devez spécifier plus d'une commande wgetrc, utilisez plusieurs instances de -e.

Options de journalisation et de fichier d'entrée

-o logfile
--output-file=logfile
Journalise tous les messages dans logfile. Les messages sont normalement affichés sur la sortie standard d'erreur.
-a logfile
--append-output=logfile
Ajoute à logfile. Ceci est identique à -o, mais ajoute à logfile au lieu d'écraser l'ancien fichier journal. Si logfile n'existe pas, un nouveau fichier est créé.
-d
--debug
Active la sortie de débogage, c'est-à-dire diverses informations importantes pour les développeurs de Wget s'il ne fonctionne pas correctement. Votre administrateur système a peut-être choisi de compiler Wget sans support de débogage, auquel cas -d ne fonctionnera pas. Veuillez noter que la compilation avec le support de débogage est toujours sans risque — Wget compilé avec le support de débogage n'affichera aucune information de débogage sauf si elle est demandée avec -d.
-q
--quiet
Désactive la sortie de Wget.
-v
--verbose
Active la sortie détaillée, avec toutes les données disponibles. La sortie par défaut est détaillée.
-nv
--no-verbose
Désactive la sortie détaillée sans être complètement silencieux (utilisez -q pour cela), ce qui signifie que les messages d'erreur et les informations de base sont toujours affichés.
--report-speed=type
Affiche la bande passante sous forme de type. La seule valeur acceptée est bits.
-i file
--input-file=file
Lit les URL depuis un fichier local ou externe file. Si - est spécifié comme file, les URL sont lues depuis l'entrée standard. (Utilisez ./- pour lire depuis un fichier littéralement nommé -.)

Si cette fonction est utilisée, aucune URL n'a besoin d'être présente sur la ligne de commande. S'il y a des URL à la fois sur la ligne de commande et dans un fichier d'entrée, celles de la ligne de commande seront les premières à être récupérées. Si --force-html n'est pas spécifié, alors file doit contenir une série d'URL, une par ligne.

Cependant, si vous spécifiez --force-html, le document sera considéré comme html. Dans ce cas, vous pourriez avoir des problèmes avec les liens relatifs, que vous pouvez résoudre soit en ajoutant "<base href="url">" aux documents, soit en spécifiant --base=url en ligne de commande.

Si le fichier est un fichier externe, le document sera automatiquement traité comme html si le Content-Type correspond à text/html. De plus, l'emplacement du fichier sera implicitement utilisé comme base href si aucun n'a été spécifié.

Si le fichier est un fichier local, sur les systèmes qui le prennent en charge, il sera ouvert avec le "O_NONBLOCK" flag pour permettre des lectures non bloquantes du fichier. Wget tentera de continuer à lire depuis le fichier jusqu'à ce que EOF soit atteint ou qu'il soit fermé. Cela permet de diffuser une liste de fichiers à récupérer, où la liste est générée dynamiquement pendant l'exécution du processus. Actuellement, cette fonctionnalité n'est pas disponible sur les plateformes Windows.

--input-metalink=fichier
Télécharge les fichiers couverts dans le fichier Metalink local. Les versions 3 et 4 de Metalink sont prises en charge.
--keep-badhash
Conserve les fichiers Metalink téléchargés avec un mauvais hash. Il ajoute .badhash au nom des fichiers Metalink qui ont une incohérence de somme de contrôle, sauf en évitant d'écraser les fichiers existants.
--metalink-over-http
Émet une requête HTTP HEAD au lieu de GET et extrait les métadonnées Metalink des en-têtes de réponse. Ensuite, il passe au téléchargement Metalink. Si aucune métadonnée Metalink valide n'est trouvée, il revient au téléchargement HTTP ordinaire. Active le téléchargement/traitement des fichiers Content-Type: application/metalink4+xml.
--metalink-index=nombre
Définit l'ordinal du metaurl Metalink application/metalink4+xml sur NOMBRE. De 1 au nombre total de "application/metalink4+xml" disponibles. Spécifiez 0 ou inf pour choisir le premier bon. Les metaurls, tels que ceux d'un --metalink-over-http, peuvent avoir été triés par valeur de clé de priorité ; gardez cela à l'esprit pour choisir le bon NOMBRE.
--preferred-location
Définit l'emplacement préféré pour les ressources Metalink. Ceci a un effet si plusieurs ressources avec la même priorité sont disponibles.
--xattr
Active l'utilisation des attributs étendus du système de fichiers pour sauvegarder l'URL d'origine et la valeur de l'en-tête HTTP Referer si utilisé.

Soyez conscient que l'URL peut contenir des informations privées telles que des jetons d'accès ou des identifiants.

-F
--force-html
Lorsque l'entrée est lue à partir d'un fichier, forcez-la à être traitée comme un fichier HTML. Cela vous permet de récupérer des liens relatifs à partir de fichiers HTML existants sur votre disque local, en ajoutant "<base href="url">" à HTML, ou en utilisant l'option de ligne de commande --base.
-B URL
--base=URL
Résout les liens relatifs en utilisant URL comme point de référence, lors de la lecture de liens à partir d'un fichier HTML spécifié via l'option -i/--input-file (en conjonction avec --force-html, ou lorsque le fichier d'entrée a été récupéré à distance à partir d'un serveur le décrivant comme HTML). Ceci est équivalent à la présence d'une balise "BASE" dans le fichier d'entrée HTML, avec URL comme valeur pour l'attribut "href".

Par exemple, si vous spécifiez http://foo/bar/a.html pour URL, et que Wget lit ../baz/b.html à partir du fichier d'entrée, cela sera résolu en http://foo/baz/b.html.

--config=FICHIER
Spécifie l'emplacement d'un fichier de démarrage que vous souhaitez utiliser à la place des fichiers par défaut. Utilisez --no-config pour désactiver la lecture des fichiers de configuration. Si --config et --no-config sont tous deux donnés, --no-config est ignoré.
--rejected-log=journal
Enregistre toutes les rejets d'URL dans le journal sous forme de valeurs séparées par des virgules. Les valeurs incluent la raison du rejet, l'URL et l'URL parent dans laquelle elle a été trouvée.

Options de téléchargement

--bind-address=ADRESSE
Lors de l'établissement de connexions TCP/IP client, lie à ADRESSE sur la machine locale. ADRESSE peut être spécifiée comme un nom d'hôte ou une adresse IP. Cette option peut être utile si votre machine est liée à plusieurs IP.
--bind-dns-address=ADRESSE
[libcares uniquement] Cette adresse remplace la route pour les requêtes DNS. Si vous avez jamais besoin de contourner les paramètres standard de /etc/resolv.conf, cette option associée à --dns-servers est votre amie. ADRESSE doit être spécifiée comme une adresse IPv4 ou IPv6. Wget doit être compilé avec libcares pour que cette option soit disponible.
--dns-servers=ADRESSES
[libcares uniquement] Les adresses données remplacent les adresses des serveurs de noms standard, par exemple celles configurées dans /etc/resolv.conf. ADRESSES peuvent être spécifiées comme adresses IPv4 ou IPv6, séparées par des virgules. Wget doit être compilé avec libcares pour que cette option soit disponible.
-t nombre
--tries=nombre
Définit le nombre d'essais sur nombre. Spécifiez 0 ou inf pour des tentatives infinies. La valeur par défaut est de réessayer 20 fois, à l'exception des erreurs fatales telles que "connexion refusée" ou "non trouvé" (404), qui ne font pas l'objet de nouvelles tentatives.
-O fichier
--output-document=fichier
Les documents ne seront pas écrits dans les fichiers appropriés, mais seront tous concaténés ensemble et écrits dans fichier. Si - est utilisé comme fichier, les documents seront imprimés sur la sortie standard, désactivant la conversion des liens. (Utilisez ./- pour imprimer dans un fichier nommé littéralement -.)

L'utilisation de -O n'est pas destinée à signifier simplement "utiliser le nom fichier au lieu de celui de l'URL"; au contraire, elle est analogue à la redirection shell : wget -O fichier http://foo est destiné à fonctionner comme wget -O - http://foo > fichier ; fichier sera immédiatement tronqué, et tout le contenu téléchargé y sera écrit.

Pour cette raison, -N (pour la vérification des horodatages) n'est pas supporté en combinaison avec -O : puisque fichier est toujours créé nouvellement, il aura toujours un horodatage très récent. Un avertissement sera émis si cette combinaison est utilisée.

De même, l'utilisation de -r ou -p avec -O peut ne pas fonctionner comme prévu : Wget ne téléchargera pas seulement le premier fichier vers fichier, puis téléchargera le reste vers leurs noms normaux : tout le contenu téléchargé sera placé dans fichier. Ceci a été désactivé dans la version 1.11, mais a été rétabli (avec un avertissement) en 1.11.2, car il existe certains cas où ce comportement peut réellement avoir une utilité.

Une combinaison avec -nc est acceptée seulement si le fichier de sortie donné n'existe pas.

Notez qu'une combinaison avec -k n'est autorisée que lors du téléchargement d'un seul document, car dans ce cas, elle convertira simplement tous les URI relatifs en URI externes ; -k n'a pas de sens pour plusieurs URI lorsqu'ils sont tous téléchargés dans un seul fichier ; -k ne peut être utilisé que lorsque la sortie est un fichier régulier.

-nc
--no-clobber
Si un fichier est téléchargé plus d'une fois dans le même répertoire, le comportement de Wget dépend de quelques options, y compris -nc. Dans certains cas, le fichier local sera écrasé, ou remplacé, lors d'un téléchargement répété. Dans d'autres cas, il sera préservé.

Lorsque vous exécutez Wget sans -N, -nc, -r, ou -p, le téléchargement du même fichier dans le même répertoire résultera en la préservation de la copie originale de fichier et la deuxième copie sera nommée fichier.1. Si ce fichier est encore téléchargé, la troisième copie sera nommée fichier.2, et ainsi de suite. (C'est aussi le comportement avec -nd, même si -r ou -p sont actifs.) Lorsque -nc est spécifié, ce comportement est supprimé, et Wget refusera de télécharger des copies plus récentes de fichier. Par conséquent, ""no-clobber"" est en fait un terme impropre dans ce mode---ce n'est pas l'écrasement qui est empêché (car les suffixes numériques empêchaient déjà l'écrasement), mais plutôt la sauvegarde de plusieurs versions qui est empêchée.

Lorsque vous exécutez Wget avec -r ou -p, mais sans -N, -nd, ou -nc, le re-téléchargement d'un fichier résultera en la nouvelle copie écrasant simplement l'ancienne. L'ajout de -nc empêchera ce comportement, provoquant plutôt la préservation de la version originale et l'ignorance des copies plus récentes sur le serveur.

Lorsque vous exécutez Wget avec -N, avec ou sans -r ou -p, la décision de télécharger ou non une copie plus récente d'un fichier dépend de l'horodatage et de la taille locaux et distants du fichier. -nc ne peut pas être spécifié en même temps que -N.

Une combinaison avec -O/--output-document est acceptée seulement si le fichier de sortie donné n'existe pas.

Notez que lorsque -nc est spécifié, les fichiers avec les suffixes .html ou .htm seront chargés depuis le disque local et analysés comme s'ils avaient été récupérés sur le Web.

--backups=sauvegardes
Avant d'écraser (ou)g un fichier, sauvegardez un fichier existant en ajoutant un suffixe .1 (_1 sur VMS) au nom du fichier. Ces fichiers de sauvegarde sont ensuite renommés en .2, .3, et ainsi de suite, jusqu'à backups (et sont perdus au-delà).
--no-netrc
N'essayez pas d'obtenir les informations d'identification du fichier .netrc. Par défaut, le fichier .netrc est recherché pour les informations d'identification si aucune n'a été passée en ligne de commande et que l'authentification est requise.
-c
--continue
Continuez à télécharger un fichier partiellement téléchargé. Ceci est utile lorsque vous souhaitez terminer un téléchargement commencé par une instance précédente de Wget, ou par un autre programme. Par exemple : 
wget -c ftp://sunsite.doc.ic.ac.uk/ls-lR.Z

S'il existe un fichier nommé ls-lR.Z dans le répertoire courant, Wget supposera qu'il s'agit de la première partie du fichier distant, et demandera au serveur de continuer la récupération à partir d'un décalage égal à la longueur du fichier local.

Notez qu'il n'est pas nécessaire de spécifier cette option si vous voulez simplement que l'invocation actuelle de Wget réessaie de télécharger un fichier si la connexion est perdue en cours de route. C'est le comportement par défaut. -c n'affecte que la reprise des téléchargements commencés avant cette invocation de Wget, et dont les fichiers locaux sont encore présents.

Sans -c, l'exemple précédent téléchargerait simplement le fichier distant dans ls-lR.Z.1, laissant le fichier tronqué ls-lR.Z intact.

Si vous utilisez -c sur un fichier non vide, et que le serveur ne prend pas en charge le téléchargement continu, Wget redémarrera le téléchargement à partir de zéro et écrasera entièrement le fichier existant.

À partir de Wget 1.7, si vous utilisez -c sur un fichier de taille égale à celui sur le serveur, Wget refusera de télécharger le fichier et affichera un message explicatif. Il en va de même lorsque le fichier est plus petit sur le serveur que localement (probablement parce qu'il a été modifié sur le serveur depuis votre dernière tentative de téléchargement) - car la "continuation" n'a pas de sens, aucun téléchargement n'a lieu.

D'autre part, lors de l'utilisation de -c, tout fichier plus volumineux sur le serveur que localement sera considéré comme un téléchargement incomplet et seuls "(longueur(distant) - longueur(local))" octets seront téléchargés et ajoutés à la fin du fichier local. Ce comportement peut être souhaitable dans certains cas - par exemple, vous pouvez utiliser wget -c pour télécharger uniquement la nouvelle partie qui a été ajoutée à une collection de données ou à un fichier journal.

Cependant, si le fichier est plus volumineux sur le serveur parce qu'il a été modifié, plutôt que simplement ajouté, vous vous retrouverez avec un fichier corrompu. Wget n'a aucun moyen de vérifier que le fichier local est réellement un préfixe valide du fichier distant. Vous devez être particulièrement prudent à ce sujet lorsque vous utilisez -c en conjonction avec -r, car chaque fichier sera considéré comme un candidat au "téléchargement incomplet".

Une autre instance où vous obtiendrez un fichier corrompu si vous essayez d'utiliser -c est si vous avez un proxy HTTP défectueux qui insère une chaîne "transfer interrupted" dans le fichier local. À l'avenir, une option "rollback" pourrait être ajoutée pour traiter ce cas.

Notez que -c ne fonctionne qu'avec les serveurs FTP et les serveurs HTTP qui prennent en charge l'en-tête "Range".

--start-pos=DECALAGE
Commencez le téléchargement à la position DECALAGE basée sur zéro. Le décalage peut être exprimé en octets, kilooctets avec le suffixe `k', ou mégaoctets avec le suffixe `m', etc.

--start-pos a une priorité plus élevée que --continue. Lorsque --start-pos et --continue sont tous deux spécifiés, wget émettra un avertissement puis procédera comme si --continue était absent.

Le support serveur pour le téléchargement continu est requis, sinon --start-pos ne pourra pas aider. Voir -c pour plus de détails.

--progress=type
Sélectionnez le type d'indicateur de progression que vous souhaitez utiliser. Les indicateurs légaux sont "dot" et "bar".

L'indicateur "bar" est utilisé par défaut. Il dessine une barre de progression graphique ASCII (également appelée affichage "thermomètre") indiquant l'état de la récupération. Si la sortie n'est pas un TTY, la barre "dot" sera utilisée par défaut.

Utilisez --progress=dot pour passer à l'affichage "dot". Il suit la récupération en imprimant des points à l'écran, chaque point représentant une quantité fixe de données téléchargées.

Le type de progression peut également accepter un ou plusieurs paramètres. Les paramètres varient en fonction du type sélectionné. Les paramètres du type sont passés en les ajoutant au type séparés par un deux-points (:) comme ceci : --progress=type:parametre1:parametre2.

Lors de l'utilisation de la récupération par points, vous pouvez définir le style en spécifiant le type comme dot:style. Différents styles attribuent une signification différente à un point. Avec le style "default", chaque point représente 1K, il y a dix points dans un cluster et 50 points par ligne. Le style "binary" a une orientation plus "informatique" - points de 8K, clusters de 16 points et 48 points par ligne (ce qui fait 384K par ligne). Le style "mega" convient au téléchargement de fichiers volumineux - chaque point représente 64K récupérés, il y a huit points dans un cluster, et 48 points par ligne (donc chaque ligne contient 3M). Si "mega" ne suffit pas, vous pouvez utiliser le style "giga" - chaque point représente 1M récupéré, il y a huit points dans un cluster, et 32 points par ligne (donc chaque ligne contient 32M).

Avec --progress=bar, il existe actuellement deux paramètres possibles, force et noscroll.

Lorsque la sortie n'est pas un TTY, la barre de progression revient toujours à "dot", même si --progress=bar a été passé à Wget lors de l'invocation. Ce comportement peut être remplacé et la sortie "bar" forcée en utilisant le paramètre "force" comme --progress=bar:force.

Par défaut, la barre de progression du style bar fait défiler le nom du fichier de gauche à droite pour le fichier en cours de téléchargement si le nom du fichier dépasse la longueur maximale allouée pour son affichage. Dans certains cas, comme avec --progress=bar:force, on peut ne pas vouloir du nom de fichier qui défile dans la barre de progression. En passant le paramètre "noscroll", Wget peut être forcé d'afficher autant du nom de fichier que possible sans le faire défiler.

Notez que vous pouvez définir le style par défaut en utilisant la commande "progress" dans .wgetrc. Ce paramètre peut être remplacé depuis la ligne de commande. Par exemple, pour forcer la sortie de la barre sans défilement, utilisez --progress=bar:force:noscroll.

--show-progress
Force wget à afficher la barre de progression quelle que soit la verbosité.

Par défaut, wget n'affiche la barre de progression qu'en mode verbeux. On peut cependant vouloir que wget affiche la barre de progression à l'écran en conjonction avec tout autre mode de verbosité comme --no-verbose ou --quiet. C'est souvent une propriété souhaitée lors de l'invocation de wget pour télécharger plusieurs fichiers petits/grands. Dans un tel cas, wget pourrait simplement être invoqué avec ce paramètre pour obtenir une sortie beaucoup plus propre à l'écran.

Cette option forcera également la barre de progression à être imprimée sur stderr lorsqu'elle est utilisée avec l'option --output-file.

-N
--timestamping
Active la mise en place des horodatages.
--no-if-modified-since
N'envoie pas d'en-tête If-Modified-Since en mode -N. Envoie une requête HEAD préliminaire à la place. Ceci n'a d'effet qu'en mode -N.
--no-use-server-timestamps
Ne définit pas l'horodatage du fichier local sur celui du serveur.

Par défaut, lorsqu'un fichier est téléchargé, ses horodatages sont réglés pour correspondre à ceux du fichier distant. Cela permet l'utilisation de --timestamping lors d'invocations ultérieures de wget. Cependant, il est parfois utile de baser l'horodatage du fichier local sur le moment où il a été effectivement téléchargé ; à cet effet, l'option --no-use-server-timestamps a été fournie.

-S
--server-response
Imprime les en-têtes envoyés par les serveurs HTTP et les réponses envoyées par les serveurs FTP.
--spider
Lorsqu'il est invoqué avec cette option, Wget se comportera comme un *araignée* Web, ce qui signifie qu'il ne téléchargera pas les pages, il vérifiera simplement qu'elles existent. Par exemple, vous pouvez utiliser Wget pour vérifier vos signets : 
wget --spider --force-html -i bookmarks.html

Cette fonctionnalité nécessite beaucoup plus de travail pour que Wget se rapproche de la fonctionnalité des vraies araignées Web.

-T secondes
--timeout=secondes
Définit le délai d'attente réseau à secondes secondes. Ceci équivaut à spécifier --dns-timeout, --connect-timeout et --read-timeout, tous en même temps.

Lors de l'interaction avec le réseau, Wget peut vérifier les délais d'attente et abandonner l'opération si elle prend trop de temps. Cela empêche des anomalies telles que des lectures bloquées et des connexions infinies. Le seul délai d'attente activé par défaut est un délai de lecture de 900 secondes. Définir un délai d'attente à 0 le désactive complètement. Sauf si vous savez ce que vous faites, il est préférable de ne pas modifier les paramètres de délai d'attente par défaut.

Toutes les options relatives aux délais d'attente acceptent des valeurs décimales, ainsi que des valeurs inférieures à la seconde. Par exemple, 0.1 secondes est un choix de délai d'attente légal (bien qu'imprudent). Les délais d'attente inférieurs à la seconde sont utiles pour vérifier les temps de réponse des serveurs ou pour tester la latence du réseau.

--dns-timeout=secondes
Définit la recherche DNS
--dns-timeout=secondes
Définit le délai d'attente DNS à secondes secondes. Les recherches DNS qui ne se terminent pas dans le délai spécifié échoueront. Par défaut, il n'y a pas de délai d'attente sur les recherches DNS, autre que celui implémenté par les bibliothèques système.
--connect-timeout=secondes
Définit le délai d'attente de connexion à secondes secondes. Les connexions TCP qui prennent plus de temps à s'établir seront interrompues. Par défaut, il n'y a pas de délai d'attente de connexion, autre que celui implémenté par les bibliothèques système.
--read-timeout=secondes
Définit le délai d'attente de lecture (et d'écriture) à secondes secondes. Le « délai » de ce délai d'attente fait référence au temps d'inactivité : si, à un moment donné du téléchargement, aucune donnée n'est reçue pendant plus du nombre de secondes spécifié, la lecture échoue et le téléchargement est redémarré. Cette option n'affecte pas directement la durée totale du téléchargement.

Bien sûr, le serveur distant peut choisir de terminer la connexion plus tôt que ce que cette option ne l'exige. Le délai d'attente de lecture par défaut est de 900 secondes.

--limit-rate=montant
Limite la vitesse de téléchargement à montant octets par seconde. Le montant peut être exprimé en octets, en kilo-octets avec le suffixe k, ou en méga-octets avec le suffixe m. Par exemple, --limit-rate=20k limitera le taux de récupération à 20 Ko/s. Ceci est utile lorsque, pour une raison quelconque, vous ne souhaitez pas que Wget consomme toute la bande passante disponible.

Cette option permet l'utilisation de nombres décimaux, généralement en conjonction avec des suffixes de puissance ; par exemple, --limit-rate=2.5k est une valeur légale.

Notez que Wget met en œuvre la limitation en dormant le temps approprié après une lecture réseau qui a pris moins de temps que spécifié par le taux. Finalement, cette stratégie ralentit le transfert TCP à environ le taux spécifié. Cependant, il peut falloir un certain temps pour que cet équilibre soit atteint, alors ne soyez pas surpris si la limitation du taux ne fonctionne pas bien avec de très petits fichiers.

-w secondes
--wait=secondes
Attend le nombre spécifié de secondes entre les récupérations. L'utilisation de cette option est recommandée, car elle allège la charge du serveur en rendant les requêtes moins fréquentes. Au lieu de secondes, le temps peut être spécifié en minutes en utilisant le suffixe "m", en heures en utilisant le suffixe "h", ou en jours en utilisant le suffixe "d".

Spécifier une valeur élevée pour cette option est utile si le réseau ou l'hôte de destination est en panne, afin que Wget puisse attendre suffisamment longtemps pour s'attendre raisonnablement à ce que l'erreur réseau soit corrigée avant la nouvelle tentative. L'intervalle d'attente spécifié par cette fonction est influencé par "--random-wait", voir ci-dessous.

--waitretry=secondes
Si vous ne souhaitez pas que Wget attende entre chaque récupération, mais seulement entre les nouvelles tentatives de téléchargements échoués, vous pouvez utiliser cette option. Wget utilisera un retard linéaire, attendant 1 seconde après le premier échec sur un fichier donné, puis attendant 2 secondes après le second échec sur ce fichier, jusqu'à un maximum de secondes que vous spécifiez.

Par défaut, Wget adoptera une valeur de 10 secondes.

--random-wait
Certains sites Web peuvent effectuer une analyse de journaux pour identifier les programmes de récupération tels que Wget en recherchant des similitudes statistiquement significatives dans le temps entre les requêtes. Cette option fait varier le temps entre les requêtes entre 0,5 et 1,5 fois le temps spécifié par wait, où wait a été spécifié à l'aide de l'option --wait, afin de masquer la présence de Wget à une telle analyse.

Un article de 2001 dans une publication consacrée au développement sur une plateforme grand public populaire fournissait du code pour effectuer cette analyse à la volée. Son auteur suggérait de bloquer au niveau de l'adresse de classe C pour garantir que les programmes de récupération automatisés soient bloqués malgré les adresses fournies par DHCP.

L'option --random-wait s'inspire de cette recommandation malavisée de bloquer de nombreux utilisateurs non liés d'un site Web en raison des actions d'un seul.

--no-proxy
Ne pas utiliser de proxys, même si la variable d'environnement appropriée *_proxy est définie.
-Q quota
--quota=quota
Spécifie un quota de téléchargement pour les récupérations automatiques. La valeur peut être spécifiée en octets (par défaut), en kilo-octets (avec le suffixe k), ou en méga-octets (avec le suffixe m).

Notez que le quota n'affectera jamais le téléchargement d'un seul fichier. Donc, si vous spécifiez wget -Q10k https://example.com/ls-lR.gz, tout le fichier ls-lR.gz sera téléchargé. Il en va de même même lorsque plusieurs URL sont spécifiées sur la ligne de commande. Le quota n'est vérifié qu'à la fin de chaque fichier téléchargé, il ne se traduira donc jamais par un fichier partiellement téléchargé. Vous pouvez donc taper en toute sécurité wget -Q2m -i sites---le téléchargement sera interrompu après le téléchargement complet du fichier qui épuise le quota.

Définir le quota à 0 ou à inf supprime la limite du quota de téléchargement.

--no-dns-cache
Désactive la mise en cache des recherches DNS. Normalement, Wget mémorise les adresses IP qu'il a recherchées auprès du DNS afin de ne pas avoir à contacter à plusieurs reprises le serveur DNS pour les mêmes hôtes (généralement peu nombreux) à partir desquels il récupère des données. Ce cache existe uniquement en mémoire ; une nouvelle exécution de Wget contactera à nouveau le DNS.

Cependant, il a été signalé que dans certaines situations, il n'est pas souhaitable de mettre en cache les noms d'hôtes, même pendant la durée d'une application de courte durée comme Wget. Avec cette option, Wget effectue une nouvelle recherche DNS (plus précisément, un nouvel appel à "gethostbyname" ou "getaddrinfo") chaque fois qu'il établit une nouvelle connexion. Veuillez noter que cette option n'affectera pas la mise en cache potentiellement effectuée par la bibliothèque de résolution ou par une couche de mise en cache externe, telle que NSCD.

Si vous ne comprenez pas exactement ce que fait cette option, vous n'en aurez probablement pas besoin.

--restrict-file-names=modes
Change les caractères trouvés dans les URL distantes qui doivent être échappés lors de la génération des noms de fichiers locaux. Les caractères qui sont restreints par cette option sont échappés, c'est-à-dire remplacés par %HH, où HH est le nombre hexadécimal qui correspond au caractère restreint. Cette option peut également être utilisée pour forcer toutes les lettres à être en minuscule ou en majuscule.

Par défaut, Wget échappe les caractères qui ne sont pas valides ou sûrs en tant que noms de fichiers sur votre système d'exploitation, ainsi que les caractères de contrôle qui sont généralement non imprimables. Cette option est utile pour modifier ces valeurs par défaut, peut-être parce que vous téléchargez vers une partition non native, ou parce que vous souhaitez désactiver l'échappement des caractères de contrôle, ou que vous souhaitez restreindre davantage les caractères à ceux de la plage de valeurs ASCII.

Les modes sont un ensemble de valeurs textuelles séparées par des virgules. Les valeurs acceptables sont unix, windows, nocontrol, ascii, lowercase, et uppercase. Les valeurs unix et windows sont mutuellement exclusives (l'une remplacera l'autre), tout comme lowercase et uppercase. Ces dernières sont des cas particuliers, car elles ne modifient pas l'ensemble des caractères qui seraient échappés, mais forcent plutôt les chemins de fichiers locaux à être convertis en minuscules ou majuscules.

Lorsque « unix » est spécifié, Wget échappe le caractère / et les caractères de contrôle dans les plages 0-31 et 128-159. C'est le comportement par défaut sur les systèmes de type Unix.

Lorsque « windows » est donné, Wget échappe les caractères \, |, /, :, ?, ", *, <, >, et les caractères de contrôle dans les plages 0-31 et 128-159. De plus, Wget en mode Windows utilise + au lieu de : pour séparer l'hôte et le port dans les noms de fichiers locaux, et utilise @ au lieu de ? pour séparer la partie requête du nom de fichier du reste. Par conséquent, une URL qui serait enregistrée sous le nom www.xemacs.org:4300/search.pl?input=blah en mode Unix serait enregistrée sous le nom www.xemacs.org+4300/search.pl@input=blah en mode Windows. Ce mode est le comportement par défaut sous Windows.

Si vous spécifiez nocontrol, alors l'échappement des caractères de contrôle est également désactivé. Cette option peut avoir un sens lorsque vous téléchargez des URL dont les noms contiennent des caractères UTF-8, sur un système qui peut enregistrer et afficher des noms de fichiers en UTF-8 (certaines valeurs d'octets possibles utilisées dans les séquences d'octets UTF-8 tombent dans la plage de valeurs désignées par Wget comme « contrôles »).

Le mode ascii est utilisé pour spécifier que tout octet dont la valeur est en dehors de la plage des caractères ASCII (c'est-à-dire supérieure à 127) doit être échappé. Cela peut être utile lors de l'enregistrement de noms de fichiers dont l'encodage ne correspond pas à celui utilisé localement.

-4
--inet4-only
-6
--inet6-only
Force la connexion à des adresses IPv4 ou IPv6. Avec --inet4-only ou -4, Wget se connectera uniquement aux hôtes IPv4, ignorant les enregistrements AAAA dans le DNS, et refusant de se connecter aux adresses IPv6 spécifiées dans les URL. Inversement, avec --inet6-only ou -6, Wget se connectera uniquement aux hôtes IPv6 et ignorera les enregistrements A et les adresses IPv4.

Aucune de ces options ne devrait être nécessaire normalement. Par défaut, un Wget prenant en charge IPv6 utilisera la famille d'adresses spécifiée par l'enregistrement DNS de l'hôte. Si le DNS répond avec des adresses IPv4 et IPv6, Wget les essaiera séquentiellement jusqu'à ce qu'il en trouve une à laquelle il peut se connecter. (Voir également l'option "--prefer-family" décrite ci-dessous.)

Ces options peuvent être utilisées pour forcer délibérément l'utilisation des familles d'adresses IPv4 ou IPv6 sur les systèmes à double famille, généralement pour faciliter le débogage ou pour gérer une configuration réseau défectueuse. Une seule des options --inet6-only et --inet4-only peut être spécifiée

at the same time. Neither option is available in Wget compiled without IPv6 support.

--prefer-family=none/IPv4/IPv6
Lorsqu'un choix de plusieurs adresses est proposé, se connecter d'abord aux adresses de la famille d'adresses spécifiée. L'ordre des adresses renvoyé par le DNS est utilisé sans modification par défaut.

Cela évite des erreurs et des tentatives de connexion erronées lors de l'accès à des hôtes qui se résolvent à la fois en adresses IPv6 et IPv4 à partir de réseaux IPv4. Par exemple, www.kame.net se résout en 2001:200:0:8002:203:47ff:fea5:3085 et en 203.178.141.194. Lorsque la famille préférée est « IPv4 », l'adresse IPv4 est utilisée en premier ; lorsque la famille préférée est « IPv6 », l'adresse IPv6 est utilisée en premier ; si la valeur spécifiée est « none », l'ordre des adresses renvoyé par le DNS est utilisé sans modification.

Contrairement à -4 et -6, cette option n'empêche pas l'accès à une famille d'adresses, elle ne fait que modifier l' *ordre* dans lequel les adresses sont accédées. Notez également que le réordonnancement effectué par cette option est *stable*---il n'affecte pas l'ordre des adresses de la même famille. C'est-à-dire que l'ordre relatif de toutes les adresses IPv4 et de toutes les adresses IPv6 reste intact dans tous les cas.

--retry-connrefused
Considérer le « refus de connexion » comme une erreur transitoire et réessayer. Normalement, Wget abandonne une URL lorsqu'il ne parvient pas à se connecter au site car l'échec de connexion est considéré comme un signe que le serveur ne fonctionne pas du tout et que les nouvelles tentatives seraient inutiles. Cette option est destinée à la mise en miroir de sites peu fiables dont les serveurs ont tendance à disparaître pendant de courtes périodes.

--password=mot de passe
Spécifier le nom d'utilisateur utilisateur et le mot de passe mot de passe pour la récupération de fichiers FTP et HTTP. Ces paramètres peuvent être remplacés en utilisant les options --ftp-user et --ftp-password pour les connexions FTP et les options --http-user et --http-password pour les connexions HTTP.
--ask-password
Demander un mot de passe pour chaque connexion établie. Ne peut pas être spécifié lorsque --password est utilisé, car ils sont mutuellement exclusifs.
--use-askpass=commande
Demander un nom d'utilisateur et un mot de passe en utilisant la commande spécifiée. Si aucune commande n'est spécifiée, la commande de la variable d'environnement WGET_ASKPASS est utilisée. Si WGET_ASKPASS n'est pas définie, la commande de la variable d'environnement SSH_ASKPASS est utilisée.

Vous pouvez définir la commande par défaut pour use-askpass dans le fichier .wgetrc. Ce paramètre peut être remplacé depuis la ligne de commande.

--no-iri
Désactiver la prise en charge des URI internationalisés (IRI). Utilisez --iri pour l'activer. La prise en charge de l'IRI est activée par défaut.

Vous pouvez définir l'état par défaut de la prise en charge de l'IRI en utilisant la commande "iri" dans .wgetrc. Ce paramètre peut être remplacé depuis la ligne de commande.

--local-encoding=encodage
Forcer Wget à utiliser encodage comme encodage système par défaut. Cela affecte la façon dont Wget convertit les URL spécifiées comme arguments de la locale en UTF-8 pour la prise en charge de l'IRI.

Wget utilise la fonction nl_langinfo() puis la variable d'environnement "CHARSET" pour obtenir la locale. En cas d'échec, ASCII est utilisé.

Vous pouvez définir l'encodage local par défaut en utilisant la commande "local_encoding" dans .wgetrc. Ce paramètre peut être remplacé depuis la ligne de commande.

--remote-encoding=encodage
Forcer Wget à utiliser encodage comme encodage serveur distant par défaut. Cela affecte la façon dont Wget convertit les URI trouvés dans les fichiers de l'encodage distant en UTF-8 lors d'un téléchargement récursif. Cette option n'est utile que pour la prise en charge de l'IRI, pour l'interprétation des caractères non ASCII.

Pour HTTP, l'encodage distant peut être trouvé dans l'en-tête HTTP "Content-Type" et dans la balise méta HTML "Content-Type http-equiv".

Vous pouvez définir l'encodage par défaut en utilisant la commande "remoteencoding" dans .wgetrc. Ce paramètre peut être remplacé depuis la ligne de commande.

--unlink
Forcer Wget à supprimer le fichier au lieu d'écraser le fichier existant. Cette option est utile pour télécharger dans un répertoire avec des liens physiques.

Options de répertoire

-nd
--no-directories
Ne pas créer de hiérarchie de répertoires lors du téléchargement récursif. Avec cette option activée, tous les fichiers seront enregistrés dans le répertoire courant, sans écrasement (si un nom apparaît plus d'une fois, les noms de fichiers recevront des extensions .n).
-x
--force-directories
Le contraire de -nd---créer une hiérarchie de répertoires, même si une n'aurait pas été créée autrement. Par exemple, wget -x http://fly.srk.fer.hr/robots.txt enregistrera le fichier téléchargé dans fly.srk.fer.hr/robots.txt.
-nH
--no-host-directories
Désactiver la génération de répertoires préfixés par le nom d'hôte. Par défaut, appeler Wget avec -r http://fly.srk.fer.hr/ créera une structure de répertoires commençant par fly.srk.fer.hr/. Cette option désactive ce comportement.
--protocol-directories
Utiliser le nom du protocole comme composant de répertoire des noms de fichiers locaux. Par exemple, avec cette option, wget -r http://hôte enregistrera dans http/hôte/... plutôt que simplement dans hôte/....
--cut-dirs=nombre
Ignorer nombre composantes de répertoire. Ceci est utile pour obtenir un contrôle précis sur le répertoire où le téléchargement récursif sera enregistré.

Prenons, par exemple, le répertoire à l'adresse ftp://ftp.xemacs.org/pub/xemacs/. Si vous le téléchargez avec -r, il sera enregistré localement sous ftp.xemacs.org/pub/xemacs/. Bien que l'option -nH puisse supprimer la partie ftp.xemacs.org/, vous êtes toujours bloqué avec pub/xemacs. C'est là que --cut-dirs est utile ; elle fait que Wget ne « voit » pas nombre composantes de répertoire distant. Voici plusieurs exemples de la façon dont l'option --cut-dirs fonctionne.

Aucune option        -> ftp.xemacs.org/pub/xemacs/
-nH               -> pub/xemacs/
-nH --cut-dirs=1  -> xemacs/
-nH --cut-dirs=2  -> .

--cut-dirs=1      -> ftp.xemacs.org/xemacs/
...

Si vous voulez simplement vous débarrasser de la structure des répertoires, cette option est similaire à une combinaison de -nd et -P. Cependant, contrairement à -nd, --cut-dirs ne perd pas les sous-répertoires---par exemple, avec -nH --cut-dirs=1, un sous-répertoire beta/ sera placé dans xemacs/beta, comme on pourrait s'y attendre.

-P préfixe
--directory-prefix=préfixe
Définir le préfixe du répertoire à préfixe. Le préfixe du répertoire est le répertoire où tous les autres fichiers et sous-répertoires seront enregistrés, c'est-à-dire le sommet de l'arborescence de téléchargement. Le défaut est . (le répertoire courant).

Options HTTP

--default-page=nom
Utiliser nom comme nom de fichier par défaut lorsqu'il n'est pas connu (c'est-à-dire pour les URL se terminant par une barre oblique), au lieu de index.html.
-E
--adjust-extension
Si un fichier de type application/xhtml+xml ou text/html est téléchargé et que l'URL ne se termine pas par l'expression régulière \.[Hh][Tt][Mm][Ll]?, cette option ajoutera le suffixe .html au nom de fichier local. Ceci est utile, par exemple, lorsque vous mettez en miroir un site distant qui utilise des pages .asp, mais que vous souhaitez que les pages mises en miroir soient consultables sur votre serveur Apache standard. Une autre bonne utilisation est lors du téléchargement de contenus générés par CGI. Une URL comme http://site.com/article.cgi?25 sera enregistrée sous le nom article.cgi?25.html.

Notez que les noms de fichiers ainsi modifiés seront re-téléchargés à chaque fois que vous remettrez en miroir un site, car Wget ne peut pas déterminer que le fichier local X.html correspond à l'URL distante X (car il ne sait pas encore que l'URL produit une sortie de type text/html ou application/xhtml+xml.

À partir de la version 1.12, Wget s'assurera également que tous les fichiers téléchargés de type text/css se terminent par le suffixe .css, et l'option a été renommée de --html-extension, pour mieux refléter son nouveau comportement. L'ancien nom de l'option est toujours acceptable, mais doit maintenant être considéré comme obsolète.

À partir de la version 1.19.2, Wget s'assurera également que tous les fichiers téléchargés avec une "Content-Encoding" de br, compress, deflate ou gzip se terminent par le suffixe .br, .Z, .zlib et .gz respectivement.

À un moment donné dans le futur, cette option pourrait bien être étendue pour inclure les suffixes d'autres types de contenu, y compris les types de contenu qui ne sont pas analysés par Wget.

--http-user=utilisateur
--http-password=mot de passe
--user=user --password=password
Spécifiez le nom d'utilisateur user et le mot de passe password sur un serveur HTTP. Selon le type de défi, Wget les encodera en utilisant le schéma d'authentification "basic" (non sécurisé), "digest", ou "NTLM" de Windows.

Une autre façon de spécifier le nom d'utilisateur et le mot de passe est dans l'URL elle-même. Les deux méthodes révèlent votre mot de passe à quiconque prend la peine d'exécuter "ps". Pour éviter que les mots de passe ne soient vus, utilisez --use-askpass ou stockez-les dans .wgetrc ou .netrc, et assurez-vous de protéger ces fichiers des autres utilisateurs avec "chmod". Si les mots de passe sont vraiment importants, ne les laissez pas non plus traîner dans ces fichiers---modifiez les fichiers et supprimez-les après que Wget a lancé le téléchargement.

--no-http-keep-alive
Désactive la fonctionnalité « keep-alive » pour les téléchargements HTTP. Normalement, Wget demande au serveur de garder la connexion ouverte afin que, lorsque vous téléchargez plusieurs documents du même serveur, ils soient transférés via la même connexion TCP. Cela permet de gagner du temps et, en même temps, de réduire la charge du serveur.

Cette option est utile lorsque, pour une raison quelconque, les connexions persistantes (keep-alive) ne fonctionnent pas pour vous, par exemple en raison d'un bug du serveur ou de l'incapacité des scripts côté serveur à gérer les connexions.

--no-cache
Désactive le cache côté serveur. Dans ce cas, Wget enverra au serveur distant des directives appropriées (Cache-Control: no-cache et Pragma: no-cache) pour obtenir le fichier du service distant, plutôt que de retourner la version mise en cache. Ceci est particulièrement utile pour récupérer et vider les documents obsolètes sur les serveurs proxy.

La mise en cache est autorisée par défaut.

--no-cookies
Désactive l'utilisation des cookies. Les cookies sont un mécanisme de maintien de l'état côté serveur. Le serveur envoie un cookie au client à l'aide de l'en-tête "Set-Cookie", et le client répond avec le même cookie lors des requêtes ultérieures. Comme les cookies permettent aux propriétaires de sites de suivre les visiteurs et aux sites d'échanger ces informations, certains considèrent cela comme une violation de la vie privée. Par défaut, les cookies sont utilisés ; cependant, la conservation des cookies n'est pas activée par défaut.
--load-cookies fichier
Charge les cookies du fichier avant la première récupération HTTP. Le fichier est un fichier textuel dans le format utilisé à l'origine par le fichier cookies.txt de Netscape.

Vous utiliserez généralement cette option lors de la mise en miroir de sites qui exigent que vous soyez connecté pour accéder à tout ou partie de leur contenu. Le processus de connexion fonctionne généralement en faisant émettre un cookie HTTP par le serveur Web lors de la réception et de la vérification de vos identifiants. Le cookie est ensuite renvoyé par le navigateur lors de l'accès à cette partie du site, et prouve ainsi votre identité.

La mise en miroir d'un tel site nécessite que Wget envoie les mêmes cookies que votre navigateur envoie lors de la communication avec le site. Ceci est réalisé par --load-cookies---il suffit de pointer Wget vers l'emplacement du fichier cookies.txt, et il enverra les mêmes cookies que votre navigateur enverrait dans la même situation. Différents navigateurs conservent les fichiers de cookies textuels dans des emplacements différents :

"Netscape 4.x."
Les cookies se trouvent dans ~/.netscape/cookies.txt.
"Mozilla et Netscape 6.x."
Le fichier de cookies de Mozilla est également nommé cookies.txt, situé quelque part sous ~/.mozilla, dans le répertoire de votre profil. Le chemin complet ressemble généralement à ~/.mozilla/default/some-weird-string/cookies.txt.
"Internet Explorer."
Vous pouvez produire un fichier de cookies que Wget peut utiliser en utilisant le menu Fichier, Importer et exporter, Exporter les cookies. Cela a été testé avec Internet Explorer 5 ; cela ne garantit pas le fonctionnement avec les versions antérieures.
"Autres navigateurs."
Si vous utilisez un autre navigateur pour créer vos cookies, --load-cookies ne fonctionnera que si vous pouvez localiser ou produire un fichier de cookies au format Netscape que Wget attend.

Si vous ne pouvez pas utiliser --load-cookies, il pourrait y avoir une alternative. Si votre navigateur prend en charge un « gestionnaire de cookies », vous pouvez l'utiliser pour afficher les cookies utilisés lors de l'accès au site que vous mettez en miroir. Notez le nom et la valeur du cookie, et demandez manuellement à Wget d'envoyer ces cookies, en contournant le support officiel des cookies :

wget --no-cookies --header "Cookie: <name>=<value>"
--save-cookies fichier
Enregistre les cookies dans le fichier avant de quitter. Cela n'enregistrera pas les cookies qui ont expiré ou qui n'ont pas de date d'expiration (cookies dits « de session »), mais consultez également --keep-session-cookies.
--keep-session-cookies
Lorsque spécifié, fait que --save-cookies enregistre également les cookies de session. Les cookies de session ne sont normalement pas enregistrés car ils sont destinés à être conservés en mémoire et oubliés lorsque vous quittez le navigateur. Leur enregistrement est utile sur les sites qui vous demandent de vous connecter ou de visiter la page d'accueil avant de pouvoir accéder à certaines pages. Avec cette option, plusieurs exécutions de Wget sont considérées comme une seule session de navigateur en ce qui concerne le site.

Comme le format du fichier de cookies ne transporte normalement pas les cookies de session, Wget les marque avec un horodatage d'expiration de 0. --load-cookies de Wget reconnaît ceux-ci comme des cookies de session, mais cela pourrait confondre d'autres navigateurs. Notez également que les cookies ainsi chargés seront traités comme d'autres cookies de session, ce qui signifie que si vous souhaitez que --save-cookies les conserve à nouveau, vous devez à nouveau utiliser --keep-session-cookies.

--ignore-length
Malheureusement, certains serveurs HTTP (en particulier les programmes CGI) envoient des en-têtes "Content-Length" erronés, ce qui fait que Wget devient fou, car il pense que tout le document n'a pas été récupéré. Vous pouvez repérer ce symptôme si Wget essaie de récupérer le même document encore et encore, prétendant à chaque fois que la connexion (sinon normale) s'est fermée sur le même octet.

Avec cette option, Wget ignorera l'en-tête "Content-Length"---comme s'il n'avait jamais existé.

--header=ligne-en-tete
Envoie la ligne-en-tete avec le reste des en-têtes dans chaque requête HTTP. L'en-tête fourni est envoyé tel quel, ce qui signifie qu'il doit contenir le nom et la valeur séparés par deux points, et ne doit pas contenir de sauts de ligne.

Vous pouvez définir plusieurs en-têtes supplémentaires en spécifiant --header plusieurs fois.

wget --header='Accept-Charset: iso-8859-2' \
     --header='Accept-Language: hr'        \
       http://fly.srk.fer.hr/

La spécification d'une chaîne vide comme valeur d'en-tête effacera tous les en-têtes définis par l'utilisateur précédemment.

À partir de Wget 1.10, cette option peut être utilisée pour remplacer les en-têtes générés automatiquement. Cet exemple demande à Wget de se connecter à localhost, mais de spécifier foo.bar dans l'en-tête "Host" :

wget --header="Host: foo.bar" http://localhost/

Dans les versions de Wget antérieures à 1.10, l'utilisation de --header provoquait l'envoi d'en-têtes dupliqués.

--compression=type
Choisit le type de compression à utiliser. Les valeurs légales sont auto, gzip et none.

Si auto ou gzip sont spécifiés, Wget demande au serveur de compresser le fichier en utilisant le format de compression gzip. Si le serveur compresse le fichier et répond avec le champ d'en-tête "Content-Encoding" correctement défini, le fichier sera automatiquement décompressé.

Si none est spécifié, wget ne demandera pas au serveur de compresser le fichier et ne décompressera aucune réponse du serveur. C'est le comportement par défaut.

Le support de la compression est actuellement expérimental. S'il est activé, veuillez signaler tout bug à "bug-wget@gnu.org".

--max-redirect=nombre
Spécifie le nombre maximum de redirections à suivre pour une ressource. La valeur par défaut est 20, ce qui est généralement bien plus que nécessaire. Cependant, dans les cas où vous souhaitez en autoriser plus (ou moins), c'est l'option à utiliser.
--proxy-user=utilisateur
--proxy-password=motdepasse
Spécifiez le nom d'utilisateur utilisateur et le mot de passe motdepasse pour l'authentification sur un serveur proxy. Wget les encodera en utilisant le schéma d'authentification "basic".

Les considérations de sécurité similaires à celles de --http-password s'appliquent également ici.

--referer=url
Inclut l'en-tête `Referer: url' dans la requête HTTP. Utile pour récupérer des documents avec traitement côté serveur qui supposent qu'ils sont toujours récupérés par des navigateurs Web interactifs et qui ne fonctionnent correctement que lorsque Referer est défini sur l'une des pages qui y pointent.
--save-headers
Enregistre les en-têtes envoyés par le serveur HTTP dans le fichier, précédant le contenu réel, avec une ligne vide comme séparateur.
-U chaine-agent
--user-agent=chaine-agent
S'identifie comme chaine-agent auprès du serveur HTTP.

Le protocole HTTP permet aux clients de s'identifier à l'aide d'un champ d'en-tête "User-Agent". Cela permet de distinguer le logiciel WWW, généralement à des fins statistiques ou pour le suivi des violations de protocole. Wget s'identifie normalement comme Wget/version, version étant le numéro de version actuel de Wget.

Cependant, certains sites ont été connus pour imposer la politique de personnalisation de la sortie en fonction du

Options « User-Agent »

--user-agent=string
Ce paramètre vous permet de spécifier une chaîne de caractères qui sera envoyée comme en-tête "User-Agent" dans les requêtes HTTP. L'en-tête "User-Agent" est utilisé par les serveurs pour identifier le client (typiquement, un navigateur Web) qui accède à leurs ressources. Cependant, certains serveurs peuvent utiliser cette information pour refuser l'accès à des clients autres que certains navigateurs spécifiques (historiquement Netscape, ou plus fréquemment, Microsoft Internet Explorer). Cette option vous permet de modifier la ligne "User-Agent" émise par Wget. Son utilisation est déconseillée, sauf si vous savez réellement ce que vous faites.

Spécifier un agent utilisateur vide avec --user-agent="" demande à Wget de ne pas envoyer l'en-tête "User-Agent" dans les requêtes HTTP.

--post-data=string
--post-file=file
Utiliser la méthode POST pour toutes les requêtes HTTP et envoyer les données spécifiées dans le corps de la requête. --post-data envoie la chaîne string comme données, tandis que --post-file envoie le contenu du fichier file. Autrement, ils fonctionnent exactement de la même manière. En particulier, ils s'attendent *tous les deux* à un contenu de la forme "clé1=valeur1&clé2=valeur2", avec encodage pourcentage pour les caractères spéciaux ; la seule différence est que l'un attend son contenu sous forme de paramètre de ligne de commande et l'autre accepte son contenu depuis un fichier. En particulier, --post-file n'est *pas* destiné à la transmission de fichiers en tant que pièces jointes de formulaire : ceux-ci doivent apparaître sous forme de données "clé=valeur" (avec l'encodage pourcentage approprié), comme tout le reste. Wget ne prend actuellement pas en charge "multipart/form-data" pour la transmission de données POST ; seulement "application/x-www-form-urlencoded". Une seule des options --post-data et --post-file doit être spécifiée.

Veuillez noter que wget n'exige pas que le contenu soit de la forme "clé1=valeur1&clé2=valeur2", et ne vérifie pas non plus s'il l'est. Wget transmettra simplement les données qui lui sont fournies. La plupart des serveurs s'attendent cependant à ce que les données POST soient dans le format ci-dessus lors du traitement des formulaires HTML.

Lors de l'envoi d'une requête POST en utilisant l'option --post-file, Wget traite le fichier comme un fichier binaire et enverra chaque caractère dans la requête POST sans supprimer les caractères de fin de ligne ou de saut de page. Tous les autres caractères de contrôle dans le texte seront également envoyés tels quels dans la requête POST.

Veuillez noter que Wget doit connaître la taille des données POST à l'avance. Par conséquent, l'argument de "--post-file" doit être un fichier ordinaire ; spécifier un FIFO ou quelque chose comme /dev/stdin ne fonctionnera pas. Il n'est pas tout à fait clair comment contourner cette limitation inhérente à HTTP/1.0. Bien que HTTP/1.1 introduise le transfert *chunked* qui ne nécessite pas de connaître la longueur de la requête à l'avance, un client ne peut pas l'utiliser s'il ne sait pas qu'il communique avec un serveur HTTP/1.1. Et il ne peut pas le savoir avant d'avoir reçu une réponse, ce qui, à son tour, nécessite que la requête ait été complétée – un problème d'œuf et de poule.

Remarque : À partir de la version 1.15, si Wget est redirigé après l'achèvement de la requête POST, son comportement dépendra du code de réponse retourné par le serveur. En cas de 301 Moved Permanently, 302 Moved Temporarily ou 307 Temporary Redirect, Wget continuera, conformément à la RFC2616, à envoyer une requête POST. Si un serveur souhaite que le client change la méthode de requête lors de la redirection, il devrait envoyer un code de réponse 303 See Other.

Cet exemple montre comment se connecter à un serveur en utilisant POST puis télécharger les pages souhaitées, supposément accessibles uniquement aux utilisateurs autorisés :

# Connexion au serveur. Ceci ne peut être fait qu'une fois.
wget --save-cookies cookies.txt \
     --post-data 'user=foo&password=bar' \
     http://example.com/auth.php

# Maintenant, récupérer la page ou les pages qui nous intéressent.
wget --load-cookies cookies.txt \
     -p http://example.com/interesting/article.php

Si le serveur utilise des cookies de session pour suivre l'authentification de l'utilisateur, ce qui précède ne fonctionnera pas car --save-cookies ne les enregistrera pas (pas plus que les navigateurs) et le fichier cookies.txt sera vide. Dans ce cas, utilisez --keep-session-cookies avec --save-cookies pour forcer l'enregistrement des cookies de session.

--method=HTTP-Method
Dans le but de scripts RESTful, Wget permet d'envoyer d'autres méthodes HTTP sans avoir besoin de les définir explicitement avec --header=Header-Line. Wget utilisera toute chaîne qui lui est passée après --method comme méthode HTTP vers le serveur.
--body-data=Data-String
--body-file=Data-File
Doit être défini lorsque des données supplémentaires doivent être envoyées au serveur avec la méthode spécifiée via --method. --body-data envoie la chaîne string comme données, tandis que --body-file envoie le contenu du fichier file. Autrement, ils fonctionnent exactement de la même manière.

Actuellement, --body-file n'est *pas* destiné à transmettre des fichiers en tant que tels. Wget ne prend pas actuellement en charge "multipart/form-data" pour la transmission de données ; seulement "application/x-www-form-urlencoded". À l'avenir, cela pourrait être modifié pour que wget envoie le --body-file comme un fichier complet au lieu d'envoyer son contenu au serveur. Veuillez noter que Wget doit connaître le contenu des données du CORPS à l'avance, et par conséquent l'argument de --body-file devrait être un fichier ordinaire. Voir --post-file pour une explication plus détaillée. Une seule des options --body-data et --body-file devrait être spécifiée.

Si Wget est redirigé après la fin de la requête, Wget suspendra la méthode actuelle et enverra une requête GET jusqu'à ce que la redirection soit terminée. Ceci est valable pour tous les codes de réponse de redirection, sauf le 307 Temporary Redirect qui est utilisé pour spécifier explicitement que la méthode de requête ne doit *pas* changer. Une autre exception est lorsque la méthode est définie sur "POST", auquel cas les règles de redirection spécifiées sous --post-data sont suivies.

--content-disposition
Si cette option est activée, un support expérimental (pas encore entièrement fonctionnel) pour les en-têtes "Content-Disposition" est activé. Cela peut actuellement entraîner des allers-retours supplémentaires vers le serveur pour une requête "HEAD", et il est connu pour souffrir de quelques bugs, c'est pourquoi il n'est pas activé par défaut actuellement.

Cette option est utile pour certains programmes CGI de téléchargement de fichiers qui utilisent les en-têtes "Content-Disposition" pour décrire comment doit être nommé un fichier téléchargé.

Lorsqu'elle est combinée avec --metalink-over-http et --trust-server-names, un fichier Content-Type: application/metalink4+xml est nommé en utilisant le champ nom de fichier de "Content-Disposition", si disponible.

--content-on-error
Si cette option est activée, wget ne sautera pas le contenu lorsque le serveur répond avec un code d'état http indiquant une erreur.
--trust-server-names
Si cela est défini, lors d'une redirection, le nom de fichier local sera basé sur l'URL de redirection. Par défaut, le nom de fichier local est basé sur l'URL d'origine. Lors de récupérations récursives, cela peut être utile car sur de nombreux sites web, les URL redirigées correspondent à une structure de fichiers sous-jacente, tandis que les URL de liens ne le font pas.
--auth-no-challenge
Si cette option est donnée, Wget enverra des informations d'authentification HTTP basique (nom d'utilisateur et mot de passe en clair) pour toutes les requêtes, comme Wget 1.10.2 et les versions antérieures le faisaient par défaut.

L'utilisation de cette option n'est pas recommandée, et est destinée uniquement à prendre en charge quelques serveurs obscurs, qui n'envoient jamais de défis d'authentification HTTP, mais acceptent des informations d'authentification non sollicitées, par exemple, en plus de l'authentification basée sur les formulaires.

--retry-on-host-error
Considérer les erreurs d'hôte, telles que "Temporary failure in name resolution", comme des erreurs non fatales et transitoires.
--retry-on-http-error=code[,code,...]
Considérer les codes de réponse HTTP donnés comme des erreurs non fatales et transitoires. Fournir une liste de codes de réponse HTTP à 3 chiffres séparés par des virgules comme argument. Utile pour contourner des circonstances spéciales où des nouvelles tentatives sont nécessaires, mais le serveur répond avec un code d'erreur qui n'est normalement pas retenté par Wget. De telles erreurs pourraient être 503 (Service Unavailable) et 429 (Too Many Requests). Les nouvelles tentatives activées par cette option sont effectuées sous réserve des limitations normales de temporisation et de nombre de tentatives de Wget.

L'utilisation de cette option est destinée à supporter des cas d'utilisation spéciaux uniquement et n'est généralement pas recommandée, car elle peut forcer des nouvelles tentatives même dans des cas où le serveur essaie en réalité de diminuer sa charge. Veuillez l'utiliser judicieusement et uniquement si vous savez ce que vous faites.

Options HTTPS (SSL/TLS)

Pour prendre en charge les téléchargements HTTP cryptés (HTTPS), Wget doit être compilé avec une bibliothèque SSL externe. La valeur par défaut actuelle est GnuTLS. De plus, Wget prend en charge HSTS (HTTP Strict Transport Security). Si Wget est compilé sans prise en charge SSL, aucune de ces options n'est disponible.

--secure-protocol=protocol
Choisir le protocole sécurisé à utiliser. Les valeurs légales sont auto, SSLv2, SSLv3, TLSv1, TLSv1_1, TLSv1_2, TLSv1_3 et PFS. Si auto est utilisé, la bibliothèque SSL a la liberté de choisir le protocole approprié automatiquement, ce qui est réalisé en envoyant un message de bienvenue TLSv1. C'est le réglage par défaut.

Spécifier SSLv2, SSLv3, TLSv1, TLSv1_1, TLSv1_2 ou TLSv1_3 force l'utilisation du protocole correspondant. Ceci est utile lorsque l'on communique avec d'anciennes implémentations de serveurs SSL boguées qui rendent difficile pour la bibliothèque SSL sous-jacente de choisir la bonne version du protocole. Heureusement, de tels serveurs sont assez rares.

Spécifier PFS impose l'utilisation du soi-

appelé les suites de chiffrement Perfect Forward Security. En bref, PFS ajoute de la sécurité en créant une clé unique pour chaque connexion SSL. Il a un impact CPU légèrement plus important sur le client et le serveur. Nous utilisons des chiffrements connus pour être sécurisés (par exemple, pas de MD4) et le protocole TLS. Ce mode exclut également explicitement les méthodes d'échange de clés non-PFS, telles que RSA.

--https-only
En mode récursif, seuls les liens HTTPS sont suivis.
--ciphers
Définit la chaîne de listes de chiffrements. Typiquement, cette chaîne définit les suites de chiffrements et autres options SSL/TLS que l'utilisateur souhaite utiliser, dans un ordre de préférence défini (GnuTLS appelle cela une 'chaîne de priorité'). Cette chaîne sera transmise telle quelle au moteur SSL/TLS (OpenSSL ou GnuTLS) et sa forme et sa syntaxe dépendent donc de celui-ci. Wget ne la traitera ni ne la manipulera d'aucune manière. Consultez la documentation OpenSSL ou GnuTLS pour plus d'informations.
--no-check-certificate
Ne vérifie pas le certificat du serveur par rapport aux autorités de certification disponibles. N'exige pas non plus que le nom d'hôte de l'URL corresponde au nom commun présenté par le certificat.

Depuis Wget 1.10, la vérification du certificat du serveur par rapport aux autorités de certification reconnues est activée par défaut, ce qui interrompt la négociation SSL et abandonne le téléchargement en cas d'échec de la vérification. Bien que cela offre des téléchargements plus sécurisés, cela rompt l'interopérabilité avec certains sites qui fonctionnaient avec les versions précédentes de Wget, en particulier ceux utilisant des certificats auto-signés, expirés ou autrement invalides. Cette option force un mode de fonctionnement « non sécurisé » qui transforme les erreurs de vérification de certificat en avertissements et vous permet de continuer.

Si vous rencontrez des erreurs de « vérification de certificat » ou des messages indiquant que « le nom commun ne correspond pas au nom d'hôte demandé », vous pouvez utiliser cette option pour contourner la vérification et poursuivre le téléchargement. Utilisez cette option uniquement si vous êtes autrement convaincu de l'authenticité du site, ou si la validité de son certificat ne vous importe pas réellement. Il est presque toujours déconseillé de ne pas vérifier les certificats lors de la transmission de données confidentielles ou importantes. Pour les certificats auto-signés/internes, vous devriez télécharger le certificat et vérifier par rapport à celui-ci au lieu de forcer ce mode non sécurisé. Si vous êtes vraiment certain de ne pas vouloir de vérification de certificat, vous pouvez spécifier --check-certificate=quiet pour dire à wget de ne pas afficher d'avertissement concernant les certificats invalides, bien que dans la plupart des cas, ce soit une mauvaise idée.

--certificate=fichier
Utilise le certificat client stocké dans fichier. Ceci est nécessaire pour les serveurs configurés pour exiger des certificats de la part des clients qui s'y connectent. Normalement, un certificat n'est pas requis et ce commutateur est facultatif.
--certificate-type=type
Spécifie le type du certificat client. Les valeurs légales sont PEM (par défaut) et DER, également connu sous le nom d'ASN1.
--private-key=fichier
Lit la clé privée à partir de fichier. Ceci vous permet de fournir la clé privée dans un fichier séparé du certificat.
--private-key-type=type
Spécifie le type de la clé privée. Les valeurs acceptées sont PEM (par défaut) et DER.
--ca-certificate=fichier
Utilise fichier comme fichier contenant le paquet d'autorités de certification (« CA ») pour vérifier les pairs. Les certificats doivent être au format PEM.

Sans cette option, Wget recherche les certificats CA dans les emplacements spécifiés par le système, choisis lors de l'installation d'OpenSSL.

--ca-directory=répertoire
Spécifie le répertoire contenant les certificats CA au format PEM. Chaque fichier contient un certificat CA, et le nom du fichier est basé sur une valeur de hachage dérivée du certificat. Ceci est réalisé en traitant un répertoire de certificats avec l'utilitaire "c_rehash" fourni avec OpenSSL. L'utilisation de --ca-directory est plus efficace que --ca-certificate lorsque de nombreux certificats sont installés, car elle permet à Wget de récupérer les certificats à la demande.

Sans cette option, Wget recherche les certificats CA dans les emplacements spécifiés par le système, choisis lors de l'installation d'OpenSSL.

--crl-file=fichier
Spécifie un fichier CRL dans fichier. Ceci est nécessaire pour les certificats qui ont été révoqués par les CA.
--pinnedpubkey=fichier/hachages
Indique à wget d'utiliser le fichier de clé publique spécifié (ou des hachages) pour vérifier le pair. Il peut s'agir d'un chemin vers un fichier contenant une seule clé publique au format PEM ou DER, ou de n'importe quel nombre de hachages sha256 encodés en base64 précédés de « sha256// » et séparés par « ; »

Lors de la négociation d'une connexion TLS ou SSL, le serveur envoie un certificat indiquant son identité. Une clé publique est extraite de ce certificat et si elle ne correspond pas exactement aux clés publiques fournies dans cette option, wget interrompra la connexion avant d'envoyer ou de recevoir des données.

--random-file=fichier
[OpenSSL et LibreSSL uniquement] Utilise fichier comme source de données aléatoires pour l'initialisation du générateur de nombres pseudo-aléatoires sur les systèmes sans /dev/urandom.

Sur de tels systèmes, la bibliothèque SSL a besoin d'une source externe d'aléatoire pour s'initialiser. L'aléatoire peut être fourni par EGD (voir --egd-file ci-dessous) ou lu à partir d'une source externe spécifiée par l'utilisateur. Si cette option n'est pas spécifiée, Wget recherche des données aléatoires dans $RANDFILE ou, si celui-ci n'est pas défini, dans $HOME/.rnd.

Si vous obtenez l'erreur « Could not seed OpenSSL PRNG; disabling SSL. », vous devriez fournir des données aléatoires en utilisant certaines des méthodes décrites ci-dessus.

--egd-file=fichier
[OpenSSL uniquement] Utilise fichier comme socket EGD. EGD signifie Entropy Gathering Daemon (Démon de collecte d'entropie), un programme en espace utilisateur qui collecte des données à partir de diverses sources système imprévisibles et les met à la disposition d'autres programmes qui pourraient en avoir besoin. Les logiciels de cryptographie, tels que la bibliothèque SSL, ont besoin de sources d'aléatoire non répétitives pour initialiser le générateur de nombres aléatoires utilisé pour produire des clés cryptographiquement fortes.

OpenSSL permet à l'utilisateur de spécifier sa propre source d'entropie en utilisant la variable d'environnement "RAND_FILE". Si cette variable n'est pas définie, ou si le fichier spécifié ne produit pas suffisamment d'aléatoire, OpenSSL lira des données aléatoires depuis le socket EGD spécifié à l'aide de cette option.

Si cette option n'est pas spécifiée (et que la commande de démarrage équivalente n'est pas utilisée), EGD n'est jamais contacté. EGD n'est pas nécessaire sur les systèmes Unix modernes qui prennent en charge /dev/urandom.

--no-hsts
Wget prend en charge HSTS (HTTP Strict Transport Security, RFC 6797) par défaut. Utilisez --no-hsts pour que Wget agisse comme un UA non conforme à HSTS. En conséquence, Wget ignorerait tous les en-têtes "Strict-Transport-Security" et n'appliquerait aucune politique HSTS existante.
--hsts-file=fichier
Par défaut, Wget stocke sa base de données HSTS dans ~/.wget-hsts. Vous pouvez utiliser --hsts-file pour outrepasser cela. Wget utilisera le fichier fourni comme base de données HSTS. Un tel fichier doit être conforme au format correct de base de données HSTS utilisé par Wget. Si Wget ne peut pas analyser le fichier fourni, le comportement n'est pas spécifié.

La base de données HSTS de Wget est un fichier texte brut. Chaque ligne contient une entrée HSTS (c'est-à-dire un site qui a émis un en-tête "Strict-Transport-Security" et qui a donc spécifié une politique HSTS concrète à appliquer). Les lignes commençant par un tiret ("#") sont ignorées par Wget. Veuillez noter que malgré cette lisibilité humaine pratique, la manipulation de la base de données HSTS n'est généralement pas une bonne idée.

Une ligne d'entrée HSTS se compose de plusieurs champs séparés par un ou plusieurs espaces blancs :

"<nom_hôte> ESPACE [<port>] ESPACE <inclure_sous_domaines> ESPACE <créé> ESPACE <max-age>"

Les champs nom_hôte et port indiquent le nom d'hôte et le port auxquels s'applique la politique HSTS donnée. Le champ port peut être zéro, et ce sera le cas dans la plupart des situations. Cela signifie que le numéro de port ne sera pas pris en compte lors de la détermination si une telle politique HSTS doit être appliquée à une requête donnée (seul le nom d'hôte sera évalué). Lorsque port est différent de zéro, le nom d'hôte cible et le port seront tous deux évalués et la politique HSTS ne sera appliquée que si les deux correspondent. Cette fonctionnalité a été incluse uniquement à des fins de test/développement. La suite de tests de Wget (dans testenv/) crée des bases de données HSTS avec des ports explicites dans le but d'assurer le comportement correct de Wget. L'application des politiques HSTS à des ports autres que les ports par défaut est déconseillée par le RFC 6797 (voir l'Annexe B « Différences entre la politique HSTS et la politique Same-Origin »). Par conséquent, cette fonctionnalité ne doit pas être utilisée dans des environnements de production et le port sera généralement zéro. Les trois derniers champs font ce qu'on attend d'eux. Le champ include_subdomains peut être 1 ou 0 et il indique si les sous-domaines du domaine cible doivent également faire partie de la politique HSTS donnée. Les champs created et max-age contiennent les valeurs d'horodatage du moment où une telle entrée a été créée (vue pour la première fois par Wget) et la valeur définie par HSTS 'max-age', qui indique combien de temps cette politique HSTS doit rester active, mesurée en secondes écoulées depuis l'horodatage stocké dans created. Une fois ce délai passé, cette politique HSTS ne sera plus valide et sera éventuellement supprimée de la base de données.

Si vous fournissez votre propre base de données HSTS via --hsts-file, sachez que Wget peut modifier le fichier fourni si des modifications surviennent entre th

e les stratégies HSTS demandées par les serveurs distants et celles du fichier. Lorsque Wget se termine, il met effectivement à jour la base de données HSTS en réécrivant le fichier de base de données avec les nouvelles entrées.

Si le fichier fourni n'existe pas, Wget en créera un. Ce fichier contiendra les nouvelles entrées HSTS. Si aucune entrée HSTS n'a été générée (aucun en-tête "Strict-Transport-Security" n'a été envoyé par l'un des serveurs), alors aucun fichier ne sera créé, pas même un fichier vide. Ce comportement s'applique également au fichier de base de données par défaut (~/.wget-hsts) : il ne sera pas créé tant qu'aucun serveur n'appliquera de politique HSTS.

Des précautions sont prises pour ne pas écraser les modifications éventuelles apportées par d'autres processus Wget en même temps sur la base de données HSTS. Avant de sauvegarder les entrées HSTS mises à jour dans le fichier, Wget le relira et fusionnera les modifications.

L'utilisation d'une base de données HSTS personnalisée et/ou la modification d'une base de données existante sont déconseillées. Pour plus d'informations sur les menaces de sécurité potentielles découlant d'une telle pratique, consultez la section 14 « Considérations de sécurité » de la RFC 6797, en particulier la section 14.9 « Manipulation créative du magasin de politique HSTS ».

Options FTP

--ftp-user=utilisateur
--ftp-password=motdepasse
Spécifie le nom d'utilisateur utilisateur et le mot de passe motdepasse sur un serveur FTP. Sans cela, ou l'option de démarrage correspondante, le mot de passe est par défaut -wget@, normalement utilisé pour le FTP anonyme.

Une autre façon de spécifier le nom d'utilisateur et le mot de passe est dans l'URL elle-même. Chaque méthode révèle votre mot de passe à quiconque prend la peine d'exécuter "ps". Pour empêcher la visualisation des mots de passe, stockez-les dans .wgetrc ou .netrc, et assurez-vous de protéger ces fichiers contre les autres utilisateurs avec "chmod". Si les mots de passe sont vraiment importants, ne les laissez pas non plus dans ces fichiers — éditez les fichiers et supprimez-les une fois que Wget a commencé le téléchargement.

--no-remove-listing
Ne supprime pas les fichiers temporaires .listing générés par les récupérations FTP. Normalement, ces fichiers contiennent les listes de répertoires brutes reçues des serveurs FTP. Ne pas les supprimer peut être utile à des fins de débogage, ou lorsque vous souhaitez pouvoir vérifier facilement le contenu des répertoires du serveur distant (par exemple, pour vérifier qu'un miroir que vous exécutez est complet).

Notez que même si Wget écrit dans un nom de fichier connu pour ce fichier, ce n'est pas une faille de sécurité dans le scénario d'un utilisateur faisant de .listing un lien symbolique vers /etc/passwd ou quelque chose de similaire et demandant à "root" d'exécuter Wget dans son répertoire. Selon les options utilisées, soit Wget refusera d'écrire dans .listing, ce qui fera échouer l'opération de globbing/récursion/horodatage, soit le lien symbolique sera supprimé et remplacé par le fichier .listing réel, soit la liste sera écrite dans un fichier .listing.numéro.

Même si cette situation n'est pas un problème, "root" ne devrait jamais exécuter Wget dans le répertoire d'un utilisateur non fiable. Un utilisateur pourrait faire quelque chose d'aussi simple que de lier index.html à /etc/passwd et demander à "root" d'exécuter Wget avec -N ou -r afin que le fichier soit écrasé.

--no-glob
Désactive le globbing FTP. Le globbing fait référence à l'utilisation de caractères spéciaux ressemblant à des shells (caractères génériques), tels que *, ?, [ et ] pour récupérer plusieurs fichiers du même répertoire à la fois, par exemple : 
wget ftp://gnjilux.srk.fer.hr/*.msg

Par défaut, le globbing sera activé si l'URL contient un caractère de globbing. Cette option peut être utilisée pour activer ou désactiver le globbing de manière permanente.

Vous devrez peut-être mettre l'URL entre guillemets pour l'empêcher d'être développée par votre shell. Le globbing amène Wget à rechercher une liste de répertoire, ce qui est spécifique au système. C'est pourquoi cela fonctionne actuellement uniquement avec les serveurs FTP Unix (et ceux qui émulent la sortie "ls" d'Unix).

--no-passive-ftp
Désactive l'utilisation du mode de transfert FTP passif. Le FTP passif impose au client de se connecter au serveur pour établir la connexion de données plutôt que l'inverse.

Si la machine est connectée directement à Internet, le FTP passif et actif devraient fonctionner de la même manière. Derrière la plupart des configurations de pare-feu et de NAT, le FTP passif a une meilleure chance de fonctionner. Cependant, dans certaines rares configurations de pare-feu, le FTP actif fonctionne réellement lorsque le FTP passif ne fonctionne pas. Si vous suspectez que c'est le cas, utilisez cette option, ou définissez "passive_ftp=off" dans votre fichier d'initialisation.

--preserve-permissions
Conserve les permissions de fichiers distants au lieu des permissions définies par umask.
--retr-symlinks
Par défaut, lors de la récupération récursive de répertoires FTP et qu'un lien symbolique est rencontré, le lien symbolique est parcouru et les fichiers pointés sont récupérés. Actuellement, Wget ne parcourt pas les liens symboliques vers des répertoires pour les télécharger récursivement, bien que cette fonctionnalité puisse être ajoutée à l'avenir.

Lorsque --retr-symlinks=no est spécifié, le fichier lié n'est pas téléchargé. Au lieu de cela, un lien symbolique correspondant est créé sur le système de fichiers local. Le fichier pointé ne sera pas récupéré à moins que cette récupération récursive ne l'ait rencontré séparément et téléchargé. Cette option présente un risque de sécurité où un serveur FTP malveillant peut amener Wget à écrire dans des fichiers en dehors des répertoires prévus via un fichier .LISTING spécialement conçu.

Notez que lors de la récupération d'un fichier (pas d'un répertoire) parce qu'il était spécifié sur la ligne de commande, plutôt que parce qu'il a été parcouru récursivement, cette option n'a aucun effet. Les liens symboliques sont toujours parcourus dans ce cas.

Options FTPS

--ftps-implicit
Cette option indique à Wget d'utiliser FTPS implicitement. FTPS implicite consiste à initialiser SSL/TLS dès le début de la connexion de contrôle. Cette option n'envoie pas de commande "AUTH TLS" : elle suppose que le serveur parle FTPS et établit directement une connexion SSL/TLS. Si la tentative réussit, la session continue comme un FTPS régulier (des commandes "PBSZ" et "PROT" sont envoyées, etc.). FTPS implicite n'est plus une exigence pour les implémentations FTPS, et donc de nombreux serveurs peuvent ne pas le supporter. Si --ftps-implicit est passé et qu'aucun numéro de port explicite n'est spécifié, le port par défaut pour FTPS implicite, 990, sera utilisé, au lieu du port par défaut pour FTPS « normal » (explicite) qui est le même que celui de FTP, 21.
--no-ftps-resume-ssl
Ne pas reprendre la session SSL/TLS dans le canal de données. Lors de l'établissement d'une connexion de données, Wget essaie de reprendre la session SSL/TLS précédemment établie dans la connexion de contrôle. La reprise de session SSL/TLS évite d'effectuer une nouvelle négociation en réutilisant les paramètres SSL/TLS d'une session précédente. Typiquement, les serveurs FTPS le souhaitent ainsi, Wget le fait donc par défaut. Dans de rares circonstances, cependant, on pourrait vouloir démarrer une nouvelle session SSL/TLS dans chaque connexion de données. C'est à cela que sert --no-ftps-resume-ssl.
--ftps-clear-data-connection
Toutes les connexions de données seront en texte clair. Seule la connexion de contrôle sera sous SSL/TLS. Wget enverra une commande "PROT C" pour y parvenir, ce qui doit être approuvé par le serveur.
--ftps-fallback-to-ftp
Revenez à FTP si FTPS n'est pas pris en charge par le serveur cible. Pour des raisons de sécurité, cette option n'est pas activée par défaut. Le comportement par défaut est de sortir avec une erreur. Si un serveur ne répond pas avec succès à la commande initiale "AUTH TLS", ou dans le cas de FTPS implicite, si la tentative de connexion SSL/TLS initiale est rejetée, il est considéré que ce serveur ne prend pas en charge FTPS.

Options de Récupération Récursive

-r
--recursive
Active la récupération récursive. La profondeur maximale par défaut est de 5.
-l profondeur
--level=profondeur
Définit le nombre maximum de sous-répertoires dans lesquels Wget va récursivement naviguer à profondeur. Afin d'éviter de télécharger accidentellement des sites web très volumineux lors de l'utilisation de la récursion
ce qui est limité par défaut à une profondeur de 5, c'est-à-dire qu'il parcourra au maximum 5 répertoires de profondeur à partir de l'URL fournie. Définissez -l 0 ou -l inf pour une profondeur de récursion infinie. 
wget -r -l 0 http://<site>/1.html

Idéalement, on s'attendrait à ce que cela ne télécharge que 1.html. Mais malheureusement, ce n'est pas le cas, car -l 0 est équivalent à -l inf, c'est-à-dire une récursion infinie. Pour télécharger une seule page HTML (ou une poignée d'entre elles), spécifiez-les toutes sur la ligne de commande et retirez -r et -l. Pour télécharger les éléments essentiels pour afficher une seule page HTML, voir requis de page.

--delete-after
Cette option indique à Wget de supprimer chaque fichier qu'il télécharge, après l'avoir fait. Elle est utile pour pré-charger des pages populaires via un proxy, par exemple : 
wget -r -nd --delete-after http://whatever.com/~popular/page/

L'option -r sert à récupérer récursivement, et -nd à ne pas créer de répertoires.

Notez que --delete-after supprime les fichiers sur la machine locale. Elle n'envoie pas la commande DELE aux sites FTP distants, par exemple. Notez également que lorsque --delete-after est spécifié, --convert-links est ignoré, de sorte que les fichiers .orig ne sont tout simplement pas créés en premier lieu.

-k
--convert-links
Une fois le téléchargement terminé, convertit les liens du document pour les rendre appropriés à une visualisation locale. Cela affecte non seulement les hyperliens visibles, mais toute partie du document qui fait référence à du contenu externe, telle que les images intégrées, les liens vers des feuilles de style, les hyperliens vers du contenu non HTML, etc.

Chaque lien sera modifié de l'une des deux manières suivantes :

  • Les liens vers les fichiers qui ont été téléchargés par Wget seront modifiés pour faire référence au fichier qu'ils pointent comme lien relatif.

    Exemple : si le fichier téléchargé /foo/doc.html pointe vers /bar/img.gif, également téléchargé, le lien dans doc.html sera modifié pour pointer vers ../bar/img.gif. Ce type de transformation fonctionne de manière fiable pour des combinaisons arbitraires de répertoires.

  • Les liens vers les fichiers qui n'ont pas été téléchargés par Wget seront modifiés pour inclure le nom d'hôte et le chemin absolu de l'emplacement auquel ils pointent.

    Exemple : si le fichier téléchargé /foo/doc.html pointe vers /bar/img.gif (ou vers ../bar/img.gif), alors le lien dans doc.html sera modifié pour pointer vers http://hostname/bar/img.gif.

Grâce à cela, la navigation locale fonctionne de manière fiable : si un fichier lié a été téléchargé, le lien fera référence à son nom local ; s'il n'a pas été téléchargé, le lien fera référence à son adresse Internet complète plutôt que de présenter un lien brisé. Le fait que les premiers liens soient convertis en liens relatifs garantit que vous pouvez déplacer la hiérarchie téléchargée vers un autre répertoire.

Notez que ce n'est qu'à la fin du téléchargement que Wget peut savoir quels liens ont été téléchargés. Pour cette raison, le travail effectué par -k sera effectué à la fin de tous les téléchargements.

--convert-file-only
Cette option convertit uniquement la partie nom de fichier des URL, laissant le reste des URL inchangé. Cette partie nom de fichier est parfois appelée le « basename », bien que nous évitions ce terme ici afin de ne pas causer de confusion.

Elle fonctionne particulièrement bien en conjonction avec --adjust-extension, bien que cette association ne soit pas obligatoire. Elle s'avère utile pour peupler les caches Internet avec des fichiers téléchargés depuis différents hôtes.

Exemple : si un lien pointe vers //foo.com/bar.cgi?xyz avec --adjust-extension activé et que sa destination locale est censée être ./foo.com/bar.cgi?xyz.css, alors le lien serait converti en //foo.com/bar.cgi?xyz.css. Notez que seule la partie nom de fichier a été modifiée. Le reste de l'URL a été laissé inchangé, y compris le chemin réseau ("//") qui serait autrement traité par Wget et converti en schéma effectif (c'est-à-dire "http://").

-K
--backup-converted
Lors de la conversion d'un fichier, sauvegardez la version originale avec un suffixe .orig. Affecte le comportement de -N.
-m
--mirror
Active les options appropriées pour la mise en miroir. Cette option active la récursion et l'horodatage, définit une profondeur de récursion infinie et conserve les listes de répertoires FTP. Elle est actuellement équivalente à -r -N -l inf --no-remove-listing.
-p
--page-requisites
Cette option permet à Wget de télécharger tous les fichiers nécessaires à l'affichage correct d'une page HTML donnée. Cela inclut les images intégrées, les sons et les feuilles de style référencées.

Normalement, lors du téléchargement d'une seule page HTML, tous les documents requis qui pourraient être nécessaires pour l'afficher correctement ne sont pas téléchargés. L'utilisation de -r conjointement avec -l peut aider, mais comme Wget ne distingue pas normalement les documents externes des documents intégrés, on se retrouve généralement avec des « documents feuilles » qui manquent de leurs requis.

Par exemple, disons que le document 1.html contient une balise "<IMG>" faisant référence à 1.gif et une balise "<A>" pointant vers le document externe 2.html. Disons que 2.html est similaire mais que son image est 2.gif et qu'il pointe vers 3.html. Disons que cela continue jusqu'à un nombre arbitrairement élevé.

Si l'on exécute la commande :

wget -r -l 2 http://<site>/1.html

alors 1.html, 1.gif, 2.html, 2.gif, et 3.html seront téléchargés. Comme vous pouvez le voir, 3.html est sans son requis 3.gif car Wget compte simplement le nombre de sauts (jusqu'à 2) à partir de 1.html pour déterminer où arrêter la récursion. Cependant, avec cette commande :

wget -r -l 2 -p http://<site>/1.html

tous les fichiers ci-dessus et le requis 3.gif de 3.html seront téléchargés. De même, 

wget -r -l 1 -p http://<site>/1.html

provoquera le téléchargement de 1.html, 1.gif, 2.html, et 2.gif. On pourrait penser que :

wget -r -l 0 -p http://<site>/1.html

ne téléchargerait que 1.html et 1.gif, mais malheureusement ce n'est pas le cas, car -l 0 est équivalent à -l inf, c'est-à-dire une récursion infinie. Pour télécharger une seule page HTML (ou une poignée d'entre elles, toutes spécifiées sur la ligne de commande ou dans un fichier d'entrée d'URL -i) et ses (leurs) requis, laissez simplement tomber -r et -l :

wget -p http://<site>/1.html

Notez que Wget se comportera comme si -r avait été spécifié, mais seule cette page unique et ses requis seront téléchargés. Les liens de cette page vers des documents externes ne seront pas suivis. En fait, pour télécharger une seule page et tous ses requis (même s'ils existent sur des sites Web distincts), et s'assurer que l'ensemble s'affiche correctement localement, cet auteur aime utiliser quelques options en plus de -p :

wget -E -H -k -K -p http://<site>/<document>

Pour conclure ce sujet, il est utile de savoir que la conception de Wget d'un lien de document externe est toute URL spécifiée dans une balise "<A>", une balise "<AREA>", ou une balise "<LINK>" autre que "<LINK REL="stylesheet">".

--strict-comments
Active l'analyse stricte des commentaires HTML. Par défaut, les commentaires sont terminés à la première occurrence de -->.

Selon les spécifications, les commentaires HTML sont exprimés comme des déclarations SGML. Une déclaration est une balise spéciale qui commence par <! et se termine par >, comme <!DOCTYPE ...>, qui peut contenir des commentaires entre une paire de délimiteurs --. Les commentaires HTML sont des « déclarations vides », des déclarations SGML sans aucun texte autre que des commentaires. Par conséquent, <!--foo--> est un commentaire valide, tout comme <!--one-- --two-->, mais <!--1--2--> ne l'est pas.

D'un autre côté, la plupart des auteurs HTML ne perçoivent pas les commentaires autrement que comme du texte délimité par <!-- et -->, ce qui n'est pas tout à fait la même chose. Par exemple, quelque chose comme <!------------> fonctionne comme un commentaire valide tant que le nombre de tirets est un multiple de quatre (!). Sinon, le commentaire dure techniquement jusqu'au prochain --, qui peut se trouver à l'autre extrémité du document. Pour cette raison, de nombreux navigateurs populaires ignorent complètement la spécification et implémentent ce que les utilisateurs ont fini par attendre : des commentaires délimités par <!-- et -->.

Jusqu'à la version 1.9, Wget interprétait les commentaires de manière stricte, ce qui entraînait la perte de liens dans de nombreuses pages Web qui s'affichaient correctement dans les navigateurs, mais qui avaient le malheur de contenir des commentaires non conformes. À partir de la version 1.9, Wget a rejoint le rang des clients qui implémentent des commentaires « naïfs », terminant chaque commentaire à la première occurrence de -->.

Si, pour une raison quelconque, vous souhaitez une analyse stricte des commentaires, utilisez cette option pour l'activer.

Options de refus/acceptation récursives

-A liste_acceptée --accept liste_acceptée
-R liste_refusée --reject liste_refusée
Spécifie des listes de suffixes ou de motifs de noms de fichiers séparés par des virgules à accepter ou à refuser. Notez que si l'un des
caractères joker, *, ?, [ ou ], apparaissent dans un élément de acclist ou rejlist, il sera traité comme un motif, plutôt qu'un suffixe. Dans ce cas, vous devez encadrer le motif entre guillemets pour éviter que votre shell ne l'étende, comme dans -A "*.mp3" ou -A '*.mp3'.

--reject-regex urlregex
Spécifiez une expression régulière pour accepter ou rejeter l'URL complète.
--regex-type regextype
Spécifiez le type d'expression régulière. Les types possibles sont posix ou pcre. Notez que pour pouvoir utiliser le type pcre, wget doit être compilé avec le support de libpcre.
-D domain-list
--domains=domain-list
Définissez les domaines à suivre. domain-list est une liste de domaines séparés par des virgules. Notez que cela n'active pas l'option -H.
--exclude-domains domain-list
Spécifiez les domaines qui ne doivent pas être suivis.
--follow-ftp
Suivre les liens FTP depuis les documents HTML. Sans cette option, Wget ignorera tous les liens FTP.
--follow-tags=list
Wget possède une table interne de paires balise/attribut HTML qu'il considère lors de la recherche de documents liés pendant un téléchargement récursif. --ignore-tags=list
Ceci est l'inverse de l'option --follow-tags. Pour ignorer certaines balises HTML lors de la recherche récursive de documents à télécharger, spécifiez-les dans une liste séparée par des virgules.

Auparavant, cette option était la meilleure approche pour télécharger une page unique et ses requis, en utilisant une commande comme :

wget --ignore-tags=a,area -H -k -K -r http://<site>/<document>

Cependant, l'auteur de cette option a rencontré une page avec des balises comme "<LINK REL="home" HREF="/">" et a réalisé que spécifier les balises à ignorer n'était pas suffisant. On ne peut pas simplement dire à Wget d'ignorer "<LINK>", car alors les feuilles de style ne seraient pas téléchargées. Désormais, la meilleure approche pour télécharger une page unique et ses requis est l'option dédiée --page-requisites.

--ignore-case
Ignorer la casse lors de la correspondance des fichiers et des répertoires. Cela influence le comportement des options -R, -A, -I et -X, ainsi que l'expansion des motifs implémentée lors du téléchargement depuis des sites FTP. Par exemple, avec cette option, -A "*.txt" correspondra à file1.txt, mais aussi à file2.TXT, file3.TxT, et ainsi de suite. Les guillemets dans l'exemple servent à empêcher le shell d'étendre le motif.
-H
--span-hosts
Activer le parcours entre les hôtes lors d'un téléchargement récursif.
-L
--relative
Suivre uniquement les liens relatifs. Utile pour télécharger une page d'accueil spécifique sans aucune distraction, même celles provenant du même hôte.
-I list
--include-directories=list
Spécifiez une liste de répertoires séparés par des virgules que vous souhaitez suivre lors du téléchargement. Les éléments de list peuvent contenir des jokers.
-X list
--exclude-directories=list
Spécifiez une liste de répertoires séparés par des virgules que vous souhaitez exclure du téléchargement. Les éléments de list peuvent contenir des jokers.
-np
--no-parent
Ne jamais remonter au répertoire parent lors d'un téléchargement récursif. C'est une option utile, car elle garantit que seuls les fichiers situés en dessous d'une certaine hiérarchie seront téléchargés.

ENVIRONNEMENT

Wget supporte les proxys pour les transferts HTTP et FTP. La manière standard de spécifier l'emplacement du proxy, que Wget reconnaît, est d'utiliser les variables d'environnement suivantes :

http_proxy
https_proxy
Si elles sont définies, les variables http_proxy et https_proxy doivent contenir les URLs des proxys pour les connexions HTTP et HTTPS respectivement.
ftp_proxy
Cette variable doit contenir l'URL du proxy pour les connexions FTP. Il est très courant que http_proxy et ftp_proxy soient définies avec la même URL.
no_proxy
Cette variable doit contenir une liste d'extensions de domaines séparées par des virgules pour lesquelles le proxy ne doit pas être utilisé. Par exemple, si la valeur de no_proxy est .mit.edu, le proxy ne sera pas utilisé pour récupérer des documents du MIT.

8
Le serveur a renvoyé une réponse d'erreur.

À l'exception de 0 et 1, les codes de sortie de plus faible numéro ont la priorité sur ceux de numéro plus élevé, lorsque plusieurs types d'erreurs sont rencontrés.

Dans les versions de Wget antérieures à 1.12, le statut de sortie de Wget avait tendance à être peu utile et incohérent. Les téléchargements récursifs renvoyaient pratiquement toujours 0 (succès), quelles que soient les difficultés rencontrées, et les transferts non récursifs ne renvoyaient que le statut correspondant au téléchargement le plus récemment tenté.

BOGUES

Vous êtes invité à soumettre vos rapports de bogues via le tracker de bogues de GNU Wget (voir <https://savannah.gnu.org/bugs/?func=additem&group=wget>) ou à notre liste de diffusion <bug-wget@gnu.org>.

Visitez https://lists.gnu.org/mailman/listinfo/bug-wget pour obtenir plus d'informations (comment s'abonner, archives de la liste, ...).

Avant de soumettre un rapport de bogue, veuillez essayer de suivre quelques directives simples.

1.
Veuillez essayer de déterminer si le comportement que vous observez est bien un bogue. Si Wget plante, c'est un bogue. Si Wget ne se comporte pas comme documenté, c'est un bogue. Si les choses fonctionnent étrangement, mais que vous n'êtes pas sûr de la manière dont elles sont censées fonctionner, cela pourrait bien être un bogue, mais vous pourriez vouloir vérifier la documentation et les listes de diffusion.
2.
Essayez de reproduire le bogue dans des circonstances aussi simples que possible. Par exemple, si Wget plante lors du téléchargement de wget -rl0 -kKE -t5 --no-proxy http://example.com -o /tmp/log, vous devriez essayer de voir si le plantage est reproductible, et s'il se produit avec un ensemble d'options plus simple. Vous pourriez même essayer de démarrer le téléchargement sur la page où le plantage s'est produit pour voir si cette page a déclenché le plantage.

De plus, bien que je serai probablement intéressé de connaître le contenu de votre fichier .wgetrc, le jeter simplement dans le message de débogage est probablement une mauvaise idée. Au lieu de cela, vous devriez d'abord essayer de voir si le bogue se répète avec .wgetrc déplacé. Seulement s'il s'avère que les paramètres de .wgetrc affectent le bogue, envoyez-moi les parties pertinentes du fichier.

3.
Veuillez lancer Wget avec l'option -d et envoyez-nous la sortie résultante (ou les parties pertinentes). Si Wget a été compilé sans support de débogage, recompilez-le - il est beaucoup plus facile de tracer les bogues avec le support de débogage activé.

Remarque : veuillez vous assurer de supprimer toute information potentiellement sensible du journal de débogage avant de l'envoyer à l'adresse des bogues. L'option "-d" ne fera pas d'efforts particuliers pour collecter des informations sensibles, mais le journal contiendra un transcript assez complet de la communication de Wget avec le serveur, qui peut inclure des mots de passe et des parties des données téléchargées. Comme l'adresse des bogues est publiquement archivée, vous pouvez supposer que tous les rapports de bogues sont visibles par le public.

4.
Si Wget a planté, essayez de le lancer dans un débogueur, par exemple "gdb `which wget` core" et tapez "where" pour obtenir la trace de la pile. Cela peut ne pas fonctionner si l'administrateur système a désactivé les fichiers core, mais cela vaut la peine d'essayer.
