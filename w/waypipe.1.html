waypipe(1) Manuel des commandes générales waypipe(1)

NOM

waypipe - Un proxy transparent pour les applications Wayland

SYNTAXE

waypipe [options...] ssh [options ssh] destination commande...

waypipe [options...] client
waypipe [options...] serveur -- commande...
waypipe bench
waypipe [--version] [-h, --help]

[options...] = [-c, --compress C] [-d, --debug] [-n, --no-gpu] [-o, --oneshot] [-s, --socket S] [--display D] [--drm-node R] [--remote-node R] [--remote-bin R] [--remote-socket S] [--login-shell] [--threads T] [--title-prefix P] [--unlink-socket] [--video V] [--vsock] [--secctx S]

DESCRIPTION

Waypipe est un proxy pour les clients Wayland, dans le but de prendre en charge un comportement similaire à ssh -X.

Préfixer une commande ssh ... pour devenir waypipe ssh ... exécutera automatiquement waypipe à la fois localement et à distance, et modifiera la commande ssh pour établir une redirection entre les deux instances de waypipe. L'instance distante agira comme un compositeur Wayland, permettant aux applications Wayland exécutées à distance d'être affichées localement.

Lorsqu'il est exécuté en tant que waypipe client, il ouvrira une socket (par défaut à /tmp/waypipe-client.sock) et se connectera au compositeur Wayland local, transférant toutes les applications Wayland qui lui ont été liées via la socket par une instance correspondante de waypipe serveur.

Lorsqu'il est exécuté en tant que waypipe serveur, il exécutera la commande qui suit dans son invocation de ligne de commande, configurera sa propre socket de compositeur Wayland, et tentera de se connecter à sa socket correspondante de waypipe client (par défaut /tmp/waypipe-server.sock) et tentera de transférer tous les clients Wayland qui se connectent à la fausse socket de compositeur vers le waypipe client correspondant.

Le mode waypipe bench peut être utilisé pour estimer quelles options de compression produisent la latence la plus faible, pour une bande passante de connexion et un nombre de threads donnés. Il teste deux images synthétiques, l'une conçue pour être à peu près aussi compressible que les images contenant du texte, et l'autre conçue pour être à peu près aussi compressible que les images contenant des images.

OPTIONS

-c C, --compress C

Sélectionne la méthode de compression appliquée aux transferts de données. Les options sont none (pour les réseaux à haute bande passante), lz4 (intermédiaire), zstd (connexion lente). La compression par défaut est lz4.† Le niveau de compression peut être choisi en ajoutant = suivi d'un nombre. Par exemple, si C est zstd=7, waypipe utilisera la compression Zstd de niveau 7.

† Sauf si waypipe est compilé sans prise en charge LZ4, auquel cas la compression par défaut sera none.

-d, --debug

Affiche les messages de journalisation de débogage.

-h, --help

Affiche le message d'aide et quitte.

-n, --no-gpu

Bloque les protocoles tels que wayland-drm et linux-dmabuf qui nécessitent un accès, par exemple, aux nœuds de rendu.

-o, --oneshot

N'autorise qu'une seule connexion et se ferme une fois celle-ci terminée.

-s S, --socket S

Utilise S comme chemin pour la socket Unix. Le chemin de socket par défaut pour le mode serveur est /tmp/waypipe-server.sock ; pour le mode client, c'est /tmp/waypipe-client.sock ; et en mode ssh, S donne le préfixe utilisé par le client et le serveur pour leurs chemins de socket. (Les chemins de socket réels en mode ssh ajoutent un suffixe aléatoire à S.) Le préfixe par défaut en mode ssh est /tmp/waypipe.

Lorsque vsock est activé, utilisez S pour spécifier un CID et un numéro de port.

--version

Décrit brièvement la version de Waypipe et les fonctionnalités avec lesquelles il a été compilé, puis quitte. Fonctionnalités possibles : prise en charge de la compression LZ4, prise en charge de la compression ZSTD, possibilité de transférer des DMABUF, prise en charge de la compression vidéo.

--display D

Pour le mode serveur ou ssh, fournit WAYLAND_DISPLAY et laisse waypipe configurer sa socket d'affichage Wayland avec un chemin correspondant. (Si D n'est pas un chemin absolu, la socket sera créée dans le dossier donné par la variable d'environnement XDG_RUNTIME_DIR.)

--drm-node R

Spécifie le chemin R vers le périphérique drm que cette instance de waypipe doit utiliser et (en mode serveur) notifier aux applications qui se connectent.

--remote-node R

En mode ssh, spécifie le chemin R vers le périphérique drm que l'instance distante de waypipe (exécutée en mode serveur) doit utiliser.

--remote-bin R

En mode ssh, spécifie le chemin R vers le binaire waypipe sur l'ordinateur distant, ou son nom s'il est disponible dans PATH. Il est par défaut waypipe si cette option n'est pas passée.

--remote-socket R

En mode ssh, spécifie le préfixe utilisé par le waypipe serveur distant pour son chemin de socket. Ceci remplace l'option --socket, côté serveur uniquement.

--login-shell

Uniquement pour le mode serveur ; si aucune commande n'est exécutée, ouvre un shell de connexion.

--threads T

Définit le nombre total de threads (y compris le thread principal) qu'une instance de waypipe créera. Ces threads seront utilisés pour paralléliser les opérations de compression. Ce drapeau est transmis à waypipe serveur lorsqu'il est donné à waypipe ssh. Le drapeau contrôle également le nombre de threads pour waypipe bench. Le comportement par défaut (choisissable en définissant T à 0) est d'utiliser la moitié du nombre de threads matériels disponibles sur l'ordinateur.

--title-prefix P

Ajoute P au début des titres de fenêtre spécifiés à l'aide du protocole XDG shell. En mode ssh, le préfixe est appliqué uniquement côté client.

--unlink-socket

Uniquement pour le mode serveur ; à l'arrêt, supprime la socket Unix à laquelle waypipe se connecte.

--video V

Compresse des formats DMABUF spécifiques à l'aide d'un codec vidéo avec perte. Les formats opaques, 10 bits et multi-plans, entre autres, ne sont pas pris en charge. V est une liste d'options séparées par des virgules pour contrôler l'encodage vidéo. (Par exemple : --video av1,hw.) Les options ultérieures remplacent les précédentes.

none

Ne pas utiliser l'encodage vidéo.

h264

Utiliser la vidéo encodée H.264.

vp9

Utiliser la vidéo encodée VP9.

av1

Utiliser la vidéo encodée VP9.

sw, swenc, swdec

Utiliser l'encodage ou le décodage logiciel, lorsque disponible.

hw, hwenc, hwdec

Utiliser l'encodage ou le décodage matériel, lorsque disponible.

bpf=B

Définit le débit binaire cible de l'encodeur vidéo, en unités de bits par image. B peut être écrit comme un entier ou avec une notation exponentielle ; ainsi --video=bpf=7.5e5 est équivalent à --video=bpf=750000.

--vsock

Utiliser vsock au lieu des sockets Unix. Ceci est utilisé lorsque waypipe s'exécute dans des machines virtuelles. Avec cette option activée, spécifiez un CID et un numéro de port dans S. Le CID n'est utilisé qu'en mode serveur et peut être omis lors de la connexion d'une machine virtuelle invitée à l'hôte.

--secctx S

Active le protocole de contexte de sécurité Wayland (modes client ou ssh). Spécifie un identifiant d'application S qui sera attaché au contexte de sécurité.

--control C
--hwvideo
--allow-tiled

Options présentes dans les versions antérieures de Waypipe qui ont été supprimées.

EXEMPLE

La sous-commande waypipe ssh suivante tentera d'exécuter weston-flower sur le serveur exserv, en affichant le résultat sur le système local.

waypipe ssh utilisateur@exserv weston-flower

On peut obtenir un comportement similaire en exécutant explicitement waypipe et ssh :

waypipe --socket /tmp/socket-client client  &
ssh -R /tmp/socket-server:/tmp/socket-client utilisateur@exserv \
	waypipe --socket /tmp/socket-server serveur -- weston-flower

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

kill %1

Waypipe peut être exécuté localement sans connexion SSH en spécifiant des chemins de socket correspondants. Par exemple :

waypipe --socket /tmp/waypipe.sock client &
waypipe --socket /tmp/waypipe.sock server weston-simple-dmabuf-egl
kill %1
rm /tmp/waypipe.sock

L'utilisation de transports autres que SSH est un peu plus compliquée. Une recette avec ncat pour se connecter à remote depuis l'ordinateur local :

    $ waypipe --socket /tmp/waypipe-remote.sock client &
    $ ncat --ssl -lk 12345 --sh-exec 'ncat -U /tmp/waypipe-remote.sock' &
    $ ssh user@remote
    > ncat -lkU /tmp/waypipe-local.sock --sh-exec 'ncat --ssl local 12345' &
    > waypipe --display wayland-local \
                --socket /tmp/waypipe-local.sock server -- sleep inf &
    > WAYLAND_DISPLAY=wayland-local application

À partir d'un fichier de certificat, socat peut également fournir une connexion chiffrée (supprimez 'verify=0' pour vérifier les certificats) :

    $ waypipe --socket /tmp/waypipe-remote.sock client &
    $ socat openssl-listen:12345,reuseaddr,cert=certificate.pem,verify=0,fork \
        unix-connect:/tmp/waypipe-remote.sock
    $ ssh user@remote
    > socat unix-listen:/tmp/waypipe-local.sock,reuseaddr,fork \
        openssl-connect:local:12345,verify=0 &
    > waypipe --socket /tmp/waypipe-local.sock server -- application

De nombreuses applications nécessitent des variables d'environnement spécifiques pour utiliser Wayland au lieu de X11. Si ssh n'est pas configuré pour prendre en charge le chargement de ~/.ssh/environment, ou pour autoriser la définition de variables spécifiques avec AcceptEnv/SetEnv, on peut exécuter waypipe ssh sans commande (et ainsi ouvrir un shell de connexion), ou utiliser env pour définir les variables nécessaires à chaque fois :

waypipe ssh user@host env XDG_SESSION_TYPE=wayland dolphin

Dans certains cas, on peut souhaiter définir des variables d'environnement pour le processus waypipe server lui-même ; l'astuce ci-dessus avec env ne le fera pas, car le processus env sera un enfant de waypipe server, et non l'inverse. Au lieu de cela, on peut utiliser ~/.ssh/environment, ou utiliser l'option --remote-bin pour changer l'instance Waypipe distante en un script shell qui définit l'environnement avant d'exécuter le programme waypipe réel.

Exécution de waypipe dans des machines virtuelles

Lorsque waypipe est exécuté dans des machines virtuelles sur le même hôte, il est possible d'utiliser vsock pour une communication inter-VM efficace. Les scénarios suivants sont pris en charge :

•
Exécution d'applications sur l'hôte depuis l'invité.
hôte> waypipe --vsock -s 1234 client
invité> waypipe --vsock -s 1234 server weston-terminal
•
Exécution d'applications dans une machine virtuelle invitée depuis l'hôte.
invité> waypipe --vsock -s 1234 client
hôte> waypipe --vsock -s 3:1234 server weston-terminal

Dans cet exemple, waypipe server se connecte à une machine virtuelle avec le CID 3 sur le port 1234.

•
Exécution d'applications dans une machine virtuelle invitée depuis d'autres machines virtuelles invitées. Lors de l'exécution du client et du serveur dans des machines virtuelles, il est possible d'activer le drapeau VMADDR_FLAG_TO_HOST pour la communication entre frères en préfixant le CID par un s :
invité> waypipe --vsock -s 1234 client
invité> waypipe --vsock -s s3:1234 server weston-terminal

Dans ce cas, tous les paquets seront routés vers l'hôte où ils pourront être transférés vers une autre machine virtuelle avec un périphérique vhost-device-vsock ou un autre utilitaire.

ENVIRONNEMENT

Lors de l'exécution en tant que serveur, par défaut, WAYLAND_DISPLAY sera défini pour le processus appelé.

Si le drapeau --oneshot est défini, waypipe définira au lieu de cela WAYLAND_SOCKET et héritera d'un descripteur de fichier de paire de sockets déjà connecté au processus appelé (enfant). Certains programmes ouvrent et ferment une connexion Wayland de manière répétée dans le cadre de leur initialisation et ne fonctionneront pas correctement avec ce drapeau.

STATUT DE SORTIE

waypipe ssh se terminera avec le code de statut de sortie de la commande distante, ou avec le code de retour 1 en cas d'erreur.

SÉCURITÉ

Waypipe ne fournit aucune garantie de sécurité forte, et la connexion à des serveurs non fiables n'est pas recommandée. Il ne filtre pas les protocoles Wayland que le compositeur rend disponibles au client (à quelques exceptions près pour les protocoles qui nécessitent des descripteurs de fichiers que Waypipe ne peut pas encore gérer). Par exemple, si un compositeur Wayland donne à tous ses clients l'accès à un protocole de capture d'écran ou de verrouillage d'écran, les clients proxysés exécutés sous Waypipe peuvent également prendre des captures d'écran ou verrouiller l'écran.

En général, les applications ne sont pas bien testées contre des compositeurs malveillants, et les compositeurs ne sont pas bien testés contre des clients malveillants. Waypipe peut les connecter et peut transmettre aveuglément des dénis de service et d'autres attaques.

Waypipe lui-même est écrit en C et se lie à des bibliothèques de compression, de graphisme et de vidéo ; lui-même et ces bibliothèques peuvent avoir des bogues de sécurité. Certains risques peuvent être évités en compilant Waypipe avec le support DMABUF désactivé, ou en exécutant Waypipe avec l'option --no-gpu afin qu'il n'expose pas les bibliothèques graphiques.

waypipe ssh n'a pas de protections explicites contre les attaques temporelles ; un observateur du trafic réseau résultant peut, en étudiant la taille et le timing des paquets, obtenir des informations sur l'interaction de l'utilisateur avec un client Wayland proxysé via waypipe ssh. Par exemple : un manque d'activité suggère que l'utilisateur n'utilise pas actuellement l'application, tandis qu'un flux intermittent de messages du compositeur vers le client peut indiquer un mouvement de souris (ou peut-être autre chose : le contenu des messages est protégé par ssh.)

La mémoire utilisée par les processus Waypipe peut, à un moment donné, inclure des messages Wayland encodant les entrées utilisateur, et le contenu des images actuelles et récentes dessinées pour les fenêtres des applications. Le swap doit être chiffré pour empêcher que ces données ne soient divulguées sur le disque.

BOGUES

Signalez les bogues à : https://gitlab.freedesktop.org/mstoeckl/waypipe/

Problèmes courants

Certains programmes (gnome-terminal, firefox, kate, entre autres) ont des mécanismes spéciaux pour garantir qu'un seul processus est exécuté à la fois. Le lancement de ces programmes sous Waypipe alors qu'ils sont exécutés sous un autre compositeur Wayland peut ouvrir silencieusement une fenêtre ou un onglet dans l'instance d'origine du programme. Ces programmes peuvent avoir un argument de ligne de commande pour créer une nouvelle instance.

La commande waypipe ssh nécessite que l'exécutable ssh prenne en charge le transfert de socket Unix ; cela n'est pris en charge que dans OpenSSH depuis la version 6.7 (à partir de 2014) et peut nécessiter une configuration spécifique. D'autres implémentations de SSH peuvent ne pas être en mesure de transférer des sockets Unix ; voir la section EXEMPLE ci-dessus pour savoir comment utiliser des transports autres que SSH.
