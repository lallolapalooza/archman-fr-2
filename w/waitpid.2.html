wait(2) Manuel des appels système wait(2)

NOM

wait, waitpid, waitid - attendre qu'un processus change d'état

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <sys/wait.h>
pid_t wait(int *_Nullable wstatus);
pid_t waitpid(pid_t pid, int *_Nullable wstatus, int options);
int waitid(idtype_t idtype, id_t id, siginfo_t *infop, int options);
                /* C'est l'interface glibc et POSIX ; voir
                   VERSIONS pour des informations sur l'appel système brut.  */

DESCRIPTION

Tous ces appels système sont utilisés pour attendre les changements d'état d'un enfant du processus appelant, et pour obtenir des informations sur l'enfant dont l'état a changé. Un changement d'état est considéré comme : l'enfant a terminé ; l'enfant a été arrêté par un signal ; ou l'enfant a été repris par un signal. Dans le cas d'un enfant terminé, l'exécution d'un wait permet au système de libérer les ressources associées à l'enfant ; si un wait n'est pas effectué, l'enfant terminé reste dans un état de "zombie" (voir NOTES ci-dessous).

Si un enfant a déjà changé d'état, ces appels retournent immédiatement. Sinon, ils bloquent jusqu'à ce qu'un enfant change d'état ou qu'un gestionnaire de signal interrompe l'appel (en supposant que les appels système ne sont pas automatiquement redémarrés en utilisant le drapeau SA_RESTART de sigaction(2)). Dans le reste de cette page, un enfant dont l'état a changé et qui n'a pas encore été attendu par l'un de ces appels système est qualifié de *attendant*.

wait() et waitpid()

L'appel système wait() suspend l'exécution du thread appelant jusqu'à ce qu'un de ses enfants se termine. L'appel wait(&wstatus) est équivalent à :


waitpid(-1, &wstatus, 0);

L'appel système waitpid() suspend l'exécution du thread appelant jusqu'à ce qu'un enfant spécifié par l'argument pid ait changé d'état. Par défaut, waitpid() attend uniquement les enfants terminés, mais ce comportement peut être modifié via l'argument options, comme décrit ci-dessous.

La valeur de pid peut être :

< -1
signifie attendre tout processus enfant dont l'ID de groupe de processus est égal à la valeur absolue de pid.
-1
signifie attendre tout processus enfant.
0
signifie attendre tout processus enfant dont l'ID de groupe de processus est égal à celui du processus appelant au moment de l'appel à waitpid().
> 0
signifie attendre l'enfant dont l'ID de processus est égal à la valeur de pid.

La valeur de options est un OR de zéro ou plusieurs des constantes suivantes :

WNOHANG
retourner immédiatement si aucun enfant n'est terminé.
WUNTRACED
retourner également si un enfant a été arrêté (mais pas tracé via ptrace(2)). L'état des enfants *tracés* qui se sont arrêtés est fourni même si cette option n'est pas spécifiée.
WCONTINUED (depuis Linux 2.6.10)
retourner également si un enfant arrêté a été repris par la réception de SIGCONT.

(Pour les options spécifiques à Linux, voir ci-dessous.)

Si wstatus n'est pas NULL, wait() et waitpid() stockent des informations d'état dans l'entier pointé par wstatus. Cet entier peut être inspecté avec les macros suivantes (qui prennent l'entier lui-même comme argument, pas un pointeur vers celui-ci, comme c'est fait dans wait() et waitpid !) :

WIFEXITED(wstatus)
retourne vrai si l'enfant s'est terminé normalement, c'est-à-dire en appelant exit(3) ou _exit(2), ou en retournant de main().
WEXITSTATUS(wstatus)
retourne le statut de sortie de l'enfant. Il s'agit des 8 bits les moins significatifs de l'argument status que l'enfant a spécifié dans un appel à exit(3) ou _exit(2) ou comme argument d'une instruction return dans main(). Cette macro ne doit être utilisée que si WIFEXITED a retourné vrai.
WIFSIGNALED(wstatus)
retourne vrai si le processus enfant a été terminé par un signal.
WTERMSIG(wstatus)
retourne le numéro du signal qui a causé la terminaison du processus enfant. Cette macro ne doit être utilisée que si WIFSIGNALED a retourné vrai.
WCOREDUMP(wstatus) // POSIX.1-2024
retourne vrai si l'enfant a produit un vidage mémoire (voir core(5)). Cette macro ne doit être utilisée que si WIFSIGNALED a retourné vrai.
WIFSTOPPED(wstatus) // POSIX.1-2024
retourne vrai si le processus enfant a été arrêté par la réception d'un signal ; ceci n'est possible que si l'appel a été effectué en utilisant WUNTRACED ou lorsque l'enfant est tracé (voir ptrace(2)).
WSTOPSIG(wstatus)
retourne le numéro du signal qui a causé l'arrêt de l'enfant. Cette macro ne doit être utilisée que si WIFSTOPPED a retourné vrai.
WIFCONTINUED(wstatus)
(depuis Linux 2.6.10) retourne vrai si le processus enfant a été repris par la réception de SIGCONT.

waitid()

L'appel système waitid() (disponible depuis Linux 2.6.9) fournit un contrôle plus précis sur les changements d'état des enfants à attendre.

Les arguments idtype et id sélectionnent l'enfant (ou les enfants) à attendre, comme suit :

idtype == P_PID
Attendre l'enfant dont l'ID de processus correspond à id.
idtype == P_PIDFD (depuis Linux 5.4)
Attendre l'enfant référencé par le descripteur de fichier PID spécifié dans id. (Voir pidfd_open(2) pour plus d'informations sur les descripteurs de fichier PID.)
idtype == P_PGID
Attendre tout enfant dont l'ID de groupe de processus correspond à id. Depuis Linux 5.4, si id est zéro, attendre tout enfant qui se trouve dans le même groupe de processus que le groupe de processus de l'appelant au moment de l'appel.
idtype == P_ALL
Attendre tout enfant ; id est ignoré.

Les changements d'état des enfants à attendre sont spécifiés en combinant par OR un ou plusieurs des drapeaux suivants dans options :

WEXITED
Attendre les enfants qui se sont terminés.
WSTOPPED
Attendre les enfants qui ont été arrêtés par la réception d'un signal.
WCONTINUED
Attendre les enfants (précédemment arrêtés) qui ont été repris par la réception de SIGCONT.

Les drapeaux suivants peuvent également être combinés par OR dans options :

WNOHANG

WNOWAIT
Laisse l'enfant dans un état attendable ; un appel d'attente ultérieur peut être utilisé pour récupérer à nouveau les informations d'état de l'enfant.

Lors d'un retour réussi, waitid() remplit les champs suivants de la structure siginfo_t pointée par infop :

si_pid
L'ID du processus de l'enfant.
si_uid
L'ID utilisateur réel de l'enfant. (Ce champ n'est pas défini sur la plupart des autres implémentations.)
si_signo
Toujours défini à SIGCHLD.
si_status
Soit le statut de sortie de l'enfant, tel que donné à _exit(2) (ou exit(3)), soit le signal qui a provoqué la terminaison, l'arrêt ou la reprise de l'enfant. Le champ si_code peut être utilisé pour déterminer comment interpréter ce champ.
si_code
Défini à l'une des valeurs suivantes : CLD_EXITED (l'enfant a appelé _exit(2)) ; CLD_KILLED (l'enfant a été tué par un signal) ; CLD_DUMPED (l'enfant a été tué par un signal et a généré un core dump) ; CLD_STOPPED (l'enfant s'est arrêté à cause d'un signal) ; CLD_TRAPPED (l'enfant tracé a été piégé) ; ou CLD_CONTINUED (l'enfant a été repris par SIGCONT).

Si WNOHANG a été spécifié dans options et qu'il n'y avait pas d'enfants dans un état attendable, alors waitid() retourne 0 immédiatement et l'état de la structure siginfo_t pointée par infop dépend de l'implémentation. Pour distinguer (de manière portable) ce cas de celui où un enfant était dans un état attendable, mettez à zéro le champ si_pid avant l'appel et vérifiez une valeur non nulle dans ce champ après le retour de l'appel.

Le corrigendum technique 1 (2013) de POSIX.1-2008 ajoute l'exigence que lorsque WNOHANG est spécifié dans options et qu'il n'y avait pas d'enfants dans un état attendable, alors waitid() doit mettre à zéro les champs si_pid et si_signo de la structure. Sur Linux et d'autres implémentations qui respectent cette exigence, il n'est pas nécessaire de mettre à zéro le champ si_pid avant d'appeler waitid(). Cependant, toutes les implémentations ne suivent pas la spécification POSIX.1 sur ce point.

VALEUR DE RETOUR

wait() : en cas de succès, retourne l'ID du processus de l'enfant terminé ; en cas d'échec, -1 est retourné.

waitpid() : en cas de succès, retourne l'ID du processus de l'enfant dont l'état a changé ; si WNOHANG a été spécifié et qu'un ou plusieurs enfants spécifiés par pid existent, mais n'ont pas encore changé d'état, alors 0 est retourné. En cas d'échec, -1 est retourné.

waitid() : retourne 0 en cas de succès ou si WNOHANG a été spécifié et qu'aucun enfant spécifié par id n'a encore changé d'état ; en cas d'échec, -1 est retourné.

En cas d'échec, chacun de ces appels définit errno pour indiquer l'erreur.

ERREURS

EAGAIN
Le descripteur de fichier PID spécifié dans id est non bloquant et le processus auquel il fait référence ne s'est pas terminé.
ECHILD
(pour wait()) Le processus appelant n'a aucun enfant non attendu.
ECHILD
(pour waitpid() ou waitid()) Le processus spécifié par pid (waitpid()) ou idtype et id (waitid()) n'existe pas ou n'est pas un enfant du processus appelant. (Cela peut arriver pour son propre enfant si l'action pour SIGCHLD est définie à SIG_IGN. Voir aussi la section Notes Linux sur les threads.)
EINTR
WNOHANG n'était pas défini et un signal non bloqué ou un SIGCHLD a été intercepté ; voir signal(7).
EINVAL
L'argument options était invalide.
ESRCH
(pour wait() ou waitpid()) pid est égal à INT_MIN.

VERSIONS

Différences bibliothèque C/noyau

wait() est en fait une fonction de bibliothèque qui (dans glibc) est implémentée comme un appel à wait4(2).

Sur certaines architectures, il n'y a pas d'appel système waitpid() ; à la place, cette interface est implémentée via une fonction enveloppe de la bibliothèque C qui appelle wait4(2).

L'appel système brut waitid() prend un cinquième argument, de type struct rusage *. Si cet argument n'est pas NULL, alors il est utilisé pour retourner des informations d'utilisation des ressources concernant l'enfant, de la même manière que wait4(2). Voir getrusage(2) pour plus de détails.

NORMES

POSIX.1-2024.

HISTORIQUE

SVr4, 4.3BSD, POSIX.1-2001.

NOTES

Un enfant qui se termine, mais qui n'a pas été attendu devient un "zombie". Le noyau conserve un ensemble minimal d'informations sur le processus zombie (PID, statut de terminaison, informations d'utilisation des ressources) afin de permettre au parent d'effectuer plus tard un wait pour obtenir des informations sur l'enfant. Tant qu'un zombie n'est pas retiré du système via un wait, il consomme un emplacement dans la table des processus du noyau, et si cette table se remplit, il ne sera pas possible de créer d'autres processus. Si un processus parent se termine, alors ses enfants "zombies" (le cas échéant) sont adoptés par init(1) (ou par le processus "subreaper" le plus proche tel que défini via l'opération PR_SET_CHILD_SUBREAPER du prctl(2)) ; init(1) effectue automatiquement un wait pour supprimer les zombies.

POSIX.1-2001 spécifie que si la disposition de SIGCHLD est définie à SIG_IGN ou si le drapeau SA_NOCLDWAIT est défini pour SIGCHLD (voir sigaction(2)), alors les enfants qui se terminent ne deviennent pas des zombies et un appel à wait() ou waitpid() sera bloqué jusqu'à ce que tous les enfants se soient terminés, puis échouera avec errno défini à ECHILD. (Le standard POSIX original laissait le comportement de la définition de SIGCHLD à SIG_IGN non spécifié. Notez que même si la disposition par défaut de SIGCHLD est "ignorer", définir explicitement la disposition à SIG_IGN entraîne un traitement différent des enfants zombies.)

Linux 2.6 est conforme aux exigences POSIX. Cependant, Linux 2.4 (et antérieur) ne l'est pas : si un appel wait() ou waitpid() est effectué pendant que SIGCHLD est ignoré, l'appel se comporte comme si SIGCHLD n'était pas ignoré, c'est-à-dire que l'appel est bloqué jusqu'à ce que le prochain enfant se termine et retourne ensuite l'ID du processus et le statut de cet enfant.

Notes Linux

Dans le noyau Linux, un thread planifié par le noyau n'est pas une construction distincte d'un processus. Au lieu de cela, un thread est simplement un processus qui est créé en utilisant l'appel clone(2) unique à Linux ; d'autres routines comme l'appel portable pthread_create(3) sont implémentées en utilisant clone(2). Avant Linux 2.4, un thread n'était qu'un cas spécial d'un processus, et par conséquent un thread ne pouvait pas attendre les enfants d'un autre thread, même lorsque ce dernier appartenait au même groupe de threads. Cependant, POSIX prescrit une telle fonctionnalité, et depuis Linux 2.4, un thread peut, et par défaut le fera, attendre les enfants d'autres threads du même groupe de threads.

Les options spécifiques à Linux suivantes sont destinées à être utilisées avec les enfants créés en utilisant clone(2) ; elles peuvent également, depuis Linux 4.7, être utilisées avec waitid() :

__WCLONE
Attendre uniquement les enfants "clone". Si omis, attendre uniquement les enfants "non-clone". (Un enfant "clone" est un enfant qui ne délivre aucun signal, ou un signal autre que SIGCHLD à son parent lors de la terminaison.) Cette option est ignorée si __WALL est également spécifié.
__WALL (depuis Linux 2.4)
Attendre tous les enfants, quel que soit leur type ("clone" ou "non-clone").
__WNOTHREAD (depuis Linux 2.4)
Ne pas attendre les enfants d'autres threads du même groupe de threads. C'était le comportement par défaut avant Linux 2.4.

Depuis Linux 4.7, le drapeau __WALL est automatiquement implicite si l'enfant est tracé (ptraced).

BOGUES

Selon POSIX.1-2008, une application appelant waitid() doit s'assurer que infop pointe vers une structure siginfo_t (c'est-à-dire que c'est un pointeur non nul). Sous Linux, si infop est NULL, waitid() réussit et retourne l'ID du processus de l'enfant attendu. Les applications devraient éviter de s'appuyer sur cette fonctionnalité incohérente, non standard et inutile.

EXEMPLES

Le programme suivant démontre l'utilisation de fork(2) et waitpid(). Le programme crée un processus enfant. Si aucun argument de ligne de commande n'est fourni au programme, alors l'enfant suspend son exécution en utilisant pause(2), pour permettre à l'utilisateur d'envoyer des signaux à l'enfant. Sinon, si un argument de ligne de commande est fourni, alors l'enfant se termine immédiatement, en utilisant l'entier fourni sur la ligne de commande comme statut de sortie. Le processus parent exécute une boucle qui surveille l'enfant à l'aide de waitpid(), et utilise les macros W*() décrites ci-dessus pour analyser la valeur du statut d'attente.

La session shell suivante démontre l'utilisation du programme :


$ ./a.out &
PID de l'enfant i
s 32360 [1] 32359 $ kill -STOP 32360 arrêté par le signal 19 $ kill -CONT 32360 continué $ kill -TERM 32360 tué par le signal 15 [1]+ Terminé ./a.out $

Source du programme

#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/types.h>
#include <sys/wait.h>
#include <unistd.h>
int
main(int argc, char *argv[])
{
    int    wstatus;
    pid_t  cpid, w;
    cpid = fork();
    if (cpid == -1) {
        perror("fork");
        exit(EXIT_FAILURE);
    }
    if (cpid == 0) {            /* Code exécuté par l'enfant */
        printf("PID de l'enfant : %jd\n", (intmax_t) getpid());
        if (argc == 1)
            pause();                    /* Attendre les signaux */
        _exit(atoi(argv[1]));
    } else {                    /* Code exécuté par le parent */
        do {
            w = waitpid(cpid, &wstatus, WUNTRACED | WCONTINUED);
            if (w == -1) {
                perror("waitpid");
                exit(EXIT_FAILURE);
            }
            if (WIFEXITED(wstatus)) {
                printf("exited, status=%d\n", WEXITSTATUS(wstatus));
            } else if (WIFSIGNALED(wstatus)) {
                printf("tué par le signal %d\n", WTERMSIG(wstatus));
            } else if (WIFSTOPPED(wstatus)) {
                printf("arrêté par le signal %d\n", WSTOPSIG(wstatus));
            } else if (WIFCONTINUED(wstatus)) {
                printf("continué\n");
            }
        } while (!WIFEXITED(wstatus) && !WIFSIGNALED(wstatus));
        exit(EXIT_SUCCESS);
    }
}
