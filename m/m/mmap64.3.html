mmap(2) Manuel des appels système mmap(2)

NOM

mmap, munmap - mapper ou démapper des fichiers ou des périphériques en mémoire

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <sys/mman.h>
void *mmap(size_t length;
           void addr[length], size_t length, int prot, int flags,
           int fd, off_t offset);
int munmap(size_t length;
           void addr[length], size_t length);

Voir VERSIONS pour des informations sur les exigences de la macro de test de fonctionnalités.

DESCRIPTION

mmap() crée un nouveau mappage dans l'espace d'adressage virtuel du processus appelant. L'adresse de départ du nouveau mappage est spécifiée dans addr. L'argument length spécifie la longueur du mappage (qui doit être supérieure à 0).

Si addr est NULL, alors le noyau choisit l'adresse (alignée sur page) à laquelle créer le mappage ; c'est la méthode la plus portable pour créer un nouveau mappage. Si addr n'est pas NULL, alors le noyau le prend comme un indice sur l'emplacement où placer le mappage ; sous Linux, le noyau choisira une limite de page proche (mais toujours supérieure ou égale à la valeur spécifiée par /proc/sys/vm/mmap_min_addr) et tentera d'y créer le mappage. Si un autre mappage existe déjà à cet endroit, le noyau choisira une nouvelle adresse qui peut ou non dépendre de l'indice. L'adresse du nouveau mappage est retournée comme résultat de l'appel.

Le contenu d'un mappage de fichier (par opposition à un mappage annonyme ; voir MAP_ANONYMOUS ci-dessous), est initialisé en utilisant length octets à partir du décalage offset dans le fichier (ou un autre objet) référencé par le descripteur de fichier fd. offset doit être un multiple de la taille de page tel que retourné par sysconf(_SC_PAGE_SIZE).

Après que l'appel mmap() est retourné, le descripteur de fichier, fd, peut être fermé immédiatement sans invalider le mappage.

L'argument prot décrit la protection mémoire souhaitée pour le mappage (et ne doit pas entrer en conflit avec le mode d'ouverture du fichier). C'est soit PROT_NONE, soit le OU bit à bit d'un ou plusieurs des drapeaux suivants :

PROT_EXEC
Les pages peuvent être exécutées.
PROT_READ
Les pages peuvent être lues.
PROT_WRITE
Les pages peuvent être écrites.
PROT_NONE
Les pages ne peuvent pas être accédées.

L'argument flags

L'argument flags détermine si les mises à jour du mappage sont visibles pour d'autres processus mappant la même région, et si les mises à jour sont reportées dans le fichier sous-jacent. Ce comportement est déterminé en incluant exactement une des valeurs suivantes dans flags :

MAP_SHARED
Partager ce mappage. Les mises à jour du mappage sont visibles pour d'autres processus mappant la même région, et (dans le cas de mappages basés sur des fichiers) sont reportées dans le fichier sous-jacent. (Pour contrôler précisément quand les mises à jour sont reportées dans le fichier sous-jacent, il faut utiliser msync(2).)
MAP_SHARED_VALIDATE (depuis Linux 4.15)
Ce drapeau fournit le même comportement que MAP_SHARED, sauf que les mappages MAP_SHARED ignorent les drapeaux inconnus dans flags. En revanche, lors de la création d'un mappage utilisant MAP_SHARED_VALIDATE, le noyau vérifie que tous les drapeaux passés sont connus et fait échouer le mappage avec l'erreur EOPNOTSUPP pour les drapeaux inconnus. Ce type de mappage est également requis pour pouvoir utiliser certains drapeaux de mappage (par exemple, MAP_SYNC).
MAP_PRIVATE
Créer un mappage privé en copie sur écriture. Les mises à jour du mappage ne sont pas visibles pour d'autres processus mappant le même fichier, et ne sont pas reportées dans le fichier sous-jacent. Il n'est pas spécifié si les modifications apportées au fichier après l'appel mmap() sont visibles dans la région mappée.

MAP_SHARED et MAP_PRIVATE sont décrits dans POSIX.1-2001 et POSIX.1-2008. MAP_SHARED_VALIDATE est une extension Linux.

En outre, zéro ou plusieurs des valeurs suivantes peuvent être combinées par OU dans flags :

MAP_32BIT (depuis Linux 2.4.20, 2.6)
Placer le mappage dans les 2 premiers Gigaoctets de l'espace d'adressage du processus. Ce drapeau n'est pris en charge que sur x86-64, pour les programmes 64 bits. Il a été ajouté pour permettre l'allocation des piles de threads dans les 2 premiers Go de mémoire, afin d'améliorer les performances de commutation de contexte sur certains processeurs 64 bits anciens. Les processeurs x86-64 modernes n'ont plus ce problème de performance, donc l'utilisation de ce drapeau n'est pas nécessaire sur ces systèmes. Le drapeau MAP_32BIT est ignoré lorsque MAP_FIXED est activé.
MAP_ANON
Synonyme de MAP_ANONYMOUS ; fourni pour la compatibilité avec d'autres implémentations.
MAP_ANONYMOUS
Le mappage n'est soutenu par aucun fichier ; son contenu est initialisé à zéro. L'argument fd est ignoré ; cependant, certaines implémentations exigent que fd soit -1 si MAP_ANONYMOUS (ou MAP_ANON) est spécifié, et les applications portables doivent s'en assurer. L'argument offset doit être zéro. Le support de MAP_ANONYMOUS en conjonction avec MAP_SHARED a été ajouté sous Linux 2.4.
MAP_DENYWRITE
Ce drapeau est ignoré. (Il y a longtemps - Linux 2.0 et antérieur - il signalait que les tentatives d'écriture dans le fichier sous-jacent devaient échouer avec ETXTBSY. Mais c'était une source d'attaques par déni de service.)
MAP_EXECUTABLE
Ce drapeau est ignoré.
MAP_FILE
Drapeau de compatibilité. Ignoré.
MAP_FIXED
N'interprète pas addr comme un indice : place le mappage exactement à cette adresse. addr doit être correctement aligné : pour la plupart des architectures, un multiple de la taille de page est suffisant ; cependant, certaines architectures peuvent imposer des restrictions supplémentaires. Si la région mémoire spécifiée par addr et length chevauche des pages de mappages existants, alors la partie chevauchée des mappages existants sera supprimée. Si l'adresse spécifiée ne peut pas être utilisée, mmap() échouera.
Les logiciels qui aspirent à être portables doivent utiliser le drapeau MAP_FIXED avec précaution, en gardant à l'esprit que la disposition exacte des mappages mémoire d'un processus est autorisée à changer de manière significative entre les versions de Linux, les versions de la bibliothèque C et les versions du système d'exploitation. Lisez attentivement la discussion de ce drapeau dans NOTES !
MAP_FIXED_NOREPLACE (depuis Linux 4.17)
Ce drapeau fournit un comportement similaire à MAP_FIXED en ce qui concerne l'application de addr, mais diffère en ce que MAP_FIXED_NOREPLACE ne supprime jamais une plage mappée préexistante. Si la plage demandée entre en collision avec un mappage existant, alors cet appel échoue avec l'erreur EEXIST. Ce drapeau peut donc être utilisé comme un moyen de mapper une plage d'adresses de manière atomique (par rapport aux autres threads) : un thread réussira ; tous les autres signaleront un échec.
Notez que les anciens noyaux qui ne reconnaissent pas le drapeau MAP_FIXED_NOREPLACE retomberont généralement (en détectant une collision avec un mappage préexistant) vers un comportement de type “non-MAP_FIXED” : ils retourneront une adresse différente de l'adresse demandée. Par conséquent, les logiciels rétrocompatibles doivent vérifier l'adresse retournée par rapport à l'adresse demandée.
MAP_GR
MAP_GROWSDOWN
Ce drapeau est utilisé pour les piles. Il indique au système de mémoire virtuelle du noyau que le mappage doit s'étendre vers le bas dans la mémoire. L'adresse de retour est une page plus basse que la zone mémoire réellement créée dans l'espace d'adressage virtuel du processus. Accéder à une adresse dans la page de "garde" sous le mappage entraînera l'extension du mappage d'une page. Cette croissance peut être répétée jusqu'à ce que le mappage croisse jusqu'à une page de la limite supérieure du mappage inférieur suivant, moment auquel l'accès à la page de "garde" provoquera un signal SIGSEGV.
MAP_HUGETLB (depuis Linux 2.6.32)
Allouer le mappage en utilisant des pages "huges". Voir le fichier source du noyau Linux Documentation/admin-guide/mm/hugetlbpage.rst pour plus d'informations, ainsi que les NOTES, ci-dessous.
MAP_HUGE_2MB
MAP_HUGE_1GB (depuis Linux 3.8)
Utilisé conjointement avec MAP_HUGETLB pour sélectionner des tailles de pages hugetlb alternatives (respectivement, 2 Mo et 1 Go) sur les systèmes qui prennent en charge plusieurs tailles de pages hugetlb.
Plus généralement, la taille de page huge souhaitée peut être configurée en encodant le logarithme en base 2 de la taille de page souhaitée dans les six bits à l'offset MAP_HUGE_SHIFT. (Une valeur de zéro dans ce champ de bits fournit la taille de page huge par défaut ; la taille de page huge par défaut peut être découverte via le champ Hugepagesize exposé par /proc/meminfo.) Ainsi, les deux constantes ci-dessus sont définies comme suit :

#define MAP_HUGE_2MB    (21 << MAP_HUGE_SHIFT)
#define MAP_HUGE_1GB    (30 << MAP_HUGE_SHIFT)

La gamme des tailles de pages huges prises en charge par le système peut être découverte en listant les sous-répertoires dans /sys/kernel/mm/hugepages.
MAP_LOCKED (depuis Linux 2.5.37)
Marquer la région mappée pour être verrouillée de la même manière que mlock(2). Cette implémentation tentera de pré-charger (prefault) toute la plage, mais l'appel mmap() n'échouera pas avec ENOMEM si cela échoue. Par conséquent, des fautes majeures peuvent survenir plus tard. La sémantique n'est donc pas aussi robuste que mlock(2). Il faut utiliser mmap() plus mlock(2) lorsque les fautes majeures ne sont pas acceptables après l'initialisation du mappage. Le drapeau MAP_LOCKED est ignoré dans les anciens noyaux.
MAP_NONBLOCK (depuis Linux 2.5.46)
Ce drapeau n'a de sens qu'en conjonction avec MAP_POPULATE. Ne pas effectuer de lecture anticipée : créer les entrées de table de pages uniquement pour les pages qui sont déjà présentes en RAM. Depuis Linux 2.6.23, ce drapeau fait que MAP_POPULATE ne fait rien. Un jour, la combinaison de MAP_POPULATE et MAP_NONBLOCK pourrait être réimplémentée.
MAP_NORESERVE
Ne pas réserver d'espace de swap pour ce mappage. Lorsque l'espace de swap est réservé, on a la garantie qu'il est possible de modifier le mappage. Lorsque l'espace de swap n'est pas réservé, on peut recevoir un SIGSEGV lors d'une écriture si aucune mémoire physique n'est disponible. Voir également la discussion sur le fichier /proc/sys/vm/overcommit_memory dans proc_sys_vm(5). Avant Linux 2.6, ce drapeau n'avait d'effet que pour les mappages privés modifiables.
MAP_POPULATE (depuis Linux 2.5.46)
Peupler (prefault) les tables de pages d'un mappage. Pour un mappage de fichier, cela entraîne une lecture anticipée du fichier. Cela aidera à réduire le blocage sur les fautes de page plus tard. L'appel mmap() n'échoue pas si le mappage ne peut pas être peuplé (par exemple, en raison de limitations sur le nombre de pages huges mappées lors de l'utilisation de MAP_HUGETLB). La prise en charge de MAP_POPULATE en conjonction avec des mappages privés a été ajoutée dans Linux 2.6.23.
MAP_STACK (depuis Linux 2.6.27)
Allouer le mappage à une adresse appropriée pour la pile d'un processus ou d'un thread.
Ce drapeau est actuellement un no-op sous Linux. Cependant, en utilisant ce drapeau, les applications peuvent s'assurer qu'elles bénéficieront d'une prise en charge transparente si le drapeau est implémenté à l'avenir. Ainsi, il est utilisé dans l'implémentation de threading de glibc pour tenir compte du fait que certaines architectures peuvent (plus tard) nécessiter un traitement spécial pour les allocations de piles. Une autre raison d'utiliser ce drapeau est la portabilité : MAP_STACK existe (et a un effet) sur certains autres systèmes (par exemple, certains BSD).
MAP_SYNC (depuis Linux 4.15)
Ce drapeau n'est disponible qu'avec le type de mappage MAP_SHARED_VALIDATE ; les mappages de type MAP_SHARED ignoreront silencieusement ce drapeau. Ce drapeau n'est pris en charge que pour les fichiers prenant en charge DAX (mappage direct de mémoire persistante). Pour les autres fichiers, la création d'un mappage avec ce drapeau entraîne une erreur EOPNOTSUPP.
Les mappages de fichiers partagés avec ce drapeau garantissent que, bien que certaines mémoires soient mappées en écriture dans l'espace d'adressage du processus, elles seront visibles dans le même fichier au même décalage même après un crash ou un redémarrage du système. En conjonction avec l'utilisation d'instructions CPU appropriées, cela offre aux utilisateurs de tels mappages un moyen plus efficace de rendre les modifications de données persistantes.
MAP_UNINITIALIZED (depuis Linux 2.6.33)
Ne pas effacer les pages anonymes. Ce drapeau vise à améliorer les performances sur les appareils embarqués. Ce drapeau n'est honoré que si le noyau a été configuré avec l'option CONFIG_MMAP_ALLOW_UNINITIALIZED. En raison des implications de sécurité, cette option n'est normalement activée que sur les appareils embarqués (c'est-à-dire les appareils sur lesquels on a un contrôle total sur le contenu de la mémoire utilisateur).

Parmi les drapeaux ci-dessus, seul MAP_FIXED est spécifié dans POSIX.1-2001 et POSIX.1-2008. Cependant, la plupart des systèmes prennent également en charge MAP_ANONYMOUS (ou son synonyme MAP_ANON).

munmap()

L'appel système munmap() supprime les mappages de la plage d'adresses spécifiée, et provoque des références ultérieures à des adresses dans la plage pour générer des références mémoire invalides. La région est également automatiquement débrayée lorsque le processus est terminé. En revanche, la fermeture du descripteur de fichier ne débraye pas la région.

L'adresse addr doit être un multiple de la taille de page (mais length n'a pas besoin de l'être). Toutes les pages contenant une partie de la plage indiquée sont débrayées, et les références ultérieures à ces pages généreront SIGSEGV. Ce n'est pas une erreur si la plage indiquée ne contient aucune page mappée.

VALEUR DE RETOUR

En cas de succès, mmap() renvoie un pointeur vers la zone mappée. En cas d'erreur, la valeur MAP_FAILED (c'est-à-dire (void *) -1) est renvoyée, et errno est définie pour indiquer l'erreur.

En cas de succès, munmap() renvoie 0. En cas d'échec, elle renvoie -1, et errno est définie pour indiquer l'erreur (probablement EINVAL).

ERREURS

EACCES
Un descripteur de fichier fait référence à un fichier non régulier. Ou un mappage de fichier a été demandé, mais fd n'est pas ouvert en lecture. Ou MAP_SHARED a été demandé et PROT_WRITE est défini, mais fd n'est pas ouvert en mode lecture/écriture (O_RDWR). Ou PROT_WRITE est défini, mais le fichier est en mode ajout uniquement.
EAGAIN
Le fichier a été verrouillé, ou trop de mémoire a été verrouillée (voir setrlimit(2)).
EBADF
fd n'est pas un descripteur de fichier valide (et MAP_ANONYMOUS n'était pas défini).
EEXIST
MAP_FIXED_NOREPLACE a été spécifié dans flags, et la plage couverte par addr et length entre en conflit avec un mappage existant.
EINVAL
Nous n'aimons pas addr, length, ou offset (par exemple, ils sont trop grands, ou ne sont pas alignés sur une limite de page).
EINVAL
(depuis Linux 2.6.12) length était 0.
EINVAL
flags ne contenait aucun de MAP_PRIVATE, MAP_SHARED, ou MAP_SHARED_VALIDATE.
ENFILE
La limite système du nombre total de fichiers ouverts a été atteinte.
ENODEV
Le système de fichiers sous-jacent du fichier spécifié ne prend pas en charge le mappage mémoire.
ENOMEM
Aucune mémoire n'est disponible.
ENOMEM
Le nombre maximum de mappages du processus aurait été dépassé. Cette erreur peut également survenir pour munmap(), lors du débrayage d'une région au milieu d'un mappage existant, car cela entraîne deux mappages plus petits de chaque côté de la région débrayée.
ENOMEM
(depuis Linux 4.7) La limite RLIMIT_DATA du processus, décrite dans getrlimit(2), aurait été dépassée.
ENOMEM
Nous n'aimons pas addr, car il dépasse l'espace d'adressage virtuel du processeur.
EOVERFLOW
Sur une architecture 32 bits avec l'extension pour fichiers volumineux (c'est-à-dire en utilisant off_t 64 bits) : le nombre de pages utilisées pour length plus le nombre de pages utilisées pour offset dépasserait unsigned long (32 bits).
EPERM
L'argument prot demande PROT_EXEC mais la zone mappée appartient à un fichier sur un système de fichiers qui a été monté
nted no-exec.
EPERM
L'opération a été empêchée par un scellage de fichier ; voir fcntl(2).
EPERM
L'indicateur MAP_HUGETLB a été spécifié, mais l'appelant n'était pas privilégié (n'avait pas la capacité CAP_IPC_LOCK) et n'est pas membre du groupe hugetlb_shm_group ; voir la description de /proc/sys/vm/hugetlb_shm_group dans proc_sys_vm(5).
ETXTBSY
MAP_DENYWRITE était défini mais l'objet spécifié par fd est ouvert en écriture.

L'utilisation d'une région mappée peut entraîner les signaux suivants :

SIGSEGV
Tentative d'écriture dans une région mappée en lecture seule.
SIGBUS
Tentative d'accès à une page du tampon qui se trouve au-delà de la fin du fichier mappé. Pour une explication du traitement des octets dans la page qui correspond à la fin d'un fichier mappé dont la taille n'est pas un multiple de la taille de page, voir NOTES.

VERSIONS

Sur certaines architectures matérielles (par exemple, i386), PROT_WRITE implique PROT_READ. Il dépend de l'architecture que PROT_READ implique ou non PROT_EXEC. Les programmes portables doivent toujours définir PROT_EXEC s'ils ont l'intention d'exécuter du code dans le nouveau mappage.

La manière portable de créer un mappage est de spécifier addr comme 0 (NULL), et d'omettre MAP_FIXED de flags. Dans ce cas, le système choisit l'adresse pour le mappage ; l'adresse est choisie de manière à ne pas entrer en conflit avec un mappage existant, et ne sera pas 0. Si l'indicateur MAP_FIXED est spécifié, et que addr est 0 (NULL), alors l'adresse mappée sera 0 (NULL).

Certaines constantes de flags ne sont définies que si des macros de test de fonctionnalités appropriées sont définies (éventuellement par défaut) : _DEFAULT_SOURCE avec glibc 2.19 ou version ultérieure ; ou _BSD_SOURCE ou _SVID_SOURCE dans glibc 2.19 et versions antérieures. (L'utilisation de _GNU_SOURCE suffit également, et exiger cette macro spécifiquement aurait été plus logique, car tous ces indicateurs sont spécifiques à Linux.) Les indicateurs pertinents sont : MAP_32BIT, MAP_ANONYMOUS (et le synonyme MAP_ANON), MAP_DENYWRITE, MAP_EXECUTABLE, MAP_FILE, MAP_GROWSDOWN, MAP_HUGETLB, MAP_LOCKED, MAP_NONBLOCK, MAP_NORESERVE, MAP_POPULATE, et MAP_STACK.

Différences bibliothèque C/noyau

Cette page décrit l'interface fournie par la fonction d'enrobage mmap() de glibc. Initialement, cette fonction invoquait un appel système du même nom. Depuis Linux 2.4, cet appel système a été remplacé par mmap2(2), et aujourd'hui la fonction d'enrobage mmap() de glibc invoque mmap2(2) avec une valeur appropriément ajustée pour offset.

POSIX.1-2024.

HISTORIQUE

POSIX.1-2001, SVr4, 4.4BSD.

Sur les systèmes POSIX où mmap(), msync(2), et munmap() sont disponibles, _POSIX_MAPPED_FILES est défini dans <unistd.h> à une valeur supérieure à 0. (Voir aussi sysconf(3).)

NOTES

La mémoire mappée par mmap() est conservée lors d'un fork(2), avec les mêmes attributs.

Un fichier est mappé par multiples de la taille de page. Pour un fichier qui n'est pas un multiple de la taille de page, les octets restants dans la page partielle à la fin du mappage sont mis à zéro lors du mappage, et les modifications apportées à cette région ne sont pas écrites dans le fichier. L'effet de la modification de la taille du fichier sous-jacent d'un mappage sur les pages qui correspondent aux régions ajoutées ou supprimées du fichier n'est pas spécifié.

Une application peut déterminer quelles pages d'un mappage sont actuellement résidentes dans le cache de tampons/pages en utilisant mincore(2).

Utilisation de MAP_FIXED en toute sécurité

La seule utilisation sûre de MAP_FIXED est lorsque la plage d'adresses spécifiée par addr et length a été précédemment réservée à l'aide d'un autre mappage ; sinon, l'utilisation de MAP_FIXED est dangereuse car elle supprime de force les mappages préexistants, ce qui permet à un processus multithreadé de corrompre facilement son propre espace d'adressage.

Par exemple, supposons que le thread A examine /proc/pid/maps afin de localiser une plage d'adresses inutilisée qu'il peut mapper en utilisant MAP_FIXED, tandis que le thread B acquiert simultanément une partie ou la totalité de cette même plage d'adresses. Lorsque le thread A utilise ensuite mmap(MAP_FIXED), il écrasera effectivement le mappage que le thread B a créé. Dans ce scénario, le thread B n'a pas besoin de créer un mappage directement ; il suffit de faire un appel de bibliothèque qui, en interne, utilise dlopen(3) pour charger une autre bibliothèque partagée. L'appel dlopen(3) mappera la bibliothèque dans l'espace d'adressage du processus. De plus, presque tout appel de bibliothèque peut être implémenté de manière à ajouter des mappages mémoire à l'espace d'adressage, soit avec cette technique, soit en allouant simplement de la mémoire. Les exemples incluent brk(2), malloc(3), pthread_create(3), et les bibliothèques PAM http://www.linux-pam.org.

Depuis Linux 4.17, un programme multithreadé peut utiliser l'indicateur MAP_FIXED_NOREPLACE pour éviter le danger décrit ci-dessus lorsqu'il tente de créer un mappage à une adresse fixe qui n'a pas été réservée par un mappage préexistant.

Changements des horodatages pour les mappages basés sur des fichiers

Pour les mappages basés sur des fichiers, le champ st_atime du fichier mappé peut être mis à jour à tout moment entre mmap() et le démappage correspondant ; la première référence à une page mappée mettra à jour le champ s'il ne l'a pas déjà été.

Les champs st_ctime et st_mtime d'un fichier mappé avec PROT_WRITE et MAP_SHARED seront mis à jour après une écriture dans la région mappée, et avant une msync(2) ultérieure avec l'indicateur MS_SYNC ou MS_ASYNC, si une telle opération se produit.

Mappages de pages volumineuses (Huge TLB)

Pour les mappages qui utilisent des pages volumineuses, les exigences concernant les arguments de mmap() et munmap() diffèrent quelque peu des exigences pour les mappages qui utilisent la taille de page native du système.

Pour mmap(), offset doit être un multiple de la taille de page volumineuse sous-jacente. Le système aligne automatiquement length pour qu'il soit un multiple de la taille de page volumineuse sous-jacente.

Pour munmap(), addr et length doivent tous deux être un multiple de la taille de page volumineuse sous-jacente.

AVERTISSEMENTS

Contrairement aux implémentations typiques de malloc(3), mmap() n'empêche pas la création d'objets plus grands que PTRDIFF_MAX. Les objets plus grands que PTRDIFF_MAX ne fonctionnent que de manière limitée en C (en particulier, la soustraction de pointeurs entraîne un comportement indéfini si le résultat est supérieur à PTRDIFF_MAX). De plus, GCC suppose qu'aucun objet n'est plus grand que PTRDIFF_MAX. PTRDIFF_MAX est généralement la moitié de la taille de l'espace d'adressage ; ainsi, pour les processus 32 bits, il s'agit généralement de 0x7fffffff (presque 2 Gio).

BOGUES

Sur Linux, il n'y a aucune garantie comme celles suggérées ci-dessus sous MAP_NORESERVE. Par défaut, tout processus peut être tué à tout moment lorsque le système manque de mémoire.

Avant Linux 2.6.7, l'indicateur MAP_POPULATE n'avait d'effet que si prot était spécifié comme PROT_NONE.

SUSv3 spécifie que mmap() doit échouer si length est 0. Cependant, avant Linux 2.6.12, mmap() réussissait dans ce cas : aucun mappage n'était créé et l'appel retournait addr. Depuis Linux 2.6.12, mmap() échoue avec l'erreur EINVAL dans ce cas.

POSIX spécifie que le système doit toujours remplir de zéros toute page partielle à la fin de l'objet et que le système n'écrira jamais de modification de l'objet au-delà de sa fin. Sur Linux, lorsque vous écrivez des données dans une telle page partielle après la fin de l'objet, les données restent dans le cache de pages même après la fermeture et le démappage du fichier et, bien que les données ne soient jamais écrites dans le fichier lui-même, les mappages ultérieurs peuvent voir le contenu modifié. Dans certains cas, cela pourrait être corrigé en appelant msync(2) avant le démappage ; cependant, cela ne fonctionne pas sur tmpfs(5) (par exemple, lors de l'utilisation de l'interface de mémoire partagée POSIX décrite dans shm_overview(7)).

EXEMPLES

Le programme suivant affiche une partie du fichier spécifié dans son premier argument de ligne de commande sur la sortie standard. La plage d'octets à imprimer est spécifiée via des valeurs d'offset et de longueur dans les deuxième et troisième arguments de ligne de commande. Le programme crée un mappage mémoire des pages requises du fichier, puis utilise write(2) pour afficher les octets souhaités.

Source du programme

#includ
e <err.h> #include <fcntl.h> #include <stdio.h> #include <stdlib.h> #include <sys/mman.h> #include <sys/stat.h> #include <sys/types.h> #include <unistd.h> int main(int argc, char *argv[]) { int fd; char *addr; off_t offset, pa_offset; size_t length; ssize_t s; struct stat sb; if (argc < 3 || argc > 4) { fprintf(stderr, "%s fichier decalage [longueur]\n", argv[0]); exit(EXIT_FAILURE); } fd = open(argv[1], O_RDONLY); if (fd == -1) err(EXIT_FAILURE, "open"); if (fstat(fd, &sb) == -1) /* Pour obtenir la taille du fichier */ err(EXIT_FAILURE, "fstat"); offset = atoi(argv[2]); pa_offset = offset & ~(sysconf(_SC_PAGE_SIZE) - 1); /* Le decalage pour mmap() doit etre aligne sur la page */ if (offset >= sb.st_size) { fprintf(stderr, "le decalage est au-delà de la fin du fichier\n"); exit(EXIT_FAILURE); } if (argc == 4) { length = atoi(argv[3]); if (offset + length > sb.st_size) length = sb.st_size - offset; /* Impossible d'afficher des octets au-delà de la fin du fichier */ } else { /* Pas d'argument de longueur ==> afficher jusqu'à la fin du fichier */ length = sb.st_size - offset; } addr = mmap(NULL, length + offset - pa_offset, PROT_READ, MAP_PRIVATE, fd, pa_offset); if (addr == MAP_FAILED) err(EXIT_FAILURE, "mmap"); s = write(STDOUT_FILENO, addr + offset - pa_offset, length); if (s != length) { if (s == -1) err(EXIT_FAILURE, "write"); fprintf(stderr, "ecriture partielle"); exit(EXIT_FAILURE); } munmap(addr, length + offset - pa_offset); close(fd); exit(EXIT_SUCCESS); }
