mmap(2) Manuel des appels système mmap(2)

NOM

mmap, munmap - mapper ou désmapper des fichiers ou des périphériques en mémoire

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <sys/mman.h>
void *mmap(void *addr, size_t length, int prot, int flags, int fd, off_t offset);
int munmap(void *addr, size_t length);

Voir VERSIONS pour les informations sur les exigences des macros de test de fonctionnalités.

DESCRIPTION

mmap() crée un nouveau mappage dans l'espace d'adressage virtuel du processus appelant. L'adresse de départ du nouveau mappage est spécifiée dans addr. L'argument length spécifie la longueur du mappage (qui doit être supérieur à 0).

Si addr est NULL, alors le noyau choisit l'adresse (alignée sur page) à laquelle créer le mappage ; c'est la méthode la plus portable pour créer un nouveau mappage. Si addr n'est pas NULL, alors le noyau l'utilise comme une indication où placer le mappage ; sous Linux, le noyau choisira une limite de page proche (mais toujours supérieure ou égale à la valeur spécifiée par /proc/sys/vm/mmap_min_addr) et tentera d'y créer le mappage. Si un autre mappage existe déjà à cet endroit, le noyau choisit une nouvelle adresse qui peut dépendre ou non de l'indication. L'adresse du nouveau mappage est retournée comme résultat de l'appel.

Le contenu d'un mappage de fichier (par opposition à un mappage annonyme ; voir MAP_ANONYMOUS ci-dessous) est initialisé en utilisant length octets à partir du décalage offset dans le fichier (ou autre objet) référencé par le descripteur de fichier fd. offset doit être un multiple de la taille de page retournée par sysconf(_SC_PAGE_SIZE).

Après le retour de l'appel mmap(), le descripteur de fichier, fd, peut être fermé immédiatement sans invalider le mappage.

L'argument prot décrit la protection mémoire souhaitée du mappage (et ne doit pas entrer en conflit avec le mode d'ouverture du fichier). C'est soit PROT_NONE, soit le OU binaire d'une ou plusieurs des indicateurs suivants :

PROT_EXEC
Les pages peuvent être exécutées.
PROT_READ
Les pages peuvent être lues.
PROT_WRITE
Les pages peuvent être écrites.
PROT_NONE
Les pages ne peuvent pas être accédées.

L'argument flags

L'argument flags détermine si les mises à jour du mappage sont visibles par d'autres processus mappant la même région, et si les mises à jour sont répercutées dans le fichier sous-jacent. Ce comportement est déterminé en incluant exactement une des valeurs suivantes dans flags :

MAP_SHARED
Partager ce mappage. Les mises à jour du mappage sont visibles par d'autres processus mappant la même région, et (dans le cas de mappages liés à un fichier) sont répercutées dans le fichier sous-jacent. (Pour contrôler précisément quand les mises à jour sont répercutées dans le fichier sous-jacent, il faut utiliser msync(2).)
MAP_SHARED_VALIDATE (depuis Linux 4.15)
Cet indicateur fournit le même comportement que MAP_SHARED sauf que les mappages MAP_SHARED ignorent les indicateurs inconnus dans flags. En revanche, lors de la création d'un mappage à l'aide de MAP_SHARED_VALIDATE, le noyau vérifie que tous les indicateurs passés sont connus et fait échouer le mappage avec l'erreur EOPNOTSUPP pour les indicateurs inconnus. Ce type de mappage est également requis pour pouvoir utiliser certains indicateurs de mappage (par exemple, MAP_SYNC).
MAP_PRIVATE
Créer un mappage privé avec copie sur écriture. Les mises à jour du mappage ne sont pas visibles par d'autres processus mappant le même fichier, et ne sont pas répercutées dans le fichier sous-jacent. Il n'est pas spécifié si les modifications apportées au fichier après l'appel mmap() sont visibles dans la région mappée.

MAP_SHARED et MAP_PRIVATE sont décrits dans POSIX.1-2001 et POSIX.1-2008. MAP_SHARED_VALIDATE est une extension Linux.

De plus, zéro ou plus des valeurs suivantes peuvent être combinées par OU dans flags :

MAP_32BIT (depuis Linux 2.4.20, 2.6)
Placer le mappage dans les 2 premiers Gigaoctets de l'espace d'adressage du processus. Cet indicateur n'est pris en charge que sur x86-64, pour les programmes 64 bits. Il a été ajouté pour permettre l'allocation des piles des threads quelque part dans les 2 premiers Go de mémoire, afin d'améliorer les performances de commutation de contexte sur certains processeurs 64 bits anciens. Les processeurs x86-64 modernes n'ont plus ce problème de performance, donc l'utilisation de cet indicateur n'est pas nécessaire sur ces systèmes. L'indicateur MAP_32BIT est ignoré lorsque MAP_FIXED est défini.
MAP_ANON
Synonyme de MAP_ANONYMOUS ; fourni pour la compatibilité avec d'autres implémentations.
MAP_ANONYMOUS
Le mappage n'est soutenu par aucun fichier ; son contenu est initialisé à zéro. L'argument fd est ignoré ; cependant, certaines implémentations exigent que fd soit -1 si MAP_ANONYMOUS (ou MAP_ANON) est spécifié, et les applications portables doivent s'en assurer. L'argument offset doit être zéro. Le support de MAP_ANONYMOUS en conjonction avec MAP_SHARED a été ajouté dans Linux 2.4.
MAP_DENYWRITE
Cet indicateur est ignoré. (Il y a longtemps — Linux 2.0 et antérieures — il signalait que les tentatives d'écriture dans le fichier sous-jacent devaient échouer avec ETXTBSY. Mais c'était une source d'attaques par déni de service.)
MAP_EXECUTABLE
Cet indicateur est ignoré.
MAP_FILE
Indicateur de compatibilité. Ignoré.
MAP_FIXED
N'interprète pas addr comme une indication : place le mappage exactement à cette adresse. addr doit être correctement aligné : pour la plupart des architectures, un multiple de la taille de page est suffisant ; cependant, certaines architectures peuvent imposer des restrictions supplémentaires. Si la région mémoire spécifiée par addr et length chevauche des pages d'un ou plusieurs mappages existants, alors la partie chevauchée des mappages existants sera rejetée. Si l'adresse spécifiée ne peut pas être utilisée, mmap() échouera.
Les logiciels qui aspirent à être portables doivent utiliser l'indicateur MAP_FIXED avec précaution, en gardant à l'esprit que la disposition exacte des mappages mémoire d'un processus est autorisée à changer significativement entre les versions de Linux, les versions de la bibliothèque C et les versions des systèmes d'exploitation. Lisez attentivement la discussion de cet indicateur dans NOTES !
MAP_FIXED_NOREPLACE (depuis Linux 4.17)
Cet indicateur fournit un comportement similaire à MAP_FIXED en ce qui concerne l'application de addr, mais diffère en ce que MAP_FIXED_NOREPLACE ne supprime jamais une plage déjà mappée. Si la plage demandée entre en collision avec un mappage existant, cet appel échoue avec l'erreur EEXIST. Cet indicateur peut donc être utilisé comme un moyen d'essayer de mapper une plage d'adresses de manière atomique (par rapport aux autres threads) : un thread réussira ; tous les autres signaleront un échec.
Notez que les anciens noyaux qui ne reconnaissent pas l'indicateur MAP_FIXED_NOREPLACE (lors de la détection d'une collision avec un mappage préexistant) se rabattront généralement sur un comportement similaire à MAP_FIXED.
MAP_GROWSDOWN
Cet indicateur est ignoré.
MAP_HUGETLB
Utiliser des pages mémoire "huge" (grandes) pour ce mappage. La taille de la page "huge" dépend du système et est généralement de 2 Mo ou 1 Go. Les mappages avec pages "huge" peuvent avoir des performances améliorées, mais sont moins flexibles. L'utilisation de pages "huge" doit être configurée via des paramètres du noyau (par exemple, /proc/sys/vm/nr_hugepages).
Les mappages de fichiers ne sont pas pris en charge avec MAP_HUGETLB. Pour utiliser cet indicateur, vous devez spécifier MAP_ANONYMOUS. La taille du mappage doit être un multiple de la taille de la page "huge". Cet indicateur est spécifique à Linux.
MAP_POPULATE (depuis Linux 2.6.18)
Effectuer l'allocation et l'initialisation des pages mémoire (dans le cas d'un mappage anonyme) ou le remplissage des pages mémoire (dans le cas d'un mappage lié à un fichier) au moment de l'appel mmap(), au lieu de le faire paresseusement à la première demande de chaque page. Cela est utile pour les applications qui ont besoin que les données soient rapidement accessibles, par exemple, les bases de données. Les pages sont remplies en arrière-plan. L'utilisation de MAP_POPULATE sans MAP_NONBLOCK bloque jusqu'à ce que toutes les pages soient remplies. Les pages remplies de manière paresseuse après cet appel ne sont pas affectées.
MAP_NONBLOCK (depuis Linux 2.6.18)
Lorsque utilisé avec MAP_POPULATE, effectue le remplissage des pages en arrière-plan, sans bloquer. Cet indicateur est ignoré s'il n'est pas utilisé avec MAP_POPULATE.
MAP_SYNC (depuis Linux 4.15)
Pour les mappages MAP_SHARED_VALIDATE, cet indicateur garantit que toutes les écritures dans la région mappée sont immédiatement écrites dans le disque sous-jacent. Cela est équivalent à appeler msync(..., MS_SYNC) immédiatement après chaque écriture, mais peut être plus performant.
MAP_UNINITIALIZED (depuis Linux 4.10)
Indique que les pages mappées ne doivent pas être automatiquement initialisées à zéro. Ceci est généralement utilisé avec des mappages de périphériques ou d'autres zones mémoire qui ne sont pas censées contenir des données sans signification. Cet indicateur peut améliorer les performances en évitant des opérations de copie et d'initialisation inutiles. Il est souvent utilisé en conjonction avec MAP_SHARED et peut affecter le comportement de certaines opérations comme mremap().

L'argument munmap supprime les mappages de la région d'adresses virtuelles spécifiée à partir de addr et de longueur length. Toute adresse de page dans la plage [addr, addr+length) qui était précédemment mappée devient inaccessible. La zone mémoire est automatiquement désallouée. Les appels ultérieurs à munmap() pour des adresses déjà désallouées ou qui ne font pas partie d'un mappage existant n'ont aucun effet.

L'appel munmap() ne déplace pas le décalage du pointeur de fichier, ni ne modifie le fichier sous-jacent.

Si une région de mémoire est mappée plusieurs fois (par exemple, via plusieurs appels à mmap() avec des flags MAP_SHARED ou MAP_PRIVATE), un appel à munmap() pour une partie de cette région rendra cette partie inaccessible. Les autres mappages de cette région ne sont pas affectés.

Les pages affectées par munmap() sont automatiquement libérées.

Si une partie d'une région mappée est supprimée avec munmap(), et si une partie restante de cette région est écrite, alors les données écrites dans la partie restante sont répercutées dans le fichier sous-jacent (dans le cas d'un mappage lié à un fichier).

VALEUR RENVOYÉE

En cas de succès, mmap() renvoie un pointeur vers l'adresse mappée. Si addr n'était pas NULL, cette adresse est égale à addr (arrondi à la taille de page la plus proche). Si addr était NULL, l'adresse renvoyée est l'adresse choisie par le noyau. En cas d'échec, mmap() renvoie MAP_FAILED (défini dans <sys/mman.h>) et errno est défini pour indiquer l'erreur.

En cas de succès, munmap() renvoie 0. En cas d'échec, -1 est renvoyé et errno est défini pour indiquer l'erreur.

ERREURS

Les erreurs typiques pour mmap() sont :

EACCES
Le fichier spécifié par fd ne peut pas être mappé avec les protections demandées. Ou, la protection demandée n'est pas compatible avec le mode d'ouverture du fichier. Ou, le processus n'a pas la permission d'accéder au fichier ou à la région mémoire.
EBADF
fd n'est pas un descripteur de fichier valide.
EAGAIN
Le système est à court de mémoire virtuelle.
EINVAL
L'une des erreurs suivantes est rencontrée :
  • length est nul.
  • fd est MAP_ANONYMOUS mais offset n'est pas zéro.
  • offset n'est pas un multiple de la taille de page.
  • addr n'est pas NULL et n'est pas correctement aligné (ou ne peut pas être utilisé pour une raison quelconque).
  • flags contient une combinaison invalide d'options.
  • Un indicateur inconnu est présent dans flags, et MAP_SHARED_VALIDATE n'a pas été spécifié.
ENFILE
Il y a trop de descripteurs de fichiers ouverts.
ENOMEM
Le processus n'a pas assez de mémoire disponible pour le mappage demandé.
EFBIG
L'opération dépasse la taille maximale autorisée pour un fichier.
EPERM
L'opération ne correspond pas aux privilèges du processus.
ETXTBSY
Le fichier est ouvert en écriture, et MAP_DENYWRITE est spécifié (cette dernière condition est obsolète et l'erreur n'est plus générée par le noyau).

Les erreurs typiques pour munmap() sont :

EINVAL
addr n'est pas un multiple de la taille de page, ou length est zéro.
ENOMEM
Le système est à court de mémoire.

CONFORMITÉ

POSIX.1-2001, POSIX.1-2008.

NOTES

La définition de MAP_ANONYMOUS diffère entre les systèmes. Sous Linux, cet indicateur est supporté à la fois pour les mappages MAP_PRIVATE et MAP_SHARED. D'autres systèmes peuvent ne pas supporter MAP_SHARED | MAP_ANONYMOUS, et peuvent exiger que fd soit -1.

Il est possible d'utiliser mmap() pour mapper des fichiers qui ne sont pas actuellement présents dans le système de fichiers (par exemple, des périphériques bloc spéciaux). Dans ce cas, le comportement dépendra du périphérique.

L'utilisation de MAP_FIXED est déconseillée pour le code portable. La disposition de la mémoire virtuelle d'un processus est gérée par le noyau, et sa structure peut varier considérablement entre les versions du système d'exploitation et même entre les versions de la bibliothèque C. Si vous utilisez MAP_FIXED, vous pourriez avoir besoin de réécrire votre code pour chaque nouvelle version de Linux. Utilisez MAP_FIXED uniquement si vous savez exactement ce que vous faites et si vous n'avez pas d'autre choix.

Si un programme mappe une région avec MAP_SHARED, écrit dans cette région, puis mappe la même région à nouveau avec MAP_PRIVATE, les modifications écrites dans la région MAP_SHARED peuvent ou non être visibles dans la nouvelle région MAP_PRIVATE. Il est spécifié que les modifications apportées au fichier sous-jacent après un appel mmap() ne sont pas nécessairement visibles dans la région mappée. En bref, le comportement de MAP_PRIVATE vis-à-vis des modifications apportées au fichier après le mappage est non spécifié.

La manière dont mmap() gère les fichiers qui sont plus petits que la longueur demandée dépend du type de mappage et du système de fichiers. Pour les mappages MAP_SHARED, les accès en lecture en dehors des limites du fichier peuvent entraîner des erreurs de segmentation ou des données arbitraires. Les écritures en dehors des limites du fichier sont généralement interdites.

Les appels système mmap() et munmap() peuvent être interrompus par des signaux. La documentation indique que dans ce cas, ils doivent être relancés, mais cela n'est pas toujours le cas. En pratique, les appels système interrompus par un signal échouent généralement avec EINTR.

Sous Linux, il est possible d'utiliser mmap() pour mapper un terminal. La signification de cet appel système dépendra de l'implémentation du terminal.

L'utilisation de MAP_HUGETLB peut améliorer les performances du système en réduisant la pression sur le TLB (Translation Lookaside Buffer). Cependant, l'utilisation de pages "huge" peut entraîner une fragmentation de la mémoire et une utilisation inefficace de la mémoire si les régions mappées sont petites.

Les indicateurs MAP_POPULATE et MAP_NONBLOCK ont été ajoutés pour améliorer la gestion des mappages d'E/S, en particulier pour les applications qui accèdent fréquemment à de grandes quantités de données. Ils permettent de pré-charger les pages mémoire et d'éviter les latences lors des premiers accès.

La combinaison de MAP_SHARED_VALIDATE et MAP_SYNC est particulièrement utile pour les applications qui nécessitent une garantie stricte de persistance des données sur le disque, comme les systèmes de bases de données ou les systèmes de fichiers.

MAP_GROWSDOWN
Ce drapeau est utilisé pour les piles (stacks). Il indique au système de mémoire virtuelle du noyau que le mappage doit s'étendre vers le bas en mémoire. L'adresse de retour est une page plus bas que la zone mémoire qui est effectivement créée dans l'espace d'adressage virtuel du processus. Toucher une adresse dans la page « garde » sous le mappage entraînera l'extension du mappage d'une page. MAP_HUGETLB (depuis Linux 2.6.32)
Allouer le mappage en utilisant des pages « énormes » (huge pages). Voir le fichier source du noyau Linux Documentation/admin-guide/mm/hugetlbpage.rst pour plus d'informations, ainsi que la section NOTES, ci-dessous.
MAP_HUGE_2MB
MAP_HUGE_1GB (depuis Linux 3.8)
Utilisé en conjonction avec MAP_HUGETLB pour sélectionner des tailles de page hugetlb alternatives (respectivement, 2 Mo et 1 Go) sur les systèmes qui prennent en charge plusieurs tailles de page hugetlb.
Plus généralement, la taille de page énorme souhaitée peut être configurée en encodant le logarithme en base 2 de la taille de page souhaitée dans les six bits à la position MAP_HUGE_SHIFT. (Une valeur de zéro dans ce champ de bits fournit la taille de page énorme par défaut ; la taille de page énorme par défaut peut être découverte via le champ Hugepagesize exposé par /proc/meminfo.) Ainsi, les deux constantes ci-dessus sont définies comme suit :

#define MAP_HUGE_2MB    (21 << MAP_HUGE_SHIFT)
#define MAP_HUGE_1GB    (30 << MAP_HUGE_SHIFT)

La gamme de tailles de pages énormes prises en charge par le système peut être découverte en listant les sous-répertoires dans /sys/kernel/mm/hugepages.
MAP_LOCKED (depuis Linux 2.5.37)
Marquer la région mappée pour être verrouillée de la même manière que mlock(2). Cette implémentation tentera de peupler (préfault) toute la plage, mais l'appel mmap() ne retournera pas ENOMEM si cela échoue. Par conséquent, des fautes majeures peuvent survenir plus tard. La sémantique n'est donc pas aussi forte que mlock(2). Il faut utiliser mmap() plus mlock(2) lorsque les fautes majeures ne sont pas acceptables après l'initialisation du mappage. Le drapeau MAP_LOCKED est ignoré dans les anciens noyaux.
MAP_NONBLOCK (depuis Linux 2.5.46)
Ce drapeau n'est significatif qu'en conjonction avec MAP_POPULATE. Ne pas effectuer de prélecture (read-ahead) : créer des entrées de table de pages uniquement pour les pages déjà présentes en RAM. Depuis Linux 2.6.23, ce drapeau fait que MAP_POPULATE ne fait rien. Un jour, la combinaison de MAP_POPULATE et MAP_NONBLOCK pourrait être réimplémentée.
MAP_NORESERVE
Ne pas réserver d'espace de swap pour ce mappage. Lorsque l'espace de swap est réservé, on a la garantie qu'il est possible de modifier le mappage. Lorsque l'espace de swap n'est pas réservé, on peut recevoir un SIGSEGV lors d'une écriture s'il n'y a pas de mémoire physique disponible. Voir aussi la discussion sur le fichier /proc/sys/vm/overcommit_memory dans proc_sys_vm(5). Avant Linux 2.6, ce drapeau n'avait d'effet que pour les mappages privés inscriptibles.
MAP_POPULATE (depuis Linux 2.5.46)
Peupler (préfault) les tables de pages pour un mappage. Pour un mappage de fichier, cela provoque une prélecture du fichier. Cela aidera à réduire le blocage sur les fautes de page plus tard. L'appel mmap() ne échoue pas si le mappage ne peut pas être peuplé (par exemple, en raison de limitations sur le nombre de pages énormes mappées lors de l'utilisation de MAP_HUGETLB). La prise en charge de MAP_POPULATE en conjonction avec les mappages privés a été ajoutée dans Linux 2.6.23.
MAP_STACK (depuis Linux 2.6.27)
Allouer le mappage à une adresse appropriée pour une pile de processus ou de thread.
Ce drapeau est actuellement un no-op sous Linux. Cependant, en utilisant ce drapeau, les applications peuvent s'assurer qu'elles obtiendront une prise en charge transparente si le drapeau est implémenté à l'avenir. Ainsi, il est utilisé dans l'implémentation des threads de glibc pour tenir compte du fait que certaines architectures peuvent (plus tard) nécessiter un traitement spécial pour les allocations de piles. Une autre raison d'utiliser ce drapeau est la portabilité : MAP_STACK existe (et a un effet) sur certains autres systèmes (par exemple, certains BSD).
MAP_SYNC (depuis Linux 4.15)
Ce drapeau n'est disponible qu'avec le type de mappage MAP_SHARED_VALIDATE ; les mappages de type MAP_SHARED ignoreront silencieusement ce drapeau. Ce drapeau n'est pris en charge que pour les fichiers prenant en charge DAX (mappage direct de la mémoire persistante). Pour les autres fichiers, la création d'un mappage avec ce drapeau entraîne une erreur EOPNOTSUPP.
Les mappages de fichiers partagés avec ce drapeau garantissent que, bien que certaines données en mémoire soient mappées en écriture dans l'espace d'adressage du processus, elles seront visibles dans le même fichier au même offset, même après un crash ou un redémarrage du système. En conjonction avec l'utilisation d'instructions CPU appropriées, cela offre aux utilisateurs de tels mappages un moyen plus efficace de rendre persistantes les modifications de données.
MAP_UNINITIALIZED (depuis Linux 2.6.33)
Ne pas effacer les pages anonymes. Ce drapeau vise à améliorer les performances sur les appareils embarqués. Ce drapeau n'est honoré que si le noyau a été configuré avec l'option CONFIG_MMAP_ALLOW_UNINITIALIZED. En raison des implications de sécurité, cette option n'est normalement activée que sur les appareils embarqués (c'est-à-dire les appareils sur lesquels on a un contrôle total sur le contenu de la mémoire utilisateur).

Parmi les drapeaux ci-dessus, seul MAP_FIXED est spécifié dans POSIX.1-2001 et POSIX.1-2008. Cependant, la plupart des systèmes prennent également en charge MAP_ANONYMOUS (ou son synonyme MAP_ANON).

munmap()

L'appel système munmap() supprime les mappages pour la plage d'adresses spécifiée, et provoque des références ultérieures à des adresses dans la plage pour générer des références mémoire invalides. La région est également automatiquement démappée lorsque le processus se termine. En revanche, la fermeture du descripteur de fichier ne démappe pas la région.

L'adresse addr doit être un multiple de la taille de page (mais length n'a pas besoin de l'être). Toutes les pages contenant une partie de la plage indiquée sont démappées, et les références ultérieures à ces pages généreront SIGSEGV. Ce n'est pas une erreur si la plage indiquée ne contient aucune page mappée.

VALEUR DE RETOUR

En cas de succès, mmap() renvoie un pointeur vers la zone mappée. En cas d'erreur, la valeur MAP_FAILED (c'est-à-dire (void *) -1) est renvoyée, et errno est définie pour indiquer l'erreur.

En cas de succès, munmap() renvoie 0. En cas d'échec, il renvoie -1, et errno est définie pour indiquer l'erreur (probablement EINVAL).

ERREURS

EACCES
Un descripteur de fichier fait référence à un fichier non régulier. Ou un mappage de fichier a été demandé, mais fd n'est pas ouvert en lecture. Ou MAP_SHARED a été demandé et PROT_WRITE est défini, mais fd n'est pas ouvert en mode lecture/écriture (O_RDWR). Ou PROT_WRITE est défini, mais le fichier est en mode ajout uniquement.
EAGAIN
Le fichier a été verrouillé, ou trop de mémoire a été verrouillée (voir setrlimit(2)).
EBADF
fd n'est pas un descripteur de fichier valide (et MAP_ANONYMOUS n'a pas été défini).
EEXIST
MAP_FIXED_NOREPLACE a été spécifié dans flags, et la plage couverte par addr et length chevauche un mappage existant.
EINVAL

VERSIONS

Sur certaines architectures matérielles (par exemple, i386), PROT_WRITE implique PROT_READ. Il est dépendant de l'architecture que PROT_READ implique ou non PROT_EXEC. Les programmes portables devraient toujours définir PROT_EXEC s'ils ont l'intention d'exécuter du code dans le nouveau mappage.

La manière portable de créer un mappage est de spécifier addr comme 0 (NULL) et d'omettre MAP_FIXED de flags. Dans ce cas, le système choisit l'adresse pour le mappage ; l'adresse est choisie de manière à ne pas entrer en conflit avec un mappage existant et ne sera pas 0. Si le drapeau MAP_FIXED est spécifié et que addr est 0 (NULL), alors l'adresse mappée sera 0 (NULL).

Certaines constantes de flags ne sont définies que si les macros de test de fonctionnalités appropriées sont définies (possiblement par défaut) : _DEFAULT_SOURCE avec glibc 2.19 ou ultérieure ; ou _BSD_SOURCE ou _SVID_SOURCE dans glibc 2.19 et antérieures. (L'utilisation de _GNU_SOURCE suffit également, et exiger spécifiquement cette macro aurait été plus logique, car ces drapeaux sont tous spécifiques à Linux.) Les drapeaux pertinents sont : MAP_32BIT, MAP_ANONYMOUS (et son synonyme MAP_ANON), MAP_DENYWRITE, MAP_EXECUTABLE, MAP_FILE, MAP_GROWSDOWN, MAP_HUGETLB, MAP_LOCKED, MAP_NONBLOCK, MAP_NORESERVE, MAP_POPULATE et MAP_STACK.

Différences bibliothèque C/noyau

Cette page décrit l'interface fournie par la fonction wrapper glibc mmap(). Initialement, cette fonction invoquait un appel système du même nom. Depuis Linux 2.4, cet appel système a été remplacé par mmap2(2), et de nos jours, la fonction wrapper glibc mmap() invoque mmap2(2) avec une valeur adaptée pour offset.

HISTORIQUE

POSIX.1-2001, SVr4, 4.4BSD.

Sur les systèmes POSIX où mmap(), msync(2), et munmap() sont disponibles, _POSIX_MAPPED_FILES est défini dans <unistd.h> à une valeur supérieure à 0. (Voir aussi sysconf(3).)

NOTES

La mémoire mappée par mmap() est préservée lors de fork(2), avec les mêmes attributs.

Un fichier est mappé par multiples de la taille de page. Pour un fichier qui n'est pas un multiple de la taille de page, les octets restants dans la page partielle à la fin du mappage sont mis à zéro lors du mappage, et les modifications apportées à cette région ne sont pas écrites dans le fichier. L'effet de la modification de la taille du fichier sous-jacent d'un mappage sur les pages correspondant aux régions ajoutées ou supprimées du fichier n'est pas spécifié.

Une application peut déterminer quelles pages d'un mappage sont actuellement résidentes dans le cache de tampons/pages en utilisant mincore(2).

Utilisation sécurisée de MAP_FIXED

La seule utilisation sûre de MAP_FIXED est lorsque la plage d'adresses spécifiée par addr et length a été précédemment réservée à l'aide d'un autre mappage ; sinon, l'utilisation de MAP_FIXED est dangereuse car elle supprime de force les mappages préexistants, ce qui permet à un processus multithread de corrompre facilement son propre espace d'adressage.

Par exemple, supposons que le thread A examine /proc/pid/maps afin de localiser une plage d'adresses inutilisée qu'il peut mapper en utilisant MAP_FIXED, tandis que le thread B acquiert simultanément tout ou partie de cette même plage d'adresses. Lorsque le thread A utilise ensuite mmap(MAP_FIXED), il écrasera effectivement le mappage créé par le thread B. Dans ce scénario, le thread B n'a pas besoin de créer un mappage directement ; il suffit de faire un appel de fonction qui, en interne, utilise dlopen(3) pour charger une autre bibliothèque partagée. L'appel dlopen(3) mappera la bibliothèque dans l'espace d'adressage du processus. De plus, presque tout appel de fonction peut être implémenté de manière à ajouter des mappages mémoire à l'espace d'adressage, soit avec cette technique, soit en allouant simplement de la mémoire. Des exemples incluent brk(2), malloc(3), pthread_create(3), et les bibliothèques PAM http://www.linux-pam.org.

Depuis Linux 4.17, un programme multithread peut utiliser le drapeau MAP_FIXED_NOREPLACE pour éviter le danger décrit ci-dessus lors de la tentative de création d'un mappage à une adresse fixe qui n'a pas été réservée par un mappage préexistant.

Modifications des horodatages pour les mappages de fichiers

Pour les mappages de fichiers, le champ st_atime du fichier mappé peut être mis à jour à tout moment entre mmap() et le démappage correspondant ; la première référence à une page mappée mettra à jour le champ s'il n'a pas déjà été fait.

Les champs st_ctime et st_mtime pour un fichier mappé avec PROT_WRITE et MAP_SHARED seront mis à jour après une écriture dans la région mappée, et avant un msync(2) ultérieur avec les drapeaux MS_SYNC ou MS_ASYNC, si cela se produit.

Mappages de pages volumineuses (Huge TLB)

Pour les mappages qui utilisent des pages volumineuses, les exigences pour les arguments de mmap() et munmap() diffèrent quelque peu des exigences pour les mappages qui utilisent la taille de page native du système.

Pour mmap(), offset doit être un multiple de la taille de la page volumineuse sous-jacente. Le système aligne automatiquement length pour qu'il soit un multiple de la taille de la page volumineuse sous-jacente.

Pour munmap(), addr et length doivent tous deux être un multiple de la taille de la page volumineuse sous-jacente.

MISES EN GARDE

Contrairement aux implémentations typiques de malloc(3), mmap() n'empêche pas la création d'objets plus grands que PTRDIFF_MAX. Les objets plus grands que PTRDIFF_MAX ne fonctionnent que de manière limitée en C (en particulier, la soustraction de pointeurs entraîne un comportement indéfini si le résultat est supérieur à PTRDIFF_MAX). De plus, GCC suppose également qu'aucun objet n'est plus grand que PTRDIFF_MAX. PTRDIFF_MAX est généralement la moitié de la taille de l'espace d'adressage ; ainsi, pour les processus 32 bits, il s'agit généralement de 0x7fffffff (presque 2 Go).

BOGUES

Sous Linux, il n'y a aucune garantie comme celles suggérées ci-dessus sous MAP_NORESERVE. Par défaut, tout processus peut être tué à tout moment lorsque le système manque de mémoire.

Avant Linux 2.6.7, le drapeau MAP_POPULATE n'avait d'effet que si prot était spécifié comme PROT_NONE.

SUSv3 spécifie que mmap() devrait échouer si length est 0. Cependant, avant Linux 2.6.12, mmap() réussissait dans ce cas : aucun mappage n'était créé et l'appel retournait addr. Depuis Linux 2.6.12, mmap() échoue avec l'erreur EINVAL pour ce cas.

POSIX spécifie que le système doit toujours remplir de zéros toute page partielle à la fin de l'objet et que le système n'écrira jamais de modification de l'objet au-delà de sa fin. Sous Linux, lorsque vous écrivez des données dans une telle page partielle après la fin de l'objet, les données restent dans le cache de pages même après la fermeture et le démappage du fichier, et bien que les données ne soient jamais écrites dans le fichier lui-même, les mappages ultérieurs peuvent voir le contenu modifié. Dans certains cas, cela pourrait être corrigé en appelant msync(2) avant le démappage ; cependant, cela ne fonctionne pas sur tmpfs(5) (par exemple, lors de l'utilisation de l'interface de mémoire partagée POSIX décrite dans shm_overview(7)).

EXEMPLES

Le programme suivant affiche une partie du fichier spécifié dans son premier argument de ligne de commande sur la sortie standard. La plage d'octets à afficher est spécifiée par l'offset et la longueur

h valeurs dans les deuxième et troisième arguments de ligne de commande. Le programme crée un mappage mémoire des pages requises du fichier, puis utilise write(2) pour écrire les octets désirés.

Source du programme

#include <err.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/mman.h>
#include <sys/stat.h>
#include <sys/types.h>
#include <unistd.h>
int
main(int argc, char *argv[])
{
    int          fd;
    char         *addr;
    off_t        offset, pa_offset;
    size_t       length;
    ssize_t      s;
    struct stat  sb;
    if (argc < 3 || argc > 4) {
        fprintf(stderr, "%s file offset [length]\n", argv[0]);
        exit(EXIT_FAILURE);
    }
    fd = open(argv[1], O_RDONLY);
    if (fd == -1)
        err(EXIT_FAILURE, "open");
    if (fstat(fd, &sb) == -1)           /* Pour obtenir la taille du fichier */
        err(EXIT_FAILURE, "fstat");
    offset = atoi(argv[2]);
    pa_offset = offset & ~(sysconf(_SC_PAGE_SIZE) - 1);
        /* l'offset pour mmap() doit être aligné sur une page */
    if (offset >= sb.st_size) {
        fprintf(stderr, "l'offset est après la fin du fichier\n");
        exit(EXIT_FAILURE);
    }
    if (argc == 4) {
        length = atoi(argv[3]);
        if (offset + length > sb.st_size)
            length = sb.st_size - offset;
                /* Impossible d'afficher les octets après la fin du fichier */
    } else {    /* Pas d'argument length ==> afficher jusqu'à la fin du fichier */
        length = sb.st_size - offset;
    }
    addr = mmap(NULL, length + offset - pa_offset, PROT_READ,
                MAP_PRIVATE, fd, pa_offset);
    if (addr == MAP_FAILED)
        err(EXIT_FAILURE, "mmap");
    s = write(STDOUT_FILENO, addr + offset - pa_offset, length);
    if (s != length) {
        if (s == -1)
            err(EXIT_FAILURE, "write");
        fprintf(stderr, "écriture partielle\n");
        exit(EXIT_FAILURE);
    }
    munmap(addr, length + offset - pa_offset);
    close(fd);
    exit(EXIT_SUCCESS);
}
