membarrier(2) Manuel des appels système membarrier(2)

NOM

membarrier - émettre des barrières mémoire sur un ensemble de threads

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNOPSIS

#include <linux/membarrier.h> /* Définition des constantes MEMBARRIER_* */
#include <sys/syscall.h>      /* Définition des constantes SYS_* */
#include <unistd.h>
int syscall(SYS_membarrier, int cmd, unsigned int flags, int cpu_id);

Note : glibc ne fournit pas de fonction d'enrobage pour membarrier(), nécessitant l'utilisation de syscall(2).

DESCRIPTION

L'appel système membarrier() aide à réduire la surcharge des instructions de barrière mémoire requises pour ordonnancer les accès mémoire sur les systèmes multi-cœurs. Cependant, cet appel système est plus lourd qu'une barrière mémoire, donc son utilisation efficace n'est pas aussi simple que de remplacer les barrières mémoire par cet appel système, mais nécessite une compréhension des détails ci-dessous.

L'utilisation des barrières mémoire doit être effectuée en tenant compte qu'une barrière mémoire doit toujours être soit appariée avec sa barrière mémoire correspondante, soit que le modèle mémoire de l'architecture ne nécessite pas les barrières appariées.

Il existe des cas où un côté des barrières appariées (que nous appellerons le "côté rapide") est exécuté beaucoup plus souvent que l'autre (que nous appellerons le "côté lent"). C'est une cible privilégiée pour l'utilisation de membarrier(). L'idée clé est de remplacer, pour ces barrières appariées, les barrières mémoire du côté rapide par de simples barrières compilateur, par exemple :


asm volatile("" : : : "memory")

et de remplacer les barrières mémoire du côté lent par des appels à membarrier().

Cela ajoutera une surcharge au côté lent, et supprimera la surcharge du côté rapide, résultant ainsi en une augmentation globale des performances tant que le côté lent est suffisamment peu fréquent pour que la surcharge des appels membarrier() ne dépasse pas le gain de performance du côté rapide.

L'argument cmd est l'une des options suivantes :

MEMBARRIER_CMD_QUERY (depuis Linux 4.3)
Interroger l'ensemble des commandes supportées. La valeur de retour de l'appel est un masque de bits des commandes supportées. MEMBARRIER_CMD_QUERY, qui a la valeur 0, n'est pas inclus dans ce masque de bits. Cette commande est toujours supportée (sur les noyaux où membarrier() est fourni).
MEMBARRIER_CMD_GLOBAL (depuis Linux 4.16)
S'assurer que tous les threads de tous les processus du système passent par un état où tous les accès mémoire aux adresses de l'espace utilisateur correspondent à l'ordre du programme entre l'entrée et le retour de l'appel système membarrier(). Tous les threads du système sont ciblés par cette commande.
MEMBARRIER_CMD_GLOBAL_EXPEDITED (depuis Linux 4.16)
Exécuter une barrière mémoire sur tous les threads en cours d'exécution de tous les processus qui se sont précédemment enregistrés avec MEMBARRIER_CMD_REGISTER_GLOBAL_EXPEDITED.
Au retour de l'appel système, le thread appelant a la garantie que tous les threads en cours d'exécution ont passé par un état où tous les accès mémoire aux adresses de l'espace utilisateur correspondent à l'ordre du programme entre l'entrée et le retour de l'appel système (les threads non en cours d'exécution sont de facto dans un tel état). Cette garantie n'est fournie que pour les threads des processus qui se sont préalablement enregistrés avec MEMBARRIER_CMD_REGISTER_GLOBAL_EXPEDITED.
Étant donné que l'enregistrement concerne l'intention de recevoir les barrières, il est valide d'invoquer MEMBARRIER_CMD_GLOBAL_EXPEDITED à partir d'un processus qui n'a pas utilisé MEMBARRIER_CMD_REGISTER_GLOBAL_EXPEDITED.
Les commandes "expedited" (accélérées) se terminent plus rapidement que les non-accélérées ; elles ne bloquent jamais, mais ont l'inconvénient de causer une surcharge supplémentaire.
MEMBARRIER_CMD_REGISTER_GLOBAL_EXPEDITED (depuis Linux 4.16)
Enregistrer l'intention du processus de recevoir les barrières mémoire MEMBARRIER_CMD_GLOBAL_EXPEDITED.
MEMBARRIER_CMD_PRIVATE_EXPEDITED (depuis Linux 4.14)
Exécuter une barrière mémoire sur chaque thread en cours d'exécution appartenant au même processus que le thread appelant.
Au retour de l'appel système, le thread appelant a la garantie que tous ses frères threads en cours d'exécution ont passé par un état où tous les accès mémoire aux adresses de l'espace utilisateur correspondent à l'ordre du programme entre l'entrée et le retour de l'appel système (les threads non en cours d'exécution sont de facto dans un tel état). Cette garantie n'est fournie que pour les threads du même processus que le thread appelant.
Les commandes "expedited" (accélérées) se terminent plus rapidement que les non-accélérées ; elles ne bloquent jamais, mais ont l'inconvénient de causer une surcharge supplémentaire.
Un processus doit enregistrer son intention d'utiliser la commande privée accélérée avant de l'utiliser.
MEMBARRIER_CMD_REGISTER_PRIVATE_EXPEDITED (depuis Linux 4.14)
Enregistrer l'intention du processus d'utiliser MEMBARRIER_CMD_PRIVATE_EXPEDITED.
MEMBARRIER_CMD_PRIVATE_EXPEDITED_SYNC_CORE (depuis Linux 4.16)
En plus de fournir les garanties d'ordonnancement mémoire décrites dans MEMBARRIER_CMD_PRIVATE_EXPEDITED, au retour de l'appel système, le thread appelant a la garantie que tous ses frères threads en cours d'exécution ont exécuté une instruction de sérialisation de cœur. Cette garantie n'est fournie que pour les threads du même processus que le thread appelant.
Les commandes "expedited" (accélérées) se terminent plus rapidement que les non-accélérées, elles ne bloquent jamais, mais ont l'inconvénient de causer une surcharge supplémentaire.
Un processus doit enregistrer son intention d'utiliser la commande privée accélérée de synchronisation de cœur avant de l'utiliser.
MEMBARRIER_CMD_REGISTER_PRIVATE_EXPEDITED_SYNC_CORE (depuis Linux 4.16)
Enregistrer l'intention du processus d'utiliser MEMBARRIER_CMD_PRIVATE_EXPEDITED_SYNC_CORE.
MEMBARRIER_CMD_PRIVATE_EXPEDITED_RSEQ (depuis Linux 5.10)
S'assurer que le thread appelant, au retour de l'appel système, que tous ses frères threads en cours d'exécution ont leurs sections critiques rseq en cours d'exécution redémarrées si le paramètre flags est 0 ; si le paramètre flags est MEMBARRIER_CMD_FLAG_CPU, alors cette opération est effectuée uniquement sur le CPU indiqué par cpu_id. Cette garantie n'est fournie que pour les threads du même processus que le thread appelant.
La barrière mémoire RSEQ n'est disponible que sous la forme "privée accélérée".
Un processus doit enregistrer son intention d'utiliser la commande privée accélérée rseq avant de l'utiliser.
MEMBARRIER_CMD_REGISTER_PRIVATE_EXPEDITED_RSEQ (depuis Linux 5.10)
Enregistrer l'intention du processus d'utiliser MEMBARRIER_CMD_PRIVATE_EXPEDITED_RSEQ.
MEMBARRIER_CMD_SHARED (depuis Linux 4.3)
Ceci est un alias pour MEMBARRIER_CMD_GLOBAL qui existe pour la compatibilité ascendante des en-têtes.

L'argument flags doit être spécifié comme 0 sauf si la commande est MEMBARRIER_CMD_PRIVATE_EXPEDITED_RSEQ, auquel cas flags peut être 0 ou MEMBARRIER_CMD_FLAG_CPU.

Le paramètre cpu_id ne doit être utilisé qu'avec la commande MEMBARRIER_CMD_PRIVATE_EXPEDITED_RSEQ et lorsque flags vaut MEMBARRIER_CMD_FLAG_CPU. Il spécifie le CPU sur lequel l'opération de redémarrage de la section critique rseq doit être effectuée.

Si une commande n'est pas supportée par le noyau, l'appel système échoue avec l'erreur ENOSYS.

VALEUR DE RETOUR

En cas de succès, membarrier() retourne 0. En cas d'échec, il retourne -1 et errno est défini pour indiquer l'erreur.

ERREURS

EACCES
Une tentative a été faite pour utiliser une commande qui nécessite l'enregistrement préalable (par exemple, MEMBARRIER_CMD_PRIVATE_EXPEDITED) sans que le processus ne se soit enregistré.
EINVAL
Une valeur invalide a été spécifiée pour cmd ou flags.
ENOSYS
La commande spécifiée n'est pas supportée par le noyau.
EOPNOTSUPP
(Depuis Linux 4.16) La commande spécifiée n'est pas supportée par le noyau.

NOTES

La première version de l'appel système, introduite dans Linux 4.3, ne prenait en charge que les commandes MEMBARRIER_CMD_QUERY et MEMBARRIER_CMD_SHARED (qui est un alias pour MEMBARRIER_CMD_GLOBAL). Les autres commandes ont été ajoutées dans des versions ultérieures du noyau.

L'utilisation de cet appel système est complexe et doit être faite avec précaution. Il est conçu pour des scénarios spécifiques où l'on peut optimiser les barrières mémoire en les remplaçant par des appels système dans les chemins de code les moins fréquents.

Les commandes qui nécessitent un enregistrement préalable (par exemple, MEMBARRIER_CMD_PRIVATE_EXPEDITED) utilisent un mécanisme de enregistrement au niveau du processus. L'enregistrement se fait en appelant membarrier() avec la commande d'enregistrement appropriée. Une fois enregistré, le processus peut utiliser la commande correspondante.

La garantie fournie par ces barrières est que les accès mémoire effectués avant l'appel système par les threads concernés seront visibles par les autres threads concernés après le retour de l'appel système, et ce, dans l'ordre du programme.

EXEMPLES

Voici un exemple simple d'utilisation de MEMBARRIER_CMD_REGISTER_PRIVATE_EXPEDITED et MEMBARRIER_CMD_PRIVATE_EXPEDITED dans un programme multi-threadé.

Supposons un scénario où un thread principal écrit des données et plusieurs threads travailleurs les lisent.

#include <stdio.h>
#include <stdlib.h>
#include <pthread.h>
#include <unistd.h>
#include <sys/syscall.h>
#include <linux/membarrier.h>

/* Fonction pour effectuer l'appel système membarrier */
int do_membarrier(int cmd, unsigned int flags, int cpu_id) {
    return syscall(SYS_membarrier, cmd, flags, cpu_id);
}

/* Données partagées */
int shared_data = 0;
int data_ready = 0;

/* Thread travailleur */
void *worker_thread(void *arg) {
    // Vérifie si les données sont prêtes
    while (!data_ready) {
        // Utilise une barrière compiler pour ne pas optimiser la boucle
        asm volatile("" ::: "memory");
    }

    // En supposant que les données sont maintenant prêtes,
    // nous voulons être sûrs de les lire correctement ordonnancées.
    // Dans un scénario réel, on pourrait utiliser MEMBARRIER_CMD_PRIVATE_EXPEDITED ici.
    // Pour cet exemple simplifié, nous supposons que la boucle while a déjà fait le travail.

    printf("Thread travailleur: shared_data = %d\n", shared_data);
    return NULL;
}

int main() {
    pthread_t tid;

    // Enregistrer l'intention d'utiliser MEMBARRIER_CMD_PRIVATE_EXPEDITED
    if (do_membarrier(MEMBARRIER_CMD_REGISTER_PRIVATE_EXPEDITED, 0, 0) == -1) {
        perror("membarrier(REGISTER_PRIVATE_EXPEDITED) failed");
        // Continuer quand même pour l'exemple, mais gérer l'erreur en production
    } else {
        printf("Enregistrement pour MEMBARRIER_CMD_PRIVATE_EXPEDITED réussi.\n");
    }

    // Créer un thread travailleur
    if (pthread_create(&tid, NULL, worker_thread, NULL) != 0) {
        perror("pthread_create");
        return 1;
    }

    // Simuler un travail
    sleep(1);

    // Préparer les données
    shared_data = 42;

    // Émettre une barrière pour s'assurer que les autres threads voient la modification
    // Ceci est le cas d'utilisation où le thread principal est le "côté lent"
    printf("Thread principal: Émission de MEMBARRIER_CMD_PRIVATE_EXPEDITED...\n");
    if (do_membarrier(MEMBARRIER_CMD_PRIVATE_EXPEDITED, 0, 0) == -1) {
        perror("membarrier(PRIVATE_EXPEDITED) failed");
        // Gérer l'erreur
    } else {
        printf("Barrière MEMBARRIER_CMD_PRIVATE_EXPEDITED émise avec succès.\n");
    }

    // Marquer les données comme prêtes
    data_ready = 1;

    // Attendre la fin du thread travailleur
    pthread_join(tid, NULL);

    printf("Programme terminé.\n");
    return 0;
}

Pour compiler et exécuter cet exemple (nécessite un noyau Linux version 4.14 ou ultérieure) :

$ gcc -o membarrier_example membarrier_example.c -pthread
$ ./membarrier_example

membarrier(2) — Arch manual pages

NAME

membarrier - issue memory-barrier commands to control memory reordering

LIBRARY

libc, -lc

SYNOPSIS

#include <linux/membarrier.h>

long membarrier(int cmd, int flags, int cpu_id);

DESCRIPTION

The membarrier() system call provides a mechanism to control memory reordering guarantees.

The behavior of membarrier() is determined by the cmd argument, which specifies the command to be executed. The possible values for cmd are defined in <linux/membarrier.h>.

MEMBARRIER_CMD_QUERY
Return a bit mask of supported commands. This command must be supported by all kernels that implement membarrier().
MEMBARRIER_CMD_GLOBAL
This command establishes a global memory barrier. All memory accesses that occur in program order before this call are guaranteed to be completed before any memory accesses that occur in program order after this call, across all threads in the calling process. The flags argument must be zero.
MEMBARRIER_CMD_GLOBAL_EXPEDITED
Similar to MEMBARRIER_CMD_GLOBAL, but potentially faster. It guarantees that all memory accesses that occur in program order before this call are completed before any memory accesses that occur in program order after this call, for all threads in the calling process. The flags argument must be zero.
MEMBARRIER_CMD_REGISTER_GLOBAL_EXPEDITED
Register the calling thread for expedited global memory barrier notifications. After this call, subsequent expedited global memory barriers will ensure that all prior memory accesses by the calling thread are completed before any subsequent memory accesses by the calling thread. The flags argument must be zero.
MEMBARRIER_CMD_PRIVATE
This command establishes a private memory barrier for the calling thread. All memory accesses that occur in program order before this call are guaranteed to be completed before any memory accesses that occur in program order after this call, for the calling thread only. The flags argument must be zero.
MEMBARRIER_CMD_PRIVATE_EXPEDITED
Similar to MEMBARRIER_CMD_PRIVATE, but potentially faster. It guarantees that all memory accesses that occur in program order before this call are completed before any memory accesses that occur in program order after this call, for the calling thread only. The flags argument must be zero.
MEMBARRIER_CMD_REGISTER_PRIVATE_EXPEDITED
Register the calling thread for expedited private memory barrier notifications. After this call, subsequent expedited private memory barriers will ensure that all prior memory accesses by the calling thread are completed before any subsequent memory accesses by the calling thread. The flags argument must be zero.
MEMBARRIER_CMD_PRIVATE_SYNC_CORE
This command establishes a private memory barrier that also synchronizes with the core. This ensures that all memory accesses are visible to other cores. The flags argument must be zero.
MEMBARRIER_CMD_REGISTER_PRIVATE_SYNC_CORE
Register the calling thread for expedited private memory barrier notifications with core synchronization. The flags argument must be zero.
MEMBARRIER_CMD_PRIVATE_EXPEDITED_SYNC_CORE
This command establishes a private expedited memory barrier that also synchronizes with the core. The flags argument must be zero.
MEMBARRIER_CMD_REGISTER_PRIVATE_EXPEDITED_SYNC_CORE
Register the calling thread for expedited private memory barrier notifications with core synchronization. The flags argument must be zero.

The flags argument can be used to modify the behavior of certain commands. Currently, the only defined flag is:

MEMBARRIER_CMD_FLAG_CPU
If this flag is set in flags, the command is targeted at a specific CPU. The cpu_id argument must specify the CPU ID. Otherwise, cpu_id is ignored.

The cpu_id argument is ignored unless flags is MEMBARRIER_CMD_FLAG_CPU, in which case it must specify the CPU targeted by this membarrier command.

All memory accesses performed in program order from each targeted thread are guaranteed to be ordered with respect to membarrier().

If we use the semantic barrier() to represent a compiler barrier forcing memory accesses to be performed in program order across the barrier, and smp_mb() to represent explicit memory barriers forcing full memory ordering across the barrier, we have the following ordering table for each pairing of barrier(), membarrier(), and smp_mb(). The pair ordering is detailed as (O: ordered, X: not ordered):

barrier() smp_mb() membarrier()
barrier() X X O
smp_mb() X O O
membarrier() O O O

RETURN VALUE

On success, the MEMBARRIER_CMD_QUERY operation returns a bit mask of supported commands, and the MEMBARRIER_CMD_GLOBAL, MEMBARRIER_CMD_GLOBAL_EXPEDITED, MEMBARRIER_CMD_REGISTER_GLOBAL_EXPEDITED, MEMBARRIER_CMD_PRIVATE_EXPEDITED, MEMBARRIER_CMD_REGISTER_PRIVATE_EXPEDITED, MEMBARRIER_CMD_PRIVATE_EXPEDITED_SYNC_CORE, and MEMBARRIER_CMD_REGISTER_PRIVATE_EXPEDITED_SYNC_CORE operations return zero. On error, -1 is returned, and errno is set to indicate the error.

For a given command, with flags set to 0, this system call is guaranteed to always return the same value until reboot. Further calls with the same arguments will lead to the same result. Therefore, with flags set to 0, error handling is required only for the first call to membarrier().

ERRORS

EINVAL
cmd is invalid, or flags is nonzero, or the MEMBARRIER_CMD_GLOBAL command is disabled because the nohz_full CPU parameter has been set, or the MEMBARRIER_CMD_PRIVATE_EXPEDITED_SYNC_CORE and MEMBARRIER_CMD_REGISTER_PRIVATE_EXPEDITED_SYNC_CORE commands are not implemented by the architecture.
ENOSYS
The membarrier() system call is not implemented by this kernel.
EPERM
The current process was not registered prior to using private expedited commands.

STANDARDS

Linux.

HISTORY

Linux 4.3.

Before Linux 5.10, the prototype was:


int membarrier(int cmd, int flags);

NOTES

A memory barrier instruction is part of the instruction set of architectures with weakly ordered memory models. It orders memory accesses prior to the barrier and after the barrier with respect to matching barriers on other cores. For instance, a load fence can order loads prior to and following that fence with respect to stores ordered by store fences.

Program order is the order in which instructions are ordered in the program assembly code.

Examples where membarrier() can be useful include implementations of Read-Copy-Update libraries and garbage collectors.

EXAMPLES

Assuming a multithreaded application where "fast_path()" is executed very frequently, and where "slow_path()" is executed infrequently, the following code (x86) can be transformed using membarrier():


#include <stdlib.h>
static volatile int a, b;
static void
fast_path(int *read_b)
{
    a = 1;
    asm volatile ("mfence" : : : "memory");
    *read_b = b;
}
static void
slow_path(int *read_a)
{
    b = 1;
    asm volatile ("mfence" : : : "memory");
    *read_a = a;
}
int
main(void)
{
    int read_a, read_b;
    /*
     * Real applications would call fast_path() and slow_path()
     * from different threads.  Call those from main() to keep
     * this example short.
     */
    slow_path(&read_a);
    fast_path(&read_b);
    /*
     * read_b == 0 implies read_a == 1 and
     * read_a == 0 implies read_b == 1.
     */
    if (read_b == 0 && read_a == 0)
        abort();
    exit(EXIT_SUCCESS);
}

The code above transformed to use membarrier() becomes:


#define _GNU_SOURCE
#include <stdlib.h>
#include <stdio.h>
#include <unistd.h>
#include <sys/syscall.h>
#include <linux/membarrier.h>
static volatile int a, b;
static int
membarrier(int cmd, unsigned int flags, int cpu_id)
{
    return syscall(__NR_membarrier, cmd, flags, cpu_id);
}
static int
init_membarrier(void)
{
    int ret;
    /* Check that membarrier() is supported.  */
    ret = membarrier(MEMBARRIER_CMD_QUERY, 0, 0);
    if (ret < 0) {
        perror("membarrier");
        return -1;
    }
    if (!(ret & MEMBARRIER_CMD_GLOBAL)) {
        fprintf(stderr,
            "membarrier does not support MEMBARRIER_CMD_GLOBAL\n");
        return -1;
    }
    return 0;
}
static void
fast_path(int *read_b)
{
    a = 1;
    asm volatile ("" : : : "memory");
    *read_b = b;
}
static void
slow_path(int *read_a)
{
    b = 1;
    membarrier(MEMBARRIER_CMD_GLOBAL, 0, 0);
    *read_a = a;
}
int
main(int argc, char *argv[])
{
    int read_a, read_b;
    if (init_membarrier())
        exit(EXIT_FAILURE);
    /*
     * Real applications would call fast_path() and slow_path()
     * from different threads.  Call those from main() to keep
     * this example short.
     */
    slow_path(&read_a);
    fast_path(&read_b);
    /*
     * read_b == 0 implies read_a == 1 and
     * read_a == 0 implies read_b == 1.
     */
    if (read_b == 0 && read_a == 0)
        abort();
    exit(EXIT_SUCCESS);
}
