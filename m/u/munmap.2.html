mmap(2) Manuel des appels système mmap(2)

NOM

mmap, munmap - mapper ou démapper des fichiers ou des périphériques en mémoire

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNOPSIS

#include <sys/mman.h>
void *mmap(size_t length;
           void addr[length], size_t length, int prot, int flags,
           int fd, off_t offset);
int munmap(size_t length;
           void addr[length], size_t length);

Voir VERSIONS pour des informations sur les exigences des macros de test de fonctionnalités.

DESCRIPTION

mmap() crée un nouveau mappage dans l'espace d'adressage virtuel du processus appelant. L'adresse de départ du nouveau mappage est spécifiée dans addr. L'argument length spécifie la longueur du mappage (qui doit être supérieur à 0).

Si addr est NULL, le noyau choisit l'adresse (alignée sur une page) à laquelle créer le mappage ; c'est la méthode la plus portable pour créer un nouveau mappage. Si addr n'est pas NULL, le noyau l'utilise comme une indication où placer le mappage ; sous Linux, le noyau choisit une frontière de page proche (mais toujours supérieure ou égale à la valeur spécifiée par /proc/sys/vm/mmap_min_addr) et tente de créer le mappage là. Si un autre mappage existe déjà à cet endroit, le noyau choisit une nouvelle adresse qui peut dépendre ou non de l'indication. L'adresse du nouveau mappage est retournée comme résultat de l'appel.

Le contenu d'un mappage de fichier (par opposition à un mappage anonyme ; voir MAP_ANONYMOUS ci-dessous) est initialisé en utilisant length octets à partir de l'offset offset dans le fichier (ou un autre objet) référencé par le descripteur de fichier fd. offset doit être un multiple de la taille de page retournée par sysconf(_SC_PAGE_SIZE).

Après le retour de l'appel mmap(), le descripteur de fichier, fd, peut être fermé immédiatement sans invalider le mappage.

L'argument prot décrit la protection mémoire souhaitée du mappage (et ne doit pas entrer en conflit avec le mode d'ouverture du fichier). Il s'agit soit de PROT_NONE, soit du OU bit à bit d'une ou plusieurs des options suivantes :

PROT_EXEC
Les pages peuvent être exécutées.
PROT_READ
Les pages peuvent être lues.
PROT_WRITE
Les pages peuvent être écrites.
PROT_NONE
Les pages ne peuvent pas être accédées.

L'argument flags

L'argument flags détermine si les mises à jour du mappage sont visibles par d'autres processus mappant la même région, et si les mises à jour sont répercutées dans le fichier sous-jacent. Ce comportement est déterminé en incluant exactement une des valeurs suivantes dans flags :

MAP_SHARED
Partager ce mappage. Les mises à jour du mappage sont visibles par d'autres processus mappant la même région et (dans le cas des mappages liés à un fichier) sont répercutées dans le fichier sous-jacent. (Pour contrôler précisément quand les mises à jour sont répercutées dans le fichier sous-jacent, il faut utiliser msync(2).)
MAP_SHARED_VALIDATE (depuis Linux 4.15)
Ce drapeau fournit le même comportement que MAP_SHARED sauf que les mappages MAP_SHARED ignorent les drapeaux inconnus dans flags. Par contraste, lors de la création d'un mappage utilisant MAP_SHARED_VALIDATE, le noyau vérifie que tous les drapeaux passés sont connus et échoue le mappage avec l'erreur EOPNOTSUPP pour les drapeaux inconnus. Ce type de mappage est également requis pour pouvoir utiliser certains drapeaux de mappage (par exemple, MAP_SYNC).
MAP_PRIVATE
Créer un mappage privé en copie sur écriture. Les mises à jour du mappage ne sont pas visibles par d'autres processus mappant le même fichier et ne sont pas répercutées dans le fichier sous-jacent. Il n'est pas spécifié si les changements apportés au fichier après l'appel mmap() sont visibles dans la région mappée.

MAP_SHARED et MAP_PRIVATE sont décrits dans POSIX.1-2001 et POSIX.1-2008. MAP_SHARED_VALIDATE est une extension Linux.

En outre, zéro ou plusieurs des valeurs suivantes peuvent être combinées par OU bit à bit dans flags :

MAP_32BIT (depuis Linux 2.4.20, 2.6)
Placer le mappage dans les 2 premiers Gigaoctets de l'espace d'adressage du processus. Ce drapeau n'est pris en charge que sur x86-64, pour les programmes 64 bits. Il a été ajouté pour permettre aux piles de threads d'être allouées quelque part dans les 2 premiers Go de mémoire, afin d'améliorer les performances des changements de contexte sur certains processeurs 64 bits anciens. Les processeurs x86-64 modernes n'ont plus ce problème de performance, donc l'utilisation de ce drapeau n'est pas nécessaire sur ces systèmes. Le drapeau MAP_32BIT est ignoré lorsque MAP_FIXED est défini.
MAP_ANON
Équivalent de MAP_ANONYMOUS ; fourni pour la compatibilité avec d'autres implémentations.
MAP_ANONYMOUS
Le mappage n'est soutenu par aucun fichier ; son contenu est initialisé à zéro. L'argument fd est ignoré ; cependant, certaines implémentations exigent que fd soit -1 si MAP_ANONYMOUS (ou MAP_ANON) est spécifié, et les applications portables doivent s'en assurer. L'argument offset doit être zéro. La prise en charge de MAP_ANONYMOUS en conjonction avec MAP_SHARED a été ajoutée dans Linux 2.4.
MAP_DENYWRITE
Ce drapeau est ignoré. (Il y a longtemps — Linux 2.0 et antérieur — il signalait que les tentatives d'écriture dans le fichier sous-jacent devaient échouer avec ETXTBSY. Mais c'était une source d'attaques par déni de service.)
MAP_EXECUTABLE
Ce drapeau est ignoré.
MAP_FILE
Drapeau de compatibilité. Ignoré.
MAP_FIXED
N'interprète pas addr comme une indication : place le mappage exactement à cette adresse. addr doit être correctement aligné : pour la plupart des architectures, un multiple de la taille de page est suffisant ; cependant, certaines architectures peuvent imposer des restrictions supplémentaires. Si la région mémoire spécifiée par addr et length chevauche des pages d'un ou plusieurs mappages existants, la partie chevauchée des mappages existants sera supprimée. Si l'adresse spécifiée ne peut pas être utilisée, mmap() échouera.
Les logiciels qui aspirent à être portables doivent utiliser le drapeau MAP_FIXED avec prudence, en gardant à l'esprit que la disposition exacte des mappages mémoire d'un processus est autorisée à changer significativement entre les versions de Linux, les versions de la bibliothèque C et les versions des systèmes d'exploitation. Lisez attentivement la discussion de ce drapeau dans NOTES !
MAP_FIXED_NOREPLACE (depuis Linux 4.17)
Ce drapeau offre un comportement similaire à MAP_FIXED concernant la contrainte sur addr, mais diffère en ce que MAP_FIXED_NOREPLACE ne supprime jamais une plage mappée préexistante. Si la plage demandée entre en collision avec un mappage existant, alors cet appel échoue avec l'erreur EEXIST. Ce drapeau peut donc être utilisé comme moyen de tenter atomiquement (par rapport aux autres threads) de mapper une plage d'adresses : un thread réussira ; tous les autres signaleront un échec.
Notez que les anciens noyaux qui ne reconnaissent pas le drapeau MAP_FIXED_NOREPLACE retomberont généralement (lorsqu'ils détectent une collision avec un mappage préexistant) vers un comportement de type « non-MAP_FIXED » : ils retourneront une adresse différente de l'adresse demandée. Par conséquent, les logiciels compatibles avec les versions antérieures devraient vérifier l'adresse retournée par rapport à l'adresse demandée.

DESCRIPTION

The mmap() system call creates a new mapping or modifies an existing mapping, or so the man page says. It returns the thread's prototypical virtual memory address space, or a pointer to the mapped area. This address is returned by the call, and has the property that the memory region starting at this address and of size length bytes is mapped.

The contents of the memory mapped region are those of the file described by the file descriptor fd, starting at offset offset and of size length bytes. The file offset offset must be a multiple of the page size.

If the length is 0, then the call may be a no-op, or it may establish a mapping that is up to sysconf(_SC_PAGESIZE) bytes long. If the length is 0, then the address returned shall be one that can subsequently be used in a `munmap()' call to unmap the mapping.

A file is a sequence of bytes. A mapping is a range of the file's bytes. Mappings are described by the kernel's virtual address space.

The flags argument determines whether updates to the mapped region are visible to other processes mapping the same file and whether they are carried through to the underlying memory. The flags argument can be an OR of the following:

MAP_32BIT (since Linux 2.6.16)
Provide a mapping in the lower 2GB of the address space. This is only useful on 64-bit systems, where it can help avoid issues related to untrusted code executing in the higher, unmapped regions of the address space.
MAP_ANOMYMOUS, MAP_ANON
The mapping is not backed by any file. The contents of the mapping are initialised to zero. The fd and offset arguments are ignored. This flag is used to create private copies of file mappings, or just to allocate memory. If MAP_ANOMYMOUS is used, the file descriptor fd must be -1.
MAP_FIXED
Do not use a free page. The mapping is created at exactly the address specified in addr. The addr argument must be a multiple of the page size. If the specified memory region overlaps existing mappings, then the existing mappings are discarded. Whether discarded mappings are freed is unspecified. If MAP_FIXED is set, then addr must be a valid address in the process's virtual address space, and addr plus length must not overflow the virtual address space. The call to mmap() fails if addr or any part of the specified memory region fall out of the range of permitted addresses.
MAP_FIXED_NOREPLACE (since Linux 2.6.18)
This flag is similar to MAP_FIXED, but if the specified memory range addr/length conflicts with an existing mapping, the call to mmap() fails with the error EEXIST, and no unmapping is performed. This flag is intended to be used to implement the MAP_ANONYMOUS mapping atomically.
MAP_GROWSDOWN
This flag is used for stacks. It indicates to the kernel virtual memory system that the mapping should extend downward in memory. The return address is one page lower than the memory area that is actually created in the process's virtual address space. Touching an address in the "guard" page below the mapping will cause the mapping to grow by a page. This growth can be repeated until the mapping grows to within a page of the high end of the next lower mapping, at which point touching the "guard" page will result in a SIGSEGV signal.
MAP_HUGETLB (since Linux 2.6.32)
Allocate the mapping using "huge" pages. See the Linux kernel source file Documentation/admin-guide/mm/hugetlbpage.rst for further information, as well as NOTES, below.
MAP_HUGE_2MB
MAP_HUGE_1GB (since Linux 3.8)
Used in conjunction with MAP_HUGETLB to select alternative hugetlb page sizes (respectively, 2 MB and 1 GB) on systems that support multiple hugetlb page sizes.
More generally, the desired huge page size can be configured by encoding the base-2 logarithm of the desired page size in the six bits at the offset MAP_HUGE_SHIFT. (A value of zero in this bit field provides the default huge page size; the default huge page size can be discovered via the Hugepagesize field exposed by /proc/meminfo.) Thus, the above two constants are defined as:

#define MAP_HUGE_2MB    (21 << MAP_HUGE_SHIFT)
#define MAP_HUGE_1GB    (30 << MAP_HUGE_SHIFT)

The range of huge page sizes that are supported by the system can be discovered by listing the subdirectories in /sys/kernel/mm/hugepages.
MAP_LOCKED (since Linux 2.5.37)
Mark the mapped region to be locked in the same way as mlock(2). This implementation will try to populate (prefault) the whole range but the mmap() call doesn't fail with ENOMEM if this fails. Therefore major faults might happen later on. So the semantic is not as strong as mlock(2). One should use mmap() plus mlock(2) when major faults are not acceptable after the initialization of the mapping. The MAP_LOCKED flag is ignored in older kernels.
MAP_NONBLOCK (since Linux 2.5.46)
This flag is meaningful only in conjunction with MAP_POPULATE. Don't perform read-ahead: create page tables entries only for pages that are already present in RAM. Since Linux 2.6.23, this flag causes MAP_POPULATE to do nothing. One day, the combination of MAP_POPULATE and MAP_NONBLOCK may be reimplemented.
MAP_NORESERVE
Do not reserve swap space for this mapping. When swap space is reserved, one has the guarantee that it is possible to modify the mapping. When swap space is not reserved one might get SIGSEGV upon a write if no physical memory is available. See also the discussion of the file /proc/sys/vm/overcommit_memory in proc_sys_vm(5). Before Linux 2.6, this flag had effect only for private writable mappings.
MAP_POPULATE (since Linux 2.5.46)
Populate (prefault) page tables for a mapping. For a file mapping, this causes read-ahead on the file. This will help to reduce blocking on page faults later. The mmap() call doesn't fail if the mapping cannot be populated (for example, due to limitations on the number of mapped huge pages when using MAP_HUGETLB). Support for MAP_POPULATE in conjunction with private mappings was added in Linux 2.6.23.
MAP_STACK (since Linux 2.6.27)
Allocate the mapping at an address suitable for a process or thread stack.
This flag is currently a no-op on Linux. However, by employing this flag, applications can ensure that they transparently obtain support if the flag is implemented in the future. Thus, it is used in the glibc threading implementation to allow for the fact that some architectures may (later) require special treatment for stack allocations. A further reason to employ this flag is portability: MAP_STACK exists (and has an effect) on some other systems (e.g., some of the BSDs).
MAP_SYNC (since Linux 4.15)
This flag is available only with the MAP_SHARED_VALIDATE mapping type; mappings of type MAP_SHARED will silently ignore this flag. This flag is supported only for files supporting DAX (direct mapping of persistent memory). For other files, creating a mapping with this flag results in an EOPNOTSUPP error.
Shared file mappings with this flag provide the guarantee that while some memory is mapped writable in the address space of the process, it will be visible in the same file at the same offset even after the system crashes or is rebooted. In conjunction with the use of appropriate CPU instructions, this provides users of such mappings with a more efficient way of making data modifications persistent.
MAP_UNINITIALIZED (since Linux 2.6.33)
Don't clear anonymous pages. This flag is intended to improve performance on embedded devices. This flag is honored only if the kernel was configured with the CONFIG_MMAP_ALLOW_UNINITIALIZED option. Because of the security implications, that option is normally enabled only on embedded devices (i.e., devices where one has complete control of the contents of user memory).

Of the above flags, only MAP_FIXED is specified in POSIX.1-2001 and POSIX.1-2008. However, most systems also support MAP_ANONYMOUS (or its synonym MAP_ANON).

munmap()

The munmap() system call deletes the mappings for the specified address range, and causes further references to addresses within the range to generate invalid memory references. The region is also automatically unmapped when the process is terminated. On the other hand, closing the file descriptor does not unmap the region.

The address addr must be a multiple of the page size (but length need not be). All pages containing a part of the indicated range are unmapped, and subsequent references to these pages will generate SIGSEGV. It is not an error if the indicated range does not contain any mapped pages.

RETURN VALUE

On success, mmap() returns a pointer to the mapped area. On error, the value MAP_FAILED (that is, (void *) -1) is returned, and errno is set to indicate the error.

On success, munmap() returns 0. On failure, it returns -1, and errno is set to indicate the error (probably to EINVAL).

ERRORS

EACCES
A file descriptor refers to a non-regular file. Or a file mapping was requested, but fd is not open for reading. Or MAP_SHARED was requested and PROT_WRITE is set, but fd is not open in read/write (O_RDWR) mode. Or PROT_WRITE is set, but the file is append-only.
EAGAIN
The file has been locked, or too much memory has been locked (see setrlimit(2)).
EBADF
fd is not a valid file descriptor (and MAP_ANOMYMOUS was not set).
EEXIST
MAP_FIXED_NOREPLACE was specified in flags, and the range covered by addr and length clashes with an existing mapping.
EINVAL
We don't like addr, length, or offset (e.g., they are too large, or not aligned on a page boundary).
EINVAL

EINVAL

ENFILE

ENODEV

ENOMEM

ENOMEM

VERSIONS

Sur certaines architectures matérielles (par exemple, i386), PROT_WRITE implique PROT_READ. Il est dépendant de l'architecture que PROT_READ implique ou non PROT_EXEC. Les programmes portables doivent toujours définir PROT_EXEC s'ils ont l'intention d'exécuter du code dans le nouveau mapping.

La manière portable de créer un mapping est de spécifier addr comme 0 (NULL) et d'omettre MAP_FIXED dans flags. Dans ce cas, le système choisit l'adresse pour le mapping ; l'adresse est choisie de manière à ne pas entrer en conflit avec tout mapping existant, et ne sera pas 0. Si le drapeau MAP_FIXED est spécifié et que addr est 0 (NULL), alors l'adresse mappée sera 0 (NULL).

Certaines constantes flags ne sont définies que si des macros de test de fonctionnalité appropriées sont définies (éventuellement par défaut) : _DEFAULT_SOURCE avec glibc 2.19 ou plus récent ; ou _BSD_SOURCE ou _SVID_SOURCE dans glibc 2.19 et versions antérieures. (L'utilisation de _GNU_SOURCE suffit également, et exiger ce macro spécifiquement aurait été plus logique, puisque ces drapeaux sont tous spécifiques à Linux.) Les drapeaux pertinents sont : MAP_32BIT, MAP_ANONYMOUS (et le synonyme MAP_ANON), MAP_DENYWRITE, MAP_EXECUTABLE, MAP_FILE, MAP_GROWSDOWN, MAP_HUGETLB, MAP_LOCKED, MAP_NONBLOCK, MAP_NORESERVE, MAP_POPULATE, et MAP_STACK.

Différences bibliothèque C/noyau

Cette page décrit l'interface fournie par la fonction d'encapsulation mmap() de glibc. Initialement, cette fonction appelait un appel système du même nom. NOTES

La mémoire mappée par mmap() est conservée lors de fork(2), avec les mêmes attributs.

Un fichier est mappé par multiples de la taille de page. Pour un fichier qui n'est pas un multiple de la taille de page, les octets restants dans la page partielle à la fin du mapping sont remplis de zéros lors du mappage, et les modifications apportées à cette région ne sont pas écrites dans le fichier. L'effet de la modification de la taille du fichier sous-jacent d'un mapping sur les pages correspondant aux régions ajoutées ou supprimées du fichier est indéfini.

Une application peut déterminer quelles pages d'un mapping sont actuellement résidentes dans le cache de tampons/pages en utilisant mincore(2).

Utilisation sûre de MAP_FIXED

La seule utilisation sûre pour MAP_FIXED est lorsque la plage d'adresses spécifiée par addr et length a été précédemment réservée à l'aide d'un autre mapping ; sinon, l'utilisation de MAP_FIXED est dangereuse car elle supprime de force les mappings préexistants, ce qui permet à un processus multithread de corrompre facilement son propre espace d'adressage.

Par exemple, supposons que le thread A examine /proc/pid/maps afin de localiser une plage d'adresses inutilisée qu'il peut mapper en utilisant MAP_FIXED, tandis que le thread B acquiert simultanément une partie ou la totalité de cette même plage d'adresses. Lorsque le thread A utilise ensuite mmap(MAP_FIXED), il écrasera efficacement le mapping que le thread B a créé. Dans ce scénario, le thread B n'a pas besoin de créer un mapping directement ; simplement effectuer un appel de bibliothèque qui, en interne, utilise dlopen(3) pour charger une autre bibliothèque partagée, suffira. L'appel dlopen(3) mappera la bibliothèque dans l'espace d'adressage du processus. De plus, presque tout appel de bibliothèque peut être implémenté de manière à ajouter des mappings mémoire à l'espace d'adressage, soit avec cette technique, soit en allouant simplement de la mémoire. Les exemples incluent brk(2), malloc(3), pthread_create(3), et les bibliothèques PAM http://www.linux-pam.org.

Depuis Linux 4.17, un programme multithread peut utiliser le drapeau MAP_FIXED_NOREPLACE pour éviter le danger décrit ci-dessus lors de la tentative de création d'un mapping à une adresse fixe qui n'a pas été réservée par un mapping préexistant.

Changements des horodatages pour les mappings basés sur fichier

Pour les mappings basés sur fichier, le champ st_atime du fichier mappé peut être mis à jour à tout moment entre le mmap() et le démappage correspondant ; la première référence à une page mappée mettra à jour le champ s'il n'a pas déjà été fait.

Les champs st_ctime et st_mtime d'un fichier mappé avec PROT_WRITE et MAP_SHARED seront mis à jour après une écriture dans la région mappée, et avant un msync(2) ultérieur avec les drapeaux MS_SYNC ou MS_ASYNC, si un tel appel se produit.

Mappings de pages volumineuses (Huge TLB)

Pour les mappings qui utilisent des pages volumineuses, les exigences pour les arguments de mmap() et munmap() diffèrent quelque peu des exigences pour les mappings qui utilisent la taille de page système native.

Pour mmap(), offset doit être un multiple de la taille de page volumineuse sous-jacente. Le système aligne automatiquement length pour qu'il soit un multiple de la taille de page volumineuse sous-jacente.

Pour munmap(), addr et length doivent tous deux être un multiple de la taille de page volumineuse sous-jacente.

AVERTISSEMENTS

Contrairement aux implémentations typiques de malloc(3), mmap() n'empêche pas la création d'objets plus grands que PTRDIFF_MAX. Les objets plus grands que PTRDIFF_MAX ne fonctionnent que de manière limitée en C (en particulier, la soustraction de pointeurs produit un comportement indéfini si le résultat dépasse PTRDIFF_MAX). De plus, GCC suppose également qu'aucun objet n'est plus grand que PTRDIFF_MAX. PTRDIFF_MAX est généralement la moitié de la taille de l'espace d'adressage ; ainsi, pour les processus 32 bits, il s'agit généralement de 0x7fffffff (presque 2 Go).

BOGUES

Sous Linux, il n'y a aucune garantie comme celles suggérées ci-dessus concernant MAP_NORESERVE. Par défaut, tout processus peut être tué à tout moment lorsque le système manque de mémoire.

Avant Linux 2.6.7, le drapeau MAP_POPULATE n'avait d'effet que si prot était spécifié comme PROT_NONE.

SUSv3 spécifie que mmap() doit échouer si length est 0. Cependant, avant Linux 2.6.12, mmap() réussissait dans ce cas : aucun mapping n'était créé et l'appel retournait addr. Depuis Linux 2.6.12, mmap() échoue avec l'erreur EINVAL dans ce cas.

POSIX spécifie que le système doit toujours remplir de zéros toute page partielle à la fin de l'objet et que le système n'écrira jamais aucune modification de l'objet au-delà de sa fin. Sous Linux, lorsque vous écrivez des données dans une telle page partielle après la fin de l'objet, les données restent dans le cache de pages même après la fermeture et le démappage du fichier, et bien que les données ne soient jamais écrites dans le fichier lui-même, les mappings ultérieurs peuvent voir le contenu modifié. Dans certains cas, cela pourrait être corrigé en appelant msync(2) avant le démappage ; cependant, cela ne fonctionne pas sur tmpfs(5) (par exemple, lors de l'utilisation de l'interface de mémoire partagée POSIX documentée dans shm_overview(7)).

EXEMPLES

Le programme suivant affiche une partie du fichier spécifié dans son premier argument de ligne de commande sur la sortie standard. La plage d'octets à afficher est spécifiée via les valeurs d'offset et de longueur dans les deuxième et troisième arguments de ligne de commande. Le programme crée un mapping mémoire des pages requises du fichier, puis utilise write(2) pour afficher les octets souhaités.

Source du programme

#includ
e <err.h> #include <fcntl.h> #include <stdio.h> #include <stdlib.h> #include <sys/mman.h> #include <sys/stat.h> #include <sys/types.h> #include <unistd.h> int main(int argc, char *argv[]) { int fd; char *addr; off_t offset, pa_offset; size_t length; ssize_t s; struct stat sb; if (argc < 3 || argc > 4) { fprintf(stderr, "%s fichier decalage [longueur]\n", argv[0]); exit(EXIT_FAILURE); } fd = open(argv[1], O_RDONLY); if (fd == -1) err(EXIT_FAILURE, "open"); if (fstat(fd, &sb) == -1) /* Pour obtenir la taille du fichier */ err(EXIT_FAILURE, "fstat"); offset = atoi(argv[2]); pa_offset = offset & ~(sysconf(_SC_PAGE_SIZE) - 1); /* le decalage pour mmap() doit etre aligne sur la page */ if (offset >= sb.st_size) { fprintf(stderr, "le decalage est apres la fin du fichier\n"); exit(EXIT_FAILURE); } if (argc == 4) { length = atoi(argv[3]); if (offset + length > sb.st_size) length = sb.st_size - offset; /* Impossible d'afficher les octets apres la fin du fichier */ } else { /* Pas d'argument longueur ==> afficher jusqu'a la fin du fichier */ length = sb.st_size - offset; } addr = mmap(NULL, length + offset - pa_offset, PROT_READ, MAP_PRIVATE, fd, pa_offset); if (addr == MAP_FAILED) err(EXIT_FAILURE, "mmap"); s = write(STDOUT_FILENO, addr + offset - pa_offset, length); if (s != length) { if (s == -1) err(EXIT_FAILURE, "write"); fprintf(stderr, "ecriture partielle"); exit(EXIT_FAILURE); } munmap(addr, length + offset - pa_offset); close(fd); exit(EXIT_SUCCESS); }
