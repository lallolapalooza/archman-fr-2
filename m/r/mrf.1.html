NOM

MRF - monochrome recursive format (bitmaps compressés)

DESCRIPTION

Ce programme fait partie de Netpbm(1)

MRF est un format compressé pour les images de type bilevel (1 bit mono). Il atteint une meilleure compression pour certaines de ces images que GIF ou PNG. (Il est également très facile à implémenter (à peu près la même difficulté que RLE, je dirais) et un lecteur MRF n'a pas besoin de tables/buffers, ce qui peut le rendre utile pour les petites machines).

Au cas où ce qui précède ne l'aurait pas rendu suffisamment clair, je ferai le point suivant explicitement : MRF ne peut absolument pas représenter de couleur. Il ne peut pas non plus représenter de niveaux de gris. C'est spécifiquement un format mono. (Si vous voulez compresser une image couleur ou niveaux de gris, mon conseil est d'utiliser JPEG2000).

Tout d'abord, voici ce qui va où dans un fichier MRF. J'expliquerai ensuite comment fonctionne la compression.

Décalage
Description
0
nombre magique - 'MRF1' (en ASCII)
4
largeur (32 bits, MSB en premier (c'est-à-dire big-endian))
8
hauteur (identique)
12
réservé (un seul octet, doit être zéro)
13
données compressées

Notez qu'il n'y a pas de marqueur de fin de fichier dans le fichier lui-même - les données compressées se poursuivent jusqu'à la fin du fichier.

La façon dont l'image est compressée est essentiellement très simple, mais comme on dit, le diable est dans les détails. Ne vous laissez donc pas rebuter si cela semble confus.

L'image est traitée comme un certain nombre de carrés de 64x64, formant une grille suffisamment grande pour l'englober. (Si une image est (par exemple) 129x65, elle sera traitée de la même manière qu'une image de 192x128. Lors de la décompression, la zone supplémentaire qui a été encodée (le contenu de cette zone est indéfini) doit être ignorée.) Chacun de ces carrés tour à tour (dans l'ordre de gauche à droite, de haut en bas) est récursivement subdivisé jusqu'à ce que les plus petits carrés complètement noirs ou blancs soient trouvés. Un pseudocode (aïe !) pour la routine de subdivision récursive devrait clarifier les choses :

    si la taille du carré > 1x1 et que le carré est de couleur unique, afficher 1 bit
    si le carré entier est noir, afficher un bit 0 et retourner
    si le carré entier est blanc, afficher un bit 1 et retourner
    afficher un bit 0
    diviser le carré en quatre quarts, appeler la routine pour
    chacun dans cet ordre : haut-gauche, haut-droit, bas-gauche, bas-droit

(Notez que l'étape 'afficher un bit 0' n'est pas atteinte pour les carrés de taille 1x1, ce qui empêche la récursion infinie. Je mentionne cela car cela peut ne pas être immédiatement évident.)

L'ensemble des données compressées est constitué des bits produits par la routine ci-dessus. Les bits sont empaquetés en octets MSB en premier, donc par exemple, afficher les bits 1,0,0,0,0,0,0,0 produirait un octet 80h. Tous les bits `inutilisés' dans le dernier octet affiché sont indéfinis ; ils sont effectivement après la fin du fichier et leur valeur n'a pas d'importance.

Si écrire cela vous semble trop laborieux :-), vous pourriez toujours adapter pbmtomrf et/ou mrftopbm. C'est la raison principale pour laquelle leur code source est dans le domaine public, après tout.

Ci-dessus, j'ai dit que le contenu de toute zone supplémentaire encodée (lorsqu'une bitmap plus petite que la grille de carrés est compressée) est indéfini. Ceci est délibéré afin que le compresseur MRF puisse rendre ces zones invisibles à sa guise pour maximiser la compression, plutôt que de les laisser simplement vides. pbmtomrf fait un peu cela mais pourrait certainement être amélioré.

L'option -1 de mrftopbm lui fait inclure les bords, le cas échéant, dans le PBM de sortie. Cela peut aider lors du débogage de l'optimisation des bords d'un compresseur.

Notez que le "F" dans le nom "MRF" vient de "format", ce qui est redondant car c'est le nom d'un format. Cela fait ressembler "format MRF" à "numéro PIN", mais ce n'est pas si terrible.
