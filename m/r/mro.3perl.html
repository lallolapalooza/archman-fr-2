mro(3perl) Guide de référence des programmeurs Perl mro(3perl)

NOM

mro - Ordre de résolution des méthodes

SYNTAXE

use mro; # active next::method et similaires globalement
use mro 'dfs'; # active le MRO DFS pour cette classe (par défaut Perl)
use mro 'c3'; # active le MRO C3 pour cette classe

DESCRIPTION

L'espace de noms « mro » fournit plusieurs utilitaires pour traiter l'ordre de résolution des méthodes et la mise en cache des méthodes en général.

Ces interfaces ne sont disponibles qu'à partir de Perl 5.9.5. Voir MRO::Compat sur CPAN pour une implémentation principalement rétrocompatible pour les anciennes versions de Perl.

APERÇU

Il est possible de changer le MRO d'une classe donnée soit en utilisant "use mro" comme montré dans la syntaxe, soit en utilisant la fonction "mro::set_mro" ci-dessous.

Les méthodes spéciales "next::method", "next::can", et "maybe::next::method" ne sont pas disponibles tant que ce module "mro" n'a pas été chargé via "use" ou "require".

Le MRO C3

En plus du MRO traditionnel par défaut de Perl (recherche en profondeur, appelée "DFS" ici), Perl offre également le MRO C3. Le support de Perl pour C3 est basé sur le travail effectué dans le module Class::C3 de Stevan Little, et la plupart de la documentation C3 ici est tirée directement de ce dernier.

Qu'est-ce que C3 ?

C3 est le nom d'un algorithme qui vise à fournir un ordre de résolution des méthodes cohérent dans le cas d'héritage multiple. Il a été introduit pour la première fois dans le langage Dylan (voir les liens dans la section « VOIR AUSSI »), puis adopté comme MRO (Method Resolution Order) préféré pour les classes de nouveau style dans Python 2.3. Plus récemment, il a été adopté comme MRO « canonique » pour les classes Raku.

Comment fonctionne C3

C3 fonctionne en préservant toujours l'ordre de précédence local. Cela signifie essentiellement qu'aucune classe n'apparaîtra avant l'une de ses sous-classes. Prenons, par exemple, le schéma classique d'héritage en diamant :

   <A>
  /   \
<B>   <C>
  \   /
   <D>

Le MRO standard de Perl 5 serait (D, B, A, C). Le résultat étant que A apparaît avant C, même si C est une sous-classe de A. L'algorithme MRO C3, cependant, produit l'ordre suivant : (D, B, C, A), qui ne présente pas ce problème.

Cet exemple est assez trivial ; pour des cas plus complexes et une explication plus approfondie, voir les liens dans la section « VOIR AUSSI ».

Fonctions

mro::get_linear_isa($classname[, $type])

Retourne une référence de tableau qui est le MRO linéarisé de la classe donnée. Utilise le MRO actuellement en vigueur pour cette classe par défaut, ou le MRO donné (soit "c3", soit "dfs" si spécifié comme $type).

Le MRO linéarisé d'une classe est un tableau ordonné de toutes les classes que l'on rechercherait lors de la résolution d'une méthode sur cette classe, en commençant par la classe elle-même.

Si la classe demandée n'existe pas encore, cette fonction réussira quand même et retournera "[ $classname ]"

Notez que "UNIVERSAL" (et tous les membres du MRO de "UNIVERSAL") ne font pas partie du MRO d'une classe, même si toutes les classes héritent implicitement de méthodes de "UNIVERSAL" et de ses parents.

mro::set_mro ($classname, $type)

Définit le MRO de la classe donnée à l'argument $type (soit "c3", soit "dfs").

mro::get_mro($classname)

Retourne le MRO de la classe donnée (soit "c3", soit "dfs").

mro::get_isarev($classname)

Récupère le "mro_isarev" pour cette classe, retourné comme une référence de tableau de noms de classes. Ce sont toutes les classes qui « sont » la classe nommée donnée, même si la relation « est » est indirecte. Ceci est utilisé en interne par le code MRO pour suivre les invalidations de la mise en cache des méthodes/MRO.

Comme avec "mro::get_linear_isa" ci-dessus, "UNIVERSAL" est spécial. Les listes isarev de "UNIVERSAL" (et de ses parents) n'incluent pas toutes les classes existantes, même si toutes les classes sont effectivement des descendants aux fins d'héritage de méthodes.

mro::is_universal($classname)

Retourne un statut booléen indiquant si le nom de classe donné est "UNIVERSAL" lui-même, ou l'un des parents de "UNIVERSAL" par héritage @ISA.

Toute classe pour laquelle cette fonction retourne vrai est « universelle » dans le sens où toutes les classes héritent potentiellement de méthodes de celle-ci.

mro::invalidate_all_method_caches()

Incrémente "PL_sub_generation", ce qui invalide la mise en cache des méthodes dans tous les paquets.

mro::method_changed_in($classname)

Invalide le cache des méthodes de toutes les classes dépendantes de la classe donnée. Ceci n'est normalement pas nécessaire. Le seul cas connu où du code Perl pur peut confondre le cache des méthodes est lorsque vous installez manuellement une nouvelle sous-routine constante en utilisant une valeur scalaire en lecture seule, comme les internes de `constant do`. Si vous trouvez un autre cas, veuillez le signaler afin que nous puissions le corriger ou documenter l'exception ici.

mro::get_pkg_gen($classname)

Retourne un entier qui est incrémenté chaque fois qu'une méthode locale réelle dans le paquet $classname change, ou que le @ISA local de $classname est modifié.

Ceci est destiné aux auteurs de modules qui font beaucoup d'introspection de classes, car cela leur permet de vérifier très rapidement si quelque chose d'important concernant les propriétés locales d'une classe donnée a changé depuis la dernière fois qu'ils ont regardé. Il n'est pas incrémenté lors des changements de méthodes/@ISA dans les superclasses.

Il vous appartient toujours de rechercher les changements réels, et il se peut qu'il n'y en ait pas eu. Peut-être que tous les changements depuis la dernière fois que vous avez vérifié se sont annulés et ont laissé le paquet dans l'état où il était auparavant.

Cet entier commence normalement à une valeur de 1 lorsqu'un stash de paquet est instancié. L'appeler sur des paquets dont les stashes n'existent pas du tout retournera 0. Si un stash de paquet est complètement supprimé (ce qui n'est pas une occurrence normale, mais peut arriver si quelqu'un fait quelque chose comme "undef %NomPaquet::"), le nombre sera réinitialisé à 0 ou 1, selon la complétude de la suppression du paquet.

NAME

mro - Method Resolution Order (MRO) support

SYNOPSIS

  use MRO::Compat;
  use mro 'c3'; # or 'dfs' or 'strict' or 'vintage'
  
  package MyClass;
  use base 'Parent1', 'Parent2';
  
  sub some_method {
    my $self = shift;
    my $superclass_answer = $self->next::method(@_);
    return $superclass_answer + 1;
  }
  
  # ...
  
  my $object = MyClass->new;
  $object->some_method;
  
  # ...
  
  package MyClass::Child;
  use base 'MyClass';
  
  sub some_method {
    my $self = shift;
    my $parent_answer = $self->next::method(@_);
    return $parent_answer * 2;
  }

DESCRIPTION

This module allows you to control the Method Resolution Order (MRO) used by Perl when performing method lookups. It is most commonly used to select the C3 MRO, which is the standard MRO used by Python and Dylan.

The MRO is the order in which parent classes are searched when a method is called on an object. In cases of multiple inheritance, the order can become complex, and different MRO algorithms exist to handle these cases.

OVERVIEW

This module provides two main mechanisms:

"next::method"
A pseudo-method that allows a method to call the next method in the MRO chain.
"next::can"
A pseudo-method that checks if a next method exists in the MRO chain.

By default, Perl uses a Depth-First Search (DFS) MRO, which can lead to unexpected behavior in complex multiple inheritance scenarios. This module allows you to switch to the C3 MRO, which is generally considered more robust and predictable.

The C3 MRO

The C3 MRO algorithm is a linearization algorithm that ensures a consistent and predictable method resolution order, even with complex multiple inheritance. It is widely used in other object-oriented languages like Python.

When you use use mro 'c3';, Perl will internally use the C3 MRO for all method lookups within the current scope and any subsequently compiled code.

It is important to note that while inheritance in general follows whichever MRO is in effect for the given class, "next::method" *only* uses the C3 MRO.

One generally uses it like so:

  sub some_method {
    my $self = shift;
    my $superclass_answer = $self->next::method(@_);
    return $superclass_answer + 1;
  }

Note that you don't (re-)specify the method name. It forces you to always use the same method name as the method you started in.

It can be called on an object or a class, of course.

The way it resolves which actual method to call is:

1.
First, it determines the linearized C3 MRO of the object or class it is being called on.
2.
Then, it determines the class and method name of the context it was invoked from.
3.
Finally, it searches down the C3 MRO list until it reaches the contextually enclosing class, then searches further down the MRO list for the next method with the same name as the contextually enclosing method.

Failure to find a next method will result in an exception being thrown (see below for alternatives).

This is substantially different than the behavior of "SUPER" under complex multiple inheritance. (This becomes obvious when one realizes that the common superclasses in the C3 linearizations of a given class and one of its parents will not always be ordered the same for both.)

Caveat: Calling "next::method" from methods defined outside the class:

There is an edge case when using "next::method" from within a subroutine which was created in a different module than the one it is called from. It sounds complicated, but it really isn't. Here is an example which will not work correctly:

  *Foo::foo = sub { (shift)->next::method(@_) };

The problem exists because the anonymous subroutine being assigned to the *Foo::foo glob will show up in the call stack as being called "__ANON__" and not "foo" as you might expect. Since "next::method" uses "caller" to find the name of the method it was called in, it will fail in this case.

But fear not, there's a simple solution. The module "Sub::Name" will reach into the perl internals and assign a name to an anonymous subroutine for you. Simply do this:

  use Sub::Name 'subname';
  *Foo::foo = subname 'Foo::foo' => sub { (shift)->next::method(@_) };

and things will Just Work.

Functions

next::can

This is similar to "next::method", but just returns either a code reference or "undef" to indicate that no further methods of this name exist.

maybe::next::method

In simple cases, it is equivalent to:

  $self->next::method(@_) if $self->next::can;

But there are some cases where only this solution works (like "goto &maybe::next::method");
