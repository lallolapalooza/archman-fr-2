mpirun, mpiexec — Exécute des jobs sériels et parallèles dans Open MPI.

NOTE :

mpirun et mpiexec sont des synonymes l'un pour l'autre. En fait, ce sont des liens symboliques vers le même exécutable. L'utilisation de l'un ou l'autre nom produira exactement le même comportement.

SYNTAXE

Modèle Single Process Multiple Data (SPMD) :

mpirun [ options ] <programme> [ <arguments> ]

Modèle Multiple Instruction Multiple Data (MIMD) :

mpirun [ options_globales ]
       [ options_locales1 ] <programme1> [ <arguments1> ] :
       [ options_locales2 ] <programme2> [ <arguments2> ] :
       ... :
       [ options_localesN ] <programmeN> [ <argumentsN> ]

Notez que dans les deux modèles, l'invocation de mpirun via un nom de chemin absolu équivaut à spécifier l'option --prefix avec une valeur <dir> équivalente au répertoire où réside mpirun, moins son dernier sous-répertoire. Par exemple :

shell$ /usr/local/bin/mpirun ...

est équivalent à

shell$ mpirun --prefix /usr/local

RÉSUMÉ RAPIDE

Si vous cherchez simplement comment exécuter une application MPI, vous voudrez probablement utiliser une ligne de commande de la forme suivante :

shell$ mpirun [ -n X ] [ --hostfile <nom_fichier> ]  <programme>

Ceci exécutera X copies de <programme> dans votre environnement d'exécution actuel (si exécuté sous un gestionnaire de ressources pris en charge, le mpirun d'Open MPI utilisera généralement automatiquement le processus de démarrage du gestionnaire de ressources correspondant, par opposition à ssh (par exemple), qui nécessite l'utilisation d'un fichier d'hôtes, ou utilisera par défaut l'exécution de toutes les copies X sur localhost), en planifiant (par défaut) de manière tournante par slot CPU. Voir le reste de cette documentation pour plus de détails.

Veuillez noter que mpirun lie automatiquement les processus aux ressources matérielles. Trois modèles de liaison sont utilisés en l'absence de toute autre directive (Voir map/rank/bind defaults pour plus de détails) :

  • Liaison au cœur : lorsque le nombre de processus est <= 2
  • Liaison au paquet : lorsque le nombre de processus est > 2
  • Pas de liaison : en cas de surallocation

Si votre application utilise des threads, vous voudrez probablement vous assurer que vous n'êtes pas lié du tout (en spécifiant --bind-to none), ou que vous êtes lié à plusieurs cœurs en utilisant un niveau de liaison approprié ou un nombre spécifique d'éléments de traitement par processus d'application.

UTILISATION DE PRRTE PAR OPEN MPI

Open MPI utilise le PMIx Reference Runtime Environment (PRRTE) comme moteur principal pour lancer, surveiller et terminer les processus MPI.

Une grande partie de la documentation ci-dessous est directement importée de PRRTE. À ce titre, elle fait fréquemment référence aux concepts et aux options de ligne de commande de PRRTE. Sauf indication contraire, ces concepts et ces arguments de ligne de commande sont tous applicables à Open MPI également. Open MPI étend les options de ligne de commande PRRTE disponibles, et modifie également légèrement les comportements par défaut de PRRTE dans quelques cas. Ceux-ci seront décrits spécifiquement dans la documentation ci-dessous.

OPTIONS DE LIGNE DE COMMANDE

Le traitement principal de mpirun d'Open MPI est effectué via le PRRTE. Plus précisément : mpirun est effectivement un wrapper autour de prterun, mais les options de ligne de commande de mpirun sont légèrement différentes des commandes de ligne de commande de PRRTE.

Utilisez l'une des options suivantes pour spécifier sur quels hôtes (nœuds) du cluster exécuter. Notez qu'à partir du début de la version v1.8, mpirun lancera un démon sur chaque hôte de l'allocation (modifié par les options suivantes) au tout début de l'exécution, qu'il y ait ou non des processus d'application qui s'y exécuteront. Ceci est fait pour permettre la collecte d'informations de topologie matérielle des nœuds distants, nous permettant ainsi de mapper les processus contre la topologie connue. Cependant, c'est un changement par rapport au comportement des versions précédentes où les démons n'étaient lancés qu'après la fin du mappage, et donc ne se produisaient que sur les nœuds où les processus d'application s'exécutaient réellement.

  • -H, --host <hôte1,hôte2,...,hôteN> : liste des hôtes sur lesquels invoquer les processus.
  • --hostfile <fichier_hotes> : Fournit un fichier d'hôtes à utiliser.
  • --default-hostfile <fichier_hotes> : Fournit un fichier d'hôtes par défaut.
  • --machinefile <fichier_machines> : Synonyme de --hostfile.
  • --cpu-set <liste> : Restreint les processus lancés aux CPU logiques spécifiés sur chaque nœud (liste séparée par des virgules). Notez que les options de liaison s'appliqueront toujours dans l'enveloppe spécifiée — par exemple, vous pouvez choisir de lier chaque processus à un seul CPU dans l'ensemble de CPU spécifié.

Les options suivantes spécifient le nombre de processus à lancer. Notez qu'aucune des options n'implique de politique de liaison particulière — par exemple, demander N processus pour chaque paquet n'implique pas que les processus seront liés au paquet.

•
-n, --n, -c, -np <#> : Exécute ce nombre de copies du prog
ram sur les nœuds donnés. Cette option indique que le fichier spécifié est un programme exécutable et non un contexte d'application. Si aucune valeur n'est fournie pour le nombre de copies à exécuter (c'est-à-dire que ni -n ni ses synonymes ne sont fournis sur la ligne de commande), Open MPI exécutera automatiquement une copie du programme sur chaque slot de processus (voir la définition de "slot" de PRRTE pour la description d'un "slot de processus"). Cette fonctionnalité, cependant, ne peut être utilisée que dans le modèle SPMD et renverra une erreur (sans commencer l'exécution de l'application) sinon.

NOTE :

L'option -n est l'option préférée pour spécifier le nombre de copies du programme à exécuter, mais les options alternatives sont également acceptées.
  • --map-by ppr:N:<object> : Lance N fois le nombre d'objets du type spécifié sur chaque nœud.
  • --npersocket <#persocket> : Sur chaque nœud, lance ce nombre de processus multiplié par le nombre de sockets processeurs sur le nœud. L'option -npersocket active également l'option --bind-to-socket. (obsolète au profit de --map-by ppr:n:package)
  • --npernode <#pernode> : Sur chaque nœud, lance ce nombre de processus. (obsolète au profit de --map-by ppr:n:node).
  • --pernode : Sur chaque nœud, lance un processus - équivalent à --npernode 1. (obsolète au profit de --map-by ppr:1:node)

Pour mapper les processus :

•
--map-by <object> : Mappe vers l'objet spécifié, par défaut package. Les options prises en charge incluent slot, hwthread, core, L1cache, L2cache, L3cache, package, numa, node, seq, rankfile, pe-list=# et ppr. Tout objet peut inclure des modificateurs en ajoutant un : et toute combinaison des éléments suivants :
  • pe=n : lie n éléments de traitement à chaque processus
  • span : équilibre la charge des processus sur l'allocation
  • oversubscribe : autorise plus de processus sur un nœud que d'éléments de traitement
  • nooversubscribe : n'autorise pas plus de processus sur un nœud que d'éléments de traitement (par défaut)
  • nolocal : ne place pas les processus sur le même hôte que le processus mpirun
  • hwtcpus : utilise les threads matériels comme slots CPU pour le mappage
  • corecpus : utilise les cœurs de processeur comme slots CPU pour le mappage (par défaut)
  • file=filename : utilisé avec rankfile ; utilise filename pour spécifier le fichier à utiliser
  • ordered : utilisé avec pe-list pour lier chaque processus à l'un des éléments de traitement spécifiés

NOTE :

socket est également accepté comme alias pour package.
  • --bycore : Mappe les processus par cœur (obsolète au profit de --map-by core).
  • --byslot : Mappe et classe les processus en round-robin par slot (obsolète au profit de --map-by slot).
  • --nolocal : N'exécute aucune copie de l'application lancée sur le même nœud que celui où orterun s'exécute. Cette option remplacera le listage de localhost avec --host ou tout autre mécanisme spécifiant des hôtes. Alias pour --map-by :nolocal.
  • --nooversubscribe : Ne surcharge aucun nœud ; erreur (sans démarrer de processus) si le nombre de processus demandé entraînerait une surcharge. Cette option définit implicitement "max_slots" égal à la valeur "slots" pour chaque nœud. (Activé par défaut). Alias pour --map-by :nooversubscribe.
  • --oversubscribe : Les nœuds sont autorisés à être surchargés, même sur un système géré, et à surcharger des éléments de traitement. Alias pour --map-by :oversubscribe.
  • --bynode : Lance les processus un par nœud, en alternance par nœud dans un ordre circulaire. Cela répartit les processus uniformément entre les nœuds et attribue les rangs MPI_COMM_WORLD dans un ordre circulaire, "par nœud". (obsolète au profit de --map-by node)
  • --cpu-list <cpus> : Liste délimitée par des virgules d'identifiants de processeurs auxquels lier les processus [par défaut="NULL"]. Les identifiants de processeurs sont interprétés comme des identifiants de cœurs logiques hwloc.

    NOTE :

Vous pouvez exécuter la commande hwloc lstopo(1) pour voir une liste des cœurs disponibles et leurs identifiants logiques.

Pour ordonner les rangs des processus dans MPI_COMM_WORLD :

•
--rank-by <mode> : Classe en mode round-robin selon le mode spécifié, par défaut slot. Les options prises en charge incluent slot, node, fill et span.

Pour la liaison des processus :

  • --bind-to <object> : Lie les processus à l'objet spécifié, par défaut core. Les options prises en charge incluent slot, hwthread, core, l1cache, l2cache, l3cache, package, numa et none.
  • --cpus-per-proc <#perproc> : Lie chaque processus au nombre spécifié de CPU. (obsolète au profit de --map-by <obj>:PE=n)
  • --cpus-per-rank <#perrank> : Alias pour --cpus-per-proc. (obsolète au profit de --map-by <obj>:PE=n)
  • --bind-to-core Lie les processus aux cœurs (obsolète au profit de --bind-to core)
  • --bind-to-socket : Lie les processus aux sockets processeurs (obsolète au profit de --bind-to package)
  • --report-bindings : Signale toute liaison pour les processus lancés.

Pour les rankfiles :

•
--rankfile <rankfile> : Fournit un fichier rankfile. (obsolète au profit de --map-by rankfile:file=FILE)

Pour gérer les E/S standard :

  • --output-filename <filename> : Redirige stdout, stderr et stddiag de tous les processus vers une version unique par processus du nom de fichier spécifié. Tous les répertoires du nom de fichier seront automatiquement créés. Chaque fichier de sortie consistera en filename.id, où l'id sera le rang du processus dans MPI_COMM_WORLD, rempli de zéros à gauche pour un ordonnancement correct dans les listages. Une valeur de chemin relatif sera convertie en chemin absolu basé sur le répertoire de travail courant où mpirun est exécuté. Notez que cela ne fonctionnera pas dans les environnements où le système de fichiers sur les nœuds de calcul diffère de celui où mpirun(1) est exécuté.
  • --stdin <rank> : Le rang MPI_COMM_WORLD du processus qui doit recevoir stdin. Par défaut, stdin est redirigé vers le rang 0 de MPI_COMM_WORLD, mais cette option peut être utilisée pour rediriger stdin vers n'importe quel processus. Il est également acceptable de spécifier none, indiquant qu'aucun processus ne doit recevoir stdin.
  • --merge-stderr-to-stdout : Fusionne stderr dans stdout pour chaque processus.
  • --tag-output : Étiquette chaque ligne de sortie vers stdout, stderr et stddiag avec [jobid, MCW_rank]<stdxxx> indiquant l'identifiant du processus et le rang MPI_COMM_WORLD du processus qui a généré la sortie, et le canal qui l'a générée.
  • --timestamp-output : Horodate chaque ligne de sortie vers stdout, stderr et stddiag.
  • --xml : Fournit toutes les sorties vers stdout, stderr et stddiag en format XML.
  • --xml-file <filename> Fournit toutes les sorties en format XML vers le fichier spécifié.
  • --xterm <ranks> : Affiche la sortie des processus identifiés par leurs rangs MPI_COMM_WORLD dans des fenêtres xterm séparées. Les rangs sont spécifiés comme une liste de plages séparées par des virgules, avec un -1 indiquant tous. Une fenêtre séparée sera créée pour chaque processus spécifié.

    NOTE :

xterm terminera normalement la fenêtre lors de la terminaison du processus qui s'y exécute. Cependant, en ajoutant un ! à la fin de la liste des rangs spécifiés, les options appropriées seront fournies pour garantir que xterm maintient la fenêtre ouverte après la terminaison du processus, vous permettant ainsi de voir la sortie du processus. Chaque fenêtre xterm devra ensuite être fermée manuellement. Remarque : Dans certains environnements, xterm peut exiger que l'exécutable soit dans le chemin de l'utilisateur, ou soit spécifié en termes absolus ou relatifs. Ainsi, il peut être nécessaire de spécifier un exécutable local comme ./my_mpi_app au lieu de simplement my_mpi_app. Si xterm ne parvient pas à trouver l'exécutable, mpirun se bloquera, mais répondra toujours correctement à un ctrl-C. Si cela se produit, veuillez vérifier que l'exécutable est correctement spécifié et réessayez.

Pour gérer les fichiers et l'environnement d'exécution :

  • --path <path> : <path> qui sera utilisé lors de la tentative de localisation des exécutables demandés. Ceci est utilisé avant l'utilisation du paramètre de la variable d'environnement PATH locale.
  • --prefix <dir> : Répertoire préfixe qui sera utilisé pour définir le PATH et LD_LIBRARY_PATH sur le nœud distant avant d'invoquer Open MPI ou le processus cible. Voir la section Exécution à distance, ci-dessous.
  • --noprefix : Désactive le comportement automatique de --prefix
  • --preload-binary : Copie le(s) exécutable(s) spécifié(s) vers les machines distantes avant de démarrer les processus distants. Les exécutables seront copiés dans le répertoire de session Open MPI et seront supprimés à la fin du travail.
  • --preload-files <files> : Précharge la liste de fichiers séparés par des virgules dans le répertoire de travail courant des machines distantes où les processus seront lancés avant de démarrer ces processus.
  • --set-cwd-to-session-dir : Définit le répertoire de travail des processus démarrés à leur répertoire de session.
  • --wd <dir> : Synonyme de -wdir.
  • --wdir <dir> : Change pour le répertoire <dir> avant que le programme de l'utilisateur ne s'exécute. Voir la section Répertoire de travail courant pour des notes sur les chemins relatifs. Remarque : Si l'option --wdir apparaît à la fois sur la ligne de commande et dans un contexte d'application, le contexte aura la priorité sur la ligne de commande. Ainsi, si le chemin vers le wdir souhaité est différent sur les nœuds backend, il doit être spécifié comme un chemin absolu correct pour le nœud backend.
  • -x <env> : Exporte les variables d'environnement spécifiées vers les nœuds distants avant d'exécuter le programme. Une seule variable d'environnement peut être spécifiée par option -x. Les variables d'environnement existantes peuvent être spécifiées ou de nouveaux noms de variables peuvent être spécifiés avec des valeurs correspondantes. Par exemple :
shell$ mpirun -x DISPLAY -x OFILE=/tmp/out ...

L'analyseur pour l'option -x n'est pas très sophistiqué ; il ne comprend même pas les valeurs entre guillemets. Il est conseillé aux utilisateurs de définir les variables dans l'environnement, puis d'utiliser -x pour les exporter (pas les définir).

Définition des paramètres MCA :

  • --gmca <clé> <valeur> : Transmet des paramètres MCA globaux applicables à tous les contextes. <clé> est le nom du paramètre ; <valeur> est la valeur du paramètre.
  • --mca <clé> <valeur> : Envoie des arguments à divers modules MCA. Voir la section Définition des paramètres MCA pour plus de détails.

    NOTE :

Open MPI tentera de discerner les paramètres MCA de PMIx et PRRTE passés via --mca et de les gérer de manière appropriée, mais il ne pourra pas toujours deviner correctement. Il est préférable d'utiliser --pmixmca et --prtemca lors de la transmission de paramètres MCA à PMIx et PRRTE, respectivement.
  • --pmixmca <clé> <valeur> : Envoie des arguments aux modules MCA du sous-système PMIx. Voir la section Définition des paramètres MCA pour plus de détails.
  • --prtemca <clé> <valeur> : Envoie des arguments aux modules MCA du sous-système PMIx Reference Runtime Environment (PRRTE). Voir la section Définition des paramètres MCA pour plus de détails.
  • --tune <fichier_tune> : Spécifie un fichier de réglage pour définir les arguments de divers modules MCA et variables d'environnement. Voir :ref:` Définition des paramètres MCA et des variables d'environnement à partir d'un fichier `. --am <arg> est un alias pour --tune <arg>.

Pour le débogage :

  • --get-stack-traces : Associé à l'option --timeout, mpirun obtiendra et imprimera les traces de pile de tous les processus lancés qui sont encore actifs lorsque le délai d'attente expire. Notez que l'obtention des traces de pile peut prendre un peu de temps et produire beaucoup de sortie, en particulier pour les travaux avec un grand nombre de processus.
  • --timeout <secondes> : Le nombre maximum de secondes pendant lesquelles mpirun s'exécutera. Après ce nombre de secondes, mpirun abandonnera le travail lancé et se terminera avec un statut de sortie non nul. L'utilisation de --timeout peut également être utile lorsqu'elle est combinée avec l'option --get-stack-traces.

Il existe également d'autres options :

  • --allow-run-as-root : Autorise mpirun à s'exécuter lorsqu'il est lancé par l'utilisateur root (mpirun abandonne par défaut lorsqu'il est lancé en tant qu'utilisateur root). Assurez-vous de consulter la section Exécution en tant que root pour plus de détails.
  • --app <fichier_app> : Fournit un fichier d'application, ignorant toutes les autres options de ligne de commande.
  • --continuous : Le travail doit s'exécuter jusqu'à ce qu'il soit explicitement terminé.
  • --disable-recovery : Désactive la récupération (réinitialise toutes les options de récupération à désactivé).
  • --do-not-launch : Effectue toutes les opérations nécessaires pour préparer le lancement de l'application, mais ne la lance pas réellement.
  • --enable-recovery : Active la récupération à partir d'une défaillance de processus (par défaut : désactivé)
  • --leave-session-attached : Ne détache pas les démons backend utilisés par cette application. Cela permet d'afficher les messages d'erreur des démons ainsi que l'environnement sous-jacent (par exemple, en cas d'échec du lancement d'un démon).
  • --max-restarts <nb> : Nombre maximum de fois où un processus défaillant doit être redémarré.
  • --personality <liste> : Liste séparée par des virgules du modèle de programmation, des langages et des conteneurs utilisés (par défaut=``ompi``).
  • --ppr <liste> : Liste séparée par des virgules du nombre de processus par type de ressource (par défaut : aucun). Alias pour --map-by ppr:N:OBJ.
  • --report-child-jobs-separately : Retourne le statut de sortie du travail principal uniquement.
  • --report-events <URI> : Signale les événements à un outil écoutant à l'URI spécifiée.
  • --report-pid <canal> : Affiche le PID de mpirun au démarrage. Le canal doit être soit un - pour indiquer que le PID doit être envoyé sur la sortie standard, soit un + pour indiquer que le PID doit être envoyé sur la sortie d'erreur standard, soit un nom de fichier dans lequel le PID doit être écrit.
  • --report-uri <canal> : Affiche l'URI de mpirun au démarrage. Le canal doit être soit un - pour indiquer que l'URI doit être envoyé sur la sortie standard, soit un + pour indiquer que l'URI doit être envoyé sur la sortie d'erreur standard, soit un nom de fichier dans lequel l'URI doit être écrit.
  • --show-progress : Affiche un bref rapport périodique sur la progression du lancement.
  • --terminate : Termine le DVM.
  • --use-hwthread-cpus : Utilise les threads matériels comme CPU indépendants.

    Notez que si un nombre d'emplacements n'est pas fourni à Open MPI (par exemple, via le mot-clé slots dans un fichier d'hôtes ou via un gestionnaire de ressources tel que Slurm), l'utilisation de cette option modifie le calcul par défaut du nombre d'emplacements sur un nœud. Voir la définition d'un "slot" dans PRRTE pour plus de détails.

    Notez également que l'utilisation de cette option modifie la définition par Open MPI d'un "élément processeur" d'un cœur de processeur à un thread matériel. Voir la définition d'un "élément processeur" dans PRRTE pour plus de détails.

Les options suivantes sont utiles pour les développeurs ; elles ne sont généralement pas utiles à la plupart des utilisateurs d'Open MPI :

  • --debug-daemons : Active le débogage des démons d'exécution utilisés par cette application.
  • --debug-daemons-file : Active le débogage des démons d'exécution utilisés par cette application, en stockant la sortie dans des fichiers.
  • --display-devel-map : Affiche un tableau plus détaillé montrant l'emplacement mappé de chaque processus avant le lancement.
  • --display-topo : Affiche la topologie dans le cadre de la carte des processus juste avant le lancement.
  • --launch-agent : Nom de l'exécutable à utiliser pour démarrer les processus sur les nœuds distants. La valeur par défaut est prted. Cette option peut être utilisée pour tester de nouveaux concepts de démons, ou pour passer des options aux démons sans que mpirun lui-même ne les voie. Par exemple, spécifier un agent de lancement de prted --prtemca odls_base_verbose 5 permet au développeur de demander à prted une sortie de débogage sans le bruit de mpirun lui-même.
  • --report-state-on-timeout : Lorsqu'elle est associée à l'option de ligne de commande --timeout, signale l'état du sous-système d'exécution de chaque processus lorsque le délai d'attente expire.

Il peut y avoir d'autres options listées avec mpirun --help.

Une invocation de mpirun lance une application MPI exécutée sous Open MPI. Si l'application est de type Single Process Multiple Data (SPMD), l'application peut être spécifiée sur la ligne de commande mpirun.

Si l'application est de type Multiple Instruction Multiple Data (MIMD), composée de plusieurs programmes, l'ensemble des programmes et des arguments peut être spécifié de l'une des deux manières suivantes : Arguments de ligne de commande étendus et Contexte d'application.

Un contexte d'application décrit l'ensemble des programmes MIMD, y compris tous les arguments, dans un fichier séparé. Ce fichier contient essentiellement plusieurs lignes de commande mpirun, moins le nom de la commande elle-même. La possibilité de spécifier des options différentes pour différentes instanciations d'un programme est une autre raison d'utiliser un contexte d'application.

Les arguments de ligne de commande étendus permettent de décrire la disposition de l'application sur la ligne de commande en utilisant des deux-points (:) pour séparer la spécification des programmes et des arguments. Certaines options sont définies globalement pour tous les programmes spécifiés (par exemple, --hostfile), tandis que d'autres sont spécifiques à un seul programme (par exemple, -n).

Les nœuds hôtes peuvent être identifiés sur la ligne de commande mpirun avec l'option --host ou dans un fichier d'hôtes.

Par exemple :

shell$ mpirun -H aa,aa,bb ./a.out

Lance deux processus sur le nœud aa et un sur bb.

Ou, considérons le fichier d'hôtes :

shell$ cat myhostfile
aa slots=2
bb slots=2
cc slots=2

Ici, nous listons à la fois les noms d'hôtes (aa, bb et cc) mais aussi le nombre d'emplacements disponibles pour chacun.

shell$ mpirun --hostfile myhostfile ./a.out

lancera deux processus sur chacun des trois nœuds.

shell$ mpirun --hostfile myhostfile --host aa ./a.out

lancera deux processus, tous deux sur le nœud aa.

shell$ mpirun --hostfile myhostfile --host dd ./a.out

ne trouvera aucun hôte sur lequel exécuter et abandonnera avec une erreur. C'est-à-dire que l'hôte spécifié dd ne se trouve pas dans le fichier d'hôtes spécifié.

Lors de l'exécution sous des gestionnaires de ressources (par exemple, Slurm, Torque, etc.), Open MPI obtiendra les noms d'hôtes

et le nombre d'emplacements directement du gestionnaire de ressources.

Comme nous venons de le voir, le nombre de processus à exécuter peut être défini en utilisant le fichier d'hôtes. D'autres mécanismes existent.

Le nombre de processus lancés peut être spécifié comme un multiple du nombre de nœuds ou de packages de processeurs disponibles. Par exemple,

shell$ mpirun -H aa,bb --map-by ppr:2:package ./a.out

lance les processus 0-3 sur le nœud aa et les processus 4-7 sur le nœud bb (en supposant que aa et bb contiennent chacun 4 emplacements).

shell$ mpirun -H aa,bb --map-by ppr:2:node ./a.out

lance les processus 0-1 sur le nœud aa et les processus 2-3 sur le nœud bb.

shell$ mpirun -H aa,bb --map-by ppr:1:node ./a.out

lance un processus par nœud hôte.

mpirun -H aa,bb --pernode ./a.out

est identique à --map-by ppr:1:node et --npernode 1.

Une autre alternative est de spécifier le nombre de processus avec l'option -n. Considérons maintenant le fichier d'hôtes :

shell$ cat myhostfile
aa slots=4
bb slots=4
cc slots=4

Exécutez maintenant avec myhostfile :

shell$ mpirun --hostfile myhostfile -n 6 ./a.out

lancera les processus 0-3 sur le nœud aa et les processus 4-5 sur le nœud bb. Les emplacements restants dans le fichier d'hôtes ne seront pas utilisés car l'option -n a indiqué que seuls 6 processus devaient être lancés.

Les exemples ci-dessus illustrent le mappage par défaut des processus aux nœuds. Ce mappage peut également être contrôlé avec diverses options mpirun qui décrivent les politiques de mappage.

Considérez le même fichier d'hôtes qu'auparavant, à nouveau avec -n 6. Le tableau ci-dessous répertorie quelques variations de mpirun et montre quels rangs MPI_COMM_WORLD se retrouvent sur quel nœud :

Commande Nœud aa Nœud bb Nœud cc
mpirun 0 1 2 3 4 5
mpirun --map-by node 0 3 1 4 2 5
mpirun --nolocal 0 1 2 3 4 5

L'option --map-by node répartira la charge des processus sur les nœuds disponibles, numérotant chaque processus de manière circulaire.

L'option --nolocal empêche tout processus d'être mappé sur l'hôte local (dans ce cas, le nœud aa). Bien que mpirun consomme généralement peu de ressources système, --nolocal peut être utile pour lancer de très grands travaux où mpirun peut réellement nécessiter l'utilisation de quantités notables de mémoire et/ou de temps de traitement.

Tout comme -n peut spécifier moins de processus qu'il n'y a d'emplacements, il peut également sur-allouer les emplacements. Par exemple, avec le même fichier d'hôtes :

shell$ mpirun --hostfile myhostfile -n 14 ./a.out

lancera les processus 0-3 sur le nœud aa, 4-7 sur bb, et 8-11 sur cc. Il ajoutera ensuite les deux processus restants aux nœuds de son choix.

On peut également spécifier des limites de sur-allocation. Par exemple, avec le même fichier d'hôtes :

shell$ mpirun --hostfile myhostfile -n 14 --nooversubscribe ./a.out

produira une erreur car --nooversubscribe empêche la sur-allocation.

Les limites de sur-allocation peuvent également être spécifiées dans le fichier d'hôtes lui-même :

shell$ cat myhostfile
aa slots=4 max_slots=4
bb         max_slots=4
cc slots=4

Le champ max_slots spécifie une telle limite. Lorsque c'est le cas, la valeur des emplacements est par défaut la limite. Maintenant :

shell$ mpirun --hostfile myhostfile -n 14 ./a.out

fait lancer les 12 premiers processus comme auparavant, mais les deux processus restants seront forcés sur le nœud cc. Les deux autres nœuds sont protégés par le fichier d'hôtes contre la sur-allocation par ce travail.

L'utilisation de l'option --nooversubscribe peut être utile car Open MPI n'obtient actuellement pas les valeurs max_slots du gestionnaire de ressources.

Bien sûr, -n peut également être utilisé avec l'option -H ou -host. Par exemple :

shell$ mpirun -H aa,bb -n 8 ./a.out

lance 8 processus. Comme seuls deux hôtes sont spécifiés, après le mappage des deux premiers processus, un sur aa et un sur bb, les processus restants sur-allouent les hôtes spécifiés.

Et voici un exemple MIMD :

shell$ mpirun -H aa -n 1 hostname : -H bb,cc -n 2 uptime

lancera le processus 0 exécutant hostname sur le nœud aa et les processus 1 et 2 exécutant chacun uptime sur les nœuds bb et cc, respectivement.

Open MPI emploie une procédure en trois phases pour attribuer les emplacements et les rangs des processus :

1.
Mappage : Attribue un emplacement par défaut à chaque processus
2.
Classement : Attribue une valeur de rang MPI_COMM_WORLD à chaque processus
3.
Liaison : Contraindre chaque processus à s'exécuter sur des processeurs spécifiques

L'étape de mappage est utilisée pour attribuer un emplacement par défaut à chaque processus en fonction du mappeur utilisé. Le mappage par emplacement, par nœud et séquentiellement entraîne l'attribution des processus au niveau du nœud. En revanche, le mappage par objet permet au mappeur d'attribuer le processus à un objet réel sur chaque nœud.

Notez que l'emplacement attribué au processus est indépendant de l'endroit où il sera lié — l'attribution est utilisée uniquement comme entrée pour l'algorithme de liaison.

Le mappage des processus aux nœuds peut être défini non seulement avec des politiques générales, mais aussi, si nécessaire, à l'aide de mappages arbitraires qui ne peuvent pas être décrits par une politique simple. On peut utiliser le « mappeur séquentiel », qui lit le fichier d'hôtes ligne par ligne, attribuant les processus aux nœuds dans l'ordre où le fichier d'hôtes le spécifie. Utilisez l'option ---map-by seq. Par exemple, en utilisant le même fichier d'hôtes qu'auparavant :

shell$ mpirun -hostfile myhostfile --map-by seq ./a.out

lancera trois processus, un sur chacun des nœuds aa, bb et cc, respectivement. Les nombres d'emplacements n'ont pas d'importance ; un processus est lancé par ligne sur le nœud indiqué sur la ligne.

Une autre façon de spécifier des mappages arbitraires est d'utiliser un fichier de rangs (rankfile), qui vous donne également un contrôle détaillé sur la liaison des processus. Les fichiers de rangs sont discutés *ci-dessous*.

La deuxième phase se concentre sur le classement du processus au sein de MPI_COMM_WORLD du travail. Open MPI sépare cela de la procédure de mappage pour permettre plus de flexibilité dans le placement relatif des processus MPI. Ceci est mieux illustré en considérant les cas suivants où nous avons utilisé l'option --np 8 --map-by ppr:2:package --host aa:4,bb:4 :

Option Nœud aa Nœud bb
--rank-by fill (c'est-à-dire, remplissage dense) Par défaut 0 1 | 2 3 4 5 | 6 7
--rank-by span (c'est-à-dire, remplissage dispersé ou équilibré) 0 4 | 1 5 2 6 | 3 7
--rank-by node 0 2 | 4 6 1 3 | 5 7

Le classement par fill attribue les rangs MCW dans une progression simple à travers chaque nœud. Le classement par span et par slot fournissent the résultat identique — une progression en tournoi des paquets sur tous les nœuds avant de retourner au premier paquet sur le premier nœud. Le classement par nœud attribue des rangs MCW en itérant d’abord sur les nœuds puis par paquet.

La phase de liaison lie effectivement chaque processus à un ensemble donné de processeurs. Cela peut améliorer les performances si le système d’exploitation place les processus de manière non optimale. Par exemple, il peut surcharger certains packages de processeurs multicœurs, laissant d’autres packages inactifs ; cela peut amener les processus à se disputer inutilement des ressources communes. Ou bien, il peut répartir les processus trop largement ; cela peut être sous-optimal si les performances de l’application sont sensibles aux coûts de communication inter-processus. La liaison peut également empêcher le système d’en migrer excessivement les processus, quelle que soit la manière dont ces processus ont été placés au départ.

Les processeurs à utiliser pour la liaison peuvent être identifiés en termes de regroupements topologiques — par exemple, la liaison à un l3cache liera chaque processus à tous les processeurs au sein de la portée d’un seul cache L3 dans leur emplacement assigné. Ainsi, si un processus est assigné par le mapper à un certain package, une directive --bind-to l3cache obligera le processus à être lié aux processeurs qui partagent un seul cache L3 au sein de ce package.

Alternativement, les processus peuvent être mappés et liés à des cœurs spécifiés en utilisant l’option --map-by pe-list=. Par exemple, --map-by pe-list=0,2,5 mappera trois processus qui seront tous liés aux cœurs logiques 0,2,5. Si vous avez l’intention de lier chacun des trois processus à des cœurs différents, le qualificateur :ordered peut être utilisé comme ceci : --map-by pe-list=0,2,5:ordered. Dans cet exemple, le premier processus sur un nœud sera lié au CPU 0, le deuxième processus sur le nœud sera lié au CPU 2, et le troisième processus sur le nœud sera lié au CPU 5.

Enfin, --report-bindings peut être utilisé pour signaler les liaisons.

À titre d’exemple, considérons un nœud avec deux packages de processeurs, chacun composé de quatre cœurs, et chacun de ces cœurs contient un thread matériel. L’option --report-bindings montre la liaison de chaque processus de manière descriptive. Voici quelques exemples.

shell$ mpirun --np 4 --report-bindings --map-by core --bind-to core
[...] Rank 0 bound to package[0][core:0]
[...] Rank 1 bound to package[0][core:1]
[...] Rank 2 bound to package[0][core:2]
[...] Rank 3 bound to package[0][core:3]

Dans le cas ci-dessus, les processus se lient aux cœurs successifs.

shell$ mpirun --np 4 --report-bindings --map-by package --bind-to package
[...] Rank 0 bound to package[0][core:0-3]
[...] Rank 1 bound to package[0][core:0-3]
[...] Rank 2 bound to package[1][core:4-7]
[...] Rank 3 bound to package[1][core:4-7]

Dans le cas ci-dessus, les processus se lient à tous les cœurs des packages successifs. Les processus parcourent les packages de processeurs de manière cyclique autant de fois que nécessaire. Par défaut, les processus sont classés de manière fill.

shell$ mpirun --np 4 --report-bindings --map-by package --bind-to package --rank-by span
[...] Rank 0 bound to package[0][core:0-3]
[...] Rank 1 bound to package[1][core:4-7]
[...] Rank 2 bound to package[0][core:0-3]
[...] Rank 3 bound to package[1][core:4-7]

Le cas ci-dessus démontre la différence de classement lorsque le qualificateur span est utilisé au lieu du qualificateur par défaut.

shell$ mpirun --np 4 --report-bindings --map-by slot:PE=2 --bind-to core
[...] Rank 0 bound to package[0][core:0-1]
[...] Rank 1 bound to package[0][core:2-3]
[...] Rank 2 bound to package[0][core:4-5]
[...] Rank 3 bound to package[0][core:6-7]

Dans le cas ci-dessus, le résultat nous montre que 2 cœurs ont été liés par processus. Plus précisément, le mappage par slot avec le qualificateur PE=2 a indiqué que chaque slot (c'est-à-dire processus) devait consommer deux éléments de processeur. Par défaut, Open MPI définit « élément de processeur » comme « cœur », et par conséquent, --bind-to core a lié chaque processus aux deux cœurs auxquels il était mappé.

shell$ mpirun --np 4 --report-bindings --map-by slot:PE=2 --use-hwthread-cpus
[...]] Rank 0 bound to package[0][hwt:0-1]
[...]] Rank 1 bound to package[0][hwt:2-3]
[...]] Rank 2 bound to package[0][hwt:4-5]
[...]] Rank 3 bound to package[0][hwt:6-7]

Dans le cas ci-dessus, nous remplaçons --bind-to core par --use-hwthread-cpus. L’option --use-hwthread-cpus est convertie en --bind-to hwthread et indique à la sortie de --report-bindings d’afficher les threads matériels auxquels un processus est lié. Dans ce cas, les processus sont liés à 2 threads matériels par processus.

shell$ mpirun --np 4 --report-bindings --bind-to none
[...] Rank 0 is not bound (or bound to all available processors)
[...] Rank 1 is not bound (or bound to all available processors)
[...] Rank 2 is not bound (or bound to all available processors)
[...] Rank 3 is not bound (or bound to all available processors)

Dans le cas ci-dessus, la liaison est désactivée et est signalée comme telle.

Le support d’Open MPI pour la liaison de processus dépend du système d’exploitation sous-jacent. Par conséquent, certaines options de liaison de processus peuvent ne pas être disponibles sur tous les systèmes.

La liaison de processus peut également être définie avec des paramètres MCA. Leur utilisation est moins pratique que celle des options mpirun. D’autre part, les paramètres MCA peuvent être définis non seulement sur la ligne de commande de mpirun, mais alternativement dans un fichier mca-params.conf système ou utilisateur, ou sous forme de variables d’environnement, comme décrit dans Setting MCA Parameters. Ce sont des paramètres MCA pour le runtime PRRTE, donc l’argument de ligne de commande --prtemca (oui, prte avec un seul r, pas deux r) doit être utilisé pour passer la paire clé/valeur du paramètre MCA. Alternativement, la paire clé/valeur du paramètre MCA peut être spécifique à la ligne de commande en préfixant la clé avec PRTE_MCA_ (encore une fois, ce n’est pas une faute de frappe : PRTE et non PRRTE). Les fichiers de rang sont des fichiers texte qui spécifient des informations détaillées sur la manière dont les processus individuels doivent être mappés aux nœuds, et aux processeurs auxquels ils doivent être liés. Chaque ligne d'un fichier de rang spécifie l'emplacement d'un processus (pour les jobs MPI, le « rang » du processus fait référence à son rang dans MPI_COMM_WORLD). La forme générale de chaque ligne dans le fichier de rang est :

rank <N>=<nom_hôte> slot=<liste_de_slots>

Par exemple :

shell$ cat myrankfile
rank 0=aa slot=1:0-2
rank 1=bb slot=0:0,1
rank 2=cc slot=2-3
shell$ mpirun -H aa,bb,cc,dd --map-by rankfile:file=myrankfile ./a.out

Signifie que :

  • Le rang 0 s'exécute sur le nœud aa, lié au package logique 1, cœurs 0-2.
  • Le rang 1 s'exécute sur le nœud bb, lié au package logique 0, cœurs 0 et 1.
  • Le rang 2 s'exécute sur le nœud cc, lié aux cœurs logiques 2 et 3.

Notez que seuls les emplacements des processeurs logiques sont pris en charge. Par défaut, les valeurs spécifiées sont considérées comme des cœurs. Si vous avez l'intention de spécifier des threads matériels spécifiques, vous devez ajouter le qualificateur :hwtcpus à l'option de ligne de commande --map-by (par exemple, --map-by rankfile:file=myrankfile:hwtcpus).

Si la spécification de liaison se chevauche entre deux rangs quelconques, une erreur se produit. Si vous avez l'intention d'autoriser les processus à partager la même unité de traitement logique, vous devez passer l'option de ligne de commande --bind-to :overload-allowed pour indiquer au runtime d'ignorer cette vérification.

Les noms d'hôtes listés ci-dessus sont « absolus », ce qui signifie que des noms d'hôtes résolubles réels sont spécifiés. Cependant, les noms d'hôtes peuvent également être spécifiés comme « relatifs », ce qui signifie qu'ils sont spécifiés par rapport à une liste de noms d'hôtes spécifiée externement (par exemple, par l'argument --host de mpirun, un fichier hôte ou un planificateur de tâches).

La spécification « relative » est de la forme +n<X>, où X est un entier spécifiant le Xème nom d'hôte dans l'ensemble de tous les noms d'hôtes disponibles, indexé à partir de 0. Par exemple :

shell$ cat myrankfile
rank 0=+n0 slot=1:0-2
rank 1=+n1 slot=0:0,1
rank 2=+n2 slot=2-3
shell$ mpirun -H aa,bb,cc,dd --map-by rankfile:file=myrankfile ./a.out

Tous les emplacements de slot de package/cœur sont spécifiés comme des indices logiques.

NOTE :

La série Open MPI v1.6 utilisait des indices physiques. Depuis Open MPI v5.0, seuls les indices logiques sont pris en charge et le paramètre MCA rmaps_rank_file_physical n'est plus reconnu.

Vous pouvez utiliser des outils tels que lstopo(1) de Hwloc pour trouver les indices logiques des packages et des cœurs.

Localisation des fichiers

Ceci est du contenu ancien et codé en dur

Ce contenu est-il toujours actuel / exact ? Doit-il être mis à jour et conservé, ou supprimé ?

Si aucun chemin relatif ou absolu n'est spécifié pour un fichier, Open MPI recherchera d'abord les fichiers en parcourant les répertoires spécifiés par l'option --path. S'il n'y a pas d'option --path définie ou si le fichier n'est pas trouvé à l'emplacement --path, alors Open MPI recherchera dans la variable d'environnement PATH de l'utilisateur, telle que définie sur les nœuds sources.

Si un répertoire relatif est spécifié, il doit être relatif au répertoire de travail initial déterminé par le lanceur spécifique utilisé. Par exemple, lors de l'utilisation du lanceur ssh, le répertoire initial est $HOME par défaut. D'autres lanceurs peuvent définir le répertoire initial sur le répertoire de travail courant lors de l'invocation de mpirun.

Répertoire de travail courant

Ceci est du contenu ancien et codé en dur

Ce contenu est-il toujours actuel / exact ? Doit-il être mis à jour et conservé, ou supprimé ?

L'option --wdir de mpirun (et son synonyme, --wd) permet à l'utilisateur de changer de répertoire arbitraire avant que le programme ne soit invoqué. Elle peut également être utilisée dans les fichiers de contexte d'application pour spécifier les répertoires de travail sur des nœuds spécifiques et/ou pour des applications spécifiques.

Si l'option --wdir apparaît à la fois dans un fichier de contexte et sur la ligne de commande, le répertoire du fichier de contexte remplacera la valeur de la ligne de commande.

Si l'option -wdir est spécifiée, Open MPI tentera de changer pour le répertoire spécifié sur tous les nœuds distants. Si cela échoue, mpirun échouera.

Si l'option -wdir n'est pas spécifiée, Open MPI enverra le nom du répertoire où mpirun a été invoqué à chaque nœud distant. Les nœuds distants tenteront de changer pour ce répertoire. S'ils ne peuvent pas (par exemple, si le répertoire n'existe pas sur ce nœud), alors Open MPI utilisera le répertoire par défaut déterminé par le lanceur.

Tous les changements de répertoire se produisent avant l'invocation du programme de l'utilisateur ; ils n'attendent pas que MPI_INIT(3) soit appelé.

Entrée/Sortie standard

Ce contenu est-il toujours actuel / exact ? Doit-il être mis à jour et conservé, ou supprimé ?

Open MPI dirige l'entrée standard UNIX vers /dev/null sur tous les processus, à l'exception du processus de rang 0 de MPI_COMM_WORLD. Le processus de rang 0 de MPI_COMM_WORLD hérite de l'entrée standard de mpirun.

NOTE :

Le nœud qui a invoqué mpirun n'a pas besoin d'être le même que le nœud où réside le processus de rang 0 de MPI_COMM_WORLD. Open MPI gère la redirection de l'entrée standard de mpirun vers le processus de rang 0.

Open MPI dirige la sortie standard et l'erreur standard UNIX des nœuds distants vers le nœud qui a invoqué mpirun et l'affiche sur la sortie standard

tput/erreur de mpirun. Les processus locaux héritent de la sortie standard/erreur de mpirun et y sont transférés directement.

Il est donc possible de rediriger l'E/S standard des applications Open MPI en utilisant la procédure de redirection de shell habituelle sur mpirun. Par exemple :

shell$ mpirun -n 2 my_app < my_input > my_output

Notez que dans cet exemple, seul le processus de rang 0 de MPI_COMM_WORLD recevra le flux de my_input sur stdin. Le stdin de tous les autres nœuds sera lié à /dev/null. Cependant, la sortie standard de tous les nœuds sera collectée dans le fichier my_output.

Propagation des signaux

Ce contenu est-il toujours actuel / précis ? Doit-il être mis à jour et conservé, ou supprimé ?

Lorsque mpirun reçoit un SIGTERM et un SIGINT, il tentera d'arrêter tout le job en envoyant à tous les processus du job un SIGTERM, en attendant un petit nombre de secondes, puis en envoyant à tous les processus du job un SIGKILL.

Les signaux SIGUSR1 et SIGUSR2 reçus par mpirun sont propagés à tous les processus du job.

Un signal SIGTSTOP à mpirun entraînera l'envoi d'un signal SIGSTOP à tous les programmes démarrés par mpirun, et de même un signal SIGCONT à mpirun entraînera l'envoi d'un signal SIGCONT.

Les autres signaux ne sont actuellement pas propagés par mpirun.

Terminaison des processus / Gestion des signaux

Contenu obsolète et codé en dur

Ce contenu est-il toujours actuel / précis ? Doit-il être mis à jour et conservé, ou supprimé ?

Pendant l'exécution d'une application MPI, si un processus meurt anormalement (soit en sortant avant d'invoquer MPI_FINALIZE(3), soit en mourant à la suite d'un signal), mpirun affichera un message d'erreur et arrêtera le reste de l'application MPI.

Les gestionnaires de signaux d'utilisateur devraient probablement éviter d'essayer de nettoyer l'état MPI (Open MPI n'est actuellement pas sûr en cas de signal asynchrone ; voir MPI_INIT_THREAD(3) pour des détails sur MPI_THREAD_MULTIPLE et la sécurité des threads). Par exemple, si une faute de segmentation se produit dans MPI_SEND(3) (peut-être parce qu'un mauvais tampon a été passé) et qu'un gestionnaire de signal utilisateur est invoqué, si ce gestionnaire tente d'invoquer MPI_FINALIZE(3), de mauvaises choses pourraient se produire car Open MPI était déjà "dans" MPI au moment où l'erreur s'est produite. Étant donné que mpirun remarquera que le processus est mort à cause d'un signal, il n'est probablement pas nécessaire (et plus sûr) pour l'utilisateur de nettoyer uniquement l'état non-MPI.

Environnement des processus

Ce contenu est-il toujours actuel / précis ? Doit-il être mis à jour et conservé, ou supprimé ?

Les processus de l'application MPI héritent de leur environnement du démon PRRTE sur le nœud sur lequel ils s'exécutent. L'environnement est typiquement hérité du shell de l'utilisateur. Sur les nœuds distants, l'environnement exact est déterminé par le module de démarrage MCA utilisé. Le module de lancement rsh, par exemple, utilise rsh/ssh pour lancer le démon PRRTE sur les nœuds distants, et exécute généralement un ou plusieurs fichiers de configuration du shell de l'utilisateur avant de lancer le démon PRRTE. Lors de l'exécution d'applications liées dynamiquement qui nécessitent que la variable d'environnement LD_LIBRARY_PATH soit définie, il faut prendre soin de s'assurer qu'elle est correctement définie lors du démarrage d'Open MPI.

Voir la section Exécution à distance pour plus de détails.

Exécution à distance

Contenu obsolète et codé en dur

Ce contenu est-il toujours actuel / précis ? Doit-il être mis à jour et conservé, ou supprimé ?

Open MPI exige que la variable d'environnement PATH soit définie pour trouver les exécutables sur les nœuds distants (ceci n'est généralement nécessaire que dans les environnements basés sur rsh ou ssh - les environnements batch/planifiés copient généralement l'environnement actuel à l'exécution des jobs distants, donc si l'environnement actuel a PATH et/ou LD_LIBRARY_PATH correctement définis, les nœuds distants les auront également correctement définis). Si Open MPI a été compilé avec le support des bibliothèques partagées, il peut également être nécessaire de définir la variable d'environnement LD_LIBRARY_PATH sur les nœuds distants (surtout pour trouver les bibliothèques partagées nécessaires à l'exécution des applications MPI utilisateur).

Cependant, il n'est pas toujours souhaitable ou possible de modifier les fichiers de démarrage du shell pour définir PATH et/ou LD_LIBRARY_PATH. L'option --prefix est fournie pour certaines configurations simples où cela n'est pas possible.

L'option --prefix prend un seul argument : le répertoire de base sur le nœud distant où Open MPI est installé. Open MPI utilisera ce répertoire pour définir PATH et LD_LIBRARY_PATH sur le nœud distant avant d'exécuter toute application Open MPI ou utilisateur. Cela permet d'exécuter des jobs Open MPI sans avoir préconfiguré PATH et LD_LIBRARY_PATH sur les nœuds distants.

Open MPI ajoute le nom de base du $bindir du nœud actuel (le répertoire où les exécutables d'Open MPI ont été installés) au préfixe et utilise cela pour définir PATH sur le nœud distant. De même, Open MPI ajoute le nom de base du $libdir du nœud actuel (le répertoire où les bibliothèques d'Open MPI ont été installées) au préfixe et utilise cela pour définir LD_LIBRARY_PATH sur le nœud distant. Par exemple :

  • Bindir local : /local/node/directory/bin
  • Libdir local : /local/node/directory/lib64

Si la ligne de commande suivante est utilisée :

shell$ mpirun --prefix /remote/node/directory

Open MPI ajoutera /remote/node/directory/bin à PATH et /remote/node/directory/lib64 à LD_LIBRARY_PATH sur le nœud distant avant de tenter d'exécuter quoi que ce soit.

L'option --prefix n'est pas suffisante si les chemins d'installation sur le nœud distant sont différents de ceux du nœud local (par exemple, si /lib est utilisé sur le nœud local, mais /lib64 est utilisé sur le nœud distant), ou si les chemins d'installation sont autre chose qu'un sous-répertoire sous un préfixe commun.

Notez que l'exécution de mpirun via un chemin absolu est équivalente à la spécification de --prefix sans le dernier sous-répertoire du chemin absolu vers mpirun. Par exemple :

shell$ /usr/local/bin/mpirun ...

est équivalent à

shell$ mpirun --prefix /usr/local

Définition des paramètres MCA

Ce contenu est-il toujours actuel / précis ? Doit-il être mis à jour et conservé, ou supprimé ?

Le commutateur --mca permet de passer des paramètres à divers modules MCA (Modular Component Architecture). Les modules MCA ont un impact direct sur les programmes MPI car ils permettent de définir des paramètres ajustables à l'exécution (comme le pilote de périphérique de communication BTL à utiliser, les paramètres à passer à ce BTL, etc.).

Le commutateur --mca prend deux arguments : <key> et <value>. L'argument <key> spécifie généralement quel module MCA recevra la valeur. Par exemple, la <key> btl est utilisée pour sélectionner le BTL à utiliser pour le transport des messages MPI. L'argument <value> est la valeur qui est passée. Par exemple :

shell$ mpirun --mca btl tcp,self -n 1 my_mpi_app

Ceci indique à Open MPI d'utiliser les BTL tcp et self, et d'exécuter une seule copie de my_mpi_app sur un nœud alloué.

shell$ mpirun --mca btl self -n 1 my_mpi_app

Indique à Open MPI d'utiliser le BTL self, et d'exécuter une seule copie de my_mpi_app sur un nœud alloué.

Le commutateur --mca peut être utilisé plusieurs fois pour spécifier différents arguments <key> et/ou <value>. Si la même <key> est spécifiée plus d'une fois, les <value> sont concaténées avec une virgule (,) pour les séparer.

Exécution en tant que root

Ce contenu est-il toujours d'actualité / exact ? Doit-il être mis à jour et conservé, ou supprimé ?

ATTENTION :

L'équipe d'Open MPI déconseille fortement d'exécuter mpirun en tant qu'utilisateur root. Les applications MPI doivent être exécutées en tant qu'utilisateurs normaux (non root).

mpirun refusera de s'exécuter en tant que root par défaut.

Pour outrepasser ce comportement par défaut, vous pouvez ajouter l'option --allow-run-as-root à la ligne de commande mpirun, ou vous pouvez définir les paramètres environnementaux OMPI_ALLOW_RUN_AS_ROOT=1 et OMPI_ALLOW_RUN_AS_ROOT_CONFIRM=1. Notez qu'il faut définir deux variables d'environnement pour obtenir le même comportement que --allow-run-as-root afin de souligner le fort conseil de l'équipe d'Open MPI contre l'exécution en tant qu'utilisateur root.

Après de longues discussions avec les communautés qui utilisent des conteneurs (où l'exécution en tant qu'utilisateur root est par défaut), il y a eu un désir persistant de pouvoir activer l'exécution root de mpirun via un contrôle environnemental (par opposition au paramètre de ligne de commande existant --allow-run-as-root). Le compromis d'utiliser deux variables d'environnement a été atteint : il permet l'exécution root via un contrôle environnemental, mais il transmet la forte recommandation de l'équipe d'Open MPI contre ce comportement.

Statut de sortie

Ceci est un contenu ancien et codé en dur

Ce contenu est-il toujours d'actualité / exact ? Doit-il être mis à jour et conservé, ou supprimé ?

Il n'y a pas de définition standard de ce que mpirun doit retourner comme statut de sortie. Après mûre réflexion, nous avons choisi la méthode suivante pour attribuer le statut de sortie de mpirun (note : dans la description suivante, le job « primaire » est l'application initiale lancée par mpirun — tous les jobs qui sont générés par ce job sont désignés comme jobs « secondaires ») :

  • Si tous les processus du job primaire se terminent normalement avec un statut de sortie de 0, mpirun retourne 0.
  • Si un ou plusieurs processus du job primaire se terminent normalement avec un statut de sortie non nul, mpirun retourne le statut de sortie du processus ayant le rang MPI_COMM_WORLD le plus bas et ayant un statut non nul.
  • Si tous les processus du job primaire se terminent normalement avec un statut de sortie de 0, et qu'un ou plusieurs processus d'un job secondaire se terminent normalement avec un statut de sortie non nul, mpirun :
1.
Retourne le statut de sortie du processus ayant le rang MPI_COMM_WORLD le plus bas dans le jobid le plus bas ayant un statut non nul, et
2.
Affiche un message résumant le statut de sortie du job primaire et de tous les jobs secondaires.
•
Si l'option de ligne de commande --report-child-jobs-separately est définie, nous retournerons uniquement le statut de sortie du job primaire. Tout statut de sortie non nul dans les jobs secondaires sera uniquement signalé dans un message récapitulatif.

Par défaut, le job sera interrompu lorsque tout processus se terminera avec un statut non nul. Le paramètre MCA --prtemca state_base_error_non_zero_exit peut être défini à « false » (ou « 0 ») pour que Open MPI n'interrompe pas un job si un ou plusieurs processus retournent un statut non nul. Dans ce cas, Open MPI enregistre et note que les processus se sont terminés avec un statut de terminaison non nul afin de retourner le statut de sortie approprié de mpirun (conformément aux points ci-dessus).

VALEUR DE RETOUR

Ceci est un contenu ancien et codé en dur

Ce contenu est-il toujours d'actualité / exact ? Doit-il être mis à jour et conservé, ou supprimé ?

mpirun retourne 0 si tous les processus démarrés par mpirun se terminent après avoir appelé MPI_FINALIZE(3). Une valeur non nulle est retournée si une erreur interne s'est produite dans mpirun, ou si un ou plusieurs processus se sont terminés avant d'avoir appelé MPI_FINALIZE(3). Si une erreur interne s'est produite dans mpirun, le code d'erreur correspondant est retourné. Dans le cas où un ou plusieurs processus se terminent avant d'avoir appelé MPI_FINALIZE(3), la valeur de retour du rang MPI_COMM_WORLD du processus que mpirun détecte en premier comme étant mort avant d'appeler MPI_FINALIZE(3) sera retournée. Il est à noter que, en général, ce sera le premier processus mort, mais ce n'est pas garanti.

Si l'option de ligne de commande --timeout est utilisée et que le délai expire avant que le job ne soit terminé (obligeant ainsi mpirun à tuer le job), mpirun retournera un statut de sortie équivalent à la valeur de ETIMEDOUT (qui est généralement 110 sur les systèmes Linux et OS X).
