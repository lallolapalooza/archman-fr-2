MARIADB-BINLOG(1) Système de base de données MariaDB MARIADB-BINLOG(1)

NOM

mariadb-binlog - utilitaire pour le traitement des fichiers de journal binaire (mariadb-binlog est maintenant un lien symbolique vers mariadb-binlog)

SYNTAXE

mariadb-binlog [options] fichier_journal ...

DESCRIPTION

Le journal binaire du serveur se compose de fichiers contenant des "événements" décrivant les modifications du contenu de la base de données. Le serveur écrit ces fichiers au format binaire. Pour afficher leur contenu au format texte, utilisez l'utilitaire mariadb-binlog. Vous pouvez également utiliser mariadb-binlog pour afficher le contenu des fichiers de journal de relais écrits par un serveur esclave dans une configuration de réplication, car les journaux de relais ont le même format que les journaux binaires.

Invoquez mariadb-binlog comme suit :

shell> mariadb-binlog [options] fichier_journal ...

Par exemple, pour afficher le contenu du fichier de journal binaire nommé binlog.000003, utilisez cette commande :

shell> mariadb-binlog binlog.0000003

La sortie inclut les événements contenus dans binlog.000003. Pour la journalisation basée sur les instructions, les informations sur les événements incluent l'instruction SQL, l'ID du serveur sur lequel elle a été exécutée, l'horodatage de l'exécution de l'instruction, le temps qu'elle a pris, etc. Pour la journalisation basée sur les lignes, l'événement indique une modification de ligne plutôt qu'une instruction SQL.

Les événements sont précédés de commentaires d'en-tête qui fournissent des informations supplémentaires. Par exemple :

# at 141
#100309  9:28:36 server id 123  end_log_pos 245
  Query thread_id=3350  exec_time=11  error_code=0

Dans la première ligne, le nombre suivant "at" indique la position de début de l'événement dans le fichier du journal binaire.

La deuxième ligne commence par une date et une heure indiquant quand l'instruction a commencé sur le serveur où l'événement est originaire. Pour la réplication, cet horodatage est propagé aux serveurs esclaves. "server id" est la valeur server_id du serveur où l'événement est originaire. "end_log_pos" indique où commence l'événement suivant (c'est-à-dire la position de fin de l'événement courant + 1). "thread_id" indique quel thread a exécuté l'événement. "exec_time" est le temps passé à exécuter l'événement, sur un serveur maître. Sur un esclave, c'est la différence entre le temps d'exécution de fin sur l'esclave et le temps d'exécution de début sur le maître. La différence sert d'indicateur du décalage de réplication par rapport au maître. "error_code" indique le résultat de l'exécution de l'événement. Zéro signifie qu'aucune erreur ne s'est produite.

La sortie de mariadb-binlog peut être réexécutée (par exemple, en l'utilisant comme entrée pour mariadb) pour refaire les instructions dans le journal. Ceci est utile pour les opérations de récupération après un crash du serveur. Pour d'autres exemples d'utilisation, voir la discussion plus loin dans cette section.

Normalement, vous utilisez mariadb-binlog pour lire les fichiers de journal binaire directement et les appliquer au serveur MariaDB local. Il est également possible de lire les journaux binaires d'un serveur distant en utilisant l'option --read-from-remote-server. Pour lire les journaux binaires distants, les options de connexion peuvent être données pour indiquer comment se connecter au serveur. Ces options sont --host, --password, --port, --protocol, --socket et --user ; elles sont ignorées sauf lorsque vous utilisez également l'option --read-from-remote-server.

mariadb-binlog prend en charge les options suivantes, qui peuvent être spécifiées sur la ligne de commande ou dans les groupes d'options [mariadb-binlog] et [client].

•--help, -?

Affiche un message d'aide et quitte.

•--base64-output=valeur

Cette option détermine quand les événements doivent être affichés encodés en chaînes base-64 en utilisant des instructions BINLOG. L'option a les valeurs autorisées suivantes (insensible à la casse) :

•AUTO ("automatique") ou UNSPEC ("non spécifié") affiche automatiquement les instructions BINLOG lorsque nécessaire (c'est-à-dire pour les événements de description de format et les événements de ligne). C'est la valeur par défaut si aucune option --base64-output n'est fournie.

Note
L'affichage automatique BINLOG est le seul comportement sûr si vous avez l'intention d'utiliser la sortie de mariadb-binlog pour réexécuter le contenu des fichiers de journal binaire. Les autres valeurs d'option sont destinées uniquement à des fins de débogage ou de test, car elles peuvent produire une sortie qui n'inclut pas tous les événements sous forme exécutable.
•NEVER indique de ne pas afficher les instructions BINLOG. mariadb-binlog quitte avec une erreur si un événement de ligne est trouvé qui doit être affiché en utilisant BINLOG.
•DECODE-ROWS spécifie à mariadb-binlog que vous avez l'intention de décoder les événements de ligne et de les afficher comme des instructions SQL commentées en spécifiant également l'option --verbose. Comme NEVER, DECODE-ROWS supprime l'affichage des instructions BINLOG, mais contrairement à NEVER, il ne quitte pas avec une erreur si un événement de ligne est trouvé.
--base64-output peut être donné comme --base64-output ou --skip-base64-output (avec le sens de AUTO ou NEVER).

Pour des exemples montrant l'effet de --base64-output et --verbose sur la sortie des événements de ligne, voir la section appelée “AFFICHAGE DES ÉVÉNEMENTS DE LIGNE MARIADB-BINLOG”.

•--binlog-row-event-max-size=chemin

Le répertoire où sont installés les jeux de caractères.

•--character-sets-dir=chemin

Le répertoire où sont installés les jeux de caractères.

•--database=nom_db, -d nom_db

Cette option fait en sorte que mariadb-binlog affiche les entrées du journal binaire (journal local uniquement) qui se produisent pendant que nom_db a été sélectionné comme base de données par défaut par l'instruction USE.

L'option --database pour mariadb-binlog est similaire à l'option --binlog-do-db pour mariadbd, mais peut être utilisée pour spécifier une seule base de données. Si --database est donnée plusieurs fois, seule la dernière instance est utilisée.

Les effets de cette option dépendent du format de journalisation basé sur les instructions ou sur les lignes utilisé, de la même manière que les effets de --binlog-do-db dépendent du format de journalisation basé sur les instructions ou sur les lignes.

Journalisation basée sur les instructions. L'option --database fonctionne comme suit :

•Pendant que nom_db est la base de données par défaut, les instructions sont affichées qu'elles modifient des tables dans nom_db ou une base de données différente.
•À moins que nom_db ne soit sélectionné comme base de données par défaut, les instructions ne sont pas affichées, même si elles modifient des tables dans nom_db.
•Il y a une exception pour CREATE DATABASE, ALTER DATABASE et DROP DATABASE. La base de données en cours de création, de modification ou de suppression est considérée comme la base de données par défaut lors de la détermination de l'affichage de l'instruction.
Supposons que le journal binaire a été créé en exécutant ces instructions en utilisant la journalisation basée sur les instructions : 
INSERT INTO test.t1 (i) VALUES(100);
INSERT INTO db2.t2 (j)  VALUES(200);
USE test;
INSERT INTO test.t1 (i) VALUES(101);
INSERT INTO t1 (i)      VALUES(102);
INSERT INTO db2.t2 (j)  VALUES(201);
USE db2;
INSERT INTO test.t1 (i) VALUES(103);
INSERT INTO db2.t2 (j)  VALUES(202);
INSERT INTO t2 (j)      VALUES(203);

mariadb-binlog --database=test n'affiche pas les deux premières instructions INSERT car il n'y a pas de base de données par défaut. Il affiche les trois instructions INSERT suivant USE test, mais pas les trois instructions INSERT suivant USE db2.

mariadb-binlog --database=db2 n'affiche pas les deux premières instructions INSERT car il n'y a pas de base de données par défaut. Il n'affiche pas les trois instructions INSERT suivant USE test, mais affiche les trois instructions INSERT suivant USE db2.

Journalisation basée sur les lignes. mariadb-binlog n'affiche que les entrées qui modifient des tables appartenant à nom_db. La base de données par défaut n'a aucun effet sur cela. Supposons que le journal binaire décrit ci-dessus ait été créé en utilisant la journalisation basée sur les lignes plutôt que basée sur les instructions. mariadb-binlog --database=test n'affiche que les entrées qui modifient t1 dans la base de données test, indépendamment de l'utilisation de USE ou de la base de données par défaut. Si un serveur fonctionne avec binlog_format réglé sur MIXED et que vous voulez qu'il soit possible d'utiliser mariadb-binlog avec l'option --database, vous devez vous assurer que les tables qui sont modifiées se trouvent dans la base de données sélectionnée.

Le mot de passe à utiliser lors de la connexion au serveur. Si vous utilisez la forme courte de l'option (-p), vous ne pouvez *pas* laisser d'espace entre l'option et le mot de passe. Spécifier un mot de passe sur la ligne de commande doit être considéré comme non sécurisé. Vous pouvez utiliser un fichier d'options pour éviter de fournir le mot de passe sur la ligne de commande.

Le numéro de port TCP/IP à utiliser pour se connecter à un serveur distant, ou 0 pour utiliser par défaut, par ordre de préférence, my.cnf, $MYSQL_TCP_PORT, /etc/services, la valeur par défaut intégrée (3306). Force --protocol=tcp lorsqu'il est spécifié sur la ligne de commande sans autres propriétés de connexion.

Le protocole de connexion à utiliser pour se connecter au serveur. Il est utile lorsque les autres paramètres de connexion entraîneraient normalement l'utilisation d'un protocole autre que celui souhaité.

•--raw

Nécessite -R. Affiche les données brutes du binlog au lieu des instructions SQL. Les fichiers de sortie sont nommés d'après les journaux du serveur.

•--read-from-remote-server, -R

Lit le journal binaire à partir d'un serveur MariaDB au lieu de lire un fichier de journal local. Toutes les options de paramètre de connexion sont ignorées à moins que cette option ne soit également fournie. Ces options sont --host, --password, --port, --protocol, --socket et --user.

Cette option nécessite que le serveur distant soit en cours d'exécution. Elle ne fonctionne que pour les fichiers de journal binaire sur le serveur distant, pas pour les fichiers de journal relais.

•--result-file=nom, -r nom

Dirige la sortie vers le fichier donné. Avec --raw, il s'agit d'un préfixe pour les noms de fichiers.

•--rewrite-db=nom, -r nom

Met à jour une base de données avec un nom différent de l'original. Exemple : rewrite-db='from->to'. Pour les événements qui sont journalisés en tant qu'instructions, la réécriture de la base de données constitue la modification de la base de données par défaut d'une instruction de db1 à db2. Il n'y a pas d'analyse d'instruction ou de réécriture d'aucune sorte, c'est-à-dire que si l'on spécifie "db1.tbl" dans l'instruction explicitement, cette occurrence ne sera pas changée en "db2.tbl". Les événements basés sur les lignes sont correctement réécrits pour utiliser le nouveau nom de base de données. Le filtrage (par exemple avec --database=nom) se produit après que les réécritures de base de données ont été effectuées. Si vous utilisez cette option sur la ligne de commande et que ">" a une signification spéciale pour votre interpréteur de commandes, mettez la valeur entre guillemets (par exemple --rewrite-db="ancien_nom->nouveau_nom".

•--server-id=id

Affiche uniquement les événements créés par le serveur ayant l'ID de serveur donné.

•--set-charset=nom_jeu_caracteres

Ajoute une instruction SET NAMES nom_jeu_caracteres à la sortie pour spécifier le jeu de caractères à utiliser pour le traitement des fichiers journaux.

•--short-form, -s

Affiche uniquement les instructions contenues dans le journal, aucune information supplémentaire et aucun événement basé sur les lignes. Ceci est destiné uniquement aux tests et ne doit pas être utilisé dans les systèmes de production. Si vous souhaitez supprimer la sortie base64, envisagez d'utiliser --base64-output=never à la place.

•--socket=chemin, -S chemin

Pour les connexions à localhost, le fichier de socket Unix à utiliser, ou, sous Windows, le nom du pipe nommé à utiliser. Force --protocol=socket lorsqu'il est spécifié sur la ligne de commande sans autres propriétés de connexion ; sous Windows, force --protocol=pipe.

•--start-datetime=datetime

Commence à lire le journal binaire au premier événement ayant un horodatage égal ou postérieur à l'argument datetime. La valeur datetime est relative au fuseau horaire local de la machine où vous exécutez mariadb-binlog. La valeur doit être dans un format accepté pour les types de données DATETIME ou TIMESTAMP. Par exemple :

shell> mariadb-binlog --start-datetime="2014-12-25 11:25:56" binlog.000003

Cette option est utile pour la récupération à un point dans le temps.

•--start-position=N, -j N

Commence à lire le journal binaire à la position N. Le type peut être un entier positif ou une liste GTID. En utilisant un entier positif, la valeur ne s'applique qu'au premier binlog passé sur la ligne de commande, et le premier événement dont la position est égale ou supérieure à N est imprimé. En mode GTID, plusieurs GTID peuvent être passés sous forme de liste séparée par des virgules, où chacun doit avoir un identifiant de domaine unique. La liste représente l'état du binlog gtid dont le client (un autre serveur « réplique ») est conscient. Par conséquent, chaque GTID est exclusif ; seuls les événements après un numéro de séquence donné seront imprimés pour permettre aux utilisateurs de recevoir les événements après leur état actuel.

Cette option est utile pour la récupération à un point dans le temps.

•--gtid-strict-mode

Traite le binlog conformément à la spécification gtid-strict-mode. Les positions de début et de fin sont vérifiées pour satisfaire la condition de comparaison start < stop. Les numéros de séquence de tout domaine gtid doivent constituer une séquence monotiquement croissante.

•--stop-datetime=datetime

Arrête la lecture du journal binaire au premier événement dont l'horodatage est égal ou postérieur à l'argument datetime. Cette option est utile pour la récupération à un point dans le temps. Voir la description de l'option --start-datetime pour des informations sur la valeur datetime.

Cette option est utile pour la récupération à un point dans le temps.

•--stop-never-slave-server-id

•--stop-position=N

Arrête la lecture du journal binaire au premier événement dont la position est égale ou supérieure à N. Le type peut être un entier positif ou une liste GTID. En utilisant un entier positif, la valeur ne s'applique qu'au dernier fichier journal nommé sur la ligne de commande. En mode GTID, plusieurs GTID peuvent être passés sous forme de liste séparée par des virgules, où chacun doit avoir un identifiant de domaine unique. Chaque GTID est inclusif ; seuls les événements jusqu'aux numéros de séquence donnés sont imprimés.

Cette option est utile pour la récupération à un point dans le temps.

•open_files_limit

Spécifie le nombre de descripteurs de fichiers ouverts à réserver.

Vous pouvez rediriger la sortie de mariadb-binlog vers le client mariadb pour exécuter les événements contenus dans le journal binaire. Cette technique est utilisée pour récupérer d'un crash lorsque vous avez une ancienne sauvegarde. Par exemple:

shell> mariadb-binlog binlog.000001 | mariadb -u root -p

Ou:

shell> mariadb-binlog binlog.[0-9]* | mariadb -u root -p

Vous pouvez également rediriger la sortie de mariadb-binlog vers un fichier texte, si vous avez besoin de modifier d'abord le journal des instructions (par exemple, pour supprimer des instructions que vous ne souhaitez pas exécuter pour une raison quelconque). Après avoir modifié le fichier, exécutez les instructions qu'il contient en l'utilisant comme entrée pour le programme mariadb:

shell> mariadb-binlog binlog.000001 > tmpfile
shell> ... éditer tmpfile ...
shell> mariadb -u root -p < tmpfile

Lorsque mariadb-binlog est invoqué avec l'option --start-position, il affiche uniquement les événements dont le décalage dans le journal binaire est supérieur ou égal à une position donnée (la position donnée doit correspondre au début d'un événement). Il dispose également d'options pour s'arrêter et démarrer lorsqu'il rencontre un événement avec une date et une heure données. Cela vous permet d'effectuer une récupération à un point précis dans le temps en utilisant l'option --stop-datetime (pour pouvoir dire, par exemple, « rembobinez mes bases de données à l'état où elles étaient aujourd'hui à 10h30 »).

Si vous avez plus d'un journal binaire à exécuter sur le serveur MariaDB, la méthode sûre consiste à les traiter tous en utilisant une seule connexion au serveur. Voici un exemple qui démontre ce qui peut être dangereux:

shell> mariadb-binlog binlog.000001 | mariadb -u root -p # DANGER !!
shell> mariadb-binlog binlog.000002 | mariadb -u root -p # DANGER !!

Traiter les journaux binaires de cette manière en utilisant différentes connexions au serveur pose des problèmes si le premier fichier journal contient une instruction CREATE TEMPORARY TABLE et que le second journal contient une instruction qui utilise la table temporaire. Lorsque le premier processus mariadb se termine, le serveur supprime la table temporaire. Lorsque le second processus mariadb tente d'utiliser la table, le serveur signale « table inconnue ».

Pour éviter de tels problèmes, utilisez un seul processus mariadb pour exécuter le contenu de tous les journaux binaires que vous souhaitez traiter. Voici une façon de le faire:

shell> mariadb-binlog binlog.000001 binlog.000002 | mariadb -u root -p

Une autre approche consiste à écrire tous les journaux dans un seul fichier, puis à traiter le fichier:

shell> mariadb-binlog binlog.000001 >  /tmp/statements.sql
shell> mariadb-binlog binlog.000002 >> /tmp/statements.sql
shell> mariadb -u root -p -e "source /tmp/statements.sql"

mariadb-binlog peut produire une sortie qui reproduit une opération LOAD DATA INFILE sans le fichier de données d'origine. mariadb-binlog copie les données dans un fichier temporaire et écrit une instruction LOAD DATA LOCAL INFILE qui fait référence au fichier. L'emplacement par défaut du répertoire où ces fichiers sont écrits est spécifique au système. Pour spécifier explicitement un répertoire, utilisez l'option --local-load.

Étant donné que mariadb-binlog convertit les instructions LOAD DATA INFILE en instructions LOAD DATA LOCAL INFILE (c'est-à-dire qu'il ajoute LOCAL), le client et le serveur que vous utilisez pour traiter les instructions doivent être configurés avec la capacité LOCAL activée.


Attention

Les fichiers temporaires créés pour les instructions LOAD DATA LOCAL ne sont pas automatiquement supprimés car ils sont nécessaires jusqu'à ce que vous exécutiez réellement ces instructions. Vous devez supprimer vous-même les fichiers temporaires après ne plus avoir besoin du journal des instructions. Les fichiers se trouvent dans le répertoire des fichiers temporaires et ont des noms tels que nom_fichier_original-#-#.

FORMAT HEXADUMP DE MARIADB-BINLOG

L'option --hexdump amène mariadb-binlog à produire un vidage hexadécimal du contenu du journal binaire:

shell> mariadb-binlog --hexdump master-bin.000001

La sortie hexadécimale se compose de lignes de commentaires commençant par #, donc la sortie pourrait ressembler à ceci pour la commande précédente:

/*!40019 SET @@session.max_delayed_threads=0*/;
/*!50003 SET @OLD_COMPLETION_TYPE=@@COMPLETION_TYPE,COMPLETION_TYPE=0*/;
# at 4
#051024 17:24:13 server id 1  end_log_pos 98
# Position  Timestamp   Type   Master ID        Size      Master Pos    Flags
# 00000004 9d fc 5c 43   0f   01 00 00 00   5e 00 00 00   62 00 00 00   00 00

AFFICHAGE DES ÉVÉNEMENTS DE LIGNE MARIADB-BINLOG

Les exemples suivants illustrent comment mariadb-binlog affiche les événements de ligne qui spécifient des modifications de données. Ceux-ci correspondent aux événements avec les codes de type WRITE_ROWS_EVENT, UPDATE_ROWS_EVENT et DELETE_ROWS_EVENT. Les options --base64-output=DECODE-ROWS et --verbose peuvent être utilisées pour affecter la sortie des événements de ligne.

Supposons que le serveur utilise la journalisation binaire basée sur les lignes et que vous exécutiez la séquence d'instructions suivante :

CREATE TABLE t
(
  id   INT NOT NULL,
  name VARCHAR(20) NOT NULL,
  date DATE NULL
) ENGINE = InnoDB;
START TRANSACTION;
INSERT INTO t VALUES(1, 'pomme', NULL);
UPDATE t SET name = 'poire', date = '2009-01-01' WHERE id = 1;
DELETE FROM t WHERE id = 1;
COMMIT;

Par défaut, mariadb-binlog affiche les événements de ligne encodés sous forme de chaînes base-64 en utilisant des instructions BINLOG. En omettant les lignes superflues, la sortie pour les événements de ligne produits par la séquence d'instructions précédente ressemble à ceci :

Remarque

Vous ne devez pas supprimer les instructions BINLOG si vous avez l'intention de ré-exécuter la sortie de mariadb-binlog.

Les instructions SQL produites par --verbose pour les événements de ligne sont beaucoup plus lisibles que les instructions BINLOG correspondantes. Cependant, elles ne correspondent pas exactement aux instructions SQL d'origine qui ont généré les événements. Les limitations suivantes s'appliquent :

•Les noms de colonnes d'origine sont perdus et remplacés par @N, où N est un numéro de colonne.
•Les informations de jeu de caractères ne sont pas disponibles dans le journal binaire, ce qui affecte l'affichage des colonnes de chaîne :
•Aucune distinction n'est faite entre les types de chaînes binaires et non binaires correspondants (BINARY et CHAR, VARBINARY et VARCHAR, BLOB et TEXT). La sortie utilise un type de données STRING pour les chaînes de longueur fixe et VARSTRING pour les chaînes de longueur variable.
•Pour les jeux de caractères multioctets, le nombre maximum d'octets par caractère n'est pas présent dans le journal binaire, de sorte que la longueur des types de chaînes est affichée en octets plutôt qu'en caractères. Par exemple, STRING(4) sera utilisé comme type de données pour les valeurs provenant de l'un ou l'autre de ces types de colonnes : 
CHAR(4) CHARACTER SET latin1
CHAR(2) CHARACTER SET ucs2
•En raison du format de stockage des événements de type UPDATE_ROWS_EVENT, les instructions UPDATE sont affichées avec la clause WHERE précédant la clause SET.

L'interprétation correcte des événements de ligne nécessite les informations de l'événement de description de format au début du journal binaire. Comme mariadb-binlog ne sait pas à l'avance si le reste du journal contient des événements de ligne, il affiche par défaut l'événement de description de format en utilisant une instruction BINLOG dans la partie initiale de la sortie.

Si le journal binaire est connu pour ne contenir aucun événement nécessitant une instruction BINLOG (c'est-à-dire aucun événement de ligne), l'option --base64-output=NEVER peut être utilisée pour empêcher l'écriture de cet en-tête.
