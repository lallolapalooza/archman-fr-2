MAILX(1P) Manuel du programmeur POSIX MAILX(1P)

PROLOG

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consultez la page de manuel Linux correspondante pour les détails du comportement sous Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

mailx — traiter les messages

SYNTAXE

Mode Envoi

mailx [-s sujet] adresse...

Mode Réception

mailx -e
mailx [-HiNn] [-F] [-u utilisateur]
mailx -f [-HiNn] [-F] [fichier]

DESCRIPTION

L'utilitaire mailx fournit une facilité d'envoi et de réception de messages. Il possède deux modes principaux, sélectionnés par les options utilisées : Mode Envoi et Mode Réception.

Sur les systèmes qui ne supportent pas l'option Utilitaires de Portabilité Utilisateur, une application utilisant mailx doit pouvoir envoyer des messages d'une manière non spécifiée (Mode Envoi). Sauf si le premier caractère d'une ou plusieurs lignes est une <virgule> ('~'), tous les caractères du message d'entrée doivent apparaître dans le message délivré, mais des caractères supplémentaires peuvent être insérés dans le message avant qu'il ne soit récupéré.

Sur les systèmes supportant l'option Utilitaires de Portabilité Utilisateur, les capacités de réception de courrier et d'autres fonctionnalités interactives, le Mode Réception, décrit ci-dessous, doit également être activé.

Mode Envoi

Le Mode Envoi peut être utilisé par les applications ou les utilisateurs pour envoyer des messages à partir du texte de l'entrée standard.

Mode Réception

Le Mode Réception est davantage orienté vers les utilisateurs interactifs. Le courrier peut être lu et envoyé dans ce mode interactif.

Lors de la lecture du courrier, mailx fournit des commandes pour faciliter la sauvegarde, la suppression et la réponse aux messages. Lors de l'envoi de courrier, mailx permet l'édition, la révision et d'autres modifications du message tel qu'il est saisi.

Le courrier entrant doit être stocké dans un ou plusieurs emplacements non spécifiés pour chaque utilisateur, collectivement appelés la boîte aux lettres système pour cet utilisateur. Lorsque mailx est invoqué en Mode Réception, la boîte aux lettres système est l'endroit par défaut pour trouver le nouveau courrier. Au fur et à mesure de la lecture des messages, ils seront marqués pour être déplacés vers un fichier secondaire pour stockage, sauf action spécifique entreprise. Ce fichier secondaire est appelé le mbox et est normalement situé dans le répertoire référencé par la variable d'environnement HOME (voir MBOX dans la section VARIABLES D'ENVIRONNEMENT pour une description de ce fichier). Les messages resteront dans ce fichier jusqu'à ce qu'ils soient explicitement supprimés. Lorsque l'option -f est utilisée pour lire des messages à partir de fichiers secondaires, les messages seront conservés dans ces fichiers sauf s'ils sont explicitement supprimés. Ces trois emplacements — boîte aux lettres système, mbox et fichier secondaire — sont désignés dans cette section simplement comme « boîtes aux lettres », sauf si une identification plus spécifique est requise.

OPTIONS

L'utilitaire mailx doit être conforme au volume Définitions de Base de POSIX.1‐2017, Section 12.2, Directives de syntaxe des utilitaires.

Les options suivantes doivent être supportées. (Seule l'option -s sujet est requise sur tous les systèmes. Les autres options ne sont requises que sur les systèmes supportant l'option Utilitaires de Portabilité Utilisateur.)

-e
Vérifie la présence de courrier dans la boîte aux lettres système. L'utilitaire mailx n'écrira rien et quittera avec un code de retour de succès s'il y a du courrier à lire.
-f
Lit les messages du fichier nommé par l'opérande fichier au lieu de la boîte aux lettres système. (Voir aussi folder.) Si aucun opérande fichier n'est spécifié, lit les messages de mbox au lieu de la boîte aux lettres système.
-F
Enregistre le message dans un fichier nommé d'après le premier destinataire. Le nom est la partie nom de connexion de l'adresse trouvée en premier sur la ligne To: dans l'en-tête du courrier. Remplace la variable record, si elle est définie (voir Variables Internes dans mailx).
-H
Écrit uniquement un résumé d'en-tête.
-i
Ignore les interruptions. (Voir aussi ignore.)
-n
N'initialise pas à partir du fichier de démarrage par défaut du système. Voir la section DESCRIPTION ÉTENDUE.
-N
N'écrit pas de résumé d'en-tête initial.
-s sujet
Définit le champ d'en-tête Subject à sujet. Tous les caractères de la chaîne sujet doivent apparaître dans le message délivré. Les résultats ne sont pas spécifiés si sujet est plus long que {LINE_MAX} - 10 octets ou contient un <nouvelle ligne>.
-u utilisateur
Lit la boîte aux lettres système de l'utilisateur nommé utilisateur. Cela ne réussira que si l'utilisateur appelant dispose des privilèges appropriés pour lire la boîte aux lettres système de cet utilisateur.

OPÉRANDES

Les opérandes suivants doivent être supportés :

adresse
Destinataire du message. Lorsque -n est spécifié et qu'aucun fichier de démarrage utilisateur n'est accédé (voir la section DESCRIPTION ÉTENDUE), l'utilisateur ou l'application doit s'assurer qu'il s'agit d'une adresse à passer au système de livraison de courrier. Tous les fichiers de démarrage système ou utilisateur peuvent activer des alias (voir alias sous Commandes dans mailx) qui peuvent modifier la forme de adresse avant qu'elle ne soit passée au système de livraison de courrier.
fichier
Un chemin de fichier à lire au lieu de la boîte aux lettres système lorsque -f est spécifié. La signification de l'argument d'option fichier sera affectée par le contenu de la variable interne folder ; voir Variables Internes dans mailx.

STDIN

Lorsque mailx est invoqué en Mode Envoi (la première ligne de syntaxe), l'entrée standard doit être le message à livrer aux adresses spécifiées. En Mode Réception, les commandes utilisateur doivent être acceptées depuis stdin. Si l'option Utilitaires de Portabilité Utilisateur n'est pas supportée, les lignes d'entrée standard commençant par un caractère <virgule> ('~') produisent des résultats non spécifiés.

Si l'option Utilitaires de Portabilité Utilisateur est supportée, alors dans les Modes Envoi et Réception, les lignes d'entrée standard commençant par le caractère d'échappement (généralement <virgule> ('~')) affecteront le traitement tel que décrit dans Échappements de commandes dans mailx.

FICHIERS D'ENTRÉE

Lorsque mailx est utilisé comme décrit par ce volume de POSIX.1‐2017, l'argument d'option fichier (voir l'option -f) et le mbox doivent être des fichiers texte contenant des messages de courrier, formatés comme décrit dans la section FICHIERS DE SORTIE. La nature de la boîte aux lettres système n'est pas spécifiée ; elle n'a pas besoin d'être un fichier.

VARIABLES D'ENVIRONNEMENT

Certaines des fonctionnalités décrites dans cette section doivent être fournies sur les implémentations qui supportent l'option Utilitaires de Portabilité Utilisateur comme décrit dans le texte, et ne sont pas davantage signalées pour cette option.

Les variables d'environnement suivantes affecteront l'exécution de mailx :

DEAD
Détermine le chemin du fichier dans lequel enregistrer les messages partiels en cas d'interruptions ou d'erreurs de livraison. La valeur par défaut est dead.letter dans le répertoire nommé par la variable HOME. Le comportement de mailx lors de l'enregistrement de messages partiels n'est pas spécifié si l'option Utilitaires de Portabilité Utilisateur n'est pas supportée et que DEAD n'est pas défini avec la valeur /dev/null.
EDITOR
Détermine le nom
f une commande utilitaire à appeler lorsque la commande edit (voir Commandes dans mailx) ou ~e (voir Échappements de commande dans mailx) est utilisée. L'éditeur par défaut n'est pas spécifié. Sur les systèmes conformes à XSI, il s'agit de ed. Les effets de cette variable ne sont pas spécifiés si l'option Utilitaires de portabilité utilisateurs n'est pas prise en charge.
HOME
Détermine le chemin d'accès du répertoire personnel de l'utilisateur.
LANG
Fournit une valeur par défaut pour les variables d'internationalisation qui sont non définies ou vides. (Voir le volume Définitions de base de POSIX.1‐2017, Section 8.2, Variables d'internationalisation pour la précédence des variables d'internationalisation utilisées pour déterminer les valeurs des catégories de locale.)
LC_ALL
Si défini à une chaîne non vide, remplace les valeurs de toutes les autres variables d'internationalisation.
LC_CTYPE
Détermine la locale pour l'interprétation des séquences d'octets de données textuelles en caractères (par exemple, caractères mono-octet par opposition aux caractères multi-octets dans les arguments et les fichiers d'entrée) et la gestion des comparaisons de noms d'adresses et de champs d'en-tête insensibles à la casse.
LC_TIME
Cette variable peut déterminer le format et le contenu des chaînes de date et d'heure écrites par mailx. Ce volume de POSIX.1‐2017 ne spécifie les effets de cette variable que pour les systèmes prenant en charge l'option Utilitaires de portabilité utilisateurs.
LC_MESSAGES

Détermine la locale qui doit être utilisée pour affecter le format et le contenu des messages de diagnostic écrits sur la sortie standard d'erreur et des messages informatifs écrits sur la sortie standard.
LISTER
Détermine une chaîne représentant la commande pour écrire le contenu du répertoire folder sur la sortie standard lorsque la commande folders est donnée (voir folders dans Commandes dans mailx). Toute chaîne acceptable comme opérande command_string pour la commande sh -c sera valide. Si cette variable est vide ou non définie, la commande de sortie sera ls. Les effets de cette variable ne sont pas spécifiés si l'option Utilitaires de portabilité utilisateurs n'est pas prise en charge.
MAILRC
Détermine le chemin d'accès du fichier de démarrage utilisateur. La valeur par défaut sera .mailrc dans le répertoire référencé par la variable d'environnement HOME. Le comportement de mailx n'est pas spécifié si l'option Utilitaires de portabilité utilisateurs n'est pas prise en charge et que MAILRC n'est pas défini avec la valeur /dev/null.
MBOX
Détermine un chemin d'accès au fichier pour enregistrer les messages de la boîte aux lettres système qui ont été lus. La commande exit remplacera cette fonction, tout comme l'enregistrement explicite du message dans un autre fichier. La valeur par défaut sera mbox dans le répertoire nommé par la variable HOME. Les effets de cette variable ne sont pas spécifiés si l'option Utilitaires de portabilité utilisateurs n'est pas prise en charge.
NLSPATH
Détermine l'emplacement des catalogues de messages pour le traitement de LC_MESSAGES.
PAGER
Détermine une chaîne représentant une commande de filtrage de sortie ou de pagination pour écrire la sortie sur le terminal. Toute chaîne acceptable comme opérande command_string pour la commande sh -c sera valide. Lorsque la sortie standard est un périphérique terminal, la sortie des messages sera dirigée via la commande si la variable interne mailx crt est définie à une valeur inférieure au nombre de lignes du message ; voir Variables internes dans mailx. Si la variable PAGER est vide ou non définie, le paginateur sera soit more, soit une autre utilitaire de pagination documenté dans la documentation du système. Les effets de cette variable ne sont pas spécifiés si l'option Utilitaires de portabilité utilisateurs n'est pas prise en charge.
SHELL
Détermine le nom d'un interpréteur de commandes préféré. La valeur par défaut sera sh. Les effets de cette variable ne sont pas spécifiés si l'option Utilitaires de portabilité utilisateurs n'est pas prise en charge.
TERM
Si la variable interne screen n'est pas spécifiée, détermine le nom du type de terminal pour indiquer d'une manière non spécifiée le nombre de lignes d'un écran d'en-têtes. Si TERM n'est pas défini ou est défini à vide, un type de terminal par défaut non spécifié sera utilisé et la valeur d'un écran est non spécifiée. Les effets de cette variable ne sont pas spécifiés si l'option Utilitaires de portabilité utilisateurs n'est pas prise en charge.
TZ
Cette variable peut déterminer le fuseau horaire utilisé pour calculer les chaînes de date et d'heure écrites par mailx. Si TZ est non défini ou vide, un fuseau horaire par défaut non spécifié sera utilisé.
VISUAL
Détermine un chemin d'accès à une utilitaire à appeler lorsque la commande visual (voir Commandes dans mailx) ou l'échappement de commande ~v (voir Échappements de commande dans mailx) est utilisé. Si cette variable est vide ou non définie, l'éditeur plein écran sera vi. Les effets de cette variable ne sont pas spécifiés si l'option Utilitaires de portabilité utilisateurs n'est pas prise en charge.

ÉVÉNEMENTS ASYNCHRONES

Lorsque mailx est en mode Envoi et que l'entrée standard n'est pas un terminal, il prendra l'action standard pour tous les signaux.

En mode Réception, ou en mode Envoi lorsque l'entrée standard est un terminal, si un signal SIGINT est reçu :

1.
En mode commande, la commande en cours, s'il y en a une, sera abandonnée, et une invite de mode commande sera affichée.
2.
En mode saisie :
a.
Si ignore est défini, mailx affichera "@\n", ignorera la ligne de saisie actuelle et continuera le traitement, en contournant le mécanisme d'abandon de message décrit au point 2b.
b.
Si l'interruption a été reçue lors de l'envoi d'un courrier, que ce soit en mode Réception ou en mode Envoi, un message sera affiché, et une autre interruption ultérieure, sans autre caractère intermédiaire tapé, sera requise pour abandonner le message électronique. Si en mode Réception et une autre interruption est reçue, une invite de mode commande sera affichée. Si en mode Envoi et une autre interruption est reçue, mailx se terminera avec un statut non nul.

Dans les deux cas mentionnés au point b, si le message n'est pas vide :

i.
Si save est activé et que le fichier nommé par DEAD peut être créé, le message sera écrit dans le fichier nommé par DEAD. Si le fichier existe, le message sera écrit pour remplacer le contenu du fichier.
ii.
Si save n'est pas activé, ou si le fichier nommé par DEAD ne peut pas être créé, le message ne sera pas sauvegardé.

L'utilitaire mailx prendra l'action standard pour tous les autres signaux.

STDOUT

En mode commande et en mode saisie, toutes les sorties, y compris les invites et les messages, seront écrites sur la sortie standard.

STDERR

La sortie standard d'erreur ne sera utilisée que pour les messages diagnostiques.

FICHIERS DE SORTIE

Diverses commandes et échappements de commande mailx peuvent créer ou ajouter des fichiers, y compris la mbox, le fichier de brouillon et les boîtes aux lettres secondaires. Lorsque mailx est utilisé comme décrit dans ce volume de POSIX.1‐2017, ces fichiers seront des fichiers texte, formatés comme suit :

ligne commençant par From<espace>
[une ou plusieurs lignes d'en-tête ; voir Commandes dans mailx]
ligne vide
[zéro ou plusieurs lignes de corps
ligne vide]
[ligne commençant par From<espace>...]

où chaque message commence par la ligne From <espace> indiquée, précédée du début du fichier ou d'une ligne vide. (La ligne From <espace> est considérée comme faisant partie de l'en-tête du message, mais pas comme l'une des lignes d'en-tête visées dans Commandes dans mailx ; par conséquent, elle ne sera pas affectée par les commandes discard, ignore ou retain.) Les formats du reste de la ligne From <espace> et de toutes les lignes d'en-tête supplémentaires ne sont pas spécifiés, à l'exception qu'aucune ne doit être vide. Le format d'une ligne de corps de message n'est pas non plus spécifié, à l'exception qu'aucune ligne suivant une ligne vide ne doit commencer par From <espace> ; mailx modifiera toute ligne de corps de message entrée par l'utilisateur (suivant une ligne vide et commençant par From <espace>) en ajoutant un ou plusieurs caractères pour précéder le 'F' ; il peut ajouter ces caractères aux lignes From <espace> qui ne sont pas précédées d'une ligne vide.

Lorsqu'un message de la boîte aux lettres système ou saisi par l'utilisateur n'est pas un fichier texte, il est défini par l'implémentation comment un tel message est stocké dans les fichiers écrits par mailx.

DESCRIPTION ÉTENDUE

La fonctionnalité de toute la section DESCRIPTION ÉTENDUE sera fournie sur les implémentations prenant en charge l'option Utilitaires de portabilité utilisateurs. La fonctionnalité décrite dans cette section sera fournie sur les implémentations qui prennent en charge l'option Utilitaires de portabilité utilisateurs (et le reste de cette section n'est pas davantage ombré pour cette option).

L'utilitaire mailx n'a pas besoin de prendre en charge tous les encodages de caractères dans toutes les circonstances. Par exemple, le courrier inter-systèmes peut être limité aux données 7 bits par le réseau sous-jacent, les données 8 bits n'ont pas besoin d'être portables vers les systèmes non internationalisés, etc. Dans ces circonstances, il est recommandé de n'utiliser que les caractères définis dans la plage de caractères de 7 bits de la version de référence internationale (équivalente à ASCII) de la norme ISO/IEC 646:1991.

Lorsque mailx est invoqué en utilisant l'une des formes de synopsis du mode de réception, il écrit une page de lignes d'en-tête et de résumé (si -N n'a pas été spécifié et s'il y a des messages, voir ci- dessous), suivie d'une invite indiquant que mailx peut accepter des commandes normales (voir Commandes dans mailx) ; ceci est appelé le mode commande. La page de lignes d'en-tête et de résumé contient le premier nouveau message s'il y en a, ou le premier message non lu s'il y en a, ou le premier message. Lorsque mailx est invoqué en utilisant la synopsis du mode d'envoi et que l'entrée standard est un terminal, si aucun sujet n'est spécifié sur la ligne de commande et que la variable asksub est définie, une invite pour le sujet est écrite. À ce stade, mailx est en mode de saisie. Ce mode de saisie est également entré lors de l'utilisation de l'une des formes de synopsis du mode de réception et qu'une réponse ou un nouveau message est composé à l'aide des commandes reply, Reply, followup, Followup ou mail et que l'entrée standard est un terminal. Lorsque le message est tapé et que la fin du message est rencontrée, le message est transmis au logiciel de distribution de courrier. Les commandes peuvent être entrées en commençant une ligne par le caractère d'échappement (par défaut, le <tilde> ('~')) suivi d'une seule lettre de commande et d'arguments optionnels. Voir Commandes dans mailx pour un résumé de ces commandes. Il n'est pas spécifié quel effet ces commandes auront si l'entrée standard n'est pas un terminal lorsqu'un message est entré en utilisant soit la synopsis du mode d'envoi, soit les commandes du mode de lecture reply, Reply, followup, Followup ou mail.

Note :
Pour des raisons de commodité de notation, cette section utilise le caractère d'échappement par défaut, <tilde>, dans toutes les références et tous les exemples.

À tout moment, le comportement de mailx est régi par un ensemble de variables environnementales et internes. Ce sont des drapeaux et des paramètres à valeur qui peuvent être définis et effacés via les commandes mailx set et unset.

Les commandes normales sont de la forme :

[commande] [liste_msg] [argument ...]

Si aucune commande n'est spécifiée en mode commande, next est supposé. En mode de saisie, les commandes sont reconnues par le caractère d'échappement, et les lignes qui ne sont pas traitées comme des commandes sont considérées comme des entrées pour le message.

En mode commande, chaque message se voit attribuer un numéro séquentiel, commençant à 1.

Tous les messages ont un état qui affecte la manière dont ils sont affichés dans le résumé d'en-tête et comment ils sont conservés ou supprimés lors de la terminaison de mailx. Il existe à tout moment la notion de message courant, qui est marqué par un '>' au début d'une ligne dans le résumé d'en-tête. Lorsque mailx est invoqué en utilisant l'une des formes de synopsis du mode de réception, le message courant est le premier nouveau message, s'il y en a un, ou le premier message non lu s'il y en a un, ou le premier message s'il y en a, ou non spécifié s'il n'y a pas de messages dans la boîte aux lettres. Chaque commande qui prend une liste optionnelle de messages (liste_msg) ou un message optionnel unique (message) sur lequel opérer laisse le message courant défini sur le message le plus numéroté des messages spécifiés, à moins que la commande ne supprime des messages, auquel cas le message courant est défini sur le premier message non supprimé (c'est-à-dire un message qui n'est pas dans l'état supprimé) après le message le plus numéroté supprimé par la commande, s'il en existe un, ou le premier message non supprimé avant le message le plus numéroté supprimé par la commande, s'il en existe un, ou à une valeur non spécifiée s'il n'y a plus de messages non supprimés. Tous les messages sont dans l'un des états suivants :

nouveau
Le message est présent dans la boîte aux lettres système et n'a pas été vu par l'utilisateur ni déplacé vers un autre état. Les messages à l'état nouveau lorsque mailx se termine sont conservés dans la boîte aux lettres système.
non lu
Le message est présent dans la boîte aux lettres système depuis plus d'une invocation de mailx et n'a pas été vu par l'utilisateur ni déplacé vers un autre état. Les messages à l'état non lu lorsque mailx se termine sont conservés dans la boîte aux lettres système.
lu
Le message a été traité par l'une des commandes suivantes : ~f, ~m, ~F, ~M, copy, mbox, next, pipe, print, Print, top, type, Type, undelete. Les commandes delete, dp et dt peuvent également marquer le message suivant comme lu, en fonction de la valeur de la variable autoprint. Les messages qui se trouvent dans la boîte aux lettres système et à l'état lu lorsque mailx se termine sont enregistrés dans mbox, à moins que la variable interne hold n'ait été définie. Les messages qui se trouvent dans mbox ou dans une boîte aux lettres secondaire et à l'état lu lorsque mailx se termine sont conservés à leur emplacement actuel.
supprimé
Le message a été traité par l'une des commandes suivantes : delete, dp, dt. Les messages à l'état supprimé lorsque mailx se termine sont supprimés. Les messages supprimés sont ignorés jusqu'à ce que mailx se termine ou change de boîte aux lettres ou qu'ils soient spécifiés à la commande undelete ; par exemple, la spécification de message /chaîne ne recherche que les lignes d'objet des messages qui n'ont pas encore été supprimés, à moins que la commande opérant sur la liste des messages ne soit undelete. Aucun message supprimé ni en-tête de message supprimé ne sont affichés par aucune commande mailx autre que undelete.
préservé
Le message a été traité par une commande preserve. Lorsque mailx se termine, le message est conservé à son emplacement actuel.
enregistré
Le message a été traité par l'une des commandes suivantes : save ou write. Si la boîte aux lettres courante est la boîte aux lettres système, et que la variable interne keepsave est définie, les messages à l'état enregistré sont enregistrés dans le fichier désigné par la variable MBOX (voir la section VARIABLES D'ENVIRONNEMENT). Si la boîte aux lettres courante est la boîte aux lettres système, les messages à l'état enregistré sont supprimés de la boîte aux lettres courante, lorsque la commande quit ou file est utilisée pour quitter la boîte aux lettres courante.

La ligne d'en-tête et de résumé pour chaque message indique l'état du message.

De nombreuses commandes acceptent une liste optionnelle de messages (liste_msg) sur laquelle opérer, qui par défaut est le message courant. Une liste_msg est une liste de spécifications de message séparées par des caractères <espace>, qui peut inclure :

n
Numéro de message n.
+
Le prochain message non supprimé, ou le prochain message supprimé pour la commande undelete.
-
Le précédent message non supprimé, ou le précédent message supprimé pour la commande undelete.
.
Le message courant.
^
Le premier message non supprimé, ou le premier message supprimé pour la commande undelete.
$
Le dernier message.
*
Tous les messages.
n‐m
Une plage inclusive de numéros de message.
adresse
Tous les messages provenant de adresse ; toute adresse telle qu'elle apparaît dans un résumé d'en-tête sera correspondante sous cette forme.
/chaîne
Tous les messages contenant chaîne dans la ligne d'objet (sensible à la casse ignoré).
:c
Tous les messages de type c, où c est l'un des éléments suivants :
d
Messages supprimés.
n
Nouveaux messages.
o
Messages anciens (tous ceux qui ne sont pas à l'état lu ou nouveau).
r
Messages lus.
u
Messages non lus.

D'autres commandes acceptent un message optionnel (message) sur lequel opérer, qui par défaut est le message courant. Toutes les formes autorisées pour liste_msg sont également autorisées pour message, mais si plus d'un message est spécifié, seul le premier sera traité.

Les autres arguments sont généralement des chaînes arbitraires dont l'utilisation dépend de la commande concernée.

Démarrage dans mailx

Au démarrage, mailx effectue les étapes suivantes dans l'ordre :

1.
Établit toutes les variables à leurs valeurs par défaut indiquées.
2.

Une ligne vide dans un fichier de démarrage est ignorée.

Variables internes dans mailx

Les variables suivantes sont des variables internes de mailx. Chaque variable interne peut être définie via la commande mailx set à tout moment. Les commandes unset et set no nom effacent ou désactivent la variable.

VARIABLES

The following variables can be used to control the behavior of mailx. Boolean variables can be set and unset using the syntax set variable and unset variable, respectively. Variables that take values are set using the syntax set variable=value. Setting a variable with no value or using the unset command can be used to erase variables.

In the following list, variables shown as:

variable

represent Boolean values. Variables shown as:

variable=value

shall be assigned string or numeric values. For string values, the rules in Commands in mailx concerning filenames and quoting shall also apply.

The defaults specified here may be changed by the unspecified system start-up file unless the user specifies the -n option.

allnet
All network names whose login name components match shall be treated as identical. This shall cause the msglist message specifications to behave similarly. The default shall be noallnet. See also the alternates command and the metoo variable.
append
Append messages to the end of the mbox file upon termination instead of placing them at the beginning. The default shall be noappend. This variable shall not affect the save command when saving to mbox.
ask, asksub
Prompt for a subject line on outgoing mail if one is not specified on the command line with the -s option. The ask and asksub forms are synonyms; the system shall refer to asksub and noasksub in its messages, but shall accept ask and noask as user input to mean asksub and noasksub. It shall not be possible to set both ask and noasksub, or noask and asksub. The default shall be asksub, but no prompting shall be done if standard input is not a terminal.
askbcc
Prompt for the blind copy list. The default shall be noaskbcc.
askcc
Prompt for the copy list. The default shall be noaskcc.
autoprint
Enable automatic writing of messages after delete and undelete commands. The default shall be noautoprint.
bang
Enable the special-case treatment of <exclamation-mark> characters ('!') in escape command lines; see the escape command and Command Escapes in mailx. The default shall be nobang, disabling the expansion of '!' in the command argument to the ~! command and the ~<!command escape.
cmd=command

Set the default command to be invoked by the pipe command. The default shall be nocmd.
crt=number
Pipe messages having more than number lines through the command specified by the value of the PAGER variable. The default shall be nocrt. If it is set to null, the value used is implementation-defined.
debug
Enable verbose diagnostics for debugging. Messages are not delivered. The default shall be nodebug.
dot
When dot is set, a <period> on a line by itself during message input from a terminal shall also signify end-of-file (in addition to normal end-of-file). The default shall be nodot. If ignoreeof is set (see below), a setting of nodot shall be ignored and the <period> is the only method to terminate input mode.
escape=c
Set the command escape character to be the character 'c'. By default, the command escape character shall be <tilde>. If escape is unset, <tilde> shall be used; if it is set to null, command escaping shall be disabled.
flipr
Reverse the meanings of the R and r commands. The default shall be noflipr.
folder=directory

The default directory for saving mail files. User-specified filenames beginning with a <plus-sign> ('+') shall be expanded by preceding the filename with this directory name to obtain the real pathname. If directory does not start with a <slash> ('/'), the contents of HOME shall be prefixed to it. The default shall be nofolder. If folder is unset or set to null, user-specified filenames beginning with '+' shall refer to files in the current directory that begin with the literal '+' character. See also outfolder below. The folder value need not affect the processing of the files named in MBOX and DEAD.
header
Enable writing of the header summary when entering mailx in Receive Mode. The default shall be header.
hold
Preserve all messages that are read in the system mailbox instead of putting them in the mbox save file. The default shall be nohold.
ignore
Ignore interrupts while entering messages. The default shall be noignore.
ignoreeof
Ignore normal end-of-file during message input. Input can be terminated only by entering a <period> ('.') on a line by itself or by the ~. command escape. The default shall be noignoreeof. See also dot above.
indentprefix=string

A string that shall be added as a prefix to each line that is inserted into the message by the ~m command escape. This variable shall default to one <tab>.
keep
When a system mailbox, secondary mailbox, or mbox is empty, truncate it to zero length instead of removing it. The default shall be nokeep.
keepsave
Keep the messages that have been saved from the system mailbox into other files in the file designated by the variable MBOX, instead of deleting them. The default shall be nokeepsave.
metoo
Suppress the deletion of the login name of the user from the recipient list when replying to a message or sending to a group. The default shall be nometoo.
onehop
When responding to a message that was originally sent to several recipients, the other recipient addresses are normally forced to be relative to the originating author's machine for the response. This flag disables alteration of the recipients' addresses, improving efficiency in a network where all machines can send directly to all other machines (that is, one hop away). The default shall be noonehop.
outfolder
Cause the files used to record outgoing messages to be located in the directory specified by the folder variable unless the pathname is absolute. The default shall be nooutfolder. See the record variable.
page
Insert a <form-feed> after each message sent through the pipe created by the pipe command. The default shall be nopage.
prompt=string

Set the command-mode prompt to string. If string is null or if noprompt is set, no prompting shall occur. The default shall be to prompt with the string "? ".
quiet
Refrain from writing the opening message and version when entering mailx. The default shall be noquiet.
record=file
Record all outgoing mail in the file with the pathname file. The default shall be norecord. See also outfolder above.
save
Enable saving of messages in the dead-letter file on interrupt or delivery error. See the variable DEAD for the location of the dead-letter file. The default shall be save.
screen=number

Set the number of lines in a screenful of headers for the headers and z commands. If screen is not specified, a value based on the terminal type identified by the TERM environment variable, the window size, the baud rate, or some combination of these shall be used.
sendwait
Wait for the background mailer to finish before returning. The default shall be nosendwait.
showto
When the sender of the message was the user who is invoking mailx, write the information from the To: line instead of the From: line in the header summary. The default shall be noshowto.
sign=string
Set the variable inserted into the text of a message when the ~a command escape is given. The default shall be nosign. The character sequences '\t' and '\n' shall be recognized in the variable as <tab> and <newline> characters, respectively. (See also ~i in Command Escapes in mailx.)
Sign=string
Set the variable inserted into the text of a message when the ~A command escape is given. The default shall be noSign. The character sequences '\t' and '\n' shall be recognized in the variable as <tab> and <newline> characters, respectively.
toplines=number

Set the number of lines of the message to write with the top command. The default shall be 5.

Pour chacune des commandes listées ci-dessous, la commande peut être entrée sous forme d'abréviation (les caractères du mot de commande du Synopsis précédant le [), la commande complète (tous les caractères indiqués pour le mot de commande, omettant le [ et ]), ou toute troncature de la commande complète jusqu'à l'abréviation. Par exemple, la commande exit (affichée sous la forme ex[it] dans le Synopsis) peut être entrée sous la forme ex, exi, ou exit.

Les arguments des commandes peuvent être cités, en utilisant les méthodes suivantes :

  • Un argument peut être entouré de guillemets doubles ("") ou simples ('') ; tout espace blanc, expansion de mots shell, ou caractères <backslash> à l'intérieur des guillemets sera traité littéralement comme faisant partie de l'argument. Un guillemet double sera traité littéralement à l'intérieur de guillemets simples et vice versa. Ces propriétés spéciales des caractères <guillemets> ne se produiront que lorsqu'ils sont appariés au début et à la fin de l'argument.
  • Un <backslash> en dehors des guillemets fermants sera supprimé et le caractère suivant sera traité littéralement comme faisant partie de l'argument.
  • Un <backslash> non cité à la fin d'une ligne de commande sera supprimé et la ligne suivante continuera la commande.

Les noms de fichiers, lorsqu'ils sont attendus, seront soumis aux transformations suivantes, dans l'ordre :

  • Si le nom de fichier commence par un <signe plus> non cité, et que la variable folder est définie (voir la variable folder), le <signe plus> sera remplacé par la valeur de la variable folder suivie d'un <slash>. Si la variable folder est désactivée ou définie à une chaîne nulle, le nom de fichier ne sera pas modifié.
  • Les expansions de mots shell seront appliquées au nom de fichier (voir la Section 2.6, Expansions de mots). Si plus d'un chemin résulte de cette expansion et que la commande attend un seul fichier, les effets ne sont pas spécifiés.

Échappements de commande dans mailx

Les commandes suivantes ne peuvent être entrées qu'en mode saisie, en commençant une ligne par le caractère d'échappement (par défaut, le <tilde> ('~')). Voir la description de la variable escape pour modifier ce caractère spécial. Le format des commandes sera :

<caractère-échappement><caractère-commande><séparateur>[<arguments>]

où le <séparateur> peut être zéro ou plusieurs caractères <blanc>.

Dans les descriptions suivantes, l'application s'assurera que l'argument commande (mais pas mailx-commande) est une chaîne de commande shell. Toute chaîne acceptable par l'interpréteur de commandes spécifié par la variable SHELL lorsqu'il est invoqué comme SHELL -c chaîne_commande sera valide. La commande peut être présentée comme plusieurs arguments (c'est-à-dire que le guillemet n'est pas requis).

Les échappements de commande qui sont listés avec des arguments msglist ou mailx-command sont invalides en Mode Envoi et produisent des résultats non spécifiés.

STATUT DE SORTIE

Lorsque l'option -e est spécifiée, les valeurs de sortie suivantes sont retournées :

 0
Courrier trouvé.
>0
Courrier non trouvé ou une erreur s'est produite.

Sinon, les valeurs de sortie suivantes sont retournées :

 0
Achèvement réussi ; noter que ce statut implique que tous les messages ont été envoyés, mais il ne donne aucune assurance qu'ils ont été effectivement délivrés.
>0
Une erreur s'est produite.

UTILISATION APPLICATIVE

La livraison de messages vers des systèmes distants nécessite l'existence de chemins de communication vers ces systèmes. Ceux-ci peuvent ne pas exister.

Les lignes d'entrée sont limitées à {LINE_MAX} octets, mais les routeurs de messagerie entre systèmes peuvent imposer des restrictions de longueur de ligne plus sévères. Ce volume de POSIX.1‐2017 ne place aucune restriction sur la longueur des messages traités par mailx, et pour la livraison de messages locaux, les seules limitations devraient être les problèmes habituels d'espace disque disponible pour le fichier de courrier de destination. Lors de l'envoi de messages à des machines externes, il est conseillé aux applications de limiter les messages à moins de 100000 octets car certaines passerelles de messagerie imposent des restrictions de longueur de message.

Le format de la boîte aux lettres système est intentionnellement non spécifié. Tous les systèmes n'implémentent pas les boîtes aux lettres système comme des fichiers plats, en particulier avec l'avènement des messages multimédias. Certaines boîtes aux lettres système peuvent être des fichiers multiples, d'autres des enregistrements dans une base de données. Le format interne des messages eux-mêmes est spécifié avec le format historique de la Version 7, mais uniquement après que les messages aient été sauvegardés dans un fichier autre que la boîte aux lettres système. Cela a été fait pour que de nombreuses applications historiques attendant des boîtes aux lettres de fichiers texte ne soient pas rompues.

De nouveaux formats de messages sont attendus à l'avenir, incluant probablement des données binaires, des images matricielles et divers objets multimédias. Tel que décrit ici, mailx n'est pas interdit de traiter de tels messages, mais il doit les stocker sous forme de fichiers texte dans des boîtes aux lettres secondaires (à moins qu'une extension, telle qu'une variable ou une option de ligne de commande, ne soit utilisée pour modifier le format stocké). Sa méthode pour ce faire est définie par l'implémentation et pourrait inclure la traduction des données sous une forme compatible ou lisible par fichier texte, ou l'omission de certaines parties du message.

RATIONALE

Les développeurs de la norme estimaient fermement qu'une méthode permettant aux applications d'envoyer des messages à des utilisateurs spécifiques était nécessaire. L'exemple évident est un utilitaire de traitement par lots, fonctionnant de manière non interactive, qui souhaite communiquer des erreurs ou des résultats à un utilisateur. Cependant, le format réel, le mécanisme de livraison et la méthode de lecture du message sont clairement en dehors du champ d'application de ce volume de POSIX.1-2017.

L'intention de cette commande est de fournir une interface simple et portable pour envoyer des messages de manière non interactive. Elle définit simplement un « frontal » au système de messagerie historique. Il est suggéré que les implémentations indiquent explicitement l'expéditeur et le destinataire dans le corps du message livré. D'autres spécifications de formats pour l'enveloppe du message ou pour le message lui-même n'ont pas été délibérément faites, car l'industrie est en train de passer des normes actuelles à une norme plus internationalisée et il est probablement incorrect, à ce moment, d'en exiger l'une ou l'autre.

Les implémentations sont encouragées à se conformer aux divers mécanismes de livraison décrits dans les normes CCITT X.400 ou aux normes Internet équivalentes, décrites dans les documents Internet Request for Comment (RFC) RFC 819, RFC 920, RFC 921, RFC 1123 et RFC 5322 (qui a succédé à RFC 822).

De nombreux systèmes historiques modifiaient chaque ligne du corps commençant par From en ajoutant un '>' avant le 'F'. Il est inutile, mais autorisé, de le faire lorsque la chaîne ne suit pas une ligne vide car elle ne peut pas être confondue avec l'en-tête suivant.

Les commandes edit et visual modifient simplement les messages spécifiés dans un fichier temporaire. Elles ne modifient pas le contenu de ces messages dans la boîte aux lettres ; une telle capacité pourrait être ajoutée comme une extension, par exemple en utilisant des noms de commandes différents.

La restriction selon laquelle la ligne d'objet ne doit pas dépasser {LINE_MAX}-10 octets est basée sur le format historique qui consomme 10 octets pour Subject: et le saut de ligne final. De nombreux systèmes de messagerie historiques que le message peut rencontrer sur d'autres systèmes ne sont pas capables de gérer des lignes aussi longues.

Comme les utilitaires logger et lp, mailx est certes difficile à tester. Cela n'a pas été jugé une justification suffisante pour exclure cet utilitaire de ce volume de POSIX.1-2017. On peut également soutenir qu'il est, en fait, testable, mais que les tests eux-mêmes ne sont pas portables.

Lorsque mailx est utilisé par une application qui souhaite recevoir les résultats comme si aucune des fonctionnalités de l'option User Portability Utilities n'était prise en charge, la variable d'environnement DEAD doit être définie sur /dev/null. Sinon, elle peut être soumise aux créations de fichiers décrites dans les ÉVÉNEMENTS ASYNCHRONES de mailx. De même, si la variable d'environnement MAILRC n'est pas définie sur /dev/null, les versions historiques de mailx et Mail lisent les commandes d'initialisation à partir d'un fichier avant le début du traitement. Étant donné que l'initialisation spécifiée par un utilisateur pourrait modifier le contenu des messages qu'une application essaie d'envoyer, de telles applications doivent définir MAILRC sur /dev/null.

La description de LC_TIME utilise « peut affecter » car de nombreuses implémentations historiques ne peuvent pas ou ne savent pas manipuler les chaînes de date et d'heure dans les en-têtes de messagerie entrants. Certains en-têtes trouvés dans les courriers entrants ne contiennent pas suffisamment d'informations pour déterminer le fuseau horaire d'origine du courrier et, par conséquent, mailx ne peut pas convertir les chaînes de date et d'heure en la forme interne qui est ensuite analysée par des routines comme strftime() qui peuvent prendre en compte les paramètres LC_TIME. La modification de toutes ces heures dans un format spécifié par l'utilisateur est autorisée, mais pas obligatoire.

Le paginateur sélectionné lorsque PAGER est nul ou non défini est partiellement non spécifié pour permettre la pratique historique de System V consistant à utiliser pg par défaut. Contourner la fonction de pagination, par exemple en déclarant que cat est le paginateur, ne correspondrait pas au sens voulu de cette description. Cependant, tout « utilisateur portable » devrait explicitement définir PAGER pour obtenir son paginateur préféré sur tous les systèmes. Le choix du paginateur a été rendu partiellement non spécifié, contrairement au choix de l'éditeur VISUAL (qui doit obligatoirement être vi) car la plupart des paginateurs historiques suivent un thème commun d'interaction utilisateur, tandis que les éditeurs diffèrent dramatiquement.

Les options pour spécifier des adresses comme cc (copie carbone) ou bcc (copie carbone invisible) ont été considérées comme des détails de format et ont été omises.

Un statut de sortie nul implique que tous les messages ont été envoyés, mais il ne donne aucune garantie qu'ils ont été effectivement livrés. La fiabilité du mécanisme de livraison n'est pas spécifiée et constitue une distinction marketing appropriée entre les systèmes.

Afin de se conformer aux Directives de Syntaxe des Utilitaires, une solution était requise pour l'argument optionnel file de -f. En faisant de file un opérande, les directives sont satisfaites et les utilisateurs restent portables. Cependant, cela oblige les implémentations à prendre en charge l'utilisation comme suit :

mailx -fin mymail.box

La méthode no nom pour désactiver les variables n'est pas présente sur tous les systèmes historiques, mais elle l'est sur System V et fournit un ensemble logique de commandes correspondant au format d'affichage des options de la commande set de mailx sans arguments.

Les variables ask et asksub sont les noms sélectionnés par BSD et System V, respectivement, pour la même fonctionnalité. Ce sont des synonymes dans ce volume de POSIX.1-2017.

La commande echo de mailx n'a pas été documentée dans la version BSD et a été omise ici car elle n'est pas manifestement utile pour les utilisateurs interactifs.

L'invite par défaut sur le mailx de System V est un <point d'interrogation>, sur Mail de BSD un <esperluette>. Étant donné que ce volume de POSIX.1-2017 a choisi le nom mailx, il a conservé la valeur par défaut de System V, en supposant que les utilisateurs BSD n'auraient pas de difficulté avec cette légère incompatibilité (qu'ils peuvent outrepasser).

Les significations de r et R sont inversées entre le mailx de System V et le Mail de SunOS. Encore une fois, étant donné que ce volume de POSIX.1-2017 a choisi le nom mailx, il a conservé la valeur par défaut de System V, mais permet à l'utilisateur SunOS d'obtenir les résultats souhaités en utilisant flipr, une variable interne de mailx de System V, bien qu'elle n'ait pas été documentée dans le SVID.

La variable indentprefix, les commandes retain et unalias, ainsi que les échappements de commande ~F et ~M ont été adoptés du Mail 4.3 BSD.

La commande version n'a pas été incluse car aucune spécification suffisamment générale des informations de version n'a pu être conçue pour être encore utile à un utilisateur portable. Ce nom de commande doit être utilisé par les fournisseurs qui souhaitent fournir des informations sur la version de la commande mailx.

Le « fichier de démarrage système spécifique à l'implémentation (non spécifié) » a historiquement été nommé /etc/mailx.rc, mais ce nom et cet emplacement spécifiques ne sont pas requis.

L'intention de la formulation de la commande next est que si une commande a déjà affiché le message actuel, elle doit afficher un message suivant, mais, sinon, elle doit afficher le message actuel. Considérez la séquence de commandes :

next 3
delete 3
next

où l'option autoprint n'était pas définie. Le texte normatif spécifie que la deuxième commande next doit afficher un message suivant le troisième message, car même si le message actuel n'a pas été affiché depuis qu'il a été défini par la commande delete, il a été affiché depuis que le message actuel était autre que le message numéro 3. Cela ne correspond pas toujours à la pratique historique de certaines implémentations, où l'adresse du fichier de commande suivie de next (ou de la commande par défaut) sautait le message pour lequel l'utilisateur avait recherché.
