MAKEHISTORY(8) Documentation InterNetNews MAKEHISTORY(8)

NOM

makehistory - Initialiser ou reconstruire la base de données de l'historique INN

SYNTAXE

makehistory [-abFIOSx] [-f nomfichier] [-l compteur] [-L charge-moyenne] [-s taille] [-T rep_temporaire]

DESCRIPTION

makehistory reconstruit le fichier texte d'history(5), qui contient une liste des ID de message des articles déjà vus par le serveur. Il peut aussi être utilisé pour reconstruire la base de données d'aperçu. Notez que même si les index dbz du fichier history sont également reconstruits par makehistory, il est utile d'exécuter makedbz(8) après makehistory afin d'améliorer l'efficacité des index (makehistory ne sait pas quelle taille donner à la table de hachage lors de la première exécution, sauf si la taille est donnée par l'indicateur -s).

L'emplacement par défaut du fichier texte history est pathdb/history ; pour spécifier un emplacement alternatif, utilisez l'indicateur -f.

Par défaut, makehistory scanne l'ensemble du spool, en utilisant le gestionnaire de stockage, et écrit une ligne d'historique pour chaque article. Pour générer également des informations d'aperçu, utilisez l'indicateur -O.

Si un article malformé est trouvé dans le spool de news, d'une manière qui empêche son intégration dans les données d'historique ou d'aperçu, une ligne de journal sera affichée et l'article malform est simplement ignoré.

RECONSTRUCTION APERÇU

AVERTISSEMENT: Si vous essayez de reconstruire la base de données d'aperçu, assurez-vous d'arrêter innd(8) et de supprimer ou de mettre à zéro la base de données existante avant de commencer pour obtenir les meilleurs résultats. Une reconstruction d'aperçu ne doit pas être effectuée pendant que le serveur est en cours d'exécution. À moins que l'aperçu existant ne soit supprimé, vous pourriez rencontrer des problèmes tels que des entrées d'aperçu dans le désordre, des tampons d'aperçu excessivement volumineux, etc.

Si ovmethod dans inn.conf est "ovdb", vous devez avoir les processus ovdb en cours d'exécution lors de la reconstruction de l'aperçu. ovdb en a besoin pendant l'écriture des entrées d'aperçu. Vous pouvez les démarrer manuellement séparément du reste du serveur en exécutant ovdb_init ; voir ovdb_init(8) pour plus de détails.

De même, si ovmethod dans inn.conf est "ovsqlite", vous devez avoir le processus ovsqlite-server en cours d'exécution lors de la reconstruction de l'aperçu. Voir ovsqlite-server(8) pour plus de détails et comment le démarrer manuellement.

Reconstruire les données d'aperçu est aussi simple que :

1.
Vérifier que le fichier de configuration de la nouvelle méthode de stockage d'aperçu est présent dans pathetc et correspond à vos besoins (buffindexed.conf, ovdb.conf ou ovsqlite.conf). Notez que la méthode de stockage d'aperçu tradindexed n'a pas de fichier de configuration dédié.
2.
S'assurer que INN est arrêté ("rc.news stop" en tant qu'utilisateur news, ou quelle que soit la commande que vous utilisez).
3.
Définir la nouvelle méthode de stockage d'aperçu dans le paramètre ovmethod de inn.conf.
4.
S'assurer que le répertoire spécifié par le paramètre pathoverview dans inn.conf existe et est vide (ou contient des tampons buffindexed fraîchement créés, si vous utilisez cette méthode de stockage d'aperçu). Sinon, renommez le répertoire actuel (pour sauvegarder les données d'aperçu existantes) et recréez pathoverview en tant qu'utilisateur news.
5.
Démarrer ovdb_init ou ovsqlite-server en tant qu'utilisateur news si la nouvelle méthode de stockage d'aperçu est respectivement ovdb ou ovsqlite.
6.
Exécuter "makehistory -O -x -F" et attendre que la commande se termine. (Vous pourriez remarquer quelques journaux concernant des articles pour lesquels les données d'aperçu ne peuvent pas être insérées dans la nouvelle méthode de stockage d'aperçu. Tant qu'il n'y en a pas des tonnes, c'est normal, notamment parce qu'il y a une limite interne à la longueur des données d'aperçu générées par makehistory, contrairement à innd. Malheureusement, ces rares articles ne seront pas présents dans le nouvel aperçu.)
7.
Arrêter les programmes d'assistance ovdb ou ovsqlite si vous les avez démarrés lors des étapes précédentes (l'exécution de "rc.news stop" en tant qu'utilisateur news les arrêtera ; ne vous inquiétez pas des messages concernant le fait que le serveur news n'était pas en cours d'exécution).
8.
Démarrer INN et vérifier les journaux pour s'assurer que tout va bien. Vous remarquerez normalement que le fichier active est renuméroté (rc.news s'en charge lorsqu'il est exécuté après une reconstruction d'aperçu ; sinon, exécutez manuellement "ctlinnd renumber ''").

OPTIONS

-a
Ajouter à la fin du fichier history plutôt que d'en générer un nouveau. Si vous ajoutez à la fin du fichier history principal, assurez-vous que innd(8) est ralenti ou arrêté, sinon vous risquez de corrompre l'historique.
-b
Supprimer tout message trouvé dans le spool qui ne possède pas de champ d'en-tête Message-ID valide.
-F
Créer un processus séparé pour écrire les données d'aperçu sur le disque plutôt que de le faire directement. L'avantage est que cela permet à makehistory de continuer à collecter plus de données du spool pendant que le premier lot de données est écrit dans la base de données d'aperçu. L'inconvénient est que jusqu'à deux fois plus d'espace disque temporaire sera utilisé pour les données d'aperçu générées. Cette option n'a de sens qu'en combinaison avec -O. Avec buffindexed, le programme overchan est appelé pour écrire l'aperçu.
-f nomfichier
Plutôt que d'écrire directement dans pathdb/history, écrire plutôt dans nomfichier, également dans pathdb.
-I
Ne pas stocker les données d'aperçu pour les articles numérotés inférieurement au numéro d'article le plus bas dans active. Ceci est utile s'il existe pour une raison quelconque de vieux articles sur disque qui ne devraient pas être accessibles aux lecteurs ou inclus dans la base de données d'aperçu.
-l compteur
Cette option spécifie combien d'articles traiter avant d'écrire les informations d'aperçu accumulées dans la base de données d'aperçu. La valeur par défaut est 10000. Comme la performance d'écriture de l'aperçu est meilleure avec des données triées, chaque "lot" est trié. Augmenter la taille du lot avec cette option peut améliorer davantage les performances d'écriture, au prix de temps de tri plus longs. De plus, de l'espace temporaire sera nécessaire pour stocker les lots d'aperçu. À une estimation grossière, environ 300 * compteur octets d'espace temporaire seront requis (sans compter les fichiers temporaires créés par sort(1)). Voir la description de l'option -T pour savoir comment spécifier l'emplacement de stockage temporaire. Cette option n'a aucun effet avec buffindexed, car buffindexed n'a pas besoin d'un aperçu trié et aucun batching n'est effectué.
-L charge-moyenne
Pause temporaire des activités si la charge moyenne du système dépasse le niveau spécifié charge-moyenne. Cela permet à makehistory de s'exécuter sur un système utilisé à d'autres fins sans monopoliser les ressources système et rendre ainsi le temps de réponse des autres applications inacceptablement lent. L'utilisation de nice(1) n'aide pas beaucoup car le problème vient de l'utilisation des E/S disque, et ionice(1) n'est pas toujours disponible ou efficace.
-O
Créer également la base de données d'aperçu en plus du fichier history. Les informations d'aperçu ne sont requises que si le serveur prend en charge les lecteurs ; elles ne sont pas nécessaires pour un serveur de transit uniquement (voir enableoverview dans inn.conf(5)). Si vous utilisez la méthode de stockage d'aperçu buffindexed, effacez tous vos tampons d'aperçu avant d'exécuter makehistory avec -O.
-S
Plutôt que de stocker les données d'aperçu dans la base de données d'aperçu, les écrire simplement sur la sortie standard sous une forme appropriée pour être fournie à overchan ultérieurement si souhaité. Lorsque cette option est utilisée, -F,

-I, -l et -T sont ignorés. Cette option n'a de sens qu'en combinaison avec -O.
-s taille
Dimensionne la base de données d'historique pour environ taille paires clé-valeur (c'est-à-dire des lignes dans history). Spécifier la taille avec précision est une optimisation qui créera une base de données plus efficace. (La taille devrait être le nombre estimé d'articles éventuels, typiquement la taille de l'ancien fichier history, en lignes.)

Par défaut, makehistory créera une base de données optimisée pour gérer environ 6 000 000 d'articles (ou 500 000 si le format de hachage marqué, plus lent, est utilisé). Cette taille ne limite pas le nombre d'articles que le serveur de news peut stocker dans son fichier history. Il deviendra simplement plus lent lorsque cette taille optimale sera dépassée, jusqu'à la prochaine exécution de news.daily qui le redimensionnera de manière appropriée.

-T tmpdir
Si -O est donné, makehistory a besoin d'un emplacement pour écrire des données temporaires d'aperçu. Par défaut, il utilise pathtmp, défini dans inn.conf, mais si cette option est donnée, le tmpdir fourni est utilisé à la place. Ceci est également utilisé pour les fichiers temporaires créés par sort(1) (qui est invoqué dans le processus d'écriture des informations d'aperçu car les informations d'aperçu triées s'écrivent plus rapidement). Par défaut, sort utilise généralement votre répertoire temporaire système ; consultez la page de manuel sort(1) sur votre système pour en être sûr.
-x
Si cette option est donnée, makehistory n'écrira pas d'entrées de fichier history. Ceci est utile principalement pour construire un aperçu sans générer un nouveau fichier history.

EXEMPLES

Voici un exemple typique de reconstruction de l'intégralité de la base de données d'historique et d'aperçu, en supprimant les articles corrompus dans le spool de news. Ceci utilise les emplacements de fichiers temporaires par défaut et doit être effectué pendant que innd n'est pas en cours d'exécution (ou est ralenti).

makehistory -b -f history.n -O -l 30000 -I

Ceci reconstruira l'aperçu (si vous utilisez buffindexed, effacez les tampons d'aperçu existants avant d'exécuter cette commande) et laissera un nouveau fichier history sous le nom "history.n" dans pathdb. Pour préserver toutes les entrées d'historique de l'ancien fichier history qui correspondent aux articles rejetés ou expirés, suivez la commande ci-dessus avec :

cd <pathdb>
awk 'NF == 2 { print }' < history >> history.n

(en remplaçant le chemin par votre pathdb, s'il n'est pas celui par défaut). Ensuite, examinez le nouveau fichier history pour d'éventuels problèmes et exécutez :

makedbz -s `wc -l < history.n` -f history.n

Ensuite, renommez tous les fichiers correspondant à "history.n.*" en "history.*", en remplaçant la base de données d'historique et les index actuels. Après cela, il est sûr de désactiver le ralentissement de innd.

Pour un exemple plus simple :

makehistory -b -f history.n -I -O

analysera le spool, supprimera les articles corrompus et générera des entrées d'historique et d'aperçu pour les articles manquants dans l'historique.

Pour pré-dimensionner le fichier history pour 100 000 000 d'articles et générer des données d'aperçu en même temps, vous pouvez directement utiliser la commande suivante :

makehistory -O -s 100000000

Vous n'avez alors pas besoin d'exécuter makedbz car le fichier history a déjà été généré et optimisé pour le nombre attendu d'articles.

Pour reconstruire uniquement l'aperçu :

makehistory -O -x -F

FICHIERS

pathdb/history
Ceci est le fichier de sortie par défaut pour makehistory.
pathtmp
Où les fichiers temporaires sont écrits à moins que -T ne soit donné.
