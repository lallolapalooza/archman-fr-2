NOM

man-pages - conventions d'écriture des pages de manuel Linux

SYNTAXE

man [section] titre

DESCRIPTION

Cette page décrit les conventions qui devraient être employées lors de l'écriture de pages de manuel pour le projet man-pages Linux, qui documente l'API de l'espace utilisateur fournie par le noyau Linux et la bibliothèque C GNU. Le projet fournit ainsi la plupart des pages des Sections 2, plusieurs pages des Sections 3, 4 et 7, ainsi que quelques pages des Sections 1, 5 et 8 des pages de manuel sur un système Linux. Les conventions décrites sur cette page peuvent également être utiles pour les auteurs écrivant des pages de manuel pour d'autres projets.

Sections des pages de manuel

Les sections du manuel sont traditionnellement définies comme suit :

1 Commandes utilisateur (Programmes)
Commandes qui peuvent être exécutées par l'utilisateur depuis un shell.
2 Appels système
Fonctions qui encapsulent les opérations effectuées par le noyau.
3 Appels de bibliothèque
Toutes les fonctions de bibliothèque à l'exception des wrappers d'appels système (La plupart des fonctions de libc).
4 Fichiers spéciaux (périphériques)
Fichiers trouvés dans /dev qui permettent d'accéder aux périphériques via le noyau.
5 Formats de fichiers et fichiers de configuration
Décrit divers formats de fichiers lisibles par l'homme et fichiers de configuration.
6 Jeux
Jeux et petits programmes amusants disponibles sur le système.
7 Vue d'ensemble, conventions et divers
Aperçus ou descriptions de divers sujets, conventions et protocoles, normes de jeux de caractères, la disposition standard du système de fichiers et diverses autres choses.
8 Commandes de gestion du système
Commandes telles que mount(8), dont beaucoup ne peuvent être exécutées que par root.

Paquet de macros

Les nouvelles pages de manuel doivent être balisées en utilisant le paquet groff an.tmac décrit dans man(7). Ce choix est principalement par souci de cohérence : la grande majorité des pages de manuel Linux existantes sont balisées en utilisant ces macros.

Conventions pour la disposition des fichiers source

Veuillez limiter la longueur des lignes de code source à environ 75 caractères autant que possible. Cela permet d'éviter le retour à la ligne dans certains clients de messagerie lorsque des correctifs sont soumis en ligne.

Ligne de titre

La première commande d'une page de manuel doit être une commande TH :

.TH titre section date source section_manuel

Les arguments de la commande sont les suivants :

titre
Le titre de la page de manuel.
section
Le numéro de la section dans laquelle la page de manuel doit être placée (par exemple, 7).
date
La date du dernier changement non trivial apporté à la page de manuel. (Au sein du projet man-pages, les mises à jour nécessaires de ces horodatages sont gérées automatiquement par des scripts, il n'est donc pas nécessaire de les mettre à jour manuellement dans le cadre d'un correctif.) Les dates doivent être écrites au format AAAA-MM-JJ.
source
Le nom et la version du projet qui fournit la page de manuel (pas nécessairement le paquet qui fournit la fonctionnalité).
section_manuel
Normalement, cela devrait être vide, car la valeur par défaut sera correcte.

Sections dans une page de manuel

La liste ci-dessous montre les sections conventionnelles ou suggérées. La plupart des pages de manuel devraient inclure au moins les sections en surbrillance. Organisez une nouvelle page de manuel de manière à ce que les sections soient placées dans l'ordre indiqué dans la liste.

NOM
BIBLIOTHÈQUE [Normalement uniquement dans les Sections 2, 3]
SYNTAXE
CONFIGURATION [Normalement uniquement dans la Section 4]
DESCRIPTION
OPTIONS [Normalement uniquement dans les Sections 1, 8]
VALEUR DE RETOUR (FIN DE L'EXÉCUTION) [Normalement uniquement dans les Sections 1, 8]
VALEUR DE RETOUR [Normalement uniquement dans les Sections 2, 3]
ERREURS [Typiquement uniquement dans les Sections 2, 3]
ENVIRONNEMENT
FICHIERS
ATTRIBUTS [Normalement uniquement dans les Sections 2, 3]
VERSIONS [Normalement uniquement dans les Sections 2, 3]
NORMES
HISTORIQUE
NOTES
AVERTISSEMENTS
BOGUES
EXEMPLES
AUTEURS [Déconseillé]
SIGNALEMENT DE BOGUES [Non utilisé dans man-pages]
COPYRIGHT [Non utilisé dans man-pages]
VOIR AUSSI

Là où un titre traditionnel s'appliquerait, veuillez l'utiliser ; ce type de cohérence peut rendre l'information plus facile à comprendre. Si vous devez créer vos propres titres s'ils facilitent la compréhension (ce qui peut être particulièrement utile pour les pages des Sections 4 et 5), faites-le. Cependant, avant de le faire, demandez-vous si vous ne pourriez pas utiliser les titres traditionnels, avec des sous-sections (.SS) à l'intérieur de ces sections.

La liste suivante détaille le contenu de chacune des sections ci-dessus.

NOM
Le nom de cette page de manuel.
Voir man(7) pour des détails importants sur les lignes qui devraient suivre la commande .SH NOM. Tous les mots de cette ligne (y compris le mot suivant immédiatement le "\-") devraient être en minuscules, sauf si la convention terminologique anglaise ou technique l'exige autrement.
BIBLIOTHÈQUE
La bibliothèque fournissant un symbole.
Elle montre le nom commun de la bibliothèque, et entre parenthèses, le nom du fichier de la bibliothèque et, si nécessaire, le drapeau de l'éditeur de liens nécessaire pour lier un programme contre elle : (libfoo[, -lfoo]).
SYNTAXE
Un bref résumé de l'interface de la commande ou de la fonction.
Pour les commandes, cela montre la syntaxe de la commande et de ses arguments (y compris les options) ; le gras est utilisé pour le texte tel quel et l'italique est utilisé pour indiquer les arguments remplaçables. Les crochets ([]) entourent les arguments optionnels, les barres verticales (|) séparent les choix, et les points de suspension (...) peuvent être répétés. Pour les fonctions, cela montre les déclarations de données requises ou les directives #include, suivies de la déclaration de la fonction.
Lorsque une macro de test de fonctionnalité doit être définie pour obtenir la déclaration d'une fonction (ou d'une variable) à partir d'un fichier d'en-tête, alors la SYNTAXE devrait l'indiquer, comme décrit dans feature_test_macros(7).
CONFIGURATION
Détails de configuration d'un périphérique.
Cette section apparaît normalement uniquement dans les pages de la Section 4.
DESCRIPTION
Une explication de ce que le programme, la fonction
, ou le format.
Décrivez comment il interagit avec les fichiers et l'entrée standard, et ce qu'il produit en sortie standard ou en erreur standard. Omettez les détails internes et d'implémentation, sauf s'ils sont critiques pour comprendre l'interface. Décrivez le cas d'utilisation habituel ; pour des informations sur les options de ligne de commande d'un programme, utilisez la section OPTIONS.
Lors de la description d'un nouveau comportement ou de nouveaux indicateurs pour un appel système ou une fonction de bibliothèque, veillez à noter la version du noyau ou de la bibliothèque C qui a introduit le changement. La méthode préférée pour noter ces informations pour les indicateurs est de les inclure dans une liste .TP, sous la forme suivante (ici, pour un nouvel indicateur d'appel système) :
XYZ_FLAG (depuis Linux 3.7)
Description de l'indicateur...
Inclure les informations de version est particulièrement utile pour les utilisateurs qui sont contraints d'utiliser d'anciennes versions du noyau ou de la bibliothèque C (ce qui est typique dans les systèmes embarqués, par exemple).
OPTIONS
Description des options de ligne de commande acceptées par un programme et de la manière dont elles modifient son comportement.
Cette section ne doit apparaître que pour les pages de manuel des sections 1 et 8.
STATUT DE SORTIE
Liste des valeurs possibles du statut de sortie d'un programme et des conditions qui entraînent le retour de ces valeurs.
Cette section ne doit apparaître que pour les pages de manuel des sections 1 et 8.
VALEUR DE RETOUR
Pour les pages des sections 2 et 3, cette section donne une liste des valeurs que la routine de bibliothèque retournera à l'appelant et les conditions qui provoquent le retour de ces valeurs.
ERREURS
Pour les pages de manuel des sections 2 et 3, il s'agit d'une liste des valeurs qui peuvent être placées dans errno en cas d'erreur, ainsi que des informations sur la cause des erreurs.
Lorsque plusieurs conditions différentes produisent la même erreur, l'approche préférée est de créer des entrées de liste séparées (avec des noms d'erreur dupliqués) pour chacune des conditions. Cela clarifie les conditions séparées, peut rendre la liste plus facile à lire et permet de marquer plus facilement les métadonnées (par exemple, le numéro de version du noyau où la condition est devenue applicable pour la première fois) pour chaque condition.
La liste des erreurs doit être triée par ordre alphabétique.
ENVIRONNEMENT
Liste de toutes les variables d'environnement qui affectent le programme ou la fonction et comment elles l'affectent.
FICHIERS
Liste des fichiers utilisés par le programme ou la fonction, tels que les fichiers de configuration, les fichiers de démarrage et les fichiers sur lesquels le programme opère directement.
Donnez le chemin complet de ces fichiers, et utilisez le processus d'installation pour modifier la partie répertoire afin qu'elle corresponde aux préférences de l'utilisateur. Pour de nombreux programmes, l'emplacement d'installation par défaut est /usr/local, donc votre page de manuel de base doit utiliser /usr/local comme base.
ATTRIBUTS
Résumé des divers attributs de la ou des fonctions documentées sur cette page. Voir attributes(7) pour plus de détails.
VERSIONS
Résumé des systèmes où l'API se comporte différemment, ou où il existe une API similaire.
NORMES
Description de toutes les normes ou conventions relatives à la fonction ou à la commande décrite par la page de manuel.
Les termes préférés à utiliser pour les différentes normes sont listés comme en-têtes dans standards(7).
Cette section doit indiquer les normes actuelles auxquelles l'API est conforme.
Si l'API n'est régie par aucune norme mais existe couramment sur d'autres systèmes, notez-les. Si l'appel est spécifique à Linux ou à GNU, notez-le. S'il est disponible dans les BSD, notez-le.
Si cette section consiste uniquement en une liste de normes (ce qui est courant), terminez la liste par un point ('.').
HISTORIQUE
Bref résumé des versions du noyau Linux ou de glibc où un appel système ou une fonction de bibliothèque est apparu, ou a changé de manière significative dans son fonctionnement.
En règle générale, toute nouvelle interface devrait inclure une section HISTORIQUE dans sa page de manuel. Malheureusement, de nombreuses pages de manuel existantes n'incluent pas ces informations (car il n'y avait pas de politique pour le faire lorsqu'elles ont été écrites). Les correctifs pour remédier à cela sont les bienvenus, mais du point de vue des programmeurs écrivant du nouveau code, ces informations sont probablement pertinentes uniquement dans le cas des interfaces du noyau qui ont été ajoutées dans Linux 2.4 ou plus tard (c'est-à-dire des changements depuis Linux 2.2), et des fonctions de bibliothèque qui ont été ajoutées à glibc depuis glibc 2.1 (c'est-à-dire des changements depuis glibc 2.0).
La page de manuel syscalls(2) fournit également des informations sur les versions du noyau dans lesquelles divers appels système sont apparus pour la première fois.

Les anciennes versions des normes doivent être mentionnées ici, plutôt que dans STANDARDS, par exemple, SUS, SUSv2 et XPG, ou les normes d'implémentation SVr4 et 4.xBSD.

NOTES
Notes diverses.
Pour les pages de manuel des sections 2 et 3, il peut être utile d'inclure des sous-sections (SS) nommées Notes Linux et Notes glibc.
Dans la section 2, utilisez l'en-tête Différences entre la bibliothèque C et le noyau pour marquer les notes qui décrivent les différences (le cas échéant) entre la fonction d'enveloppement de la bibliothèque C pour un appel système et l'interface d'appel système brute fournie par le noyau.
ATTENTION
Avertissements concernant les mésusages typiques d'une API par l'utilisateur, qui ne constituent pas un bug de l'API ou un défaut de conception.
BOGUES
Liste des limitations, des défauts connus ou des inconvénients, et autres activités douteuses.
EXEMPLES
Un ou plusieurs exemples démontrant comment cette fonction, ce fichier ou cette commande est utilisé.
Pour plus de détails sur la rédaction de programmes exemples, voir Programmes exemples ci-dessous.
AUTEURS
Liste des auteurs de la documentation ou du programme.
L'utilisation d'une section AUTEURS est fortement déconseillée. En général, il est préférable de ne pas encombrer chaque page d'une liste d'auteurs (potentiellement nombreux au fil du temps) ; si vous écrivez ou modifiez significativement une page, ajoutez un avis de droit d'auteur sous forme de commentaire dans le fichier source. Si vous êtes l'auteur d'un pilote de périphérique et souhaitez inclure une adresse pour signaler les bogues, placez-la dans la section BUGS.
SIGNALEMENT DES BOGUES
Le projet man-pages n'utilise pas de section SIGNALEMENT DES BOGUES dans les pages de manuel. Les informations sur le signalement des bogues sont fournies dans la section COLOPHON générée par le script. Cependant, divers projets utilisent une section SIGNALEMENT DES BOGUES. Il est recommandé de la placer près du pied de la page.
DROIT D'AUTEUR
Le projet man-pages n'utilise pas de section DROIT D'AUTEUR dans les pages de manuel. Les informations de droit d'auteur sont conservées dans la source de la page. Dans les pages où cette section est présente, il est recommandé de la placer près du pied de la page, juste avant VOIR AUSSI.
VOIR AUSSI
Liste séparée par des virgules des pages de manuel associées, éventuellement suivie d'autres pages ou documents connexes.
La liste doit être triée par numéro de section puis par ordre alphabétique par nom. Ne terminez pas cette liste par un point.
Lorsque la liste VOIR AUSSI contient de nombreux noms de pages de manuel longs, pour améliorer le résultat visuel de la sortie, il peut être utile d'utiliser les directives .ad l en (ne pas justifier à droite) et .nh (ne pas hyphenner). L'hyphenation des noms de pages individuels peut être empêchée en précédant les mots de la chaîne "\%".
Compte tenu de la nature distribuée et autonome des projets FOSS et de leur documentation, il est parfois nécessaire — et dans de nombreux cas souhaitable — que la section VOIR AUSSI inclue des références à des pages de manuel fournies par d'autres projets.

CONVENTIONS DE MISE EN FORME ET DE RÉDACTION

Les sous-sections suivantes notent certains détails concernant les conventions de mise en forme et de rédaction préférées dans diverses sections des pages du projet man-pages.

SYNOPSIS

Encadrez le ou les prototypes de fonction dans une paire .nf/.fi pour empêcher le remplissage.

Les déclarations anticipées de paramètres dans les fonctions ne doivent pas utiliser de gras ni d'italique ; cela permet de les distinguer visuellement des paramètres réels. Par exemple :


int snprintf(size_t size;
             char str[restrict size], size_t size,
             const char *restrict format, ...);

En général, lorsque plusieurs prototypes de fonction sont affichés dans le SYNOPSIS, ils ne doivent pas être séparés par des lignes vides. Cependant, des lignes vides (obtenues à l'aide de .P) peuvent être ajoutées dans les cas suivants :

•
pour séparer de longues listes de prototypes de fonctions en groupes liés (voir par exemple list(3)) ;
•
dans d'autres cas qui peuvent améliorer la lisibilité.

Dans le SYNOPSIS, un long prototype de fonction peut devoir être reporté sur la ligne suivante. La ligne de continuation est indentée selon les règles suivantes :

(1)
S'il existe un seul prototype de ce type qui doit être poursuivi, alignez la ligne de continuation de sorte que lorsque la page est rendue sur un appareil à police à largeur fixe (par exemple, sur un xterm), la ligne de continuation commence juste en dessous du début de la liste des arguments de la ligne précédente. (Exception : le retrait peut être ajusté si nécessaire pour éviter une ligne de continuation très longue ou une autre ligne de continuation où le prototype de fonction est très long.) Par exemple :

int tcsetattr(int fd, int optional_actions,
              const struct termios *termios_p);

(2)
Mais, lorsque plusieurs fonctions dans le SYNOPSIS nécessitent des lignes de continuation, et que les noms des fonctions ont des longueurs différentes, alignez toutes les lignes de continuation pour qu'elles commencent dans la même colonne. Cela offre un meilleur rendu dans la sortie PDF (car le SYNOPSIS utilise une police à largeur variable où les espaces rendent plus étroitement que la plupart des caractères). Par exemple :

int getopt(int argc, char * const argv[],
           const char *optstring);
int getopt_long(int argc, char * const argv[],
           const char *optstring,
           const struct option *longopts, int *longindex);

VALEUR DE RETOUR

La formulation préférée pour décrire comment errno est défini est "errno est défini pour indiquer l'erreur" ou une formulation similaire. Cette formulation est cohérente avec celle utilisée dans POSIX.1 et FreeBSD.

ATTRIBUTS

Notez ce qui suit :

•
Encapsulez le tableau de cette section dans une paire .ad l/.ad pour désactiver le remplissage du texte et une paire .nh/.hy pour désactiver la césure.
•
Assurez-vous que le tableau occupe toute la largeur de la page en utilisant une description lbx pour l'une des colonnes (généralement la première colonne, bien que dans certains cas la dernière colonne si elle contient beaucoup de texte).
•
Faites un usage libre des paires de macros T{/T} pour permettre aux cellules du tableau d'être réparties sur plusieurs lignes (tout en gardant à l'esprit que les pages peuvent parfois être rendues sur une largeur inférieure à 80 colonnes).

Pour des exemples de tout ce qui précède, consultez le code source des différentes pages.

GUIDE DE STYLE

Les sous-sections suivantes décrivent le style préféré pour le projet man-pages. Pour les détails non couverts ci-dessous, le Chicago Manual of Style est généralement une bonne source ; essayez également de rechercher les utilisations préexistantes dans l'arborescence source du projet.

UNIX for Beginners [2ème éd., Brian W. Kernighan] contient également une section remarquable, « Hints for Preparing Documents ».

Utilisation de langage neutre vis-à-vis du genre

Dans la mesure du possible, utilisez un langage neutre vis-à-vis du genre dans le texte des pages man. L'utilisation de « iel » (« eux », « soi-même », « leur ») comme pronom singulier neutre vis-à-vis du genre est acceptable.

Conventions de mise en forme pour les pages man décrivant des commandes

Pour les pages man qui décrivent une commande (typiquement dans les sections 1 et 8), les arguments sont toujours spécifiés en italique, même dans la section SYNOPSIS.

Le nom de la commande et ses options doivent toujours être formatés en gras.

Conventions de mise en forme pour les pages man décrivant des fonctions

Pour les pages man qui décrivent des fonctions (typiquement dans les sections 2 et 3), les arguments sont toujours spécifiés en italique, même dans la section SYNOPSIS, où le reste de la fonction est spécifié en gras :

int maFonction(int argc, char **argv);

Les noms de variables doivent, comme les noms d'arguments, être spécifiés en italique.

Toute référence au sujet de la page man actuelle doit être écrite avec le nom en gras suivi d'une paire de parenthèses en police romaine (normale). Par exemple, dans la page man de fcntl(2), les références au sujet de la page seraient écrites comme : fcntl(). La manière préférée de l'écrire dans le fichier source est :

    .BR fcntl ()

(Utiliser ce format, plutôt que l'utilisation de « \fB...\fP() » facilite l'écriture d'outils qui analysent les fichiers sources des pages man.)

Utilisation des sauts de ligne sémantiques

Dans la source d'une page man, les nouvelles phrases doivent commencer sur de nouvelles lignes, les phrases longues doivent être coupées en lignes aux limites de clauses (virgules, points-virgules, deux-points, etc.), et les clauses longues doivent être coupées aux limites de phrases. Cette convention, parfois appelée « sauts de ligne sémantiques », facilite la visualisation de l'effet des correctifs, qui opèrent souvent au niveau des phrases, clauses ou expressions individuelles.

Listes

Il existe différents types de listes :

Paragraphes étiquetés
Ceux-ci sont utilisés pour une liste d'étiquettes et leurs descriptions. Lorsque les étiquettes sont des constantes (macros ou nombres), elles sont en gras. Utilisez la macro .TP.
Un exemple est cette sous-section « Paragraphes étiquetés » elle-même.
Listes ordonnées
Les éléments sont précédés d'un nombre entre parenthèses (1), (2). Ceux-ci représentent un ensemble d'étapes qui ont un ordre.
Lorsqu'il y a des sous-étapes, elles seront numérotées comme (4.2).
Listes positionnelles
Les éléments sont précédés d'un nombre (indice) entre crochets [4], [5]. Ceux-ci représentent des champs dans un ensemble. Le premier indice sera :
0
Lorsqu'il représente des champs d'une structure de données C, pour être cohérent avec les tableaux.
1
Lorsqu'il représente des champs d'un fichier, pour être cohérent avec des outils comme cut(1).
Liste d'alternatives
Les éléments sont précédés d'une lettre entre parenthèses (a), (b). Ceux-ci représentent un ensemble d'alternatives (normalement) exclusives.
Listes à puces
Les éléments sont précédés de symboles de puce (\[bu]). Tout ce qui ne rentre pas ailleurs est généralement couvert par ce type de liste.
Notes numérotées
Pas vraiment une liste, mais la syntaxe est identique aux « listes positionnelles ».

Il doit toujours y avoir exactement 2 espaces entre le symbole de liste et les éléments. Cela ne s'applique pas aux « paragraphes étiquetés », qui utilisent les règles de retrait par défaut.

Conventions de mise en forme (générales)

Les paragraphes doivent être séparés par des marqueurs appropriés (généralement .P ou .IP). Ne séparez pas les paragraphes par des lignes vides, car cela entraîne un rendu médiocre dans certains formats de sortie (tels que PostScript et PDF).

Les noms de fichiers (qu'il s'agisse de chemins ou de références à des fichiers d'en-tête) sont toujours en italique (par exemple, <stdio.h>), sauf dans la section SYNOPSIS, où les fichiers inclus sont en gras (par exemple, #include <stdio.h>). Lorsque vous faites référence à une inclusion de fichier d'en-tête standard, spécifiez le fichier d'en-tête entouré d'accolades, de la manière habituelle en C (par exemple, <stdio.h>).

Les macros spéciales, généralement en majuscules, sont en gras (par exemple, MAXINT). Exception : ne mettez pas NULL en gras.

Lors de l'énumération d'une liste de codes d'erreur, les codes sont en gras (cette liste utilise généralement la macro .TP).

Les commandes complètes doivent, si elles sont longues, être écrites comme une ligne en retrait seule, avec une ligne vide avant et après la commande, par exemple


man 7 man-pages

Si la commande est courte, elle peut être incluse en ligne dans le texte, en italique, par exemple, man 7 man-pages. Dans ce cas, il peut être utile d'utiliser des espaces insécables (\~) à des endroits appropriés de la commande. Les options de commande doivent être écrites en italique (par exemple, -l).

Les expressions, si elles ne sont pas écrites sur une ligne en retrait séparée, doivent être spécifiées en italique. Là encore, l'utilisation d'espaces insécables peut être appropriée si l'expression est intégrée dans du texte normal.

Lors de la présentation de sessions shell d'exemple, les entrées utilisateur doivent être formatées en gras, par exemple


$ date;
Jeu 7 juil 13:01:27 CEST 2016

Toute référence à une autre page man doit être écrite avec le nom en gras, toujours suivi du numéro de section, formaté en police romaine (normale), sans espace de séparation (par exemple, intro(2)). La manière préférée de l'écrire dans le fichier source est :

    .BR intro (2)

(Inclure le numéro de section dans les références croisées permet aux outils comme man2html(1) de créer des pages correctement hyperliées.)

Les caractères de contrôle doivent être écrits en gras, sans guillemets ; par exemple, ^X.

Orthographe

À partir de la version 2.59, man-pages suit les conventions d'orthographe américaines (auparavant, il y avait un mélange aléatoire d'orthographes britanniques et américaines) ; veuillez écrire toutes les nouvelles pages et corrections selon ces conventions.

Outre les différences d'orthographe bien connues, il y a quelques autres subtilités à surveiller :



Variations en matière d'orthographe

•
L'anglais américain tend à utiliser les formes « backward », « upward », « toward », et ainsi de suite plutôt que les formes britanniques « backwards », « upwards », « towards », et ainsi de suite.
•
Les opinions sont divisées sur « acknowledgement » contre « acknowledgment ». Ce dernier est l'usage prédominant, mais pas universel dans l'anglais américain. POSIX et la licence BSD utilisent la première orthographe. Dans le projet des pages de manuel Linux, nous utilisons « acknowledgement ».

Numéros de version BSD

Le schéma classique pour écrire les numéros de version BSD est *x.yBSD*, où *x.y* est le numéro de version (par exemple, 4.2BSD). Évitez les formes telles que *BSD 4.3*.

Mise en majuscules

Dans les titres des sous-sections (« SS »), mettez une majuscule au premier mot du titre, mais utilisez par ailleurs des minuscules, sauf lorsque l'usage anglais (par exemple, les noms propres) ou les exigences du langage de programmation (par exemple, les noms d'identificateurs) dictent le contraire. Par exemple :


.SS Unicode sous Linux

NULL, NUL, pointeur nul, et octet nul

Un *pointeur nul* est un pointeur qui ne pointe vers rien, et est normalement indiqué par la constante *NULL*. D'autre part, *NUL* est l'*octet nul*, un octet de valeur 0, représenté en C par la constante caractère *'\0'*.

Le terme préféré pour le pointeur est « pointeur nul » ou simplement « NULL » ; évitez d'écrire « NULL pointer ».

Le terme préféré pour l'octet est « octet nul ». Évitez d'écrire « NUL », car il est trop facilement confondu avec « NULL ». Évitez également les termes « octet zéro » et « caractère nul ». L'octet qui termine une chaîne C doit être décrit comme « l'octet nul de terminaison » ; les chaînes peuvent être décrites comme « terminées par un octet nul », mais évitez l'utilisation de « terminées par NUL ».

Hyperliens

Pour les hyperliens, utilisez la paire de macros .UR/.UE (voir groff_man(7)). Cela produit des hyperliens corrects qui peuvent être utilisés dans un navigateur web, lors du rendu d'une page avec, par exemple :


BROWSER=firefox man -H pagename

Utilisation de par ex., c.-à-d., etc., alias, et similaires

En général, l'utilisation d'abréviations telles que « e.g. », « i.e. », « etc. », « cf. », et « a.k.a. » devrait être évitée, au profit de formulations complètes appropriées (« par exemple », « c'est-à-dire », « et ainsi de suite », « comparer à », « aussi connu sous le nom de »).

Le seul endroit où de telles abréviations peuvent être acceptables est dans des *courtes* remarques entre parenthèses (par ex., comme celle-ci).

Incluez toujours des points dans de telles abréviations, comme indiqué ici. De plus, « e.g. » et « i.e. » doivent toujours être suivis d'une virgule.

NAME

man-pages - conventions for writing manual pages

DESCRIPTION

This document describes the conventions and style that should be followed when writing manual pages for the Linux operating system. The goal is to maintain consistency across the manual pages.

Formatting and Wording Conventions

The following conventions apply to the formatting and wording of manual pages:

•
The name of a command, utility, or system call should be in boldface in the text when it first appears, and in italics or constant width in subsequent appearances.
•
Filenames should be in italics or constant width.
•
Manual page cross-references should be in constant width, e.g., printf(3).
•
Command-line arguments and options should be in constant width, e.g., -l.
•
Variable names, if used, should be in italics or constant width.
•
Do not use boldface for emphasis. Use italics instead.
•
Use the `P' macro for paragraphs. For subsections, use the `SS' macro.
•
Use `Bl-tag' for lists of items, `Bl-item' for list items.
•
For quoted strings, use the `QS' and `QE' macros.
•
For code examples, use the `EX' and `EE' macros.
•
For tabular data, use the `tbl' macro.

When using prefixes like "re-", "non-", "un-", "pre-", "anti-", "mis-", "dis-", "co-", "de-", "in-", "im-", "il-", "ir-", "sub-", "inter-", "intra-", "super-", "over-", "under-", "counter-", "hyper-", "hypo-", "multi-", "pseudo-", "semi-", "sym-", "syn-", "tele-", "trans-", "ultra-", "archi-", "auto-", "bio-", "chrono-", "eco-", "geo-", "logo-", "macro-", "micro-", "mono-", "neuro-", "ortho-", "paleo-", "pan-", "photo-", "poly-", "psycho-", "radio-", "retro-", "socio-", "stereo-", "thermo-", "topo-", "uni-", "vita-", and "zoo-", it is generally recommended to hyphenate the word to avoid ambiguity and ensure clarity. This is particularly important for words that might be misread or have alternative meanings without the hyphen.

re-established
re-initialize
re-arm
re-read
sub-component
sub-directory
sub-system

Hyphens should be retained when the prefixes are used in nonstandard English words, with trademarks, proper nouns, acronyms, or compound terms. Some examples:

non-ASCII
non-English
non-NULL
non-real-time

Finally, note that "re-create" and "recreate" are two different verbs, and the former is probably what you want.

Generating optimal glyphs

Where a real minus character is required (e.g., for numbers such as -1, for man page cross references such as utf-8(7), or when writing options that have a leading dash, such as in ls -l), use the following form in the man page source:


\-

This guideline applies also to code examples.

The use of real minus signs serves the following purposes:

•
To provide better renderings on various targets other than ASCII terminals, notably in PDF and on Unicode/UTF-8-capable terminals.
•
To generate glyphs that when copied from rendered pages will produce real minus signs when pasted into a terminal.

To produce unslanted single quotes that render well in ASCII, UTF-8, and PDF, use "\[aq]" ("apostrophe quote"); for example


\[aq]C\[aq]

where C is the quoted character. This guideline applies also to character constants used in code examples.

Where a proper caret (^) that renders well in both a terminal and PDF is required, use "\[ha]". This is especially necessary in code samples, to get a nicely rendered caret when rendering to PDF.

Using a naked "~" character results in a poor rendering in PDF. Instead use "\[ti]". This is especially necessary in code samples, to get a nicely rendered tilde when rendering to PDF.

Example programs and shell sessions

Manual pages may include example programs demonstrating how to use a system call or library function. However, note the following:

•
Example programs should be written in C.
•
An example program is necessary and useful only if it demonstrates something beyond what can easily be provided in a textual description of the interface. An example program that does nothing other than call an interface usually serves little purpose.
•
Example programs should ideally be short (e.g., a good example can often be provided in less than 100 lines of code), though in some cases longer programs may be necessary to properly illustrate the use of an API.
•
Expressive code is appreciated.
•
Comments should included where helpful. Complete sentences in free-standing comments should be terminated by a period. Periods should generally be omitted in "tag" comments (i.e., comments that are placed on the same line of code); such comments are in any case typically brief phrases rather than complete sentences.
•
Example programs should do error checking after system calls and library function calls.
•
Example programs should be complete, and compile without warnings when compiled with cc -Wall.
•
Where possible and appropriate, example programs should allow experimentation, by varying their behavior based on inputs (ideally from command-line arguments, or alternatively, via input read by the program).
•
Example programs should be laid out according to Kernighan and Ritchie style, with 4-space indents. (Avoid the use of TAB characters in source code!) The following command can be used to format your source code to something close to the preferred style:

indent -npro -kr -i4 -ts4 -sob -l72 -ss -nut -psl prog.c

•
For consistency, all example programs should terminate using either of:

exit(EXIT_SUCCESS);
exit(EXIT_FAILURE);

Avoid using the following forms to terminate a program:

exit(0);
exit(1);
return n;

•
If there is extensive explanatory text before the program source code, mark off the source code with a subsection heading Program source, as in:

.SS Program source

Always do this if the explanatory text includes a shell session log.

If you include a shell session log demonstrating the use of a program or other system feature:

•
Place the session log above the source code listing.
•
Indent the session log by four spaces.
•
Boldface the user input text, to distinguish it from output produced by the system.

For some examples of what example programs should look like, see wait(2) and pipe(2).
