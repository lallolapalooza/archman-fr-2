MASTER(5) Manuel des formats de fichiers MASTER(5)

NOM

master — Format du fichier de configuration du processus maître Postfix

DESCRIPTION


Le système de messagerie Postfix est implémenté par un petit nombre de commandes (principalement) clientes qui sont invoquées par les utilisateurs, et par un plus grand nombre de services qui s'exécutent en arrière-plan.

Les services Postfix sont implémentés par des processus démons. Ceux-ci s'exécutent en arrière-plan, démarrés à la demande par le processus master(8). Le fichier de configuration master.cf définit comment un programme client se connecte à un service, et quel programme démon s'exécute lorsqu'un service est demandé. La plupart des processus démons sont de courte durée et se terminent volontairement après avoir servi max_use clients, ou après une inactivité de max_idle unités de temps ou plus.

Tous les démons spécifiés ici doivent parler un protocole interne à Postfix. Afin d'exécuter des logiciels non-Postfix, utilisez les services local(8), pipe(8) ou spawn(8), ou exécutez le logiciel avec inetd(8) ou équivalent.

Après avoir modifié master.cf, vous devez exécuter "postfix reload" pour recharger la configuration.

SYNTAXE

Le format général du fichier master.cf est le suivant :

  • Les lignes vides et les lignes contenant uniquement des espaces sont ignorées, tout comme les lignes dont le premier caractère non-espace est un `#'.
  • Une ligne logique commence par du texte non-espace. Une ligne commençant par un espace continue une ligne logique.
  • Chaque ligne logique définit un seul service Postfix. Chaque service est identifié par son nom et son type, comme décrit ci-dessous. Lorsque plusieurs lignes spécifient le même nom de service et le même type, seule la dernière est conservée. Autrement, l'ordre des définitions de services dans master.cf n'a pas d'importance.

Chaque ligne logique se compose de huit champs séparés par des espaces. Ceux-ci sont décrits ci-dessous dans l'ordre où ils apparaissent dans le fichier master.cf.

Lorsque applicable, un champ de "-" demande à ce que la valeur par défaut intégrée soit utilisée. Pour les champs booléens, spécifiez "y" ou "n" pour remplacer la valeur par défaut.

Nom du service
La syntaxe du nom du service dépend du type de service, comme décrit ensuite.
Type de service
Spécifiez l'un des types de service suivants :
inet
Le service écoute sur une socket TCP/IP et est accessible via le réseau.

Le nom du service est spécifié sous la forme hôte:port, indiquant l'hôte et le port sur lesquels les nouvelles connexions doivent être acceptées. La partie hôte (et le deux-points) peuvent être omises. L'hôte ou le port peuvent être donnés sous forme symbolique (voir hosts(5) ou services(5)) ou sous forme numérique (adresse IP ou numéro de port). Les informations d'hôte peuvent être entourées de crochets "[]" ; cette forme est nécessaire uniquement avec les adresses IPv6.

Exemples : un service nommé 127.0.0.1:smtp ou ::1:smtp reçoit le courrier via l'interface de bouclage uniquement ; et un service nommé 10025 accepte les connexions sur le port TCP 10025 via toutes les interfaces configurées avec le paramètre inet_interfaces.

Remarque : avec Postfix version 2.2 et ultérieures, spécifiez "inet_interfaces = loopback-only" dans main.cf, au lieu d'encoder en dur les informations d'adresse IP de bouclage dans master.cf ou dans main.cf.

unix
Le service écoute sur une socket de flux UNIX et est accessible uniquement aux clients locaux.

Le nom du service est un chemin relatif au répertoire de la file d'attente de Postfix (chemin contrôlé par le paramètre de configuration queue_directory dans main.cf).

Sur les systèmes Solaris 8 et antérieurs, le type unix est implémenté avec des sockets de flux.

unix-dgram
Le service écoute sur une socket de datagramme UNIX et est accessible uniquement aux clients locaux.

Le nom du service est un chemin relatif au répertoire de la file d'attente de Postfix (chemin contrôlé par le paramètre de configuration queue_directory dans main.cf).

fifo (obsolète)
Le service écoute sur un FIFO (tube nommé) et est accessible uniquement aux clients locaux.

Le nom du service est un chemin relatif au répertoire de la file d'attente de Postfix (chemin contrôlé par le paramètre de configuration queue_directory dans main.cf).

pass
Le service écoute sur une socket de flux UNIX, et est accessible uniquement aux clients locaux. Il reçoit une connexion ouverte (transfert de descripteur de fichier) par demande de connexion.

Le nom du service est un chemin relatif au répertoire de la file d'attente de Postfix (chemin contrôlé par le paramètre de configuration queue_directory dans main.cf).

Sur les systèmes Solaris 8 et antérieurs, le type pass est implémenté avec des sockets de flux.

Cette fonctionnalité est disponible à partir de la version 2.5 de Postfix.

Privé (par défaut : y)
Indique si un service est interne à Postfix (le chemin commence par private/), ou exposé via les outils en ligne de commande Postfix (le chemin commence par public/). Les services Internet (type inet) ne peuvent pas être privés.
Sans privilèges (par défaut : y)
Indique si le service s'exécute avec les privilèges root ou en tant que propriétaire du système Postfix (le nom du propriétaire est contrôlé par la variable de configuration mail_owner dans le fichier main.cf).

Les démons local(8), pipe(8), spawn(8), et virtual(8) nécessitent des privilèges.

Chroot (par défaut : Postfix >= 3.0 : n, Postfix < 3.0 : y)
Indique si le service s'exécute en chroot dans le répertoire de la file d'attente de courrier (le chemin est contrôlé par la variable de configuration queue_directory dans le fichier main.cf).

Chroot ne doit pas être utilisé avec les démons local(8), pipe(8), spawn(8), et virtual(8). Bien que le serveur proxymap(8) puisse s'exécuter en chroot, le faire annule la plupart de l'intérêt d'avoir ce service en premier lieu.

Les fichiers dans le sous-répertoire examples/chroot-setup de la source Postfix montrent comment configurer un environnement chroot Postfix sur divers systèmes. Voir également BASIC_CONFIGURATION_README pour les problèmes liés à l'exécution de démons en chroot.

Temps de réveil (par défaut : 0)
Réveille automatiquement le service nommé après le nombre spécifié de secondes. Le réveil est implémenté en se connectant au service et en envoyant une requête de réveil. Un ? à la fin du champ de temps de réveil demande qu'aucun événement de réveil ne soit envoyé avant la première utilisation du service. Spécifiez 0 pour aucun réveil automatique.

Les démons pickup(8), qmgr(8) et flush(8) nécessitent un minuteur de réveil.

Limite de processus (par défaut : $default_process_limit)
Le nombre maximum de processus qui peuvent exécuter ce service simultanément. Spécifiez 0 pour aucune limite de nombre de processus.

NOTE : Certains services Postfix doivent être configurés comme un service à processus unique (par exemple, qmgr(8)) et certains services doivent être configurés sans limite de processus (par exemple, cleanup(8)). Ces limites ne doivent pas être modifiées.

Nom de commande + arguments
La commande à exécuter. Les caractères spéciaux pour le shell tels que ">" ou "|" n'ont aucune signification spéciale ici, et les guillemets ne peuvent pas être utilisés pour protéger les arguments contenant des espaces. Pour protéger les espaces, utilisez "{" et "}" comme décrit ci-dessous.

Le nom de la commande est relatif au répertoire binaire de Postfix.

master(5) — Postfix master.cf

NAME

master.cf — Postfix multi-process server control file

DESCRIPTION

The Postfix master.cf file controls the execution of Postfix daemons. It is not designed to be edited by hand. Instead, use the postconf utility to edit the file, or to retrieve configuration parameter values. The master.cf file is used by the master(8) daemon.

The master.cf file is organized into sections. Each section specifies a service, a command, command-line arguments, and execution information.

The format of a master.cf entry is:

service     type  private   unpriv  chroot  wakeup  maxproc  command + args

The fields are:

  • service: The name of the service. For network-facing services, this is typically a port number or service name (e.g., smtp, submission). For internal services, this is a name like bounce or defer.
  • type: The type of service. Common types are:
    inet
    The service listens on a network socket. The private, unpriv, and chroot fields are interpreted as described below.
    unix
    The service uses a UNIX-domain socket. The private, unpriv, and chroot fields are interpreted as described below.
    fifo
    The service uses a named pipe. The private, unpriv, and chroot fields are ignored.
    inet_proto
    This is like inet, but the service is available on all network interfaces. The default is to listen only on the loopback interface. This is supported from Postfix 2.2.
  • private: This field specifies whether the service socket should be created with restricted access.
    y
    The socket is created with restrictive permissions (typically, only accessible by the owner). This is the default for unix type services.
    n
    The socket is created with world-readable and world-writable permissions. This is the default for inet type services.
  • unpriv: This field specifies whether the daemon process runs with privileges.
    y
    The daemon process runs with reduced privileges (as the mail_owner user). This is the default for inet type services.
    n
    The daemon process runs with the privileges of the root user. This is the default for unix type services.
  • chroot: This field specifies whether the daemon process is run in a chroot jail.
    y
    The daemon process is chrooted to the directory specified by the chroot configuration parameter. This is the default for inet type services.
    n
    The daemon process is not chrooted. This is the default for unix type services.
  • wakeup: The time in seconds to wait before starting a new instance of the daemon. This is used for daemons that are started on demand. A value of 0 means that the daemon is started immediately.
  • maxproc: The maximum number of concurrent processes for this service. A value of 0 means that there is no limit.
  • command + args: The command to execute, followed by its arguments. The command path is relative to the stfix daemon directory (pathname is controlled by the daemon_directory configuration variable).

    The command argument syntax for specific commands is specified in the respective daemon manual page.

    The following command-line options have the same effect for all daemon programs:

    -D
    Run the daemon under control by the command specified with the debugger_command variable in the main.cf configuration file. See DEBUG_README for hints and tips.
    -o { name = value } (long form, Postfix >= 3.0)
    Override the named main.cf configuration parameter. The parameter value can refer to other parameters as $name etc., just like in main.cf. See postconf(5) for syntax.

    The "long form" supports whitespace in parameter values. Whitespace after the outer "{", around "=", and before the outer "}" is ignored. Example:

    /etc/postfix/master.cf:
    submission inet .... smtpd
        -o { smtpd_xxx_yyy = text with whitespace... }

    NOTE: Over-zealous use of parameter overrides makes the Postfix configuration hard to understand and maintain. At a certain point, it might be easier to configure multiple instances of Postfix, instead of configuring multiple personalities via master.cf.

    -o name=value (short form)
    Override the named main.cf configuration parameter. The parameter value can refer to other parameters as $name etc., just like in main.cf. See postconf(5) for syntax.

    The "short form" does not support whitespace around the "=" or in parameter values. To specify a parameter value that contains whitespace, use the long form described above, or use commas instead of spaces if the parameter supports that, or specify the value in main.cf. Example:

    /etc/postfix/master.cf:
    submission inet .... smtpd
        -o smtpd_xxx_yyy=$submission_xxx_yyy

/etc/postfix/main.cf
    submission_xxx_yyy = text with whitespace...

    NOTE: Over-zealous use of parameter overrides makes the Postfix configuration hard to understand and maintain. At a certain point, it might be easier to configure multiple instances of Postfix, instead of configuring multiple personalities via master.cf.

    -v
    Increase the verbose logging level. Specify multiple -v options to make a Postfix daemon process increasingly verbose.
    Command-line arguments that start with {
    Command-line arguments that contain whitespace
    Command-line arguments that must be empty
    Specify "{" and "}" around such arguments (Postfix 3.0 and later). The outer "{" and "}" will be removed, together with any leading or trailing whitespace in the remaining text.
