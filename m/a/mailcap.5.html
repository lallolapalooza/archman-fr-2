MAILCAP(5) Manuel des formats de fichiers MAILCAP(5)

NOM

mailcap - fichier des capacités de metamail

DESCRIPTION

Le fichier mailcap est lu par le programme metamail pour déterminer comment afficher les données non textuelles sur le site local.

La syntaxe d'un fichier mailcap est assez simple, du moins comparée aux fichiers termcap. Toute ligne commençant par "#" est un commentaire. Les lignes vides sont ignorées. Sinon, chaque ligne définit une seule entrée mailcap pour un seul type de contenu. Les lignes longues peuvent être continuées en les terminant par un caractère backslash, \.

Chaque entrée mailcap individuelle se compose d'une spécification de type de contenu, d'une commande à exécuter et (éventuellement) d'un ensemble de valeurs de "flags" (indicateurs) optionnelles. Par exemple, une entrée mailcap très simple (qui est en fait un comportement par défaut intégré pour metamail) ressemblerait à ceci :

text/plain; cat %s

Les indicateurs optionnels peuvent être utilisés pour spécifier des informations supplémentaires sur la commande de gestion du courrier. Par exemple :

text/plain; cat %s; copiousoutput

peut être utilisé pour indiquer que la sortie de la commande 'cat' peut être volumineuse, nécessitant soit une fenêtre défilante, un paginator, soit un autre mécanisme d'adaptation approprié.

Le champ "type" (text/plain, dans l'exemple ci-dessus) est simplement un nom de type de contenu légal, tel que défini par la RFC 822. En pratique, il s'agit de presque toute chaîne de caractères. C'est la chaîne qui sera comparée à l'en-tête "Content-type" (ou à la valeur passée avec -c) pour décider si c'est l'entrée mailcap qui correspond au message courant. De plus, le champ type peut spécifier un sous-type (par exemple "text/ISO-8859-1") ou un caractère générique pour correspondre à tous les sous-types (par exemple "image/*").

Le champ "command" (commande) est toute commande UNIX ("cat %s" dans l'exemple ci-dessus), et est utilisé pour spécifier l'interpréteur pour le type de message donné. Elle sera passée au shell via la fonction système system(3). Les points-virgules et les barres obliques inverses dans la commande doivent être échappés avec des barres obliques inverses. Si la commande contient "%s", ces deux caractères seront remplacés par le nom d'un fichier contenant le corps du message. Si elle contient "%t", ces deux caractères seront remplacés par le champ type de contenu, y compris le sous-type, le cas échéant. (C'est-à-dire, si le type de contenu était "image/pbm; opt1=quelquechose-dautre", alors "%t" serait remplacé par "image/pbm".) Si le champ commande contient "%{" suivi d'un nom de paramètre et d'un "}" de fermeture, alors tous ces caractères seront remplacés par la valeur du paramètre nommé, le cas échéant, de l'en-tête Content-type. Ainsi, dans l'exemple précédent, "%{opt1}" sera remplacé par "quelquechose-dautre". Enfin, si la commande contient "\%", ces deux caractères seront remplacés par un seul caractère %. (En fait, la barre oblique inverse peut être utilisée pour échapper n'importe quel caractère, y compris elle-même.)

Si aucun "%s" n'apparaît dans le champ commande, alors au lieu de placer le corps du message dans un fichier temporaire, metamail transmettra le corps à la commande sur l'entrée standard. Ceci est utile pour économiser de l'espace disque /tmp, mais peut être problématique pour les applications orientées fenêtre sous certains systèmes de fenêtrage comme MGR.

Deux codes spéciaux peuvent apparaître dans la commande d'affichage pour les objets de type multipart (quel que soit le sous-type). Ce sont "%n" et "%F". %n sera remplacé par le nombre de parties dans l'objet multipart. %F sera remplacé par une série d'arguments, deux pour chaque partie, donnant d'abord le type de contenu puis le nom du fichier temporaire où la partie décodée a été stockée. De plus, pour chaque fichier créé par %F, un second fichier est créé, portant le même nom suivi de "H", qui contient les informations d'en-tête pour cette partie du corps. Ceci ne sera pas nécessaire pour la plupart des gestionnaires multipart, mais il est là si vous en avez jamais besoin.

Le champ "notes=xxx" est une chaîne non interprétée qui est utilisée pour spécifier le nom de la personne qui a installé cette entrée dans le fichier mailcap. (Le "xxx" peut être remplacé par n'importe quelle chaîne de texte.)

Le champ "test=xxx" est une commande qui est exécutée pour déterminer si la ligne mailcap s'applique ou non. Autrement dit, si le champ type de contenu correspond au type de contenu du message, mais qu'un champ "test=" est présent, alors le test doit réussir avant que la ligne mailcap ne soit considérée comme correspondant au message en cours de visualisation. La commande peut être n'importe quelle commande UNIX, utilisant la même syntaxe et les mêmes échappements % que pour la commande d'affichage, comme décrit ci-dessus. Une commande est considérée comme réussie si elle se termine avec un statut de sortie nul, et échoue sinon.

Le champ "print=xxx" est une commande qui est exécutée pour imprimer les données au lieu de les afficher interactivement. Ce comportement est généralement une conséquence de l'invocation de metamail avec le commutateur "-h".

Le champ "textualnewlines" peut être utilisé dans le cas plutôt obscur où les règles par défaut de metamail pour traiter les sauts de ligne dans les données encodées en base64 ne sont pas satisfaisantes. Par défaut, metamail traduira CRLF en caractère de saut de ligne local dans la sortie décodée en base64 si le type de contenu est "text" (quel que soit le sous-type), mais ne le fera pas autrement. Une entrée mailcap avec un champ de "textualnewlines=1" forcera une telle traduction pour le type de contenu spécifié, tandis que "textualnewlines=0" garantira que la traduction n'aura pas lieu, même pour les types de contenu textuels.

Le champ "compose" peut être utilisé pour spécifier un programme pouvant servir à composer un nouveau corps ou une nouvelle partie de corps dans le format donné. Son utilisation prévue est de prendre en charge les agents de composition de courrier qui supportent la composition de plusieurs types de courrier en utilisant des agents de composition externes. Comme avec la commande d'affichage, la commande de composition sera exécutée après avoir remplacé certaines séquences d'échappement commençant par "%". En particulier, %s doit être remplacé par le nom d'un fichier vers lequel les données composées doivent être écrites par le programme de composition spécifié, permettant ainsi au programme appelant (par exemple metamail) d'indiquer au programme appelé où stocker les données composées. Si %s n'apparaît pas, alors les données composées seront supposées être écrites par les programmes de composition sur la sortie standard. Le résultat du programme de composition peut être des données qui ne sont PAS encore adaptées au transport par courrier -- c'est-à-dire qu'un Content-Transfer-Encoding peut encore devoir être appliqué aux données.

Le champ "composetyped" est similaire au champ "compose", mais est destiné à être utilisé lorsque le programme de composition a besoin de spécifier le champ d'en-tête Content-type à appliquer aux données composées. Le champ "compose" est plus simple, et est préféré pour une utilisation avec des programmes existants (non orientés courrier) pour composer des données dans un format donné. Le champ "composetyped" est nécessaire lorsque les informations de type de contenu doivent inclure des paramètres auxiliaires, et que le programme de composition doit alors connaître suffisamment les formats de courrier pour produire une sortie incluant les informations de type de courrier, et appliquer tout Content-Transfer-Encoding nécessaire. Conceptuellement, "compose" spécifie un programme qui produit simplement le type de données spécifié sous forme brute, tandis que "composetyped" spécifie un programme qui produit les données sous forme d'objet MIME, avec tous les en-têtes Content-* nécessaires déjà en place.

needsterminal
Si cet indicateur est donné, l'interpréteur nommé a besoin d'interagir avec l'utilisateur sur un terminal. Dans certains environnements (par exemple, un lecteur de courrier orienté fenêtre sous X11) cela nécessitera la création d'une nouvelle fenêtre d'émulation de terminal, tandis que dans la plupart des environnements, cela ne sera pas le cas. Si l'entrée mailcap spécifie "needsterminal" et que metamail ne s'exécute pas sur un terminal (tel que déterminé par isatty(3), l'option -x, et la variable d'environnement MM_NOTTTY) alors metamail essaiera d'exécuter la commande dans une nouvelle fenêtre d'émulation de terminal. Actuellement, metamail sait comment créer de nouvelles fenêtres sous les systèmes de fenêtrage X11, SunTools et WM.
copiousoutput
Cet indicateur doit être donné chaque fois que l'interpréteur est capable de produire plus que quelques lignes de sortie sur stdout, et n'interagit pas avec l'utilisateur. Si l'entrée mailcap spécifie copiousoutput, et que la pagination a été demandée via l'option "-p", alors la sortie de la commande exécutée sera canalisée à travers un programme de pagination ("more" par défaut, mais cela peut être remplacé par la variable d'environnement METAMAIL_PAGER).

mailcap.5 - Man Page

NAME

mailcap

file format for mailcap configuration files

DESCRIPTION

The mailcap file format is used to specify how mail readers should handle various types of non-textual data found in electronic mail messages. Each line in a mailcap file specifies how to handle a single MIME content type.

A mailcap entry has the following general form:

contentType(/.*)?;\s*(<command>)(\s*;.*)?

The contentType is a MIME content type, such as text/plain, image/gif, or application/octet-stream. An optional subtype can be specified using a regular expression match on the subtype.

The command is a shell command to be executed to view or process the data. The command can use several special sequences:

%s
The entire data is sent to the standard input of the command.
%1
The first argument (if any) following the command in the mailcap entry. This is typically a filename.
%c
The data is written to a temporary file, and the name of that file is passed as an argument to the command.
%%
A literal % character.

Other optional fields can follow the command, separated by semicolons. Common options include:

compose=command
Specifies the command to use to create mail of this type.
compose-text=command
Specifies the command to use to create plain text that will be converted to this type.
print=command
Specifies the command to use to print mail of this type.
view=command
Specifies the command to use to view mail of this type.
x-name=string
A descriptive name for the content type.

Comments start with a # character and continue to the end of the line.

BUILT-IN CONTENT-TYPE SUPPORT

Metamail has some built-in support for common MIME types, such as text/plain, text/enriched, text/html, text/richtext, multipart/mixed, multipart/alternative, multipart/parallel, multipart/digest, message/rfc822, message/partial, message/external-body, and message/news. This support is incomplete for many subtypes -- for example, it only supports US-ASCII text in general. This kind of built-in support can be OVERRIDDEN by an entry in any mailcap file on the user's search path. Metamail also has rudimentary built-in support for types that are totally unrecognized -- i.e. for which no mailcap entry or built-in handler exists. For such unrecognized types, metamail will write a file with a "clean" copy of the data -- i.e. a copy in which all mail headers have been removed, and in which any 7-bit transport encoding has been decoded.

FILES

$HOME/.mailcap:/etc/mailcap:/usr/etc/mailcap:/usr/local/etc/mailcap -- default path for mailcap files.
