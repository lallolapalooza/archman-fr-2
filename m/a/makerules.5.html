NOM

makerules - Guide du programmeur système pour compiler des projets sur différentes plateformes

SYNTAXE

SRCROOT= ..
RULESDIR= RULES
include $(SRCROOT)/$(RULESDIR)/rules.top
les définitions locales sont ici
include $(SRCROOT)/$(RULESDIR)/rules.*

Voir le chapitre TYPES DE CIBLES ACTUELLEMENT PRIS EN CHARGE pour les valeurs possibles de rules.*.

DESCRIPTION

Makerules est un ensemble de règles qui permet la compilation de projets structurés avec des Makefiles petits et uniformément structurés. Toutes les règles sont situées dans un répertoire central. La compilation des projets sur différentes plateformes peut être effectuée simultanément sans avoir besoin de modifier aucun des Makefiles situés dans les répertoires des projets.

Makerules est un ensemble d'outils de portabilité de haut niveau, supérieur à autoconf et plus facile à utiliser.

Trois programmes make sont actuellement pris en charge : Sunpro make, GNU make et smake. Si vous souhaitez ajouter la prise en charge d'autres programmes make, lisez les sections sur les exigences minimales pour un programme make et sur la structure du système de règles make.

Ce manuel aidera les programmeurs qui ont besoin d'apporter des modifications au système de règles make lui-même. Si vous voulez savoir quelque chose sur l'utilisation du système de Makefiles, consultez makefiles(4).

L'objectif principal de conception était de n'avoir qu'une seule définition à un seul endroit dans les règles make. Cela implique que les programmeurs système qui souhaitent ajouter ou modifier des règles doivent suivre cet objectif afin de ne pas détruire la fonctionnalité ailleurs.

Le résultat visible pour l'utilisateur est un ensemble de Makefiles petits et faciles à lire, chacun situé dans le répertoire feuille du projet et donc appelé makefile feuille.

Chacun de ces Makefiles feuilles ne contient en fait aucune règle. Il définit simplement quelques macros pour le programme make et inclut deux fichiers d'un dépôt central de règles make. Ces fichiers inclus définissent les règles nécessaires pour compiler le projet.

Chaque makefile feuille est formé de manière très simple :

•
Il définit d'abord deux macros qui définissent l'emplacement relatif du répertoire racine du projet et le nom du répertoire contenant l'ensemble complet des règles, puis il inclut le fichier de règles rules.top depuis le répertoire qui forme le dépôt central de règles. Vous n'avez qu'à modifier la macro SRCROOT pour refléter l'emplacement relatif du répertoire racine du projet.
•
La partie suivante d'un makefile feuille définit des macros qui décrivent la cible et la source. Vous ne pouvez avoir qu'une seule cible par makefile feuille. Bien sûr, il peut y avoir de nombreux fichiers source nécessaires pour créer cette cible. Si vous souhaitez créer plus d'une cible dans un répertoire spécifique, vous devez placer plus d'un makefile dans ce répertoire. C'est la partie d'un makefile qui décrit une cible unique. Modifiez cette partie pour y inclure tous les fichiers source, tous les fichiers d'en-tête locaux et tous les indicateurs de compilation non globaux nécessaires à votre cible. Pour une cible typique, c'est aussi simple que de remplir un formulaire.
•
Chaque makefile feuille inclut finalement un fichier du répertoire des règles qui contient les règles pour le type de cible approprié qui doit être créé à partir de ce makefile feuille.

Le makefile dans chaque répertoire doit s'appeler Makefile. Si vous souhaitez avoir plus d'un makefile dans un répertoire spécifique, vous devez choisir des noms différents pour les autres Makefiles.

Types de cibles actuellement pris en charge

Il existe des règles pour les types de cibles suivants :

commandes
Les règles make pour les commandes utilisateur comme cat, ls etc. sont situées dans le fichier rules.cmd
pilotes
Les règles make pour les pilotes de périphériques sont situées dans le fichier rules.drv
bibliothèques
Les règles make pour les bibliothèques non partagées sont situées dans le fichier rules.lib
bibliothèques partagées
Les règles make pour les bibliothèques partagées sont situées dans le fichier rules.shl
fichiers localisés
Les règles make pour les fichiers localisés sont situées dans le fichier rules.loc
fichiers non localisés
Les règles make pour les fichiers non localisés sont situées dans le fichier rules.aux
scripts shell
Les règles make pour les scripts shell (une variante des fichiers localisés) sont situées dans le fichier rules.scr
pages de manuel
Les règles make pour les pages de manuel (une variante des fichiers localisés) sont situées dans le fichier rules.man
Makefiles redirigés
Les règles make pour les projets qui nécessitent plus d'un makefile dans un répertoire spécifique sont situées dans le fichier rules.mks Il contient une règle qui redirige vers les sous-Makefiles listés. Chaque sous-makefile peut être de n'importe quel type.
répertoires
Les règles make pour les sous-répertoires sont situées dans le fichier rules.dir

Exigences minimales pour un programme make

Les règles make prennent actuellement en charge Sunpro make, GNU make et smake. Si vous souhaitez ajouter la prise en charge d'autres programmes make, ils doivent posséder des fonctionnalités minimales qui vont au-delà des capacités du programme make standard de UNIX. BSDmake pourrait être pris en charge s'il prend correctement en charge les règles de correspondance de motifs.

inclure
Le programme make doit être capable d'inclure récursivement d'autres fichiers à partir d'un makefile. Le nom du fichier à inclure doit pouvoir être une macro. Le programme make doit pouvoir le faire de telle sorte que si le fichier à inclure est le résultat d'une règle make. par exemple, si le fichier à inclure n'existe pas ou est obsolète, il doit être construit avant qu'une tentative ne soit faite pour l'inclure réellement.
ajout à une macro
Une référence de macro de la forme :

macro += addval

devrait ajouter addval à la chaîne actuellement contenue dans macro.

remplacement de macro par suffixe
Une référence de macro de la forme :

out= $(macro:string1=string2)

devrait remplacer un suffixe string1 par string2 dans tous les mots contenus dans macro, où string1 est soit un suffixe, soit un mot à remplacer dans la définition de la macro, et string2 est le suffixe ou le mot de remplacement. String1 et string2 doivent être remplacés correctement même s'ils sont eux-mêmes des macros. Les mots dans une valeur de macro sont séparés par ESPACE, TAB et les caractères NEWLINE échappés.

remplacement de macro par motif
Une référence de macro de la forme :

out= $(macro:op%os=np%ns)

devrait remplacer un motif central dans macro, où op est le préfixe existant (ancien) et os est le suffixe existant (ancien), np et ns sont respectivement le nouveau préfixe et le nouveau suffixe, et le motif correspondant à % (une chaîne de zéro caractère ou plus) est conservé de la valeur remplacée. Par exemple :

PROGRAM=fabricate
DEBUG= $(PROGRAM:%=tmp/%-g)

définit la valeur de DEBUG à tmp/fabricate-g. Op, os, np et ns doivent être remplacés correctement même s'ils sont eux-mêmes des macros.

Comprendre les algorithmes de base

L'un des algorithmes de base utilisés dans le système de règles make est nécessaire pour définir une macro non définie

o à une valeur par défaut garantie. Comme tous les programmes de génération ne prennent pas en charge les structures si alors sinon, une méthode différente doit être utilisée.

La méthode utilisée dans les règles de génération est implémentée en utilisant le remplacement de macro par suffixe et le remplacement de macro par motif.

Premièrement, une macro contenant un suffixe unique est définie :

# Définir le cookie unique magique
_UNIQ= .XxZzy-

Cette macro est utilisée pour tous les endroits où il est nécessaire d'avoir une macro avec une valeur par défaut garantie. L'exemple suivant montre l'algorithme de base qui est utilisé pour implémenter la phrase : Si $(MAKE_NAME) contient une valeur, alors $(XMAKEPROG) sera défini sur $(MAKE_NAME) sinon $(XMAKEPROG) sera défini sur $(MAKEPROG).

_MAKEPROG= $(_UNIQ)$(MAKE_NAME)
__MAKEPROG= $(_MAKEPROG:$(_UNIQ)=$(MAKEPROG))
XMAKEPROG= $(__MAKEPROG:$(_UNIQ)%=%)

La première ligne de cet exemple définit la macro _MAKEPROG par la concaténation de la valeur de MAKE_NAME et de .XxZzy-. Si la macro MAKE_NAME est vide à ce moment, _MAKEPROG ne contiendra que .XxZzy-.

Dans la deuxième ligne, __MAKEPROG est défini sur la valeur de _MAKEPROG. Si _MAKEPROG ne contient que .XxZzy-, cela implique que .XxZzy- est le suffixe. Ce suffixe est alors remplacé par la valeur de MAKEPROG ; dans ce cas, __MAKEPROG contiendra la valeur non modifiée de MAKEPROG. Si _MAKEPROG contient une concaténation de .XxZzy- et d'autre chose, .XxZzy- ne sera pas un suffixe, mais un préfixe de _MAKEPROG et pour cette raison __MAKEPROG contiendra la valeur non modifiée de _MAKEPROG, qui est une concaténation de .XxZzy- et de la valeur de MAKE_NAME.

Dans la troisième ligne, XMAKEPROG est défini sur la valeur de __MAKEPROG. Si __MAKEPROG a le préfixe .XxZzy- à ce moment, .XxZzy- en sera supprimé.

La Structure des Noms de Macros de Génération

Les noms utilisés pour les macros de génération sont structurés de manière à permettre l'utilisation de grep(1) pour rechercher les noms dans les règles de génération. Pour permettre cela, aucun nom ne doit être une sous-chaîne d'un autre nom.

Si une commande nécessite des options qui doivent être spécifiées dans des macros, il existe une macro de génération nommée XXXFLAGS. Ceci est conforme aux règles habituelles des fichiers de génération. Il existe des macros de génération internes appelées XXXOPTS et XXXOPTX qui seront combinées pour XXXFLAGS :

LDFLAGS= $(LDOPTS) $(LDOPTX)

Où XXXOPTS est le nom de la macro utilisée en interne et XXXOPTX est le nom de la macro qui peut être utilisée depuis la ligne de commande du programme de génération. XXXOPTX est donc utilisé pour ajouter au contenu de XXXFLAGS. Si la valeur de XXXFLAGS doit être écrasée, XXXOPTS peut être utilisé dans les options de la ligne de commande du programme de génération.

La Structure du Système de Règles de Génération

La Structure des Règles de Base dans rules.top

Le fichier RULES/rules.top inclut d'abord un fichier de règles qui dépend du programme de génération utilisé. Le nom de ce fichier est RULES/mk-makeprog.id où makeprog doit être remplacé par le nom réel du programme de génération, par exemple make, gmake, smake. Le but de ce fichier est de configurer une liste de macros qui identifient le système sur lequel le projet est actuellement construit. Ces macros ont des valeurs ne contenant que des lettres minuscules et définissent :

l'architecture du processeur
Si deux systèmes exécutent le même système d'exploitation, c'est une valeur unique si un simple programme utilisateur n'a pas besoin d'être recompilé pour fonctionner sur l'autre système. Les valeurs possibles sont sparc, mc68020, pentium. C'est la sortie de uname -p. La valeur est stockée dans P_ARCH.
l'architecture du noyau
Si deux systèmes peuvent utiliser la même valeur pour P_ARCH mais qu'un programme utilisateur fortement dépendant du système a besoin d'être recompilé pour fonctionner sur l'autre système, ces deux systèmes ont des architectures de noyau différentes. C'est la sortie de uname -m. Les valeurs possibles sont sun3, sun4c, sun4m. La valeur est stockée dans K_ARCH.
l'architecture de la machine
Une macro obsolète utile uniquement sur les systèmes Sun. N'utilisez pas ceci, utilisez P_ARCH à la place. C'est la sortie de arch. Les valeurs possibles sont sun3, sun4. La valeur est stockée dans M_ARCH.
le nom d'hôte
Le nom de la machine sur laquelle la compilation a lieu. C'est la sortie de uname -n. La valeur est stockée dans HOSTNAME.
le nom du système d'exploitation
C'est la sortie de uname -s. Les valeurs possibles sont sunos, dgux, hp-ux, irix. La valeur est stockée dans OSNAME.
la version du système d'exploitation
C'est la sortie de uname -r. Les valeurs possibles sont 5.5, 4.1.4. La valeur est stockée dans OSREL.

Le fichier suivant à inclure à partir de RULES/rules.top est RULES/os-système d'exploitation.id. Il définit les macros O_ARCH et -O_ARCH et peut modifier l'une des macros qui sont définies dans RULES/mk-makeprog.id. Les macros O_ARCH et -O_ARCH sont utilisées pour distinguer les différents systèmes d'exploitation. Les noms des fichiers de configuration du compilateur ont -O_ARCH comme partie centrale. Sur certains systèmes d'exploitation, par exemple SunOS et DG-UX, il est nécessaire de distinguer entre SunOS 4.x et SunOS 5.x ou DG-UX 3.x et DG-UX 4.x.

Le fichier suivant à inclure à partir de RULES/rules.top est Defaults. Il définit les macros DEFCCOM , DEFINCDIRS , LDPATH , RUNPATH , INS_BASE et INS_KBASE. Si les définitions doivent être différentes sur différents systèmes, ce fichier peut contenir une ligne sous la forme :

include $(SRCROOT)/Defaults.$(O_ARCH)

Les définitions réelles devront alors être déplacées dans ces fichiers.

Ensuite, après avoir défini quelques valeurs par défaut internes, RULES/rules.top inclut le fichier de configuration du compilateur dont le nom est :

$(SRCROOT)/$(RULESDIR)/$(XARCH).rul

Ce fichier contient tout le matériel dépendant du système nécessaire pour configurer le compilateur C sur le système approprié. C'est une mauvaise idée d'en créer un nouveau à partir de zéro. Regardez les autres fichiers de configuration du compilateur et modifiez un fichier similaire pour vos besoins. Notez qu'il y a fondamentalement deux critères importants dans un fichier de configuration de compilateur. L'un est de savoir si le système utilise le format d'en-tête ELF ou non. L'autre est de savoir si le système utilise des bibliothèques partagées ou non.

La Structure des Règles Spécifiques à l'Application

Les fichiers de règles spécifiques à l'application sont conçus de manière à inclure tout le matériel nécessaire pour cette tâche spécifique. Les fichiers de règles spécifiques à l'application sont :

$(RULES)/rules.aux
Règles pour installer des fichiers auxiliaires non localisés.
$(RULES)/rules.cmd
Règles pour les commandes comme sh.
$(RULES)/rules.dir
Règles pour les sous-répertoires.
$(RULES)/rules.drv
Règles pour les pilotes chargeables.
$(RULES)/rules.lib
Règles pour les bibliothèques statiques.
$(RULES)/rules.loc
Règles pour installer des fichiers auxiliaires localisés.
$(RULES)/rules.man
Règles pour installer des pages de manuel localisées.
$(RULES)/rules.mks
Règles pour les sous-makefiles.
$(RULES)/rules.mod
Règles pour les modules de flux chargeables.
$(RULES)/rules.scr
Règles pour installer des scripts shell localisés.
$(RULES)/rules.shl
Règles pour les bibliothèques partagées.

Comprendre la Structure du Système de Règles de Génération

Pour comprendre la structure du système de règles de génération lors de modifications, essayez d'utiliser l'option -xM dans le programme smake. Cette option affichera la liste des dépendances d'inclusion (c'est-à-dire une liste qui indique quelle règle de génération est incluse par quelle autre règle).

Notez que certaines règles dépendent du programme de génération. Si vous souhaitez apporter des modifications à ces règles, vous devrez peut-être placer les définitions dans des fichiers de règles séparés, chacun pour le programme de génération approprié. Regardez dans le répertoire RULES pour quelques exemples.

DIAGNOSTICS

Les messages de diagnostic dépendent du programme de génération. Consultez la page de manuel appropriée.

NOTES

Les règles de génération peuvent être utilisées avec Sunpro make, Gnu make et smake. Bien que Gnu make fonctionne sur de nombreuses plateformes, il n'a pas de sortie de débogage utile.

Utilisez Sunpro make ou smake si vous avez des problèmes avec un makefile. Sunpro make et smake, tous deux ont un drapeau -D, qui vous permet de visualiser les makefiles après la première expansion. Utilisez cette option si vous avez des doutes quant à l'expansion correcte de votre makefile et si les bonnes règles sont incluses. Il existe également une option -d qui fournit une sortie de débogage.

OPTIONS

Le programme smake a un certain nombre d'options qui contrôlent son comportement. Les options qui augmentent la verbosité sont notamment :

-v
Active le mode verbeux. Affiche les règles et les commandes avant qu'elles ne soient exécutées. Peut être spécifié plusieurs fois pour augmenter la verbosité.
-d
Augmente le niveau de débogage. Les niveaux plus élevés (par ex. -dd, -ddd) fournissent des informations de débogage plus détaillées.
-xM
Affiche les dépendances d'inclusion pour les règles make. Utile pour comprendre comment les règles sont incluses et gérées.

Lorsque make est en cours d'exécution, si vous souhaitez plus d'informations, utilisez -dd, -ddd et ainsi de suite.

Smake a une option -xM qui vous montre la dépendance d'inclusion pour les règles make.
