NOM

mandocd — processus serveur pour formater les pages de manuel en mode batch

SYNTAXE

mandocd [-I os=nom] [-T sortie] descripteur_socket

DESCRIPTION

L'utilitaire mandocd formate de nombreuses pages de manuel sans nécessiter de surcharge de fork(2) et exec(3) entre les opérations. Il ne nécessite pas de lister tous les manuels à formater sur la ligne de commande et prend en charge l'écriture de chaque manuel formaté vers son propre descripteur de fichier.

Ce serveur nécessite qu'un socket(2) de domaine UNIX connecté soit déjà présent au moment de l'exec(3). Par conséquent, il ne peut pas être démarré depuis la ligne de commande sh(1) car le shell ne peut pas fournir un tel socket. Typiquement, le socket est créé par le processus parent à l'aide de socketpair(2) avant d'appeler fork(2) et exec(3) sur mandocd. Le processus parent passera le numéro du descripteur de fichier comme argument à exec(3), formaté comme un entier décimal codé en ASCII. Voir catman(8) pour une implémentation typique d'un processus parent.

mandocd boucle en lisant des messages d'un octet avec recvmsg(2) depuis le descripteur de fichier numéro descripteur_socket. Il ignore l'octet lu et utilise uniquement les données de contrôle auxiliaires hors bande de type struct cmsghdr, typiquement fournies par le processus appelant à l'aide de CMSG_FIRSTHDR(3). Le processus parent est censé passer trois descripteurs de fichier avec chaque octet factice. Le premier est utilisé pour l'entrée mdoc(7) ou man(7), le second pour la sortie formatée et le troisième pour la sortie d'erreur.

Les options sont les suivantes :

-I os=nom
Remplace le nom du système d'exploitation par défaut nom pour la macro Os de mdoc(7) et pour la macro TH de man(7).
-T sortie
Format de sortie. L'argument sortie peut être ascii, utf8, ou html ; voir mandoc(1). En mode de sortie html, l'option de sortie fragment est implicite. D'autres options de sortie ne sont pas prises en charge.

Après avoir épuisé un descripteur de fichier d'entrée, les trois descripteurs de fichier sont fermés avant de lire le prochain octet factice et le message de contrôle.

mandocd se termine lorsqu'un message de taille nulle est lu, lorsque le descripteur_socket est fermé par le processus parent, ou lorsqu'une erreur se produit.

STATUT DE SORTIE

L'utilitaire mandocd se termine avec le code 0 en cas de succès, et avec un code  >0 en cas d'erreur.

Un message de taille nulle ou un descripteur_socket fermé est considéré comme un succès. Les erreurs possibles incluent :

  • arguments d'exec(3) manquants, invalides ou excessifs
  • échec de recvmsg(2), par exemple en raison de EMSGSIZE
  • données de contrôle manquantes ou inattendues, en particulier un cmsg_level dans le struct cmsghdr différent de SOL_SOCKET, un cmsg_type différent de SCM_RIGHTS, ou un cmsg_len qui n'est pas trois fois la taille d'un int
  • descripteurs de fichier invalides passés dans le CMSG_DATA(3)
  • épuisement des ressources, en particulier échec de dup(2) ou malloc(3)

À l'exception de l'épuisement de la mémoire et des défaillances système similaires, les erreurs d'analyse et de formatage ne provoquent pas la renvoi d'un code de sortie d'erreur par mandocd. Même après de graves erreurs d'analyse, mandocd acceptera et traitera le descripteur de fichier d'entrée suivant.

VOIR AUSSI

mandoc(1), mandoc(3), catman(8)

HISTORIQUE

L'utilitaire mandocd est apparu dans la version 1.14.1 ou la mandoc toolkit.

AUTEURS

Le concept a été conçu et implémenté par Michael Stapelberg <stapelberg@debian.org>. La colle mandoc(3) nécessaire pour en faire un processus autonome a été ajoutée par Ingo Schwarze <schwarze@openbsd.org>.

CAVEATS

Si les pages de manuel analysées contiennent des requêtes .so de roff(7), mandocd doit être démarré avec le répertoire de travail courant défini à la racine de l'arborescence des pages de manuel. Évitez de le démarrer dans des répertoires contenant des fichiers secrets dans des sous-répertoires, en particulier si l'utilisateur qui le démarre a un accès en lecture à ces fichiers secrets.
