NAME

mdoc - Mono Documentation XML Format

DESCRIPTION

Les divers programmes de documentation Mono génèrent ou manipulent des fichiers XML qui suivent le schéma de documentation mono :

mdoc update
Crée ou met à jour la documentation XML mono pour un ensemble d'assemblages.
mdoc validate
Valide la documentation XML mono par rapport au schéma XML de documentation mono.
mdoc assemble
Convertit la documentation XML mono au sein d'une structure de répertoires en un ensemble de fichiers utilisables avec monodoc(1).
mdoc export-html
Convertit la documentation XML mono au sein d'une structure de répertoires en un ensemble de fichiers HTML qui peuvent être visualisés avec un navigateur web.

Tous ces outils (et d'autres) utilisent le schéma XML commun décrit dans cette page de manuel.

STRUCTURE DES FICHIERS/RÉPERTOIRES

Il existe trois ensembles de fichiers XML de documentation Mono :

*
index.xml : contient une liste de tous les assemblages présents dans le répertoire contenant, ainsi que de tous les types et espaces de noms au sein de ces assemblages.
*
ns-*.xml : Il y a un fichier ns-*.xml pour chaque espace de noms de l'assemblage ; ces fichiers sont frères de index.xml.

Exemples de fichiers ns-*.xml : ns-System.xml, ns-System.Collections.xml, et ns-.xml (pour l'espace de noms racine, bien qu'il soit recommandé de NE PAS placer de types dans l'espace de noms racine, car monodoc(1) ne les affiche pas).

Les fichiers ns-*.xml contiennent la documentation par espace de noms.

*
NamespaceName/TypeName.xml : Ces fichiers se trouvent dans un répertoire avec des points nommé NamespaceName, et TypeName est le nom du type.

Exemples : RootType.xml (si le type n'a pas d'espace de noms), System/String.xml, System.Collections/IEnumerable.xml, et System.Collections.Generic/List`1+Enumerator.xml (le `` `1`` est le nombre de paramètres de type générique que le type accepte, et tout ce qui suit le ``+`` est un type imbriqué).

Par conséquent, le contenu typique d'un répertoire ressemblerait à ceci :

    index.xml
    ns-System.xml
    ns-System.Collections.Generic.xml
    System/String.xml
    System.Collections.Generic/List`1.xml

FORMAT DE LA DOCUMENTATION

Format du fichier index.xml

Le fichier index.xml contient une liste des assemblages imbriqués sous le répertoire contenant index.xml, ainsi que tous les espaces de noms et types au sein de ces assemblages. Il ressemble à ceci :

    <Overview>
      <Assemblies>
        <Assembly Name="mscorlib" Version="2.0.0.0" />
        <!-- autres éléments <Assembly/>... -->
      </Assemblies>
      <Remarks>À ajouter.</Remarks>
      <Copyright>À ajouter.</Copyright>
      <Types>
        <Namespace Name="System">
          <Type Name="String" />
          <!-- Autres éléments <Type/> -->
        </Namespace>
        <Namespace Name="System.Collections.Generic">
          <Type Name="List`1" DisplayName="List&lt;T&gt;" />
          <!-- Autres éléments <Type/> -->
        </Namespace>
        <!-- autres éléments <Namespace/> -->
      </Types>
      <Title>DocTest</Title>
    </Overview>

La majeure partie de ceci est maintenue automatiquement, en particulier les éléments /Overview/Assemblies et /Overview/Types.

L'attribut //Namespace/@Name correspond à un répertoire qui contient des fichiers nommés //Type/@Name.xml, tandis que l'attribut //Type/@DisplayName contient un nom de type C# (si //Type/@DisplayName n'est pas trouvé, alors //Type/@Name est utilisé comme nom d'affichage). Il devrait également y avoir un fichier ns-[//Namespace/@Name].xml.

Il y a trois éléments qui intéressent les auteurs : /Overview/Remarks, /Overview/Copyright, et /Overview/Title, qui contiennent la documentation au niveau de l'assemblage. Ces éléments peuvent contenir l'un des éléments XML suivants (documentés dans la section Éléments XML de documentation) : block, code, example, list, para, paramref, typeparamref, see, et ul.

Format du fichier ns-*.xml

Les fichiers ns-*.xml contiennent la documentation des espaces de noms :

    <Namespace Name="System">
      <Docs>
        <summary>À ajouter.</summary>
        <remarks>À ajouter.</remarks>
      </Docs>
    </Namespace>

Les éléments /Namespace/Docs/summary et /Namespace/Docs/remarks doivent contenir la documentation de l'espace de noms.

Les éléments remarks et summary sont documentés dans la section Éléments XML de documentation.

Format du fichier NamespaceName/TypeName.xml

Le format de documentation Mono est similaire au format de documentation Ecma, tel que décrit dans ECMA-335 3ème Édition, Partition IV, Chapitre 7. La principale différence par rapport au format ECMA est que chaque type a son propre fichier, dans un répertoire identique à l'espace de noms du type. Il y a beaucoup d'informations qui sont maintenues automatiquement par mdoc(1) ; la plupart des informations dans la documentation ne devraient pas être modifiées. Cela inclut le nom du type (/Type/@FullName), les interfaces implémentées (/Type/Interfaces), les informations sur les membres (/Type/Members/Member/@MemberName, /Type/Members/Member/MemberSignature, /Type/Members/Member/MemberType, /Type/Members/Member/Parameters, etc.).

    <Type Name="DocAttribute" FullName="Mono.DocTest.DocAttribute">
      <TypeSignature Language="C#" Value="public class DocAttribute : Attribute" />
      <AssemblyInfo>
        <AssemblyName>DocTest</AssemblyName>
        <AssemblyVersion>0.0.0.0</AssemblyVersion>
      </AssemblyInfo>
      <Base>
        <BaseTypeName>System.Attribute</BaseTypeName>
      </Base>
      <Interfaces />
      <Attributes>
        <Attribute>
          <AttributeName>System.AttributeUsage(System.AttributeTargets.All)</AttributeName>
        </Attribute>
      </Attributes>
      <Docs>
        <summary>À ajouter.</summary>
        <remarks>À ajouter.</remarks>
      </Docs>
      <Members>
        <Member MemberName=".ctor">
          <MemberSignature Language="C#" Value="public DocAttribute (string docs);" />
          <MemberType>Constructor</MemberType>
          <AssemblyInfo>
            <AssemblyVersion>0.0.0.0</AssemblyVersion>
          </AssemblyInfo>
          <Parameters>
            <Parameter Name="docs" Type="System.String" />
          </Parameters>
          <Docs>
            <param name="docs">À ajouter.</param>
            <summary>À ajouter.</summary>
            <remarks>À ajouter.</remarks>
          </Docs>
        </Member>
      </Members>
    </Type>

Les seuls éléments qui nécessitent normalement une modification sont les enfants des éléments //Docs, qui contiennent généralement le texte À ajouter. L'élément /Type/Docs contient la documentation au niveau du type, tandis que l'élément /Type/Members/Member/Docs contient la documentation par membre.

Les éléments //Docs peuvent contenir les éléments suivants : altcompliant, altmember, example, exception, param, permission, remarks, returns, since, summary, threadsafe, typeparam, et value.

Les types imbriqués ne sont pas des membres ; ce sont des types, et ils sont documentés dans leur propre fichier. Par conséquent, les fichiers NamespaceName/TypeName.xml ne sont pas récursifs ; vous ne stockez pas un élément <Type/> à l'intérieur d'un élément <Type/>.

Éléments XML de documentation

Le contenu de

l'élément Docs est identique en sémantique et en structure au format de documentation C# en ligne, composé de ces éléments (listés dans ECMA-334 3ème Édition, Annexe E, Section 2). Les éléments suivants sont utilisés dans les descriptions des éléments :

CREF
Fait référence à une référence de classe (ou de membre), et est une chaîne dans le format décrit ci-dessous dans la section FORMAT CREF.
TEXTE
Texte non XML, et aucun XML ne doit être imbriqué.
XML
Seuls des éléments XML doivent être imbriqués (qui peuvent indirectement contenir du texte), mais le texte non blanc ne doit pas être un nœud enfant immédiat.
TEXTE_XML
Texte et XML libres, de sorte que d'autres éléments XML puissent être imbriqués.

Les éléments suivants sont utilisés dans la documentation :

<altmember cref="CREF" />
<altmember/> est un élément de niveau supérieur, et doit être imbriqué directement sous l'élément <Docs/>.

Permet de générer une entrée pour la section Voir aussi. Utilisez <see/> pour spécifier un lien depuis le texte.

    <altmember cref="P:System.Exception.Message" />
<block subset="SOUSENSEMBLE" type="TYPE">TEXTE_XML</block>
Crée un bloc de texte, similaire en concept à un paragraphe, mais utilisé pour créer des divisions dans le texte. Dans une certaine mesure, un <block/> est équivalent à la balise HTML <h2/>.

SOUSENSEMBLE doit toujours être la valeur "none".

TYPE spécifie le titre et le formatage à utiliser. Les types reconnus sont :

behaviors Crée une section avec le titre Opération.

note Crée une section avec le titre Note :.

overrides Crée une section avec le titre Note aux héritiers.

usage Crée une section avec le titre Utilisation.

L'élément block peut contenir les éléments suivants : block, c, code, list, para, paramref, see, subscript, sup, et typeparamref.

<c>TEXTE_XML</c>
Définit le texte dans une police de code (similaire à l'élément HTML <tt/>).

L'élément c peut contenir les éléments suivants : code, para, paramref, see, et typeparamref.

<code lang="LANGAGE" src="SOURCE">TEXTE</code>
Affiche plusieurs lignes de texte dans une police de code (similaire à l'élément HTML <pre/>).

LANGAGE est la langue pour ce bloc de code. Par exemple, si LANGAGE est C#, alors TEXTE obtiendra une coloration syntaxique pour le langage C# dans le Navigateur de Documentation Mono.

SOURCE n'est interprété que par mdoc-update(1). Si l'attribut src est présent lors de l'exécution de mdoc-update(1), alors SOURCE est un fichier (relatif au répertoire --out de mdoc-update(1)) qui doit être inséré comme valeur pour le TEXTE. Le contenu de TEXTE sera ignoré par mdoc-update(1) et remplacé à chaque invocation. SOURCE peut également contenir une « ancre », par exemple src="path/to/file.cs#RegionMarker". Si une ancre est présente, *et* que LANGAGE est C#, alors #region RegionMarker sera recherché, et le contenu entre le #region et le #endregion suivant sera inséré comme valeur pour l'élément TEXTE.

<example>TEXTE_XML</example>
Indique un exemple qui doit être affiché de manière spéciale. Par exemple : 
    <example>
      <para>Un paragraphe d'introduction.</para>
      <code lang="C#">
        class Example {
          public static void Main ()
          {
            System.Console.WriteLine ("Hello, World!");
          }
        }
      </code>
    </example>

L'élément example peut contenir les éléments suivants : c, code, list, para, et see.

<exception cref="CREF">TEXTE_XML</exception>
Identifie une exception qui peut être lancée par le membre documenté.

<exception/> est un élément de niveau supérieur, et doit être imbriqué directement sous l'élément <Docs/>.

CREF est le type d'exception qui est lancée, tandis que TEXTE_XML contient les circonstances qui provoqueraient le lancement de CREF.

    <exception cref="T:System.ArgumentNullException">
      <paramref name="foo" /> était <see langword="null" />.
    </exception>

L'élément exception peut contenir les éléments suivants : block, para, paramref, see, et typeparamref.

<format type="TYPE">TEXTE_XML</format>
L'élément <format/> est une « échappatoire », pour inclure (éventuellement du contenu XML) qui n'est pas un contenu valide mdoc(5). C'est l'équivalent moral des blocs =begin format de perlpod(1).

TYPE est le type mime de TEXTE_XML. Les processeurs mdoc(5) peuvent ignorer les blocs format/> s'ils utilisent un type non supporté.

Par exemple :

    <format type="text/html">
      <table width="100%">
        <tr><td style="color:red">Hello, world!</td></tr>
      </table>
    </format>

entraînerait l'insertion de l'élément <table/> HTML embarqué en ligne dans le document HTML résultant lorsque mdoc-export-html(1) traite le fichier. (De même, il peut être ignoré s'il est traité par un autre programme.)

format/> est destiné à simplifier l'importation de documentation à partir de sources de documentation existantes. Il ne faut pas s'y fier, si possible.

<list>XML</list>
Crée une liste ou un tableau d'éléments. <list/> utilise les éléments imbriqués <item>XML</item>, <listheader>XML</listheader>, <term>TEXTE_XML</term>, et <description>TEXTE_XML</description>.

Les Listes ont la syntaxe :

    <list type="bullet"> <!-- ou type="number" -->
      <item><term>Puce 1</term></item>
      <item><term>Puce 2</term></item>
      <item><term>Puce 3</term></item>
    </list>

Les Tableaux ont la syntaxe :

    <list type="table">
      <listheader> <!-- listheader met en gras cette ligne -->
        <term>Colonne 1</term>
        <description>Colonne 2</description>
        <description>Colonne 3</description>
      </listheader>
      <item>
        <term>Élément 1-A</term>
        <description>Élément 1-B</description>
        <description>Élément 1-C</description>
      </item>
      <item>
        <term>Élément 2-A</term>
        <description>Élément 2-B</description>
        <description>Élément 2-C</description>
      </item>
    </list>

Les éléments item et description peuvent chacun contenir du texte et les éléments suivants : block, c, para, paramref, see, sup, et typeparamref.

<para>TEXTE_XML</para>
Insère un paragraphe de TEXTE_XML. Par exemple, 
    <para>
      Ceci est un paragraphe de texte.
    </para>

L'élément para peut contenir les éléments suivants : block, c, example, link, list, onequarter, paramref, see, sub, sup, typeparamref, et ul.

<param name="NOM">TEXTE_XML</param>
<param/> est un élément de niveau supérieur, et doit être imbriqué directement sous l'élément <Docs/>.

Décrit le paramètre NOM du constructeur, de la méthode ou de la propriété actuelle :

    <param name="count">
      Un <see cref="T:System.Int32" /> contenant le nombre
      de widgets à traiter.
    </param>

L'élément param peut contenir les éléments suivants : block, c, example, para, paramref, see, et typeparamref.

<paramref name="NOM" />
Indique que NOM est un paramètre.

Cela rend généralement NOM en texte italique, il est donc fréquemment (mal) utilisé comme un équivalent de l'élément HTML <i/>. Voir la documentation de <exception/> (ci-dessus) pour un exemple.

<permission cref="CREF">TEXTE_XML</permission>
Documente les exigences d'accessibilité de sécurité du membre actuel.

<permission/> est un élément de niveau supérieur, et doit être imbriqué directement sous l'élément <Docs/>.

CREF est une référence de type à la permission de sécurité requise, tandis que TEXTE_XML est une description de la raison pour laquelle la permission est requise.

    <permission cref="T:System.Security.Permissions.FileIOPermission">
      Nécessite la permission de lire et d'écrire des fichiers. Voir
      <see cref="F:System.Security.Permissions.FileIOPermissionAccess.Read" />,
      <see cref="F:System.Security.Permissions.FileIOPermissionAccess.Write" />.
    </permission>

L'élément permission peut contenir les éléments suivants : block, para, paramref, see, et typeparamref.

<remarks>TEXTE_XML</remarks>
Contient des informations détaillées sur un membre.

<remarks/> est un élément de niveau supérieur, et doit être imbriqué directement sous l'élément <Docs/>. 

    <remarks>
      Insérez des informations détaillées ici.
    </remarks>

DESCRIPTION

Les documents XML générés par les outils de documentation Mono (comme mdoc(1)) utilisent des balises XML pour décrire les types et les membres d'une bibliothèque.

XML DOCUMENTATION TAGS

Voici une liste des balises XML courantes utilisées dans la documentation des bibliothèques Mono.

<altmember cref="CREF" />
Un membre alternatif. Utilisé pour lier vers un autre membre qui est fonctionnellement similaire, par exemple, un membre précédent dans une version antérieure de l'API.
<assembly name="NAME" />
Définit le nom de l'assembly auquel ce document appartient.
<code>XML_TEXT</code>
Formate le texte comme du code. Les balises internes telles que <see> seront traitées.
<example>XML_TEXT</example>
Décrit un exemple d'utilisation du type ou du membre.
<exception cref="CREF">XML_TEXT</exception>
Décrit une exception levée par la méthode.
<list type="TYPE">...</list>
Crée une liste. Le type peut être bullet, number, table.
<listheader><term>NAME</term><description>DESC</description></listheader>
Utilisé dans les listes de type table pour définir les en-têtes.
<listheader><item><term>NAME</term><description>DESC</description></item></listheader>
Utilisé dans les listes de type table pour définir les éléments.
<param name="NAME">XML_TEXT</param>
Décrit un paramètre de méthode. NAME est le nom du paramètre.
<paramref name="NAME">
Indique que NAME est un paramètre de méthode.
<permission cref="CREF">XML_TEXT</permission>
Décrit une autorisation requise pour accéder au membre.
<remarks>XML_TEXT</remarks>

<remarks/> est un élément de niveau supérieur, et devrait être imbriqué directement sous l'élément <Docs/>.

Fournit des informations supplémentaires sur le type ou le membre de type, au-delà du résumé.

L'élément remarks peut contenir les éléments suivants : block, c, code, example, list, para, paramref, see, et typeparamref.

<returns>XML_TEXT</returns>

<returns/> est un élément de niveau supérieur, et devrait être imbriqué directement sous l'élément <Docs/>.

Décrit la valeur de retour d'une méthode :

    <returns>
      Un <see cref="T:System.Boolean" /> spécifiant si
      le processus peut ou non accéder
      à <see cref="P:Mono.Unix.UnixFileSystemInfo.FullName" />.
    </returns>

L'élément returns peut contenir les éléments suivants : c, format, list, para, paramref, see, et typeparamref.

<see cref="CREF" />, <see langword="LANGWORD" />
Crée un lien vers le membre spécifié dans le texte courant : 
    <see cref="M:Some.Namespace.With.Type.Method" />

ou spécifie que LANGWORD est un mot-clé du langage :

    <see langword="null" />
<seealso cref="CREF" />
N'utilisez pas seealso, utilisez altmember.
<since version="VERSION" />

<since/> est un élément de niveau supérieur, et devrait être imbriqué directement sous l'élément <Docs/>.

Permet de spécifier quelle version a introduit le type ou le membre spécifié.

    <since version="Gtk# 2.4" />

Ce n'est généralement pas nécessaire, car les éléments //AssemblyInfo/AssemblyVersion suivent quelles versions d'assembly contiennent le type ou le membre.

<summary>XML_TEXT</summary>

<summary/> est un élément de niveau supérieur, et devrait être imbriqué directement sous l'élément <Docs/>.

Fournit un aperçu (bref !) d'un type ou d'un membre de type.

Ceci est généralement affiché dans le cadre de la déclaration d'une classe, et devrait être une description raisonnablement courte du type/membre. Utilisez <remarks/> pour des informations plus détaillées.

L'élément summary peut contenir les éléments suivants : block, list, para, paramref, see, et typeparamref.

<typeparam name="NAME">XML_TEXT</typeparam>
<typeparam/> est un élément de niveau supérieur, et devrait être imbriqué directement sous l'élément <Docs/>.

Ceci est utilisé pour documenter un paramètre de type pour un type générique ou une méthode générique.

NAME est le nom du paramètre de type, tandis que XML_TEXT contient une description du paramètre (son utilité, les restrictions qu'il doit respecter, etc.).

    <typeparam name="T">
      Le type de la collection sous-jacente
    </typeparam>

L'élément typeparam peut contenir les éléments suivants : block, c, para, paramref, see, et typeparamref.

<typeparamref name="NAME">
Utilisé pour indiquer que NAME est un paramètre de type.
<value>XML_TEXT</value>
<value/> est un élément de niveau supérieur, et devrait être imbriqué directement sous l'élément <Docs/>.

Permet de décrire une propriété.

    <value>
      Un <see cref="T:System.String" /> contenant un nom de widget.
    </value>

L'élément value peut contenir les éléments suivants : block, c, example, list, para, paramref, see, et typeparamref.

FORMAT CREF

Les identifiants de chaîne (CREFs) sont utilisés pour faire référence à un type ou un membre d'un type. Les identifiants de chaîne sont documentés dans ECMA-334 3rd Edition, Annexe E.3.1. Ils consistent en un préfixe de type de membre, le nom complet du type (espace de noms + nom, séparés par .), éventuellement suivi du nom du membre et d'autres informations.

Préfixes de type de membre :

C:
Le CREF fait référence à un constructeur. La liste de paramètres (optionnelle) est entourée de parenthèses et suit le nom du type : C:System.String(System.Char,System.Int32).
E:
Le CREF fait référence à un événement. Le nom de l'événement suit le nom du type : E:System.AppDomain.AssemblyLoad.
F:
Le CREF fait référence à un champ. Le nom du champ suit le nom du type : F:System.Runtime.InteropServices.DllImportAttribute.SetLastError.
M:
Fait référence à un constructeur ou une méthode. Les constructeurs peuvent ajouter .ctor au nom du type (au lieu d'utiliser le format de constructeur C: ci-dessus), tandis que les méthodes ajoutent le nom de la méthode et un nombre (optionnel) de paramètres génériques. Les deux, constructeurs et méthodes, peuvent ajouter la liste des paramètres de la méthode entourée de parenthèses.

Exemples : M:System.Object..ctor, M:System.String..ctor(System.Char[]), M:System.String.Concat(System.Object), M:System.Array.Sort``1(``0[]), M:System.Collections.Generic.List`1..ctor, M:System.Collections.Generic.List`1.Add(`0).

N:
Fait référence à un espace de noms, par ex. N:System.
P:
Fait référence à une propriété. Si la propriété est un indexeur ou prend des paramètres, les types de paramètres sont ajoutés au nom de la propriété et entourés de parenthèses : P:System.String.Length, P:System.String.Chars(System.Int32).
T:
Le CREF fait référence à un type, avec le nombre de types génériques ajoutés : T:System.String, T:System.Collections.Generic.List`1, T:System.Collections.Generic.List`1.Enumerator.

Pour rendre les choses plus intéressantes, les types et membres génériques ont deux représentations : la représentation "non liée" (montrée dans les exemples ci-dessus), où les noms de classes ont le nombre de paramètres génériques ajoutés à leur nom. Il existe également une représentation "liée", où la liaison des paramètres génériques est listée entre '{' et '}' ou '<' et '>'. (L'utilisation de '<' et '>' est moins courante, car à l'intérieur d'un document XML, leurs entités de caractères échappées doivent être utilisées à la place, menant à '<' et '>'.)

Non liée :

*
T:System.Collections.Generic.List`1
*
T:System.Collections.Generic.Dictionary`2

Liée :

*
T:System.Collections.Generic.List{System.Int32}
*
T:System.Collections.Generic.List<System.Int32>
*
T:System.Collections.Generic.List&lt;System.Int32&gt;
*
T:System.Predicate{System.Action{System.String}}

Comme vous pouvez le voir, les variantes liées peuvent être arbitrairement complexes (tout comme les génériques).

De plus, si un paramètre générique est lié au paramètre générique d'un type ou d'une méthode, l'"indice" du paramètre générique du type/méthode est utilisé comme liaison, donc étant donné

    class FooType {
      public static void Foo<T> (System.Predicate<T> predicate)
      {
      }
    }

Le CREF pour cette méthode est M:FooType.Foo``1(System.Predicate{``0}), ``0 est l'indice du 0ème paramètre générique qui est lié à System.Predicate<T>.
