FBB::Milter(3bobcat) Interface Milter FBB::Milter(3bobcat)

NOM

FBB::Milter - Interface aux installations de filtrage de courrier de sendmail

SYNOPSIS

#include <bobcat/milter>
Option de liaison : -lmilter -lbobcat

DESCRIPTION

Milter définit une classe de base abstraite s'interfaçant avec les installations de filtre de courrier (milter) de sendmail. Elle définit une interface C++, basée sur l'hypothèse qu'un seul programme de filtre de courrier n'implémente pas plusieurs filtres de courrier. L'API Milter traditionnelle basée sur C utilise un pointeur (SMFICTX) représentant une connexion de courrier, et un pointeur vers des données 'privées' spécifiques à la connexion, nécessitant au constructeur Milter d'effectuer de nombreuses tâches administratives. Bien que cela soit acceptable dans un environnement C, ces tâches administratives détournent de la tâche principale : la fonctionnalité de filtrage de courrier du Milter. La classe FBB::Milter masque ces tâches administratives du programmeur, qui peut ainsi se concentrer sur le filtrage du courrier. Les principaux avantages de Milter sont donc :

o
L'administration de base est effectuée par la classe Milter
o
L'interface de la classe est plus orientée C++ que l'interface C brute offerte par l'API milter.
o
L'administration, l'allocation et la communication de données spécifiques à la connexion ne sont plus requises
o
Il n'est normalement plus nécessaire d'utiliser des données spécifiques à la connexion, comme un pointeur identifiant la connexion, lors de l'implémentation du Milter.
o
Milter utilise des modèles de conception actuels imposant des principes de logiciel réutilisable, simplifiant ainsi la construction du Milter réel. Pour activer un milter à partir du fichier de configuration sendmail.mc, utilisez, par exemple, INPUT_MAIL_FILTER(`name’, `S=socket’), où name est le nom du milter, et socket est le nom du socket. Voir également le membre setConnection ci-dessous.

FBB

ÉNUMÉRATIONS

La classe définit quatre énumérations. Une énumération est utilisée pour indiquer les fonctions de rappel qui doivent être appelées, la deuxième renomme les indicateurs qui peuvent être passés à sendmail pour indiquer quelles actions le milter est autorisé à effectuer. La troisième définit des valeurs d'état qui peuvent être utilisées pour informer sendmail comment traiter davantage un message. La quatrième définit les valeurs de retour. Les énumérations sont :

enum CallBack
Cette énumération contient les valeurs suivantes :

o
CONNECT :
Indique que le milter définit (remplace) la fonctionnalité de connexion. C'est la première fonction de rappel qui peut être appelée par sendmail ;
o
HELO :
Indique que le milter définit (remplace) la fonctionnalité helo. Cela indique que la fonction helo doit être appelée par sendmail, fournissant au milter des informations sur le client connecté ;
o
SENDER :
Indique que le milter définit (remplace) la fonctionnalité sender. Cela indique que la fonction sender doit être appelée par sendmail, fournissant au milter les informations d'enveloppe de l'expéditeur ;
o
RECIPIENT :
Indique que le milter définit (remplace) la fonctionnalité recipient. Cela indique que la fonction recipient doit être appelée par sendmail, fournissant au milter les informations d'enveloppe du destinataire ;
o
HEADER :
Indique que le milter définit (remplace) la fonctionnalité header. Cela indique que la fonction header doit être appelée par sendmail pour chaque en-tête d'e-mail utilisé dans le message courant ;
o
EOH :
Indique que le milter définit (remplace) la fonctionnalité end-of-header. Cela indique que la fonction eoh doit être appelée par sendmail une fois que toutes les lignes d'en-tête ont été traitées ;
o
BODY :
Indique que le milter définit (remplace) la fonctionnalité body. Cela indique que la fonction body doit être appelée par sendmail, proposant le corps du message au milter ;
o
EOM :
Indique que le milter définit (remplace) la fonctionnalité end-of-message. Cela indique que la fonction eom doit être appelée par sendmail, une fois que tous les éléments du message e-mail ont été traités ;
o
ABORT :
Indique que le milter définit (remplace) la fonctionnalité abort. La fonction abort peut être appelée par sendmail avant que eom ne soit appelée. Elle doit récupérer toutes les ressources utilisées par le message, mais ne pas supprimer la mémoire allouée par le milter, car c'est le rôle de close ;
o
CLOSE :
Indique que le milter définit (remplace) la fonctionnalité close. La fonction close doit supprimer toute mémoire (spécifique à la connexion) allouée par le milter. Elle peut être appelée 'hors séquence', c'est-à-dire même avant que connect ne soit appelée et les développeurs doivent anticiper cette possibilité lors de la rédaction de leur code close. En particulier, il est incorrect de supposer que le pointeur de contexte privé sera autre chose que 0 dans ce rappel ;
o
UNKNOWN :
Actuellement non utilisé. Réservé pour les versions dépassant la version 2 de l'API milter de sendmail ;
o
DATA :
Actuellement non utilisé. Réservé pour les versions dépassant la version 3 de l'API milter de sendmail ;
o
ALL_CALLBACKS :
Raccourci pour indiquer toutes les fonctionnalités de rappel. Les valeurs CallBack sont des indicateurs binaires. L'opérateur bit_or peut être utilisé pour les combiner, et l'opérateur bit_not peut être utilisé pour supprimer un indicateur de ALL_CALLBACKS (par exemple, ALL_CALLBACKS && ~ABORT).

enum Flags
Cette énumération contient les valeurs suivantes :

o
NO_FLAGS :
Aucun indicateur n'est défini ;
o
ADD_HEADERS :
Cet indicateur indique que le milter est autorisé à ajouter des en-têtes au message e-mail courant ;
o
ADD_RECIPIENTS :
Cet indicateur indique que le milter est autorisé à ajouter des destinataires au message e-mail courant ;

CHANGE_BODY :

DELETE_RECIPIENTS :

QUARANTINE :
Cet indicateur indique que le milter est autorisé à demander à sendmail de mettre en quarantaine le message e-mail courant ;

Status
Cette énumération simplifie les valeurs étendues SMFIS_ utilisées par l'API C. Ces valeurs peuvent être utilisées pour retourner des valeurs sfsistat :

o
ACCEPT :
Cette valeur est égale à SMFIS_ACCEPT, indiquant que Sendmail doit accepter le message. Pour un rappel orienté connexion (voir ci-dessous dans PROTECTED VIRTUAL MEMBER FUNCTIONS), acceptez cette connexion sans traitement supplémentaire du filtre, appelez close (voir ci-dessous). Pour les autres rappels : acceptez ce message sans filtrage supplémentaire ;
o
CONTINUE :
Cette valeur est égale à SMFIS_CONTINUE, indiquant que Sendmail doit continuer le traitement. C'est la valeur par défaut pour toutes les fonctions de rappel qui ne sont pas remplacées par la classe dérivée de Milter ;
o
DISCARD :
Cette valeur est égale à SMFIS_DISCARD, indiquant que Sendmail doit rejeter le message électronique. Elle ne doit pas être retournée par un rappel orienté connexion. Pour les autres rappels : le message est accepté, mais silencieusement rejeté ;
o
REJECT :
Cette valeur est égale à SMFIS_REJECT, indiquant que Sendmail doit rejeter le message électronique. Pour un rappel orienté connexion, rejetez cette connexion ; appelez close. Pour un rappel orienté message (sauf pour eom ou abort, voir ci-dessous), rejetez ce message. Pour un rappel orienté destinataire, rejetez le destinataire actuel (mais continuez le traitement du message actuel) ;
o
TEMPFAIL :
Cette valeur est égale à SMFIS_TEMPFAIL, indiquant que Sendmail doit retourner un message « temporairement indisponible » à l'expéditeur du message électronique. Pour un rappel orienté message (sauf sender, voir ci-dessous), échouez pour ce message. Pour un rappel orienté connexion, échouez pour cette connexion et appelez close. Pour un rappel orienté destinataire, échouez uniquement pour le destinataire actuel et continuez le traitement du message.

Return
Cette énumération simplifie les valeurs étendues MI_ utilisées par l'API C. La plupart des valeurs de retour utilisées par la classe Milter sont cependant des valeurs bool. Les valeurs de Return sont :

o
FAILURE :
Cette valeur est égale à MI_FAILURE, indiquant qu'une fonction de l'API C n'a pas réussi à accomplir sa tâche ;
o
SUCCESS :
Cette valeur est égale à MI_SUCCESS, indiquant qu'une fonction de l'API C a réussi à accomplir sa tâche.

FONCTIONS MEMBRES STATIQUES PUBLIQUES

Ces fonctions constituent le cœur de la classe de base Milter. Elles peuvent être appelées pour initialiser, démarrer et arrêter le Milter.

o
void initialize(std::string const &name, Milter &milter, callback_set callbacks = CONNECT, flag_set flags = NO_FLAGS) :
Cette fonction initialise l'administration du Milter. Elle attend le nom du filtre de messagerie comme premier argument. Son deuxième argument est une référence à un objet Milter. Comme Milter est une classe de base abstraite, l'objet réel est toujours un objet d'une classe dérivée de Milter. Son troisième argument spécifie les rappels à appeler pour ce milter. Par défaut, les rappels connect et close sont appelés. À partir de la version 6.04.00 de bobcat, le rappel close est toujours appelé une fois qu'une connexion se termine : il peut être spécifié lors de la spécification de l'argument callbacks, mais sinon le rappel close est toujours appelé. Le dernier argument définit les drapeaux, spécifiant les capacités du Milter ;
o
std::string const &name() :
Cette fonction retourne le nom du milter ;
o
bool start() :
Cette fonction membre appelle smfi_main, contrôlant la boucle d'événements du milter. Elle retourne true si la boucle d'événements est terminée avec succès ;
o
void stop() :
Cette fonction membre termine la boucle d'événements du milter, après avoir terminé tous les threads. Après cet appel, start peut être appelé à nouveau pour continuer le milter.

FONCTIONS MEMBRES PROTÉGÉES

Les membres suivants ne sont pas virtuels. Ils peuvent être appelés par les membres des classes dérivées de Milter :

o
bool addHeader(std::string const &hdrName, std::string const &hdrValue) :
Ce membre ne peut être appelé que depuis eom, et le drapeau ADD_HEADERS doit avoir été spécifié sinon il échouera. Les hdrName et hdrValue doivent être des chaînes non vides. Chaque ligne d'en-tête doit faire moins de 2048 caractères et moins de 998 caractères. Si des en-têtes plus longs sont nécessaires, rendez-les multi-lignes. Pour créer un en-tête multi-lignes, insérez un saut de ligne (\n) suivi d'au moins un caractère d'espacement tel qu'un espace ou une tabulation (\t). Le saut de ligne ne doit *pas* être précédé d'un retour chariot. Il incombe au développeur du filtre de s'assurer qu'aucune norme n'est violée ;
o
bool addRecipient(std::string const &rcptName) :
Ce membre ne peut être appelé que depuis eom, et le drapeau ADD_RECIPIENTS doit avoir été spécifié sinon il échouera ;
o
bool changeHeader(std::string const &hdrName, size_t headerNr, std::string const &hdrValue) :
Ce membre ne peut être appelé que depuis eom, et le drapeau CHANGE_HEADERS doit avoir été spécifié sinon il échouera. Voir addHeader pour les exigences des en-têtes. Le paramètre headerNr est un indice d'en-tête basé sur 1. Une valeur de headerNr de 1 modifiera la première occurrence d'un en-tête nommé hdrValue. Si headerNr est supérieur au nombre d'occurrences de hdrName, un nouvel en-tête hdrName sera ajouté. Si hdrValue est vide, l'en-tête est supprimé ;
o
bool deleteRecipient(std::string const &rcptName) :
Ce membre ne peut être appelé que depuis eom, et le drapeau DELETE_RECIPIENTS doit avoir été spécifié sinon il échouera. Ce membre supprime le destinataire nommé de l'enveloppe du message actuel ;
o
SMFICTX *id() const :
Ce membre peut être appelé par l'objet Milter pour obtenir un pointeur identifiant sa connexion sendmail. Normalement, il ne devrait pas être nécessaire d'appeler ce membre ;
o
bool insertHeader(size_t hdrIdx, std::string const &hdrName, std::string const &hdrValue) :
Ce membre ne peut être appelé que depuis eom, et le drapeau ADD_HEADERS doit avoir été spécifié sinon il échouera. Voir addHeader pour les exigences des en-têtes. Le paramètre headerNr est un indice d'en-tête. Une valeur de headerNr de 0 insérera cet en-tête comme le premier des en-têtes hdrName. Si headerNr est supérieur au nombre d'occurrences de hdrName, un nouvel en-tête hdrName sera ajouté ;
o
bool openSocket(bool removeIfTrue = true) :
Ce membre doit être appelé avant que start ne soit appelé. Ce membre tente de créer le socket spécifié par setConnection (voir ci-dessous). Cela permet à l'application appelante de s'assurer que le socket peut être créé, en modifiant éventuellement sa protection (droits d'accès) avant que le milter ne commence son travail. Si ce membre n'est pas appelé, il sera appelé implicitement lorsque run sera démarré. Il retourne true si le socket a pu être créé ;
o
bool quarantine(std::string const &reason) :
Ce membre ne peut être appelé que depuis eom et provoque la mise en quarantaine du message par le MTA en utilisant la raison donnée ;
o
bool replaceBody(std::string const &body) :

FONCTIONS MEMBRES PUBLIQUES

o
static Milter *initialize(int argc, char **argv):
This function is the main entry point for a milter. It sets up the connection between the milter and the MTA. It takes the command-line arguments passed to the milter, and returns a pointer to a newly allocated Milter object. The standard `virtual constructor' design pattern is used here. See section PRIVATE VIRTUAL MEMBER FUNCTIONS below for a description of the clone function. The return value is a pointer to the new object, or 0 if initialization fails;
o
virtual void close(SMFICTX *ctx):
This member is called at the end of the connection. It is intended to allow the programmer to clean up any per-connection data structures. The parameter ctx is the context pointer returned by initialize.
o
virtual sfsistat connect(const char *hostname, _SOCK_ADDR *hostaddr):
This member is called once at the start of each SMTP connection. The parameter hostname is the hostname of the message sender, as determined by a reverse lookup on the host address. If the reverse lookup fails, hostname will contain the sender's IP address enclosed in square brackets (e.g. [a.b.c.d]). The parameter hostaddr is the host address, as determined by a getpeername(2) call on the SMTP socket. It is 0 if the type is not supported, or if the SMTP connection is made via stdin;
o
virtual sfsistat data():
Not yet supported. Will be available with libmilter versions beyond 3;
o
virtual sfsistat header(char *headerf, char *headerv):
This member is called zero or more times between recipient and eoh, once per message header. The headerf parameter contains the name of the header, the headerv parameter contains its value. E.g., if an e-mail message contains the following headers: 
    From: sender <f@example.com>
    Subject:no
then header will be called twice with the following values for, respectively headerf and headerv: 
    First header:   "From",     " sender <f@example.com>"
    Second header:  "Subject",  "no"
Further details about header information is given in RFC 882;
o
virtual sfsistat helo(char *helohost):
This member is called once after the connect call, when the MTA has received the HELO or EHLO command from the sending host;
o
virtual sfsistat heloreply(char *helohost):
This member is called after the MTA has received the HELO or EHLO command from the sending host and has checked the hostname against its access list;
o
virtual sfsistat message(SMFICTX *ctx):
This member is called once per message, after the connect and helo calls;
o
virtual sfsistat recipient(char *recipient):
This member is called once per recipient address;
o
virtual sfsistat unknown(char *line):
This member is called for any SMTP command not recognized by libmilter;
o
virtual sfsistat xheader(char *name, char *value):
This member is called for any header line that is not recognized by libmilter. The name parameter contains the header name, and the value parameter contains the header value;

FONCTIONS MEMBRES PROTÉGÉES

o
int abort(SMFICTX *ctx):
This member is called when the message is aborted outside the filter’s control and the filter has not completed its message-oriented processing. For example, if a filter has already returned ACCEPT, REJECT, or DISCARD from a message-oriented routine, abort will not be called even if the message is later aborted outside its control; The function returns CONTINUE;
o
int body(SMFICTX *ctx, unsigned char *bodyp, size_t bodysze):
This member is called zero or more times between eoh and eom. bodyp points to a sequence of bytes. It is not necessarily a 0-terminated. Moreover, the sequence may contain 0-characters. Since message bodies can be very large, defining body can significantly impact filter performance. End-of-lines are represented as received from SMTP (normally CR/LF). Later filters will see body changes made by earlier ones, and message bodies may be sent in multiple chunks, with one call to body per chunk;
o
int changeheader(SMFICTX *ctx, char *name, char *value):
This member is used to change the value of a header. If the header does not exist, it will be added. It is only valid from within the eom callback;
o
int addheader(SMFICTX *ctx, char *name, char *value):
This member is used to add a new header to the message. It is only valid from within the eom callback;
o
int deleteheader(SMFICTX *ctx, char *name):
This member is used to delete a header from the message. It is only valid from within the eom callback;
o
int eoh(SMFICTX *ctx):
This member is called once after all headers have been processed;
o
int eom(SMFICTX *ctx):
This member is called once after all calls to body for a given message have been completed. Note that only in this function modifications to the message headers, body, and envelope can be made (see the add-, change- and delete- members listed above);
o
int Freeport(SMFICTX *ctx):
This member is called once when the connection is closed by the MTA. It is used to free resources associated with the connection;
o
char *getheader(SMFICTX *ctx, char *name):

o

int getreply(SMFICTX *ctx, char *rcode, size_t rcodesize, char *xcode, size_t xcodesize, char *message, size_t messagesize):

int optneg(SMFICTX *ctx, int opt, void *value):

o
int quoted(SMFICTX *ctx, char *line):

o
int recipient(SMFICTX *ctx, char *recipient):

o
int setreply(SMFICTX *ctx, char const *rcode, char const *xcode = "", char const *msg = ""):
This member sets the default SMTP error reply code. It may be called from any callback member, except connect. The parameter rcode should be a three-digit (RFC 821/2821) SMTP reply code and it must be a valid 4XX or 5XX reply code. The parameter xcode, when specified, must be an extended (RFC 1893/2034) reply code. The parameter msg may be an additional textual message.
o
int start(SMFICTX *ctx):
This member is called once after the connect call, and before any other callbacks are made;
o
char *symval(SMFICTX *ctx, char *name):
This member returns the value of a specific sendmail macro. The name parameter should be set to the name of a sendmail macro. Single letter macros can optionally be enclosed in braces ({ and }), longer macro names must be enclosed in braces, just as in a sendmail.cf file. 0 is returned if the macro is not defined. By default, the following macros are valid in the given contexts:
for connect: daemon_name, if_name, if_addr, j, _;
for helo: tls_version, cipher, cipher_bits, cert_subject, cert_issuer;
for mail: i, auth_type, auth_authen, auth_ssf, auth_author, mail_mailer, mail_host, mail_addr;
for recipient: rcpt_mailer, rcpt_host, rcpt_addr.
All macros stay in effect from the point they are received until the end of the connection for the first two sets, the end of the message for the third (mail), and just for each recipient for the final set (recipient).
The following macros may be specified in the sendmail.mc configuration file:
define(`confMILTER_MACROS_CONNECT’, `m1’, ...), define(`confMILTER_MACROS_HELO’, ...), define(`confMILTER_MACROS_ENVFROM’, ...), define(`confMILTER_MACROS_ENVRCPT’, ...), where `m1’, ... represents a comma separated list of returnable macros. Single letter macros can optionally be enclosed in braces ({ and }), longer macro names must be enclosed in braces;
o
int tell(SMFICTX *ctx, const char *fmt, ...):
This function can be used to send any SMTP reply code. It is useful for sending non-standard reply codes, or for sending specific codes in response to specific commands;
o
int unquoted(SMFICTX *ctx, char *line):
This member is called for any line that is part of an unquoted header;
o
int quit(SMFICTX *ctx):
This member is called when the MTA sends the QUIT command;
o
int reset(SMFICTX *ctx):
This member is called when the MTA sends the RSET command;
o

This member is used to associate private data with a connection. The parameter ctx is the context pointer returned by initialize. The parameter priv is a pointer to the private data;

o
int replacebody(SMFICTX *ctx, const char *body):
This member replaces the entire message body with the provided string. It is only valid from within the eom callback;
o
int replaceheader(SMFICTX *ctx, char *name, char *value):
This member replaces the value of a header. If the header does not exist, it will be added. It is only valid from within the eom callback;

ENVIRONNEMENT

The following environment variables can be set by the MTA:

_MILTER_PATH
Specifies the path to the milter socket. This can be one of the following:
/path/to/file - A named pipe;
net:port@{hostname|ip-address} - An IPV4 socket;
inet6:port@{hostname|ip-address} - An IPV6 socket.

If possible, filters should not run as root when communicating over unix/local domain sockets.

Unix/local sockets should have their permissions set to 0600 (read/write permission only for the socket’s owner) or 0660 (read/write permission for the socket’s owner and group) which is useful if the sendmail RunAsUser option is used. The permissions for a unix/local domain socket are determined as usual by umask, which should be set to 007 or 077.

Possible failure of this function cannot be determined from its return value. Rather, run will fail;

char const *symval(std::string const &name) const:
This member returns the value of a specific sendmail macro. The name parameter should be set to he name of a sendmail macro . Single letter macros can optionally be enclosed in braces ({ and }), longer macro names must be enclosed in braces, just as in a sendmail.cf file.0 is returned if the macro is not defined. By default, the following macros are valid in the given contexts:
for connect: daemon_name, if_name, if_addr, j, _;
for helo: tls_version, cipher, cipher_bits, cert_subject, cert_issuer;
for sender: i, auth_type, auth_authen, auth_ssf, auth_author, mail_mailer, mail_host, mail_addr;
for recipient: rcpt_mailer, rcpt_host, rcpt_addr.
All macros stay in effect from the point they are received until the end of the connection for the first two sets, the end of the message for the third (sender), and just for each recipient for the final set (recipient).
The following macros may be specified in the sendmail.mc configuration file:
define(`confMILTER_MACROS_CONNECT’, `m1’, ...), define(`confMILTER_MACROS_HELO’, ...), define(`confMILTER_MACROS_ENVFROM’, ...), define(`confMILTER_MACROS_ENVRCPT’, ...), where `m1’, ... represents a comma separated list of returnable macros. Single letter macros can optionally be enclosed in braces ({ and }), longer macro names must be enclosed in braces;

bool wait():
This member may only be called from eom and tells the MTA that the filter is still working on a message, causing the MTA to re-start its timeouts.

FONCTIONS MEMBRES VIRTUELS PRIVÉES

The remaining functionality of the class Milter is useful only for Milter-implementations in classes derived from Milter. The following members can be overridden by derived classes. Note that clone must be overridden. Except for clone, all the members in this sections are callback functions. I.e., the MTA will call them to process parts of the mail message. Recipient-, message-, and connection-oriented callbacks are distinguished.

The recipient-oriented callback (recipient, see below) may affect the processing of a single message to a single recipient. Connection-oriented callbacks (connect, helo and close) affect the processing of the entire connection (during which multiple messages may be delivered to multiple sets of recipients). The remaining callbacks are message-oriented, affecting the processing of a single message to all its recipients.

o
virtual sfsistat abort():
This message-oriented member may be called at any time during message processing (i.e. between some message-oriented routine and eom). abort reclaim any resources allocated on a per-message basis (which are not the connection specific data, which should be handled by the derived class’ destructor), and must be tolerant of being called between any two message-oriented callbacks. abort is only called if the message is aborted outside the filter’s control and the filter has not completed its message-oriented processing. For example, if a filter has already returned ACCEPT, REJECT, or DISCARD from a message-oriented routine, abort will not be called even if the message is later aborted outside its control;
o
virtual sfsistat body(unsigned char *text, size_t length):
This message-oriented member is called zero or more times between eoh and eom. text points to a sequence of bytes. It is not necessarily a 0-terminated. Moreover, the sequence may contain 0-characters. Since message bodies can be very large, defining body can significantly impact filter performance. End-of-lines are represented as received from SMTP (normally CR/LF). Later filters will see body changes made by earlier ones, and message bodies may be sent in multiple chunks, with one call to body per chunk;
o
virtual Milter *clone() const = 0:
This pure virtual function must be implemented by derived classes to return a newly allocated copy of the derived object passed to the initialize static member. It is used by the standard `virtual constructor’ design pattern. The destruction of the allocated object is the responsibility of clone’s caller;
o
virtual sfsistat close():
This connection-oriented member is always called once at the end of each connection. It may be called "out-of-order", i.e. before even the connect is called. After a connection is established by the MTA to the filter, if the MTA decides this connection’s traffic will be discarded (e.g. via an access_db result), no data will be passed to the filter from the MTA until the client closes down. At that time, close is called. It can therefore be the only callback ever used for a given connection, and developers should anticipate this possibility when crafting their close code. The member close is called on close even if the previous mail transaction was aborted. The default implementation of the member close is 
    sfsistat Milter::close()
    {
        smfi_setpriv(d_ctx, 0);         // delete this d_ctx data
        return CONTINUE;
    }
By calling smfi_setpriv with second argumnt 0 any data associated with the current connection is deleted by the milter. Implementations overriding close should at least call smfi_setpriv, passing the value returned by the member id (cf. section PROTECTED MEMBER FUNCTIONS) as first argument and 0 as second argument. Other data managed by the milter and specifically associated with a connection should be accessed via the connection’s id (e.g., using a std::unordered_map using an SMFICTX * as key);
o
virtual sfsistat connect(char *hostname, _SOCK_ADDR *hostaddr):
This connection-oriented member may be called once, at the start of each SMTP connection. The parameter hostname is he host name of the message sender, as determined by a reverse lookup on the host address. If the reverse lookup fails, hostname will contain the message sender’s IP address enclosed in square brackets (e.g. [a.b.c.d]). The parameter hostaddr is the host address, as determined by a getpeername(2) call on the SMTP socket. It is 0 if the type is not supported in the current version or if the SMTP connection is made via stdin;

virtual sfsistat header(char *headerf, char *headerv):
This message-oriented member is called zero or more times between recipient and eoh, once per message header. The headerf parameter contains the text of the header, the headerv parameter contains its value. E.g., if an e-mail message contains the following headers: 
    From: sender <f@example.com>
    Subject:no
then header will be called twice with the following values for, respectively headerf and headerv: 
    First header:   "From",     " sender <f@example.com>"
    Second header:  "Subject",  "no"
Further details about header information is given in RFC 882;

DESCRIPTION

La bibliothèque libmilter fournit une interface pour écrire des filtres de messagerie SMTP (Mail Filter) pour le programme sendmail. Elle permet au programme sendmail de déléguer certaines tâches de traitement des e-mails à un programme externe, qui peut alors inspecter, modifier ou rejeter les e-mails en fonction de règles définies par l'administrateur.

L'interface est basée sur des rappels (callbacks) que le programme filtre doit implémenter. Sendmail appellera ces fonctions de rappel à différentes étapes du traitement d'un message SMTP.

La structure milter_callbacks_t contient des pointeurs vers ces fonctions de rappel. La fonction milter_init est appelée pour initialiser la bibliothèque et enregistrer les rappels. La fonction milter_loop démarre la boucle principale du filtre, qui attend les connexions de sendmail et gère la communication.

Les constantes milter_abort, milter_accept, milter_discard, milter_reject, et milter_tempfail sont retournées par les fonctions de rappel pour indiquer à sendmail comment traiter le message.

ESPACE NOMINAL

Aucun espace de noms n'est spécifiquement défini pour cette interface. Toutes les fonctions et structures sont globales.

HERITE DE

Aucune information d'héritage n'est directement applicable ici, car il s'agit d'une interface de bibliothèque C.

ENUMERATIONS

Aucune énumération n'est explicitement définie dans cette interface, mais les valeurs de retour des fonctions de rappel (par exemple, milter_accept) agissent comme des codes d'état.

CONSTRUCTEUR/DESTRUCTEUR

milter_init: Initialise la bibliothèque milter et enregistre les rappels définis par l'utilisateur. Prend en paramètre un pointeur vers une structure milter_callbacks_t contenant les fonctions de rappel, un chemin de configuration optionnel et des données utilisateur.

milter_close: Nettoie les ressources utilisées par la bibliothèque milter.

Ce membre orienté connexion est appelé une fois par connexion entrante. Les paramètres indiquent le nom d'hôte du client, la famille d'adresses (par exemple, AF_INET) et le port distant.
o
virtual sfsistat getconn(char *host, char *family, char *port):
Ce membre orienté connexion est appelé une fois par connexion entrante, après connect. Les paramètres indiquent le nom d'hôte du client, la famille d'adresses et le port distant.

Similaire à getconn, mais le paramètre str contient une représentation textuelle des informations de connexion.

Ce membre orienté connexion est appelé une fois par connexion, lorsque le client envoie une commande HELO/EHLO. Le paramètre helohost devrait être le nom de domaine de l'hôte expéditeur (mais en pratique, c'est tout ce que l'hôte expéditeur veut envoyer).
o
virtual sfsistat mail(char **argv):
Ce membre orienté message est appelé une fois au début de chaque message, avant rcpt. argv[0] est garanti d'être l'adresse de l'enveloppe de l'expéditeur. Les arguments suivants sont les arguments ESMTP. TEMPFAIL peut être retourné, indiquant que sendmail doit renvoyer une erreur temporaire pour ce message particulier ; abort n'est pas appelé. REJECT rejettera ce message ; abort n'est pas appelé. DISCARD acceptera (mais supprimera) le message, abort sera appelé. ACCEPT acceptera le destinataire, abort ne sera pas appelé. Plus de détails sur les réponses ESMTP sont décrits dans la RFC 1869.
o
virtual sfsistat optneg(int option, int value):
Ce membre orienté connexion est appelé une fois par connexion pour négocier les options ESMTP. Les options sont décrites dans la RFC 1869.
o
virtual sfsistat rcpt(char **argv):
Ce membre orienté destinataire est appelé une fois par destinataire, donc une ou plusieurs fois par message, immédiatement après mail. Le paramètre argv est un tableau terminé par 0 de pointeurs vers les arguments de la commande SMTP ; argv[0] est garanti d'être l'adresse du destinataire. Les arguments ultérieurs sont les arguments ESMTP. TEMPFAIL peut être retourné pour indiquer que sendmail doit renvoyer une erreur temporaire pour ce destinataire particulier ; les destinataires suivants peuvent toujours être envoyés, abort n'est pas appelé. REJECT rejettera ce destinataire particulier ; les destinataires suivants peuvent toujours être envoyés, abort n'est pas appelé. DISCARD acceptera (mais supprimera) le message, abort sera appelé. ACCEPT acceptera le destinataire, abort ne sera pas appelé. Plus de détails sur les réponses ESMTP sont décrits dans la RFC 1869.
o
virtual sfsistat unknown(char *ptr):
