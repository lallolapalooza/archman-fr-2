MISE(1) Manuel des commandes générales MISE(1)

NOM

mise - Le frontal de votre environnement de développement

SYNTAXE

mise [OPTIONS] [<TACHE>] [<ARGS_TACHE>] ... [<ARGS_TACHE_DERNIERE>] ... [COMMANDE]

DESCRIPTION

mise gère les outils de développement, les variables d'environnement et exécute les tâches. https://github.com/jdx/mise

OPTIONS

-c, --continue-on-error
Continuer l'exécution des tâches même si l'une d'elles échoue
-C, --cd <DIR>
Changer de répertoire avant d'exécuter la commande
-E, --env <ENV>
Définir l'environnement pour charger `mise.<ENV>.toml`
-f, --force
Forcer l'opération
-i, --interleave
Définir la verbosité de la sortie des logs
-j, --jobs <JOBS>
Nombre de tâches à exécuter en parallèle [par défaut : 8]
-n, --dry-run
Simulation, ne rien faire réellement
-p, --prefix
-P, --profile <PROFIL>
Définir le profil (environnement)
-q, --quiet
Supprimer les messages autres que les erreurs
-s, --shell <SHELL>
-t, --tool <OUTIL@VERSION>
Outil(s) à exécuter en plus de ceux présents dans les fichiers mise.toml, par exemple : node@20 python@3.10
-v, --verbose
Afficher des informations supplémentaires (utiliser -vv pour encore plus)
-V, --version
-y, --yes
Répondre oui à toutes les invites de confirmation
--debug
Définit le niveau de log à debug
--log-level <NIVEAU>
--no-config
Ne pas charger de fichiers de configuration

Peut également être utilisé avec `MISE_NO_CONFIG=1`

--no-timings
Masque le temps écoulé après chaque tâche terminée

Par défaut, toujours masquer avec `MISE_TASK_TIMINGS=0`

--output <SORTIE>
--raw
Lire/écrire directement depuis/vers stdin/stdout/stderr au lieu de ligne par ligne
--silent
Supprimer toutes les sorties de tâches et les messages non-erreurs de mise
--timings
Affiche le temps écoulé après chaque tâche terminée

Par défaut, toujours afficher avec `MISE_TASK_TIMINGS=1`

--trace
Définit le niveau de log à trace

ARGUMENTS

<TACHE>
Tâche à exécuter.

Raccourci pour `mise task run <TACHE>`.

<ARGS_TACHE>
Arguments de la tâche

MISE ACTIVATE

Initialise mise dans la session shell actuelle

Ceci doit être placé dans le fichier rc de votre shell ou dans le shell de connexion. Sinon, il ne prendra effet que dans la session actuelle. (par exemple, ~/.zshrc, ~/.zprofile, ~/.zshenv, ~/.bashrc, ~/.bash_profile, ~/.profile, ~/.config/fish/config.fish, ou $PROFILE pour powershell)

Typiquement, cela peut être ajouté avec quelque chose comme ce qui suit :


echo 'eval "$(mise activate zsh)"' >> ~/.zshrc

Cependant, cela nécessite que "mise" soit dans votre PATH. S'il ne l'est pas, vous devez spécifier le chemin complet comme ceci :


echo 'eval "$(/path/to/mise activate zsh)"' >> ~/.zshrc

Personnalisez la sortie du statut avec les paramètres `status`.

Utilisation : mise activate [OPTIONS] [<SHELL_TYPE>]

Options :

-q, --quiet
Supprimer les messages non liés aux erreurs
-s, --shell <SHELL>
Type de shell pour lequel générer le script
--no-hook-env
N'appelle pas automatiquement hook-env

Cela peut être utile pour le débogage de mise. Si vous exécutez `eval "$(mise activate --no-hook-env)"`, vous pouvez ensuite appeler `mise hook-env` manuellement, ce qui affichera les variables d'environnement sur stdout sans modifier l'environnement. De cette façon, vous pouvez faire des choses comme `mise hook-env --trace` pour obtenir plus d'informations ou simplement voir les valeurs que hook-env affiche.

--shims
Utiliser des shims au lieu de modifier le PATH. Efficacement la même chose que :


PATH="$HOME/.local/share/mise/shims:$PATH"

`mise activate --shims` ne supporte pas toutes les fonctionnalités de `mise activate`. Voir https://mise.jdx.dev/dev-tools/shims.html#shims-vs-path pour plus d'informations

--status
Afficher le message "mise: <PLUGIN>@<VERSION>" lors du changement
ng répertoires Arguments : 
<TYPE_SHELL>
Type de shell pour lequel générer le script.

MISE EXEC

Execute a command with tool(s) set

use this to avoid modifying the shell session or running ad-hoc commands with mise tools set.

Tools will be loaded from mise.toml, though they can be overridden with <RUNTIME> args Note that only the plugin specified will be overridden, so if a `mise.toml` file includes "node 20" but you run `mise exec python@3.11`; it will still load node@20.

The "--" separates runtimes from the commands to pass along to the subprocess.

Usage: mise exec [OPTIONS] [<TOOL@VERSION>] ... [<COMMAND>] ...

Options:

-c, --command <C>
Command string to execute
-j, --jobs <JOBS>
Number of jobs to run in parallel [default: 4]
--raw
Directly pipe stdin/stdout/stderr from plugin to user Sets --jobs=1 Arguments:
<TOOL@VERSION>
Tool(s) to start e.g.: node@20 python@3.10
<COMMAND>
Command string to execute (same as --command)

MISE GENERATE TOOL-STUB

Generate a tool stub for HTTP-based tools

This command generates tool stubs that can automatically download and execute tools from HTTP URLs. It can detect checksums, file sizes, and binary paths automatically by downloading and analyzing the tool.

When generating stubs with platform-specific URLs, the command will append new platforms to existing stub files rather than overwriting them. This allows you to incrementally build cross-platform tool stubs.

Usage: mise generate tool-stub [OPTIONS] <OUTPUT>

Options:

-b, --bin <BIN>
Binary path within the extracted archive

If not specified and the archive is downloaded, will auto-detect the

most likely binary

-u, --url <URL>
URL pour télécharger l'outil

Exemple : https://github.com/owner/repo/releases/download/v2.0.0/tool-linux-x64.tar.gz

--fetch
Récupère les sommes de contrôle et les tailles pour un fichier stub d'outil existant

Ceci lit un fichier stub existant et remplit les champs de somme de contrôle/taille manquants en téléchargeant les fichiers. Les URL doivent déjà être présentes dans le stub.

--http <HTTP>
Type de backend HTTP à utiliser
--platform-bin <PLATFORM_BIN>
Chemins binaires spécifiques à la plateforme au format plateforme:chemin

Exemples : --platform-bin windows-x64:tool.exe --platform-bin linux-x64:bin/tool

--platform-url <PLATFORM_URL>
URL spécifiques à la plateforme au format plateforme:url ou juste url (détection automatique de la plateforme)

Lorsque le fichier de sortie existe déjà, de nouvelles plateformes seront ajoutées à la table des plateformes existantes. Les URL de plateformes existantes seront mises à jour si elles sont spécifiées à nouveau.

Si seule une URL est fournie (sans plateforme:), la plateforme sera détectée automatiquement à partir du nom de fichier de l'URL.

Exemples : --platform-url linux-x64:https://... --platform-url https://nodejs.org/dist/v22.17.1/node-v22.17.1-darwin-arm64.tar.gz

--skip-download
Ignorer le téléchargement pour la détection de la somme de contrôle et du chemin binaire (plus rapide mais moins informatif)

MISE RUN

Exécuter une ou plusieurs tâches

Cette commande exécute une tâche, ou plusieurs tâches en parallèle. Les tâches peuvent avoir des dépendances sur d'autres tâches ou sur des fichiers source. Si la configuration `source` est activée pour une tâche, celle-ci ne s'exécutera que si les fichiers source ont été modifiés.

Les tâches peuvent être définies dans `mise.toml` ou comme des scripts autonomes. Dans `mise.toml`, les tâches ont cette forme :


[tasks.build]
run = "npm run build"
sources = ["src/**/*.ts"]
outputs = ["dist/**/*.js"]

Alternativement, les tâches peuvent être définies comme des scripts autonomes. Ceux-ci doivent être situés dans `mise-tasks`, `.mise-tasks`, `.mise/tasks`, `mise/tasks` ou `.config/mise/tasks`. Le nom du script sera le nom de la tâche.


$ cat .mise/tasks/build<<EOF
#!/usr/bin/env bash
npm run build
EOF
$ mise run build

#!/usr/bin/env bash
npm run build

MISE TOOL-STUB

-o, --on-busy-update <MODE>
Que faire lorsqu'on reçoit des événements pendant que la commande s'exécute

Par défaut, c'est 'do-nothing', qui ignore les événements pendant que la commande s'exécute, de sorte que les changements qui surviennent suite à la commande sont ignorés, comme les sorties de compilation. Vous pouvez également utiliser 'queue' qui exécutera à nouveau la commande une fois la course actuelle terminée si des événements se produisent pendant son exécution, ou 'restart', qui termine la commande en cours et en démarre une nouvelle. Enfin, il y a 'signal', qui envoie seulement un signal ; cela peut être utile avec des programmes qui peuvent recharger leur configuration sans redémarrage complet.

Le signal peut être spécifié avec l'option '--signal'.

-r, --restart
Redémarre le processus s'il est toujours en cours d'exécution

C'est un raccourci pour '--on-busy-update=restart'.

-s, --signal <SIGNAL>
Envoie un signal au processus lorsqu'il est toujours en cours d'exécution

Spécifie un signal à envoyer au processus lorsqu'il est toujours en cours d'exécution. Ceci implique '--on-busy-update=signal' ; sinon, le signal utilisé lorsque ce mode est 'restart' est contrôlé par '--stop-signal'.

Voir la documentation longue pour '--stop-signal' pour la syntaxe.

Les signaux ne sont pas pris en charge sous Windows pour le moment, et seront toujours remplacés par 'kill'. Voir '--stop-signal' pour plus d'informations sur les "signaux" sous Windows.

--stop-signal <SIGNAL>
Signal à envoyer pour arrêter la commande

Ceci est utilisé par les modes 'restart' et 'signal' de '--on-busy-update' (sauf si '--signal' est fourni). Le comportement de redémarrage consiste à envoyer le signal, attendre que la commande se termine, et si elle ne s'est pas terminée après un certain temps (voir '--timeout-stop'), la terminer de force.

La valeur par défaut sur unix est "SIGTERM".

L'entrée est analysée comme un nom de signal complet (comme "SIGTERM"), un nom de signal court (comme "TERM"), ou un numéro de signal (comme "15"). Toute entrée est insensible à la casse.

Sous Windows, cette option est techniquement prise en charge mais ne prend en charge que l'événement "KILL", car Watchexec ne peut pas encore délivrer d'autres événements. Windows n'a pas de signaux en tant que tels ; il a plutôt la terminaison (appelée ici "KILL" ou "STOP") et les événements "CTRL+C", "CTRL+BREAK" et "CTRL+CLOSE". Pour la portabilité, les signaux unix "SIGKILL", "SIGINT", "SIGTERM", et "SIGHUP" sont respectivement mappés à ceux-ci.

--stop-timeout <TIMEOUT>
Temps d'attente pour que la commande se termine gracieusement

Ceci est utilisé par le mode 'restart' de '--on-busy-update'. Après l'envoi du signal d'arrêt gracieux, Watchexec attendra que la commande se termine. Si elle ne s'est pas terminée après ce délai, elle est terminée de force.

Accepte une valeur sans unité en secondes, ou une valeur de durée telle que "5min 20s". Fournir une valeur sans unité est déconseillé et générera un avertissement ; ce sera une erreur à l'avenir.

La valeur par défaut est 10 secondes. Réglez à 0 pour forcer la terminaison immédiate de la commande.

Cela n'a pas d'effet pratique sous Windows car la commande est toujours terminée de force ; voir '--stop-signal' pour la raison.

--map-signal <SIGNAL:SIGNAL>
Traduit les signaux du système d'exploitation en signaux à envoyer à la commande

Accepte une paire de noms de signaux, séparés par deux-points, comme "TERM:INT" pour mapper SIGTERM à SIGINT. Le premier signal est celui reçu par watchexec, et le second est celui envoyé à la commande. Le second peut être omis pour ignorer le premier signal, comme "TERM:" pour ne rien faire lors de SIGTERM.

Si SIGINT ou SIGTERM sont mappés, ils ne quittent plus Watchexec. En plus de rendre difficile la sortie de Watchexec lui-même, cela est utile pour passer un Ctrl-C à la commande sans terminer également Watchexec et le programme sous-jacent, par exemple avec "INT:INT".

Cette option peut être spécifiée plusieurs fois pour mapper plusieurs signaux.

La syntaxe des signaux est insensible à la casse pour les noms courts (comme "TERM", "USR2") et les noms longs (comme "SIGKILL", "SIGHUP"). Les numéros de signaux sont également pris en charge (comme "15", "31"). Sous Windows, les formes "STOP", "CTRL+C", et "CTRL+BREAK" sont également prises en charge pour la réception, mais Watchexec ne peut pas encore délivrer d'autres "signaux" qu'un STOP.

-d, --debounce <TIMEOUT>
Temps d'attente des nouveaux événements avant d'agir

Lorsqu'un événement est reçu, Watchexec attendra jusqu'à ce délai avant de le traiter (comme exécuter la commande). Ceci est essentiel car ce que vous pourriez percevoir comme un seul changement peut en réalité émettre de nombreux événements, et sans ce comportement, Watchexec s'exécuterait beaucoup trop souvent. De plus, il n'est pas rare que les écritures de fichiers ne soient pas atomiques, et chaque écriture peut émettre un événement, donc c'est un bon moyen d'éviter d'exécuter une commande pendant qu'un fichier est partiellement écrit.

Une utilisation alternative est de définir une valeur élevée (comme "30min" ou plus), pour économiser de l'énergie ou de la bande passante sur des tâches intensives, comme un script de sauvegarde ad hoc. Dans ces cas d'utilisation, notez que chaque événement accumulé sera stocké en mémoire.

Accepte une valeur sans unité en millisecondes, ou une valeur de durée telle que "5sec 20ms". Fournir une valeur sans unité est déconseillé et générera un avertissement ; ce sera une erreur à l'avenir.

La valeur par défaut est 50 millisecondes. Il est fortement déconseillé de régler à 0.

--stdin-quit
Quitte lorsque stdin se ferme

Ceci surveille le descripteur de fichier stdin pour EOF, et quitte Watchexec gracieusement lorsqu'il est fermé. Ceci est utilisé par certains gestionnaires de processus pour éviter de laisser des processus zombies traîner.

--no-vcs-ignore
Ne charge pas les gitignores

Parmi d'autres fichiers d'exclusion de VCS, comme pour Mercurial, Subversion, Bazaar, DARCS, Fossil. Notez que Watchexec détectera lequel de ceux-ci est utilisé, le cas échéant, et ne chargera que les fichiers pertinents. Les fichiers globaux (comme '~/.gitignore') et locaux (comme '.gitignore') sont pris en compte.

Cette option est utile si vous souhaitez surveiller des fichiers ignorés par Git.

--no-project-ignore
Ne charge pas les ignorés locaux du projet

Ceci désactive le chargement des fichiers d'ignorés locaux du projet, tels que '.gitignore' ou '.ignore' dans le projet surveillé. Ceci est contrasté avec '--no-vcs-ignore', qui désactive le chargement des fichiers d'ignorés Git et autres VCS, et avec '--no-global-ignore', qui désactive le chargement des fichiers d'ignorés globaux ou utilisateur, tels que '~/.gitignore' ou '~/.config/watchexec/ignore'.

Les fichiers d'ignorés de projet pris en charge

es:


- Git : .gitignore à la racine du projet et dans les sous-répertoires, .git/info/exclude, et le fichier pointé par `core.excludesFile` dans .git/config.
- Mercurial : .hgignore à la racine du projet et dans les sous-répertoires.
- Bazaar : .bzrignore à la racine du projet.
- Darcs : _darcs/prefs/boring
- Fossil : .fossil-settings/ignore-glob
- Ripgrep/Watchexec/générique : .ignore à la racine du projet et dans les sous-répertoires.

Les fichiers d'ignorance des VCS (Git, Mercurial, Bazaar, Darcs, Fossil) ne sont utilisés que si le VCS correspondant est découvert comme étant en cours d'utilisation pour le projet/l'origine. Par exemple, un .bzrignore dans un dépôt Git sera rejeté.

--no-global-ignore
Ne pas charger les ignorances globales

Ceci désactive le chargement des fichiers d'ignorance globaux ou utilisateur, tels que '~/.gitignore', '~/.config/watchexec/ignore', ou '%APPDATA%\Bazzar\2.0\ignore'. À distinguer de '--no-vcs-ignore' et '--no-project-ignore'.

Fichiers d'ignorance globaux pris en charge


- Git (si core.excludesFile est défini) : le fichier à ce chemin
- Git (sinon) : le premier trouvé parmi $XDG_CONFIG_HOME/git/ignore, %APPDATA%/.gitignore, %USERPROFILE%/.gitignore, $HOME/.config/git/ignore, $HOME/.gitignore.
- Bazaar : le premier trouvé parmi %APPDATA%/Bazzar/2.0/ignore, $HOME/.bazaar/ignore.
- Watchexec : le premier trouvé parmi $XDG_CONFIG_HOME/watchexec/ignore, %APPDATA%/watchexec/ignore, %USERPROFILE%/.watchexec/ignore, $HOME/.watchexec/ignore.

Comme pour les fichiers de projet, les fichiers globaux Git et Bazaar ne seront utilisés que pour le VCS correspondant tel qu'utilisé dans le projet.

--no-default-ignore
Ne pas utiliser les ignorances par défaut internes

Watchexec a un ensemble de motifs d'ignorance par défaut, tels que les fichiers d'échange d'éditeur, `*.pyc`, `*.pyo`, `.DS_Store`, `.bzr`, `_darcs`, `.fossil-settings`, `.git`, `.hg`, `.pijul`, `.svn`, et les fichiers journaux de Watchexec.

--no-discover-ignore
Ne pas découvrir les fichiers d'ignorance du tout

Ceci est un raccourci pour '--no-global-ignore', '--no-vcs-ignore', '--no-project-ignore', mais encore plus efficace car il évitera tous les mécanismes de découverte d'ignorance dès le départ.

Notez que les ignorances par défaut sont toujours chargées, voir '--no-default-ignore'.

--ignore-nothing
Ne rien ignorer du tout

Ceci est un raccourci pour '--no-discover-ignore', '--no-default-ignore'.

Notez que les ignorances chargées explicitement via d'autres options de ligne de commande, telles que '--ignore' ou '--ignore-file', seront toujours utilisées.

-p, --postpone
Attendre le premier changement avant d'exécuter la commande

Par défaut, Watchexec exécutera la commande une fois immédiatement. Avec cette option, il attendra plutôt qu'un événement soit détecté avant d'exécuter la commande normalement.

--delay-run <DURATION>
Dormir avant d'exécuter la commande

Cette option fera dormir Watchexec pendant la durée spécifiée avant d'exécuter la commande, après la détection d'un événement. C'est comme utiliser "sleep 5 && command" dans un shell, mais portable et légèrement plus efficace.

Prend une valeur sans unité en secondes, ou une valeur de durée telle que "2min 5s". Fournir une valeur sans unité est déprécié et générera un avertissement ; ce sera une erreur à l'avenir.

--poll <INTERVAL>
Sonder les changements du système de fichiers

Par défaut, et là où c'est disponible, Watchexec utilise les capacités de surveillance du système de fichiers natif du système d'exploitation. Cette option désactive cela et utilise à la place un mécanisme de sondage, qui est moins efficace mais peut contourner les problèmes avec certains systèmes de fichiers (comme les partages réseau) ou les cas limites.

Prend optionnellement une valeur sans unité en millisecondes, ou une valeur de durée telle que "2s 500ms", à utiliser comme intervalle de sondage. Si elle n'est pas spécifiée, la valeur par défaut est de 30 secondes. Fournir une valeur sans unité est déprécié et générera un avertissement ; ce sera une erreur à l'avenir.

Alias '--force-poll'.

--shell <SHELL>
Utiliser un shell différent

Par défaut, Watchexec utilisera '$SHELL' s'il est défini ou un défaut de 'sh' sur Unix-likes, et soit 'pwsh', 'powershell', soit 'cmd' (CMD.EXE) sous Windows, en fonction de ce que Watchexec détecte comme étant le shell en cours d'exécution.

Avec cette option, vous pouvez outrepasser cela et utiliser un shell différent, par exemple un shell avec plus de fonctionnalités ou un shell qui possède vos alias et fonctions personnalisés.

Si la valeur contient des espaces, elle est analysée comme une ligne de commande, et le premier mot utilisé comme programme shell, avec le reste comme arguments pour le shell.

La commande est exécutée avec le drapeau '-c' (sauf pour 'cmd' sous Windows, où c'est '/C').

La valeur spéciale 'none' peut être utilisée pour désactiver complètement l'utilisation du shell. Dans ce cas, la commande fournie à Watchexec sera analysée, le premier mot étant l'exécutable et le reste étant les arguments, et exécutée directement. Notez que cette analyse est rudimentaire et peut ne pas fonctionner comme prévu dans tous les cas.

L'utilisation de 'none' est un peu plus efficace et peut permettre une interprétation plus stricte de l'entrée, mais cela signifie également que vous ne pouvez pas utiliser les fonctionnalités du shell comme le globbing, la redirection, le contrôle de flux, la logique, ou les pipes.

Exemples :

Utiliser sans shell :

$ watchexec -n -- zsh -x -o shwordsplit scr

Utiliser avec powershell core :

$ watchexec --shell=pwsh -- Test-Connection localhost

Utiliser avec CMD.exe :

$ watchexec --shell=cmd -- dir

Utiliser avec un shell unix différent :

$ watchexec --shell=bash -- 'echo $BASH_VERSION'

Utiliser avec un shell unix et des options :

$ watchexec --shell='zsh -x -o shwordsplit' -- scr

-n
Raccourci pour '--shell=none'
--emit-events-to <MODE>
Configurer l'émission d'événements

Watchexec peut émettre des informations sur les événements lors de l'exécution d'une commande, ce qui peut être utilisé par le processus enfant pour cibler des fichiers modifiés spécifiques.

Il faut faire attention à ne pas supposer un comportement inhérent là où il n'y a que des probabilités. Notamment, il pourrait sembler que la variable `RENAMED` contienne à la fois le chemin d'origine et le nouveau chemin renommé. Dans les versions précédentes, il semblait même sur certaines plateformes que l'original venait toujours avant le nouveau. Cependant, rien de tout cela n'était vrai. Il est impossible de savoir de manière fiable et portable quel chemin modifié est l'ancien ou le nouveau, des renommages "partiels" peuvent apparaître (seulement l'original, seulement le nouveau), des renommages "inconnus" peuvent apparaître (le changement était un renommage, mais on ne sait pas si c'était l'ancien ou le nouveau), les événements de renommage peuvent se diviser sur deux limites de dé-duplication, et ainsi de suite.

Cette option contrôle où ces informations sont émises. Elle est par défaut sur 'none', qui n'émet aucune information d'événement. Les autres options sont 'environment' (déprécié), 'stdio', 'file', 'json-stdio', et 'json-file'.

Les modes 'stdio' et 'file' sont basés sur du texte : 'stdio' écrit des chemins absolus vers l'entrée standard de la commande, un par ligne, chacun préfixé par `create:`, `remove:`, `rename:`, `modify:`, ou `other:`, puis ferme le handle ; 'file' écrit la même chose dans un fichier temporaire, et son chemin est donné avec la variable d'environnement $WATCHEXEC_EVENTS_FILE.

Il existe également deux modes JSON, basés sur des objets JSON et pouvant représenter l'ensemble complet des événements gérés par Watchexec. Voici un exemple de création de dossier sous Linux :

```json
{
"tags": [
{
"kind": "path",
"absolute": "/home/user/your/new-folder",
"filetype": "dir"
},
{
"kind": "fs",
"simple": "create",
"full": "Create(Folder)"
},
{
"kind": "source",
"source": "filesystem"
}
],
"metadata": {
"notify-backend": "inotify"
}
} ```

Les champs sont les suivants :


- `tags`, données structurées de l'événement.
- `tags[].kind`, qui peut être :
* 'path', avec :
+ `absolute`, un chemin absolu.
+ `filetype`, le type de fichier s'il est connu ('dir', 'file', 'symlink', 'other').
* 'fs' :
+ `simple`, le type d'événement "simple" ('access', 'create', 'modify', 'remove', ou 'other').
+ `full`, le type d'événement "complet", trop complexe pour être entièrement décrit ici, mais ressemblant à 'General(Precise(Specific))'.
* 'source', avec :
+ `source`, la source de l'événement ('filesystem', 'keyboard', 'mouse', 'os', 'time', 'internal').
* 'keyboard', avec :
+ `keycode`. Actuellement, seule la valeur 'eof' est prise en charge.
* 'process', pour les événements causés par des processus :
+ `pid`, l'ID du processus.
* 'signal', pour les signaux envoyés à Watchexec :
+ `signal`, le nom normalisé du signal ('hangup', 'interrupt', 'quit', 'terminate', 'user1', 'user2').
* 'completion', pour la fin d'une commande :
+ `disposition`, la disposition de sortie ('success', 'error', 'signal', 'stop', 'exception', 'continued').
+ `code`, le code de sortie, de signal, d'arrêt ou d'exception.
- `metadata`, informations supplémentaires sur l'événement.

Le mode 'json-stdio' émettra des événements JSON vers l'entrée standard de la commande, un par ligne, puis fermera stdin. Le mode 'json-file' créera un fichier temporaire, y écrira les événements et fournira le chemin du fichier avec le $WATCvariable d'environnement HEXEC_EVENTS_FILE.

Enfin, le mode 'environment' était le mode par défaut jusqu'à la version 2.0. Il définit les variables d'environnement avec les chemins des fichiers concernés, pour les événements du système de fichiers :

$WATCHEXEC_COMMON_PATH est défini sur le chemin commun le plus long de toutes les variables ci-dessous, et doit donc être préfixé à chaque chemin pour obtenir le chemin complet/réel. Ensuite :


- $WATCHEXEC_CREATED_PATH est défini lorsque des fichiers/dossiers ont été créés
- $WATCHEXEC_REMOVED_PATH est défini lorsque des fichiers/dossiers ont été supprimés
- $WATCHEXEC_RENAMED_PATH est défini lorsque des fichiers/dossiers ont été renommés
- $WATCHEXEC_WRITTEN_PATH est défini lorsque des fichiers/dossiers ont été modifiés
- $WATCHEXEC_META_CHANGED_PATH est défini lorsque les métadonnées des fichiers/dossiers ont été modifiées
- $WATCHEXEC_OTHERWISE_CHANGED_PATH est défini pour tout autre type d'événement de chemin

Les chemins multiples sont séparés par le séparateur de chemin du système, ';' sur Windows et ':' sur unix. Dans chaque variable, les chemins sont dédupliqués et triés par ordre binaire (c'est-à-dire sans tenir compte de l'unicode ou des paramètres régionaux).

C'est le mode hérité, il est déprécié et sera supprimé à l'avenir. L'environnement est un espace très restreint, tout en étant limité dans ce qu'il peut représenter utilement. Un grand nombre de fichiers entraînera soit la troncature de l'environnement, soit des erreurs, soit le plantage complet du processus. Le $WATCHEXEC_COMMON_PATH est également peu intuitif, comme en témoignent les nombreuses requêtes confuses qui m'ont été envoyées au fil des ans.

--only-emit-events
Émettre uniquement des événements vers la sortie standard, n'exécuter aucune commande.

C'est une option pratique pour utiliser Watchexec comme un moniteur de fichiers, sans exécuter de commandes. Elle est presque équivalente à utiliser `cat` comme commande, sauf qu'elle ne lancera pas de nouveau processus pour chaque événement.

Cette option nécessite que `--emit-events-to` soit défini, et restreint les modes disponibles à `stdio` et `json-stdio`, en modifiant leur comportement pour écrire vers la sortie standard au lieu de l'entrée standard de la commande.

-E, --env <CLE=VALEUR>
Ajouter des variables d'environnement à la commande

C'est une option pratique pour définir des variables d'environnement pour la commande, sans les définir pour le processus Watchexec lui-même.

Utilisez la syntaxe clé=valeur. Plusieurs variables peuvent être définies en répétant l'option.

--wrap-process <MODE>
Configurer comment le processus est encapsulé

Par défaut, Watchexec exécutera la commande dans un groupe de processus sous Unix, et dans un Job Object sous Windows.

Certains programmes Unix préfèrent s'exécuter dans une session, tandis que d'autres ne fonctionnent pas dans un groupe de processus.

Utilisez 'group' pour utiliser un groupe de processus, 'session' pour utiliser une session de processus, et 'none' pour exécuter la commande directement. Sous Windows, 'group' ou 'session' utiliseront un Job Object.

-N, --notify
Alerter lorsque les commandes démarrent et se terminent

Avec cela, Watchexec émettra une notification de bureau lorsqu'une commande démarre et se termine, sur les plateformes prises en charge. Sur les plateformes non prises en charge, il peut silencieusement ne rien faire, ou enregistrer un avertissement.

--color <MODE>
Quand utiliser les couleurs du terminal

Définir la variable d'environnement `NO_COLOR` à n'importe quelle valeur est équivalent à `--color=never`.

--timings
Afficher combien de temps a pris l'exécution de la commande

Cela peut ne pas être exact, car cela inclut une certaine surcharge de Watchexec lui-même. Utilisez l'utilitaire `time`, des minuteurs de haute précision ou des outils de benchmarking pour des résultats plus précis.

-q, --quiet
Ne pas afficher les messages de démarrage et d'arrêt

Par défaut, Watchexec affichera un message lorsque la commande démarre et s'arrête. Cette option désactive ce comportement, de sorte que seule la sortie, les avertissements et les erreurs de la commande seront affichés.

--bell
Faire sonner la cloche du terminal à la fin de l'exécution de la commande
--project-origin <REPERTOIRE>
Définir l'origine du projet

Watchexec tentera de découvrir l'"origine" (ou la "racine") du projet en recherchant une variété de marqueurs, tels que des fichiers ou des motifs de répertoires. Il fait de son mieux mais se trompe parfois, et vous pouvez outrepasser cela avec cette option.

L'origine du projet est utilisée pour déterminer le chemin de certains fichiers d'ignorance, quel VCS est utilisé, la signification d'un '/' en tête dans les motifs de filtrage, et peut-être plus à l'avenir.

Lorsqu'il est défini, Watchexec ne s'embêtera pas non plus à chercher, ce qui peut être considérablement plus rapide.

--workdir <REPERTOIRE>
Définir le répertoire de travail

Par défaut, le répertoire de travail de la commande est le répertoire de travail de Watchexec. Vous pouvez le modifier avec cette option. Notez que les chemins peuvent être moins intuitifs à utiliser avec ceci.

-e, --exts <EXTENSIONS>
Extensions de nom de fichier à filtrer

C'est un filtre rapide pour n'émettre des événements que pour les fichiers avec les extensions données. Les extensions peuvent être données avec ou sans le point initial (par exemple, 'js' ou '.js'). Plusieurs extensions peuvent être données en répétant l'option ou en les séparant par des virgules.

-f, --filter <MOTIF>
Motifs de nom de fichier à filtrer

Fournissez un motif de type glob, et seuls les événements pour les fichiers correspondant au motif seront émis. Plusieurs motifs peuvent être donnés en répétant l'option. Les événements qui ne proviennent pas de fichiers (par exemple, signaux, événements clavier) passeront sans être modifiés.

--filter-file <CHEMIN>
Fichiers à partir desquels charger les filtres

Fournissez un chemin vers un fichier contenant des filtres, un par ligne. Les lignes vides et les lignes commençant par '#' sont ignorées. Utilise le même format de motif que l'option '--filter'.

Cela peut également être utilisé via la variable d'environnement $WATCHEXEC_FILTER_FILES.

-J, --filter-prog <EXPRESSION>
[expérimental] Programmes de filtrage.

/!\ Cette option est EXPÉRIMENTALE et peut changer et/ou disparaître sans préavis.

Fournissez vos propres programmes de filtrage personnalisés en syntaxe jaq (similaire à jq). Les programmes reçoivent un événement dans le même format que décrit dans '--emit-events-to' et doivent retourner un booléen. Les programmes invalides empêcheront watchexec de démarrer ; utilisez '-v' pour voir les erreurs d'exécution du programme.

En plus de la bibliothèque standard jaq, watchexec ajoute quelques définitions de filtre personnalisées :

- 'path | file_meta' retourne les métadonnées du fichier ou null si le fichier n'existe pas.

- 'path | file_size' retourne la taille du fichier au chemin donné, ou null s'il n'existe pas.

- 'path | file_read(bytes)' retourne une chaîne avec les n premiers octets du fichier au chemin donné. Si le fichier est plus petit que n octets, le fichier entier est retourné. Il n'y a pas de filtre pour lire le fichier entier à la fois pour encourager la limitation de la quantité de données lues et traitées.

- 'string | hash', et 'path | file_hash' retournent le hash de la chaîne ou du fichier au chemin donné. Aucune garantie n'est faite quant à l'algorithme utilisé : considérez-le comme une valeur opaque.

- 'any | kv_store(key)', 'kv_fetch(key)', et 'kv_clear' fournissent un simple magasin clé-valeur. Les données sont conservées uniquement en mémoire, il n'y a pas de persistance. La cohérence n'est pas garantie.

- 'any | printout', 'any | printerr', et 'any | log(level)' afficheront ou enregistreront n'importe quelle valeur donnée sur la sortie standard, la sortie d'erreur, ou le log (niveaux = error, warn, info, debug, trace), et transmettront la valeur (ainsi '[1] | log("debug") | .[]' produira un '1' et enregistrera '[1]').

Tout filtrage effectué avec de tels programmes, et en particulier ceux utilisant l'accès kv ou au système de fichiers, est beaucoup plus lent que les autres méthodes de filtrage. Si le filtrage est trop lent, les événements s'accumuleront et bloqueront watchexec. Soyez prudent lors de la conception de vos filtres.

Si l'argument de cette option commence par un '@', le reste de l'argument est considéré comme le chemin vers un fichier contenant un programme jaq.

Les programmes Jaq sont exécutés dans l'ordre, après tous les autres filtres, et s'arrêtent brièvement : si un filtre (jaq ou non) rejette un événement, l'exécution s'arrête là, et aucun autre filtre n'est exécuté. De plus, ils s'arrêtent après avoir émis la première valeur, vous voudrez donc utiliser 'any' ou 'all' lors de l'itération, sinon seul le premier élément sera traité, ce qui peut être assez déroutant !

Trouvez des programmes contribués par des utilisateurs ou soumettez les vôtres sur https://github.com/watchexec/watchexec/discussions/592.

## Exemples :

Filtre d'ignorance par expression régulière sur les chemins :

'all(.tags[] | select(.kind == "path"); .absolute | test("[.]test[.]js$")) | not'

Passer tout événement qui crée un fichier :

'any(.tags[] | select(.kind == "fs"); .simple == "create")'

Passer les événements qui touchent des fichiers exécutables :

'any(.tags[] | select(.kind == "path" && .filetype == "file"); .absolute | metadata | .executable)'

Ignorer les fichiers qui commencent par des shebangs :

'any(.tags[] | select(.kind == "path" && .filetype == "file"); .absolute | read(2) == "#!") | not'

-i, --ignore <MOTIF>
Motifs de nom de fichier à exclure

Fournissez un motif de type glob, et les événements pour les fichiers correspondant au motif seront exclus. Plusieurs motifs peuvent être donnés en répétant l'option. Les événements qui ne proviennent pas de fichiers (par exemple, signaux, événements clavier) passeront sans être modifiés.

--ignore-file <CHEMIN>
Fichiers à partir desquels charger les ignorances

Fournissez un chemin vers un fichier contenant des ignorances, une par ligne. Les lignes vides et les lignes commençant par '#'

' sont ignorés. Utilise le même format de motif que l'option '--ignore'.

Ceci peut également être utilisé via la variable d'environnement $WATCHEXEC_IGNORE_FILES.

--fs-events <événements>
Événements du système de fichiers pour filtrer

C'est un filtre rapide pour n'émettre des événements que pour les types de changements du système de fichiers donnés. Choisissez parmi 'access', 'create', 'remove', 'rename', 'modify', 'metadata'. Plusieurs types peuvent être donnés en répétant l'option ou en les séparant par des virgules. Par défaut, il s'agit de tous les types, à l'exception de 'access'.

Cela peut appliquer un filtrage au niveau du noyau lorsque possible, ce qui peut être plus efficace, mais peut être plus déroutant lors de la lecture des journaux.

--no-meta
Ne pas émettre d'événements fs pour les changements de métadonnées

C'est un raccourci pour '--fs-events create,remove,rename,modify'. Son utilisation en conjonction avec l'option '--fs-events' est absurde et non autorisée.

--print-events
Imprimer les événements qui déclenchent des actions

Ceci imprime les événements qui ont déclenché l'action lors de sa gestion (après le dé-rebond), sous une forme lisible par l'homme. Ceci est utile pour le débogage des filtres.

Utilisez '-vvv' à la place lorsque vous avez besoin de plus d'informations de diagnostic.

--manual
Afficher la page de manuel

Ceci affiche la page de manuel pour Watchexec, si la sortie est un terminal et que le programme 'man' est disponible. Sinon, la page de manuel est imprimée sur stdout au format ROFF (adapté à l'écriture dans un fichier watchexec.1). Arguments :

<TACHE>
Tâches à exécuter Peut spécifier plusieurs tâches en les séparant par `:::` par exemple : `mise run task1 arg1 arg2 ::: task2 arg1 arg2`
<ARGS>
Tâche et arguments à exécuter
