NOM

mysqlrouter - MySQL Router

SYNTAXE

mysqlrouter [options]

DESCRIPTION

• Résumé des options de mysqlrouter
• Descriptions des options de mysqlrouter

MySQL Router accepte des options de ligne de commande qui sont passées à mysqlrouter pour affecter son comportement, ou pour amorcer le routeur en se basant sur un InnoDB Cluster.

Au démarrage du Router, vous pouvez éventuellement utiliser --config pour spécifier l'emplacement du fichier de configuration principal (sinon l'emplacement par défaut est utilisé) et --extra-config pour un fichier de configuration supplémentaire.

Les options de ligne de commande d'amorçage affectent les fichiers et répertoires générés qui sont utilisés lors du démarrage de MySQL Router. Résumé des options de mysqlrouter Descriptions des options de mysqlrouter

•--version, -V
Format de ligne de commande --version , -V

Affiche le numéro de version et les informations connexes de l'application, puis quitte. Par exemple :

$> mysqlrouter --version
MySQL Router v8.4.5 on Linux (64-bit) (édition communautaire GPL)
•--help, -?
Format de ligne de commande --help , -?

Affiche l'aide et des informations informatives, puis quitte.

L'option --help a un avantage supplémentaire. Outre l'explication de chacune des options, l'option --help affiche également les chemins utilisés pour trouver le fichier de configuration, ainsi que plusieurs chemins par défaut. L'extrait suivant de la sortie de --help montre un exemple provenant d'une machine Ubuntu 16.04 :

$> mysqlrouter --help
...
Démarrer MySQL Router.
La configuration est lue à partir des fichiers suivants dans l'ordre spécifié
(entre parenthèses signifie non disponible pour la lecture) :
  (/etc/mysqlrouter/mysqlrouter.conf)
  /home/philip/.mysqlrouter.conf
Chemin des plugins :
  /usr/lib/x86_64-linux-gnu/mysqlrouter
Répertoire de logs par défaut :
  /var/log/mysqlrouter
Répertoire de données persistantes par défaut :
  /var/lib/mysqlrouter
Répertoire d'état d'exécution par défaut :
  /run/mysqlrouter
Utilisation : mysqlrouter [-V|--version] [-?|--help]
...

La section de configuration montre l'ordre des chemins qui peuvent être utilisés pour lire le fichier de configuration. Dans ce cas, seul le deuxième fichier est accessible.

•--bootstrap URI, -B URI
Format de ligne de commande --bootstrap URI, -B URI
Type Chaîne

L'option principale pour effectuer un amorçage de MySQL Router en se connectant au serveur de métadonnées de l'InnoDB Cluster à l'URI fournie. MySQL Router se configure lui-même en fonction des informations récupérées du serveur de métadonnées de l'InnoDB Cluster. Un mot de passe est demandé si nécessaire. Si aucun nom d'utilisateur n'est fourni dans le cadre de l'URI, le nom d'utilisateur par défaut "root" est utilisé. Voir Connexion via des chaînes de connexion de type URI[1] pour plus d'informations sur l'utilisation d'un chemin pour spécifier une instance de serveur.


Note
Bien que --bootstrap accepte une URI pour les connexions TCP/IP, l'utilisation de l'option --bootstrap-socket avec un nom de socket de domaine Unix local remplace la partie "hôte:port" de l'URI passée à l'option --bootstrap par le socket sur la même machine.
Par défaut, le processus d'amorçage effectue une configuration globale de MySQL Router. Une seule instance de MySQL Router peut être configurée pour un fonctionnement global. L'instance système de MySQL Router a un nom de routeur "system". Si des instances supplémentaires sont souhaitées, utilisez l'option --directory pour créer des installations MySQL Router autonomes.

URI : une instance de serveur d'un InnoDB Cluster pour récupérer des informations de métadonnées. Si l'URI fournie est une instance en lecture seule, MySQL Router se reconnecte automatiquement à une instance en lecture-écriture dans l'InnoDB Cluster afin de pouvoir enregistrer MySQL Router.

Si un fichier de configuration existe déjà lorsque vous démarrez MySQL Router avec --bootstrap, l'id de routeur existant dans ce fichier est réutilisé, et un processus de reconfiguration se produit. Le fichier de configuration est régénéré à partir de zéro et le compte du serveur de métadonnées de MySQL Router est recréé, bien qu'avec le même nom.

Au cours du processus de reconfiguration, toutes les modifications apportées à un fichier de configuration existant sont supprimées. Pour personnaliser un fichier de configuration tout en conservant la capacité de reconfiguration automatique (amorçage), vous pouvez utiliser l'option de ligne de commande --extra-config pour spécifier un fichier de configuration supplémentaire qui est lu après le fichier de configuration principal. Ces options de configuration sont utilisées car ce fichier de configuration supplémentaire est chargé après le fichier de configuration principal.

Le processus d'amorçage crée un nouveau compte utilisateur MySQL avec un mot de passe généré aléatoirement pour être utilisé par cette instance spécifique de MySQL Router. Ce compte est utilisé par MySQL Router lors de la connexion au serveur de métadonnées et à l'InnoDB Cluster pour récupérer des informations sur son état actuel. Pour des informations détaillées sur cet utilisateur, y compris comment son mot de passe est stocké et le privilège MySQL qu'il nécessite, voir la documentation de l'option utilisateur MySQL.

Le fichier de configuration généré est nommé mysqlrouter.conf, et son emplacement dépend du type d'instance configuré, du système et du paquet. Pour les installations globales, le fichier de configuration généré est ajouté au répertoire de configuration du système tel que /etc ou %PROGRAMDATA%\MySQL\MySQL Router\. L'exécution de mysqlrouter --help affichera cet emplacement.

L'option --user est requise si vous effectuez un amorçage avec un super-utilisateur (uid=0). Bien que non recommandé, il est possible de forcer l'utilisation du super-utilisateur en passant son nom comme argument, par exemple --user=root.

Les privilèges GRANT minimum requis pour exécuter --bootstrap sont :

GRANT CREATE USER ON *.* TO 'bootstrapuser'@'%' WITH GRANT OPTION;
GRANT SELECT, INSERT, UPDATE, DELETE, EXECUTE ON mysql_innodb_cluster_metadata.* TO 'bootstrapuser'@'%';
GRANT SELECT ON mysql.user TO 'bootstrapuser'@'%';
GRANT SELECT ON performance_schema.replication_group_members TO 'bootstrapuser'@'%';
GRANT SELECT ON performance_schema.replication_group_member_stats TO 'bootstrapuser'@'%';
GRANT SELECT ON performance_schema.global_variables TO 'bootstrapuser'@'%';

L'utilisation de --bootstrap ajoute des valeurs par défaut au fichier de configuration MySQL Router généré, et certaines de ces valeurs par défaut dépendent d'autres conditions. Vous trouverez ci-dessous certaines des conditions qui affectent les valeurs par défaut générées, où par défaut est défini en passant simplement --bootstrap.

•--core-file
Format de ligne de commande --core-file[={0|1}]
Type Booléen
Valeur par défaut 0

Écrit un fichier core si mysqlrouter plante. Le nom et l'emplacement du fichier core dépendent du système. Sous Linux, un fichier core nommé core.pid est écrit dans le répertoire de travail courant du processus. pid représente l'identifiant du processus du serveur. •--directory dir_path, -d dir_path
Format de ligne de commande --directory dir_path, -d dir_path
Type Chaîne de caractères

Spécifie qu'une installation MySQL Router autonome sera créée dans le répertoire défini au lieu de configurer l'instance de routeur système. Cela permet également de créer plusieurs instances de routeur sur le même système.

La structure de répertoire autonome pour Router est :

$path/start.sh
$path/stop.sh
$path/mysqlrouter.pid
$path/mysqlrouter.conf
$path/mysqlrouter.key
$path/run
$path/run/keyring
$path/data
$path/log
$path/log/mysqlrouter.log

Si cette option est spécifiée, le fichier keyring est stocké sous le répertoire d'état d'exécution de cette instance, sous run/ dans le répertoire spécifié, par opposition au répertoire d'état d'exécution système.

Si --conf-use-sockets est également activé, les fichiers sockets générés sont également ajoutés à ce répertoire.

•--master-key-writer
Format de ligne de commande --master-key-writer file_path
Type Chaîne de caractères

Cette option d'initialisation facultative accepte un script qui lit la clé maître depuis STDIN. Elle utilise également la variable d'environnement ROUTER_ID définie par MySQL Router avant que le script master-key-writer ne soit appelé.

Les options master-key-writer et master-key-reader doivent être utilisées ensemble, et leur utilisation signifie que l'option master_key_file ne doit pas être définie dans mysqlrouter.conf car la clé maître n'est pas écrite dans le fichier de clé maître mysqlrouter.key.

Ceci est également écrit dans le fichier de configuration MySQL Router généré en tant qu'option master-key-writer [DEFAULT].

Exemple de contenu d'un script bash nommé writer.sh utilisé dans notre exemple :

#!/bin/bash
KID_=$(keyctl padd user ${ROUTER_ID} @us <&0)

Exemple d'utilisation :

$> mysqlrouter --bootstrap=127.0.0.1:3310 --master-key-reader=./reader.sh
  --master-key-writer=./writer.sh

Ceci affecte également le mysqlrouter.conf généré, par exemple :

[DEFAULT]
...
master-key-reader=reader.sh
master-key-writer=writer.sh
•--master-key-reader
Format de ligne de commande --master-key-reader file_path
Type Chaîne de caractères

Cette option d'initialisation facultative accepte un script qui écrit la clé maître sur STDOUT. Elle utilise également la variable d'environnement ROUTER_ID définie par MySQL Router avant que le script master-key-reader ne soit appelé.

Les options master-key-reader et master-key-writer doivent être utilisées ensemble, et leur utilisation signifie que l'option master_key_file ne doit pas être définie dans mysqlrouter.conf car la clé maître n'est pas écrite dans le fichier de clé maître mysqlrouter.key, et utilise à la place la valeur fournie par le script de cette option.

Ceci est également écrit dans le fichier de configuration MySQL Router généré en tant qu'option master-key-reader [DEFAULT].

Exemple de contenu d'un script bash nommé reader.sh utilisé dans notre exemple :

#!/bin/bash
KID_=$(keyctl search @us user ${ROUTER_ID} 2>/dev/null)
if [ ! -z $KID_ ]; then
  keyctl pipe $KID_
fi

Exemple d'utilisation :

$> mysqlrouter --bootstrap=127.0.0.1:3310 --master-key-reader=./reader.sh
  # Ou, plusieurs hôtes--master-key-writer=./writer.sh

Ceci affecte également le mysqlrouter.conf généré, par exemple :

[DEFAULT]
...
master-key-reader=reader.sh
master-key-writer=writer.sh
•--strict
Format de ligne de commande --strict
Type Chaîne de caractères

Active le mode strict, qui par exemple fait que la vérification de l'utilisateur --account lors de l'initialisation arrête le processus d'initialisation plutôt que de simplement émettre un avertissement et de continuer si l'utilisateur fourni ne réussit pas la vérification.

•--account
Format de ligne de commande --account username
Type Chaîne de caractères

Une option d'initialisation pour spécifier l'utilisateur MySQL à utiliser, qui réutilise un compte utilisateur MySQL existant ou en crée un ; le comportement est contrôlé par l'option associée --account-create.

Avec --account, l'utilisation privilégie la facilité de gestion à la facilité de déploiement car plusieurs routeurs peuvent partager le même compte, et le nom d'utilisateur ainsi que le mot de passe sont définis manuellement plutôt qu'auto-générés.

La définition de cette option déclenche une invite de mot de passe pour ce compte, indépendamment du fait que le mot de passe soit disponible dans le keyring.

L'initialisation sans passer --account ne recrée pas un compte serveur MySQL existant.

L'utilisation de cette option suppose que l'utilisateur dispose des droits d'accès suffisants pour Router car le processus d'initialisation ne tente pas d'ajouter les privilèges manquants aux comptes existants. Le processus d'initialisation vérifie les permissions et affiche des informations sur la console concernant l'échec de la vérification. Le processus d'initialisation se poursuit malgré ces échecs de vérification, sauf si l'option facultative --strict est également utilisée. Exemple de permissions requises :

GRANT USAGE ON *.* TO `theuser`@`%`
GRANT SELECT, EXECUTE ON `mysql_innodb_cluster_metadata`.* TO `theuser`@`%`
GRANT INSERT, UPDATE, DELETE ON `mysql_innodb_cluster_metadata`.`routers` TO `theuser`@`%`
GRANT INSERT, UPDATE, DELETE ON `mysql_innodb_cluster_metadata`.`v2_routers` TO `theuser`@`%`
GRANT SELECT ON `performance_schema`.`global_variables` TO `theuser`@`%`
GRANT SELECT ON `performance_schema`.`replication_group_member_stats` TO `theuser`@`%`
GRANT SELECT ON `performance_schema`.`replication_group_members` TO `theuser`@`%`

Un mot de passe n'est pas accepté en ligne de commande. Par exemple, passer "foo:bar" suppose que "foo:bar" est le nom d'utilisateur souhaité plutôt que l'utilisateur foo avec le mot de passe bar.

•--account-create
Format de ligne de commande --account-create behavior
Type Chaîne de caractères
Valeur par défaut if-not-exists
Valeurs valides if-not-exists always never

Spécifie la politique de création de compte pour éviter d'initialiser accidentellement avec le mauvais compte utilisateur. Les valeurs possibles sont :

•if-not-exists (par défaut) : Initialise dans tous les cas ; réutilise le compte s'il existe, sinon le crée.
•always : N'initialise que si le compte n'existe pas déjà ; et le crée.
•never : N'initialise que si le compte existe déjà ; et le réutilise.

Cette option nécessite que l'option --account soit également utilisée, et que --account-host ne soit pas utilisée.

•--account-host
Format de ligne de commande --account-host host_pattern
Type Chaîne de caractères
Valeur par défaut %

Le modèle d'hôte utilisé pour les comptes créés par MySQL Router pendant le processus d'initialisation. Ceci est facultatif et vaut par défaut '%'.

Passez cette option plusieurs fois pour définir plusieurs modèles, auquel cas les comptes MySQL générés utilisent le même mot de passe.


Note
Router n'effectue pas de vérification de cohérence et ne garantit pas que le modèle autorise Router à se connecter.

Note
L'initialisation réutilise les comptes Router existants en supprimant et recréant l'utilisateur, et ce processus de recréation d'utilisateur s'applique à tous les hôtes.
Exemples : 
# Un hôte
$> mysqlrouter --bootstrap localhost:3310 --account-host host1
# Ou, plusieurs hôtes
$> mysqlrouter --bootstrap localhost:3310 --account-host host1 --account-host host2
  --account-host host3
•--conf-use-sockets
Format de ligne de commande --conf-use-sockets
Spécifique à la plateforme Linux

Active les sockets de domaine Unix locaux.

Cette option est utilisée lors de l'initialisation, et son activation ajoute l'option socket au fichier de configuration généré.

Le nom du fichier socket généré dépend de l'option protocol. Avec le protocole classique activé, le fichier est nommé mysql.sock pour les connexions en lecture-écriture,et mysqlro.sock pour les connexions en lecture seule. Avec le protocole X activé, le fichier est nommé mysqlx.sock pour les connexions en lecture/écriture et mysqlxro.sock pour les connexions en lecture seule.

Cette option n'est pas disponible sous Windows.

•--conf-use-gr-notifications
Format en ligne de commande --conf-use-gr-notifications

Active l'option use_gr_notifications [metadata_cache] pendant le bootstrap. Lorsqu'elle est activée, Router est notifié de manière asynchrone de la plupart des changements du cluster. Voir use_gr_notifications pour plus d'informations. De plus, l'utilisation de cette option définit ttl=60 et auth_cache_refresh_interval=60.

•--pid-file chemin
Format en ligne de commande --pid-file chemin
Type Chaîne

Définit l'emplacement du fichier PID. Cela peut être défini de trois manières différentes (par ordre de priorité) : cette option de ligne de commande --pid-file, la définition de pid_file dans le fichier de configuration de Router, ou la définition de la variable d'environnement ROUTER_PID.

Si --bootstrap est spécifié, alors la définition de --pid-file provoque l'échec de Router. Ceci est différent de ROUTER_PID et de l'option de configuration pid_file, qui sont ignorés si --bootstrap est spécifié.

Si --bootstrap n'est pas spécifié, alors les conditions suivantes provoquent l'échec de Router : le fichier --pid-file existe déjà, pid_file ou ROUTER_PID sont définis mais vides, ou si Router ne peut pas écrire le fichier PID.

•--report-host
Format en ligne de commande --report-host nom_hote
Type Chaîne

Définit éventuellement le nom d'hôte de Router au lieu de s'appuyer sur la détection automatique pour déterminer le nom d'hôte visible de l'extérieur enregistré dans les métadonnées pendant le processus de bootstrap.

Router ne vérifie ni ne confirme que le nom d'hôte fourni est accessible, mais utilise le RFC 1123 pour valider les noms d'hôtes et le RFC 2181 pour valider les adresses.

Le nom d'hôte fourni est écrit dans le champ host_name de la table mysql_innodb_cluster_metadata.hosts dans le magasin de métadonnées du cluster MySQL InnoDB.

•--conf-skip-tcp
Format en ligne de commande --conf-skip-tcp
Spécifique à la plateforme Linux

Ignore la configuration d'un port TCP pour l'écoute des connexions entrantes. Voir aussi --conf-use-sockets.

Cette option n'est pas disponible sous Windows.

•--conf-base-port port_num
Format en ligne de commande --conf-base-port port_num
Type Entier
Valeur par défaut 0

Valeur de base (première) utilisée pour les ports TCP d'écoute en définissant bind_port pour chaque route bootstrapée.

Cette valeur est utilisée pour la route classique lecture/écriture, et chaque port supplémentaire alloué est incrémenté de un. L'ordre des ports défini est classique lecture/écriture / lecture seule, puis x lecture/écriture / lecture seule.

Définir --conf-base-port à 0 change les valeurs par défaut de bind_port aux valeurs par défaut suivantes, qui étaient : Pour le protocole classique, Lecture/Écriture utilise 6446 et Lecture Seule utilise 6447, et pour le protocole X, Lecture/Écriture utilise 64460 et Lecture Seule utilise 64470.

Exemple d'utilisation :

# Exemple sans --conf-base-port
$> mysqlrouter --bootstrap root@localhost:3310
...
Connexions au protocole MySQL classique au cluster 'devCluster' :
- Connexions Lecture/Écriture : localhost:6446
- Connexions Lecture Seule : localhost:6447
Connexions au protocole X au cluster 'devCluster' :
- Connexions Lecture/Écriture : localhost:6448
- Connexions Lecture Seule : localhost:6449
# Exemple démontrant --conf-base-port défini à 0
$> mysqlrouter --bootstrap root@localhost:3310 --conf-base-port 0
...
Connexions au protocole MySQL classique au cluster 'devCluster' :
- Connexions Lecture/Écriture : localhost:6446
- Connexions Lecture Seule : localhost:6447
Connexions au protocole X au cluster 'devCluster' :
- Connexions Lecture/Écriture : localhost:64460
- Connexions Lecture Seule : localhost:64470
•--conf-bind-address adresse
Format en ligne de commande --conf-bind-address adresse
Type Chaîne
Valeur par défaut 0.0.0.0

Modifie la valeur bind_address définie par --bootstrap dans le fichier de configuration Router généré. Par défaut, le bootstrap définit bind_address=0.0.0.0 pour chaque route, et cette option modifie cette valeur.


Note
La valeur par défaut de bind_address est 127.0.0.1 si bind_address n'est pas définie.
•--read-timeout sec_num
Format en ligne de commande --read-timeout sec_num
Type Entier
Valeur par défaut 30

Nombre de secondes avant que les opérations de lecture vers un serveur de métadonnées ne soient considérées comme expirées.

Cela affecte les opérations de lecture pendant le processus de bootstrap, et affecte également les opérations normales de MySQL Router en définissant l'option associée read_timeout dans le fichier mysqlrouter.conf généré.

Cette option est définie dans l'espace de noms [DEFAULT].

•--connect-timeout sec_num
Format en ligne de commande --connect-timeout sec_num
Type Entier
Valeur par défaut 30

Nombre de secondes avant que les tentatives de connexion à un serveur de métadonnées ne soient considérées comme expirées.

Cela affecte les connexions pendant le processus de bootstrap, et affecte également les opérations normales de MySQL Router en définissant l'option associée connect_timeout dans le fichier mysqlrouter.conf généré.

Il existe deux variantes de connect_timeout. La variante serveur de métadonnées est définie dans l'espace de noms [DEFAULT], tandis que la variante serveur MySQL est définie dans l'espace de noms [routing].

•--user {nom_utilisateur|id_utilisateur}, -u {nom_utilisateur|id_utilisateur}
Format en ligne de commande --user {nom_utilisateur|id_utilisateur}, -u {nom_utilisateur|id_utilisateur}
Spécifique à la plateforme Linux
Type Chaîne

Exécute mysqlrouter en tant qu'utilisateur ayant le nom nom_utilisateur ou l'ID utilisateur numérique id_utilisateur. L'"utilisateur" dans ce contexte fait référence à un compte de connexion système, et non à un utilisateur MySQL listé dans les tables de privilèges. Lors du bootstrap, tous les fichiers générés appartiennent à cet utilisateur, et cela définit également l'option associée user.

Cet utilisateur système est défini dans le fichier de configuration sous l'espace de noms [DEFAULT]. Pour plus d'informations, voir la documentation de l'option user que --user configure.

L'option --user est requise si l'on exécute un bootstrap en tant qu'utilisateur superutilisateur (uid=0). Bien que déconseillé, forcer l'utilisateur superutilisateur est possible en passant son nom comme argument, par exemple --user=root.

Cette option n'est pas disponible sous Windows.

•--name nom_router
Format en ligne de commande --name nom_router
Type Chaîne
Valeur par défaut system

Lors du bootstrap initial, spécifie un nom symbolique pour une instance de Router autonome. Cette option est facultative et est utilisée avec --directory. Lors de la création de plusieurs instances, les noms doivent être uniques.

•--force-password-validation
Format en ligne de commande --force-password-validation
Spécifique à la plateforme Linux

Par défaut, MySQL Router ignore le mécanisme de validation de mot de passe du serveur MySQL et utilise à la place un mot de passe FORT généré par Router, basé sur les paramètres par défaut connus de validation de mot de passe. Ceci est dû au fait que la validation de mot de passe peut être configurée par l'utilisateur et que Router ne peut pas prendre en compte des paramètres personnalisés inhabituels.

Cette option garantit que la validation de mot de passe (validate_password) n'est pas ignorée pour les mots de passe générés, et elle est désactivée par défaut.

•--password-retries nb_tentatives
Format en ligne de commande --password-retries nb_tentatives
Type Entier
Valeur par défaut 20
Valeur minimale 1
Valeur maximale 10000

Spécifie le nombre de fois que MySQL Router doit tenter de générer un mot de passe lors de la création d'un compte utilisateur avec les règles de validation de mot de passe. La valeur par défaut est 20. La plage valide est de 1 à 10000.

La raison la plus probable d'échec est due à des paramètres validate_password personnalisés avec des exigences inhabituelles, telles qu'un minimum de 50 caractères. Dans ce scénario d'échec, soit --force-password-validation est défini sur vrai et/ou le plugin MySQL Server mysql_native_password est désactivé (ce plugin permet de contourner la validation).

•--ssl-mode mode
Format en ligne de commande --ssl-mode mode
Type Chaîne de caractères
Valeur par défaut PREFERRED
Valeurs valides PREFERRED DISABLED REQUIRED VERIFY_CA VERIFY_IDENTITY

Mode de connexion SSL à utiliser pendant l'amorçage et le fonctionnement normal lors de la connexion au serveur de métadonnées. Analogue à --ssl-mode dans le client mysql.

Pendant l'amorçage, toutes les connexions aux serveurs de métadonnées effectuées par le Routeur utiliseront les options SSL spécifiées. Si ssl_mode n'est pas spécifié dans la configuration, sa valeur par défaut sera PREFERRED. Pendant le fonctionnement normal, après le lancement du Routeur, son plugin Metadata Cache lira et respectera tous les paramètres SSL configurés.

Lorsqu'il est défini sur une valeur autre que la valeur par défaut (PREFERRED), une entrée ssl_mode est insérée dans la section [metadata_cache] du fichier de configuration généré.

Les valeurs disponibles sont DISABLED, PREFERRED, REQUIRED, VERIFY_CA et VERIFY_IDENTITY. PREFERRED est la valeur par défaut. Comme pour le client mysql, cette valeur ne respecte pas la casse.

L'équivalent du fichier de configuration est documenté séparément à ssl_mode.

•--conf-target-cluster
Format de ligne de commande --conf-target-cluster valeur
Type Chaîne
Valeurs valides current primary

Définit l'option de métadonnées MySQL Router target_cluster. Accepte l'une des chaînes suivantes :

•current : définit target_cluster sur le cluster contenant le nœud en cours de démarrage. Il le définit comme la valeur UUID du cluster.

Si c'est également le Primaire, il ne suit pas dynamiquement les changements de rôle comme le fait primary ; il reste statique.

•primary : définit target_cluster sur le cluster primaire, y compris lorsqu'il change à l'exécution.

Voir aussi --config-target-cluster-by-name, qui définit target_cluster sur un nom de cluster statique spécifique.

Le démarrage sur un ClusterSet[2] nécessite que l'option de configuration du Routeur cluster_type soit définie sur gr.
•--conf-set-option
Format de ligne de commande --conf-set-option nom_section[:clé_section_optionnelle].option=valeur
Type Chaîne

Définit une valeur pour une option de configuration générée pendant le démarrage ; cela peut définir une valeur pour toute option démarrée, par exemple :

$> mysqlrouter -B 127.0.0.1:5000 \
               --directory=dir1  \
               --conf-set-option=logger.level=debug \
               --conf-set-option=routing:test_rw.max_connect_errors=0 \
               --conf-set-option=routing:test_ro.max_connect_errors=0

Ces commandes modifient les valeurs par défaut de ces options spécifiques en les définissant comme suit :

[logger]
level=debug
[routing:test_rw]
...
max_connect_errors=0
...
[routing:test_ro]
...
max_connect_errors=0
...

Les définitions --conf-set-option ont la priorité sur les paramètres spécifiques de l'option pour définir une valeur spécifique. Par exemple, si --connect-timeout=X et --conf-set-option=DEFAULT.connect_timeout=Y sont spécifiés lors du démarrage, le connect_timeout est défini sur Y dans le fichier de configuration généré.
