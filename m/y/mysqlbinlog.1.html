MARIADB-BINLOG(1) Système de base de données MariaDB MARIADB-BINLOG(1)

NOM

mariadb-binlog - utilitaire pour traiter les fichiers de journal binaire (mariadb-binlog est maintenant un lien symbolique vers mariadb-binlog)

SYNTAXE

mariadb-binlog [options] fichier_log ...

DESCRIPTION

Le journal binaire du serveur se compose de fichiers contenant des « événements » qui décrivent les modifications apportées au contenu de la base de données. Le serveur écrit ces fichiers au format binaire. Pour afficher leur contenu sous forme de texte, utilisez l'utilitaire mariadb-binlog. Vous pouvez également utiliser mariadb-binlog pour afficher le contenu des fichiers de journal relais écrits par un serveur esclave dans une configuration de réplication, car les journaux relais ont le même format que les journaux binaires.

Appelez mariadb-binlog comme ceci :

shell> mariadb-binlog [options] fichier_log ...

Par exemple, pour afficher le contenu du fichier journal binaire nommé binlog.000003, utilisez cette commande :

shell> mariadb-binlog binlog.0000003

La sortie inclut les événements contenus dans binlog.000003. Pour la journalisation basée sur les instructions, les informations sur les événements incluent l'instruction SQL, l'ID du serveur sur lequel elle a été exécutée, l'horodatage lors de son exécution, le temps nécessaire, etc. Pour la journalisation basée sur les lignes, l'événement indique un changement de ligne plutôt qu'une instruction SQL.

Les événements sont précédés de commentaires d'en-tête qui fournissent des informations supplémentaires. Par exemple :

# at 141
#100309  9:28:36 server id 123  end_log_pos 245
  Query thread_id=3350  exec_time=11  error_code=0

Dans la première ligne, le numéro suivant at indique la position de départ de l'événement dans le fichier journal binaire.

La deuxième ligne commence par une date et une heure indiquant quand l'instruction a commencé sur le serveur où l'événement a été généré. Pour la réplication, cet horodatage est propagé aux serveurs esclaves. server id est la valeur de server_id du serveur où l'événement a été généré. end_log_pos indique où commence l'événement suivant (c'est-à-dire la position de fin de l'événement actuel + 1). thread_id indique quel thread a exécuté l'événement. exec_time est le temps passé à exécuter l'événement, sur un serveur maître. Sur un esclave, il s'agit de la différence entre l'heure de fin d'exécution sur l'esclave et l'heure de début d'exécution sur le maître. La différence sert d'indicateur du retard de réplication par rapport au maître. error_code indique le résultat de l'exécution de l'événement. Zéro signifie qu'aucune erreur ne s'est produite.

La sortie de mariadb-binlog peut être réexécutée (par exemple, en l'utilisant comme entrée pour mariadb) pour refaire les instructions du journal. Ceci est utile pour les opérations de récupération après un crash du serveur. Pour d'autres exemples d'utilisation, voir la discussion plus loin dans cette section.

Normalement, vous utilisez mariadb-binlog pour lire directement les fichiers de journal binaire et les appliquer au serveur MariaDB local. Il est également possible de lire les journaux binaires d'un serveur distant en utilisant l'option --read-from-remote-server. Pour lire les journaux binaires distants, les options de connexion peuvent être données pour indiquer comment se connecter au serveur. Ces options sont --host, --password, --port, --protocol, --socket, et --user ; elles sont ignorées sauf si vous utilisez également l'option --read-from-remote-server.

mariadb-binlog prend en charge les options suivantes, qui peuvent être spécifiées en ligne de commande ou dans les groupes de fichiers d'options [mariadb-binlog] et [client].

•--help, -?

Affiche un message d'aide et quitte.

•--base64-output=valeur

Cette option détermine quand les événements doivent être affichés encodés sous forme de chaînes base-64 à l'aide d'instructions BINLOG. L'option a les valeurs autorisées suivantes (insensibles à la casse) :

•AUTO (« automatique ») ou UNSPEC (« non spécifié ») affiche automatiquement les instructions BINLOG lorsque nécessaire (c'est-à-dire pour les événements de description de format et les événements de ligne). C'est le comportement par défaut si aucune option --base64-output n'est donnée.

Note
L'affichage automatique de BINLOG est le seul comportement sûr si vous avez l'intention d'utiliser la sortie de mariadb-binlog pour réexécuter le contenu des fichiers de journal binaire. Les autres valeurs d'option sont destinées uniquement à des fins de débogage ou de test car elles peuvent produire une sortie qui n'inclut pas tous les événements sous une forme exécutable.
•NEVER fait en sorte que les instructions BINLOG ne soient pas affichées. mariadb-binlog se termine avec une erreur si un événement de ligne est trouvé qui doit être affiché à l'aide de BINLOG.
•DECODE-ROWS spécifie à mariadb-binlog que vous avez l'intention que les événements de ligne soient décodés et affichés sous forme d'instructions SQL commentées en spécifiant également l'option --verbose. Comme NEVER, DECODE-ROWS supprime l'affichage des instructions BINLOG, mais contrairement à NEVER, il ne se termine pas par une erreur si un événement de ligne est rencontré.
Le --base64-output peut être donné comme --base64-output ou --skip-base64-output (avec le sens de AUTO ou NEVER).

Pour des exemples montrant l'effet de --base64-output et --verbose sur la sortie des événements de ligne, voir la section appelée « AFFICHAGE DES ÉVÉNEMENTS DE LIGNE DE MARIADB-BINLOG ».

•--binlog-row-event-max-size=chemin

Le répertoire où sont installés les jeux de caractères.

•--character-sets-dir=chemin

Le répertoire où sont installés les jeux de caractères.

•--database=nom_db, -d nom_db

Cette option fait en sorte que mariadb-binlog génère les entrées du journal binaire (journal local uniquement) qui se produisent pendant que nom_db a été sélectionné comme base de données par défaut par USE.

L'option --database pour mariadb-binlog est similaire à l'option --binlog-do-db pour mariadbd, mais peut être utilisée pour spécifier une seule base de données. Si --database est donnée plusieurs fois, seule la dernière instance est utilisée.

Les effets de cette option dépendent du fait que le format de journalisation basé sur les instructions ou basé sur les lignes est utilisé, de la même manière que les effets de --binlog-do-db dépendent du fait que la journalisation basée sur les instructions ou basée sur les lignes est utilisée.

Journalisation basée sur les instructions. L'option --database fonctionne comme suit :

•Tant que nom_db est la base de données par défaut, les instructions sont générées qu'elles modifient des tables dans nom_db ou une base de données différente.
•À moins que nom_db ne soit sélectionné comme base de données par défaut, les instructions ne sont pas générées, même si elles modifient des tables dans nom_db.
•Il y a une exception pour CREATE DATABASE, ALTER DATABASE et DROP DATABASE. La base de données en cours de *création, modification ou suppression* est considérée comme la base de données par défaut lors de la détermination de la nécessité de générer l'instruction.
Supposons que le journal binaire a été créé en exécutant ces instructions à l'aide de la journalisation basée sur les instructions : 
INSERT INTO test.t1 (i) VALUES(100);
INSERT INTO db2.t2 (j)  VALUES(200);
USE test;
INSERT INTO test.t1 (i) VALUES(101);
INSERT INTO t1 (i)      VALUES(102);
INSERT INTO db2.t2 (j)  VALUES(201);
USE db2;
INSERT INTO test.t1 (i) VALUES(103);
INSERT INTO db2.t2 (j)  VALUES(202);
INSERT INTO t2 (j)      VALUES(203);

mariadb-binlog --database=test ne génère pas les deux premières instructions INSERT car il n'y a pas de base de données par défaut. Il génère les trois instructions INSERT qui suivent USE test, mais pas les trois instructions INSERT qui suivent USE db2.

mariadb-binlog --database=db2 ne génère pas les deux premières instructions INSERT car il n'y a pas de base de données par défaut. Il ne génère pas les trois instructions INSERT qui suivent USE test, mais génère les trois instructions INSERT qui suivent USE db2.

Journalisation basée sur les lignes. mariadb-binlog génère uniquement les entrées qui modifient les tables appartenant à nom_db. La base de données par défaut n'a aucun effet sur cela. Supposons que le journal binaire décrit a été créé en utilisant la journalisation basée sur les lignes plutôt que la journalisation basée sur les instructions. mariadb-binlog --database=test génère uniquement les entrées qui modifient t1 dans la base de données test, qu'il ait été fait appel à USE ou quelle que soit la base de données par défaut. Si un serveur s'exécute avec binlog_format défini sur MIXED et que vous souhaitez pouvoir utiliser mariadb-binlog avec l'option --database, vous devez vous assurer que les tables qui sont modifiées sont dans la base de données sélectionnée

par UTILISATION. (En particulier, aucune mise à jour inter-bases de données ne doit être utilisée.)


Note
Cette option ne fonctionnait pas correctement pour mariadb-binlog avec l'enregistrement basé sur les lignes avant MySQL 5.1.37.
•--debug[=options_debug], -# [options_debug]

Écrit un journal de débogage. Une chaîne typique d' options_debug est 'd:t:o,nom_fichier'. La valeur par défaut est 'd:t:o,/tmp/mariadb-binlog.trace'.

•--debug-check

Affiche des informations de débogage à la sortie du programme.

•--debug-info

Affiche des informations de débogage ainsi que des statistiques d'utilisation de la mémoire et du processeur à la sortie du programme.

•--defaults-extra-file=nom

Lit ce fichier après les fichiers globaux.

•--defaults-file=nom

Ne lit les options par défaut que dans le fichier spécifié.

•--default-auth=nom

Plugin d'authentification côté client par défaut à utiliser.

•--disable-log-bin, -D

Désactive l'enregistrement binaire. Ceci est utile pour éviter une boucle infinie si vous utilisez l'option --to-last-log et que vous envoyez la sortie au même serveur MariaDB. Cette option est également utile lors de la restauration après un crash pour éviter la duplication des instructions que vous avez enregistrées.

Cette option nécessite que vous ayez le privilège SUPER. Elle provoque l'inclusion par mariadb-binlog d'une instruction SET sql_log_bin = 0 dans sa sortie pour désactiver l'enregistrement binaire de la sortie restante. L'instruction SET est inefficace à moins que vous n'ayez le privilège SUPER.

•--flashback, -B

Prend en charge le mode flashback.

•--force-if-open

Force si le binlog n'a pas été fermé correctement. Par défaut, activé ; utilisez --skip-force-if-open pour désactiver.

•--force-read, -f

Avec cette option, si mariadb-binlog lit un événement de journal binaire qu'il ne reconnaît pas, il affiche un avertissement, ignore l'événement et continue. Sans cette option, mariadb-binlog s'arrête s'il lit un tel événement.

•--hexdump, -H

Affiche une sortie hexadécimale du journal dans les commentaires, comme décrit dans la section intitulée “FORMAT DE SORTIE HEXADECIMALE DE MARIADB-BINLOG”. La sortie hexadécimale peut être utile pour le débogage de la réplication.

•--host=nom_hote, -h nom_hote

Obtient le journal binaire du serveur MariaDB sur l'hôte donné.

•--local-load=chemin, -l chemin

Prépare les fichiers temporaires locaux pour LOAD DATA INFILE dans le répertoire spécifié.

•--no-defaults

Ne lit pas les options par défaut dans les fichiers d'options.

•--offset=N, -o N

Ignore les N premières entrées du journal.

•--open-files-limit=NB

Définit la variable open_files_limit, qui est utilisée pour réserver des descripteurs de fichiers pour mariadb-binlog.

•--password[=mot_de_passe], -p[mot_de_passe]

Le mot de passe à utiliser lors de la connexion au serveur. Si vous utilisez la forme courte de l'option (-p), vous ne pouvez pas avoir d'espace entre l'option et le mot de passe. Si vous omettez la valeur mot_de_passe après l'option --password ou -p sur la ligne de commande, mariadb-binlog vous le demandera.

Spécifier un mot de passe sur la ligne de commande doit être considéré comme non sécurisé. Vous pouvez utiliser un fichier d'options pour éviter de donner le mot de passe sur la ligne de commande.

•--plugin-dir=nom_répertoire

Répertoire pour les plugins côté client.

•--print-defaults

Affiche la liste des arguments du programme à partir de tous les fichiers d'options et quitte.

•--port=num_port, -P num_port

Le numéro de port TCP/IP à utiliser pour se connecter à un serveur distant, ou 0 pour la valeur par défaut, dans l'ordre de préférence : my.cnf, $MYSQL_TCP_PORT, /etc/services, valeur par défaut intégrée (3306). Force --protocol=tcp lorsqu'il est spécifié sur la ligne de commande sans autres propriétés de connexion.

•--protocol={TCP|SOCKET|PIPE|MEMORY}

Le protocole de connexion à utiliser pour se connecter au serveur. Il est utile lorsque les autres paramètres de connexion entraîneraient normalement l'utilisation d'un protocole autre que celui souhaité.

•--raw

Nécessite -R. Affiche les données brutes du binlog au lieu des instructions SQL. Les fichiers de sortie sont nommés d'après les journaux du serveur.

•--read-from-remote-server, -R

Lit le journal binaire à partir d'un serveur MariaDB plutôt que de lire un fichier de journal local. Toutes les options de paramètre de connexion sont ignorées à moins que cette option ne soit également donnée. Ces options sont --host, --password, --port, --protocol, --socket, et --user.

Cette option nécessite que le serveur distant soit en cours d'exécution. Elle ne fonctionne que pour les fichiers de journaux binaires sur le serveur distant, pas pour les fichiers de journaux relais.

•--result-file=nom, -r nom

Dirige la sortie vers le fichier donné. Avec --raw, c'est un préfixe pour les noms de fichiers.

•--rewrite-db=nom, -r nom

Met à jour une base de données avec un nom différent de l'original. Exemple : rewrite-db='from->to'. Pour les événements qui sont enregistrés en tant qu'instructions, réécrire la base de données constitue le changement de la base de données par défaut d'une instruction de db1 à db2. Il n'y a pas d'analyse d'instruction ni de réécriture d'aucune sorte, c'est-à-dire que si l'on spécifie "db1.tbl" explicitement dans l'instruction, cette occurrence ne sera pas modifiée en "db2.tbl". Les événements basés sur les lignes sont correctement réécrits pour utiliser le nouveau nom de base de données. Le filtrage (par exemple avec --database=name) se produit après que les réécritures de base de données ont été effectuées. Si vous utilisez cette option sur la ligne de commande et que ">" a une signification spéciale pour votre interpréteur de commande, mettez la valeur entre guillemets (par exemple --rewrite-db="anciennom->nouveaunom".

•--server-id=id

Affiche uniquement les événements créés par le serveur ayant l'ID de serveur donné.

•--set-charset=nom_jeu_caracteres

Ajoute une instruction SET NAMES nom_jeu_caracteres à la sortie pour spécifier le jeu de caractères à utiliser pour le traitement des fichiers journaux.

•--short-form, -s

Affiche uniquement les instructions contenues dans le journal, sans informations supplémentaires ni événements basés sur les lignes. Ceci est uniquement à des fins de test et ne doit pas être utilisé dans les systèmes de production. Si vous souhaitez supprimer la sortie base64, envisagez d'utiliser --base64-output=never à la place.

•--socket=chemin, -S chemin

Pour les connexions à localhost, le fichier socket Unix à utiliser, ou, sous Windows, le nom du tuyau nommé à utiliser. Force --protocol=socket lorsqu'il est spécifié sur la ligne de commande sans autres propriétés de connexion ; sous Windows, force --protocol=pipe.

•--start-datetime=datetime

Commence à lire le journal binaire au premier événement dont l'horodatage est égal ou postérieur à l'argument datetime. La valeur datetime est relative au fuseau horaire local de la machine où vous exécutez mariadb-binlog. La valeur doit être dans un format accepté pour les types de données DATETIME ou TIMESTAMP. Par exemple :

shell> mariadb-binlog --start-datetime="2014-12-25 11:25:56" binlog.000003

Cette option est utile pour la récupération à un point précis dans le temps.

•--start-position=N, -j N

Commence à lire le journal binaire à la position N. Le type peut être un entier positif ou une liste GTID. Lors de l'utilisation d'un entier positif, la valeur ne s'applique qu'au premier binlog passé sur la ligne de commande, et le premier événement dont la position est égale ou supérieure à N est affiché. En mode GTID, plusieurs GTID peuvent être passés sous forme de liste séparée par des virgules, où chaque GTID doit avoir un identifiant de domaine unique. La liste représente l'état du binlog gtid dont le client (un autre serveur "réplique") a connaissance. Par conséquent, chaque GTID est exclusif ; seuls les événements après un numéro de séquence donné seront affichés pour permettre aux utilisateurs de recevoir les événements après leur état actuel.

Cette option est utile pour la récupération à un point précis dans le temps.

•--gtid-strict-mode

Traite le binlog conformément à la spécification gtid-strict-mode. Les positions de début et de fin sont vérifiées pour satisfaire la condition de comparaison start < stop. Les numéros de séquence de tout domaine gtid doivent constituer une séquence monotiquement croissante.

•--stop-datetime=datetime

Arrête de lire le journal binaire au premier événement dont l'horodatage est égal ou postérieur à l'argument datetime. Cette option est utile pour la récupération à un point précis dans le temps. Voir la description de l'option --start-datetime pour des informations sur la valeur datetime.

Cette option est utile pour la récupération à un point précis dans le temps.

•--stop-never

Attend plus de données du serveur au lieu de s'arrêter à la fin du dernier journal. Implique --to-last-log.

•--stop-never-slave-server-id

L'ID du serveur esclave utilisé pour --read-from-remote-server --stop-never.

•--stop-position=N

Arrête de lire le journal binaire au premier événement dont la position est égale ou supérieure à N. Le type peut être un entier positif ou une liste GTID. Lors de l'utilisation d'un entier positif, la valeur ne s'applique qu'au dernier fichier journal nommé sur la ligne de commande. En mode GTID, plusieurs GTID peuvent être passés sous forme de liste séparée par des virgules, où chaque GTID doit avoir un identifiant de domaine unique. Chaque GTID est inclusif ; seuls les événements jusqu'aux numéros de séquence donnés sont affichés.

Cette option est utile pour la récupération à un point précis dans le temps.

•--table, -T

Liste les entrées pour cette table uniquement (journal local uniquement).

• --to-last-log, -t

Ne pas s'arrêter à la fin du journal binaire demandé à partir d'un serveur MariaDB, mais continuer l'impression jusqu'à la fin du dernier journal binaire. Si vous envoyez la sortie au même serveur MariaDB, cela peut entraîner une boucle sans fin, cette option nécessite donc --read-from-remote-server.

•--user=nom_utilisateur, -u nom_utilisateur

Nom d'utilisateur MariaDB à utiliser lors de la connexion à un serveur distant.

•--verbose, -v

Reconstruire les événements de ligne et les afficher sous forme d'instructions SQL commentées. Si cette option est donnée deux fois, la sortie inclut des commentaires pour indiquer les types de données des colonnes et certains métadonnées. Si cette option est donnée trois fois, la sortie inclut des avertissements de diagnostic sur l'intégrité des événements avant la sortie du programme.

Pour des exemples qui montrent l'effet de --base64-output et --verbose sur l'affichage des événements de ligne, voir la section intitulée « MARIADB-BINLOG ROW EVENT DISPLAY ».

•--version, -V

Afficher les informations de version et quitter.

Vous pouvez également définir la variable suivante en utilisant la syntaxe --nom_variable=valeur :

•open_files_limit

Spécifier le nombre de descripteurs de fichiers ouverts à réserver.

Vous pouvez rediriger la sortie de mariadb-binlog vers le client mariadb pour exécuter les événements contenus dans le journal binaire. Cette technique est utilisée pour récupérer après un crash lorsque vous disposez d'une ancienne sauvegarde. Par exemple :

shell> mariadb-binlog binlog.000001 | mariadb -u root -p

Ou :

shell> mariadb-binlog binlog.[0-9]* | mariadb -u root -p

Vous pouvez également rediriger la sortie de mariadb-binlog vers un fichier texte, si vous avez besoin de modifier le journal des instructions au préalable (par exemple, pour supprimer des instructions que vous ne souhaitez pas exécuter pour une raison quelconque). Après avoir modifié le fichier, exécutez les instructions qu'il contient en l'utilisant comme entrée pour le programme mariadb :

shell> mariadb-binlog binlog.000001 > tmpfile
shell> ... modifier tmpfile ...
shell> mariadb -u root -p < tmpfile

Lorsque mariadb-binlog est invoqué avec l'option --start-position, il affiche uniquement les événements dont le décalage dans le journal binaire est supérieur ou égal à une position donnée (la position donnée doit correspondre au début d'un événement). Il dispose également d'options pour arrêter et démarrer lorsqu'il rencontre un événement à une date et une heure données. Cela vous permet d'effectuer une récupération à un point précis dans le temps en utilisant l'option --stop-datetime (pour pouvoir dire, par exemple, « rembobiner mes bases de données à leur état d'aujourd'hui à 10h30 »).

Si vous avez plus d'un journal binaire à exécuter sur le serveur MariaDB, la méthode sûre consiste à les traiter tous en utilisant une seule connexion au serveur. Voici un exemple qui démontre ce qui peut être dangereux :

shell> mariadb-binlog binlog.000001 | mariadb -u root -p # DANGER !!
shell> mariadb-binlog binlog.000002 | mariadb -u root -p # DANGER !!

Traiter les journaux binaires de cette manière en utilisant différentes connexions au serveur pose des problèmes si le premier fichier journal contient une instruction CREATE TEMPORARY TABLE et que le deuxième journal contient une instruction qui utilise la table temporaire. Lorsque le premier processus mariadb se termine, le serveur supprime la table temporaire. Lorsque le deuxième processus mariadb tente d'utiliser la table, le serveur signale « table inconnue ».

Pour éviter ce type de problèmes, utilisez un *unique* processus mariadb pour exécuter le contenu de tous les journaux binaires que vous souhaitez traiter. Voici une façon de le faire :

shell> mariadb-binlog binlog.000001 binlog.000002 | mariadb -u root -p

Une autre approche consiste à écrire tous les journaux dans un seul fichier, puis à traiter ce fichier :

shell> mariadb-binlog binlog.000001 > /tmp/statements.sql
shell> mariadb-binlog binlog.000002 >> /tmp/statements.sql
shell> mariadb -u root -p -e "source /tmp/statements.sql"

mariadb-binlog peut produire une sortie qui reproduit une opération LOAD DATA INFILE sans le fichier de données d'origine. mariadb-binlog copie les données dans un fichier temporaire et écrit une instruction LOAD DATA LOCAL INFILE qui fait référence au fichier. L'emplacement par défaut du répertoire où ces fichiers sont écrits dépend du système. Pour spécifier explicitement un répertoire, utilisez l'option --local-load.

Étant donné que mariadb-binlog convertit les instructions LOAD DATA INFILE en instructions LOAD DATA LOCAL INFILE (c'est-à-dire qu'il ajoute LOCAL), le client et le serveur que vous utilisez pour traiter les instructions doivent être configurés avec la capacité LOCAL activée.


Attention

Les fichiers temporaires créés pour les instructions LOAD DATA LOCAL ne sont pas supprimés automatiquement car ils sont nécessaires jusqu'à ce que vous exécutiez réellement ces instructions. Vous devez supprimer vous-même les fichiers temporaires après ne plus avoir besoin du journal des instructions. Les fichiers se trouvent dans le répertoire des fichiers temporaires et portent des noms tels que nom_fichier_originale-#-#.

MARIADB-BINLOG FORMAT HEX DUMP

L'option --hexdump fait en sorte que mariadb-binlog produise une sortie hexadécimale du contenu du journal binaire :

shell> mariadb-binlog --hexdump master-bin.000001

La sortie hexadécimale se compose de lignes de commentaires commençant par #, de sorte que la sortie pourrait ressembler à ceci pour la commande précédente :

/*!40019 SET @@session.max_delayed_threads=0*/;
/*!50003 SET @OLD_COMPLETION_TYPE=@@COMPLETION_TYPE,COMPLETION_TYPE=0*/;
# at 4
#051024 17:24:13 server id 1  end_log_pos 98
# Position  Timestamp   Type   Master ID        Size      Master Pos    Flags
# 00000004 9d fc 5c 43   0f   01 00 00 00   5e 00 00 00   62 00 00 00   00 00
# 00000017 04 00 35 2e 30 2e 31 35  2d 64 65 62 75 67 2d 6c |..5.0.15.debug.l|
# 00000027 6f 67 00 00 00 00 00 00  00 00 00 00 00 00 00 00 |og..............|

AFFICHAGE DES ÉVÉNEMENTS DE LIGNE MARIADB-BINLOG

Les exemples suivants illustrent comment mariadb-binlog affiche les événements de ligne qui spécifient des modifications de données. Ceux-ci correspondent aux événements avec les codes de type WRITE_ROWS_EVENT, UPDATE_ROWS_EVENT et DELETE_ROWS_EVENT. Les options --base64-output=DECODE-ROWS et --verbose peuvent être utilisées pour affecter la sortie des événements de ligne.

Supposons que le serveur utilise la journalisation binaire basée sur les lignes et que vous exécutiez la séquence d'instructions suivante :

CREATE TABLE t
(
  id   INT NOT NULL,
  name VARCHAR(20) NOT NULL,
  date DATE NULL
) ENGINE = InnoDB;
START TRANSACTION;
INSERT INTO t VALUES(1, 'apple', NULL);
UPDATE t SET name = 'pear', date = '2009-01-01' WHERE id = 1;
DELETE FROM t WHERE id = 1;
COMMIT;

Par défaut, mariadb-binlog affiche les événements de ligne encodés sous forme de chaînes base64 à l'aide d'instructions BINLOG. En omettant les lignes superflues, la sortie des événements de ligne produits par la séquence d'instructions précédente ressemble à ceci :

Note

Vous ne devez pas supprimer les instructions BINLOG si vous avez l'intention de réexécuter la sortie de mariadb-binlog.

Les instructions SQL produites par --verbose pour les événements de ligne sont beaucoup plus lisibles que les instructions BINLOG correspondantes. Cependant, elles ne correspondent pas exactement aux instructions SQL d'origine qui ont généré les événements. Les limitations suivantes s'appliquent :

•Les noms de colonnes d'origine sont perdus et remplacés par @N, où N est un numéro de colonne.
•Les informations sur le jeu de caractères ne sont pas disponibles dans le journal binaire, ce qui affecte l'affichage des colonnes de chaîne :
•Il n'y a pas de distinction entre les types de chaînes binaires et non binaires correspondants (BINARY et CHAR, VARBINARY et VARCHAR, BLOB et TEXT). La sortie utilise un type de données STRING pour les chaînes de longueur fixe et VARSTRING pour les chaînes de longueur variable.
•Pour les jeux de caractères multi-octets, le nombre maximum d'octets par caractère n'est pas présent dans le journal binaire, de sorte que la longueur des types de chaînes est affichée en octets plutôt qu'en caractères. Par exemple, STRING(4) sera utilisé comme type de données pour les valeurs des deux types de colonnes suivants : 
CHAR(4) CHARACTER SET latin1
CHAR(2) CHARACTER SET ucs2
•En raison du format de stockage des événements de type UPDATE_ROWS_EVENT, les instructions UPDATE sont affichées avec la clause WHERE précédant la clause SET.

L'interprétation correcte des événements de ligne nécessite les informations de l'événement de description de format au début du journal binaire. Comme mariadb-binlog ne sait pas à l'avance si le reste du journal contient des événements de ligne, il affiche par défaut l'événement de description de format à l'aide d'une instruction BINLOG dans la partie initiale de la sortie.

Si l'on sait que le journal binaire ne contient aucun événement nécessitant une instruction BINLOG (c'est-à-dire aucun événement de ligne), l'option --base64-output=NEVER peut être utilisée pour empêcher l'écriture de cet en-tête.
