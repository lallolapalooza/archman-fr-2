MQTT(7) Conventions et divers MQTT(7)

NOM

mqtt - MQ Telemetry Transport

SYNTAXE

MQTT

DESCRIPTION

MQTT est un protocole de messagerie léger de type publication/abonnement. Il est utile pour les capteurs à faible consommation d'énergie, mais applicable à de nombreux scénarios.

Ce manuel décrit certaines des fonctionnalités de MQTT version 3.1.1/3.1, pour aider les utilisateurs finaux à tirer le meilleur parti du protocole. Pour des informations plus complètes sur MQTT, consultez http://mqtt.org/.

PUBLICATION/ABONNEMENT

Le protocole MQTT est basé sur le principe de publication de messages et d'abonnement à des sujets, ou « pub/sub ». Plusieurs clients se connectent à un broker et s'abonnent aux sujets qui les intéressent. Les clients se connectent également au broker et publient des messages sur des sujets. De nombreux clients peuvent s'abonner aux mêmes sujets et utiliser les informations comme ils le souhaitent. Le broker et MQTT agissent comme une interface simple et commune pour que tout se connecte. Cela signifie que si vous avez des clients qui déversent les messages abonnés dans une base de données, sur Twitter, Cosm ou même un simple fichier texte, il devient très simple d'ajouter de nouveaux capteurs ou d'autres entrées de données à une base de données, Twitter ou similaire.

SUJETS/ABONNEMENTS

Les messages dans MQTT sont publiés sur des sujets. Il n'est pas nécessaire de configurer un sujet, la publication sur celui-ci suffit. Les sujets sont traités comme une hiérarchie, utilisant le slash (/) comme séparateur. Cela permet une organisation logique des thèmes courants, un peu comme un système de fichiers. Par exemple, plusieurs ordinateurs peuvent publier les informations de température de leur disque dur sur le sujet suivant, en remplaçant le nom de l'ordinateur et du disque dur appropriés :

•capteurs/NOM_ORDINATEUR/temperature/NOM_DISQUE_DUR

Les clients peuvent recevoir des messages en créant des abonnements. Un abonnement peut être à un sujet explicite, auquel cas seuls les messages sur ce sujet seront reçus, ou il peut inclure des caractères génériques. Deux caractères génériques sont disponibles : + ou #.

+ peut être utilisé comme caractère générique pour un seul niveau de hiérarchie. Il pourrait être utilisé avec le sujet ci-dessus pour obtenir des informations sur tous les ordinateurs et disques durs comme suit :

•capteurs/+/temperature/+

Autre exemple : pour un sujet « a/b/c/d », les abonnements suivants correspondent :

•a/b/c/d
•+/b/c/d
•a/+/c/d
•a/+/+/d
•+/+/+/+

Les abonnements suivants ne correspondent pas :

•a/b/c
•b/+/c/d
•+/+/+

# peut être utilisé comme caractère générique pour tous les niveaux restants de la hiérarchie. Cela signifie qu'il doit être le dernier caractère d'un abonnement. Avec un sujet « a/b/c/d », les abonnements suivants correspondent :

•a/b/c/d
•#
•a/#
•a/b/#
•a/b/c/#
•+/b/c/#

Les niveaux de sujet de longueur nulle sont valides, ce qui peut conduire à un comportement légèrement inhabituel. Par exemple, un sujet « a//topic » correspondra correctement à un abonnement « a/+/topic ». De même, des niveaux de sujet de longueur nulle peuvent exister au début et à la fin d'une chaîne de sujet, donc « /a/topic » correspondra à un abonnement « +/a/topic », « # » ou « /# », et un sujet « a/topic/ » correspondra à un abonnement « a/topic/+ » ou « a/topic/# ».

QUALITÉ DE SERVICE

MQTT définit trois niveaux de Qualité de Service (QoS). La QoS définit les efforts déployés par le broker/client pour garantir qu'un message est reçu. Les messages peuvent être envoyés à n'importe quel niveau de QoS, et les clients peuvent tenter de s'abonner à des sujets à n'importe quel niveau de QoS. Cela signifie que le client choisit la QoS maximale qu'il recevra. Par exemple, si un message est publié avec la QoS 2 et qu'un client est abonné avec la QoS 0, le message sera délivré à ce client avec la QoS 0. Si un deuxième client est également abonné au même sujet, mais avec la QoS 2, il recevra le même message mais avec la QoS 2. Autre exemple : si un client est abonné avec la QoS 2 et qu'un message est publié avec la QoS 0, le client le recevra avec la QoS 0.

Les niveaux de QoS plus élevés sont plus fiables, mais entraînent une latence plus élevée et des exigences de bande passante plus importantes.

•0 : Le broker/client délivre le message une fois, sans confirmation.
•1 : Le broker/client délivre le message au moins une fois, avec confirmation requise.
•2 : Le broker/client délivre le message exactement une fois en utilisant une poignée de main en quatre étapes.

MESSAGES CONSERVÉS

Tous les messages peuvent être marqués comme conservés. Cela signifie que le broker conservera le message même après l'avoir envoyé à tous les abonnés actuels. Si un nouvel abonnement est créé qui correspond au sujet du message conservé, alors le message sera envoyé au client. Ceci est utile comme mécanisme de « dernière bonne connaissance connue ». Si un sujet n'est mis à jour qu'inféquemment, sans message conservé, un client nouvellement abonné pourrait attendre longtemps pour recevoir une mise à jour. Avec un message conservé, le client recevra une mise à jour instantanée.

SESSION NETTE / CONNEXIONS DURABLES

Lors de la connexion, un client définit le drapeau « session nette », parfois également appelé drapeau « démarrage net ». Si la session nette est définie sur false, alors la connexion est traitée comme durable. Cela signifie que lorsque le client se déconnecte, tous les abonnements qu'il a restent et tous les messages QoS 1 ou 2 ultérieurs seront stockés jusqu'à ce qu'il se reconnecte à l'avenir. Si la session nette est vraie, alors tous les abonnements seront supprimés pour le client lorsqu'il se déconnecte.

WILLS

Lorsqu'un client se connecte à un broker, il peut informer le broker qu'il a un "will" (une volonté). Il s'agit d'un message que le broker doit envoyer lorsque le client se déconnecte de manière inattendue. Le message "will" a un sujet, une QoS et un statut de conservation, tout comme tout autre message.
