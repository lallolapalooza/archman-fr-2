NOM

mkisofs - créer une image de système de fichiers hybride ISO-9660/JOLIET/HFS/UDF avec attributs Rock Ridge optionnels.

SYNTAXE

mkisofs [ options ] [ -o nom_fichier ] spécification_chemin [spécification_chemin ...]
mkisofs [ options ] [ -o nom_fichier ] -find [expression find]

DESCRIPTION

mkisofs est effectivement un programme de pré-masterisation pour générer un système de fichiers hybride ISO-9660/JOLIET/HFS/UDF.

Les systèmes de fichiers ISO-9660/JOLIET/UDF sont limités à une taille maximale de 8 To. La taille maximale d'un seul fichier est de 8 To (les fichiers uniques en UDF sont actuellement limités à environ 200 Go). Si vous souhaitez avoir des fichiers de plus de 2 Go, vous devez spécifier -iso-level 3 ou supérieur. Si un hybride HFS est créé, la taille maximale de fichier pour les fichiers dans l'hybride HFS est de 2 Go dans tous les cas.

Support des systèmes de fichiers hybrides

mkisofs est capable de générer les enregistrements du protocole de partage d'utilisation du système (SUSP) spécifiés par le protocole d'échange Rock Ridge. Ceci est utilisé pour décrire plus en détail les fichiers dans le système de fichiers ISO-9660 pour un hôte UNIX, et fournit des informations telles que des noms de fichiers plus longs, uid/gid, permissions POSIX, liens symboliques, liens physiques, périphériques bloc et caractères.

Si des options de ligne de commande Joliet, HFS ou UDF sont spécifiées, mkisofs créera des métadonnées de système de fichiers supplémentaires séparées pour Joliet, HFS ou UDF. Le contenu du fichier dans ce cas fait référence aux mêmes blocs de données sur le média. Il générera un système de fichiers ISO-9660 pur sauf si les options de ligne de commande Joliet, HFS ou UDF sont données.

mkisofs peut générer un système de fichiers hybride HFS *vrai* (ou *partagé*). Les mêmes fichiers sont vus comme des fichiers HFS lorsqu'ils sont accédés depuis un Macintosh et comme des fichiers ISO-9660 lorsqu'ils sont accédés depuis d'autres machines. HFS signifie *Hierarchical File System* et est le système de fichiers natif utilisé sur les ordinateurs Macintosh jusqu'à Mac OS 9.

En alternative, mkisofs peut générer les *Extensions Apple pour ISO-9660* ou *UDF* pour chaque fichier. Ces extensions fournissent à chaque fichier des informations CREATOR, TYPE et certains indicateurs Finder lorsqu'ils sont accédés depuis un Macintosh. Voir la section FORMATS DE FICHIERS MACINTOSH HFS ci-dessous.

Description fonctionnelle

mkisofs prend une "instantané" d'une arborescence de répertoires donnée, et génère une image binaire qui correspondra à un système de fichiers ISO-9660 ou Joliet/HFS/UDF lorsqu'elle sera écrite sur un périphérique bloc.

Chaque fichier écrit dans le système de fichiers ISO-9660 doit avoir un nom de fichier au format 8.3 (8 caractères, point, 3 caractères, tous en majuscules), même si les attributs Rock Ridge sont utilisés. Ce nom de fichier est utilisé sur les systèmes qui ne sont pas capables d'utiliser les extensions Rock Ridge (comme MS-DOS), et chaque nom de fichier dans chaque répertoire doit être différent des autres noms de fichiers dans le même répertoire. mkisofs essaie généralement de former des noms corrects en forçant le nom de fichier UNIX en majuscules et en le tronquant si nécessaire, mais souvent cela donne des résultats insatisfaisants lorsqu'il y a des cas où les noms tronqués ne sont pas tous uniques. mkisofs attribue des pondérations à chaque nom de fichier, et si deux noms qui sont autrement identiques sont trouvés, le nom avec la priorité la plus basse est renommé pour avoir un nombre à 3 chiffres comme extension (où le nombre est garanti d'être unique). Un exemple de ceci serait les fichiers foo.bar et foo.bar.~1~ - le fichier foo.bar.~1~ serait écrit sous le nom FOO000.BAR;1 et le fichier foo.bar serait écrit sous le nom FOO.BAR;1

Lorsqu'il est utilisé avec diverses options HFS ou UDF, mkisofs tentera de reconnaître les fichiers stockés dans un certain nombre de formats de fichiers Apple/Unix et copiera les fourches de données et de ressources ainsi que toute information Finder pertinente. Voir la section FORMATS DE FICHIERS MACINTOSH HFS ci-dessous pour en savoir plus sur les formats pris en charge par mkisofs.

Notez que mkisofs n'est pas conçu pour communiquer directement avec les graveurs de médias optiques. La plupart des graveurs ont des ensembles de commandes propriétaires qui varient d'un fabricant à l'autre, et vous avez besoin d'un outil spécialisé comme cdrecord pour graver réellement le disque.

L'utilitaire cdrecord est un utilitaire capable de graver un disque réel. La dernière version de cdrecord est disponible sur https://sourceforge.net/projects/cdrtools/files/ ou https://sourceforge.net/projects/cdrtools/files/alpha/

Il faut également savoir que la plupart des graveurs de CD sont très exigeants en matière de synchronisation. Une fois que vous commencez à graver un disque, vous ne pouvez pas laisser leur tampon se vider avant d'avoir terminé, sinon vous vous retrouverez avec un disque corrompu. Il est donc essentiel que vous soyez en mesure de maintenir un flux de données ininterrompu vers le graveur pendant toute la durée de la gravure du disque.

Gestion des noms de chemin

spécification_chemin est le chemin de l'arborescence de répertoires à copier dans le système de fichiers ISO-9660. Plusieurs chemins peuvent être spécifiés, et mkisofs fusionnera les fichiers trouvés dans tous les composants de chemin spécifiés pour former l'image du CD-ROM.

Si l'option -graft-points a été spécifiée, il est possible de greffer les chemins à des points autres que le répertoire racine, et il est possible de greffer des fichiers ou des répertoires sur l'image du CD-ROM avec des noms différents de ceux qu'ils ont dans le système de fichiers source. Ceci est plus facile à illustrer avec quelques exemples. Commençons par supposer qu'un fichier local ../old.lis existe, et vous souhaitez l'inclure dans l'image du CD-ROM.

foo/bar/=../old.lis

inclura le fichier old.lis dans l'image du CD-ROM à /foo/bar/old.lis, tandis que

foo/bar/xxx=../old.lis

inclura le fichier old.lis dans l'image du CD-ROM sous le nom /foo/bar/xxx. Le même type de syntaxe peut être utilisé avec des répertoires. mkisofs créera tous les répertoires nécessaires afin que les points de greffe existent sur l'image du CD-ROM - les répertoires n'ont pas besoin d'apparaître dans l'un des chemins. Par défaut, tous les répertoires qui sont créés à la volée de cette manière auront des permissions 0555 et sembleront appartenir à la personne exécutant mkisofs. Si vous souhaitez d'autres permissions ou propriétaires pour les répertoires intermédiaires, voir -uid, -gid, -dir-mode, -file-mode et -new-dir-mode.

mkisofs fonctionnera également sur les machines Win9x/NTx lorsqu'il est compilé avec le cygwin de Cygnus (disponible à partir de http://sourceware.cygnus.com/cygwin/). Par conséquent, la plupart des références dans cette page de manuel à *Unix* s'appliquent également à *Win32* ou *Win64*.

OPTIONS

-abstract FICHIER
Spécifie le nom du fichier abstrait dans le descripteur de volume primaire. Il y a de la place sur le disque pour 37 caractères d'information. L'entrée Joliet associée est limitée à 18 caractères. Ce paramètre peut également être défini dans le fichier .mkisofsrc avec ABST=nom_fichier. S'il est spécifié aux deux endroits, la version en ligne de commande est utilisée.

Il appartient à l'utilisateur de mkisofs d'inclure un fichier avec le nom approprié dans l'arbre de fichiers créé.

-A id_application
-appid id_application
Spécifie une chaîne de caractères qui sera écrite dans l'en-tête du volume. Ceci devrait décrire l'application qui sera sur le disque. Il y a de la place sur le disque pour 128 caractères d'information. L'entrée Joliet associée est limitée à 64 caractères. Ce paramètre peut également être défini dans le fichier .mkisofsrc avec APPI=id. S'il est spécifié aux deux endroits, la version en ligne de commande est utilisée.
-allow-leading-dots
-ldots
Autorise les noms de fichiers ISO-9660 à commencer par un point. Habituellement, un point initial est remplacé par un trait de soulignement afin de maintenir la compatibilité MS-DOS.
Ceci viole la norme ISO-9660, mais fonctionne sur de nombreux systèmes. Utilisez avec prudence.
-allow-lowercase
Cette option autorise les caractères minuscules à apparaître dans les noms de fichiers ISO-9660.

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

Ceci enfreint la norme ISO-9660, mais fonctionne sur certains systèmes. Utiliser avec prudence.
-no-allow-lowercase
Ceci annule l'effet de -allow-lowercase et fonctionne même lorsque -U, -untranslated-filenames ou -iso-level 4 ont été utilisés pour autoriser les noms de fichiers en minuscules.
-allow-multidot
Cette option autorise la présence de plus d'un point dans les noms de fichiers ISO-9660. Un point de départ n'est pas affecté par cette option, il peut être autorisé séparément en utilisant l'option -allow-leading-dots.
Ceci enfreint la norme ISO-9660, mais fonctionne sur de nombreux systèmes. Utiliser avec prudence.
-biblio FICHIER
Spécifie le nom du fichier bibliographique dans le descripteur de volume primaire. Il y a de la place sur le disque pour 37 caractères d'information. L'entrée Joliet associée est limitée à 18 caractères. Ce paramètre peut également être défini dans le fichier .mkisofsrc avec BIBLO=nom_fichier. S'il est spécifié aux deux endroits, la version en ligne de commande est utilisée.

Il appartient à l'utilisateur de mkisofs d'inclure un fichier avec le nom approprié dans l'arborescence du système de fichiers créé.

-cache-inodes
Met en cache les numéros d'inode et de périphérique pour trouver les liens physiques vers les fichiers. Si mkisofs trouve un lien physique (un fichier avec plusieurs noms), le fichier n'apparaîtra qu'une seule fois sur le CD. Cela permet d'économiser de l'espace sur le CD. L'option -cache-inodes est activée par défaut sur les systèmes d'exploitation de type UNIX. Soyez prudent lors de l'utilisation de cette option sur un système de fichiers sans numéros d'inode uniques, car elle pourrait entraîner des fichiers contenant un contenu incorrect sur le CD.

Voir l'option -duplicates-once pour une méthode qui fonctionne sur les systèmes de fichiers sans numéros d'inode uniques.

Si les inodes ne sont pas mis en cache, mkisofs reviendra à l'ancienne version Rrip Version-1.10 (voir -rrip110) et mkisofs ne pourra pas créer de numéros d'inode corrects pour les fichiers de taille zéro.

-no-cache-inodes
Ne pas mettre en cache les numéros d'inode et de périphérique. Cette option est nécessaire lorsque un système de fichiers n'a pas de numéros d'inode uniques. C'est le comportement par défaut sur les anciennes versions de Cygwin. Comme le système d'exploitation Microsoft qui tourne sous Cygwin utilise des numéros d'inode de 64 bits pour NTFS, il n'a pas de numéros d'inode uniques dans la plage de 32 bits. Les anciennes versions de Cygwin créent de faux numéros d'inode de 32 bits à partir d'un algorithme de hachage et créent ainsi des numéros non uniques. Si mkisofs mettait en cache les inodes sur les anciennes versions de Cygwin, il croirait que certains fichiers sont identiques bien qu'ils ne le soient pas. Le résultat dans ce cas sont des fichiers qui contiennent un contenu incorrect si une quantité significative de fichiers différents (> ~5000) se trouve dans l'arborescence à archiver. Cela n'arrive pas lorsque l'option -no-cache-inodes est utilisée, mais le désavantage est que mkisofs ne peut plus détecter les liens physiques et l'image CD résultante peut être plus grande que prévu.

Si les inodes ne sont pas mis en cache, mkisofs reviendra à l'ancienne version Rrip Version-1.10 (voir -rrip110) et mkisofs ne pourra pas créer de numéros d'inode corrects pour les fichiers de taille zéro.

-duplicates-once
Indique à mkisofs d'utiliser une somme de contrôle de hachage de message pour identifier les fichiers identiques comme étant des fichiers apparemment liés physiquement. Cela permet à mkisofs d'archiver les numéros d'inode et les liens physiques même lorsqu'il est exécuté sur des plates-formes non POSIX comme DOS.
-b image_de_démarrage_eltorito
-eltorito-boot image_de_démarrage_eltorito
Spécifie le chemin et le nom de fichier de l'image de démarrage à utiliser lors de la création d'un CD de démarrage "El Torito". Le nom de chemin doit être relatif au chemin source et à l'intérieur de l'arborescence source spécifiée à mkisofs. Cette option est requise pour créer un CD de démarrage "El Torito". L'image de démarrage doit avoir exactement la taille d'une disquette de 1200, 1440 ou 2880 Ko, et mkisofs utilisera cette taille lors de la création du système de fichiers ISO-9660 de sortie. Il est supposé que le premier secteur de 512 octets doit être lu à partir de l'image de démarrage (il émule essentiellement un lecteur de disquette normal). Cela fonctionnera, par exemple, si l'image de démarrage est une disquette de démarrage.

Si l'image de démarrage n'est pas une image de disquette, vous devez ajouter l'une des options : -hard-disk-boot ou -no-emul-boot. Si le système ne doit pas démarrer sur le disque émulé, utilisez -no-boot.

Plus d'une entrée de démarrage peuvent être spécifiées, voir -eltorito-platform et -eltorito-alt-boot pour savoir comment spécifier plus d'entrées de démarrage. La première entrée de démarrage est l'entrée de démarrage par défaut. Les entrées de démarrage supplémentaires sont des membres d'une configuration de démarrage multiple.

Si l'option -sort n'a pas été spécifiée, les images de démarrage sont triées avec une priorité faible (+2) au début du support. Si cela ne vous convient pas, vous devez spécifier un poids de tri de 0 pour les images de démarrage.

-eltorito-alt-boot
Commence avec un nouvel ensemble de paramètres de démarrage "El Torito". Cela permet d'avoir plus d'une entrée de démarrage El Torito sur un CD. Un maximum de 63 entrées de démarrage El Torito peuvent être placées sur un seul CD.

L'option -eltorito-alt-boot démarre une nouvelle entrée de démarrage avec le même identifiant de plateforme mais sans nouvelle section de démarrage, sauf si elle apparaît après la première entrée de démarrage qui est l'entrée de démarrage par défaut.

-eltorito-platform id
Définit l'identifiant de plateforme "El Torito" pour un enregistrement de démarrage ou une section d'enregistrements de démarrage. Le paramètre id peut être l'un des éléments suivants :
x86
C'est la valeur id de plateforme par défaut et spécifie les entrées pour la plateforme PC. Si aucune option -eltorito-platform n'apparaît avant la première option -eltorito-boot, l'entrée de démarrage par défaut devient une entrée pour la plateforme PC x86.
PPC
Entrées de démarrage pour la plateforme Power PC.
Mac
Entrées de démarrage pour la plateforme Apple Mac.
efi
Entrées de démarrage pour les PC basés sur EFI.
#
Une valeur numérique spécifiant n'importe quel id de plateforme.

Si l'option -eltorito-platform apparaît avant la première option -eltorito-boot, elle définit l'id de plateforme pour l'entrée de démarrage par défaut.

Si l'option -eltorito-platform apparaît après une option -eltorito-boot et définit l'id de plateforme à une valeur différente de la valeur précédente, elle démarre un nouvel ensemble d'entrées de démarrage.

La deuxième entrée de démarrage et tout nouvel id de plateforme créent un nouvel en-tête de section et réduisent le nombre d'entrées de démarrage par CD de un.

errctl= nom
errctl= spécification_de_contrôle_des_erreurs
Ajoute le contenu du fichier nom aux définitions de contrôle des erreurs ou ajoute spécification_de_contrôle_des_erreurs aux définitions de contrôle des erreurs. Il est possible d'avoir plus d'un fichier de contrôle des erreurs et plus d'une spécification de contrôle des erreurs ainsi qu'un mélange des deux formes.

La raison de l'utilisation du contrôle des erreurs est de rendre mkisofs silencieux sur les conditions d'erreur connues pour être sans importance pour la qualité du système de fichiers créé, ou de demander à mkisofs d'avorter sur certaines conditions d'erreur au lieu d'essayer de continuer avec le système de fichiers.

Une raison typique d'utiliser le contrôle des erreurs est de supprimer les avertissements concernant les fichiers journaux en croissance lors d'une sauvegarde sur un système de fichiers actif. Une autre raison typique d'utiliser le contrôle des erreurs est de demander à mkisofs d'avorter si, par exemple, un fichier n'a pas pu être archivé au lieu de continuer à archiver d'autres fichiers d'une liste.

Le fichier de contrôle des erreurs contient un ensemble de lignes, chacune commençant par une liste de conditions d'erreur à ignorer, suivie d'un espace blanc, puis d'un modèle de nom de fichier (voir match(1) ou patmatch(3) pour plus d'informations). La spécification de contrôle des erreurs utilise la même syntaxe qu'une seule ligne du fichier de contrôle des erreurs. Si le modèle de nom de fichier doit commencer par un espace blanc, utilisez une barre oblique inverse pour échapper le début du nom de fichier. Il n'est pas possible d'avoir des caractères de nouvelle ligne dans le modèle de nom de fichier. Chaque fois qu'une situation d'erreur est rencontrée, mkisofs vérifie les lignes du fichier de contrôle des erreurs en commençant par le haut. Si la condition d'erreur actuelle est listée sur une ligne du fichier de contrôle des erreurs, alors mkisofs vérifie si le modèle sur le reste de la ligne correspond au nom de fichier actuel. Si c'est le cas, mkisofs utilise la spécification de contrôle des erreurs actuelle pour contrôler la condition d'erreur actuelle.

La liste des conditions d'erreur à traiter peut utiliser un ou plusieurs (dans ce cas séparés par un caractère '|') identifiants de la liste ci-dessous :

ABORT
Si cette méta-condition est incluse dans une condition d'erreur, mkisofs avorte (se termine) dès que possible après avoir vu cette condition d'erreur au lieu de rendre mkisofs silencieux sur la condition. Ce drapeau de condition d'erreur ne peut être utilisé qu'avec une autre condition d'erreur ou une liste de conditions d'erreur (séparées par un caractère '|').
WARN
Si cette méta-condition est incluse dans une condition d'erreur, mkisofs affiche l'avertissement concernant la condition d'erreur, mais la condition d'erreur n'affecte pas le code de sortie de mkisofs et les statistiques d'erreur (qui sont affichées à la fin) n'incluent pas les erreurs associées. Ce drapeau de condition d'erreur ne peut être utilisé qu'avec une autre condition d'erreur ou une liste de conditions d'erreur (séparées par un caractère '|'). La méta-condition WARN a une priorité inférieure à ABORT.
ALL
C'est un raccourci pour toutes les conditions d'erreur ci-dessous.
STAT
Supprimer les avertissements indiquant que mkisofs n'a pas pu stat(2) un fichier.
GETACL
Supprimer les avertissements concernant
ACL
Supprimer les avertissements concernant les fichiers pour lesquels mkisofs a eu des problèmes pour récupérer les informations ACL.
OPEN
Supprimer les avertissements concernant les fichiers qui n'ont pas pu être ouverts.
READ
Supprimer les avertissements concernant les erreurs de lecture sur les fichiers.
WRITE
Supprimer les avertissements concernant les erreurs d'écriture sur les fichiers.
READLINK
Supprimer les avertissements concernant les erreurs de readlink(2) sur les liens symboliques.
GROW
Supprimer les avertissements concernant les fichiers qui ont grandi pendant qu'ils étaient archivés.
SHRINK
Supprimer les avertissements concernant les fichiers qui ont diminué pendant qu'ils étaient archivés.
MISSLINK
Supprimer les avertissements concernant les fichiers pour lesquels mkisofs n'a pas pu archiver tous les liens physiques.
NAMETOOLONG
Supprimer les avertissements concernant les fichiers qui n'ont pas pu être archivés car le nom du fichier est trop long pour le format d'archive.
FILETOOBIG
Supprimer les avertissements concernant les fichiers qui n'ont pas pu être archivés car la taille du fichier est trop grande pour le format d'archive.
SPECIALFILE
Supprimer les avertissements concernant les fichiers qui n'ont pas pu être archivés car le type de fichier n'est pas supporté par le format d'archive.
GETXATTR
Supprimer les avertissements concernant les fichiers pour lesquels mkisofs n'a pas pu récupérer les informations des attributs étendus du fichier.
SETTIME
Supprimer les avertissements concernant les fichiers pour lesquels mkisofs n'a pas pu définir les informations de temps pendant l'extraction.
SETMODE
Supprimer les avertissements concernant les fichiers pour lesquels mkisofs n'a pas pu définir les modes d'accès pendant l'extraction.
SECURITY
Supprimer les avertissements concernant les fichiers qui ont été ignorés lors de l'extraction car ils étaient considérés comme présentant un risque de sécurité. Cela s'applique actuellement à tous les fichiers contenant une séquence '/../' lorsque -.. n'a pas été spécifié.
LSECURITY
Supprimer les avertissements concernant les liens qui ont été ignorés lors de l'extraction car ils étaient considérés comme présentant un risque de sécurité. Cela s'applique actuellement à tous les noms de liens commençant par '/' ou contenant une séquence '/../' lorsque -secure-links a été spécifié. Dans ce cas, mkisofs tente de faire correspondre le nom du lien avec le modèle dans le fichier de contrôle des erreurs.
SAMEFILE
Supprimer les avertissements concernant les liens qui ont été ignorés lors de l'extraction car la source et la cible du lien pointent vers le même fichier. Si mkisofs ne sautait pas ces fichiers, il finirait par supprimer complètement le fichier. Dans ce cas, mkisofs tente de faire correspondre le nom du lien avec le modèle dans le fichier de contrôle des erreurs.
BADACL
Supprimer les avertissements concernant les problèmes de conversion de la liste de contrôle d'accès.
SETACL
Supprimer les avertissements concernant les fichiers pour lesquels mkisofs n'a pas pu définir les informations ACL pendant l'extraction.
SETXATTR
Supprimer les avertissements concernant les fichiers pour lesquels mkisofs n'a pas pu définir les informations des attributs étendus du fichier pendant l'extraction.

Si une condition d'erreur spécifique est ignorée, la condition d'erreur est non seulement traitée de manière silencieuse, mais également exclue des statistiques d'erreur qui sont imprimées à la fin de l'exécution de mkisofs.

Soyez très prudent lorsque vous utilisez le contrôle d'erreurs, car vous pouvez ignorer toute condition d'erreur. Si vous ignorez les mauvaises conditions d'erreur, vous pourriez ne plus voir les vrais problèmes.

Notez qu'actuellement, seuls les balises OPEN, READ, GROW, SHRINK sont vérifiées par mkisofs.

-B img_sun4,img_sun4c,img_sun4m,img_sun4d,img_sun4e
-sparc-boot img_sun4,img_sun4c,img_sun4m,img_sun4d,img_sun4e
Spécifie une liste d'images de démarrage séparées par des virgules, nécessaires pour créer un CD amorçable pour les systèmes sparc. La partition 0 est utilisée pour l'image ISO-9660, la première image de fichier est mappée sur la partition 1. Il peut y avoir des champs vides dans la liste séparée par des virgules. Le nombre maximum de partitions possibles est de 8, il est donc impossible de spécifier plus de 7 images de partition. Cette option est requise pour créer un CD amorçable pour les systèmes Sun sparc. Si l'option -B ou -sparc-boot a été spécifiée, le premier secteur de l'image résultante contiendra une étiquette de disque Sun. Cette étiquette de disque spécifie la tranche 0 pour l'image ISO-9660 et les tranches 1 à 7 pour les images de démarrage spécifiées avec cette option. L'octet 512 à 8191 de chacune des images de démarrage supplémentaires doit contenir un amorçage primaire qui fonctionne pour l'architecture sparc appropriée. Le reste de chacune des images contient généralement un système de fichiers ufs qui constitue la première étape de l'amorçage du noyau.

La méthode de démarrage implémentée est celle trouvée avec SunOS 4.x et SunOS 5.x. Cependant, elle ne dépend pas des détails internes de SunOS, mais uniquement des propriétés de l'Open Boot prom. Pour cette raison, elle devrait être utilisable pour tout OS qui démarre sur un système sparc.

Définit la date de modification dans le descripteur de volume primaire (PVD) à une valeur différente de l'heure actuelle. Ceci permet par exemple de configurer un UUID intentionnel pour grub.

Le format de date-spec est :

yyyy[mm[dd[hh[mm[ss]]]]][.hh][+-ghgm]

Les champs sont année, mois, jour du mois, heure, minute, seconde, centaines de seconde, décalage GMT en heures et minutes. L'heure est interprétée comme l'heure locale.

L'année et le décalage GMT sont des champs à quatre chiffres, tous les autres champs prennent deux chiffres. Le décalage GMT peut être compris entre -12 et +13 heures par pas de 15 minutes. Les emplacements à l'est de Greenwich ont des valeurs positives. La valeur est la somme du décalage du fuseau horaire et des effets de l'heure d'été. Les valeurs omises sont remplacées par les valeurs minimales possibles. Si le décalage GMT est omis, il est calculé à partir de la valeur de l'heure locale qui a été fournie.

entre le mois et le jour de mois, un séparateur choisi parmi '/' et '-' peut apparaître. -pad
Rembourrer la fin de l'image entière par 150 secteurs (300 Ko). Le rembourrage est nécessaire car de nombreux systèmes d'exploitation (par exemple, Linux) implémentent des bugs de lecture anticipée dans leur I/O de système de fichiers. L'option -print-size permet d'obtenir cette taille lors d'un "dry-run" avant que le CD ne soit réellement gravé. Les anciennes versions de mkisofs écrivaient ces informations (entre autres) sur *stderr*. Comme cela s'avère difficile à analyser, le nombre sans aucune autre information est maintenant également imprimé sur stdout. Si vous souhaitez écrire un script shell simple, redirigez stderr et capturez le nombre depuis stdout. Ceci peut être fait avec :

cdblocks=` mkisofs -print-size -quiet ... `

-rock
Générer des enregistrements SUSP et RR en utilisant le protocole Rock Ridge pour décrire davantage les fichiers sur le système de fichiers ISO-9660. Le protocole Rock Ridge est nécessaire pour ajouter des métadonnées de fichiers de type POSIX telles que les permissions, les horodatages étendus, les IDs utilisateur/groupe, les nombres de liens, les numéros d'inode et les liens symboliques. Le protocole Rock Ridge permet d'archiver des arbres hiérarchiques de profondeur illimitée.
-r
-rational-rock
C'est comme l'option -R, mais la propriété et les modes des fichiers sont réglés sur des valeurs plus utiles. L'uid et le gid sont mis à zéro, car ils sont généralement utiles uniquement sur le système de l'auteur, et non sur le client. Tous les bits de lecture des fichiers sont mis à vrai, de sorte que les fichiers et les répertoires soient lisibles globalement sur le client. Si un bit d'exécution est défini pour un fichier, tous les bits d'exécution sont définis, de sorte que les exécutables soient globalement exécutables sur le client. Si un bit de recherche est défini pour un répertoire, tous les bits de recherche sont définis, de sorte que les répertoires soient globalement accessibles en recherche sur le client. Tous les bits d'écriture sont effacés, car le CD-Rom sera monté en lecture seule dans tous les cas. Si des bits de mode spéciaux sont définis, ils sont effacés, car les verrous de fichiers ne sont pas utiles sur un système de fichiers en lecture seule, et les bits set-id ne sont pas souhaitables pour uid 0 ou gid 0. Lorsqu'il est utilisé sous Win32, le bit d'exécution est défini sur *tous* les fichiers. Ceci est le résultat du manque de permissions de fichiers sous Win32 et de la couche d'émulation POSIX Cygwin. Voir aussi -uid, -gid, -dir-mode, -file-mode et -new-dir-mode.

-old-root dir
Cette option est nécessaire lors de l'écriture d'une image multisession et que la session précédente (ou plus ancienne) a été écrite avec -root dir. L'utilisation d'un nom de répertoire introuvable dans la session précédente provoque l'arrêt de mkisofs avec une erreur.

Sans cette option, mkisofs ne serait pas en mesure de trouver les fichiers non modifiés et serait obligé de réécrire leurs données dans l'image une fois de plus.

-root et -old-root sont destinés à être utilisés ensemble pour effectuer des sauvegardes incrémentielles. La session initiale utiliserait par exemple : mkisofs -root backup_1 dirs. La sauvegarde incrémentielle suivante avec mkisofs -root backup_2 -old-root backup_1 dirs. prendrait un autre instantané de ces répertoires. Le premier instantané serait trouvé dans backup_1, le second dans backup_2, mais seuls les fichiers modifiés ou nouveaux devraient être écrits dans la seconde session.

Sans ces options, de nouveaux fichiers seraient ajoutés et les anciens seraient conservés. Mais les anciens seraient écrasés si le fichier était modifié. La récupération des fichiers en copiant l'ensemble du répertoire depuis le CD restaurerait également les fichiers qui ont été intentionnellement supprimés. L'accès à plusieurs anciennes versions d'un fichier nécessite le support du système d'exploitation pour choisir quelles sessions doivent être montées.

Trie les emplacements des fichiers sur le média. Le tri est contrôlé par un fichier qui contient des paires de noms de fichiers et de pondérations de décalage de tri. Si la pondération est plus élevée, le fichier sera situé plus près du début du média, si la pondération est plus basse, le fichier sera situé plus près de la fin du média. Il ne doit y avoir qu'un seul espace ou tabulation entre le nom du fichier et le poids, et le poids doit être les derniers caractères d'une ligne. Le nom du fichier est considéré comme incluant tous les caractères jusqu'au dernier espace ou tabulation inclus, mais pas le caractère lui-même. Spécifie une liste d'images de systèmes de fichiers séparées par des virgules nécessaires pour créer un CD bootable pour les systèmes Solaris x86.

Notez que la partition 1 est utilisée pour l'image ISO-9660 et que la partition 2 est le disque entier, donc les partitions 1 et 2 ne peuvent pas être utilisées par des données de partition externes. JEUX DE CARACTÈRES

mkisofs traite les noms de fichiers d'une manière conforme à POSIX comme des chaînes de caractères 8 bits. Pour représenter tous les codages de toutes les langues, les caractères 8 bits ne suffisent pas. Unicode ou ISO-10646 définissent des codages de caractères qui nécessitent au moins 21 bits pour représenter toutes les langues connues. Ils peuvent être représentés avec un codage UTF-32, UTF-16 ou UTF-8. UTF-32 utilise un codage 32 bits simple mais semble être peu courant. UCS-2 est utilisé par Microsoft avec Win32. Ce codage est similaire à UTF-16 avec le désavantage qu'il ne prend en charge qu'un sous-ensemble de 16 bits (sauf lorsque des surrogates sont utilisés) de tous les codes et que les caractères 16 bits ne sont pas conformes à l'interface de système de fichiers POSIX.

Les systèmes d'exploitation UNIX modernes peuvent utiliser le codage UTF-8 pour les noms de fichiers. Ce codage permet d'utiliser l'ensemble complet des codes Unicode. Chaque caractère 32 bits est représenté par un ou plusieurs caractères 8 bits. Si un caractère est codé en ISO-8859-1 (utilisé en Europe centrale et en Amérique du Nord), il est mappé 1:1 à un caractère Unicode codé en UTF-32 ou UTF-16. Si un caractère est codé en ASCII 7 bits (utilisé aux États-Unis et dans d'autres pays avec un jeu de caractères limité), il est mappé 1:1 à un caractère Unicode codé en UTF-32, UTF-16 ou UTF-8. Les codes de caractères qui ne peuvent pas être représentés comme un seul octet en UTF-8 (typiquement si la valeur est supérieure à 0x7F) utilisent des séquences d'échappement qui correspondent à plus d'un caractère 8 bits.

Si tous les systèmes d'exploitation utilisaient le codage UTF-8, mkisofs n'aurait pas besoin de recoder les caractères dans les noms de fichiers. Malheureusement, Apple utilise des codages complètement non standard et Microsoft utilise un codage Unicode incompatible avec l'interface de nom de fichier POSIX.

Pour tous les systèmes d'exploitation non codés en UTF-8, le caractère réel que chaque octet représente dépend du jeu de caractères ou de la page de codes (qui est le nom utilisé par Microsoft) utilisé par le système d'exploitation local en cours d'utilisation - les caractères d'un jeu de caractères refléteront la région ou la langue naturelle utilisée par l'utilisateur.

Généralement, les codes de caractères 0x00-0x1f sont des caractères de contrôle, les codes 0x20-0x7f sont les caractères ASCII 7 bits et (sur les PC et Mac) 0x80-0xff sont utilisés pour d'autres caractères. Malheureusement, même cela ne suit pas les normes ISO qui réservent la plage 0x80-0x9f aux caractères de contrôle et n'autorisent que 0xa0-0xff pour d'autres caractères.

Comme il y a beaucoup plus de 256 caractères/symboles utilisés, seul un petit sous-ensemble est représenté dans un jeu de caractères. Par conséquent, le même code de caractère peut représenter un caractère différent dans différents jeux de caractères. Ainsi, un nom de fichier généré, disons en Europe centrale, peut ne pas afficher le même caractère lorsqu'il est consulté sur une machine dans, disons, l'Europe de l'Est.

Pour compliquer les choses, différents systèmes d'exploitation utilisent différents jeux de caractères pour la région ou la langue. Par exemple, le code de caractère pour "petit e avec accent aigu" peut être le code de caractère 0x82 sur un PC, le code 0x8e sur un Macintosh et le code 0xe9 sur un système UNIX. Notez que bien que les codages utilisés sur un PC ou un Mac ne soient pas standard, Unicode code ce caractère comme 0x00000000e9, ce qui est essentiellement la même valeur que celle utilisée par la plupart des systèmes UNIX.

Tant que tous les systèmes d'exploitation et applications n'utiliseront pas le jeu de caractères Unicode comme base pour les noms de fichiers d'une manière unique, il peut être nécessaire de spécifier le jeu de caractères que vos noms de fichiers utilisent et le jeu de caractères sous lequel les noms de fichiers doivent apparaître sur le CD.

Il existe quatre options pour spécifier les jeux de caractères que vous souhaitez utiliser :

-input-charset
Définit le jeu de caractères local que vous utilisez sur votre machine hôte. Toutes les conversions de jeu de caractères qui ont lieu utiliseront ce jeu de caractères comme point de départ. Les jeux de caractères d'entrée par défaut sont cp437 sur les systèmes basés sur DOS et iso8859-1 sur tous les autres systèmes.

Si l'option -J est donnée, alors les équivalents Unicode du jeu de caractères d'entrée seront utilisés dans le répertoire Joliet. L'utilisation de l'option -jcharset est identique à l'utilisation des options -input-charset et -J.

-output-charset
Définit le jeu de caractères qui sera utilisé pour les noms Rock Ridge sur le CD. Par défaut, le jeu de caractères d'entrée. Seulement susceptible d'être utile s'il est utilisé sur une plateforme non Unix. Par exemple, utiliser mkisofs sur une machine Microsoft Win32 pour créer des CD Rock Ridge. Si vous utilisez mkisofs sur une machine Unix, il est probable que le jeu de caractères de sortie sera le même que le jeu de caractères d'entrée.
-input-hfs-charset
Définit le jeu de caractères HFS utilisé pour les noms de fichiers HFS décodés à partir de l'un des différents formats de fichiers Apple/Unix. Uniquement utile lorsqu'il est utilisé avec l'option -mac-name. Voir la section NOMS DE FICHIERS MACINTOSH HFS pour plus d'informations. Par défaut, cp10000 (Mac Roman).
-output-hfs-charset
Définit le jeu de caractères HFS utilisé pour créer les noms de fichiers HFS à partir du jeu de caractères d'entrée en cours d'utilisation. Dans la plupart des cas, t
Cette option sera extraite du jeu de caractères fourni avec l'option -input-charset. Par défaut, le jeu de caractères d'entrée HFS.

Le jeu de caractères par défaut est intégré à mkisofs. Un certain nombre d'autres jeux de caractères sont lus à partir du système de fichiers par mkisofs à partir d'un répertoire relatif au chemin d'installation. Pour obtenir une liste, utilisez mkisofs -input-charset help.

Des jeux de caractères supplémentaires d'iconv(1) peuvent être utilisés sur les systèmes qui prennent en charge iconv(1). Dans ce cas, appelez iconv -l pour obtenir une liste des jeux de caractères valides pour cette méthode de codage. Pour forcer un codage basé sur iconv(1), utilisez iconv:nom au lieu de nom pour le jeu de caractères.

Si vous utilisez des jeux de caractères non basés sur iconv(1), des jeux de caractères supplémentaires peuvent être lus à partir d'un fichier pour n'importe laquelle des options de jeu de caractères en donnant un nom de fichier comme argument aux options. Un jeu de caractères donné sera lu à partir d'un fichier chaque fois que le nom fourni contient un '/'.

Le format des fichiers de jeu de caractères est le même que celui des fichiers de mappage disponibles sur http://www.unicode.org/Public/MAPPINGS Le format de ces fichiers est le suivant :

La colonne n° 1 est le code octet d'entrée (en hexadécimal comme 0xXX)
La colonne n° 2 est l'Unicode (en hexadécimal comme 0xXXXX)
Le reste de la ligne est ignoré.

Toute ligne vide, ligne sans deux (ou plus) colonnes dans le format ci-dessus ou lignes de commentaire (commençant par le caractère #) sont ignorées sans aucun avertissement. Tout code d'entrée manquant est mappé au caractère Unicode 0x0000.

Notez qu'il n'y a pas de prise en charge pour l'UNICODE 16 bits (UTF-16) ou l'UNICODE 32 bits (UTF-32) car ce codage n'est pas conforme POSIX. Il devrait y avoir une prise en charge pour le codage UNICODE UTF-8, qui est compatible avec les noms de fichiers POSIX et pris en charge par les implémentations UNIX modernes comme Solaris.

Un mappage de jeu de caractères 1:1 peut être défini en utilisant le mot-clé default comme argument pour l'une des options de jeu de caractères. C'est le comportement des anciennes versions (v1.12) de mkisofs.

Les noms de fichiers ISO-9660 générés à partir des noms de fichiers d'entrée ne sont pas convertis à partir du jeu de caractères d'entrée. Le jeu de caractères ISO-9660 est un sous-ensemble très limité des caractères ASCII, donc toute conversion serait inutile.

Tout caractère que mkisofs ne peut pas convertir sera remplacé par un caractère '_'.

HFS CRÉATEUR/TYPE

Un fichier Macintosh possède deux propriétés associées qui définissent quelle application a créé le fichier, le CRÉATEUR, et quel type de données le fichier contient, le TYPE. Les deux sont des chaînes de (exactement) 4 lettres. Habituellement, cela permet à un utilisateur Macintosh de double-cliquer sur un fichier et de lancer l'application correcte, etc. Le CRÉATEUR et le TYPE d'un fichier particulier peuvent être trouvés en utilisant quelque chose comme ResEdit (ou similaire) sur un Macintosh.

Les informations de CRÉATEUR et de TYPE sont stockées dans tous les divers fichiers codés Apple/Unix. Pour d'autres fichiers, il est possible de baser le CRÉATEUR et le TYPE sur l'extension du nom de fichier en utilisant un fichier de mappage (l'option -map) et/ou en utilisant le nombre magique (généralement une signature dans les premiers octets) d'un fichier (l'option -magic). Si ces deux options sont données, leur ordre sur la ligne de commande est important. Si l'option -map est donnée en premier, une correspondance d'extension de nom de fichier est tentée avant une correspondance de nombre magique. Cependant, si l'option -magic est donnée en premier, une correspondance de nombre magique est tentée avant une correspondance d'extension de nom de fichier.

Si un fichier de mappage ou magique n'est pas utilisé, ou si aucune correspondance n'est trouvée, alors le CRÉATEUR et le TYPE par défaut pour tous les fichiers réguliers peuvent être définis en utilisant des entrées dans le fichier .mkisofsrc ou en utilisant les options -hfs-creator et/ou -hfs-type, sinon le CRÉATEUR et le TYPE par défaut sont 'unix' et 'TEXT'.

Le format du fichier de mappage est le même format afpfile qu'utilisé par aufs. Ce fichier a cinq colonnes pour l'*extension*, la *traduction* du fichier, le *CRÉATEUR*, le *TYPE* et le *Commentaire*. Les lignes commençant par le caractère '#' sont des lignes de commentaire et sont ignorées. Un exemple de fichier ressemblerait à ceci :

# Exemple de fichier de mappage de noms de fichiers
#
# EXT XLate CREATEUR TYPE Commentaire
.tif Raw '8BIM' 'TIFF' "Image TIFF Photoshop"
.hqx Ascii 'BnHq' 'TEXT' "Fichier BinHex"
.doc Raw 'MSWD' 'WDBN' "Fichier Word"
.mov Raw 'TVOD' 'MooV' "Film QuickTime"
* Ascii 'ttxt' 'TEXT' "Fichier texte"

Où :

La première colonne EXT définit l'extension du nom de fichier Unix à mapper. Le mappage par défaut pour toute extension de nom de fichier qui ne correspond pas est défini avec le caractère "*".
La colonne XLate définit le type de traduction de texte entre le fichier Unix et le fichier Macintosh ; elle est ignorée par mkisofs, mais conservée pour être compatible avec aufs(1). Bien que mkisofs ne modifie pas le contenu d'un fichier, si un fichier binaire a son TYPE défini comme 'TEXT', il peut être lu de manière incorrecte sur un Macintosh. Par conséquent, un meilleur choix pour le TYPE par défaut pourrait être '????'
Les mots-clés CRÉATEUR et TYPE doivent avoir 4 caractères et être entourés de guillemets simples.
Le champ commentaire est entouré de guillemets doubles ; il est ignoré par mkisofs, mais conservé pour être compatible avec aufs.

Le format du fichier magique est presque identique au fichier magic(4) utilisé par la commande file(1) de Linux ; les routines de lecture et de décodage du fichier magique sont basées sur la commande file(1) de Linux.

Ce fichier a quatre colonnes séparées par des tabulations pour le *décalage d'octet*, le *type*, le *test* et le *message*. Les lignes commençant par le caractère '#' sont des lignes de commentaire et sont ignorées. Un exemple de fichier ressemblerait à ceci :

# Exemple de fichier magique
#
# off type test message
0 string GIF8 8BIM GIFf image GIF
0 beshort 0xffd8 8BIM données d'image JPEG
0 string SIT! SIT! SIT! Archive StuffIt
0 string \037\235 compression unix standard LZIV ZIVU
0 string \037\213 données compressées gzip GNUz ZIVU
0 string %! ASPS TEXT Postscript
0 string \004%! ASPS TEXT Postscript PC avec un ^D pour commencer
4 string moov txtt MooV fichier film QuickTime (moov)
4 string mdat txtt MooV fichier film QuickTime (mdat)

Le format du fichier est décrit dans la page de manuel magic(4). La seule différence ici est que pour chaque entrée dans le fichier magique, le *message* pour le décalage initial doit être de 4 caractères pour le CRÉATEUR suivis de 4 caractères pour le TYPE ; les espaces blancs sont facultatifs entre eux. Tous les autres caractères sur cette ligne sont ignorés. Les lignes de continuation (commençant par un '>') sont également ignorées, c'est-à-dire que seules les lignes de décalage initial sont utilisées.

L'utilisation de l'option -magic peut augmenter considérablement le temps de traitement car chaque fichier doit être ouvert et lu pour trouver son nombre magique.

En résumé, pour tous les fichiers, le CRÉATEUR par défaut est 'unix' et le TYPE par défaut est 'TEXT'. Ceux-ci peuvent être modifiés en utilisant des entrées dans le fichier .mkisofsrc ou en utilisant les options -hfs-creator et/ou -hfs-type.

Si un fichier est dans l'un des formats Apple/Unix connus (et que le format a été sélectionné), alors le CRÉATEUR et le TYPE sont pris des valeurs stockées dans le fichier Apple/Unix.

D'autres fichiers peuvent avoir leur CRÉATEUR et TYPE définis à partir de leur extension de nom de fichier (l'option -map), ou de leur nombre magique (l'option -magic). Si la correspondance par défaut est utilisée dans le fichier de mappage, alors ces valeurs remplacent le CRÉATEUR et TYPE par défaut.

Une base de données complète des CRÉATEUR/TYPE peut être trouvée sur http://www.angelfire.com/il/szekely/index.html

FORMATS DE FICHIERS HFS MACINTOSH

Les fichiers Macintosh ont deux parties appelées le fork Données et le fork Ressource. L'un ou l'autre peut être vide. Unix (et de nombreux autres OS) ne peut gérer que des fichiers ayant une seule partie (ou fork). Pour ajouter à cela, les fichiers Macintosh ont un certain nombre d'attributs associés ; les plus importants sont probablement le TYPE et le CRÉATEUR. Encore une fois, Unix n'a pas de concept pour ces types d'attributs.

par exemple, un fichier Macintosh peut être une image JPEG où l'image est stockée dans le fork de données et une miniature de bureau stockée dans le fork de ressource. C'est généralement l'information dans le fork de données qui est utile sur plusieurs plateformes.

Par conséquent, pour stocker un fichier Macintosh sur un système de fichiers Unix, une méthode doit être trouvée pour gérer les deux forks et les attributs supplémentaires (qui sont désignés comme les informations du finder). Malheureusement, il semble que chaque paquet logiciel qui stocke des fichiers Macintosh sur Unix ait choisi une méthode de stockage complètement différente.

Les formats Apple/Unix que mkisofs prend en charge (partiellement) sont :

Format CAP AUFS
Fork de données stocké dans un fichier. Fork de ressource dans le sous-répertoire .resource avec le même nom de fichier que le fork de données. Informations du finder dans le sous-répertoire .finderinfo avec le même nom de fichier.
AppleDouble/Netatalk
Fork de données stocké dans un fichier. Fork de ressource stocké dans un fichier avec le même nom préfixé par "%". Informations du finder également stockées dans le même fichier "%". Netatalk utilise le même
format, mais la ressource fork/finderinfo stockée dans le sous-répertoire .AppleDouble avec le même nom que la data fork.
AppleSingle
Structures de données similaires à ci-dessus, sauf que les deux fourches et les informations du Finder sont stockées dans un seul fichier.
Helios EtherShare
Data fork stockée dans un fichier. Resource fork et finder info ensemble dans le sous-répertoire .rsrc avec le même nom de fichier que la data fork.
IPT UShare
Très similaire au format EtherShare, mais les informations du Finder sont stockées différemment.
MacBinary
Les deux fourches et les informations du Finder sont stockées dans un seul fichier.
Apple PC Exchange
Utilisé par les Macintosh pour stocker des fichiers Apple sur des disques DOS (FAT). La data fork est stockée dans un fichier. La resource fork dans le sous-répertoire resource.frk (ou RESOURCE.FRK). Les informations du Finder comme un enregistrement dans le fichier finder.dat (ou FINDER.DAT). Un finder.dat séparé pour chaque répertoire de la data fork.
Note : mkisofs doit connaître la taille de cluster FAT native du disque sur lequel se trouvent (ou ont été copiés) les fichiers PC Exchange. Cette taille est donnée par l'option -cluster-size. La taille du cluster ou d'allocation peut être trouvée en utilisant l'utilitaire DOS CHKDSK.
Peut ne pas fonctionner avec les fichiers PC Exchange v2.2 ou supérieurs (disponibles avec MacOS 8.1). Les supports DOS contenant des fichiers PC Exchange doivent être montés en tant que type msdos (pas vfat) lors de l'utilisation de Linux.
SGI/XINET
Utilisé par les machines SGI lorsqu'elles montent des disques HFS. La data fork est stockée dans un fichier. La resource fork dans le sous-répertoire .HSResource avec le même nom. Les informations du Finder comme un enregistrement dans le fichier .HSancillary. Un .HSancillary séparé pour chaque répertoire de la data fork.
Thursby Software Systems DAVE
Permet aux Macintosh de stocker des fichiers Apple sur des serveurs SMB. La data fork est stockée dans un fichier. La resource fork dans le sous-répertoire resource.frk. Utilise le format AppleDouble pour stocker la resource fork.
Services pour Macintosh
Format des fichiers stockés par les serveurs NT sur les systèmes de fichiers NTFS. La data fork est stockée sous le nom de "nom_fichier". La resource fork est stockée sous forme d'un flux NTFS nommé "nom_fichier:AFP_Resource". Les informations du Finder sont stockées sous forme d'un flux NTFS nommé "nom_fichier:Afp_AfpInfo". Ces flux sont normalement invisibles pour l'utilisateur.
Attention : mkisofs ne prend en charge que partiellement le format SFM. Si un fichier ou dossier HFS stocké sur le serveur NT contient un caractère illégal pour NT dans son nom, alors NT convertit ces caractères en caractères Unicode à usage privé. Les caractères sont : " * / < > ?  | ainsi qu'un espace ou un point s'il s'agit du dernier caractère du nom de fichier, codes de caractère 0x01 à 0x1f (caractères de contrôle) et le logo pomme d'Apple.
Malheureusement, ces caractères Unicode privés ne sont pas lisibles par l'exécutable NT de mkisofs. Par conséquent, tout nom de fichier ou répertoire contenant ces caractères sera ignoré - y compris le contenu de tout répertoire de ce type.
MacOS X AppleDouble
Lorsque les fichiers HFS/HFS+ sont copiés ou enregistrés par MacOS X sur un système de fichiers non-HFS (par exemple, UFS, NFS, etc.), les fichiers sont stockés au format AppleDouble. La data fork est stockée dans un fichier. La resource fork est stockée dans un fichier portant le même nom, précédé de "._". Les informations du Finder sont également stockées dans le même fichier "._".
MacOS X HFS (Alpha)
Pas vraiment un encodage Apple/Unix, mais des fichiers HFS/HFS+ réels sur un système MacOS X. La data fork est stockée dans un fichier. La resource fork est stockée dans un pseudo-fichier portant le même nom avec le suffixe '/rsrc'. Les finderinfo ne sont disponibles que via un appel de bibliothèque MacOS X.
Notes : (voir également README.macosx)
Ne fonctionne que lorsqu'il est utilisé sur MacOS X.
Si un fichier est trouvé avec une resource fork de longueur nulle et des finderinfo vides, il est supposé ne pas avoir d'encodage Apple/Unix - par conséquent, un TYPE et un CREATOR peuvent être définis par d'autres méthodes.

mkisofs tentera de définir le CREATOR, le TYPE, la date et éventuellement d'autres indicateurs à partir des informations du Finder. De plus, si elle existe, le nom de fichier Macintosh est défini à partir des informations du Finder, sinon le nom Macintosh est basé sur le nom Unix - voir la section NOMS DE FICHIERS MACINTOSH HFS ci-dessous.

Lors de l'utilisation de l'option -apple, le TYPE et le CREATOR sont stockés dans le champ facultatif System Use ou SUSP dans l'enregistrement du répertoire ISO-9660 - de la même manière que les attributs Rock Ridge. En fait, pour simplifier les choses, les extensions Apple sont ajoutées au début des attributs Rock Ridge existants (c'est-à-dire que pour obtenir les extensions Apple, vous obtenez également les extensions Rock Ridge).

Les extensions Apple nécessitent que la resource fork soit stockée en tant que fichier associé ISO-9660. C'est comme n'importe quel fichier normal stocké dans le système de fichiers ISO-9660, sauf que l'indicateur de fichier associé est défini dans l'enregistrement du répertoire (bit 2). Ce fichier porte le même nom que la data fork (le fichier vu par les machines non-Apple). Les fichiers associés sont normalement ignorés par les autres systèmes d'exploitation.

Lors de l'utilisation de l'option -hfs, le TYPE et le CREATOR ainsi que d'autres informations du Finder sont stockés dans un répertoire HFS séparé, invisible sur le volume ISO-9660. Le répertoire HFS référence les mêmes fichiers de données et de ressources décrits ci-dessus.

Dans la plupart des cas, il est préférable d'utiliser l'option -hfs plutôt que l'option -apple, car cette dernière impose les caractères ISO-9660 limités autorisés dans les noms de fichiers. Cependant, les extensions Apple offrent l'avantage que les fichiers sont compressés sur le disque plus efficacement et il peut être possible de faire tenir plus de fichiers sur un CD - ce qui est important lorsque la taille totale des fichiers source approche les 650 Mo.

NOMS DE FICHIERS MACINTOSH HFS

Dans la mesure du possible, le nom de fichier HFS qui est stocké avec un fichier Apple/Unix est utilisé pour la partie HFS du CD. Cependant, tous les encodages Apple/Unix ne stockent pas le nom de fichier HFS avec les finderinfo. Dans ces cas, le nom de fichier Unix est utilisé - avec les caractères spéciaux échappés. Les caractères spéciaux incluent '/' et les caractères dont les codes sont supérieurs à 127.

Aufs échappe ces caractères en utilisant ":" suivi du code caractère sous forme de deux chiffres hexadécimaux. Netatalk et EtherShare ont un schéma similaire, mais utilisent "%" au lieu de ":".

Si mkisofs ne trouve pas de nom de fichier HFS, il utilise le nom Unix, avec les caractères %xx ou :xx (xx == deux chiffres hexadécimaux) convertis en un seul code caractère. Si "xx" ne sont pas des chiffres hexadécimaux ([0-9a-fA-F]), alors ils sont laissés tels quels - bien que tout ":" restant soit converti en "%" car le deux-points est le séparateur de répertoire HFS. Il faut faire attention, car un fichier Unix ordinaire avec %xx ou :xx sera également converti. Par exemple :

This:2fFile converti en This/File
This:File converti en This%File
This:t7File converti en This%t7File

Bien que les noms de fichiers HFS semblent prendre en charge les lettres majuscules et minuscules, le système de fichiers est insensible à la casse. C'est-à-dire que les noms de fichiers "aBc" et "AbC" sont identiques. Si un fichier est trouvé dans un répertoire avec le même nom HFS, alors mkisofs tentera, dans la mesure du possible, de créer un nom unique en ajoutant des caractères '_' à l'un des noms de fichiers.

Si un nom de fichier HFS existe pour un fichier, alors mkisofs peut utiliser ce nom comme point de départ pour les noms de fichiers ISO-9660, Joliet et Rock Ridge en utilisant l'option -mac-name. Les fichiers Unix normaux sans nom HFS utiliseront toujours leur nom Unix. Par exemple :

Si un fichier MacBinary (ou PC Exchange) est stocké sous le nom someimage.gif.bin sur le système de fichiers Unix, mais contient un fichier HFS appelé someimage.gif, alors c'est ce nom qui apparaîtra sur la partie HFS du CD. Cependant, comme mkisofs utilise le nom Unix comme point de départ pour les autres noms, le nom ISO-9660 généré sera probablement SOMEIMAG.BIN et le Joliet/Rock Ridge sera someimage.gif.bin. Bien que les données réelles (dans ce cas) soient une image GIF. Cette option utilisera le nom de fichier HFS comme point de départ et le nom ISO-9660 sera probablement SOMEIMAG.GIF et le Joliet/Rock Ridge sera someimage.gif.

L'utilisation de l'option -mac-name ne fonctionnera actuellement pas avec l'option -T - le nom Unix sera utilisé dans le fichier TRANS.TBL, pas le nom Macintosh.

Le jeu de caractères utilisé pour convertir tout nom de fichier HFS en nom de fichier Joliet/Rock Ridge est par défaut cp10000 (Mac Roman). Le jeu de caractères utilisé peut être spécifié à l'aide de l'option -input-hfs-charset. D'autres jeux de caractères HFS intégrés sont : cp10006 (MacGreek), cp10007 (MacCyrillic), cp10029 (MacLatin2), cp10079 (MacIcelandic) et cp10081 (MacTurkish).

Note : les codes de caractères utilisés par les noms de fichiers HFS extraits des différents formats Apple/Unix ne seront pas convertis car ils sont supposés être dans le bon jeu de caractères Apple. Seuls les noms Joliet/Rock Ridge dérivés des noms de fichiers HFS seront convertis.

Le code mkisofs existant filtrera tous les caractères illégaux pour les noms de fichiers ISO-9660 et Joliet, mais comme mkisofs s'attend à traiter directement les noms Unix, il laisse les noms Rock Ridge tels quels. Mais comme '/' est un caractère de nom de fichier HFS légal, l'option -mac-name convertit '/' en '_' dans les noms de fichiers Rock Ridge.

Si les extensions Apple sont utilisées, alors seuls les noms de fichiers ISO-9660 apparaîtront sur le Macintosh. Cependant, comme les pilotes ISO-9660 Macintosh peuvent utiliser des noms de fichiers de niveau 2, vous pouvez utiliser des options comme -allow-multidot sans problème sur un Macintosh - faites toujours attention aux noms, par exemple this.file.name sera converti en THIS.FILE, c'est-à-dire qu'il n'y aura qu'un seul '.', également le nom de fichier abcdefgh sera vu comme ABCDEFGH mais abcdefghi sera vu comme ABCDEFGHI., c'est-à-dire avec un '.' à la fin - je ne sais pas si c'est un problème Macintosh ou un problème mkisofs/mkhybrid. Tous les noms de fichiers seront en majuscules lorsqu'ils sont vus sur un Macintosh. Bien sûr, les machines DOS/Win3.X ne pourront pas voir les noms de fichiers de niveau 2...

ICONES PERSONNALISÉES DE VOLUME/DOSSIER HFS

Pour donner à un CD HFS une icône personnalisée, assurez-vous que le dossier racine (de niveau supérieur) inclut un fichier d'icône de volume Macintosh standard. Pour donner à un volume une icône personnalisée sur un Macintosh, une icône doit être collée par-dessus l'icône du volume dans le

"Boîte d'informations" du volume. Cela crée un fichier invisible nommé 'Icon\r' ('\r' est le caractère 'retour chariot') dans le dossier racine.

Une icône de dossier personnalisée est très similaire - un fichier invisible nommé 'Icon\r' existe dans le dossier lui-même.

La façon la plus simple de créer une icône personnalisée que mkisofs peut utiliser est probablement de formater une disquette vierge HFS sur un Mac, puis de coller une icône dans sa boîte "Informations". Si vous utilisez Linux avec le module HFS installé, montez la disquette en utilisant quelque chose comme :

mount -t hfs /dev/fd0 /mnt/floppy

La disquette sera montée par défaut comme un système de fichiers CAP. Ensuite, exécutez mkisofs en utilisant quelque chose comme :

mkisofs --cap -o output source_dir /mnt/floppy

Si vous n'utilisez pas Linux, vous pouvez utiliser hfsutils pour copier le fichier icône depuis la disquette. Cependant, il faut faire attention, car le fichier icône contient un caractère de contrôle. Par exemple :

hmount /dev/fd0
hdir -a
hcopy -m Icon^V^M icon_dir/icon

Où '^V^M' représente Control-V suivi de Control-M. Ensuite, exécutez mkisofs en utilisant quelque chose comme :

mkisofs --macbin -o output source_dir icon_dir

La procédure de création/utilisation d'icônes de dossiers personnalisées est très similaire - collez une icône dans la boîte "Informations" du dossier et transférez le fichier 'Icon\r' résultant dans le répertoire approprié de l'arborescence source de mkisofs.

Vous voudrez peut-être masquer les fichiers icônes des arbres ISO-9660 et Joliet.

Pour donner une icône personnalisée à un CD Joliet, suivez les instructions trouvées à : http://www.fadden.com/cdrfaq/faq03.html#[3-21]

DRIVER DE DÉMARRAGE HFS

Il peut être possible de rendre le CD hybride amorçable sur un Macintosh.

Un CD HFS amorçable nécessite un pilote Apple CD-ROM (ou compatible), une partition HFS amorçable et les fichiers système, Finder, etc. nécessaires.

Un pilote peut être obtenu à partir de tout autre CD-ROM amorçable Macintosh en utilisant l'utilitaire apple_driver. Ce fichier peut ensuite être utilisé avec l'option -boot-hfs-file.

La partition HFS (c'est-à-dire le disque hybride dans notre cas) doit contenir un dossier Système approprié, à nouveau à partir d'un autre CD-ROM ou disque.

Pour qu'une partition soit amorçable, son bloc de démarrage doit être défini. Le bloc de démarrage se trouve dans les deux premiers blocs d'une partition. Pour une partition non amorçable, le bloc de démarrage est rempli de zéros. Normalement, lorsqu'un fichier Système est copié sur une partition d'un disque Macintosh, le bloc de démarrage est rempli avec un certain nombre de paramètres requis - malheureusement, je ne connais pas les spécifications complètes du bloc de démarrage, je suppose donc que ce qui suit fonctionnera correctement.

Par conséquent, l'utilitaire apple_driver extrait également le bloc de démarrage de la première partition HFS qu'il trouve sur le CD-ROM donné, et celui-ci est utilisé pour la partition HFS créée par mkisofs.

TABLE D'INFORMATIONS DE DÉMARRAGE EL TORITO

Lorsque l'option -boot-info-table est donnée, mkisofs modifiera le fichier de démarrage spécifié par l'option -b en insérant une "table d'informations de démarrage" de 56 octets à l'offset 8 dans le fichier. Cette modification est effectuée dans le système de fichiers source, assurez-vous donc d'utiliser une copie si ce fichier n'est pas facilement recréable ! Ce fichier contient des pointeurs qui peuvent ne pas être obtenus facilement ou de manière fiable au moment du démarrage.

Le format de cette table est le suivant ; tous les entiers sont au format de la section 7.3.1 ("little endian").

Offset	Nom	Taille	Signification
 8	bi_pvd	4 octets	LBA du descripteur de volume primaire
12	bi_file	4 octets	LBA du fichier de démarrage
16	bi_length	4 octets	Longueur du fichier de démarrage en octets
20	bi_csum	4 octets	Somme de contrôle de 32 bits
24	bi_reserved	40 octets	Réservé

La somme de contrôle de 32 bits est la somme de tous les mots de 32 bits dans le fichier de démarrage à partir de l'offset 8. Toutes les adresses de bloc linéaires (LBA) sont données en secteurs CD (normalement 2048 octets).

CONFIGURATION

mkisofs recherche le fichier .mkisofsrc, d'abord dans le répertoire de travail courant, puis dans le répertoire personnel de l'utilisateur, et enfin dans le répertoire où se trouve l'exécutable mkisofs. Ce fichier est censé contenir une série de lignes de la forme TAG=valeur, et vous pouvez ainsi spécifier certaines options. La casse de la balise n'est pas significative. Certains champs de l'en-tête du volume ne sont pas configurables en ligne de commande, mais peuvent être modifiés via cette fonctionnalité. Les commentaires peuvent être placés dans ce fichier, en utilisant des lignes commençant par un caractère dièse (#).

APPI
L'identifiant de l'application doit décrire l'application qui sera sur le disque. Il y a de la place sur le disque pour 128 caractères d'informations. L'entrée Joliet correspondante est limitée à 64 caractères. Peut être remplacé en utilisant l'option de ligne de commande -A.
COPY
Les informations de copyright, souvent le nom d'un fichier sur le disque contenant l'avis de droit d'auteur. Il y a de la place sur le disque pour 37 caractères d'informations. L'entrée Joliet correspondante est limitée à 18 caractères. Peut être remplacé en utilisant l'option de ligne de commande -copyright.
ABST
Les informations abstraites, souvent le nom d'un fichier sur le disque contenant un résumé. Il y a de la place sur le disque pour 37 caractères d'informations. L'entrée Joliet correspondante est limitée à 18 caractères. Peut être remplacé en utilisant l'option de ligne de commande -abstract.
BIBL
Les informations bibliographiques, souvent le nom d'un fichier sur le disque contenant une bibliographie. Il y a de la place sur le disque pour 37 caractères d'informations. L'entrée Joliet correspondante est limitée à 18 caractères. Peut être remplacé en utilisant l'option de ligne de commande -bilio.
PREP
Ceci doit décrire le préparateur du CDROM, généralement avec une adresse postale et un numéro de téléphone. Il y a de la place sur le disque pour 128 caractères d'informations. L'entrée Joliet correspondante est limitée à 64 caractères. Peut être remplacé en utilisant l'option de ligne de commande -p.
PUBL
Ceci doit décrire l'éditeur du CDROM, généralement avec une adresse postale et un numéro de téléphone. Il y a de la place sur le disque pour 128 caractères d'informations. L'entrée Joliet correspondante est limitée à 64 caractères. Peut être remplacé en utilisant l'option de ligne de commande -publisher.
SYSI
L'identifiant du système. Il y a de la place sur le disque pour 32 caractères d'informations. Peut être remplacé en utilisant l'option de ligne de commande -sysid.
VOLI
L'identifiant du volume. Il y a de la place sur le disque pour 32 caractères d'informations. Peut être remplacé en utilisant l'option de ligne de commande -V.
VOLS
Le nom de l'ensemble de volumes. Il y a de la place sur le disque pour 128 caractères d'informations. L'entrée Joliet correspondante est limitée à 64 caractères. Peut être remplacé en utilisant l'option de ligne de commande -volset.
HFS_TYPE
Le TYPE par défaut pour les fichiers Macintosh. Doit comporter exactement 4 caractères. Peut être remplacé en utilisant l'option de ligne de commande -hfs-type.
HFS_CREATOR
Le CRÉATEUR par défaut pour les fichiers Macintosh. Doit comporter exactement 4 caractères. Peut être remplacé en utilisant l'option de ligne de commande -hfs-creator.

mkisofs peut également être configuré à la compilation avec des valeurs par défaut pour nombre de ces champs. Voir le fichier defaults.h.

EXEMPLES

Pour créer une image de système de fichiers ISO-9660 vierge dans le fichier cd.iso, où le répertoire cd_dir deviendra le répertoire racine de l'image ISO du CD, appelez :

% mkisofs -o cd.iso cd_dir

Pour créer un CD avec les extensions Rock Ridge du répertoire source cd_dir :

% mkisofs -o cd.iso -R cd_dir

Pour créer un CD avec les extensions Rock Ridge du répertoire source cd_dir où tous les fichiers ont au moins la permission de lecture et où tous les fichiers appartiennent à root, appelez :

% mkisofs -o cd.iso -r cd_dir

Pour graver directement une archive tar sur un CD qui contiendra plus tard un système de fichiers ISO-9660 simple avec l'archive tar, appelez :

% star -c . | mkisofs -stream-media-size 333000 | \
cdrecord dev=b,t,l -dao tsize=333000s -

Pour créer un CD hybride HFS avec les extensions Joliet et Rock Ridge du répertoire source cd_dir :

% mkisofs -o cd.iso -R -J -hfs cd_dir

Pour créer un CD hybride HFS à partir du répertoire source cd_dir qui contient des fichiers Netatalk Apple/Unix :

% mkisofs -o cd.iso --netatalk cd_dir

Pour créer un CD hybride HFS à partir du répertoire source cd_dir, en donnant à tous les fichiers un CRÉATEUR et des TYPES basés uniquement sur leurs extensions de nom de fichier listées dans le fichier "mapping".:

% mkisofs -o cd.iso -map mapping cd_dir

Pour créer un CD avec les 'Extensions Apple à ISO-9660', à partir des répertoires source cd_dir et another_dir. Les fichiers dans tous les formats Apple/Unix connus sont décodés et tous les autres fichiers reçoivent un CRÉATEUR et un TYPE basés sur leur nombre magique indiqué dans le fichier "magic" :

% mkisofs -o cd.iso -apple -magic magic -probe \
cd_dir another_dir

L'exemple suivant place différents fichiers sur le CD qui ont tous le nom README, mais ont des contenus différents lorsqu'ils sont vus comme un CD ISO-9660/RockRidge, Joliet ou HFS.

Le répertoire courant contient :

% ls -F
README.hfs README.joliet README.unix cd_dir/

La commande suivante place le contenu du répertoire cd_dir sur le CD ainsi que les trois fichiers README - mais un seul sera vu depuis chacun des trois systèmes de fichiers :

% mkisofs -o cd.iso -hfs -J -r -graft-points \
-hide README.hfs -hide README.joliet \
-hide-joliet README.hfs -hide-joliet README.unix \
-hide-hfs README.joliet -hide-hfs README.unix \
README=README.hfs README=README.joliet \
README=README.unix cd_dir

c'est-à-dire que le fichier README.hfs sera vu comme README sur le CD HFS et les deux autres fichiers README seront cachés. Similairement pour le CD Joliet et ISO-9660/RockRidge.

Il est probable que toutes sortes de résultats étranges soient possibles avec les combinaisons des options de masquage...

Pour créer un DVD-Audio à partir du répertoire source conforme DVD-Audio DVD :

% mkisofs -o dvda.iso -dvd-audio DVD

NOTES

Mkisofs peut être installé en toute sécurité suid root. Cela peut être nécessaire pour permettre à mkisofs de lire la session précédente lors de la création d'une image multi-sessions.

mkisofs n'est pas basé sur les outils standards mk*fs pour unix, car nous devons générer une copie complète d'un système de fichiers existant sur un disque dans le système de fichiers ISO-9660. Le nom mkisofs est probablement un peu trompeur, puisqu'il ne crée pas seulement le système de fichiers, mais qu'il le remplit également. Cependant, le nom d'outil approprié pour un outil UNIX qui crée des systèmes de fichiers peuplés - mkproto - n'est pas bien connu.

Si mkisofs crée une image de système de fichiers avec des attributs Rock Ridge et que le niveau d'imbrication des répertoires de l'arborescence de répertoires source est trop élevé pour ISO-9660, mkisofs effectuera une relocalisation de répertoire en profondeur. Cela se traduit par un répertoire appelé RR_MOVED dans le répertoire racine du CD. Vous ne pouvez pas éviter ce répertoire dans l'arborescence des répertoires qui est visible avec ISO-9660, mais il est automatiquement caché dans l'arborescence Rock Ridge.

Le support de démarrage sparc implémenté avec les options -sparc-boot suit entièrement les exigences officielles de démarrage CD Sparc du PROM de démarrage des systèmes Sun Sparc. Certaines distributions Linux pour systèmes Sparc utilisent un chargeur de démarrage appelé SILO qui, malheureusement, n'est pas conforme au démarrage CD Sparc. Il est agaçant de constater que les auteurs de SILO ne corrigent pas SILO mais fournissent plutôt un "patch" totalement inutile à mkisofs qui incorpore beaucoup plus de code source que la correction pour SILO ne le nécessiterait.

BOGUES

•
Ne lit pas correctement les répertoires relocalisés en mode multi-sessions lors de l'ajout de données.

Tout répertoire profond relocalisé est perdu si la nouvelle session n'inclut pas le répertoire profond.

Répéter en : créant la première session avec relocalisation de répertoire profond, puis en ajoutant une nouvelle session avec un seul répertoire différent de l'ancien chemin profond.

•
Ne réutilise pas RR_MOVED lors de la réalisation de multi-sessions à partir de TRANS.TBL

Il peut y en avoir d'autres. Merci de les signaler à l'auteur.

PROBLEMES/LIMITATIONS HFS

J'ai dû faire plusieurs hypothèses sur la manière dont je m'attends à ce que les routines libhfs modifiées fonctionnent, mais il peut y avoir des situations auxquelles je n'ai pas pensé, ou que j'ai rencontrées lorsque ces hypothèses échouent. Par conséquent, je ne peux pas garantir que mkisofs fonctionnera comme prévu (bien que je n'aie pas encore eu de problème majeur). La plupart des fonctionnalités HFS fonctionnent bien, cependant, certaines ne sont pas entièrement testées. Elles sont marquées comme Alpha ci-dessus.

Bien que les noms de fichiers HFS semblent supporter les lettres majuscules et minuscules, le système de fichiers est insensible à la casse. C'est-à-dire que les noms de fichiers "aBc" et "AbC" sont identiques. Si un fichier est trouvé dans un répertoire avec le même nom HFS, alors mkisofs tentera, lorsque cela est possible, de créer un nom unique en ajoutant des caractères '_' à l'un des noms de fichiers.

Les noms de fichiers/répertoires HFS qui partagent les 31 premiers caractères ont _N' (N == nombre décimal) substitué aux derniers caractères pour générer des noms uniques.

Il faut être prudent lors de la "greffe" de fichiers ou répertoires Apple/Unix (voir ci-dessus pour la méthode et la syntaxe impliquées). Il n'est pas possible d'utiliser un nouveau nom pour un fichier/répertoire encodé Apple/Unix. Par exemple, si un fichier encodé Apple/Unix nommé "anciennom" doit être ajouté au CD, alors vous ne pouvez pas utiliser la ligne de commande :

mkisofs -o output.raw -hfs -graft-points nouveaunom=anciennom cd_dir

mkisofs ne pourra pas décoder "anciennom". Cependant, vous pouvez greffer des fichiers ou répertoires encodés Apple/Unix tant que vous n'essayez pas de leur donner de nouveaux noms comme ci-dessus.

Lors de la création d'un volume HFS avec les options multi-sessions, -M et -C, seuls les fichiers de la dernière session seront dans le volume HFS. C'est-à-dire que mkisofs ne peut pas *ajouter* de fichiers existants de sessions précédentes au volume HFS.

Cependant, si chaque session est créée avec l'option -part, alors chaque session apparaîtra comme des volumes séparés lorsqu'elle sera montée sur un Mac. Dans ce cas, il est utile d'utiliser l'option -V ou -hfs-volid pour donner à chaque session un nom de volume unique, sinon chaque "volume" apparaîtra sur le bureau avec le même nom.

Les liens symboliques (comme tous les autres fichiers non réguliers) ne sont pas ajoutés au répertoire HFS.

Les volumes hybrides peuvent être plus volumineux que les volumes ISO-9660 purs contenant les mêmes données. Dans certains cas (par exemple, les volumes de taille DVD), le volume hybride peut être significativement plus grand. À mesure qu'un volume HFS grandit, la taille du bloc d'allocation (la plus petite quantité d'espace qu'un fichier peut occuper) augmente également. Pour un CD de 650 Mo, le bloc d'allocation est de 10 Ko, pour un DVD de 4,7 Go, il sera d'environ 70 Ko.

Le nombre maximum de fichiers dans un volume HFS est d'environ 65500 - bien que la limite réelle soit quelque peu inférieure.

Le volume hybride résultant peut être accédé sur une machine Unix en utilisant les routines hfsutils. Cependant, aucune modification ne peut être apportée au volume car il est défini comme verrouillé. L'option -hfs-unlock créera une image de sortie qui n'est pas verrouillée - cependant, aucune modification ne doit être apportée au contenu du volume (sauf si vous savez vraiment ce que vous faites) car ce n'est pas un "vrai" volume HFS.

L'utilisation de l'option -mac-name ne fonctionnera pas actuellement avec l'option -T - le nom Unix sera utilisé dans le fichier TRANS.TBL, pas le nom Macintosh.

Bien que mkisofs ne modifie pas le contenu d'un fichier, si un fichier binaire a son TYPE défini sur 'TEXT', il *peut* être lu incorrectement sur un Macintosh. Par conséquent, un meilleur choix pour le TYPE par défaut pourrait être '????'

L'option -mac-boot-file peut ne pas fonctionner du tout...

Peut ne pas fonctionner avec les fichiers PC Exchange v2.2 ou supérieur (disponibles avec MacOS 8.1). Les médias DOS contenant des fichiers PC Exchange doivent être montés comme type msdos (pas vfat) lors de l'utilisation de Linux.

Le format SFM n'est que partiellement pris en charge - voir la section FORMATS DE FICHIERS MACINTOSH HFS ci-dessus.

Il n'est pas possible d'utiliser les options -sparc-boot ou -generic-boot avec les options -boot-hfs-file, -prep-boot ou -chrp-boot.

mkisofs devrait être capable de créer des images hybrides HFS sur plus de 4 Go, bien que cela n'ait pas été entièrement testé.

mkhybrid(8) - Manual Page

NAME

mkhybrid - create a hybrid CD-ROM filesystem image

SYNOPSIS

mkhybrid [ OPTIONS ] ISO9660

DESCRIPTION

The mkhybrid utility creates a CD-ROM filesystem image file (e.g. for burning to a CD-ROM, or for mounting under Linux) that is compatible with multiple operating systems. It starts by creating an ISO9660 filesystem image with the specified parameters, and then adds support for other operating systems by adding the necessary filesystem structures.

The primary goal is to create a CD-ROM that can be read by all common operating systems (Linux, Windows, macOS). This is achieved by creating an ISO9660 filesystem, and then adding the Joliet extension for Windows and the HFS extension for macOS.

OPTIONS

The following options are supported:

-o output_file
Specifies the output file name. If not specified, the output is written to standard output.
-v
Verbose output. Prints information about the files being processed.
-J
Enable Joliet extensions (Windows).
-R
Enable Rock Ridge extensions (POSIX/Linux).
-l
Enable ISO9660 Level 1 support.
-L
Enable ISO9660 Level 2 support.
-h
Enable HFS extensions (macOS).
-H level
Specifies the HFS filesystem type. level can be:
-
No HFS extensions are created.
hfs
Standard HFS filesystem.
hfsplus
HFS+ filesystem (requires macOS 8.1 or later).
-e
Enable El Torito bootable CD-ROM support.
-b boot_image
Specifies the boot image file for El Torito support. This is typically a floppy disk image or a CD-ROM boot image.
-c catalog_file
Specifies the boot catalog file for El Torito support. If not specified, a default catalog will be created.
-A
Enable Apple Extensions (for PowerPC boot).
-p platform_id
Specifies the platform ID for El Torito boot. Common values are:
0x00
No Emulation (for bare boot).
0x01
1.2MB Floppy Disk Emulation.
0x02
1.44MB Floppy Disk Emulation.
0x03
2.88MB Floppy Disk Emulation.
0x04
CD-ROM Hard Disk Emulation (for PowerPC).
-T emulation_type
Specifies the emulation type for El Torito boot. Common values are:
none
No emulation.
bootmgr
Windows boot manager.
grub
GRUB bootloader.
-t timestamp
Specifies the timestamp for all files in the image. Format is YYYYMMDDHHMMSS.
-m volume_id
Specifies the volume ID (name) for the CD-ROM.
-q
Quiet mode. Suppresses most output.
-g
Generate a GUID (Globally Unique Identifier) for the HFS filesystem.
-G guid
Specifies a custom GUID for the HFS filesystem.
-k icon_file
Specifies a custom icon file for the HFS volume.
-P creator_type
Specifies the creator and type for HFS files. Format is 'cccc' 'ttttt'.
-M mac_file_format
Specifies the Macintosh file format for HFS files.
-u uid
Specifies the user ID for all files.
-g gid
Specifies the group ID for all files.
-r mode
Specifies the file mode for all files.
-ascii
Convert all file names to ASCII (for ISO9660).
-utf8
Convert all file names to UTF-8 (for Joliet).

HFS OPTIONS

The following options are specific to HFS (macOS) extensions:

-h
Enable HFS extensions.
-H level
Specifies the HFS filesystem type. level can be:
-
No HFS extensions.
hfs
Standard HFS filesystem.
hfsplus
HFS+ filesystem (requires macOS 8.1 or later).
-g
Generate a GUID (Globally Unique Identifier) for the HFS filesystem.
-G guid
Specifies a custom GUID for the HFS filesystem.
-k icon_file
Specifies a custom icon file for the HFS volume.
-P creator_type
Specifies the creator and type for HFS files. Format is 'cccc' 'ttttt'.
-M mac_file_format
Specifies the Macintosh file format for HFS files. Can be 'hfs' or 'hfsplus'.

CHARACTER SETS

By default, mkhybrid uses the system's character set for file names. You can specify the character set to be used for the ISO9660 and Joliet filesystems with the following options:

-ascii
Convert all file names to ASCII.
-utf8
Convert all file names to UTF-8.

HFS CREATOR/TYPE

The creator and type of a file are used by macOS to determine how to open the file. You can specify the creator and type for all files in the HFS filesystem with the -P option. The format is four characters for the creator and four characters for the type, enclosed in single quotes.

Example: -P 'APPL' 'TEXT'

HFS MACINTOSH FILE FORMATS

The -M option allows you to specify the Macintosh file format to be used for HFS files. The default is 'hfs'. You can also use 'hfsplus' for HFS+ filesystem support.

HFS MACINTOSH FILE NAMES

HFS file names can be up to 31 characters long and can contain spaces and punctuation. By default, mkhybrid will convert file names to conform to HFS naming conventions.

HFS CUSTOM VOLUME/FOLDER ICONS

You can specify a custom icon for the HFS volume using the -k option. The icon file should be a standard Macintosh icon file (ICN#).

HFS BOOT DRIVER

HFS boot drivers are not directly supported by mkhybrid. If you need to create a bootable HFS CD-ROM, you will need to use a specialized tool like mkfs.hfs or hdiutil from macOS.

EL TORITO BOOT INFORMATION TABLE

The El Torito specification defines a standard way to make CD-ROMs bootable. mkhybrid supports this specification through the -e, -b, -c, -p, and -T options.

CONFIGURATION

mkhybrid does not use a configuration file. All options are specified on the command line.

EXAMPLES

Create a hybrid CD-ROM image with ISO9660, Joliet, and Rock Ridge extensions:

mkhybrid -o hybrid.iso -R -J /path/to/your/files

Create a hybrid CD-ROM image with HFS+ support and a custom volume ID:

mkhybrid -o mac_hybrid.iso -h -H hfsplus -m "My CD-ROM" /path/to/your/files

Create a bootable El Torito CD-ROM image (e.g., for a Linux rescue system):

mkhybrid -o boot.iso -e -b boot/isolinux/isolinux.bin -c boot/isolinux/boot.cat -no-emul-boot -boot-load-size 4 -boot-info-table /path/to/your/files
