NOM

mkisofs - créer une image de système de fichiers hybride ISO-9660/JOLIET/HFS/UDF avec des attributs Rock Ridge optionnels.

SYNOPIS

mkisofs [ options ] [ -o nom_fichier ] spécification_chemin [spécification_chemin ...]
mkisofs [ options ] [ -o nom_fichier ] -find [expression find]

DESCRIPTION

mkisofs est essentiellement un programme de pré-mastering pour générer un système de fichiers hybride ISO-9660/JOLIET/HFS/UDF.

Les systèmes de fichiers ISO-9660/JOLIET/UDF sont limités à une taille maximale de 8 To. La taille maximale d'un fichier unique est de 8 To (les fichiers uniques dans UDF sont actuellement limités à environ 200 Go). Si vous souhaitez avoir des fichiers de plus de 2 Go, vous devez spécifier -iso-level 3 ou supérieur. Si un hybride HFS est créé, la taille maximale des fichiers dans l'hybride HFS est de 2 Go dans tous les cas.

Support des systèmes de fichiers hybrides

mkisofs est capable de générer les enregistrements System Use Sharing Protocol (SUSP) spécifiés par le Rock Ridge Interchange Protocol. Ceci est utilisé pour décrire davantage les fichiers dans le système de fichiers ISO-9660 pour un hôte UNIX, et fournit des informations telles que des noms de fichiers plus longs, uid/gid, permissions POSIX, liens symboliques, liens physiques, périphériques blocs et caractères.

Si des options de ligne de commande pour l'hybride Joliet, HFS ou UDF sont spécifiées, mkisofs créera des métadonnées de système de fichiers séparées supplémentaires pour Joliet, HFS ou UDF. Le contenu des fichiers dans ce cas fait référence aux mêmes blocs de données sur le support. Il générera un système de fichiers ISO-9660 pur à moins que les options de ligne de commande pour l'hybride Joliet, HFS ou UDF ne soient fournies.

mkisofs peut générer un système de fichiers hybride HFS *véritable* (ou *partagé*). Les mêmes fichiers sont vus comme des fichiers HFS lorsqu'ils sont accédés depuis un Macintosh et comme des fichiers ISO-9660 lorsqu'ils sont accédés depuis d'autres machines. HFS signifie *Hierarchical File System* et est le système de fichiers natif utilisé sur les ordinateurs Macintosh jusqu'à Mac OS 9.

En alternative, mkisofs peut générer les *Extensions Apple à ISO-9660* ou *UDF* pour chaque fichier. Ces extensions fournissent à chaque fichier un CRÉATEUR, un TYPE et certains indicateurs du Finder lorsqu'ils sont accédés depuis un Macintosh. Voir la section FORMATS DE FICHIERS MACINTOSH HFS ci-dessous.

Description fonctionnelle

mkisofs prend un instantané d'un arbre de répertoires donné, et génère une image binaire qui correspondra à un système de fichiers ISO-9660 ou Joliet/HFS/UDF lorsqu'elle est écrite sur un périphérique bloc.

Chaque fichier écrit dans le système de fichiers ISO-9660 doit avoir un nom de fichier au format 8.3 (8 caractères, point, 3 caractères, tous en majuscules), même si les attributs Rock Ridge sont utilisés. Ce nom de fichier est utilisé sur les systèmes qui ne sont pas capables d'utiliser les extensions Rock Ridge (comme MS-DOS), et chaque nom de fichier dans chaque répertoire doit être différent des autres noms de fichiers dans le même répertoire. mkisofs essaie généralement de former des noms corrects en forçant le nom de fichier UNIX en majuscules et en le tronquant si nécessaire, mais souvent cela donne des résultats insatisfaisants lorsqu'il y a des cas où les noms tronqués ne sont pas tous uniques. mkisofs attribue des pondérations à chaque nom de fichier, et si deux noms qui sont autrement identiques sont trouvés, le nom avec la priorité la plus basse est renommé pour avoir un numéro à 3 chiffres comme extension (où le numéro est garanti unique). Un exemple de ceci serait les fichiers foo.bar et foo.bar.~1~ - le fichier foo.bar.~1~ serait écrit comme FOO000.BAR;1 et le fichier foo.bar serait écrit comme FOO.BAR;1

Lorsqu'il est utilisé avec diverses options HFS ou UDF, mkisofs tentera de reconnaître les fichiers stockés dans un certain nombre de formats de fichiers Apple/Unix et copiera les fourches de données et de ressources ainsi que toute information pertinente du Finder. Voir la section FORMATS DE FICHIERS MACINTOSH HFS ci-dessous pour plus d'informations sur les formats pris en charge par mkisofs.

Notez que mkisofs n'est pas conçu pour communiquer directement avec les graveurs pour médias optiques. La plupart des graveurs ont des jeux de commandes propriétaires qui varient d'un fabricant à l'autre, et vous avez besoin d'un outil spécialisé comme cdrecord pour graver réellement le disque.

L'utilitaire cdrecord est un utilitaire capable de graver un disque réel. La dernière version de cdrecord est disponible sur https://sourceforge.net/projects/cdrtools/files/ ou https://sourceforge.net/projects/cdrtools/files/alpha/

Vous devriez également savoir que la plupart des graveurs de CD sont très pointilleux sur le timing. Une fois que vous commencez à graver un disque, vous ne pouvez pas laisser leur tampon se vider avant d'avoir terminé, sinon vous vous retrouverez avec un disque corrompu. Il est donc essentiel que vous puissiez maintenir un flux de données ininterrompu vers le graveur pendant toute la durée de l'écriture du disque.

Gestion des noms de chemin

spécification_chemin est le chemin de l'arbre de répertoires à copier dans le système de fichiers ISO-9660. Plusieurs chemins peuvent être spécifiés, et mkisofs fusionnera les fichiers trouvés dans tous les composants de chemin spécifiés pour former l'image du cdrom.

Si l'option -graft-points a été spécifiée, il est possible de greffer les chemins à d'autres points que le répertoire racine, et il est possible de greffer des fichiers ou des répertoires sur l'image cdrom avec des noms différents de ceux qu'ils ont dans le système de fichiers source. Ceci est plus facile à illustrer avec quelques exemples. Commençons par supposer qu'un fichier local ../old.lis existe, et que vous souhaitez l'inclure dans l'image cdrom.

foo/bar/=../old.lis

inclura le fichier old.lis dans l'image cdrom à /foo/bar/old.lis, tandis que

foo/bar/xxx=../old.lis

inclura le fichier old.lis dans l'image cdrom à /foo/bar/xxx. Le même type de syntaxe peut être utilisé avec des répertoires. mkisofs créera tous les répertoires nécessaires pour que les points de greffe existent sur l'image cdrom - les répertoires n'ont pas besoin d'apparaître dans l'un des chemins. Par défaut, tous les répertoires créés à la volée de cette manière auront des permissions 0555 et sembleront appartenir à la personne exécutant mkisofs. Si vous souhaitez d'autres permissions ou propriétaires pour les répertoires intermédiaires, voir -uid, -gid, -dir-mode, -file-mode et -new-dir-mode.

mkisofs fonctionnera également sur les machines Win9x/NTx lorsqu'il est compilé avec cygwin de Cygnus (disponible sur http://sourceware.cygnus.com/cygwin/). Par conséquent, la plupart des références dans cette page de manuel à *Unix* s'appliquent également à *Win32* ou *Win64*.

OPTIONS

-abstract FICHIER
Spécifie le nom du fichier abstrait dans le descripteur de volume primaire. Il y a de la place sur le disque pour 37 caractères d'information. L'entrée Joliet correspondante est limitée à 18 caractères. Ce paramètre peut également être défini dans le fichier .mkisofsrc avec ABST=nom_fichier. S'il est spécifié aux deux endroits, la version en ligne de commande est utilisée.

Il appartient à l'utilisateur de mkisofs d'inclure un fichier avec le nom approprié dans l'arborescence du système de fichiers créée.

-A id_application
-appid id_application
Spécifie une chaîne de texte qui sera écrite dans l'en-tête du volume. Elle doit décrire l'application qui sera sur le disque. Il y a de la place sur le disque pour 128 caractères d'information. L'entrée Joliet correspondante est limitée à 64 caractères. Ce paramètre peut également être défini dans le fichier .mkisofsrc avec APPI=id. S'il est spécifié aux deux endroits, la version en ligne de commande est utilisée.
-allow-leading-dots
-ldots
Autorise les noms de fichiers ISO-9660 à commencer par un point. Habituellement, un point initial est remplacé par un trait de soulignement afin de maintenir la compatibilité MS-DOS.
Ceci viole la norme ISO-9660, mais cela fonctionne sur de nombreux systèmes. Utiliser avec prudence.
-allow-lowercase
Cette option autorise les caractères minuscules dans les noms de fichiers ISO-9660.

Ceci viole la norme ISO-9660, mais cela fonctionne sur certains systèmes. Utilisez avec prudence.
-no-allow-lowercase
Ceci annule l'effet de -allow-lowercase et fonctionne même lorsque -U, -untranslated-filenames ou -iso-level 4 ont été utilisés pour autoriser les noms de fichiers en minuscules.
-allow-multidot
Cette option autorise la présence de plus d'un point dans les noms de fichiers ISO-9660. Un point de départ n'est pas affecté par cette option, il peut être autorisé séparément en utilisant l'option -allow-leading-dots.
Ceci viole la norme ISO-9660, mais cela fonctionne sur de nombreux systèmes. Utilisez avec prudence.
-biblio FICHIER
Spécifie le nom du fichier bibliographique dans le descripteur de volume primaire. Il y a de la place sur le disque pour 37 caractères d'information. L'entrée Joliet associée est limitée à 18 caractères. Ce paramètre peut également être défini dans le fichier .mkisofsrc avec BIBLO=nomfichier. Si spécifié aux deux endroits, la version de la ligne de commande est utilisée.

Il appartient à l'utilisateur de mkisofs d'inclure un fichier avec le nom approprié dans l'arborescence du système de fichiers créé.

-cache-inodes
Met en cache les numéros d'inode et de périphérique pour trouver les liens physiques vers les fichiers. Si mkisofs trouve un lien physique (un fichier avec plusieurs noms), alors le fichier n'apparaîtra qu'une seule fois sur le CD. Cela permet d'économiser de l'espace sur le CD. L'option -cache-inodes est activée par défaut sur les systèmes d'exploitation de type UNIX. Soyez prudent lorsque vous utilisez cette option sur un système de fichiers sans numéros d'inode uniques, car cela pourrait entraîner des fichiers contenant le mauvais contenu sur le CD.

Voir l'option -duplicates-once pour une méthode qui fonctionne sur les systèmes de fichiers sans numéros d'inode uniques.

Si les inodes ne sont pas mis en cache, mkisofs reviendra à l'ancienne version Rrip Version-1.10 (voir -rrip110) et mkisofs ne pourra pas créer de numéros d'inode corrects pour les fichiers de taille nulle.

-no-cache-inodes
Ne met pas en cache les numéros d'inode et de périphérique. Cette option est nécessaire chaque fois qu'un système de fichiers n'a pas de numéros d'inode uniques. C'est la valeur par défaut sur les anciennes versions de Cygwin. Comme le système d'exploitation Microsoft qui s'exécute sous Cygwin utilise des numéros d'inode de 64 bits pour NTFS, il n'a pas de numéros d'inode uniques dans la plage de 32 bits. Les anciennes versions de Cygwin créent de faux numéros d'inode de 32 bits à partir d'un algorithme de hachage et créent ainsi des numéros non uniques. Si mkisofs mettait en cache les inodes sur les anciennes versions de Cygwin, il croirait que certains fichiers sont identiques bien qu'ils ne le soient pas. Le résultat dans ce cas sont des fichiers qui contiennent le mauvais contenu si une quantité significative de fichiers différents (> ~5000) se trouve dans l'arborescence à archiver. Cela ne se produit pas lorsque -no-cache-inodes est utilisé, mais l'inconvénient est que mkisofs ne peut plus détecter les liens physiques et que l'image CD résultante peut être plus grande que prévu.

Si les inodes ne sont pas mis en cache, mkisofs reviendra à l'ancienne version Rrip Version-1.10 (voir -rrip110) et mkisofs ne pourra pas créer de numéros d'inode corrects pour les fichiers de taille nulle.

-duplicates-once
Indique à mkisofs d'utiliser une somme de contrôle de hachage de message pour identifier les fichiers identiques comme étant apparemment liés physiquement. Cela permet à mkisofs d'archiver les numéros d'inode et les liens physiques même lorsqu'il est exécuté sur des plateformes non POSIX comme DOS.
-b image_de_démarrage_eltorito
-eltorito-boot image_de_démarrage_eltorito
Spécifie le chemin et le nom de fichier de l'image de démarrage à utiliser lors de la création d'un CD amorçable "El Torito". Le chemin d'accès doit être relatif au chemin source et à l'intérieur de l'arborescence source spécifiée à mkisofs. Cette option est requise pour créer un CD amorçable "El Torito". L'image de démarrage doit avoir exactement la taille d'une disquette de 1200, 1440 ou 2880 Ko, et mkisofs utilisera cette taille lors de la création du système de fichiers ISO-9660 de sortie. Il est supposé que le premier secteur de 512 octets doit être lu à partir de l'image de démarrage (il émule essentiellement un lecteur de disquette normal). Cela fonctionnera, par exemple, si l'image de démarrage est une disquette de démarrage.

Si l'image de démarrage n'est pas une image de disquette, vous devez ajouter l'une des options : -hard-disk-boot ou -no-emul-boot. Si le système ne doit pas démarrer à partir du disque émulé, utilisez -no-boot.

Plusieurs entrées de démarrage peuvent être spécifiées, voir -eltorito-platform et -eltorito-alt-boot pour savoir comment spécifier plusieurs entrées de démarrage. La première entrée de démarrage est l'entrée de démarrage par défaut. Les entrées de démarrage supplémentaires sont des membres d'une configuration de démarrage multiple.

Si l'option -sort n'a pas été spécifiée, les images de démarrage sont triées avec une faible priorité (+2) au début du support. Si cela ne vous convient pas, vous devez spécifier un poids de tri de 0 pour les images de démarrage.

-eltorito-alt-boot
Commence avec un nouvel ensemble de paramètres de démarrage "El Torito". Cela permet d'avoir plus d'une entrée de démarrage El Torito sur un CD. Un maximum de 63 entrées de démarrage El Torito peuvent être placées sur un seul CD.

L'option -eltorito-alt-boot démarre une nouvelle entrée de démarrage avec le même identifiant de plateforme mais sans nouvelle section de démarrage, sauf lorsqu'elle apparaît après la première entrée de démarrage qui est l'entrée de démarrage par défaut.

-eltorito-platform id
Définit l'identifiant de plateforme "El Torito" pour un enregistrement de démarrage ou une section d'enregistrements de démarrage. Le paramètre id peut être soit :
x86
C'est la valeur par défaut de l'identifiant de plateforme id et spécifie les entrées pour la plateforme PC. Si aucune option -eltorito-platform n'apparaît avant la première option -eltorito-boot, l'entrée de démarrage par défaut devient une entrée pour la plateforme PC x86.
PPC
Entrées de démarrage pour la plateforme Power PC.
Mac
Entrées de démarrage pour la plateforme Apple Mac.
efi
Entrées de démarrage pour les PC basés sur EFI.
#
Une valeur numérique spécifiant n'importe quel identifiant de plateforme.

Si l'option -eltorito-platform apparaît avant la première option -eltorito-boot, elle définit l'identifiant de plateforme id pour l'entrée de démarrage par défaut.

Si l'option -eltorito-platform apparaît après une option -eltorito-boot et définit l'identifiant de plateforme id à une valeur différente de la valeur précédente, elle démarre un nouvel ensemble d'entrées de démarrage.

La deuxième entrée de démarrage et tout nouvel identifiant de plateforme créent un nouvel en-tête de section et réduisent le nombre d'entrées de démarrage par CD de un.

errctl= nom
errctl= spécification_de_contrôle_d'erreur
Ajoute le contenu du fichier nom aux définitions de contrôle d'erreur ou ajoute la spécification_de_contrôle_d'erreur aux définitions de contrôle d'erreur. Plus d'un fichier de contrôle d'erreur et plus d'une spécification_de_contrôle_d'erreur ainsi qu'un mélange des deux formes sont possibles.

La raison d'utiliser le contrôle d'erreurs est de rendre mkisofs silencieux sur les conditions d'erreur connues pour être sans importance pour la qualité du système de fichiers créé ou pour indiquer à mkisofs d'avorter sur certaines conditions d'erreur au lieu d'essayer de continuer avec le système de fichiers.

Une raison typique d'utiliser le contrôle d'erreurs est de supprimer les avertissements concernant la croissance des fichiers journaux lors d'une sauvegarde sur un système de fichiers actif. Une autre raison typique d'utiliser le contrôle d'erreurs est d'indiquer à mkisofs d'avorter si, par exemple, un fichier n'a pas pu être archivé au lieu de continuer à archiver d'autres fichiers d'une liste.

Le fichier de contrôle d'erreurs contient un ensemble de lignes, chacune commençant par une liste de conditions d'erreur à ignorer, suivie d'un espace blanc, puis d'un modèle de nom de fichier (voir match(1) ou patmatch(3) pour plus d'informations). La spécification_de_contrôle_d'erreur utilise la même syntaxe qu'une seule ligne du fichier de contrôle d'erreurs. Si le modèle de nom de fichier doit commencer par un espace blanc, utilisez une barre oblique inverse pour échapper le début du nom de fichier. Il n'est pas possible d'avoir des caractères de nouvelle ligne dans le modèle de nom de fichier. Chaque fois qu'une situation d'erreur est rencontrée, mkisofs vérifie les lignes du fichier de contrôle d'erreurs en commençant par le haut. Si la condition d'erreur actuelle est répertoriée sur une ligne du fichier de contrôle d'erreurs, alors mkisofs vérifie si le modèle du reste de la ligne correspond au nom de fichier actuel. Si c'est le cas, mkisofs utilise la spécification de contrôle d'erreurs actuelle pour contrôler la condition d'erreur actuelle.

La liste des conditions d'erreur à traiter peut utiliser un ou plusieurs (dans ce cas séparés par un caractère '|') identifiants de la liste ci-dessous :

ABORT
Si cette méta-condition est incluse dans une condition d'erreur, mkisofs avortera (s'arrêtera) dès que possible après que cette condition d'erreur a été vue au lieu de rendre mkisofs silencieux sur la condition. Ce drapeau de condition d'erreur ne peut être utilisé qu'avec une autre condition d'erreur ou une liste de conditions d'erreur (séparées par un caractère '|').
WARN
Si cette méta-condition est incluse dans une condition d'erreur, mkisofs imprimera l'avertissement concernant la condition d'erreur, mais la condition d'erreur n'affectera pas le code de sortie de mkisofs et les statistiques d'erreur (qui sont imprimées à la fin) n'incluront pas les erreurs associées. Ce drapeau de condition d'erreur ne peut être utilisé qu'avec une autre condition d'erreur ou une liste de conditions d'erreur (séparées par un caractère '|'). La méta-condition WARN a une priorité inférieure à ABORT.
ALL
C'est un raccourci pour toutes les conditions d'erreur ci-dessous.
STAT
Supprime les avertissements indiquant que mkisofs n'a pas pu stat(2) un fichier.
GETACL
Supprime les avertissements concernant
OPEN
Supprime les avertissements concernant les fichiers qui n'ont pas pu être ouverts.
READ
Supprime les avertissements concernant les erreurs de lecture sur les fichiers.
WRITE
Supprime les avertissements concernant les erreurs d'écriture sur les fichiers.
READLINK
Supprime les avertissements concernant les erreurs readlink(2) sur les liens symboliques.
GROW
Supprime les avertissements concernant les fichiers qui ont grandi pendant leur archivage.
SHRINK
Supprime les avertissements concernant les fichiers qui ont rétréci pendant leur archivage.
MISSLINK
Supprime les avertissements concernant les fichiers pour lesquels mkisofs n'a pas pu archiver tous les liens physiques.
NAMETOOLONG
Supprime les avertissements concernant les fichiers qui n'ont pas pu être archivés car le nom du fichier est trop long pour le format d'archive.
FILETOOBIG
Supprime les avertissements concernant les fichiers qui n'ont pas pu être archivés car la taille du fichier est trop grande pour le format d'archive.
SPECIALFILE
Supprime les avertissements concernant les fichiers qui n'ont pas pu être archivés car le type de fichier n'est pas supporté par le format d'archive.
GETXATTR
Supprime les avertissements concernant les fichiers pour lesquels mkisofs n'a pas pu récupérer les informations des attributs étendus de fichier.
SETTIME
Supprime les avertissements concernant les fichiers pour lesquels mkisofs n'a pas pu définir les informations de temps lors de l'extraction.
SETMODE
Supprime les avertissements concernant les fichiers pour lesquels mkisofs n'a pas pu définir les modes d'accès lors de l'extraction.
SECURITY
Supprime les avertissements concernant les fichiers qui ont été ignorés lors de l'extraction car ils ont été considérés comme présentant un risque pour la sécurité. Cela s'applique actuellement à tous les fichiers contenant une séquence '/../' lorsque -.. n'a pas été spécifié.
LSECURITY
Supprime les avertissements concernant les liens qui ont été ignorés lors de l'extraction car ils ont été considérés comme présentant un risque pour la sécurité. Cela s'applique actuellement à tous les noms de liens commençant par '/' ou contenant une séquence '/../' lorsque -secure-links a été spécifié. Dans ce cas, mkisofs essaie de faire correspondre le nom du lien avec le motif dans le fichier de contrôle d'erreur.
SAMEFILE
Supprime les avertissements concernant les liens qui ont été ignorés lors de l'extraction car la source et la cible du lien pointent vers le même fichier. Si mkisofs n'ignorait pas ces fichiers, il finirait par supprimer complètement le fichier. Dans ce cas, mkisofs essaie de faire correspondre le nom du lien avec le motif dans le fichier de contrôle d'erreur.
BADACL
Supprime les avertissements concernant les problèmes de conversion de listes de contrôle d'accès.
SETACL
Supprime les avertissements concernant les fichiers pour lesquels mkisofs n'a pas pu définir les informations ACL lors de l'extraction.
SETXATTR
Supprime les avertissements concernant les fichiers pour lesquels mkisofs n'a pas pu définir les informations des attributs étendus de fichier lors de l'extraction.

Si une condition d'erreur spécifique est ignorée, la condition d'erreur est non seulement traitée de manière silencieuse mais également exclue des statistiques d'erreurs imprimées à la fin de l'exécution de mkisofs.

Soyez très prudent lors de l'utilisation du contrôle d'erreurs, car vous pourriez ignorer n'importe quelle condition d'erreur. Si vous ignorez les bonnes conditions d'erreur, vous pourriez ne plus être en mesure de voir les vrais problèmes.

Notez qu'actuellement seuls les identificateurs OPEN, READ, GROW, SHRINK sont vérifiés par mkisofs.

-B img_sun4,img_sun4c,img_sun4m,img_sun4d,img_sun4e
-sparc-boot img_sun4,img_sun4c,img_sun4m,img_sun4d,img_sun4e
Spécifie une liste d'images de démarrage séparées par des virgules qui sont nécessaires pour créer un CD amorçable pour les systèmes sparc. La partition 0 est utilisée pour l'image ISO-9660, la première image de fichier est mappée sur la partition 1. Il peut y avoir des champs vides dans la liste séparée par des virgules. Le nombre maximum de partitions possibles est de 8, il est donc impossible de spécifier plus de 7 images de partition. Cette option est requise pour créer un CD amorçable pour les systèmes Sun sparc. Si l'option -B ou -sparc-boot a été spécifiée, le premier secteur de l'image résultante contiendra une étiquette de disque Sun. Cette étiquette de disque spécifie la tranche 0 pour l'image ISO-9660 et les tranches 1 à 7 pour les images de démarrage spécifiées avec cette option. Les octets 512 à 8191 de chaque image de démarrage supplémentaire doivent contenir une amorce primaire qui fonctionne pour l'architecture sparc appropriée. Le reste de chaque image contient généralement un système de fichiers ufs utilisé pour le premier stade d'amorçage du noyau.

La méthode d'amorçage implémentée est celle trouvée avec SunOS 4.x et SunOS 5.x. Cependant, elle ne dépend pas des internes de SunOS mais uniquement des propriétés du PROM Open Boot. Pour cette raison, elle devrait être utilisable pour tout OS qui démarre sur un système sparc.

Pour plus d'informations, consultez également la section NOTES ci-dessous.

-rational-rock
C'est comme l'option -R, mais la propriété et les permissions des fichiers sont définies sur des valeurs plus utiles. L'uid et le gid sont mis à zéro, car ils ne sont généralement utiles que sur le système de l'auteur, et non utiles pour le client. Tous les bits de lecture des fichiers sont mis à vrai, de sorte que les fichiers et les répertoires soient globalement lisibles sur le client. Si un bit d'exécution est défini pour un fichier, tous les bits d'exécution sont définis, de sorte que les exécutables soient globalement exécutables sur le client. Si un bit de recherche est défini pour un répertoire, tous les bits de recherche sont définis, de sorte que les répertoires soient globalement consultables sur le client. Tous les bits d'écriture sont effacés, car le CD-Rom sera monté en lecture seule dans tous les cas. Si l'un des bits de mode spéciaux est défini, effacez-les, car les verrous de fichiers ne sont pas utiles sur un système de fichiers en lecture seule, et les bits set-id ne sont pas souhaitables pour uid 0 ou gid 0. Lorsqu'il est utilisé sous Win32, le bit d'exécution est défini sur *tous* les fichiers. Ceci est le résultat du manque de permissions de fichiers sous Win32 et de la couche d'émulation POSIX Cygwin. JEUX DE CARACTÈRES

mkisofs traite les noms de fichiers d'une manière conforme POSIX en tant que chaînes de caractères 8 bits. Pour représenter tous les codages de toutes les langues, les caractères 8 bits ne sont pas suffisants. Unicode ou ISO-10646 définissent des codages de caractères qui nécessitent au moins 21 bits pour représenter toutes les langues connues. Ils peuvent être représentés avec le codage UTF-32, UTF-16 ou UTF-8. UTF-32 utilise un codage 32 bits simple mais semble être peu courant. UCS-2 est utilisé par Microsoft avec Win32. Ce codage est similaire à UTF-16 avec le désavantage qu'il ne prend en charge qu'un sous-ensemble de 16 bits (sauf lorsque des surrogats sont utilisés) de tous les codes et que les caractères 16 bits ne sont pas conformes à l'interface de nom de fichier POSIX.

Les systèmes d'exploitation UNIX modernes peuvent utiliser le codage UTF-8 pour les noms de fichiers. Ce codage permet d'utiliser l'ensemble complet des codes Unicode. Chaque caractère 32 bits est représenté par un ou plusieurs caractères 8 bits. Si un caractère est codé en ISO-8859-1 (utilisé en Europe centrale et en Amérique du Nord) il correspond 1:1 à un caractère Unicode codé en UTF-32 ou UTF-16. Si un caractère est codé en ASCII 7 bits (utilisé aux États-Unis et dans d'autres pays avec un jeu de caractères limité) il correspond 1:1 à un caractère Unicode codé en UTF-32, UTF-16 ou UTF-8. Les codes de caractères qui ne peuvent pas être représentés par un seul octet en UTF-8 (typiquement si la valeur est supérieure à 0x7F) utilisent des séquences d'échappement qui correspondent à plus d'un caractère 8 bits.

Si tous les systèmes d'exploitation utilisaient le codage UTF-8, mkisofs n'aurait pas besoin de recoder les caractères dans les noms de fichiers. Malheureusement, Apple utilise des codages complètement non standard et Microsoft utilise un codage Unicode qui n'est pas compatible avec l'interface de nom de fichier POSIX.

Pour tous les systèmes d'exploitation non codés en UTF-8, le caractère réel que chaque octet représente dépend du jeu de caractères ou de la page de codes (qui est le nom utilisé par Microsoft) utilisé par le système d'exploitation local en cours d'utilisation - les caractères d'un jeu de caractères refléteront la région ou la langue naturelle utilisée par l'utilisateur.

Généralement, les codes de caractères 0x00-0x1f sont des caractères de contrôle, les codes 0x20-0x7f sont les caractères ASCII 7 bits et (sur les PC et Mac) 0x80-0xff sont utilisés pour d'autres caractères. Malheureusement, cela ne suit même pas les normes ISO qui réservent la plage 0x80-0x9f pour les caractères de contrôle et n'autorisent que 0xa0-0xff pour d'autres caractères.

Comme il y a beaucoup plus de 256 caractères/symboles utilisés, seul un petit sous-ensemble est représenté dans un jeu de caractères. Par conséquent, le même code de caractère peut représenter un caractère différent dans des jeux de caractères différents. Ainsi, un nom de fichier généré, disons en Europe centrale, peut ne pas afficher le même caractère lorsqu'il est visualisé sur une machine dans, disons, l'Europe de l'Est.

Pour compliquer les choses, différents systèmes d'exploitation utilisent des jeux de caractères différents pour la région ou la langue. Par exemple, le code de caractère pour « petit e avec accent aigu » peut être le code de caractère 0x82 sur un PC, le code 0x8e sur un Macintosh et le code 0xe9 sur un système UNIX. Notez que bien que les codages utilisés sur un PC ou un Mac soient non standard, Unicode code ce caractère comme 0x00000000e9, ce qui est essentiellement la même valeur que la valeur utilisée par la plupart des systèmes UNIX.

Tant que tous les systèmes d'exploitation et toutes les applications n'utiliseront pas l'ensemble de caractères Unicode comme base pour les noms de fichiers d'une manière unique, il peut être nécessaire de spécifier quel jeu de caractères vos noms de fichiers utilisent et quel jeu de caractères les noms de fichiers doivent apparaître sur le CD.

Il existe quatre options pour spécifier les jeux de caractères que vous souhaitez utiliser :

Définit le jeu de caractères local que vous utilisez sur votre machine hôte. Toute conversion de jeu de caractères qui a lieu utilisera ce jeu de caractères comme point de départ. Les jeux de caractères d'entrée par défaut sont cp437 sur les systèmes basés sur DOS et iso8859-1 sur tous les autres systèmes.

Si l'option -J est donnée, alors les équivalents Unicode du jeu de caractères d'entrée seront utilisés dans le répertoire Joliet. L'utilisation de l'option -jcharset est identique à l'utilisation des options -input-charset et -J.

Définit le jeu de caractères qui sera utilisé pour les noms Rock Ridge sur le CD. Par défaut, il utilise le jeu de caractères d'entrée. Il est seulement susceptible d'être utile lorsqu'il est utilisé sur une plateforme non Unix. Par exemple, utiliser mkisofs sur une machine Microsoft Win32 pour créer des CD Rock Ridge. Si vous utilisez mkisofs sur une machine Unix, il est probable que le jeu de caractères de sortie soit le même que le jeu de caractères d'entrée.

L'ensemble de caractères par défaut est intégré à mkisofs. Un certain nombre d'autres ensembles de caractères sont lus à partir du système de fichiers par mkisofs à partir d'un répertoire relativement au chemin d'installation. Pour obtenir une liste, utilisez mkisofs -input-charset help.

Les ensembles de caractères supplémentaires de iconv(1) peuvent être utilisés sur les systèmes qui prennent en charge iconv(1). Dans ce cas, appelez iconv -l pour obtenir une liste des ensembles de caractères valides de cette méthode de codage. Pour forcer un codage basé sur iconv(1), utilisez iconv:nom au lieu de nom pour l'ensemble de caractères.

Si vous utilisez des ensembles de caractères non basés sur iconv(1), des ensembles de caractères supplémentaires peuvent être lus à partir d'un fichier pour toutes les options d'ensemble de caractères en donnant un nom de fichier comme argument aux options. Un ensemble de caractères donné sera lu à partir d'un fichier chaque fois que le nom fourni contient un '/'.

Le format des fichiers d'ensemble de caractères est le même que celui des fichiers de mappage disponibles sur http://www.unicode.org/Public/MAPPINGS. Le format de ces fichiers est le suivant :

La colonne n° 1 est le code d'octet d'entrée (en hexadécimal, 0xXX)
La colonne n° 2 est l'Unicode (en hexadécimal, 0xXXXX)
Le reste de la ligne est ignoré.

Toute ligne vide, toute ligne sans deux colonnes (ou plus) au format ci-dessus ou toute ligne de commentaire (commençant par le caractère #) est ignorée sans avertissement. Tout code d'entrée manquant est mappé au caractère Unicode 0x0000.

Notez qu'il n'y a pas de prise en charge de l'UNICODE 16 bits (UTF-16) ou de l'UNICODE 32 bits (UTF-32) car ce codage n'est pas conforme POSIX. Il devrait y avoir une prise en charge du codage UNICODE UTF-8, compatible avec les noms de fichiers POSIX et pris en charge par les implémentations UNIX modernes comme Solaris.

Un mappage de caractères 1:1 peut être défini en utilisant le mot-clé default comme argument pour l'une des options d'ensemble de caractères. C'est le comportement des versions plus anciennes (v1.12) de mkisofs.

Les noms de fichiers ISO-9660 générés à partir des noms de fichiers d'entrée ne sont pas convertis à partir de l'ensemble de caractères d'entrée. L'ensemble de caractères ISO-9660 est un sous-ensemble très limité des caractères ASCII, donc toute conversion serait inutile.

Tout caractère que mkisofs ne peut pas convertir sera remplacé par un caractère '_' .

HFS CREATEUR/TYPE

Un fichier Macintosh possède deux propriétés associées qui définissent l'application qui a créé le fichier, le CREATEUR et ce que le fichier contient, le TYPE. Les deux sont des chaînes de 4 lettres (exactement). Généralement, cela permet à un utilisateur Macintosh de double-cliquer sur un fichier et de lancer l'application correcte, etc. Le CREATEUR et le TYPE d'un fichier particulier peuvent être trouvés en utilisant quelque chose comme ResEdit (ou similaire) sur un Macintosh.

Les informations CREATEUR et TYPE sont stockées dans tous les divers fichiers encodés Apple/Unix. Pour les autres fichiers, il est possible de baser le CREATEUR et le TYPE sur l'extension du nom du fichier en utilisant un fichier de mappage (l'option -map) et/ou en utilisant le nombre magique (généralement une signature dans les premiers octets) d'un fichier (l'option -magic). Si ces deux options sont données, leur ordre sur la ligne de commande est important. Si l'option -map est donnée en premier, une correspondance d'extension de nom de fichier est tentée avant une correspondance de nombre magique. Cependant, si l'option -magic est donnée en premier, une correspondance de nombre magique est tentée avant une correspondance d'extension de nom de fichier.

Si un fichier de mappage ou magique n'est pas utilisé, ou si aucune correspondance n'est trouvée, alors le CREATEUR et le TYPE par défaut pour tous les fichiers réguliers peuvent être définis en utilisant des entrées dans le fichier .mkisofsrc ou en utilisant les options -hfs-creator et/ou -hfs-type, sinon le CREATEUR et le TYPE par défaut sont 'unix' et 'TEXT'.

Le format du fichier de mappage est le même format afpfile que celui utilisé par aufs. Ce fichier a cinq colonnes pour l'extension, la traduction de fichier, le CREATEUR, le TYPE et le Commentaire. Les lignes commençant par le caractère '#' sont des lignes de commentaire et sont ignorées. Un exemple de fichier pourrait ressembler à ceci :

# Exemple de fichier de mappage de noms de fichiers
#
# EXT XLate CREATEUR TYPE Commentaire
.tif Raw '8BIM' 'TIFF' "Image TIFF Photoshop"
.hqx Ascii 'BnHq' 'TEXT' "Fichier BinHex"
.doc Raw 'MSWD' 'WDBN' "Fichier Word"
.mov Raw 'TVOD' 'MooV' "Film QuickTime"
* Ascii 'ttxt' 'TEXT' "Fichier texte"

Où :

La première colonne EXT définit l'extension du nom de fichier Unix à mapper. La correspondance par défaut pour toute extension de nom de fichier qui ne correspond pas est définie avec le caractère "*".
La colonne Xlate définit le type de traduction de texte entre Unix et Macintosh. Elle est ignorée par mkisofs, mais conservée pour être compatible avec aufs(1). Bien que mkisofs ne modifie pas le contenu d'un fichier, si un fichier binaire a son TYPE défini sur 'TEXT', il *peut* être lu incorrectement sur un Macintosh. Par conséquent, un meilleur choix pour le TYPE par défaut pourrait être '????'.
Les mots-clés CREATEUR et TYPE doivent avoir 4 caractères de long et être entourés de guillemets simples.
Le champ commentaire est entouré de guillemets doubles - il est ignoré par mkisofs, mais conservé pour être compatible avec aufs.

Le format du fichier magic est presque identique au fichier magic(4) utilisé par la commande Linux file(1) - les routines de lecture et de décodage du fichier magic sont basées sur la commande Linux file(1).

Ce fichier a quatre colonnes séparées par des tabulations pour l'*offset d'octet*, le *type*, le *test* et le *message*. Les lignes commençant par le caractère '#' sont des lignes de commentaire et sont ignorées. Un exemple de fichier pourrait ressembler à ceci :

# Exemple de fichier magique
#
# off type test message
0 string GIF8 8BIM GIFf Image GIF
0 beshort 0xffd8 8BIM Données d'image JPEG
0 string SIT! SIT! SIT! Archive StuffIt
0 string \037\235 Compression Unix standard LZIV ZIVU
0 string \037\213 Données compressées gzip GNUz ZIVU
0 string %! ASPS TEXT Postscript
0 string \004%! ASPS TEXT Postscript PC avec un ^D pour commencer
4 string moov txtt MooV Fichier film QuickTime (moov)
4 string mdat txtt MooV Fichier film QuickTime (mdat)

Le format du fichier est décrit dans la page de manuel magic(4). La seule différence ici est que pour chaque entrée du fichier magique, le *message* pour l'offset initial *doit* être de 4 caractères pour le CREATEUR suivi de 4 caractères pour le TYPE - l'espacement est facultatif entre eux. Tout autre caractère sur cette ligne est ignoré. Les lignes de continuation (commençant par un '>') sont également ignorées, c'est-à-dire que seules les lignes d'offset initial sont utilisées.

L'utilisation de l'option -magic peut augmenter considérablement le temps de traitement car chaque fichier doit être ouvert et lu pour trouver son nombre magique.

En résumé, pour tous les fichiers, le CREATEUR par défaut est 'unix' et le TYPE par défaut est 'TEXT'. Ceux-ci peuvent être modifiés en utilisant des entrées dans le fichier .mkisofsrc ou en utilisant les options -hfs-creator et/ou -hfs-type.

Si un fichier est dans l'un des formats Apple/Unix connus (et que le format a été sélectionné), alors le CREATEUR et le TYPE sont tirés des valeurs stockées dans le fichier Apple/Unix.

D'autres fichiers peuvent avoir leur CREATEUR et TYPE définis à partir de leur extension de nom de fichier (l'option -map), ou de leur nombre magique (l'option -magic). Si la correspondance par défaut est utilisée dans le fichier de mappage, alors ces valeurs remplacent le CREATEUR et TYPE par défaut.

Une base de données complète des CREATEUR/TYPE peut être trouvée sur http://www.angelfire.com/il/szekely/index.html

HFS FORMATS DE FICHIERS MACINTOSH

Les fichiers Macintosh ont deux parties appelées le fork de Données et le fork de Ressources. L'un ou l'autre peut être vide. Unix (et de nombreux autres systèmes d'exploitation) ne peut gérer que des fichiers ayant une seule partie (ou fork). Pour ajouter à cela, les fichiers Macintosh ont un certain nombre d'attributs associés - probablement les plus importants sont le TYPE et le CREATEUR. Encore une fois, Unix n'a aucun concept de ces types d'attributs.

Par exemple, un fichier Macintosh peut être une image JPEG où l'image est stockée dans le fork de Données et une miniature de bureau stockée dans le fork de Ressources. C'est généralement l'information contenue dans le fork de données qui est utile sur toutes les plateformes.

Par conséquent, pour stocker un fichier Macintosh sur un système de fichiers Unix, il faut trouver un moyen de gérer les deux forks et les attributs supplémentaires (qui sont désignés comme les *informations du finder*). Malheureusement, il semble que chaque paquet logiciel qui stocke des fichiers Macintosh sur Unix ait choisi une méthode de stockage complètement différente.

Les formats Apple/Unix que mkisofs prend (partiellement) en charge sont :

Format CAP AUFS
Fork de données stocké dans un fichier. Fork de ressources dans le sous-répertoire .resource avec le même nom de fichier que le fork de données. Informations du finder dans le sous-répertoire .finderinfo avec le même nom de fichier.
AppleDouble/Netatalk

Si un fichier est trouvé avec une fourche de ressources de longueur nulle et des informations du Finder vides, il est supposé ne pas avoir d'encodage Apple/Unix - par conséquent, un TYPE et un CREATEUR peuvent être définis par d'autres méthodes.

mkisofs tentera de définir le CREATEUR, le TYPE, la date et potentiellement d'autres indicateurs à partir des informations du Finder. De plus, si elle existe, le nom de fichier Macintosh est défini à partir des informations du Finder, sinon le nom Macintosh est basé sur le nom Unix - voir la section NOMS DE FICHIERS MACINTOSH HFS ci-dessous.

Lors de l'utilisation de l'option -apple, le TYPE et le CREATEUR sont stockés dans le champ facultatif System Use ou SUSP de l'enregistrement de répertoire ISO-9660 - de la même manière que les attributs Rock Ridge. En fait, pour simplifier les choses, les extensions Apple sont ajoutées au début des attributs Rock Ridge existants (c'est-à-dire que pour obtenir les extensions Apple, vous obtenez également les extensions Rock Ridge).

Les extensions Apple nécessitent que la fourche de ressources soit stockée en tant que fichier associé ISO-9660. C'est comme tout fichier normal stocké dans le système de fichiers ISO-9660, sauf que l'indicateur de fichier associé est défini dans l'enregistrement de répertoire (bit 2). Ce fichier porte le même nom que la fourche de données (le fichier visible par les machines non-Apple). Les fichiers associés sont normalement ignorés par les autres systèmes d'exploitation.

Lors de l'utilisation de l'option -hfs, le TYPE et le CREATEUR ainsi que d'autres informations du Finder sont stockés dans un répertoire HFS séparé, non visible sur le volume ISO-9660. Le répertoire HFS référence les mêmes fichiers de données et de ressources décrits ci-dessus.

Dans la plupart des cas, il est préférable d'utiliser l'option -hfs plutôt que l'option -apple, car cette dernière impose les caractères ISO-9660 limités autorisés dans les noms de fichiers. Cependant, les extensions Apple offrent l'avantage que les fichiers sont empaquetés plus efficacement sur le disque et il peut être possible de faire tenir plus de fichiers sur un CD - important lorsque la taille totale des fichiers sources approche les 650 Mo.

NOMS DE FICHIERS MACINTOSH HFS

Dans la mesure du possible, le nom de fichier HFS qui est stocké avec un fichier Apple/Unix est utilisé pour la partie HFS du CD. Cependant, tous les encodages Apple/Unix ne stockent pas le nom de fichier HFS avec les informations du Finder. Dans ces cas, le nom de fichier Unix est utilisé - avec des caractères spéciaux échappés. Les caractères spéciaux incluent '/' et les caractères dont les codes sont supérieurs à 127.

Aufs échappe ces caractères en utilisant ":" suivi du code caractère en deux chiffres hexadécimaux. Netatalk et EtherShare ont un schéma similaire, mais utilisent "%" au lieu de ":".

Si mkisofs ne trouve pas de nom de fichier HFS, il utilise le nom Unix, avec les caractères %xx ou :xx (xx == deux chiffres hexadécimaux) convertis en un seul code caractère. Si "xx" ne sont pas des chiffres hexadécimaux ([0-9a-fA-F]), ils sont laissés tels quels - bien que tout ":" restant soit converti en "%" car le deux-points est le séparateur de répertoire HFS. Il faut faire attention, car un fichier Unix ordinaire avec %xx ou :xx sera également converti. Par exemple :

This:2fFile converti en This/File
This:File converti en This%File
This:t7File converti en This%t7File

Bien que les noms de fichiers HFS semblent prendre en charge les lettres majuscules et minuscules, le système de fichiers est insensible à la casse. C'est-à-dire que les noms de fichiers "aBc" et "AbC" sont identiques. Si un fichier est trouvé dans un répertoire avec le même nom HFS, alors mkisofs tentera, dans la mesure du possible, de créer un nom unique en ajoutant des caractères '_' à l'un des noms de fichiers.

Si un nom de fichier HFS existe pour un fichier, alors mkisofs peut utiliser ce nom comme point de départ pour les noms de fichiers ISO-9660, Joliet et Rock Ridge en utilisant l'option -mac-name. Les fichiers Unix normaux sans nom HFS utiliseront toujours leur nom Unix. Par exemple :

Si un fichier MacBinary (ou PC Exchange) est stocké sous le nom someimage.gif.bin sur le système de fichiers Unix, mais contient un fichier HFS appelé someimage.gif, alors c'est ce nom qui apparaîtra sur la partie HFS du CD. Cependant, comme mkisofs utilise le nom Unix comme point de départ pour les autres noms, le nom ISO-9660 généré sera probablement SOMEIMAG.BIN et le Joliet/Rock Ridge sera someimage.gif.bin. Bien que les données réelles (dans ce cas) soient une image GIF. Cette option utilisera le nom de fichier HFS comme point de départ et le nom ISO-9660 sera probablement SOMEIMAG.GIF et le Joliet/Rock Ridge sera someimage.gif.

L'utilisation de l'option -mac-name ne fonctionnera pas actuellement avec l'option -T - le nom Unix sera utilisé dans le fichier TRANS.TBL, pas le nom Macintosh.

L'ensemble de caractères utilisé pour convertir tout nom de fichier HFS en nom de fichier Joliet/Rock Ridge est par défaut cp10000 (Mac Roman). L'ensemble de caractères utilisé peut être spécifié à l'aide de l'option -input-hfs-charset. Les autres jeux de caractères HFS intégrés sont : cp10006 (MacGreek), cp10007 (MacCyrillic), cp10029 (MacLatin2), cp10079 (MacIcelandic) et cp10081 (MacTurkish).

Note : les codes de caractères utilisés par les noms de fichiers HFS tirés des différents formats Apple/Unix ne seront pas convertis car ils sont supposés être dans le jeu de caractères Apple correct. Seuls les noms Joliet/Rock Ridge dérivés des noms de fichiers HFS seront convertis.

Le code mkisofs existant filtrera tous les caractères illégaux pour les noms de fichiers ISO-9660 et Joliet, mais comme mkisofs s'attend à traiter directement les noms Unix, il laisse les noms Rock Ridge tels quels. Mais comme '/' est un caractère de nom de fichier HFS légal, l'option -mac-name convertit '/' en '_' dans les noms de fichiers Rock Ridge.

Si les extensions Apple sont utilisées, seuls les noms de fichiers ISO-9660 apparaîtront sur le Macintosh. Cependant, comme les pilotes ISO-9660 Macintosh peuvent utiliser des noms de fichiers Niveau 2, vous pouvez utiliser des options telles que -allow-multidot sans problème sur un Macintosh - faites toujours attention aux noms, par exemple this.file.name sera converti en THIS.FILE, c'est-à-dire qu'il n'y aura qu'un seul '.', également le nom de fichier abcdefgh sera vu comme ABCDEFGH mais abcdefghi sera vu comme ABCDEFGHI., c'est-à-dire avec un '.' à la fin - on ne sait pas si c'est un problème Macintosh ou mkisofs/mkhybrid. Tous les noms de fichiers seront en majuscules lorsqu'ils sont vus sur un Macintosh. Bien sûr, les machines DOS/Win3.X ne pourront pas voir les noms de fichiers de niveau 2...

ICONES DE VOLUME/DOSSIER PERSONNALISES HFS

Pour donner une icône personnalisée à un CD HFS, assurez-vous que le dossier racine (de niveau supérieur) inclut un fichier d'icône de volume Macintosh standard. Pour donner une icône personnalisée à un volume sur un Macintosh, une icône doit être collée par-dessus l'icône du volume dans le

"Obtenir des informations" de ce volume. Cela crée un fichier invisible appelé « Icon\r » (« \r » est le caractère de retour chariot) dans le répertoire racine.

Une icône de dossier personnalisée est très similaire : un fichier invisible appelé « Icon\r » existe dans le dossier lui-même.

La manière la plus simple de créer une icône personnalisée que mkisofs puisse utiliser est probablement de formater une disquette HFS vierge sur un Mac, de coller une icône dans sa boîte « Obtenir des informations ». Si vous utilisez Linux avec le module HFS installé, montez la disquette en utilisant quelque chose comme :

mount -t hfs /dev/fd0 /mnt/floppy

La disquette sera montée comme un système de fichiers CAP par défaut. Ensuite, exécutez mkisofs en utilisant quelque chose comme :

mkisofs --cap -o output source_dir /mnt/floppy

Si vous n'utilisez pas Linux, vous pouvez utiliser les utilitaires hfsutils pour copier le fichier icône de la disquette. Cependant, il faut faire attention, car le fichier icône contient un caractère de contrôle. Par exemple :

hmount /dev/fd0
hdir -a
hcopy -m Icon^V^M icon_dir/icon

Où « ^V^M » est Ctrl-V suivi de Ctrl-M. Ensuite, exécutez mkisofs en utilisant quelque chose comme :

mkisofs --macbin -o output source_dir icon_dir

La procédure de création/utilisation d'icônes de dossier personnalisées est très similaire : collez une icône dans la boîte « Obtenir des informations » du dossier et transférez le fichier « Icon\r » résultant dans le répertoire approprié de l'arborescence source de mkisofs.

Vous voudrez peut-être masquer les fichiers icônes des arbres ISO-9660 et Joliet.

Pour donner une icône personnalisée à un CD Joliet, suivez les instructions trouvées à l'adresse : http://www.fadden.com/cdrfaq/faq03.html#[3-21]

PILOTE DE DÉMARRAGE HFS

Il peut être possible de rendre le CD hybride amorçable sur un Macintosh.

Un CD HFS amorçable nécessite un pilote Apple CD-ROM (ou compatible), une partition HFS amorçable et les fichiers système, Finder, etc. nécessaires.

Un pilote peut être obtenu à partir de n'importe quel autre CD-ROM amorçable de Macintosh en utilisant l'utilitaire apple_driver. Ce fichier peut ensuite être utilisé avec l'option -boot-hfs-file.

La partition HFS (c'est-à-dire le disque hybride dans notre cas) doit contenir un dossier système approprié, à nouveau à partir d'un autre CD-ROM ou disque.

Pour qu'une partition soit amorçable, son bloc d'amorçage doit être défini. Le bloc d'amorçage se trouve dans les deux premiers blocs d'une partition. Pour une partition non amorçable, le bloc d'amorçage est rempli de zéros. Normalement, lorsqu'un fichier système est copié sur une partition d'un disque Macintosh, le bloc d'amorçage est rempli d'un certain nombre de paramètres requis - malheureusement, je ne connais pas toutes les spécifications du bloc d'amorçage, je suppose donc que ce qui suit fonctionnera correctement.

Par conséquent, l'utilitaire apple_driver extrait également le bloc d'amorçage de la première partition HFS qu'il trouve sur le CD-ROM donné et celui-ci est utilisé pour la partition HFS créée par mkisofs.

Veuillez noter
En utilisant un pilote d'un CD Apple et en copiant des logiciels Apple sur votre CD, vous vous engagez à respecter les accords de licence logicielle d'Apple Computer, Inc.

TABLE D'INFORMATIONS D'AMORÇAGE EL TORITO

Lorsque l'option -boot-info-table est donnée, mkisofs modifiera le fichier d'amorçage spécifié par l'option -b en insérant une « table d'informations d'amorçage » de 56 octets à l'offset 8 dans le fichier. Cette modification est effectuée dans le système de fichiers source, assurez-vous donc d'utiliser une copie si ce fichier n'est pas facilement recréable ! Ce fichier contient des pointeurs qui peuvent ne pas être obtenus facilement ou de manière fiable au moment de l'amorçage.

Le format de cette table est le suivant ; tous les entiers sont au format de la section 7.3.1 (« little endian »).

Offset	Nom	Taille	Signification
 8	bi_pvd	4 octets	LBA du descripteur de volume primaire
12	bi_file	4 octets	LBA du fichier d'amorçage
16	bi_length	4 octets	Longueur du fichier d'amorçage en octets
20	bi_csum	4 octets	Somme de contrôle sur 32 bits
24	bi_reserved	40 octets	Réservé

La somme de contrôle sur 32 bits est la somme de tous les mots sur 32 bits dans le fichier d'amorçage à partir de l'offset 64 octets. Toutes les adresses de bloc linéaires (LBA) sont données en secteurs CD (normalement 2048 octets).

CONFIGURATION

mkisofs recherche le fichier .mkisofsrc, d'abord dans le répertoire de travail actuel, puis dans le répertoire personnel de l'utilisateur, et enfin dans le répertoire où se trouve le binaire mkisofs. Ce fichier est supposé contenir une série de lignes de la forme TAG=valeur, et de cette manière vous pouvez spécifier certaines options. La casse de la balise n'est pas significative. Certains champs de l'en-tête de volume ne peuvent pas être définis en ligne de commande, mais peuvent être modifiés via cette installation. Des commentaires peuvent être placés dans ce fichier, en utilisant des lignes qui commencent par un caractère dièse (#).

APPI
L'identifiant de l'application doit décrire l'application qui sera sur le disque. Il y a de la place sur le disque pour 128 caractères d'informations. L'entrée Joliet associée est limitée à 64 caractères. Peut être remplacé en utilisant l'option de ligne de commande -A.
COPY
Les informations de copyright, souvent le nom d'un fichier sur le disque contenant l'avis de droit d'auteur. Il y a de la place sur le disque pour 37 caractères d'informations. L'entrée Joliet associée est limitée à 18 caractères. Peut être remplacé en utilisant l'option de ligne de commande -copyright.
ABST
Les informations résumées, souvent le nom d'un fichier sur le disque contenant un résumé. Il y a de la place sur le disque pour 37 caractères d'informations. L'entrée Joliet associée est limitée à 18 caractères. Peut être remplacé en utilisant l'option de ligne de commande -abstract.
BIBL
Les informations bibliographiques, souvent le nom d'un fichier sur le disque contenant une bibliographie. Il y a de la place sur le disque pour 37 caractères d'informations. L'entrée Joliet associée est limitée à 18 caractères. Peut être remplacé en utilisant l'option de ligne de commande -bilio.
PREP
Ceci doit décrire le préparateur du CDROM, généralement avec une adresse postale et un numéro de téléphone. Il y a de la place sur le disque pour 128 caractères d'informations. L'entrée Joliet associée est limitée à 64 caractères. Peut être remplacé en utilisant l'option de ligne de commande -p.
PUBL
Ceci doit décrire l'éditeur du CDROM, généralement avec une adresse postale et un numéro de téléphone. Il y a de la place sur le disque pour 128 caractères d'informations. L'entrée Joliet associée est limitée à 64 caractères. Peut être remplacé en utilisant l'option de ligne de commande -publisher.
SYSI
L'identifiant du système. Il y a de la place sur le disque pour 32 caractères d'informations. Peut être remplacé en utilisant l'option de ligne de commande -sysid.
VOLI
L'identifiant du volume. Il y a de la place sur le disque pour 32 caractères d'informations. Peut être remplacé en utilisant l'option de ligne de commande -V.
VOLS
Le nom de l'ensemble de volumes. Il y a de la place sur le disque pour 128 caractères d'informations. L'entrée Joliet associée est limitée à 64 caractères. Peut être remplacé en utilisant l'option de ligne de commande -volset.
HFS_TYPE
Le TYPE par défaut pour les fichiers Macintosh. Doit être exactement 4 caractères. Peut être remplacé en utilisant l'option de ligne de commande -hfs-type.
HFS_CREATOR
Le CRÉATEUR par défaut pour les fichiers Macintosh. Doit être exactement 4 caractères. Peut être remplacé en utilisant l'option de ligne de commande -hfs-creator.

mkisofs peut également être configuré au moment de la compilation avec des valeurs par défaut pour bon nombre de ces champs. Voir le fichier defaults.h.

EXEMPLES

Pour créer une image de système de fichiers ISO-9660 vierge dans le fichier cd.iso, où le répertoire cd_dir deviendra le répertoire racine de l'image ISO du CD, appelez :

% mkisofs -o cd.iso cd_dir

Pour créer un CD avec les extensions Rock Ridge du répertoire source cd_dir :

% mkisofs -o cd.iso -R cd_dir

Pour créer un CD avec les extensions Rock Ridge du répertoire source cd_dir où tous les fichiers ont au moins la permission de lecture et où tous les fichiers appartiennent à root, appelez :

% mkisofs -o cd.iso -r cd_dir

Pour écrire une archive tar directement sur un CD qui contiendra plus tard un simple système de fichiers ISO-9660 avec l'archive tar, appelez :

% star -c . | mkisofs -stream-media-size 333000 | \
cdrecord dev=b,t,l -dao tsize=333000s -

Pour créer un CD hybride HFS avec les extensions Joliet et Rock Ridge du répertoire source cd_dir :

% mkisofs -o cd.iso -R -J -hfs cd_dir

Pour créer un CD hybride HFS à partir du répertoire source cd_dir qui contient des fichiers Netatalk Apple/Unix :

% mkisofs -o cd.iso --netatalk cd_dir

Pour créer un CD hybride HFS à partir du répertoire source cd_dir, en donnant à tous les fichiers un CRÉATEUR et un TYPE basés uniquement sur leurs extensions de nom de fichier listées dans le fichier « mapping » :

% mkisofs -o cd.iso -map mapping cd_dir

Pour créer un CD avec les « Extensions Apple aux normes ISO-9660 », à partir des répertoires source cd_dir et another_dir. Les fichiers dans tous les formats Apple/Unix connus sont décodés et tous les autres fichiers reçoivent un CRÉATEUR et un TYPE basés sur leur nombre magique donné dans le fichier « magic » :

% mkisofs -o cd.iso -apple -magic magic -probe \
cd_dir another_dir

L'exemple suivant place différents fichiers sur le CD qui ont tous le nom README, mais ont un contenu différent lorsqu'ils sont vus comme un CD ISO-9660/RockRidge, Joliet ou HFS.

Le répertoire actuel contient :

% ls -F
README.hfs README.joliet README.unix cd_dir/

La commande suivante place le contenu du répertoire cd_dir sur le CD ainsi que les trois fichiers README - mais un seul sera vu à partir de chacun des trois systèmes de fichiers :

% mkisofs -o cd.iso -hfs -J -r -graft-points \
-hide README.hfs -hide README.joliet \
-hide-joliet README.hfs -hide-joliet README.unix \
-hide-hfs README.joliet -hide-hfs README.unix \
README=README.hfs README=README.joliet \ < br/> README=README.unix cd_dir

c'est-à-dire que le fichier README.hfs sera vu comme README sur le CD HFS et que les deux autres fichiers README seront cachés. Idem pour les CD Joliet et ISO-9660/RockRidge.

Il est probable que toutes sortes de résultats étranges soient possibles avec des combinaisons des options de masquage...

Pour créer un DVD-Audio à partir du répertoire source conforme DVD-Audio DVD :

% mkisofs -o dvda.iso -dvd-audio DVD

NOTES

Mkisofs peut être installé en toute sécurité en tant que suid root. Ceci peut être nécessaire pour permettre à mkisofs de lire la session précédente lors de la création d'une image multi-sessions.

mkisofs n'est pas basé sur les outils standard mk*fs pour Unix, car nous devons générer une copie complète d'un système de fichiers existant sur un disque dans le système de fichiers ISO-9660. Le nom mkisofs est probablement un peu trompeur, car il ne fait pas seulement que créer le système de fichiers, il le peuple également. Cependant, le nom d'outil approprié pour un outil UNIX qui crée des systèmes de fichiers peuplés - mkproto - n'est pas bien connu.

Si mkisofs crée une image de système de fichiers avec des attributs Rock Ridge et que le niveau d'imbrication des répertoires de l'arborescence source est trop élevé pour ISO-9660, mkisofs effectuera une relocalisation de répertoire en profondeur. Cela se traduit par un répertoire appelé RR_MOVED dans le répertoire racine du CD. Vous ne pouvez pas éviter ce répertoire dans l'arborescence visible avec ISO-9660, mais il est automatiquement caché dans l'arborescence Rock Ridge.

Le support de démarrage sparc implémenté avec les options -sparc-boot suit entièrement les exigences officielles de démarrage de CD Sparc du PROM de démarrage des systèmes Sun Sparc. Certaines distributions Linux pour systèmes Sparc utilisent un chargeur de démarrage appelé SILO qui n'est malheureusement pas conforme au démarrage de CD Sparc. Il est agaçant de constater que les auteurs de SILO ne corrigent pas SILO mais fournissent plutôt un "patch" complètement inutile à mkisofs qui incorpore beaucoup plus de code source que ce qui serait nécessaire pour la correction de SILO.

BOGUES

•
Ne lit pas correctement les répertoires relocalisés en mode multi-session lors de l'ajout de données.

Tout répertoire profond relocalisé est perdu si la nouvelle session n'inclut pas le répertoire profond.

Répéter en créant d'abord une session avec relocalisation de répertoire profond, puis en ajoutant une nouvelle session avec un seul répertoire différent de l'ancien chemin profond.

•
Ne réutilise pas RR_MOVED lors de la création de multi-sessions à partir de TRANS.TBL

Il peut y en avoir d'autres. Veuillez les signaler à l'auteur.

PROBLEMES/LIMITATIONS HFS

J'ai dû faire plusieurs suppositions sur la façon dont j'attendais que les routines libhfs modifiées fonctionnent, cependant, il peut y avoir des situations auxquelles je n'ai pas pensé, ou que j'ai rencontrées lorsque ces suppositions échouent. Par conséquent, je ne peux pas garantir que mkisofs fonctionnera comme prévu (bien que je n'aie pas encore eu de problème majeur). La plupart des fonctionnalités HFS fonctionnent bien, cependant, certaines ne sont pas entièrement testées. Elles sont marquées comme Alpha ci-dessus.

Bien que les noms de fichiers HFS semblent prendre en charge les lettres majuscules et minuscules, le système de fichiers ne fait pas la distinction entre majuscules et minuscules. C'est-à-dire que les noms de fichiers "aBc" et "AbC" sont identiques. Si un fichier est trouvé dans un répertoire portant le même nom HFS, alors mkisofs tentera, dans la mesure du possible, de créer un nom unique en ajoutant des caractères '_' à l'un des noms de fichiers.

Les fichiers/répertoires HFS partageant les 31 premiers caractères ont _N' (N == nombre décimal) substitué aux derniers caractères pour générer des noms uniques.

Il faut faire attention lors de "l'insertion" de fichiers ou répertoires Apple/Unix (voir ci-dessus pour la méthode et la syntaxe). Il n'est pas possible d'utiliser un nouveau nom pour un fichier/répertoire codé Apple/Unix. Par exemple, si un fichier codé Apple/Unix appelé "anciennom" doit être ajouté au CD, vous ne pouvez pas utiliser la ligne de commande :

mkisofs -o output.raw -hfs -graft-points nouveau nom=anciennom cd_dir

mkisofs ne pourra pas décoder "anciennom". Cependant, vous pouvez insérer des fichiers ou répertoires codés Apple/Unix tant que vous n'essayez pas de leur donner de nouveaux noms comme ci-dessus.

Lors de la création d'un volume HFS avec les options de multi-session, -M et -C, seuls les fichiers de la dernière session seront présents dans le volume HFS. C'est-à-dire que mkisofs ne peut pas ajouter de fichiers existants de sessions précédentes au volume HFS.

Cependant, si chaque session est créée avec l'option -part, alors chaque session apparaîtra comme un volume distinct lorsqu'elle sera montée sur un Mac. Dans ce cas, il est utile d'utiliser l'option -V ou -hfs-volid pour donner à chaque session un nom de volume unique, sinon chaque "volume" apparaîtra sur le bureau avec le même nom.

Les liens symboliques (comme tous les autres fichiers non réguliers) ne sont pas ajoutés au répertoire HFS.

Les volumes hybrides peuvent être plus volumineux que les volumes ISO-9660 purs contenant les mêmes données. Dans certains cas (par exemple, les volumes de taille DVD), le volume hybride peut être considérablement plus grand. À mesure qu'un volume HFS grossit, la taille du bloc d'allocation (la plus petite quantité d'espace qu'un fichier peut occuper) augmente également. Pour un CD de 650 Mo, le bloc d'allocation est de 10 Ko, pour un DVD de 4,7 Go, il sera d'environ 70 Ko.

Le nombre maximum de fichiers dans un volume HFS est d'environ 65500 - bien que la limite réelle soit légèrement inférieure.

Le volume hybride résultant peut être accédé sur une machine Unix en utilisant les routines hfsutils. Cependant, aucune modification ne peut être apportée au volume car il est défini comme verrouillé. L'option -hfs-unlock créera une image de sortie déverrouillée - cependant, aucune modification ne doit être apportée au contenu du volume (sauf si vous savez vraiment ce que vous faites) car ce n'est pas un "vrai" volume HFS.

L'utilisation de l'option -mac-name ne fonctionnera actuellement pas avec l'option -T - le nom Unix sera utilisé dans le fichier TRANS.TBL, pas le nom Macintosh.

Bien que mkisofs ne modifie pas le contenu d'un fichier, si un fichier binaire a son TYPE défini sur 'TEXT', il peut être lu incorrectement sur un Macintosh. Par conséquent, un meilleur choix pour le TYPE par défaut peut être '????'

L'option -mac-boot-file peut ne pas fonctionner du tout...

Peut ne pas fonctionner avec les fichiers PC Exchange v2.2 ou supérieur (disponibles avec MacOS 8.1). Les supports DOS contenant des fichiers PC Exchange doivent être montés en tant que type msdos (pas vfat) lors de l'utilisation de Linux.

Le format SFM n'est que partiellement pris en charge - voir la section FORMATS DE FICHIERS HFS MACINTOSH ci-dessus.

Il n'est pas possible d'utiliser les options -sparc-boot ou -generic-boot avec les options -boot-hfs-file, -prep-boot ou -chrp-boot.

mkisofs devrait être capable de créer des images hybrides HFS de plus de 4 Go, bien que cela n'ait pas été entièrement testé.

STABILITE DE LINTERFACE

Les interfaces fournies par mkisofs sont conçues pour une stabilité à long terme. Comme mkisofs dépend des interfaces fournies par le système d'exploitation sous-jacent, la stabilité des interfaces offertes par mkisofs dépend de la stabilité des interfaces du système d'exploitation. Les interfaces modifiées dans le système d'exploitation peuvent nécessiter des interfaces modifiées dans mkisofs.
