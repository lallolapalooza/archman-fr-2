DESCRIPTION

mkosi est un outil pour construire facilement des images d'OS personnalisées. C'est un enveloppeur sophistiqué autour de dnf, apt, pacman et zypper qui peut générer des images disque avec un certain nombre de fonctionnalités supplémentaires.

Verbes de ligne de commande

Les verbes de ligne de commande suivants sont reconnus :

résumé
Affiche un résumé lisible par l'homme de toutes les options utilisées pour construire les images. Ceci analysera la ligne de commande et les fichiers de configuration, mais n'affichera que ce qui est configuré et ne construira ni n'exécutera quoi que ce soit.
afficher-config
Affiche les noms et le contenu de tous les fichiers de configuration chargés. mkosi charge un ensemble de fichiers à partir de différents emplacements et cette commande facilite la compréhension de ce qui est configuré où.
construire
Construit l'image en fonction des paramètres passés en ligne de commande et dans les fichiers de configuration. Cette commande est celle par défaut si aucun verbe n'est spécifié. Tous les arguments de ligne de commande spécifiés après le verbe seront passés directement au script de construction, s'il en est défini un.
shell
Ceci construit l'image si elle n'est pas encore construite, puis invoque systemd-nspawn pour exécuter un shell interactif dans l'image. Ceci ne nécessite pas de démarrer le système, c'est comme un chroot amélioré. Une ligne de commande optionnelle peut être spécifiée après le verbe shell, pour être invoquée à la place du shell dans le conteneur. Utilisez -f pour reconstruire inconditionnellement l'image avant d'acquérir le shell, voir ci-dessous. Cette commande doit être exécutée en tant que root.
démarrer
Similaire à shell, mais au lieu de lancer un shell, il démarre systemd dans l'image en utilisant systemd-nspawn. Une ligne de commande optionnelle peut être spécifiée après le verbe démarrer, qui peut contenir des options nspawn supplémentaires ainsi que des arguments qui sont passés comme la ligne de commande du noyau au système d'init dans l'image.
vm
Similaire à démarrer, mais utilise le moniteur de machine virtuelle configuré (par défaut qemu) pour démarrer l'image, c'est-à-dire qu'au lieu de la virtualisation de conteneur, la virtualisation de machine virtuelle est utilisée. La manière dont les arguments de ligne de commande supplémentaires sont interprétés dépend du moniteur de machine virtuelle configuré. Voir VirtualMachineMonitor= pour plus d'informations.
ssh
Lorsque l'image est construite avec l'option Ssh=yes, cette commande se connecte à une machine virtuelle démarrée via SSH. Assurez-vous d'exécuter mkosi ssh avec la même configuration que mkosi construire afin qu'elle dispose des informations nécessaires pour se connecter à la machine virtuelle en cours d'exécution via SSH. Plus précisément, la clé privée SSH du paramètre SshKey= est utilisée pour se connecter à la machine virtuelle. Utilisez mkosi générer-clé pour générer automatiquement une clé et un certificat qui seront récupérés par mkosi. Tous les arguments passés après le verbe ssh sont passés comme arguments à l'invocation de ssh. Pour vous connecter à un conteneur, utilisez machinectl login ou machinectl shell.

L'option Machine= peut être utilisée pour donner à la machine un nom d'hôte personnalisé lors de son démarrage, qui peut ensuite être utilisé pour se connecter en ssh à l'image (par exemple, mkosi --machine=mamachine démarrer puis mkosi --machine=mamachine ssh).

journalctl
Utilise journalctl pour inspecter le journal à l'intérieur de l'image. Tous les arguments spécifiés après le verbe journalctl sont ajoutés à l'invocation de journalctl.
coredumpctl
Utilise coredumpctl pour rechercher des coredumps dans l'image. Tous les arguments spécifiés après le verbe coredumpctl sont ajoutés à l'invocation de coredumpctl.
sysupdate
Invoque systemd-sysupdate avec l'option --transfer-source= définie sur le répertoire de sortie et l'option --definitions= définie sur le répertoire configuré avec SysupdateDirectory=. Tous les arguments spécifiés après le verbe sysupdate sont passés directement à l'invocation de systemd-sysupdate.
bac-à-sable
Exécute des commandes arbitraires à l'intérieur du même bac à sable utilisé pour exécuter d'autres verbes tels que démarrer, shell, vm et plus encore. Cela signifie que /usr sera remplacé par /usr de l'arborescence des outils si une est utilisée, tandis que tout le reste restera en place. Si aucune commande n'est fournie, $SHELL sera exécuté ou bash si $SHELL n'est pas défini.
nettoyer
Supprime les artefacts de construction générés lors d'une construction précédente. Si combiné avec -f, supprime également les images de cache de construction incrémentielle. Si -f est spécifié deux fois, supprime également tout cache de paquets.
servir
Ceci construit l'image si elle n'est pas encore construite, puis sert le répertoire de sortie (c'est-à-dire généralement mkosi.output/, voir ci-dessous) via un petit serveur HTTP intégré, écoutant sur le port 8081. Combinez avec -f pour reconstruire inconditionnellement l'image avant de la servir. Cette commande est utile pour tester l'acquisition basée sur le réseau d'images d'OS, par exemple via machinectl pull-raw ... et machinectl pull-tar ....
graver <périphérique>
Ceci construit l'image si elle n'est pas encore construite, puis l'écrit sur le périphérique bloc spécifié. Le contenu des partitions est écrit tel quel, mais la table de partitions GPT est corrigée pour correspondre à la taille du secteur et du disque du support spécifié.
augmenter
Augmente la version de l'image à partir de s

VERBS

The following verbs are supported:

bump
Increases the version number stored in mkosi.version. It can also be used to write an initial version number if mkosi.version does not exist. This verb bumps the file mkosi.version and writes the resulting version string to mkosi.version. This is useful for implementing a simple versioning scheme: each time this verb is called the version is bumped in preparation for the subsequent build. Note that --auto-bump/-B may be used to automatically bump the version after each successful build.
genkey
Generate a pair of SecureBoot keys for usage with the SecureBootKey=/--secure-boot-key= and SecureBootCertificate=/--secure-boot-certificate= options.
documentation
Show mkosi’s documentation. If no argument is given, the mkosi man page is shown, but the arguments mkosi, mkosi-initrd, initrd, mkosi-sandbox, sandbox, mkosi.news and news are supported and respectively show the man pages for mkosi, mkosi-initrd, mkosi-sandbox and mkosi’s NEWS file.

By default this verb will try several ways to output the documentation, but a specific option can be chosen with the --doc-format option. Distro packagers are encouraged to add a file mkosi.1 into the mkosi/resources directory of the Python package, if it is missing, as well as to install it in the appropriate search path for man pages. The man page can be generated from the markdown file mkosi/resources/man/mkosi.1.md e.g via pandoc -t man -s -o mkosi.1 mkosi.1.md.

completion
Generate shell completion for the shell given as argument and print it to stdout. The arguments bash, fish, and zsh are understood.
dependencies
Output the list of packages required by mkosi to build and boot images.

This list can be piped directly to a package manager to install the packages. For example, if the host system uses the dnf package manager, the packages could be installed as follows:

mkosi dependencies | xargs -d '\n' dnf install
help
This verb is equivalent to the --help switch documented below: it shows a brief usage explanation.

Commandline-only Options

Those settings cannot be configured in the configuration files.

--force, -f
Replace the output file if it already exists, when building an image. By default when building an image and an output artifact already exists mkosi will refuse operation. Specify this option once to delete all build artifacts from a previous run before re-building the image. If incremental builds are enabled, specifying this option twice will ensure the intermediary cache files are removed, too, before the re-build is initiated. If a package cache is used (also see the Files section below), specifying this option thrice will ensure the package cache is removed too, before the re-build is initiated. For the clean operation this option has a slightly different effect: by default the verb will only remove build artifacts from a previous run, when specified once the incremental cache files are deleted too, and when specified twice the package cache is also removed.
--directory=, -C
Takes a path to a directory. mkosi switches to this directory before doing anything. Note that the various configuration files are searched for in this directory, hence using this option is an effective way to build a project located in a specific directory.
--debug
Enable additional debugging output.
--debug-shell
When executing a command in the image fails, mkosi will start an interactive shell in the image allowing further debugging.
--debug-workspace
When specified, the workspace directory will not be deleted and its location will be logged when mkosi exits.
--debug-sandbox
Run mkosi-sandbox with strace.
--version
Show package version.
--help, -h
Show brief usage information.
--genkey-common-name=
Common name to be used when generating keys via mkosi’s genkey command. Defaults to mkosi of %u, where %u expands to the username of the user invoking mkosi.
--genkey-valid-days=
Number of days that the keys should remain valid when generating keys via mkosi’s genkey command. Defaults to two years (730 days).
--auto-bump=, -B
If specified, after each successful build the version is bumped in a fashion equivalent to the bump verb, in preparation for the next build. This is useful for simple, linear version management: each build in a series will have a version number one higher then the previous one.
--doc-format
The format to show the documentation in. Supports the values markdown, man, pandoc, system and auto. In the case of markdown the documentation is shown in the original Markdown format. man shows the documentation in man page format, if it is available. pandoc will generate the man page format on the fly, if pandoc is available. system will show the system-wide man page for mkosi, which may or may not correspond to the version you are using, depending on how you installed mkosi. auto, which is the default, will try all methods in the order man, pandoc, markdown, system.
--json
Show the summary output as JSON-SEQ.
--wipe-build-dir, -w
Wipe the build directory if one is configured before building the image.

Supported output formats

The following output formats are supported:

•
Raw GPT disk image, created using systemd-repart (disk)
•
Plain directory, containing the OS tree (directory)
•
Tar archive (tar)
•
CPIO archive (cpio)

The output format may also be set to none to have mkosi produce no image at all. This can be useful if you only want to use the image to produce another output in the build scripts (e.g. build an RPM).

When a GPT disk image is created, repart partition definition files may be placed in mkosi.repart/ to configure the generated disk image.

It is highly recommended to run mkosi on a file system that supports reflinks such as XFS and btrfs and to keep all related directories on the same file system. This allows mkosi to create images very quickly by using reflinks to perform copying via copy-on-write operations.

Configuration Settings

The following settings can be set through configuration files (the syntax with SomeSetting=value) and on the command line (the syntax with --some-setting=value). For some command line parameters, a single-letter shortcut is also allowed. In the configuration files, the setting must be in the appropriate section, so the settings are grouped by section below.

Configuration is parsed in the following order:

•
The command line arguments are parsed.
•
mkosi.local.conf or mkosi.local is parsed if it exists. This file or directory should be in .gitignore (or equivalent) and is intended for local configuration.
•
Any default paths (depending on the option) are configured if the corresponding path exists.
•
mkosi.conf is parsed if it exists in the directory configured with --directory= or the current working directory if --directory= is not used.
•
mkosi.conf.d/ is parsed in the same directory if it exists. Each directory and each file with the .conf extension in mkosi.conf.d/ is parsed. Any directory in mkosi.conf.d is parsed as if it were a regular top level dir
ectory.
•
Si des profils sont configurés, leur configuration est analysée à partir du répertoire mkosi.profiles/.
•
Les sous-images sont analysées à partir du répertoire mkosi.images s'il existe.

Notez que les paramètres configurés via la ligne de commande remplacent toujours les paramètres configurés via les fichiers de configuration. Si le même paramètre est configuré plus d'une fois via des fichiers de configuration, les affectations ultérieures remplacent les affectations antérieures, sauf pour les paramètres qui acceptent une collection de valeurs. De plus, les paramètres lus à partir de mkosi.local ou mkosi.local.conf remplacent les paramètres des fichiers de configuration analysés ultérieurement, mais pas les paramètres spécifiés sur la ligne de commande.

Pour les paramètres qui acceptent une valeur unique, l'affectation vide (SomeSetting= ou --some-setting=) peut être utilisée pour remplacer un paramètre précédent et le réinitialiser à la valeur par défaut.

Les paramètres qui acceptent une collection de valeurs sont fusionnés en ajoutant les nouvelles valeurs aux valeurs précédemment configurées. Affecter une chaîne vide à un tel paramètre supprime toutes les valeurs précédemment affectées et remplace également toutes les valeurs par défaut configurées. Les valeurs spécifiées sur la ligne de commande sont ajoutées après toutes les valeurs des fichiers de configuration.

Pour inclure conditionnellement des fichiers de configuration, la section [Match] peut être utilisée. Une section [Match] se compose de conditions individuelles. Les conditions peuvent utiliser un symbole pipe (|) après le signe égal (...=|...), ce qui fait de la condition une condition de déclenchement. Le fichier de configuration sera inclus si le ET logique de toutes les conditions non déclenchantes et le OU logique de toutes les conditions déclenchantes est satisfait. Pour nier le résultat d'une condition, préfixez l'argument avec un point d'exclamation. Si un argument est préfixé par le symbole pipe et un point d'exclamation, le symbole pipe doit être passé en premier, et le point d'exclamation ensuite.

Notez que les conditions [Match] sont comparées aux valeurs actuelles de paramètres spécifiques et ne prennent pas en compte les modifications apportées au paramètre dans les fichiers de configuration qui n'ont pas encore été analysés (les paramètres spécifiés sur la ligne de commande sont pris en compte). Notez également que la correspondance avec un paramètre, puis la modification de sa valeur ultérieurement dans un autre fichier de configuration peut entraîner des résultats inattendus.

La section [Match] d'un fichier mkosi.conf dans un répertoire s'applique à l'ensemble du répertoire. Si les conditions ne sont pas satisfaites, le répertoire entier est ignoré. Les sections [Match] des fichiers dans mkosi.conf.d/ et mkosi.local.conf ne s'appliquent qu'au fichier lui-même.

S'il existe plusieurs sections [Match] dans le même fichier de configuration, chacune d'elles doit être satisfaite pour que le fichier de configuration soit inclus. Plus précisément, les conditions de déclenchement ne s'appliquent qu'à la section [Match] actuelle et sont réinitialisées entre plusieurs sections [Match]. Par exemple, ce qui suit ne correspondra que si le format de sortie est l'un de disk ou directory et que l'architecture est l'un de x86-64 ou arm64:

[Match]
Format=|disk
Format=|directory
[Match]
Architecture=|x86-64
Architecture=|arm64

La section [TriggerMatch] peut être utilisée pour indiquer des sections de correspondance déclenchante. Celles-ci sont identiques aux conditions de déclenchement, sauf qu'elles s'appliquent à l'ensemble de la section de correspondance au lieu d'une seule condition. Par exemple, ce qui suit correspondra si la distribution est debian et la version est bookworm, ou si la distribution est ubuntu et la version est noble.

[TriggerMatch]
Distribution=debian
Release=bookworm
[TriggerMatch]
Distribution=ubuntu
Release=noble

La sémantique des conditions dans les sections [TriggerMatch] est la même que dans les sections [Match], c'est-à-dire que toutes les conditions normales sont jointes par un ET logique et toutes les conditions de déclenchement sont jointes par un OU logique. Lors du mélange des sections [Match] et [TriggerMatch], une correspondance est obtenue lorsque toutes les sections [Match] correspondent et qu'au moins une section [TriggerMatch] correspond. L'absence de sections de correspondance est considérée comme vraie. Logiquement, cela signifie :

(⋀ᵢ Matchᵢ) ∧ (⋁ᵢ TriggerMatchᵢ)

Les options de ligne de commande qui ne prennent pas d'argument sont affichées sans = dans leur version longue. Dans les fichiers de configuration, elles doivent être spécifiées avec un argument booléen : soit 1, yes, ou true pour activer, soit 0, no, false pour désactiver.

Section [Distribution]

Distribution=, --distribution=, -d
La distribution à installer dans l'image. Prend l'un des arguments suivants : fedora, debian, kali, ubuntu, arch, opensuse, mageia, centos, rhel, rhel-ubi, openmandriva, rocky, alma, azure ou custom. Si non spécifié, utilise par défaut la distribution de l'hôte ou custom si la distribution de l'hôte n'est pas une distribution prise en charge.
Release=, --release=, -r
La version de la distribution à installer dans l'image. La syntaxe précise de l'argument qu'elle prend dépend de la distribution utilisée, et il s'agit soit d'une chaîne numérique (dans le cas de Fedora Linux, CentOS, ..., par exemple 29), soit d'un nom de version de distribution (dans le cas de Debian, Kali, Ubuntu, ..., par exemple artful). Par défaut, une version récente de la distribution choisie, ou la version de la distribution s'exécutant sur l'hôte si elle correspond à la distribution configurée.
Architecture=, --architecture=
L'architecture pour laquelle construire l'image. Les architectures réellement prises en charge dépendent de la distribution utilisée et si une image amorçable est demandée ou non. Lors de la construction pour une architecture étrangère, vous devrez également installer et enregistrer un émulateur en mode utilisateur pour cette architecture.

L'une des architectures suivantes peut être spécifiée par image construite : alpha, arc, arm, arm64, ia64, loongarch64, mips64-le, mips-le, parisc, ppc, ppc64, ppc64-le, riscv32, riscv64, s390, s390x, tilegx, x86, x86-64.

Mirror=, --mirror=, -m
Le miroir à utiliser pour télécharger les paquets de la distribution. Attend une URL de miroir comme argument. S'il n'est pas fourni, le miroir par défaut pour la distribution est utilisé.

Les miroirs par défaut pour chaque distribution sont les suivants (sauf indication contraire, le même miroir est utilisé pour toutes les architectures) :

x86-64 aarch64
debian http://deb.debian.org/debian
arch https://geo.mirror.pkgbuild.com http://mirror.archlinuxarm.org
opensuse http://download.opensuse.org
kali http://http.kali.org/kali
ubuntu http://archive.ubuntu.com http://ports.ubuntu.com
centos https://mirrors.centos.org
rocky https://mirrors.rockylinux.org
alma https://mirrors.almalinux.org
fedora https://mirrors.fedoraproject.org
rhel-ubi https://cdn-ubi.redhat.com
mageia https://www.mageia.org
openmandriva http://mirrors.openmandriva.org
azure https://packages.microsoft.com/
LocalMirror=, --local-mirror=
Le miroir sera utilisé comme un miroir local, simple et direct, au lieu de l'utiliser comme préfixe pour l'ensemble complet de dépôts normalement pris en charge par les distributions. Utile pour les constructions entièrement hors ligne avec un seul dépôt. Pris en charge sur les distributions basées sur deb, rpm et pacman. Remplace --mirror= mais uniquement pour la construction mkosi locale, il ne sera pas configuré dans l'image finale, --mirror= (ou le dépôt par défaut) sera configuré dans l'image finale à la place.
RepositoryKeyCheck=, --repository-key-check=
Contrôle les vérifications de signature/clé lors de l'utilisation de dépôts, activées par défaut. Utile pour désactiver les vérifications lorsqu'elles sont combinées avec --local-mirror= et en utilisant uniquement un dépôt d'un système de fichiers local.
RepositoryKeyFetch=, --repository-key-fetch=
Contrôle si mkosi récupérera les clés GPG de distribution à distance. Activé par défaut sur Ubuntu lorsqu'un arbre d'outils n'est pas utilisé ou lorsqu'un arbre d'outils Ubuntu est utilisé pour construire des distributions Arch Linux ou basées sur RPM. Désactivé par défaut sur toutes les autres distributions. Lorsqu'il est désactivé, les clés GPG de distribution pour la distribution cible doivent être installées localement sur le système hôte, aux côtés du gestionnaire de paquets pour cette distribution.

Ce paramètre n'est implémenté que pour les distributions utilisant dnf, pacman ou zypper comme gestionnaire de paquets. Pour les autres distributions, les clés GPG de distribution sont toujours recherchées localement, quelle que soit la valeur de ce paramètre. Pour rendre les clés GPG de distribution disponibles sans activer ce paramètre, le paquet correspondant doit être installé sur l'hôte. Il s'agit généralement de archlinux-keyring, debian-keyring, kali-archive-keyring, ubuntu-keyring ou distribution-gpg-keys (pour les distributions basées sur RPM).

Repositories=, --repositories=
Active les dépôts de paquets qui sont désactivés par défaut. Cela peut être utilisé pour activer les dépôts EPEL pour CentOS ou différents composants des dépôts Debian/Kali/Ubuntu.

[Sortie] Section

Format=, --format=, -t
Le type de format d'image à générer. L'un des formats suivants : directory (pour générer une image OS directement dans un répertoire local), tar (similaire, mais une archive tar de l'image OS est générée), cpio (similaire, mais une archive cpio est générée), disk (une image OS sur un périphérique bloc avec une table de partitions GPT), uki (une image noyau unifiée avec l'image OS dans la section PE .initrd), esp (uki mais encapsulé dans une image disque avec seulement une partition ESP), oci (un répertoire compatible avec la spécification d'image OCI), sysext, confext, portable, addon ou none (l'image OS est uniquement destinée à être une image de construction pour produire un autre artefact).

Si le format de sortie disk est utilisé, l'image disque est générée à l'aide de systemd-repart. Les fichiers de définition de partitions de réparation à utiliser peuvent être configurés à l'aide du paramètre RepartDirectories= ou via mkosi.repart/. Lorsque des partitions de vérification (verity) sont configurées à l'aide du paramètre Verity= de systemd-repart, mkosi analysera automatiquement le roothash de la partition de hachage de vérification à partir de la sortie JSON de systemd-repart et l'inclura dans la ligne de commande du noyau de toutes les images noyau unifiées construites par mkosi.

Si le format de sortie none est utilisé, les sorties d'une construction précédente ne sont pas supprimées, mais les scripts de nettoyage (voir CleanScripts=) sont toujours exécutés. Cela permet de relancer un script de construction (voir BuildScripts=) sans supprimer les résultats d'une construction précédente.

ManifestFormat=, --manifest-format=
Le(s) type(s) de format de manifeste à générer. Une liste délimitée par des virgules composée de json (le format de sortie JSON standard qui décrit les paquets installés), changelog (un format texte lisible par l'homme conçu pour la comparaison). Par défaut, aucun manifeste n'est généré.
Output=, --output=, -o
Nom à utiliser pour le fichier ou répertoire d'image de sortie généré. Par défaut, il s'agit de image ou, si ImageId= est spécifié, il est utilisé comme nom de sortie par défaut, éventuellement suffixé par la version définie avec ImageVersion= ou si une image spécifique est construite à partir de mkosi.images, le nom de l'image est préféré à ImageId. Notez que cette option ne permet pas de configurer le répertoire de sortie, utilisez OutputDirectory= pour cela.

Notez que cela ne spécifie que le préfixe de sortie, en fonction du format de sortie spécifique, de la compression et de la version d'image utilisés, le nom de sortie complet pourrait être image_7.8.raw.xz.

CompressOutput=, --compress-output=
Configure la compression pour l'image ou l'archive résultante. L'argument peut être un booléen ou un algorithme de compression (xz, zstd). La compression zstd est utilisée par défaut, à l'exception de CentOS et de ses dérivés jusqu'à la version 8, qui utilisent xz par défaut, et des images OCI, qui utilisent gzip par défaut. Notez que lorsqu'elle est appliquée aux types d'images de périphériques blocs, la compression signifie que l'image ne peut pas être démarrée directement mais doit être décompressée au préalable. Cela signifie également que les verbes shell, boot, vm ne sont pas disponibles lorsque cette option est utilisée. Implicite pour tar, cpio, uki, esp, oci et addon.
CompressLevel=, --compress-level=
Configure le niveau de compression à utiliser. Prend un entier. Les valeurs possibles dépendent de la compression utilisée.
OutputDirectory=, --output-directory=, -O
Chemin d'accès à un répertoire où placer tous les artefacts générés. Si ce n'est pas spécifié et que le répertoire mkosi.output/ existe dans le répertoire local, il est automatiquement utilisé à cette fin.
OutputMode=, --output-mode=
Mode d'accès au système de fichiers utilisé lors de la création du fichier d'image de sortie. Prend un mode d'accès en notation octale. S'il n'est pas défini, utilise les paramètres par défaut du système actuel.
ImageVersion=, --image-version=
Configure la version de l'image. Accepte toute chaîne de caractères, mais il est recommandé de spécifier une série de composants séparés par des points. La version peut également être configurée en lisant un fichier mkosi.version (auquel cas elle peut être gérée facilement via le verbe bump ou l'option --auto-bump) ou en lisant la sortie standard si elle est exécutable (voir la section Scripts ci-dessous). Lorsqu'elle est spécifiée, la version de l'image est incluse dans le nom de fichier de sortie par défaut, c'est-à-dire au lieu de image.raw, la valeur par défaut sera image_0.1.raw pour la version 0.1 de l'image, et ainsi de suite. La version est également transmise via la variable $IMAGE_VERSION à tous les scripts de construction invoqués (ce qui peut être utile pour la patcher dans /usr/lib/os-release ou similaire, en particulier le champ IMAGE_VERSION= de celui-ci).

partition et noyau unifié. Par défaut, uki, kernel et initrd sont séparés.

Packages=, --package=, -p
Installe les paquets de distribution spécifiés (c'est-à-dire RPM, deb, ...) dans l'image. Prend une liste de spécifications de paquets séparés par des virgules. Cette option peut être utilisée plusieurs fois, auquel cas les listes de paquets spécifiées sont combinées. Utilisez BuildPackages= pour spécifier les paquets qui doivent uniquement être installés dans une surcouche montée lors de l'exécution des scripts de préparation avec l'argument build et lors de l'exécution des scripts de build.

Les types et la syntaxe des spécifications de paquets autorisées dépendent du gestionnaire de paquets (par exemple, dnf pour les distributions basées sur RPM ou apt pour les distributions basées sur deb), mais peuvent inclure des noms de paquets, des noms de paquets avec version et/ou architecture, des jokers de noms de paquets, des groupes de paquets et des fournitures virtuelles, y compris des chemins de fichiers.

Voir PackageDirectories= pour des informations sur la façon de rendre les paquets locaux disponibles pour l'installation avec Packages=.

Exemple : lors de l'utilisation d'une distribution qui utilise dnf, la configuration suivante installerait le paquet meson (dans la dernière version), la version 32 bits du paquet libfdisk-devel, tous les paquets disponibles commençant par le préfixe git-, un RPM systemd du système de fichiers local, l'un des paquets qui fournit /usr/bin/ld, les paquets du groupe Outils de Développement, et le paquet qui contient le module python mypy.

Packages=meson
         libfdisk-devel.i686
         git-*
         /usr/bin/ld
         @development-tools
         python3dist(mypy)

Cette option doit être utilisée pour lister les paquets contenant les fichiers d'en-tête, les compilateurs, les systèmes de build, les linkers et autres outils de build dont les scripts mkosi.build ont besoin pour fonctionner. VolatilePackages=, --volatile-package=

PackageDirectories=, --package-directory=
Spécifie les répertoires contenant des paquets supplémentaires à rendre disponibles pendant le build. mkosi créera un dépôt local contenant tous les paquets dans ces répertoires et le rendra disponible lors de l'installation de paquets ou de l'exécution de scripts. Si le répertoire mkosi.packages/ est trouvé dans le répertoire local, il est également utilisé à cette fin.

BaseTrees=, --base-tree=

Au lieu d'un répertoire, un fichier tar ou une image disque peut être fourni. Dans ce cas, il est décompressé dans l'arbre du système d'exploitation. SkeletonTrees=, --skeleton-tree=
Prend une liste de paires de chemins séparés par des deux-points. Utilisez ceci pour insérer des fichiers et des répertoires dans l'arbre du système d'exploitation avant que le gestionnaire de paquets n'installe des paquets. Comme avec la logique de l'arbre de base ci-dessus, au lieu d'un répertoire, un fichier tar peut également être fourni. mkosi.skeleton.tar sera automatiquement utilisé s'il est trouvé dans le répertoire local.

Bootable=, --bootable=
Prend une valeur booléenne ou auto. Active ou désactive la génération d'une image amorçable. Si activé, mkosi installera un chargeur de démarrage EFI et ajoutera une partition ESP lorsque la sortie d'image disque est utilisée. Si le chargeur de démarrage EFI sélectionné (voir Bootloader=) n'est pas installé ou si aucun noyau n'est trouvé, la compilation échouera. auto se comporte comme si l'option était activée, mais la compilation ne réussira pas si aucun noyau ou le chargeur de démarrage EFI sélectionné ne peuvent être trouvés. Si désactivé, aucun chargeur de démarrage ne sera installé, même s'il est trouvé dans l'image, aucune image de noyau unifiée ne sera générée et aucune partition ESP ne sera ajoutée à l'image si le format de sortie disque est utilisé.
Bootloader=, --bootloader=
Prend l'une des valeurs none, systemd-boot, uki, grub, systemd-boot-signed, uki-signed ou grub-signed. Par défaut, il s'agit de systemd-boot. Si défini sur none, aucun chargeur de démarrage EFI ne sera installé dans l'image. Si défini sur systemd-boot, systemd-boot sera installé et pour chaque noyau installé, un UKI sera généré et stocké dans EFI/Linux dans l'ESP. Si défini sur uki, un seul UKI sera généré pour le dernier noyau installé (celui avec la version la plus élevée) qui sera installé dans EFI/BOOT/BOOTX64.EFI dans l'ESP. Si défini sur grub, pour chaque noyau installé, un UKI sera généré et stocké dans EFI/Linux dans l'ESP. Pour chaque UKI généré, une entrée de menu est ajoutée à la configuration grub dans grub/grub.cfg dans l'ESP qui lance l'UKI. Un fichier grub.cfg de shim est également écrit dans EFI/<distribution>/grub.cfg dans l'ESP qui charge grub/grub.cfg dans l'ESP pour la compatibilité avec les versions signées de grub qui chargent la configuration grub à partir de cet emplacement.

Les variantes signed installeront uniquement des binaires EFI pré-signés expédiés par la distribution.

Les noyaux doivent être placés dans le système de fichiers racine (par exemple, en utilisant ExtraTrees=) sous /usr/lib/modules/$version, nommés vmlinux ou vmlinuz. Le $version est tel qu'il est produit par la cible kernelversion de `make` de Kbuild.

BiosBootloader=, --bios-bootloader=
Prend l'une des valeurs none ou grub. Par défaut, il s'agit de none. Si défini sur none, aucun chargeur de démarrage BIOS ne sera installé. Si défini sur grub, grub sera installé comme chargeur de démarrage BIOS si une image amorçable est demandée avec l'option Bootable=. Si aucun fichier de définition de partition repart n'est configuré, mkosi ajoutera une partition de démarrage BIOS grub et une partition système EFI aux fichiers de définition de partition par défaut.

Notez que cette option n'est pas mutuellement exclusive avec Bootloader=. Il est possible d'avoir une image qui est à la fois amorçable sur UEFI et BIOS en configurant à la fois Bootloader= et BiosBootloader=.

La partition de démarrage BIOS grub doit avoir l'UUID 21686148-6449-6e6f-744e-656564454649 et doit être d'au moins 1 Mo.

Même si aucun chargeur de démarrage EFI n'est installé, nous avons toujours besoin d'une ESP pour le démarrage BIOS, car c'est là que nous stockons le noyau, l'initrd et les modules grub.

ShimBootloader=, --shim-bootloader=
Prend l'une des valeurs none, unsigned, ou signed. Par défaut, il s'agit de none. Si défini sur none, shim et MokManager ne seront pas installés dans l'ESP. Si défini sur unsigned, mkosi recherchera des binaires EFI shim et MokManager non signés et les installera. Si SecureBoot= est activé, mkosi signera les binaires EFI non signés avant de les installer. Si défini sur signed, mkosi recherchera des binaires EFI signés et les installera. Même si SecureBoot= est activé, mkosi ne signera pas ces binaires à nouveau.

Notez que cette option ne prend effet que lorsqu'une image amorçable sur firmware UEFI est demandée à l'aide d'autres options (Bootable=, Bootloader=).

Notez que lorsque cette option est activée, mkosi n'installera que des binaires de chargeur de démarrage signés, des fichiers d'image noyau et des images de noyau unifiées signés, car les binaires auto-signés ne seraient pas acceptés par la version signée de shim.

UnifiedKernelImages=, --unified-kernel-images=
Spécifie si les images de noyau unifiées doivent être utilisées ou non lorsque Bootloader= est défini sur systemd-boot ou grub. Accepte une valeur booléenne ou auto. La valeur par défaut est auto. Si activé, les images de noyau unifiées sont toujours utilisées et la compilation échouera si des composants nécessaires à la construction des images de noyau unifiées sont manquants. Si défini sur auto, les images de noyau unifiées seront utilisées si tous les composants nécessaires sont disponibles. Sinon, les entrées de Type 1 définies par la spécification du chargeur de démarrage seront utilisées à la place. Si désactivé, les entrées de Type 1 seront toujours utilisées.

KernelModulesInclude=, --kernel-modules-include=

KernelModulesInitrdExclude=, --kernel-modules-initrd-exclude=

Utilise mkosi.env s'il est trouvé dans le répertoire local. Les variables sont d'abord lues à partir de mkosi.env s'il existe, puis à partir de la liste fournie de fichiers, et enfin à partir des paramètres Environment=.
WithTests=, --without-tests, -T
Si défini sur faux (ou lorsque l'option de ligne de commande est utilisée), la variable d'environnement $WITH_TESTS est définie sur 0 lors de l'invocation des scripts mkosi.build. Ceci est censé être utilisé par les scripts de construction pour contourner les tests unitaires ou d'intégration qui sont normalement exécutés pendant le processus de construction des sources. Notez que cette option n'a aucun effet à moins que les scripts de construction mkosi.build ne la respectent.
WithNetwork=, --with-network=
Lorsque défini sur vrai, active la connectivité réseau pendant l'invocation des scripts de construction mkosi.build. Par défaut, les scripts de construction s'exécutent avec le réseau désactivé. La variable d'environnement $WITH_NETWORK est transmise aux scripts de construction mkosi.build indiquant si la construction est effectuée avec ou sans réseau.
ProxyUrl=, --proxy-url=
Configure un proxy à utiliser pour toutes les connexions réseau sortantes. Divers outils que mkosi invoque et pour lesquels le proxy peut être configuré sont configurés pour utiliser ce proxy. mkosi définit également diverses variables d'environnement bien connues pour spécifier le proxy à utiliser pour tous les programmes qu'il invoque et qui peuvent avoir besoin d'un accès Internet.
ProxyExclude=, --proxy-exclude=
Configure des noms d'hôtes pour lesquels les requêtes ne doivent pas passer par le proxy. Prend une liste de noms d'hôtes séparés par des virgules.
ProxyPeerCertificate=, --proxy-peer-certificate=
Configure un fichier contenant les certificats utilisés pour vérifier le proxy. Par défaut, utilise le magasin de certificats système.

Actuellement, la définition d'un certificat de pair proxy n'est prise en charge que lorsque dnf ou dnf5 est utilisé pour construire l'image.

ProxyClientCertificate=, --proxy-client-certificate=
Configure un fichier contenant le certificat utilisé pour authentifier le client auprès du proxy.

Actuellement, la définition d'un certificat client proxy n'est prise en charge que lorsque dnf ou dnf5 est utilisé pour construire l'image.

ProxyClientKey=, --proxy-client-key=
Configure un fichier contenant la clé privée utilisée pour authentifier le client auprès du proxy. Par défaut, utilise le certificat client proxy s'il est fourni.

Actuellement, la définition d'une clé client proxy n'est prise en charge que lorsque dnf ou dnf5 est utilisé pour construire l'image.

Section [Runtime] (anciennement connue sous le nom de section [Host])

NSpawnSettings=, --settings=
Spécifie un fichier de configuration .nspawn pour systemd-nspawn à utiliser dans les verbes boot et shell, et à placer à côté de l'image générée. Ceci est utile pour configurer l'environnement systemd-nspawn lorsque l'image est exécutée. Si ce paramètre n'est pas utilisé mais qu'un fichier mkosi.nspawn est trouvé dans le répertoire local, il est automatiquement utilisé à cet effet.
VirtualMachineMonitor=, --vmm=
Configure le moniteur de machine virtuelle à utiliser. Prend l'une des valeurs qemu ou vmspawn. Par défaut, utilise qemu.

Lorsque défini sur qemu, l'image est démarrée avec qemu. La plupart des formats de sortie peuvent être démarrés dans qemu. Tous les arguments spécifiés après le verbe sont ajoutés à l'invocation de qemu et interprétés comme des arguments de ligne de commande qemu supplémentaires.

Lorsque défini sur vmspawn, systemd-vmspawn est utilisé pour démarrer l'image. vmspawn ne prend en charge que les images de type disque et répertoire. Tous les arguments spécifiés après le verbe sont ajoutés à l'invocation de systemd-vmspawn et interprétés comme des options vmspawn supplémentaires et des arguments de ligne de commande noyau supplémentaires.

Console=, --console=
Configure la manière de configurer la console de la VM. Prend l'une des valeurs interactive, read-only, native, ou gui. Par défaut, utilise interactiveinteractive fournit une interface de terminal interactive à la VM. read-only est similaire, mais est strictement en lecture seule, c'est-à-dire qu'il n'accepte aucune entrée de l'utilisateur. native fournit également une interface basée sur TTY, mais utilise l'implémentation native de qemu (ce qui signifie que le moniteur qemu est disponible). gui affiche l'interface graphique qemu.
CPUs=, --cpus=
Configure le nombre de cœurs de processeur à attribuer à l'invité lors du démarrage d'une machine virtuelle. Par défaut, il est de 2.

Lorsqu'il est défini sur 0, le nombre de processeurs disponibles pour le processus mkosi sera utilisé.

RAM=, --ram=
Configure la quantité de RAM attribuée à l'invité lors du démarrage d'une machine virtuelle. Par défaut, il est de 2G.
KVM=, --kvm=
Configure si l'accélération KVM doit être utilisée lors du démarrage d'une machine virtuelle. Prend une valeur booléenne ou auto. Par défaut, il est de auto.
Vsock=, --vsock=
Configure si un vsock doit être provisionné lors du démarrage d'une machine virtuelle. Prend une valeur booléenne ou auto. Par défaut, il est de auto.
VsockConnectionId=, vsock-cid=
Configure l'identifiant de connexion vsock à utiliser lors du démarrage d'une machine virtuelle. Prend un nombre dans l'intervalle [3, 0xFFFFFFFF) ou hash ou auto. Par défaut, il est de auto. Lorsqu'il est défini sur hash, l'identifiant de connexion sera dérivé du chemin complet de l'image. Lorsqu'il est défini sur auto, mkosi essaiera de trouver automatiquement un identifiant de connexion libre. Sinon, le nombre fourni sera utilisé tel quel.
TPM=, --tpm=
Configure si un TPM virtuel doit être utilisé lors du démarrage d'une machine virtuelle. Prend une valeur booléenne ou auto. Par défaut, il est de auto.
CDROM=, --cdrom=
Configure si l'image doit être attachée en tant que périphérique CD-ROM lors du démarrage d'une machine virtuelle. Prend une valeur booléenne. Par défaut, il est de no.
Removable=, --removable=
Configure si l'image doit être attachée en tant que périphérique amovible lors du démarrage d'une machine virtuelle. Prend une valeur booléenne. Par défaut, il est de no.
Firmware=, --firmware=
Configure le firmware de la machine virtuelle à utiliser. Prend l'une des valeurs uefi, uefi-secure-boot, bios, linux ou auto. Par défaut, il est de auto. Lorsqu'il est défini sur uefi, le firmware OVMF sans prise en charge du démarrage sécurisé est utilisé. Lorsqu'il est défini sur uefi-secure-boot, le firmware OVMF avec prise en charge du démarrage sécurisé est utilisé. Lorsqu'il est défini sur bios, le firmware SeaBIOS par défaut est utilisé. Lorsqu'il est défini sur linux, le démarrage direct du noyau est utilisé. Voir l'option Linux= pour plus de détails sur l'image du noyau utilisée avec le démarrage direct du noyau. Lorsqu'il est défini sur auto, uefi-secure-boot est utilisé si possible et linux sinon.
FirmwareVariables=, --firmware-variables=
Configure le chemin d'accès au fichier de variables du firmware de la machine virtuelle à utiliser. Actuellement, cette option n'est prise en compte que lorsque le firmware uefi ou uefi-secure-boot est utilisé. Si elle n'est pas spécifiée, mkosi recherchera le fichier de variables par défaut et l'utilisera à la place.

Lorsqu'il est défini sur microsoft, un fichier de variables de firmware avec les certificats de démarrage sécurisé Microsoft déjà inscrits sera utilisé.

Lorsqu'il est défini sur microsoft-mok, un fichier de variables de firmware avec les certificats de démarrage sécurisé Microsoft déjà inscrits sera étendu avec une variable MokList contenant le certificat de démarrage sécurisé de SecureBootCertificate=. Ceci est destiné à être utilisé avec des binaires shim signés par la distribution et des binaires EFI signés localement.

Lorsqu'il est défini sur custom, le certificat de démarrage sécurisé de SecureBootCertificate= sera inscrit dans le fichier de variables du firmware par défaut.

virt-fw-vars du projet virt-firmware peut être utilisé pour personnaliser les fichiers de variables OVMF.

Linux=, --linux=
Définit l'image du noyau à utiliser pour le démarrage direct du noyau qemu. Si elle n'est pas spécifiée, mkosi utilisera le noyau fourni via la ligne de commande (option -kernel) ou le dernier noyau installé dans l'image (ou échouera si aucun noyau n'a été installé dans l'image).

Notez que lorsque le format de sortie cpio est utilisé, le démarrage direct du noyau est utilisé quel que soit le firmware configuré. Selon le firmware configuré, qemu peut démarrer le noyau lui-même ou via le firmware configuré.

Drives=, --drive=
Ajoute un lecteur. Prend une chaîne délimitée par des deux-points de format <id>:<taille>[:<répertoire>[:<options>[:<id-fichier>]]]]. id spécifie l'identifiant attribué au lecteur. Il peut être utilisé comme propriété drive= dans divers périphériques qemu. taille spécifie la taille du lecteur. Cela prend une taille en octets. De plus, les suffixes K, M et G peuvent être utilisés pour spécifier une taille en kilo-octets, méga-octets et giga-octets respectivement. répertoire spécifie éventuellement le répertoire dans lequel créer le fichier supportant le lecteur. options spécifie éventuellement des propriétés supplémentaires délimitées par des virgules qui sont passées telles quelles à l'option -drive de qemu. id-fichier spécifie l'identifiant du fichier supportant le lecteur. Les lecteurs ayant le même identifiant de fichier partageront le fichier de support. Le répertoire et la taille du fichier seront déterminés à partir du premier lecteur avec un identifiant de fichier donné.

Exemple d'utilisation :

[Runtime]
Drives=btrfs:10G
       ext4:20G
QemuArgs=-device nvme,serial=btrfs,drive=btrfs
         -device nvme,serial=ext4,drive=ext4
QemuArgs=
Liste d'arguments supplémentaires séparés par des espaces à passer lors de l'invocation de qemu.
Ephemeral=, --ephemeral
Lorsqu'il est utilisé avec les verbes shell, boot ou vm, cette option exécute le verbe spécifié sur un instantané temporaire de l'image de sortie qui est supprimé immédiatement lorsque le conteneur se termine. La prise d'un instantané temporaire est plus efficace sur les systèmes de fichiers qui prennent en charge les reflinks nativement (btrfs ou xfs) que sur les systèmes de fichiers plus traditionnels qui ne le font pas (ext4).
Credentials=, --credential=
Définit les informations d'identification à passer à systemd-nspawn ou à la machine virtuelle respectivement lorsque mkosi shell/boot ou mkosi vm sont utilisés. Cette option prend une liste de valeurs séparées par des espaces qui peuvent être des paires clé=valeur ou des chemins d'accès. Si un chemin d'accès est fourni, s'il s'agit d'un fichier, le nom de l'information d'identification sera le nom du fichier. Si le fichier est exécutable, la valeur de l'information d'identification sera la sortie de l'exécution du fichier. Sinon, la valeur de l'information d'identification sera le contenu du fichier. Si le chemin d'accès est un répertoire, la même logique s'applique à chaque fichier du répertoire.

Notez que les valeurs ne seront traitées comme des chemins d'accès que si elles ne contiennent pas le délimiteur (=).

KernelCommandLineExtra=, --kernel-command-line-extra=
Définit des entrées supplémentaires pour la ligne de commande du noyau qui sont ajoutées à la ligne de commande du noyau au moment de l'exécution lors du démarrage de l'image. Lors du démarrage dans un conteneur, elles sont passées comme arguments supplémentaires à systemd. Lors du démarrage dans une VM, elles sont ajoutées à la ligne de commande du noyau via la chaîne OEM SMBIOS io.systemd.stub.kernel-cmdline-extra. Ceci ne sera pris en compte que par les versions de systemd-boot et systemd-stub plus récentes ou égales à v254.
RuntimeTrees=, --runtime-tree=
Prend une paire de chemins séparés par des deux-points. Le premier chemin fait référence à un répertoire à monter dans n'importe quelle machine (conteneur ou VM) démarrée par mkosi. Le second chemin fait référence au répertoire cible à l'intérieur de la machine. Si le second chemin n'est pas fourni, le répertoire est monté sur /root/src dans la machine. Si le second chemin est relatif, il est interprété par rapport à /root/src dans la machine.

Pour chaque répertoire monté, l'uid et le gid de l'utilisateur en cours d'exécution

mkosi sont mappés à l'utilisateur root dans la machine. Cela signifie que tous les fichiers et répertoires apparaîtront comme s'ils étaient la propriété de root dans la machine, et tous les nouveaux fichiers et répertoires créés par root dans la machine dans ces répertoires seront la propriété de l'utilisateur exécutant mkosi sur l'hôte.

Notez que lors de l'utilisation de mkosi vm avec cette fonctionnalité, systemd v254 ou plus récent doit être installé dans l'image.

RuntimeSize=, --runtime-size=
Si spécifié, les images disque sont agrandies à la taille spécifiée lors de leur démarrage avec mkosi boot ou mkosi vm. Prend une taille en octets. De plus, les suffixes K, M et G peuvent être utilisés pour spécifier une taille en kilo-octets, méga-octets et gigaoctets respectivement.
RuntimeScratch=, --runtime-scratch=
Prend une valeur booléenne ou auto. Spécifie si un espace temporaire supplémentaire doit être monté sur /var/tmp. Si activé, un espace temporaire pratiquement illimité est mis à disposition sous /var/tmp lors du démarrage de l'image avec mkosi vm, mkosi boot ou mkosi shell.

Notez que l'utilisation de cette fonctionnalité avec mkosi vm nécessite systemd v254 ou plus récent dans l'invité.

RuntimeNetwork=, --runtime-network=
Prend l'une des valeurs user, interface ou none. Par défaut, il s'agit de user. Spécifie la configuration réseau à mettre en place lors du démarrage de l'image. user configure le réseau en mode utilisateur. interface établit une connexion réseau virtuelle entre l'hôte et l'image. Cela se traduit par une interface veth pour mkosi shell et mkosi boot, et une interface tap pour mkosi vm et mkosi vmspawn.

Notez que lorsque l'option interface est utilisée, mkosi ne configure pas automatiquement l'interface hôte. Il est attendu qu'une version récente de systemd-networkd soit en cours d'exécution sur l'hôte et qu'elle configure automatiquement l'interface hôte de la liaison.

RuntimeBuildSources=, --runtime-build-sources=
Monte les sources de construction configurées avec BuildSources= et le répertoire de construction (s'il y en a un configuré) aux mêmes emplacements dans /work où ils étaient montés lors de l'exécution du script de construction lors de l'utilisation de mkosi boot ou mkosi vm.
RuntimeHome=, --runtime-home=
Monte le répertoire personnel actuel à partir duquel mkosi est exécuté sur /root lors de l'utilisation de mkosi boot ou mkosi vm.
UnitProperties=, --unit-property=
Configure les propriétés des unités systemd à ajouter aux scopes systemd alloués lors de l'utilisation de mkosi boot ou mkosi vm. Celles-ci sont passées directement aux options --property de systemd-nspawn et systemd-run respectivement.
SshKey=, --ssh-key=
Chemin vers la clé privée X.509 au format PEM à utiliser pour se connecter à une machine virtuelle démarrée avec mkosi vm et construite avec l'option Ssh= activée via la commande mkosi ssh. Si non configuré et que mkosi.key existe dans le répertoire de travail, il sera automatiquement utilisé à cet effet. Exécutez mkosi genkey pour générer automatiquement une clé dans mkosi.key.
SshCertificate=, --ssh-certificate=
Chemin vers le certificat X.509 au format PEM à provisionner en tant que clé publique SSH dans les machines virtuelles démarrées avec mkosi vm. Si non configuré et que mkosi.crt existe dans le répertoire de travail, il sera automatiquement utilisé à cet effet. Exécutez mkosi genkey pour générer automatiquement un certificat dans mkosi.crt.
Machine=, --machine=
Spécifie le nom de la machine à utiliser lors du démarrage de l'image. Peut également être utilisé pour faire référence à une image spécifique lors de la connexion SSH à une image (par exemple, mkosi --image=myimage ssh).

Notez que Ephemeral= doit être activé pour démarrer plusieurs instances de la même image.

Register=, --register=
Prend une valeur booléenne ou auto. Spécifie si la vm/le conteneur doit être enregistré auprès de systemd-machined. Si activé, mkosi échouera s'il ne parvient pas à enregistrer la vm/le conteneur auprès de systemd-machined. Si désactivé, mkosi n'enregistrera pas la vm/le conteneur auprès de systemd-machined. Si auto, mkosi enregistrera la vm/le conteneur auprès de systemd-machined s'il est disponible. Par défaut, il s'agit de auto.
ForwardJournal=, --forward-journal=
Spécifie le chemin vers lequel les logs du journal des conteneurs et des machines virtuelles doivent être transférés. Si le chemin a l'extension .journal, il est interprété comme un fichier vers lequel le journal doit être écrit. Sinon, le chemin est interprété comme un répertoire vers lequel le journal doit être écrit.

Notez que systemd v256 ou plus récent est requis dans la machine virtuelle pour que le transfert de logs fonctionne.

Notez que si un chemin avec l'extension .journal est fourni, la taille du journal est limitée à 4G. Configurez un répertoire de sortie au lieu d'un fichier si votre charge de travail produit plus de 4G de données de journal.

SysupdateDirectory=, --sysupdate-directory=
Chemin vers un répertoire contenant des fichiers de définition de transfert systemd-sysupdate qui sont utilisés par mkosi sysupdate. Si mkosi.sysupdate/ existe dans le répertoire local, il sera également utilisé à cette fin.

Notez que mkosi sysupdate invoque systemd-sysupdate avec --transfer-source= défini sur le répertoire de sortie de mkosi. Pour en tirer parti dans un fichier de définition de transfert, définissez PathRelativeTo=explicit pour que le paramètre Path= pour la source de transfert soit interprété par rapport au répertoire de sortie de mkosi. Généralement, la configuration de PathRelativeTo=explicit et Path=/ pour la source de transfert est suffisante pour que le modèle de correspondance soit interprété par rapport au répertoire de sortie de mkosi.

Scripts

Pour permettre une personnalisation de l'image qui ne peut pas être implémentée à l'aide des fonctionnalités intégrées de mkosi, mkosi prend en charge l'exécution de scripts à divers points du processus de construction de l'image qui peuvent personnaliser l'image selon les besoins. Les scripts sont exécutés sur le système hôte en tant que root (soit root réel, soit root dans l'espace de noms utilisateur que mkosi a créé en s'exécutant sans privilèges) avec un environnement personnalisé pour simplifier la modification de l'image. Pour chaque script, les sources de construction configurées (BuildSources=) sont montées dans le répertoire de travail actuel avant d'exécuter le script dans le répertoire de travail actuel. $SRCDIR est défini pour pointer vers le répertoire de travail actuel. Les scripts suivants sont supportés :

•
Si mkosi.configure (ConfigureScripts=) existe, il est exécuté avant la construction de l'image. Ce script peut être utilisé pour modifier dynamiquement la configuration. Il reçoit la configuration sérialisée au format JSON sur stdin et devrait sortir la configuration modifiée sérialisée au format JSON sur stdout. Notez que ce script ne s'exécute que lors de la construction ou du démarrage de l'image (verbes build, vm, boot et shell). Si un arbre d'outils par défaut est configuré, il sera construit avant l'exécution des scripts de configuration et les scripts de configuration s'exécuteront avec l'arbre d'outils disponible. Cela signifie également que les modifications apportées par les scripts de configuration ne seront pas visibles dans la sortie summary.
•
Si mkosi.sync (SyncScripts=) existe, il est exécuté avant la construction de l'image. Ce script peut être utilisé pour mettre à jour diverses sources utilisées pour construire l'image. Un cas d'utilisation est d'exécuter git pull sur divers dépôts sources avant de construire l'image. Spécifiquement, le paramètre BuildSourcesEphemeral= ne s'applique pas aux scripts de synchronisation, ce qui signifie que les scripts de synchronisation peuvent être utilisés pour mettre à jour les sources de construction même si BuildSourcesEphemeral= est activé.
•
Si mkosi.prepare (PrepareScripts=) existe, il est d'abord appelé avec l'argument final, juste
t après l'installation des paquets logiciels. Il est appelé une seconde fois avec le paramètre de ligne de commande build, juste après que les paquets de construction soient installés et que la superposition de construction soit montée sur le répertoire racine de l'image. Ce script a un accès réseau et peut être utilisé pour installer des paquets à partir d'autres sources que le gestionnaire de paquets de la distribution (par exemple, pip, npm, ...), après que tous les paquets logiciels soient installés mais avant que l'image ne soit mise en cache (si le mode incrémental est activé). Contrairement à une installation à usage général, il est sûr d'installer des paquets dans le système (pip install, npm install -g) au lieu de dans $SRCDIR lui-même car l'image de construction n'est utilisée que pour un seul projet et peut être facilement jetée et reconstruite, il n'y a donc aucun risque de conflits de dépendances et aucun risque de polluer le système hôte.
•
Si mkosi.build (BuildScripts=) existe, il est exécuté avec la superposition de construction montée sur le répertoire racine de l'image. Lors de l'exécution du script de construction, $DESTDIR pointe vers un répertoire où le script doit placer tous les fichiers générés qu'il souhaite voir figurer dans l'image. Notez que les systèmes de construction basés sur make, automake et meson honorent généralement $DESTDIR, ce qui rend très naturel de construire des arbres de sources à partir du script de construction. Après l'exécution du script de construction, le contenu de $DESTDIR est copié dans l'image.
•
Si mkosi.postinst (PostInstallationScripts=) existe, il est exécuté après que l'arbre de construction (optionnel) et les arbres supplémentaires ont été installés. Ce script peut être utilisé pour modifier les images sans aucune restriction, après que tous les paquets logiciels et les sources construites aient été installés.
•
Si mkosi.finalize (FinalizeScripts=) existe, il est exécuté comme dernière étape de préparation d'une image.
•
Si mkosi.postoutput (PostOutputScripts=) existe, il est exécuté juste après que tous les fichiers de sortie ont été générés, avant qu'ils ne soient déplacés dans le répertoire de sortie. Ceci peut être utilisé pour générer des sorties supplémentaires ou alternatives, par exemple des fichiers SHA256FILES ou des manifestes SBOM.
•
Si mkosi.clean (CleanScripts=) existe, il est exécuté juste après que les sorties d'une construction précédente aient été nettoyées. Un script de nettoyage peut nettoyer toutes les sorties que mkosi ne connaît pas (par exemple, les artefacts de SplitArtifacts=partitions ou les RPM construits dans un script de construction). Notez que ce script n'utilise pas l'arbre d'outils même s'il est configuré.
•
Si mkosi.version existe et est exécutable, il est exécuté lors de l'analyse de la configuration et remplit ImageVersion= avec la sortie sur stdout. Ceci peut être utilisé pour le suivi de version externe, par exemple avec git describe ou date '+%Y-%m-%d'. Notez que ce script est exécuté sur le système hôte sans aucun sandboxing.
•
Si mkosi.rootpw existe et est exécutable, il est exécuté lors de l'analyse de la configuration et remplit RootPassword= avec la sortie sur stdout. Ceci peut être utilisé pour générer aléatoirement un mot de passe et peut être mémorisé en le sortant sur stderr ou en lisant $MKOSI_CONFIG dans un autre script (par exemple, mkosi.postoutput). Notez que ce script est exécuté sur le système hôte sans aucun sandboxing.

Si un script utilise l'extension .chroot, mkosi fera un chroot dans l'image en utilisant mkosi-chroot (voir ci-dessous) avant d'exécuter le script. Par exemple, si mkosi.postinst.chroot existe, mkosi fera un chroot dans l'image et l'exécutera comme script post-installation.

Au lieu d'un seul fichier script, mkosi lira également tous les fichiers dans l'ordre lexicographique des répertoires .d nommés de manière appropriée, par exemple, tous les fichiers dans un répertoire mkosi.build.d seraient utilisés comme scripts de construction. Ceci est pris en charge par

•
mkosi.sync.d,
•
mkosi.prepare.d,
•
mkosi.build.d,
•
mkosi.postinst.d,
•
mkosi.finalize.d,
•
mkosi.postoutput.d, et
•
mkosi.clean.d.

Ceci peut être combiné avec l'extension .chroot, par exemple, mkosi.build.d/01-foo.sh serait exécuté sans chroot dans l'image et mkosi.build.d/02-bar.sh.chroot serait exécuté après un chroot dans l'image.

Les scripts exécutés par mkosi reçoivent les variables d'environnement suivantes :

•
$ARCHITECTURE contient l'architecture définie dans le paramètre Architecture=. Si Architecture= n'est pas défini, il contiendra l'architecture native de la machine hôte. Voir la documentation de Architecture= pour les valeurs possibles de cette variable.
•
$QEMU_ARCHITECTURE contient l'architecture de $ARCHITECTURE dans le format utilisé par qemu. Utile pour trouver le binaire qemu ( qemu-system-$QEMU_ARCHITECTURE).
•
$DISTRIBUTION contient la distribution définie dans le paramètre Distribution=.
•
$RELEASE contient la version définie dans le paramètre Release=.
•
$DISTRIBUTION_ARCHITECTURE contient l'architecture de $ARCHITECTURE dans le format utilisé par la distribution configurée.
•
$PROFILES contient les profils du paramètre Profiles= sous forme de chaîne délimitée par des virgules.
•
$CACHED= est défini à 1 si une image mise en cache est disponible, 0 sinon.
•
$CHROOT_SCRIPT contient le chemin du script en cours d'exécution par rapport au répertoire racine de l'image. L'utilisation principale de cette variable est en combinaison avec le script mkosi-chroot. Voir la description de mkosi-chroot ci-dessous pour plus d'informations.
•
$SRCDIR contient le chemin vers le répertoire d'où mkosi a été invoqué, avec les sources de construction configurées montées par-dessus. $CHROOT_SRCDIR contient la valeur que $SRCDIR aura après l'invocation de mkosi-chroot.
•
$BUILDDIR n'est défini que si mkosi.builddir existe et pointe vers le répertoire de construction à utiliser. Ceci est utile pour tous les systèmes de construction qui prennent en charge les constructions hors arbre afin de réutiliser les artefacts déjà construits à partir des exécutions précédentes. $CHROOT_BUILDDIR contient la valeur que $BUILDDIR aura après l'invocation de mkosi-chroot.
•
$DESTDIR est un répertoire dans lequel tout logiciel installé généré par un script de construction peut être placé. Cette variable n'est définie que lors de l'exécution d'un script de construction. $CHROOT_DESTDIR contient la valeur que $DESTDIR aura après l'invocation de mkosi-chroot.
•
$OUTPUTDIR pointe vers le répertoire de staging utilisé pour stocker les artefacts de construction générés pendant la construction. $CHROOT_OUTPUTDIR contient la valeur que $OUTPUTDIR aura après l'invocation de mkosi-chroot.
•
$PACKAGEDIR pointe vers le répertoire contenant le dépôt de paquets local. Les scripts de construction peuvent ajouter plus de paquets au dépôt local en écrivant les paquets dans $PACKAGEDIR.
•
$ARTIFACTDIR pointe vers le répertoire utilisé pour transférer les artefacts de construction générés pendant la construction et les rendre disponibles pour utilisation par mkosi. Ceci est similaire à PACKAGEDIR, mais est destiné aux artefacts qui peuvent ne pas être des paquets reconnus par le gestionnaire de paquets, par exemple, les initrds créés par d'autres générateurs d'initrd que mkosi. Les scripts de construction peuvent ajouter plus d'artefacts au répertoire en les plaçant dans $ARTIFACTDIR. Les fichiers de ce répertoire ne sont disponibles que pour la construction en cours et ne sont pas copiés à l'extérieur comme le contenu de $OUTPUTDIR.

mkosi utilisera également certains sous-répertoires d'un répertoire d'artefacts pour utiliser automatiquement leur contenu à certaines étapes. Actuellement, les deux sous-répertoires suivants dans le répertoire d'artefacts sont utilisés par mkosi :

•
io.mkosi.microcode : Tous les fichiers de ce répertoire sont utilisés comme fichiers microcode, c'est-à-dire qu'ils sont préfixés aux initrds dans l'ordre lexicographique.
•
io.mkosi.initrd : Tous les fichiers de ce répertoire sont utilisés comme initrds et joints dans l'ordre lexicographique.

Il est recommandé que les utilisateurs de $ARTIFACTDIR placent les éléments pour leur propre usage dans un répertoire similaire nommé, par exemple, local.my.namespace.

•
$BUILDROOT est le répertoire racine de l'image en cours de construction, avec éventuellement la superposition de construction montée par-dessus en fonction du script qui est exécuté.
•
$WITH_DOCS est soit 0 soit 1 selon qu'une construction sans ou avec la documentation installée a été demandée (WithDocs=yes). Un script de construction devrait supprimer l'installation de toute documentation de paquet dans $DESTDIR dans le cas
$WITH_DOCS est défini sur 0.
•
$WITH_TESTS est soit 0, soit 1 selon qu'une compilation sans ou avec exécution de la suite de tests a été demandée (WithTests=no). Un script de compilation doit éviter d'exécuter des tests unitaires ou d'intégration si $WITH_TESTS est 0.
•
$WITH_NETWORK est soit 0 soit 1 selon qu'une compilation sans ou avec réseau est en cours d'exécution (WithNetwork=no). Un script de compilation doit éviter toute communication réseau si $WITH_NETWORK est 0.
•
$SOURCE_DATE_EPOCH est défini si demandé (SourceDateEpoch=TIMESTAMP, Environment=SOURCE_DATE_EPOCH=TIMESTAMP ou la variable d'environnement hôte $SOURCE_DATE_EPOCH). Ceci est utile pour rendre les compilations reproductibles. Voir SOURCE_DATE_EPOCH pour plus d'informations.
•
$MKOSI_UID et $MKOSI_GID sont respectivement l'uid, gid de l'utilisateur qui a invoqué mkosi.
•
$MKOSI_CONFIG est un fichier contenant un résumé json des paramètres de l'image actuelle. Ce fichier peut être analysé à l'intérieur des scripts pour accéder à tous les paramètres de l'image actuelle.
•
$IMAGE_ID contient l'identifiant de le réglage ImageId= ou --image-id=.
•
$IMAGE_VERSION contient la version du réglage ImageVersion= ou --image-version=.

De plus, lorsqu'un script est exécuté, quelques scripts sont mis à disposition via $PATH pour simplifier les cas d'utilisation courants.

•
mkosi-chroot: Ce script chroote dans l'image et exécute la commande donnée. En plus de chrooter dans l'image, il monte également divers fichiers et répertoires ($SRCDIR, $DESTDIR, $BUILDDIR, $OUTPUTDIR, $CHROOT_SCRIPT) dans l'image et modifie les variables d'environnement correspondantes pour pointer vers les emplacements à l'intérieur de l'image. Il monte également les systèmes de fichiers APIVFS (/proc, /dev, ...) pour s'assurer que les scripts et les outils exécutés à l'intérieur du chroot fonctionnent correctement. Il propage également /etc/resolv.conf de l'hôte dans le chroot si demandé, afin que la résolution DNS fonctionne à l'intérieur du chroot. Après la sortie de la commande mkosi-chroot, divers points de montage sont nettoyés.

Par exemple, pour appeler ls à l'intérieur de l'image, utilisez ce qui suit:

mkosi-chroot ls ...

Pour exécuter le script entier à l'intérieur de l'image, ajoutez un suffixe .chroot au nom (mkosi.build.chroot au lieu de mkosi.build, etc.).

•
Pour tous les gestionnaires de paquets supportés (dnf, rpm, apt, dpkg, pacman, zypper), des scripts du même nom sont placés dans $PATH, qui s'assurent que ces commandes opèrent sur le répertoire racine de l'image avec la configuration fournie par l'utilisateur au lieu d'opérer sur le système hôte. Cela signifie que depuis un script, vous pouvez faire par exemple dnf install vim pour installer vim dans l'image.

De plus, mkosi-install, mkosi-reinstall, mkosi-upgrade et mkosi-remove invoqueront l'opération correspondante du gestionnaire de paquets utilisé pour construire l'image.

•
git est automatiquement invoqué avec safe.directory=* pour éviter les erreurs de permission lors de l'exécution en tant qu'utilisateur root dans un espace utilisateur.
•
useradd et groupadd sont automatiquement invoqués avec --root=$BUILDROOT lorsqu'ils sont exécutés en dehors de l'image.

Lorsque les scripts sont exécutés, tous les répertoires encore en écriture sont également rendus en lecture seule (/home, /var, /root, ...) et seul le jeu minimal de répertoires nécessitant d'être en écriture reste accessible en écriture. Ceci est fait pour garantir que les scripts ne puissent pas interférer avec le système hôte lorsque mkosi s'exécute en tant que root.

Notez que lors de l'exécution de scripts, tous les répertoires source sont rendus éphémères, ce qui signifie que toutes les modifications apportées aux répertoires source pendant l'exécution des scripts sont supprimées une fois que les scripts ont terminé. Utilisez les répertoires de sortie, de construction ou de cache si vous avez besoin de conserver des données entre les builds.

Fichiers

Pour faciliter la construction d'images pour les versions de développement de vos projets, mkosi peut lire des données de configuration à partir du répertoire local, en supposant qu'il est invoqué à partir d'un arbre de source. Spécifiquement, les fichiers suivants sont utilisés s'ils existent dans le répertoire local:

•
Le répertoire mkosi.skeleton/ ou l'archive mkosi.skeleton.tar peuvent être utilisés pour insérer des fichiers dans l'image. Les fichiers sont copiés avant que les paquets de distribution ne soient installés dans l'image. Cela permet la création de fichiers qui doivent être fournis tôt, par exemple pour configurer le gestionnaire de paquets ou définir les préréglages systemd.

Lors de l'utilisation du répertoire, la propriété des fichiers n'est pas conservée : tous les fichiers copiés appartiendront à root. Pour préserver la propriété, utilisez une archive tar.

•
Le répertoire mkosi.extra/ ou l'archive mkosi.extra.tar peuvent être utilisés pour insérer des fichiers supplémentaires dans l'image, en plus de ce que la distribution inclut dans ses paquets. Ils sont similaires à mkosi.skeleton/ et mkosi.skeleton.tar, mais les fichiers sont copiés dans l'arborescence de l'image après l'installation du système d'exploitation.

Lors de l'utilisation du répertoire, la propriété des fichiers n'est pas conservée : tous les fichiers copiés appartiendront à root. Pour préserver la propriété, utilisez une archive tar.

•
Le répertoire mkosi.sandbox/ ou l'archive mkosi.sandbox.tar peuvent être utilisés pour configurer le gestionnaire de paquets sans que les fichiers ne soient insérés dans l'image. Si les fichiers doivent être inclus dans l'image, utilisez plutôt mkosi.skeleton/ et mkosi.skeleton.tar.

Lors de l'utilisation du répertoire, la propriété des fichiers n'est pas conservée : tous les fichiers copiés appartiendront à root. Pour préserver la propriété, utilisez une archive tar.

•
Le fichier de paramètres nspawn mkosi.nspawn sera copié au même endroit que le fichier image de sortie, s'il existe. Ceci est utile car nspawn recherche des fichiers de paramètres à côté des fichiers images qu'il démarre, pour des paramètres de runtime de conteneur supplémentaires.
•
Le répertoire mkosi.cache/, s'il existe, est automatiquement utilisé comme cache de téléchargement de paquets, afin d'accélérer les exécutions répétées de l'outil.
•
Le répertoire mkosi.builddir/, s'il existe, est automatiquement utilisé comme répertoire de construction hors arbre, si les commandes de construction dans les scripts mkosi.build le supportent. Plus précisément, ce répertoire sera monté dans le conteneur de construction, et la variable d'environnement $BUILDDIR sera définie sur celui-ci lorsque les scripts de construction sont invoqués. Un script de construction peut alors utiliser ce répertoire comme répertoire de construction, pour des constructions hors arbre de type automake ou ninja. Cela accélère considérablement les constructions, en particulier lorsque mkosi est utilisé en mode incrémental (-i) : non seulement l'image et la surcouche de construction, mais aussi l'arbre de construction sont réutilisés entre les invocations successives. Notez que si ce répertoire n'existe pas, la variable d'environnement $BUILDDIR n'est pas définie, et il appartient aux scripts de construction de décider s'il faut effectuer une construction dans l'arbre ou hors arbre, et quel répertoire de construction utiliser.
•
Le fichier mkosi.rootpw peut être utilisé pour fournir le mot de passe de l'utilisateur root de l'image. Si le mot de passe est préfixé par hashed:, il est traité comme un mot de passe root déjà haché. Le mot de passe peut facultativement être suivi d'un caractère de nouvelle ligne qui est implicitement supprimé. Le fichier doit avoir un mode d'accès de 0600 ou moins. Si ce fichier n'existe pas, le mot de passe root par défaut de la distribution est défini (ce qui signifie généralement que l'accès à l'utilisateur root est bloqué).
•
Le fichier mkosi.passphrase fournit la phrase secrète à utiliser lorsque le chiffrement LUKS est sélectionné. Il doit contenir la phrase secrète littéralement, et
(c'est-à-dire dans le même format que cryptsetup et /etc/crypttab attendent les fichiers de phrase de passe). Le fichier doit avoir un mode d'accès de 0600 ou moins.
•
Les fichiers mkosi.crt et mkosi.key contiennent un certificat X.509 et une clé privée PEM à utiliser lorsque la signature est requise (UEFI SecureBoot, verity, ...).
•
Le répertoire mkosi.output/ est utilisé pour stocker tous les artefacts de construction.
•
Le répertoire mkosi.credentials/ est utilisé comme source d'informations d'identification supplémentaires, similaire à l'option Credentials=. Pour chaque fichier du répertoire, le nom du fichier sera utilisé comme nom d'information d'identification et le contenu du fichier deviendra la valeur de l'information d'identification, ou, si le fichier est exécutable, mkosi exécutera le fichier et la sortie de la commande vers la sortie standard sera utilisée comme valeur de l'information d'identification. La sortie vers la sortie d'erreur sera ignorée. Les informations d'identification configurées avec Credentials= ont la priorité sur les fichiers dans mkosi.credentials.
•
Le répertoire mkosi.repart/ est utilisé comme source pour les fichiers de définition de partition de systemd-repart qui sont passés à systemd-repart lors de la construction d'une image disque. S'il n'existe pas et que le paramètre RepartDirectories= n'est pas configuré, mkosi utilisera par défaut les fichiers de définition de partition suivants :

00-esp.conf (si nous construisons une image amorçable) :

[Partition]
Type=esp
Format=vfat
CopyFiles=/boot:/
CopyFiles=/efi:/
SizeMinBytes=512M
SizeMaxBytes=512M

05-bios.conf (si nous construisons une image amorçable par BIOS) :

[Partition]
# UUID de la partition de démarrage BIOS grub dont grub a besoin sur GPT pour
# s'intégrer.
Type=21686148-6449-6e6f-744e-656564454649
SizeMinBytes=1M
SizeMaxBytes=1M

10-root.conf

[Partition]
Type=root
Format=<distribution-default-filesystem>
CopyFiles=/
Minimize=guess

Notez que si mkosi.repart/ est trouvé ou si RepartDirectories= est utilisé, nous n'utiliserons aucune des définitions de partition par défaut.

Tous ces fichiers sont facultatifs.

Notez que l'emplacement de tous ces fichiers peut également être configuré lors de l'invocation via des options de ligne de commande, et comme paramètres dans mkosi.conf, au cas où les paramètres par défaut ne conviendraient pas à un projet.

MISE EN CACHE

mkosi prend en charge trois caches différents pour accélérer les reconstructions d'images répétitives. Spécifiquement :

1.
Le cache des paquets du gestionnaire de paquets de distribution peut être mis en cache entre les constructions. Ceci est configuré avec l'option --cache-directory= ou le répertoire mkosi.cache/. Cette forme de mise en cache repose sur le gestionnaire de paquets de la distribution, et met en cache les paquets de distribution (RPM, deb, ...) après leur téléchargement, mais avant leur décompression.
2.
Si le mode de construction incrémentielle est activé avec --incremental, des copies mises en cache de l'image finale et de la surcouche de construction sont effectuées juste avant que les sources de construction soient copiées (pour la surcouche de construction) ou que les artefacts générés par mkosi.build soient copiés (dans le cas de l'image finale). Cette forme de mise en cache permet de contourner l'étape de décompression des paquets, longue et coûteuse en temps, des gestionnaires de paquets de distribution, mais n'est efficace que si la liste des paquets à utiliser reste stable, mais que les sources de construction et leurs scripts changent régulièrement. Notez que ce cache nécessite un vidage manuel : chaque fois que la liste des paquets est modifiée, les images mises en cache doivent être explicitement supprimées avant la prochaine reconstruction, en utilisant le commutateur -f.
3.
Enfin, entre plusieurs constructions, le répertoire des artefacts de construction peut être partagé, en utilisant le répertoire mkosi.builddir/. Ce répertoire permet aux systèmes de construction tels que Meson de réutiliser des sources déjà compilées d'une construction précédente, accélérant ainsi le processus de construction d'un script de construction mkosi.build.

Le cache des paquets et le mode incrémentiel sont toujours utiles. Le cache final ne s'applique qu'aux utilisations de mkosi avec un arbre source et un script de construction. Lorsque les trois sont activés ensemble, les temps de rotation pour les constructions d'images complètes sont minimes, car seuls les fichiers sources modifiés doivent être recompilés.

VARIABLES D'ENVIRONNEMENT

•
$MKOSI_LESS remplace les options de less lorsqu'il est appelé par mkosi pour paginer la sortie.
•
$MKOSI_DNF peut être utilisé pour remplacer l'exécutable utilisé comme dnf. Ceci est particulièrement utile pour choisir entre dnf et dnf5.
•
$EPEL_MIRROR peut être utilisé pour remplacer l'emplacement du miroir par défaut utilisé pour les dépôts epel lorsque Mirror= est utilisé. Par défaut, mkosi recherche les dépôts epel dans le sous-répertoire fedora du répertoire parent du miroir spécifié dans Mirror=. Par exemple, si le miroir est défini sur https://mirror.net/centos-stream, mkosi recherchera les dépôts epel dans https://mirror.net/fedora/epel.
•
SYSEXT_SCOPE et CONFEXT_SCOPE peuvent être utilisés pour remplacer la valeur par défaut du fichier extension-release respectif lors de la construction d'un sysext ou confext. Par défaut, la valeur est définie sur initrd system portable.

EXEMPLES

Créez et exécutez une image brute GPT avec ext4, sous le nom image.raw :

# mkosi -p systemd --incremental boot

Créez et exécutez une image GPT amorçable, sous le nom foobar.raw :

$ mkosi -d fedora -p kernel-core -p systemd -p systemd-boot -p udev -o foobar.raw
# mkosi --output foobar.raw boot
$ mkosi --output foobar.raw vm

Créez et exécutez une image Fedora Linux dans un répertoire simple :

# mkosi --distribution fedora --format directory boot

Créez une image compressée image.raw.xz avec SSH installé et ajoutez un fichier de somme de contrôle :

$ mkosi --distribution fedora --format disk --checksum --compress-output --package=openssh-clients

Dans le répertoire source d'un projet basé sur automake, configurez mkosi de manière à ce que l'invocation simple de mkosi sans paramètres crée une image système contenant une version construite du projet dans son état actuel :

$ cat >mkosi.conf <<EOF
[Distribution]
Distribution=fedora
[Output]
Format=disk
[Content]
Packages=kernel,systemd,systemd-udev,openssh-clients,httpd
BuildPackages=make,gcc,libcurl-devel
EOF
$ cat >mkosi.build <<EOF
#!/bin/sh
if [ "$container" != "mkosi" ]; then
    exec mkosi-chroot "$CHROOT_SCRIPT" "$@"
fi
cd $SRCDIR
./autogen.sh
./configure --prefix=/usr
make -j `nproc`
make install
EOF
$ chmod +x mkosi.build
# mkosi --incremental boot
# systemd-nspawn -bi image.raw

Différentes manières de démarrer avec vm

La manière la plus simple de démarrer une machine virtuelle est de créer une image avec les composants requis et de laisser mkosi appeler qemu avec toutes les bonnes options :

$ mkosi -d fedora \
    --autologin \
    -p systemd-udev,systemd-boot,kernel-core \
    build
$ mkosi -d fedora vm
...
fedora login: root (connexion automatique)
[root@fedora ~]#

Par défaut, le démarrage se fait uniquement avec une console texte. Dans ce mode, les messages du chargeur de démarrage, du noyau et de systemd, puis l'invite de connexion getty et le shell utilisent tous le même terminal. Il est possible de basculer entre la console qemu et le moniteur en appuyant sur Ctrl-a c. Le moniteur qemu peut par exemple être utilisé pour injecter des touches spéciales ou arrêter la machine rapidement. Alternativement, la machine peut être arrêtée en utilisant Ctrl-a x.

Pour démarrer avec une fenêtre graphique, ajoutez --console=gui :

$ mkosi -d fedora --console=gui qemu

Un noyau peut être démarré directement avec mkosi vm -kernel ... -initrd ... -append '...'. C'est un peu plus rapide car aucun chargeur de démarrage n'est utilisé, et il est également plus facile d'expérimenter avec différents noyaux et lignes de commande du noyau. Notez que malgré le nom, l'option -append de qemu remplace la ligne de commande du noyau par défaut intégrée au noyau et toute spécification -append précédente.

L'UKI est également copié dans le répertoire de sortie et peut être démarré directement :

$ mkosi vm -kernel mkosi.output/fedora~38/image.efi

Lors du démarrage à l'aide d'un noyau externe, nous n'avons pas besoin du noyau dans l'image, mais nous voudrions toujours que les modules du noyau soient installés.

Il est également possible de faire un démarrage direct du noyau vers un chargeur de démarrage, en tirant parti du fait que systemd-boot(7) est un binaire UEFI valide :

$ mkosi vm -kernel /usr/lib/systemd/boot/efi/systemd-bootx64.efi

Dans ce scénario, le noyau est chargé depuis l'ESP dans l'image par systemd-boot.

EXIGENCES

mkosi est empaqueté pour diverses distributions : Debian, Kali, Ubuntu, Arch Linux, Fedora Linux, OpenMandriva, Gentoo. Notez que cela fait un moment depuis la dernière version et que les paquets distribués par les distributions sont très obsolètes. Nous recommandons actuellement d'exécuter mkosi depuis git jusqu'à ce qu'une nouvelle version soit publiée.

mkosi nécessite un noyau Linux qui fournit mount_setattr(), introduit dans la version 5.12.

mkosi nécessite actuellement systemd 254 pour construire des images disque amorçables.

Lorsque vous n'utilisez pas les paquets de distribution, assurez-vous d'installer les dépendances nécessaires. Par exemple, sur Fedora Linux, vous avez besoin de :

# dnf install btrfs-progs apt dosfstools mtools edk2-ovmf e2fsprogs squashfs-tools gnupg python3 tar xfsprogs xz zypper sbsigntools

Sur Debian/Kali/Ubuntu, il peut être nécessaire d'installer explicitement les paquets ubuntu-keyring, ubuntu-archive-keyring, kali-archive-keyring et/ou debian-archive-keyring, en plus de apt, en fonction du type d'images de distribution que vous souhaitez construire.

Notez que la version minimale de Python requise est 3.9.

mkosi a besoin de capacités illimitées pour créer et agir dans des espaces de noms. Certaines distributions restreignent la création ou les capacités au sein des espaces de noms utilisateur, ce qui bloque mkosi.

Pour plus d'informations sur Ubuntu, qui implémente de telles restrictions à l'aide d'AppArmor, voir https://ubuntu.com/blog/ubuntu-23-10-restricted-unprivileged-user-namespaces. Pour d'autres systèmes, essayez de rechercher les sysctls kernel.unprivileged_userns_clone ou user.max.user_namespace.

Pour les systèmes Ubuntu, vous pouvez supprimer les restrictions pour mkosi en adaptant cet extrait pour pointer vers votre binaire mkosi, en le copiant dans /etc/apparmor.d/path.to.mkosi, puis en exécutant systemctl reload apparmor :

abi <abi/4.0>,
include <tunables/global>
/path/to/mkosi flags=(default_allow) {
  userns,
}

Foire Aux Questions (FAQ)

•
Pourquoi mkosi vm avec KVM ne fonctionne-t-il pas sur Debian/Kali/Ubuntu ?

Alors que d'autres distributions autorisent l'accès à /dev/kvm, sur Debian/Kali/Ubuntu, cela n'est autorisé que pour les utilisateurs du groupe kvm. Parce que mkosi se désunit d'un espace de noms utilisateur lorsqu'il s'exécute sans privilèges, même si l'utilisateur appelant était dans le groupe kvm, lorsque mkosi se désunit de l'espace de noms utilisateur pour s'exécuter sans privilèges, il perd l'accès au groupe kvm et au moment où nous démarrons qemu, nous n'avons plus accès à /dev/kvm. En solution de contournement, vous pouvez modifier les permissions des nœuds de périphérique en 0666, ce qui est suffisant pour que KVM fonctionne sans privilèges. Pour rendre ces paramètres persistants après les redémarrages, copiez /usr/lib/tmpfiles.d/static-nodes-permissions.conf vers /etc/tmpfiles.d/static-nodes-permissions.conf et modifiez le mode de /dev/kvm de 0660 à 0666.

•
Comment ajouter un utilisateur régulier à une image ?

Vous pouvez utiliser l'extrait suivant dans un script post-installation :

useradd --create-home --user-group $USER --password "$(openssl passwd -stdin -6 <$USER_PASSWORD_FILE)"

Notez qu'à partir de systemd v256, si activé, systemd-homed-firstboot.service invitera à créer un utilisateur régulier lors du premier démarrage s'il n'y a pas d'utilisateurs réguliers.

•
Pourquoi vois-je des échecs de chown de fichiers lors de la création d'images ?

Lorsque vous n'êtes pas exécuté en tant que root, votre utilisateur ne peut pas changer la propriété des fichiers à des propriétaires arbitraires. Diverses distributions fournissent encore des fichiers dans leurs paquets qui ne sont pas détenus par l'utilisateur root. Lorsque vous n'êtes pas exécuté en tant que root, mkosi mappe l'utilisateur actuel à root lors de l'appel des gestionnaires de paquets, ce qui signifie que le changement de propriété à root fonctionnera, mais le changement de propriété à tout autre utilisateur ou groupe échouera.

Notez que les appels chown ne sont supprimés que lors de l'exécution des gestionnaires de paquets, mais pas lors de l'exécution de scripts. Si cela est nécessaire, par exemple pour un script de construction, vous pouvez définir la variable MKOSI_CHROOT_SUPPRESS_CHOWN à une valeur vraie (par exemple

="Li">1, oui, vrai) pour supprimer les appels chown dans mkosi-chroot et les scripts .chroot.

Si ce comportement entraîne un mauvais fonctionnement des applications s'exécutant dans votre image, vous pouvez envisager d'exécuter mkosi en tant que root, ce qui évite ce problème. Alternativement, si l'exécution de mkosi en tant que root n'est pas souhaitée, vous pouvez utiliser unshare --map-auto --map-current-user --setuid 0 --setgid 0 pour devenir root dans un espace de noms utilisateur avec plus d'un utilisateur, en supposant que les mappages UID/GID dans /etc/subuid et /etc/subgid sont correctement configurés. Notez que l'exécution de mkosi en tant que root ou avec unshare signifie que tous les fichiers de sortie produits par mkosi n'appartiendront plus à votre utilisateur actuel.

Notez que pour les services systemd qui ont besoin de répertoires dans /var appartenant à l'utilisateur et au groupe du service, une alternative à l'expédition de ces répertoires dans les paquets ou à leur création via systemd-tmpfiles est d'utiliser StateDirectory=, CacheDirectory= ou LogsDirectory= dans le fichier de service, ce qui demande à systemd de créer le répertoire lors de son premier démarrage du service.

Alternativement, les directives z ou Z pour systemd-tmpfiles peuvent être utilisées pour changer le propriétaire de divers répertoires et fichiers pour leur utilisateur propriétaire lors du premier démarrage du système.

•
Pourquoi portablectl inspect <image>/systemd-dissect <image> dit-il que mon service portable n'en est pas un ?

systemd-dissect et portablectl inspect recherchent PORTABLE_PREFIXES= dans os-release et si la clé est manquante, ils ne reconnaissent pas un service portable comme tel, affichant ✗ sous Utiliser comme pour systemd-dissect ou n/a sous Service portable pour portablectl.

Comme il n'y a pas de valeur par défaut appropriée à définir pour cette clé et que les images de service portable générées s'attacheront toujours correctement, même lorsque la clé n'est pas définie, mkosi n'en définit pas.

Vous pouvez définir PORTABLE_PREFIXES= dans le fichier os-release vous-même dans un script postinst.
