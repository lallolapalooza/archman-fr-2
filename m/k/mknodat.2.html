mknod(2) Manuel des appels système mknod(2)

NOM

mknod, mknodat - créer un fichier spécial ou ordinaire

BIBLIOTHEQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <sys/stat.h>
int mknod(const char *path, mode_t mode, dev_t dev);
#include <fcntl.h>           /* Définition des constantes AT_* */
#include <sys/stat.h>
int mknodat(int dirfd, const char *path, mode_t mode, dev_t dev);
Exigences de macro de test de fonctionnalité pour glibc (voir feature_test_macros(7)):

mknod():

    _XOPEN_SOURCE >= 500
        || /* Depuis glibc 2.19 : */ _DEFAULT_SOURCE
        || /* glibc <= 2.19 : */ _BSD_SOURCE || _SVID_SOURCE

DESCRIPTION

L'appel système mknod() crée un nœud de système de fichiers (fichier, fichier spécial d'appareil, ou tube nommé) nommé path, avec les attributs spécifiés par mode et dev.

L'argument mode spécifie à la fois le mode de fichier à utiliser et le type de nœud à créer. Il doit être une combinaison (utilisant l'opérateur OU bit à bit) de l'un des types de fichiers listés ci-dessous et de zéro ou plusieurs bits de mode de fichier listés dans inode(7).

Le mode de fichier est modifié par l'umask du processus de la manière habituelle : en l'absence d'ACL par défaut, les permissions du nœud créé sont (mode & ~umask).

Le type de fichier doit être l'un de S_IFREG, S_IFCHR, S_IFBLK, S_IFIFO, ou S_IFSOCK pour spécifier un fichier ordinaire (qui sera créé vide), un fichier spécial caractère, un fichier spécial bloc, un FIFO (tube nommé), ou un socket UNIX, respectivement. (Un type de fichier zéro est équivalent au type S_IFREG.)

Si le type de fichier est S_IFCHR ou S_IFBLK, alors dev spécifie les numéros majeur et mineur du nouveau fichier spécial d'appareil créé (makedev(3) peut être utile pour construire la valeur pour dev) ; sinon, il est ignoré.

Si path existe déjà, ou est un lien symbolique, cet appel échoue avec une erreur EEXIST.

Le nouveau nœud créé appartiendra à l'ID utilisateur effectif du processus. Si le répertoire contenant le nœud a le bit set-group-ID défini, ou si le système de fichiers est monté avec la sémantique de groupe BSD, le nouveau nœud héritera de la propriété du groupe de son répertoire parent ; sinon, il appartiendra à l'ID de groupe effectif du processus.

mknodat()

L'appel système mknodat() fonctionne exactement de la même manière que mknod(), sauf pour les différences décrites ici.

Si path est relatif, il est interprété par rapport au répertoire référencé par le descripteur de fichier dirfd (plutôt que par rapport au répertoire de travail courant du processus appelant, comme le fait mknod() pour un chemin relatif).

Si path est relatif et dirfd est la valeur spéciale AT_FDCWD, alors path est interprété par rapport au répertoire de travail courant du processus appelant (comme mknod()).

Si path est absolu, alors dirfd est ignoré.

Voir openat(2) pour une explication de la nécessité de mknodat().

VALEUR DE RETOUR

mknod() et mknodat() retournent zéro en cas de succès. En cas d'erreur, -1 est retourné et errno est défini pour indiquer l'erreur.

ERREURS

EACCES
Le répertoire parent ne permet pas l'écriture au processus, ou l'un des répertoires du préfixe du chemin de path ne permettait pas la permission de recherche. (Voir aussi path_resolution(7).)
EBADF
(mknodat()) path est relatif mais dirfd n'est ni AT_FDCWD ni un descripteur de fichier valide.
EDQUOT
Le quota de blocs disque ou d'inodes de l'utilisateur sur le système de fichiers est épuisé.
EEXIST
path existe déjà. Cela inclut le cas où path est un lien symbolique, valide ou non.
EFAULT
path pointe en dehors de votre espace d'adressage accessible.
EINVAL
mode a demandé la création de quelque chose d'autre qu'un fichier ordinaire, un fichier spécial d'appareil, un FIFO ou un socket.
ELOOP
Trop de liens symboliques ont été rencontrés lors de la résolution de path.
ENAMETOOLONG
path était trop long.
ENOENT
Un composant de répertoire dans path n'existe pas ou est un lien symbolique non valide.
ENOMEM
Une mémoire noyau insuffisante était disponible.
ENOSPC
Le périphérique contenant path n'a pas de place pour le nouveau nœud.
ENOTDIR
Un composant utilisé comme répertoire dans path n'est pas, en fait, un répertoire.
ENOTDIR
(mknodat()) path est relatif et dirfd est un descripteur de fichier faisant référence à un fichier autre qu'un répertoire.
EPERM
mode a demandé la création de quelque chose d'autre qu'un fichier ordinaire, un FIFO (tube nommé), ou un socket UNIX, et l'appelant n'est pas privilégié (Linux : ne possède pas la capacité CAP_MKNOD) ; également retourné si le système de fichiers contenant path ne supporte pas le type de nœud demandé.
EROFS
path fait référence à un fichier sur un système de fichiers en lecture seule.

VERSIONS

POSIX.1-2001 dit : "La seule utilisation portable de mknod() est de créer un fichier spécial FIFO. Si mode n'est pas S_IFIFO ou si dev n'est pas 0, le comportement de mknod() n'est pas spécifié." Cependant, de nos jours, on ne devrait jamais utiliser mknod() à cette fin ; on devrait utiliser mkfifo(3), une fonction spécialement définie à cet effet.

Sous Linux, mknod() ne peut pas être utilisé pour créer des répertoires. On devrait créer des répertoires avec mkdir(2).

NORMES

POSIX.1-2024.

HISTORIQUE

mknod()
SVr4, 4.4BSD, POSIX.1-2001 (mais voir VERSIONS).
mknodat()
Linux 2.6.16, glibc 2.4. POSIX.1-2008.

NOTES

Il existe de nombreuses imperfections dans le protocole sous-jacent à NFS. Certaines d'entre elles affectent mknod() et mknodat().
