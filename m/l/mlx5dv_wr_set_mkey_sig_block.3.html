mlx5dv_wr_set_mkey_sig_block(3) Manuel des fonctions de bibliothèque mlx5dv_wr_set_mkey_sig_block(3)

NOM

mlx5dv_wr_set_mkey_sig_block - Configure une MKEY pour une opération de signature de bloc (intégrité des données).

SYNTAXE

#include <infiniband/mlx5dv.h>
static inline void mlx5dv_wr_set_mkey_sig_block(struct mlx5dv_QP_ex *mqp,
                                                const struct mlx5dv_sig_block_attr *attr)

DESCRIPTION

Configure une MKEY avec des propriétés de protection des données au niveau du bloc. Avec cela, le périphérique peut ajouter/modifier/supprimer/valider des champs d'intégrité par bloc lors de la transmission de données de la mémoire vers le réseau et lors de la réception de données du réseau vers la mémoire.

Ce setter peut être appelé facultativement après qu'une requête de travail de configuration de MKEY a été initiée en utilisant mlx5dv_wr_mkey_configure(3). La configuration des propriétés de signature de bloc pour une MKEY se fait en décrivant quel type de signature est requis (ou attendu) dans deux domaines : le domaine du fil (wire domain) et le domaine de la mémoire (memory domain).

La MKEY représente une mémoire virtuellement contiguë, en lui configurant une disposition (layout). Le domaine de signature de la mémoire décrit si les données dans cette mémoire virtuellement contiguë incluent des champs d'intégrité et, le cas échéant, quel type (enum mlx5dv_sig_type) et quelle taille de bloc (enum mlx5dv_block_size).

Le domaine de signature du fil décrit les mêmes propriétés pour les données telles qu'elles apparaissent sur le fil. Ensuite, en fonction de l'opération réelle effectuée (TX ou RX), le périphérique fera la "bonne chose" en fonction des configurations de signature des deux domaines.

Exemple 1 :

Le domaine de signature de la mémoire est configuré pour CRC32 tous les 512 octets par bloc.

Le domaine de signature du fil est configuré pour aucune signature.

Un SEND est émis en utilisant la MKEY comme clé locale.

Résultat : le périphérique rassemblera les données avec les champs CRC32 de la MKEY (en utilisant la disposition configurée pour la MKEY afin de localiser la mémoire réelle), validera chaque CRC32 par rapport aux 512 octets de données précédents, supprimera le champ CRC32 et transmettra uniquement 512 octets de données sur le fil.

Exemple 1.1 :

Identique à ci-dessus, mais un RECV est émis avec la même clé, et la réception (RX) se produit.

Résultat : le périphérique recevra les données du fil, les dispersera dans la MKEY (en utilisant la disposition configurée pour la MKEY afin de localiser la mémoire réelle), générant et dispersant un champ CRC32 supplémentaire après chaque 512 octets dispersés.

Exemple 2 :

Le domaine de signature de la mémoire est configuré pour aucune signature.

Le domaine de signature du fil est configuré pour T10DIF tous les 4Ko par bloc.

La MKEY est envoyée à un nœud distant qui émet une RDMA_READ vers cette MKEY.

Résultat : le périphérique rassemblera les données de la MKEY (en utilisant la disposition configurée pour la MKEY afin de localiser la mémoire réelle), les transmettra sur le fil tout en générant un champ T10DIF supplémentaire tous les 4Ko de données.

Exemple 2.1 :

Identique à ci-dessus, mais le nœud distant émet une RDMA_WRITE vers cette MKEY.

Résultat : le périphérique recevra les données du fil, validera chaque champ T10DIF par rapport aux 4Ko de données précédents, supprimera le champ T10DIF et dispersera les données seules dans la MKEY (en utilisant la disposition configurée pour la MKEY afin de localiser la mémoire réelle).

ARGUMENTS

mqp
Le QP où une requête de travail de configuration de MKEY a été créée par

mlx5dv_wr_mkey_configure().

attr
Attributs de signature de bloc à définir pour la MKEY.

Attributs de signature de bloc

Les attributs de signature de bloc décrivent les structures de données d'entrée et de sortie dans les domaines mémoire et fil.

struct mlx5dv_sig_block_attr {
    const struct mlx5dv_sig_block_domain *mem;
    const struct mlx5dv_sig_block_domain *wire;
    uint32_t flags;
    uint8_t check_mask;
    uint8_t copy_mask;
    uint64_t comp_mask;
};
mem
Un pointeur vers la configuration de signature pour le domaine mémoire ou NULL si le domaine n'a pas de signature.
wire
Un pointeur vers la configuration de signature pour le domaine fil ou NULL si le domaine n'a pas de signature.
flags
Un OR bit à bit des différentes valeurs décrites ci-dessous.
MLX5DV_SIG_BLOCK_ATTR_FLAG_COPY_MASK
Si le bit n'est pas défini, alors copy_mask est ignoré. Voir les détails dans la description de copy_mask.
check_mask
Chaque bit de check_mask correspond à un octet du champ de signature dans le domaine d'entrée. L'octet de la signature d'entrée est vérifié si le bit correspondant dans check_mask est défini. Les bits non pertinents pour le type de signature sont ignorés.

Disposition de check_mask.

check_mask (bits) 7 6 5 4 3 2 1 0
T10-DIF (octets) GUARD[1] GUARD[0] APP[1] APP[0] REF[3] REF[2] REF[1] REF[0]
CRC32C/CRC32 (octets) 3 2 1 0
CRC64_XP10 (octets) 7 6 5 4 3 2 1 0

Les masques couramment utilisés sont définis dans enum mlx5dv_sig_mask. D'autres masques sont également pris en charge. Suivez le tableau ci-dessus pour définir un masque personnalisé. Par exemple, cela peut être utile pour le champ de balise d'application (application tag) de la signature T10DIF. L'utilisation de la balise d'application est hors du champ de la spécification T10DIF et dépend de l'implémentation. check_mask permet de valider une partie de la balise d'application si nécessaire.

copy_mask
Un masque pour spécifier quelle partie de la signature est copiée du domaine source vers le domaine destination. Le masque de copie est généralement calculé automatiquement. La signature est copiée si le même type de signature est configuré sur les deux domaines. Les parties du T10-DIF sont comparées et traitées indépendamment.

Si MLX5DV_SIG_BLOCK_ATTR_FLAG_COPY_MASK est défini, l'attribut copy_mask remplace la valeur calculée du masque de copie. Sinon, copy_mask est ignoré.

Chaque bit de copy_mask correspond à un octet du champ de signature. Si le bit correspondant dans copy_mask est défini, l'octet du champ de signature est copié du domaine d'entrée vers le domaine de sortie. Le calcul selon la configuration du domaine de sortie n'est pas effectué dans ce cas. Les bits non pertinents pour le type de signature sont ignorés. copy_mask ne peut être utilisé que si les domaines d'entrée et de sortie ont la même structure, c'est-à-dire la même taille de bloc et le même type de signature. La configuration de la MKEY échouera si MLX5DV_SIG_BLOCK_ATTR_FLAG_COPY_MASK est défini mais que les domaines ont des structures de signature différentes.

Les masques prédéfinis sont disponibles dans enum mlx5dv_sig_mask. Il est également possible de spécifier un masque défini par l'utilisateur. Suivez le tableau dans la description de check_mask pour définir un masque personnalisé.

mlx5dv_wr_set_mkey_sig_block(3) — rdma-core

NAME

mlx5dv_wr_set_mkey_sig_block - configurer la signature de bloc pour MKEY

SYNOPSIS

#include <infiniband/mlx5dv.h>

    void
    mlx5dv_wr_set_mkey_sig_block(
        struct ibv_pd *pd,
        struct mlx5dv_wr_mkey_config *mkey_conf,
        const struct mlx5dv_sig_block_domain *block_domain,
        uint64_t comp_mask);

DESCRIPTION

La fonction mlx5dv_wr_set_mkey_sig_block configure le champ de signature de bloc pour les opérations de gestion de mémoire pour les périphériques Mellanox ConnectX-4 et ultérieurs. Ceci est utilisé pour le chiffrement et la protection des données au niveau du bloc.

Elle doit être appelée avant la fonction mlx5dv_wr_mkey_configure(3). La fonction est considérée comme une partie de l'API DV (Direct Verbs) de Mellanox.

Le champ comp_mask est utilisé pour spécifier le comportement des bits qui ne peuvent pas être vérifiés, mais doivent être préservés. Dans ce cas, les bits correspondants doivent être effacés dans check_mask et mis dans copy_mask.

comp_mask
Réservé pour une extension future, doit être 0 maintenant.

Domaine de signature de bloc

struct mlx5dv_sig_block_domain {
    enum mlx5dv_sig_type sig_type;
    union {
        const struct mlx5dv_sig_t10dif *dif;
        const struct mlx5dv_sig_crc *crc;
    } sig;
    enum mlx5dv_block_size block_size;
    uint64_t comp_mask;
};
sig_type
Le type de signature pour ce domaine, l'un des suivants
MLX5DV_SIG_TYPE_T10DIF
La protection des données au niveau du bloc définie dans les spécifications T10 (T10 SBC-3).
MLX5DV_SIG_TYPE_CRC
La protection des données au niveau du bloc basée sur un contrôle de redondance cyclique (CRC). Le type spécifique de CRC est défini dans sig.
sig
Selon sig_type, il s'agit de la configuration spécifique à chaque type de signature.
block_size
La taille du bloc pour ce domaine, l'une des valeurs de l'énumération enum mlx5dv_block_size.
comp_mask
Réservé pour une extension future, doit être 0 maintenant.

Signature CRC

struct mlx5dv_sig_crc {
    enum mlx5dv_sig_crc_type type;
    uint64_t seed;
};
type
Le type CRC spécifique, l'un des suivants.
MLX5DV_SIG_CRC_TYPE_CRC32
La signature CRC32 est créée en calculant une CRC 32 bits définie dans l'interface physique et de signalisation Fibre Channel (FC-PH), ANSI X3.230:1994.
MLX5DV_SIG_CRC_TYPE_CRC32C
La signature CRC32C est créée en calculant une CRC 32 bits appelée CRC de Castagnoli, définie dans le protocole Internet Small Computer Systems Interface (iSCSI) rfc3720.
MLX5DV_SIG_CRC_TYPE_CRC64_XP10
La signature CRC64_XP10 est créée en calculant une CRC 64 bits définie dans la norme de compression Microsoft XP10.
seed
Une graine pour le calcul du CRC par bloc. Les bits non pertinents pour le type CRC sont ignorés. Par exemple, tous les bits sont utilisés pour CRC64_XP10, mais seulement les 32 bits les moins significatifs sont utilisés pour CRC32/CRC32C.

Seules les valeurs suivantes sont prises en charge comme graine : CRC32/CRC32C - 0, 0xFFFFFFFF (UINT32_MAX) ; CRC64_XP10 - 0, 0xFFFFFFFFFFFFFFFF (UINT64_MAX).

Signature T10DIF

La signature T10DIF est définie dans les spécifications T10 (T10 SBC-3) pour la protection des données au niveau du bloc. La taille du bloc de données protégé par T10DIF doit être modulo 8 octets, comme requis par les spécifications T10DIF. Notez que lors de la définition de la valeur LBA initiale sur ref_tag, il devrait s'agir de la valeur du premier bloc à transmettre.

struct mlx5dv_sig_t10dif {
    enum mlx5dv_sig_t10dif_bg_type bg_type;
    uint16_t bg;
    uint16_t app_tag;
    uint32_t ref_tag;
    uint16_t flags;
};
bg_type
Le type de garde de bloc à utiliser, l'un des suivants.
MLX5DV_SIG_T10DIF_CRC
Utiliser le CRC dans le champ de garde de bloc comme requis dans les spécifications T10DIF.
MLX5DV_SIG_T10DIF_CSUM
Utiliser la somme de contrôle IP au lieu du CRC dans le champ de garde de bloc.
bg
Une graine pour le calcul de la garde de bloc par bloc.

Les valeurs suivantes sont prises en charge comme graine : 0, 0xFFFF (UINT16_MAX).

app_tag
Une balise d'application à générer ou à valider.
ref_tag
Une balise de référence à générer ou à valider.
flags
Indicateurs pour les attributs T10DIF, l'un des suivants.
MLX5DV_SIG_T10DIF_FLAG_REF_REMAP
Incrémenter la balise de référence par bloc.
MLX5DV_SIG_T10DIF_FLAG_APP_ESCAPE
Ne pas vérifier la garde de bloc si la balise d'application est 0xFFFF.
MLX5DV_SIG_T10DIF_FLAG_APP_REF_ESCAPE
Ne pas vérifier la garde de bloc si la balise d'application est 0xFFFF et la balise de référence est 0xFFFFFFFF.

VALEUR DE RETOUR

Cette fonction ne retourne aucune valeur.

En cas d'erreur, l'utilisateur sera informé ultérieurement lors de la finalisation de la chaîne de DV WRs.

Notes

Un contexte DEVX doit être ouvert en utilisant mlx5dv_open_device(3).

MKEY doit être créé avec le drapeau MLX5DV_MKEY_INIT_ATTR_FLAGS_BLOCK_SIGNATURE.

La dernière opération publiée sur le QP fourni doit être mlx5dv_wr_mkey_configure(3), ou l'un de ses configureurs associés, et l'opération doit toujours être ouverte (aucun doorbell émis).

En cas d'échec de ibv_wr_complete() ou d'appel à ibv_wr_abort(), le MKey peut rester dans un état inconnu. La prochaine configuration de celui-ci ne doit supposer aucun état précédent du MKey, c.-à-d. que la signature/le cryptage doit être reconfiguré ou réinitialisé, selon les besoins. Par exemple, en supposant que mlx5dv_wr_set_mkey_sig_block() puis ibv_wr_abort() aient été appelés, alors lors de la prochaine configuration du MKey, si la signature n'est pas nécessaire, elle doit être réinitialisée en utilisant MLX5DV_MKEY_CONF_FLAG_RESET_SIG_ATTR.

VOIR AUSSI

mlx5dv_wr_mkey_configure(3), mlx5dv_create_mkey(3), mlx5dv_destroy_mkey(3)
