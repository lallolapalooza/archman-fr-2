mlx5dv_create_qp(3) Manuel du programmeur mlx5 mlx5dv_create_qp(3)

NOM

mlx5dv_create_qp - crée une paire de files d'attente (QP)

SYNTAXE

#include <infiniband/mlx5dv.h>
struct ibv_qp *mlx5dv_create_qp(struct ibv_context         *context,
                                struct ibv_qp_init_attr_ex *qp_attr,
                                struct mlx5dv_qp_init_attr *mlx5_qp_attr)

DESCRIPTION

mlx5dv_create_qp() crée une paire de files d'attente (QP) avec des propriétés spécifiques au pilote.

ARGUMENTS

Veuillez consulter la page de manuel de ibv_create_qp_ex(3) pour context et qp_attr.

mlx5_qp_attr

struct mlx5dv_qp_init_attr {
    uint64_t comp_mask;
    uint32_t create_flags;
    struct mlx5dv_dc_init_attr  dc_init_attr;
    uint64_t send_ops_flags;
};
comp_mask
Masque de bits spécifiant quels champs de la structure sont valides : MLX5DV_QP_INIT_ATTR_MASK_QP_CREATE_FLAGS : valeurs valides dans create_flags MLX5DV_QP_INIT_ATTR_MASK_DC : valeurs valides dans dc_init_attr MLX5DV_QP_INIT_ATTR_MASK_SEND_OPS_FLAGS : valeurs valides dans send_ops_flags
create_flags
Un OU logique des différentes valeurs décrites ci-dessous.

MLX5DV_QP_CREATE_TUNNEL_OFFLOADS : Active le déchargement tel que la somme de contrôle et LRO pour le trafic tunnel entrant.

MLX5DV_QP_CREATE_TIR_ALLOW_SELF_LOOPBACK_UC : Autorise la réception du trafic unicast en boucle locale.

MLX5DV_QP_CREATE_TIR_ALLOW_SELF_LOOPBACK_MC : Autorise la réception du trafic multicast en boucle locale.

MLX5DV_QP_CREATE_DISABLE_SCATTER_TO_CQE : Désactive la fonctionnalité de dispersion dans le CQE, qui est activée par défaut.

MLX5DV_QP_CREATE_ALLOW_SCATTER_TO_CQE : Autorise la dispersion dans le CQE pour le demandeur même si le QP n'a pas été configuré pour signaler tous les WRs.

MLX5DV_QP_CREATE_PACKET_BASED_CREDIT_MODE : Configure le QP pour fonctionner en mode de crédit fin-à-fin basé sur les paquets, au lieu des crédits basés sur les messages par défaut (section 9.7.7.2 de la spécification IB).

Il incombe à l'application de s'assurer que le QP distant est configuré avec le même mode.

MLX5DV_QP_CREATE_SIG_PIPELINING : Si le drapeau est défini, le QP est déplacé à l'état SQD lors de la rencontre d'une erreur de signature, et IBV_EVENT_SQ_DRAINED est généré pour informer du nouvel état. La fonctionnalité de pipelining de signature est une optimisation des performances, qui réduit la latence des opérations de lecture dans les protocoles de stockage. La fonctionnalité est optionnelle. La création du QP échoue si le noyau ou l'appareil ne prend pas en charge cette fonctionnalité. Dans ce cas, une application doit revenir au mode de compatibilité descendante et gérer les opérations de lecture sans pipelining. Voir les détails sur le pipelining de signature dans mlx5dv_qp_cancel_posted_send_wrs(3).

MLX5DV_QP_CREATE_OOO_DP : Si le drapeau est défini, les WRs de réception du côté récepteur du QP sont autorisés à être consommés hors séquence et le côté émetteur du QP est autorisé à transmettre des messages sans garantir aucun ordre d'arrivée du côté récepteur.

Le drapeau, lorsqu'il est défini, doit l'être à la fois côté émetteur et côté récepteur d'un QP (par exemple, DCT et DCI).
La définition du drapeau est facultative et la disponibilité de cette fonctionnalité doit être interrogée par l'application (voir les détails dans
**mlx5dv_query_device**(3)) et il n'y a pas de repli automatique : si le
drapeau est défini alors que le noyau ou l'appareil ne prend pas en charge la fonctionnalité, la création du QP échoue. Ainsi, avant de créer un QP avec ce drapeau défini,
l'application doit interroger le nombre maximal de WRs de réception en attente possibles sur un QP avec ce drapeau défini, selon le type de QP (voir les détails dans
**mlx5dv_query_device**(3)) et s'assurer que la capacité est prise en charge.
> **Note**
>
> Tout ce qui suit décrit le comportement et la sémantique d'un QP
> avec ce drapeau défini.
Ordre de livraison des completions :
Un WR de réception posté sur ce QP peut être consommé par n'importe quel message arrivant à ce QP qui nécessite une consommation de WR de réception. Néanmoins, l'ordre dans lequel les completions de travail sont livrées pour les WRs postés, côté émetteur et côté récepteur, reste inchangé lorsque ce drapeau est défini (et est indépendant de l'ordre dans lequel les WRs de réception sont consommés). Le wr_id livré dans chaque work completion spécifiera quel WR a été complété par la work completion livrée.
Placement des données et ordre d'exécution des opérations :
Les opérations RDMA Read et RDMA Atomic sont exécutées côté répondeur dans l'ordre, c'est-à-dire que ces opérations sont exécutées après que toutes les opérations précédentes ont été exécutées.
Cependant, l'ordre des paquets de réponse RDMA Read étant dispersés dans la mémoire côté demandeur n'est pas garanti. Cela signifie que, bien que les données soient lues après l'exécution de toutes les opérations précédentes, elles peuvent être dispersées dans le désordre côté demandeur.
L'ordre des requêtes d'écriture vers la mémoire côté répondeur, initiées par RDMA Send, RDMA Send with Immediate, RDMA Write ou RDMA Write with Immediate n'est pas garanti.
Bonne et mauvaise pratique :
Puisqu'il ne peut être garanti quel RDMA Send (et/ou RDMA Send with Immediate) consommera un WR de réception (et dispersera ses données dans les tampons mémoire spécifiés dans le WR), il n'est pas recommandé de poster des WRs de réception de tailles différentes.
Sonder toute mémoire utilisée par l'appareil pour disperser des données n'est pas recommandé car l'ordre du placement des données des RDMA Send, RDMA Write et RDMA Write with Immediate n'est pas garanti.
Le récepteur, lors de la réception d'une completion pour un RDMA Write with Immediate, ne doit pas se fier uniquement au wr_id pour déterminer dans quelle mémoire les données ont été dispersées par l'opération.
dc_init_attr
Attributs d'initialisation DC.

dc_init_attr

struct mlx5dv_dci_streams {
    uint8_t log_num_concurent;
    uint8_t log_num_errored;
};
struct mlx5dv_dc_init_attr {
    enum mlx5dv_dc_type dc_type;
    union {
        uint64_t dct_access_key;
        struct mlx5dv_dci_streams dci_streams;
    };
};
dc_type
MLX5DV_DCTYPE_DCT Type de QP : DC cible. MLX5DV_DCTYPE_DCI Type de QP : Initiateur DC.
dct_access_key
utilisé pour créer un QP DCT.
dci_streams
dci_streams utilisé pour définir un QP DCI avec plusieurs flux concurrents. Valide lorsque comp_mask inclut MLX5DV_QP_INIT_ATTR_MASK_DCI_STREAMS.

log_num_concurent Définit le nombre de flux différents parallèles qui pourraient être gérés par le matériel. Toutes les requêtes de travail d'un stream_id spécifique sont gérées dans l'ordre.

log_num_errored Définit le nombre de canaux de flux d'erreur DCI avant de passer le DCI à un état d'erreur.

send_ops_flags
Un OU logique des différentes valeurs décrites ci-dessous.

MLX5DV_QP_EX_WITH_MR_INTERLEAVED : Active la requête de travail mlx5dv_wr_mr_interleaved() sur ce QP.

MLX5DV_QP_EX_WITH_MR_LIST : Active la requête de travail mlx5dv_wr_mr_list() sur ce QP.

MLX5DV_QP_EX_WITH_MKEY_CONFIGURE : Active la requête de travail mlx5dv_wr_mkey_configure() et les définisseurs associés sur ce QP.

NOTES

mlx5dv_qp_ex_from_ibv_qp_ex() est utilisé pour obtenir la struct mlx5dv_qp_ex pour accéder aux interfaces des opérations d'envoi lorsque IBV_QP_INIT_ATTR_SEND_OPS_FLAGS est utilisé.

Le drapeau MLX5DV_QP_CREATE_DISABLE_SCATTER_TO_CQE doit être défini dans les cas où IOVA ne correspond pas à l'adresse virtuelle du processus et où la taille de la charge utile du message est suffisamment petite pour déclencher la fonctionnalité de dispersion dans le CQE.

Lorsque la mémoire de l'appareil est utilisée, IBV_SEND_INLINE et la dispersion dans le CQE ne doivent pas être utilisés, car la copie mémoire (memcpy) n'est pas possible.

VALEUR DE RETOUR

mlx5dv_create_qp() renvoie un pointeur vers le QP créé. En cas d'erreur, NULL sera renvoyé et errno sera défini.
