mlock(2) Manuel des appels système mlock(2)

NOM

mlock, mlock2, munlock, mlockall, munlockall - verrouiller et déverrouiller la mémoire

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <sys/mman.h>
int mlock(const void addr, size_t len);
int mlock2(const void addr, size_t len, unsigned int flags);
int munlock(const void addr, size_t len);
int mlockall(int flags);
int munlockall(void);

DESCRIPTION

mlock(), mlock2() et mlockall() verrouillent tout ou partie de l'espace d'adressage virtuel du processus appelant en RAM, empêchant ainsi cette mémoire d'être paginée vers la zone d'échange.

munlock() et munlockall() effectuent l'opération inverse, déverrouillant tout ou partie de l'espace d'adressage virtuel du processus appelant, de sorte que les pages dans la plage d'adresses virtuelles spécifiée puissent être à nouveau échangées si nécessaire par le gestionnaire de mémoire du noyau.

Le verrouillage et le déverrouillage de la mémoire sont effectués par unités de pages entières.

mlock(), mlock2(), et munlock()

mlock() verrouille les pages dans la plage d'adresses commençant à addr et s'étendant sur len octets. Toutes les pages qui contiennent une partie de la plage d'adresses spécifiée sont garanties d'être résidentes en RAM lorsque l'appel retourne avec succès ; les pages sont garanties de rester en RAM jusqu'à ce qu'elles soient déverrouillées plus tard.

mlock2() verrouille également les pages dans la plage spécifiée commençant à addr et s'étendant sur len octets. Cependant, l'état des pages contenues dans cette plage après le retour réussi de l'appel dépendra de la valeur de l'argument flags.

L'argument flags peut être 0 ou la constante suivante :

MLOCK_ONFAULT
Verrouille les pages actuellement résidentes et marque la plage entière de manière à ce que les pages non résidentes restantes soient verrouillées lorsqu'elles sont peuplées par une faute de page.

Si flags est 0, mlock2() se comporte exactement comme mlock().

munlock() déverrouille les pages dans la plage d'adresses commençant à addr et s'étendant sur len octets. Après cet appel, toutes les pages qui contiennent une partie de la plage mémoire spécifiée peuvent à nouveau être déplacées vers l'espace d'échange externe par le noyau.

mlockall() et munlockall()

mlockall() verrouille toutes les pages mappées dans l'espace d'adressage du processus appelant. Cela inclut les pages du code, des données et du segment de pile, ainsi que les bibliothèques partagées, les données du noyau en espace utilisateur, la mémoire partagée et les fichiers mappés en mémoire. Toutes les pages mappées sont garanties d'être résidentes en RAM lorsque l'appel retourne avec succès ; les pages sont garanties de rester en RAM jusqu'à ce qu'elles soient déverrouillées plus tard.

L'argument flags est construit comme le OU bit à bit d'une ou plusieurs des constantes suivantes :

MCL_CURRENT
Verrouille toutes les pages actuellement mappées dans l'espace d'adressage du processus.
MCL_FUTURE
Verrouille toutes les pages qui seront mappées dans l'espace d'adressage du processus à l'avenir. Il peut s'agir, par exemple, de nouvelles pages requises par un tas et une pile en croissance, ainsi que de nouveaux fichiers mappés en mémoire ou de nouvelles régions de mémoire partagée.
MCL_ONFAULT (depuis Linux 4.4)
Utilisé conjointement avec MCL_CURRENT, MCL_FUTURE, ou les deux. Marque toutes les pages actuelles (avec MCL_CURRENT) ou futures (avec MCL_FUTURE) pour verrouiller les pages lorsqu'elles sont sollicitées. Lorsqu'il est utilisé avec MCL_CURRENT, toutes les pages présentes sont verrouillées, mais mlockall() ne sollicitera pas les pages non présentes. Lorsqu'il est utilisé avec MCL_FUTURE, tous les mappages futurs seront marqués pour verrouiller les pages lorsqu'elles seront sollicitées, mais elles ne seront pas peuplées par le verrouillage lors de la création du mappage. MCL_ONFAULT doit être utilisé avec soit MCL_CURRENT, soit MCL_FUTURE, soit les deux.

Si MCL_FUTURE a été spécifié, alors un appel système ultérieur (par exemple, mmap(2), sbrk(2), malloc(3)) peut échouer s'il devait entraîner le dépassement du nombre d'octets verrouillés par rapport au maximum autorisé (voir ci-dessous). Dans les mêmes circonstances, la croissance de la pile peut également échouer : le noyau refusera l'extension de la pile et délivrera un signal SIGSEGV au processus.

munlockall() déverrouille toutes les pages mappées dans l'espace d'adressage du processus appelant.

VALEUR RETOURNEE

En cas de succès, ces appels système retournent 0. En cas d'erreur, -1 est retourné, errno est défini pour indiquer l'erreur, et aucune modification n'est apportée aux verrous dans l'espace d'adressage du processus.

ERREURS

EAGAIN
(mlock(), mlock2(), et munlock()) Une partie ou la totalité de la plage d'adresses spécifiée n'a pas pu être verrouillée.
EINVAL
(mlock(), mlock2(), et munlock()) Le résultat de l'addition addr+len était inférieur à addr (par exemple, l'addition a pu provoquer un dépassement).
EINVAL
(mlock2()) Des flags inconnus ont été spécifiés.

VERSIONS

Linux

Sous Linux, mlock(), mlock2() et munlock() arrondissent automatiquement addr à la limite de page inférieure la plus proche. Cependant, la spécification POSIX.1 de mlock() et munlock() permet à une implémentation d'exiger que addr soit aligné sur une page, donc les applications portables devraient s'en assurer.

mlock2(2) — Arch manual pages

NAME

mlock2 — lock (and unlock) portions of memory

LIBRARY

Real-time library (librt, -lrt)

SYNOPSIS

#include <sys/mman.h>

int mlock(const void *addr, size_t len);
int munlock(const void *addr, size_t len);
int mlockall(int flags);
int munlockall(void);
int mlock2(const void *addr, size_t len, unsigned long flags);

DESCRIPTION

The mlock(), munlock(), mlockall(), and munlockall() functions lock the pages of the process's virtual address space specified by addr and len into RAM, while mlock2() adds new locking options.

Locking pages into RAM prevents the kernel from swapping them out.

mlock() and munlock()

The mlock() function locks the pages of the calling process's virtual address space that contain the bytes in the range [addr, addr + len - 1]. The range must be suitably aligned. Specifically, the value of addr must be a multiple of the page size, and len must be a multiple of the page size. The pages are locked in memory until they are unlocked. The pages are unlocked by a call to munlock() specifying the same range.

The munlock() function unlocks the pages in the range [addr, addr + len - 1]. The range must be suitably aligned as for mlock().

mlockall() and munlockall()

The mlockall() function locks all currently mapped pages of the calling process's virtual address space and any pages that are mapped in the future. The behavior is controlled by flags, which can be bitwise ORed:

MCL_CURRENT
Lock all pages that are currently mapped for the process.
MCL_FUTURE
Lock pages that will be mapped in the future for the process. This includes memory that will be allocated by subsequent calls to mmap(2) and brk(2).
MCL_ONFAULT
Lock pages in all current and future mappings as they are accessed. This is a more efficient way to lock memory, as it avoids the penalty of locking all pages in a large mapping even if only a small portion is actually touched. This flag can be combined with MCL_CURRENT and MCL_FUTURE.

The munlockall() function unlocks all pages that have been locked by mlockall().

mlock2()

The mlock2() function is a superset of mlock(). It locks the pages of the calling process's virtual address space that contain the bytes in the range [addr, addr + len - 1]. The range must be suitably aligned. The behavior is controlled by flags, which can be bitwise ORed:

MLOCK_ONFAULT
Lock pages in the specified range as they are accessed. This flag can be combined with MLOCK_CURRENT (implicitly enabled if MLOCK_ONFAULT is used alone) and MLOCK_FUTURE.
MLOCK_FUTURE
Lock pages that will be mapped in the future for the process within the specified range. This flag can be combined with MLOCK_ONFAULT.

The mlock2() function locks pages in RAM. It is similar to mlock() but supports the MLOCK_ONFAULT and MLOCK_FUTURE flags.

RETURN VALUE

On success, zero is returned. On failure, -1 is returned, and errno is set to indicate the error.

ERRORS

The mlock(), munlock(), mlockall(), and mlock2() functions can fail for the following reasons:

EAGAIN
Not enough memory is available to satisfy the locking request.
EINVAL
mlock() or munlock() was called with non page-aligned addresses or size, or an invalid flag was specified to mlock2().
EPERM
The calling process does not have the CAP_IPC_LOCK capability, and the memory lock limit (setrlimit(2) RLIMIT_MEMLOCK) has been reached.
ENOMEM
The specified address range is not valid.

The munlockall() function can fail with EPERM if the caller does not have the CAP_IPC_LOCK capability and the memory lock limit has been reached.

VERSIONS

The mlock2() function was introduced in Linux 4.4.

mlock() and munlock()

These functions first appeared in Linux Kernel 1.1.18.

mlockall() and munlockall()

These functions first appeared in Linux Kernel 1.1.37.

STANDARDS

mlock(), munlock(), mlockall(), and munlockall() conform to POSIX.1-2008.

mlock2() is Linux-specific.

On POSIX systems on which mlock() and munlock() are available, _POSIX_MEMLOCK_RANGE is defined in <unistd.h> and the number of bytes in a page can be determined from the constant PAGESIZE (if defined) in <limits.h> or by calling sysconf(_SC_PAGESIZE).

On POSIX systems on which mlockall() and munlockall() are available, _POSIX_MEMLOCK is defined in <unistd.h> to a value greater than 0. (See also sysconf(3).)

HISTORY

mlock()

These functions first appeared in Linux Kernel 1.1.18.

mlockall()

These functions first appeared in Linux Kernel 1.1.37.

mlock2()

Linux 4.4.

NOTES

Memory locking has two main applications: real-time algorithms and high-security data processing. Real-time applications require deterministic timing, and, like scheduling, paging is one major cause of unexpected program execution delays. Real-time applications will usually also switch to a real-time scheduler with sched_setscheduler(2). Cryptographic security software often handles critical bytes like passwords or secret keys as data structures. As a result of paging, these secrets could be transferred onto a persistent swap store medium, where they might be accessible to the enemy long after the security software has erased the secrets in RAM and terminated. (But be aware that the suspend mode on laptops and some desktop computers will save a copy of the system's RAM to disk, regardless of memory locks.)

Real-time processes that are using mlockall() to prevent delays on page faults should reserve enough locked stack pages before entering the time-critical section, so that no page fault can be caused by function calls. This can be achieved by calling a function that allocates a sufficiently large automatic variable (an array) and writes to the memory occupied by this array in order to touch these stack pages. This way, enough pages will be mapped for the stack and can be locked into RAM. The dummy writes ensure that not even copy-on-write page faults can occur in the critical section.

Memory locks are not inherited by a child created via fork(2) and are automatically removed (unlocked) during an execve(2) or when the process terminates. The mlockall() MCL_FUTURE and MCL_FUTURE | MCL_ONFAULT settings are not inherited by a child created via fork(2) and are cleared during an execve(2).

Note that fork(2) will prepare the address space for a copy-on-write operation. The consequence is that any write access that follows will cause a page fault that in turn may cause high latencies for a real-time process. Therefore, it is crucial not to invoke fork(2) after an mlockall() or mlock() operation—not even from a thread which runs at a low priority within a process which also has a thread running at elevated priority.

The memory lock on an address range is automatically removed if the address range is unmapped via munmap(2).

Memory locks do not stack, that is, pages which have been locked several times by calls to mlock(), mlock2(), or mlockall() will be unlocked by a single call to munlock() for the corresponding range or by munlockall(). Pages which are mapped to several locations or by several processes stay locked into RAM as long as they are locked at least at one location or by at least one process.

If a call to mlockall() which uses the MCL_FUTURE flag is followed by another call that does not specify this flag, the changes made by the MCL_FUTURE call will be lost.

The mlock2() MLOCK_ONFAULT flag and the mlockall() MCL_ONFAULT flag allow efficient memory locking for applications that deal with large mappings where only a (small) portion of pages in the mapping are touched. In such cases, locking all of the pages in a mapping would incur a significant penalty for memory locking.

Limits and permissions

In Linux 2.6.8 and earlier, a process must be privileged (CAP_IPC_LOCK) in order to lock memory and the RLIMIT_MEMLOCK soft resource limit defines a limit on how much memory the process may lock.

Since Linux 2.6.9, no limits are placed on the amount of memory that a privileged process can lock and the RLIMIT_MEMLOCK soft resource limit instead defines a limit on how much memory an unprivileged process may lock.

BUGS

In Linux 4.8 and earlier, a bug in the kernel's accounting of locked memory for unprivileged processes (i.e., without CAP_IPC_LOCK) meant that if the region specified by addr and len overlapped an existing lock, then the already locked bytes in the overlapping region were counted twice when checking against the limit. Such double accounting could incorrectly calculate a "total locked memory" value for the process that exceeded the RLIMIT_MEMLOCK limit, with the result that mlock() and mlock2() would fail on requests that should have succeeded. This bug was fixed in Linux 4.9.

In Linux 2.4 series of kernels up to and including Linux 2.4.17, a bug caused the mlockall() MCL_FUTURE flag to be inherited across a fork(2). This was rectified in Linux 2.4.18.

Since Linux 2.6.9, if a privileged process calls mlockall(MCL_FUTURE) and later drops privileges (loses the CAP_IPC_LOCK capability by, for example, setting its effective UID to a nonzero value), then subsequent memory allocations (e.g., mmap(2), brk(2)) will fail if the RLIMIT_MEMLOCK resource limit is encountered.
