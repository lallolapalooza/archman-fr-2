NOM

mosquitto_pub - un client MQTT version 5/3.1.1/3.1 pour publier des messages simples

SYNTAXE

mosquitto_pub {[-h nom_hôte] [--unix chemin_socket] [-p numéro_port] [-u nom_utilisateur] [-P mot_de_passe] -t sujet_message... | -L URL} [-A adresse_liaison] [-c] [-d] [-D commande identifiant valeur] [-i id_client] [-I préfixe_id_client] [-k temps_maintien_connexion] [--nodelay] [-q QoS_message] [--quiet] [-r] [--repeat nombre] [--repeat-delay secondes] [-S] [-V version_protocole] [-x intervalle_expiration_session] {-f fichier | -l | -m message | -n | -s} [--will-topic sujet [--will-payload charge_utile] [--will-qos qos] [--will-retain]] [[{--cafile fichier | --capath répertoire} [--cert fichier] [--key fichier] [--ciphers chiffrements] [--tls-version version] [--tls-alpn protocole] [--tls-engine moteur] [--keyform {pem | moteur}] [--tls-engine-kpass-sha1 kpass-sha1] [--tls-use-os-certs] [--insecure]] | [--psk clé_hex --psk-identity identité [--ciphers chiffrements] [--tls-version version]]] [--proxy url_socks]

mosquitto_pub [--help]

DESCRIPTION

mosquitto_pub est un client simple de MQTT version 5 qui publie un seul message sur un sujet et se termine.

CONNEXIONS CHIFFRÉES

mosquitto_pub prend en charge les connexions chiffrées TLS. Il est fortement recommandé d'utiliser une connexion chiffrée pour toute application autre que la configuration la plus basique.

Pour activer les connexions TLS lors de l'utilisation de certificats x509, l'une des options --cafile ou --capath peut être fournie.

Alternativement, si l'option -p 8883 est utilisée, les certificats fournis par le système d'exploitation seront chargés et ni --cafile ni --capath ne seront nécessaires.

Pour activer les connexions TLS lors de l'utilisation de TLS-PSK, vous devez utiliser les options --psk et --psk-identity.

OPTIONS

Les options ci-dessous peuvent être fournies en ligne de commande, mais peuvent également être placées dans un fichier de configuration situé à $XDG_CONFIG_HOME/mosquitto_pub ou $HOME/.config/mosquitto_pub avec une paire -option valeur par ligne. Les valeurs du fichier de configuration seront utilisées comme valeurs par défaut et peuvent être remplacées en utilisant la ligne de commande. Les exceptions à cela sont les options de type de message, dont une seule peut être spécifiée. Notez également que certaines options ne peuvent pas être niées, par exemple -S. Les lignes de fichier de configuration qui commencent par un # sont traitées comme des commentaires et ne sont pas traitées davantage.

-A

Lier la connexion sortante à une adresse IP/nom d'hôte local. Utilisez cet argument si vous avez besoin de restreindre la communication réseau à une interface particulière.

-c, --disable-clean-session

Désactiver la session "propre" / activer le mode client persistant. Lorsque cet argument est utilisé, le broker sera invité à ne pas nettoyer les sessions existantes pour le même identifiant client lors de la connexion du client, et les sessions n'expireront jamais lorsque le client se déconnectera. Les clients MQTT v5 peuvent modifier leur intervalle d'expiration de session avec l'argument -x.

Lorsqu'une session est conservée sur le broker, les abonnements du client seront maintenus après sa déconnexion, ainsi que les messages ultérieurs de QoS 1 et QoS 2 qui arrivent. Lorsque le client se reconnecte et ne nettoie pas la session, il recevra tous les messages mis en file d'attente.

Si vous utilisez cette option, l'identifiant client doit être défini manuellement avec --id

--cafile

Définir le chemin vers un fichier contenant les certificats CA encodés en PEM qui sont de confiance. Utilisé pour activer la communication SSL.

Voir aussi --capath

--capath

Définir le chemin vers un répertoire contenant les certificats CA encodés en PEM qui sont de confiance. Utilisé pour activer la communication SSL.

Pour que --capath fonctionne correctement, les fichiers de certificat doivent avoir l'extension ".crt" et vous devez exécuter "openssl rehash <chemin vers capath>" chaque fois que vous ajoutez/supprimez un certificat.

Voir aussi --cafile

--cert

Définir le chemin vers un fichier contenant un certificat encodé en PEM pour ce client, si requis par le serveur.

Voir aussi --key et la section Connexions Chiffrées.

--ciphers

Une liste de chiffrements TLS compatible openssl à prendre en charge par le client. Voir ciphers(1) pour plus d'informations.

-d, --debug

Activer les messages de débogage.

-D, --property

Utiliser une propriété MQTT v5 avec cette publication. Si vous utilisez cette option, le client sera configuré pour être un client MQTT v5. Cette option a deux formes :

-D commande identifiant valeur

-D commande identifiant nom valeur

commande est l'identifiant de la commande/du paquet MQTT et peut être CONNECT, PUBLISH, PUBREL, DISCONNECT, AUTH, ou WILL. Les propriétés disponibles pour chaque commande sont listées dans la section Propriétés.

identifiant est le nom de la propriété à ajouter. Il est décrit dans la spécification, mais avec '-' comme séparateur de mots. Par exemple : payload-format-indicator. Plus de détails dans la section Propriétés.

valeur est la valeur de la propriété à ajouter, avec un type de données spécifique à la propriété.

nom est utilisé uniquement pour la propriété user-property comme première des deux chaînes de la paire de chaînes. Dans ce cas, valeur est la seconde des chaînes de la paire.

-f, --file

Envoyer le contenu d'un fichier comme message.

--help

Afficher les informations d'utilisation.

-h, --host

Spécifier l'hôte de connexion. Par défaut : localhost.

-i, --id

L'identifiant à utiliser pour ce client. S'il n'est pas fourni, un identifiant client sera généré en fonction de la version MQTT utilisée. Pour v3.1.1/v3.1, le client génère un identifiant client au format mosq-XXXXXXXXXXXXXXXXXX, où les X sont remplacés par des caractères alphanumériques aléatoires. Pour v5.0, le client envoie un identifiant client de longueur nulle, et le serveur générera un identifiant client pour le client.

Cette option ne peut pas être utilisée en même temps que l'argument --id-prefix.

-I, --id-prefix

Fournir un préfixe à partir duquel l'identifiant client sera construit en ajoutant l'ID de processus du client. Ceci est utile lorsque le broker utilise l'option clientid_prefixes. Ne peut pas être utilisé en même temps que l'argument --id.

--insecure

Lors de l'utilisation du chiffrement basé sur des certificats, cette option désactive la vérification du nom d'hôte du serveur dans le certificat serveur. Cela peut être utile lors des tests de configurations initiales du serveur, mais rend possible pour un tiers malveillant d'usurper votre serveur par un renvoi DNS, par exemple. Utilisez cette option en test uniquement. Si vous avez besoin de recourir à cette option dans un environnement de production, votre configuration est défectueuse et il est inutile d'utiliser le chiffrement.

-k, --keepalive

Le nombre de secondes entre l'envoi des commandes PING au broker afin de l'informer que nous sommes toujours connectés et fonctionnels. Par défaut, 60 secondes.

--key

Définir le chemin vers un fichier contenant une clé privée encodée en PEM pour ce client, si requis par le serveur.

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

r.

Voir aussi --cert et la section Connexions chiffrées.

--keyform

Spécifie le type de clé privée utilisée lors de l'établissement de connexions TLS. Cela peut être « pem » ou « engine ». Ce paramètre est utile lorsqu'un module TPM est utilisé et que la clé privée a été créée avec lui. La valeur par défaut est « pem », ce qui signifie que des fichiers de clés privées normaux sont utilisés.

Voir aussi --tls-engine.

-L, --url

Spécifiez l'utilisateur, le mot de passe, le nom d'hôte, le port et le sujet en une seule fois sous forme d'URL. L'URL doit être de la forme : mqtt(s)://[nom_utilisateur[:mot_de_passe]@]hôte[:port]/sujet

Si le schéma est mqtt://, le port par défaut est 1883. Si le schéma est mqtts://, le port par défaut est 8883.

-l, --stdin-line

Envoie des messages lus depuis l'entrée standard, en divisant les lignes séparées en messages distincts.

-m, --message

Envoie un seul message depuis la ligne de commande.

-n, --null-message

Envoie un message nul (de longueur zéro).

--nodelay

Désactive l'algorithme de Nagle pour le socket. Cela signifie que la latence des messages envoyés est réduite, ce qui est particulièrement perceptible pour les messages petits et raisonnablement peu fréquents. L'utilisation de cette option peut entraîner l'envoi d'un plus grand nombre de paquets que nécessaire normalement.

-p, --port

Connectez-vous au port spécifié. Si non spécifié, le défaut de 1883 pour le MQTT brut ou 8883 pour le MQTT sur TLS sera utilisé.

-P, --pw

Fournissez un mot de passe à utiliser pour l'authentification auprès du courtier. L'utilisation de cet argument sans spécifier également un nom d'utilisateur est invalide lors de l'utilisation de MQTT v3.1 ou v3.1.1. Voir aussi l'option --username.

--proxy

Spécifiez un proxy SOCKS5 pour vous connecter. Les types d'authentification « None » et « username » sont pris en charge. L'URL socks-url doit être de la forme socks5h://[nom_utilisateur[:mot_de_passe]@]hôte[:port]. Le préfixe de protocole socks5h signifie que les noms d'hôte sont résolus par le proxy. Les symboles %25, %3A et %40 sont décodés en URL en %, : et @ respectivement, s'ils sont présents dans le nom d'utilisateur ou le mot de passe.

Si le nom d'utilisateur n'est pas donné, aucune authentification n'est tentée. Si le port n'est pas donné, le défaut de 1080 est utilisé.

D'autres versions de SOCKS pourraient être disponibles à l'avenir, en fonction de la demande, et utiliseront des préfixes de protocole différents comme décrit dans curl(1).

--psk

Fournissez la clé pré-partagée (psk) hexadécimale (sans préfixe 0x) correspondant à celle utilisée sur le courtier pour utiliser la prise en charge du chiffrement TLS-PSK. --psk-identity doit également être fourni pour activer TLS-PSK.

--psk-identity

L'identité client à utiliser avec la prise en charge TLS-PSK. Cela peut être utilisé à la place d'un nom d'utilisateur si le courtier est configuré pour le faire.

-q, --qos

Spécifiez la qualité de service (QoS) à utiliser pour le message, de 0, 1 et 2. La valeur par défaut est 0.

--quiet

Si cet argument est donné, aucune erreur d'exécution ne sera imprimée. Cela exclut les messages d'erreur donnés en cas d'entrée utilisateur invalide (par exemple, en utilisant --port sans port).

-r, --retain

Si retain est donné, le message sera conservé comme une valeur « dernière bonne connue » sur le courtier. Voir mqtt(7) pour plus d'informations. Notez que les charges utiles de longueur nulle ne sont jamais conservées. Si vous envoyez un message conservé avec une charge utile de longueur nulle, cela effacera tout message conservé sur le sujet.

--repeat

Si le mode de publication est -m, -f, ou -s (c'est-à-dire les modes où un seul message est envoyé), alors --repeat peut être utilisé pour spécifier que le message sera publié plusieurs fois.

Voir aussi --repeat-delay.

--repeat-delay

Si vous utilisez --repeat, le comportement par défaut est de publier les messages répétés dès que le message précédent est délivré. Utilisez --repeat-delay pour spécifier le nombre de secondes à attendre après la délivrance du message précédent avant de publier le suivant. N'a pas besoin d'être un nombre entier de secondes.

Notez qu'il n'y a aucune garantie quant à l'intervalle réel entre les messages, cette option définit simplement le temps minimum entre la délivrance d'un message et le début de la publication du suivant.

-s, --stdin-file

Envoie un message lu depuis l'entrée standard, en envoyant tout le contenu comme un seul message.

-S

Utilise les recherches SRV pour déterminer quel hôte contacter. Effectue des recherches pour _mqtt._tcp.<hôte> lorsqu'il est utilisé en conjonction avec -h, sinon utilise _mqtt._tcp.<domaine dns local>.

-t, --topic

Le sujet MQTT sur lequel publier le message. Voir mqtt(7) pour plus d'informations sur les sujets MQTT.

--tls-alpn

Fournissez un protocole à utiliser lors de la connexion à un courtier qui dispose de plusieurs protocoles disponibles sur un seul port, par exemple MQTT et WebSockets.

--tls-engine

Un identifiant de moteur openssl valide. Ceux-ci peuvent être listés avec la commande openssl engine.

Voir aussi --keyform.

--tls-engine-kpass-sha1

SHA1 du mot de passe de la clé privée lors de l'utilisation d'un moteur TLS. Certains moteurs TLS tels que le moteur TPM peuvent nécessiter l'utilisation d'un mot de passe pour y accéder. Cette option permet de fournir directement un hachage SHA1 hexadécimal du mot de passe au moteur, au lieu que l'utilisateur soit invité à entrer le mot de passe.

Voir aussi --tls-engine.

--tls-use-os-certs

Si utilisé, cela chargera et fera confiance aux certificats CA fournis par le système d'exploitation. Cela peut être utilisé en conjonction avec --cafile et --capath et peut être utilisé seul pour activer le mode TLS. Ceci sera défini par défaut si -L mqtts://... est utilisé, ou si le port est 8883 et aucune autre option de certificat n'est utilisée.

--tls-version

Choisissez la version du protocole TLS à utiliser lors de la communication avec le courtier. Les options valides sont tlsv1.3, tlsv1.2 et tlsv1.1. La valeur par défaut est tlsv1.2. Doit correspondre à la version du protocole utilisée par le courtier.

-u, --username

Fournissez un nom d'utilisateur à utiliser pour l'authentification auprès du courtier. Voir aussi l'argument --pw.

--unix

Connectez-vous à un courtier via un socket de domaine Unix local au lieu d'un socket TCP. Ceci remplace -h et -L. Par exemple : mosquitto_pub --unix /tmp/mosquitto.sock ...

Voir l'option socket_domain dans mosquitto.conf(5) pour configurer Mosquitto pour écouter sur un socket Unix.

-V, --protocol-version

Spécifiez quelle version du protocole MQTT doit être utilisée lors de la connexion au courtier distant. Peut être 5, 311, 31, ou les plus verbeux mqttv5, mqttv311, ou mqttv31. La valeur par défaut est 311.

--will-payload

Spécifiez un message qui sera stocké par le courtier et envoyé si ce client se déconnecte de manière inattendue. Ceci doit être utilisé en conjonction avec --will-topic.

--will-qos

Le QoS à utiliser pour le Will. La valeur par défaut est 0. Ceci doit être utilisé en conjonction avec --will-topic.

--will-retain

Si donné, si le client se déconnecte de manière inattendue, le message envoyé sera traité comme un message conservé. Ceci doit être utilisé en conjonction avec --will-topic. Notez que les charges utiles de longueur nulle ne sont jamais conservées. Si vous envoyez un message conservé avec une charge utile de longueur nulle, cela effacera tout message conservé sur le sujet.

--will-topic

Le sujet sur lequel envoyer un Will, dans le cas où le client se déconnecte de manière inattendue.

-x

Définit la propriété session-expiry-interval sur le paquet CONNECT. S'applique uniquement aux clients MQTT v5. Défini sur 0-4294967294 pour spécifier que la session expirera dans ce nombre de secondes après la déconnexion du client, ou utilisez -1, 4294967295, ou ∞ pour une session qui n'expire pas. La valeur par défaut est -1 si -c est également donné, ou 0 si -c n'est pas donné.

Si la session est définie pour ne jamais expirer, que ce soit avec -x ou -c, alors un identifiant client doit être fourni.

WILLS

mosquitto_sub peut enregistrer un message auprès du courtier qui sera envoyé s'il se déconnecte de manière inattendue. Voir mqtt(7) pour plus d'informations.

L'exigence minimale pour cela est d'utiliser --will-topic pour spécifier sur quel sujet le Will doit être envoyé. Cela entraînera un message non conservé, de longueur nulle et de QoS 0.

Utilisez les arguments --will-retain, --will-payload et --will-qos pour modifier les autres paramètres du Will.

PROPRIÉTÉS

L'option -D / --property permet d'ajouter des propriétés à différentes étapes de l'exécution de mosquitto_pub. Les propriétés prises en charge pour chaque commande sont les suivantes :

Connect

•authentication-data (données binaires - remarque : traité comme une chaîne dans mosquitto_pub)
•authentication-method (paire de chaînes UTF-8)
•maximum-packet-size (entier non signé 32 bits)
•receive-maximum (entier non signé 16 bits)
•request-problem-information (entier non signé 8 bits)
•request-response-information (entier non signé 8 bits)
•session-expiry-interval (entier non signé 32 bits, notez l'utilisation de -x à la place)
•topic-alias-maximum (entier non signé 16 bits)
•user-property (paire de chaînes UTF-8)

Publish

•content-type (chaîne UTF-8)
•correlation-data (données binaires - remarque : traité comme une chaîne dans mosquitto_pub)
•message-expiry-interval (entier non signé 32 bits)
•payload-format-indicator (entier non signé de 8 bits)
•response-topic (chaîne UTF-8)
•topic-alias (entier non signé de 16 bits)
•user-property (paire de chaînes UTF-8)

Disconnect

•session-expiry-interval (entier non signé de 32 bits)
•user-property (paire de chaînes UTF-8)

Will properties

•content-type (chaîne UTF-8)
•correlation-data (données binaires - noté comme une chaîne dans mosquitto_pub)
•message-expiry-interval (entier non signé de 32 bits)
•payload-format-indicator (entier non signé de 8 bits)
•response-topic (chaîne UTF-8)
•user-property (paire de chaînes UTF-8)
•will-delay-interval (entier non signé de 32 bits)

EXIT STATUS

mosquitto_sub retourne zéro en cas de succès, ou une valeur non nulle en cas d'erreur. Si la connexion est refusée par le broker au niveau MQTT, le code de sortie est le code de raison CONNACK. Si une autre erreur se produit, le code de sortie est une valeur de retour de libmosquitto.

Codes CONNACK MQTT v3.1.1 :

•0 Succès
•1 Connexion refusée : mauvaise version de protocole
•2 Connexion refusée : identifiant rejeté
•3 Connexion refusée : serveur indisponible
•4 Connexion refusée : mauvais nom d'utilisateur/mot de passe
•5 Connexion refusée : non autorisé

Codes CONNACK MQTT v5 :

•0 Succès
•128 Erreur non spécifiée
•129 Paquet malformé
•130 Erreur de protocole
•131 Erreur spécifique à l'implémentation
•132 Version de protocole non prise en charge
•133 ID client invalide
•134 Mauvais nom d'utilisateur ou mot de passe
•135 Non autorisé
•136 Serveur indisponible
•137 Serveur occupé
•138 Bannière
•139 Serveur en cours d'arrêt
•140 Méthode d'authentification incorrecte
•141 Dépassement du délai de conservation
•142 Session reprise
•143 Filtre de sujet invalide
•144 Nom de sujet invalide
•147 Dépassement du maximum de réception
•148 Alias de sujet invalide
•149 Paquet trop volumineux
•148 Taux de messages trop élevé
•151 Quota dépassé
•152 Action administrative
•153 Format de charge utile invalide
•154 Rétention non prise en charge
•155 QoS non pris en charge
•156 Utiliser un autre serveur
•157 Serveur déplacé
•158 Abonnements partagés non pris en charge
•159 Taux de connexion dépassé
•160 Durée maximale de connexion
•161 ID d'abonnement non pris en charge
•162 Abonnements génériques non pris en charge

EXAMPLES

Publier des informations de température sur localhost avec QoS 1 :

•mosquitto_pub -t sensors/temperature -m 32 -q 1

Publier des informations d'horodatage et de température sur un hôte distant sur un port non standard et avec QoS 0 :

•mosquitto_pub -h 192.168.1.1 -p 1885 -t sensors/temperature -m "1266193804 32"

Publier l'état de l'interrupteur de lumière. Le message est défini comme conservé car il peut y avoir un long délai entre les événements d'interrupteur de lumière :

•mosquitto_pub -r -t switches/kitchen_lights/status -m "on"

Envoyer le contenu d'un fichier de deux manières :

•mosquitto_pub -t my/topic -f ./data
•mosquitto_pub -t my/topic -s < ./data

Envoyer des données d'utilisation d'électricité analysées à partir d'un compteur Current Cost, en lisant depuis stdin avec une ligne/lecture par message :

•read_cc128.pl | mosquitto_pub -t sensors/cc128 -l
