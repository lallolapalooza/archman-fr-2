NOM

mono - Générateur de code natif ECMA-CLI de Mono (Juste-à-temps et Ahead-of-Time)

SYNTAXE

mono [options] fichier [arguments...]

mono-sgen [options] fichier [arguments...]

DESCRIPTION

mono est une implémentation d'exécution de l'infrastructure commune ECMA (ECMA Common Language Infrastructure). Elle peut être utilisée pour exécuter des applications ECMA et .NET.

L'environnement d'exécution charge le fichier spécifié et transmet éventuellement les arguments à celui-ci. Le fichier est un assemblage ECMA. Ils ont généralement une extension .exe ou .dll.

Ces exécutables peuvent référencer des fonctionnalités supplémentaires sous forme de références d'assemblage. Par défaut, ces références d'assemblage sont résolues comme suit : mscorlib.dll est résolu à partir du profil système configuré par Mono, et d'autres assemblages sont chargés depuis le Global Assembly Cache (GAC).

L'environnement d'exécution contient un générateur de code natif qui transforme le langage intermédiaire commun (Common Intermediate Language) en code natif.

Le générateur de code peut fonctionner dans deux modes : compilation juste-à-temps (JIT) ou compilation Ahead-of-time (AOT). Étant donné que le code peut être chargé dynamiquement, l'environnement d'exécution et le JIT sont toujours présents, même si le code est compilé ahead-of-time.

L'environnement d'exécution fournit un certain nombre d'options de configuration pour exécuter des applications, pour le développement et le débogage, ainsi que pour tester et déboguer l'environnement d'exécution lui-même.

La commande mono utilise le garbage collector SGen (mobile et générationnel), tandis que la commande mono-boehm utilise le garbage collector conservateur de Boehm.

PORTABILITÉ

Sur les systèmes de type Unix, Mono fournit un mécanisme pour émuler l'accès aux fichiers de style Windows, y compris la fourniture d'une vue du système de fichiers insensible à la casse, la cartographie des séparateurs de répertoire (de \ à /) et la suppression des lettres de lecteur.

Cette fonctionnalité est activée en définissant la variable d'environnement MONO_IOMAP sur l'une des valeurs suivantes : all, drive et case.

Voir la description de MONO_IOMAP dans la section des variables d'environnement pour plus de détails.

DESCRIPTION DES MÉTHODES

Un certain nombre d'options de ligne de commande de diagnostic prennent comme argument une description de méthode. Une description de méthode est une représentation textuelle qui peut être utilisée pour identifier uniquement une méthode. La syntaxe est la suivante :

[espace_de_noms]nom_classe:nom_méthode[(arguments)]

Les valeurs entre crochets sont facultatives, comme l'espace de noms et les arguments. Les arguments eux-mêmes sont soit vides, soit une liste d'arguments séparés par des virgules. Le nom_classe et le nom_méthode peuvent tous deux être définis sur la valeur spéciale '*' pour correspondre à n'importe quelle valeur (les utilisateurs de shells Unix devraient échapper l'argument pour éviter que le shell n'interprète cela).

Les arguments, s'ils sont présents, doivent être une liste de types séparés par des virgules, soit un nom de type complet, soit, pour les types intégrés, il faut utiliser les noms de types ILAsm de bas niveau pour les types intégrés, comme 'void', 'char', 'bool', 'byte', 'sbyte', 'uint16', 'int16', 'uint',

Les types pointeurs doivent être le nom du type, suivi de '*', les tableaux doivent être le nom du type suivi de '[' une ou plusieurs virgules (pour indiquer le rang du tableau), et ']'.

Les valeurs génériques doivent utiliser '<', un ou plusieurs noms de types, séparés par une virgule et un espace, et '>'.

Les arguments passés par référence doivent inclure un "&" après le nom du type.

Exemples :

*:ctor(int)		// Tous les constructeurs qui prennent un int comme argument
*:Main			// Méthodes nommées Main dans n'importe quelle classe
*:Main(string[])	// Méthodes nommées Main qui prennent un tableau de chaînes dans n'importe quelle classe

OPTIONS DE RUNTIME

Les options suivantes sont disponibles :

--aot, --aot[=options]
Cette option est utilisée pour précompiler le code CIL de l'assemblage spécifié en code natif. Le code généré est stocké dans un fichier avec l'extension .so. Ce fichier sera automatiquement récupéré par l'exécution lorsque l'assemblage sera exécuté. La compilation Ahead-of-Time est plus utile si vous l'utilisez en combinaison avec l'option -O=all,-shared qui active toutes les optimisations dans le générateur de code. Certaines de ces optimisations ne sont pas pratiques pour la compilation Juste-à-temps car elles peuvent être très chronophages. Contrairement au .NET Framework, la compilation Ahead-of-Time ne générera pas de code indépendant du domaine : elle génère le même code que celui que le compilateur Juste-à-temps produirait. Comme la plupart des applications utilisent un seul domaine, cela convient. Si vous souhaitez optimiser le code généré pour une utilisation dans des applications multi-domaines, envisagez d'utiliser l'option -O=shared. Ceci précompile les méthodes, mais l'assemblage d'origine est toujours requis pour l'exécution car celui-ci contient les métadonnées et les informations d'exception qui ne sont pas disponibles dans le fichier généré. Lors de la précompilation du code, vous pourriez vouloir compiler avec toutes les optimisations (-O=all). Le code précompilé est du code indépendant de la position. La précompilation est simplement un mécanisme pour réduire le temps de démarrage, augmenter le partage de code entre plusieurs processus mono et éviter les coûts de démarrage du programme de compilation Juste-à-temps. L'assemblage d'origine doit toujours être présent, car les métadonnées y sont contenues. Le code AOT ne peut généralement pas être déplacé d'un ordinateur à l'autre (optimisations spécifiques au processeur détectées au moment de l'exécution), vous ne devriez donc pas essayer de déplacer les assemblages pré-générés ou de les empaqueter pour le déploiement. Quelques options sont disponibles en tant que paramètre de l'option de ligne de commande --aot. Les options sont séparées par des virgules, et plus d'une peut être spécifiée :
asmonly
Demande au compilateur AOT de produire du code assembleur au lieu d'un fichier objet.
bind-to-runtime-version
Si spécifié, force les fichiers AOT générés à être liés à la version de l'environnement d'exécution du Mono qui compile. Cela empêchera les fichiers AOT d'être utilisés par un environnement d'exécution Mono différent.
data-outfile=FICHIER.dll.aotdata
Cela demande au générateur de code AOT de produire certaines constructions de données dans un fichier séparé. Cela peut réduire les images exécutables d'environ cinq à vingt pour cent. Les développeurs doivent ensuite expédier les aotdata résultants en tant que ressource et enregistrer un hook pour charger les données à la demande en utilisant la méthode mono_install_load_aot_data_hook.
direct-icalls
Lorsque cette option est spécifiée, les icalls (appels internes de la bibliothèque standard vers le code de l'environnement d'exécution mono) sont invoqués directement au lieu de passer par l'opération de recherche de symboles du système d'exploitation. Cela nécessite l'utilisation de l'option static.
direct-pinvoke
Lorsque cette option est spécifiée, les méthodes P/Invoke sont invoquées directement au lieu de passer par l'opération de recherche de symboles du système d'exploitation. Cela nécessite l'utilisation de l'option static.
dwarfdebug
Demande au compilateur AOT d'émettre des informations de débogage DWARF. Lorsqu'elle est utilisée conjointement avec l'option nodebug, seules les informations de débogage DWARF sont émises, mais pas les informations qui peuvent être utilisées au moment de l'exécution.
full
Ceci crée des binaires qui peuvent être utilisés avec l'option --full-aot.
hybrid
Ceci crée des binaires qui peuvent être utilisés avec l'option --hybrid-aot.
llvm
L'AOT sera effectué avec le backend LLVM au lieu du backend Mono lorsque possible. Cela sera plus lent à compiler mais entraînera très probablement une amélioration des performances.
llvmonly
L'AOT sera effectué exclusivement avec le backend LLVM et le backend Mono ne sera pas utilisé. Le seul résultat dans ce mode sera le fichier bitcode normalement spécifié avec l'option llvm-outfile. L'utilisation de llvmonly active automatiquement les options full et llvm. Cette fonctionnalité est expérimentale.
llvmopts=[options]
Utilisez cette option pour ajouter des indicateurs supplémentaires à l'ensemble d'indicateurs intégrés transmis à l'optimiseur LLVM. Lorsque vous invoquez la commande mono avec --aot=llvm, elle affiche la liste actuelle des indicateurs transmis à la commande opt. La liste des indicateurs possibles qui peuvent être transmis peut être obtenue en appelant le programme opt groupé qui accompagne Mono, et en l'appelant comme ceci : 
opt --help
llvmllc=[options]
Utilisez cette option pour ajouter des indicateurs supplémentaires à l'ensemble d'indicateurs intégrés transmis au compilateur statique LLVM (llc). La liste des indicateurs possibles qui peuvent être transmis peut être obtenue en appelant le programme llc groupé qui accompagne Mono, et en l'appelant comme ceci : 
llc --help
mcpu=[native o generic]
cpu=native permet au mode AOT d'utiliser toutes les instructions prises en charge par le CPU actuel, par exemple AVX2, SSE42, etc. La valeur par défaut est 'generic'. mattr=[cpu feature] permet au générateur de code AOT d'utiliser des fonctionnalités CPU spécifiées lorsque cela est possible, y compris `System.Runtime.Intrinsics.*'. Par exemple, `mattr=+avx2,mattr=-lzcnt' déverrouille sse1-4.2, avx1-2 et désactive lzcnt. C'est utile pour la compilation croisée ou lorsqu'il n'est pas possible d'utiliser `-mcpu=native' (qui active toutes les fonctionnalités CPU du CPU actuel). llvm-outfile=[filename] Donne le chemin du fichier temporaire de bitcode LLVM créé pendant l'AOT. dedup Chaque module AOT contient généralement le code des méthodes gonflées et des wrappers appelés par le code de ce module. En mode dedup, nous identifions et ignorons la compilation de toutes ces méthodes. Lors de l'utilisation de ce mode avec fullaot, dedup-include est requis, sinon ces méthodes resteront manquantes.
dedup-include=[filename]
En mode dedup-include, nous sommes dans l'étape de compilation où nous compilons les méthodes que nous avions précédemment ignorées. Toutes sont émises dans l'assembly passé comme cette option. Nous consolidons les nombreuses copies dupliquées de la même méthode en une seule.
info
Affiche l'architecture ciblée par l'AOT dans cette copie de Mono et quitte.
interp
Génère tous les wrappers requis, de sorte qu'il est possible d'exécuter --interpreter sans aucune génération de code à l'exécution. Cette option n'a de sens qu'avec mscorlib.dll. Les intégrateurs peuvent définir
depfile=[filename]
Produit un fichier de dépendance de style gcc -M. 
mono_jit_set_aot_mode (MONO_AOT_MODE_INTERP);
ld-flags
Indicateurs supplémentaires à passer à l'éditeur de liens C (si le mode AOT actuel nécessite son invocation).
llvm-path=<PREFIX>
Idem pour les outils llvm 'opt' et 'llc'.
msym-dir=<PATH>
Indique au compilateur AOT de générer des points de séquence hors ligne sous forme de fichiers .msym. Les fichiers .msym générés seront stockés dans un sous-dossier de <PATH> nommé d'après l'AOTID de compilation.
mtriple=<TRIPLE>
Utilise le triple de cible de style GNU <TRIPLE> pour déterminer certaines options de génération de code, c'est-à-dire --mtriple=armv7-linux-gnueabi générera du code ciblant ARMv7. Ceci n'est actuellement pris en charge que par le backend ARM. En mode LLVM, ce triple est transmis au compilateur LLVM llc.
nimt-trampolines=[number]
Lors de la compilation en mode full aot, les trampolines IMT doivent être précréées dans l'image AOT. Vous pouvez ajouter des trampolines de méthode supplémentaires avec cet argument. La valeur par défaut est 512.
ngsharedvt-trampolines=[number]
Lors de la compilation en mode full aot, les trampolines de partage générique de types valeur doivent être précréées dans l'image AOT. Vous pouvez ajouter des trampolines de méthode supplémentaires avec cet argument. La valeur par défaut est 512.
nodebug
Indique au compilateur AOT de ne pas générer d'informations de débogage.
no-direct-calls
Ceci empêche le compilateur AOT de générer des appels directs vers une méthode. Le compilateur AOT génère généralement des appels directs pour certaines méthodes qui ne nécessitent pas de passer par le PLT (par exemple, les méthodes dont on sait qu'elles ne nécessitent pas de crochet comme un constructeur statique) ou qui appellent des appels internes simples.
nrgctx-trampolines=[number]
Lors de la compilation en mode full aot, les trampolines de partage générique doivent être précréées dans l'image AOT. Vous pouvez ajouter des trampolines de méthode supplémentaires avec cet argument. La valeur par défaut est 4096.
nrgctx-fetch-trampolines=[number]
Lors de la compilation en mode full aot, les trampolines de récupération de partage générique doivent être précréées dans l'image AOT. Vous pouvez ajouter des trampolines de méthode supplémentaires avec cet argument. La valeur par défaut est 128.
ntrampolines=[number]
Lors de la compilation en mode full aot, les trampolines de méthode doivent être précréées dans l'image AOT. Vous pouvez ajouter des trampolines de méthode supplémentaires avec cet argument. La valeur par défaut est 4096.
outfile=[filename]
Indique au compilateur AOT de sauvegarder la sortie dans le fichier spécifié.
print-skipped-methods
Si le compilateur AOT ne peut pas compiler une méthode pour une raison quelconque, l'activation de cet indicateur affichera les méthodes ignorées sur la console.
profile=[file]
Spécifie un fichier à utiliser pour l'optimisation guidée par profil. Voir la sous-section Profileur AOT. Pour spécifier plusieurs fichiers, incluez l'option profile plusieurs fois.
profile-only
Compile AOT *uniquement* les méthodes décrites dans les fichiers spécifiés avec l'option profile. Voir la sous-section Profileur AOT.
readonly-value=namespace.typename.fieldname=type/value
Remplace la valeur d'un champ statique en lecture seule. Généralement, lors de la compilation JIT, le constructeur statique est exécuté de manière anticipée, de sorte que la valeur d'un champ statique en lecture seule est connue au moment de la compilation et que le compilateur peut effectuer un certain nombre d'optimisations basées sur celle-ci. En AOT, en revanche, le constructeur statique ne peut pas être exécuté, de sorte que cette option peut être utilisée pour définir la valeur d'un tel champ et activer le même ensemble d'optimisations. Type peut être l'un des i1, i2, i4 pour les entiers des tailles respectives (en octets). Notez que les nombres signés/non signés n'ont pas d'importance ici, seule la taille de stockage compte. Cette option peut être spécifiée plusieurs fois et n'empêche pas l'exécution du constructeur statique pour le type définissant le champ selon les règles habituelles à l'exécution (calculant donc potentiellement une valeur différente pour le champ).
save-temps,keep-temps
Indique au compilateur AOT de conserver les fichiers temporaires.
soft-debug
Ceci indique au compilateur de générer des vérifications de points de séquence qui permettent au débogueur logiciel de Mono de déboguer des applications même sur des systèmes où il n'est pas possible de définir des points d'arrêt ou d'exécuter pas à pas (certaines configurations matérielles comme les téléphones portables et les consoles de jeux vidéo).
static
Crée un fichier objet ELF (.o) ou un fichier .s qui peut être lié statiquement à un exécutable lors de l'intégration du runtime mono. Lorsque cette option est utilisée, le fichier objet doit être enregistré auprès du runtime intégré à l'aide de la fonction mono_aot_register_module qui prend comme argument le symbole global mono_aot_module_<ASSEMBLY NAME>_info du fichier objet : 
extern void *mono_aot_module_hello_info;
mono_aot_register_module (mono_aot_module_hello_info);
stats
Affiche diverses statistiques collectées pendant la compilation AOT.
temp-path=[path]
Spécifie explicitement le chemin pour stocker les fichiers temporaires créés pendant la compilation AOT.
threads=[number]
Il s'agit d'une option expérimentale pour que le compilateur AOT utilise plusieurs threads lors de la compilation des méthodes.
tool-prefix=<PREFIX>
Ajoute <PREFIX> au nom des outils exécutés par le compilateur AOT, c'est-à-dire 'as'/'ld'. Par exemple, --tool=prefix=arm-linux-gnueabi- fera exécuter au compilateur AOT
ld-name=NAME
L'un des outils utilisés pour les builds AOT est l'éditeur de liens. Son nom diffère selon les systèmes et il peut arriver que le nom par défaut supposé du binaire ne soit pas présent. Si la chaîne d'outils utilisée n'a pas d'éditeur de liens portant le nom par défaut (par exemple, Android NDK r22 n'a pas l'éditeur de liens par défaut 'ld' préfixé par 'tool-prefix' ci-dessus, mais a les éditeurs de liens préfixés 'ld.gold' et 'ld.bfd'), cette option peut être utilisée pour définir le nom du binaire de l'éditeur de liens. Il sera préfixé par 'tool-prefix' pour former le nom complet de l'exécutable de l'éditeur de liens.
verbose
Affiche des informations supplémentaires sur les échecs de chargement de type.
write-symbols,no-write-symbols
Indique au compilateur AOT d'émettre (ou de ne pas émettre) les informations de symboles de débogage.
no-opt
Indique au compilateur AOT de ne pas appeler opt lors de la compilation avec LLVM.

Pour plus d'informations sur l'AOT, voir : http://www.mono-project.com/docs/advanced/aot/

--aot-path=PATH
Liste des répertoires supplémentaires dans lesquels rechercher les images AOT.
--apply-bindings=FILE
Applique les liaisons d'assemblage du fichier de configuration spécifié lors de l'exécution du compilateur AOT. Ceci est utile lors de la compilation d'un assemblage auxiliaire référencé par un assemblage principal qui fournit un fichier de configuration. Par exemple, si app.exe utilise lib.dll, alors pour rendre les liaisons d'assemblage de app.exe.config disponibles lors de la compilation de lib.dll à l'avance, utilisez : 
mono --apply-bindings=app.exe.config --aot lib.dll
--assembly-loader=MODE
Si le mode est strict, Mono vérifiera que le jeton de clé publique, la culture et la version d'un assemblage candidat correspondent au nom fort demandé. Si le mode est legacy, tant que le nom correspond, le candidat sera autorisé. strict est le comportement cohérent avec le .NET Framework mais peut casser certaines applications existantes basées sur Mono. La valeur par défaut est legacy.
--attach=[options]
Actuellement, la seule option prise en charge par cet argument de ligne de commande est disable qui désactive la fonctionnalité d'attachement.
--config filename
Charge le fichier de configuration spécifié au lieu des fichiers par défaut. Les fichiers par défaut sont /etc/mono/config et ~/.mono/config ou le fichier spécifié dans la variable d'environnement MONO_CONFIG, s'il est défini. Voir la page de manuel mono-config(5) pour plus de détails sur le format de ce fichier.
--debugger-agent=[options]
Ceci demande au runtime Mono de démarrer un agent de débogage à l'intérieur du runtime Mono et de le connecter à une interface utilisateur client qui contrôlera le processus Mono. Cette option est généralement utilisée par les IDE, comme les IDE MonoDevelop ou Visual Studio.
La configuration est spécifiée à l'aide d'une ou plusieurs des options suivantes :
address=host:port
Utilisez cette option pour spécifier l'adresse IP sur laquelle votre client de débogage écoute.
loglevel=LEVEL
Spécifie le niveau de journalisation des diagnostics pour
logfile=filename
Utilisé pour spécifier le fichier où le journal sera stocké, il est par défaut sur la sortie standard.
server=[y/n]
Par défaut à non, avec l'option par défaut Mono se connectera activement à l'hôte/port configuré avec l'option address. Si vous le définissez sur 'y', il demande au runtime Mono de démarrer le débogage en mode serveur, où Mono attend activement que le frontend du débogueur se connecte au processus Mono. Mono affichera sur la sortie standard l'adresse IP et le port sur lesquels il écoute.
setpgid=[y/n]
S'il est défini sur oui, Mono appellera setpgid(0, 0) au démarrage, si cette fonction est disponible sur le système. Ceci est utile pour garantir que les signaux envoyés à un processus qui exécute le programme débogué ne soient pas propagés au programme débogué, par exemple lorsque Ctrl-C envoie SIGINT à l'outil sdb.
suspend=[y/n]
Par défaut à oui, avec l'option par défaut Mono suspendra la vm au démarrage jusqu'à ce qu'elle se connecte avec succès à un frontend de débogueur. Si vous le définissez sur 'n', en conjonction avec server=y, il demande au runtime Mono de s'exécuter normalement, tout en mettant en cache les métadonnées à envoyer au frontend du débogueur lors de la connexion..
transport=transport_name
Ceci est utilisé pour spécifier le transport que le débogueur utilisera pour communiquer. Il doit être spécifié et nécessite actuellement qu'il soit 'dt_socket'.
--desktop
Configure la machine virtuelle pour qu'elle soit mieux adaptée aux applications de bureau. Actuellement, cela configure le système GC pour éviter d'étendre le tas autant que possible, au détriment d'un ralentissement de la récupération de mémoire.
--full-aot
Ce drapeau demande au runtime Mono de ne générer aucun code au moment de l'exécution et de dépendre exclusivement du code généré précédemment à l'aide de mono --aot=full. Ceci est utile pour les plateformes qui n'autorisent pas la génération de code dynamique, ou si vous avez besoin d'exécuter des assemblages dont l'IL a été supprimée (par exemple en utilisant mono-cil-strip). Notez que cette fonctionnalité arrêtera l'exécution au moment de l'exécution si un chemin de code dans votre programme, ou les bibliothèques de classes de Mono, tente de générer du code dynamiquement. Vous devriez tester votre logiciel au préalable et vous assurer que vous n'utilisez aucune fonctionnalité dynamique.
--full-aot-interp
Identique à --full-aot avec repli vers l'interpréteur.
--gc=boehm, --gc=sgen
Sélectionne le moteur de Garbage Collector que Mono doit utiliser, Boehm ou SGen. Actuellement, cela garantit simplement que vous exécutez soit les commandes mono soit mono-sgen. Ce drapeau peut être défini dans la variable d'environnement MONO_ENV_OPTIONS pour forcer tous vos processus enfants à utiliser un type particulier de GC avec le runtime Mono.
--gc-debug=[options]
Équivalent en ligne de commande de la variable d'environnement MONO_GC_DEBUG.
--gc-params=[options]
Équivalent en ligne de commande de la variable d'environnement MONO_GC_PARAMS.
--arch=32, --arch=64
(Uniquement Mac OS X) : Sélectionne la "bitude" du binaire Mono utilisé, si disponible. Si le binaire utilisé est déjà pour la "bitude" sélectionnée, rien ne change. Sinon, l'exécution bascule vers un binaire avec le suffixe de "bitude" sélectionné installé côte à côte (par exemple, '/bin/mono --arch=64' basculera vers '/bin/mono64' si '/bin/mono' est une compilation 32 bits).
--help, -h
Affiche les instructions d'utilisation.
--interpreter
Le runtime Mono utilisera son interpréteur pour exécuter un assemblage donné. L'interpréteur est généralement plus lent que le JIT, mais il peut être utile sur les plateformes où la génération de code au moment de l'exécution n'est pas autorisée.
--hybrid-aot
Ce drapeau permet au runtime Mono d'exécuter des assemblages dont l'IL a été supprimée, par exemple à l'aide de mono-cil-strip. Pour que cela fonctionne, l'assemblage doit avoir été compilé en AOT avec --aot=hybrid.

Ce drapeau est similaire à --full-aot, mais il ne désactive pas le JIT. Cela signifie que vous pouvez utiliser des fonctionnalités dynamiques telles que System.Reflection.Emit.

--llvm
Si le runtime Mono a été compilé avec le support LLVM (non disponible dans toutes les configurations), Mono utilisera le moteur d'optimisation et de génération de code LLVM pour JIT ou AOT compiler. Pour plus d'informations, consultez : http://www.mono-project.com/docs/advanced/mono-llvm/
--ffast-math
Ce drapeau permet à Mono et LLVM d'appliquer des optimisations agressives en virgule flottante. Peut enfreindre la conformité IEEE754.
--nollvm
Lors de l'utilisation d'un Mono compilé avec le support LLVM, cela force Mono à revenir à son moteur JIT et à ne pas utiliser le backend LLVM.
--optimize=MODE, -O=MODE
MODE est une liste d'optimisations séparées par des virgules. Elles permettent également de désactiver des optimisations en préfixant le nom de l'optimisation par un signe moins. En général, Mono a été optimisé pour utiliser l'ensemble par défaut d'options, avant d'utiliser ces options pour un environnement de déploiement, vous pourriez vouloir mesurer les avantages de leur utilisation. Les options d'optimisation suivantes sont implémentées dans le moteur principal : 
             abcrem     Suppression des bornes de tableau
             all        Activer toutes les optimisations
             aot        Utilisation du code compilé Ahead Of Time
             branch     Optimisations de branchement
             cfold      Repliage de constantes
             cmov       Mouvements conditionnels [dépendance d'architecture]
             deadce     Élimination du code mort
             consprop   Propagation de constantes
             copyprop   Propagation de copie
             fcmov      Comparaisons FP rapides x86 [dépendance d'architecture]
             float32	Effectuer l'arithmétique flottante 32 bits en utilisant des opérations 32 bits
             gshared    Activer le partage de code générique.
             inline     Inlining d'appels de méthodes
             intrins    Implémentations de méthodes intrinsèques
             linears    Allocation globale de registres par analyse linéaire
             leaf       Optimisations des procédures feuilles
             loop       Optimisations liées aux boucles
             peephole   Passe post-optimisation "peephole"
             precomp    Précompiler toutes les méthodes avant d'exécuter Main
             sched      Ordonnancement des instructions
             shared     Émettre du code par domaine
             sse2       Instructions SSE2 sur x86 [dépendance d'architecture]
             tailc      Récursion terminale et appels terminaux
Par exemple, pour activer toutes les optimisations sauf l'élimination du code mort et l'inlining, vous pouvez utiliser : 
-O=all,-deadce,-inline
Les drapeaux marqués de [dépendance d'architecture] indiquent que l'option donnée, si utilisée en combinaison avec la compilation Ahead of Time (drapeau --aot), produirait un code précompilé qui dépendra du CPU actuel et pourrait ne pas être déplacé en toute sécurité vers un autre ordinateur.

Les optimisations suivantes sont prises en charge

float32
Demande au runtime d'effectuer des opérations flottantes 32 bits en utilisant uniquement 32 bits. Par défaut, le runtime Mono essaie d'utiliser la plus haute précision disponible pour les opérations flottantes, mais bien que cela puisse donner de meilleurs résultats, le code peut s'exécuter plus lentement. Cette option affecte également le code généré par le backend LLVM.
inline
Contrôle si le runtime doit attacher
vide pour transformer en ligne (par défaut), ou ne pas inclure les invocations de méthodes
--response=FICHIER Fournit un fichier de réponse, cela demande à la commande Mono de lire d'autres options de ligne de commande à partir du fichier spécifié, comme si les options avaient été spécifiées sur la ligne de commande. Utile lorsque vous avez des lignes de commande très longues.
--runtime=VERSION
Mono prend en charge différentes versions de runtime. La version utilisée dépend du programme qui est exécuté ou de son fichier de configuration (nommé programme.exe.config). Cette option peut être utilisée pour remplacer une telle autodétection, en forçant une version de runtime différente à être utilisée. Notez que cela ne devrait être utilisé que pour sélectionner une version de runtime compatible plus récente que celle pour laquelle le programme a été compilé. Un usage typique est de faire fonctionner un programme 1.1 sur une version 2.0 : 
         mono --runtime=v2.0.50727 programme.exe
--server
Configure la machine virtuelle pour qu'elle soit mieux adaptée aux opérations serveur (actuellement, permet une initialisation plus lourde du pool de threads).
--use-map-jit
Demande à Mono de générer du code en utilisant MAP_JIT sur MacOS. Nécessaire pour les applications regroupées.
--verify-all
Vérifie mscorlib et les assemblies dans le cache global des assemblies pour un IL valide, et tout le code utilisateur pour la vérifiabilité de l'IL.

Ceci est différent de `verifiable` ou `validil` de --security car ces options ne vérifient que le code utilisateur et ignorent mscorlib et les assemblies situés dans le cache global des assemblies.

-V, --version
Affiche les informations sur la version JIT (configuration système, numéro de version et noms de branches si disponibles).
--version=nombre
N'affiche que le numéro de version.

OPTIONS DE DÉVELOPPEMENT

Les options suivantes sont utilisées pour aider au développement d'une application JITée.

--debug, --debug=OPTIONS
Active le mode de débogage dans le runtime. Si un assembly a été compilé avec des informations de débogage, il produira des informations sur les numéros de ligne pour les traces de pile.

L'argument optionnel OPTIONS est une liste d'options de débogage séparées par des virgules. Ces options sont désactivées par défaut car elles génèrent un code plus volumineux et plus lent à l'exécution.

Les options suivantes sont prises en charge :
casts
Produit une erreur détaillée lors de la levée d'une InvalidCastException. Cette option doit être activée car elle génère un code plus verbeux à l'exécution.
mdb-optimizations
Désactive certaines optimisations JIT qui ne sont généralement désactivées que lors de l'exécution dans le débogueur. Cela peut être utile si vous souhaitez vous attacher au processus en cours d'exécution avec mdb.
gdb
Génère et enregistre des informations de débogage avec gdb. Ceci n'est pris en charge que sur certaines plateformes et uniquement lorsque gdb 7.0 ou une version ultérieure est utilisé.
--profile[=profiler[:profiler_args]]
Charge un module de profilage avec les arguments donnés. Pour plus d'informations, voir la section PROFILAGE. Cette option peut être utilisée plusieurs fois ; chaque fois chargera un module de profilage supplémentaire.
--trace[=expression]
Affiche les noms des méthodes au fur et à mesure de leur invocation. Par défaut, toutes les méthodes sont tracées. Le traçage peut être personnalisé pour inclure ou exclure des méthodes, des classes ou des assemblies. Une expression de traçage est une liste de cibles séparées par des virgules, chaque cible pouvant être précédée d'un signe moins pour désactiver une cible particulière. Les mots `program`, `all` et `disabled` ont une signification spéciale. `program` fait référence au programme principal exécuté, et `all` signifie tous les appels de méthode. L'option `disabled` est utilisée pour démarrer avec le traçage désactivé. Il peut être activé ultérieurement dans le programme en envoyant le signal SIGUSR2 au runtime. Les assemblies sont spécifiés par leur nom, par exemple, pour tracer tous les appels dans l'assembly System, utilisez : 
mono --trace=System app.exe
Les classes sont spécifiées avec le préfixe T:. Par exemple, pour tracer tous les appels à la classe System.String, utilisez : 
mono --trace=T:System.String app.exe
Et les méthodes individuelles sont référencées avec le préfixe M:, et la notation standard des méthodes : 
mono --trace=M:System.Console:WriteLine app.exe
Les exceptions peuvent également être tracées, cela provoquera l'impression d'une trace de pile chaque fois qu'une exception du type spécifié est levée. Le type d'exception peut être spécifié avec ou sans le namespace, et pour tracer toutes les exceptions, spécifiez 'all' comme nom de type. 
mono --trace=E:System.Exception app.exe
Comme mentionné précédemment, diverses règles peuvent être spécifiées en une seule fois : 
mono --trace=T:System.String,T:System.Random app.exe
Vous pouvez exclure des éléments, l'exemple suivant trace les appels à System.String à l'exception de la méthode System.String:Concat. 
mono --trace=T:System.String,-M:System.String:Concat
Vous pouvez tracer les transitions managées vers non-managées en utilisant le qualificateur wrapper : 
mono --trace=wrapper app.exe
Enfin, les namespaces peuvent être spécifiés en utilisant le préfixe N: : 
mono --trace=N:System.Xml
--no-x86-stack-align
Ne pas aligner les cadres de pile sur l'architecture x86. Par défaut, Mono aligne les cadres de pile sur 16 octets sur x86, de sorte que les variables flottantes et SIMD locales puissent être correctement alignées. Cette option désactive l'alignement, ce qui économise généralement une instruction par appel, mais peut entraîner des performances nettement inférieures en virgule flottante et SIMD.
--jitmap
Génère une carte de méthodes JIT dans un fichier /tmp/perf-PID.map. Ce fichier est ensuite utilisé, par exemple, par l'outil perf inclus dans les noyaux Linux récents. Chaque ligne du fichier contient : 
ADRESSEHEX TAILLEHEX nomdeméthode
Actuellement, cette option n'est prise en charge que sous Linux.

OPTIONS MAITENEUR JIT

Les options de maintenance ne sont utilisées que par ceux qui développent le runtime lui-même, et ne sont généralement pas d'intérêt pour les utilisateurs ou les développeurs du runtime.

--bisect=optimisation:nom_de_fichier
Ce drapeau est utilisé par le bissecteur automatique de bugs d'optimisation. Il prend une optimisation et un nom de fichier contenant une liste de noms de méthodes complets, un par ligne. Lorsqu'il compile l'une des méthodes du fichier, il utilisera l'optimisation donnée, en plus des optimisations qui sont autrement activées. Notez que si l'optimisation est activée par défaut, vous devriez la désactiver avec `-O`, sinon elle ne s'appliquera qu'à chaque méthode, qu'elle soit dans le fichier ou non.
--break méthode
Insère un point d'arrêt avant la méthode dont le nom est `méthode' (namespace.classe:nom_methode). Utilisez `Main' comme nom de méthode pour insérer un point d'arrêt sur la méthode principale de l'application. Vous pouvez également l'utiliser avec des génériques, par exemple "System.Collections.Generic.Queue`1:Peek"
--breakonex
Insère un point d'arrêt sur les exceptions. Cela vous permet de déboguer votre application avec un débogueur natif lorsqu'une exception est levée.
--compile nom
Compile une méthode (namespace.nom:nom_methode), cela est utilisé pour tester les performances du compilateur ou pour examiner la sortie du générateur de code.
--compile-all
Compile toutes les méthodes d'un assembly. Ceci est utilisé pour tester les performances du compilateur ou pour examiner la sortie du générateur de code
--graph=TYPE METHODE
Génère un fichier postscript avec un graphique détaillé sur la méthode spécifiée (namespace.nom:nom_methode). Cela nécessite que `dot` et ghostview soient installés (il s'attend à ce que Ghostview soit appelé "gv"). Les graphiques suivants sont disponibles : 
          cfg        Graphe de flux de contrôle (CFG)
          dtree      Arbre de dominance
          code       CFG montrant le code
          ssa        CFG montrant le code après traduction SSA
          optcode    CFG montrant le code après optimisations IR
Certains graphiques ne seront disponibles que si certaines optimisations sont activées.
--ncompile
Demande au runtime le nombre de fois où la méthode spécifiée par --compile (ou toutes les méthodes si --compile-all est utilisé) doit être compilée. Ceci est utilisé pour tester les performances du générateur de code.
--stats=[méthode]
Affiche des informations sur le travail effectué par le runtime pendant l'exécution d'une application. Si une méthode (namespace.nom:nom_methode) est spécifiée, elle affichera ces informations lorsque la méthode sera exécutée pour la première fois, en plus de la fin de l'exécution du programme.
--wapi=hps|semdel
Effectue la maintenance des données partagées du processus. semdel supprimera le semaphore global. hps listera les handles actuellement utilisés.
-v, --verbose
Augmente le niveau de verbosité, chaque fois qu'il est listé, augmente le niveau de verbosité pour inclure plus d'informations (y compris, par exemple, un désassemblage du code natif produit, des informations sur le sélecteur de code, etc.).

SUPPORT D'ATTACHEMENT

Le runtime Mono permet à des processus externes de s'attacher à un processus en cours d'exécution et de charger des assemblies dans le programme en cours d'exécution. Pour s'attacher au processus, un protocole spécial est implémenté dans l'assembly Mono.Management assembly.

Avec ce support, il est possible de charger des assemblies qui ont un point d'entrée (ils sont créés avec -target:exe ou -target:winexe) pour être chargés et exécutés.

d dans le processus Mono.

Le code est chargé dans le domaine racine et commence son exécution sur le thread d'attachement spécial du runtime. Le programme attaché doit créer ses propres threads et retourner après invocation.

Ce support permet, par exemple, de déboguer des applications en faisant s'attacher le shell csharp à des processus en cours d'exécution.

PROFILAGE

Le runtime Mono inclut une API de profileur que les modules de profileur chargés dynamiquement et les intégrateurs peuvent utiliser pour collecter des données relatives aux performances d'une application. Les modules de profileur sont chargés en passant l'argument de ligne de commande --profile au runtime Mono.

Mono est livré avec quelques modules de profileur, dont le profileur log est le plus riche en fonctionnalités. C'est également le profileur par défaut si l'argument profiler n'est pas donné, ou si default est donné. Il est possible d'écrire vos propres modules de profileur ; voir la sous-section Profileurs personnalisés.

Profileur log

Le profileur log peut être utilisé pour collecter de nombreuses informations sur un programme s'exécutant dans le runtime Mono. Ces données peuvent être utilisées (à la fois pendant que le processus s'exécute et plus tard) pour analyser le comportement du programme, déterminer l'utilisation des ressources, identifier les problèmes de performance, voire rechercher des modèles d'exécution particuliers.

Ceci est accompli en enregistrant les événements fournis par le runtime Mono via l'API de profileur et en les écrivant périodiquement dans un fichier qui peut ensuite être inspecté avec l'outil mprof-report(1).

Plus d'informations sur l'utilisation du profileur log sont disponibles sur la page mono-profilers(1), sous la section PROFILEUR LOG, ainsi que sur la page mprof-report(1).

Profileur couverture

Le profileur de couverture de code peut instrumenter un programme pour aider à déterminer quelles classes, méthodes, chemins de code, etc. sont effectivement exécutés. Ceci est particulièrement utile lors de l'exécution d'une suite de tests pour déterminer si les tests couvrent réellement le code prévu.

Plus d'informations sur l'utilisation du profileur de couverture sont disponibles sur la page mono-profilers(1), sous la section PROFILEUR DE COUVERTURE.

Profileur AOT

Le profileur AOT peut aider à améliorer les performances de démarrage en enregistrant les instanciations génériques utilisées par un programme, ce qui permet au compilateur AOT de compiler ces instanciations à l'avance afin qu'elles n'aient pas à être compilées JIT au démarrage.

Plus d'informations sur l'utilisation du profileur AOT sont disponibles sur la page mono-profilers(1), sous la section PROFILEUR AOT.

Profileurs personnalisés

Les modules de profileur personnalisés peuvent être chargés exactement de la même manière que les modules standard fournis avec Mono. Ils peuvent également accéder à la même API de profileur pour collecter toutes sortes d'informations sur le code exécuté.

Par exemple, pour utiliser un profileur tiers appelé custom, vous le chargeriez comme suit :

mono --profile=custom programme.exe

Vous pourriez également lui passer des arguments :

mono --profile=custom:arg1,arg2=arg3 programme.exe

Dans l'exemple ci-dessus, Mono chargera le profileur à partir de la bibliothèque partagée nommée libmono-profiler-custom.so (le nom varie selon la plateforme, par exemple libmono-profiler-custom.dylib sur OS X). Ce module de profileur doit se trouver dans votre chemin de bibliothèques du linker dynamique (LD_LIBRARY_PATH sur la plupart des systèmes, DYLD_LIBRARY_PATH sur OS X).

Pour un exemple de la façon d'écrire votre propre profileur personnalisé, regardez le fichier samples/profiler/sample.c dans l'arborescence des sources de Mono.

AIDES AU DÉBOGAGE

Pour déboguer des applications managées, vous pouvez utiliser la commande mdb, un débogueur en ligne de commande.

Il est possible d'obtenir une trace de la pile de tous les threads actifs dans Mono en envoyant le signal QUIT à Mono, vous pouvez le faire depuis la ligne de commande, comme ceci :

kill -QUIT pid
Où pid est l'ID de processus du processus Mono que vous souhaitez examiner. Le processus continuera de s'exécuter ensuite, mais son état n'est pas garanti.

Important : il s'agit d'un mécanisme de dernier recours pour le débogage d'applications et ne doit pas être utilisé pour surveiller ou sonder une application de production. L'intégrité du runtime après l'envoi de ce signal n'est pas garantie et l'application pourrait planter ou se terminer à tout moment par la suite.

L'option --debug=casts peut être utilisée pour obtenir des informations plus détaillées pour les opérations de transtypage invalides, elle fournira des informations sur les types impliqués.

Vous pouvez utiliser les variables d'environnement MONO_LOG_LEVEL et MONO_LOG_MASK pour obtenir une sortie de débogage détaillée sur l'exécution de votre application dans Mono.

La variable d'environnement MONO_LOG_LEVEL, si elle est définie, modifie le niveau de journalisation à la valeur définie. Les valeurs possibles sont "error", "critical", "warning", "message", "info", "debug". La valeur par défaut est "error". Les messages dont le niveau de journalisation est supérieur ou égal au niveau de journalisation seront imprimés sur stdout/stderr.

Utilisez "info" pour suivre le chargement dynamique des assemblages.

Utilisez la variable d'environnement MONO_LOG_MASK pour limiter l'étendue des messages que vous recevez : Si elle est définie, le masque de journalisation est modifié à la valeur définie. Les valeurs possibles sont "asm" (chargeur d'assemblages), "type", "dll" (chargeur de bibliothèques natives), "gc" (ramasse-miettes), "cfg" (chargeur de fichiers de configuration), "aot" (précompilateur), "security" (par exemple, support CoreCLR de Moonlight), "threadpool" (pool de threads générique), "io-selector" (opérations de sockets asynchrones), "io-layer" (couche d'E/S - processus, fichiers, sockets, événements, sémaphores, mutex et descripteurs), "io-layer-process", "io-layer-file", "io-layer-socket", "io-layer-event", "io-layer-semaphore", "io-layer-mutex", "io-layer-handle" et "all". La valeur par défaut est "all". Changer la valeur du masque vous permet d'afficher uniquement les messages pour un composant spécifique. Vous pouvez utiliser plusieurs masques en les séparant par des virgules. Par exemple, pour voir les messages du fichier de configuration et les messages du chargeur d'assemblages, définissez votre masque à "asm,cfg".

Voici une utilisation courante pour résoudre les problèmes avec P/Invoke :

$ MONO_LOG_LEVEL="debug" MONO_LOG_MASK="dll" mono glue.exe

DÉBOGAGE AVEC LLDB

Si vous utilisez LLDB, vous pouvez utiliser le script mono.py pour imprimer certaines structures de données internes avec lui. Pour l'utiliser, ajoutez ceci à votre fichier $HOME/.lldbinit :

command script import $PREFIX/lib/mono/lldb/mono.py

Où $PREFIX est la valeur du préfixe que vous avez utilisée lors de la configuration de Mono (typiquement /usr).

Une fois cela fait, vous pouvez inspecter certaines structures de données du Runtime Mono, par exemple :

(lldb) p method
(MonoMethod *) $0 = 0x05026ac0 [mscorlib]System.OutOfMemoryException:.ctor()

SERIALISATION

Le moteur de sérialisation XML de Mono utilise par défaut une approche basée sur la réflexion qui peut être lente pour un traitement continu (applications de services web). Le moteur de sérialisation déterminera quand une classe doit utiliser un sérialiseur ajusté à la main en fonction de quelques paramètres et, si nécessaire, il produira un sérialiseur C# personnalisé pour vos types au moment de l'exécution. Ce sérialiseur personnalisé est ensuite chargé dynamiquement dans votre application.

Vous pouvez contrôler cela avec la variable d'environnement MONO_XMLSERIALIZER_THS.

Les valeurs possibles sont `no' pour désactiver l'utilisation d'un sérialiseur personnalisé C#, ou un entier qui est le nombre minimum d'utilisations avant que le runtime ne produise un sérialiseur personnalisé (0 produira un sérialiseur personnalisé dès le premier accès, 50 produira un sérialiseur lors de la 50ème utilisation). Mono se rabattra sur un sérialiseur interprété si la génération du sérialiseur échoue d'une manière ou d'une autre. Ce comportement peut être désactivé en définissant l'option `nofallback' (par exemple : MONO_XMLSERIALIZER_THS=0,nofallback).

VARIABLES D'ENVIRONNEMENT

GC_DONT_GC
Désactive le ramasse-miettes dans Mono. Ceci ne devrait être utilisé qu'à des fins de débogage
HTTP_PROXY
(Aussi http_proxy) Si définie, les requêtes web utilisant la Bibliothèque de Classes Mono seront automatiquement redirigées via l'URL donnée. Non pris en charge sous Windows, Mac OS, iOS ou Android. Voir aussi NO_PROXY.
LLVM_COUNT
Lorsque Mono est compilé avec le support LLVM, ceci demande au runtime de cesser d'utiliser LLVM après que le nombre spécifié de méthodes ont été compilées JIT. C'est un outil utilisé en diagnostic pour aider à isoler les problèmes dans le backend de génération de code. Par exemple, LLVM_COUNT=10 ne compilera que 10 méthodes avec LLVM puis passera au moteur JIT de Mono. LLVM_COUNT=0 désactivera complètement le moteur LLVM.
MONO_ASPNET_INHIBIT_SETTINGSMAP
Mono contient une fonctionnalité qui permet de modifier les paramètres des fichiers .config fournis avec Mono en utilisant des mappeurs de section de configuration. Les mappeurs et les règles de mappage sont définis dans le fichier $prefix/etc/mono/2.0/settings.map et, éventuellement, dans le fichier settings.map trouvé dans le répertoire de niveau supérieur de votre application ASP.NET. Les deux fichiers sont lus par System.Web au démarrage de l'application, s'ils sont trouvés aux emplacements ci-dessus. Si vous ne souhaitez pas que le mappage soit effectué, vous pouvez définir cette variable dans votre environnement avant de démarrer l'application et aucune action ne sera entreprise.
MONO_ASPNET_WEBCONFIG_CACHESIZE
Mono dispose d'un cache d'objets ConfigSection pour accélérer WebConfigurationManager
queries. Sa taille par défaut est de 100 éléments, et lorsque plus d'éléments sont nécessaires, les évictions du cache commencent à se produire. Si les évictions sont trop fréquentes, cela peut entraîner une surcharge inutile, qui pourrait être évitée en utilisant cette variable d'environnement pour configurer une taille de cache plus grande (ou pour réduire les besoins en mémoire en la diminuant).
MONO_CAIRO_DEBUG_DISPOSE
Si défini, provoque la collecte des traces de pile par Mono.Cairo lors de l'allocation d'objets, de sorte que les avertissements de finalisation/Dispose incluent des informations sur l'origine de l'instance.
MONO_CFG_DIR
Si défini, cette variable remplace le répertoire de configuration système par défaut ($PREFIX/etc). Elle est utilisée pour localiser le fichier machine.config.
MONO_COM
Définit le style de l'interopérabilité COM. Si la valeur de cette variable est "MS", Mono utilisera les routines de marshaling de chaînes de la librairie de types liboleaut32 pour le type BSTR, toute autre valeur utilisera le marshaling de chaînes BSTR intégré à Mono.
MONO_CONFIG
Si défini, cette variable remplace le fichier de configuration du runtime par défaut ($PREFIX/etc/mono/config). L'option de ligne de commande --config remplace la variable d'environnement.
MONO_CPU_ARCH
Remplace le mécanisme de détection automatique du processeur. Actuellement utilisé uniquement sur ARM. Le format de la valeur est le suivant : 
"armvV [thumb[2]]"
où V est le numéro d'architecture 4, 5, 6, 7 et les options peuvent être actuellement "thumb" ou "thumb2". Exemple : 
MONO_CPU_ARCH="armv4 thumb" mono ...
MONO_ARM_FORCE_SOFT_FLOAT
Lorsque Mono est compilé avec un recours au flottant logiciel sur ARM et que cette variable est définie sur "1", Mono émettra toujours du code flottant logiciel, même si une unité VFP est détectée.
MONO_DARWIN_USE_KQUEUE_FSW
Utilise l'implémentation kqueue de FileSystemWatcher sous Darwin. L'implémentation par défaut est l'implémentation FSEvent.
MONO_DARWIN_WATCHER_MAXFDS
Ceci est une aide au débogage utilisée pour forcer des limites sur l'implémentation kqueue de FileSystemWatcher sous Darwin. Il n'y a pas de limite par défaut.
MONO_DISABLE_MANAGED_COLLATION
Si cette variable d'environnement est "yes", le runtime utilise la collation non gérée (ce qui signifie en fait aucune collation sensible à la culture). Elle désactive en interne les fonctionnalités de collation gérée invoquées via les membres de la classe System.Globalization.CompareInfo. La collation est activée par défaut.
MONO_DISABLE_SHARED_AREA
Unix uniquement : Si défini, désactive l'utilisation de la mémoire partagée pour exposer les compteurs de performance. Cela signifie qu'il ne sera pas possible de lire les compteurs de performance de ce processus depuis l'extérieur, ni de lire ceux des processus externes.
MONO_DNS
Lorsqu'il est défini, active l'utilisation d'un résolveur DNS entièrement géré au lieu des fonctions libc habituelles. Ce résolveur offre de meilleures performances lorsque plusieurs requêtes sont exécutées en parallèle.

Notez que /etc/nsswitch.conf sera ignoré.

MONO_EGD_SOCKET
Pour les plateformes qui n'ont pas d'autre moyen d'obtenir des octets aléatoires, cette variable peut être définie sur le nom d'un socket de système de fichiers sur lequel un démon egd ou prngd écoute.
MONO_ENABLE_AIO
Si défini, indique à Mono de tenter d'utiliser les services d'E/S asynchrones natifs. Si non défini, une implémentation par défaut basée sur select/poll est utilisée. Actuellement, epoll et kqueue sont pris en charge.
MONO_THREADS_SUSPEND Sélectionne un mécanisme que Mono utilisera pour suspendre
les threads. Peut être défini sur "preemptive", "coop", ou "hybrid". Les threads peuvent avoir besoin d'être suspendus par le débogueur, ou en utilisant certaines API de threading .NET, et le plus souvent lorsque le garbage collector SGen doit arrêter tous les threads pendant une phase critique de la collecte des déchets. Le mode préemptif est le mode que Mono a utilisé historiquement, remontant à l'époque de Boehm, où le garbage collector pouvait s'exécuter à tout moment et suspendre l'exécution de tous les threads si nécessaire pour effectuer une collecte des déchets. Le mode coopératif, en revanche, nécessite la coopération de tous les threads pour s'arrêter à un point sûr. Cela rend le garbage collector plus facile à déboguer et améliore la stabilité du runtime car les threads ne sont pas suspendus lors de l'accès à des ressources critiques. Dans les scénarios où Mono est intégré dans une autre application, la suspension coopérative nécessite que le code intégrateur suive des directives de codage pour coopérer avec le garbage collector. La suspension coopérative dans Mono embarqué est actuellement expérimentale. Le mode hybride est une combinaison des deux qui conserve une meilleure compatibilité avec les scénarios où Mono est intégré dans une autre application : les threads qui exécutent du code géré ou du code qui compose le runtime Mono seront suspendus de manière coopérative, tandis que les threads exécutant du code intégrateur seront suspendus de manière préemptive. La suspension hybride est la valeur par défaut sur certaines plateformes de bureau.

Alternativement, les modes coopératif et hybride peuvent être activés au moment de la compilation en utilisant les options --enable-cooperative-suspend ou --enable-hybrid-suspend, respectivement, lors de l'appel à configure. La variable d'environnement MONO_THREADS_SUSPEND a la priorité sur la valeur par défaut compilée.

Notez que si des options de configuration ont été fournies pour activer la suspension coopérative ou hybride, cette variable est ignorée.

En général, si vous rencontrez des problèmes avec les encodages dans vos noms de fichiers, vous devriez utiliser le programme "convmv".
MONO_GC_PARAMS
Lors de l'utilisation de Mono avec le garbage collector SGen, cette variable contrôle plusieurs paramètres du collecteur. La valeur de la variable est une liste de mots séparés par des virgules.
max-heap-size=taille
Définit la taille maximale du tas. La taille est spécifiée en octets et doit être une puissance de deux. Les suffixes 'k', 'm' et 'g' peuvent être utilisés pour spécifier des kilo-, méga- et gigaoctets, respectivement. La limite est la somme de la pépinière, du tas majeur et du tas d'objets volumineux. Une fois la limite atteinte, l'application recevra des exceptions OutOfMemory lors de la tentative d'allocation. Toute la mémoire définie dans max-heap-size pourrait ne pas être disponible pour satisfaire une seule allocation en raison de la fragmentation interne. Par défaut, les limites du tas sont désactivées et le GC tentera d'utiliser toute la mémoire disponible.
nursery-size=taille
Définit la taille de la pépinière. La taille est spécifiée en octets et doit être une puissance de deux. Les suffixes 'k', 'm' et 'g' peuvent être utilisés pour spécifier des kilo-, méga- et gigaoctets, respectivement. La pépinière est la première génération (sur deux). Une pépinière plus grande accélérera généralement le programme mais utilisera évidemment plus de mémoire. T
nursery-size=size
The default nursery size is 4 MB.
major=collector
Spécifie quel collecteur principal utiliser. Les options sont `marksweep` pour le collecteur Mark&Sweep, `marksweep-conc` pour Mark&Sweep concurrent et `marksweep-conc-par` pour Mark&Sweep parallèle et concurrent. Le collecteur Mark&Sweep concurrent est le collecteur par défaut.
mode=balanced|throughput|pause[:max-pause]
Spécifie quel doit être l'objectif du garbage collector. Le mode `throughput` vise à réduire le temps passé dans le garbage collector et à améliorer la vitesse de l'application, le mode `pause` vise à minimiser les temps de pause et reçoit l'argument max-pause qui spécifie le temps de pause maximum en millisecondes acceptable, et le mode `balanced` qui est un mode optimal polyvalent.
soft-heap-limit=size
Une fois que la taille du tas dépasse cette taille, ignorez ce que la métrique de déclenchement de la collecte principale par défaut dit et n'autorisez qu'une croissance de quatre tailles de pépinière du tas principal entre les collectes principales.
evacuation-threshold=threshold
Définit le seuil d'évacuation en pourcentage. Cette option n'est disponible que sur les collecteurs principaux Mark&Sweep. La valeur doit être un entier compris entre 0 et 100. La valeur par défaut est 66. Si la phase de balayage de la collecte constate que l'occupation d'un type de bloc de tas spécifique est inférieure à ce pourcentage, elle effectuera une collecte par copie pour ce type de bloc lors de la prochaine collecte principale, restaurant ainsi l'occupation à près de 100 pour cent. Une valeur de 0 désactive l'évacuation.
(no-)lazy-sweep
Active ou désactive le balayage paresseux pour le collecteur Mark&Sweep. Si activé, le balayage des blocs de tas principaux individuels est effectué petit à petit chaque fois que le besoin s'en fait sentir, généralement lors des collectes de pépinière. Le balayage paresseux est activé par défaut.
(no-)concurrent-sweep
Active ou désactive le balayage concurrent pour le collecteur Mark&Sweep. Si activé, l'itération de tous les blocs principaux pour déterminer lesquels peuvent être libérés et lesquels doivent être conservés et balayés, est effectuée simultanément avec le programme en cours d'exécution. Le balayage concurrent est activé par défaut.
stack-mark=mark-mode
Spécifie comment les threads d'application doivent être analysés. Les options sont `precise` et `conservative`. Le marquage précis permet au collecteur de savoir quelles valeurs sur la pile sont des références et lesquelles ne le sont pas. Le marquage conservateur traite toutes les valeurs comme des références potentielles et les laisse inchangées. Le marquage précis réduit le garbage flottant et peut accélérer le taux de collecte de pépinière et d'allocation, il a pour inconvénient de nécessiter une quantité de mémoire supplémentaire importante par méthode compilée. Le choix de l'option appropriée, malheureusement, nécessite des expérimentations.
save-target-ratio=ratio
Spécifie le ratio de sauvegarde cible pour le collecteur principal. Le collecteur laisse une certaine quantité de mémoire être promue de la pépinière en raison des collectes mineures avant de déclencher une collecte principale. Cette quantité est basée sur la quantité de mémoire qu'il s'attend à libérer. Elle est représentée par un ratio de la taille du tas après une collecte principale. Les valeurs valides sont comprises entre 0.1 et 2.0. La valeur par défaut est 0.5. Des valeurs plus petites maintiendront la taille du tas principal plus petite mais déclencheront plus de collectes principales. De même, des valeurs plus grandes utiliseront plus de mémoire et entraîneront moins de collectes principales fréquentes. Cette option est EXPÉRIMENTALE, elle pourrait donc disparaître dans les futures versions de mono.
default-allowance-ratio=ratio
Spécifie l'allocation autorisée par défaut lorsque la taille calculée est trop petite. L'allocation autorisée est la quantité de mémoire que le collecteur laisse être promue avant de déclencher une collecte principale. C'est un ratio de la taille de la pépinière. Les valeurs valides sont comprises entre 1.0 et 10.0. La valeur par défaut est 4.0. Des valeurs plus petites conduisent à des tas plus petits et à des collectes principales plus fréquentes. De même, des valeurs plus grandes permettront au tas de croître plus rapidement mais utiliseront plus de mémoire lorsqu'il atteindra une taille stable. Cette option est EXPÉRIMENTALE, elle pourrait donc disparaître dans les futures versions de mono.
minor=minor-collector
Spécifie quel collecteur mineur utiliser. Les options sont `simple` qui promu tout les objets de la pépinière directement vers la vieille génération, `simple-par` qui a le même comportement de promotion que `simple` mais en utilisant plusieurs threads, et `split` qui laisse les objets rester plus longtemps dans la pépinière avant de les promouvoir.
alloc-ratio=ratio
Spécifie le ratio de mémoire de la pépinière à utiliser par l'espace d'allocation. Cela ne peut être utilisé qu'avec le collecteur mineur `split`. Les valeurs valides sont des entiers compris entre 1 et 100. La valeur par défaut est 60.
promotion-age=age
Spécifie l'âge requis d'un objet dans la pépinière avant d'être promu vers la vieille génération. Cela ne peut être utilisé qu'avec le collecteur mineur `split`. Les valeurs valides sont des entiers compris entre 1 et 14. La valeur par défaut est 2.
(no-)cementing
Active ou désactive le cimentage. Cela peut considérablement raccourcir les temps de collecte de pépinière sur certains benchmarks où des objets épinglés sont référencés depuis le tas principal.
allow-synchronous-major
Cela interdit au collecteur principal d'effectuer des collectes principales synchrones. Le collecteur principal pourrait vouloir effectuer une collecte synchrone en raison d'une fragmentation excessive. Désactiver cela pourrait déclencher une erreur OutOfMemory dans des situations qui ne se produiraient pas autrement.
MONO_GC_DEBUG
Lors de l'utilisation de Mono avec le garbage collector SGen, cette variable d'environnement peut être utilisée pour activer diverses fonctionnalités de débogage du collecteur. La valeur de cette variable est une liste de mots séparés par des virgules. N'utilisez pas ces options en production.
number
Définit le niveau de débogage sur le nombre spécifié.
print-allowance
Après chaque collecte principale, affiche la consommation de mémoire avant et après la collecte, ainsi que l'allocation autorisée pour le collecteur mineur, c'est-à-dire combien le tas est autorisé à croître à partir des collectes mineures avant que la prochaine collecte principale ne soit déclenchée.
print-pinning

collect-before-allocs

Effectue une vérification de cohérence du remset à diverses occasions, et également efface la pépinière au moment de la collecte, au lieu de la valeur par défaut, lorsque les tampons sont alloués (clear-at-gc). La vérification de cohérence garantit qu'il n'y a pas de références du tas principal vers la pépinière qui ne sont pas sur les ensembles mémorisés.
mod-union-consistency-check
Vérifie que la table de cartes mod-union est cohérente avant chaque pause de fin de collecte principale. Cette vérification n'est applicable qu'aux collecteurs principaux concurrents.
check-mark-bits
Vérifie que les bits de marquage dans le tas principal sont cohérents à la fin de chaque collecte principale. Des bits de marquage cohérents signifient que si un objet est marqué, tous les objets auxquels il faisait référence doivent également être marqués.
check-nursery-untag
Après les garbage collections, vérifie si tous les pointeurs vtable ne sont plus tagués.
xdomain-checks
Effectue une vérification pour s'assurer qu'aucune référence n'est laissée à un AppDomain non chargé.
clear-at-tlab-creation
Efface la pépinière de manière incrémentielle lorsque les tampons d'allocation locaux au thread (TLAB) sont créés. Le réglage par défaut efface toute la pépinière au moment du GC.

Cela efface la pépinière au moment du GC au lieu de le faire lors de la création du tampon d'allocation local au thread (TLAB). La valeur par défaut est d'effacer la pépinière au moment de la création du TLAB.

Ne pas effectuer de collectes mineures. Si la pépinière est pleine, une collecte principale est déclenchée à la place, sauf si elle est également désactivée.

Ne pas effectuer de collectes principales.
conservative-stack-mark
Force le GC à analyser la pile de manière conservatrice, même si une analyse précise est disponible.

Désactive l'allocateur géré.
managed-allocator
Active l'allocateur géré.
check-scan-starts
Si défini, effectue une vérification de plausibilité des scan_starts avant et après chaque collecte.
verify-nursery-at-minor-gc

keep-delegates
Cette option permettra de conserver en mémoire les trampolines de délégués qui ne sont plus référencés afin de présenter à l'utilisateur plus d'informations sur une mauvaise utilisation des délégués. Essentiellement, une instance de délégué peut être créée, passée à du code non managé, et aucune référence n'est conservée en code managé, ce qui entraînera le garbage collection du code. Avec cette option, il est possible de retracer la source des problèmes.
no-gdb-backtrace
Cette option désactivera la trace GDB émise par le runtime après un SIGSEGV ou un SIGABRT dans du code non managé.
partial-sharing
Lorsque cette option est activée, le runtime peut partager le code généré entre les types génériques, réduisant ainsi efficacement la quantité de code généré.
reverse-pinvoke-exceptions
Cette option provoquera l'arrêt de mono avec un message descriptif lorsque, lors du déchargement de la pile après une exception, il atteint une frame de pile native. Cela se produit lorsqu'un délégué managé est passé à du code natif et que le délégué managé lève une exception. Mono essaiera normalement de décharger la pile jusqu'au premier gestionnaire d'exception (managé), en ignorant toutes les frames de pile natives. Cela conduit à un comportement indéfini (car mono ne sait pas comment traiter les frames natives), des fuites et potentiellement des plantages.
single-imm-size
Cela garantit que chaque fois que du code managé est compilé, les mêmes instructions et registres sont utilisés, quelle que soit la taille des valeurs utilisées.
soft-breakpoints
Cette option permet d'utiliser des pas à pas uniques et des points d'arrêt sur le matériel où nous ne pouvons pas le faire avec des signaux.
suspend-on-native-crash
Cette option suspendra le programme lors d'un crash natif (SIGSEGV, SIGILL, ...). Ceci est utile pour déboguer des plantages qui ne se produisent pas sous gdb, car un processus vivant contient plus d'informations qu'un fichier core.
suspend-on-sigsegv
Identique à suspend-on-native-crash.
suspend-on-exception
Cette option suspendra le programme lorsqu'une exception se produit.
suspend-on-unhandled
Cette option suspendra le programme lorsqu'une exception non gérée se produit.
thread-dump-dir=DIR
Utilise DIR pour le stockage des vidages de threads créés par SIGQUIT.
weak-memory-model
N'applique pas le modèle mémoire CLR sur les plateformes avec des modèles mémoire faibles. Cela peut entraîner des plantages aléatoires dans certains cas rares, pour les environnements multithread. Ceci peut être utilisé pour un gain de performance sur les applications mono-thread.
verbose-gdb
Rend la sortie GDB sur les plantages natifs plus verbeuse.
MONO_LOG_LEVEL
Le niveau de journalisation, les valeurs possibles sont `error', `critical', `warning', `message', `info' et `debug'. Voir la section DEBUGGING pour plus de détails.
MONO_LOG_MASK
Contrôle le domaine du runtime Mono auquel la journalisation s'appliquera. Si défini, le masque de journalisation est modifié pour la valeur définie. Les valeurs possibles sont "asm" (chargeur d'assemblage), "type", "dll" (chargeur de bibliothèque native), "gc" (collecteur de garbage), "cfg" (chargeur de fichier de configuration), "aot" (précompilateur), "security" (par exemple, support CoreCLR de Moonlight) et "all". La valeur par défaut est "all". Modifier la valeur du masque vous permet d'afficher uniquement les messages pour un composant donné. Vous pouvez utiliser plusieurs masques en les séparant par des virgules. Par exemple, pour voir les messages du fichier de configuration et les messages du chargeur d'assemblage, définissez votre masque sur "asm,cfg".
MONO_LOG_DEST
Contrôle où les messages de trace de journal sont écrits. S'il n'est pas défini, les messages vont vers stdout. S'il est défini, la chaîne spécifie soit un chemin vers un fichier auquel les messages seront ajoutés, soit la chaîne "syslog", auquel cas les messages seront écrits dans le journal système. Sous Windows, ceci est simulé en écrivant dans un fichier appelé "mono.log". MONO_LOG_HEADER Contrôle si les messages de trace de journal qui ne sont pas dirigés vers syslog ont l'ID, l'horodatage et le PID comme préfixe du message de journal. Pour activer un en-tête, cette variable d'environnement doit simplement ne pas être nulle.
MONO_TRACE
Utilisé pour le traçage du runtime des appels de méthodes. Le format des options de traçage séparées par des virgules est : 
[-]M:nom de méthode
[-]N:espace de noms
[-]T:nom de classe
[-]all
[-]program
disabled		Sortie de traçage désactivée au démarrage.
Vous pouvez activer/désactiver la sortie de traçage en envoyant un signal SIGUSR2 au programme.
MONO_TRACE_LISTENER
S'il est défini, active le System.Diagnostics.DefaultTraceListener, qui affichera la sortie des classes System.Diagnostics Trace et Debug. Il peut être défini sur un nom de fichier, et sur Console.Out ou Console.Error pour afficher la sortie sur la sortie standard ou l'erreur standard, respectivement. S'il est défini sur Console.Out ou Console.Error, vous pouvez ajouter un préfixe optionnel qui sera utilisé lors de l'écriture des messages comme ceci : Console.Error:MonNomProgramme. Voir la documentation de System.Diagnostics.DefaultTraceListener pour plus d'informations.
MONO_WCF_TRACE
Ceci facilite la fonctionnalité de diagnostic WCF en sortant simplement tous les messages de journal du moteur WCF vers "stdout", "stderr" ou tout fichier pa

VARIABLES D'ENVIRONNEMENT POUR LE DÉBOGAGE

MONO_GC_DEBUG
Permet de spécifier les options de débogage du Garbage Collector. Par exemple, «n`'s enables the generation of C# code for the method, which will be emitted to the standard error. When using this option, you can attach to the running process with gdb and use the command 'info mono gc' to see the status of the GC. See the file `mono/metadata/gc-internal.h' for a list of options.
MONO_GC_LOG
Log GC activity to the specified file. The log format is the same as usual diagnostic output.
MONO_XEXCEPTIONS
Ceci déclenche une exception lorsqu'une erreur X11 est rencontrée ; par défaut, un message est affiché mais l'exécution continue.
MONO_XMLSERIALIZER_DEBUG
Définissez cette valeur sur 1 pour empêcher le sérialiseur de supprimer les fichiers temporaires qui sont créés pour une sérialisation rapide ; cela peut être utile lors du débogage.
MONO_XSYNC
Ceci est utilisé dans l'implémentation de System.Windows.Forms lors de l'exécution avec le backend X11. Il est utilisé pour déboguer des problèmes dans Windows.Forms car il force toutes les commandes envoyées au serveur X11 à être exécutées de manière synchrone. Le mode de fonctionnement par défaut est asynchrone, ce qui rend difficile l'isolement de la cause de certains problèmes.
MONO_XDEBUG
Lorsque la variable d'environnement MONO_XDEBUG est définie, les informations de débogage pour le code JITté sont émises dans une bibliothèque partagée, chargeable dans gdb. Cela permet, par exemple, de voir les noms des trames managées dans les traces de pile gdb.
MONO_VERBOSE_METHOD
Active la verbosité JIT maximale pour la méthode spécifiée. Ceci est très utile pour diagnostiquer des problèmes de mauvaise compilation d'une méthode spécifique. Il peut s'agir d'une liste de noms de méthodes séparés par des points-virgules. Si le nom est simple, cela s'applique à toute méthode portant ce nom, sinon vous pouvez utiliser une description de méthode mono (voir la section DESCRIPTIONS DES MÉTHODES).
MONO_JIT_DUMP_METHOD
Active l'envoi de la représentation intermédiaire du JIT pour une méthode spécifiée vers l'outil IdealGraphVisualizer.
MONO_VERBOSE_HWCAP
Si défini, le JIT affiche des informations sur les fonctionnalités du CPU détectées (telles que SSE, CMOV, FCMOV, etc.) sur la sortie standard.
MONO_CONSERVATIVE_HWCAP
Si défini, le JIT n'effectuera aucune détection de capacité matérielle. Ceci peut être utile pour identifier la cause des problèmes JIT. C'est le comportement par défaut lorsque Mono est compilé en tant que compilateur croisé AOT, afin que le code généré s'exécute sur la plupart du matériel.

VALGRIND

Si vous souhaitez utiliser Valgrind, vous trouverez le fichier `mono.supp' utile, il contient les suppressions pour le GC qui déclenchent des avertissements incorrects. Utilisez-le comme suit :

    valgrind --suppressions=mono.supp mono ...

DTRACE

Sur certaines plateformes, Mono peut exposer un ensemble de sondes DTrace (également connues sous le nom de sondes prédéfinies statiquement dans l'espace utilisateur, sondes USDT).

Elles sont définies dans le fichier `mono.d'.
ves-init-begin, ves-init-end
Début et fin de l'initialisation du runtime.
method-compile-begin, method-compile-end
Début et fin de la compilation d'une méthode. Les arguments des sondes sont le nom de la classe, le nom et la signature de la méthode, et dans le cas de method-compile-end, le succès ou l'échec de la compilation.
gc-begin, gc-end
Début et fin du Garbage Collection.
Pour vérifier la disponibilité des sondes, exécutez :
    dtrace -P mono'$target' -l -c mono

PERMISSIONS

L'implémentation Ping de Mono pour détecter l'accessibilité du réseau peut créer les paquets ICMP elle-même sans nécessiter la commande ping du système pour effectuer le travail. Si vous souhaitez activer cela sous Linux pour les utilisateurs non root, vous devez accorder des permissions spéciales au binaire Mono.

En tant que root, exécutez cette commande :

   # setcap cap_net_raw=+ep /usr/bin/mono

FICHIERS

Sous Unix, les assemblies sont chargés depuis le répertoire lib d'installation. Si vous définissez `prefix' sur /usr, les assemblies seront situées dans /usr/lib. Sous Windows, les assemblies sont chargées depuis le répertoire où se trouvent mono et mint.

~/.mono/aot-cache
Le répertoire pour les assemblies créées à la demande par le compilateur ahead-of-time sont situées.
/etc/mono/config, ~/.mono/config
Fichier de configuration du runtime Mono. Voir la page de manuel mono-config(5) pour plus d'informations.
~/.config/.mono/certs, /usr/share/.mono/certs
Contient les magasins de certificats Mono pour les utilisateurs / la machine. Voir la page de manuel certmgr(1) pour plus d'informations sur la gestion des magasins de certificats et la page mozroots(1) pour des informations sur la manière d'importer les certificats racines Mozilla dans le magasin de certificats Mono.
~/.mono/assemblies/ASSEMBLY/ASSEMBLY.config
Les fichiers dans ce répertoire permettent à un utilisateur de personnaliser la configuration d'un assembly système donné, le format est celui décrit dans la page mono-config(5).
~/.config/.mono/keypairs, /usr/share/.mono/keypairs
Contient les paires de clés cryptographiques Mono pour les utilisateurs / la machine. Elles peuvent être accédées en utilisant un objet CspParameters avec les classes DSACryptoServiceProvider et RSACryptoServiceProvider.
~/.config/.isolatedstorage, ~/.local/share/.isolatedstorage, /usr/share/.isolatedstorage
Contient le stockage isolé Mono pour les utilisateurs non itinérants, les utilisateurs itinérants et la machine locale. Le stockage isolé peut être accédé en utilisant les classes de l'espace de noms System.IO.IsolatedStorage.
<assembly>.config
Les informations de configuration pour les assemblies individuels sont chargées par le runtime à partir de fichiers côte à côte avec les fichiers .config, voir http://www.mono-project.com/Config pour plus d'informations.
Web.config, web.config
Les applications ASP.NET sont configurées via ces fichiers, la configuration se fait par répertoire. Pour plus d'informations sur ce sujet, voir la page http://www.mono-project.com/Config_system.web.
