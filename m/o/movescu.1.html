NOM

movescu - SCU de récupération DICOM (C-MOVE)

SYNTAXE

movescu [options] pair port [fichier-dcm-entree...]

DESCRIPTION

L'application movescu implémente à la fois un SCU pour la classe de service Requête/Récupération et un SCP pour la classe de service Stockage. movescu prend en charge la fonctionnalité de récupération à l'aide du message C-MOVE. Il envoie des clés de requête à un SCP et attend les réponses. Il acceptera les associations dans le but de recevoir les images envoyées suite à la requête C-MOVE. L'application peut être utilisée pour tester les SCP de la classe de service Requête/Récupération. L'application movescu peut initier le transfert d'images vers un tiers ou récupérer les images vers elle-même. Notez que le terme « move » est un terme impropre. L'opération C-MOVE effectue en fait une copie d'image (aucune image ne sera supprimée du SCP).

PARAMETRES

pair        nom d'hôte du pair DICOM
port        numéro de port TCP/IP du pair
fichier-dcm-entree  fichiers DICOM de requête

NOTES

Chaque fichier fourni sur la ligne de commande sera envoyé au SCP dans le cadre d'une requête C-MOVE. Le fichier de requête doit être un jeu de données DICOM valide contenant la partie jeu de données d'un message C-MOVE-RQ. Le fichier de requête pourrait, par exemple, être créé avec l'utilitaire dump2dcm à partir d'un script comme l'exemple suivant :

# demander toutes les images pour le patient avec l'ID=PAT001
(0008,0052) CS [PATIENT]     # QueryRetrieveLevel
(0010,0020) LO [PAT001]      # PatientID

Les attributs individuels de chaque fichier envoyé peuvent être modifiés ou complétés à l'aide de l'option -k (ou --key). Par exemple, la commande :

movescu -k 0010,0020=PAT002 caesar 5678 patqry.dcm

lorsqu'elle est envoyée au SCP caesar sur le port TCP/IP 5678, entraînera la valeur 'PAT002' pour tout attribut PatientID dans patqry.dcm. Si un tel attribut est présent, il sera remplacé ; s'il est absent, il sera inséré. L'option -k peut être présente plusieurs fois. La partie valeur (après le '=') peut être absente, provoquant l'envoi de l'attribut avec une longueur nulle. Il n'est pas possible de remplacer ou d'insérer des attributs dans des séquences à l'aide de l'option -k.

Si aucun fichier n'est spécifié sur la ligne de commande, la requête doit être spécifiée entièrement avec une ou plusieurs options -k. Si plusieurs fichiers de requête sont fournis, movescu enverra plusieurs requêtes C-MOVE au SCP.

Pour toutes les utilisations de movescu, le SCP doit être configuré pour « connaître » le titre AE vers lequel les images doivent être transmises. Ceci est nécessaire car la requête C-MOVE ne contient que le titre AE de la cible, et le SCP doit être capable de convertir ce titre AE en adresse TCP/IP et numéro de port afin d'envoyer réellement les images sur une association distincte.

L'opération C-MOVE du service Query/Retrieve peut récupérer des images (lorsque l'option --port est utilisée) ou initier une copie d'images vers un tiers.

Problèmes connus

movescu est destiné à être utilisé comme outil de test pour les développeurs de logiciels DICOM. Le fichier des clés de requête doit être créé manuellement en fonction du contenu du SCP.

L'application movescu ne fait aucune tentative pour empêcher les requêtes incorrectes. En particulier, les clés de requête d'une demande C-MOVE ne devraient contenir que l'attribut QueryRetrieveLevel et un ou plusieurs des « attributs de clé uniques » (PatientID, StudyInstanceUID, SeriesInstanceUID et SOPInstanceUID).

Dans le cas où le client de stockage ne termine pas la connexion pendant que movescu joue le rôle du serveur de stockage (c'est-à-dire que --port est utilisé), mais que le client s'attend plutôt à ce que movescu ferme la connexion de stockage, movescu attendra indéfiniment. Dans ce cas, movescu ne fermera pas non plus l'association qui a été utilisée pour émettre la requête C-MOVE au serveur C-MOVE.

L'application movescu prend en charge les classes SOP suivantes en tant que SCU :

Contrôle d'accès

Lorsqu'il est compilé sur des plateformes Unix avec le support des "TCP wrappers", le contrôle d'accès basé sur les hôtes peut être activé avec l'option de ligne de commande --access-control. Dans ce cas, les règles de contrôle d'accès définies dans les tables de contrôle d'accès des hôtes du système pour movescu sont appliquées. Les emplacements par défaut des tables de contrôle d'accès des hôtes sont /etc/hosts.allow et /etc/hosts.deny. Plus de détails sont décrits dans hosts_access(5).

EXEMPLES

movescu --patient --port 9876 --move TEST_AE --call ARCHIVE caesar 104 q.dcm

envoie les attributs contenus dans le fichier DICOM "q.dcm" dans le cadre d'une requête C-MOVE à l'entité applicative ARCHIVE sur l'hôte caesar au port 104 en utilisant le modèle de requête Patient Root. movescu utilise lui-même le titre AE par défaut MOVESCU. La requête C-MOVE spécifiera que les images doivent être transférées à l'entité AE de destination TEST_AE (via l'option --move). La façon dont le SCP interprète cette requête dépend de sa configuration. movescu écoutera sur le port 9876 les associations entrantes afin de recevoir les images demandées du SCP.

Les images peuvent être copiées vers un tiers en utilisant un titre AE de destination différent (par exemple, --move ANOTHER_AE). Bien sûr, le SCP doit "connaître" ce titre AE et la destination doit agir comme un SCP de la classe de service de stockage (l'application storescp peut être utilisée à cet effet).

JOURNALISATION

Le niveau de sortie de journalisation des différents outils en ligne de commande et des bibliothèques sous-jacentes peut être spécifié par l'utilisateur. Par défaut, seuls les erreurs et les avertissements sont écrits sur le flux d'erreurs standard. L'utilisation de l'option --verbose permet également de signaler des messages d'information tels que les détails de traitement. L'option --debug peut être utilisée pour obtenir plus de détails sur l'activité interne, par exemple à des fins de débogage. D'autres niveaux de journalisation peuvent être sélectionnés à l'aide de l'option --log-level. En mode --quiet, seuls les erreurs fatales sont signalées. Dans des événements d'erreur aussi graves, l'application se terminera généralement. Pour plus de détails sur les différents niveaux de journalisation, voir la documentation du module "oflog".

Si la sortie de journalisation doit être écrite dans un fichier (éventuellement avec rotation de fichier journal), vers syslog (Unix) ou le journal des événements (Windows), l'option --log-config peut être utilisée. Ce fichier de configuration permet également de diriger certains messages uniquement vers un flux de sortie particulier et de filtrer certains messages en fonction du module ou de l'application où ils sont générés. Un exemple de fichier de configuration est fourni dans <etcdir>/logger.cfg.

LIGNE DE COMMANDE

Tous les outils en ligne de commande utilisent la notation suivante pour les paramètres : les crochets indiquent les valeurs optionnelles (0-1), trois points de suspension indiquent que plusieurs valeurs sont autorisées (1-n), une combinaison des deux signifie 0 à n valeurs.

Les options de ligne de commande sont distinguées des paramètres par un signe '+' ou '-' respectivement. Habituellement, l'ordre et la position des options de ligne de commande sont arbitraires (c'est-à-dire qu'elles peuvent apparaître n'importe où). Cependant, si les options sont mutuellement exclusives, c'est l'apparition la plus à droite qui est utilisée. Ce comportement est conforme aux règles d'évaluation standard des shells Unix courants.

De plus, un ou plusieurs fichiers de commande peuvent être spécifiés en utilisant le signe '@' comme préfixe du nom de fichier (par exemple, @command.txt). Un tel argument de commande est remplacé par le contenu du fichier texte correspondant (plusieurs espaces sont traités comme un seul séparateur sauf s'ils apparaissent entre deux guillemets) avant toute autre évaluation. Veuillez noter qu'un fichier de commande ne peut pas contenir un autre fichier de commande. Cette approche simple mais efficace permet de résumer des combinaisons courantes d'options/paramètres et évite les lignes de commande trop longues et confuses (un exemple est fourni dans le fichier <datadir>/dumppat.txt).

ENVIRONNEMENT

L'utilitaire movescu tentera de charger les dictionnaires de données DICOM spécifiés dans la variable d'environnement DCMDICTPATH. Par défaut, c'est-à-dire si la variable d'environnement DCMDICTPATH n'est pas définie, le fichier <datadir>/dicom.dic sera chargé, sauf si le dictionnaire est intégré à l'application (par défaut pour Windows).

Le comportement par défaut doit être préféré et la variable d'environnement DCMDICTPATH ne doit être utilisée que lorsque des dictionnaires de données alternatifs sont requis. La variable d'environnement DCMDICTPATH a le même format que la variable PATH des shells Unix, c'est-à-dire qu'un deux-points (":") sépare les entrées. Sur les systèmes Windows, un point-virgule (";") est utilisé comme séparateur. Le code du dictionnaire de données tentera de charger chaque fichier spécifié dans la variable d'environnement DCMDICTPATH. C'est une erreur si aucun dictionnaire de données ne peut être chargé.
