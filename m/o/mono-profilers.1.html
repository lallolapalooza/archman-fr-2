Paquet: mono

mono-profilers(1) Manuel des commandes générales mono-profilers(1)

NOM

mono-profilers - Modules de profilage groupés de Mono

SYNTAXE

mono --profile=log[:option,...] programme.exe [args]...

mono --profile=coverage[:option,...] programme.exe [args]...

mono --profile=aot[:option,...] programme.exe [args]...

DESCRIPTION

Mono est livré avec quelques modules de profilage qui permettent la plupart des scénarios de profilage typiques. Cette page décrit chacun d'eux dans les sections ci-dessous.

PROFILAGE LOG

Le profiler log est le profiler de performance généraliste de Mono. Il peut collecter une grande variété de données qui peuvent être analysées par des outils tels que mprof-report(1) ou le Profiler Xamarin.

Par défaut, le profiler log écrit sa sortie dans output.mlpd. Référez-vous au fichier mono/profiler/log.h dans l'arbre source de Mono pour la documentation sur le format de fichier du profiler log.

Une invocation par défaut du profiler log ne rassemble que des données de base : événements de chargement et déchargement de métadonnées, événements de démarrage et d'arrêt de threads, échantillons de compteurs de performance, lancements d'exceptions, etc. La plupart des utilisateurs voudront activer certaines des fonctionnalités plus lourdes telles que l'enregistrement des allocations GC, l'échantillonnage statistique, la capture instantanée de tas (heapshots), ou l'instrumentation d'entrée et de sortie de méthodes. Voir la sous-section Options.

Notez que, dans la plupart des scénarios réalistes, le profiler log enregistrera une quantité énorme de données. Cela peut entraîner des fichiers journaux très volumineux. (Les options zip et report peuvent aider à gérer cela.)

Options

Le profiler log prend en charge les options suivantes :

help
Affiche les instructions d'utilisation.
output=[+|#||]fichier
Écrit les données du log dans fichier. Les modificateurs optionnels sont :
+
Le PID du programme est ajouté au nom du fichier. Par exemple, output=+out.mlpd sort dans out.mlpd.1234 si le PID est 1234.
#
fichier est analysé comme un descripteur de fichier, qui est ouvert avec fdopen(3). Ceci est principalement utile dans les scénarios d'intégration.
|
fichier est traité comme un nom de programme. Il sera lancé avec popen(3) et les données du log seront redirigées vers son entrée standard.
report
Génère un rapport directement au lieu d'écrire les données du log dans un fichier. Si cette option est utilisée conjointement avec l'option output, le rapport sera écrit dans le fichier spécifié au lieu des données du log.
zip
Compresse le fichier de sortie avec gzip(1).
port=port
Utilise port pour écouter les connexions du serveur de commandes. Voir la sous-section Serveur de commandes.
nodefaults
Désactive la compatibilité pré-Mono 5.6. En particulier, cela désactive les événements d'exception et l'échantillonnage des compteurs de performance par défaut. Cela garantit également que les événements de déplacement GC ne seront pas activés par défaut lorsque les heapshots sont activés. Pour utiliser cette option, elle doit être la première option donnée au profiler log.
Cette option sera la valeur par défaut dans une future version du profiler log.
[no]event
Active ou désactive la collecte de données pour event, qui peut être :
exception
Événements de lancement et d'évaluation de clauses d'exception (catch, finally, etc.). Activé par défaut sauf si nodefaults est utilisé.
monitor
Événements de contention, d'acquisition et de libération des moniteurs.
gc
Événements de démarrage, de progression, d'arrêt et de redimensionnement du GC.
gcalloc
Événements d'allocation GC.
gcmove
Événements de déplacement GC.
gcroot
Événements de rapport de racines GC. Générés à chaque collecte si activés, sauf si nodefaults est utilisé, auquel cas ils ne sont générés que lors des heapshots.
gchandle
Événements de création et de suppression de handles GC.
finalization
Événements de finalisation d'objets.
counter
Événements d'échantillons de compteurs de performance. Activé par défaut sauf si nodefaults est utilisé.
jit
Événements de buffer de code JIT.
alloc
Alias pour gc, gcalloc et gcmove.
legacy
Alias pour exception, monitor, gc, gcmove, gcroot, gchandle, finalization et counter.
sample[-real][=freq]
Active l'échantillonnage statistique. La valeur par défaut est d'échantillonner à une fréquence de 100 Hz, mais freq peut être utilisé pour la remplacer.
Par défaut, l'échantillonnage utilise le temps processeur (c'est-à-dire que plus un processus effectue de travail, plus il collecte d'échantillons). La variante -real utilise le temps réel (horloge murale) à la place. Le temps réel est meilleur pour les programmes liés aux E/S.
maxsamples=num
Limite le nombre d'événements d'échantillons réutilisables à num allocations. Une valeur de zéro signifie aucune limite. Par défaut, la valeur de ce paramètre est basée sur le nombre de cœurs de processeur. Quelques ajustements de ce paramètre peuvent être nécessaires pour les programmes ayant un nombre inhabituellement élevé de threads.
calls
Active l'instrumentation d'entrée et de sortie de méthodes. C'est une alternative à l'échantillonnage statistique lorsque vous avez besoin d'informations plus précises. Notez que ce mode est extrêmement lourd et peut ralentir la plupart des programmes considérablement.
callspec=spec
Limite l'instrumentation d'entrée et de sortie de méthodes aux méthodes correspondant à la spécification d'appel spécifiée. Ceci utilise la même syntaxe que l'option --trace de mono(1), donc référez-vous à cette page pour plus d'informations.
calldepth=num
Limite la collecte des événements d'entrée et de sortie de méthodes à une profondeur d'appel de num.
maxframes=num
Limite les traces de pile dans divers événements (y compris les échantillons statistiques) à num cadres.
heapshot[=mode]
Active les captures instantanées de tas. mode, s'il est donné, peut être l'un des suivants :
ondemand
Ne réalise une heapshot que lors de la réception d'une commande via le serveur de commandes ou lorsqu'elle est déclenchée via la bibliothèque managée.
numgc
Réalise une heapshot sur chaque num collecte de la génération majeure.
numms
Réalise une heapshot lors d'une collecte de la génération majeure si num millisecondes se sont écoulées depuis la dernière heapshot.
Si mode n'est pas donné, une heapshot sera effectuée sur chaque collecte de la génération majeure.
heapshot-on-shutdown
En plus de tout autre paramètre de heapshot

PROFILAGE COVÉRAAGE

Le profiler de couverture mesure la couverture du code exécuté. Il ne nécessite aucune option spéciale pour commencer, mais il existe quelques options pour ajuster son comportement.

Options

Le profiler de couverture prend en charge les options suivantes :

help
Affiche les instructions d'utilisation.
output=fichier
Écrit les données du log dans fichier. Le PID est ajouté au nom de fichier par défaut.
port=port
Utilise port pour écouter les connexions du serveur de commandes.
module=nom
Active la génération de rapports de couverture pour le module spécifié.

PROFILAGE AOT

Le profiler AOT est utilisé pour profiler la compilation Ahead-Of-Time (AOT). Il génère une image AOT du code managé exécuté, puis le profile.

Options

Le profiler AOT prend en charge les options suivantes :

help
Affiche les instructions d'utilisation.
output=fichier
Utilise fichier comme nom de fichier de sortie pour l'image AOT.
port=port
Utilise port pour écouter les connexions du serveur de commandes.
temp-path=chemin
Utilise chemin comme répertoire temporaire pour stocker les images AOT générées.
aot-options=options
Transmet les options spécifiées au compilateur AOT.

SERVEUR DE COMMANDES

Tous les profilers mentionnés ci-dessus peuvent être contrôlés à distance via un serveur de commandes. Pour ce faire, vous devez démarrer le processus managé avec l'option --profile=type:port=port, où type est le type de profiler et port est le numéro de port TCP à utiliser. Ensuite, vous pouvez vous connecter à ce port avec un client tel que mono-cmd(1).

Le serveur de commandes accepte les commandes suivantes :

heapshot
Demande une capture instantanée de tas.
shutdown
Arrête le serveur de commandes et termine le processus.
quit
Arrête le serveur de commandes sans terminer le processus.

EXEMPLES

Profi le programme my_program.exe avec le profiler log, en activant la journalisation des allocations GC et en générant un rapport :

$ mono --profile=log:alloc,report my_program.exe

Profi le programme my_program.exe avec le profiler de couverture, en écrivant la sortie dans coverage.log :

$ mono --profile=coverage:output=coverage.log my_program.exe

Profi le programme my_program.exe avec le profiler AOT, en utilisant le répertoire temporaire /tmp/aot et en passant l'option --optimize=inline au compilateur AOT :

$ mono --profile=aot:temp-path=/tmp/aot:aot-options='--optimize=inline' my_program.exe

Profi le programme my_program.exe avec le profiler log, en activant le serveur de commandes sur le port 12345 :

$ mono --profile=log:port=12345 my_program.exe

Ensuite, dans une autre console, connectez-vous au serveur de commandes et demandez une capture instantanée de tas :

$ mono-cmd --port 12345 heapshot

Serveur de commandes

Le profiler de journalisation dispose d'un simple serveur de commandes qui est actuellement uniquement utilisé pour déclencher des heaptshots manuels (typiquement lors de l'utilisation du mode à la demande, mais utilisable également avec les autres modes). Un port aléatoire sera utilisé pour écouter les connexions, sauf si l'option port est utilisée. Pour déclencher un heapshot, ouvrez une connexion TCP au serveur de commandes et envoyez la chaîne C "heapshot\n".

Le serveur de commandes prend en charge plusieurs connexions simultanées.

Bibliothèque gérée

Le profiler de journalisation est livré avec une bibliothèque gérée appelée Mono.Profiler.Log. Cette bibliothèque permet de lire facilement des fichiers journaux dans du code géré (par exemple, C#) ainsi que d'interagir avec le profiler au moment de l'exécution.

Grâce à la possibilité de lire facilement les fichiers journaux, les utilisateurs peuvent écrire toutes sortes d'analyses intéressantes qui pourraient ne pas être fournies par les outils standard (par exemple, mprof-report(1)).

La classe LogProfiler permet aux utilisateurs de reconfigurer les paramètres du profiler au moment de l'exécution. Par exemple, certains types d'événements peuvent être activés ou désactivés, le mode et la fréquence des heaptshots et de l'échantillonnage peuvent être modifiés, etc. Les heaptshots peuvent également être déclenchés manuellement.

Pour utiliser cette bibliothèque, passez simplement -r:Mono.Profiler.Log lors de la compilation de votre code.

Exemple

Collecter les données d'allocation GC et d'échantillonnage pour un programme, puis générer un rapport :

mono --profile=log:alloc,sample program.exe
mprof-report output.mlpd

Effectuer un heapshot à chaque 5ème collection et générer un rapport directement :

mono --profile=log:heapshot=5gc,report program.exe

PROFILER DE COUVERTURE

Le profiler de couverture de code collecte des informations sur la fréquence d'exécution des chemins de code. Ceci est fait en instrumentant le code compilé JIT à tous les points de séquence. À la sortie du programme, le profiler de couverture collecte toutes les informations de comptage d'exécution et les écrit dans un fichier XML. Le principal cas d'utilisation du profiler de couverture est les tests unitaires : en exécutant des suites de tests unitaires avec le profiler de couverture, il est possible de déterminer si les tests unitaires couvrent réellement tout le code qu'ils devraient couvrir.

Par défaut, le profiler de couverture écrit sa sortie dans coverage.xml. Référez-vous au fichier mono/profiler/coverage.c dans l'arborescence source de Mono pour la documentation sur le schéma.

Veuillez noter que le profiler de couverture ne prend actuellement pas en charge l'instrumentation du code compilé AOT. Lors de la collecte de données de couverture, il peut être souhaitable d'exécuter Mono avec l'option -O=-aot pour désactiver le chargement du code compilé AOT.

Options

Le profiler de couverture prend en charge les options suivantes :

help
Imprimer les instructions d'utilisation.
output=[+|#||]fichier
Écrire les données de couverture dans fichier. Les modificateurs optionnels sont :
+
Le PID du programme est ajouté au nom du fichier. Par exemple, output=+cov.xml écrit dans cov.xml.1234 si le PID est 1234.
#
fichier est analysé comme un numéro de descripteur de fichier, qui est ouvert avec fdopen(3). Ceci est principalement utile dans les scénarios d'intégration.
|
fichier est traité comme un nom de programme. Il sera lancé avec popen(3) et les données de couverture seront envoyées via un pipe à son entrée standard.
covfilter-file=fichier
Fournir un fichier de filtre de couverture. Cette option peut être donnée plusieurs fois. Voir la sous-section Fichiers de filtre.

Fichiers de filtre

Les fichiers de filtre peuvent être utilisés pour choisir les types qui doivent être pris en compte pour l'instrumentation de couverture. Un fichier de filtre se compose d'une série de lignes de la forme :

+|-[nom_image]préfixe_nom_type

Ici, nom_image est quelque chose comme mscorlib. préfixe_nom_type peut être quelque chose comme System.Int32 pour un type spécifique ou System.App pour sélectionner tous les types commençant par App dans le namespace System.

Les lignes commençant par + indiquent qu'un type doit être instrumenté pour la couverture, tandis que les lignes commençant par - indiquent le contraire. Les lignes commençant par + remplacent toujours les lignes commençant par -, quel que soit leur ordre d'apparition.

Les lignes ne commençant par aucun de ces caractères sont ignorées. Ceci peut être utilisé pour écrire des commentaires. Par exemple, ceci est un fichier valide :

# Ignorer la couverture dans le code lié au réseau, sauf le code client HTTP.
-[MonProgramme]MonProgramme.Net
+[MonProgramme]MonProgramme.Net.Http.HttpClient

Exemple

Les données de couverture pour un programme peuvent être collectées comme suit :

mono -O=-aot --profile=coverage:output=cov.xml program.exe

cov.xml contiendra maintenant les données de couverture.

PROFILER AOT

Le profiler AOT enregistrera quelles instanciations génériques un programme utilise et sauvegardera les informations dans un fichier spécifié. Ces données peuvent ensuite être utilisées par le compilateur AOT pour compiler ces instanciations génériques à l'avance afin de réduire le temps de démarrage du programme.

Par défaut, le profiler AOT écrit sa sortie dans output.aotprofile. Référez-vous au fichier mono/profiler/aot.h dans l'arborescence source de Mono pour la documentation sur le format de fichier du profiler AOT.

Options

Le profiler AOT prend en charge les options suivantes :

duration=nombre
Profiler uniquement NUM secondes d'exécution, puis écrire les données.
help
Imprimer les instructions d'utilisation.
output=[+|#||]fichier
Écrire les données de sortie dans fichier. Les modificateurs optionnels sont :
+
Le PID du programme est ajouté au nom du fichier. Par exemple, output=+out.aotprofile écrit dans out.aotprofile.1234 si le PID est 1234.
#
fichier est analysé comme un numéro de descripteur de fichier, qui est ouvert avec fdopen(3). Ceci est principalement utile dans les scénarios d'intégration.
|
fichier est traité comme un nom de programme. Il sera lancé avec popen(3) et les données du journal seront envoyées via un pipe à son entrée standard.
verbose
Imprimer des informations de débogage détaillées. La plupart des utilisateurs ne devraient pas utiliser cette option.

Exemple

Un profil peut être collecté et utilisé comme suit :

mono --profile=aot:output=program.aotprofile program.exe
mono --aot=profile=program.aotprofile program.exe
mono program.exe
