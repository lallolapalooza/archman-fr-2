MONIT(1) Commandes utilisateur MONIT(1)

NOM

Monit - utilitaire pour surveiller les services sur un système Unix

SYNTAXE

monit [options] <arguments>

DESCRIPTION

Monit est un utilitaire pour gérer et surveiller les processus, programmes, fichiers, répertoires et systèmes de fichiers sur un système Unix. Monit effectue des tâches de maintenance et de réparation automatiques et peut exécuter des actions causales significatives en cas d'erreur. Par exemple, Monit peut démarrer un processus s'il ne tourne pas, redémarrer un processus s'il ne répond pas et arrêter un processus s'il utilise trop de ressources. Vous pouvez utiliser Monit pour surveiller les fichiers, les répertoires et les systèmes de fichiers pour détecter des changements, tels que des changements d'horodatage, des changements de checksum ou des changements de taille.

Monit est contrôlé via un fichier de configuration facile à configurer basé sur une syntaxe libre et orientée jetons. Monit enregistre dans syslog ou dans son propre fichier journal et vous informe des conditions d'erreur via des messages d'alerte personnalisables. Monit peut effectuer diverses vérifications réseau TCP/IP, des vérifications de protocoles et peut utiliser SSL pour ces vérifications. Monit fournit une interface HTTP(S) et vous pouvez utiliser un navigateur pour accéder au programme Monit.

QUOI SURVEILLER ?

Vous pouvez utiliser Monit pour surveiller des processus de démons ou des programmes similaires fonctionnant sur localhost. Monit est particulièrement utile pour surveiller les processus de démons, tels que ceux démarrés au démarrage du système. Par exemple sendmail, sshd, apache et mysql. Contrairement à de nombreux autres systèmes de surveillance, Monit peut agir si une situation d'erreur se produit, par exemple ; si sendmail ne tourne pas, monit peut redémarrer sendmail automatiquement ou si apache utilise trop de ressources (par exemple, si une attaque DoS est en cours), Monit peut arrêter ou redémarrer apache et vous envoyer un message d'alerte. Monit peut également surveiller les caractéristiques des processus, telles que la quantité de mémoire ou de cycles CPU utilisés par un processus.

Vous pouvez également utiliser Monit pour surveiller des fichiers, des répertoires et des systèmes de fichiers sur localhost. Monit peut surveiller ces éléments pour détecter des changements, tels que des changements d'horodatage, des changements de checksum ou des changements de taille. Ceci est également utile pour des raisons de sécurité - vous pouvez surveiller la checksum md5 ou sha1 des fichiers qui ne devraient pas changer et recevoir une alerte ou effectuer une action s'ils devaient changer.

Monit peut surveiller les connexions réseau vers divers serveurs, soit sur localhost, soit sur des hôtes distants. Les sockets TCP, UDP et Unix Domain sont pris en charge. Les tests réseau peuvent être effectués au niveau du protocole ; Monit a des tests intégrés pour les principaux protocoles Internet, tels que HTTP, SMTP etc. Même si un protocole n'est pas pris en charge, vous pouvez toujours tester le serveur car vous pouvez configurer Monit pour envoyer n'importe quelle donnée et tester la réponse du serveur.

Monit peut être utilisé pour tester des programmes ou des scripts à des moments précis, un peu comme cron, mais en plus, vous pouvez tester la valeur de retour d'un programme et effectuer une action ou envoyer une alerte si la valeur de retour indique une erreur. Cela signifie que vous pouvez utiliser Monit pour effectuer tout type de vérification pour lequel vous pouvez écrire un script.

Enfin, Monit peut être utilisé pour surveiller les ressources générales du système sur localhost telles que l'utilisation globale du CPU, la mémoire et la charge système.

FONCTIONNEMENT GÉNÉRAL

Le comportement de Monit est contrôlé par des options en ligne de commande et un fichier de contrôle d'exécution, monitrc, dont la syntaxe est décrite dans une section ultérieure. Les options en ligne de commande remplacent les déclarations du fichier .monitrc.

L'emplacement par défaut pour monitrc est ~/.monitrc. Si ce fichier n'existe pas, Monit essaiera /etc/monitrc et quelques autres endroits. Voir FICHIERS pour plus de détails. Vous pouvez également spécifier le fichier de contrôle directement en utilisant le commutateur de commande -c de monit. Par exemple,

$ monit -c /var/monit/monitrc

Avant que Monit ne soit démarré pour la première fois, vous pouvez tester le fichier de contrôle pour les erreurs de syntaxe :

$ monit -t
$ Syntaxe du fichier de contrôle OK

S'il y avait une erreur, Monit affichera un message d'erreur sur la console, y compris le numéro de ligne dans le fichier de contrôle où l'erreur a été trouvée.

Une fois que vous avez un fichier de contrôle Monit fonctionnel, démarrez simplement Monit depuis la console, comme ceci :

$ monit

Vous pouvez modifier certaines directives de configuration via des commutateurs en ligne de commande, mais par souci de simplicité, il est recommandé de les placer dans le fichier de contrôle.

Monit se détachera du terminal et s'exécutera en tant que processus d'arrière-plan, c'est-à-dire en tant que processus démon. En tant que démon, Monit s'exécute par cycles ; il surveille les services, puis se met en veille pendant une période configurée, puis se réveille et recommence la surveillance dans une boucle infinie.

Arguments

Une fois que Monit s'exécute en tant que processus démon, vous pouvez appeler Monit avec l'un des arguments suivants. Monit se connectera alors au démon Monit (sur le port TCP 127.0.0.1:2812 par défaut) et demandera au démon Monit d'effectuer l'action demandée. En d'autres termes, appeler monit sans arguments démarre le démon Monit, et appeler monit avec des arguments vous permet de communiquer avec le processus démon Monit.

start all
Démarre tous les services listés dans le fichier de configuration et active leur surveillance. Si l'option groupe est définie (-g), démarre et active la surveillance uniquement des services du groupe nommé (ici, "all" n'est pas requis).
start <nom|motif>
Démarre le service nommé et active sa surveillance. Le nom est un nom d'entrée de service du fichier monitrc. Vous pouvez également utiliser un motif regex (notez qu'il est insensible à la casse).
stop all
Arrête tous les services listés dans le fichier de configuration et désactive leur surveillance. Si l'option groupe est définie, arrête et désactive la surveillance uniquement des services du groupe nommé (ici, "all" n'est pas requis).
stop <nom|motif>
Arrête le service nommé et désactive sa surveillance. Le nom est un nom d'entrée de service du fichier monitrc. Vous pouvez également utiliser un motif regex (notez qu'il est insensible à la casse).
restart all
Arrête et démarre tous les services. Si l'option groupe est définie, redémarre uniquement les services du groupe nommé (ici, "all" n'est pas requis).
restart <nom|motif>
Redémarre le service nommé. Le nom est un nom d'entrée de service du fichier monitrc.

LE FICHIER DE CONTROLE MONIT

Monit est configuré et contrôlé via un fichier de contrôle appelé monitrc. L'emplacement par défaut de ce fichier est ~/.monitrc. Si ce fichier n'existe pas, Monit essaiera /etc/monitrc, puis @sysconfdir@/monitrc et enfin ./monitrc. Si vous compilez Monit à partir des sources, la valeur de @sysconfdir@ peut être spécifiée lors de la configuration avec ./configure --sysconfdir. Par exemple, en utilisant ./configure --sysconfdir /var/monit/etc, Monit recherchera monitrc dans /var/monit/etc.

Pour protéger la sécurité de votre fichier de contrôle et de vos mots de passe, le fichier de contrôle doit avoir des permissions de lecture-écriture pas supérieures à 0700 (u=xrw,g=,o=); Monit se plaindra et se terminera sinon.

Lorsqu'il y a un conflit entre les arguments de la ligne de commande et les arguments de ce fichier, les arguments de la ligne de commande ont la priorité.

Monit utilise son propre langage spécifique à un domaine (DSL); Le fichier de contrôle se compose d'une série d'entrées de service et d'instructions d'options globales.

Les commentaires commencent par un '#' et s'étendent jusqu'à la fin de la ligne. Sinon, le fichier se compose d'une série d'entrées de service ou d'instructions d'options globales dans une syntaxe de format libre, orientée jetons.

Vous pouvez utiliser des mots-clés superflus comme 'if', 'and', 'with(in)', 'has', 'us(ing|e)', 'on(ly)', 'then', 'for', 'of' n'importe où dans une entrée pour la faire ressembler à de l'anglais. Ils sont ignorés, mais peuvent rendre les entrées beaucoup plus faciles à lire d'un coup d'œil. Les mots-clés sont insensibles à la casse.

Il existe trois types de jetons : grammaire, nombres (c'est-à-dire des séquences de chiffres décimaux) et chaînes. Les chaînes peuvent être quotées ou non quotées. Une chaîne quotée est délimitée par des guillemets doubles et peut contenir des espaces (et les chiffres quotés sont traités comme une chaîne). Une chaîne non quotée est tout jeton délimité par des espaces, contenant des caractères et/ou des nombres.

Sur le plan sémantique, le fichier de contrôle se compose de trois types d'entrées :

1. Instructions globales set-statements
Une instruction globale set-statement commence par le mot-clé "set" et l'élément à configurer.
2. Instruction globale include-statement
L'instruction include se compose du mot-clé "include" et d'une chaîne glob. Cette instruction est utilisée pour inclure des directives de configuration à partir de fichiers séparés.
3. Une ou plusieurs instructions d'entrée de service.

Vérifications des services

Chaque entrée de service se compose des mots-clés "check", suivis du type de service. Chaque entrée nécessite un nom descriptif unique, qui peut être choisi librement. Ce nom est utilisé par Monit pour faire référence au service en interne et dans toutes les interactions avec l'utilisateur. Le nom est insensible à la casse.

Actuellement, neuf types d'instructions de vérification sont pris en charge :

Process

CHECK PROCESS <nom unique> <PIDFILE <chemin> | MATCHING <regex>>

<chemin> est le chemin absolu du fichier pid du programme. Un fichier pid est un fichier contenant l'ID unique d'un processus. Si le fichier pid n'existe pas ou ne contient pas le numéro PID d'un processus en cours d'exécution, Monit appellera la méthode de démarrage de l'entrée si elle est définie.

<regex> est une alternative à l'utilisation des fichiers PID et utilise la correspondance de nom de processus par motif pour trouver le processus à surveiller. Le parent correspondant le plus élevé avec le temps de fonctionnement le plus long est sélectionné, donc cette forme de vérification est la plus utile si le nom du processus est unique. Pid-file devrait être utilisé autant que possible car il définit exactement le PID attendu. Vous pouvez vérifier si un processus correspond à un motif depuis la ligne de commande en utilisant "monit procmatch "motif-regex"". Cela listera tous les processus correspondant ou non au motif regex.

File

CHECK FILE <nom unique> PATH <chemin>

<chemin> est le chemin absolu du fichier. Si le fichier n'existe pas, Monit appellera la méthode de démarrage de l'entrée si elle est définie. Si <chemin> ne pointe pas vers un type de fichier régulier (par exemple, un répertoire), Monit désactivera la surveillance de cette entrée. Si Monit s'exécute en mode passif ou si la méthode de démarrage n'est pas définie, Monit enverra simplement une alerte en cas d'erreur.

Fifo

CHECK FIFO <nom unique> PATH <chemin>

<chemin> est le chemin absolu du fifo. Si le fifo n'existe pas, Monit appellera la méthode de démarrage de l'entrée si elle est définie. Si <chemin> ne pointe pas vers un type fifo (par exemple, un répertoire), Monit désactivera la surveillance de cette entrée. Si Monit s'exécute en mode passif ou si la méthode de démarrage n'est pas définie, Monit enverra simplement une alerte en cas d'erreur.

Filesystem

CHECK FILESYSTEM <nom unique> PATH <chaîne>

<chemin> est le chemin vers le périphérique/disque, le point de montage ou la chaîne de connexion NFS/CIFS/FUSE. Si le système de fichiers devient indisponible, Monit appellera la méthode de démarrage du service si elle est définie. Si Monit s'exécute en mode passif ou si la méthode de démarrage n'est pas définie, Monit enverra simplement une alerte en cas d'erreur.

Directory

CHECK DIRECTORY <nom unique> PATH <chemin>

<chemin> est le chemin absolu du répertoire. Si le répertoire n'existe pas, Monit appellera la méthode de démarrage de l'entrée si elle est définie. Si <chemin> ne pointe pas vers un répertoire, Monit désactivera la surveillance de cette entrée. Si Monit s'exécute en mode passif ou si la méthode de démarrage n'est pas définie, Monit enverra simplement une alerte en cas d'erreur.

Remote host

CHECK HOST <nom unique> ADDRESS <hôte>

L'adresse de l'hôte peut être spécifiée sous forme de chaîne de nom d'hôte ou sous forme de chaîne d'adresse IP au format décimal pointé. Par exemple, "tildeslash.com" ou "64.87.72.95".

System

CHECK SYSTEM <nom unique>

Le nom unique est généralement le nom d'hôte local, mais tout nom descriptif peut être utilisé. Si vous utilisez la variable $HOST comme nom, elle sera développée en nom d'hôte. Cette vérification permet de surveiller les ressources système générales telles que l'utilisation du CPU, l'utilisation totale de la mémoire ou la charge moyenne. Le nom unique est utilisé comme nom d'hôte du système dans les alertes par e-mail et comme nom initial de l'entrée hôte dans M/Monit.

Program

CHECK PROGRAM <nom unique> PATH <fichier exécutable> [TIMEOUT <nombre> SECONDS]

<chemin> est le chemin absolu du programme ou script exécutable. Le test d'état permet de vérifier le code de sortie du programme. Si le programme ne termine pas son exécution dans le délai de <nombre> secondes, Monit le terminera. Le délai d'attente par défaut du programme est de 300 secondes (5 minutes). La sortie du programme est enregistrée et mise à disposition dans l'interface utilisateur et dans les alertes, jusqu'à 512 octets par défaut. Vous pouvez modifier la limite de sortie en utilisant l'instruction set limits).

Network

CHECK NETWORK <nom unique> <ADDRESS <adresse ip> | INTERFACE <nom>>

<adresse ip> est l'adresse IPv4 ou IPv6 de l'interface réseau surveillée. Il est également possible d'utiliser le nom de l'interface, comme "eth0" sous Linux.

JOURNALISATION

Monit enregistrera les statuts et les messages d'erreur dans un fichier ou via syslog. Utilisez l'instruction set log dans le fichier de contrôle monitrc.

Pour configurer Monit afin qu'il journalise dans son propre fichier, utilisez par exemple set log /var/log/monit.log. Notez que l'instruction set logfile précédente est dépréciée, mais peut être utilisée alternativement.

Si syslog est donné comme valeur pour le commutateur de ligne de commande "-l" ou si le mot-clé set log syslog est trouvé dans le fichier de contrôle, Monit utilisera le démon système syslog pour enregistrer les messages avec une priorité attribuée à chaque message en fonction du contexte.

Pour désactiver la journalisation

, il suffit de ne pas définir le log dans le fichier de contrôle (et bien sûr, ne pas utiliser le commutateur -l)

Le format d'une entrée dans le fichier journal est :

[date] priorité : message

par exemple :

[2020-08-12T16:35:00+0200] info : 'localhost' Monit démarré

SORTIE TERMINALE

Monit utilise des séquences d'échappement ANSI pour coloriser les parties importantes de la sortie de la ligne de commande, si le terminal prend en charge les couleurs, et des caractères de boîte UTF-8 pour la sortie tabulaire.

Si vous souhaitez traiter la sortie CLI de monit dans un script, vous pouvez utiliser l'option -B ou la déclaration suivante dans le fichier de configuration de monit pour désactiver complètement la sortie tabulaire et les couleurs :

SET TERMINAL BATCH

MODE DAEMON

Utilisez

SET DAEMON <secondes>
    [[WITH] START DELAY <secondes>]

pour spécifier la durée du cycle de scrutation de Monit et exécuter Monit en mode démon. Vous devez spécifier un argument numérique qui est un intervalle de scrutation en secondes.

En mode démon, Monit se détache de la console, se met en arrière-plan et s'exécute en continu, surveillant chaque service spécifié, puis se met en veille pendant l'intervalle de scrutation donné, se réveille et recommence à surveiller dans un cycle sans fin.

Alternativement, vous pouvez utiliser le commutateur de ligne de commande "-d" pour définir l'intervalle de scrutation, mais il est fortement recommandé de définir l'intervalle de scrutation dans votre fichier ~/.monitrc, en utilisant set daemon.

Monit démarrera alors toujours en mode démon. Si vous n'utilisez pas cette déclaration et ne lancez pas monit avec l'option -d, Monit parcourra les vérifications de service une seule fois puis se terminera. Cela peut être utile dans certaines situations, mais Monit est principalement conçu pour s'exécuter en tant que processus démon.

Appeler "monit" avec un démon Monit en cours d'exécution en arrière-plan envoie un signal de réveil au démon, le forçant à vérifier les services immédiatement. Appeler "monit" avec l'argument quit tuera un processus démon Monit en cours d'exécution au lieu de le réveiller.

L'option de délai de démarrage peut être utilisée pour attendre (une seule fois) avant que Monit ne commence à vérifier les services après le redémarrage du système. Monit commencera par défaut à vérifier les services immédiatement au démarrage.

SUPPORT INIT

La déclaration "set init" empêche Monit de se transformer en processus démon. Au lieu de cela, Monit s'exécutera en tant que processus de premier plan. (Vous devriez toujours utiliser "set daemon" pour spécifier le cycle de scrutation).

Ceci est nécessaire pour exécuter Monit à partir d'init. Utiliser init pour démarrer Monit est probablement la meilleure façon d'exécuter Monit si vous voulez être sûr d'avoir toujours un démon Monit en cours d'exécution sur votre système. Une autre option est d'exécuter Monit à partir de crontab. Dans tous les cas, vous devez vous assurer que le fichier de contrôle ne contient aucune erreur de syntaxe avant de démarrer Monit à partir d'init ou de crontab (utilisez "monit -t" pour vérifier).

Pour configurer Monit pour qu'il s'exécute à partir d'init, vous pouvez soit utiliser la déclaration "set init" dans le fichier de contrôle de Monit, soit utiliser l'option "-I" depuis la ligne de commande. Voici ce que vous devez ajouter à "/etc/inittab" :

# Exécute Monit dans les niveaux d'exécution standard
mo:2345:respawn:/usr/local/bin/monit -Ic /etc/monitrc

Après avoir modifié le fichier de configuration d'init, vous pouvez exécuter la commande suivante pour réexaminer /etc/inittab et démarrer Monit :

telinit q

Pour les systèmes sans telinit :

kill -1 1

Si Monit est utilisé pour surveiller des services qui sont également démarrés au moment du démarrage (par exemple, des services démarrés via les scripts rc de SYSV init ou via inittab), alors, dans certains cas, une condition de concurrence pourrait se produire. C'est-à-dire ; si un service est lent à démarrer, Monit peut supposer que le service ne fonctionne pas et tenter de le démarrer et d'émettre une alerte, alors qu'en fait le service est déjà sur le point de démarrer ou est déjà dans sa séquence de démarrage. Veuillez consulter la FAQ pour une solution à ce problème. La version courte est de démarrer Monit sur un niveau d'exécution supérieur après les processus système.

FICHIERS INCLUDE

Le fichier de contrôle de Monit, "monitrc", peut inclure des fichiers de configuration supplémentaires. Cette fonctionnalité permet d'organiser la configuration en fichiers séparés au lieu d'avoir tout dans un seul fichier, si vous aimez ce genre de chose. Les instructions d'inclusion peuvent être placées pratiquement n'importe où dans "monitrc", bien que la convention soit de les mettre en bas. La syntaxe est la suivante :

INCLUDE <globstring>

La globstring est de n'importe quel type de chaîne tel que défini dans glob(7). Ainsi, vous pouvez faire référence à un seul fichier ou vous pouvez charger plusieurs fichiers à la fois. Si vous souhaitez utiliser des espaces dans votre chaîne, la globstring doit être intégrée entre guillemets (') ou guillemets doubles ("). Si la globstring correspond à un répertoire et non à un fichier, elle est silencieusement ignorée.

Toute instruction include dans un fichier inclus est analysée comme dans le fichier de contrôle principal.

Si la globstring correspond à plusieurs résultats, les fichiers sont inclus de manière non triée. Si vous avez besoin de compter sur un ordre particulier, vous devez éviter le globbing avec caractères génériques et spécifier plutôt le chemin complet des fichiers inclus.

Un exemple,

include /etc/monit.d/*.cfg

Cela chargera tout fichier correspondant à la globstring. C'est-à-dire tous les fichiers dans /etc/monit.d qui se terminent par le préfixe .cfg.

Jusqu'à 1024 fichiers d'inclusion sont pris en charge. Si cette limite est dépassée, Monit signalera une erreur.

OPTIONS SSL

Les options SSL/TLS courantes peuvent être définies à l'aide de la déclaration suivante et s'appliqueront à toutes les connexions SSL effectuées via Monit :

SET <SSL | TLS> [OPTIONS] {
    VERSION: <AUTO | [-]SSLV2 | [-]SSLV3 | [-]TLSV1 | [-]TLSV11 | [-]TLSV12 | [-]TLSV13>, ...
    VERIFY: <ENABLE | DISABLE>
    SELFSIGNED: <ALLOW | REJECT>
    CIPHERS: <string>
    PEMFILE: <path>
    PEMCHAIN: <path>
    PEMKEY: <path>
    CLIENTPEMFILE: <path>
    CACERTIFICATEFILE: <path>
    CACERTIFICATEPATH: <path>
}

VERSION définit la version SSL/TLS spécifique à utiliser. Par défaut, Monit utilise AUTO. En mode AUTO, seuls TLS 1.2 et 1.3 sont autorisés, tous les autres protocoles sont considérés comme obsolètes. Si vous souhaitez utiliser le protocole obsolète, vous devez explicitement définir la version. Vous pouvez exclure le protocole en utilisant le préfixe "-". Exemple de liste d'exclusion :
set ssl {
version: auto -sslv2 -sslv3 -tlsv1 -tlsv11
} Exemple de liste de protocoles autorisés :
set ssl {
version: tlsv12 tlsv13
}

VERIFY active la vérification du certificat du serveur SSL. Cela vérifiera et signalera une erreur si le certificat du serveur n'est pas approuvé, n'est pas valide ou a expiré. Par défaut, la vérification du certificat est désactivée, bien que nous recommandions de l'activer, sinon il n'y a aucune garantie que Monit communique avec le serveur auquel vous pensez.

SELFSIGNED les certificats auto-signés sont rejetés par défaut. Utilisez cette option pour autoriser les certificats auto-signés. Attention : non recommandé en production pour des raisons de sécurité, car dans ce cas, le client ne peut pas vérifier qu'il parle au bon serveur et des types d'attaques comme l'homme du milieu ou le détournement DNS sont possibles).

CIPHERS remplace les chiffrements SSL/TLS par défaut.

PEMFILE définit le chemin vers le "fichier de base de données" du certificat serveur SSL au format PEM. Cette option n'a d'effet que pour l'interface HTTP de monit.

Comme alternative à la définition de PEMFILE avec un fichier chaîne-clé combiné, PEMCHAIN et PEMKEY définissent le chemin vers la chaîne de certificats SSL respectivement le fichier de clé privée du serveur au format PEM. Ces options n'ont d'effet que pour l'interface HTTP de monit.

CLIENTPEMFILE définit le chemin vers le fichier de base de données des certificats clients SSL encodés en PEM. S'il est défini, une authentification par certificat client est activée.

CACERTIFICATEFILE définit le chemin vers le fichier encodé en PEM contenant les certificats de l'autorité de certification (CA). Monit utilise les certificats CA par défaut d'OpenSSL si cette option n'est pas utilisée (openssl version -d peut être utilisé pour obtenir les certificats CA par défaut). De nombreuses distributions sont livrées avec SSL et les certificats CA déjà configurés et l'utilisation de cette option n'est normalement pas nécessaire.

CACERTIFICATEPATH définit le chemin vers le répertoire contenant les certificats de l'autorité de certification (CA). Monit utilise les certificats CA par défaut d'OpenSSL si cette option n'est pas utilisée. De nombreuses distributions sont livrées avec SSL et les certificats CA déjà configurés et l'utilisation de cette option n'est normalement pas nécessaire.

La déclaration d'options SSL s'appliquera globalement à toutes les connexions SSL/TLS effectuées via Monit. Les options SSL peuvent également être définies dans une vérification locale, dans les paramètres mailserver ou dans la déclaration mmonit, et remplaceront alors ou étendront les paramètres globaux.

Pour définir les options SSL globales, placez cette déclaration en haut de votre fichier .monitrc :

set ssl options {...}

Voici un exemple de définition d'options SSL globales et locales :

# Activer la vérification du certificat pour toutes les connexions SSL
# Les certificats auto-signés ne sont pas autorisés par défaut
set ssl options {
        verify: enable
}
# Vérifier le certificat (via paramètre global)
# Autoriser le certificat auto-signé pour cette vérification
check host example with address example.com
        if failed
                port 443
                protocol https
                with ssl options {selfsigned: allow}
        then alert
# Ne pas vérifier le certificat de example2.com (remplace le paramètre global)
check host example2 with address example2.com
        if failed
                port 443
                protocol https
                with ssl options {verify: disable}
        then alert

MODE FIPS

Pour activer le mode FIPS (si votre bibliothèque OpenSSL le prend en charge), ajoutez cette déclaration au fichier de contrôle de Monit :

SET FIPS

MONIT HTTPD

Si spécifié dans le fichier de contrôle, Monit démarrera avec le support HTTP. Vous pourrez alors utiliser la CLI de Monit pour démarrer et arrêter des services, désactiver ou activer la surveillance des services ainsi que visualiser l'état de chaque service.

Si le support HTTP est activé sur TCP plutôt que sur un socket Unix, vous pouvez également visualiser le tableau de bord informatif de Monit dans votre navigateur web

wser.

Notez que si la prise en charge HTTP est désactivée, l'interface CLI de Monit aura des fonctionnalités réduites, car la plupart des commandes CLI (telles que « monit status ») doivent communiquer avec le processus d'arrière-plan de Monit via l'interface HTTP. Nous recommandons fortement de garder la prise en charge HTTP activée. Si la sécurité est une préoccupation, liez l'interface HTTP uniquement à l'hôte local ou utilisez un socket Unix afin que Monit ne soit pas accessible depuis l'extérieur.

SOCKET UNIX

Syntaxe pour le socket Unix :

SET HTTPD UNIX SOCKET <chemin>
    [UID <uid | nom d'utilisateur>]
    [GID <gid | nom de groupe>]
    [PERMISSION <nombre octal>]
    ALLOW <utilisateur:mot de passe>+

Exemple :

set httpd unixsocket /var/run/monit.sock
    allow username:password

UNIXSOCKET définit le chemin d'accès au socket Unix auquel Monit doit se lier et sur lequel il doit écouter.

UID Propriétaire du socket (facultatif, par défaut l'utilisateur qui exécute Monit)

GID Groupe du socket (facultatif, par défaut le groupe primaire de l'utilisateur qui exécute Monit)

PERMISSION Permissions du socket - mode octal absolu (facultatif, l'UMASK du processus est appliqué par défaut)

PORT TCP

Syntaxe pour le port TCP :

SET HTTPD PORT <numéro>
    [ADDRESS <nom d'hôte | adresse IP>]
    [[with] SSL {pemfile: <chemin>}]
    ALLOW <utilisateur:mot de passe | adresse IP | plage IP>+

PORT définit le port sur lequel Monit doit se lier et écouter. Monit est généralement configuré sur le port 2812. Exemple :

set httpd port 2812
    allow username:password

Vous pouvez maintenant utiliser http://localhost:2812/ pour accéder à l'interface Web de Monit depuis un navigateur, après avoir entré le nom d'utilisateur et le mot de passe comme identifiants. Vous pourriez avoir besoin d'utiliser des guillemets doubles autour du mot de passe s'il contient des caractères spéciaux tels que « p@ssw:r# ».

ADDRESS oblige Monit à n'écouter que sur une interface spécifique. Par exemple, si vous ne voulez *pas* exposer l'interface Web de Monit sur le réseau, liez-la uniquement à localhost. Monit acceptera les connexions sur toutes les adresses si l'option ADDRESS n'est pas utilisée :

set httpd
    port 2812
    use address 127.0.0.1
    allow username:password

Monit HTTP sur TCP prend en charge les versions IP 4 et 6. La prise en charge est transparente et ne nécessite aucune configuration spéciale. Si l'adresse de liaison *n'*est pas spécifiée, comme dans cet exemple :

set httpd
  port 2812
  allow ...

Monit se liera et écoutera sur le port 2812 sur toutes les interfaces, IPv4 et IPv6 si disponibles. Pour forcer Monit HTTP à n'écouter et accepter les connexions que via l'IP version 6, spécifiez une adresse IPv6 :

set httpd
  port 2812
  use address « fe80::222:19ff:fe53:6c59 »
  allow ...

De même, pour forcer Monit HTTP à n'écouter et accepter les connexions que via l'IP version 4, spécifiez une adresse IPv4 :

set httpd
  port 2812
  use address 62.109.39.247
  allow ...

Paramètres SSL

SSL active SSL/TLS pour l'interface Web de Monit. Voir les options pour la liste complète des options SSL.

PEMFILE définit le chemin d'accès au fichier codé PEM, qui contient la clé privée et le certificat du serveur. Ce fichier doit être stocké dans un endroit sûr sur le système de fichiers et avoir des permissions strictes, pas plus de 0700.

Alternativement, *PEMCHAIN* et *PEMKEY* définissent le chemin d'accès aux fichiers séparés de chaîne de certificats et de clé privée codés PEM. Le fichier de clé doit être stocké dans un endroit sûr sur le système de fichiers et avoir des permissions strictes, pas plus de 0700.

Exemple d'utilisation de pemfile :

set httpd
    port 2812
    with ssl {
       pemfile: /etc/ssl/certs/monit.pem
    }
    allow myuser:mypassword

Exemple d'utilisation d'une chaîne de certificats et d'une clé séparées :

set httpd
    port 2812
    with ssl {
       pemchain: /etc/ssl/certs/monit.chain.pem
       pemkey: /etc/ssl/certs/monit.key.pem
    }
    allow myuser:mypassword

Vous pouvez maintenant utiliser https://localhost:2812/ pour accéder au serveur Web Monit via une connexion cryptée TLS.

Note sur les certificats serveur auto-signés : L'interface CLI de Monit fonctionne sur une base client-serveur et utilise l'interface graphique HTTP de Monit pour collecter l'état du démon Monit et lui transmettre des commandes comme démarrer/arrêter. Comme les certificats auto-signés sont rejetés par défaut pour des raisons de sécurité, l'interface CLI ne fonctionnera pas à moins que vous ne l'autorisiez explicitement en utilisant l'option *SELFSIGNED: ALLOW* :

set httpd
   port 2812
   with ssl {
      pemfile: /etc/ssl/certs/monit.pem
      selfsigned: allow
   }
   allow myuser:mypassword

CLIENTPEMFILE active une authentification basée sur un certificat client et définit le chemin d'accès à un fichier de base de données codé PEM, qui contient une liste de certificats clients autorisés. Un client se connectant doit fournir un certificat connu de Monit (listé dans *clientpemfile*), sinon il est rejeté. Ce fichier doit également inclure tous les certificats CA nécessaires. Par défaut, les certificats clients auto-signés sont *rejetés* pour des raisons de sécurité, si vous souhaitez autoriser les certificats clients auto-signés (recommandé uniquement pour les tests), vous devez l'autoriser explicitement en utilisant l'option SELFSIGNED: ALLOW (voir l'exemple ci-dessus). Consultez la documentation de votre navigateur pour savoir comment importer un certificat client dedans.

Exemple :

set httpd
    port 2812
    with SSL {
        pemfile:       /etc/ssl/certs/monit.pem
        clientpemfile: /etc/ssl/certs/monit-client.pem
    }

Signature de version Monit

SIGNATURE peut être utilisée pour masquer la version de Monit de l'en-tête de réponse HTTP et des pages d'erreur. Par exemple :

set httpd
  port 2812
  signature disable
  allow myuser:mypassword

Authentification

L'accès à l'interface Web de Monit est principalement contrôlé par l'option ALLOW qui est utilisée pour spécifier l'authentification et autoriser uniquement certains clients à se connecter.

Si l'interface de ligne de commande de Monit est utilisée, au moins un mot de passe en clair est nécessaire (voir ci-dessous), sinon l'interface de ligne de commande de Monit ne pourra pas se connecter à l'interface Web de Monit.

Les clients qui tentent de se connecter à Monit, mais soumettent un nom d'utilisateur et/ou un mot de passe incorrect sont enregistrés avec leur adresse IP.

Certificats clients

Cette méthode d'authentification est un mécanisme d'authentification forte et utilise des certificats clients HTTPS pour vérifier l'authenticité d'un client connecté. Les clients doivent posséder un certificat à clé publique connu de Monit. Le client doit se connecter à Monit via SSL et Monit demandera au client d'envoyer son certificat. Après réception du certificat, Monit le compare aux certificats situés dans le fichier *CLIENTPEMFILE*. L'accès est accordé si le certificat client se trouve dans ce fichier. Voir les paramètres SSL pour plus de détails.

Authentification de base

Monit prend en charge l'Authentification de Base telle que décrite dans la RFC 2617.

En bref ; un serveur met au défi un client (par exemple, un navigateur) de lui envoyer des informations d'authentification (nom d'utilisateur et mot de passe) et si elles sont acceptées, le serveur autorisera le client à accéder au document demandé.

La plus grande faiblesse de l'Authentification de Base est que le nom d'utilisateur et le mot de passe sont envoyés en clair sur le réseau (c'est-à-dire encodés en base64). Il est donc recommandé de ne pas utiliser cette méthode d'authentification à moins que vous n'exécutiez Monit avec la prise en charge *ssl*. Avec SSL, il est sûr d'utiliser l'Authentification de Base car *toutes* les données HTTP, y compris les en-têtes d'Authentification de Base, seront cryptées.

Utilisateur et mot de passe en clair

Monit utilisera l'Authentification de Base si une instruction ALLOW contient un nom d'utilisateur et un mot de passe séparés par un seul caractère « : ».

Note : Les caractères spéciaux peuvent être utilisés, mais pour les non-alphanumériques, le mot de passe doit être entre guillemets.

Syntaxe :

ALLOW <nom d'utilisateur>:<mot de passe>

Liste d'autorisation d'hôtes et de réseaux

Monit maintient une liste de contrôle d'accès des hôtes et des réseaux autorisés à se connecter. Vous pouvez ajouter autant d'hôtes que vous le souhaitez, mais seuls les hôtes avec un nom de domaine valide ou leur adresse IP sont autorisés.

Monit interrogera un serveur de noms pour vérifier tous les hôtes qui tentent de se connecter. Si un hôte (client) tente de se connecter, mais ne peut pas être trouvé dans la liste d'accès ou ne peut pas être résolu, Monit fermera promptement la connexion au client.

Exemple de fichier de contrôle :

set httpd port 2812
    allow localhost
    allow my.other.work.machine.com
    allow 10.1.1.1
    allow 192.168.1.0/255.255.255.0
    allow 10.0.0.0/8

Les clients, non mentionnés dans la liste d'autorisation et tentant de se connecter à Monit, se verront refuser l'accès et seront enregistrés avec leur adresse IP.

PAM

PAM est pris en charge sur les plateformes qui fournissent PAM (telles que Linux, macOS, FreeBSD, NetBSD).

Syntaxe :

ALLOW @<groupe>

où « groupe » est le nom du groupe autorisé à accéder à l'interface Web de Monit. Monit utilise un service PAM appelé *monit* pour l'authentification PAM, consultez la page man PAM pour des instructions détaillées sur la configuration du service PAM et des plugins d'authentification PAM.

Exemple de service PAM pour Monit sur macOS (enregistrer en tant que fichier « /etc/pam.d/monit ») :

# monit: auth account password session
#auth       sufficient     pam_securityserver.so
#auth       sufficient     pam_unix.so
auth       sufficient     pam_opendirectory.so
auth       required       pam_deny.so
account    required       pam_permit.so
password   required       pam_deny.so
session    required       pam_permit.so

Et un service PAM similaire pour Monit sous Linux (enregistrer en tant que fichier « /etc/pam.d/monit ») :

# monit: auth account password session
auth       sufficient   pam_unix2.so
auth       required     pam_deny.so
account    required     pam_permit.so
password   required     pam_deny.so
session    required     pam_permit.so

Une configuration « monitrc » qui n'autorise que les groupes « admin » et « staff » authentifiés via PAM à accéder à l'interface Web :

set httpd
    port 2812
    allow @admin
    allow @staff readonly

Fichier htpasswd

Alternativement, vous pouvez stocker les identifiants dans un fichier formaté « htpasswd » (une entrée *utilisateur:mot de passe* par ligne), comme ceci : allow [cleartext|crypt|md5] /chemin [utilisateurs]. Par défaut, ce sont des mots de passe en clair. Si les mots de passe sont hachés, il est nécessaire de spécifier la méthode cryptographique. Si vous ne voulez pas que tous les utilisateurs du fichier de mots de passe aient accès à Monit, vous pouvez spécifier uniquement les utilisateurs qui devraient avoir accès dans l'instruction ALLOW. Sinon, tous les utilisateurs sont ajoutés.

Exemple 1 :

`e>définir httpd port 2812
    allow md5 /etc/httpd/htpasswd john paul ringo george

Si vous utilisez cette méthode conjointement avec une liste d'hôtes, seuls les clients des hôtes listés seront autorisés à se connecter au serveur HTTP Monit et chaque client sera invité à fournir un nom d'utilisateur et un mot de passe.

Exemple2 :

définir httpd port 2812
    allow localhost
    allow 10.1.1.1
    allow hauk:"passw@rd"

Si vous souhaitez uniquement utiliser l'authentification de base, fournissez simplement des entrées "allow" avec nom d'utilisateur et mot de passe ou des fichiers de mots de passe comme dans l'exemple 1 ci-dessus.

Utilisateurs en lecture seule

De plus, il est possible de définir certains utilisateurs comme étant en lecture seule. Un utilisateur en lecture seule peut consulter les pages Web de Monit mais n'aura *pas* accès aux boutons poussoirs et ne pourra pas modifier un service depuis l'interface Web.

définir httpd port 2812
    allow admin:password
    allow hauk:password read-only
    allow @admins
    allow @users read-only

Un utilisateur est défini en lecture seule en utilisant le mot-clé read-only **après** le nom d'utilisateur:mot de passe. Dans l'exemple ci-dessus, l'utilisateur hauk est défini comme un utilisateur en lecture seule, tandis que l'utilisateur admin a tous les droits d'accès.

Serveur HTTP en lecture seule

Enfin, il est possible de restreindre l'ensemble de l'interface Web en lecture seule. Tous les utilisateurs, qu'ils soient définis avec ou sans le mot-clé read-only, n'ont que les permissions décrites ci-dessus. Lors de l'utilisation de ce paramètre, il est recommandé de configurer également un **UNIX SOCKET**, sinon le CLI de Monit ne fonctionnera **pas**.

définir httpd
    port 2812
        read-only
    unixsocket /run/monit.socket
    allow @users

MESSAGES D'ALERTE

Monit déclenchera une alerte dans les situations suivantes :

o Un service n'existe pas (par ex. le processus ne tourne pas)
o Impossible de lire les données du service (par ex. impossible d'obtenir l'utilisation du système de fichiers)
o L'exécution d'un script lié au service a échoué (par ex. l'arrêt a échoué)
o Type de service invalide (par ex. si le chemin pointe vers un répertoire au lieu d'un fichier)
o Le script de test personnalisé a renvoyé une erreur
o Le test Ping a échoué
o Connexion TCP/UDP et/ou test de port échoué
o Test d'utilisation des ressources échoué (par ex. utilisation du processeur trop élevée)
o Inadéquation ou modification de la somme de contrôle (par ex. le fichier a changé)
o Test de taille de fichier échoué (par ex. le fichier est trop grand)
o Test d'horodatage échoué (par ex. le fichier est plus ancien que prévu)
o Test de permission échoué (par ex. le mode de fichier ne correspond pas)
o Test d'UID échoué (par ex. fichier appartenant à un utilisateur différent)
o Test de GID échoué (par ex. fichier appartenant à un groupe différent)
o Le PID d'un processus a changé hors du contrôle de Monit
o Le PPID d'un processus a changé hors du contrôle de Monit
o Trop de tentatives de récupération de service ont échoué
o Le test de contenu de fichier a trouvé une correspondance
o Les indicateurs du système de fichiers ont changé
o Une action sur le service a été effectuée par l'administrateur
o Un lien réseau est tombé ou s'est rétabli
o La capacité d'un lien réseau a changé
o L'assainissement d'un lien réseau a échoué
o Le taux de téléchargement/téléversement d'un lien réseau a échoué
o Monit a été démarré, arrêté ou rechargé

Pour recevoir une alerte par e-mail, définissez la cible de l'alerte à l'aide de l'instruction globale "set alert" (pour tous les services) ou de l'instruction "alert" dans le contexte d'une entrée de service (pour un seul service).

Définition d'un destinataire d'alerte

Si un événement se produit, Monit envoie une alerte. Il existe deux types d'instructions d'alerte : globale et locale.

Syntaxe globale :

SET ALERT adresse-mail [[PAS] {événement, ...}] [RAPPEL cycles]

Exemple :

définir alert foo@bar

enverra un e-mail par défaut à l'adresse foo@bar chaque fois qu'un événement se produit sur n'importe quel service.

Si vous souhaitez envoyer des messages d'alerte à plusieurs adresses e-mail, ajoutez une instruction "set alert 'email'" pour chaque adresse.

Il est également possible d'utiliser l'instruction d'alerte locale dans le contexte d'une vérification de service pour activer l'alerte uniquement pour le service donné :

ALERT adresse-mail [[PAS] {événement, ...}] [RAPPEL cycles]

Exemple d'alerte locale :

check host myhost with address 1.2.3.4
    if failed port 3306 protocol mysql then alert
    if failed port 80 protocol http then alert
    alert foo@baz # Alerte de service locale

Vous pouvez combiner des instructions d'alerte globales et locales. En cas de conflit, l'alerte locale a la priorité et remplace l'instruction globale.

Définition d'un filtre d'événements

Si vous souhaitez qu'un message d'alerte ne soit envoyé que pour certains événements, listez-les dans un bloc "{événement, ...}", par exemple :

définir alert foo@bar seulement sur { timeout, nonexist }

La liste d'événements peut également être niée pour envoyer des alertes pour tous les événements *sauf* ceux qui sont listés, en préfixant la liste par le mot "not". Par exemple, pour recevoir toutes les alertes sauf les notifications de démarrage et d'arrêt du programme Monit :

définir alert foo@bar mais pas sur { instance }

Définition d'un rappel d'erreur

Monit envoie par défaut une seule notification si un service a échoué et une autre lorsqu'il se rétablit. Si vous souhaitez être informé que le service est toujours dans un état défaillant, vous pouvez utiliser l'option de rappel dans l'instruction d'alerte :

SET ALERT adresse-mail [AVEC] RAPPEL [SUR] nombre [CYCLES]

Par exemple, si vous souhaitez être informé à chaque dixième cycle si un service reste dans un état défaillant, vous pouvez utiliser :

alert foo@bar avec rappel sur 10 cycles

De même, si vous souhaitez être informé à chaque cycle défaillant, vous pouvez utiliser :

alert foo@bar avec rappel sur 1 cycle

Désactivation des alertes pour certains services

Pour supprimer les alertes pour un utilisateur et un service donnés, ajoutez l'instruction "noalert" dans le contexte d'une vérification de service.

NOALERT adresse-mail

Exemple (envoyer toutes les alertes à foo@bar sauf pour le service p3) :

définir alert foo@bar
check process p1 with pidfile /var/run/p1.pid
check process p2 with pidfile /var/run/p2.pid
check process p3 with pidfile /var/run/p3.pid
    noalert foo@bar

Format du message

Le format du message d'alerte peut être modifié en utilisant l'instruction "set mail-format" :

SET MAIL-FORMAT {format-mail}

Exemple :

définir mail-format {
     from: Support Monit <monit@foo.bar>
reply-to: support@domain.com
  subject: $SERVICE $EVENT à $DATE
  message: Monit $ACTION $SERVICE à $DATE sur $HOST : $DESCRIPTION.
           Cordialement,
           monit
}

L'option from: est l'adresse e-mail de l'expéditeur pour les alertes Monit. Un nom d'expéditeur est facultatif, mais s'il est utilisé, il nécessite que l'adresse e-mail suivante soit entre crochets comme dans l'exemple ci-dessus.

L'option reply-to: peut être utilisée pour définir l'en-tête de réponse du courrier, éventuellement avec un nom.

L'option subject: définit l'objet du message et doit être sur une seule ligne.

L'option message: définit le corps du courrier. Cette option doit toujours être la dernière dans une instruction mail-format. Le corps du courrier peut être aussi long que nécessaire, mais ne doit pas contenir le caractère '}' de fermeture de bloc.

Vous n'êtes pas obligé d'utiliser toutes les options, uniquement celles que vous souhaitez remplacer. Par exemple, pour modifier globalement uniquement l'adresse de l'expéditeur :

définir mail-format { from: bofh@foo.bar }

Le sujet et le corps peuvent contenir des variables $NOM, qui sont développées par Monit. Voici une liste de variables qui peuvent être utilisées lors de la composition d'un message d'alerte.

  • $EVENT

    Une chaîne décrivant l'événement qui s'est produit.

  • $SERVICE

    Le nom du service

  • $DATE

    L'heure et la date actuelles (style date RFC 822).

  • $HOST

    Le nom de l'hôte sur lequel Monit est en cours d'exécution

  • $ACTION

    Le nom de l'action effectuée par Monit.

  • $DESCRIPTION

    La description de la condition d'erreur.

Configuration d'un serveur mail pour la livraison des alertes

Le serveur mail que Monit doit utiliser pour envoyer des messages d'alerte est défini avec une instruction "set mailserver" :

SET MAILSERVER
       <nom-hote|adresse-ip>
       [PORT nombre]
       [USERNAME chaîne] [PASSWORD chaîne]
       [using SSL [with options {...}]
       [CERTIFICATE CHECKSUM [MD5|SHA1] <hash>],
       ...
  [with TIMEOUT X SECONDS]
  [using HOSTNAME nom-hote]

Plusieurs serveurs mail peuvent être configurés en utilisant une liste séparée par des virgules. Si Monit ne parvient pas à se connecter au premier serveur, il essaiera le suivant dans la liste, et ainsi de suite.

L'instruction port permet de remplacer le port SMTP par défaut (465 pour SSL, ou 25 pour TLS et connexion non sécurisée).

Monit prend en charge AUTH PLAIN et AUTH LOGIN pour l'authentification SMTP. Vous pouvez définir un nom d'utilisateur et un mot de passe en utilisant les options USERNAME et PASSWORD.

Vous pouvez définir des options SSL/TLS pour la connexion et également vérifier une somme de contrôle de certificat SSL.

Le délai d'attente de connexion par défaut est de 30 secondes. Vous pouvez modifier cette limite en utilisant l'option TIMEOUT.

Exemple (configuration de deux serveurs mail pour le basculement) :

set mailserver smtp.gmail.com, smtp.other.host

Par défaut, Monit utilise le nom d'hôte local dans les commandes SMTP HELO/EHLO et dans l'en-tête Message-ID. Vous pouvez remplacer cela en utilisant l'option HOSTNAME.

File d'attente des événements

Si aucun serveur mail n'est disponible, Monit peut mettre en file d'attente les événements sur le système de fichiers local pour retry jusqu'à ce que le serveur mail soit rétabli.

Si Monit est utilisé avec M/Monit, la file d'attente des événements fournit un stockage d'événements sécurisé pour M/Monit en cas de problèmes temporaires.

La file d'attente des événements est persistante lors des redémarrages de Monit et, à condition que le système de fichiers sous-jacent soit persistant, également lors du redémarrage du système.

Par défaut, la file d'attente est désactivée et si le gestionnaire d'alertes échoue, Monit abandonnera simplement le message d'alerte.

Pour activer la file d'attente des événements, ajoutez l'instruction suivante :

SET EVENTQUEUE BASEDIR <chemin> [SLOTS <nombre>]

Le <chemin> est le chemin vers le répertoire où les événements seront stockés.

Optionnellement, si vous souhaitez limiter la taille de la file d'attente, utilisez l'option slots pour stocker jusqu'à nombre messages d'événement.

Exemple :

set eventqueue basedir /var/monit slots 5000

Si vous exécutez plus d'une instance de Monit sur la même machine, vous devez utiliser des répertoires de file d'attente d'événements séparés.

MÉTHODES DE SERVICE

Chaque service peut avoir des méthodes start, stop et restart associées que Monit peut utiliser pour exécuter des actions sur le service.

Syntaxe :

<START | STOP | RESTART> [PROGRAM] = "programme"
       [[AS] UID <nombre | chaîne>]
       [[AS] GID <nombre | chaîne>]
       [[WITH] TIMEOUT <nombre> SECONDE(S)]

Si le "programme" est un script shell, il doit commencer par "#!" et le reste de la première ligne doit spécifier un interpréteur pour le programme. Par exemple, "#!/bin/sh".

Le "programme" doit également être exécutable (par exemple, mode 0755).

Il est possible d'écrire des scripts directement dans le programme de cette manière :

stop = "/bin/sh -c 'kill -s SIGTERM `cat /var/run/process.pid`'"

Par défaut, le programme est exécuté par l'utilisateur sous lequel Monit s'exécute. Si Monit s'exécute en tant que root, vous pouvez éventuellement spécifier l'UID et le GID auxquels le programme exécuté doit basculer.

Exemple :

check process mmonit with pidfile /usr/local/mmonit/mmonit/logs/mmonit.pid
  start program = "/usr/local/mmonit/bin/mmonit" as uid "mmonit" and gid "mmonit"
  stop program = "/usr/local/mmonit/bin/mmonit stop" as uid "mmonit" and gid "mmonit"

Dans le cas d'une vérification de processus, Monit attendra jusqu'à 30 secondes que l'action de démarrage/arrêt se termine avant d'abandonner et de signaler une erreur. Vous pouvez remplacer ce délai d'attente en utilisant l'option TIMEOUT ou globalement en utilisant les limites définies.

Exemple :

check process foobar with pidfile /var/run/foobar.pid
  start program = "/etc/init.d/foobar start" with timeout 60 seconds
  stop program = "/etc/init.d/foobar stop"

TEMPS DE POLL DES SERVICES

Les services sont vérifiés régulièrement à un intervalle défini par l'instruction "set daemon n". Les vérifications sont effectuées dans le même ordre qu'elles sont écrites dans le fichier ".monitrc", sauf si des dépendances sont configurées entre les services, auquel cas les services prérequis sont testés en premier.

Il est possible de modifier la planification des vérifications d'un service en utilisant l'instruction "every".

Il existe trois variantes :

1. Un multiple du cycle de poll
EVERY [nombre] CYCLES
2. Style cron
EVERY [cron]
3. Style cron négatif (ne pas vérifier)
NOT EVERY [cron]

Une chaîne de style cron se compose de 5 champs séparés par des espaces blancs. Tous les champs sont requis :

Nom :        | Valeurs autorisées :       | Caractères spéciaux :
---------------------------------------------------------------
Minutes      | 0-59                       | * - ,
Heures        | 0-23                       | * - ,
Jour du mois | 1-31                       | * - ,
Mois        | 1-12 (1=janv, 12=déc)       | * - ,
Jour de la semaine | 0-6 (0=dim, 6=sam) | * - ,

Les caractères spéciaux :

Caractère:   | Description :
---------------------------------------------------------------
* (astérisque) | L'astérisque indique que l'expression
             | correspondra à toutes les valeurs du champ ; par
             | exemple, utiliser un astérisque dans le 4ème
             | champ (mois) indiquerait tous les mois.
- (tiret)    | Les tirets sont utilisés pour définir des
             | intervalles. Par exemple, 8-9 dans le champ
             | heures indique entre 8h et 9h. Notez que
             | l'intervalle va de l'heure de début jusqu'à
             | et incluant l'heure de fin. C'est-à-dire, de
             | 8h jusqu'à 10h, sauf si les minutes sont
             | définies. Autre exemple, 1-5 dans le champ
             | jour de la semaine, spécifie du lundi au
             | vendredi (y compris le vendredi).
, (virgule)    | Les virgules sont utilisées pour spécifier une
             | séquence. Par exemple, 17,18 dans le champ
             | jour indique le 17ème et 18ème jour du mois.
             | Une séquence peut également inclure des
             | intervalles. Par exemple, en utilisant 1-5,0
             | dans le champ jour de la semaine indique du
             | lundi au vendredi et le dimanche.

Exemple 1 : Vérifier une fois toutes les deux cycles

check process nginx with pidfile /var/run/nginx.pid
      every 2 cycles

Exemple 2 : Vérifier tous les jours ouvrables entre 8h et 19h

check program checkOracleDatabase
       with path /var/monit/programs/checkoracle.pl
      every "* 8-19 * * 1-5"

Exemple 3 : Ne pas exécuter la vérification pendant la fenêtre de sauvegarde le dimanche entre 0h et 3h du matin, sinon exécuter la vérification avec la fréquence de cycle de poll régulière.

check process mysqld with pidfile /var/run/mysqld.pid
      not every "* 0-3 * * 0"

Limitations :

Le planificateur actuel est basé sur les cycles de poll. Si une vérification de service est planifiée avec l'instruction every cron, Monit vérifiera si l'heure actuelle correspond au modèle de la chaîne cron. Si c'est le cas, la vérification est effectuée, sinon elle est ignorée. La spécification cron ne garantit pas quand exactement le test sera exécuté, cela dépend du temps de poll par défaut et de la durée du cycle de vérification. En d'autres termes, nous ne pouvons pas garantir que Monit s'exécutera à une heure précise. Par conséquent, nous recommandons fortement d'utiliser un astérisque dans le champ des minutes ou au minimum un intervalle, par exemple, 0-15. N'utilisez jamais une minute spécifique, car Monit pourrait ne pas s'exécuter à cette minute.

Nous aborderons cette limitation dans une future version et convertirons le planificateur d'un polling série à un planificateur parallèle non bloquant où les vérifications seront garanties de s'exécuter à temps et avec une résolution à la seconde.

GROUPES DE SERVICES

Les entrées de service dans le fichier de contrôle, monitrc, peuvent être regroupées par l'instruction group. La syntaxe est simplement (mot-clé en majuscules) :

GROUP nom-groupe

Avec cette instruction, il est possible de regrouper des entrées de service similaires et de les gérer comme un tout. Monit fournit des fonctions pour démarrer, arrêter, redémarrer, surveiller et désactiver la surveillance d'un groupe de services, comme suit :

Pour démarrer un groupe de services depuis la console :

monit -g <nom-groupe> start

Pour arrêter un groupe de services :

monit -g <nom-groupe> stop

Pour redémarrer un groupe de services :

monit -g <nom-groupe> restart

Un service peut être ajouté à plusieurs groupes en utilisant plusieurs instructions group :

group www
group filesystem

MODE DE SURVEILLANCE DES SERVICES

Monit prend en charge deux modes de surveillance : actif et passif.

Syntaxe :

MODE <ACTIVE | PASSIVE>

En mode actif, Monit surveillera de manière proactive un service et en cas de problème, déclenchera des alertes et redémarrera le service. Actif est le mode par défaut.

Le mode passif est similaire au mode actif, sauf si le service échoue, Monit n'essaiera pas de résoudre le problème en redémarrant le service et ne déclenchera que des alertes.

REDÉMARRAGE DU SYSTÈME ET DÉMARRAGE DES SERVICES

Monit prend en charge trois modes de redémarrage : start, nostart et laststate.

Syntaxe :

ONREBOOT <START | NOSTART | LASTSTATE>

En mode start, Monit démarrera toujours le service automatiquement au redémarrage, même s'il était arrêté avant le redémarrage. C'est le mode par défaut et il est utilisé si onreboot n'est pas spécifié.

En mode nostart, le service n'est jamais démarré automati

MODE DE COMPORTEMENT AU REDÉMARRAGE

Monit peut être configuré pour agir d'une manière spécifique lors du démarrage des services après un redémarrage.

Il existe trois modes ONREBOOT:

START
Avec le mode START, Monit essaiera de démarrer tous les services qui étaient actifs avant le redémarrage. Si un service ne démarre pas, il sera vérifié à nouveau après un cycle de surveillance.
NOSTART
Avec le mode NOSTART, tous les services seront arrêtés lors du redémarrage de Monit. Ce mode est idéal pour les solutions de haute disponibilité avec des clusters actifs/passifs. Par exemple, un groupe de services HA, composé par exemple d'un alias IP mobile et d'un serveur d'applications, est démarré sur l'hôte H1, l'hôte H2 est en mode de secours et un signal de battement est en place entre les deux hôtes. Le groupe de services HA doit être démarré sur un seul nœud. Si H1 tombe en panne, H2 prend le relais du groupe HA. Si H1 redémarre, il est important qu'il n'essaie pas de démarrer également le groupe HA. Même si le groupe était actif sur H1 avant sa défaillance, car HA fonctionne maintenant sur H2.
LASTSTATE
En mode laststate, l'état de surveillance d'un service est persistant après redémarrage. Par exemple, si un service était démarré avant le redémarrage, il sera démarré après le redémarrage. S'il était arrêté avant le redémarrage, il ne sera pas démarré et ainsi de suite.

Le mode de démarrage par défaut ONREBOOT START peut être remplacé globalement :

SET ONREBOOT <START | NOSTART | LASTSTATE>

LIMITE DE REDÉMARRAGE DU SERVICE

Monit fournit un mécanisme de limite de redémarrage pour les situations où un service refuse simplement de démarrer ou de répondre pendant une période prolongée.

Le mécanisme de limite de redémarrage est basé sur le nombre de redémarrages de service et le nombre de cycles de surveillance. Par exemple, si un service a eu x redémarrages dans les y cycles de surveillance (où x <= y), Monit effectuera une action (par exemple, désactiver la surveillance du service). En cas de dépassement de délai, Monit enverra une alerte si vous avez manifesté votre intérêt pour cet événement.

La syntaxe de l'instruction de dépassement de délai est la suivante (les mots-clés sont en majuscules) :

IF <nombre> RESTART <nombre> CYCLE(S) THEN <action>

La valeur action est soit l'une des actions courantes, soit TIMEOUT (pour la compatibilité ascendante, équivaut à l'action UNMONITOR).

Voici un exemple où Monit désactivera la surveillance du service s'il a été redémarré 2 fois en 3 cycles :

if 2 restarts within 3 cycles then unmonitor

Pour que Monit vérifie à nouveau le service après que la surveillance ait été désactivée, exécutez "monit monitor nomduservice" depuis la ligne de commande.

Exemple pour définir une exécution personnalisée en cas de dépassement de délai :

if 5 restarts within 5 cycles then exec "/foo/bar"

Exemple pour arrêter le service :

if 7 restarts within 10 cycles then stop

DÉPENDANCES DU SERVICE

Si spécifié dans le fichier de contrôle, Monit peut vérifier les dépendances avant de démarrer, d'arrêter, de surveiller ou de cesser de surveiller les services. L'instruction de dépendance peut être utilisée dans n'importe quelle entrée de service des fichiers de contrôle de Monit.

La syntaxe de l'instruction DEPENDS est simplement :

DEPENDS on service[, service [,...]]

Où service est le nom d'une entrée de service de vérification utilisée dans votre fichier ".monitrc", par exemple apache ou datafs.

Vous pouvez ajouter plus d'un nom de service de n'importe quel type ou utiliser plus d'une instruction DEPENDS dans une entrée.

Les services spécifiés dans une instruction depend seront vérifiés lors des opérations d'arrêt/démarrage/surveillance/désactivation de surveillance.

Si un service est arrêté ou si sa surveillance est désactivée, cela arrêtera/désactivera la surveillance de tous les services qui en dépendent.

Si le service est démarré, tous les services dont ce service dépend seront démarrés avant le démarrage de ce service. Si le démarrage d'un service a échoué, le service avec des prérequis ne sera PAS démarré, mais il se souviendra qu'il devrait démarrer et réessayera au prochain cycle.

Si un service est redémarré, il arrêtera d'abord tous les services actifs qui en dépendent, et après son démarrage, il redémarrera tous les services dépendants qui étaient actifs avant le redémarrage.

Voici un exemple où nous configurons une entrée de service apache pour dépendre du binaire apache sous-jacent. Si le binaire change, une alerte est envoyée et apache n'est plus surveillé. La raison est la sécurité et que Monit ne devrait pas exécuter un binaire apache potentiellement compromis.

(1) check process apache with pidfile "/var/run/httpd.pid"
(2)    depends on httpd
(3)    ...
(4)
(5) check file httpd with path /usr/bin/httpd
(6)    if failed checksum then stop

La première entrée est l'entrée de processus pour apache. La deuxième ligne établit une dépendance entre cette entrée et l'entrée de service nommée httpd à la ligne 5. Un arbre de dépendances fonctionne comme suit : si une action est effectuée dans une branche inférieure, elle se propage vers le haut de l'arbre et pour chaque entrée dépendante, exécute la même action. Dans ce cas, si la somme de contrôle échoue à la ligne 6, une action d'arrêt est exécutée et le binaire apache n'est plus vérifié. Mais comme l'entrée du processus apache dépend de l'entrée httpd, cette entrée exécutera également l'action d'arrêt. En bref, si le test de somme de contrôle pour le fichier binaire httpd échoue, l'entrée check file httpd et l'entrée check process apache sont toutes deux arrêtées.

Un arbre de dépendances est une structure générale et peut être utilisé entre tous les types d'entrées de service et s'étendre sur plusieurs niveaux, propagant toute action prise en charge (sauf l'action exec qui ne se propagera pas vers le haut dans un arbre de dépendances pour des raisons évidentes).

Voici un autre exemple différent. Considérons la configuration de serveur courante suivante :

WEB-SERVER -> APPLICATION-SERVER -> DATABASE -> FILESYSTEM
    (a)               (b)             (c)          (d)

Vous pouvez définir des dépendances de telle sorte que le serveur web dépende du serveur d'applications pour s'exécuter avant le démarrage du serveur web, et que le serveur d'applications dépende du serveur de base de données, et que la base de données dépende du système de fichiers pour être montée avant son démarrage. Voir également la section d'exemples ci-dessous pour des exemples utilisant l'instruction depend.

Ici, nous décrivons comment Monit fonctionnera avec les dépendances ci-dessus :

Si aucun service n'est en cours d'exécution
Monit démarrera les serveurs dans l'ordre suivant : d, c, b, a
Si tous les serveurs sont en cours d'exécution
Lorsque vous exécutez 'monit stop all', voici l'ordre d'arrêt : a, b, c, d. Si vous exécutez 'Monit stop d', alors a, b et c sont également arrêtés car ils dépendent de d et finalement d est arrêté.
Si a n'est pas en cours d'exécution
Monit démarrera a
Si b n'est pas en cours d'exécution
Monit arrêtera d'abord a, puis démarrera b et enfin démarrera a si b est à nouveau opérationnel.
Si c n'est pas en cours d'exécution
Monit arrêtera d'abord a et b, puis démarrera c et enfin démarrera b puis a.
Si d n'est pas en cours d'exécution
Monit arrêtera d'abord a, b et c, puis démarrera d et enfin démarrera c, b puis a.
Si le fichier de contrôle contient une boucle de dépendance.
Une boucle de dépendance est par exemple ; a->b et b->a ou a->b->c->a.

Lorsque Monit démarre, il vérifiera ces boucles et signalera une erreur avant de quitter si une boucle est trouvée. Il quittera également avec une erreur si une instruction de dépendance a été utilisée qui ne pointe pas vers un service présent dans le fichier de contrôle.

SYNTAXE GÉNÉRALE

Monit propose plusieurs tests if que vous pouvez utiliser dans une instruction 'check' pour tester divers aspects d'un service.

Vous pouvez tester à la fois une valeur prédéfinie ou une plage, et prendre des mesures si la valeur change.

Syntaxe générale pour tester une valeur spécifique ou une plage :

IF <test> THEN <action> [ELSE <action>]

L'action est évaluée chaque fois que la condition <TEST> est vraie. L'action de succès est facultative et exécutée uniquement lorsque l'état passe de l'échec au succès. Si l'action de succès n'est pas définie, Monit enverra une alerte de récupération par défaut.

Syntaxe générale pour un test de changement de valeur :

IF CHANGED <test> THEN <action>

L'action est exécutée chaque fois que la valeur change. Monit mémorisera la nouvelle valeur et déclenchera un événement si la valeur change à nouveau.

ACTION

Chaque test peut avoir des méthodes associées alert, start, stop, restart, unmonitor ou exec que Monit peut utiliser pour exécuter des actions ou des programmes sur le service. L'action de succès prend également en charge la méthode ignore.

Syntaxe :

ALERT | IGNORE | START | STOP | R
ESTART | UNMONITOR

ou :

EXEC « programme »
[[AS] UID <nombre | chaîne>]
[[AS] GID <nombre | chaîne>]
[[WITH] TIMEOUT <nombre> SECONDE(S)]
[REPEAT EVERY [<nombre>] CYCLE(S)]

Dans chaque test, vous devez sélectionner l'action à exécuter dans cette liste :

  • ALERT envoie une alerte à l'utilisateur à chaque changement d'état.
  • RESTART redémarre le service et envoie une alerte. Le redémarrage est effectué en appelant la méthode de redémarrage enregistrée du service ou en appelant d'abord la méthode stop suivie de la méthode start si le redémarrage n'est pas défini.
  • START démarre le service en appelant la méthode de démarrage enregistrée du service et envoie une alerte.
  • STOP arrête le service en appelant la méthode d'arrêt enregistrée du service et envoie une alerte. Si Monit arrête un service, il ne sera plus vérifié par Monit ni redémarré plus tard. Pour réactiver la surveillance du service, vous devez explicitement l'activer depuis l'interface web ou depuis la console.
  • EXEC peut être utilisé pour exécuter un programme arbitraire et envoyer une alerte. Si vous choisissez cette action, vous devez spécifier le programme à exécuter et, si le programme nécessite des arguments, vous devez encapsuler le programme et ses arguments dans une chaîne de caractères entre guillemets. Vous pouvez éventuellement spécifier l'uid et le gid auxquels le programme exécuté doit passer au démarrage. Le programme n'est exécuté qu'une seule fois si le test échoue. Vous pouvez activer la répétition de l'exécution si l'erreur persiste pendant un nombre donné de cycles. Par exemple : 
    if failed <test> then exec "/usr/local/bin/sms.sh"
     as uid "nobody" and gid "nobody"
     repeat every 5 cycles

    N'oubliez pas que si Monit est exécuté par root, tous les programmes exécutés par Monit seront démarrés avec des privilèges de superutilisateur, sauf si l'extension uid et gid est utilisée.

  • UNMONITOR désactivera la surveillance du service et enverra une alerte. Le service ne sera plus vérifié par Monit ni redémarré plus tard. Pour réactiver la surveillance du service, vous devez explicitement l'activer depuis l'interface web ou depuis la console.
  • IGNORE peut être utilisé dans l'action pour ne pas générer d'alerte une fois que la vérification rentre dans l'état.

TOLÉRANCE AUX FAUTES

Par défaut, une action est exécutée si elle correspond et si le service correspondant est dans un état d'erreur. Cependant, vous pouvez exiger qu'un test échoue plus d'une fois avant que l'événement d'erreur ne soit déclenché et que l'état du service ne passe à "failed". Ceci est utile pour éviter de recevoir des alertes sur des erreurs sporadiques, qui peuvent survenir, en particulier avec les tests réseau.

Syntaxe :

FOR <X> CYCLES ...

ou :

<X> [TIMES WITHIN] <Y> CYCLES ...

La condition peut être utilisée pour les actions d'échec et de succès.

Le premier format, plus simple et recommandé, exige "X" événements consécutifs avant de changer l'état :

if failed
   port 80
   for 3 cycles
then alert

Le second format est plus avancé et permet de tolérer des problèmes intermittents, tout en détectant les problèmes excessifs, où le service oscille fréquemment entre les états d'erreur et de succès.

Par exemple, si un cycle sur deux échoue (1-0-1-0-1-0-...), la condition "for 2 cycles" ne sera jamais satisfaite, malgré les problèmes du service. L'instruction suivante détectera un tel état :

if failed
   port 80
   for 3 times within 5 cycles
then alert

Exemple qui définit plusieurs niveaux d'erreur et actions :

check filesystem rootfs with path /dev/hda1
 if space usage > 80% for 5 times within 15 cycles then alert
 if space usage > 90% for 5 cycles then exec '/try/to/free/the/space'

Note : la valeur maximale pour les cycles est de 64.

TESTS D'EXISTENCE

Ce test permet de déclencher une action en fonction de l'existence de l'objet surveillé. Il est supporté pour les services de type processus, fichier, répertoire, système de fichiers et fifo.

Si aucun test d'existence n'est défini, le test implicite de non-existence avec action de redémarrage est activé, donc par exemple, si le processus s'arrête, Monit le redémarrera.

Il existe deux types de tests d'existence :

NON-EXIST

Ce test déclenchera une action si l'objet n'existe pas. Il peut être utilisé par exemple pour s'assurer qu'apache est en cours d'exécution, que le système de fichiers de données est monté, etc.

IF [DOES] NOT EXIST THEN <action>

action est un choix parmi "ALERT", "RESTART", "START", "STOP", "EXEC" ou "UNMONITOR".

Exemple : Exécuter un script si un système de fichiers N'EXISTE PAS : 

check filesystem disk1 with path /dev/sda1
     if does not exist then exec "/sbin/mount..."

EXIST

Ce test est l'inverse du test de non-existence : il déclenchera une action si l'objet EXISTE. Il peut être utilisé par exemple pour tuer un processus qui ne devrait pas être en cours d'exécution.

IF [DOES] EXIST THEN <action>

action est un choix parmi "ALERT", "RESTART", "START", "STOP", "EXEC" ou "UNMONITOR".

Exemple : tuer un processus qui ne devrait pas s'exécuter :

check process vmware matching "vmware"
      if exist then exec "/usr/bin/pkill -9 vmware"

Exemple : Alerter si un fichier existe alors qu'il ne le devrait pas

check file x with path /some/path/x
      if exist then alert

TESTS DE RESSOURCES

Monit peut examiner la quantité de ressources qu'un service utilise. Ce test ne peut être utilisé qu'à l'intérieur d'une entrée de service système ou processus dans le fichier de configuration de Monit.

Selon les caractéristiques du système ou du processus, les services peuvent être arrêtés ou redémarrés et des alertes peuvent être générées. Il est ainsi possible d'utiliser les systèmes inactifs et d'épargner les systèmes sous forte charge.

Syntaxe :

IF <ressource> <opérateur> <valeur> THEN <action>

opérateur est un choix parmi "<", ">", "!=", "==" en notation C, "gt", "lt", "eq", "ne" en notation shell sh et "greater", "less", "equal", "notequal" sous forme lisible par l'homme (si non spécifié, la valeur par défaut est EQUAL).

valeur est soit un entier, soit un nombre réel.

action est un choix parmi "ALERT", "RESTART", "START", "STOP", "EXEC" ou "UNMONITOR".

ressource dépend du type de service :

Tests de ressources système

LOADAVG([1min|5min|15min]) [PER CORE] fait référence à la charge moyenne du système. La charge moyenne est le nombre de processus dans la file d'attente d'exécution du système par cœur de CPU, moyenné sur la période spécifiée. Exemple :

if loadavg (1min) per core > 2 for 15 cycles then alert
if loadavg (5min) per core > 1.5 for 10 cycles then alert
if loadavg (15min) per core > 1 for 8 cycles then alert

Si vous omettez l'option per core, le test vérifiera la charge moyenne totale, quel que soit le nombre de cœurs CPU.

CPU([user|system|wait|nice|hardirq|softirq|steal|guest|guestnice]) est le pourcentage de temps que le système passe dans un type de tâche donné :

user
Le CPU exécute du code en mode espace utilisateur, ce qui inclut tout processus n'appartenant pas au noyau, tel que les serveurs web, les bases de données, les shells et les programmes liés au bureau.
system
Le CPU exécute le noyau, ce qui inclut les pilotes et autres modules du noyau. Le noyau gère également les requêtes des processus en espace utilisateur, telles que l'allocation mémoire, les entrées/sorties disque et réseau, et la création de processus enfants.
wait
L'attente d'E/S se produit lorsque le CPU est inactif en attendant qu'une opération d'E/S disque ou réseau se termine.
nice
Les statistiques 'nice' comptabilisent les processus en espace utilisateur qui s'exécutent avec une priorité modifiée (plus élevée ou plus basse que la normale).
hardirq
Le noyau traite les requêtes d'interruptions matérielles. Les interruptions matérielles proviennent de périphériques tels que le clavier, les interfaces réseau, les disques, l'horloge système, etc.
softirq
Le noyau traite les requêtes d'interruptions logicielles. Les interruptions logicielles proviennent de processus en cours d'exécution dans le système.
steal
Ceci s'applique uniquement aux machines virtuelles sur un hyperviseur. Le temps volé indique le pourcentage de temps pendant lequel une machine virtuelle a dû attendre le CPU réel pendant que l'hyperviseur traitait une autre machine virtuelle. Si ce nombre reste élevé, le système hôte est trop occupé et peut nécessiter plus de CPU physiques ou le déchargement de certaines machines virtuelles sur un autre hôte.
guest
Ceci s'applique uniquement aux machines hôtes exécutant un hyperviseur. Il indique le temps passé à exécuter un CPU virtuel pour des systèmes d'exploitation invités sous le contrôle du noyau Linux. Cette valeur est déjà incluse dans les statistiques "user".
guestnice
Ceci s'applique uniquement aux machines hôtes exécutant un hyperviseur. Il indique le temps passé à exécuter un CPU virtuel pour des systèmes d'exploitation invités sous le contrôle du noyau Linux, avec une priorité modifiée. Cette valeur est déjà incluse dans les statistiques "nice".

Le modificateur user/system/wait/nice/hardirq/softirq/steal/guest/guestnice est optionnel et sa prise en charge dépend de la plateforme (la prise en charge Linux dépend de la version du noyau, toutes les statistiques sont disponibles depuis le noyau 2.6.33) :

Tests de ressources de processus

CPU est l'utilisation du CPU par le processus lui-même [%]. Monit calcule l'utilisation du CPU en fonction du nombre de threads par rapport aux cœurs CPU disponibles. Si le processus a un seul thread, une utilisation CPU de 100% équivaut à une utilisation de 100% d'un cœur CPU. S'il a 2 threads, une utilisation CPU de 100% est signalée lorsqu'il utilise 2 cœurs CPU à 100%, etc. Si le processus a plus de threads que les cœurs CPU disponibles de la machine, alors une utilisation CPU de 100% correspond à l'utilisation de tous les cœurs CPU disponibles.

si le cpu > 10% pendant 5 cycles alors redémarrer

si le cpu total > 50% pendant 10 cycles alors redémarrer

THREADS est le nombre de threads du processus. Exemple:

si le nombre de threads > 3 alors alerter

CHILDREN est le nombre de processus enfants du processus. Exemple:

si le nombre d'enfants > 10 alors alerter

si l'utilisation de la mémoire > 8 Mo alors alerter

MÉMOIRE TOTALE est l'utilisation de la mémoire par le processus et ses processus enfants, en pourcentage ou en quantité [B, kB, MB, GB]. Exemple:

TEST DE SOMME DE CONTRÔLE DE FICHIER

L'instruction checksum ne peut être utilisée que dans une entrée de service de fichier et peut être utilisée pour vérifier la somme de contrôle MD5 ou SHA1 du fichier.

Vérifier une somme de contrôle spécifique :

SI SOMME DE CONTRÔLE [MD5|SHA1] ÉCHOUE [ATTENDRE somme de contrôle] ALORS action

Vérifier toute modification de fichier :

SI SOMME DE CONTRÔLE [MD5|SHA1] CHANGÉE ALORS action

Le choix de MD5 ou SHA1 est facultatif. MD5 dispose d'une somme de contrôle de 128 bits (chaîne encodée en hexadécimal de 32 octets) et SHA1 d'une somme de contrôle de 160 bits (chaîne encodée en hexadécimal de 40 octets). Si cette option est omise, Monit essaiera de deviner la méthode à partir de la chaîne EXPECT ou utilisera MD5 comme somme de contrôle par défaut.

"expect" est facultatif et, s'il est utilisé, spécifie la chaîne md5 ou sha1 que Monit doit attendre lors du test de la somme de contrôle d'un fichier. Monit ne calculera alors pas de somme de contrôle initiale pour le fichier, mais utilisera la chaîne que vous soumettez. Par exemple :

si échoue
   somme de contrôle attendue 8f7f419955cefa0b33a2ba316cba3659
alors alerter

Vous pouvez, par exemple, utiliser l'utilitaire GNU md5sum(1) ou sha1sum(1) pour créer une chaîne de somme de contrôle pour un fichier et utiliser cette chaîne dans l'instruction expect.

Rechargement d'un serveur si son fichier de configuration a été modifié :

vérifier le fichier conf_apache avec le chemin /etc/apache/httpd.conf
    si somme de contrôle changée alors exécuter "/usr/bin/apachectl graceful"

action est un choix parmi "ALERTER", "REDÉMARRER", "DÉMARRER", "ARRÊTER", "EXÉC" ou "DÉMONITORER".

TEST D'HORODATAGE

L'instruction timestamp ne peut être utilisée que dans une entrée de service de fichier, de fifo ou de répertoire.

Syntaxe d'horodatage relatif :

SI <TEMPS D'ACCÈS | ATIME | TEMPS DE MODIFICATION | MTIME | TEMPS DE CHANGEMENT | CTIME | TIME[STAMP]> <opérateur> <valeur> [unité] ALORS <action>

Syntaxe de changement d'horodatage :

SI CHANGEMENT <TEMPS D'ACCÈS | ATIME | TEMPS DE MODIFICATION | MTIME | TEMPS DE CHANGEMENT | CTIME | TIME[STAMP]> ALORS action

Il existe quatre types de tests d'horodatage :

ACCÈS (ATIME)
Teste l'horodatage qui est mis à jour chaque fois que l'objet est accédé, par exemple lorsque le fichier est lu. Le système de fichiers permet généralement de désactiver les mises à jour d'atime à l'aide des options de montage, donc ce test ne fonctionnera que si le système de fichiers effectue des mises à jour d'atime.
CHANGEMENT (CTIME)
Teste l'horodatage qui est mis à jour chaque fois que les métadonnées de l'objet, telles que le propriétaire, le groupe, les permissions ou le nombre de liens physiques, sont modifiées.
MODIFICATION (MTIME)
Teste l'horodatage qui est mis à jour chaque fois que le contenu de l'objet est modifié. L'horodatage de modification du fichier est mis à jour chaque fois que le fichier est tronqué ou écrit. L'horodatage de modification du répertoire est mis à jour chaque fois que des fichiers/sous-répertoires sont ajoutés au répertoire ou supprimés de ce répertoire.
DÉFAUT (LE DERNIER DES HORODATAGES DE CHANGEMENT ET DE MODIFICATION)
Si aucun type d'horodatage spécifique n'est défini, le dernier des horodatages de changement et de modification est vérifié. Ce test permet un test simple de toute modification d'objet (données et métadonnées).

opérateur est un choix parmi "<", ">", "!=","==" en notation C, "GT", "LT", "EQ", "NE" en notation shell sh et "PLUS RECENT", "PLUS ANCIEN", "SUPERIEUR", "INFERIEUR", "EGAL", "DIFFERENT" sous forme lisible (si non spécifié, la valeur par défaut est ÉGAL).

valeur est un seuil de temps.

unité est soit "SECONDE(S)", "MINUTE(S)", "HEURE(S)" ou "JOUR(S)".

action est un choix parmi "ALERT", "RESTART", "START", "STOP", "EXEC" ou "UNMONITOR".

Par exemple, pour recharger apache si le fichier de configuration a changé :

check file apache_conf with path /etc/apache/httpd.conf
  if changed timestamp then exec "/usr/bin/apachectl graceful"

Par exemple, pour tester l'ajout ou la suppression de fichiers dans un répertoire :

check directory bar path /foo/bar
  if changed timestamp then alert

Exemple pour envoyer une alerte si un fichier journal n'est pas mis à jour depuis plus d'une heure :

if timestamp is older than 1 hour then alert

TEST DE TAILLE DE FICHIER

L'instruction size ne peut être utilisée que dans une entrée de service de fichier de vérification. Si elle est spécifiée dans le fichier de contrôle, Monit calculera une taille pour un fichier.

Test d'une taille ou d'une plage spécifique :

IF SIZE [[operator] value [unit]] THEN action

Test des changements de taille :

IF CHANGED SIZE THEN action

opérateur est un choix parmi "<", ">", "!=","==" en notation C, "GT", "LT", "EQ", "NE" en notation shell sh et "SUPERIEUR", "INFERIEUR", "EGAL", "DIFFERENT" sous forme lisible (si non spécifié, la valeur par défaut est ÉGAL).

valeur est un seuil de taille.

unité est un choix parmi "B","KB","MB","GB" ou les alternatives longues "byte", "kilobyte", "megabyte", "gigabyte". Si elle n'est pas spécifiée, l'unité "byte" est supposée par défaut.

action est un choix parmi "ALERT", "RESTART", "START", "STOP", "EXEC" ou "UNMONITOR".

Par exemple, pour envoyer une alerte si le fichier est trop grand :

check file mydb with path /data/mydatabase.db
      if size > 1 GB then alert

TEST DE CONTENU DE FICHIER

L'instruction content peut être utilisée pour tester incrémentalement le contenu d'un fichier texte à l'aide d'expressions régulières.

Syntaxe :

IF CONTENT <opérateur> <regex|chemin> THEN action

opérateur est soit "=" pour une correspondance, soit "!=" pour une non-correspondance.

regex est une chaîne contenant l'expression régulière étendue. Voir aussi regex(7).

chemin est un chemin absolu vers un fichier contenant une expression régulière étendue sur chaque ligne. Voir aussi regex(7).

action est un choix parmi "ALERT", "RESTART", "START", "STOP", "EXEC" ou "UNMONITOR".

Au démarrage, la position de lecture est définie à la fin du fichier et Monit continue de scanner jusqu'à la fin du fichier à chaque cycle.

Si la taille du fichier diminue ou si l'inode change, la position de lecture est définie au début du fichier.

Seules les lignes se terminant par un caractère de nouvelle ligne sont inspectées.

Par défaut, seuls les 511 premiers caractères d'une ligne sont inspectés. Vous pouvez augmenter la limite en utilisant l'instruction set limits.

IGNORE CONTENT <opérateur> <regex|chemin>

Les lignes correspondant à un IGNORE ne sont pas inspectées lors des évaluations ultérieures. IGNORE CONTENT a toujours la priorité sur IF CONTENT.

Tous les énoncés IGNORE CONTENT sont évalués en premier, dans l'ordre de leur apparition. Ensuite, tous les énoncés IF CONTENT sont évalués.

Par exemple :

check file syslog with path /var/log/syslog
      ignore content = "monit"
      if content = "^mrcoffee" then alert

TEST DES OPTIONS DE MONTAGE DU SYSTÈME DE FICHIERS

Monit peut tester les options de montage du système de fichiers pour des changements. Ce test est implicite et Monit enverra une alerte en cas d'échec par défaut.

Ce test est utile pour détecter les changements des options du système de fichiers, comme si le système de fichiers devient en lecture seule (en cas d'erreur disque) ou si les options de montage ont été modifiées (comme nosuid).

La syntaxe de l'instruction fsflags est :

TEST D'UTILISATION DE L'ESPACE

Monit peut tester l'utilisation de l'espace d'un système de fichiers ou d'un disque. Ce test ne peut être utilisé que dans le contexte d'un type de service de système de fichiers.

Les systèmes de fichiers ont généralement de l'espace réservé pour l'utilisateur root (environ 1 à 5%), de sorte que les utilisateurs non super-utilisateurs ne peuvent pas écrire sur un système de fichiers presque plein. action est un choix parmi "ALERT", "RESTART", "START", "STOP", "EXEC" ou "UNMONITOR".

check filesystem rootfs with path /
      if space usage > 90% then alert

IF FAILED PERM(ission) octalnumber THEN action

Syntaxe pour tester tout changement de permission :

IF CHANGED PERM(ission) THEN action

check file shadow with path /etc/shadow

TEST DE STATUT DE PROGRAMME

Vous pouvez vérifier le code de sortie d'un programme ou d'un script. Ce test ne peut être utilisé qu'à l'intérieur d'une entrée de service check program dans le fichier de configuration Monit.

Syntaxe pour tester une valeur de sortie spécifique:

SI STATUT opérateur valeur ALORS action

Syntaxe pour tester tout changement de valeur de sortie:

SI STATUT CHANGÉ ALORS action

opérateur est un choix parmi "<", ">", "!=", "==" en notation C, "gt", "lt", "eq", "ne" en notation shell sh et "greater", "less", "equal", "notequal" sous forme lisible (si non spécifié, la valeur par défaut est ÉGAL).

action est un choix parmi "ALERT", "RESTART", "START", "STOP", "EXEC" ou "UNMONITOR".

Exemple:

vérifier programme monsript avec chemin /usr/local/bin/monsript.sh
      si statut != 0 alors alerter

Script d'exemple pour l'exemple ci-dessus (/usr/local/bin/monsript.sh):

#!/bin/sh
echo test
exit $?

Vous pouvez également envoyer des paramètres avec le programme:

vérifier programme lister-fichiers avec chemin "/bin/ls -lrt /tmp/"
      si statut != 0 alors alerter

Les arguments du programme ou du script sont une séquence de chaînes séparées par des espaces. Dans l'exemple ci-dessus, les chaînes '-lrt' et '/tmp/' sont des arguments du programme '/bin/ls'. Si des arguments sont utilisés, il est recommandé d'utiliser des guillemets " pour englober la chaîne, sinon, si aucun argument n'est utilisé, les guillemets ne sont pas nécessaires.

Notes: Si le programme est un script, l'interpréteur est requis dans la première ligne. Le programme ou le script doit également être exécutable.

Si Monit est exécuté en tant qu'utilisateur root, vous pouvez éventuellement exécuter le programme sous un autre utilisateur et/ou groupe. Dans cet exemple, nous exécutons le programme ls sous l'utilisateur www et le groupe staff:

vérifier programme ls avec chemin "/bin/ls /tmp"
         en tant que uid "www"
         et gid "staff"
      si statut != 0 alors alerter

Monit exécutera le programme périodiquement et si le code de sortie du programme ne correspond pas au résultat attendu, Monit peut effectuer une action. Dans l'exemple ci-dessus, Monit déclenchera une alerte si la valeur de sortie est différente de 0. Par convention, 0 signifie que le programme s'est terminé normalement.

Les vérifications de programme sont asynchrones. Cela signifie que Monit n'attendra pas la fin du programme, mais exécutera le programme en arrière-plan et continuera immédiatement à vérifier l'entrée de service suivante dans monitrc. Au cycle suivant, Monit vérifiera si le programme est terminé et, le cas échéant, collectera le code de sortie du programme. Si le statut indique un échec, Monit déclenchera un message d'alerte contenant la sortie d'erreur (stderr) du programme, le cas échéant. Si le programme n'est pas sorti après le premier cycle, Monit attendra un autre cycle et ainsi de suite. Si le programme est toujours en cours d'exécution après 5 minutes, Monit le tuera et générera un événement de dépassement de délai du programme. Il est possible de remplacer le délai d'attente par défaut (voir la syntaxe ci-dessous).

Plusieurs tests de statut peuvent être utilisés, par exemple:

vérifier programme testmatériel avec chemin /usr/local/bin/testmatériel.sh
      avec timeout 500 secondes
      si statut = 1 alors alerter
      si statut = 3 pendant 5 cycles alors exécuter "/usr/local/bin/urgence.sh"

TEST DE CONTENU DE SORTIE DE PROGRAMME

L'instruction content peut être utilisée pour tester le contenu d'un programme à l'aide d'expressions régulières ou pour vérifier les modifications de la sortie.

Syntaxe:

SI CONTENU <opérateur> <regex> ALORS action
SI CONTENU [PAS] CHANGÉ ALORS action

vérifier programme route_ip avec chemin "/usr/bin/ip route"

Syntaxe du test d'envoi total :

IF TOTAL UPLOADED opérateur valeur PACKETS IN LAST nombre time-unit THEN action

Syntaxe du test de réception total :

IF TOTAL DOWNLOADED opérateur valeur PACKETS IN LAST nombre time-unit THEN action

opérateur est un choix parmi « < », « > », « != », « == » en notation c, « gt », « lt », « eq », « ne » en notation shell sh et « greater », « less », « equal », « notequal » sous forme lisible par l'homme (si non spécifié, la valeur par défaut est EQUAL).

time-unit est un choix parmi « MINUTE(S) », « HOUR(S) », « DAY ». REMARQUE : Monit ne conserve les statistiques d'envoi/réception totales que pour les dernières 24 heures. La valeur de `time-unit` ne peut donc pas s'étendre sur plus d'une journée.

action est un choix parmi « ALERT », « RESTART », « START », « STOP », « EXEC » ou « UNMONITOR ».

Exemples :

check network eth0 with interface eth0
      if upload > 1000 packets/s then alert
      if total uploaded > 900000 packets in last hour then alert

TEST DE PING RÉSEAU

Monit peut effectuer un test de ping réseau en envoyant des paquets de datagrammes ICMP Echo Request à un hôte et attendre la réponse. Ce test ne peut être utilisé qu'à l'intérieur d'une instruction `check host`. Monit doit également s'exécuter en tant qu'utilisateur root pour pouvoir effectuer le test de ping (car le test de ping doit utiliser des sockets bruts auxquels seul le super-utilisateur est généralement autorisé).

Syntaxe :

IF <FAILED|SUCCEEDED> PING[4|6]
   [COUNT nombre]
   [SIZE nombre]
   [RESPONSETIME opérateur nombre <MILLISECONDS|SECONDS>]
   [TIMEOUT nombre SECONDS]
   [ADDRESS chaîne]
THEN action

Si un nom d'hôte DNS a été utilisé dans l'instruction `check host` et que le nom d'hôte résout plusieurs adresses (IPv4 ou IPv6), Monit enverra un ping à la première adresse disponible et continuera avec l'adresse suivante jusqu'à ce qu'une connexion réussisse ou qu'il n'y ait plus d'adresses à essayer. Vous pouvez forcer Monit à ne pinger que des adresses IPv4 ou IPv6 en utilisant le mot-clé PING4 ou PING6 au lieu de PING.

Le paramètre COUNT spécifie le nombre maximum de requêtes ping consécutives qui seront envoyées à l'hôte par cycle. La valeur par défaut est 3.

Le paramètre SIZE spécifie la taille de la charge utile de la requête ping. La valeur par défaut est 64 octets, le minimum est de 8 octets, le maximum est de 1492 octets.

Le paramètre RESPONSETIME définit la limite de temps de réponse. opérateur est un choix parmi « < », « > », « != », « == » en notation c, « gt », « lt », « eq », « ne » en notation shell sh et « greater », « less », « equal », « notequal » sous forme lisible par l'homme (si non spécifié, la valeur par défaut est EQUAL).

Si aucune réponse n'arrive dans les TIMEOUT secondes, Monit signale une erreur. Si au moins une réponse a été reçue, le test de ping est considéré comme un succès.

Le paramètre ADDRESS spécifie l'adresse IP source.

Monit enverra, par défaut, jusqu'à trois paquets de requête ping par cycle pour éviter les fausses alarmes (c'est-à-dire qu'une perte de paquets allant jusqu'à 66 % est tolérée). Vous pouvez régler l'option COUNT sur une valeur comprise entre 1 et 20 pour envoyer plus ou moins de paquets. Si vous exigez un succès de ping à 100 %, réglez `count` sur 1 (c'est-à-dire qu'une seule requête sera envoyée, et si le paquet est perdu, une erreur sera signalée).

Notez que de nombreux FAI ont commencé à filtrer les paquets ping ou ICMP, auquel cas il n'y aura pas de réponse de l'hôte.

Si un test de ping est utilisé dans une entrée `check host`, ce test est exécuté en premier et si le test échoue, nous supposons que la connexion à l'hôte est interrompue et Monit ne continuera pas avec les tests de port ultérieurs.

Exemple :

check host mmonit.com with address mmonit.com
      if failed ping then alert  # IPv4 ou IPv6
check host mmonit.com with address 62.109.39.247
      if failed ping then alert # L'adresse est IPv4, donc IPv4 est privilégié

ou tester que le système est explicitement accessible via IPv4 et IPv6 :

check host mmonit.com with address mmonit.com
      if failed ping4 then alert  # IPv4 uniquement
      if failed ping6 then alert  # IPv6 uniquement

ou avec tous les paramètres ; envoyer cinq pings de 128 octets à mmonit.com et attendre jusqu'à 10 secondes pour une réponse

check host mmonit.com with address mmonit.com
      if failed ping count 5 size 128 with timeout 10 seconds then alert

Vous pouvez également surveiller un hôte censé être hors ligne :

check host offlinehost with address 192.168.100.50
      if succeeded ping then alert

TESTS DE CONNEXION

Monit peut effectuer des tests de connexion via des ports réseau ou des sockets Unix. Un test de connexion ne peut être utilisé qu'à l'intérieur d'un contexte de type de service `process` ou `host`.

Si un service écoute sur un ou plusieurs sockets, Monit peut se connecter au port (en utilisant TCP ou UDP) et vérifier que le service acceptera une connexion et qu'il est possible d'écrire et de lire à partir du socket. Si une connexion n'est pas acceptée ou s'il y a un problème avec les E/S du socket, Monit exécutera une action spécifiée.

Pour les ports TCP/UDP, Monit peut alerter en cas de connexion réussie, par exemple, lorsqu'un service comme mysql ne devrait pas être publiquement disponible.

Syntaxe du test de port TCP/UDP :

IF <FAILED|SUCCEEDED>
   [HOST chaîne]
   <PORT nombre>
   [ADDRESS chaîne]
   [IPV4 | IPV6]
   [TYPE <TCP|UDP>]
   [<SSL|TLS> [with options {...}]
   [CERTIFICATE CHECKSUM [MD5|SHA1] chaîne]
   [CERTIFICATE VALID for nombre DAYS]
   [PROTOCOL protocole | <SEND|EXPECT> "chaîne",...]
   [RESPONSETIME opérateur nombre <MILLISECONDS|SECONDS>]
   [TIMEOUT nombre SECONDS]
   [RETRY nombre]
THEN action

Syntaxe du test de socket Unix :

IF <FAILED|SUCCEEDED>
   <UNIX SOCKET chemin>
   [TYPE <TCP|UDP>]
   [PROTOCOL protocole | <SEND|EXPECT> "chaîne",...]
   [RESPONSETIME opérateur nombre <MILLISECONDS|SECONDS>]
   [TIMEOUT nombre SECONDS]
   [RETRY nombre]
THEN action

Exemples :

if failed port 80 then alert
if failed port 53 type udp protocol dns then alert
if succeeded host example.org port 3306 type tcp protocol mysql then alert
if failed unixsocket /var/run/sophie then alert

Options :

HOST chaîne. Spécifie éventuellement l'hôte auquel se connecter. Si l'hôte n'est pas donné, `localhost` est supposé si ce test est utilisé à l'intérieur d'une entrée `process`. Si ce test est utilisé à l'intérieur d'une entrée `remote host`, l'hôte distant de l'entrée est supposé.

PORT nombre. Le numéro de port auquel se connecter.

UNIX SOCKET chemin. Spécifie le chemin vers un socket Unix (machine locale uniquement).

ADDRESS chaîne. L'adresse IP source à utiliser.

IPV4 | IPV6. Spécifie éventuellement la version IP que Monit doit utiliser lors de la tentative de connexion au port. Si non utilisé, Monit tentera de se connecter à la première adresse disponible (IPv4 ou IPv6). S'il existe plusieurs adresses disponibles et que la connexion à une adresse échoue, Monit essaiera l'adresse suivante et ainsi de suite jusqu'à ce qu'une connexion réussisse ou qu'il n'y ait plus d'adresses disponibles.

TYPE [TCP | UDP]. Spécifie éventuellement le type de socket que Monit doit utiliser lors de la tentative de connexion au port. Les différents types de sockets sont : TCP ou UDP, où TCP est un socket régulier basé sur des flux, UDP, un socket de datagrammes. Le type de socket par défaut est TCP.

[SSL | TLS] [with options {...}]. Définit les options SSL/TLS et remplace les options SSL globales/par défaut. Vous pouvez définir la version SSL/TLS à utiliser, si les certificats doivent être vérifiés, si les certificats auto-signés doivent être approuvés ou définir le fichier de base de données de certificats client SSL pour l'authentification par certificat client.

CERTIFICATE CHECKSUM [MD5|SHA1] hash. Vérifie le certificat serveur SSL en vérifiant sa somme de contrôle. Vous pouvez utiliser une somme de contrôle MD5 ou SHA1 (si vous ne spécifiez pas le type, Monit déterminera le digest en fonction de la longueur du hash). Vous pouvez utiliser l'outil en ligne de commande openssl pour obtenir la valeur de la somme de contrôle de votre certificat, que vous pouvez ensuite utiliser dans le fichier de configuration de Monit :

openssl x509 -fingerprint -sha1 -in server.crt | head -1 | cut -f2 -d'='

Exemple :

if failed
    port 443
    protocol https
    and certificate checksum = "1ED948A6F4258ACAB964227EF4EB19FCC453B0F8"
then alert

Exemple :

if failed
    port 443
    protocol https
    and certificate valid > 30 days
then alert

Options de test de protocole spécifiques

GENERIC (SEND/EXPECT)

Si Monit ne prend pas en charge le protocole utilisé par le serveur, vous pouvez écrire votre propre test de protocole en utilisant les chaînes send et expect. L'instruction SEND envoie une chaîne au port du serveur et l'instruction EXPECT compare une chaîne lue depuis le serveur avec la chaîne fournie dans l'instruction expect.

Syntaxe :

[<SEND|EXPECT> "chaîne"]+

Monit enverra la chaîne telle quelle, et vous devez vous souvenir d'inclure CR et LF dans la chaîne envoyée au serveur si le protocole attend de tels caractères pour terminer une chaîne (la plupart des protocoles basés sur du texte utilisés sur Internet le font).

Monit lira par défaut jusqu'à 255 octets depuis le serveur et utilisera cette chaîne lors de la comparaison avec la chaîne EXPECT. Vous pouvez outrepasser la valeur par défaut en utilisant l'instruction set limits.

Vous pouvez utiliser des caractères non imprimables dans une chaîne SEND si nécessaire. Utilisez la notation hexadécimale, \0xHEXHEX pour envoyer n'importe quel caractère dans la plage \0x00-\0xFF, c'est-à-dire 0-255 en décimal. Par exemple, pour tester un serveur Quake 3 :

send "\0xFF\0xFF\0xFF\0xFFgetstatus"
expect "sv_floodProtect|sv_maxPing"

Si votre système prend en charge les expressions régulières POSIX, vous pouvez utiliser des expressions régulières dans la chaîne EXPECT, voir regex(7) pour en savoir plus sur les types d'expressions régulières que vous pouvez utiliser dans une chaîne expect.

Étant donné que la comparaison d'expressions régulières et de chaînes opère sur une chaîne terminée par zéro, vous ne pouvez pas tester '\0' dans un tampon EXPECT car ce caractère marque la fin du tampon. Cependant, nous échappons '\0' dans le tampon d'attente sous la forme "\0" sur laquelle vous pouvez tester. C'est-à-dire, '\' suivi de la valeur ASCII de 0. Par exemple, voici comment tester une chaîne d'attente qui commence par zéro suivi d'un nombre quelconque de caractères.

expect "^[\\]0.*"

Voici un exemple simple de protocole SMTP :

if failed
   port 25 and
   expect "^220.*"
   send   "HELO localhost.localdomain\r\n"
   expect "^250.*"
   send   "QUIT\r\n"
then alert

SEND/EXPECT peut être utilisé avec n'importe quel type de socket, tel que les sockets TCP, les sockets UNIX et les sockets UDP.

HTTP

Syntaxe :

PROTO(COL) HTTP
    [USERNAME "chaîne"]
    [PASSWORD "chaîne"]
    [REQUEST "chaîne"]
    [METHOD <GET|HEAD>]
    [STATUS opérateur nombre]
    [CHECKSUM checksum]
    [HTTP HEADERS liste d'en-têtes]
    [CONTENT < "=" | "!=" > CHAÎNE]

USERNAME est un nom d'utilisateur facultatif pour l'authentification de base.

PASSWORD est un mot de passe facultatif pour l'authentification de base.

L'option REQUEST peut définir une chaîne d'URL spécifiant un document sur le serveur HTTP. Si l'instruction request n'est pas spécifiée, la page par défaut "/" sera demandée.

Par exemple :

if failed
   port 80
   protocol http
   request "/data/show?a=b&c=d"
then restart

METHOD définit la méthode de requête HTTP. Si elle n'est pas spécifiée, Monit privilégie la méthode de requête HTTP GET, qui est plus courante que la méthode HEAD. On peut vouloir définir explicitement la méthode sur HEAD pour économiser de la bande passante réseau.

L'option STATUS peut être utilisée pour tester explicitement le code d'état HTTP renvoyé par le serveur HTTP. Si elle n'est pas utilisée, le test du protocole HTTP échouera si le code d'état renvoyé est supérieur ou égal à 400. Vous pouvez outrepasser ce comportement en utilisant le qualificateur status.

Par exemple, pour tester qu'une page n'existe pas (le serveur HTTP devrait retourner 404 dans ce cas) :

if failed
   port 80
   protocol http
   request "/non/existent.php"
   status = 404
then alert

CHECKSUM Vous pouvez tester la somme de contrôle des documents renvoyés par un serveur HTTP. Les hachages MD5 ou SHA1 peuvent être utilisés. Monit ne testera pas la somme de contrôle d'un document si le serveur ne définit pas l'en-tête HTTP Content-Length. Un serveur HTTP devrait définir cet en-tête lorsqu'il sert un document statique (c'est-à-dire un fichier). Il n'y a pas de limite à la taille du document, mais gardez à l'esprit que Monit prendra du temps pour télécharger le document sur le réseau afin de calculer la somme de contrôle.

Exemple :

if failed
   port 80
   protocol http
   request "/page.html"
   checksum 8f7f419955cefa0b33a2ba316cba3659
then alert

HTTP HEADERS peut être utilisé pour envoyer une liste d'en-têtes HTTP lors de l'utilisation du test de protocole HTTP. Par exemple, l'en-tête host. Si l'en-tête host n'est pas défini, Monit utilisera le nom d'hôte ou l'adresse IP de l'hôte tels que spécifiés dans l'instruction check host. Spécifier un en-tête host est utile si vous souhaitez vous connecter et tester un hôte virtuel basé sur le nom. La syntaxe pour définir les en-têtes HTTP est

http headers [nom:valeur, nom:valeur,..]

où chaque paire nom:valeur est séparée par ','. Si vous avez besoin d'utiliser ':' dans la chaîne de valeur, par exemple pour définir le numéro de port pour un en-tête host, vous devez entourer la valeur de guillemets. Par exemple,

http headers [Host: "mmonit.com:443"]

Dans un contexte de check host, l'utilisation de cette instruction peut ressembler à

check host mmonit.com with address mmonit.com
  if failed
     port 80 protocol http
     with http headers [Host: mmonit.com, Cache-Control: no-cache,
       Cookie: csrftoken=nj1bI3CnMCaiNv4beqo8ZaCfAQQvpgLH]
     and request /monit/ with content = "Monit [0-9.]+"
  then alert

La définition des en-têtes HTTP est associée au test de protocole HTTP et doit précéder request comme dans l'exemple ci-dessus.

L'option CONTENT définit le modèle attendu dans les données renvoyées par le serveur. Si le modèle ne correspond pas, le test échoue. Dans l'exemple ci-dessus, si le serveur ne renvoie pas une page nommée Monit suivie d'un numéro de version, le test échouera.

Par défaut, 1 Mo de contenu au maximum est inspecté. Vous pouvez augmenter cette limite en utilisant l'instruction set limits.

Par exemple :

if failed
   port 80
   protocol http
   content = "foobar [0-9.]+"
then alert

APACHE-STATUS

Le test APACHE-STATUS permet de vérifier les performances du serveur en examinant la page de statut générée par mod_status d'Apache, qui est attendue à son adresse par défaut http://www.example.com/server-status.

Syntaxe :

PROTOCOL APACHE-STATUS [PATH <chemin>] [USERNAME <chaîne>] [PASSWORD <chaîne>] [<propriété> <opérateur> <nombre>]+

PATH est un chemin facultatif vers le statut Apache ("/server-status" par défaut)

USERNAME est un nom d'utilisateur facultatif pour l'authentification de base.

PASSWORD est un mot de passe facultatif pour l'authentification de base.

propriété est l'acronyme du statut des enfants :

(1) logging (loglimit)
(2) closing connections (closelimit)
(3) performing DNS lookups (dnslimit)
(4) in keepalive with a client (keepalivelimit)
(5) replying to a client (replylimit)
(6) receiving a request (requestlimit)
(7) initialising (startlimit)
(8) waiting for incoming connections (waitlimit)
(9) gracefully closing down (gracefullimit)
(10) performing cleanup procedures (cleanuplimit)

opérateur est l'un des "<", "=", ">".

nombre est une limite numérique en pourcentage.

Chacune de ces limites peut être comparée à une valeur par rapport au nombre total de processus enfants Apache actifs.

Vous pouvez combiner tous ces tests en une seule expression ou choisir de tester une certaine limite uniquement. Si vous combinez les limites, vous devez les relier à l'aide du mot-clé OR.

Exemple :

if failed port 80 protocol apache-status
       loglimit > 10% or
       dnslimit > 50% or
       waitlimit < 20%
then alert

PROTOCOL MQTT [USERNAME chaîne PASSWORD chaîne]

USERNAME nom d'utilisateur MQTT

PASSWORD mot de passe MQTT

MYSQL

Syntaxe :

PROTOCOL MYSQL[S] [USERNAME chaîne PASSWORD chaîne [RSAKEY CHECKSUM chaîne]]

USERNAME nom d'utilisateur MySQL.

PASSWORD mot de passe MySQL (les caractères spéciaux peuvent être utilisés, mais pour les caractères non alphanumériques, le mot de passe doit être mis entre guillemets).

Monit vérifiera l'empreinte de la clé avant d'envoyer le mot de passe au serveur.

Le nom d'utilisateur et le mot de passe (identifiants) sont optionnels et s'ils ne sont pas définis, Monit effectuera le test en utilisant une connexion anonyme. Cela peut entraîner une erreur d'authentification dans votre journal MySQL, en fonction de votre configuration MySQL.

Si des identifiants sont définis, Monit tentera de se connecter. Monit ne nécessite aucun privilège de base de données, il a juste besoin de l'utilisateur de la base de données. Vous voudrez peut-être créer un utilisateur autonome que Monit utilisera lors des tests, par exemple :

CREATE USER 'monit'@'host_from_which_monit_performs_testing' IDENTIFIED BY 'mysecretpassword';
FLUSH PRIVILEGES;

check process mysql with pidfile /var/run/mysqld/mysqld.pid
    start program = "/sbin/start mysql"
    stop program = "/sbin/stop mysql"
    if failed
       port 3306
       protocol mysql username "foo" password "bar"
    then alert

ou avec des commandes start/stop via socket unix

check p
rocess mysql avec pidfile /var/run/mysqld/mysqld.pid
    start program = "/usr/local/mysql/support-files/mysql.server start"
    stop program = "/usr/local/mysql/support-files/mysql.server stop"
    if failed
       unixsocket /tmp/mysql.sock
       protocol mysql username "foo" password "bar"

if failed

SIP

Le protocole SIP est utilisé par les serveurs de plateformes de communication tels qu'Asterisk et FreeSWITCH.

Syntaxe :

PROTOCOL SIP [TARGET valid@uri] [MAXFORWARD n]

TARGET vous pouvez spécifier un destinataire alternatif pour le message, en ajoutant un URI sip valide après ce mot-clé.

MAXFORWARD Limite le nombre de proxys ou de passerelles qui peuvent transmettre la requête au serveur suivant. Sa valeur est un entier dans la plage 0-255, définie par défaut à 70. Si max-forward = 0, le serveur suivant peut répondre 200 OK (test réussi) ou envoyer un 483 Too Many Hops (test échoué)

Par exemple :

check host openser_all with address 127.0.0.1
  if failed
     port 5060 type udp protocol sip
     with target "localhost:5060" and maxforward 6
  then alert

Syntaxe :

PROTOCOL SMTP[S] [USERNAME string PASSWORD string]

USERNAME Nom d'utilisateur SMTP.

PASSWORD Mot de passe SMTP (des caractères spéciaux peuvent être utilisés, mais pour les caractères non alphanumériques, le mot de passe doit être entre guillemets).

Les identifiants sont optionnels et lorsqu'ils sont utilisés, ils effectuent l'authentification pendant les tests, vous permettant ainsi de tester également le fonctionnement de l'authentification. Nous recommandons d'utiliser smtps si l'authentification doit être utilisée pour chiffrer la communication. Si aucun identifiant n'est défini, Monit effectuera simplement un test de protocole de base.

Exemple :

check process postfix with pidfile /var/spool/postfix/pid/master.pid
    start program = "/etc/init.d/postfix start"
    stop  program = "/etc/init.d/postfix stop"
    if failed
       port 25
       protocol smtp
    then alert

Exemple utilisant l'authentification et STARTTLS/SMTPS :

check process postfix with pidfile /var/spool/postfix/pid/master.pid
    start program = "/etc/init.d/postfix start"
    stop  program = "/etc/init.d/postfix stop"
    if failed
       port 25
       protocol smtps
       username "foo"
       password "bar"
    then alert

WEBSOCKET

Syntaxe :

PROTOCOL WEBSOCKET
        [REQUEST string]
        [HOST string]
        [ORIGIN string]
        [VERSION number]

HOST vous pouvez spécifier un en-tête Host alternatif

REQUEST vous pouvez spécifier une requête alternative, le défaut est "/"

ORIGIN vous pouvez spécifier une origine alternative, le défaut est "https://mmonit.com"

VERSION vous pouvez spécifier une version alternative, le défaut est "0"

Par exemple :

check host websocket.org with address "echo.websocket.org"
      if failed
         port 80 protocol websocket
         host "echo.websocket.org"
         request "/"
         origin 'http://websocket.com'
         version 13
      then alert

GEREZ VOS INSTANCES MONIT

M/Monit https://mmonit.com étend les capacités de Monit et fournit la surveillance et la gestion de tous vos hôtes activés pour Monit.

M/Monit utilise Monit comme agent. À intervalles réguliers, Monit envoie un message d'état à M/Monit avec un instantané de l'hôte sur lequel il s'exécute.

M/Monit présente les données collectées sous forme de graphiques et de journaux d'événements et vous donne la possibilité de visualiser les données clés de performance de tous vos hôtes dans une interface utilisateur moderne, épurée et bien conçue, qui fonctionne également sur les appareils mobiles.

Depuis M/Monit, vous pouvez également démarrer, arrêter et redémarrer les services sur vos hôtes exécutant Monit.

Pour envoyer des données à M/Monit, ajoutez l'instruction suivante à votre fichier de contrôle Monit :

SET MMONIT <url>
      [TIMEOUT <number> SECONDS]
      [REGISTER WITHOUT CREDENTIALS]
      [[WITH] HOSTGROUPS '[' "name", ... ']' ]

Exemple :

set mmonit https://monit:monit@192.168.1.10:8443/collector

Monit s'enregistrera dans M/Monit et commencera à envoyer des messages d'état et d'événements à M/Monit. Nous recommandons d'utiliser https comme dans l'exemple ci-dessus pour garantir que la communication entre Monit et M/Monit est sécurisée.

Le mot de passe doit être encodé en URL s'il contient des caractères significatifs pour l'URL tels que ":", "?", "@".

Le délai d'attente par défaut est de 5 secondes, vous pouvez personnaliser le délai d'attente en utilisant l'option TIMEOUT.

Lorsque Monit s'enregistre dans M/Monit, il envoie des identifiants qui peuvent être utilisés pour effectuer des actions sur les services depuis M/Monit. Vous pouvez désactiver l'envoi des identifiants en utilisant REGISTER WITHOUT CREDENTIALS et ajouter manuellement les identifiants dans M/Monit à la place.

Vous pouvez éventuellement ajouter Monit à un ou plusieurs groupes d'hôtes M/Monit. Si le groupe d'hôtes n'existe pas, il sera créé automatiquement. Exemple :

set mmonit
    https://monit:monit@192.168.1.10:8443/collector
    with hostgroups [ Oslo, "Mail servers" ]

EXEMPLES DE CONFIGURATION

La forme la plus simple est juste l'instruction check. Dans cet exemple, nous vérifions si notre serveur web est en cours d'exécution et lèverons une alerte s'il ne l'est pas :

check process nginx with pidfile /var/run/nginx.pid

Pour que Monit démarre le serveur s'il n'est pas en cours d'exécution, ajoutez une instruction start :

check process nginx with pidfile /var/run/nginx.pid
      start program = "/etc/init.d/nginx start"

Voici un exemple plus avancé pour surveiller un serveur web Apache qui écoute sur le port par défaut pour HTTP et HTTPS. Dans cet exemple, Monit redémarrera Apache s'il n'accepte pas les connexions sur les ports. La méthode utilisée par Monit pour le redémarrage consiste à d'abord exécuter le programme stop, puis à attendre (jusqu'à 30 secondes) que le processus s'arrête, puis à exécuter le programme start et à attendre (30 secondes) qu'il démarre. La durée de l'attente de démarrage ou d'arrêt peut être remplacée en utilisant l'option 'timeout'. Si Monit n'a pas réussi à arrêter ou à démarrer le service, un message d'alerte d'échec sera envoyé si vous avez demandé l'envoi de messages d'alerte.

check process apache with pidfile /var/run/httpd.pid
      start program = "/etc/init.d/httpd start" with timeout 60 seconds
      stop program  = "/etc/init.d/httpd stop"
      if failed port 80 for 2 cycles then restart
      if failed port 443 for 2 cycles then restart

Cet exemple démontre comment vous pouvez exécuter un programme en tant qu'utilisateur spécifié (uid) et avec un groupe spécifié (gid). De nombreux programmes démons peuvent effectuer le changement d'uid et gid eux-mêmes, mais pour les programmes qui ne le font pas (par exemple, les programmes Java), la capacité de Monit à démarrer un programme en tant que certain utilisateur peut être très utile. Dans cet exemple, nous démarrons le moteur de Servlet Java Tomcat en tant qu'utilisateur et groupe nobody standard. Veuillez noter que Monit ne peut changer l'uid et le gid pour le programme que si le super-utilisateur exécute Monit, sinon Monit ignorera simplement la demande de changement d'uid et de gid.

check process tomcat with pidfile /var/run/tomcat.pid
      start program = "/etc/init.d/tomcat start"
            as uid "nobody" and gid "nobody"
      stop program  = "/etc/init.d/tomcat stop"
            # Vous pouvez également utiliser des numéros d'identifiant et écrire :
            as uid 99 and with gid 99
      if failed port 8080 then alert

Dans cet exemple, nous utilisons udp pour le test de connexion afin de vérifier si le serveur de noms est en cours d'exécution :

check process named with pidfile /var/run/named.pid
      start program = "/etc/init.d/named start"
      stop program  = "/etc/init.d/named stop"
      if failed port 53 use type udp protocol dns then restart

L'exemple suivant illustre comment vérifier si le service 'sophie' répond aux connexions sur son socket de domaine Unix :

check process sophie with pidfile /var/run/sophie.pid
      start program = "/etc/init.d/sophie start"
      stop  program = "/etc/init.d/sophie stop"
      if failed unix /var/run/sophie then restart

SIGNALS

If a Monit daemon is running, SIGUSR1 wakes it up from its sleep phase and forces a poll of all services. SIGTERM and SIGINT will gracefully terminate a Monit daemon. The SIGTERM signal is sent to a Monit daemon if Monit is started with the quit action argument.

Sending a SIGHUP signal to a running Monit daemon will force the daemon to reinitialise itself, specifically it will reread configuration, close and reopen log files.

Running Monit in foreground while a background Monit daemon is running will wake up the daemon.

NOTES

This is a very silent program. Use the -v switch if you want to see what Monit is doing, and tail -f the log file. Optionally for testing purposes; you can start Monit with the -Iv switch. Monit will then print debug information to the console, to stop monit in this mode, simply press CTRL^C (i.e. SIGINT) in the same console.
