MOUNT.CIFS, MOUNT.SMB3(8) Manuel de l'administrateur système MOUNT.CIFS, MOUNT.SMB3(8)

NOM

mount.cifs, mount.smb3 - monter en utilisant Common Internet File System (CIFS)

SYNTAXE

mount.cifs {service} {point-de-montage} [-o options]

Cet outil fait partie de la suite cifs-utils.

mount.cifs monte un système de fichiers CIFS ou SMB3 depuis Linux. Il est généralement appelé indirectement par la commande mount(8) lorsqu'on utilise l'option "-t cifs". Cette commande ne fonctionne que sous Linux, et le noyau doit prendre en charge le système de fichiers cifs. Le protocole SMB3 est le successeur du protocole CIFS (SMB) et est pris en charge par la plupart des serveurs Windows, Azure (stockage cloud), Mac et de nombreux autres serveurs commerciaux et appliances de stockage en réseau (NAS), ainsi que par Samba, le populaire serveur Open Source.

mount.smb3 monte uniquement le système de fichiers SMB3. Il est généralement appelé indirectement par la commande mount(8) lorsqu'on utilise l'option "-t smb3". Le type de système de fichiers smb3 a été ajouté dans le noyau 4.18 et versions ultérieures. Il fonctionne de manière similaire à mount.cifs, sauf qu'il transmet le type de système de fichiers comme smb3.

L'utilitaire mount.cifs attache le nom UNC (ressource réseau exportée) spécifié comme service (en utilisant la syntaxe //serveur/partage, où "serveur" est le nom du serveur ou son adresse IP et "partage" est le nom du partage) au répertoire local point-de-montage.

Les options de mount.cifs sont spécifiées sous forme de liste séparée par des virgules de paires clé=valeur. Il est possible de passer d'autres options que celles listées ici, à condition que le module du noyau du système de fichiers cifs (cifs.ko) les prenne en charge. Les options de montage cifs non reconnues passées au code du noyau vfs cifs seront enregistrées dans le journal du noyau.

mount.cifs lance un thread nommé cifsd via le vfs cifs. Après le montage, il reste actif jusqu'à ce que la ressource montée soit démontée (généralement via l'utilitaire umount).

La commande mount.cifs -V affiche la version de l'utilitaire de montage cifs.

La commande modinfo cifs affiche la version du module cifs.

OPTIONS

username=arg|user=arg
spécifie le nom d'utilisateur à utiliser pour la connexion. Si ce n'est pas donné, la variable d'environnement USER est utilisée.

Les versions antérieures de mount.cifs permettaient également de spécifier le nom d'utilisateur sous la forme user%motdepasse ou groupe_travail/utilisateur ou groupe_travail/utilisateur%motdepasse pour permettre la spécification du mot de passe et du groupe de travail dans le nom d'utilisateur. La prise en charge de ces formats alternatifs de nom d'utilisateur est maintenant dépréciée et ne devrait plus être utilisée. Les utilisateurs doivent utiliser les options distinctes password= et domain= pour spécifier ces valeurs. Bien que certaines versions du module noyau cifs acceptent user= comme abréviation pour cette option, son utilisation peut induire en erreur le programme mount standard en lui faisant croire qu'il s'agit d'un montage non superutilisateur. Il est donc recommandé d'utiliser le nom d'option complet username=.

password=arg|pass=arg
spécifie le mot de passe CIFS. Si cette option n'est pas donnée, la variable d'environnement PASSWD est utilisée. Si le mot de passe n'est pas spécifié directement ou indirectement via un argument à mount, mount.cifs demandera un mot de passe, sauf si l'option guest est spécifiée.

Notez qu'un mot de passe contenant le caractère délimiteur (c'est-à-dire une virgule ',') ne sera pas analysé correctement sur la ligne de commande. Cependant, le même mot de passe défini dans la variable d'environnement PASSWD ou via un fichier d'identification ou saisi à l'invite du mot de passe sera lu correctement.

password2=arg|pass2=arg
spécifie un mot de passe alternatif pour aider à la rotation des mots de passe. Si cette option n'est pas donnée, la variable d'environnement PASSWD2 est utilisée. Si password2 n'est pas spécifié directement ou indirectement via un argument à mount, mount.cifs ne demandera PAS password2.

Notez qu'un mot de passe2 contenant le caractère délimiteur (c'est-à-dire une virgule ',') ne sera pas analysé correctement sur la ligne de commande. Cependant, le même mot de passe2 défini dans la variable d'environnement PASSWD2 ou via un fichier d'identification (voir ci-dessous) sera lu correctement.

credentials=filename|cred=filename
spécifie un fichier contenant un nom d'utilisateur et/ou un mot de passe et éventuellement un mot de passe alternatif et/ou le nom du groupe de travail. Le format du fichier est :
username=valeur
password=valeur
password2=valeur
domain=valeur

Ceci est préférable à avoir des mots de passe en clair dans un fichier partagé, comme /etc/fstab. Assurez-vous de protéger correctement tout fichier d'identification.

uid=arg
définit l'uid qui sera propriétaire de tous les fichiers ou répertoires sur le système de fichiers monté lorsque le serveur ne fournit pas d'informations de propriété. Il peut être spécifié sous forme de nom d'utilisateur ou d'uid numérique. Lorsqu'il n'est pas spécifié, la valeur par défaut est uid 0. L'utilitaire mount.cifs doit être de la version 1.10 ou supérieure pour prendre en charge la spécification de l'uid sous forme non numérique. Voir la section sur la PROPRIÉTÉ ET LES PERMISSIONS DES FICHIERS ET RÉPERTOIRES ci-dessous pour plus d'informations.
forceuid
indique au client d'ignorer tout uid fourni par le serveur pour les fichiers et répertoires et d'assigner toujours le propriétaire à la valeur de l'option uid=. Voir la section sur la PROPRIÉTÉ ET LES PERMISSIONS DES FICHIERS ET RÉPERTOIRES ci-dessous pour plus d'informations.
cruid=arg
définit l'uid du propriétaire du cache d'identification. Ceci est principalement utile avec sec=krb5. La valeur par défaut est l'uid réel du processus effectuant le montage. La définition de ce paramètre dirige l'appel externe pour rechercher un cache d'identification appartenant à cet utilisateur.
gid=arg
définit le gid qui sera propriétaire de tous les fichiers ou répertoires sur le système de fichiers monté lorsque le serveur ne fournit pas d'informations de propriété. Il peut être spécifié sous forme de nom de groupe ou de gid numérique. Lorsqu'il n'est pas spécifié, la valeur par défaut est gid 0. L'utilitaire mount.cifs doit être de la version 1.10 ou supérieure pour prendre en charge la spécification du gid sous forme non numérique. Voir la section sur la PROPRIÉTÉ ET LES PERMISSIONS DES FICHIERS ET RÉPERTOIRES ci-dessous pour plus d'informations.
forcegid
indique au client d'ignorer tout gid fourni par le serveur pour les fichiers et répertoires et d'assigner toujours le propriétaire à la valeur de l'option gid=. Voir la section sur la PROPRIÉTÉ ET LES PERMISSIONS DES FICHIERS ET RÉPERTOIRES ci-dessous pour plus d'informations.
idsfromsid
Extrait uid/gid d'un SID spécial au lieu de le mapper. Voir la section sur la PROPRIÉTÉ ET LES PERMISSIONS DES FICHIERS ET RÉPERTOIRES ci-dessous pour plus d'informations.
port=arg
définit le numéro de port sur lequel le client tentera de contacter le serveur CIFS. Si cette valeur est spécifiée, recherche une connexion existante avec ce port, et l'utilise si elle existe. Si elle n'existe pas, essaie de créer une nouvelle connexion sur ce port. Si cette connexion échoue, renvoie une erreur. Si cette valeur n'est pas spécifiée, recherche une connexion existante sur le port 445 ou 139. Si aucune connexion de ce type n'existe, essaie de se connecter d'abord sur le port 445 puis sur le port 139 si cela échoue. Renvoie une erreur si les deux échouent.
netbiosname=arg
Lors du montage vers des serveurs via le port 139, spécifie le nom source RFC1001 à utiliser pour représenter la machine NetBIOS cliente pendant l'initialisation de la session NetBIOS.
servern=arg
Similaire à netbiosname sauf qu'il spécifie le nom NetBIOS du serveur au lieu du client. Bien que rarement nécessaire pour le montage vers des serveurs plus récents, cette option est nécessaire pour le montage vers certains serveurs plus anciens (comme OS/2 ou Windows 98 et Windows ME) car lors de la connexion sur le port 139, ils, contrairement à la plupart des serveurs plus récents, ne prennent pas en charge un nom de serveur par défaut. Un nom de serveur peut comporter jusqu'à 15 caractères et est généralement en majuscules.

file_mode=arg
Si le serveur ne prend pas en charge les extensions Unix CIFS, cela remplace le mode de fichier par défaut.
dir_mode=arg
Si le serveur ne prend pas en charge les extensions Unix CIFS, cela remplace le mode par défaut pour les répertoires.
ip=arg|addr=arg
définit l'adresse IP de destination. Cette option est définie automatiquement si la partie nom du serveur de la requête UNC peut être résolue, elle a donc rarement besoin d'être spécifiée par l'utilisateur.
domain=arg|dom=arg|workgroup=arg
Définit le domaine (groupe de travail) de l'utilisateur. Si aucun domaine n'est donné, le domaine vide sera utilisé. Utilisez domainauto pour deviner automatiquement le domaine du serveur auquel vous vous connectez.
domainauto
Lors de l'utilisation de l'authentification NTLM et sans fournir de domaine via domain, devinez le domaine à partir du défi NTLM du serveur. Ce comportement était le comportement par défaut sur les noyaux plus anciens que 2.6.36.
guest
ne pas demander de mot de passe.
iocharset
Jeu de caractères utilisé pour convertir les noms de chemins locaux en et à partir d'Unicode. Unicode est utilisé par défaut pour les noms de chemins réseau si le serveur le prend en charge. Si iocharset n'est pas spécifié, alors le nls_default spécifié lors de la compilation du noyau client local sera utilisé. Si le serveur ne prend pas en charge Unicode, ce paramètre est inutilisé.
ro
monter en lecture seule.
rw
monter en lecture-écriture.
setuids
Si les extensions Unix CIFS sont négociées avec le serveur, le client tentera de définir l'uid et le gid effectifs du processus local sur les nouveaux fichiers, répertoires et périphériques créés (create, mkdir, mknod). Si les extensions Unix CIFS ne sont pas négociées, au lieu d'utiliser l'uid et le gid par défaut spécifiés lors du montage, les uid et gid du nouveau fichier seront mis en cache localement, ce qui signifie que l'uid du fichier peut changer lorsque l'inode est rechargé (ou que l'utilisateur remonte le partage).
nosetuids
Le client ne tentera pas de définir l'uid et le gid sur les nouveaux fichiers, répertoires et périphériques créés (create, mkdir, mknod), ce qui aura pour conséquence que le serveur définira l'uid et le gid par défaut (généralement l'uid serveur de l'utilisateur qui a monté le partage). Laisser le serveur (plutôt que le client) définir l'uid et le gid est le comportement par défaut. Si les extensions Unix CIFS ne sont pas négociées, alors l'uid et le gid des nouveaux fichiers apparaîtront comme l'uid (gid) de celui qui a monté ou l'uid (gid) spécifié lors du montage.
perm
Le client effectue des vérifications de permissions (vérification vfs_permission de l'uid et du gid du fichier par rapport au mode et à l'opération désirée), à noter que cela s'ajoute à la vérification ACL normale sur la machine cible effectuée par le logiciel serveur. La vérification des permissions côté client est activée par défaut.
noperm
Le client n'effectue pas de vérifications de permissions. Cela peut exposer les fichiers sur ce montage à l'accès par d'autres utilisateurs sur le système client local. C'est généralement uniquement nécessaire lorsque le serveur prend en charge les extensions Unix CIFS mais que les UIDs/GIDs sur le client et le serveur ne correspondent pas assez étroitement pour permettre l'accès par l'utilisateur qui effectue le montage. Il est à noter que cela n'affecte pas la vérification ACL normale sur la machine cible effectuée par le logiciel serveur (l'ACL serveur par rapport au nom d'utilisateur fourni lors du montage).
dynperm
Demande au serveur de maintenir en mémoire la propriété et les permissions qui ne peuvent pas être stockées sur le serveur. Ces informations peuvent disparaître à tout moment (dès que l'inode est vidé du cache), donc bien que cela puisse aider certaines applications à fonctionner, son comportement est plutôt peu fiable. Voir la section ci-dessous sur LA PROPRIÉTÉ ET LES PERMISSIONS DES FICHIERS ET RÉPERTOIRES pour plus d'informations.
cache=arg
Mode de cache. Voir la section ci-dessous sur LA COHÉRENCE DU CACHE pour plus de détails. Les valeurs autorisées sont :
  • none - ne pas mettre en cache les données de fichiers du tout
  • strict - suivre strictement le protocole CIFS/SMB2
  • loose - autoriser des sémantiques de mise en cache souples

Le comportement par défaut dans les noyaux antérieurs au 3.7 était loose. À partir du noyau 3.7, le comportement par défaut est strict.

nostrictsync
Ne pas demander au serveur de vider sur fsync(). Certains serveurs effectuent des écritures non mises en mémoire tampon par défaut, auquel cas le vidage est redondant. Dans les charges de travail où un client effectue de nombreuses petites opérations d'écriture + fsync combinées et où la latence réseau est beaucoup plus élevée que la latence serveur, cela apporte une amélioration de performance de 2x. Cette option est également un bon candidat dans les scénarios où nous privilégions la performance à la cohérence.
handlecache
(par défaut) Dans SMB2 et supérieur, le client doit souvent ouvrir la racine du partage (chemin vide) à divers endroits lors du montage, de la revalidation de chemin et de l'appel système statfs(2). Cette option réduit le trafic aller-retour redondant (ouvertures et fermetures) en conservant simplement la poignée du répertoire pour la racine une fois ouverte.
nohandlecache
Désactiver la mise en cache de la poignée du répertoire racine du partage.
max_cached_dirs=arg
Le nombre maximum de répertoires mis en cache par partage. Les répertoires sont mis en cache localement lorsqu'un bail est accordé par le serveur, ce qui améliore les performances en réduisant le trafic réseau.

Par défaut, max_cached_dirs est défini sur 16 et peut prendre des valeurs comprises entre 0 et une valeur maximale de 2^32 - 1.

handletimeout=arg
Le temps (en millisecondes) pendant lequel le serveur doit réserver la poignée après un basculement en attendant la reconnexion du client. Lors du montage avec l'option de montage resilienthandles ou persistenthandles, ou lorsque leur utilisation est demandée par le serveur (partages à disponibilité continue), ce paramètre remplace le délai d'attente de poignée par défaut du serveur (qui pour la plupart des serveurs est de 120 secondes).
rwpidforward
Transmet le pid d'un processus qui a ouvert un fichier à toute opération de lecture ou d'écriture sur ce fichier. Cela empêche les applications comme wine(1) d'échouer en lecture et écriture si nous utilisons le style de verrou mandataire (brlock).
mapchars
Traduit six des sept caractères réservés (pas le backslash, mais incluant le deux-points, le point d'interrogation, le pipe, l'astérisque, le supérieur à et le inférieur à) vers la plage de remappage (au-dessus de 0xF000), ce qui permet également au client CIFS de reconnaître les fichiers créés avec de tels caractères par les Services pour Mac de Windows. Ceci peut également être utile lors du montage sur la plupart des versions de Samba (qui interdisent également la création et l'ouverture de fichiers dont les noms contiennent l'un de ces sept caractères). Cela n'a aucun effet si le serveur ne prend pas en charge Unicode sur le réseau. Veuillez noter que les fichiers créés avec l'option de montage mapchars peuvent ne pas être accessibles si le partage est monté sans cette option.
nomapchars
(par défaut) Ne traduit aucun de ces sept caractères.
mapposix
Traduit les caractères réservés de manière similaire à mapchars mais utilise le mappage de Microsoft "Services For Unix".
intr
actuellement non implémenté.
nointr
(par défaut) actuellement non implémenté.
hard
Le programme accédant à un fichier sur le système de fichiers monté cifs restera bloqué lorsque le serveur plantera.
soft
(par défaut) Le programme accédant à un fichier sur le système de fichiers monté cifs ne restera pas bloqué lorsque le serveur plantera et retournera des erreurs à l'application utilisateur.
noacl
Ne pas autoriser les opérations ACL POSIX même si le serveur les supporterait.

Le client CIFS peut obtenir et définir les ACL POSIX (getfacl, setfacl) sur les serveurs Samba version 3.0.10 et ultérieures. La définition des ACL POSIX nécessite l'activation de CONFIG_CIFS_XATTR puis de CONFIG_CIFS_POSIX dans les options de configuration CIFS lors de la compilation du module cifs. Le support des ACL POSIX peut être désactivé par montage en spécifiant noacl lors du montage.

cifsacl
Cette option est utilisée pour mapper les ACL CIFS/NTFS vers/depuis les bits de permissions Linux, mapper les SIDs vers/depuis les UIDs et GIDs, et obtenir et définir les descripteurs de sécurité.

Voir la section sur les ACL CIFS/NTFS, le MAPPAGE SID/UID/GID, les DESCRIPTEURS DE SÉCURITÉ pour plus d'informations.

backupuid=arg
L'accès aux fichiers par cet utilisateur doit être effectué avec le drapeau d'intention de sauvegarde défini. Un nom ou un identifiant doit être fourni en argument, il n'y a pas de valeurs par défaut.

Voir la section ACCÈS AUX FICHIERS AVEC INTENTION DE SAUVEGARDE pour plus de détails.

backupgid=arg
L'accès aux fichiers par les utilisateurs membres de ce groupe doit être effectué avec le drapeau d'intention de sauvegarde défini. Un nom ou un identifiant doit être fourni en argument, il n'y a pas de valeurs par défaut.

Voir la section ACCÈS AUX FICHIERS AVEC INTENTION DE SAUVEGARDE pour plus de détails.

nocase
Demander une correspondance de nom de chemin insensible à la casse (la casse sensible est le comportement par défaut si le serveur le prend en charge).
ignorecase
Synonyme de nocase.
sec=arg
Mode de sécurité. Les valeurs autorisées sont :
  • none - tenter de se connecter en tant qu'utilisateur null (sans nom)
  • krb5 - Utiliser l'authentification Kerberos version 5
  • krb5i - Utilise l'authentification Kerberos et active de force la signature des paquets
  • ntlm - Utilise le hachage de mot de passe NTLM
  • ntlmi - Utilise le hachage de mot de passe NTLM et force la signature des paquets
  • ntlmv2 - Utilise le hachage de mot de passe NTLMv2
  • ntlmv2i - Utilise le hachage de mot de passe NTLMv2 et force la signature des paquets
  • ntlmssp - Utilise le hachage de mot de passe NTLMv2 encapsulé dans un message NTLMSSP brut
  • ntlmsspi - Utilise le hachage de mot de passe NTLMv2 encapsulé dans un message NTLMSSP brut, et force la signature des paquets

La valeur par défaut dans les versions du noyau principal avant la v3.8 était sec=ntlm. Dans la v3.8, la valeur par défaut a été changée en sec=ntlmssp.

Si le serveur requiert une signature lors de la négociation du protocole, elle peut être activée automatiquement. La signature des paquets peut également être activée automatiquement si elle est activée dans /proc/fs/cifs/SecurityFlags.

seal
Demande le chiffrement au niveau SMB. L'algorithme de chiffrement utilisé est AES-128-CCM. Nécessite SMB3 ou supérieur (voir vers).
esize=arg
La taille minimale (en octets) d'une réponse de lecture chiffrée à laquelle le client délègue le déchiffrement à un thread de travail distinct. Ceci fonctionne lorsque le nombre de requêtes en cours est supérieur à 1.

Le déchiffrement des réponses de lecture chiffrées volumineuses peut être coûteux en calcul et, lorsque plusieurs lectures sont en cours, déléguer le travail peut améliorer les performances.

La valeur par défaut est esize=0, ce qui signifie que toutes les réponses de lecture chiffrées sont déchiffrées sans délégation et peuvent être définies jusqu'à la taille maximale du tampon, qui peut varier de 8192 à 130048 octets, et est par défaut de 16384 octets.

rdma
Se connecte directement au serveur en utilisant SMB Direct via un adaptateur RDMA. Nécessite SMB3 ou supérieur (voir vers).
resilienthandles
Active les descripteurs résilients. Si le serveur le prend en charge, conserve les fichiers ouverts lors des reconnexions. Nécessite SMB2.1 (voir vers).
noresilienthandles
(par défaut) Désactive les descripteurs résilients.
persistenthandles
Active les descripteurs persistants. Si le serveur le prend en charge, conserve les fichiers ouverts lors des reconnexions. Les descripteurs persistants sont également valides entre les serveurs d'un cluster et ont des garanties plus solides que les descripteurs résilients. Nécessite SMB3 ou supérieur (voir vers).
nopersistenthandles
(par défaut) Désactive les descripteurs persistants.
snapshot=time
Monte un instantané spécifique du partage distant. time doit être un entier positif identifiant l'instantané demandé (en unités de 100 nanosecondes écoulées depuis le 1er janvier 1601, ou alternativement, il peut être spécifié au format GMT, par exemple @GMT-2019.03.27-20.52.19). Pris en charge dans le noyau Linux à partir de la v4.19.
nobrl
N'envoie pas de requêtes de verrouillage de plage d'octets au serveur. Ceci est nécessaire pour certaines applications qui ne fonctionnent pas avec les verrouillages obligatoires de plage d'octets de type cifs (et la plupart des serveurs cifs ne prennent pas encore en charge la demande de verrouillages de plage d'octets consultatifs).
forcemandatorylock
N'utilise pas les verrous POSIX même lorsqu'ils sont disponibles via les extensions Unix. Utilise toujours les verrous obligatoires de type cifs.
locallease
Vérifie les baux locaux en cache localement au lieu d'interroger le serveur.
nolease
Ne demande pas de bail/oplock lors de l'ouverture d'un fichier sur le serveur. Ceci désactive la mise en cache locale des opérations d'E/S, de plage d'octets et de lecture de métadonnées (voir actimeo pour plus d'informations sur la mise en cache des métadonnées). Nécessite SMB2 et supérieur (voir vers).
sfu
Lorsque les extensions Unix CIFS ou SMB3 ne sont pas négociées, tente de créer des fichiers de périphériques et des FIFOs dans un format compatible avec Services for Unix (SFU). De plus, récupère les bits 10-12 du mode via l'attribut étendu SETFILEBITS (comme le fait SFU). À l'avenir, les 9 bits inférieurs du mode seront également émulés en interrogeant le descripteur de sécurité (ACL). [NB : nécessite la version 1.39 ou ultérieure du module VFS CIFS. Pour reconnaître les liens symboliques et pouvoir créer des liens symboliques dans un format interopérable SFU, nécessite la version 1.40 ou ultérieure du module noyau VFS CIFS.
mfsymlinks
Active la prise en charge des liens symboliques Minshall+French (voir
http://wiki.samba.org/index.php/UNIX_Extensions#Minshall.2BFrench_symlinks ). Cette option est ignorée lorsqu'elle est spécifiée avec l'option sfu. Les liens symboliques Minshall+French sont utilisés même si le serveur prend en charge les extensions Unix CIFS.
echo_interval=n
définit l'intervalle auquel les requêtes echo sont envoyées au serveur sur une connexion inactive. Ce réglage affecte également le temps nécessaire pour qu'une connexion à un serveur non réactif expire. Ici, n est l'intervalle d'écho en secondes. La reconnexion se produit au double de la valeur de l'echo_interval définie pour un serveur non réactif. Si cette option n'est pas fournie, la valeur par défaut de 60 secondes est utilisée. La valeur minimale réglable est de 1 seconde et la valeur maximale peut aller jusqu'à 600 secondes.
serverino
Utilise les numéros d'inode (identifiants de fichier persistants uniques) renvoyés par le serveur au lieu de générer automatiquement des numéros d'inode temporaires sur le client. Bien que les numéros d'inode du serveur facilitent la détection des fichiers liés en dur (car ils auront les mêmes numéros d'inode) et que les numéros d'inode puissent être persistants (ce qui est utile pour certains logiciels), le serveur ne garantit pas que les numéros d'inode soient uniques si plusieurs montages côté serveur sont exportés sous un partage unique de niveau supérieur (car les numéros d'inode sur les serveurs peuvent ne pas être uniques si plusieurs systèmes de fichiers sont montés sous le même répertoire de niveau supérieur partagé). Notez que tous les serveurs ne prennent pas en charge le renvoi des numéros d'inode du serveur, bien que ceux qui prennent en charge les extensions Unix CIFS, et les serveurs Windows 2000 et plus récents le prennent généralement en charge (bien que pas nécessairement sur chaque système de fichiers serveur local). Le paramètre n'a aucun effet si le serveur ne prend pas en charge le renvoi de numéros d'inode ou équivalent. Ce comportement est activé par défaut.
noserverino
Le client génère lui-même les numéros d'inode au lieu d'utiliser ceux du serveur.

Voir la section NUMÉROS D'INODE pour plus d'informations.

(par défaut) Active les extensions Unix pour ce montage. Nécessite CIFS (vers=1.0) ou SMB3.1.1 (vers=3.1.1) et un serveur les prenant en charge.

Désactive les extensions Unix pour ce montage. Ceci peut être utile pour désactiver plusieurs paramètres à la fois. Cela inclut les ACL POSIX, les verrous POSIX, les chemins POSIX, la prise en charge des liens symboliques et la récupération des uid/gid/mode depuis le serveur. Ceci peut également être utile pour contourner un bug dans un serveur qui prend en charge les extensions Unix.

Voir la section NUMÉROS D'INODE pour plus d'informations.

Ne suit pas les renvois du système de fichiers distribué (DFS). Les E/S sur un fichier non stocké sur le serveur échoueront au lieu de se connecter transparencement au serveur cible.
noautotune
Utilise une taille fixe pour les tampons de socket de réception/envoi du noyau.

N'essaie pas de réutiliser les sockets si le système est déjà connecté au serveur via un point de montage existant. Cela forcera le client à toujours établir une nouvelle connexion au serveur, quelle que soit la connexion déjà établie. Ceci peut être utile pour simuler plusieurs clients se connectant au même serveur, car chaque point de montage utilisera un socket TCP différent.
noblocksend
Envoie des données sur le socket en utilisant des opérations non bloquantes (indicateur MSG_DONTWAIT).
rsize=bytes
Quantité maximale de données que le noyau demandera dans une requête de lecture en octets. La taille maximale acceptée par les serveurs est typiquement de 8 Mo pour les dialectes SMB3 ou ultérieurs. La valeur par défaut demandée lors du montage est de 4 Mo. Avant le noyau 4.20, la valeur par défaut demandée était de 1 Mo. Avant le dialecte SMB2.1, la taille maximale était généralement de 64 Ko.
wsize=bytes
Quantité maximale de données que le noyau enverra dans une requête d'écriture en octets. La taille maximale acceptée par les serveurs est typiquement de 8 Mo pour les dialectes SMB3 ou ultérieurs. La valeur par défaut demandée lors du montage est de 4 Mo. Avant le noyau 4.20, la valeur par défaut demandée était de 1 Mo. Avant le dialecte SMB2.1, la taille maximale était généralement de 64 Ko.

Remplace la taille de bloc par défaut (1 Mo) signalée sur les fichiers SMB3 (nécessite le noyau version 5.1 ou ultérieure). Avant la version 5.1 du noyau, la taille de bloc était toujours signalée comme 16 Ko au lieu de 1 Mo (et n'était pas configurable), ce qui pouvait nuire aux performances d'outils comme cp et scp (en particulier pour les E/S non mises en cache) qui décident de la taille de lecture et d'écriture à utiliser pour les copies de fichiers en fonction de la taille de bloc de l'inode. bsize ne peut pas être inférieur à 16 Ko ni supérieur à 16 Mo.

Crédits maximum que le client SMB2 peut avoir. Par défaut, 32000. Doit être défini sur un nombre compris entre 20 et 60000.

Cette option pourrait être utile pour améliorer les performances sur une liaison lente, un serveur fortement chargé et/ou un réseau où la lecture depuis le disque est plus rapide que la lecture depuis le serveur (via le réseau). multiuser
Mappe les accès des utilisateurs à des informations d'identification individuelles lors de l'accès au serveur. Par défaut, les points de montage CIFS n'utilisent qu'un seul ensemble d'informations d'identification d'utilisateur (les informations d'identification du montage) lors de l'accès à un partage. Avec cette option, le client crée plutôt une nouvelle session avec le serveur en utilisant les informations d'identification de l'utilisateur chaque fois qu'un nouvel utilisateur accède au point de montage. Les accès ultérieurs par cet utilisateur utiliseront également ces informations d'identification. Étant donné que le noyau ne peut pas demander de mots de passe, les montages multi-utilisateurs sont limités aux montages utilisant les options sec= qui ne nécessitent pas de mots de passe.

Avec cette modification, il est possible pour le serveur de gérer l'application des autorisations, de sorte que cette option implique également noperm. De plus, lorsque les extensions Unix ne sont pas utilisées et que l'administrateur n'a pas outrepassé la propriété en utilisant les options uid= ou gid=, la propriété des fichiers est présentée comme l'utilisateur actuel accédant au partage.

actimeo=arg
Le temps (en secondes) pendant lequel le client CIFS met en cache les attributs d'un fichier ou d'un répertoire avant de demander des informations d'attributs à un serveur. Pendant cette période, les modifications qui se produisent sur le serveur restent indétectées jusqu'à ce que le client vérifie à nouveau le serveur.

Par défaut, le délai d'expiration du cache d'attributs est réglé sur 1 seconde. Cela signifie des appels plus fréquents sur le réseau au serveur pour vérifier si les attributs ont changé, ce qui pourrait affecter les performances. Avec cette option, les utilisateurs peuvent faire un compromis entre les performances et la correction des métadonnées du cache, en fonction des besoins de la charge de travail. Des délais d'expiration plus courts signifient une meilleure cohérence du cache, mais un nombre croissant d'appels fréquents au serveur. Des délais d'expiration plus longs signifient un nombre réduit d'appels au serveur mais une cohérence de cache plus lâche. La valeur actimeo est un entier positif qui peut contenir des valeurs comprises entre 0 et une valeur maximale de 2^30 * HZ (fréquence de l'interruption du minuteur). La définir à 0 désactive la mise en cache.

acregmax=arg
Le temps maximum (en secondes) pendant lequel le client CIFS met en cache les attributs d'un fichier régulier avant de demander des informations d'attributs fraîches à un serveur. Si cette option n'est pas spécifiée, alors la valeur acregmax sera définie sur la valeur actimeo, voir actimeo pour plus de détails.
acdirmax=arg
Le temps maximum (en secondes) pendant lequel le client CIFS met en cache les attributs d'un répertoire avant de demander des informations d'attributs fraîches à un serveur. Si cette option n'est pas spécifiée, alors la valeur acdirmax sera définie sur la valeur actimeo, voir actimeo pour plus de détails.
upcall_target=arg
Détermine l'espace de noms dans lequel les appels ascendants du système de fichiers SMB doivent être traités. Les valeurs autorisées sont : - mount - Résoudre les appels ascendants dans l'espace de noms de l'hôte. - app - Résoudre les appels ascendants dans l'espace de noms du thread appelant (application). La valeur par défaut est app. Cette option est utile dans des environnements comme Kubernetes, où le montage peut être effectué par un pod pilote au nom d'une application s'exécutant dans un conteneur séparé. Elle garantit que les informations d'identification Kerberos et d'autres données spécifiques à l'utilisateur sont accessibles dans l'espace de noms correct. En spécifiant app, les appels ascendants peuvent être résolus dans l'espace de noms de l'application, garantissant l'utilisation des informations d'identification correctes. mount permet la résolution dans l'espace de noms de l'hôte, ce qui peut être nécessaire lorsque les informations d'identification ou les configurations sont gérées en dehors du conteneur.
multichannel
Cette option active la fonctionnalité multichannel. Multichannel est une fonctionnalité du protocole SMB3 qui permet au client d'établir plusieurs connexions de transport vers un serveur SMB et de les lier en une seule session SMB authentifiée. Cette fonctionnalité améliore la tolérance aux pannes et augmente le débit en répartissant le trafic sur plusieurs connexions. Avec cette option de montage, la valeur par défaut est d'utiliser deux canaux si le serveur prend en charge le multichannel. Le paramètre max_channels peut être spécifié si vous souhaitez utiliser plus de deux canaux.
max_channels=arg
Cette option est applicable lors de l'utilisation de la fonctionnalité multichannel. L'option max_channels permet à l'utilisateur de spécifier le nombre de connexions de transport qui doivent être établies entre le client et le serveur, jusqu'à une limite de 16. L'utilisation de cette option active implicitement la fonctionnalité multichannel. Si l'option max_channels n'est pas spécifiée, la fonctionnalité multichannel utilise par défaut 2 connexions.
closetimeo=arg
Le temps maximum (en secondes) pendant lequel le client CIFS diffère l'envoi de la fermeture SMB3 finale lorsque le client détient un bail sur le fichier.

Par défaut, closetimeo est réglé sur 1 seconde et peut contenir des valeurs comprises entre 0 et une valeur maximale de 2^30 * HZ.

FORMATAGE ET DÉLIMITEURS DE SERVICE

Il est généralement préférable d'utiliser des barres obliques (/) comme délimiteur dans les noms de services. Elles sont considérées comme le "délimiteur universel" car elles ne sont généralement pas autorisées à être intégrées dans les composants de chemin sur les machines Windows et le client peut les convertir inconditionnellement en barres obliques inverses (\). Inversement, les caractères de barre oblique inverse sont autorisés par POSIX à faire partie d'un composant de chemin, et ne peuvent pas être automatiquement convertis de la même manière.

mount.cifs tentera de convertir les barres obliques inverses en barres obliques lorsque cela est possible, mais ne pourra pas le faire dans les composants de chemin qui suivent le nom du partage.

NUMÉROS D'INODE

Lorsque les extensions Unix sont activées, nous utilisons le numéro d'inode réel fourni par le serveur en réponse aux appels POSIX comme numéro d'inode.

Lorsque les extensions Unix sont désactivées et que l'option de montage serverino est activée, il n'y a aucun moyen d'obtenir le numéro d'inode du serveur. Le client mappe généralement le UniqueID attribué par le serveur sur un numéro d'inode.

Notez que le UniqueID est une valeur différente du numéro d'inode du serveur. La valeur UniqueID est unique sur l'ensemble du serveur et est souvent supérieure à 2 puissance 32. Cette valeur fait souvent que les programmes qui ne sont pas compilés avec LFS (Large File Support) déclenchent une erreur glibc EOVERFLOW car elle ne rentre pas dans le champ de la structure cible. Il est fortement recommandé de compiler vos programmes avec le support LFS (c'est-à-dire avec -D_FILE_OFFSET_BITS=64) pour éviter ce problème. Vous pouvez également utiliser l'option de montage noserverino pour générer des numéros d'inode inférieurs à 2 puissance 32 sur le client. Mais vous pourriez ne pas être en mesure de détecter correctement les liens matériels.

COHÉRENCE DU CACHE

Avec un système de fichiers réseau comme CIFS ou NFS, le client doit faire face au fait que l'activité d'autres clients ou du serveur pourrait modifier le contenu ou les attributs d'un fichier.

Mise en cache

Le protocole CIFS est conçu pour le partage de fichiers et il est souvent nécessaire pour le client de mettre en cache des données de fichiers localement pour améliorer les performances. Cependant, le fait de mettre en cache des données localement crée un problème de cohérence si le fichier est modifié sur le serveur par un autre client ou par le serveur lui-même, sans que le client en soit conscient. Une façon de traiter un tel problème est d'exiger que tous les accès aux fichiers se fassent directement sur le serveur. Cependant, cela est prohibitif en termes de performances, donc la plupart des protocoles ont un mécanisme pour permettre au client de mettre en cache des données localement.

Le protocole CIFS impose (en effet) que le client ne mette pas en cache les données de fichiers à moins qu'il ne détienne un verrouillage opportuniste (opportunistic lock, aka oplock) ou un bail (lease). Ces deux entités permettent au client de garantir certains types d'accès exclusif à un fichier afin qu'il puisse accéder à son contenu sans avoir besoin d'interagir continuellement avec le serveur. Le serveur rappellera le client lorsqu'il aura besoin de révoquer l'un d'eux et accordera au client un certain temps pour vider toute donnée mise en cache.

Le client CIFS utilise le cache de pages (pagecache) du noyau pour mettre en cache les données de fichiers. Toute E/S effectuée via le cache de pages est généralement alignée sur les pages. Cela peut poser problème lorsqu'il est combiné avec des verrous par plage d'octets (byte-range locks), car le verrouillage de Windows est obligatoire et peut bloquer les lectures et les écritures.

cache=none signifie que le client n'utilise jamais le cache pour les lectures et écritures normales. Il accède toujours directement au serveur pour satisfaire une demande de lecture ou d'écriture.

cache=strict signifie que le client tentera de suivre strictement le protocole CIFS/SMB2. C'est-à-dire que le cache n'est fiable que lorsque le client détient un oplock. Lorsque le client ne détient pas d'oplock, il contourne le cache et accède directement au serveur pour satisfaire une demande de lecture ou d'écriture. Ce faisant, le client évite les problèmes avec les verrous par plage d'octets. De plus, les verrous par plage d'octets sont mis en cache côté client lorsqu'il détient un oplock et sont « poussés » vers le serveur lorsque cet oplock est rappelé.

cache=loose permet au client d'utiliser des sémantiques de protocole plus souples, ce qui peut parfois offrir de meilleures performances au détriment de la cohérence du cache. L'accès aux fichiers implique toujours le cache de pages. Lorsqu'un oplock ou un bail n'est pas détenu, le client tentera de vider le cache peu de temps après une écriture dans un fichier. Notez que cette vidange ne se produit pas nécessairement avant que l'appel système d'écriture ne retourne.

Dans le cas d'une lecture sans détenir d'oplock, le client tentera de vérifier périodiquement les attributs du fichier afin de déterminer s'il a changé et si le cache pourrait ne plus être valide. Ce mécanisme ressemble à celui utilisé par NFSv2/v3 pour la cohérence du cache, mais il est particulièrement problématique avec CIFS. Windows est assez « paresseux » en ce qui concerne la mise à jour du champ LastWriteTime que le client utilise pour vérifier cela. L'effet est que cache=loose peut entraîner une corruption des données lorsque plusieurs lecteurs et écrivains travaillent sur les mêmes fichiers.

Pour cette raison, lorsque plusieurs clients accèdent au même ensemble de fichiers, cache=strict est recommandé. Cela permet d'éliminer les problèmes de cohérence du cache en suivant plus strictement les protocoles CIFS/SMB2.

Notez également que quel que soit le modèle de mise en cache utilisé, le client utilisera toujours le cache de pages pour gérer les fichiers mmap'és. Les écritures dans les fichiers mmap'és ne sont garanties d'être vidées sur le serveur que lorsque msync() est appelé, ou à la fermeture().

La valeur par défaut dans les noyaux antérieurs à 3.7 était loose. À partir de 3.7, la valeur par défaut est strict.

CIFS/NTFS ACL, MAPPAGE SID/UID/GID, DESCRIPTEURS DE SÉCURITÉ

Cette option est utilisée pour travailler avec des objets de fichier qui possèdent des descripteurs de sécurité et des ACL CIFS/NTFS au lieu d'un modèle d'authentification utilisateur basé sur UID, GID, bits de permission de fichier et ACL POSIX. C'est le modèle d'authentification le plus courant pour les serveurs CIFS et c'est celui utilisé par Windows.

La prise en charge de ceci nécessite que le module du noyau cifs soit compilé avec les options CONFIG_CIFS_XATTR et CONFIG_CIFS_ACL activées. Depuis Linux 5.3, l'option CONFIG_CIFS_ACL n'existe plus car la prise en charge des ACL CIFS/NTFS est toujours intégrée au module du noyau cifs.

La plupart des noyaux de distribution auront déjà ces options activées par défaut, mais vous pouvez toujours vérifier si elles sont activées avec :

cat /lib/modules/$(uname -r)/build/.config

Alternativement, si le noyau est configuré avec CONFIG_IKCONFIG_PROC :

zcat /proc/config.gz

Une ACL CIFS/NTFS est mappée aux bits de permission de fichier à l'aide d'un algorithme spécifié dans le document Microsoft TechNet suivant :


http://technet.microsoft.com/en-us/library/bb463216.aspx

Pour mapper les SID aux UID et GID, et vice versa, les éléments suivants sont requis :

  • un appel système (upcall) vers l'utilitaire cifs.idmap configuré via request-key.conf(5)
  • la prise en charge de winbind ou sssd configurée via nsswitch.conf(5)

Veuillez vous référer aux pages de manuel respectives de cifs.idmap(8), winbindd(8) et sssd(8) pour plus d'informations.

Les descripteurs de sécurité d'un objet de fichier peuvent être récupérés et définis directement à l'aide de l'attribut étendu nommé system.cifs_acl. Les descripteurs de sécurité présentés via cette interface sont des « blobs » de données « bruts » et nécessitent un utilitaire en espace utilisateur pour soit les analyser et les formater, soit les assembler, tels que getcifsacl(1) et setcifsacl(1) respectivement.

Voici quelques points à considérer lors de l'utilisation de cette option de montage :

  • Il peut y avoir une latence accrue lors du traitement des métadonnées en raison des requêtes supplémentaires pour obtenir et définir les descripteurs de sécurité.
  • Le mappage entre une ACL CIFS/NTFS et les bits de permission de fichier POSIX est imparfait et certaines informations d'ACL peuvent être perdues lors de la traduction.
  • Si l'appel système vers cifs.idmap n'est pas correctement configuré ou si winbind ou sssd n'est pas configuré et en cours d'exécution, le mappage des ID échouera. Dans ce cas, uid et gid seront par défaut soit ceux du partage, soit les valeurs des options de montage uid et/ou gid si elles sont spécifiées.

ACCÈS AUX FICHIERS AVEC INTENTION DE SAUVEGARDE

Pour un utilisateur sur le serveur, l'accès souhaité à un fichier est déterminé par les permissions et les droits associés à ce fichier. Ceci est généralement accompli en utilisant la propriété et les ACL. Pour un utilisateur qui n'a pas les droits d'accès à un fichier, il est toujours possible d'accéder à ce fichier pour un objectif spécifique ou ciblé en lui accordant des droits spéciaux. L'un des objectifs spécifiques est d'accéder à un fichier avec l'intention de sauvegarder ou de restaurer, c'est-à-dire une intention de sauvegarde. Le droit d'accéder à un fichier avec l'intention de sauvegarde peut généralement être accordé en faisant partie du groupe intégré *Opérateurs de sauvegarde*. Ainsi, lorsque cet utilisateur tente d'ouvrir un fichier avec l'intention de sauvegarde, la requête d'ouverture est envoyée en définissant le bit FILE_OPEN_FOR_BACKUP_INTENT comme l'une des CreateOptions.

Par exemple, sur un serveur Windows, un utilisateur nommé *testuser*, ne peut pas ouvrir ce fichier avec un descripteur de sécurité tel que :

REVISION:0x1
CONTROL:0x9404
OWNER:Administrator
GROUP:Domain Users
ACL:Administrator:ALLOWED/0x0/FULL

Mais l'utilisateur *testuser*, s'il fait partie du groupe *Opérateurs de sauvegarde*, peut ouvrir le fichier avec l'intention de sauvegarde.

Tout utilisateur côté client qui peut s'authentifier en tant qu'un tel utilisateur sur le serveur peut accéder aux fichiers avec l'intention de sauvegarde. Mais il est souhaitable et préférable pour des raisons de sécurité, entre autres, de restreindre ce droit spécial.

L'option de montage backupuid est utilisée pour restreindre ce droit spécial à un utilisateur spécifié par un nom ou un ID. L'option de montage backupgid est utilisée pour restreindre ce droit spécial aux utilisateurs d'un groupe spécifié par un nom ou un ID. Seuls les utilisateurs correspondant à backupuid ou backupgid tenteront d'accéder aux fichiers avec l'intention de sauvegarde. Ces deux options de montage peuvent être utilisées conjointement.

PROPRIÉTÉ ET PERMISSIONS DES FICHIERS ET DES RÉPERTOIRES

Le protocole CIFS de base ne fournit pas d'informations sur la propriété Unix ni de mode pour les fichiers et répertoires. Pour cette raison, les fichiers et répertoires apparaîtront généralement comme appartenant aux valeurs définies par les options uid= ou gid=, et auront des permissions définies sur les valeurs par défaut file_mode et dir_mode pour le montage. Tenter de modifier ces valeurs via chmod/chown retournera succès mais n'aura aucun effet.

Lorsque le client et le serveur négocient les extensions Unix, les fichiers et répertoires se verront attribuer l'UID, le GID et le mode fournis par le serveur. Étant donné que les montages CIFS sont généralement à usage unique, et que les mêmes identifiants sont utilisés quel que soit l'utilisateur qui accède au montage, les nouveaux fichiers et répertoires auront généralement une propriété correspondant aux identifiants utilisés pour monter le partage.

Si les UID et GID utilisés ne correspondent pas sur le client et le serveur, les options forceuid et forcegid peuvent être utiles. Notez cependant qu'il n'existe pas d'option correspondante pour remplacer le mode. Les permissions attribuées à un fichier lorsque forceuid ou forcegid sont effectives peuvent ne pas refléter les permissions réelles.

Lorsque les extensions Unix ne sont pas négociées, il est également possible de les émuler localement sur le serveur en utilisant l'option de montage dynperm. Lorsque cette option de montage est en vigueur, les nouveaux fichiers et répertoires recevront ce qui semble être des permissions correctes. Ces permissions ne sont cependant pas stockées sur le serveur et peuvent disparaître à tout moment dans le futur (sujet aux caprices du noyau qui vide le cache d'inodes). En général, cette option de montage est déconseillée.

Il est également possible de contourner complètement la vérification des permissions sur le client via l'option noperm. Les vérifications de permissions côté serveur ne peuvent pas être contournées. Les vérifications de permissions effectuées par le serveur correspondront toujours aux identifiants utilisés pour monter le partage, et pas nécessairement à l'utilisateur qui accède au partage.

VARIABLES D'ENVIRONNEMENT

La variable USER peut contenir le nom d'utilisateur de la personne à utiliser pour s'authentifier auprès du serveur. La variable peut être utilisée pour définir à la fois le nom d'utilisateur et le mot de passe en utilisant le format username%password.

Les variables PASSWD et PASSWD2 peuvent contenir le mot de passe et le mot de passe alternatif de la personne utilisant le client, respectivement.

Les variables PASSWD_FILE et PASSWD2_FILE peuvent contenir le chemin d'accès au fichier à partir duquel lire le mot de passe ou le mot de passe2, respectivement. Une seule ligne d'entrée est lue et utilisée comme

NOTES

Cette commande ne peut être utilisée que par root, sauf si elle est installée setuid, auquel cas les options de montage noexec et nosuid sont activées. Lorsqu'elle est installée en tant que programme setuid, le programme suit les conventions établies par le programme mount pour les montages utilisateur, avec la restriction supplémentaire que les utilisateurs doivent pouvoir changer de répertoire (chdir()) dans le point de montage avant le montage afin de pouvoir monter dessus.

Certains outils clients samba comme smbclient(8) respectent les paramètres de configuration côté client présents dans smb.conf. Contrairement à ces outils clients, mount.cifs ignore complètement smb.conf.

CONFIGURATION

Le mécanisme principal pour apporter des modifications de configuration et pour lire les informations de débogage pour le vfs cifs est via le système de fichiers /proc de Linux. Dans le répertoire /proc/fs/cifs se trouvent divers fichiers de configuration et fichiers pseudo qui peuvent afficher des informations de débogage et des statistiques de performance. Il existe des options de démarrage supplémentaires telles que la taille maximale du tampon et le nombre de tampons qui ne peuvent être définies que lorsque le module vfs cifs du noyau (module cifs.ko) est chargé. Celles-ci peuvent être vues en exécutant l'utilitaire modinfo sur le fichier cifs.ko, qui listera les options qui peuvent être passées à cifs lors de l'installation du module (chargement du pilote de périphérique). Pour plus d'informations, consultez le fichier du noyau fs/cifs/README. Lors de la configuration du traçage dynamique (trace-cmd), notez que la liste des événements SMB3 qui peuvent être activés peut être vue à l'adresse : /sys/kernel/debug/tracing/events/cifs/.

SÉCURITÉ

L'utilisation de SMB2.1 ou ultérieur (y compris le dernier dialecte SMB3.1.1) est recommandée pour une sécurité améliorée et SMB1 n'est plus demandé par défaut au moment du montage. Les anciens dialectes tels que CIFS (SMB1, c'est-à-dire vers=1.0) ont une sécurité beaucoup plus faible. L'utilisation de CIFS (SMB1) peut être désactivée en utilisant modprobe cifs disable_legacy_dialects=y.

BOGUES

Le montage utilisant la spécification d'URL CIFS n'est actuellement pas pris en charge.

Le fichier credentials ne gère pas les noms d'utilisateur ou les mots de passe avec un espace en début de chaîne.

Notez que la réponse typique à un rapport de bug est une suggestion d'essayer d'abord la dernière version. Veuillez donc essayer de le faire d'abord, et incluez toujours les versions que vous utilisez des logiciels pertinents lors du signalement de bugs (minimum : mount.cifs (essayez mount.cifs -V), noyau (voir /proc/version) et type de serveur que vous essayez de contacter).
