monodocer(1) Manuel des commandes générales monodocer(1)

NOM

monodocer - Support du format de documentation ECMA

SYNTAXE

monodocer [OPTIONS]*

OPTIONS

-assembly:ASSEMBLY
ASSEMBLY est un assemblage .NET pour lequel générer des squelettes de documentation.

Spécifiez un chemin de fichier ou le nom d'un assemblage GAC.

-delete
Permet à monodocer de supprimer des membres des fichiers de documentation. Les seuls membres supprimés sont ceux qui ne sont plus présents dans l'assemblage.

Si un type n'est plus présent, le fichier de documentation n'est *pas* supprimé, mais est plutôt renommé avec une extension .remove.

-?, -help
Afficher les informations sur les arguments du programme.
-ignoremembers
Ne pas mettre à jour les membres.

Cela ajoutera des squelettes de documentation pour les types ajoutés, mais n'*ajoutera* ou ne *supprimera* aucune documentation pour les membres d'un type quelconque (y compris les types ajoutés).

-importslashdoc:FILE
FILE est un fichier XML généré avec l'indicateur du compilateur C# /doc:FILE (par exemple, mcs -doc:foo.xml foo.cs). Importe la documentation des membres contenue dans FILE dans le format de documentation utilisé par monodoc.
-name:NAME
NAME est le nom du projet pour lequel cette documentation est destinée.

Cela définit l'élément /Overview/Title dans le fichier index.xml créé dans le répertoire spécifié par -path. Ceci est utilisé par certains programmes pour les informations de titre (par exemple, monodocs2html).

-namespace:NAMESPACE
Mettre à jour uniquement les types dans l'espace de noms NAMESPACE.
-overrides
Inclure les méthodes surchargées dans la documentation.

Ce n'est normalement pas nécessaire, car le Navigateur de Documentation Mono fournira un lien vers les membres du type de base de toute façon, tout comme monodocs2html si le type de base est dans le même assemblage.

-path:OUTPUT_DIR
OUTPUT_DIR est le répertoire qui contiendra les squelettes de documentation nouveaux/mis à jour.
-pretty
Indente proprement les fichiers XML.
-since:SINCE
Crée un élément <since/> pour les types et membres ajoutés avec la valeur SINCE.

Par exemple, si l'on donne -since:"Gtk# 2.4", un élément sera inséré dans l'élément Docs pour tous les types et membres de type ajoutés :

<since version="Gtk# 2.4" />
Le Navigateur de Documentation Mono et monodocs2html utiliseront cet élément pour spécifier dans quelle version un membre a été ajouté.
-type:TYPE
Créer/mettre à jour la documentation uniquement pour le type TYPE.
-updateto:PATH
Lors de la mise à jour de la documentation, écrire les fichiers de documentation mis à jour dans le répertoire PATH.
-V, -version
Afficher la version et les informations de licence.

DESCRIPTION

monodocer a été rendu obsolète par mdoc(1). Voir la page de manuel de mdoc-update(1).

monodocer est un programme qui crée des squelettes de documentation XML au format ECMA. Il ne repose pas sur la documentation trouvée dans le code source.

Les avantages sont :

*
Lisibilité du code. Une bonne documentation est souvent (a) verbeuse, et (b) remplie d'exemples. (À titre de comparaison, comparez la documentation du Framework .NET de Microsoft, qui est souvent une page ou plus de documentation pour chaque membre, à la documentation JavaDoc, qui peut souvent être une phrase pour chaque membre.)

Insérer une bonne documentation dans le code source peut souvent gonfler le fichier source, car la documentation peut être plus longue que la méthode réelle qui est documentée.

*
Localisation. Les formats de documentation dans le code source (comme /doc) n'ont aucun support pour plusieurs langues humaines. Si vous devez prendre en charge plus d'une langue humaine à des fins de documentation, monodocer est utile car il permet à chaque langue d'avoir son propre répertoire, et monodocer peut ajouter des types/membres pour chaque répertoire de documentation séparé.
*
Administration. Il n'est pas rare d'avoir des équipes de documentation et de développement distinctes. Il est également possible que l'équipe de documentation ait une expérience minimale avec le langage de programmation utilisé. Dans de telles circonstances, la documentation intégrée n'est pas souhaitable car l'équipe de documentation pourrait inadvertamment insérer une erreur dans le code source lors de la mise à jour de la documentation. Alternativement, vous pourriez ne pas vouloir que l'équipe de documentation ait accès au code source pour des raisons de sécurité. monodocer permet à la documentation d'être conservée de manière *totalement* séparée et distincte du code source utilisé pour créer l'assemblage.

Pour transformer la documentation monodocer en quelque chose qui peut être consommé par le Navigateur de Documentation Mono (le navigateur d'aide de bureau, ou son interface web), il est nécessaire de compiler la documentation dans un format compressé. Ceci est fait avec l'outil mdassembler, par exemple, vous pourriez utiliser cette chaîne d'outils comme ceci :

$ monodocer -assembly:MyWidgets -path:generated_docs
$ mdassembler --ecma generated_docs -out:MyWidgets
Ce qui précède générerait un MyWidgets.zip et un MyWidgets.tree qui pourraient ensuite être installés dans le système. En plus des deux fichiers (.zip et .tree), vous devez fournir un fichier .sources qui décrit où dans le système d'aide la documentation doit être connectée. C'est un fichier XML très simple, comme ceci : 
<?xml version="1.0"?>
<monodoc>
  <source provider="ecma" basefile="MyWidgets" path="classlib-gnome"/>
</monodoc>
Le fichier de configuration ci-dessus décrit que la documentation est au format ECMA (la version compilée), que le nom de fichier de base est MyWidgets et qu'elle doit être connectée dans la partie "classlib-gnome" de l'arbre. Si vous souhaitez examiner les différents nœuds définis dans la documentation, vous pouvez consulter le fichier monodoc.xml qui est généralement installé dans /usr/lib/monodoc/monodoc.xml.

Une fois que vous avez tous vos fichiers (.zip, .tree et .sources), vous pouvez les installer dans le système avec la commande suivante :

        $ cp MyWidgets.tree MyWidgets.zip MyWidgets.source `pkg-config monodoc --variable sourcesdir`
Ce qui précède copiera les fichiers dans le répertoire que Monodoc a enregistré (vous pourriez avoir besoin des permissions root pour ce faire). Le répertoire réel est retourné par l'invocation pkg-config.

FORMAT ID CHAÎNE

Les ID de chaînes sont utilisés pour faire référence à un type ou à un membre d'un type. Les ID de chaînes sont documentés dans ECMA-334 3ème Édition, Annexe E.3.1. Ils se composent d'un préfixe de type de membre, du nom complet du type (espace de noms + nom, séparés par '.'), éventuellement suivi du nom du membre et d'autres informations.

Préfixes de type de membre :

E:
L'ID de chaîne fait référence à un événement. Le nom de l'événement suit le nom du type : E:System.AppDomain.AssemblyLoad
F:
L'ID de chaîne fait référence à un champ. Le nom du champ suit le nom du type : F:System.Runtime.InteropServices.DllImportAttribute.SetLastError
M:
Fait référence à un constructeur ou une méthode. Les constructeurs ajoutent .ctor au nom du type, tandis que les méthodes ajoutent le nom de la méthode (avec un nombre optionnel de paramètres génériques).

Si le constructeur ou la méthode prend des arguments, ceux-ci sont listés entre parenthèses après le nom du constructeur/méthode :

M:System.Object..ctor , M:System.String..ctor(Syste

FORMAT DES IDENTIFIANTS DE CHAÎNE

Les identifiants de chaîne sont utilisés pour désigner les types et les membres dans la documentation. Ils sont de la forme suivante :

E:
Fait référence à un événement, par exemple E:System.Console.CustomFormatter.
F:
Fait référence à un champ (variable membre statique). Par exemple F:System.Console.OutputEncoding.
M:
Fait référence à une méthode. Les paramètres sont décrits après le nom de la méthode, séparés par des parenthèses. Les types des paramètres sont identifiés par leur nom de chaîne correspondant. Les types génériques sont identifiés par des délimiteurs ` et un nombre qui indique le nombre de paramètres génériques. Les types génériques non liés sont représentés par les délimiteurs ` suivi du nombre de paramètres génériques. Les membres génériques sont représentés par les délimiteurs `` suivi de l'index du paramètre générique. Par exemple : M:System.String.ToLower(System.Globalization.CultureInfo), M:System.String.Compare(System.String,System.String), M:System.Array.Sort``1(``0[]), M:System.String.Concat(System.Object), M:System.Array.Sort``1(``0[]), M:System.Collections.Generic.List`1..ctor, M:System.Collections.Generic.List`1.Add(`0).
N:
Fait référence à un espace de noms, par exemple N:System.
P:
Fait référence à une propriété. Si la propriété est un indexeur ou prend des paramètres, les types des paramètres sont ajoutés au nom de la propriété et encadrés par des parenthèses : P:System.String.Length, P:System.String.Chars(System.Int32).
T:
L'identifiant de chaîne fait référence à un type, avec le nombre de types génériques ajouté : T:System.String, T:System.Collections.Generic.List`1.

Pour rendre les choses plus intéressantes, les types et membres génériques ont deux représentations : la représentation « non liée » (montrée dans les exemples ci-dessus), où les noms de classes ont le nombre de paramètres génériques ajouté à leur nom. Il existe également une représentation « liée », où la liaison des paramètres génériques est listée entre '{' et '}'.

Non liée : T:System.Collections.Generic.List`1, T:System.Collections.Generic.Dictionary`2.

Liée : T:System.Collections.Generic.List{System.Int32} T:System.Collections.Generic.Dictionary{System.String,System.Collections.Generic.List{System.Predicate{System.String}}}.

Comme vous pouvez le voir, les variantes liées peuvent être arbitrairement complexes (tout comme les génériques).

De plus, si un paramètre générique est lié au paramètre générique d'un type ou d'une méthode, l'« index » du paramètre générique du type/de la méthode est utilisé comme liaison, donc étant donné

class FooType {
  public static void Foo<T> (System.Predicate<T> predicate) {}
}
L'identifiant de chaîne pour cette méthode est M:FooType.Foo``1(System.Predicate{``0}), car ``0 est l'index du 0ème paramètre générique qui est lié à System.Predicate<T>.

FORMAT DE LA DOCUMENTATION

monodocer génère une documentation similaire au format de documentation Ecma, tel que décrit dans ECMA-335 3ème Édition, Partition IV, Chapitre 7.

La principale différence avec le format ECMA est que chaque type obtient son propre fichier, dans un répertoire identique à l'espace de noms du type.

La plupart des informations contenues dans la documentation ne devraient *pas* être modifiées. Cela inclut le nom du type ( /Type/@FullName ), les interfaces implémentées ( /Type/Interfaces ), les informations sur les membres ( /Type/Members/Member/@MemberName , /Type/Members/Member/MemberSignature , /Type/Members/Member/MemberType , /Type/Members/Member/Parameters , etc.).

Ce qui *devrait* être modifié, ce sont tous les éléments avec le texte À ajouter., qui sont présents sous les éléments //Docs (par exemple, /Type/Docs, /Type/Members/Member/Docs). Le contenu de l'élément Docs est *identique* en sémantique et en structure au format de documentation C# en ligne, composé de ces éléments (listés dans ECMA-334 3ème Édition, Annexe E, Section 2). Les éléments suivants sont utilisés dans les descriptions de documentation :

CREF
Fait référence à une référence de classe (ou de membre), et est une chaîne dans le format décrit ci-dessus dans la section FORMAT DES IDENTIFIANTS DE CHAÎNE.
TEXT
Texte non-XML, et le XML ne doit pas être imbriqué.
XML
Seuls les éléments XML peuvent être imbriqués (ce qui peut indirectement contenir du texte), mais le texte non-espace blanc ne doit pas être un enfant immédiat.
XML_TEXT
Texte et XML de forme libre, de sorte que d'autres éléments XML puissent être imbriqués.

Les éléments suivants sont utilisés dans la documentation :

<block subset="SUBSET" type="TYPE">XML_TEXT</block>
Crée un bloc de texte, similaire dans le concept à un paragraphe, mais il est utilisé pour créer des divisions dans le texte. Dans une certaine mesure, un <block/> est équivalent à la balise HTML <h2/>.

SUBSET doit toujours être la valeur none.

TYPE spécifie l'en-tête et le formatage à utiliser. Les types reconnus sont :

behaviors Crée une section avec l'en-tête Opération.

note Crée une section avec l'en-tête Note :.

overrides Crée une section avec l'en-tête Note aux héritiers.

usage Crée une section avec l'en-tête Utilisation.

<c>XML_TEXT</c>
Met le texte dans une police de type code (similaire à l'élément HTML <tt/>).
<code lang="LANGUAGE">TEXT</code>
Affiche plusieurs lignes de texte dans une police de type code (similaire à l'élément HTML <pre/>). LANGUAGE est la langue pour ce bloc de code. Par exemple, si LANGUAGE est C#, alors TEXT aura une coloration syntaxique pour le langage C# dans le Navigateur de Documentation Mono.
<example>XML_TEXT</example>
Indique un exemple qui doit être affiché de manière spéciale. Par exemple : 
<example>
  <para>Un paragraphe d'introduction.</para>
  <code lang="C#">
    class Example {
      public static void Main ()
      {
        System.Console.WriteLine ("Bonjour, le monde !");
      }
    }
  </code>
</example>
<exception cref="CREF">XML_TEXT</exception>
Identifie une exception qui peut être levée par le membre documenté.

<exception/> est un élément de niveau supérieur, et doit être imbriqué directement sous l'élément <Docs/>.

CREF est le type d'exception levé, tandis que XML_TEXT contient les circonstances qui provoqueraient la levée de CREF.

<exception cref="T:System.ArgumentNullException">
  <paramref name="foo" /> était <see langword="null" />.
</exception>
<list>XML</list>
Crée une liste ou un tableau d'éléments. <list/> utilise les éléments imbriqués <item>XML</item>, <listheader>XML</listheader>, <term>XML_TEXT</term>, et <description>XML_TEXT</description>.

Les listes ont la syntaxe suivante :

<list type="bullet"> <!-- ou type="number" -->
  <item><term>Puce 1</term></item>
  <item><term>Puce 2</term></item>
  <item><term>Puce 3</term></item>
</list>

Les tableaux ont la syntaxe suivante :

<list type="table">
  <listheader> <!-- listheader met cette ligne en gras -->
    <term>Colonne 1</term>
    <description>Colonne 2</description>
    <description>Colonne 3</description>
  </listheader>
  <item>
    <term>Élément 1-A</term>
    <description>Élément 1-B</description>
    <description>Élément 1-C</description>
  </item>
  <item>
    <term>Élément 2-A</term>
    <description>Élément 2-B</description>
    <description>Élément 2-C</description>
  </item>
</list>
<para>XML_TEXT</para>
Insère un paragraphe de XML_TEXT. Ceci est destiné à être utilisé dans d'autres balises, telles que <example/>, <remarks/>, <returns/>, <term/> et <description/> (voir <list/>, ci-dessus), et la plupart des autres éléments.

Par exemple,

<para>Ceci est un paragraphe de texte.</para>
<param name="NAME">XML_TEXT</param>
<param/> est un élément de niveau supérieur, et doit être imbriqué directement sous l'élément <Docs/>.

Décrit le paramètre NAME du constructeur, de la méthode ou de la propriété actuelle :

<param name="count">
  Un <see cref="T:System.Int32" /> contenant le nombre
  de widgets à traiter.
</param>
<paramref name="NAME" />
Indique que NAME est un paramètre.

Ceci rend généralement NAME en texte italique, il est donc fréquemment (mal) utilisé comme équivalent à l'élément HTML <i/>. Voir la documentation de <exception/> (ci-dessus) pour un exemple.

<permission cref="CREF">XML_TEXT</permission>
Documente les exigences d'accessibilité de sécurité du membre actuel.

<permission/> est un élément de niveau supérieur, et doit être imbriqué directement sous l'élément <Docs/>.

CREF est une référence de type à la permission de sécurité requise, tandis que XML_TEXT est une description de pourquoi la permission est requise.

<permission cref="T:System.Security.Permissions.FileIOPermission">
  Requiert la permission de lire et d'écrire des fichiers. Voir
  <see cref="F:System.Security.Permissions.FileIOPermissionAccess.Read" />,
  <see cref="F:System.Security.Permissions.FileIOPermissionAccess.Write" />.
</permission>
<remarks>XML_TEXT</remarks>
Contient des informations détaillées sur un membre.

<remarks/> est un élément de niveau supérieur, et doit être imbriqué directement sous l'élément <Docs/>.

<remarks>Insérer des informations détaillées ici.</remarks>
<returns>XML_TEXT</returns>

<remarks/> est un élément de niveau supérieur, et doit être imbriqué directement sous l'élément <Docs/>.

Décrit la valeur de retour d'une méthode :

<returns>
  Un <see cref="T:System.Boolean" /> spécifiant si
  le processus peut ou non accéder à
  <see cref="P:Mono.Unix.UnixFileSystemInfo.FullName" />.
</returns>
<see cref="CREF" />
Crée un lien vers le membre spécifié dans le texte actuel : 
<see cref="M:Some.Namespace.With.Type.Method" />
<seealso cref="CREF" />

<seealso/> est un élément de niveau supérieur, et doit être imbriqué directement sous l'élément <Docs/>.

Permet de générer une entrée pour la sous-section Voir aussi.

<summary>XML_TEXT</summary>
Fournit un résumé court et concis d'un membre.

<summary/> est un élément de niveau supérieur, et doit être imbriqué directement sous l'élément <Docs/>.

<summary>Résume l'objet.</summary>
<typeparam name="NAME">XML_TEXT</typeparam>
Décrit le paramètre générique NAME d'un type ou d'une méthode générique.

<typeparam/> est un élément de niveau supérieur, et doit être imbriqué directement sous l'élément <Docs/>.

<typeparam name="T">
  Le type des éléments de la liste.
</typeparam>
<typeparamref name="NAME" />
Indique que NAME est un paramètre générique. Similaire à <paramref/>.

Par exemple :

<summary>
  Une liste générique.
  <typeparamref name="T" /> spécifie le type des éléments.
</summary>
<value>XML_TEXT</value>
Décrit la valeur d'une propriété.

<value/> est un élément de niveau supérieur, et doit être imbriqué directement sous l'élément <Docs/>.

<value>Un entier représentant le nombre d'éléments dans la collection.</value>

DESCRIPTION

Le programme monodocer est un utilitaire de ligne de commande qui permet de générer de la documentation à partir des fichiers sources C#. Il analyse les commentaires de documentation XML générés par le compilateur C# (csc) et produit une sortie dans un format lisible par l'homme.

Ce programme est utile pour la génération de documentation pour des projets Mono ou .NET, permettant aux développeurs de fournir des informations détaillées sur leur code.

Format de la documentation

monodocer utilise les conventions de documentation XML standard de .NET. Voici quelques balises courantes utilisées dans les commentaires XML pour la génération de documentation :

<summary>DESCRIPTION</summary>

<summary/> est un élément de premier niveau, et doit être imbriqué directement sous l'élément <Docs/>.

Fournit un aperçu (bref !) d'un type ou d'un membre de type.

Ceci est généralement affiché dans le cadre d'une déclaration de classe, et doit être une description raisonnablement courte du type/membre. Utilisez <remarks/> pour des informations plus détaillées.

<remarks>DESCRIPTION</remarks>

<remarks/> est un élément de premier niveau, et doit être imbriqué directement sous l'élément <Docs/>.

Fournit des informations plus détaillées sur un type ou un membre de type.

Cette section est généralement affichée après le résumé.

<param name="NOM">DESCRIPTION</param>

<param/> est un élément de premier niveau, et doit être imbriqué directement sous l'élément <Docs/>.

Utilisé pour décrire un paramètre de méthode ou de constructeur.

NOM est le nom du paramètre, tandis que DESCRIPTION contient une description du paramètre (son but, ses contraintes, etc.).

<param name="format">Le format de chaîne à utiliser.</param>
<typeparam name="NOM">DESCRPITION</typeparam>
<typeparam/> est un élément de premier niveau, et doit être imbriqué directement sous l'élément <Docs/>.

Ceci est utilisé pour décrire un paramètre de type pour un type générique ou une méthode générique.

NOM est le nom du paramètre de type, tandis que DESCRIPTION contient une description du paramètre (à quoi il sert, quelles restrictions il doit respecter, etc.).

<typeparam name="T">Le type de la collection sous-jacente</typeparam>
<returns>DESCRIPTION</returns>

<returns/> est un élément de premier niveau, et doit être imbriqué directement sous l'élément <Docs/>.

Permet de décrire la valeur de retour d'une méthode.

<returns>Un booléen indiquant le succès de l'opération.</returns>
<exception cref="TYPE">DESCRIPTION</exception>

<exception/> est un élément de premier niveau, et doit être imbriqué directement sous l'élément <Docs/>.

Permet de décrire les exceptions qui peuvent être levées par un type ou un membre.

TYPE est le nom qualifié complet du type d'exception. DESCRIPTION décrit la condition dans laquelle l'exception est levée.

<exception cref="T:System.ArgumentNullException">Levée si <paramref name="input" /> est null.</exception>
<permission cref="TYPE">DESCRIPTION</permission>

<permission/> est un élément de premier niveau, et doit être imbriqué directement sous l'élément <Docs/>.

Décrit l'accès aux permissions pour un type ou un membre.

<permission cref="T:System.Security.Permissions.FileIOPermissionAttribute">
  Nécessite FileIOPermissionAccess.Write pour accéder au fichier.
</permission>
<altmember cref="MEMBER" />

<altmember/> est un élément de premier niveau, et doit être imbriqué directement sous l'élément <Docs/>.

Permet de spécifier un autre membre qui est étroitement lié.

Utilisez <see/> pour spécifier un lien à partir de texte.

<seealso cref="P:System.Exception.Message" />
<since version="VERSION" />

<since/> est un élément de premier niveau, et doit être imbriqué directement sous l'élément <Docs/>.

Permet de spécifier quelle version a introduit le type ou le membre spécifié.

<since version="Gtk# 2.4" />
<typeparamref>
Utilisé pour indiquer qu'un mot est un paramètre de type, pour être utilisé dans d'autres blocs de texte (par exemple, dans <para/> ). 
<para>Si <typeparamref name="T" /> est une structure, alors...</para>
<value>DESCRIPTION</value>
<value/> est un élément de premier niveau, et doit être imbriqué directement sous l'élément <Docs/>.

Permet de décrire une propriété.

<value>
  Une chaîne de caractères (<see cref="T:System.String" />) contenant le nom du widget.
</value>
