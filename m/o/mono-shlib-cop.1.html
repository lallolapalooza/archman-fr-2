mono-shlib-cop(1) Manuel des commandes générales mono-shlib-cop(1)

NOM

mono-shlib-cop - Vérificateur d'utilisation des bibliothèques partagées

SYNOPSIS

mono-shlib-cop [OPTIONS]* [NOM-FICHIER-ASSEMBLAGE]*

OPTIONS

-p, --prefixes=PRÉFIXE
Préfixes d'installation de Mono. Ceci sert à trouver le fichier $prefix/etc/mono/config. La valeur par défaut est basée sur l'emplacement de mscorlib.dll, et est normalement correcte.

DESCRIPTION

mono-shlib-cop est un outil qui inspecte un assemblage géré à la recherche d'une utilisation erronée ou suspecte des bibliothèques partagées.

L'outil prend un ou plusieurs noms de fichiers d'assemblage et inspecte chaque assemblage spécifié.

Les erreurs recherchées incluent :

*
La bibliothèque partagée existe-t-elle ?
*
Le symbole demandé existe-t-il dans la bibliothèque partagée ?

Les avertissements recherchés incluent :

*
La bibliothèque partagée cible est-elle une bibliothèque versionnée ? (Pertinent uniquement sur les systèmes Unix, pas sur Mac OS X ou Windows.)

En général, seules les bibliothèques versionnées telles que libc.so.6 sont présentes sur la machine de l'utilisateur, et les tentatives de charger libc.so entraîneront une System.DllNotFoundException. Il existe trois solutions à cela :

1.
Exiger que l'utilisateur installe tous les paquets -devel qui fournissent la bibliothèque non versionnée. Cela nécessite généralement que l'utilisateur installe un grand nombre de paquets supplémentaires, ce qui complique le processus d'installation.
2.
Utiliser un nom entièrement versionné dans vos instructions DllImport. Cela nécessite de modifier votre code source et de recompiler chaque fois que vous devez cibler une version différente de la bibliothèque partagée.
3.
Fournir un fichier assembly.config contenant des éléments <dllmap/> pour remapper le nom de la bibliothèque partagée utilisé par votre assemblage à la bibliothèque partagée versionnée réelle présente sur le système de l'utilisateur. Mono fournit un certain nombre d'entrées <dllmap/> préexistantes, y compris celles pour libc.so et libX11.so.

EXEMPLE

Le code suivant contient des exemples des erreurs et avertissements susmentionnés :

using System.Runtime.InteropServices; // pour DllImport
class Demo {
	[DllImport ("bad-library-name")]
	private static extern void BadLibraryName ();
	[DllImport ("libc.so")]
	private static extern void BadSymbolName ();
	[DllImport ("libcap.so")]
	private static extern int cap_clear (IntPtr cap_p);
}
Mauvais nom de bibliothèque
En supposant que la bibliothèque bad-library-name n'existe pas sur votre machine, Demo.BadLibraryName générera une erreur, car elle nécessite une bibliothèque partagée qui ne peut pas être chargée. Cela peut être ignoré ; voir BOGUES
Mauvais nom de symbole
Demo.BadSymbolName générera une erreur, car libc.so (remapper en libc.so.6 par le fichier $prefix/etc/mono/config de mono) ne contient pas la fonction BadSymbolName
Dépendance de bibliothèque non versionnée
En supposant que vous possédez le fichier libcap.so, Demo.cap_clear générera un avertissement car, bien que libcap.so puisse être chargé, libcap.so pourrait ne pas exister sur la machine de l'utilisateur (sur FC2, /lib/libcap.so est fourni par libcap-devel, et on ne peut pas supposer que les utilisateurs finaux auront des paquets -devel installés).

CORRECTION DU CODE

La correction dépend de l'avertissement ou de l'erreur :

Mauvais noms de bibliothèques
Utilisez un nom de bibliothèque valide dans l'attribut DllImport, ou fournissez une entrée <dllmap/> pour mapper votre nom de bibliothèque existant à un nom de bibliothèque valide.
Mauvais noms de symboles
Référencez un symbole qui existe réellement dans la bibliothèque cible.
Dépendance de bibliothèque non versionnée
Fournissez une entrée <dllmap/> pour référencer une bibliothèque correctement versionnée, ou ignorez l'avertissement (voir BOGUES).

ENTRÉES DLLMAP

Mono recherche des informations de mappage de NOM-ASSEMBLAGE. Par exemple, avec mcs.exe, Mono lirait mcs.exe.config, et pour Mono.Posix.dll, Mono lirait Mono.Posix.dll.config

Le fichier .config est un document XML contenant une section <configuration/> de niveau supérieur avec des entrées <dllmap/> imbriquées, qui contiennent les attributs dll et target. L'attribut dll doit contenir la même chaîne que celle utilisée dans votre attribut DllImport, et l'attribut target spécifie quelle bibliothèque partagée mono doit réellement charger à l'exécution.

Un exemple de fichier .config est :

<configuration>
	<dllmap dll="gtkembedmoz" target="libgtkembedmoz.so" />
</configuration>

BOGUES

*
Seules les entrées DllImport sont vérifiées ; le IL environnant est ignoré. Par conséquent, si une vérification à l'exécution est effectuée pour choisir quelle bibliothèque partagée invoquer, une erreur sera signalée même si la bibliothèque spécifiée n'est jamais utilisée. Considérez ce code : 
using System.Runtime.InteropServices; // pour DllImport
class Beep {
	[DllImport ("kernel32.dll")]
	private static extern int Beep (int dwFreq, int dwDuration);
	[DllImport ("libcurses.so")]
	private static extern int beep ();
	public static void Beep ()
	{
		if (System.IO.Path.DirectorySeparatorChar == '\\') {
			Beep (750, 300);
		}
		else {
			beep ();
		}
	}
}
Si mono-shlib-cop est exécuté sur cet assemblage, une erreur sera signalée pour l'utilisation de kernel32.dll, même si kernel32.dll ne sera jamais utilisé sur les plateformes Unix.
*
mono-shlib-cop examine actuellement uniquement l'extension du fichier de bibliothèque partagée pour déterminer si un avertissement doit être généré. Une extension .so générera toujours un avertissement, même si le .so n'est pas un lien symbolique, n'est pas fourni dans un paquet -devel, et qu'il n'y a pas de bibliothèque partagée versionnée (exemples possibles incluant /usr/lib/libtcl8.4.so, /usr/lib/libubsec.so, etc.).

Par conséquent, les avertissements pour de telles bibliothèques sont inutiles et incorrects.

Windows et Mac OS X ne généreront jamais d'avertissements, car ces plateformes utilisent des extensions de bibliothèques partagées différentes.
