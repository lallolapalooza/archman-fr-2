mount_setattr(2) System Calls Manual mount_setattr(2)

NAME

mount_setattr - change properties of a mount or mount tree

LIBRARY

Standard C library (libc, -lc)

SYNOPSIS

#include <fcntl.h>       /* Definition of AT_* constants */
#include <sys/mount.h>
int mount_setattr(int dirfd, const char *path, unsigned int flags,
                  struct mount_attr *attr, size_t size);

DESCRIPTION

The mount_setattr() system call is part of the suite of file-descriptor-based mount facilities in Linux.

mount_setattr() changes the mount properties of a mount or an entire mount tree. If path is relative, then it is interpreted relative to the directory referred to by the file descriptor dirfd. If dirfd is the special value AT_FDCWD, then path is interpreted relative to the current working directory of the calling process. If path is the empty string and AT_EMPTY_PATH is specified in flags, then the mount properties of the mount identified by dirfd are changed. (See openat(2) for an explanation of why the dirfd argument is useful.)

The mount_setattr() system call uses an extensible structure (struct mount_attr) to allow for future extensions. Any non-flag extensions to mount_setattr() will be implemented as new fields appended to the this structure, with a zero value in a new field resulting in the kernel behaving as though that extension field was not present. Therefore, the caller must zero-fill this structure on initialization. See the "Extensibility" subsection under NOTES for more details.

The size argument should usually be specified as sizeof(struct mount_attr). However, if the caller is using a kernel that supports an extended struct mount_attr, but the caller does not intend to make use of these features, it is possible to pass the size of an earlier version of the structure together with the extended structure. This allows the kernel to not copy later parts of the structure that aren't used anyway. With each extension that changes the size of struct mount_attr, the kernel will expose a definition of the form MOUNT_ATTR_SIZE_VERnumber. For example, the macro for the size of the initial version of struct mount_attr is MOUNT_ATTR_SIZE_VER0.

The flags argument can be used to alter the pathname resolution behavior. The supported values are:

AT_EMPTY_PATH
If path is the empty string, change the mount properties on dirfd itself.
AT_RECURSIVE
Change the mount properties of the entire mount tree.
AT_SYMLINK_NOFOLLOW
Don't follow trailing symbolic links.
AT_NO_AUTOMOUNT
Don't trigger automounts.

The attr argument of mount_setattr() is a pointer to a mount_attr structure, described in mount_attr(2type).

The attr_set and attr_clr members are used to specify the mount properties that are supposed to be set or cleared for a mount or mount tree. Flags set in attr_set enable a property on a mount or mount tree, and flags set in attr_clr remove a property from a mount or mount tree.

When changing mount properties, the kernel will first clear the flags specified in the attr_clr field, and then set the flags specified in the attr_set field. For example, these settings:


struct mount_attr attr = {
    .attr_clr = MOUNT_ATTR_NOEXEC | MOUNT_ATTR_NODEV,
    .attr_set = MOUNT_ATTR_RDONLY | MOUNT_ATTR_NOSUID,
};

are equivalent to the following steps:


unsigned int current_mnt_flags = mnt->mnt_flags;
/*
 * Clear all flags set in .attr_clr,
 * clearing MOUNT_ATTR_NOEXEC and MOUNT_ATTR_NODEV.
 */
current_mnt_flags &= ~attr->attr_clr;
/*
 * Now set all flags set in .attr_set,
 * applying MOUNT_ATTR_RDONLY and MOUNT_ATTR_NOSUID.
 */
current_mnt_flags |= attr->attr_set;
mnt->mnt_flags = current_mnt_flags;

As a result of this change, the mount or mount tree (a) is read-only; (b) blocks the execution of set-user-ID and set-group-ID programs; (c) allows execution of programs; and (d) allows access to devices.

Multiple changes with the same set of flags requested in attr_clr and attr_set are guaranteed to be idempotent after the changes have been applied.

The following mount attributes can be specified in the attr_set or attr_clr fields:

MOUNT_ATTR_RDONLY
If set in attr_set, makes the mount read-only. If set in attr_clr, removes the read-only setting if set on the mount.
MOUNT_ATTR_NOSUID
If set in attr_set, causes the mount not to honor the set-user-ID and set-group-ID mode bits and file capabilities when executing programs. If set in attr_clr, clears the set-user-ID, set-group-ID, and file capability restriction if set on this mount.
MOUNT_ATTR_NODEV
If set in attr_set, prevents access to devices on this mount. If set in attr_clr, removes the restriction that prevented accessing devices on this mount.
MOUNT_ATTR_NOEXEC
If set in attr_set, prevents executing programs on this mount. If set in attr_clr, removes the restriction that prevented executing programs on this mount.
MOUNT_ATTR_NOSYMFOLLOW
If set in attr_set, prevents following symbolic links on this mount. If set in attr_clr, removes the restriction that prevented following symbolic links on this mount.
MOUNT_ATTR_NODIRATIME
If set in attr_set, prevents updating access time for directories on this mount. If set in attr_clr, removes the restriction that prevented updating access time for directories. Note that MOUNT_ATTR_NODIRATIME can be combined with other access-time settings and is implied by the noatime setting. All other access-time settings are mutually exclusive.
MOUNT_ATTR__ATIME - changing access-time settings
The access-time values listed below are an enumeration that includes the value zero, expressed in the bits defined by the mask MOUNT_ATTR__ATIME. Even though these bits are an enumeration (in contrast to the other mount flags such as MOUNT_ATTR_NOEXEC), they are nonetheless passed in attr_set and attr_clr for consistency with fsmount(2), which introduced this behavior.
Note that, since the access-time values are an enumeration rather than bit values, a caller wanting to transition to a different access-time setting cannot simply specify the access-time setting in attr_set, but must also include MOUNT_ATTR__ATIME in the attr_clr field. The kernel will verify that MOUNT_ATTR__ATIME isn't partially set in attr_clr (i.e., either all bits in the MOUNT_ATTR__ATIME bit field are either set or clear), and that attr_set doesn't have any access-time bits set if MOUNT_ATTR__ATIME isn't set in attr_clr.
MOUNT_ATTR_RELATIME
When a file is accessed via this mount, update the file's last access time (atime) only if the current value of atime is less than or equal to the file's last modification time (mtime) or last status change time (ctime).
To enable this access-time setting on a mount or mount tree, MOUNT_ATTR_RELATIME must be set in attr_set and MOUNT_ATTR__ATIME must be set in attr_clr. The kernel will check that MOUNT_ATTR__ATIME is fully set or unset in attr_clr. If MOUNT_ATTR__ATIME is unset in attr_clr, then attr_set must not contain any access-time bits.

The following behavior is observed when setting or clearing access-time attributes:

MOUNT_ATTR_STRICTATIME
Always update the access time.
To set this attribute, specify MOUNT_ATTR_STRICTATIME in attr_set and MOUNT_ATTR__ATIME in attr_clr.
MOUNT_ATTR_NOATIME
Never update the access time.
To set this attribute, specify MOUNT_ATTR_NOATIME in attr_set and MOUNT_ATTR__ATIME in attr_clr.

A call to mount_setattr() for a mount or mount tree may fail if the caller lacks the necessary privileges (see CAP_SYS_ADMIN in capabilities(7)) or if the specified combination of flags is invalid.

An invalid combination may include attempting to set flags that are mutually exclusive (e.g. MOUNT_ATTR_NOATIME and MOUNT_ATTR_RELATIME).

It is also possible to attempt to set flags that are not supported by the filesystem.

Extensibility

The struct mount_attr is designed to be extensible. New fields may be added to the end of the structure in future kernel versions. When the kernel receives a struct mount_attr, it checks the size argument. If size is larger than the size of the structure known to the kernel, the extra fields are ignored. The kernel defines macros like MOUNT_ATTR_SIZE_VER0 for the size of the initial structure. Users should initialize the structure with zeros and pass sizeof(struct mount_attr).

RETURN VALUE

On success, mount_setattr() returns 0. On failure, it returns -1, and errno is set to indicate the error.

ERRORS

EACCES
path is not searchable. Or, write access to path is not allowed, or the mount point is not writable and appropriate privileges are not held.
EALREADY
A non-blocking operation is already in progress.
EBUSY
The specified mount point is busy and cannot be modified.
EINVAL
An invalid value was passed in flags or attr. For example, an invalid combination of flags was specified, or an unsupported attribute was requested.
ELOOP
Too many symbolic links encountered while processing path.
EMLINK
Too many links.
ENAMETOOLONG
path is too long.
ENOENT
A component of path does not exist or path is an empty string and AT_EMPTY_PATH was not specified.
ENOMEM
Not enough memory available.
ENOTDIR
A component of path is not a directory. Or, path is not relative and dirfd refers to a directory.
ENOTSUP
The filesystem does not support the requested attribute change.
EOVERFLOW
Path was too convoluted, or the filesystem is too full.
EROFS
The filesystem is mounted read-only.
ESRCH
dirfd is not a valid file descriptor.

STANDARDS

This system call is Linux-specific.

HISTORY

The mount_setattr() system call first appeared in Linux kernel 5.12.

NOTES

Montages mappés par ID

La création d'un montage mappé par ID permet de modifier la propriété de tous les fichiers situés sous un montage. Ainsi, les montages mappés par ID permettent de modifier la propriété de manière temporaire et localisée. Il s'agit d'un changement localisé car les modifications de propriété ne sont visibles que via un montage spécifique. Tous les autres utilisateurs et emplacements où le système de fichiers est exposé ne sont pas affectés. Il s'agit d'un changement temporaire car les modifications de propriété sont liées à la durée de vie du montage.

Chaque fois que les appelants interagissent avec le système de fichiers via un montage mappé par ID, le mappage d'ID du montage sera appliqué aux ID utilisateur et groupe associés aux objets du système de fichiers. Cela inclut les ID utilisateur et groupe associés aux inodes ainsi que les clés d'xattr(7) suivantes :

•
security.capability, chaque fois que les capacités du système de fichiers sont stockées ou retournées dans le format VFS_CAP_REVISION_3, qui stocke un ID utilisateur root à côté des capacités (voir capabilities(7)).
•
system.posix_acl_access et system.posix_acl_default, lorsque des ID utilisateur ou des ID de groupe sont stockés dans des entrées ACL_USER ou ACL_GROUP.

Les conditions suivantes doivent être remplies pour créer un montage mappé par ID :

•
L'appelant doit posséder la capacité CAP_SYS_ADMIN dans l'espace de noms utilisateur dans lequel le système de fichiers a été monté.
•
Le système de fichiers sous-jacent doit prendre en charge les montages mappés par ID. Actuellement, les systèmes de fichiers suivants prennent en charge les montages mappés par ID
ts:
•
xfs(5) (depuis Linux 5.12)
•
ext4(5) (depuis Linux 5.12)
•
FAT (depuis Linux 5.12)
•
btrfs(5) (depuis Linux 5.15)
•
ntfs3 (depuis Linux 5.15)
•
f2fs (depuis Linux 5.18)
•
erofs (depuis Linux 5.19)
•
overlayfs (couches inférieure et supérieure avec mappage d'ID prises en charge depuis Linux 5.19)
•
squashfs (depuis Linux 6.2)
•
tmpfs (depuis Linux 6.3)
•
cephfs (depuis Linux 6.7)
•
hugetlbfs (depuis Linux 6.9)
•
Le montage ne doit pas être déjà mappé par ID. Ceci implique également que le mappage d'ID d'un montage ne peut pas être modifié.
•
Le montage ne doit avoir aucun écrivain.
•
Le montage doit être un montage détaché ; c'est-à-dire qu'il doit avoir été créé en appelant open_tree(2) avec le drapeau OPEN_TREE_CLONE et qu'il ne doit pas avoir été visible dans un espace de noms de montage. (Pour dire les choses autrement : le montage ne doit pas avoir été attaché à la hiérarchie du système de fichiers avec un appel système tel que move_mount(2).)

Les mappages d'ID peuvent être créés pour les ID d'utilisateur, les ID de groupe et les ID de projet. Un mappage d'ID est essentiellement un mappage d'une plage d'ID d'utilisateur ou de groupe vers une autre plage d'ID d'utilisateur ou de groupe, ou la même. Les mappages d'ID sont écrits pour mapper les fichiers sous forme de trois nombres séparés par des espaces. Les deux premiers nombres spécifient l'ID d'utilisateur ou de groupe de départ dans chacun des deux espaces de noms d'utilisateur. Le troisième nombre spécifie la plage du mappage d'ID. Par exemple, un mappage pour les ID d'utilisateur tel que "1000 1001 1" indiquerait que l'ID d'utilisateur 1000 dans l'espace de noms d'utilisateur de l'appelant est mappé à l'ID d'utilisateur 1001 dans son espace de noms d'utilisateur parent. Étant donné que la plage de mappage est de 1, seul l'ID d'utilisateur 1000 est mappé.

Il est possible de spécifier jusqu'à 340 mappages d'ID pour chaque type de mappage d'ID. Si des ID d'utilisateur ou des ID de groupe ne sont pas mappés, tous les fichiers appartenant à cet ID d'utilisateur ou ID de groupe non mappé apparaîtront comme appartenant à l'ID d'utilisateur de dépassement ou à l'ID de groupe de dépassement respectivement.

Pour plus de détails sur la configuration des mappages d'ID, voir user_namespaces(7).

Dans le cas courant, l'espace de noms d'utilisateur passé dans userns_fd (avec MOUNT_ATTR_IDMAP dans attr_set) pour créer un montage mappé par ID sera l'espace de noms d'utilisateur d'un conteneur. Dans d'autres scénarios, ce sera un espace de noms d'utilisateur dédié associé à la session de connexion d'un utilisateur, comme c'est le cas pour les répertoires personnels portables dans systemd-homed.service(8). Il est également tout à fait possible de créer un espace de noms d'utilisateur dédié dans le but de mapper par ID un montage.

Les montages mappés par ID peuvent être utiles dans les scénarios suivants et dans une variété d'autres scénarios :

•
Partage de fichiers ou de systèmes de fichiers entre plusieurs utilisateurs ou plusieurs machines, en particulier dans des scénarios complexes. Par exemple, les montages mappés par ID sont utilisés pour implémenter des répertoires personnels portables dans systemd-homed.service(8), où ils permettent aux utilisateurs de déplacer leur répertoire personnel vers un périphérique de stockage externe et de l'utiliser sur plusieurs ordinateurs où ils se voient attribuer différents ID d'utilisateur et ID de groupe. Cela permet effectivement d'attribuer des ID d'utilisateur et des ID de groupe aléatoires à l'heure de connexion.
•
Partage de fichiers ou de systèmes de fichiers depuis l'hôte avec des conteneurs non privilégiés. Cela permet à un utilisateur d'éviter de changer la propriété de manière permanente via chown(2).
•
Mappage par ID du système de fichiers racine d'un conteneur. Les utilisateurs n'ont pas besoin de changer la propriété de manière permanente via chown(2). Surtout pour les grands systèmes de fichiers racines, l'utilisation de chown(2) peut être prohibitif.
•
Partage de fichiers ou de systèmes de fichiers entre conteneurs avec des mappages d'ID qui ne se chevauchent pas.
•
Mise en œuvre du contrôle d'accès discrétionnaire (DAC) pour les systèmes de fichiers qui n'ont pas de concept de propriété.
•
Modification efficace de la propriété par montage. Contrairement à chown(2), la modification de la propriété d'un grand nombre de fichiers est instantanée avec les montages mappés par ID. Ceci est particulièrement utile lorsque la propriété d'un système de fichiers racine entier d'une machine virtuelle ou d'un conteneur doit être modifiée, comme mentionné ci-dessus. Avec les montages mappés par ID, un seul appel système mount_setattr() sera suffisant pour changer la propriété de tous les fichiers.
•
Prise en compte de la propriété actuelle. Les mappages d'ID spécifient précisément à quoi un ID d'utilisateur ou de groupe doit être mappé. Ceci contraste avec l'appel système chown(2) qui ne peut pas, en soi, tenir compte de la propriété actuelle des fichiers qu'il modifie. Il change simplement la propriété à l'ID d'utilisateur et à l'ID de groupe spécifiés.
•
Modifications locales et temporairement restreintes de la propriété. Les montages mappés par ID permettent de modifier la propriété localement, en restreignant les modifications de la propriété à des montages spécifiques, et temporairement car les modifications de la propriété ne s'appliquent que tant que le montage existe. En revanche, la modification de la propriété via l'appel système chown(2) modifie la propriété de manière globale et permanente.

Attributs de montage et paramètres de système de fichiers

Certains attributs de montage (traditionnellement associés aux options de style mount(8)) ont un paramètre de système de fichiers frère avec un comportement superficiellement similaire pour l'utilisateur. Par exemple, l'option -o ro de mount(8) peut faire référence au paramètre de système de fichiers "en lecture seule", ou à l'attribut de montage "en lecture seule". Ces deux options rendent les objets de montage en lecture seule, mais leur comportement est différent.

La distinction entre ces deux types d'options est que les attributs des objets de montage sont appliqués par objet de montage (permettant à différents objets de montage dérivés d'une instance de système de fichiers donnée d'avoir des attributs différents), tandis que les paramètres de l'instance de système de fichiers ("drapeaux de superbloc" dans le jargon des développeurs du noyau) s'appliquent à tous les objets de montage dérivés de la même instance de système de fichiers.

Lorsque l'on utilise mount(2), la ligne entre ces deux types d'options de montage était floue. Cependant, avec mount_setattr() et fsconfig(2), la distinction est beaucoup plus claire. Les attributs de montage sont configurés avec mount_setattr(), tandis que les paramètres du système de fichiers sont configurés à l'aide de fsconfig(2).

Extensibilité

Afin de permettre une extensibilité future, mount_setattr() exige que l'application en espace utilisateur spécifie la taille de la structure mount_attr qu'elle transmet. En fournissant cette information, il est possible pour mount_setattr() d'assurer la compatibilité avant et arrière, size agissant comme un numéro de version implicite. (Étant donné que les nouveaux champs d'extension seront toujours ajoutés, la taille de la structure augmentera toujours.) Cette conception d'extensibilité est très similaire à d'autres appels système tels que perf_setattr(2), perf_event_open(2), clone3(2) et openat2(2).

Soit usize la taille de la structure telle que spécifiée par l'application en espace utilisateur, et soit ksize la taille de la structure prise en charge par le noyau, alors il y a trois cas à considérer :

•
Si ksize est égal à usize, alors il n'y a pas de décalage de version et attr peut être utilisé tel quel.
•
Si ksize est supérieur à usize, alors il y a des champs d'extension que le noyau prend en charge et dont l'application en espace utilisateur n'est pas consciente. Étant donné qu'une valeur nulle dans tout champ d'extension ajouté signifie un no-op (pas d'opération), le noyau traite tous les champs d'extension non fournis par l'application en espace utilisateur comme ayant des valeurs nulles. Cela assure la compatibilité ascendante.
•
Si ksize est inférieur à usize, alors il y a des champs d'extension dont l'application en espace utilisateur est consciente mais que le noyau ne prend pas en charge. Étant donné que tout champ d'extension doit avoir des valeurs nulles signifiant un no-op, le noyau peut ignorer en toute sécurité les champs d'extension non pris en charge s'ils sont tous nuls. Si des champs d'extension non pris en charge sont non nuls, alors -1 est retourné et errno est défini sur E2BIG. Cela assure la compatibilité descendante.

Étant donné que la définition de struct mount_attr peut changer à l'avenir (avec l'ajout de nouveaux champs lors de la mise à jour des en-têtes système), les applications en espace utilisateur doivent initialiser à zéro struct mount_attr pour s'assurer que la recompilation du programme avec de nouveaux en-têtes ne produira pas d'erreurs parasites au moment de l'exécution. La manière la plus simple est d'utiliser un initialiseur désigné :


struct mount_attr attr = {
    .attr_set = MOUNT_ATTR_RDONLY,
    .attr_clr = MOUNT_ATTR_NODEV
};

Alternativement, la structure peut être initialisée à zéro en utilisant memset(3) ou des fonctions similaires :


struct mount_attr attr;
memset(&attr, 0, sizeof(attr));
attr.attr_set = MOUNT_ATTR_RDONLY;
attr.attr_clr = MOUNT_ATTR_NODEV;

Une application en espace utilisateur qui souhaite déterminer quelles extensions le noyau en cours d'exécution prend en charge peut le faire en effectuant une recherche binaire sur size avec une structure dont chaque octet est non nul (pour trouver la plus grande valeur qui ne produit pas d'erreur E2BIG).
