mount(2) Manuel des appels système mount(2)

NOM

mount - monter un système de fichiers

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNOPSIS

#include <sys/mount.h>
int mount(const char *source, const char *target,
          const char *filesystemtype, unsigned long mountflags,
          const void *_Nullable data);

DESCRIPTION

mount() attache le système de fichiers spécifié par source (qui est souvent un chemin d'accès faisant référence à un périphérique, mais peut aussi être le chemin d'accès d'un répertoire ou d'un fichier, ou une chaîne factice) à l'emplacement (un répertoire ou un fichier) spécifié par le chemin d'accès dans target.

Un privilège approprié (Linux : la capacité CAP_SYS_ADMIN) est requis pour monter des systèmes de fichiers.

Les valeurs pour l'argument filesystemtype prises en charge par le noyau sont listées dans /proc/filesystems (par exemple, "btrfs", "ext4", "jfs", "xfs", "vfat", "fuse", "tmpfs", "cgroup", "proc", "mqueue", "nfs", "cifs", "iso9660"). D'autres types peuvent devenir disponibles lorsque les modules appropriés sont chargés.

L'argument data est interprété par les différents systèmes de fichiers. Il s'agit généralement d'une chaîne d'options séparées par des virgules comprises par ce système de fichiers. Voir mount(8) pour les détails des options disponibles pour chaque type de système de fichiers. Cet argument peut être spécifié comme NULL, s'il n'y a pas d'options.

Un appel à mount() effectue l'un des types d'opérations générales, en fonction des bits spécifiés dans mountflags. Le choix de l'opération à effectuer est déterminé en testant les bits définis dans mountflags, les tests étant effectués dans l'ordre indiqué ici :

•
Remonter un montage existant : mountflags inclut MS_REMOUNT.
•
Créer un montage de liaison (bind mount) : mountflags inclut MS_BIND.
•
Changer le type de propagation d'un montage existant : mountflags inclut l'un de MS_SHARED, MS_PRIVATE, MS_SLAVE, ou MS_UNBINDABLE.
•
Déplacer un montage existant vers un nouvel emplacement : mountflags inclut MS_MOVE.
•
Créer un nouveau montage : mountflags n'inclut aucun des drapeaux précédents.

Chacune de ces opérations est détaillée plus loin sur cette page. Des drapeaux supplémentaires peuvent être spécifiés dans mountflags pour modifier le comportement de mount(), comme décrit ci-dessous.

Drapeaux de montage supplémentaires

La liste ci-dessous décrit les drapeaux supplémentaires qui peuvent être spécifiés dans mountflags. Notez que certains types d'opérations ignorent certains ou tous ces drapeaux, comme décrit plus loin sur cette page.

MS_DIRSYNC (depuis Linux 2.5.19)
Rendre les modifications de répertoire sur ce système de fichiers synchrones. (Cette propriété peut être obtenue pour des répertoires ou des sous-arborescences individuels à l'aide de chattr(1).)
MS_LAZYTIME (depuis Linux 4.0)
Réduire les mises à jour sur disque des horodatages d'inodes (atime, mtime, ctime) en conservant ces modifications uniquement en mémoire. Les horodatages sur disque sont mis à jour uniquement lorsque :
•
l'inode doit être mis à jour pour un changement non lié aux horodatages de fichier ;
•
l'application utilise fsync(2), syncfs(2), ou sync(2) ;
•
un inode non supprimé est évincé de la mémoire ; ou
•
plus de 24 heures se sont écoulées depuis que l'inode a été écrit sur le disque.
Cette option de montage réduit considérablement les écritures nécessaires pour mettre à jour les horodatages de l'inode, en particulier mtime et atime. Cependant, en cas de crash du système, les champs atime et mtime sur le disque peuvent être obsolètes jusqu'à 24 heures.
Des exemples de charges de travail où cette option pourrait être d'un grand avantage incluent les écritures aléatoires fréquentes sur des fichiers pré-alloués, ainsi que les cas où l'option de montage MS_STRICTATIME est également activée. (L'avantage de combiner MS_STRICTATIME et MS_LAZYTIME est que stat(2) renverra l'atime correctement mis à jour, mais les mises à jour atime ne seront poussées sur disque que dans les cas listés ci-dessus.)
MS_MANDLOCK
Permettre le verrouillage obligatoire (mandataire) sur les fichiers de ce système de fichiers. (Le verrouillage obligatoire doit toujours être activé par fichier, comme décrit dans fcntl(2).) Depuis Linux 4.5, cette option de montage nécessite la capacité CAP_SYS_ADMIN et un noyau configuré avec l'option CONFIG_MANDATORY_FILE_LOCKING. Le verrouillage obligatoire a été entièrement déprécié dans Linux 5.15, donc ce drapeau doit être considéré comme déprécié.
MS_NOATIME
Ne pas mettre à jour les heures d'accès aux fichiers (de tous types) sur ce système de fichiers.
MS_NODEV
Ne pas autoriser l'accès aux périphériques (fichiers spéciaux) sur ce système de fichiers.
MS_NODIRATIME
Ne pas mettre à jour les heures d'accès aux répertoires sur ce système de fichiers. Ce drapeau fournit un sous-ensemble de la fonctionnalité fournie par MS_NOATIME ; c'est-à-dire que MS_NOATIME implique MS_NODIRATIME.
MS_NOEXEC
Ne pas autoriser l'exécution de programmes depuis ce système de fichiers.
MS_NOSUID
Ne pas tenir compte des bits set-user-ID et set-group-ID ou des capacités de fichier lors de l'exécution de programmes depuis ce système de fichiers. De plus, les transitions de domaine SELinux nécessitent la permission nosuid_transition, qui à son tour nécessite également la capacité de politique nnp_nosuid_transition.
MS_RDONLY
Monter le système de fichiers en lecture seule.
MS_REC (depuis Linux 2.4.11)
Utilisé conjointement avec MS_BIND pour créer un montage de liaison récursif, et conjointement avec les drapeaux de type de propagation pour changer récursivement le type de propagation de tous les montages d'une sous-arborescence. Voir ci-dessous pour plus de détails.
MS_RELATIME (depuis Linux 2.6.20)
Lorsqu'un fichier de ce système de fichiers est accédé, mettre à jour l'heure de dernier accès du fichier (atime) uniquement si la valeur actuelle de atime est inférieure ou égale à l'heure de dernière modification du fichier (mtime) ou à l'heure de dernier changement d'état (ctime). Cette option est utile pour les programmes, tels que mutt(1), qui doivent savoir quand un fichier a été lu depuis sa dernière modification. Depuis Linux 2.6.30, le noyau utilise par défaut le comportement fourni par ce drapeau (sauf si MS_NOATIME a été spécifié), et le drapeau MS_STRICTATIME est requis pour obtenir la sémantique traditionnelle. De plus, depuis Linux 2.6.30, l'heure de dernier accès du fichier est toujours mise à jour si elle a plus d'un jour.
MS_SILENT (depuis Linux 2.6.17)
Supprimer l'affichage de certains messages d'avertissement (printk()) dans le journal du noyau. Ce drapeau remplace le drapeau mal nommé et obsolète MS_VERBOSE (disponible depuis Linux 2.4.12), qui a la même signification.
MS_STRICTATIME (depuis Linux 2.6.30)
Toujours mettre à jour l'heure de dernier accès (atime) lorsque des fichiers de ce système de fichiers sont accédés. (C'était le comportement par défaut avant Linux 2.6.30.) Spécifier ce drapeau remplace l'ef

MS_SYNCHRONOUS
Rend les écritures sur ce système de fichiers synchrones (comme si l'indicateur O_SYNC passé à open(2) avait été spécifié pour toutes les ouvertures de fichiers sur ce système de fichiers).
MS_NOSYMFOLLOW (depuis Linux 5.10)
Ne suit pas les liens symboliques lors de la résolution des chemins. Les liens symboliques peuvent toujours être créés, et readlink(1), readlink(2), realpath(1) et realpath(3) fonctionnent toujours correctement.

À partir de Linux 2.4, certains des indicateurs ci-dessus peuvent être définis par point de montage, tandis que d'autres s'appliquent au superbloc du système de fichiers monté, ce qui signifie que tous les montages du même système de fichiers partagent ces indicateurs. (Auparavant, tous les indicateurs étaient par superbloc.)

Les indicateurs par point de montage sont les suivants :

•
Depuis Linux 2.4 : les indicateurs MS_NODEV, MS_NOEXEC et MS_NOSUID peuvent être définis par point de montage.
•
De plus, depuis Linux 2.6.16 : MS_NOATIME et MS_NODIRATIME.
•
De plus, depuis Linux 2.6.20 : MS_RELATIME.

Les indicateurs suivants sont par superbloc : MS_DIRSYNC, MS_LAZYTIME, MS_MANDLOCK, MS_SILENT et MS_SYNCHRONOUS. Les paramètres initiaux de ces indicateurs sont déterminés lors du premier montage du système de fichiers et seront partagés par tous les montages ultérieurs du même système de fichiers. Par la suite, les paramètres des indicateurs peuvent être modifiés via une opération de remonte (voir ci-dessous). De telles modifications seront visibles via tous les montages associés au système de fichiers.

Depuis Linux 2.6.16, MS_RDONLY peut être défini ou effacé par point de montage ainsi que sur le superbloc sous-jacent du système de fichiers. Le système de fichiers monté ne sera accessible en écriture que si ni le système de fichiers ni le point de montage ne sont marqués comme lecture seule.

Remontage d'un montage existant

Un montage existant peut être remonté en spécifiant MS_REMOUNT dans mountflags. Cela permet de modifier les mountflags et les data d'un montage existant sans avoir à démonter et remonter le système de fichiers. target doit être la même valeur que celle spécifiée dans l'appel initial mount().

Les arguments source et filesystemtype sont ignorés.

Les arguments mountflags et data doivent correspondre aux valeurs utilisées dans l'appel mount() d'origine, à l'exception des paramètres qui sont délibérément modifiés.

Les mountflags suivants peuvent être modifiés : MS_LAZYTIME, MS_MANDLOCK, MS_NOATIME, MS_NODEV, MS_NODIRATIME, MS_NOEXEC, MS_NOSUID, MS_RELATIME, MS_RDONLY, MS_STRICTATIME (dont l'effet est d'effacer les indicateurs MS_NOATIME et MS_RELATIME) et MS_SYNCHRONOUS. Les tentatives de modification du paramètre des indicateurs MS_DIRSYNC et MS_SILENT lors d'un remontage sont silencieusement ignorées. Notez que les modifications apportées aux indicateurs par superbloc sont visibles via tous les montages du système de fichiers associé (car les indicateurs par superbloc sont partagés par tous les montages).

Depuis Linux 3.17, si aucun des indicateurs MS_NOATIME, MS_NODIRATIME, MS_RELATIME ou MS_STRICTATIME n'est spécifié dans mountflags, l'opération de remontage préserve les valeurs existantes de ces indicateurs (au lieu de revenir par défaut à MS_RELATIME).

Depuis Linux 2.6.26, l'indicateur MS_REMOUNT peut être utilisé avec MS_BIND pour modifier uniquement les indicateurs par point de montage. Ceci est particulièrement utile pour définir ou effacer l'indicateur "lecture seule" sur un montage sans modifier les paramètres du système de fichiers sous-jacent. L'argument data est ignoré. Les indicateurs par point de montage existants du point de montage sont effacés et remplacés par ceux de mountflags. Cela signifie que si vous souhaitez conserver les indicateurs par point de montage existants, vous devez les inclure dans mountflags, ainsi que les indicateurs par point de montage que vous souhaitez définir (ou avec les indicateurs que vous souhaitez effacer manquants). Spécifier mountflags comme :


MS_REMOUNT | MS_BIND | MS_RDONLY

rendra l'accès via ce point de montage en lecture seule (effaçant tous les autres indicateurs par point de montage), sans affecter les autres montages de ce système de fichiers.

Création d'un montage par liaison (bind mount)

Si mountflags inclut MS_BIND (disponible depuis Linux 2.4), alors effectuez un montage par liaison. Un montage par liaison rend un fichier ou un sous-arbre de répertoire visible à un autre endroit dans la hiérarchie de répertoires unique. Les montages par liaison peuvent traverser les limites des systèmes de fichiers et enjamber les chroot(2) jails.

Les arguments filesystemtype et data sont ignorés.

Les bits restants (autres que MS_REC, décrit ci-dessous) de l'argument mountflags sont également ignorés. (Le montage par liaison a les mêmes options de montage que le montage sous-jacent.) Cependant, voir la discussion sur le remontage ci-dessus pour une méthode de rendre un montage par liaison existant en lecture seule.

Par défaut, lorsqu'un répertoire est monté par liaison, seul ce répertoire est monté ; s'il y a des sous-montages dans l'arborescence du répertoire, ils ne sont pas montés par liaison. Si l'indicateur MS_REC est également spécifié, alors une opération de montage par liaison récursive est effectuée : tous les sous-montages sous le sous-arbre source (à l'exception des montages non liables) sont également montés par liaison à l'emplacement correspondant dans le sous-arbre target.

Modification du type de propagation d'un montage existant

Si mountflags inclut l'un des indicateurs MS_SHARED, MS_PRIVATE, MS_SLAVE ou MS_UNBINDABLE (tous disponibles depuis Linux 2.6.15), alors le type de propagation d'un montage existant est modifié. Si plus d'un de ces indicateurs est spécifié, une erreur se produit.

Les seuls autres indicateurs qui peuvent être spécifiés lors de la modification du type de propagation sont MS_REC (décrit ci-dessous) et MS_SILENT (qui est ignoré).

Les arguments source, filesystemtype et data sont ignorés.

Les significations des indicateurs de type de propagation sont les suivantes :

MS_SHARED
Rendre ce montage partagé. Les événements de montage et de démontage immédiatement sous ce montage se propageront aux autres montages membres du groupe de pairs de ce montage. La propagation ici signifie que le même montage ou démontage se produira automatiquement sous tous les autres montages du groupe de pairs. Inversement, les événements de montage et de démontage qui se produisent sous les montages pairs se propageront à ce montage.
MS_PRIVATE
Rendre ce montage privé. Les événements de montage et de démontage ne se propagent pas dans ou hors de ce montage.
MS_SLAVE
S'il s'agit d'un montage partagé membre d'un groupe de pairs contenant d'autres membres, le convertir en montage esclave. S'il s'agit d'un montage partagé membre d'un groupe de pairs ne contenant aucun autre membre, le convertir en montage privé. Sinon, le type de propagation du montage n'est pas modifié.
Lorsqu'un montage est un esclave, les événements de montage et de démontage se propagent dans ce montage à partir du groupe de pairs partagé (maître) dont il était auparavant membre. Les événements de montage et de démontage sous ce montage ne se propagent à aucun pair.
Un montage peut être l'esclave d'un autre groupe de pairs tout en partageant simultanément les événements de montage et de démontage avec un groupe de pairs dont il est membre.
MS_UNBINDABLE
Rendre ce montage non liable. C'est similaire à un montage privé, et en outre, ce montage ne peut pas être monté par liaison. Lorsqu'un montage par liaison récursif (mount() avec les indicateurs MS_BIND et MS_REC) est effectué sur un sous-arbre de répertoire, tous les montages non liables dans le sous-arbre sont automatiquement élagués (c'est-à-dire non répliqués) lors de la réplication de ce sous-arbre pour produire le sous-arbre cible.

Par défaut, la modification du type de propagation affecte uniquement le montage target. Si l'indicateur MS_REC est également spécifié dans mountflags, alors le type de propagation de tous les montages sous target est également modifié.

Pour plus de détails sur les types de propagation des montages (y compris le type de propagation par défaut attribué aux nouveaux montages), voir mount_namespaces(7).

Déplacement d'un montage

Si mountflags contient l'indicateur MS_MOVE (disponible depuis Linux 2.4.18), alors déplacez un sous-arbre : source spécifie un montage existant et target spécifie le nouvel emplacement où ce montage doit être déplacé. Le déplacement est atomique : à aucun moment le sous-arbre n'est démonté.

Les bits restants dans l'argument mountflags sont ignorés, tout comme les arguments filesystemtype et data.

Création d'un nouveau montage

Si aucun des indicateurs MS_REMOUNT, MS_BIND, MS_MOVE, MS_SHARED, MS_PRIVATE, MS_SLAVE ou MS_UNBINDABLE n'est spécifié dans mountflags, alors mount() effectue son action par défaut : la création d'un nouveau montage. source spécifie la source du nouveau montage, et target spécifie le répertoire où créer le point de montage.

Les arguments filesystemtype et data sont utilisés, et d'autres bits peuvent être spécifiés dans mountflags pour modifier le comportement de l'appel.

VALEUR DE RETOUR

En cas de succès, zéro est retourné. En cas d'erreur, -1 est retourné, et errno est défini pour indiquer l'erreur.

ERREURS

Les valeurs d'erreur données ci-dessous résultent d'erreurs indépendantes du type de système de fichiers. Chaque type de système de fichiers peut avoir ses propres erreurs spéciales et son propre comportement spécial. Voir le code source du noyau Linux pour plus de détails.

EACCES
Un composant d'un chemin n'était pas accessible en lecture. (Voir aussi path_resolution(7).)
EACCES

Le système de fichiers peut être en lecture seule pour diverses raisons, notamment : il réside sur un disque optique en lecture seule ; il réside sur un périphérique avec un commutateur physique qui a été réglé pour marquer le périphérique comme étant en lecture seule ; l'implémentation du système de fichiers a été compilée avec le support en lecture seule ; ou des erreurs ont été détectées lors du montage initial du système de fichiers, de sorte qu'il a été marqué en lecture seule et ne peut pas être remonté en lecture-écriture (jusqu'à ce que les erreurs soient corrigées).
Certains systèmes de fichiers renvoient à la place l'erreur EROFS lors d'une tentative de montage d'un système de fichiers en lecture seule.

HISTORIQUE

Les définitions de MS_DIRSYNC, MS_MOVE, MS_PRIVATE, MS_REC, MS_RELATIME, MS_SHARED, MS_SLAVE, MS_STRICTATIME, et MS_UNBINDABLE ont été ajoutées aux en-têtes glibc dans glibc 2.12.

Depuis Linux 2.4, un seul système de fichiers peut être monté à plusieurs points de montage, et plusieurs montages peuvent être empilés sur le même point de montage.

L'argument mountflags peut avoir le nombre magique 0xC0ED (MS_MGC_VAL) dans les 16 bits supérieurs. (Tous les autres drapeaux décrits dans la DESCRIPTION occupent les 16 bits de poids faible de mountflags.) La spécification de MS_MGC_VAL était requise avant Linux 2.4, mais depuis Linux 2.4 elle n'est plus requise et est ignorée si spécifiée.

Le drapeau original MS_SYNC a été renommé MS_SYNCHRONOUS en 1.1.69 lorsqu'un autre MS_SYNC a été ajouté à <mman.h>.

Avant Linux 2.4, une tentative d'exécution d'un programme set-user-ID ou set-group-ID sur un système de fichiers monté avec MS_NOSUID échouait avec EPERM. Depuis Linux 2.4, les bits set-user-ID et set-group-ID sont simplement ignorés silencieusement dans ce cas.

NOTES

Espaces de noms de montage

À partir de Linux 2.4.19, Linux fournit des espaces de noms de montage. Un espace de noms de montage est l'ensemble des montages de système de fichiers visibles pour un processus. Les espaces de noms de montage peuvent être (et sont généralement) partagés entre plusieurs processus, et les modifications apportées à l'espace de noms (c'est-à-dire, les montages et démontages) par un processus sont visibles pour tous les autres processus partageant le même espace de noms. (La situation avant 2.4.19 sous Linux peut être considérée comme un seul espace de noms partagé par tous les processus du système.)

Un processus enfant créé par fork(2) partage l'espace de noms de montage de son parent ; l'espace de noms de montage est préservé lors d'un execve(2).

Un processus peut obtenir un espace de noms de montage privé si : il a été créé à l'aide du drapeau clone(2) CLONE_NEWNS, auquel cas son nouvel espace de noms est initialisé pour être une copie de l'espace de noms du processus qui a appelé clone(2) ; ou il appelle unshare(2) avec le drapeau CLONE_NEWNS, ce qui amène l'espace de noms de montage de l'appelant à obtenir une copie privée de l'espace de noms qu'il partageait auparavant avec d'autres processus, de sorte que les futurs montages et démontages de l'appelant soient invisibles aux autres processus (sauf aux processus enfants que l'appelant crée ensuite) et vice versa.

Pour plus de détails sur les espaces de noms de montage, voir mount_namespaces(7).

Relation parentale entre les montages

Chaque montage a un montage parent. La relation parentale globale de tous les montages définit la hiérarchie de répertoires unique vue par les processus dans un espace de noms de montage.

Le parent d'un nouveau montage est défini lors de la création du montage. Dans le cas habituel, le parent d'un nouveau montage est le montage du système de fichiers contenant le répertoire ou le fichier auquel le nouveau montage est attaché. Dans le cas où un nouveau montage est empilé sur un montage existant, le parent du nouveau montage est le montage précédent qui était empilé à cet emplacement.

La relation parentale entre les montages peut être découverte via le fichier /proc/pid/mountinfo (voir ci-dessous).

/proc/pid/mounts et /proc/pid/mountinfo

Le fichier /proc/pid/mounts, spécifique à Linux, expose la liste des montages dans l'espace de noms de montage du processus avec l'identifiant spécifié. Le fichier /proc/pid/mountinfo expose encore plus d'informations sur les montages, y compris le type de propagation et les informations d'ID de montage qui permettent de découvrir la relation parentale entre les montages. Voir proc(5) et mount_namespaces(7) pour les détails de ce fichier.
