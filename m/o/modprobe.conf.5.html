MODPROBE.D(5) modprobe.d MODPROBE.D(5)

NOM

modprobe.d - Répertoire de configuration pour modprobe

SYNOPIS

/etc/modprobe.d/*.conf

/run/modprobe.d/*.conf

/usr/local/lib/modprobe.d/*.conf

/usr/lib/modprobe.d/*.conf

/lib/modprobe.d/*.conf

DESCRIPTION

Comme la commande modprobe peut ajouter ou supprimer plusieurs modules, en raison des dépendances des modules, nous avons besoin d'une méthode pour spécifier quelles options doivent être utilisées avec ces modules. On peut également les utiliser pour créer des alias pratiques : des noms alternatifs pour un module, ou ils peuvent remplacer complètement le comportement normal de modprobe pour ceux qui ont des besoins spéciaux (tels que l'insertion de plusieurs modules).

Notez que les noms de modules et d'alias (comme les autres noms de modules) peuvent comporter des tirets (-) ou des underscores (\_) : les deux sont interchangeables dans toutes les commandes de modules car la conversion des underscores se fait automatiquement.

FORMAT DE CONFIGURATION

Les fichiers de configuration contiennent une commande par ligne, les lignes vides et celles commençant par '#' étant ignorées (utile pour ajouter des commentaires). Un '\' à la fin d'une ligne provoque sa continuation sur la ligne suivante, ce qui rend les fichiers un peu plus nets.

Voir la section COMMANDES ci-dessous pour plus de détails.

RÉPERTOIRES DE CONFIGURATION ET PRÉCÉDENCE

Les fichiers de configuration sont lus à partir des répertoires listés dans SYNOPIS dans cet ordre de priorité. Une fois qu'un fichier portant un nom de fichier donné est chargé, tout fichier portant le même nom dans les répertoires suivants est ignoré.

Tous les fichiers de configuration sont triés par ordre lexicographique, quel que soit le répertoire dans lequel ils se trouvent. Les fichiers de configuration peuvent être complètement remplacés (en ayant un nouveau fichier de configuration portant le même nom dans un répertoire de priorité supérieure) ou partiellement remplacés (en ayant un fichier de configuration qui est classé plus tard).

NOTE : Les répertoires de configuration peuvent être modifiés via la variable d'environnement MODPROBE_OPTIONS. Voir la section ENVIRONNEMENT dans modprobe(8).

COMMANDES

alias wildcard nom_module

Cela vous permet de donner des noms alternatifs pour un module. Par exemple : « alias my-mod really_long_modulename » signifie que vous pouvez utiliser « modprobe my-mod » au lieu de « modprobe really_long_modulename ». Vous pouvez également utiliser des jokers de style shell, donc « alias my-mod* really_long_modulename » signifie que « modprobe my-mod-something » a le même effet. Vous ne pouvez pas avoir d'alias vers d'autres alias (cela mène à la folie), mais les alias peuvent avoir des options, qui seront ajoutées à toutes les autres options.

Notez que les modules peuvent également contenir leurs propres alias, que vous pouvez voir à l'aide de modinfo. Ces alias sont utilisés en dernier recours (c'est-à-dire s'il n'y a pas de vrai module, de commande install, remove ou alias dans la configuration).

blacklist nom_module

Les modules peuvent contenir leurs propres alias : généralement, ce sont des alias décrivant les périphériques qu'ils prennent en charge, tels que « pci:123... ». Ces alias « internes » peuvent être remplacés par des mots-clés « alias » normaux, mais il y a des cas où deux modules ou plus prennent en charge les mêmes périphériques, ou un module prétend à tort prendre en charge un périphérique qu'il ne prend pas en charge : le mot-clé blacklist indique que tous les alias internes de ce module particulier doivent être ignorés.

install nom_module commande...

Cette commande demande à modprobe d'exécuter votre commande au lieu d'insérer le module dans le noyau normalement. La commande peut être n'importe quelle commande shell : cela vous permet d'effectuer tout traitement complexe que vous pourriez souhaiter. Par exemple, si le module « fred » fonctionne mieux avec le module « barney » déjà installé (mais il n'en dépend pas, donc modprobe ne le chargera pas automatiquement), vous pourriez dire « install fred /sbin/modprobe barney; /sbin/modprobe --ignore-install fred », ce qui ferait ce que vous vouliez. Notez --ignore-install, qui empêche le second modprobe d'exécuter la même commande install à nouveau. Voir aussi remove ci-dessous.

L'avenir à long terme de cette commande en tant que solution au problème de fourniture de dépendances de modules supplémentaires n'est pas assuré et il est prévu de remplacer cette commande par un avertissement quant à sa suppression ou sa dépréciation éventuelle à un moment donné dans une future version. Son utilisation complique la détermination automatique des dépendances de modules par les utilitaires de distribution, tels que mkinitrd (car ceux-ci doivent maintenant interpréter d'une manière ou d'une autre ce que les commandes install pourraient faire. Dans un monde parfait, les modules fourniraient toutes les informations de dépendance sans utiliser cette commande et des travaux sont en cours pour implémenter le support des dépendances douces au sein du noyau Linux.

Si vous utilisez la chaîne « $CMDLINE_OPTS » dans la commande, elle sera remplacée par toutes les options spécifiées sur la ligne de commande de modprobe. Cela peut être utile car les utilisateurs s'attendent à ce que « modprobe fred opt=1 » passe l'argument « opt=1 » au module, même s'il y a une commande install dans le fichier de configuration. Donc, notre exemple ci-dessus devient « install fred /sbin/modprobe barney; /sbin/modprobe --ignore-install fred $CMDLINE_OPTS »

options nom_module option...

Cette commande permet d'ajouter des options au module nom_module (qui peut être un alias) chaque fois qu'il est inséré dans le noyau : que ce soit directement (en utilisant modprobe nom_module) ou parce que le module inséré dépend de ce module.

Toutes les options sont additionnées : elles peuvent provenir d'une commande option pour le module lui-même, pour un alias, et sur la ligne de commande.

remove nom_module commande...

Ceci est similaire à la commande install ci-dessus, sauf qu'elle est appelée lorsque « modprobe -r » est exécuté.

softdep nom_module pre: modules... post: modules...

La commande softdep permet de spécifier des dépendances de modules douces, ou optionnelles. nom_module peut être utilisé sans ces modules optionnels installés, mais généralement avec certaines fonctionnalités manquantes. Par exemple, un pilote pour une HBA de stockage pourrait nécessiter qu'un autre module soit chargé afin d'utiliser les fonctionnalités de gestion.

Les modules pre-deps et post-deps sont des listes de noms et/ou d'alias d'autres modules que modprobe tentera d'installer (ou de supprimer) en premier et après le module principal donné dans l'argument nom_module.

Exemple : Supposons que « softdep c pre: a b post: d e » soit fourni dans la configuration. L'exécution de « modprobe c » équivaut maintenant à « modprobe a b c d e » sans le softdep. Les drapeaux tels que --use-blacklist sont appliqués à tous les modules spécifiés, tandis que les paramètres du module ne s'appliquent qu'au module c.

Note : s'il existe des commandes install ou remove avec le même argument nom_module, softdep a la priorité.

weakdep nom_module modules...

La commande weakdep permet de spécifier des dépendances de modules faibles. Celles-ci sont similaires aux pré-softdeps, à la différence que l'espace utilisateur n'essaie pas de charger cette dépendance avant le module spécifié. Au lieu de cela, le noyau peut demander un ou plusieurs d'entre eux lors de la sonde du module, en fonction du matériel auquel il se lie. Le but des modules faibles est de permettre à un pilote de spécifier qu'une certaine dépendance peut être nécessaire, afin qu'elle soit présente dans le système de fichiers (par exemple, dans initramfs) lorsque ce module est sondé.

Exemple : Supposons « weakdep c a b ». Un programme créant un initramfs sait qu'il doit ajouter a, b et c au système de fichiers car a et b peuvent être nécessaires/désirés à l'exécution. Lorsque c est chargé et qu'il est sondé, il peut émettre des appels à request_module() provoquant également le chargement de a ou b.

COMPATIBILITÉ

Une future version de kmod viendra avec un avertissement fort pour éviter l'utilisation de la commande install comme expliqué ci-dessus. Cela se produira une fois que le support des dépendances douces dans le noyau sera complet. Ce support complétera le support softdep existant au sein de cet utilitaire en fournissant ces dépendances directement dans les modules.
