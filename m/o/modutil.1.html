MODUTIL(1) Outils de sécurité NSS MODUTIL(1)

NOM

modutil - Gérer les informations des modules PKCS #11 dans la base de données des modules de sécurité.

SYNTAXE

modutil [options] [[arguments]]

STATUT

Cette documentation est encore en cours de développement. Merci de contribuer à l'examen initial dans le bug 836477 de Mozilla NSS[1]

DESCRIPTION

L'outil de base de données de modules de sécurité, modutil, est un utilitaire en ligne de commande permettant de gérer les informations des modules PKCS #11 à la fois dans les fichiers secmod.db et dans les jetons matériels. modutil peut ajouter et supprimer des modules PKCS #11, changer les mots de passe des bases de données de sécurité, définir des valeurs par défaut, lister le contenu des modules, activer ou désactiver des slots, activer ou désactiver la conformité FIPS 140-2, et assigner des fournisseurs par défaut pour les opérations cryptographiques. Cet outil peut également créer des fichiers de bases de données de sécurité pour les certificats, les clés et les modules.

Les tâches associées à la gestion des bases de données de modules de sécurité font partie d'un processus qui implique généralement également la gestion des bases de données de clés et des bases de données de certificats.

OPTIONS

L'exécution de modutil nécessite toujours une (et une seule) option pour spécifier le type d'opération du module. Chaque option peut prendre des arguments, allant de zéro à plusieurs arguments.

Options

-add nom_module

Ajoute le module PKCS #11 nommé à la base de données. Utilisez cette option avec les arguments -libfile, -ciphers et -mechanisms.

-changepw nom_jeton

Change le mot de passe sur le jeton nommé. Si le jeton n'a pas été initialisé, cette option initialise le mot de passe. Utilisez cette option avec les arguments -pwfile et -newpwfile. Un mot de passe équivaut à un numéro d'identification personnel (PIN).

-chkfips

Vérifie si le module est dans le mode FIPS donné. true signifie vérifier que le module est en mode FIPS, tandis que false signifie vérifier que le module n'est pas en mode FIPS.

-create

Crée de nouvelles bases de données de certificats, de clés et de modules. Utilisez l'argument de répertoire -dbdir pour spécifier un répertoire. Si l'une de ces bases de données existe déjà dans un répertoire spécifié, modutil renvoie un message d'erreur.

-default nom_module

Spécifie les mécanismes de sécurité pour lesquels le module nommé sera un fournisseur par défaut. Les mécanismes de sécurité sont spécifiés avec l'argument -mechanisms.

-delete nom_module

Supprime le module nommé. Le module PKCS #11 interne par défaut de NSS ne peut pas être supprimé.

-disable nom_module

Désactive tous les slots sur le module nommé. Utilisez l'argument -slot pour désactiver un slot spécifique.

Le module PKCS #11 interne de NSS ne peut pas être désactivé.

-enable nom_module

Active tous les slots sur le module nommé. Utilisez l'argument -slot pour activer un slot spécifique.

-fips [true | false]

Active (true) ou désactive (false) la conformité FIPS 140-2 pour le module NSS par défaut.

-force

Désactive les invites interactives de modutil afin qu'il puisse être exécuté à partir d'un script. Utilisez cette option uniquement après avoir testé manuellement chaque opération prévue pour vérifier les avertissements et s'assurer que le contournement des invites ne causera aucune faille de sécurité ni perte d'intégrité de la base de données.

-jar Fichier_JAR

Ajoute un nouveau module PKCS #11 à la base de données en utilisant le fichier JAR nommé. Utilisez cette commande avec les arguments -installdir et -tempdir. Le fichier JAR utilise le format de fichier JAR PKCS #11 de NSS pour identifier tous les fichiers à installer, le nom du module, les indicateurs de mécanisme et les indicateurs de chiffrement, ainsi que tout fichier à installer sur la machine cible, y compris le fichier de bibliothèque du module PKCS #11 et d'autres fichiers tels que la documentation. Ceci est couvert dans la section du fichier d'installation JAR de la page de manuel, qui détaille le script spécial nécessaire pour effectuer une installation via un serveur ou avec modutil.

-list [nom_module]

Affiche des informations de base sur le contenu du fichier secmod.db. Spécifier un nom_module affiche des informations détaillées sur un module particulier et ses slots et jetons.

-rawadd

Ajoute la chaîne de spécification du module à la base de données secmod.db.

-rawlist

Affiche les spécifications du module pour un module spécifié ou pour tous les modules chargeables.

-undefault nom_module

Spécifie les mécanismes de sécurité pour lesquels le module nommé ne sera pas un fournisseur par défaut. Les mécanismes de sécurité sont spécifiés avec l'argument -mechanisms.

Arguments

MODULE

Donne le module de sécurité à accéder.

MODULESPEC

Donne la spécification du module de sécurité à charger dans la base de données de sécurité.

-ciphers liste_activation_chiffrement

Active des chiffrements spécifiques dans un module qui est ajouté à la base de données. La liste_activation_chiffrement est une liste de noms de chiffrements délimités par des deux-points. Encadrez cette liste entre guillemets si elle contient des espaces.

-dbdir répertoire

Spécifie le répertoire de base de données dans lequel accéder ou créer les fichiers de base de données des modules de sécurité.

modutil prend en charge deux types de bases de données : les bases de données de sécurité héritées (cert8.db, key3.db et secmod.db) et les bases de données SQLite (cert9.db, key4.db et pkcs11.txt). Si le préfixe dbm: n'est pas utilisé, l'outil suppose que les bases de données fournies sont au format SQLite.

--dbprefix préfixe

Spécifie le préfixe utilisé sur les fichiers de base de données, par exemple my_ pour my_cert9.db. Cette option est fournie comme cas spécial. Il n'est pas recommandé de changer les noms des bases de données de certificats et de clés.

-installdir répertoire_installation_racine

Spécifie le répertoire d'installation racine par rapport auquel les fichiers seront installés par l'option -jar. Ce répertoire doit être celui en dessous duquel il est approprié de stocker des fichiers de bibliothèque dynamique, comme le répertoire racine d'un serveur.

-libfile fichier_bibliothèque

Spécifie le chemin d'accès à un fichier bibliothèque contenant l'implémentation de l'interface module PKCS #11 qui est ajoutée à la base de données.

-mechanisms liste_mécanismes

Spécifie les mécanismes de sécurité pour lesquels un module particulier sera marqué comme fournisseur par défaut. La liste_mécanismes est une liste de noms de mécanismes délimités par des deux-points. Encadrez cette liste entre guillemets si elle contient des espaces.

Le module devient un fournisseur par défaut pour les mécanismes listés lorsque ces mécanismes sont activés. Si plus d'un module revendique être le fournisseur par défaut d'un mécanisme particulier, le fournisseur par défaut de ce mécanisme est indéfini.

modutil prend en charge plusieurs mécanismes : RSA, DSA, RC2, RC4, RC5, AES, DES, DH, SHA1, SHA256, SHA512, SSL, TLS, MD5, MD2, RANDOM (pour la génération de nombres aléatoires) et FRIENDLY (signifiant que les certificats sont lisibles publiquement).

-newpwfile fichier_nouveau_mot_de_passe

Spécifie un fichier texte contenant le nouveau mot de passe ou le mot de passe de remplacement d'un jeton afin qu'un mot de passe puisse être entré automatiquement avec l'option -changepw.

-nocertdb

N'ouvre pas les bases de données de certificats ou de clés. Cela a plusieurs effets :
•Avec la commande -create, seul un fichier de sécurité de module est créé ; les bases de données de certificats et de clés ne sont pas créées.
•Avec la commande -jar, les signatures sur le fichier JAR ne sont pas vérifiées.
•Avec la commande -changepw, le mot de passe du module interne NSS ne peut pas être défini ou modifié, car ce mot de passe est stocké dans la base de données des clés.

-pwfile fichier_ancien_mot_de_passe

Spécifie un fichier texte contenant le mot de passe existant d'un jeton afin qu'un mot de passe puisse être entré automatiquement lorsque l'option -changepw est utilisée pour changer les mots de passe.

-secmod nom_secmod

Donne le nom de la base de données du module de sécurité (comme secmod.db) à charger.

-slot nom_slot

Spécifie un slot particulier à activer ou désactiver avec les options -enable ou -disable.

-string CHAÎNE_CONFIG

Passe une chaîne de configuration pour le module en cours d'ajout à la base de données.

-tempdir répertoire_temporaire

Donne un emplacement de répertoire où les fichiers temporaires sont créés lors de l'installation par l'option -jar. Si aucun répertoire temporaire n'est spécifié, le répertoire courant est utilisé.

UTILISATION ET EXEMPLES

Création de fichiers de base de données

Avant que toute opération puisse être effectuée, un ensemble de bases de données de sécurité doit être disponible. modutil peut être utilisé pour créer ces fichiers. L'unique argument requis est le répertoire où les bases de données seront situées.

modutil -create -dbdir répertoire

Ajout d'un module cryptographique

L'ajout d'un module PKCS #11 implique la soumission d'un fichier de bibliothèque de support, l'activation de ses chiffrements et la définition du statut de fournisseur par défaut pour divers mécanismes de sécurité. Cela peut être fait en fournissant toutes les informations directement via modutil ou en exécutant un fichier JAR et un script d'installation. Pour le cas le plus basique, il suffit de télécharger la bibliothèque :

modutil -add nom-module -libfile fichier-bibliothèque [-ciphers liste-chiffrements-activés] [-mechanisms liste-mécanismes]

Par exemple :

modutil -dbdir /home/my/sharednssdb -add "Exemple de Module PKCS #11" -libfile "/tmp/crypto.so" -mechanisms RSA:DSA:RC2:RANDOM 
Utilisation du répertoire de base de données... 
Module "Exemple de Module PKCS #11" ajouté à la base de données.

Installation d'un module cryptographique à partir d'un fichier JAR

Les modules PKCS #11 peuvent également être chargés à l'aide d'un fichier JAR, qui contient toutes les bibliothèques requises et un script d'installation décrivant comment installer le module. Le script d'installation JAR est décrit plus en détail dans la section intitulée « FORMAT DU FICHIER D'INSTALLATION JAR ».

Le script d'installation JAR définit les informations de configuration pour chaque plateforme sur laquelle le module peut être installé. Par exemple :

Platforms { 
   Linux:5.4.08:x86 { 
      ModuleName { "Exemple de Module PKCS #11" } 
      ModuleFile { crypto.so } 
      DefaultMechanismFlags{0x0000} 
      CipherEnableFlags{0x0000} 
      Files { 
         crypto.so { 
            Path{ /tmp/crypto.so } 
         } 
         setup.sh { 
            Executable 
            Path{ /tmp/setup.sh } 
         } 
      } 
   } 
   Linux:6.0.0:x86 { 
      EquivalentPlatform { Linux:5.4.08:x86 } 
   } 
}

Le script d'installation et les bibliothèques requises doivent être regroupés dans un fichier JAR, spécifié avec l'argument -jar.

modutil -dbdir /home/my/sharednssdb -jar install.jar -installdir /home/my/sharednssdb

Ajout d'une spécification de module

Chaque module possède des informations stockées dans la base de données de sécurité concernant sa configuration et ses paramètres. Celles-ci peuvent être ajoutées ou modifiées à l'aide de la commande -rawadd. Pour les paramètres actuels ou pour voir le format de la spécification du module dans la base de données, utilisez l'option -rawlist.

modutil -rawadd spécification-module

Suppression d'un module

Un module PKCS #11 spécifique peut être supprimé de la base de données secmod.db :

modutil -delete nom-module -dbdir répertoire

Affichage des informations sur les modules

La base de données secmod.db contient des informations sur les modules PKCS #11 disponibles pour une application ou un serveur. La liste de tous les modules, des informations sur des modules spécifiques et des spécifications de configuration de base de données pour les modules peuvent être consultées.

Pour simplement obtenir une liste des modules dans la base de données, utilisez la commande -list.

modutil -list [nom-module] -dbdir répertoire

La liste des modules affiche le nom du module, son statut et d'autres bases de données de sécurité associées pour les certificats et les clés. Par exemple :

Définition d'un fournisseur par défaut pour les mécanismes de sécurité

Plusieurs modules de sécurité peuvent fournir une prise en charge des mêmes mécanismes de sécurité. Il est possible de définir un module de sécurité spécifique comme fournisseur par défaut pour un mécanisme de sécurité spécifique (ou, inversement, d'interdire à un fournisseur de fournir ces mécanismes).

modutil -default nom-module -mechanisms liste-mécanismes

Pour définir un module comme fournisseur par défaut pour les mécanismes, utilisez la commande -default avec une liste de mécanismes séparés par des deux-points. Les mécanismes disponibles dépendent du module ; NSS fournit presque tous les mécanismes courants. Par exemple :

modutil -default "Module PKCS #11 Interne NSS" -dbdir -mechanisms RSA:DSA:RC2 
Utilisation du répertoire de base de données c:\databases...
Défauts modifiés avec succès.

La suppression du fournisseur par défaut utilise le même format :

modutil -undefault "Module PKCS #11 Interne NSS" -dbdir -mechanisms MD2:MD5

Activation et désactivation de modules et de slots

Les modules, et les slots spécifiques sur les modules, peuvent être sélectivement activés ou désactivés à l'aide de modutil. Les deux commandes ont le même format :

modutil -enable|-disable nom-module [-slot nom-slot]

Par exemple :

modutil -enable "Module PKCS #11 Interne NSS" -slot "Services Cryptographiques Internes NSS                            " -dbdir .
Slot "Services Cryptographiques Internes NSS                            " activé.

Assurez-vous que la quantité appropriée d'espaces blancs de fin se trouve après le nom du slot. Certains noms de slot comportent une quantité importante d'espaces blancs qui doit être incluse, sinon l'opération échouera.

Activation et vérification de la conformité FIPS

La conformité FIPS 140-2 des modules NSS peut être activée ou désactivée à l'aide de modutil avec l'option -fips. Par exemple :

modutil -fips true -dbdir /home/my/sharednssdb/
Mode FIPS activé.

Pour vérifier le statut du mode FIPS, exécutez la commande -chkfips avec un indicateur vrai ou faux (peu importe lequel). L'outil renvoie le réglage FIPS actuel.

modutil -chkfips false -dbdir /home/my/sharednssdb/
Mode FIPS activé.

Modification du mot de passe d'un jeton

Initialisation ou modification du mot de passe d'un jeton :

modutil -changepw nom-jeton [-pwfile fichier-ancien-mot-de-passe] [-newpwfile fichier-nouveau-mot-de-passe]

FORMAT DU FICHIER D'INSTALLATION JAR

Lorsqu'un fichier JAR est exécuté par un serveur, par modutil, ou par tout programme qui n'interprète pas JavaScript, un fichier d'informations spécial doit être inclus pour installer les bibliothèques. Il y a plusieurs points à garder à l'esprit concernant ce fichier :

•Il doit être déclaré dans le fichier manifeste de l'archive JAR.
•Le script peut porter n'importe quel nom.
•La balise meta-info pour cela est Pkcs11_install_script. Pour déclarer des méta-informations dans le fichier manifeste, placez-les dans un fichier qui est passé à signtool.

Exemple de script

Par exemple, le script d'installation PKCS #11 pourrait être dans le fichier pk11install. Si c'est le cas, le fichier meta-info pour signtool inclut une ligne telle que celle-ci :

+ Pkcs11_install_script: pk11install

Le script doit définir la plateforme et le numéro de version, le nom et le fichier du module, et toute information facultative telle que les chiffrements et mécanismes pris en charge. Plusieurs plateformes peuvent être définies dans un seul fichier d'installation.

ForwardCompatible { IRIX:6.2:mips SUNOS:5.5.1:sparc }
Platforms {
   WINNT::x86 {
      ModuleName { "Exemple de module" }
      ModuleFile { win32/fort32.dll }
      DefaultMechanismFlags{0x0001}
      DefaultCipherFlags{0x0001}
      Files {
         win32/setup.exe {
            Executable
            RelativePath { %temp%/setup.exe }
         }
         win32/setup.hlp {
            RelativePath { %temp%/setup.hlp }
         }
         win32/setup.cab {
            RelativePath { %temp%/setup.cab }
         }
      }
   }
   SUNOS:5.5.1:sparc {
      ModuleName { "Exemple de module UNIX" }
      ModuleFile { unix/fort.so }
      DefaultMechanismFlags{0x0001}
      CipherEnableFlags{0x0001}
      Files {
         unix/fort.so {
            RelativePath{%root%/lib/fort.so}
            AbsolutePath{/usr/local/netscape/lib/fort.so}
            FilePermissions{555}
         }
         xplat/instr.html {
            RelativePath{%root%/docs/inst.html}
            AbsolutePath{/usr/local/netscape/docs/inst.html}
            FilePermissions{555}
         }
      }
   }
   IRIX:6.2:mips {
      EquivalentPlatform { SUNOS:5.5.1:sparc }
   }
}

Grammaire du script

Le script est du Java de base, autorisant les listes, les paires clé-valeur, les chaînes de caractères et les combinaisons de tous ceux-ci.

--> valuelist
valuelist --> value valuelist
               <null>
value ---> key_value_pair
            string
key_value_pair --> key { valuelist }
key --> string
string --> simple_string
            "complex_string"
simple_string --> [^ \t\n\""{""}"]+ 
complex_string --> ([^\"\\\r\n]|(\\\")|(\\\\))+

Les guillemets et les barres obliques inverses doivent être échappés avec une barre oblique inverse. Une chaîne complexe ne doit pas contenir de sauts de ligne ou de retours chariot. En dehors des chaînes complexes, tous les espaces blancs (par exemple, espaces, tabulations et retours chariot) sont considérés comme égaux et sont utilisés uniquement pour délimiter les jetons.

Clés

Le fichier d'installation Java utilise des clés pour définir les informations de plateforme et de module.

ForwardCompatible donne une liste de plateformes compatibles avec les versions futures. Si la plateforme actuelle ne se trouve pas dans la liste des plateformes prises en charge, la liste ForwardCompatible est vérifiée pour toute plateforme ayant le même système d'exploitation et la même architecture dans une version antérieure. Si une plateforme est trouvée, ses attributs sont utilisés pour la plateforme actuelle.

Platforms (obligatoire) Donne une liste de plateformes. Chaque entrée de la liste est elle-même une paire clé-valeur : la clé est le nom de la plateforme et la liste de valeurs contient divers attributs de la plateforme. La chaîne de plateforme est au format nom du système:version du système d'exploitation:architecture. L'installateur obtient ces valeurs de NSPR. La version du système d'exploitation est une chaîne vide sur les systèmes d'exploitation non Unix. NSPR prend en charge ces plateformes :

•AIX (rs6000)
•BSDI (x86)
•FREEBSD (x86)
•HPUX (hppa1.1)
•IRIX (mips)
•LINUX (ppc, alpha, x86)
•MacOS (PowerPC)
•NCR (x86)
•NEC (mips)
•OS2 (x86)
•OSF (alpha)
•ReliantUNIX (mips)
•SCO (x86)
•SOLARIS (sparc)
•SONY (mips)
•SUNOS (sparc)
•UnixWare (x86)
•WIN16 (x86)
•WIN95 (x86)
•WINNT (x86)

Par exemple :

IRIX:6.2:mips
SUNOS:5.5.1:sparc
Linux:2.0.32:x86
WIN95::x86

Les informations du module sont définies indépendamment pour chaque plateforme dans les attributs ModuleName, ModuleFile et Files. Ces attributs doivent être spécifiés, sauf si un attribut EquivalentPlatform est fourni.

Clés par plateforme

Les clés par plateforme n'ont de sens qu'à l'intérieur de la liste de valeurs d'une entrée de la liste Platforms.

ModuleName (obligatoire) donne le nom commun du module. Ce nom est utilisé pour référencer le module par les serveurs et par l'outil modutil.

ModuleFile (obligatoire) nomme le fichier du module PKCS #11 pour cette plateforme. Le nom est donné comme le chemin relatif du fichier dans l'archive JAR.

Files (obligatoire) liste les fichiers qui doivent être installés pour ce module. Chaque entrée de la liste de fichiers est une paire clé-valeur. La clé est le chemin du fichier dans l'archive JAR, et la liste de valeurs contient les attributs du fichier. Au moins RelativePath ou AbsolutePath doit être spécifié pour chaque fichier.

DefaultMechanismFlags spécifie les mécanismes pour lesquels ce module est le fournisseur par défaut ; cela équivaut à l'option -mechanism avec la commande -add. Cette paire clé-valeur est une chaîne de bits spécifiée au format hexadécimal (0x). Elle est construite comme un OU binaire. Si l'entrée DefaultMechanismFlags est omise, la valeur par défaut est 0x0.

RSA:                   0x00000001
DSA:                   0x00000002
RC2:                   0x00000004
RC4:                   0x00000008
DES:                   0x00000010
DH:                    0x00000020
FORTEZZA:              0x00000040
RC5:                   0x00000080
SHA1:                  0x00000100
MD5:                   0x00000200
MD2:                   0x00000400
RANDOM:                0x08000000
FRIENDLY:              0x10000000
OWN_PW_DEFAULTS:       0x20000000
DISABLE:               0x40000000

CipherEnableFlags spécifie les chiffrements que ce module fournit et que NSS ne fournit pas (afin que le module active ces chiffrements pour NSS). Ceci équivaut à l'argument -cipher avec la commande -add. Cette clé est une chaîne de bits spécifiée au format hexadécimal (0x). Elle est construite comme un OU binaire. Si l'entrée CipherEnableFlags est omise, la valeur par défaut est 0x0.

EquivalentPlatform spécifie que les attributs de la plateforme nommée doivent également être utilisés pour la plateforme actuelle. Cela facilite les choses lorsque plus d'une plateforme utilise les mêmes paramètres.

Clés par fichier

Certaines clés n'ont de sens qu'à l'intérieur de la liste de valeurs d'une entrée d'une liste Files.

Chaque fichier nécessite une clé de chemin qui identifie où se trouve le fichier. Soit RelativePath soit AbsolutePath doit être spécifié. Si les deux sont spécifiés, le chemin relatif est essayé en premier, et le chemin absolu est utilisé seulement si aucun répertoire racine relatif n'est fourni par le programme d'installation.

RelativePath spécifie le répertoire de destination du fichier, relatif à un répertoire déterminé au moment de l'installation. Deux variables peuvent être utilisées dans le chemin relatif : %root% et %temp%. %root% est remplacé à l'exécution par le répertoire par rapport auquel les fichiers doivent être installés ; par exemple, il peut s'agir du répertoire racine du serveur. Le répertoire %temp% est créé au début de l'installation et détruit à la fin. Le but de %temp% est de contenir les fichiers exécutables (tels que les programmes d'installation) ou les fichiers utilisés par ces programmes. Les fichiers destinés au répertoire temporaire sont garantis d'être en place avant que tout fichier exécutable ne soit exécuté ; ils ne sont pas supprimés tant que tous les fichiers exécutables n'ont pas terminé.

AbsolutePath spécifie le répertoire de destination du fichier sous forme de chemin absolu.

Executable spécifie que le fichier doit être exécuté pendant le processus d'installation. Typiquement, cette chaîne est utilisée pour un programme d'installation fourni par un fournisseur de module, tel qu'un exécutable d'installation auto-extractible. Plus d'un fichier peut être spécifié comme exécutable, auquel cas les fichiers sont exécutés dans l'ordre dans lequel ils sont spécifiés dans le fichier script.

FilePermissions définit les permissions sur tous les fichiers référencés dans une chaîne de chiffres octaux, selon le format Unix standard. Cette chaîne est un OU binaire.

lecture utilisateur:                0400
écriture utilisateur:               0200
exécution utilisateur:             0100
lecture groupe:               0040
écriture groupe:              0020
exécution groupe:            0010
lecture autre:               0004
écriture autre:              0002
exécution autre:            0001

Certaines plateformes peuvent ne pas comprendre ces permissions. Elles ne sont appliquées que dans la mesure où elles ont du sens pour la plateforme actuelle. Si cet attribut est omis, un défaut de 777 est supposé.

TYPES DE BASES DE DONNÉES NSS

NSS utilisait initialement des bases de données BerkeleyDB pour stocker les informations de sécurité. Les dernières versions de ces bases de données héritées sont :

•cert8.db pour les certificats
•key3.db pour les clés
•secmod.db pour les informations de module PKCS #11

Cependant, BerkeleyDB présente des limitations de performance, ce qui empêche son utilisation facile par plusieurs applications simultanément. NSS offre une certaine flexibilité qui permet aux applications d'utiliser leur propre moteur de base de données indépendant tout en conservant une base de données partagée et en contournant les problèmes d'accès. Néanmoins, NSS nécessite plus de flexibilité pour fournir une base de données de sécurité véritablement partagée.

En 2009, NSS a introduit un nouvel ensemble de bases de données qui sont des bases de données SQLite plutôt que BerkleyDB. Ces nouvelles bases de données offrent une meilleure accessibilité et performance :

•cert9.db pour les certificats
•key4.db pour les clés
•pkcs11.txt, qui est la liste de tous les modules PKCS #11 contenus dans un nouveau sous-répertoire dans le répertoire des bases de données de sécurité

Étant donné que les bases de données SQLite sont conçues pour être partagées, il s'agit du type de base de données partagé. Le type de base de données partagé est préféré ; le format hérité est inclus pour la compatibilité descendante.

Par défaut, les outils (certutil, pk12util, modutil) supposent que les bases de données de sécurité données utilisent le type SQLite. L'utilisation des bases de données héritées doit être spécifiée manuellement en utilisant le préfixe dbm: avec le répertoire de sécurité donné. Par exemple :

modutil -create -dbdir dbm:/home/my/sharednssdb

Pour définir le type de base de données hérité comme type par défaut pour les outils, définissez la variable d'environnement NSS_DEFAULT_DB_TYPE sur dbm :

export NSS_DEFAULT_DB_TYPE="dbm"

Cette ligne peut être ajoutée au fichier ~/.bashrc pour rendre le changement permanent pour l'utilisateur.

•https://wiki.mozilla.org/NSS_Shared_DB_Howto

Pour une version préliminaire d'ingénierie sur les changements dans les bases de données NSS partagées, consultez le wiki du projet NSS :

•https://wiki.mozilla.org/NSS_Shared_DB
