NOM

mbox - Format de stockage des messages électroniques.

DESCRIPTION

Ce document décrit le format traditionnellement utilisé par les hôtes Unix pour stocker localement les messages électroniques. Les fichiers mbox résident généralement dans le spool de messagerie du système, sous divers noms dans les répertoires Mail des utilisateurs, et sous le nom mbox dans les répertoires personnels des utilisateurs.

Un mbox est un fichier texte contenant un nombre arbitraire de messages électroniques. Chaque message se compose d'un cachet (postmark), suivi d'un message électronique formaté selon les RFC822, RFC2822. Le format du fichier est basé sur les lignes. Les lignes sont séparées par des caractères de saut de ligne (ASCII 10).

Une ligne de cachet se compose des quatre caractères « From », suivis d'un espace, suivis de l'adresse de l'expéditeur de l'enveloppe du message, suivis d'espaces blancs et d'un horodatage. Cette ligne est souvent appelée ligne From_.

L'adresse de l'expéditeur est attendue être un addr-spec tel que défini dans la RFC2822 3.4.1. La date est attendue être un date-time tel que produit par asctime(3). Pour des raisons de compatibilité avec les logiciels existants, les années à deux chiffres supérieures ou égales à 70 doivent être interprétées comme les années 1970+, tandis que les années à deux chiffres inférieures à 70 doivent être interprétées comme les années 2000- 2069. Les logiciels lisant des fichiers dans ce format devraient également être préparés à accepter des informations de fuseau horaire non numériques telles que « CET DST » pour l'heure d'Europe centrale, heure d'été.

Exemple :

>From example@example.com Ven 23 juin 02:56:55 2000

Afin d'éviter une mauvaise interprétation des lignes dans les corps de messages qui commencent par les quatre caractères « From », suivis d'un espace, l'agent de livraison de courrier doit échapper toute occurrence de « From » au début d'une ligne de corps en y préfixant un '>'.

Il existe deux schémas d'échappement différents, le premier (MBOXO) n'échappe que les lignes simples « From » dans le corps en préfixant un '>' à la ligne ; le second (MBOXRD) échappe également les lignes « From » déjà échappées en préfixant un '>' (c'est-à-dire « >From », « >>From », ...). Ce dernier a l'avantage que des lignes telles que

>From the command line you can use the '-p' option

ne sont pas déséchappées à tort car un MDA MBOXRD transformerait la ligne en

>>From the command line you can use the '-p' option

avant de la stocker. En plus de MBOXO et MBOXRD, il existe également MBOXCL qui est MBOXO avec un champ « Content-Length: » indiquant le nombre d'octets dans le corps du message ; certains MUA (comme neomutt(1)) transforment automatiquement les boîtes aux lettres MBOXO en MBOXCL car MBOXCL peut être lu par n'importe quel MUA MBOXO sans aucun problème.

Si l'heure de modification (généralement déterminée via stat(2)) d'un fichier mbox non vide est supérieure à l'heure d'accès, le fichier contient de nouveaux messages. De nombreux MUA placent un en-tête Status: dans chaque message pour indiquer quels messages ont déjà été lus.

VERROUILLAGE

Étant donné que les fichiers mbox sont fréquemment accédés par plusieurs programmes en parallèle, les fichiers mbox ne doivent généralement pas être accédés sans verrouillage.

Trois mécanismes de verrouillage différents (et leurs combinaisons) sont couramment utilisés :

  • Le verrouillage fcntl(2) est principalement utilisé sur les systèmes récents et conformes POSIX. L'utilisation de cette méthode de verrouillage est, en particulier, conseillée si les fichiers mbox sont accessibles via le Network File System (NFS), car elle semble être la seule façon d'invalider de manière fiable les caches des clients NFS.
  • Le verrouillage flock(2) est principalement utilisé sur les systèmes basés sur BSD.

Si plusieurs méthodes sont combinées, les implémenteurs doivent s'assurer d'utiliser les variantes non bloquantes des appels système fcntl(2) et flock(2) afin d'éviter les interblocages.

Si plusieurs méthodes sont combinées, un fichier mbox ne doit pas être considéré comme ayant été verrouillé avec succès avant que tous les verrous individuels aient été obtenus. Lorsqu'une des méthodes de verrouillage individuelles échoue, une application doit libérer tous les verrous qu'elle a acquis avec succès, et redémarrer toute la procédure de verrouillage depuis le début, après un délai approprié.

Le mécanisme de verrouillage utilisé sur un système particulier est une question de politique locale, et doit être utilisé de manière cohérente par toutes les applications installées sur le système qui accèdent aux fichiers mbox. Ne pas le faire peut entraîner une perte de données de courrier électronique et des fichiers mbox corrompus.

FICHIERS

/var/spool/mail/$LOGNAME

Dossier de messagerie entrante de $LOGNAME.

$HOME/mbox

Messages électroniques archivés de l'utilisateur, dans son répertoire $HOME.

$HOME/Mail/

Un répertoire dans le répertoire $HOME de l'utilisateur qui est couramment utilisé pour contenir des dossiers au format mbox.
