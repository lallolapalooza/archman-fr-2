mfsscadmin - Outil d'administration des classes de stockage MooseFS

DESCRIPTION

Ceci est un ensemble d'outils pour gérer les classes de stockage MooseFS. Les classes de stockage sont utilisées pour définir la politique de redondance au sein du cluster. Elles doivent ensuite être appliquées à des objets MooseFS particuliers (fichiers ou dossiers) avec les outils mfssclass (voir mfssclass(1)). Une classe de stockage est un ensemble nommé d'expressions d'étiquettes et d'autres options. L'expression d'étiquettes indique le format de redondance, le niveau de redondance désiré, et la politique de stockage désirée. Le format de redondance peut être soit des copies, soit de l'effacement de codage (EC). Le niveau de redondance est soit le nombre de copies (de 1 à 9), soit le nombre de parties de données plus de parité (4+n ou 8+n), en fonction du format de redondance indiqué. La politique de stockage spécifie, par l'utilisation d'étiquettes, quels serveurs de chunks doivent être utilisés pour le stockage physique des données assignées à la classe de stockage particulière.

mfscreatesclass crée une nouvelle classe de stockage avec les options données, décrites ci-dessous, et la nomme NOM_CLASSE_STOCKAGE; plusieurs noms peuvent être fournis, plusieurs classes de stockage avec la même définition seront alors créées.

mfsmodifysclass modifie les options données dans une classe ou des classes indiquées par le(s) paramètre(s) NOM_CLASSE_STOCKAGE.

mfsdeletesclass supprime la ou les classes indiquées par le(s) paramètre(s) NOM_CLASSE_STOCKAGE; si l'une des classes n'est pas vide (c'est-à-dire qu'elle est encore utilisée par certains objets MooseFS), elle ne sera pas supprimée et l'outil renverra une erreur et un message d'erreur sera affiché; les classes vides seront supprimées dans tous les cas.

mfsclonesclass copie la classe indiquée par NOM_SRC_CLASSE_STOCKAGE sous un nouveau nom fourni avec NOM_DST_CLASSE_STOCKAGE.

mfsrenamesclass change le nom d'une classe de NOM_SRC_CLASSE_STOCKAGE à NOM_DST_CLASSE_STOCKAGE.

mfslistsclass liste toutes les classes.

mfsimportsclass importe les définitions de classes de stockage depuis stdin ou un fichier et les crée; le format d'entrée doit être identique à la sortie de mfslistsclass -l.

OPTIONS

-C paramètre optionnel, qui indique au système sur quels serveurs de chunks, définis par l'expression ETIQUETTES_CREATION, le chunk doit être écrit juste après sa création; si ce paramètre n'est pas fourni pour une classe, les serveurs de chunks ETIQUETTES_A_CONSERVER seront utilisés.

-K paramètre obligatoire, qui indique au système sur quels serveurs de chunks, définis par l'expression ETIQUETTES_A_CONSERVER, le(s) chunk(s) doivent toujours être conservé(s), sauf conditions spéciales comme la création, l'archivage et la suppression (déplacement vers la corbeille), si elles sont définies.

-A paramètre optionnel, qui indique au système sur quels serveurs de chunks, définis par l'expression ETIQUETTES_ARCHIVAGE, le(s) chunk(s) doivent être conservé(s) à des fins d'archivage; le système commence à traiter un chunk comme archive lorsque son atime/mtime/ctime (tel que défini par -o) est plus ancien que le nombre d'heures spécifié avec l'option -d; voir également la section COMPORTEMENT D'ARCHIVAGE ci-dessous.

-d paramètre optionnel qui définit après combien de temps depuis l'atime/mtime/ctime (tel que défini par -o) un fichier (et ses chunks) est traité comme archive; l'unité minimale est l'heure, la valeur par défaut est 24; pour le formatage des valeurs, voir TEMPS.

-o paramètre optionnel qui définit les drapeaux d'archive. C - ctime, M - mtime, A - atime, R - réversible, F - mode rapide, P - par chunk ; la valeur par défaut est C; voir la section COMPORTEMENT D'ARCHIVAGE pour plus de détails.

-s paramètre optionnel qui définit la longueur minimale du fichier en octets qui peut être archivée; la valeur par défaut est 0.

-T paramètre optionnel, qui indique au système sur quels serveurs de chunks, définis par l'expression ETIQUETTES_CORBEILLE, le(s) chunk(s) de fichiers dans la corbeille doivent être conservé(s); voir également -t.

-t paramètre optionnel, qui définit combien de temps dans la corbeille doit s'écouler pour que le système utilise le schéma défini dans -T pour un chunk; l'unité minimale est l'heure, la valeur par défaut est 0; pour le formatage des valeurs, voir TEMPS.

-c paramètre optionnel, qui définit une description de classe, pour la commodité de l'utilisateur (une chaîne de caractères, longueur maximale de 255 octets).

-p paramètre optionnel, qui définit une priorité de classe; la valeur par défaut est 0; voir la section PRIORITÉ DES CLASSES DE STOCKAGE.

-g paramètre optionnel, qui définit un groupe d'export de classe; les valeurs possibles sont de 0 à 15, la valeur par défaut est 0; voir mfsexport.cfg(5) pour une explication.

-a peut être soit 1 soit 0 et indique si la classe de stockage est disponible pour tout le monde (0) ou seulement pour l'administrateur (1).

-m mode d'étiquettes utilisé; les valeurs possibles sont l (ou L, loose, Loose, LOOSE) pour le mode LOOSE, d (ou D, std, Std, STD) pour le mode STANDARD et s (ou S, strict, Strict, STRICT) pour le mode STRICT; si aucun mode n'est défini, le mode STANDARD est supposé; le comportement des modes d'étiquettes est décrit ci-dessous dans la section MODES D'ÉTIQUETTES.

-l liste également les définitions, pas seulement les noms des classes de stockage existantes.

-i correspondance de nom de classe de stockage insensible à la casse.

-r remplace (écrase) les classes existantes lors de l'importation des classes de stockage.

-n utilise le nom de fichier fourni comme source des définitions de classes de stockage pour l'importation, au lieu de stdin.

-M point de montage MooseFS, il n'est pas nécessaire de le spécifier si un outil est exécuté dans un répertoire monté MooseFS ou si MooseFS est monté dans /mnt/mfs/.

-? affiche un court message d'utilisation.

NOTES

EXPRESSIONS D'ÉTIQUETTES

Les étiquettes sont des lettres (A-Z - 26 lettres) qui peuvent être attribuées aux serveurs de chunks. Chaque serveur de chunks peut avoir plusieurs (jusqu'à 26) étiquettes. Les étiquettes sont définies dans le fichier mfschunkserver.cfg, pour plus d'informations, référez-vous à la page de manuel appropriée.

Une expression d'étiquettes est un ensemble de sous-expressions séparées par des virgules. Pour des copies complètes, chaque sous-expression spécifie le schéma de stockage d'une copie d'un fichier. Une sous-expression peut être : un astérisque ou un schéma d'étiquettes. Un schéma d'étiquettes peut être une seule étiquette ou une expression avec des sommes, des multiplications, des négations et des parenthèses. La somme signifie qu'un fichier peut être stocké sur n'importe quel serveur de chunks correspondant à n'importe quel élément de la somme (ou logique). La multiplication signifie qu'un fichier ne peut être stocké que sur un serveur de chunks correspondant à tous les éléments (et logique). L'astérisque signifie n'importe quel serveur de chunks. La négation signifie n'importe quel serveur de chunks sauf celui correspondant à la sous-expression négée. Des sous-expressions identiques peuvent être raccourcies en ajoutant un nombre devant une au lieu de la répéter plusieurs fois.

Pour l'EC, l'expression d'étiquettes commence par le signe @, suivi du nombre de parties de données, puis le signe + et un nombre qui indique combien de parties de parité le chunk doit avoir. Nombre possible

4 ou 8. Les nombres possibles de parties de parité sont 1 (version CE) ou 1 à 9 (version PRO). Ainsi, par exemple, @4+1 signifie EC avec 4 parties de données et 1 partie de parité, @8+3 signifie EC avec 8 parties de données et 3 parties de parité. Si le nombre de parties de données est omis, le maître utilise la valeur par défaut définie par DEFAULT_EC_DATA_PARTS - voir mfsmaster.cfg (5). Dans ce cas, @2 signifie @8+2 ou @4+2. Ensuite, au maximum deux sous-expressions peuvent suivre, séparées par des virgules. Si une seule est présente, elle définit où toutes les parties doivent être conservées. Si les deux sont présentes, la première sous-expression définit où les parties de données doivent être conservées, la seconde sous-expression définit où les parties de parité doivent être conservées.

L'expression des libellés peut être soit une expression de libellés régulière, soit une expression de libellés EC (c'est-à-dire qu'une expression de libellés EC ne peut pas être une sous-expression). L'expression de libellés EC ne peut être utilisée qu'à la place de ARCHIVE_LABELS ou TRASH_LABELS dans la définition de la classe de stockage, l'expression de libellés régulière peut être utilisée n'importe où.

À la fin de chaque expression de libellés, une ou deux informations d'extension, divisées par un séparateur spécial, peuvent être ajoutées. La première extension possible est l'extension de distinction et le séparateur est le signe slash (/). La seconde est la substitution du mode de libellés et cette extension est séparée par un signe deux-points (:).

L'extension de distinction peut être une liste de libellés ou l'une des chaînes de caractères spéciales suivantes :

[IP] ou [I] - distinguer par numéro IP

[RACK] ou [R] - distinguer par RACK, tel que défini dans la topologie, voir mfstopology.cfg (5)

Si elle est présente, la partie de distinction indique au système qu'il doit essayer de distribuer des copies complètes de manière à ce que chaque copie soit soit sur un libellé différent de la liste, soit sur un chunkserver avec une adresse IP différente, soit dans un rack différent. Pour l'EC, la partie de distinction est actuellement ignorée.

AVIS ! Si CHUNKS_UNIQUE_MODE est défini dans mfsmaster.cfg à une valeur autre que 0, il remplacera tout paramètre de distinction dans les classes de stockage. Pour plus d'informations sur ce paramètre, reportez-vous au manuel de mfsmaster.cfg (5).

L'extension de substitution du mode de libellés peut être l'un des trois caractères : d (alternativement D ou sous forme de chaîne std ou Std ou STD), s (alternativement S ou sous forme de chaîne strict ou Strict ou STRICT) ou l (alternativement L ou sous forme de chaîne loose ou Loose ou LOOSE) et ils signifient que le mode de libellés STANDARD, STRICT ou LOOSE, respectivement, doit être appliqué uniquement à cette expression de libellés. Pour une explication des modes de libellés, voir la section MODES DE LIBELLÉS.

Une ou les deux extensions peuvent être présentes pour chaque expression de libellés, chacune doit commencer par son séparateur et si les deux sont présentes, l'ordre doit être respecté, c'est-à-dire que l'extension de distinction doit être la première et l'extension du mode de libellés doit être la seconde.

Exemples d'expressions de libellés :

A,B - les fichiers auront deux copies, une copie sera stockée sur un ou plusieurs chunkservers avec le libellé A, l'autre sur un ou plusieurs chunkservers avec le libellé B

A,* - les fichiers auront deux copies, une copie sera stockée sur un ou plusieurs chunkservers avec le libellé A, l'autre sur n'importe quel chunkserver

A,!A - les fichiers auront deux copies, une copie sera stockée sur un ou plusieurs chunkservers avec le libellé A, l'autre sur n'importe quel chunkserver qui n'a pas le libellé A

*,* - les fichiers auront deux copies, stockées sur n'importe quels chunkservers (différents pour chaque copie)

AB,C+D+E - les fichiers auront deux copies, une copie sera stockée sur n'importe quel chunkserver ayant les deux libellés A et B (multiplication des libellés), l'autre sur n'importe quel chunkserver ayant soit le libellé C, soit le libellé D, soit le libellé E (somme des libellés)

A,B[X+Y],C[X+Y] - les fichiers auront trois copies, une copie sera stockée sur n'importe quel chunkserver avec le libellé A, la seconde sur n'importe quel chunkserver ayant le libellé B et soit le libellé X soit le libellé Y, la troisième sur n'importe quel chunkserver ayant le libellé C et soit le libellé X soit le libellé Y

L'expression 2A est équivalente à l'expression A,A

L'expression A,3BC est équivalente à l'expression A,BC,BC,BC

L'expression 2 est équivalente à l'expression 2* est équivalente à l'expression *,*

3*/[IP] - les fichiers auront 3 copies, chaque copie sera conservée sur un chunkserver avec une adresse IP différente

A,B/[RACK] - les fichiers auront deux copies, une copie sera stockée sur un ou plusieurs chunkservers avec le libellé A, l'autre sur un ou plusieurs chunkservers avec le libellé B dans un rack différent de l'autre copie

S,H,H/[RACK] - les fichiers auront 3 copies, une sur un serveur avec le libellé S, deux sur des serveurs avec le libellé H, mais chaque copie sera sur un serveur avec un libellé différent de l'ensemble A, B, X, Y, Z

@4+1 - les fichiers seront conservés au format EC, 4 parties de données et 1 partie de parité

@8+3 - les fichiers seront conservés au format EC, 8 parties de données et 3 parties de parité

@2 - les fichiers seront conservés au format EC, nombre par défaut de parties de données, 2 parties de parité

@4+3,Z - les fichiers seront conservés au format EC, 4 parties de données et 3 parties de parité - toutes sur des chunkservers avec le libellé Z.

@2,A(X+Y) - les fichiers seront conservés au format EC, nombre par défaut de parties de données, 2 parties de parité, toutes les parties seront conservées sur des chunkservers avec le libellé A et soit X soit Y

@3,S,H - les fichiers seront conservés au format EC, le nombre par défaut de parties de données sera conservé sur des chunkservers avec le libellé S, 3 parties de parité seront conservées sur des chunkservers avec le libellé H

AB,AC:l - les fichiers seront conservés au format de copies, une copie sur un serveur avec les libellés A et B, la seconde sur un serveur avec les libellés A et C et le comportement de ceci devrait être LOOSE

@4+2,X,Y:s - les fichiers seront conservés au format EC, 4 parties de données seront conservées sur des serveurs avec le libellé X, 2 parties de parité (checksum) devraient être conservées sur des serveurs avec le libellé Y et le comportement de ceci devrait être STRICT

2A/[IP]:s - les fichiers devraient être conservés en 2 copies, les deux copies sur des serveurs avec le libellé A, mais chaque serveur devrait avoir une IP différente, le comportement de ceci lors de la prise en compte des libellés devrait être STRICT

MODES DE LIBELLES

Il est important de spécifier ce qu'il faut faire lorsqu'il n'est pas possible de satisfaire aux exigences de libellés d'une classe de stockage, c'est-à-dire : il n'y a pas d'espace disponible sur tous les serveurs avec les libellés requis, il n'y a pas assez de serveurs avec les libellés requis, ou les serveurs avec les libellés requis sont tous occupés. La question est de savoir si le système doit créer des chunks sur d'autres serveurs (avec des libellés non conformes) ou non. Cette décision doit être prise par l'utilisateur.

Il existe 3 modes de fonctionnement : STANDARD, LOOSE et STRICT. Les modes fonctionnent un peu différemment selon que le chunk est stocké en format de copies ou en format EC, en raison de la nature et des algorithmes différents que chacun de ces formats utilise.

Pour le format de copies, les 3 modes se comportent comme suit :

En mode STANDARD, en cas de serveurs surchargés, le système attendra, mais en cas de manque d'espace, il utilisera d'autres serveurs et répliquera les données vers les serveurs corrects lorsqu'il le pourra. Cela signifie que si certains serveurs sont en état occupé pendant une longue période, il pourrait ne pas être possible de créer de nouveaux chunks avec certaines classes de stockage et les chunks menacés (en sous-effectif) de ces classes courent un risque plus élevé d'être complètement perdus en raison de réplications retardées.

En mode STRICT, lors de l'écriture d'un nouveau fichier, le système renverra une erreur (ENOSPC) en cas de manque d'espace sur les serveurs marqués avec les libellés spécifiés pour la création de chunks. Il attendra toujours les serveurs surchargés. Les réplications en sous-effectif ne seront pas effectuées s'il n'y a pas d'espace sur les serveurs avec des libellés correspondant à la classe de stockage. Cela signifie un risque élevé de perte de données si les serveurs avec certains libellés sont définitivement remplis de données !

En mode LOOSE, le système utilisera immédiatement d'autres serveurs en cas de serveurs surchargés ou de manque d'espace sur les serveurs et répliquera les données vers les serveurs corrects lorsqu'il le pourra. Il n'y a pas de délai ni d'erreur lors de la création de fichiers et les réplications en sous-effectif sont toujours effectuées dès que possible.

Pour les chunks stockés au format EC, les 3 modes se comportent comme suit :

En général, les chunks ne seront convertis du format copie au format EC que s'il y a suffisamment de serveurs dans le système pour stocker en toute sécurité toutes les parties du format EC. Pour le format EC @N+X, où N est le nombre de parties de données et peut être soit 4 soit 8, et X est le nombre de parties de parité/checksum et peut être égal à 1 (version CE) ou à n'importe quel nombre de 1 à 9 (version PRO), les exigences générales sont :
- au moins N+2X chunkservers pour convertir les nouveaux chunks du format copie au format EC
- au moins N+X chunkservers pour conserver les chunks déjà au format EC dans ce format
- s'il y a moins de N+X serveurs, tous les chunks reviendront au format copie (définition KEEP).

En mode LOOSE, le système utilisera d'abord les serveurs correspondant à l'expression de libellés définie dans la classe de stockage utilisée, mais si suffisamment de serveurs avec les libellés "corrects" ne sont pas disponibles (parce qu'ils sont occupés, n'ont pas d'espace ou ne sont simplement pas définis), il utilisera n'importe quel chunkserver disponible indépendamment du libellé ; ainsi, N+2X et N+X sont calculés à partir de tous les chunkservers disponibles lorsque le système décide du format à utiliser pour conserver un chunk. De plus, lorsqu'une partie d'un chunk au format EC devient indisponible ou corrompue, la restauration de cette partie sera également effectuée sur n'importe quel serveur disponible, si un serveur avec les libellés "corrects" ne peut pas être utilisé actuellement.

Il est important de se rappeler que si suffisamment de serveurs avec les libellés "corrects" ne sont pas disponibles pour un chunk en mode LOOSE, le système peut utiliser autant de "autres" chunkservers qu'il le souhaite, pas seulement le nombre minimum manquant par rapport au nombre "correct" de serveurs.

En mode STRICT, le système n'utilisera que les serveurs correspondant à l'expression de libellés définie dans la classe de stockage utilisée, donc seuls les serveurs disponibles ou occupés à court terme

rvers correspondant à l'expression de libellé définie sera utilisé pour le calcul de N+2X et N+X lorsque le système décidera du format à utiliser pour stocker un bloc. Lorsqu'une partie d'un bloc au format EC devient indisponible ou corrompue, la restauration de cette partie ne peut être effectuée que sur un serveur avec un libellé "correct" ; si un tel serveur est indisponible à long terme (c'est-à-dire indisponible ou temporairement occupé), cela signifiera automatiquement que le bloc devra être reconverti au format de copie de toute façon (si la partie manquante est une partie de parité/checksum, le bloc sera simplement reconverti au format de copie en utilisant toutes les parties de données disponibles, si une partie de données est manquante, elle sera restaurée sur un serveur de bloc hébergeant une autre partie du même bloc - ce qui n'est pas autorisé dans des circonstances normales - puis la conversion au format de copie suivra immédiatement).

En mode STANDARD, le système se comportera comme en mode STRICT lorsqu'il devra décider s'il convertira un nouveau bloc du format de copie au format EC, c'est-à-dire que le N+2X à cette étape sera calculé uniquement à partir des serveurs libellés "correctement". Mais pour décider si les blocs existants doivent être reconvertis du format EC au format de copie, il examinera tous les serveurs disponibles, indépendamment des libellés, de sorte que le N+X à cette étape soit calculé à partir de tous les serveurs disponibles, comme en mode LOOSE. En cas de pièces manquantes, s'il n'est pas possible de les restaurer sur des serveurs de blocs avec des libellés "corrects", le système adaptera également le comportement du mode LOOSE et essaiera d'utiliser n'importe quel serveur disponible.

Attention ! Lorsqu'un bloc est converti du format de copie au format EC, le système effectue d'abord une opération de "fractionnement local", c'est-à-dire qu'il sélectionne une copie du bloc et calcule toutes les parties EC nécessaires sur le serveur occupé par cette copie sélectionnée. Ensuite, ces parties sont déplacées vers des serveurs de blocs distincts, correspondant aux libellés définis dans la classe de stockage pour le mode EC utilisé. Mais temporairement, entre le fractionnement et le "déplacement" des parties, elles peuvent être enregistrées sur un serveur de bloc "incorrect" même en mode STRICT. Ceci est dû à la mécanique de l'opération de "fractionnement local".

TEMPS

Pour les variables de temps, leur valeur peut être définie comme un nombre de secondes ou d'heures (entier), selon l'unité minimale de la variable, ou comme une période de temps dans l'un des deux formats possibles :

premier format : #.#T où T est l'un des : s-secondes, m-minutes, h-heures, d-jours ou w-semaines ; les fractions de l'unité minimale seront arrondies à la valeur entière

deuxième format : #w#d#h#m#s, n'importe quel nombre de définitions peut être omis, mais les définitions restantes doivent être dans l'ordre (donc #d#m est toujours une définition valide, mais #m#d ne l'est pas) ; plages : s,m : 0 à 59, h : 0 à 23, d : 0 à 6, w est illimité et la première définition est également toujours illimitée (c'est-à-dire que pour #d#h#m, d sera illimité)

Si une unité minimale d'une variable est supérieure aux secondes, les unités inférieures à l'unité minimale ne seront pas acceptées. Par exemple, une variable dont l'unité minimale est l'heure n'acceptera pas les unités s et m.

Exemples :

1.5j est identique à 1j12h, est identique à 36h

2.5s est identique à 2s3j12h, est identique à 420h ; 2s84h n'est pas une période valide (h n'est pas la première définition, elle est donc limitée à la plage 0 à 23)

COMPORTEMENT D'ARCHIVAGE

Les blocs ont un drapeau d'archive défini lors de la boucle de maintenance des fichiers, ce qui signifie que le temps d'archivage défini par l'option -d est le temps minimum qui doit s'écouler avant que le drapeau ne soit défini, et non le temps exact.

Le comportement par défaut du système est qu'une fois qu'un bloc a le drapeau d'archive activé, il N'EST PAS désactivé même si atime/ctime/mtime change, sauf si le drapeau R est défini par l'option -o. L'écriture sur un bloc désactivera toujours son drapeau d'archive.

Drapeaux d'archive :

C - utilise le ctime du fichier pour déterminer si le drapeau d'archive doit être activé - c'est le drapeau par défaut

M - utilise le mtime du fichier pour déterminer si le drapeau d'archive doit être activé

A - utilise l'atime du fichier pour déterminer si le drapeau d'archive doit être activé

R - réversible, si atime/mtime/ctime change pour un fichier, le système vérifie si le drapeau d'archive doit être désactivé pour ses blocs

F - mode rapide, le bloc a son drapeau d'archive activé dès que possible, tout ce qui est défini avec l'option -d est ignoré

P - mode "par bloc", utilise le mtime du bloc pour déterminer si le drapeau d'archive doit être activé

Le drapeau d'archive peut être modifié manuellement. Voir mfsarchive (1)

Note : l'état ARCHIVE ne signifie pas que les blocs ou les fichiers sont indisponibles, bloqués en écriture, etc. La désignation ARCHIVE est seulement utilisée pour indiquer que ces données sont déjà destinées à un stockage à long terme. Contrairement à l'état KEEP, qui signifie que les données sont "chaudes" et peuvent être modifiées fréquemment. La distinction entre les états KEEP et ARCHIVE permet donc uniquement de définir la manière physique de stocker ces données. Du point de vue de l'utilisateur, le fichier est accessible de manière identique : il a les mêmes permissions, le même nom et se trouve dans le même répertoire. Par exemple, du fait que l'écriture en mode EC puisse être plus lente, nous suggérons de stocker les données "chaudes" (KEEP) en utilisant une copie et de les convertir au format EC (en attribuant le mode ARCHIVE) après un certain temps. Un autre exemple est le transfert automatique de données "froides" vers des disques/serveurs de blocs plus anciens/plus lents/moins chers - en utilisant des libellés différents.

PRIORITÉ DES CLASSES DE STOCKAGE

Les classes de stockage sont attribuées aux fichiers, mais un bloc (un fragment d'un fichier) peut appartenir à plusieurs fichiers, grâce au mécanisme de snapshot (voir mfssnapshots (1)). Si un bloc appartient à plusieurs fichiers ayant des classes de stockage différentes, une classe de stockage doit être choisie pour spécifier comment les copies de ce bloc doivent être conservées dans le système. Jusqu'à la version 4.56.0 de MooseFS, une classe prédéfinie était artificiellement attribuée à un tel bloc. Actuellement, l'une des classes des fichiers sera utilisée, selon les priorités attribuées par l'utilisateur, pour être précis : le système choisira la classe avec la priorité la plus élevée parmi toutes les classes des fichiers.

Exemple 1 : 3 classes sont définies :
ClasseA, avec une priorité de 100,
ClasseB, avec une priorité de 206,
ClasseC, avec une priorité de 1001.

Un bloc, appartenant à 2 fichiers, l'un dans ClasseA, l'autre dans ClasseB, sera stocké selon la définition fournie par la classeB (priorité plus élevée que ClasseA).
Un bloc, appartenant à 3 fichiers, l'un dans ClasseA, un dans ClasseB, un dans ClasseC, sera stocké selon la définition fournie par la classeC (priorité plus élevée que ClasseA et ClasseB).

Si deux classes ou plus ont la même priorité, alors les facteurs suivants seront pris en compte, par ordre d'importance, pour déterminer quelle classe sera choisie :
- une classe avec un niveau de redondance (RL) plus élevé sera choisie (le maximum des niveaux de redondance KEEP et ARCHIVE de chaque classe sera considéré comme le niveau de redondance de cette classe),
- une classe qui a le format EC en état ARCHIVE sera préférée à une classe sans EC,
- une classe qui utilise des libellés pour l'état KEEP ou ARCHIVE sera préférée à une classe sans libellés,
- une classe qui a le format EC en état TRASH sera préférée à une classe sans EC,
- une classe qui utilise des libellés pour l'état TRASH sera préférée à une classe sans libellés,
- si aucune des conditions ci-dessus n'est utilisée, une classe avec un identifiant de classe plus élevé sera utilisée.

Exemple 2 : 5 classes sont définies, toutes avec la même priorité (par exemple, la priorité par défaut 0) :
ClasseA (id=1) a 3 copies en état KEEP (RL=2),
ClasseB (id=2) a 2 copies en état KEEP et EC4+1 en état ARCHIVE (RL=1, a EC en ARCHIVE),
ClasseC (id=3) a 2 copies en état KEEP, stockées sur des libellés X (RL=1, pas d'EC en ARCHIVE, a des libellés en KEEP),
ClasseD (id=4) a 2 copies en état KEEP, stockées sur des libellés Y (RL=1, pas d'EC en ARCHIVE, a des libellés en KEEP),
ClasseE (id=5) a 2 copies en état KEEP (RL=1).
Il existe également une classe ClassF définie, qui a une priorité de 77 et 2 copies en état KEEP (RL=1).

Un bloc, appartenant aux fichiers dans les classes : ClasseA, ClasseC et ClasseE sera stocké selon la définition de ClasseA (RL le plus élevé).
Un bloc, appartenant aux fichiers dans les classes : ClasseB, ClasseC sera stocké selon la définition de ClasseB (RL identique, mais ClasseB a EC).
Un bloc, appartenant aux fichiers dans les classes : ClasseC et ClasseE sera stocké selon la définition de ClasseC (RL identique, mais ClasseC a des libellés).
Un bloc, appartenant aux fichiers dans les classes : ClasseC et ClasseD sera stocké selon la définition de ClasseD (RL identique, pas d'EC, les deux ont des libellés, donc l'ID de classe le plus élevé est choisi).
Un bloc, appartenant aux fichiers dans 6 classes, de ClasseA à ClasseF, sera stocké selon la définition de ClasseF, car celle-ci a une priorité plus élevée que toutes les autres classes (77>0).
Dans un système avec ces 6 classes de stockage, la classeE ne sera jamais utilisée pour un bloc appartenant à plusieurs fichiers, elle a la priorité la plus basse possible (0) et aucune condition supplémentaire pour justifier son choix (RL existant le plus bas, pas d'EC et pas de libellés).

CLASSES DE STOCKAGE PRÉDÉFINIES

Une nouvelle instance de MooseFS aura les classes suivantes prédéfinies :

2CP - seul l'état KEEP est défini, conserve 2 copies sur n'importe quel libellé (classe par défaut pour le répertoire /)

3CP - seul l'état KEEP est défini, conserve 3 copies sur n'importe quel libellé

EC4+1 - en état KEEP, conserve 2 copies sur n'importe quel libellé, en état ARCHIVE, conserve les blocs au format EC4+1 sur n'importe quel libellé, le délai d'archivage est de 1 jour et est calculé en utilisant le ctime du fichier, les fichiers de moins de 512 KiB ne seront pas convertis au format EC

EC4+2 - (pro uniquement) en état KEEP, conserve 3 copies sur n'importe quel libellé, en état ARCHIVE, conserve les blocs au format EC4+2 sur n'importe quel libellé, le délai d'archivage est de 1 jour et est calculé en utilisant le ctime du fichier, les fichiers de moins de 512 KiB ne seront pas convertis au format EC

EC8+1 - en état KEEP, conserve 2 copies sur n'importe quel libellé, en état ARCHIVE, conserve les blocs au format EC8+1 sur n'importe quel libellé, le délai d'archivage est de 1 jour et est calculé en utilisant le ctime du fichier, les fichiers de moins de 512 KiB ne seront pas convertis au format EC

EC8+2 - (pro uniquement) en état KEEP, conserve 3 copies sur n'importe quel libellé, en état ARCHIVE, conserve les blocs au format EC8+2 sur n'importe quel libellé, le délai d'archivage est de 1 jour et est calculé en utilisant le ctime du fichier, les fichiers de moins de 512 KiB ne seront pas convertis au format EC

Ces classes sont entièrement modifiables et supprimables et peuvent être remplacées par des classes choisies par l'utilisateur.

Jusqu'à la version 4.56.0 de MooseFS, les classes prédéfinies étaient différentes. Les informations suivantes concernent l'ancien comportement de MooseFS. Dans les versions plus récentes de MooseFS, les classes mentionnées ci-dessous peuvent exister

mfscreatesclass - Manual page

NOM

mfscreatesclass - crée une nouvelle classe de stockage

SYNTAXIS

mfscreatesclass [-a] [-C chaîne_de_caractères] [-K chaîne_de_caractères] [-A chaîne_de_caractères] [-d durée] [-o mode_d_archivage] [-m mode_de_réplication] [-s priorité] [-p paire_de_classess] nom_classe

DESCRIPTION

L'utilitaire mfscreatesclass crée une nouvelle classe de stockage avec le nom spécifié dans le paramètre nom_classe. Les classes de stockage sont utilisées pour définir des politiques de stockage différentes pour différents groupes de fichiers.

Les classes de stockage sont décrites dans le fichier de configuration mfsmaster.cfg. Leurs définitions sont permanentes (elles sont enregistrées dans le répertoire de métadonnées de MooseFS).

Il est possible de définir une classe de stockage lors de la création d'un nouveau fichier (option -C), de la manière dont les copies de chunks seront gardées (option -K) et dans quelle archive les chunks seront archivés (option -A). Les paramètres par défaut sont définis dans la section GLOBAL du fichier mfsmaster.cfg.

Les options -C, -K et -A utilisent une syntaxe spéciale pour définir le nombre de copies et le type d'archivage :

  • N* : conserver N copies sur des serveurs de chunks quelconques.
  • N : conserver exactement N copies.
  • N,M : conserver N copies, dont M sur des labels spécifiés.
  • A,B,C : conserver des copies sur des serveurs avec les labels A, B et C.
  • @FORMAT : utiliser le format d'archivage spécifié. Exemples : @1 ; @2 ; @4 ; @4+1 ; @6+2 ; @8+2 ; @10+3.

L'option -a permet de créer une classe d'archivage. Elle ne sera utilisée que lorsque les fichiers seront archivés, pas lors de la création.

L'option -d permet de définir le délai avant l'archivage d'un fichier.

L'option -o permet de définir le mode d'archivage (par exemple, m pour modifier les chunks existants).

L'option -m permet de définir le mode de réplication (par exemple, l pour le mode lâche).

L'option -s permet de définir la priorité de la classe.

L'option -p permet de définir une paire de classes pour la réplication.

OPTIONS

-a
Crée une classe d'archivage.
-C chaîne_de_caractères
Définit le nombre de copies pour les nouveaux chunks créés.
-K chaîne_de_caractères
Définit le nombre de copies pour les chunks existants.
-A chaîne_de_caractères
Définit le format d'archivage des chunks.
-d durée
Définit le délai avant l'archivage d'un fichier. La durée peut être spécifiée en jours (d), heures (h) ou minutes (m). Exemples : 1d, 12h, 30m.
-o mode_d_archivage
Définit le mode d'archivage. Les modes disponibles sont :
m
Archive les chunks existants.
-m mode_de_réplication
Définit le mode de réplication. Les modes disponibles sont :
l
Mode lâche : si les serveurs de chunks spécifiés sont surchargés, les copies peuvent être placées sur d'autres serveurs.
-s priorité
Définit la priorité de la classe. Les valeurs plus élevées indiquent une priorité plus faible.
-p paire_de_classess
Définit une paire de classes pour la réplication. Le format est classe1,classe2.

NOTES

Les classes de stockage prédéfinies ne peuvent pas être supprimées.

Il est conseillé de créer de nouvelles classes de stockage plutôt que de modifier les classes prédéfinies.

(Comportement jusqu'à la version 4.56.0) Pour des raisons de compatibilité, chaque instance fraîche ou récemment mise à niveau de MooseFS possède 9 classes de stockage prédéfinies. Leurs noms sont des chiffres uniques, de 1 à 9, et leurs définitions sont * à 9*. Ils sont les équivalents des objectifs numériques simples des versions précédentes du système. En cas de mise à niveau, tous les fichiers qui avaient l'objectif N avant la mise à niveau auront maintenant la classe de stockage N. Ces classes ne peuvent être modifiées que lorsque l'option -f est spécifiée. Il est conseillé de créer de nouvelles classes de stockage dans un système mis à niveau et de migrer les fichiers avec l'outil mfsxchgsclass, plutôt que de modifier les classes prédéfinies. Les classes prédéfinies NE PEUVENT PAS être supprimées.

EXEMPLES

Créer une nouvelle classe de stockage nommée "Class2Copies" avec 2 copies. La première copie sur un serveur de chunks avec le label "A" et la deuxième copie sur un serveur de chunks avec le label "B" :

mfscreatesclass -K A,B Class2Copies

Créer une nouvelle classe de stockage nommée "Class3Copies". Les chunks fraîchement créés (-C) seront conservés n'importe où avec 2 copies (2*). Peu après la création, ils seront conservés (-K) en 3 copies : la première copie sur un serveur de chunks avec le label "A", la deuxième copie sur un serveur de chunks avec le label "B" et la troisième sur n'importe quel serveur de chunks :

mfscreatesclass -C '2*' -K 'A,B,*' Class3Copies

Créer une nouvelle classe de stockage nommée "ClassEC4_1". Les chunks seront créés et conservés (-K) n'importe où en 2 copies (2*) pendant 24 heures à partir de la création du fichier. Plus tard, ils seront archivés (-A) au format EC4+1 sur n'importe quel serveur de chunks :

mfscreatesclass -K '2*' -A '@4+1' ClassEC4_1

Modifier la classe de stockage "ClassEC4_1" pour archiver les chunks après 48 heures à partir de la modification du fichier (pas de la création) :

mfscreatesclass -d 2d -o m ClassEC4_1

Modifier la classe de stockage "Class3Copies" pour conserver les chunks sur d'autres serveurs de chunks (mode LOOSE) si ceux avec les labels "A" et "B" sont trop occupés (surchargés) :

mfscreatesclass -m l Class3Copies
