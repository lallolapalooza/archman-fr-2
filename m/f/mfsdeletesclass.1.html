DESCRIPTION

Il s'agit d'un ensemble d'outils pour gérer les classes de stockage MooseFS. Les classes de stockage sont utilisées pour définir la politique de redondance au sein du cluster. Elles doivent être appliquées ultérieurement à des objets MooseFS particuliers (fichiers ou dossiers) avec les outils mfssclass (voir mfssclass(1)). Une classe de stockage est un ensemble nommé d'expressions d'étiquettes et d'autres options. L'expression d'étiquettes indique le format de redondance, le niveau de redondance souhaité et la politique de stockage souhaitée. Le format de redondance peut être soit des copies, soit de l'effacement de code (EC). Le niveau de redondance est soit le nombre de copies (de 1 à 9), soit le nombre de parties de données plus de parité (4+n ou 8+n), selon le format de redondance indiqué. La politique de stockage spécifie, par l'utilisation d'étiquettes, quels serveur de blocs (chunkservers) doivent être utilisés pour le stockage physique des données attribuées à la classe de stockage particulière.

mfscreatesclass crée une nouvelle classe de stockage avec les options données, décrites ci-dessous, et la nomme NOM_CLASSE_STOCKAGE ; plusieurs noms peuvent être fournis, créant alors plusieurs classes de stockage avec la même définition.

mfsmodifysclass modifie les options données dans une classe ou des classes indiquées par les paramètres NOM_CLASSE_STOCKAGE.

mfsdeletesclass supprime la ou les classes indiquées par les paramètres NOM_CLASSE_STOCKAGE ; si l'une des classes n'est pas vide (c'est-à-dire si elle est toujours utilisée par des objets MooseFS), elle ne sera pas supprimée et l'outil retournera une erreur avec un message ; les classes vides seront supprimées dans tous les cas.

mfsclonesclass copie la classe indiquée par NOM_CLASSE_SRC sous un nouveau nom fourni avec NOM_CLASSE_DST.

mfsrenamesclass change le nom d'une classe de NOM_CLASSE_SRC à NOM_CLASSE_DST.

mfslistsclass liste toutes les classes.

mfsimportsclass importe les définitions des classes de stockage depuis stdin ou un fichier et les crée ; le format d'entrée doit être identique à la sortie de mfslistsclass -l.

OPTIONS

-C paramètre optionnel, qui indique au système sur quels serveurs de blocs, définis par l'expression ETIQUETTES_CREER, le bloc doit être écrit en premier juste après sa création ; si ce paramètre n'est pas fourni pour une classe, les serveurs de blocs ETIQUETTES_CONSERVER seront utilisés.

-K paramètre obligatoire, qui indique au système sur quels serveurs de blocs, définis par l'expression ETIQUETTES_CONSERVER, le ou les blocs doivent toujours être conservés, sauf dans des conditions spéciales comme la création, l'archivage et la suppression (déplacement vers la Corbeille), si définies.

-A paramètre optionnel, qui indique au système sur quels serveurs de blocs, définis par l'expression ETIQUETTES_ARCHIVER, le ou les blocs doivent être conservés à des fins d'archivage ; le système commence à traiter un bloc comme archive lorsque l'atime/mtime/ctime (tel que défini par -o) du fichier auquel il appartient est plus ancien que le nombre d'heures spécifié avec l'option -d ; voir également la section COMPORTEMENT D'ARCHIVAGE ci-dessous.

-d paramètre optionnel qui définit après combien de temps depuis l'atime/mtime/ctime (tel que défini par -o) un fichier (et ses blocs) est traité comme archive ; l'unité minimale est l'heure, la valeur par défaut est 24 ; pour le formatage de la valeur, voir TEMPS.

-o paramètre optionnel qui définit les indicateurs d'archivage. C - ctime, M - mtime, A - atime, R - réversible, F - mode rapide, P - par bloc ; la valeur par défaut est C ; voir la section COMPORTEMENT D'ARCHIVAGE ci-dessous pour plus de détails.

-s paramètre optionnel qui définit la longueur minimale du fichier en octets qui peut être archivée ; la valeur par défaut est 0.

-T paramètre optionnel, qui indique au système sur quels serveurs de blocs, définis par l'expression ETIQUETTES_CORBEILLE, le ou les blocs des fichiers dans la Corbeille doivent être conservés ; voir aussi -t.

-t paramètre optionnel, qui définit combien de temps en Corbeille doit s'écouler pour que le système utilise le schéma défini dans -T pour un bloc ; l'unité minimale est l'heure, la valeur par défaut est 0 ; pour le formatage de la valeur, voir TEMPS.

-c paramètre optionnel, qui définit une description de la classe, pour la commodité de l'utilisateur (une chaîne de caractères, longueur maximale de 255 octets).

-p paramètre optionnel, qui définit une priorité de classe ; la valeur par défaut est 0 ; voir la section PRIORITÉ DES CLASSES DE STOCKAGE.

-g paramètre optionnel, qui définit un groupe d'exportation de classe ; les valeurs possibles sont de 0 à 15, la valeur par défaut est 0 ; voir mfsexport.cfg(5) pour une explication.

-a peut être soit 1 soit 0 et indique si la classe de stockage est disponible pour tout le monde (0) ou seulement pour l'administrateur (1).

-m mode d'étiquette utilisé ; les valeurs possibles sont l (ou L, loose, Loose, LOOSE) pour le mode LOOSE, d (ou D, std, Std, STD) pour le mode STANDARD et s (ou S, strict, Strict, STRICT) pour le mode STRICT ; si aucun mode n'est défini, le mode STANDARD est supposé ; le comportement des modes d'étiquettes est décrit ci-dessous dans la section MODES D'ÉTIQUETTES.

-l liste également les définitions, pas seulement les noms des classes de stockage existantes.

-i correspondance des noms de classes de stockage insensible à la casse.

-r remplace (écrase) les classes existantes lors de l'importation de classes de stockage.

-n utilise le nom de fichier fourni comme source des définitions de classes de stockage pour l'importation, au lieu de stdin.

-M point de montage MooseFS, pas besoin de le spécifier si l'outil est exécuté à l'intérieur d'un répertoire monté MooseFS ou si MooseFS est monté dans /mnt/mfs/.

-? affiche un court message d'utilisation.

NOTES

EXPRESSIONS D'ÉTIQUETTES

Les étiquettes sont des lettres (A-Z - 26 lettres) qui peuvent être attribuées aux serveurs de blocs. Chaque serveur de blocs peut avoir plusieurs (jusqu'à 26) étiquettes. Les étiquettes sont définies dans le fichier mfschunkserver.cfg, pour plus d'informations référez-vous à la page man appropriée.

Une expression d'étiquettes est un ensemble de sous-expressions séparées par des virgules. Pour des copies complètes, chaque sous-expression spécifie le schéma de stockage d'une copie d'un fichier. Une sous-expression peut être : un astérisque ou un schéma d'étiquette. Un schéma d'étiquette peut être une seule étiquette ou une expression avec des sommes, des multiplications, des négations et des parenthèses. La somme signifie qu'un fichier peut être stocké sur n'importe quel serveur de blocs correspondant à n'importe quel élément de la somme (ou logique). La multiplication signifie qu'un fichier ne peut être stocké que sur un serveur de blocs correspondant à tous les éléments (et logique). L'astérisque signifie n'importe quel serveur de blocs. La négation signifie n'importe quel serveur de blocs sauf celui correspondant à la sous-expression niée. Des sous-expressions identiques peuvent être abrégées en ajoutant un nombre devant l'une d'elles au lieu de la répéter plusieurs fois.

Pour l'EC, l'expression d'étiquettes commence par le signe @, suivi du nombre de parties de données, puis du signe + et d'un nombre indiquant combien de parties de parité le bloc doit avoir. Nombre possible

s de parties de données sont 4 ou 8. Le nombre possible de parties de parité est 1 (version CE ) ou 1 à 9 (version PRO). Ainsi, par exemple, @4+1 signifie EC avec 4 parties de données et 1 partie de parité, @8+3 signifie EC avec 8 parties de données et 3 parties de parité. Si le nombre de parties de données est omis, le maître utilise la valeur par défaut définie par DEFAULT_EC_DATA_PARTS - voir mfsmaster.cfg (5). Dans ce cas, @2 signifie @8+2 ou @4+2. Ensuite, un maximum de deux sous-expressions peuvent suivre, séparées par des virgules. S'il n'y en a qu'une, elle définit où toutes les parties doivent être conservées. S'il y en a deux, la première sous-expression définit où les parties de données doivent être conservées, la seconde sous-expression définit où les parties de parité doivent être conservées.

L'expression d'étiquettes peut être soit une expression d'étiquettes régulière, soit une expression d'étiquettes EC (c'est-à-dire qu'une expression d'étiquettes EC ne peut pas être une sous-expression). Une expression d'étiquettes EC ne peut être utilisée qu'à la place de ARCHIVE_LABELS ou TRASH_LABELS dans la définition de la classe de stockage, une expression d'étiquettes régulière peut être utilisée n'importe où.

À la fin de chaque expression d'étiquettes, une ou deux informations supplémentaires, divisées par un séparateur spécial, peuvent être ajoutées. La première extension possible est l'extension de distinction et le séparateur est le signe barre oblique (/ ). La seconde est la substitution du mode d'étiquettes et cette extension est séparée par un signe deux-points (: ).

L'extension de distinction peut être une liste d'étiquettes ou l'une des chaînes spéciales suivantes :

[IP] ou [I] - distinction par numéro IP

[RACK] ou [R] - distinction par RACK, tel que défini dans la topologie, voir mfstopology.cfg (5)

Si elle est présente, la partie de distinction indique au système qu'il doit essayer de distribuer les copies complètes de manière à ce que chaque copie soit soit sur une étiquette différente de la liste, soit sur un serveur de fragments avec une adresse IP différente, soit provenant d'un rack différent. Pour EC, la partie de distinction est actuellement ignorée.

ATTENTION ! Si CHUNKS_UNIQUE_MODE est défini dans mfsmaster.cfg à une valeur autre que 0, il remplacera tout paramètre de distinction dans les classes de stockage. Pour plus d'informations sur ce paramètre, reportez-vous au manuel mfsmaster.cfg (5).

L'extension de substitution du mode d'étiquettes peut être l'un des trois caractères : d (alternativement D ou sous forme de chaîne std ou Std ou STD), s (alternativement S ou sous forme de chaîne strict ou Strict ou STRICT) ou l (alternativement L ou sous forme de chaîne loose ou Loose ou LOOSE) et ils signifient que le mode d'étiquettes STANDARD, STRICT ou LOOSE, respectivement, doit être appliqué uniquement à cette expression d'étiquettes. Pour une explication des modes d'étiquettes, voir la section MODES D'ÉTIQUETTES.

Une ou deux extensions peuvent être présentes pour chaque expression d'étiquettes, chacune doit commencer par son séparateur et si les deux sont présentes, l'ordre doit être conservé, c'est-à-dire que l'extension de distinction doit être la première et l'extension du mode d'étiquettes doit être la seconde.

Exemples d'expressions d'étiquettes :

A,B - les fichiers auront deux copies, une copie sera stockée sur un ou plusieurs serveurs de fragments avec l'étiquette A, l'autre sur un ou plusieurs serveurs de fragments avec l'étiquette B

A,* - les fichiers auront deux copies, une copie sera stockée sur un ou plusieurs serveurs de fragments avec l'étiquette A, l'autre sur n'importe quel serveur de fragments

A,!A - les fichiers auront deux copies, une copie sera stockée sur un ou plusieurs serveurs de fragments avec l'étiquette A, l'autre sur n'importe quel serveur de fragments qui n'a pas l'étiquette A

*,* - les fichiers auront deux copies, stockées sur n'importe quel serveur de fragments (différent pour chaque copie)

AB,C+D+E - les fichiers auront deux copies, une copie sera stockée sur n'importe quel serveur de fragments qui possède les deux étiquettes A et B (multiplication des étiquettes), l'autre sur n'importe quel serveur de fragments qui possède l'étiquette C ou l'étiquette D ou l'étiquette E (somme des étiquettes)

A,B[X+Y],C[X+Y] - les fichiers auront trois copies, une copie sera stockée sur n'importe quel serveur de fragments avec l'étiquette A, la deuxième sur n'importe quel serveur de fragments qui possède l'étiquette B et soit l'étiquette X, soit l'étiquette Y, la troisième sur n'importe quel serveur de fragments qui possède l'étiquette C et soit l'étiquette X, soit l'étiquette Y

L'expression 2A est équivalente à l'expression A,A

L'expression A,3BC est équivalente à l'expression A,BC,BC,BC

L'expression 2 est équivalente à l'expression 2* est équivalente à l'expression *,*

3*/[IP] - les fichiers auront 3 copies, chaque copie sera conservée sur un serveur de fragments avec une adresse IP différente

A,B/[RACK] - les fichiers auront deux copies, une copie sera stockée sur un ou plusieurs serveurs de fragments avec l'étiquette A, l'autre sur un ou plusieurs serveurs de fragments avec l'étiquette B dans un rack différent de l'autre copie

S,H,H/[RACK] - les fichiers auront 3 copies, une sur un serveur avec l'étiquette S, deux sur des serveurs avec l'étiquette H, mais chaque copie sera sur un serveur avec une étiquette différente de l'ensemble A, B, X, Y, Z

@4+1 - les fichiers seront conservés au format EC, 4 parties de données et 1 partie de parité

@8+3 - les fichiers seront conservés au format EC, 8 parties de données et 3 parties de parité

@2 - les fichiers seront conservés au format EC, nombre par défaut de parties de données, 2 parties de parité

@4+3,Z - les fichiers seront conservés au format EC, 4 parties de données et 3 parties de parité - toutes sur des serveurs de fragments avec l'étiquette Z.

@2,A(X+Y) - les fichiers seront conservés au format EC, nombre par défaut de parties de données, 2 parties de parité, toutes les parties seront conservées sur des serveurs de fragments avec l'étiquette A et soit X, soit Y

@3,S,H - les fichiers seront conservés au format EC, le nombre par défaut de parties de données sera conservé sur des serveurs de fragments avec l'étiquette S, 3 parties de parité seront conservées sur des serveurs de fragments avec l'étiquette H

AB,AC:l - les fichiers seront conservés au format de copies, une copie sur un serveur avec les étiquettes A et B, la seconde sur un serveur avec les étiquettes A et C et le comportement de ceci doit être LOOSE

@4+2,X,Y:s - les fichiers seront conservés au format EC, 4 parties de données seront conservées sur des serveurs avec l'étiquette X, 2 parties de parité (somme de contrôle) doivent être conservées sur des serveurs avec l'étiquette Y et le comportement de ceci doit être STRICT

2A/[IP]:s - les fichiers doivent être conservés en 2 copies, les deux copies sur des serveurs avec l'étiquette A, mais chaque serveur doit avoir une IP différente, le comportement de ceci lors de la prise en compte des étiquettes doit être STRICT

MODES D'ÉTIQUETTES

Il est important de spécifier quoi faire lorsqu'il n'est pas possible de satisfaire aux exigences d'étiquettes d'une classe de stockage, c'est-à-dire : il n'y a pas d'espace disponible sur tous les serveurs avec les étiquettes nécessaires, il n'y a pas assez de serveurs avec les étiquettes nécessaires, ou les serveurs avec les étiquettes nécessaires sont tous occupés. La question est de savoir si le système doit créer des fragments sur d'autres serveurs (avec des étiquettes non correspondantes) ou non. Cette décision doit être prise par l'utilisateur.

Il existe 3 modes de fonctionnement : STANDARD, LOOSE et STRICT. Les modes fonctionnent un peu différemment selon que le fragment est stocké sous forme de copies ou au format EC, en raison de la nature et des algorithmes différents que chacun de ces formats utilise.

Pour le format de copies, les 3 modes se comportent comme suit :

En mode STANDARD, en cas de surcharge des serveurs, le système attendra, mais en cas de manque d'espace, il utilisera d'autres serveurs et répliquera les données vers les serveurs corrects lorsque cela deviendra possible. Cela signifie que si certains serveurs sont dans un état occupé pendant une longue période, il pourrait ne pas être possible de créer de nouveaux fragments avec certaines classes de stockage et les fragments menacés (sous-objectifs) de ces classes risquent davantage d'être complètement perdus en raison des réplications retardées.

En mode STRICT, lors de l'écriture d'un nouveau fichier, le système renverra une erreur (ENOSPC) en cas de manque d'espace sur les serveurs marqués avec les étiquettes spécifiées pour la création de fragments. Il attendra toujours les serveurs surchargés. Les réplications sous-objectifs ne seront pas effectuées s'il n'y a pas d'espace sur les serveurs dont les étiquettes correspondent à la classe de stockage. Cela signifie un risque élevé de perte de données si les serveurs avec certaines étiquettes sont définitivement remplis de données !

En mode LOOSE, le système utilisera immédiatement d'autres serveurs en cas de surcharge ou de manque d'espace sur les serveurs et répliquera les données vers les serveurs corrects lorsque cela deviendra possible. Il n'y a pas de délai ou d'erreur lors de la création de fichiers et les réplications sous-objectifs sont toujours effectuées dès que possible.

Pour les fragments stockés au format EC, les 3 modes se comportent comme suit :

En général, les fragments ne seront convertis du format de copie au format EC que s'il y a suffisamment de serveurs dans le système pour stocker en toute sécurité toutes les parties du format EC. Pour le format EC @N+X, où N est le nombre de parties de données et peut être soit 4 soit 8, et X est le nombre de parties de parité/somme de contrôle et peut être égal à 1 (version CE) ou tout nombre de 1 à 9 (version PRO), les exigences générales sont :
- au moins N+2X serveurs de fragments pour convertir de nouveaux fragments du format de copie au format EC
- au moins N+X serveurs de fragments pour conserver les fragments déjà au format EC dans ce format
- s'il y a moins de N+X serveurs, tous les fragments reviendront au format de copie (définition KEEP).

En mode LOOSE, le système essaiera d'utiliser d'abord les serveurs correspondant à l'expression d'étiquettes définie dans la classe de stockage utilisée, mais s'il n'y a pas assez de serveurs avec les étiquettes "correctes" disponibles (parce qu'ils sont occupés, n'ont pas d'espace, ou ne sont tout simplement pas définis), il utilisera n'importe quel serveur de fragments disponible, quelle que soit l'étiquette ; ainsi N+2X et N+X sont calculés à partir de tous les serveurs de fragments disponibles lorsque le système décide du format à utiliser pour conserver un fragment. De plus, lorsqu'une partie d'un fragment au format EC devient indisponible ou corrompue, la restauration de cette partie sera également effectuée sur n'importe quel serveur disponible, si un serveur avec les étiquettes "correctes" ne peut pas être utilisé actuellement.

Il est important de se rappeler que s'il n'y a pas assez de serveurs avec les étiquettes "correctes" disponibles pour un fragment en mode LOOSE, le système peut utiliser autant de serveurs "autres" qu'il le souhaite, pas seulement le nombre minimal manquant par rapport au nombre "correct" de serveurs.

En mode STRICT, le système n'utilisera que les serveurs correspondant à l'expression d'étiquettes définie dans la classe de stockage utilisée, donc seulement les serveurs disponibles ou occupés à court terme

rvers correspondant à l'expression d'étiquette définie seront utilisés pour le calcul de N+2X et N+X lorsque le système décide du format à utiliser pour conserver un bloc. Lorsqu'une partie d'un bloc au format EC devient indisponible ou corrompue, la restauration de cette partie ne peut être effectuée que sur un serveur avec une étiquette « correcte » ; si un tel serveur est indisponible à long terme (c'est-à-dire qu'il est totalement indisponible ou seulement temporairement occupé), cela signifiera automatiquement que le bloc devra être reconverti au format de conservation de toute façon (si la partie manquante est une partie de parité/somme de contrôle, le bloc sera simplement reconverti au format de copie en utilisant toutes les parties de données disponibles ; si une partie de données est manquante, elle sera restaurée sur un serveur de blocs hébergeant une autre partie du même bloc - ce qui n'est pas autorisé dans des circonstances normales - puis la conversion au format de copie suivra immédiatement).

En mode STANDARD, le système se comportera comme en mode STRICT lorsqu'il doit décider s'il convertira un nouveau bloc du format de copie au format EC, c'est-à-dire que N+2X à cette étape est calculé uniquement à partir de serveurs étiquetés « correctement ». Mais pour décider si les blocs existants doivent être reconvertis du format EC au format de copie, il examinera tous les serveurs disponibles, indépendamment des étiquettes, de sorte que N+X à cette étape est calculé à partir de tous les serveurs disponibles, comme en mode LOOSE. X. En cas de parties manquantes, s'il n'est pas possible de les restaurer sur des serveurs de blocs avec des étiquettes « correctes », le système adaptera également le comportement du mode LOOSE et tentera d'utiliser tous les serveurs disponibles.

Attention ! Lorsqu'un bloc est converti du format de copie au format EC, le système effectue d'abord une opération de « fractionnement local », c'est-à-dire qu'il sélectionne une copie du bloc et calcule toutes les parties EC nécessaires sur le serveur occupant cette copie sélectionnée. Ensuite, ces parties sont déplacées vers des serveurs de blocs distincts, correspondant aux étiquettes définies dans la classe de stockage pour le mode EC utilisé. Mais temporairement, entre le fractionnement et le « déplacement » des parties, elles peuvent être enregistrées sur un serveur de blocs « incorrect » même en mode STRICT. Ceci est dû aux mécanismes de l'opération de « fractionnement local ».

TEMPS

Pour les variables de temps, leur valeur peut être définie comme un nombre de secondes ou d'heures (entier), en fonction de l'unité minimale de la variable, ou comme une période de temps dans l'un des deux formats possibles :

premier format : #.#T où T est l'un de : s-secondes, m-minutes, h-heures, d-jours ou w-semaines ; les fractions de l'unité minimale seront arrondies à la valeur entière

deuxième format : #w#d#h#m#s, un nombre quelconque de définitions peut être omis, mais les définitions restantes doivent être dans l'ordre (donc #d#m est toujours une définition valide, mais #m#d ne l'est pas) ; plages : s,m : 0 à 59, h : 0 à 23, d : 0 à 6, w est illimité et la première définition est également toujours illimitée (c'est-à-dire que pour #d#h#m, d sera illimité)

Si l'unité minimale d'une variable est supérieure aux secondes, les unités en dessous de l'unité minimale ne seront pas acceptées. Par exemple, une variable dont l'unité minimale est l'heure n'acceptera pas les unités s et m.

Exemples :

1.5d équivaut à 1d12h, équivaut à 36h

2.5w équivaut à 2w3d12h, équivaut à 420h ; 2w84h n'est pas une période de temps valide (h n'est pas la première définition, elle est donc limitée par la plage 0 à 23)

COMPORTEMENT ARCHIVAGE

Les blocs ont l'indicateur d'archive défini lors de la boucle de maintenance des fichiers, ce qui signifie que le temps d'archivage défini par l'option -d est le temps minimum qui doit s'écouler avant que l'indicateur ne soit défini, et non le temps exact.

Le comportement par défaut du système est qu'une fois qu'un bloc a l'indicateur d'archive activé, il n'est PAS désactivé même si atime/ctime/mtime change, à moins que l'indicateur R ne soit défini par l'option -o. L'écriture sur un bloc désactivera toujours son indicateur d'archive.

Indicateurs d'archive :

C - utilise ctime du fichier pour déterminer si l'indicateur d'archive doit être activé - c'est l'indicateur par défaut

M - utilise mtime du fichier pour déterminer si l'indicateur d'archive doit être activé

A - utilise atime du fichier pour déterminer si l'indicateur d'archive doit être activé

R - réversible, si atime/mtime/ctime change pour un fichier, le système vérifie si l'indicateur d'archive doit être désactivé pour ses blocs

F - mode rapide, le bloc a l'indicateur d'archive activé dès que possible, tout ce qui est défini avec l'option -d est ignoré

P - mode « par bloc », utilise mtime du bloc pour déterminer si l'indicateur d'archive doit être activé

L'indicateur d'archive peut être modifié manuellement. Voir mfsarchive (1)

Remarque : l'état ARCHIVE ne signifie pas que les blocs ou les fichiers sont indisponibles, bloqués en écriture, etc. La désignation ARCHIVE est uniquement utilisée pour indiquer que ces données sont déjà destinées au stockage à long terme. Contrairement à l'état KEEP, qui signifie que les données sont « chaudes » et peuvent être modifiées fréquemment. La distinction entre les états KEEP et ARCHIVE sert donc uniquement à permettre une définition appropriée de la manière physique de stocker ces données. Du point de vue de l'utilisateur, le fichier est accessible de la même manière : il a des permissions, un nom identiques et se trouve dans le même répertoire. Par exemple, en raison du fait que l'écriture en mode EC peut être plus lente, nous suggérons de stocker les données « chaudes » (KEEP) en utilisant une copie et de les convertir au format EC (en attribuant le mode ARCHIVE) après un certain temps. Un autre exemple est le transfert automatique de données « froides » vers des disques et des serveurs de blocs plus anciens/plus lents/moins chers - en utilisant des étiquettes différentes.

PRIORITÉ DES CLASSES DE STOCKAGE

Les classes de stockage sont attribuées aux fichiers, mais un bloc (un fragment d'un fichier) peut appartenir à de nombreux fichiers, grâce au mécanisme d'instantané (voir mfssnapshots (1)). Si un bloc appartient à plusieurs fichiers avec des classes de stockage différentes, une classe de stockage doit être choisie pour spécifier comment les copies de ce bloc doivent être conservées dans le système. Jusqu'à la version 4.56.0 de MooseFS, une classe prédéfinie était artificiellement attribuée à un tel bloc. Actuellement, l'une des classes des fichiers sera utilisée, selon les priorités attribuées par l'utilisateur, pour être précis : le système choisira la classe avec la priorité la plus élevée parmi toutes les classes des fichiers.

Exemple 1 : 3 classes sont définies :
ClassA, avec une priorité de 100,
ClassB, avec une priorité de 206,
ClassC, avec une priorité de 1001.

Un bloc, appartenant à 2 fichiers, l'un dans ClassA, l'autre dans ClassB, sera stocké selon la définition fournie par classB (priorité plus élevée que ClassA).
Un bloc, appartenant à 3 fichiers, l'un dans ClassA, l'un dans ClassB, l'un dans ClassC, sera stocké selon la définition fournie par classC (priorité plus élevée que ClassA et ClassB).

Si deux classes ou plus ont la même priorité, alors les facteurs suivants seront pris en compte, par ordre d'importance, pour déterminer quelle classe sera choisie :
- une classe avec un niveau de redondance (RL) plus élevé sera choisie (le maximum des niveaux de redondance KEEP et ARCHIVE de chaque classe sera considéré comme le niveau de redondance de cette classe),
- une classe qui a le format EC en état ARCHIVE sera choisie plutôt qu'une classe sans EC,
- une classe qui utilise des étiquettes pour l'état KEEP ou ARCHIVE sera choisie plutôt qu'une classe sans étiquettes,
- une classe qui a le format EC en état TRASH sera choisie plutôt qu'une classe sans EC,
- une classe qui utilise des étiquettes pour l'état TRASH sera choisie plutôt qu'une classe sans étiquettes,
- si aucune des conditions ci-dessus n'est utilisée, une classe avec un identifiant de classe plus élevé sera utilisée.

Exemple 2 : 5 classes sont définies, toutes avec la même priorité (par exemple, la priorité par défaut 0) :
ClassA (id=1) a 3 copies en état KEEP (RL=2),
ClassB (id=2) a 2 copies en état KEEP et EC4+1 en état ARCHIVE (RL=1, a EC en ARCHIVE),
ClassC (id=3) a 2 copies en état KEEP, stockées sur des étiquettes X (RL=1, pas d'EC en ARCHIVE, a des étiquettes en KEEP),
ClassD (id=4) a 2 copies en état KEEP, stockées sur des étiquettes Y (RL=1, pas d'EC en ARCHIVE, a des étiquettes en KEEP),
ClassE (id=5) a 2 copies en état KEEP (RL=1).
Il y a également une classe ClassF définie, qui a une priorité de 77 et 2 copies en état KEEP (RL=1).

Un bloc, appartenant aux fichiers dans les classes : ClassA, ClassC et ClassE sera stocké selon la définition de ClassA (RL le plus élevé).
Un bloc, appartenant aux fichiers dans les classes : ClassB, ClassC sera stocké selon la définition de ClassB (même RL, mais ClassB a EC).
Un bloc, appartenant aux fichiers dans les classes : ClassC et ClassE sera stocké selon la définition de ClassC (même RL, mais ClassC a des étiquettes).
Un bloc, appartenant aux fichiers dans les classes : ClassC et ClassD sera stocké selon la définition de ClassD (même RL, pas d'EC, les deux ont des étiquettes, donc l'ID de classe le plus élevé est choisi).
Un bloc, appartenant aux fichiers dans 6 classes, de ClassA à ClassF, sera stocké selon la définition de ClassF, car celle-ci a une priorité plus élevée que toutes les autres classes (77>0).
Dans un système avec ces 6 classes de stockage, classE ne sera jamais utilisée pour un bloc appartenant à plusieurs fichiers, elle a la priorité la plus basse possible (0) et aucune condition supplémentaire pour justifier son choix (RL le plus bas existant, pas d'EC et pas d'étiquettes).

CLASSES DE STOCKAGE PRÉDÉFINIES

Une nouvelle instance MooseFS aura les classes suivantes prédéfinies :

2CP - seul l'état KEEP est défini, conserve 2 copies sur n'importe quelles étiquettes (classe par défaut pour le répertoire /)

3CP - seul l'état KEEP est défini, conserve 3 copies sur n'importe quelles étiquettes

EC4+1 - en état KEEP, conserve 2 copies sur n'importe quelles étiquettes, en état ARCHIVE, conserve les blocs au format EC4+1 sur n'importe quelles étiquettes, le délai d'archivage est de 1 jour et est calculé en utilisant ctime du fichier, les fichiers de moins de 512KiB ne seront pas convertis au format EC

EC4+2 - (pro uniquement) en état KEEP, conserve 3 copies sur n'importe quelles étiquettes, en état ARCHIVE, conserve les blocs au format EC4+2 sur n'importe quelles étiquettes, le délai d'archivage est de 1 jour et est calculé en utilisant ctime du fichier, les fichiers de moins de 512KiB ne seront pas convertis au format EC

EC8+1 - en état KEEP, conserve 2 copies sur n'importe quelles étiquettes, en état ARCHIVE, conserve les blocs au format EC8+1 sur n'importe quelles étiquettes, le délai d'archivage est de 1 jour et est calculé en utilisant ctime du fichier, les fichiers de moins de 512KiB ne seront pas convertis au format EC

EC8+2 - (pro uniquement) en état KEEP, conserve 3 copies sur n'importe quelles étiquettes, en état ARCHIVE, conserve les blocs au format EC8+2 sur n'importe quelles étiquettes, le délai d'archivage est de 1 jour et est calculé en utilisant ctime du fichier, les fichiers de moins de 512KiB ne seront pas convertis au format EC

Ces classes sont entièrement modifiables et supprimables et peuvent être remplacées par des classes choisies par l'utilisateur.

Jusqu'à la version 4.56.0 de MooseFS, les classes prédéfinies étaient différentes. Les informations suivantes concernent le comportement ancien de MooseFS. Dans les versions plus récentes de MooseFS, les classes mentionnées ci-dessous peuvent exister

as a result of an upgrade, but will behave exactly like any user-defined classes. This information is left here purely for informative reasons and will be removed from this manual page at some point:

(Behaviour up to version 4.56.0) "For compatibility reasons, every fresh or freshly upgraded instance of MooseFS has 9 predefined storage classes. Their names are single digits, from 1 to 9, and their definitions are * to 9*. They are equivalents of simple numeric goals from previous versions of the system. In case of an upgrade, all files that had goal N before upgrade, will now have N storage class. These classes can be modified only when option -f is specified. It is advised to create new storage classes in an upgraded system and migrate files with mfsxchgsclass tool, rather than modify the predefined classes. The predefined classes CANNOT be deleted."

EXEMPLES

Créez une nouvelle classe de stockage nommée "Class2Copies" avec 2 copies. La première copie sur un des chunkservers avec le label "A" et la seconde copie sur un des chunkservers avec le label "B" :

mfscreatesclass -K A,B Class2Copies

Créez une nouvelle classe de stockage nommée "Class3Copies". Les nouveaux chunks (-C) seront conservés partout avec 2 copies (2*). Bientôt après leur création, ils seront conservés (-K) en 3 copies : la première copie sur un des chunkservers avec le label "A", la seconde copie sur un des chunkservers avec le label "B" et la troisième sur n'importe quel chunkserver :

mfscreatesclass -C '2*' -K 'A,B,*' Class3Copies

Créez une nouvelle classe de stockage nommée "ClassEC4_1". Les chunks seront créés et conservés (-K) partout en 2 copies (2*) pendant 24 heures à partir de la création du fichier. Plus tard, ils seront archivés (-A) au format EC4+1 sur n'importe quel chunkserver :

mfscreatesclass -K '2*' -A '@4+1' ClassEC4_1

Modifiez la classe de stockage "ClassEC4_1" pour archiver les chunks 48 heures après la modification (et non la création) du fichier :

mfsmodifysclass -d 2d -o m ClassEC4_1

Modifiez la classe de stockage "Class3Copies" pour conserver les chunks sur d'autres chunkservers (mode LOOSE) si ceux avec les labels "A" et "B" sont trop occupés (surchargés) :

mfsmodifysclass -m l Class3Copies
