NOM

mfscreatesclass - Outil d'administration de classes de stockage MooseFS

SYNTAXE

mfscreatesclass [-?] [-M POINTDEMONTAGE] -K ETIQUETTES_CONSERVER [-c description] [-p priorite] [-g groupe_export] [-a admin_seulement] [-m mode_etiquettes] [-o mode_archivage] [-C ETIQUETTES_CREER] [-A ETIQUETTES_ARCHIVAGE [-d delai_archivage] [-s longueur_min_fichier]] [-T ETIQUETTES_CORBEILLE [-t retention_min_corbeille]] NOM_CLASSE_STOCKAGE...

mfsmodifysclass [-?] [-M POINTDEMONTAGE] [-c description] [-p priorite] [-g groupe_export] [-a admin_seulement] [-m mode_etiquettes] [-o mode_archivage] [-C ETIQUETTES_CREER] [-K ETIQUETTES_CONSERVER] [-A ETIQUETTES_ARCHIVAGE] [-d delai_archivage] [-s longueur_min_fichier] [-T ETIQUETTES_CORBEILLE] [-t retention_min_corbeille] NOM_CLASSE_STOCKAGE...

mfsdeletesclass [-?] [-M POINTDEMONTAGE] NOM_CLASSE_STOCKAGE...

mfsclonesclass [-?] [-M POINTDEMONTAGE] NOM_CLASSE_SOURCE NOM_CLASSE_DESTINATION...

mfsrenamesclass [-?] [-M POINTDEMONTAGE] NOM_CLASSE_SOURCE NOM_CLASSE_DESTINATION

mfslistsclass [-?] [-M POINTDEMONTAGE] [-l] [-i] [MODELE_GLOB_NOM_CLASSE]

mfsimportsclass [-?] [-M POINTDEMONTAGE] [-r] [-n nom_fichier]

DESCRIPTION

Il s'agit d'un ensemble d'outils pour gérer les classes de stockage MooseFS. Les classes de stockage sont utilisées pour définir la politique de redondance au sein du cluster. Elles doivent ensuite être appliquées à des objets MooseFS particuliers (fichiers ou dossiers) avec les outils mfssclass (voir mfssclass(1)). Une classe de stockage est un ensemble nommé d'expressions d'étiquettes et d'autres options. L'expression d'étiquettes indique le format de redondance, le niveau de redondance souhaité et la politique de stockage souhaitée. Le format de redondance peut être soit des copies, soit de l'effacement-codage (EC). Le niveau de redondance est soit le nombre de copies (de 1 à 9), soit le nombre de parties de données plus de parité (4+n ou 8+n), selon le format de redondance indiqué. La politique de stockage spécifie, par l'utilisation d'étiquettes, quels serveurs de chunks (chunkservers) doivent être utilisés pour le stockage physique des données assignées à la classe de stockage particulière.

mfscreatesclass crée une nouvelle classe de stockage avec les options données, décrites ci-dessous, et la nomme NOM_CLASSE_STOCKAGE ; plusieurs noms peuvent être fournis, auquel cas plusieurs classes de stockage avec la même définition seront créées.

mfsmodifysclass modifie les options données dans une classe ou des classes indiquées par les paramètres NOM_CLASSE_STOCKAGE.

mfsdeletesclass supprime la ou les classes indiquées par les paramètres NOM_CLASSE_STOCKAGE ; si l'une des classes n'est pas vide (c'est-à-dire si elle est toujours utilisée par certains objets MooseFS), elle ne sera pas supprimée et l'outil retournera une erreur et un message d'erreur sera affiché ; les classes vides seront supprimées dans tous les cas.

mfsclonesclass copie la classe indiquée par NOM_CLASSE_SOURCE sous un nouveau nom fourni avec NOM_CLASSE_DESTINATION.

mfsrenamesclass change le nom d'une classe de NOM_CLASSE_SOURCE à NOM_CLASSE_DESTINATION.

mfslistsclass liste toutes les classes.

mfsimportsclass importe les définitions de classes de stockage depuis stdin ou un fichier et les crée ; le format d'entrée doit être identique à la sortie de mfslistsclass -l.

OPTIONS

-C paramètre optionnel, qui indique au système sur quels serveurs de chunks, définis par l'expression ETIQUETTES_CREER, le chunk doit être écrit juste après sa création ; si ce paramètre n'est pas fourni pour une classe, les serveurs de chunks ETIQUETTES_CONSERVER seront utilisés.

-K paramètre obligatoire, qui indique au système sur quels serveurs de chunks, définis par l'expression ETIQUETTES_CONSERVER, le ou les chunks doivent toujours être conservés, sauf conditions spéciales comme la création, l'archivage et la suppression (déplacement vers la Corbeille), si elles sont définies.

-A paramètre optionnel, qui indique au système sur quels serveurs de chunks, définis par l'expression ETIQUETTES_ARCHIVAGE, le ou les chunks doivent être conservés à des fins d'archivage ; le système commence à traiter un chunk comme archive lorsque son atime/mtime/ctime (tel que défini par -o) est plus ancien que le nombre d'heures spécifié avec l'option -d ; voir également la section COMPORTEMENT D'ARCHIVAGE ci-dessous.

-d paramètre optionnel qui définit après combien de temps à partir de l'atime/mtime/ctime (tel que défini par -o) un fichier (et ses chunks) est traité comme archive ; l'unité minimale est l'heure, la valeur par défaut est 24 ; pour le formatage de la valeur, voir TEMPS.

-o paramètre optionnel qui définit les indicateurs d'archivage. C - ctime, M - mtime, A - atime, R - réversible, F - mode rapide, P - par chunk ; la valeur par défaut est C ; voir la section COMPORTEMENT D'ARCHIVAGE ci-dessous pour les détails.

-s paramètre optionnel qui définit la longueur minimale du fichier en octets qui peut être archivée ; la valeur par défaut est 0.

-T paramètre optionnel, qui indique au système sur quels serveurs de chunks, définis par l'expression ETIQUETTES_CORBEILLE, le ou les chunks des fichiers dans la Corbeille doivent être conservés ; voir également -t.

-t paramètre optionnel, qui définit combien de temps un fichier doit rester dans la Corbeille pour que le système utilise le schéma défini dans -T pour un chunk ; l'unité minimale est l'heure, la valeur par défaut est 0 ; pour le formatage de la valeur, voir TEMPS.

-c paramètre optionnel, qui définit une description de classe, pour la commodité de l'utilisateur (une chaîne, longueur maximale 255 octets).

-p paramètre optionnel, qui définit une priorité de classe ; la valeur par défaut est 0 ; voir la section PRIORITÉ DES CLASSES DE STOCKAGE.

-g paramètre optionnel, qui définit un groupe d'exportation de classe ; les valeurs possibles sont de 0 à 15, la valeur par défaut est 0 ; voir mfsexport.cfg(5) pour une explication.

-a peut être 1 ou 0 et indique si la classe de stockage est disponible pour tout le monde (0) ou uniquement pour l'administrateur (1).

-m mode d'étiquette utilisé ; les valeurs possibles sont l (ou L, loose, Loose, LOOSE) pour le mode LOOSE, d (ou D, std, Std, STD) pour le mode STANDARD et s (ou S, strict, Strict, STRICT) pour le mode STRICT ; si aucun mode n'est défini, le mode STANDARD est supposé ; le comportement des modes d'étiquettes est décrit ci-dessous dans la section MODES D'ÉTIQUETTES.

-l liste également les définitions, pas seulement les noms des classes de stockage existantes.

-i correspondance des noms de classe de stockage insensible à la casse.

-r remplace (écrase) les classes existantes lors de l'importation des classes de stockage.

-n utilise le nom de fichier fourni comme source des définitions de classes de stockage pour l'importation, au lieu de stdin.

-M MooseFS point de montage, il n'est pas nécessaire de le spécifier si un outil est exécuté à l'intérieur d'un répertoire monté MooseFS ou si MooseFS est monté dans /mnt/mfs/.

-? affiche un court message d'utilisation.

NOTES

EXPRESSIONS D'ÉTIQUETTES

Les étiquettes sont des lettres (A-Z - 26 lettres) qui peuvent être attribuées aux serveurs de chunks. Chaque serveur de chunks peut avoir plusieurs (jusqu'à 26) étiquettes. Les étiquettes sont définies dans le fichier mfschunkserver.cfg, pour plus d'informations, référez-vous à la page de manuel appropriée.

Une expression d'étiquettes est un ensemble de sous-expressions séparées par des virgules. Pour les copies complètes, chaque sous-expression spécifie le schéma de stockage d'une copie d'un fichier. Une sous-expression peut être : un astérisque ou un schéma d'étiquette. Un schéma d'étiquette peut être une seule étiquette ou une expression avec des sommes, des multiplications, des négations et des parenthèses. La somme signifie qu'un fichier peut être stocké sur n'importe quel serveur de chunks correspondant à n'importe quel élément de la somme (OU logique). La multiplication signifie qu'un fichier ne peut être stocké que sur un serveur de chunks correspondant à tous les éléments (ET logique). L'astérisque signifie n'importe quel serveur de chunks. La négation signifie n'importe quel serveur de chunks sauf celui correspondant à la sous-expression niée. Des sous-expressions identiques peuvent être raccourcies en ajoutant un nombre devant l'une au lieu de la répéter plusieurs fois.

Pour l'EC, l'expression d'étiquettes commence par le signe @, suivi du nombre de parties de données, puis du signe + et d'un nombre qui indique combien de parties de parité le chunk doit avoir. Nombre possible

EXPRESSIONS D'ÉTIQUETTES

Une expression d'étiquettes spécifie quels serveurs de blocs (chunkservers) peuvent être utilisés pour stocker des blocs de données. Elle est composée d'une ou plusieurs parties, séparées par des virgules. Chaque partie spécifie un ensemble de critères de sélection de serveurs. La sélection globale est une union de ces ensembles, c'est-à-dire qu'un bloc peut être stocké sur des serveurs correspondant à n'importe laquelle des parties.

Chaque partie de l'expression peut être une combinaison de plusieurs étiquettes, séparées par un signe plus (+). Cela correspond à une intersection d'étiquettes, c'est-à-dire qu'un serveur doit avoir toutes les étiquettes spécifiées dans cette partie pour être sélectionné. Par exemple, A+B signifie que le serveur doit avoir à la fois l'étiquette A et l'étiquette B.

Le nombre de copies d'un fichier est spécifié par un préfixe numérique. Par exemple, 2A signifie que le fichier doit avoir deux copies, chacune stockée sur un serveur ayant l'étiquette A. Si le nombre est omis, la valeur par défaut définie par DEFAULT_FILE_REPLICAS dans mfsmaster.cfg (5) est utilisée (typiquement 2).

Une expression d'étiquettes peut également spécifier des blocs à code d'effacement (EC - Erasure Code). Les parties EC sont précédées de '@'. Le nombre de parties de données est spécifié avant le signe plus (+) et le nombre de parties de parité après. Par exemple, @4+1 signifie que les blocs seront stockés au format EC avec 4 parties de données et 1 partie de parité. Le nombre de parties de données peut être 4 ou 8. Le nombre de parties de parité peut être 1 (version CE) ou de 1 à 9 (version PRO). Ainsi, par exemple, @4+1 signifie EC avec 4 parties de données et 1 partie de parité, @8+3 signifie EC avec 8 parties de données et 3 parties de parité. Si le nombre de parties de données est omis, le maître utilise la valeur par défaut définie par DEFAULT_EC_DATA_PARTS - voir mfsmaster.cfg (5). Dans ce cas, @2 signifie @8+2 ou @4+2. Ensuite, au maximum deux sous-expressions peuvent suivre, séparées par des virgules. Si une seule est présente, elle définit où toutes les parties doivent être conservées. Si les deux sont présentes, la première sous-expression définit où les parties de données doivent être conservées, la seconde sous-expression définit où les parties de parité doivent être conservées.

L'expression d'étiquettes peut être soit une expression d'étiquettes régulière, soit une expression d'étiquettes EC (c'est-à-dire qu'une expression d'étiquettes EC ne peut pas être une sous-expression). L'expression d'étiquettes EC ne peut être utilisée qu'à la place de ARCHIVE_LABELS ou TRASH_LABELS dans la définition de la classe de stockage, une expression d'étiquettes régulière peut être utilisée n'importe où.

À la fin de chaque expression d'étiquettes, une ou deux informations supplémentaires, séparées par un séparateur spécial, peuvent être ajoutées. La première extension possible est l'extension de distinction et le séparateur est le signe barre oblique (/), la seconde est la substitution du mode d'étiquettes et cette extension est séparée par le signe deux-points (:).

L'extension de distinction peut être une liste d'étiquettes ou l'une des chaînes spéciales suivantes :

[IP] ou [I] - distinguer par numéro IP

[RACK] ou [R] - distinguer par RACK, tel que défini dans la topologie, voir mfstopology.cfg (5)

Si elle est présente, la partie de distinction indique au système qu'il doit essayer de distribuer les copies complètes de manière à ce que chaque copie soit soit sur une étiquette différente de la liste, soit sur un chunkserver avec une adresse IP différente, soit d'un rack différent. Pour l'EC, la partie de distinction est actuellement ignorée.

REMARQUE ! Si CHUNKS_UNIQUE_MODE est défini dans mfsmaster.cfg à une valeur autre que 0, il remplacera tout paramètre de distinction dans les classes de stockage. Pour plus d'informations sur ce paramètre, reportez-vous au manuel de mfsmaster.cfg (5).

L'extension de substitution du mode d'étiquettes peut être l'un des trois caractères : d (alternativement D ou sous forme de chaîne std ou Std ou STD), s (alternativement S ou sous forme de chaîne strict ou Strict ou STRICT) ou l (alternativement L ou sous forme de chaîne loose ou Loose ou LOOSE) et ils signifient que le mode d'étiquettes STANDARD, STRICT ou LOOSE, respectivement, doit être appliqué uniquement à cette expression d'étiquettes. Pour une explication sur les modes d'étiquettes, voir la section MODES D'ÉTIQUETTES.

Une ou deux extensions peuvent être présentes pour chaque expression d'étiquettes, chacune doit commencer par son séparateur et si les deux sont présentes, l'ordre doit être conservé, c'est-à-dire que l'extension de distinction doit être la première et l'extension du mode d'étiquettes doit être la seconde.

Exemples d'expressions d'étiquettes :

A,B - les fichiers auront deux copies, une copie sera stockée sur le(s) chunkserver(s) avec l'étiquette A, l'autre sur le(s) chunkserver(s) avec l'étiquette B

A,* - les fichiers auront deux copies, une copie sera stockée sur le(s) chunkserver(s) avec l'étiquette A, l'autre sur n'importe quel(s) chunkserver(s)

A,!A - les fichiers auront deux copies, une copie sera stockée sur le(s) chunkserver(s) avec l'étiquette A, l'autre sur n'importe quel(s) chunkserver(s) qui n'ont pas l'étiquette A

*,* - les fichiers auront deux copies, stockées sur n'importe quel(s) chunkserver(s) (différent pour chaque copie)

AB,C+D+E - les fichiers auront deux copies, une copie sera stockée sur n'importe quel(s) chunkserver(s) qui ont à la fois les étiquettes A et B (multiplication des étiquettes), l'autre sur n'importe quel(s) chunkserver(s) qui a soit l'étiquette C, soit l'étiquette D, soit l'étiquette E (somme des étiquettes)

A,B[X+Y],C[X+Y] - les fichiers auront trois copies, une copie sera stockée sur n'importe quel(s) chunkserver(s) avec l'étiquette A, la deuxième sur n'importe quel(s) chunkserver(s) qui a l'étiquette B et soit l'étiquette X, soit l'étiquette Y, la troisième sur n'importe quel(s) chunkserver(s), qui a l'étiquette C et soit l'étiquette X, soit l'étiquette Y

L'expression 2A est équivalente à l'expression A,A

L'expression A,3BC est équivalente à l'expression A,BC,BC,BC

L'expression 2 est équivalente à l'expression 2* est équivalente à l'expression *,*

3*/[IP] - les fichiers auront 3 copies, chaque copie sera conservée sur un chunkserver avec une adresse IP différente

A,B/[RACK] - les fichiers auront deux copies, une copie sera stockée sur le(s) chunkserver(s) avec l'étiquette A, l'autre sur le(s) chunkserver(s) avec l'étiquette B dans un rack différent de l'autre copie

S,H,H/[RACK] - les fichiers auront 3 copies, une sur un serveur avec l'étiquette S, deux sur des serveurs avec l'étiquette H, mais chaque copie sera sur un serveur avec une étiquette différente de l'ensemble de A, B, X, Y, Z

@4+1 - les fichiers seront conservés au format EC, 4 parties de données et 1 partie de parité

@8+3 - les fichiers seront conservés au format EC, 8 parties de données et 3 parties de parité

@2 - les fichiers seront conservés au format EC, nombre par défaut de parties de données, 2 parties de parité

@4+3,Z - les fichiers seront conservés au format EC, 4 parties de données et 3 parties de parité - toutes sur des chunkservers avec l'étiquette Z.

@2,A(X+Y) - les fichiers seront conservés au format EC, nombre par défaut de parties de données, 2 parties de parité, toutes les parties seront conservées sur des chunkservers avec l'étiquette A et soit X, soit Y

@3,S,H - les fichiers seront conservés au format EC, le nombre par défaut de parties de données sera conservé sur des chunkservers avec l'étiquette S, 3 parties de parité seront conservées sur des chunkservers avec l'étiquette H

AB,AC:l - les fichiers seront conservés au format copies, une copie sur un serveur avec les étiquettes A et B, la seconde sur un serveur avec les étiquettes A et C et le comportement de cela doit être LOOSE

@4+2,X,Y:s - les fichiers seront conservés au format EC, 4 parties de données seront conservées sur des serveurs avec l'étiquette X, 2 parties de parité (checksum) devraient être conservées sur des serveurs avec l'étiquette Y et le comportement de cela devrait être STRICT

2A/[IP]:s - les fichiers devraient être conservés en 2 copies, les deux copies sur des serveurs avec l'étiquette A, mais chaque serveur devrait avoir une IP différente, le comportement de cela lors de la prise en compte des étiquettes devrait être STRICT

MODES D'ÉTIQUETTES

Il est important de spécifier quoi faire lorsqu'il n'est pas possible de satisfaire les exigences d'étiquettes d'une classe de stockage, c'est-à-dire : il n'y a pas d'espace disponible sur tous les serveurs avec les étiquettes requises, il n'y a pas assez de serveurs avec les étiquettes requises ou les serveurs avec les étiquettes requises sont tous occupés. La question est de savoir si le système doit créer des blocs sur d'autres serveurs (avec des étiquettes non conformes) ou non. Cette décision doit être prise par l'utilisateur.

Il existe 3 modes de fonctionnement : STANDARD, LOOSE et STRICT. Les modes fonctionnent un peu différemment selon que le bloc est stocké en copies ou au format EC, en raison de la nature et des algorithmes différents que chacun de ces formats utilise.

Pour le format copies, les 3 modes se comportent comme suit :

En mode STANDARD, en cas de surcharge des serveurs, le système attendra, mais en cas de manque d'espace, il utilisera d'autres serveurs et répliquera les données sur les serveurs corrects lorsque cela deviendra possible. Cela signifie que si certains serveurs sont en état d'occupation prolongée, il pourrait ne pas être possible de créer de nouveaux blocs avec certaines classes de stockage et les blocs menacés (en sous-objectif) de ces classes risquent davantage d'être complètement perdus en raison de réplications retardées.

En mode STRICT, lors de l'écriture d'un nouveau fichier, le système renverra une erreur (ENOSPC) en cas de manque d'espace sur les serveurs marqués avec les étiquettes spécifiées pour la création de blocs. Il attendra toujours les serveurs surchargés. Les réplications en sous-objectif ne seront pas effectuées s'il n'y a pas d'espace sur les serveurs ayant des étiquettes correspondant à la classe de stockage. Cela signifie un risque élevé de perte de données si les serveurs avec certaines étiquettes sont définitivement remplis de données !

En mode LOOSE, le système utilisera immédiatement d'autres serveurs en cas de surcharge des serveurs ou de manque d'espace sur les serveurs et répliquera les données sur les serveurs corrects lorsque cela deviendra possible. Il n'y a pas de délai ou d'erreur lors de la création de fichiers et les réplications en sous-objectif sont toujours effectuées dès que possible.

Ce tableau résume le comportement des modes pour les blocs stockés au format copie :

STANDARD STRICT LOOSE
CRÉATION - SURCHARGE ATTENDRE ATTENDRE ÉCRIRE N'IMPORTE OÙ
CRÉATION - PAS D'ESPACE ÉCRIRE N'IMPORTE OÙ ENOSPC ÉCRIRE N'IMPORTE OÙ
RÉPLICATION - SURCHARGE ATTENDRE ATTENDRE ÉCRIRE N'IMPORTE OÙ
RÉPLICATION - PAS D'ESPACE ÉCRIRE N'IMPORTE OÙ PAS DE COPIE ÉCRIRE N'IMPORTE OÙ

Pour les blocs stockés au format EC, les 3 modes se comportent comme suit :

En général, les blocs ne seront convertis du format copies au format EC que s'il y a suffisamment de serveurs dans le système pour stocker sécuritairement toutes les parties du format EC. Pour le format EC @N+X, où N est le nombre de parties de données et peut être soit 4 soit 8 et X est le nombre de parties de parité/checksum et peut être égal à 1 (version CE) ou n'importe quel nombre de 1 à 9 (version PRO), les exigences générales sont :
- au moins N+2X chunkservers pour convertir de nouveaux blocs du format copies au format EC
- au moins N+X chunkservers pour conserver les blocs déjà au format EC dans ce format
- s'il y a moins de N+X serveurs, tous les blocs reviendront au format copies (définition KEEP).

En mode LOOSE, le système utilisera d'abord les serveurs correspondant à l'expression d'étiquettes définie dans la classe de stockage utilisée, mais s'il n'y a pas assez de serveurs avec les étiquettes "correctes" disponibles (parce qu'ils sont occupés, n'ont pas d'espace ou ne sont tout simplement pas définis), il utilisera n'importe quel chunkserver disponible quelle que soit l'étiquette ; ainsi N+2X et N+X sont calculés à partir de tous les chunkservers disponibles lorsque le système décide du format à utiliser pour conserver un bloc. De plus, lorsqu'une partie d'un bloc au format EC devient indisponible ou corrompue, la restauration de cette partie sera également effectuée sur n'importe quel serveur disponible, si un serveur avec les étiquettes "correctes" ne peut pas être utilisé actuellement.

Il est important de se rappeler que s'il n'y a pas assez de serveurs avec les étiquettes "correctes" disponibles pour un bloc en mode LOOSE, le système peut utiliser n'importe quel nombre de "autres" chunkservers, pas seulement le nombre minimal qui manque par rapport au nombre "correct" de serveurs.

En mode STRICT, le système n'utilisera que les serveurs correspondant à l'expression d'étiquettes définie dans la classe de stockage utilisée, ainsi seuls les serveurs disponibles ou temporairement occupés

STORAGE CLASSES

Storage classes allow you to define different ways of storing data. This can be used for example to store frequently accessed data on faster disks and archive data on slower, cheaper ones. Each storage class defines various attributes such as:

  • Mode - defines how the system interacts with chunk servers that have specific labels, when converting chunks between copy and EC (Erase Coding) formats.

    • STRICT - Only servers with correctly matching labels for the desired format (KEEP or ARCHIVE) will be used.

    • STANDARD - When converting to EC format, only servers with correct labels are considered. However, when deciding to revert from EC to copy format, all available servers are considered, regardless of their labels. If restoration to correctly labeled servers is not possible, it defaults to the LOOSE behavior.

    • LOOSE - All available chunk servers are used for label matching, regardless of whether they match the required labels or not. This is the most flexible mode but may lead to less optimal storage choices.

  • Redundancy Level (RL) - defines the number of copies of a chunk to be kept in case of Copy format, or the parameters for EC format (e.g. EC4+1 means 4 data parts and 1 parity part).

  • Labels - Allows specifying which chunk servers should be used for storing data. This can be used to assign data to specific disks or groups of servers.

  • Archive Delay - specifies the minimum time that must pass before a chunk is considered for archiving.

  • Archive Conversion Parameters - settings related to the conversion of data to EC format for archiving.

Each storage class can define different settings for KEEP (active data) and ARCHIVE (less frequently accessed data) states. This allows for fine-grained control over data storage and retrieval.

EC MODE LABEL MATCHING

The label matching behaviour is determined by the Mode setting within a storage class. This setting dictates how chunk servers with specific labels are selected when the system needs to convert chunks between copy and EC (Erase Coding) formats.

In STRICT mode, only chunk servers that have labels matching the requirements for the target format (either KEEP or ARCHIVE) are considered. This ensures that data is stored according to the defined labeling strategy.

The servers matching defined label expression will be used for calculation of N+2X and N+X when the system decides what format to use to keep a chunk. When one part of a chunk in EC format becomes unavailable or corrupted, restoration of such part can only be done to a server with "correct" label; if such a server is unavailable long term (i.e. is not available outright or only temporarily busy), this will automatically mean that the chunk needs to be reverted to keep format anyway (if the missing part is a parity/checksum part, the chunk will just revert to copy format using all available data parts, if a data part is missing, it will be restored to a chunk server hosting another part of the same chunk - which is not allowed under normal circumstances - and then the conversion to copy format will follow immediately).

In STANDARD mode the system will behave like in STRICT mode when it needs to make a decision whether it will convert a new chunk from copy format to EC format, that is the N+2X in this step is calculated only from "correctly" labeled servers. But to make a decision whether existing chunks need to be converted back from EC format to copy format it will look at all available servers, regardless of labels, so the N+X in this step is calculated from all available servers, like in LOOSE mode. X. In case of missing parts, if it's not possible to restore them to chunk servers with "correct" labels, the system will also adapt the LOOSE mode behaviour and try to use any available servers.

Notice! When a chunk is converted from copy format to EC format, the system first performs a "local split" operation, that is it picks one copy of the chunk and calculates all EC parts necessary on the server occupied by this selected copy. Then these parts are moved to separate chunkservers, matching the labels in the storage class definition for used EC mode. But temporarily, between the split and the "moving out" of the parts, they can be recorded on a "wrong" chunk server even in STRICT mode. This is because of the mechanics of the "local split" operation.

TEMPS

Pour les variables temporelles, leur valeur peut être définie comme un nombre de secondes ou d'heures (entier), en fonction de l'unité minimale de la variable, ou comme une période de temps dans l'un des deux formats possibles:

premier format : #.#T où T est l'un des éléments suivants : s-secondes, m-minutes, h-heures, d-jours ou w-semaines ; les fractions de l'unité minimale seront arrondies à la valeur entière

deuxième format : #w#d#h#m#s, n'importe quel nombre de définitions peut être omis, mais les définitions restantes doivent être dans l'ordre (ainsi #d#m est toujours une définition valide, mais #m#d ne l'est pas) ; plages : s,m : 0 à 59, h : 0 à 23, d : 0 à 6, w est illimité et la première définition est également toujours illimitée (c'est-à-dire que pour #d#h#m, d sera illimité)

Si une unité minimale d'une variable est supérieure aux secondes, les unités inférieures à l'unité minimale ne seront pas acceptées. Par exemple, une variable dont les heures sont l'unité minimale n'acceptera pas les unités s et m.

Exemples :

1.5d équivaut à 1d12h, équivaut à 36h

2.5w équivaut à 2w3d12h, équivaut à 420h ; 2w84h n'est pas une période de temps valide (h n'est pas la première définition, elle est donc limitée à la plage 0 à 23)

COMPORTEMENT D'ARCHIVAGE

Les blocs ont le drapeau d'archive défini lors de la boucle de maintenance des fichiers, ce qui signifie que le délai d'archivage défini par l'option -d est le temps minimum qui doit s'écouler avant que le drapeau ne soit défini, et non le temps exact.

Le comportement par défaut du système est qu'une fois qu'un bloc a le drapeau d'archive activé, il N'EST PAS désactivé même si atime/ctime/mtime changent, à moins que le drapeau R ne soit défini par l'option -o. L'écriture sur un bloc désactive toujours son drapeau d'archive.

Drapeaux d'archive :

C - utilise ctime du fichier pour déterminer si le drapeau d'archive doit être activé - c'est le drapeau par défaut

M - utilise mtime du fichier pour déterminer si le drapeau d'archive doit être activé

A - utilise atime du fichier pour déterminer si le drapeau d'archive doit être activé

R - réversible, si atime/mtime/ctime changent pour un fichier, le système vérifie si le drapeau d'archive doit être désactivé pour ses blocs

F - mode rapide, le bloc a son drapeau d'archive activé dès que possible, tout ce qui est défini avec l'option -d est ignoré

P - mode "par bloc", utilise mtime du bloc pour déterminer si le drapeau d'archive doit être activé

Le drapeau d'archive peut être modifié manuellement. Voir mfsarchive (1)

Remarque : l'état ARCHIVE ne signifie pas que les blocs ou les fichiers sont indisponibles, bloqués en écriture, etc. La désignation ARCHIVE sert uniquement à indiquer que ces données sont déjà destinées au stockage à long terme. Contrairement à l'état KEEP, qui signifie que les données sont "chaudes" et peuvent être modifiées fréquemment. La distinction entre les états KEEP et ARCHIVE sert donc uniquement à permettre une définition appropriée de la manière physique de stocker ces données. Du point de vue de l'utilisateur, le fichier est accessible de la même manière : il a des permissions, un nom identiques, et se trouve dans le même répertoire. Par exemple, en raison du fait que l'écriture en mode EC peut être plus lente, nous suggérons de stocker les données "chaudes" (KEEP) en utilisant une copie et de les convertir en format EC (en attribuant le mode ARCHIVE) après un certain temps. Un autre exemple est le transfert automatique des données "froides" vers des disques/blocs plus anciens/lents/bon marché - en utilisant des étiquettes différentes.

PRIORITÉ DES CLASSES DE STOCKAGE

Les classes de stockage sont attribuées aux fichiers, mais un bloc (un fragment d'un fichier) peut appartenir à plusieurs fichiers, grâce au mécanisme de snapshot (voir mfssnapshots (1)). Si un bloc appartient à plusieurs fichiers avec des classes de stockage différentes, une classe de stockage doit être choisie pour spécifier comment les copies de ce bloc doivent être conservées dans le système. Jusqu'à la version 4.56.0 de MooseFS, une classe prédéfinie était attribuée artificiellement à un tel bloc. Actuellement, l'une des classes des fichiers sera utilisée, selon les priorités attribuées par l'utilisateur, pour être exact : le système choisira la classe avec la plus haute priorité parmi toutes les classes des fichiers.

Exemple 1 : il y a 3 classes définies :
ClassA, avec une priorité de 100,
ClassB, avec une priorité de 206,
ClassC, avec une priorité de 1001.

Un bloc, qui appartient à 2 fichiers, l'un en ClassA, l'autre en ClassB, sera stocké selon la définition fournie par classB (priorité plus élevée que ClassA).
Un bloc, qui appartient à 3 fichiers, l'un en ClassA, un en ClassB, un en ClassC, sera stocké selon la définition fournie par classC (priorité plus élevée que ClassA et ClassB).

Si deux classes ou plus ont la même priorité, alors les facteurs suivants seront pris en compte, par ordre d'importance, pour déterminer quelle classe sera choisie :
- une classe avec un niveau de redondance (RL) plus élevé sera choisie (le maximum des niveaux de redondance KEEP et ARCHIVE de chaque classe sera considéré comme le niveau de redondance de cette classe),
- une classe qui a le format EC en état ARCHIVE sera choisie plutôt qu'une classe sans EC,
- une classe qui utilise des étiquettes pour l'état KEEP ou ARCHIVE sera choisie plutôt qu'une classe sans étiquettes,
- une classe qui a le format EC en état TRASH sera choisie plutôt qu'une classe sans EC,
- une classe qui utilise des étiquettes pour l'état TRASH sera choisie plutôt qu'une classe sans étiquettes,
- si aucune des conditions ci-dessus n'est utilisée, une classe avec un id de classe plus élevé sera utilisée.

Exemple 2 : il y a 5 classes définies, toutes avec la même priorité (par exemple, la priorité par défaut 0) :
ClassA (id=1) a 3 copies en état KEEP (RL=2),
ClassB (id=2) a 2 copies en état KEEP et EC4+1 en état ARCHIVE (RL=1, a EC en ARCHIVE),
ClassC (id=3) a 2 copies en état KEEP, stockées sur des étiquettes X (RL=1, pas d'EC en ARCHIVE, a des étiquettes en KEEP),
ClassD (id=4) a 2 copies en état KEEP, stockées sur des étiquettes Y (RL=1, pas d'EC en ARCHIVE, a des étiquettes en KEEP),
ClassE (id=5) a 2 copies en état KEEP (RL=1).
Il y a aussi une classe ClassF définie, qui a une priorité de 77 et 2 copies en état KEEP (RL=1).

Un bloc, qui appartient aux fichiers dans les classes : ClassA, ClassC et ClassE sera stocké selon la définition de ClassA (RL la plus élevée).
Un bloc, qui appartient aux fichiers dans les classes : ClassB, ClassC sera stocké selon la définition de ClassB (RL identique, mais ClassB a EC).
Un bloc, qui appartient aux fichiers dans les classes : ClassC et ClassE sera stocké selon la définition de ClassC (RL identique, mais ClassC a des étiquettes).
Un bloc, qui appartient aux fichiers dans les classes : ClassC et ClassD sera stocké selon la définition de ClassD (RL identique, pas d'EC, les deux ont des étiquettes, donc l'ID de classe plus élevé est choisi).
Un bloc, qui appartient à 6 classes de fichiers, de ClassA à ClassF, sera stocké selon la définition de ClassF, car celle-ci a une priorité plus élevée que toutes les autres classes (77>0).
Dans un système avec ces 6 classes de stockage, classE ne sera jamais utilisée pour un bloc appartenant à plusieurs fichiers, elle a la priorité la plus basse possible (0) et aucune condition supplémentaire pour justifier son choix (RL le plus bas existant, pas d'EC et pas d'étiquettes).

CLASSES DE STOCKAGE PRÉDÉFINIES

Une nouvelle instance MooseFS aura les classes suivantes prédéfinies :

2CP - seul l'état KEEP est défini, conserve 2 copies sur toutes les étiquettes (classe par défaut pour le répertoire /)

3CP - seul l'état KEEP est défini, conserve 3 copies sur toutes les étiquettes

EC4+1 - en état KEEP, conserve 2 copies sur toutes les étiquettes, en état ARCHIVE, conserve les blocs au format EC4+1 sur toutes les étiquettes, le délai d'archivage est de 1 jour et est calculé à l'aide de ctime du fichier, les fichiers de moins de 512kiB ne seront pas convertis au format EC

EC4+2 - (pro uniquement) en état KEEP, conserve 3 copies sur toutes les étiquettes, en état ARCHIVE, conserve les blocs au format EC4+2 sur toutes les étiquettes, le délai d'archivage est de 1 jour et est calculé à l'aide de ctime du fichier, les fichiers de moins de 512kiB ne seront pas convertis au format EC

EC8+1 - en état KEEP, conserve 2 copies sur toutes les étiquettes, en état ARCHIVE, conserve les blocs au format EC8+1 sur toutes les étiquettes, le délai d'archivage est de 1 jour et est calculé à l'aide de ctime du fichier, les fichiers de moins de 512kiB ne seront pas convertis au format EC

EC8+2 - (pro uniquement) en état KEEP, conserve 3 copies sur toutes les étiquettes, en état ARCHIVE, conserve les blocs au format EC8+2 sur toutes les étiquettes, le délai d'archivage est de 1 jour et est calculé à l'aide de ctime du fichier, les fichiers de moins de 512kiB ne seront pas convertis au format EC

Ces classes sont entièrement modifiables et supprimables et peuvent être remplacées par le choix de classes de l'utilisateur.

Jusqu'à la version 4.56.0 de MooseFS, les classes prédéfinies étaient différentes. Les informations suivantes concernent le comportement ancien de MooseFS. Dans les versions plus récentes de MooseFS, les classes mentionnées ci-dessous pourraient exister

DESCRIPTION

L'utilitaire mfscreatesclass crée une nouvelle classe de stockage nommée nom_classe. Les classes de stockage définissent des stratégies de stockage pour les fichiers, telles que le nombre de copies, les labels des serveurs de blocs sur lesquels les copies doivent être stockées, le format d'archivage et le délai avant l'archivage.

Les classes de stockage sont utilisées par la commande mfssetgoal pour définir les objectifs de stockage pour les fichiers.

OPTIONS

Vous pouvez spécifier plusieurs options dans une seule commande mfscreatesclass pour définir différentes politiques pour les fichiers selon le moment où ils sont créés ou modifiés, ou selon qu'ils sont en ligne ou archivés.

-C

politique

Définit la politique de stockage pour les nouvelles données créées. La politique est un nombre de copies. Par exemple, -C 3 pour 3 copies.
-K

politique

Définit la politique de stockage pour le maintien des données (en ligne). La politique est un nombre de copies ou une liste de labels de serveurs de blocs séparés par des virgules. Par exemple, -K 2 pour 2 copies, ou -K A,B pour stocker les copies sur des serveurs avec les labels A et B.
-A

politique

Définit la politique de stockage pour l'archivage des données. La politique peut être un format d'archivage (par exemple, @4+1 pour l'archivage Reed-Solomon 4+1) ou une liste de labels de serveurs de blocs séparés par des virgules.
-M

politique

Définit la politique pour les métadonnées des données archivées.
-T

politique

Définit la politique pour les données temporaires.
-L

politique

Définit la politique de stockage en cas de surcharge. Les copies seront stockées sur d'autres serveurs de blocs si ceux spécifiés dans les options -K, -C, etc. sont surchargés.
-d

délai

Définit le délai avant l'archivage des données. Le délai peut être spécifié en jours (par exemple, 7d) ou en heures (par exemple, 24h).
-o

mode

Définit le mode de conservation des données après l'archivage. Les modes possibles sont m (maintenir les données d'origine) ou a (supprimer les données d'origine après l'archivage).
-r

ratio

Définit le ratio de compression pour l'archivage.
-m

mode

-p

NOTES

Les classes de stockage prédéfinies sont créées automatiquement lors de l'installation de MooseFS. Elles sont nommées de 1 à 9 et leurs définitions sont 1* à 9*.

Ces classes prédéfinies ne peuvent pas être supprimées. Il est recommandé de créer de nouvelles classes de stockage personnalisées plutôt que de modifier les classes prédéfinies.

Les classes de stockage sont stockées dans le fichier de configuration du gestionnaire MooseFS (généralement mfsmaster.cfg).

Les classes de stockage prédéfinies peuvent être modifiées uniquement avec l'option -f. Il est conseillé de créer de nouvelles classes de stockage dans un système mis à niveau et de migrer les fichiers avec l'outil mfsxchgsclass plutôt que de modifier les classes prédéfinies. Les classes prédéfinies NE PEUVENT PAS être supprimées.

(Comportement jusqu'à la version 4.56.0) Pour des raisons de compatibilité, chaque instance neuve ou récemment mise à niveau de MooseFS possède 9 classes de stockage prédéfinies. Leurs noms sont des chiffres uniques, de 1 à 9, et leurs définitions sont \* à 9\*. Elles sont équivalentes aux objectifs numériques simples des versions précédentes du système. En cas de mise à niveau, tous les fichiers qui avaient l'objectif N avant la mise à niveau auront désormais la classe de stockage N. Ces classes ne peuvent être modifiées qu'en spécifiant l'option -f. Il est conseillé de créer de nouvelles classes de stockage dans un système mis à niveau et de migrer les fichiers avec l'outil mfsxchgsclass, plutôt que de modifier les classes prédéfinies. Les classes prédéfinies NE PEUVENT PAS être supprimées.

EXEMPLES

Créer une nouvelle classe de stockage nommée "Class2Copies" avec 2 copies. La première copie sur un des serveurs de blocs avec le label "A" et la seconde copie sur un des serveurs de blocs avec le label "B":

mfscreatesclass -K A,B Class2Copies

Créer une nouvelle classe de stockage nommée "Class3Copies". Les nouveaux blocs créés (-C) seront conservés n'importe où avec 2 copies (2*). Peu après leur création, ils seront conservés (-K) en 3 copies : la première copie sur un des serveurs de blocs avec le label "A", la seconde copie sur un des serveurs de blocs avec le label "B" et la troisième sur n'importe quel serveur de blocs :

mfscreatesclass -C '2*' -K 'A,B,*' Class3Copies

Créer une nouvelle classe de stockage nommée "ClassEC4_1". Les blocs seront créés et conservés (-K) n'importe où en 2 copies (2*) pendant 24 heures à partir de la création du fichier. Plus tard, ils seront archivés (-A) au format EC4+1 sur n'importe quel serveur de blocs :

mfscreatesclass -K '2*' -A '@4+1' ClassEC4_1

Modifier la classe de stockage "ClassEC4_1" pour archiver les blocs après 48 heures à partir de la modification du fichier (et non de la création) :

mfsmodifysclass -d 2d -o m ClassEC4_1

Modifier la classe de stockage "Class3Copies" pour conserver les blocs sur d'autres serveurs de blocs (mode LOOSE) si ceux avec les labels "A" et "B" sont trop occupés (surchargés) :

mfsmodifysclass -m l Class3Copies
