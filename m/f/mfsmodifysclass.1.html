DESCRIPTION

Il s'agit d'un ensemble d'outils pour gérer les classes de stockage MooseFS. Les classes de stockage sont utilisées pour définir la politique de redondance au sein du cluster. Elles doivent être appliquées ultérieurement à des objets MooseFS particuliers (fichiers ou dossiers) avec les outils mfssclass (voir mfssclass(1)). Une classe de stockage est un ensemble nommé d'expressions d'étiquettes et d'autres options. L'expression d'étiquettes indique le format de redondance, le niveau de redondance souhaité et la politique de stockage souhaitée. Le format de redondance peut être soit des copies, soit de l'effacement-codage (EC). Le niveau de redondance est soit le nombre de copies (de 1 à 9), soit le nombre de parties de données plus parité (4+n ou 8+n), selon le format de redondance indiqué. La politique de stockage spécifie, par l'utilisation d'étiquettes, quels serveurs de blocs doivent être utilisés pour le stockage physique des données attribuées à la classe de stockage particulière.

mfscreatesclass crée une nouvelle classe de stockage avec les options données, décrites ci-dessous, et la nomme NOM_CLASSE_STOCKAGE ; il peut y avoir plus d'un nom fourni, auquel cas plusieurs classes de stockage avec la même définition seront créées.

mfsmodifysclass modifie les options données dans une classe ou des classes indiquées par les paramètres NOM_CLASSE_STOCKAGE.

mfsdeletesclass supprime la ou les classes indiquées par les paramètres NOM_CLASSE_STOCKAGE ; si l'une des classes n'est pas vide (c'est-à-dire si elle est encore utilisée par des objets MooseFS), elle ne sera pas supprimée et l'outil retournera une erreur et un message d'erreur sera imprimé ; les classes vides seront supprimées dans tous les cas.

mfsclonesclass copie la classe indiquée par NOM_CLASSE_SOURCE sous un nouveau nom fourni avec NOM_CLASSE_DESTINATION.

mfsrenamesclass change le nom d'une classe de NOM_CLASSE_SOURCE à NOM_CLASSE_DESTINATION.

mfslistsclass liste toutes les classes.

mfsimportsclass importe les définitions de classes de stockage depuis stdin ou un fichier et les crée ; le format d'entrée doit être identique à la sortie de mfslistsclass -l.

OPTIONS

-C paramètre optionnel, qui indique au système sur quels serveurs de blocs, définis par l'expression ETIQUETTES_CREER, le bloc devrait être écrit en premier juste après sa création ; si ce paramètre n'est pas fourni pour une classe, les serveurs de blocs ETIQUETTES_CONSERVER seront utilisés.

-K paramètre obligatoire, qui indique au système sur quels serveurs de blocs, définis par l'expression ETIQUETTES_CONSERVER, le bloc (ou les blocs) doit toujours être conservé, sauf conditions spéciales comme la création, l'archivage et la suppression (déplacement vers la Corbeille), si elles sont définies.

-A paramètre optionnel, qui indique au système sur quels serveurs de blocs, définis par l'expression ETIQUETTES_ARCHIVAGE, le bloc (ou les blocs) doit être conservé à des fins d'archivage ; le système commence à traiter un bloc comme archive lorsque atime/mtime/ctime (tel que défini par -o) du fichier auquel il appartient est plus ancien que le nombre d'heures spécifié par l'option -d ; voir aussi la section COMPORTEMENT D'ARCHIVAGE ci-dessous.

-d paramètre optionnel qui définit après combien de temps depuis atime/mtime/ctime (tel que défini par -o) un fichier (et ses blocs) est traité comme archive ; l'unité minimale est l'heure, la valeur par défaut est 24, pour le formatage de la valeur voir TEMPS.

-o paramètre optionnel qui définit les indicateurs d'archive. C - ctime, M - mtime, A - atime, R - réversible, F - mode rapide, P - par bloc ; par défaut est C ; voir la section COMPORTEMENT D'ARCHIVAGE ci-dessous pour plus de détails.

-s paramètre optionnel qui définit la longueur minimale du fichier en octets qui peut être archivée ; par défaut est 0.

-T paramètre optionnel, qui indique au système sur quels serveurs de blocs, définis par l'expression ETIQUETTES_CORBEILLE, le bloc (ou les blocs) des fichiers dans la Corbeille doit être conservé ; voir aussi -t.

-t paramètre optionnel, qui définit combien de temps dans la Corbeille doit s'écouler pour que le système utilise réellement le schéma défini dans -T pour un bloc ; l'unité minimale est l'heure, par défaut est 0, pour le formatage de la valeur voir TEMPS.

-c paramètre optionnel, qui définit une description de classe, pour la commodité de l'utilisateur (une chaîne de caractères, longueur maximale de 255 octets).

-p paramètre optionnel, qui définit une priorité de classe ; la valeur par défaut est 0, voir la section PRIORITÉ DES CLASSES DE STOCKAGE.

-g paramètre optionnel, qui définit un groupe d'exportation de classe ; les valeurs possibles sont de 0 à 15, par défaut est 0 ; voir mfsexport.cfg(5) pour une explication.

-a peut être soit 1 soit 0 et indique si la classe de stockage est disponible pour tout le monde (0) ou seulement pour l'administrateur (1).

-m mode d'étiquettes utilisé ; les valeurs possibles sont l (ou L, loose, Loose, LOOSE) pour le mode LOOSE, d (ou D, std, Std, STD) pour le mode STANDARD et s (ou S, strict, Strict, STRICT) pour le mode STRICT ; si aucun mode n'est défini, le mode STANDARD est supposé ; le comportement des modes d'étiquettes est décrit ci-dessous dans la section MODES D'ÉTIQUETTES.

-l liste également les définitions, pas seulement les noms des classes de stockage existantes.

-i correspondance de nom de classe de stockage insensible à la casse.

-r remplace (écrase) les classes existantes lors de l'importation des classes de stockage.

-n utilise le nom de fichier fourni comme source des définitions de classes de stockage pour l'importation, au lieu de stdin.

-M point de montage MooseFS, il n'est pas nécessaire de le spécifier si un outil est exécuté dans un répertoire monté MooseFS ou si MooseFS est monté dans /mnt/mfs/.

-? affiche un bref message d'utilisation.

NOTES

EXPRESSIONS D'ÉTIQUETTES

Les étiquettes sont des lettres (A-Z - 26 lettres) qui peuvent être attribuées aux serveurs de blocs. Chaque serveur de blocs peut avoir plusieurs (jusqu'à 26) étiquettes. Les étiquettes sont définies dans le fichier mfschunkserver.cfg, pour plus d'informations, veuillez vous référer à la page de manuel appropriée.

L'expression d'étiquettes est un ensemble de sous-expressions séparées par des virgules. Pour des copies complètes, chaque sous-expression spécifie le schéma de stockage d'une copie d'un fichier. Une sous-expression peut être : un astérisque ou un schéma d'étiquettes. Un schéma d'étiquettes peut être une seule étiquette ou une expression avec des sommes, des multiplications, des négations et des parenthèses. La somme signifie qu'un fichier peut être stocké sur n'importe quel serveur de blocs correspondant à n'importe quel élément de la somme (ou logique). La multiplication signifie qu'un fichier ne peut être stocké que sur un serveur de blocs correspondant à tous les éléments (et logique). L'astérisque signifie n'importe quel serveur de blocs. La négation signifie n'importe quel serveur de blocs sauf celui qui correspond à la sous-expression niée. Des sous-expressions identiques peuvent être raccourcies en ajoutant un nombre devant l'une d'elles au lieu de la répéter un certain nombre de fois.

Pour l'EC, l'expression d'étiquettes commence par le signe @, suivi d'un nombre de parties de données, puis du signe + et d'un nombre qui indique combien de parties de parité le bloc doit avoir. Nombre possible

LABELS

The number of data parts are 4 or 8. The possible number of parity parts are 1 (version CE) or 1 to 9 (version PRO). Ainsi, par exemple, @4+1 signifie EC avec 4 parties de données et 1 partie de parité, @8+3 signifie EC avec 8 parties de données et 3 parties de parité. Si le nombre de parties de données est omis, le maître utilise la valeur par défaut définie par DEFAULT_EC_DATA_PARTS - voir mfsmaster.cfg (5). Dans ce cas, @2 signifie @8+2 ou @4+2. Ensuite, au maximum deux sous-expressions peuvent suivre, séparées par des virgules. S'il n'y en a qu'une, elle définit où toutes les parties doivent être conservées. S'il y en a deux, la première sous-expression définit où les parties de données doivent être conservées, la seconde sous-expression définit où les parties de parité doivent être conservées.

L'expression des étiquettes peut être soit une expression régulière d'étiquettes, soit une expression d'étiquettes EC (c'est-à-dire qu'une expression d'étiquettes EC ne peut pas être une sous-expression). L'expression d'étiquettes EC ne peut être utilisée qu'à la place de ARCHIVE_LABELS ou TRASH_LABELS dans la définition de la classe de stockage, une expression régulière d'étiquettes peut être utilisée n'importe où.

À la fin de chaque expression d'étiquettes, une ou deux informations supplémentaires, séparées par un séparateur spécial, peuvent être ajoutées. La première extension possible est l'extension de distinction et le séparateur est le signe barre oblique (/), la seconde est la substitution du mode d'étiquettes et cette extension est séparée par un signe deux-points (:).

L'extension de distinction peut être une liste d'étiquettes ou l'une des chaînes spéciales suivantes :

[IP] ou [I] - distinguer par numéro IP

[RACK] ou [R] - distinguer par RACK, tel que défini dans la topologie, voir mfstopology.cfg (5)

Si elle est présente, la partie de distinction indique au système qu'il doit essayer de distribuer des copies complètes de telle sorte que chaque copie soit soit sur une étiquette différente de la liste, soit sur un chunkserver avec une adresse IP différente, soit dans un rack différent. Pour EC, la partie de distinction est actuellement ignorée.

ATTENTION ! Si CHUNKS_UNIQUE_MODE est défini dans mfsmaster.cfg à une valeur autre que 0, il remplacera tout paramètre de distinction dans les classes de stockage. Pour plus d'informations sur ce paramètre, référez-vous au manuel mfsmaster.cfg (5).

L'extension de substitution du mode d'étiquettes peut être l'un des trois caractères : d (alternativement D ou sous forme de chaîne std ou Std ou STD), s (alternativement S ou sous forme de chaîne strict ou Strict ou STRICT) ou l (alternativement L ou sous forme de chaîne loose ou Loose ou LOOSE) et ils signifient que le mode d'étiquettes STANDARD, STRICT ou LOOSE, respectivement, doit être appliqué uniquement à cette expression d'étiquettes. Pour une explication des modes d'étiquettes, voir la section MODES D'ÉTIQUETTES.

Une ou deux extensions peuvent être présentes pour chaque expression d'étiquettes, chacune doit commencer par son séparateur et si les deux sont présentes, l'ordre doit être respecté, c'est-à-dire que l'extension de distinction doit être la première et l'extension de mode d'étiquettes doit être la seconde.

Exemples d'expressions d'étiquettes :

A,B - les fichiers auront deux copies, une copie sera stockée sur le(s) chunkserver(s) avec l'étiquette A, l'autre sur le(s) chunkserver(s) avec l'étiquette B

A,* - les fichiers auront deux copies, une copie sera stockée sur le(s) chunkserver(s) avec l'étiquette A, l'autre sur n'importe quel(s) chunkserver(s)

A,!A - les fichiers auront deux copies, une copie sera stockée sur le(s) chunkserver(s) avec l'étiquette A, l'autre sur n'importe quel(s) chunkserver(s) qui n'a pas l'étiquette A

*,* - les fichiers auront deux copies, stockées sur n'importe quel(s) chunkserver(s) (différent pour chaque copie)

AB,C+D+E - les fichiers auront deux copies, une copie sera stockée sur n'importe quel(s) chunkserver(s) ayant à la fois les étiquettes A et B (multiplication des étiquettes), l'autre sur n'importe quel(s) chunkserver(s) ayant soit l'étiquette C, soit l'étiquette D, soit l'étiquette E (somme des étiquettes)

A,B[X+Y],C[X+Y] - les fichiers auront trois copies, une copie sera stockée sur n'importe quel(s) chunkserver(s) avec l'étiquette A, la deuxième sur n'importe quel(s) chunkserver(s) ayant l'étiquette B et soit l'étiquette X, soit l'étiquette Y, la troisième sur n'importe quel(s) chunkserver(s) ayant l'étiquette C et soit l'étiquette X, soit l'étiquette Y

L'expression 2A est équivalente à l'expression A,A

L'expression A,3BC est équivalente à l'expression A,BC,BC,BC

L'expression 2 est équivalente à l'expression 2* est équivalente à l'expression *,*

3*/[IP] - les fichiers auront 3 copies, chaque copie sera conservée sur un chunkserver avec une adresse IP différente

A,B/[RACK] - les fichiers auront deux copies, une copie sera stockée sur le(s) chunkserver(s) avec l'étiquette A, l'autre sur le(s) chunkserver(s) avec l'étiquette B dans un rack différent de l'autre copie

S,H,H/[RACK] - les fichiers auront 3 copies, une sur un serveur avec l'étiquette S, deux sur des serveurs avec l'étiquette H, mais chaque copie sera sur un serveur avec une étiquette différente de l'ensemble A, B, X, Y, Z

@4+1 - les fichiers seront conservés au format EC, 4 parties de données et 1 partie de parité

@8+3 - les fichiers seront conservés au format EC, 8 parties de données et 3 parties de parité

@2 - les fichiers seront conservés au format EC, nombre de parties de données par défaut, 2 parties de parité

@4+3,Z - les fichiers seront conservés au format EC, 4 parties de données et 3 parties de parité - toutes sur les chunkservers avec l'étiquette Z.

@2,A(X+Y) - les fichiers seront conservés au format EC, nombre de parties de données par défaut, 2 parties de parité, toutes les parties seront conservées sur les chunkservers avec l'étiquette A et soit X, soit Y

@3,S,H - les fichiers seront conservés au format EC, le nombre par défaut de parties de données sera conservé sur les chunkservers avec l'étiquette S, 3 parties de parité seront conservées sur les chunkservers avec l'étiquette H

AB,AC:l - les fichiers seront conservés au format de copies, une copie sur un serveur avec les étiquettes A et B, la seconde sur un serveur avec les étiquettes A et C et le comportement de ceci sera LOOSE

@4+2,X,Y:s - les fichiers seront conservés au format EC, 4 parties de données seront conservées sur les serveurs avec l'étiquette X, 2 parties de parité (checksum) devraient être conservées sur les serveurs avec l'étiquette Y et le comportement de ceci devrait être STRICT

2A/[IP]:s - les fichiers devraient être conservés en 2 copies, les deux copies sur les serveurs avec l'étiquette A, mais chaque serveur devrait avoir une IP différente, le comportement de ceci lors de la prise en compte des étiquettes devrait être STRICT

MODES D'ÉTIQUETTES

Il est important de spécifier ce qu'il faut faire lorsqu'il n'est pas possible de satisfaire les exigences d'étiquettes d'une classe de stockage, c'est-à-dire : il n'y a pas d'espace disponible sur tous les serveurs avec les étiquettes nécessaires, il n'y a pas assez de serveurs avec les étiquettes nécessaires ou les serveurs avec les étiquettes nécessaires sont tous occupés. La question est de savoir si le système doit créer des chunks sur d'autres serveurs (avec des étiquettes non correspondantes) ou non. Cette décision doit être prise par l'utilisateur.

Il existe 3 modes de fonctionnement : STANDARD, LOOSE et STRICT. Les modes fonctionnent un peu différemment selon que le chunk est stocké en format de copies ou en format EC, en raison de la nature différente et des algorithmes utilisés par chacun de ces formats.

Pour le format de copies, les 3 modes se comportent comme suit :

En mode STANDARD, en cas de surcharge des serveurs, le système attendra, mais en cas de manque d'espace, il utilisera d'autres serveurs et répliquera les données vers les serveurs corrects dès que possible. Cela signifie que si certains serveurs sont en état d'occupation prolongée, il pourrait ne pas être possible de créer de nouveaux chunks avec certaines classes de stockage et les chunks menacés (en sous-objectif) de ces classes risquent davantage d'être complètement perdus en raison de réplications retardées.

En mode STRICT, lors de l'écriture d'un nouveau fichier, le système retournera une erreur (ENOSPC) en cas de manque d'espace sur les serveurs marqués avec les étiquettes spécifiées pour la création de chunks. Il attendra toujours les serveurs surchargés. Les réplications sous-objectif ne seront pas effectuées s'il n'y a pas d'espace sur les serveurs avec les étiquettes correspondant à la classe de stockage. Cela signifie un risque élevé de perte de données si les serveurs avec certaines étiquettes sont remplis de données de manière permanente !

En mode LOOSE, le système utilisera immédiatement d'autres serveurs en cas de surcharge des serveurs ou de manque d'espace sur les serveurs et répliquera les données vers les serveurs corrects dès que possible. Il n'y a pas de délai ni d'erreur lors de la création de fichiers et les réplications sous-objectif sont toujours effectuées dès que possible.

Ce tableau résume le comportement des modes pour les chunks stockés au format de copie :

STANDARD STRICT LOOSE
CRÉATION - SURCHARGE ATTENDRE ATTENDRE ÉCRIRE N'IMPORTE OÙ
CRÉATION - PAS D'ESPACE ÉCRIRE N'IMPORTE OÙ ENOSPC ÉCRIRE N'IMPORTE OÙ
RÉPLICATION - SURCHARGE ATTENDRE ATTENDRE ÉCRIRE N'IMPORTE OÙ
RÉPLICATION - PAS D'ESPACE ÉCRIRE N'IMPORTE OÙ PAS DE COPIE ÉCRIRE N'IMPORTE OÙ

Pour les chunks stockés au format EC, les 3 modes se comportent comme suit :

En général, les chunks ne seront convertis du format de copie au format EC que s'il y a suffisamment de serveurs dans le système pour stocker en toute sécurité toutes les parties du format EC. Pour le format EC @N+X, où N est le nombre de parties de données et peut être soit 4 soit 8, et X est le nombre de parties de parité/checksum et peut être égal à 1 (version CE) ou à n'importe quel nombre de 1 à 9 (version PRO), les exigences générales sont :
- au moins N+2X chunkservers pour convertir les nouveaux chunks du format de copie au format EC
- au moins N+X chunkservers pour conserver les chunks déjà au format EC dans ce format
- s'il y a moins de N+X serveurs, tous les chunks reviendront au format de copie (définition KEEP).

En mode LOOSE, le système essaiera d'abord d'utiliser les serveurs correspondant à l'expression d'étiquettes définie dans la classe de stockage utilisée, mais s'il n'y a pas assez de serveurs avec les étiquettes "correctes" (parce qu'ils sont occupés, n'ont pas d'espace ou ne sont tout simplement pas définis), il utilisera n'importe quel chunkserver disponible, quelle que soit l'étiquette ; ainsi, les N+2X et N+X sont calculés à partir de tous les chunkservers disponibles lorsque le système décide du format à utiliser pour conserver un chunk. De plus, lorsqu'une partie d'un chunk au format EC devient indisponible ou corrompue, la restauration de cette partie sera également effectuée sur n'importe quel serveur disponible, si un serveur avec les étiquettes "correctes" ne peut pas être utilisé pour le moment.

Il est important de se rappeler que s'il n'y a pas assez de serveurs avec les étiquettes "correctes" disponibles pour un chunk en mode LOOSE, le système peut utiliser n'importe quel nombre de "autres" chunkservers, pas seulement le nombre minimal manquant par rapport au nombre "correct" de serveurs.

En mode STRICT, le système n'utilisera que les serveurs correspondant à l'expression d'étiquettes définie dans la classe de stockage utilisée, donc seulement les serveurs disponibles ou occupés à court terme.

rvers correspondant à l'expression d'étiquette définie seront utilisés pour le calcul de N+2X et N+X lorsque le système décidera du format à utiliser pour conserver un bloc. Lorsqu'une partie d'un bloc au format EC devient indisponible ou corrompue, la restauration de cette partie ne peut être effectuée que sur un serveur avec une étiquette "correcte" ; si un tel serveur est indisponible à long terme (c'est-à-dire inaccessible purement et simplement ou seulement temporairement occupé), cela signifiera automatiquement que le bloc doit de toute façon être ramené au format de conservation (si la partie manquante est une partie de parité/somme de contrôle, le bloc reviendra simplement au format de copie en utilisant toutes les parties de données disponibles ; si une partie de données manque, elle sera restaurée sur un serveur de blocs hébergeant une autre partie du même bloc - ce qui n'est pas autorisé en circonstances normales - et ensuite la conversion au format de copie suivra immédiatement).

En mode STANDARD, le système se comportera comme en mode STRICT lorsqu'il doit décider s'il convertira un nouveau bloc du format de copie au format EC, c'est-à-dire que le N+2X dans cette étape est calculé uniquement à partir des serveurs étiquetés "correctement". Mais pour décider si les blocs existants doivent être reconvertis du format EC au format de copie, il examinera tous les serveurs disponibles, indépendamment des étiquettes, de sorte que le N+X dans cette étape est calculé à partir de tous les serveurs disponibles, comme en mode LOOSE. X. En cas de parties manquantes, s'il n'est pas possible de les restaurer sur des serveurs de blocs avec des étiquettes "correctes", le système adaptera également le comportement du mode LOOSE et tentera d'utiliser tous les serveurs disponibles.

Attention ! Lorsqu'un bloc est converti du format de copie au format EC, le système effectue d'abord une opération de "division locale", c'est-à-dire qu'il sélectionne une copie du bloc et calcule toutes les parties EC nécessaires sur le serveur occupé par cette copie sélectionnée. Ensuite, ces parties sont déplacées vers des serveurs de blocs séparés, correspondant aux étiquettes définies dans la classe de stockage pour le mode EC utilisé. Mais temporairement, entre la division et le "déplacement" des parties, elles peuvent être enregistrées sur un serveur de blocs "incorrect" même en mode STRICT. Ceci est dû à la mécanique de l'opération de "division locale".

TEMPS

Pour les variables temporelles, leur valeur peut être définie comme un nombre de secondes ou d'heures (entier), en fonction de l'unité minimale de la variable, ou comme une période de temps dans l'un des deux formats possibles :

premier format : #.#T où T est l'un des suivants : s-secondes, m-minutes, h-heures, d-jours ou w-semaines ; les fractions de l'unité minimale seront arrondies à la valeur entière

second format : #w#d#h#m#s, un nombre quelconque de définitions peut être omis, mais les définitions restantes doivent être dans l'ordre (ainsi #d#m est toujours une définition valide, mais #m#d ne l'est pas) ; plages : s,m : 0 à 59, h : 0 à 23, d : 0 à 6, w est illimité et la première définition est également toujours illimitée (c'est-à-dire que pour #d#h#m, d sera illimité)

Si l'unité minimale d'une variable est supérieure à la seconde, les unités inférieures à l'unité minimale ne seront pas acceptées. Par exemple, une variable dont l'unité minimale est l'heure n'acceptera pas les unités s et m.

Exemples :

1.5d équivaut à 1d12h, équivaut à 36h

2.5w équivaut à 2w3d12h, équivaut à 420h ; 2w84h n'est pas une période de temps valide (h n'est pas la première définition, elle est donc limitée par la plage de 0 à 23)

COMPORTEMENT D'ARCHIVAGE

Les blocs ont un indicateur d'archive défini pendant la boucle de maintenance des fichiers, ce qui signifie que le délai d'archivage défini par l'option -d est le temps minimum qui doit s'écouler avant que l'indicateur ne soit défini, et non le temps exact.

Le comportement par défaut du système est qu'une fois qu'un bloc a l'indicateur d'archive activé, il N'EST PAS désactivé même si atime/ctime/mtime change, à moins que l'indicateur R ne soit défini par l'option -o. L'écriture sur un bloc désactivera toujours son indicateur d'archive.

Indicateurs d'archive :

C - utilise le ctime du fichier pour déterminer si l'indicateur d'archive doit être activé - c'est l'indicateur par défaut

M - utilise le mtime du fichier pour déterminer si l'indicateur d'archive doit être activé

A - utilise le atime du fichier pour déterminer si l'indicateur d'archive doit être activé

R - réversible, si atime/mtime/ctime change pour un fichier, le système vérifie si l'indicateur d'archive doit être désactivé pour ses blocs

F - mode rapide, l'indicateur d'archive du bloc est défini dès que possible, indépendamment de ce qui est défini avec l'option -d

P - mode "par bloc", utilise le mtime du bloc pour déterminer si l'indicateur d'archive doit être activé

L'indicateur d'archive peut être modifié manuellement. Voir mfsarchive (1)

Note : l'état ARCHIVE ne signifie pas que les blocs ou les fichiers sont indisponibles, bloqués en écriture, etc. La désignation ARCHIVE est uniquement utilisée pour indiquer que ces données sont destinées au stockage à long terme. Contrairement à l'état KEEP, qui signifie que les données sont "chaudes" et peuvent être modifiées fréquemment. La distinction entre les états KEEP et ARCHIVE permet donc seulement de définir la manière physique de stocker ces données. Du point de vue de l'utilisateur, le fichier est également accessible : il a les mêmes permissions, le même nom et se trouve dans le même répertoire. Par exemple, en raison du fait que l'écriture en mode EC peut être plus lente, nous suggérons de stocker les données "chaudes" (KEEP) en utilisant une copie et de les convertir au format EC (en leur attribuant le mode ARCHIVE) après un certain temps. Un autre exemple est le transfert automatique de données "froides" vers des disques et des serveurs de blocs plus anciens/plus lents/moins chers - en utilisant différentes étiquettes.

PRIORITÉ DES CLASSES DE STOCKAGE

Les classes de stockage sont attribuées aux fichiers, mais un bloc (un fragment d'un fichier) peut appartenir à de nombreux fichiers, grâce au mécanisme de snapshot (voir mfssnapshots (1)). Si un bloc appartient à plusieurs fichiers avec des classes de stockage différentes, une classe de stockage doit être choisie pour spécifier comment les copies de ce bloc doivent être conservées dans le système. Jusqu'à la version 4.56.0 de MooseFS, une classe prédéfinie était artificiellement attribuée à un tel bloc. Actuellement, l'une des classes des fichiers sera utilisée, selon les priorités définies par l'utilisateur, plus précisément : le système choisira la classe avec la priorité la plus élevée parmi toutes les classes des fichiers.

Exemple 1 : il y a 3 classes définies :
ClassA, avec une priorité de 100,
ClassB, avec une priorité de 206,
ClassC, avec une priorité de 1001.

Un bloc, appartenant à 2 fichiers, l'un dans ClassA, l'autre dans ClassB, sera stocké selon la définition fournie par classB (priorité plus élevée que ClassA).
Un bloc, appartenant à 3 fichiers, l'un dans ClassA, un dans ClassB, un dans ClassC, sera stocké selon la définition fournie par classC (priorité plus élevée que ClassA et ClassB).

Si deux classes ou plus ont la même priorité, alors les facteurs suivants seront pris en compte, par ordre d'importance, pour déterminer quelle classe sera choisie :
- une classe avec un niveau de redondance (RL) plus élevé sera choisie (le maximum des niveaux de redondance KEEP et ARCHIVE de chaque classe sera considéré comme le niveau de redondance de cette classe),
- une classe qui a le format EC en état ARCHIVE sera choisie par rapport à une classe sans EC,
- une classe qui utilise des étiquettes pour l'état KEEP ou ARCHIVE sera choisie par rapport à une classe sans étiquettes,
- une classe qui a le format EC en état TRASH sera choisie par rapport à une classe sans EC,
- une classe qui utilise des étiquettes pour l'état TRASH sera choisie par rapport à une classe sans étiquettes,
- si aucune des conditions ci-dessus n'est utilisée, une classe avec un identifiant de classe plus élevé sera utilisée.

Exemple 2 : il y a 5 classes définies, toutes avec la même priorité (par exemple, la priorité par défaut 0) :
ClassA (id=1) a 3 copies en état KEEP (RL=2),
ClassB (id=2) a 2 copies en état KEEP et EC4+1 en état ARCHIVE (RL=1, a EC en ARCHIVE),
ClassC (id=3) a 2 copies en état KEEP, stockées sur des étiquettes X (RL=1, pas d'EC en ARCHIVE, a des étiquettes en KEEP),
ClassD (id=4) a 2 copies en état KEEP, stockées sur des étiquettes Y (RL=1, pas d'EC en ARCHIVE, a des étiquettes en KEEP),
ClassE (id=5) a 2 copies en état KEEP (RL=1).
Il existe également une classe ClassF définie, qui a une priorité de 77 et 2 copies en état KEEP (RL=1).

Un bloc, appartenant à des fichiers dans les classes : ClassA, ClassC et ClassE sera stocké selon la définition de ClassA (RL le plus élevé).
Un bloc, appartenant à des fichiers dans les classes : ClassB, ClassC sera stocké selon la définition de ClassB (RL identique, mais ClassB a EC).
Un bloc, appartenant à des fichiers dans les classes : ClassC et ClassE sera stocké selon la définition de ClassC (RL identique, mais ClassC a des étiquettes).
Un bloc, appartenant à des fichiers dans les classes : ClassC et ClassD sera stocké selon la définition de ClassD (RL identique, pas d'EC, les deux ont des étiquettes, donc l'ID de classe le plus élevé est choisi).
Un bloc, appartenant à des fichiers dans 6 classes, de ClassA à ClassF, sera stocké selon la définition de ClassF, car celle-ci a une priorité plus élevée que toutes les autres classes (77>0).
Dans un système avec ces 6 classes de stockage, classE ne sera jamais utilisée pour un bloc appartenant à plusieurs fichiers, elle a la priorité la plus basse possible (0) et aucune condition supplémentaire pour justifier son choix (RL existant le plus bas, pas d'EC et pas d'étiquettes).

CLASSES DE STOCKAGE PRÉDÉFINIES

Une nouvelle instance MooseFS aura les classes suivantes prédéfinies :

2CP - état KEEP uniquement défini, conserve 2 copies sur n'importe quelles étiquettes (classe par défaut pour le répertoire /)

3CP - état KEEP uniquement défini, conserve 3 copies sur n'importe quelles étiquettes

EC4+1 - en état KEEP, conserve 2 copies sur n'importe quelles étiquettes, en état ARCHIVE, conserve les blocs au format EC4+1 sur n'importe quelles étiquettes, le délai d'archivage est de 1 jour et il est calculé en utilisant le ctime du fichier, les fichiers de moins de 512 Ko ne seront pas convertis au format EC

EC4+2 - (pro uniquement) en état KEEP, conserve 3 copies sur n'importe quelles étiquettes, en état ARCHIVE, conserve les blocs au format EC4+2 sur n'importe quelles étiquettes, le délai d'archivage est de 1 jour et il est calculé en utilisant le ctime du fichier, les fichiers de moins de 512 Ko ne seront pas convertis au format EC

EC8+1 - en état KEEP, conserve 2 copies sur n'importe quelles étiquettes, en état ARCHIVE, conserve les blocs au format EC8+1 sur n'importe quelles étiquettes, le délai d'archivage est de 1 jour et il est calculé en utilisant le ctime du fichier, les fichiers de moins de 512 Ko ne seront pas convertis au format EC

EC8+2 - (pro uniquement) en état KEEP, conserve 3 copies sur n'importe quelles étiquettes, en état ARCHIVE, conserve les blocs au format EC8+2 sur n'importe quelles étiquettes, le délai d'archivage est de 1 jour et il est calculé en utilisant le ctime du fichier, les fichiers de moins de 512 Ko ne seront pas convertis au format EC

Ces classes sont entièrement modifiables et supprimables et peuvent être remplacées par des classes choisies par l'utilisateur.

Jusqu'à la version 4.56.0 de MooseFS, les classes prédéfinies étaient différentes. Les informations suivantes concernent le comportement des anciennes versions de MooseFS. Dans les versions plus récentes de MooseFS, les classes mentionnées ci-dessous peuvent exister

mfscreatesclass(1) — MooseFS man pages

NOM

mfscreatesclass — crée une nouvelle classe de stockage.

SYNOPSIS

mfscreatesclass [-f] [-d délai] [-m mode] [-C chaîne] [-K chaîne] [-A chaîne] nom_classe

DESCRIPTION

La commande mfscreatesclass crée une nouvelle classe de stockage nommée nom_classe. Les classes de stockage permettent de définir des règles de placement des données. Les règles peuvent être basées sur des labels de serveurs de morceaux (chunkservers) ou sur des objectifs de nombre de copies, de type d'archivage, etc.

Les classes de stockage sont utilisées par les outils mfsfileinfo, mfsmount, mfsxchgsclass, mfsgetattr, mfsetattr, mfssetgoal, mfsgetgoal et mfsadmin.

Les règles spécifiées avec les options -C, -K et -A peuvent être des chaînes de caractères définissant des objectifs de stockage. Voici quelques exemples de syntaxes valides :

  • N : nombre de copies. Par exemple, 3 signifie que le fichier doit avoir 3 copies.
  • N* : nombre minimum de copies. Par exemple, 2* signifie qu'au moins 2 copies doivent être disponibles.
  • N,M,P : nombre de copies sur des serveurs de morceaux avec des labels spécifiques. Par exemple, A,B,C signifie que la première copie doit être sur un serveur avec le label A, la deuxième sur un serveur avec le label B, et la troisième sur un serveur avec le label C.
  • * : n'importe quel serveur de morceaux.
  • @format : spécifie le format d'archivage. Par exemple, @4+1 signifie un encodage Reed-Solomon avec 4 données et 1 parité.
  • @format+N : spécifie le format d'archivage avec une exigence de redondance supplémentaire. Par exemple, @4+1+1 signifie un encodage Reed-Solomon avec 4 données, 1 parité, et une copie supplémentaire sur un serveur différent.

Les règles peuvent être combinées. Par exemple, '2*,A,B' signifie que le fichier doit avoir au moins 2 copies, dont une sur un serveur étiqueté A et une sur un serveur étiqueté B.

La durée de rétention des données pour les règles d'archivage peut être spécifiée en utilisant les suffixes de temps suivants :

  • s : secondes
  • m : minutes
  • h : heures
  • d : jours
  • w : semaines
  • M : mois
  • y : années

OPTIONS

-f
Force la création ou la modification d'une classe de stockage, même si elle existe déjà. Cette option est nécessaire pour modifier les classes de stockage prédéfinies.
-d délai
Spécifie le délai avant qu'une action (par exemple, l'archivage) ne soit effectuée. Le délai est interprété par rapport à la création ou à la modification du fichier, selon le contexte.
-m mode
Spécifie le mode de placement des données. Les modes possibles sont :
s
Strict : les données doivent être placées sur les serveurs spécifiés.
l
Loose : les données peuvent être placées sur d'autres serveurs si les serveurs spécifiés sont surchargés ou indisponibles.
-C chaîne
Définit la règle de création des nouveaux morceaux (chunks).
-K chaîne
Définit la règle de conservation des morceaux (chunks) existants.
-A chaîne
Définit la règle d'archivage des morceaux (chunks).

NOTES

Les classes de stockage prédéfinies (de 1 à 9) ne peuvent pas être supprimées et ne peuvent être modifiées qu'avec l'option -f. Il est recommandé de créer de nouvelles classes de stockage personnalisées et d'utiliser l'outil mfsxchgsclass pour migrer les fichiers, plutôt que de modifier les classes prédéfinies.

(Comportement jusqu'à la version 4.56.0) Pour des raisons de compatibilité, chaque instance fraîche ou mise à jour de MooseFS possède 9 classes de stockage prédéfinies. Leurs noms sont des chiffres uniques, de 1 à 9, et leurs définitions sont * à 9*. Elles sont équivalentes aux objectifs numériques simples des versions précédentes du système. En cas de mise à niveau, tous les fichiers qui avaient l'objectif N avant la mise à niveau auront désormais la classe de stockage N. Ces classes ne peuvent être modifiées qu'en spécifiant l'option -f. Il est conseillé de créer de nouvelles classes de stockage dans un système mis à niveau et de migrer les fichiers avec l'outil mfsxchgsclass, plutôt que de modifier les classes prédéfinies. Les classes prédéfinies NE PEUVENT PAS être supprimées.

EXEMPLES

Créez une nouvelle classe de stockage nommée "Class2Copies" avec 2 copies. La première copie sur un des serveurs de morceaux avec le label "A" et la deuxième copie sur un des serveurs de morceaux avec le label "B" :

mfscreatesclass -K A,B Class2Copies

Créez une nouvelle classe de stockage nommée "Class3Copies". Les nouveaux morceaux créés (-C) seront conservés partout avec 2 copies (2*). Peu après leur création, ils seront conservés (-K) en 3 copies : la première copie sur un des serveurs de morceaux avec le label "A", la deuxième copie sur un des serveurs de morceaux avec le label "B" et la troisième sur n'importe quel serveur de morceaux :

mfscreatesclass -C '2*' -K 'A,B,*' Class3Copies

Créez une nouvelle classe de stockage nommée "ClassEC4_1". Les morceaux seront créés et conservés (-K) partout en 2 copies (2*) pendant 24 heures à partir de la création du fichier. Plus tard, ils seront archivés (-A) au format EC4+1 sur n'importe quel serveur de morceaux :

mfscreatesclass -K '2*' -A '@4+1' ClassEC4_1

Modifiez la classe de stockage "ClassEC4_1" pour archiver les morceaux après 48 heures à partir de la modification du fichier (et non de la création) :

mfscreatesclass -d 2d -o m ClassEC4_1

Modifiez la classe de stockage "Class3Copies" pour conserver les morceaux sur d'autres serveurs de morceaux (mode LOOSE) si ceux avec les labels "A" et "B" sont trop occupés (surchargés) :

mfscreatesclass -m l Class3Copies
