NOM

mfsscadmin - Outil d'administration des classes de stockage MooseFS

SYNOPIS

mfscreatesclass [-?] [-M POINT_DE_MONTAGE] -K ETIQUETTES_CONSERVER [-c description] [-p priorité] [-g groupe_export] [-a admin_seulement] [-m mode_etiquettes] [-o mode_archivage] [-C ETIQUETTES_CREER] [-A ETIQUETTES_ARCHIVAGE [-d delai_archivage] [-s longueur_min_fichier]] [-T ETIQUETTES_CORBEILLE [-t duree_min_retention_corbeille]] NOM_CLASSE_STOCKAGE...

mfsmodifysclass [-?] [-M POINT_DE_MONTAGE] [-c description] [-p priorité] [-g groupe_export] [-a admin_seulement] [-m mode_etiquettes] [-o mode_archivage] [-C ETIQUETTES_CREER] [-K ETIQUETTES_CONSERVER] [-A ETIQUETTES_ARCHIVAGE] [-d delai_archivage] [-s longueur_min_fichier] [-T ETIQUETTES_CORBEILLE] [-t duree_min_retention_corbeille] NOM_CLASSE_STOCKAGE...

mfsdeletesclass [-?] [-M POINT_DE_MONTAGE] NOM_CLASSE_STOCKAGE...

mfsclonesclass [-?] [-M POINT_DE_MONTAGE] NOM_CLASSE_SOURCE NOM_CLASSE_DESTINATION...

mfsrenamesclass [-?] [-M POINT_DE_MONTAGE] NOM_CLASSE_SOURCE NOM_CLASSE_DESTINATION

mfslistsclass [-?] [-M POINT_DE_MONTAGE] [-l] [-i] [MOTIF_GLOB_NOM_CLASSE_STOCKAGE]

mfsimportsclass [-?] [-M POINT_DE_MONTAGE] [-r] [-n nom_fichier]

DESCRIPTION

Il s'agit d'un ensemble d'outils pour gérer les classes de stockage MooseFS. Les classes de stockage sont utilisées pour définir la politique de redondance au sein du cluster. Elles doivent être appliquées ultérieurement à des objets MooseFS particuliers (fichiers ou dossiers) avec les outils mfssclass (voir mfssclass(1)). Une classe de stockage est un ensemble nommé d'expressions d'étiquettes et d'autres options. L'expression d'étiquette indique le format de redondance, le niveau de redondance souhaité et la politique de stockage souhaitée. Le format de redondance peut être soit des copies, soit un codage par effacement (EC). Le niveau de redondance est soit le nombre de copies (de 1 à 9), soit le nombre de données plus les blocs de parité (4+n ou 8+n), selon le format de redondance indiqué. La politique de stockage spécifie, par l'utilisation d'étiquettes, quels chunkservers doivent être utilisés pour le stockage physique des données assignées à la classe de stockage particulière.

mfscreatesclass crée une nouvelle classe de stockage avec les options données, décrites ci-dessous, et la nomme NOM_CLASSE_STOCKAGE ; plusieurs noms peuvent être fournis, plusieurs classes de stockage avec la même définition seront alors créées.

mfsmodifysclass modifie les options données dans une classe ou des classes indiquées par le(s) paramètre(s) NOM_CLASSE_STOCKAGE.

mfsdeletesclass supprime la ou les classes indiquées par le(s) paramètre(s) NOM_CLASSE_STOCKAGE ; si l'une des classes n'est pas vide (c'est-à-dire si elle est toujours utilisée par des objets MooseFS), elle ne sera pas supprimée et l'outil retournera une erreur et un message d'erreur sera affiché ; les classes vides seront supprimées dans tous les cas.

mfsclonesclass copie la classe indiquée par NOM_CLASSE_SOURCE sous un nouveau nom fourni avec NOM_CLASSE_DESTINATION.

mfsrenamesclass change le nom d'une classe de NOM_CLASSE_SOURCE à NOM_CLASSE_DESTINATION.

mfslistsclass liste toutes les classes.

mfsimportsclass importe les définitions de classes de stockage depuis stdin ou un fichier et les crée ; le format d'entrée doit être identique à la sortie de mfslistsclass -l.

OPTIONS

-C paramètre optionnel, qui indique au système sur quels chunkservers, définis par l'expression ETIQUETTES_CREER, le bloc doit être écrit juste après sa création ; si ce paramètre n'est pas fourni pour une classe, les chunkservers ETIQUETTES_CONSERVER seront utilisés.

-K paramètre obligatoire, qui indique au système sur quels chunkservers, définis par l'expression ETIQUETTES_CONSERVER, le(s) bloc(s) doit (doivent) toujours être conservé(s), à l'exception de conditions spéciales comme la création, l'archivage et la suppression (déplacement vers la Corbeille), si elles sont définies.

-A paramètre optionnel, qui indique au système sur quels chunkservers, définis par l'expression ETIQUETTES_ARCHIVAGE, le(s) bloc(s) doit (doivent) être conservé(s) à des fins d'archivage ; le système commence à traiter un bloc comme une archive lorsque son atime/mtime/ctime (tel que défini par -o) est plus ancien que le nombre d'heures spécifié avec l'option -d ; voir également la section COMPORTEMENT D'ARCHIVAGE ci-dessous.

-d paramètre optionnel qui définit après combien de temps depuis l'atime/mtime/ctime (tel que défini par -o) un fichier (et ses blocs) est traité comme une archive ; l'unité minimale est l'heure, la valeur par défaut est 24 ; pour le formatage de la valeur, voir TEMPS.

-o paramètre optionnel qui définit les drapeaux d'archive. C - ctime, M - mtime, A - atime, R - réversible, F - mode rapide, P - par bloc ; la valeur par défaut est C ; voir la section COMPORTEMENT D'ARCHIVAGE ci-dessous pour plus de détails.

-s paramètre optionnel qui définit la longueur minimale du fichier en octets qui peut être archivée ; la valeur par défaut est 0.

-T paramètre optionnel, qui indique au système sur quels chunkservers, définis par l'expression ETIQUETTES_CORBEILLE, le(s) bloc(s) des fichiers dans la Corbeille doit (doivent) être conservé(s) ; voir aussi -t.

-t paramètre optionnel, qui définit combien de temps dans la Corbeille doit s'écouler pour que le système utilise le schéma défini dans -T pour un bloc ; l'unité minimale est l'heure, la valeur par défaut est 0 ; pour le formatage de la valeur, voir TEMPS.

-c paramètre optionnel, qui définit une description de classe, pour la commodité de l'utilisateur (une chaîne de caractères, longueur maximale de 255 octets).

-p paramètre optionnel, qui définit une priorité de classe ; la valeur par défaut est 0 ; voir la section PRIORITÉ DES CLASSES DE STOCKAGE.

-g paramètre optionnel, qui définit un groupe d'exportation de classe ; les valeurs possibles sont de 0 à 15, la valeur par défaut est 0 ; voir mfsexport.cfg(5) pour l'explication.

-a peut être soit 1 soit 0 et indique si la classe de stockage est disponible pour tout le monde (0) ou uniquement pour l'administrateur (1).

-m mode d'étiquette utilisé ; les valeurs possibles sont l (ou L, loose, Loose, LOOSE) pour le mode LOOSE, d (ou D, std, Std, STD) pour le mode STANDARD et s (ou S, strict, Strict, STRICT) pour le mode STRICT ; si aucun mode n'est défini, le mode STANDARD est supposé ; le comportement des modes d'étiquettes est décrit ci-dessous dans la section MODES D'ÉTIQUETTES.

-l liste également les définitions, pas seulement les noms des classes de stockage existantes.

-i correspondance des noms de classes de stockage insensible à la casse.

-r remplace (écrase) les classes existantes lors de l'importation des classes de stockage.

-n utilise le nom de fichier fourni comme source des définitions de classes de stockage pour l'importation, au lieu de stdin.

-M point de montage MooseFS, il n'est pas nécessaire de le spécifier si un outil est exécuté dans un répertoire monté par MooseFS ou si MooseFS est monté dans /mnt/mfs/.

-? affiche un message d'utilisation court.

NOTES

EXPRESSIONS D'ÉTIQUETTES

Les étiquettes sont des lettres (A-Z - 26 lettres) qui peuvent être attribuées aux chunkservers. Chaque chunkserver peut avoir plusieurs (jusqu'à 26) étiquettes. Les étiquettes sont définies dans le fichier mfschunkserver.cfg, pour plus d'informations, reportez-vous à la page de manuel appropriée.

L'expression d'étiquettes est un ensemble de sous-expressions séparées par des virgules. Pour des copies complètes, chaque sous-expression spécifie le schéma de stockage d'une copie d'un fichier. Une sous-expression peut être : un astérisque ou un schéma d'étiquette. Un schéma d'étiquette peut être une seule étiquette ou une expression avec des sommes, des multiplications, des négations et des parenthèses. La somme signifie qu'un fichier peut être stocké sur n'importe quel chunkserver correspondant à n'importe quel élément de la somme (OU logique). La multiplication signifie qu'un fichier ne peut être stocké que sur un chunkserver correspondant à tous les éléments (ET logique). L'astérisque signifie n'importe quel chunkserver. La négation signifie n'importe quel chunkserver sauf celui correspondant à la sous-expression négativée. Des sous-expressions identiques peuvent être raccourcies en ajoutant un nombre devant l'une d'elles au lieu de la répéter plusieurs fois.

Pour l'EC, l'expression d'étiquettes commence par le signe @, suivi d'un nombre de blocs de données puis du signe + et d'un nombre qui indique combien de blocs de parité le bloc doit avoir. Nombres possibles

of data parts are 4 or 8. Possible numbers of parity parts are 1 (CE version) or 1 to 9 (PRO version). So, for example, @4+1 means EC with 4 data parts and 1 parity part, @8+3 means EC with 8 data parts and 3 parity parts. If number of data parts is omitted then the master uses the default value defined by DEFAULT_EC_DATA_PARTS - see mfsmaster.cfg (5). In this case @2 means @8+2 or @4+2. Then, maximum of two subexpressions can follow, separated by commas. If only one is present, it defines where all the parts should be kept. If both are present, the first subexpression defines where data parts should be kept, the second subexpression defines where parity parts should be kept.

Labels expression can be either a regular labels expression or EC labels expression (i.e. EC labels expression cannot be a subexpression). EC labels expression can only be used in place of ARCHIVE_LABELS or TRASH_LABELS in the storage class definition, regular labels expression can be use in any place.

At the end of each label expression one or two extending information, divided with a special separator, can be added. The first possible extension, is the distinguish extension and the separator is the slash (/) sign. Second is labels mode override and this extension is separated by colon (:) sign.

Distinguish extension can be a list of labels or one of the following special strings:

[IP] or [I] - distinguish by IP number

[RACK] or [R] - distinguish by RACK, as defined in topology, see mfstopology.cfg (5)

If present, the distinguish part lets the system know that it should try to distribute full copies so that each copy is either on a different label from the list or on a chunkserver with different IP address or from a different rack. For EC the distinguish part is currently ignored.

NOTICE! If CHUNKS_UNIQUE_MODE is defined in mfsmaster.cfg to a value other than 0, it will override any distinguish setting in storage classes. For more information about this parameter refer to mfsmaster.cfg (5) manual.

Labels mode override extension can be one of three characters: d (alternatively D or in string form std or Std or STD), s (alternatively S or in string form strict or Strict or STRICT) or l (alternatively L or in string form loose or Loose or LOOSE) and they mean that the STANDARD, STRICT or LOOSE label mode, respectively, should be applied only to this one labels expression. For explanation about label modes see the LABEL MODES section.

One or both extensions can be present for each labels expression, each has to start with their separator and if both are present, the order has to be kept, i.e. the distinguish extension has to be first and the label mode extension needs to be second.

Examples of labels expressions:

A,B - files will have two copies, one copy will be stored on chunkserver(s) with label A, the other on chunkserver(s) with label B

A,* - files will have two copies, one copy will be stored on chunkserver(s) with label A, the other on any chunkserver(s)

A,!A - files will have two copies, one copy will be stored on chunkserver(s) with label A, the other on any chunkserver(s) that doesn't have the label A

*,* - files will have two copies, stored on any chunkservers (different for each copy)

AB,C+D+E - files will have two copies, one copy will be stored on any chunkserver(s) that has both labels A and B (multiplication of labels), the other on any chunkserver(s) that has either the C label or the D label or the E label (sum of labels)

A,B[X+Y],C[X+Y] - files will have three copies, one copy will be stored on any chunkserver(s) with A label, the second on any chunserver(s) that has the B label and either X or Y label, the third on any chunkserver(s), that has the C label and either X or Y label

2A expression is equivalent to A,A expression

A,3BC expression is equivalent to A,BC,BC,BC expression

2 expression is equivalent to 2* expression is equivalent to *,* expression

3*/[IP] - files will have 3 copies, each copy will be kept on a chunkserver with different IP address

A,B/[RACK] - files will have two copies, one copy will be stored on chunkserver(s) with label A, the other on chunkserver(s) with label B in a different rack than the other copy

S,H,H/[RACK] - files will have 3 copies, one on server with label S, two on servers with label H, but each copy will be on a server with different rack than the other copies

@4+1 - files will be kept in EC format, 4 data parts and 1 parity part

@8+3 - files will be kept in EC format, 8 data parts and 3 parity parts

@2 - files will be kept in EC format, default number of data parts, 2 parity parts

@4+3,Z - files will be kept in EC format, 4 data parts and 3 parity parts - all on chunkservers with label Z.

@2,A(X+Y) - files will be kept in EC format, default number of data parts, 2 parity parts, all parts will be kept on chunsevers with label A and either X or Y

@3,S,H - files will be kept in EC format, default number of data parts will be kept on chunkservers with label S, 3 parity parts will be kept on chunkservers with label H

AB,AC:l - files will be kept in copies format, one copy on a server with labels A and B, the second on a server with labels A and C and the behaviour of this should be LOOSE

@4+2,X,Y:s - files will be kept in EC format, 4 data parts will be kept on servers with label X, 2 parity (checksum) parts should be kept on servers with label Y and the behaviour of this should be STRICT

2A/[IP]:s - files should be kept in 2 copies, both copies on servers with label A, but each server should have different IP, behaviour of this when accounting for labels should be STRICT

MODES DES ÉTIQUETTES

Il est important de spécifier quoi faire lorsqu'il n'est pas possible de satisfaire aux exigences d'étiquetage d'une classe de stockage, c'est-à-dire : il n'y a pas d'espace disponible sur tous les serveurs avec les étiquettes nécessaires, il n'y a pas assez de serveurs avec les étiquettes nécessaires ou les serveurs avec les étiquettes nécessaires sont tous occupés. La question est de savoir si le système doit créer des blocs sur d'autres serveurs (avec des étiquettes non correspondantes) ou non. Cette décision doit être prise par l'utilisateur.

Il existe 3 modes de fonctionnement : STANDARD, LOOSE (lâche) et STRICT (strict). Les modes fonctionnent un peu différemment selon que le bloc est stocké en copies ou au format EC, en raison de la nature et des algorithmes différents utilisés par chacun de ces formats.

Pour le format de copies, les 3 modes se comportent comme suit :

En mode STANDARD, en cas de serveurs surchargés, le système attendra pour eux, mais en cas de manque d'espace, il utilisera d'autres serveurs et répliquera les données vers les serveurs corrects lorsque cela deviendra possible. Cela signifie que si certains serveurs sont en état d'occupation prolongée, il peut ne pas être possible de créer de nouveaux blocs avec certaines classes de stockage et les blocs menacés (en sous-effectif) de ces classes risquent davantage d'être complètement perdus en raison de réplications retardées.

En mode STRICT, lors de l'écriture d'un nouveau fichier, le système renverra une erreur (ENOSPC) en cas de manque d'espace sur les serveurs marqués avec les étiquettes spécifiées pour la création des blocs. Il attendra toujours les serveurs surchargés. Les réplications en sous-effectif ne seront pas effectuées s'il n'y a pas d'espace sur les serveurs dont les étiquettes correspondent à la classe de stockage. Cela signifie un risque élevé de perte de données si les serveurs avec certaines étiquettes sont définitivement remplis de données !

En mode LOOSE, le système utilisera immédiatement d'autres serveurs en cas de serveurs surchargés ou de manque d'espace sur les serveurs et répliquera les données vers les serveurs corrects lorsque cela deviendra possible. Il n'y a aucun délai ni erreur lors de la création de fichiers et les réplications en sous-effectif sont toujours effectuées dès que possible.

Ce tableau résume le comportement des modes pour les blocs stockés en format de copie :

STANDARD STRICT LOOSE
CRÉER - SURCHARGÉ ATTENDRE ATTENDRE ÉCRIRE N'IMPORTE OÙ
CRÉER - PAS D'ESPACE ÉCRIRE N'IMPORTE OÙ ENOSPC ÉCRIRE N'IMPORTE OÙ
RÉPLIQUER - SURCHARGÉ ATTENDRE ATTENDRE ÉCRIRE N'IMPORTE OÙ
RÉPLIQUER - PAS D'ESPACE ÉCRIRE N'IMPORTE OÙ PAS DE COPIE ÉCRIRE N'IMPORTE OÙ

Pour les blocs stockés au format EC, les 3 modes se comportent comme suit :

En général, les blocs ne seront convertis du format de copie au format EC que s'il y a suffisamment de serveurs dans le système pour stocker en toute sécurité toutes les parties du format EC. Pour le format EC @N+X, où N est le nombre de parties de données et peut être soit 4, soit 8, et X est le nombre de parties de parité/somme de contrôle et peut être égal à 1 (version CE) ou n'importe quel nombre de 1 à 9 (version PRO), les exigences générales sont :
- au moins N+2X serveurs de blocs pour convertir les nouveaux blocs du format de copie au format EC
- au moins N+X serveurs de blocs pour maintenir les blocs déjà au format EC dans ce format
- s'il y a moins de N+X serveurs, tous les blocs reviendront au format de copie (définition KEEP).

En mode LOOSE, le système essaiera d'abord d'utiliser les serveurs correspondant à l'expression d'étiquettes définie dans la classe de stockage utilisée, mais si un nombre suffisant de serveurs avec des étiquettes « correctes » ne sont pas disponibles (parce qu'ils sont occupés, manquent d'espace ou ne sont tout simplement pas définis), il utilisera n'importe quels serveurs de blocs disponibles, quelle que soit l'étiquette ; ainsi, N+2X et N+X sont calculés à partir de tous les serveurs de blocs disponibles lorsque le système décide du format à utiliser pour conserver un bloc. De plus, lorsqu'une partie d'un bloc au format EC devient indisponible ou corrompue, la restauration d'une telle partie sera également effectuée sur n'importe quel serveur disponible, si un serveur avec des étiquettes « correctes » ne peut pas être utilisé actuellement.

Il est important de se rappeler que si un nombre suffisant de serveurs avec des étiquettes « correctes » ne sont pas disponibles pour un bloc en mode LOOSE, le système peut utiliser autant de serveurs de blocs « autres » qu'il le souhaite, et pas seulement le nombre minimal manquant par rapport au nombre « correct » de serveurs.

En mode STRICT, le système n'utilisera que les serveurs correspondant à l'expression d'étiquettes définie dans la classe de stockage utilisée, ainsi seuls les serveurs disponibles ou temporairement occupés.

STORAGE CLASSES

Les classes de stockage d'un fichier déterminent le comportement du système de stockage MooseFS, par exemple, si le fichier doit être stocké en format de copie (chaque morceau est dupliqué) ou en format de code d'effacement (les morceaux sont répartis en données et en parité/checksum), et sur quels serveurs les morceaux doivent être stockés.

Les classes de stockage sont utilisées pour définir les règles de stockage pour les fichiers. Chaque classe de stockage peut avoir des paramètres différents pour les états KEEP et ARCHIVE.

Chaque état (KEEP, ARCHIVE, TRASH) peut définir les paramètres suivants :

  • Type de format : Type de format à utiliser pour les morceaux (COPY, EC).
    • COPY : Le morceau est dupliqué N fois.
    • EC : Le morceau est divisé en K parties de données et M parties de parité/checksum. Le nombre de copies des morceaux de données sera N, ce qui correspond à N pièces de données et M pièces de parité/checksum. Le nombre de copies des morceaux de parité/checksum sera également N. Les formats EC disponibles sont ECx+y, où x est le nombre de parties de données et y est le nombre de parties de parité/checksum. Le nombre total de parties est x+y. Le nombre de morceaux de données est K=x et le nombre de morceaux de parité/checksum est M=y. Les valeurs de x et y sont définies dans la classe de stockage.
  • Nombre de copies (N) : Pour le format COPY, c'est le nombre de copies du morceau. Pour le format EC, c'est le nombre de fois où les morceaux de données et de parité/checksum sont dupliqués.
  • Labels : Spécifie les labels des serveurs de morceaux qui doivent être utilisés pour stocker les morceaux. Les labels sont des chaînes de caractères qui peuvent être attribuées aux serveurs de morceaux.
  • Délai d'archivage : Pour l'état ARCHIVE, c'est le délai minimum qui doit s'écouler avant que les morceaux ne soient convertis en format ARCHIVE.
  • Fichiers ignorés : Pour l'état ARCHIVE, c'est la taille maximale des fichiers qui ne seront pas convertis en format ARCHIVE.

MODES

Le système peut fonctionner dans trois modes différents qui affectent la façon dont les décisions sont prises concernant la conversion des morceaux entre les formats COPY et EC, et le respect des labels : STRICT, STANDARD et LOOSE.

STRICT : Dans ce mode, le système s'assure que toutes les opérations, y compris le calcul des formats EC et la restauration, sont effectuées uniquement sur des serveurs portant les labels corrects spécifiés dans la définition de la classe de stockage. Si un serveur avec le label correct n'est pas disponible, le système ne pourra pas effectuer l'opération et le morceau pourrait être converti en format COPY si nécessaire.

STANDARD : Ce mode est un mélange des modes STRICT et LOOSE. Lors de la décision de convertir un nouveau morceau du format COPY en format EC, le système se comporte comme en mode STRICT, en utilisant uniquement les serveurs portant les labels corrects pour le calcul de N+2X. Cependant, pour décider si des morceaux existants doivent être reconvertis du format EC au format COPY, le système examine tous les serveurs disponibles, quel que soit leur label, pour le calcul de N+X. En cas de morceaux manquants, si la restauration sur des serveurs avec des labels corrects n'est pas possible, le système adoptera le comportement du mode LOOSE et tentera d'utiliser n'importe quel serveur disponible.

LOOSE : Dans ce mode, le système est plus flexible. Il utilise tous les serveurs disponibles, quel que soit leur label, pour le calcul de N+2X et N+X lors de la conversion des morceaux. Si un morceau en format EC devient indisponible ou corrompu, le système tentera de le restaurer en utilisant n'importe quel serveur disponible portant un label "correct", même s'il ne correspond pas exactement à la définition de la classe de stockage. Si le serveur manquant est une partie de parité/checksum, le morceau sera simplement reconverti au format COPY en utilisant toutes les parties de données disponibles. Si une partie de données est manquante, elle sera restaurée sur un serveur de morceaux hébergeant une autre partie du même morceau (ce qui n'est normalement pas autorisé) et la conversion au format COPY suivra immédiatement.

Remarque ! Lorsque le système convertit un morceau du format COPY au format EC, il effectue d'abord une opération de "division locale". Cela signifie qu'il choisit une copie du morceau et calcule toutes les parties EC nécessaires sur le serveur qui héberge cette copie sélectionnée. Ensuite, ces parties sont déplacées vers des serveurs de morceaux distincts, conformément aux labels spécifiés dans la définition de la classe de stockage pour le mode EC utilisé. Cependant, temporairement, entre la division et le "déplacement" des parties, elles peuvent être enregistrées sur un serveur de morceaux "incorrect" même en mode STRICT. Ceci est dû aux mécanismes de l'opération de "division locale".

TEMPS

Pour les variables temporelles, leur valeur peut être définie comme un nombre de secondes ou d'heures (entier), selon l'unité minimale de la variable, ou comme une période de temps dans l'un des deux formats possibles :

premier format : #.#T où T est l'un des : s-secondes, m-minutes, h-heures, d-jours ou w-semaines ; les fractions de l'unité minimale seront arrondies à la valeur entière

deuxième format : #w#d#h#m#s, n'importe quel nombre de définitions peut être omis, mais les définitions restantes doivent être dans l'ordre (donc #d#m est toujours une définition valide, mais #m#d ne l'est pas) ; plages : s,m : 0 à 59, h : 0 à 23, d : 0 à 6, w est illimité et la première définition est également toujours illimitée (c'est-à-dire que pour #d#h#m, d sera illimité)

Si une unité minimale d'une variable est supérieure aux secondes, les unités inférieures à l'unité minimale ne seront pas acceptées. Par exemple, une variable dont l'unité minimale est l'heure n'acceptera pas les unités s et m.

Exemples :

1.5d est la même chose que 1d12h, est la même chose que 36h

2.5w est la même chose que 2w3d12h, est la même chose que 420h ; 2w84h n'est pas une période de temps valide (h n'est pas la première définition, elle est donc limitée par la plage de 0 à 23)

COMPORTEMENT D'ARCHIVAGE

Les morceaux ont un indicateur d'archive défini lors de la boucle de maintenance des fichiers, ce qui signifie que le temps d'archivage défini par l'option -d est le temps minimum qui doit s'écouler avant que l'indicateur ne soit défini, et non le temps exact.

Le comportement par défaut du système est qu'une fois qu'un morceau a l'indicateur d'archive activé, il N'EST PAS désactivé même si atime/ctime/mtime change, à moins que le drapeau R ne soit défini par l'option -o. L'écriture sur un morceau désactivera toujours son indicateur d'archive.

Indicateurs d'archive :

C - utilise le ctime du fichier pour déterminer si l'indicateur d'archive doit être activé - c'est l'indicateur par défaut

M - utilise le mtime du fichier pour déterminer si l'indicateur d'archive doit être activé

A - utilise le atime du fichier pour déterminer si l'indicateur d'archive doit être activé

R - réversible, si atime/mtime/ctime change pour un fichier, le système vérifie si l'indicateur d'archive doit être désactivé pour ses morceaux

F - mode rapide, le morceau a son indicateur d'archive activé dès que possible, quelle que soit la définition de l'option -d

P - mode "par morceau", utilise le mtime du morceau pour déterminer si l'indicateur d'archive doit être activé

L'indicateur d'archive peut être modifié manuellement. Voir mfsarchive(1)

Remarque : l'état ARCHIVE ne signifie pas que les morceaux ou les fichiers sont indisponibles, bloqués en écriture, etc. La désignation ARCHIVE indique seulement que ces données sont déjà destinées au stockage à long terme. Contrairement à l'état KEEP, qui signifie que les données sont "chaudes" et peuvent être modifiées fréquemment. La distinction entre les états KEEP et ARCHIVE permet donc de définir de manière appropriée la manière physique de stocker ces données. Du point de vue de l'utilisateur, le fichier est également accessible : il a les mêmes permissions, le même nom et se trouve dans le même répertoire. Par exemple, en raison du fait que l'écriture en mode EC peut être plus lente, nous suggérons de stocker les données "chaudes" (KEEP) en utilisant une copie et de passer au format EC (en attribuant le mode ARCHIVE) après un certain temps. Un autre exemple est le transfert automatique de données "froides" vers des disques/serveurs de morceaux plus anciens/plus lents/moins chers - en utilisant des labels différents.

PRIORITÉ DES CLASSES DE STOCKAGE

Les classes de stockage sont attribuées aux fichiers, mais un morceau (un fragment d'un fichier) peut appartenir à de nombreux fichiers, grâce au mécanisme d'instantanés (voir mfssnapshots(1)). Si un morceau appartient à plusieurs fichiers avec des classes de stockage différentes, une classe de stockage doit être choisie pour spécifier comment les copies de ce morceau doivent être conservées dans le système. Jusqu'à la version 4.56.0 de MooseFS, une classe prédéfinie était attribuée artificiellement à un tel morceau. Actuellement, l'une des classes des fichiers sera utilisée, selon les priorités définies par l'utilisateur, pour être exact : le système choisira la classe avec la priorité la plus élevée parmi toutes les classes des fichiers.

Exemple 1 : il y a 3 classes définies :
ClassA, avec une priorité de 100,
ClassB, avec une priorité de 206,
ClassC, avec une priorité de 1001.

Un morceau, appartenant à 2 fichiers, l'un dans ClassA, l'autre dans ClassB, sera stocké conformément à la définition fournie par classB (priorité plus élevée que ClassA).
Un morceau, appartenant à 3 fichiers, l'un dans ClassA, un dans ClassB, un dans ClassC, sera stocké conformément à la définition fournie par classC (priorité plus élevée que ClassA et ClassB).

Si deux classes ou plus ont la même priorité, les facteurs suivants seront pris en compte, par ordre d'importance, pour déterminer quelle classe sera choisie :
- la classe avec un niveau de redondance (RL) plus élevé sera choisie (le maximum des niveaux de redondance KEEP et ARCHIVE de chaque classe sera considéré comme le niveau de redondance de cette classe),
- la classe qui a le format EC en état ARCHIVE sera préférée à une classe sans EC,
- la classe qui utilise des labels pour l'état KEEP ou ARCHIVE sera préférée à une classe sans labels,
- la classe qui a le format EC en état TRASH sera préférée à une classe sans EC,
- la classe qui utilise des labels pour l'état TRASH sera préférée à une classe sans labels,
- si aucune des conditions ci-dessus n'est utilisée, une classe avec un ID de classe plus élevé sera utilisée.

Exemple 2 : il y a 5 classes définies, toutes avec la même priorité (par exemple, la priorité par défaut 0) :
ClassA (id=1) a 3 copies en état KEEP (RL=2),
ClassB (id=2) a 2 copies en état KEEP et EC4+1 en état ARCHIVE (RL=1, a EC en ARCHIVE),
ClassC (id=3) a 2 copies en état KEEP, stockées sur des labels X (RL=1, pas d'EC en ARCHIVE, a des labels en KEEP),
ClassD (id=4) a 2 copies en état KEEP, stockées sur des labels Y (RL=1, pas d'EC en ARCHIVE, a des labels en KEEP),
ClassE (id=5) a 2 copies en état KEEP (RL=1).
Il y a aussi une classe ClassF définie, qui a une priorité de 77 et 2 copies en état KEEP (RL=1).

Un morceau, appartenant à des fichiers dans les classes : ClassA, ClassC et ClassE sera stocké selon la définition de ClassA (RL le plus élevé).
Un morceau, appartenant à des fichiers dans les classes : ClassB, ClassC sera stocké selon la définition de ClassB (RL identique, mais ClassB a EC).
Un morceau, appartenant à des fichiers dans les classes : ClassC et ClassE sera stocké selon la définition de ClassC (RL identique, mais ClassC a des labels).
Un morceau, appartenant à des fichiers dans les classes : ClassC et ClassD sera stocké selon la définition de ClassD (RL identique, pas d'EC, les deux ont des labels, donc l'ID de classe le plus élevé est choisi).
Un morceau, appartenant à des fichiers dans 6 classes, de ClassA à ClassF, sera stocké selon la définition de ClassF, car celle-ci a une priorité plus élevée que toutes les autres classes (77>0).
Dans un système avec ces 6 classes de stockage, classE ne sera jamais utilisée pour un morceau appartenant à plusieurs fichiers, elle a la priorité la plus basse possible (0) et aucune condition supplémentaire pour justifier son choix (RL le plus bas existant, pas d'EC et pas de labels).

CLASSES DE STOCKAGE PRÉDÉFINIES

Une nouvelle instance de MooseFS aura les classes suivantes prédéfinies :

2CP - seul l'état KEEP est défini, conserve 2 copies sur n'importe quels labels (classe par défaut pour le répertoire /)

3CP - seul l'état KEEP est défini, conserve 3 copies sur n'importe quels labels

EC4+1 - en état KEEP, conserve 2 copies sur n'importe quels labels, en état ARCHIVE, conserve les morceaux au format EC4+1 sur n'importe quels labels, le délai d'archivage est de 1 jour et est calculé en utilisant le ctime du fichier, les fichiers plus petits que 512kiB ne seront pas convertis au format EC

EC4+2 - (pro uniquement) en état KEEP, conserve 3 copies sur n'importe quels labels, en état ARCHIVE, conserve les morceaux au format EC4+2 sur n'importe quels labels, le délai d'archivage est de 1 jour et est calculé en utilisant le ctime du fichier, les fichiers plus petits que 512kiB ne seront pas convertis au format EC

EC8+1 - en état KEEP, conserve 2 copies sur n'importe quels labels, en état ARCHIVE, conserve les morceaux au format EC8+1 sur n'importe quels labels, le délai d'archivage est de 1 jour et est calculé en utilisant le ctime du fichier, les fichiers plus petits que 512kiB ne seront pas convertis au format EC

EC8+2 - (pro uniquement) en état KEEP, conserve 3 copies sur n'importe quels labels, en état ARCHIVE, conserve les morceaux au format EC8+2 sur n'importe quels labels, le délai d'archivage est de 1 jour et est calculé en utilisant le ctime du fichier, les fichiers plus petits que 512kiB ne seront pas convertis au format EC

Ces classes sont entièrement modifiables et supprimables et peuvent être remplacées par les classes choisies par l'utilisateur.

Jusqu'à la version 4.56.0 de MooseFS, les classes prédéfinies étaient différentes. Les informations suivantes concernent l'ancien comportement de MooseFS. Dans les versions plus récentes de MooseFS, les classes mentionnées ci-dessous pourraient exister

en tant que résultat d'une mise à niveau, mais se comporteront exactement comme des classes définies par l'utilisateur. Ces informations sont laissées ici à des fins purement informatives et seront retirées de cette page de manuel à un moment donné :

(Comportement jusqu'à la version 4.56.0) "Pour des raisons de compatibilité, chaque instance neuve ou fraîchement mise à niveau de MooseFS possède 9 classes de stockage prédéfinies. Leurs noms sont des chiffres uniques, de 1 à 9, et leurs définitions sont * à 9*. Ce sont des équivalents des objectifs numériques simples des versions précédentes du système. En cas de mise à niveau, tous les fichiers qui avaient l'objectif N avant la mise à niveau auront désormais la classe de stockage N. Ces classes ne peuvent être modifiées que lorsque l'option -f est spécifiée. Il est conseillé de créer de nouvelles classes de stockage dans un système mis à niveau et de migrer les fichiers avec l'outil mfsxchgsclass plutôt que de modifier les classes prédéfinies. Les classes prédéfinies NE PEUVENT PAS être supprimées."

EXEMPLES

Créez une nouvelle classe de stockage nommée "Class2Copies" avec 2 copies. La première copie sur un serveur de blocs avec le label "A" et la deuxième copie sur un serveur de blocs avec le label "B" :

mfscreatesclass -K A,B Class2Copies

Créez une nouvelle classe de stockage nommée "Class3Copies". Les nouveaux blocs créés (-C) seront conservés n'importe où avec 2 copies (2*). Peu après leur création, ils seront conservés (-K) en 3 copies : la première copie sur un serveur de blocs avec le label "A", la deuxième copie sur un serveur de blocs avec le label "B" et la troisième sur n'importe quel serveur de blocs :

mfscreatesclass -C '2*' -K 'A,B,*' Class3Copies

Créez une nouvelle classe de stockage nommée "ClassEC4_1". Les blocs seront créés et conservés (-K) n'importe où en 2 copies (2*) pendant 24 heures à partir de la création du fichier. Plus tard, ils seront archivés (-A) au format EC4+1 sur n'importe quel serveur de blocs :

mfscreatesclass -K '2*' -A '@4+1' ClassEC4_1

Modifiez la classe de stockage "ClassEC4_1" pour archiver les blocs après 48 heures à partir de la modification (et non de la création) du fichier :

mfsmodifysclass -d 2d -o m ClassEC4_1

Modifiez la classe de stockage "Class3Copies" pour conserver les blocs sur d'autres serveurs de blocs (mode LOOSE) si ceux avec les labels "A" et "B" sont trop occupés (surchargés) :

mfsmodifysclass -m l Class3Copies
