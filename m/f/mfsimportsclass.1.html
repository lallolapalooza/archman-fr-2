mfsscadmin - outil d'administration des classes de stockage MooseFS

DESCRIPTION

Ceci est un ensemble d'outils pour gérer les classes de stockage MooseFS. Les classes de stockage sont utilisées pour définir la politique de redondance au sein du cluster. Elles doivent ensuite être appliquées à des objets MooseFS particuliers (fichiers ou dossiers) avec les outils mfssclass (voir mfssclass(1)). Une classe de stockage est un ensemble nommé d'expressions d'étiquettes et d'autres options. L'expression d'étiquettes indique le format de redondance, le niveau de redondance désiré, et la politique de stockage désirée. Le format de redondance peut être soit des copies, soit de l'effacement-codage (EC). Le niveau de redondance est soit le nombre de copies (de 1 à 9), soit le nombre de parties de données plus parité (4+n ou 8+n), en fonction du format de redondance indiqué. La politique de stockage spécifie, à travers l'usage des étiquettes, quels chunkservers doivent être utilisés pour le stockage physique des données assignées à la classe de stockage particulière.

mfscreatesclass crée une nouvelle classe de stockage avec les options données, décrites ci-dessous, et la nomme NOM_CLASSE_STOCKAGE ; il peut y avoir plusieurs noms fournis, plusieurs classes de stockage avec la même définition seront alors créées.

mfsmodifysclass change les options données dans une classe ou des classes indiquées par le(s) paramètre(s) NOM_CLASSE_STOCKAGE.

mfsdeletesclass supprime la ou les classes indiquées par le(s) paramètre(s) NOM_CLASSE_STOCKAGE ; si l'une des classes n'est pas vide (c'est-à-dire si elle est toujours utilisée par des objets MooseFS), elle ne sera pas supprimée et l'outil retournera une erreur et un message d'erreur sera affiché ; les classes vides seront supprimées dans tous les cas.

mfsclonesclass copie la classe indiquée par NOM_CLASSE_SOURCE sous un nouveau nom fourni avec NOM_CLASSE_DESTINATION.

mfsrenamesclass change le nom d'une classe de NOM_CLASSE_SOURCE à NOM_CLASSE_DESTINATION.

mfslistsclass liste toutes les classes.

mfsimportsclass importe les définitions des classes de stockage depuis stdin ou un fichier et les crée ; le format d'entrée doit être identique à la sortie de mfslistsclass -l.

OPTIONS

-C paramètre optionnel, qui indique au système sur quels chunkservers, définis par l'expression ETIQUETTES_CREER, le bloc doit être d'abord écrit juste après sa création ; si ce paramètre n'est pas fourni pour une classe, les chunkservers ETIQUETTES_CONSERVER seront utilisés.

-K paramètre obligatoire, qui indique au système sur quels chunkservers, définis par l'expression ETIQUETTES_CONSERVER, le(s) bloc(s) doivent toujours être conservé(s), sauf conditions spéciales comme la création, l'archivage et la suppression (déplacement vers la Corbeille), si définies.

-A paramètre optionnel, qui indique au système sur quels chunkservers, définis par l'expression ETIQUETTES_ARCHIVER, le(s) bloc(s) doivent être conservé(s) à des fins d'archivage ; le système commence à traiter un bloc comme archive lorsque le atime/mtime/ctime (tel que défini par -o) du fichier auquel il appartient est plus ancien que le nombre d'heures spécifié avec l'option -d ; voir également la section COMPORTEMENT D'ARCHIVAGE ci-dessous.

-d paramètre optionnel qui définit après combien de temps à partir de atime/mtime/ctime (tel que défini par -o) un fichier (et ses blocs) est traité comme archive ; l'unité minimale est les heures, la valeur par défaut est 24, pour le formatage des valeurs voir TIME.

-o paramètre optionnel qui définit les indicateurs d'archivage. C - ctime, M - mtime, A - atime, R - réversible, F - mode rapide, P - par bloc ; la valeur par défaut est C ; voir la section COMPORTEMENT D'ARCHIVAGE ci-dessous pour les détails.

-s paramètre optionnel qui définit la longueur minimale du fichier en octets qui peut être archivée ; la valeur par défaut est 0.

-T paramètre optionnel, qui indique au système sur quels chunkservers, définis par l'expression ETIQUETTES_CORBEILLE, les blocs des fichiers dans la Corbeille doivent être conservés ; voir également -t.

-t paramètre optionnel, qui définit combien de temps en Corbeille doit s'écouler pour que le système utilise réellement le schéma défini dans -T pour un bloc ; l'unité minimale est les heures, la valeur par défaut est 0, pour le formatage des valeurs voir TIME.

-c paramètre optionnel, qui définit une description de classe, pour la commodité de l'utilisateur (une chaîne, longueur maximale 255 octets).

-p paramètre optionnel, qui définit une priorité de classe ; la valeur par défaut est 0, voir la section PRIORITÉ DES CLASSES DE STOCKAGE.

-g paramètre optionnel, qui définit un groupe d'exportation de classe ; les valeurs possibles sont de 0 à 15, la valeur par défaut est 0 ; voir mfsexport.cfg(5) pour l'explication.

-a peut être soit 1 soit 0 et indique si la classe de stockage est disponible pour tout le monde (0) ou seulement pour l'administrateur (1).

-m mode d'étiquette utilisé ; les valeurs possibles sont l (ou L, loose, Loose, LOOSE) pour le mode LOOSE, d (ou D, std, Std, STD) pour le mode STANDARD et s (ou S, strict, Strict, STRICT) pour le mode STRICT ; si aucun mode n'est défini, le mode STANDARD est supposé ; le comportement des modes d'étiquettes est décrit ci-dessous dans la section MODES D'ÉTIQUETTES.

-l liste également les définitions, pas seulement les noms des classes de stockage existantes.

-i correspondance des noms de classes de stockage insensible à la casse.

-r remplace (écrase) les classes existantes lors de l'importation des classes de stockage.

-n utilise le nom de fichier fourni comme source des définitions des classes de stockage pour l'importation, au lieu de stdin.

-M point de montage MooseFS, il n'est pas nécessaire de le spécifier si un outil est exécuté à l'intérieur d'un répertoire monté par MooseFS ou si MooseFS est monté dans /mnt/mfs/.

-? affiche un court message d'utilisation.

NOTES

EXPRESSIONS D'ÉTIQUETTES

Les étiquettes sont des lettres (A-Z - 26 lettres) qui peuvent être attribuées aux chunkservers. Chaque chunkserver peut avoir plusieurs (jusqu'à 26) étiquettes. Les étiquettes sont définies dans le fichier mfschunkserver.cfg, pour plus d'informations référez-vous à la page de manuel appropriée.

L'expression d'étiquettes est un ensemble de sous-expressions séparées par des virgules. Pour des copies complètes, chaque sous-expression spécifie le schéma de stockage d'une copie d'un fichier. Une sous-expression peut être : un astérisque ou un schéma d'étiquette. Un schéma d'étiquette peut être une seule étiquette ou une expression avec des sommes, des multiplications, des négations et des parenthèses. Une somme signifie qu'un fichier peut être stocké sur n'importe quel chunkserver correspondant à n'importe quel élément de la somme (OU logique). Une multiplication signifie qu'un fichier ne peut être stocké que sur un chunkserver correspondant à tous les éléments (ET logique). Un astérisque signifie n'importe quel chunkserver. Une négation signifie n'importe quel chunkserver sauf celui correspondant à la sous-expression niée. Des sous-expressions identiques peuvent être raccourcies en ajoutant un nombre devant l'une au lieu de la répéter plusieurs fois.

Pour EC, l'expression d'étiquettes commence par le signe @, suivi du nombre de parties de données, puis du signe + et d'un nombre qui indique combien de parties de parité le bloc doit avoir. Nombre possible

Remarque ! Lorsqu'un bloc est converti du format copie au format EC, le système effectue d'abord une opération de "fractionnement local", c'est-à-dire qu'il sélectionne une copie du bloc et calcule toutes les parties EC nécessaires sur le serveur occupé par cette copie sélectionnée. Ensuite, ces parties sont déplacées vers des serveurs de blocs séparés, correspondant aux étiquettes dans la définition de la classe de stockage pour le mode EC utilisé. Mais temporairement, entre le fractionnement et le "déplacement" des parties, elles peuvent être enregistrées sur un serveur de blocs "incorrect" même en mode STRICT. Ceci est dû à la mécanique de l'opération de "fractionnement local".

TEMPS

Pour les variables de temps, leur valeur peut être définie comme un nombre de secondes ou d'heures (entier), en fonction de l'unité minimale de la variable, ou comme une période de temps dans l'un des deux formats possibles :

premier format : #.#T où T est l'un des suivants : s-secondes, m-minutes, h-heures, d-jours ou w-semaines ; les fractions de l'unité minimale seront arrondies à la valeur entière

deuxième format : #w#d#h#m#s, n'importe quel nombre de définitions peut être omis, mais les définitions restantes doivent être dans l'ordre (donc #d#m est toujours une définition valide, mais #m#d ne l'est pas) ; plages : s,m : 0 à 59, h : 0 à 23, d : 0 à 6, w est illimité et la première définition est également toujours illimitée (c'est-à-dire que pour #d#h#m, d sera illimité)

Si une unité minimale d'une variable est supérieure aux secondes, les unités inférieures à l'unité minimale ne seront pas acceptées. Par exemple, une variable qui a les heures comme unité minimale n'acceptera pas les unités s et m.

Exemples :

1.5d est équivalent à 1d12h, est équivalent à 36h

2.5w est équivalent à 2w3d12h, est équivalent à 420h ; 2w84h n'est pas une période de temps valide (h n'est pas la première définition, donc elle est limitée par la plage de 0 à 23)

COMPORTEMENT D'ARCHIVAGE

Les blocs ont le drapeau d'archive défini lors de la boucle de maintenance des fichiers, ce qui signifie que le temps d'archivage défini par l'option -d est le temps minimum qui doit s'écouler avant que le drapeau ne soit défini, et non le temps exact.

Le comportement par défaut du système est qu'une fois qu'un bloc a le drapeau d'archive activé, il n'est PAS désactivé même si atime/ctime/mtime changent, sauf si le drapeau R est défini par l'option -o. L'écriture sur un bloc désactivera toujours son drapeau d'archive.

Drapeaux d'archive :

C - utilise ctime du fichier pour déterminer si le drapeau d'archive doit être défini - c'est le drapeau par défaut

M - utilise mtime du fichier pour déterminer si le drapeau d'archive doit être défini

A - utilise atime du fichier pour déterminer si le drapeau d'archive doit être défini

R - réversible, si atime/mtime/ctime d'un fichier change, le système vérifie si le drapeau d'archive doit être désactivé pour ses blocs

F - mode rapide, le bloc a le drapeau d'archive défini sur activé dès que possible, tout ce qui est défini avec l'option -d est ignoré

P - mode "par bloc", utilise mtime du bloc pour déterminer si le drapeau d'archive doit être défini

Le drapeau d'archive peut être modifié manuellement. Voir mfsarchive (1)

Remarque : l'état ARCHIVE ne signifie pas que les blocs ou les fichiers sont indisponibles, bloqués en écriture, etc. La désignation ARCHIVE est uniquement utilisée pour indiquer que ces données sont déjà destinées au stockage à long terme. Contrairement à l'état KEEP, qui signifie que les données sont "chaudes" et peuvent être modifiées fréquemment. La distinction entre les états KEEP et ARCHIVE sert donc uniquement à permettre une définition appropriée de la manière physique de stocker ces données. Du point de vue de l'utilisateur, le fichier est également accessible : il a des permissions, un nom identiques et se trouve dans le même répertoire. Par exemple, en raison du fait que l'écriture en mode EC peut être plus lente, nous suggérons de stocker les données "chaudes" (KEEP) en utilisant une copie et de les convertir en format EC (en leur attribuant le mode ARCHIVE) après un certain temps. Un autre exemple est le transfert automatique de données "froides" vers des disques/serveurs de blocs plus anciens/plus lents/moins chers - en utilisant différentes étiquettes.

PRIORITÉ DES CLASSES DE STOCKAGE

Les classes de stockage sont attribuées aux fichiers, mais un bloc (un fragment d'un fichier) peut appartenir à de nombreux fichiers, grâce au mécanisme d'instantané (voir mfssnapshots (1)). Si un bloc appartient à plusieurs fichiers avec des classes de stockage différentes, une classe de stockage doit être choisie pour spécifier comment les copies de ce bloc doivent être conservées dans le système. Jusqu'à la version 4.56.0 de MooseFS, une classe prédéfinie était attribuée artificiellement à un tel bloc. Actuellement, l'une des classes des fichiers sera utilisée, en fonction des priorités définies par l'utilisateur, pour être exact : le système choisira la classe avec la priorité la plus élevée parmi toutes les classes des fichiers.

Exemple 1 : 3 classes sont définies :
ClassA, avec une priorité de 100,
ClassB, avec une priorité de 206,
ClassC, avec une priorité de 1001.

Un bloc, appartenant à 2 fichiers, l'un dans ClassA, l'autre dans ClassB, sera stocké selon la définition fournie par classB (priorité plus élevée que ClassA).
Un bloc, appartenant à 3 fichiers, un dans ClassA, un dans ClassB, un dans ClassC, sera stocké selon la définition fournie par classC (priorité plus élevée que ClassA et ClassB).

Si deux classes ou plus ont la même priorité, alors les facteurs suivants seront pris en compte, dans l'ordre d'importance, pour déterminer quelle classe sera choisie :
- une classe avec un niveau de redondance (RL) plus élevé sera choisie (le maximum des niveaux de redondance KEEP et ARCHIVE de chaque classe sera considéré comme le niveau de redondance de cette classe),
- une classe qui a le format EC en état ARCHIVE sera choisie de préférence à une classe sans EC,
- une classe qui utilise des étiquettes pour l'état KEEP ou ARCHIVE sera choisie de préférence à une classe sans étiquettes,
- une classe qui a le format EC en état TRASH sera choisie de préférence à une classe sans EC,
- une classe qui utilise des étiquettes pour l'état TRASH sera choisie de préférence à une classe sans étiquettes,
- si aucune des conditions ci-dessus n'est utilisée, une classe avec un identifiant de classe plus élevé sera utilisée.

Exemple 2 : 5 classes sont définies, toutes avec la même priorité (par exemple, la priorité par défaut 0) :
ClassA (id=1) a 3 copies en état KEEP (RL=2),
ClassB (id=2) a 2 copies en état KEEP et EC4+1 en état ARCHIVE (RL=1, a EC en ARCHIVE),
ClassC (id=3) a 2 copies en état KEEP, stockées sur des étiquettes X (RL=1, pas d'EC en ARCHIVE, a des étiquettes en KEEP),
ClassD (id=4) a 2 copies en état KEEP, stockées sur des étiquettes Y (RL=1, pas d'EC en ARCHIVE, a des étiquettes en KEEP),
ClassE (id=5) a 2 copies en état KEEP (RL=1).
Il y a aussi une classe ClassF définie, qui a une priorité de 77 et 2 copies en état KEEP (RL=1).

Un bloc, appartenant aux fichiers dans les classes : ClassA, ClassC et ClassE sera stocké selon la définition de ClassA (RL la plus élevée).
Un bloc, appartenant aux fichiers dans les classes : ClassB, ClassC sera stocké selon la définition de ClassB (même RL, mais ClassB a EC).
Un bloc, appartenant aux fichiers dans les classes : ClassC et ClassE sera stocké selon la définition de ClassC (même RL, mais ClassC a des étiquettes).
Un bloc, appartenant aux fichiers dans les classes : ClassC et ClassD sera stocké selon la définition de ClassD (même RL, pas d'EC, les deux ont des étiquettes, donc l'ID de classe le plus élevé est choisi).
Un bloc, appartenant aux fichiers dans 6 classes, de ClassA à ClassF, sera stocké selon la définition de ClassF, car celle-ci a une priorité plus élevée que toutes les autres classes (77>0).
Dans un système avec ces 6 classes de stockage, classE ne sera jamais utilisée pour un bloc appartenant à plusieurs fichiers, elle a la priorité la plus basse possible (0) et aucune condition supplémentaire pour justifier son choix (RL le plus bas existant, pas d'EC et pas d'étiquettes).

CLASSES DE STOCKAGE PRÉDÉFINIES

Une nouvelle instance de MooseFS aura les classes suivantes prédéfinies :

2CP - seul état KEEP défini, conserve 2 copies sur n'importe quelles étiquettes (classe par défaut pour le répertoire /)

3CP - seul état KEEP défini, conserve 3 copies sur n'importe quelles étiquettes

EC4+1 - en état KEEP, conserve 2 copies sur n'importe quelles étiquettes, en état ARCHIVE, conserve les blocs au format EC4+1 sur n'importe quelles étiquettes, le délai d'archivage est de 1 jour et il est calculé à partir de ctime du fichier, les fichiers de moins de 512kiB ne seront pas convertis au format EC

EC4+2 - (pro uniquement) en état KEEP, conserve 3 copies sur n'importe quelles étiquettes, en état ARCHIVE, conserve les blocs au format EC4+2 sur n'importe quelles étiquettes, le délai d'archivage est de 1 jour et il est calculé à partir de ctime du fichier, les fichiers de moins de 512kiB ne seront pas convertis au format EC

EC8+1 - en état KEEP, conserve 2 copies sur n'importe quelles étiquettes, en état ARCHIVE, conserve les blocs au format EC8+1 sur n'importe quelles étiquettes, le délai d'archivage est de 1 jour et il est calculé à partir de ctime du fichier, les fichiers de moins de 512kiB ne seront pas convertis au format EC

EC8+2 - (pro uniquement) en état KEEP, conserve 3 copies sur n'importe quelles étiquettes, en état ARCHIVE, conserve les blocs au format EC8+2 sur n'importe quelles étiquettes, le délai d'archivage est de 1 jour et il est calculé à partir de ctime du fichier, les fichiers de moins de 512kiB ne seront pas convertis au format EC

Ces classes sont entièrement modifiables et supprimables et peuvent être remplacées par le choix de classes de l'utilisateur.

Jusqu'à la version 4.56.0 de MooseFS, les classes prédéfinies étaient différentes. Les informations suivantes concernent le comportement ancien de MooseFS. Dans les versions plus récentes de MooseFS, les classes mentionnées ci-dessous peuvent exister

mfsimportsclass(1) — MooseFS — Linux man pages

NAME

mfsimportsclass — imports storage classes from MooseFS 4.56.0 or older

SYNOPSIS

mfsimportsclass [OPTIONS] <CLASS_NAME>

DESCRIPTION

This utility imports the predefined storage classes that were available in MooseFS versions 4.56.0 and older. These classes are represented by single digits from 1 to 9 and have corresponding default definitions.

OPTIONS

-m
Force creation even if class with the same name already exists.
-s
Print status message. Default behaviour.
-q
Quiet mode. Don't print status messages.
-d
Debug mode. Print debug messages.

NOTES

Starting from MooseFS version 4.57.0, the predefined storage classes are no longer created automatically during installation or upgrades. This tool is provided for backward compatibility and to allow users who upgraded from older versions to retain their predefined class setup. New storage classes should be defined using mfscreatesclass and managed as user-defined classes.

The predefined classes imported by this tool will behave like any user-defined class. They can be modified or deleted after import, unless they are specifically protected.

(Behaviour up to version 4.56.0) "For compatibility reasons, every fresh or freshly upgraded instance of MooseFS has 9 predefined storage classes. Their names are single digits, from 1 to 9, and their definitions are * to 9*. They are equivalents of simple numeric goals from previous versions of the system. In case of an upgrade, all files that had goal N before upgrade, will now have N storage class. These classes can be modified only when option -f is specified. It is advised to create new storage classes in an upgraded system and migrate files with mfsxchgsclass tool, rather than modify the predefined classes. The predefined classes CANNOT be deleted."

EXAMPLES

Import the predefined storage classes and name the set "LegacyClasses":

mfsimportsclass LegacyClasses

Import the predefined storage classes, force creation if the class name already exists, and do not print status messages:

mfsimportsclass -m -q LegacyClasses
