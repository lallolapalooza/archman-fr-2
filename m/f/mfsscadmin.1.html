NOM

mfsscadmin - outil d'administration des classes de stockage MooseFS

SYNTAXE

mfscreatesclass [-?] [-M POINTDEMONTAGE] -K ETIQUETTES_CONSERVER [-c description] [-p priorité] [-g groupe_export] [-a admin_seulement] [-m mode_etiquettes] [-o mode_arch] [-C ETIQUETTES_CREER] [-A ETIQUETTES_ARCHIVER [-d delai_arch] [-s longueur_min_fichier]] [-T ETIQUETTES_POUBELLE [-t duree_min_poubelle]] NOM_CLASSESTOCKAGE...

mfsmodifysclass [-?] [-M POINTDEMONTAGE] [-c description] [-p priorité] [-g groupe_export] [-a admin_seulement] [-m mode_etiquettes] [-o mode_arch] [-C ETIQUETTES_CREER] [-K ETIQUETTES_CONSERVER] [-A ETIQUETTES_ARCHIVER] [-d delai_arch] [-s longueur_min_fichier] [-T ETIQUETTES_POUBELLE] [-t duree_min_poubelle] NOM_CLASSESTOCKAGE...

mfsdeletesclass [-?] [-M POINTDEMONTAGE] NOM_CLASSESTOCKAGE...

mfsclonesclass [-?] [-M POINTDEMONTAGE] NOM_CLASSE SOURCE NOM_CLASSE DESTINATION...

mfsrenamesclass [-?] [-M POINTDEMONTAGE] NOM_CLASSE SOURCE NOM_CLASSE DESTINATION

mfslistsclass [-?] [-M POINTDEMONTAGE] [-l] [-i] [MOTIF_GLOB_NOM_CLASSE]

mfsimportsclass [-?] [-M POINTDEMONTAGE] [-r] [-n nom_fichier]

DESCRIPTION

Il s'agit d'un ensemble d'outils pour gérer les classes de stockage MooseFS. Les classes de stockage sont utilisées pour définir la politique de redondance au sein du cluster. Elles devraient être ensuite appliquées à des objets MooseFS particuliers (fichiers ou dossiers) avec les outils mfssclass (voir mfssclass(1)). Une classe de stockage est un ensemble nommé d'expressions d'étiquettes et d'autres options. L'expression d'étiquettes indique le format de redondance, le niveau de redondance souhaité et la politique de stockage souhaitée. Le format de redondance peut être soit des copies, soit de l'erasure-coding (EC). Le niveau de redondance est soit le nombre de copies (de 1 à 9), soit le nombre de parties de données plus de parité (4+n ou 8+n), en fonction du format de redondance indiqué. La politique de stockage spécifie, par l'utilisation d'étiquettes, quels serveurs de chunks (chunkservers) doivent être utilisés pour le stockage physique des données assignées à la classe de stockage particulière.

mfscreatesclass crée une nouvelle classe de stockage avec les options données, décrites ci-dessous, et la nomme NOM_CLASSESTOCKAGE ; plusieurs noms peuvent être fournis, auquel cas plusieurs classes de stockage avec la même définition seront créées.

mfsmodifysclass modifie les options données dans une classe ou des classes indiquées par les paramètres NOM_CLASSESTOCKAGE.

mfsdeletesclass supprime la classe ou les classes indiquées par les paramètres NOM_CLASSESTOCKAGE ; si l'une des classes n'est pas vide (c'est-à-dire qu'elle est toujours utilisée par des objets MooseFS), elle ne sera pas supprimée et l'outil retournera une erreur et un message d'erreur sera affiché ; les classes vides seront supprimées dans tous les cas.

mfsclonesclass copie la classe indiquée par NOM_CLASSE SOURCE sous un nouveau nom fourni avec NOM_CLASSE DESTINATION.

mfsrenamesclass modifie le nom d'une classe de NOM_CLASSE SOURCE à NOM_CLASSE DESTINATION.

mfslistsclass liste toutes les classes.

mfsimportsclass importe les définitions des classes de stockage depuis stdin ou un fichier et les crée ; le format d'entrée doit être identique à la sortie de mfslistsclass -l.

OPTIONS

-C paramètre optionnel, qui indique au système sur quels serveurs de chunks, définis par l'expression ETIQUETTES_CREER, le chunk doit être écrit juste après sa création ; si ce paramètre n'est pas fourni pour une classe, les serveurs de chunks ETIQUETTES_CONSERVER seront utilisés.

-K paramètre obligatoire, qui indique au système sur quels serveurs de chunks, définis par l'expression ETIQUETTES_CONSERVER, les chunks doivent être conservés en permanence, sauf conditions spéciales comme la création, l'archivage et la suppression (déplacement vers la Poubelle), si elles sont définies.

-A paramètre optionnel, qui indique au système sur quels serveurs de chunks, définis par l'expression ETIQUETTES_ARCHIVER, les chunks doivent être conservés à des fins d'archivage ; le système commence à traiter un chunk comme archive lorsque atime/mtime/ctime (tel que défini par -o) du fichier auquel il appartient est plus ancien que le nombre d'heures spécifié par l'option -d ; voir aussi la section COMPORTEMENT D'ARCHIVAGE ci-dessous.

-d paramètre optionnel qui définit après combien de temps depuis atime/mtime/ctime (tel que défini par -o) un fichier (et ses chunks) est traité comme archive ; l'unité minimum est l'heure, la valeur par défaut est 24 ; pour le formatage de la valeur, voir TIME.

-o paramètre optionnel qui définit les drapeaux d'archivage. C - ctime, M - mtime, A - atime, R - réversible, F - mode rapide, P - par chunk ; la valeur par défaut est C ; voir la section COMPORTEMENT D'ARCHIVAGE ci-dessous pour les détails.

-s paramètre optionnel qui définit la longueur minimale du fichier en octets qui peut être archivée ; la valeur par défaut est 0.

-T paramètre optionnel, qui indique au système sur quels serveurs de chunks, définis par l'expression ETIQUETTES_POUBELLE, les chunks des fichiers dans la Poubelle doivent être conservés ; voir aussi -t.

-t paramètre optionnel, qui définit combien de temps dans la Poubelle doit s'écouler pour que le système utilise réellement le schéma défini dans -T pour un chunk ; l'unité minimum est l'heure, la valeur par défaut est 0 ; pour le formatage de la valeur, voir TIME.

-c paramètre optionnel, qui définit une description de classe, pour la commodité de l'utilisateur (une chaîne de caractères, longueur maximale 255 octets).

-p paramètre optionnel, qui définit une priorité de classe ; la valeur par défaut est 0 ; voir la section PRIORITÉ DES CLASSES DE STOCKAGE.

-g paramètre optionnel, qui définit un groupe d'exportation de classe ; les valeurs possibles sont de 0 à 15, la valeur par défaut est 0 ; voir mfsexport.cfg(5) pour l'explication.

-a peut être soit 1 soit 0 et indique si la classe de stockage est disponible pour tout le monde (0) ou seulement pour l'administrateur (1).

-m mode d'étiquettes utilisé ; les valeurs possibles sont l (ou L, loose, Loose, LOOSE) pour le mode LOOSE, d (ou D, std, Std, STD) pour le mode STANDARD et s (ou S, strict, Strict, STRICT) pour le mode STRICT ; si aucun mode n'est défini, le mode STANDARD est supposé ; le comportement des modes d'étiquettes est décrit ci-dessous dans la section MODES D'ÉTIQUETTES.

-l liste également les définitions, pas seulement les noms des classes de stockage existantes.

-i comparaison des noms de classes de stockage insensible à la casse.

-r remplace (écrase) les classes existantes lors de l'importation de classes de stockage.

-n utilise le nom de fichier fourni comme source des définitions des classes de stockage pour l'importation, au lieu de stdin.

-M point de montage MooseFS ; il n'est pas nécessaire de le spécifier si un outil est exécuté à l'intérieur d'un répertoire monté par MooseFS ou si MooseFS est monté dans /mnt/mfs/.

-? affiche un court message d'utilisation.

NOTES

EXPRESSIONS D'ÉTIQUETTES

Les étiquettes sont des lettres (A-Z - 26 lettres) qui peuvent être attribuées aux serveurs de chunks. Chaque serveur de chunks peut avoir plusieurs étiquettes (jusqu'à 26). Les étiquettes sont définies dans le fichier mfschunkserver.cfg, pour plus d'informations, reportez-vous à la page man appropriée.

Une expression d'étiquettes est un ensemble de sous-expressions séparées par des virgules. Pour des copies complètes, chaque sous-expression spécifie le schéma de stockage d'une copie d'un fichier. Une sous-expression peut être : un astérisque ou un schéma d'étiquette. Un schéma d'étiquette peut être une seule étiquette ou une expression avec des sommes, des multiplications, des négations et des parenthèses. La somme signifie qu'un fichier peut être stocké sur n'importe quel serveur de chunks correspondant à n'importe quel élément de la somme (ou logique). La multiplication signifie qu'un fichier ne peut être stocké que sur un serveur de chunks correspondant à tous les éléments (et logique). L'astérisque signifie n'importe quel serveur de chunks. La négation signifie n'importe quel serveur de chunks sauf celui qui correspond à la sous-expression niée. Des sous-expressions identiques peuvent être abrégées en ajoutant un nombre devant l'une d'elles au lieu de la répéter plusieurs fois.

Pour EC, l'expression d'étiquettes commence par le signe @, suivi du nombre de parties de données, puis du signe + et d'un nombre qui indique combien de parties de parité le chunk doit avoir. Les nombres possibles de

data parts sont 4 ou 8. Le nombre de parts de parité possibles est 1 (version CE) ou 1 à 9 (version PRO). Ainsi, par exemple, @4+1 signifie EC avec 4 parts de données et 1 part de parité, @8+3 signifie EC avec 8 parts de données et 3 parts de parité. Si le nombre de parts de données est omis, le maître utilise la valeur par défaut définie par DEFAULT_EC_DATA_PARTS - voir mfsmaster.cfg (5). Dans ce cas, @2 signifie @8+2 ou @4+2. Ensuite, un maximum de deux sous-expressions peuvent suivre, séparées par des virgules. Si une seule est présente, elle définit où toutes les parts doivent être conservées. Si les deux sont présentes, la première sous-expression définit où les parts de données doivent être conservées, la seconde sous-expression définit où les parts de parité doivent être conservées.

L'expression des étiquettes peut être soit une expression d'étiquettes ordinaire, soit une expression d'étiquettes EC (c'est-à-dire qu'une expression d'étiquettes EC ne peut pas être une sous-expression). Une expression d'étiquettes EC ne peut être utilisée qu'à la place de ARCHIVE_LABELS ou TRASH_LABELS dans la définition de la classe de stockage, une expression d'étiquettes ordinaire peut être utilisée n'importe où.

À la fin de chaque expression d'étiquettes, une ou deux informations supplémentaires, divisées par un séparateur spécial, peuvent être ajoutées. La première information possible est l'extension de distinction et le séparateur est le signe slash (/). La seconde est la substitution du mode d'étiquettes et cette extension est séparée par le signe deux-points (:).

L'extension de distinction peut être une liste d'étiquettes ou l'une des chaînes spéciales suivantes :

[IP] ou [I] - distinguer par numéro IP

[RACK] ou [R] - distinguer par RACK, tel que défini dans la topologie, voir mfstopology.cfg (5)

Si elle est présente, la partie de distinction indique au système qu'il doit essayer de distribuer les copies complètes de manière à ce que chaque copie soit soit sur une étiquette différente de la liste, soit sur un chunkserver avec une adresse IP différente, soit dans un rack différent. Pour l'EC, la partie de distinction est actuellement ignorée.

ATTENTION ! Si CHUNKS_UNIQUE_MODE est défini dans mfsmaster.cfg à une valeur autre que 0, il remplacera tout paramètre de distinction dans les classes de stockage. Pour plus d'informations sur ce paramètre, consultez le manuel mfsmaster.cfg (5).

L'extension de substitution du mode d'étiquettes peut être l'un des trois caractères : d (alternativement D ou sous forme de chaîne std ou Std ou STD), s (alternativement S ou sous forme de chaîne strict ou Strict ou STRICT) ou l (alternativement L ou sous forme de chaîne loose ou Loose ou LOOSE) et ils signifient que le mode d'étiquettes STANDARD, STRICT ou LOOSE, respectivement, doit être appliqué uniquement à cette expression d'étiquettes. Pour des explications sur les modes d'étiquettes, voir la section MODES D'ÉTIQUETTES.

Une ou deux extensions peuvent être présentes pour chaque expression d'étiquettes, chacune doit commencer par son séparateur et si les deux sont présentes, l'ordre doit être respecté, c'est-à-dire que l'extension de distinction doit être la première et l'extension du mode d'étiquettes doit être la seconde.

Exemples d'expressions d'étiquettes :

A,B - les fichiers auront deux copies, une copie sera stockée sur le(s) chunkserver(s) avec l'étiquette A, l'autre sur le(s) chunkserver(s) avec l'étiquette B

A,* - les fichiers auront deux copies, une copie sera stockée sur le(s) chunkserver(s) avec l'étiquette A, l'autre sur n'importe quel(s) chunkserver(s)

A,!A - les fichiers auront deux copies, une copie sera stockée sur le(s) chunkserver(s) avec l'étiquette A, l'autre sur n'importe quel(s) chunkserver(s) qui n'ont pas l'étiquette A

*,* - les fichiers auront deux copies, stockées sur n'importe quel(s) chunkserver(s) (différent pour chaque copie)

AB,C+D+E - les fichiers auront deux copies, une copie sera stockée sur n'importe quel(s) chunkserver(s) ayant à la fois les étiquettes A et B (multiplication des étiquettes), l'autre sur n'importe quel(s) chunkserver(s) ayant soit l'étiquette C, soit l'étiquette D, soit l'étiquette E (somme des étiquettes)

A,B[X+Y],C[X+Y] - les fichiers auront trois copies, une copie sera stockée sur n'importe quel(s) chunkserver(s) avec l'étiquette A, la seconde sur n'importe quel(s) chunserver(s) ayant l'étiquette B et soit l'étiquette X, soit l'étiquette Y, la troisième sur n'importe quel(s) chunkserver(s), ayant l'étiquette C et soit l'étiquette X, soit l'étiquette Y

L'expression 2A est équivalente à l'expression A,A

L'expression A,3BC est équivalente à l'expression A,BC,BC,BC

L'expression 2 est équivalente à l'expression 2* est équivalente à l'expression *,*

3*/[IP] - les fichiers auront 3 copies, chaque copie sera conservée sur un chunkserver avec une adresse IP différente

A,B/[RACK] - les fichiers auront deux copies, une copie sera stockée sur le(s) chunkserver(s) avec l'étiquette A, l'autre sur le(s) chunkserver(s) avec l'étiquette B dans un rack différent de l'autre copie

S,H,H/[RACK] - les fichiers auront 3 copies, une sur un serveur avec l'étiquette S, deux sur des serveurs avec l'étiquette H, mais chaque copie sera sur un serveur avec une étiquette différente de l'ensemble A, B, X, Y, Z

@4+1 - les fichiers seront conservés au format EC, 4 parts de données et 1 part de parité

@8+3 - les fichiers seront conservés au format EC, 8 parts de données et 3 parts de parité

@2 - les fichiers seront conservés au format EC, nombre de parts de données par défaut, 2 parts de parité

@4+3,Z - les fichiers seront conservés au format EC, 4 parts de données et 3 parts de parité - toutes sur des chunkservers avec l'étiquette Z.

@2,A(X+Y) - les fichiers seront conservés au format EC, nombre de parts de données par défaut, 2 parts de parité, toutes les parts seront conservées sur des chunsevers avec l'étiquette A et soit X, soit Y

@3,S,H - les fichiers seront conservés au format EC, le nombre par défaut de parts de données sera conservé sur des chunkservers avec l'étiquette S, 3 parts de parité seront conservées sur des chunkservers avec l'étiquette H

AB,AC:l - les fichiers seront conservés au format copie, une copie sur un serveur avec les étiquettes A et B, la seconde sur un serveur avec les étiquettes A et C et le comportement de ceci sera LOOSE

@4+2,X,Y:s - les fichiers seront conservés au format EC, 4 parts de données seront conservées sur des serveurs avec l'étiquette X, 2 parts de parité (checksum) seront conservées sur des serveurs avec l'étiquette Y et le comportement de ceci sera STRICT

2A/[IP]:s - les fichiers doivent être conservés en 2 copies, les deux copies sur des serveurs avec l'étiquette A, mais chaque serveur doit avoir une IP différente, le comportement de ceci lors de la prise en compte des étiquettes doit être STRICT

MODES D'ÉTIQUETTES

Il est important de spécifier quoi faire lorsqu'il n'est pas possible de satisfaire les exigences d'étiquettes d'une classe de stockage, c'est-à-dire : il n'y a pas d'espace disponible sur tous les serveurs avec les étiquettes requises, il n'y a pas assez de serveurs avec les étiquettes requises ou les serveurs avec les étiquettes requises sont tous occupés. La question est de savoir si le système doit créer des chunks sur d'autres serveurs (avec des étiquettes non correspondantes) ou non. Cette décision doit être prise par l'utilisateur.

Il existe 3 modes de fonctionnement : STANDARD, LOOSE et STRICT. Les modes fonctionnent de manière légèrement différente selon que le chunk est stocké au format copie ou EC, en raison de la nature et des algorithmes différents utilisés par chacun de ces formats.

Pour le format copie, les 3 modes se comportent comme suit :

En mode STANDARD, en cas de serveurs surchargés, le système attendra, mais en cas de manque d'espace, il utilisera d'autres serveurs et répliquera les données vers les serveurs corrects lorsque cela sera possible. Cela signifie que si certains serveurs sont en état d'occupation prolongée, il pourrait ne pas être possible de créer de nouveaux chunks avec certaines classes de stockage et les chunks en danger (sous-objectif) de ces classes courent un risque plus élevé d'être complètement perdus en raison de réplications retardées.

En mode STRICT, lors de l'écriture d'un nouveau fichier, le système renverra une erreur (ENOSPC) en cas de manque d'espace sur les serveurs marqués avec les étiquettes spécifiées pour la création des chunks. Il attendra toujours les serveurs surchargés. Les réplications sous-objectif ne seront pas effectuées s'il n'y a pas d'espace sur les serveurs portant les étiquettes correspondant à la classe de stockage. Cela signifie un risque élevé de perte de données si les serveurs avec certaines étiquettes sont définitivement remplis de données !

En mode LOOSE, le système utilisera immédiatement d'autres serveurs en cas de serveurs surchargés ou de manque d'espace sur les serveurs et répliquera les données vers les serveurs corrects lorsque cela deviendra possible. Il n'y a pas de délai ou d'erreur lors de la création de fichiers et les réplications sous-objectif sont toujours effectuées dès que possible.

Ce tableau résume le comportement des modes pour les chunks stockés au format copie :

STANDARD STRICT LOOSE
CRÉATION - SURCHARGE ATTENDRE ATTENDRE ÉCRIRE N'IMPORTE OÙ
CRÉATION - PAS D'ESPACE ÉCRIRE N'IMPORTE OÙ ENOSPC ÉCRIRE N'IMPORTE OÙ
RÉPLICATION - SURCHARGE ATTENDRE ATTENDRE ÉCRIRE N'IMPORTE OÙ
RÉPLICATION - PAS D'ESPACE ÉCRIRE N'IMPORTE OÙ PAS DE COPIE ÉCRIRE N'IMPORTE OÙ

Pour les chunks stockés au format EC, les 3 modes se comportent comme suit :

En général, les chunks ne seront convertis du format copie au format EC que s'il y a suffisamment de serveurs dans le système pour stocker en toute sécurité toutes les parts du format EC. Pour le format EC @N+X, où N est le nombre de parts de données et peut être soit 4, soit 8, et X est le nombre de parts de parité/checksum et peut être égal à 1 (version CE) ou à n'importe quel nombre de 1 à 9 (version PRO), les exigences générales sont :
- au moins N+2X chunkservers pour convertir de nouveaux chunks du format copie au format EC
- au moins N+X chunkservers pour conserver les chunks déjà au format EC dans ce format
- s'il y a moins de N+X serveurs, tous les chunks reviendront au format copie (définition KEEP).

En mode LOOSE, le système essaiera d'utiliser d'abord les serveurs correspondant à l'expression d'étiquettes définie dans la classe de stockage utilisée, mais si suffisamment de serveurs avec les étiquettes "correctes" ne sont pas disponibles (parce qu'ils sont occupés, n'ont pas d'espace ou ne sont tout simplement pas définis), il utilisera n'importe quel chunkserver disponible indépendamment de l'étiquette ; ainsi, N+2X et N+X sont calculés à partir de tous les chunkservers disponibles lorsque le système décide du format à utiliser pour conserver un chunk. De plus, lorsqu'une part d'un chunk au format EC devient indisponible ou corrompue, la restauration de cette part sera également effectuée sur n'importe quel serveur disponible, si un serveur avec les étiquettes "correctes" ne peut pas être utilisé actuellement.

Il est important de se rappeler que s'il n'y a pas assez de serveurs avec les étiquettes "correctes" disponibles pour un chunk en mode LOOSE, le système peut utiliser autant de chunkservers "autres" qu'il le souhaite, pas seulement le nombre minimal manquant par rapport au nombre "correct" de serveurs.

En mode STRICT, le système n'utilisera que les serveurs correspondant à l'expression d'étiquettes définie dans la classe de stockage utilisée, donc uniquement les serveurs disponibles ou occupés à court terme

matching defined label expression will be used for calculation of N+2X and N+X when the system decides what format to use to keep a chunk. When one part of a chunk in EC format becomes unavailable or corrupted, restoration of such part can only be done to a server with "correct" label; if such a server is unavailable long term (i.e. is not available outright or only temporarily busy), this will automatically mean that the chunk needs to be reverted to keep format anyway (if the missing part is a parity/checksum part, the chunk will just revert to copy format using all available data parts, if a data part is missing, it will be restored to a chunk server hosting another part of the same chunk - which is not allowed under normal circumstances - and then the conversion to copy format will follow immediately).

In STANDARD mode the system will behave like in STRICT mode when it needs to make a decision whether it will convert a new chunk from copy format to EC format, that is the N+2X in this step is calculated only from "correctly" labeled servers. But to make a decision whether existing chunks need to be converted back from EC format to copy format it will look at all available servers, regardless of labels, so the N+X in this step is calculated from all available servers, like in LOOSE mode. X. In case of missing parts, if it's not possible to restore them to chunk servers with "correct" labels, the system will also adapt the LOOSE mode behaviour and try to use any available servers.

Notice! When a chunk is converted from copy format to EC format, the system first performs a "local split" operation, that is it picks one copy of the chunk and calculates all EC parts necessary on the server occupied by this selected copy. Then these parts are moved to separate chunkservers, matching the labels in the storage class definition for used EC mode. But temporarily, between the split and the "moving out" of the parts, they can be recorded on a "wrong" chunk server even in STRICT mode. This is because of the mechanics of the "local split" operation.

TEMPS

Pour les variables temporelles, leur valeur peut être définie comme un nombre de secondes ou d'heures (entier), selon l'unité minimale de la variable, ou comme une période de temps dans l'un des deux formats possibles :

premier format : #.#T où T est l'un des suivants : s-secondes, m-minutes, h-heures, d-jours ou w-semaines ; les fractions de l'unité minimale seront arrondies à la valeur entière

deuxième format : #w#d#h#m#s, un nombre quelconque de définitions peut être omis, mais les définitions restantes doivent être dans l'ordre (donc #d#m est toujours une définition valide, mais #m#d ne l'est pas) ; plages : s,m : 0 à 59, h : 0 à 23, d : 0 à 6, w est illimité et la première définition est également toujours illimitée (c'est-à-dire que pour #d#h#m, d sera illimité)

Si une unité minimale d'une variable est supérieure à la seconde, les unités inférieures à l'unité minimale ne seront pas acceptées. Par exemple, une variable dont l'unité minimale est l'heure n'acceptera pas les unités s et m.

Exemples :

1.5d est équivalent à 1d12h, est équivalent à 36h

2.5w est équivalent à 2w3d12h, est équivalent à 420h ; 2w84h n'est pas une période de temps valide (h n'étant pas la première définition, elle est limitée par la plage de 0 à 23)

COMPORTEMENT D'ARCHIVAGE

Les blocs (chunks) ont un indicateur d'archive défini lors de la boucle de maintenance des fichiers, ce qui signifie que le temps d'archivage défini par l'option -d est le temps minimum qui doit s'écouler avant que l'indicateur ne soit défini, et non le temps exact.

Le comportement par défaut du système est qu'une fois qu'un bloc a l'indicateur d'archive activé, il n'est PAS désactivé même si atime/ctime/mtime change, sauf si le drapeau R est défini par l'option -o. L'écriture sur un bloc désactivera toujours son indicateur d'archive.

Indicateurs d'archive :

C - utilise le ctime du fichier pour déterminer si l'indicateur d'archive doit être activé - c'est l'indicateur par défaut

M - utilise le mtime du fichier pour déterminer si l'indicateur d'archive doit être activé

A - utilise l'atime du fichier pour déterminer si l'indicateur d'archive doit être activé

R - réversible, si atime/mtime/ctime change pour un fichier, le système vérifie si l'indicateur d'archive doit être désactivé pour ses blocs

F - mode rapide (fastmode), le bloc a l'indicateur d'archive activé dès que possible, tout ce qui est défini avec l'option -d est ignoré

P - mode "par bloc" (per chunk), utilise le mtime du bloc pour déterminer si l'indicateur d'archive doit être activé

L'indicateur d'archive peut être modifié manuellement. Voir mfsarchive (1)

Note : l'état ARCHIVE ne signifie pas que les blocs ou les fichiers sont indisponibles, bloqués en écriture, etc. La désignation ARCHIVE sert uniquement à indiquer que ces données sont destinées à un stockage à long terme. Contrairement à l'état KEEP, qui signifie que les données sont "chaudes" et peuvent être modifiées fréquemment. La distinction entre les états KEEP et ARCHIVE sert donc uniquement à définir la manière physique de stocker ces données. Du point de vue de l'utilisateur, le fichier est accessible de la même manière : il a les mêmes permissions, le même nom et se trouve dans le même répertoire. Par exemple, étant donné que l'écriture en mode EC peut être plus lente, nous suggérons de stocker les données "chaudes" (KEEP) en utilisant une copie et de passer au format EC (en attribuant le mode ARCHIVE) après un certain temps. Un autre exemple est le transfert automatique de données "froides" vers des disques et des serveurs de blocs plus anciens/plus lents/moins chers - en utilisant des étiquettes différentes.

PRIORITÉ DES CLASSES DE STOCKAGE

Les classes de stockage sont attribuées aux fichiers, mais un bloc (un fragment de fichier) peut appartenir à plusieurs fichiers, grâce au mécanisme de snapshot (voir mfssnapshots (1)). Si un bloc appartient à plusieurs fichiers avec des classes de stockage différentes, une classe de stockage doit être choisie pour spécifier comment les copies de ce bloc doivent être conservées dans le système. Jusqu'à la version 4.56.0 de MooseFS, une classe prédéfinie était artificiellement attribuée à un tel bloc. Actuellement, l'une des classes des fichiers sera utilisée, en fonction des priorités attribuées par l'utilisateur, plus précisément : le système choisira la classe avec la priorité la plus élevée parmi toutes les classes des fichiers.

Exemple 1 : 3 classes sont définies :
ClassA, avec une priorité de 100,
ClassB, avec une priorité de 206,
ClassC, avec une priorité de 1001.

Un bloc appartenant à 2 fichiers, l'un en ClassA et l'autre en ClassB, sera stocké selon la définition fournie par classB (priorité plus élevée que ClassA).
Un bloc appartenant à 3 fichiers, l'un en ClassA, un en ClassB, un en ClassC, sera stocké selon la définition fournie par classC (priorité plus élevée que ClassA et ClassB).

Si deux classes ou plus ont la même priorité, les facteurs suivants seront pris en compte, par ordre d'importance, pour déterminer quelle classe sera choisie :
- une classe avec un niveau de redondance (RL) plus élevé sera choisie (le maximum des niveaux de redondance KEEP et ARCHIVE de chaque classe sera considéré comme le niveau de redondance de cette classe),
- une classe qui a le format EC en état ARCHIVE sera choisie par rapport à une classe sans EC,
- une classe qui utilise des étiquettes pour l'état KEEP ou ARCHIVE sera choisie par rapport à une classe sans étiquettes,
- une classe qui a le format EC en état TRASH sera choisie par rapport à une classe sans EC,
- une classe qui utilise des étiquettes pour l'état TRASH sera choisie par rapport à une classe sans étiquettes,
- si aucune des conditions ci-dessus n'est utilisée, une classe avec un ID de classe plus élevé sera utilisée.

Exemple 2 : 5 classes sont définies, toutes avec la même priorité (par exemple, la priorité par défaut 0) :
ClassA (id=1) a 3 copies en état KEEP (RL=2),
ClassB (id=2) a 2 copies en état KEEP et EC4+1 en état ARCHIVE (RL=1, a EC en ARCHIVE),
ClassC (id=3) a 2 copies en état KEEP, stockées sur des étiquettes X (RL=1, pas d'EC en ARCHIVE, a des étiquettes en KEEP),
ClassD (id=4) a 2 copies en état KEEP, stockées sur des étiquettes Y (RL=1, pas d'EC en ARCHIVE, a des étiquettes en KEEP),
ClassE (id=5) a 2 copies en état KEEP (RL=1).
Il y a également une classe ClassF définie, qui a une priorité de 77 et 2 copies en état KEEP (RL=1).

Un bloc appartenant aux fichiers des classes : ClassA, ClassC et ClassE sera stocké selon la définition de ClassA (RL le plus élevé).
Un bloc appartenant aux fichiers des classes : ClassB, ClassC sera stocké selon la définition de ClassB (RL identique, mais ClassB a EC).
Un bloc appartenant aux fichiers des classes : ClassC et ClassE sera stocké selon la définition de ClassC (RL identique, mais ClassC a des étiquettes).
Un bloc appartenant aux fichiers des classes : ClassC et ClassD sera stocké selon la définition de ClassD (RL identique, pas d'EC, les deux ont des étiquettes, donc l'ID de classe le plus élevé est choisi).
Un bloc appartenant aux fichiers de 6 classes, de ClassA à ClassF, sera stocké selon la définition de ClassF, car celle-ci a une priorité plus élevée que toutes les autres classes (77 > 0).
Dans un système avec ces 6 classes de stockage, classE ne sera jamais utilisée pour un bloc appartenant à plusieurs fichiers, elle a la priorité la plus basse possible (0) et aucune condition supplémentaire pour justifier son choix (RL existant le plus bas, pas d'EC et pas d'étiquettes).

CLASSES DE STOCKAGE PRÉDÉFINIES

Une nouvelle instance de MooseFS aura les classes suivantes prédéfinies :

2CP - seul l'état KEEP est défini, conserve 2 copies sur n'importe quelles étiquettes (classe par défaut pour le répertoire /)

3CP - seul l'état KEEP est défini, conserve 3 copies sur n'importe quelles étiquettes

EC4+1 - en état KEEP, conserve 2 copies sur n'importe quelles étiquettes, en état ARCHIVE, conserve les blocs au format EC4+1 sur n'importe quelles étiquettes, le délai d'archivage est de 1 jour et est calculé en utilisant le ctime du fichier, les fichiers de moins de 512kiB ne seront pas convertis au format EC

EC4+2 - (pro uniquement) en état KEEP, conserve 3 copies sur n'importe quelles étiquettes, en état ARCHIVE, conserve les blocs au format EC4+2 sur n'importe quelles étiquettes, le délai d'archivage est de 1 jour et est calculé en utilisant le ctime du fichier, les fichiers de moins de 512kiB ne seront pas convertis au format EC

EC8+1 - en état KEEP, conserve 2 copies sur n'importe quelles étiquettes, en état ARCHIVE, conserve les blocs au format EC8+1 sur n'importe quelles étiquettes, le délai d'archivage est de 1 jour et est calculé en utilisant le ctime du fichier, les fichiers de moins de 512kiB ne seront pas convertis au format EC

EC8+2 - (pro uniquement) en état KEEP, conserve 3 copies sur n'importe quelles étiquettes, en état ARCHIVE, conserve les blocs au format EC8+2 sur n'importe quelles étiquettes, le délai d'archivage est de 1 jour et est calculé en utilisant le ctime du fichier, les fichiers de moins de 512kiB ne seront pas convertis au format EC

Ces classes sont entièrement modifiables et supprimables et peuvent être remplacées par des classes choisies par l'utilisateur.

Jusqu'à la version 4.56.0 de MooseFS, les classes prédéfinies étaient différentes. Les informations suivantes concernent le comportement ancien de MooseFS. Dans les versions plus récentes de MooseFS, les classes mentionnées ci-dessous pourraient exister comme un

mfsscadmin(1) — MooseFS 4.58.2-1

NOM

mfsscadmin - outil de gestion des classes de stockage MooseFS

SYNTAXE

mfsscadmin [-h|--help] [-v|--version] [command] [args]

DESCRIPTION

L'outil mfsscadmin est utilisé pour gérer les classes de stockage dans un système MooseFS.

OPTIONS

Aucune option globale n'est prise en charge par cet outil.

COMMANDES

Les commandes suivantes sont prises en charge :

create class_name [-C template] [-K template] [-A template] [-M template] [-S template] [-d days] [-o mode]
Crée une nouvelle classe de stockage nommée class_name. Les modèles spécifiés par -C, -K, -A, -M et -S définissent les stratégies de stockage pour la création, la conservation, l'archivage, le montage et le stockage de base respectivement. L'option -d spécifie le délai en jours avant l'application de la stratégie d'archivage. L'option -o définit le mode de stockage (par exemple, par défaut, l pour LAISSER-PASSER).
modify class_name [-C template] [-K template] [-A template] [-M template] [-S template] [-d days] [-o mode]
Modifie une classe de stockage existante nommée class_name. Les options sont les mêmes que pour la commande create.
delete class_name
Supprime une classe de stockage nommée class_name.
list
Liste toutes les classes de stockage existantes.
show class_name
Affiche les détails d'une classe de stockage spécifique nommée class_name.
setgoals class_name file...
Définit la classe de stockage class_name pour les fichiers spécifiés.
setclass class_name file...
Définit la classe de stockage class_name pour les fichiers spécifiés. C'est un synonyme de setgoals.

Les modèles de stockage peuvent inclure :

N
Le nombre de copies à conserver.
*
N'importe quel serveur de chunks.
label
Un serveur de chunks avec une étiquette spécifique.
N*
N'importe quel serveur de chunks, mais avec un minimum de N copies.
label1,label2,...
Serveurs de chunks avec les étiquettes spécifiées.
@X+Y
Format de codage d'effacement (par exemple, @4+1 pour Reed-Solomon 4 parité).

NOTES

Les classes de stockage sont un résultat d'une mise à niveau, mais se comporteront exactement comme n'importe quelle classe définie par l'utilisateur. Ces informations sont laissées ici à des fins purement informatives et seront supprimées de cette page de manuel à un moment donné :

(Comportement jusqu'à la version 4.56.0) "Pour des raisons de compatibilité, chaque instance fraîche ou fraîchement mise à niveau de MooseFS a 9 classes de stockage prédéfinies. Leurs noms sont des chiffres uniques, de 1 à 9, et leurs définitions sont * à 9*. Ce sont des équivalents des objectifs numériques simples des versions précédentes du système. En cas de mise à niveau, tous les fichiers qui avaient l'objectif N avant la mise à niveau auront désormais la classe de stockage N. Ces classes ne peuvent être modifiées que lorsque l'option -f est spécifiée. Il est conseillé de créer de nouvelles classes de stockage dans un système mis à niveau et de migrer les fichiers avec l'outil mfsxchgsclass, plutôt que de modifier les classes prédéfinies. Les classes prédéfinies NE PEUVENT PAS être supprimées."

EXEMPLES

Créez une nouvelle classe de stockage nommée "Class2Copies" avec 2 copies. La première copie sur un serveur de chunks avec l'étiquette "A" et la deuxième copie sur un serveur de chunks avec l'étiquette "B" :

mfscreatesclass -K A,B Class2Copies

Créez une nouvelle classe de stockage nommée "Class3Copies". Les nouveaux chunks créés (-C) seront conservés n'importe où avec 2 copies (2*). Peu après leur création, ils seront conservés (-K) en 3 copies : la première copie sur un serveur de chunks avec l'étiquette "A", la deuxième copie sur un serveur de chunks avec l'étiquette "B" et la troisième sur n'importe quel serveur de chunks :

mfscreatesclass -C '2*' -K 'A,B,*' Class3Copies

Créez une nouvelle classe de stockage nommée "ClassEC4_1". Les chunks seront créés et conservés (-K) n'importe où en 2 copies (2*) pendant 24 heures à compter de la création du fichier. Plus tard, ils seront archivés (-A) au format EC4+1 sur n'importe quel serveur de chunks :

mfscreatesclass -K '2*' -A '@4+1' ClassEC4_1

Modifiez la classe de stockage "ClassEC4_1" pour archiver les chunks après 48 heures à compter de la modification (et non de la création) du fichier :

mfsmodifysclass -d 2d -o m ClassEC4_1

Modifiez la classe de stockage "Class3Copies" pour conserver les chunks sur d'autres serveurs de chunks (mode LAISSER-PASSER) si ceux avec les étiquettes "A" et "B" sont trop occupés (surchargés) :

mfsmodifysclass -m l Class3Copies
