NOM

openssl-ts - Commande d'Autorité de Cachet Horaire

SYNTAXE

openssl ts -help

openssl ts -query [-config fichier_config] [-data fichier_a_hasher] [-digest octets_digest] [-digest] [-tspolicy oid_objet] [-no_nonce] [-cert] [-in requete.tsq] [-out requete.tsq] [-text] [-rand fichiers] [-writerand fichier] [-provider nom] [-provider-path chemin] [-provparam [nom:]cle=valeur] [-propquery propq]

openssl ts -reply [-config fichier_config] [-section section_tsa] [-queryfile requete.tsq] [-passin source_mot_de_passe] [-signer cert_tsa.pem] [-inkey nom_fichier|uri] [-digest] [-chain fichier_certs.pem] [-tspolicy oid_objet] [-in reponse.tsr] [-token_in] [-out reponse.tsr] [-token_out] [-text] [-engine id] [-provider nom] [-provider-path chemin] [-provparam [nom:]cle=valeur] [-propquery propq]

openssl ts -verify [-data fichier_a_hasher] [-digest octets_digest] [-queryfile requete.tsq] [-in reponse.tsr] [-token_in] [-untrusted fichiers|uris] [-CAfile fichier] [-CApath rep] [-CAstore uri] [-allow_proxy_certs] [-attime horodatage] [-no_check_time] [-check_ss_sig] [-crl_check] [-crl_check_all] [-explicit_policy] [-extended_crl] [-ignore_critical] [-inhibit_any] [-inhibit_map] [-partial_chain] [-policy arg] [-policy_check] [-policy_print] [-purpose but] [-suiteB_128] [-suiteB_128_only] [-suiteB_192] [-trusted_first] [-no_alt_chains] [-use_deltas] [-auth_level num] [-verify_depth num] [-verify_email email] [-verify_hostname nom_hote] [-verify_ip ip] [-verify_name nom] [-x509_strict] [-issuer_checks] [-provider nom] [-provider-path chemin] [-provparam [nom:]cle=valeur] [-propquery propq]

DESCRIPTION

Cette commande est une application de base d'Autorité de Cachet Horaire (TSA) client et serveur, telle que spécifiée dans la RFC 3161 (Time-Stamp Protocol, TSP). Une TSA peut faire partie d'un déploiement PKI et son rôle est de fournir une preuve à long terme de l'existence d'une certaine donnée avant une heure donnée. Voici une brève description du protocole :

1.
Le client TSA calcule une valeur de hachage unidirectionnelle pour un fichier de données et envoie le hachage à la TSA.
2.
La TSA attache la date et l'heure actuelles à la valeur de hachage reçue, les signe et renvoie le jeton de cachet horaire au client. En créant ce jeton, la TSA certifie l'existence du fichier de données original au moment de la génération de la réponse.
3.
Le client TSA reçoit le jeton de cachet horaire et vérifie sa signature. Il vérifie également si le jeton contient la même valeur de hachage qu'il avait envoyée à la TSA.

Il existe une unité de données de protocole codée en DER définie pour transporter une requête de cachet horaire vers la TSA et une autre pour renvoyer la réponse de cachet horaire au client. Cette commande a trois fonctions principales : créer une requête de cachet horaire basée sur un fichier de données, créer une réponse de cachet horaire basée sur une requête, vérifier si une réponse correspond à une requête ou à un fichier de données particulier.

Il n'y a pas encore de support pour l'envoi automatique des requêtes/réponses via HTTP ou TCP, comme suggéré dans la RFC 3161. Les utilisateurs doivent envoyer les requêtes soit par ftp, soit par e-mail.

OPTIONS

-help
Affiche un message d'utilisation.
-query
Génère une requête TS. Pour plus de détails, voir "Génération de requête de cachet horaire".
-reply
Génère une réponse TS. Pour plus de détails, voir "Génération de réponse de cachet horaire".
-verify
Vérifie une réponse TS. Pour plus de détails, voir "Vérification de réponse de cachet horaire".

Génération de requête de cachet horaire

La commande -query peut être utilisée pour créer et afficher une requête de cachet horaire avec les options suivantes :

-config fichier_config
Le fichier de configuration à utiliser. Optionnel ; pour une description de la valeur par défaut, voir "RÉSUMÉ DES COMMANDES" dans openssl(1).
-data fichier_a_hasher
Le fichier de données pour lequel la requête de cachet horaire doit être créée. stdin est la valeur par défaut si aucun des paramètres -data ni -digest n'est spécifié. (Optionnel)
-digest octets_digest
Il est possible de spécifier explicitement l'empreinte du message sans le fichier de données. L'empreinte doit être spécifiée en format hexadécimal, deux caractères par octet, les octets éventuellement séparés par des deux-points (par ex., 1A:F6:01:... ou 1AF601...). Le nombre d'octets doit correspondre à l'algorithme de résumé de message utilisé. (Optionnel)
-digest
Le résumé de message à appliquer au fichier de données. Tout résumé pris en charge par la commande openssl-dgst(1) peut être utilisé. Le défaut est SHA-256. (Optionnel)
-tspolicy oid_objet
La politique que le client attend de la TSA pour créer le jeton de cachet horaire. La notation OID en pointillé ou les noms OID définis dans le fichier de configuration peuvent être utilisés. Si aucune politique n'est demandée, la TSA utilisera sa propre politique par défaut. (Optionnel)
-no_nonce
Aucun nonce n'est spécifié dans la requête si cette option est donnée. Sinon, un nonce pseudo-aléatoire de 64 bits est inclus dans la requête. Il est recommandé d'utiliser un nonce pour se protéger contre les attaques par rejeu. (Optionnel)
-cert
La TSA est censée inclure son certificat de signature dans la réponse. (Optionnel)
-in requete.tsq
Cette option spécifie une requête de cachet horaire précédemment créée en format DER qui sera affichée dans le fichier de sortie. Utile lorsque vous avez besoin d'examiner le contenu d'une requête dans un format lisible par l'homme. (Optionnel)
-out requete.tsq
Nom du fichier de sortie dans lequel la requête sera écrite. Le défaut est stdout. (Optionnel)
-text
Si cette option est spécifiée, la sortie est au format texte lisible par l'homme au lieu de DER. (Optionnel)
-rand fichiers, -writerand fichier
Voir "Options d'état aléatoire" dans openssl(1) pour les détails.

Génération de réponse de cachet horaire

Une réponse de cachet horaire (TimeStampResp) se compose d'un état de réponse et du jeton de cachet horaire lui-même (ContentInfo), si la génération du jeton a réussi. La commande -reply sert à créer une réponse de cachet horaire ou un jeton de cachet horaire basé sur une requête et à afficher la réponse/le jeton dans un format lisible par l'homme. Si -token_out n'est pas spécifié, la sortie est toujours une réponse de cachet horaire (TimeStampResp), sinon c'est un jeton de cachet horaire (ContentInfo).

-config fichier_config
Le fichier de configuration à utiliser. Optionnel ; pour une description de la valeur par défaut, voir "RÉSUMÉ DES COMMANDES" dans " dans openssl(1). Voir "OPTIONS DE FICHIER DE CONFIGURATION" pour les variables configurables.
-section tsa_section
Le nom de la section du fichier de configuration contenant les paramètres pour la génération de la réponse. Si non spécifié, la section TSA par défaut est utilisée, voir "OPTIONS DE FICHIER DE CONFIGURATION" pour les détails. (Optionnel)
-queryfile request.tsq
Le nom du fichier contenant une requête d'horodatage encodée en DER. (Optionnel)
-passin password_src
Spécifie la source du mot de passe pour la clé privée du TSA. Voir la description dans openssl(1). (Optionnel)
-signer tsa_cert.pem
Le certificat de signature du TSA au format PEM. Le certificat de signature du TSA doit avoir exactement un usage de clé étendu attribué : timeStamping. L'usage de clé étendu doit également être critique, sinon le certificat sera refusé. Remplace la variable signer_cert du fichier de configuration. (Optionnel)
-inkey filename|uri
La clé privée de signature du TSA au format PEM. Remplace l'option de fichier de configuration signer_key. (Optionnel)
-digest
Digest de signature à utiliser. Remplace l'option de fichier de configuration signer_digest. (Obligatoire sauf si spécifié dans le fichier de configuration)
-chain certs_file.pem
La collection de certificats au format PEM qui seront tous inclus dans la réponse en plus du certificat de signature si l'option -cert a été utilisée pour la requête. Ce fichier est censé contenir la chaîne de certificats pour le certificat de signature, de son émetteur vers le haut. La commande -reply ne construit pas de chaîne de certificats automatiquement. (Optionnel)
-tspolicy object_id
La politique par défaut à utiliser pour la réponse, sauf si le client exige explicitement une politique TSA particulière. L'OID peut être spécifié soit en notation décimale, soit avec son nom. Remplace l'option de fichier de configuration default_policy. (Optionnel)
-in response.tsr
Spécifie une réponse d'horodatage ou un jeton d'horodatage précédemment créé (si -token_in est également spécifié) au format DER qui sera écrit dans le fichier de sortie. Cette option ne nécessite pas de requête, elle est utile par exemple lorsque vous avez besoin d'examiner le contenu d'une réponse ou d'un jeton, ou que vous souhaitez extraire le jeton d'horodatage d'une réponse. Si l'entrée est un jeton et la sortie est une réponse d'horodatage, une information de statut 'granted' par défaut est ajoutée au jeton. (Optionnel)
-token_in
Ce drapeau peut être utilisé conjointement avec l'option -in et indique que l'entrée est un jeton d'horodatage encodé en DER (ContentInfo) au lieu d'une réponse d'horodatage (TimeStampResp). (Optionnel)
-out response.tsr
La réponse est écrite dans ce fichier. Le format et le contenu du fichier dépendent des autres options (voir -text, -token_out). La valeur par défaut est stdout. (Optionnel)
-token_out
La sortie est un jeton d'horodatage (ContentInfo) au lieu d'une réponse d'horodatage (TimeStampResp). (Optionnel)
-text
Si cette option est spécifiée, la sortie est au format texte lisible par l'homme au lieu de DER. (Optionnel)
-engine id
Voir "Options de Moteur" dans openssl(1). Cette option est obsolète.
-provider name
-provider-path path
-provparam [name:]key=value
-propquery propq
Voir "Options de Fournisseur" dans openssl(1), provider(7), et property(7).

Vérification de la réponse d'horodatage

La commande -verify sert à vérifier si une réponse d'horodatage ou un jeton d'horodatage est valide et correspond à une requête d'horodatage ou un fichier de données particulier. La commande -verify n'utilise pas le fichier de configuration.

-data file_to_hash
La réponse ou le jeton doit être vérifié par rapport à file_to_hash. Le fichier est haché avec l'algorithme de digest de message spécifié dans le jeton. Les options -digest et -queryfile ne doivent pas être spécifiées avec celle-ci. (Optionnel)
-digest digest_bytes
La réponse ou le jeton doit être vérifié par rapport au digest de message spécifié avec cette option. Le nombre d'octets doit correspondre à l'algorithme de digest de message spécifié dans le jeton. Les options -data et -queryfile ne doivent pas être spécifiées avec celle-ci. (Optionnel)
-queryfile request.tsq
La requête d'horodatage originale au format DER. Les options -data et -digest ne doivent pas être spécifiées avec celle-ci. (Optionnel)
-in response.tsr
La réponse d'horodatage qui doit être vérifiée au format DER. (Obligatoire)
-token_in
Ce drapeau peut être utilisé conjointement avec l'option -in et indique que l'entrée est un jeton d'horodatage encodé en DER (ContentInfo) au lieu d'une réponse d'horodatage (TimeStampResp). (Optionnel)
-untrusted files|uris
Un ensemble de certificats non approuvés supplémentaires qui pourraient être nécessaires lors de la construction de la chaîne de certificats pour le certificat de signature du TSA. Ils n'ont pas besoin de contenir le certificat de signature du TSA et les certificats d'autorité de certification intermédiaires tant que la réponse les inclut déjà. (Optionnel)

Plusieurs sources peuvent être fournies, séparées par des virgules et/ou des espaces. Chaque fichier peut contenir plusieurs certificats.

-CAfile file, -CApath dir, -CAstore uri
Voir "Options de Certificat de Confiance" dans openssl-verification-options(1) pour les détails. Au moins l'une des options -CAfile, -CApath ou -CAstore doit être spécifiée.
-allow_proxy_certs, -attime, -no_check_time, -check_ss_sig, -crl_check, -crl_check_all, -explicit_policy, -extended_crl, -ignore_critical, -inhibit_any, -inhibit_map, -no_alt_chains, -partial_chain, -policy, -policy_check, -policy_print, -purpose, -suiteB_128, -suiteB_128_only, -suiteB_192, -trusted_first, -use_deltas, -auth_level, -verify_depth, -verify_email, -verify_hostname, -verify_ip, -verify_name, -x509_strict -issuer_checks
Définit diverses options de vérification de la chaîne de certificats. Voir "Options de Vérification" dans openssl-verification-options(1) pour les détails.

Toute erreur de vérification entraînera la sortie de la commande.

OPTIONS DE FICHIER DE CONFIGURATION

Les commandes -query et -reply utilisent un fichier de configuration. Voir config(5) pour une description générale de la syntaxe du fichier de configuration. La commande -query utilise uniquement la section des noms OID symboliques et peut fonctionner sans elle. Cependant, la commande -reply a besoin du fichier de configuration pour fonctionner.

Lorsqu'il existe un interrupteur de ligne de commande équivalent à une variable, l'interrupteur remplace toujours les paramètres du fichier de configuration.

section tsa, default_tsa
C'est la section principale et elle spécifie le nom d'une autre section qui contient toutes les options pour la commande -reply. Cette section par défaut peut être remplacée par l'interrupteur de ligne de commande -section. (Optionnel)
oid_file
Ceci spécifie un fichier contenant des OBJECT IDENTIFIERS supplémentaires. Chaque ligne du fichier doit se composer de la forme numérique de l'identifiant d'objet, suivie d'espaces, puis du nom court, suivie d'espaces, et enfin du nom long. (Optionnel)
oid_section
Ceci spécifie une section du fichier de configuration contenant des identifiants d'objet supplémentaires. Chaque ligne doit se composer du nom court de l'identifiant d'objet suivi de = et de la forme numérique. Les noms courts et longs sont les mêmes lorsque cette option est utilisée. (Optionnel)
RANDFILE
Au démarrage, le fichier spécifié est chargé dans le générateur de nombres aléatoires, et à la sortie, 256 octets y seront écrits. (Note : l'utilisation d'un RANDFILE n'est plus nécessaire, voir la section "HISTORIQUE".
serial
Le nom du fichier contenant le numéro de série hexadécimal de la dernière réponse d'horodatage créée. Ce numéro est incrémenté de 1 pour chaque réponse. Si le fichier n'existe pas au moment de la génération de la réponse, un nouveau fichier est créé avec le numéro de série 1. (Obligatoire)
crypto_device
Spécifie le moteur OpenSSL qui sera défini comme par défaut pour tous les algorithmes disponibles. La valeur par défaut est intégrée, vous pouvez spécifier tout autre moteur pris en charge

NAME

openssl-ts - Time Stamp Protocol (TSP) implementation

SYNOPSIS

openssl ts [-engine id] [-config configfile] [-query | -reply | -verify | -list] [-in file] [-out file] [-text] [-port port] [-engine_verify] [-crl_check] [-crl_check_all] [-token_in] [-token_out] [-cert_in] [-cert_out] [-serial] [-sha1 | -sha256 | -sha384 | -sha512] [-data file] [-digest digest] [-sigopt opt:value] [-MMD value] [-nonce] [-no_nonce] [-tspolicy oid] [-policy file] [-cert] [-digest_in file] [-fingerprint] [-issuer] [-pubkey] [-serial_in file] [-subj subj] [-chain file] [-CAfile file] [-CApath dir] [-untrusted file] [-partial_chain] [-policy_check] [-strict] [-quiet] [-rand file] [-engine_rand] [-purpose purpose] [-verify_depth depth] [-verify_name] [-verify_exp] [-verify_root_end_time] [-attime time] [-check_ss_cert]

DESCRIPTION

The openssl ts utility implements the Time Stamp Protocol (TSP) as described in RFC 3161. It can be used to generate timestamping requests, process them and generate TSA (Time Stamping Authority) responses, and verify timestamping requests and responses.

The command line options are divided into several groups:

Query / Request Generation
The following options are used to generate a timestamping request. This is an ASN.1 structure that contains the message hash, nonce (if requested), policy (if requested), etc. The request is sent to a TSA, which will return a signed timestamping response.
Reply / Response Generation
The following options are used to generate a TSA response. A TSA response is a signed timestamping reply, which contains the timestamp token. The timestamp token contains the message hash, the time the token was created, and other information.
Verification
The following options are used to verify a TSA request and/or response.

Configuration File Options

The openssl ts utility can be configured using the standard OpenSSL configuration file mechanism. The default configuration file is specified by the OPENSSL_CONF environment variable, or if that is not set, it defaults to openssl.cnf in the OpenSSL installation directory. The configuration entries for the ts command are located under the [ts] section.

default_tsa
The name of the default TSA to use. If this option is not specified, the first TSA defined in the configuration file is used. (Optional)
tsa
This is a sub-section for a specific TSA configuration. The section name is defined by the default_tsa option or the first TSA found in the configuration file. Multiple TSA sections can be defined in the configuration file. Each section must contain the following parameters:

TSA Section Parameters

ssid
The TSA identifier. This is an OID string. (Mandatory)
url
The URL of the TSA. (Optional)
provider
The cryptographic provider to use for signing, etc. The default is OpenSSL's internal provider. Use this to specify other providers, e.g. PKCS#11 providers. (Optional)
digest
The message digest algorithm to use for signing. The default is sha256. (Optional)
chain
A file containing a set of PEM encoded certificates that need to be included in the response. The same as the -chain command line option. (Optional)
certs
A file containing a set of PEM encoded certificates that need to be included in the response. The same as the -chain command line option. (Optional)
private_key
The private key of the TSA in PEM format. The same as the -inkey command line option. (Optional)
certificate
The TSA signing certificate in PEM format. The same as the -signer command line option. (Optional)
digest_identifier
The OID of the digest algorithm to use. (Optional)
policy
The TSA policy OID. (Optional)
engine_<id>
This option is used to specify a specific engine to be used for cryptographic operations, e.g. for signing by OpenSSL (e.g. use chil for the NCipher HSM). (Optional)
signer_cert
TSA signing certificate in PEM format. The same as the -signer command line option. (Optional)
certs
A file containing a set of PEM encoded certificates that need to be included in the response. The same as the -chain command line option. (Optional)
signer_key
The private key of the TSA in PEM format. The same as the -inkey command line option. (Optional)
signer_digest
Signing digest to use. The same as the -digest command line option. (Mandatory unless specified on the command line)
default_policy
The default policy to use when the request does not mandate any policy. The same as the -tspolicy command line option. (Optional)
other_policies
Comma separated list of policies that are also acceptable by the TSA and used only if the request explicitly specifies one of them. (Optional)
digests
The list of message digest algorithms that the TSA accepts. At least one algorithm must be specified. (Mandatory)
accuracy
The accuracy of the time source of the TSA in seconds, milliseconds and microseconds. E.g. secs:1, millisecs:500, microsecs:100. If any of the components is missing zero is assumed for that field. (Optional)
clock_precision_digits
Specifies the maximum number of digits, which represent the fraction of seconds, that need to be included in the time field. The trailing zeros must be removed from the time, so there might actually be fewer digits, or no fraction of seconds at all. Supported only on UNIX platforms. The maximum value is 6, default is 0. (Optional)
ordering
If this option is yes the responses generated by this TSA can always be ordered, even if the time difference between two responses is less than the sum of their accuracies. Default is no. (Optional)
tsa_name
Set this option to yes if the subject name of the TSA must be included in the TSA name field of the response. Default is no. (Optional)
ess_cert_id_chain
The SignedData objects created by the TSA always contain the certificate identifier of the signing certificate in a signed attribute (see RFC 2634, Enhanced Security Services). If this variable is set to no, only this signing certificate identifier is included in the SigningCertificate signed attribute. If this variable is set to yes and the certs variable or the -chain option is specified then the certificate identifiers of the chain will also be included, where the -chain option overrides the certs variable. Default is no. (Optional)
ess_cert_id_alg
This option specifies the hash function to be used to calculate the TSA's public key certificate identifier. Default is sha256. (Optional)

EXAMPLES

All the examples below presume that OPENSSL_CONF is set to a proper configuration file, e.g. the example configuration file openssl/apps/openssl.cnf will do.

Timestamp Request

To create a timestamp request for design1.txt with SHA-256 digest, without nonce and policy, and without requirement for a certificate in the response:

openssl ts -query -data design1.txt -no_nonce \
      -out design1.tsq

To create a similar timestamp request with specifying the message imprint explicitly:

openssl ts -query -digest b7e5d3f93198b38379852f2c04e78d73abdd0f4b \
       -no_nonce -out design1.tsq

To print the content of the previous request in human readable format:

openssl ts -query -in design1.tsq -text

To create a timestamp request which includes the SHA-512 digest of design2.txt, requests the signer certificate and nonce, and specifies a policy id (assuming the tsa_policy1 name is defined in the OID section of the config file):

openssl ts -query -data design2.txt -sha512 \
      -tspolicy tsa_policy1 -cert -out design2.tsq

Timestamp Response

Before generating a response a signing certificate must be created for the TSA that contains the timeStamping critical extended key usage extension without any other key usage extensions. You can add this line to the user certificate section of the config file to generate a proper certificate;

extendedKeyUsage = critical,timeStamping

See openssl-req(1), openssl-ca(1), and openssl-x509(1) for instructions. The examples below assume that cacert.pem contains the certificate of the CA, tsacert.pem is the signing certificate issued by cacert.pem and tsakey.pem is the private key of the TSA.

To create a timestamp response for a request:

openssl ts -reply -queryfile design1.tsq -inkey tsakey.pem \
      -signer tsacert.pem -out design1.tsr

If you want to use the settings in the config file you could just write:

openssl ts -reply -queryfile design1.tsq -out design1.tsr

To print a timestamp reply to stdout in human readable format:

openssl ts -reply -in design1.tsr -text

To create a timestamp token instead of timestamp response:

openssl ts -reply -queryfile design1.tsq -out design1_token.der -token_out

To print a timestamp token to stdout in human readable format:

openssl ts -reply -in design1_token.der -token_in -text -token_out

To extract the timestamp token from a response:

openssl ts -reply -in design1.tsr -out design1_token.der -token_out

To add 'granted' status info to a timestamp token thereby creating a valid response:

openssl ts -reply -in design1_token.der -token_in -out design1.tsr

Timestamp Verification

To verify a timestamp reply against a request:

openssl ts -verify -queryfile design1.tsq -in design1.tsr \
      -CAfile cacert.pem -untrusted tsacert.pem

To verify a timestamp reply that includes the certificate chain:

openssl ts -verify -queryfile design2.tsq -in design2.tsr \
      -CAfile cacert.pem

To verify a timestamp token against the original data file:

openssl ts -verify -data design2.txt -in design2.tsr \
      -CAfile cacert.pem

To verify a timestamp token against a message imprint:

openssl ts -verify -digest b7e5d3f93198b38379852f2c04e78d73abdd0f4b \
       -in design2.tsr -CAfile cacert.pem

You could also look at the 'test' directory for more examples.

BUGS

  • No support for timestamps over SMTP, though it is quite easy to implement an automatic e-mail based TSA with procmail(1) and perl(1). HTTP server support is provided in the form of a separate apache module. HTTP client support is provided by tsget(1). Pure TCP/IP protocol is not supported.
  • The file containing the last serial number of the TSA is not locked when being read or written. This is a problem if more than one instance of openssl(1) is trying to create a timestamp response at the same time. This is not an issue when using the apache server module, it does proper locking.
  • Look for the FIXME word in the source files.
  • The source code should really be reviewed by somebody else, too.
  • More testing is needed, I have done only some basic tests (see test/testtsa).

HISTORY

OpenSSL 1.1.1 introduced a new random generator (CSPRNG) with an improved seeding mechanism. The new seeding mechanism makes it unnecessary to define a RANDFILE for saving and restoring randomness. This option is retained mainly for compatibility reasons.

The -engine option was deprecated in OpenSSL 3.0.
