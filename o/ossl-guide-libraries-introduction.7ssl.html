NOM

ossl-guide-libraries-introduction - Guide OpenSSL : Introduction aux bibliothèques OpenSSL

INTRODUCTION

OpenSSL fournit deux bibliothèques qui peuvent être utilisées par les applications, connues sous le nom de "libcrypto" et "libssl".

La bibliothèque "libcrypto" fournit des API pour la cryptographie à usage général telles que le chiffrement, les signatures numériques, les fonctions de hachage, etc. Elle fournit également des API de support pour les normes liées à la cryptographie, par exemple pour lire et écrire des certificats numériques (également connus sous le nom de certificats X.509). Enfin, elle fournit diverses API de support supplémentaires qui ne sont pas directement liées à la cryptographie mais qui sont néanmoins utiles et dépendues par d'autres API. Par exemple, les fonctions "BIO" offrent des capacités pour abstraire les E/S, par exemple via un fichier ou sur un réseau.

La bibliothèque "libssl" fournit des fonctions pour effectuer des communications sécurisées entre deux pairs sur un réseau. Plus important encore, elle implémente le support des normes SSL/TLS, DTLS et QUIC.

La bibliothèque "libssl" dépend et utilise plusieurs des capacités fournies par "libcrypto". Toute application liée à "libssl" sera également liée à "libcrypto", et la plupart des applications qui le font utiliseront directement les fonctions API fournies par les deux bibliothèques.

Des applications peuvent être écrites qui utilisent uniquement les capacités de "libcrypto" et ne sont pas liées du tout à "libssl".

FOURNISSEURS

En plus des deux bibliothèques principales, OpenSSL est également livré avec un ensemble de fournisseurs.

Un fournisseur dans OpenSSL est un composant qui rassemble des implémentations d'algorithmes (par exemple, une implémentation de l'algorithme de chiffrement symétrique AES). Pour utiliser un algorithme, vous devez avoir au moins un fournisseur chargé qui contient une implémentation de celui-ci. OpenSSL est livré avec plusieurs fournisseurs et ils peuvent également être obtenus auprès de tiers.

Les fournisseurs peuvent être "intégrés" ou sous la forme d'un fichier de module chargeable séparé (généralement un se terminant par ".so" ou ".dll" selon la plateforme). Un fournisseur intégré est soit déjà présent dans "libcrypto", soit celui que l'application a fourni elle-même directement. Des tiers peuvent également fournir des fournisseurs sous forme de modules chargeables.

Si vous ne chargez pas un fournisseur explicitement (soit dans le code du programme, soit via la configuration), le fournisseur "par défaut" intégré à OpenSSL sera automatiquement chargé.

Voir "OPENSSL PROVIDERS" ci-dessous pour une description des fournisseurs qu'OpenSSL fournit lui-même.

Le chargement et le déchargement des fournisseurs sont des opérations assez coûteuses. Ils sont normalement effectués une seule fois, tôt dans le cycle de vie de l'application, et ces fournisseurs restent chargés pendant toute la durée d'exécution de l'application.

CONTEXTES DE BIBLIOTHÈQUE

De nombreuses fonctions API OpenSSL utilisent un contexte de bibliothèque. Un contexte de bibliothèque peut être considéré comme une "portée" dans laquelle les options de configuration prennent effet. Lorsqu'un fournisseur est chargé, il n'est chargé que dans la portée d'un contexte de bibliothèque donné. De cette manière, il est possible pour différentes parties d'une application complexe d'utiliser chacune un contexte de bibliothèque différent et d'avoir des fournisseurs différents chargés avec des paramètres de configuration différents.

Si une application ne crée pas explicitement un contexte de bibliothèque, le contexte de bibliothèque "par défaut" sera utilisé.

Les contextes de bibliothèque sont représentés par le type OSSL_LIB_CTX. De nombreuses fonctions API OpenSSL prennent un contexte de bibliothèque comme paramètre. Les applications peuvent toujours passer NULL pour ce paramètre afin d'utiliser simplement le contexte de bibliothèque par défaut.

Le contexte de bibliothèque par défaut est automatiquement créé la première fois qu'il est nécessaire. Cela chargera automatiquement tout fichier de configuration disponible et initialisera OpenSSL pour utilisation. Contrairement aux versions antérieures d'OpenSSL (avant 1.1.0), aucune étape d'initialisation explicite n'a besoin d'être effectuée.

De même, lorsque l'application se termine, le contexte de bibliothèque par défaut est automatiquement détruit. Aucune étape de désinitialisation explicite n'a besoin d'être effectuée.

Voir OSSL_LIB_CTX(3) pour plus d'informations sur les contextes de bibliothèque. Voir également "ALGORITHM FETCHING" dans ossl-guide-libcrypto-introduction(7).

CHAÎNES DE REQUÊTE DE PROPRIÉTÉS

Dans certains cas, les fournisseurs disponibles peuvent signifier que plus d'une implémentation de n'importe quel algorithme donné pourrait être disponible. Par exemple, le fournisseur FIPS d'OpenSSL fournit des implémentations alternatives de nombre des mêmes algorithmes qui sont disponibles dans le fournisseur par défaut d'OpenSSL.

Le processus de sélection d'une implémentation d'algorithme est connu sous le nom de "fetching" (récupération). Lorsque OpenSSL récupère un algorithme à utiliser, il est possible de spécifier une "chaîne de requête de propriétés" pour guider le processus de sélection. Par exemple, une chaîne de requête de propriétés de "provider=default" pourrait être utilisée pour forcer la sélection à ne considérer que les implémentations d'algorithmes dans le fournisseur par défaut.

Les chaînes de requête de propriétés peuvent être spécifiées explicitement comme argument d'une fonction. Il est également possible de spécifier une chaîne de requête de propriétés par défaut pour l'ensemble du contexte de bibliothèque en utilisant les fonctions EVP_set_default_properties(3) ou EVP_default_properties_enable_fips(3). Lorsque des propriétés par défaut et des propriétés spécifiques à la fonction sont spécifiées, elles sont combinées. Les propriétés spécifiques à la fonction remplaceront les propriétés par défaut en cas de conflit.

Voir "ALGORITHM FETCHING" dans ossl-guide-libcrypto-introduction(7) pour plus d'informations sur la récupération. Voir property(7) pour plus d'informations sur les propriétés.

APPLICATIONS MULTITHREADÉES

Tant qu'OpenSSL a été compilé avec le support des threads (cas par défaut sur la plupart des plateformes), la plupart des *fonctions* OpenSSL sont thread-safe dans le sens où il est sûr d'appeler la même fonction à partir de plusieurs threads en même temps. Cependant, la plupart des *structures de données* OpenSSL ne sont pas thread-safe. Par exemple, les fonctions BIO_write(3) et BIO_read(3) sont thread-safe. Cependant, il ne serait pas thread-safe d'appeler BIO_write() depuis un thread tout en appelant BIO_read() depuis un autre, où les deux fonctions sont passées le même objet BIO, car toutes deux peuvent tenter d'apporter des modifications au même objet BIO.

Il existe des exceptions à ces règles. Un petit nombre de fonctions ne sont pas thread-safe du tout. Lorsque c'est le cas, cette restriction doit être notée dans la documentation de la fonction. De même, certaines structures de données peuvent être partiellement ou totalement thread-safe. Par exemple, il est toujours sûr d'utiliser un OSSL_LIB_CTX dans plusieurs threads.

Voir openssl-threads(7) pour une discussion plus détaillée sur le support du threading d'OpenSSL.

GESTION DES ERREURS

La plupart des fonctions OpenSSL fourniront une valeur de retour indiquant si la fonction a réussi ou non. Il est considéré comme une bonne pratique de toujours vérifier la valeur de retour des fonctions OpenSSL (lorsqu'elle est disponible).

La plupart des fonctions qui retournent une valeur de pointeur retourneront NULL en cas d'échec.

La plupart des fonctions qui retournent une valeur entière retourneront un entier positif pour le succès. Certaines de ces fonctions retourneront 0 pour indiquer un échec. D'autres peuvent retourner 0 ou une valeur négative pour un échec.

Certaines fonctions ne peuvent pas échouer et ont un type de retour void. Il existe également un petit nombre de fonctions qui ne sont pas conformes aux conventions ci-dessus (par exemple, elles peuvent retourner 0 pour indiquer le succès).

FOURNISSEURS OPENSSL

OpenSSL est livré avec un ensemble de fournisseurs.

Les algorithmes disponibles dans chacun de ces fournisseurs peuvent varier en raison des options de configuration au moment de la compilation. La commande openssl-list(1) peut être utilisée pour lister les algorithmes actuellement disponibles.

Les noms des algorithmes affichés par openssl-list(1) peuvent être utilisés comme identifiant d'algorithme pour la fonction de récupération appropriée. Voir également les pages de manuel spécifiques aux fournisseurs liées ci-dessous pour plus de détails sur l'utilisation des algorithmes disponibles dans chacun des fournisseurs.

En plus des fournisseurs OpenSSL, des tiers peuvent également implémenter des fournisseurs. Pour plus d'informations sur la rédaction d'un fournisseur, voir provider(7).

Fournisseur par défaut

Le fournisseur par défaut est intégré à la bibliothèque libcrypto et contient toutes les implémentations d'algorithmes les plus couramment utilisées. S'il est nécessaire (si d'autres fournisseurs sont chargés et proposent des implémentations des mêmes algorithmes), la chaîne de requête de propriétés « provider=default » peut être utilisée comme critère de recherche pour ces implémentations. Le fournisseur par défaut inclut toutes les fonctionnalités du fournisseur de base ci-dessous.

Si vous ne chargez aucun fournisseur, le fournisseur « default » sera automatiquement chargé. Si vous chargez explicitement un fournisseur, le fournisseur « default » devrait également être chargé explicitement s'il est requis.

Voir OSSL_PROVIDER-default(7).

Fournisseur de base

Le fournisseur de base est intégré à la bibliothèque libcrypto et contient des implémentations d'algorithmes pour le codage et le décodage des clés OpenSSL. S'il est nécessaire (si d'autres fournisseurs sont chargés et proposent des implémentations des mêmes algorithmes), la chaîne de requête de propriétés « provider=base » peut être utilisée comme critère de recherche pour ces implémentations. Certaines implémentations d'algorithmes de codage et de décodage ne sont pas elles-mêmes des implémentations d'algorithmes FIPS, mais prennent en charge les algorithmes du fournisseur FIPS et sont autorisées pour une utilisation en « mode FIPS ». La chaîne de requête de propriétés « fips=yes » peut être utilisée pour sélectionner de tels algorithmes.

Voir OSSL_PROVIDER-base(7).

Fournisseur FIPS

Le fournisseur FIPS est un module chargeable dynamiquement et doit par conséquent être chargé explicitement, soit dans le code, soit via la configuration OpenSSL (voir config(5)). Il contient des implémentations d'algorithmes qui ont été validées conformément aux normes FIPS. S'il est nécessaire (si d'autres fournisseurs sont chargés et proposent des implémentations des mêmes algorithmes), la chaîne de requête de propriétés « provider=fips » peut être utilisée comme critère de recherche pour ces implémentations. Toutes les implémentations d'algorithmes approuvées dans le fournisseur FIPS peuvent également être sélectionnées avec la propriété « fips=yes ». Le fournisseur FIPS peut également contenir des implémentations d'algorithmes non approuvés et celles-ci peuvent être sélectionnées avec la propriété « fips=no ».

Généralement, le « Fournisseur de base » devra également être chargé car le fournisseur FIPS ne prend pas en charge le codage ou le décodage des clés.

Voir OSSL_PROVIDER-FIPS(7) et fips_module(7).

Fournisseur hérité

Le fournisseur hérité est un module chargeable dynamiquement et doit par conséquent être chargé explicitement, soit dans le code, soit via la configuration OpenSSL (voir config(5)). Il contient des implémentations d'algorithmes considérés comme peu sûrs, ou qui ne sont plus couramment utilisés, tels que MD2 ou RC4. S'il est nécessaire (si d'autres fournisseurs sont chargés et proposent des implémentations des mêmes algorithmes), la propriété « provider=legacy » peut être utilisée comme critère de recherche pour ces implémentations.

Voir OSSL_PROVIDER-legacy(7).

Fournisseur nul

Le fournisseur nul est intégré à la bibliothèque libcrypto. Il ne contient aucun algorithme. Lors de la récupération d'algorithmes, le fournisseur par défaut sera automatiquement chargé si aucun autre fournisseur n'a été explicitement chargé. Pour empêcher cela, vous pouvez charger explicitement le fournisseur nul.

Vous pouvez l'utiliser si vous créez votre propre contexte de bibliothèque et que vous souhaitez vous assurer que tous les appels API ont correctement passé le contexte de bibliothèque créé et n'utilisent pas accidentellement le contexte de bibliothèque par défaut. Chargez le fournisseur nul dans le contexte de bibliothèque par défaut afin que le contexte de bibliothèque par défaut n'ait aucune implémentation d'algorithme disponible.

Voir OSSL_PROVIDER-null(7).

CONFIGURATION

Par défaut, OpenSSL chargera un fichier de configuration lors de sa première utilisation. Cela configurera divers paramètres de configuration dans le contexte de bibliothèque par défaut. Les applications qui créent leurs propres contextes de bibliothèque peuvent facultativement les configurer avec un fichier de configuration en utilisant la fonction OSSL_LIB_CTX_load_config(3).

Le fichier de configuration peut être utilisé pour charger automatiquement des fournisseurs et définir des chaînes de requête de propriétés par défaut.

Pour plus d'informations sur le format du fichier de configuration OpenSSL, voir config(5).

CONVENTIONS DE BIBLIOTHÈQUE

De nombreuses fonctions OpenSSL qui « obtiennent » ou « définissent » une valeur suivent une convention de nommage utilisant les nombres 0 et 1, c'est-à-dire « get0 », « get1 », « set0 » et « set1 ». Cela peut également s'appliquer à certaines fonctions qui « ajoutent » une valeur à un ensemble existant, c'est-à-dire « add0 » et « add1 ».

Par exemple, les fonctions :

int X509_CRL_add0_revoked(X509_CRL *crl, X509_REVOKED *rev);
int X509_add1_trust_object(X509 *x, const ASN1_OBJECT *obj);

Dans la version 0, la propriété de l'objet est transmise à (pour un ajout ou une définition) ou conservée par (pour une obtention) l'objet parent. Par exemple, après avoir appelé la fonction X509_CRL_add0_revoked() ci-dessus, la propriété de l'objet rev est transmise à l'objet crl. Par conséquent, après avoir appelé cette fonction, rev ne doit pas être libéré directement. Il sera libéré implicitement lorsque crl sera libéré.

Dans la version 1, la propriété de l'objet n'est ni transmise ni conservée par l'objet parent. Au lieu de cela, une copie ou une « référence supplémentaire » de l'objet est effectuée. Ainsi, après avoir appelé la fonction X509_add1_trust_object() ci-dessus, l'application sera toujours responsable de libérer la valeur obj le cas échéant.

De nombreuses fonctions OpenSSL respectent une convention de nommage de la forme NOMCLASSE_nom_fonction(). Dans cette convention de nommage, le NOMCLASSE est le nom d'une structure de données OpenSSL (indiqué en majuscules) sur laquelle la fonction opère principalement. La partie « nom_fonction » du nom est généralement en minuscules et indique le but de la fonction.

APPLICATIONS DE DÉMONSTRATION

OpenSSL est distribué avec un ensemble d'applications de démonstration qui fournissent quelques exemples sur la façon d'utiliser les différentes fonctions d'API. Pour les consulter, téléchargez le code source d'OpenSSL depuis le site Web d'OpenSSL (https://www.openssl.org/source/). Extrayez le fichier .tar.gz téléchargé pour la version d'OpenSSL que vous utilisez et examinez les différents fichiers dans le sous-répertoire demos.

Les Makefiles dans les sous-répertoires donnent des instructions sur la façon de compiler et d'exécuter les applications de démonstration.

NAME

ossl-guide-libraries-introduction - OpenSSL libraries introduction

INTRODUCTION

The OpenSSL library is a robust, commercial-grade, and fully featured toolkit for the Transport Layer Security (TLS) and Secure Sockets Layer (SSL) protocols. It is also a general-purpose cryptography library.

This document provides a high-level overview of the OpenSSL library and its components. It is intended for developers who want to understand how to use the OpenSSL library in their applications.

PROVIDERS

OpenSSL supports the concept of providers, which are dynamic modules that implement cryptographic algorithms. This allows for greater flexibility and extensibility, as different providers can be loaded and unloaded as needed.

Common providers include:

  • default: The default provider, which includes a wide range of common cryptographic algorithms.
  • legacy: A provider that includes older, less secure algorithms that may still be needed for compatibility with older systems.
  • ...: Other providers may be available depending on the OpenSSL build and system configuration.

Providers are typically configured in the openssl.cnf file.

LIBRARY CONTEXTS

The OpenSSL library uses the concept of a "library context" (OSSL_LIB_CTX) to manage configuration, providers, and other global settings. When you initialize OpenSSL, you are usually working with a default library context. You can create and manage custom library contexts to isolate configurations or to use specific providers.

PROPERTY QUERY STRINGS

When requesting an algorithm from a provider, you can specify a property query string. This allows you to select algorithms based on their properties, such as their performance characteristics, security level, or specific features.

For example, you might query for an algorithm with a specific property like "provider=default" or "digest=sha256,security=high".

MULTI-THREADED APPLICATIONS

OpenSSL is designed to be thread-safe. However, you need to be mindful of certain aspects when using it in multi-threaded applications:

  • Use locking callbacks: For older versions of OpenSSL (prior to 1.1.0), you needed to set up locking callbacks to handle internal data structures. Modern versions handle this internally.
  • Avoid global state modification: If you are using custom configurations or providers, ensure that modifications to library contexts are done in a thread-safe manner.

ERROR HANDLING

OpenSSL uses a combination of return values and an error queue to report errors. Functions typically return a value indicating success or failure. If a failure occurs, you can retrieve detailed error information from the error queue using functions like ERR_get_error() and ERR_error_string().

OPENSSL PROVIDERS

The OpenSSL 3.0 release introduced a new provider framework. Providers are dynamically loadable modules that implement cryptographic algorithms and other functionalities. This architecture separates the core OpenSSL library from the specific implementations of algorithms, allowing for more flexibility and easier updates.

You can load and unload providers, and choose which provider to use for specific operations based on properties.

CONFIGURATION

OpenSSL's behavior can be configured using configuration files, typically named openssl.cnf. These files allow you to set default values, specify provider loading paths, define certificate policies, and more.

You can specify a configuration file explicitly when initializing OpenSSL or rely on the default locations.

LIBRARY CONVENTIONS

OpenSSL APIs generally follow a C-style convention. Functions often return integers (0 for success, non-zero for failure, or vice versa depending on the function) or pointers. Error details are usually retrieved from an error queue.

Data structures are often passed by pointer, and functions may modify them or return new ones.

DEMO APPLICATIONS

The OpenSSL source distribution includes a set of demonstration applications (often found in the apps/ directory). These applications showcase how to use various OpenSSL functionalities and can serve as examples for your own development.

FURTHER READING

For more in-depth information, refer to:

  • The official OpenSSL documentation: https://www.openssl.org/docs/
  • The OpenSSL source code and header files.
  • The man pages for specific OpenSSL commands and library functions.
