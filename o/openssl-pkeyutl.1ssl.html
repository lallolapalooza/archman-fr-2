NOM

openssl-pkeyutl - commande de clé publique/privée

SYNOPSIS

openssl pkeyutl [-help] [-in fichier] [-rawin] [-digest algorithme] [-out fichier] [-secret fichier] [-sigfile fichier] [-inkey nomfichier|uri] [-keyform DER|PEM|P12|ENGINE] [-passin arg] [-pubin] [-certin] [-rev] [-sign] [-verify] [-verifyrecover] [-encrypt] [-decrypt] [-derive] [-peerkey fichier] [-peerform DER|PEM|P12|ENGINE] [-encap] [-decap] [-kdf algorithme] [-kdflen longueur] [-kemop mode] [-pkeyopt opt:valeur] [-pkeyopt_passin opt[:passarg]] [-hexdump] [-asn1parse] [-engine id] [-engine_impl] [-rand fichiers] [-writerand fichier] [-provider nom] [-provider-path chemin] [-provparam [nom:]clé=valeur] [-propquery propq] [-config fichierconfig]

DESCRIPTION

Cette commande peut être utilisée pour effectuer des opérations de bas niveau sur des clés asymétriques (publiques ou privées) en utilisant tout algorithme supporté.

Par défaut, l'opération de signature (voir l'option -sign) est supposée.

OPTIONS

-help
Affiche un message d'utilisation.
-in nomfichier
Ce paramètre spécifie le nom du fichier d'entrée à lire ou l'entrée standard si cette option n'est pas spécifiée.
-rawin
Indique que les données d'entrée de signature ou de vérification sont des données brutes, qui ne sont pas hachées par un quelconque algorithme de résumé de message. Sauf avec EdDSA, l'utilisateur peut spécifier un algorithme de résumé en utilisant l'option -digest. Pour les algorithmes de signature comme RSA, DSA et ECDSA, l'algorithme de résumé par défaut est SHA256. Pour SM2, c'est SM3.

Cette option ne peut être utilisée qu'avec -sign et -verify. Pour EdDSA (les algorithmes Ed25519 et Ed448), cette option est implicite depuis OpenSSL 3.5, et obligatoire dans les versions antérieures.

L'option -digest implique -rawin depuis OpenSSL 3.5.

-digest algorithme
Cette option ne peut être utilisée qu'avec -sign et -verify. Elle spécifie l'algorithme de résumé qui est utilisé pour hacher les données d'entrée avant de les signer ou de les vérifier avec la clé d'entrée. Cette option peut être omise si l'algorithme de signature ne nécessite pas de prétraiter l'entrée via une fonction de hachage pluggable avant la signature (par exemple, EdDSA). Si cette option est omise mais que l'algorithme de signature en requiert une et que l'option -rawin est fournie, une valeur par défaut sera utilisée (voir -rawin pour les détails). Si cette option est présente, alors l'option -rawin est implicite depuis OpenSSL 3.5, et obligatoire dans les versions antérieures.

À l'heure actuelle, HashEdDSA (la variante ph ou "prehash" d'EdDSA) n'est pas supportée, donc l'option -digest ne peut pas être utilisée avec EdDSA.

-out nomfichier
Spécifie le nom du fichier de sortie où écrire, ou la sortie standard par défaut.
-secret nomfichier
Spécifie le nom du fichier de sortie du secret partagé lors de l'encapsulation via l'option -encap ou de la décapsulation via l'option -decap. L'option -encap produit également une sortie séparée (publique) de chiffrement qui est par défaut écrite dans la sortie standard, mais étant des données binaires non textuelles, elle est généralement également redirigée vers un fichier sélectionné via l'option -out.
-sigfile fichier
Fichier de signature, requis et autorisé pour les opérations -verify uniquement.
-inkey nomfichier|uri
La clé d'entrée, par défaut il devrait s'agir d'une clé privée.
-keyform DER|PEM|P12|ENGINE
Le format de la clé ; non spécifié par défaut. Voir openssl-format-options(1) pour plus de détails.
-passin arg
La source du mot de passe de la clé d'entrée. Pour plus d'informations sur le format de arg, voir openssl-passphrase-options(1).
-pubin
Par défaut, une clé privée est lue à partir de l'entrée de clé. Avec cette option, une clé publique est lue à la place. Si l'entrée ne contient pas de clé publique mais une clé privée, sa partie publique est utilisée.
-certin
L'entrée est un certificat contenant une clé publique.
-rev
Inverse l'ordre du tampon d'entrée. Ceci est utile pour certaines bibliothèques (comme CryptoAPI) qui représentent le tampon au format little-endian. Cela ne peut pas être utilisé en conjonction avec -rawin.
-sign
Signe les données d'entrée et produit le résultat signé. Cela nécessite une clé privée. L'utilisation d'une opération de résumé de message avec ceci est recommandée, lorsque applicable, voir les options -rawin et -digest pour les détails. Sinon, les données d'entrée fournies avec l'option -in sont supposées être déjà un résumé, mais cela peut alors nécessiter un -pkeyopt supplémentaire "digest:"md dans certains cas (par exemple, RSA avec le mode de remplissage PKCS#1 par défaut). Même pour d'autres algorithmes comme ECDSA, où l'option supplémentaire -pkeyopt n'affecte pas la sortie de signature, elle est recommandée, car elle permet de vérifier que la longueur d'entrée est cohérente avec le résumé visé.
-verify
Vérifie les données d'entrée par rapport à la signature fournie avec l'option -sigfile et indique si la vérification a réussi ou échoué. Les données d'entrée fournies avec l'option -in sont supposées être une valeur de hachage sauf si l'option -rawin est spécifiée ou implicite. Avec des données brutes, lorsqu'un algorithme de résumé est applicable, bien qu'il puisse être inféré de la signature ou prendre une valeur par défaut, il devrait également être spécifié.
-verifyrecover
Vérifie la signature donnée et produit les données récupérées (charge utile de la signature). Par exemple, dans le cas de RSA PKCS#1, les données récupérées sont l'encodage DER EMSA-PKCS-v1_5 de l'algorithme de résumé et de la valeur spécifiés dans la RFC8017 Section 9.2 https://datatracker.ietf.org/doc/html/rfc8017#section-9.2.

Notez qu'ici les données fournies avec l'option -in ne sont pas une entrée de signature (comme avec les options -sign et -verify) mais une valeur de sortie de signature, généralement produite en utilisant l'option -sign.

Cette option n'est disponible que pour une utilisation avec des clés RSA.

-encrypt
Chiffre les données d'entrée en utilisant une clé publique.
-decrypt
Déchiffre les données d'entrée en utilisant une clé privée.
-derive
Dérive un secret partagé en utilisant sa propre clé privée (EC)DH et la clé du pair.
-peerkey fichier
Fichier contenant la clé publique ou privée (EC)DH du pair à utiliser avec l'opération de dérivation (accord) de clé. Son type doit correspondre au type de la propre clé privée fournie avec -inkey.
-peerform DER|PEM|P12|ENGINE
Le format de la clé du pair ; non spécifié par défaut. Voir openssl-format-options(1) pour plus de détails.
-encap
Utilise un Mécanisme d'Encapsulation de Clé (KEM) pour encapsuler un secret partagé vers la clé publique d'un pair. L'encapsulateu

L'option -secret doit également être fournie pour spécifier le fichier de sortie pour la valeur secrète partagée dérivée générée lors du processus d'encapsulation. L'encapsulation est prise en charge avec un certain nombre d'algorithmes de clé publique, actuellement : ML-KEM, X25519, X449 et EC. Les algorithmes ECX et EC utilisent la construction DHKEM de la RFC9180 https://www.rfc-editor.org/rfc/rfc9180. L'encapsulation est également prise en charge avec des clés RSA via la construction RSASVE.

Au niveau de l'API, l'encapsulation et la décapsulation sont également prises en charge pour quelques algorithmes hybrides ECDHE (sans DHKEM) plus ML-KEM, mais ceux-ci sont principalement destinés à une utilisation avec TLS et ne doivent pas être utilisés de manière autonome. Il n'existe en tout cas aucun format standard de clé publique et privée pour les algorithmes hybrides, il n'est donc pas possible de fournir le matériel de clé requis.

-decap
Décoder un secret encapsulé, avec l'utilisation d'une clé -private, pour dériver le même secret partagé que celui obtenu lors de l'encapsulation du secret à la clé publique correspondante. Le secret encapsulé est par défaut lu depuis l'entrée standard, ou à partir du fichier spécifié avec -in. Le secret partagé dérivé est écrit dans le fichier spécifié avec l'option -secret, qui doit également être fournie. La décapsulation est prise en charge avec un certain nombre d'algorithmes de clé publique, actuellement : ML-KEM, X25519, X448 et EC. Les algorithmes ECX et EC utilisent la construction DHKEM de la RFC9180 https://www.rfc-editor.org/rfc/rfc9180. La décapsulation est également prise en charge avec des clés RSA via la construction RSASVE.
-kemop mode
Cette option est utilisée avec les commandes -encap/-decap et spécifie le mode KEM spécifique à l'algorithme de clé lorsqu'il n'y a pas de moyen par défaut d'encapsuler et de décapsuler des secrets partagés avec le type de clé choisi. Tous les algorithmes pris en charge ne prennent actuellement en charge que leur mode par défaut, et cette option, bien que disponible, n'est pas requise.
-kdf algorithme
Utiliser la fonction de dérivation de clé algorithme. Les algorithmes pris en charge sont actuellement TLS1-PRF et HKDF. Note : des paramètres supplémentaires et la longueur de sortie du KDF devront normalement être définis pour que cela fonctionne. Voir EVP_PKEY_CTX_set_hkdf_md(3) et EVP_PKEY_CTX_set_tls1_prf_md(3) pour les paramètres de chaîne pris en charge pour chaque algorithme.
-kdflen longueur
Définir la longueur de sortie pour le KDF.
-pkeyopt opt:valeur
Options de clé publique spécifiées sous forme de opt:valeur. Voir NOTES ci-dessous pour plus de détails.
-pkeyopt_passin opt[:passarg]
Permet de lire une option de clé publique opt depuis stdin ou une source de mot de passe. Si seule opt est spécifiée, l'utilisateur sera invité à entrer un mot de passe sur stdin. Alternativement, passarg peut être spécifié, qui peut être n'importe quelle valeur prise en charge par openssl-passphrase-options(1).
-hexdump
Afficher la sortie de données au format hexadécimal.
-asn1parse
Analyser les données de sortie ASN.1 pour vérifier leur encodage DER et afficher toute erreur. Lorsqu'il est combiné avec l'option -verifyrecover, cela peut être utile dans le cas où une structure codée en DER ASN.1 aurait été signée directement (sans la hacher) et lors de la vérification d'une signature au format PKCS#1 v1.5, qui a un codage DER.
-engine id
Voir "Options du moteur" dans openssl(1). Cette option est obsolète.
-engine_impl
Lorsqu'elle est utilisée avec l'option -engine, elle spécifie d'utiliser également le moteur id pour les opérations cryptographiques.
-rand fichiers, -writerand fichier
Voir "Options d'état aléatoire" dans openssl(1) pour plus de détails.
-provider nom
-provider-path chemin
-provparam [nom:]clé=valeur
-propquery propq
Voir "Options du fournisseur" dans openssl(1), provider(7) et property(7).
-config fichierconfig
Voir "Option de configuration" dans openssl(1).

NOTES

Les opérations et options prises en charge varient en fonction de l'algorithme de clé et de son implémentation. Les opérations et options OpenSSL sont indiquées ci-dessous.

Sauf mention contraire, l'option -pkeyopt prend en charge pour tous les types de clés publiques l'argument "digest:"alg, qui spécifie le digest utilisé pour les opérations de signature et de vérification. La valeur alg doit représenter un nom de digest tel qu'utilisé dans la fonction EVP_get_digestbyname(), par exemple sha256. Cette valeur n'est pas utilisée pour hacher les données d'entrée. Elle est utilisée (par certains algorithmes) pour vérifier la cohérence des longueurs des données fournies et pour créer les structures qui composent la signature (par exemple, DigestInfo dans les signatures RSASSA PKCS#1 v1.5).

Par exemple, si la valeur de l'argument "digest" de l'option -pkeyopt est sha256, l'entrée de signature ou de vérification doit être la valeur binaire de 32 octets de la sortie de la fonction de hachage SHA256.

Sauf si -rawin est utilisé ou implicite, cette commande ne hache pas les données d'entrée mais utilisera plutôt les données directement comme entrée pour l'algorithme de signature. En fonction du type de clé, du type de signature et du mode de rembourrage, les longueurs maximales raisonnables des données d'entrée diffèrent. Avec RSA, les données signées ne peuvent pas être plus longues que le module de clé. Dans le cas d'ECDSA et DSA, les données ne doivent pas être plus longues que la taille du champ, sinon elles seront tronquées silencieusement à la taille du champ. Dans tous les cas, la taille d'entrée ne doit pas être supérieure à la taille de sortie de digest prise en charge la plus grande, EVP_MAX_MD_SIZE, qui est actuellement de 64 octets.

ALGORITHME RSA

L'algorithme RSA prend généralement en charge les opérations de chiffrement, déchiffrement, signature, vérification et verifyrecover. Cependant, certains modes de rembourrage ne prennent en charge qu'un sous-ensemble de ces opérations. Les valeurs supplémentaires suivantes pour pkeyopt sont prises en charge :

rsa_padding_mode:mode
Ceci définit le mode de rembourrage RSA. Les valeurs acceptables pour mode sont pkcs1 pour le rembourrage PKCS#1, none pour aucun rembourrage, oaep pour le mode OAEP, x931 pour le mode X9.31 et pss pour PSS.

En rembourrage PKCS#1, si le digest du message n'est pas défini, les données fournies sont signées ou vérifiées directement au lieu d'utiliser une structure DigestInfo. Si un digest est défini, la structure DigestInfo est utilisée et sa longueur doit correspondre au type de digest.

Notez que pour le rembourrage pkcs1, pour se protéger contre l'attaque de Bleichenbacher, le déchiffrement n'échouera pas en cas d'échec de vérification du rembourrage. Utilisez none et une inspection manuelle du message déchiffré pour vérifier si la valeur déchiffrée a un rembourrage PKCS#1 v1.5 correct.

Pour le mode oaep, seuls le chiffrement et le déchiffrement sont pris en charge.

Pour x931, si le type de digest est défini, il est utilisé pour formater les données du bloc, sinon le premier octet est utilisé pour spécifier l'ID du digest X9.31. Les opérations de signature, vérification et verifyrecover peuvent être effectuées dans ce mode.

Pour le mode pss, seules la signature et la vérification sont prises en charge, et le type de digest doit être spécifié.

rsa_pss_saltlen:len
Pour le mode pss uniquement, cette option spécifie la longueur du sel. Trois valeurs spéciales sont prises en charge : digest définit la longueur du sel à la longueur du digest, max définit la longueur du sel à la valeur maximale permise. Lors de la vérification, auto provoque la détermination automatique de la longueur du sel en fonction de la structure du bloc PSS.
rsa_mgf1_md:digest
Pour le rembourrage PSS et OAEP, définit le digest MGF1. Si le digest MGF1 n'est pas explicitement défini en mode PSS, le digest de signature est utilisé.
rsa_oaep_md:digest
Définit le digest utilisé pour la fonction de hachage OAEP. S'il n'est pas explicitement défini, SHA256 est utilisé.
rsa_pkcs1_implicit_rejection:flag
Désactive (lorsqu'il est défini sur 0) ou active (lorsqu'il est défini sur 1) l'utilisation du rejet implicite avec le déchiffrement PKCS#1 v1.5. Lorsqu'il est activé (par défaut), pour se protéger contre l'attaque de Bleichenbacher, la bibliothèque générera un texte brut aléatoire déterministe qu'elle renverra à l'appelant en cas d'échec de la vérification du rembourrage. Lorsqu'il est désactivé, il incombe à l'appelant de gérer les erreurs retournées de manière à ne pas créer de canaux auxiliaires.

ALGORITHME RSA-PSS

L'algorithme RSA-PSS est une version restreinte de l'algorithme RSA qui ne prend en charge que les opérations de signature et de vérification avec rembourrage PSS. Les valeurs supplémentaires suivantes pour -pkeyopt sont prises en charge :

rsa_padding_mode:mode, rsa_pss_saltlen:len, rsa_mgf1_md:digest
Ces options ont la même signification que pour l'algorithme RSA, avec certaines
restrictions supplémentaires. Le mode de remplissage ne peut être défini que sur pss, qui est la valeur par défaut.

Si la clé a des restrictions de paramètres, le résumé, le résumé MGF1 et la longueur du sel sont définis sur les valeurs spécifiées dans les paramètres. Le résumé et le MG ne peuvent pas être modifiés et la longueur du sel ne peut pas être définie sur une valeur inférieure à la restriction minimale.

ALGORITHME DSA

L'algorithme DSA prend en charge uniquement les opérations de signature et de vérification. Actuellement, il n'y a pas d'options -pkeyopt supplémentaires autres que digest. Le résumé SHA256 est supposé par défaut.

ALGORITHME DH

L'algorithme DH prend en charge uniquement l'opération de dérivation et aucune option -pkeyopt supplémentaire.

ALGORITHME EC

L'algorithme EC prend en charge les opérations de signature, de vérification et de dérivation. Les opérations de signature et de vérification utilisent ECDSA et la dérivation utilise ECDH. SHA256 est supposé par défaut pour l'option -pkeyopt digest.

ALGORITHMES X25519 ET X448

Les algorithmes X25519 et X448 ne prennent en charge que la dérivation de clé. Actuellement, il n'y a pas d'options supplémentaires.

ALGORITHMES SLH-DSA

Les algorithmes SLH-DSA (SLH-DSA-SHA2-128s, SLH-DSA-SHA2-128f, SLH-DSA-SHA2-192s, SLH-DSA-SHA2-192f, SLH-DSA-SHA2-256s, SLH-DSA-SHA2-256f) sont des algorithmes de signature post-quantiques. Lors de l'utilisation de SLH-DSA avec pkeyutl, les options suivantes sont disponibles :

-sign
Signer les données d'entrée à l'aide d'une clé privée SLH-DSA. Par exemple : 
$ openssl pkeyutl -sign -in file.txt -inkey slhdsa.pem -out sig
-verify
Vérifier la signature à l'aide d'une clé publique SLH-DSA. Par exemple : 
$ openssl pkeyutl -verify -in file.txt -inkey slhdsa.pem -sigfile sig

Voir EVP_PKEY-SLH-DSA(7) et EVP_SIGNATURE-SLH-DSA(7) pour des détails supplémentaires sur l'algorithme SLH-DSA et son implémentation.

ALGORITHMES ML-DSA-44, ML-DSA-65 ET ML-DSA-87

Les algorithmes ML-DSA sont des algorithmes de signature post-quantiques qui prennent en charge la signature et la vérification de messages « bruts ». Aucun hachage préliminaire n'est effectué. Lors de l'utilisation de ML-DSA avec pkeyutl, les options suivantes sont disponibles :

-sign
Signer les données d'entrée à l'aide d'une clé privée ML-DSA. Par exemple : 
$ openssl pkeyutl -sign -in file.txt -inkey mldsa65.pem -out sig
-verify
Vérifier la signature à l'aide d'une clé publique ML-DSA. Par exemple : 
$ openssl pkeyutl -verify -in file.txt -inkey mldsa65.pem -sigfile sig
-pkeyopt opt:valeur
Options supplémentaires pour la signature et la vérification ML-DSA :
message-encoding:valeur
Spécifie le mode de codage du message utilisé pour la signature. Ceci contrôle la façon dont le message d'entrée est traité avant la signature. Les valeurs valides sont décrites dans EVP_SIGNATURE-ML-DSA(7). Par exemple : 
$ openssl pkeyutl -sign -in file.txt -inkey mldsa65.pem -out sig -pkeyopt message-encoding:1
test-entropy:valeur
Spécifie une valeur d'entropie de test pour la signature déterministe. Par exemple : 
$ openssl pkeyutl -sign -in file.txt -inkey mldsa65.pem -out sig -pkeyopt test-entropy:abcdefghijklmnopqrstuvwxyz012345
hextest-entropy:valeur
Spécifie une valeur d'entropie de test au format hexadécimal. Par exemple : 
$ openssl pkeyutl -sign -in file.txt -inkey mldsa65.pem -out sig -pkeyopt hextest-entropy:000102030405060708090a0b0c0d0e0f101112131415161718191a1b1c1d1e1f
deterministic:valeur
Active la signature déterministe. Par exemple : 
$ openssl pkeyutl -sign -in file.txt -inkey mldsa65.pem -out sig -pkeyopt deterministic:1
mu:valeur
Spécifie le paramètre mu. Par exemple : 
$ echo -n "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef" >file.txt
$ openssl pkeyutl -sign -in file.txt -inkey mldsa65.pem -out sig -pkeyopt mu:1
context-string:chaîne
Spécifie une chaîne de contexte pour les opérations de signature et de vérification. La chaîne de contexte doit être la même pour que la vérification réussisse. Par exemple : 
$ openssl pkeyutl -sign -in file.txt -inkey mldsa65.pem -out sig -pkeyopt context-string:mycontext
$ openssl pkeyutl -verify -in file.txt -inkey mldsa65.pem -sigfile sig -pkeyopt context-string:mycontext
hexcontext-string:chaîne
Spécifie une chaîne de contexte au format hexadécimal, permettant des valeurs de contrôle binaires. Par exemple : 
$ openssl pkeyutl -sign -in file.txt -inkey mldsa65.pem -out sig -pkeyopt hexcontext-string:6d79636f6e74657874

L'opération de signature prend en charge une option deterministic:bool, où bool est défini sur 1 si une signature déterministe doit être générée avec une entrée aléatoire fixe entièrement composée de zéros. Par défaut, ou si le bool est 0, une valeur d'entropie aléatoire est utilisée. Un résultat déterministe peut également être obtenu en spécifiant une valeur d'entropie explicite via le paramètre hextest-entropy:valeur. La signature ML-DSA déterministe ne doit être utilisée que dans les tests.

Voir EVP_SIGNATURE-ML-DSA(7) pour des détails supplémentaires sur les algorithmes ML-DSA et leur implémentation.

ALGORITHMES ML-KEM-512, ML-KEM-768 ET ML-KEM-1024

Les algorithmes ML-KEM prennent en charge uniquement l'encapsulation et la décapsulation. L'opération d'encapsulation prend en charge une option hexikme:entropie, où entropie est le codage hexadécimal sur 64 chiffres d'une valeur de 32 octets. Ceci ne doit être utilisé que dans les tests ; les valeurs connues ou divulguées de l'option peuvent compromettre le secret partagé généré.

Voir EVP_KEM-ML-KEM(7) pour plus de détails.

ALGORITHMES ED25519 ET ED448

Ces algorithmes ne prennent en charge que la signature et la vérification. OpenSSL n'implémente que les variantes « pures » de ces algorithmes, de sorte que des données brutes peuvent leur être passées directement sans les hacher au préalable. OpenSSL ne prend en charge que l'opération « oneshot » avec ces algorithmes. Cela signifie que l'intégralité du fichier à signer/vérifier doit être chargée en mémoire avant son traitement. La signature ou la vérification de fichiers très volumineux doit être évitée. De plus, la taille du fichier doit être connue pour que cela fonctionne. Si la taille du fichier ne peut pas être déterminée (par exemple, si l'entrée est stdin), l'opération de signature ou de vérification échouera.

SM2

L'algorithme SM2 prend en charge les opérations de signature, de vérification, de chiffrement et de déchiffrement. Pour les opérations de signature et de vérification, SM2 nécessite qu'une chaîne d'identification distinguante soit fournie. La valeur -pkeyopt suivante est prise en charge :

distid:chaîne
Définit la chaîne d'ID utilisée dans les opérations de signature ou de vérification SM2. Lors de la vérification d'une signature SM2, la chaîne d'ID doit être la même que celle utilisée lors de la signature des données. Sinon, la vérification échouera.
hexdistid:chaîne_hex
Définit la chaîne d'ID utilisée dans les opérations de signature ou de vérification SM2. Lors de la vérification d'une signature SM2, la chaîne d'ID doit être la même que celle utilisée lors de la signature des données. Sinon, la vérification échouera. La chaîne d'ID fournie avec cette option doit être une valeur hexadécimale valide.

EXEMPLES

Signer des données à l'aide d'une clé privée :

openssl pkeyutl -sign -in file -inkey key.pem -out sig

Récupérer les données signées (par exemple, si une clé RSA est utilisée) :

openssl pkeyutl -verifyrecover -in sig -inkey key.pem

Vérifier la signature (par exemple, une clé DSA) :

openssl pkeyutl -verify -in file -sigfile sig -inkey key.pem

Signer des données à l'aide d'une valeur de résumé de message (ceci n'est actuellement valide que pour RSA) :

openssl pkeyutl -sign -in file -inkey key.pem -out sig -pkeyopt digest:sha256

Dériver un secret partagé :

openssl pkeyutl -derive -inkey key.pem -peerkey pubkey.pem -out secret

Hexdump 48 octets de TLS1 PRF en utilisant le résumé SHA256 et un secret partagé et une graine constitués de l'unique octet 0xFF :

openssl pkeyutl -kdf TLS1-PRF -kdflen 48 -pkeyopt md:SHA256 \
   -pkeyopt hexsecret:ff -pkeyopt hexseed:ff -hexdump

Dériver une clé à l'aide de scrypt où le mot de passe est lu depuis la ligne de commande :

openssl pkeyutl -kdf scrypt -kdflen 16 -pkeyopt_passin pass \
   -pkeyopt hexsalt:aabbcc -pkeyopt N:16384 -pkeyopt r:8 -pkeyopt p:1

Dériver en utilisant le même algorithme, mais lire la clé à partir de la variable d'environnement MYPASS :

openssl pkeyutl -kdf scrypt -kdflen 16 -pkeyopt_passin pass:env:MYPASS \
   -pkeyopt hexsalt:aabbcc -pkeyopt N:16384 -pkeyopt r:8 -pkeyopt p:1

Signer des données à l'aide d'une clé privée SM2(7) et d'un ID spécifique :

openssl pkeyutl -sign -in file -inkey sm2.key -out sig -rawin -digest sm3 \
   -pkeyopt distid:someid

Vérifier des données à l'aide d'un certificat SM2(7) et d'un ID spécifique :

openssl pkeyutl -verify -certin -in

EXEMPLES

Chiffrer des données à l'aide d'une clé publique avec remplissage OAEP en utilisant SHA256:

openssl pkeyutl -encrypt -in file -inkey pubkey.pem -out secret \
   -pkeyopt rsa_padding_mode:oaep -pkeyopt rsa_oaep_md:sha256

Déchiffrer des données à l'aide d'une clé privée avec remplissage OAEP en utilisant SHA256:

openssl pkeyutl -decrypt -in file -inkey key.pem -out secret \
   -pkeyopt rsa_padding_mode:oaep -pkeyopt rsa_oaep_md:sha256

Créer une paire de clés ML-DSA et signer des données avec une chaîne de contexte spécifique:

$ openssl genpkey -algorithm ML-DSA-65 -out mldsa65.pem
$ openssl pkeyutl -sign -in file.txt -inkey mldsa65.pem -out sig -pkeyopt context-string:example

Vérifier une signature à l'aide de ML-DSA avec la même chaîne de contexte:

$ openssl pkeyutl -verify -in file.txt -inkey mldsa65.pem -sigfile sig -pkeyopt context-string:example

Générer une paire de clés ML-KEM et l'utiliser pour l'encapsulation:

$ openssl genpkey -algorithm ML-KEM-768 -out mlkem768.pem
$ openssl pkey -in mlkem768.pem -pubout -out mlkem768_pub.pem
$ openssl pkeyutl -encap -inkey mlkem768_pub.pem -pubin -out ciphertext -secret shared_secret.bin

Décapsuler un secret partagé à l'aide d'une clé privée ML-KEM:

$ openssl pkeyutl -decap -inkey mlkem768.pem -in ciphertext -secret decapsulated_secret.bin

Créer une paire de clés SLH-DSA et signer des données:

$ openssl genpkey -algorithm SLH-DSA-SHA2-128s -out slh-dsa.pem
$ openssl pkeyutl -sign -in file.txt -inkey slh-dsa.pem -out sig

Vérifier une signature à l'aide de SLH-DSA:

$ openssl pkeyutl -verify -in file.txt -inkey slh-dsa.pem -sigfile sig

HISTORIQUE

Depuis OpenSSL 3.5, l'option -digest implique -rawin, et ces deux options ne sont plus requises lors de la signature ou de la vérification avec une clé Ed25519 ou Ed448.

Également depuis OpenSSL 3.5, l'option -kemop n'est plus requise pour aucun des algorithmes pris en charge, le seul mode pris en charge étant désormais le mode par défaut.

L'option -engine a été dépréciée dans OpenSSL 3.0.
