NOM

ovsdb-server - Schéma de base de données du _Serveur

Chaque ovsdb-server (version 2.9 ou ultérieure) héberge toujours une instance de ce schéma, qui contient des informations sur l'état et la configuration du serveur lui-même. Cette base de données est en lecture seule. Cette page de manuel décrit le schéma de cette base de données.

RÉSUMÉ DES TABLES

La liste suivante résume l'objectif de chacune des tables de la base de données _Server. Chaque table est décrite plus en détail sur une page ultérieure.

Table
Objectif
Database
Bases de données.

TABLE Database

Cette table décrit les bases de données hébergées par le serveur de base de données, avec une ligne par base de données. Au fur et à mesure que sa configuration et son état changent, le serveur met automatiquement et immédiatement à jour la table pour qu'elle corresponde.

Le protocole OVSDB spécifié dans la RFC 7047 ne fournit aucun moyen pour un client OVSDB de connaître certains types de changements de configuration, tels que les bases de données ajoutées ou supprimées pendant qu'un client est connecté au serveur, ou les changements de bases de données entre lecture/écriture et lecture seule en raison d'une transition entre les rôles actif et de secours. Cette table fournit une solution : les clients peuvent surveiller le contenu de la table pour connaître les changements importants.

Traditionnellement, ovsdb-server déconnecte tous ses clients lorsqu'un changement de configuration important se produit, car cela invite un client bien écrit à réévaluer ce qui est disponible à partir du serveur lorsqu'il se reconnecte. Comme cette table fournit un moyen alternatif et plus efficace de connaître ces changements, OVS 2.9 introduit également l'appel RPC set_db_change_aware, documenté dans ovsdb-server(7), pour permettre aux clients de supprimer ce comportement de déconnexion.

Lorsqu'une base de données est supprimée du serveur, en plus des mises à jour de la table Database, le serveur envoie des messages canceled, tels que décrits dans la section 4.1.4 de la RFC 7047, en réponse aux transactions en attente pour la base de données supprimée. Le serveur annule également toute surveillance en attente initiée par monitor ou monitor_cond demandée sur la base de données supprimée, en envoyant l'appel RPC monitor_canceled décrit dans ovsdb-server(7). Seuls les clients qui désactivent la déconnexion avec set_db_change_aware reçoivent ces messages.

Les clients peuvent utiliser la colonne _uuid de cette table comme numéro de génération. Le serveur génère un nouveau _uuid chaque fois qu'il ajoute une base de données, de sorte que la suppression puis la réajout d'une base de données au serveur entraînent la modification du _uuid de sa ligne.

Détails:

name: chaîne de caractères
Le nom de la base de données, tel que spécifié dans son schéma.
model: chaîne de caractères, l'un de clustered, relay, ou standalone
Le modèle de stockage : standalone pour une base de données autonome ou actif-passif, clustered pour une base de données clusterisée, relay pour une base de données relais.
schema: chaîne de caractères optionnelle
Le schéma de la base de données, sous forme de chaîne JSON. Dans le cas d'une base de données clusterisée, elle est vide jusqu'à ce qu'elle finisse de rejoindre son cluster. Dans le cas d'une base de données relais, elle est vide jusqu'à ce qu'elle se connecte à la source relais.
connected: booléen
Vrai si la base de données est connectée à son stockage. Une base de données autonome est toujours connectée. Une base de données clusterisée est connectée si le serveur est en contact avec une majorité de son cluster. Une base de données relais est connectée si le serveur est en contact avec la source relais, c'est-à-dire s'il est connecté au serveur dont il se synchronise. Une base de données non connectée ne peut pas être modifiée et ses données peuvent être indisponibles ou obsolètes.
Bases de données clusterisées :

Ces colonnes sont les plus intéressantes et dans certains cas les seules pertinentes pour les bases de données clusterisées, c'est-à-dire celles pour lesquelles la colonne model est clustered.

leader: booléen
Vrai si la base de données est le leader de son cluster. Pour une base de données autonome ou actif-passif, ceci est toujours vrai. Pour une base de données relais, ceci est toujours faux.
cid: uuid optionnel
L'identifiant du cluster pour cette base de données, qui est le même pour tous les serveurs qui hébergent cette base de données clusterisée particulière. Pour une base de données autonome, actif-passif ou relais, elle est vide.
sid: uuid optionnel
L'identifiant du serveur pour cette base de données, différent pour chaque serveur qui héberge une base de données clusterisée particulière. Un serveur qui héberge plus d'une base de données clusterisée aura un sid différent dans chacune. Pour une base de données autonome, actif-passif ou relais, elle est vide.
index: entier optionnel
Pour une base de données clusterisée, l'index de l'entrée de journal actuellement exposée aux clients. Pour un serveur donné, cela augmente de manière monotone. Lorsqu'un client passe d'un serveur à un autre dans un cluster, il peut s'assurer qu'il ne voit jamais un instantané plus ancien des données en évitant les serveurs dont l'index est inférieur à la plus grande valeur qu'ils ont déjà observée.
Pour une base de données autonome, actif-passif ou relais, elle est vide.
