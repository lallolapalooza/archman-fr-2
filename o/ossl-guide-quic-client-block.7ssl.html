ossl-guide-quic-client-block - Guide OpenSSL : Écrire un client QUIC bloquant simple

EXEMPLE CLIENT QUIC BLOQUANT SIMPLE

Cette page présente divers exemples de code démontrant comment écrire une application client QUIC bloquante simple qui se connecte à un serveur, lui envoie une requête HTTP/1.0 et lit la réponse. Notez que HTTP/1.0 sur QUIC n'est pas standard et ne sera pas pris en charge par les serveurs réels. Ceci est à des fins de démonstration uniquement.

Nous supposons que vous avez déjà installé OpenSSL sur votre système ; que vous avez déjà une compréhension fondamentale des concepts OpenSSL, de TLS et de QUIC (voir ossl-guide-libraries-introduction(7), ossl-guide-tls-introduction(7) et ossl-guide-quic-introduction(7)) ; et que vous savez comment écrire et compiler du code C et le lier aux bibliothèques libcrypto et libssl fournies par OpenSSL. Il suppose également que vous avez une compréhension de base d'UDP/IP et des sockets. Le code d'exemple que nous allons construire dans ce tutoriel modifiera l'exemple de client TLS bloquant abordé dans ossl-guide-tls-client-block(7). Seules les différences entre ce client et celui-ci seront discutées, nous supposons donc que vous avez suivi et compris ce tutoriel.

Pour ce tutoriel, notre client utilisera un seul flux QUIC. Un tutoriel ultérieur discutera de la manière d'écrire un client multi-flux (voir ossl-guide-quic-multi-stream(7)).

Le code source complet de cet exemple de client QUIC bloquant est disponible dans le répertoire "demos/guide" de la distribution source OpenSSL, dans le fichier "quic-client-block.c". Il est également disponible en ligne à l'adresse https://github.com/openssl/openssl/blob/master/demos/guide/quic-client-block.c.

Création des objets SSL_CTX et SSL

Dans le tutoriel TLS (ossl-guide-tls-client-block(7)), nous avons créé un objet SSL_CTX pour notre client et l'avons utilisé pour créer un objet SSL représentant la connexion TLS. Une connexion QUIC fonctionne exactement de la même manière. Nous créons d'abord un objet SSL_CTX, puis nous l'utilisons pour créer un objet SSL représentant la connexion QUIC.

Comme dans l'exemple TLS, la première étape consiste à créer un objet SSL_CTX pour notre client. Ceci est fait de la même manière qu'auparavant, sauf que nous utilisons une "méthode" différente. OpenSSL propose deux méthodes client QUIC différentes, c'est-à-dire OSSL_QUIC_client_method(3) et OSSL_QUIC_client_thread_method(3).

La première est l'équivalent de TLS_client_method(3) mais pour le protocole QUIC. La seconde est identique, mais elle créera en outre un thread d'arrière-plan pour gérer les événements basés sur le temps (connu sous le nom de "mode assisté par thread", voir ossl-guide-quic-introduction(7)). Pour ce tutoriel, nous utiliserons OSSL_QUIC_client_method(3) car nous ne laisserons pas la connexion QUIC inactivité dans notre application et le mode assisté par thread n'est donc pas nécessaire.

/*
 * Crée un SSL_CTX que nous pouvons utiliser pour créer des objets SSL à partir.
 * Nous voulons un SSL_CTX pour créer des clients, nous utilisons donc OSSL_QUIC_client_method()
 * ici.
 */
ctx = SSL_CTX_new(OSSL_QUIC_client_method());
if (ctx == NULL) {
    printf("Échec de la création du SSL_CTX\n");
    goto end;
}

Les autres étapes de configuration que nous avons appliquées au SSL_CTX pour TLS s'appliquent également à QUIC, à l'exception de la restriction des versions TLS que nous acceptons. L'implémentation du protocole QUIC dans OpenSSL ne prend actuellement en charge que TLSv1.3. Il n'est pas nécessaire d'appeler SSL_CTX_set_min_proto_version(3) ou SSL_CTX_set_max_proto_version(3) dans une application QUIC OpenSSL, et tout appel de ce type sera ignoré.

Une fois le SSL_CTX créé, l'objet SSL est construit exactement de la même manière que pour l'application TLS.

Création du socket et du BIO

Une différence majeure entre TLS et QUIC réside dans le protocole de transport sous-jacent. TLS utilise TCP tandis que QUIC utilise UDP. La manière dont le socket QUIC est créé dans notre code d'exemple est très similaire à celle de TLS. Nous utilisons les fonctions d'assistance BIO_lookup_ex(3) et BIO_socket(3) comme nous l'avons fait dans le tutoriel précédent, sauf que nous passons SOCK_DGRAM comme argument pour indiquer UDP (au lieu de SOCK_STREAM pour TCP).

/*
 * Recherche les informations d'adresse IP du serveur.
 */
if (!BIO_lookup_ex(hostname, port, BIO_LOOKUP_CLIENT, family, SOCK_DGRAM, 0,
                   &res))
    return NULL;
/*
 * Parcourt toutes les adresses possibles pour le serveur et en trouve une
 * à laquelle nous pouvons nous connecter.
 */
for (ai = res; ai != NULL; ai = BIO_ADDRINFO_next(ai)) {
    /*
     * Crée un socket TCP. Nous pourrions tout aussi bien utiliser des appels
     * non-OpenSSL tels que "socket" ici pour cela et les fonctions suivantes
     * de connexion et de fermeture. Mais pour des raisons de portabilité et
     * aussi pour obtenir des erreurs sur la pile OpenSSL en cas d'échec,
     * nous utilisons les versions OpenSSL de ces fonctions.
     */
    sock = BIO_socket(BIO_ADDRINFO_family(ai), SOCK_DGRAM, 0, 0);
    if (sock == -1)
        continue;
    /* Connecte le socket à l'adresse du serveur */
    if (!BIO_connect(sock, BIO_ADDRINFO_address(ai), 0)) {
        BIO_closesocket(sock);
        sock = -1;
        continue;
    }
    /* Passe en mode non bloquant */
    if (!BIO_socket_nbio(sock, 1)) {
        BIO_closesocket(sock);
        sock = -1;
        continue;
    }
    break;
}
if (sock != -1) {
    *peer_addr = BIO_ADDR_dup(BIO_ADDRINFO_address(ai));
    if (*peer_addr == NULL) {
        BIO_closesocket(sock);
        return NULL;
    }
}
/* Libère les ressources d'informations d'adresse que nous avons allouées précédemment */
BIO_ADDRINFO_free(res);

Vous remarquerez peut-être quelques autres différences entre ce code et la version que nous avons utilisée pour TLS.

Premièrement, nous mettons le socket en mode non bloquant. Cela doit toujours être fait pour une application QUIC OpenSSL. Cela peut surprendre étant donné que nous essayons d'écrire un client bloquant. Malgré cela, l'objet SSL aura toujours un comportement bloquant. Voir ossl-guide-quic-introduction(7) pour plus d'informations à ce sujet.

Deuxièmement, nous prenons note de l'adresse IP du pair auquel nous nous connectons. Nous stockons ces informations. Nous en aurons besoin plus tard.

Voir BIO_lookup_ex(3), BIO_socket(3), BIO_connect(3), BIO_closesocket(3), BIO_ADDRINFO_next(3), BIO_ADDRINFO_address(3), BIO_ADDRINFO_free(3) et BIO_ADDR_dup(3) pour plus d'informations sur les fonctions utilisées ici. Dans le code d'exemple ci-dessus, les variables hostname et port sont des chaînes de caractères, par exemple "www.example.com" et "443".

Comme pour notre client TLS, une fois le socket créé et connecté, nous devons l'associer à un objet BIO :

BIO *bio;
/* Crée un BIO pour envelopper le socket */
bio = BIO_new(BIO_s_datagram());
if (bio == NULL) {
    BIO_closesocket(sock);
    return NULL;
}
/*
 * Associe le BIO nouvellement créé au socket sous-jacent. En passant
 * BIO_CLOSE ici, le socket sera automatiquement fermé lorsque le BIO
 * sera libéré. Sinon, vous pouvez utiliser BIO_NOCLOSE, auquel cas vous
 * devez fermer explicitement le socket lorsqu'il n'est plus nécessaire.
 */
BIO_set_fd(bio, sock, BIO_CLOSE);

Notez l'utilisation de BIO_s_datagram(3) ici, par opposition à BIO_s_socket(3) que nous avons utilisé pour notre client TLS. Ceci est à nouveau dû au fait que QUIC utilise UDP au lieu de TCP pour sa couche de transport. Voir BIO_new(3), BIO_s_datagram(3) et BIO_set_fd(3) pour

Définition du nom d'hôte du serveur

Comme dans le tutoriel TLS, nous devons définir le nom d'hôte du serveur à la fois pour SNI (Server Name Indication) et pour la validation du certificat. Les étapes sont identiques à celles du tutoriel TLS et ne seront pas répétées ici.

Définition de l'ALPN

ALPN (Application-Layer Protocol Negotiation) est une fonctionnalité de TLS qui permet à l'application de négocier le protocole à utiliser sur la connexion. Par exemple, si vous avez l'intention d'utiliser HTTP/3 sur la connexion, la valeur ALPN pour cela est "h3" (voir https://www.iana.org/assignments/tls-extensiontype-values/tls-extensiontype-values.xml#alpn-protocol-ids). OpenSSL permet à un client de spécifier l'ALPN à utiliser via la fonction SSL_set_alpn_protos(3). Ceci est facultatif pour un client TLS et notre client simple que nous avons développé dans ossl-guide-tls-client-block(7) ne l'utilisait pas. Cependant, QUIC exige que la négociation TLS utilisée pour établir une connexion QUIC utilise ALPN.

unsigned char alpn[] = { 8, 'h', 't', 't', 'p', '/', '1', '.', '0' };
/* SSL_set_alpn_protos retourne 0 en cas de succès ! */
if (SSL_set_alpn_protos(ssl, alpn, sizeof(alpn)) != 0) {
    printf("Échec de la définition de l'ALPN pour la connexion\n");
    goto end;
}

L'ALPN est spécifié à l'aide d'un tableau d'octets non signés préfixé par sa longueur (ce n'est pas une chaîne terminée par NUL). Notre démo client bloquant TLS originale utilisait HTTP/1.0. Nous utiliserons la même pour cet exemple. Contrairement à la plupart des fonctions OpenSSL, SSL_set_alpn_protos(3) retourne zéro en cas de succès et une valeur non nulle en cas d'échec.

Définition de l'adresse du pair

Une application OpenSSL QUIC doit spécifier l'adresse cible du serveur auquel elle se connecte. Dans la section "Création du socket et du BIO" ci-dessus, nous avons sauvegardé cette adresse pour une utilisation future. Nous devons maintenant l'utiliser via la fonction SSL_set1_initial_peer_addr(3).

/* Définir l'adresse IP du pair distant */
if (!SSL_set1_initial_peer_addr(ssl, peer_addr)) {
    printf("Échec de la définition de l'adresse initiale du pair\n");
    goto end;
}

Notez que nous devrons libérer la valeur peer_addr que nous avons allouée précédemment via BIO_ADDR_dup(3) :

BIO_ADDR_free(peer_addr);

La négociation et le transfert des données d'application

Une fois la configuration initiale de l'objet SSL terminée, nous effectuons la négociation via SSL_connect(3) exactement de la même manière que pour le client TLS, nous ne le répéterons donc pas ici.

Nous pouvons également effectuer le transfert de données en utilisant un flux QUIC par défaut qui est automatiquement associé à l'objet SSL pour nous. Nous pouvons transmettre des données en utilisant SSL_write_ex(3) et recevoir des données en utilisant SSL_read_ex(3) de la même manière qu'avec TLS. La principale différence est que nous devons gérer les échecs différemment. Avec QUIC, le flux peut être réinitialisé par le pair (ce qui est fatal pour ce flux), mais la connexion sous-jacente peut toujours être saine.

D'abord, nous écrivons toute la requête dans le flux. Nous devons également nous assurer de signaler au serveur que nous avons fini d'écrire. Cela peut être fait en passant le drapeau SSL_WRITE_FLAG_CONCLUDE à SSL_write_ex2(3) ou en appelant SSL_stream_conclude(3). Puisque la première méthode est plus efficace, nous choisissons de le faire.

/* Écrire une requête GET HTTP au pair */
if (!SSL_write_ex(ssl, request_start, strlen(request_start), &written)) {
    printf("Échec de l'écriture du début de la requête HTTP\n");
    goto end;
}
if (!SSL_write_ex(ssl, hostname, strlen(hostname), &written)) {
    printf("Échec de l'écriture du nom d'hôte dans la requête HTTP\n");
    goto end;
}
if (!SSL_write_ex2(ssl, request_end, strlen(request_end),
    SSL_WRITE_FLAG_CONCLUDE, &written)) {
    printf("Échec de l'écriture de la fin de la requête HTTP\n");
    goto end;
}

Ensuite, nous lisons la réponse du serveur.

/*
 * Lire jusqu'à sizeof(buf) octets de la réponse. Nous continuons à lire
 * jusqu'à ce que le serveur ferme la connexion.
 */
while (SSL_read_ex(ssl, buf, sizeof(buf), &readbytes)) {
    /*
    * OpenSSL ne garantit pas que les données retournées sont une chaîne
    * ou qu'elles sont terminées par NUL, nous utilisons donc fwrite()
    * pour écrire le nombre exact d'octets que nous avons lus. Les données
    * pourraient être non imprimables ou contenir des caractères NUL au milieu.
    * Pour cet exemple simple, nous allons les imprimer sur stdout de toute façon.
    */
    fwrite(buf, 1, readbytes, stdout);
}
/* Au cas où la réponse ne se termine pas par une nouvelle ligne, nous en ajoutons une maintenant */
printf("\n");
/*
 * Vérifier si nous avons terminé la boucle while ci-dessus normalement ou
 * à la suite d'une erreur. L'argument 0 passé à SSL_get_error() est le
 * code de retour que nous avons reçu de l'appel SSL_read_ex(). Il doit
 * être 0 pour arriver ici. L'achèvement normal est indiqué par SSL_ERROR_ZERO_RETURN.
 * En termes QUIC, cela signifie que le pair a envoyé FIN sur le flux pour
 * indiquer qu'aucune donnée supplémentaire ne sera envoyée.
 */
switch (SSL_get_error(ssl, 0)) {
case SSL_ERROR_ZERO_RETURN:
    /* Achèvement normal du flux */
    break;
case SSL_ERROR_SSL:
    /*
     * Une erreur fatale du flux s'est produite. Il pourrait s'agir d'une
     * réinitialisation du flux - ou d'une défaillance sur la connexion sous-jacente.
     */
    switch (SSL_get_stream_read_state(ssl)) {
    case SSL_STREAM_STATE_RESET_REMOTE:
        printf("Réinitialisation du flux produite\n");
        /* Le flux a été réinitialisé mais la connexion est toujours saine. */
        break;
    case SSL_STREAM_STATE_CONN_CLOSED:
        printf("Connexion fermée\n");
        /* La connexion est déjà fermée. Ignorer SSL_shutdown() */
        goto end;
    default:
        printf("Échec inconnu du flux\n");
        break;
    }
    break;
default:
    /* Une autre erreur inattendue s'est produite */
    printf ("Échec de la lecture des données restantes\n");
    break;
}

Dans l'exemple de code ci-dessus, vous pouvez voir que SSL_ERROR_SSL indique une erreur fatale du flux. Nous pouvons utiliser SSL_get_stream_read_state(3) pour déterminer si le flux a été réinitialisé, ou si une autre erreur fatale s'est produite.

Fermeture de la connexion

Dans le tutoriel TLS, nous savions que le serveur avait fini d'envoyer des données car SSL_read_ex(3) retournait 0, et SSL_get_error(3) retournait SSL_ERROR_ZERO_RETURN. Il en va de même avec QUIC, sauf que SSL_ERROR_ZERO_RETURN doit être interprété légèrement différemment. Avec TLS, nous savions que cela signifiait que le serveur avait envoyé une alerte "close_notify". Aucune donnée supplémentaire ne serait envoyée par le serveur sur cette connexion.

Avec QUIC, cela signifie que le serveur a indiqué "FIN" sur le flux, ce qui signifie qu'il n'enverra plus aucune donnée sur ce flux. Cependant, cela ne nous donne que des informations sur le flux lui-même et ne nous dit rien sur la connexion sous-jacente. D'autres données pourraient encore être envoyées par le serveur sur un autre flux. De plus, bien que le serveur n'envoie plus de données au client, cela n'empêche pas le client d'envoyer plus de données au serveur.

Dans ce tutoriel, une fois que nous avons fini de lire les données du serveur sur le flux que nous utilisons, nous fermerons la connexion. Comme auparavant, nous le faisons via la fonction SSL_shutdown(3). Cet exemple pour QUIC est très similaire à la version TLS. Cependant, la fonction SSL_shutdown(3) devra être appelée plus d'une fois :

/*
 * Appeler SSL_shutdown() de manière répétée jusqu'à ce que la connexion soit
 * complètement fermée.
 */
do {
    ret = SSL_shutdown(ssl);
    if (ret < 0) {
        printf("Erreur lors de la fermeture : %d\n", ret);
        goto end;
    }
} while (ret != 1);

Le processus de fermeture se déroule en deux étapes. Dans la première étape, nous attendons que toutes les données que nous avons mises en tampon pour l'envoi sur n'importe quel flux aient été envoyées avec succès et acquittées par le pair, puis nous envoyons une CONNECTION_CLOSE au pair pour indiquer que la connexion n'est plus utilisable. Cela ferme immédiatement la connexion et aucune autre donnée ne peut être envoyée ou reçue. SSL_shutdown(3) retourne 0 une fois la première étape terminée.

Dans la seconde étape, la connexion entre dans un état de "fermeture". Les données d'application ne peuvent être ni envoyées ni reçues dans cet état, mais les paquets arrivant tardivement du pair seront traités correctement. Une fois cette étape terminée avec succès, SSL_shutdown(3) retournera 1 pour indiquer le succès.
