NOM

opendkim - Filtre de signature et de vérification DKIM pour les MTA

SYNTAXE

opendkim [-A] [-b modes] [-c canon] [-d domaine[,...]] [-D] [-e nom] [-f] [-F temps] [-k fichierclé] [-l] [-L min] [-n] [-o listerend] [-p socketspéc] [-P pidfile] [-Q] [-r] [-s sélecteur] [-S signalg] [-t fichiervérif] [-T sec] [-u userid[:groupe]] [-v] [-V] [-W] [-x fichierconf] [-X]

DESCRIPTION

opendkim implémente la norme DKIM pour la signature et/ou la vérification des messages électroniques par domaine.

opendkim utilise l'interface milter, initialement distribuée avec la version 8.11 de sendmail(8), pour fournir le service de signature et/ou de vérification DKIM pour les courriers transitant par un MTA compatible milter.

La plupart, sinon toutes, les options de ligne de commande listées ci-dessous peuvent également être définies via un fichier de configuration. Voir l'option -x pour plus de détails.

ENSEMBLES DE DONNÉES

Plusieurs paramètres de ligne de commande et de fichier de configuration feront référence à un « ensemble de données » comme valeurs. Cela fait référence à une chaîne qui contient soit la liste des valeurs souhaitées, soit un fichier qui les contient, soit (si activé lors de la compilation) une base de données contenant les données.

Certains ensembles de données exigent que la valeur contienne plus d'une entrée. La manière de procéder dépend du type d'ensemble de données utilisé.

Le type utilisé dépend du format de la chaîne de spécification. Notez que tous ces types ne sont pas nécessairement pris en charge pour toutes les installations ; la plupart d'entre eux dépendent de la disponibilité d'une bibliothèque tierce particulière au moment de la compilation.

En particulier :

a)
Si la chaîne commence par « file: », alors le reste de la chaîne est présumé faire référence à un fichier plat contenant les éléments de l'ensemble de données, un par ligne. Si une ligne contient des valeurs séparées par des espaces, la ligne est présumée définir une clé et sa valeur correspondante. Les lignes vides sont ignorées, et le caractère dièse (« # ») dénote le début d'un commentaire. Si une valeur contient plusieurs entrées, les entrées doivent être séparées par des deux-points.
b)
Si la chaîne commence par « refile: », alors le reste de la chaîne est présumé spécifier un fichier contenant un ensemble de motifs, un par ligne, et leurs valeurs associées. Le motif est pris depuis le début de la ligne jusqu'au premier espace, et la partie après cet espace est prise comme valeur à utiliser lorsque ce motif est mis en correspondance. Les motifs sont de simples motifs génériques, mettant en correspondance tout texte sauf que le caractère astérisque (« * ») est considéré comme un caractère générique. Si une valeur contient plusieurs entrées, les entrées doivent être séparées par des deux-points.
c)
Si la chaîne commence par « db: » et que le programme a été compilé avec le support de Sleepycat DB, alors le reste de la chaîne est présumé identifier une base de données Sleepycat contenant des clés et des valeurs correspondantes. Celles-ci ne peuvent être utilisées que pour tester l'appartenance à l'ensemble de données, ou pour stocker des clés et des valeurs correspondantes. Si une valeur contient plusieurs entrées, les entrées doivent être séparées par des deux-points.
d)
Si la chaîne commence par « dsn: » et que la bibliothèque OpenDKIM a été compilée pour prendre en charge ce type de base de données, alors le reste de la chaîne est un Nom de Source de Données décrivant le type, les paramètres d'emplacement et les informations d'identification d'accès à une base de données ODBC ou SQL. Le DSN est de la forme :

backend://[utilisateur[:motdepasse@][port+]hôte/basedonnées[/clé=valeur[?...]]

où backend est le nom d'un mécanisme de base de données supporté (par exemple, « mysql »), utilisateur et motdepasse sont des identifiants de connexion optionnels pour la base de données, port et hôte décrivent la destination d'une connexion TCP pour se connecter à cette base de données, basedonnées est le nom de la base de données à accéder, et les paires clé=valeur doivent spécifier au moins les valeurs « table », « keycol » et « datacol » spécifiant le nom de la table, le nom de la colonne à considérer comme clé, et le(s) nom(s) de la ou des colonnes à considérer comme valeurs (séparés par des virgules). Par exemple (tout sur une ligne) :

mysql:://dbuser:dbpass@3306+dbhost/odkim/table=macros
?keycol=host?datacol=v1,v2

définit une base de données MySQL écoutant au port 3306 sur l'hôte « dbhost » ; l'identifiant « dbuser » et le mot de passe « dbpass » doivent être utilisés pour accéder à la base de données ; le nom de la base de données est « odkim », et les données se trouvent dans les colonnes « host » (les clés) et « v1 » et « v2 » (les valeurs) dans la table « macros ». Cet exemple retournerait donc deux valeurs lorsqu'une correspondance est trouvée.

La clé peut également inclure une valeur « filter » qui sera incluse dans toutes les requêtes SQL générées sous forme de clause AND après la clause WHERE qui déclare les critères de recherche. Par exemple, étant donné la spécification DSN ci-dessus avec une valeur « filter » supplémentaire de « ID > 1000 », la requête SQL générée pour une recherche de « foo » ressemblerait à ceci :

SELECT v1,v2 FROM macros WHERE host = 'foo' AND ID > 1000

Aucune valeur dans le DSN ne peut contenir l'un des six caractères de ponctuation (« : », « / », « @ », « + », « ? » et « = ») utilisés pour délimiter les parties du DSN. Pour inclure de tels caractères dans une valeur, codez-les en style quoted-printable (par exemple, « =20 » sera traduit en un seul caractère d'espace). L'encodage des espaces est également conseillé.

e)
Si la chaîne commence par « ldap: », « ldaps: » ou « ldapi: », elle est présumée être un ensemble d'une ou plusieurs URL LDAP séparées par des espaces qui identifient un ensemble de serveurs à interroger. La première devrait être une URL LDAP complète RFC4516 indiquant un modèle de DN de base et une portée, un filtre et des noms d'attributs optionnels à utiliser dans les requêtes. Lors de la construction d'un modèle de DN ou d'un filtre, les jetons spéciaux « $d » et « $D » sont remplacés par la clé interrogée et la clé décomposée en composants, séparés par des points (« . »), chaque composant précédé de « dc= » et suivi de « , » (ainsi « example.com » deviendrait « dc=example,dc=com »). Si un ensemble de données nécessite plusieurs valeurs à retourner, les noms d'attributs appropriés doivent être donnés dans le bon ordre pour satisfaire de telles demandes.
f)
Si la chaîne commence par « lua: », elle est présumée faire référence à un fichier contenant un script Lua à exécuter chaque fois qu'une requête est effectuée. La clé de la requête est placée dans une variable globale appelée « query », que le script appelé peut alors accéder. Le script peut retourner un nombre quelconque de valeurs selon le type de requête effectuée.
g)
Si la chaîne commence par « memcache: », elle est présumée faire référence à une base de données de cache mémoire fournie par memcached. Le reste de la chaîne est une liste d'hôtes séparés par des virgules vers lesquels les tentatives de requête doivent être effectuées, chacun éventuellement suivi de « : » et d'un numéro de port ; cette liste doit être suivie d'un slash (« / ») et d'une chaîne qui sera utilisée pour préfixer les requêtes envoyées au cache. Par exemple :

memcache:localhost,otherhost/keyname

Ceci utiliserait soit « localhost » soit « otherhost » pour effectuer les requêtes, et toutes les chaînes envoyées à l'ensemble de données seraient préfixées par « keyname: ».

h)
Si la chaîne ne contient aucun de ces préfixes mais se termine par « .db », elle est présumée être une base de données Sleepycat DB comme décrit ci-dessus (si le support pour celle-ci est compilé).
i)
Si la chaîne ne contient aucun de ces préfixes mais commence par un slash (« / »), elle est présumée être un fichier plat comme décrit ci-dessus.
j)
Si la chaîne commence par « csl: », la chaîne est traitée comme une liste séparée par des virgules comme décrit dans m) ci-dessous.
k)
Si la chaîne commence par « erlang: », elle est présumée faire référence à une fonction appelée pour être
fait aux nœud(s) Erlang distribué(s) spécifié(s). La spécification est de la forme

erlang:node@host[,...]:cookie:module:function

où node[,...] est une liste de nœuds Erlang séparés par des virgules, cookie est le cookie pour les nœuds connus de la configuration Erlang distribuée, module est le nom du module Erlang où réside la fonction à appeler, function est le nom de la fonction Erlang à appeler. Par exemple, (tout sur une seule ligne) :

erlang:mynode@myhost,myothernode@myotherhost:
chocolate:dkim:lookup

rejoindra la configuration Erlang distribuée en se connectant à "mynode@myhost" ou "myothernode@myotherhost" (les connexions aux nœuds sont essayées dans l'ordre) en utilisant "chocolate" comme cookie, et utilisera la fonction "dkim:lookup/1" pour les recherches.

l)
Si la chaîne commence par "mdb:", elle fait référence à un répertoire qui contient une base de données mémoire, telle que fournie par libmdb d'OpenLDAP.
m)
Dans tous les autres cas, la chaîne est présumée être une liste séparée par des virgules. Les éléments de la liste sont soit des éléments de données simples qui font partie de l'ensemble, soit, dans le cas d'une entrée de la forme "x=y", sont stockés sous forme de paires clé-valeur comme décrit ci-dessus.

OPTIONS

-A
Redémarre automatiquement en cas d'échec. À utiliser avec prudence ; si le filtre échoue instantanément après son démarrage, cela peut entraîner une boucle serrée de fork(2). Cela peut être atténué en utilisant certaines valeurs dans le fichier de configuration pour limiter les redémarrages. Voir opendkim.conf(5).
-b modes
Sélectionne les modes de fonctionnement. modes est une concaténation de caractères indiquant le(s) mode(s) de fonctionnement souhaité(s). Les modes valides sont s (signataire) et v (vérificateur). La valeur par défaut est sv sauf en mode test (voir -t ci-dessous) auquel cas la valeur par défaut est v.
-c canon
Sélectionne la ou les méthodes de canonicalisation à utiliser lors de la signature des messages. Lors de la vérification, l'en-tête DKIM-Signature du message spécifie la méthode de canonicalisation. Les valeurs reconnues sont relaxed et simple telles que définies par la spécification DKIM. La valeur par défaut est simple. La valeur peut inclure deux canonicalisations différentes séparées par un caractère slash ("/"), auquel cas la première sera appliquée aux en-têtes et la seconde au corps.
-d dataset
Un ensemble de domaines dont les e-mails doivent être signés par ce filtre. Les e-mails d'autres domaines seront vérifiés plutôt que d'être signés.
-D
Signe également les sous-domaines de ceux listés par l'option -d ainsi que les domaines réels.
-e name
Extrait la valeur de name du fichier de configuration (s'il y en a un).
-f
Normalement, opendkim se détache et se termine immédiatement, laissant le service s'exécuter en arrière-plan. Ce drapeau supprime ce comportement afin qu'il s'exécute au premier plan.
-F time
Spécifie une heure fixe à utiliser lors de la génération des signatures. Ignoré sauf si utilisé en conjonction avec -t (voir ci-dessous). L'heure doit être exprimée dans le format time_t habituel de UNIX (secondes depuis l'époque).
-k keyfile
Indique l'emplacement d'une clé privée au format PEM à utiliser pour signer tous les messages. Ignoré si un fichier de configuration est référencé qui définit une KeyTable.
-l
Journalise via des appels à syslog(3) toute activité intéressante.
-L min[%+]
Indique au code de vérification d'échouer les messages pour lesquels une signature partielle a été reçue. Il existe trois formats possibles : min indiquant qu'au moins min octets du message doivent être signés (ou si le message est plus petit que min, alors tout doit être signé) ; min% exigeant qu'au moins min pour cent du message reçu doivent être signés ; et min+ signifiant qu'il ne peut pas y avoir plus de min octets de données non signées ajoutées au message pour qu'il soit considéré comme valide.
-n
Analyse le fichier de configuration et les arguments de la ligne de commande, signale toutes les erreurs trouvées, puis se termine. La valeur de sortie sera 0 si le filtre démarre sans plainte, ou non nulle sinon.
-o dataset
Spécifie une liste d'en-têtes qui doivent être omis lors de la génération des signatures. Si une entrée de la liste nomme un en-tête qui est requis par la spécification DKIM, l'entrée est ignorée. Un ensemble d'en-têtes est listé dans la spécification DKIM comme "SHOULD NOT" être signé ; la liste par défaut pour ce paramètre contient ces en-têtes (Return-Path, Received, Comments, Keywords, Bcc, Resent-Bcc et DKIM-Signature). Pour omettre aucun en-tête, utilisez simplement la chaîne "-" (ou toute chaîne qui ne correspondra à aucun en-tête).
-p socketspec
Spécifie le socket qui doit être établi par le filtre pour recevoir les connexions de sendmail(8) afin de fournir un service. socketspec est sous l'une des deux formes : local:path qui crée un socket de domaine UNIX au path spécifié, ou inet:port[@host] ou inet6:port[@host] qui crée un socket TCP sur le port spécifié en utilisant la famille de protocoles demandée. Si l' host n'est pas donné comme nom d'hôte ou adresse IP, le socket écoutera sur toutes les interfaces. Une adresse IP littérale doit être entourée de crochets. Si aucun type de socket n'est spécifié, local est supposé, signifiant que le paramètre est interprété comme un chemin où le socket doit être créé. Ce paramètre est obligatoire ici ou dans le fichier de configuration.
-P pidfile
Spécifie un fichier dans lequel le filtre doit écrire son ID de processus au démarrage.
-Q
Mode test de requête. Le filtre lira deux lignes de l'entrée standard, l'une contenant une description de base de données à ouvrir et l'autre une chaîne de la forme "q/n" où "q" est la requête à effectuer et "n" est le nombre de champs à récupérer.
-r
Vérifie tous les messages pour leur conformité aux exigences de comptage d'en-têtes RFC5322. Les messages non conformes sont rejetés.
-s selector
Définit le nom du sélecteur à utiliser lors de la signature des messages. Voir la spécification DKIM pour les détails.
-S signalg
Sélectionne l'algorithme de signature à utiliser lors de la génération des signatures. Utilisez 'opendkim -V' pour voir la liste des algorithmes pris en charge. La valeur par défaut est rsa-sha256 s'il est disponible, sinon ce sera rsa-sha1.
-t testfiles
Évalue (vérifie) un ou plusieurs messages formatés RFC5322 trouvés dans testfiles et se termine. La valeur de testfiles doit être une liste séparée par des virgules d'un ou plusieurs noms de fichiers, dont l'un peut être "-" si le message doit être lu depuis l'entrée standard.
-T secs
Définit le délai d'attente DNS en secondes. Une valeur de 0 provoque une attente infinie. La valeur par défaut est 5. Ignoré si un package de résolution asynchrone n'est pas utilisé. Voir également la section NOTES ci-dessous.
-u userid[:group]
Tente de devenir l' userid spécifié avant de commencer les opérations. Le processus se verra attribuer tous les groupes et l'ID de groupe primaire de l' userid nommé, sauf si un group alternatif est spécifié. Voir la section PERMISSIONS DE FICHIER pour plus d'informations.
-v
Augmente la sortie détaillée pendant le mode test (voir -t ci-dessus). Peut être spécifié plus d'une fois pour demander des quantités croissantes de sortie.
-V
Affiche le numéro de version et les algorithmes de canonicalisation et de signature pris en charge, puis se termine sans rien faire d'autre.
-W
Si la journalisation est activée (voir -l ci-dessus), émet une journalisation très détaillée sur la logique derrière la décision du filtre de signer ou de vérifier un message. Le "W" signifie "Why?!" puisque la logique derrière la décision n'est pas triviale et peut être déroutante pour les administrateurs qui ne connaissent pas son fonctionnement. Une description de la manière dont la décision est prise se trouve dans la section OPÉRATION de ce document. Cela entraîne une augmentation significative de la quantité de données de journal générées pour chaque message, elle doit donc être limitée à une utilisation de débogage et ne pas être activée pour le fonctionnement général.
-x configfile
Lit le fichier de configuration nommé. Voir la page de manuel opendkim.conf(5) pour les détails. Les valeurs du fichier de configuration sont remplacées lorsque leurs équivalents sont fournis sur la ligne de commande jusqu'à ce qu'un rechargement de configuration se produise. La section OPÉRATION décrit comment les rechargements sont déclenchés. La valeur par défaut est de lire un fichier de configuration à partir de /etc/opendkim/opendkim.conf s'il existe, ou sinon d'appliquer les valeurs par défaut à toutes les valeurs.
-X
Tolère les éléments du fichier de configuration qui ont été marqués en interne comme "dépréciés". Normalement, lorsqu'un élément du fichier de configuration est supprimé du package, il est marqué de cette manière pendant au moins un cycle de publication complet. La présence d'un élément de fichier de configuration déprécié provoque généralement une erreur du filtre qui refuse de démarrer. La définition de ce drapeau permettra au filtre de démarrer et un avertissement sera consigné. Dans une version future où l'élément sera complètement supprimé, une erreur différente se produira et il ne sera pas possible de démarrer le filtre. L'utilisation de ce drapeau N'EST PAS RECOMMANDÉE ; cela pourrait masquer efficacement un changement de configuration majeur avec de graves implications de sécurité.

NOM

opendkim — un démons de signature et de vérification DKIM

SYNOPIS

opendkim [-b] [-c configfile] [-d domain] [-e] [-f] [-h] [-M] [-n] [-p socket] [-q] [-s selector] [-t] [-u user] [-v]

DESCRIPTION

opendkim est un démons de serveur de messagerie qui peut être utilisé pour signer des messages électroniques sortants à l'aide de la clé privée associée à un domaine, et pour vérifier les messages entrants qui sont signés à l'aide de DKIM (DomainKeys Identified Mail).

Le démon fonctionne comme un filtre de messagerie via l'interface Milter de Sendmail. Lorsqu'il est configuré pour signer des messages, il ajoute une en-tête DKIM-Signature: au message en utilisant la clé privée fournie. Lorsqu'il est configuré pour vérifier des messages, il ajoute une en-tête Authentication-Results: indiquant le succès ou l'échec de la vérification.

Ce démon peut être configuré pour signer des messages sur la base de champs d'en-tête spécifiques, tels que l'adresse de l'expéditeur, ou pour vérifier des messages quel que soit leur domaine.

ENSEMBLES DE DONNÉES

Les ensembles de données suivants peuvent être spécifiés dans le fichier de configuration ou sur la ligne de commande.

KeyFile
Chemin d'accès au fichier contenant la clé privée utilisée pour signer les messages. Ce réglage est requis lorsque le démon est configuré pour signer des messages.
KeyTable
Un fichier qui mappe les noms d'hôtes ou les adresses IP aux clés privées à utiliser pour signer les messages. Ceci est utile lorsque le démon doit signer des messages pour plusieurs domaines avec des clés différentes. Le format est nom_d’hôte:nom_de_clé, où nom_d’hôte peut être un nom d'hôte, une adresse IP, ou une adresse IP avec un masque CIDR. nom_de_clé est une chaîne qui sera recherchée dans le fichier KeyFile.
Domain
Le domaine pour lequel signer les messages. Ceci est utilisé lorsque le démon est configuré pour signer des messages et que le champ KeyTable n'est pas utilisé.
Selector
Le sélecteur DNS à utiliser lors de la publication de la clé publique. Ceci est utilisé lorsque le démon est configuré pour signer des messages et que le champ KeyTable n'est pas utilisé.
SenderHeaders
Une liste de champs d'en-tête qui seront utilisés pour déterminer le domaine de l'expéditeur lors de la signature des messages. Les champs spécifiés sont testés dans l'ordre jusqu'à ce qu'un domaine soit trouvé. Si aucun domaine n'est trouvé, le démon utilise le domaine spécifié par le paramètre Domain.
InternalHosts
Un fichier contenant une liste d'adresses IP ou de noms d'hôtes qui sont considérés comme internes. Les messages provenant de ces hôtes seront signés même s'ils ne sont pas envoyés depuis le domaine configuré.
AllowSHA1InDNS
Autorise l'utilisation de SHA1 lors de la recherche de clés publiques DNS. Par défaut, seul SHA256 est autorisé.
Canonicalization
Définit la méthode de canonicalisation à utiliser lors de la génération de la signature. Les valeurs possibles sont simple et relaxed/simple. La valeur par défaut est relaxed/simple.
UserID
L'utilisateur sous lequel le démon doit s'exécuter après avoir ouvert ses fichiers de configuration et ses clés. Utile pour lancer le démon en tant qu'utilisateur non-root.
UMask
Le masque de création de fichier utilisé par le démon. Utile pour contrôler les permissions des fichiers temporaires créés par le démon.
PidFile
Chemin d'accès au fichier dans lequel le PID du démon doit être écrit. Utile pour gérer le processus du démon.
Socket
L'adresse de la socket sur laquelle le démon doit écouter les connexions Milter. Il peut s'agir d'une socket de domaine UNIX ou d'une socket TCP/IP.
MTAs
Une liste d'émons MTA qui sont autorisés à se connecter au démon. Ceci est utilisé pour restreindre l'accès au démon.
MacroList
Une liste de macros MTA qui doivent être définies pour que le démon traite un message. Ceci est utilisé pour contrôler les messages qui sont signés ou vérifiés.
Mode
Le mode de fonctionnement du démon. Les valeurs possibles sont sign (pour signer les messages) et verify (pour vérifier les messages). La valeur par défaut est sign.
Database
Le type de base de données à utiliser pour stocker les clés publiques. Les valeurs possibles sont hash (pour un fichier plat) ou ldap (pour un serveur LDAP).
QueryCache
Définit la taille du cache DNS. Si ce paramètre est défini, le démon mettra en cache les résultats des requêtes DNS pour améliorer les performances.
AutoRestart
Si ce paramètre est défini sur true, le démon tentera de redémarrer automatiquement en cas de crash.
AutoRestartCount
Le nombre de fois que le démon tentera de redémarrer automatiquement avant d'abandonner.
AutoRestartRate
La fréquence maximale des redémarrages automatiques, en secondes.
MilterDebug
Définit le niveau de débogage pour les messages Milter. Utile pour le dépannage.
TestPublicKeys
Si ce paramètre est défini sur true, le démon testera les clés publiques avec des tests spécifiques lors de la vérification.
StrictTestMode
Si ce paramètre est défini sur true, le démon appliquera des vérifications plus strictes lors des tests.
POPDBFile
Chemin d'accès à la base de données des adresses IP POP utilisées pour l'authentification.
Quarantine
Définit le répertoire dans lequel les messages non signés ou échouant à la vérification doivent être mis en quarantaine.
ChangeRootDirectory
Le répertoire racine vers lequel le processus doit se déplacer après avoir chargé la configuration et les clés. Utile pour des raisons de sécurité.

OPTIONS

Les options suivantes sont disponibles sur la ligne de commande.

-b
Utilise le mode d'authentification de l'expéditeur pour la vérification. Si cette option est activée, le démon vérifiera que l'adresse de l'expéditeur dans le champ d'en-tête From: correspond au domaine pour lequel la signature est vérifiée.
-c configfile
Spécifie un fichier de configuration alternatif à utiliser. Si cette option n'est pas spécifiée, le démon recherche par défaut les fichiers de configuration dans /etc/opendkim.conf.
-d domain
Spécifie le domaine pour lequel signer les messages. Ceci remplace le réglage Domain dans le fichier de configuration.
-e
Active le mode d'extension pour les signatures DKIM. Cela signifie que les signatures générées incluront des champs supplémentaires pour fournir plus d'informations sur la signature.
-f
Force la signature de tous les messages, même si le domaine de l'expéditeur ne correspond pas à celui configuré. À utiliser avec précaution.
-h
Affiche un message d'aide résumant les options disponibles.
-M
Signale le démarrage du démon au système pour qu'il puisse être surveillé par systemd ou d'autres systèmes de supervision. Le démon ne se déconnectera pas du terminal.
-n
Désactive la signature des messages. Le démon ne fera qu'effectuer des vérifications.
-p socket
Spécifie le socket sur lequel le démon doit écouter les connexions Milter. Ceci remplace le réglage Socket dans le fichier de configuration.
-q
Active le mode de mise en quarantaine. Les messages non signés ou échouant à la vérification seront déplacés vers le répertoire spécifié par Quarantine.
-s selector
Spécifie le sélecteur DNS à utiliser pour la signature des messages. Ceci remplace le réglage Selector dans le fichier de configuration.
-t timeout
Spécifie le délai d'attente en secondes pour les opérations DNS. La valeur par défaut est 5.
-u user
Spécifie l'utilisateur sous lequel le démon doit s'exécuter. Ceci remplace le réglage UserID dans le fichier de configuration.
-v
Active le mode verbeux, affichant plus d'informations sur le fonctionnement du démon.

OPÉRATION

Le démon opendkim fonctionne comme un filtre Milter pour Sendmail. Il intercepte les messages électroniques et applique les règles de signature ou de vérification DKIM.

Les messages sont signés ou vérifiés selon les critères suivants : (1) le domaine de l'adresse From: (s'il est présent) doit être listé via le commutateur de ligne de commande -d ou le réglage du fichier de configuration Domain, et (2) (a) le client se connectant au MTA doit s'être authentifié, ou (b) le client se connectant au MTA doit être listé dans le fichier référencé par le réglage du fichier de configuration InternalHosts (ou être dans la liste par défaut pour cette option), ou (c) le client doit être connecté à un port de démon nommé par le réglage du fichier de configuration MTAs, ou (d) le MTA doit avoir défini une ou plusieurs macros correspondant aux critères définis par le réglage du fichier de configuration MacroList.

Pour (a) ci-dessus, le test consiste à déterminer si la macro MTA "{auth_type}" est définie et contient une valeur non vide. Cela signifie que le MTA doit passer la valeur de cette macro au filtre avant ou pendant la phase de fin d'en-tête (EOH) afin que sa valeur puisse être testée. Consultez la documentation de configuration de votre MTA pour plus de détails.

Pour (1) ci-dessus, d'autres champs d'en-tête peuvent être sélectionnés en utilisant le réglage du fichier de configuration SenderHeaders. Voir opendkim.conf(5) pour plus d'informations.

Lors de la signature d'un message, un en-tête DKIM-Signature: sera ajouté au début du message. La signature est calculée en utilisant la clé privée fournie. Vous devez utiliser une version de sendmail(8) suffisamment récente pour pouvoir effectuer des opérations d'ajout d'en-tête (8.13.0 ou ultérieure).

Lors de la vérification d'un message, un en-tête Authentication-Results: sera ajouté pour indiquer la présence d'une signature et si elle a pu être validée par rapport au corps du message en utilisant la clé publique annoncée par le serveur de noms de l'expéditeur. La valeur de cet en-tête peut être utilisée par les agents utilisateur de courrier pour trier ou supprimer les messages qui n'ont pas été signés ou qui n'ont pas pu être vérifiés.

À la réception de SIGUSR1, si le filtre a été démarré avec un fichier de configuration, celui-ci sera relu et les nouvelles valeurs utilisées. Notez que les substitutions de ligne de commande fournies au démarrage seront perdues lorsque cela se produira. De plus, les valeurs de fichier de configuration suivantes (et leurs éléments de ligne de commande correspondants, le cas échéant) ne sont pas rechargées par ce processus : AutoRestart (-A), AutoRestartCount, AutoRestartRate, Background, MilterDebug, PidFile (-P), POPDBFile, Quarantine (-q), QueryCache, Socket (-p), StrictTestMode, TestPublicKeys, UMask, UserID (-u). Le filtre ne vérifie pas automatiquement le fichier de configuration pour les changements et ne recharge pas.

MACROS MTA

opendkim utilise trois macros fournies par le MTA, plus celles demandées par la configuration. Les trois principales sont : « i » (l'ID d'enveloppe, également connu sous le nom d'ID de travail ou d'ID de file d'attente), qui est utilisé pour la journalisation ; « daemon_name » (le nom symbolique donné à l'instance MTA qui a accepté la connexion), qui est utilisé lors de l'exécution de tests par rapport à tout réglage « MTAs » utilisé ; et « auth_type », qui est utilisé pour déterminer si le client SMTP s'est authentifié auprès du MTA. Si le MTA ne les fournit pas à opendkim, il ne peut pas appliquer leurs tests correspondants ni faire une journalisation utile. Consultez la documentation de configuration de votre MTA pour savoir comment ajuster sa configuration si tout ou partie de ces macros ne sont pas disponibles.

PERMISSIONS FICHIER

Lorsque le filtre est démarré en tant que superutilisateur et que le paramètre UserID (-u) est utilisé, le filtre abandonne ses privilèges root en changeant d'utilisateur vers l'utilisateur spécifié après que les étapes suivantes ont été effectuées : (1) le fichier de configuration (le cas échéant) est chargé ; (2) si le paramètre KeyFile (-k) est utilisé, cette clé est chargée en mémoire ; (3) tous les ensembles de données du fichier de configuration sont ouverts, et ceux qui sont basés sur des fichiers plats sont également lus en mémoire ; et (4) si ChangeRootDirectory est défini, la racine du processus est changée pour ce répertoire. Cela signifie que lors du rechargement de la configuration, le filtre n'accédera pas à ces fichiers ni au fichier de configuration en tant que superutilisateur (et éventuellement depuis une racine différente), et que tout fichier de clé référencé par la KeyTable sera également accessible par le nouvel utilisateur.

Par conséquent, les clés référencées par la KeyTable doivent toujours être accessibles en lecture par l'utilisateur non privilégié. De plus, les rechargements à l'exécution ne sont pas possibles si d'autres fichiers ne sont pas lisibles par l'utilisateur non privilégié.

ENVIRONNEMENT

La ou les variables d'environnement suivantes peuvent être utilisées pour ajuster le comportement de ce filtre :

DKIM_TMPDIR
Le répertoire à utiliser lors de la création de fichiers temporaires. La valeur par défaut est /tmp.

NOTES

Lors de l'utilisation de délais d'attente DNS (voir l'option -T ci-dessus), assurez-vous de ne pas utiliser un délai d'attente supérieur à celui utilisé pour l'interaction entre sendmail et le filtre. Sinon, le MTA pourrait abandonner un message en attendant une réponse du filtre, qui attend à son tour une réponse DNS.

La base de données d'authentification POP est attendue comme un fichier Sleepycat DB (anciennement connu sous le nom de Berkeley DB) au format hash avec des clés contenant l'adresse IP sous forme de texte sans NULL de fin. Les valeurs de ces enregistrements ne sont pas vérifiées ; seule l'existence de tels enregistrements est pertinente. Le filtre tentera d'établir un verrouillage partagé sur la base de données avant d'en lire, de sorte que tout programme qui écrit dans la base de données doit limiter son utilisation des verrous au minimum, sinon ce filtre semblera bloqué en attendant la fin de l'opération de verrouillage.

Les fonctionnalités qui impliquent la spécification d'adresses IPv4 ou de blocs CIDR utiliseront la fonction inet_addr(3) pour analyser ces informations. Les utilisateurs doivent se familiariser avec la manière dont cette fonction gère les cas non triviaux (par exemple, « 192.0.2/24 » et « 192.0.2.0/24 » ne sont pas la même chose).
