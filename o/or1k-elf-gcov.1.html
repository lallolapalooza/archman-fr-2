DESCRIPTION

gcov est un programme de test de couverture. Utilisez-le en conjonction avec GCC pour analyser vos programmes afin de créer un code plus efficace et plus rapide, et pour découvrir les parties non testées de votre programme. Vous pouvez utiliser gcov comme un outil de profilage pour déterminer où vos efforts d'optimisation auront le plus d'impact. Vous pouvez également utiliser gcov avec l'autre outil de profilage, gprof, pour évaluer quelles parties de votre code consomment le plus de temps de calcul.

Les outils de profilage vous aident à analyser les performances de votre code. En utilisant un profileur tel que gcov ou gprof, vous pouvez obtenir des statistiques de performance de base, telles que :

  • la fréquence d'exécution de chaque ligne de code
  • quelles lignes de code sont effectivement exécutées
  • le temps de calcul utilisé par chaque section de code

Une fois que vous connaissez ces informations sur le fonctionnement de votre code une fois compilé, vous pouvez examiner chaque module pour voir les modules qui devraient être optimisés. gcov vous aide à déterminer où concentrer vos efforts d'optimisation.

Les développeurs de logiciels utilisent également les tests de couverture en conjonction avec des suites de tests, pour s'assurer que le logiciel est réellement suffisamment bon pour une publication. Les suites de tests peuvent vérifier qu'un programme fonctionne comme prévu ; un programme de couverture vérifie quelle partie du programme est exercée par la suite de tests. Les développeurs peuvent alors déterminer quels types de cas de test doivent être ajoutés aux suites de tests pour créer à la fois des tests meilleurs et un produit final meilleur.

Vous devriez compiler votre code sans optimisation si vous prévoyez d'utiliser gcov, car l'optimisation, en combinant certaines lignes de code en une seule fonction, peut ne pas vous fournir autant d'informations que nécessaire pour rechercher les "points chauds" où le code utilise une grande quantité de temps de calcul. De même, comme gcov accumule des statistiques par ligne (à la plus basse résolution), il fonctionne mieux avec un style de programmation qui place une seule instruction par ligne. Si vous utilisez des macros complexes qui se développent en boucles ou en autres structures de contrôle, les statistiques sont moins utiles --- elles ne rendent compte que de la ligne où apparaît l'appel de macro. Si vos macros complexes se comportent comme des fonctions, vous pouvez les remplacer par des fonctions `inline` pour résoudre ce problème.

gcov crée un fichier journal appelé fichier_source.gcov qui indique combien de fois chaque ligne d'un fichier source fichier_source.c a été exécutée. Vous pouvez utiliser ces fichiers journaux avec gprof pour affiner les performances de vos programmes. gprof donne des informations de temps que vous pouvez utiliser avec les informations obtenues de gcov.

gcov ne fonctionne que sur le code compilé avec GCC. Il n'est pas compatible avec tout autre mécanisme de profilage ou de test de couverture.

OPTIONS

-a
--all-blocks
Écrit les comptes d'exécution individuels pour chaque bloc de base. Normalement, gcov ne fournit les comptes d'exécution que pour les blocs principaux d'une ligne. Avec cette option, vous pouvez déterminer si des blocs au sein d'une même ligne ne sont pas exécutés.
-b
--branch-probabilities
Écrit les fréquences de branchement dans le fichier de sortie, et écrit un résumé des branches sur la sortie standard. Cette option vous permet de voir à quelle fréquence chaque branche de votre programme a été prise. Les branches inconditionnelles ne seront pas affichées, sauf si l'option -u est donnée.
-c
--branch-counts
Écrit les fréquences de branchement sous forme de nombre de branches prises, plutôt que sous forme de pourcentage de branches prises.
-g
--conditions
Écrit la couverture des conditions dans le fichier de sortie, et écrit un résumé des conditions sur la sortie standard. Cette option vous permet de voir si les conditions de votre programme ont eu au moins une fois un effet indépendant sur le résultat de l'expression booléenne (couverture conditionnelle modifiée/décisionnelle). Cela nécessite de compiler la source avec -fcondition-coverage.
-d
--display-progress
Affiche la progression sur la sortie standard.
-f
--function-summaries
Produit des résumés pour chaque fonction en plus du résumé au niveau du fichier.
-h
--help
Affiche l'aide sur l'utilisation de gcov (sur la sortie standard), et quitte sans effectuer d'autres traitements.
-j
--json-format
Produit le fichier gcov dans un format intermédiaire JSON facile à analyser qui ne nécessite pas de code source pour la génération. Le fichier JSON est compressé avec l'algorithme de compression gzip et les fichiers ont l'extension .gcov.json.gz.

La structure du JSON est la suivante :

{
  "current_working_directory": "foo/bar",
  "data_file": "a.out",
  "format_version": "2",
  "gcc_version": "11.1.1 20210510"
  "files": ["$file"]
}

Les champs de l'élément racine ont les sémantiques suivantes :

  • current_working_directory : répertoire de travail dans lequel une unité de compilation a été compilée
  • data_file : nom du fichier de données (GCDA)
  • format_version : version sémantique du format

    Changements dans la version 2 :

*
calls : des informations sur les appels de fonction sont ajoutées
*
gcc_version : version du compilateur GCC

Chaque file a la forme suivante :

{
  "file": "a.c",
  "functions": ["$function"],
  "lines": ["$line"]
}

Les champs de l'élément file ont les sémantiques suivantes :

*
file_name : nom du fichier source

Chaque function a la forme suivante :

{
  "blocks": 2,
  "blocks_executed": 2,
  "demangled_name": "foo",
  "end_column": 1,
  "end_line": 4,
  "execution_count": 1,
  "name": "foo",
  "start_column": 5,
  "start_line": 1
}

Les champs de l'élément function ont les sémantiques suivantes :

  • blocks : nombre de blocs dans la fonction
  • blocks_executed : nombre de blocs exécutés de la fonction
  • demangled_name : nom démêlé de la fonction
  • end_column : colonne dans le fichier source où la fonction se termine
  • end_line : ligne dans le fichier source où la fonction se termine
  • execution_count : nombre d'exécutions de la fonction
  • name : nom de la fonction
  • start_column : colonne dans le fichier source où la fonction commence
  • start_line : ligne dans le fichier source où la fonction commence

Chaque line a la forme suivante :

{
  "blocks": ["$block"],
  "count": 1,
  "file": "a.c",
  "line_number": 2
}

Les champs de l'élément line ont les sémantiques suivantes :

  • blocks : liste des blocs qui sont dans la ligne
  • count : nombre d'exécutions de la ligne
  • file : nom du fichier source
  • line_number : numéro de ligne dans le fichier source

Chaque block a la forme suivante :

{
  "count": 1,
  "line_number": 2
}

Les champs de l'élément block ont les sémantiques suivantes :

  • count : nombre d'exécutions du bloc
  • line_number : numéro de ligne dans le fichier source
-H
--human-readable
Affiche les données de couverture de manière lisible par l'homme. Peut être utilisé avec l'option -j ou --json-format.
-k
--use-colors
Affiche les données de couverture avec des couleurs.
-l
--long-file-names
Ne supprime pas les préfixes de répertoire des noms de fichiers. Par défaut, gcov supprime les préfixes de répertoire des noms de fichiers. Ceci désactive cette fonctionnalité.
-m
--demangled-names
Affiche les noms démêlés des fonctions.
-n
--no-output
Ne produit aucun fichier de sortie. Utile uniquement si vous souhaitez supprimer les fichiers de sortie qui seraient autrement générés.
-o
--object-directory répertoire|fichier
Ce commutateur permet de spécifier le répertoire ou le fichier qui contient les fichiers objets et les fichiers de données de couverture. Ceci est utile si vous avez compilé vos fichiers sources dans un répertoire différent du répertoire courant.
-p
--preserve-paths
N'enleve pas les préfixes de chemin des noms de fichiers. Par défaut, gcov supprime les préfixes de chemin des noms de fichiers. Ceci désactive cette fonctionnalité.
-q
--use-hotness-colors
Affiche les données de couverture avec des couleurs basées sur la "chaleur" (fréquence d'exécution).
-r
--relative-only
Ne montre que les chemins relatifs.
-s
--source-prefix répertoire
Supprime le préfixe de répertoire spécifié des noms de fichiers sources lors de la génération des rapports. Utile pour s'assurer que les rapports sont cohérents, quel que soit le répertoire de build.
-t
--stdout
Écrit la sortie sur la sortie standard au lieu de créer des fichiers .gcov.
-u
--unconditional-branches
Inclut les branches inconditionnelles dans le rapport de couverture des branches. Par défaut, seules les branches conditionnelles sont rapportées. Utilisez cette option avec -b pour voir toutes les branches.
-x
--hash-filenames
Utilise des noms de fichiers hachés pour la sortie.
-v
--version
Affiche la version de gcov et quitte.

EXEMPLES

Pour générer un rapport de couverture pour un programme nommé myprog compilé avec GCC, vous pouvez utiliser la commande suivante :

Compilez d'abord votre programme avec l'option de débogage et l'option de couverture activée :

gcc -fprofile-arcs -ftest-coverage myprog.c -o myprog

Exécutez votre programme pour générer les données de couverture :

./myprog

Générez ensuite le rapport de couverture avec gcov :

gcov myprog.c

Cela créera un fichier nommé myprog.c.gcov contenant les informations de couverture pour votre fichier source.

Pour inclure les probabilités de branchement, utilisez :

gcov -b myprog.c

Pour obtenir un format JSON :

gcov -j myprog.c

Pour obtenir un rapport lisible par l'homme en JSON :

gcov -jH myprog.c

En-tête du fichier source où la fonction commence
  • start_line : ligne dans le fichier source où la fonction commence

    • Notez que les numéros de ligne et de colonne commencent à 1. Dans l'implémentation actuelle, start_line et start_column n'incluent pas les paramètres de modèle et le type de retour de tête, mais cela devrait être corrigé à l'avenir.

    Chaque line a la forme suivante :

    {
  "block_ids": ["$block_id"],
  "branches": ["$branch"],
  "calls": ["$call"],
  "count": 2,
  "conditions": ["$condition"],
  "line_number": 15,
  "unexecuted_block": false,
  "function_name": "foo",
}

    Les branches et les appels ne sont présents qu'avec l'option -b. Les champs de l'élément line ont la sémantique suivante :

    • block_ids : identifiants des blocs de base appartenant à la ligne
    • count : nombre d'exécutions de la ligne
    • line_number : numéro de ligne
    • unexecuted_block : indicateur indiquant si la ligne contient un bloc non exécuté (toutes les instructions de la ligne ne sont pas exécutées)
    • function_name : nom d'une fonction à laquelle appartient cette line (peut ne pas être défini pour une ligne avec des instructions inline)

    Chaque branch a la forme suivante :

    {
  "count": 11,
  "destination_block_id": 17,
  "fallthrough": true,
  "source_block_id": 13,
  "throw": false
}

    Les champs de l'élément branch ont la sémantique suivante :

    • count : nombre d'exécutions de la branche
    • fallthrough : true si la branche est une branche de chute
    • throw : true si la branche est une branche exceptionnelle
    • isource_block_id : identifiant du bloc de base où cette branche se produit
    • destination_block_id : identifiant du bloc de base vers lequel cette branche saute

    Chaque call a la forme suivante :

    {
  "destination_block_id": 1,
  "returned": 11,
  "source_block_id": 13
}

    Les champs de l'élément call ont la sémantique suivante :

    • returned : nombre de fois qu'un appel de fonction est revenu (le nombre d'appels est égal à line::count)
    • isource_block_id : identifiant du bloc de base où cet appel se produit
    • destination_block_id : identifiant du bloc de base où l'exécution continue après le retour

    Chaque condition a la forme suivante :

    {
  "count": 4,
  "covered": 2,
  "not_covered_false": [],
  "not_covered_true": [0, 1],
}

    Les champs de l'élément condition ont la sémantique suivante :

    • count : nombre de résultats de condition dans cette expression
    • covered : nombre de résultats de condition couverts dans cette expression
    • not_covered_true : termes, par index, qui n'ont pas été vus comme vrais dans cette expression
    • not_covered_false : termes, par index, qui n'ont pas été vus comme faux dans cette expression
    -H
    --human-readable
    Écrire les comptes dans un format lisible par l'homme (comme 24,6 k).
    -k
    --use-colors
    Utiliser des couleurs pour les lignes de code ayant une couverture nulle. Nous utilisons la couleur rouge pour les lignes non exceptionnelles et le cyan pour les lignes exceptionnelles. Les mêmes couleurs sont utilisées pour les blocs de base avec l'option -a.

    --long-file-names
    Créer des noms de fichiers longs pour les fichiers source inclus. Cela peut être utile si x.h est inclus dans plusieurs fichiers source et que vous souhaitez voir les contributions individuelles. Si vous utilisez l'option -p, les noms des fichiers incluant et inclus seront des chemins complets.
    -m
    --demangled-names
    Afficher les noms de fonctions démêlés dans la sortie. Par défaut, les noms de fonctions sont emmêlés.
    -n

    -o directory|file
    --object-directory directory

Si un répertoire est spécifié, les fichiers de données se trouvent dans ce répertoire et sont nommés d'après le nom du fichier d'entrée, sans son extension. Si un fichier est spécifié ici, les fichiers de données sont nommés d'après ce fichier, sans son extension.

    --preserve-paths
    Conserver les informations de chemin complètes dans les noms des fichiers .gcov générés. Sans cette option, seul le composant nom de fichier est utilisé. Avec cette option, tous les répertoires sont utilisés, avec des caractères / traduits en caractères #, les composants de répertoire . supprimés et les composants .. non supprimables renommés en ^. Ceci est utile si les fichiers source se trouvent dans plusieurs répertoires différents.
    -q
    --use-hotness-colors
    Émettre une sortie colorée de type perf pour les lignes chaudes. La légende de l'échelle de couleurs est imprimée tout au début du fichier de sortie.
    -r
    --relative-only
    N'afficher que les informations sur les fichiers source avec un chemin relatif (après élision du préfixe source). Les chemins absolus sont généralement des fichiers d'en-tête système et la couverture des fonctions inline qu'ils contiennent n'est normalement pas intéressante.
    -s directory
    --source-prefix directory
    Un préfixe pour les noms de fichiers source à supprimer lors de la génération des fichiers de couverture de sortie. Cette option est utile lors de la compilation dans un répertoire séparé, et que le chemin d'accès au répertoire source n'est pas souhaité lors de la détermination des noms de fichiers de sortie. Notez que cette détection de préfixe est appliquée avant de déterminer si le fichier source est absolu.
    -t
    --stdout
    Sortie vers la sortie standard au lieu des fichiers de sortie.
    -u
    --unconditional-branches
    Lorsque les probabilités de branche sont fournies, inclure celles des branches inconditionnelles. Les branches inconditionnelles ne sont normalement pas intéressantes.
    -v
    --version
    Afficher la version de gcov (sur la sortie standard) et quitter sans aucun traitement supplémentaire.
    -w
    --verbose
    Afficher des informations détaillées relatives aux blocs de base et aux arcs.
    -x
    --hash-filenames
    Lors de l'utilisation de --preserve-paths, gcov utilise le chemin complet des fichiers source pour créer un nom de fichier de sortie. Cela peut entraîner des noms de fichiers longs qui peuvent dépasser les limites du système de fichiers. Cette option crée des noms de la forme source-file##md5.gcov, où le composant source-file est la partie finale du nom de fichier et le composant md5 est calculé à partir du nom emmêlé complet qui aurait été utilisé autrement. L'option est une alternative à --preserve-paths sur les systèmes qui ont une limite de système de fichiers.

    gcov doit être exécuté avec le répertoire courant identique à celui où vous avez invoqué le compilateur. Sinon, il ne pourra pas localiser les fichiers source. gcov produit des fichiers appelés mangledname.gcov dans le répertoire courant. Ceux-ci contiennent les informations de couverture du fichier source auquel ils correspondent. Un fichier .gcov est produit pour chaque fichier source (ou d'en-tête) contenant du code, qui a été compilé pour produire les fichiers de données. La partie mangledname du nom du fichier de sortie est généralement simplement le nom du fichier source, mais peut être quelque chose de plus compliqué si les options -l ou -p sont données. Se référer à ces options pour plus de détails.

    Si vous invoquez gcov avec plusieurs fichiers d'entrée, les contributions de chaque fichier d'entrée sont additionnées. Typiquement, vous l'invoqueriez avec la même liste de fichiers que pour la liaison finale de votre exécutable.

    Les fichiers .gcov contiennent des champs séparés par des : ainsi que le code source du programme. Le format est

    <execution_count>:<line_number>:<source line text>

    Des informations de bloc supplémentaires peuvent succéder chaque ligne, lorsqu'elles sont demandées par une option de ligne de commande. Le execution_count est - pour les lignes ne contenant aucun code. Les lignes non exécutées sont marquées ##### ou =====, selon qu'elles sont accessibles par des chemins non exceptionnels ou uniquement par des chemins exceptionnels tels que les gestionnaires d'exceptions C++, respectivement. Étant donné l'option -a, les blocs non exécutés sont marqués $$$$$ ou %%%%%, selon qu'un bloc de base est accessible via des chemins non exceptionnels ou exceptionnels. Les blocs de base exécutés ayant une instruction avec un execution_count nul se terminent par un caractère * et sont colorés en magenta avec l'option -k. Cette fonctionnalité n'est pas prise en charge en Ada.

    Notez que GCC peut supprimer complètement les corps des fonctions qui ne sont pas nécessaires -- par exemple, si elles sont intégrées partout. Ces fonctions sont marquées avec -, ce qui peut être source de confusion. Utilisez l'option -fkeep-inline-func

    ions et les options -fkeep-static-functions pour conserver ces fonctions et permettre à gcov d'afficher correctement leur execution_count.

    Certaines lignes d'informations au début ont un line_number de zéro. Ces lignes d'en-tête sont de la forme

    -:0:<tag>:<valeur>

    L'ordre et le nombre de ces lignes d'en-tête seront augmentés à mesure que le développement de gcov progresse ; ne comptez pas sur leur conservation. Utilisez tag pour localiser une ligne d'en-tête particulière.

    Les informations supplémentaires sur les blocs sont de la forme

    <tag> <information>

    L'information est lisible par l'homme, mais conçue pour être suffisamment simple pour être également analysée par machine.

    Lors de l'affichage des pourcentages, 0% et 100% ne sont affichés que lorsque les valeurs sont exactement 0% et 100% respectivement. Les autres valeurs qui seraient conventionnellement arrondies à 0% ou 100% sont alors affichées comme la valeur non limite la plus proche.

    Lorsque vous utilisez gcov, vous devez d'abord compiler votre programme avec une option spéciale de GCC : --coverage. Cela indique au compilateur de générer les informations supplémentaires nécessaires à gcov (essentiellement un graphe de flot du programme) et inclut également du code supplémentaire dans les fichiers objets pour générer les informations de profilage supplémentaires requises par gcov. Ces fichiers supplémentaires sont placés dans le répertoire où se trouve le fichier objet.

    L'exécution du programme générera une sortie de profilage. Pour chaque fichier source compilé avec -fprofile-arcs, un fichier .gcda accompagnant sera placé dans le répertoire du fichier objet.

    L'exécution de gcov avec les noms de fichiers sources de votre programme en arguments produira maintenant une liste du code ainsi que la fréquence d'exécution pour chaque ligne. Par exemple, si votre programme s'appelle tmp.cpp, voici ce que vous voyez lorsque vous utilisez la fonctionnalité de base de gcov :

    $ g++ --coverage tmp.cpp -c
$ g++ --coverage tmp.o
$ a.out
$ gcov tmp.cpp -m

    Dans ce mode, chaque bloc de base n'est affiché que sur une seule ligne, la dernière ligne du bloc. Un bloc de plusieurs lignes ne contribuera qu'au nombre d'exécutions de cette dernière ligne, et les autres lignes ne seront pas affichées comme contenant du code, à moins que des blocs précédents ne se terminent sur ces lignes. Le nombre total d'exécutions d'une ligne est affiché et les lignes suivantes montrent les nombres d'exécutions pour les blocs individuels qui se terminent sur cette ligne. Après chaque bloc, les comptes de branchements et d'appels du bloc seront affichés, si l'option -b est donnée.

    En raison de la manière dont GCC instrumente les appels, un nombre d'appels peut être affiché après une ligne sans blocs individuels. Comme vous pouvez le voir, la ligne 33 contient un bloc de base qui n'a pas été exécuté.

    Pour chaque fonction, une ligne est imprimée indiquant combien de fois la fonction est appelée, combien de fois elle retourne et quel pourcentage des blocs de la fonction ont été exécutés.

    Pour chaque bloc de base, une ligne est imprimée après la dernière ligne du bloc de base décrivant le branchement ou l'appel qui termine le bloc de base. Il peut y avoir plusieurs branchements et appels listés pour une seule ligne source s'il y a plusieurs blocs de base qui se terminent sur cette ligne. Dans ce cas, les branchements et les appels reçoivent chacun un numéro. Il n'y a pas de moyen simple de relier ces branchements et appels aux constructions sources. En général, cependant, le branchement ou l'appel le plus bas numéroté correspondra à la construction la plus à gauche sur la ligne source.

    Pour un branchement, s'il a été exécuté au moins une fois, alors un pourcentage indiquant le nombre de fois où le branchement a été pris divisé par le nombre de fois où le branchement a été exécuté sera imprimé. Sinon, le message "jamais exécuté" sera imprimé.

    Pour un appel, s'il a été exécuté au moins une fois, alors un pourcentage indiquant le nombre de fois où l'appel est retourné divisé par le nombre de fois où l'appel a été exécuté sera imprimé. Ce sera généralement 100%, mais peut être inférieur pour les fonctions qui appellent "exit" ou "longjmp", et donc peuvent ne pas retourner à chaque fois qu'elles sont appelées.

    Les nombres d'exécutions sont cumulatifs. Si le programme exemple était exécuté à nouveau sans supprimer le fichier .gcda, le compte du nombre de fois où chaque ligne du code source a été exécutée serait ajouté aux résultats de l'exécution précédente. Ceci est potentiellement utile de plusieurs manières. Par exemple, cela pourrait être utilisé pour accumuler des données sur un certain nombre d'exécutions de programme dans le cadre d'une suite de vérification de tests, ou pour fournir des informations plus précises à long terme sur un grand nombre d'exécutions de programme.

    Les données des fichiers .gcda sont enregistrées juste avant la sortie du programme. Pour chaque code source

    ce file compiled with -fprofile-arcs, the profiling code first attempts to read in an existing .gcda file; if the file doesn't match the executable (differing number of basic block counts) it will ignore the contents of the file. It then adds in the new execution counts and finally writes the data to the file.

    Utiliser gcov avec l'optimisation GCC

    Si vous prévoyez d'utiliser gcov pour aider à optimiser votre code, vous devez d'abord compiler votre programme avec une option spéciale de GCC, --coverage. Outre cela, vous pouvez utiliser toutes les autres options de GCC ; mais si vous voulez prouver que chaque ligne de votre programme a été exécutée, vous ne devriez pas compiler avec l'optimisation en même temps. Sur certaines machines, l'optimiseur peut éliminer certaines lignes de code simples en les combinant avec d'autres lignes. Par exemple, un code comme celui-ci :

    if (a != b)
  c = 1;
else
  c = 0;

    peut être compilé en une seule instruction sur certaines machines. Dans ce cas, il n'y a aucun moyen pour gcov de calculer des comptages d'exécution distincts pour chaque ligne, car il n'y a pas de code distinct pour chaque ligne. Par conséquent, la sortie de gcov ressemble à ceci si vous avez compilé le programme avec optimisation :

    100:   12:if (a != b)
100:   13:  c = 1;
100:   14:else
100:   15:  c = 0;

    La sortie montre que ce bloc de code, combiné par l'optimisation, a été exécuté 100 fois. Dans un sens, ce résultat est correct, car il n'y avait qu'une seule instruction représentant ces quatre lignes. Cependant, la sortie n'indique pas combien de fois le résultat était 0 et combien de fois le résultat était 1.

    Les fonctions inlinables peuvent créer des comptages de lignes inattendus. Les comptages de lignes sont affichés pour le code source de la fonction inlinable, mais ce qui est affiché dépend de l'endroit où la fonction est inlinée, ou si elle n'est pas du tout inlinée.

    Si la fonction n'est pas inlinée, le compilateur doit émettre une copie hors ligne de la fonction, dans tout fichier objet qui en a besoin. Si fileA.o et fileB.o contiennent tous deux des corps hors ligne d'une fonction inlinable particulière, ils contiendront également tous deux les compteurs de couverture pour cette fonction. Lorsque fileA.o et fileB.o sont liés ensemble, l'éditeur de liens sélectionnera, sur de nombreux systèmes, l'un de ces corps hors ligne pour tous les appels à cette fonction, et supprimera ou ignorera l'autre. Malheureusement, il ne supprimera pas les compteurs de couverture pour le corps de fonction inutilisé. Par conséquent, lorsqu'il est instrumenté, tous les appels à cette fonction, sauf un, afficheront des comptes de zéro.

    Si la fonction est inlinée à plusieurs endroits, la structure du bloc à chaque emplacement peut ne pas être la même. Par exemple, une condition peut maintenant être calculable au moment de la compilation dans certains cas. Comme la couverture de toutes les utilisations de la fonction inlinée sera affichée pour les mêmes lignes sources, les comptages de lignes eux-mêmes peuvent sembler incohérents.

    Les applications de longue durée peuvent utiliser les fonctionnalités "__gcov_reset" et "__gcov_dump" pour limiter la collecte de profils à la région du programme d'intérêt. Appeler "__gcov_reset(void)" effacera tous les compteurs de profils d'exécution à zéro, et appeler "__gcov_dump(void)" provoquera le vidage des informations de profil collectées à ce point dans les fichiers de sortie .gcda. Les applications instrumentées utilisent un destructeur statique de priorité 99 pour invoquer la fonction "__gcov_dump". Ainsi, "__gcov_dump" est exécuté après tous les destructeurs statiques définis par l'utilisateur, ainsi que les gestionnaires enregistrés avec "atexit".

    Si un exécutable charge un objet partagé dynamique via la fonctionnalité dlopen, -Wl,--dynamic-list-data est nécessaire pour dumper toutes les données de profil.

    La bibliothèque d'exécution de profilage signale diverses erreurs liées à la manipulation et à la sauvegarde du profil. Les erreurs sont imprimées dans la sortie d'erreur standard ou dans le fichier GCOV_ERROR_FILE, si la variable d'environnement est utilisée. Pour terminer immédiatement après qu'une erreur se soit produite, définissez la variable d'environnement GCOV_EXIT_AT_ERROR. Cela peut aider les utilisateurs à trouver les conflits de profil qui conduisent à un profil trompeur.
