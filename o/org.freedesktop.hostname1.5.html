NOM

org.freedesktop.hostname1 - L'interface D-Bus de systemd-hostnamed

INTRODUCTION

systemd-hostnamed.service(8) est un service système qui peut être utilisé pour contrôler le nom d'hôte et les métadonnées de machine associées à partir de programmes utilisateurs. Cette page décrit la sémantique du nom d'hôte et l'interface D-Bus.

L'API D-BUS

Le service expose les interfaces suivantes sur le bus :

                 in  b interactive);

                    in  b interactive);

                  in  b interactive);

      Describe(out s json);
    properties:
      readonly s Hostname = '...';
      readonly s StaticHostname = '...';
      readonly s PrettyHostname = '...';
      @org.freedesktop.DBus.Property.EmitsChangedSignal("const")
      readonly s DefaultHostname = '...';

      readonly s KernelRelease = '...';

      readonly s KernelVersion = '...';

      readonly s OperatingSystemPrettyName = '...';

      readonly t OperatingSystemSupportEnd = ...;

      readonly s HomeURL = '...';
      @org.freedesktop.DBus.Property.EmitsChangedSignal("const")

Chaque fois que le nom d'hôte ou d'autres métadonnées sont modifiés via le démon, des signaux PropertyChanged sont envoyés aux clients abonnés. La modification d'un nom d'hôte via cette interface est authentifiée via polkit[1].

SEMANTIQUE

La propriété StaticHostname expose le nom d'hôte "statique" configuré dans /etc/hostname. Il n'est pas toujours synchronisé avec le nom d'hôte actuel tel que retourné par l'appel système gethostname(3). Si aucun nom d'hôte statique n'est configuré, cette propriété sera une chaîne vide.

Lorsque systemd(1) ou systemd-hostnamed.service(8) définit le nom d'hôte, ce nom d'hôte statique a la plus haute priorité.

La propriété Hostname expose le nom d'hôte réel configuré dans le noyau via sethostname(2). Il peut être différent du nom d'hôte statique. Cette propriété n'est jamais vide.

La propriété PrettyHostname expose le "nom d'hôte joli" (pretty hostname), qui est un nom d'hôte en forme libre UTF-8 pour la présentation à l'utilisateur. Les interfaces utilisateur doivent s'assurer que le nom d'hôte joli et le nom d'hôte statique restent synchronisés. Par exemple, lorsque le premier est "Ordinateur de Lennart", le second devrait être "ordinateur-de-lennart". Si aucun nom d'hôte joli n'est défini, ce paramètre sera une chaîne vide. Les applications devraient alors trouver une solution de repli appropriée, comme le nom d'hôte dynamique.

La propriété DefaultHostname expose le nom d'hôte par défaut (configuré via os-release(5), ou une solution de repli définie à la compilation).

La propriété HostnameSource expose l'origine du nom d'hôte actuellement configuré. L'une des valeurs parmi : "static" (défini à partir de /etc/hostname), "transient" (un nom d'hôte non permanent provenant d'une source externe), "default" (la valeur de os-release ou la valeur de repli intégrée).

La propriété IconName expose le nom de l'icône suivant la spécification de nommage d'icônes XDG. Si elle n'est pas définie, des informations telles que le type de châssis (voir ci-dessous) sont utilisées pour trouver un nom d'icône de repli approprié (c'est-à-dire que "ordinateur-portable" ou "ordinateur-bureau" est choisi en fonction des informations du châssis). Si aucune donnée de ce type n'est disponible, la chaîne vide est retournée. Dans ce cas, une application devrait se replier sur une icône de remplacement, par exemple "ordinateur". Si cette propriété est définie à la chaîne vide, la sélection automatique du nom de repli est à nouveau activée.

La propriété Chassis expose un type de châssis, l'un des types de châssis actuellement définis : "desktop", "laptop", "server", "tablet", "handset", ainsi que les types de châssis spéciaux "vm" et "container" pour les systèmes virtualisés. Notez que dans la plupart des cas, le type de châssis sera déterminé automatiquement à partir des informations du firmware DMI/SMBIOS/ACPI. La modification de ce paramètre est donc utile uniquement pour outrepasser les types de châssis mal détectés, ou pour configurer le type de châssis s'il n'a pas pu être détecté automatiquement. Définissez cette propriété à la chaîne vide pour réactiver la détection automatique du type de châssis à partir des informations du firmware.

Notez que systemd-hostnamed ne démarre que sur demande et se termine après une courte période d'inactivité. Cela signifie effectivement que les messages PropertyChanged ne sont pas envoyés pour les modifications apportées directement aux fichiers (c'est-à-dire : l'administrateur modifie les fichiers avec vi). C'est le comportement attendu : les modifications de configuration manuelles devraient nécessiter un rechargement manuel.

Le nom d'hôte transitoire (dynamique) exposé par la propriété Hostname correspond directement au nom d'hôte du noyau. Ce nom d'hôte devrait être considéré comme très dynamique, et par conséquent surveillé directement, sans dépendre des messages PropertyChanged de systemd-hostnamed. Pour ce faire, ouvrez /proc/sys/kernel/hostname et utilisez poll(3) pour SIGHUP qui est déclenché par le noyau chaque fois que le nom d'hôte change. Encore une fois : ceci est spécifique au nom d'hôte transitoire (dynamique), et ne s'applique pas au nom d'hôte configuré (fixe).

Les applications peuvent lire les données du nom d'hôte directement si les notifications de changement de nom d'hôte ne sont pas nécessaires. Utilisez gethostname(2), /etc/hostname (éventuellement avec des solutions de repli par distribution), et machine-info(5) pour cela. Pour plus d'informations sur ces fichiers et appels système, consultez les pages de manuel respectives.

    DESCRIPTION

    ngSystemPrettyName, OperatingSystemCPEName, et HomeURL exposent les champs PRETTY_NAME=, CPE_NAME= et HOME_URL= de os-release(5). Le but de ces propriétés est de permettre aux clients distants d'accéder à ces informations via D-Bus. Les clients locaux peuvent accéder directement aux informations.

    MachineID expose l'ID machine 128 bits, voir machine-id(5) pour plus de détails.

    BootID expose l'ID de démarrage 128 bits, tel que défini dans /proc/sys/kernel/random/boot_id.

    VSockCID expose le CID (Context Identifier, c'est-à-dire l'adresse) local AF_VSOCK du système, s'il est disponible dans l'environnement de la machine virtuelle. Défini à UINT32_MAX sinon. Voir vsock(7) pour plus de détails.

    OperatingSystemSupportEnd expose la date de fin du support du fournisseur du système d'exploitation, si cette information est connue. Il s'agit d'une valeur non signée de 64 bits, en µs depuis l'époque UNIX, UTC. Si cette information n'est pas connue, elle porte la valeur 2^64-1, c'est-à-dire UINT64_MAX.

    OperatingSystemImageID et OperatingSystemImageVersion exposent le nom et la version de l'image du système d'exploitation s'ils sont disponibles, ou contiennent des chaînes vides sinon. Cela correspond principalement aux champs IMAGE_ID= et IMAGE_VERSION= du fichier os-release.

    HardwareVendor, HardwareModel, HardwareSKU, et HardwareVersion exposent les informations du vendeur concernant le matériel du système. L'unité de gestion de stock (SKU) décrit un type de matériel distinct pour la vente, l'achat ou la gestion des stocks. Le SKU et la version ne sont disponibles que s'ils diffèrent du modèle et entre eux. Par conséquent, la version est plus spécifique et n'est disponible que si elle diffère du modèle et du SKU. Si aucune information de ce type ne peut être déterminée, ces propriétés sont définies sur des chaînes vides.

    FirmwareVersion et FirmwareVendor exposent des informations sur le firmware du système, c'est-à-dire une chaîne de version et un nom de fournisseur. Si aucune information de ce type ne peut être déterminée, ces propriétés sont définies sur des chaînes vides.

    FirmwareDate expose la date de création du firmware, si cette information est connue. Il s'agit d'une valeur non signée de 64 bits, en µs depuis l'époque UNIX, UTC. Si elle n'est pas connue, elle vaut UNIT64_MAX.

    ChassisAssetTag expose un identifiant unique du châssis du système. Si cette information n'est pas connue, cette propriété est définie sur une chaîne vide.

    Méthodes

    SetHostname() définit le nom d'hôte transitoire (dynamique), qui est utilisé si aucun nom d'hôte statique n'est défini. Cette valeur doit être un nom d'hôte de style Internet, en ASCII 7 bits minuscules, sans caractères spéciaux ni espaces. Une chaîne vide effacera le nom d'hôte transitoire.

    SetStaticHostname() définit le nom d'hôte statique qui est exposé par la propriété StaticHostname. Lorsqu'elle est appelée avec un argument vide, la configuration statique dans /etc/hostname est supprimée. Étant donné que le nom d'hôte statique a la priorité la plus élevée, l'appel de cette fonction affecte généralement également la propriété Hostname et le nom d'hôte effectif configuré dans le noyau.

    SetPrettyHostname() définit le nom d'hôte joli qui est exposé par la propriété PrettyHostname.

    SetIconName(), SetChassis(), SetDeployment(), et SetLocation() définissent respectivement les propriétés IconName (le nom de l'icône représentant la machine), Chassis (le facteur de forme de la machine), Deployment (l'environnement de déploiement du système) et Location (l'emplacement physique du système).

    PrettyHostname, IconName, Chassis, Deployment, et Location sont stockés dans /etc/machine-info. Voir machine-info(5) pour la sémantique de ces paramètres.

    GetProductUUID() renvoie l'« UUID du produit » tel qu'exposé par le noyau basé sur les informations DMI dans /sys/class/dmi/id/product_uuid. La lecture directe du fichier nécessite des privilèges root, et cette méthode permet l'accès aux clients non privilégiés via le framework polkit.

    GetHardwareSerial() renvoie le « numéro de série du matériel » tel qu'exposé par le noyau basé sur les informations DMI. La lecture directe du fichier nécessite des privilèges root, et cette méthode permet l'accès aux clients non privilégiés via le framework polkit.

    Describe() renvoie une représentation JSON de toutes les propriétés en une seule fois.

    Sécurité

    Les paramètres booléens interactive peuvent être utilisés pour contrôler si polkit doit demander interactivement à l'utilisateur ses identifiants d'authentification si nécessaire.

    L'action polkit pour SetHostname() est org.freedesktop.hostname1.set-hostname. Pour SetStaticHostname() et SetPrettyHostname(), c'est org.freedesktop.hostname1.set-static-hostname. Pour SetIconName(), SetChassis(), SetDeployment() et SetLocation(), c'est org.freedesktop.hostname1.set-machine-info.

    RECOMMANDATIONS

    Voici trois exemples qui montrent comment le nom d'hôte joli et le nom d'icône doivent être utilisés :

    •Lors de l'enregistrement des services DNS-SD : utiliser le nom d'hôte joli dans le nom du service, et passer le nom d'icône dans les données TXT, s'il y a un nom d'icône. Les clients de navigation peuvent alors afficher l'icône du serveur sur chaque service. Ceci est particulièrement utile pour les applications WebDAV ou le partage de médias UPnP.
    •Définir le nom Bluetooth sur le nom d'hôte joli.
    •Lorsque votre explorateur de fichiers possède une icône « Ordinateur », remplacez le nom par le nom d'hôte joli s'il est défini, et l'icône par le nom d'icône s'il est défini.

    Pour gérer correctement les recherches de noms avec des noms d'hôtes locaux changeants sans avoir à modifier /etc/hosts, nous recommandons d'utiliser systemd-hostnamed en combinaison avec nss-myhostname(8).

    Voici quelques recommandations à suivre lors de la génération d'un nom d'hôte statique (Internet) à partir d'un nom joli :

    •Générer une seule étiquette DNS, pas un FQDN. Cela signifie que les points sont interdits. Supprimez-les ou remplacez-les par "-".
    •Il est probablement plus sûr de ne pas utiliser de caractères non ASCII, même si DNS le permet d'une certaine manière de nos jours. En fait, limitez votre jeu de caractères à "a-zA-Z0-9" et "-". Supprimez les autres caractères, ou essayez de les remplacer de manière intelligente par des caractères de cet ensemble, par exemple "ä" → "ae", et utilisez "-" comme remplacement pour tous les caractères de ponctuation et les espaces.
    •Essayez d'éviter de créer des "-" répétés, ainsi que des "-" en début ou fin de chaîne.
    •Limitez le nom d'hôte à 63 caractères, ce qui est la longueur d'une étiquette DNS.
    •Si, après suppression des caractères spéciaux, la chaîne vide est le résultat, vous pouvez la passer telle quelle à systemd-hostnamed, auquel cas il utilisera automatiquement un substitut approprié.
    •Les caractères majuscules doivent être remplacés par leurs équivalents minuscules.

    Notez que bien que systemd-hostnamed applique certains contrôles au nom d'hôte que vous fournissez, ceux-ci sont beaucoup plus souples que les recommandations ci-dessus. Par exemple, systemd-hostnamed acceptera également "_" dans le nom d'hôte, mais nous recommandons de ne pas l'utiliser pour éviter les conflits avec les types de services DNS-SD. systemd-hostnamed autorise également des noms d'hôtes plus longs, mais en raison des limitations des étiquettes DNS, nous recommandons de ne pas en profiter.

    Voici quelques exemples de conversions :

    •"Lennart's PC" → "lennarts-pc"
    •"Müllers Computer" → "muellers-computer"
    •"Voran!" → "voran"
    •"Es war einmal ein Männlein" → "es-war-einmal-ein-maennlein"
    •"Jawoll. Ist doch wahr!" → "jawoll-ist-doch-wahr"
    •"レナート" → "localhost"
    •"...zack!!! zack!..." → "zack-zack"

    Bien sûr, une étiquette de nom d'hôte Internet déjà valide que vous saisissez et qui passe par cette conversion devrait rester inchangée, afin que les utilisateurs aient un contrôle direct dessus, s'ils le souhaitent – en ignorant simplement le fait que le nom d'hôte joli est joli et en le modifiant comme s'il s'agissait du nom Internet normal.
