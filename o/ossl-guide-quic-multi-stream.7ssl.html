NOM

ossl-guide-quic-multi-stream - Guide OpenSSL : Écrire un client QUIC multi-flux simple

INTRODUCTION

Cette page présentera certains concepts importants requis pour écrire une application QUIC multi-flux simple. Elle suppose une compréhension de base de QUIC et de son utilisation dans OpenSSL. Voir ossl-guide-quic-introduction(7) et ossl-guide-quic-client-block(7).

FLUX QUIC

Dans une application QUIC multi-flux, nous séparons les concepts de « connexion » QUIC et de « flux » QUIC. Un objet de connexion représente les détails globaux de la connexion entre un client et un serveur, y compris tous ses paramètres négociés et configurés. Nous utilisons l'objet SSL pour cela dans une application OpenSSL (connu sous le nom d'objet SSL de connexion). Il est créé par une application appelant SSL_new(3).

Séparément, une connexion peut avoir zéro flux ou plus associés. Un flux est utilisé pour envoyer et recevoir des données entre les deux pairs. Chaque flux est également représenté par un objet SSL. Un flux est logiquement indépendant de tous les autres flux associés à la même connexion. Les données envoyées sur un flux sont garanties d'être livrées dans l'ordre où elles ont été envoyées au sein de ce flux. Il en va de même pour les flux, par exemple, si une application envoie des données sur le flux 1 d'abord, puis envoie des données supplémentaires sur le flux 2 ensuite, le pair distant peut recevoir les données envoyées sur le flux 2 avant de recevoir les données envoyées sur le flux 1.

Une fois que l'objet SSL de connexion a terminé son handshake (c'est-à-dire que SSL_connect(3) a retourné 1), les objets SSL de flux sont créés par l'application appelant SSL_new_stream(3) ou SSL_accept_stream(3) (voir « CRÉATION DE NOUVEAUX FLUX » ci-dessous).

Les mêmes règles d'interfaçage s'appliquent aux objets SSL comme à la plupart des objets OpenSSL (voir ossl-guide-libraries-introduction(7)). En particulier, la plupart des fonctions OpenSSL sont thread-safe, mais l'objet SSL ne l'est pas. Cela signifie que vous pouvez utiliser un objet SSL représentant un flux en même temps qu'un autre thread utilise un objet SSL différent pour un flux différent sur la même connexion. Mais vous ne pouvez pas utiliser le même objet SSL sur deux threads différents en même temps (sans verrouillage supplémentaire au niveau de l'application).

LE FLUX PAR DÉFAUT

Un objet SSL de connexion peut également être associé (facultativement) à un flux. Ce flux est connu sous le nom de flux par défaut. Le flux par défaut est automatiquement créé et associé à l'objet SSL lorsque l'application appelle SSL_read_ex(3), SSL_read(3), SSL_write_ex(3) ou SSL_write(3) et passe l'objet SSL de connexion comme paramètre.

Si une application cliente appelle d'abord SSL_write_ex(3) ou SSL_write(3), alors (par défaut) le flux par défaut sera un flux bidirectionnel initié par le client. Si une application cliente appelle d'abord SSL_read_ex(3) ou SSL_read(3), alors le premier flux initié par le serveur sera utilisé comme flux par défaut (qu'il soit bidirectionnel ou unidirectionnel).

Ce comportement peut être contrôlé via le mode de flux par défaut. Voir SSL_set_default_stream_mode(3) pour plus de détails.

Il est recommandé que les nouvelles applications multi-flux n'utilisent pas du tout de flux par défaut et utilisent plutôt un objet SSL de flux séparé pour chaque flux utilisé. Cela nécessite d'appeler SSL_set_default_stream_mode(3) et de définir le mode sur SSL_DEFAULT_STREAM_MODE_NONE.

CRÉATION DE NOUVEAUX FLUX

Un point d'extrémité peut créer un nouveau flux en appelant SSL_new_stream(3). Cela crée un flux initié localement. Pour ce faire, vous devez passer l'objet SSL de connexion QUIC en paramètre. Vous pouvez également spécifier si vous souhaitez un flux bidirectionnel ou unidirectionnel.

La fonction renvoie un nouvel objet SSL de flux QUIC pour envoyer et recevoir des données sur ce flux.

Le pair peut également initier des flux. Une application peut utiliser la fonction SSL_get_accept_stream_queue_len(3) pour déterminer le nombre de flux que le pair a initiés et qui attendent d'être traités par l'application. Une application peut appeler SSL_accept_stream(3) pour créer un nouvel objet SSL pour un flux initié par le pair. Si le pair n'en a initié aucun, cet appel bloquera jusqu'à ce qu'un soit disponible si l'objet de connexion est en mode bloquant (voir SSL_set_blocking_mode(3)).

Lors de l'utilisation d'un flux par défaut, OpenSSL empêchera l'acceptation de nouveaux flux. Pour outrepasser ce comportement, vous devez appeler SSL_set_incoming_stream_policy(3) pour définir la politique sur SSL_INCOMING_STREAM_POLICY_ACCEPT. Voir la page de manuel pour plus de détails. Ceci n'est pas pertinent si le flux par défaut a été désactivé comme décrit dans « LE FLUX PAR DÉFAUT » ci-dessus.

Tout flux peut être bidirectionnel ou unidirectionnel. S'il est unidirectionnel, l'initiateur peut y écrire mais pas y lire, et vice-versa pour le pair. Vous pouvez déterminer quel type de flux un objet SSL représente en appelant SSL_get_stream_type(3). Voir la page de manuel pour plus de détails.

UTILISER UN FLUX POUR ENVOYER ET RECEVOIR DES DONNÉES

Une fois que vous avez un objet SSL de flux (qui inclut l'objet SSL de connexion si un flux par défaut est utilisé), vous pouvez envoyer et recevoir des données via celui-ci en utilisant les fonctions SSL_write_ex(3), SSL_write(3), SSL_read_ex(3) ou SSL_read(3). Voir les pages de manuel pour plus de détails.

Dans le cas où l'une de ces fonctions ne renvoie pas un code de succès, vous devez appeler SSL_get_error(3) pour obtenir plus de détails sur l'erreur. En mode bloquant, il s'agira soit d'une erreur fatale (par exemple, SSL_ERROR_SYSCALL ou SSL_ERROR_SSL), soit de SSL_ERROR_ZERO_RETURN, qui peut survenir lors de la tentative de lecture de données d'un flux et que le pair a indiqué que le flux est terminé (c'est-à-dire que « FIN » a été signalé sur le flux). Cela signifie que le pair n'enverra plus de données sur ce flux. Notez que l'interprétation de SSL_ERROR_ZERO_RETURN est légèrement différente pour une application QUIC par rapport à une application TLS. En TLS, cela se produit lorsque la connexion a été fermée par le pair. En QUIC, cela indique seulement que le flux actuel a été conclu par le pair. Cela ne vous dit rien sur la connexion sous-jacente. Si le pair a conclu le flux, aucune autre donnée ne sera reçue, cependant une application peut toujours envoyer des données au pair jusqu'à ce que le côté envoi du flux soit également conclu. Cela peut se produire par l'application appelant SSL_stream_conclude(3). Il est erroné de tenter d'envoyer plus de données sur un flux après que SSL_stream_conclude(3) ait été appelé.

Il est également possible d'abandonner un flux anormalement en appelant SSL_stream_reset(3).

Une fois qu'un objet de flux n'est plus nécessaire, il doit être libéré par un appel à SSL_free(3). Une application ne doit pas l'appeler avec SSL_shutdown(3) car cela n'a de sens que pour les objets SSL au niveau de la connexion. La libération du flux signalera automatiquement STOP_SENDING au pair.

FLUX ET CONNEXIONS

Étant donné un objet flux, il est possible d'obtenir l'objet SSL correspondant à la connexion via un appel à SSL_get0_connection(3). Les restrictions liées au multithreading s'appliquent, il faut donc être prudent lors de l'utilisation de l'objet connexion renvoyé. Plus précisément, si vous gérez chacun de vos objets flux dans un thread différent et que vous appelez SSL_get0_connection(3) depuis ce thread, vous devez veiller à ne pas appeler une fonction utilisant l'objet connexion en même temps qu'un autre thread utilise également cet objet connexion (à l'exception de SSL_accept_stream(3) et SSL_get_accept_stream_queue_len(3) qui sont thread-safe).

Un objet flux n'hérite pas de tous ses paramètres et valeurs de son objet parent de connexion SSL. Par conséquent, certains appels de fonction pertinents pour la connexion dans son ensemble ne fonctionneront pas sur un flux. Par exemple, la fonction SSL_get_certificate(3) peut être utilisée pour obtenir un handle sur le certificat pair lorsqu'elle est appelée avec un objet SSL de connexion. Lorsqu'elle est appelée avec un objet SSL de flux, elle renvoie NULL.

EXEMPLE SIMPLE DE CLIENT QUIC MULTI-FLUX

Cette section présentera divers exemples de code démontrant comment écrire une application client QUIC multi-flux simple qui se connecte à un serveur, lui envoie quelques requêtes HTTP/1.0 et lit les réponses. Notez que HTTP/1.0 sur QUIC n'est pas standard et ne sera pas pris en charge par les serveurs du monde réel. Ceci est uniquement à des fins de démonstration.

Nous nous appuierons sur le code d'exemple du client QUIC bloquant simple couvert dans la page ossl-guide-quic-client-block(7) et nous supposerons que vous la connaissez. Nous décrirons uniquement les différences entre le client QUIC bloquant simple et le client QUIC multi-flux. Bien que le code d'exemple utilise des objets SSL bloquants, vous pouvez également utiliser des objets SSL non bloquants. Voir ossl-guide-quic-client-non-block(7) pour plus d'informations sur l'écriture d'un client QUIC non bloquant.

Le code source complet de cet exemple de client QUIC multi-flux est disponible dans le répertoire "demos/guide" de la distribution source OpenSSL dans le fichier "quic-multi-stream.c". Il est également disponible en ligne à l'adresse https://github.com/openssl/openssl/blob/master/demos/guide/quic-multi-stream.c.

Désactivation du flux par défaut

Comme discuté ci-dessus dans "LE FLUX PAR DÉFAUT", nous suivrons la recommandation de désactiver le flux par défaut pour notre client multi-flux. Pour ce faire, nous appelons la fonction SSL_set_default_stream_mode(3) et passons notre objet SSL de connexion et la valeur SSL_DEFAULT_STREAM_MODE_NONE.

/*
 * Nous utiliserons plusieurs flux, nous désactiverons donc le mode de flux par défaut.
 * Ce n'est pas une exigence pour utiliser plusieurs flux, mais c'est recommandé.
 */
if (!SSL_set_default_stream_mode(ssl, SSL_DEFAULT_STREAM_MODE_NONE)) {
    printf("Échec de la désactivation du mode de flux par défaut\n");
    goto end;
}

Création des flux de requêtes

Aux fins de cet exemple, nous créerons deux flux différents pour envoyer deux requêtes HTTP différentes au serveur. Aux fins de démonstration, le premier sera un flux bidirectionnel et le second un flux unidirectionnel :

/*
 * Nous créons deux nouveaux flux initiés par le client. Le premier sera
 * bidirectionnel, et le second sera unidirectionnel.
 */
stream1 = SSL_new_stream(ssl, 0);
stream2 = SSL_new_stream(ssl, SSL_STREAM_FLAG_UNI);
if (stream1 == NULL || stream2 == NULL) {
    printf("Échec de la création des flux\n");
    goto end;
}

Écriture de données dans les flux

Une fois les flux créés avec succès, nous pouvons commencer à y écrire des données. Dans cet exemple, nous enverrons une requête HTTP différente sur chaque flux. Pour éviter de répéter trop de code, nous écrivons une fonction d'aide simple pour envoyer une requête HTTP à un flux :

int write_a_request(SSL *stream, const char *request_start,
                    const char *hostname)
{
    const char *request_end = "\r\n\r\n";
    size_t written;
    if (!SSL_write_ex(stream, request_start, strlen(request_start), &written))
        return 0;
    if (!SSL_write_ex(stream, hostname, strlen(hostname), &written))
        return 0;
    if (!SSL_write_ex(stream, request_end, strlen(request_end), &written))
        return 0;
    return 1;
}

Nous supposons que les chaînes request1_start et request2_start contiennent les requêtes HTTP appropriées. Nous pouvons alors appeler notre fonction d'aide ci-dessus pour envoyer les requêtes sur les deux flux. Pour plus de simplicité, cet exemple le fait séquentiellement, en écrivant d'abord sur stream1 et, une fois cela réussi, en écrivant ensuite sur stream2. Rappelez-vous que notre client est bloquant, donc ces appels ne retourneront qu'une fois qu'ils auront été effectués avec succès. Une application réelle n'aurait pas besoin de faire ces écritures séquentiellement ou dans un ordre particulier. Par exemple, nous pourrions démarrer deux threads (un pour chaque flux) et écrire simultanément les requêtes dans chaque flux.

/* Écrire une requête HTTP GET sur chacun de nos flux vers le pair */
if (!write_a_request(stream1, request1_start, hostname)) {
    printf("Échec de l'écriture de la requête HTTP sur le flux 1\n");
    goto end;
}
if (!write_a_request(stream2, request2_start, hostname)) {
    printf("Échec de l'écriture de la requête HTTP sur le flux 2\n");
    goto end;
}

Lecture de données à partir d'un flux

Dans cet exemple, stream1 est un flux bidirectionnel, donc une fois que nous y avons envoyé la requête, nous pouvons tenter de lire la réponse du serveur. Ici, nous appelons simplement à plusieurs reprises SSL_read_ex(3) jusqu'à ce que cette fonction échoue (indiquant soit un problème, soit que le pair a signalé le flux comme étant conclu).

printf("Données du flux 1 :\n");
/*
 * Obtenir jusqu'à sizeof(buf) octets de la réponse du flux 1 (qui est un
 * flux bidirectionnel). Nous continuons à lire jusqu'à ce que le serveur ferme
 * la connexion.
 */
while (SSL_read_ex(stream1, buf, sizeof(buf), &readbytes)) {
    /*
    * OpenSSL ne garantit pas que les données renvoyées forment une chaîne ou
    * qu'elles sont terminées par NUL, nous utilisons donc fwrite() pour écrire le nombre exact
    * d'octets lus. Les données pourraient être non imprimables ou
    * contenir des caractères NUL en leur milieu. Pour cet exemple simple,
    * nous allons quand même les imprimer sur stdout.
    */
    fwrite(buf, 1, readbytes, stdout);
}
/* Au cas où la réponse ne se terminerait pas par une nouvelle ligne, nous en ajoutons une maintenant */
printf("\n");

Dans une application bloquante comme celle-ci, les appels à SSL_read_ex(3) réussiront immédiatement en renvoyant les données disponibles, ou ils bloqueront en attendant plus de données disponibles et les renverront lorsqu'elles seront là, ou ils échoueront avec un code de réponse de 0.

Une fois que nous sortons de la boucle while ci-dessus, nous savons que le dernier appel à SSL_read_ex(3) a renvoyé un code de réponse de 0, nous appelons donc la fonction SSL_get_error(3) pour obtenir plus de détails. Comme il s'agit d'une application bloquante, cela renverra soit SSL_ERROR_SYSCALL ou SSL_ERROR_SSL indiquant un problème fondamental, soit elle renverra SSL_ERROR_ZERO_RETURN indiquant que le flux est terminé et qu'il n'y aura plus de données disponibles à lire. Il faut veiller à distinguer une erreur au niveau du flux (c'est-à-dire une réinitialisation de flux) d'une erreur au niveau de la connexion (c'est-à-dire une fermeture de connexion). La fonction SSL_get_stream_read_state(3) peut être utilisée pour distinguer ces différents cas.

/*
 * Vérifiez si nous avons terminé la boucle while ci-dessus normalement ou à la suite
 * d'une erreur. L'argument 0 à SSL_get_error() est le code de retour
 * que nous avons reçu de l'appel SSL_read_ex(). Il doit être 0 pour
 * arriver ici. L'achèvement normal est indiqué par SSL_ERROR_ZERO_RETURN. En
 * termes QUIC, cela signifie que le pair a envoyé FIN sur le flux pour
 * indiquer qu'aucune donnée supplémentaire ne sera envoyée.
 */
switch (SSL_get_error(stream1, 0)) {
case SSL_ERROR_ZERO_RETURN:
    /* Achèvement normal du flux */
    break;
case SSL_ERROR_SSL:
    /*
     * Une erreur fatale de flux s'est produite. Cela pourrait être dû à une réinitialisation
     * du flux - ou à une défaillance sur la connexion sous-jacente.
     */
    switch (SSL_get_stream_read_state(stream1)) {
    case SSL_STREAM_STATE_RESET_REMOTE:
        printf("Réinitialisation du flux produite\n");
        /* Le flux a été réinitialisé mais la connexion est toujours saine. */
        break;
    case SSL_STREAM_STATE_CONN_CLOSED:
        printf("Connexion fermée\n");
        /* La connexion est déjà fermée. Ignorer SSL_shutdown() */
        goto end;
    default:
        printf("Échec inconnu du flux\n");
        break;
    }
    break;
default:
    /* Une autre erreur inattendue s'est produite */
    printf ("Échec de la lecture des données restantes\n");
    break;
}

Acceptation d'un flux entrant

Notre objet stream2 que nous avons créé ci-dessus était un flux unidirectionnel, il ne peut donc pas être utilisé pour recevoir des données du serveur. Dans cet exemple hypothétique, nous supposons que le serveur initie un nouveau flux pour nous renvoyer les données que nous avons demandées. Pour ce faire, nous appelons SSL_accept_stream(3). Comme il s'agit d'une application bloquante, cela attendra indéfiniment jusqu'à ce que le nouveau flux arrive et soit disponible pour nous à accepter. En cas d'erreur, il renverra NULL.

/*
 * Dans notre protocole hypothétique HTTP/1.0 sur QUIC que nous utilisons, nous
 * supposons que le serveur répondra avec un flux initié par le serveur
 * contenant les données demandées dans notre flux unidirectionnel. Cela n'a
 * pas vraiment de sens de faire cela dans un vrai protocole, mais c'est juste
 * à des fins de démonstration.
 *
 * Nous utilisons le mode bloquant, donc cela bloquera jusqu'à ce qu'un flux devienne
* disponible. Nous pourrions outrepasser ce comportement si nous le souhaitions en définissant * le drapeau SSL_ACCEPT_STREAM_NO_BLOCK dans le deuxième argument ci-dessous. */ stream3 = SSL_accept_stream(ssl, 0); if (stream3 == NULL) { printf("Échec de l'acceptation d'un nouveau flux\n"); goto end; }

Nous pouvons maintenant lire des données du flux de la même manière que nous l'avons fait pour stream1 ci-dessus. Nous ne répéterons pas cela ici.

Nettoyage des flux

Une fois que nous avons fini d'utiliser nos flux, nous pouvons simplement les libérer en appelant SSL_free(3). Facultativement, nous pourrions appeler SSL_stream_conclude(3) sur eux si nous voulons indiquer au pair que nous ne leur enverrons plus de données, mais nous ne le faisons pas dans cet exemple car nous supposons que le protocole d'application HTTP fournit suffisamment d'informations pour que le pair sache quand nous avons fini d'envoyer les données de la requête.

Nous ne devrions pas appeler SSL_shutdown(3) ou SSL_shutdown_ex(3) sur les objets de flux car ces appels ne doivent pas être utilisés pour les flux.

SSL_free(stream1);
SSL_free(stream2);
SSL_free(stream3);
