ocamlopt.opt(1)

Paquet: ocaml

OCAMLOPT(1) Manuel des commandes générales OCAMLOPT(1)

NOM

ocamlopt - Le compilateur OCaml en code natif

SYNTAXE

ocamlopt [ options ] nom_fichier ...

ocamlopt.opt (mêmes options)

DESCRIPTION

Le compilateur OCaml haute performance en code natif ocamlopt(1) compile des fichiers source OCaml en fichiers objets en code natif et lie ces fichiers objets pour produire des exécutables autonomes.

La commande ocamlopt(1) a une interface en ligne de commande très proche de celle de ocamlc(1). Elle accepte les mêmes types d'arguments et les traite séquentiellement, après que toutes les options ont été traitées :

Les arguments se terminant par .mli sont considérés comme des fichiers source pour les interfaces d'unités de compilation. Les interfaces spécifient les noms exportés par les unités de compilation : elles déclarent les noms de valeurs avec leurs types, définissent les types de données publics, déclarent les types de données abstraits, etc. À partir du fichier x.mli, le compilateur ocamlopt(1) produit une interface compilée dans le fichier x.cmi. L'interface produite est identique à celle produite par le compilateur bytecode ocamlc(1).

Les arguments se terminant par .ml sont considérés comme des fichiers source pour les implémentations d'unités de compilation. Les implémentations fournissent les définitions des noms exportés par l'unité, et contiennent également des expressions à évaluer pour leurs effets de bord. À partir du fichier x.ml, le compilateur ocamlopt(1) produit deux fichiers : x.o, contenant le code objet natif, et x.cmx, contenant des informations supplémentaires pour la liaison et l'optimisation des clients de l'unité. L'implémentation compilée doit toujours être référencée sous le nom x.cmx (lorsqu'un fichier .o est donné, ocamlopt(1) suppose qu'il contient du code compilé à partir de C, et non d'OCaml).

L'implémentation est vérifiée par rapport au fichier d'interface x.mli (s'il existe) comme décrit dans le manuel de ocamlc(1).

Les arguments se terminant par .cmx sont considérés comme du code objet compilé. Ces fichiers sont liés ensemble, avec les fichiers objets obtenus en compilant les arguments .ml (s'il y en a), et la bibliothèque standard OCaml, pour produire un programme exécutable en code natif. L'ordre dans lequel les arguments .cmx et .ml sont présentés sur la ligne de commande est pertinent : les unités de compilation sont initialisées dans cet ordre à l'exécution, et il est une erreur de liaison d'utiliser un composant d'une unité avant de l'avoir initialisée. Par conséquent, un fichier x.cmx donné doit précéder tous les fichiers .cmx qui référencent l'unité x.

Les arguments se terminant par .cmxa sont considérés comme des bibliothèques de code objet. Une telle bibliothèque regroupe dans deux fichiers lib.cmxa et lib.a un ensemble de fichiers objets (.cmx/.o). Les bibliothèques sont construites avec ocamlopt -a (voir la description de l'option -a ci-dessous). Les fichiers objets contenus dans la bibliothèque sont liés comme des fichiers .cmx réguliers (voir ci-dessus), dans l'ordre spécifié lors de la construction de la bibliothèque. La seule différence est que si un fichier objet contenu dans une bibliothèque n'est référencé nulle part dans le programme, il n'est pas lié.

Les arguments se terminant par .c sont passés au compilateur C, qui génère un fichier objet .o. Ce fichier objet est lié au programme.

Les arguments se terminant par .o ou .a sont supposés être des fichiers objets et bibliothèques C. Ils sont liés au programme.

La sortie de la phase de liaison est un fichier exécutable Unix ordinaire. Il n'a pas besoin de ocamlrun(1) pour fonctionner.

ocamlopt.opt est le même compilateur que ocamlopt, mais compilé par lui-même au lieu d'être compilé par le compilateur bytecode ocamlc(1). Ainsi, il se comporte exactement comme ocamlopt, mais compile plus rapidement. ocamlopt.opt n'est pas disponible dans toutes les installations d'OCaml.

OPTIONS

Les options suivantes en ligne de commande sont reconnues par ocamlopt(1).

-a
Construit une bibliothèque (.cmxa/.a) avec les fichiers objets (.cmx/.o) fournis sur la ligne de commande, au lieu de les lier dans un fichier exécutable. Le nom de la bibliothèque doit être défini avec l'option -o.

Si les options -cclib ou -ccopt sont passées sur la ligne de commande, ces options sont stockées dans la bibliothèque .cmxa résultante. Ensuite, la liaison avec cette bibliothèque ajoute automatiquement les options -cclib et -ccopt comme si elles avaient été fournies sur la ligne de commande, à moins que l'option -noautolink ne soit donnée. De plus, une sous-chaîne $CAMLORIGIN dans une option -ccopt sera remplacée par le chemin complet vers la bibliothèque .cma, en excluant le nom du fichier.

-absname
Afficher les noms de fichiers absolus dans les messages d'erreur.
-no-absname
Ne pas essayer d'afficher les noms de fichiers absolus dans les messages d'erreur.
-annot
Obsolète depuis OCaml 4.11. Veuillez utiliser -bin-annot à la place.
-bin-annot
Dump des informations détaillées sur la compilation (types, liaisons, appels récursifs, etc.) au format binaire. Les informations pour le fichier src.ml sont placées dans le fichier src.cmt. En cas d'erreur de type, dump toutes les informations inférées par le vérificateur de type avant l'erreur. Les fichiers d'annotation produits par -bin-annot contiennent plus d'informations et sont beaucoup plus compacts que les fichiers produits par -annot.
-c
Compiler uniquement. Supprime la phase de liaison de la compilation. Les fichiers source sont transformés en fichiers compilés, mais aucun fichier exécutable n'est produit. Cette option est utile pour compiler des modules séparément.
-cc ccomp
Utiliser ccomp comme lieur C appelé pour construire l'exécutable final et comme compilateur C pour compiler les fichiers source .c.
-cclib -lnomlib
Passer l'option -lnomlib au lieur. Cela provoque la liaison de la bibliothèque C donnée avec le programme.
-ccopt option
Passer l'option donnée au compilateur et au lieur C. Par exemple, -ccopt -Lrep fait en sorte que le lieur C recherche les bibliothèques C dans le répertoire rep.
-color mode
Activer ou désactiver les couleurs dans les messages du compilateur (en particulier les avertissements et les erreurs). Les modes suivants sont supportés :

auto utilise des heuristiques pour activer les couleurs uniquement si la sortie les prend en charge (un terminal tty compatible ANSI) ;

always active les couleurs inconditionnellement ;

never désactive la sortie en couleur.

La variable d'environnement "OCAML_COLOR" est prise en compte si -color n'est pas fourni. Ses valeurs sont auto/always/never comme ci-dessus.

Si -color n'est pas fourni, "OCAML_COLOR" n'est pas défini et la variable d'environnement "NO_COLOR" est définie, alors la sortie en couleur est désactivée. Sinon, le réglage par défaut est auto, et l'heuristique actuelle vérifie que la variable "TERM" existe et n'est ni vide ni "dumb", et que isatty(stderr) est vrai.

-error-style mode
Contrôler la façon dont les messages d'erreur et les avertissements sont imprimés. Les modes suivants sont supportés :

short imprime uniquement l'erreur et sa localisation ;

contextual comme "short", mais affiche également l'extrait de code source correspondant à la localisation de l'erreur.

Le réglage par défaut est contextual.

La variable d'environnement "OCAML_ERROR_STYLE" est prise en compte si -error-style n'est pas fourni. Ses valeurs sont short/contextual comme ci-dessus.

-compact
Optimise le code produit pour l'espace plutôt que pour le temps. Cela se traduit par des programmes plus petits mais légèrement plus lents. La valeur par défaut est d'optimiser pour la vitesse.
-config
Affiche le numéro de version de ocamlopt(1) et un résumé détaillé de sa configuration, puis quitte.
-config-var
Affiche la valeur d'une variable de configuration spécifique de la sortie de -config, puis quitte. Si la variable n'existe pas, le code de sortie est non nul.
-depend ocamldep-args
Calcule les dépendances, comme le ferait ocamldep.
-for-pack module-path
Génère un fichier objet (.cmx et .o) qui peut plus tard être inclus comme sous-module (avec le chemin d'accès donné) d'une unité de compilation construite avec -pack. Par exemple, ocamlopt -for-pack P -c A.ml générera les fichiers a.cmx et a.o qui pourront plus tard être utilisés avec ocamlopt -pack -o P.cmx a.cmx.
-g
Ajoute des informations de débogage lors de la compilation et de l'édition des liens. Cette option est requise pour produire des traces de pile lorsque le programme se termine sur une exception non interceptée (voir ocamlrun(1)).
-no-g
N'enregistre pas les informations de débogage (par défaut).
-i
Force le compilateur à afficher tous les noms définis (avec leurs types inférés ou leurs définitions) lors de la compilation d'une implémentation (.ml file). Aucun fichier compilé (.cmo et .cmi files) n'est produit. Ceci peut être utile pour vérifier les types inférés par le compilateur. De plus, comme la sortie suit la syntaxe des interfaces, elle peut aider à écrire une interface explicite (.mli file) pour un fichier : redirigez simplement la sortie standard du compilateur vers un fichier .mli, et éditez ce fichier pour supprimer toutes les déclarations de noms non exportés.
-cmi-file filename
Vérifie le type de l'implémentation source à compiler par rapport au fichier d'interface spécifié (court-circuite la recherche normale des fichiers .mli et .cmi).
-I directory
Ajoute le répertoire donné à la liste des répertoires recherchés pour les fichiers d'interface compilés (.cmi), les fichiers objets compilés (.cmx), et les bibliothèques (.cmxa). Par défaut, le répertoire courant est recherché en premier, puis le répertoire de la bibliothèque standard. Les répertoires ajoutés avec -I sont recherchés après le répertoire courant, dans l'ordre où ils ont été donnés sur la ligne de commande, mais avant le répertoire de la bibliothèque standard. Voir aussi l'option -nostdlib.

Si le répertoire donné commence par +, il est interprété relativement au répertoire de la bibliothèque standard. Par exemple, -I +compiler-libs ajoute le sous-répertoire compiler-libs de la bibliothèque standard au chemin de recherche.

-impl filename
Compile le fichier filename comme un fichier d'implémentation, même si son extension n'est pas .ml.
-inline n
Définit l'agressivité de l'inlining à n, où n est un entier positif. Spécifier -inline 0 empêche l'inlining de toutes les fonctions, sauf celles dont le corps est plus petit que le site d'appel. Ainsi, l'inlining ne cause aucune expansion de la taille du code. L'agressivité par défaut, -inline 1, permet à des fonctions légèrement plus grandes d'être inlinées, résultant en une légère expansion de la taille du code. Des valeurs plus élevées pour l'option -inline font que des fonctions de plus en plus grandes deviennent candidates à l'inlining, mais peuvent entraîner une augmentation sérieuse de la taille du code.
-insn-sched
Active le passage d'ordonnancement des instructions dans le backend du compilateur.
-intf filename
Compile le fichier filename comme un fichier d'interface, même si son extension n'est pas .mli.
-intf-suffix string
Reconnaît les noms de fichiers se terminant par string comme des fichiers d'interface (au lieu du défaut .mli).
-keep-docs
Conserve les chaînes de documentation dans les fichiers .cmi générés.
-keep-locs
Conserve les localisations dans les fichiers .cmi générés.
-labels
Les labels ne sont pas ignorés dans les types, les labels peuvent être utilisés dans les applications, et les paramètres labellisés peuvent être donnés dans n'importe quel ordre. Ceci est le défaut.
-linkall
Force tous les modules contenus dans les bibliothèques à être liés. Si ce flag n'est pas donné, les modules non référencés ne sont pas liés. Lors de la construction d'une bibliothèque (flag -a), définir le flag -linkall force tous les liens ultérieurs de programmes impliquant cette bibliothèque à lier tous les modules contenus dans la bibliothèque. Lors de la compilation d'un module (option -c), définir l'option -linkall garantit que ce module sera toujours lié s'il est placé dans une bibliothèque et que cette bibliothèque est liée.
-linscan
Utilise l'allocation de registres par scan linéaire. Compiler avec cet allocateur est plus rapide qu'avec l'allocateur habituel par coloriage de graphe, parfois de manière assez drastique pour les fonctions et modules longs. D'un autre côté, le code généré peut être un peu plus lent.
-match-context-rows
Définit le nombre de lignes de contexte utilisées lors de la compilation des patterns de correspondance. Des valeurs plus basses entraînent une compilation plus rapide, mais un code moins optimisé. La valeur par défaut est 32.
-no-alias-deps
N'enregistre pas les dépendances pour les alias de modules.
-no-app-funct
Désactive le comportement applicatif des foncteurs. Avec cette option, chaque application de foncteur génère de nouveaux types dans son résultat et l'application du même foncteur deux fois sur le même argument produit deux structures incompatibles.
-noassert
Ne compile pas les vérifications d'assertions. Notez que la forme spéciale assert false est toujours compilée car elle est typée spécialement. Ce flag n'a aucun effet lors de l'édition de liens de fichiers déjà compilés.
-noautolink
Lors de l'édition de liens de bibliothèques .cmxa, ignore les options -cclib et -ccopt potentiellement contenues dans les bibliothèques (si ces options ont été données lors de la construction des bibliothèques). Ceci peut être utile si une bibliothèque contient des spécifications incorrectes de bibliothèques C ou d'options C ; dans ce cas, lors de l'édition de liens, définissez -noautolink et passez les bonnes bibliothèques et options C sur la ligne de commande.
-nodynlink
Permet au compilateur d'utiliser certaines optimisations qui ne sont valides que pour le code qui n'est jamais lié dynamiquement.
-no-insn-sched
Désactive le passage d'ordonnancement des instructions dans le backend du compilateur.
-nostdlib
N'ajoute pas automatiquement le répertoire de la bibliothèque standard à la liste des répertoires recherchés pour les fichiers d'interface compilés (.cmi), les fichiers objets compilés (.cmx), et les bibliothèques (.cmxa). Voir aussi l'option -I.
-nolabels
Ignore les labels non optionnels dans les types. Les labels ne peuvent pas être utilisés dans les applications, et l'ordre des paramètres devient strict.
-o exec-file
Spécifie le nom du fichier de sortie produit par l'éditeur de liens. Le nom de sortie par défaut est a.out, conformément à la tradition Unix. Si l'option -a est donnée, spécifie le nom de la bibliothèque produite. Si l'option -pack est donnée, spécifie le nom du fichier objet packagé produit. Si l'option -output-obj est donnée, spécifie le nom du fichier de sortie produit. Si l'option -shared est donnée, spécifie le nom du fichier plugin produit. Ceci peut également être utilisé lors de la compilation d'un fichier d'interface ou d'implémentation, sans édition de liens, auquel cas il définit le nom du fichier cmi ou cmo, et définit également le nom du module au nom du fichier jusqu'au premier point.
-opaque
Lors de la compilation d'un fichier d'interface .mli, cela a le même effet que l'option -opaque du compilateur bytecode. Lors de la compilation d'un fichier d'implémentation .ml, cela produit un fichier .cmx sans informations d'optimisation inter-modules, ce qui réduit les recompilations lors des changements de modules.
-open module
Ouvre le module donné avant de traiter les fichiers d'interface ou d'implémentation. Si plusieurs options -open sont données, elles sont traitées dans l'ordre, comme si les instructions open! module1;; ... open! moduleN;; étaient ajoutées en tête de chaque fichier.
-output-obj
Force l'éditeur de liens à produire un fichier objet C au lieu d'un fichier exécutable. Ceci est utile pour encapsuler du code OCaml sous forme de bibliothèque C, appelable depuis n'importe quel programme C. Le nom du fichier objet de sortie doit être défini avec l'option -o. Cette option peut également être utilisée pour produire une bibliothèque dynamique compilée (.so extension). -output-complete-obj Identique à -output-obj sauf que le fichier objet produit inclut le runtime et les bibliothèques autolink.
-pack
Construit un fichier objet (.cmx et .o) et son interface compilée associée (.cmi) qui combine les fichiers objets .cmx donnés sur la ligne de commande, les faisant apparaître comme des sous-modules du fichier .cmx de sortie. Le nom du fichier .cmx de sortie doit être donné avec l'option -o. Par exemple, ocamlopt -pack -o P.cmx A.cmx B.cmx C.cmx génère les fichiers compilés P.cmx, P.o et P.cmi décrivant une unité de compilation ayant trois sous-modules A, B et C, correspondant au contenu des fichiers objets A.cmx, B.cmx et C.cmx. Ces contenus peuvent être référencés comme P.A, P.B et P.C dans le reste du programme.

Les fichiers objets .cmx combinés doivent avoir été compilés avec l'option -for-pack appropriée. Dans l'exemple ci-dessus, A.cmx, B.cmx et C.cmx doivent avoir été compilés avec ocamlopt -for-pack P.

Plusieurs niveaux d'empaquetage peuvent être obtenus en combinant -pack avec -for-pack. Voir le chapitre "Compilation en code natif" du manuel de l'utilisateur OCaml pour plus de détails.

-pp command
Force le compilateur à appeler la command donnée comme un
preprocesseur pour chaque fichier source. La sortie de command est redirigée vers un fichier intermédiaire, qui est ensuite compilé. S'il n'y a pas d'erreurs de compilation, le fichier intermédiaire est supprimé par la suite.
-ppx commande
Après l'analyse syntaxique, le flot de l'arbre syntaxique abstrait est transmis au préprocesseur commande. Le module Ast_mapper(3) implémente l'interface externe d'un préprocesseur.
-principal
Vérifier le chemin d'information pendant la vérification des types, afin de s'assurer que tous les types sont dérivés de manière principale. Tous les programmes acceptés en mode -principal sont également acceptés en mode par défaut avec des types équivalents, mais avec des signatures binaires différentes.
-no-principal
Ne pas vérifier la principauté de l'inférence de types. C'est le comportement par défaut.
-rectypes
Autoriser les types récursifs arbitraires lors de la vérification des types. Par défaut, seuls les types récursifs où la récursion passe par un type objet sont supportés. Notez qu'une fois que vous avez créé une interface en utilisant ce drapeau, vous devez l'utiliser à nouveau pour toutes les dépendances.
-no-rectypes
Ne pas autoriser les types récursifs arbitraires lors de la vérification des types. C'est le comportement par défaut.
-runtime-variant suffixe
Ajouter suffixe au nom de la bibliothèque d'exécution qui sera utilisée par le programme. Si OCaml a été configuré avec l'option -with-debug-runtime, alors le suffixe d est supporté et donne une version de débogage de la bibliothèque d'exécution.
-S
Conserver le code assembleur produit lors de la compilation. Le code assembleur pour le fichier source x.ml est enregistré dans le fichier x.s.
-safe-string
Appliquer la séparation entre les types string et bytes, rendant ainsi les chaînes de caractères en lecture seule. C'est le comportement par défaut.
-safer-matching
Ne pas utiliser les informations de type pour optimiser la correspondance de motifs. Cela permet de détecter les échecs de correspondance même si une correspondance de motifs était supposée à tort être exhaustive. Cela n'affecte que la compilation des GADT et des variantes polymorphes.
-save-ir-after etape
Enregistrer la représentation intermédiaire après l'étape de compilation donnée. Les étapes actuellement supportées sont : scheduling.
-shared
Construire un plugin (généralement .cmxs) qui peut être chargé dynamiquement avec le module Dynlink. Le nom du plugin doit être défini avec l'option -o. Un plugin peut inclure un certain nombre de modules et de bibliothèques OCaml, ainsi que des objets natifs supplémentaires (.o, .a files). La construction de plugins natifs n'est supportée que pour certains systèmes d'exploitation. Sur certains systèmes (actuellement, uniquement Linux AMD 64), tout le code OCaml lié dans un plugin doit avoir été compilé sans le drapeau -nodynlink. Certaines contraintes peuvent également s'appliquer à la manière dont les objets natifs supplémentaires ont été compilés (sous Linux AMD 64, ils ne doivent contenir que du code indépendant de la position).
-short-paths
Lorsqu'un type est visible sous plusieurs chemins de module, utiliser le plus court lors de l'impression du nom du type dans les interfaces inférées et les messages d'erreur et d'avertissement.
-stop-after etape
Arrêter la compilation après l'étape de compilation donnée. Les étapes actuellement supportées sont : parsing, typing, scheduling, emit.
-strict-sequence
La partie gauche d'une séquence doit avoir le type unit.
-no-strict-sequence
La partie gauche d'une séquence n'a pas besoin d'avoir le type unit. C'est le comportement par défaut.
-unboxed-types
Lorsqu'un type est déboxable (c'est-à-dire un enregistrement avec un seul argument ou un type de données concret avec un seul constructeur à un argument), il sera déboxé sauf s'il est annoté avec [@@ocaml.boxed].
-no-unboxed-types
Lorsqu'un type est déboxable, il sera boxé sauf s'il est annoté avec [@@ocaml.unboxed]. C'est le comportement par défaut.
-unsafe
Désactiver la vérification des limites pour les accès aux tableaux et aux chaînes de caractères (les constructions v.(i) et s.[i]). Les programmes compilés avec -unsafe sont donc plus rapides, mais dangereux : tout peut arriver si le programme accède à un tableau ou une chaîne en dehors de ses limites. De plus, désactiver la vérification du diviseur zéro dans les opérations de division et de modulo entières. Avec -unsafe, une division entière (ou modulo) par zéro peut arrêter le programme ou continuer avec un résultat indéterminé au lieu de lever une exception Division_by_zero.
-unsafe-string
Identifier les types string et bytes, rendant ainsi les chaînes de caractères modifiables. Ceci est destiné à la compatibilité avec d'anciens codes sources et ne doit pas être utilisé avec de nouveaux logiciels.
-v
Afficher le numéro de version du compilateur et l'emplacement du répertoire de la bibliothèque standard, puis quitter.
-verbose
Afficher toutes les commandes externes avant qu'elles ne soient exécutées, en particulier les appels à l'assembleur, au compilateur C et à l'éditeur de liens.
-version ou -vnum
Afficher le numéro de version du compilateur sous forme abrégée (par exemple, "3.11.0"), puis quitter.
-w liste-avertissements
Activer, désactiver ou marquer comme fatals les avertissements spécifiés par l'argument liste-avertissements. Voir ocamlc(1) pour la syntaxe de liste-avertissements.
-warn-error liste-avertissements
Marquer comme fatals les avertissements spécifiés dans l'argument liste-avertissements. Le compilateur s'arrêtera avec une erreur lorsqu'un de ces avertissements sera émis. La liste-avertissements a la même signification que pour l'option -w : un signe + (ou une lettre majuscule) marque les avertissements correspondants comme fatals, un signe - (ou une lettre minuscule) les retransforme en avertissements non fatals, et un signe @ active et marque comme fatals les avertissements correspondants.

Remarque : il n'est pas recommandé d'utiliser l'option -warn-error dans du code de production, car cela empêchera presque certainement la compilation de votre programme avec des versions ultérieures d'OCaml lorsqu'elles ajouteront de nouveaux avertissements ou modifieront des avertissements existants.

Le réglage par défaut est -warn-error -a (aucun avertissement n'est fatal).

-warn-help
Afficher la description de tous les numéros d'avertissement disponibles.
-where
Afficher l'emplacement de la bibliothèque standard, puis quitter.
-with-runtime
Inclure le système d'exécution dans le programme généré. C'est le comportement par défaut.
-without-runtime
Le compilateur n'inclut pas le système d'exécution (ni une référence à celui-ci) dans le programme généré ; il doit être fourni séparément.
- fichier
Traiter fichier comme un nom de fichier, même s'il commence par un caractère de tiret (-).
-help ou --help
Afficher un bref résumé de l'utilisation et quitter.

OPTIONS POUR LA MITOYENNE FLAMBDA

Lorsque le générateur de code Flambda a été activé lors de la configuration, son comportement peut être ajusté avec les options supplémentaires suivantes :

-02
Effectuer plus d'optimisations que d'habitude. Les temps de compilation peuvent s'allonger.
-03
Effectuer encore plus d'optimisations que d'habitude, y compris potentiellement le déroulement de fonctions récursives. Les temps de compilation peuvent être considérablement allongés.
-Oclassic
Prendre des décisions d'inlining au point de définition d'une fonction plutôt qu'au(x) site(s) d'appel. Cela reflète le comportement des compilateurs OCaml n'utilisant pas Flambda. Par rapport à la compilation utilisant les nouvelles heuristiques d'inlining de Flambda (par exemple à -O2), cela produit des fichiers .cmx plus petits, des temps de compilation plus courts et un code qui s'exécute probablement plutôt plus lentement.
-inlining-report
Émettre des fichiers .inlining (un par tour d'optimisation) montrant toutes les décisions de l'inliner.

OPTIONS POUR L'ARCHITECTURE AMD64

ocamlopt.opt(1)

NOM

ocamlopt.opt - Le compilateur natif OCaml.

SYNOPSIS

ocamlopt.opt [options] fichiers.ml ...

ocamlopt.opt -c [options] fichiers.ml ...

ocamlopt.opt [options] fichiers.cmx ...

ocamlopt.opt -a [options] fichiers.cmx ...

DESCRIPTION

ocamlopt.opt est le compilateur natif pour le langage OCaml. Il traduit les sources OCaml en code machine exécutable pour l'architecture de la machine cible.

Il utilise un système de bibliothèques de compilation qui génère des fichiers .cmx (compilé) et .o pour les interfaces de modules compilés. Pour les bibliothèques compilées, utilisez ocamlopt.opt -a.

OPTIONS

Les options suivantes sont reconnues par ocamlopt.opt :

-c
Ne compile que les fichiers sources OCaml en fichiers objets .o, sans les lier.
-o nom
Nommer le fichier exécutable de sortie nom (par défaut, a.out).
-I dir
Ajouter le répertoire dir au chemin de recherche des fichiers de bibliothèques compilées.
-L dir
Ajouter le répertoire dir au chemin de recherche des bibliothèques partagées.
-linkall
Lier toutes les bibliothèques spécifiées, même si elles ne sont pas utilisées.
-noassert
Désactiver les assertions (par défaut activées).
-tag type:valeur
Définir la valeur de tag pour le type spécifié.
-g
Générer des informations de débogage.
-principal
Afficher le nom du module principal d'un fichier compilé.
-version
Afficher la version du compilateur et quitter.
--help
Afficher un message d'aide et quitter.

OPTIONS POUR LE MILIEU DE COMPILATION FLAMBDA

Les options suivantes sont passées au milieu de compilation Flambda :

-O3
Activer les optimisations de niveau 3.
-inline n
Taille maximale de fonction pour l'inlining (par défaut 10).
-unbox-small-structs
Déballer les petites structures pour améliorer les performances.

OPTIONS POUR L'ARCHITECTURE AMD64

Les options suivantes sont spécifiques à l'architecture AMD64 :

-no-flat-backend
Désactiver le backend plat (par défaut activé).
-no-pixel
Désactiver le pixel (par défaut activé).
