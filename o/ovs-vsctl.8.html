NOM

ovs-vsctl - utilitaire pour interroger et configurer ovs-vswitchd

SYNTAXE

ovs-vsctl [options] -- [options] commande [arguments] [-- [options] commande [arguments]]...

DESCRIPTION

Le programme ovs-vsctl configure ovs-vswitchd(8) en fournissant une interface de haut niveau à sa base de données de configuration. Voir ovs-vswitchd.conf.db(5) pour une documentation complète du schéma de la base de données.

ovs-vsctl se connecte à un processus ovsdb-server qui maintient une base de données de configuration Open vSwitch. À l'aide de cette connexion, il interroge et éventuellement applique des modifications à la base de données, en fonction des commandes fournies. Ensuite, s'il a appliqué des modifications, il attend par défaut que ovs-vswitchd ait fini de se reconfigurer avant de se terminer. (Si vous utilisez ovs-vsctl lorsque ovs-vswitchd n'est pas en cours d'exécution, utilisez --no-wait.)

ovs-vsctl peut effectuer un nombre quelconque de commandes en une seule exécution, implémentées comme une seule transaction atomique par rapport à la base de données.

La ligne de commande ovs-vsctl commence par des options globales (voir OPTIONS ci-dessous pour les détails). Les options globales sont suivies d'une ou plusieurs commandes. Chaque commande doit commencer par -- seul en tant qu'argument de ligne de commande, pour la séparer des commandes suivantes. (Le -- avant la première commande est facultatif.) La commande elle-même commence par des options spécifiques à la commande, le cas échéant, suivies du nom de la commande et de ses arguments. Voir EXEMPLES ci-dessous pour des exemples de syntaxe.

Compatibilité de pontage VLAN Linux

Le programme ovs-vsctl prend en charge le modèle d'un pont implémenté par Open vSwitch, dans lequel un seul pont prend en charge des ports sur plusieurs VLAN. Dans ce modèle, chaque port d'un pont est soit un port trunk qui transmet potentiellement des paquets étiquetés avec des en-têtes 802.1Q qui désignent des VLAN, soit il est assigné à un seul VLAN implicite qui n'est jamais étiqueté avec un en-tête 802.1Q.

Pour assurer la compatibilité avec les logiciels conçus pour le pont Linux, ovs-vsctl prend également en charge un modèle dans lequel le trafic associé à un VLAN 802.1Q donné est segmenté dans un pont séparé. Une forme spéciale de la commande add-br (voir ci-dessous) crée un « pont fantôme » au sein d'un pont Open vSwitch pour simuler ce comportement. Lorsqu'un tel « pont fantôme » est actif, ovs-vsctl le traite de manière similaire à un pont séparé de son « pont parent », mais l'implémentation réelle dans Open vSwitch utilise un seul pont, avec des ports sur le pont fantôme assignés au VLAN implicite du pont fantôme dont ils sont membres. (Un pont fantôme pour le VLAN 0 reçoit les paquets qui n'ont pas d'étiquette 802.1Q ou une étiquette avec le VLAN 0.)

OPTIONS

Les options suivantes affectent le comportement de ovs-vsctl dans son ensemble. Certaines commandes individuelles acceptent également leurs propres options, qui sont données juste avant le nom de la commande. Si la première commande sur la ligne de commande a des options, alors ces options doivent être séparées des options globales par --.

--db=serveur
Définit serveur comme serveur de base de données auquel ovs-vsctl se connecte pour interroger ou modifier la configuration. serveur peut être une méthode de connexion active ou passive OVSDB, telle que décrite dans ovsdb(7). La valeur par défaut est unix:/run/openvswitch/db.sock.
--no-wait
Empêche ovs-vsctl d'attendre que ovs-vswitchd se reconfigure selon la base de données modifiée. Cette option doit être utilisée si ovs-vswitchd n'est pas en cours d'exécution ; sinon, ovs-vsctl ne se terminera pas tant que ovs-vswitchd ne démarrera pas.
Cette option n'a aucun effet si les commandes spécifiées ne modifient pas la base de données.
--no-syslog
Par défaut, ovs-vsctl enregistre ses arguments et les détails des modifications qu'il apporte dans le journal système. Cette option désactive cette journalisation.
Cette option est équivalente à --verbose=vsctl:syslog:warn.
--oneline
Modifie le format de sortie de manière à ce que la sortie de chaque commande soit imprimée sur une seule ligne. Les caractères de nouvelle ligne qui sépareraient autrement les lignes sont imprimés comme \n, et toute instance de \ qui apparaîtrait autrement dans la sortie est doublée. Imprime une ligne vide pour chaque commande qui n'a pas de sortie. Cette option n'affecte pas le formatage de la sortie des commandes list ou find ; voir Options de formatage de table ci-dessous.
--dry-run
Empêche ovs-vsctl de modifier réellement la base de données.
-t secondes

--timeout=secondes
Par défaut, ou avec une valeur de secondes de 0, ovs-vsctl attend éternellement une réponse de la base de données. Cette option limite le temps d'exécution à environ secondes secondes. Si le délai d'attente expire, ovs-vsctl se terminera avec un signal SIGALRM. (Un délai d'attente ne se produirait normalement que si la base de données ne peut pas être contactée ou si le système est surchargé.)
--retry
Sans cette option, si ovs-vsctl se connecte à l'extérieur au serveur de base de données (par défaut), alors ovs-vsctl essaiera de se connecter une fois et se terminera avec une erreur si la connexion échoue (ce qui signifie généralement que ovsdb-server n'est pas en cours d'exécution).
Avec cette option, ou si --db spécifie que ovs-vsctl doit attendre une connexion entrante du serveur de base de données, alors ovs-vsctl attendra la connexion à la base de données pour toujours.
Indépendamment de ce réglage, --timeout limite toujours le temps pendant lequel ovs-vsctl attendra.

Options de formatage de table

Ces options contrôlent le format de la sortie des commandes list et find.

-f format

--format=format
Définit le type de formatage de la table. Les types de format suivants sont disponibles :
table
Tables textuelles 2D avec des colonnes alignées.
list (par défaut)
Une liste avec une colonne par ligne et des lignes séparées par une ligne vide.
html
Tables HTML.
csv
Valeurs séparées par des virgules telles que définies dans la RFC 4180.
json
Format JSON tel que défini dans la RFC 4627. La sortie est une séquence d'objets JSON, chacun correspondant à une table. Chaque objet JSON a les membres suivants avec les valeurs indiquées :
caption
La légende de la table. Ce membre est omis si la table n'a pas de légende.
headings
Un tableau avec un élément par colonne de table. Chaque élément du tableau est une chaîne de caractères donnant l'en-tête de la colonne correspondante.
data
Un tableau avec un élément par ligne de table. Chaque élément est également un tableau avec un élément par colonne de table. Les éléments de ce tableau de second niveau sont les cellules qui constituent la table. Les cellules qui représentent des données ou des types de données OVSDB sont exprimées dans le format décrit dans la spécification OVSDB ; d'autres cellules sont simplement exprimées sous forme de chaînes de caractères.
-d format

--data=format
Définit le formatage des cellules dans les tables de sortie, sauf si le format de table est défini sur json,
dans quel cas la mise en forme json est-elle toujours utilisée lors de la mise en forme des cellules. Les types de format suivants sont disponibles :
string (par défaut)
Le format simple décrit dans la section Valeurs de base de données ci-dessous.
bare
Le format simple sans ponctuation : [] et {} sont omis autour des ensembles, des cartes et des colonnes vides, les éléments des ensembles et des cartes sont séparés par des espaces, et les chaînes ne sont jamais entre guillemets. Ce format peut être plus facile à analyser pour les scripts.
json
Le format JSON RFC 4627 tel que décrit ci-dessus.
--no-headings
Cette option supprime la ligne d'en-tête qui apparaît autrement dans la première ligne de la sortie du tableau.
--pretty
Par défaut, le JSON dans la sortie est imprimé de manière aussi compacte que possible. Cette option fait que le JSON dans la sortie est imprimé de manière plus lisible. Les membres des objets et les éléments des tableaux sont imprimés un par ligne, avec indentation.
Cette option n'affecte pas le JSON dans les tableaux, qui est toujours imprimé de manière compacte.
--bare
Équivalent à --format=list --data=bare --no-headings.
--max-column-width=n
Pour la sortie de tableau uniquement, limite la largeur de toute colonne dans la sortie à n colonnes. Les données de cellule plus longues sont tronquées pour s'adapter, si nécessaire. Les colonnes sont toujours suffisamment larges pour afficher les noms de colonnes, si la ligne d'en-tête est imprimée.

Options d'infrastructure à clé publique

-p privkey.pem

--private-key=privkey.pem
Spécifie un fichier PEM contenant la clé privée utilisée comme identité de ovs-vsctl pour les connexions SSL/TLS sortantes.
-c cert.pem

--certificate=cert.pem
Spécifie un fichier PEM contenant un certificat qui certifie que la clé privée spécifiée dans -p ou --private-key est digne de confiance. Le certificat doit être signé par l'autorité de certification (AC) que le pair dans les connexions SSL/TLS utilisera pour le vérifier.
-C cacert.pem

--ca-cert=cacert.pem
Spécifie un fichier PEM contenant le certificat de l'AC que ovs-vsctl doit utiliser pour vérifier les certificats qui lui sont présentés par les pairs SSL/TLS. (Cela peut être le même certificat que les pairs SSL/TLS utilisent pour vérifier le certificat spécifié dans -c ou --certificate, ou il peut être différent, selon la conception de la PKI utilisée.)
-C none

--ca-cert=none
Désactive la vérification des certificats présentés par les pairs SSL/TLS. Cela introduit un risque de sécurité, car cela signifie que les certificats ne peuvent pas être vérifiés comme étant ceux d'hôtes connus et fiables.
--bootstrap-ca-cert=cacert.pem
Lorsque cacert.pem existe, cette option a le même effet que -C ou --ca-cert. S'il n'existe pas, alors ovs-vsctl tentera d'obtenir le certificat de l'AC auprès du pair SSL/TLS lors de sa première connexion SSL/TLS et l'enregistrera dans le fichier PEM nommé. S'il réussit, il abandonnera immédiatement la connexion et se reconnectera, et à partir de ce moment-là, toutes les connexions SSL/TLS devront être authentifiées par un certificat signé par le certificat de l'AC ainsi obtenu.
Cette option expose la connexion SSL/TLS à une attaque de l'homme du milieu lors de l'obtention du certificat de l'AC initial, mais elle peut être utile pour le bootstrapping.
Cette option n'est utile que si le pair SSL/TLS envoie son certificat d'AC dans le cadre de la chaîne de certificats SSL/TLS. Les protocoles SSL/TLS n'exigent pas que le serveur envoie le certificat de l'AC.
Cette option est mutuellement exclusive avec -C et --ca-cert.
--peer-ca-cert=peer-cacert.pem
Spécifie un fichier PEM qui contient un ou plusieurs certificats supplémentaires à envoyer aux pairs SSL/TLS. peer-cacert.pem doit être le certificat de l'AC utilisé pour signer le propre certificat de ovs-vsctl, c'est-à-dire le certificat spécifié dans -c ou --certificate. Si le certificat de ovs-vsctl est auto-signé, alors --certificate et --peer-ca-cert doivent spécifier le même fichier.
Cette option n'est pas utile en fonctionnement normal, car le pair SSL/TLS doit déjà posséder le certificat de l'AC pour que le pair ait confiance dans l'identité de ovs-vsctl. Cependant, cela offre un moyen à une nouvelle installation de bootstrappper le certificat de l'AC lors de sa première connexion SSL/TLS.
-v[spec]

--verbose=[spec]
Définit les niveaux de journalisation. Sans aucun spec, définit le niveau de journalisation pour chaque module et destination sur dbg. Sinon, spec est une liste de mots séparés par des espaces, des virgules ou des deux-points, au plus un de chaque catégorie ci-dessous :
  • Un nom de module valide, tel qu'affiché par la commande vlog/list sur ovs-appctl(8), limite le changement de niveau de journalisation au module spécifié.
  • syslog, console ou file, pour limiter le changement de niveau de journalisation uniquement au journal système, à la console ou à un fichier, respectivement. (Si --detach est spécifié, ovs-vsctl ferme ses descripteurs de fichiers standard, de sorte que la journalisation sur la console n'aura aucun effet.)
Sur la plateforme Windows, syslog est accepté comme mot et n'est utile qu'avec l'option --syslog-target (le mot n'a aucun effet sinon).
•
off, emer, err, warn, info ou dbg, pour contrôler le niveau de journalisation. Les messages de la sévérité donnée ou supérieure seront enregistrés, et les messages de sévérité inférieure seront filtrés. off filtre tous les messages. Voir ovs-appctl(8) pour une définition de chaque niveau de journalisation.
La casse n'est pas significative dans spec.
Indépendamment des niveaux de journalisation définis pour file, la journalisation dans un fichier n'aura pas lieu à moins que --log-file ne soit également spécifié (voir ci-dessous).
Pour la compatibilité avec les anciennes versions d'OVS, any est accepté comme mot mais n'a aucun effet.
-v

--verbose
Définit le niveau de verbosité de journalisation maximal, équivalent à --verbose=dbg.
-vPATTERN:destination:pattern

--verbose=PATTERN:destination:pattern
Définit le modèle de journalisation pour destination sur pattern. Reportez-vous à ovs-appctl(8) pour une description de la syntaxe valide pour pattern.
-vFACILITY:facility

--verbose=FACILITY:facility
Définit la facilité RFC5424 du message de journal. facility peut être l'une des suivantes : kern, user, mail, daemon, auth, syslog, lpr, news, uucp, clock, ftp, ntp, audit, alert, clock2, local0, local1, local2, local3, local4, local5, local6 ou local7. Si cette option n'est pas spécifiée, daemon est utilisé par défaut pour le syslog du système local et local0 est utilisé lors de l'envoi d'un message à la cible fournie via l'option --syslog-target.
--log-file[=file]
Active la journalisation dans un fichier. Si file est spécifié, il est utilisé comme nom exact pour le fichier journal. Le nom de fichier journal par défaut utilisé si file est omis est /var/log/openvswitch/ovs-vsctl.log.
--syslog-target=host:port
Envoie les messages syslog au port UDP port sur host, en plus du syslog système. L'host doit être une adresse IP numérique, pas un nom d'hôte.
--syslog-method=method
Spécifie la méthode d'envoi des messages syslog au démon syslog. Les formes suivantes sont prises en charge :
  • libc, utilise la fonction syslog() de libc. L'inconvénient de cette option est que libc ajoute un préfixe fixe à chaque message avant qu'il ne soit réellement envoyé au démon syslog via le socket de domaine UNIX /dev/log.
  • unix:file, utilise directement un socket de domaine UNIX. Il est possible de spécifier un format de message arbitraire avec cette option. Cependant, rsyslogd 8.9 et les versions antérieures utilisent de toute façon une fonction d'analyse codée en dur, ce qui limite l'utilisation des sockets de domaine UNIX. Si vous souhaitez utiliser un format de message arbitraire avec d'anciennes versions de rsyslogd, utilisez plutôt un socket UDP vers l'adresse IP de localhost.
  • udp:ip:port, utilise un socket UDP. Avec cette méthode, il est possible d'utiliser un format de message arbitraire également avec d'anciennes versions de rsyslogd. Lors de l'envoi de messages syslog via un socket UDP, des précautions supplémentaires doivent être prises en compte, par exemple, le démon syslog doit être configuré pour écouter sur le port UDP spécifié, des règles iptables accidentelles pourraient interférer avec le trafic syslog local et il existe certaines considérations de sécurité qui s'appliquent aux sockets UDP, mais pas aux sockets de domaine UNIX.
  • null, rejette tous les messages envoyés au syslog.
La valeur par défaut est prise de la variable d'environnement OVS_SYSLOG_METHOD ; si elle n'est pas définie, la valeur par défaut est libc.
-h

--help
Affiche un bref message d'aide sur la console.
-V

--version
Affiche les informations de version sur la console.

COMMANDES

Les commandes implémentées par ovs-vsctl sont décrites dans les sections ci-dessous.

Commandes Open vSwitch

Ces commandes fonctionnent avec une instance Open vSwitch dans son ensemble.

init
Initialise la base de données Open vSwitch, si elle est vide. Si la base de données a déjà été initialisée, cette commande n'a aucun effet.
Toute commande ovs-vsctl réussie initialise automatiquement la base de données Open vSwitch si elle est vide. Cette commande est fournie pour initialiser la base de données sans exécuter aucune autre commande.
show
Affiche un bref aperçu du contenu de la base de données.
emer-reset
Réinitialise la configuration à un état propre. Elle déconfigure les contrôleurs OpenFlow, les serveurs OVSDB et SSL/TLS, et supprime la duplication de ports, la configuration fail_mode, NetFlow, sFlow et IPFIX. Cette commande supprime également toutes les clés other-config de tous les enregistrements de la base de données, à l'exception de other-config:hwaddr qui est préservée si elle est présente dans un enregistrement Bridge. Les autres configurations réseau sont laissées telles qu'elles sont.

Commandes Bridge

Ces commandes examinent et manipulent les ponts Open vSwitch.

[--may-exist] add-br bridge
Crée un nouveau pont nommé bridge. Initialement, le pont n'aura aucun port (autre que le pont lui-même).
Sans --may-exist, tenter de créer un pont qui existe est une erreur. Avec --may-exist, cette commande ne fait rien si bridge existe déjà en tant que pont réel.
[--may-exist] add-br bridge parent vlan
Crée un « faux pont » nommé bridge au sein du pont Open vSwitch existant parent, qui doit déjà exister et ne doit pas lui-même être un faux pont. Le nouveau faux pont sera sur le VLAN 802.1Q vlan, qui doit être un entier compris entre 0 et 4095. Le pont parent ne doit pas déjà avoir de faux pont pour vlan. Initialement, bridge n'aura aucun port (autre que le pont lui-même).
Sans --may-exist, tenter de créer un pont qui existe est une erreur. Avec --may-exist, cette commande ne fait rien si bridge existe déjà en tant que pont VLAN sous parent pour vlan.
[--if-exists] del-br bridge
Supprime bridge et tous ses ports. Si bridge est un pont réel, cette commande supprime également tous les faux ponts qui ont été créés avec bridge comme parent, y compris tous leurs ports.
Sans --if-exists, tenter de supprimer un pont qui n'existe pas est une erreur. Avec --if-exists, tenter de supprimer un pont qui n'existe pas n'a aucun effet.
[--real|--fake] list-br
Liste tous les ponts réels et faux existants sur la sortie standard, un par ligne. Avec --real ou --fake, seuls les ponts de ce type sont renvoyés.
br-exists bridge
Teste si bridge existe en tant que pont réel ou faux. Si c'est le cas, ovs-vsctl se termine avec succès avec le code de sortie 0. Sinon, ovs-vsctl se termine avec échec avec le code de sortie 2.
br-to-vlan bridge
Si bridge est un faux pont, affiche le VLAN 802.1Q du pont sous forme d'entier décimal. Si bridge est un pont réel, affiche 0.
br-to-parent bridge
Si bridge est un faux pont, affiche le nom de son pont parent. Si bridge est un pont réel, affiche bridge.
br-set-external-id bridge key [value]
Définit ou efface une valeur d'"ID externe" sur bridge. Ces valeurs sont destinées à identifier des entités externes à Open vSwitch avec lesquelles bridge est associé, par exemple l'identifiant du pont dans une plateforme de gestion de la virtualisation. Le schéma de base de données d'Open vSwitch spécifie des valeurs de key connues, mais key et value sont autrement des chaînes arbitraires.
Si value est spécifié, alors key est défini sur value pour bridge, écrasant toute valeur précédente. Si value est omis, alors key est supprimé de l'ensemble des IDs externes de bridge (s'il était présent).
Pour les ponts réels, l'effet de cette commande est similaire à celui d'une commande set ou remove dans la colonne external-ids de la table Bridge. Pour les faux ponts, elle modifie réellement des clés dont les noms sont préfixés par fake-bridge- dans la table Port.
br-get-external-id bridge [key]
Interroge les IDs externes sur bridge. Si key est spécifié, la sortie est la valeur pour cette key ou une chaîne vide si key n'est pas définie. Si key est omis, la sortie est key=value, une par ligne, pour chaque paire clé-valeur.
Pour les ponts réels, l'effet de cette commande est similaire à celui d'une commande get dans la colonne external-ids de la table Bridge. Pour les faux ponts, elle interroge des clés dont les noms sont préfixés par fake-bridge- dans la table Port.

Commandes Port

Ces commandes examinent et manipulent les ports Open vSwitch. Ces commandes traitent un port agrégé comme une seule entité.

list-ports bridge
Liste tous les ports du bridge sur la sortie standard, un par ligne. Le port local bridge n'est pas inclus dans la liste.
[--may-exist] add-port bridge port [column[:key]=value]...
Crée sur bridge un nouveau port nommé port à partir du périphérique réseau du même nom.
Les arguments optionnels définissent les valeurs de colonne dans l'enregistrement Port créé par la commande. Par exemple, tag=9 ferait du port un port d'accès pour le VLAN 9. La syntaxe est la même que celle de la commande set (voir Commandes de base de données ci-dessous).
Sans --may-exist, tenter de créer un port qui existe est une erreur. Avec --may-exist, cette commande ne fait rien si port existe déjà sur bridge et n'est pas un port agrégé.
[--if-exists] del-port [bridge] port
Supprime port. Si bridge est omis, port est supprimé du pont qui le contient ; si bridge est spécifié, il doit s'agir du pont réel ou faux qui contient port.
Sans --if-exists, tenter de supprimer un port qui n'existe pas est une erreur. Avec --if-exists, tenter de supprimer un port qui n'existe pas n'a aucun effet.
[--if-exists] --with-iface del-port [bridge] iface
Supprime le port nommé iface ou qui a une interface nommée iface. Si bridge est omis, le port est supprimé du pont qui le contient ; si bridge est spécifié, il doit s'agir du pont réel ou faux qui contient le port.
Sans --if-exists, tenter de supprimer le port d'une interface qui n'existe pas est une erreur. Avec --if-exists, tenter de supprimer le port d'une interface qui n'existe pas n'a aucun effet.
port-to-br port
Affiche le nom du pont qui contient port sur la sortie standard.

Commandes Bond

Ces commandes fonctionnent avec des ports qui ont plusieurs interfaces, ce qu'Open vSwitch appelle des « bonds ».

[--fake-iface] add-bond bridge port iface... [column[:key]=value]...
Crée sur bridge un nouveau port nommé port qui agrège les périphériques réseau donnés sous chaque iface. Au moins deux interfaces doivent être nommées. Si les interfaces sont activées DPDK, la transaction devra inclure des opérations pour définir explicitement le type d'interface sur 'dpdk'.
Les arguments optionnels définissent les valeurs de colonne dans l'enregistrement Port créé par la commande. La syntaxe est la même que celle de la commande set (voir Commandes de base de données ci-dessous).
Avec --fake-iface, une interface factice nommée port est créée. Cela ne devrait être utilisé que pour la compatibilité avec les anciens logiciels qui l'exigent.
Sans --may-exist, tenter de créer un port qui existe est une erreur. Avec --may-exist, cette commande ne fait rien si port existe déjà sur bridge et agrège exactement les interfaces spécifiées.
[--may-exist] add-bond-iface bond iface
Ajoute iface comme nouvelle interface de bond au port existant bond. Si bond n'avait précédemment qu'un seul port, cela le transforme en bond.
Sans --may-exist, tenter d'ajouter une iface qui fait déjà partie de bond est une erreur. Avec --may-exist, cette commande ne fait rien si iface fait déjà partie de bond. (Il est toujours erroné si iface est une interface d'un autre port ou bond.)
[--if-exists] del-bond-iface [bond] iface
Supprime iface de son port. Si bond est omis, iface est supprimé du port qui le contient ; si bond est spécifié, il doit s'agir du port qui contient bond.
Si la suppression de iface fait que son port n'a qu'une seule int
interface, alors ce port est transformé d'un port lié en un port ordinaire. C'est une erreur si iface est la seule interface dans son port.
Sans --if-exists, tenter de supprimer une interface qui n'existe pas est une erreur. Avec --if-exists, tenter de supprimer une interface qui n'existe pas n'a aucun effet.

Commandes d'Interface

Ces commandes examinent les interfaces attachées à un pont Open vSwitch. Ces commandes traitent un port lié comme une collection de deux interfaces ou plus, plutôt que comme un seul port.

list-ifaces bridge
Liste toutes les interfaces dans bridge sur la sortie standard, une par ligne. Le port local bridge n'est pas inclus dans la liste.
iface-to-br iface
Imprime le nom du pont qui contient iface sur la sortie standard.

Commandes de Zone Conntrack

Ces commandes interrogent et modifient les zones CT du datapath, les stratégies de délai d'attente et les limites.

[--may-exist] add-zone-tp datapath zone=zone_id policies
Crée une politique de délai d'attente de zone conntrack avec zone_id dans datapath. Les policies se composent de paires key=value, séparées par des espaces. Par exemple, icmp_first=30 icmp_reply=60 spécifie une politique de délai d'attente de 30 secondes pour le premier paquet ICMP et une politique de 60 secondes pour les paquets de réponse ICMP. Voir la table CT_Timeout_Policy dans ovs-vswitchd.conf.db(5) pour les clés supportées.
Sans --may-exist, tenter d'ajouter une policy pour zone_id qui a déjà une politique est une erreur.
Avec --may-exist, cette commande ne fait rien si la politique pour
zone_id existe déjà.

list-zone-tp datapath
Imprime les politiques de délai d'attente de toutes les zones dans datapath.

Connectivité du Contrôleur OpenFlow

ovs-vswitchd peut effectuer toutes les opérations de pontage et de commutation configurées localement, ou il peut être configuré pour communiquer avec un ou plusieurs contrôleurs OpenFlow externes. Le commutateur est généralement configuré pour se connecter à un contrôleur principal qui prend en charge la table de flux du pont pour implémenter une politique réseau. De plus, le commutateur peut être configuré pour écouter les connexions des contrôleurs de service. Les contrôleurs de service sont généralement utilisés pour le support et la maintenance occasionnels, par exemple avec ovs-ofctl.

get-controller bridge
Imprime la cible du contrôleur configurée.
del-controller bridge
Supprime la cible du contrôleur configurée.
set-controller bridge target...
Définit la ou les cibles du contrôleur configurées. Chaque target peut utiliser l'une des formes suivantes :
ssl:host[:port]

tcp:host[:port]
Le port spécifié sur le host donné, qui peut être exprimé soit comme un nom DNS (si compilé avec la bibliothèque unbound) soit comme une adresse IP au format IPv4 ou IPv6. Encadrez les adresses IPv6 entre crochets, par exemple, tcp:[::1]:6653. Sous Linux, utilisez %device pour désigner une portée pour les adresses de niveau lien IPv6, par exemple, tcp:[fe80::1234%eth0]:6653. Pour ssl, les options --private-key, --certificate et --ca-cert sont obligatoires.
Si port n'est pas spécifié, il est par défaut à 6653.
unix:file
Sur POSIX, un socket serveur de domaine Unix nommé file.
Sous Windows, connectez-vous à un pipe nommé local qui est représenté par un fichier créé dans le chemin file pour imiter le comportement d'un socket de domaine Unix.
pssl:[port][:host]

ptcp:[port][:host]
Écoute les connexions OpenFlow sur le port. Le port par défaut est 6653. Par défaut, les connexions sont autorisées depuis n'importe quelle adresse IPv4. Spécifiez host comme une adresse IPv4 ou une adresse IPv6 entre crochets (par exemple, ptcp:6653:[::1]). Sous Linux, utilisez %device pour désigner une portée pour les adresses de niveau lien IPv6, par exemple, ptcp:6653:[fe80::1234%eth0]. Les noms DNS peuvent être utilisés s'ils sont compilés avec la bibliothèque unbound. Pour pssl, les options --private-key, --certificate et --ca-cert sont obligatoires.
punix:file
Écoute les connexions OpenFlow sur le socket serveur de domaine Unix nommé file.
Paramètres de défaillance du contrôleur

Lorsqu'un contrôleur est configuré, il est, en général, responsable de la mise en place de tous les flux sur le commutateur. Ainsi, si la connexion au contrôleur échoue, aucune nouvelle connexion réseau ne peut être établie. Si la connexion au contrôleur reste coupée assez longtemps, aucun paquet ne peut transiter par le commutateur.

Si la valeur est standalone, ou si aucun de ces paramètres n'est défini, ovs-vswitchd prendra en charge la mise en place des flux lorsqu'aucun message n'a été reçu du contrôleur pendant trois fois l'intervalle de sonde d'inactivité. Dans ce mode, ovs-vswitchd fait agir le datapath comme un commutateur ordinaire apprenant les adresses MAC. ovs-vswitchd continuera à essayer de se connecter au contrôleur en arrière-plan et, lorsque la connexion réussira, il cessera son comportement autonome.

Si cette option est définie sur secure, ovs-vswitchd ne mettra pas en place de flux de manière autonome lorsque la connexion du contrôleur échouera.

get-fail-mode bridge
Imprime le mode de défaillance configuré.
del-fail-mode bridge
Supprime le mode de défaillance configuré.
set-fail-mode bridge standalone|secure
Définit le mode de défaillance configuré.

Configuration SSL/TLS

Lorsque ovs-vswitchd est configuré pour se connecter via SSL/TLS pour la gestion ou la connectivité du contrôleur, les paramètres suivants sont requis :

Spécifie un fichier PEM contenant la clé privée utilisée comme identité du commutateur virtuel pour les connexions SSL/TLS au contrôleur.

Spécifie un fichier PEM contenant un certificat, signé par l'autorité de certification (CA) utilisée par le contrôleur et le gestionnaire, qui certifie la clé privée du commutateur virtuel, identifiant un commutateur digne de confiance.

Spécifie un fichier PEM contenant le certificat CA utilisé pour vérifier que le commutateur virtuel est connecté à un contrôleur digne de confiance.

Ces fichiers

Une fois lus uniquement, au moment du démarrage de **ovs-vswitchd**. Si leur contenu change, **ovs-vswitchd** doit être arrêté et redémarré.

Ces paramètres SSL/TLS s'appliquent à toutes les connexions SSL/TLS établies par le commutateur virtuel.

get-ssl
Affiche la configuration SSL/TLS.
del-ssl
Supprime la configuration SSL/TLS actuelle.
[--bootstrap] set-ssl clé-privée certificat cert-ca
Définit la configuration SSL/TLS. L'option --bootstrap est décrite ci-dessous.
Amorçage du certificat de l'autorité de certification (CA)

Normalement, tous les fichiers nommés dans la configuration SSL/TLS doivent exister au démarrage de **ovs-vswitchd**. Cependant, si le fichier cert-ca n'existe pas et que l'option --bootstrap est fournie, **ovs-vswitchd** tentera d'obtenir le certificat de l'autorité de certification à partir du contrôleur lors de sa première connexion SSL/TLS et de l'enregistrer dans le fichier PEM spécifié. S'il réussit, il interrompra immédiatement la connexion et se reconnectera, et à partir de ce moment, toutes les connexions SSL/TLS devront être authentifiées par un certificat signé par le certificat de l'autorité de certification ainsi obtenu.

Cette option expose la connexion SSL/TLS à une attaque de l'homme du milieu lors de l'obtention du certificat de l'autorité de certification initial, mais elle peut être utile pour l'amorçage.

Cette option n'est utile que si le contrôleur envoie son certificat de l'autorité de certification dans le cadre de la chaîne de certificats SSL/TLS. Les protocoles SSL/TLS n'exigent pas que le contrôleur envoie le certificat de l'autorité de certification.

Commandes Auto-Attach

La norme IETF Auto-Attach SPBM draft décrit une méthode compacte pour utiliser le protocole LLDP (IEEE 802.1AB Link Layer Discovery Protocol) avec un réseau SPB (IEEE 802.1aq Shortest Path Bridging) pour attacher automatiquement les périphériques réseau à des services individuels dans un réseau SPB. L'intention est de permettre aux applications réseau et aux périphériques utilisant OVS de profiter facilement des fonctionnalités offertes par les réseaux SPB standard de l'industrie. Un élément fondamental de la fonctionnalité Auto-Attach est de mapper les VLAN traditionnels sur les I_SID de SPB. Ces commandes gèrent les mappages I-SID/VLAN Auto-Attach.

add-aa-mapping pont i-sid vlan
Crée un nouveau mappage Auto-Attach sur pont pour i-sid et vlan.
del-aa-mapping pont i-sid vlan
Supprime un mappage Auto-Attach sur pont pour i-sid et vlan.
get-aa-mapping pont
Liste tous les mappages Auto-Attach au sein de pont sur la sortie standard.

Commandes Base de données

Ces commandes interrogent et modifient le contenu des tables **ovsdb**. Elles constituent une légère abstraction de l'interface **ovsdb** et, en tant que telles, elles fonctionnent à un niveau inférieur à celui des autres commandes **ovs-vsctl**.

Identification des tables, enregistrements et colonnes

Chacune de ces commandes possède un paramètre table pour identifier une table dans la base de données. Beaucoup d'entre elles prennent également un paramètre record qui identifie un enregistrement particulier dans une table. Le paramètre record peut être l'UUID d'un enregistrement, et de nombreuses tables offrent des moyens supplémentaires d'identifier les enregistrements. Certaines commandes prennent également des paramètres column qui identifient un champ particulier dans les enregistrements d'une table.

Pour une liste des tables et de leurs colonnes, voir ovs-vswitchd.conf.db(5) ou la liste des tables obtenue avec l'option --help.

Les noms des enregistrements doivent être spécifiés en entier et avec la casse correcte, à l'exception des UUID qui peuvent être abrégés à leurs 4 (ou plus) premiers chiffres hexadécimaux, tant que cela est unique dans la table. Les noms des tables et des colonnes ne sont pas sensibles à la casse, et - et _ sont traités de manière interchangeable. Des abréviations uniques des noms de tables et de colonnes sont acceptables, par exemple net ou n suffit pour identifier la table NetFlow.

Valeurs de base de données

Chaque colonne de la base de données accepte un type de données fixe. Les types de base actuellement définis, et leurs représentations, sont les suivants :

entier
Un entier décimal dans la plage de -2**63 à 2**63-1, inclus.
réel
Un nombre à virgule flottante.
Booléen
Vrai ou faux, écrit vrai ou faux, respectivement.
chaîne
Une chaîne Unicode arbitraire, à l'exception des octets nuls qui ne sont pas autorisés. Les guillemets sont facultatifs pour la plupart des chaînes qui commencent par une lettre anglaise ou un trait de soulignement et qui ne contiennent que des lettres, des traits de soulignement, des tirets et des points. Cependant, vrai et faux, ainsi que les chaînes qui correspondent à la syntaxe des UUID (voir ci-dessous), doivent être entourées de guillemets doubles pour les distinguer des autres types de base. Lorsque des guillemets doubles sont utilisés, la syntaxe est celle des chaînes en JSON, par exemple, les barres obliques inverses peuvent être utilisées pour échapper les caractères spéciaux. La chaîne vide doit être représentée par une paire de guillemets doubles ("").
UUID
Soit un identifiant unique universel dans le style de la RFC 4122, par exemple, f81d4fae-7dec-11d0-a765-00a0c91e6bf6, soit un nom @nom défini par une commande get ou create dans la même invocation **ovs-vsctl**.

Plusieurs valeurs dans une seule colonne peuvent être séparées par des espaces ou une seule virgule. Lorsque plusieurs valeurs sont présentes, les doublons ne sont pas autorisés et l'ordre n'a pas d'importance. Inversement, certaines colonnes de base de données peuvent avoir un ensemble vide de valeurs, représenté par [], et des crochets peuvent éventuellement entourer d'autres ensembles non vides ou des valeurs uniques. Pour une colonne acceptant un ensemble d'entiers, les commandes de base de données acceptent une plage. Une plage est représentée par deux entiers séparés par -. Une plage est inclusive. Une plage a une taille maximale de 4096 éléments. Si plus d'éléments sont nécessaires, ils peuvent être spécifiés dans des plages séparées.

Quelques colonnes de base de données sont des ``maps'' de paires clé-valeur, où la clé et la valeur sont chacune d'un type de base de données fixe. Celles-ci sont spécifiées sous la forme clé=valeur, où clé et valeur suivent la syntaxe du type de clé et du type de valeur de la colonne, respectivement. Lorsque plusieurs paires sont présentes (séparées par des espaces ou une virgule), les doublons de clés ne sont pas autorisés et l'ordre n'a pas non plus d'importance. Les doublons de valeurs sont autorisés. Une map vide est représentée par {}. Des accolades peuvent éventuellement entourer des maps non vides également (mais utilisez des guillemets pour empêcher le shell d'étendre other-config={0=x,1=y} en other-config=0=x other-config=1=y, ce qui pourrait ne pas avoir l'effet désiré).

Syntaxe des commandes de base de données
[--if-exists] [--columns=colonne[,colonne]...] list table [enregistrement]...
Liste les données de chaque enregistrement spécifié. Si aucun enregistrement n'est spécifié, liste tous les enregistrements de la table.
Si --columns est spécifié, seules les colonnes demandées sont listées, dans l'ordre spécifié. Sinon, toutes les colonnes sont listées, par ordre alphabétique du nom de la colonne.
Sans --if-exists, c'est une erreur si un enregistrement spécifié n'existe pas. Avec --if-exists, la commande ignore tout enregistrement qui n'existe pas, sans produire de sortie.
[--columns=colonne[,colonne]...] find table [colonne[:clé]=valeur]...
Liste les données de chaque enregistrement de la table dont la colonne est égale à la valeur ou, si une clé est spécifiée, dont la colonne contient une clé avec la valeur spécifiée. Les opérateurs suivants peuvent être utilisés à la place de = dans le résumé de la syntaxe :
= != < > <= >=
Sélectionne les enregistrements dans lesquels la colonne[:clé] est égale, différente, inférieure, supérieure, inférieure ou égale, ou supérieure ou égale à la valeur, respectivement.
Considérez la colonne[:clé] et la valeur comme des ensembles d'éléments. Des ensembles identiques sont considérés comme égaux. Sinon, si les ensembles ont un nombre différent d'éléments, l'ensemble avec le plus d'éléments est considéré comme plus grand. Sinon, considérez un élément de chaque ensemble par paires, dans l'ordre croissant au sein de chaque ensemble. La première paire qui diffère détermine le résultat. (Pour une colonne contenant des paires clé-valeur, d'abord toutes les clés sont comparées, et les valeurs ne sont considérées que si les deux ensembles contiennent des clés identiques.)
{=} {!=}
Test d'égalité ou d'inégalité d'ensembles, respectivement.
{<=}
Sélectionne les enregistrements dans lesquels la colonne[:clé] est un sous-ensemble de la valeur. Par exemple, flood-vlans{<=}1,2 sélectionne les enregistrements dans lesquels la colonne flood-vlans est l'ensemble vide ou contient 1 ou 2 ou les deux.
{<}
Sélectionne les enregistrements dans lesquels la colonne[:clé] est un sous-ensemble propre de la valeur. Par exemple, flood-vlans{<}1,2 sélectionne les enregistrements dans lesquels la colonne flood-vlans est l'ensemble vide ou contient 1 ou 2 mais pas les deux.
{>=} {>}
Identique à {<=} et {<}, respectivement, sauf que la relation est inversée. Par exemple, flood-vlans{>=}1,2 sélectionne les enregistrements dans lesquels la colonne flood-vlans contient à la fois 1 et 2.

Les opérateurs suivants sont disponibles uniquement dans Open vSwitch 2.16 et versions ultérieures :

{in}
Sélectionne les enregistrements dans lesquels chaque élément de colonne[:clé] est également dans la valeur. (Ceci est identique à {<=}.)
{not-in}
Sélectionne les enregistrements dans lesquels chaque élément de colonne[:clé] n'est pas dans la valeur.
Pour les opérateurs arithmétiques (= != < > <= >=), lorsque la clé est spécifiée mais qu'une colonne d'un enregistrement donné ne contient pas la clé, l'enregistrement est toujours omis des résultats. Ainsi, la condition other-config:mtu!=1500 correspond aux enregistrements qui ont une clé mtu dont la valeur n'est pas 1500, mais pas à ceux qui n'ont pas de clé mtu.
Pour les opérateurs d'ensembles, lorsque la clé est spécifiée
spécifié mais un colonne d'un enregistrement particulier ne contient pas clé, la comparaison est effectuée par rapport à un ensemble vide. Ainsi, la condition autre-config:mtu{!=}1500 correspond aux enregistrements qui ont une clé mtu dont la valeur n'est pas 1500 et à ceux qui n'ont pas de clé mtu.
N'oubliez pas d'échapper < ou > pour éviter leur interprétation par le shell.
Si --colonnes est spécifié, seules les colonnes demandées sont listées, dans l'ordre spécifié. Sinon, toutes les colonnes sont listées, par ordre alphabétique par nom de colonne.
Les UUID affichés pour les lignes créées dans la même invocation ovs-vsctl seront incorrects.
[--si-existe] [--id=@nom] get table enregistrement [colonne[:clé]]...
Affiche la valeur de chaque colonne spécifiée dans l'enregistrement donné dans la table. Pour les colonnes de type map, une clé peut facultativement être spécifiée, auquel cas la valeur associée à la clé dans la colonne est affichée, au lieu de la map entière.
Sans --si-existe, une erreur se produit si l'enregistrement n'existe pas ou si la clé est spécifiée, si la clé n'existe pas dans l'enregistrement. Avec --si-existe, un enregistrement manquant ne produit aucune sortie et une clé manquante affiche une ligne vide.
Si @nom est spécifié, alors l'UUID de l'enregistrement peut être référencé par ce nom plus tard dans la même invocation ovs-vsctl dans des contextes où un UUID est attendu.
--id et les arguments colonne sont facultatifs, mais généralement au moins l'un des deux devrait être spécifié. Si les deux sont omis, alors get n'a aucun effet autre que de vérifier que l'enregistrement existe dans la table.
--id et --si-existe ne peuvent pas être utilisés ensemble.
[--si-existe] set table enregistrement colonne[:clé]=valeur...
Définit la valeur de chaque colonne spécifiée dans l'enregistrement donné dans la table à valeur. Pour les colonnes de type map, une clé peut facultativement être spécifiée, auquel cas la valeur associée à la clé dans cette colonne est modifiée (ou ajoutée, si aucune n'existe), au lieu de la map entière.
Sans --si-existe, une erreur se produit si l'enregistrement n'existe pas. Avec --si-existe, cette commande ne fait rien si l'enregistrement n'existe pas.
[--si-existe] add table enregistrement colonne [clé=]valeur...
Ajoute la valeur spécifiée ou la paire clé-valeur à la colonne de l'enregistrement dans la table. Si la colonne est une map, alors la clé est requise, sinon elle est interdite. Si la clé existe déjà dans une colonne de map, alors la valeur actuelle n'est pas remplacée (utilisez la commande set pour remplacer une valeur existante).
Sans --si-existe, une erreur se produit si l'enregistrement n'existe pas. Avec --si-existe, cette commande ne fait rien si l'enregistrement n'existe pas.
[--si-existe] remove table enregistrement colonne valeur...

[--si-existe] remove table enregistrement colonne clé...

[--si-existe] remove table enregistrement colonne clé=valeur...
Supprime les valeurs spécifiées ou les paires clé-valeur de la colonne de l'enregistrement dans la table. La première forme s'applique aux colonnes qui ne sont pas des maps : chaque valeur spécifiée est supprimée de la colonne. La deuxième et la troisième forme s'appliquent aux colonnes de map : si seule une clé est spécifiée, alors toute paire clé-valeur avec la clé donnée est supprimée, quelle que soit sa valeur ; si une valeur est donnée alors une paire n'est supprimée que si la clé et la valeur correspondent.
Ce n'est pas une erreur si la colonne ne contient pas la clé ou la valeur ou la paire spécifiée.
Sans --si-existe, une erreur se produit si l'enregistrement n'existe pas. Avec --si-existe, cette commande ne fait rien si l'enregistrement n'existe pas.
[--si-existe] clear table enregistrement colonne...
Définit chaque colonne dans l'enregistrement de la table à l'ensemble vide ou à la map vide, selon le cas. Cette commande s'applique uniquement aux colonnes qui sont autorisées à être vides.
Sans --si-existe, une erreur se produit si l'enregistrement n'existe pas. Avec --si-existe, cette commande ne fait rien si l'enregistrement n'existe pas.
[--id=(@nom | uuid] create table colonne[:clé]=valeur...
Crée un nouvel enregistrement dans la table et définit les valeurs initiales de chaque colonne. Les colonnes non définies explicitement recevront leurs valeurs par défaut. Renvoie l'UUID de la nouvelle ligne.
Si @nom est spécifié, alors l'UUID de la nouvelle ligne peut être référencé par ce nom ailleurs dans la même invocation ovs-vsctl dans des contextes où un UUID est attendu. Ces références peuvent précéder ou suivre la commande create.
Si un uuid valide est spécifié, alors il est utilisé comme UUID de la nouvelle ligne.
Attention (ovs-vsctl comme exemple)
Les enregistrements dans la base de données Open vSwitch ne sont significatifs que lorsqu'ils peuvent être atteints directement ou indirectement depuis la table Open_vSwitch. À l'exception des enregistrements dans les tables QoS ou Queue, les enregistrements qui ne sont pas atteignables depuis la table Open_vSwitch sont automatiquement supprimés de la base de données. Cette suppression se produit immédiatement, sans attendre des commandes ovs-vsctl supplémentaires ou d'autres activités de la base de données. Ainsi, une commande create doit généralement être accompagnée de commandes supplémentaires au sein de la même invocation ovs-vsctl pour ajouter une chaîne de références à l'enregistrement nouvellement créé depuis l'enregistrement de haut niveau Open_vSwitch. La section EXEMPLES donne quelques exemples montrant comment faire cela.
[--si-existe] destroy table enregistrement...
Supprime chaque enregistrement spécifié de la table. Sauf si --si-existe est spécifié, chaque enregistrement doit exister.
--all destroy table
Supprime tous les enregistrements de la table.
Attention (ovs-vsctl comme exemple)
La commande destroy n'est utile que pour les enregistrements dans les tables QoS ou Queue. Les enregistrements dans d'autres tables sont automatiquement supprimés de la base de données lorsqu'ils deviennent inaccessibles depuis la table Open_vSwitch. Cela signifie que la suppression de la dernière référence à un enregistrement est suffisante pour supprimer l'enregistrement lui-même. Pour les enregistrements de ces tables, destroy est silencieusement ignoré. Voir la section EXEMPLES ci-dessous pour plus d'informations.
wait-until table enregistrement [colonne[:clé]=valeur]...
Attend jusqu'à ce que la table contienne un enregistrement nommé enregistrement dont la colonne est égale à valeur ou, si une clé est spécifiée, dont la colonne contient une clé avec la valeur spécifiée. Cette commande prend en charge les mêmes opérateurs et sémantiques décrits pour la commande find ci-dessus.
Si aucun argument colonne[:clé]=valeur n'est fourni, cette commande attend seulement que l'enregistrement existe. Si plus d'un argument de ce type est fourni, la commande attend jusqu'à ce que tous soient satisfaits.
Attention (ovs-vsctl comme exemple)
Généralement, wait-until devrait être placé au début d'un ensemble de commandes ovs-vsctl. Par exemple, wait-until bridge br0 -- get bridge br0 datapath_id attend qu'un pont nommé br0 soit créé, puis affiche sa colonne datapath_id, tandis que get bridge br0 datapath_id -- wait-until bridge br0 échouera s'il n'y a pas de pont nommé br0 lorsque ovs-vsctl se connecte initialement à la base de données.
Envisagez de spécifier --timeout=0 avec --wait-until, pour empêcher ovs-vsctl de se terminer après avoir attendu au maximum 5 secondes.
comment [arg]...
Cette commande n'a aucun effet sur le comportement, mais tout enregistrement de journal de base de données créé par la commande inclura la commande et ses arguments.

EXEMPLES

Créez un nouveau pont nommé br0 et ajoutez-y le port eth0 :

ovs-vsctl add-br br0
ovs-vsctl add-port br0 eth0

Alternativement, effectuez les deux opérations en une seule transaction atomique :

ovs-vsctl add-br br0 -- add-port br0 eth0

Supprimez le pont br0, en signalant une erreur s'il n'existe pas :

ovs-vsctl del-br br0

Supprimez le pont br0 s'il existe :

ovs-vsctl --si-existe del-br br0

Définissez la colonne qos de l'enregistrement Port pour eth0 afin qu'elle pointe vers un nouvel enregistrement QoS, qui à son tour pointe sa file d'attente 0 vers un nouvel enregistrement Queue :

ovs-vsctl -- set port eth0 qos=@newqos -- --id=@newqos create qos type=linux-htb other-config:max-rate=1000000 queues:0=@newqueue -- --id=@newqueue create queue other-config:min-rate=1000000 other-config:max-rate=1000000

CUISINE DE CONFIGURATION

Configuration des ports

Ajoutez un port "interne" vlan10 au pont br0 en tant que port d'accès VLAN pour le VLAN 10, et configurez-le avec une adresse IP :

ovs-vsctl add-port br0 vlan10 tag=10 -- set Interface vlan10 type=internal
ip addr add 192.168.0.123/24 dev vlan10

Ajoutez un port de tunnel GRE gre0 à l'adresse IP distante 1.2.3.4 au pont br0 :

ovs-vsctl add-port br0 gre0 -- set Interface gre0 type=gre options:remote_ip=1.2.3.4

Miroir de ports

ort Miroir

Miroir tous les paquets reçus ou envoyés sur eth0 ou eth1 vers eth2, en supposant que tous ces ports existent sur le pont br0 (par conséquent, tous les paquets reçus sur eth2 seront ignorés) :

ovs-vsctl -- set Bridge br0 mirrors=@m \
-- --id=@eth0 get Port eth0 \
-- --id=@eth1 get Port eth1 \
-- --id=@eth2 get Port eth2 \
-- --id=@m create Mirror name=mymirror select-dst-port=@eth0,@eth1 select-src-port=@eth0,@eth1 output-port=@eth2

Supprimer le miroir créé ci-dessus de br0, ce qui détruit également l'enregistrement de miroir (car il n'est plus référencé) :

ovs-vsctl -- --id=@rec get Mirror mymirror \
-- remove Bridge br0 mirrors @rec

La commande plus simple suivante fonctionne également :

ovs-vsctl clear Bridge br0 mirrors

Qualité de Service (QoS)

Créer un enregistrement QoS linux-htb qui pointe vers quelques files d'attente et l'utiliser sur eth0 et eth1 :

ovs-vsctl -- set Port eth0 qos=@newqos \
-- set Port eth1 qos=@newqos \
-- --id=@newqos create QoS type=linux-htb other-config:max-rate=1000000000 queues=0=@q0,1=@q1 \
-- --id=@q0 create Queue other-config:min-rate=100000000 other-config:max-rate=100000000 \
-- --id=@q1 create Queue other-config:min-rate=500000000

Désactiver l'enregistrement QoS ci-dessus sur eth1 uniquement :

ovs-vsctl clear Port eth1 qos

Pour désactiver l'enregistrement QoS sur eth0 et eth1, puis supprimer l'enregistrement QoS (ce qui doit être fait explicitement car les enregistrements QoS non référencés ne sont pas automatiquement détruits) :

ovs-vsctl -- destroy QoS eth0 -- clear Port eth0 qos -- clear Port eth1 qos

(Cette commande laissera deux enregistrements de file d'attente non référencés dans la base de données. Pour les supprimer, utilisez "ovs-vsctl list Queue" pour trouver leurs UUID, puis "ovs-vsctl destroy Queue uuid1 uuid2" pour détruire chacun d'eux ou utilisez "ovs-vsctl -- --all destroy Queue" pour supprimer tous les enregistrements.)

Surveillance de la connectivité

Surveiller la connectivité à un point de maintenance distant sur eth0.

ovs-vsctl set Interface eth0 cfm_mpid=1

Désactiver la surveillance de la connectivité ci-dessus :

ovs-vsctl clear Interface eth0 cfm_mpid

NetFlow

Configurer le pont br0 pour envoyer des enregistrements NetFlow au port UDP 5566 sur l'hôte 192.168.0.34, avec un délai d'expiration actif de 30 secondes :

ovs-vsctl -- set Bridge br0 netflow=@nf \
-- --id=@nf create NetFlow targets=\"192.168.0.34:5566\" active-timeout=30

Mettre à jour la configuration NetFlow créée par la commande précédente pour utiliser un délai d'expiration actif de 60 secondes :

ovs-vsctl set NetFlow br0 active_timeout=60

Désactiver la configuration NetFlow du pont br0, ce qui détruit également l'enregistrement NetFlow (car il n'est plus référencé) :

ovs-vsctl clear Bridge br0 netflow

sFlow

Configurer le pont br0 pour envoyer des enregistrements sFlow à un collecteur sur 10.0.0.1 au port 6343, en utilisant l'adresse IP de eth1 comme source, avec des paramètres d'échantillonnage spécifiques :

ovs-vsctl -- --id=@s create sFlow agent=eth1 target=\"10.0.0.1:6343\" header=128 sampling=64 polling=10 \
-- set Bridge br0 sflow=@s

Désactiver sFlow du pont br0, ce qui détruit également l'enregistrement sFlow (car il n'est plus référencé) :

ovs-vsctl -- clear Bridge br0 sflow

IPFIX

Configurer le pont br0 pour envoyer un enregistrement de flux IPFIX par échantillon de paquet au port UDP 4739 sur l'hôte 192.168.0.34, avec un ID de domaine d'observation (Obs Domain ID) de 123 et un ID de point d'observation (Obs Point ID) de 456, un délai d'expiration actif du cache de flux de 1 minute (60 secondes), une taille maximale du cache de flux de 13 flux, et des flux échantillonnés sur le port de sortie avec des informations de tunnel (l'échantillonnage sur les ports d'entrée et de sortie est activé par défaut s'il n'est pas désactivé) :

ovs-vsctl -- set Bridge br0 ipfix=@i \
-- --id=@i create IPFIX targets=\"192.168.0.34:4739\" obs_domain_id=123 obs_point_id=456 cache_active_timeout=60 cache_max_flows=13 \
other_config:enable-input-sampling=false other_config:enable-tunnel-sampling=true

Désactiver la configuration IPFIX du pont br0, ce qui détruit également l'enregistrement IPFIX (car il n'est plus référencé) :

ovs-vsctl clear Bridge br0 ipfix

802.1D Protocole d'arbre couvrant (STP)

Configurer le pont br0 pour participer à un arbre couvrant 802.1D :

ovs-vsctl set Bridge br0 stp_enable=true

Définir la priorité du pont br0 à 0x7800 :

ovs-vsctl set Bridge br0 other_config:stp-priority=0x7800

Définir le coût de chemin du port eth0 à 10 :

ovs-vsctl set Port eth0 other_config:stp-path-cost=10

Désactiver le STP ci-dessus :

ovs-vsctl set Bridge br0 stp_enable=false

Multicast Snooping

Configurer le pont br0 pour activer le multicast snooping :

ovs-vsctl set Bridge br0 mcast_snooping_enable=true

Définir le temps de vieillissement du multicast snooping de br0 à 300 secondes :

ovs-vsctl set Bridge br0 other_config:mcast-snooping-aging-time=300

Définir la taille de la table de multicast snooping de br0 à 2048 entrées :

ovs-vsctl set Bridge br0 other_config:mcast-snooping-table-size=2048

Désactiver l'inondation des paquets multicast non enregistrés vers tous les ports. Lorsque défini sur true, le commutateur enverra les paquets multicast non enregistrés uniquement aux ports connectés aux routeurs multicast. Lorsqu'il est défini sur false, le commutateur les enverra à tous les ports. Cette commande désactive l'inondation des paquets non enregistrés sur le pont br0.

ovs-vsctl set Bridge br0 other_config:mcast-snooping-disable-flood-unregistered=true

Activer l'inondation des paquets multicast (sauf Rapports) sur un port spécifique.

ovs-vsctl set Port eth1 other_config:mcast-snooping-flood=true

Activer l'inondation des Rapports sur un port spécifique.

ovs-vsctl set Port eth1 other_config:mcast-snooping-flood-reports=true

Désactiver le multicasting snooping ci-dessus :

ovs-vsctl set Bridge br0 mcast_snooping_enable=false

802.1D-2004 Protocole d'arbre couvrant rapide (RSTP)

Configurer le pont br0 pour participer à un arbre couvrant rapide 802.1D-2004 :

ovs-vsctl set Bridge br0 rstp_enable=true

Définir l'adresse du pont br0 à 00:aa:aa:aa:aa:aa :

ovs-vsctl set Bridge br0 other_config:rstp-address=00:aa:aa:aa:aa:aa

Définir la priorité du pont br0 à 0x7000. La valeur doit être spécifiée en notation décimale et être un multiple de 4096 (sinon, elle est arrondie au multiple de 4096 inférieur le plus proche). La valeur de priorité par défaut est 0x800 (32768).

ovs-vsctl set Bridge br0 other_config:rstp-priority=28672

Définir le temps de vieillissement du pont br0 à 1000 s. La valeur du temps de vieillissement doit être comprise entre 10 s et 1000000 s. La valeur par défaut est 300 s.

ovs-vsctl set Bridge br0 other_config:rstp-ageing-time=1000

Définir la version du protocole de force du pont br0 à 0. La version du protocole de force a deux valeurs acceptables : 0 (mode de compatibilité STP) et 2 (fonctionnement normal).

ovs-vsctl set Bridge br0 other_config:rstp-force-protocol-version=0

Définir l'âge maximal du pont br0 à 10 s. La valeur de l'âge maximal doit être comprise entre 6 s et 40 s. La valeur par défaut est 20 s.

ovs-vsctl set Bridge br0 other_config:rstp-max-age=10

Définir le délai de transmission du pont br0 à 15 s. Cette valeur doit être comprise entre 4 s et 30 s. La valeur par défaut est 15 s.

ovs-vsctl set Bridge br0 other_config:rstp-forward-delay=15

Définir le nombre de maintenances de transmission du pont br0 à 7 s. Cette valeur doit être comprise entre 1 s et 10 s. La valeur par défaut est 6 s.

ovs-vsctl set Bridge br0 other_config:rstp-transmit-hold-count=7

Activer RSTP sur le port eth0 :

ovs-vsctl set Port eth0 other_config:rstp-enable=true

Désactiver RSTP sur le port eth0 :

ovs-vsctl set Port eth0 other_config:rstp-enable=false

Définir la priorité du port eth0 à 32. La valeur doit être spécifiée en notation décimale et être un multiple de 16 (sinon, elle est arrondie au multiple de 16 inférieur le plus proche). La valeur de priorité par défaut est 0x80 (128).

NOM

ovs-vsctl - utilitaire de configuration de l'Open vSwitch

SYNOPSIS

ovs-vsctl [options] -- command [ arg... ] [ -- command [ arg... ] ]...

DESCRIPTION

Le programme utilitaire ovs-vsctl interagit avec le démon ovs-vswitchd pour interroger et mettre à jour la base de données de configuration de l'Open vSwitch. Il est utilisé pour initialiser, configurer et interroger les commutateurs Open vSwitch.

Le programme ovs-vsctl prend une série de commandes et d'arguments. Les commandes sont traitées dans l'ordre où elles apparaissent. Lorsque plusieurs commandes sont spécifiées sur la ligne de commande, elles sont exécutées atomiquement dans une seule transaction. Si une commande échoue, aucune des commandes de la ligne de commande n'est exécutée.

Les options communes incluent :

--timeout=SECS
Définit le délai d'attente maximal pour les opérations sur la base de données OVSDB, en secondes.
--no-wait-interval
Ne pas utiliser d'intervalle d'attente lorsque le démon ovsdb-server n'est pas joignable. Utile pour une détection d'erreur rapide.
--format=FORMAT
Utilise FORMAT pour formater la sortie. Les formats pris en charge sont a ``table'', a ``list'', a ``csv'', et a ``json''. La valeur par défaut est table.
--data=FORMAT
Spécifie le format des données d'entrée. Les formats pris en charge sont a ``string'', a ``semicolon-separated'', a ``csv'', et a ``json''. La valeur par défaut est string.
--oneline
Produit une sortie plus compacte sur une seule ligne.
--bare
Produit une sortie plus compacte, sans en-têtes.
-H, --help
Affiche un message d'aide et quitte.
-V, --version
Affiche la version et quitte.

CONFIGURATION COOKBOOK

Voici quelques exemples de configuration courante :

Définir la priorité du port de l'interface eth0 pour RSTP sur 32 :

ovs-vsctl set Port eth0 other_config:rstp-port-priority=32

Définir le numéro de port de l'interface eth0 sur 3 :

ovs-vsctl set Port eth0 other_config:rstp-port-num=3

Définir le coût du chemin de l'interface eth0 sur 150 :

ovs-vsctl set Port eth0 other_config:rstp-path-cost=150

Définir la valeur de bord administratif de l'interface eth0 :

ovs-vsctl set Port eth0 other_config:rstp-port-admin-edge=true

Définir la valeur de bord automatique de l'interface eth0 :

ovs-vsctl set Port eth0 other_config:rstp-port-auto-edge=true

Définir la valeur MAC point à point administrative de l'interface eth0. Les valeurs acceptables sont 0 (pas point à point), 1 (point à point, la valeur par défaut) ou 2 (détection automatique). Le mode de détection automatique n'est pas actuellement implémenté, et la valeur 2 a le même effet que 0 (pas point à point).

ovs-vsctl set Port eth0 other_config:rstp-admin-p2p-mac=1

Définir la valeur d'état du port administratif de l'interface eth0. true est la valeur par défaut.

ovs-vsctl set Port eth0 other_config:rstp-admin-port-state=false

Définir la valeur mcheck de l'interface eth0 :

ovs-vsctl set Port eth0 other_config:rstp-port-mcheck=true

Déconfigurer RSTP à partir de ce qui précède :

ovs-vsctl set Bridge br0 rstp_enable=false

Version OpenFlow

Configurer le commutateur br0 pour prendre en charge les versions OpenFlow 1.0, 1.2 et 1.3 :

ovs-vsctl set bridge br0 protocols=OpenFlow10,OpenFlow12,OpenFlow13

Configuration Table Flux

Faire en sorte que la table de flux 0 sur le commutateur br0 refuse d'accepter plus de 100 flux :

ovs-vsctl -- --id=@ft create Flow_Table flow_limit=100 overflow_policy=refuse -- set Bridge br0 flow_tables=0=@ft

Faire en sorte que la table de flux 0 sur le commutateur br0 expulse les flux, avec une équité basée sur le port d'entrée correspondant, lorsqu'il y en a plus de 100 :

ovs-vsctl -- --id=@ft create Flow_Table flow_limit=100 overflow_policy=evict groups='"NXM_OF_IN_PORT[]"' -- set Bridge br0 flow_tables:0=@ft
