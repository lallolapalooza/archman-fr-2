NOM

os-release, initrd-release, extension-release - Identification du système d'exploitation

SYNTAXE

/etc/os-release
/usr/lib/os-release
/etc/initrd-release
/usr/lib/extension-release.d/extension-release.IMAGE

DESCRIPTION

Les fichiers /etc/os-release et /usr/lib/os-release contiennent des données d'identification du système d'exploitation.

Le format de os-release est une liste d'affectations de variables, séparées par des sauts de ligne et compatibles avec le shell. Il est possible de sourcer la configuration à partir de scripts shell Bourne, cependant, au-delà de simples affectations de variables, aucune fonctionnalité shell n'est prise en charge (cela signifie que l'expansion de variables n'est explicitement pas prise en charge), permettant aux applications de lire le fichier sans implémenter de moteur d'exécution compatible avec le shell. Les valeurs d'affectation de variables doivent être entourées de guillemets doubles ou simples si elles contiennent des espaces, des points-virgules ou d'autres caractères spéciaux en dehors de A–Z, a–z, 0–9. (Les affectations qui ne contiennent pas ces caractères spéciaux peuvent également être entourées de guillemets, mais c'est facultatif.) Les caractères spéciaux du shell ("$ ", guillemets, antislash, backtick) doivent être échappés avec des antislashs, suivant le style du shell. Toutes les chaînes doivent être encodées en UTF-8, et les caractères non imprimables ne doivent pas être utilisés. La concaténation de plusieurs chaînes individuellement citées n'est pas prise en charge. Les lignes commençant par "#" sont traitées comme des commentaires. Les lignes vides sont permises et ignorées.

Le fichier /etc/os-release a la priorité sur /usr/lib/os-release. Les applications doivent vérifier l'existence du premier et utiliser exclusivement ses données s'il existe, et ne recourir à /usr/lib/os-release que si celui-ci est manquant. Les applications ne doivent pas combiner les données des deux fichiers. /usr/lib/os-release est l'endroit recommandé pour stocker les informations de version de l'OS dans le cadre des arbres de vendeurs. /etc/os-release devrait être un lien symbolique relatif vers /usr/lib/os-release, pour assurer la compatibilité avec les applications qui ne recherchent que dans /etc/. Un lien symbolique relatif au lieu d'un lien symbolique absolu est nécessaire pour éviter de casser le lien dans un environnement chroot ou initrd.

os-release contient des données définies par le fournisseur du système d'exploitation et ne devrait généralement pas être modifié par l'administrateur.

Comme ce fichier ne code que des noms et des identifiants, il ne doit pas être localisé.

Les fichiers /etc/os-release et /usr/lib/os-release peuvent être des liens symboliques vers d'autres fichiers, mais il est important que le fichier soit disponible dès le début du démarrage et qu'il soit donc situé sur le système de fichiers racine.

os-release ne doit pas contenir de clés répétées. Néanmoins, les lecteurs doivent privilégier les entrées situées plus loin dans le fichier en cas de répétition, de manière similaire à ce qu'un shell ferait en sourçant le fichier. Un lecteur peut avertir des entrées répétées.

Pour une analyse plus approfondie d'os-release, veuillez vous référer à l'Annonce de /etc/os-release[1].

/etc/initrd-release

Dans l'initrd[2] et l'exitrd, /etc/initrd-release joue le même rôle que os-release dans le système principal. De plus, la présence de ce fichier signifie que le système est en phase initrd/exitrd. /etc/os-release devrait être lié symboliquement à /etc/initrd-release (ou vice versa), de sorte que les programmes qui ne recherchent que /etc/os-release (comme décrit ci-dessus) fonctionnent correctement.

Le reste de ce document qui parle d'os-release doit être compris comme s'appliquant également à initrd-release.

/usr/lib/extension-release.d/extension-release.IMAGE

/usr/lib/extension-release.d/extension-release.IMAGE joue le même rôle pour les images d'extension que os-release pour le système principal, et suit la syntaxe et les règles décrites sur la page Services Portables[3]. Le but de ce fichier est d'identifier l'extension et de permettre au système d'exploitation de vérifier que l'image d'extension correspond à l'OS de base. Ceci est généralement implémenté en vérifiant que l'option ID= de l'extension correspond soit à l'option ID= de l'hôte, soit est incluse dans l'option ID_LIKE= de l'hôte, et soit SYSEXT_LEVEL= existe et correspond également, soit s'il n'est pas présent, VERSION_ID= existe et correspond. Cela garantit la compatibilité ABI/API entre les couches et empêche la fusion d'une image incompatible dans une superposition.

Afin d'identifier l'image d'extension elle-même, les mêmes champs définis ci-dessous peuvent être ajoutés au fichier extension-release avec un préfixe SYSEXT_ (pour désambiguïser des champs utilisés pour la correspondance avec l'image de base). Par exemple : SYSEXT_ID=myext, SYSEXT_VERSION_ID=1.2.3.

Dans le nom de fichier extension-release.IMAGE, la partie IMAGE doit correspondre exactement au nom du fichier de l'image parente sans le suffixe. S'il n'est pas possible de garantir qu'un nom de fichier d'image est stable et ne change pas entre les phases de construction et de déploiement, il est possible de relâcher cette vérification : si exactement un fichier dont le nom correspond à "extension-release.*" est présent dans ce répertoire, et que le fichier est tagué avec un attribut user.extension-release.strict xattr(7) défini sur la chaîne "0", il sera utilisé à la place.

Le reste de ce document qui parle d'os-release doit être compris comme s'appliquant également à extension-release.

OPTIONS

Les paramètres d'identification de l'OS suivants peuvent être définis en utilisant os-release :

Informations générales identifiant le système d'exploitation

NAME=

Une chaîne identifiant le système d'exploitation, sans composant de version, et adaptée à une présentation à l'utilisateur. Si non défini, une valeur par défaut de "NAME=Linux" peut être utilisée.

Exemples : "NAME=Fedora", "NAME="Debian GNU/Linux"".

ID=

Une chaîne en minuscules (sans espaces ni autres caractères en dehors de 0–9, a–z, ".", "_" et "-") identifiant le système d'exploitation, excluant toute information de version et adaptée à un traitement par des scripts ou une utilisation dans des noms de fichiers générés. Si non défini, une valeur par défaut de "ID=linux" peut être utilisée. Notez que même si cette chaîne ne peut pas inclure de caractères nécessitant un échappement shell, l'échappement peut néanmoins être utilisé.

Exemples : "ID=fedora", "ID=debian".

ID_LIKE=

Une liste d'identifiants de systèmes d'exploitation séparés par des espaces, dans la même syntaxe que le paramètre ID=. Elle devrait lister les identifiants des systèmes d'exploitation étroitement liés au système d'exploitation local en termes de paquets et d'interfaces de programmation, par exemple en listant un ou plusieurs identifiants d'OS dont l'OS local est un dérivé. Un OS ne devrait généralement lister que d'autres identifiants d'OS dont il est lui-même un dérivé, et non les OS qui en sont dérivés, bien que des relations symétriques soient possibles. Les scripts de construction et similaires devraient vérifier cette variable s'ils ont besoin d'identifier le système d'exploitation local et que la valeur de ID= n'est pas reconnue. Les systèmes d'exploitation devraient être listés dans l'ordre de la proximité du système d'exploitation local avec les systèmes listés, en commençant par le plus proche. Ce champ est facultatif.

Exemples : pour un système d'exploitation avec "ID=centos", une affectation de "ID_LIKE="rhel fedora"" serait appropriée. Pour un système d'exploitation avec "ID=ubuntu", une affectation de "ID_LIKE=debian" est appropriée.

PRETTY_NAME=

Un nom de système d'exploitation joli, dans un format adapté à une présentation à l'utilisateur. Peut contenir ou non un nom de code de version ou une version de l'OS d'une certaine sorte, selon ce qui convient. Si non défini, une valeur par défaut de "PRETTY_NAME="Linux"" peut être utilisée.

Exemple : "PRETTY_NAME="Fedora 17 (Beefy Miracle)"".

CPE_NAME=

Un nom CPE pour le système d'exploitation, en syntaxe de liaison URI, suivant la Spécification d'énumération commune de plateforme[4] telle que proposée par le NIST. Ce champ est facultatif.

Exemple : "CPE_N

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

AME="cpe:/o:fedoraproject:fedora:17""

VARIANT=

Chaîne identifiant une variante ou une édition spécifique du système d'exploitation, appropriée pour être présentée à l'utilisateur. Ce champ peut être utilisé pour informer l'utilisateur que la configuration de ce système est soumise à un ensemble spécifique de règles divergentes ou à des paramètres de configuration par défaut. Ce champ est optionnel et peut ne pas être implémenté sur tous les systèmes.

Exemples : "VARIANT="Server Edition"", "VARIANT="Smart Refrigerator Edition"".

Note : ce champ est uniquement destiné à l'affichage. Le champ VARIANT_ID doit être utilisé pour prendre des décisions programmatiques.

Ajouté dans la version 220.

VARIANT_ID=

Chaîne en minuscules (sans espaces ou autres caractères en dehors de 0–9, a–z, ".", "_" et "-"), identifiant une variante ou une édition spécifique du système d'exploitation. Ceci peut être interprété par d'autres paquets afin de déterminer une configuration par défaut divergente. Ce champ est optionnel et peut ne pas être implémenté sur tous les systèmes.

Exemples : "VARIANT_ID=server", "VARIANT_ID=embedded".

Ajouté dans la version 220.

Informations sur la version du système d'exploitation

VERSION=

Chaîne identifiant la version du système d'exploitation, excluant toute information sur le nom du système d'exploitation, pouvant inclure un nom de code de publication, et appropriée pour être présentée à l'utilisateur. Ce champ est optionnel.

Exemples : "VERSION=17", "VERSION="17 (Beefy Miracle)"".

VERSION_ID=

Chaîne en minuscules (principalement numérique, sans espaces ou autres caractères en dehors de 0–9, a–z, ".", "_" et "-") identifiant la version du système d'exploitation, excluant toute information sur le nom du système d'exploitation ou le nom de code de publication, et appropriée pour le traitement par scripts ou l'utilisation dans des noms de fichiers générés. Ce champ est optionnel.

Exemples : "VERSION_ID=17", "VERSION_ID=11.04".

VERSION_CODENAME=

Chaîne en minuscules (sans espaces ou autres caractères en dehors de 0–9, a–z, ".", "_" et "-") identifiant le nom de code de publication du système d'exploitation, excluant toute information sur le nom du système d'exploitation ou la version de publication, et appropriée pour le traitement par scripts ou l'utilisation dans des noms de fichiers générés. Ce champ est optionnel et peut ne pas être implémenté sur tous les systèmes.

Exemples : "VERSION_CODENAME=buster", "VERSION_CODENAME=xenial".

Ajouté dans la version 231.

BUILD_ID=

Chaîne identifiant de manière unique l'image système utilisée à l'origine comme base d'installation. Dans la plupart des cas, VERSION_ID ou IMAGE_ID+IMAGE_VERSION sont mis à jour lorsque l'image système entière est remplacée lors d'une mise à jour. BUILD_ID peut être utilisé dans les distributions où la version de l'image d'installation d'origine est importante : VERSION_ID changerait lors des mises à jour incrémentielles du système, mais BUILD_ID ne changerait pas. Ce champ est optionnel.

Exemples : "BUILD_ID="2013-03-20.3"", "BUILD_ID=201303203".

Ajouté dans la version 200.

IMAGE_ID=

Chaîne en minuscules (sans espaces ou autres caractères en dehors de 0–9, a–z, ".", "_" et "-"), identifiant une image spécifique du système d'exploitation. Ceci est censé être utilisé pour les environnements où les images de systèmes d'exploitation sont préparées, construites, expédiées et mises à jour en tant qu'images complètes et cohérentes. Ce champ est optionnel et peut ne pas être implémenté sur tous les systèmes, en particulier pas sur ceux qui ne sont pas gérés via des images mais assemblés et mis à jour à partir de paquets individuels et sur le système local.

Exemples : "IMAGE_ID=vendorx-cashier-system", "IMAGE_ID=netbook-image".

Ajouté dans la version 249.

IMAGE_VERSION=

Chaîne en minuscules (principalement numérique, sans espaces ou autres caractères en dehors de 0–9, a–z, ".", "_" et "-") identifiant la version de l'image du système d'exploitation. Ceci est censé être utilisé conjointement avec IMAGE_ID décrit ci-dessus, pour distinguer différentes versions de la même image.

Exemples : "IMAGE_VERSION=33", "IMAGE_VERSION=47.1rc1".

Ajouté dans la version 249.

RELEASE_TYPE=

Chaîne en minuscules (sans espaces ou autres caractères en dehors de 0-9, a-z, ".", "_", et "-"), décrivant le type de publication de cette version du système d'exploitation. Les valeurs connues sont les suivantes :
•"stable" : pour les publications normales du système, appropriées pour une utilisation en production. Généralement, les publications stables deviennent obsolètes peu après la sortie de la prochaine publication stable majeure, bien que cela puisse ne pas être le cas si, par exemple, une distribution adopte un modèle de publication continue et reste prête pour la production. Les exemples incluent Fedora 40, Ubuntu 23.10, OpenSUSE Tumbleweed et Arch Linux.
•"lts" : pour les publications de support à long terme du système, appropriées pour une utilisation en production et prises en charge pendant une période prolongée. Généralement, les publications LTS continuent de recevoir un support même si de nouvelles publications majeures de la distribution sont disponibles. Les exemples incluent Ubuntu 24.04, Debian 12 Bookworm et RHEL 9.4.
•"development" : pour les versions instables du système, inappropriées pour une utilisation en production, telles que les versions alpha, bêta ou instables en continu. Les exemples incluent Fedora Rawhide, Debian Testing, Fedora 40 Beta et GNOME OS Nightly.
•"experiment" : pour les versions expérimentales du système, créées spécifiquement pour tester une fonctionnalité en cours de développement. Ceci est destiné à être utilisé en combinaison avec EXPERIMENT=.

Si non défini, ou avec une valeur inconnue, supposer que la publication est "stable".

Exemples : "RELEASE_TYPE=development", "RELEASE_TYPE=lts".

Ajouté dans la version 257.

Pour résumer : si les mises à jour d'image sont construites et expédiées en tant qu'unités complètes, IMAGE_ID+IMAGE_VERSION est le mieux adapté. Sinon, si les mises à jour remplacent entièrement le contenu précédemment installé, comme dans une distribution binaire typique, VERSION_ID doit être utilisé pour identifier les versions majeures du système d'exploitation. BUILD_ID peut être utilisé à la place ou en complément de VERSION_ID lorsque la version de l'image système d'origine est importante.

Informations de présentation et liens

HOME_URL=, DOCUMENTATION_URL=, SUPPORT_URL=, BUG_REPORT_URL=, PRIVACY_POLICY_URL=

Liens vers des ressources sur Internet relatives au système d'exploitation. HOME_URL= doit pointer vers la page d'accueil du système d'exploitation, ou alternativement vers une page d'accueil de la version spécifique du système d'exploitation. DOCUMENTATION_URL= doit pointer vers la page de documentation principale de ce système d'exploitation. SUPPORT_URL= doit pointer vers la page de support principale du système d'exploitation, s'il en existe une. Ceci est principalement destiné aux systèmes d'exploitation pour lesquels les fournisseurs fournissent un support. BUG_REPORT_URL= doit pointer vers la page principale de signalement de bogues du système d'exploitation, s'il en existe une. Ceci est principalement destiné aux systèmes d'exploitation qui dépendent de l'assurance qualité communautaire. PRIVACY_POLICY_URL= doit pointer vers la page principale de la politique de confidentialité du système d'exploitation, s'il en existe une. Ces paramètres sont optionnels, et la fourniture de seulement certains de ces paramètres est courante. Ces URL sont destinées à être affichées dans les interfaces utilisateur "À propos de ce système" sous des liens avec des légendes telles que "À propos de ce système d'exploitation", "Obtenir du support", "Signaler un bogue" ou "Politique de confidentialité". Les valeurs doivent être au format RFC3986[5], et doivent être des URL "http:" ou "https:", et éventuellement "mailto:" ou "tel:". Une seule URL doit être listée dans chaque paramètre. Si plusieurs ressources doivent être référencées, il est recommandé de fournir une page d'atterrissage en ligne liant toutes les ressources disponibles.

Exemples : "HOME_URL="https://fedoraproject.org/"", "BUG_REPORT_URL="https://bugzilla.redhat.com/"".

SUPPORT_END=

Date à laquelle le support de cette version du système d'exploitation se termine. (Ce que signifie exactement le "manque de support" varie selon les fournisseurs, mais en général, les utilisateurs doivent supposer que les mises à jour, y compris les correctifs de sécurité, ne seront pas fournies.) La valeur est une date au format ISO 8601 "AAAA-MM-JJ", et spécifie le premier jour où le support n'est pas fourni.

Par exemple, "SUPPORT_END=2001-01-01" signifie que le système était supporté jusqu'à la fin du dernier jour du millénaire précédent.

Ajouté dans la version 252.

LOGO=

Chaîne spécifiant le nom d'une icône telle que définie par la Spécification des thèmes d'icônes freedesktop.org[6]. Ceci peut être utilisé par les applications graphiques pour afficher le logo d'un système d'exploitation ou d'un distributeur. Ce champ est optionnel et peut ne pas nécessairement être implémenté sur tous les systèmes.

Exemples : "LOGO=fedora-logo", "LOGO=distributor-logo-opensuse"

Ajouté dans la version 240.

ANSI_COLOR=

Une couleur de présentation suggérée lors de l'affichage du nom du système d'exploitation sur la console. Ceci doit être spécifié sous forme de chaîne appropriée pour être incluse dans le code d'échappement ANSI/ECMA-48 ESC [ m pour définir le rendu graphique. Ce champ est optionnel.

Exemples : "ANSI_COLOR="0;31"" pour le rouge, "ANSI_COLOR="1;34"" pour le bleu clair, ou "ANSI_COLOR="0;38;2;60;110;180"" pour le bleu Fedora.

VENDOR_NAME=

Le nom du fournisseur du système d'exploitation. C'est le nom de l'organisation ou de l'entreprise qui produit le système d'exploitation. Ce champ est optionnel.

Ce nom est destiné à être affiché dans les interfaces utilisateur "À propos de ce système" ou dans les interfaces utilisateur de mise à jour logicielle lorsque cela est nécessaire pour distinguer le fournisseur du système d'exploitation du système d'exploitation lui-même. Il est destiné à être lisible par l'homme.

Exemples : "VENDOR_NAME="Fedora Project"" pour Fedora Linux, "VENDOR_NAME="Canonical"" pour Ubuntu.

Ajouté dans la version 254.

VENDOR_URL=

La page d'accueil du fournisseur du système d'exploitation. Ce champ est optionnel. Le champ VENDOR_NAME= doit être défini si celui-ci l'est, bien que les clients doivent être robustes contre l'absence de l'un ou l'autre champ.

La va

lue doit être au format RFC3986[5], et doit être une URL « http: » ou « https: ». Une seule URL peut être listée dans le paramètre.

Exemples : « VENDOR_URL= »https://fedoraproject.org/« » , « VENDOR_URL= »https://canonical.com/« ».

Ajouté dans la version 254.

EXPERIMENT=

Une description lisible par l'homme de ce qui rend cette version de l'OS expérimentale. Ce champ est optionnel. Le champ RELEASE_TYPE doit être défini sur « experiment » si ce champ est défini, sinon les clients doivent ignorer ce champ.

Cette description est destinée à être affichée au moment de l'installation du système, ou dans les interfaces utilisateur « À propos de ce système », pour avertir l'utilisateur qu'il installe/exécute une version expérimentale de l'OS. Si RELEASE_TYPE est « experiment » mais que ce champ n'est pas défini, l'interface utilisateur devrait toujours avertir l'utilisateur, mais elle ne sera pas en mesure d'expliquer ce qui est exactement expérimental dans la version actuelle de l'OS.

Exemples : « EXPERIMENT= »Switch to DNF5« » pour une version expérimentale de Fedora Linux réalisée pour tester DNF5, « EXPERIMENT= »Port to Apple M3 chip« » pour des versions expérimentales d'Asahi Linux portées sur le SoC Apple M3, « EXPERIMENT= »Mutter !1441: Dynamic triple/double buffering (v4)« » pour des versions de GNOME OS créées par le CI de Mutter pour la demande de fusion !1441.

Ajouté dans la version 257.

EXPERIMENT_URL=

La page d'information principale sur ce qui rend la version actuelle de l'OS expérimentale, où les utilisateurs peuvent en apprendre davantage sur l'état de l'expérience et potentiellement laisser des commentaires. Ce champ est optionnel. Le champ EXPERIMENT= doit être défini si celui-ci l'est, bien que les clients doivent être robustes face à l'absence de l'un ou l'autre des champs.

La valeur doit être au format RFC3986[5], et doit être une URL « http: » ou « https: ». Une seule URL doit être listée dans le paramètre.

Exemples, correspondant aux exemples ci-dessus dans EXPERIMENT= : « EXPERIMENT_URL= »https://fedoraproject.org/wiki/Changes/SwitchToDnf5« » , « EXPERIMENT_URL= »https://github.com/AsahiLinux/docs/wiki/M3-Series-Feature-Support« » , « EXPERIMENT_URL= »https://gitlab.gnome.org/GNOME/mutter/-/merge_requests/1441« ».

Ajouté dans la version 257.

Valeurs par défaut et métadonnées au niveau de la distribution

DEFAULT_HOSTNAME=

Une chaîne spécifiant le nom d'hôte si hostname(5) n'est pas présent et aucune autre source de configuration ne spécifie le nom d'hôte. Doit être soit une seule étiquette DNS (une chaîne composée de caractères minuscules ASCII 7 bits et sans espaces ni points, limitée au format autorisé pour les étiquettes de noms de domaine DNS), soit une séquence d'étiquettes de ce type séparées par des points uniques formant un FQDN DNS valide. Le nom d'hôte ne doit pas dépasser 64 caractères, ce qui est une limitation de Linux (DNS autorise des noms plus longs).

Si le caractère point d'interrogation « ? » apparaît dans le nom d'hôte, il est automatiquement substitué par un caractère hexadécimal dérivé de l'machine-id(5) lors de son application, de manière sécurisée et déterministe par hachage cryptographique. Exemple : « foobar-????-???? » sera automatiquement étendu à « foobar-92a9-061c » ou similaire, en fonction de l'ID de machine locale.

Voir org.freedesktop.hostname1(5) pour une description de la manière dont systemd-hostnamed.service(8) détermine le nom d'hôte de secours.

Ajouté dans la version 248.

ARCHITECTURE=

Une chaîne qui spécifie pour quelle architecture CPU les binaires de l'espace utilisateur sont requis. Les identifiants d'architecture sont les mêmes que pour ConditionArchitecture= décrits dans systemd.unit(5). Le champ est optionnel et ne doit être utilisé que lorsqu'une seule architecture est supportée. Il peut fournir des informations redondantes lorsqu'il est utilisé dans une partition GPT avec un type GUID qui encode déjà l'architecture. Si ce n'est pas le cas, l'architecture doit être spécifiée, par exemple, dans une image d'extension, pour empêcher un hôte incompatible de la charger.

Ajouté dans la version 252.

SYSEXT_LEVEL=

Une chaîne en minuscules (principalement numérique, sans espaces ni autres caractères en dehors de 0-9, a-z, « . », « _ » et « - ») identifiant le niveau de prise en charge des extensions du système d'exploitation, pour indiquer quelles images d'extension sont prises en charge. Voir /usr/lib/extension-release.d/extension-release.IMAGE, initrd[2] et systemd-sysext(8) pour plus d'informations.

Exemples : « SYSEXT_LEVEL=2 » , « SYSEXT_LEVEL=15.14 ».

Ajouté dans la version 248.

CONFEXT_LEVEL=

Sémantiquement identique à SYSEXT_LEVEL= mais pour les images confext. Voir /etc/extension-release.d/extension-release.IMAGE pour plus d'informations.

Exemples : « CONFEXT_LEVEL=2 » , « CONFEXT_LEVEL=15.14 ».

Ajouté dans la version 254.

SYSEXT_SCOPE=

Accepte une liste d'une ou plusieurs des chaînes « system », « initrd » et « portable », séparées par des espaces. Ce champ n'est supporté que dans les fichiers extension-release.d/ et indique à quels environnements l'extension système s'applique : c'est-à-dire aux systèmes réguliers, aux initrds et exitrds, ou aux images de services portables. S'il n'est pas spécifié, « SYSEXT_SCOPE=system portable » est implicite, c'est-à-dire que toute extension système sans ce champ est applicable aux systèmes réguliers et aux environnements de services portables, mais pas aux environnements initrd/exitrd.

Ajouté dans la version 250.

CONFEXT_SCOPE=

Sémantiquement identique à SYSEXT_SCOPE= mais pour les images confext.

Ajouté dans la version 254.

PORTABLE_PREFIXES=

Accepte une liste d'une ou plusieurs chaînes valides de correspondance de préfixes pour la logique des Services Portables[3], séparées par des espaces. Ce champ a deux objectifs : il est informatif, identifiant les images de services portables comme telles (et permettant ainsi de les distinguer des autres images OS, telles que les images système bootables). Il est également utilisé lorsqu'une image de service portable est attachée : le préfixe de service portable spécifié ou implicite est vérifié par rapport à la liste spécifiée ici, afin de faire respecter les restrictions sur la manière dont les images peuvent être attachées à un système.

Ajouté dans la version 250.

Notes

Si vous utilisez ce fichier pour déterminer l'OS ou une version spécifique de celui-ci, utilisez les champs ID et VERSION_ID, éventuellement avec ID_LIKE comme solution de repli pour ID. Lorsque vous recherchez une chaîne d'identification de l'OS à présenter à l'utilisateur, utilisez le champ PRETTY_NAME.

Notez que les fournisseurs de systèmes d'exploitation peuvent choisir de ne pas fournir d'informations de version, par exemple pour s'adapter aux versions continues (rolling releases). Dans ce cas, VERSION et VERSION_ID peuvent ne pas être définis. Les applications ne doivent pas compter sur la définition de ces champs.

Les fournisseurs de systèmes d'exploitation peuvent étendre le format du fichier et introduire de nouveaux champs. Il est fortement recommandé de préfacer les nouveaux champs avec un nom spécifique à l'OS afin d'éviter les conflits de noms. Les applications lisant ce fichier doivent ignorer les champs inconnus.

Exemple : « DEBIAN_BTS= »debbugs://bugs.debian.org/« ».

Les gestionnaires d'exécution de conteneurs et de sandbox peuvent rendre les données d'identification de l'hôte disponibles aux applications en fournissant le fichier /etc/os-release de l'hôte (s'il est disponible, sinon /usr/lib/os-release en secours) sous /run/host/os-release.

#!/bin/sh -eu

. "${os_release}"
echo "Running on ${PRETTY_NAME:-Linux}"
if [ "${ID:-linux}" = "debian" ] || [ "${ID_LIKE#*debian*}" != "${ID_LIKE}" ]; then
    echo "Looks like Debian!"

Exemple 4. Lecture de os-release en python(1) (versions >= 3.10)

#!/usr/bin/python
# SPDX-License-Identifier: MIT-0
import platform
os_release = platform.freedesktop_os_release()
pretty_name = os_release.get('PRETTY_NAME', 'Linux')
print(f'Running on {pretty_name!r}')
if 'fedora' in [os_release.get('ID', 'linux'),
                *os_release.get('ID_LIKE', '').split()]:
    print('Looks like Fedora!')
