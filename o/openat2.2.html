openat2(2) Manuel des appels système openat2(2)

NOM

openat2 - ouvrir et potentiellement créer un fichier (étendu)

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <fcntl.h>          /* Définition des constantes O_* et S_* */
#include <linux/openat2.h>  /* Définition des constantes RESOLVE_* */
#include <sys/syscall.h>    /* Définition des constantes SYS_* */
#include <unistd.h>
long syscall(SYS_openat2, int dirfd, const char *path,
             struct open_how *how, size_t size);

Note : glibc ne fournit pas d'enveloppe pour openat2(), ce qui nécessite l'utilisation de syscall(2).

DESCRIPTION

L'appel système openat2() est une extension de openat(2) et fournit un sur-ensemble de ses fonctionnalités.

L'appel système openat2() ouvre le fichier spécifié par path. Si le fichier spécifié n'existe pas, il peut éventuellement (si O_CREAT est spécifié dans how.flags) être créé.

Comme avec openat(2), si path est relatif, alors il est interprété par rapport au répertoire référencé par le descripteur de fichier dirfd (ou le répertoire de travail courant du processus appelant, si dirfd est la valeur spéciale AT_FDCWD). Si path est absolu, alors dirfd est ignoré (sauf si how.resolve contient RESOLVE_IN_ROOT, auquel cas path est résolu par rapport à dirfd).

Plutôt que de prendre un seul argument flags, une structure extensible (how) est passée pour permettre des extensions futures. L'argument size doit être spécifié comme sizeof(struct open_how).

La structure open_how

L'argument how spécifie comment path doit être ouvert, et agit comme un sur-ensemble des arguments flags et mode de openat(2). Cet argument est un pointeur vers une structure open_how, décrite dans open_how(2type).

Toutes les futures extensions de openat2() seront implémentées comme de nouveaux champs ajoutés à la structure open_how, avec une valeur zéro dans un nouveau champ entraînant le comportement du noyau comme si ce champ d'extension n'était pas présent. Par conséquent, l'appelant doit initialiser cette structure à zéro. (Voir la section "Extensibilité" des NOTES pour plus de détails sur la raison pour laquelle cela est nécessaire.)

Les champs de la structure how sont les suivants :

flags
Ce champ spécifie les drapeaux de création de fichier et d'état de fichier à utiliser lors de l'ouverture du fichier. Tous les drapeaux O_* définis pour openat(2) sont des valeurs de drapeau valides pour openat2().
Alors que openat(2) ignore les bits inconnus dans son argument flags, openat2() renvoie une erreur si des drapeaux inconnus ou conflictuels sont spécifiés dans how.flags.
mode
Ce champ spécifie le mode pour le nouveau fichier, avec des sémantiques identiques à l'argument mode de openat(2).
Alors que openat(2) ignore les bits autres que ceux de la plage 07777 dans son argument mode, openat2() renvoie une erreur si how.mode contient des bits autres que 07777. De même, une erreur est renvoyée si openat2() est appelé avec un how.mode non nul et que how.flags ne contient pas O_CREAT ou O_TMPFILE.
resolve
Ceci est un masque de bits de drapeaux qui modifient la manière dont tous les composants de path seront résolus. (Voir path_resolution(7) pour des informations de fond.)
Le cas d'utilisation principal de ces drapeaux est de permettre aux programmes de confiance de restreindre la manière dont les chemins non fiables (ou les chemins à l'intérieur de répertoires non fiables) sont résolus. La liste complète des drapeaux resolve est la suivante :
RESOLVE_BENEATH
Ne pas permettre à la résolution de chemin de réussir si un composant de la résolution n'est pas un descendant du répertoire indiqué par dirfd. Cela rejette les liens symboliques absolus (et les valeurs absolues de path).
Actuellement, ce drapeau désactive également la résolution des liens magiques (voir ci-dessous). Cependant, cela pourrait changer à l'avenir. Par conséquent, pour s'assurer que les liens magiques ne sont pas résolus, l'appelant doit spécifier explicitement RESOLVE_NO_MAGICLINKS.
RESOLVE_IN_ROOT
Traiter le répertoire référencé par dirfd comme le répertoire racine lors de la résolution de path. Les liens symboliques absolus sont interprétés par rapport à dirfd. Si un composant préfixe de path est équivalent à dirfd, alors un composant .. immédiatement suivant est également équivalent à dirfd (tout comme /.. est traditionnellement équivalent à /). Si path est absolu, il est également interprété par rapport à dirfd.
L'effet de ce drapeau est comme si le processus appelant avait utilisé chroot(2) pour modifier (temporairement) son répertoire racine (vers le répertoire référencé par dirfd). Cependant, contrairement à chroot(2) (qui modifie la racine du système de fichiers de manière permanente pour un processus), RESOLVE_IN_ROOT permet à un programme de restreindre efficacement la résolution de chemin par ouverture.
Actuellement, ce drapeau désactive également la résolution des liens magiques. Cependant, cela pourrait changer à l'avenir. Par conséquent, pour s'assurer que les liens magiques ne sont pas résolus, l'appelant doit explicitement spécifier RESOLVE_NO_MAGICLINKS.
RESOLVE_NO_MAGICLINKS
Interdire toute résolution de lien magique pendant la résolution de chemin.
Les liens magiques sont des objets de type lien symbolique que l'on trouve le plus notablement dans proc(5) ; les exemples incluent /proc/pid/exe et /proc/pid/fd/*. (Voir symlink(7) pour plus de détails.)
L'ouverture à l'insu de liens magiques peut être risquée pour certaines applications. Voici des exemples de tels risques :
•
Si le processus ouvrant un nom de chemin est un processus de contrôle qui n'a actuellement pas de terminal de contrôle (voir credentials(7)), alors l'ouverture d'un lien magique dans /proc/pid/fd qui se réfère à un terminal provoquerait l'acquisition d'un terminal de contrôle par le processus.
•
Dans un environnement conteneurisé, un lien magique dans /proc peut se référer à un objet à l'extérieur du conteneur, et peut donc fournir un moyen de s'échapper du conteneur.
En raison de tels risques, une application peut préférer désactiver la résolution des liens magiques en utilisant le drapeau RESOLVE_NO_MAGICLINKS.
Si le composant final (c'est-à-dire le nom de base) de path est un lien magique, how.resolve contient RESOLVE_NO_MAGICLINKS, et how.flags contient à la fois O_PATH et O_NOFOLLOW, alors un descripteur de fichier O_PATH référençant le lien magique sera retourné.
RESOLVE_NO_SYMLINKS
Interdire la résolution des liens symboliques pendant la résolution de chemin. Cette option implique RESOLVE_NO_MAGICLINKS.
Si le composant final (c'est-à-dire le nom de base) de path est un lien symbolique, how.resolve contient RESOLVE_NO_SYMLINKS, et how.flags contient à la fois O_PATH et O_NOFOLLOW, alors un descripteur de fichier O_PATH référençant le lien symbolique sera retourné.

openat2(2) — openat2()

NAME

openat2 — open a file or directory using advanced features

LIBRARY

Standard C library (libc, -lc)

SYNOPSIS

#include <fcntl.h>

int openat2(int dirfd, const char *path, struct open_how *how);

DESCRIPTION

The openat2() system call provides a unified interface for opening files and directories using a wide range of flags and options, including control over path resolution behavior.

It extends the functionality of openat(2) by introducing the struct open_how structure, which allows for more complex open operations.

The arguments are:

dirfd
A file descriptor referring to a directory. If dirfd is AT_FDCWD, the path is interpreted relative to the current working directory.
path
The path to the file or directory to be opened.
how
A pointer to a struct open_how structure that specifies the desired behavior for the open operation. The structure is defined as follows:
struct open_how {
    __u64 flags;      /* Flags for the open operation (e.g., O_RDONLY, O_CREAT) */
    __u64 resolve;    /* Flags for path resolution behavior */
    __u64 unused[3];  /* Reserved for future extensions */
};

The flags member contains standard open flags such as O_RDONLY, O_WRONLY, O_RDWR, O_CREAT, O_TRUNC, O_APPEND, O_EXCL, O_CLOEXEC, O_NOCTTY, O_NONBLOCK, O_SYNC, O_DSYNC, O_RSYNC, O_DIRECTORY, O_NOFOLLOW, O_nofollow_symlink, O_DIRECT, O_LARGEFILE, O_PATH, O_TMPFILE, and O_NOATIME. Note that some flags may be ignored depending on the context and the other flags specified.

The resolve member specifies how path resolution should be performed. The following values can be specified:

RESOLVE_IN_ROOT
Perform path resolution within the specified root directory (see openat(2)). This means that path components cannot escape the root directory via symbolic links or other means.
RESOLVE_BENEATH
Ensure that the resolved path is strictly beneath the directory specified by dirfd. This flag is useful for preventing access to files outside of a designated directory, even if symbolic links are involved.
RESOLVE_NO_MAGICLINKS
Do not follow magic links. Magic links are symbolic links that, when followed, change the root directory for subsequent path resolution. This flag prevents such behavior.
RESOLVE_NO_SYMLINKS
Do not follow any symbolic links during path resolution. This flag affects all components of the path, unlike the O_NOFOLLOW file creation flag which only affects the final component.
Applications that employ the RESOLVE_NO_SYMLINKS flag are encouraged to make its use configurable (unless it is used for a specific security purpose), as symbolic links are very widely used by end-users. Setting this flag indiscriminately—i.e., for purposes not specifically related to security—for all uses of openat2() may result in spurious errors on previously functional systems. This may occur if, for example, a system pathname that is used by an application is modified (e.g., in a new distribution release) so that a pathname component (now) contains a symbolic link.
RESOLVE_NO_XDEV
Disallow traversal of mount points during path resolution (including all bind mounts). Consequently, path must either be on the same mount as the directory referred to by dirfd, or on the same mount as the current working directory if dirfd is specified as AT_FDCWD.
Applications that employ the RESOLVE_NO_XDEV flag are encouraged to make its use configurable (unless it is used for a specific security purpose), as bind mounts are widely used by end-users. Setting this flag indiscriminately—i.e., for purposes not specifically related to security—for all uses of openat2() may result in spurious errors on previously functional systems. This may occur if, for example, a system pathname that is used by an application is modified (e.g., in a new distribution release) so that a pathname component (now) contains a bind mount.
RESOLVE_CACHED (since Linux 5.12)
Make the open operation fail unless all path components are already present in the kernel's lookup cache. If any kind of revalidation or I/O is needed to satisfy the lookup, openat2() fails with the error EAGAIN. This is useful in providing a fast-path open that can be performed without resorting to thread offload, or other mechanisms that an application might use to offload slower operations.
If any bits other than those listed above are set in how.resolve, an error is returned.

RETURN VALUE

On success, a new file descriptor is returned. On error, -1 is returned, and errno is set to indicate the error.

ERRORS

The set of errors returned by openat2() includes all of the errors returned by openat(2), as well as the following additional errors:

E2BIG
An extension that this kernel does not support was specified in how. (See the "Extensibility" section of NOTES for more detail on how extensions are handled.)
EAGAIN
how.resolve contains either RESOLVE_IN_ROOT or RESOLVE_BENEATH, and the kernel could not ensure that a ".." component didn't escape (due to a race condition or potential attack). The caller may choose to retry the openat2() call.
EAGAIN
RESOLVE_CACHED was set, and the open operation cannot be performed using only cached information. The caller should retry without RESOLVE_CACHED set in how.resolve.
EINVAL
An unknown flag or invalid value was specified in how.
EINVAL
mode is nonzero, but how.flags does not contain O_CREAT or O_TMPFILE.
EINVAL
size was smaller than any known version of struct open_how.
ELOOP
how.resolve contains RESOLVE_NO_SYMLINKS, and one of the path components was a symbolic link (or magic link).
ELOOP
how.resolve contains RESOLVE_NO_MAGICLINKS, and one of the path components was a magic link.
EXDEV
how.resolve contains either RESOLVE_IN_ROOT or RESOLVE_BENEATH, and an escape from the root during path resolution was detected.
EXDEV
how.resolve contains RESOLVE_NO_XDEV, and a path component crosses a mount point.

STANDARDS

Linux.

HISTORY

Linux 5.6.

The semantics of RESOLVE_BENEATH were modeled after FreeBSD's O_BENEATH, but avoided a well-known correctness bug in FreeBSD's implementation that rendered it effectively insecure. Later, FreeBSD 13 introduced O_RESOLVE_BENEATH to replace the insecure O_BENEATH. FreeBSD's O_RESOLVE_BENEATH semantics are based on Linux's RESOLVE_BENEATH and the two are now functionally equivalent.

NOTES

Extensibility

In order to allow for future extensibility, openat2() requires the user-space application to specify the size of the struct open_how that it is passing. By providing this information, it is possible for openat2() to provide both forwards- and backwards-compatibility, with size acting as an implicit version number. (Because new extension fields will always be appended, the structure size will always increase.) This extensibility design is very similar to other system calls such as sched_setattr(2), perf_event_open(2), and clone3(2).

If we let usize be the size of the structure as specified by the user-space application, and ksize be the size of the structure which the kernel supports, then there are three cases to consider:

•
If ksize equals usize, then there is no version mismatch and how can be used verbatim.
•
If ksize is larger than usize, then there are some extension fields that the kernel supports which the user-space application is unaware of. Because a zero value in any added extension field signifies a no-op, the kernel treats all of the extension fields not provided by the user-space application as having zero values. This provides backwards-compatibility.
•
If ksize is smaller than usize, then there are some extension fields which the user-space application is aware of but which the kernel does not support. Because any extension field must have its zero values signify a no-op, the kernel can safely ignore the unsupported extension fields if they are all-zero. If any unsupported extension fields are nonzero, then -1 is returned and errno is set to E2BIG. This provides forwards-compatibility.

Because the definition of struct open_how may change in the future (with new fields being added when system headers are updated), user-space applications should zero-fill struct open_how to ensure that recompiling the program with new headers will not result in spurious errors at run time. The simplest way is to use a designated initializer:


struct open_how how = { .flags = O_RDWR,
                        .resolve = RESOLVE_IN_ROOT };

or explicitly using memset(3) or similar:


struct open_how how;
memset(&how, 0, sizeof(how));
how.flags = O_RDWR;
how.resolve = RESOLVE_IN_ROOT;

A user-space application that wishes to determine which extensions the running kernel supports can do so by conducting a binary search on size with a structure which has every byte nonzero (to find the largest value which doesn't produce an error of E2BIG).

SEE ALSO

openat2(2)

Open a file relative to a directory file descriptor - Linux manual pages

NAME

openat2 - Open a file relative to a directory file descriptor

SYNOPSIS

#include <fcntl.h>

int openat2(int dirfd, const char *pathname, const struct open_how *how);

DESCRIPTION

The openat2() syscall is a more flexible interface than openat(2). It allows the caller to specify the desired file creation and access flags in a structured way.

The dirfd argument is a file descriptor referring to a directory.

The pathname argument specifies the file to be opened relative to the directory referred to by dirfd.

The how argument is a pointer to a struct open_how, which specifies the desired flags for opening and creating the file. The struct open_how is defined as follows: 

struct open_how {
    uint64_t flags;         /* Flags for opening the file */
    uint64_t mode;          /* Mode for file creation (if O_CREAT is set) */
    uint64_t align;         /* Alignment requirement for the file */
};

The flags field contains the access and creation flags, similar to the second argument of open(2). These include:

  • O_RDONLY: Open for reading only.
  • O_WRONLY: Open for writing only.
  • O_RDWR: Open for reading and writing.
  • O_CREAT: Create the file if it does not exist.
  • O_EXCL: If O_CREAT is specified, and the file already exists, then openat2() fails.
  • O_NOCTTY: If pathname refers to a terminal device, this flag prevents the special device from becoming the controlling terminal for the process.
  • O_TRUNC: If the file exists and is opened for writing (by O_RDWR or O_WRONLY), truncate its length to 0.
  • O_APPEND: Open the file in append mode. Every write will be executed at the end of the file, regardless of the lseek(2) call. The O_SYNC and O_DSYNC options are deprecated and should not be used.
  • O_NONBLOCK: Enable non-blocking mode.
  • O_SYNC: Synchronous I/O for data, and all attributes meaning that writing the data to the underlying storage device.
  • O_DSYNC: Synchronous I/O for data only.
  • O_DIRECT: Minimize the cache effect of the operating system on read and write operations.
  • O_LARGEFILE: This is a traditional extension, now usually the default on 32-bit systems: allow files to exceed 2 GiB.

The mode field specifies the file permissions to be used if O_CREAT is specified in flags. It is a bitmask like that used by open(2).

The align field specifies an alignment requirement for the file. This can be used to hint to the kernel about how the file should be laid out on disk for optimal performance.

If pathname is relative, then it is interpreted relative to the directory referred to by dirfd. If pathname is absolute, the dirfd is ignored. If dirfd is AT_FDCWD, then pathname must refer to a path relative to the current working directory.

RETURN VALUE

On success, openat2() returns the new file descriptor. On failure, it returns -1 and sets errno to indicate the error.

ERRORS

  • EBADF: dirfd is not a valid file descriptor.
  • ENOTDIR: dirfd refers to a file that is not a directory.
  • ENOENT: The directory referred to by dirfd does not exist, or a path component of pathname does not exist.
  • EACCES: dirfd or a path component of pathname is not searchable. Or the requested access mode is not allowed.
  • EMFILE: The process has reached its limit for the number of open file descriptors.
  • ENFILE: The system has reached its limit for the number of open files.
  • ELOOP: Too many symbolic links encountered while resolving pathname.
  • ENAMETOOLONG: pathname is too long.
  • EINVAL: how is NULL, or how->flags contains invalid flags, or how->mode is invalid.

STANDARDS

openat2() is a Linux-specific syscall.

HISTORY

The openat2() syscall was introduced in Linux kernel version 5.6.

NOTES

The openat2() syscall is intended to replace the older openat(2) syscall, providing a more flexible and extensible interface for opening files.

The align field is a hint and may not be honored by all filesystems.

SEE ALSO

open(2), openat(2), creat(3)
