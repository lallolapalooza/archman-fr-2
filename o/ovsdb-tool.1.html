NOM

ovsdb-tool - Utilitaire de gestion de base de données Open vSwitch

SYNOPSIS

Commandes de création de base de données :
ovsdb-tool [options] create [db [schema]]
ovsdb-tool [options] [--election-timer=ms] create-cluster db contents address
ovsdb-tool [options] [--cid=uuid] join-cluster db name local remote...
Commandes de gestion de version :
ovsdb-tool [options] convert [db [schema [target]]]
ovsdb-tool [options] needs-conversion [db [schema]]
ovsdb-tool [options] db-version [db]
ovsdb-tool [options] schema-version [schema]
ovsdb-tool [options] db-cksum [db]
ovsdb-tool [options] schema-cksum [schema]
ovsdb-tool [options] compare-versions a op b
Autres commandes :
ovsdb-tool [options] compact [db [target]]
ovsdb-tool [options] [--rbac-role=role] query [db] transaction
ovsdb-tool [options] [--rbac-role=role] transact [db] transaction
ovsdb-tool [options] [-m | --more]... show-log [db]
ovsdb-tool [options] check-cluster db...
ovsdb-tool [options] db-name [db]
ovsdb-tool [options] schema-name [schema]
ovsdb-tool [options] db-cid db

[-v[module[:destination[:level]]]]...
[--verbose[=module[:destination[:level]]]]...
[--log-file[=file]]
Options communes :
[-h | --help] [-V | --version]

DESCRIPTION

Le programme ovsdb-tool est un outil en ligne de commande pour la gestion des fichiers de base de données Open vSwitch (OVSDB). Il n'interagit pas directement avec les serveurs de base de données Open vSwitch en cours d'exécution (utilisez plutôt ovsdb-client). Pour une introduction à OVSDB et son implémentation dans Open vSwitch, consultez ovsdb(7).

Chaque commande qui prend un argument facultatif db ou schema a un emplacement de fichier par défaut s'il n'est pas spécifié. Le db par défaut est /etc/openvswitch/conf.db. Le schema par défaut est /usr/share/openvswitch/vswitch.ovsschema.

Cette implémentation OVSDB prend en charge les modèles de service de base de données autonomes et active-sauvegarde avec un format sur disque et un modèle de service de base de données clusterisé avec un format différent. ovsdb-tool prend en charge les deux formats, mais certaines commandes ne conviennent qu'à un seul format, comme documenté pour les commandes individuelles ci-dessous. Pour une spécification de ces formats, consultez ovsdb(5). Pour plus d'informations sur les modèles de service OVSDB, consultez la section Modèles de service de ovsdb(7).

Commandes de création de base de données

Ces commandes créent un nouveau fichier de base de données OVSDB. Elles ne remplaceront pas un fichier de base de données existant. Pour remplacer une base de données existante par une nouvelle, supprimez d'abord l'ancienne.

create [db [schema]]
Utilisez cette commande pour créer la base de données pour contrôler ovs-vswitchd ou une autre base de données autonome ou active-sauvegarde. Elle crée le fichier de base de données db avec le schema donné, qui doit être le nom d'un fichier contenant un schéma OVSDB au format JSON, tel que spécifié dans la spécification OVSDB. La nouvelle base de données est initialement vide. (Vous pouvez utiliser cp pour copier une base de données, y compris son schéma et ses données.)
[--election-timer=ms] create-cluster db contents local
Utilisez cette commande pour initialiser le premier serveur dans un cluster de haute disponibilité de 3 serveurs de base de données (ou plus), par exemple pour une base de données dans un environnement qui ne peut pas tolérer un point de défaillance unique. Elle crée le fichier de base de données clusterisé db et configure le serveur pour écouter sur local, qui doit avoir la forme protocol:ip:port, où protocol est tcp ou ssl, ip est l'IP du serveur (une adresse IPv4 ou une adresse IPv6 entre crochets), et port est un numéro de port TCP. Une seule adresse est spécifiée, pour le premier serveur du cluster, généralement celui du serveur exécutant create-cluster. L'adresse est utilisée pour la communication au sein du cluster, pas pour la communication avec les clients OVSDB, et ne doit pas utiliser le même port que le protocole OVSDB.
La nouvelle base de données est initialisée avec contents, qui doit nommer un fichier contenant soit un schéma OVSDB au format JSON, soit une base de données OVSDB autonome. S'il s'agit d'un fichier de schéma, la nouvelle base de données sera initialement vide, avec le schéma donné. S'il s'agit d'un fichier de base de données, la nouvelle base de données aura le même schéma et le même contenu.
L'élection du leader sera initiée par un follower s'il n'y a pas de battement de cœur reçu du leader du cluster dans le délai d'élection spécifié. Le délai d'élection du leader par défaut est de 1000 millisecondes. Pour utiliser une valeur différente lors de la création de la base de données, spécifiez --election-timer=ms, où ms est une valeur en millisecondes comprise entre 100 et 600000 inclus.
[--cid=uuid] join-cluster db name local remote...
Utilisez cette commande pour initialiser chaque serveur après le premier dans un cluster OVSDB à haute disponibilité. Elle crée le fichier de base de données clusterisé db pour une base de données nommée name, et configure le serveur pour écouter sur local et pour se connecter initialement à remote, qui doit être un serveur qui appartient déjà au cluster. local et remote utilisent la même syntaxe protocol:ip:port que create-cluster.
Le name doit être le nom du schéma ou de la base de données passé à create-cluster. Par exemple, le nom du schéma de base de données OVN Southbound est OVN_Southbound. Utilisez la commande schema-name ou db-name de ovsdb-tool pour connaître le nom d'un schéma ou d'une base de données, respectivement.
Cette commande n'effectue aucune opération réseau, ce qui signifie qu'elle ne peut pas réellement joindre le nouveau serveur au cluster. Au lieu de cela, le fichier db qu'elle crée prépare le serveur à rejoindre le cluster lorsque ovsdb-server le sert pour la première fois. Dans le cadre de la jonction au cluster, le nouveau serveur récupère le schéma de la base de données et obtient la liste de tous les membres du cluster. Ce n'est qu'après cela qu'il devient un membre à part entière du cluster.
Facultativement, plus d'un remote peut être spécifié ; par exemple, dans un cluster qui contient déjà plusieurs serveurs, on pourrait spécifier tous les serveurs existants. Ceci est bénéfique si certains des serveurs existants sont en panne pendant que le nouveau serveur rejoint, mais ce n'est pas autrement nécessaire.
Par défaut, le db créé par join-cluster rejoindra toute base de données clusterisée nommée name disponible à un remote. En théorie, si des machines s'allument et s'éteignent et que les adresses IP changent de la bonne manière, il pourrait rejoindre le mauvais cluster de base de données. Pour éviter cette possibilité, spécifiez --cid=uuid, où uuid est l'ID du cluster à rejoindre, tel qu'affiché par ovsdb-tool get-cid.

Commandes de migration de base de données

Ces commandes convertiront une base de données clusterisée en une base de données autonome.

cluster-to-standalone db clusterdb
Convertit la base de données clusterisée clusterdb en une base de données autonome db. La base de données autonome résultante ne contiendra pas les informations de versionnement ou d'appartenance au cluster.

Commandes de gestion de version

convert [db [schema [target]]]
Convertit db pour utiliser le schéma spécifié par schema. Le fichier schema doit être un schéma OVSDB valide. Si target est donné, la nouvelle base de données est écrite dans ce fichier ; sinon, elle remplace db. Ceci est utilisé pour mettre à jour le schéma d'une base de données, par exemple lors de la mise à niveau d'Open vSwitch.
needs-conversion [db [schema]]
Retourne 0 si db utilise déjà le schéma spécifié par schema. Retourne 1 s'il doit être converti. Retourne 2 si db n'est pas un fichier OVSDB valide. Les erreurs sont signalées sur stderr.
db-version [db]
Imprime la version de la base de données contenue dans db. La version est une chaîne, par exemple "1.0".
schema-version schema
Imprime la version du schéma contenu dans schema. La version est une chaîne, par exemple "1.0".
db-cksum [db]
Imprime la somme de contrôle (checksum) du contenu de la base de données contenue dans db. La somme de contrôle est une chaîne hexadécimale qui représente le contenu de la base de données.
schema-cksum schema
Imprime la somme de contrôle (checksum) du contenu du schéma contenu dans schema. La somme de contrôle est une chaîne hexadécimale qui représente le contenu du schéma.
compare-versions a op b
Compare les versions de chaînes a et b en utilisant l'opérateur op. Les opérateurs valides sont, comme on peut s'y attendre, ==, !=, <, <=, >, >=. Retourne 0 si la comparaison est vraie, 1 sinon. Les versions sont comparées en tant que chaînes, donc "1.10" est considéré comme "plus grand" que "1.2".

Autres commandes

compact [db [target]]
Réécrit db dans un format compacté. Si target est donné, la base de données compactée est écrite dans ce fichier ; sinon, elle remplace db. La compression réduit la taille du fichier de base de données, mais elle peut avoir un impact sur les performances d'accès.
query [db] transaction
transact [db] transaction
Exécute transaction sur la base de données db. transaction doit être un JSON valide représentant une ou plusieurs opérations OVSDB. Pour plus d'informations sur le format des transactions, consultez la page de manuel ovsdb(7). Les commandes query et transact diffèrent seulement dans leur comportement en cas d'échec de la transaction : query renvoie une erreur, tandis que transact annule toutes les modifications apportées par la transaction.
[-m | --more]... show-log [db]
Affiche les entrées du journal de la base de données db. Les options -m ou --more peuvent être utilisées plusieurs fois pour afficher plus d'informations par entrée du journal. Par défaut, le journal est affiché dans un format compact.
check-cluster db...
Vérifie l'intégrité des bases de données clusterisées spécifiées. Ceci est principalement utilisé pour le débogage.
db-name [db]
Imprime le nom de la base de données contenu dans db. Le nom est une chaîne, par exemple "OVN_Southbound".
schema-name schema
Imprime le nom du schéma contenu dans schema. Le nom est une chaîne, par exemple "OVN_Southbound".
db-cid db
Imprime l'identifiant unique du cluster (UUID) de la base de données clusterisée db.
db-sid db
Imprime l'identifiant unique du serveur (UUID) de la base de données clusterisée db.
db-local-address db
Imprime l'adresse locale à laquelle le serveur de base de données clusterisée db est configuré pour écouter.
help
Affiche un message d'aide résumant les commandes disponibles.

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

>
Utilisez cette commande pour convertir une base de données groupée en base de données autonome lorsque le cluster est arrêté et ne peut pas être redémarré. Elle crée un nouveau fichier de base de données db autonome à partir du fichier de base de données groupée db donné.

Commandes de gestion de version

Un schéma OVSDB a un numéro de version de schéma, et une base de données OVSDB intègre une version particulière d'un schéma OVSDB. Ces numéros de version prennent la forme x.y.z, par exemple 1.2.3. L'implémentation OVSDB n'impose pas de schéma de numérotation de version particulier, mais les schémas gérés dans le cadre du projet Open vSwitch utilisent l'approche suivante. Chaque fois que le schéma de la base de données est modifié d'une manière non rétrocompatible (par exemple, suppression d'une colonne ou d'une table), x est incrémenté (et y et z sont réinitialisés à 0). Lorsque le schéma de la base de données est modifié d'une manière rétrocompatible (par exemple, ajout d'une nouvelle colonne), y est incrémenté (et z est réinitialisé à 0). Lorsque le schéma de la base de données est modifié de manière cosmétique (par exemple, réindentation de sa syntaxe), z est incrémenté.

Certaines bases de données et schémas OVSDB, en particulier les plus anciens, n'ont pas de numéro de version.

Les numéros de version de schéma et les numéros de version Open vSwitch sont indépendants.

Ces commandes fonctionnent avec différentes versions de schémas et de bases de données OVSDB.

convert [db [schema [cible]]]
Lit db, le traduit dans le schéma spécifié dans schema, et écrit la nouvelle interprétation. Si cible est spécifié, la version traduite est écrite sous forme d'un nouveau fichier nommé cible, qui ne doit pas exister au préalable. Si cible est omis, la version traduite de la base de données remplace db sur place. La conversion sur place ne peut pas avoir lieu si la base de données est actuellement servie par ovsdb-server (arrêtez ovsdb-server d'abord ou utilisez la commande convert de ovsdb-client).
Cette commande peut effectuer des « mises à niveau » et des « rétrogradations » simples sur le schéma d'une base de données. Les données dans db doivent être valides lorsqu'elles sont interprétées sous schema, avec une seule exception : les données dans db pour les tables et les colonnes qui n'existent pas dans schema sont ignorées. Les colonnes qui existent dans schema mais pas dans db reçoivent leurs valeurs par défaut. Toutes les contraintes de schema s'appliquent intégralement.
Certaines utilisations de cette commande peuvent entraîner une perte de données irrécupérable. Par exemple, la conversion d'une base de données d'un schéma qui possède une colonne ou une table donnée vers un schéma qui n'en possède pas supprimera toutes les données de cette colonne ou de cette table. Sauvegardez les bases de données critiques avant de les convertir.
Cette commande est uniquement destinée aux bases de données autonomes et active-backup. Pour les bases de données groupées, utilisez la commande convert de ovsdb-client pour les convertir en ligne.
needs-conversion [db [schema]]
Lit le schéma intégré dans db et le schéma JSON de schema et les compare. Si les schémas sont identiques, affiche no sur stdout ; s'ils diffèrent, affiche yes.
Cette commande est uniquement destinée aux bases de données autonomes et active-backup. Pour les bases de données groupées, utilisez plutôt la commande needs-conversion de ovsdb-client.
db-version [db]

schema-version [schema]
Affiche le numéro de version du schéma intégré dans la base de données db ou dans le schéma JSON schema sur stdout. Si schema ou db a été créé avant l'introduction de la version des schémas, il n'aura pas de numéro de version et cette commande affichera une ligne vide.
La commande db-version est uniquement destinée aux bases de données autonomes et active-backup. Pour les bases de données groupées, utilisez plutôt la commande schema-version de ovsdb-client.
db-cksum [db]

schema-cksum [schema]
Affiche la somme de contrôle du schéma intégré dans la base de données db ou du schéma JSON schema sur stdout. Si schema ou db a été créé avant l'introduction des sommes de contrôle de schéma, il n'aura pas de somme de contrôle et cette commande affichera une ligne vide.
La commande db-cksum est uniquement destinée aux bases de données autonomes et active-backup. Pour les bases de données groupées, utilisez plutôt la commande schema-cksum de ovsdb-client.
compare-versions a op b
Compare a et b selon op. a et b doivent être des numéros de version de schéma OVSDB sous la forme x.y.z, comme décrit dans ovsdb(7), et op doit être l'un des opérateurs < <= == >= > !=. Si la comparaison est vraie, quitte avec le statut 0 ; si elle est fausse, quitte avec le statut 2. (Le statut de sortie 1 indique une erreur, par exemple, a ou b a une syntaxe incorrecte pour une version OVSDB ou op n'est pas un opérateur de comparaison valide.)

Autres commandes

compact [db [cible]]
Lit db et écrit une version compactée. Si cible est spécifié, la version compactée est écrite sous forme d'un nouveau fichier nommé cible, qui ne doit pas exister au préalable. Si cible est omis, la version compactée de la base de données remplace db sur place. Cette commande n'est pas nécessaire en fonctionnement normal car ovsdb-server compacte périodiquement une base de données dont la taille dépasse largement sa taille minimale.
Cette commande ne fonctionne pas si db est actuellement servie par ovsdb-server, ou si elle est autrement verrouillée en écriture par un autre processus. Cette commande ne fonctionne pas non plus avec les bases de données groupées. À la place, dans l'un ou l'autre cas, envoyez la commande ovsdb-server/compact à ovsdb-server, via ovs-appctl).
[--rbac-role=rôle] query [db] transaction
Ouvre db, exécute transaction dessus, et affiche les résultats. La transaction doit être un tableau JSON au format du tableau params pour la méthode JSON-RPC transact, comme décrit dans la spécification OVSDB.
Cette commande ouvre db en accès en lecture seule, elle peut donc s'exécuter en toute sécurité en parallèle avec d'autres activités de base de données, y compris ovsdb-server et d'autres écritures de base de données. La transaction peut spécifier des modifications de base de données, mais celles-ci n'auront aucun effet sur db.
Par défaut, la transaction est exécutée en utilisant le rôle RBAC « superutilisateur ». Utilisez --rbac-role pour spécifier un rôle différent.
Cette commande ne fonctionne pas avec les bases de données groupées. Utilisez plutôt la commande query de ovsdb-client pour envoyer la requête à ovsdb-server.
[--rbac-role=rôle] transact [db] transaction
Ouvre db, exécute transaction dessus, affiche les résultats, et valide toutes les modifications dans db. La transaction doit être un tableau JSON au format du tableau params pour la méthode JSON-RPC transact, comme décrit dans la spécification OVSDB.
Cette commande ne fonctionne pas si db est actuellement servie par ovsdb-server, ou si elle est autrement verrouillée en écriture par un autre processus. Cette commande ne fonctionne pas non plus avec les bases de données groupées. À la place, dans l'un ou l'autre cas, utilisez la commande transact de ovsdb-client pour envoyer la requête à ovsdb-server.
Par défaut, la transaction est exécutée en utilisant le rôle RBAC « superutilisateur ». Utilisez --rbac-role pour spécifier un rôle différent.
[-m | --more]... show-log [db]
Affiche un résumé des enregistrements dans le journal de db, y compris l'heure et la date auxquelles chaque modification de base de données s'est produite et tout commentaire associé. Ceci peut être utile pour le débogage.
Pour augmenter la verbosité de la sortie, ajoutez -m (ou --more) une ou plusieurs fois sur la ligne de commande. Avec un -m, show-log affiche un résumé des enregistrements ajoutés, supprimés ou modifiés par chaque transaction. Avec deux -m, show-log affiche également les valeurs des colonnes modifiées par chaque changement apporté à un enregistrement.
Cette commande fonctionne avec les bases de données autonomes et active-backup ainsi qu'avec les bases de données groupées, mais les formats de sortie sont différents.
check-cluster db...
Lit tous les enregistrements des bases de données fournies, qui doivent être collectées à partir de serveurs différents (et idéalement de tous les serveurs) d'un même cluster. Vérifie chaque base de données pour son auto-cohérence et l'ensemble pour sa cohérence croisée. Si ovsdb-tool détecte un contenu inhabituel mais pas nécessairement incorrect, il affiche un avertissement ou des avertissements sur stdout. Si ovsdb-tool trouve des erreurs de cohérence, il affiche une erreur sur stderr et quitte avec le statut 1. Les erreurs indiquent généralement des bugs dans ovsdb-server ; envisagez de les signaler aux développeurs d'Open vSwitch.
db-name [db]

schema-name [schema]
Affiche le nom du schéma intégré dans la base de données db ou dans le schéma JSON schema sur stdout.
db-cid db
Affiche l'ID du cluster, qui est un UUID identifiant le cluster, pour db. Si db est une base de données nouvellement créée par ovsdb-tool cluster-join qui n'a pas encore rejoint son cluster avec succès, et si --cid n'a pas été spécifié sur la ligne de commande cluster-join, alors cette commande produira une erreur et quittera avec le statut 2, car l'ID du cluster n'est pas encore connu. Cette commande ne fonctionne qu'avec les bases de données groupées.
L'UUID de tous les zéros n'est pas un ID de cluster valide.
db-sid db
Affiche l'ID du serveur, qui est un UUID identifiant le serveur, pour db. Cette commande ne fonctionne qu'avec les bases de données groupées. Elle fonctionne même si db est une base de données nouvellement créée par ovsdb-tool cluster-join qui n'a pas encore rejoint son cluster avec succès.
db-local-address db
Affiche l'adresse locale utilisée pour le clustering de base de données pour db, dans le même format protocole:ip:port utilisé sur create-cluster et join-cluster.
db-is-clustered db

db-is-standalone db
Teste si db est un fichier de base de données au format clusterisé ou autonome, respectivement. Si c'est le cas, se termine avec le statut 0 ; sinon, se termine avec le statut 2. (Le statut de sortie 1 indique une erreur, par exemple, db n'est pas une base de données OVSDB ou n'existe pas.)

OPTIONS

Options de journalisation

-v[spéc]

--verbose=[spéc]
Définit les niveaux de journalisation. Sans aucun spéc, définit le niveau de journalisation pour chaque module et destination à dbg. Sinon, spéc est une liste de mots séparés par des espaces, des virgules ou des deux-points, jusqu'à un par catégorie ci-dessous :
  • Un nom de module valide, tel qu'affiché par la commande vlog/list sur ovs-appctl(8), limite le changement de niveau de journalisation au module spécifié.
  • syslog, console ou file, pour limiter le changement de niveau de journalisation uniquement au journal système, à la console ou à un fichier, respectivement. (Si --detach est spécifié, ovsdb-tool ferme ses descripteurs de fichiers standard, donc la journalisation vers la console n'aura aucun effet.)
Sur la plateforme Windows, syslog est accepté comme mot et n'est utile qu'avec l'option --syslog-target (le mot n'a aucun effet autrement).
•
off, emer, err, warn, info ou dbg, pour contrôler le niveau de journalisation. Les messages de la gravité donnée ou supérieure seront journalisés, et les messages de gravité inférieure seront filtrés. off filtre tous les messages. Voir ovs-appctl(8) pour une définition de chaque niveau de journalisation.
La casse n'est pas sensible dans spéc.
Indépendamment des niveaux de journalisation définis pour file, la journalisation dans un fichier n'aura pas lieu à moins que --log-file ne soit également spécifié (voir ci-dessous).
Pour la compatibilité avec les anciennes versions d'OVS, any est accepté comme mot mais n'a aucun effet.
-v

--verbose
Définit le niveau de verbosité de journalisation maximal, équivalent à --verbose=dbg.
-vPATTERN:destination:motif

--verbose=PATTERN:destination:motif
Définit le motif de journalisation pour destination à motif. Référez-vous à ovs-appctl(8) pour une description de la syntaxe valide pour motif.
-vFACILITY:facilité

--verbose=FACILITY:facilité
Définit la facilité RFC5424 du message de journal. facilité peut être l'une des suivantes : kern, user, mail, daemon, auth, syslog, lpr, news, uucp, clock, ftp, ntp, audit, alert, clock2, local0, local1, local2, local3, local4, local5, local6 ou local7. Si cette option n'est pas spécifiée, daemon est utilisé par défaut pour le syslog système local et local0 est utilisé lors de l'envoi d'un message à la cible fournie via l'option --syslog-target.
--log-file[=fichier]
Active la journalisation dans un fichier. Si fichier est spécifié, il est utilisé comme nom exact pour le fichier de journal. Le nom de fichier de journal par défaut utilisé si fichier est omis est /var/log/openvswitch/ovsdb-tool.log.
--syslog-target=hote:port
Envoie les messages syslog au port UDP sur hote, en plus du syslog système. L'hote doit être une adresse IP numérique, pas un nom d'hôte.
--syslog-method=methode
Spécifie la methode par laquelle les messages syslog doivent être envoyés au démon syslog. Les formes suivantes sont prises en charge :
  • libc, utilise la fonction syslog() de libc. L'inconvénient de cette option est que libc ajoute un préfixe fixe à chaque message avant qu'il ne soit effectivement envoyé au démon syslog via un socket de domaine UNIX /dev/log.
  • unix:fichier, utilise directement un socket de domaine UNIX. Il est possible de spécifier un format de message arbitraire avec cette option. Cependant, rsyslogd 8.9 et les versions antérieures utilisent de toute façon une fonction d'analyse codée en dur qui limite l'utilisation du socket de domaine UNIX. Si vous souhaitez utiliser un format de message arbitraire avec les anciennes versions de rsyslogd, utilisez plutôt un socket UDP vers l'adresse IP de localhost.
  • udp:ip:port, utilise un socket UDP. Avec cette méthode, il est possible d'utiliser un format de message arbitraire également avec les anciennes versions de rsyslogd. Lors de l'envoi de messages syslog sur un socket UDP, des précautions supplémentaires doivent être prises, par exemple, le démon syslog doit être configuré pour écouter sur le port UDP spécifié, des règles iptables accidentelles pourraient interférer avec le trafic syslog local et il existe certaines considérations de sécurité qui s'appliquent aux sockets UDP, mais pas aux sockets de domaine UNIX.
  • null, rejette tous les messages journalisés vers syslog.
La valeur par défaut est prise de la variable d'environnement OVS_SYSLOG_METHOD ; si elle est non définie, la valeur par défaut est libc.
