NOM

ot2kpx - extraire les informations de crénage des polices OpenType

SYNTAXE

ot2kpx [ -afm | -kpx | -lua ] <fichier_police>

DESCRIPTION

ot2kpx extrait les données de crénage des polices OpenType et les imprime sur la sortie standard ("stdout"), soit au format KPX d'Adobe (pour l'ajout à un fichier afm), soit comme une fonctionnalité personnalisée Luatex, pour utilisation avec la commande "\directlua".

OPTIONS ET ARGUMENTS

-help
Affiche un bref texte d'aide et quitte.
-version
Affiche la version de ot2kpx et quitte.
-afm, -kpx
Produit les données de crénage au format KPX d'Adobe, tel qu'utilisé dans les fichiers afm. C'est le format de sortie par défaut.
-lua
Produit les données de crénage sous forme de fonctionnalité de police personnalisée Luatex, à inclure dans une commande "\directlua".
<fichier_police>
La police OpenType (les formats otf et ttf sont pris en charge).

RESTRICTIONS

-
ot2kpx n'implémente pas toute la spécification OpenType. Les éléments manquants incluent : la prise en charge des fichiers de polices contenant plusieurs polices, les LookupTables avec des LookupTypes autres que 2, les tables "kern" avec un format autre que 0 et les ValueRecords avec des types de données autres que des données XAdvance.

La plupart de ces limitations n'auront pas d'importance, car les fonctionnalités manquantes sont rares (les seules polices que je connaisse qui les utilisent sont les polices non occidentales fournies avec Adobe Reader). De plus, bon nombre de ces fonctionnalités définissent (selon la spécification OpenType) des ajustements subtils, dépendant du périphérique, à des tailles de police ou des résolutions de périphérique spécifiques; puisqu'il n'y a aucun moyen d'exprimer de tels ajustements au format afm, les ignorer semble être la seule option de toute façon.

-
ot2kpx collecte d'abord les données de crénage de la table "kern", puis de toutes les LookupTables associées à la fonctionnalité "kern"; si une paire de crénage apparaît plusieurs fois, la première valeur rencontrée est choisie. Il y a (ou peut y avoir) plusieurs problèmes avec cette approche :
  • La spécification OpenType stipule que les polices au format otf ne devraient pas utiliser la table "kern" du tout, seulement les lookups de la table "GPOS". De nombreuses polices de ce type contiennent cependant une table "kern", mais pas de table "GPOS"; nous utilisons donc la table "kern" de toute façon.
  • Au lieu de lire toutes les LookupTables, il serait peut-être préférable de laisser l'utilisateur spécifier un script et une langue et de ne traiter que les LookupTables pour ces valeurs. Cependant, du moins dans les polices que j'ai vérifiées, toutes les combinaisons de scripts/langues pointent finalement vers les mêmes LookupTables "kern", donc cette approche ne ferait aucune différence (en plus de compliquer davantage le code).
