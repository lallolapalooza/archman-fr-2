NAME

ossl-guide-quic-client-non-block - Guide OpenSSL : Écrire un client QUIC non bloquant simple

EXEMPLE DE CLIENT QUIC NON BLOQUANT SIMPLE

Cette page s'appuie sur l'exemple développé dans la page ossl-guide-quic-client-block(7) qui démontre comment écrire un client QUIC bloquant simple. Sur cette page, nous modifierons ce code de démonstration afin qu'il prenne en charge la fonctionnalité non bloquante.

Le code source complet de cet exemple de client QUIC non bloquant est disponible dans le répertoire demos/guide de la distribution source OpenSSL, dans le fichier quic-client-non-block.c. Il est également disponible en ligne sur https://github.com/openssl/openssl/blob/master/demos/guide/quic-client-non-block.c.

Comme nous l'avons vu dans l'exemple précédent, une application QUIC OpenSSL utilise toujours un socket non bloquant. Cependant, malgré cela, l'objet SSL a toujours un comportement bloquant. Lorsque l'objet SSL a un comportement bloquant, cela signifie qu'il attend (bloque) jusqu'à ce que des données soient disponibles en lecture si vous tentez de lire à partir de celui-ci alors qu'il n'y a pas encore de données. De même, il attend lors de l'écriture si l'objet SSL ne peut pas écrire pour le moment. Cela peut simplifier le développement du code car vous n'avez pas à vous soucier de ce qu'il faut faire dans ces cas. L'exécution du code s'arrêtera simplement jusqu'à ce qu'elle puisse continuer. Cependant, dans de nombreux cas, vous ne voulez pas ce comportement. Plutôt que de s'arrêter et d'attendre, votre application peut avoir besoin d'effectuer d'autres tâches pendant que l'objet SSL est incapable de lire/écrire, par exemple mettre à jour une interface graphique ou effectuer des opérations sur une autre connexion ou un autre flux.

Nous verrons plus loin dans ce tutoriel comment modifier l'objet SSL pour qu'il ait un comportement non bloquant. Avec un objet SSL non bloquant, des fonctions telles que SSL_read_ex(3) ou SSL_write_ex(3) reviendront immédiatement avec une erreur non fatale si elles ne peuvent actuellement pas lire ou écrire respectivement.

Étant donné que cette page s'appuie sur l'exemple développé dans la page ossl-guide-quic-client-block(7), nous supposons que vous en êtes familier et nous n'expliquons que les différences de cet exemple.

Effectuer du travail en attendant le socket

Dans une application non bloquante, vous aurez besoin de travail à effectuer dans le cas où nous voulons lire ou écrire sur l'objet SSL, mais que nous en sommes actuellement incapables. En fait, c'est tout l'intérêt d'utiliser un objet SSL non bloquant, c'est-à-dire donner à l'application l'opportunité de faire autre chose. Quoi qu'il en soit, l'application doit également être prête à revenir et à retenter périodiquement l'opération qu'elle a précédemment tentée pour voir si elle peut maintenant réussir. Idéalement, elle ne le ferait que si quelque chose a changé de telle sorte que la tentative de relance puisse réussir, mais ce n'est pas obligatoire. Elle peut retenter à tout moment.

Notez qu'il est important de retenter exactement la même opération que celle que vous avez essayée la dernière fois. Vous ne pouvez pas commencer quelque chose de nouveau. Par exemple, si vous tentiez d'écrire le texte "Hello World" et que l'opération a échoué parce que l'objet SSL ne peut pas écrire actuellement, alors vous ne pouvez pas tenter d'écrire un autre texte lors de la nouvelle tentative.

Dans cette application de démonstration, nous allons créer une fonction d'aide qui simule l'exécution d'autres travaux. En fait, pour des raisons de simplicité, elle ne fera rien d'autre qu'attendre que l'état du socket sous-jacent change ou jusqu'à ce qu'un délai d'attente expire après quoi l'état de l'objet SSL pourrait avoir changé. Nous appellerons notre fonction wait_for_activity().

    static void wait_for_activity(SSL *ssl)
    {
        fd_set wfds, rfds;
        int width, sock, isinfinite;
        struct timeval tv;
        struct timeval *tvp = NULL;
        /* Obtenir le descripteur de fichier sous-jacent pour le socket */
        sock = SSL_get_fd(ssl);
        FD_ZERO(&wfds);
        FD_ZERO(&rfds);
        /*
         * Déterminer si nous souhaitons écrire sur le socket, ou en lire (ou
         * les deux)
         */
        if (SSL_net_write_desired(ssl))
            FD_SET(sock, &wfds);
        if (SSL_net_read_desired(ssl))
            FD_SET(sock, &rfds);
        width = sock + 1;
        /*
         * Déterminer quand OpenSSL souhaite être appelé à nouveau, indépendamment
         * du fait que l'état du socket sous-jacent ait changé ou non.
         */
        if (SSL_get_event_timeout(ssl, &tv, &isinfinite) && !isinfinite)
            tvp = &tv;
        /*
         * Attendre jusqu'à ce que le socket soit accessible en écriture ou en lecture.
         * Nous utilisons select ici pour des raisons de simplicité et de portabilité,
         * mais vous pourriez tout aussi bien utiliser poll/epoll ou des fonctions similaires.
         *
         * REMARQUE : Aux fins de ce code de démonstration, cela fait effectivement
         * que cette démo bloque jusqu'à ce qu'elle ait quelque chose de plus utile à faire.
         * Dans une application réelle, vous voudrez probablement effectuer d'autres
         * tâches ici (par exemple, mettre à jour une interface graphique, ou gérer
         * d'autres connexions).
         *
         * Disons, par exemple, que vous souhaitez mettre à jour le compteur de
         * progression d'une interface graphique toutes les 100 ms. Une façon de le
         * faire serait d'utiliser le délai d'attente dans le dernier paramètre de
         * "select" ci-dessous. Si la valeur de tvp est supérieure à 100 ms, utilisez
         * 100 ms à la place. Ensuite, lorsque select renvoie, vous vérifiez s'il
         * l'a fait en raison d'une activité sur les descripteurs de fichiers ou
         * en raison du délai d'attente. Si le délai d'attente de l'interface graphique
         * de 100 ms a expiré mais que le délai d'attente de tvp n'a pas expiré, alors
         * allez mettre à jour l'interface graphique, puis redémarrez le
         * "select" (avec des délais d'attente mis à jour).
         */
        select(width, &rfds, &wfds, NULL, tvp);
}

Si vous êtes familier avec la façon d'écrire des applications non bloquantes dans OpenSSL pour TLS (voir ossl-guide-tls-client-non-block(7)) alors vous devriez noter qu'il y a une différence importante ici entre la façon dont fonctionne une application QUIC et une application TLS. Avec une application TLS, si nous essayons de lire ou d'écrire quelque chose sur l'objet SSL et que nous obtenons une réponse "retry" (SSL_ERROR_WANT_READ ou SSL_ERROR_WANT_WRITE), alors nous pouvons supposer que c'est parce qu'OpenSSL a tenté de lire ou d'écrire sur le socket sous-jacent et que le socket a signalé le "retry". Avec QUIC, ce n'est pas le cas. OpenSSL peut signaler un retry à la suite d'un appel à SSL_read_ex(3) ou SSL_write_ex(3) (ou similaire) qui indique l'état du flux. Ceci est entièrement indépendant du fait que le socket sous-jacent doive ou non réessayer.

Pour déterminer si OpenSSL souhaite actuellement lire ou écrire sur le socket sous-jacent pour une application QUIC, nous devons appeler les fonctions SSL_net_read_desired(3) et SSL_net_write_desired(3).

Il est également important avec QUIC d'appeler périodiquement une fonction d'E/S (ou d'appeler autrement la fonction SSL_handle_events(3)) pour s'assurer que la connexion QUIC reste saine. C'est particulièrement important avec une application non bloquante car vous risquez de laisser l'objet SSL inactif pendant un certain temps pendant que l'application effectue d'autres tâches. La fonction SSL_get_event_timeout(3) peut être utilisée pour déterminer la date limite du prochain appel à une fonction d'E/S (ou l'appel à SSL_handle_events(3)).

Une alternative à l'utilisation de SSL_get_event_timeout(3) pour trouver la prochaine échéance à laquelle OpenSSL doit être appelé à nouveau est d'utiliser le mode "assisté par thread". En mode "assisté par thread", OpenSSL démarre un thread supplémentaire qui appellera périodiquement SSL_handle_events(3) automatiquement, ce qui signifie que l'application peut laisser la connexion inactive en sachant que la connexion sera toujours maintenue dans un état sain. Voir "Création des objets SSL_CTX et SSL" ci-dessous pour plus de détails à ce sujet.

Dans cet exemple, nous utilisons la fonction "select" pour vérifier la lisibilité/l'écrivabilité du socket car elle est très simple à utiliser et disponible sur la plupart des systèmes d'exploitation. Cependant, vous pourriez utiliser toute autre fonction similaire pour faire la même chose. "select" attend que l'état du sous-jacent

ng socket(s) à devenir lisible/écrivable ou jusqu'à ce que le délai d'attente soit expiré avant de retourner.

Gestion des erreurs des fonctions d'E/S OpenSSL

Une application QUIC configurée pour un comportement non bloquant devra être préparée à gérer les erreurs retournées par les fonctions d'E/S OpenSSL telles que SSL_read_ex(3) ou SSL_write_ex(3). Les erreurs peuvent être fatales pour le flux (par exemple parce que le flux a été réinitialisé ou parce que la connexion sous-jacente a échoué), ou non fatales (par exemple parce que nous essayons de lire à partir du flux mais aucune donnée n'est encore arrivée du pair pour ce flux).

SSL_read_ex(3) et SSL_write_ex(3) retourneront 0 pour indiquer une erreur et SSL_read(3) et SSL_write(3) retourneront 0 ou une valeur négative pour indiquer une erreur. SSL_shutdown(3) retournera une valeur négative pour indiquer une erreur.

En cas d'erreur, une application doit appeler SSL_get_error(3) pour savoir quel type d'erreur s'est produit. Si l'erreur n'est pas fatale et peut être retentée, SSL_get_error(3) retournera SSL_ERROR_WANT_READ ou SSL_ERROR_WANT_WRITE selon que OpenSSL souhaitait lire depuis ou écrire vers le flux mais n'a pas pu. Notez qu'un appel à SSL_read_ex(3) ou SSL_read(3) peut toujours générer SSL_ERROR_WANT_WRITE. De même, les appels à SSL_write_ex(3) ou SSL_write(3) peuvent générer SSL_ERROR_WANT_READ.

Un autre type d'erreur non fatale qui peut se produire est SSL_ERROR_ZERO_RETURN. Cela indique un EOF (End-Of-File) qui peut se produire si vous tentez de lire des données à partir d'un objet SSL mais que le pair a indiqué qu'il n'enverra plus de données sur le flux. Dans ce cas, vous voudrez peut-être toujours écrire des données sur le flux, mais vous ne recevrez plus de données.

Les erreurs fatales qui peuvent se produire sont SSL_ERROR_SYSCALL et SSL_ERROR_SSL. Celles-ci indiquent que le flux n'est plus utilisable. Par exemple, cela peut être parce que le flux a été réinitialisé par le pair, ou parce que la connexion sous-jacente a échoué. Vous pouvez consulter la pile d'erreurs OpenSSL pour plus de détails (par exemple, en appelant ERR_print_errors(3) pour imprimer les détails des erreurs qui se sont produites). Vous pouvez également consulter la valeur de retour de SSL_get_stream_read_state(3) pour déterminer si l'erreur est locale au flux, ou si la connexion sous-jacente a également échoué. Une valeur de retour de SSL_STREAM_STATE_RESET_REMOTE vous indique que le flux a été réinitialisé par le pair et SSL_STREAM_STATE_CONN_CLOSED vous indique que la connexion sous-jacente s'est fermée.

Dans notre application de démonstration, nous écrirons une fonction pour gérer ces erreurs des fonctions d'E/S OpenSSL :

static int handle_io_failure(SSL *ssl, int res)
{
    switch (SSL_get_error(ssl, res)) {
    case SSL_ERROR_WANT_READ:
    case SSL_ERROR_WANT_WRITE:
        /* Échec temporaire. Attendre jusqu'à ce que nous puissions lire/écrire et réessayer */
        wait_for_activity(ssl);
        return 1;
    case SSL_ERROR_ZERO_RETURN:
        /* EOF */
        return 0;
    case SSL_ERROR_SYSCALL:
        return -1;
    case SSL_ERROR_SSL:
        /*
         * Une erreur fatale de flux s'est produite. Cela peut être dû à une
         * réinitialisation de flux - ou à un échec sur la connexion
         * sous-jacente.
         */
        switch (SSL_get_stream_read_state(ssl)) {
        case SSL_STREAM_STATE_RESET_REMOTE:
            printf("Stream reset occurred\n");
            /*
             * Le flux a été réinitialisé mais la connexion est toujours
             * saine.
             */
            break;
        case SSL_STREAM_STATE_CONN_CLOSED:
            printf("Connection closed\n");
            /* La connexion est déjà fermée. */
            break;
        default:
            printf("Unknown stream failure\n");
            break;
        }
        /*
         * Si l'échec est dû à une erreur de vérification, nous pouvons obtenir plus
         * d'informations à ce sujet via SSL_get_verify_result().
         */
        if (SSL_get_verify_result(ssl) != X509_V_OK)
            printf("Verify error: %s\n",
                X509_verify_cert_error_string(SSL_get_verify_result(ssl)));
        return -1;
    default:
        return -1;
    }
}

Cette fonction prend en arguments l'objet SSL qui représente la connexion, ainsi que le code de retour de la fonction d'E/S qui a échoué. En cas d'échec non fatal, elle attend qu'une nouvelle tentative de l'opération d'E/S puisse réussir (en utilisant la fonction wait_for_activity() que nous avons développée dans la section précédente). Elle retourne 1 en cas d'erreur non fatale (sauf EOF), 0 en cas d'EOF, ou -1 si une erreur fatale s'est produite.

Création des objets SSL_CTX et SSL

Afin de se connecter à un serveur, nous devons créer des objets SSL_CTX et SSL pour cela. La plupart des étapes pour y parvenir sont les mêmes que pour un client bloquant et sont expliquées sur la page ossl-guide-quic-client-block(7). Nous ne répéterons pas cette information ici.

Une différence clé est que nous devons mettre l'objet SSL en mode non bloquant (le mode par défaut est bloquant). Pour ce faire, nous utilisons la fonction SSL_set_blocking_mode(3) :

/*
 * Le socket sous-jacent est toujours non bloquant avec QUIC, mais le comportement
 * par défaut de l'objet SSL est toujours de bloquer. Nous le définissons en mode non bloquant
 * dans cette démo.
 */
if (!SSL_set_blocking_mode(ssl, 0)) {
    printf("Failed to turn off blocking mode\n");
    goto end;
}

Bien que l'application de démonstration que nous développons ici ne l'utilise pas, il est possible d'utiliser le "mode assisté par thread" lors du développement d'applications QUIC. Normalement, lors de l'écriture d'une application QUIC OpenSSL, il est important que SSL_handle_events(3) (ou alternativement toute fonction d'E/S) soit appelée périodiquement sur l'objet SSL de la connexion pour maintenir la connexion en bon état. Voir "Effectuer des tâches en attendant le socket" pour plus de discussion à ce sujet. Ceci est particulièrement important à garder à l'esprit lors de l'écriture d'une application QUIC non bloquante, car il est courant de laisser l'objet de connexion SSL inactif pendant un certain temps lors de l'utilisation du mode non bloquant. En utilisant le "mode assisté par thread", un thread séparé est créé par OpenSSL pour gérer cela automatiquement, ce qui signifie que le développeur de l'application n'a pas besoin de gérer cet aspect. Pour ce faire, nous devons utiliser OSSL_QUIC_client_thread_method(3) lors de la construction du SSL_CTX, comme montré ci-dessous :

ctx = SSL_CTX_new(OSSL_QUIC_client_thread_method());
if (ctx == NULL) {
    printf("Failed to create the SSL_CTX\n");
    goto end;
}

Effectuer la poignée de mains SSL

Comme dans la démo pour un client QUIC bloquant, nous utilisons la fonction SSL_connect(3) pour effectuer la poignée de mains avec le serveur. Étant donné que nous utilisons un objet SSL non bloquant, il est très probable que les appels à cette fonction échoueront avec une erreur non fatale pendant que nous attendons la réponse du serveur à nos messages de poignée de mains. Dans un tel cas, nous devons retenter le même appel à SSL_connect(3) ultérieurement. Dans cette démo, nous le faisons dans une boucle :

/* Effectuer la poignée de mains avec le serveur */
while ((ret = SSL_connect(ssl)) != 1) {
    if (handle_io_failure(ssl, ret) == 1)
        continue; /* Retenter */
    printf("Failed to connect to server\n");
    goto end; /* Impossible de retenter : erreur */
}

Nous appelons continuellement SSL_connect(3) jusqu'à ce qu'il nous donne une réponse de succès. Sinon, nous utilisons la fonction handle_io_failure() que nous avons créée précédemment pour déterminer ce qu'il faut faire ensuite. Notez que nous ne nous attendons pas à un EOF à ce stade, donc une telle réponse est traitée de la même manière qu'une erreur fatale.

Envoi et réception de données

Comme avec la démo du client QUIC bloquant, nous utilisons la fonction SSL_write_ex(3) pour envoyer des données au serveur. Comme avec SSL_connect(3) ci-dessus, parce que nous utilisons un objet SSL non bloquant, cet appel peut échouer avec une erreur non fatale. Dans ce cas, nous devrions retenter exactement le même appel à SSL_write_ex(3). Notez que les paramètres doivent être *exactement* les mêmes, c'est-à-dire le même pointeur vers le tampon à écrire avec la même longueur. Vous ne devez pas tenter d'envoyer des données différentes lors d'une nouvelle tentative. Un mode optionnel existe (SSL_MODE_ACCEPT_MOVING_WRITE_BUFFER) qui configurera OpenSSL pour permettre au tampon d'être écrit de changer d'une tentative à l'autre. Cependant, dans ce cas, vous devez toujours retenter les mêmes données - même si le tampon qui contient ces données peut changer d'emplacement. Voir SSL_CTX_set_mode(3) pour plus de détails. Comme dans les tutoriels TLS (ossl-guide-tls-client-block(7)), nous écrivons la requête en trois morceaux.

Premièrement, nous écrivons la requête entière dans le flux. Nous devons également nous assurer de signaler au serveur que nous avons fini d'écrire. Cela peut être fait en passant le flag SSL_WRITE_FLAG_CONCLUDE à SSL_write_ex2(3) ou en appelant SSL_stream_conclude(3). Puisque la première méthode est plus efficace, nous choisissons de le faire.

/* Écrire une requête GET HTTP au pair */
while (!SSL_write_ex(ssl, request_start, strlen(request_start), &written)) {
    if (handle_io_failure(ssl, 0) == 1)
        continue; /* Retenter */
    printf("Failed to write start of HTTP request\n");
    goto end; /* Impossible de retenter : erreur */
}
while (!SSL_write_ex(ssl, hostname, strlen(hostname), &written)) {
    if (handle_io_failure(ssl, 0) == 1)
        continue; /* Retenter */
    printf("Failed to write hostname in HTTP request\n");
    goto end; /* Impossible de retenter : erreur */
}
while (!SSL_write_ex2(ssl, request_end, strlen(request_end),
       SSL_WRITE_FLAG_CONCLUDE, &written)) {
    if (handle_io_failure(ssl, 0) == 1)
        continue; /* Retenter */
    printf("Failed to write end of HTTP request\n"
;); goto end; /* Impossible de réessayer : erreur */ }

Lors d'une écriture, nous ne nous attendons pas à recevoir une réponse EOF, nous traitons donc ce cas de la même manière qu'une erreur fatale.

Lire une réponse du serveur est similaire :

do {
    /*
     * Lire jusqu'à sizeof(buf) octets de la réponse. Nous continuons à lire
     * jusqu'à ce que le serveur ferme la connexion.
     */
    while (!eof && !SSL_read_ex(ssl, buf, sizeof(buf), &readbytes)) {
        switch (handle_io_failure(ssl, 0)) {
        case 1:
            continue; /* Réessayer */
        case 0:
            eof = 1;
            continue;
        case -1:
        default:
            printf("Échec de la lecture des données restantes\n");
            goto end; /* Impossible de réessayer : erreur */
        }
    }
    /*
     * OpenSSL ne garantit pas que les données retournées sont une chaîne
     * ou qu'elles sont terminées par NUL, nous utilisons donc fwrite()
     * pour écrire le nombre exact d'octets que nous avons lus. Les données
     * pourraient être non imprimables ou contenir des caractères NUL
     * au milieu. Pour cet exemple simple, nous allons les imprimer
     * sur stdout de toute façon.
     */
    if (!eof)
        fwrite(buf, 1, readbytes, stdout);
} while (!eof);
/* Au cas où la réponse ne se terminerait pas par un saut de ligne, nous en ajoutons un maintenant */
printf("\n");

La principale différence cette fois-ci est qu'il est valide pour nous de recevoir une réponse EOF lors de la tentative de lecture de données du serveur. Cela se produira lorsque le serveur fermera la connexion après avoir envoyé toutes les données de sa réponse.

Dans cette démo, nous imprimons simplement toutes les données reçues en réponse du serveur. Nous continuons à tourner dans la boucle jusqu'à ce que nous rencontrions une erreur fatale ou que nous recevions un EOF (indiquant une fin gracieuse).

Fermeture de la connexion

Comme dans l'exemple de client QUIC bloquant, nous devons fermer la connexion lorsque nous avons terminé avec elle.

Même si nous avons reçu un EOF sur le flux à partir duquel nous lisions ci-dessus, cela ne nous dit rien sur l'état de la connexion sous-jacente. Notre application de démonstration initiera le processus de fermeture de connexion via SSL_shutdown(3).

Étant donné que notre application initie la fermeture, nous pourrions nous attendre à ce que SSL_shutdown(3) renvoie 0, puis nous devrions continuer à l'appeler jusqu'à ce que nous recevions un retour de 1 (signifiant que nous avons terminé avec succès la fermeture). Comme nous utilisons un objet SSL non bloquant, nous pourrions devoir réessayer cette opération plusieurs fois. Si SSL_shutdown(3) renvoie un résultat négatif, nous devons appeler SSL_get_error(3) pour déterminer la marche à suivre. Nous utilisons notre fonction handle_io_failure() que nous avons développée précédemment pour cela :

/*
 * Appeler SSL_shutdown() de manière répétée jusqu'à ce que la connexion
 * soit complètement fermée.
 */
while ((ret = SSL_shutdown(ssl)) != 1) {
    if (ret < 0 && handle_io_failure(ssl, ret) == 1)
        continue; /* Réessayer */
}

Nettoyage final

Comme pour l'exemple de client QUIC bloquant, une fois que notre connexion est terminée, nous devons la libérer. Les étapes pour le faire pour cet exemple sont les mêmes que pour l'exemple bloquant, nous ne le répéterons donc pas ici.
