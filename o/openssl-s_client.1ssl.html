DESCRIPTION

Cette commande implémente un client SSL/TLS générique qui se connecte à un hôte distant en utilisant SSL/TLS. C'est un outil de diagnostic *très* utile pour les serveurs SSL.

OPTIONS

En plus des options ci-dessous, cette commande prend également en charge les options communes et spécifiques aux clients documentées dans la section "Supported Command Line Commands" de la page de manuel SSL_CONF_cmd(3).

-help
Affiche un message d'utilisation.
-ssl_config section
Utilise la section spécifiée du fichier de configuration pour configurer l'objet SSL_CTX.
-connect hôte:port
Ceci spécifie l'hôte et le port optionnel auxquels se connecter. Il est possible de sélectionner l'hôte et le port en utilisant l'argument positionnel cible optionnel à la place. Si ni ceci ni l'argument positionnel cible ne sont spécifiés, une tentative de connexion à l'hôte local sur le port 4433 est effectuée. Si la chaîne de l'hôte est une adresse IPv6, elle doit être entourée de "[" et "]".
-host nom_hôte
Hôte auquel se connecter ; utilisez plutôt -connect.
-port port
Connectez-vous au port spécifié ; utilisez plutôt -connect.
-bind hôte:port
Ceci spécifie l'adresse de l'hôte et/ou le port à lier comme source pour la connexion. Pour les sockets de domaine Unix, le port est ignoré et l'hôte est utilisé comme adresse de socket source. Si la chaîne de l'hôte est une adresse IPv6, elle doit être entourée de "[" et "]".
-proxy hôte:port
Lorsqu'il est utilisé avec l'option -connect, le programme utilise l'hôte et le port spécifiés avec cette option et émet une commande HTTP CONNECT pour se connecter au serveur désiré. Si la chaîne de l'hôte est une adresse IPv6, elle doit être entourée de "[" et "]".
-proxy_user identifiant
Lorsqu'il est utilisé avec l'option -proxy, le programme tentera d'authentifier le proxy spécifié en utilisant l'authentification de base (base64). NB : L'authentification de base n'est pas sécurisée ; les identifiants sont envoyés au proxy dans un encodage base64 facilement réversible avant que toute session TLS/SSL ne soit établie. Par conséquent, ces identifiants sont facilement récupérables par quiconque capable de sniffer/tracer le réseau. À utiliser avec prudence.
-proxy_pass arg
La source du mot de passe proxy, utilisée avec l'option -proxy_user. Pour plus d'informations sur le format de arg, voir openssl-passphrase-options(1).
-unix chemin

nnect sur le socket de domaine Unix spécifié.
-4
Utiliser IPv4 uniquement.
-6
Utiliser IPv6 uniquement.
-quic
Se connecter en utilisant le protocole QUIC. Si spécifié, l'option -alpn doit également être fournie.
-servername nom
Définir l'extension SNI (Server Name Indication) TLS dans le message ClientHello à la valeur donnée. Si -servername n'est pas fourni, l'extension TLS SNI sera remplie avec le nom donné à -connect s'il suit un format de nom DNS. Si -connect n'est pas non plus fourni, le SNI est défini sur "localhost". C'est le comportement par défaut depuis OpenSSL 1.1.1.

Même si le SNI devrait normalement être un nom DNS et non une adresse IP, si -servername est fourni, ce nom sera envoyé, qu'il s'agisse d'un nom DNS ou non.

Cette option ne peut pas être utilisée conjointement avec -noservername.

-noservername
Supprime l'envoi de l'extension SNI (Server Name Indication) dans le message ClientHello. Ne peut pas être utilisé conjointement avec les options -servername ou -dane_tlsa_domain.
-cert nom_fichier
Le certificat client à utiliser, si l'un est demandé par le serveur. Par défaut, aucun certificat n'est utilisé.

La chaîne du certificat client peut être spécifiée en utilisant -cert_chain.

-certform DER|PEM|P12
Le format du fichier du certificat client à utiliser ; non spécifié par défaut. Voir openssl-format-options(1) pour les détails.
-cert_chain
Un fichier ou une URI de certificats non approuvés à utiliser lors de la tentative de construction de la chaîne de certificats liée au certificat spécifié via l'option -cert. L'entrée peut être au format PEM, DER ou PKCS#12.
-build_chain
Spécifie si l'application doit construire la chaîne de certificats client à fournir au serveur.
-CRL nom_fichier
Fichier CRL à utiliser pour vérifier le certificat du serveur.
-CRLform DER|PEM
Le format du fichier CRL ; non spécifié par défaut. Voir openssl-format-options(1) pour les détails.
-crl_download
Télécharge les CRL depuis les points de distribution dans le certificat. Notez que cette option est ignorée si l'option -crl_check n'est pas fournie. Notez que la taille maximale d'un CRL est limitée par la fonction X509_CRL_load_http(3).
-key nom_fichier|uri
La clé privée client à utiliser. Si non spécifiée, le fichier de certificat sera également utilisé pour lire la clé.
-keyform DER|PEM|P12|ENGINE
Le format de la clé ; non spécifié par défaut. Voir openssl-format-options(1) pour les détails.
-pass arg
La source du mot de passe du fichier de clé privée et de certificat. Pour plus d'informations sur le format de arg, voir openssl-passphrase-options(1).
-verify profondeur
La profondeur de vérification à utiliser. Ceci spécifie la longueur maximale de la chaîne de certificats du serveur et active la vérification du certificat serveur. Sauf si l'option -verify_return_error est donnée, l'opération de vérification continue après les erreurs, de sorte que tous les problèmes avec une chaîne de certificats puissent être vus. Par effet secondaire, la connexion n'échouera jamais en raison d'un échec de vérification du certificat serveur.

Par défaut, la validation des certificats serveur et de leur chaîne est effectuée par rapport au but (D)TLS Serveur ("sslserver"). Pour plus de détails, voir "Certificate Extensions" dans openssl-verification-options(1).

-verify_return_error
Active la vérification du certificat serveur, comme avec -verify, mais renvoie les erreurs de vérification au lieu de continuer. Cela interrompra généralement la négociation avec une erreur fatale.
-verify_quiet
Limite la sortie de vérification aux erreurs uniquement.
-verifyCAfile nom_fichier
Un fichier au format PEM contenant des certificats de confiance à utiliser pour vérifier le certificat du serveur.
-verifyCApath répertoire
Un répertoire contenant des certificats de confiance à utiliser pour vérifier le certificat du serveur. Ce répertoire doit être au "format hash", voir openssl-verify(1) pour plus d'informations.
-verifyCAstore uri
L'URI d'un magasin contenant des certificats de confiance à utiliser pour vérifier le certificat du serveur.
-chainCAfile fichier
Un fichier au format PEM contenant des certificats de confiance à utiliser lors de la tentative de construction de la chaîne de certificats client.
-chainCApath répertoire
Un répertoire contenant des certificats de confiance à utiliser pour construire la chaîne de certificats client fournie au serveur. Ce répertoire doit être au "format hash", voir openssl-verify(1) pour plus d'informations.
-chainCAstore uri
L'URI d'un magasin contenant des certificats de confiance à utiliser lors de la tentative de construction de la chaîne de certificats client. L'URI peut indiquer un seul certificat, ainsi qu'une collection de ceux-ci. Avec les URIs du schéma "file:", cela agit comme -chainCAfile ou -chainCApath, selon que l'URI indique un répertoire ou un seul fichier. Voir ossl_store-file(7) pour plus d'informations sur le schéma "file:".
-requestCAfile fichier
Un fichier contenant une liste de certificats dont les noms de sujet seront envoyés au serveur dans l'extension certificate_authorities. Uniquement supporté pour TLS 1.3
-dane_tlsa_domain domaine
Active l'authentification DANE TLSA RFC6698/RFC7671 et spécifie le domaine de base TLSA qui devient l'indice SNI par défaut et l'identifiant de référence principal pour les vérifications de nom d'hôte. Cela doit être utilisé en combinaison avec au moins une instance de l'option -dane_tlsa_rrdata ci-dessous.

Lorsque l'authentification DANE réussit, la sortie diagnostique inclura la profondeur la plus basse (la plus proche de 0) à laquelle un enregistrement TLSA a authentifié un certificat de chaîne. Lorsque cet enregistrement TLSA est une clé publique d'ancre de confiance "2 1 0" qui a signé (plutôt que fait correspondre) le certificat le plus haut de la chaîne, le résultat est rapporté comme "TA public key verified". Sinon, soit l'enregistrement TLSA "matched TA certificate" à une profondeur positive, soit "matched EE certificate" à la profondeur 0.

-dane_tlsa_rrdata rrdata
Utiliser une ou plusieurs fois pour spécifier les champs RRDATA de l'ensemble RR DANE TLSA associé au service cible. La valeur rrdata est spécifiée en "forme de présentation", c'est-à-dire quatre champs séparés par des espaces qui spécifient l'usage, le sélecteur, le type de correspondance et les données associées, ces dernières étant encodées en hexadécimal. Les espaces optionnels sont ignorés dans le champ des données associées. Par exemple : 
$ openssl s_client -brief -starttls smtp \
  -connect smtp.example.com:25 \
  -dane_tlsa_domain smtp.example.com \
  -dane_tlsa_rrdata "2 1 1
    B111DD8A1C2091A89BD4FD60C57F0716CCE50FEEFF8137CDBEE0326E 02CF362B" \
  -dane_tlsa_rrdata "2 1 1
    60B87575447DCBA2A36B7D11AC09FB24A9DB406FEE12D2CC90180517 616E8A18"
...
Verification: OK
Verified peername: smtp.example.com
DANE TLSA 2 1 1 ...ee12d2cc90180517616e8a18 matched TA certificate at depth 1
...
-dane_ee_no_namechecks
Ceci désactive les vérifications de nom de serveur lors de l'authentification via les enregistrements TLSA de DANE-EE(3). Pour certaines applications, principalement les navigateurs Web, il n'est pas sûr de désactiver les vérifications de nom en raison des attaques par "partage de clé inconnu", dans lesquelles un serveur malveillant peut convaincre un client qu'une connexion à un serveur victime est en fait une connexion sécurisée au serveur malveillant. Le serveur malveillant peut alors être en mesure de violer les restrictions de script inter-origines. Ainsi, malgré le texte de la RFC7671, les vérifications de nom sont activées par défaut pour les enregistrements TLSA de DANE-EE(3), et peuvent être désactivées dans les applications où cela est sûr. En particulier, les clients SMTP et XMPP devraient définir cette option car les enregistrements SRV et MX permettent déjà à un domaine distant de rediriger les connexions client vers n'importe quel serveur de son choix, et dans tous les cas, les clients SMTP et XMPP n'exécutent pas de scripts téléchargés à partir de serveurs distants.
-reconnect
Reconnecte au même serveur 5 fois en utilisant le même identifiant de session, cela peut être utilisé comme test que la mise en cache de session fonctionne.
-showcerts
Affiche la liste des certificats serveur telle qu'envoyée par le serveur : elle ne se compose que des certificats que le serveur a envoyés (dans l'ordre où le serveur les a envoyés). Ce n'est **pas** une chaîne vérifiée.
-prexit
Affiche les informations de session lorsque le programme se termine. Cela tentera toujours d'afficher les informations même si la connexion échoue. Normalement, les informations ne sont affichées qu'une fois si la connexion réussit. Th
est option est utile car le chiffrement utilisé peut être renégocié ou la connexion peut échouer car un certificat client est requis ou est demandé uniquement après une tentative d'accès à une certaine URL. Remarque : la sortie produite par cette option n'est pas toujours précise car une connexion n'a peut-être jamais été établie.
-no-interactive
Ce drapeau peut être utilisé pour exécuter le client en mode non interactif.
-state
Affiche les états de la session SSL.
-debug
Affiche des informations de débogage étendues, y compris un vidage hexadécimal de tout le trafic.
-nocommands
N'utilise pas de lettres de commande interactives.
-adv
Utilise le mode de commande avancé.
-security_debug
Active les messages de débogage de sécurité.
-security_debug_verbose
Produit une sortie de débogage de sécurité plus détaillée.
-msg
Affiche les messages du protocole.
-timeout
Active le délai d'attente d'envoi/réception sur les connexions DTLS.
-mtu taille
Définit la MTU de la couche de liaison à la taille spécifiée.
-no_ems
Désactive la négociation du secret maître étendu.
-keymatexport étiquette
Exporte le matériel de chiffrement en utilisant l'étiquette spécifiée.
-keymatexportlen len
Exporte le nombre d'octets spécifié de matériel de chiffrement ; par défaut 20.

Affiche tous les messages du protocole avec un vidage hexadécimal.

-trace
Affiche une sortie de trace détaillée des messages du protocole.
-msgfile nom_fichier
Fichier de destination pour la sortie de -msg ou -trace, par défaut la sortie standard.
-nbio_test
Teste les E/S non bloquantes.
-nbio
Active les E/S non bloquantes.
-crlf
Cette option transforme un saut de ligne du terminal en CR+LF, comme requis par certains serveurs.
-ign_eof
Empêche la fermeture de la connexion lorsque la fin du fichier est atteinte dans l'entrée. Ceci active implicitement également -nocommands.
-quiet
Empêche l'affichage des informations de session et de certificat. Ceci active implicitement également -ign_eof et -nocommands.
-no_ign_eof
Ferme la connexion lorsque la fin du fichier est atteinte dans l'entrée. Peut être utilisé pour outre l'implicite -ign_eof après -quiet.
-psk_identity identité
Utilise l'identité PSK identité lors de l'utilisation d'une suite de chiffrement PSK. La valeur par défaut est "Client_identity" (sans les guillemets).
-psk clé
Utilise la clé PSK clé lors de l'utilisation d'une suite de chiffrement PSK. La clé est donnée sous forme de nombre hexadécimal sans 0x initial, par exemple -psk 1a2b3c4d. Cette option doit être fournie pour utiliser un chiffrement PSK.
-psk_session fichier
Utilise les données SSL_SESSION encodées pem stockées dans fichier comme base d'un PSK. Notez que cela ne fonctionnera que si TLSv1.3 est négocié.
-sctp
Utilise SCTP pour le protocole de transport au lieu d'UDP dans DTLS. Doit être utilisé conjointement avec -dtls, -dtls1 ou -dtls1_2. Cette option n'est disponible que là où OpenSSL prend en charge SCTP.
-sctp_label_bug
Utilise le comportement incorrect des anciennes implémentations OpenSSL lors du calcul des secrets partagés d'une paire de points d'extrémité pour DTLS/SCTP. Cela permet la communication avec d'anciennes implémentations défectueuses mais brise l'interopérabilité avec des implémentations correctes. Doit être utilisé conjointement avec -sctp. Cette option n'est disponible que là où OpenSSL prend en charge SCTP.
-fallback_scsv
Envoie TLS_FALLBACK_SCSV dans le ClientHello.
-async
Active le mode asynchrone. Les opérations cryptographiques seront effectuées de manière asynchrone. Cela n'aura d'effet que si un moteur capable d'asynchronisme est également utilisé via l'option -engine. À des fins de test, le moteur asynchrone factice (dasync) peut être utilisé (si disponible).
-maxfraglen len
Active la négociation de la longueur maximale des fragments ; les valeurs autorisées sont 512, 1024, 2048 et 4096.
-max_send_frag int
La taille maximale du fragment de données à envoyer. Voir SSL_CTX_set_max_send_fragment(3) pour plus d'informations.
-split_send_frag int
La taille utilisée pour diviser les données pour les pipelines de chiffrement. Si plus de données sont écrites en une seule fois que cette valeur, elles seront divisées en plusieurs pipelines, jusqu'au nombre maximum de pipelines défini par max_pipelines. Cela n'a d'effet que si une suite de chiffrement appropriée a été négociée, qu'un moteur prenant en charge le pipelining a été chargé et que max_pipelines est supérieur à 1. Voir SSL_CTX_set_split_send_fragment(3) pour plus d'informations.
-max_pipelines int
Le nombre maximum de pipelines de chiffrement/déchiffrement à utiliser. Cela n'aura d'effet que si un moteur a été chargé qui prend en charge le pipelining (par exemple, le moteur dasync) et qu'une suite de chiffrement appropriée a été négociée. La valeur par défaut est 1. Voir SSL_CTX_set_max_pipelines(3) pour plus d'informations.
-read_buf int
La taille du tampon de lecture par défaut à utiliser pour les connexions. Cela n'aura d'effet que si la taille du tampon est supérieure à la taille qui serait autrement utilisée et que le pipelining est en cours d'utilisation (voir SSL_CTX_set_default_read_buffer_len(3) pour plus d'informations.
-ignore_unexpected_eof
Certaines implémentations TLS n'envoient pas l'alerte close_notify obligatoire lors de la fermeture. Si l'application essaie d'attendre l'alerte close_notify mais que le pair ferme la connexion sans l'envoyer, une erreur est générée. Lorsque cette option est activée, le pair n'a pas besoin d'envoyer l'alerte close_notify et une connexion fermée sera traitée comme si l'alerte close_notify avait été reçue. Pour plus d'informations sur la fermeture d'une connexion, voir SSL_shutdown(3).
-no_tx_cert_comp
Désactive la prise en charge de l'envoi de certificats compressés TLSv1.3.
-no_rx_cert_comp
Désactive la prise en charge de la réception de certificats compressés TLSv1.3.
-brief
Ne fournit qu'un bref résumé des paramètres de connexion au lieu de la sortie détaillée normale.
-starttls protocole
Envoie le(s) message(s) spécifique(s) au protocole pour passer à TLS pour la communication. protocole est un mot-clé pour le protocole visé. Actuellement, les seuls mots-clés pris en charge sont "smtp", "pop3", "imap", "ftp", "xmpp", "xmpp-server", "irc", "postgres", "mysql", "lmtp", "nntp", "sieve" et "ldap".
-xmpphost nom_hote
Cette option, lorsqu'elle est utilisée avec "-starttls xmpp" ou "-starttls xmpp-server", spécifie l'hôte pour l'attribut "to" de l'élément stream. Si cette option n'est pas spécifiée, l'hôte spécifié avec "-connect" sera utilisé.

Cette option est un alias de l'option -name pour "xmpp" et "xmpp-server".

-name nom_hote
Cette option est utilisée pour spécifier des informations de nom d'hôte pour divers protocoles utilisés avec l'option -starttls. Actuellement, seuls "xmpp", "xmpp-server", "smtp" et "lmtp" peuvent utiliser cette option -name.

Si cette option est utilisée avec "-starttls xmpp" ou "-starttls xmpp-server", elle spécifie l'hôte pour l'attribut "to" de l'élément stream. Si cette option n'est pas spécifiée, alors l'hôte spécifié avec "-connect" sera utilisé.

Si cette option est utilisée avec "-starttls lmtp" ou "-starttls smtp", elle spécifie le nom à utiliser dans le message "LMTP LHLO" ou "SMTP EHLO", respectivement. Si cette option n'est pas spécifiée, alors "mail.example.com" sera utilisé.

-tlsextdebug
Affiche un vidage hexadécimal de toutes les extensions TLS reçues du serveur.
-sess_out nom_fichier
Sortie de la session SSL vers nom_fichier.
-sess_in nom_fichier
Charge la session SSL depuis nom_fichier. Le client tentera de reprendre une connexion à partir de cette session.
-serverinfo types
Une liste de types d'extensions TLS séparés par des virgules (nombres entre 0 et 65535). Chaque type sera envoyé comme une extension TLS ClientHello vide. La réponse du serveur (le cas échéant) sera encodée et affichée sous forme de fichier PEM.
-status
Envoie une requête de statut de certificat au serveur (agrafage OCSP). La réponse du serveur (le cas échéant) est affichée.
-ocsp_check_leaf
Exige la vérification du statut du certificat serveur (entité finale), où toute réponse OCSP fournie lors de l'établissement de la connexion TLS (par le biais de l'« agrafage OCSP ») est essayée en premier. Si aucune réponse OCSP valide et concluante ne peut être trouvée, la vérification basée sur CRL est tentée en dernier recours si elle est activée, sinon la vérification du statut échoue.

Cela implique -status.

-ocsp_check_all
Comme l'option précédente, mais exige la vérification du statut du certificat également pour la chaîne d'émetteurs du certificat serveur (c'est-à-dire les certificats d'autorité de certification intermédiaires, à l'exclusion de l'ancre de confiance).

Cela implique -status et -ocsp_check_leaf.

-alpn protocoles, -nextprotoneg protocoles
Ces indicateurs activent respectivement l'extension de négociation de protocole au niveau applicatif (ALPN) ou de négociation de protocole suivant (NPN). ALPN est la norme IETF et remplace NPN. La liste protocoles est une liste de noms de protocoles séparés par des virgules que le client doit annoncer supporter. La liste doit contenir les protocoles les plus désirables en premier. Les noms de protocoles sont des chaînes ASCII imprimables, par exemple "http/1.1" ou "spdy/3". Une liste vide de protocoles est traitée spécialement et entraînera l'annonce par le client de son support pour l'extension TLS, mais il se déconnectera juste après avoir reçu ServerHello avec une liste de protocoles supportés par le serveur. L'indicateur -nextprotoneg ne peut pas être spécifié si -tls1_3 est utilisé.
-ct, -noct
Utilisez l'une de ces deux options pour contrôler si la Transparence des Certificats (CT) est activée (-ct) ou désactivée (-noct). Si CT est activée, les horodatages de certificats signés (SCT) seront demandés au serveur et rapportés à la fin de l'établissement de la connexion.

L'activation de CT active également l'agrafage OCSP, car c'est une méthode de livraison possible pour les SCT.

COMMANDES CONNECTÉES (BASIQUE)

Si une connexion est établie avec un serveur SSL/TLS, toutes les données reçues du serveur sont affichées et toutes les frappes au clavier sont envoyées au serveur. Si la fin du fichier est atteinte, la connexion sera fermée.

Lorsqu'il est utilisé de manière interactive (ce qui signifie que ni -quiet ni -ign_eof n'ont été donnés), et qu'aucun des options -adv ou -nocommands n'est donné, le mode de commande "Basique" est entré. Dans ce mode, certains commandes sont reconnues et effectuent des opérations spéciales. Ces commandes sont une lettre qui doit apparaître au début d'une ligne. Toutes les données suivantes après la lettre initiale sur la ligne sont ignorées. Les commandes sont listées ci-dessous.

Q
Termine la connexion SSL actuelle et quitte.
R
Renégocie la session SSL (TLSv1.2 et versions inférieures uniquement).
C
Tente de se reconnecter au serveur en utilisant une poignée de main de reprise.
k
Envoie un message de mise à jour des clés au serveur (TLSv1.3 uniquement)
K
Envoie un message de mise à jour des clés au serveur et en demande un en retour (TLSv1.3 uniquement)

COMMANDES CONNECTÉES (AVANCÉES)

Si -adv a été donné, le mode de commande "avancé" est entré. Comme en mode basique, si une connexion est établie avec un serveur SSL/TLS, toutes les données reçues du serveur sont affichées et toutes les frappes au clavier sont envoyées au serveur. Si la fin du fichier est atteinte, la connexion sera fermée.

Des commandes spéciales peuvent être fournies en les plaçant entre accolades, par exemple "{help}" ou "{quit}". Ces commandes peuvent apparaître n'importe où dans le texte saisi dans s_client, mais elles ne sont pas envoyées au serveur. Certaines commandes peuvent accepter un argument en terminant le nom de la commande par ":" et en fournissant ensuite l'argument, par exemple "{keyup:req}". Certaines commandes ne sont disponibles que lorsque certaines versions de protocole ont été négociées.

Si un saut de ligne apparaît à la fin d'une ligne saisie dans s_client, celui-ci est également envoyé au serveur. Si une commande apparaît seule sur une ligne, sans autre texte sur la même ligne, le saut de ligne est supprimé et n'est pas envoyé au serveur.

Les commandes suivantes sont reconnues.

help
Affiche un résumé d'aide sur les commandes disponibles.
quit
Ferme la connexion avec le pair.
reconnect
Reconnecte avec le pair et tente une poignée de main de reprise.
keyup
Envoie un message de mise à jour des clés. TLSv1.3 uniquement. Cette commande accepte un argument facultatif. Si l'argument "req" est fourni, le pair est également invité à mettre à jour ses clés. Sinon, si "noreq" est fourni, le pair n'est pas invité à mettre à jour ses clés. La valeur par défaut est "req".
reneg
Initie une renégociation avec le serveur. (D)TLSv1.2 ou inférieur uniquement.
fin
Indique FIN sur le flux actuel. QUIC uniquement. Une fois FIN envoyé, tout texte supplémentaire entré pour ce flux est ignoré.

NOTES

Cette commande peut être utilisée pour déboguer des serveurs SSL. Pour se connecter à un serveur SSL HTTP, la commande :

openssl s_client -connect nom_serveur:443

serait typiquement utilisée (https utilise le port 443). Si la connexion réussit, une commande HTTP peut être donnée comme "GET /" pour récupérer une page Web.

Si la poignée de main échoue, plusieurs causes sont possibles. Si ce n'est rien d'évident comme l'absence de certificat client, les options -bugs, -ssl3, -tls1, -no_ssl3, -no_tls1 peuvent être essayées au cas où il s'agirait d'un serveur bogué. En particulier, vous devriez jouer avec ces options avant de soumettre un rapport de bug à une liste de diffusion OpenSSL.

Un problème fréquent lors de la tentative de faire fonctionner les certificats clients est qu'un client Web se plaint de ne pas avoir de certificats ou donne une liste vide à choisir. C'est normalement parce que le serveur n'envoie pas son autorité de certification cliente dans sa "liste de CA acceptables" lorsqu'il demande un certificat. En utilisant cette commande, la liste des CA peut être visualisée et vérifiée. Cependant, certains serveurs ne demandent l'authentification du client qu'après qu'une URL spécifique a été demandée. Pour obtenir la liste dans ce cas, il est nécessaire d'utiliser l'option -prexit et d'envoyer une requête HTTP pour une page appropriée.

Si un certificat est spécifié sur la ligne de commande à l'aide de l'option -cert, il ne sera pas utilisé à moins que le serveur ne demande spécifiquement un certificat client. Par conséquent, le simple fait d'inclure un certificat client sur la ligne de commande ne garantit pas que le certificat fonctionne.

S'il y a des problèmes pour vérifier un certificat serveur, l'option -showcerts peut être utilisée pour afficher tous les certificats envoyés par le serveur.

Cette commande est un outil de test et est conçue pour poursuivre la poignée de main après toute erreur de vérification de certificat. Par conséquent, elle acceptera toute chaîne de certificats (approuvée ou non) envoyée par le pair. Les applications non-test ne devraient pas faire cela car cela les rend vulnérables à une attaque MITM. Ce comportement peut être modifié avec l'option -verify_return_error : toute erreur de vérification est alors renvoyée, abortant la poignée de main.

L'option -bind peut être utile si le serveur ou un pare-feu exige que les connexions proviennent d'une adresse et/ou d'un port particulier.

Note sur l'utilisation non interactive

Lorsque s_client est exécuté dans un environnement non interactif (par exemple, un cron job ou un script sans stdin valide), il peut fermer la connexion prématurément, en particulier avec TLS 1.3. Pour éviter cela, vous pouvez utiliser l'indicateur -ign_eof, qui maintient s_client en cours d'exécution même après avoir atteint la fin du fichier depuis stdin.

Par exemple :

openssl s_client -connect <adresse_serveur>:443 -tls1_3
                 -sess_out /chemin/vers/fichier_parametres_session_tls
                 -ign_eof </dev/null

Cependant, se fier uniquement à -ign_eof peut entraîner des problèmes si le serveur maintient la connexion ouverte, s'attendant à ce que le client se ferme en premier. Dans de tels cas, le client peut rester bloqué indéfiniment. Ce comportement n'est pas rare, en particulier avec les protocoles où le serveur attend une déconnexion gracieuse du client.

Par exemple, lors de la connexion à un serveur SMTP, la session peut faire une pause si le serveur attend une commande QUIT avant de se fermer :

$ openssl s_client -brief -ign_eof -starttls smtp
                   -connect <adresse_serveur>:25 </dev/null
CONNEXION ÉTABLIE
Version du protocole : TLSv1.3
Suite de chiffrement : TLS_AES_256_GCM_SHA384
...
250 CHUNKING
[longue pause]

Pour éviter de tels blocages, il est préférable d'utiliser une commande au niveau de l'application pour initier une déconnexion propre. Pour SMTP, vous pouvez envoyer une commande QUIT :

printf 'QUIT\r\n' | openssl s_client -connect <adresse_serveur>:25
                                     -starttls smtp -brief -ign_eof

De même, pour les connexions HTTP/1.1, l'inclusion d'un en-tête `Connection: close` garantit que le serveur ferme la connexion après avoir répondu :

printf 'GET / HTTP/1.1\r\nHost: <adresse_serveur>\r\nConnection: close\r\n\r\n'
    | openssl s_client -connect <adresse_serveur>:443 -brief

Ces approches aident à gérer la fermeture de la connexion de manière gracieuse et à éviter les blocages causés par le serveur qui attend que le client initie la déconnexion.

BOGUES

Parce que ce programme a beaucoup d'options et parce que certaines des techniques utilisées sont plutôt anciennes, le code source C de cette commande est plutôt difficile à lire et n'est pas un modèle de la façon dont les choses devraient être faites. Un programme client SSL typique serait beaucoup plus simple.

L'option -prexit est un peu une rustine. Nous devrions en fait signaler les informations chaque fois qu'une session est renégociée.
