outlook.pst - format du fichier .pst de MS Outlook

SYNOPSIS

outlook.pst

APERÇU

Les éléments de bas niveau ou primitifs d'un fichier .pst sont identifiés par une valeur I_ID. Les éléments de haut niveau ou composites d'un fichier .pst sont identifiés par une valeur D_ID. Il existe deux arbres b distincts indexés par ces valeurs I_ID et D_ID. À partir d'Outlook 2003, le format de fichier a changé, passant de pointeurs 32 bits à des pointeurs 64 bits. Nous décrivons les deux formats ici.

Nous ne prenons en charge que les types d'index 0x0e, 0x0f, 0x15 et 0x17, et les types de chiffrement 0x00, 0x01 et 0x02. Le type d'index 0x0e est l'ancien format Outlook 32 bits. Le type d'index 0x0f semble rare, et jusqu'à présent les données semblent identiques à celles des fichiers de type 0x0e. Le type d'index 0x17 est le nouveau format Outlook 64 bits. Le type d'index 0x15 semble rare, et selon le projet libpff, il devrait avoir le même format que les fichiers de type 0x17. Il a été trouvé dans un fichier pst 64 bits créé par Visual Recovery. Il se peut que les types d'index inférieurs à 0x10 soient en 32 bits, et que les types d'index supérieurs ou égaux à 0x10 soient en 64 bits, et que les quatre bits de poids faible du type d'index représentent un sous-type ou un numéro de version mineure.

Le type de chiffrement 0x00 est sans chiffrement, le type 0x01 est un chiffrement "compressible" qui est un simple chiffre de substitution, et le type 0x02 est un chiffrement "fort", qui est un simple chiffre Enigma à trois rotors de la Seconde Guerre mondiale.

offsetIndex1 est le décalage dans le fichier de la racine de l'arbre b index1, qui contient des tuples (I_ID, offset, size, unknown) pour chaque élément dans le fichier. backPointer1 est la valeur qui devrait apparaître dans le pointeur parent de ce nœud racine.

offsetIndex2 est le décalage dans le fichier de la racine de l'arbre b index2, qui contient des tuples (D_ID, DESC-I_ID, TREE-I_ID, PARENT-D_ID) pour chaque élément dans le fichier. backPointer2 est la valeur qui devrait apparaître dans le pointeur parent de ce nœud racine.

Notez la signature de 0x7cec. Il existe d'autres formats de blocs descripteurs avec d'autres signatures. Notez l'indexOffset de 0x017a - en commençant à cette position dans le bloc descripteur, nous avons un tableau d'entiers de deux octets. Le premier entier (0x0006) est un (compte-1) du nombre de paires superposées suivant le compte. La première paire est (0, 0xc), la paire suivante est (0xc, 0x14) et la dernière (7ème) paire est (0x160, 0x179). Ces paires sont les décalages (début, fin+1) des éléments de ce bloc. Nous avons donc count+2 entiers après la valeur du compte.

Notez le 7coffset de 0x0040, qui est une référence d'index. Dans ce cas, il s'agit d'un pointeur de référence interne, qui doit être décalé vers la droite de 4 bits pour devenir 0x0004, ce qui est alors un décalage d'octet à ajouter à l'indexOffset ci-dessus plus deux (pour ignorer le compte), il pointe donc vers la paire (0x14, 0xea). 0014  unknown         [2 octets] 0x0000     dans ce cas

Notez le b5Offset de 0x0020, qui est une référence d'index. Dans ce cas, il s'agit d'un pointeur de référence interne, qui doit être décalé vers la droite de 4 bits pour devenir 0x0002, ce qui est alors un décalage d'octet à ajouter à l'indexOffset ci-dessus plus deux (pour ignorer le compte), il pointe donc vers la paire (0xc, 0x14). Enfin, nous avons le décalage et la taille du bloc « b5 » situé au décalage 0xc avec une taille de 8 octets dans ce bloc descripteur. Le bloc « b5 » a le format suivant :

0000  signature       [2 octets] 0x04b5     constant
0002  datasize        [2 octets] 0x0002     +4 pour les entrées de 6 octets dans ce cas
0004  descoffset      [4 octets] 0x0060     référence d'index

Notez le descoffset de 0x0060, qui est à nouveau une référence d'index. Dans ce cas, il s'agit d'un pointeur de référence interne, qui doit être décalé vers la droite de 4 bits pour devenir 0x0006, ce qui est alors un décalage d'octet à ajouter à l'indexOffset ci-dessus plus deux (pour ignorer le compte), il pointe donc vers la paire (0xea, 0xf0). La datasize (2) plus le code b5 (04) donne la taille des entrées, dans ce cas 6 octets. Nous avons maintenant le décalage 0xea d'un bloc de données inutilisé dans un format inconnu, composé d'entrées de 6 octets. Cela nous donne (0xf0 - 0xea)/6 = 1, donc nous avons un recordCount de un.

Nous avons vu des cas où le descoffset dans le bloc b5 est zéro, et l'index2Offset dans le bloc 7c est zéro. Cela a été vu pour des objets qui semblent être des pièces jointes à des messages qui ont été lus. Avant que le message ne soit lu, il n'avait pas de pièces jointes.

Notez l'index2Offset ci-dessus de 0x0080, qui est à nouveau une référence d'index. Dans ce cas, il s'agit d'un pointeur de référence interne, qui doit être décalé vers la droite de 4 bits pour devenir 0x0008, ce qui est alors un décalage d'octet à ajouter à l'indexOffset ci-dessus plus deux (pour ignorer le compte), il pointe donc vers la paire (0xf0, 0x155). Il s'agit d'un tableau de tables d'entiers de quatre octets. Nous les appellerons les tables IND2. La taille de chacune de ces tables est spécifiée par le champ recordSize de l'en-tête « 7c ». Le nombre de ces tables est la valeur recordCount dérivée du bloc « b5 ».

Maintenant, les données restantes dans le bloc « 7c » après l'en-tête commencent au décalage 0x2a. Il devrait y avoir itemCount éléments de 8 octets ici, avec le format suivant :

0000  referenceType   [2 octets]
0002  itemType        [2 octets]
0004  ind2Offset      [2 octets]
0006  size            [1 octet]
0007  unknown         [1 octet]

L'ind2Offset est un décalage d'octet dans la table IND2 actuelle d'une certaine valeur. Si cette valeur est un entier de quatre octets, alors une fois que nous l'avons récupérée, nous avons le même triple (type d'élément, type de référence, valeur) que celui que l'on trouve dans les blocs descripteurs de style 0xbcec. Sinon, cette valeur est utilisée directement. Ces descripteurs de 8 octets sont traités recordCount fois, en utilisant à chaque fois la table IND2 suivante. Les types d'élément et de référence sont tels que décrits ci-dessus pour le bloc descripteur au format 0xbcec.

DESCripteur ASSOCIÉ 32 bits ITEM 0X0101

Ce bloc descripteur contient une liste de valeurs I_ID. Il est utilisé lorsqu'un I_ID (qui pointerait normalement vers un bloc descripteur de type 0x7cec ou 0xbcec) contient plus de données qu'il n'en tient dans un seul descripteur de ces types.
