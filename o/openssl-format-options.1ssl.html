NOM

openssl-format-options - Options d'entrée et de sortie des formats de la commande OpenSSL

SYNTAXE

openssl commande [ options ... ] [ paramètres ... ]

DESCRIPTION

Plusieurs commandes OpenSSL peuvent prendre des entrées ou générer des sorties dans une variété de formats.

Depuis OpenSSL 3.0, les clés, les certificats uniques et les CRL peuvent être lus à partir de fichiers dans n'importe lequel des formats DER, PEM ou P12. Il n'est plus nécessaire de spécifier leur format d'entrée et les commandes openssl essaieront automatiquement tous les formats possibles. Cependant, si le format d'entrée DER ou PEM est spécifié, il sera appliqué.

Afin d'accéder à une clé via un moteur, le format d'entrée ENGINE peut être utilisé ; alternativement, l'identifiant de la clé dans l'argument <uri> de l'option de clé respective peut être précédé de "org.openssl.engine:". Voir "Engine Options" dans openssl(1) pour un exemple d'utilisation de ce dernier.

OPTIONS

Options de format

Les options pour spécifier le format sont les suivantes. Reportez-vous à la page de manuel individuelle pour voir quelles options sont acceptées.

-inform format, -outform format
Le format des flux d'entrée ou de sortie.
-keyform format
Format d'une source d'entrée de clé privée.
-CRLform format
Format d'une source d'entrée de CRL.

Arguments d'option de format

Les arguments de format possibles sont décrits ci-dessous. Les majuscules et les minuscules sont acceptées.

La liste des arguments de format acceptables, ainsi que le défaut, est décrite dans la documentation de chaque commande.

DER
Un format binaire, encodé ou analysé selon les Distinguished Encoding Rules (DER) du langage de données ASN.1.
ENGINE
Utilisé pour spécifier que le matériel cryptographique se trouve dans un moteur OpenSSL. Un moteur doit être configuré ou spécifié en utilisant l'option -engine. Un mot de passe ou un code PIN peut être fourni au moteur en utilisant l'option -passin.
P12
Un fichier encodé DER contenant un objet PKCS#12. Il peut être nécessaire de fournir un mot de passe de déchiffrement pour récupérer la clé privée.
PEM
Un format texte défini dans les RFC 1421 et RFC 7468 de l'IETF. En bref, c'est un bloc d'encodage base-64 (défini dans la RFC 4648 de l'IETF), avec des lignes spécifiques utilisées pour marquer le début et la fin : 
Le texte avant la ligne BEGIN est ignoré.
----- BEGIN object-type -----
OT43gQKBgQC/2OHZoko6iRlNOAQ/tMVFNq7fL81GivoQ9F1U0Qr+DH3ZfaH8eIkX
xT0ToMPJUzWAn8pZv0snA0um6SIgvkCuxO84OkANCVbttzXImIsL7pFzfcwV/ERK
UM6j0ZuSMFOCr/lGPAoOQU0fskidGEHi1/kW+suSr28TqsyYZpwBDQ==
----- END object-type -----
Le texte après la ligne END est également ignoré

Le type_objet doit correspondre au type d'objet attendu. Par exemple, une "BEGIN X509 CERTIFICATE" ne correspondra pas si la commande essaie de lire une clé privée. Les types pris en charge incluent :

ANY PRIVATE KEY
CERTIFICATE
CERTIFICATE REQUEST
CMS
DH PARAMETERS
DSA PARAMETERS
DSA PUBLIC KEY
EC PARAMETERS
EC PRIVATE KEY
ECDSA PUBLIC KEY
ENCRYPTED PRIVATE KEY
PARAMETERS
PKCS #7 SIGNED DATA
PKCS7
PRIVATE KEY
PUBLIC KEY
RSA PRIVATE KEY
SSL SESSION PARAMETERS
TRUSTED CERTIFICATE
X509 CRL
X9.42 DH PARAMETERS

Les types_objet hérités suivants sont également pris en charge pour assurer la compatibilité avec les versions antérieures :

DSA PRIVATE KEY
NEW CERTIFICATE REQUEST
RSA PUBLIC KEY
X509 CERTIFICATE
SMIME
Un objet S/MIME tel que décrit dans la RFC 8551 de l'IETF. Les versions antérieures étaient connues sous le nom de CMS et sont compatibles. Notez que l'analyse est simple et pourrait ne pas analyser certaines données valides.
