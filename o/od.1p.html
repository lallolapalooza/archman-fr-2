OD(1P) Manuel du programmeur POSIX OD(1P)

PROLOGUE

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consultez la page de manuel Linux correspondante pour les détails du comportement Linux), ou l'interface peut ne pas être implémentée sur Linux.

NOM

od — vidange de fichiers dans divers formats

SYNOPIS

od [-v] [-A base_adresse] [-j saut] [-N compte] [-t chaîne_type]...
    [fichier...]
od [-bcdosx] [fichier] [[+]décalage[.][b]]

DESCRIPTION

L'utilitaire od écrira le contenu de ses fichiers d'entrée sur la sortie standard dans un format spécifié par l'utilisateur.

OPTIONS

L'utilitaire od sera conforme au volume Définitions de base de POSIX.1‐2017, Section 12.2, Directives de syntaxe des utilitaires, à l'exception de l'ordre de présentation des options -t et des options -bcdosx qui est significatif.

Les options suivantes seront prises en charge :

-A base_adresse

Spécifie la base de l'adresse d'entrée. Voir la section DESCRIPTION ÉTENDUE. L'application devra s'assurer que l'argument d'option base_adresse est un caractère. Les caractères 'd', 'o' et 'x' spécifient que la base de l'adresse sera écrite en décimal, octal ou hexadécimal, respectivement. Le caractère 'n' spécifie que l'adresse ne sera pas écrite.
-b
Interprète les octets en octal. Cela sera équivalent à -t o1.
-c
Interprète les octets comme des caractères spécifiés par le réglage actuel de la catégorie LC_CTYPE. Certains caractères non graphiques apparaissent comme des échappements C : "NUL=\0", "BS=\b", "FF=\f", "NL=\n", "CR=\r", "HT=\t" ; d'autres apparaissent comme des nombres octaux à 3 chiffres.
-d
Interprète les mots (unités de deux octets) en décimal non signé. Cela sera équivalent à -t u2.
-j saut
Saute saut octets depuis le début de l'entrée. L'utilitaire od lira ou se déplacera au-delà des premiers saut octets dans les fichiers d'entrée concaténés. Si l'entrée combinée n'est pas d'au moins saut octets, l'utilitaire od écrira un message de diagnostic sur la sortie d'erreur standard et se terminera avec un statut de sortie non nul.

Par défaut, l'argument d'option saut sera interprété comme un nombre décimal. Avec un préfixe 0x ou 0X, l'adresse sera interprétée comme un nombre hexadécimal ; sinon, avec un préfixe '0', l'adresse sera interprétée comme un nombre octal. L'ajout du caractère 'b', 'k' ou 'm' à l'adresse provoquera son interprétation comme un multiple de 512, 1024 ou 1048576 octets, respectivement. Si le nombre saut est hexadécimal, tout 'b' ajouté sera considéré comme le dernier chiffre hexadécimal.

-N compte
Formate au plus compte octets d'entrée. Par défaut, compte sera interprété comme un nombre décimal. Avec un préfixe 0x ou 0X, compte sera interprété comme un nombre hexadécimal ; sinon, avec un préfixe '0', il sera interprété comme un nombre octal. Si compte octets d'entrée (après avoir sauté avec succès, si -j saut est spécifié) ne sont pas disponibles, cela ne sera pas considéré comme une erreur ; l'utilitaire od formatera l'entrée disponible.
-o
Interprète les mots (unités de deux octets) en octal. Cela sera équivalent à -t o2.
-s
Interprète les mots (unités de deux octets) en décimal signé. Cela sera équivalent à -t d2.
-t chaîne_type

Spécifie un ou plusieurs types de sortie. Voir la section DESCRIPTION ÉTENDUE. L'application devra s'assurer que l'argument d'option chaîne_type est une chaîne spécifiant les types à utiliser lors de l'écriture des données d'entrée. La chaîne sera composée des caractères de spécification de type a, c, d, f, o, u et x, spécifiant respectivement caractère nommé, caractère, décimal signé, virgule flottante, octal, décimal non signé et hexadécimal. Les caractères de spécification de type d, f, o, u et x peuvent être suivis d'un entier décimal non signé optionnel qui spécifie le nombre d'octets à transformer par chaque instance du type de sortie. Le caractère de spécification de type f peut être suivi d'un F, D ou L optionnel indiquant que la conversion doit être appliquée à un élément de type float, double ou long double, respectivement. Les caractères de spécification de type d, o, u et x peuvent être suivis d'un C, S, I ou L optionnel indiquant que la conversion doit être appliquée à un élément de type char, short, int ou long, respectivement. Plusieurs types peuvent être concaténés dans la même chaîne_type et plusieurs options -t peuvent être spécifiées. Les lignes de sortie seront écrites pour chaque type spécifié dans l'ordre où les caractères de spécification de type sont spécifiés.
-v
Écrit toutes les données d'entrée. Sans l'option -v, tout nombre de groupes de lignes de sortie, qui seraient identiques au groupe de lignes de sortie immédiatement précédent (sauf pour les adresses d'octets), sera remplacé par une ligne contenant uniquement un <astérisque> ('*').
-x
Interprète les mots (unités de deux octets) en hexadécimal. Cela sera équivalent à -t x2.

Plusieurs types peuvent être spécifiés en utilisant plusieurs options -bcdostx. Les lignes de sortie sont écrites pour chaque type spécifié dans l'ordre où les types sont spécifiés.

OPÉRANDES

Les opérandes suivants seront pris en charge :

fichier
Un nom de chemin d'un fichier à lire. Si aucun opérande fichier n'est spécifié, la sortie standard sera utilisée.

S'il n'y a pas plus de deux opérandes, aucune des options -A, -j, -N, -t ou -v n'est spécifiée, et si l'une des conditions suivantes est vraie : le premier caractère du dernier opérande est un <signe plus> ('+'), ou il y a deux opérandes et le premier caractère du dernier opérande est numérique ; le dernier opérande sera interprété comme un opérande de décalage sur les systèmes conformes XSI. Dans ces conditions, les résultats ne sont pas spécifiés sur les systèmes qui ne sont pas conformes XSI.

[+]décalage[.][b]
L'opérande décalage spécifie le décalage dans le fichier où la vidange doit commencer. Cet opérande est normalement interprété en octets octaux. Si '.' est ajouté, le décalage sera interprété en décimal. Si 'b' est ajouté, le décalage sera interprété en unités de 512 octets.

STDIN

La sortie standard sera utilisée si aucun opérande fichier n'est spécifié, et sera utilisée si un opérande fichier est '-' et que l'implémentation traite le '-' comme signifiant la sortie standard. Sinon, la sortie standard ne sera pas utilisée. Voir la section FICHIERS D'ENTRÉE.

FICHIERS D'ENTRÉE

Les fichiers d'entrée peuvent être de n'importe quel type.

VARIABLES D'ENVIRONNEMENT

Les variables d'environnement suivantes affecteront l'exécution de od :

LANG
Fournir une valeur par défaut pour les catégories suivantes : LC_ADDRESS, LC_CTYPE, LC_MESSAGES, LC_NUMERIC.
LC_ALL
Sans effet.
LC_CTYPE
Déterminer le comportement des caractères spécifiés par la catégorie LC_CTYPE lors de l'utilisation de l'option -c.
LC_MESSAGES
Déterminer l'écriture des messages de diagnostic et des messages de suivi qui seront écrits sur la sortie d'erreur standard.
NLSPATH
Déterminer l'emplacement des fichiers de messages pour le traitement de LC_MESSAGES.

STATUT DE SORTIE

Les effets de la sortie normale de od seront les suivants :

0
Aucune erreur ne s'est produite.
1
Une erreur s'est produite lors de la lecture d'un fichier ou du traitement des options.

DESCRIPTION ÉTENDUE

L'utilitaire od copiera séquentiellement chaque fichier d'entrée vers la sortie standard, en transformant les données d'entrée conformément aux types de sortie spécifiés par l'option -t ou les options -bcdosx. Si aucun type de sortie n'est spécifié, la sortie par défaut sera comme si -t oS avait été spécifié.

Le nombre d'octets transformés par le spécificateur de type de sortie c peut varier en fonction de la catégorie LC_CTYPE.

Le nombre d'octets par défaut transformés par les spécificateurs de type d, f, o, u et x correspond aux différents types du langage C comme suit. Si le compilateur c99 est présent sur le système, ces spécificateurs correspondront aux tailles utilisées par défaut dans ce compilateur. Sinon, ces tailles peuvent varier entre les systèmes conformes à POSIX.1‐2008.

*
Pour les caractères spécificateurs de type d, o, u et x, le nombre d'octets par défaut correspondra à la taille du type entier de base de l'implémentation sous-jacente. Pour ces caractères spécificateurs, l'implémentation supportera les valeurs du nombre optionnel d'octets à convertir correspondant au nombre d'octets des types du langage C char, short, int et long. Ces nombres peuvent également être spécifiés par une application sous forme des caractères 'C', 'S', 'I' et 'L', respectivement. L'implémentation supportera également les valeurs 1, 2, 4 et 8, même si elle ne fournit pas de types en langage C de ces tailles. L'implémentation supportera la valeur décimale correspondant au type long long du langage C. L'ordre des octets utilisé lors de l'interprétation des valeurs numériques est défini par l'implémentation, mais correspondra à l'ordre dans lequel une constante du type correspondant est stockée en mémoire sur le système.
*
Pour le caractère spécificateur de type f, le nombre d'octets par défaut correspondra au nombre d'octets du type de données flottantes en virgule flottante double précision de base de l'implémentation sous-jacente. L'implémentation supportera les valeurs du nombre optionnel d'octets à convertir correspondant au nombre d'octets des types du langage C float, double et long double. Ces nombres peuvent également être spécifiés par une application sous forme des caractères 'F', 'D' et 'L', respectivement.

Le caractère spécificateur de type a indique que les octets doivent être interprétés comme des caractères nommés de la version de référence internationale (IRV) de la norme ISO/IEC 646:1991. Seuls les sept bits de poids faible de chaque octet doivent être utilisés pour cette spécification de type. Les octets dont les valeurs sont listées dans le tableau suivant seront écrits en utilisant les noms correspondants pour ces caractères.

Le caractère spécificateur de type c indique que les octets doivent être interprétés comme des caractères spécifiés par le réglage actuel de la catégorie de locale LC_CTYPE. Les caractères listés dans le tableau du volume des définitions de base de POSIX.1‐2017, Chapitre 5, Notation des formats de fichier ('\\', '\a', '\b', '\f', '\n', '\r', '\t', '\v') seront écrits sous forme des séquences d'échappement correspondantes, à l'exception du caractère <barre oblique inverse> qui sera écrit comme une seule <barre oblique inverse> et un caractère nul qui sera écrit comme '\0'. Les autres caractères non imprimables seront écrits sous forme d'un nombre octal à trois chiffres pour chaque octet du caractère. Les caractères multi-octets imprimables seront écrits dans la zone correspondant au premier octet du caractère ; la séquence de deux caractères "**" sera écrite dans la zone correspondant à chaque octet restant du caractère, pour indiquer que le caractère est continué. Lorsque l'option -j skip ou l'option -N count est spécifiée avec le spécificateur de type c, et que cela entraîne une tentative de démarrage ou de fin au milieu d'un caractère multi-octets, le résultat est défini par l'implémentation.

Les données d'entrée seront manipulées par blocs, un bloc étant défini comme un multiple du plus petit commun multiple du nombre d'octets transformés par les types de sortie spécifiés. Si le plus petit commun multiple est supérieur à 16, les résultats ne sont pas spécifiés. Chaque bloc d'entrée sera écrit tel que transformé par chaque type de sortie, un par ligne écrite, dans l'ordre où les types de sortie ont été spécifiés. Si la taille du bloc d'entrée est supérieure au nombre d'octets transformés par le type de sortie, le type de sortie transformera séquentiellement les parties du bloc d'entrée, et la sortie de chacune des transformations sera séparée par un ou plusieurs caractères <espace>.

Si, suite à la spécification de l'option -N ou à la fin du fichier atteinte sur le dernier fichier d'entrée, les données d'entrée ne satisfont que partiellement un type de sortie, l'entrée sera complétée avec des octets nuls suffisants pour écrire le dernier octet de l'entrée.

Sauf si -A n est spécifié, la première ligne de sortie produite pour chaque bloc d'entrée sera précédée du décalage d'entrée, cumulé sur les fichiers d'entrée, du prochain octet à écrire. Le format du décalage d'entrée n'est pas spécifié ; cependant, il ne contiendra aucun caractère <espace>, commencera au premier caractère de la ligne de sortie, et sera suivi d'un ou plusieurs caractères <espace>. De plus, le décalage de l'octet suivant le dernier octet écrit sera écrit après que toutes les données d'entrée aient été traitées, mais ne sera suivi d'aucun caractère <espace>.

Si aucune option -A n'est spécifiée, la base du décalage d'entrée n'est pas spécifiée.

STATUT DE SORTIE

Les valeurs de sortie suivantes doivent être retournées :

 0
Tous les fichiers d'entrée ont été traités avec succès.
>0
Une erreur s'est produite.

UTILISATION DES APPLICATIONS

Les applications conformes XSI sont averties de ne pas utiliser de noms de fichiers commençant par '+' ou un premier opérande commençant par un caractère numérique afin que les anciennes fonctionnalités puissent être maintenues par les implémentations, sauf si elles spécifient l'une des options -A, -j ou -N. Pour garantir que l'un de ces noms de fichiers soit toujours interprété comme un nom de fichier, une application pourrait toujours spécifier le format de base d'adresse avec l'option -A.

RATIONALE

L'utilitaire od a connu plusieurs noms dans les premières propositions, notamment hd, xd, et plus récemment hexdump. Il y a eu plusieurs objections à tous ces noms pour les raisons suivantes :

*
Les noms hd et xd entraient en conflit avec des utilitaires historiques qui se comportaient différemment.
*
La description de hexdump était beaucoup plus complexe que nécessaire pour un simple utilitaire de vidage.
*
L'utilitaire od était disponible sur toutes les implémentations historiques et il n'était pas nécessaire de créer un nouveau nom pour un utilitaire si similaire à l'utilitaire historique od.

Les raisons originales de ne pas standardiser l'historique od étaient également assez répandues. Ces raisons sont données ci-dessous, avec une justification expliquant pourquoi les développeurs du standard pensent que cette version ne souffre pas du problème indiqué :

*
Les versions BSD et System V de od ont divergé, et l'intersection des fonctionnalités fournies par les deux ne répond pas aux besoins de la communauté des utilisateurs. En fait, la version System V ne fournit qu'un mécanisme pour vider des octets octaux et des shorts, des shorts décimaux signés et non signés, des shorts hexadécimaux et des caractères ASCII. BSD a ajouté la capacité de vider des floats, des doubles, des caractères ASCII nommés, et des longs octaux, décimaux signés, décimaux non signés et hexadécimaux. La version présentée ici fournit des formes plus normalisées pour le vidage d'octets, de shorts, d'ints et de longs en octal, décimal signé, décimal non signé et hexadécimal ; float, double et long double ; et caractères ASCII nommés ainsi que caractères de la locale actuelle.
*
Il ne serait pas possible de créer un sur-ensemble compatible des drapeaux BSD et System V qui répondrait aux exigences des développeurs du standard. La sortie od par défaut historique est la sortie par défaut spécifiée de cet utilitaire. Aucune des lettres d'option choisies pour cette version de od n'entre en conflit avec aucune des options des versions historiques de od.
*
Sur les systèmes où les tailles de short, int et long diffèrent, il n'y avait aucun moyen de demander des vidages d'ints, même dans la version BSD. En raison de la manière dont les options sont nommées, l'espace de noms ne pouvait pas être étendu pour résoudre ces problèmes. C'est pourquoi l'option -t a été ajoutée (avec des spécificateurs de type plus proches des formats printf() utilisés dans le reste de ce volume de POSIX.1‐2017) et les tailles de champ optionnelles ont été ajoutées aux spécificateurs de type d, f, o, u et x. C'est aussi l'une des raisons pour lesquelles la pratique historique n'a pas été mandatée comme une forme obsolète requise de od. (Bien que les anciennes versions de od ne soient pas listées comme forme obsolète, il est conseillé aux implémentations de continuer à reconnaître les anciennes formes pendant plusieurs années encore.) Les types a, c, f, o et x correspondent au sens des caractères de format correspondants dans les implémentations historiques de od, à l'exception des tailles par défaut des champs convertis. Le format d est signé dans ce volume de POSIX.1‐2017 pour correspondre à la notation printf(). (Les versions historiques de od utilisaient d comme synonyme de u dans cette version. L'implémentation System V utilise s pour le décimal signé ; BSD utilise i pour le décimal signé et s pour les chaînes terminées par null.) À l'exception de d et u, tous les spécificateurs de type correspondent aux caractères de format de la version BSD historique de od.

Les tailles des types C char, short, int, long, float, double et long double sont utilisées, bien qu'il soit reconnu qu'il puisse y avoir zéro ou plusieurs compilateurs pour le langage C sur une implémentation et qu'ils puissent utiliser différentes tailles pour certains de ces types. (Par exemple, un compilateur pourrait utiliser des shorts de 2 octets, des ints de 2 octets et des longs de 4 octets, tandis qu'un autre compilateur (ou une option du même compilateur) utilise des shorts de 2 octets, des ints de 4 octets et des longs de 4 octets.) Néanmoins, il doit y avoir une taille de base connue par l'implémentation pour ces types, correspondant aux valeurs rapportées par les invocations de l'utilitaire getconf lorsqu'il est appelé avec les opérandes system_var {UCHAR_MAX}, {USHORT_MAX}, {UINT_MAX} et {ULONG_MAX} pour les types char, short, int et long, respectivement. Il existe des constantes similaires requises par la norme ISO C, mais non requises par le volume Interfaces système de POSIX.1‐2017 ou ce volume de POSIX.1‐2017. Ce sont {FLT_MANT_DIG}, {DBL_MANT_DIG} et {LDBL_MANT_DIG} pour les types float, double et long double, respectivement. Si l'utilitaire optionnel c99 est fourni par l'implémentation et utilisé conformément aux spécifications de ce volume de POSIX.1‐2017, ce sont les tailles qui seraient fournies. Si une option est utilisée qui spécifie des tailles différentes pour ces types, il n'y a aucune garantie que l'utilitaire od soit capable d'interpréter correctement les données binaires produites par un tel programme.

Ce volume de POSIX.1‐2017 exige que les valeurs numériques de ces longueurs soient reconnues par l'utilitaire od et que les formes symboliques soient également reconnues. Ainsi, une application conforme peut toujours examiner un tableau d'éléments de données unsigned long en utilisant od -t uL.

*
La méthode de spécification du format du champ d'adresse basée sur la spécification d'un décalage de départ dans un fichier liait inutilement les deux. L'option -A spécifie maintenant la base d'adresse et l'option -S spécifie un décalage de départ.
*
Il serait difficile de rompre la dépendance à l'US ASCII pour réaliser un utilitaire internationalisé. Il ne semble pas plus difficile pour od de vider des caractères dans la locale actuelle que pour les commandes l de ed ou sed. Le spécificateur de type c le fait sans difficulté et est entièrement compatible avec les implémentations historiques du caractère de format c lorsque la locale actuelle utilise un sur-ensemble de la norme ISO/IEC 646:1991 comme jeu de codes. Le spécificateur de type a (issu du caractère de format a de BSD) a été conservé comme moyen portable de vider l'ASCII (ou plus correctement la norme ISO/IEC 646:1991 (IRV)) afin que les en-têtes produits par pax puissent être déchiffrés même sur les systèmes qui n'utilisent pas la norme ISO/IEC 646:1991 comme sous-ensemble de leur jeu de codes de base.

L'utilisation de "**" comme indication de continuation d'un caractère multi-octets dans la sortie du spécificateur c a été choisie en observant une implémentation qui utilise cette méthode. Les octets de continuation doivent être marqués d'une manière qui ne soit pas ambiguë avec un autre caractère mono-octet ou multi-octets.

Une proposition antérieure utilisait -S et -n, respectivement, pour les options -j et -N finalement sélectionnées. Celles-ci ont été modifiées pour éviter les conflits avec les implémentations historiques.

Le standard original spécifiait -t o2 comme défaut lorsqu'aucun type de sortie

été donné. Ceci a été changé en -t oS (la longueur d'un short) pour s'adapter à une implémentation de supercalculateur qui utilisait historiquement 64 bits comme valeur par défaut (et qui définissait les shorts à 64 bits). Ce changement ne devrait pas affecter les applications conformes. L'exigence de prendre en charge les longueurs de 1, 2 et 4 a été ajoutée en même temps pour résoudre un problème d'implémentation historique qui n'avait pas de types de données de deux octets dans son compilateur C.

L'utilisation d'un type de données entier de base est destinée à permettre à l'implémentation de choisir une taille de mot couramment utilisée par les applications sur cette architecture.

Les versions antérieures de cette norme autorisaient des implémentations avec des octets autres que huit bits, mais cela a été modifié dans cette version.
