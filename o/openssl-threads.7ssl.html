NOM

openssl-threads - Aperçu de la sécurité des threads dans OpenSSL

DESCRIPTION

Dans cette page de manuel, nous utilisons le terme thread-safe pour indiquer qu'un objet ou une fonction peut être utilisé par plusieurs threads simultanément.

OpenSSL peut être compilé avec ou sans prise en charge des threads. L'utilisation la plus importante de cette prise en charge est de permettre à OpenSSL lui-même d'utiliser une API unique et cohérente, comme montré dans les "EXEMPLES" de CRYPTO_THREAD_run_once(3). Les applications multiplateformes peuvent également utiliser cette API.

En particulier, être configuré pour la prise en charge des threads n'implique pas que tous les objets OpenSSL soient thread-safe. Pour souligner : la plupart des objets ne peuvent pas être utilisés simultanément en toute sécurité. Les exceptions à cela doivent être documentées dans les pages de manuel spécifiques, et des conseils généraux de haut niveau sont donnés ici.

Une utilisation majeure de l'API de threading OpenSSL est l'implémentation du comptage de références. De nombreux objets au sein d'OpenSSL sont comptés par référence, de sorte que les ressources ne sont pas libérées tant que la dernière référence n'est pas supprimée. Les références sont souvent augmentées automatiquement (par exemple, lorsqu'un objet certificat X509 est ajouté à un magasin de confiance X509_STORE). Il existe souvent une fonction objet_up_ref() qui peut être utilisée pour augmenter le compteur de références. L'échec de faire correspondre les appels objet_up_ref() avec le bon nombre d'appels objet_free() est une source courante de fuites de mémoire lorsqu'un programme se termine.

De nombreux objets ont des API de définition et d'obtention pour définir des attributs dans l'objet. Un "set0" transmet la propriété de l'appelant à l'objet et un "get0" renvoie un pointeur mais la propriété de l'attribut reste avec l'objet et une référence à celui-ci est renvoyée. Une fonction "set1" ou "get1" ne change pas la propriété, mais met plutôt à jour le compteur de références de l'attribut de sorte que l'objet soit partagé entre l'appelant et l'objet ; l'appelant doit libérer l'attribut retourné lorsqu'il a terminé. Les fonctions qui impliquent des attributs ayant eux-mêmes des compteurs de références, mais qui sont nommées simplement avec "set" ou "get" sont historiques ; et la documentation doit indiquer comment les références sont gérées. Les méthodes d'obtention sont souvent thread-safe tant que les exigences de propriété sont satisfaites et que les objets partagés ne sont pas modifiés. Les méthodes de définition, ou la modification d'objets partagés, ne sont généralement pas thread-safe comme discuté ci-dessous.

Les objets sont thread-safe tant que les API invoquées ne modifient pas l'objet ; dans ce cas, le paramètre est généralement marqué dans l'API comme "const". Tous les paramètres ne sont pas marqués ainsi. Notez qu'une déclaration "const" ne signifie pas immuable ; par exemple, X509_cmp(3) prend des pointeurs vers des objets "const", mais l'implémentation utilise un transtypage C pour le supprimer afin de pouvoir verrouiller les objets, générer et mettre en cache un encodage DER, etc.

Une autre instance de sécurité des threads est lorsque les mises à jour de l'état interne d'un objet, telles que les valeurs mises en cache, sont effectuées avec des verrous. Un exemple de ceci est l'API de comptage de références décrite ci-dessus.

Dans tous les cas, cependant, il n'est généralement pas sûr qu'un thread mute un objet, tel que la définition d'éléments d'une clé privée ou publique, pendant qu'un autre thread utilise cet objet, tel que la vérification d'une signature.

Les mêmes API peuvent généralement être utilisées simultanément sur différents objets sans interférence. Par exemple, deux threads peuvent calculer une signature en utilisant deux objets EVP_PKEY_CTX différents.

Pour l'état global implicite ou les singletons, la sécurité des threads dépend de la facilité. Les API CRYPTO_secure_malloc(3) et connexes ont leur propre verrou, tandis que CRYPTO_malloc(3) suppose que l'allocation sous-jacente de la plateforme effectuera tout verrouillage nécessaire. Certaines API, telles que NCONF_load(3) et connexes, ne font aucun verrouillage du tout ; cela peut être considéré comme un bug.

Une question distincte, bien que connexe, est la modification des objets "fabriques" lorsque d'autres objets ont été créés à partir de ceux-ci. Par exemple, un objet SSL_CTX créé par SSL_CTX_new(3) est utilisé pour créer des objets SSL par connexion en appelant SSL_new(3). Dans ce cas précis, et probablement pour les méthodes de fabrique en général, il n'est pas sûr de modifier l'objet fabrique après qu'il ait été utilisé pour créer d'autres objets.
