NOM

ovdb - méthode de stockage de l'aperçu pour INN

DESCRIPTION

L'aperçu ovdb est une méthode de stockage qui utilise la bibliothèque Berkeley DB pour stocker les données de l'aperçu. Elle nécessite la version 4.4 ou ultérieure de la bibliothèque Berkeley DB (4.7+ est recommandé car les versions plus anciennes souffrent de divers problèmes).

La méthode d'aperçu ovdb utilise pleinement les fonctionnalités de transaction/journalisation/verrouillage de l'environnement Berkeley DB. Berkeley DB peut être téléchargé depuis https://www.oracle.com/database/technologies/related/berkeleydb.html et est nécessaire pour construire le backend ovdb.

Cette méthode est accompagnée d'un utilitaire de support qui permet la manipulation des informations d'aperçu. Voir ovdb_stat(8) pour plus de détails.

MISE À NIVEAU

Il existe plusieurs versions de la méthode de stockage ovdb :

  • Version 1, la version initiale livrée avec INN 2.3.0 jusqu'à INN 2.3.5.
  • Version 2, avec des performances améliorées, depuis INN 2.4.0.
  • Version 3, correspondant à la version 2 avec compression activée, à partir de INN 2.5.0.

Si vous avez une base de données créée avec une version précédente d'ovdb, votre base de données devra être mise à niveau à l'aide de ovdb_init. Voir la page de manuel ovdb_init(8) pour les instructions de mise à niveau, ainsi que la section "COMPRESSION" ci-dessous.

Notez que lorsque la bibliothèque Berkeley DB est mise à jour vers une nouvelle version, la base de données ovdb doit également être mise à niveau.

INSTALLATION

Si la bibliothèque Berkeley DB est trouvée au moment de la configuration, INN sera compilé avec le support Berkeley DB à moins que le drapeau --without-bdb ne soit explicitement passé à configure. Par défaut, configure recherchera Berkeley DB dans les emplacements standard ; il y aura un message dans la sortie de configure indiquant le chemin d'accès qui sera utilisé.

Vous pouvez remplacer ce chemin d'accès en ajoutant un chemin à l'option, par exemple --with-bdb=/usr/BerkeleyDB.4.4. Ce répertoire est censé avoir les sous-répertoires include et lib (lib32 et lib64 sont également vérifiés), contenant respectivement db.h, et la bibliothèque elle-même. Dans le cas où des chemins non standard vers les bibliothèques Berkeley DB sont utilisés, une ou deux des options --with-bdb-include et --with-bdb-lib peuvent être données à configure avec un chemin.

La base de données ovdb peut occuper plus d'espace disque pour un spool donné que les autres méthodes d'aperçu. Prévoyez au moins 1,1 Ko pour chaque article de votre spool (sans compter les crossposts). Ainsi, si vous avez 5 millions d'articles, il vous faudra au moins 5,5 Go d'espace disque pour ovdb. Avec la compression activée, cette estimation passe à 0,9 Ko par article, vous aurez donc besoin d'au moins 4,5 Go d'espace disque pour 5 millions d'articles. Voir la section "COMPRESSION" ci-dessous. De plus, vous aurez besoin d'espace supplémentaire pour les journaux de transactions : au moins 100 Mo. Par défaut, les journaux de transactions se trouvent dans le même répertoire que la base de données. Pour améliorer les performances, ils peuvent être placés sur un disque différent -- voir la section "DB_CONFIG".

CONFIGURATION

Pour activer la méthode d'aperçu ovdb, définissez le paramètre ovmethod dans inn.conf sur "ovdb". La base de données ovdb est stockée dans le répertoire spécifié par le paramètre pathoverview dans inn.conf. C'est le répertoire "DB_HOME". Pour commencer, ce répertoire doit être vide (à l'exception d'un fichier DB_CONFIG optionnel ; voir "DB_CONFIG" pour les détails), et innd (ou makehistory) créera les fichiers nécessaires dans ce répertoire. Assurez-vous également que le répertoire appartient à l'utilisateur news.

D'autres paramètres pour configurer ovdb se trouvent dans le fichier de configuration ovdb.conf. Les paramètres suivants peuvent être définis dans ce fichier :

compress
Si INN a été compilé avec zlib, et que ce paramètre compress est vrai, ovdb compressera les enregistrements d'aperçu de plus de 600 octets. Voir la section "COMPRESSION" ci-dessous.
cachesize
Taille du cache de la mémoire pools, en kilo-octets. Le cache aura un fichier de stockage de secours dans le répertoire DB qui sera au moins aussi grand. En général, plus le cache est grand, mieux c'est. Utilisez "ovdb_stat -m" pour voir les pourcentages de succès du cache. Pour qu'un changement de ce paramètre prenne effet, arrêtez et redémarrez INN (assurez-vous de tuer tous les processus nnrpd lors de l'arrêt). La valeur par défaut est 8000 (Ko), ce qui est adéquat pour les serveurs de petite à moyenne taille. Les grands serveurs auront probablement besoin d'au moins 20000 (Ko).
ncache
Nombre de régions sur lesquelles diviser le cache. La taille de la région est égale à cachesize divisé par ncache. La valeur par défaut est 1 pour ncache, c'est-à-dire que le cache sera alloué de manière contiguë en mémoire.
numdbfiles
Les données d'aperçu sont réparties entre ce nombre de fichiers. Actuellement, innd gardera tous les fichiers ouverts, n'augmentez donc pas trop cette valeur ou innd pourrait manquer de descripteurs de fichiers. nnrpd n'en ouvre qu'un à la fois, quoi qu'il arrive. Peut être réglé sur un, ou seulement quelques-uns, mais ne le faites que si votre OS prend en charge les fichiers volumineux (> 2 Go). Modifier ce paramètre n'a aucun effet sur une base de données déjà établie. La valeur par défaut est 32.
txn_nosync
Si txn_nosync est réglé sur faux, Berkeley DB vide le journal après chaque transaction. Cela minimise le nombre de transactions susceptibles d'être perdues en cas de crash, mais entraîne une dégradation significative des performances. La valeur par défaut est vraie, auquel cas ovdb_monitor vide les journaux de transactions toutes les 30 secondes.
useshm
Si useshm est réglé sur vrai, Berkeley DB utilisera la mémoire partagée au lieu de mmap pour ses régions d'environnement (cache, verrou, etc.). Sur certaines plateformes, cela peut améliorer les performances. La valeur par défaut est fausse.
shmkey
Définit la clé de mémoire partagée utilisée par Berkeley DB lorsque useshm est vrai. Berkeley DB créera plusieurs (généralement 5) segments de mémoire partagée, en utilisant des clés numérotées séquentiellement commençant par "shmkey". Choisissez une clé qui n'entre pas en conflit avec les segments de mémoire partagée existants sur votre système. La valeur par défaut est 6400.
pagesize
Définit la taille de page pour les fichiers DB (en octets). Doit être une puissance de 2. Les meilleurs choix sont 4096 ou 8192. La valeur par défaut est 8192. Modifier ce paramètre n'a aucun effet sur une base de données déjà établie.
minkey
Définit le nombre minimum de clés par page. Voir la documentation Berkeley DB pour plus d'informations. La valeur par défaut est basée sur la taille de page et si la compression est activée : 
default_minkey = MAX(2, pagesize / 2600) si compress est faux
default_minkey = MAX(2, pagesize / 1500) si compress est vrai

Le plus petit minkey autorisé est 2. Définir minkey plus haut que la valeur par défaut n'est pas recommandé, car cela entraînera beaucoup de pages de débordement pour les bases de données. Modifier ce paramètre n'a aucun effet sur une base de données déjà établie.

maxlocks
Définit le paramètre lk_max de Berkeley DB, qui est le nombre maximum de verrous pouvant exister dans la base de données simultanément. La valeur par défaut est 4000.
nocompact
Le paramètre nocompact affecte le comportement de expireover. La fonction expireover dans ovdb peut accomplir sa tâche de deux manières : en supprimant simplement les enregistrements expirés de la base de données ; ou en réécrivant les enregistrements d'aperçu dans un autre loca
tion en laissant de côté les enregistrements expirés. La première méthode est plus rapide, mais elle laisse des « trous » qui entraînent un espace qui ne peut pas être immédiatement réutilisé. La seconde méthode « compacte » les enregistrements en les réécrivant.

Si ce paramètre est défini sur 0, expireover compactera tous les groupes de discussion ; s'il est défini sur 1, expireover ne compactera aucun groupe de discussion ; et s'il est défini sur une valeur supérieure à un, expireover ne compactera que les groupes qui ont moins que ce nombre d'articles.

L'expérience a montré que la compaction a un effet minime (autre que de faire durer expireover plus longtemps), donc la valeur par défaut est 1. Ce paramètre sera probablement supprimé à l'avenir.

readserver
Lorsque le paramètre readserver est défini sur false, chaque processus nnrpd accède directement à l'environnement Berkeley DB. Le processus de connexion à la base de données (et de déconnexion une fois terminé) est assez coûteux, et peut entraîner des charges élevées dans les situations où il y a beaucoup de connexions de lecteur de durée relativement courte.

Lorsque le paramètre readserver est défini sur true, les processus nnrpd accéderont à l'aperçu via un serveur auxiliaire (ovdb_server -- qui est démarré par ovdb_init). Toutes les lectures ovdb seront alors canalisées par un seul processus avec une interface plus propre vers la base de données Berkeley DB sous-jacente. Cela entraînera des arrêts plus propres pour la base de données, améliorant la stabilité et évitant les blocages, les problèmes de synchronisation et les bases de données corrompues. C'est pourquoi vous devriez essayer de définir ce paramètre sur true si vous rencontrez une instabilité dans la méthode d'aperçu ovdb.

La valeur par défaut est true.

numrsprocs
Ce paramètre est utilisé uniquement lorsque readserver est true. Il définit le nombre de processus ovdb_server. Comme chaque ovdb_server ne peut traiter qu'une seule transaction à la fois, l'exécution de plusieurs serveurs peut améliorer les temps de réponse des lecteurs. La valeur par défaut est 5.
maxrsconn
Ce paramètre est utilisé uniquement lorsque readserver est true. Il définit un nombre maximum de lecteurs qu'un processus ovdb_server donné servira à la fois. Cela signifie que le nombre maximum de lecteurs pour l'ensemble des processus ovdb_server est (numrsprocs * maxrsconn). Cela ne limite *pas* le nombre réel de lecteurs, car nnrpd se rabattra sur l'ouverture directe de la base de données s'il ne peut pas se connecter à un ovdb_server. La valeur par défaut est 0, ce qui signifie qu'un nombre illimité de connexions est autorisé.

COMPRESSION

La méthode de stockage ovdb a la capacité de compresser les données d'aperçu avant de les stocker dans la base de données. En plus de consommer moins d'espace disque, la compression maintient la taille moyenne des clés de base de données plus petite. Cela augmente à son tour le nombre moyen de clés par page, ce qui peut considérablement améliorer les performances et aide également à maintenir la base de données plus compacte. Cette fonctionnalité nécessite que INN soit compilé avec zlib. Seuls les enregistrements de plus de 600 octets sont compressés, car c'est le point à partir duquel la compression commence à être significative.

Si la compression n'est pas activée (soit par l'option compress dans ovdb.conf, soit parce que INN n'a pas été compilé avec le support zlib), la base de données sera rétrocompatible avec les anciennes versions d'ovdb. Cependant, si la compression est activée, la base de données est marquée avec une nouvelle version qui empêchera les anciennes versions d'ovdb d'ouvrir la base de données.

Vous pouvez mettre à niveau une base de données existante pour utiliser la compression en définissant simplement compress sur true dans ovdb.conf. Notez que les enregistrements existants dans la base de données resteront non compressés ; seuls les nouveaux enregistrements ajoutés après l'activation de la compression seront compressés.

Si vous désactivez la compression sur une base de données qui l'avait précédemment activée, les nouveaux enregistrements seront stockés non compressés, mais la base de données sera toujours incompatible avec les anciennes versions d'ovdb (et sera également incompatible avec cette version d'ovdb si INN n'a pas été compilé avec le support zlib). Ainsi, pour revenir à une base de données entièrement non compressée, vous devrez reconstruire la base de données en utilisant makehistory.

DB_CONFIG

Un fichier appelé DB_CONFIG peut être placé dans le répertoire de la base de données (pathoverview dans inn.conf) pour personnaliser l'emplacement d'écriture des différents fichiers de base de données et journaux de transactions. Par défaut, tous les fichiers sont écrits dans le répertoire "DB_HOME". Une façon d'améliorer les performances est de placer les journaux de transactions sur un disque différent. Pour ce faire, placez :

DB_LOG_DIR /chemin/vers/logs

dans le fichier DB_CONFIG. Si le chemin que vous donnez commence par un "/", il est traité comme un chemin absolu ; sinon, il est relatif au répertoire "DB_HOME". Assurez-vous que tous les répertoires que vous spécifiez existent et ont les bonnes propriétés de propriété/mode avant de démarrer INN, car ils ne seront pas créés automatiquement. De plus, ne modifiez pas le fichier DB_CONFIG pendant que tout ce qui utilise ovdb est en cours d'exécution.

Une autre chose que vous pouvez faire avec ce fichier est de répartir la base de données d'aperçu sur plusieurs disques. Dans le fichier DB_CONFIG, vous pouvez lister les répertoires que Berkeley DB recherchera lorsqu'il ira ouvrir une base de données.

Par exemple, supposons que vous ayez défini pathoverview sur /mnt/overview et que vous ayez quatre systèmes de fichiers supplémentaires créés sur /mnt/ovX. Vous créeriez un fichier /mnt/overview/DB_CONFIG contenant les lignes suivantes :

set_data_dir /mnt/overview
set_data_dir /mnt/ov1
set_data_dir /mnt/ov2
set_data_dir /mnt/ov3
set_data_dir /mnt/ov4

Répartissez vos fichiers ovNNNNN dans les quatre systèmes de fichiers (disons, 8 chacun). Lorsqu'il sera appelé pour ouvrir un fichier de base de données, la bibliothèque db le recherchera dans chacun des répertoires spécifiés (dans l'ordre). Si ledit fichier n'est pas trouvé, un sera créé dans le premier de ces répertoires.

Chaque fois que vous modifiez DB_CONFIG ou déplacez des fichiers de base de données, assurez-vous que tous les processus d'actualités qui utilisent la base de données sont d'abord arrêtés (y compris les processus nnrpd).

La fonctionnalité DB_CONFIG fait partie de Berkeley DB elle-même, plutôt que quelque chose fourni par ovdb. Consultez la documentation Berkeley DB pour connaître tous les détails de la version de Berkeley DB que vous utilisez.

EXÉCUTION

Au démarrage du système de nouvelles, rc.news appellera le programme ovdb_init. Consultez la page de manuel ovdb_init(8) pour des informations sur les tâches qu'il effectue. ovdb_init doit être exécuté avant d'utiliser la base de données.

Et à l'arrêt d'INN, rc.news tue les processus ovdb_monitor après que les autres processus INN aient été arrêtés.

DIAGNOSTICS

Les problèmes liés à ovdb sont enregistrés dans news.err avec "OVDB" dans le message d'erreur.

Les programmes INN qui utilisent l'aperçu échoueront au démarrage si les processus ovdb_monitor ne sont pas en cours d'exécution. Assurez-vous d'exécuter ovdb_init avant d'exécuter quoi que ce soit qui accède à l'aperçu.

De plus, les programmes INN qui utilisent l'aperçu échoueront au démarrage si l'utilisateur qui les exécute n'est pas l'utilisateur news.

Si un programme accédant à la base de données plante, ou se termine autrement de manière non propre, il peut laisser un verrouillage obsolète dans la base de données. Ce verrouillage peut amener d'autres processus à se bloquer sur ce verrouillage obsolète. Pour résoudre ce problème, arrêtez tous les processus d'actualités (en utilisant "kill -9" si nécessaire) puis redémarrez. ovdb_init devrait effectuer une opération de récupération qui supprimera les verrous et réparera les dommages causés par l'arrêt des processus bloqués.

FICHIERS

pathetc/inn.conf
Les paramètres ovmethod et pathoverview sont pertinents pour ovdb.
pathetc/ovdb.conf
Fichier de configuration optionnel pour le réglage. Voir « CONFIGURATION » ci-dessus.
pathoverview
Répertoire où va la base de données. Berkeley DB l'appelle le répertoire "DB_HOME".
pathoverview/DB_CONFIG
Fichier optionnel pour configurer la disposition des fichiers de base de données.
pathrun/ovdb.sem
Un fichier qui est verrouillé par chaque processus qui accède à la base de données. Ceci est utilisé par ovdb_init pour déterminer si la base de données est active ou inactive.
pathrun/ovdb_monitor.pid
Contient l'identifiant du processus de ovdb_monitor.

À FAIRE

inn(5)

page de manuel de INN

NOM

inn - Fichiers et sous-répertoires de configuration et de données pour INN

DESCRIPTION

Ce manuel décrit les fichiers de configuration et les sous-répertoires utilisés par le serveur de news INN (Internet News).

MISE À NIVEAU

Lors de la mise à niveau d'une version d'INN à une autre, vous devrez peut-être ajuster votre fichier de configuration inn.conf. Les anciens fichiers de configuration peuvent ne pas être entièrement compatibles avec les nouvelles versions, et il est conseillé de consulter les notes de publication pour les changements spécifiques.

INSTALLATION

Le paquet inn sur Arch Linux installe les fichiers de configuration et les données nécessaires dans les répertoires appropriés du système. Après l'installation, le logiciel est généralement prêt à être configuré.

CONFIGURATION

La configuration principale d'INN se fait via le fichier inn.conf. Ce fichier contient de nombreuses options qui contrôlent le comportement du serveur de news, telles que les hôtes à autoriser, les chemins d'accès aux fichiers, les paramètres de mise en réseau, etc.

D'autres fichiers de configuration importants incluent :

  • newsfeeds : Définit comment les articles sont distribués aux groupes de news.
  • readers.conf : Contrôle l'accès des utilisateurs aux groupes de news.

COMPRESSION

INN utilise des schémas de compression pour réduire la taille des articles stockés. Les détails de la configuration de la compression, y compris les algorithmes utilisables, se trouvent généralement dans inn.conf.

DB_CONFIG

Si INN utilise une base de données pour stocker des informations, le fichier db_config peut être utilisé pour spécifier les paramètres de la base de données. Cela inclut le type de base de données et les chemins d'accès aux fichiers de la base de données.

EXÉCUTION

INN est généralement exécuté comme un démon en arrière-plan. Le processus d'installation et de configuration initial devrait inclure la configuration de ce démon pour qu'il démarre automatiquement au lancement du système.

DIAGNOSTIC

Les journaux d'INN, généralement situés dans /var/log/inn/, sont essentiels pour le diagnostic des problèmes. En cas de problème, consultez ces fichiers pour obtenir des informations sur les erreurs ou les avertissements.

FICHIERS

Les fichiers et répertoires importants gérés par INN comprennent :

  • /etc/inn/inn.conf : Fichier de configuration principal.
  • /etc/inn/newsfeeds : Configuration des flux de news.
  • /etc/inn/readers.conf : Configuration de l'accès lecteur.
  • /var/lib/inn/ : Répertoire pour les données des articles et les bases de données.
  • /var/log/inn/ : Répertoire pour les journaux d'INN.

À FAIRE

Cette section est généralement réservée aux tâches futures ou aux améliorations planifiées pour INN. Elle n'est pas toujours présente dans les versions publiques.

HISTORIQUE

Le projet INN a une longue histoire en tant que serveur de news open source. L'historique spécifique des modifications pour la version installée peut être trouvé dans les journaux de version du paquet Arch Linux ou dans la documentation amont.
