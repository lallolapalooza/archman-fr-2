NOM

oci-hooks - Répertoires de configuration des hooks OCI

SYNTAXE

/usr/share/containers/oci/hooks.d/*.json

DESCRIPTION

Offre un moyen aux utilisateurs de configurer les hooks prévus pour les conteneurs Open Container Initiative afin qu'ils ne soient exécutés que pour les conteneurs qui ont besoin de leur fonctionnalité, et seulement pour les étapes où ils sont nécessaires.

RÉPERTOIRES

Les hooks sont configurés avec des fichiers JSON (se terminant par l'extension .json) dans une série de répertoires de hooks. Le répertoire par défaut est /usr/share/containers/oci/hooks.d, mais les outils utilisant ce format peuvent modifier ce défaut, inclure des répertoires supplémentaires ou fournir à leurs appelants des moyens d'ajuster les répertoires de configuration.

Si plusieurs répertoires sont configurés, un nom de fichier JSON dans un répertoire préféré masque les entrées portant le même nom de fichier dans des répertoires de moindre priorité. Par exemple, si un outil consommateur surveille les hooks dans /etc/containers/oci/hooks.d et /usr/share/containers/oci/hooks.d (par ordre de priorité décroissante), alors une définition de hook dans /etc/containers/oci/hooks.d/01-my-hook.json masquera toute définition dans /usr/share/containers/oci/hooks.d/01-my-hook.json.

Les outils utilisant ce format peuvent également choisir de surveiller les répertoires de hooks pour les changements, auquel cas ils remarqueront les ajouts, modifications et suppressions de fichiers JSON sans avoir besoin d'être redémarrés ou signalés autrement. Lorsque l'outil surveille plusieurs répertoires de hooks, la priorité mentionnée dans le paragraphe précédent s'applique toujours. Par exemple, si un outil consommateur surveille les hooks dans /etc/containers/oci/hooks.d et /usr/share/containers/oci/hooks.d (par ordre de priorité décroissante), alors l'écriture d'une nouvelle définition de hook dans /etc/containers/oci/hooks.d/01-my-hook.json masquera le hook précédemment chargé depuis /usr/share/containers/oci/hooks.d/01-my-hook.json. Les modifications ultérieures apportées à /etc/containers/oci/hooks.d/01-my-hook.json n'auront aucun effet sur l'outil consommateur tant que /etc/containers/oci/hooks.d/01-my-hook.json existera. La suppression de /etc/containers/oci/hooks.d/01-my-hook.json rechargera le hook depuis /usr/share/containers/oci/hooks.d/01-my-hook.json.

Les hooks sont injectés dans l'ordre obtenu en triant les noms de fichiers JSON, après les avoir convertis en minuscules, en fonction de leurs points de code Unicode. Par exemple, un hook correspondant défini dans 01-my-hook.json sera injecté avant les hooks correspondants définis dans 02-another-hook.json et 01-UPPERCASE.json. Il est fortement recommandé de rendre l'ordre de tri sans ambiguïté en dépendant d'un préfixe ASCII uniquement (comme le 01/02 ci-dessus).

Chaque fichier JSON doit contenir un objet avec l'un des schémas suivants.

Schéma de hook 1.0.0

version (chaîne de caractères requise)
Définit la version de la définition du hook. Pour cette version de schéma, la valeur sera 1.0.0.

hook (objet requis)
Le hook à injecter, avec le schéma d'entrée de hook défini par la spécification OCI Runtime 1.0.2.

when (objet requis)
Conditions dans lesquelles le hook est injecté. Les propriétés suivantes peuvent être spécifiées, et au moins une doit être spécifiée :

  • always (booléen optionnel)
    Si défini à true, cette condition correspond.
  • annotations (objet optionnel)
    Si toutes les paires clé/valeur des annotations correspondent à une paire clé/valeur des annotations configurées, cette condition correspond.
    Les clés et les valeurs doivent être des expressions régulières étendues POSIX.
  • commands (tableau de chaînes de caractères optionnel)
    Si process.args[0] configuré correspond à une entrée, cette condition correspond.
    Les entrées doivent être des expressions régulières étendues POSIX.
  • hasBindMounts (booléen optionnel)
    Si hasBindMounts est vrai et que l'appelant a demandé des montages bind de l'hôte vers le conteneur, cette condition correspond.

stages (tableau de chaînes de caractères requis)
Étapes pendant lesquelles le hook doit être injecté. Les entrées doivent être choisies parmi les étapes de hook de la spécification OCI Runtime 1.0.2 ou parmi les étapes d'extension prises en charge par le consommateur du package.

Si toutes les conditions définies dans when correspondent, alors le hook doit être injecté pour les étapes définies dans stages.

Schéma de hook 0.1.0

hook (chaîne de caractères requise)
Définit le chemin dans le hook injecté.

arguments (tableau de chaînes de caractères optionnel)
Arguments supplémentaires à passer au hook. Les args du hook injecté sont hook avec les arguments ajoutés.

stages (tableau de chaînes de caractères requis)
Étapes pendant lesquelles le hook doit être injecté. stage est un synonyme autorisé pour cette propriété, mais vous ne devez pas définir stages et stage. Les entrées doivent être choisies parmi les étapes de hook de la spécification OCI Runtime 1.0.2 ou parmi les étapes d'extension prises en charge par le consommateur du package.

cmds (tableau de chaînes de caractères optionnel)
Le hook doit être injecté si process.args[0] configuré correspond à une entrée. cmd est un synonyme autorisé pour cette propriété, mais vous ne devez pas définir cmds et cmd. Les entrées doivent être des expressions régulières étendues POSIX.

annotations (tableau de chaînes de caractères optionnel)
Le hook doit être injecté si une entrée des annotations correspond à une valeur des annotations configurées. annotation est un synonyme autorisé pour cette propriété, mais vous ne devez pas définir annotations et annotation. Les entrées doivent être des expressions régulières étendues POSIX.

hasbindmounts (booléen optionnel)
Le hook doit être injecté si hasBindMounts est vrai et que l'appelant a demandé des montages bind de l'hôte vers le conteneur.

EXEMPLE

Schéma de hook 1.0.0

La configuration suivante injecte oci-systemd-hook dans les étapes prestart et poststop si process.args[0] se termine par /init ou /systemd :

$ cat /etc/containers/oci/hooks.d/oci-systemd-hook.json
{
  "version": "1.0.0",
  "hook": {
    "path": "/usr/libexec/oci/hooks.d/oci-systemd-hook"
  },
  "when": {
    "commands": [".*/init$" , ".*/systemd$"]
  },
  "stages": ["prestart", "poststop"]
}

L'exemple suivant injecte oci-umount --debug dans l'étape prestart si le conteneur est configuré pour monter bind des répertoires hôtes dans le conteneur.

$ cat /etc/containers/oci/hooks.d/oci-umount.json
{
  "version": "1.0.0",
  "hook": {
    "path": "/usr/libexec/oci/hooks.d/oci-umount",
    "args": ["oci-umount", "--debug"],
  },
  "when": {
    "hasBindMounts": true
  },
  "stages": ["prestart"]
}

L'exemple suivant injecte nvidia-container-runtime-hook prestart avec des variables d'environnement particulières dans l'étape prestart si le conteneur est configuré avec une entrée annotations dont la clé correspond à ^com\.example\.department$ et dont la valeur correspond à .*fluid-dynamics.*.

$ cat /etc/containers/oci/hooks.d/nvidia.json
{
  "version": "1.0.0",
  "hook": {
    "path": "/usr/sbin/nvidia-container-runtime-hook",
    "args": ["nvidia-container-runtime-hook", "prestart"],
    "env": [
      "NVIDIA_REQUIRE_CUDA=cuda>=9.1",
      "NVIDIA_VISIBLE_DEVICES=GPU-fef8089b"
    ]
  },
  "when": {
    "annotations": {
      "^com\\.example\\.department$": ".*fluid-dynamics$"
    }
  },
  "stages": ["prestart"]
}

Schéma de hook 0.1.0

La configuration suivante injecte oci-systemd-hook dans les étapes prestart et poststop si process.args[0] se termine par /init ou /systemd :

$ cat /etc/containers/oci/hooks.d/oci-systemd-hook.json
{
  "cmds": [".*/init$" , ".*/systemd$"],
  "hook": "/usr/libexec/oci/hooks.d/oci-systemd-hook",
  "stages": ["prestart", "poststop"]
}

oci-hooks(5)

NAME

oci-hooks - OCI hooks configuration file

SYNOPSIS

/etc/containers/oci/hooks.d/*.json

DESCRIPTION

OCI hooks are executable programs that are run at specific points in the container lifecycle, such as when a container is created, started, or stopped. This allows for customization and integration with other systems.

This man page describes the format of OCI hook configuration files, which are typically placed in the /etc/containers/oci/hooks.d/ directory.

Each configuration file must be a JSON file ending with .json. The file specifies the hook executable, its arguments, and the conditions under which it should be executed.

A hook configuration object has the following fields:

hook
The path to the hook executable. This field is mandatory.
arguments
A list of strings representing the arguments to pass to the hook executable. This field is optional.
env
A dictionary of environment variables to set for the hook executable. This field is optional.
when
A dictionary specifying conditions for running the hook. This field is optional.
when.hasbindmounts
If set to true, the hook will only run if the container has bind mounts configured. This field is optional.
when.labels
A dictionary of label key-value pairs. The hook will only run if the container's labels match all of the specified labels. This field is optional.
when.annotations
A dictionary of annotation key-value pairs. The hook will only run if the container's annotations match all of the specified annotations. Values can be regular expressions. This field is optional.
stages
A list of strings specifying the container lifecycle stages in which the hook should be executed. Valid stages include: prestart, poststart, prestop, poststop, precreate, postcreate. This field is optional, and if omitted, the hook will run in all stages.
hasbindmounts
Deprecated. Use when.hasbindmounts instead.

The configuration files are processed in alphabetical order by filename within the /etc/containers/oci/hooks.d/ directory.

Directories

OCI hooks can be configured in the following directories:

  • /etc/containers/oci/hooks.d: System-wide hooks.
  • $HOME/.config/containers/oci/hooks.d: User-specific hooks.

EXAMPLE

The following example configures the oci-umount hook to run in the prestart stage if the container has bind mounts. The --debug argument is passed to the hook.

$ cat /etc/containers/oci/hooks.d/oci-umount.json
{
  "hook": "/usr/libexec/oci/hooks.d/oci-umount",
  "arguments": ["--debug"],
  "hasbindmounts": true,
  "stages": ["prestart"]
}

The following example injects nvidia-container-runtime-hook prestart in the pre-start stage if the container is configured with an annotations entry whose value matches .*fluid-dynamics.*.

$ cat /etc/containers/oci/hooks.d/osystemd-hook.json
{
  "hook": "/usr/sbin/nvidia-container-runtime-hook",
  "arguments": ["prestart"],
  "annotations: [".*fluid-dynamics.*"],
  "stages": ["prestart"]
}
