OCAMLC(1) Manuel des commandes générales OCAMLC(1)

NOM

ocamlc - Le compilateur bytecode OCaml

SYNTAXE

ocamlc [ options ] fichier ...

ocamlc.opt [ options ] fichier ...

DESCRIPTION

Le compilateur bytecode OCaml ocamlc(1) compile les fichiers source OCaml en fichiers objets bytecode et lie ces fichiers objets pour produire des fichiers exécutables bytecode autonomes. Ces fichiers exécutables sont ensuite exécutés par l'interpréteur bytecode ocamlrun(1).

La commande ocamlc(1) a une interface en ligne de commande similaire à celle de la plupart des compilateurs C. Elle accepte plusieurs types d'arguments et les traite séquentiellement, une fois toutes les options traitées :

Les arguments se terminant par .mli sont considérés comme des fichiers source pour les interfaces d'unités de compilation. Les interfaces spécifient les noms exportés par les unités de compilation : elles déclarent des noms de valeurs avec leurs types, définissent des types de données publiques, déclarent des types de données abstraites, etc. À partir du fichier x.mli, le compilateur ocamlc(1) produit une interface compilée dans le fichier x.cmi.

Les arguments se terminant par .ml sont considérés comme des fichiers source pour les implémentations d'unités de compilation. Les implémentations fournissent des définitions pour les noms exportés par l'unité, et contiennent également des expressions à évaluer pour leurs effets de bord. À partir du fichier x.ml, le compilateur ocamlc(1) produit un fichier objet bytecode compilé dans le fichier x.cmo.

Si le fichier d'interface x.mli existe, l'implémentation x.ml est vérifiée par rapport à l'interface compilée correspondante x.cmi, qui est supposée exister. Si aucune interface x.mli n'est fournie, la compilation de x.ml produit un fichier d'interface compilée x.cmi en plus du fichier de code objet compilé x.cmo. Le fichier x.cmi produit correspond à une interface qui exporte tout ce qui est défini dans l'implémentation x.ml.

Les arguments se terminant par .cmo sont considérés comme des objets bytecode compilés. Ces fichiers sont liés ensemble, avec les fichiers objets obtenus par compilation des arguments .ml (le cas échéant), et la bibliothèque standard OCaml, pour produire un programme exécutable autonome. L'ordre dans lequel les arguments .cmo et .ml sont présentés sur la ligne de commande est pertinent : les unités de compilation sont initialisées dans cet ordre au moment de l'exécution, et il est une erreur de liaison d'utiliser un composant d'une unité avant de l'avoir initialisé. Par conséquent, un fichier x.cmo donné doit apparaître avant tous les fichiers .cmo qui référencent l'unité x.

Les arguments se terminant par .cma sont considérés comme des bibliothèques de bytecode objet. Une bibliothèque de bytecode objet regroupe dans un seul fichier un ensemble de fichiers bytecode objet (.cmo files). Les bibliothèques sont construites avec ocamlc -a (voir la description de l'option -a ci-dessous). Les fichiers objets contenus dans la bibliothèque sont liés comme des fichiers .cmo réguliers (voir ci-dessus), dans l'ordre spécifié lors de la création du fichier .cma. La seule différence est que si un fichier objet contenu dans une bibliothèque n'est référencé nulle part dans le programme, il n'est pas lié.

Les arguments se terminant par .c sont passés au compilateur C, qui génère un fichier objet .o. Ce fichier objet est lié au programme si le drapeau -custom est défini (voir la description de -custom ci-dessous).

Les arguments se terminant par .o ou .a sont supposés être des fichiers objets C et des bibliothèques. Ils sont passés à l'éditeur de liens C lors de la liaison en mode -custom (voir la description de -custom ci-dessous).

Les arguments se terminant par .so sont supposés être des bibliothèques partagées C (DLL). Pendant la liaison, ils sont recherchés pour les fonctions C externes référencées depuis le code OCaml, et leurs noms sont écrits dans l'exécutable bytecode généré. Le système d'exécution ocamlrun(1) les charge ensuite dynamiquement au démarrage du programme.

La sortie de la phase de liaison est un fichier contenant du bytecode compilé exécutable par l'interpréteur bytecode OCaml : la commande ocamlrun(1). Si caml.out est le nom du fichier produit par la phase de liaison, la commande ocamlrun caml.out arg1 arg2 ... argn exécute le code compilé contenu dans caml.out, en lui passant comme arguments les chaînes de caractères arg1 à argn. (Voir ocamlrun(1) pour plus de détails.)

Sur la plupart des systèmes, le fichier produit par la phase de liaison peut être exécuté directement, comme ceci : ./caml.out arg1 arg2 ... argn. Le fichier produit a le bit exécutable défini, et il parvient à lancer lui-même l'interpréteur bytecode.

ocamlc.opt est le même compilateur que ocamlc, mais compilé avec le compilateur de code natif ocamlopt(1). Il se comporte donc exactement comme ocamlc, mais compile plus rapidement. ocamlc.opt peut ne pas être disponible dans toutes les installations d'OCaml.

OPTIONS

Les options suivantes en ligne de commande sont reconnues par ocamlc(1).

-a
Construit une bibliothèque (.cma file) avec les fichiers objets (.cmo files) fournis en ligne de commande, au lieu de les lier en un fichier exécutable. Le nom de la bibliothèque doit être défini avec l'option -o.
Si des options -custom, -cclib ou -ccopt sont passées en ligne de commande, ces options sont stockées dans la bibliothèque .cma résultante. Ensuite, la liaison avec cette bibliothèque ajoute automatiquement les options -custom, -cclib et -ccopt comme si elles avaient été fournies en ligne de commande, sauf si l'option -noautolink est donnée. De plus, une sous-chaîne $CAMLORIGIN à l'intérieur d'une option -ccopt sera remplacée par le chemin complet vers la bibliothèque .cma, excluant le nom du fichier.
-absname
Afficher les noms de fichiers absolus dans les messages d'erreur.
-no-absname
Ne pas essayer d'afficher les noms de fichiers absolus dans les messages d'erreur.
-annot
Obsolète depuis la version 4.11. Veuillez utiliser -bin-annot à la place.
-bin-annot
Dump des informations détaillées sur la compilation (types, liaisons, appels de queue, etc.) en format binaire. Les informations pour le fichier src.ml sont placées dans le fichier src.cmt. En cas d'erreur de type, dump toutes les informations inférées par le vérificateur de types avant l'erreur. Les fichiers d'annotation produits par -bin-annot contiennent plus d'informations et sont beaucoup plus compacts que les fichiers produits par -annot.
-c
Compiler uniquement. Supprime la phase de liaison de la compilation. Les fichiers source sont transformés en fichiers compilés, mais aucun fichier exécutable n'est produit. Cette option est utile pour compiler des modules séparément.
-cc ccomp
Utiliser ccomp comme éditeur de liens C lors de la liaison en mode "runtime custom" (voir l'option -custom) et comme compilateur C pour la compilation des fichiers .c.
-cclib -llibname
Passer l'option -llibname à l'éditeur de liens C lors de la liaison en mode "runtime custom" (voir l'option -custom). Cela provoque la liaison de la bibliothèque C donnée avec le programme.
-ccopt option
Passer l'option option donnée au compilateur C et à l'éditeur de liens, lors de la liaison en mode "runtime custom" (voir l'option -custom). Par exemple, -ccopt -Ldir demande à l'éditeur de liens C de rechercher les bibliothèques C dans le répertoire dir.
-color mode
Activer ou désactiver les couleurs dans les messages du compilateur (en particulier les avertissements et les erreurs). Les modes suivants sont supportés :

auto utilise des heuristiques pour activer les couleurs uniquement si la sortie les supporte (un terminal tty compatible ANSI) ;

always active les couleurs inconditionnellement ;

never désactive la sortie en couleurs.

La variable d'environnement "OCAML_COLOR" est prise en compte si -color n'est pas fourni. Ses valeurs sont auto/always/never comme ci-dessus.

Si -color n'est pas fourni, "OCAML_COLOR" n'est pas défini et la variable d'environnement "NO_COLOR"

" est défini, alors la couleur la sortie est désactivée. Sinon, le réglage par défaut est auto, et l'heuristique actuelle vérifie que la variable d'environnement « TERM » existe et n'est pas vide ou « dumb », et que isatty(stderr) est vrai.

-error-style mode
Contrôle la manière dont les messages d'erreur et les avertissements sont imprimés. Les modes suivants sont pris en charge :

short imprime uniquement l'erreur et sa localisation ;

contextual comme « short », mais affiche également le extrait de code source correspondant à la localisation de l'erreur.

Le réglage par défaut est contextual.

La variable d'environnement « OCAML_ERROR_STYLE » est prise en compte si -error-style n'est pas fourni. Ses valeurs sont short/contextual comme ci-dessus.

-compat-32
Vérifie que l'exécutable bytecode généré peut s'exécuter sur des plateformes 32 bits et signale une erreur si ce n'est pas le cas. Ceci est utile lors de la compilation de bytecode sur une machine 64 bits.
-config
Imprime le numéro de version de ocamlc(1) et un résumé détaillé de sa configuration, puis quitte.
-config-var
Imprime la valeur d'une variable de configuration spécifique de la sortie -config, puis quitte. Si la variable n'existe pas, le code de sortie est non nul.
-custom
Lie en mode « runtime personnalisé ». Dans le mode de liaison par défaut, l'éditeur de liens produit un bytecode destiné à être exécuté avec le système d'exécution partagé, ocamlrun(1). En mode runtime personnalisé, l'éditeur de liens produit un fichier de sortie contenant à la fois le système d'exécution et le bytecode du programme. Le fichier résultant est plus volumineux, mais il peut être exécuté directement, même si la commande ocamlrun(1) n'est pas installée. De plus, le mode « runtime personnalisé » permet de lier du code OCaml avec des fonctions C définies par l'utilisateur.

N'utilisez jamais la commande strip(1) sur les exécutables produits par ocamlc -custom, cela supprimerait la partie bytecode de l'exécutable.

Avertissement de sécurité : ne définissez jamais les bits « setuid » ou « setgid » sur les exécutables produits par ocamlc -custom, cela les rendrait vulnérables aux attaques.

-depend ocamldep-args
Calcule les dépendances, comme le ferait ocamldep.
-dllib -llibname
Arrange pour que la bibliothèque partagée C dlllibname.so soit chargée dynamiquement par le système d'exécution ocamlrun(1) au démarrage du programme.
-dllpath dir
Ajoute le répertoire dir au chemin de recherche d'exécution des bibliothèques C partagées. Au moment de la liaison, les bibliothèques partagées sont recherchées dans le chemin de recherche standard (celui correspondant à l'option -I). L'option -dllpath stocke simplement dir dans le fichier exécutable produit, où ocamlrun(1) peut le trouver et l'utiliser.
-for-pack module-path
Génère un fichier objet (.cmo) qui peut plus tard être inclus comme sous-module (avec le chemin d'accès donné) d'une unité de compilation construite avec -pack. Par exemple, ocamlc -for-pack P -c A.ml générera a.cmo qui pourra plus tard être utilisé avec ocamlc -pack -o P.cmo a.cmo. Note : vous pouvez toujours empaqueter un module compilé sans -for-pack mais dans ce cas les exceptions seront imprimées avec les mauvais noms.
-g
Ajoute des informations de débogage lors de la compilation et de la liaison. Cette option est requise pour pouvoir déboguer le programme avec ocamldebug(1) et pour produire des traces de pile lorsque le programme se termine sur une exception non interceptée.
-no-g
N'enregistre pas les informations de débogage (par défaut).
-i
Fait en sorte que le compilateur imprime tous les noms définis (avec leurs types inférés ou leurs définitions) lors de la compilation d'une implémentation (.ml file). Aucun fichier compilé (.cmo et .cmi files) n'est produit. Ceci peut être utile pour vérifier les types inférés par le compilateur. De plus, comme la sortie suit la syntaxe des interfaces, cela peut aider à écrire une interface explicite (.mli file) pour un fichier : il suffit de rediriger la sortie standard du compilateur vers un fichier .mli, et d'éditer ce fichier pour supprimer toutes les déclarations de noms non exportés.
-cmi-file filename
Vérifie le type de l'implémentation source à compiler par rapport au fichier d'interface spécifié (ignore la recherche normale des fichiers .mli et .cmi).
-I directory
Ajoute le répertoire donné à la liste des répertoires recherchés pour les fichiers d'interface compilés (.cmi), les fichiers de code objet compilé (.cmo), les bibliothèques (.cma), et les bibliothèques C spécifiées avec -cclib -lxxx. Par défaut, le répertoire courant est recherché en premier, puis le répertoire de la bibliothèque standard. Les répertoires ajoutés avec -I sont recherchés après le répertoire courant, dans l'ordre où ils ont été donnés sur la ligne de commande, mais avant le répertoire de la bibliothèque standard. Voir aussi l'option -nostdlib.

Si le répertoire donné commence par +, il est pris par rapport au répertoire de la bibliothèque standard. Par exemple, -I +compiler-libs ajoute le sous-répertoire compiler-libs de la bibliothèque standard au chemin de recherche.

-impl filename
Compile le fichier filename comme un fichier d'implémentation, même si son extension n'est pas .ml.
-intf filename
Compile le fichier filename comme un fichier d'interface, même si son extension n'est pas .mli.
-intf-suffix string
Reconnaît les noms de fichiers se terminant par string comme des fichiers d'interface (au lieu du .mli par défaut).
-keep-docs
Conserve les chaînes de documentation dans les fichiers .cmi générés.
-keep-locs
Conserve les emplacements dans les fichiers .cmi générés.
-keywords version+list
Définit les mots-clés selon la spécification version+list.

Cette spécification commence par un numéro de version optionnel, définissant l'ensemble de base des mots-clés, suivi d'une liste séparée par des + de mots-clés supplémentaires à ajouter à cet ensemble de base. Sans numéro de version explicite, l'ensemble de base des mots-clés est l'ensemble des mots-clés dans la version actuelle d'OCaml. Les mots-clés supplémentaires qui ne correspondent à aucun mot-clé connu dans la version actuelle du langage déclenchent une erreur chaque fois qu'ils sont présents dans le code source.

-labels
Les étiquettes ne sont pas ignorées dans les types, les étiquettes peuvent être utilisées dans les applications, et les paramètres étiquetés peuvent être donnés dans n'importe quel ordre. C'est le comportement par défaut.
-linkall
Force la liaison de tous les modules contenus dans les bibliothèques. Si ce drapeau n'est pas donné, les modules non référencés ne sont pas liés. Lors de la construction d'une bibliothèque (option -a), la définition de l'option -linkall force toutes les liaisons ultérieures de programmes impliquant cette bibliothèque à lier tous les modules contenus dans la bibliothèque. Lors de la compilation d'un module (option -c), la définition de l'option -linkall garantit que ce module sera toujours lié s'il est placé dans une bibliothèque et que cette bibliothèque est liée.
-make-runtime
Construit un système d'exécution personnalisé (dans le fichier spécifié par l'option -o) intégrant les fichiers objets C et les bibliothèques donnés sur la ligne de commande. Ce système d'exécution personnalisé peut être utilisé plus tard pour exécuter des exécutables bytecode produits avec l'option ocamlc -use-runtime nom-runtime.
-match-context-rows
Définit le nombre de lignes de contexte utilisées lors de la compilation de la correspondance de motifs. Des valeurs plus basses entraînent une compilation plus rapide, mais un code moins optimisé. La valeur par défaut est 32.
-no-alias-deps
N'enregistre pas les dépendances pour les alias de modules.
-no-app-funct
Désactive le comportement applicatif des foncteurs. Avec cette option, chaque application de foncteur génère de nouveaux types dans son résultat et l'application du même foncteur deux fois au même argument produit deux structures incompatibles.
-noassert
Ne compile pas les vérifications d'assertions. Notez que la forme spéciale assert false est toujours compilée car elle est typée spécialement. Ce drapeau n'a aucun effet lors de la liaison de fichiers déjà compilés (fichiers .cmo).
-noautolink
Lors de la liaison des bibliothèques .cma, ignore les options -custom, -cclib et -ccopt potentiellement contenues dans les bibliothèques (si ces options ont été données lors de la construction des bibliothèques). Ceci peut être utile si une bibliothèque contient des spécifications incorrectes de bibliothèques C ou d'options C ; dans ce cas, lors de la liaison, définissez -noautolink et passez les bibliothèques C et les options correctes sur la ligne de commande.
-nolabels
Ignore les étiquettes non optionnelles dans les types. Les étiquettes ne peuvent pas être utilisées dans les applications, et l'ordre des paramètres devient strict.
-nostdlib
N'ajoute pas automatiquement le répertoire de la bibliothèque standard à la liste des répertoires recherchés pour les fichiers d'interface compilés (.cmi), les fichiers de code objet compilé (.cmo), les bibliothèques (.cma), et les bibliothèques C spécifiées avec -cclib -lxxx. Voir aussi l'option -I.
-o exec-file
Spécifie le nom du fichier de sortie produit par l'éditeur de liens. Le nom de sortie par défaut est a.out, conformément à la tradition Unix. Si l'option -a est donnée, spécifi
ify le nom de la bibliothèque produite. Si l'option -pack est donnée, spécifiez le nom du fichier objet empaqueté produit. Si l'option -output-obj ou -output-complete-obj est donnée, spécifiez le nom du fichier de sortie produit. Ceci peut également être utilisé lors de la compilation d'un fichier d'interface ou d'implémentation, sans liaison, auquel cas il définit le nom du fichier cmi ou cmo, et définit également le nom du module au nom du fichier jusqu'au premier point.
-opaque
Les fichiers d'interface compilés avec cette option sont marqués de sorte que les autres unités de compilation qui en dépendent ne s'appuieront sur aucun détail d'implémentation de l'implémentation compilée. Le compilateur natif n'accédera pas au fichier .cmx de cette unité -- ni ne signalera s'il est absent. Ceci peut améliorer la vitesse de compilation, pour les builds initiaux et incrémentiels, au détriment des performances du code généré.
-open module
Ouvre le module donné avant de traiter les fichiers d'interface ou d'implémentation. Si plusieurs options -open sont données, elles sont traitées dans l'ordre, comme si les instructions open! module1;; ... open! moduleN;; étaient ajoutées en haut de chaque fichier.
-output-obj
Demande à l'éditeur de liens de produire un fichier objet C au lieu d'un fichier exécutable bytecode. Ceci est utile pour encapsuler du code OCaml en tant que bibliothèque C, appelable depuis n'importe quel programme C. Le nom du fichier objet de sortie doit être défini avec l'option -o. Cette option peut également être utilisée pour produire un fichier source C (.extension c) ou une bibliothèque partagée/dynamique compilée (.extension so).
-output-complete-obj
Identique à -output-obj sauf lors de la création d'un fichier objet où il inclut le runtime et les bibliothèques d'autolien.
-pack
Construit un fichier objet bytecode (.fichier cmo) et son interface compilée associée (.cmi) qui combine les fichiers objets donnés sur la ligne de commande, les faisant apparaître comme des sous-modules du fichier .cmo de sortie. Le nom du fichier .cmo de sortie doit être donné avec l'option -o. Par exemple, ocamlc -pack -o p.cmo a.cmo b.cmo c.cmo génère les fichiers compilés p.cmo et p.cmi décrivant une unité de compilation ayant trois sous-modules A, B et C, correspondant au contenu des fichiers objets a.cmo, b.cmo et c.cmo. Ces contenus peuvent être référencés comme P.A, P.B et P.C dans le reste du programme.
-pp commande
Demande au compilateur d'appeler la commande donnée comme préprocesseur pour chaque fichier source. La sortie de la commande est redirigée vers un fichier intermédiaire, qui est compilé. S'il n'y a pas d'erreurs de compilation, le fichier intermédiaire est supprimé par la suite.
-ppx commande
Après l'analyse syntaxique, redirige l'arbre syntaxique abstrait à travers le préprocesseur commande. Le module Ast_mapper(3) implémente l'interface externe d'un préprocesseur.
-principal
Vérifie le chemin d'information lors de la vérification des types, pour s'assurer que tous les types sont dérivés de manière principale. Lors de l'utilisation d'arguments nommés et/ou de méthodes polymorphes, ce drapeau est requis pour garantir que les futures versions du compilateur pourront inférer les types correctement, même si les algorithmes internes changent. Tous les programmes acceptés en mode -principal sont également acceptés en mode par défaut avec des types équivalents, mais des signatures binaires différentes, et cela peut ralentir la vérification des types ; il est néanmoins conseillé de l'utiliser une fois avant de publier le code source.
-no-principal
Ne vérifie pas la principauté de l'inférence de types. C'est le comportement par défaut.
-rectypes
Autorise les types récursifs arbitraires lors de la vérification des types. Par défaut, seuls les types récursifs où la récursion passe par un type objet sont supportés. Notez qu'une fois que vous avez créé une interface en utilisant ce drapeau, vous devez l'utiliser à nouveau pour toutes les dépendances.
-no-rectypes
N'autorise pas les types récursifs arbitraires lors de la vérification des types. C'est le comportement par défaut.
-runtime-variant suffixe
Ajoute le suffixe au nom de la bibliothèque runtime qui sera utilisée par le programme. Si OCaml a été configuré avec l'option -with-debug-runtime, alors le suffixe d est supporté et donne une version de débogage du runtime.
-safe-string
Enforce la séparation entre les types string et bytes , rendant ainsi les chaînes de caractères en lecture seule. C'est le comportement par défaut.
-safer-matching
N'utilise pas les informations de type pour optimiser la correspondance de motifs. Ceci permet de détecter les échecs de correspondance même si une correspondance de motifs était supposée à tort être exhaustive. Ceci n'affecte que la compilation GADT et de variantes polymorphes.
-short-paths
Lorsqu'un type est visible sous plusieurs chemins de modules, utilisez le plus court lors de l'impression du nom du type dans les interfaces inférées et les messages d'erreur et d'avertissement.
-stop-after etape
Arrête la compilation après l'étape de compilation donnée. Les étapes actuellement supportées sont : parsing, typing.
-strict-sequence
Force la partie gauche de chaque séquence à avoir le type unit.
-no-strict-sequence
La partie gauche d'une séquence n'a pas besoin d'avoir le type unit. C'est le comportement par défaut.
-unboxed-types
Lorsqu'un type est déballable (c'est-à-dire un enregistrement avec un seul argument ou une donnée concrète avec un seul constructeur d'un argument) il sera déballé sauf s'il est annoté avec [@@ocaml.boxed].
-no-unboxed-types
Lorsqu'un type est déballable, il sera empaqueté sauf s'il est annoté avec [@@ocaml.unboxed]. C'est le comportement par défaut.
-unsafe
Désactive la vérification des limites pour les accès aux tableaux et chaînes (les constructions v.(i) et s.[i]). Les programmes compilés avec -unsafe sont donc légèrement plus rapides, mais non sécurisés : tout peut arriver si le programme accède à un tableau ou une chaîne en dehors de ses limites.
-unsafe-string
Identifie les types string et bytes , rendant ainsi les chaînes écrivables. Ceci est destiné à la compatibilité avec l'ancien code source et ne doit pas être utilisé avec de nouveaux logiciels.
-use-runtime nom-runtime
Génère un fichier exécutable bytecode qui peut être exécuté sur le système runtime personnalisé nom-runtime, construit précédemment avec ocamlc -make-runtime nom-runtime.
-v
Affiche le numéro de version du compilateur et l'emplacement du répertoire de la bibliothèque standard, puis quitte.
-verbose
Affiche toutes les commandes externes avant leur exécution, en particulier les invocations du compilateur C et de l'éditeur de liens en mode -custom. Utile pour déboguer des problèmes de bibliothèques C.
-vnum ou -version
Affiche le numéro de version du compilateur sous forme courte (par exemple, "3.11.0"), puis quitte.
-w liste-avertissements
Active, désactive ou marque comme fatales les erreurs spécifiées par l'argument liste-avertissements.

Chaque avertissement peut être activé ou désactivé , et chaque avertissement peut être fatal ou non fatal. Si un avertissement est désactivé, il n'est pas affiché et n'affecte en rien la compilation (même s'il est fatal). S'il est activé, il est affiché normalement par le compilateur chaque fois que le code source le déclenche. S'il est activé et fatal, le compilateur s'arrêtera également avec une erreur après l'avoir affiché.

L'argument liste-avertissements est soit un spécificateur d'avertissement mnémonique soit une séquence de spécificateurs d'avertissement à un seul caractère, sans séparateurs entre eux. Un spécificateur d'avertissement mnémonique est l'un des suivants

+nom   Active l'avertissement nom.

-nom   Désactive l'avertissement nom.

@nom   Active et marque comme fatal l'avertissement nom.

Un spécificateur d'avertissement à un seul caractère est l'un des suivants :

+num   Active l'avertissement numéro num.

-num   Désactive l'avertissement numéro num.

@num   Active et marque comme fatal l'avertissement numéro num.

+num1..num2   Active tous les avertissements entre num1 et num2 (inclus).

-num1..num2   Désactive tous les avertissements entre num1 et num2 (inclus).

@num1..num2   Active et marque comme fatals tous les avertissements entre num1 et num2 (inclus).

+lettre   Active l'ensemble des avertissements correspondant à la lettre. La lettre peut être majuscule ou minuscule.

-lettre   Désactive l'ensemble des avertissements correspondant à la lettre. La lettre peut être majuscule ou minuscule.

@lettre   Active et marque comme fatals l'ensemble des avertissements correspondant à la lettre. La lettre peut être majuscule ou minuscule.

lettre-majuscule   Active l'ensemble des avertissements correspondant à la lettre-majuscule.

lettre-minuscule   Désactive l'ensemble des avertissements correspondant à la lettre-minuscule.

-warn-error liste-avertissements
Marque comme erreurs les avertissements spécifiés dans l'argument liste-avertissements. Le compilateur s'arrêtera avec une erreur lorsqu'un de ces avertissements sera émis. La liste-avertissements a la même signification que pour l'option -w : un signe + (ou une lettre majuscule) marque les avertissements correspondants comme fatals, un signe - (ou une lettre minuscule) les retransforme en avertissements non fatals, et un signe @ active les avertissements correspondants et les marque comme fatals.

Note : il n'est pas recommandé d'utiliser l'option -warn-error dans du code de production, car cela empêchera presque certainement la compilation de votre programme avec des versions ultérieures d'OCaml lorsqu'elles ajouteront de nouveaux avertissements ou modifieront ceux existants.

Le réglage par défaut est -warn-error -a (aucun avertissement n'est fatal).
