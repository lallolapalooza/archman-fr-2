ossl-guide-tls-client-block - Guide OpenSSL : Écrire un client TLS bloquant simple

EXEMPLE DE CLIENT TLS BLOQUANT SIMPLE

Cette page présente divers exemples de code démontrant comment écrire une application client TLS simple qui se connecte à un serveur, lui envoie une requête HTTP/1.0 et lit la réponse.

Nous utilisons un socket bloquant pour cet exemple. Cela signifie que tenter de lire des données à partir d'un socket sur lequel aucune donnée n'est disponible pour la lecture bloquera (et la fonction ne retournera pas), jusqu'à ce que des données soient disponibles. Par exemple, cela peut se produire si nous avons envoyé notre requête, mais que nous attendons toujours la réponse du serveur. De même, toute tentative d'écriture sur un socket qui ne peut pas écrire pour le moment bloquera jusqu'à ce que l'écriture soit possible.

Ce comportement bloquant simplifie l'implémentation d'un client car vous n'avez pas à vous soucier de ce qui se passe si les données ne sont pas encore disponibles. L'application attendra simplement jusqu'à ce qu'elles soient disponibles.

Le code source complet de cet exemple de client TLS bloquant est disponible dans le répertoire demos/guide de la distribution source OpenSSL, dans le fichier tls-client-block.c. Il est également disponible en ligne à l'adresse https://github.com/openssl/openssl/blob/master/demos/guide/tls-client-block.c.

Nous supposons que vous avez déjà OpenSSL installé sur votre système ; que vous avez déjà une compréhension fondamentale des concepts OpenSSL et TLS (voir ossl-guide-libraries-introduction(7) et ossl-guide-tls-introduction(7)) ; et que vous savez comment écrire et compiler du code C et le lier aux bibliothèques libcrypto et libssl fournies par OpenSSL. Cela suppose également que vous avez une compréhension de base de TCP/IP et des sockets.

Création des objets SSL_CTX et SSL

La première étape consiste à créer un objet SSL_CTX pour notre client. Nous utilisons la fonction SSL_CTX_new(3) à cet effet. Nous pourrions utiliser SSL_CTX_new_ex(3) si nous voulons associer le SSL_CTX à un OSSL_LIB_CTX particulier (voir ossl-guide-libraries-introduction(7) pour en savoir plus sur OSSL_LIB_CTX). Nous passons comme argument le résultat de la fonction TLS_client_method(3). Vous devriez utiliser cette méthode chaque fois que vous écrivez un client TLS. Cette méthode utilisera automatiquement la négociation de version TLS pour sélectionner la version la plus élevée du protocole qui est mutuellement prise en charge par le client et le serveur.

/*
 * Crée un SSL_CTX que nous pouvons utiliser pour créer des objets SSL. Nous
 * voulons un SSL_CTX pour créer des clients, donc nous utilisons TLS_client_method()
 * ici.
 */
ctx = SSL_CTX_new(TLS_client_method());
if (ctx == NULL) {
    printf("Échec de la création du SSL_CTX\n");
    goto end;
}

Puisque nous écrivons un client, nous devons nous assurer de vérifier le certificat du serveur. Nous le faisons en appelant la fonction SSL_CTX_set_verify(3) et en lui passant la valeur SSL_VERIFY_PEER. Le dernier argument de cette fonction est une fonction de rappel que vous pouvez facultativement fournir pour remplacer la gestion par défaut de la vérification du certificat. La plupart des applications n'ont pas besoin de le faire, cela peut donc être défini en toute sécurité sur NULL pour obtenir la gestion par défaut.

/*
 * Configure le client pour qu'il abandonne la négociation si la vérification
 * du certificat échoue. Presque tous les clients devraient le faire, sauf si vous
 * savez vraiment ce que vous faites.
 */
SSL_CTX_set_verify(ctx, SSL_VERIFY_PEER, NULL);

Pour que la vérification du certificat réussisse, vous devez avoir configuré l'emplacement du magasin de certificats de confiance à utiliser (voir ossl-guide-tls-introduction(7)). Dans la plupart des cas, vous souhaitez simplement utiliser le magasin par défaut, nous appelons donc SSL_CTX_set_default_verify_paths(3).

/* Utilise le magasin de certificats de confiance par défaut */
if (!SSL_CTX_set_default_verify_paths(ctx)) {
    printf("Échec de la configuration du magasin de certificats de confiance par défaut\n");
    goto end;
}

Nous aimerions également restreindre les versions TLS que nous sommes prêts à accepter à TLSv1.2 ou supérieur. Les versions du protocole TLS antérieures à celle-ci doivent généralement être évitées autant que possible. Nous pouvons le faire en utilisant SSL_CTX_set_min_proto_version(3) :

/*
 * TLSv1.1 et les versions antérieures sont dépréciés par l'IETF et doivent
 * généralement être évités autant que possible. Nous exigeons une version minimale
 * du protocole TLS de TLSv1.2.
 */
if (!SSL_CTX_set_min_proto_version(ctx, TLS1_2_VERSION)) {
    printf("Échec de la définition de la version minimale du protocole TLS\n");
    goto end;
}

C'est tout ce que nous avons besoin de configurer pour le SSL_CTX, donc ensuite nous devons créer un objet SSL pour représenter la connexion TLS. Dans une application réelle, nous pourrions nous attendre à créer plus d'une connexion TLS au fil du temps. Dans ce cas, nous nous attendrions à réutiliser le SSL_CTX que nous avons déjà créé à chaque fois. Il n'est pas nécessaire de répéter ces étapes. En fait, il est préférable de ne pas le faire car certaines ressources internes sont mises en cache dans le SSL_CTX. Vous obtiendrez de meilleures performances en réutilisant un SSL_CTX existant au lieu d'en créer un nouveau à chaque fois.

La création de l'objet SSL est une simple affaire d'appel de la fonction SSL_new(3) et de passage du SSL_CTX que nous avons créé comme argument.

/* Crée un objet SSL pour représenter la connexion TLS */
ssl = SSL_new(ctx);
if (ssl == NULL) {
    printf("Échec de la création de l'objet SSL\n");
    goto end;
}

Création du socket et du BIO

Les données TLS sont transmises sur une couche de transport sous-jacente. Normalement un socket TCP. Il incombe à l'application de s'assurer que le socket est créé et associé à un objet SSL (via un BIO).

La création de socket à utiliser par un client est généralement un processus en 2 étapes, c'est-à-dire la construction du socket ; et la connexion du socket.

La manière de construire un socket est spécifique à la plateforme, mais la plupart des plateformes (y compris Windows) fournissent une interface compatible POSIX via la fonction socket, par exemple pour créer un socket TCP IPv4 :

int sock;
sock = socket(AF_INET, SOCK_STREAM, 0);
if (sock == -1)
    return NULL;

Une fois le socket construit, il doit être connecté au serveur distant. Encore une fois, les détails sont spécifiques à la plateforme, mais la plupart des plateformes (y compris Windows) fournissent la fonction connect compatible POSIX. Par exemple :

struct sockaddr_in serveraddr;
struct hostent *server;
server = gethostbyname("www.openssl.org");
if (server == NULL) {
    close(sock);
    return NULL;
}
memset(&serveraddr, 0, sizeof(serveraddr));
serveraddr.sin_family = server->h_addrtype;
serveraddr.sin_port = htons(443);
memcpy(&serveraddr.sin_addr.s_addr, server->h_addr, server->h_length);
if (connect(sock, (struct sockaddr *)&serveraddr,
            sizeof(serveraddr)) == -1) {
    close(sock);
    return NULL;
}

OpenSSL fournit des fonctions d'aide portables pour effectuer ces tâches, qui s'intègrent également dans le système d'erreurs OpenSSL pour enregistrer les données d'erreur, par exemple :

int sock = -1;
BIO_ADDRINFO *res;
const BIO_ADDRINFO *ai = NULL;
/*
 * Recherche les informations d'adresse IP du serveur.
 */
if (!BIO_lookup_ex(hostname, port, BIO_LOOKUP_CLIENT, family, SOCK_STREAM, 0,
                   &res))
    return NULL;
/*
 * Parcourt toutes les adresses possibles pour le serveur et en trouve une
 * à laquelle nous pouvons nous connecter.
 */
for (ai = res; ai != NULL; ai = BIO_ADDRINFO_next(ai)) {
    /*
     * Crée un socket TCP. Nous pourrions aussi bien utiliser des appels non-OpenSSL
     * comme "socket" ici pour cela et les fonctions connect et close ultérieures.
     * Mais pour des raisons de portabilité et aussi pour que nous obtenions
     * des erreurs dans la pile OpenSSL en cas d'échec, nous utilisons
     * les versions OpenSSL de ces fonctions.
     */
    sock = BIO_socket(BIO_ADDRINFO_family(ai), SOCK_STREAM, 0, 0);
    if (sock == -1)
        continue;
    /* Connecte le socket à l'adresse du serveur */
    if (!BIO_connect(sock, BIO_ADDRINFO_address(ai), BIO_SOCK_NODELAY)) {
        BIO_closesocket(sock);
        sock = -1;
        continue;
    }
    /* Nous avons un socket connecté, donc nous sortons de la boucle */
    break;
}
/* Libère les ressources d'informations d'adresse que nous avons allouées précédemment */
BIO_ADDRINFO_free(res);

Voir BIO_lookup_ex(3), BIO_socket(3), BIO_connect(3), BIO_closesocket(3), BIO_ADDRINFO_free(3), BIO_ADDRINFO_next(3), et BIO_ADDRINFO_address(3) pour plus de détails.

Nous devons maintenant associer le socket à notre objet SSL. Le moyen le plus simple de faire cela est d'utiliser une structure BIO (Basic I/O) qui encapsule notre socket. Nous créons un BIO pour notre socket en utilisant la fonction BIO_new_socket(3) :

/* Crée un BIO associé à notre socket */
bio = BIO_new_socket(sock, BIO_NOCLOSE);
if (bio == NULL) {
    printf("Échec de la création du BIO\n");
    goto end;
}

Il existe plusieurs options pour la manière dont le BIO gère la fermeture du socket sous-jacent. Dans cet exemple, nous passons BIO_NOCLOSE car nous voulons fermer le socket nous-mêmes lorsque nous aurons terminé. Si nous avions passé BIO_CLOSE, alors la fermeture du BIO aurait également fermé le socket.

Maintenant, nous lions le BIO à notre objet SSL. Ceci est fait en utilisant la fonction SSL_set_bio(3) :

/* Lie le BIO à l'objet SSL */
SSL_set_bio(ssl, bio, bio);

Nous avons maintenant terminé la configuration des objets nécessaires. Les BIOs utilisés ici sont le BIO "read" et le BIO "write". En passant le même BIO pour les deux, nous obtenons le comportement par défaut où les opérations de lecture et d'écriture sur l'objet SSL liront et écriront sur le même socket sous-jacent.

Effectuer la négociation TLS

Nous sommes maintenant prêts à effectuer la négociation TLS. C'est la phase où le client et le serveur s'authentifient mutuellement (si nécessaire) et établissent les paramètres de sécurité pour la connexion. Ceci est fait en appelant la fonction SSL_connect(3) :

/*
 * Effectue la négociation TLS.
 */
if (SSL_connect(ssl) <= 0) {
    /*
     * Nous avons rencontré une erreur. Nous devons la signaler, mais nous
     * pouvons aussi vouloir essayer de réessayer si l'erreur était temporaire.
     */
    ERR_print_errors_fp(stderr);
    goto end;
}

Le comportement de SSL_connect(3) est défini par la manière dont les BIOs sous-jacents se comportent. Dans notre cas, le BIO sous-jacent est un socket bloquant. Par conséquent, SSL_connect(3) se comportera également de manière bloquante. Il retournera uniquement lorsque la négociation sera terminée ou qu'une erreur irrécupérable se produira.

Si SSL_connect(3) renvoie une valeur <= 0, cela signifie qu'il y a eu un problème. Nous imprimons les erreurs qui se sont produites en utilisant ERR_print_errors_fp(3).

Une fois la négociation terminée avec succès, nous pouvons vouloir vérifier l'identité du serveur. Nous faisons cela en appelant SSL_get_verify_result(3). Une valeur de X509_V_OK signifie que la vérification a réussi. Sinon, un code d'erreur est retourné qui peut être utilisé pour déterminer la raison de l'échec.

/*
 * Vérifie que la négociation s'est bien déroulée et que le certificat
 * du serveur est valide.
 */
if (SSL_get_verify_result(ssl) != X509_V_OK) {
    fprintf(stderr, "Erreur de vérification du certificat du serveur.\n");
    ERR_print_errors_fp(stderr);
    goto end;
}

Nous pouvons également vouloir connaître le nom de l'émetteur du certificat du serveur et sa date d'expiration. Le certificat lui-même est obtenu en appelant SSL_get_peer_certificate(3). La structure X509 retournée contient toutes les informations du certificat.

/*
 * Récupère le certificat du pair et affiche des informations à son sujet.
 */
cert = SSL_get_peer_certificate(ssl);
if (cert == NULL) {
    printf("Aucun certificat du pair n'a été récupéré.\n");
    goto end;
}
printf("Certificat du pair obtenu:\n");
X509_print_fp(stdout, cert);

N'oubliez pas de libérer la structure X509 lorsque vous avez terminé avec elle en appelant X509_free(3).

X509_free(cert);

À ce stade, la connexion TLS est établie et nous pouvons commencer à envoyer et recevoir des données. Pour cet exemple, nous envoyons une requête HTTP simple.

Envoi et réception de données

L'envoi et la réception de données sur une connexion TLS sont très similaires à l'envoi et à la réception de données sur un socket normal. La principale différence est que nous utilisons les fonctions SSL_read(3) et SSL_write(3) au lieu de read(3) et write(3).

Voici comment nous envoyons une requête HTTP GET simple :

/*
 * Envoie une requête HTTP GET simple au serveur.
 */
snprintf(request, sizeof(request), "GET / HTTP/1.0\r\nHost: %s\r\n\r\n", hostname);
printf("Envoi de la requête:\n%s", request);
written = SSL_write(ssl, request, strlen(request));
if (written <= 0) {
    ERR_print_errors_fp(stderr);
    goto end;
}

Encore une fois, les fonctions SSL_read(3) et SSL_write(3) se comporteront de manière bloquante car le BIO sous-jacent est un socket bloquant. Si des données ne sont pas encore disponibles pour la lecture, SSL_read(3) bloquera jusqu'à ce qu'elles le soient. De même, si le socket ne peut pas accepter plus de données pour l'écriture, SSL_write(3) bloquera jusqu'à ce qu'il le puisse.

Après avoir envoyé notre requête, nous voulons lire la réponse du serveur. Nous pouvons le faire dans une boucle, en lisant les données par morceaux jusqu'à ce que le serveur ferme la connexion.

/*
 * Lit la réponse du serveur.
 */
printf("Réponse du serveur:\n");
for (;;) {
    /*
     * Essaie de lire jusqu'à 1024 octets de données du serveur.
     */
    bytes_read = SSL_read(ssl, buffer, sizeof(buffer) - 1);
    if (bytes_read <= 0) {
        /*
         * Une valeur <= 0 signifie que la lecture a échoué, ou que le
         * serveur a fermé la connexion.
         */
        if (bytes_read == 0) {
            /* Connexion fermée par le serveur */
            break;
        } else {
            /* Erreur de lecture */
            ERR_print_errors_fp(stderr);
            goto end;
        }
    }
    /* Assure que le buffer est terminé par un caractère nul pour l'affichage */
    buffer[bytes_read] = '\0';
    /* Affiche les données lues */
    printf("%s", buffer);
}

La boucle se termine lorsque SSL_read(3) renvoie 0, ce qui indique que le serveur a fermé la connexion de manière gracieuse.

Nettoyage

Une fois que nous avons terminé avec la connexion TLS, nous devons la fermer et libérer toutes les ressources que nous avons allouées. La fermeture de la connexion TLS est effectuée en appelant SSL_shutdown(3) :

/*
 * Ferme la connexion TLS.
 */
if (SSL_shutdown(ssl) <= 0) {
    /*
     * La fermeture peut échouer si la connexion n'était pas encore complètement
     * établie ou si une erreur s'est produite. Nous ignorons l'erreur pour
     * l'instant, car nous allons libérer les ressources de toute façon.
     */
    ERR_print_errors_fp(stderr);
}

Notez que SSL_shutdown(3) peut nécessiter plus d'une tentative pour se terminer complètement, en particulier si une négociation de fermeture est nécessaire. Pour cet exemple simple, nous n'essayons qu'une seule fois. Dans une application plus robuste, vous devriez gérer plusieurs appels à SSL_shutdown(3) jusqu'à ce qu'il soit terminé ou qu'une erreur irrécupérable se produise.

Enfin, nous libérons toutes les ressources allouées :

end:
/* Libère les ressources */
SSL_free(ssl);
/* Ferme le socket. Notez que si nous avions utilisé BIO_CLOSE, cela n'aurait
 * pas été nécessaire ici. */
BIO_closesocket(sock);
SSL_CTX_free(ctx);
return 0;

La libération de l'objet SSL est effectuée en appelant SSL_free(3). La fermeture du socket est effectuée en appelant BIO_closesocket(3). Enfin, nous libérons le SSL_CTX en appelant SSL_CTX_free(3).

Dans l'exemple de code ci-dessus, les variables hostname et port sont des chaînes de caractères, par exemple "www.example.com" et "443". Notez également l'utilisation de la variable family, qui peut prendre les valeurs AF_INET ou AF_INET6 en fonction de l'option de ligne de commande -6, pour permettre des connexions spécifiques à un hôte activé ipv4 ou ipv6.

Les sockets créés en utilisant les méthodes décrites ci-dessus seront automatiquement des sockets bloquantes - ce qui est exactement ce que nous voulons pour cet exemple.

Une fois que le socket a été créé et connecté, nous devons l'associer à un objet BIO :

BIO *bio;
/* Créer un BIO pour encapsuler le socket */
bio = BIO_new(BIO_s_socket());
if (bio == NULL) {
    BIO_closesocket(sock);
    return NULL;
}
/*
 * Associer le BIO nouvellement créé au socket sous-jacent. En passant
 * BIO_CLOSE, le socket sera automatiquement fermé lorsque le BIO sera libéré.
 * Alternativement, vous pouvez utiliser BIO_NOCLOSE, auquel cas vous devez fermer
 * le socket explicitement lorsqu'il n'est plus nécessaire.
 */
BIO_set_fd(bio, sock, BIO_CLOSE);

Voir BIO_new(3), BIO_s_socket(3) et BIO_set_fd(3) pour plus d'informations sur ces fonctions.

Enfin, nous associons l'objet SSL que nous avons créé précédemment avec le BIO en utilisant la fonction SSL_set_bio(3). Notez que cela transfère la propriété de l'objet BIO à l'objet SSL. Une fois la propriété transférée, l'objet SSL est responsable de sa gestion et le libérera automatiquement lorsque le SSL sera libéré. Ainsi, une fois que SSL_set_bio(3) a été appelée, vous ne devriez pas appeler BIO_free(3) sur le BIO.

SSL_set_bio(ssl, bio, bio);

Définir le nom d'hôte du serveur

Nous avons déjà connecté notre socket sous-jacent au serveur, mais le client a toujours besoin de connaître le nom d'hôte du serveur. Il utilise ces informations à 2 fins principales et nous devons définir le nom d'hôte pour chacune d'elles.

Premièrement, le nom d'hôte du serveur est inclus dans le message initial ClientHello envoyé par le client. Ceci est connu sous le nom de Server Name Indication (SNI). C'est important car il est courant que plusieurs noms d'hôtes soient devant un seul serveur qui gère les requêtes pour tous. En d'autres termes, un seul serveur peut avoir plusieurs noms d'hôtes associés, et il est important d'indiquer celui auquel nous voulons nous connecter. Sans ces informations, nous pourrions avoir un échec de handshake, ou nous pourrions être connectés au serveur "par défaut" qui pourrait ne pas être celui attendu.

Pour définir les données du nom d'hôte SNI, nous appelons la fonction SSL_set_tlsext_host_name(3) comme suit :

/*
 * Indiquer au serveur pendant le handshake quel nom d'hôte nous essayons
 * de contacter au cas où le serveur prendrait en charge plusieurs hôtes.
 */
if (!SSL_set_tlsext_host_name(ssl, hostname)) {
    printf("Échec de la définition du nom d'hôte SNI\n");
    goto end;
}

Ici, l'argument "hostname" est une chaîne de caractères représentant le nom d'hôte du serveur, par exemple "www.example.com".

Deuxièmement, nous devons indiquer à OpenSSL quel nom d'hôte nous nous attendons à voir dans le certificat renvoyé par le serveur. C'est presque toujours le même que celui que nous avons demandé dans la requête initiale. C'est important car, sans cela, nous ne vérifions pas que le nom d'hôte dans le certificat est celui que nous attendons et n'importe quel certificat est acceptable à moins que votre application ne le vérifie explicitement elle-même. Nous faisons cela via la fonction SSL_set1_host(3) :

/*
 * Assurez-vous que nous vérifions pendant la validation du certificat que le serveur
 * a fourni un certificat pour le nom d'hôte que nous attendions.
 * Pratiquement tous les clients devraient faire cela, sauf si vous savez vraiment ce que vous faites.
 */
if (!SSL_set1_host(ssl, hostname)) {
    printf("Échec de la définition du nom d'hôte pour la vérification du certificat");
    goto end;
}

Toutes les étapes ci-dessus doivent avoir lieu avant que nous n'essayions d'effectuer le handshake, sinon elles n'auront aucun effet.

Effectuer le handshake

Avant de pouvoir commencer à envoyer ou recevoir des données d'application sur une connexion TLS, le handshake TLS doit être effectué. Nous pouvons le faire explicitement via la fonction SSL_connect(3).

/* Effectuer le handshake avec le serveur */
if (SSL_connect(ssl) < 1) {
    printf("Échec de la connexion au serveur\n");
    /*
     * Si l'échec est dû à une erreur de vérification, nous pouvons obtenir plus
     * d'informations à son sujet à partir de SSL_get_verify_result().
     */
    if (SSL_get_verify_result(ssl) != X509_V_OK)
        printf("Erreur de vérification : %s\n",
            X509_verify_cert_error_string(SSL_get_verify_result(ssl)));
    goto end;
}

La fonction SSL_connect(3) peut retourner 1, 0 ou moins de 0. Seule une valeur de retour de 1 est considérée comme un succès. Pour un client bloquant simple, nous n'avons besoin de nous préoccuper que de savoir si l'appel a réussi ou non. Tout le reste indique que nous avons échoué à nous connecter au serveur.

Une cause fréquente d'échec à ce stade est un problème lors de la vérification du certificat du serveur. Par exemple, si le certificat a expiré, ou s'il n'est pas signé par une CA dans notre magasin de certificats de confiance. Nous pouvons utiliser la fonction SSL_get_verify_result(3) pour obtenir plus d'informations sur l'échec de la vérification. Une valeur de retour de X509_V_OK indique que la vérification a réussi (donc l'erreur de connexion doit être due à une autre cause). Sinon, nous utilisons la fonction X509_verify_cert_error_string(3) pour obtenir un message d'erreur lisible par l'homme.

Envoi et réception de données

Une fois le handshake terminé, nous sommes en mesure d'envoyer et de recevoir des données d'application. Exactement quelles données sont envoyées et dans quel ordre est généralement contrôlé par un protocole au niveau de l'application. Dans cet exemple, nous utilisons HTTP 1.0, qui est un protocole de requête et réponse très simple. Le client envoie une requête au serveur. Le serveur envoie les données de réponse puis ferme immédiatement la connexion.

Pour envoyer des données au serveur, nous utilisons la fonction SSL_write_ex(3) et pour recevoir des données du serveur, nous utilisons la fonction SSL_read_ex(3). En HTTP 1.0, le client écrit toujours d'abord les données. Notre requête HTTP inclura le nom d'hôte auquel nous nous connectons. Pour simplifier, nous écrivons la requête HTTP en trois parties. D'abord, nous écrivons le début de la requête. Ensuite, nous écrivons le nom d'hôte auquel nous envoyons la requête. Enfin, nous envoyons la fin de la requête.

size_t written;
const char *request_start = "GET / HTTP/1.0\r\nConnection: close\r\nHost: ";
const char *request_end = "\r\n\r\n";
/* Écrire une requête HTTP GET au pair */
if (!SSL_write_ex(ssl, request_start, strlen(request_start), &written)) {
    printf("Échec de l'écriture du début de la requête HTTP\n");
    goto end;
}
if (!SSL_write_ex(ssl, hostname, strlen(hostname), &written)) {
    printf("Échec de l'écriture du nom d'hôte dans la requête HTTP\n");
    goto end;
}
if (!SSL_write_ex(ssl, request_end, strlen(request_end), &written)) {
    printf("Échec de l'écriture de la fin de la requête HTTP\n");
    goto end;
}

La fonction SSL_write_ex(3) retourne 0 en cas d'échec et 1 en cas de succès. En cas de succès, nous pouvons passer à l'attente d'une réponse du serveur.

size_t readbytes;
char buf[160];
/*
 * Obtenir jusqu'à sizeof(buf) octets de la réponse. Nous continuons à lire jusqu'à ce que
 * le serveur ferme la connexion.
 */
while (SSL_read_ex(ssl, buf, sizeof(buf), &readbytes)) {
    /*
    * OpenSSL ne garantit pas que les données retournées sont une chaîne ou
    * qu'elles sont terminées par un NUL, nous utilisons donc fwrite() pour écrire le nombre exact
    * d'octets que nous avons lus. Les données pourraient être non imprimables ou
    * contenir des caractères NUL au milieu. Pour cet exemple simple,
    * nous allons les imprimer sur stdout de toute façon.
    */
    fwrite(buf, 1, readbytes, stdout);
}
/* Au cas où la réponse ne se terminerait pas par une nouvelle ligne, nous en ajoutons une maintenant */
printf("\n");

Nous utilisons la fonction SSL_read_ex(3) pour lire la réponse. Nous ne savons pas exactement quelle quantité de données nous allons recevoir, nous entrons donc dans une boucle de lecture de blocs de données du serveur et d'impression de chaque bloc reçu à l'écran. La boucle se termine dès que SSL_read_ex(3) retourne 0 - ce qui signifie qu'elle n'a pas réussi à lire de données.

Un échec de lecture de données pourrait signifier qu'il y a eu un problème, ou cela pourrait simplement signifier que le serveur a envoyé toutes les données qu'il voulait envoyer et a indiqué qu'il a terminé en envoyant une alerte "close_notify". Cette alerte est un message au niveau du protocole TLS indiquant que le point de terminaison a fini d'envoyer toutes ses données et n'en enverra plus. Ces deux conditions entraînent une valeur de retour de 0 de SSL_read_ex(3) et nous devons utiliser la fonction SSL_get_error(3) pour déterminer la cause de la valeur de retour de 0.

/*
 * Vérifier si nous avons terminé la boucle while ci-dessus normalement ou suite
 * à une erreur. L'argument 0 à SSL_get_error() est le code de retour
 * que nous avons reçu de l'appel SSL_read_ex(). Il doit être 0 pour
 * arriver ici. Une fin normale est indiquée par SSL_ERROR_ZERO_RETURN.
 */
if (SSL_get_error(ssl, 0) != SSL_ERROR_ZERO_RETURN) {
    /*
     * Une autre erreur s'est produite autre qu'une fermeture normale par le
     * pair
     */
    printf ("Échec de la lecture des données restantes\n");
    goto end;
}

Si SSL_get_error(3) retourne SSL_ERROR_ZERO_RETURN, nous savons que le serveur a fini d'envoyer ses données. Sinon, une erreur s'est produite.

NAME

ossl-guide-tls-client-block — TLS client demo, blocking socket

SIMPLE BLOCKING TLS CLIENT EXAMPLE

This page shows a simple TLS client example using OpenSSL's libssl. It demonstrates how to establish a TLS connection, send and receive data, and gracefully shut down the connection.

We'll be building this example piece by piece, explaining each part as we go.

Setting up the SSL context

Before we can establish a TLS connection we need to set up an SSL_CTX. This is an object that contains configuration information for TLS connections. It's used to create SSL objects, which represent individual TLS connections.

/* Create context */
ctx = SSL_CTX_new(TLS_client_method());
if (!ctx) {
    fprintf(stderr, "Error creating the SSL context...\n");
    goto end;
}

We use SSL_CTX_new(3) to create a new context. TLS_client_method() specifies that this context will be used for client-side TLS connections.

Configuring the SSL context

Next, we need to configure the context. This typically involves setting the trusted CA certificates, which are used to verify the server's certificate.

/* Load trusted certificates */
if (SSL_CTX_load_verify_locations(ctx, CA_CERT_FILE, NULL) <= 0) {
    fprintf(stderr, "Error loading CA certificate file...\n");
    ERR_print_errors_fp(stderr);
    goto end;
}

We use SSL_CTX_load_verify_locations(3) to load the trusted CA certificates from the file specified by CA_CERT_FILE. If CA_CERT_FILE is set to NULL, the default system store is used.

/* Set verification mode */
SSL_CTX_set_verify(ctx, SSL_VERIFY_PEER, NULL);

We use SSL_CTX_set_verify(3) to set the verification mode. SSL_VERIFY_PEER means that the client will attempt to verify the server's certificate.

Creating an SSL object

Now that we have a configured context, we can create an SSL object for our specific connection.

/* Create the SSL object */
ssl = SSL_new(ctx);
if (!ssl) {
    fprintf(stderr, "Error creating the SSL object...\n");
    goto end;
}

We use SSL_new(3) to create the SSL object, passing it our context.

Setting up the BIO

BIO (Basic Input/Output) objects are used by OpenSSL to handle I/O. We need to associate a BIO object with our SSL object to handle the network communication.

/* Create BIO */
bio = BIO_new_ssl_socket(sock, BIO_NOCLOSE);
if (!bio) {
    fprintf(stderr, "Error creating BIO...\n");
    goto end;
}

We use BIO_new_ssl_socket(3) to create a BIO object that wraps our socket. BIO_NOCLOSE prevents the BIO from closing the socket when it's freed.

/* Set the BIO for the SSL object */
SSL_set_bio(ssl, bio, bio);

We then use SSL_set_bio(3) to associate the BIO with the SSL object. The first bio is for reading, and the second is for writing.

Performing the TLS handshake

With everything set up, we can initiate the TLS handshake.

/* Perform the handshake */
ret = SSL_connect(ssl);
if (ret < 1) {
    fprintf(stderr, "Error during the SSL connection...\n");
    ERR_print_errors_fp(stderr);
    goto end;
}

The SSL_connect(3) function attempts to complete the TLS handshake. It returns 1 on success, 0 if the handshake is not yet complete (which shouldn't happen with a blocking socket), and a negative value on error.

If SSL_connect(3) returns an error, we print the OpenSSL error stack using ERR_print_errors_fp(3) for debugging.

Sending and Receiving Data

Once the handshake is complete, we can send and receive data using SSL_write(3) and SSL_read(3).

/* Write data */
ret = SSL_write(ssl, msg, strlen(msg));
if (ret < 1) {
    fprintf(stderr, "Error writing to the socket...\n");
    ERR_print_errors_fp(stderr);
    goto end;
}

We use SSL_write(3) to send data. It returns the number of bytes written, or a value less than 1 on error.

/* Read data */
ret = SSL_read(ssl, buf, sizeof(buf) - 1);
if (ret < 1) {
    /*
     * If SSL_read returns SSL_ERROR_ZERO_RETURN, it means the peer
     * has shut down the connection gracefully.
     */
    if (ret == 0) {
        printf("Peer has closed the connection gracefully.\n");
        /* We should do the same */
        goto shutdown;
    }
    fprintf(stderr, "Error reading from the socket...\n");
    ERR_print_errors_fp(stderr);
    goto end;
}

We use SSL_read(3) to read data. It returns the number of bytes read. A return value of 0 indicates that the peer has closed the connection gracefully. A negative value indicates an error.

Graceful Shutdown

To shut down the connection gracefully, we need to send a "close_notify" alert to the server.

shutdown:
/* Send close_notify alert */
ret = SSL_shutdown(ssl);
if (ret < 1) {
    /*
     * ret < 0 indicates an error. ret == 0 would be unexpected here
     * because that means "we've sent a close_notify and we're waiting
     * for one back". But we already know we got one from the peer
     * because of the SSL_ERROR_ZERO_RETURN above.
     */
    printf("Error shutting down\n");
    goto end;
}

The SSL_shutdown(3) function initiates the shutdown process. It returns 1 on success (meaning both sides have sent and received close_notify), 0 if we've sent close_notify but haven't received one back yet, and a negative value on error.

In this example, we expect to receive a close_notify from the peer before calling SSL_shutdown(3) (due to the SSL_ERROR_ZERO_RETURN from SSL_read(3)). Therefore, a return value of 0 from SSL_shutdown(3) should ideally not occur and is treated as an error here.

Final clean up

Finally, we free the allocated resources.

   /* Success! */
   res = EXIT_SUCCESS;
end:
   /*
    * If something bad happened then we will dump the contents of the
    * OpenSSL error stack to stderr. There might be some useful diagnostic
    * information there.
    */
   if (res == EXIT_FAILURE)
       ERR_print_errors_fp(stderr);
   /*
    * Free the resources we allocated. We do not free the BIO object here
    * because ownership of it was immediately transferred to the SSL object
    * via SSL_set_bio(). The BIO will be freed when we free the SSL object.
    */
   SSL_free(ssl);
   SSL_CTX_free(ctx);
   return res;

We use ERR_print_errors_fp(3) to print any accumulated OpenSSL errors to stderr if an error occurred.

We then free the SSL object using SSL_free(3) and the SSL_CTX using SSL_CTX_free(3).

TROUBLESHOOTING

Failure to connect the underlying socket

This can be due to network issues, firewalls, DNS problems, or the server not running.

Verification failure of the server certificate

This typically occurs during the SSL_connect(3) call and indicates a problem with the server's certificate or the client's trust store.

Verify error:unable to get local issuer certificate
40E74AF1F47F0000:error:0A000086:SSL routines:tls_post_process_server_certificate:certificate verify failed:ssl/statem/statem_clnt.c:2069:

Common causes include:

Failure to correctly setup the trusted certificate store
Ensure your CA_CERT_FILE is correctly specified or that your system's trust store is properly configured. Refer to ossl-guide-tls-introduction(7).
Unrecognised CA
The Certificate Authority (CA) that signed the server's certificate is not present in the client's trusted certificate store. This can happen with self-signed certificates.
Missing intermediate CAs
The server has not provided all the necessary intermediate CA certificates to establish a complete trust chain.
Mismatched hostname
The hostname the client is trying to connect to does not match the hostname specified in the server's certificate.
Expired certificate
The server's certificate has passed its validity period.

The specific error "unable to get local issuer certificate" means the client couldn't find the issuer of the server's certificate (or one of its intermediates) in its trusted store.
