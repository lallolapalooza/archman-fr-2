NOM

ovsqlite - Méthode de stockage d'aperçus basée sur SQLite pour INN

DESCRIPTION

Cette méthode utilise SQLite pour stocker les données d'aperçu. Elle nécessite la version 3.8.2 ou ultérieure de la bibliothèque SQLite (3.20.0+ recommandée).

La source, la documentation, etc. de SQLite sont disponibles sur https://www.sqlite.org/. L'un des objectifs déclarés du format de fichier SQLite est la stabilité et la compatibilité à long terme, ce qui fait de cette méthode de stockage un choix parfait pour stocker les données d'aperçu.

Seule une version de protocole de la méthode de stockage ovsqlite existe actuellement, implémentée depuis INN 2.7.0.

Cette méthode est accompagnée d'un utilitaire de support (ovsqlite-util) et d'un module Perl ("INN::ovsqlite_client") qui permettent d'accéder et de manipuler les informations d'aperçu. Consultez leurs pages de manuel pour plus de détails sur leurs possibilités.

INSTALLATION

Le script configure activera automatiquement le support ovsqlite s'il trouve la bibliothèque SQLite. Si la bibliothèque n'est pas installée dans un emplacement standard, vous devrez peut-être spécifier l'option --with-sqlite3 pour aider configure à la trouver. Pour les cas complexes, vous pouvez utiliser des options distinctes --with-sqlite3-include et --with-sqlite3-lib. Enfin, si vous ne voulez *pas* de support ovsqlite même si votre système possède la bibliothèque SQLite, vous pouvez utiliser l'option --without-sqlite3.

Si vous avez une installation Linux récente, SQLite est très probablement déjà installée. Vous devrez peut-être installer un paquet séparé avec un nom similaire à "libsqlite3-dev" pour obtenir les fichiers d'en-tête requis.

Prévoyez au moins 0.93 Ko par article dans votre spool (sans compter les crossposts). Ainsi, si vous avez 5 millions d'articles, vous aurez besoin d'au moins 4,65 Go d'espace disque pour ovsqlite. Avec la compression activée, cette estimation passe à 0,4 Ko par article, vous aurez donc besoin d'au moins 2 Go d'espace disque pour 5 millions d'articles. De plus, vous aurez besoin d'espace supplémentaire pour les journaux de transaction (quelques Mo).

CONFIGURATION

Pour sélectionner ovsqlite comme méthode d'aperçu, définissez le paramètre ovmethod dans inn.conf sur "ovsqlite". Le fichier de base de données sera créé dans le répertoire spécifié par le paramètre pathoverview dans inn.conf. Redémarrez INN pour prendre en compte le changement (après avoir reconstruit votre aperçu existant avec makehistory, si nécessaire).

Les paramètres supplémentaires suivants sont lus à partir du fichier de configuration ovsqlite.conf :

cachesize
La taille du cache de pages en mémoire de SQLite en kilo-octets. La valeur par défaut est laissée à la bibliothèque SQLite et semble être stable à 2000 Ko.
compress
Si INN a été compilé avec le support zlib et que ce paramètre est vrai, ovsqlite compressera les enregistrements d'aperçu chaque fois que cela permettra de gagner de l'espace. Ce paramètre n'est consulté que lors de la création d'une nouvelle base de données. L'activation de la compression permet d'économiser environ 55% d'espace disque sur les données d'aperçu standard. La valeur par défaut est fausse.
pagesize
La taille de page de la base de données SQLite en octets. Doit être une puissance de 2, minimum 512, maximum 65536. Les valeurs appropriées incluent la taille de page de la mémoire virtuelle et la taille de bloc d'allocation du système de fichiers. Ce paramètre n'est consulté que lors de la création d'une nouvelle base de données. La valeur par défaut est laissée à la bibliothèque SQLite et varie selon les versions.
transrowlimit
Le nombre maximum de lignes d'articles pouvant être insérées ou supprimées dans une seule transaction SQL. La valeur par défaut est de 10000 articles.
transtimelimit
La durée maximale de vie d'une transaction SQL en secondes. La valeur par défaut est de 10 secondes.

Une transaction a lieu tous les transrowlimit articles ou toutes les transtimelimit secondes, selon la première éventualité. Il est recommandé de conserver la valeur par défaut pour les limites de lignes et, à la place, d'ajuster la limite de temps en fonction du nombre d'articles que votre serveur de news accepte généralement par seconde en fonctionnement normal (vous pouvez trouver des statistiques sur les articles entrants dans vos rapports Usenet quotidiens). L'insertion ou la suppression d'une ligne de base de données dans une transaction est très rapide, tandis que la validation d'une transaction est lente, en particulier sur un stockage rotatif. Définir des limites de transaction trop basses entraîne de mauvaises performances. Lors de la reconstruction des données d'aperçu, il peut être utile d'augmenter temporairement ces valeurs sur les systèmes avec un processeur lent ou un stockage rotatif (par exemple, multiplier par 10 les valeurs par défaut). Les performances ne changeront pas beaucoup sur les systèmes rapides.

EXÉCUTION

Tout accès à la base de données d'aperçu passe par le démon ovsqlite-server. Pour un fonctionnement ordinaire, rc.news le démarre et l'arrête automatiquement. Si vous souhaitez toucher à la base de données d'aperçu pendant que innd n'est pas en cours d'exécution, vous devrez d'abord démarrer ovsqlite-server manuellement. Voir ovsqlite-server(8).
