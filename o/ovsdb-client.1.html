NAME

ovsdb-client - command-line interface to ovsdb-server(1)

SYNOPSIS

Server-Level Commands:
ovsdb-client [options] list-dbs [server]
Database Schema Commands:
ovsdb-client [options] get-schema [server] [database]
ovsdb-client [options] list-tables [server] [database]
ovsdb-client [options] list-columns [server] [database] [table]
Database Version Management Commands:
ovsdb-client [options] convert [server] schema
ovsdb-client [options] needs-conversion [server] schema
ovsdb-client [options] get-schema-version [server] [database]
Data Management Commands:
ovsdb-client [options] transact [server] transaction
ovsdb-client [options] query [server] transaction
ovsdb-client [options] dump [server] [database] [table [column...]]
ovsdb-client [options] backup [server] [database] > snapshot
ovsdb-client [options] [--force] restore [server] [database] < snapshot
ovsdb-client [options] monitor [server] [database] table [column[,column]...]...
ovsdb-client [options] monitor [server] [database] ALL
ovsdb-client [options] monitor-cond [server] [database] conditions table [column[,column]...]...
ovsdb-client [options] monitor-cond-since [server] [database] [last-id] conditions table [column[,column]...]...
ovsdb-client [options] wait [server] database state

ovsdb-client [options] lock [server] lock
ovsdb-client [options] steal [server] lock

Other Commands:
ovsdb-client help

Output formatting options:
[--format=format] [--data=format] [--no-headings] [--pretty] [--bare] [--timestamp]
Daemon options:
[--pidfile[=pidfile]] [--overwrite-pidfile] [--detach] [--no-chdir] [--no-self-confinement]
Logging options:
[-v[module[:destination[:level]]]]...
[--verbose[=module[:destination[:level]]]]...
[--log-file[=file]]
Public key infrastructure options:
[--private-key=privkey.pem]
[--certificate=cert.pem]
[--ca-cert=cacert.pem]
[--bootstrap-ca-cert=cacert.pem]
SSL/TLS connection options:
[--ssl-protocols=protocols]
[--ssl-ciphers=ciphers]
[--ssl-ciphersuites=ciphersuites]
Replay options:
[--record[=directory]] [--replay[=directory]]
Common options:
[-h | --help] [-V | --version]

DESCRIPTION

The ovsdb-client program is a command-line client for interacting with a running ovsdb-server process. Each command connects to the specified OVSDB server, which may be an OVSDB active or passive connection method, as described in ovsdb(7). The default server is unix:/run/openvswitch/db.sock and the default database is Open_vSwitch.

ovsdb-client supports the method1,method2,...,methodN syntax described in ovsdb(7) for connecting to a cluster. When this syntax is used, ovsdb-client tries the cluster members in random order until it finds the cluster leader. Specify the --no-leader-only option to instead accept any server that is connected to the cluster.

For an introduction to OVSDB and its implementation in Open vSwitch, see ovsdb(7).

The following sections describe the commands that ovsdb-client supports.

Server-Level Commands

Most ovsdb-client commands work with an individual database, but these commands apply to an entire database server.

list-dbs [server]
Connects to server, retrieves the list of known databases, and prints them one per line. These database names are the ones that other commands may use for database.

Database Schema Commands

These commands obtain the schema from a database and print it or part of it.

get-schema [server] [database]
Connects to server, retrieves the schema for database, and prints it in JSON format.
list-tables [server] [database]
Connects to server, retrieves the schema for database, and prints a table listing the name of each table within the database.
list-columns [server] [database] table
Connects to server, retrieves the schema for database, and prints a table listing the name and type of each column. If table is specified, only columns in that table are listed; otherwise, the tables include columns in all tables.

Database Version Management Commands

An OVSDB schema has a schema version number, and an OVSDB database embeds a particular version of an OVSDB schema. These version numbers take the form x.y.z, e.g. 1.2.3. The OVSDB implementation does not enforce a particular version numbering scheme, but schemas managed within the Open vSwitch project use the following approach. Whenever the database schema is changed in a non-backward compatible way (e.g. deleting a column or a table), x is incremented (and y and z are reset to 0). When the database schema is changed in a backward compatible way (e.g. adding a new column), y is incremented (and z is reset to 0). When the database schema is changed cosmetically (e.g. reindenting its syntax), z is incremented.

Some OVSDB databases and schemas, especially very old ones, do not have a version number.

Schema version numbers and Open vSwitch version numbers are independent.

These commands work with different versions of OVSDB schemas and databases.

convert [server] schema
Connects to server and attempts to convert the schema for database to the version specified by schema. This command is useful for upgrading databases. The schema must be a JSON file that describes the target schema.
needs-conversion [server] schema
Connects to server and determines whether the schema for database needs to be converted to the version specified by schema. Prints a non-zero exit status if conversion is needed, and a zero exit status otherwise. This command is useful in scripts that need to perform conversions automatically.
get-schema-version [server] [database]
Connects to server, retrieves the schema for database, and prints its version string. Prints a non-zero exit status if the database does not have a version string.

Data Management Commands

transact [server] transaction
Executes an OVSDB transaction. The transaction must be a JSON array specifying the operations to execute. The results of the transaction are printed in JSON format. See ovsdb(7) for details on the transaction syntax.
query [server] transaction
Similar to transact, but only performs read operations. This can be used to query the database without modifying it.
dump [server] [database] [table [column...]]
Dumps the contents of table in database on server. If columns are specified, only those columns are dumped. If table is omitted, all tables are dumped. By default, dumps are printed in JSON format. Use --bare, --format, and --data to obtain plain-text output.
backup [server] [database] > snapshot
Creates a backup (snapshot) of database on server and writes it to standard output. The snapshot is a JSON array of JSON objects, where each object represents a row in the database. The format is described in the Open vSwitch manual.
restore [server] [database] < snapshot
Restores database on server from a backup file (snapshot) read from standard input. The --force option may be used to overwrite the existing database without confirmation. This command should only be used when the database is not in use by any clients.
monitor [server] [database] table [column[,column]...]...
monitor [server] [database] ALL
Monitors table in database on server for changes. If columns are specified, only those columns are monitored. If ALL is specified, all tables are monitored. This command prints a JSON array containing the initial state of the monitored tables, followed by a stream of JSON objects representing changes to the database. This command is useful for applications that need to stay up-to-date with the database state.
monitor-cond [server] [database] conditions table [column[,column]...]...
Monitors table in database on server for changes that satisfy the given conditions. The conditions are specified as a JSON array of strings, where each string is a condition in the OVSDB expression language. This command prints the same output as monitor, but only includes rows that satisfy the conditions.
monitor-cond-since [server] [database] [last-id] conditions table [column[,column]...]...
Monitors table in database on server for changes that satisfy the given conditions, starting from a specific change identifier (last-id). This command is useful for resuming monitoring after a disconnection.
wait [server] database state
Waits until database on server reaches the specified state. The state should be one of the following:
stable
Wait until the database is stable (no pending transactions).
connected
Wait until the database is connected.
disconnected
Wait until the database is disconnected.

Testing Commands

These commands are useful for testing OVSDB client applications and provide an interface to OVSDB's distributed locking mechanism.

lock [server] lock
Acquires the distributed lock named lock on server. If the lock is already held by another client, this command blocks until the lock is released. The lock is released when the client disconnects or when unlock is called.
steal [server] lock
Acquires the distributed lock named lock on server, even if it is currently held by another client. This will cause the other client to lose the lock, which may cause it to terminate or enter a degraded state.
unlock [server] lock
Releases the distributed lock named lock on server. This command should only be used if the lock was previously acquired by the same client.

Other Commands

help
Prints a list of available commands and their descriptions.

Options

Cluster Options:
--no-leader-only: Normally, ovsdb-client connects only to the leader of an OVSDB cluster. This option allows it to connect to any server in the cluster, even if it is not the leader.
Output formatting options:
--format=format: Specifies the output format. Possible values are json, table, and line. The default is json.
--data=format: Specifies the data format for the dump command. Possible values are json and line. The default is json.
--no-headings: Suppresses the printing of table headings.
--pretty: Prints JSON output in a human-readable format.
--bare: Prints output in a compact, machine-readable format. For tables, this means printing only the data, without any extra formatting.
--timestamp: Prepends a timestamp to each line of output.
Daemon options:
--pidfile[=pidfile]: Creates a PID file containing the process ID of the client. If pidfile is not specified, the PID file will be created in the OVS runtime directory.
--overwrite-pidfile: Overwrite an existing PID file.
--detach: Detaches the client process from the terminal and runs it in the background.
--no-chdir: Do not change the working directory when detaching.
--no-self-confinement: Disables various self-confinement mechanisms, such as changing the working directory and dropping privileges.
Logging options:
-v[module[:destination[:level]]]
--verbose[=module[:destination[:level]]]
These options enable logging. module specifies the module to log, destination specifies where to log (e.g. console, syslog, file), and level specifies the logging level (e.g. dbg, info, warn, err). If no module is specified, all modules are logged. If no destination is specified, console is used. If no level is specified, info is used.
--log-file[=file]: Logs to the specified file instead of the console or syslog.
Public key infrastructure options:
--private-key=privkey.pem: Specifies the private key file for SSL/TLS connections.
--certificate=cert.pem: Specifies the certificate file for SSL/TLS connections.
--ca-cert=cacert.pem: Specifies the CA certificate file for SSL/TLS connections.
--bootstrap-ca-cert=cacert.pem: Specifies the CA certificate file for bootstrapping SSL/TLS connections. This option is used when the server's certificate is not yet signed by a trusted CA.
SSL/TLS connection options:
--ssl-protocols=protocols: Specifies the SSL/TLS protocols to use (e.g. TLSv1.2,TLSv1.3).
--ssl-ciphers=ciphers: Specifies the SSL/TLS ciphers to use (e.g. high:!aNULL:!MD5).
--ssl-ciphersuites=ciphersuites: Specifies the SSL/TLS cipher suites to use (e.g. TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256).
Replay options:
--record[=directory]: Records all client communication to the specified directory. If directory is not specified, it defaults to the current directory.
--replay[=directory]: Replays client communication from the specified directory. If directory is not specified, it defaults to the current directory.
Common options:
-h | --help: Prints a help message and exits.
-V | --version: Prints version information and exits.

EXIT STATUS

Returns 0 on success, a non-zero value on failure.

Ces commandes sont principalement destinées à tester l'exactitude du serveur OVSDB.

lock [serveur] verrou

steal [serveur] verrou

unlock [serveur] verrou
Se connecte à serveur et émet les opérations de verrouillage RFC 7047 correspondantes sur verrou. Affiche la réponse json ou les messages de mise à jour suivants. L'option --detach fait en sorte que ovsdb-client se détache après avoir reçu et affiché avec succès la réponse initiale.
Lorsqu'elles sont exécutées avec l'option --detach, les commandes lock, steal, unlock et exit peuvent être émises à l'aide de ovs-appctl. La commande exit amène ovsdb-client à fermer sa connexion ovsdb-server avant de quitter. Les commandes lock, steal et unlock peuvent être utilisées pour émettre des opérations de verrouillage supplémentaires sur la même connexion ovsdb-server. Toutes les commandes ci-dessus prennent un seul argument verrou, qui n'a pas besoin d'être le même que le verrou avec lequel ovsdb-client a démarré.

OPTIONS

Options de formatage de la sortie

Une grande partie de la sortie de ovsdb-client se présente sous forme de tableaux. Les options suivantes contrôlent le formatage de la sortie :

-f format

--format=format
Définit le type de formatage du tableau. Les types de format suivants sont disponibles :
table (par défaut)
Tableaux texte 2D avec des colonnes alignées.
list
Une liste avec une colonne par ligne et des lignes séparées par une ligne vide.
html
Tableaux HTML.
csv
Valeurs séparées par des virgules telles que définies dans la RFC 4180.
json
Format JSON tel que défini dans la RFC 4627. La sortie est une séquence d'objets JSON, chacun correspondant à un tableau. Chaque objet JSON a les membres suivants avec les valeurs indiquées :
caption
La légende du tableau. Ce membre est omis si le tableau n'a pas de légende.
headings
Un tableau avec un élément par colonne de tableau. Chaque élément du tableau est une chaîne de caractères donnant l'en-tête de la colonne correspondante.
data
Un tableau avec un élément par ligne de tableau. Chaque élément est également un tableau avec un élément par colonne de tableau. Les éléments de ce tableau de second niveau sont les cellules qui constituent le tableau. Les cellules qui représentent des données ou des types de données OVSDB sont exprimées dans le format décrit dans la spécification OVSDB ; les autres cellules sont simplement exprimées sous forme de chaînes de caractères.
-d format

--data=format
Définit le formatage des cellules dans les tableaux de sortie, sauf si le format du tableau est défini sur json, auquel cas le formatage json est toujours utilisé pour le formatage des cellules. Les types de format suivants sont disponibles :
string (par défaut)
Le format simple décrit dans la section Valeurs de la base de données de ovs-vsctl(8).
bare
Le format simple avec la ponctuation supprimée : [] et {} sont omis autour des ensembles, des cartes et des colonnes vides, les éléments dans les ensembles et les cartes sont séparés par des espaces, et les chaînes ne sont jamais mises entre guillemets. Ce format peut être plus facile à analyser pour les scripts.
json
Le format JSON RFC 4627 tel que décrit ci-dessus.
--no-headings
Cette option supprime la ligne d'en-tête qui apparaît autrement dans la première ligne de la sortie du tableau.
--pretty
Par défaut, le JSON dans la sortie est imprimé de manière aussi compacte que possible. Cette option fait en sorte que le JSON dans la sortie soit imprimé d'une manière plus lisible. Les membres des objets et les éléments des tableaux sont imprimés un par ligne, avec une indentation.
Cette option n'affecte pas le JSON dans les tableaux, qui est toujours imprimé de manière compacte.
--bare
Équivalent à --format=list --data=bare --no-headings.
--max-column-width=n
Pour la sortie de type tableau uniquement, limite la largeur de toute colonne de sortie à n colonnes. Les données de cellules plus longues sont tronquées pour s'adapter, si nécessaire. Les colonnes sont toujours suffisamment larges pour afficher les noms de colonnes, si la ligne d'en-tête est imprimée.
--timestamp
Pour les commandes monitor, monitor-cond et monitor-cond-since, ajoutez un horodatage à chaque mise à jour de tableau. La plupart des formats de sortie ajoutent l'horodatage sur une ligne séparée juste au-dessus du tableau. Le format de sortie JSON place l'horodatage dans un membre de l'objet JSON de niveau supérieur nommé time.
-t

--timeout=secs
Limite l'exécution de ovsdb-client à environ secs secondes. Si le délai d'attente expire, ovsdb-client se terminera avec un signal SIGALRM.

Options de daemon

Les options de daemon s'appliquent uniquement aux commandes monitor, monitor-cond et monitor-cond-since. Avec toute autre commande, elles n'ont aucun effet.

Les options suivantes sont valides sur les plateformes basées sur POSIX.

--pidfile[=pidfile]
Crée un fichier (par défaut, ovsdb-client.pid) indiquant le PID du processus en cours d'exécution. Si l'argument pidfile n'est pas spécifié, ou s'il ne commence pas par /, il est créé dans /run/openvswitch.
Si --pidfile n'est pas spécifié, aucun fichier pid n'est créé.
--overwrite-pidfile
Par défaut, lorsque --pidfile est spécifié et que le fichier pid spécifié existe déjà et est verrouillé par un processus en cours d'exécution, ovsdb-client refuse de démarrer. Spécifiez --overwrite-pidfile pour qu'il écrase le fichier pid à la place.
Lorsque --pidfile n'est pas spécifié, cette option n'a aucun effet.
--detach
Exécute ovsdb-client en tant que processus d'arrière-plan. Le processus se divise, et dans l'enfant, il démarre une nouvelle session, ferme les descripteurs de fichiers standards (ce qui a pour effet de désactiver la journalisation sur la console) et change son répertoire courant pour la racine (sauf si --no-chdir est spécifié). Une fois que l'enfant a terminé son initialisation, le parent se termine.
--monitor
Crée un processus supplémentaire pour surveiller le daemon ovsdb-client. Si le daemon meurt à cause d'un signal indiquant une erreur de programmation (SIGABRT, SIGALRM, SIGBUS, SIGFPE, SIGILL, SIGPIPE, SIGSEGV, SIGXCPU ou SIGXFSZ), le processus de surveillance démarre une nouvelle copie de celui-ci. Si le daemon meurt ou se termine pour une autre raison, le processus de surveillance se termine.
Cette option est normalement utilisée avec --detach, mais elle fonctionne aussi sans elle.
--no-chdir
Par défaut, lorsque --detach est spécifié, ovsdb-client change son répertoire de travail courant vers le répertoire racine après s'être détaché. Sinon, l'invocation de ovsdb-client depuis un répertoire choisi imprudemment empêcherait l'administrateur de démonter le système de fichiers qui contient ce répertoire.
La spécification de --no-chdir supprime ce comportement, empêchant ovsdb-client de changer son répertoire de travail courant. Cela peut être utile pour collecter des fichiers core, car il est courant d'écrire des dumps core dans le répertoire de travail courant et le répertoire racine n'est pas un bon répertoire à utiliser.
Cette option n'a aucun effet lorsque --detach n'est pas spécifié.
--no-self-confinement
Par défaut, le daemon essaie de se confiner pour travailler avec des fichiers sous des répertoires bien connus déterminés lors de la compilation. Il est préférable de s'en tenir à ce comportement par défaut et de ne pas utiliser ce drapeau, sauf si une autre mesure de contrôle d'accès est utilisée pour confiner le daemon. Notez que contrairement à d'autres implémentations de contrôle d'accès qui sont généralement appliquées depuis le noyau (par exemple, DAC ou MAC), l'auto-confinement est imposé par le daemon de l'espace utilisateur lui-même et ne doit donc pas être considéré comme une stratégie de confinement complète, mais plutôt comme une couche de sécurité supplémentaire.
--user
Fait en sorte que ovsdb-client s'exécute sous un utilisateur différent spécifié dans "utilisateur:groupe", abandonnant ainsi la plupart des privilèges root. Les formes courtes "utilisateur" et ":groupe" sont également autorisées, avec l'utilisateur ou le groupe actuel présumé respectivement. Seuls les daemons démarrés par l'utilisateur root acceptent cet argument.
Sur Linux, les daemons recevront CAP_IPC_LOCK et CAP_NET_BIND_SERVICES avant d'abandonner les privilèges root. Les daemons qui interagissent avec un datapath, tels que ovs-vswitchd, se verra accorder trois capacités supplémentaires, à savoir CAP_NET_ADMIN, CAP_NET_BROADCAST et CAP_NET_RAW. La modification des capacités s'appliquera même si le nouvel utilisateur est root.
Sous Windows, cette option n'est pas prise en charge actuellement. Pour des raisons de sécurité, la spécification de cette option empêchera le démarrage du processus démon.

Options de journalisation

-v[spéc]

--verbose=[spéc]
Définit les niveaux de journalisation. Sans aucun spéc, définit le niveau de journalisation pour chaque module et destination sur dbg. Sinon, spéc est une liste de mots séparés par des espaces, des virgules ou des deux-points, au plus un de chaque catégorie ci-dessous :
  • Un nom de module valide, tel qu'affiché par la commande vlog/list sur ovs-appctl(8), limite la modification du niveau de journalisation au module spécifié.
  • syslog, console ou file, pour limiter la modification du niveau de journalisation uniquement au journal système, à la console ou à un fichier, respectivement. (Si --detach est spécifié, ovsdb-client ferme ses descripteurs de fichiers standard, de sorte que la journalisation sur la console n'aura aucun effet.)
Sur la plateforme Windows, syslog est accepté comme mot et n'est utile qu'avec l'option --syslog-target (le mot n'a aucun effet autrement).
•
off, emer, err, warn, info ou dbg, pour contrôler le niveau de journalisation. Les messages de la gravité donnée ou supérieure seront enregistrés, et les messages de gravité inférieure seront filtrés. off filtre tous les messages. Voir ovs-appctl(8) pour une définition de chaque niveau de journalisation.
La casse n'est pas significative dans spéc.
Indépendamment des niveaux de journalisation définis pour file, la journalisation dans un fichier n'aura lieu que si --log-file est également spécifié (voir ci-dessous).
Pour la compatibilité avec les anciennes versions d'OVS, any est accepté comme mot mais n'a aucun effet.
-v

--verbose
Définit le niveau de verbosité de journalisation maximal, équivalent à --verbose=dbg.
-vPATTERN:destination:modèle

--verbose=PATTERN:destination:modèle
Définit le modèle de journalisation pour destination sur modèle. Reportez-vous à ovs-appctl(8) pour une description de la syntaxe valide pour modèle.
-vFACILITY:facility

--verbose=FACILITY:facility
Définit la fonctionnalité RFC5424 du message de journalisation. facility peut être l'une des suivantes : kern, user, mail, daemon, auth, syslog, lpr, news, uucp, clock, ftp, ntp, audit, alert, clock2, local0, local1, local2, local3, local4, local5, local6 ou local7. Si cette option n'est pas spécifiée, daemon est utilisé par défaut pour le syslog système local et local0 est utilisé lors de l'envoi d'un message à la cible fournie via l'option --syslog-target.
--log-file[=fichier]
Active la journalisation dans un fichier. Si fichier est spécifié, il est utilisé comme nom exact du fichier journal. Le nom de fichier journal par défaut utilisé si fichier est omis est /var/log/openvswitch/ovsdb-client.log.
--syslog-target=hôte:port
Envoie les messages syslog au port UDP sur hôte, en plus du syslog système. L'hôte doit être une adresse IP numérique, pas un nom d'hôte.
--syslog-method=méthode
Spécifie la méthode par laquelle les messages syslog doivent être envoyés au démon syslog. Les formes suivantes sont prises en charge :
  • libc, utilise la fonction syslog() de libc. L'inconvénient de l'utilisation de cette option est que libc ajoute un préfixe fixe à chaque message avant qu'il ne soit réellement envoyé au démon syslog via un socket de domaine UNIX /dev/log.
  • unix:fichier, utilise directement un socket de domaine UNIX. Il est possible de spécifier un format de message arbitraire avec cette option. Cependant, rsyslogd versions 8.9 et antérieures utilise de toute façon une fonction d'analyse codée en dur qui limite l'utilisation des sockets de domaine UNIX. Si vous souhaitez utiliser un format de message arbitraire avec les anciennes versions de rsyslogd, utilisez plutôt un socket UDP vers l'adresse IP de localhost.
  • udp:ip:port, utilise un socket UDP. Avec cette méthode, il est possible d'utiliser un format de message arbitraire également avec les anciennes versions de rsyslogd. Lors de l'envoi de messages syslog sur un socket UDP, des précautions supplémentaires doivent être prises en compte, par exemple, le démon syslog doit être configuré pour écouter sur le port UDP spécifié, des règles iptables accidentelles pourraient interférer avec le trafic syslog local et il existe certaines considérations de sécurité qui s'appliquent aux sockets UDP, mais pas aux sockets de domaine UNIX.
  • null, rejette tous les messages journalisés dans syslog.
La valeur par défaut est prise à partir de la variable d'environnement OVS_SYSLOG_METHOD ; si elle n'est pas définie, la valeur par défaut est libc.

Options d'infrastructure à clé publique

-p clef_privee.pem

--private-key=clef_privee.pem
Spécifie un fichier PEM contenant la clé privée utilisée comme identité de ovsdb-client pour les connexions SSL/TLS sortantes.
-c certificat.pem

--certificate=certificat.pem
Spécifie un fichier PEM contenant un certificat qui certifie que la clé privée spécifiée avec -p ou --private-key est digne de confiance. Le certificat doit être signé par l'autorité de certification (AC) que le pair dans les connexions SSL/TLS utilisera pour le vérifier.
-C cert_ac.pem

--ca-cert=cert_ac.pem
Spécifie un fichier PEM contenant le certificat AC que ovsdb-client doit utiliser pour vérifier les certificats qui lui sont présentés par les pairs SSL/TLS. (Il peut s'agir du même certificat que celui que les pairs SSL/TLS utilisent pour vérifier le certificat spécifié avec -c ou --certificate, ou d'un certificat différent, selon la conception de l'infrastructure à clé publique utilisée.)
-C none

--ca-cert=none
Désactive la vérification des certificats présentés par les pairs SSL/TLS. Cela introduit un risque de sécurité, car cela signifie que les certificats ne peuvent pas être vérifiés comme appartenant à des hôtes de confiance connus.
--bootstrap-ca-cert=cert_ac.pem
Lorsque cert_ac.pem existe, cette option a le même effet que -C ou --ca-cert. S'il n'existe pas, ovsdb-client tentera d'obtenir le certificat AC du pair SSL/TLS lors de sa première connexion SSL/TLS et l'enregistrera dans le fichier PEM nommé. S'il réussit, il abandonnera immédiatement la connexion et se reconnectera, et à partir de ce moment, toutes les connexions SSL/TLS devront être authentifiées par un certificat signé par le certificat AC ainsi obtenu.
Cette option expose la connexion SSL/TLS à une attaque de l'homme du milieu lors de l'obtention du certificat AC initial, mais elle peut être utile pour l'amorçage.
Cette option n'est utile que si le pair SSL/TLS envoie son certificat AC dans le cadre de la chaîne de certificats SSL/TLS. Les protocoles SSL/TLS n'exigent pas que le serveur envoie le certificat AC.
Cette option est mutuellement exclusive avec -C et --ca-cert.

Options de connexion SSL/TLS

--ssl-protocols=protocoles
Spécifie une plage ou une liste de protocoles SSL/TLS délimitée par des virgules ou des espaces que ovsdb-client activera pour les connexions SSL/TLS. Les protocoles pris en charge incluent TLSv1 (obsolète), TLSv1.1 (obsolète), TLSv1.2 et TLSv1.3. Les plages peuvent être fournies sous la forme de deux noms de protocoles séparés par un tiret, ou comme un seul nom de protocole avec un signe plus. Par exemple, utilisez TLSv1.1-TLSv1.3 pour autoriser TLSv1.1, TLSv1.2 et TLSv1.3. Utilisez TLSv1.2+ pour autoriser TLSv1.2 et tout protocole ultérieur. L'option accepte une liste de protocoles ou exactement une plage. La plage est le moyen préféré de spécifier les protocoles et l'option se comporte toujours comme si la plage entre la version minimale et maximale spécifiée était fournie, c'est-à-dire, si l'option est définie sur TLSv1.1,TLSv1.3, TLSv1.2 sera également activé comme s'il s'agissait d'une plage. Indépendamment de l'ordre, le protocole le plus élevé pris en charge par les deux parties sera choisi lors de l'établissement de la connexion. La valeur par défaut lorsque cette option est omise est TLSv1.2 ou une version ultérieure.
--ssl-ciphers=chiffrements
Spécifie, au format de chaîne de chiffrements OpenSSL, les chiffrements que ovsdb-client prendra en charge pour les connexions SSL/TLS avec TLSv1.2 et les versions antérieures. La valeur par défaut lorsque cette option est omise est DEFAULT:@SECLEVEL=2.
--ssl-ciphersuites=suites_chiffrement
Spécifie, au format de chaîne de suites de chiffrement OpenSSL, les suites de chiffrement que ovsdb-client prendra en charge pour les connexions SSL/TLS avec TLSv1.3 et les versions ultérieures. La valeur par défaut d'OpenSSL sera be used when this option is omitted.

Autres options

--record[=répertoire]
Met le processus en mode "enregistrement", dans lequel il enregistrera toutes les connexions, les données provenant des flux (sockets de domaine Unix et réseau) et d'autres éléments importants nécessaires, afin qu'ils puissent être rejoués plus tard. Les données enregistrées sont stockées dans des fichiers de relecture dans le répertoire spécifié. Si répertoire ne commence pas par /, il est interprété comme relatif à /run/openvswitch. Si répertoire n'est pas spécifié, /run/openvswitch sera utilisé.
--replay[=répertoire]
Met le processus en mode "relecture", dans lequel il lira les informations sur les connexions, les données provenant des flux (sockets de domaine Unix et réseau) et d'autres éléments nécessaires directement à partir des fichiers de relecture au lieu d'utiliser de vrais sockets. Les fichiers de relecture du répertoire seront utilisés. Si répertoire ne commence pas par /, il est interprété comme relatif à /run/openvswitch. Si répertoire n'est pas spécifié, /run/openvswitch sera utilisé.
-h

--help
Affiche un bref message d'aide sur la console.
-V

--version
Affiche les informations de version sur la console.
