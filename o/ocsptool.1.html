ocsptool(1) Commandes utilisateur ocsptool(1)

NOM

ocsptool - Outil OCSP GnuTLS

SYNOPIS

ocsptool [-indicateurs] [-indicateur [valeur]] [--nom-option[[=| ]valeur]]

Tous les arguments doivent être des options.

DESCRIPTION

Lors de la vérification
Les réponses sont généralement signées/émises par des certificats désignés ou des autorités de certification et donc cet outil nécessite, lors de la vérification, le certificat de l'émetteur ou la chaîne de certificats complète afin de déterminer l'autorité de signature appropriée. Le certificat spécifié de l'émetteur est supposé fiable.

OPTIONS

-d num, --debug=num

Active le débogage. Cette option prend un nombre entier comme argument. La valeur de num est contrainte d'être : 
dans la plage 0 à 9999

Spécifie le niveau de débogage.

-V, --verbose

Sortie plus détaillée.
--infile=fichier

Fichier d'entrée.
--outfile=str

Fichier de sortie.
--ask=nom_serveur|url

Interroge un serveur OCSP/HTTP sur la validité d'un certificat.

Se connecte au serveur OCSP HTTP spécifié et interroge la validité du certificat chargé. Son argument peut être une URL ou un simple nom de serveur. Il peut être combiné avec --load-chain, où il vérifie tous les certificats de la chaîne fournie, ou avec les options --load-cert et --load-issuer. Ces dernières vérifient le certificat fourni par rapport à son émetteur spécifié.

-e, --verify-response

Vérifie la réponse.

Vérifie la réponse OCSP fournie par rapport aux points d'ancrage de confiance du système (sauf si --load-trust est fourni). Elle nécessite les options --load-signer ou --load-chain pour obtenir le signataire de la réponse OCSP.

-i, --request-info

Affiche des informations sur une requête OCSP.

Affiche des informations détaillées sur la requête OCSP fournie.

-j, --response-info

Affiche des informations sur une réponse OCSP.

Affiche des informations détaillées sur la réponse OCSP fournie.

-q, --generate-request

Génère une requête OCSP.
--nonce, --no-nonce

Utilise (ou non) un nonce pour la requête OCSP. La forme no-nonce désactive l'option.
--load-chain=fichier

Lit un ensemble de certificats formant une chaîne depuis le fichier.
--load-issuer=fichier

Lit le certificat de l'émetteur depuis le fichier.
--load-cert=fichier

Lit le certificat à vérifier depuis le fichier.
--load-trust=fichier

Lit les points d'ancrage de confiance OCSP depuis le fichier. Cette option ne doit pas apparaître en combinaison avec aucune des options suivantes : load-signer.

Lors de la vérification d'une réponse OCSP, lit les points d'ancrage de confiance depuis le fichier fourni. Si ce n'est pas fourni, les points d'ancrage de confiance du système seront utilisés.

--load-signer=fichier

Lit le signataire de la réponse OCSP depuis le fichier. Cette option ne doit pas apparaître en combinaison avec aucune des options suivantes : load-trust.
--inder, --no-inder

Utilise le format DER pour les certificats d'entrée et les clés privées. La forme no-inder désactive l'option.
--outder

Utilise le format DER pour la sortie des réponses (c'est le défaut).

La sortie sera au format encodé DER. Contrairement aux autres outils GnuTLS, c'est le comportement par défaut de cet outil.

--outpem

Utilise le format PEM pour la sortie des réponses.

La sortie sera au format PEM.

-Q fichier, --load-request=fichier

Lit la requête OCSP encodée en DER depuis le fichier.
-S fichier, --load-response=fichier

Lit la réponse OCSP encodée en DER depuis le fichier.
--ignore-errors

Ignore toutes les erreurs de vérification.
--verify-allow-broken

Autorise les algorithmes brisés, tels que MD5 pour la vérification.

Cela peut être combiné avec --verify-response.

--attime=timestamp

Effectue la validation au timestamp spécifié au lieu de l'heure système.

Le timestamp est une instance temporelle encodée en temps Unix ou dans une chaîne temporelle lisible par l'homme telle que "29 Feb 2004", "2004-02-29". Documentation complète disponible à https://www.gnu.org/software/coreutils/manual/html_node/Date-input-formats.html ou localement via info '(coreutils) date invocation'.

-v arg, --version=arg

Affiche la version du programme et quitte. Le mode par défaut est `v', une simple version. Le mode `c' affichera les informations de copyright et `n' affichera la notice de copyright complète.
-h, --help

Affiche les informations d'utilisation et quitte.
-!, --more-help

Transmet les informations d'utilisation étendues via un paginator.

EXEMPLES

Afficher les informations sur une requête OCSP

Pour analyser une requête OCSP et afficher des informations sur son contenu, les paramètres -i ou --request-info peuvent être utilisés comme suit. Le paramètre -Q spécifie le nom du fichier contenant la requête OCSP, et il doit contenir la requête OCSP au format binaire DER.


$ ocsptool -i -Q ocsp-request.der

Le fichier d'entrée peut également être envoyé à l'entrée standard comme ceci :


$ cat ocsp-request.der | ocsptool --request-info

Afficher les informations sur une réponse OCSP

Semblable à l'analyse des requêtes OCSP, les réponses OCSP peuvent être analysées en utilisant -j ou --response-info comme suit.


$ ocsptool -j -Q ocsp-response.der
$ cat ocsp-response.der | ocsptool --response-info

Générer une requête OCSP

Les paramètres -q ou --generate-request sont utilisés pour générer une requête OCSP. Par défaut, la requête OCSP est écrite sur la sortie standard au format binaire DER, mais peut être stockée dans un fichier à l'aide de --outfile. Pour générer une requête OCSP, l'émetteur du certificat à vérifier doit être spécifié avec --load-issuer et le certificat à vérifier avec --load-cert. Par défaut, le format PEM est utilisé pour ces fichiers, bien que --inder puisse être utilisé pour spécifier que les fichiers d'entrée sont au format DER.


$ ocsptool -q --load-issuer issuer.pem --load-cert client.pem            --outfile ocsp-request.der

Lors de la génération de requêtes OCSP, l'outil ajoutera une extension OCSP contenant un nonce. Ce comportement peut être désactivé en spécifiant --no-nonce.

Vérifier la signature dans la réponse OCSP

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

>Pour vérifier la signature dans une réponse OCSP, le paramètre -e ou --verify-response est utilisé. L'outil lira une réponse OCSP au format DER depuis l'entrée standard, ou depuis le fichier spécifié par --load-response. La réponse OCSP est vérifiée par rapport à un ensemble d'ancres de confiance, qui sont spécifiées à l'aide de --load-trust. Les ancres de confiance sont des certificats concaténés au format PEM. Le certificat qui a signé la réponse OCSP doit faire partie de l'ensemble des ancres de confiance, ou l'émetteur du certificat signataire doit faire partie de l'ensemble des ancres de confiance et le bit Usage Étendu OCSP doit être affirmé dans le certificat signataire.


$ ocsptool -e --load-trust issuer.pem --load-response ocsp-response.der

L'outil affichera le statut de la vérification.

Vérifier la signature dans la réponse OCSP par rapport à un certificat donné

Il est possible de remplacer la logique de confiance normale si vous savez qu'un certain certificat est censé avoir signé la réponse OCSP et que vous souhaitez l'utiliser pour vérifier la signature. Ceci est réalisé en utilisant --load-signer au lieu de --load-trust. Cela chargera un certificat qui sera utilisé pour vérifier la signature dans la réponse OCSP. Il ne vérifiera pas le bit Usage Étendu.


$ ocsptool -e --load-signer ocsp-signer.pem --load-response ocsp-response.der

Cette approche n'est normalement pertinente que dans deux situations. La première est lorsque la réponse OCSP ne contient pas une copie du certificat signataire, de sorte que le code --load-trust échouerait. La seconde est si vous souhaitez éviter le mode indirect où le certificat signataire de la réponse OCSP est signé par une ancre de confiance.

Exemple concret

Voici un exemple de la façon de générer une requête OCSP pour un certificat et de vérifier la réponse. Pour l'illustration, nous utiliserons l'hôte blog.josefsson.org, qui (au moment de la rédaction) utilise un certificat de CACert. Nous utiliserons d'abord gnutls-cli pour obtenir une copie de la chaîne de certificats du serveur. Le serveur n'est pas obligé d'envoyer ces informations, mais celui-ci particulier est configuré pour le faire.


$ echo | gnutls-cli -p 443 blog.josefsson.org --save-cert chain.pem

Les certificats enregistrés contiennent normalement un pointeur vers l'emplacement du répondeur OCSP, dans l'extension d'informations d'accès d'autorité. Par exemple, à partir de certtool -i < chain.pem, on trouve ces informations :


		Authority Information Access Information (not critical):
			Access Method: 1.3.6.1.5.5.7.48.1 (id-ad-ocsp)
			Access Location URI: https://ocsp.CAcert.org/

Cela signifie que ocsptool peut découvrir les serveurs à contacter par HTTP. Nous pouvons maintenant demander des informations sur les certificats de la chaîne.


$ ocsptool --ask --load-chain chain.pem

La requête est envoyée via HTTP à l'adresse du serveur OCSP trouvée dans les certificats. Il est possible de remplacer l'adresse du serveur OCSP ainsi que de demander des informations sur un certificat particulier en utilisant --load-cert et --load-issuer.


$ ocsptool --ask https://ocsp.CAcert.org/ --load-chain chain.pem

STATUT DE SORTIE

L'une des valeurs de sortie suivantes sera retournée :

0 (EXIT_SUCCESS)

Exécution réussie du programme.
1 (EXIT_FAILURE)

L'opération a échoué ou la syntaxe de la commande était invalide.
