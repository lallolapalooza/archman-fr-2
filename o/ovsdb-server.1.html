NOM

ovsdb-server - Serveur de base de données Open vSwitch

SYNTAXE

ovsdb-server [base_de_données]... [relais:nom_schéma:distant]... [--remote=distant]... [--config-file=fichier] [--run=commande]

Options démon :
[--pidfile[=fichier_pid]] [--overwrite-pidfile] [--detach] [--no-chdir] [--no-self-confinement]

[--service] [--service-monitor]
Options de journalisation :
[-v[module[:destination[:niveau]]]]...
[--verbose[=module[:destination[:niveau]]]]...
[--log-file[=fichier]]
Options sauvegarde active :
[--sync-from=serveur] [--sync-exclude-tables=db:table[,db:table]...] [--active]
Options infrastructure à clé publique :
[--private-key=clé_privée.pem]
[--certificate=certificat.pem]

Options communes :
[-h | --help] [-V | --version]

DESCRIPTION

Le programme ovsdb-server fournit des interfaces RPC à une ou plusieurs bases de données Open vSwitch (OVSDB). Il prend en charge les connexions clients JSON-RPC via des sockets TCP/IP ou de domaine Unix actifs ou passifs. Pour une introduction à OVSDB et à son implémentation dans Open vSwitch, consultez ovsdb(7).

Chaque fichier OVSDB peut être spécifié sur la ligne de commande comme base_de_données. Les bases de données relais peuvent être spécifiées sur la ligne de commande comme relais:nom_schéma:distant. Pour une description détaillée de l'argument de base de données relais, consultez ovsdb(7). Si aucun fichier de base de données ou base de données relais n'est spécifié, la valeur par défaut est /etc/openvswitch/conf.db. Les fichiers de base de données doivent avoir déjà été créés et initialisés en utilisant, par exemple, la commande create, create-cluster, ou join-cluster de ovsdb-tool.

Tous les types de bases de données peuvent alternativement être ajoutés en utilisant un fichier de configuration fourni via l'option --config-file. Cette option est mutuellement exclusive avec la spécification de base_de_données sur la ligne de commande. Pour une description détaillée du format du fichier de configuration, consultez ovsdb(7).

Cette implémentation OVSDB prend en charge les modèles de service de base de données autonomes, actif-sauvegarde, relais et groupés, ainsi que la réplication de base de données. Consultez la section Modèles de service de ovsdb(7) pour plus d'informations.

Pour les bases de données groupées, lorsque l'option --detach est utilisée, ovsdb-server se détache sans attendre que le serveur rejoigne avec succès un groupe (si le fichier de base de données est fraîchement créé avec ovsdb-tool join-cluster) ou se connecte à un groupe qu'il a déjà rejoint. Utilisez ovsdb-client wait (voir ovsdb-client(1)) pour attendre que le serveur ait rejoint et se soit connecté avec succès à un groupe. Il en va de même pour les bases de données relais. Les mêmes commandes peuvent être utilisées pour attendre qu'une base de données relais se connecte à la source relais (distante).

En plus des bases de données spécifiées par l'utilisateur, ovsdb-server version 2.9 et ultérieures héberge toujours une base de données intégrée nommée _Server. Veuillez consulter ovsdb-server(5) pour la documentation sur le schéma de cette base de données.

OPTIONS

--remote=distant
Ajoute distant comme méthode de connexion utilisée par ovsdb-server. Le distant peut être une méthode de connexion active ou passive OVSDB, par exemple pssl:6640, comme décrit dans ovsdb(7). La forme supplémentaire suivante est également prise en charge :
db:db,table,colonne
Lit les méthodes de connexion supplémentaires à partir de la colonne dans toutes les lignes de la table au sein de la db. Au fur et à mesure que le contenu de la colonne change, ovsdb-server ajoute et supprime également les méthodes de connexion en conséquence.
Si le type de la colonne est chaîne ou ensemble de chaînes, alors les méthodes de connexion sont prises directement de la colonne. Les méthodes de connexion dans la colonne doivent avoir l'une des formes décrites ci-dessus.
Si le type de la colonne est UUID ou ensemble d'UUID et référence une table, alors chaque UUID est recherché dans la table référencée pour obtenir une ligne. Les colonnes suivantes dans la ligne, si elles sont présentes et du bon type, configurent une méthode de connexion. Toutes les colonnes supplémentaires sont ignorées.
target (chaîne)
Méthode de connexion, dans l'une des formes décrites ci-dessus. Cette colonne est obligatoire : si elle est absente ou vide, aucune méthode de connexion ne peut être configurée.
max_backoff (entier)
Nombre maximum de millisecondes à attendre entre les tentatives de connexion.
inactivity_probe (entier)
Temps maximum d'inactivité sur la connexion au client avant d'envoyer un message de sonde d'inactivité.
read_only (booléen)
Si vrai, seules les transactions en lecture seule sont autorisées sur cette connexion.
C'est une erreur que la colonne ait un autre type.
Pour se connecter ou écouter sur plusieurs méthodes de connexion, utilisez plusieurs options --remote.
Alternativement, les remotes peuvent être spécifiés dans une section "remotes" du fichier de configuration, si fourni via l'option --config-file. Les options --config-file et --remote sont mutuellement exclusives.
--config-file=fichier
Spécifie un fichier de configuration pour ovsdb-server. Ce fichier peut contenir les méthodes de connexion et les bases de données utilisées par le serveur. Le fichier contient un objet JSON avec deux éléments principaux :
remotes
Objet JSON qui contient un ensemble de méthodes de connexion au format suivant : "cible": { "option": valeur, ... }. Où cible est dans le même format que distant dans l'option --remote. option peut être max-backoff (entier), inactivity-probe (entier), read-only (booléen), role (chaîne) ou dscp (entier) avec leurs valeurs autorisées respectivement. La signification de ces options est la même que dans la configuration de distant via une ligne de base de données avec l'option --remote.
databases
Objet JSON qui décrit les bases de données qui devraient être ajoutées à ovsdb-server dans le format suivant : "nom":{ "option": valeur, ... }. Où nom est soit un nom de fichier d'une base de données précédemment créée et initialisée, soit un nom de schéma dans le cas de bases de données relais. Les options disponibles sont :
service-mo
del (string)
Décrit le modèle de service de cette base de données. L'un des éléments suivants : standalone, clustered, active-backup ou relay. Cette option est requise pour tous les types, à l'exception de standalone et clustered. Pour ces bases de données, le modèle de service sera déduit du fichier, s'il n'est pas spécifié explicitement. ovsdb-server refusera d'ajouter une base de données si le service-model spécifié ne correspond pas au fichier fourni.
source (objet JSON ; active-backup ou relay)
Décrit la méthode de connexion à la base de données active ou à la source relais. C'est un objet JSON avec exactement un élément dans le même format que les éléments de "remotes", à l'exception du fait que les options read-only et role ne sont pas applicables. Par exemple : "source": { "unix:db.sock": { "inactivity-probe": 10000, "max-backoff": 8000 } }
backup (booléen ; active-backup uniquement)
S'il est défini sur true, ovsdb-server utilisera cette base de données comme sauvegarde pour la source spécifiée. Elle sera servie comme base de données active sinon.
exclude-tables (tableau JSON de chaînes ; active-backup uniquement)
Liste des noms de tables qui doivent être exclus de la réplication en mode sauvegarde, par exemple : "exclude-tables": [ "Table_One", "Table_Two" ].
Le contenu du fichier de configuration le plus basique peut ressembler à ceci : { "remotes": { "pssl:6640": {} }, "databases": { "conf.db": {} } }
Des exemples de fichiers de configuration pour différents modèles de service peuvent être trouvés dans ovsdb(7).
L'option --config-file est mutuellement exclusive avec --remote ainsi qu'avec la spécification de database sur la ligne de commande. Elle est également mutuellement exclusive avec toutes les Options Active-Backup et toutes les COMMANDES DE GESTION DES RUNTIMES qui peuvent modifier la configuration du serveur en conflit avec le contenu du fichier, c'est-à-dire toutes les commandes qui manipulent les remotes et les bases de données. Les commandes en lecture seule peuvent toujours être utilisées.
En cas de modifications dans le fichier, les utilisateurs doivent exécuter la commande ovsdb-server/reload avec ovs-appctl(8) pour que les modifications prennent effet.

--run=commande]
Normalement, ovsdb-server s'exécute indéfiniment, ou jusqu'à ce qu'il soit arrêté (voir COMMANDES DE GESTION DES RUNTIMES ci-dessous). Avec cette option, ovsdb-server démarre à la place un sous-processus shell exécutant commande. Lorsque le sous-processus se termine, ovsdb-server se termine également gracieusement. Si le sous-processus se termine normalement avec un code de sortie de 0, alors ovsdb-server se termine également avec un code de sortie de 0 ; sinon, il se termine avec un code de sortie de 1.
Cette option peut être utile lorsqu'un serveur de base de données n'est nécessaire que pour exécuter une seule commande, par exemple : ovsdb-server --remote=punix:socket --run='ovsdb-client dump unix:socket Open_vSwitch'
Cette option n'est pas prise en charge sur la plateforme Windows.

Options Daemon

Les options suivantes sont valides sur les plateformes basées sur POSIX.

--pidfile[=pidfile]
Crée un fichier (par défaut, ovsdb-server.pid) indiquant le PID du processus en cours d'exécution. Si l'argument pidfile n'est pas spécifié, ou s'il ne commence pas par /, il est créé dans /run/openvswitch.
Si --pidfile n'est pas spécifié, aucun fichier pid n'est créé.
--overwrite-pidfile
Par défaut, lorsque --pidfile est spécifié et que le fichier pid spécifié existe déjà et est verrouillé par un processus en cours d'exécution, ovsdb-server refuse de démarrer. Spécifiez --overwrite-pidfile pour qu'il écrase plutôt le fichier pid.
Lorsque --pidfile n'est pas spécifié, cette option n'a aucun effet.
--detach
Exécute ovsdb-server en tant que processus d'arrière-plan. Le processus se diviser, et dans l'enfant, il démarre une nouvelle session, ferme les descripteurs de fichiers standards (ce qui a pour effet de désactiver la journalisation sur la console) et change son répertoire courant pour la racine (sauf si --no-chdir est spécifié). Une fois que l'enfant a terminé son initialisation, le parent se termine. ovsdb-server se détache uniquement après avoir commencé à écouter sur toutes les remotes configurées. À ce stade, toutes les bases de données autonomes et active-backup sont prêtes à être utilisées. Les bases de données clusterisées ne deviennent prêtes à être utilisées qu'après avoir terminé leur jonction à leurs clusters (ce qui peut déjà s'être produit lors d'exécutions précédentes de ovsdb-server).
--monitor
Crée un processus supplémentaire pour surveiller le démon ovsdb-server. Si le démon meurt suite à un signal indiquant une erreur de programmation (SIGABRT, SIGALRM, SIGBUS, SIGFPE, SIGILL, SIGPIPE, SIGSEGV, SIGXCPU, ou SIGXFSZ), alors le processus de surveillance démarre une nouvelle copie de celui-ci. Si le démon meurt ou se termine pour une autre raison, le processus de surveillance se termine.
Cette option est normalement utilisée avec --detach, mais elle fonctionne également sans elle.
--no-chdir
Par défaut, lorsque --detach est spécifié, ovsdb-server change son répertoire de travail courant pour le répertoire racine après s'être détaché. Sinon, invoquer ovsdb-server depuis un répertoire choisi négligemment empêcherait l'administrateur de démonter le système de fichiers qui contient ce répertoire.
Spécifier --no-chdir supprime ce comportement, empêchant ovsdb-server de changer son répertoire de travail courant. Cela peut être utile pour collecter des fichiers core, car il est courant d'écrire des dumps core dans le répertoire de travail courant et le répertoire racine n'est pas un bon répertoire à utiliser.
Cette option n'a aucun effet lorsque --detach n'est pas spécifié.
--no-self-confinement
Par défaut, le démon tentera de s'auto-confiner pour travailler avec des fichiers sous des répertoires bien connus déterminés lors de la compilation. Il est préférable de s'en tenir à ce comportement par défaut et de ne pas utiliser ce drapeau à moins qu'une autre stratégie de contrôle d'accès ne soit utilisée pour confiner le démon. Notez qu'à la différence d'autres implémentations de contrôle d'accès qui sont généralement appliquées depuis l'espace noyau (par exemple, DAC ou MAC), l'auto-confinement est imposé par le démon dans l'espace utilisateur et ne doit donc pas être considéré comme une stratégie de confinement complète, mais plutôt comme une couche de sécurité supplémentaire.
--user
Fait en sorte que ovsdb-server s'exécute en tant qu'utilisateur différent spécifié dans "user:group", abandonnant ainsi la plupart des privilèges root. Les formes courtes "user" et ":group" sont également autorisées, avec l'utilisateur ou le groupe courant assumé respectivement. Seuls les démons démarrés par l'utilisateur root acceptent cet argument.
Sur Linux, les démons recevront CAP_IPC_LOCK et CAP_NET_BIND_SERVICES avant d'abandonner les privilèges root. Les démons qui interagissent avec un datapath, tels que ovs-vswitchd, recevront trois capacités supplémentaires, à savoir CAP_NET_ADMIN, CAP_NET_BROADCAST et CAP_NET_RAW. Le changement de capacité s'appliquera même si le nouvel utilisateur est root.
Sur Windows, cette option n'est pas prise en charge actuellement. Pour des raisons de sécurité, la spécification de cette option entraînera l'impossibilité de démarrer le processus démon.

Options de Service

Les options suivantes sont valides uniquement sur la plateforme Windows.

--service
Fait en sorte que ovsdb-server s'exécute en tant que service en arrière-plan. Le service doit déjà avoir été créé via des outils externes tels que SC.exe.
--service-monitor
Fait en sorte que le service ovsdb-server soit automatiquement redémarré par le gestionnaire de services Windows si le service meurt ou se termine pour des raisons inattendues.
Lorsque --service n'est pas spécifié, cette option n'a aucun effet.

Options de Journalisation

-v[spec]

--verbose=[spec]
Définit les niveaux de journalisation. Sans spec, définit le niveau de journalisation pour chaque module et destination sur dbg. Sinon, spec est une liste de mots séparés par des espaces, des virgules ou des deux-points, un seul mot de chaque catégorie ci-dessous :
  • Un nom de module valide, tel qu'affiché par la commande vlog/list sur ovs-appctl(8), limite la modification du niveau de journalisation au module spécifié.
  • syslog, console ou file, pour limiter la modification du niveau de journalisation uniquement au journal système, à la console ou à un fichier, respectivement. (Si --detach est spécifié, ovsdb-server ferme ses descripteurs de fichiers standards, donc la journalisation sur la console n'aura aucun effet.)
Sur la plateforme Windows, syslog est accepté comme mot et n'est utile qu'avec l'option --syslog-target (le mot n'a aucun effet autrement).
•
off, emer, err, warn, info ou dbg, pour contrôler le niveau de journalisation. Les messages de la gravité donnée ou supérieure seront journalisés, et les messages de gravité inférieure seront filtrés. off filtre tous les messages. Voir ovs-appctl(8) pour une définition de chaque niveau de journalisation.
La casse n'est pas significative dans spec.
Indépendamment des niveaux de journalisation définis pour file, lo
gging à un fichier n'aura lieu que si --log-file est également spécifié (voir ci-dessous).
Par compatibilité avec les anciennes versions d'OVS, any est accepté comme un mot mais n'a aucun effet.
-v

--verbose
Définit le niveau de verbosité maximal de la journalisation, équivalent à --verbose=dbg.
-vPATTERN:destination:pattern

--verbose=PATTERN:destination:pattern
Définit le modèle de journalisation pour destination sur pattern. Voir ovs-appctl(8) pour une description de la syntaxe valide pour pattern.
-vFACILITY:facility

--verbose=FACILITY:facility
Définit la facilité RFC5424 du message de journal. facility peut être l'un des éléments suivants : kern, user, mail, daemon, auth, syslog, lpr, news, uucp, clock, ftp, ntp, audit, alert, clock2, local0, local1, local2, local3, local4, local5, local6 ou local7. Si cette option n'est pas spécifiée, daemon est utilisé par défaut pour le syslog du système local et local0 est utilisé lors de l'envoi d'un message à la cible fournie via l'option --syslog-target.
--log-file[=fichier]
Active la journalisation dans un fichier. Si fichier est spécifié, il est utilisé comme nom exact du fichier journal. Le nom de fichier journal par défaut utilisé si fichier est omis est /var/log/openvswitch/ovsdb-server.log.
--syslog-target=hôte:port
Envoie les messages syslog au port UDP sur hôte, en plus du syslog système. L'hôte doit être une adresse IP numérique, pas un nom d'hôte.
--syslog-method=méthode
Spécifie la méthode par laquelle les messages syslog doivent être envoyés au démon syslog. Les formes suivantes sont prises en charge :
  • libc, utilise la fonction syslog() de libc. L'inconvénient de l'utilisation de cette option est que libc ajoute un préfixe fixe à chaque message avant qu'il ne soit effectivement envoyé au démon syslog via le socket de domaine UNIX /dev/log.
  • unix:fichier, utilise directement le socket de domaine UNIX. Il est possible de spécifier un format de message arbitraire avec cette option. Cependant, rsyslogd 8.9 et les versions antérieures utilisent de toute façon une fonction d'analyse codée en dur qui limite l'utilisation du socket de domaine UNIX. Si vous souhaitez utiliser un format de message arbitraire avec les anciennes versions de rsyslogd, utilisez plutôt un socket UDP vers l'adresse IP localhost.
  • udp:ip:port, utilise un socket UDP. Avec cette méthode, il est également possible d'utiliser un format de message arbitraire avec les anciennes versions de rsyslogd. Lors de l'envoi de messages syslog via un socket UDP, des précautions supplémentaires doivent être prises, par exemple, le démon syslog doit être configuré pour écouter sur le port UDP spécifié, des règles iptables accidentelles pourraient interférer avec le trafic syslog local et il existe certaines considérations de sécurité qui s'appliquent aux sockets UDP, mais pas aux sockets de domaine UNIX.
  • null, ignore tous les messages journalisés dans syslog.
La valeur par défaut est prise de la variable d'environnement OVS_SYSLOG_METHOD ; si elle n'est pas définie, la valeur par défaut est libc.

Options Active-Backup

Ces options prennent en charge le modèle de service active-backup d'ovsdb-server et la réplication de base de données. Ces options s'appliquent uniquement aux bases de données au format utilisé pour les bases de données autonomes et active-backup, qui est le format de base de données créé par ovsdb-tool create. Par défaut, lorsqu'il sert une base de données de ce format, ovsdb-server s'exécute comme un serveur autonome. Ces options peuvent le configurer pour une utilisation en mode active-backup :

  • Utilisez --sync-from=serveur pour démarrer le serveur dans le rôle de sauvegarde, en répliquant les données à partir de serveur. Lorsque ovsdb-server s'exécute en tant que serveur de sauvegarde, il rejette toutes les transactions susceptibles de modifier le contenu de la base de données, y compris les commandes de verrouillage. La même forme peut être utilisée pour configurer la base de données locale en tant que réplique de serveur.
  • Utilisez --sync-from=serveur --active pour démarrer le serveur dans le rôle actif, mais prêt à passer au rôle de sauvegarde dans lequel il répliquerait les données à partir de serveur. Lorsque ovsdb-server s'exécute en mode actif, il autorise toutes les transactions, y compris celles qui modifient la base de données.

À l'exécution, les commandes de gestion peuvent modifier le rôle d'un serveur et gérer d'autres fonctionnalités active-backup. Voir Commandes Active-Backup, ci-dessous, pour plus d'informations.

--sync-from=serveur
Configure ovsdb-server pour synchroniser ses bases de données avec les bases de données de serveur, qui doit être une méthode de connexion active sous l'une des formes décrites dans ovsdb-client(1). Chaque transaction validée par serveur sera répliquée vers ovsdb-server. Cette option fait démarrer ovsdb-server en tant que serveur de sauvegarde ; ajoutez --active pour qu'il démarre en tant que serveur actif.
--sync-exclude-tables=db:table[,db:table]...
Indique que les tables spécifiées doivent être exclues de la réplication.
--active
Par défaut, --sync-from fait démarrer ovsdb-server comme sauvegarde pour serveur. Avec --active, cependant, ovsdb-server démarre comme serveur actif. Utilisez cette option pour permettre la spécification des options de synchronisation via les options de ligne de commande, tout en démarrant le serveur, comme serveur actif par défaut. Pour passer le serveur en cours d'exécution en mode sauvegarde, utilisez ovs-appctl(1) pour exécuter la commande ovsdb-server/connect-active-ovsdb-server.

Ces options sont mutuellement exclusives avec --config-file.

Options d'Infrastructure de Clés Publiques

Les options décrites ci-dessous pour la configuration de l'infrastructure de clés publiques SSL acceptent une syntaxe spéciale pour obtenir leur configuration à partir de la base de données. Si l'une de ces options reçoit db:db,table,colonne comme argument, alors le nom de fichier réel est lu à partir de la colonne spécifiée dans table au sein de la base de données db. La colonne doit être de type chaîne de caractères ou ensemble de chaînes. La première chaîne non vide de la table est considérée comme le nom de fichier. (Cela signifie que, normalement, il ne devrait y avoir qu'une seule ligne dans table.)

-p clef_privee.pem

--private-key=clef_privee.pem
Spécifie un fichier PEM contenant la clé privée utilisée comme identité de ovsdb-server pour les connexions SSL/TLS sortantes.
-c cert.pem

--certificate=cert.pem
Spécifie un fichier PEM contenant un certificat qui certifie que la clé privée spécifiée sur -p ou --private-key est digne de confiance. Le certificat doit être signé par l'autorité de certification (AC) que le pair dans les connexions SSL/TLS utilisera pour le vérifier.
-C cert_ac.pem

--ca-cert=cert_ac.pem
Spécifie un fichier PEM contenant le certificat de l'AC que ovsdb-server doit utiliser pour vérifier les certificats qui lui sont présentés par les pairs SSL/TLS. (Il peut s'agir du même certificat que celui utilisé par les pairs SSL/TLS pour vérifier le certificat spécifié sur -c ou --certificate, ou il peut s'agir d'un certificat différent, en fonction de la conception de l'infrastructure PKI utilisée.)
-C none

--ca-cert=none
Désactive la vérification des certificats présentés par les pairs SSL/TLS. Cela introduit un risque de sécurité, car cela signifie que les certificats ne peuvent pas être vérifiés comme appartenant à des hôtes connus et fiables.
--bootstrap-ca-cert=cert_ac.pem
Lorsque cert_ac.pem existe, cette option a le même effet que -C ou --ca-cert. S'il n'existe pas, alors ovsdb-server tentera d'obtenir le certificat de l'AC à partir du pair SSL/TLS lors de sa première connexion SSL/TLS et l'enregistrera dans le fichier PEM nommé. S'il réussit, il interrompra immédiatement la connexion et se reconnectera, et à partir de ce moment, toutes les connexions SSL/TLS devront être authentifiées par un certificat signé par le certificat de l'AC ainsi obtenu.
Cette option expose la connexion SSL/TLS à une attaque de l'homme du milieu lors de l'obtention du certificat de l'AC initial, mais elle peut être utile pour l'amorçage.
Cette option n'est utile que si le pair SSL/TLS envoie son certificat d'AC dans le cadre de la chaîne de certificats SSL/TLS. Les protocoles SSL/TLS n'exigent pas que le serveur envoie le certificat de l'AC.
Cette option est mutuellement exclusive avec -C et --ca-cert.
--peer-ca-cert=cert_ac_pair.pem
Spécifie un fichier PEM contenant un ou plusieurs certificats supplémentaires à envoyer aux pairs SSL/TLS. cert_ac_pair.pem doit être le certificat de l'AC qui a signé le propre certificat de ovsdb-server, c'est-à-dire le certificat spécifié sur -c ou --certificate. Si le certificat de ovsdb-server est auto-signé, alors --certificate et --peer-ca-cert doivent spécifier le même fichier.
Cette option n'est pas utile en fonctionnement normal, car le pair SSL/TLS doit déjà disposer du certificat de l'AC pour que le pair ait une quelconque confiance dans l'identité de ovsdb-server.
y. Cependant, cela offre un moyen pour une nouvelle installation d'amorcer le certificat de CA lors de sa première connexion SSL/TLS.

Options de Connexion SSL

--ssl-protocols=protocoles
Spécifie une plage ou une liste de protocoles SSL/TLS séparés par des virgules ou des espaces que ovsdb-server activera pour les connexions SSL/TLS. Les protocoles pris en charge incluent TLSv1 (obsolète), TLSv1.1 (obsolète), TLSv1.2 et TLSv1.3. Les plages peuvent être fournies sous forme de deux noms de protocoles séparés par un tiret, ou comme un seul nom de protocole avec un signe plus. Par exemple, utilisez TLSv1.1-TLSv1.3 pour autoriser TLSv1.1, TLSv1.2 et TLSv1.3. Utilisez TLSv1.2+ pour autoriser TLSv1.2 et tout protocole ultérieur. L'option accepte une liste de protocoles ou exactement une plage. La plage est la manière préférée de spécifier les protocoles et l'option se comporte toujours comme si la plage entre la version minimale et la version maximale spécifiée était fournie, c'est-à-dire, si l'option est définie sur TLSv1.1,TLSv1.3, le TLSv1.2 sera également activé comme s'il s'agissait d'une plage. Indépendamment de l'ordre, le protocole le plus élevé pris en charge par les deux parties sera choisi lors de l'établissement de la connexion. La valeur par défaut lorsque cette option est omise est TLSv1.2 ou supérieur.
--ssl-ciphers=chiffrements
Spécifie, au format de chaîne de chiffrement OpenSSL, les chiffrements que ovsdb-server prendra en charge pour les connexions SSL/TLS avec TLSv1.2 et versions antérieures. La valeur par défaut lorsque cette option est omise est DEFAULT:@SECLEVEL=2.
--ssl-ciphersuites=suites-de-chiffrement
Spécifie, au format de chaîne de suites de chiffrement OpenSSL, les suites de chiffrement que ovsdb-server prendra en charge pour les connexions SSL/TLS avec TLSv1.3 et versions ultérieures. La valeur par défaut d'OpenSSL sera utilisée lorsque cette option est omise.

Autres Options

--unixctl=socket
Définit le nom du socket de contrôle sur lequel ovsdb-server écoute les commandes de gestion à l'exécution (voir COMMANDES DE GESTION À L'EXÉCUTION, ci-dessous). Si socket ne commence pas par /, il est interprété comme relatif à /run/openvswitch. Si --unixctl n'est pas utilisé du tout, le socket par défaut est /run/openvswitch/ovsdb-server.pid.ctl, où pid est l'ID de processus de ovsdb-server.
Sous Windows, un pipe nommé local est utilisé pour écouter les commandes de gestion à l'exécution. Un fichier est créé au chemin absolu indiqué par socket ou si --unixctl n'est pas utilisé du tout, un fichier est créé sous ovsdb-server.ctl dans le répertoire OVS_RUNDIR configuré. Le fichier existe uniquement pour imiter le comportement d'un socket de domaine Unix.
Spécifier none pour socket désactive la fonctionnalité de socket de contrôle.
--record[=répertoire]
Définit le processus en mode "enregistrement", dans lequel il enregistrera toutes les connexions, les données des flux (sockets de domaine Unix et réseau) et certains autres éléments importants nécessaires, afin qu'ils puissent être rejoués plus tard. Les données enregistrées sont stockées dans des fichiers de relecture dans le répertoire spécifié. Si le répertoire ne commence pas par /, il est interprété comme relatif à /run/openvswitch. Si le répertoire n'est pas spécifié, /run/openvswitch sera utilisé.
--replay[=répertoire]
Définit le processus en mode "relecture", dans lequel il lira les informations sur les connexions, les données des flux (sockets de domaine Unix et réseau) et certains autres éléments nécessaires directement à partir des fichiers de relecture au lieu d'utiliser de vrais sockets. Les fichiers de relecture du répertoire seront utilisés. Si le répertoire ne commence pas par /, il est interprété comme relatif à /run/openvswitch. Si le répertoire n'est pas spécifié, /run/openvswitch sera utilisé.

COMMANDES DE GESTION À L'EXÉCUTION

ovs-appctl(8) peut envoyer des commandes à un processus ovsdb-server en cours d'exécution. Les commandes actuellement prises en charge sont décrites ci-dessous.

Commandes ovsdb-server

Ces commandes sont spécifiques à ovsdb-server.

exit
Provoque la terminaison gracieuse de ovsdb-server.
ovsdb-server/compact [db]
Compacte la base de données db en place. Si db n'est pas spécifié, compacte chaque base de données en place. Une base de données est également compactée automatiquement lorsqu'une transaction est enregistrée si elle dépasse 2 fois sa taille de compactage précédente (et au moins 10 Mo), mais pas avant 100 commits ajoutés ou 10 minutes écoulées depuis la dernière compaction. Elle sera également compactée automatiquement après 24 heures depuis la dernière compaction si 100 commits ont été ajoutés, quelle que soit sa taille.
ovsdb-server/memory-trim-on-compaction on|off
Si cette option est on, ovsdb-server tentera de récupérer toute la mémoire libre du tas vers le système après chaque compaction de base de données réussie pour réduire la consommation mémoire du processus. off par défaut.
ovsdb-server/reconnect
Fait en sorte que ovsdb-server abandonne toutes les connexions JSON-RPC aux clients de base de données et se reconnecte.
Cette commande peut être utile pour le débogage des problèmes avec les clients de base de données.
ovsdb-server/add-remote remote
Ajoute un serveur distant, comme si --remote=remote avait été spécifié sur la ligne de commande de ovsdb-server. (Si remote est déjà un serveur distant configuré, cette commande réussit sans modifier la configuration.)
Mutuellement exclusif avec l'option --config-file.
ovsdb-server/remove-remote remote
Supprime le remote spécifié de la configuration, échouant avec une erreur si remote n'est pas configuré comme un serveur distant. Cette commande ne fonctionne qu'avec les serveurs distants qui ont été nommés sur --remote ou ovsdb-server/add-remote, c'est-à-dire qu'elle ne supprimera pas les serveurs distants ajoutés indirectement car ils ont été lus depuis la base de données en configurant un serveur distant db:db,table,column. (Vous pouvez supprimer une source de base de données avec ovsdb-server/remove-remote db:db,table,column, mais pas les serveurs distants individuels trouvés indirectement via la base de données.)
Mutuellement exclusif avec l'option --config-file.
ovsdb-server/list-remotes
Affiche une liste des serveurs distants actuellement configurés nommés sur --remote ou ovsdb-server/add-remote, c'est-à-dire qu'elle n'affiche pas les serveurs distants ajoutés indirectement car ils ont été lus depuis la base de données en configurant un serveur distant db:db,table,column.
ovsdb-server/add-db base_de_donnees
Ajoute la base_de_donnees au ovsdb-server en cours d'exécution. base_de_donnees peut être un fichier de base de données ou une description de relais au format suivant : relay:schema_name:remote. Le fichier de base de données doit déjà avoir été créé et initialisé en utilisant, par exemple, ovsdb-tool create.
Mutuellement exclusif avec l'option --config-file.
ovsdb-server/remove-db base_de_donnees
Supprime la base_de_donnees du ovsdb-server en cours d'exécution. base_de_donnees doit être un nom de base de données tel que listé par ovsdb-server/list-dbs.
Si un serveur distant a été configuré et pointe vers la base_de_donnees spécifiée (par exemple, --remote=db:base_de_donnees,... sur la ligne de commande), alors il sera désactivé jusqu'à ce qu'une autre base de données portant le même nom soit ajoutée à nouveau (avec ovsdb-server/add-db).
Toutes les options d'infrastructure de clé publique spécifiées via cette base de données (par exemple, --private-key=db:base_de_donnees,... sur la ligne de commande) seront désactivées jusqu'à ce qu'une autre base de données portant le même nom soit ajoutée à nouveau (avec ovsdb-server/add-db).
Mutuellement exclusif avec l'option --config-file.
ovsdb-server/list-dbs
Affiche une liste des bases de données actuellement configurées ajoutées soit via la ligne de commande, soit via la commande ovsdb-server/add-db.
ovsdb-server/tlog-set base_de_donnees:table on|off
Active ou désactive l'enregistrement de toutes les opérations exécutées sur la base de données et la table spécifiées. Les journaux sont générés au niveau INFO et sont limités en débit.
ovsdb-server/tlog-list
Affiche l'état de journalisation pour toutes les bases de données et tables actuellement configurées.

Commandes Active-Backup

Ces commandes interrogent et mettent à jour le rôle de ovsdb-server au sein d'une paire de serveurs actif-sauvegarde. Voir Options Active-Backup, ci-dessus, et Modèle de Service de Base de Données Active-Backup dans ovsdb(7) pour plus d'informations.

Toutes les Commandes Active-Backup qui modifient l'état de ovsdb-server sont mutuellement exclusives avec l'option --config-file.

ovsdb-server/set-active-ovsdb-server serveur
Définit le serveur actif auquel ovsdb-server se connecte via ovsdb-server/connect-active-ovsdb-server. Cela remplace l'option de ligne de commande --sync-from.
ovsdb-server/get-active-ovsdb-server
Obtient le serveur actif à partir duquel ovsdb-server synchronise actuellement ses bases de données.
ovsdb-server/connect-active-ovsdb-server
Fait passer le serveur à un rôle de sauvegarde. Le serveur commence à synchroniser ses bases de données avec le serveur actif spécifié par ovsdb-server/set-active-ovsdb-server (ou l'option de ligne de commande --sync-from) et ferme toutes les connexions client existantes, ce qui oblige les clients à se reconnecter.

Fait passer le serveur à un rôle actif. Le serveur arrête de synchroniser ses bases de données avec un serveur actif et ferme toutes les connexions client existantes, ce qui oblige les clients à se reconnecter.
ovsdb-server/set-active-ovsdb-server-probe-interval intervalle de sonde
Définit l'intervalle de sonde (en millisecondes) pour la connexion au serveur actif serveur.
ovsdb-server/set-sync-exclude-tables db:table[,db:table]...
Définit la ou les table(s) dans la ou les base(s) de données qui seront exclues de la synchronisation. Cela remplace l'option de ligne de commande --sync-exclude-tables.
ovsdb-server/get-sync-exclude-tables
Obtient les tables actuellement exclues de la synchronisation.
ovsdb-server/sync-status
Affiche un résumé des informations sur le temps d'exécution de la réplication. Les informations d'état sont toujours fournies, indiquant si le serveur fonctionne en mode actif ou sauvegarde. Pour toutes les bases de données avec le modèle de service actif-sauvegarde, le statut de la connexion de réplication, qui peut être en cours de connexion, en cours de réplication ou erreur, est affiché. Lorsque la connexion est en état de réplication, des informations supplémentaires indiquent les tables qui sont actuellement exclues de la réplication.

Commandes Cluster

Ces commandes prennent en charge le modèle de service clusterisé de ovsdb-server. Elles ne s'appliquent qu'aux bases de données au format utilisé pour les bases de données clusterisées, qui est le format de base de données créé par ovsdb-tool create-cluster et ovsdb-tool join-cluster.

cluster/cid db
Affiche l'ID du cluster pour db, qui est un UUID identifiant le cluster. Si db est une base de données nouvellement créée par ovsdb-tool cluster-join qui n'a pas encore rejoint son cluster avec succès, et que --cid n'a pas été spécifié sur la ligne de commande cluster-join, alors cette commande signalera une erreur car l'ID du cluster n'est pas encore connu.
cluster/sid db
Affiche l'ID du serveur pour db, qui est un UUID identifiant ce serveur au sein du cluster.
cluster/status db
Affiche le statut de ce serveur au sein du cluster et le statut de ses connexions aux autres serveurs du cluster.
cluster/leave db
Cette commande démarre la suppression progressive du serveur du cluster. Au moins un serveur doit rester, et le cluster doit être sain, c'est-à-dire que plus de la moitié des serveurs du cluster doivent être opérationnels.
Lorsque le serveur quitte le cluster avec succès, il cesse de servir db, comme si ovsdb-server/remove-db db avait été exécuté.
Utilisez ovsdb-client wait (voir ovsdb-client(1)) pour attendre que le serveur ait quitté le cluster.
Une fois qu'un serveur quitte un cluster, il ne peut jamais le rejoindre à nouveau. Créez plutôt un nouveau serveur et rejoignez-le au cluster.
Notez que la suppression du serveur du cluster modifie la taille totale du cluster. Par exemple, si vous supprimez deux serveurs d'un cluster de trois serveurs, le « cluster » devient un seul serveur fonctionnel. Cela n'entraîne pas un cluster de trois serveurs manquant de quorum.
cluster/kick db server
Démarre la suppression progressive du serveur du cluster de db, comme cluster/leave, sauf qu'elle peut supprimer n'importe quel serveur, pas seulement celui-ci.
serveur peut être un ID de serveur, tel qu'affiché par cluster/sid, ou l'adresse réseau locale du serveur passée à la commande create-cluster ou join-cluster de ovsdb-tool. Utilisez cluster/status pour voir la liste des membres du cluster.
cluster/change-election-timer db temps
Modifie la valeur de base du délai d'attente d'élection du leader du cluster, en millisecondes.
L'élection du leader sera initiée par un follower s'il ne reçoit pas de battement de cœur du leader dans ce délai plus un temps aléatoire compris entre 0 et 1 seconde.
La valeur par défaut est 1000, si elle n'est pas modifiée avec cette commande. Cette commande peut être utilisée pour ajuster la valeur si nécessaire, en fonction de la charge attendue et du temps de réponse des serveurs.
Cette commande doit être exécutée sur le leader. Elle initie le changement dans le cluster. Pour voir si le changement prend effet (est validé), utilisez cluster/status pour afficher le réglage actuel. Une fois qu'un changement est validé, il est conservé lors des redémarrages du serveur.
cluster/set-backlog-threshold db n_msgs n_bytes
Définit les limites de backlog pour les connexions RAFT de db à un maximum de n_msgs messages ou n_bytes octets. Si le backlog d'une des connexions atteint la limite, elle sera déconnectée (et rétablie). Les valeurs ne sont vérifiées que si le backlog contient plus de 50 messages.

COMMANDES VLOG

Ces commandes gèrent les paramètres de journalisation de ovsdb-server.

vlog/set [spécification]
Définit les niveaux de journalisation. Sans aucune spécification, définit le niveau de journalisation de chaque module et destination à dbg. Sinon, spécification est une liste de mots séparés par des espaces, des virgules ou des deux-points, jusqu'à un de chaque catégorie ci-dessous :
  • Un nom de module valide, tel qu'affiché par la commande vlog/list sur ovs-appctl(8), limite la modification du niveau de journalisation au module spécifié.
  • syslog, console ou file, pour limiter la modification du niveau de journalisation uniquement au journal système, à la console ou à un fichier, respectivement.
Sur la plateforme Windows, syslog est accepté comme mot et n'est utile qu'avec l'option --syslog-target (le mot n'a aucun effet sinon).
•
off, emer, err, warn, info ou dbg, pour contrôler le niveau de journalisation. Les messages de la gravité donnée ou supérieure seront enregistrés, et les messages de gravité inférieure seront filtrés. off filtre tous les messages. Voir ovs-appctl(8) pour une définition de chaque niveau de journalisation.
La casse n'est pas sensible dans spécification.
Indépendamment des niveaux de journalisation définis pour file, la journalisation dans un fichier n'aura pas lieu à moins que ovsdb-server n'ait été invoqué avec l'option --log-file.
Pour la compatibilité avec les anciennes versions d'OVS, any est accepté comme mot mais n'a aucun effet.

Définit le motif de journalisation pour destination à motif. Reportez-vous à ovs-appctl(8) pour une description de la syntaxe valide pour motif.
vlog/list
Liste les modules de journalisation pris en charge et leurs niveaux actuels.
vlog/list-pattern
Liste les motifs de journalisation utilisés pour chaque destination.
vlog/close
Fait en sorte que ovsdb-server ferme son fichier journal, s'il est ouvert. (Utilisez vlog/reopen pour le rouvrir plus tard.)
vlog/reopen
Fait en sorte que ovsdb-server ferme son fichier journal, s'il est ouvert, puis le rouvre. (Ceci est utile après la rotation des fichiers journaux, pour faire utiliser un nouveau fichier journal.)
Cela n'a aucun effet à moins que ovsdb-server n'ait été invoqué avec l'option --log-file.
vlog/disable-rate-limit [module]...

vlog/enable-rate-limit [module]...
Par défaut, ovsdb-server limite la fréquence à laquelle certains messages peuvent être enregistrés. Lorsqu'un message apparaît plus fréquemment que la limite, il est supprimé. Cela permet d'économiser de l'espace disque, de rendre les journaux plus faciles à lire et d'accélérer l'exécution, mais le dépannage nécessite parfois plus de détails. Par conséquent, vlog/disable-rate-limit permet de désactiver les limites de débit au niveau d'un module de journalisation individuel. Spécifiez un ou plusieurs noms de modules, tels qu'affichés par la commande vlog/list. La spécification d'aucun nom de module ou du mot-clé any désactive les limites de débit pour tous les modules de journalisation.
La commande vlog/enable-rate-limit, dont la syntaxe est identique à celle de vlog/disable-rate-limit, peut être utilisée pour réactiver une limite de débit qui était précédemment désactivée.

ovsdb-server(1) — Open vSwitch — French

NOM

ovsdb-server — serveur de base de données Open vSwitch

SYNTAXE

ovsdb-server [ -h | --help ] [ -V | --version ] [ -d | --detach ] [ -v[[spec]] | --verbose=[spec] ] [ -o option | --option=option ] [ --log-file=file ] [ --pidfile=[file] ] [ --overwrite-pidfile ] [ -m | --mlockall ] [ --user ] [ --unixctl=socket ] [ --unixctl-perms=perms ] Bases de données...

DESCRIPTION

Le démon ovsdb-server gère les bases de données Open vSwitch (OVSDB). Il implémente l'interface du protocole JSON-RPC OVSDB vers les bases de données, et il gère les données elles-mêmes. Il implémente également l'API de gestion des bases de données par le biais des commandes de gestion du runtime.

Les bases de données sont spécifiées sur la ligne de commande, où chaque argument non optionnel est une base de données qui doit être ouverte par ovsdb-server. Le format général d'une spécification de base de données est le suivant :

type
Le type de base de données. Actuellement, les seuls types pris en charge sont “privlocal” (pour les bases de données locales privées) et “ssl” (pour les bases de données accessibles via SSL via TCP).
file
Le chemin d'accès au fichier de base de données.
options
Facultatif. Une liste de paires clé-valeur séparées par des virgules, chaque paire étant sous la forme clé=valeur. Les options prises en charge dépendent du type de base de données.

Pour le type de base de données “privlocal”, l'option unique prise en charge est mmapsize, qui spécifie la taille du fichier de base de données en octets. Par défaut, il est défini sur 16 Mo.

Pour le type de base de données “ssl”, les options prises en charge sont :

remote
Une adresse IP ou un nom d'hôte et un numéro de port, sous la forme IP:port ou hostname:port. Indique l'adresse à laquelle le démon doit se connecter.
bootstrap-ca-cert=FILE
Le chemin d'accès à un fichier contenant le certificat de l'autorité de certification (CA) à utiliser pour vérifier les certificats des pairs. Si cette option est utilisée, le pair doit fournir un certificat valide signé par cette CA.
ca-cert=FILE
Le chemin d'accès à un fichier contenant le certificat de l'autorité de certification (CA) à utiliser pour vérifier les certificats des pairs. Si cette option est utilisée, le pair doit fournir un certificat valide signé par cette CA.
peer-ca-cert=FILE
Le chemin d'accès à un fichier contenant le certificat de l'autorité de certification (CA) à utiliser pour vérifier le certificat du pair. Si cette option est utilisée, le pair doit fournir un certificat valide signé par cette CA.
local-cert=FILE
Le chemin d'accès à un fichier contenant le certificat et la clé privée du démon. Il doit être au format PKCS-12 ou PEM.
private-key=FILE
Le chemin d'accès à un fichier contenant la clé privée du démon. Nécessaire uniquement si local-cert n'inclut pas la clé privée.
bootstrap-secret=STRING
Le secret à utiliser lors de la première connexion à un nouveau pair pour lequels un certificat n'a pas encore été échangé.

Les bases de données avec le préfixe “ssl:” sont considérées comme des bases de données activées pour SSL. Les bases de données sans préfixe sont considérées comme des bases de données non activées pour SSL.

Les bases de données sans extension .db sont supposées être des bases de données à accès partagé (shared access), qui sont des bases de données non privées utilisées par le démon pour stocker des informations qui ne sont pas sensibles. Les bases de données avec l'extension .db sont supposées être des bases de données privées.

Si aucune base de données n'est spécifiée sur la ligne de commande, ovsdb-server crée une base de données par défaut nommée conf.db.

Le démon ovsdb-server fonctionne en arrière-plan par défaut. L'option -d ou --detach peut être utilisée pour le faire fonctionner en premier plan.

Les options de journalisation sont prises en charge comme décrit dans ovs-vswitchd(8).

L'option --unixctl=SOCKET spécifie un chemin d'accès au socket Unix sur lequel ovsdb-server doit écouter les commandes de gestion du runtime. Le socket par défaut est /var/run/openvswitch/ovsdb-server.sock.

ovsdb-server peut être configuré pour utiliser des bases de données activées pour SSL. Lorsque cela est fait, les clients OVSDB peuvent se connecter à ces bases de données via SSL en utilisant les options appropriées lors de la configuration des clients.

Définit les permissions du socket Unix sur perms. perms doit être un entier octal à 3 chiffres.

COMMANDES DE GESTION DU RUNTIME

Le démon ovsdb-server expose une API de gestion du runtime par le biais de son socket Unix, qui est accessible via la commande ovs-appctl(8). Les commandes suivantes sont prises en charge :

exit
Arrête ovsdb-server proprement.
ovsdb-server/ovsdb-server-memory-usage
Affiche l'utilisation de la mémoire de ovsdb-server. Les informations sont formatées comme une liste de paires clé-valeur, où chaque paire représente une partie de la mémoire utilisée et sa taille en octets.
ovsdb-server/memory-usage
Similaire à ovsdb-server/ovsdb-server-memory-usage, mais plus détaillé.
ovsdb-server/list-databases
Liste les bases de données actuellement gérées par le démon.
ovsdb-server/list-tables database
Liste les tables de la base de données spécifiée.
ovsdb-server/list-columns database table
Liste les colonnes de la table spécifiée dans la base de données spécifiée.
ovsdb-server/get-schema database
Affiche le schéma de la base de données spécifiée.
ovsdb-server/get-schema-version database
Affiche la version du schéma de la base de données spécifiée.
ovsdb-server/log-level [ facility [ level ] ]

Contrôle le niveau de verbosité des journaux.

Sans arguments, il imprime le niveau de verbosité actuel pour chaque installation.

Si facility est spécifié, il imprime le niveau de verbosité pour cette installation uniquement.

Si facility et level sont spécifiés, il définit le niveau de verbosité de facility sur level. Les niveaux de verbosité sont 0 (le plus bas) à 9 (le plus élevé).

ovsdb-server/disable-monitor database table
Désactive les notifications de modification de table pour la table spécifiée dans la base de données spécifiée. Ces notifications sont générées lorsque des lignes sont ajoutées, supprimées ou modifiées dans la table.
ovsdb-server/enable-monitor database table
Active les notifications de modification de table pour la table spécifiée dans la base de données spécifiée. Ces notifications sont générées lorsque des lignes sont ajoutées, supprimées ou modifiées dans la table.
coverage/show
Affiche les débits moyens par seconde pour les quelques dernières secondes, la dernière minute et la dernière heure, ainsi que les décomptes totaux de tous les compteurs de couverture.
coverage/read-counter counter
Affiche le décompte total pour le counter de couverture spécifié.

ovsdb-server enregistre également ces informations peu après le démarrage et périodiquement à mesure que sa consommation de mémoire augmente.

COMMANDES DE COUVERTURE

Ces commandes gèrent les ``compteurs de couverture'' de ovsdb-server, qui comptent le nombre de fois où des événements particuliers se produisent pendant l'exécution d'un démon. En plus de ces commandes, ovsdb-server enregistre automatiquement les valeurs des compteurs de couverture, au niveau INFO, lorsqu'il détecte que la boucle principale du démon prend anormalement du temps à s'exécuter.

Les compteurs de couverture sont principalement utiles pour l'analyse des performances et le débogage.

coverage/show
Affiche les débits moyens par seconde pour les quelques dernières secondes, la dernière minute et la dernière heure, ainsi que les décomptes totaux de tous les compteurs de couverture.
coverage/read-counter counter
Affiche le décompte total pour le counter de couverture spécifié.

BOGUES

Dans Open vSwitch avant la version 2.4, lorsque ovsdb-server envoyait des réponses d'erreur JSON-RPC à certaines requêtes, il les formulait incorrectement avec le result et l'error échangés, de sorte que la réponse semblait indiquer un succès (avec un résultat absurde) plutôt qu'une erreur. Les requêtes qui souffraient de ce problème étaient :

transact

get_schema
Uniquement si la requête nomme une base de données inexistante.
monitor

lock

unlock
Dans tous les cas d'erreur.

Parmi ces cas, la seule erreur queLikely une application bien écrite rencontrera en pratique est un monitor de tables ou de colonnes qui n'existent pas, dans une situation où l'application a été mise à jour mais que le vieux schéma de base de données est encore temporairement utilisé. Pour gérer cette situation avec élégance, nous recommandons aux clients de traiter une réponse monitor avec un result contenant une paire clé-valeur error comme une erreur (en supposant que la base de données surveillée ne contienne pas de table nommée error).
