LD(1) Outils de développement GNU LD(1)

NOM

ld - L'éditeur de liens GNU

SYNTAXE

ld [options] objfile ...

DESCRIPTION

ld combine un certain nombre de fichiers objet et d'archives, relocalise leurs données et résout les références de symboles. Habituellement, la dernière étape de la compilation d'un programme est d'exécuter ld.

ld accepte des fichiers de langage de commande de l'éditeur de liens, écrits dans un sur-ensemble de la syntaxe du langage de commande de l'éditeur de liens d'AT&T, afin de fournir un contrôle explicite et total sur le processus d'édition de liens.

Cette page de manuel ne décrit pas le langage de commande ; voir l'entrée ld dans "info" pour des détails complets sur le langage de commande et sur d'autres aspects de l'éditeur de liens GNU.

Cette version de ld utilise les bibliothèques BFD à usage général pour opérer sur les fichiers objet. Cela permet à ld de lire, combiner et écrire des fichiers objet dans de nombreux formats différents, par exemple, COFF ou "a.out". Différents formats peuvent être liés ensemble pour produire n'importe quel type de fichier objet disponible.

Outre sa flexibilité, l'éditeur de liens GNU est plus utile que d'autres éditeurs de liens pour fournir des informations diagnostiques. De nombreux éditeurs de liens abandonnent l'exécution immédiatement en cas d'erreur ; dans la mesure du possible, ld continue l'exécution, vous permettant d'identifier d'autres erreurs (ou, dans certains cas, d'obtenir un fichier de sortie malgré l'erreur).

L'éditeur de liens GNU ld est conçu pour couvrir un large éventail de situations et pour être aussi compatible que possible avec les autres éditeurs de liens. Par conséquent, vous avez de nombreux choix pour contrôler son comportement.

OPTIONS

L'éditeur de liens prend en charge une pléthore d'options en ligne de commande, mais en pratique peu d'entre elles sont utilisées dans un contexte particulier. Par exemple, une utilisation fréquente de ld est de lier des fichiers objet Unix standards sur un système Unix standard et pris en charge. Sur un tel système, pour lier un fichier "hello.o" :

ld -o <sortie> /lib/crt0.o hello.o -lc

Cela indique à ld de produire un fichier nommé sortie comme résultat de la liaison du fichier "/lib/crt0.o" avec "hello.o" et la bibliothèque "libc.a", qui proviendra des répertoires de recherche standard. (Voir la discussion sur l'option -l ci-dessous.)

Certaines des options en ligne de commande de ld peuvent être spécifiées à n'importe quel moment de la ligne de commande. Cependant, les options qui font référence à des fichiers, telles que -l ou -T, provoquent la lecture du fichier au moment où l'option apparaît dans la ligne de commande, par rapport aux fichiers objet et aux autres options de fichier. Répéter des options qui ne sont pas des fichiers avec un argument différent n'aura soit aucun effet supplémentaire, soit annulera les occurrences précédentes (celles plus à gauche sur la ligne de commande) de cette option. Les options qui peuvent être spécifiées plusieurs fois de manière significative sont notées dans les descriptions ci-dessous.

Les arguments qui ne sont pas des options sont des fichiers objet ou des archives qui doivent être liés ensemble. Ils peuvent suivre, précéder ou être mélangés avec les options de la ligne de commande, à l'exception qu'un argument de fichier objet ne peut pas être placé entre une option et son argument.

Habituellement, l'éditeur de liens est appelé avec au moins un fichier objet, mais vous pouvez spécifier d'autres formes de fichiers d'entrée binaires en utilisant -l, -R et le langage de commande par script. Si aucun fichier d'entrée binaire n'est spécifié du tout, l'éditeur de liens ne produit aucune sortie et émet le message No input files.

Si l'éditeur de liens ne peut pas reconnaître le format d'un fichier objet, il supposera qu'il s'agit d'un script d'éditeur de liens. Un script spécifié de cette manière augmente le script d'éditeur de liens principal utilisé pour la liaison (soit le script d'éditeur de liens par défaut, soit celui spécifié à l'aide de -T). Cette fonctionnalité permet à l'éditeur de liens de se lier à un fichier qui ressemble à un objet ou une archive, mais qui définit en réalité des valeurs de symboles, ou utilise "INPUT" ou "GROUP" pour charger d'autres objets. Spécifier un script de cette manière augmente simplement le script d'éditeur de liens principal, les commandes supplémentaires étant placées après le script principal ; utilisez l'option -T pour remplacer entièrement le script d'éditeur de liens par défaut, mais notez l'effet de la commande "INSERT".

Pour les options dont les noms sont une seule lettre, les arguments d'option doivent soit suivre la lettre d'option sans espace blanc intermédiaire, soit être donnés comme arguments séparés immédiatement après l'option qui les requiert.

Pour les options dont les noms sont composés de plusieurs lettres, un seul tiret ou deux peuvent précéder le nom de l'option ; par exemple, -trace-symbol et --trace-symbol sont équivalents. Notez qu'il y a une exception à cette règle. Les options à plusieurs lettres qui commencent par une lettre minuscule 'o' ne peuvent être précédées que de deux tirets. Ceci afin de réduire la confusion avec l'option -o. Ainsi, par exemple, -omagic définit le nom du fichier de sortie à magic tandis que --omagic définit le drapeau NMAGIC sur la sortie.

Les arguments des options à plusieurs lettres doivent être séparés du nom de l'option par un signe égal, ou être donnés comme arguments séparés immédiatement après l'option qui les requiert. Par exemple, --trace-symbol foo et --trace-symbol=foo sont équivalents. Les abréviations uniques des noms des options à plusieurs lettres sont acceptées.

Notez que si l'éditeur de liens est appelé indirectement, via un pilote de compilateur (par exemple, gcc), alors toutes les options de ligne de commande de l'éditeur de liens doivent être précédées de -Wl, (ou quelque chose d'approprié pour le pilote de compilateur particulier), comme suit :

gcc -Wl,--start-group foo.o bar.o -Wl,--end-group

C'est important, car sinon le programme pilote de compilateur peut silencieusement ignorer les options de l'éditeur de liens, entraînant une mauvaise liaison. La confusion peut également survenir lors du passage d'options nécessitant des valeurs à travers un pilote, car l'utilisation d'un espace entre l'option et l'argument agit comme un séparateur, et amène le pilote à ne passer que l'option à l'éditeur de liens et l'argument au compilateur. Dans ce cas, il est plus simple d'utiliser les formes jointes des options à une et à plusieurs lettres, telles que :

gcc foo.o bar.o -Wl,-eENTRY -Wl,-Map=a.map

Voici un tableau des commutateurs génériques acceptés en ligne de commande par l'éditeur de liens GNU :

@fichier
Lit les options de la ligne de commande depuis fichier. Les options lues sont insérées à la place de l'option @fichier d'origine. Si fichier n'existe pas, ou ne peut pas être lu, alors l'option sera traitée littéralement, et ne sera pas supprimée.

Les options dans fichier sont séparées par des espaces blancs. Un caractère d'espace blanc peut être inclus dans une option en entourant l'option entière de guillemets simples ou doubles. N'importe quel caractère (y compris un antislash) peut être inclus en faisant précéder le caractère à inclure d'un antislash. Le fichier peut lui-même contenir des options @fichier supplémentaires ; ces options seront traitées récursivement.

-a mot-clé
Cette option est prise en charge pour la compatibilité HP/UX. L'argument mot-clé doit être l'une des chaînes archive, shared, ou default. -aarchive est fonctionnellement équivalent à -Bstatic, et les deux autres mots-clés sont fonctionnellement équivalents à -Bdynamic. Cette option peut être utilisée plusieurs fois.
--audit AUDITLIB
Ajoute AUDITLIB à l'entrée "DT_AUDIT" de la section dynamique. AUDITLIB n'est pas vérifié pour son existence, ni n'utilisera le DT_SONAME spécifié dans la bibliothèque. S'il est spécifié plusieurs fois, "DT_AUDIT" contiendra une liste séparée par des deux-points des interfaces d'audit à utiliser. Si l'éditeur de liens trouve un objet avec une entrée d'audit lors de la recherche de bibliothèques partagées, il ajoutera une entrée "DT_DEPAUDIT" correspondante dans le fichier de sortie. Cette option n'est significative que sur les plateformes ELF prenant en charge l'interface rtld-audit.
-b format-entrée
--format=format-entrée
ld peut être configuré pour prendre en charge plus d'un type de fichier objet. Si votre ld est configuré de cette manière, vous pouvez utiliser l'option -b pour spécifier le format binaire pour les fichiers objet qui suivent cette option dans la ligne de commande. Même lorsque ld est configuré pour prendre en charge des formats objet alternatifs, vous n'avez généralement pas besoin de le spécifier, car ld devrait être configuré pour attendre comme un

Vous pourriez vouloir utiliser cette option si vous liez des fichiers avec un format binaire inhabituel. Vous pouvez également utiliser -b pour basculer explicitement de formats (lors de la liaison de fichiers objets de formats différents), en incluant -b input-format avant chaque groupe de fichiers objets d'un format particulier.

Le format par défaut est pris de la variable d'environnement "GNUTARGET".

-c fichier-commande-MRI
--mri-script=fichier-commande-MRI
Pour la compatibilité avec les linkeurs produits par MRI, ld accepte des fichiers de script écrits dans un langage de commande alternatif et restreint, décrit dans la section Fichiers de script compatibles MRI de la documentation GNU ld. Introduisez les fichiers de script MRI avec l'option -c ; utilisez l'option -T pour exécuter des scripts de linkeur écrits dans le langage de script généraliste ld. Si fichier-commande-MRI n'existe pas, ld le recherche dans les répertoires spécifiés par toute option -L.
-d
-dc
-dp
Ces trois options sont équivalentes ; plusieurs formes sont supportées pour la compatibilité avec d'autres linkeurs. Elles allouent de l'espace pour les symboles communs même si un fichier de sortie relocalisable est spécifié (avec -r). La commande de script "FORCE_COMMON_ALLOCATION" a le même effet.
--depaudit BIBLIOAUDIT
-P BIBLIOAUDIT
Ajoute BIBLIOAUDIT à l'entrée "DT_DEPAUDIT" de la section dynamique. BIBLIOAUDIT n'est pas vérifié pour son existence, ni n'utilisera le DT_SONAME spécifié dans la bibliothèque. S'il est spécifié plusieurs fois, "DT_DEPAUDIT" contiendra une liste d'interfaces d'audit séparées par des deux-points à utiliser. Cette option n'est pertinente que sur les plateformes ELF supportant l'interface rtld-audit. L'option -P est fournie pour la compatibilité Solaris.
--enable-linker-version
Active la directive de script de linkeur "LINKER_VERSION", décrite dans Données de section de sortie. Si cette directive est utilisée dans un script de linkeur et que cette option a été activée, alors une chaîne contenant la version du linkeur sera insérée au point actuel.

Notez que l'emplacement de cette option sur la ligne de commande du linkeur est significatif. Elle n'affectera que les scripts de linkeur qui viennent après elle sur la ligne de commande, ou qui sont intégrés au linkeur.

--disable-linker-version
Désactive la directive de script de linkeur "LINKER_VERSION", de sorte qu'elle n'insère pas de chaîne de version. C'est le comportement par défaut.
--enable-non-contiguous-regions
Cette option évite de générer une erreur si une section d'entrée ne correspond pas à une section de sortie correspondante. Le linkeur tente d'allouer la section d'entrée aux sections de sortie correspondantes subséquentes, et ne génère une erreur que si aucune section de sortie n'est suffisamment grande. Ceci est utile lorsque plusieurs régions de mémoire non contiguës sont disponibles et que la section d'entrée n'en nécessite pas une en particulier. L'ordre dans lequel les sections d'entrée sont évaluées ne change pas, par exemple : 
MEMORY {
  MEM1 (rwx) : ORIGIN = 0x1000, LENGTH = 0x14
  MEM2 (rwx) : ORIGIN = 0x1000, LENGTH = 0x40
  MEM3 (rwx) : ORIGIN = 0x2000, LENGTH = 0x40
}
SECTIONS {
  mem1 : { *(.data.*); } > MEM1
  mem2 : { *(.data.*); } > MEM2
  mem3 : { *(.data.*); } > MEM3
}

avec les sections d'entrée :
.data.1: taille 8
.data.2: taille 0x10
.data.3: taille 4

résulte en .data.1 affecté à mem1, et .data.2 et .data.3
affectés à mem2, même si .data.3 rentrerait dans mem3.

Cette option est incompatible avec les instructions INSERT car elle modifie la manière dont les sections d'entrée sont mappées aux sections de sortie.

--enable-non-contiguous-regions-warnings
Cette option active les avertissements lorsque "--enable-non-contiguous-regions" permet des correspondances potentiellement inattendues dans le mappage des sections, conduisant potentiellement à l'élimination silencieuse d'une section au lieu d'échouer parce qu'elle ne rentre dans aucune région de sortie.
-e entrée
--entry=entrée
Utilise entrée comme symbole explicite pour commencer l'exécution de votre programme, au lieu du point d'entrée par défaut. S'il n'existe aucun symbole nommé entrée, le linkeur tentera d'analyser entrée comme un nombre, et l'utilisera comme adresse d'entrée (le nombre sera interprété en base 10 ; vous pouvez utiliser un préfixe 0x pour la base 16, ou un préfixe 0 pour la base 8).
--exclude-libs lib,lib,...
Spécifie une liste de bibliothèques d'archives dont les symboles ne doivent pas être exportés automatiquement. Les noms de bibliothèques peuvent être délimités par des virgules ou des deux-points. Spécifier "--exclude-libs ALL" exclut les symboles de toutes les bibliothèques d'archives de l'exportation automatique. Cette option n'est disponible que pour le port ciblé i386 PE du linkeur et pour les ports ciblés ELF. Pour i386 PE, les symboles explicitement listés dans un fichier .def sont toujours exportés, indépendamment de cette option. Pour les ports ciblés ELF, les symboles affectés par cette option seront traités comme cachés.
--exclude-modules-for-implib module,module,...
Spécifie une liste de fichiers objets ou de membres d'archives, dont les symboles ne doivent pas être exportés automatiquement, mais qui doivent être copiés en bloc dans la bibliothèque d'importation générée pendant la liaison. Les noms de modules peuvent être délimités par des virgules ou des deux-points, et doivent correspondre exactement aux noms de fichiers utilisés par ld pour ouvrir les fichiers ; pour les membres d'archives, il s'agit simplement du nom du membre, mais pour les fichiers objets, le nom listé doit inclure et correspondre précisément à tout chemin utilisé pour spécifier le fichier d'entrée sur la ligne de commande du linkeur. Cette option n'est disponible que pour le port ciblé i386 PE du linkeur. Les symboles explicitement listés dans un fichier .def sont toujours exportés, indépendamment de cette option.
-E
--export-dynamic
--no-export-dynamic
Lors de la création d'un exécutable lié dynamiquement, l'utilisation de l'option -E ou de l'option --export-dynamic fait que le linkeur ajoute tous les symboles à la table des symboles dynamiques. La table des symboles dynamiques est l'ensemble des symboles qui sont visibles depuis les objets dynamiques au moment de l'exécution.

Si vous n'utilisez aucune de ces options (ou utilisez l'option --no-export-dynamic pour rétablir le comportement par défaut), la table des symboles dynamiques contiendra normalement uniquement les symboles qui sont référencés par un objet dynamique mentionné dans la liaison.

Si vous utilisez "dlopen" pour charger un objet dynamique qui doit faire référence aux symboles définis par le programme, plutôt qu'à un autre objet dynamique, alors vous aurez probablement besoin d'utiliser cette option lors de la liaison du programme lui-même.

Vous pouvez également utiliser la liste dynamique pour contrôler quels symboles doivent être ajoutés à la table des symboles dynamiques si le format de sortie le supporte. Voir la description de --dynamic-list.

Notez que cette option est spécifique aux ports ciblés ELF. Les cibles PE supportent une fonction similaire pour exporter tous les symboles d'une DLL ou d'un EXE ; voir la description de --export-all-symbols ci-dessous.

--export-dynamic-symbol=glob
Lors de la création d'un exécutable lié dynamiquement, les symboles correspondant à glob seront ajoutés à la table des symboles dynamiques. Lors de la création d'une bibliothèque partagée, les références aux symboles correspondant à glob ne seront pas liées aux définitions au sein de la bibliothèque partagée. Cette option est une opération nulle lors de la création d'une bibliothèque partagée et que -Bsymbolic ou --dynamic-list ne sont pas spécifiés. Cette option n'est pertinente que sur les plateformes ELF qui supportent les bibliothèques partagées.
--export-dynamic-symbol-list=fichier
Spécifie un --export-dynamic-symbol pour chaque modèle dans le fichier. Le format du fichier est le même que celui du nœud de version sans portée ni nom de nœud. Voir VERSION pour plus d'informations.
-EB
Lie des objets big-endian. Cela affecte le format de sortie par défaut.
-EL
Lie des objets little-endian. Cela affecte le format de sortie par défaut.
-f nom
--auxiliary=nom
Lors de la création d'un objet partagé ELF, définit le champ interne DT_AUXILIARY au nom spécifié. Cela indique au linkeur dynamique que la table des symboles de l'objet partagé doit être utilisée comme filtre auxiliaire sur la table des symboles de l'objet partagé nom.

Si vous liez plus tard un programme contre cet objet filtre, alors, lors de l'exécution du programme, le linkeur dynamique verra le champ DT_AUXILIARY. Si le linkeur dynamique résout des symboles à partir de l'objet filtre, il vérifiera d'abord s'il existe une définition dans l'objet partagé nom. S'il y en a une, elle sera utilisée à la place de la définition dans l'objet filtre. L'objet partagé nom n'a pas besoin d'exister. Ainsi, l'objet partagé nom peut être utilisé pour fournir une implémentation alternative de certaines fonctions, peut-être pour le débogage ou pour des performances spécifiques à la machine.

Cette option peut être spécifiée plusieurs fois. Les entrées DT_AUXILIARY seront créées dans l'ordre où elles apparaissent sur la ligne de commande.

-F nom
--filter=nom
Lors de la création d'un objet partagé ELF, définit le champ interne DT_FILTER sur le nom spécifié. Cela indique à l'éditeur de liens dynamique que la table des symboles de l'objet partagé qui est en cours de création doit être utilisée comme filtre sur la table des symboles de l'objet partagé nom.

Si vous liez plus tard un programme à cet objet filtre, alors, lorsque vous exécutez le programme, l'éditeur de liens dynamique verra le champ DT_FILTER. L'éditeur de liens dynamique résoudra les symboles selon la table des symboles de l'objet filtre comme d'habitude, mais il se liera réellement aux définitions trouvées dans l'objet partagé nom. Ainsi, l'objet filtre peut être utilisé pour sélectionner un sous-ensemble des symboles fournis par l'objet nom.

Certains éditeurs de liens plus anciens utilisaient l'option -F tout au long d'une chaîne d'outils de compilation pour spécifier le format du fichier objet pour les fichiers objets d'entrée et de sortie. L'éditeur de liens GNU utilise d'autres mécanismes à cet effet : les options -b, --format, --oformat, la commande "TARGET" dans les scripts d'éditeur de liens, et la variable d'environnement "GNUTARGET". L'éditeur de liens GNU ignorera l'option -F lorsqu'il ne crée pas d'objet partagé ELF.

-fini=nom
Lors de la création d'un exécutable ou d'un objet partagé ELF, appelle NOM lorsque l'exécutable ou l'objet partagé est déchargé, en définissant DT_FINI à l'adresse de la fonction. Par défaut, l'éditeur de liens utilise "_fini" comme fonction à appeler.
-g
Ignoré. Fourni pour la compatibilité avec d'autres outils.
-G valeur
--gpsize=valeur
Définit la taille maximale des objets à optimiser à l'aide du registre GP sur taille. Ceci n'est pertinent que pour les formats de fichiers objets tels que MIPS ELF qui prennent en charge la mise dans des sections différentes d'objets volumineux et petits. Ceci est ignoré pour les autres formats de fichiers objets.
-h nom
-soname=nom
Lors de la création d'un objet partagé ELF, définit le champ interne DT_SONAME sur le nom spécifié. Lorsqu'un exécutable est lié à un objet partagé qui a un champ DT_SONAME, alors lorsque l'exécutable est exécuté, l'éditeur de liens dynamique tentera de charger l'objet partagé spécifié par le champ DT_SONAME plutôt que d'utiliser le nom de fichier donné à l'éditeur de liens.
-i
Effectue une liaison incrémentielle (identique à l'option -r).
-init=nom
Lors de la création d'un exécutable ou d'un objet partagé ELF, appelle NOM lorsque l'exécutable ou l'objet partagé est chargé, en définissant DT_INIT à l'adresse de la fonction. Par défaut, l'éditeur de liens utilise "_init" comme fonction à appeler.
-l spécification_nom
--library=spécification_nom
Ajoute l'archive ou le fichier objet spécifié par spécification_nom à la liste des fichiers à lier. Cette option peut être utilisée un nombre quelconque de fois. Si spécification_nom est de la forme :nom_fichier, ld recherchera dans le chemin de la bibliothèque un fichier nommé nom_fichier, sinon il recherchera dans le chemin de la bibliothèque un fichier nommé libspécification_nom.a.

Sur les systèmes qui prennent en charge les bibliothèques partagées, ld peut également rechercher des fichiers autres que libspécification_nom.a. Plus précisément, sur les systèmes ELF et SunOS, ld recherchera dans un répertoire une bibliothèque nommée libspécification_nom.so avant d'en rechercher une nommée libspécification_nom.a. (Par convention, une extension ".so" indique une bibliothèque partagée.) Notez que ce comportement ne s'applique pas à :nom_fichier, qui spécifie toujours un fichier nommé nom_fichier.

L'éditeur de liens ne recherchera une archive qu'une seule fois, à l'emplacement où elle est spécifiée dans la ligne de commande. Si l'archive définit un symbole qui était indéfini dans un objet apparu avant l'archive dans la ligne de commande, l'éditeur de liens inclura les fichiers appropriés de l'archive. Cependant, un symbole indéfini dans un objet apparaissant plus tard dans la ligne de commande n'entraînera pas l'éditeur de liens à rechercher à nouveau l'archive.

Voir l'option -( pour une façon de forcer l'éditeur de liens à rechercher les archives plusieurs fois.

Vous pouvez lister la même archive plusieurs fois dans la ligne de commande.

Ce type de recherche d'archives est standard pour les éditeurs de liens Unix. Cependant, si vous utilisez ld sur AIX, notez qu'il est différent du comportement de l'éditeur de liens AIX.

-L répertoire_recherche
--library-path=répertoire_recherche
Ajoute le chemin répertoire_recherche à la liste des chemins que ld recherchera pour les bibliothèques d'archives et les scripts de contrôle de ld. Vous pouvez utiliser cette option un nombre quelconque de fois. Les répertoires sont recherchés dans l'ordre dans lequel ils sont spécifiés dans la ligne de commande. Les répertoires spécifiés dans la ligne de commande sont recherchés avant les répertoires par défaut. Toutes les options -L s'appliquent à toutes les options -l, quel que soit l'ordre dans lequel les options apparaissent. Les options -L n'affectent pas la façon dont ld recherche un script d'éditeur de liens, sauf si l'option -T est spécifiée.

Si répertoire_recherche commence par "=" ou $SYSROOT, alors ce préfixe sera remplacé par le préfixe sysroot, contrôlé par l'option --sysroot, ou spécifié lors de la configuration de l'éditeur de liens.

L'ensemble par défaut de chemins recherchés (sans être spécifiés avec -L) dépend du mode d'émulation utilisé par ld, et dans certains cas également de la manière dont il a été configuré.

Les chemins peuvent également être spécifiés dans un script de liaison avec la commande "SEARCH_DIR". Les répertoires spécifiés de cette manière sont recherchés au moment où le script de liaison apparaît dans la ligne de commande.

-m émulation
Émule l'éditeur de liens émulation. Vous pouvez lister les émulations disponibles avec les options --verbose ou -V.

Si l'option -m n'est pas utilisée, l'émulation est prise de la variable d'environnement "LDEMULATION", si elle est définie.

Sinon, l'émulation par défaut dépend de la manière dont l'éditeur de liens a été configuré.

--remap-inputs=modèle=nom_fichier
--remap-inputs-file=fichier
Ces options permettent de modifier les noms des fichiers d'entrée avant que l'éditeur de liens ne tente de les ouvrir. L'option --remap-inputs=foo.o=bar.o fera en sorte que toute tentative de chargement d'un fichier nommé foo.o essaie plutôt de charger un fichier nommé bar.o. Les caractères génériques sont autorisés dans le premier nom de fichier, donc --remap-inputs=foo*.o=bar.o renommera tout fichier d'entrée correspondant à foo*.o en bar.o.

Une forme alternative de l'option --remap-inputs-file=nom_fichier permet de lire les remappages à partir d'un fichier. Chaque ligne du fichier peut contenir un seul remappage. Les lignes vides sont ignorées. Tout ce qui suit un caractère dièse (#) jusqu'à la fin d'une ligne est considéré comme un commentaire et est également ignoré. Le modèle de remappage peut être séparé du nom de fichier par des espaces blancs ou un signe égal (=).

Les options peuvent être spécifiées plusieurs fois. Leur contenu s'accumule. Les remappages seront traités dans l'ordre où ils apparaissent dans la ligne de commande, et s'ils proviennent d'un fichier, dans l'ordre où ils apparaissent dans le fichier. Si une correspondance est trouvée, aucune vérification supplémentaire pour ce nom de fichier ne sera effectuée.

Si le nom de fichier de remplacement est /dev/null ou simplement NUL, le remappage entraînera effectivement l'ignorance du fichier d'entrée. Cela peut être un moyen pratique d'expérimenter la suppression de fichiers d'entrée d'un environnement de construction complexe.

Notez que cette option dépend de la position et n'affecte que les noms de fichiers qui la suivent dans la ligne de commande. Ainsi :

ld foo.o --remap-inputs=foo.o=bar.o

N'aura aucun effet, tandis que :

ld --remap-inputs=foo.o=bar.o foo.o

Renommera le fichier d'entrée foo.o en bar.o.

Notez que ces options affectent également les fichiers référencés par des instructions INPUT dans les scripts d'éditeur de liens. Mais comme les scripts d'éditeur de liens sont traités après la lecture de toute la ligne de commande, la position des options de remappage dans la ligne de commande n'est pas significative.

Si l'option verbose est activée, les correspondances trouvées seront signalées, bien que l'option verbose doive être activée dans la ligne de commande avant que les noms de fichiers remappés n'apparaissent.

Si les options -Map ou --print-map sont activées, la liste de remappage sera incluse dans la sortie de la carte.

-M
--print-map
Affiche une carte de liaison sur la sortie standard. Une carte de liaison fournit des informations sur la liaison, notamment :
  • Où les fichiers objets sont mappés en mémoire.
  • Comment les symboles communs sont alloués.
  • Tous les membres d'archive inclus dans la liaison, avec une mention du symbole qui a causé l'inclusion du membre d'archive.
  • Les valeurs attribuées aux symboles.

    Notez que les symboles dont les valeurs sont calculées par une expression impliquant une référence à une valeur précédente du même symbole peuvent ne pas avoir le résultat correct affiché dans la carte de liaison. Ceci est dû au fait que l'éditeur de liens jette les résultats intermédiaires et ne conserve que la valeur finale d'une expression. Dans de telles circonstances, l'éditeur de liens affichera la valeur finale entourée de crochets. Ainsi, par exemple, un script d'éditeur de liens contenant :

    foo = 1
foo = foo * 4
foo = foo + 8

    Produira la sortie suivante dans la carte de liaison si l'option -M est utilisée :

    0x00000001                foo = 0x1
[0x0000000c]                foo = (foo * 0x4)
[0x0000000c]                foo = (foo + 0x8)

    Voir Expressions pour plus d'informations.

pour les expressions dans les scripts de liaison.

  • Comment les propriétés GNU sont fusionnées.

    Lorsque l'éditeur de liens fusionne les sections d'entrée .note.gnu.property en une section de sortie .note.gnu.property, certaines propriétés sont supprimées ou mises à jour. Ces actions sont rapportées dans la carte de liaison. Par exemple :

    Propriété 0xc0000002 supprimée pour fusionner foo.o (0x1) et bar.o (non trouvé)

    Cela indique que la propriété 0xc0000002 est supprimée de la sortie lors de la fusion des propriétés dans foo.o, dont la valeur de la propriété 0xc0000002 est 0x1, et bar.o, qui n'a pas la propriété 0xc0000002.

    Propriété 0xc0010001 (0x1) mise à jour pour fusionner foo.o (0x1) et bar.o (0x1)

    Cela indique que la valeur de la propriété 0xc0010001 est mise à jour à 0x1 en sortie lors de la fusion des propriétés dans foo.o, dont la valeur de la propriété 0xc0010001 est 0x1, et bar.o, dont la valeur de la propriété 0xc0010001 est 0x1.

  • Sur certaines cibles ELF, une liste de corrections insérées par --relax 
    foo.o: Ajustement du saut à 0x00000008 vers "far" dans la section .text

    Cela indique que le saut à 0x00000008 dans foo.o, ciblant le symbole "far" dans la section .text, a été remplacé par un trampoline.

    -z defs
    Signale les références de symboles non résolues des fichiers objets réguliers. Ceci est fait même si l'éditeur de liens crée une bibliothèque partagée non symbolique. Le commutateur --[no-]allow-shlib-undefined contrôle le comportement pour signaler les références non résolues trouvées dans les bibliothèques partagées en cours de liaison.

    Les effets de cette option peuvent être annulés en utilisant "-z undefs".

    --allow-multiple-definition
    -z muldefs
    Normalement, lorsqu'un symbole est défini plusieurs fois, l'éditeur de liens signale une erreur fatale. Ces options autorisent les définitions multiples et la première définition sera utilisée.
    --allow-shlib-undefined
    --no-allow-shlib-undefined
    Autorise ou interdit les symboles indéfinis dans les bibliothèques partagées. Ce commutateur est similaire à --no-undefined sauf qu'il détermine le comportement lorsque les symboles indéfinis se trouvent dans une bibliothèque partagée plutôt que dans un fichier objet régulier. Il n'affecte pas la façon dont les symboles indéfinis des fichiers objets réguliers sont traités.

    Le comportement par défaut est de signaler les erreurs pour tous les symboles indéfinis référencés dans les bibliothèques partagées si l'éditeur de liens est utilisé pour créer un exécutable, mais de les autoriser si l'éditeur de liens est utilisé pour créer une bibliothèque partagée.

    Les raisons pour autoriser les références de symboles indéfinis dans les bibliothèques partagées spécifiées au moment de la liaison sont que :

    • Une bibliothèque partagée spécifiée au moment de la liaison peut ne pas être la même que celle qui est disponible au moment du chargement, de sorte que le symbole pourrait en fait être résoluble au moment du chargement.
    • Il existe certains systèmes d'exploitation, par exemple BeOS et HPPA, où les symboles indéfinis dans les bibliothèques partagées sont normaux.

      Le noyau BeOS, par exemple, patch les bibliothèques partagées au moment du chargement pour sélectionner la fonction la plus appropriée pour l'architecture actuelle. Ceci est utilisé, par exemple, pour sélectionner dynamiquement une fonction memset appropriée.

    --error-handling-script=scriptname
    Si cette option est fournie, l'éditeur de liens invoquera scriptname chaque fois qu'une erreur sera rencontrée. Actuellement, seuls deux types d'erreurs sont pris en charge : symboles manquants et bibliothèques manquantes. Deux arguments seront passés au script : le mot-clé "undefined-symbol" ou "missing-lib" et le nom du symbole indéfini ou de la bibliothèque manquante. L'intention est que le script fournisse des suggestions à l'utilisateur sur l'endroit où le symbole ou la bibliothèque pourrait être trouvé. Une fois le script terminé, le message d'erreur normal de l'éditeur de liens sera affiché.

    La disponibilité de cette option est contrôlée par un commutateur de configuration, elle peut donc ne pas être présente dans des implémentations spécifiques.

    --no-undefined-version
    Normalement, lorsqu'un symbole a une version indéfinie, l'éditeur de liens l'ignore. Cette option interdit les symboles avec une version indéfinie et une erreur fatale sera émise à la place.
    --default-symver
    Crée et utilise une version de symbole par défaut (le soname) pour les symboles exportés non versionnés.
    --warn-common
    Signaler les symboles communs non définis.

    Le comportement par défaut peut être restauré en spécifiant --no-warn-common.

    id="default~3">--default-imported-symver
    Crée et utilise une version de symbole par défaut (le soname) pour les symboles importés sans version.
    --no-warn-mismatch
    Normalement, ld générera une erreur si vous essayez de lier des fichiers d'entrée qui sont incompatibles pour une raison quelconque, par exemple parce qu'ils ont été compilés pour des processeurs différents ou pour des boutistes différents. Cette option indique à ld de permettre silencieusement de telles erreurs potentielles. Cette option ne doit être utilisée qu'avec prudence, dans les cas où vous avez pris des mesures spéciales pour garantir que les erreurs du lieur sont inappropriées.
    --no-warn-search-mismatch
    Normalement, ld émettra un avertissement s'il trouve une bibliothèque incompatible lors d'une recherche de bibliothèque. Cette option fait taire l'avertissement.
    --no-whole-archive
    Désactive l'effet de l'option --whole-archive pour les fichiers d'archive suivants.
    --noinhibit-exec
    Conserve le fichier de sortie exécutable tant qu'il est utilisable. Normalement, le lieur ne produira pas de fichier de sortie s'il rencontre des erreurs pendant le processus de liaison ; il se termine sans écrire de fichier de sortie lorsqu'il émet une erreur quelconque.
    -nostdlib
    Ne recherche les répertoires de bibliothèques que ceux explicitement spécifiés sur la ligne de commande. Les répertoires de bibliothèques spécifiés dans les scripts de liaison (y compris les scripts de liaison spécifiés sur la ligne de commande) sont ignorés.
    --oformat=format-sortie
    ld peut être configuré pour prendre en charge plus d'un type de fichier objet. Si votre ld est configuré de cette manière, vous pouvez utiliser l'option --oformat pour spécifier le format binaire pour le fichier objet de sortie. Même lorsque ld est configuré pour prendre en charge les formats d'objets alternatifs, vous n'avez généralement pas besoin de le spécifier, car ld devrait être configuré pour produire par défaut le format de sortie le plus courant sur chaque machine. format-sortie est une chaîne de texte, le nom d'un format particulier pris en charge par les bibliothèques BFD. (Vous pouvez lister les formats binaires disponibles avec objdump -i.) La commande de script "OUTPUT_FORMAT" peut également spécifier le format de sortie, mais cette option la remplace.
    --out-implib fichier
    Crée une bibliothèque d'importation dans fichier correspondant à l'exécutable que le lieur génère (par exemple, une DLL ou un programme ELF). Cette bibliothèque d'importation (qui devrait s'appeler "*.dll.a" ou "*.a" pour les DLL) peut être utilisée pour lier des clients à l'exécutable généré ; ce comportement permet d'éviter une étape séparée de création de bibliothèque d'importation (par exemple, "dlltool" pour les DLL). Cette option n'est disponible que pour les ports du lieur ciblés i386 PE et ELF.
    -pie
    --pic-executable
    Crée un exécutable indépendant de la position. Ceci n'est actuellement pris en charge que sur les plateformes ELF. Les exécutables indépendants de la position sont similaires aux bibliothèques partagées dans le sens où ils sont relocalisés par le lieur dynamique à l'adresse virtuelle que le système d'exploitation choisit pour eux (ce qui peut varier entre les invocations). Comme les exécutables liés dynamiquement normaux, ils peuvent être exécutés et les symboles définis dans l'exécutable ne peuvent pas être remplacés par des bibliothèques partagées.
    -no-pie
    Crée un exécutable dépendant de la position. C'est le comportement par défaut.
    -qmagic
    Cette option est ignorée pour la compatibilité Linux.
    -Qy
    Cette option est ignorée pour la compatibilité SVR4.
    --relax
    --no-relax
    Une option avec des effets dépendants de la machine. Cette option n'est prise en charge que sur quelques cibles.

    Sur certaines plateformes, l'option --relax effectue des optimisations globales spécifiques à la cible qui deviennent possibles lorsque le lieur résout l'adressage dans le programme, telles que l'assouplissement des modes d'adressage, la synthèse de nouvelles instructions, la sélection de versions plus courtes d'instructions actuelles et la combinaison de valeurs constantes.

    Sur certaines plateformes, ces optimisations globales au moment de la liaison peuvent rendre le débogage symbolique de l'exécutable résultant impossible. C'est le cas connu pour la famille de processeurs Matsushita MN10200 et MN10300.

    Sur les plateformes où la fonctionnalité est prise en charge, l'option --no-relax la désactivera.

    Sur les plateformes où la fonctionnalité n'est pas prise en charge, --relax et --no-relax sont acceptés, mais ignorés.

    --retain-symbols-file=nomfichier
    Ne conserve *que* les symboles listés dans le fichier nomfichier, en supprimant tous les autres. nomfichier est simplement un fichier plat, avec un nom de symbole par ligne. Cette option est particulièrement utile dans les environnements (comme VxWorks) où une grande table de symboles globale est accumulée progressivement, afin de conserver la mémoire d'exécution.

    --retain-symbols-file ne supprime *pas* les symboles indéfinis, ni les symboles nécessaires aux relocalisations.

    Vous ne pouvez spécifier --retain-symbols-file qu'une seule fois sur la ligne de commande. Elle remplace -s et -S.

    -rpath=rép
    Ajoute un répertoire au chemin de recherche des bibliothèques d'exécution. Ceci est utilisé lors de la liaison d'un exécutable ELF avec des objets partagés. Tous les arguments -rpath sont concaténés et transmis au lieur d'exécution, qui les utilise pour localiser les objets partagés au moment de l'exécution.

    L'option -rpath est également utilisée lors de la localisation des objets partagés nécessaires aux objets partagés inclus explicitement dans la liaison ; voir la description de l'option -rpath-link. La recherche de -rpath de cette manière n'est prise en charge que par les lieurs natifs et les lieurs croisés qui ont été configurés avec l'option --with-sysroot.

    Si -rpath n'est pas utilisé lors de la liaison d'un exécutable ELF, le contenu de la variable d'environnement "LD_RUN_PATH" sera utilisé s'il est défini.

    L'option -rpath peut également être utilisée sur SunOS. Par défaut, sur SunOS, le lieur forme un chemin de recherche d'exécution à partir de toutes les options -L qui lui sont données. Si une option -rpath est utilisée, le chemin de recherche d'exécution sera formé exclusivement en utilisant les options -rpath, ignorant les options -L. Cela peut être utile lors de l'utilisation de gcc, qui ajoute de nombreuses options -L qui peuvent se trouver sur des systèmes de fichiers montés NFS.

    Par souci de compatibilité avec d'autres lieurs ELF, si l'option -R est suivie d'un nom de répertoire, plutôt que d'un nom de fichier, elle est traitée comme l'option -rpath.

    -rpath-link=rép
    Lors de l'utilisation d'ELF ou de SunOS, une bibliothèque partagée peut en requérir une autre. Cela se produit lorsqu'une liaison "ld -shared" inclut une bibliothèque partagée comme l'un des fichiers d'entrée.

    Lorsque le lieur rencontre une telle dépendance lors d'une liaison non partagée et non déplaçable, il essaiera automatiquement de localiser la bibliothèque partagée requise et de l'inclure dans la liaison, si elle n'est pas incluse explicitement. Dans ce cas, l'option -rpath-link spécifie le premier ensemble de répertoires à rechercher. L'option -rpath-link peut spécifier une séquence de noms de répertoires soit en spécifiant une liste de noms séparés par des deux-points, soit en apparaissant plusieurs fois.

    Les jetons $ORIGIN et $LIB peuvent apparaître dans ces répertoires de recherche. Ils seront remplacés par le chemin complet du répertoire contenant le programme ou l'objet partagé dans le cas de $ORIGIN et soit lib - pour les binaires 32 bits - soit lib64 - pour les binaires 64 bits - dans le cas de $LIB.

    La forme alternative de ces jetons - ${ORIGIN} et ${LIB} peut également être utilisée. Le jeton $PLATFORM n'est pas pris en charge.

    Cette option doit être utilisée avec prudence car elle remplace le chemin de recherche qui peut avoir été codé en dur dans une bibliothèque partagée. Dans un tel cas, il est possible d'utiliser involontairement un chemin de recherche différent de celui que le lieur d'exécution utiliserait.

    Le lieur utilise les chemins de recherche suivants pour localiser les bibliothèques partagées requises :

    1.
    Tous les répertoires spécifiés par les options -rpath-link.
    2.
    Tous les répertoires spécifiés par les options -rpath. La différence entre -rpath et -rpath-link est que les répertoires spécifiés par les options -rpath sont inclus dans l'exécutable et utilisés au moment de l'exécution, tandis que l'option -rpath-link n'est effective qu'au moment de la liaison. La recherche de -rpath de cette manière n'est prise en charge que par les lieurs natifs et les lieurs croisés qui ont été configurés avec l'option --with-sysroot.
    3.
    Sur un système ELF, pour les lieurs natifs, si les options -rpath et -rpath-link n'ont pas été utilisées, recherchez dans le contenu de la variable d'environnement "LD_RUN_PATH".
    4.
    Sur SunOS, si l'option -rpath n'a pas été utilisée, recherchez dans tous les répertoires spécifiés à l'aide des options -L.
    5.
    Pour un lieur natif, recherchez dans le contenu de la variable d'environnement "LD_LIBRARY_PATH".
    6.
    Pour un lieur ELF natif, les répertoires dans "DT_RUNPATH" ou "DT_RPATH" d'une bibliothèque partagée sont recherchés pour les bibliothèques partagées dont elle a besoin. Les entrées "DT_RPATH" sont ignorées si des entrées "DT_RUNPATH" existent.
    7.
    Pour un lieur pour un système Linux, si le fichier /etc/ld.so.conf existe, la liste des répertoires trouvés dans ce fichier. Note : le chemin vers ce fichier est précédé de la valeur "sysroot", si elle est définie, puis de toute chaîne "prefix" si le lieur a été configuré avec le
    >--prefix=<chemin> option.
    8.
    Pour un éditeur de liens natif sur un système FreeBSD, tout répertoire spécifié par la macro "_PATH_ELF_HINTS" définie dans le fichier d'en-tête elf-hints.h.
    9.
    Tout répertoire spécifié par une commande "SEARCH_DIR" dans un script d'éditeur de liens donné sur la ligne de commande, y compris les scripts spécifiés par -T (mais pas -dT).
    10.
    Les répertoires par défaut, normalement /lib et /usr/lib.
    11.
    Tout répertoire spécifié par un plugin LDPT_SET_EXTRA_LIBRARY_PATH.
    12.
    Tout répertoire spécifié par une commande "SEARCH_DIR" dans un script d'éditeur de liens par défaut.

    Notez cependant que sur les systèmes basés sur Linux, il y a une mise en garde supplémentaire : si l'option --as-needed est active *et* qu'une bibliothèque partagée est trouvée qui satisferait normalement la recherche *et* que cette bibliothèque n'a pas de tag DT_NEEDED pour libc.so *et* qu'une bibliothèque partagée plus loin dans l'ensemble des répertoires de recherche satisfait également la recherche *et* que cette seconde bibliothèque partagée a un tag DT_NEEDED pour libc.so, *alors* la seconde bibliothèque sera sélectionnée à la place de la première.

    Si la bibliothèque partagée requise n'est pas trouvée, l'éditeur de liens affichera un avertissement et poursuivra l'édition de liens.

    -shared
    -Bshareable
    Crée une bibliothèque partagée. Ceci n'est actuellement pris en charge que sur les plateformes ELF, XCOFF et SunOS. Sur SunOS, l'éditeur de liens créera automatiquement une bibliothèque partagée si l'option -e n'est pas utilisée et qu'il y a des symboles indéfinis dans l'édition de liens.
    --sort-common
    --sort-common=ascending
    --sort-common=descending
    Cette option indique à ld de trier les symboles communs par alignement dans un ordre croissant ou décroissant lors de leur placement dans les sections de sortie appropriées. Les alignements de symboles considérés sont de seize octets ou plus, huit octets, quatre octets, deux octets et un octet. Ceci afin d'éviter les espaces entre les symboles dus aux contraintes d'alignement. Si aucun ordre de tri n'est spécifié, l'ordre décroissant est supposé.
    --sort-section=name
    Cette option appliquera "SORT_BY_NAME" à tous les modèles de sections génériques dans le script de l'éditeur de liens.
    --sort-section=alignment
    Cette option appliquera "SORT_BY_ALIGNMENT" à tous les modèles de sections génériques dans le script de l'éditeur de liens.
    --spare-dynamic-tags=nombre
    Cette option spécifie le nombre d'emplacements vides à laisser dans la section .dynamic des objets partagés ELF. Des emplacements vides peuvent être nécessaires pour les outils de post-traitement, tels que le pré-éditeur de liens. La valeur par défaut est 5.
    --split-by-file[=taille]
    Similaire à --split-by-reloc mais crée une nouvelle section de sortie pour chaque fichier d'entrée lorsque la taille est atteinte. taille vaut par défaut 1 si elle n'est pas donnée.
    --split-by-reloc[=compte]
    Tente de créer des sections supplémentaires dans le fichier de sortie de sorte qu'aucune section de sortie unique dans le fichier ne contienne plus de compte réallocations. Ceci est utile lors de la génération de fichiers relocalisables volumineux pour le téléchargement dans certains noyaux temps réel avec le format de fichier objet COFF ; car COFF ne peut pas représenter plus de 65535 réallocations dans une seule section. Notez que cela ne fonctionnera pas avec les formats de fichiers objet qui ne supportent pas les sections arbitraires. L'éditeur de liens ne fractionnera pas les sections d'entrée individuelles pour la redistribution, donc si une seule section d'entrée contient plus de compte réallocations, une section de sortie contiendra ce nombre de réallocations. compte vaut par défaut 32768.
    --stats
    Calcule et affiche des statistiques sur le fonctionnement de l'éditeur de liens, telles que le temps d'exécution et l'utilisation de la mémoire.
    --sysroot=répertoire
    Utilise répertoire comme emplacement du sysroot, remplaçant la valeur par défaut de configuration. Cette option n'est prise en charge que par les éditeurs de liens qui ont été configurés à l'aide de --with-sysroot.
    --task-link
    Ceci est utilisé par les cibles basées sur COFF/PE pour créer un fichier objet lié à une tâche où tous les symboles globaux ont été convertis en statiques.
    --traditional-format
    Pour certaines cibles, la sortie de ld diffère à certains égards de la sortie de certains éditeurs de liens existants. Ce commutateur demande à ld d'utiliser le format traditionnel à la place.

    Par exemple, sur SunOS, ld combine les entrées dupliquées dans la table des chaînes de symboles. Cela peut réduire la taille d'un fichier de sortie avec des informations de débogage complètes de plus de 30 %. Malheureusement, le programme "dbx" de SunOS ne peut pas lire le programme résultant ("gdb" n'a aucun problème). Le commutateur --traditional-format indique à ld de ne pas combiner les entrées dupliquées.

    --section-start=nomsection=org
    Localise une section dans le fichier de sortie à l'adresse absolue donnée par org. Vous pouvez utiliser cette option autant de fois que nécessaire pour localiser plusieurs sections dans la ligne de commande. org doit être un seul entier hexadécimal ; pour la compatibilité avec d'autres éditeurs de liens, vous pouvez omettre le préfixe 0x généralement associé aux valeurs hexadécimales. Note : il ne doit pas y avoir d'espace blanc entre nomsection, le signe égal ("="), et org.
    -Tbss=org
    -Tdata=org
    -Ttext=org
    Identique à --section-start, avec ".bss", ".data" ou ".text" comme nomsection.
    -Ttext-segment=org
    Lors de la création d'un exécutable ELF, cela définit l'adresse du premier octet du segment de texte.
    -Trodata-segment=org
    Lors de la création d'un exécutable ou d'un objet partagé ELF pour une cible où les données en lecture seule se trouvent dans leur propre segment, séparé du texte exécutable, cela définit l'adresse du premier octet du segment de données en lecture seule.
    -Tldata-segment=org
    Lors de la création d'un exécutable ou d'un objet partagé ELF pour le modèle de mémoire moyen x86-64, cela définit l'adresse du premier octet du segment ldata.
    --unresolved-symbols=méthode
    Détermine comment gérer les symboles non résolus. Il existe quatre valeurs possibles pour méthode :
    ignore-all
    Ne signaler aucun symbole non résolu.
    report-all
    Signaler tous les symboles non résolus. C'est la valeur par défaut.
    ignore-in-object-files
    Signaler les symboles non résolus contenus dans les bibliothèques partagées, mais les ignorer s'ils proviennent de fichiers objet réguliers.
    ignore-in-shared-libs
    Signaler les symboles non résolus provenant de fichiers objet réguliers, mais les ignorer s'ils proviennent de bibliothèques partagées. Cela peut être utile lors de la création d'un binaire dynamique et si l'on sait que toutes les bibliothèques partagées auxquelles il devrait faire référence sont incluses dans la ligne de commande de l'éditeur de liens.

    Le comportement pour les bibliothèques partagées seules peut également être contrôlé par l'option --[no-]allow-shlib-undefined.

    Normalement, l'éditeur de liens générera un message d'erreur pour chaque symbole non résolu signalé, mais l'option --warn-unresolved-symbols peut changer cela en un avertissement.

    --dll-verbose
    --verbose[=NOMBRE]
    Affiche le numéro de version de ld et liste les émulations d'éditeur de liens supportées. Affiche les fichiers d'entrée qui peuvent être ouverts et ceux qui ne le peuvent pas. Affiche le script de l'éditeur de liens utilisé par celui-ci. Si l'argument NOMBRE optionnel est supérieur à 1, l'état des symboles des plugins sera également affiché.
    --version-script=fichier-script-version
    Spécifie le nom d'un script de version à l'éditeur de liens. Ceci est généralement utilisé lors de la création de bibliothèques partagées pour spécifier des informations supplémentaires sur la hiérarchie des versions de la bibliothèque créée. Cette option n'est entièrement prise en charge que sur les plateformes ELF qui supportent les bibliothèques partagées ; voir VERSION. Elle est partiellement prise en charge sur les plateformes PE, qui peuvent utiliser des scripts de version pour filtrer la visibilité des symboles en mode d'exportation automatique : tous les symboles marqués comme local dans le script de version ne seront pas exportés.
    --warn-common
    Avertit lorsqu'un symbole commun est combiné avec un autre symbole commun ou avec la définition d'un symbole. Les éditeurs de liens Unix autorisent cette pratique quelque peu laxiste, mais les éditeurs de liens sur certains autres systèmes d'exploitation ne le font pas. Cette option vous permet de détecter des problèmes potentiels liés à la combinaison de symboles globaux. Malheureusement, certaines bibliothèques C utilisent cette pratique, vous pouvez donc recevoir des avertissements concernant des symboles dans les bibliothèques ainsi que dans vos programmes.

    Il existe trois types de symboles globaux, illustrés ici par des exemples en C :

    int i = 1;
    Une définition, qui va dans la section des données initialisées du fichier de sortie.
    extern int i;
    Une référence indéfinie, qui dne alloue pas d'espace. Il doit y avoir soit une définition, soit un symbole commun pour la variable quelque part.
    int i;
    Un symbole commun. S'il n'y a qu'un (ou plusieurs) symbole(s) commun(s) pour une variable, elle est placée dans la zone de données non initialisées du fichier de sortie. L'éditeur de liens fusionne plusieurs symboles communs pour la même variable en un seul symbole. S'ils sont de tailles différentes, il choisit la taille la plus grande. L'éditeur de liens transforme un symbole commun en une déclaration si une définition de la même variable existe.

    L'option --warn-common peut produire cinq types d'avertissements. Chaque avertissement se compose d'une paire de lignes : la première décrit le symbole que l'on vient de rencontrer, et la seconde décrit le symbole précédent rencontré avec le même nom. Un ou les deux symboles seront un symbole commun.

    1.
    Transformer un symbole commun en une référence, car il existe déjà une définition pour le symbole. 
    <fichier>(<section>): avertissement : commun de `<symbole>'
   remplacé par une définition
<fichier>(<section>): avertissement : défini ici
    2.
    Transformer un symbole commun en une référence, car une définition ultérieure du symbole est rencontrée. C'est le même cas que le précédent, sauf que les symboles sont rencontrés dans un ordre différent. 
    <fichier>(<section>): avertissement : définition de `<symbole>'
   remplaçant un commun
<fichier>(<section>): avertissement : le commun est ici
    3.
    Fusionner un symbole commun avec un symbole commun précédent de même taille. 
    <fichier>(<section>): avertissement : commun multiple
   de `<symbole>'
<fichier>(<section>): avertissement : le commun précédent est ici
    4.
    Fusionner un symbole commun avec un symbole commun précédent plus grand. 
    <fichier>(<section>): avertissement : commun de `<symbole>'
   remplacé par un commun plus grand
<fichier>(<section>): avertissement : le commun plus grand est ici
    5.
    Fusionner un symbole commun avec un symbole commun précédent plus petit. C'est le même cas que le précédent, sauf que les symboles sont rencontrés dans un ordre différent. 
    <fichier>(<section>): avertissement : commun de `<symbole>'
   remplaçant un commun plus petit
<fichier>(<section>): avertissement : le commun plus petit est ici
    --warn-constructors
    Avertir si des constructeurs globaux sont utilisés. Ceci n'est utile que pour quelques formats de fichiers objet. Pour des formats comme COFF ou ELF, l'éditeur de liens ne peut pas détecter l'utilisation de constructeurs globaux.
    --warn-execstack
    --warn-execstack-objects
    --no-warn-execstack
    Sur les plateformes ELF, l'éditeur de liens peut générer des messages d'avertissement s'il est demandé de créer un fichier de sortie contenant une pile exécutable. Il y a trois états possibles :
    1.
    Ne générer aucun avertissement.
    2.
    Générer toujours des avertissements, même si la pile exécutable est demandée via l'option de ligne de commande -z execstack.
    3.
    Générer un avertissement uniquement si un fichier objet demande une pile exécutable, mais pas si l'option -z execstack est utilisée.

    L'état par défaut dépend de la manière dont l'éditeur de liens a été configuré lors de sa construction. L'option --no-warn-execstack met toujours l'éditeur de liens dans l'état sans avertissements. L'option --warn-execstack met l'éditeur de liens dans l'état d'avertissement permanent. L'option --warn-execstack-objects met l'éditeur de liens dans l'état d'avertissement uniquement pour les fichiers objet.

    Note : les fichiers d'entrée au format ELF peuvent spécifier qu'ils nécessitent une pile exécutable en ayant une section .note.GNU-stack avec le bit exécutable défini dans ses drapeaux de section. Ils peuvent spécifier qu'ils n'ont pas besoin d'une pile exécutable en ayant la même section, mais sans le bit d'exécution défini. Si un fichier d'entrée n'a pas de section .note.GNU-stack, le comportement par défaut est spécifique à la cible. Pour certaines cibles, l'absence d'une telle section implique qu'une pile exécutable est requise. C'est souvent un problème pour les fichiers assembleur conçus manuellement.

    --error-execstack
    --no-error-execstack
    Si l'éditeur de liens est sur le point de générer un message d'avertissement concernant une pile exécutable, l'option --error-execstack transformera cet avertissement en erreur. Notez que cette option ne modifie pas l'état de génération des avertissements d'execstack de l'éditeur de liens. Utilisez --warn-execstack ou --warn-execstack-objects pour définir un état d'avertissement spécifique.

    L'option --no-error-execstack rétablira le comportement par défaut de génération de messages d'avertissement.

    --warn-multiple-gp
    Avertir si plusieurs valeurs de pointeur global sont requises dans le fichier de sortie. Ceci n'est pertinent que pour certains processeurs, comme l'Alpha. Plus spécifiquement, certains processeurs placent les constantes de grande valeur dans une section spéciale. Un registre spécial (le pointeur global) pointe vers le milieu de cette section, de sorte que les constantes peuvent être chargées efficacement via un mode d'adressage relatif au registre de base. Comme le décalage en mode relatif au registre de base est fixe et relativement petit (par exemple, 16 bits), cela limite la taille maximale du pool de constantes. Ainsi, dans les grands programmes, il est souvent nécessaire d'utiliser plusieurs valeurs de pointeur global pour pouvoir adresser toutes les constantes possibles. Cette option provoque un avertissement chaque fois que ce cas se produit.
    --warn-once
    N'avertir qu'une seule fois pour chaque symbole non défini, plutôt qu'une fois par module qui y fait référence.
    --warn-rwx-segments
    --no-warn-rwx-segments
    Avertir si l'éditeur de liens crée un segment chargeable, de taille non nulle, qui possède les trois indicateurs de permission lecture, écriture et exécution définis. Un tel segment représente une vulnérabilité de sécurité potentielle. De plus, des avertissements seront générés si un segment de stockage local à thread est créé avec l'indicateur de permission d'exécution défini, indépendamment de la présence ou non des indicateurs de lecture et/ou d'écriture.

    Ces avertissements sont activés par défaut. Ils peuvent être désactivés via l'option --no-warn-rwx-segments et réactivés via l'option --warn-rwx-segments.

    --error-rwx-segments
    --no-error-rwx-segments
    Si l'éditeur de liens est sur le point de générer un message d'avertissement concernant un segment exécutable et inscriptible, ou un segment TLS exécutable, l'option --error-rwx-segments transformera cet avertissement en erreur. L'option --no-error-rwx-segments rétablira le comportement par défaut de simple génération d'un message d'avertissement.

    Notez que l'option --error-rwx-segments n'active pas en soi les avertissements concernant ces segments. Ces avertissements sont soit activés par défaut, si l'éditeur de liens a été configuré ainsi, soit via l'option de ligne de commande --warn-rwx-segments.

    --warn-section-align
    Avertir si l'adresse d'une section de sortie est modifiée en raison de l'alignement. Typiquement, l'alignement sera défini par une section d'entrée. L'adresse ne sera modifiée que si elle n'est pas explicitement spécifiée ; c'est-à-dire si la commande "SECTIONS" ne spécifie pas d'adresse de démarrage pour la section.
    --warn-textrel
    Avertir si l'éditeur de liens ajoute DT_TEXTREL à un exécutable indépendant de la position ou à un objet partagé.
    --warn-alternate-em
    Avertir si un objet a un code machine ELF alternatif.
    --warn-unresolved-symbols
    Si l'éditeur de liens doit signaler un symbole non résolu (voir l'option --unresolved-symbols), il générera normalement une erreur. Cette option le fait générer un avertissement à la place.
    --error-unresolved-symbols
    Ceci rétablit le comportement par défaut de l'éditeur de liens consistant à générer des erreurs lorsqu'il signale des symboles non résolus.
    --whole-archive
    Pour chaque archive mentionnée sur la ligne de commande après l'option --whole-archive, inclure chaque fichier objet de l'archive dans la liaison, plutôt que de rechercher dans l'archive les fichiers objets requis. Ceci est normalement utilisé pour transformer un fichier archive en une bibliothèque partagée, forçant chaque objet à être inclus dans la bibliothèque partagée résultante. Cette option peut être utilisée plus d'une fois.

    Deux notes lors de l'utilisation de cette option depuis gcc : Premièrement, gcc ne connaît pas cette option, vous devez donc utiliser -Wl,-whole-archive. Deuxièmement, n'oubliez pas d'utiliser -Wl,-no-whole-archive après votre liste d'archives, car gcc ajoutera sa propre liste d'archives à votre lien et vous ne voudrez peut-être pas que cet indicateur affecte également celles-ci.

    --wrap=symbole
    Utiliser une fonction d'encapsulation (wrapper) pour symbole. Toute référence non définie à symbole sera résolue en "__wrap_symbole". Toute référence non définie à "__real_symbole" sera résolue en symbole.

    Ceci peut être utilisé pour fournir une fonction d'encapsulation pour une fonction système. La fonction d'encapsulation doit être nommée "__wrap_symbole". Si elle souhaite appeler la fonction système, elle doit appeler "__real_symbole".

    Voici un exemple trivial :

    void *
__wrap_malloc (size_t c)
{
  printf ("malloc appelé avec %zu\n", c);
  return __real_malloc (c);
}

    Si vous liez d'autres codes avec ce fichier en utilisant --wrap malloc, tous les appels à "malloc" appelleront la fonction "__wrap_malloc" à la place. L'appel à "__real_malloc" dans "__wrap_malloc" an> appellera la fonction "malloc" réelle.

    Vous pourriez souhaiter fournir également une fonction "__real_malloc", afin que les liens sans l'option --wrap réussissent. Si vous faites cela, vous ne devriez pas mettre la définition de "__real_malloc" dans le même fichier que "__wrap_malloc" ; si vous le faites, l'assembleur peut résoudre l'appel avant que l'éditeur de liens n'ait la chance de le rediriger vers "malloc".

    Seules les références indéfinies sont remplacées par l'éditeur de liens. Ainsi, les références internes à l'unité de traduction vers symbole ne sont pas résolues en "__wrap_symbole". Dans l'exemple suivant, l'appel à "f" dans "g" n'est pas résolu en "__wrap_f".

    int
f (void)
{
  return 123;
}

int
g (void)
{
  return f();
}
    --eh-frame-hdr
    --no-eh-frame-hdr
    Demande (--eh-frame-hdr) ou supprime (--no-eh-frame-hdr) la création de la section ".eh_frame_hdr" et de l'en-tête de segment ELF "PT_GNU_EH_FRAME".
    --no-ld-generated-unwind-info
    Demande la création d'informations de déroulement (unwind info) de ".eh_frame" pour les sections de code générées par l'éditeur de liens comme PLT. Cette option est activée par défaut si la génération d'informations de déroulement par l'éditeur de liens est prise en charge. Cette option contrôle également la génération d'informations de trace de pile ".sframe" pour les sections de code générées par l'éditeur de liens comme PLT.
    --enable-new-dtags
    --disable-new-dtags
    Cet éditeur de liens peut créer les nouvelles balises dynamiques en ELF. Mais les anciens systèmes ELF pourraient ne pas les comprendre. Si vous spécifiez --enable-new-dtags, les nouvelles balises dynamiques seront créées si nécessaire et les anciennes balises dynamiques seront omises. Si vous spécifiez --disable-new-dtags, aucune nouvelle balise dynamique ne sera créée. Par défaut, les nouvelles balises dynamiques ne sont pas créées. Notez que ces options ne sont disponibles que pour les systèmes ELF.
    --hash-size=nombre
    Définit la taille par défaut des tables de hachage de l'éditeur de liens à un nombre premier proche de nombre. Augmenter cette valeur peut réduire le temps nécessaire à l'éditeur de liens pour accomplir ses tâches, au dépens de l'augmentation des besoins en mémoire de l'éditeur de liens. De même, réduire cette valeur peut réduire les besoins en mémoire au dépens de la vitesse.
    --hash-style=style
    Définit le type des tables de hachage de l'éditeur de liens. style peut être soit "sysv" pour la section ELF classique ".hash", "gnu" pour la nouvelle section GNU ".gnu.hash", soit "both" pour les deux tables de hachage, classique ELF ".hash" et nouvelle GNU ".gnu.hash". La valeur par défaut dépend de la manière dont l'éditeur de liens a été configuré, mais pour la plupart des systèmes basés sur Linux, ce sera "both".
    --compress-debug-sections=none
    --compress-debug-sections=zlib
    --compress-debug-sections=zlib-gnu
    --compress-debug-sections=zlib-gabi
    --compress-debug-sections=zstd
    Sur les plateformes ELF, ces options contrôlent comment les sections de débogage DWARF sont compressées en utilisant zlib.

    --compress-debug-sections=none ne compresse pas les sections de débogage DWARF. --compress-debug-sections=zlib-gnu compresse les sections de débogage DWARF et les renomme pour commencer par .zdebug au lieu de .debug. --compress-debug-sections=zlib-gabi compresse également les sections de débogage DWARF, mais au lieu de les renommer, elle définit l'indicateur SHF_COMPRESSED dans les en-têtes des sections.

    L'option --compress-debug-sections=zlib est un alias pour --compress-debug-sections=zlib-gabi.

    --compress-debug-sections=zstd compresse les sections de débogage DWARF en utilisant zstd.

    Notez que cette option remplace toute compression dans les sections de débogage d'entrée, donc si un binaire est lié avec --compress-debug-sections=none par exemple, alors toute section de débogage compressée dans les fichiers d'entrée sera décompressée avant d'être copiée dans le binaire de sortie.

    Le comportement de compression par défaut varie en fonction de la cible concernée et des options de configuration utilisées pour construire la chaîne d'outils. La valeur par défaut peut être déterminée en examinant la sortie de l'option --help de l'éditeur de liens.

    --reduce-memory-overheads
    Cette option réduit les besoins en mémoire au moment de l'exécution de ld, au détriment de la vitesse de liaison. Elle a été introduite pour sélectionner l'ancien algorithme O(n^2) pour la génération du fichier de carte de liaison, plutôt que le nouvel algorithme O(n) qui utilise environ 40 % de mémoire en plus pour le stockage des symboles.

    Un autre effet de l'option est de définir la taille par défaut de la table de hachage à 1021, ce qui économise à nouveau de la mémoire au coût d'un allongement du temps d'exécution de l'éditeur de liens. Cependant, ce n'est pas fait si l'option --hash-size a été utilisée.

    L'option --reduce-memory-overheads peut également être utilisée pour activer d'autres compromis dans les futures versions de l'éditeur de liens.

    --max-cache-size=taille
    ld met normalement en cache les informations de relocalisation et les tables de symboles des fichiers d'entrée en mémoire avec une taille illimitée. Cette option définit la taille maximale du cache à taille.
    --build-id
    --build-id=style
    Demande la création d'une section de note ELF ".note.gnu.build-id" ou d'une section COFF ".buildid". Le contenu de la note est composé de bits uniques identifiant ce fichier lié. style peut être "uuid" pour utiliser 128 bits aléatoires, "sha1" pour utiliser un hachage SHA1 de 160 bits sur les parties normatives du contenu de sortie, "md5" pour utiliser un hachage MD5 de 128 bits sur les parties normatives du contenu de sortie, ou "0xchaînehex" pour utiliser une chaîne de bits choisie spécifiée comme un nombre pair de chiffres hexadécimaux (les caractères "-" et ":" entre les paires de chiffres sont ignorés). Si style est omis, "sha1" est utilisé.

    Les styles "md5" et "sha1" produisent un identifiant qui est toujours le même pour un fichier de sortie identique, mais qui sera unique parmi tous les fichiers non identiques. Il n'est pas destiné à être comparé comme une somme de contrôle du contenu du fichier. Un fichier lié peut être modifié ultérieurement par d'autres outils, mais la chaîne de bits d'identifiant de construction identifiant le fichier lié d'origine ne change pas.

    Passer "none" pour style désactive le réglage de toute option "--build-id" précédente sur la ligne de commande.

    --package-metadata=JSON
    Demande la création d'une section de note ELF ".note.package". Le contenu de la note est en format JSON, conformément à la spécification des métadonnées de paquet. Pour plus d'informations, voir : https://systemd.io/ELF_PACKAGE_METADATA/ Si l'argument JSON est manquant/vide, cela désactivera la création de la note de métadonnées, si elle avait été activée par une occurrence antérieure de l'option --package-metadata. Si l'éditeur de liens a été construit avec libjansson, la chaîne JSON sera validée.

    L'éditeur de liens i386 PE prend en charge l'option -shared, qui fait que la sortie est une bibliothèque dynamiquement liée (DLL) au lieu d'un exécutable normal. Vous devriez nommer la sortie "*.dll" lorsque vous utilisez cette option. De plus, l'éditeur de liens prend entièrement en charge les fichiers "*.def" standard, qui peuvent être spécifiés sur la ligne de commande de l'éditeur de liens comme un fichier objet (en fait, il devrait précéder les archives dont il exporte des symboles, pour s'assurer qu'ils sont liés, tout comme un fichier objet normal).

    En plus des options communes à toutes les cibles, l'éditeur de liens i386 PE prend en charge des options de ligne de commande supplémentaires spécifiques à la cible i386 PE. Les options qui prennent des valeurs peuvent être séparées de leurs valeurs par un espace ou un signe égal.

    --add-stdcall-alias
    Si donné, les symboles avec un suffixe stdcall (@nn) seront exportés tels quels et aussi avec le suffixe retiré. [Cette option est spécifique au port de l'éditeur de liens ciblant i386 PE]
    --base-file fichier
    Utiliser fichier comme nom d'un fichier dans lequel sauvegarder les adresses de base de toutes les relocalisations nécessaires pour générer des DLL avec dlltool. [Ceci est une option spécifique à i386 PE]
    --dll
    Créer une DLL au lieu d'un exécutable normal. Vous pouvez également utiliser -shared ou spécifier une "LIBRARY" dans un fichier ".def" donné. [Cette option est spécifique au port de l'éditeur de liens ciblant i386 PE]
    --enable-long-section-names
    --disable-long-section-names
    Les variantes PE du format d'objet COFF ajoutent une extension qui permet l'utilisation de noms de section plus longs que huit caractères, la limite normale pour COFF. Par défaut, ces noms ne sont que
    autorisé dans les fichiers objets, car les images exécutables entièrement liées ne contiennent pas la table de chaînes COFF requise pour prendre en charge les noms plus longs. En tant qu'extension GNU, il est possible d'autoriser leur utilisation dans les images exécutables également, ou de (probablement inutilement !) les interdire dans les fichiers objets, en utilisant ces deux options. Les images exécutables générées avec ces noms de section longs sont légèrement non standard, car elles contiennent une table de chaînes, et peuvent générer une sortie confuse lorsqu'elles sont examinées avec des outils non-GNU compatibles PE, tels que les visualiseurs de fichiers et les dumpers. Cependant, GDB s'appuie sur l'utilisation des noms de section longs PE pour trouver les sections d'informations de débogage Dwarf-2 dans une image exécutable à l'exécution, et donc si aucune des options n'est spécifiée sur la ligne de commande, ld activera les noms de section longs, outrepassant le comportement par défaut et techniquement correct, lorsqu'il détecte la présence d'informations de débogage lors de la liaison d'une image exécutable et que les symboles ne sont pas supprimés. [Cette option est valide pour tous les ports du lieur ciblant PE]
    --enable-stdcall-fixup
    --disable-stdcall-fixup
    Si le lieur trouve un symbole qu'il ne peut pas résoudre, il tentera de faire un « liaison floue » en recherchant un autre symbole défini qui diffère uniquement dans le format du nom du symbole (cdecl vs stdcall) et résoudra ce symbole en le liant à la correspondance. Par exemple, le symbole indéfini "_foo" pourrait être lié à la fonction "_foo@12", ou le symbole indéfini "_bar@16" pourrait être lié à la fonction "_bar". Lorsque le lieur fait cela, il affiche un avertissement, car normalement il aurait dû échouer à la liaison, mais parfois les bibliothèques d'importation générées à partir de dll tierces peuvent nécessiter cette fonctionnalité pour être utilisables. Si vous spécifiez --enable-stdcall-fixup, cette fonctionnalité est entièrement activée et les avertissements ne sont pas imprimés. Si vous spécifiez --disable-stdcall-fixup, cette fonctionnalité est désactivée et de telles incompatibilités sont considérées comme des erreurs. [Cette option est spécifique au port du lieur ciblant i386 PE]
    --leading-underscore
    --no-leading-underscore
    Pour la plupart des cibles, le préfixe de symbole par défaut est un trait de soulignement et est défini dans la description de la cible. Avec cette option, il est possible de désactiver/activer le préfixe de symbole de trait de soulignement par défaut.
    --export-all-symbols
    Si spécifié, tous les symboles globaux des objets utilisés pour construire une DLL seront exportés par la DLL. Notez que c'est le comportement par défaut s'il n'y aurait autrement aucun symbole exporté. Lorsque les symboles sont explicitement exportés via des fichiers DEF ou implicitement exportés via des attributs de fonction, le comportement par défaut est de ne rien exporter d'autre sauf si cette option est spécifiée. Notez que les symboles "DllMain@12", "DllEntryPoint@0", "DllMainCRTStartup@12", et "impure_ptr" ne seront pas exportés automatiquement. De plus, les symboles importés d'autres DLL ne seront pas réexportés, ni les symboles spécifiant la disposition interne de la DLL tels que ceux commençant par "_head_" ou se terminant par "_iname". De plus, aucun symbole de "libgcc", "libstd++", "libmingw32", ou "crtX.o" ne sera exporté. Les symboles dont les noms commencent par "__rtti_" ou "__builtin_" ne seront pas exportés, pour aider avec les DLL C++. Enfin, il existe une liste étendue de symboles privés à cygwin qui ne sont pas exportés (évidemment, cela s'applique lors de la construction de DLL pour les cibles cygwin). Ces exclusions cygwin sont : "_cygwin_dll_entry@12", "_cygwin_crt0_common@8", "_cygwin_noncygwin_dll_entry@12", "_fmode", "_impure_ptr", "cygwin_attach_dll", "cygwin_premain0", "cygwin_premain1", "cygwin_premain2", "cygwin_premain3", et "environ". [Cette option est spécifique au port du lieur ciblant i386 PE]
    --exclude-symbols symbole,symbole,...
    Spécifie une liste de symboles qui ne doivent pas être exportés automatiquement. Les noms de symboles peuvent être délimités par des virgules ou des deux-points. [Cette option est spécifique au port du lieur ciblant i386 PE]
    --exclude-all-symbols
    Spécifie qu'aucun symbole ne doit être exporté automatiquement. [Cette option est spécifique au port du lieur ciblant i386 PE]
    --file-alignment
    Spécifie l'alignement du fichier. Les sections dans le fichier commenceront toujours à des décalages de fichier qui sont des multiples de ce nombre. La valeur par défaut est 512. [Cette option est spécifique au port du lieur ciblant i386 PE]
    --heap réservation
    --heap réservation,validation
    Spécifie le nombre d'octets de mémoire à réserver (et éventuellement valider) à utiliser comme tas pour ce programme. La valeur par défaut est 1 Mo réservé, 4 Ko validés. [Cette option est spécifique au port du lieur ciblant i386 PE]
    --image-base valeur
    Utilise valeur comme adresse de base de votre programme ou DLL. C'est le plus bas emplacement mémoire qui sera utilisé lors du chargement de votre programme ou de votre DLL. Pour réduire le besoin de relocalisation et améliorer les performances de vos DLL, chacune devrait avoir une adresse de base unique et ne pas chevaucher d'autres DLL. La valeur par défaut est 0x400000 pour les exécutables, et 0x10000000 pour les DLL. [Cette option est spécifique au port du lieur ciblant i386 PE]
    --kill-at
    Si spécifié, les suffixes stdcall (@nn) seront supprimés des symboles avant leur exportation. [Cette option est spécifique au port du lieur ciblant i386 PE]
    --large-address-aware
    Si spécifié, le bit approprié dans le champ « Characteristics » de l'en-tête COFF est défini pour indiquer que cet exécutable prend en charge les adresses virtuelles supérieures à 2 gigaoctets. Ceci doit être utilisé conjointement avec le commutateur /3GB ou /USERVA=valeur mégaoctets dans la section « [operating systems] » du fichier BOOT.INI. Sinon, ce bit n'a aucun effet. [Cette option est spécifique aux ports du lieur ciblant PE]
    --disable-large-address-aware
    Annule l'effet d'une option précédente --large-address-aware. Ceci est utile si --large-address-aware est toujours défini par le pilote du compilateur (par exemple, Cygwin gcc) et que l'exécutable ne prend pas en charge les adresses virtuelles supérieures à 2 gigaoctets. [Cette option est spécifique aux ports du lieur ciblant PE]
    --major-image-version valeur
    Définit le numéro majeur de la « version de l'image ». La valeur par défaut est 1. [Cette option est spécifique au port du lieur ciblant i386 PE]
    --major-os-version valeur
    Définit le numéro majeur de la « version du système d'exploitation ». La valeur par défaut est 4. [Cette option est spécifique au port du lieur ciblant i386 PE]
    --major-subsystem-version valeur
    Définit le numéro majeur de la « version du sous-système ». La valeur par défaut est 4. [Cette option est spécifique au port du lieur ciblant i386 PE]
    --minor-image-version valeur
    Définit le numéro mineur de la « version de l'image ». La valeur par défaut est 0. [Cette option est spécifique au port du lieur ciblant i386 PE]
    --minor-os-version valeur
    Définit le numéro mineur de la « version du système d'exploitation ». La valeur par défaut est 0. [Cette option est spécifique au port du lieur ciblant i386 PE]
    --minor-subsystem-version valeur
    Définit le numéro mineur de la « version du sous-système ». La valeur par défaut est 0. [Cette option est spécifique au port du lieur ciblant i386 PE]
    --output-def fichier
    Le lieur créera le fichier fichier qui contiendra un fichier DEF correspondant à la DLL que le lieur génère. Ce fichier DEF (qui devrait être nommé "*.def") peut être utilisé pour créer une bibliothèque d'importation avec "dlltool" ou peut être utilisé comme référence pour les symboles exportés automatiquement ou implicitement. [Cette option est spécifique au port du lieur ciblant i386 PE]
    --enable-auto-image-base
    --enable-auto-image-base=valeur
    Choisit automatiquement la base d'image pour les DLL, en commençant éventuellement par la base valeur, sauf si une est spécifiée à l'aide de l'argument "--image-base". [Cette option est spécifique au port du lieur ciblant i386 PE]

    Note : L'utilisation de l'extension 'auto-import' rendra la section de texte du fichier image modifiable en écriture. Ceci n'est pas conforme à la spécification du format PE-COFF publiée par Microsoft.

    Note - l'utilisation de l'extension 'auto-import' entraînera également le placement des données en lecture seule qui seraient normalement placées dans la section .rdata, dans la section .data à la place. Ceci afin de contourner un problème avec les constantes qui est décrit ici : http://www.cygwin.com/ml/cygwin/2004-09/msg01101.html

    L'utilisation de 'auto-import' fonctionnera généralement « sans problème » - mais parfois vous verrez ce message :

    "variable '<var>' ne peut pas être auto-importée. Veuillez lire la documentation de ld concernant "--enable-auto-import" pour plus de détails."

    Ce message survient lorsque certaines (sous-)expressions accèdent à une adresse donnée ultimement par la somme de deux constantes (les tables d'importation Win32 n'autorisent qu'une seule). Les instances où cela peut se produire incluent les accès aux champs membres de variables structurées importées d'une DLL, ainsi que l'utilisation d'un indice constant dans une variable tableau importée d'une DLL. Toute variable multi-mots (tableaux, structures, long long, etc.) peut déclencher cette condition d'erreur. Cependant, quel que soit le type de données exact de la variable exportée fautive, ld la détectera toujours, émettra l'avertissement et quittera.

    Il existe plusieurs façons de résoudre cette difficulté, quel que soit le type de données de la variable exportée :

    Une façon est d'utiliser le commutateur --enable-runtime-pseudo-reloc. Ceci laisse la tâche d'ajuster les références dans votre code client à l'environnement d'exécution, donc cette méthode ne fonctionne que lorsque l'environnement d'exécution prend en charge cette fonctionnalité.

    Une deuxième solution consiste à forcer l'une des 'constantes' à être une variable - c'est-à-dire, inconnue et non optimisable au moment de la compilation. Pour les tableaux, il y a deux possibilités : a) rendre l'indexé (l'adresse du tableau) une variable, ou b) rendre l'indice 'constant' une variable. Ainsi :

    extern type extern_array[];
extern_array[1] -->
   { volatile type *t=extern_array; t[1] }

    ou

    extern type extern_array[];
extern_array[1] -->
   { volatile int t=1; extern_array[t] }

    Pour les structures (et la plupart des autres types de données multi-mots), la seule option est de rendre la structure elle-même (ou le long long, ou le ...) variable :

    extern struct s extern_struct;
extern_struct.field -->
   { volatile struct s *t=&extern_struct; t->field }

    ou

    extern long long extern_ll;
extern_ll -->
  { volatile long long * local_ll=&extern_ll; *local_ll }

    Une troisième méthode pour traiter cette difficulté est d'abandonner 'auto-import' pour le symbole fautif et de le marquer avec "__declspec(dllimport)". Cependant, en pratique, cela nécessite l'utilisation de #defines au moment de la compilation pour indiquer si vous construisez une DLL, si vous construisez du code client qui se liera à la DLL, ou si vous construisez/liez simplement à une bibliothèque statique. En faisant le choix entre les différentes méthodes pour résoudre le problème de 'adresse directe avec décalage constant', vous devriez considérer l'usage typique dans le monde réel :

    Original :

    --foo.h
extern int arr[];
--foo.c
#include "foo.h"
void main(int argc, char **argv){
  printf("%d\n",arr[1]);
}

    Solution 1 :

    --foo.h
extern int arr[];
--foo.c
#include "foo.h"
void main(int argc, char **argv){
  /* Ce contournement est pour win32 et cygwin ; ne pas "optimiser" */
  volatile int *parr = arr;
  printf("%d\n",parr[1]);
}

    Solution 2 :

    --foo.h
/* Note : auto-export est supposé (pas de __declspec(dllexport)) */
#if (defined(_WIN32) || defined(__CYGWIN__)) && \
  !(defined(FOO_BUILD_DLL) || defined(FOO_STATIC))
#define FOO_IMPORT __declspec(dllimport)
#else
#define FOO_IMPORT
#endif
extern FOO_IMPORT int arr[];
--foo.c
#include "foo.h"
void main(int argc, char **argv){
  printf("%d\n",arr[1]);
}

    Une quatrième façon d'éviter ce problème est de recoder votre bibliothèque pour utiliser une interface fonctionnelle plutôt qu'une interface de données pour les variables fautives (par exemple, des fonctions d'accès set_foo() et get_foo()).

    OPTIONS

    The following options are supported to control the handling of sections in the output file.

    --[no-]alloc-section name
    This option controls whether the section named name is allocated or not. By default, all sections are allocated.
    --[no-]discard-section name
    This option controls whether the section named name is discarded or not. By default, no sections are discarded.
    --[no-]keep-section name
    This option controls whether the section named name is kept or not. By default, all sections are kept.
    --[no-]relocatable-output
    This option controls whether the output file is to be treated as relocatable. This is the default behaviour for the native linker, but other linkers may not support it. When output is relocatable, the linker will not perform any relocations itself, but will instead produce a relocatable executable file which can be used as input to another linker. This option is disabled by default.
    --[no-]split-relocs
    This option controls whether relocations are split into separate sections. This can be useful for some targets, but may make the output file larger. This option is enabled by default.

    --insert-timestamp

    Insère un véritable horodatage dans l'image. C'est le comportement par défaut car il correspond au code hérité et signifie que l'image fonctionnera avec d'autres outils propriétaires. Le problème avec ce défaut est qu'il en résultera des images légèrement différentes produites à chaque fois que les mêmes sources sont liées.     -N
    --omagic
    Marque la sortie comme "OMAGIC" (0407) dans l'en-tête a.out pour indiquer que le segment de texte ne doit pas être protégé en écriture et partagé.     -n
    --nmagic
    Marque la sortie comme "NMAGIC" (0410) dans l'en-tête a.out pour indiquer que lorsque le fichier de sortie est exécuté, la partie texte sera en lecture seule et partageable entre tous les processus exécutant le même fichier.     -z
    --imagic
    Marque la sortie comme "IMAGIC" (0411) dans l'en-tête a.out pour indiquer que lorsque le fichier de sortie est exécuté, les zones de texte et de données du programme seront chargées dans des espaces d'adressage séparés en utilisant la fonctionnalité d'espace d'instructions et de données séparés de l'unité de gestion de mémoire dans les modèles plus grands du PDP11. Cela double l'espace d'adressage disponible pour le programme. Le segment de texte est à nouveau pur, protégé en écriture et partageable. La seule différence dans le format de sortie entre cette option et les autres, outre le nombre magique, est que les segments de texte et de données commencent tous deux à l'emplacement 0. L'option -z sélectionnait ce format dans 2.11BSD. Cette option crée un format d'exécutable séparé.

    Équivalent à --nmagic pour pdp11-aout.

    ENVIRONMENT

    Vous pouvez modifier le comportement de ld avec les variables d'environnement "GNUTARGET", "LDEMULATION" et "COLLECT_NO_DEMANGLE".

    "GNUTARGET" détermine le format d'objet du fichier d'entrée si vous n'utilisez pas -b (ou son synonyme --format). Sa valeur doit être l'un des noms BFD pour un format d'entrée. S'il n'y a pas de "GNUTARGET" dans l'environnement, ld utilise le format naturel de la cible. Si "GNUTARGET" est défini sur "default", alors BFD tente de découvrir le format d'entrée en examinant les fichiers d'entrée binaires ; cette méthode réussit souvent, mais il existe des ambiguïtés potentielles, car il n'y a pas de méthode pour garantir que le nombre magique utilisé pour spécifier les formats de fichiers objet est unique. Cependant, la procédure de configuration pour BFD sur chaque système place le format conventionnel pour ce système en premier dans la liste de recherche, donc les ambiguïtés sont résolues en faveur de la convention.

    "LDEMULATION" détermine l'émulation par défaut si vous n'utilisez pas l'option -m. L'émulation peut affecter divers aspects du comportement de l'éditeur de liens, en particulier le script de l'éditeur de liens par défaut. Vous pouvez lister les émulations disponibles avec les options --verbose ou -V. Si l'option -m n'est pas utilisée, et que la variable d'environnement "LDEMULATION" n'est pas définie, l'émulation par défaut dépend de la manière dont l'éditeur de liens a été configuré.

    Normalement, l'éditeur de liens effectue le démangling des symboles par défaut. Cependant, si "COLLECT_NO_DEMAN

    E" est défini dans l'environnement, alors il sera par défaut de ne pas démangler les symboles. Cette variable d'environnement est utilisée de manière similaire par le "gcc" programme d'enrobage de l'éditeur de liens. La valeur par défaut peut être remplacée par les options --demangle et --no-demangle.
