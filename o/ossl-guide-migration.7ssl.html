ossl-guide-migration, migration_guide - Guide OpenSSL : Migration depuis d'anciennes versions d'OpenSSL

SYNTAXE

Voir les pages de manuel individuelles pour plus de détails.

DESCRIPTION

Ce guide détaille les changements requis pour migrer vers de nouvelles versions d'OpenSSL. Actuellement, il couvre OpenSSL 3.0 et 3.1. Pour les versions antérieures, référez-vous à https://github.com/openssl/openssl/blob/master/CHANGES.md. Pour un aperçu de certains des concepts clés introduits dans OpenSSL 3.0, consultez crypto(7).

OPENSSL 3.6

Changements principaux depuis OpenSSL 3.5

Les fonctions EVP_PKEY_asn1_*() et EVP_PKEY_get0_asn1(3) ont été dépréciées au profit de l'API du fournisseur. EVP_PKEY_assign_[DSA|SIPHASH]() ont également été dépréciées. Veuillez utiliser la nouvelle API de haut niveau et du fournisseur.

OPENSSL 3.1

Changements principaux depuis OpenSSL 3.0

Le fournisseur FIPS dans OpenSSL 3.1 inclut certains algorithmes non validés FIPS, par conséquent la requête de propriété "fips=yes" est obligatoire pour les applications qui souhaitent fonctionner d'une manière approuvée par FIPS. Les algorithmes sont :

Triple DES ECB
Triple DES CBC
EdDSA

Il n'y a pas d'autres changements nécessitant des mesures de migration supplémentaires depuis OpenSSL 3.0.

OPENSSL 3.0

Changements principaux depuis OpenSSL 1.1.1

Publication majeure

OpenSSL 3.0 est une publication majeure et par conséquent toute application qui utilise actuellement une version plus ancienne d'OpenSSL devra au minimum être recompilée pour fonctionner avec la nouvelle version. L'intention est que la grande majorité des applications fonctionneront sans modification avec OpenSSL 3.0 si ces applications fonctionnaient auparavant avec OpenSSL 1.1.1. Cependant, cela n'est pas garanti et certains changements peuvent être requis dans certains cas. Des changements peuvent également être requis si les applications doivent tirer parti de certaines des nouvelles fonctionnalités disponibles dans OpenSSL 3.0, telles que la disponibilité du module FIPS.

Changement de licence

Dans les versions précédentes, OpenSSL était licencié sous les licences doubles OpenSSL et SSLeay https://www.openssl.org/source/license-openssl-ssleay.txt (les deux licences s'appliquent). À partir d'OpenSSL 3.0, celle-ci est remplacée par la licence Apache v2 https://www.openssl.org/source/apache-license-2.0.txt.

Fournisseurs et support FIPS

L'un des changements clés par rapport à OpenSSL 1.1.1 est l'introduction du concept de Fournisseur (Provider). Les fournisseurs regroupent et rendent disponibles les implémentations d'algorithmes. Avec OpenSSL 3.0, il est possible de spécifier, soit par programmation, soit via un fichier de configuration, les fournisseurs que vous souhaitez utiliser pour une application donnée. OpenSSL 3.0 est livré avec 5 fournisseurs différents en standard. Au fil du temps, des tiers peuvent distribuer des fournisseurs supplémentaires qui peuvent être intégrés à OpenSSL. Toutes les implémentations d'algorithmes accessibles via les fournisseurs sont accessibles via les API « de haut niveau » (par exemple, les fonctions préfixées par "EVP"). Elles ne peuvent pas être accessibles en utilisant les « API de bas niveau ».

L'un des fournisseurs standard disponibles est le fournisseur FIPS. Celui-ci rend disponibles les algorithmes cryptographiques validés FIPS. Le fournisseur FIPS est désactivé par défaut et doit être explicitement activé au moment de la configuration en utilisant l'option "enable-fips". S'il est activé, le fournisseur FIPS est compilé et installé en plus des autres fournisseurs standard. Aucune procédure d'installation distincte n'est nécessaire. Il existe cependant une cible `make` dédiée "install_fips", qui sert le but spécial d'installer uniquement le fournisseur FIPS dans une installation OpenSSL existante.

Tous les algorithmes ne peuvent pas être disponibles pour l'application à un moment donné. Si le code de l'application utilise un algorithme de hachage ou de chiffrement via l'interface EVP, l'application doit vérifier le résultat des fonctions EVP_EncryptInit(3), EVP_EncryptInit_ex(3), et EVP_DigestInit(3). Dans le cas où l'algorithme demandé n'est pas disponible, ces fonctions échoueront.

Voir aussi « Algorithmes Hérités » pour des informations sur le fournisseur hérité.

Voir aussi « Compléter l'installation du Module FIPS » et « Utiliser le Module FIPS dans les applications ».

API de bas niveau

OpenSSL a historiquement fourni deux ensembles d'API pour invoquer des algorithmes cryptographiques : les API « de haut niveau » (telles que les API "EVP") et les API « de bas niveau ». Les API de haut niveau sont généralement conçues pour fonctionner sur tous les types d'algorithmes. Les API « de bas niveau » ciblent une implémentation d'algorithme spécifique. Par exemple, les API EVP fournissent les fonctions EVP_EncryptInit_ex(3), EVP_EncryptUpdate(3) et EVP_EncryptFinal(3) pour effectuer le chiffrement symétrique. Ces fonctions peuvent être utilisées avec les algorithmes AES, CHACHA, 3DES, etc. D'autre part, pour effectuer un chiffrement AES en utilisant les API de bas niveau, il faudrait appeler des fonctions spécifiques à AES telles que AES_set_encrypt_key(3), AES_encrypt(3), et ainsi de suite. Les fonctions pour 3DES sont différentes. L'utilisation des API de bas niveau a été officieusement découragée par l'équipe de développement d'OpenSSL pendant longtemps. Cependant, dans OpenSSL 3.0, cela devient plus formel. Toutes ces API de bas niveau ont été dépréciées. Vous pouvez toujours les utiliser dans vos applications, mais vous pourriez commencer à voir des avertissements de dépréciation pendant la compilation (en fonction du support du compilateur pour cela). Les API dépréciées peuvent être supprimées des versions futures d'OpenSSL, vous êtes donc fortement encouragé à mettre à jour votre code pour utiliser les API de haut niveau à la place.

Ceci est décrit plus en détail dans « Dépréciation des fonctions de bas niveau ».

Algorithmes Hérités

Certains algorithmes cryptographiques tels que MD2 et DES qui étaient disponibles via les API EVP sont maintenant considérés comme hérités et leur utilisation est fortement déconseillée. Ces algorithmes EVP hérités sont toujours disponibles dans OpenSSL 3.0 mais pas par défaut. Si vous souhaitez les utiliser, vous devez charger le fournisseur hérité. Cela peut être aussi simple qu'une modification de fichier de configuration, ou peut être fait par programmation. Voir OSSL_PROVIDER-legacy(7) pour une liste complète des algorithmes. Les applications utilisant les API EVP pour accéder à ces algorithmes devraient plutôt utiliser des algorithmes plus modernes. Si cela n'est pas possible, ces applications doivent s'assurer que le fournisseur hérité a été chargé. Cela peut être réalisé soit par programmation, soit via la configuration. Voir la page de manuel crypto(7) pour plus d'informations sur les fournisseurs.

Moteurs et API « METHOD »

Le refactoring pour supporter les Fournisseurs entre en conflit en interne avec les API utilisées pour supporter les moteurs, y compris l'API ENGINE et toute fonction qui crée ou modifie des « METHODS » personnalisés (par exemple EVP_MD_meth_new(3), EVP_CIPHER_meth_new(3), EVP_PKEY_meth_new(3), RSA_meth_new(3), EC_KEY_METHOD_new(3), etc.). Ces fonctions sont dépréciées dans OpenSSL 3.0, et les utilisateurs de ces API doivent savoir que leur utilisation peut probablement contourner la sélection et la configuration des fournisseurs, avec des conséquences imprévues. C'est particulièrement

pertinent pour les applications écrites pour utiliser le module OpenSSL 3.0 FIPS, comme détaillé ci-dessous. Les auteurs et mainteneurs de moteurs externes sont fortement encouragés à refactoriser leur code en transformant les moteurs en fournisseurs en utilisant la nouvelle API de fournisseur et en évitant les méthodes obsolètes.

Support des moteurs hérités

Si openssl n'est pas compilé sans support des moteurs ou sans support des API obsolètes, les moteurs continueront de fonctionner. Cependant, leur applicabilité sera limitée.

Les nouveaux algorithmes fournis via les moteurs fonctionneront toujours.

Les clés basées sur les moteurs peuvent être chargées via une implémentation personnalisée OSSL_STORE. Dans ce cas, les objets EVP_PKEY créés via ENGINE_load_private_key(3) seront considérés comme hérités et continueront de fonctionner.

Pour assurer la compatibilité future, les moteurs doivent être transformés en fournisseurs. Pour préférer la décharge matérielle basée sur les fournisseurs, vous pouvez spécifier les propriétés par défaut pour préférer votre fournisseur.

La définition de méthodes cryptographiques de bas niveau par défaut, basées sur les moteurs ou les applications, telles que RSA_METHOD ou EC_KEY_METHOD, est toujours possible et les clés dans le fournisseur par défaut utiliseront l'implémentation basée sur les moteurs pour les opérations cryptographiques. Cependant, les EVP_PKEY créés par décodage à l'aide de OSSL_DECODER, des API PEM_ ou d2i_ seront basés sur les fournisseurs. Pour créer des EVP_PKEY entièrement hérités, les fonctions EVP_PKEY_set1_RSA(3), EVP_PKEY_set1_EC_KEY(3) ou similaires doivent être utilisées.

Schéma de versionnement

Le schéma de versionnement d'OpenSSL a changé avec la sortie d'OpenSSL 3.0. Le nouveau schéma de versionnement a ce format :

MAJEUR.MINEUR.PATCH

Pour OpenSSL 1.1.1 et les versions antérieures, différents niveaux de correctifs étaient indiqués par une lettre à la fin du numéro de version de publication. Cela ne sera plus utilisé et le niveau de correctif sera indiqué par le dernier chiffre de la version. Un changement dans le deuxième chiffre (MINEUR) indique que de nouvelles fonctionnalités peuvent avoir été ajoutées. Les versions d'OpenSSL avec le même numéro majeur sont compatibles API et ABI. Si le numéro majeur change, la compatibilité API et ABI n'est pas garantie.

Pour plus d'informations, voir OpenSSL_version(3).

Autres nouvelles fonctionnalités majeures

Protocole de gestion de certificats (CMP, RFC 4210)

Cela couvre également CRMF (RFC 4211) et le transfert HTTP (RFC 6712). Voir openssl-cmp(1) et OSSL_CMP_exec_certreq(3) comme points de départ.

Client HTTP(S)

Un client HTTP(S) complet prenant en charge GET et POST, la redirection, les contenus en texte brut et encodés ASN.1, les proxys et les délais d'attente.

API de fonction de dérivation de clé (EVP_KDF)

Cela simplifie le processus d'ajout de nouvelles implémentations de KDF et de PRF.

Auparavant, les algorithmes de KDF étaient contraints d'utiliser l'objet EVP_PKEY, ce qui n'était pas une correspondance logique. Les applications existantes qui utilisent des algorithmes de KDF via EVP_PKEY (scrypt, TLS1 PRF et HKDF) peuvent être plus lentes car elles utilisent un pont EVP_KDF en interne. Toutes les nouvelles applications devraient utiliser la nouvelle interface EVP_KDF(3). Voir également « Fonction de dérivation de clé (KDF) » dans OSSL_PROVIDER-default(7) et « Fonction de dérivation de clé (KDF) » dans OSSL_PROVIDER-FIPS(7).

API de code d'authentification de message (EVP_MAC)

Cela simplifie le processus d'ajout d'implémentations de MAC.

Cela inclut un pont générique EVP_PKEY vers EVP_MAC, pour faciliter l'utilisation continue des MAC via des clés privées brutes dans des fonctionnalités telles que EVP_DigestSign(3) et EVP_DigestVerify(3).

Toutes les nouvelles applications devraient utiliser la nouvelle interface EVP_MAC(3). Voir également « Code d'authentification de message (MAC) » dans OSSL_PROVIDER-default(7) et « Code d'authentification de message (MAC) » dans OSSL_PROVIDER-FIPS(7).

Récupération d'algorithmes

L'utilisation d'appels à des fonctions pratiques telles que EVP_sha256() et EVP_aes_256_gcm() peut entraîner une pénalité de performance lors de l'utilisation de fournisseurs. La récupération d'algorithmes à partir de fournisseurs implique une recherche d'algorithme par nom. C'est beaucoup plus lent que d'accéder directement à une table de méthodes. Il est recommandé de pré-charger les algorithmes si un algorithme est utilisé plusieurs fois. Voir « Performance » dans crypto(7), « Récupération explicite » dans crypto(7) et « Récupération implicite » dans crypto(7).

Support pour le TLS du noyau Linux

Pour utiliser KTLS, son support doit être compilé à l'aide de l'option de configuration "enable-ktls". Il doit également être activé à l'exécution à l'aide de l'option SSL_OP_ENABLE_KTLS.

Nouveaux algorithmes

  • Algorithmes KDF « SINGLE STEP » et « SSH »

    Voir EVP_KDF-SS(7) et EVP_KDF-SSHKDF(7)

  • Algorithmes MAC « GMAC » et « KMAC »

    Voir EVP_MAC-GMAC(7) et EVP_MAC-KMAC(7).

  • Algorithme KEM « RSASVE »

    Voir EVP_KEM-RSA(7).

  • Algorithme de chiffrement « AES-SIV »

    Voir « Mode SIV » dans EVP_EncryptInit(3).

  • Chiffrements inverses de KEM AES pris en charge par la couche EVP.

    Les chiffrements inverses utilisent le déchiffrement AES pour l'enveloppement et le chiffrement AES pour le déballage. Les algorithmes sont : « AES-128-WRAP-INV », « AES-192-WRAP-INV », « AES-256-WRAP-INV », « AES-128-WRAP-PAD-INV », « AES-192-WRAP-PAD-INV » et « AES-256-WRAP-PAD-INV ».

  • Chiffrements CTS ajoutés à la couche EVP.

    Les algorithmes sont « AES-128-CBC-CTS », « AES-192-CBC-CTS », « AES-256-CBC-CTS », « CAMELLIA-128-CBC-CTS », « CAMELLIA-192-CBC-CTS » et « CAMELLIA-256-CBC-CTS ». Les variantes CS1, CS2 et CS3 sont supportées.

Mises à jour CMS et PKCS#7

  • Ajout du support de vérification de signature CAdES-BES.
  • Ajout du schéma de signature CAdES-BES et du support des attributs (RFC 5126) à l'API CMS.
  • Ajout du type de contenu AuthEnvelopedData (RFC 5083) utilisant AES_GCM

    Utilise le paramètre AES-GCM (RFC 5084) pour la syntaxe de message cryptographique. Son but est de supporter le chiffrement et le déchiffrement d'une enveloppe numérique qui est à la fois authentifiée et chiffrée en mode AES GCM.

  • PKCS7_get_octet_string(3) et PKCS7_type_is_other(3) ont été rendus publics.

Mises à jour de l'API PKCS#12

Les algorithmes par défaut pour la création de pkcs12 avec la fonction PKCS12_create() ont été modifiés pour utiliser des algorithmes plus modernes basés sur PBKDF2 et AES. Le nombre d'itérations MAC par défaut a été modifié pour PKCS12_DEFAULT_ITER afin qu'il soit égal au nombre d'itérations de chiffrement basé sur mot de passe. L'algorithme de digest par défaut pour le calcul MAC a été modifié en SHA-256. L'application pkcs12 prend maintenant en charge l'option -legacy qui restaure les algorithmes par défaut précédents pour supporter l'interopérabilité avec les systèmes hérités.

Ajout d'API PKCS#12 améliorées qui acceptent un contexte de bibliothèque OSSL_LIB_CTX et (le cas échéant) une requête de propriétés. D'autres API qui gèrent les objets PKCS#7 et PKCS#8 ont également été améliorées si nécessaire. Cela inclut :

PKCS12_add_key_ex(3), PKCS12_add_safe_ex(3), PKCS12_add_safes_ex(3), PKCS12_create_ex(3), PKCS12_decrypt_skey_ex(3), PKCS12_init_ex(3), PKCS12_item_decrypt_d2i_ex(3), PKCS12_item_i2d_encrypt_ex(3), PKCS12_key_gen_asc_ex(3), PKCS12_key_gen_uni_ex(3), PKCS12_key_gen_utf8_ex(3), PKCS12_pack_p7encdata_ex(3), PKCS12_pbe_crypt_ex(3), PKCS12_PBE_keyivgen_ex(3), PKCS12_SAFEBAG_create_pkcs8_encrypt_ex(3), PKCS5_pbe2_set_iv_ex(3), PKCS5_pbe_set0_algor_ex(3), PKCS5_pbe_set_ex(3), PKCS5_pbkdf2_set_ex(3), PKCS5_v2_PBE_keyivgen_ex(3), PKCS5_v2_scrypt_keyivgen_ex(3), PKCS8_decrypt_ex(3), PKCS8_encrypt_ex(3), PKCS8_set0_pbe_ex(3).

Dans le cadre de ce changement, les API EVP_PBE_xxx peuvent également accepter un contexte de bibliothèque et une requête de propriétés et appeler une version étendue de la fonction de dérivation de clé/IV qui supporte ces paramètres. Cela inclut EVP_PBE_CipherInit_ex(3), EVP_PBE_find_ex(3) et EVP_PBE_scrypt_ex(3).

KDF PKCS#12 contre FIPS

Contrairement à la version 1.x.y, le PKCS12KDF utilisé lors de la création d'une structure PKCS#12 avec un MAC qui ne fonctionne pas avec le fournisseur FIPS, car le PKCS12KDF n'est pas un mécanisme approuvé par FIPS.

Voir EVP_KDF-PKCS12KDF(7), PKCS12_create(3), openssl-pkcs12(1), OSSL_PROVIDER-FIPS(7).

Changements de synchronisation des threads sous Windows

La synchronisation des threads sous Windows utilise des primitives de lecture/écriture (SRWLock) lorsque le système d'exploitation le prend en charge, sinon CriticalSection continue d'être utilisé.

API de traçage

Une nouvelle API de traçage générique a été ajoutée, offrant un support pour l'activation de l'instrumentation via la sortie de traçage. Cette fonctionnalité est principalement destinée à aider les développeurs et est désactivée par défaut. Pour l'utiliser, OpenSSL doit être configuré avec l'option "enable-trace".

n.

Si l'API de traçage est activée, l'application peut activer la sortie de traçage en enregistrant des BIO en tant que canaux de traçage pour un certain nombre de catégories de traçage et de débogage. Voir OSSL_trace_enabled(3).

Mises à jour de la validation de clé

EVP_PKEY_public_check(3) et EVP_PKEY_param_check(3) fonctionnent désormais pour plus de types de clés. Cela inclut RSA, DSA, ED25519, X25519, ED448 et X448. Auparavant (en 1.1.1) ils renvoyaient -2. Pour les types de clés qui n'ont pas de paramètres, EVP_PKEY_param_check(3) renverra toujours 1.

Autres dépréciations et changements notables

La partie code fonction du code d'erreur OpenSSL n'est plus pertinente

Ce code est maintenant toujours défini sur zéro. Les fonctions associées sont obsolètes.

Les macros STACK et HASH ont été nettoyées

Les wrappers types sécurisés sont déclarés partout et implémentés une fois. Voir DEFINE_STACK_OF(3) et DEFINE_LHASH_OF_EX(3).

Le sous-système RAND_DRBG a été supprimé

Le nouveau EVP_RAND(3) est un remplacement partiel : le framework de rappel DRBG est absent. L'API RAND_DRBG ne s'intégrait pas bien dans le nouveau concept de fournisseur tel qu'implémenté par EVP_RAND et EVP_RAND_CTX.

Suppression de FIPS_mode() et FIPS_mode_set()

Ces fonctions sont des API héritées qui ne sont pas applicables au nouveau modèle de fournisseur. Les applications devraient plutôt utiliser EVP_default_properties_is_fips_enabled(3) et EVP_default_properties_enable_fips(3).

La génération de clés est plus lente

Le test de Miller-Rabin utilise maintenant 64 tours, ce qui est utilisé pour toute génération de nombres premiers, y compris la génération de clés RSA. Cela affecte le temps pour les tailles de clés plus grandes.

La méthode de génération de clés par défaut pour les clés RSA régulières à 2 nombres premiers a été modifiée pour utiliser la méthode FIPS186-4 B.3.6 (Génération de nombres premiers probables avec des conditions basées sur des nombres premiers probables auxiliaires). Cette méthode est plus lente que la méthode originale.

Changement de PBKDF2 pour être conforme à SP800-132 au lieu de l'ancien PKCS5 RFC2898

Cela vérifie que la longueur du sel est d'au moins 128 bits, que la longueur de la clé dérivée est d'au moins 112 bits, et que le nombre d'itérations est d'au moins 1000. Pour des raisons de compatibilité ascendante, ces vérifications sont désactivées par défaut dans le fournisseur par défaut, mais sont activées par défaut dans le fournisseur FIPS.

Pour activer ou désactiver les vérifications, voir OSSL_KDF_PARAM_PKCS5 dans EVP_KDF-PBKDF2(7). Le paramètre peut être défini en utilisant EVP_KDF_derive(3).

Application d'une taille minimale de modulus DH de 512 bits

Les tailles plus petites entraînent maintenant une erreur.

Changements des clés SM2

Les EVP_PKEY EC avec la courbe SM2 ont été retravaillées pour devenir automatiquement EVP_PKEY_SM2 plutôt qu'EVP_PKEY_EC.

Contrairement aux versions précédentes d'OpenSSL, cela signifie que les applications ne peuvent pas appeler EVP_PKEY_set_alias_type(pkey, EVP_PKEY_SM2) pour obtenir des calculs SM2.

La génération de paramètres et de clés a également été retravaillée pour permettre la génération de paramètres et de clés EVP_PKEY_SM2. Les applications doivent maintenant générer directement des clés SM2 et ne doivent pas d'abord créer une clé EVP_PKEY_EC. Il n'est plus possible d'importer une clé SM2 avec des paramètres de domaine autres que ceux de la courbe elliptique SM2.

La validation des clés SM2 a été séparée de la validation des clés EC régulières, permettant d'améliorer le processus de validation SM2 pour rejeter les clés privées chargées qui ne sont pas conformes à la norme ISO SM2. En particulier, un scalaire privé k en dehors de l'intervalle 1 <= k < n-1 est maintenant correctement rejeté.

Méthode EVP_PKEY_set_alias_type() supprimée

Cette fonction rendait un objet EVP_PKEY mutable après sa configuration. Dans OpenSSL 3.0, il a été décidé qu'une clé fournie ne devrait pas pouvoir changer son type, donc cette fonction a été supprimée.

Les fonctions qui renvoient une clé interne doivent être traitées comme en lecture seule

Les fonctions telles que EVP_PKEY_get0_RSA(3) se comportent légèrement différemment dans OpenSSL 3.0. Auparavant, elles renvoyaient un pointeur vers la clé de bas niveau utilisée en interne par libcrypto. Depuis OpenSSL 3.0, cette clé peut maintenant être détenue dans un fournisseur. L'appel de ces fonctions ne renverra qu'un handle sur la clé interne lorsque l'EVP_PKEY a été construit avec cette clé en premier lieu, par exemple en utilisant une fonction ou une macro telle que EVP_PKEY_assign_RSA(3), EVP_PKEY_set1_RSA(3), etc. Lorsque l'EVP_PKEY détient une clé gérée par un fournisseur, ces fonctions renvoient maintenant une copie mise en cache de la clé. Les changements apportés à la clé du fournisseur interne qui se produisent après la première fois que la clé mise en cache est accédée ne seront pas reflétés dans la copie mise en cache. De même, toute modification apportée à la copie mise en cache par le code de l'application ne sera pas reflétée dans la clé interne du fournisseur.

Pour les raisons susmentionnées, les clés renvoyées par ces fonctions doivent généralement être traitées comme en lecture seule. Pour souligner cela, la valeur renvoyée par EVP_PKEY_get0_RSA(3), EVP_PKEY_get0_DSA(3), EVP_PKEY_get0_EC_KEY(3) et EVP_PKEY_get0_DH(3) a été rendue const. Cela peut casser du code existant. Les applications cassées par ce changement doivent être modifiées. La solution préférée est de refactoriser le code pour éviter l'utilisation de ces fonctions obsolètes. À défaut, le code doit être modifié pour utiliser un pointeur const à la place. Les fonctions EVP_PKEY_get1_RSA(3), EVP_PKEY_get1_DSA(3), EVP_PKEY_get1_EC_KEY(3) et EVP_PKEY_get1_DH(3) continuent de renvoyer un pointeur non-const pour permettre de les "libérer". Cependant, elles doivent également être traitées comme en lecture seule.

La vérification de la clé publique a été déplacée de EVP_PKEY_derive() vers EVP_PKEY_derive_set_peer()

Cela peut entraîner une erreur dans EVP_PKEY_derive_set_peer(3) plutôt que lors de EVP_PKEY_derive(3). Pour désactiver cette vérification, utilisez EVP_PKEY_derive_set_peer_ex(dh, peer, 0).

Le format d'impression a des changements cosmétiques pour certaines fonctions

La sortie de nombreuses fonctions de "impression" telles que X509_signature_print(3), X509_print_ex(3), X509_CRL_print_ex(3), et d'autres fonctions similaires a été modifiée de telle sorte qu'il peut y avoir des différences cosmétiques entre la sortie observée en 1.1.1 et 3.0. Cela s'applique également à la sortie -text des applications openssl x509 et openssl crl.

Le mode interactif du programme openssl a été supprimé

Désormais, l'exécuter sans arguments équivaut à openssl help.

Les valeurs de retour d'erreur de certains appels de contrôle (ctrl) ont changé

Un changement significatif est que les contrôles qui renvoyaient auparavant -2 pour des entrées invalides renvoient maintenant -1 indiquant une condition d'erreur générique à la place.

Les types de clés DH et DHX ont des paramètres configurables différents

Auparavant (en 1.1.1), ces paramètres conflictuels étaient autorisés, mais entraîneront désormais des erreurs. Voir EVP_PKEY-DH(7) pour plus de détails. Cela affecte le comportement de openssl-genpkey(1) pour la génération de paramètres DH.

Changement de l'ordre de EVP_CIPHER_CTX_set_flags()

Si vous utilisez un chiffrement d'un fournisseur, le drapeau EVP_CIPH_FLAG_LENGTH_BITS ne peut être défini qu'après que le chiffrement a été assigné au contexte de chiffrement. Voir "FLAGS" dans EVP_EncryptInit(3) pour plus d'informations.

Validation des paramètres du contexte d'opération

En raison du déplacement de l'implémentation des opérations cryptographiques vers les fournisseurs, la validation de divers paramètres d'opération peut être reportée jusqu'à ce que l'opération réelle soit exécutée, alors qu'auparavant elle se produisait immédiatement lors de la définition d'un paramètre d'opération.

Par exemple, lors de la définition d'une courbe non prise en charge avec EVP_PKEY_CTX_set_ec_paramgen_curve_nid(), cet appel de fonction n'échouera pas, mais les opérations de génération de clés ultérieures avec l'EVP_PKEY_CTX échoueront.

Suppression du code fonction des codes d'erreur

La partie code fonction du code d'erreur est maintenant toujours définie sur 0. Pour cette raison, la macro ERR_GET_FUNC() a été supprimée. Les applications doivent résoudre les codes d'erreur uniquement en utilisant le numéro de bibliothèque et le code de raison.

Le chiffrement ChaCha20-Poly1305 n'autorise pas l'utilisation d'une longueur d'IV tronquée

Dans OpenSSL 3.0, définir la longueur de l'IV à une valeur autre que 12 entraînera une erreur. Avant OpenSSL 3.0, l'ivlen pouvait être inférieur à la longueur requise de 12 octets, en utilisant EVP_CIPHER_CTX_ctrl(ctx, EVP_CRTL_AEAD_SET_IVLEN, ivlen, NULL). Cela a résulté en un IV avec un remplissage initial de zéros.

Upgrading OpenSSL

This document describes issues that may arise when upgrading applications from older versions of OpenSSL to OpenSSL 3.0.

The primary difficulties are likely to be related to API changes that have been introduced. Most of these changes are intended to make OpenSSL easier to use and extend in the future. However, they do involve changes to existing code.

Upgrading from OpenSSL 1.1.1

Upgrading to OpenSSL 3.0 from OpenSSL 1.1.1 is a relatively straightforward task for most applications. The majority of the API remains compatible. However, there are a few areas where changes are required.

The main change is the introduction of the concept of "Providers". Previously, OpenSSL algorithms were built directly into the library. In OpenSSL 3.0, algorithms are loaded dynamically from providers. This means that applications can now choose which cryptographic algorithms to use, and can even load their own custom algorithms.

The main impact of this change is that functions that previously returned algorithm identifiers (e.g. EVP_sha256(3)) now return an opaque pointer to an algorithm. Applications will need to use the new algorithm fetching functions (e.g. EVP_MD_fetch(3)) to obtain these pointers. See "ALGORITHM FETCHING" in crypto(7) for details.

Additionally, many functions that previously took algorithm identifiers as arguments now take an algorithm name string instead. This allows the algorithm to be fetched from a provider. For example, a call to EVP_DigestInit_ex(3) previously took a digest algorithm identifier. It now takes a digest algorithm name string.

There are also some changes to error handling. Previously, OpenSSL used a set of error codes that were specific to the OpenSSL version. In OpenSSL 3.0, a new set of error codes has been introduced that are more generic. Applications that check for particular error reason codes on key loading failures might need an update.

Password-protected keys may deserve special attention. If only some errors are treated as an indicator that the user should be asked about the password again, it's worth testing these scenarios and processing the newly relevant codes.

There may be more cases to treat specially, depending on the calling application code.

Upgrading from OpenSSL 1.0.2

Upgrading to OpenSSL 3.0 from OpenSSL 1.0.2 is likely to be significantly more difficult. In addition to the issues discussed above in the section about "Upgrading from OpenSSL 1.1.1", the main things to be aware of are:

1.
The build and installation procedure has changed significantly.

Check the file INSTALL.md in the top of the installation for instructions on how to build and install OpenSSL for your platform. Also read the various NOTES files in the same directory, as applicable for your platform.

2.
Many structures have been made opaque in OpenSSL 3.0.

The structure definitions have been removed from the public header files and moved to internal header files. In practice this means that you can no longer stack allocate some structures. Instead they must be heap allocated through some function call (typically those function names have a "_new" suffix to them). Additionally you must use "setter" or "getter" functions to access the fields within those structures.

For example code that previously looked like this:

EVP_MD_CTX md_ctx;
/* This line will now generate compiler errors */
EVP_MD_CTX_init(&md_ctx);

The code needs to be amended to look like this:

EVP_MD_CTX *md_ctx;
md_ctx = EVP_MD_CTX_new();
...
...
EVP_MD_CTX_free(md_ctx);
3.
Support for TLSv1.3 has been added.

This has a number of implications for SSL/TLS applications. See the TLS1.3 page https://github.com/openssl/openssl/wiki/TLS1.3 for further details.

More details about the breaking changes between OpenSSL versions 1.0.2 and 1.1.0 can be found on the OpenSSL 1.1.0 Changes page https://github.com/openssl/openssl/wiki/OpenSSL_1.1.0_Changes.

Upgrading from the OpenSSL 2.0 FIPS Object Module

The OpenSSL 2.0 FIPS Object Module was a separate download that had to be built separately and then integrated into your main OpenSSL 1.0.2 build. In OpenSSL 3.0 the FIPS support is fully integrated into the mainline version of OpenSSL and is no longer a separate download. For further information see "Completing the installation of the FIPS Module".

The function calls FIPS_mode() and FIPS_mode_set() have been removed from OpenSSL 3.0. You should rewrite your application to not use them. See fips_module(7) and OSSL_PROVIDER-FIPS(7) for details.

Completing the installation of the FIPS Module

The FIPS Module will be built and installed automatically if FIPS support has been configured. The current documentation can be found in the README-FIPS https://github.com/openssl/openssl/blob/master/README-FIPS.md file.

Programming

Applications written to work with OpenSSL 1.1.1 will mostly just work with OpenSSL 3.0. However changes will be required if you want to take advantage of some of the new features that OpenSSL 3.0 makes available. In order to do that you need to understand some new concepts introduced in OpenSSL 3.0. Read "Library contexts" in crypto(7) for further information.

Library Context

A library context allows different components of a complex application to each use a different library context and have different providers loaded with different configuration settings. See "Library contexts" in crypto(7) for further info.

If the user creates an OSSL_LIB_CTX via OSSL_LIB_CTX_new(3) then many functions may need to be changed to pass additional parameters to handle the library context.

Using a Library Context - Old functions that should be changed

If a library context is needed then all EVP_* digest functions that return a const EVP_MD * such as EVP_sha256() should be replaced with a call to EVP_MD_fetch(3). See "ALGORITHM FETCHING" in crypto(7).

If a library context is needed then all EVP_* cipher functions that return a const EVP_CIPHER * such as EVP_aes_128_cbc() should be replaced vith a call to EVP_CIPHER_fetch(3). See "ALGORITHM FETCHING" in crypto(7).

If NULL is passed instead then the created object will be set up with the default library context. Use X509_new_ex(3), X509_CRL_new_ex(3), X509_REQ_new_ex(3) and X509_PUBKEY_new_ex(3) if a library context is required.

    Dépréciation des fonctions de bas niveau

    Un nombre significatif d'API ont été dépréciées dans OpenSSL 3.0. Cette section décrit quelques catégories courantes de dépréciations. Voir « Mappages de fonctions dépréciées » pour la liste des fonctions dépréciées qui font référence à ces catégories.

    Les fournisseurs remplacent les moteurs et les remplacements de méthodes de bas niveau

    Tout accesseur qui utilise un ENGINE est déprécié (comme EVP_PKEY_set1_engine()). Les applications utilisant des moteurs devraient plutôt utiliser des fournisseurs.

    Avant l'ajout des fournisseurs, les algorithmes étaient remplacés en modifiant les méthodes utilisées par les algorithmes. Toutes ces méthodes comme RSA_new_method() et RSA_meth_new() sont maintenant dépréciées et peuvent être remplacées en utilisant des fournisseurs à la place.

    Toutes les fonctions i2d et d2i telles que d2i_DHparams() qui prennent un type de clé de bas niveau ont été dépréciées. Les applications devraient plutôt utiliser les API OSSL_DECODER(3) et OSSL_ENCODER(3) pour lire et écrire des fichiers. Voir « Migration » dans d2i_RSAPrivateKey(3) pour plus de détails.

    Accesseurs et mutateurs de bas niveau dépréciés pour les objets clés

    Les applications qui définissent ou obtiennent des objets clés de bas niveau (comme EVP_PKEY_set1_DH() ou EVP_PKEY_get0()) devraient plutôt utiliser les API OSSL_ENCODER (voir OSSL_ENCODER_to_bio(3)) ou OSSL_DECODER (voir OSSL_DECODER_from_bio(3)), ou alternativement utiliser EVP_PKEY_fromdata(3) ou EVP_PKEY_todata(3).

    Fonctions d'échange de clés de bas niveau dépréciées

    De nombreuses fonctions de bas niveau sont découragées depuis longtemps. Les applications devraient plutôt utiliser EVP_PKEY_derive(3). Voir EVP_KEYEXCH-DH(7), EVP_KEYEXCH-ECDH(7) et EVP_KEYEXCH-X25519(7).

    Fonctions de génération de clés de bas niveau dépréciées

    De nombreuses fonctions de bas niveau sont découragées depuis longtemps. Les applications devraient plutôt utiliser EVP_PKEY_keygen_init(3) et EVP_PKEY_generate(3) comme décrit dans EVP_PKEY-DSA(7), EVP_PKEY-DH(7), EVP_PKEY-RSA(7), EVP_PKEY-EC(7) et EVP_PKEY-X25519(7). La fonction rapide en une seule passe EVP_PKEY_Q_keygen(3) et les macros pour les cas les plus courants : <EVP_RSA_gen(3)> et EVP_EC_gen(3) peuvent également être utilisées.

    Fonctions de lecture et d'écriture de clés de bas niveau dépréciées

    L'utilisation d'objets de bas niveau (tels que DSA) est découragée depuis longtemps. Les fonctions pour lire et écrire ces objets de bas niveau (tels que PEM_read_DSA_PUBKEY()) devraient être remplacées. Les applications devraient plutôt utiliser OSSL_ENCODER_to_bio(3) et OSSL_DECODER_from_bio(3).

    Fonctions d'impression de clés de bas niveau dépréciées

    L'utilisation d'objets de bas niveau (tels que DSA) est découragée depuis longtemps. Les fonctions pour imprimer ces objets de bas niveau tels que DSA_print() devraient être remplacées par les fonctions EVP_PKEY équivalentes. L'application devrait utiliser l'une des fonctions : EVP_PKEY_print_public(3), EVP_PKEY_print_private(3), EVP_PKEY_print_params(3), EVP_PKEY_print_public_fp(3), EVP_PKEY_print_private_fp(3) ou EVP_PKEY_print_params_fp(3). Notez qu'en interne, elles utilisent OSSL_ENCODER_to_bio(3) et OSSL_DECODER_from_bio(3).

    NOM

    openssl - Guide de migration vers OpenSSL 3.0

    SYNOPSIS

    openssl(1)

    DESCRIPTION

    Ce document décrit les changements et les modifications nécessaires lors de la mise à niveau d'OpenSSL 1.1.1 vers OpenSSL 3.0.

    Les applications utilisant les anciennes API devraient être mises à jour pour utiliser les nouvelles API du module de fournisseur. Bien que les anciennes API soient toujours disponibles dans OpenSSL 3.0, elles peuvent être supprimées dans les futures versions. Il est fortement recommandé de passer aux nouvelles API du fournisseur dès que possible.

    Changements des applications

    Les applications qui utilisent des algorithmes à base de chaînes de caractères (comme sha256) doivent être mises à jour pour utiliser les noms d'algorithmes standardisés d'OpenSSL 3.0. Par exemple, l'algorithme sha256 est maintenant représenté par SHA256. Les applications qui ne sont pas mises à jour peuvent rencontrer des erreurs lors de l'utilisation de ces algorithmes.

    La fonction RAND_load_file() ne charge plus automatiquement des données aléatoires à partir du fichier spécifié par la variable d'environnement RANDFILE. Les applications doivent explicitement appeler RAND_load_file() pour charger des données aléatoires.

    Le comportement de RAND_bytes() a également été modifié. Il ne repose plus sur un appel à RAND_load_file(). Si vous avez besoin de données aléatoires initialisées à partir d'un fichier, vous devez appeler RAND_load_file() avant d'appeler RAND_bytes().

    La commande openssl speed n'utilise plus d'appels API de bas niveau. Cela implique que certains chiffres de performance pourraient ne pas être comparables aux versions précédentes en raison d'un overhead plus élevé. Cela s'applique particulièrement à la mesure des performances sur de petits blocs de données.

    Les commandes openssl dhparam, openssl dsa, openssl gendsa, openssl dsaparam, openssl genrsa et openssl rsa ont été modifiées pour utiliser les API PKEY. openssl genrsa et openssl rsa écrivent maintenant des clés PKCS #8 par défaut.

    Paramètres par défaut

    "SHA256" est maintenant le digest par défaut pour la requête TS utilisée par openssl ts.

    Applications obsolètes

    openssl rsautl est obsolète, utilisez openssl pkeyutl à la place. openssl dhparam, openssl dsa, openssl gendsa, openssl dsaparam, openssl genrsa, openssl rsa, openssl genrsa et openssl rsa sont maintenant en mode maintenance et aucune nouvelle fonctionnalité ne leur sera ajoutée.

    Changements TLS

    • Support de l'échange de clés FFDHE TLS 1.3 ajouté

      Ceci utilise des groupes de nombres premiers sûrs DH.

    • Support des groupes TLSv1.3 entièrement "plugables".

      Cela signifie que les fournisseurs peuvent proposer leurs propres implémentations de groupe (en utilisant les méthodes "échange de clés" ou "encapsulation de clés") qui seront automatiquement détectées et utilisées par libssl.

    • Les options SSL et SSL_CTX sont maintenant sur 64 bits au lieu de 32 bits.

      Les signatures des fonctions pour obtenir et définir les options sur les objets SSL et SSL_CTX sont passées du type "unsigned long" au type "uint64_t".

      Cela peut nécessiter des changements dans le code source. Par exemple, il n'est plus possible d'utiliser les valeurs macro SSL_OP_ dans les conditions de préprocesseur "#if". Cependant, il est toujours possible de tester si ces macros sont définies ou non.

      Voir SSL_CTX_get_options(3), SSL_CTX_set_options(3), SSL_get_options(3) et SSL_set_options(3).

    • Modifications de SSL_set1_host() et SSL_add1_host()

      Ces fonctions acceptent maintenant des adresses IP littérales ainsi que des noms d'hôte réels.

    • Ajout de l'option SSL SSL_OP_CLEANSE_PLAINTEXT

      Si l'option est définie, openssl nettoie (efface à zéro) les octets en clair des tampons internes après les avoir livrés à l'application. Notez que l'application est toujours responsable du nettoyage des autres copies (par exemple, les données reçues par SSL_read(3)).

    • La renégociation initiée par le client est désactivée par défaut.

      Pour l'autoriser, utilisez l'option -client_renegotiation, le drapeau SSL_OP_ALLOW_CLIENT_RENEGOTIATION, ou le paramètre de configuration "ClientRenegotiation", selon ce qui convient.

    • La renégociation sécurisée est maintenant requise par défaut pour les connexions TLS

      Le support de la renégociation sécurisée RFC 5746 est maintenant requis par défaut pour que les connexions SSL ou TLS réussissent. Les applications qui nécessitent la capacité de se connecter à des pairs hérités devront explicitement définir SSL_OP_LEGACY_SERVER_CONNECT. En conséquence, SSL_OP_LEGACY_SERVER_CONNECT n'est plus défini dans le cadre de SSL_OP_ALL.

    • La combinaison des options de configuration no-ec et no-dh ne désactive plus TLSv1.3

      Généralement, si OpenSSL n'a pas d'algorithmes EC ou DH, il ne peut pas supporter les connexions TLSv1.3. Cependant, OpenSSL supporte maintenant les groupes "plugables" via les fournisseurs. Par conséquent, les fournisseurs tiers peuvent proposer des implémentations de groupe même là où il n'y en a pas d'intégrées. Tenter de créer des connexions TLS dans une telle construction sans désactiver TLSv1.3 à l'exécution ou sans utiliser de groupes de fournisseurs tiers peut entraîner des échecs de négociation. TLSv1.3 peut être désactivé à la compilation en utilisant l'option de configuration "no-tls1_3".

    • Modifications de SSL_CTX_set_ciphersuites() et SSL_set_ciphersuites().

      Les méthodes ignorent maintenant les chiffrements inconnus.

    • Modification du callback de sécurité.

      Le callback de sécurité, qui peut être personnalisé par le code de l'application, supporte l'opération de sécurité SSL_SECOP_TMP_DH. Ceci est défini pour prendre un EVP_PKEY dans le paramètre "other". Dans la plupart des endroits, c'est ce qui est passé. Tous ces endroits se produisent côté serveur. Cependant, il y a eu un appel côté client de cette opération de sécurité et il a passé un objet DH au lieu de cela. Ceci est incorrect selon la définition de SSL_SECOP_TMP_DH, et est incohérent avec tous les autres emplacements. Par conséquent, cet appel côté client a été modifié pour passer un EVP_PKEY à la place.

    • Nouvelle option SSL SSL_OP_IGNORE_UNEXPECTED_EOF

      L'option SSL SSL_OP_IGNORE_UNEXPECTED_EOF est introduite. Si cette option est définie, un EOF inattendu est ignoré, il fait semblant qu'un close notify a été reçu à la place et donc l'erreur retournée devient SSL_ERROR_ZERO_RETURN.

    • La force de sécurité des signatures basées sur SHA1 et MD5 dans TLS a été réduite.

      Cela a pour conséquence que SSL 3, TLS 1.0, TLS 1.1 et DTLS 1.0 ne fonctionnent plus au niveau de sécurité par défaut de 1 et nécessitent à la place le niveau de sécurité 0. Le niveau de sécurité peut être modifié soit en utilisant la chaîne de chiffrements avec @SECLEVEL, soit en appelant SSL_CTX_set_security_level(3). Cela signifie également que lorsque l'extension des algorithmes de signature est manquante dans un ClientHello, la négociation échouera en TLS 1.2 au niveau de sécurité 1. En effet, bien que cette extension soit optionnelle, ne pas en fournir une signifie qu'OpenSSL se rabattra sur un ensemble par défaut d'algorithmes de signature. Cet ensemble par défaut nécessite la disponibilité de SHA1.

    • Les certificats X509 signés avec SHA1 ne sont plus autorisés aux niveaux de sécurité 1 et supérieurs.

      En TLS/SSL, le niveau de sécurité par défaut est 1. Il peut être défini soit en utilisant la chaîne de chiffrements avec @SECLEVEL, soit en appelant SSL_CTX_set_security_level(3). Si le certificat feuille est signé avec SHA-1, un appel à SSL_CTX_use_certificate(3) échouera si le niveau de sécurité n'est pas d'abord abaissé. En dehors de TLS/SSL, le niveau de sécurité par défaut est -1 (effectivement 0). Il peut être défini à l'aide de X509_VERIFY_PARAM_set_auth_level(3) ou en utilisant les options -auth_level des commandes.
