NOM

offlineimap - Synchroniser les boîtes aux lettres et Maildirs dans les deux sens ou dans un sens.

SYNOPIS

offlineimap (options)

DESCRIPTION

Synchronise les comptes configurés dans le fichier de configuration via IMAP. Chaque compte a deux côtés. L'un des côtés doit être un serveur IMAP. L'autre côté peut être un Maildir ou un autre serveur IMAP.

Fonctionne avec Python 2.

OPTIONS

-h, --help

Affiche un résumé des options.

--version

Affiche la version.

-V

Affiche la version d'offlineimap et des informations supplémentaires sur imaplib2.

--dry-run

Exécute en mode simulation.

Ne modifie aucun stockage mais vérifie et affiche les actions de synchronisation qui seraient effectuées si une synchronisation était réalisée. Il ne donnera pas précisément les informations exactes sur ce qui se passera. Si par exemple, nous devons créer un dossier, il affichera simplement Voudrait créer le dossier X, mais pas combien et quels messages il transférerait.

--info

Affiche des informations sur les dépôts d'e-mails configurés.

Utile pour le débogage et le signalement de bugs. À utiliser en conjonction avec l'option ‘-a’ pour limiter la sortie à un seul compte. Ce mode empêchera toute synchronisation réelle et se terminera après avoir affiché les informations de débogage.

-1

Limite les opérations multithread et exécute une synchronisation à un seul thread.

Ceci définit effectivement les variables de fichier de configuration maxsyncaccounts et toutes les maxconnections à 1 (le nombre).

-P <répertoire>

Met OfflineIMAP en mode profilage.

Le programme créera le répertoire DIR (il ne doit pas exister au préalable). Au fur et à mesure de son exécution, des informations de profilage Python sur chaque thread sont enregistrées dans le répertoire de profilage. Veuillez noter : cette option est présente pour le débogage et l'optimisation uniquement, et ne doit pas être utilisée sauf si vous avez une raison spécifique de le faire. Elle diminuera considérablement les performances du programme, pourrait réduire la fiabilité et peut générer d'énormes quantités de données. Cette option implique l'option ‘-1’.

-a <compte1[,compte2[,...]]>

Remplace la section des comptes dans le fichier de configuration.

Permet de spécifier un compte particulier ou un ensemble de comptes à synchroniser sans avoir à modifier le fichier de configuration.

-c <chemin/vers/fichier_configuration>

Spécifie un fichier de configuration à utiliser.

-d <type1[,type2[,...]]>

Active le débogage pour OfflineIMAP.

Ceci est utile si vous souhaitez résoudre un dysfonctionnement ou comprendre ce qui se passe en coulisses. Cette option nécessite un ou plusieurs types de débogage, séparés par des virgules. Ceux-ci définissent ce qui sera débogué exactement, et incluent jusqu'à présent les options : "imap", "thread", "maildir" ou "ALL". L'option imap activera le débogage du flux et de l'analyse du protocole IMAP. Notez que la sortie peut contenir des mots de passe, veillez donc à les supprimer de la sortie de débogage avant de l'envoyer à quiconque. L'option maildir activera le débogage pour certaines opérations Maildir. L'utilisation de toute option de débogage (sauf si "thread" est inclus), implique l'option monothread ‘-1’.

-l <chemin/vers/fichier.log>

Envoie les journaux vers <fichier.log>.

-s

Envoie les journaux vers syslog.

-f <dossier1[,dossier1[,...]]>

Synchronise uniquement les dossiers spécifiés.

Les noms de dossiers sont les noms de dossiers non traduits du dépôt distant. Cette option en ligne de commande remplace toute option folderfilter et folderincludes dans le fichier de configuration.

-k <[section:]option=valeur

Remplace toute option du fichier de configuration.

Si "section" est omis, il prend par défaut "general". Tous les traits de soulignement dans le nom de section sont remplacés par des espaces : par exemple, pour remplacer l'option "autorefresh" dans la section "[Account Personal]" du fichier de configuration, vous utiliseriez ‘-k Account_Personal:autorefresh=30’. Répétez cette option autant de fois que nécessaire pour redéfinir plusieurs options.

-o

Exécute une seule fois.

Ignore tout réglage d'actualisation automatique dans le fichier de configuration.

-q

Exécute uniquement des synchronisations rapides.

Ignore toutes les mises à jour de drapeaux sur les serveurs IMAP. Si un drapeau sur le serveur IMAP distant change, et que nous avons le message localement, il sera laissé intact lors d'une exécution rapide. Cette option est ignorée si maxage est défini.

-u <UI>

Spécifie une interface utilisateur alternative à utiliser.

Ceci remplace la valeur par défaut spécifiée dans le fichier de configuration. L'interface utilisateur spécifiée avec ‘-u’ sera forcée d'être utilisée, même si des vérifications déterminent qu'elle n'est pas utilisable. Les choix d'interface possibles sont : quiet, basic, syslog, ttyui, blinkenlights, machineui.

--delete-folder

Supprime un dossier du dépôt distant.

Un seul compte doit être spécifié/configuré pour que cette fonctionnalité fonctionne ou vous devez fournir un compte avec -a. Le nom du dossier doit être fourni avec les séparateurs distants (probablement /) en UTF-8 si utf8foldernames est activé ou en IMAP sinon. Par exemple : "Remote/folder/name".

--migrate-fmd5-using-nametrans

Migre les hachages FMD5 des versions antérieures à 6.3.5.

La manière dont les hachages FMD5 sont calculés a été modifiée dans la version 6.3.5 (utilisant désormais le nom de dossier nametrans) introduisant une régression qui peut entraîner le re-téléchargement de tous les messages. Tente de corriger la régression ci-dessus en calculant les valeurs FMD5 correctes et en renommant les messages correspondants.


Attention

Étant donné que la partie FMD5 du nom de fichier change, cela peut entraîner des conflits d'UID. Assurez-vous de disposer d'une sauvegarde appropriée du cache et du Maildir avant d'exécuter cette correction, ainsi que de vérifier les résultats en utilisant d'abord l'indicateur ‘--dry-run’.

--mbnames-prune

Supprime les entrées orphelines pour les comptes supprimés ou si mbnames n'est pas activé/utilisé.

En interne, offlineimap crée des fichiers mbnames intermédiaires. Ils sont ajoutés automatiquement lorsque mbnames est activé. Cependant, désactiver des comptes pour qu'ils ne soient plus synchronisés ne signifie pas nécessairement qu'ils doivent être supprimés du fichier créé par mbnames. Il est nécessaire de démarrer offlineimap avec cette option CLI chaque fois que des comptes sont supprimés. Lors de l'exécution, tous les comptes qui ne sont pas dans l'option de configuration accounts sont supprimés du fichier mbnames.

Il est possible de supprimer manuellement les fichiers intermédiaires dans <metadata>/mbnames/.

Notez que cette option respecte --dry-run.

PERFORMANCE DE SYNCHRONISATION

Par défaut, nous utilisons des paramètres assez conservateurs qui sont sûrs pour la synchronisation mais qui ne sont peut-être pas les plus performants. Une fois que vous avez tout configuré et que tout fonctionne, vous pourriez vouloir vous pencher sur l'accélération de votre synchronisation. Voici quelques indices et astuces sur la façon d'y parvenir.

1.Synchroniser plus d'un compte.

Par défaut, nous n'utilisons qu'une seule connexion à un serveur IMAP. Utiliser 2 ou même 3 accélère considérablement les choses dans la plupart des cas. Afin de synchroniser plus d'un compte simultanément, envisagez de lancer une instance d'offlineimap par compte.


Avertissement
activer les options maxsyncaccounts et maxconnections est déprécié car il est connu qu'il y a des conditions de concurrence (race conditions).
2.Utiliser les filtres de dossiers.

La synchronisation la plus rapide est une synchronisation qui peut ignorer certains dossiers. Je trie ma boîte de réception en dossiers mensuels et ignore tous les dossiers qui ont plus de 2-3 mois, cela me permet de n'inspecter qu'une fraction de mes e-mails à chaque synchronisation. Si vous ne l'avez pas encore fait, faites-le :). Voir la section folderfilter dans offlineimap.conf.

3.Le cache sqlite.

OfflineImap met en cache l'état de la synchronisation pour, par exemple, pouvoir déterminer si un message a été ajouté ou supprimé d'un côté ou de l'autre.

Le cache d'état historique était un fichier texte brut qui écrivait le fichier complet pour chaque nouveau message (ou même drapeau modifié) dans un fichier temporaire. S'il y avait beaucoup de fil

dans un dossier auquel cela était lié ralentir les choses. Le cache d'état le plus récent est sqlite. Cela évite de nombreuses opérations sur le disque.

Le cache d'état brut historique n'est plus pris en charge, mais la migration depuis une très ancienne installation utilisant le cache texte brut est toujours prise en charge. Dans ce cas, vous voudrez peut-être supprimer manuellement l'ancien répertoire de cache dans <metadata>/Account-<account>/LocalStatus (le cache sqlite se trouve dans le dossier LocalStatus-sqlite). Tout d'abord, assurez-vous d'avoir exécuté la nouvelle version d'offlineimap pour tous vos comptes afin que le cache d'état ait été migré.

4. Utiliser la synchronisation rapide.

Une synchronisation normale demandera tous les drapeaux et tous les UID de tous les messages dans chaque dossier, ce qui prend beaucoup de temps. Une synchronisation rapide ne compare que le nombre de messages dans un dossier côté IMAP (elle détectera les modifications de drapeaux côté Maildir). Une synchronisation rapide sur mon compte, de taille moyenne, prendra 7 secondes au lieu de 40 secondes. Par exemple, exécutez un script cron qui effectue une synchronisation normale une fois par jour, et effectue des synchronisations rapides '-q' uniquement pour '-f INBOX' entre-temps.

5. Désactiver fsync.

Dans la section [general], vous pouvez régler fsync sur True ou False. Si vous voulez jouer à 110% en sécurité et attendre que toutes les opérations touchent le disque avant de continuer, vous pouvez régler ceci sur True. Si vous le réglez sur False, vous perdez une partie de cette sécurité, en échange de vitesse.

SECURITÉ ET SSL

Par défaut, OfflineIMAP se connectera en utilisant toute méthode que openssl prend en charge, c'est-à-dire SSLv2, SSLv3 ou TLSv1.

Notez que SSLv2 est notoirement peu sûr et déprécié. Malheureusement, python2 n'offre pas de moyens faciles de désactiver SSLv2. Il est recommandé de tester votre configuration et de vous assurer que le serveur de messagerie n'utilise pas de connexion SSLv2. Utilisez par exemple "openssl s_client -host mail.server -port 443" pour connaître la connexion utilisée par défaut.

• Vérification du certificat

Malheureusement, par défaut, nous ne vérifierons pas le certificat d'un serveur IMAP TLS/SSL auquel nous nous connectons, donc la connexion SSL n'est pas une garantie contre les attaques de type homme du milieu. Bien que la vérification de l'empreinte du certificat du serveur soit recommandée. Il n'existe actuellement qu'un seul moyen sûr de s'assurer que vous vous connectez au bon serveur de manière cryptée : vous pouvez spécifier un paramètre sslcacertfile dans la section de votre dépôt de offlineimap.conf pointant vers un fichier qui contient (entre autres) un certificat d'autorité de certification au format PEM qui valide votre certificat serveur. Dans ce cas, nous vérifierons que :

1. Le certificat SSL du serveur est validé par le certificat CA.
2. Le nom d'hôte du serveur correspond au certificat SSL.
3. Le certificat du serveur n'est pas expiré.

La FAQ contient une entrée sur la création de votre propre certificat et certificat CA.

• StartTLS

Si vous n'avez pas configuré votre compte pour vous connecter via SSL de toute façon, OfflineImap tentera toujours d'établir une connexion SSL via la fonction STARTTLS, si le serveur imap la supporte.

Aucune vérification de certificat ou d'empreinte n'est impliquée lors de l'utilisation de STARTTLS (la bibliothèque imaplib sous-jacente ne le prend pas encore en charge). Cela signifie que vous serez protégé contre les écoutes clandestines passives et qu'elles ne pourront pas voir votre mot de passe ou le contenu de vos e-mails. Cependant, cela ne vous protégera pas contre les attaques actives, telles que les attaques de type homme du milieu qui vous font vous connecter au mauvais serveur et prétendre être votre serveur de messagerie.

NE VOUS FIER PAS À STARTTLS COMME UNE GARANTIE DE CONNEXION SÛRE ASSURANT L'AUTHENTICITÉ DE VOTRE SERVEUR IMAP !

SIGNaux UNIX

OfflineImap écoute les signaux Unix SIGUSR1, SIGUSR2, SIGTERM, SIGINT, SIGHUP, SIGQUIT.

• S'il reçoit un SIGUSR1, il interrompra tout délai d'attente en cours (ou futur) de tous les comptes configurés pour autorefresh. En effet, cela déclenchera une synchronisation complète de tous les comptes dès que possible.
• S'il reçoit un SIGUSR2 ou SIGABRT, il désactivera le mode autorefresh pour tous les comptes. C'est-à-dire que les comptes interrompront tout délai d'attente en cours et sortiront après la fin d'une synchronisation en cours. Ce signal peut être utilisé pour quitter gracieusement un processus "démon" offlineimap en cours d'exécution.
• SIGTERM, SIGINT, SIGHUP sont tous traités pour une terminaison gracieuse dès que possible. Cela signifie qu'il terminera la synchronisation du dossier courant dans chaque compte, fermera les connexions maintenues actives, supprimera les verrous sur les comptes et quittera.

Cela peut prendre jusqu'à 10 secondes, si l'option autorefresh est utilisée.

Plusieurs SIGTERM se comporteront comme SIGQUIT.

• S'il reçoit SIGQUIT, il déversera les traces de pile de tous les threads et tentera de déverser le cœur du processus.

PROBLÈMES CONNUS

• Suppressions.

Pendant une exécution normale, les suppressions sont propagées. Pour éviter la perte de données, la suppression d'un dossier fait resynchroniser le dossier par offlineimap. Cependant, la propagation de la suppression de tout le contenu d'un dossier peut se produire dans les deux cas suivants :

• Tout le contenu d'un dossier est supprimé mais le répertoire du dossier existe toujours.
• Le répertoire parent du dossier a été supprimé.
• SSL3 write pending.

Les utilisateurs activant SSL peuvent rencontrer un bug concernant "SSL3 write pending". Si c'est le cas, le(s) compte(s) resteront non synchronisé(s) à partir du moment où le bug est apparu. Relancer OfflineIMAP peut aider. Nous travaillons toujours sur ce bug. Des correctifs ou des rapports de bugs détaillés seraient appréciés. Veuillez vérifier que vous exécutez la dernière version stable et envoyez-nous un rapport à la liste de diffusion incluant le journal complet.

• La prise en charge de l'IDLE est incomplète et expérimentale. Des bugs peuvent être rencontrés.
• Il n'existe pas de crochet pour "exécuter après une réponse IDLE".

Les e-mails apparaîtront, mais peuvent ne pas être traités avant le prochain cycle de rafraîchissement.

• nametrans peut ne pas être correctement pris en charge.
• IMAP IDLE <→ IMAP IDLE ne fonctionne pas encore.
• IDLE peut cesser de synchroniser lors d'une suspension/reprise du système.
• IDLE peut ne fonctionner que "une fois" par rafraîchissement.

Si vous rencontrez ce bug, veuillez envoyer un rapport à la liste !

• Prise en charge de Maildir sur les lecteurs Windows.

Maildir utilise le caractère deux-points (:) dans les noms de fichiers de messages. Le deux-points est cependant un caractère interdit sur les lecteurs Windows. Il existe plusieurs solutions de contournement pour cette situation :

1. Activer la traduction des noms de fichiers dans le registre Windows (non testé).
•http://support.microsoft.com/kb/289627
2. Utiliser un montage géré par cygwin (non testé).
• non disponible depuis cygwin 1.7
3. Utiliser "maildir-windows-compatible = yes" dans la configuration du compte OfflineIMAP.
• Cela fait qu'OfflineIMAP utilise le point d'exclamation (!) au lieu du deux-points pour stocker les messages. De tels fichiers peuvent être écrits sur des partitions Windows. Mais vous perdrez probablement la compatibilité avec d'autres programmes essayant de lire le même Maildir.
• Le point d'exclamation a été choisi en raison de la note dans http://docs.python.org/library/mailbox.html
• Si vous avez déjà des messages stockés sans cette option, vous devrez les resynchroniser à nouveau
• OfflineIMAP confus après une mise en veille du système.

Lors de la reprise d'une session suspendue, OfflineIMAP ne gère pas proprement les sockets brisés si l'option socktimeout n'est pas définie. Vous devriez activer cette option avec une valeur comme 10.

• OfflineIMAP confus lorsque les mails changent pendant une synchronisation.

Lorsque OfflineIMAP est en cours de synchronisation, certains événements survenus depuis l'invocation côté distant ou local sont mal gérés. OfflineIMAP ne suivra pas les changements pendant la synchronisation.

• Partage d'un maildir avec plusieurs serveurs IMAP.

En général, une mise en garde s'impose lors du mélange de dépôts IMAP sur la même racine Maildir. Vous devez faire attention à ne jamais utiliser le même dossier maildir pour 2 serveurs IMAP. Dans le meilleur des cas, le MD5 du dossier sera différent, et vous obtiendrez une boucle où il téléchargera vos mails sur les deux serveurs en alternance (à l'infini !) car il pensera que vous avez placé de nouveaux mails dans le Maildir local. Dans le pire des cas, le MD5 est le même (probable) et les UID des mails se chevauchent (probable aussi !) et il échouera à synchroniser certains mails car il pense qu'ils existent déjà.

Je créerais un nouveau dépôt Maildir local pour le Gmail personnel et utiliserais une racine différente pour être sûr ici. Vous pourriez par exemple utiliser

`~/mail/Pro' comme racine Maildir pour ProGmail et
`~/mail/Personal' comme racine pour celui personnel.

Si vous pointez ensuite votre mutt local, ou tout autre MUA que vous utilisez, vers `~/mail/` comme racine, il devrait toujours reconnaître tous les dossiers.

• Cas limites avec maxage causant la synchronisation de trop de messages.

Tous les messages datant d'au plus maxage jours auparavant (+/- quelques heures, selon les fuseaux horaires) sont synchronisés, mais il existe des cas où des messages plus anciens peuvent également être synchronisés. Cela se produit lorsqu'un UID de message est significativement plus élevé que ceux d'autres messages avec des dates similaires, par exemple, lorsque des messages sont ajoutés au dossier local en arrière de offlineimap, leur attribuant un nouvel UID, ou lorsque offlineimap synchronise pour la première fois un Maildir préexistant. Dans ce dernier cas, il peut sembler qu'un sous-ensemble notable et aléatoire de vieux messages soit synchronisé.

• Offlineimap se bloque.

En cas de blocages inattendus, il est conseillé de régler `singlethreadperfolder` sur yes, surtout en mode IMAP/IMAP (pas de maildir).

• Mots de passe dans netrc.

Offlineimap ne sait pas comment récupérer les mots de passe lorsque plus d'un compte est stocké dans le fichier netrc. Voir https://github.com/OfflineIMAP/offlineimap/issues/295.

• XOAUTH2

XOAUTH2 peut être un peu délicat à configurer. Assurez-vous d'avoir suivi le guide étape par étape dans offlineimap.conf. Les bugs connus concernant Gmail

sont suivis à https://github.com/OfflineIMAP/offlineimap/labels/Gmail.

Parfois, vous pourriez rencontrer l'une des erreurs suivantes:

•[imap]: xoauth2handler: response "{u’error': u’invalid_grant'}"
•oauth2handler got: {u’error': u’invalid_grant'}

Dans ce cas, nous avons eu des rapports indiquant que la génération d'un nouveau jeton d'actualisation à partir du même ID client et du même secret peut aider.

Documentation Google sur "invalid_grant".

Lorsque vous essayez d'utiliser un jeton d'actualisation, ce qui suit vous renvoie une erreur invalid_grant :
  - L'horloge de votre serveur n'est pas synchronisée avec le protocole de temps réseau - NTP.
  - La limite de jetons d'actualisation a été dépassée.

Expiration du jeton.

Il est possible qu'un jeton accordé ne fonctionne plus. Un jeton peut cesser de fonctionner pour l'une des raisons suivantes :
  - L'utilisateur a révoqué l'accès.
  - Le jeton n'a pas été utilisé pendant six mois.
  - L'utilisateur a changé de mot de passe et le jeton contient des champs d'application Gmail.
  - Le compte utilisateur a dépassé un certain nombre de demandes de jetons.
Il y a actuellement une limite de 50 jetons d'actualisation par compte utilisateur par client. Si la limite est atteinte, la création d'un nouveau jeton invalide automatiquement le jeton le plus ancien sans avertissement. Cette limite ne s'applique pas aux comptes de service.

Voir https://developers.google.com/analytics/devguides/config/mgmt/v3/authorization et https://developers.google.com/identity/protocols/OAuth2#expiration pour en savoir plus.

•"ne possède pas de message avec UID" avec les serveurs Microsoft 
`ERREUR : Le serveur IMAP 'Server ### Remote' ne possède pas de message avec l'UID 'xxx'`

Les serveurs IMAP de Microsoft ne sont pas conformes aux RFC. Il est actuellement nécessaire de filtrer certains dossiers défectueux. Voir http://www.offlineimap.org/doc/FAQ.html#exchange-and-office365 pour une liste détaillée.
