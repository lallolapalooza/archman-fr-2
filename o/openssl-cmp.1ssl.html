NOM

openssl-cmp - Application du protocole de gestion de certificats (CMP, RFC 4210)

SYNOPSIS

openssl cmp [-help] [-config fichier] [-section noms] [-verbosity niveau]

Options génériques de message :

[-cmd ir|cr|kur|p10cr|rr|genm] [-infotype nom] [-profile nom] [-geninfo valeurs] [-template fichier] [-keyspec fichier]

[-newkey fichier|uri] [-newkeypass arg] [-centralkeygen [-newkeyout fichier] [-subject nom] [-days nombre] [-reqexts nom] [-sans spec] [-san_nodefault] [-policies nom] [-policy_oids noms] [-policy_oids_critical] [-popo nombre] [-csr fichier] [-out_trusted fichiers|uris] [-implicit_confirm] [-disable_confirm] [-certout fichier] [-chainout fichier]

[-oldcert fichier|uri] [-issuer nom] [-serial nombre] [-revreason nombre]

[-server [http[s]://][userinfo@]hôte[:port][/chemin][?query][#fragment]] [-proxy [http[s]://][userinfo@]hôte[:port][/chemin][?query][#fragment]] [-no_proxy adresses] [-recipient nom] [-path chemin_distant] [-keep_alive valeur] [-msg_timeout secondes] [-total_timeout secondes]

Options d'authentification du serveur :

DESCRIPTION

La commande cmp est une implémentation client du protocole de gestion de certificats (CMP) tel que défini dans la RFC4210. Elle peut être utilisée pour demander des certificats à un serveur d'AC, mettre à jour leurs certificats, demander la révocation de certificats, et effectuer d'autres types de requêtes CMP.

OPTIONS

-help
Affiche un résumé de toutes les options.
-config fichier
Fichier de configuration à utiliser. Une chaîne vide "" signifie aucun. Le nom de fichier par défaut provient de la variable d'environnement "OPENSSL_CONF".
-section noms
Section(s) à utiliser dans le fichier de configuration définissant les options CMP. Une chaîne vide "" signifie aucune section spécifique. Par défaut, c'est "cmp".

Plusieurs noms de section peuvent être donnés, séparés par des virgules et/ou des espaces blancs (auquel cas l'argument entier doit être entre guillemets "..."). Le contenu des sections nommées plus tard peut remplacer le contenu des sections nommées précédemment. Dans tous les cas, comme d'habitude, la section "[default]" et finalement la section sans nom (si présente) peuvent fournir des valeurs de secours par option.

-verbosity niveau
Niveau de verbosité pour la journalisation, la sortie d'erreur, etc. 0 = EMERG, 1 = ALERT, 2 = CRIT, 3 = ERR, 4 = WARN, 5 = NOTE, 6 = INFO, 7 = DEBUG, 8 = TRACE. Par défaut, 6 = INFO.

Options génériques de message

-cmd ir|cr|kur|p10cr|rr|genm
Commande CMP à exécuter. Les commandes actuellement implémentées sont :
ir   - Demande d'initialisation
cr   - Demande de certificat
p10cr - Demande de certification PKCS#10 (pour la compatibilité héritée)
kur   - Demande de mise à jour de clé
rr   - Demande de révocation
genm - Message Générale

ir demande l'initialisation d'une entité finale dans une hiérarchie PKI en délivrant un premier certificat.

cr demande la délivrance d'un certificat supplémentaire pour une entité finale déjà initialisée dans la hiérarchie PKI.

p10cr demande la délivrance d'un certificat supplémentaire de manière similaire à cr mais en utilisant le format CSR PKCS#10 hérité.

kur demande une mise à jour (de clé) pour un certificat existant.

rr demande la révocation d'un certificat existant.

genm demande des informations à l'aide d'un Message Général, où des InfoTypeAndValue optionnellement inclus peuvent être utilisés pour spécifier les informations d'intérêt. Lors de la réception de la Réponse Générale, les informations sur tous les infoType ITAV reçus sont affichées sur stdout.

-infotype nom
Définit le nom du type d'information à utiliser pour demander des informations spécifiques dans genm, par exemple "signKeyPairTypes". Il existe un support spécifique pour "caCerts", "rootCaCert", "certReqTemplate", et "crlStatusList" (récupération de mise à jour CRL).
-profile nom
Nom d'un profil de certificat à placer dans le champ generalInfo du PKIHeader des messages de requête.
-geninfo valeurs
Une liste d'InfoTypeAndValue séparée par des virgules à placer dans le champ generalInfo du PKIHeader des messages de requête. Chaque InfoTypeAndValue donne un OID et une valeur entière ou chaîne de la forme OID:int:nombre ou OID:str:texte, par exemple '1.2.3.4:int:56789, id-kp:str:name'.
-template nom_fichier
Fichier où enregistrer tout certTemplate CRMF au format DER reçu dans un message genp avec id-it-certReqTemplate.
-keyspec nom_fichier
Il est optionnel et utilisé pour spécifier le fichier où enregistrer tout keySpec s'il est présent dans un message genp avec id-it-keyGenParameters.

Note : le contenu de tout champ keySpec reçu est enregistré comme INFO.

Options de prise en compte de certificats

-newkey nom_fichier|uri
Source de la clé privée ou publique pour le certificat demandé. Par défaut, la clé publique dans le CSR PKCS#10 donné avec l'option -csr, la clé publique du certificat de référence, ou la clé client actuelle.

La partie publique de la clé est placée dans la requête de certificat.

Sauf si -cmd p10cr, -popo -1, ou -popo 0 est spécifié, la clé privée sera également nécessaire pour fournir la preuve de possession (POPO), où l'option -key peut fournir une solution de repli.

-newkeypass arg
Source de la phrase de passe pour la clé donnée avec l'option -newkey. Si non spécifié ici, le mot de passe sera demandé si nécessaire.

Pour plus d'informations sur le format de arg, voir openssl-passphrase-options(1).

-centralkeygen
Demande la génération centrale de clés pour la prise en compte de certificats. Ceci s'applique à -cmd ir|cr|kur|p10cr.
-newkeyout nom_fichier
Fichier où enregistrer la clé privée générée centralement, au format PEM.
-subject nom
Nom Distinctif (DN) X.509 à utiliser comme champ sujet dans le modèle de certificat demandé dans les messages IR/CR/KUR. Si le NULL-DN ("/") est donné, aucun sujet n'est placé dans le modèle. Par défaut, c'est le DN sujet de tout CSR PKCS#10 donné avec l'option -csr. Pour KUR, un recours supplémentaire est le DN sujet du certificat de référence (voir -oldcert) s'il est fourni. Ce recours est utilisé pour IR et CR uniquement si aucun SAN n'est défini.

S'il est fourni et qu'aucun de -cert, -oldcert, ou -csr n'est donné, le DN sujet est utilisé comme expéditeur de secours des messages CMP sortants.

L'argument doit être formaté comme /type0=valeur0/type1=valeur1/type2=.... Les caractères spéciaux peuvent être échappés par "\" (antislash) ; les espaces sont conservés. Les valeurs vides sont permises, mais le type correspondant ne sera pas inclus. Donner un simple "/" entraînera une séquence vide de RDNs (un NULL-DN). Les RDNs multi-valeurs peuvent être formés en plaçant un caractère "+" à la place d'un "/" entre les assertions de valeur d'attribut (AVA) qui spécifient les membres de l'ensemble. Exemple :

"/DC=org/DC=OpenSSL/DC=users/UID=123456+CN=John Doe"

-days nombre
Nombre de jours pour lesquels le nouveau certificat est demandé, en comptant à partir de l'heure actuelle de l'hôte. Déclenche également la demande explicite que la période de validité commence à partir de l'heure actuelle (telle que vue par l'hôte).
-reqexts nom
Nom de la section dans le fichier de configuration OpenSSL définissant les extensions de requête de certificat. Si l'option -csr est présente, ces extensions complètent les extensions contenues dans le CSR PKCS#10 donné, en remplaçant toute extension ayant le même OID.
-sans spécification
Une ou plusieurs adresses IP, adresses e-mail, noms DNS, ou URI séparés par des virgules ou des espaces (dans ce dernier cas, l'argument entier doit être entre guillemets "...") à ajouter comme extension de nom alternatif du sujet (SAN) dans la requête de certificat. Si l'élément spécial "critical" est donné, les SANs sont marqués comme critiques. Ne peut pas être utilisé si une extension de nom alternatif du sujet est définie via -reqexts.
-san_nodefault
Lorsque les noms alternatifs du sujet ne sont pas fournis via -sans ni définis via -reqexts, ils sont copiés par défaut du certificat de référence (voir -oldcert). Ceci peut être désactivé en donnant l'option -san_nodefault.
-policies nom
Nom de la section dans le fichier de configuration OpenSSL définissant les politiques à définir comme extension de requête de certificat. Cette option ne peut pas être utilisée conjointement avec -policy_oids.
-policy_oids noms
Un ou plusieurs OID(s), séparés par des virgules et/ou des espaces (dans ce dernier cas, l'argument entier doit être entre guillemets "...") à ajouter comme extension de requête de politiques de certificat. Cette option ne peut pas être utilisée conjointement avec -policies.
-policy_oids_critical
Marque les politiques données avec -policy_oids comme critiques.
-popo nombre
Méthode de preuve de possession (POPO) à utiliser pour IR/CR/KUR ; valeurs : -1..<2> où -1 = NONE, ce qui implique une génération centrale de clé, 0 = RAVERIFIED, 1 = SIGNATURE (par défaut), 2 = KEYENC.

Notez qu'un POPO basé sur la signature ne peut être produit que si une clé privée est fournie via les options -newkey ou -key.

-csr nom_fichier
CSR PKCS#10 au format PEM ou DER contenant une requête de certificat. Avec -cmd p10cr, il est utilisé directement dans un message P10CR hérité.

Lorsqu'il est utilisé avec -cmd ir, cr, ou kur, il est transformé en la requête CMP régulière respective. Dans ce cas, une clé privée doit être fournie (avec -newkey ou -key) pour la preuve de possession (sauf si -popo -1 ou -popo 0 est utilisé) et la clé publique respective est placée dans la requête de certificat (plutôt que de reprendre la clé publique contenue dans le CSR PKCS#10).

L'entrée CSR PKCS#10 peut également être utilisée avec -cmd rr pour spécifier le certificat à révoquer via le nom sujet et la clé publique inclus. Son sujet est utilisé comme expéditeur de secours dans les en-têtes de message CMP si -cert et -oldcert ne sont pas donnés.

-out_trusted noms_fichiers|uris
Certificat(s) de confiance à utiliser pour valider le certificat nouvellement délivré. Pendant cette vérification, toute vérification de statut de certificat est désactivée.

Plusieurs sources peuvent être fournies, séparées par des virgules et/ou des espaces (dans ce dernier cas, l'argument entier doit être entre guillemets "..."). Chaque source peut contenir plusieurs certificats.

Les options de vérification de certificat -verify_hostname, -verify_ip, et -verify_email n'affectent que la vérification de certificat activée via cette option.

-implicit_confirm
Demande la confirmation implicite des certificats nouvellement délivrés.
-disable_confirm
N'envoie pas de message de confirmation de certificat pour le certificat nouvellement délivré sans demander de confirmation implicite afin de gérer les serveurs défectueux ne prenant pas correctement en charge la confirmation implicite. AVERTISSEMENT : Ceci conduit à un comportement qui viole la RFC 4210.
-certout nom_fichier
Fichier où tout certificat nouvellement délivré doit être enregistré.
-chainout nom_fichier
Fichier où la chaîne de tout certificat nouvellement délivré doit être enregistrée. Cette chaîne exclut le certificat feuille, c'est-à-dire t
Le nouveau certificat enregistré certificat. De plus, l'ancre de confiance (le certificat racine) n'est pas incluse.

Si l'option -certout est également donnée, avec le même argument filename, alors le fichier produit contient les deux sorties concaténées : le nouveau certificat enregistré suivi de sa chaîne.

Options d'enregistrement et de révocation de certificat

-oldcert filename|uri
Le certificat à mettre à jour (c'est-à-dire à renouveler ou à ré-émettre) dans les messages de demande de mise à jour de clé (KUR) ou à révoquer dans les messages de demande de révocation (RR). Pour KUR, le certificat à mettre à jour est par défaut -cert, et le certificat résultant est appelé certificat de référence. Pour RR, le certificat à révoquer peut également être spécifié en utilisant -csr. -oldcert et -csr sont ignorés si -issuer et -serial sont fournis.

Le certificat de référence, le cas échéant, est également utilisé pour dériver le nom distinctif du sujet par défaut et les noms alternatifs du sujet ainsi que l'entrée de l'émetteur par défaut dans le modèle de certificat demandé d'un IR/CR/KUR. Sa clé publique est utilisée comme solution de repli dans le modèle des demandes de certification. Son sujet est utilisé comme expéditeur des messages sortants si -cert n'est pas donné. Son émetteur est utilisé comme destinataire par défaut dans les en-têtes de message CMP si -recipient, -srvcert ou -issuer n'est pas donné.

-issuer name
Nom distinctif (DN) X.509 à placer comme champ émetteur dans le modèle de certificat demandé dans les messages IR/CR/KUR/RR. Si le DN NULL ("/") est donné, aucun émetteur n'est placé dans le modèle.

Si fourni et si -recipient ou -srvcert n'est pas donné, le DN de l'émetteur est utilisé comme destinataire de repli des messages CMP sortants.

L'argument doit être formaté comme /type0=value0/type1=value1/type2=.... Pour plus de détails, voir la description de l'option -subject.

-serial number
Spécifie le numéro de série du certificat à révoquer dans la demande de révocation. Le numéro de série peut être décimal ou hexadécimal (s'il est précédé de "0x").
-revreason number
Définit la raison de révocation (CRLReason) à inclure dans la demande de révocation (RR) ; valeurs : 0..10 ou -1 pour aucune (ce qui est la valeur par défaut).

Les numéros de raison définis dans la RFC 5280 sont :

CRLReason ::= ENUMERATED {
     unspecified             (0),
     keyCompromise           (1),
     cACompromise            (2),
     affiliationChanged      (3),
     superseded              (4),
     cessationOfOperation    (5),
     certificateHold         (6),
     -- la valeur 7 n'est pas utilisée
     removeFromCRL           (8),
     privilegeWithdrawn      (9),
     aACompromise           (10)
 }

Options de transfert de message

-server [http[s]://][userinfo@]host[:port][/path][?query][#fragment]
Le nom de domaine ou l'adresse IP de l'hôte et éventuellement le port du serveur CMP auquel se connecter en utilisant HTTP(S). L'adresse IP peut être pour v4 ou v6, comme 127.0.0.1 ou "[::1]" pour localhost. Si la chaîne hôte est une adresse IPv6, elle doit être entourée de "[" et "]".

Cette option exclut -port et -use_mock_srv. Elle est ignorée si -rspin est donné avec suffisamment d'arguments de nom de fichier.

Si le schéma "https" est donné, l'option -tls_used est implicite. Lorsque TLS est utilisé, le port par défaut est 443, sinon 80. Les composantes facultatives userinfo et fragment sont ignorées. Toute composante de requête donnée est traitée comme faisant partie de la composante de chemin. Si un chemin est inclus, il fournit la valeur par défaut pour l'option -path.

-proxy [http[s]://][userinfo@]host[:port][/path][?query][#fragment]
Le serveur proxy HTTP(S) à utiliser pour atteindre le serveur CMP, sauf si -no_proxy s'applique, voir ci-dessous. Si la chaîne hôte est une adresse IPv6, elle doit être entourée de "[" et "]". Le port du proxy est par défaut 80 ou 443 si le schéma est "https" ; à part cela, le préfixe facultatif "http://" ou "https://" est ignoré (notez que l'utilisation de TLS peut être requise par -tls_used ou -server avec le préfixe "https"), ainsi que tout chemin, userinfo, requête et composantes de fragment. Par défaut, la variable d'environnement "http_proxy" si définie, sinon "HTTP_PROXY" au cas où aucun TLS n'est utilisé, sinon "https_proxy" si définie, sinon "HTTPS_PROXY". Cette option est ignorée si -server n'est pas donné.
-no_proxy addresses
Liste d'adresses IP et/ou de noms DNS de serveurs pour lesquels aucun proxy HTTP(S) ne doit être utilisé, séparés par des virgules et/ou des espaces blancs (auquel cas l'argument entier doit être entouré de "..."). Par défaut, provient de la variable d'environnement "no_proxy" si elle est définie, sinon "NO_PROXY". Cette option est ignorée si -server n'est pas donné.
-recipient name
Nom distinctif (DN) à utiliser dans le champ destinataire des en-têtes de message de requête CMP, c'est-à-dire le serveur CMP (généralement l'AC adressé).

Le champ destinataire dans l'en-tête d'un message CMP est obligatoire. S'il n'est pas explicitement donné, le destinataire est déterminé dans l'ordre suivant : le sujet du certificat du serveur CMP donné avec l'option -srvcert, l'option -issuer, l'émetteur du certificat donné avec l'option -oldcert, l'émetteur du certificat client CMP (option -cert), dans la mesure où l'un d'entre eux est présent, sinon le DN NULL en dernier recours.

L'argument doit être formaté comme /type0=value0/type1=value1/type2=.... Pour plus de détails, voir la description de l'option -subject.

-path remote_path
Chemin HTTP sur le serveur CMP (alias serveur CMP) à utiliser pour les requêtes POST. Par défaut, tout chemin donné avec -server, sinon "/".
-keep_alive value
Si la valeur donnée est 0, les connexions HTTP sont fermées après chaque réponse (ce qui serait le comportement par défaut de HTTP 1.0) même si une transaction CMP nécessite plus d'un aller-retour. Si la valeur est 1 ou 2, une connexion persistante est demandée pour chaque transaction. Si la valeur est 2, une connexion persistante est requise, c'est-à-dire qu'une erreur se produit si le serveur ne l'accorde pas. La valeur par défaut est 1, ce qui signifie préférer garder la connexion ouverte.
-msg_timeout seconds
Nombre de secondes pendant lesquelles un aller-retour de message requête-réponse CMP est autorisé avant qu'une erreur de délai d'attente ne soit renvoyée. Une valeur <= 0 signifie aucune limitation (attente indéfinie). La valeur par défaut utilise le réglage -total_timeout.
-total_timeout seconds
Nombre maximum total de secondes qu'une transaction peut prendre, y compris le sondage, etc. Une valeur <= 0 signifie aucune limitation (attente indéfinie). La valeur par défaut est 0.

Options d'authentification du serveur

-trusted filenames|uris
Les certificats, généralement d'AC racines, que le client doit utiliser comme ancres de confiance lors de la validation de la protection basée sur la signature des messages de réponse CMP. Cette option est ignorée si l'option -srvcert est également donnée. Elle offre plus de flexibilité que -srvcert car le certificat de protection CMP du serveur n'est pas épinglé mais peut être n'importe quel certificat à partir duquel une chaîne peut être construite vers l'une des ancres de confiance données.

Si ni -trusted, ni -srvcert, ni -secret n'est donné, des erreurs de validation de message seront générées, sauf si -unprotected_errors autorise une exception.

Plusieurs sources peuvent être fournies, séparées par des virgules et/ou des espaces blancs (auquel cas l'argument entier doit être entouré de "..."). Chaque source peut contenir plusieurs certificats.

Les options de vérification de certificat -verify_hostname, -verify_ip et -verify_email n'ont aucun effet sur la vérification de certificat activée via cette option.

-untrusted filenames|uris
Certificat(s) d'AC intermédiaire(s) non approuvé(s). Tout certificat supplémentaire donné avec l'option -cert leur est ajouté. Tous ces certificats peuvent être utiles pour la construction de la chaîne de certificats pour son propre certificat de signature CMP (à inclure dans le champ extraCerts des messages de requête) et pour le certificat client TLS (si TLS est utilisé) ainsi que pour la construction de la chaîne lors de la validation des certificats serveur (vérification de la protection du message CMP basée sur la signature) et lors de la validation des certificats nouvellement enregistrés.

Plusieurs sources peuvent être fournies, séparées par des virgules et/ou des espaces blancs (auquel cas l'argument entier doit être entouré de "..."). Chaque source peut contenir plusieurs certificats.

-srvcert filename|uri
Le certificat spécifique du serveur CMP à attendre et à approuver directement (même s'il est expiré) lors de la vérification de la protection basée sur la signature des messages de réponse CMP. Cela épingle le serveur accepté et entraîne l'ignorance de l'option -trusted.

Si défini, le sujet du

le certificat est également utilisé comme valeur par défaut pour le destinataire des requêtes CMP et comme valeur par défaut pour l'expéditeur attendu des réponses CMP.

-expect_sender nom
Nom Distinctif (DN) attendu dans le champ de l'expéditeur des messages CMP entrants. Par défaut, le DN du sujet du -srvcert épinglé, s'il existe.

Ceci peut être utilisé pour s'assurer que seule une entité particulière est acceptée comme signataire du message CMP, et que les attaquants ne peuvent pas utiliser de certificats arbitraires d'une hiérarchie PKI de confiance pour se faire passer frauduleusement pour un serveur CMP. Notez que cette option offre légèrement plus de liberté que la définition de -srvcert, qui épingle le serveur au détenteur d'un certificat particulier, tandis que le nom de l'expéditeur attendu continuera à correspondre après les mises à jour du certificat du serveur.

L'argument doit être formaté comme /type0=valeur0/type1=valeur1/type2=.... Pour plus de détails, voir la description de l'option -subject.

-ignore_keyusage
Ignore les restrictions d'utilisation de clé dans les certificats de signataire CMP lors de la validation de la protection basée sur la signature des messages CMP entrants. Par défaut, "digitalSignature" doit être autorisé par les certificats de signataire CMP. Cette option s'applique aux clients CMP et au serveur mock.
-unprotected_errors
Accepte la protection manquante ou invalide des réponses négatives du serveur. Ceci s'applique aux types de messages et contenus suivants :
  • messages d'erreur
  • réponses négatives de certificat (IP/CP/KUP)
  • réponses négatives de révocation (RP)
  • messages PKIConf négatifs

ATTENTION : Ce réglage entraîne un comportement non spécifié et est destiné exclusivement à permettre l'interopérabilité avec des implémentations de serveur qui violent la RFC 4210, par exemple :

  • la section 5.1.3.1 autorise des exceptions à la protection uniquement pour des cas spéciaux : "Il PEUT y avoir des cas dans lesquels la chaîne de bits PKIProtection n'est délibérément pas utilisée pour protéger un message [...] car une autre protection, externe à PKIX, sera appliquée à la place."
  • la section 5.3.21 est claire sur ErrMsgContent : "La CA DOIT toujours la signer avec une clé de signature."
  • l'annexe D.4 montre un message PKIConf ayant une protection
-no_cache_extracerts
Ne met pas en cache les certificats dans le champ extraCerts des messages CMP reçus. Par défaut, ils sont conservés car ils peuvent être utiles pour valider d'autres messages. Cette option s'applique aux clients CMP et au serveur mock.
-srvcertout nom_fichier
Le fichier où enregistrer le certificat validé avec succès, le cas échéant, que le serveur CMP a utilisé pour la protection des messages de réponse basée sur la signature. S'il n'y a pas de tel certificat, généralement parce que la protection était basée sur MAC, ceci est indiqué en supprimant le fichier (s'il existait).
-extracertsout nom_fichier
Le fichier où enregistrer la liste des certificats contenus dans le champ extraCerts du dernier message de réponse reçu qui n'est ni pollRep ni PKIConf.
-cacertsout nom_fichier
Le fichier où enregistrer la liste des certificats CA contenus dans le champ caPubs si un message de réponse de certificat positif (c'est-à-dire IP, CP ou KUP) a été reçu ou contenu dans un message de réponse général (genp) avec infoType "caCerts".
-oldwithold nom_fichier
Le certificat racine de la CA à inclure dans une requête genm de infoType "rootCaCert". S'il est présent et que le certificat optionnel oldWithNew est reçu, il est vérifié en utilisant le certificat newWithNew comme point d'ancrage de confiance (unique).
-newwithnew nom_fichier
Cette option doit être fournie lorsque -infotype rootCaCert est donné. Elle spécifie le fichier où enregistrer le certificat newWithNew reçu dans un message genp de type "rootCaKeyUpdate". Si, en cas de succès, aucun certificat de ce type n'a été reçu, ce fichier (s'il est présent) est supprimé pour indiquer que la mise à jour du certificat racine de la CA demandée n'est pas disponible.

Tout certificat newWithNew reçu est vérifié en utilisant tout certificat newWithOld reçu comme certificat intermédiaire non fiable et le certificat fourni avec -oldwithold comme point d'ancrage de confiance (unique), ou s'il n'est pas fourni, en utilisant les certificats fournis avec l'option -trusted.

ATTENTION : Le certificat newWithNew est destiné à être un certificat qui sera approuvé. La confiance accordée à celui-ci ne peut pas être plus forte que la confiance accordée au certificat -oldwithold s'il est présent, sinon elle ne peut pas être plus forte que la confiance la plus faible accordée à l'un des certificats -trusted.

-newwithold nom_fichier
Le fichier où enregistrer tout certificat newWithOld reçu dans un message genp de infoType "rootCaKeyUpdate". Si, en cas de succès, aucun certificat de ce type n'a été reçu, ceci est indiqué en supprimant le fichier.
-oldwithnew nom_fichier
Le fichier où enregistrer tout certificat oldWithNew reçu dans un message genp de infoType "rootCaKeyUpdate". Si, en cas de succès, aucun certificat de ce type n'a été reçu, ceci est indiqué en supprimant le fichier.
-crlcert nom_fichier
Certificat à partir duquel dériver les données de l'émetteur de CRL pour le champ source lors de l'obtention d'une CRL dans une requête genm avec infoType "crlStatusList". Tout point de distribution disponible est préféré aux noms d'émetteur.
-oldcrl nom_fichier
La CRL pour laquelle obtenir une mise à jour dans une requête genm avec infoType "crlStatusList". Sauf si l'option -crlcert est également fournie, la CRL donnée est utilisée pour dériver les données de l'émetteur de CRL pour le champ source. Tout point de distribution disponible est préféré aux noms d'émetteur. Si la CRL contient un champ thisUpdate, sa valeur est copiée dans la requête.
-crlout nom_fichier
Le fichier où enregistrer toute CRL reçue dans un message genp de infoType "crls". Si, en cas de succès, aucune CRL de ce type n'a été reçue, ceci est indiqué en supprimant le fichier.

Options d'authentification du client

-ref valeur
Numéro/chaîne/valeur de référence à utiliser comme senderKID de secours ; ceci est requis si aucun nom d'expéditeur ne peut être déterminé à partir des options -cert ou <-subject> et est typiquement utilisé lors de l'authentification avec une clé pré-partagée (MAC basé sur mot de passe).
-secret arg
Fournit la source d'une valeur secrète à utiliser avec la protection de message basée sur MAC. Ceci a priorité sur les options -cert et -key. Le secret est utilisé pour créer la protection basée sur MAC des messages sortants et pour valider les messages entrants qui ont une protection basée sur MAC. L'algorithme utilisé par défaut est le Code d'Authentification de Message Basé sur Mot de Passe (PBM) tel que défini dans la section 5.1.3.1 de la RFC 4210.

Pour plus d'informations sur le format de arg, voir openssl-passphrase-options(1).

-cert nom_fichier|uri
Le certificat de signataire CMP actuel du client. Nécessite que la clé correspondante soit fournie avec -key.

Le sujet et la clé publique contenus dans ce certificat servent de valeurs de secours dans le modèle de certificat des messages IR/CR/KUR.

Le sujet de ce certificat sera utilisé comme expéditeur des messages CMP sortants, tandis que le sujet de -oldcert ou -subjectName peut fournir des valeurs de secours.

L'émetteur de ce certificat est utilisé comme l'une des valeurs de secours du destinataire et comme entrée d'émetteur de secours dans le modèle de certificat des messages IR/CR/KUR.

Lors de la réalisation d'une protection de message basée sur la signature, ce "certificat de protection", également appelé "certificat de signataire", sera inclus en premier dans le champ extraCerts des messages sortants et la signature sera effectuée avec la clé correspondante. Dans les messages de Demande d'Initialisation (IR), ceci peut être utilisé pour l'authentification à l'aide d'un certificat d'entité externe tel que défini dans l'annexe E.7 de la RFC 4210.

Pour les messages de Demande de Mise à Jour de Clé (KUR), il est également utilisé comme certificat à mettre à jour si l'option -oldcert n'est pas fournie.

Si le fichier inclut d'autres certificats, ils sont ajoutés aux certificats non fiables car ils constituent généralement la chaîne du certificat client, qui est incluse dans le champ extraCerts dans les messages de requête protégés par signature.

-own_trusted noms_fichiers|uris
Si cette liste de certificats est fournie, alors la chaîne construite pour le certificat de signataire CMP côté client fourni avec l'option -cert est vérifiée en utilisant les certificats fournis comme points d'ancrage de confiance.

Plusieurs sources peuvent être fournies, séparées par des virgules et/ou des espaces blancs (auquel cas l'argument entier doit être entouré de "..."). Chaque source peut contenir plusieurs certificats.

Les options de vérification de certificat -verify_hostname, -verify_ip et -verify_email n'ont aucun effet sur la vérification de certificat activée via cette option.

-key nom_fichier|uri
Le fichier de clé privée correspondant au certificat actuel du client fourni dans l'option -cert. Il sera utilisé pour la protection des messages basée sur la signature, sauf si l'option -secret indiquant la protection basée sur MAC ou -unprotected_requests est g
iven.

Il est également utilisé comme solution de secours pour l'option -newkey avec les messages IR/CR/KUR.

-keypass arg
Source de la phrase secrète pour la clé privée fournie avec l'option -key. Également utilisé pour -cert et -oldcert s'il s'agit d'un fichier PKCS#12 chiffré. Si non spécifié ici, le mot de passe sera demandé si nécessaire.

Pour plus d'informations sur le format de arg, voir openssl-passphrase-options(1).

-digest nom
Spécifie le nom d'un condensat pris en charge à utiliser dans MSG_SIG_ALG de la RFC 4210 et comme fonction unidirectionnelle (OWF) dans "MSG_MAC_ALG". Le cas échéant, ceci est utilisé pour la protection des messages et les signatures de preuve de possession (POPO). Pour voir la liste des condensats pris en charge, utilisez "openssl list -digest-commands". La valeur par défaut est "sha256".
-mac nom
Spécifie le nom de l'algorithme MAC dans "MSG_MAC_ALG". Pour obtenir les noms des algorithmes MAC pris en charge, utilisez "openssl list -mac-algorithms" et combinez éventuellement un tel nom avec le nom d'un algorithme de condensat pris en charge, par exemple, hmacWithSHA256. La valeur par défaut est "hmac-sha1" conformément à la RFC 4210.
-extracerts fichiers|uris
Certificats à ajouter au champ extraCerts lors de l'envoi de messages. Ils peuvent être utilisés comme chaîne de certificats de signataire CMP par défaut à inclure.

Plusieurs sources peuvent être fournies, séparées par des virgules et/ou des espaces blancs (auquel cas l'argument entier doit être entouré de guillemets). Chaque source peut contenir plusieurs certificats.

-unprotected_requests
Envoie les messages de requête sans protection au niveau CMP.

Options de format des informations d'identification

-certform PEM|DER
Format de fichier à utiliser lors de la sauvegarde d'un certificat dans un fichier. La valeur par défaut est PEM.
-crlform PEM|DER
Format de fichier à utiliser lors de la sauvegarde d'une CRL dans un fichier. La valeur par défaut est DER. Le format DER est préféré car il permet un stockage plus efficace des grandes CRL.
-keyform PEM|DER|P12|ENGINE
Le format de l'entrée de la clé ; non spécifié par défaut. Voir "Options de format" dans openssl(1) pour les détails.
-otherpass arg
Source de la phrase secrète pour les certificats fournis avec les options -trusted, -untrusted, -own_trusted, -srvcert, -crlcert, -out_trusted, -extracerts, -srv_trusted, -srv_untrusted, -ref_cert, -rsp_extracerts, -rsp_capubs, -rsp_newwithnew, -rsp_newwithold, -rsp_oldwithnew, -tls_extra, et -tls_trusted. Si non spécifié ici, le mot de passe sera demandé si nécessaire.

Pour plus d'informations sur le format de arg, voir openssl-passphrase-options(1).

-engine id
Voir "Options de moteur" dans openssl(1). Cette option est obsolète.

Au lieu d'utiliser cette combinaison :

-engine {engineid} -key {keyid} -keyform ENGINE

... il est également possible de simplement fournir l'identifiant de la clé sous forme d'URI à -key, comme ceci :

-key org.openssl.engine:{engineid}:{keyid}

Cela s'applique à toutes les options spécifiant des clés : -key, -newkey, et -tls_key.

-propquery propq

Options de connexion TLS

-tls_used
Fait utiliser TLS par le client CMP (indépendamment si d'autres options liées à TLS sont définies) pour l'échange de messages avec le serveur via HTTP. Cette option n'est pas prise en charge avec l'option -port. Elle est implicite si l'option -server est fournie avec le schéma "https". Elle est ignorée si l'option -server n'est pas fournie ou si -use_mock_srv est fournie ou si -rspin est fournie avec suffisamment d'arguments de nom de fichier.

Les options suivantes liées à TLS sont ignorées si TLS n'est pas utilisé.

-tls_cert nom_fichier|uri
Certificat TLS du client à utiliser pour l'authentification auprès du serveur TLS. Si la source inclut d'autres certificats, ils sont utilisés (avec les certificats -untrusted) pour construire la chaîne de certificats client fournie au serveur TLS.
-tls_key nom_fichier|uri
Clé privée du certificat TLS du client.
-tls_keypass arg
Source de la phrase secrète pour la clé privée TLS du client -tls_key. Également utilisée pour -tls_cert s'il s'agit d'un fichier PKCS#12 chiffré. Si non fournie ici, le mot de passe sera demandé si nécessaire.

Pour plus d'informations sur le format de arg, voir openssl-passphrase-options(1).

-tls_extra noms_fichiers|uris
Certificats supplémentaires à fournir au serveur TLS pendant l'établissement de la connexion.
-tls_trusted noms_fichiers|uris
Certificat(s) de confiance à utiliser pour valider le certificat du serveur TLS. Cela implique la validation du nom d'hôte.

-tls_host nom
Adresse à vérifier lors de la validation du nom d'hôte. Il peut s'agir d'un nom DNS ou d'une adresse IP. Si non fournie, elle prend par défaut l'adresse du -server.

Options côté client pour le débogage et les scénarios hors ligne

-batch
Ne pas demander interactivement d'informations, par exemple lorsqu'un mot de passe est nécessaire. Ceci peut être utile pour le traitement par lots et les tests.
-repeat nombre
Invoque la commande le nombre de fois donné avec les mêmes paramètres. La valeur par défaut est une invocation.
-reqin noms_fichiers
Prend la séquence de requêtes CMP à envoyer au serveur à partir du(des) fichier(s) donné(s) plutôt que de la séquence de requêtes produite en interne.

Cette option est utile pour prendre en charge les scénarios hors ligne où la requête de certificat (ou toute autre requête CMP) est produite à l'avance et envoyée plus tard.

Cette option est ignorée si l'option -rspin est fournie car, dans ce cas, aucune requête n'est réellement envoyée.

Notez que dans tous les cas, le client produit en interne sa séquence de messages de requête CMP. Par conséquent, toutes les options requises pour ce faire (telles que -cmd et toutes les options fournissant les paramètres requis) doivent également être fournies lorsque l'option -reqin est présente.

Si l'option -reqin est fournie pour une requête de certificat et qu'aucune option -newkey, -key, -oldcert ou -csr n'est fournie, une clé publique de secours est prise du fichier de message de requête (s'il est inclus dans le modèle de certificat).

Indice : Dans le cas où l'option -reqin est fournie pour une requête de certificat, il existe des situations où le client a accès à la clé publique à certifier mais pas à la clé privée qui, par défaut, sera nécessaire pour la preuve de possession. Dans ce cas, la POPO n'est pas réellement nécessaire (car le message de requête de certificat produit en interne ne sera pas envoyé), et sa génération peut être désactivée à l'aide des options -popo -1 ou -popo 0.

Plusieurs noms de fichiers peuvent être fournis, séparés par des virgules et/ou des espaces blancs (auquel cas l'argument entier doit être entouré de guillemets).

Les fichiers sont lus autant que nécessaire pour terminer la transaction et les noms de fichiers ont été fournis. Si des requêtes supplémentaires sont nécessaires, les requêtes restantes sont prises à la position respective dans la séquence de requêtes produite internall

y.

Le client doit mettre à jour le champ recipNonce dans les requêtes données (sauf la première) afin de satisfaire les vérifications qui seront effectuées par le serveur. Cela entraîne une re-protection (si la protection des requêtes est requise).

-reqin_new_tid
Utiliser un nouvel identifiant de transaction pour les messages de requête CMP lus avec -reqin, ce qui entraîne leur reprotection (si la protection des requêtes est requise). Cela peut être nécessaire si la séquence de requêtes est réutilisée et que le serveur CMP se plaint que l'identifiant de transaction a déjà été utilisé.
-reqout fichiers
Enregistrer la séquence de requêtes CMP créées par le client dans les fichiers donnés. Ces requêtes ne sont pas envoyées au serveur si l'option -reqin est également utilisée.

Plusieurs noms de fichiers peuvent être donnés, séparés par des virgules et/ou des espaces blancs.

Les fichiers sont écrits autant que nécessaire pour enregistrer la transaction et les noms de fichiers ont été fournis. Si la transaction contient plus de requêtes, les requêtes restantes ne sont pas enregistrées.

-reqout_only fichier
Enregistrer les premières requêtes CMP créées par le client dans le fichier donné et quitter. Toute option relative aux serveurs CMP et à leurs réponses est ignorée.

Cette option est utile pour prendre en charge les scénarios hors ligne où la requête de certificat (ou toute autre requête CMP) est produite à l'avance et envoyée plus tard.

-rspin fichiers
Traiter la séquence de réponses CMP fournies dans les fichiers donnés, sans contacter aucun serveur donné, tant que suffisamment de noms de fichiers sont fournis pour compléter la transaction.

Plusieurs noms de fichiers peuvent être donnés, séparés par des virgules et/ou des espaces blancs.

Tout serveur spécifié via les options -server ou -use_mock_srv n'est contacté que si des réponses supplémentaires sont nécessaires pour compléter la transaction. Dans ce cas, la transaction échouera à moins que le serveur n'ait été préparé pour continuer la transaction déjà commencée.

-rspout fichiers
Enregistrer la séquence des réponses CMP réellement utilisées dans les fichiers donnés. Celles-ci ont été reçues du serveur à moins que -rspin ne soit effectif.

Plusieurs noms de fichiers peuvent être donnés, séparés par des virgules et/ou des espaces blancs.

Les fichiers sont écrits autant que nécessaire pour enregistrer les réponses contenues dans la transaction et les noms de fichiers ont été fournis. Si la transaction contient plus de réponses, les réponses restantes ne sont pas enregistrées.

-use_mock_srv
Tester le client à l'aide de la maquette interne du serveur CMP au niveau de l'API, en contournant le transfert basé sur socket via HTTP. Cela exclut les options -server et -port.

NOTES

Lorsqu'un client obtient, d'un serveur CMP, des certificats d'AC auxquels il va faire confiance, par exemple via le champ "caPubs" d'une réponse de certificat ou en utilisant des messages généraux avec le type d'information "caCerts" ou "rootCaCert", l'authentification du serveur CMP est particulièrement critique. Par conséquent, un soin particulier doit être apporté à la configuration de l'authentification du serveur en utilisant -trusted et les options associées pour l'authentification basée sur certificat ou -secret pour la protection basée sur MAC. Si l'authentification est basée sur certificat, l'option -srvcertout doit être utilisée pour obtenir le certificat serveur validé et effectuer une vérification d'autorisation basée sur celui-ci.

Lors de la configuration de CMP et de l'expérimentation avec les options d'enregistrement, diverses erreurs surviennent généralement jusqu'à ce que la configuration soit correcte et complète. Lorsque le serveur CMP signale une erreur, le client vérifie par défaut la protection du message de réponse CMP. Pourtant, certains services CMP ont tendance à ne pas protéger les réponses négatives. Dans ce cas, le client les rejettera, et par conséquent leur contenu ne sera pas affiché bien qu'ils contiennent généralement des indices qui seraient utiles pour le diagnostic. Pour aider dans de tels cas, le client CMP offre une solution de contournement via l'option -unprotected_errors, qui permet d'accepter de tels messages négatifs.

Si OpenSSL a été compilé avec le support de traçage activé (par exemple, "./config enable-trace") et que la variable d'environnement OPENSSL_TRACE inclut HTTP, les requêtes et les en-têtes de réponse transférés via HTTP sont imprimés.

EXEMPLES

Exemples simples utilisant le fichier de configuration OpenSSL par défaut

Cette implémentation client CMP est livrée avec des sections CMP démonstratives dans le fichier de configuration d'exemple openssl/apps/openssl.cnf, qui peut être utilisé pour interagir facilement avec l'AC Insta Demo.

Afin d'enregistrer un certificat initial de cet AC, il suffit d'exécuter les commandes shell suivantes.

export OPENSSL_CONF=/chemin/vers/openssl/apps/openssl.cnf
openssl genrsa -out insta.priv.pem
openssl cmp -section insta

Cela devrait produire le fichier insta.cert.pem contenant un nouveau certificat pour la clé privée détenue dans insta.priv.pem. Il peut être consulté en utilisant, par exemple,

openssl x509 -noout -text -in insta.cert.pem

Dans le cas où la configuration réseau nécessite l'utilisation d'un proxy HTTP, il peut être fourni comme d'habitude via la variable d'environnement http_proxy ou via l'option -proxy dans le fichier de configuration ou l'argument de ligne de commande CMP -proxy, par exemple

-proxy http://192.168.1.1:8080

Dans le scénario de l'AC Insta Demo, les clients et le serveur peuvent utiliser le secret pré-partagé insta et la valeur de référence 3078 pour s'authentifier mutuellement.

Alternativement, les messages CMP peuvent être protégés par signature, où l'ancre de confiance est dans ce cas insta.ca.crt et le client peut utiliser tout certificat déjà obtenu de cet AC, comme spécifié dans la section [signature] de l'exemple de configuration. Ceci peut être utilisé en combinaison avec la section [insta] simplement en

openssl cmp -section insta,signature

Par défaut, le type de message CMP IR est utilisé, mais CR fonctionne également ici. Ceci peut être spécifié directement en ligne de commande :

openssl cmp -section insta -cmd cr

ou en référençant en plus la section [cr] de l'exemple de configuration :

openssl cmp -section insta,cr

Afin de mettre à jour le certificat enregistré, on peut appeler

openssl cmp -section insta,kur,signature

en utilisant la protection par signature avec le certificat qui doit être mis à jour. Pour les mises à jour de certificats, la protection basée sur MAC ne doit généralement pas être utilisée.

De la même manière, tout certificat précédemment enregistré peut être révoqué par

openssl cmp -section insta,rr -trusted insta.ca.crt

ou

openssl cmp -section insta,rr,signature

Beaucoup plus d'options peuvent être fournies dans le fichier de configuration et/ou sur la ligne de commande. Par exemple, l'option CLI -reqexts peut faire référence à une section du fichier de configuration définissant les extensions X.509 à utiliser dans les requêtes de certificat, telles que "v3_req" dans openssl/apps/openssl.cnf :

openssl cmp -section insta,cr -reqexts v3_req

Enregistrement de certificat

Les exemples suivants n'utilisent pas de fichier de configuration au départ. Ils supposent qu'un serveur CMP peut être contacté sur le port TCP local 80 et accepte les requêtes sous l'alias /pkix/.

Pour enregistrer son tout premier certificat, le client génère une clé client et envoie un message de requête initial au serveur CMP local en utilisant une clé secrète pré-partagée pour l'authentification mutuelle. Dans cet exemple, le client n'a pas encore le certificat de l'AC, donc nous spécifions le nom de l'AC avec l'option -recipient et enregistrons tous les certificats d'AC que nous pourrions recevoir dans le fichier "capubs.pem".

Dans les exemples d'utilisation de ligne de commande ci-dessous, le "\" à la fin des lignes est utilisé uniquement pour le formatage ; chaque invocation de commande doit être sur une seule ligne.

openssl genrsa -out cl_key.pem
openssl cmp -cmd ir -server 127.0.0.1:80/pkix/ -recipient "/CN=CMPserver" \
  -ref 1234 -secret pass:1234-5678 \
  -newkey cl_key.pem -subject "/CN=MyName" \
  -cacertsout capubs.pem -certout cl_cert.pem

Mise à jour de certificat

Ensuite, lorsque le certificat client et sa paire clé associée doivent être mis à jour, le client peut envoyer une requête de mise à jour de clé en prenant les certificats dans "capubs.pem" comme confiance pour l'authentification du serveur et en utilisant le certificat et la clé précédents pour sa propre authentification. Ensuite, il peut commencer à utiliser le nouveau certificat et la nouvelle clé.

openssl genrsa -out cl_key_new.pem
openssl cmp -cmd kur -server 127.0.0.1:80/pkix/ \
  -trusted capubs.pem \
  -cert cl_cert.pem -key cl_key.pem \
  -newkey cl_key_new.pem -certout cl_cert.pem
cp cl_key_new.pem cl_key.pem

Cette séquence de commandes peut être répétée autant de fois que nécessaire.

Demande d'informations auprès du serveur CMP

Demande de "toutes les informations pertinentes" avec un message général vide. Ceci affiche les informations sur tous les infoTypes ITAV reçus sur stdout.

openssl cmp -cmd genm -server 127.0.0.1/pkix/ -recipient "/CN=CMPserver" \
  -ref 1234 -secret pass:1234-5678

Utilisation d'un fichier de configuration personnalisé

Pour les invocations client CMP, en particulier pour l'enregistrement de certificats, de nombreux paramètres doivent généralement être définis, ce qui est fastidieux et sujet aux erreurs à faire sur la ligne de commande. Par conséquent, le client offre la possibilité de lire les options à partir de sections du fichier de configuration OpenSSL, généralement appelé openssl.cnf. Les valeurs trouvées là peuvent toujours être étendues et même remplacées par des sections chargées ultérieurement et sur la ligne de commande.

Après avoir inclus dans le fichier de configuration les sections suivantes :

[cmp]
server = 127.0.0.1
path = pkix/
trusted = capubs.pem
cert = cl_cert.pem
key = cl_key.pem
newkey = cl_key.pem
certout = cl_cert.pem
[init]
recipient = "/CN=CMPserver"
trusted =
cert =
key =
ref = 1234
secret = pass:1234-5678-1234-567
subject = "/CN=MyName"
cacertsout = capubs.pem

les transactions d'enregistrement ci-dessus se réduisent à

openssl cmp -section cmp,init
openssl cmp -cmd kur -newkey cl_key_new.pem

et la transaction ci-dessus utilisant un message général se réduit à

openssl cmp -section cmp,init -cmd genm

NOM

openssl-cmp — Client pour le protocole PKCS#7 CMP.

SYNTAXE

openssl cmp [options]

DESCRIPTION

La commande openssl cmp est un client pour le protocole PKCS#7 CMP (Certificate Management Protocol).

OPTIONS

-server <hôte>:<port>
Spécifie le serveur CMP à contacter.
-cert <fichier_certificat>
Le certificat du client.
-key <fichier_clé>
La clé privée du client.
-cacert <fichier_cacert>
Le certificat de l'autorité de certification (CA).
-req <fichier_requête>
Le fichier de requête de certificat.
-new
Demande un nouveau certificat.
-poll
Demande la publication d'un certificat.
-revoke
Demande la révocation d'un certificat.
-getcertinit
Demande un certificat initial.
-getcertreq
Demande une requête de certificat.
-challenge <défi>
Spécifie le défi pour l'authentification.
-ref <référence>
Spécifie la référence du certificat.
-verbose
Active la sortie détaillée.
-help
Affiche l'aide.

NOTES

Cette commande est utile pour interagir avec des serveurs CMP pour la gestion des certificats.

EXEMPLES

Exemple d'utilisation :

openssl cmp -server cmp.example.com:8080 -cert client.pem -key client.key -cacert ca.pem -new
