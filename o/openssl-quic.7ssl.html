NOM

openssl-quic - QUIC d'OpenSSL

DESCRIPTION

OpenSSL 3.2 et versions ultérieures prennent en charge le protocole de transport QUIC. Vous pouvez utiliser les capacités QUIC d'OpenSSL pour les applications client et serveur. Cette page de manuel décrit comment permettre aux applications d'utiliser le protocole QUIC via l'API libssl.

Le protocole QUIC est mappé sur l'API SSL standard. Une connexion QUIC est représentée par un objet SSL de la même manière qu'une connexion TLS. Seuls des changements minimaux sont nécessaires dans les applications existantes qui utilisent l'API libssl pour intégrer la prise en charge du protocole QUIC. Les clients QUIC peuvent utiliser OSSL_QUIC_client_method(3) ou OSSL_QUIC_client_thread_method(3) avec SSL_CTX_new(3). Voir ci-dessous pour plus de détails sur la différence entre les deux. Pour les serveurs, il n'y a qu'une seule option : la méthode SSL OSSL_QUIC_server_method(3) avec SSL_CTX_new(3).

Le reste de cette page de manuel discute, dans l'ordre :

  • Mode de flux par défaut par rapport au mode multi-flux pour les clients ;
  • Les modifications apportées aux API libssl existantes qui sont dictées par les exigences d'implémentation liées à QUIC, que les applications existantes doivent garder à l'esprit ;
  • Les aspects qui doivent être pris en compte par les applications existantes lors de l'adoption de QUIC, y compris les modifications potentielles qui pourraient être nécessaires.
  • Approches d'utilisation recommandées pour les nouvelles applications.
  • Nouvelles API spécifiques à QUIC.

MODES DE FONCTIONNEMENT DU CLIENT

Lorsqu'un client crée une connexion QUIC, par défaut, il fonctionne en mode de flux par défaut, conçu pour assurer la compatibilité avec les modèles d'utilisation des applications existantes sans QUIC. Dans ce mode, la connexion a un seul flux associé. Les appels à SSL_read(3) et SSL_write(3) sur l'objet SSL de la connexion QUIC lisent et écrivent sur ce flux. Que le flux soit initié par le client ou par le serveur du point de vue QUIC dépend de l'appel à SSL_read(3) ou SSL_write(3) qui est effectué en premier.

Le mode de flux par défaut est principalement destiné à la compatibilité avec les applications existantes. Pour les nouvelles applications utilisant QUIC, il est recommandé de désactiver ce mode et d'adopter plutôt l'API multi-flux. Voir la section RECOMMANDATIONS POUR LES NOUVELLES APPLICATIONS pour plus de détails.

Mode de flux par défaut

Une connexion client QUIC peut être utilisée en mode de flux par défaut ou en mode multi-flux. Par défaut, un objet SSL de connexion QUIC nouvellement créé utilise le mode de flux par défaut.

En mode de flux par défaut, un flux est implicitement créé et lié à l'objet SSL de la connexion QUIC ; les appels à SSL_read(3) et SSL_write(3) sur l'objet SSL de la connexion QUIC fonctionnent par défaut et sont mappés à ce flux.

Lorsque le mode de flux par défaut est utilisé, toute fonction API qui peut être appelée sur un objet SSL de flux QUIC peut également être appelée sur un objet SSL de connexion QUIC, auquel cas elle affecte le flux par défaut lié à la connexion.

L'identité d'un flux QUIC, y compris son ID de flux, varie selon que le flux est initié par le client ou par le serveur. En mode de flux par défaut, si une application cliente appelle SSL_read(3) avant tout appel à SSL_write(3) sur la connexion, il est supposé que le protocole applicatif utilise un flux initié par le serveur, et l'appel à SSL_read(3) ne se terminera pas (soit en bloquant, soit en échouant de manière appropriée si le mode non bloquant est configuré) tant que le serveur n'aura pas initié un flux. Inversement, si l'application cliente appelle SSL_write(3) avant tout appel à SSL_read(3) sur la connexion, il est supposé qu'un flux initié par le client doit être utilisé et un tel flux est créé automatiquement.

Le mode de flux par défaut est destiné à faciliter la compatibilité avec les applications existantes. Les nouvelles applications adoptant QUIC devraient utiliser le mode multi-flux, décrit ci-dessous, et éviter l'utilisation des fonctionnalités de flux par défaut.

Il est possible d'utiliser des flux supplémentaires en mode de flux par défaut en utilisant SSL_new_stream(3) et SSL_accept_stream(3) ; notez que la politique de flux entrant par défaut devra être modifiée à l'aide de SSL_set_incoming_stream_policy(3) pour utiliser SSL_accept_stream(3) dans ce cas. Cependant, il est fortement recommandé aux applications utilisant des flux supplémentaires d'utiliser plutôt le mode multi-flux.

Appeler SSL_new_stream(3) ou SSL_accept_stream(3) avant qu'un flux par défaut n'ait été associé à l'objet SSL de la connexion QUIC inhibera la création future d'un flux par défaut.

Mode multi-flux

Le mode d'utilisation recommandé pour les nouvelles applications adoptant QUIC est le mode multi-flux, dans lequel aucun flux par défaut n'est attaché à l'objet SSL de la connexion QUIC et les tentatives d'appels à SSL_read(3) et SSL_write(3) sur l'objet SSL de la connexion QUIC échouent. Au lieu de cela, une application appelle SSL_new_stream(3) ou SSL_accept_stream(3) pour créer des objets SSL de flux individuels pour envoyer et recevoir des données d'application en utilisant SSL_read(3) et SSL_write(3).

Pour utiliser le mode multi-flux, appelez SSL_set_default_stream_mode(3) avec l'argument SSL_DEFAULT_STREAM_MODE_NONE ; cette fonction doit être appelée avant d'initier la connexion. Le mode de flux par défaut ne peut pas être modifié après l'initiation d'une connexion.

Lorsque le mode multi-flux est utilisé, ce qui signifie qu'aucun flux par défaut n'est associé à la connexion, les appels aux fonctions API définies comme opérant sur un flux QUIC échouent lorsqu'ils sont appelés sur l'objet SSL de la connexion QUIC. Par exemple, des appels tels que SSL_write(3) ou SSL_get_stream_id(3) échoueront.

    CONSIDÉRATIONS POUR LES APPLICATIONS EXISTANTES

    Les applications existantes cherchant à adopter QUIC devraient appliquer la liste suivante pour déterminer les changements qu'elles devront apporter :

    • Une application client souhaitant utiliser QUIC doit utiliser OSSL_QUIC_client_method(3) ou OSSL_QUIC_client_thread_method(3) comme méthode SSL. Pour plus d'informations sur les différences entre ces deux méthodes, voir MODE ASSISTÉ PAR THREADS.
    • Une application serveur souhaitant utiliser QUIC doit utiliser OSSL_QUIC_server_method(3). Le serveur peut alors accepter de nouvelles connexions avec SSL_accept_connection(3).
    • Déterminer comment fournir un accès réseau à QUIC. Déterminer lesquels des éléments ci-dessous s'appliquent à votre application :
    • Votre application utilise BIO_s_socket(3) pour construire un BIO qui est passé à l'objet SSL pour lui fournir un accès réseau.

      Changements nécessaires : Modifiez votre application pour utiliser BIO_s_datagram(3) à la place lors de l'utilisation de QUIC. La socket doit être configurée en mode non bloquant. Vous pourriez ou non avoir besoin d'utiliser SSL_set1_initial_peer_addr(3) pour définir l'adresse du pair initial ; voir la section API SPÉCIFIQUES QUIC pour les détails.

    • Votre application utilise BIO_new_ssl_connect(3) pour construire un BIO qui est passé à l'objet SSL pour lui fournir un accès réseau.

      Changements nécessaires : Aucun changement nécessaire. L'utilisation de QUIC est détectée automatiquement et un socket datagramme est créé au lieu d'un socket TCP normal.

    • Votre application utilise une autre stratégie d'E/S de cette liste mais la combine avec un BIO_f_buffer(3), par exemple en utilisant BIO_push(3).

      Changements nécessaires : Désactivez l'utilisation de BIO_f_buffer(3) lors de l'utilisation de QUIC. L'utilisation d'un tel tampon est incompatible avec QUIC car QUIC nécessite des sémantiques datagrammes dans son interaction avec le réseau.

    • Votre application utilise une paire de BIO pour que l'objet SSL lise et écrive du trafic réseau dans un tampon mémoire. Votre application gère la transmission et la réception des données tamponnées elle-même d'une manière inconnue de libssl.

      Changements nécessaires : Passez d'une paire de BIO conventionnelle à BIO_s_dgram_pair(3) à la place, qui possède les sémantiques datagrammes nécessaires. Vous devrez modifier votre application pour transmettre et recevoir à l'aide d'une socket UDP et utiliser des sémantiques datagrammes lors de l'interaction avec l'instance de BIO_s_dgram_pair(3).

    • Votre application utilise une méthode BIO personnalisée pour fournir un accès réseau à l'objet SSL.

      Changements nécessaires : Le BIO personnalisé doit être réarchitecturé pour avoir des sémantiques datagrammes. BIO_sendmmsg(3) et BIO_recvmmsg(3) doivent être implémentés. Ces appels doivent fonctionner en mode non bloquant. Implémentez éventuellement les méthodes BIO_get_rpoll_descriptor(3) et BIO_get_wpoll_descriptor(3) si désiré. L'implémentation de ces méthodes est requise si des sémantiques bloquantes au niveau de l'API SSL sont souhaitées.

    • Une application doit explicitement configurer si elle souhaite utiliser les API SSL en mode bloquant ou non. Traditionnellement, un objet SSL fonctionnait automatiquement en mode bloquant ou non bloquant en fonction du fait que le BIO réseau sous-jacent fonctionnait en mode bloquant ou non bloquant. QUIC nécessite l'utilisation d'un BIO réseau non bloquant, par conséquent le mode de blocage au niveau applicatif peut être configuré explicitement par l'application en utilisant la nouvelle API SSL_set_blocking_mode(3). Le mode par défaut est bloquant. Si une application souhaite utiliser les API de l'objet SSL au niveau applicatif de manière non bloquante, elle doit ajouter un appel à SSL_set_blocking_mode(3) pour désactiver le mode bloquant.
    • Si votre application cliente ne choisit pas d'utiliser le mode assisté par threads, elle doit s'assurer qu'elle appelle régulièrement une fonction d'E/S sur l'objet SSL (par exemple, SSL_read(3) ou SSL_write(3)), ou la nouvelle fonction SSL_handle_events(3). Si l'objet SSL est utilisé en mode bloquant, un appel bloquant continu à une fonction d'E/S satisfait cette exigence. Ceci est requis pour garantir que les événements de temporisation requis par QUIC sont gérés en temps voulu. <

      BACKGROUND

      Most applications will service the SSL object by calling SSL_read(3) or SSL_write(3) regularly. If an application does not do this, it should ensure that SSL_handle_events(3) is called regularly.

      SSL_get_event_timeout(3) can be used to determine when SSL_handle_events(3) must next be called.

      If the SSL object is being used with an underlying network BIO which is pollable (such as BIO_s_datagram(3)), the application can use SSL_get_rpoll_descriptor(3), SSL_get_wpoll_descriptor(3) to obtain resources which can be used to determine when SSL_handle_events(3) should be called due to network I/O.

      Client applications which use thread assisted mode do not need to be concerned with this requirement, as the QUIC implementation ensures timeout events are handled in a timely manner. See THREAD ASSISTED MODE for details.

      API CHANGES AND GUIDANCE

      • Ensure that your usage of SSL_want(3), SSL_want_read(3) and SSL_want_write(3) reflects the API changes described in CHANGES TO EXISTING APIS. In particular, you should use these APIs to determine the ability of a QUIC stream to receive or provide application data, not to to determine if network I/O is required.
      • Evaluate your application's use of SSL_shutdown(3) in light of the changes discussed in CHANGES TO EXISTING APIS. Depending on whether your application wishes to prioritise RFC conformance or rapid shutdown, consider using the new SSL_shutdown_ex(3) API instead. See QUIC-SPECIFIC APIS for details.

      RECOMMENDED USAGE IN NEW APPLICATIONS

      The recommended usage in new applications varies depending on three independent design decisions:

      • Whether the application will use blocking or nonblocking I/O at the application level (configured using SSL_set_blocking_mode(3)).

        If the application does nonblocking I/O at the application level it can choose to manage its own polling and event loop; see APPLICATION-DRIVEN EVENT LOOPS.

      • Whether the application intends to give the QUIC implementation direct access to a network socket (e.g. via BIO_s_datagram(3)) or whether it intends to buffer transmitted and received datagrams via a BIO_s_dgram_pair(3) or custom BIO.

        The former is preferred where possible as it reduces latency to the network, which enables QUIC to achieve higher performance and more accurate connection round trip time (RTT) estimation.

      • Whether thread assisted mode will be used (see THREAD ASSISTED MODE).

      Simple demos for QUIC usage under these various scenarios can be found at https://github.com/openssl/openssl/tree/master/doc/designs/ddd.

      Applications which wish to implement QUIC-specific protocols should be aware of the APIs listed under QUIC-SPECIFIC APIS which provide access to QUIC-specific functionality. For example, SSL_stream_conclude(3) can be used to indicate the end of the sending part of a stream, and SSL_shutdown_ex(3) can be used to provide a QUIC application error code when closing a connection.

      Regardless of the design decisions chosen above, it is recommended that new applications avoid use of the default stream mode and use the multi-stream API by calling SSL_set_default_stream_mode(3); see the MODES OF OPERATION section for details.

      QUIC-SPECIFIC APIS

      This section details new APIs which are directly or indirectly related to QUIC. For details on the operation of each API, see the referenced man pages.

      The following SSL APIs are new but relevant to both QUIC and DTLS:

      SSL_get_event_timeout(3)
      Determines when the QUIC implementation should next be woken up via a call to SSL_handle_events(3) (or another I/O function such as SSL_read(3) or SSL_write(3)), if ever.

      This can also be used with DTLS and supersedes DTLSv1_get_timeout(3) for new usage.

      SSL_handle_events(3)
      This is a non-specific I/O operation which makes a best effort attempt to perform any pending I/O or timeout processing. It can be used to advance the QUIC state machine by processing incoming network traffic, generating outgoing network traffic and handling any expired timeout events. Most other I/O functions on an SSL object, such as SSL_read(3) and SSL_write(3), implicitly perform event handling on the SSL object, so calling this function is only needed if no other I/O function is to be called.

      This can also be used with DTLS and supersedes DTLSv1_handle_timeout(3) for new usage.

      The following SSL APIs are specific to QUIC:

      SSL_new_listener(3)
      Creates a listener SSL object, which differs from an ordinary SSL object in that it is used to provide an abstraction for the acceptance of network connections in a protocol-agnostic manner.

      Currently, listener SSL objects are only supported for QUIC server usage or client-only usage. The listener interface may expand to support additional protocols in the future.

      SSL_new_listener_from(3)
      Creates a listener SSL object which is subordinate to a QUIC domain SSL object ssl. See SSL_new_domain(3) and openssl-quic-concurrency(7) for details on QUIC domain SSL objects.
      SSL_is_listener(3)
      Returns 1 if and only if an SSL object is a listener SSL object.
      SSL_get0_listener(3)
      Returns an SSL object pointer (potentially to the same object on which it is called) or NULL.
      SSL_listen(3)
      Begin listening after a listener has been created. It is ordinarily not needed to call this because it will be called automatically on the first call to SSL_accept_connection(3).
      SSL_accept_connection(3)
      Accepts a new incoming connection for a listner SSL object. A new SSL object representing the accepted connection is created and returned on success. If no incoming connection is available and the listener SSL object is configured in nonblocking mode, NULL is returned.
      SSL_get_accept_connection_queue_len(3)
      Returns an informational value listing the number of connections waiting to be popped from the queue via calls to SSL_accept_connection().
      SSL_new_from_listener(3)
      Creates a client connection under a given listener SSL object. For QUIC, it is also possible to use SSL_new_from_listener() in conjunction with a listener which does accept incoming connections (i.e., which was not created using SSL_LISTENER_FLAG_NO_ACCEPT), leading to a UDP network endpoint which has both incoming and outgoing connections.
      SSL_new_domain(3)
      Creates a new QUIC event domain, represented as an SSL object. This is known as a QUIC domain SSL object. The concept of a QUIC event domain is discussed in detail in openssl-quic-concurrency(7).
      SSL_is_domain(3)
      Returns 1 if an SSL object is a QUIC domain SSL object.
      SSL_get0_domain(3)
      SSL_get0_domain() obtains a pointer to the QUIC domain SSL object in an SSL object hierarchy (if any).
      SSL_set_blocking_mode(3), SSL_get_blocking_mode(3)
      Configures whether blocking semantics are used at the application level. This determines whether calls to functions such as SSL_read(3) and SSL_write(3) will block.
      SSL_get_rpoll_descriptor(3), SSL_get_wpoll_descriptor(3)
      These functions facilitate operation in nonblocking mode.

      When an SSL object is being used with an underlying network read BIO which supports polling, SSL_get_rpoll_descriptor(3) outputs an OS resource which can be used to synchronise on network read

      ability events qui devraient entraîner un appel à SSL_handle_events(3). SSL_get_wpoll_descriptor(3) fonctionne de manière analogue pour le BIO d'écriture réseau sous-jacent.

      Les descripteurs de sondage fournis par ces fonctions ne doivent être utilisés que lorsque SSL_net_read_desired(3) et SSL_net_write_desired(3) retournent 1, respectivement.

      SSL_net_read_desired(3), SSL_net_write_desired(3)
      Ces fonctions facilitent le fonctionnement en mode non bloquant et sont utilisées conjointement avec SSL_get_rpoll_descriptor(3) et SSL_get_wpoll_descriptor(3) respectivement. Elles déterminent si le descripteur de sondage respectif est actuellement pertinent aux fins de la sondage.
      SSL_set1_initial_peer_addr(3)
      Cette fonction peut être utilisée pour définir l'adresse initiale du pair pour une connexion QUIC sortante. Cette fonction doit être utilisée dans le cas général lors de la création d'une connexion QUIC sortante ; cependant, la bonne adresse initiale du pair peut être auto-détectée dans certains cas. Voir SSL_set1_initial_peer_addr(3) pour plus de détails.
      SSL_shutdown_ex(3)
      Ceci complète SSL_shutdown(3) en permettant de spécifier un code d'erreur d'application. Il permet également à une application de décider de la rapidité avec laquelle elle souhaite qu'une fermeture soit effectuée, potentiellement en faisant des compromis sur la stricte conformité RFC.
      SSL_stream_conclude(3)
      Ceci permet à une application d'indiquer la fin normale de la partie émission d'un flux QUIC. Ceci correspond au drapeau FIN dans la RFC QUIC. La partie réception d'un flux reste utilisable.
      SSL_stream_reset(3)
      Ceci permet à une application d'indiquer la terminaison anormale de la partie émission d'un flux. Ceci correspond à la trame RESET_STREAM dans la RFC QUIC.
      SSL_get_stream_write_state(3) et SSL_get_stream_read_state(3)
      Ceci permet à une application de déterminer les états actuels des flux pour les parties émission et réception d'un flux respectivement.

      Ceci permet à une application de déterminer le code d'erreur d'application qui a été signalé par un pair ayant effectué une terminaison de flux non normale de la partie émission ou réception respective d'un flux, le cas échéant.
      SSL_get_conn_close_info(3)
      Ceci permet à une application de déterminer le code d'erreur qui a été signalé lorsque le point d'extrémité local ou distant a terminé la connexion QUIC.
      SSL_get0_connection(3)
      Récupère l'objet SSL de connexion QUIC à partir d'un objet SSL de flux QUIC.

      SSL_get_stream_type(3)

      Les API BIO suivantes ne sont pas spécifiques à QUIC mais ont été ajoutées pour faciliter les exigences spécifiques à QUIC et sont étroitement associées à son utilisation :

      BIO_s_dgram_pair(3)
      Ceci est une nouvelle méthode BIO qui est similaire à une paire BIO conventionnelle mais fournit une sémantique de datagramme.
      BIO_get_rpoll_descriptor(3), BIO_get_wpoll_descriptor(3)
      Ceci est une nouvelle API BIO qui permet à un BIO d'exposer un descripteur de sondage. Cette API est utilisée pour implémenter les API SSL correspondantes SSL_get_rpoll_descriptor(3) et SSL_get_wpoll_descriptor(3).
      BIO_sendmmsg(3), BIO_recvmmsg(3)
      Ceci est une nouvelle API BIO qui peut être implémentée par des BIOs qui implémentent une sémantique de datagramme. Elle est implémentée par BIO_s_datagram(3) et BIO_s_dgram_pair(3). Elle est utilisée par l'implémentation QUIC pour envoyer et recevoir des datagrammes UDP.
      BIO_dgram_set_no_trunc(3), BIO_dgram_get_no_trunc(3)
      Par défaut, BIO_s_dgram_pair(3) a une sémantique comparable à celle des sockets Berkeley utilisés avec une sémantique de datagramme. Cela permet d'activer un mode alternatif dans lequel les datagrammes ne seront pas tronqués silencieusement s'ils sont trop volumineux.
      BIO_dgram_set_caps(3), BIO_dgram_get_caps(3)
      Ces fonctions sont utilisées pour permettre à l'utilisateur d'une extrémité d'une paire BIO_s_dgram_pair(3) d'indiquer ses capacités à l'autre extrémité d'une BIO_s_dgram_pair(3). En particulier, cela permet à une application d'informer l'implémentation QUIC si elle est préparée à gérer les adresses locales et/ou de pair dans les datagrammes transmis et de fournir les informations applicables dans les datagrammes reçus.
      BIO_dgram_get_local_addr_cap(3), BIO_dgram_set_local_addr_enable(3), BIO_dgram_get_local_addr_enable(3)
      Le support d'adressage local fait référence à la capacité d'un BIO avec une sémantique de datagramme à permettre la spécification d'une adresse source lors de la transmission et à signaler l'adresse de destination lors de la réception. Ces fonctions peuvent être utilisées pour déterminer si un BIO peut supporter l'adressage local et pour activer le support d'adressage local s'il le peut.
      BIO_err_is_non_fatal(3)
      Ceci est utilisé pour déterminer si une erreur lors de l'appel à BIO_sendmmsg(3) ou BIO_recvmmsg(3) est de nature éphémère, comme les erreurs "would block".

      MODE ASSISTÉ PAR THREAD

      Le mode optionnel assisté par thread pour les clients peut être utilisé avec OSSL_QUIC_client_thread_method(3). Dans ce mode, un thread d'arrière-plan est créé automatiquement. L'implémentation QUIC d'OpenSSL prend alors la responsabilité de s'assurer que les événements de temporisation sont gérés en temps utile, même si aucune fonction d'E/S SSL telle que SSL_read(3) ou SSL_write(3) n'est appelée par l'application pendant longtemps.

      Toutes les opérations de verrouillage nécessaires sont gérées automatiquement en interne, mais les garanties de sécurité des threads pour l'API SSL publique restent inchangées. Par conséquent, une application doit toujours effectuer son propre verrouillage si elle souhaite utiliser l'API SSL publique de manière concurrente.

      Étant donné que ce mode repose sur les threads, il n'est pas disponible sur les plateformes où le support des threads n'est pas disponible ou n'est pas pris en charge par OpenSSL. Cependant, il offre le mode d'utilisation le plus simple pour une application.

      BOUCLES D'ÉVÉNEMENTS PILOTÉES PAR L'APPLICATION

      L'implémentation QUIC d'OpenSSL est conçue pour faciliter les applications qui souhaitent utiliser les API SSL de manière bloquante, mais elle est également conçue pour faciliter les applications qui souhaitent utiliser les API SSL de manière non bloquante et gérer directement leurs propres boucles d'événements et leur propre polling. Ceci est utile lorsqu'il est souhaitable d'héberger l'implémentation QUIC d'OpenSSL sur l'infrastructure d'E/S non bloquante existante d'une application.

      Ceci est pris en charge via le concept de descripteurs de sondage ; voir BIO_get_rpoll_descriptor(3) pour les détails. En général, un BIO_POLL_DESCRIPTOR est une structure qui exprime une sorte de ressource système qui peut être utilisée pour synchroniser les événements d'E/S. L'implémentation QUIC fournit un BIO_POLL_DESCRIPTOR basé sur le descripteur de sondage fourni par le BIO réseau sous-jacent. Il s'agit généralement d'un handle de socket système, bien que les BIO personnalisés puissent choisir d'implémenter leur propre format de descripteur de sondage.

      En général, une application qui souhaite gérer sa propre boucle d'événements doit interagir avec l'objet SSL comme suit :

      • Elle doit fournir des BIO de lecture et d'écriture avec des sémantiques de datagrammes non bloquants à l'objet SSL en utilisant SSL_set0_rbio(3) et SSL_set0_wbio(3). Cela pourrait être un BIO abstraiant un socket réseau tel que BIO_s_datagram(3), ou un BIO abstraiant une sorte de tampon mémoire tel que BIO_s_dgram_pair(3). L'utilisation d'un BIO personnalisé est également possible.
      • Elle doit configurer l'objet SSL en mode non bloquant en appelant SSL_set_blocking_mode(3).
      • Elle doit configurer l'objet SSL comme souhaité, définir un pair initial au besoin en utilisant SSL_set1_initial_peer_addr(3), et déclencher le processus de connexion en appelant SSL_connect(3).
      • Si les BIO de lecture et d'écriture réseau fournis étaient sondables (par exemple, un BIO_s_datagram(3), ou un BIO personnalisé qui implémente BIO_get_rpoll_descriptor(3) et BIO_get_wpoll_descriptor(3)), elle doit effectuer les étapes suivantes de manière répétée :
      • L'application doit appeler SSL_get_rpoll_descriptor(3) et SSL_get_wpoll_descriptor(3) pour identifier les ressources système qui peuvent être utilisées pour la synchronisation.
      • Elle doit appeler SSL_net_read_desired(3) et SSL_net_write_desired(3) pour déterminer si l'implémentation QUIC est actuellement intéressée par les événements de lisibilité et d'écrivabilité sur le BIO réseau sous-jacent qui a été fourni, et appeler SSL_get_event_timeout(3) pour déterminer si un événement de timeout deviendra applicable à l'avenir.
      • Elle doit attendre qu'un des événements suivants se produise :
      • Le descripteur de sondage retourné par SSL_get_rpoll_descriptor(3) devient lisible (si SSL_net_read_desired(3) a retourné 1) ;
      • Le descripteur de sondage retourné par SSL_get_wpoll_descriptor(3) devient écrivable (si SSL_net_write_desired(3) a retourné 1) ;
      • Le timeout retourné par SSL_get_event_timeout(3) (s'il y en a un) expire.

      Une fois que l'un de ces événements se produit, SSL_handle_events(3) doit être appelé.

      •
      Si les BIO de lecture et d'écriture réseau fournis n'étaient pas sondables (par exemple, dans le cas de BIO_s_dgram_pair(3)), l'application est responsable de la gestion et de la synchronisation des E/S réseau. Elle doit appeler SSL_handle_events(3) après avoir écrit des données dans un BIO_s_dgram_pair(3) ou avoir pris une autre mesure afin que l'implémentation QUIC puisse lire de nouveaux datagrammes via un appel à BIO_recvmmsg(3) sur le BIO réseau sous-jacent. L'implémentation QUIC peut sortir des datagrammes via un appel à BIO_sendmmsg(3) et l'application est responsable de s'assurer qu'ils sont transmis.

      L'application doit appeler SSL_get_event_timeout(3) après chaque appel à SSL_handle_events(3) (ou une autre fonction d'E/S sur l'objet SSL), et s'assurer qu'un appel à SSL_handle_events(3) est effectué après le timeout spécifié (le cas échéant).
