NOM

org.freedesktop.resolve1 - L'interface D-Bus de systemd-resolved

INTRODUCTION

systemd-resolved.service(8) est un service système qui fournit la résolution de noms d'hôte et la mise en cache en utilisant DNS, LLMNR et mDNS. Il effectue également la validation DNSSEC. Cette page décrit la sémantique de résolution et l'interface D-Bus.

Cette page ne contient qu'une référence d'API. Si vous recherchez une explication plus longue sur l'utilisation de cette API, veuillez consulter Écrire des gestionnaires de configuration réseau[1] et Écrire des clients résolveurs[2].

L'OBJET MANAGER

Le service expose les interfaces suivantes sur l'objet Manager dans le bus :

Méthodes

ResolveHostname() prend un nom d'hôte et le résout en une ou plusieurs adresses IP. En tant que paramètres, elle prend l'index de l'interface réseau Linux sur laquelle exécuter la requête, ou 0 si elle peut être effectuée sur n'importe quelle interface appropriée. Le paramètre name spécifie le nom d'hôte à résoudre. Notez que si nécessaire, la conversion IDNA est appliquée à ce nom sauf s'il est résolu via LLMNR ou MulticastDNS. Le paramètre family limite les résultats à une famille d'adresses spécifique. Il peut être AF_INET, AF_INET6 ou AF_UNSPEC. Si AF_UNSPEC est spécifié (recommandé), les deux types sont récupérés, sous réserve de la configuration réseau locale (c'est-à-dire si aucune adresse IPv6 locale et routable n'est trouvée, aucune adresse IPv6 n'est récupérée ; et de même pour IPv4). Un champ flags de 64 bits peut être utilisé pour modifier le comportement de l'opération du résolveur (voir ci-dessous). La méthode renvoie un tableau d'enregistrements d'adresses. Chaque enregistrement d'adresse se compose de l'index de l'interface à laquelle l'adresse appartient, d'une famille d'adresses ainsi que d'un tableau d'octets contenant les données réelles de l'adresse IP (qui a soit 4, soit 16 éléments, selon la famille d'adresses). La famille d'adresses renvoyée sera soit AF_INET, soit AF_INET6. Pour IPv6, l'index de l'interface d'adresse renvoyée doit être utilisé pour initialiser le champ .sin6_scope_id d'une instance de structure sockaddr_in6 afin de permettre la résolution vers des adresses IP link-local. Le tableau d'adresses est suivi du nom canonique de l'hôte, qui peut être identique ou non au nom d'hôte résolu. Enfin, un champ flags de 64 bits est renvoyé, défini de manière similaire au champ flags qui a été passé, mais contenant des informations sur les données résolues (voir ci-dessous). Si le nom d'hôte passé est une adresse IPv4 ou IPv6 formatée sous forme de chaîne, elle est analysée et le résultat est renvoyé. Dans ce cas, aucune communication réseau n'est effectuée.

ResolveAddress() exécute l'opération inverse : elle prend une adresse IP et acquiert un ou plusieurs noms d'hôte pour celle-ci. En tant que paramètres, elle prend l'index de l'interface sur laquelle exécuter la requête, ou 0 si toutes les interfaces appropriées conviennent. Le paramètre family indique la famille d'adresses de l'adresse IP à résoudre. Il peut s'agir de AF_INET ou de AF_INET6. Le paramètre address prend les données brutes de l'adresse IP (sous forme de tableau de 4 ou 16 octets). Le paramètre d'entrée flags peut être utilisé pour modifier l'opération du résolveur (voir ci-dessous). La méthode renvoie un tableau d'enregistrements de noms, chacun composé d'un index d'interface et d'un nom d'hôte. Le champ de sortie flags contient des informations supplémentaires sur l'opération du résolveur (voir ci-dessous).

ResolveRecord() prend un type, une classe et un nom d'enregistrement de ressource (RR) DNS, et récupère l'ensemble complet d'enregistrements de ressources (RRset), y compris le RDATA, pour celui-ci. En tant que paramètre, elle prend l'index de l'interface réseau Linux sur laquelle exécuter la requête, ou 0 si elle peut être effectuée sur n'importe quelle interface appropriée. Le paramètre name spécifie le nom de domaine RR à rechercher (aucune conversion IDNA n'est appliquée), suivi des champs de classe et de type sur 16 bits (qui peuvent être ANY). Enfin, un champ flags peut être passé pour modifier le comportement de la recherche (voir ci-dessous). À l'achèvement, un tableau d'éléments RR est renvoyé. Chaque entrée de tableau se compose de l'index de l'interface réseau sur laquelle le RR a été découvert, des champs type et classe du RR trouvé, et d'un tableau d'octets du RR brut découvert. Les données brutes du RR commencent par le nom de domaine du RR, dans sa casse d'origine, suivis du type RR, de la classe, du TTL et du RDATA, dans le format binaire documenté dans RFC 1035[3]. Pour les RR qui prennent en charge la compression de noms dans la charge utile (tels que MX ou PTR), la compression est ex

panded dans les données retournées.

Notez qu'actuellement, le champ class doit être spécifié comme IN ou ANY. La spécification d'une autre classe renverra une erreur indiquant que les recherches de ce type ne sont pas prises en charge. De même, certains types spéciaux ne sont pas non plus pris en charge (AXFR, OPT, ...). Bien que systemd-resolved analyse et valide les enregistrements de ressources de nombreux types, il est crucial que les clients utilisant cette API comprennent que les données RR proviennent du réseau et doivent être validées minutieusement avant utilisation.

ResolveService() peut être utilisé pour résoudre un enregistrement de service DNS SRV, ainsi que les noms d'hôte qui y sont référencés, et éventuellement un enregistrement TXT DNS-SD d'accompagnement contenant des métadonnées de service supplémentaires. Le principal avantage d'utiliser cette méthode plutôt que ResolveRecord() en spécifiant le type SRV est qu'elle résoudra les RR SRV et TXT ainsi que les noms d'hôte référencés dans le SRV en une seule opération. Comme paramètres, elle prend un index d'interface réseau Linux, un nom de service, un type de service et un domaine de service. Cette méthode peut être appelée dans trois modes différents :

1.Pour résoudre un service DNS-SD, spécifiez le nom du service (par exemple, "Lennart's Files"), le type de service (par exemple, "_webdav._tcp") et le domaine à rechercher (par exemple, "local") comme trois paramètres de service. Le nom du service doit être au format UTF-8, et aucune conversion IDNA n'est appliquée à celui-ci dans ce mode (conformément aux spécifications DNS-SD). Cependant, si nécessaire, une conversion IDNA est appliquée au paramètre de domaine.
2.Pour résoudre un enregistrement SRV simple, définissez le paramètre de nom de service sur une chaîne vide et définissez correctement le type de service et le domaine. (La conversion IDNA est appliquée au domaine, si nécessaire.)
3.Alternativement, laissez vides le nom du service et le type, et spécifiez le nom de domaine complet de l'enregistrement SRV (c'est-à-dire, précédé du type de service) dans le paramètre de domaine. (Aucune conversion IDNA n'est appliquée dans ce mode.)

Le paramètre *family* de la méthode ResolveService() encode la famille d'adresses souhaitée à résoudre (utilisez AF_INET, AF_INET6 ou AF_UNSPEC). Si cela est activé (Utilisez le drapeau NO_ADDRESS pour désactiver la résolution d'adresses, voir ci-dessous). Le paramètre *flags* prend un certain nombre d'indicateurs qui peuvent être utilisés pour modifier le fonctionnement du résolveur.

À l'achèvement, ResolveService() renvoie un tableau de structures d'enregistrements SRV. Chaque élément se compose des champs priorité, poids et port ainsi que du nom d'hôte à contacter, tels qu'encodés dans l'enregistrement SRV. Immédiatement après suit un tableau des adresses de cet hôte, chaque élément se composant de l'index de l'interface, de la famille d'adresses et des données d'adresse dans un tableau d'octets. Ce tableau d'adresses est suivi du nom d'hôte canonisé. Après ce tableau de structures d'enregistrements SRV, un tableau de tableaux d'octets suit qui encode les chaînes d'enregistrements TXT, si les recherches DNS-SD sont activées. Les paramètres suivants sont le nom de service canonique, le type et le domaine. Ils peuvent être identiques ou non aux paramètres passés. Enfin, un champ *flags* est renvoyé qui contient des informations sur l'opération du résolveur effectuée.

La méthode ResetStatistics() réinitialise les différents compteurs de statistiques que systemd-resolved maintient à zéro. (Pour plus de détails, voir les propriétés des statistiques ci-dessous.)

La méthode GetLink() prend un index d'interface réseau et renvoie le chemin de l'objet vers l'objet org.freedesktop.resolve1.Link qui lui correspond.

La méthode SetLinkDNS() définit les serveurs DNS à utiliser sur une interface spécifique. Cette méthode (et celles qui suivent) peut être utilisée par les logiciels de gestion réseau pour configurer les paramètres DNS par interface. Elle prend un index d'interface réseau ainsi qu'un tableau d'enregistrements d'adresses IP de serveurs DNS. Chaque élément du tableau se compose d'une famille d'adresses (soit AF_INET, soit AF_INET6), suivie d'un tableau de 4 ou 16 octets contenant les données brutes de l'adresse. Cette méthode est un raccourci en une étape pour récupérer l'objet Link pour une interface réseau en utilisant GetLink() (voir ci-dessus) puis en appelant la méthode SetDNS() (voir ci-dessous) sur celui-ci.

SetLinkDNSEx() est similaire à SetLinkDNS(), mais permet de spécifier un port IP (au lieu du port 53 par défaut) et un nom DNS pour chaque serveur DNS. Le nom du serveur est utilisé pour l'Indication de Nom de Serveur (SNI), ce qui est utile lorsque DNS-over-TLS est utilisé. Voir *DNS=* dans resolved.conf(5).

SetLinkDefaultRoute() spécifie si le lien doit être utilisé comme route par défaut pour les requêtes de noms. Voir la description du routage de noms dans systemd-resolved.service(8) pour plus de détails.

La méthode SetLinkDomains() définit les domaines de recherche et de routage à utiliser sur une interface réseau spécifique pour les recherches DNS. Elle prend un index d'interface réseau et un tableau de domaines, chacun avec un paramètre booléen indiquant si le domaine spécifié doit être utilisé comme domaine de recherche (faux) ou simplement comme domaine de routage (vrai). Les domaines de recherche sont utilisés pour qualifier les noms à un seul label en noms de domaine complets (FQDN) lors de la recherche d'hôtes, ainsi que pour prendre des décisions de routage sur quelle interface envoyer les requêtes se terminant par le domaine. Les domaines de routage sont uniquement utilisés pour les décisions de routage et ne sont pas utilisés pour la qualification de noms à un seul label. Passez les domaines de recherche dans l'ordre où ils doivent être utilisés.

La méthode SetLinkLLMNR() active ou désactive la prise en charge de LLMNR sur une interface réseau spécifique. Elle prend un index d'interface réseau ainsi qu'une chaîne qui peut être vide ou l'une des valeurs "yes", "no" ou "resolve". Si elle est vide, le paramètre LLMNR par défaut au niveau du système est utilisé. Si "yes", LLMNR est utilisé pour la résolution des noms à un seul label et le nom d'hôte local est enregistré sur tous les réseaux locaux pour la résolution LLMNR par les pairs. Si "no", LLMNR est complètement désactivé sur cette interface. Si "resolve", LLMNR est uniquement activé pour la résolution des noms, mais le nom d'hôte local n'est pas enregistré pour être utilisé par d'autres pairs.

De même, la méthode SetLinkMulticastDNS() active ou désactive la prise en charge de MulticastDNS sur une interface spécifique. Elle prend les mêmes paramètres que SetLinkLLMNR() décrits ci-dessus.

La méthode SetLinkDNSSEC() active ou désactive la validation DNSSEC sur une interface réseau spécifique. Elle prend un index d'interface réseau ainsi qu'une chaîne qui peut être vide ou l'une des valeurs "yes", "no", ou "allow-downgrade". Si elle est vide, le paramètre DNSSEC par défaut au niveau du système est utilisé. Si "yes", une validation DNSSEC complète est effectuée pour toutes les recherches. Si le serveur DNS sélectionné ne prend pas en charge DNSSEC, les recherches échoueront si ce mode est utilisé. Si "no", la validation DNSSEC est complètement désactivée. Si "allow-downgrade", la validation DNSSEC est activée, mais désactivée automatiquement si le serveur sélectionné ne la prend pas en charge (exposant ainsi le comportement aux attaques par dégradation). Notez que DNSSEC s'applique uniquement au DNS traditionnel, et non à LLMNR ou MulticastDNS.

La méthode SetLinkDNSSECNegativeTrustAnchors() peut être utilisée pour configurer des Ancrages de Confiance Négatifs DNSSEC (NTA) pour une interface réseau spécifique. Elle prend un index d'interface réseau et une liste de domaines comme arguments.

La méthode SetLinkDNSOverTLS() active ou désactive DNS-over-TLS. Voir *DNSOverTLS=* dans systemd-resolved.service(8) pour plus de détails.

Les logiciels de gestion réseau s'intégrant à systemd-resolved doivent appeler SetLinkDNS() ou SetLinkDNSEx(), SetLinkDefaultRoute(), SetLinkDomains() et d'autres après l'apparition de l'interface dans le noyau (et donc après l'attribution d'un index d'interface réseau), mais avant que l'interface réseau ne soit activée (IFF_UP défini) afin que tous les paramètres prennent effet pendant toute la durée de vie de l'interface réseau. Il est cependant possible de modifier les paramètres lorsque l'interface est active. Utilisez RevertLink() (décrit ci-dessous) pour réinitialiser tous les paramètres par interface.

La méthode RevertLink() peut être utilisée pour rétablir tous les paramètres par lien décrits ci-dessus aux valeurs par défaut.

La méthode FlushCaches() vide tous les caches d'enregistrements de ressources maintenus par le résolveur, et garantit que toutes les recherches subséquentes redemandent leurs réponses à leurs sources.

La méthode ResetServerFeatures() vide toute information de fonctionnalité apprise sur les serveurs DNS distants. Cela garantit que les recherches subséquentes seront initialement tentées au niveau de fonctionnalité de protocole DNS le plus élevé à nouveau, nécessitant potentiellement un cycle de dégradation (potentiellement lent) pour reconnaître à nouveau le niveau de fonctionnalité supporté.

La méthode RegisterService() peut être utilisée pour enregistrer un service DNS-SD sur l'hôte. Cette fonctionnalité est étroitement liée à la fonctionnalité fournie par les fichiers systemd.dnssd(5). Elle prend une chaîne d'identifiant de serveur comme premier paramètre (ceci est juste un identifiant local, et doit être choisi de manière à ne pas entrer en collision avec le nom de base des fichiers *.dnssd ni avec les noms choisis par d'autres clients IPC). Elle prend également une chaîne de modèle de nom pour le nom du service DNS-SD visible sur le réseau. Cette chaîne est soumise à une expansion de spécificateur, comme documenté pour le paramètre *Name=* dans les fichiers *.dnssd. Elle prend également une chaîne de type de service contenant le type de service DNS-SD, ainsi qu'un port IP, une paire priorité/poids pour l'enregistrement SRV DNS-SD. Enfin, elle prend un tableau de données d'enregistrements TXT. Elle renvoie un chemin d'objet qui peut être utilisé comme handle pour le service enregistré.

La méthode UnregisterService() annule l'effet de RegisterService() et supprime un service DNS-SD précédemment créé via IPC.

La méthode GetDelegate() renvoie le chemin de l'objet D-Bus pour l'ID de délégation DNS spécifié.

La méthode ListDelegates() renvoie une liste des ID et des chemins d'objet D-Bus des délégations DNS actuellement configurées.

Le paramètre Flags

Les quatre méthodes ci-dessus acceptent et renvoient une valeur de flags de 64 bits. Dans la plupart des cas, passer 0 est suffisant et recommandé. Cependant, les indicateurs suivants sont définis pour modifier la recherche :

/* Entrée/Sortie : Protocole/portée */
#define SD_RESOLVED_DNS                (UINT64_C(1) <<  0)
#define SD_RESOLVED_LLMNR_IPV4         (UINT64_C(1) <<  1)
#define SD_RESOLVED_LLMNR_IPV6         (UINT64_C(1) <<  2)
#define SD_RESOLVED_MDNS_IPV4          (UINT64_C(1) <<  3)
#define SD_RESOLVED_MDNS_IPV6          (UINT64_C(1) <<  4)
/* Entrée : Restrictions */
#define SD_RESOLVED_NO_CNAME           (UINT64_C(1) <<  5)
#define SD_RESOLVED_NO_TXT             (UINT64_C(1) <<  6)
#define SD_RESOLVED_NO_ADDRESS         (UINT64_C(1) <<  7)
#define SD_RESOLVED_NO_SEARCH          (UINT64_C(1) <<  8)
#define SD_RESOLVED_NO_VALIDATE        (UINT64_C(1) << 10)
#define SD_RESOLVED_NO_SYNTHESIZE      (UINT64_C(1) << 11)
#define SD_RESOLVED_NO_CACHE           (UINT64_C(1) << 12)
#d
#define SD_RESOLVED_NO_ZONE (UINT64_C(1) << 13) #define SD_RESOLVED_NO_TRUST_ANCHOR (UINT64_C(1) << 14) #define SD_RESOLVED_NO_NETWORK (UINT64_C(1) << 15) #define SD_RESOLVED_NO_STALE (UINT64_C(1) << 24) #define SD_RESOLVED_RELAX_SINGLE_LABEL (UINT64_C(1) << 25) /* Sortie : Sécurité */ #define SD_RESOLVED_AUTHENTICATED (UINT64_C(1) << 9) #define SD_RESOLVED_CONFIDENTIAL (UINT64_C(1) << 18) /* Sortie : Origine */ #define SD_RESOLVED_SYNTHETIC (UINT64_C(1) << 19) #define SD_RESOLVED_FROM_CACHE (UINT64_C(1) << 20) #define SD_RESOLVED_FROM_ZONE (UINT64_C(1) << 21) #define SD_RESOLVED_FROM_TRUST_ANCHOR (UINT64_C(1) << 22) #define SD_RESOLVED_FROM_NETWORK (UINT64_C(1) << 23)

En entrée, les cinq premiers indicateurs contrôlent les protocoles à utiliser pour la recherche. Ils se réfèrent respectivement au DNS unicast classique, au LLMNR via IPv4/UDP et IPv6/UDP, ainsi qu'au MulticastDNS via IPv4/UDP et IPv6/UDP. Si ces cinq bits sont tous désactivés en entrée (ce qui est fortement recommandé), la recherche sera effectuée via tous les protocoles appropriés pour la recherche spécifique. Notez que ces indicateurs fonctionnent uniquement comme un filtre, mais ne peuvent pas forcer une recherche à être effectuée via un protocole. Spécifiquement, systemd-resolved ne dirigera les recherches au sein du TLD .local que vers MulticastDNS (plus certains domaines de recherche d'adresses inverses), et les noms à étiquette unique vers LLMNR (plus certains domaines de recherche d'adresses inverses). Il ne dirigera aucun de ceux-ci vers des serveurs DNS unicast. De plus, il n'utilisera LLMNR et Multicast DNS que sur les interfaces appropriées pour le multicast.

En sortie, ces cinq indicateurs indiquent quel protocole a été utilisé pour exécuter l'opération, et donc où les données ont été trouvées.

Les principaux cas d'utilisation pour ces cinq indicateurs sont les recherches de suivi basées sur des données DNS récupérées précédemment. Dans ce cas, il est souvent judicieux de limiter la recherche de suivi au protocole qui a été utilisé pour découvrir le premier résultat DNS.

L'indicateur NO_CNAME contrôle si les enregistrements de ressources CNAME/DNAME doivent être suivis pendant la recherche. Cet indicateur n'est disponible qu'en entrée, aucune des fonctions ne le retournera en sortie. Si un enregistrement CNAME/DNAME est découvert lors de la résolution d'un nom d'hôte, une erreur est renvoyée à la place. Par défaut, lorsque l'indicateur est désactivé, les enregistrements CNAME/DNAME sont suivis.

Les indicateurs NO_TXT et NO_ADDRESS n'influencent que le fonctionnement de la méthode ResolveService(). Ils ne sont définis que pour l'entrée, pas pour la sortie. Si NO_TXT est défini, la recherche de l'enregistrement TXT DNS-SD n'est pas effectuée dans la même opération. Si NO_ADDRESS est défini, les noms d'hôtes découverts ne sont pas implicitement traduits en leurs adresses.

L'indicateur NO_SEARCH désactive la logique des domaines de recherche. Il n'est défini qu'en entrée dans ResolveHostname(). Lorsqu'il est spécifié, les noms d'hôtes à étiquette unique ne sont pas qualifiés en utilisant les domaines de recherche définis, s'il y en a de configurés. Notez que ResolveRecord() ne qualifiera jamais les noms de domaine à étiquette unique en utilisant les domaines de recherche. Notez également que les noms d'hôtes à plusieurs étiquettes ne sont jamais soumis à l'expansion de la liste de recherche.

NO_VALIDATE peut être défini pour désactiver la validation via DNSSEC même si elle serait normalement utilisée.

Les six indicateurs suivants permettent de désactiver certaines sources pendant la résolution. NO_SYNTHESIZE désactive les enregistrements synthétiques, par exemple le nom d'hôte local, voir la section ENREGISTREMENTS SYNTHÉTIQUES dans systemd-resolved.service(8) pour plus d'informations. NO_CACHE désactive l'utilisation du cache des enregistrements précédemment résolus. NO_ZONE désactive les réponses utilisant les enregistrements de ressources LLMNR/mDNS publics enregistrés localement. NO_TRUST_ANCHOR désactive les réponses utilisant les ancres de confiance configurées localement. NO_NETWORK exige que toutes les réponses soient fournies sans utiliser le réseau, c'est-à-dire soit à partir de sources locales soit du cache. L'indicateur NO_STALE peut être défini pour désactiver la réponse aux requêtes avec des enregistrements obsolètes.

Le bit AUTHENTICATED n'est défini que dans les indicateurs de sortie des quatre fonctions. S'il est défini, les données renvoyées ont été entièrement authentifiées. Spécifiquement, ce bit est défini pour toutes les données protégées par DNSSEC pour lesquelles une chaîne de confiance complète peut être établie vers une ancre de domaine de confiance. Il est également défini pour les données synthétisées localement, telles que "localhost" ou les données de /etc/hosts. De plus, il est défini pour tous les enregistrements LLMNR ou mDNS qui proviennent de l'hôte local. Les applications qui nécessitent des données d'enregistrement authentifiées pour fonctionner doivent vérifier cet indicateur avant de faire confiance aux données. Notez que systemd-resolved ne renverra jamais de données invalidées, donc cet indicateur permet simplement de discerner les cas où les données sont connues pour être fiables, ou lorsqu'il y a une preuve que les données sont "légitimement" non authentifiées (ce qui inclut les cas où le protocole ou le serveur sous-jacent ne prend pas en charge l'authentification des données).

CONFIDENTIAL signifie que la requête a été résolue via des canaux cryptés ou n'a jamais quitté ce système.

Les cinq indicateurs de bits suivants sont utilisés en sortie et fournissent des informations sur l'origine de la réponse. FROM_SYNTHETIC signifie que la requête a été (au moins partiellement) synthétisée localement. FROM_CACHE signifie que la requête a été répondue (au moins partiellement) en utilisant le cache. FROM_ZONE signifie que la requête a été répondue (au moins partiellement) sur la base d'enregistrements publics enregistrés localement. FROM_TRUST_ANCHOR signifie que la requête a été répondue (au moins partiellement) en utilisant les ancres de confiance locales. FROM_NETWORK signifie que la requête a été répondue (au moins partiellement) en utilisant le réseau.

Propriétés

Les propriétés LLMNR et MulticastDNS indiquent si LLMNR et MulticastDNS sont activés (globalement). Chacune peut prendre l'une des valeurs "yes", "no" et "resolve". Voir SetLinkLLMNR() et SetLinkMulticastDNS() ci-dessus.

LLMNRHostname contient le nom d'hôte actuellement exposé sur le réseau via LLMNR. Il suit généralement le nom d'hôte du système tel qu'il peut être interrogé via gethostname(3), mais peut différer si un conflit est détecté sur le réseau.

DNS et DNSEx contiennent des tableaux de tous les serveurs DNS actuellement utilisés par systemd-resolved. DNS contient des informations similaires aux données des serveurs DNS dans /run/systemd/resolve/resolv.conf. Chaque structure du tableau se compose d'un index d'interface réseau numérique, d'une famille d'adresses et d'un tableau d'octets contenant l'adresse du serveur DNS (soit 4 octets pour IPv4, soit 16 octets pour IPv6). DNSEx est similaire, mais contient en outre le port IP et le nom du serveur (utilisé pour l'indication du nom du serveur, SNI). Les deux tableaux contiennent les serveurs DNS configurés globalement, y compris ceux éventuellement lus à partir d'un /etc/resolv.conf étranger ou du paramètre DNS= dans /etc/systemd/resolved.conf, ainsi que les informations de serveur DNS par interface récupérées de systemd-networkd(8), ou configurées par un logiciel externe via SetLinkDNS() ou SetLinkDNSEx() (voir ci-dessus). L'index de l'interface réseau sera 0 pour les services configurés globalement et non nul pour les serveurs par lien.

FallbackDNS et FallbackDNSEx contiennent des tableaux de tous les serveurs DNS configurés comme serveurs de secours, le cas échéant, dans le même format que DNS et DNSEx décrits ci-dessus. Voir la description de FallbackDNS= dans resolved.conf(5) pour la description des cas où ces serveurs sont utilisés.

CurrentDNSServer et CurrentDNSServerEx spécifient le serveur actuellement utilisé pour la résolution des requêtes, dans le même format qu'une seule entrée dans les tableaux DNS et DNSEx décrits ci-dessus.

De même, la propriété Domains contient un tableau de tous les domaines de recherche et de routage actuellement utilisés par systemd-resolved. Chaque entrée se compose d'un index d'interface réseau (à nouveau, 0 encode les entrées globales), du nom de domaine réel et de si l'entrée est utilisée uniquement pour le routage (vrai) ou pour le routage et la recherche (faux).

La propriété TransactionStatistics contient des informations sur le nombre de transactions traitées par systemd-resolved. Elle contient une paire de compteurs non signés de 64 bits, le premier contenant le nombre de transactions actuellement en cours, le second le nombre total de transactions que systemd-resolved traite ou a traitées. La dernière valeur peut être réinitialisée en utilisant la méthode ResetStatistics() décrite ci-dessus. Notez que le nombre de transactions ne correspond pas directement au nombre d'appels de méthodes de bus du résolveur émis. Bien que les recherches simples ne nécessitent généralement qu'une seule transaction, les recherches plus complexes peuvent en résulter davantage, par exemple lorsque des CNAME ou DNSSEC sont en cours d'utilisation.

La propriété CacheStatistics contient des informations sur les opérations de cache exécutées jusqu'à présent. Elle expose trois compteurs de 64 bits : le premier étant le nombre total d'entrées de cache actuelles (positives et négatives), le second le nombre de succès de cache (hits), et le troisième le nombre de misses de cache. Les derniers compteurs peuvent être réinitialisés en utilisant ResetStatistics() (voir ci-dessus).

La propriété DNSSEC spécifie l'état actuel de la validation DNSSEC. Elle prend l'une des valeurs "yes" (la validation est appliquée), "no" (aucune validation n'est effectuée), "allow-downgrade" (la validation est effectuée si le serveur DNS actuel la prend en charge). Voir la description de DNSSEC= dans resolved.conf(5).

La propriété DNSSECStatistics contient des informations sur les validations DNSSEC exécutées jusqu'à présent. Elle contient quatre compteurs de 64 bits : le nombre de validations DNSSEC sécurisées, non sécurisées, bogus et indéterminées jusqu'à présent. Les compteurs sont incrémentés pour chaque jeu d'enregistrements validé, et chaque preuve de non-existence. Le compteur sécurisé est incrémenté pour chaque opération qui a vérifié avec succès une réponse signée, le compteur non sécurisé est incrémenté pour chaque opération qui a vérifié avec succès qu'une réponse non signée est légitimement non signée. Le compteur bogus est incrémenté pour chaque opération où la validation n'a pas abouti et où les données ont probablement été altérées. Enfin, le compteur indéterminé est incrémenté pour chaque opération qui ne s'est pas terminée parce que les clés nécessaires n'ont pas pu être acquises ou que les algorithmes cryptographiques étaient inconnus.

La propriété booléenne DNSSECSupported indique si DNSSEC est activé et si les serveurs DNS sélectionnés le prennent en charge. Elle combine les informations sur les paramètres DNS globaux et par lien (voir ci-dessous), et ne renvoie true que si DNSSEC est activé et pris en charge sur chaque interface pour laquelle le DNS est configuré et pour les paramètres globaux s'il y en a. Notez que systemd-resolved suppose que DNSSEC est pris en charge par les serveurs DNS jusqu'à ce qu'il vérifie que ce n'est pas le cas. Ainsi, la valeur signalée peut initialement être vraie, jusqu'à ce que les premières transactions soient exécutées.

La propriété booléenne DNSOverTLS indique si DNS-over-TLS est activé.

La propriété ResolvConfMode expose la manière dont /etc/resolv.conf est géré sur l'hôte. Actuellement, les valeurs "uplink", "stub", "static" (ces trois correspondent aux trois fichiers différents fournis par systemd-resolved.service), "foreign" (le fi

le est géré par l'administrateur ou un autre service, systemd-resolved.service le consomme juste), "manquant" (/etc/resolv.conf est manquant).

La propriété DNSStubListener indique si l'écouteur stub sur le port 53 est activé. Les valeurs possibles sont "yes" (activé), "no" (désactivé), "udp" (seul l'écouteur UDP est activé) et "tcp" (seul l'écouteur TCP est activé).

La propriété DNSSECNegativeTrustAnchors contient une liste d'ancres de confiance négatives DNSSEC reconnues et une liste de domaines.

Pour chaque interface réseau Linux, un objet "Link" est créé, qui expose la configuration et l'état DNS par lien. Utilisez GetLink() sur l'interface Manager pour récupérer le chemin de l'objet pour un objet de lien étant donné l'index de l'interface réseau (voir ci-dessus).

Méthodes

Les différentes méthodes exposées par l'interface Link sont équivalentes à leurs homologues portant le même nom sur l'interface Manager. Par exemple, SetDNS() sur l'objet Link correspond à SetLinkDNS() sur l'objet Manager, la principale différence étant que ce dernier attend un index d'interface à spécifier. L'invocation des méthodes sur l'interface Manager présente l'avantage de réduire les allers-retours, car il n'est pas nécessaire de demander d'abord le chemin de l'objet Link via GetLink() avant d'invoquer les méthodes. La même relation s'applique à SetDNSEx(), SetDomains(), SetDefaultRoute(), SetLLMNR(), SetMulticastDNS(), SetDNSOverTLS(), SetDNSSEC(), SetDNSSECNegativeTrustAnchors() et Revert(). Pour plus de détails sur ces méthodes, voir la documentation du Manager ci-dessus.

Propriétés

ScopesMask définit quels scopes de résolution sont actuellement actifs sur cette interface. Ce champ entier non signé de 64 bits est un masque de bits composé d'un sous-ensemble des bits du paramètre flags décrit ci-dessus. Spécifiquement, il peut avoir les bits DNS, LLMNR et MDNS (ce dernier en saveurs IPv4 et IPv6) définis. Chaque bit individuel est défini lorsque le protocole s'applique à une interface spécifique et qu'il est activé pour elle. Il est désactivé sinon. Spécifiquement, une interface capable de multicast dans l'état "UP" avec une adresse IP convient pour LLMNR ou MulticastDNS, et toute interface qui est UP et possède une adresse IP convient pour DNS. Notez la relation des bits exposés ici avec les propriétés LLMNR et MulticastDNS également exposées sur l'interface Link. Ces dernières exposent ce qui est *configuré* pour être utilisé sur l'interface, les premières exposent ce qui est réellement utilisé sur l'interface, en tenant compte des capacités de l'interface.

DNSSECSupported expose un champ booléen qui indique si DNSSEC est actuellement configuré et utilisé sur l'interface. Notez que si DNSSEC est activé sur une interface, il est supposé disponible jusqu'à ce qu'il soit détecté que le serveur configuré ne le prend pas réellement en charge. Ainsi, cette propriété peut initialement indiquer que DNSSEC est pris en charge sur une interface.

DefaultRoute expose un champ booléen qui indique si l'interface sera utilisée comme route par défaut pour les requêtes de noms. Voir SetLinkDefaultRoute() ci-dessus.

Les autres propriétés reflètent l'état des différents paramètres de configuration du lien qui peuvent être définis avec les différentes appels de méthodes tels que SetDNS() ou SetLLMNR().

$ resolvectl dns eth0 8.8.8.8 1.1.1.1

$ resolvectl domain eth0 example.com *.example.com

To set the hostname:

$ hostnamectl set-hostname my-host
