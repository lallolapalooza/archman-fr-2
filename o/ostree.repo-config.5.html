NOM

ostree.repo-config - Configuration du dépôt OSTree

DESCRIPTION

Le fichier de configuration dans un dépôt OSTree est un « keyfile » au format XDG Desktop Entry Specification[1]. Il contient plusieurs indicateurs globaux, ainsi que zéro ou plusieurs entrées distantes qui décrivent comment accéder aux dépôts distants.

Voir ostree.repo(5) pour plus d'informations sur les dépôts OSTree.

OPTIONS DE LA SECTION [CORE]

Options globales du dépôt. Les entrées suivantes sont définies :

mode

L'un des modes suivants : bare, bare-user, bare-user-only, ou archive-z2 (notez que archive est utilisé partout ailleurs).

repo_version

Actuellement, cette valeur doit être définie sur 1.

auto-update-summary

Valeur booléenne contrôlant si le fichier summary doit être automatiquement mis à jour après l'ajout, la suppression ou la mise à jour d'une référence. D'autres modifications qui peuvent rendre un fichier summary obsolète (comme les deltas statiques ou les identifiants de collection) ne déclenchent pas actuellement de mise à jour automatique.

commit-update-summary

Cette option est obsolète. Utilisez auto-update-summary à la place, dont cette option est maintenant un alias.

fsync

Valeur booléenne contrôlant si les fichiers doivent être assurés d'être sur un stockage stable lors de l'exécution d'opérations telles que les commits, les pulls et les checkouts. La valeur par défaut est true.

Si vous désactivez fsync, OSTree ne sera plus robuste face aux pannes de noyau ou aux pertes de courant.

Vous pourriez choisir de désactiver cela pour des dépôts de développement locaux, en supposant qu'ils peuvent être recréés à partir des sources. De même, vous pourriez désactiver cela pour un miroir où vous pourriez ré-extraire les données.

Pour le dépôt système, vous pourriez choisir de désactiver fsync si vous disposez d'onduleurs et d'un noyau bien testé.

per-object-fsync

Par défaut, OSTree regroupe les appels fsync() après avoir écrit tout le contenu ; cependant, cela peut provoquer des pics de latence pour d'autres processus qui invoquent également fsync(). Activez ce booléen pour réduire les pics de latence potentiels, au détriment d'une mise à jour plus lente d'OSTree. Vous voudrez très probablement activer cela par défaut pour les mises à jour du système d'exploitation en arrière-plan.

min-free-space-percent

Valeur entière en pourcentage (0-99) qui spécifie un pourcentage minimum d'espace total (en blocs) dans le système de fichiers sous-jacent à laisser libre. La valeur par défaut est 3, qui est appliquée lorsque ni cette option ni min-free-space-size ne sont définies.

Si min-free-space-size est définie sur une valeur non nulle, min-free-space-percent est ignorée. Notez que min-free-space-percent n'est pas appliqué aux objets de métadonnées. On suppose que les objets de métadonnées sont relativement petits par rapport aux objets de contenu et sont donc maintenus en dehors du champ d'application de cette option.

min-free-space-size

Valeur (en Mo, Go ou To de puissances de 2) qui spécifie un espace minimum à laisser libre dans le système de fichiers sous-jacent. Exemples de valeurs acceptables : 500 Mo (524 288 000 octets), 1 Go (1 073 741 824 octets), 1 To (1 099 511 627 776 octets).

Si cette option est définie sur une valeur non nulle, et que min-free-space-percent est également définie, cette option a la priorité. Notez que min-free-space-size n'est pas appliqué aux objets de métadonnées. On suppose que les objets de métadonnées sont relativement petits par rapport aux objets de contenu et sont donc maintenus en dehors du champ d'application de cette option.

add-remotes-config-dir

Valeur booléenne contrôlant si les nouvelles télécommandes seront ajoutées dans le répertoire de configuration des télécommandes. Par défaut, la valeur est true pour les dépôts ostree système. Lorsque c'est false, les télécommandes seront ajoutées dans le fichier de configuration du dépôt.

Ceci ne s'applique qu'aux dépôts qui utilisent un répertoire de configuration des télécommandes, comme les dépôts ostree système, qui utilisent /etc/ostree/remotes.d. Les dépôts non système n'utilisent pas de répertoire de configuration des télécommandes à moins qu'un ne soit spécifié lors de l'ouverture du dépôt.

payload-link-threshold

Une valeur entière qui spécifie une taille de fichier minimale pour créer un lien de charge utile. Par défaut, elle est désactivée.

collection-id

Un nom de domaine DNS inversé sous votre contrôle, qui permet la distribution peer-to-peer des références dans ce dépôt. Voir la section --collection-id dans ostree-init(1)

locking

Valeur booléenne contrôlant si OSTree effectue ou non le verrouillage interne du dépôt. Cela utilise des verrous de fichiers et est donc destiné à l'exclusion multiprocesse (par exemple, Flatpak et OSTree écrivant séparément dans le même dépôt). Ceci est activé par défaut depuis 2018.5.

lock-timeout-secs

Valeur entière contrôlant le nombre de secondes pendant lesquelles on bloque en tentant d'acquérir un verrou (voir ci-dessus). Une valeur de -1 signifie bloquer indéfiniment. La valeur par défaut est 300. Ce délai d'attente est maintenant considéré comme une erreur ; car il est susceptible de provoquer des instabilités. Il est recommandé de le régler sur -1, et d'avoir des délais d'attente à un niveau d'application supérieur si désiré.

default-repo-finders

Liste de références séparées par des points-virgules des localisateurs (sources de références) à utiliser lors du pull. Cela peut être utilisé pour désactiver le pull depuis des systèmes de fichiers montés, des pairs sur le réseau local, ou Internet. Cependant, notez que cela ne s'applique que lorsqu'un ensemble de localisateurs n'est pas explicitement spécifié, soit par un consommateur de l'API libostree, soit en ligne de commande. Les valeurs possibles : config, lan, et mount (ou toute combinaison de ceux-ci). Si non défini, cela vaut par défaut config;mount; (car le localisateur LAN est coûteux).

no-deltas-in-summary

Valeur booléenne contrôlant si OSTree doit omettre d'inclure un index des deltas disponibles dans le fichier summary. Par défaut, la valeur est false.

Depuis 2020.7, OSTree peut utiliser des index de deltas en dehors du fichier summary, rendant le fichier summary plus petit (surtout pour les gros dépôts). Cependant, par défaut, nous créons toujours l'index dans le fichier summary pour que les anciens clients fonctionnent. Si vous savez que tous les clients seront en version 2020.7 ou ultérieure, vous pouvez activer cela pour économiser de la bande passante.

OPTIONS DE LA SECTION [NOM DE LA TÉLÉCOMMANDE"]

Décrit l'emplacement d'un dépôt distant.

url

Doit être présent ; déclare l'URL pour accéder aux métadonnées et au contenu pour le distant. Voir aussi contenturl. Les schémas supportés sont documentés ci-dessous.

contenturl

Déclare l'URL pour accéder au contenu (fichiers, parties de deltas statiques). Lorsqu'elle est spécifiée, url est utilisée uniquement pour les métadonnées : summary, "superblocks" de deltas statiques.

branches

Une liste de chaînes de caractères. Représente les branches configurées par défaut à extraire du distant lorsque aucune branche spécifique n'est demandée pendant une opération de pull.

proxy

Une valeur de chaîne de caractères, si elle est fournie, doit être une URL pour un proxy HTTP à utiliser pour l'accès à ce dépôt.

gpg-verify

Une valeur booléenne, par défaut true. Contrôle si OSTree exigera ou non que les commits soient signés par une clé GPG connue. Pour plus d'informations, voir le manuel ostree(1) sous GPG.

gpg-verify-summary

Une valeur booléenne, par défaut false. Contrôle si OSTree vérifiera ou non si le résumé est signé par une clé GPG connue. Pour plus d'informations, voir le manuel ostree(1) sous GPG.

tls-permissive

Une valeur booléenne, par défaut false. Par défaut, les certificats TLS du serveur seront vérifiés par rapport au magasin de certificats système. Si cette variable est définie, tout certificat sera accepté.

tls-client-cert-path

Chemin vers le fichier du certificat côté client, à présenter lors de la réalisation de requêtes à ce dépôt.

tls-client-key-path

Chemin vers le fichier contenant la clé du certificat côté client, à présenter lors de la réalisation de requêtes à ce dépôt.

tls-ca-path

Chemin vers le fichier contenant des ancres de confiance au lieu de la base de données CA système.

http2

Une valeur booléenne, par défaut true. Par défaut, libostree utilisera HTTP2 ; la définir sur false le désactivera. Peut être utile pour contourner des serveurs défectueux.

u

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

ostree.repo-config(5) — OSTree documentation

NAME

ostree.repo-config - Configuration file format for OSTree repositories

DESCRIPTION

The configuration file for an OSTree repository is typically located at <repo>/config. This file is a UTF-8 encoded text file containing sections, where each section is introduced by a heading in square brackets, e.g. [core]. Sections contain key-value pairs, where the key and value are separated by an equals sign (=). Lines beginning with # are comments.

The following sections are recognized:

[CORE] SECTION OPTIONS

Options for the core repository behavior. The following entries are defined:

repo-directory

A string, specifying the root directory of the OSTree repository. This is typically set automatically by OSTree itself.

core.trust-content

A boolean value, defaulting to false. If true, OSTree will not perform checksum validation on objects read from the repository. This is useful for debugging and potentially for performance in trusted environments, but dangerous otherwise.

core.check-local-metadatas

A boolean value, defaulting to true. If false, OSTree will skip checking the integrity of local metadata files, which can speed up operations.

core.bare-repo

A boolean value, defaulting to false. If true, the repository will be considered a "bare" repository, meaning it will not contain a working tree. This is typically used for server-side repositories.

core.check-signatures

A boolean value, defaulting to true. If false, signature checking will be disabled.

core.protected-refs

A list of ref globs (e.g. refs/heads/*). If set, any attempt to push a ref matching these globs will fail unless the push comes from a trusted source (e.g. a local repository or a specific remote). This is intended to prevent accidental or malicious modification of critical refs.

core.signed-commits

A boolean value, defaulting to false. If true, OSTree will require all commits to be signed.

core.commit-signature-type

Specifies the type of signature to use for commits. Can be gpg or ssh. Defaults to gpg.

core.commit-gpg-key-path

Path to the GPG key to use for signing commits.

core.commit-ssh-key-path

Path to the SSH key to use for signing commits.

[REMOTE NAME"] SECTION OPTIONS"

This section defines configuration options for a specific remote repository. The name of the section should be the name of the remote. The following entries are defined:

url

The base URL of the remote repository.

contenturl

An alternative URL for fetching repository content. This can be used to serve content from a different location than metadata. See REPOSITORY URL/CONTENTURL below.

mirrorlist

A URL that provides a list of mirrors for the repository. See REPOSITORY URL/CONTENTURL below.

fetchgroup

A list of refs that should be fetched from this remote. If not specified, all refs are fetched.

pushurl

The base URL to use for pushing to the remote repository. If not specified, the value of url is used.

gpgkey

The URL or path to the GPG public key used to verify objects from this remote. See PER-REMOTE GPG KEYRINGS AND VERIFICATION below.

peer-gkey

The URL or path to a GPG key for establishing a peer connection.

tls-ca-path

The path to a CA certificate file to use for verifying the TLS certificate of the remote server.

tls-client-cert-path

The path to a client certificate file to use for TLS client authentication.

tls-client-key-path

The path to a client key file to use for TLS client authentication.

timeout

The connection timeout in seconds for operations against this remote.

max-connections

The maximum number of concurrent connections to use when fetching from this remote.

nconfigured-state

If set, pulls from this remote will fail with the configured text. This is intended for OS vendors which have a subscription process to access content.

custom-backend

If set, pulls from this remote via libostree will fail with an error that mentions the value. It is recommended to make this a software identifier token (e.g. "examplecorp-fetcher"), not freeform text ("ExampleCorp Fetcher"). This is intended to be used by higher level software that wants to fetch ostree commits via some other mechanism, while still reusing the core libostree infrastructure around e.g. signatures.

[SYSROOT] SECTION OPTIONS

Options for the sysroot, which contains the OSTree repository, deployments, and stateroots. The following entries are defined:

readonly

A boolean value. If this is set to true, then the /sysroot mount point is mounted read-only. This is configured a legacy repository configuration and the equivalent option in ostree/prepare-root.conf should be used instead - see ostree-prepare-root(1).

bootloader

Configure the bootloader that OSTree uses when deploying the sysroot. This may take the values bootloader=none, bootloader=auto, bootloader=grub2, bootloader=syslinux, bootloader=uboot or bootloader=zipl. Default is auto.

If none, then OSTree will generate only BLS (Boot Loader Specification) fragments in sysroot/boot/loader/entries/ for the deployment.

If auto, then in addition to generating BLS fragments, OSTree will dynamically check for the existence of grub2, uboot, and syslinux bootloaders. If one of the bootloaders is found, then OSTree will generate a config for the bootloader found. For example, grub2-mkconfig is run for the grub2 case.

A specific bootloader type may also be explicitly requested by choosing grub2, syslinux, uboot or zipl.

boot-counting-tries

Integer value controlling the number of maximum boot attempts. The boot counting data is stored in the name of the boot loader entry. A boot loader entry file name may contain a plus (+) followed by a number. This may optionally be followed by a minus (-) followed by a second number. The dot (.) and file name suffix (conf or efi) must immediately follow. More details in the The Boot Loader Specification[2]

bls-append-except-default

A semicolon separated string list of key-value pairs. For example: bls-append-except-default=key1=value1;key2=value2. These key-value pairs will be injected into the generated BLS fragments of the non-default deployments. In other words, the BLS fragment of the default deployment will be unaffected by bls-append-except-default.

bootprefix

A boolean value; defaults to false. If set to true, the bootloader entries generated will include /boot as a prefix. This will likely be turned on by default in the future.

[EX-INTEGRITY] SECTION OPTIONS

The "ex-" prefix here signifies experimental options. The ex-integrity section contains options related to system integrity. Information about experimental options is canonically found in upstream tracking issues.

/ETC/OSTREE/REMOTES.D

In addition to the /ostree/repo/config file, remotes may also be specified in /etc/ostree/remotes.d. The remote configuration file must end in .conf; files whose name does not end in .conf will be ignored.

REPOSITORY URL/CONTENTURL

Originally, OSTree had just a url option for remotes. Since then, the contenturl option was introduced. Both of these support file, http, and https schemes.

Additionally, both of these can be prefixed with the string mirrorlist=, which instructs the client that the target url is a "mirrorlist" format, which is a plain text file of newline-separated URLs. Earlier URLs will be given precedence.

Note that currently, the tls-ca-path and tls-client-cert-path options apply to every HTTP request, even when contenturl and/or mirrorlist are in use. This may change in the future to only apply to metadata (i.e. url, not contenturl) fetches.

PER-REMOTE GPG KEYRINGS AND VERIFICATION

OSTree supports a per-remote GPG keyring, as well as a gpgkeypath option. For more information see ostree(1). in the section GPG verification.

PER-REMOTE HTTP COOKIES

Some content providers may want to control access to remote repositories via HTTP cookies. The ostree remote add-cookie and ostree remote delete-cookie commands will update a per-remote lookaside cookie jar, named $remotename.cookies.txt.
