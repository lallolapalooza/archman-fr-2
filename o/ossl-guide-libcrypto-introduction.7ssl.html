INTRODUCTION

La bibliothèque cryptographique OpenSSL ("libcrypto") permet d'accéder à un large éventail d'algorithmes cryptographiques utilisés dans divers standards Internet. Les services fournis par cette bibliothèque sont utilisés par les implémentations OpenSSL de TLS et CMS, et ont également été utilisés pour implémenter de nombreux autres produits et protocoles tiers.

La fonctionnalité comprend le chiffrement symétrique, la cryptographie à clé publique, l'accord de clés, la gestion des certificats, les fonctions de hachage cryptographique, les générateurs de nombres pseudo-aléatoires cryptographiques, les codes d'authentification de messages (MAC), les fonctions de dérivation de clés (KDF) et diverses utilités.

Algorithmes

Les primitives cryptographiques telles que le digest SHA256, ou le chiffrement AES sont désignées dans OpenSSL comme des « algorithmes ». Chaque algorithme peut avoir plusieurs implémentations disponibles. Par exemple, l'algorithme RSA est disponible sous forme d'implémentation « par défaut » adaptée à un usage général, et une implémentation « fips » qui a été validée selon les normes FIPS 140 pour les situations où cela est important. Il est également possible qu'un tiers ajoute des implémentations supplémentaires, par exemple dans un module de sécurité matériel (HSM).

Les algorithmes sont implémentés dans des fournisseurs (providers). Voir ossl-guide-libraries-introduction(7) pour plus d'informations sur les fournisseurs.

Opérations

Différents algorithmes peuvent être regroupés par leur objectif. Par exemple, il existe des algorithmes de chiffrement et différents algorithmes de hachage de données. Ces différents groupes sont appelés « opérations » dans OpenSSL. Chaque opération a un ensemble différent de fonctions associées. Par exemple, pour effectuer une opération de chiffrement à l'aide d'AES (ou de tout autre algorithme de chiffrement), vous utiliseriez les fonctions de chiffrement détaillées sur la page EVP_EncryptInit(3). Ou pour effectuer une opération de hachage à l'aide de SHA256, vous utiliseriez les fonctions de hachage sur la page EVP_DigestInit(3).

CHERCHE ALGORITHME

Pour utiliser un algorithme, une implémentation doit d'abord être « cherchée ». Chercher est le processus qui consiste à parcourir les implémentations disponibles, à appliquer des critères de sélection (via une chaîne de requête de propriétés) et enfin à choisir l'implémentation qui sera utilisée.

Deux types de recherche sont pris en charge par OpenSSL : la « recherche explicite » et la « recherche implicite ».

Recherche explicite

La recherche explicite implique d'appeler directement une API spécifique pour rechercher une implémentation d'algorithme auprès d'un fournisseur. Cet objet recherché peut ensuite être passé à d'autres API. Ces fonctions de recherche explicite ont généralement le nom "NOMAPI_fetch", où "NOMAPI" est le nom de l'opération. Par exemple, EVP_MD_fetch(3) peut être utilisé pour rechercher explicitement une implémentation d'algorithme de hachage. L'utilisateur est responsable de libérer l'objet renvoyé par la fonction "NOMAPI_fetch" à l'aide de "NOMAPI_free" lorsqu'il n'est plus nécessaire.

Ces fonctions de recherche suivent un schéma assez courant, où trois arguments sont passés :

Le contexte de la bibliothèque
Voir OSSL_LIB_CTX(3) pour une description plus détaillée. Ceci peut être NULL pour indiquer le contexte de bibliothèque par défaut (global), ou un contexte créé par l'utilisateur. Seuls les fournisseurs chargés dans ce contexte de bibliothèque (voir OSSL_PROVIDER_load(3)) seront pris en compte par la fonction de recherche. Dans le cas où aucun fournisseur n'a été chargé dans ce contexte de bibliothèque, le fournisseur par défaut sera chargé en tant que solution de repli (voir OSSL_PROVIDER-default(7)).
Un identifiant
Pour toutes les fonctions de recherche actuellement implémentées, il s'agit du nom de l'algorithme. Chaque fournisseur prend en charge une liste d'implémentations d'algorithmes. Voir la documentation spécifique du fournisseur pour des informations sur les implémentations d'algorithmes disponibles dans chaque fournisseur : « OPÉRATIONS ET ALGORITHMES » dans OSSL_PROVIDER-default(7), « OPÉRATIONS ET ALGORITHMES » dans OSSL_PROVIDER-FIPS(7), « OPÉRATIONS ET ALGORITHMES » dans OSSL_PROVIDER-legacy(7) et « OPÉRATIONS ET ALGORITHMES » dans OSSL_PROVIDER-base(7).

Notez que bien que les fournisseurs puissent enregistrer des algorithmes sous une liste de noms en utilisant une chaîne avec une liste de noms séparés par des deux-points, la recherche d'algorithmes en utilisant ce format n'est actuellement pas prise en charge.

Une chaîne de requête de propriétés
La chaîne de requête de propriétés utilisée pour guider la sélection de l'implémentation de l'algorithme. Voir « CHAÎNES DE REQUÊTE DE PROPRIÉTÉS » dans ossl-guide-libraries-introduction(7).

L'implémentation de l'algorithme qui est recherchée peut ensuite être utilisée avec d'autres fonctions diverses qui les utilisent. Par exemple, la fonction EVP_DigestInit_ex(3) prend en paramètre un objet EVP_MD qui peut avoir été renvoyé par un appel précédent à EVP_MD_fetch(3).

Recherche implicite

OpenSSL dispose d'un certain nombre de fonctions qui renvoient un objet algorithme sans implémentation associée, telles que EVP_sha256(3), EVP_aes_128_cbc(3), EVP_get_cipherbyname(3) ou EVP_get_digestbyname(3). Celles-ci sont présentes pour la compatibilité avec OpenSSL avant la version 3.0 où la recherche explicite n'était pas disponible.

Lorsqu'elles sont utilisées avec des fonctions telles que EVP_DigestInit_ex(3) ou EVP_CipherInit_ex(3), l'implémentation réelle à utiliser est recherchée implicitement en utilisant des critères de recherche par défaut (qui utilisent NULL pour le contexte de la bibliothèque et la chaîne de requête de propriétés).

Dans certains cas, une recherche implicite peut également se produire lorsqu'un paramètre d'algorithme NULL est fourni. Dans ce cas, une implémentation d'algorithme est recherchée implicitement en utilisant des critères de recherche par défaut et un nom d'algorithme cohérent avec le contexte dans lequel il est utilisé.

Les fonctions qui utilisent un EVP_PKEY_CTX ou un EVP_PKEY(3), telles que EVP_DigestSignInit(3), recherchent toutes implicitement les implémentations. Généralement, l'algorithme à rechercher est déterminé en fonction du type de clé utilisé et de la fonction appelée.

Performance

Si vous effectuez la même opération plusieurs fois avec le même algorithme, il est recommandé d'effectuer une seule recherche explicite de l'algorithme, puis de réutiliser cet algorithme recherché explicitement à chaque fois suivante. Ce sera généralement plus rapide que de rechercher implicitement l'algorithme à chaque utilisation. Voir un exemple de recherche explicite dans « UTILISATION DES ALGORITHMES DANS LES APPLICATIONS ».

Avant OpenSSL 3.0, des fonctions telles que EVP_sha256() qui renvoient un objet « const » étaient utilisées directement pour indiquer l'algorithme à utiliser dans divers appels de fonction. Si vous passez la valeur de retour de l'une de ces fonctions utilitaires à une opération, vous utilisez la recherche implicite. Si vous convertissez une application qui fonctionnait avec une version d'OpenSSL antérieure à OpenSSL 3.0, envisagez de remplacer les occurrences de recherche implicite par une recherche explicite.

Si aucun objet recherché explicitement n'est passé à une opération, toute recherche implicite utilisera un objet pré-recherché mis en cache en interne, mais ce sera toujours plus lent que de passer directement l'objet recherché explicitement.

EXEMPLES DE RÉCUPÉRATION

La section suivante fournit une série d'exemples de récupération d'implémentations d'algorithmes.

Récupère toute implémentation disponible de SHA2-256 dans le contexte par défaut. Notez que certains algorithmes ont des alias. Ainsi, "SHA256" et "SHA2-256" sont synonymes :

EVP_MD *md = EVP_MD_fetch(NULL, "SHA2-256", NULL);
...
EVP_MD_free(md);

Récupère toute implémentation disponible de AES-128-CBC dans le contexte par défaut :

EVP_CIPHER *cipher = EVP_CIPHER_fetch(NULL, "AES-128-CBC", NULL);
...
EVP_CIPHER_free(cipher);

Récupère une implémentation de SHA2-256 du fournisseur par défaut dans le contexte par défaut :

EVP_MD *md = EVP_MD_fetch(NULL, "SHA2-256", "provider=default");
...
EVP_MD_free(md);

Récupère une implémentation de SHA2-256 qui n'est pas du fournisseur par défaut dans le contexte par défaut :

EVP_MD *md = EVP_MD_fetch(NULL, "SHA2-256", "provider!=default");
...
EVP_MD_free(md);

Récupère une implémentation de SHA2-256 qui provient de préférence du fournisseur FIPS dans le contexte par défaut :

EVP_MD *md = EVP_MD_fetch(NULL, "SHA2-256", "provider=?fips");
...
EVP_MD_free(md);

Récupère une implémentation de SHA2-256 du fournisseur par défaut dans le contexte de bibliothèque spécifié :

EVP_MD *md = EVP_MD_fetch(libctx, "SHA2-256", "provider=default");
...
EVP_MD_free(md);

Charge le fournisseur legacy dans le contexte par défaut, puis récupère une implémentation de WHIRLPOOL à partir de celui-ci :

/* Ceci ne doit être fait qu'une seule fois - généralement au démarrage de l'application */
OSSL_PROVIDER *legacy = OSSL_PROVIDER_load(NULL, "legacy");
EVP_MD *md = EVP_MD_fetch(NULL, "WHIRLPOOL", "provider=legacy");
...
EVP_MD_free(md);

Notez que dans l'exemple ci-dessus, la chaîne de propriétés "provider=legacy" est facultative car, en supposant qu'aucun autre fournisseur n'a été chargé, la seule implémentation de l'algorithme "whirlpool" se trouve dans le fournisseur "legacy". Notez également que le fournisseur par défaut doit être explicitement chargé s'il est requis en plus d'autres fournisseurs :

/* Ceci ne doit être fait qu'une seule fois - généralement au démarrage de l'application */
OSSL_PROVIDER *legacy = OSSL_PROVIDER_load(NULL, "legacy");
OSSL_PROVIDER *default = OSSL_PROVIDER_load(NULL, "default");
EVP_MD *md_whirlpool = EVP_MD_fetch(NULL, "whirlpool", NULL);
EVP_MD *md_sha256 = EVP_MD_fetch(NULL, "SHA2-256", NULL);
...
EVP_MD_free(md_whirlpool);
EVP_MD_free(md_sha256);

UTILISATION DES ALGORITHMES DANS LES APPLICATIONS

Les algorithmes cryptographiques sont mis à la disposition des applications via les API "EVP". Chacune des diverses opérations telles que le chiffrement, la condensation, les codes d'authentification de message, etc., dispose d'un ensemble d'appels de fonction EVP qui peuvent être invoqués pour les utiliser. Voir la page evp(7) pour plus de détails.

La plupart d'entre elles suivent un schéma commun. Un objet "contexte" est d'abord créé. Par exemple, pour une opération de condensation, vous utiliseriez un EVP_MD_CTX, et pour une opération de chiffrement/déchiffrement, vous utiliseriez un EVP_CIPHER_CTX. L'opération est ensuite initialisée, prête à l'emploi, via une fonction "init" - en passant éventuellement un ensemble de paramètres (en utilisant le type OSSL_PARAM(3)) pour configurer le comportement de l'opération. Ensuite, les données sont transmises à l'opération dans une série d'appels "update". L'opération est finalisée à l'aide d'un appel "final" qui fournira généralement une sorte de sortie. Enfin, le contexte est nettoyé et libéré.

Ce qui suit montre un exemple complet pour réaliser ce processus de condensation de données à l'aide de SHA256. Le processus est similaire pour d'autres opérations telles que le chiffrement/déchiffrement, les signatures, les codes d'authentification de message, etc. D'autres exemples peuvent être trouvés dans les démos OpenSSL (voir "DÉMONSTRATIONS D'APPLICATIONS" dans ossl-guide-libraries-introduction(7)).

#include <stdio.h>
#include <openssl/evp.h>
#include <openssl/bio.h>
#include <openssl/err.h>
int main(void)
{
    EVP_MD_CTX *ctx = NULL;
    EVP_MD *sha256 = NULL;
    const unsigned char msg[] = {
        0x00, 0x01, 0x02, 0x03
    };
    unsigned int len = 0;
    unsigned char *outdigest = NULL;
    int ret = 1;
    /* Créer un contexte pour l'opération de condensation */
    ctx = EVP_MD_CTX_new();
    if (ctx == NULL)
        goto err;
    /*
     * Récupérer l'implémentation de l'algorithme SHA256 pour effectuer la condensation. Nous utilisons
     * le contexte de bibliothèque "default" ici (premier paramètre NULL), et
     * nous ne fournissons aucun critère de recherche particulier pour notre implémentation SHA256
     * (deuxième paramètre NULL). Toute implémentation SHA256 fera l'affaire.
     * Dans une application plus grande, cette récupération ne serait effectuée qu'une seule fois, et pourrait
     * être utilisée pour plusieurs appels à d'autres opérations telles que EVP_DigestInit_ex().
     */
    sha256 = EVP_MD_fetch(NULL, "SHA256", NULL);
    if (sha256 == NULL)
        goto err;
   /* Initialiser l'opération de condensation */
   if (!EVP_DigestInit_ex(ctx, sha256, NULL))
       goto err;
    /*
     * Passer le message à condenser. Il peut être passé sur plusieurs
     * appels EVP_DigestUpdate si nécessaire
     */
    if (!EVP_DigestUpdate(ctx, msg, sizeof(msg)))
        goto err;
    /* Allouer le tampon de sortie */
    outdigest = OPENSSL_malloc(EVP_MD_get_size(sha256));
    if (outdigest == NULL)
        goto err;
    /* Calculer maintenant la condensation elle-même */
    if (!EVP_DigestFinal_ex(ctx, outdigest, &len))
        goto err;
    /* Afficher le résultat de la condensation */
    BIO_dump_fp(stdout, outdigest, len);
    ret = 0;
 err:
    /* Nettoyer toutes les ressources que nous avons allouées */
    OPENSSL_free(outdigest);
    EVP_MD_free(sha256);
    EVP_MD_CTX_free(ctx);
    if (ret != 0)
       ERR_print_errors_fp(stderr);
    return ret;
}

ENCODAGE ET DÉCODAGE DES CLÉS

De nombreux algorithmes nécessitent l'utilisation d'une clé. Les clés peuvent être générées dynamiquement à l'aide des API EVP (par exemple, voir EVP_PKEY_Q_keygen(3)). Cependant, il est souvent nécessaire de sauvegarder ou de charger des clés (ou leurs paramètres associés) à partir ou vers un format externe tel que PEM ou DER (voir openssl-glossary(7)). OpenSSL utilise des encodeurs et des décodeurs pour effectuer cette tâche.

Les encodeurs et décodeurs sont des implémentations d'algorithmes comme toute autre implémentation d'algorithme dans OpenSSL. Ils sont implémentés par des fournisseurs. Les encodeurs et décodeurs OpenSSL sont disponibles dans le fournisseur par défaut. Ils sont également dupliqués dans le fournisseur de base.

Pour plus d'informations sur les encodeurs, voir OSSL_ENCODER_CTX_new_for_pkey(3). Pour plus d'informations sur les décodeurs, voir OSSL_DECODER_CTX_new_for_pkey(3).

En plus d'utiliser directement des encodeurs/décodeurs, il existe également des fonctions d'aide qui peuvent être utilisées pour certains formats bien connus et couramment utilisés. Par exemple, voir PEM_read_PrivateKey(3) et PEM_write_PrivateKey(3) pour des informations sur la lecture et l'écriture de données de clé à partir de fichiers encodés PEM.
