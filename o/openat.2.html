DESCRIPTION

L'appel système open() ouvre le fichier spécifié par path. Si le fichier spécifié n'existe pas, il peut éventuellement (si O_CREAT est spécifié dans flags) être créé par open().

La valeur de retour de open() est un descripteur de fichier, un entier petit et non négatif qui est un index dans la table des descripteurs de fichiers ouverts du processus. Le descripteur de fichier est utilisé dans les appels système ultérieurs (read(2), write(2), lseek(2), fcntl(2), etc.) pour faire référence au fichier ouvert. Le descripteur de fichier retourné par un appel réussi sera le descripteur de fichier portant le plus petit numéro qui n'est pas actuellement ouvert pour le processus.

Par défaut, le nouveau descripteur de fichier est défini pour rester ouvert lors d'un execve(2) (c'est-à-dire que le drapeau de descripteur de fichier FD_CLOEXEC décrit dans fcntl(2) est initialement désactivé) ; le drapeau O_CLOEXEC, décrit ci-dessous, peut être utilisé pour modifier ce comportement par défaut. Le décalage de fichier est défini au début du fichier (voir lseek(2)).

Un appel à open() crée une nouvelle description de fichier ouverte, une entrée dans la table des fichiers ouverts au niveau du système. La description de fichier ouverte enregistre le décalage de fichier et les drapeaux d'état du fichier (voir ci-dessous). Un descripteur de fichier est une référence à une description de fichier ouverte ; cette référence n'est pas affectée si path est supprimé ultérieurement ou modifié pour pointer vers un fichier différent. Pour plus de détails sur les descriptions de fichiers ouverts, voir NOTES.

L'argument flags doit inclure l'un des modes d'accès suivants : O_RDONLY, O_WRONLY, ou O_RDWR. Ceux-ci demandent l'ouverture du fichier en lecture seule, en écriture seule, ou en lecture/écriture, respectivement.

En outre, zéro ou plusieurs drapeaux de création de fichier et drapeaux d'état de fichier peuvent être combinés par un OU bit à bit dans flags. Les drapeaux de création de fichier sont O_CLOEXEC, O_CREAT, O_DIRECTORY, O_EXCL, O_NOCTTY, O_NOFOLLOW, O_TMPFILE, et O_TRUNC. Les drapeaux d'état de fichier sont tous les drapeaux restants listés ci-dessous. La distinction entre ces deux groupes de drapeaux est que les drapeaux de création de fichier affectent la sémantique de l'opération d'ouverture elle-même, tandis que les drapeaux d'état de fichier affectent la sémantique des opérations d'E/S ultérieures. Les drapeaux d'état de fichier peuvent être récupérés et (dans certains cas) modifiés ; voir fcntl(2) pour plus de détails.

La liste complète des drapeaux de création de fichier et des drapeaux d'état de fichier est la suivante :

O_APPEND
Le fichier est ouvert en mode ajout. Avant chaque write(2), le décalage du fichier est positionné à la fin du fichier, comme avec lseek(2). La modification du décalage de fichier et l'opération d'écriture sont effectuées comme une seule étape atomique.
O_APPEND peut entraîner des fichiers corrompus sur les systèmes de fichiers NFS si plus d'un processus ajoute des données à un fichier simultanément. Ceci est dû au fait que NFS ne prend pas en charge l'ajout à un fichier, de sorte que le noyau client doit le simuler, ce qui ne peut pas être fait sans condition de concurrence.
O_ASYNC
Active l'E/S pilotée par signal : génère un signal (SIGIO par défaut, mais cela peut être changé via fcntl(2)) lorsque l'entrée ou la sortie devient possible sur ce descripteur de fichier. Cette fonctionnalité n'est disponible que pour les terminaux, pseudoterminaux, sockets et (depuis Linux 2.6) pipes et FIFOs. Voir fcntl(2) pour plus de détails. Voir aussi BUGS, ci-dessous.
O_CLOEXEC (depuis Linux 2.6.23)
Active le drapeau de fermeture à l'exécution pour le nouveau descripteur de fichier. La spécification de ce drapeau permet à un programme d'éviter des opérations supplémentaires de fcntl(2) F_SETFD pour définir le drapeau FD_CLOEXEC.
Notez que l'utilisation de ce drapeau est essentielle dans certains programmes multithreadés, car l'utilisation d'une opération séparée de fcntl(2) F_SETFD pour définir le drapeau FD_CLOEXEC ne suffit pas à éviter les conditions de concurrence où un thread ouvre un descripteur de fichier et tente de définir son drapeau de fermeture à l'exécution à l'aide de fcntl(2) en même temps qu'un autre thread effectue un fork(2) plus un execve(2). Selon l'ordre d'exécution, la condition de concurrence peut entraîner la fuite involontaire du descripteur de fichier retourné par open() vers le programme exécuté par le processus enfant créé par fork(2). (Ce type de condition de concurrence est en principe possible pour tout appel système qui crée un descripteur de fichier dont le drapeau de fermeture à l'exécution doit être défini, et divers autres appels système Linux fournissent un équivalent du drapeau O_CLOEXEC pour traiter ce problème.)
O_CREAT
Si path n'existe pas, créez-le sous forme de fichier ordinaire.
Le propriétaire (ID utilisateur) du nouveau fichier est défini sur l'ID utilisateur effectif du processus.
Le groupe propriétaire (ID de groupe) du nouveau fichier est défini soit sur l'ID de groupe effectif du processus (sémantique System V), soit sur l'ID de groupe du répertoire parent (sémantique BSD). Sous Linux, le comportement dépend du fait que le bit de mode set-group-ID soit défini sur le répertoire parent : si ce bit est défini, la sémantique BSD s'applique ; sinon, la sémantique System V s'applique. Pour certains systèmes de fichiers, le comportement dépend également des options de montage bsdgroups et sysvgroups décrites dans mount(8).
L'argument mode spécifie les bits de mode de fichier à appliquer lorsqu'un nouveau fichier est créé. Si ni O_CREAT ni O_TMPFILE ne sont spécifiés dans flags, alors mode est ignoré (et peut donc être spécifié comme 0, ou simplement omis). L'argument mode doit être fourni si O_CREAT ou O_TMPFILE est spécifié dans flags ; s'il n'est pas fourni, des octets arbitraires de la pile seront appliqués comme mode de fichier.
Le mode effectif est modifié par le umask du processus de la manière habituelle : en l'absence d'ACL par défaut, le mode du fichier créé est (mode & ~umask).
Notez que mode ne s'applique qu'aux accès futurs du fichier nouvellement créé ; l'appel open() qui crée un fichier en lecture seule peut très bien retourner un descripteur de fichier en lecture/écriture.
Les constantes symboliques suivantes sont fournies pour mode :
S_IRWXU

S_IRUSR
00400 l'utilisateur a la permission de lecture
S_IWUSR
00200 l'utilisateur a la permission d'écriture
S_IXUSR
00100 l'utilisateur a la permission d'exécution
S_IRWXG
00070 le groupe a les permissions de lecture, écriture et exécution
S_IRGRP
00040 le groupe a la permission de lecture
S_IWGRP
00020 le groupe a la permission d'écriture
S_IXGRP
00010 le groupe a la permission d'exécution
S_IRWXO
00007 les autres ont les permissions de lecture, écriture et exécution
S_IROTH
00004 les autres ont la permission de lecture

Les permissions de fichier sont généralement configurées en combinant ces constantes (par exemple, S_IRUSR | S_IWUSR pour définir les permissions de lecture et d'écriture pour le propriétaire).

O_DIRECTORY (depuis Linux 2.6.15)
Si path n'est pas un répertoire, l'appel échoue avec le message d'erreur ENOTDIR. Ce drapeau est conçu pour être utilisé avec les appels open() sur des descripteurs de fichier retournés par openat(2). Il est utile pour ouvrir un répertoire sans risque de suivre un lien symbolique pointant vers un fichier régulier.
O_DSYNC
Chemin d'accès synchronisé pour les données d'écriture. Les appels d'écriture sur le descripteur de fichier retourné seront bloquants jusqu'à ce que les données d'écriture soient transférées vers le périphérique de stockage. Les données et les métadonnées associées doivent être écrites. Ce drapeau peut entraîner des performances réduites sur certains systèmes. Les effets de O_DSYNC sont les mêmes que ceux de O_SYNC dans la plupart des cas, mais ils ne garantissent pas que les métadonnées soient écrites.
O_EXCL
Utilisé avec O_CREAT : si le fichier existe déjà, l'appel échoue avec le message d'erreur EEXIST.
O_EXCL n'est pas pris en charge de manière fiable sur tous les systèmes de fichiers. Les systèmes de fichiers réseau en particulier peuvent échouer à implémenter correctement cette fonctionnalité. Par conséquent, l'utilisation de O_EXCL sans l'une des autres conditions d'ouverture de création (O_CREAT) peut ne pas être sensée.
O_LARGEFILE
Les systèmes Linux modernes ne prennent plus en charge ce drapeau. Il était utilisé pour permettre aux fichiers de plus de 2 Go d'être créés sur des systèmes 32 bits. Le comportement par défaut de open() sur les systèmes Linux récents est de permettre la création de fichiers de grande taille.
O_NOATIME (depuis Linux 2.6.8)
Ne pas mettre à jour le temps d'accès au fichier. Ce drapeau affecte les mises à jour du champ st_atime dans la structure stat (voir stat(2)). L'impact sur les performances de l'activation de ce drapeau peut être significatif, car il évite une écriture sur le système de fichiers.
O_NOCTTY
Si le chemin spécifié est un descripteur de fichier de terminal, alors ce terminal ne deviendra pas le terminal de contrôle du processus. C'est utile dans les processus qui ne devraient pas avoir de terminal de contrôle, comme les démons.
O_NOFOLLOW (depuis Linux 2.6.15)
Ne pas suivre les liens symboliques. Si le chemin final du nom de fichier est un lien symbolique, l'appel échoue avec le message d'erreur ELOOP.
O_PATH (depuis Linux 3.11)
Peut être utilisé pour obtenir un descripteur de fichier représentant le chemin d'accès au fichier, sans l'ouvrir pour des opérations d'E/S. Le descripteur de fichier résultant est un descripteur de chemin. Il peut être utilisé avec certains appels système tels que fstatat(2), stat(2), renameat(2), unlinkat(2), et futimesat(2) pour effectuer des opérations sur le fichier représenté par le descripteur de chemin. Ce drapeau est utile pour éviter les conditions de concurrence lors de la manipulation de fichiers dans des espaces de noms (par exemple, dans les conteneurs) ou pour manipuler des fichiers sans les ouvrir (par exemple, pour éviter d'acquérir des privilèges ou d'allouer des ressources.
Lorsqu'il est utilisé avec O_RDONLY, le descripteur de chemin retourné par open() peut être passé aux appels système mentionnés ci-dessus, qui ont une forme d'argument spécifiant un descripteur de fichier et un nom de fichier relatif (par exemple, fstatat(2), unlinkat(2)). L'appelant peut alors utiliser ce descripteur de chemin pour accéder au fichier sous-jacent. Lorsque O_PATH est utilisé, les seuls autres drapeaux qui peuvent être OR-és avec lui sont O_DIRECTORY, O_NOFOLLOW, O_NOATIME, et les drapeaux d'accès O_RDONLY, O_WRONLY, O_RDWR.
O_SYNC
Accès synchronisé aux données et aux métadonnées. Tous les effets des opérations d'écriture sur le descripteur de fichier retourné seront visibles sur le système de stockage avant que l'appel de retour de la fonction ne soit autorisé. L'appel sera bloquant jusqu'à ce que les données et les métadonnées associées soient transférées vers le périphérique de stockage.
O_TMPFILE (depuis Linux 2.6.22)
Crée un fichier temporaire anonyme. Ce drapeau doit être utilisé avec O_RDWR ou O_WRONLY et l'un de O_CREAT. Le fichier sera créé dans le répertoire spécifié par le dernier composant de chemin de path (par exemple, si path est "/tmp/foo", le fichier est créé dans /tmp/). Si path est un répertoire vide, le fichier est créé dans ce répertoire. Le fichier est créé sans nom visible dans le système de fichiers, et sera automatiquement supprimé lorsque le dernier descripteur de fichier ouvert sera fermé. Les fichiers temporaires créés avec O_TMPFILE ne peuvent pas être renommés, et il est impossible de créer un lien sur eux. L'utilisation de O_TMPFILE sans O_CREAT est une erreur. Les implémentations de systèmes de fichiers qui ne prennent pas en charge les fichiers temporaires anonymes peuvent retourner EOPNOTSUPP.
O_TRUNC
Si le fichier existe et est ouvert pour l'écriture, son contenu est tronqué à une longueur de zéro.

Si O_CREAT est spécifié, et que le fichier existe déjà, et que O_TRUNC est spécifié, le fichier est tronqué, et aucune valeur de mode ne doit être spécifiée.

Si O_CREAT est spécifié, et que le fichier existe déjà, et que O_TRUNC n'est pas spécifié, alors les valeurs de flags sont stockées comme décrit ci-dessus, mais le fichier n'est pas tronqué.

Si O_CREAT est spécifié, et que le fichier n'existe pas, il est créé avec les permissions spécifiées par mode. Le fichier est ouvert avec les drapeaux spécifiés par flags.

Les opérations d'E/S sur les fichiers ouverts avec O_APPEND s'effectuent toujours à la fin du fichier. Si O_APPEND n'est pas spécifié, les opérations de lecture et d'écriture commencent au décalage actuel du fichier. Ce décalage est modifié par les opérations de lecture et d'écriture et peut être modifié par lseek(2). Si O_SYNC est spécifié, les opérations d'E/S se terminent lorsque toutes les écritures sont complétées.

L'argument facultatif mode est ignoré si O_CREAT n'est pas spécifié.

Les valeurs de retour de open() sont le descripteur de fichier ouvert, ou -1 en cas d'erreur.

openat() et creat()

L'appel système openat() est similaire à open(), mais il permet d'ouvrir un fichier dans un répertoire spécifié par un descripteur de fichier dirfd. Ce comportement est utile pour plusieurs raisons :

  • Si path est un chemin relatif, il est interprété par rapport au répertoire auquel se réfère dirfd, au lieu du répertoire de travail courant.
  • Si path est un chemin absolu, alors dirfd est ignoré.
  • Si path est un chemin relatif et que dirfd est AT_FDCWD (qui est défini dans <fcntl.h>), alors path est interprété par rapport au répertoire de travail courant, comme avec open().

L'utilisation de openat() avec O_CREAT est également supportée. Dans ce cas, si path n'existe pas, il est créé dans le répertoire spécifié par dirfd.

L'appel système creat() est une manière obsolète de créer un fichier. Il est équivalent à appeler open() avec seulement les drapeaux O_WRONLY | O_CREAT | O_TRUNC. L'utilisation de open() est préférée.

Les descripteurs de fichier sont des ressources limitées, et il est par conséquent important de les fermer lorsqu'ils ne sont plus nécessaires. Cela peut être fait en appelant close(2).

NORMES

Le standard POSIX.1-2008 décrit open() et openat(). L'appel système creat() est obsolète mais fait partie de POSIX.1-2001. Les drapeaux O_ASYNC, O_DIRECT, O_NOATIME, O_PATH, O_TMPFILE ne font pas partie des standards POSIX. O_CLOEXEC est décrit dans POSIX.1-2008. Les drapeaux O_DIRECTORY et O_NOFOLLOW sont décrits dans POSIX.1-2008.

NOTES

Descriptions de fichiers ouverts

Un appel réussi à open(), openat() ou creat() retourne un nouveau descripteur de fichier. Ce descripteur de fichier fait référence à une entrée dans la table des fichiers ouverts du processus. Chaque entrée de descripteur de fichier contient :

  • Un drapeau FD_CLOEXEC, qui détermine si le descripteur de fichier doit être fermé lors de l'exécution d'un programme différent (voir fcntl(2)).
  • Un drapeau d'état de fichier, qui est une copie des drapeaux passés à l'appel d'ouverture (par exemple, O_RDONLY, O_APPEND).
  • Un décalage de fichier, qui est un pointeur vers une position dans le fichier.

Lorsque plusieurs descripteurs de fichier (potentiellement dans des processus différents) font référence à la même description de fichier ouverte, ils partagent la même position de décalage et le même drapeau d'état de fichier. Une modification du décalage de fichier par un appel lseek(2) ou un appel d'E/S affectera tous les descripteurs de fichier faisant référence à la même description de fichier ouverte.

Les différentes descriptions de fichiers ouvertes peuvent référencer le même fichier sous-jacent (c'est-à-dire le même inode sur un système de fichiers).

Atomicité de openat()

L'appel système openat() est atomique par rapport aux autres appels système qui opèrent sur le même descripteur de fichier et le même chemin relatif. Cela signifie que les conditions de concurrence qui pourraient survenir lors de l'accès à des fichiers dans des répertoires différents (par exemple, lors de la manipulation de liens symboliques) sont évitées.

Drapeaux spécifiques à Linux

Les drapeaux suivants ne sont disponibles que sur Linux : O_DIRECTORY, O_NOFOLLOW, O_PATH, O_TMPFILE.

O_DIRECT (depuis Linux 2.4.10)
Tenter de minimiser les effets de cache des E/S vers et depuis ce fichier. En général, cela dégradera les performances, mais est utile dans des situations spéciales, comme lorsque les applications effectuent leur propre mise en cache. Les E/S de fichiers sont effectuées directement vers/depuis des tampons en espace utilisateur. Le drapeau O_DIRECT seul s'efforce de transférer les données de manière synchrone, mais ne donne pas les garanties du drapeau O_SYNC que les données et les métadonnées nécessaires sont transférées. Pour garantir les E/S synchrones, O_SYNC doit être utilisé en plus de O_DIRECT. Voir NOTES ci-dessous pour une discussion plus approfondie.
Une interface sémantiquement similaire (mais dépréciée) pour les périphériques bloc est décrite dans raw(8).
O_DIRECTORY
Si path n'est pas un répertoire, faire échouer open(). Ce drapeau a été ajouté dans Linux 2.1.126, pour éviter les problèmes de déni de service si opendir(3) est appelé sur un FIFO ou un périphérique de bande.
O_DSYNC
Les opérations d'écriture sur le fichier se termineront conformément aux exigences de la complétion d'intégrité des données synchronisées.
Au moment où write(2) (et similaires) retournent, les données de sortie ont été transférées vers le matériel sous-jacent, ainsi que toutes les métadonnées de fichier qui seraient nécessaires pour récupérer ces données (c'est-à-dire comme si chaque write(2) était suivi d'un appel à fdatasync(2)).
O_EXCL
Assurer que cet appel crée le fichier : si ce drapeau est spécifié avec O_CREAT, et que path existe déjà, alors open() échoue avec l'erreur EEXIST.
Lorsque ces deux drapeaux sont spécifiés, les liens symboliques ne sont pas suivis : si path est un lien symbolique, alors open() échoue, quel que soit l'endroit où le lien symbolique pointe.
En général, le comportement de O_EXCL est indéfini s'il est utilisé sans O_CREAT. Il y a une exception : sur Linux 2.6 et versions ultérieures, O_EXCL peut être utilisé sans O_CREAT si path fait référence à un périphérique bloc. Si le périphérique bloc est utilisé par le système (par exemple, monté), open() échoue avec l'erreur EBUSY.
Sur NFS, O_EXCL n'est pris en charge qu'avec NFSv3 ou plus récent sur un noyau 2.6 ou plus récent. Dans les environnements NFS où la prise en charge de O_EXCL n'est pas fournie, les programmes qui s'en servent pour effectuer des tâches de verrouillage conteniront une condition de concurrence (race condition). Les programmes portables qui souhaitent effectuer un verrouillage de fichier atomique à l'aide d'un fichier de verrouillage, et qui doivent éviter de dépendre de la prise en charge NFS pour O_EXCL, peuvent créer un fichier unique sur le même système de fichiers (par exemple, en incorporant le nom d'hôte et le PID), et utiliser link(2) pour créer un lien vers le fichier de verrouillage. Si link(2) renvoie 0, le verrouillage est réussi. Sinon, utiliser stat(2) sur le fichier unique pour vérifier si son nombre de liens a augmenté à 2, auquel cas le verrouillage est également réussi.
O_LARGEFILE
(LFS) Permet d'ouvrir des fichiers dont la taille ne peut pas être représentée dans un off_t (mais peut l'être dans un off64_t). Le macro _LARGEFILE64_SOURCE doit être définie (avant d'inclure tous les fichiers d'en-tête) afin d'obtenir cette définition. Définir le macro de test de fonctionnalité _FILE_OFFSET_BITS à 64 (plutôt que d'utiliser O_LARGEFILE) est la méthode préférée pour accéder aux gros fichiers sur les systèmes 32 bits (voir feature_test_macros(7)).
O_NOATIME (depuis Linux 2.6.8)
Ne pas mettre à jour le dernier temps d'accès au fichier (st_atime dans l'inode) lorsque le fichier est lu (read(2)).
Ce drapeau ne peut être utilisé que si l'une des conditions suivantes est vraie :
•
L'UID effectif du processus correspond à l'UID propriétaire du fichier.
•
Le processus appelant possède la capacité CAP_FOWNER dans son espace utilisateur et l'UID propriétaire du fichier a un mappage dans l'espace utilisateur.
Ce drapeau est destiné à être utilisé par des programmes d'indexation ou de sauvegarde, où son utilisation peut réduire considérablement l'activité disque. Ce drapeau peut ne pas être efficace sur tous les systèmes de fichiers. Un exemple est NFS, où le serveur maintient le temps d'accès.
O_NOCTTY
Si path fait référence à un périphérique terminal (voir tty(4)), il ne deviendra pas le terminal de contrôle du processus même si le processus n'en a pas.
O_NOFOLLOW
Si le composant final (c'est-à-dire le basename) de path est un lien symbolique, alors l'ouverture échoue, avec l'erreur ELOOP. Les liens symboliques dans les composants précédents du chemin seront toujours suivis. (Notez que l'erreur ELOOP qui peut survenir dans ce cas est indiscernable de le cas où une ouverture échoue car il y a trop de liens symboliques trouvés lors de la résolution des composants dans le préfixe du chemin.)
Ce drapeau est une extension FreeBSD, qui a été ajoutée dans Linux 2.1.126, et a été par la suite standardisée dans POSIX.1-2008.
Voir aussi O_PATH ci-dessous.
O_NONBLOCK ou O_NDELAY
Lorsque c'est possible, le fichier est ouvert en mode non bloquant. Ni l'appel open() ni aucune opération d'E/S ultérieure sur le descripteur de fichier qui est retourné ne feront attendre le processus appelant.
Notez que la définition de ce drapeau n'a aucun effet sur le fonctionnement de poll(2), select(2), epoll(7), et similaires, car ces interfaces informent simplement l'appelant si un descripteur de fichier est "prêt", ce qui signifie qu'une opération d'E/S effectuée sur le descripteur de fichier avec le drapeau O_NONBLOCK *effacé* ne bloquerait pas.
Notez que ce drapeau n'a aucun effet pour les fichiers ordinaires et les périphériques bloc ; c'est-à-dire que les opérations d'E/S bloqueront (brièvement) lorsque l'activité du périphérique est requise, indépendamment de la définition de O_NONBLOCK. Puisque les sémantiques de O_NONBLOCK pourraient éventuellement être implémentées, les applications ne devraient pas dépendre du comportement de blocage lors de la spécification de ce drapeau pour les fichiers ordinaires et les périphériques bloc.
Pour la gestion des FIFO (tubes nommés), voir aussi fifo(7). Pour une discussion de l'effet de O_NONBLOCK en conjonction avec les verrous de fichiers obligatoires et les baux de fichiers, voir fcntl(2).
O_PATH (depuis Linux 2.6.39)
Obtenir un descripteur de fichier qui peut être utilisé à deux fins : pour indiquer un emplacement dans l'arborescence du système de fichiers et pour effectuer des opérations qui agissent uniquement au niveau du descripteur de fichier. Le fichier lui-même n'est pas ouvert, et d'autres opérations de fichier (par exemple, read(2), write(2), fchmod(2), fchown(2), fgetxattr(2), ioctl(2), mmap(2)) échouent avec l'erreur EBADF.
Les opérations suivantes peuvent être effectuées sur le descripteur de fichier résultant :
•
close(2).
•
fchdir(2), si le descripteur de fichier fait référence à un répertoire (depuis Linux 3.5).
•
fstat(2) (depuis Linux 3.6).
•
fstatfs(2) (depuis Linux 3.12).
•
Duplication du descripteur de fichier (dup(2), fcntl(2) F_DUPFD, etc.).
•
Obtention et définition des drapeaux de descripteur de fichier (fcntl(2) F_GETFD et F_SETFD).
•
Récupération des drapeaux de statut de fichier ouvert à l'aide de l'opération fcntl(2) F_GETFL : les drapeaux retournés incluront le bit O_PATH.
•
Passage du descripteur de fichier comme argument dirfd de openat() et des autres appels système "*at()". Cela inclut linkat(2) avec AT_EMPTY_PATH (ou via procfs en utilisant AT_SYMLINK_FOLLOW) même si le fichier n'est pas un répertoire.
•
Passage du descripteur de fichier à un autre processus via un socket de domaine UNIX (voir SCM_RIGHTS dans unix(7)).
Lorsque O_PAT H est spécifié dans les flags, les bits de drapeau autres que O_CLOEXEC, O_DIRECTORY et O_NOFOLLOW sont ignorés.
L'ouverture d'un fichier ou d'un répertoire avec le drapeau O_PATH ne nécessite aucune permission sur l'objet lui-même (mais requiert la permission d'exécution sur les répertoires du préfixe du chemin). Selon l'opération ultérieure, une vérification des permissions de fichier appropriées peut être effectuée (par exemple, fchdir(2) nécessite la permission d'exécution sur le répertoire référencé par son descripteur de fichier argument). Par contraste, obtenir une référence à un objet de système de fichiers en l'ouvrant avec le drapeau O_RDONLY nécessite que l'appelant ait la permission de lecture sur l'objet, même lorsque l'opération ultérieure (par exemple, fchdir(2), fstat(2)) ne nécessite pas la permission de lecture sur l'objet.
Si path est un lien symbolique et que le drapeau O_NOFOLLOW est également spécifié, alors l'appel renvoie un descripteur de fichier faisant référence au lien symbolique. Ce descripteur de fichier peut être utilisé comme argument dirfd dans les appels à fchownat(2), fstatat(2), linkat(2) et readlinkat(2) avec un nom de chemin vide pour que les appels s'appliquent au lien symbolique.
Si path fait référence à un point d'automontage qui n'a pas encore été déclenché, de sorte qu'aucun autre système de fichiers n'est monté dessus, alors l'appel renvoie un descripteur de fichier faisant référence au répertoire d'automontage sans déclencher de montage. fstatfs(2) peut alors être utilisé pour déterminer s'il s'agit, en fait, d'un point d'automontage non déclenché (.f_type == AUTOFS_SUPER_MAGIC).
Une utilisation de O_PATH pour les fichiers réguliers est de fournir l'équivalent de la fonctionnalité O_EXEC de POSIX.1. Cela nous permet d'ouvrir un fichier pour lequel nous avons la permission d'exécution mais pas la permission de lecture, puis d'exécuter ce fichier, avec des étapes similaires à celles-ci :

char buf[PATH_MAX];
fd = open("some_prog", O_PATH);
snprintf(buf, PATH_MAX, "/proc/self/fd/%d", fd);
execl(buf, "some_prog", (char *) NULL);

Un descripteur de fichier O_PATH peut également être passé comme argument de fexecve(3).
O_SYNC
Les opérations d'écriture sur le fichier s'achèveront conformément aux exigences de la complétion d'intégrité de fichier par E/S synchronisées (par opposition à la complétion d'intégrité des données par E/S synchronisées fournie par O_DSYNC).
Au moment où write(2) (ou similaire) revient, les données de sortie et les métadonnées associées du fichier ont été transférées vers le matériel sous-jacent (c'est-à-dire comme si chaque write(2) était suivi d'un appel à fsync(2)). Voir VERSIONS.
O_TMPFILE (depuis Linux 3.11)
Crée un fichier régulier temporaire sans nom. L'argument path spécifie un répertoire ; un inode sans nom sera créé dans le système de fichiers de ce répertoire. Tout ce qui est écrit dans le fichier résultant sera perdu lorsque le dernier descripteur de fichier sera fermé, à moins que le fichier ne reçoive un nom.
O_TMPFILE doit être spécifié avec l'un des drapeaux O_RDWR ou O_WRONLY et, éventuellement, O_EXCL. Si O_EXCL n'est pas spécifié, alors linkat(2) peut être utilisé pour lier le fichier temporaire au système de fichiers, le rendant permanent, en utilisant un code comme suit :

char path[PATH_MAX];
fd = open("/path/to/dir", O_TMPFILE | O_RDWR,
                        S_IRUSR | S_IWUSR);
/* E/S fichier sur 'fd'...  */
linkat(fd, "", AT_FDCWD, "/path/for/file", AT_EMPTY_PATH);
/* Si l'appelant n'a pas la capacité CAP_DAC_READ_SEARCH
   (nécessaire pour utiliser AT_EMPTY_PATH avec linkat(2)),
   et qu'un système de fichiers proc(5) est monté, alors
   l'appel linkat(2) ci-dessus peut être remplacé par :
snprintf(path, PATH_MAX,  "/proc/self/fd/%d", fd);
linkat(AT_FDCWD, path, AT_FDCWD, "/path/for/file",
                        AT_SYMLINK_FOLLOW);
*/

Dans ce cas, l'argument mode de open() détermine le mode de permission du fichier, comme avec O_CREAT.
La spécification de O_EXCL en conjonction avec O_TMPFILE empêche un fichier temporaire d'être lié au système de fichiers de la manière décrite ci-dessus. (Notez que la signification de O_EXCL dans ce cas est différente de la signification de O_EXCL autrement.)
Il existe deux cas d'utilisation principaux pour O_TMPFILE :
•
Fonctionnalité améliorée de tmpfile(3) : création sans interférences de fichiers temporaires qui (1) sont automatiquement supprimés à la fermeture ; (2) ne peuvent jamais être atteints via un nom de chemin ; (3) ne sont pas sujets aux attaques par lien symbolique ; et (4) ne nécessitent pas que l'appelant invente des noms uniques.
•
Création d'un fichier initialement invisible, qui est ensuite rempli de données et ajusté pour avoir les attributs de système de fichiers appropriés (fchown(2), fchmod(2), fsetxattr(2), etc.) avant d'être atomiquement lié au système de fichiers dans un état complètement formé (en utilisant linkat(2) comme décrit ci-dessus).
O_TMPFILE nécessite le support du système de fichiers sous-jacent ; seul un sous-ensemble de systèmes de fichiers Linux fournit ce support. Dans l'implémentation initiale, le support était fourni dans les systèmes de fichiers ext2, ext3, ext4, UDF, Minix et tmpfs. Le support pour d'autres systèmes de fichiers a été ajouté par la suite : XFS (Linux 3.15) ; Btrfs (Linux 3.16) ; F2FS (Linux 3.16) ; et ubifs (Linux 4.9)
O_TRUNC
Si le fichier existe déjà et est un fichier régulier et que le mode d'accès autorise l'écriture (c'est-à-dire est O_RDWR ou O_WRONLY), il sera tronqué à la longueur 0. Si le fichier est un FIFO ou un fichier de périphérique terminal, le drapeau O_TRUNC est ignoré. Sinon, l'effet de O_TRUNC n'est pas spécifié.

creat()

Un appel à creat() est équivalent à un appel à open() avec flags égal à O_CREAT|O_WRONLY|O_TRUNC.

openat()

L'appel système openat() fonctionne exactement de la même manière que open(), sauf pour les différences décrites ici.

L'argument dirfd est utilisé en conjonction avec l'argument path comme suit :

•
Si le nom de chemin donné dans path est absolu, alors dirfd est ignoré.
•
Si le nom de chemin donné dans path est relatif et que dirfd est la valeur spéciale AT_FDCWD, alors path est interprété par rapport au répertoire de travail courant du processus appelant (comme open()).
•
Si le nom de chemin donné dans path est relatif, alors il est interprété par rapport au répertoire référencé par le descripteur de fichier dirfd (plutôt que par rapport au répertoire de travail courant du processus appelant, comme le fait open() pour un nom de chemin relatif). Dans ce cas, dirfd doit être un répertoire qui a été ouvert en lecture (O_RDONLY) ou en utilisant le drapeau O_PATH.

Si le nom de chemin donné dans path est relatif, et que dirfd n'est pas un descripteur de fichier valide, une erreur (EBADF) en résulte. (Spécifier un numéro de descripteur de fichier invalide dans dirfd peut être utilisé comme moyen de s'assurer que path est absolu.)

openat2(2)

L'appel système openat2(2) est une extension de openat(), et fournit un sur-ensemble des fonctionnalités de openat(). Il est documenté séparément, dans openat2(2).

VALEUR DE RETOUR

En cas de succès, open(), openat() et creat() renvoient le nouveau descripteur de fichier (un entier non négatif). En cas d'erreur, -1 est renvoyé et errno est défini pour indiquer l'erreur.

ERREURS

open(), openat() et creat() peuvent échouer avec les erreurs suivantes :

EACCES
L'accès demandé au fichier n'est pas autorisé, ou la permission de recherche est refusée pour l'un des répertoires dans le préfixe du chemin de path, ou le fichier n'existait pas encore et l'accès en écriture au répertoire parent n'est pas autorisé. (Voir aussi path_resolution(7).)
EACCES
Lorsque O_CREAT est spécifié, que protected_fifos ou protected_regular est activé, que le fichier existe déjà et est un FIFO ou un fichier régulier, que le propriétaire du fichier n'est ni l'utilisateur courant ni le propriétaire du répertoire contenant, et que le répertoire contenant est à la fois accessible en écriture par tous ou par groupe et collant (sticky). Pour plus de détails, voir les descriptions de /proc/sys/fs/protected_fifos et /proc/sys/fs/protected_regular dans proc_sys_fs(5).
EBADF
(openat()) path est relatif mais dirfd n'est ni AT_FDCWD ni un descripteur de fichier valide.
EBUSY
O_EXCL a été spécifié dans flags et path fait référence à un périphérique bloc en cours d'utilisation par le système (par exemple, il est monté).
EDQUOT
Lorsque O_CREAT est spécifié, que le fichier n'existe pas, et que le quota de blocs disque ou d'inodes de l'utilisateur sur le système de fichiers a été épuisé.
EEXIST
path existe déjà et O_CREAT et O_EXCL ont été utilisés.
EFAULT
path pointe en dehors de votre espace d'adressage accessible.
EFBIG
Voir EOVERFLOW.
EINTR
Alors qu'il attendait de terminer une ouverture d'un périphérique lent (par exemple, un FIFO ; voir fifo(7)), l'appel a été interrompu par un gestionnaire de signaux ; voir signal(7).
EINVAL
Le système de fichiers ne prend pas en charge l'indicateur O_DIRECT. Voir NOTES pour plus d'informations.
EINVAL
Valeur invalide dans flags.
EINVAL
O_TMPFILE a été spécifié dans flags, mais ni O_WRONLY ni O_RDWR n'a été spécifié.
EINVAL
O_CREAT et O_DIRECTORY ont tous deux été spécifiés dans flags, et la version du noyau Linux est 6.4 ou ultérieure. (Les noyaux précédents étaient incohérents dans ce domaine, et POSIX ne spécifie pas le comportement.)
EINVAL
O_CREAT a été spécifié dans flags et le composant final (« basename ») du nouveau fichier path est invalide (par exemple, il contient des caractères non autorisés par le système de fichiers sous-jacent).
EINVAL
Le composant final (« basename ») de path est invalide (par exemple, il contient des caractères non autorisés par le système de fichiers sous-jacent).
EISDIR
path fait référence à un répertoire et l'accès demandé impliquait une écriture (c'est-à-dire que O_WRONLY ou O_RDWR est défini).
EISDIR
path fait référence à un répertoire existant, O_TMPFILE et l'un de O_WRONLY ou O_RDWR ont été spécifiés dans flags, mais cette version du noyau ne fournit pas la fonctionnalité O_TMPFILE.
ELOOP
Trop de liens symboliques ont été rencontrés lors de la résolution de path.
ELOOP
path était un lien symbolique, et flags spécifiait O_NOFOLLOW mais pas O_PATH.
EMFILE
La limite par processus du nombre de descripteurs de fichiers ouverts a été atteinte (voir la description de RLIMIT_NOFILE dans getrlimit(2)).
ENAMETOOLONG
path était trop long.
ENFILE
La limite globale du système sur le nombre total de fichiers ouverts a été atteinte.
ENODEV
path fait référence à un fichier spécial de périphérique et aucun périphérique correspondant n'existe. (C'est un bug du noyau Linux ; dans cette situation, ENXIO doit être retourné.)
ENOENT
O_CREAT n'est pas défini et le fichier nommé n'existe pas.
ENOENT
Un composant de répertoire dans path n'existe pas ou est un lien symbolique pendant.
ENOENT
path fait référence à un répertoire inexistant, O_TMPFILE et l'un de O_WRONLY ou O_RDWR ont été spécifiés dans flags, mais cette version du noyau ne fournit pas la fonctionnalité O_TMPFILE.
ENOMEM
Le fichier nommé est un FIFO, mais la mémoire pour le tampon FIFO ne peut pas être allouée car la limite stricte par utilisateur pour l'allocation de mémoire pour les tubes a été atteinte et l'appelant n'est pas privilégié ; voir pipe(7).
ENOMEM
La mémoire noyau disponible était insuffisante.
ENOSPC
path devait être créé mais le périphérique contenant path n'a pas de place pour le nouveau fichier.
ENOTDIR
Un composant utilisé comme répertoire dans path n'est pas, en fait, un répertoire, ou O_DIRECTORY a été spécifié et path n'était pas un répertoire.
ENOTDIR
(openat()) path est un chemin relatif et dirfd est un descripteur de fichier faisant référence à un fichier autre qu'un répertoire.
ENXIO
O_NONBLOCK | O_WRONLY est défini, le fichier nommé est un FIFO, et aucun processus n'a le FIFO ouvert en lecture.
ENXIO
Le fichier est un fichier spécial de périphérique et aucun périphérique correspondant n'existe.
ENXIO
Le fichier est un socket de domaine UNIX.
EOPNOTSUPP
Le système de fichiers contenant path ne prend pas en charge O_TMPFILE.
EOVERFLOW
path fait référence à un fichier régulier trop volumineux pour être ouvert. Le scénario habituel ici est qu'une application compilée sur une plateforme 32 bits sans -D_FILE_OFFSET_BITS=64 a tenté d'ouvrir un fichier dont la taille dépasse (1<<31)-1 octets ; voir également O_LARGEFILE ci-dessus. C'est l'erreur spécifiée par POSIX.1 ; avant Linux 2.6.24, Linux retournait l'erreur EFBIG pour ce cas.
EPERM
L'indicateur O_NOATIME a été spécifié, mais l'ID utilisateur effectif de l'appelant ne correspondait pas au propriétaire du fichier et l'appelant n'était pas privilégié.
EPERM
L'opération a été empêchée par un sceau de fichier ; voir fcntl(2).
EROFS
path fait référence à un fichier sur un système de fichiers en lecture seule et un accès en écriture a été demandé.
ETXTBSY
path fait référence à une image exécutable en cours d'exécution et un accès en écriture a été demandé.
ETXTBSY
path fait référence à un fichier actuellement utilisé comme fichier d'échange, et l'indicateur O_TRUNC a été spécifié.
ETXTBSY
path fait référence à un fichier actuellement lu par le noyau (par exemple, pour le chargement de modules/firmwares), et un accès en écriture a été demandé.
EWOULDBLOCK
L'indicateur O_NONBLOCK a été spécifié, et un bail incompatible était détenu sur le fichier (voir fcntl(2)).

VERSIONS

L'effet (non défini) de O_RDONLY | O_TRUNC varie selon les implémentations. Sur de nombreux systèmes, le fichier est effectivement tronqué.

E/S synchronisées

L'option « E/S synchronisées » de POSIX.1-2008 spécifie différentes variantes d'E/S synchronisées et spécifie les indicateurs open() O_SYNC, O_DSYNC et O_RSYNC pour contrôler le comportement. Indépendamment du fait qu'une implémentation prenne en charge ou non cette option, elle doit au moins prendre en charge l'utilisation de O_SYNC pour les fichiers réguliers.

Linux implémente O_SYNC et O_DSYNC, mais pas O_RSYNC. De manière quelque peu incorrecte, glibc définit O_RSYNC pour avoir la même valeur que O_SYNC. (O_RSYNC est défini dans le fichier d'en-tête Linux <asm/fcntl.h> sur HP PA-RISC, mais il n'est pas utilisé.)

O_SYNC fournit une complétion d'intégrité de fichier d'E/S synchronisées, ce qui signifie que les opérations d'écriture videront les données et toutes les métadonnées associées sur le matériel sous-jacent. O_DSYNC fournit une complétion d'intégrité de données d'E/S synchronisées, ce qui signifie que les opérations d'écriture videront les données sur le matériel sous-jacent, mais ne videront que les mises à jour de métadonnées nécessaires pour permettre à une opération de lecture ultérieure de se terminer avec succès. La complétion de l'intégrité des données peut réduire le nombre d'opérations disque requises pour les applications qui n'ont pas besoin des garanties de complétion de l'intégrité des fichiers.

Pour comprendre la différence entre les deux types de complétion, considérez deux éléments de métadonnées de fichier : l'horodatage de dernière modification du fichier (st_mtime) et la longueur du fichier. Toutes les opérations d'écriture mettront à jour l'horodatage de dernière modification du fichier, mais seules les écritures qui ajoutent des données à la fin du fichier modifieront la longueur du fichier. L'horodatage de dernière modification n'est pas nécessaire pour garantir qu'une lecture se termine avec succès, mais la longueur du fichier l'est. Ainsi, O_DSYNC garantirait uniquement le vidage des mises à jour de la métadonnée de longueur de fichier (tandis que O_SYNC viderait également toujours la métadonnée d'horodatage de dernière modification).

Avant Linux 2.6.33, Linux n'implémentait que l'indicateur O_SYNC pour open(). Cependant, lorsque cet indicateur était spécifié, la plupart des systèmes de fichiers fournissaient en réalité l'équivalent d'une complétion d'intégrité de données d'E/S synchronisées (c'est-à-dire que O_SYNC était en fait implémenté comme l'équivalent de O_DSYNC).

Depuis Linux 2.6.33, le support O_SYNC approprié est fourni. Cependant, pour assurer la compatibilité binaire descendante, O_DSYNC a été défini avec la même valeur que l'ancien O_SYNC, et O_SYNC a été défini comme une nouvelle valeur d'indicateur (à deux bits) qui inclut la valeur de l'indicateur O_DSYNC. Cela garantit que les applications compilées avec de nouveaux en-têtes obtiennent au moins les sémantiques de O_DSYNC avant Linux 2.6.33.

Descriptions de fichiers ouverts

Le terme description de fichier ouvert est celui utilisé par POSIX pour désigner les entrées dans la table système des fichiers ouverts. Dans d'autres contextes, cet objet est également appelé indifféremment "objet de fichier ouvert", "handle de fichier", "entrée de table de fichier ouvert" ou, dans le jargon des développeurs noyau, un struct file.

Lorsqu'un descripteur de fichier est dupliqué (à l'aide de dup(2) ou similaire), le duplicata fait référence à la même description de fichier ouvert que le descripteur de fichier d'origine, et les deux descripteurs de fichiers partagent par conséquent le décalage de fichier et les drapeaux de statut du fichier. Un tel partage peut également se produire entre processus : un processus enfant créé via fork(2) hérite de duplicatas des descripteurs de fichiers de son parent, et ces duplicatas font référence aux mêmes descriptions de fichiers ouverts.

Chaque appel à open() d'un fichier crée une nouvelle description de fichier ouvert ; ainsi, il peut y avoir plusieurs descriptions de fichiers ouverts correspondant à un inode de fichier.

Sous Linux, on peut utiliser l'opération kcmp(2) KCMP_FILE pour tester si deux descripteurs de fichiers (dans le même processus ou dans deux processus différents) font référence à la même description de fichier ouvert.

NFS

Il existe de nombreuses imperfections dans le protocole sous-jacent à NFS, affectant entre autres O_SYNC et O_NDELAY.

Sur les systèmes de fichiers NFS avec mappage d'UID activé, open() peut renvoyer un descripteur de fichier mais, par exemple, les requêtes read(2) sont refusées avec EACCES. Ceci est dû au fait que le client effectue open() en vérifiant les permissions, mais le mappage d'UID est effectué par le serveur lors des requêtes de lecture et d'écriture.

Tubes nommés (FIFO)

L'ouverture de l'extrémité de lecture ou d'écriture d'un FIFO bloque jusqu'à ce que l'autre extrémité soit également ouverte (par un autre processus ou thread). Voir fifo(7) pour plus de détails.

Mode d'accès au fichier

Contrairement aux autres valeurs pouvant être spécifiées dans flags, les valeurs du mode d'accès O_RDONLY, O_WRONLY et O_RDWR ne spécifient pas des bits individuels. Elles définissent plutôt les deux bits de poids faible de flags, et sont respectivement définies comme 0, 1 et 2. Autrement dit, la combinaison O_RDONLY | O_WRONLY est une erreur logique, et n'a certainement pas la même signification que O_RDWR.

Linux réserve le mode d'accès spécial non standard 3 (binaire 11) dans flags pour signifier : vérifier les permissions de lecture et d'écriture sur le fichier et renvoyer un descripteur de fichier qui ne peut pas être utilisé pour la lecture ou l'écriture. Ce mode d'accès non standard est utilisé par certains pilotes Linux pour renvoyer un descripteur de fichier destiné uniquement aux opérations ioctl(2) spécifiques au périphérique.

Raison d'être de openat() et des autres API de descripteurs de fichiers de répertoire

openat() et les autres appels système et fonctions de bibliothèque qui prennent un argument de descripteur de fichier de répertoire (c'est-à-dire execveat(2), faccessat(2), fanotify_mark(2), fchmodat(2), fchownat(2), fspick(2), fstatat(2), futimesat(2), linkat(2), mkdirat(2), mknodat(2), mount_setattr(2), move_mount(2), name_to_handle_at(2), open_tree(2), openat2(2), readlinkat(2), renameat(2), renameat2(2), statx(2), symlinkat(2), unlinkat(2), utimensat(2), mkfifoat(3), et scandirat(3)) résolvent deux problèmes avec les interfaces plus anciennes qui les précédaient. Ici, l'explication porte sur l'appel openat(), mais la logique est analogue pour les autres interfaces.

Premièrement, openat() permet à une application d'éviter les conditions de concurrence qui pourraient survenir lors de l'utilisation de open() pour ouvrir des fichiers dans des répertoires autres que le répertoire de travail courant. Ces conditions de concurrence résultent du fait que certains composants du préfixe de répertoire donné à open() pourraient être modifiés en parallèle avec l'appel à open(). Supposons, par exemple, que nous souhaitions créer le fichier dir1/dir2/xxx.dep si le fichier dir1/dir2/xxx existe. Le problème est qu'entre la vérification d'existence et l'étape de création du fichier, dir1 ou dir2 (qui pourraient être des liens symboliques) pourraient être modifiés pour pointer vers un emplacement différent. De telles courses peuvent être évitées en ouvrant un descripteur de fichier pour le répertoire cible, puis en spécifiant ce descripteur de fichier comme argument dirfd de (par exemple) fstatat(2) et openat(). L'utilisation du descripteur de fichier dirfd a également d'autres avantages :

•
le descripteur de fichier est une référence stable vers le répertoire, même si le répertoire est renommé ; et
•
le descripteur de fichier ouvert empêche le système de fichiers sous-jacent d'être démonté, tout comme lorsqu'un processus a un répertoire de travail courant sur un système de fichiers.

Deuxièmement, openat() permet l'implémentation d'un "répertoire de travail courant" par thread, via des descripteurs de fichiers maintenus par l'application. (Cette fonctionnalité peut également être obtenue par des astuces basées sur l'utilisation de /proc/self/fd/dirfd, mais de manière moins efficace.)

L'argument dirfd pour ces API peut être obtenu en utilisant open() ou openat() pour ouvrir un répertoire (avec le drapeau O_RDONLY ou O_PATH). Alternativement, un tel descripteur de fichier peut être obtenu en appliquant dirfd(3) à un flux de répertoire créé à l'aide de opendir(3).

Lorsque ces API reçoivent un argument dirfd de AT_FDCWD ou que le chemin spécifié est absolu, elles traitent leur argument de chemin de la même manière que les API conventionnelles correspondantes. Cependant, dans ce cas, plusieurs des API ont un argument flags qui donne accès à des fonctionnalités qui ne sont pas disponibles avec les API conventionnelles correspondantes.

O_DIRECT

Le drapeau O_DIRECT peut imposer des restrictions d'alignement sur la longueur et l'adresse des tampons d'espace utilisateur et sur le décalage de fichier des E/S. Sous Linux, les restrictions d'alignement varient selon le système de fichiers et la version du noyau et pourraient être totalement absentes. La gestion des E/S O_DIRECT mal alignées varie également ; elles peuvent soit échouer avec EINVAL, soit se replier sur les E/S mises en tampon.

Depuis Linux 6.1, la prise en charge de O_DIRECT et les restrictions d'alignement pour un fichier peuvent être interrogées à l'aide de statx(2), en utilisant le drapeau STATX_DIOALIGN. La prise en charge de STATX_DIOALIGN varie selon le système de fichiers ; voir statx(2).

Certains systèmes de fichiers fournissent leurs propres interfaces pour interroger les restrictions d'alignement O_DIRECT, par exemple l'opération XFS_IOC_DIOINFO dans xfsctl(3). STATX_DIOALIGN doit être utilisé à la place lorsque cela est disponible.

NAME

openat, open, creat — open or create a file

LIBRARY

Standard C library (libc, -lc)

SYNOPSIS

In `fcntl.h`

int openat(int dirfd, const char *pathname, int flags);
int openat(int dirfd, const char *pathname, int flags, mode_t mode);
int open(const char *pathname, int flags);
int open(const char *pathname, int flags, mode_t mode);
int creat(const char *pathname, mode_t mode);

DESCRIPTION

The behavior of these system calls depends on the value of the flags argument.

The openat() system call is the modern interface to file opening. It is equivalent to calling open() except in the case where pathname is relative. If pathname specifies a relative path, then it is interpreted relative to the directory referred to by the file descriptor dirfd, which is a file descriptor obtained from a successful open() or openat() call, or one of the special file descriptors `.` (AT_FDCWD), open() itself.

If pathname is relative and dirfd is `.` (AT_FDCWD), then pathname is interpreted relative to the current working directory. See openat(2) for details on the possible values for dirfd.

The open() system call can be used to open or create a file and return a new file descriptor therefore. If the named file does not exist, it is created if the flags argument includes O_CREAT. The permissions of the created file are determined by the mode argument (see chmod(2)), and modified by the process's umask. If the file exists, the permissions specified by mode are ignored. The creat() system call is equivalent to calling open() with only the O_WRONLY and O_CREAT flags set.

flags

The flags argument is the bitwise OR of zero or more of the following options:

O_ACCMODE
Mask for access modes; any of O_RDONLY, O_WRONLY, or O_RDWR must be included in flags.
O_APPEND
Append mode: each write operation writes data at the end of the file, regardless of the write offset. This flag is ignored in conjunction with O_RDONLY. The file offset is set to the end of the file prior to each write.
O_CLOEXEC
If this flag is set, the file descriptor is not inherited across execve(2) (see fcntl(2)).
O_CREAT
If the file does not exist, create it. The owning user and group IDs are set to the effective user ID and effective group ID of the calling process, respectively. The permissions of the created file are determined by the mode argument, and modified by the process's umask. This flag is ignored if the file already exists.
O_DIRECT
Attempt to minimize cache effects of the I/O subsystem. A common use of this flag is to bypass the kernel page cache entirely for direct access to the storage device. The O_DIRECT flag can bypass the kernel page cache for both reads and writes, and it can also allow writes to data that is not yet fully written to disk to be synchronous. The alignment restrictions can only be assumed from known characteristics of the filesystem, the individual file, the underlying storage device(s), and the kernel version. In Linux 2.4, most filesystems based on block devices require that the file offset and the length and memory address of all I/O segments be multiples of the filesystem block size (typically 4096 bytes). In Linux 2.6.0, this was relaxed to the logical block size of the block device (typically 512 bytes). A block device's logical block size can be determined using the ioctl(2) BLKSSZGET operation or from the shell using the command:


blockdev --getss

O_DIRECT I/Os should never be run concurrently with the fork(2) system call, if the memory buffer is a private mapping (i.e., any mapping created with the mmap(2) MAP_PRIVATE flag; this includes memory allocated on the heap and statically allocated buffers). Any such I/Os, whether submitted via an asynchronous I/O interface or from another thread in the process, should be completed before fork(2) is called. Failure to do so can result in data corruption and undefined behavior in parent and child processes. This restriction does not apply when the memory buffer for the O_DIRECT I/Os was created using shmat(2) or mmap(2) with the MAP_SHARED flag. Nor does this restriction apply when the memory buffer has been advised as MADV_DONTFORK with madvise(2), ensuring that it will not be available to the child after fork(2).

The O_DIRECT flag was introduced in SGI IRIX, where it has alignment restrictions similar to those of Linux 2.4. IRIX has also a fcntl(2) call to query appropriate alignments, and sizes. FreeBSD 4.x introduced a flag of the same name, but without alignment restrictions.

O_DIRECT support was added in Linux 2.4.10. Older Linux kernels simply ignore this flag. Some filesystems may not implement the flag, in which case open() fails with the error EINVAL if it is used.

Applications should avoid mixing O_DIRECT and normal I/O to the same file, and especially to overlapping byte regions in the same file. Even when the filesystem correctly handles the coherency issues in this situation, overall I/O throughput is likely to be slower than using either mode alone. Likewise, applications should avoid mixing mmap(2) of files with direct I/O to the same files.

The behavior of O_DIRECT with NFS will differ from local filesystems. Older kernels, or kernels configured in certain ways, may not support this combination. The NFS protocol does not support passing the flag to the server, so O_DIRECT I/O will bypass the page cache only on the client; the server may still cache the I/O. The client asks the server to make the I/O synchronous to preserve the synchronous semantics of O_DIRECT. Some servers will perform poorly under these circumstances, especially if the I/O size is small. Some servers may also be configured to lie to clients about the I/O having reached stable storage; this will avoid the performance penalty at some risk to data integrity in the event of server power failure. The Linux NFS client places no alignment restrictions on O_DIRECT I/O.

In summary, O_DIRECT is a potentially powerful tool that should be used with caution. It is recommended that applications treat use of O_DIRECT as a performance option which is disabled by default.

O_DIRECTORY
Only allow opening a directory. If the named file is not a directory, the call fails with the error EINVAL.
O_DSYNC
Write I/O synchronization. This means that all of the output in the buffer associated with this file descriptor is written to the underlying storage device. The data is written, but the metadata may not be updated until later. If this flag is set, writes will complete only after the data has been committed to stable storage. Reads will not return data that was written before the write operation completed.
O_EXCL
Used with O_CREAT. Ensure that this call creates an exclusive use file. It fails if the file already exists. This is useful for programs that need to establish a lockfile and can't rely on lockf(3) or fcntl(2) locking.
O_LARGEFILE
This flag is ignored since Linux 2.2. The kernel handles large files automatically.
O_NOATIME
Do not update access times when querying or modifying files. This flag can be overridden by other operations. See also open(2) and stat(2).
O_NOCTTY
If pathname refers to a terminal device, this flag does not cause it to become the process's controlling terminal. This flag is ignored if the file descriptor referred to is not a terminal device.
O_NONBLOCK
Do not block on read or write operations. Set or clear this flag using fcntl(2).
O_PATH
Obtain a file descriptor referring to the target of the filename, not the file itself. This implies that O_DIRECTORY and O_NOFOLLOW will be set, and that O_RDWR is implied. This flag is useful for operations that need to be performed on a file through its path, without the possibility of breaking symlinks or accessing the wrong file.
O_RDONLY
Open for reading only.
O_RDWR
Open for reading and writing.
O_SYNC
Synchronous writes. Equivalent to O_DSYNC | O_RSYNC.
O_TRUNC
Truncate the file to zero length when opening. All previous contents of the file are lost. If the file does not exist, it is created unless O_CREAT is not specified.
O_TMPFILE
Create a temporary file. This flag must be specified with O_TMPFILE and one of O_WRONLY or O_RDWR. The file is created in the directory referred to by dirfd. The filename in pathname is ignored except for its symbolic significance. A file created with O_TMPFILE is anonymous, and is automatically deleted when the last file descriptor referring to it is closed. Such a file is not visible in the filesystem namespace. The file is deleted by default. To create a file that is visible, you must pass a pathname. If pathname is not `.` and is not specified for openat, then the file is created in the directory specified by pathname. This flag is intended for use by applications that need temporary files but do not need a name for them in the filesystem. It is useful for avoiding races in the creation of temporary files.
O_WRONLY
Open for writing only.

RETURN VALUE

Upon successful completion, these calls return a non-negative integer representing the lowest numbered unused file descriptor. Otherwise, they return -1 and set errno to indicate the error.

ERRORS

The open() and creat() system calls can fail for any of the errors specified for openat() except for EBADF, ENOTDIR, EACCES, ELOOP, and ENAMETOOLONG.

The openat() system call can fail with any of the following errors:

EACCES
Search permission denied for one of the components of the prefix pathname, or O_WRONLY or O_RDWR was specified, but the file could not be opened for writing, or O_RDONLY was specified, but the file could not be opened for reading.
EEXIST
pathname refers to a file that exists, but O_EXCL and O_CREAT were both specified.
EINVAL
flags contains an invalid value, or the file system does not support the requested flags (e.g., O_DIRECT on a filesystem that does not support it).
EISDIR
pathname refers to a directory, and the flags specified are not compatible with opening a directory (e.g. O_WRONLY or O_TRUNC).
EMFILE
The process has reached its limit for the number of open file descriptors.
ENAMETOOLONG
pathname is too long.
ENFILE
The system limit on the total number of open files has been reached.
ENOENT
pathname does not exist and O_CREAT was not specified. Or, O_TMPFILE was specified, and dirfd referred to a deleted directory.
ENOMEM
Out of memory.
ENOTDIR
pathname is a relative path, and dirfd referred to a file descriptor that was not a directory. Or O_DIRECTORY was specified and pathname was not a directory.
ENXIO
The named file does not exist and O_CREAT was not specified. Or a device special file exists but did not have the required block set up.
EROFS
The named file resides on a read-only filesystem, and O_WRONLY or O_RDWR was specified.
ETXTBSY
Text file busy. This occurs when a program is being executed from a file, and the user attempts to open the file in write-only mode.
