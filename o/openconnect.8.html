NOM

openconnect - Client VPN multi-protocoles, pour les VPN Cisco AnyConnect et autres

SYNTAXE

openconnect [--config fichier_config] [-b,--background] [--pid-file fichier_pid] [-c,--certificate cert] [-e,--cert-expire-warning jours] [-k,--sslkey clé] [-C,--cookie cookie] [--cookie-on-stdin] [--compression MODE] [-d,--deflate] [-D,--no-deflate] [--force-dpd intervalle] [--force-trojan intervalle] [-F,--form-entry form:opt=valeur] [-g,--usergroup groupe] [-h,--help] [--http-auth méthodes] [--external-browser navigateur] [-i,--interface nom_interface] [-l,--syslog] [--timestamp] [--passtos] [-U,--setuid utilisateur] [--csd-user utilisateur] [-m,--mtu mtu] [--base-mtu mtu] [-p,--key-password mot_de_passe] [-P,--proxy url_proxy] [--proxy-auth méthodes] [--no-proxy] [--libproxy] [--key-password-from-fsid] [-q,--quiet] [-Q,--queue-len longueur] [-s,--script script_vpnc] [-S,--script-tun] [-u,--user nom] [-V,--version] [-v,--verbose] [-x,--xmlconfig config] [--authgroup groupe] [--authenticate] [--cookieonly] [--printcookie] [--cafile fichier] [--disable-ipv6] [--dtls-ciphers liste] [--dtls12-ciphers liste] [--dtls-local-port port] [--dump-http-traffic] [--no-system-trust] [--pfs] [--no-dtls] [--no-http-keepalive] [--no-passwd] [--no-xmlpost] [--non-inter] [--passwd-on-stdin] [--protocol proto] [--token-mode mode] [--token-secret {secret[,compteur]|@fichier}] [--reconnect-timeout secondes] [--resolve hote:ip] [--sni hote] [--servercert sha1] [--useragent chaine] [--version-string chaine] [--local-hostname chaine] [--os chaine] [--server] [https://]hote[:port][/groupe]

DESCRIPTION

Le programme openconnect se connecte à des serveurs VPN utilisant les protocoles TLS/SSL, DTLS et ESP standards pour le transport des données.

Il a été initialement écrit pour prendre en charge les serveurs VPN Cisco "AnyConnect", et a depuis été étendu avec un support expérimental pour les serveurs VPN Juniper Network Connect (--protocol=nc), Junos/Ivanti Pulse (--protocol=pulse), PAN GlobalProtect (--protocol=gp), F5 Big-IP (--protocol=f5), Fortinet Fortigate (--protocol=fortinet), et Array Networks SSL VPN (--protocol=array).

La connexion se fait en deux phases. D'abord, il y a une connexion HTTPS simple sur laquelle l'utilisateur s'authentifie d'une manière ou d'une autre – en utilisant un certificat, un mot de passe ou SecurID, etc. Après authentification, l'utilisateur reçoit un cookie d'authentification qui peut être utilisé pour établir la véritable connexion VPN.

La deuxième phase utilise ce cookie pour se connecter à un tunnel via HTTPS, et les paquets de données peuvent être transmis sur la connexion résultante. Lorsque possible, un tunnel UDP est également configuré : AnyConnect utilise DTLS, tandis que Juniper et GlobalProtect utilisent ESP encapsulé dans UDP. Le tunnel UDP peut être désactivé avec --no-dtls, mais il est préféré lorsqu'il est correctement pris en charge par le serveur et le réseau pour des raisons de performance. (TCP fonctionne mal et de manière peu fiable sur les tunnels basés sur TCP ; voir http://sites.inka.de/~W1011/devel/tcp-tcp.html.)

OPTIONS

--config=FICHIER_CONFIG
Lit les options supplémentaires dans FICHIER_CONFIG avant de continuer à traiter les options de la ligne de commande. Le fichier doit contenir des options au format long telles qu'elles seraient acceptées en ligne de commande, mais sans les deux tirets préfixant "--". Les lignes vides, ou les lignes dont le premier caractère non-espacé est un caractère #, sont ignorées.

Toute option sauf l'option config peut être spécifiée dans le fichier.

-b,--background
Continue en arrière-plan après le démarrage.
--pid-file=FICHIER_PID
Sauvegarde le PID dans FICHIER_PID lors de la mise en arrière-plan.
-c,--certificate=CERT [,--mca-certificate=CERT]
Utilise le certificat client SSL CERT qui peut être soit un nom de fichier, soit, si OpenConnect a été compilé avec une version appropriée de GnuTLS, une URL PKCS#11.

L'option --mca-certificate définit le certificat secondaire pour l'authentification multi-certificats (selon la terminologie de Cisco, le certificat client SSL est appelé certificat "machine", et le second certificat est appelé certificat "utilisateur").

-e,--cert-expire-warning=JOURS
Affiche un avertissement lorsque le certificat client SSL a JOURS avant expiration.
-k,--sslkey=CLE [,--mca-key=CLE]
Utilise la clé privée SSL CLE qui peut être soit un nom de fichier, soit, si OpenConnect a été compilé avec une version appropriée de GnuTLS, une URL PKCS#11.

L'option --mca-key définit la clé privée du certificat secondaire (voir --mca-certificate).

-C,--cookie=COOKIE
Utilise le cookie d'authentification COOKIE.
--cookie-on-stdin
Lit le cookie depuis l'entrée standard.
-d,--deflate
Active toute compression, y compris les modes stateful. Par défaut, seuls les algorithmes de compression stateless sont activés.
-D,--no-deflate
Désactive toute compression.
--compression=MODE
Définit le mode de compression, où MODE est l'une des valeurs suivantes : stateless, none ou all.

Par défaut, seuls les algorithmes de compression stateless qui ne maintiennent pas d'état entre les paquets (et qui peuvent être utilisés sur les transports UDP) sont activés. En définissant le mode sur all, les algorithmes stateful (actuellement uniquement zlib deflate) peuvent être activés. Ou toute compression peut être désactivée en définissant le mode sur none.

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

--force-dpd=INTERVAL
Utilisez INTERVAL comme intervalle de détection de pair inactif (en secondes). Cela amènera le client à utiliser la DPD à l'intervalle spécifié même si le serveur ne l'a pas demandée, ou à un intervalle différent de celui demandé par le serveur.

Les mécanismes DPD varient selon le protocole et le transport (TLS ou DTLS/ESP), mais sont tous fonctionnellement similaires : ils permettent au client VPN ou au serveur VPN d'envoyer un signal au pair, demandant une réponse immédiate qui peut être utilisée pour confirmer que le lien entre les deux pairs fonctionne toujours.

-g,--usergroup=GROUP
Définissez le chemin URL de la connexion HTTPS initiale vers le serveur.

Avec certains protocoles, ce chemin peut fonctionner comme un groupe de connexion ou un domaine, d'où le nom de cette option. Par exemple, les invocations suivantes d'OpenConnect sont équivalentes :

openconnect --usergroup=loginPath vpn.server.com
openconnect https://vpn.server.com/loginPath
-F,--form-entry=FORM:OPTION[=VALUE]
Fournissez une entrée de formulaire d'authentification, où FORM et OPTION sont les identifiants du formulaire et du champ de saisie spécifique, et VALUE est la chaîne qui sera automatiquement remplie. Par exemple, le champ de nom d'utilisateur standard (également géré par l'option --user) pourrait également être fourni avec cette option ainsi : --form-entry main:username=joebloggs.

Si VALUE n'est pas spécifié, cette option amènera un champ de formulaire caché à être traité comme un champ de saisie de texte standard.

Cette option ne doit pas être utilisée pour entrer des mots de passe. --passwd-on-stdin doit être utilisé à cet effet. Non seulement cette option exposera la valeur du mot de passe via la ligne de commande du processus OpenConnect, mais contrairement à --passwd-on-stdin, cette option ne reconnaîtra pas le cas d'un mot de passe incorrect et ne cessera pas d'essayer de le saisir à plusieurs reprises.

-h,--help
Afficher le texte d'aide
--http-auth=METHODS
Utilisez uniquement les méthodes spécifiées pour l'authentification HTTP auprès d'un serveur. Par défaut, seules les authentifications Negotiate, NTLM et Digest sont activées. L'authentification Basic est également prise en charge, mais comme elle est non sécurisée, elle doit être explicitement activée. L'argument est une liste de méthodes séparées par des virgules à activer. Notez que l'ordre n'a pas d'importance : OpenConnect utilisera l'authentification Negotiate, NTLM, Digest et Basic dans cet ordre, si chacune est activée, quel que soit l'ordre spécifié dans la chaîne METHODS.
--external-browser=BROWSER
Définissez BROWSER comme l'exécutable utilisé par OpenConnect pour gérer le processus d'authentification avec les passerelles qui prennent en charge la méthode d'authentification single-sign-on-external-browser.
-i,--interface=IFNAME
Utilisez IFNAME pour l'interface tunnel
-l,--syslog
Une fois le tunnel établi, utilisez syslog pour les messages de progression ultérieurs
--timestamp
Ajouter un horodatage devant chaque message de progression
--passtos
Copiez le TOS / TCLASS du paquet de charge utile dans les paquets DTLS et ESP. Ceci n'est pas défini par défaut car cela peut divulguer des informations sur la charge utile (par exemple, en différenciant le trafic vocal/vidéo).
-U,--setuid=USER
Abandonnez les privilèges après la connexion, pour devenir l'utilisateur USER
--csd-user=USER
Abandonnez les privilèges pendant l'exécution du binaire ou du script trojan (CSD, TNCC ou HIP).
--csd-wrapper=SCRIPT
Exécutez SCRIPT à la place du binaire ou du script trojan.
--force-trojan=INTERVAL
Utilisez INTERVAL comme intervalle (en secondes) pour l'exécution répétée du binaire ou du script Trojan, en remplaçant l'intervalle par défaut et/ou celui défini par le serveur.
-m,--mtu=MTU
Demandez au serveur MTU comme MTU du tunnel.
--base-mtu=MTU
Indiquez MTU comme le MTU du chemin entre le client et le serveur sur le réseau non chiffré. Les serveurs plus récents calculeront automatiquement le MTU à utiliser sur le tunnel à partir de cette valeur.
-p,--key-password=PASS [,--mca-key-password=PASS]
Fournissez la phrase secrète pour le fichier de certificat, ou le code PIN SRK (System Root Key) pour TPM.

--mca-key-password fournit la phrase secrète pour le certificat secondaire (voir --mca-certificate).

-P,--proxy=PROXYURL
Utilisez un proxy HTTP ou SOCKS pour la connexion. Un nom d'utilisateur et un mot de passe peuvent être fournis dans l'URL donnée, et seront utilisés pour l'authentification. Si une authentification est requise mais qu'aucun identifiant n'est fourni, une authentification GSSAPI et NTLM automatique utilisant l'outil d'aide ntlm_auth de Samba peut être tentée.
--proxy-auth=METHODS
Utilisez uniquement les méthodes spécifiées pour l'authentification HTTP auprès d'un proxy. Par défaut, seules les authentifications Negotiate, NTLM et Digest sont activées. L'authentification Basic est également prise en charge, mais comme elle est non sécurisée, elle doit être explicitement activée. L'argument est une liste de méthodes séparées par des virgules à activer. Notez que l'ordre n'a pas d'importance : OpenConnect utilisera Negotiate, NTLM, Digest et Basic dans cet ordre, si chacune est activée, quel que soit l'ordre spécifié dans la chaîne METHODS.
--no-proxy
Désactiver l'utilisation du proxy
--libproxy
Utiliser libproxy pour configurer automatiquement le proxy (lorsqu'il est compilé avec le support de libproxy)
--key-password-from-fsid
La phrase secrète pour le fichier de certificat est générée automatiquement à partir du fsid du système de fichiers sur lequel il est stocké. Le fsid est obtenu à partir de l'appel système statvfs(2) ou statfs(2), selon le système d'exploitation. Sur un système Linux ou similaire avec GNU coreutils, le fsid utilisé par cette option doit être égal à la sortie de la commande : 
stat --file-system --printf=%i\\n $CERTIFICATE
Ce n'est pas le même que l'UUID 128 bits du système de fichiers.
-q,--quiet
Moins de sortie
-Q,--queue-len=LEN
Définir la limite de la file d'attente des paquets à LEN paquets. La valeur par défaut est 32. Une valeur élevée peut permettre une meilleure bande passante globale, mais au détriment de la latence. Si vous utilisez la voix sur IP ou d'autres trafics interactifs sur le VPN, vous ne voulez pas que ces paquets soient mis en file d'attente derrière des milliers d'autres gros paquets qui font partie d'un transfert groupé.

Cette option définit les tailles maximales des files d'attente de paquets entrants et sortants dans OpenConnect lui-même, qui contrôlent le nombre de paquets qui seront envoyés et reçus par lot, tout en affectant d'autres tampons tels que le tampon d'envoi de socket (SO_SNDBUF) pour les connexions réseau et le périphérique tunnel du système d'exploitation.

En fin de compte, la bonne taille pour une file d'attente est "juste assez de paquets pour qu'elle ne soit jamais complètement vide avant que d'autres ne lui soient poussés". Toute valeur supérieure introduit simplement du bufferbloat et une latence supplémentaire sans aucun bénéfice. Avec la valeur par défaut de 32, nous sommes capables de saturer un seul Gigabit Ethernet à partir de matériel modeste, ce qui est plus que suffisant pour la plupart des utilisateurs VPN.

Si OpenConnect est compilé avec le support de vhost-net, il ne sera utilisé que si la longueur de la file d'attente est définie à 16 ou plus. En effet, vhost-net introduit une légère latence supplémentaire, mais améliore considérablement la bande passante totale pour ceux qui utilisent des débits de trafic élevés. Il est donc logique de l'utiliser lorsque l'utilisateur a indiqué une préférence pour la bande passante plutôt que la latence, en augmentant la taille de la file d'attente.

-s,--script=SCRIPT
Invoquez SCRIPT pour configurer le réseau après la connexion. Sans cela, le routage et le service de noms risquent de ne pas fonctionner correctement. Le script doit être compatible avec vpnc-script, qui est fourni avec le client VPN "vpnc". Voir https://www.infradead.org/openconnect/vpnc-script.html pour plus d'informations. Cette version d'OpenConnect est configurée pour utiliser /etc/vpnc/vpnc-script par défaut.

Sur Windows, un répertoire relatif pour le script par défaut sera traité comme commençant depuis le répertoire à partir duquel l'exécutable openconnect s'exécute, plutôt que depuis le répertoire courant. Le script sera invoqué avec l'hôte de script basé sur la ligne de commande cscript.exe.

-S,--script-tun
Transmettez le trafic à un programme 'script' via un socket UNIX, au lieu d'un périphérique tun/tap du noyau. Cela permet au trafic IP VPN d'être géré entièrement dans l'espace utilisateur, par exemple par un programme qui utilise lwIP pour fournir un accès SOCKS au VPN.
--server=[https://]HOST[:PORT][/PATH]
Définissez le serveur VPN comme un simple HOST ou comme une URL contenant le HOST et éventuellement le numéro de PORT et le PATH ; avec certains protocoles, le chemin peut fonctionner comme un groupe de connexion ou un domaine, et il peut être spécifié de manière équivalente avec --usergroup.

Alternativement, définissez le serveur VPN comme argument de ligne de commande non optionnel.

-u,--user=NAME
Définissez le nom d'utilisateur de connexion à NAME
-V,--version
Afficher le numéro de version
-v,--verbose
Plus de sortie (peut être spécifié plusieurs fois pour une sortie supplémentaire)
-x,--xmlconfig=CONFIG
Fichier de configuration XML
--authgroup=GROUP
Sélectionnez le GROUP de la liste déroulante d'authentification ou de l'entrée de liste.

De nombreux VPN exigent une se

lection à partir d'une liste déroulante ou d'une liste lors du processus d'authentification. Cette sélection peut être connue sous le nom de authgroup (sur les VPN Cisco), realm (Juniper, Pulse, Fortinet), domain (F5), et gateway (GlobalProtect). Cette option tente de remplir automatiquement le champ spécifique au protocole approprié avec la valeur souhaitée.

--authenticate
S'authentifier auprès du VPN, afficher les informations nécessaires pour établir la connexion sous une forme qui peut être utilisée pour définir des variables d'environnement shell, puis quitter.

Lorsqu'il est appelé avec cette option, OpenConnect ne créera pas réellement la connexion VPN ni ne configurera d'interface tunnel, mais en cas de succès, il affichera quelque chose comme ceci sur stdout :

COOKIE='3311180634@13561856@1339425499@B315A0E29D16C6FD92EE...'
HOST='10.0.0.1'
CONNECT_URL='https://vpnserver.example.com'
FINGERPRINT='469bb424ec8835944d30bc77c77e8fc1d8e23a42'
RESOLVE='vpnserver.example.com:10.0.0.1'
Ainsi, vous pouvez invoquer openconnect en tant qu'utilisateur non privilégié (avec accès aux tokens PKCS#11 de l'utilisateur, etc.) pour l'authentification, puis invoquer openconnect séparément pour établir la connexion réelle en tant que root : 
eval `openconnect --authenticate https://vpnserver.example.com`;
[ -n ["$COOKIE"] ] && echo ["$COOKIE"] |
  sudo openconnect --cookie-on-stdin $CONNECT_URL --servercert $FINGERPRINT --resolve $RESOLVE

Les versions antérieures d'OpenConnect produisaient uniquement la variable HOST (contenant l'adresse numérique du serveur), et non les variables CONNECT_URL ou RESOLVE. Par la suite, nous avons découvert que les serveurs derrière des proxys peuvent ne pas répondre correctement sauf si le nom DNS correct est présent lors de la phase de connexion, et nous avons ajouté la prise en charge des protocoles VPN où le composant path de l'URL du serveur peut être significatif lors de la phase de connexion, ce qui a conduit à l'ajout de CONNECT_URL et RESOLVE, et à la recommandation de les utiliser comme décrit ci-dessus. Si vous n'êtes pas certain d'invoquer une version plus récente d'OpenConnect qui génère ces variables, utilisez la commande suivante (compatible avec la plupart des dérivés de shells Bourne) qui fonctionnera avec une version plus récente ou plus ancienne :

sudo openconnect --cookie-on-stdin ${CONNECT_URL:-$HOST} --servercert $FINGERPRINT ${RESOLVE:+--resolve=$RESOLVE}
--cookieonly
Récupérer et afficher le cookie uniquement ; ne pas se connecter (ceci est essentiellement un sous-ensemble de --authenticate).
--printcookie
Afficher le cookie sur stdout avant de se connecter (voir --authenticate pour la signification de ce cookie)
--cafile=FICHIER
Fichier CA supplémentaire pour la vérification du serveur. Par défaut, cela amène simplement OpenConnect à faire confiance à des certificats racines supplémentaires en plus de ceux qui sont approuvés par le système. Utilisez --no-system-trust pour empêcher OpenConnect de faire confiance aux autorités de certification par défaut du système.
--no-system-trust
Ne pas faire confiance aux autorités de certification par défaut du système. Si cette option est fournie, seules les autorités de certification fournies avec l'option --cafile, le cas échéant, seront automatiquement approuvées.
--disable-ipv6
Ne pas annoncer la capacité IPv6 au serveur
--dtls-ciphers=LISTE
Définir les chiffrements OpenSSL à prendre en charge pour DTLS
--dtls12-ciphers=LISTE
Définir les chiffrements OpenSSL pour le DTLS v1.2 de Cisco
--dtls-local-port=PORT
Utiliser PORT comme port local pour les datagrammes DTLS et UDP
--dump-http-traffic
Activer la sortie détaillée de toutes les requêtes HTTP et des corps de toutes les réponses reçues du serveur.
--pfs
Impose le Perfect Forward Secrecy (PFS). Cela garantit que si la clé à long terme du serveur est compromise, toutes les clés de session établies avant la compromission ne seront pas affectées. Si cette option est fournie et que le serveur ne prend pas en charge le PFS dans le canal TLS, la connexion échouera.

Le PFS est disponible dans les versions 9.1(2) et supérieures d'ASA Cisco ; une suite de chiffrement appropriée peut devoir être activée manuellement par l'administrateur à l'aide du paramètre ssl encryption.

--no-dtls
Désactiver DTLS et ESP
--no-http-keepalive
La version 8.2.2.5 du logiciel Cisco ASA contient un bug où elle oublie le certificat SSL du client lorsque les connexions HTTP sont réutilisées pour plusieurs requêtes. Jusqu'à présent, cela n'a été observé que lors de la connexion initiale, où le serveur renvoie une réponse de redirection HTTP/1.0 avec une directive explicite Connection: Keep-Alive. OpenConnect à partir de la v2.22 contient une solution de contournement inconditionnelle pour cela, qui consiste à ne jamais obéir à cette directive après une réponse HTTP/1.0.

Cependant, l'équipe de support de Cisco n'a donné aucune réponse compétente au rapport de bug et nous ne savons pas dans quelles autres circonstances leur bug pourrait se manifester. Donc, cette option existe pour désactiver TOUTE réutilisation des sessions HTTP et provoquer une nouvelle connexion pour chaque requête. Si votre serveur semble ne pas reconnaître votre certificat, essayez cette option. Si cela fait une différence, veuillez signaler ces informations à la liste de diffusion openconnect-devel@lists.infradead.org.

--no-passwd
Ne jamais tenter l'authentification par mot de passe (ou SecurID).
--no-external-auth
Empêcher OpenConnect d'annoncer au serveur qu'il prend en charge tout type de mode d'authentification qui nécessite un navigateur externe.

Certains serveurs forceront le client à utiliser un tel mode d'authentification si le client l'annonce, mais se rabattront vers un mode d'authentification plus "scriptable" si le client ne semble pas le prendre en charge.

--no-xmlpost
Ne pas tenter d'envoyer une requête d'authentification/configuration XML au serveur ; utiliser plutôt l'ancienne méthode GET utilisée par les anciens clients et serveurs.

Cette option est un filet de sécurité temporaire, pour pallier des problèmes de compatibilité potentiels avec le code qui se rabat automatiquement sur l'ancienne méthode. Elle fait en sorte qu'OpenConnect se comporte davantage comme les anciennes versions (4.08 et inférieures). Si vous constatez que vous devez utiliser cette option, vous avez trouvé un bug dans OpenConnect. Veuillez consulter https://www.infradead.org/openconnect/mail.html et le signaler aux développeurs.

--allow-insecure-crypto
Les anciens chiffrements 3DES et RC4, tous deux défectueux, sont peu sûrs ; nous les désactivons explicitement par défaut. Cependant, certains serveurs VPN encore en utilisation ne peuvent pas faire mieux.

Cette option permet l'utilisation de ces chiffrements peu sûrs, ainsi que l'utilisation de SHA1 pour la validation des certificats serveur.

--non-inter
Ne pas attendre d'entrée utilisateur ; quitter si elle est requise.
--passwd-on-stdin
Lire le mot de passe depuis l'entrée standard
--protocol=PROTO
Sélectionner le protocole VPN PROTO à utiliser pour la connexion. Les protocoles pris en charge sont anyconnect pour Cisco AnyConnect (par défaut), nc pour un support expérimental de Juniper Network Connect (également pris en charge par la plupart des serveurs Junos/Ivanti Pulse), pulse pour un support expérimental de Junos/Ivanti Pulse, gp pour un support expérimental de PAN GlobalProtect, f5 pour un support expérimental de F5 Big-IP, fortinet pour un support expérimental de Fortinet Fortigate, et array pour un support expérimental de Array Networks SSL VPN.

Consultez https://www.infradead.org/openconnect/protocols.html pour plus de détails sur les fonctionnalités et les lacunes des protocoles individuels.

OpenConnect ne prend pas encore en charge toutes les options d'authentification utilisées par Pulse, ni le Host Checker/TNCC avec Pulse. Si votre VPN Junos/Ivanti Pulse n'est pas encore pris en charge avec --protocol=pulse, alors --protocol=nc peut être une option de repli utile.

--token-mode=MODE
Activer la génération de mot de passe à usage unique à l'aide de l'algorithme MODE. --token-mode=rsa appellera libstoken pour générer un code token RSA SecurID, --token-mode=totp générera un mot de passe basé sur le temps RFC 6238, et --token-mode=hotp générera un mot de passe basé sur HMAC RFC 4226. Les tokens Yubikey qui génèrent des codes OATH en matériel sont pris en charge avec --token-mode=yubioath. --token-mode=oidc utilisera le token OpenIDConnect fourni comme jeton porteur RFC 6750.
--token-secret={ SECRET[,COMPTEUR] | @NOMFICHIER }
Le secret à utiliser lors de la génération de mots de passe à usage unique/codes de vérification. Les secrets TOTP/HOTP encodés en Base 32 peuvent être utilisés en spécifiant "base32:" au début du secret, et pour les secrets HOTP, le compteur de tokens peut être spécifié après une virgule.

Les secrets RSA SecurID peuvent être spécifiés sous forme d'URI Android/iPhone ou d'une chaîne CTF numérique brute (avec ou sans tirets).

Pour Yubikey OATH, le secret du token spécifie le nom de l'identifiant à utiliser. S'il n'est pas fourni, le premier identifiant OATH trouvé sur l'appareil sera utilisé.

Pour OIDC, le secret est le jeton porteur à utiliser.

NOMFICHIER, s'il est spécifié, peut contenir l'une des chaînes ci-dessus. Ou, il peut contenir une graine XML SecurID (SDTID).

Si cette option est omise et que --token-mode est "rsa", libstoken essaiera d'utiliser la graine du token logiciel sauvegardée dans ~/.stokenrc par la commande "stoken import".

--reconnect-timeout=SECONDES
Après déconnexion ou détection de pair défectueux, continuer à essayer de se reconnecter pendant SECONDES. La valeur par défaut est 300 secondes, ce qui signifie qu'openconnect peut récupérer une connexion VPN après une interruption réseau temporaire durant

NAME

openconnect — multiprotocol VPN client

SYNOPSIS

openconnect [options] [server]

DESCRIPTION

OpenConnect is a VPN client that supports the Cisco AnyConnect VPN client, GlobalProtect, Juniper's Junos Pulse, and the ocserv (OpenConnect SSL VPN server) protocol.

This manual page details the options available for the OpenConnect client.

OPTIONS

--authnone
Do not prompt for authentication; use existing cookie/token.
--authtoken=TOKEN
Use TOKEN as the authentication token.
--authuser=USER
Use USER as the username for authentication.
--bash-completion
Output the bash completion script.
--binary-growth
Report arbitrary server binary growth.
--ca-cert-file=FILE
Use FILE as the CA certificate bundle.
--ca-cert-hash=HASH
Accept server's SSL certificate only if it matches the provided fingerprint. This option implies --no-system-trust, and may be specified multiple times in order to accept multiple possible fingerprints.

The allowed fingerprint types are SHA1, SHA256, and PIN-SHA256. They are distinguished by the 'sha1:', 'sha256:' and 'pin-sha256:' prefixes to the encoded hash. The first two are custom identifiers providing hex encoding of the peer's public key, while 'pin-sha256:' is the RFC7469 key PIN, which utilizes base64 encoding. To ease certain testing use-cases, a partial match of the hash will also be accepted, if it is at least 4 characters past the prefix.

--ciphers=CIPHER-LIST
Use CIPHER-LIST as the list of SSL ciphers to use.
--cookie-timeout=SECONDS
Set the cookie timeout to SECONDS seconds. The default is up to 300 seconds.
--csd-wrapper=PROG
Use PROG as the wrapper program for the Cisco Secure Desktop (CSD) component.
--daemon
Run as a daemon in the background.
--disable-http-keepalive
Disable HTTP keepalive.
--disable-ipv6
Disable IPv6 support.
--enable-http-1.0
Use HTTP/1.0 instead of HTTP/1.1.
--explicit-exit-notify
Explicitly notify the server of client exit.
--force-proxy-auth
Force proxy authentication, even if not required.
--gateway-cert-hash=HASH
Accept gateway's SSL certificate only if it matches the provided fingerprint. This option implies --no-system-trust, and may be specified multiple times in order to accept multiple possible fingerprints.

The allowed fingerprint types are SHA1, SHA256, and PIN-SHA256. They are distinguished by the 'sha1:', 'sha256:' and 'pin-sha256:' prefixes to the encoded hash. The first two are custom identifiers providing hex encoding of the peer's public key, while 'pin-sha256:' is the RFC7469 key PIN, which utilizes base64 encoding. To ease certain testing use-cases, a partial match of the hash will also be accepted, if it is at least 4 characters past the prefix.

--help
Show help message.
--http-proxy=HOST[:PORT]
Use HOST and optional PORT as an HTTP proxy.
--json-status
Output status information in JSON format.
--json-status-file=FILE
Output status information in JSON format to FILE.
--keepalive-interval=SECONDS
Set the keepalive interval to SECONDS seconds.
--key-file=FILE
Use FILE as the client's private key.
--local-hostname=STRING
Use STRING as 'X-CSTP-Hostname:' field value in HTTP header. For example --local-hostname 'mypc', will advertise the value 'mypc' as the suggested hostname to point to the provided IP address.
--login-timeout=SECONDS
Set the login timeout to SECONDS seconds. The default is up to 300 seconds.
--no-cert-check
Do not check the server's certificate.
--no-dns
Disable DNS resolution.
--no-system-trust
Do not trust the system's CA certificate store.
--os=STRING
OS type to report to gateway. Recognized values are: linux, linux-64, win, mac-intel, android, apple-ios. Reporting a different OS type may affect the dynamic access policy (DAP) applied to the VPN session. If the gateway requires CSD, it will also cause the corresponding CSD trojan binary to be downloaded, so you may need to use --csd-wrapper if this code is not executable on the local machine.
--password-stdin
Read the password from standard input.
--pppd-compress
Enable compression for the PPP connection.
--pppd-use-pty
Use a pseudo-terminal for the PPP connection.
--prefer-mac-compat
Prefer macOS compatibility.
--private-key-password=PASSWORD
Use PASSWORD to decrypt the private key.
--proxy-auth=USER:PASS
Use USER and PASS for proxy authentication.
--script-tun
Use the vpnc-script to configure the tunnel.
--servercert=HASH
Accept server's SSL certificate only if it matches the provided fingerprint. This option implies --no-system-trust, and may be specified multiple times in order to accept multiple possible fingerprints.

The allowed fingerprint types are SHA1, SHA256, and PIN-SHA256. They are distinguished by the 'sha1:', 'sha256:' and 'pin-sha256:' prefixes to the encoded hash. The first two are custom identifiers providing hex encoding of the peer's public key, while 'pin-sha256:' is the RFC7469 key PIN, which utilizes base64 encoding. To ease certain testing use-cases, a partial match of the hash will also be accepted, if it is at least 4 characters past the prefix.

--service-name=NAME
Use NAME as the service name for the connection.
--session-cookie-timeout=SECONDS
Set the session cookie timeout to SECONDS seconds.
--sha256
Use SHA256 for certificate hashing.
--silent
Run in silent mode, suppressing most output.
--sni=HOST
When creating new TLS connections, always present the hostname HOST as the SNI (Server Name Indication) in place of the correct hostname, which will still be sent in the HTTP 'Host:' header, and expect the peer's certificate to match the SNI rather than the correct hostname. This may be useful for Domain Fronting, by which some filtered or censored Internet connections can be bypassed.

Note that sending different values for the SNI and 'Host:' header violates HTTP standards and is prevented by many cloud hosting providers.

--socks-proxy=HOST[:PORT]
Use HOST and optional PORT as a SOCKS proxy.
--ssh-agent-prog=PROG
Use PROG as the ssh-agent program.
--timestamp-log
Add timestamps to log messages.
--token-mode=MODE
Set the token mode to MODE. Recognized values are: password, rsa-token, gcd-token, otp, pkcs11.
--usercert=FILE
Use FILE as the client's certificate.
--useragent=STRING
Use STRING as 'User-Agent:' field value in HTTP header.

Some VPN servers may require specific values matching those sent by proprietary VPN clients in order to successfully authenticate or connect. For example, when connecting to a Cisco VPN server, --useragent 'AnyConnect Windows 4.10.06079' or --useragent 'Cisco AnyConnect VPN Agent for Windows 2.2.0133', or when connecting to a Pulse server, --useragent 'Pulse-Secure/9.1.11.6725'.

--version-string=STRING
Use STRING as the software version reported to the head end. (e.g. --version-string '2.2.0133')
--vpn-plugin=PLUGIN
Use PLUGIN as the VPN plugin.
--xml-status
Output status information in XML format.
--xml-status-file=FILE
Output status information in XML format to FILE.
--resolve=HOST:IP
Automatically resolve the hostname HOST to IP instead of using the normal resolver to look it up.

SIGNALS

In the data phase of the connection, the following signals are handled:

SIGINT / SIGTERM
performs a clean shutdown by logging the session off, disconnecting from the gateway, and running the vpnc-script to restore the network configuration.
SIGHUP
disconnects from the gateway and runs the vpnc-script, but does not log the session off; this allows for reconnection later using --cookie.
SIGUSR1
writes progress message with detailed connection information and statistics.
SIGUSR2
forces an immediate disconnection and reconnection; this can be used to quickly recover from LAN IP address changes.
