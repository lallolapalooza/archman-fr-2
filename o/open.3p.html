OPEN(3P) Manuel du programmeur POSIX OPEN(3P)

PROLOGUE

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consultez la page de manuel Linux correspondante pour les détails du comportement Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

open, openat — ouvrir un fichier

SYNOPIS

#include <sys/stat.h>
#include <fcntl.h>
int open(const char *chemin, int flags_ouverture, ...);
int openat(int fd, const char *chemin, int flags_ouverture, ...);

DESCRIPTION

La fonction open() établit la connexion entre un fichier et un descripteur de fichier. Elle crée une description de fichier ouvert qui se réfère à un fichier et un descripteur de fichier qui se réfère à cette description de fichier ouvert. Le descripteur de fichier est utilisé par d'autres fonctions d'E/S pour se référer à ce fichier. L'argument chemin pointe vers un nom de fichier.

La fonction open() retourne un descripteur de fichier pour le fichier nommé, alloué comme décrit dans la Section 2.14, Allocation des descripteurs de fichiers. La description de fichier ouvert est nouvelle, et donc le descripteur de fichier ne la partagera avec aucun autre processus dans le système. Le drapeau FD_CLOEXEC du descripteur de fichier associé au nouveau descripteur de fichier sera effacé, sauf si le drapeau O_CLOEXEC est défini dans flags_ouverture.

Le décalage de fichier utilisé pour marquer la position actuelle dans le fichier sera défini au début du fichier.

Les drapeaux d'état de fichier et les modes d'accès au fichier de la description de fichier ouvert seront définis conformément à la valeur de flags_ouverture.

Les valeurs pour flags_ouverture sont construites par un OU inclusif au niveau du bit des drapeaux de la liste suivante, définis dans <fcntl.h>. Les applications doivent spécifier exactement un des cinq premiers (modes d'accès fichier) ci-dessous dans la valeur de flags_ouverture:

O_EXEC
Ouverture en exécution uniquement (fichiers non-répertoires). Le résultat n'est pas spécifié si ce drapeau est appliqué à un répertoire.
O_RDONLY
Ouverture en lecture seule.
O_RDWR
Ouverture en lecture et écriture. Le résultat est indéfini si ce drapeau est appliqué à un FIFO.
O_SEARCH
Ouverture d'un répertoire en recherche uniquement. Le résultat n'est pas spécifié si ce drapeau est appliqué à un fichier non-répertoire.
O_WRONLY
Ouverture en écriture uniquement.

Toute combinaison des drapeaux suivants peut être utilisée :

O_APPEND
S'il est défini, le décalage de fichier sera positionné à la fin du fichier avant chaque écriture.
O_CLOEXEC
S'il est défini, le drapeau FD_CLOEXEC pour le nouveau descripteur de fichier sera défini.
O_CREAT
Si le fichier existe, ce drapeau n'a aucun effet sauf comme noté sous O_EXCL ci-dessous. Sinon, si O_DIRECTORY n'est pas défini, le fichier sera créé en tant que fichier régulier ; l'ID utilisateur du fichier sera défini à l'ID utilisateur effectif du processus ; l'ID de groupe du fichier sera défini à l'ID de groupe du répertoire parent du fichier ou à l'ID de groupe effectif du processus ; et les bits d'autorisation d'accès (voir <sys/stat.h>) du mode de fichier seront définis à la valeur de l'argument suivant l'argument flags_ouverture, pris comme type mode_t, modifiés comme suit : une opération ET au niveau du bit est effectuée sur les bits du mode de fichier et les bits correspondants du complément du masque de création de mode de fichier du processus. Ainsi, tous les bits du mode de fichier dont le bit correspondant dans le masque de création de mode de fichier est défini sont effacés. Lorsque des bits autres que les bits d'autorisation de fichier sont définis, l'effet n'est pas spécifié. L'argument suivant l'argument flags_ouverture n'affecte pas si le fichier est ouvert en lecture, écriture, ou les deux. Les implémentations doivent fournir un moyen d'initialiser l'ID de groupe du fichier à l'ID de groupe du répertoire parent. Les implémentations peuvent, mais ne sont pas obligées, fournir un moyen défini par l'implémentation pour initialiser l'ID de groupe du fichier à l'ID de groupe effectif du processus appelant.
O_DIRECTORY
Si chemin résout en un fichier non-répertoire, échouer et définir errno à [ENOTDIR].
O_DSYNC
Les opérations d'E/S d'écriture sur le descripteur de fichier doivent s'achever comme défini par l'achèvement de l'intégrité des données d'E/S synchronisées.
O_EXCL
Si O_CREAT et O_EXCL sont définis, open() échouera si le fichier existe. La vérification de l'existence du fichier et la création du fichier s'il n'existe pas seront atomiques par rapport aux autres threads exécutant open() nommant le même nom de fichier dans le même répertoire avec O_EXCL et O_CREAT définis. Si O_EXCL et O_CREAT sont définis, et que chemin nomme un lien symbolique, open() échouera et définira errno à [EEXIST], indépendamment du contenu du lien symbolique. Si O_EXCL est défini et O_CREAT n'est pas défini, le résultat est indéfini.
O_NOCTTY
S'il est défini et que chemin identifie un périphérique terminal, open() ne doit pas faire du périphérique terminal le terminal de contrôle du processus. Si chemin n'identifie pas un périphérique terminal, O_NOCTTY sera ignoré.
O_NOFOLLOW
Si chemin nomme un lien symbolique, échouer et définir errno à [ELOOP].
O_NONBLOCK
Lors de l'ouverture d'un FIFO avec O_RDONLY ou O_WRONLY défini :
*
Si O_NONBLOCK est défini, une ouverture open() en lecture seule doit retourner sans délai. Une ouverture open() en écriture seule doit retourner une erreur si aucun processus n'a actuellement le fichier ouvert en lecture.
*
Si O_NONBLOCK est effacé, une ouverture open() en lecture seule doit bloquer le thread appelant jusqu'à ce qu'un thread ouvre le fichier en écriture. Une ouverture open() en écriture seule doit bloquer le thread appelant jusqu'à ce qu'un thread ouvre le fichier en lecture.

Lors de l'ouverture d'un fichier spécial de bloc ou de caractère qui supporte les ouvertures non bloquantes :

*
Si O_NONBLOCK est défini, la fonction open() doit retourner sans bloquer pour que le périphérique soit prêt ou disponible. Le comportement ultérieur du périphérique est spécifique au périphérique.
*
Si O_NONBLOCK est effacé, la fonction open() doit bloquer le thread appelant jusqu'à ce que le périphérique soit prêt ou disponible avant de retourner.

Sinon, le drapeau O_NONBLOCK ne doit pas causer d'erreur, mais il n'est pas spécifié si les drapeaux d'état du fichier incluront le drapeau O_NONBLOCK.

O_RSYNC
Les opérations d'E/S de lecture sur le descripteur de fichier doivent s'achever au même niveau d'intégrité que spécifié par les drapeaux O_DSYNC et O_SYNC. Si O_DSYNC et O_RSYNC sont tous deux définis dans flags_ouverture, toutes les opérations d'E/S sur le descripteur de fichier doivent s'achever comme défini par l'achèvement de l'intégrité des données d'E/S synchronisées. Si O_SYNC et O_RSYNC sont tous deux définis dans les drapeaux, toutes les opérations d'E/S sur le descripteur de fichier doivent s'achever comme défini par l'achèvement de l'intégrité du fichier d'E/S synchronisées.
O_SYNC
Les opérations d'E/S d'écriture sur le descripteur de fichier doivent s'achever comme défini par l'achèvement de l'intégrité du fichier d'E/S synchronisées.

Le drapeau O_SYNC doit être supporté pour les fichiers réguliers, même si l'option Entrées et Sorties Synchronisées n'est pas supportée.

O_TRUNC
Si le fichier existe et est un fichier régulier, et que le fichier est ouvert avec succès avec O_RDWR ou O_WRONLY, sa longueur sera tronquée à 0, et le mode et le propriétaire resteront inchangés. Il n'aura aucun effet sur les fichiers spéciaux FIFO ou les fichiers de périphériques terminaux. Son effet sur d'autres types de fichiers est défini par l'implémentation. Le résultat de l'utilisation de O_TRUNC sans O_RDWR ni O_WRONLY est indéfini.
O_TTY_INIT
Si chemin identifie un périphérique terminal autre qu'un pseudo-terminal, que le périphérique n'est pas déjà ouvert par un processus, et que O_TTY_INIT est défini dans flags_ouverture

g ou O_TTY_INIT a la valeur zéro, open() doit définir tout paramètre de terminal non standard de la structure termios dans un état qui fournit un comportement conforme ; voir le volume des Définitions de base de POSIX.1‐2017, Section 11.2, Paramètres pouvant être définis. Il n'est pas précisé si O_TTY_INIT a un effet si le périphérique est déjà ouvert dans un processus quelconque. Si path identifie le côté esclave d'un pseudo-terminal qui n'est pas déjà ouvert dans un processus quelconque, open() doit définir tout paramètre de terminal non standard de la structure termios dans un état qui fournit un comportement conforme, que O_TTY_INIT soit défini ou non. Si path n'identifie pas un périphérique de terminal, O_TTY_INIT doit être ignoré.

Si O_CREAT et O_DIRECTORY sont définis et que le mode d'accès demandé n'est ni O_WRONLY ni O_RDWR, le résultat n'est pas précisé.

Si O_CREAT est défini et que le fichier n'existait pas auparavant, en cas de succès, open() doit marquer pour mise à jour les horodatages du dernier accès aux données, de la dernière modification des données et du dernier changement de statut du fichier, ainsi que les horodatages de la dernière modification des données et du dernier changement de statut du répertoire parent.

Si O_TRUNC est défini et que le fichier existait auparavant, en cas de succès, open() doit marquer pour mise à jour les horodatages de la dernière modification des données et du dernier changement de statut du fichier.

Si les indicateurs O_SYNC et O_DSYNC sont tous deux définis, l'effet est le même que si seul l'indicateur O_SYNC était défini.

Si path fait référence à un fichier STREAMS, oflag peut être construit à partir de O_NONBLOCK OR'é avec soit O_RDONLY, O_WRONLY, soit O_RDWR. D'autres valeurs d'indicateur ne sont pas applicables aux périphériques STREAMS et n'ont aucun effet sur eux. La valeur O_NONBLOCK affecte le fonctionnement des pilotes STREAMS et de certaines fonctions appliquées aux descripteurs de fichiers associés aux fichiers STREAMS. Pour les pilotes STREAMS, l'implémentation de O_NONBLOCK est spécifique au périphérique.

L'application doit s'assurer qu'elle spécifie l'indicateur O_TTY_INIT lors de la première ouverture d'un périphérique de terminal depuis le démarrage du système ou depuis que le périphérique a été fermé par le processus qui le détenait en dernier. L'application n'a pas besoin de spécifier l'indicateur O_TTY_INIT lors de l'ouverture de pseudo-terminaux. Si path nomme le côté maître d'un périphérique pseudo-terminal, il n'est pas précisé si open() verrouille le côté esclave de manière à ce qu'il ne puisse pas être ouvert. Les applications conformes doivent appeler unlockpt() avant d'ouvrir le côté esclave.

La plus grande valeur pouvant être représentée correctement dans un objet de type off_t doit être définie comme le maximum de décalage dans la description du fichier ouvert.

La fonction openat() doit être équivalente à la fonction open() sauf dans le cas où path spécifie un chemin relatif. Dans ce cas, le fichier à ouvrir est déterminé par rapport au répertoire associé au descripteur de fichier fd au lieu du répertoire de travail courant. Si le mode d'accès de la description du fichier ouvert associée au descripteur de fichier n'est pas O_SEARCH, la fonction doit vérifier si les recherches de répertoires sont autorisées en utilisant les permissions actuelles du répertoire sous-jacent au descripteur de fichier. Si le mode d'accès est O_SEARCH, la fonction ne doit pas effectuer la vérification.

Le paramètre oflag et le quatrième paramètre optionnel correspondent exactement aux paramètres de open().

Si openat() est appelée avec la valeur spéciale AT_FDCWD dans le paramètre fd, le répertoire de travail courant doit être utilisé et le comportement sera identique à un appel à open().

VALEUR DE RETOUR

En cas de succès, ces fonctions doivent ouvrir le fichier et renvoyer un entier non négatif représentant le descripteur de fichier. Sinon, ces fonctions doivent renvoyer -1 et définir errno pour indiquer l'erreur. Si -1 est renvoyé, aucun fichier ne doit être créé ou modifié.

ERREURS

Ces fonctions doivent échouer si :

EACCES
La permission de recherche est refusée sur un composant du préfixe du chemin, ou le fichier existe et les permissions spécifiées par oflag sont refusées, ou le fichier n'existe pas et la permission d'écriture est refusée pour le répertoire parent du fichier à créer, ou O_TRUNC est spécifié et la permission d'écriture est refusée.
EEXIST
O_CREAT et O_EXCL sont définis, et le fichier nommé existe.
EINTR
Un signal a été intercepté pendant open().
EINVAL
L'implémentation ne prend pas en charge les E/S synchronisées pour ce fichier.
EIO
L'argument path nomme un fichier STREAMS et un blocage ou une erreur s'est produit pendant open().
EISDIR
Le fichier nommé est un répertoire et oflag inclut O_WRONLY ou O_RDWR, ou inclut O_CREAT sans O_DIRECTORY.
ELOOP
Une boucle existe dans les liens symboliques rencontrés lors de la résolution de l'argument path, ou O_NOFOLLOW a été spécifié et l'argument path nomme un lien symbolique.
EMFILE
Tous les descripteurs de fichiers disponibles pour le processus sont actuellement ouverts.
ENAMETOOLONG

La longueur d'un composant d'un nom de fichier est supérieure à {NAME_MAX}.
ENFILE
Le nombre maximum de fichiers autorisés est actuellement ouvert dans le système.
ENOENT
O_CREAT n'est pas défini et un composant de path ne nomme pas un fichier existant, ou O_CREAT est défini et un composant du préfixe de chemin de path ne nomme pas un fichier existant, ou path pointe vers une chaîne vide.
ENOENT ou ENOTDIR

O_CREAT est défini, et l'argument path contient au moins un caractère différent de <slash> et se termine par un ou plusieurs <slash> de fin. Si path sans les <slash> de fin nomme un fichier existant, une erreur [ENOENT] ne doit pas se produire.
ENOSR
L'argument path nomme un fichier basé sur STREAMS et le système ne peut pas allouer de STREAM.
ENOSPC
Le répertoire ou le système de fichiers qui contiendrait le nouveau fichier ne peut pas être étendu, le fichier n'existe pas et O_CREAT est spécifié.
ENOTDIR
Un composant du préfixe du chemin nomme un fichier existant qui n'est ni un répertoire ni un lien symbolique vers un répertoire ; ou O_CREAT et O_EXCL ne sont pas spécifiés, l'argument path contient au moins un caractère différent de <slash> et se termine par un ou plusieurs <slash> de fin, et le dernier composant du nom de fichier nomme un fichier existant qui n'est ni un répertoire ni un lien symbolique vers un répertoire ; ou O_DIRECTORY a été spécifié et l'argument path aboutit à un fichier qui n'est pas un répertoire.
ENXIO
O_NONBLOCK est défini, le fichier nommé est un FIFO, O_WRONLY est défini, et aucun processus n'a le fichier ouvert en lecture.
ENXIO
Le fichier nommé est un fichier spécial caractère ou spécial bloc, et le périphérique associé à ce fichier spécial n'existe pas.
EOVERFLOW
Le fichier nommé est un fichier régulier et la taille du fichier ne peut pas être représentée correctement dans un objet de type off_t.
EROFS
Le fichier nommé réside sur un système de fichiers en lecture seule et soit O_WRONLY, O_RDWR, O_CREAT (si le fichier n'existe pas), soit O_TRUNC est défini dans l'argument oflag.

La fonction openat() doit échouer si :

EACCES
Le mode d'accès de la description du fichier ouvert associée à fd n'est pas O_SEARCH et les permissions du répertoire sous-jacent à fd ne permettent pas les recherches de répertoires.
EBADF
L'argument path ne spécifie pas un chemin absolu et l'argument fd n'est ni AT_FDCWD ni un descripteur de fichier valide ouvert en lecture ou en recherche.
ENOTDIR
L'argument path n'est pas un chemin absolu et fd est un descripteur de fichier associé à un fichier non répertoire.

Ces fonctions peuvent échouer si :

EAGAIN
L'argument path nomme le côté esclave d'un périphérique pseudo-terminal qui est verrouillé.
EINVAL
La valeur de l'argument oflag n'est pas valide.
ELOOP
Plus de {SYMLOOP_MAX} liens symboliques ont été rencontrés lors de la résolution de l'argument path.
ENAMETOOLONG

La longueur d'un nom de fichier dépasse {PATH_MAX}, ou la résolution du nom de fichier d'un lien symbolique a produit un résultat intermédiaire dont la longueur dépasse {PATH_MAX}.
ENOMEM
L'argument path nomme un fichier STREAMS et le système ne peut pas allouer de ressources.
EOPNOTSUPP
L'argument path nomme un socket.
ETXTBSY
Le fichier est un fichier de procédure pure (texte partagé) qui est en cours d'exécution et oflag est O_WRONLY ou O_RDWR.

EXEMPLES

Ouverture d'un Fichier en Écriture par le Propriétaire

L'exemple suivant ouvre le fichier /tmp/file, soit en le créant (s'il n'existe pas déjà), soit en le tronquant

En tronquant sa longueur à 0 (s'il existe). Dans le premier cas, si l'appel crée un nouveau fichier, les bits d'autorisation d'accès dans le mode de fichier du fichier sont définis pour permettre la lecture et l'écriture par le propriétaire, et pour permettre la lecture uniquement par les membres du groupe et les autres.

Si l'appel à open() réussit, le fichier est ouvert en écriture.

#include <fcntl.h>
...
int fd;
mode_t mode = S_IRUSR | S_IWUSR | S_IRGRP | S_IROTH;
char *pathname = "/tmp/file";
...
fd = open(pathname, O_WRONLY | O_CREAT | O_TRUNC, mode);
...

Ouverture d'un Fichier avec Vérification d'Existence

L'exemple suivant utilise la fonction open() pour tenter de créer le fichier LOCKFILE et de l'ouvrir en écriture. Comme la fonction open() spécifie le drapeau O_EXCL, l'appel échoue si le fichier existe déjà. Dans ce cas, le programme suppose que quelqu'un d'autre met à jour le fichier de mots de passe et se termine.

#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#define LOCKFILE "/etc/ptmp"
...
int pfd; /* Entier pour le descripteur de fichier retourné par l'appel open(). */
...
if ((pfd = open(LOCKFILE, O_WRONLY | O_CREAT | O_EXCL,
    S_IRUSR | S_IWUSR | S_IRGRP | S_IROTH)) == -1)
{
    fprintf(stderr, "Impossible d'ouvrir /etc/ptmp. Réessayez plus tard.\n");
    exit(1);
}
...

Ouverture d'un Fichier en Écriture

L'exemple suivant ouvre un fichier en écriture, créant le fichier s'il n'existe pas déjà. Si le fichier existe, le système tronque le fichier à zéro octet.

#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#define LOCKFILE "/etc/ptmp"
...
int pfd;
char pathname[PATH_MAX+1];
...
if ((pfd = open(pathname, O_WRONLY | O_CREAT | O_TRUNC,
    S_IRUSR | S_IWUSR | S_IRGRP | S_IROTH)) == -1)
{
    perror("Impossible d'ouvrir le fichier de sortie\n"); exit(1);
}
...

UTILISATION DES APPLICATIONS

POSIX.1‐2008 n'exige pas que les paramètres du terminal soient automatiquement définis à un état quelconque lors de la première ouverture, ni qu'ils soient réinitialisés après la dernière fermeture. Il est possible qu'une application non conforme laisse un périphérique terminal dans un état où le processus suivant utilisant ce périphérique le trouve dans un état non conforme, mais n'ait aucun moyen de le déterminer. Pour s'assurer que le périphérique est défini dans un état initial conforme, les applications qui effectuent une première ouverture d'un terminal (autre qu'un pseudo-terminal) devraient le faire en utilisant le drapeau O_TTY_INIT pour définir les paramètres associés au terminal dans un état conforme.

Sauf indication contraire dans ce volume de POSIX.1‐2017, les drapeaux autorisés dans oflag ne sont pas mutuellement exclusifs et n'importe quel nombre d'entre eux peut être utilisé simultanément. Toutes les combinaisons de drapeaux n'ont pas de sens. Par exemple, l'utilisation de O_SEARCH | O_CREAT ouvrira avec succès un répertoire préexistant pour la recherche, mais s'il n'existe aucun fichier portant ce nom, il n'est pas spécifié si un fichier régulier sera créé. De même, si un descripteur de fichier non-répertoire est retourné avec succès, il n'est pas spécifié si ce descripteur aura des autorisations d'exécution comme avec O_EXEC (notez qu'il n'est pas spécifié si O_EXEC et O_SEARCH ont la même valeur).

RATIONALE

Certaines implémentations permettent d'ouvrir des FIFO avec O_RDWR. Comme les FIFO pourraient être implémentées d'autres manières, et comme deux descripteurs de fichiers peuvent être utilisés pour le même effet, cette possibilité est laissée indéfinie.

Voir getgroups() concernant le groupe d'un fichier nouvellement créé.

L'utilisation de open() pour créer un fichier régulier est préférable à l'utilisation de creat(), car cette dernière est redondante et n'est incluse que pour des raisons historiques.

L'utilisation du drapeau O_TRUNC sur les FIFO et les répertoires (les pipes ne peuvent pas être ouverts avec open()) doit être permise sans effets secondaires imprévus (par exemple, creat() sur une FIFO ne doit pas supprimer de données). Comme les fichiers spéciaux de terminal peuvent avoir des données de pré-lecture stockées dans le tampon, O_TRUNC ne doit pas affecter leur contenu, en particulier si un programme qui ouvre normalement un fichier régulier devrait ouvrir le terminal de contrôle actuel à la place. D'autres types de fichiers, en particulier ceux définis par l'implémentation, sont laissés à la définition de l'implémentation.

POSIX.1‐2008 autorise que [EACCES] soit retourné pour des conditions autres que celles explicitement listées.

Le drapeau O_NOCTTY a été ajouté pour permettre aux applications d'éviter d'acquérir involontairement un terminal de contrôle comme effet secondaire de l'ouverture d'un fichier de terminal. Ce volume de POSIX.1‐2017 ne spécifie pas comment un terminal de contrôle est acquis, mais il permet à une implémentation de fournir cela sur open() si le drapeau O_NOCTTY n'est pas défini et que d'autres conditions spécifiées dans le volume des définitions de base de POSIX.1‐2017, Chapitre 11, Interface Générale des Terminaux sont remplies.

Dans les implémentations historiques, la valeur de O_RDONLY est zéro. Pour cette raison, il n'est pas possible de détecter la présence de O_RDONLY et d'une autre option. Les implémentations futures devraient coder O_RDONLY et O_WRONLY comme des drapeaux de bits afin que :

O_RDONLY | O_WRONLY == O_RDWR

O_EXEC et O_SEARCH sont spécifiés comme deux des cinq modes d'accès aux fichiers. Comme O_EXEC ne s'applique pas aux répertoires, et O_SEARCH ne s'applique qu'aux répertoires, leurs valeurs n'ont pas besoin d'être distinctes. Comme O_RDONLY a historiquement eu la valeur zéro, les implémentations ne peuvent pas distinguer O_SEARCH de O_SEARCH | O_RDONLY, et de même pour O_EXEC.

En général, la fonction open() suit le lien symbolique si path pointe vers un lien symbolique. Cependant, la fonction open(), lorsqu'elle est appelée avec O_CREAT et O_EXCL, doit échouer avec [EEXIST] si path pointe vers un lien symbolique existant, même si le lien symbolique fait référence à un fichier inexistant. Ce comportement est requis pour que les applications privilégiées puissent créer un nouveau fichier dans un emplacement connu sans risque qu'un lien symbolique puisse entraîner la création du fichier dans un emplacement différent.

Par exemple, une application privilégiée qui doit créer un fichier avec un nom prévisible dans un répertoire inscriptible par l'utilisateur, tel que le répertoire personnel de l'utilisateur, pourrait être compromise si l'utilisateur crée un lien symbolique portant ce nom qui fait référence à un fichier inexistant dans un répertoire système. Si l'utilisateur peut influencer le contenu d'un fichier, il pourrait compromettre le système en créant un nouveau fichier de configuration système ou un fichier de file d'attente qui serait alors interprété par le système. Le test d'un lien symbolique faisant référence à un fichier inexistant doit être atomique avec la création d'un nouveau fichier.

De plus, la fonction open() refuse d'ouvrir les non-répertoires si le drapeau O_DIRECTORY est défini. Cela évite les conditions de concurrence où un utilisateur pourrait compromettre le système en substituant un lien physique vers un fichier sensible (par exemple, un périphérique ou une FIFO) pendant qu'une application privilégiée s'exécute, où l'ouverture d'un fichier, même en lecture seule, pourrait avoir des effets secondaires indésirables.

De plus, la fonction open() ne suit pas les liens symboliques si le drapeau O_NOFOLLOW est défini. Cela évite les conditions de concurrence où un utilisateur pourrait compromettre le système en substituant un lien symbolique vers un fichier sensible (par exemple, un périphérique) pendant qu'une application privilégiée s'exécute, où l'ouverture d'un fichier, même en lecture seule, pourrait avoir des effets secondaires indésirables.

La norme POSIX.1‐1990 exigeait que l'ID de groupe d'un fichier nouvellement créé soit défini sur l'ID de groupe de son répertoire parent ou sur l'ID de groupe effectif du processus créateur. FIPS 151‐2 exigeait que les implémentations fournissent un moyen de définir l'ID de groupe sur l'ID de groupe du répertoire contenant, mais n'interdisait pas aux implémentations de supporter également un moyen de définir l'ID de groupe sur l'ID de groupe effectif du processus créateur. Les applications conformes ne devraient pas supposer quel ID de groupe sera utilisé. Si cela est important, une application peut utiliser chown() pour définir l'ID de groupe après la création du fichier, ou déterminer dans quelles conditions l'implémentation définira l'ID de groupe souhaité.

L'objectif de la fonction openat() est de permettre l'ouverture de fichiers dans des répertoires autres que le répertoire de travail actuel sans exposition aux conditions de concurrence. N'importe quelle partie du chemin d'un fichier pourrait être modifiée en parallèle à un appel à open(), entraînant un comportement indéfini. En ouvrant un descripteur de fichier pour le répertoire cible et en utilisant la fonction openat(), il peut être garanti que le fichier ouvert est situé par rapport au répertoire souhaité. Certaines implémentations utilisent la fonction openat() à d'autres fins également. Dans certains cas, si le paramètre oflag a le drapeau O_XATTR défini, le descripteur de fichier retourné donne accès aux attributs étendus. Cette fonctionnalité n'est pas standardisée ici.
