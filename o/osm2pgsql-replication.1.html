NOM

osm2pgsql-replication - Mise à jour de la base de données osm2pgsql

SYNOPIS

osm2pgsql-replication {-h | {init,update,status} ...}

DESCRIPTION

Met à jour une base de données osm2pgsql avec les modifications provenant d'un serveur de réplication OSM.

Cet outil initialise le processus de mise à jour en examinant le fichier
d'importation ou le plus nouvel objet dans la base de données. L'état est ensuite sauvegardé dans une table
de la base de données. Les exécutions ultérieures téléchargent les données nouvellement disponibles et les appliquent
à la base de données.

Consultez l'aide des commandes 'init' et 'update' pour plus d'informations sur
l'utilisation d'osm2pgsql-replication.

OPTIONS

Sous-commandes

osm2pgsql-replication init

Initialise le processus de réplication.
osm2pgsql-replication update

Télécharge les nouvelles données disponibles et les applique à la base de données.
osm2pgsql-replication status

Affiche des informations sur l'état actuel de la réplication, éventuellement au format JSON.

OPTIONS 'osm2pgsql-replication init'

usage: osm2pgsql-replication init [-h] [-q] [-v] [-d DB] [-U NOM]
[-H HOTE] [-P PORT] [-p PREFIX]
[--schema-intermediaire SCHEMA] [--schema SCHEMA]
[--fichier-osm FICHIER | --serveur URL]
[--demarrer-a HEURE]

Initialise le processus de réplication.

Cette fonction définit le service de réplication à utiliser et détermine à partir
de quelle date appliquer les mises à jour. Vous devez appeler cette fonction au moins une fois
pour configurer le processus de réplication. Elle peut être appelée à nouveau en toute sécurité plus tard
pour changer les serveurs de réplication ou pour revenir en arrière dans le processus de mise à jour et
réappliquer les mises à jour.

Il existe différentes méthodes d'initialisation disponibles. Lorsque aucun paramètre
supplémentaire n'est donné, les données sont initialisées à partir des données
de la base de données. Si les données ont été importées à partir d'un fichier contenant des informations de réplication
et que la table des propriétés est disponible (pour osm2pgsql >= 1.9),
alors la réplication à partir du fichier est utilisée. Sinon, le service de mise à jour minute
d'openstreetmap.org est utilisé comme service de réplication par défaut. La date de début est soit prise à partir de l'horodatage de la base de données
(pour osm2pgsql >= 1.9) soit déterminée à partir du chemin le plus récent dans la base de données
en interrogeant l'API OSM sur sa date de création.

Le service de réplication peut être changé avec le paramètre '--serveur'.
Pour utiliser une date de début différente, ajoutez '--demarrer-a' avec un horodatage ISO absolu
(par exemple, 2007-08-20T12:21:53Z). Lorsque le programme détermine la
date de début à partir de l'horodatage de la base de données ou de la date de création du chemin, il
soustraie par défaut 3 heures supplémentaires pour s'assurer que toutes les nouvelles modifications sont disponibles. Pour changer cette période d'annulation, utilisez '--demarrer-a' avec le
nombre de minutes à annuler. Ce mode d'annulation peut également être utilisé pour
forcer l'initialisation à utiliser la date de la base de données et ignorer la date
des informations de réplication dans le fichier.

Le processus d'initialisation peut également utiliser directement les informations de réplication provenant
d'un fichier OSM et ignorer toutes les autres informations de date.
Utilisez la commande 'osm2pgsql-replication --fichier-osm <nomdefichier>' pour cela.

OPTIONS 'osm2pgsql-replication update'

usage: osm2pgsql-replication update update [options] [-- param [param ...]]

Télécharge les nouvelles données disponibles et les applique à la base de données.

Les données sont téléchargées par lots de '--taille-max-diff' Mo. Chaque lot est
sauvegardé dans un fichier temporaire et importé avec osm2pgsql à partir de là. Le
fichier temporaire est normalement supprimé ensuite, sauf si vous spécifiez un emplacement explicite
avec '--fichier-diff'. Une fois que la base de données est à jour avec la
source de réplication, le processus de mise à jour se termine avec 0.

Tous les arguments supplémentaires pour osm2pgsql doivent être fournis après '--'. La base de
données et le paramètre de préfixe sont transmis à osm2pgsql. Ils n'ont pas besoin
d'être répétés. '--append' et '--slim' seront toujours ajoutés également.

Utilisez le paramètre '--post-traitement' pour exécuter un script après que osm2pgsql ait
exécuté avec succès. Si les mises à jour consistent en plusieurs exécutions car la
taille maximale des données téléchargées a été atteinte, alors le script est exécuté
chaque fois qu'osm2pgsql s'est exécuté. Si le post-traitement échoue, alors
l'ensemble de l'exécution de mise à jour est considérée comme un échec et les informations de réplication
ne sont pas mises à jour. Cela signifie que lors de la prochaine exécution de 'update', il reprendra
le téléchargement des différences et leur réapplication à la base de données. C'est généralement sûr. Le script reçoit deux paramètres :
l'identifiant de séquence et l'horodatage de la dernière exécution réussie. L'horodatage
peut être manquant dans le rare cas où le service de réplication cesse de répondre
après que les mises à jour aient été téléchargées.

param
Paramètres supplémentaires à transmettre à osm2pgsql.
--fichier-diff FICHIER
Fichier pour sauvegarder les modifications avant qu'elles ne soient appliquées à osm2pgsql.
--taille-max-diff TAILLE_MAX_DIFF
Données maximales à charger en Mo (par défaut : 500 Mo).
--cmd-osm2pgsql CMD_OSM2PGSQL
Chemin vers la commande osm2pgsql.
--une-fois
Exécuter les mises à jour une seule fois, même si plus de données sont disponibles.
--post-traitement SCRIPT
Script de post-traitement à exécuter après chaque exécution d'osm2pgsql.

Afficher uniquement les messages d'erreur.
-v, --verbeux
Augmenter la verbosi

osm2pgsql-replication(1) — osm2pgsql 2.0.1

NAME

osm2pgsql-replication - managing replication state

SYNOPSIS

osm2pgsql-replication
init [-h] [-q] [-v] [-d DB] [-U NAME] [-H HOST]
[-P PORT] [-p PREFIX] [--middle-schema SCHEMA] [--schema SCHEMA]
[--last-update-timestamp TIMESTAMP] [--last-update-sequence SEQUENCE]
[--replication-update-interval SECONDS]
osm2pgsql-replication
update [-h] [-q] [-v] [-d DB] [-U NAME] [-H HOST]
[-P PORT] [-p PREFIX] [--middle-schema SCHEMA] [--schema SCHEMA]
[--replication-update-interval SECONDS]
osm2pgsql-replication
status [-h] [-q] [-v] [-d DB] [-U NAME] [-H HOST]
[-P PORT] [-p PREFIX] [--middle-schema SCHEMA] [--schema SCHEMA]
[--json]

DESCRIPTION

This command manages the replication state for osm2pgsql. It supports three subcommands: init, update and status.

The replication state is stored in a database table called replication_status. By default, this table is created in the public schema and named planet_osm_replication_status. The schema and table prefix can be changed using the ’--schema’ and ’--prefix’ options.

The replication state consists of the replication timestamp and sequence number. These are used by osm2pgsql to determine the last processed state when starting up.

The replication state can be stored in a separate schema using the ’--middle-schema’ option. This schema is only used for the replication state table, not for the OSM data tables.

The replication state is updated periodically by the osm2pgsql-replication update command. This command fetches the latest replication state from the replication server and updates the local database.

The replication state can be checked using the osm2pgsql-replication status command. This command prints the current replication status, including the server's status and the local database's status.

init

Initializes the replication state table in the database. This command should be run before the first update or status check.

update

Fetches the latest replication state from the replication server and updates the local database. This command should be run periodically to keep the replication state up-to-date.

status

Prints information about the current replication status, optionally as JSON.

OPTIONS

Common options for all subcommands:

Show help message and exit.
-q, --quiet
Print only error messages.
-v, --verbose
Increase verboseness of output.

-H HOST, --host HOST
Database server host name or socket location.
-P PORT, --port PORT
Database server port.
-p PREFIX, --prefix PREFIX

--middle-schema SCHEMA

--schema SCHEMA

OPTIONS 'osm2pgsql-replication init'

usage: osm2pgsql-replication init [-h] [-q] [-v] [-d DB] [-U NAME] [-H HOST]
[-P PORT] [-p PREFIX]
[--middle-schema SCHEMA] [--schema SCHEMA]
[--last-update-timestamp TIMESTAMP] [--last-update-sequence SEQUENCE]
[--replication-update-interval SECONDS]

--last-update-timestamp TIMESTAMP
Initial timestamp for replication state.
--last-update-sequence SEQUENCE
Initial sequence number for replication state.
--replication-update-interval SECONDS
Interval in seconds for updating replication state. Default is 300 seconds (5 minutes).

OPTIONS 'osm2pgsql-replication update'

[-P PORT] [-p PREFIX]
[--middle-schema SCHEMA] [--schema SCHEMA]
[--replication-update-interval SECONDS]

--replication-update-interval SECONDS
Interval in seconds for updating replication state. Default is 300 seconds (5 minutes).

OPTIONS 'osm2pgsql-replication status'

usage: osm2pgsql-replication status [-h] [-q] [-v] [-d DB] [-U NAME] [-H HOST]
[-P PORT] [-p PREFIX]
[--middle-schema SCHEMA] [--schema SCHEMA]
[--json]

Print information about the current replication status, optionally as JSON.

Sample output:


2021-08-17 15:20:28 [INFO]: Using replication service 'https://planet.openstreetmap.org/replication/minute', which is at sequence 4675115 ( 2021-08-17T13:19:43Z )
2021-08-17 15:20:28 [INFO]: Replication server's most recent data is <1 minute old
2021-08-17 15:20:28 [INFO]: Local database is 8288 sequences behind the server, i.e. 5 day(s) 20 hour(s) 58 minute(s)
2021-08-17 15:20:28 [INFO]: Local database's most recent data is 5 day(s) 20 hour(s) 59 minute(s) old

With the ’--json’ option, the status is printed as a json object.


{
"server": {
"base_url": "https://planet.openstreetmap.org/replication/minute",
"sequence": 4675116,
"timestamp": "2021-08-17T13:20:43Z",
"age_sec": 27
},
"local": {
"sequence": 4666827,
"timestamp": "2021-08-11T16:21:09Z",
"age_sec": 507601
},
"status": 0
}

’status’ is 0 if there were no problems getting the status. 1 & 2 for
improperly set up replication. 3 for network issues. If status ≠ 0, then
the ’error’ key is an error message (as string). ’status’ is used as the
exit code.

’server’ is the replication server's current status. ’sequence’ is it's
sequence number, ’timestamp’ the time of that, and 'age_sec' the age of the
data in seconds.

’local’ is the status of your server.

Output status as json.

-P PORT, --port PORT
Database server port
-p PREFIX, --prefix PREFIX
Prefix for table names (default 'planet_osm')
--middle-schema SCHEMA
Name of the schema to store the table for the replication state in
--schema SCHEMA
Name of the schema for the database
