NOM

ovs-testcontroller - Contrôleur OpenFlow simple pour les tests

SYNTAXE

ovs-testcontroller [options] méthode [méthode]...

DESCRIPTION

ovs-testcontroller est un contrôleur OpenFlow simple qui gère un nombre quelconque de commutateurs via le protocole OpenFlow, les faisant fonctionner comme des commutateurs L2 apprenant les MAC ou des concentrateurs (hubs). Il convient aux tests initiaux des réseaux OpenFlow. Ce n'est ni une partie nécessaire ni souhaitable d'un déploiement OpenFlow en production.

ovs-testcontroller contrôle un ou plusieurs commutateurs OpenFlow, spécifiés comme une ou plusieurs des méthodes de connexion OpenFlow suivantes :

pssl:[port][:hôte]

ptcp:[port][:hôte]
Écoute les connexions OpenFlow sur le port. Le port par défaut est 6653. Par défaut, les connexions sont autorisées depuis n'importe quelle adresse IPv4. Spécifiez hôte comme une adresse IPv4 ou une adresse IPv6 entre crochets (par exemple, ptcp:6653:[::1]). Sous Linux, utilisez %périphérique pour désigner une portée pour les adresses IPv6 de niveau lien, par exemple, ptcp:6653:[fe80::1234%eth0]. Les noms DNS peuvent être utilisés s'ils sont compilés avec la bibliothèque unbound. Pour pssl, les options --private-key, --certificate et --ca-cert sont obligatoires.
punix:fichier
Écoute les connexions OpenFlow sur le socket serveur de domaine Unix nommé fichier.
ssl:hôte[:port]

tcp:hôte[:port]
Le port spécifié sur l'hôte donné, qui peut être exprimé soit comme un nom DNS (s'il est compilé avec la bibliothèque unbound) soit comme une adresse IP au format IPv4 ou IPv6. Entourez les adresses IPv6 de crochets, par exemple, tcp:[::1]:6653. Sous Linux, utilisez %périphérique pour désigner une portée pour les adresses IPv6 de niveau lien, par exemple, tcp:[fe80::1234%eth0]:6653. Pour ssl, les options --private-key, --certificate et --ca-cert sont obligatoires.
Si port n'est pas spécifié, il est défini par défaut sur 6653.
unix:fichier
Sur POSIX, un socket serveur de domaine Unix nommé fichier.
Sous Windows, connectez-vous à un pipe nommé local qui est représenté par un fichier créé dans le chemin fichier pour imiter le comportement d'un socket de domaine Unix.

OPTIONS

-n

--noflow
Par défaut, ovs-testcontroller configure un flux dans chaque commutateur OpenFlow lorsqu'il reçoit un paquet dont la destination est connue grâce à l'apprentissage des MAC. Cette option désactive la configuration des flux, de sorte que chaque paquet du réseau passe par le contrôleur.
Cette option est surtout utile pour le débogage. Elle réduit les performances de commutation, elle ne doit donc pas être utilisée en production.
--max-idle=secs|permanent
Définit secs comme le nombre de secondes pendant lesquelles un flux configuré par le contrôleur restera dans la table de flux du commutateur sans aucun paquet correspondant vu. Si permanent est spécifié, ce qui n'est pas recommandé, les flux n'expireront jamais. La valeur par défaut est 60 secondes.
Cette option n'a aucun effet lorsque -n (ou --noflow) est utilisé (car le contrôleur ne configure pas de flux dans ce cas).
-H

--hub
Par défaut, le contrôleur agit comme un commutateur L2 apprenant les MAC. Cette option modifie son comportement pour qu'il agisse comme un concentrateur (hub) qui diffuse les paquets sur tous les ports sauf celui d'entrée.
Si -H (ou --hub) et -n (ou --noflow) sont utilisés ensemble, l'effet cumulé est que chaque paquet passe par le contrôleur et chaque paquet est diffusé.
Cette option est surtout utile pour le débogage. Elle réduit les performances de commutation, elle ne doit donc pas être utilisée en production.
-w[masque_generique]

--wildcards[=masque_generique]
Par défaut, ovs-testcontroller configure des flux d'appariement exact. Cette option lui permet de configurer des flux génériques, ce qui peut réduire la latence de configuration des flux en envoyant moins de trafic vers le contrôleur.
Le masque_generique facultatif est un masque de bits générique OpenFlow en hexadécimal qui spécifie les champs à rendre génériques. Si aucun masque_generique n'est spécifié, la valeur par défaut 0x2820F0 est utilisée, qui spécifie la commutation L2 uniquement et rend génériques les champs L3 et L4. Une autre valeur intéressante est 0x2000EC, qui spécifie la commutation L3 uniquement et rend génériques les champs L2 et L4.
Cette option n'a aucun effet lorsque -n (ou --noflow) est utilisé (car le contrôleur ne configure pas de flux dans ce cas).
-N

--normal
Par défaut, ovs-testcontroller dirige les paquets vers un port particulier ou les diffuse. Cette option lui fait diriger les paquets non diffusés vers le port OpenFlow OFPP_NORMAL. Cela permet au commutateur lui-même de prendre des décisions concernant les destinations des paquets. La prise en charge de OFPP_NORMAL est facultative dans OpenFlow, donc cette option peut ne pas bien fonctionner avec certains commutateurs autres que Open vSwitch.
--mute
Empêche ovs-testcontroller de répondre à tout message OpenFlow qui lui est envoyé par les commutateurs.
Cette option est uniquement destinée au débogage de l'implémentation du mode « fail open » d'Open vSwitch. Elle ne doit pas être utilisée en production.
-q id

--queue=id
Par défaut, ovs-testcontroller utilise la file d'attente OpenFlow par défaut pour envoyer des paquets et configurer des flux. Utilisez l'une de ces options, en fournissant id comme ID de file d'attente OpenFlow sous forme de nombre décimal, pour utiliser à la place cette file d'attente spécifique.
Cette option est incompatible avec -N ou --normal et avec -H ou --hub. Si plusieurs sont spécifiées, cette option a la priorité.
Cette option peut être utile pour tester ou déboguer des configurations de qualité de service.
-Q nom-port:id-file
--port-queue nom-port:id-file
Configure les paquets reçus sur le port nommé nom-port (par exemple, eth0) pour être sortis sur l'ID de file d'attente OpenFlow id-file (spécifié sous forme de nombre décimal). Pour le port spécifié, cette option remplace celle par défaut spécifiée sur -q ou --queue.
Cette option peut être spécifiée un nombre quelconque de fois avec des arguments nom-port différents.
Cette option est incompatible avec -N ou --normal et avec -H ou --hub. Si plusieurs sont spécifiées, cette option a la priorité.
Cette option peut être utile pour tester ou déboguer des configurations de qualité de service.
--with-flows fichier
Lorsqu'un commutateur se connecte, insère les entrées de flux décrites dans fichier. Chaque ligne de fichier est une entrée de flux dans le format décrit pour la commande add-flows dans la section Syntaxe des flux de la page de manuel ovs-ofctl(8).
Utilisez cette option plus d'une fois pour ajouter des flux à partir de plusieurs fichiers.

Options d'infrastructure de clés publiques

-p cle_privee

--private-key=cle_privee
Le fichier contenant la clé privée du certificat de l'entité qui s'authentifie. Le format de fichier est PEM. Si vous utilisez une clé protégée par mot de passe, ovs-testcontroller vous demandera le mot de passe.
-c certificat

--certificate=certificat
Le fichier contenant le certificat de l'entité qui s'authentifie. Le format de fichier est PEM.
-C ca-certificat

--ca-cert=ca-certificat
Le fichier contenant un certificat de l'autorité de certification qui a signé le certificat de l'entité qui s'authentifie. Le format de fichier est PEM. Si ce fichier est fourni, il est utilisé pour valider le certificat du pair. Si aucun certificat d'autorité de certification n'est fourni, l'entité qui s'authentifie doit être approuvée explicitement par d'autres moyens pour que la connexion soit établie.
-a ca-certificat

--add-ca-cert=ca-certificat
Ajoute un certificat d'autorité de certification, pour une utilisation avec --remote-ca-cert, à une liste de certificats d'autorité de certification approuvés. Le format de fichier est PEM. Ce commutateur peut être utilisé plusieurs fois pour ajouter plusieurs certificats.
-r ca-certificat

--remote-ca-cert=ca-certificat
Le fichier contenant un certificat de l'autorité de certification qui a signé le certificat du pair distant. Le format de fichier est PEM. Utilisé pour valider le certificat du pair distant. Ce commutateur peut être utilisé plusieurs fois pour ajouter plusieurs certificats.
-h

--help
Affiche un message d'aide et quitte.
-V

--version
Affiche des informations sur la version et quitte.

ey.pem

--private-key=privkey.pem
Spécifie un fichier PEM contenant la clé privée utilisée comme identité de ovs-testcontroller pour les connexions SSL/TLS sortantes.
-c cert.pem

--certificate=cert.pem
Spécifie un fichier PEM contenant un certificat qui certifie que la clé privée spécifiée avec -p ou --private-key est digne de confiance. Le certificat doit être signé par l'autorité de certification (CA) que le pair dans les connexions SSL/TLS utilisera pour le vérifier.
-C cacert.pem

--ca-cert=cacert.pem
Spécifie un fichier PEM contenant le certificat CA que ovs-testcontroller doit utiliser pour vérifier les certificats qui lui sont présentés par les pairs SSL/TLS. (Ce peut être le même certificat que les pairs SSL/TLS utilisent pour vérifier le certificat spécifié avec -c ou --certificate, ou il peut être différent, selon la conception de l'infrastructure à clé publique (PKI) utilisée.)
-C none

--ca-cert=none
Désactive la vérification des certificats présentés par les pairs SSL/TLS. Cela introduit un risque de sécurité, car cela signifie que les certificats ne peuvent pas être vérifiés comme appartenant à des hôtes de confiance connus.
--peer-ca-cert=peer-cacert.pem
Spécifie un fichier PEM qui contient un ou plusieurs certificats supplémentaires à envoyer aux pairs SSL/TLS. peer-cacert.pem doit être le certificat CA utilisé pour signer le propre certificat de ovs-testcontroller, c'est-à-dire le certificat spécifié avec -c ou --certificate. Si le certificat de ovs-testcontroller est auto-signé, alors --certificate et --peer-ca-cert doivent spécifier le même fichier.
Cette option n'est pas utile en fonctionnement normal, car le pair SSL/TLS doit déjà posséder le certificat CA pour avoir une quelconque confiance dans l'identité de ovs-testcontroller. Cependant, cela offre un moyen à une nouvelle installation d'amorcer le certificat CA lors de sa première connexion SSL/TLS.

Options du démon

Les options suivantes sont valides sur les plateformes basées sur POSIX.

--pidfile[=pidfile]
Crée un fichier (par défaut, ovs-testcontroller.pid) indiquant le PID du processus en cours d'exécution. Si l'argument pidfile n'est pas spécifié, ou s'il ne commence pas par /, alors il est créé dans /run/openvswitch.
Si --pidfile n'est pas spécifié, aucun fichier pid n'est créé.
--overwrite-pidfile
Par défaut, lorsque --pidfile est spécifié et que le fichier pid spécifié existe déjà et est verrouillé par un processus en cours d'exécution, ovs-testcontroller refuse de démarrer. Spécifiez --overwrite-pidfile pour qu'il écrase plutôt le fichier pid.
Lorsque --pidfile n'est pas spécifié, cette option n'a aucun effet.
--detach
Exécute ovs-testcontroller en tant que processus d'arrière-plan. Le processus se divise, et dans le processus enfant, il démarre une nouvelle session, ferme les descripteurs de fichiers standards (ce qui a pour effet secondaire de désactiver la journalisation sur la console) et change son répertoire courant pour la racine (sauf si --no-chdir est spécifié). Une fois que le processus enfant a terminé son initialisation, le processus parent se termine.
--monitor
Crée un processus supplémentaire pour surveiller le démon ovs-testcontroller. Si le démon meurt à cause d'un signal indiquant une erreur de programmation (SIGABRT, SIGALRM, SIGBUS, SIGFPE, SIGILL, SIGPIPE, SIGSEGV, SIGXCPU ou SIGXFSZ), alors le processus de surveillance démarre une nouvelle copie de celui-ci. Si le démon meurt ou se termine pour une autre raison, le processus de surveillance se termine.
Cette option est normalement utilisée avec --detach, mais elle fonctionne également sans.
--no-chdir
Par défaut, lorsque --detach est spécifié, ovs-testcontroller change son répertoire de travail courant vers le répertoire racine après s'être détaché. Sinon, invoquer ovs-testcontroller à partir d'un répertoire choisi négligemment empêcherait l'administrateur de démonter le système de fichiers qui contient ce répertoire.
Spécifier --no-chdir supprime ce comportement, empêchant ovs-testcontroller de changer son répertoire de travail courant. Cela peut être utile pour collecter des fichiers core, car il est courant d'écrire les vidages de mémoire dans le répertoire de travail courant et le répertoire racine n'est pas un bon répertoire à utiliser.
Cette option n'a aucun effet lorsque --detach n'est pas spécifié.
--no-self-confinement
Par défaut, le démon tentera de se confiner pour travailler avec des fichiers dans des répertoires bien connus déterminés lors de la compilation. Il est préférable de s'en tenir à ce comportement par défaut et de ne pas utiliser ce drapeau, sauf si une autre méthode de contrôle d'accès est utilisée pour confiner le démon. Notez qu'à la différence d'autres implémentations de contrôle d'accès qui sont généralement appliquées depuis l'espace noyau (par exemple, DAC ou MAC), le self-confinement est imposé par le démon d'espace utilisateur et ne doit donc pas être considéré comme une stratégie de confinement complète, mais plutôt comme une couche de sécurité supplémentaire.
--user
Fait en sorte que ovs-testcontroller s'exécute sous un utilisateur différent spécifié dans "utilisateur:groupe", abandonnant ainsi la plupart des privilèges root. Les formes courtes "utilisateur" et ":groupe" sont également autorisées, l'utilisateur ou le groupe actuel étant supposé respectivement. Seuls les démons démarrés par l'utilisateur root acceptent cet argument.
Sous Linux, les démons recevront CAP_IPC_LOCK et CAP_NET_BIND_SERVICES avant d'abandonner les privilèges root. Les démons qui interagissent avec un dataplane, tels que ovs-vswitchd, recevront trois capacités supplémentaires, à savoir CAP_NET_ADMIN, CAP_NET_BROADCAST et CAP_NET_RAW. Le changement de capacité s'appliquera même si le nouvel utilisateur est root.
Sous Windows, cette option n'est pas prise en charge actuellement. Pour des raisons de sécurité, la spécification de cette option entraînera le non-démarrage du processus démon.
-v[spec]

--verbose=[spec]
Définit les niveaux de journalisation. Sans aucun spec, définit le niveau de journalisation pour chaque module et destination sur dbg. Sinon, spec est une liste de mots séparés par des espaces, des virgules ou des deux-points, jusqu'à un par catégorie ci-dessous :
  • Un nom de module valide, tel qu'affiché par la commande vlog/list sur ovs-appctl(8), limite la modification du niveau de journalisation au module spécifié.
  • syslog, console ou file, pour limiter la modification du niveau de journalisation uniquement au journal système, à la console ou à un fichier, respectivement. (Si --detach est spécifié, ovs-testcontroller ferme ses descripteurs de fichiers standards, de sorte que la journalisation sur la console n'aura aucun effet.)
Sur la plateforme Windows, syslog est accepté comme un mot et n'est utile qu'avec l'option --syslog-target (le mot n'a aucun effet sinon).
•
off, emer, err, warn, info ou dbg, pour contrôler le niveau de journalisation. Les messages de la gravité donnée ou supérieure seront enregistrés, et les messages de gravité inférieure seront filtrés. off filtre tous les messages. Voir ovs-appctl(8) pour une définition de chaque niveau de journalisation.
La casse n'est pas significative dans spec.
Indépendamment des niveaux de journalisation définis pour file, la journalisation dans un fichier n'aura lieu que si --log-file est également spécifié (voir ci-dessous).
Pour assurer la compatibilité avec les anciennes versions d'OVS, any est accepté comme un mot mais n'a aucun effet.
-v

--verbose
Définit le niveau de verbosité de journalisation maximal, équivalent à --verbose=dbg.
-vPATTERN:destination:pattern

--verbose=PATTERN:destination:pattern
Définit le modèle de journalisation pour destination sur pattern. Reportez-vous à ovs-appctl(8) pour une description de la syntaxe valide pour pattern.
-vFACILITY:facility

--verbose=FACILITY:facility
Définit la facilité RFC5424 du message de journalisation. facility peut être l'un des éléments suivants : kern, user, mail, daemon, auth, syslog, lpr, news, uucp, clock, ftp, ntp, audit, alert, clock2, local0, local1, local2, local3, local4, local5, local6 ou local7. Si cette option n'est pas spécifiée, daemon est utilisé par défaut pour le syslog du système local et local0 est utilisé lors de l'envoi d'un message à la cible fournie via l'option --syslog-target.
--log-file[=file]
Active la journalisation dans un fichier. Si file est spécifié, alors il est utilisé comme nom exact pour le fichier journal. Le nom de fichier journal par défaut utilisé si file est omis est /var/log/openvswitch/ovs-testcontroller.log.
--syslog-target=hote:port
Envoie les messages syslog au port UDP port sur l'hôte hote, en plus des messages syslog du système. L'hote doit être une adresse IP numérique, pas un nom d'hôte.
--syslog-method=methode
Spécifie la methode par laquelle les messages syslog doivent être envoyés au démon syslog. Les formes suivantes sont supportées :
  • libc, utilise la fonction syslog() de la libc. L'inconvénient de cette option est que la libc ajoute un préfixe fixe à chaque message avant qu'il ne soit réellement envoyé au démon syslog via le socket de domaine UNIX /dev/log.
  • unix:fichier, utilise directement le socket de domaine UNIX. Il est possible de spécifier un format de message arbitraire avec cette option. Cependant, rsyslogd 8.9 et les versions antérieures utilisent de toute façon une fonction d'analyse (parser) codée en dur qui limite l'utilisation du socket de domaine UNIX. Si vous souhaitez utiliser un format de message arbitraire avec des versions plus anciennes de rsyslogd, utilisez plutôt un socket UDP vers l'adresse IP de localhost.
  • udp:ip:port, utilise un socket UDP. Avec cette méthode, il est possible d'utiliser un format de message arbitraire également avec des versions plus anciennes de rsyslogd. Lors de l'envoi de messages syslog via un socket UDP, des précautions supplémentaires doivent être prises, par exemple, le démon syslog doit être configuré pour écouter sur le port UDP spécifié, des règles iptables accidentelles pourraient interférer avec le trafic syslog local et il existe certaines considérations de sécurité qui s'appliquent aux sockets UDP, mais pas aux sockets de domaine UNIX.
  • null, rejette tous les messages enregistrés dans syslog.
La valeur par défaut est prise de la variable d'environnement OVS_SYSLOG_METHOD; si elle n'est pas définie, la valeur par défaut est libc.
--unixctl=socket
Définit le nom du socket de contrôle sur lequel ovs-testcontroller écoute les commandes de gestion d'exécution (voir COMMANDES DE GESTION D'EXÉCUTION, ci-dessous). Si socket ne commence pas par /, il est interprété par rapport à /run/openvswitch. Si --unixctl n'est pas du tout utilisé, le socket par défaut est /run/openvswitch/ovs-testcontroller.pid.ctl, où pid est l'identifiant de processus de ovs-testcontroller.
Sous Windows, un pipe nommé local est utilisé pour écouter les commandes de gestion d'exécution. Un fichier est créé dans le chemin absolu indiqué par socket ou si --unixctl n'est pas du tout utilisé, un fichier est créé sous le nom ovs-testcontroller.ctl dans le répertoire OVS_RUNDIR configuré. Le fichier existe uniquement pour imiter le comportement d'un socket de domaine UNIX.
Spécifier none pour socket désactive la fonctionnalité de socket de contrôle.
-h

--help
Affiche un bref message d'aide sur la console.
-V

--version
Affiche les informations de version sur la console.
-O [version[,version]...]

--protocols=[version[,version]...]
Définit les versions de protocole OpenFlow qui sont autorisées lors de l'établissement d'une session OpenFlow.
Ces versions de protocole sont activées par défaut :
•
OpenFlow10, pour OpenFlow 1.0.
Les versions de protocole suivantes sont généralement supportées, mais pour des raisons de compatibilité avec les anciennes versions d'Open vSwitch, elles ne sont pas activées par défaut :
  • OpenFlow11, pour OpenFlow 1.1.
  • OpenFlow12, pour OpenFlow 1.2.
  • OpenFlow13, pour OpenFlow 1.3.
  • OpenFlow14, pour OpenFlow 1.4.
  • OpenFlow15, pour OpenFlow 1.5.
