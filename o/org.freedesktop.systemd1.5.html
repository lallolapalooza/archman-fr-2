org.freedesktop.systemd1 - L'interface D-Bus de systemd

INTRODUCTION

systemd(1) et ses démons auxiliaires exposent un certain nombre d'API via D-Bus. Cette page ne décrit que les différentes API exposées par le gestionnaire de système et de services lui-même. Elle ne couvre pas les démons auxiliaires.

Le gestionnaire de services expose un certain nombre d'objets sur le bus : un objet Manager comme point d'entrée central pour les clients, ainsi que des objets individuels pour chaque unité et pour chaque tâche mise en file d'attente. Les objets unité implémentent une interface Unit générique ainsi qu'une interface spécifique au type. Par exemple, les unités de service implémentent à la fois org.freedesktop.systemd1.Unit et org.freedesktop.system1.Service. L'objet gestionnaire peut lister les objets unité et tâche ou convertir directement un nom d'unité ou un identifiant de tâche en un chemin de bus de l'objet D-Bus correspondant.

Les propriétés exposant des valeurs temporelles sont généralement encodées en microsecondes (μs) sur le bus, même si leurs paramètres correspondants dans les fichiers d'unité sont en secondes.

PID 1 utilise polkit[1] pour autoriser l'accès aux opérations privilégiées pour les processus non privilégiés. Certaines opérations (telles que l'arrêt/redémarrage/suspension) sont également disponibles via l'API D-Bus de logind, voir org.freedesktop.login1(5).

Méthodes

Notez que de nombreuses méthodes existent en double : une sur l'objet Manager et une sur les objets d'unité respectifs. Ceci afin d'optimiser les temps d'accès de sorte que les méthodes appartenant aux objets d'unité n'aient pas à être appelées avec un chemin d'unité résolu, mais puissent également être appelées avec seulement l'identifiant d'unité.

GetUnit() peut être utilisé pour obtenir le chemin de l'objet d'unité pour un nom d'unité. Il prend le nom de l'unité et renvoie le chemin de l'objet. Si une unité n'a pas encore été chargée sous ce nom, cette méthode échouera.

GetUnitByPID() peut être utilisé pour obtenir le chemin de l'objet d'unité auquel appartient un processus. Il prend un PID UNIX et renvoie le chemin de l'objet. Le PID doit faire référence à un processus système existant. GetUnitByPIDFD() peut être utilisé pour interroger avec un PIDFD Linux (voir : pidfd_open(2)) au lieu d'un PID, ce qui est plus sûr car les PID UNIX peuvent être réutilisés. Cette dernière méthode renvoie l'identifiant de l'unité et l'identifiant d'invocation ensemble avec le chemin de l'objet d'unité.

LoadUnit() est similaire à GetUnit() mais chargera l'unité depuis le disque si possible.

StartUnit() met en file d'attente un travail de démarrage et éventuellement des travaux dépendants. Il prend l'unité à activer et une chaîne de mode en arguments. Le mode doit être l'un de "replace", "fail", "isolate", "ignore-dependencies", ou "ignore-requirements". Si c'est "replace", la méthode démarrera l'unité et ses dépendances, remplaçant éventuellement les travaux déjà mis en file d'attente qui entrent en conflit avec. Si c'est "fail", la méthode démarrera l'unité et ses dépendances, mais échouera si cela change un travail déjà mis en file d'attente. Si c'est "isolate", la méthode démarrera l'unité en question et terminera toutes les unités qui n'en sont pas des dépendances. Si "ignore-dependencies", elle démarrera une unité mais ignorera toutes ses dépendances. Si "ignore-requirements", elle démarrera une unité mais ignorera uniquement les dépendances requises. Il est déconseillé d'utiliser les deux dernières options. En réponse, si elle réussit, cette méthode renvoie le nouvel objet de travail créé qui a été mis en file d'attente pour une activation asynchrone. Les appelants qui souhaitent suivre le résultat de l'opération de démarrage réelle doivent surveiller le résultat de ce travail. Cela peut être réalisé sans problème de concurrence en s'abonnant d'abord au signal JobRemoved(), puis en appelant StartUnit() et en utilisant l'objet de travail renvoyé pour filtrer les signaux JobRemoved() non pertinents, jusqu'à ce que celui désiré soit reçu, qui portera alors le résultat de l'opération de démarrage.

StartUnitReplace() est similaire à StartUnit() mais remplace un travail mis en file d'attente pour une unité par un travail pour une autre unité.

StartUnitWithFlags() est similaire à StartUnit() mais permet à l'appelant de passer un paramètre flags supplémentaire, qui ne prend en charge aucun drapeau pour le moment et est réservé aux extensions futures.

StopUnit() est similaire à StartUnit() mais arrête l'unité spécifiée plutôt que de la démarrer. Notez que le mode "isolate" est invalide pour cette méthode.

ReloadUnit(), RestartUnit(), TryRestartUnit(), ReloadOrRestartUnit(), ou ReloadOrTryRestartUnit() peuvent être utilisés pour redémarrer et/ou recharger une unité. Ces méthodes prennent des arguments similaires à StartUnit(). Le rechargement est effectué uniquement si l'unité est déjà en cours d'exécution et échoue sinon. Si un service est redémarré alors qu'il n'est pas en cours d'exécution, il sera démarré, sauf si le mode "Try" est utilisé, auquel cas un service qui n'est pas en cours d'exécution n'est pas affecté par le redémarrage. Les modes "ReloadOrRestart" tentent un rechargement si l'unité le prend en charge et utilisent un redémarrage sinon.

EnqueueMarkedJobs() crée des travaux de rechargement/redémarrage pour les unités qui ont été correctement marquées, voir la propriété Markers ci-dessus. Ceci équivaut à appeler TryRestartUnit() ou ReloadOrTryRestartUnit() pour les unités marquées.

BindMountUnit() peut être utilisé pour monter par liaison de nouveaux fichiers ou répertoires dans l'espace de noms de montage d'un service en cours d'exécution. Si pris en charge par le noyau, tout montage précédent sur la cible sélectionnée sera remplacé par le nouveau montage. S'il n'est pas pris en charge, tout montage précédent sera superposé, mais restera épinglé et inaccessible.

MountImageUnit() peut être utilisé pour monter de nouvelles images dans l'espace de noms de montage d'un service en cours d'exécution. S'il est pris en charge par le noyau, tout montage précédent sur la cible sélectionnée sera remplacé par le nouveau montage. S'il n'est pas pris en charge, tout montage précédent sera superposé, mais restera épinglé et inaccessible.

KillUnit() peut être utilisé pour tuer (c'est-à-dire envoyer un signal à) tous les processus d'une unité. Il prend le *nom* de l'unité, une énumération *who* et un numéro de signal UNIX *signal* à envoyer. L'énumération *who* est l'un de "main", "control", "cgroup" ou "all". Si c'est "main", seul le processus principal de l'unité est tué. Si c'est "control", seul le processus de contrôle de l'unité est tué. Si "cgroup" est spécifié, seuls les processus du groupe de contrôle de l'unité sont tués, ce qui peut inclure ou non les processus principaux et de contrôle. Si c'est "all", tous les processus sont tués, c'est-à-dire le processus principal, le processus de contrôle et ceux du groupe de contrôle. Un processus "control" est, par exemple, un processus configuré via ExecStop= et qui est lancé en parallèle au processus daemon principal afin de l'arrêter. La valeur peut être suffixée par "-fail" auquel cas l'opération échouera si aucun processus correspondant n'a été trouvé (sinon, elle réussira, sans aucune opération).

KillUnitSubgroup() est identique à KillUnit() mais prend un argument de chemin supplémentaire qui sélectionne un sous-groupe de contrôle du groupe de contrôle de l'unité. Seuls les processus de ce sous-groupe sont tués. Le chemin peut être spécifié avec ou sans slash initial "/", dans les deux cas, il est pris relativement au groupe de contrôle de l'unité. Si le chemin du sous-groupe est spécifié comme une chaîne vide ou comme "/" il a le même effet que KillUnit(). S'il est spécifié comme autre chose, le paramètre "whom" doit être défini sur "cgroup" ou "cgroup-fail".

QueueSig

The SystemdManager interface is the main entry point to the systemd service manager. SD_SYSTEMD_UNIT_PORTABLE ajoutera ou supprimera les liens symboliques dans /etc/systemd/system.attached et /run/systemd/system.attached.

DisableUnitFilesWithFlagsAndInstallInfo() est similaire à DisableUnitFilesWithFlags() et prend les mêmes arguments, mais retourne un booléen pour indiquer si les fichiers d'unité contiennent des informations d'activation, comme EnableUnitFiles(). Les modifications apportées sont toujours retournées dans un tableau.

De même, ReenableUnitFiles() applique les modifications à une ou plusieurs unités qui résulteraient de la désactivation et de l'activation de l'unité rapidement l'une après l'autre de manière atomique. Ceci est utile pour appliquer les informations [Install] mises à jour contenues dans les fichiers d'unité.

De même, LinkUnitFiles() lie les fichiers d'unité (qui sont situés en dehors des chemins de recherche d'unités habituels) dans le chemin de recherche d'unités.

De même, PresetUnitFiles() active/désactive un ou plusieurs fichiers d'unité selon la politique de préréglage. Voir systemd.preset(5) pour plus d'informations.

De même, MaskUnitFiles() masque les fichiers d'unité et UnmaskUnitFiles() les démasque à nouveau.

SetDefaultTarget() modifie le lien default.target. Voir bootup(7) pour plus d'informations.

GetDefaultTarget() récupère le nom de l'unité à laquelle default.target est aliasé.

SetUnitProperties() peut être utilisé pour modifier certaines propriétés de l'unité à l'exécution. Toutes les propriétés ne peuvent pas être modifiées à l'exécution, mais de nombreux paramètres de gestion des ressources (principalement ceux listés dans systemd.resource-control(5)) le peuvent. Les modifications sont appliquées instantanément et stockées sur disque pour les futurs démarrages, sauf si runtime est vrai, auquel cas les paramètres ne s'appliquent que jusqu'au prochain redémarrage. name est le nom de l'unité à modifier. properties sont les paramètres à définir, encodés sous forme de tableau de paires nom de propriété et valeur. Notez que ce n'est pas un dictionnaire ! Notez également que lors de la définition de propriétés de type tableau avec cette méthode, cela résulte généralement en un ajout au tableau préconfiguré. Pour réinitialiser les tableaux configurés, définissez d'abord la propriété sur un tableau vide, puis ajoutez-y des éléments.

StartTransientUnit() peut être utilisé pour créer et démarrer une unité transitoire qui sera libérée dès qu'elle ne sera plus en cours d'exécution ou référencée, ou lorsque le système redémarre. name est le nom de l'unité incluant son suffixe et doit être unique. mode est le même que dans StartUnit(), properties contient les propriétés de l'unité, spécifiées comme dans SetUnitProperties(). aux n'est actuellement pas utilisé et doit être passé comme un tableau vide. Voir l'**Interface de groupe de contrôle**[2] pour plus d'informations sur l'utilisation de cette fonctionnalité à des fins de contrôle des ressources.

DumpUnitFileDescriptorStore() retourne un tableau d'informations sur les descripteurs de fichiers actuellement dans le magasin de descripteurs de fichiers de l'unité spécifiée. Cet appel est équivalent à DumpFileDescriptorStore() sur l'org.freedesktop.systemd1.Service. Pour plus de détails, voir ci-dessous.

CleanUnit() supprime les répertoires de configuration, d'état, de journaux, de cache et de données d'exécution et vide le magasin de descripteurs de fichiers pour l'unité, comme spécifié dans les paramètres de masquage. Les valeurs possibles sont "configuration", "state", "logs", "cache", "runtime", "fdstore", et "all".

RemoveSubgroupFromUnit() supprime un sous-groupe appartenant au cgroup d'une unité. Prend trois arguments : le nom de l'unité (si vide, par défaut l'unité appelante), un chemin cgroup (qui doit commencer par un slash "/"), qui est pris par rapport au cgroup de l'unité, et un argument de drapeaux (qui doit être zéro pour l'instant). Ceci est principalement utile pour les gestionnaires de services non privilégiés afin de demander au gestionnaire de services système la suppression des sous-groupes qu'il gère, au cas où l'un d'eux aurait été délégué à d'autres UID.

Signaux

Notez que la plupart des signaux ne sont envoyés qu'après que Subscribe() a été invoqué par au moins un client. Assurez-vous d'invoquer cette méthode lors de la souscription à ces signaux !

UnitNew() et UnitRemoved() sont envoyés chaque fois qu'une nouvelle unité est chargée ou déchargée. Notez que cela a peu à voir avec la disponibilité d'une unité sur le disque ou non, et reflète simplement les unités actuellement chargées en mémoire. Les signaux prennent deux paramètres : le nom de l'unité principale et le chemin de l'objet.

JobNew() et JobRemoved() sont envoyés chaque fois qu'un nouveau travail est mis en file d'attente ou retiré de la file d'attente. Les deux signaux prennent l'identifiant numérique du travail, le chemin du bus et le nom de l'unité principale pour ce travail comme arguments. JobRemoved() inclut également une chaîne de résultat qui est l'une des suivantes : "done", "canceled", "timeout", "failed", "dependency", ou "skipped". "done" indique l'exécution réussie d'un travail. "canceled" indique qu'un travail a été annulé (via CancelJob() ci-dessus) avant qu'il n'ait terminé son exécution (cela ne signifie pas nécessairement que l'opération du travail est réellement annulée aussi, voir ci-dessus). "timeout" indique que le délai d'attente du travail a été atteint. "failed" indique que le travail a échoué. "dependency" indique qu'un travail dont dépendait ce travail a échoué et que le travail a donc également été supprimé. "skipped" indique qu'un travail a été ignoré car il ne s'appliquait pas à l'état actuel de l'unité.

StartupFinished() est envoyé lorsque le démarrage est terminé. Il transporte six valeurs de temps en microsecondes, indiquant chacune combien de temps de démarrage a été passé dans le firmware (si connu), dans le chargeur de démarrage (si connu), dans la phase d'initialisation du noyau, dans l'initrd (si connu), dans l'espace utilisateur et au total. Ces valeurs peuvent également être calculées à partir des propriétés FirmwareTimestampMonotonic, LoaderTimestampMonotonic, InitRDTimestampMonotonic, UserspaceTimestampMonotonic et FinishTimestampMonotonic (voir ci-dessous).

UnitFilesChanged() est envoyé chaque fois que la liste des fichiers d'unité activés ou masqués sur le disque a changé.

Reloading() est envoyé juste avant qu'un rechargement du démon ne soit effectué (avec le paramètre booléen défini sur True) et après qu'un rechargement du démon soit terminé (avec le paramètre booléen défini sur False). Ceci peut être utilisé par les interfaces utilisateur pour optimiser les mises à jour de l'interface utilisateur.

Propriétés

La plupart des propriétés reflètent simplement les options respectives dans /etc/systemd/system.conf et la ligne de commande du noyau.

Les autres :

Version encode la chaîne de version de l'instance systemd en cours d'exécution. Notez que la chaîne de version est purement informative. Elle ne doit pas être analysée et l'on ne peut pas supposer que la version est formatée d'une manière particulière. Nous nous réservons le droit de modifier le schéma de versionnement à tout moment et il ne fait pas partie de l'API publique.

Features encode les fonctionnalités qui ont été activées et désactivées pour cette compilation. Les options activées sont préfixées par "+", les options désactivées par "-".

Tainted encode les drapeaux de souillure sous forme de liste séparée par des deux-points. Lorsque systemd détecte qu'il s'exécute sur un système présentant un problème, il définira un drapeau de souillure approprié. Les souillures peuvent être utilisées pour réduire la probabilité de rapports de bogues erronés. Les souillures suivantes sont actuellement connues :

"unmerged-usr"

/bin, /sbin et /lib* ne sont pas des liens symboliques vers leurs homologues sous /usr/. Pour plus d'informations sur ce problème, consultez Le cas de la fusion /usr[3].

Ajouté dans la version 252.

"unmerged-bin"

/usr/sbin n'est pas un lien symbolique vers /usr/bin/.

Ajouté dans la version 256.

"var-run-bad"

/run/ n'existe pas ou /var/run n'est pas un lien symbolique vers /run/.

Ajouté dans la version 252.

"cgroupsv1"

Le système utilise la hiérarchie dépréciée cgroup v1.

Ajouté dans la version 252.

"local-hwclock"

L'horloge matérielle locale (RTC) est configurée pour être en heure locale plutôt qu'en UTC.

Ajouté dans la version 252.

"support-ended"

Le système s'exécute après la fin du support déclaré par le fournisseur. Voir la description de SUPPORT_END= dans os-release(5).

Ajouté dans la version 252.

"old-kernel"

Le système exécute une version de noyau antérieure à la version minimale prise en charge par cette version de systemd.

Ajouté dans la version 252.

"overflowuid-not-65534", "overflowgid-not-65534"

L'UID ou le GID de débordement du noyau ont une valeur autre que 65534.

Ajouté dans la version 252.

"short-uid-range", "short-gid-range"

La plage d'UID ou de GID attribuée à l'instance systemd en cours d'exécution couvre moins que 0...65534.

Ajouté dans la version 252.

FirmwareTimestamp, FirmwareTimestampMonotonic, LoaderTimestamp, LoaderTimestampMonotonic, KernelTimestamp, KernelTimestampMonotonic, InitRDTimestamp, InitRDTimestampMonotonic, UserspaceTimestamp, UserspaceTimestampMonotonic, FinishTimestamp, FinishTimestampMonotonic, ShutdownStartTimestamp et ShutdownStartTimestampMonotonic encodent les timestamps en microsecondes de CLOCK_REALTIME et CLOCK_MONOTONIC pris lorsque le firmware a commencé son exécution, lorsque le chargeur de démarrage a commencé son exécution, lorsque le noyau a commencé son exécution, lorsque l'initrd a commencé son exécution, lorsque l'instance principale de systemd a commencé son exécution, lorsque tous les travaux de démarrage mis en file d'attente ont terminé leur exécution et enfin, lorsqu'une opération d'arrêt a commencé son exécution. Ces valeurs sont utiles pour déterminer les performances au démarrage. Notez que comme le temps monotone commence avec le démarrage du noyau, le timestamp KernelTimestampMonotonic sera toujours 0 et FirmwareTimestampMonotonic et LoaderTimestampMonotonic doivent être lus comme des valeurs négatives. De plus, tous les champs ne sont pas toujours disponibles, en fonction du firmware, du chargeur de démarrage ou de l'implémentation de l'initrd utilisé. Dans ces cas, les paires de timestamps respectives sont toutes deux à 0, indiquant qu'aucune donnée n'est disponible.

UnitsLoadTimestamp et UnitsLoadTimestampMonotonic encodent les timestamps en microsecondes CLOCK_REALTIME et CLOCK_MONOTONIC (comme décrit ci-dessus). Les timestamps sont pris chaque fois que le gestionnaire commence à charger les fichiers d'unité.

De même, les timestamps SecurityStartTimestamp, GeneratorsStartTimestamp et LoadUnitTimestamp (ainsi que leurs homologues monotonic et stop) exposent des données de performance pour le téléchargement des politiques de sécurité dans le noyau (telles que les politiques SELinux, IMA ou SMACK ), pour l'exécution des outils générateurs et pour le chargement des unités de fichiers.

NNames encode le nombre de noms d'unités actuellement connus. Cela n'inclut que les noms des unités actuellement chargées et peut être supérieur à la quantité d'unités réellement chargées, car les unités peuvent avoir plus d'un nom.

NJobs encode le nombre de tâches actuellement en file d'attente.

NInstalledJobs encode le nombre total de tâches ayant jamais été mises en file d'attente.

NFailedJobs encode le nombre total de tâches ayant échoué.

Progress encode la progression du démarrage sous forme de valeur flottante comprise entre 0,0 et 1,0. Cette valeur commence à 0,0 au début du démarrage et se termine à 1,0 une fois le démarrage terminé, et est basée sur le nombre de tâches exécutées et mises en file d'attente. Après le démarrage, ce champ est toujours 1,0, indiquant un démarrage terminé.

Environment encode le bloc d'environnement transmis à tous les services exécutés. Il peut être modifié par des appels de bus tels que SetEnvironment() (voir ci-dessus).

ShowStatus encode la politique actuelle de systemd pour l'affichage des messages de statut pendant le démarrage et l'arrêt. Sa valeur peut être n'importe quelle valeur valide pour le paramètre du noyau systemd.show_status (voir systemd(1)). Elle peut être modifiée à l'aide de SetShowStatus() (voir ci-dessus).

UnitPath encode le chemin de recherche des fichiers d'unités actuellement actif. C'est un tableau de chemins de système de fichiers encodés sous forme de chaînes de caractères.

SoftRebootsCount encode le nombre de redémarrages logiciels ayant été effectués avec succès depuis le dernier démarrage complet. Commence à "0".

Virtualization contient une courte chaîne d'identifiant décrivant la technologie de virtualisation sur laquelle le système s'exécute. Sur du matériel nu, il s'agit de la chaîne vide. Sinon, il contient un identifiant tel que "kvm", "vmware", etc. Pour une liste complète des identifiants, voir systemd-detect-virt(1). Notez que seule la technologie de virtualisation "la plus interne" est exportée ici. Ceci détecte à la fois les virtualisations de machine complète (VM) et la virtualisation à noyau partagé (conteneurs).

ConfidentialVirtualization contient une courte chaîne d'identifiant décrivant la technologie de virtualisation confidentielle sur laquelle le système s'exécute. Sur du matériel nu, il s'agit de la chaîne vide. Sinon, il contient un identifiant tel que "sev", "sev-es", "sev-snp", "tdx", etc. Pour une liste complète des identifiants, voir systemd-detect-virt(1).


.PP Architecture contient une courte chaîne d'identifiant décrivant l'architecture sur laquelle l'instance systemd s'exécute. Ceci suit le même vocabulaire que ConditionArchitectures=.

ControlGroup contient le chemin de la racine du groupe de contrôle de ce gestionnaire système. Notez que le chemin de la racine est encodé sous forme de chaîne vide ici (pas comme "/" !), de sorte qu'il puisse être facilement ajouté à /sys/fs/cgroup/systemd. Cette valeur sera définie sur la chaîne vide pour l'instance hôte et sur une autre chaîne pour les instances de conteneur.

AccessSELinuxContext contient le contexte SELinux utilisé pour contrôler l'accès à l'unité. Il est lu à partir du fichier d'unité lors de son chargement et mis en cache jusqu'à ce que le gestionnaire de services soit rechargé. Cette propriété contient une chaîne vide si SELinux n'est pas utilisé ou si aucune étiquette n'a pu être lue (par exemple, parce que l'unité n'est pas sauvegardée par un fichier sur disque).

SystemState contient l'état actuel du gestionnaire système. Les valeurs possibles sont :

"initializing"

Le système démarre et basic.target n'a pas encore été atteint.

"starting"

Le système démarre et basic.target a été atteint.

"running"

Le système a terminé son démarrage et aucune unité n'est dans l'état d'échec.

"degraded"

Le système a terminé son démarrage, mais certaines unités sont dans l'état d'échec.

"maintenance"

Le système a terminé son démarrage, mais il a été mis en mode secours ou de maintenance.

"stopping"

Le système s'arrête.

Sécurité

L'accès en lecture est généralement accordé à tous les clients. De plus, pour les clients non privilégiés, certaines opérations sont autorisées via le système de privilèges polkit. Les opérations qui modifient l'état de l'unité (StartUnit(), StopUnit(), KillUnit(), KillUnitSubgroup(), QueueSignalUnit(), RestartUnit() et similaires, SetProperty()) nécessitent org.freedesktop.systemd1.manage-units. Les opérations qui modifient l'état d'activation des fichiers d'unité (EnableUnitFiles(), DisableUnitFiles(), EnableUnitFilesWithFlags(), DisableUnitFilesWithFlags(), ReenableUnitFiles(), LinkUnitFiles(), PresetUnitFiles(), MaskUnitFiles() et similaires) nécessitent org.freedesktop.systemd1.manage-unit-files. Les opérations qui modifient l'environnement exporté (SetEnvironment(), UnsetEnvironment(), UnsetAndSetEnvironment()) nécessitent org.freedesktop.systemd1.set-environment. Reload() et Reexecute() nécessitent org.freedesktop.systemd1.reload-daemon. Les opérations qui déversent l'état interne nécessitent org.freedesktop.systemd1.bypass-dump-ratelimit pour éviter les limites de débit.

Méthodes

Start(), Stop(), Reload(), Restart(), TryRestart(), ReloadOrRestart(), ReloadOrTryRestart(), Kill(), KillSubgroup(), QueueSignal(), ResetFailed(), et SetProperties() implémentent la même opération que les méthodes respectives sur l'objet Manager (voir ci-dessus). Cependant, ces méthodes opèrent sur l'objet unité et ne prennent donc pas de paramètre de nom d'unité. Invoquer les méthodes directement sur l'objet Manager offre l'avantage de ne pas nécessiter d'appel à GetUnit() pour obtenir l'objet unité pour un nom d'unité spécifique. Appeler les méthodes sur l'objet Manager constitue donc une optimisation de trajet aller-retour.

Propriétés

Id contient le nom principal de l'unité.

Names contient tous les noms de l'unité, y compris le nom principal qui est également exposé dans Id.

Following contient soit la chaîne vide, soit le nom d'une autre unité dont cette unité suit l'état. Ceci est utilisé pour certaines unités de périphérique qui reflètent la machine d'état d'une autre unité, et dont l'unité dont il s'agit pourrait potentiellement changer.

Requires, RequiresOverridable, Requisite, RequisiteOverridable, Wants, BindsTo, RequiredBy, RequiredByOverridable, WantedBy, BoundBy, Conflicts, ConflictedBy, Before, After, OnFailure, Triggers, TriggeredBy, PropagatesReloadTo, et RequiresMountsFor contiennent des tableaux qui encodent les dépendances et leurs dépendances inverses (lorsque cela s'applique) telles que configurées dans le fichier unité ou déterminées automatiquement.

Description contient la chaîne de description lisible par l'homme pour l'unité.

SourcePath contient le chemin d'un fichier de configuration à partir duquel cette unité est générée automatiquement dans le cas où ce n'est pas une unité native (auquel cas elle contient la chaîne vide). Par exemple, toutes les unités de montage générées à partir de /etc/fstab ont ce champ défini sur /etc/fstab.

Documentation contient un tableau de chaînes avec les URL de la documentation pour cette unité.

LoadState contient une valeur d'état qui reflète si le fichier de configuration de cette unité a été chargé. Les états suivants sont actuellement définis : « loaded », « error », et « masked ». « loaded » indique que la configuration a été chargée avec succès. « error » indique que le chargement de la configuration a échoué. Le champ LoadError (voir ci-dessous) contient des informations sur la cause de cet échec. « masked » indique que l'unité est actuellement masquée (c'est-à-dire symlink vers /dev/null ou vide). Notez que le LoadState est entièrement orthogonal à l'ActiveState (voir ci-dessous) car les unités sans configuration valide chargée pourraient être actives (car la configuration pourrait avoir été rechargée à un moment où une unité était déjà active).

ActiveState contient une valeur d'état qui reflète si l'unité est actuellement active ou non. Les états suivants sont actuellement définis :

Tableau 1. États ACTIFS des unités

État Description
active Démarré, lié, branché, ..., selon le type d'unité.
inactive Arrêté, délié, débranché, ..., selon le type d'unité.
failed Similaire à inactive, mais l'unité a échoué d'une manière ou d'une autre (le processus a retourné un code d'erreur à la sortie, a planté, une opération a expiré, ou après trop de redémarrages).
activating Transition de inactive à active.
deactivating Transition de active à inactive.
maintenance L'unité est inactive et une opération de maintenance est en cours.
reloading L'unité est active et elle recharge sa configuration.
refreshing L'unité est active et un nouveau montage est en cours d'activation dans son espace de noms.

SubState
encode les états de la même machine d'état que couvre ActiveState, mais connaît des états plus granulaires qui sont spécifiques au type d'unité. Là où ActiveState ne couvre que huit états de haut niveau, SubState couvre potentiellement beaucoup plus d'états de bas niveau spécifiques au type d'unité qui sont mappés aux huit états de haut niveau. Notez que plusieurs états de bas niveau peuvent être mappés au même état de haut niveau, mais pas l'inverse. Tous les états de haut niveau n'ont pas de contreparties de bas niveau sur tous les types d'unités. À ce stade, les états de bas niveau ne sont pas documentés ici, et sont plus susceptibles d'être étendus plus tard que les états de haut niveau courants expliqués ci-dessus.

FragmentPath contient le chemin du fichier unité à partir duquel cette unité a été lue, s'il y en a un (sinon, il contient la chaîne vide).

UnitFileState encode l'état d'installation du fichier unité de FragmentPath. Il connaît actuellement les états suivants : « enabled », « enabled-runtime », « linked », « linked-runtime », « masked », « masked-runtim

e", "statique", "désactivé", et "invalide". "activé" indique qu'un fichier d'unité est activé en permanence. "activation-runtime" indique que le fichier d'unité n'est activé que temporairement et ne sera plus activé après un redémarrage (c'est-à-dire qu'il est activé via des liens symboliques /run/, plutôt que /etc/). "lié" indique qu'une unité est liée de manière permanente dans /etc/. "lié-runtime" indique qu'une unité est liée temporairement dans /run/ (jusqu'au prochain redémarrage). "masqué" indique que le fichier d'unité est masqué en permanence. "masqué-runtime" indique qu'il est masqué dans /run/ temporairement (jusqu'au prochain redémarrage). "statique" indique que l'unité est statiquement activée, c'est-à-dire toujours activée et ne nécessite pas d'être activée explicitement. "invalide" indique qu'il n'a pas été possible de déterminer si le fichier d'unité est activé.

InactiveExitTimestamp, InactiveExitTimestampMonotonic, ActiveEnterTimestamp, ActiveEnterTimestampMonotonic, ActiveExitTimestamp, ActiveExitTimestampMonotonic, InactiveEnterTimestamp, et InactiveEnterTimestampMonotonic contiennent des horodatages de 64 bits en microsecondes de CLOCK_REALTIME et CLOCK_MONOTONIC du dernier moment où une unité a quitté l'état inactif, est entrée dans l'état actif, est sortie de l'état actif, ou est entrée dans un état inactif. Ce sont les moments où l'unité a transitionné de "inactif"/"en échec" → "activation", "activation" → "actif", "actif" → "désactivation", et enfin "désactivation" → "inactif"/"en échec". Les champs sont à 0 si une telle transition n'a pas encore été enregistrée lors de ce démarrage.

CanStart, CanStop, et CanReload sont encodés comme des booléens pour indiquer si l'unité prend en charge les opérations de démarrage, d'arrêt ou de rechargement. Même si une unité prend en charge une telle opération, le client peut ne pas avoir les privilèges nécessaires pour les exécuter.

CanIsolate est encodé comme un booléen pour indiquer si l'unité peut être démarrée en mode d'isolation.

Job encode l'ID du travail et le chemin de l'objet du travail actuellement planifié ou exécuté pour cette unité, s'il y en a un. S'il n'y a pas de travail planifié ou exécuté, le champ ID du travail sera à 0.

StopWhenUnneeded, RefuseManualStart, RefuseManualStop, AllowIsolate, DefaultDependencies, OnFailureIsolate, IgnoreOnIsolate, IgnoreOnSnapshot correspondent directement aux paramètres booléens de configuration correspondants dans le fichier d'unité.

NeedDaemonReload est un booléen qui indique si le fichier de configuration à partir duquel cette unité est chargée (c'est-à-dire FragmentPath ou SourcePath) a changé depuis la lecture de la configuration et, par conséquent, si un rechargement de la configuration est recommandé.

Markers est un tableau de chaînes de caractères qui peuvent être définies à l'aide de SetUnitProperties() pour indiquer que le service doit être rechargé ou redémarré. Les valeurs connues actuellement sont "needs-restart" et "needs-reload". Les scripts de package peuvent utiliser la première pour marquer les unités pour un redémarrage ultérieur lorsqu'une nouvelle version du package est installée. Les scripts de gestion de configuration peuvent utiliser la seconde pour marquer les unités pour un rechargement ultérieur lorsque la configuration est ajustée. Ces indicateurs ne sont pas définis par le gestionnaire, sauf pour les désactiver de manière appropriée lorsque l'unité est arrêtée, redémarrée ou rechargée.

JobTimeoutUSec correspond directement au paramètre de configuration correspondant dans le fichier d'unité.

ConditionTimestamp et ConditionTimestampMonotonic contiennent les horodatages en microsecondes de CLOCK_REALTIME/CLOCK_MONOTONIC du dernier moment où les conditions configurées de l'unité ont été vérifiées, ou 0 si elles n'ont jamais été vérifiées. Les conditions sont vérifiées lorsqu'une unité est demandée à démarrer.

ConditionResult contient le résultat des conditions de la dernière vérification des conditions configurées de cette unité.

Conditions contient toutes les conditions configurées de l'unité. Pour chaque condition, cinq champs sont donnés : type de condition (par exemple, ConditionPathExists), si la condition est une condition de déclenchement, si la condition est inversée, la partie droite de la condition (par exemple, le chemin dans le cas de ConditionPathExists), et le statut. Le statut peut être 0, auquel cas la condition n'a pas encore été vérifiée, une valeur positive, auquel cas la condition a été satisfaite, ou une valeur négative, auquel cas la condition n'est pas remplie. Actuellement, seuls 0, +1 et -1 sont utilisés, mais des valeurs supplémentaires peuvent être utilisées à l'avenir, en conservant la signification des valeurs zéro/positive/négative.

LoadError contient une paire de chaînes de caractères. Si l'unité n'a pas pu être chargée (comme encodé dans LoadState, voir ci-dessus), cela inclura une paire d'erreurs D-Bus composée de l'ID d'erreur et d'une chaîne explicative lisible par l'homme sur ce qui s'est passé. Si le chargement a réussi, il s'agira d'une paire de chaînes vides.

Transient contient un booléen qui indique si l'unité a été créée en tant qu'unité transitoire (c'est-à-dire via StartTransientUnit() sur l'objet gestionnaire).

ActivationDetails contient une liste de paires clé-valeur qui décrivent l'événement qui a provoqué l'activation de l'unité, le cas échéant. La clé décrit l'information (par exemple : trigger_unit, avec la valeur foo.service). Ceci n'est rempli que si l'unité a été déclenchée par une unité Path ou Timer, et ce n'est fourni qu'à titre indicatif : il n'est pas garanti qu'il soit défini, et il n'est pas garanti qu'il soit le seul déclencheur. Il est seulement garanti qu'il s'agit d'un déclencheur valide qui a provoqué la mise en file d'attente et la réussite du travail d'activation. Les paires clé-valeur correspondent (en minuscules) aux variables d'environnement décrites dans la section "Variables d'environnement définies ou propagées par le gestionnaire de services" dans systemd.exec(5). Notez que de nouvelles paires clé-valeur peuvent être ajoutées à tout moment dans les versions futures. Les entrées existantes ne seront pas supprimées.

DebugInvocation contient un booléen qui passera à true lorsque l'unité sera redémarrée avec le niveau de journalisation défini sur débogage en raison d'une défaillance antérieure, et qui repassera à false lorsque l'unité démarrera avec succès ou que la limite de taux de redémarrage sera atteinte. Voir la section "RestartMode=" dans systemd.service(5) pour plus de détails.

Sécurité

De même que pour les méthodes de l'objet Manager, l'accès en lecture seule est autorisé pour tout le monde. Toutes les opérations sont autorisées pour les clients lorsque le privilège org.freedesktop.systemd1.manage-units est accordé par polkit.

Méthodes

BindMount() et MountImage() implémentent les mêmes opérations que les méthodes respectives sur l'objet Manager (voir ci-dessus). Cependant, ces méthodes opèrent sur l'objet service et n'acceptent donc pas de paramètre de nom d'unité. L'invocation des méthodes directement sur l'objet Manager présente l'avantage de ne pas nécessiter d'appel GetUnit() pour obtenir l'objet unité pour un nom d'unité spécifique. L'appel des méthodes sur l'objet Manager est donc une optimisation d'aller-retour.

DumpFileDescriptorStore() renvoie un tableau d'informations sur les descripteurs de fichiers actuellement présents dans le magasin de descripteurs de fichiers du service. Chaque entrée se compose d'un nom de descripteur de fichier (c'est-à-dire le champ FDNAME=), du type d'inode et du mode d'accès du descripteur de fichier sous forme d'entier (c'est-à-dire une valeur mode_t, des indicateurs tels que S_IFREG, S_IRUSR, ...), des numéros majeur et mineur du numéro de périphérique du système de fichiers sous-jacent à l'inode du descripteur de fichier, du numéro d'inode, des numéros majeur et mineur du numéro de périphérique s'il fait référence à un nœud de périphérique caractère ou bloc, d'un chemin de système de fichiers pointant vers l'inode et des indicateurs de descripteur de fichier (c'est-à-dire O_RDWR, O_RDONLY, ...).

Propriétés

La plupart des propriétés de l'interface Service correspondent directement aux paramètres correspondants dans les fichiers d'unité de service. Par souci de brièveté, voici une liste des exceptions uniquement :

TimeoutStartUSec, TimeoutStopUSec et TimeoutAbortUSec contiennent les délais de démarrage, d'arrêt et d'interruption, en microsecondes. Notez la légère différence de nom par rapport aux paramètres correspondants du fichier d'unité (voir systemd.service(5)) : ces propriétés de bus utilisent strictement les microsecondes (et sont donc suffixées ...USec) tandis que les paramètres du fichier d'unité sont par défaut dans une unité de temps de secondes (et sont donc suffixés ...Sec), sauf si une autre unité est explicitement spécifiée. Cela reflète le fait que le gestionnaire de service opère en interne uniquement en unités de microsecondes, et que les propriétés du bus sont un concept de niveau relativement bas (binaire) qui expose cela. Les paramètres du fichier d'unité, en revanche, sont des concepts de niveau relativement élevé (basés sur des chaînes) et prennent donc en charge des spécifications de temps plus conviviales qui sont par défaut dans les unités de temps de secondes mais permettent également d'autres unités, si spécifiées.

WatchdogTimestamp et WatchdogTimestampMonotonic contiennent les horodatages en microsecondes de CLOCK_REALTIME/CLOCK_MONOTONIC du dernier ping de surveillance reçu du service, ou 0 si aucun n'a jamais été reçu.

ExecStartPre, ExecStart, ExecStartPost, ExecReload, ExecStop et ExecStop sont des tableaux de structures où chaque structure contient : le chemin binaire à exécuter ; un tableau avec tous les arguments à passer à la commande exécutée, en commençant par l'argument 0 ; un booléen indiquant s'il faut considérer comme un échec si le processus se termine de manière incorrecte ; deux paires d'horodatages en microsecondes CLOCK_REALTIME/CLOCK_MONOTONIC indiquant quand le processus a commencé et s'est terminé la dernière fois, ou 0 s'il n'a jamais été exécuté ou jamais terminé ; le PID du processus, ou 0 s'il n'a pas encore été exécuté ; le code de sortie et le statut de la dernière exécution. Ce champ correspond donc plus ou moins au paramètre correspondant dans le fichier d'unité de service mais est complété par des données d'exécution.

LimitCPU (et propriétés associées) correspondent plus ou moins directement aux paramètres correspondants dans les fichiers d'unité de service, sauf que s'ils ne sont pas définis, leur valeur est 18446744073709551615 (c'est-à-dire -1).

Capabilities contient les capacités configurées, formatées avec cap_to_text(3).

SecureBits, CapabilityBoundingSet, MountFlags correspondent également aux paramètres configurés des fichiers d'unité, mais au lieu d'être formatés sous forme de chaînes, ils sont encodés sous forme des indicateurs binaires réels qu'ils sont.

ExecMainStartTimestamp, ExecMainStartTimestampMonotonic, ExecMainExitTimestamp, ExecMainExitTimestampMonotonic, ExecMainHandoffTimestamp, ExecMainHandoffTimestampMonotonic, ExecMainPID, ExecMainCode, ExecMainStatus contiennent des informations sur le processus principal du service dans la mesure où il est connu. Les horodatages ExecMainStartTimestamp enregistrent quand le processus principal du service est créé. Les horodatages ExecMainExitTimestamp enregistrent quand la sortie du processus principal a été détectée par le gestionnaire de service. Les horodatages ExecMainHandoffTimestamp enregistrent quand le binaire du service est sur le point d'être exécuté par systemd-executor (cet horodatage est enregistré que l'appel système execve() immédiatement suivant réussisse ou échoue). Il s'agit souvent des mêmes informations d'exécution qui sont également maintenues pour ExecStart=. Cependant, cela diffère pour les services avec Type=forking ainsi que pour les services qui utilisent des messages sd_notify() MAINPID= car le processus principal du service n'est pas directement dissocié par le gestionnaire de service dans ce cas. Ces champs contiennent soit des informations de la dernière exécution du processus, soit du processus en cours d'exécution.

MainPID et ControlPID contiennent le PID principal et le PID de contrôle du service. Le PID principal est le PID principal actuel du service et est 0 lorsque le service n'a actuellement aucun PID principal. Le PID de contrôle est le PID du processus de démarrage/arrêt/rechargement en cours d'exécution et est 0 si aucun processus de ce type n'est actuellement en cours. Cela signifie que ExecMainPID et MainPID diffèrent en ce que ce dernier reflète immédiatement si un processus principal est actuellement en cours d'exécution tandis que le premier peut contenir des informations collectées lors de la dernière exécution, même si le processus n'est plus là.

StatusText, StatusErrno, StatusBusError et StatusVarlinkError contiennent respectivement le texte d'état, le numéro d'erreur et le nom d'erreur D-Bus/Varlink passés au gestionnaire de service via sd_notify(3). Ils peuvent être utilisés par les services pour informer le gestionnaire de service de leur état interne.

Result encode le résultat d'exécution de la dernière exécution du service. Il est utile de déterminer la raison pour laquelle un service a échoué s'il est dans l'état « échec » (voir ActiveState ci-dessus). Les valeurs suivantes sont actuellement connues : « success » est défini si l'unité n'a pas échoué. « resources » indique que les ressources disponibles n'étaient pas suffisantes pour créer et exécuter les processus du service. « timeout » indique qu'un délai d'attente s'est produit lors de l'exécution d'une opération de service. « exit-code » indique qu'un processus de service s'est terminé avec un code de sortie incorrect. « signal » indique qu'un processus de service s'est terminé avec un signal non intercepté. « core-dump » indique qu'un processus de service s'est terminé de manière incorrecte et a généré un core dump. « watchdog » indique qu'un service n'a pas envoyé de messages de ping de surveillance suffisamment souvent. « start-limit-hit » indique qu'un service a été démarré trop fréquemment dans un laps de temps spécifique (tel que configuré dans StartLimitInterval, StartLimitBurst). « oom-kill » indique qu'un service a été terminé en raison d'une situation de manque de mémoire (OOM).

ControlGroup indique le chemin du groupe de contrôle dans lequel les processus de cette unité de service sont placés.

Les propriétés suivantes correspondent 1:1 aux paramètres correspondants du fichier d'unité : RootDirectory RootImage RootImageOptions RootVerity RootHash RootHashSignature MountImages ExtensionImages ExtensionDirectories voir systemd.exec(5) pour leur signification.

MemoryAvailable prend en compte les « MemoryMax » ou « MemoryHigh » de l'unité et de ses parents ou la RAM physiquement disponible par rapport à la consommation mémoire du niveau donné et prend le minimum. Attention, d'autres unités sous la tranche parente la plus stricte peuvent consommer la mémoire plus rapidement et moins que la valeur rapportée ne resterait pour l'allocation propre. Cela fonctionne mieux en conjonction avec MemoryAccounting=yes sur les unités impliquées.

DelegateSubgroup contient le sous-groupe cgroup dans lequel placer les processus des unités invoquées. Tel que configuré par l'option du même nom dans les fichiers d'unité. Ceci est défini comme une chaîne vide lorsqu'il ne s'applique pas ou qu'aucun sous-groupe n'a été configuré.

RuntimeDirectorySymlink, StateDirectorySymlink, CacheDirectorySymlink et LogsDirectorySymlink implémentent respectivement le paramètre de destination des paramètres de fichier d'unité RuntimeDirectory, StateDirectory, CacheDirectory et LogsDirectory, qui créeront un lien symbolique du nom donné vers le répertoire respectif. Les messages prennent un paramètre flags qui rend le répertoire en lecture seule :

#define SD_EXEC_DIRECTORY_READ_ONLY            (UINT64_C(1) << 0)

ExtraFileDescriptorNames contient les noms des descripteurs de fichiers passés au service via la propriété ExtraFileDescriptors de la méthode StartTransientUnit(). Voir sd_listen_fds(3) pour plus d'informations sur la manière de récupérer ces descripteurs de fichiers. Contrairement à la propriété d'entrée ExtraFileDescriptors, ExtraFileDescriptorNames ne contient que des noms et non les descripteurs de fichiers.

ManagedOOMMemoryPressureDurationUSec implémente le paramètre de destination du paramètre de fichier d'unité ManagedOOMMemoryPressureDurationSec= listé dans systemd.resource-control(5). Notez que l'unité de temps est exprimée en « μs ».

ProtectControlGroupsEx implémente le paramètre de destination du paramètre de fichier d'unité ProtectControlGroups= listé dans systemd.exec(5). Contrairement au booléen ProtectControlGroups, ProtectControlGroupsEx est de type chaîne.

PrivatePIDs implémente le paramètre de destination du paramètre de fichier d'unité PrivatePIDs= listé dans systemd.exec(5). Notez que PrivatePIDs est de type chaîne pour permettre l'ajout de valeurs à l'avenir.

ProtectHostnameEx implémente le paramètre de destination du paramètre de fichier d'unité ProtectHostname= listé dans systemd.exec(5). Contrairement à ProtectHostname, qui est un booléen, ProtectHostnameEx est une paire de chaînes de caractères. La première est une chaîne booléenne ou la valeur spéciale « private », et la seconde est un nom d'hôte privé optionnel qui sera défini dans un nouvel espace de noms UTS pour l'unité.

Les propriétés *PollLimitIntervalUSec* et *PollLimitBurst* configurent la limite de scrutation pour l'unité de socket. Attend une durée en µs et un entier non signé, respectivement. Si l'une d'elles est mise à zéro, la fonctionnalité de limitation est désactivée.

Propriétés

La plupart des propriétés correspondent directement aux paramètres des fichiers d'unité de socket. Les unités de socket peuvent inclure des champs *ExecStartPre* (et similaires) qui contiennent des informations sur les processus à exécuter. Elles partagent également la plupart des champs relatifs au contexte d'exécution que les objets Service exposent (voir ci-dessus).

En plus de ces propriétés, il y a les suivantes :

*NAccepted* contient le nombre cumulé de connexions jamais acceptées sur ce socket. Ceci ne s'applique qu'aux sockets avec *Accept* réglé sur "yes", c'est-à-dire ceux pour lesquels systemd est responsable des connexions acceptées.

De même, *NConnections* contient le nombre de connexions actuellement ouvertes sur ce socket. Ceci ne s'applique qu'aux unités de socket avec *Accept* réglé sur "yes".

*Result* encode la raison pour laquelle une unité de socket a échoué si elle est dans l'état "failed" (voir *ActiveState* ci-dessus). Les valeurs "success", "resources", "timeout", "exit-code", "signal" et "core-dump" ont la même signification que pour le champ correspondant des unités de service (voir ci-dessus). De plus, la valeur "service-failed-permanent" indique que le service de ce socket a échoué de manière permanente.

*FlushPending* spécifie si le socket doit être vidé juste avant d'entrer dans l'état d'écoute. Ce paramètre ne s'applique qu'aux sockets avec *Accept=no*.

Propriétés

Unit contient le nom de l'unité à activer lorsque la minuterie expire.

TimersMonotonic contient un tableau de structures qui contiennent des informations sur toutes les minuteries monotones de cette unité de minuterie. Les structures contiennent une chaîne identifiant la base de la minuterie, qui est l'une des valeurs "OnActiveUSec", "OnBootUSec", "OnStartupUSec", "OnUnitActiveUSec" ou "OnUnitInactiveUSec" qui correspondent aux paramètres des mêmes noms dans les fichiers d'unité de minuterie ; le décalage en microsecondes par rapport à cette base de minuterie en temps monotone ; le prochain point d'expiration sur l'horloge CLOCK_MONOTONIC, par rapport à son époque.

TimersCalendar contient un tableau de structures qui contiennent des informations sur toutes les minuteries temps réel/calendrier de cette unité de minuterie. Les structures contiennent une chaîne identifiant la base de la minuterie, qui ne peut être que "OnCalendar" pour le moment ; la chaîne de spécification du calendrier ; le prochain point d'expiration sur l'horloge CLOCK_REALTIME, par rapport à son époque.

NextElapseUSecRealtime contient le prochain point d'expiration sur l'horloge CLOCK_REALTIME en microsecondes depuis l'époque, ou 0 si cet événement de minuterie n'inclut pas au moins un événement de calendrier.

De même, NextElapseUSecMonotonic contient le prochain point d'expiration sur l'horloge CLOCK_MONOTONIC en microsecondes depuis l'époque, ou 0 si cet événement de minuterie n'inclut pas au moins un événement monotone.

Result connaît les valeurs "success" et "resources" avec les mêmes significations que les valeurs correspondantes de la propriété de l'interface de service.

NAME

systemd.directives - Directives pour les fichiers de configuration de systemd

INTRODUCTION

Ce document décrit les directives de configuration qui sont utilisées dans les divers fichiers de configuration de systemd, comme ceux dans /etc/systemd/system, /etc/systemd/user, /usr/lib/systemd/system, /usr/lib/systemd/user, /etc/tmpfiles.d/, /usr/lib/tmpfiles.d/, /etc/environment-d/, et /usr/lib/environment-d/.

Les directives sont organisées par type de fichier de configuration, et par catégorie lorsque cela est approprié. Certaines directives ne sont valides que dans certains contextes.
