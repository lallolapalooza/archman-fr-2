NOM

ovs-ofctl - administrer les commutateurs OpenFlow

SYNOPIS

ovs-ofctl [options] commande [commutateur] [args...]

DESCRIPTION

L'outil ovs-ofctl est une interface en ligne de commande pour surveiller et administrer les commutateurs OpenFlow. Il peut également afficher l'état actuel d'un commutateur OpenFlow, y compris ses fonctionnalités, sa configuration et les entrées de ses tables. Il devrait fonctionner avec n'importe quel commutateur OpenFlow, pas seulement avec Open vSwitch.

Commandes de gestion des commutateurs OpenFlow

Ces commandes permettent à ovs-ofctl de surveiller et d'administrer un commutateur OpenFlow. Il est capable d'afficher l'état actuel d'un commutateur, y compris ses fonctionnalités, sa configuration et les entrées de ses tables.

La plupart de ces commandes prennent un argument qui spécifie la méthode de connexion à un commutateur OpenFlow. Les méthodes de connexion suivantes sont prises en charge :

ssl:hôte[:port]

tcp:hôte[:port]
Le port spécifié sur l'hôte donné, qui peut être exprimé soit sous forme de nom DNS (si compilé avec la bibliothèque unbound) soit sous forme d'adresse IP au format IPv4 ou IPv6. Encadrez les adresses IPv6 entre crochets, par exemple tcp:[::1]:6653. Sur Linux, utilisez %périphérique pour désigner une portée pour les adresses de niveau lien IPv6, par exemple tcp:[fe80::1234%eth0]:6653. Pour ssl, les options --private-key, --certificate et --ca-cert sont obligatoires.
Si le port n'est pas spécifié, la valeur par défaut est 6653.
unix:fichier
Sur POSIX, un socket serveur de domaine Unix nommé fichier.
Sous Windows, connectez-vous à un pipe nommé local représenté par un fichier créé dans le chemin fichier pour imiter le comportement d'un socket de domaine Unix.
fichier
Ceci est un raccourci pour unix:fichier, tant que fichier ne contient pas de deux-points.
pont
Ceci est un raccourci pour unix:/run/openvswitch/pont.mgmt, tant que pont ne contient pas de deux-points.
[type@]dp
Tente de rechercher le pont associé à dp et de l'ouvrir comme ci-dessus. Si type est fourni, il spécifie le fournisseur de dataplane de dp, sinon le fournisseur par défaut system est supposé.
show commutateur
Affiche sur la console des informations sur le commutateur, y compris des informations sur ses tables de flux et ses ports.
dump-tables commutateur
Affiche sur la console des statistiques pour chacune des tables de flux utilisées par le commutateur.
dump-table-features commutateur
Affiche sur la console les fonctionnalités de chacune des tables de flux utilisées par le commutateur.
dump-table-desc commutateur
Affiche sur la console la configuration de chacune des tables de flux utilisées par le commutateur pour OpenFlow 1.4+.
mod-table commutateur table paramètre
Cette commande configure les paramètres de la table de flux dans le commutateur pour la table OpenFlow table, qui peut être exprimée sous forme de nombre ou (sauf si --no-names est spécifié) de nom.
Les paramètres disponibles dépendent de la version d'OpenFlow utilisée. En OpenFlow 1.1 et 1.2 (qui doit être activé avec l'option -O) uniquement, mod-table configure le comportement lorsqu'aucun flux n'est trouvé lors de la recherche d'un paquet dans une table de flux. Les valeurs de paramètre suivantes sont disponibles :
drop
Jeter le paquet.
continue
Continuer vers la table suivante dans le pipeline. (C'est ainsi qu'un commutateur OpenFlow 1.0 traite toujours les paquets qui ne correspondent à aucun flux, dans les tables autres que la dernière.)
controller
Envoyer au contrôleur. (C'est ainsi qu'un commutateur OpenFlow 1.0 traite toujours les paquets qui ne correspondent à aucun flux dans la dernière table.)
En OpenFlow 1.3 et versions ultérieures (qui doit être activé avec l'option -O) et Open vSwitch 2.11 et versions ultérieures uniquement, mod-table peut modifier le nom d'une table :
name:nouveau-nom
Change le nom de la table en nouveau-nom. Utilisez un nouveau-nom vide pour effacer le nom. (Ceci sera inefficace si le nom est défini via la colonne name dans la table Flow_Table de la base de données Open_vSwitch, comme décrit dans ovs-vswitchd.conf.db(5).)
En OpenFlow 1.4 et versions ultérieures (qui doit être activé avec l'option -O) uniquement, mod-table configure le comportement lorsqu'un contrôleur tente d'ajouter un flux à une table de flux pleine. Les valeurs de paramètre suivantes sont disponibles :
evict
Supprime un flux existant de la table de flux, selon l'algorithme décrit pour la table Flow_Table dans ovs-vswitchd.conf.db(5).
noevict
Refuse d'ajouter le nouveau flux. (L'éviction peut toujours être activée via la colonne overflow_policy dans la table Flow_Table documentée dans ovs-vswitchd.conf.db(5).)
vacancy:bas,haut
Active l'envoi d'événements de vacance aux contrôleurs à l'aide de messages TABLE_STATUS, basés sur les seuils de pourcentage bas et haut.
novacancy
Désactive les événements de vacance.
dump-ports commutateur [netdev]
Affiche sur la console des statistiques sur les périphériques réseau associés au commutateur. Si netdev est spécifié, seules les statistiques associées à ce périphérique seront affichées. netdev peut être un numéro de port attribué par OpenFlow ou un nom de périphérique, par exemple eth0.
dump-ports-desc commutateur [port]
Affiche sur la console des informations détaillées sur les périphériques réseau associés au commutateur. Pour afficher uniquement un port spécifique, spécifiez son numéro en tant que port. Sinon, si port est omis, ou s'il est spécifié comme ANY, tous les ports sont affichés. Ceci est un sous-ensemble des informations fournies par la commande show.
Si la connexion au commutateur négocie OpenFlow 1.0, 1.2 ou 1.2, cette commande utilise une extension OpenFlow implémentée uniquement dans Open vSwitch (version 1.7 et ultérieures).
Seulement OpenFlow 1.5 et versions ultérieures prennent en charge l'affichage d'un port spécifique. Les versions antérieures d'OpenFlow affichent toujours tous les ports.
mod-port commutateur port action
Modifie les caractéristiques du port port dans le commutateur. port peut être un numéro ou un nom de port OpenFlow (sauf si --no-names est spécifié) ou le mot-clé LOCAL (la manière préférée de désigner le port local OpenFlow). L'action peut être l'une des suivantes :

up

down
Active ou désactive l'interface. Ceci est équivalent à ip link set up ou ip link set down sur un système Unix.
stp

no
Désactive ou active STP (Spanning Tree Protocol) pour le port.
cost:valeur
Définit le coût du port. Cette valeur est utilisée par le protocole STP. Une valeur plus faible indique un coût plus faible. La valeur par défaut est 0.
port-speed:valeur
Définit la vitesse du port. La valeur doit être une puissance de 2, représentant la vitesse en mégabits par seconde (par exemple, 1000 pour 1 Gbit/s). La valeur 0 désactive la vitesse.

Pour utiliser les options mod-port, la négociation de la version d'OpenFlow doit être gérée par l'option -O ou par la configuration du contrôleur.

dump-ports-amsmath commutateur [port]
Affiche sur la console des statistiques sur les nombres de paquets et d'octets pour les ports du commutateur. Si port est spécifié, affiche les statistiques pour ce port uniquement. Sinon, affiche les statistiques pour tous les ports.
dump-flows commutateur [options]
Imprime sur la console les flux du commutateur. Les options suivantes sont disponibles :
--names
Affiche les noms des groupes de ports, des types de ports, des champs de flux, des actions de flux, etc., au lieu de leurs nombres correspondants.
--no-names
L'inverse de --names. Ce comportement est le comportement par défaut.
--sort
Trie les flux par priorité descendante.
--no-sort
L'inverse de --sort. Ce comportement est le comportement par défaut.
--stats
Affiche des statistiques sur les flux, y compris le nombre de paquets et d'octets, le temps de vie des flux et les statistiques de groupe.
--idle-timeout=secondes
Ne montre que les flux qui ont expiré après secondes. Ce paramètre ne fonctionne qu'avec les versions d'OpenFlow 1.1 et ultérieures.
--hard-timeout=secondes
Ne montre que les flux dont le délai d'expiration matériel a expiré après secondes. Ce paramètre ne fonctionne qu'avec les versions d'OpenFlow 1.1 et ultérieures.
match

table=table
Ne montre que les flux dans la table spécifiée. La table peut être un numéro ou un nom.
add switch table [priority] match action...
Ajoute un flux au commutateur. table spécifie la table de flux dans laquelle ajouter le flux. priority est un entier facultatif spécifiant la priorité du flux (plus le nombre est élevé, plus la priorité est élevée ; la valeur par défaut est 100). match spécifie les critères de correspondance du flux. action spécifie l'action à effectuer lorsque le flux correspond. Les actions peuvent être séparées par des virgules.
mkkey field...
Crée un champ de flux qui peut être utilisé pour créer un flux. Les champs peuvent être spécifiés en utilisant le format du langage de filtrage des flux, par exemple ip,tcp,eth_src=00:01:02:03:04:05.
del switch [table] [match]
Supprime des flux du commutateur. Si table et match sont spécifiés, tous les flux correspondant sont supprimés. Si seule la table est spécifiée, tous les flux de cette table sont supprimés. Si aucun argument n'est spécifié, tous les flux de toutes les tables sont supprimés.
mod-flows switch [table] [match] actions...
Modifie les actions des flux existants dans le commutateur. Les arguments table et match sont facultatifs et fonctionnent de la même manière que pour la commande del. Les actions spécifient les nouvelles actions à appliquer aux flux correspondants.
test-flows switch file
Lit les spécifications de flux à partir du fichier et les teste sur le commutateur. Les spécifications de flux doivent être au format spécifié pour la commande dump-flows.
bundle switch [port]
Crée un bundle de ports sur le commutateur. Si port est spécifié, le bundle est créé pour ce port. Sinon, un bundle est créé pour tous les ports.
group switch [options]
Gère les groupes sur le commutateur. Les options suivantes sont disponibles :
dump-groups switch
Affiche tous les groupes sur le commutateur.
group-type commutateur type
Affiche les groupes du type spécifié sur le commutateur.
add-group commutateur type actions...
Ajoute un nouveau groupe de type type avec les actions spécifiées au commutateur.
del-group commutateur [group]
Supprime les groupes du commutateur. Si group est spécifié, seul ce groupe est supprimé.
mod-group commutateur group actions...
Modifie un groupe existant sur le commutateur. group spécifie le groupe à modifier, et actions spécifie les nouvelles actions.
meter switch [options]
Gère les compteurs sur le commutateur. Les options suivantes sont disponibles :
dump-meters switch
Affiche tous les compteurs sur le commutateur.
meter-type switch type
Affiche les compteurs du type spécifié sur le commutateur.
add-meter switch type bands...
Ajoute un nouveau compteur de type type avec les bandes spécifiées au commutateur.
del-meter switch [meter]
Supprime les compteurs du commutateur. Si meter est spécifié, seul ce compteur est supprimé.
mod-meter switch meter bands...
Modifie un compteur existant sur le commutateur. meter spécifie le compteur à modifier, et bands spécifie les nouvelles bandes.
monitor switch [options]
Surveille les flux du commutateur et affiche les événements reçus. Les options suivantes sont disponibles :
event=event[,event]...
Seulement pour les événements spécifiés. Les événements disponibles sont : packet-in, flow-rem, port-status, table-status, flow-mod-failed.
duration=secondes
Arrête la surveillance après secondes.
version switch
Affiche la version du protocole OpenFlow prise en charge par le commutateur.
new=file
Lit les spécifications de flux à partir du fichier et les ajoute au commutateur. Les spécifications de flux doivent être au format spécifié pour la commande dump-flows.
snoop switch [port]
Capture les paquets du commutateur. Si port est spécifié, seuls les paquets du port spécifié sont capturés. Sinon, tous les paquets sont capturés. Les paquets capturés sont envoyés à la sortie standard au format pcap.
get-config switch
Affiche la configuration du commutateur.
set-config switch config
Définit la configuration du commutateur. La configuration doit être une liste de paires clé-valeur séparées par des virgules.
ssl-purge switch
Supprime toutes les connexions SSL du commutateur.
ct-clear switch [match]
Supprime toutes les connexions de suivi de connexion (connection tracking) du commutateur. Si match est spécifié, seules les connexions correspondant au match sont supprimées.
set-active-fault-tolerance-minimal-miss-timeout switch timeout
Définit le délai d'attente minimal pour les tentatives de connexion aux commutateurs. La valeur timeout est en secondes.
set-send-flow-rem-on-snoop switch value
Définit si les notifications de suppression de flux doivent être envoyées lorsqu'un snooping de paquet est actif. La valeur peut être true ou false.

OPTIONS

--strict
Exige que toutes les opérations réussissent. En cas d'échec d'une seule opération, ovs-ofctl renvoie un code de sortie d'erreur.
--NO--STRICT
L'inverse de --strict. Les opérations qui échouent ne sont pas signalées.
-F FOND[,FOND]...
Spécifie un ou plusieurs fichiers de spécification de flux. ovs-ofctl charge les flux à partir de ces fichiers et les applique au commutateur. Les fichiers doivent être au format spécifié pour la commande dump-flows.
-P PRIORITÉ
Spécifie la priorité des flux ajoutés à l'aide de l'option -F. La valeur par défaut est 100.
-t SECONDES
Définit le délai d'attente pour les opérations de connexion et de commande sur le commutateur. La valeur par défaut est 5 secondes.
--timeout=SECONDES
Identique à -t.
-C FICHIER
Lit les spécifications de flux à partir du fichier et les supprime du commutateur.
--flow-removals-file=FICHIER
Identique à -C.
--strict-cookie
Lors de la suppression de flux, exige que le cookie corresponde exactement.
--NO--STRICT--COOKIE
L'inverse de --strict-cookie.
-W FICHIER
Lit les spécifications de flux à partir du fichier et les modifie sur le commutateur.
--flow-modifications-file=FICHIER
Identique à -W.
-A ACTIONS
Spécifie les actions à appliquer aux flux lors de la modification de flux à l'aide de l'option -W.
--actions=ACTIONS
Identique à -A.
-O VER
Utilise la version du protocole OpenFlow spécifiée par VER. Les valeurs valides sont OpenFlow10, OpenFlow11, OpenFlow12, OpenFlow13, OpenFlow14, OpenFlow15. Si cette option n'est pas spécifiée, ovs-ofctl essaie de négocier automatiquement la version du protocole avec le commutateur. Les valeurs peuvent être spécifiées en majuscules ou en minuscules.
-h
--help
Affiche un message d'aide et quitte.
-V
--version
Affiche des informations sur la version et quitte.

CONFIGURATION TLS

Pour se connecter à un commutateur à l'aide de TLS, il est nécessaire de configurer les certificats et clés TLS appropriés. Les options suivantes sont disponibles :

--private-key=PEM-FILE
Fichier contenant la clé privée du certificat du client.
--certificate=PEM-FILE
Fichier contenant le certificat du client.
--ca-cert=PEM-FILE
Fichier contenant le certificat de l'autorité de certification.
--peer-ca-cert=PEM-FILE
Fichier contenant le certificat de l'autorité de certification du pair. Ceci est utilisé pour vérifier le certificat du serveur.
--ssl-allow-invalid-cert
Autorise les certificats invalides. Ceci est utile pour les tests, mais ne doit pas être utilisé en production.

EXEMPLES

Afficher les informations sur le commutateur my-switch :
ovs-ofctl show my-switch
Afficher les flux du commutateur my-switch :
ovs-ofctl dump-flows my-switch
Ajouter un flux au commutateur my-switch :
ovs-ofctl add-flow my-switch in_port=1,actions=output:2
Supprimer tous les flux du commutateur my-switch :
ovs-ofctl del-flows my-switch
Surveiller les paquets sur le commutateur my-switch :
ovs-ofctl monitor my-switch -- 

  event=packet-in -- 

  duration=10

>no-stp
Active ou désactive le protocole de spanning tree 802.1D (STP) sur l'interface. Les implémentations OpenFlow qui ne prennent pas en charge le STP refuseront de l'activer.
receive

no-receive

receive-stp

no-receive-stp
Active ou désactive le traitement OpenFlow des paquets reçus sur cette interface. Lorsque le traitement des paquets est désactivé, les paquets seront ignorés au lieu d'être traités via la table OpenFlow. Le réglage receive ou no-receive s'applique à tous les paquets sauf les paquets de spanning tree 802.1D, qui sont contrôlés séparément par receive-stp ou no-receive-stp.
forward

no-forward
Autorise ou refuse la transmission du trafic vers cette interface. Par défaut, la transmission est activée.
flood

no-flood
Contrôle si une action OpenFlow flood envoie du trafic hors de cette interface. Par défaut, le flood est activé. Désactiver le flood est principalement utile pour éviter les boucles lorsqu'un protocole de spanning tree n'est pas utilisé.
packet-in

no-packet-in
Contrôle si les paquets reçus sur cette interface qui ne correspondent pas à une entrée de table de flux génèrent un message « packet in » vers le contrôleur OpenFlow. Par défaut, les messages « packet in » sont activés.
La commande show affiche (entre autres informations) la configuration que mod-port modifie.
get-frags switch
Affiche le mode de gestion des fragments du switch. Voir set-frags, ci-dessous, pour une description de chaque mode de gestion des fragments.
La commande show affiche également le mode de gestion des fragments parmi ses autres sorties.
set-frags switch frag_mode
Configure le traitement des fragments IPv4 et IPv6 par le switch. Les choix pour frag_mode sont :
normal
Les fragments traversent la table de flux comme les paquets non fragmentés. Les ports TCP, les ports UDP et les champs type et code ICMP sont toujours définis sur 0, même pour les fragments où ces informations seraient autrement disponibles (fragments avec un décalage de 0). C'est le mode de gestion des fragments par défaut pour un commutateur OpenFlow.
drop
Les fragments sont ignorés sans passer par la table de flux.
reassemble
Le commutateur réassemble les fragments en paquets IP complets avant de les transmettre à la table de flux. Open vSwitch n'implémente pas ce mode de gestion des fragments.
nx-match
Les fragments traversent la table de flux comme les paquets non fragmentés. Les ports TCP, les ports UDP et les champs type et code ICMP sont disponibles pour la correspondance pour les fragments avec un décalage de 0, et définis sur 0 dans les fragments avec un décalage non nul. Ce mode est une extension Nicira.
Voir la description de ip_frag, dans ovs-fields(7), pour une façon de faire correspondre si un paquet est un fragment et sur son décalage de fragment.
dump-flows switch [flows]
Affiche sur la console toutes les entrées de flux dans les tables du switch qui correspondent à flows. Si flows est omis, tous les flux du commutateur sont récupérés. Voir Syntaxe des flux, ci-dessous, pour la syntaxe de flows. Le format de sortie est décrit dans Sortie des entrées de table .
Par défaut, ovs-ofctl affiche les entrées de flux dans le même ordre que le commutateur les envoie, ce qui est peu susceptible d'être intuitif ou cohérent. Utilisez --sort et --rsort pour contrôler l'ordre d'affichage. Les options --names/--no-names et --stats/--no-stats affectent également le format de sortie. Voir les descriptions de ces options, sous OPTIONS ci-dessous, pour plus d'informations.
dump-aggregate switch [flows]
Affiche sur la console les statistiques agrégées pour les flux dans les tables du switch qui correspondent à flows. Si flows est omis, les statistiques sont agrégées sur tous les flux dans les tables de flux du commutateur. Voir Syntaxe des flux, ci-dessous, pour la syntaxe de flows. Le format de sortie est décrit dans Sortie des entrées de table.
queue-stats switch [port [queue]]
Affiche sur la console les statistiques de la queue spécifiée sur le port dans le switch. port peut être un numéro ou un nom de port OpenFlow, le mot-clé LOCAL (la manière préférée de se référer au port local OpenFlow), ou le mot-clé ALL. Soit port, soit queue, soit les deux peuvent être omis (ou de manière équivalente le mot-clé ALL). Si les deux sont omis, les statistiques sont affichées pour toutes les queues sur tous les ports. Si seule la queue est omise, alors les statistiques sont affichées pour toutes les queues sur le port ; si seul le port est omis, alors les statistiques sont affichées pour la queue sur chaque port où elle existe.
queue-get-config switch [port [queue]]
Affiche sur la console la configuration de la queue sur le port dans le switch. Si port est omis ou est ANY, signale les queues pour tous les ports. Si queue est omis ou est ANY, signale toutes les queues. Pour OpenFlow 1.3 et les versions antérieures, la sortie inclut toujours toutes les queues, ignorant queue si elle est spécifiée.
Cette commande a une utilité limitée, car les ports n'ont souvent pas de queues configurées et parce que le protocole OpenFlow ne fournit que des informations très limitées sur la configuration d'une queue.
dump-ipfix-bridge switch
Affiche sur la console les statistiques IPFIX du pont pour le switch. Si IPFIX du pont est configuré sur le switch, les statistiques IPFIX peuvent être récupérées. Sinon, un message d'erreur sera affiché.
Cette commande utilise une extension Open vSwitch qui n'est présente que dans Open vSwitch 2.6 et versions ultérieures.
dump-ipfix-flow switch
Affiche sur la console les statistiques IPFIX basées sur les flux pour le switch. Si IPFIX basé sur les flux est configuré sur le switch, les statistiques de tous les identifiants d'ensembles de collecteurs sur le switch seront affichées. Sinon, affiche un message d'erreur.
Référez-vous à ovs-vswitchd.conf.db(5) pour plus de détails sur la configuration d'IPFIX basé sur les flux et des identifiants d'ensembles de collecteurs.
Cette commande utilise une extension Open vSwitch qui n'est présente que dans Open vSwitch 2.6 et versions ultérieures.
ct-flush-zone switch zone
Vide les entrées de suivi de connexion dans la zone sur le switch.
Cette commande utilise une extension Open vSwitch qui n'est présente que dans Open vSwitch 2.6 et versions ultérieures.
ct-flush switch [zone=N] [mark=X[/M]] [labels=Y[/N]] [ct-orig-tuple [ct-reply-tuple]]
Vide les entrées de connexion sur le switch en fonction de la zone, de la mark, des labels et des tuples de suivi de connexion ct-[orig|reply]-tuple.
Si ct-[orig|reply]-tuple n'est pas fourni, vide toutes les entrées de connexion. Si la zone est spécifiée, vide uniquement les connexions dans cette zone. Si mark ou labels est fourni, il ne videra que les entrées correspondant aux mark/labels spécifiques.
Si ct-[orig|reply]-tuple est fourni, vide l'entrée de connexion spécifiée par ct-[orig|reply]-tuple dans la zone. La zone par défaut est 0 si elle n'est pas fournie. La mark et les labels par défaut sont "0/0" s'ils ne sont pas fournis. Le suivi de connexion en espace utilisateur nécessite de vider avec le tuple d'origine avant le NAT et un avertissement sera sinon généré. Le tuple peut être partiel et supprimera toutes les connexions qui correspondent aux champs spécifiés. Pour spécifier uniquement ct-reply-tuple, fournissez une chaîne vide comme ct-orig-tuple.
Note : Il y a actuellement une limitation pour la correspondance sur ICMP ; pour correspondre partiellement aux paramètres ICMP, le ct-[orig|reply]-tuple doit inclure soit l'adresse IP source, soit l'adresse IP de destination.
Un exemple de ct-[orig|reply]-tuple ICMP IPv4 :
"ct_nw_src=10.1.1.1,ct_nw_dst=10.1.1.2,ct_nw_proto=1,icmp_type=8,icmp_code=0,icmp_id=10"
Un exemple de ct-[orig|reply]-tuple TCP IPv6 :
"ct_ipv6_src=fc00::1,ct_ipv6_dst=fc00::2,ct_nw_proto=6,ct_tp_src=1,ct_tp_dst=2"
Cette commande utilise une extension Open vSwitch qui n'est présente que dans Open vSwitch 3.1 et versions ultérieures. La prise en charge de la correspondance sur mark et labels n'est présente que dans Open vSwitch 3.3 et versions ultérieures.

Commandes de la table de flux du commutateur OpenFlow

Ces commandes gèrent la table de flux dans un commutateur OpenFlow. Dans chaque cas, flow spécifie une entrée de flux dans le format décrit dans Syntaxe des flux, ci-dessous, file est un fichier texte qui contient zéro ou plusieurs flux dans la même syntaxe, un par ligne, et l'option facultative --bundle exécute la commande comme une seule transaction atomique, voir l'option --bundle, ci-dessous.

[--bundle] add-flow switch flow

[--bundle] add-flow switch - < file

[--bundle] add-flows switch file
Ajoute chaque entrée de flux aux tables du switch. Chaque spécification de flux (par exemple, chaque ligne dans file) peut commencer par
ajouter, modifier, supprimer, modifier_strict, ou supprimer_strict pour spécifier si un flux doit être ajouté, modifié ou supprimé, et si la modification ou la suppression est stricte ou non. Pour la compatibilité ascendante, une spécification de flux sans l'un de ces mots-clés est traitée comme un ajout de flux. Toutes les modifications de flux sont exécutées dans l'ordre spécifié.
[--bundle] [--strict] mod-flows switch flow

[--bundle] [--strict] mod-flows switch - < file
Modifie les actions dans les entrées des tables du switch qui correspondent aux flux spécifiés. Avec --strict, les jokers ne sont pas considérés comme actifs aux fins de correspondance.
[--bundle] del-flows switch

[--bundle] [--strict] del-flows switch [flow]

[--bundle] [--strict] del-flows switch - < file

Lit les entrées de flux du file (ou stdin si file est -) et interroge la table de flux du switch. Ensuite, il corrige les différences, ajoutant les flux du flow manquants sur le switch, supprimant les flux du switch qui ne sont pas dans le file, et mettant à jour les flux dans le switch dont les actions, cookies ou timeouts diffèrent dans le file.
Avec --readd, ovs-ofctl ajoute tous les flux du file, même ceux qui existent avec les mêmes actions, cookies et timeouts dans le switch. Lit les entrées de flux de source1 et source2 et affiche les différences. Pour cette commande, un code de sortie de 0 signifie qu'aucune différence n'a été trouvée, 1 signifie qu'une erreur s'est produite et 2 signifie que des différences ont été trouvées.

Commandes de Table TLV de Tunnel de Switch OpenFlow

Open vSwitch maintient une table de correspondance entre les TLV d'options de tunnel (définis par <classe, type, longueur>) et les champs NXM tun_metadatan, où n va de 0 à 63, sur lesquels il est possible d'opérer à des fins de correspondances, d'actions, etc. Cette table TLV peut être utilisée pour les TLV d'options Geneve ou d'autres protocoles avec des options dans le même format TLV que les options Geneve. Cette correspondance doit être explicitement spécifiée par l'utilisateur via les commandes suivantes.

Une correspondance TLV est spécifiée avec la syntaxe {class=classe,type=type,len=longueur}->tun_metadatan. Lorsqu'une correspondance d'option existe pour un tun_metadatan donné, la mise en correspondance du champ défini devient possible, par exemple :

ovs-ofctl add-tlv-map br0 "{class=0xffff,type=0,len=4}->tun_metadata0"

ovs-ofctl add-flow br0 tun_metadata0=1234,actions=controller

Une correspondance ne doit pas être modifiée pendant qu'elle est activement utilisée par un flux. Le résultat d'une telle modification est indéfini.

Ces commandes sont des extensions Nicira à OpenFlow et nécessitent Open vSwitch 2.5 ou une version ultérieure.

Ajoute chaque option aux tables du switch. Les champs en double sont rejetés.
del-tlv-map switch [option[,option]]...
Supprime chaque option de la table du switch, ou toutes les correspondances TLV d'option si aucune option n'est spécifiée. Les champs qui ne sont pas mappés sont ignorés.
dump-tlv-map switch
Affiche les champs actuellement mappés dans la table d'options du switch ainsi que les capacités du switch.

Commandes de Surveillance de Switch OpenFlow

snoop switch
Se connecte au switch et affiche sur la console tous les messages OpenFlow reçus. Contrairement aux autres commandes ovs-ofctl, si switch est le nom d'un pont, la commande snoop se connecte à un socket de domaine Unix nommé /run/openvswitch/switch.snoop. ovs-vswitchd écoute sur un tel socket pour chaque pont et lui envoie tous les messages OpenFlow envoyés à ou reçus de son contrôleur OpenFlow configuré. Ainsi, cette commande peut être utilisée pour visualiser l'activité du protocole OpenFlow entre un switch et son contrôleur.
Lorsqu'un switch a plusieurs contrôleurs configurés, seul le trafic vers et depuis un seul contrôleur est affiché. Si aucun des contrôleurs n'est configuré comme primaire ou secondaire (en utilisant une extension Nicira à OpenFlow 1.0 ou 1.1, ou une requête standard dans OpenFlow 1.2 ou ultérieur), alors un contrôleur est choisi arbitrairement parmi eux. S'il y a un contrôleur principal, il est choisi ; sinon, s'il y a des contrôleurs qui ne sont ni primaires ni secondaires, l'un d'eux est choisi arbitrairement ; sinon, un contrôleur secondaire est choisi arbitrairement. Ce choix est effectué une fois au moment de la connexion et ne change pas à mesure que les contrôleurs reconfigurent leurs rôles.
Si un switch n'a aucun contrôleur configuré, ou si le contrôleur configuré est déconnecté, aucun trafic n'est envoyé, donc la surveillance ne montrera aucun trafic.
monitor switch [miss-len] [invalid_ttl] [watch:[spec...]]
Se connecte au switch et affiche sur la console tous les messages OpenFlow reçus. Habituellement, switch doit spécifier le nom d'un pont dans la base de données ovs-vswitchd. Ceci n'est disponible qu'en OpenFlow 1.0 sous forme d'extension Nicira.
Si miss-len est fourni, ovs-ofctl envoie un message OpenFlow "set configuration" lors de l'établissement de la connexion qui demande miss-len octets de chaque paquet qui manque la table de flux. Open vSwitch n'envoie pas ces messages et d'autres messages asynchrones à une connexion client ovs-ofctl monitor à moins qu'une valeur non nulle ne soit spécifiée pour cet argument. (Ainsi, si miss-len n'est pas spécifié, très peu de trafic sera habituellement affiché.)
Si invalid_ttl est passé, ovs-ofctl envoie un message OpenFlow "set configuration" lors de l'établissement de la connexion qui demande INVALID_TTL_TO_CONTROLLER, de sorte que ovs-ofctl monitor puisse recevoir des messages "packet-in" lorsque le TTL atteint zéro lors de l'action dec_ttl. Seuls OpenFlow 1.1 et 1.2 prennent en charge invalid_ttl ; Open vSwitch l'implémente également pour OpenFlow 1.0 en tant qu'extension.
watch:[spec...] fait en sorte que ovs-ofctl envoie un message d'extension Nicira "monitor request" au switch lors de l'établissement de la connexion. Ce message demande au switch d'envoyer des informations sur les changements de table de flux au fur et à mesure qu'ils se produisent. La syntaxe spec suivante, séparée par des virgules, est disponible :
!initial
Ne pas signaler le contenu initial de la table de flux du switch.
!add
Ne pas signaler les flux nouvellement ajoutés.
!delete
Ne pas signaler les flux supprimés.
!modify
Ne pas signaler les modifications apportées aux flux existants.
!own
Abréger les modifications apportées à la table de flux par la propre connexion d'ovs-ofctl au switch. (Celles-ci ne pourraient survenir qu'en utilisant la commande ofctl/send décrite ci-dessous sous la section COMMANDES DE GESTION EN TEMPS RÉEL.)
!actions
Ne pas signaler les actions dans le cadre des mises à jour de flux.
table=table
Limite la surveillance à la table avec le table donné, qui peut être exprimé sous forme d'un nombre compris entre 0 et 254 ou (sauf si --no-names est spécifié) d'un nom. Par défaut, toutes les tables sont surveillées.
out_port=port
S'il est défini, seuls les flux qui sortent vers le port sont surveillés. Le port peut être un numéro de port OpenFlow ou un mot-clé (par exemple LOCAL).
out_group=groupe
S'il est défini, seuls les flux qui sortent vers le numéro de groupe sont surveillés. Ce champ nécessite OpenFlow 1.4 (-OOpenFlow14) ou une version ultérieure.
field=valeur
Ne surveille que les flux qui ont le field spécifié comme la valeur donnée. Toute syntaxe valide pour la mise en correspondance sur dump-flows peut être utilisée.
Cette commande peut être utile pour le débogage des implémentations de switch ou de contrôleur. Avec watch:, elle est particulièrement utile pour observer comment un contrôleur met à jour les tables de flux.

Les commandes suivantes, comme celles de la section précédente, peuvent être appliquées aux switches OpenFlow, en utilisant l'une des méthodes de connexion décrites dans cette section. Contrairement à ces commandes, elles peuvent également être appliquées aux contrôleurs OpenFlow.

Syntaxe de Flux

Certaines commandes ovs-ofctl acceptent un argument qui décrit un ou plusieurs flux. Ces descriptions de flux comprennent une série d'affectations champ=valeur, séparées par des virgules ou des espaces. (L'intégration d'espaces dans une description de flux nécessite normalement des guillemets pour empêcher le shell de diviser la description en plusieurs arguments.)

Les descriptions de flux doivent être en forme normale. Cela signifie qu'un flux ne peut spécifier une valeur pour un champ L3 que s'il spécifie également un protocole L2 particulier, et qu'un flux ne peut spécifier un champ L4 que s'il spécifie également des types de protocoles L2 et L3 particuliers. Par exemple, si le type de protocole L2 d

l_type est traité comme un joker, alors les champs L3 nw_src, nw_dst et nw_proto doivent également être traités comme des jokers. De même, si dl_type ou nw_proto (le type de protocole L3) est traité comme un joker, les champs L4 tcp_dst et tcp_src doivent l'être aussi. ovs-ofctl affichera un avertissement pour les flux qui ne sont pas sous forme normale.

ovs-fields(7) décrit les champs pris en charge et comment les faire correspondre. En plus des champs de correspondance, les commandes qui opèrent sur les flux acceptent quelques paires clé-valeur supplémentaires :

table=table
Pour les commandes de vidage de flux, limite les flux vidés à ceux de table, qui peut être exprimée comme un nombre entre 0 et 255 ou (sauf si --no-names est spécifié) un nom. Si non spécifié (ou si 255 est spécifié comme table), alors les flux de toutes les tables sont vidés.
Pour les commandes de modification de table de flux, le comportement varie en fonction de la version d'OpenFlow utilisée pour se connecter au commutateur :
OpenFlow 1.0
OpenFlow 1.0 ne prend pas en charge table pour la modification des flux. ovs-ofctl se terminera avec une erreur si table (autre que table=255) est spécifié pour un commutateur qui ne prend en charge qu'OpenFlow 1.0.
Dans OpenFlow 1.0, le commutateur choisit la table dans laquelle insérer un nouveau flux. Le commutateur logiciel Open vSwitch choisit toujours la table 0. D'autres datapaths Open vSwitch et d'autres implémentations OpenFlow peuvent choisir des tables différentes.
Le comportement OpenFlow 1.0 dans Open vSwitch pour modifier ou supprimer des flux dépend de l'utilisation ou non de --strict. Sans --strict, la commande s'applique aux flux correspondants dans toutes les tables. Avec --strict, la commande opérera sur un seul flux correspondant dans n'importe quelle table ; elle ne fera rien s'il y a des correspondances dans plus d'une table. (La distinction entre ces comportements n'a d'importance que si des commandes non-OpenFlow 1.0 ont également été utilisées, car OpenFlow 1.0 seul ne peut pas ajouter de flux avec les mêmes critères de correspondance à plusieurs tables.)
OpenFlow 1.0 avec extension table_id
Open vSwitch implémente une extension OpenFlow qui permet au contrôleur de spécifier la table sur laquelle opérer. ovs-ofctl active automatiquement l'extension lorsque table est spécifié et OpenFlow 1.0 est utilisé. ovs-ofctl détecte automatiquement si le commutateur prend en charge l'extension. À l'heure actuelle, cette extension n'est connue que pour être implémentée par Open vSwitch.
Avec cette extension, ovs-ofctl opère sur la table demandée lorsque table est spécifié, et agit comme décrit pour OpenFlow 1.0 ci-dessus lorsque table n'est pas spécifié (ou pour table=255).
OpenFlow 1.1
OpenFlow 1.1 exige que les commandes de modification de table de flux spécifient une table. Lorsque table n'est pas spécifié (ou que table=255 est spécifié), ovs-ofctl utilise la table 0 par défaut.
OpenFlow 1.2 et versions ultérieures
OpenFlow 1.2 et versions ultérieures autorisent les commandes de suppression de flux, mais pas les autres commandes de modification de table de flux, à opérer sur toutes les tables de flux, avec le comportement décrit ci-dessus pour OpenFlow 1.0.
duration=...

n_packet=...

n_bytes=...
ovs-ofctl ignore les affectations à ces « champs » pour permettre à la sortie de la commande dump-flows d'être utilisée comme entrée pour d'autres commandes qui analysent les flux.

Les commandes add-flow, add-flows et mod-flows nécessitent un champ supplémentaire, qui doit être le dernier champ spécifié :

actions=[action][,action...]
Spécifie une liste d'actions séparées par des virgules à effectuer sur un paquet lorsque l'entrée de flux correspond. Si aucune action n'est spécifiée, les paquets correspondant au flux sont abandonnés. Voir ovs-actions(7) pour les détails sur la syntaxe et la sémantique des actions. K

Un identifiant opaque appelé cookie peut être utilisé comme poignée pour identifier un ensemble de flux :

cookie=valeur
Un cookie peut être associé à un flux à l'aide des commandes add-flow, add-flows et mod-flows. valeur peut être n'importe quel nombre de 64 bits et n'a pas besoin d'être unique parmi les flux. Si ce champ est omis, une valeur de cookie par défaut de 0 est utilisée.
cookie=valeur/masque
Lors de l'utilisation de NXM, le cookie peut être utilisé comme poignée pour interroger, modifier et supprimer des flux. valeur et masque peuvent être fournis pour les commandes del-flows, mod-flows, dump-flows et dump-aggregate afin de limiter les cookies correspondants. Un bit 1 dans masque indique que le bit correspondant dans cookie doit correspondre exactement, et un bit 0 rend ce bit joker. Un masque de -1 peut être utilisé pour faire correspondre exactement un cookie.
La commande mod-flows peut mettre à jour les cookies des flux qui correspondent à un cookie en spécifiant le champ cookie deux fois (une fois avec un masque pour la correspondance et une fois sans pour indiquer la nouvelle valeur) :
ovs-ofctl mod-flows br0 cookie=1,actions=normal
Modifie les cookies de tous les flux à 1 et leurs actions à normal.
ovs-ofctl mod-flows br0 cookie=1/-1,cookie=2,actions=normal
Met à jour les cookies avec une valeur de 1 à 2 et change leurs actions à normal.
La possibilité de faire correspondre les cookies a été ajoutée dans Open vSwitch 1.5.0.

Le champ supplémentaire suivant définit la priorité pour les flux ajoutés par les commandes add-flow et add-flows. Pour mod-flows et del-flows lorsque --strict est spécifié, la priorité doit correspondre avec le reste de la spécification du flux. Pour mod-flows sans --strict, la priorité n'est significative que si la commande crée un nouveau flux, c'est-à-dire que mod-flows non-strict ne correspond pas à la priorité et ne modifiera pas la priorité des flux existants. D'autres commandes ne permettent pas de spécifier la priorité.

priority=valeur
La priorité à laquelle une entrée jokérisée correspondra par rapport aux autres. valeur est un nombre compris entre 0 et 65535, inclus. Une valeur plus élevée correspondra avant une valeur plus basse. Une entrée à correspondance exacte aura toujours la priorité sur une entrée contenant des jokers, elle a donc une valeur de priorité implicite de 65535. Lors de l'ajout d'un flux, si le champ n'est pas spécifié, la priorité du flux sera par défaut à 32768.
OpenFlow laisse le comportement indéfini lorsque deux flux ou plus avec la même priorité peuvent correspondre à un seul paquet. Certains utilisateurs s'attendent à un comportement « sensible », comme des flux plus spécifiques ayant la préséance sur des flux moins spécifiques, mais OpenFlow ne le spécifie pas et Open vSwitch ne l'implémente pas. Les utilisateurs doivent donc veiller à utiliser les priorités pour garantir le comportement attendu.

Les commandes add-flow, add-flows et mod-flows prennent en charge les options supplémentaires suivantes. Ces options n'affectent que les nouveaux flux. Ainsi, pour add-flow et add-flows, ces options sont toujours significatives, mais pour mod-flows, elles ne sont significatives que si la commande crée un nouveau flux, c'est-à-dire que leurs valeurs ne mettent pas à jour ou n'affectent pas les flux existants.

idle_timeout=secondes
Fait expirer le flux après le nombre de secondes d'inactivité donné. Une valeur de 0 (par défaut) empêche un flux d'expirer en raison d'inactivité.
hard_timeout=secondes
Fait expirer le flux après le nombre de secondes donné, quelle que soit l'activité. Une valeur de 0 (par défaut) ne donne aucune échéance d'expiration rigoureuse au flux.
importance=valeur
Définit l'importance d'un flux. Le mécanisme d'éviction des entrées de flux peut utiliser l'importance comme facteur pour décider quel flux évincer. Une valeur de 0 (par défaut) rend le flux non évicable sur la base de l'importance. Spécifiez une valeur comprise entre 0 et 65535.
Seuls OpenFlow 1.4 et versions ultérieures prennent en charge importance.
send_flow_rem
Marque le flux avec un indicateur qui fait que le commutateur génère un message « flux supprimé » et l'envoie aux contrôleurs intéressés lorsque le flux expire ou est supprimé ultérieurement.
check_overlap
Force le commutateur à vérifier que la correspondance de flux ne chevauche pas celle de tout autre flux ayant la même priorité dans la même table. (Cette vérification est coûteuse, il est donc préférable de l'éviter.)
reset_counts
Lorsque cet indicateur est spécifié sur un flux ajouté à un commutateur, et que le commutateur a déjà un flux avec une correspondance identique, un commutateur OpenFlow 1.2 (ou ultérieur) réinitialise les compteurs de paquets et d'octets du flux à 0. Sans l'indicateur, les compteurs de paquets et d'octets sont préservés.
Les commutateurs OpenFlow 1.0 et 1.1 réinitialisent toujours les compteurs dans cette situation, comme si reset_counts était toujours spécifié.
Open vSwitch 1.10 a ajouté la prise en charge de reset_counts.
no_packet_counts

no_byte_counts
L'ajout de ces indicateurs à un flux conseille à un commutateur OpenFlow 1.3 (ou ultérieur) que le contrôleur n'a pas besoin de compteurs de paquets ou d'octets, respectivement, pour le flux. Certaines implémentations de commutateurs peuvent atteindre des performances plus élevées ou réduire la consommation de ressources lorsque ces indicateurs sont utilisés. Ces indicateurs n'apportent aucun avantage à l'implémentation du commutateur logiciel Open vSwitch.
OpenFlow 1.2 et versions antérieures ne prennent pas en charge ces indicateurs.
Open vSwitch 1.10 a ajouté la prise en charge de no_packet_counts et no_byte_counts.

Les commandes dump-flows, dump-aggregate, les commandes del-flow et del-flows prennent en charge ces champs optionnels supplémentaires :

out_port=port

out_group=group
S'il est défini, un flux correspondant doit inclure une action group nommant group, qui doit être un numéro de groupe OpenFlow. Ce champ est pris en charge dans Open vSwitch 2.5 et versions ultérieures et nécessite OpenFlow 1.1 ou ultérieur.

Sortie d'Entrée de Table

Les commandes dump-tables et dump-aggregate impriment des informations sur les entrées dans les tables d'un datapath. Chaque ligne de sortie est une entrée de flux telle que décrite dans Syntaxe des Flux, ci-dessus, plus quelques champs supplémentaires :

duration=secs
Le temps, en secondes, pendant lequel l'entrée a été dans la table. secs inclut autant de précision que le commutateur fournit, éventuellement à la résolution nanoseconde.
n_packets
Le nombre de paquets qui ont correspondu à l'entrée.
n_bytes
Le nombre total d'octets des paquets qui ont correspondu à l'entrée.

Les champs supplémentaires suivants sont inclus uniquement si le commutateur est Open vSwitch 1.6 ou version ultérieure et que le format de flux NXM est utilisé pour vider le flux (voir la description de l'option --flow-format ci-dessous). Les valeurs de ces champs supplémentaires ne sont que des approximations et en particulier idle_age deviendra parfois non nul même pour les flux actifs.

hard_age=secs
Le nombre entier de secondes depuis que le flux a été ajouté ou modifié. hard_age est affiché uniquement s'il diffère de la partie entière de duration. (Ceci est distinct de duration car mod-flows redémarre le minuteur hard_timeout sans remettre à zéro duration.)
idle_age=secs
Le nombre entier de secondes écoulées sans qu'aucun paquet ne traverse le flux.

in_port=port
Le numéro de port à considérer comme in_port lors du traitement des actions. Cela peut être n'importe quel numéro de port OpenFlow valide, ou l'un des LOCAL, CONTROLLER ou NONE. Ce champ est obligatoire.

Facultativement, l'utilisateur peut spécifier une liste de champs de pipeline pour un message packet-out. Les champs de pipeline pris en charge incluent les champs de tunnel et les champs de registre tels que définis dans ovs-fields(7).

Le paquet réel à envoyer, exprimé sous forme de chaîne d'octets hexadécimaux. Ce champ est obligatoire.

Syntaxe de Groupe

Certaines commandes ovs-ofctl acceptent un argument qui décrit un ou plusieurs groupes. Ces descriptions de flux comprennent une série d'affectations field=value, séparées par des virgules ou des espaces blancs. (L'intégration d'espaces dans une description de groupe nécessite normalement des guillemets pour empêcher le shell de diviser la description en plusieurs arguments.). Sauf indication contraire, seule la dernière occurrence de chaque champ est honorée.

group_id=id
L'ID de groupe entier du groupe. Lorsque ce champ est spécifié dans del-groups ou dump-groups, le mot-clé "all" peut être utilisé pour désigner tous les groupes. Ce champ est obligatoire.
type=type
Le type du groupe. Les commandes add-group, add-groups et mod-groups nécessitent ce champ. Il est interdit pour les autres commandes. Les mots-clés suivants désignent les types autorisés :
all
Exécuter tous les buckets du groupe.
select
Exécuter un bucket du groupe, en équilibrant entre les buckets selon leurs poids. Pour sélectionner un bucket, pour chaque bucket actif, Open vSwitch hache les données du flux avec l'ID du bucket et multiplie par le poids du bucket pour obtenir un ``score'', puis sélectionne le bucket avec le score le plus élevé. Utilisez selection_method pour contrôler les données du flux utilisées pour la sélection.
indirect
Exécute le bucket unique du groupe.
ff

fast_failover
Exécute le premier bucket actif du groupe qui est associé à un port ou un groupe actif.
command_bucket_id=id
Le bucket sur lequel opérer. Les commandes insert-buckets et remove-buckets nécessitent ce champ. Il est interdit pour les autres commandes. id peut être un entier ou l'un des mots-clés suivants :
all
Opérer sur tous les buckets du groupe. Valide uniquement lorsqu'il est utilisé avec la commande remove-buckets, auquel cas l'effet est de supprimer tous les buckets du groupe.
first
Opérer sur le premier bucket présent dans le groupe. Dans le cas de la commande insert-buckets, l'effet est d'insérer de nouveaux buckets juste avant le premier bucket déjà présent dans le groupe ; ou de remplacer les buckets du groupe s'il n'y a pas de buckets déjà présents dans le groupe. Dans le cas de la commande remove-buckets, l'effet est de supprimer le premier bucket du groupe ; ou de ne rien faire s'il n'y a pas de buckets présents dans le groupe.
last
Opérer sur le dernier bucket présent dans le groupe. Dans le cas de la commande insert-buckets, l'effet est d'insérer de nouveaux buckets juste après le dernier bucket déjà présent dans le groupe ; ou de remplacer les buckets du groupe s'il n'y a pas de buckets déjà présents dans le groupe. Dans le cas de la commande remove-buckets, l'effet est de supprimer le dernier bucket du groupe ; ou de ne rien faire s'il n'y a pas de buckets présents dans le groupe.
Si id est un entier, il doit correspondre au bucket_id d'un bucket présent dans le groupe. Dans le cas de la commande insert-buckets, l'effet est d'insérer des buckets juste avant le bucket dans le groupe dont le bucket_id est id. Dans le cas de la commande iremove-buckets, l'effet est de supprimer le bucket dans le groupe dont le bucket_id est id. C'est une erreur s'il n'y a pas de bucket présent dans le groupe dont le bucket_id est id.
selection_method=method
La méthode de sélection utilisée pour choisir un bucket pour un groupe de type select. Il s'agit d'une chaîne de 1 à 15 octets de longueur connue des couches inférieures. Ce champ est facultatif pour les commandes add-group, add-groups et mod-group sur les groupes de type select. Interdit sinon. Si aucune méthode de sélection n'est spécifiée, Open vSwitch jusqu'à la version 2.9 applique la méthode hash avec les champs de hachage par défaut. À partir de la version 2.10, Open vSwitch utilise par défaut la méthode dp_hash avec un algorithme de hachage L3/L4 symétrique, tant que les buckets pondérés du groupe peuvent être mappés à des valeurs dp_hash avec une précision suffisante. En 2.10, cela était limité à un maximum de 64 buckets, et en 2.17, la limite a été augmentée à 256 buckets. Dans ces rares cas, Open vSwitch 2.10 et versions ultérieures reviennent à la méthode hash avec l'ensemble par défaut de champs de hachage.
dp_hash
Utilise une valeur de hachage calculée par le datapath. L'algorithme de hachage varie selon les implémentations du datapath. dp_hash utilise les 32 bits supérieurs de selection_method_param comme sélecteur d'algorithme de hachage du datapath. Les valeurs prises en charge sont 0 (correspondant au calcul de hachage sur le tuple IP 5-tuplet) et 1 (correspondant à un calcul de hachage symétrique sur le tuple IP 5-tuplet). La sélection de champs spécifiques avec l'option fields n'est pas prise en charge avec dp_hash). Les 32 bits inférieurs sont utilisés comme base de hachage.
L'utilisation de dp_hash présente l'avantage de ne pas nécessiter que les flux de datapath générés correspondent exactement à des champs d'en-tête de paquet supplémentaires. Par exemple, même si plusieurs connexions TCP ainsi hachées vers différents buckets de groupe select ont des numéros de port source différents, la plupart d'entre elles seraient généralement gérées avec un petit ensemble de flux de datapath déjà établis, résultant en une latence réduite pour les paquets SYN TCP. L'inconvénient est que les flux de datapath partagés doivent correspondre à chaque paquet deux fois, car le calcul de la valeur de hachage du datapath n'intervient que lorsque cela est nécessaire, et une seconde correspondance est requise pour faire correspondre certains bits de celle-ci.
s valeur. Cette double correspondance entraîne un léger surcoût de latence pour chaque paquet, mais cette latence est d'ordres de grandeur inférieure à la latence de création de nouveaux flux de chemin de données pour de nouvelles connexions TCP.
hash
Utilise une fonction de hachage calculée sur les champs spécifiés avec l'option fields, voir ci-dessous. Si aucun champ de hachage n'est spécifié, hash utilise par défaut un hachage symétrique sur la combinaison des adresses MAC, des étiquettes VLAN, du type Ethernet, des adresses IP et des numéros de port L4. hash utilise le selection_method_param comme base de hachage.
Notez que les champs hachés deviennent des correspondances exactes par les flux de chemin de données. Par exemple, si le port source TCP est haché, les flux de chemin de données créés correspondront à la valeur exacte du port source TCP présente dans le paquet reçu. Comme chaque connexion TCP a généralement une valeur de port source différente, un flux de chemin de données distinct devra être inséré pour chaque connexion TCP ainsi hachée dans un seau de sélection.
Cette option utilise une extension Netronome OpenFlow qui n'est prise en charge qu'avec Open vSwitch 2.4 et versions ultérieures avec OpenFlow 1.5 et versions ultérieures.
selection_method_param=param
Paramètre entier de 64 bits pour la méthode de sélection sélectionnée par le champ selection_method. L'utilisation du paramètre est définie par la couche inférieure qui implémente la selection_method. Il est facultatif si le champ selection_method est spécifié comme une chaîne non vide. Interdit sinon. La valeur par défaut est zéro.
Cette option utilise une extension Netronome OpenFlow qui n'est prise en charge qu'avec Open vSwitch 2.4 et versions ultérieures avec OpenFlow 1.5 et versions ultérieures.
fields=field

fields(field[=mask]...)
Les paramètres de champ pour la méthode de sélection sélectionnée par le champ selection_method. La syntaxe est décrite dans la Syntaxe de flux avec les restrictions supplémentaires que si une valeur est fournie, elle est traitée comme un masque générique et les masques génériques suivant une barre oblique sont interdits. Les prérequis des champs doivent être fournis par tous les flux qui sortent vers le groupe. L'utilisation des champs est définie par la couche inférieure qui implémente la selection_method. Ils sont facultatifs si le champ selection_method est spécifié comme ``hash'', interdit sinon. La valeur par défaut est aucun champ.
Cette option utilisera une extension Netronome OpenFlow qui n'est prise en charge qu'avec Open vSwitch 2.4 et versions ultérieures avec OpenFlow 1.5 et versions ultérieures.
bucket=bucket_parameters
Les commandes add-group, add-groups et mod-group nécessitent au moins un champ de seau. Les champs de seau doivent apparaître après tous les autres champs. Plusieurs champs de seau pour spécifier plusieurs seaux. L'ordre dans lequel les seaux sont spécifiés correspond à leur ordre dans le groupe. Si le type du groupe est "indirect", alors un seul groupe peut être spécifié. bucket_parameters consiste en une liste d'affectations field=value, séparées par des virgules ou des espaces blancs suivies d'une liste d'actions séparées par des virgules. Les champs pour bucket_parameters sont :
bucket_id=id
L'identifiant entier de 32 bits du groupe du seau. Les valeurs supérieures à 0xffffff00 sont réservées. Ce champ a été ajouté dans Open vSwitch 2.4 pour être conforme à la spécification OpenFlow 1.5. Il n'est pas pris en charge lorsque des versions antérieures d'OpenFlow sont utilisées. Open vSwitch attribuera automatiquement des identifiants de seau lorsqu'ils ne sont pas spécifiés.
actions=[action][,action...]
La syntaxe des actions est identique au champ actions= décrit dans la Syntaxe de flux ci-dessus. La spécification de actions= est facultative, tout paramètre de seau inconnu sera interprété comme une action.
weight=value
Le poids relatif du seau sous forme d'entier. Ceci peut être utilisé par le commutateur lors de la sélection du seau pour les groupes dont le type est select.
watch_port=port
Port utilisé pour déterminer la disponibilité du groupe. Ce champ ou le champ watch_group est requis pour les groupes dont le type est ff ou fast_failover. Ce champ ou le champ watch_group peut également être utilisé pour les groupes dont le type est select.
watch_group=group_id
Identifiant de groupe du groupe utilisé pour déterminer la disponibilité du groupe. Ce champ ou le champ watch_port est requis pour les groupes dont le type est ff ou fast_failover. Ce champ ou le champ watch_port peut également être utilisé pour les groupes dont le type est select.

Syntaxe des compteurs

Les commandes de table de compteurs acceptent un argument qui décrit un compteur. Ces descriptions de compteurs comprennent une série d'affectations field=value, séparées par des virgules ou des espaces blancs. (L'intégration d'espaces dans une description de groupe nécessite normalement des guillemets pour éviter que le shell ne divise la description en plusieurs arguments.). meter=id
L'identifiant du compteur. Un entier est utilisé pour spécifier un compteur défini par l'utilisateur. Lorsque ce champ est spécifié dans del-meter, dump-meter ou meter-stats, le mot-clé "all" peut être utilisé pour désigner tous les compteurs. Ce champ est requis, à l'exception de meter-stats, qui déverse toutes les statistiques lorsque ce champ n'est pas spécifié.
kbps

pktps
L'unité pour les paramètres de bande rate et burst_size. kbps spécifie les kilobits par seconde, et pktps spécifie les paquets par seconde. Une unité est requise pour les commandes add-meter et mod-meter.
burst
Si défini, active le support des rafales pour les bandes de compteur via le paramètre burst_size.
stats
Si défini, active la collecte des statistiques de compteur et de bande.
bands=band_parameters

type=type
Le type de la bande de compteur. Ce mot-clé commence une nouvelle spécification de bande. Chaque bande spécifie un débit au-delà duquel la bande doit effectuer une action. Les mots-clés suivants désignent les types de bande de compteur autorisés :
drop
Supprime les paquets dépassant la limite de débit de la bande.
Les autres band_parameters sont :
rate=value
La limite de débit relative pour cette bande, en kilobits par seconde ou en paquets par seconde, selon que kbps ou pktps a été spécifié.
burst_size=size
Si burst est spécifié pour l'entrée du compteur, configure la rafale maximale autorisée pour la bande en kilobits ou en paquets, selon que kbps ou pktps a été spécifié. Si non spécifié, le commutateur est libre de choisir une valeur raisonnable en fonction de sa configuration.

OPTIONS

--strict
Utilise la correspondance stricte lors de l'exécution des commandes de modification de flux.
--names

--no-names
Chaque port OpenFlow a un nom et un numéro, et chaque table de flux OpenFlow a un numéro et parfois un nom. Par défaut, les commandes ovs-ofctl acceptent les noms et les numéros de port et de table, et elles affichent les noms de port et de table si ovs-ofctl est exécuté sur une console interactive, les numéros sinon. Avec --names, les commandes ovs-ofctl acceptent et affichent les noms de port et de table ; avec --no-names, les commandes n'acceptent ni n'affichent les noms de port et de table.
Si un nom de port ou de table contient des caractères spéciaux ou pourrait être confondu avec un mot-clé dans un flux, il peut être entouré de guillemets doubles (échappé du shell). Si nécessaire, des séquences d'échappement de style JSON peuvent être utilisées entre guillemets, comme spécifié dans la RFC 7159. Lorsqu'il affiche les noms de port et de table, ovs-ofctl met entre guillemets tout nom qui ne commence pas par une lettre suivie de lettres ou de chiffres.
Open vSwitch a ajouté la prise en charge des noms de port et de ces options. Open vSwitch 2.10 a ajouté la prise en charge des noms de table. Les versions antérieures se comportaient toujours comme si --no-names était spécifié.
Open vSwitch ne place pas sa propre limite sur la longueur des noms de port, mais OpenFlow limite les noms de port à 15 octets. Comme ovs-ofctl utilise OpenFlow pour récupérer la correspondance entre les noms de port et les numéros, les noms plus longs que cette limite seront tronqués pour l'affichage et l'acceptation. La troncature peut également faire apparaître des noms longs et différents comme étant identiques ; lorsqu'un commutateur a deux ports portant le même nom (tronqué), ovs-ofctl refuse d'afficher ou d'accepter le nom, en utilisant le numéro à la place.
OpenFlow et Open vSwitch limitent
il est conseillé de limiter les noms de table à 32 octets.
--stats

--no-stats
La commande dump-flows, par défaut ou avec --stats, inclut la durée du flux, les comptes de paquets et d'octets, ainsi que l'âge inactif et l'âge difficile dans sa sortie. Avec --no-stats, elle omet tous ceux-ci, ainsi que les valeurs de cookie et les identifiants de table s'ils sont nuls.
--read-only
Ne pas exécuter les commandes de lecture/écriture.
--bundle
Exécuter les modifications de flux en tant que transaction atomique de paquet OpenFlow 1.4.
  • Dans un paquet, toutes les modifications de flux sont traitées dans l'ordre où elles apparaissent et en tant que transaction atomique unique, ce qui signifie que si l'une d'entre elles échoue, l'ensemble de la transaction échoue et aucune des modifications n'est apportée à la table de flux du switch, et que chaque paquet donné traversant les tables OpenFlow voit les tables de flux soit comme avant la transaction, soit après que toutes les modifications de flux du paquet aient été appliquées avec succès.
  • Le début et la fin des commandes de modification de table de flux dans un paquet sont délimités par des messages de contrôle de paquet OpenFlow 1.4, ce qui permet de diffuser les commandes incluses sans barrières OpenFlow explicites, qui sont autrement utilisées après chaque commande de modification de table de flux. Cela peut rendre les modifications importantes plus rapides à exécuter sous forme de paquet.
  • Les paquets nécessitent OpenFlow 1.4 ou supérieur. Une option -O OpenFlow14 explicite n'est pas nécessaire, mais vous devrez peut-être activer la prise en charge d'OpenFlow 1.4 pour OVS en définissant la colonne protocols d'OVSDB dans la table bridge.

Affiche la sortie triée par le champ du flux dans l'ordre croissant (--sort) ou décroissant (--rsort), où champ est l'un des champs autorisés pour la correspondance ou priority pour trier par priorité. Lorsque champ est omis, la sortie est triée par priorité. Spécifiez ces options plusieurs fois pour trier par plusieurs champs.
Un flux donné ne spécifiera pas nécessairement une valeur pour un champ donné. Cela nécessite un traitement spécial :
  • Un flux qui ne spécifie aucune partie d'un champ utilisé pour le tri est trié après tous les flux qui spécifient le champ. Par exemple, --sort=tcp_src triera tous les flux qui spécifient un port source TCP par ordre croissant, suivis des flux qui ne spécifient pas de port source TCP du tout.
  • Un flux qui ne spécifie que certains bits dans un champ est trié comme si les bits masqués étaient nuls. Par exemple, --sort=nw_src trierait un flux qui spécifie nw_src=192.168.0.0/24 de la même manière que nw_src=192.168.0.0.
Ces options affectent actuellement uniquement la sortie de dump-flows.

Options de démon

Les options suivantes sont valides sur les plateformes basées sur POSIX.

--pidfile[=pidfile]
Crée un fichier (by défaut, ovs-ofctl.pid) pour indiquer le PID du processus en cours d'exécution. Si l'argument pidfile n'est pas spécifié, ou s'il ne commence pas par /, il est créé dans /run/openvswitch.
Si --pidfile n'est pas spécifié, aucun fichier PID n'est créé.
--overwrite-pidfile
Par défaut, lorsque --pidfile est spécifié et que le fichier PID spécifié existe déjà et est verrouillé par un processus en cours d'exécution, ovs-ofctl refuse de démarrer. Spécifiez --overwrite-pidfile pour qu'il écrase le fichier PID.
Lorsque --pidfile n'est pas spécifié, cette option n'a aucun effet.
--detach
Exécute ovs-ofctl en tant que processus d'arrière-plan. Le processus se divise, et dans le processus enfant, il démarre une nouvelle session, ferme les descripteurs de fichiers standards (ce qui désactive la journalisation sur la console) et change son répertoire courant vers la racine (sauf si --no-chdir est spécifié). Après que le processus enfant ait terminé son initialisation, le processus parent se termine. ovs-ofctl se détache uniquement lors de l'exécution des commandes monitor ou snoop.
--monitor
Crée un processus supplémentaire pour surveiller le démon ovs-ofctl. Si le démon meurt à cause d'un signal indiquant une erreur de programmation (SIGABRT, SIGALRM, SIGBUS, SIGFPE, SIGILL, SIGPIPE, SIGSEGV, SIGXCPU, ou SIGXFSZ), alors le processus moniteur en démarre une nouvelle copie. Si le démon meurt ou se termine pour une autre raison, le processus moniteur se termine.
Cette option est normalement utilisée avec --detach, mais elle fonctionne aussi sans.
--no-chdir
Par défaut, lorsque --detach est spécifié, ovs-ofctl change son répertoire de travail courant vers le répertoire racine après s'être détaché. Sinon, l'invocation de ovs-ofctl à partir d'un répertoire choisi négligemment empêcherait l'administrateur de démonter le système de fichiers qui contient ce répertoire.
La spécification de --no-chdir supprime ce comportement, empêchant ovs-ofctl de changer son répertoire de travail courant. Cela peut être utile pour collecter des fichiers core, car il est courant d'écrire les dumps de core dans le répertoire de travail courant et le répertoire racine n'est pas un bon répertoire à utiliser.
Cette option n'a aucun effet lorsque --detach n'est pas spécifié.
--no-self-confinement
Par défaut, le démon essaiera de s'auto-confiner pour travailler avec des fichiers sous des répertoires bien connus déterminés lors de la construction. Il est préférable de s'en tenir à ce comportement par défaut et de ne pas utiliser ce drapeau à moins qu'une autre mesure de contrôle d'accès ne soit utilisée pour confiner le démon. Notez que contrairement à d'autres implémentations de contrôle d'accès qui sont généralement appliquées depuis l'espace noyau (par exemple, DAC ou MAC), l'auto-confinement est imposé par le démon de l'espace utilisateur lui-même et ne doit donc pas être considéré comme une stratégie de confinement complète, mais plutôt comme une couche de sécurité supplémentaire.
--user
Fait en sorte que ovs-ofctl s'exécute en tant qu'utilisateur différent spécifié dans "user:group", abandonnant ainsi la plupart des privilèges root. Les formes courtes "user" et ":group" sont également autorisées, avec l'utilisateur ou le groupe actuel supposé respectivement. Seuls les démons démarrés par l'utilisateur root acceptent cet argument.
Sous Linux, les démons recevront CAP_IPC_LOCK et CAP_NET_BIND_SERVICES avant d'abandonner les privilèges root. Les démons qui interagissent avec un datapath, comme ovs-vswitchd, recevront trois capacités supplémentaires, à savoir CAP_NET_ADMIN, CAP_NET_BROADCAST et CAP_NET_RAW. Le changement de capacité s'appliquera même si le nouvel utilisateur est root.
Sous Windows, cette option n'est pas prise en charge actuellement. Pour des raisons de sécurité, la spécification de cette option entraînera l'échec du démarrage du processus démon.
--unixctl=socket
Définit le nom du socket de contrôle sur lequel ovs-ofctl écoute les commandes de gestion d'exécution (voir COMMANDES DE GESTION D'EXÉCUTION, ci-dessous). Si socket ne commence pas par /, il est interprété relativement à /run/openvswitch. Si --unixctl n'est pas du tout utilisé, le socket par défaut est /run/openvswitch/ovs-ofctl.pid.ctl, où pid est l'ID de processus de ovs-ofctl.
Sous Windows, un pipe nommé local est utilisé pour écouter les commandes de gestion d'exécution. Un fichier est créé dans le chemin absolu indiqué par socket ou si --unixctl n'est pas utilisé du tout, un fichier est créé sous le nom ovs-ofctl.ctl dans le répertoire OVS_RUNDIR configuré. Le fichier existe uniquement pour imiter le comportement d'un socket de domaine Unix.
La spécification de none pour socket désactive la fonctionnalité de socket de contrôle.

Options d'infrastructure de clé publique

-p privkey.pem

--private-key=privkey.pem
Spécifie un fichier PEM contenant la clé privée utilisée comme identité de ovs-ofctl pour les connexions SSL/TLS sortantes.
-c cert.pem

--certificate=cert.pem
Spécifie un fichier PEM contenant un certificat qui certifie la clé privée spécifiée sur -p ou --private-key comme étant digne de confiance. Le certificat doit être signé par l'autorité de certification (AC) que le pair dans les connexions SSL/TLS utilisera pour le vérifier.
-C cacert.pem

--ca-cert=cacert.pem
Spécifie un fichier PEM contenant le certificat de l'AC que ovs-ofctl devrait utiliser pour vérifier les certificats qui lui sont présentés par les pairs SSL/TLS. (Il peut s'agir du même certificat que celui que les pairs SSL/TLS utilisent pour vérifier le certificat spécifié sur -c ou --certificate, ou d'un certificat différent, en fonction de la conception de l'infrastructure à clé publique utilisée.)
-C none

--ca-cert=none
Désactive la vérification des certificats présentés par les pairs SSL/TLS. Cela introduit un risque de sécurité, car cela signifie que les certificats ne peuvent pas être vérifiés comme étant ceux d'hôtes de confiance connus.
-v[spec]

--verbose=[spec]
Définit les niveaux de journalisation. Sans spec, définit le niveau de journalisation pour chaque module et destination sur dbg. Sinon, spec est une liste de mots séparés par des espaces, des virgules ou des deux-points, jusqu'à un de chaque catégorie ci-dessous :
  • Un nom de module valide, tel qu'affiché par la commande vlog/list sur ovs-appctl(8), limite le changement de niveau de journalisation au module spécifié.
  • syslog, console, ou file, pour limiter le changement de niveau de journalisation uniquement au journal système, à la console ou à un fichier, respectivement. (Si --detach est spécifié, ovs-ofctl ferme ses descripteurs de fichiers standards, donc la journalisation sur la console n'aura aucun effet.)
Sur la plateforme Windows, syslog est accepté comme mot et n'est utile qu'avec l'option --syslog-target (le mot n'a aucun effet sinon).
•
off, emer, err, warn, info, ou dbg, pour contrôler le niveau de journalisation. Les messages de la sévérité donnée ou supérieure seront journalisés, et les messages de sévérité inférieure seront filtrés. off filtre tous les messages. Voir ovs-appctl(8) pour une définition de chaque niveau de journalisation.
La casse n'est pas significative dans spec.
Indépendamment des niveaux de journalisation définis pour file, la journalisation dans un fichier n'aura lieu que si --log-file est également spécifié (voir ci-dessous).
Pour la compatibilité avec les anciennes versions d'OVS, any est accepté comme mot mais n'a aucun effet.
-v

--verbose
Définit le niveau de verbosité de journalisation maximal, équivalent à --verbose=dbg.
-vPATTERN:destination:pattern

--verbose=PATTERN:destination:pattern
Définit le modèle de journalisation pour destination sur pattern. Référez-vous à ovs-appctl(8) pour une description de la syntaxe valide pour pattern.
-vFACILITY:facility

--verbose=FACILITY:facility
Définit la facilité RFC5424 du message de journalisation. facility peut être l'un des suivants : kern, user, mail, daemon, auth, syslog, lpr, news, uucp, clock, ftp, ntp, audit, alert, clock2, local0, local1, local2, local3, local4, local5, local6 ou local7. Si cette option n'est pas spécifiée, daemon est utilisé comme défaut pour le syslog système local et local0 est utilisé lors de l'envoi d'un message à la cible fournie via l'option --syslog-target.
--log-file[=file]
Active la journalisation dans un fichier. Si file est spécifié, il est utilisé comme nom exact pour le fichier de journalisation. Le nom de fichier de journalisation par défaut utilisé si file est omis est /var/log/openvswitch/ovs-ofctl.log.
--syslog-target=hôte:port
Envoie les messages syslog au port UDP port sur hôte, en plus du syslog système. L'hôte doit être une adresse IP numérique, pas un nom d'hôte.
--syslog-method=méthode
Spécifie la méthode par laquelle les messages syslog doivent être envoyés au démon syslog. Les formes suivantes sont prises en charge :
  • libc, utilise la fonction syslog() de libc. L'inconvénient de l'utilisation de cette option est que libc ajoute un préfixe fixe à chaque message avant qu'il ne soit réellement envoyé au démon syslog via un socket de domaine UNIX /dev/log.
  • unix:fichier, utilise directement un socket de domaine UNIX. Il est possible de spécifier un format de message arbitraire avec cette option. Cependant, les versions rsyslogd 8.9 et antérieures utilisent de toute façon une fonction d'analyse codée en dur qui limite l'utilisation du socket de domaine UNIX. Si vous souhaitez utiliser un format de message arbitraire avec les anciennes versions de rsyslogd, utilisez plutôt un socket UDP vers l'adresse IP de localhost.
  • udp:ip:port, utilise un socket UDP. Avec cette méthode, il est possible d'utiliser un format de message arbitraire également avec les anciennes versions de rsyslogd. Lors de l'envoi de messages syslog via un socket UDP, des précautions supplémentaires doivent être prises en compte, par exemple, le démon syslog doit être configuré pour écouter sur le port UDP spécifié, des règles iptables accidentelles pourraient interférer avec le trafic syslog local et il existe certaines considérations de sécurité qui s'appliquent aux sockets UDP, mais pas aux sockets de domaine UNIX.
  • null, supprime tous les messages enregistrés dans syslog.
La valeur par défaut est prise dans la variable d'environnement OVS_SYSLOG_METHOD ; si elle n'est pas définie, la valeur par défaut est libc.
--color[=quand]
Colorise la sortie (pour certaines commandes) ; quand peut être jamais, toujours ou auto (la valeur par défaut).

Seules certaines commandes prennent en charge la coloration de la sortie. Les noms de couleurs et les couleurs par défaut peuvent changer dans les futures versions.

La variable d'environnement OVS_COLORS peut être utilisée pour spécifier des couleurs définies par l'utilisateur et d'autres attributs utilisés pour mettre en évidence différentes parties de la sortie. Si elle est définie, sa valeur est une liste de capacités séparées par des deux-points qui par défaut est ac:01;31:dr=34:le=31:pm=36:pr=35:sp=33:vl=32. Les capacités prises en charge ont été initialement conçues pour coloriser les flux de la commande ovs-ofctl dump-flows switch, et elles sont les suivantes.

ac=01;31
Sous-chaîne SGR pour le mot-clé actions= dans un flux. La valeur par défaut est un texte en premier plan rouge gras.
dr=34
Sous-chaîne SGR pour le mot-clé drop. La valeur par défaut est un texte en premier plan bleu foncé.
le=31
Sous-chaîne SGR pour le mot-clé learn= dans un flux. La valeur par défaut est un texte en premier plan rouge.
pm=36
Sous-chaîne SGR pour les noms d'attributs de correspondance de flux. La valeur par défaut est un texte en premier plan cyan.
pr=35
Sous-chaîne SGR pour les mots-clés dans un flux qui sont suivis d'arguments entre parenthèses. La valeur par défaut est un texte en premier plan magenta.
sp=33
Sous-chaîne SGR pour certains mots-clés spéciaux dans un flux, notamment : table=, priority=, load:, output:, move:, group:, CONTROLLER:, set_field:, resubmit:, exit. La valeur par défaut est un texte en premier plan jaune.
vl=32
Sous-chaîne SGR pour un attribut de correspondance de flux isolé sans nom de champ. La valeur par défaut est un texte en premier plan vert.

Consultez la section Sélection des codes d'échappement de rendu graphique (SGR) dans la documentation du terminal texte utilisé pour les valeurs autorisées et leur signification en tant qu'attributs de caractères.

COMMANDES DE GESTION DU TEMPS RÉEL

ovs-appctl(8) peut envoyer des commandes à un processus ovs-ofctl en cours d'exécution. Les commandes prises en charge sont énumérées ci-dessous.

exit
Provoque la terminaison gracieuse de ovs-ofctl. Cette commande ne s'applique que lors de l'exécution des commandes monitor ou snoop.
ofctl/set-output-file fichier
Provoque l'envoi de toutes les sorties ultérieures vers fichier au lieu de stderr. Cette commande ne s'applique que lors de l'exécution des commandes monitor ou snoop.
ofctl/send ofmsg...
Envoie chaque ofmsg, spécifié comme une séquence de chiffres hexadécimaux qui représente un message OpenFlow, sur la connexion OpenFlow. Cette commande n'est utile que lors de l'exécution de la commande monitor.
ofctl/packet-out packet-out
Envoie un message OpenFlow PACKET_OUT spécifié dans la Syntaxe Packet-Out, sur la connexion OpenFlow. Voir la section Syntaxe Packet-Out pour plus d'informations. Cette commande n'est utile que lors de l'exécution de la commande monitor.
ofctl/barrier
Envoie une requête de barrière OpenFlow sur la connexion OpenFlow et attend une réponse. Cette commande n'est utile que pour la commande monitor.

EXEMPLES

Les exemples suivants supposent que ovs-vswitchd a un pont nommé br0 configuré.

ovs-ofctl dump-tables br0
Affiche les statistiques de table du commutateur. (Ceci est plus intéressant après le passage de trafic.)
ovs-ofctl dump-flows br0
Affiche les entrées de flux dans le commutateur.
ovs-ofctl add-flow table=0 actions=learn(table=1,hard_timeout=10, NXM_OF_VLAN_TCI[0..11],output:NXM_OF_IN_PORT[]), resubmit(,1)
ovs-ofctl add-flow table=1 priority=0 actions=flood Implémente un commutateur d'apprentissage MAC de niveau 2 en utilisant learn.
ovs-ofctl add-flow br0 'table=0,priority=0 actions=load:3->NXM_NX_REG0[0..15],learn(table=0,priority=1,idle_timeout=10,NXM_OF_ETH_SRC[],NXM_OF_VLAN_TCI[0..11],output:NXM_NX_REG0[0..15]),output:2
Dans cette utilisation d'une action learn, le premier paquet de chaque adresse MAC source sera envoyé au port 2. Les paquets suivants seront envoyés au port 3, avec un délai d'expiration d'inactivité de 10 secondes. Les noms de champs NXM et les noms de champs de correspondance sont tous deux acceptés, par exemple NXM_NX_REG0 ou reg0 pour le premier registre, et les crochets vides peuvent être omis.
Des exemples supplémentaires peuvent être trouvés documentés dans le cadre des sections connexes.
