EXEMPLE CLIENT TLS NON BLOQUANT SIMPLE

Cette page s'appuie sur l'exemple développé dans la page ossl-guide-tls-client-block(7) qui montre comment écrire un client TLS bloquant simple. Sur cette page, nous allons modifier ce code de démonstration afin qu'il prenne en charge un socket non bloquant.

Le code source complet de cet exemple de client TLS non bloquant est disponible dans le répertoire demos/guide de la distribution source OpenSSL, dans le fichier tls-client-non-block.c. Il est également disponible en ligne à l'adresse https://github.com/openssl/openssl/blob/master/demos/guide/tls-client-non-block.c.

Comme nous l'avons vu dans l'exemple précédent, un socket bloquant est un socket qui attend (bloque) jusqu'à ce que des données soient disponibles en lecture si vous tentez d'y lire alors qu'il n'y a pas encore de données. De même, il attend lors de l'écriture si le socket ne peut actuellement pas écrire. Cela peut simplifier le développement de code car vous n'avez pas à vous soucier de ce qu'il faut faire dans ces cas. L'exécution du code s'arrêtera simplement jusqu'à ce qu'elle puisse continuer. Cependant, dans de nombreux cas, vous ne souhaitez pas ce comportement. Plutôt que de s'arrêter et d'attendre, votre application peut avoir besoin d'effectuer d'autres tâches pendant que le socket est incapable de lire/écrire, par exemple la mise à jour d'une interface graphique ou l'exécution d'opérations sur un autre socket.

Avec un socket non bloquant, tenter de lire ou d'écrire sur un socket qui est actuellement incapable de lire ou d'écrire retournera immédiatement avec une erreur non fatale. Bien qu'OpenSSL effectue la lecture/écriture sur le socket, ce comportement non bloquant est propagé à l'application, de sorte que les fonctions d'E/S d'OpenSSL telles que SSL_read_ex(3) ou SSL_write_ex(3) ne bloqueront pas.

Étant donné que cette page s'appuie sur l'exemple développé dans la page ossl-guide-tls-client-block(7), nous supposons que vous la connaissez et nous expliquons uniquement en quoi cet exemple diffère.

Mise du socket en mode non bloquant

La première étape pour écrire une application qui prend en charge le mode non bloquant consiste à mettre le socket en mode non bloquant. Un socket sera bloquant par défaut. Les détails exacts sur la façon de procéder peuvent varier d'une plateforme à l'autre. Heureusement, OpenSSL offre une fonction portable qui s'en chargera pour vous :

/* Mettre en mode non bloquant */
if (!BIO_socket_nbio(sock, 1)) {
    sock = -1;
    continue;
}

Vous n'êtes pas obligé d'utiliser la fonction d'OpenSSL pour cela. Vous pouvez bien sûr appeler directement les fonctions que votre système d'exploitation fournit à cet effet sur votre plateforme.

Effectuer un travail en attendant le socket

Dans une application non bloquante, vous devrez avoir du travail à effectuer dans le cas où nous souhaitons lire ou écrire sur le socket, mais que nous en sommes actuellement incapables. En fait, c'est tout l'intérêt d'utiliser un socket non bloquant, c'est-à-dire de donner à l'application l'opportunité de faire autre chose. Quoi qu'il en soit, l'application doit également être prête à revenir et à réessayer périodiquement l'opération qu'elle a précédemment tentée pour voir si elle peut maintenant s'achever. Idéalement, elle ne le ferait que si l'état du socket sous-jacent a réellement changé (par exemple, il est devenu lisible alors qu'il ne l'était pas auparavant), mais ce n'est pas obligatoire. Elle peut réessayer à tout moment.

Notez qu'il est important de réessayer exactement la même opération que celle que vous avez tentée la dernière fois. Vous ne pouvez pas en commencer une nouvelle. Par exemple, si vous tentiez d'écrire le texte "Hello World" et que l'opération a échoué parce que le socket ne peut actuellement pas écrire, vous ne pouvez pas ensuite tenter d'écrire un autre texte lors de la nouvelle tentative.

Dans cette application de démonstration, nous allons créer une fonction d'aide qui simule l'exécution d'autres tâches. En fait, pour plus de simplicité, elle ne fera rien d'autre qu'attendre que l'état du socket change.

Nous appelons notre fonction wait_for_activity() car tout ce qu'elle fait est d'attendre que le socket sous-jacent devienne lisible ou accessible en écriture alors qu'il ne l'était pas auparavant.

static void wait_for_activity(SSL *ssl, int write)
{
    fd_set fds;
    int width, sock;
    /* Obtenir le descripteur de fichier sous-jacent pour le socket */
    sock = SSL_get_fd(ssl);
    FD_ZERO(&fds);
    FD_SET(sock, &fds);
    width = sock + 1;
    /*
     * Attendre jusqu'à ce que le socket soit accessible en écriture ou en lecture.
     * Nous utilisons select ici pour des raisons de simplicité et de portabilité,
     * mais vous pourriez tout aussi bien utiliser poll/epoll ou des fonctions similaires.
     *
     * REMARQUE : Aux fins de ce code de démonstration, cela fait effectivement
     * que cette démo bloque jusqu'à ce qu'elle ait quelque chose de plus utile à faire.
     * Dans une application réelle, vous voudrez probablement effectuer d'autres
     * tâches ici (par exemple, mettre à jour une interface graphique, ou servir
     * d'autres connexions).
     *
     * Disons, par exemple, que vous souhaitez mettre à jour le compteur de progression
     * sur une interface graphique toutes les 100 ms. Une façon de le faire serait
     * d'ajouter un délai d'attente de 100 ms dans le dernier paramètre de "select" ci-dessous.
     * Ensuite, lorsque select retourne, vous vérifiez s'il l'a fait en raison de l'activité
     * sur les descripteurs de fichiers ou en raison du délai d'attente. S'il s'agit d'un
     * délai d'attente, mettez à jour l'interface graphique, puis redémarrez "select".
     */
    if (write)
        select(width, NULL, &fds, NULL, NULL);
    else
        select(width, &fds, NULL, NULL, NULL);
}

Dans cet exemple, nous utilisons la fonction "select" car elle est très simple à utiliser et est disponible sur la plupart des systèmes d'exploitation. Cependant, vous pourriez utiliser toute autre fonction similaire pour faire la même chose. "select" attend que l'état du ou des sockets sous-jacents devienne lisible/accessible en écriture avant de retourner. Elle prend également en charge un "délai d'attente" (comme la plupart des autres fonctions similaires), de sorte que dans vos propres applications, vous pouvez l'utiliser pour vous réveiller périodiquement et effectuer des tâches pendant que vous attendez que l'état du socket change. Mais nous n'utilisons pas cette capacité de délai d'attente dans cet exemple pour des raisons de simplicité.

Gestion des erreurs des fonctions d'E/S OpenSSL

Une application qui utilise un socket non bloquant devra être prête à gérer les erreurs retournées par les fonctions d'E/S OpenSSL telles que SSL_read_ex(3) ou SSL_write_ex(3). Les erreurs peuvent être fatales (par exemple, parce que la connexion sous-jacente a échoué) ou non fatales (par exemple, parce que nous essayons de lire depuis le socket sous-jacent mais que les données ne sont pas encore arrivées du pair).

SSL_read_ex(3) et SSL_write_ex(3) retourneront 0 pour indiquer une erreur et SSL_read(3) et SSL_write(3) retourneront 0 ou une valeur négative pour indiquer une erreur. SSL_shutdown(3) retournera une valeur négative pour indiquer une erreur.

En cas d'erreur, une application doit appeler SSL_get_error(3) pour savoir quel type d'erreur s'est produit. Si l'erreur n'est pas fatale et peut être retentée, SSL_get_error(3) retournera SSL_ERROR_WANT_READ ou SSL_ERROR_WANT_WRITE selon que OpenSSL voulait lire depuis ou écrire sur le socket mais n'a pas pu. Notez qu'un appel à SSL_read_ex(3) ou SSL_read(3) peut toujours générer SSL_ERROR_WANT_WRITE car OpenSSL peut avoir besoin d'écrire des messages de protocole (comme pour mettre à jour des clés cryptographiques) même si l'application essaie uniquement de lire des données. De même, les appels à SSL_write_ex(3) ou SSL_write(3) pourraient générer SSL_ERROR_WANT_READ.

Un autre type d'erreur non fatale qui peut survenir est SSL_ERROR_ZERO_RETURN. Cela indique un EOF (End-Of-File) qui peut se produire si vous tentez de lire des données à partir d'un objet SSL mais que le pair a indiqué qu'il n'enverra plus de données. Dans ce cas, vous pouvez toujours vouloir écrire des données dans la connexion mais vous ne recevrez plus de données.

Gestion des erreurs d'E/S

Les erreurs les plus courantes pouvant survenir sont SSL_ERROR_SYSCALL et SSL_ERROR_SSL. Celles-ci indiquent que la connexion sous-jacente a échoué. Vous ne devez pas tenter de la fermer avec SSL_shutdown(3). SSL_ERROR_SYSCALL indique qu'OpenSSL a tenté d'effectuer un appel système qui a échoué. Vous pouvez consulter errno pour plus de détails. SSL_ERROR_SSL indique qu'une erreur OpenSSL s'est produite. Vous pouvez consulter la pile d'erreurs OpenSSL pour plus de détails (par exemple, en appelant ERR_print_errors(3) pour afficher les détails des erreurs survenues).

Dans notre application de démonstration, nous allons écrire une fonction pour gérer ces erreurs provenant des fonctions d'E/S d'OpenSSL :

static int handle_io_failure(SSL *ssl, int res)
{
    switch (SSL_get_error(ssl, res)) {
    case SSL_ERROR_WANT_READ:
        /* Échec temporaire. Attendre qu'on puisse lire et réessayer */
        wait_for_activity(ssl, 0);
        return 1;
    case SSL_ERROR_WANT_WRITE:
        /* Échec temporaire. Attendre qu'on puisse écrire et réessayer */
        wait_for_activity(ssl, 1);
        return 1;
    case SSL_ERROR_ZERO_RETURN:
        /* EOF */
        return 0;
    case SSL_ERROR_SYSCALL:
        return -1;
    case SSL_ERROR_SSL:
        /*
        * Si l'échec est dû à une erreur de vérification, nous pouvons obtenir plus
        * d'informations à ce sujet à partir de SSL_get_verify_result().
        */
        if (SSL_get_verify_result(ssl) != X509_V_OK)
            printf("Verify error: %s\n",
                X509_verify_cert_error_string(SSL_get_verify_result(ssl)));
        return -1;
    default:
        return -1;
    }
}

Cette fonction prend comme arguments l'objet SSL qui représente la connexion, ainsi que le code de retour de la fonction d'E/S qui a échoué. En cas d'échec non fatal, elle attend qu'une nouvelle tentative de l'opération d'E/S puisse réussir (en utilisant la fonction wait_for_activity() que nous avons développée dans la section précédente). Elle renvoie 1 en cas d'erreur non fatale (sauf EOF), 0 en cas d'EOF, ou -1 si une erreur fatale s'est produite.

Création des objets SSL_CTX et SSL

Afin de nous connecter à un serveur, nous devons créer des objets SSL_CTX et SSL pour cela. Les étapes pour y parvenir sont les mêmes que pour un client bloquant et sont expliquées sur la page ossl-guide-tls-client-block(7). Nous ne répéterons pas ces informations ici.

Exécution de la poignée de main

Comme dans la démonstration pour un client TLS bloquant, nous utilisons la fonction SSL_connect(3) pour effectuer la poignée de main TLS avec le serveur. Puisque nous utilisons une socket non bloquante, il est très probable que les appels à cette fonction échouent avec une erreur non fatale pendant que nous attendons que le serveur réponde à nos messages de poignée de main. Dans un tel cas, nous devons retenter le même appel à SSL_connect(3) plus tard. Dans cette démo, nous faisons cela dans une boucle :

/* Effectuer la poignée de main avec le serveur */
while ((ret = SSL_connect(ssl)) != 1) {
    if (handle_io_failure(ssl, ret) == 1)
        continue; /* Réessayer */
    printf("Échec de la connexion au serveur\n");
    goto end; /* Impossible de réessayer : erreur */
}

Nous appelons continuellement SSL_connect(3) jusqu'à ce qu'il nous donne une réponse de succès. Sinon, nous utilisons la fonction handle_io_failure() que nous avons créée plus tôt pour déterminer ce que nous devons faire ensuite. Notez que nous ne nous attendons pas à ce qu'un EOF se produise à ce stade, donc une telle réponse est traitée de la même manière qu'une erreur fatale.

Envoi et réception de données

Comme pour la démo du client TLS bloquant, nous utilisons la fonction SSL_write_ex(3) pour envoyer des données au serveur. Comme avec SSL_connect(3) ci-dessus, parce que nous utilisons une socket non bloquante, cet appel pourrait échouer avec une erreur non fatale. Dans ce cas, nous devrions retenter exactement le même appel à SSL_write_ex(3). Notez que les paramètres doivent être exactement les mêmes, c'est-à-dire le même pointeur vers le tampon à écrire avec la même longueur. Vous ne devez pas tenter d'envoyer des données différentes lors d'une nouvelle tentative. Un mode optionnel existe ( SSL_MODE_ACCEPT_MOVING_WRITE_BUFFER) qui configurera OpenSSL pour permettre au tampon utilisé pour l'écriture de changer d'une tentative à l'autre. Cependant, dans ce cas, vous devez toujours retenter les mêmes données - même si le tampon qui contient ces données peut changer d'emplacement. Voir SSL_CTX_set_mode(3) pour plus de détails. Comme dans le tutoriel client TLS bloquant (ossl-guide-tls-client-block(7)), nous écrivons la requête en trois parties.

/* Écrire une requête HTTP GET vers le pair */
while (!SSL_write_ex(ssl, request_start, strlen(request_start), &written)) {
    if (handle_io_failure(ssl, 0) == 1)
        continue; /* Réessayer */
    printf("Échec de l'écriture du début de la requête HTTP\n");
    goto end; /* Impossible de réessayer : erreur */
}
while (!SSL_write_ex(ssl, hostname, strlen(hostname), &written)) {
    if (handle_io_failure(ssl, 0) == 1)
        continue; /* Réessayer */
    printf("Échec de l'écriture du nom d'hôte dans la requête HTTP\n");
    goto end; /* Impossible de réessayer : erreur */
}
while (!SSL_write_ex(ssl, request_end, strlen(request_end), &written)) {
    if (handle_io_failure(ssl, 0) == 1)
        continue; /* Réessayer */
    printf("Échec de l'écriture de la fin de la requête HTTP\n");
    goto end; /* Impossible de réessayer : erreur */
}

Lors d'une écriture, nous ne nous attendons pas à voir une réponse EOF donc nous traitons ce cas de la même manière qu'une erreur fatale.

La lecture d'une réponse du serveur est similaire :

do {
    /*
     * Obtenir jusqu'à sizeof(buf) octets de la réponse. Nous continuons à lire jusqu'à ce que
     * le serveur ferme la connexion.
     */
    while (!eof && !SSL_read_ex(ssl, buf, sizeof(buf), &readbytes)) {
        switch (handle_io_failure(ssl, 0)) {
        case 1:
            continue; /* Réessayer */
        case 0:
            eof = 1;
            continue;
        case -1:
        default:
            printf("Échec de la lecture des données restantes\n");
            goto end; /* Impossible de réessayer : erreur */
        }
    }
    /*
     * OpenSSL ne garantit pas que les données renvoyées sont une chaîne de caractères ou
     * qu'elles sont terminées par NUL, nous utilisons donc fwrite() pour écrire le nombre exact
     * d'octets que nous avons lus. Les données pourraient être non imprimables ou
     * contenir des caractères NUL au milieu. Pour cet exemple simple, nous allons quand même les imprimer sur stdout.
     */
    if (!eof)
        fwrite(buf, 1, readbytes, stdout);
} while (!eof);
/* Au cas où la réponse ne se terminerait pas par un saut de ligne, nous en ajoutons un maintenant */
printf("\n");

La principale différence cette fois-ci est qu'il est valide pour nous de recevoir une réponse EOF lors de la tentative de lecture de données depuis le serveur. Cela se produira lorsque le serveur fermera la connexion après avoir envoyé toutes les données de sa réponse.

Dans cette démo, nous nous contentons d'imprimer toutes les données que nous avons reçues en retour dans la réponse du serveur. Nous continuons de boucler jusqu'à ce que nous rencontrions soit une erreur fatale, soit un EOF (indiquant une fin normale).

Arrêt de la connexion

Comme dans l'exemple du client TLS bloquant, nous devons arrêter la connexion lorsque nous avons terminé avec elle.

Si notre application initiait l'arrêt, nous nous attendrions à ce que SSL_shutdown(3) retourne 0, puis nous continuerions à l'appeler jusqu'à ce que nous recevions un retour de 1 (signifiant que nous avons achevé l'arrêt avec succès). Dans cet exemple particulier, nous ne nous attendons pas à ce que SSL_shutdown() retourne 0 car nous avons déjà reçu EOF du serveur indiquant qu'il s'est déjà arrêté. Nous continuons donc à l'appeler jusqu'à ce que SSL_shutdown() retourne 1. Puisque nous utilisons une socket non bloquante, nous pourrions avoir à retenter cette opération plusieurs fois. Si SSL_shutdown(3) retourne un résultat négatif, nous devons appeler SSL_get_error(3) pour déterminer quoi faire ensuite. Nous utilisons notre fonction handle_io_failure() que nous avons développée précédemment pour cela :

/*
 * Le pair s'est déjà arrêté gracieusement (nous le savons à cause du
 * SSL_ERROR_ZERO_RETURN (c'est-à-dire EOF) ci-dessus). Nous devrions faire de même en retour.
 */
while ((ret = SSL_shutdown(ssl)) != 1) {
    if (ret < 0 && handle_io_failure(ssl, ret) == 1)
        continue; /* Réessayer */
    /*
     * ret == 0 est inattendu ici car cela signifie "nous avons envoyé un
     * close_notify et nous en attendons un en retour". Mais nous savons déjà
     * que nous en avons reçu un du pair à cause du SSL_ERROR_ZERO_RETURN
     * (c'est-à-dire EOF) ci-dessus.
     */
    printf("Erreur lors de l'arrêt\n");
    goto end; /* Impossible de réessayer : erreur */
}

Nettoyage final

Comme dans l'exemple du client TLS bloquant, une fois que notre connexion est terminée, nous devons la libérer. Les étapes pour le faire dans cet exemple sont les mêmes que pour l'exemple bloquant, nous ne les répéterons donc pas ici.
