DESCRIPTIO

N

gpsd est un démon de surveillance qui collecte des informations provenant de GPS, de radios GPS différentielles, ou de récepteurs AIS connectés à la machine hôte. Chaque GPS, radio DGPS, ou récepteur AIS doit être directement connecté à l'hôte via un périphérique série USB ou RS232C. Le périphérique série peut être spécifié à gpsd au démarrage, ou il peut être défini via une commande envoyée sur un socket de contrôle local (par exemple par un script de hotplug USB). Étant donné un périphérique GPS par l'un ou l'autre moyen, gpsd découvre la vitesse de port et le protocole corrects pour

celui-ci.

gpsd devrait pouvoir interroger tout GPS qui parle soit le protocole textuel standard NMEA 0183, ou les dialectes NMEA étendus (différents) utilisés par MTK-3301, iTrax, Motorola OnCore, Sony CXD2951, Ashtech/Thales et certains autres périphériques. Il peut aussi interpréter les protocoles binaires utilisés par les périphériques EverMore, Garmin, Javad, Navcom, Rockwell/Zodiac, SiRF, Trimble, et u-blox. Sous Linux, il peut lire les paquets NMEA2000 via le socket CAN du noyau. Il peut lire les informations de cap et d'attitude des boussoles numériques TNT

Revolution.

Les formats de rapport GPS pris en charge par votre binaire de gpsd peuvent différer selon la manière dont il a été compilé ; les versions à usage général en prennent en charge beaucoup, mais il peut être construit avec des sous-ensembles de protocoles réduits à un seul pour une utilisation dans des environnements contraints. Pour une liste des protocoles GPS pris en charge par votre binaire, voir la sortie de gpsd

-l

gpsd masque efficacement les différences entre les types de GPS qu'il prend en charge. Il connaît aussi et utilise des commandes qui ajustent ces GPS pour une latence plus faible. En utilisant gpsd comme intermédiaire, les applications évitent la contention pour les périphériques

série.

gpsd peut utiliser des corrections GPS différentielles provenant d'une radio DGPS ou via le réseau, depuis une station de sol exécutant un serveur DGPSIP ou un diffuseur Ntrip qui rapporte des données RTCM-104 ; cela peut réduire les erreurs de position. Quand gpsd ouvre un périphérique série émettant du RTCM-104, il reconnaît automatiquement cela et utilise le périphérique comme source de correction pour tous les GPS connectés qui acceptent les corrections RTCM (cela dépend du type du GPS ; tous les GPS n'ont pas la capacité firmware d'accepter les paquets de correction RTCM)

.

Les applications clientes communiquent généralement avec gpsd via un port TCP/IP, le port 2947 par défaut. Les connexions IPv4 et IPv

6 sont prises en charge et un client
peut se connecter via l'une ou l'autre.

En interne, le démon maintient un pool de périphériques contenant les chemins des périphériques et des serveurs distants connus du démon. GESTION DES PÉRIPHÉRIQUES

GPS

gpsd maintient une liste interne de périphériques GPS (le "pool de périphériques"). Si vous spécifiez des périphériques sur la ligne de commande, la liste est initialisée avec ces chemins, sinon la liste commence vide. Les commandes pour ajouter et supprimer des chemins de périphériques GPS de la liste de périphériques du démon doivent être écrites sur un socket de domaine Unix local qui ne sera accessible qu'aux programmes s'exécutant en tant que root. Ce socket de contrôle sera situé là où l'option -F le

spécifie.

Un périphérique peut également être retiré du pool si GPSD reçoit une lecture de longueur zéro de celui-ci. Cette condition de fin de fichier indique que le périphérique a été

déconnecté.

Lorsque gpsd est installé avec des scripts de notification hotplug fonctionnels qui lui envoient des commandes d'ajout de périphérique via le socket de contrôle, gpsd ne devrait nécessiter aucune configuration ni action de l'utilisateur pour trouver les périphériques

hotplug.

L'envoi de SIGHUP à un gpsd en cours d'exécution le force à fermer tous les GPS et toutes les connexions clients. Il essaiera alors de se reconnecter à tous les GPS de sa liste de périphériques et de reprendre l'écoute des connexions clients. Cela peut être utile si votre GPS entre dans un état bloqué ou confus mais peut être réinitialisé en abaissant

DTR.

Lorsque >gpsd est appelé sans aucun périphérique initial (donc, il s'attend à ce que les périphériques lui soient transmis par des notifications au socket de contrôle), et atteint un état où aucun périphérique n'est connecté et aucun abonné après que certains périphériques aient été vus, il s'arrête proprement. Il est attendu que les futurs événements de connexion à chaud des périphériques le réactiveront.

Pour pointer gpsd vers un périphérique susceptible d'être un GPS, écrivez sur le socket de contrôle un signe plus ('+') suivi du nom du périphérique suivi de LF ou CR-LF. Ainsi, pour pointer le démon vers /dev/foo. envoyez "+/dev/foo\n". Pour indiquer au démon qu'un périphérique a été déconnecté et n'est plus disponible, envoyez un signe moins ('-') suivi du nom du périphérique suivi de LF ou CR-LF. Ainsi, pour supprimer /dev/foo de la liste de recherche, envoyez "-/dev/foo\n".

Pour envoyer une chaîne de contrôle à un périphérique spécifié, écrivez sur le socket de contrôle un '!', suivi du nom du périphérique, suivi de '=', suivi de la chaîne de contrôle.

Pour envoyer une chaîne de contrôle binaire à un périphérique spécifié, écrivez sur le socket de contrôle un '&', suivi du nom du périphérique, suivi de '=', suivi de la chaîne de contrôle en chiffres hexadécimaux appariés.

Votre client peut attendre une réponse, qui sera une ligne commençant par "OK" ou "ERROR". Une réponse ERROR à une commande 'add' signifie que le périphérique n'a pas émis de données reconnaissables comme des paquets GPS, une réponse ERROR à une commande de suppression signifie que le périphérique spécifié n'était pas dans le pool de périphériques de gpsd. Une réponse ERROR à une commande '!' signifie que le démon n'a pas reconnu le nom du périphérique spécifié.

Le socket de contrôle est destiné à être utilisé par des scripts de branchement à chaud et d'autres services de découverte de périphériques. Ce canal de contrôle est séparé du port de service public de gpsd et n'est accessible qu'en local, afin d'éviter les attaques par déni de service et d'usurpation à distance.

ACCURACY

L'erreur d'estimation de la portée utilisateur (UERE) de base des GPS est de 8 mètres ou moins à 66% de confiance, 15 mètres ou moins à 95% de confiance. L'erreur horizontale réelle sera UERE multipliée par un facteur de dilution dépendant de la position actuelle des satellites. La détermination de l'altitude est plus sensible à la variabilité du décalage du signal ionosphérique que la latitude/longitude, et est également soumise aux erreurs d'estimation du niveau moyen de la mer local, l'erreur de base est de 12 mètres à 66% de confiance, 23 mètres à 95% de confiance. Encore une fois, cela sera multiplié par une dilution de précision verticale (VDOP) dépendant de la géométrie des satellites, et le VDOP est généralement plus grand que le HDOP. Les utilisateurs ne doivent *pas* compter sur l'altitude GPS pour des tâches critiques pour la vie telles que l'atterrissage d'un avion.

Ces erreurs sont intrinsèques à la conception et à la physique du système GPS. gpsd effectue ses calculs internes avec une précision suffisante pour n'ajouter aucune erreur de position mesurable.

La correction DGPS peut réduire l'UERE, à condition que vous soyez à environ 100 miles (160 km) d'une station au sol DGPS dont vous recevez des corrections.

Sur une connexion 4800bps, la latence des corrections fournies par gpsd sera d'une seconde ou moins dans 95% des cas. La majeure partie de ce décalage est due au fait que les GPS émettent normalement des corrections une fois par seconde, donc la latence attendue est de 0,5 seconde. Sur le matériel informatique personnel disponible à partir de 2005, le décalage de calcul induit par gpsd sera négligeable, de l'ordre d'un milliseconde. Néanmoins, la latence peut introduire des erreurs importantes pour les véhicules en mouvement, à une vitesse de 50 km/h, 1 seconde de décalage correspond à un changement de position de 13,8 mètres entre les mises à jour.

Le rapport temporel du système GPS lui-même a une limite de précision intrinsèque de 14 nanosecondes, mais cela ne peut être qu'approximé par des récepteurs spécialisés utilisant le PPS (Pulse-Per-Second) de haute précision envoyé sur RS232 pour commander un cristal d'horloge. La plupart des récepteurs GPS ne rapportent que l'heure avec une précision de 0,01 s ou 0,001 s, et sans garantie de précision en dessous de 1 seconde.

Si votre GPS utilise un chipset SiRF avec le niveau de firmware 231, l'heure UTC rapportée peut être décalée de la différence entre le décalage de seconde intercalaire par défaut qui a été compilé et la correction de seconde intercalaire actuellement applicable, depuis le démarrage jusqu'à la réception des informations complètes de sous-trame. Les niveaux de firmware 232 et supérieurs n'ont pas ce problème. Vous pouvez exécuter gpsd au niveau de débogage 4 pour voir le type de chipset et le niveau de révision du firmware.

Il existe exactement deux circonstances dans lesquelles gpsd s'appuie sur l'horloge du système hôte :

Dans le signal de diffusion GPS, l'heure GPS est représentée à l'aide d'un numéro de semaine qui se réinitialise après 2^10 ou 2^13 semaines (environ 19,6 ans, ou 157 ans), selon le vaisseau spatial. Les récepteurs sont tenus de désambiguïser cela pour obtenir la date correcte, mais peuvent avoir des difficultés en raison de ne pas connaître l'heure à moins de la moitié de cet intervalle, ou peuvent avoir des bugs. Des utilisateurs ont rapporté des dates incorrectes qui semblent être dues à ce problème. gpsd utilise l'heure de démarrage du démon pour détecter et compenser les réinitialisations pendant son exécution, mais sinon, il rapporte la date telle qu'elle est rapportée par le récepteur sans tenter de la corriger.

Si vous utilisez un GPS NMEA uniquement (c'est-à-dire que vous n'utilisez pas le mode binaire SiRF, Garmin ou Zodiac), gpsd s'appuie sur l'horloge système pour connaître le siècle actuel. Si l'horloge système renvoie une valeur invalide proche de zéro, et que le GPS n'émet pas de GPZDA au début de son cycle de mise à jour (ce que la plupart des GPS NMEA grand public ne font pas), alors la partie siècle des dates que gpsd livre peut être erronée. De plus, près du changement de siècle, une plage de dates aussi large en secondes que la précision de votre horloge système peut être référée au siècle incorrect.

UTILISATION AVEC NTP

gpsd peut fournir des informations d'horloge de référence à ntpd ou chronyd, pour maintenir l'horloge système synchronisée avec l'heure fournie par le récepteur GPS.

Sur Linux, gpsd inclut la prise en charge de l'interprétation des impulsions PPS émises au début de chaque seconde sur les lignes de détection de porteuse de certains GPS série ; cette impulsion peut être utilisée pour mettre à jour NTP avec une précision beaucoup plus élevée que celle fournie par l'heure des messages. Vous pouvez déterminer si votre GPS émet cette impulsion en exécutant avec -D 5 et en observant les messages de changement d'état de détection de porteuse dans le fichier journal. De plus, si votre noyau fournit l'API du noyau RFC 2783 pour le PPS, gpsd l'utilisera pour une précision supplémentaire.

gpsd communique avec ntpd en utilisant des segments de mémoire partagée (SHM). Les SHM sont numérotés SHM(0) à SHM(7) et ont un nom (clé) de NTP0 à NTP7. La première source de temps locale sur la ligne de commande peut utiliser NTP0 et NTP1. La seconde peut utiliser NTP2 et NTP3, etc.

Vous pouvez voir la sortie de gpsd vers ntpd en temps réel avec la commande ntpshmmon.

D'autres démons, tels que ptp4l, peuvent également utiliser les mêmes SHM pour communiquer avec ntpd.

Des instructions détaillées pour utiliser GPSD afin de configurer un service horaire de haute qualité sont disponibles dans la documentation du site Web de GPSD.

UTILISATION AVEC D-BUS

Sur les systèmes d'exploitation qui prennent en charge D-BUS, gpsd peut être compilé pour diffuser des corrections GPS aux applications compatibles D-BUS. Comme D-BUS est encore à un stade pré-1.0, nous n'essaierons pas de documenter cette interface ici. Lisez le code source de gpsd pour en savoir plus.

PROBLÈMES DE SÉCURITÉ ET DE PERMISSIONS

gpsd, s'il reçoit l'option -G, écoutera les connexions de n'importe quel hôte joignable, puis divulguera la position actuelle. Avant d'utiliser l'option -G, demandez-vous si vous considérez que la localisation de votre ordinateur est une donnée sensible à garder privée ou quelque chose que vous souhaitez publier.

gpsd doit démarrer en tant que root pour ouvrir le segment de mémoire partagée NTPD, ouvrir son fichier journal et créer son socket de contrôle local. Notez que démarrer gpsd avec sudo n'est pas la même chose que démarrer en tant que root. Avant de traiter des données GPS, il essaie de renoncer aux privilèges root en définissant son UID sur "nobody" (ou un autre ID utilisateur configuré) et son GID sur le groupe du GPS initial passé en ligne de commande — ou, si ce périphérique n'existe pas, sur le groupe de /dev/ttyS0.

La suppression de privilèges est une mesure de précaution contre la possibilité que des données soigneusement conçues, soit présentées depuis un socket client, soit depuis un périphérique série compromis se faisant passer pour un GPS, puissent être utilisées pour induire un comportement erroné dans les internes de gpsd. Cela garantit que toute compromission de ce type ne peut pas être utilisée pour une élévation de privilèges vers root.

L'hypothèse derrière le comportement particulier de gpsd est que tous les périphériques tty auxquels un GPS pourrait être connecté appartiennent au même groupe non root et autorisent la lecture/écriture en groupe, bien que le groupe puisse varier en fonction des pratiques administratives spécifiques à la distribution ou locales. Si cette hypothèse est fausse, gpsd pourrait ne pas être en mesure d'ouvrir les périphériques GPS pour les lire (ces échecs seront enregistrés).

Pour se prémunir contre les attaques par déni de service involontaires des scanners de ports (sans parler des attaques délibérées), gpsd interrompra les connexions client inactives. Avant que le client n'ait émis une commande demandant une affectation de canal, un court délai d'attente (60 secondes) s'applique. Il n'y a pas de délai d'attente pour les clients en mode watcher ou raw ; plutôt, gpsd déconnecte ces clients s'ils ne parviennent pas à lire les données assez longtemps pour que le tampon d'écriture du socket de sortie soit plein. Les clients ayant un périphérique affecté en mode polling sont soumis à un délai d'attente plus long (15 minutes).

LIMITATION

S

Si plusieurs émetteurs NMEA envoient des phrases RMC, GLL et GGA au même port série (possible avec un adaptateur RS422 connecté à certains systèmes de navigation marine), une réponse « TPV » peut mélanger une altitude provenant du GGA d'un appareil avec la latitude/longitude du RMC/GLL d'un autre après l'arrivée de la deuxième

phrase.

gpsd peut modifier les paramètres de contrôle de votre GPS (comme la fréquence d'émission de certaines phrases ou paquets) et ne pas restaurer les paramètres d'origine à la sortie. C'est le résultat des insuffisances des protocoles NMEA et binaires propriétaires des GPS, qui ne donnent souvent aucun moyen aux clients d'interroger les valeurs des paramètres de contrôle afin de pouvoir les restaurer

ultérieurement.

Certains récepteurs ne rapportent pas les valeurs VDOP/TDOP/GDOP et les estimations d'erreur associées. Dans ce cas, elles peuvent être calculées par gpsd à la place. Ce calcul ne correspond pas exactement à ce que les puces font en interne, ce qui inclut un certain pondération de satellites utilisant des paramètres gpsd ne peut pas

voir.

L'auto-configuration de la vitesse de transmission sur les GPS Trimble peut prendre jusqu'à 20 secondes, ou plus, si la vitesse de l'appareil n'est pas adaptée à celle du GPS. Utilisez l'option -s pour éviter les délais d'auto-configuration

.

La génération des estimations d'erreur de position (eph, epv, epd, eps, epc) à partir des données incomplètes renvoyées par les protocoles de rapport GPS implique à la fois beaucoup de mathématiques ésotériques et des hypothèses fragiles dépendant de l'appareil. Ce code a été sujet aux bugs par le passé et des problèmes peuvent encore s'y

cacher.

Le décodage AIVDM des types 16-17, 22-23 et 25-26 n'est pas

vérifié.

GPSD ne reconnaît actuellement pleinement que le niveau 2.1 de RTCM2 (types de messages 1, 3, 4, 5, 6, 7, 9, 16). Les types de messages 13, 14 et 31 de la version 2.3 sont reconnus et rapportés. Les types de messages 8, 10-12, 15-27, 28-30 (non définis), 31-37, 38-58 (non définis) et 60-63 ne sont pas encore pris en

charge.

La logique du décodeur ISGPS utilisé pour RTCM2 et les sous-trames est suffisamment complexe pour déconcerter certains optimiseurs de compilateurs, notamment GCC 3.x avec -O2, en générant du code

incorrect.

Les appareils destinés à utiliser PPS pour une horodatage de haute précision peuvent échouer s'ils sont spécifiés après le démarrage par une commande de socket de contrôle, par opposition à la ligne de commande originale du démon. Les privilèges root sont abandonnés tôt, et certaines variantes Unix les exigent pour configurer la discipline de ligne PPS. Sous Linux, la capacité POSIX de configurer la discipline de ligne est conservée, mais les autres plateformes ne peuvent pas utiliser ce

code.

Les appareils GPS USB ne s'identifient souvent pas à travers le sous-système USB ; ils se présentent généralement comme la classe 00h (non définie) ou la classe FFh (spécifique au fournisseur) des adaptateurs USB vers série. En raison de cela, les scripts de hotplug Linux doivent dire à gpsd de renifler les données de chaque adaptateur USB vers série qui devient actif et qui est connu comme étant d'un type utilisé dans les GPS. Aucune chaîne de configuration n'est envoyée à un tel appareil avant qu'il n'ait été identifié comme un GPS, et gpsd n'ouvre jamais un appareil qui est ouvert par un autre processus. Mais il existe une très petite fenêtre pour les appareils non-GPS non ouverts ; si l'application qui les ve

ut perd une course contre GPSD, l'ouverture de son appareil échouera et devra être réessay
ée après que GPSD ait reniflé l'appareil (normalement moins d'une seconde plus tard).

APPLICABLE

STANDARDS

Les standards officiels du protocole NMEA pour NMEA0183 et NMEA2000 sont disponibles auprès de la National Marine Electronics Association, mais sont propriétaires et coûteux ; les mainteneurs de gpsd ont fait une règle de ne pas les consulter. Le site web du projet GPSD fournit des liens vers plusieurs documents qui rassemblent des informations publiquement divulguées sur le

protocole.

gpsd analyse les phrases NMEA suivantes : RMC, GGA, GLL, GSA, GSV, VTG, ZDA, GBS, HDT, DBT, GST. Il les reconnaît avec soit le préfixe d'identifiant d'émetteur GP normal, soit le préfixe GN utilisé par GLONASS, soit le préfixe II émis par les systèmes de navigation marine Seahawk Autohelm, soit le préfixe IN émis par certaines unités Garmin, soit le préfixe EC émis par les unités ECDIS, soit le préfixe SD émis par les sondeurs de profondeur, soit les préfixes HC et TI émis par certains équipements Airmar. Il reconnaît certaines extensions propriétaires : le PGRME émis par certains modèles de GPS Garmin, le PTNTHTM émis par les boussoles numériques True North, le PMTK omis par certains GPS San Jose Navigation, et les phrases PASHR émis par certains GPS

Ashtech.

Notez que gpsd JSON renvoie des degrés décimaux purs, pas le format hybride degrés/minutes décrit dans le standard

NMEA.

Les corrections différentielles GPS sont transmises par les protocoles RTCM. Le standard applicable pour RTCM-104 V2 est RTCM Recommended Standards for Differential GNSS (Global Navigation Satellite) Service RTCM Paper 136-2001/SC 104-STD. Le standard applicable pour RTCM-104 V3 est RTCM Standard 10403.1 for Differential GNSS Services - Version 3 RTCM Paper 177-2006-SC104-STD. Les instructions de commande des standards RTCM sont accessibles depuis le site web de la Radio Technical Commission for Maritime Services sous « Publications »

.

AIS est défini par la Recommandation UIT M.1371, Technical Characteristics for a Universal Shipborne Automatic Identification System Using Time Division Multiple Access. Le format AIVDM/AIVDO compris par ce programme est défini par IEC-PAS 61162-100, Maritime navigation and radiocommunication equipment and systems. Une description plus accessible des deux se trouve dans AIVDM/AIVDO Protocol Decoding, sur la page des références du site web du projet

GPSD.

Les données de sous-trame sont définies par IS-GPS-200, GLOBAL POSITIONING SYSTEM WING (GPSW) SYSTEMS ENGINEERING & INTEGRATION, INTERFACE SPECIFICATION IS-GPS-200. Le format compris par ce programme est défini dans la Section 20 (Annexe II)
