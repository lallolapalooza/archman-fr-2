PRÉSENTATIO

N

gpsd est un démon de service qui peut être utilisé pour surveiller des GPS, des récepteurs DGPS, des émissions AIS maritimes et divers autres capteurs liés à la localisation et à la

cinématique.

Les clients peuvent communiquer avec gpsd au moyen de requêtes et de réponses textuelles sur un socket. Il est déconseillé aux applications de parler directement le protocole : elles devraient plutôt utiliser la bibliothèque client libgps (pour C ; des liaisons existent également pour d'autres langages) et prendre les précautions appropriées pour vérifier dans leur code les versions majeure et mineure attendues du

protocole.

Le protocole GPSD est construit au-dessus de JSON, JavaScript Object Notation, tel que spécifié dans [RFC-7159] : The JavaScript Object Notation (JSON) Data Interchange Format. Similaire à ECMA

404.

L'utilisation de JSON par GPSD est restreinte de certaines manières qui facilitent son analyse dans des langages à taille fixe (comme C)

.

Une ligne de requête est introduite par "?" et peut inclure plusieurs commandes. Les commandes commencent par un identifiant de commande, suivi soit par un ";" terminal, soit par un signe égal "=" et un objet JSON traité comme argument. Tout ";" ou indication de fin de ligne (LF ou CR-LF) après la fin d'une commande est ignoré. Toutes les lignes de requête doivent être composées de caractères US-ASCII et ne peuvent pas dépasser 80 caractères de longueur, à l'exclusion du retour à la ligne

final.

Les réponses sont des objets JSON uniques possédant un attribut "class" dont la valeur est le type d'objet. Les types d'objets incluent, sans s'y limiter : "TPV", "SKY", "DEVICE" et "ERROR". Les objets sont envoyés aussi bien en réponse à des commandes que périodiquement lorsque gpsd envoie des rapports. Chaque objet est terminé par un retour chariot et un nouveau ligne (CR-NL)

.

L'ordre des attributs JSON au sein d'un objet de réponse n'est jamais significatif, et vous pouvez spécifier les attributs de commande dans n'importe quel ordre. Les réponses ne contiennent jamais la valeur JSON spéciale null ; à la place, les attributs avec des valeurs vides ou indéfinies sont omis. La limite de longueur pour les réponses et les rapports est actuellement de 10240 caractères, y compris le CR-NL final. Les réponses plus longues seront tronquées, le code client doit donc être préparé à la possibilité de fragments JSON

invalides.

La longueur maximale par défaut des messages est définie par GPS_JSON_RESPONSE_MAX dans include/gpsd_json.h, au moment de la

compilation.

Dans les rapports JSON, si un attribut n'est présent que si l'attribut parent est présent ou a une plage particulière, alors l'attribut parent est émis en

premier.

Il existe une contrainte sur l'ordre dans lequel les attributs seront omis. Si un attribut optionnel n'est présent que lorsque l'attribut parent a une valeur ou une plage de valeurs spécifiée, l'attribut parent sera émis en premier pour faciliter

l'analyse.

La section suivante documente le protocole GPSD de base. Les extensions sont documentées dans les sections suivantes. Les extensions peuvent ne pas être prises en charge dans votre instance de gpsd si elle a été compilée avec un ensemble de fonctionnalités

restreint.

TP

Un objet TPV est un rapport temps-position-vitesse. Les champs "class" et "mode" seront présents de manière fiable. Lorsque "mode" est 0 (Inconnu), il n'y a probablement pas de données utilisables dans la phrase. Les champs restants sont optionnels, leur présence dépend des données que le récepteur GNSS a envoyées, et de ce que gpsd peut calculer à partir de ces

données.

Un objet TPV sera généralement envoyé au moins une fois pour chaque époque de mesure telle que déterminée par le champ "time". À moins que le récepteur n'ait une solution solide et ne connaisse la seconde intercalaire actuelle, le temps peut être

aléatoire.

Plusieurs objets TPV sont souvent envoyés par époque. Lorsque le récepteur fait couler les données vers gpsd, alors gpsd n'a d'autre choix que de les faire couler vers le client dans plusieurs messages

TPV.

Le champ optionnel "status" (alias type de solution) est un modificateur (adjectif) pour mode. Ce n'est pas un remplacement de, ni un sur-ensemble du, champ "mode". C'est presque, mais pas tout à fait, la même chose que les valeurs d'indicateur de qualité GPS xxGGA de la norme NMEA 4.x. Beaucoup de récepteurs GNSS ne le fournissent pas. Ceux qui le font interprètent la spécification de diverses manières incompatibles. Pour économiser de l'espace dans la sortie et éviter la confusion, le JSON n'inclut jamais les valeurs de statut 0 ou

1.

Toutes les estimations d'erreur (epc, epd, epe, eph, ept, epv, epx, epy) sont supposées être à 95% de confiance, peuvent aussi être à 50%, à une sigma, ou à deux sigma de confiance. Beaucoup de récepteurs GNSS ne spécifient pas de niveau de confiance. Aucun ne spécifie comment la valeur est calculée. Utilisez les estimations d'erreur avec prudence, et seulement comme indicateurs relatifs de "bonté". Si le GPS rapporte une valeur à gpsd, alors gpsd rapportera cette valeur. Sinon gpsd essaiera de calculer la valeur à partir de la vue du

ciel.

Voir le fichier include/gps.h, en particulier struct gps_data_t, pour des notes détaillées sur les éléments et les valeurs du message

TPV.

Un objet ATT est un rapport d'attitude du véhicule. Il est renvoyé par des capteurs de boussole numérique et de gyroscope ; selon l'appareil, il peut inclure : le cap, le tangage, le roulis, le lacet, le gyroscope et des relevés de champ magnétique. Comme de tels capteurs sont souvent intégrés dans des systèmes de navigation maritime, la réponse ATT peut également inclure la profondeur de

l'eau.

Les champs "class" et "mode" seront présents de manière fiable. Les autres peuvent être rapportés ou non selon le type spécifique de

l'appareil.

L'objet ATT est synchrone à l'époque GNSS. Certains appareils rapportent des informations d'attitude avec des échelles de temps arbitraires, voire désordonnées. gpsd les rapporte dans un objet IMU. Les objets ATT et IMU ont les mêmes champs, mais les objets IMU sont produits dès que possible. Certains appareils produisent les deux types avec un entrelacement

arbitraire.

IMU

L'objet IMU est asynchrone par rapport à l'époque GNSS. Il est rapporté avec des échelles de temps arbitraires, voire désordonnées.

Les objets ATT et IMU ont les mêmes champs, mais les objets IMU sont produits dès que possible.

Voir la description de l'objet ATT pour les détails des champs.

TOFF

Ce message est émis à chaque cycle et rapporte le décalage entre l'horloge de l'hôte et le temps GPS au début de la seconde (en fait, lorsque les premières données du cycle de rapport sont reçues).

Ce message reflète exactement le message PPS.

PPS

Ce message est émis chaque fois que le démon voit une impulsion PPS (Pulse Per Second) valide provenant d'un appareil.

Ce message reflète exactement le message TOFF.

Le message TOFF rapporte le temps GPS tel que dérivé du flux de données série GPS. Le message PPS rapporte le temps GPS tel que dérivé de l'impulsion PPS GPS.

Il existe diverses sources d'erreur dans les temps d'horloge rapportés. La vitesse de la connexion série entre le GPS et le système ajoute un retard au début de la détection de cycle. Une erreur encore plus importante est ajoutée par le temps de calcul variable à l'intérieur du GPS. Pris ensemble, le temps dérivé du début du cycle GPS peut avoir des décalages de 10 millisecondes à 700 millisecondes et une gigue et une dérive combinées de 100 à 300 millisecondes.

?DEVICE; ?DEVICE=

Cette commande rapporte (lorsqu'elle est suivie de ';') l'état d'un appareil, ou définit (lorsqu'elle est suivie de '=' et d'un objet DEVICE) des bits de contrôle spécifiques à l'appareil, notamment la vitesse et le mode série de l'appareil, ainsi que le bit de mode natif. La forme de réglage des paramètres sera rejetée si plus d'un client est attaché au canal et si un chemin d'appareil n'est pas spécifié.

Faites attention à la réponse, car il est possible que cette commande échoue si le GPS ne prend pas en charge une commande ou ne prend en charge que certaines combinaisons de modes. En cas d'échec, le démon et le GPS continueront de communiquer à l'ancienne vitesse.

Utilisez la forme de réglage des paramètres avec prudence. Sur les GPS USB et Bluetooth, il est également possible que le réglage du mode série échoue, soit parce que la puce de l'adaptateur série ne prend pas en charge les modes autres que 8N1, soit parce que le firmware de l'appareil ne synchronise pas correctement la puce de l'adaptateur série avec l'UART du chipset GPS lorsque la vitesse change. Ces échecs peuvent bloquer votre appareil, nécessitant éventuellement un cycle d'alimentation du GPS ou (dans les cas extrêmes) le débranchement physique de la batterie de sauvegarde NVRAM.

TRANSMISSIONS FILAIRES

RTCM

Les stations de correction GPS différentielles se composent d'un récepteur de référence GPS couplé à un émetteur basse fréquence (LF). Le récepteur de référence GPS est un GPS de niveau géodésique qui effectue le suivi de la porteuse GPS et peut déterminer sa position à quelques millimètres près. Il génère des corrections de distance et de vitesse de distance et les encode en RTCM104. Il transmet le RTCM104 à l'émetteur LF via un signal série rs-232 à 100 ou 200 bauds selon les exigences de

l'émetteur.

L'émetteur LF diffuse le signal radio d'environ 300 kHz que les récepteurs radio GPS différentiels captent. Les émetteurs destinés à une plus grande portée

devront émettre à un débit plus lent. Plus le débit de données est élevé, plus il sera difficile pour le récepteur radio distant de recevoir un bon rapport s
ignal sur bruit. (Les signaux à débit de données élevé ne peuvent pas être moyennés sur une aussi longue période, ils apparaissent donc comme plus bruités.)

FORMATS FILAIRES

RTCM

Un message RTCM 2.x se compose d'une séquence d'au plus 33 mots de 30 bits. Les 24 bits de poids fort de chaque mot sont des données et les six bits de poids faible sont la parité. L'algorithme de parité utilisé est le même ISGPS-2000 que celui utilisé sur les liaisons descendantes des satellites GPS. Chaque message RTCM 2.x se compose de deux mots d'en-tête suivis de zéro ou plusieurs mots de données, selon le type de

message.

Un message RTCM 3.x commence par un octet d'amorce fixe 0xD3. S'y suivent six bits d'information de version

et 10 bits d'information de longueur de charge utile. Vient ensuite la charge utile ; après celle-ci se
trouve une somme de contrôle de 3 octets de la charge utile calculée avec l'algorithme Qualcomm CRC-24Q.

FORMATS DE DUMP

AIS

La prise en charge de l'AIS est une extension. Elle peut ne pas être présente si votre instance de gpsd a été construite avec un ensemble de fonctionnalités

restreint.

Les paquets AIS sont dumpés en tant qu'objets JSON avec la classe "AIS". Chaque objet de rapport AIS contient un champ "type" donnant le type de message AIS et un champ "scaled" indiquant si le reste des champs est dumpé sous forme mise à l'échelle ou non. (Ceux-ci seront émis avant tout champ spécifique au type.) Il contiendra également un champ "device" nommant la source de données. Les autres champs ont les noms et types tels que spécifiés dans le document AIVDM/AIVDO Protocol Decoding sur le site web du projet GPSD ; chaque tableau de champs de message peut être directement interprété comme une spécification pour les membres du type d'objet JSON

correspondant.

Par défaut, certaines opérations de mise à l'échelle et de conversion sont effectuées pour la sortie JSON. Les latitudes et longitudes sont mises à l'échelle en degrés décimaux plutôt que dans l'unité native AIS de 1/10000e de minute d'arc. Les vitesses des navires (mais pas des aéronefs) sont mises à l'échelle en nœuds plutôt qu'en dixièmes de nœud. La vitesse de rotation peut apparaître comme "nan" si elle est indisponible, ou comme l'une des chaînes "fastright" ou "fastleft" si elle est hors de la plage de codage AIS ; sinon, elle est rétro-mappée quadratiquement sur le numéro du capteur de rotation en degrés par minute. Les tirants d'eau des navires sont convertis en mètres décimaux plutôt qu'en décimètres AIS natifs. Diverses autres conversions de mise à l'échelle sont décrites dans « AIVDM/AIVDO Protocol Decoding

»
.

Beware. What most people think of as the PRN is not the PRN that each constellation (GPS, GLONASS, BeiDou, etc.) uses in its

documentation.

Each constellation numbers its PRNs starting from 1. GPS reserves all PRNs up to 1023. What most users think of as the PRN is what NMEA calls a PRN, which is not the native, standardized, PRN. NMEA PRNs started out as the GPS PRNs, but when other constellations became available, GNSS receiver vendors overloaded that NMEA field. Without standardizing, or coordinating, between themselves. Some receivers use different PRN mappings depending on runtime configuration. Don’t expect any specificity in an NMEA PRN, there is no consensus

meaning.

To leave this mess behind, receiver vendors now refer to each satellite by its constellation (GPS, GLONASS, etc.), and its PRN (starting at 1) within that

constellation.
