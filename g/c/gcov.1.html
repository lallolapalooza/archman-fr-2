NOM

gcov - outil de test de couverture

DESCRIPTION

gcov est un programme de test de couverture. Utilisez-le en conjonction avec GCC pour analyser vos programmes afin de vous aider à créer du code plus efficace et plus rapide, et à découvrir les parties non testées de votre programme. Vous pouvez utiliser gcov comme un outil de profilage pour vous aider à découvrir où vos efforts d'optimisation auront le plus d'effet sur votre code. Vous pouvez également utiliser gcov avec l'autre outil de profilage, gprof, pour évaluer quelles parties de votre code utilisent le plus grand temps de calcul.

Les outils de profilage vous aident à analyser les performances de votre code. En utilisant un profileur tel que gcov ou gprof, vous pouvez obtenir certaines statistiques de performance de base, telles que :

  • la fréquence d'exécution de chaque ligne de code
  • quelles lignes de code sont réellement exécutées
  • le temps de calcul utilisé par chaque section de code

Une fois que vous savez ces choses sur le fonctionnement de votre code lors de la compilation, vous pouvez examiner chaque module pour voir quels modules devraient être optimisés. gcov vous aide à déterminer où travailler sur l'optimisation.

Les développeurs de logiciels utilisent également le test de couverture en conjonction avec des suites de tests, pour s'assurer que le logiciel est réellement suffisamment bon pour une publication. Les suites de tests peuvent vérifier qu'un programme fonctionne comme prévu ; un programme de couverture teste pour voir dans quelle mesure le programme est exercé par la suite de tests. Les développeurs peuvent alors déterminer quels types de cas de test doivent être ajoutés aux suites de tests pour créer à la fois de meilleurs tests et un meilleur produit final.

Vous devriez compiler votre code sans optimisation si vous prévoyez d'utiliser gcov car l'optimisation, en combinant certaines lignes de code en une fonction, peut ne pas vous donner autant d'informations que nécessaire pour rechercher les « points chauds » où le code utilise une grande quantité de temps machine. De même, car gcov accumule les statistiques par ligne (à la plus faible résolution), il fonctionne le mieux avec un style de programmation qui ne place qu'une seule instruction sur chaque ligne. Si vous utilisez des macros compliquées qui s'étendent en boucles ou en autres structures de contrôle, les statistiques sont moins utiles---elles ne rapportent que la ligne où l'appel de macro apparaît. Si vos macros complexes se comportent comme des fonctions, vous pouvez les remplacer par des fonctions en ligne pour résoudre ce problème.

gcov crée un fichier journal appelé sourcefile.gcov qui indique combien de fois chaque ligne d'un fichier source sourcefile.c a été exécutée. Vous pouvez utiliser ces fichiers journal avec gprof pour aider à régler finement les performances de vos programmes. gprof fournit des informations de chronométrage que vous pouvez utiliser avec les informations que vous obtenez de gcov.

gcov ne fonctionne que sur du code compilé avec GCC. Il n'est pas compatible avec aucun autre mécanisme de profilage ou de test de couverture.

OPTIONS

-a
--all-blocks
Écrit les comptages d'exécution individuels pour chaque bloc de base. Normalement, gcov ne produit des comptages d'exécution que pour les blocs principaux d'une ligne. Avec cette option, vous pouvez déterminer si des blocs à l'intérieur d'une seule ligne ne sont pas exécutés.
-b
--branch-probabilities
Écrit les fréquences de branchement dans le fichier de sortie et écrit les informations de résumé de branchement sur la sortie standard. Cette option vous permet de voir combien de fois chaque branche de votre programme a été prise. Les branches inconditionnelles ne seront pas affichées, sauf si l'option -u est donnée.
-c
--branch-counts
Écrit les fréquences de branchement sous forme de nombre de branches prises, plutôt que sous forme de pourcentage de branches prises.
-g
--conditions
Écrit la couverture des conditions dans le fichier de sortie et écrit les informations de résumé des conditions sur la sortie standard. Cette option vous permet de voir si les conditions de votre programme ont eu au moins une fois un effet indépendant sur le résultat de l'expression booléenne (couverture condition/décision modifiée). Cela nécessite de compiler la source avec -fcondition-coverage.
-e
--prime-paths
Écrit la couverture des chemins dans le fichier de sortie et écrit les informations de résumé des chemins sur la sortie standard. Cette option vous permet de voir combien de chemins premiers ont été empruntés au moins une fois. Un chemin est une séquence de blocs de base. Un chemin est simple s'il n'a pas de blocs répétés (pas de boucles) sauf peut-être le premier et le dernier bloc, et premier s'il s'agit d'un chemin simple de longueur maximale. Pour la sortie régulière, cette option n'inclut que le nombre de chemins couverts. Pour des informations plus détaillées sur les chemins, vous pouvez utiliser --prime-paths-lines ou --prime-paths-source. Avec --json-format tous les détails des chemins sont inclus dans la sortie. Cela nécessite de compiler la source avec -fpath-coverage.
--prime-paths-lines [=type]
Écrit la couverture des chemins dans le fichier de sortie et écrit les informations de résumé des chemins sur la sortie standard. Cette option vous permet de voir combien de chemins premiers ont été empruntés au moins une fois, et un rapport détaillé sur les chemins couverts ou non couverts et comment les couvrir. Ce mode est utile pour le reporting automatisé et le suivi de progression. type peut être omis, ou être l'un des suivants :
  • uncovered - Inclure les chemins non couverts (non empruntés). C'est la valeur par défaut.
  • covered - Inclure les chemins couverts (empruntés).
  • both - Inclure tous les chemins. C'est équivalent à utiliser à la fois covered et uncovered.

Voici un exemple de sortie de --prime-paths-lines :

paths covered 12 of 15
path  2 not covered: lines 8 8(false) 11(true) 11 13(true) 13(true) 14 17
path  3 not covered: lines 8 8(false) 11(true) 11 13(true) 13(false) 16 17
path  4 not covered: lines 8 8(false) 11(true) 11 13(false) 16 17

Cela signifie que pour couvrir le chemin 2, vous devez exécuter les lignes 8, 11, 13, 14 et 17, en évaluant la décision à 8 comme fausse et les décisions à 11 et 13 comme "false".

--prime-paths-source [=type]
Écrit la couverture des chemins dans le fichier de sortie et écrit les informations de résumé des chemins sur la sortie standard. Cette option vous permet de voir combien de chemins premiers ont été empruntés au moins une fois, et un rapport détaillé sur les chemins non couverts et comment les couvrir. Ce mode est utile pour comprendre les chemins et les interactions entre les sections de votre programme. type peut être omis, ou être l'un des suivants :
  • uncovered - Inclure les chemins non couverts (non empruntés). C'est la valeur par défaut.
  • covered - Inclure les chemins couverts (empruntés).
  • both - Inclure tous les chemins. C'est équivalent à utiliser à la fois covered et uncovered.

Voici un exemple de sortie de --prime-paths-source :

path 10 not covered:
BB  3:           8:  for (i = 0; i < 10; i++)
BB  3:           9:    total += i;
BB  4: (false)   8:  for (i = 0; i < 10; i++)
BB  5: (true)   11:  int v = total > 100 ? 1 : 2;
BB  6:          11:  int v = total > 100 ? 1 : 2;
BB  8: (false)  13:  if (total != 45 && v == 1)
BB 11:          16:    printf ("Success\n");
BB 12:          17:  return 0;

La première colonne (BB) est la séquence des blocs de base (voir -w). La colonne du milieu (true/false) est la décision pour cette ligne. La troisième colonne est le numéro de ligne. La quatrième colonne est la ligne elle-même. Ces lignes doivent être exécutées dans cet ordre pour couvrir le chemin 10.

-d
--display-progress
Affiche la progression sur la sortie standard.
-f
--function-summaries
Affiche les résumés pour chaque fonction en plus du résumé au niveau du fichier.
--include regex
Inclut les fonctions correspondant à regex. Cette option fait que gcov ne rapporte que sur les fonctions qui correspondent à l'expression régulière étendue regex. Ce drapeau peut être combiné avec --exclude. Si une fonction correspond à la fois aux inclusions et aux exclusions, la dernière inclusion/exclusion s'applique. Par défaut gcov rapporte sur toutes les fonctions, mais si un --include est utilisé, seules les fonctions correspondant à l'inclusion seront rapportées.
--exclude regex
Exclut les fonctions correspondant à regex. Cette option fait que gcov ne rapporte pas sur les fonctions qui correspondent à l'expression régulière étendue regex. Ce drapeau peut être combiné avec --include. Si une fonction correspond à la fois aux inclusions et aux exclusions, la dernière inclusion/exclusion s'applique. Par défaut gcov rapporte sur toutes les fonctions, et si un --exclude est utilisé, les fonctions qui y correspondent seront omises.
-h
--help
Affiche l'aide sur l'utilisation de gcov (sur la sortie standard) et termine sans effectuer aucun traitement supplémentaire.
-j
--json-format
Sort le fichier gcov dans un format intermédiaire JSON facile à analyser qui ne nécessite pas le code source pour sa génération. Le fichier JSON est compressé avec l'algorithme de compression gzip et les fichiers ont l'extension .gcov.json.gz .

La structure du JSON est la suivante :

{
  "current_working_directory": "foo/bar",
  "data_file": "a.out",
  "format_version": "2",
  "gcc_version": "11.1.1 20210510"
  "files": ["$file"]
}

Les champs de l'élément racine ont la sémantique suivante :

  • current_working_directory: répertoire de travail dans lequel l'unité de compilation a été compilée
  • data_file: nom du fichier de données (GCDA)
  • format_version: version sémantique du format

    Changements dans la version 2:

*
calls: des informations sur les appels de fonctions sont ajoutées
*
gcc_version: version du compilateur GCC

Chaque file a la forme suivante :

{
  "file": "a.c",
  "functions": ["$function"],
  "lines": ["$line"]
}

Les champs de l'élément file ont la sémantique suivante :

*
file_name: nom du fichier source

Chaque function a la forme suivante :

{
  "blocks": 2,
  "blocks_executed": 2,
  "demangled_name": "foo",
  "end_column": 1,
  "end_line": 4,
  "execution_count": 1,
  "name": "foo",
  "start_column": 5,
  "start_line": 1
}

Les champs de l'élément function ont la sémantique suivante :

  • blocks: nombre de blocs présents dans la fonction
  • blocks_executed: nombre de blocs exécutés de la fonction
  • demangled_name: nom dé-manglé de la fonction
  • end_column: colonne dans le fichier source où la fonction se termine
  • end_line: ligne dans le fichier source où la fonction se termine
  • execution_count: nombre d'exécutions de la fonction
  • name: nom de la fonction
  • start_column: colonne dans le fichier source où la fonction commence
  • start_line: ligne dans le fichier source où la fonction commence

Notez que les numéros de ligne et de colonne commencent à 1. Dans l'implémentation actuelle, start_line et start_column n'incluent pas les paramètres de gabarit ni le type de retour initial, mais cela sera probablement corrigé à l'avenir.

Chaque line a la forme suivante :

{
  "block_ids": ["$block_id"],
  "branches": ["$branch"],
  "calls": ["$call"],
  "count": 2,
  "conditions": ["$condition"],
  "line_number": 15,
  "unexecuted_block": false,
  "function_name": "foo",
}

Les branches et les appels ne sont présents qu'avec l'option -b . Les champs de l'élément line ont la sémantique suivante :

  • block_ids: identifiants des blocs de base appartenant à la ligne
  • count: nombre d'exécutions de la ligne
  • line_number: numéro de ligne
  • unexecuted_block: drapeau indiquant si la ligne contient un bloc non exécuté (toutes les instructions de la ligne ne sont pas exécutées)
  • function_name: nom de la fonction à laquelle cette line appartient (pour une ligne avec des instructions inlinées, peut ne pas être défini)

Chaque branch a la forme suivante :

{
  "count": 11,
  "destination_block_id": 17,
  "fallthrough": true,
  "source_block_id": 13,
  "throw": false
}

Les champs de l'élément branch ont la sémantique suivante :

  • count: nombre d'exécutions de la branche
  • fallthrough: vrai lorsque la branche est une branche de passage (fall through)
  • throw: vrai lorsque la branche est une branche exceptionnelle
  • isource_block_id: identifiant du bloc de base où cette branche se produit
  • destination_block_id: identifiant du bloc de base vers lequel cette branche saute

Chaque call a la forme suivante :

{
  "destination_block_id": 1,
  "returned": 11,
  "source_block_id": 13
}

Les champs de l'élément call ont la sémantique suivante :

  • returned: nombre de fois où un appel de fonction est retourné (le nombre d'appels est égal à line::count)
  • isource_block_id: identifiant du bloc de base où cet appel se produit
  • destination_block_id: identifiant du bloc de base où cet appel se poursuit après le retour

Chaque condition a la forme suivante :

{
  "count": 4,
  "covered": 2,
  "not_covered_false": [],
  "not_covered_true": [0, 1],
}

Les champs de l'élément condition ont la sémantique suivante :

  • count: nombre de résultats de conditions dans cette expression
  • covered: nombre de résultats de conditions couverts dans cette expression
  • not_covered_true: termes, par index, non vus comme vrais dans cette expression
  • not_covered_false: termes, par index, non vus comme faux dans cette expression
-H
--human-readable
Écrit les comptages dans un format lisible par l'humain (comme 24.6k).
-k
--use-colors
Utilise des couleurs pour les lignes de code ayant une couverture nulle. Nous utilisons la couleur rouge pour les lignes non exceptionnelles et le cyan pour les exceptionnelles. Les mêmes couleurs sont utilisées pour les blocs de base avec l'option -a .
-l
--long-file-names
Crée des noms de fichiers longs pour les fichiers source inclus. Par exemple, si le fichier d'en-tête x.h contient du code et a été inclus dans le fichier a.c, alors l'exécution de gcov sur le fichier a.c produira un fichier de sortie appelé a.c##x.h.gcov au lieu de x.h.gcov. Cela peut être utile si x.h est inclus dans plusieurs fichiers source et vous voulez voir les contributions individuelles. Si vous utilisez l'option -p , les noms de fichiers inclus et incluant seront des chemins complets.
-m
--demangled-names
Affiche les noms de fonctions dé-manglés dans la sortie. Par défaut, les noms de fonctions mangés sont affichés.
-M
--filter-on-demangled
Fait que --include et --exclude correspondent aux noms dé-manglés. Cela n'affecte que la correspondance et n'implique pas --demangled-names, mais cela peut être combiné en toute sécurité avec celui-ci.
-n
--no-output
Ne crée pas le fichier de sortie gcov .
-o directory|file
--object-directory directory
--object-file file
Spécifie soit le répertoire contenant les fichiers de données gcov, soit le chemin de l'objet. Les fichiers de données .gcnoet .gcda sont recherchés en utilisant cette option. Si un répertoire est spécifié, les fichiers de données se trouvent dans ce répertoire et sont nommés d'après le nom du fichier d'entrée, sans son extension. Si un fichier est spécifié ici, les fichiers de données sont nommés d'après ce fichier, sans son extension.
-p
--preserve-paths
Préserve les informations complètes des chemins dans les noms des fichiers .gcov générés. Sans cette option, seul le composant nom de fichier est utilisé. Avec cette option, tous les répertoires sont utilisés, avec les caractères / traduits en caractères #, les composants de répertoire . supprimés et les composants .. non supprimables renommés en ^. Ceci est utile si les fichiers source se trouvent dans plusieurs répertoires différents.
-q
--use-hot-colors
Émet une sortie colorée de type perf pour les lignes chaudes. La légende de l'échelle de couleurs est imprimée tout au début du fichier de sortie.
-r
--relative-only
N'émet des informations que sur les fichiers source avec un chemin relatif (après élision du préfixe source). Les chemins absolus sont généralement des fichiers d'en-tête système et la couverture de toute fonction inline en eux n'est normalement pas intéressante.
-s directory
--source-prefix directory
Un préfixe pour les noms de fichiers source à supprimer lors de la génération des fichiers de sortie de couverture. Cette option est utile lors de la compilation dans un répertoire séparé, et le chemin d'accès au répertoire source n'est pas souhaité lors de la détermination des noms de fichiers de sortie. Notez que cette détection de préfixe est appliquée avant de déterminer si le fichier source est absolu.
-t
--stdout
Sortie vers la sortie standard au lieu des fichiers de sortie.
-u
--unconditional-branches
Lorsque les probabilités de branche sont données, inclure celles des branches inconditionnelles. Les branches inconditionnelles ne sont normalement pas intéressantes.
-v
--version
Affiche le numéro de version de gcov (sur la sortie standard) et quitte sans effectuer aucun autre traitement.
-w
--verbose
Affiche des informations détaillées relatives aux blocs de base et aux arcs.
-x
--hash-filenames
Lors de l'utilisation de --preserve-paths, gcov utilise le chemin complet des fichiers source pour créer un nom de fichier de sortie. Cela peut conduire à des noms de fichiers longs qui peuvent dépasser les limites du système de fichiers. Cette option crée des noms de la forme source-file##md5.gcov, où le composant source-file est la partie finale du nom de fichier et le composant md5 est calculé à partir du nom complet qui aurait été utilisé autrement. L'option est une alternative à --preserve-paths sur les systèmes qui ont une limite de système de fichiers.

gcov doit être exécuté avec le répertoire courant identique à celui dans lequel vous avez appelé le compilateur. Sinon, il ne pourra pas localiser les fichiers source. gcov produit des fichiers appelés mangledname.gcov dans le répertoire courant. Ceux-ci contiennent les informations de couverture du fichier source auquel ils correspondent. Un fichier .gcov est produit pour chaque fichier source (ou en-tête) contenant du code, qui a été compilé pour produire les fichiers de données. Le composant mangledname du nom du fichier de sortie est généralement simplement le nom du fichier source, mais peut être quelque chose de plus compliqué si les options -l ou -p sont données. Référez-vous à ces options pour plus de détails.

Si vous invoquez gcov avec plusieurs fichiers d'entrée, les contributions de chaque fichier d'entrée sont additionnées. Typiquement, vous l'invoqueriez avec la même liste de fichiers que pour la liaison finale de votre exécutable.

Les fichiers .gcov contiennent des champs séparés par des : ainsi que le code source du programme. Le format est

<execution_count>:<line_number>:<source line text>

Des informations supplémentaires sur les blocs peuvent succéder à chaque ligne, lorsque demandées par une option de ligne de commande. L' execution_count est - pour les lignes ne contenant aucun code. Les lignes non exécutées sont marquées ##### ou =====, selon qu'elles sont accessibles par des chemins non exceptionnels ou seulement par des chemins exceptionnels tels que les gestionnaires d'exceptions C++, respectivement. Avec l'option -a, les blocs non exécutés sont marqués $$$$$ ou %%%%%, selon qu'un bloc de base est accessible via des chemins non exceptionnels ou exceptionnels. Les blocs de base exécutés ayant une instruction avec un execution_count de zéro se terminent par le caractère * et sont colorés en magenta avec l'option -k. Cette fonctionnalité n'est pas prise en charge en Ada.

Notez que GCC peut complètement supprimer les corps des fonctions qui ne sont pas nécessaires -- par exemple si elles sont inlinées partout. De telles fonctions sont marquées avec -, ce qui peut être déroutant. Utilisez les options -fkeep-inline-functions et -fkeep-static-functions pour conserver ces fonctions et permettre à gcov de montrer correctement leur execution_count.

Certaines lignes d'information au début ont un line_number de zéro. Ces lignes d'en-tête sont de la forme

-:0:<tag>:<value>

L'ordre et le nombre de ces lignes d'en-tête seront augmentés au fur et à mesure que le développement de gcov progresse --- ne comptez pas sur leur maintien inchangé. Utilisez tag pour localiser une ligne d'en-tête particulière.

Les informations supplémentaires sur les blocs sont de la forme

<tag> <information>

L'information est lisible par l'homme, mais conçue pour être suffisamment simple pour être analysée par machine également.

Lors de l'impression des pourcentages, 0% et 100% ne sont imprimés que lorsque les valeurs sont exactement 0% et 100% respectivement. Les autres valeurs qui seraient conventionnellement arrondies à 0% ou 100% sont au lieu de cela imprimées comme la valeur non limite la plus proche.

Lorsque vous utilisez gcov, vous devez d'abord compiler votre programme avec une option spéciale de GCC --coverage. Cela indique au compilateur de générer les informations supplémentaires nécessaires à gcov (principalement un graphe de flux du programme) et inclut également du code supplémentaire dans les fichiers objets pour générer les informations de profilage supplémentaires nécessaires à gcov. Ces fichiers supplémentaires sont placés dans le répertoire où se trouve le fichier objet.

L'exécution du programme entraînera la génération d'une sortie de profilage. Pour chaque fichier source compilé avec -fprofile-arcs, un fichier .gcda accompagnant sera placé dans le répertoire du fichier objet.

L'exécution de gcov avec les noms de fichiers source de votre programme comme arguments produira maintenant une liste du code ainsi que la fréquence d'exécution pour chaque ligne. Par exemple, si votre programme s'appelle tmp.cpp, voici ce que vous voyez lorsque vous utilisez la fonctionnalité de base de gcov :

$ g++ --coverage tmp.cpp -c
$ g++ --coverage tmp.o
$ a.out
$ gcov tmp.cpp -m
File 'tmp.cpp'
Lines executed:92.86% of 14
Creating 'tmp.cpp.gcov'

Les comptes d'exécution sont cumulatifs. Si le programme d'exemple était exécuté à nouveau sans supprimer le fichier .gcda [[66]], le compte pour le nombre de fois où chaque ligne du source a été exécuté serait ajouté aux résultats de la ou des exécutions précédentes. C'est potentiellement utile de plusieurs manières. Par exemple, cela pourrait être utiliséo accumuler des données au cours d'un certain nombre d'exécutions du programme dans le cadre d'une suite de vérification de tests, ou pour fournir des informations à long terme plus précises sur un grand nombre d'exécutions du programme.

Les données dans les fichiers .gcda sont enregistrées juste avant la sortie du programme. Pour chaque fichier source compilé avec -fprofile-arcs, le code de profilage tente d'abord de lire un fichier .gcda existant ; si le fichier ne correspond pas à l'exécutable (nombre différent de comptages de blocs de base), il ignorera le contenu du fichier. Il ajoute ensuite les nouveaux comptages d'exécution et écrit enfin les données dans le fichier.

Utilisation de gcov avec l'optimisation de GCC

Si vous prévoyez d'utiliser gcov pour aider à optimiser votre code, vous devez d'abord compiler votre programme avec une option GCC spéciale --coverage. En dehors de cela, vous pouvez utiliser n'importe quelles autres options GCC ; mais si vous voulez prouver que chaque ligne de votre programme a été exécutée, vous ne devriez pas compiler avec l'optimisation en même temps. Sur certaines machines, l'optimiseur peut éliminer certaines lignes de code simples en les combinant avec d'autres lignes. Par exemple, du code comme ceci :

if (a != b)
  c = 1;
else
  c = 0;

peut être compilé en une seule instruction sur certaines machines. Dans ce cas, il n'y a aucun moyen pour gcov de calculer des comptages d'exécution séparés pour chaque ligne car il n'y a pas de code séparé pour chaque ligne. Par conséquent, la sortie de gcov ressemble à ceci si vous avez compilé le programme avec l'optimisation :

100:   12:if (a != b)
100:   13:  c = 1;
100:   14:else
100:   15:  c = 0;

La sortie montre que ce bloc de code, combiné par l'optimisation, s'est exécuté 100 fois. En un sens, ce résultat est correct, car il n'y avait qu'une seule instruction représentant ces quatre lignes. Cependant, la sortie n'indique pas combien de fois le résultat était 0 et combien de fois le résultat était 1.

Les fonctions pouvant être inlinées peuvent créer des comptages de lignes inattendus. Les comptages de lignes sont affichés pour le code source de la fonction pouvant être inlinée, mais ce qui est affiché dépend de l'endroit où la fonction est inlinée, ou si elle n'est pas inlinée du tout.

Si la fonction n'est pas inlinée, le compilateur doit émettre une copie hors ligne de la fonction, dans n'importe quel fichier objet qui en a besoin. Si fileA.o et fileB.o contiennent tous deux des corps hors ligne d'une fonction pouvant être inlinée particulière, ils contiendront aussi tous deux des comptages de couverture pour cette fonction. Lorsque fileA.o et fileB.o sont liés ensemble, l'éditeur de liens sélectionnera, sur de nombreux systèmes, l'un de ces corps hors ligne pour tous les appels à cette fonction, et supprimera ou ignorera l'autre. Malheureusement, il ne supprimera pas les compteurs de couverture du corps de fonction inutilisé. Par conséquent, lorsqu'il est instrumenté, tous les usages de cette fonction sauf un montreront des comptages à zéro.

Si la fonction est inlinée à plusieurs endroits, la structure de blocs à chaque emplacement pourrait ne pas être la même. Par exemple, une condition pourrait maintenant être calculable à la compilation dans certaines instances. Comme la couverture de tous les usages de la fonction inlinée sera affichée pour les mêmes lignes de source, les comptages de lignes eux-mêmes pourraient sembler incohérents.

Les applications à longue durée d'exécution peuvent utiliser les fonctionnalités "__gcov_reset" et "__gcov_dump" pour restreindre la collecte de profil à la région du programme d'intérêt. Appeler "__gcov_reset(void)" mettra à zéro tous les compteurs de profil à l'exécution, et appeler "__gcov_dump(void)" provoquera le vidage des informations de profil collectées à ce moment-là vers les fichiers de sortie .gcda . Les applications instrumentées utilisent un destructeur statique avec la priorité 99 pour invoquer la fonction "__gcov_dump" . Ainsi "__gcov_dump" est exécuté après tous les destructeurs statiques définis par l'utilisateur, ainsi que les gestionnaires enregistrés avec "atexit".

Si un exécutable charge un objet partagé dynamique via la fonctionnalité dlopen, -Wl,--dynamic-list-data est nécessaire pour vider toutes les données de profil.

La bibliothèque d'exécution de profilage signale diverses erreurs liées à la manipulation du profil et à l'enregistrement du profil. Les erreurs sont imprimées dans la sortie d'erreur standard ou dans le fichier GCOV_ERROR_FILE , si la variable d'environnement est utilisée. Afin de se terminer immédiatement après qu'une erreur se produise, définissez la variable d'environnement GCOV_EXIT_AT_ERROR . Cela peut aider les utilisateurs à trouver les conflits de profil qui conduisent à un profil trompeur.
