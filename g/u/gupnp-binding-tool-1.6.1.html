NOM

gupnp-binding-tool-1.6 - crée des wrappers C pratiques pour les services UPnP

SYNTAXE

gupnp-binding-tool-1.6 [--prefix {PREFIX}] [--mode {client|server}] {fichier SCPD}

DESCRIPTION

gupnp-binding-tool-1.6 prend un fichier SCPD et génère des fonctions C pratiques qui appellent les fonctions GUPnP réelles. Les liaisons côté client peuvent être considérées comme une version spécifique au service de l'API GUPnPServiceProxy et les liaisons côté serveur sont les mêmes pour GUPnPService.

Ces fonctions générées sont moins verbeuses et aussi plus sûres car les paramètres des appels de fonction sont correctement typés. Les noms d'action, de variable et de requête sont plus faciles à obtenir correctement avec des liaisons (ou du moins les erreurs seront des erreurs de compilation au lieu d'erreurs d'exécution), et sont également disponibles dans l'autocomplétion de l'éditeur.

LIAISONS CÔTÉ CLIENT

Par exemple, cette action :

<action>
  <name>DeletePortMapping</name>
  <argumentList>
    <argument>
      <name>NewRemoteHost</name>
      <direction>in</direction>
      <relatedStateVariable>RemoteHost</relatedStateVariable>
    </argument>
    <argument>
      <name>NewExternalPort</name>
      <direction>in</direction>
      <relatedStateVariable>ExternalPort</relatedStateVariable>
    </argument>
    <argument>
      <name>NewProtocol</name>
      <direction>in</direction>
      <relatedStateVariable>PortMappingProtocol</relatedStateVariable>
    </argument>
  </argumentList>
</action>

Générera la fonction côté client synchrone suivante (point de contrôle) :

static inline gboolean
igd_delete_port_mapping (GUPnPServiceProxy *proxy,
                         const gchar *in_new_remote_host,
                         const guint in_new_external_port,
                         const gchar *in_new_protocol,
                         GError **error);

Comme on peut le voir, les arguments ont les types corrects et sont précédés de la direction de l'argument.

gupnp-binding-tool-1.6 génère des wrappers synchrones et asynchrones. L'exemple igd_delete_port_mapping ci-dessus est la forme synchrone, la forme asynchrone est la suivante :

typedef void (*igd_delete_port_mapping_reply) (GUPnPServiceProxy *proxy,
                                               GError *error,
                                               gpointer userdata);
static inline GUPnPServiceProxyAction *
igd_delete_port_mapping_async (GUPnPServiceProxy *proxy,
                               const gchar *in_new_remote_host,
                               const guint in_new_external_port,
                               const gchar *in_new_protocol,
                               igd_delete_port_mapping_reply callback,
                               gpointer userdata);

La forme asynchrone (implémentée à l'aide de gupnp_service_proxy_begin_action() et gupnp_service_proxy_end_action()) retournera sans bloquer et appellera plus tard le rappel à partir de la boucle principale lorsque la réponse sera reçue.

L'outil crée également des liaisons pour les notifications de variables d'état. Cette définition de variable d'état :

<stateVariable sendEvents="yes">
  <name>ExternalIPAddress</name>
  <dataType>string</dataType>
</stateVariable>

Créera cette liaison client qui peut être utilisée pour recevoir des notifications sur les changements de "ExternalIPAddress" :

typedef void
(*igd_external_ip_address_changed_callback) (GUPnPServiceProxy *proxy,
                                             const gchar *external_ip_address,
                                             gpointer userdata);
static inline gboolean
igd_external_ip_address_add_notify (GUPnPServiceProxy *proxy,
                                    igd_external_ip_address_changed_callback callback,
                                    gpointer userdata);

Tous les exemples ont été produits avec gupnp-binding-tool-1.6 --prefix igd --mode client WANIPConnection.xml.

LIAISONS CÔTÉ SERVEUR

Les liaisons serveur correspondantes pour la même action UPnP (DeletePortMapping) ressemblent à ceci :

void
igd_delete_port_mapping_action_get (GUPnPServiceAction *action,
                                    gchar **in_new_remote_host,
                                    guint *in_new_external_port,
                                    gchar **in_new_protocol);
gulong
igd_delete_port_mapping_action_connect (GUPnPService *service,
                                        GCallback callback,
                                        gpointer userdata);

La fonction générée *_action_connect() peut être utilisée pour connecter le gestionnaire d'actions. Les fonctions *_action_get() et *_action_set() peuvent ensuite être utilisées à l'intérieur du gestionnaire d'actions pour obtenir/définir les variables d'action. Si les variables notifiées sont modifiées, *_variable_notify() doit être utilisé pour envoyer les notifications (voir ci-dessous).

typedef gchar *(*igd_external_ip_address_query_callback) (GUPnPService *service,
                                                          gpointer userdata);
gulong
igd_external_ip_address_query_connect (GUPnPService *service,
                                       igd_external_ip_address_query_callback callback,
                                       gpointer userdata);
void
igd_external_ip_address_variable_notify (GUPnPService *service,
                                         const gchar *external_ip_address);

La fonction *_query_connect() peut être utilisée pour connecter le gestionnaire de requêtes spécifique au service. La valeur de retour du gestionnaire est la valeur de la variable d'état retournée.

Tous les exemples ont été produits avec gupnp-binding-tool-1.6 --prefix igd --mode server WANIPConnection.xml.
