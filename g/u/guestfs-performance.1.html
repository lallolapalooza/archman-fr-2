DESCRIPTIO

N

Cette page documente comment obtenir les meilleures performances de libguestfs, en particulier lorsque vous prévoyez d'utiliser libguestfs pour manipuler des milliers de machines virtuelles ou d'images de

disque.

Trois domaines principaux sont couverts. Libguestfs exécute un appliance (une petite distribution Linux) à l'intérieur de qemu/K

VM. Les deux premiers domaines sont : minimiser le temps nécessaire au démarrage de cet appliance, et le nombre de fois où l'
appliance doit être démarré. Le troisième domaine est de réduire le temps nécessaire à l'inspection des machines virtuelles.

MESURES DE

RÉFÉRENCE

Avant d'apporter des modifications à votre utilisation de libguestfs, effectuez des mesures de

référence.

Référence : Démarrage de

l'appliance

Sur une machine non sollicitée, mesurez le temps nécessaire au démarrage de l'appliance

: 
time guestfish -a /dev/null
run

Exécutez cette commande plusieurs fois de suite et ignorez les premières exécutions, afin de mesurer un cas typique de « cache chaud »

.

Note pour les développeurs : il existe un programme appelé boot-benchmark dans https://github.com/libguestfs/libguestfs-analysis-tools qui fait la même chose, mais effectue plusieurs exécutions et affiche la moyenne et l'écart

type.

Explicatio

n

La commande guestfish ci-dessus démarre l'appliance libguestfs sur un disque nul, puis l'arrête immédiatement. La première fois que vous exécutez la commande, elle créera un appliance et le mettra en cache (généralement sous /var/tmp/.guestfs-*). Les exécutions suivantes devraient réutiliser l'appliance en

cache.

Résultats

attendus

Vous devriez obtenir des temps inférieurs à 6 secondes. Si les temps que

vous observez sur une machine non sollicitée sont supérieurs à cela, c
onsultez la section « DÉPANNAGE DES MAUVAISES PERFORMANCES » ci-dessous.

Référence : Inspection d'un

invité

Pour ce test, vous aurez besoin d'une machine non sollicitée et d'au moins un invité ou une image de disque réelle. Si vous prévoyez d'utiliser libguestfs uniquement avec des invités X (par ex. X = Windows), l'utilisation d'un invité X ici serait la plus appropriée. Si vous prévoyez d'exécuter libguestfs sur un mélange d'invités, utilisez un mélange d'invités pour les tests

ici.

Mesurez le temps nécessaire pour effectuer l'inspection et monter les disques de l'invité. Utilisez la première commande si vous allez utiliser des images de disque, et la seconde si vous allez utiliser

libvirt. 
time guestfish --ro -a disk.img -i exit
time guestfish --ro -d GuestName -i
exit

Exécutez la commande plusieurs fois de suite et ignorez les premières exécutions, afin de mesurer un cas typique de « cache chaud »

.

Explicatio

n

Cette commande démarre l'appliance libguestfs sur l'image de disque ou l'invité libvirt nommé, effectue l'inspection libguestfs sur celui-ci (voir « INSPECTION » dans guestfs(3)), monte les disques de l'invité, puis jette tous ces résultats et

s'arrête.

La première fois que vous exécutez la commande, elle créera un appliance et le mettra en cache (généralement sous /var/tmp/.guestfs-*). Les exécutions suivantes devraient réutiliser l'appliance en

cache.

Résultats

attendus

Vous devriez obtenir des temps ≤ 5 secondes supérieurs à ceux

mesurés dans le premier test de référence ci-dessus. (Par ex
emple, si le premier test de référence s'est exécuté en 5 se
condes, alors ce test devrait s'exécuter en ≤ 10 secondes).

COMPRENDRE L'APPLIANCE ET QUAND ELLE EST CONSTRUITE/MISE EN

CACHE

La première fois que vous utilisez libguestfs, il construira et mettra en cache un appliance. C'est généralement dans /var/tmp/.guestfs-*, sauf si vous avez défini $TMPDIR ou $LIBGUESTFS_CACHEDIR, auquel cas il sera sous ce répertoire

temporaire.

Pour plus d'informations sur la construction de l'appliance, voir « SUPERMIN APPLIANCES » dans supermin

(1).

Chaque fois que libguestfs s'exécute, il vérifie qu'aucun fichier hôte utilisé par l'appliance n'a changé. Si c'est le cas, l'appliance est reconstruit. Cela se produit généralement lorsqu'un paquet est installé ou mis à jour sur l'hôte (par ex. en utilisant des programmes comme « yum » ou « apt-get »). La raison de la reconstruction de l'appliance est la sécurité : le nouveau programme qui a été installé peut contenir une correction de sécurité, et nous voulons donc inclure automatiquement le programme corrigé dans

l'appliance.

Voici les implications sur les performances

:
  • Le processus de construction (ou reconstruction) de l'appliance en cache est lent, et vous pouvez éviter cela en utilisant un appliance fixe (voir ci-dessous)
    • .
  • Si vous n'utilisez pas un appliance fixe, sachez que la mise à jour des logiciels sur l'hôte entraînera une reconstruction unique de
    • l'appliance.
  • /var/tmp (ou $TMPDIR, $LIBGUESTFS_CACHEDIR) devrait être sur un disq
    • ue rapide et dispo
ser de suffisamment d'e
space pour l'appliance.

UTILISER UN APPLIANCE

FIXE

Pour contrôler complètement le moment de la construction de l'appliance, vous pouvez construire un appliance fixe. Cet appliance devrait être stocké sur un disque local

rapide.

Pour construire l'appliance, exécutez la commande

: 
libguestfs-make-fixed-appliance
<directory>

en remplaçant « <directory> » par le nom d'un répertoire où l'appliance sera stocké (normalement vous nommeriez un sous-répertoire, par exemple : /usr/local/lib/guestfs/appliance ou /dev/shm/appl

iance).

Définissez ensuite $LIBGUESTFS_PATH (et assurez-vous que cette variable d'environnement est définie dans votre programme libguestfs), ou modifiez votre programme pour qu'il appelle « guestfs_set_path ». Par exemple

: 
export LIBGUESTFS_PATH=/usr/local/lib/guestfs/applianc
e

Vous pouvez maintenant exécuter les programmes libguestfs, les outils virt, guestfish, etc. normalement. Les programmes utiliseront votre appliance fixe et ne construiront, ne reconstruiront ni ne mettront jamais en cache leur propre

appliance.

(Pour des informations détaillées sur ce sujet, voir : libguestfs-make-fixed-appliance(1))

.

Performance de l'appliance

fixe

Dans nos tests, nous n'avons pas constaté que l'utilisation d'un appliance fixe apportait un avantage de performance mesurable, même lorsque l'appliance était situé en mémoire (c'est-à-dire sur /dev/shm). Cependant, deux points doivent être considérés

:
1
.
L'utilisation d'un appliance fixe empêche libguestfs de reconstruire l'appliance, ce qui signifie que libguestfs aura des temps de démarrage plus
prévisibles.
2
.
L'appliance est chargé à la demande. Un test simple comme : 
time guestfish -a /dev/null
run

ne charge pas grand-chose de l'appliance. Un v

rai programme libguestfs utilisant des
appels d'API complexes chargerait à la demande
beaucoup plus de l'appliance. Pouvoir
stocker l'appliance dans un emplacemen
t spécifié rend la performance plus prévisible.

RÉDUIRE LE NOMBRE DE FOIS OÙ L'APPLIANCE EST

LANCÉ

De loin la méthode la plus efficace, bien que pas toujours la plus simple, pour obtenir de bonnes performances est de s'assurer que l'appliance est lancé le minimum de fois possible. Cela impliquera probablement de modifier votre application

libguestfs.

Essayez d'appeler « guestfs_launch » au plus une fois par machine virtuelle ou image de disque

cible.

Au lieu d'utiliser une instance séparée de guestfish(1) pour effectuer une série de modifications sur le même invité, utilisez une seule instance de guestfish et/ou utilisez l'option --listen de

guestfish.

Envisagez d'écrire votre programme en tant que démon qui maintient un invité ouvert tout en effectuant une série de modifications. Ou regroupez toutes les opérations que vous voulez effectuer avant d'ouvrir

l'invité.

Vous pouvez également essayer d'ajouter des disques provenant de plusieurs invités à une seule appliance. Avant d'essayer cela, notez les points suivants

:
1
.
Ajouter plusieurs invités à une seule appliance constitue un problème de sécurité car cela peut permettre à un invité de perturber les disques d'un autre invité. Ne le faites que si vous faites confiance à tous les invités, ou si vous pouvez regrouper les invités par niveau de
confiance.
2
.
Il existe une limite stricte au nombre de disques que vous pouvez ajouter à une seule appliance. Appelez "guestfs_max_disks" dans guestfs(3) pour obtenir cette limite. Pour plus d'informations, voir "LIMITS" dans guestfs
(3).
3
.
Utiliser libguestfs de cette manière est compliqué. Les disques peuvent présenter des interactions inattendues : par exemple, si deux invités utilisent le même UUID pour un système de fichiers (parce qu'ils ont été clonés), ou s'ils ont des groupes de volumes avec le même nom (mais voir "guestfs_lvm_
set_fil
ter").

virt-df(1) ajoute plusieurs disques par défaut, le code sou

rce de ce programme serai
t donc un bon point de départ.

RACCOURCIR LE TEMPS D'INSPECTION DES

VM

Le conseil principal est évident : N'effectuez pas l'inspection (qui est coûteuse) sauf si vous avez besoin des

résultats.

Si vous avez déjà effectué l'inspection de l'invité, il peut être sûr de mettre en cache et de réutiliser les résultats de la dernière

fois.

Certains disques n'ont pas besoin d'être inspectés du tout : par exemple, si vous créez une image de disque, ou si l'image de disque n'est pas une VM, ou si l'image de disque a une disposition

connue.

Même lorsque l'inspection de base ("guestfs_inspect_os") est requise, les opérations d'inspection auxiliaires peuvent être évitées

:
  • Monter les disques n'est nécessaire que pour obtenir d'autres informations sur le système de
    • fichiers.
  • Lister les applications ("guestfs_inspect_list_applications") est une opération coûteuse sur Linux, mais presque gratuite sur
    • Windows.
  • Générer une icône d'invité ("guestfs_inspect_get_icon") est pe

Le script Perl simple ci-dessous a été utilisé pour collecter les données du graphique ci-dessus, mais il existe beaucoup plus d'informations sur ce sujet, y compris des scripts de test et des graphiques plus avancés, disponibles dans les publications de blog suivantes

:

http://rwmj.wordpress.com/2013/02/25/multiple-libguestfs-appliances-in-parallel-part-1/ http://rwmj.wordpress.com/2013/02/25/multiple-libguestfs-appliances-in-parallel-part-2/ http://rwmj.wordpress.com/2013/02/25/multiple-libguestfs-appliances-in-parallel-part-3/ http://rwmj.wordpress.com/2013/02/25/multiple-libguestfs-appliances-in-parallel-part-4

/ 
#!/usr/bin/env perl

use strict;
use threads;
use warnings;
use Sys::Guestfs;
use Time::HiRes qw(time);

sub test {
    my $g = Sys::Guestfs->new;
    $g->add_drive_ro ("/dev/null");
    $g->launch ();

    # Vous pourriez ajouter du travail pour libguestfs ici.

    $g->close ();
}

# Mettre tout en cache.
test (); test (); test ();

for my $nr_threads (1..20) {
    my $start_t = time ();
    my @threads;
    foreach (1..$nr_threads) {
        push @threads, threads->create (\&test)
    }
    foreach (@threads) {
        $_->join ();
        if (my $err = $_->error ()) {
            die "launch failed with $nr_threads threads: $err"
        }
    }
    my $end_t = time ();
    printf ("%d %.2f\n", $nr_threads, $end_t - $start_t);
}

DÉPANNAGE DES PERFORMANCES

MÉDIOCRES

S'assurer que la virtualisation matérielle est

disponible

Utilisez /proc/cpuinfo pour vous assurer que la virtualisation matérielle est disponible. Notez que vous devrez peut-être l'activer dans votre

BIOS.

La virtualisation matérielle n'est généralement pas disponible à l'intérieur des VM, et libguestfs s'exécutera lente

ment à l'intérieur d'une autre machine virtuelle quoi que vous fassiez. La virtualisation imbriquée ne fonctionne pas
bien selon notre expérience, et n'est certainement pas un substitut à l'exécution de libguestfs sur du matériel nu.

S'assurer que KVM est

disponible

Assurez-vous que KVM est activé et disponible pour l'utilisateur qui exécutera libguestfs. Il devrait être sûr de définir les permissions 0666 sur /dev/kvm et la plupart des d

istributions le
font maintenant.

Processeurs à

éviter

Évitez les processeurs qui n'ont pas de virtualisation ma

térielle, et certains processeurs qui sont simplement
très lents (AMD Geode en étant un excellent exemple).

Xen

dom0

Dans Xen, dom0 est une machine virt

uelle, et donc la virtualisation m
atérielle n'est pas disponible.

Utiliser libguestfs ≥ 1.34 et qemu ≥ 2.

7

Pendant le cycle de développement de libguestfs 1.33, nous avons passé une grande quantité de temps à nous c

oncentrer sur les performances de démarrage, et avons ajouté des correctifs à libguestfs, qemu et Linux qui
dans certains cas peuvent réduire les temps de démarrage à bien moins d'une seconde. Vous pourriez donc obte
nir de bien meilleures performances en passant aux versions de libguestfs ou qemu mentionnées dans le titre.

Débogage détaillé avec

gdb

Vous pouvez vous attacher au BIOS/noyau de l'appliance avec gdb. Si vous savez ce que vous faites, cela peut être un moyen utile de diagnostiquer les régressions de

démarrage.

Premièrement, vous devez modifier qemu pour qu'il s'exécute avec le "-S&quot; et "-s". Ces options font que qemu se met en pause au démarrage et permettent d'y attacher un débogueur. Lisez qemu(1) pour plus d'informations. Libguestfs invoque qemu plusieurs fois (pour analyser l'aide, etc.) et vous ne voulez que la dernière invocation de qemu utiliser ces options, utilisez donc un script wrapper pour qemu comme ceci

: 
#!/bin/bash -

# Définissez ici le chemin vers le vrai binaire qemu.
qemu=/usr/bin/qemu-kvm

if [ "$1" != "-global" ]; then
    # Analyse de l'aide, etc.
    exec $qemu "$@"
else 
    # Vraie exécution de qemu.
    exec $qemu -S -s "$@"
fi

Exécutez maintenant guestfish ou un autre outil libguestfs avec le wrapper qemu (voir « QEMU WRAPPERS » dans guestfs(3) pour comprendre ce que cela fait)

: 
LIBGUESTFS_HV=/chemin/vers/qemu-wrapper guestfish -a /dev/null -v
run

Cela devrait se mettre en pause juste après le lancement de qemu. Dans une autre fenêtre, attachez-vous à qemu avec gdb

: 
$ gdb
(gdb) set architecture i8086
The target architecture is assumed to be i8086
(gdb) target remote :1234
Remote debugging using :1234
0x0000fff0 in ?? ()
(gdb)
cont

À ce stade, vous pouvez utiliser les techniques gdb habituelles, par exemple appuyer sur "^C" pour interrompre le démarrage et "bt" pour obtenir une trace de pile, définir des points d'arrêt, etc. Notez q

ue lorsque vous êtes passé le BIOS et ent
ré dans le noyau Linux, vous voudrez
changer l'architecture en 32 ou 64 bits.

PROGRAMMES

.
