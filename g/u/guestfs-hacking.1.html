NOM

guestfs-hacking - étendre et contribuer à libguestfs

DESCRIPTION

Cette page manuelle est destinée aux développeurs qui souhaitent étendre libguestfs lui-même.

LE CODE SOURCE

Le code source de libguestfs se trouve dans le dépôt github https://github.com/libguestfs/libguestfs

De grandes quantités de code généré dans libguestfs (RPC, liaisons, documentation) sont générés automatiquement. Cela signifie que de nombreux fichiers sources semblent manquer lors d'un simple checkout git. Vous devez exécuter le générateur ("./configure && make -C generator") afin de créer ces fichiers.

Libguestfs utilise un système de compilation basé sur autotools, les fichiers principaux étant configure.ac et Makefile.am. Voir « SYSTÈME DE COMPILATION ».

Le generator sous-répertoire contient le générateur, ainsi que les fichiers décrivant l'API. Le lib sous-répertoire contient le code source de la bibliothèque. Les appliance et daemon sous-répertoires contiennent respectivement le code source pour la construction de l'appliance et le code qui s'exécute dans l'appliance. Les autres répertoires sont décrits dans la section « SOUS-RÉPERTOIRES DU CODE SOURCE » ci-dessous.

En dehors du fait que tous les points d'entrée de l'API passent par du code généré, la bibliothèque est simple. (En fait, même le code généré est conçu pour être lisible, et devrait être lu comme du code ordinaire). Certaines actions s'exécutent entièrement dans la bibliothèque, et sont écrites sous forme de fonctions C dans des fichiers situés sous lib. D'autres sont transmises au démon où (après un marshalling RPC généré) elles apparaissent comme des fonctions C dans des fichiers situés sous daemon.

Pour compiler à partir des sources, lisez d'abord la page guestfs-building(1).

LE SYSTÈME DE COMPILATION

Libguestfs utilise le système de compilation GNU autotools (autoconf, automake, libtool).

Le ./configure script est généré à partir de configure.ac et m4/guestfs-*.m4. La plupart du script de configuration est répartie sur de nombreux fichiers de macros m4 par thème, par exemple m4/guestfs-daemon.m4 traite des dépendances du démon.

Le rôle du Makefile.am de premier niveau est principalement de lister les sous-répertoires ("SUBDIRS") dans l'ordre dans lequel ils doivent être compilés.

common-rules.mk est inclus dans chaque Makefile.am (premier niveau et sous-répertoires). subdir-rules.mk est inclus uniquement dans les fichiers Makefile.am des sous-répertoires.

Il y a de nombreuses cibles make. Utilisez cette commande pour les lister toutes :

make help

EXTENSION DE LIBGUESTFS

AJOUT D'UNE NOUVELLE API

Comme de grandes quantités de code générique dans libguestfs sont générées, cela facilite l'extension de l'API libguestfs.

Pour ajouter une nouvelle action d'API, il y a deux changements :

1.
Vous devez ajouter une description de l'appel (nom, paramètres, type de retour, tests, documentation) à generator/actions_*.ml et éventuellement à generator/proc_nr.ml.

Il y a deux types d'actions d'API, selon que l'appel passe au démon dans l'appliance, ou est entièrement pris en charge par la bibliothèque (voir « ARCHITECTURE » dans guestfs-internals(1)). « guestfs_sync » dans guestfs(3) est un exemple du premier cas, puisque la synchronisation est faite dans l'appliance. « guestfs_set_trace » dans guestfs(3) est un exemple du second, puisqu'un indicateur de trace est maintenu dans le handle et que tout le traçage est fait côté bibliothèque.

La plupart des nouvelles actions sont du premier type et sont ajoutées à la liste "daemon_functions" . Chaque fonction a un numéro de procédure unique utilisé dans le protocole RPC qui est attribué à cette action lorsque nous publions libguestfs et ne peut pas être réutilisé. Prenez le dernier numéro de procédure et incrémentez-le.

Pour les actions de bibliothèque uniquement du second type, ajoutez à la liste "non_daemon_functions" . Puisque ces fonctions sont prises en charge par la bibliothèque et ne transitent pas par le mécanisme RPC vers le démon, ces fonctions n'ont pas besoin d'un numéro de procédure, et donc le numéro de procédure est défini à -1.

2.
Implémentez l'action (en C) :

Pour les actions du démon, implémentez la fonction "do_<name>" dans le répertoire "daemon/" .

Pour les actions de la bibliothèque, implémentez la fonction "guestfs_impl_<name>" dans le répertoire "lib/" .

Dans les deux cas, utilisez une autre fonction comme exemple de ce qu'il faut faire.

3.
En alternative à l'étape 2 : Depuis libguestfs 1.38, les actions du démon peuvent être implémentées en OCaml. Vous devez définir l'indicateur "impl = OCaml ..." dans le générateur. Jetez un œil à daemon/file.ml pour un exemple.

Après avoir fait ces changements, utilisez "make" pour compiler.

Notez que vous n'avez pas besoin d'implémenter le RPC, les liaisons de langage, les pages de manuel ou quoi que ce soit d'autre. Tout est automatiquement généré à partir de la description OCaml.

Ajout de tests pour une API

Vous pouvez fournir zéro ou autant de tests que vous le souhaitez par appel d'API. Les tests peuvent être ajoutés comme partie de la description de l'API (generator/actions_*.ml), ou dans certains cas plus rares, vous voudrez peut-être déposer un script dans "tests/*/". Notez que l'ajout d'un script dans "tests/*/" est plus lent, donc si c'est possible, utilisez la première méthode.

Ce qui suit décrit l'environnement de test utilisé lorsque vous ajoutez un test d'API dans actions_*.ml.

L'environnement de test a 4 périphériques de bloc :

/dev/sda 2 Go
Périphérique de bloc général pour les tests.
/dev/sdb 2 Go
/dev/sdb1 est un système de fichiers ext2 utilisé pour tester les opérations d'écriture du système de fichiers.
/dev/sdc 10 Mo
Utilisé dans quelques tests où deux périphériques de bloc sont nécessaires.
/dev/sdd
ISO avec un contenu fixe (voir images/test.iso).

Pour pouvoir exécuter les tests dans un délai raisonnable, l' appliance libguestfs et les périphériques de bloc sont réutilisés entre les tests. N'essayez donc pas de tester « guestfs_kill_subprocess » dans guestfs(3) :-x

Chaque test commence par un scénario initial, sélectionné à l'aide de l'une des expressions "Init*" , décrites dans generator/types.ml. Celles-ci initialisent les disques mentionnés ci-dessus d'une manière particulière comme documenté dans types.ml. Vous ne devez supposer rien sur le contenu précédent des autres disques qui ne sont pas initialisés.

Vous pouvez ajouter une clause de prérequis à n'importe quel test individuel. C'est une vérification à l'exécution, qui, si elle échoue, fait sauter le test. Utile si le test une commande qui pourrait ne pas fonctionner sur toutes les variantes de libguestfs builds. Un test dont le prérequis est "Toujours" signifie qu'il doit s'exécuter sans condition.

De plus, les packagers peuvent sauter des tests individuels en définissant des variables d'environnement avant d'exécuter "make check".

SAUTER_TEST_<CMD>_<NUM>=1

par ex: "SAUTER_TEST_COMMAND_3=1" saute le test n°3 de "guestfs_command" dans guestfs(3).

ou:

SAUTER_TEST_<CMD>=1

par ex: "SAUTER_TEST_ZEROFREE=1" saute tous les tests "guestfs_zerofree" de guestfs(3).

Les packagers peuvent exécuter uniquement certains tests en définissant par exemple:

TEST_UNIQUEMENT="type_vfs zerofree"

Voir tests/c-api/tests.c pour plus de détails sur le fonctionnement de ces variables d'environnement.

Débogage des nouvelles API

Testez le bon fonctionnement des nouvelles actions avant de les soumettre.

Vous pouvez utiliser guestfish pour essayer de nouvelles commandes.

Le débogage du démon est problématique car il s'exécute dans un environnement minimal. Cependant, vous pouvez imprimer des messages dans le démon vers stderr, et ils apparaîtront si vous utilisez "guestfish -v".

AJOUTER UNE NOUVELLE LIAISON DE LANGAGE

Toutes les liaisons de langage doivent être générées par le générateur (voir le sous-répertoire generator).

Il n'y a pas encore de documentation à ce sujet. Nous vous suggérons de regarder une liaison existante, par exemple generator/ocaml.ml ou generator/perl.ml.

Ajout de tests pour les liaisons de langage

Les liaisons de langage devraient être accompagnées de tests. Auparavant, les tests des liaisons de langage étaient assez ad-hoc, mais nous avons essayé de formaliser l'ensemble des tests que chaque liaison de langage devrait utiliser.

Actuellement, seules les liaisons OCaml et Perl implémentent l'ensemble complet des tests, et les liaisons OCaml sont canoniques, vous devriez donc émuler ce que font les tests OCaml.

Voici le schéma de numérotation utilisé par les tests:

- 000+ tests de base:

  010  charger la bibliothèque
  020  créer
  030  options de création
  040  créer plusieurs handles
  050  tester la définition et l'obtention des propriétés de configuration
  060  fermeture explicite
  065  fermeture implicite (dans les langages à ramasse-miettes)
  070  arguments optionnels
  080  version
  090  valeurs de retour

- 100  lancement, création de partitions et de LVs et de systèmes de fichiers

- 400+ événements:

  410  événement de fermeture
  420  messages de journalisation
  430  messages de progression

- 800+ tests de régression (spécifiques au langage)

- 900+ tous les autres tests personnalisés pour le langage

Pour gagner du temps lors de l'exécution des tests, seuls les tests 100, 430, 800+ et 900+ devraient lancer le handle.

MISE EN FORME DU CODE

Notre code source C adhère généralement à quelques conventions de base de mise en forme du code. La base de code existante n'est pas totalement cohérente sur ce point, mais nous préférons que le code contribué soit formaté de manière similaire. En bref, utilisez des espaces et non des TABs pour l'indentation, utilisez 2 espaces pour chaque niveau d'indentation, et en dehors de cela, suivez le style K&R.

Si vous utilisez Emacs, ajoutez ceci à l'un de vos fichiers de démarrage (par ex., ~/.emacs) pour vous assurer d'avoir une indentation correcte:

;;; Dans libguestfs, indenter avec des espaces partout (pas de TABs).
;;; Exceptions : modes Makefile et ChangeLog.
(add-hook 'find-file-hook
    '(lambda () (if (and buffer-file-name
                         (string-match "/libguestfs\\>"
                             (buffer-file-name))
                         (not (string-equal mode-name "Change Log"))
                         (not (string-equal mode-name "Makefile")))
                    (setq indent-tabs-mode nil))))

;;; Lors de l'édition de sources C dans libguestfs, utiliser ce style.
(defun libguestfs-c-mode ()
  "Mode C avec des défauts ajustés pour une utilisation avec libguestfs."
  (interactive)
  (c-set-style "K&R")
  (setq c-indent-level 2)
  (setq c-basic-offset 2))
(add-hook 'c-mode-hook
          '(lambda () (if (string-match "/libguestfs\\>"
                              (buffer-file-name))
                          (libguestfs-c-mode))))

Exécute certains tests lents/de longue durée qui ne sont pas exécutés par défaut.

Pour marquer un test comme lent/de longue durée:

  • Ajoutez-le à la liste de "TESTS" dans le Makefile.am, comme un test normal.
  • Modifiez le test pour qu'il vérifie si la variable d'environnement "LENT=1" est définie, et si elle n'est pas définie, il saute (c'est-à-dire qu'il retourne avec le code de sortie 77). Si vous utilisez tests/functions.sh, vous pouvez appeler la fonction "test_lent" pour cela.
  • Ajoutez une variable "TESTS_LENTS" au Makefile.am listant les tests lents.
  • Ajoutez une règle au Makefile.am: 
    check-slow:
  $(MAKE) check TESTS="$(TESTS_LENTS)" LENT=1

  • Ajoutez-le à la liste de "TESTS" dans le Makefile.am, comme un test normal.
  • Modifiez le test pour qu'il vérifie si euid == 0, et si ce n'est pas le cas, il saute (c'est-à-dire qu'il retourne avec le code de sortie 77). Si vous utilisez tests/functions.sh, vous pouvez appeler la fonction "test_root" pour cela.

  • Ajoutez une règle au Makefile.am: 
    check-root:

"make check-release"

VALGRIND

Lorsque vous exécutez "make check-valgrind", il recherche tout Makefile.am dans l'arborescence qui a une cible "check-valgrind:" et l'exécute.

Écrire correctement le Makefile.am et les tests pour utiliser valgrind et travailler avec les tests parallèles d'automake est subtil.

Si vos tests sont exécutés via un script wrapper shell, alors dans le wrapper utilisez:

$VG virt-foo

et dans le Makefile.am utilisez:

check-valgrind:
    make VG="@VG@" check

Cependant, si vos binaires s'exécutent directement depuis la règle "TESTS", vous devez modifier le Makefile.am comme suit:

LOG_COMPILER = $(VG)

check-valgrind:
    make VG="@VG@" check

Dans les deux cas, vérifiez que le bon programme est testé en examinant attentivement les fichiers journaux tmp/valgrind*.

SUJETS DIVERS

COMMENT LES PROGRAMMES OCAML SONT COMPILÉS ET LIÉS

Cette section traite principalement de « comment faire fonctionner ensemble automake et ocamlopt », car les programmes OCaml eux-mêmes sont faciles à compiler.

Automake n'a pas de support natif pour les programmes OCaml, ni pour ocamlc ni pour ocamlopt. Ce que nous faisons à la place, c'est de traiter les programmes OCaml comme des programmes C qui contiennent ces « autres objets » ("DEPENDENCIES" dans le jargon d'automake) qui se trouvent être les objets OCaml. Cela fonctionne car les programmes OCaml ont généralement des fichiers C pour les liaisons natives, etc.

Ainsi, un programme typique est décrit par ses sources C uniquement :

virt_customize_SOURCES = ... crypt-c.c perl_edit-c.c

Pour les programmes qui n'ont pas de sources C explicites, nous créons un fichier dummy.c vide et nous le listons à la place :

virt_resize_SOURCES = dummy.c

Les objets OCaml qui contiennent la majeure partie du code sont répertoriés comme dépendances automake (d'autres dépendances peuvent également être répertoriées) :

virt_customize_DEPENDENCIES = ... customize_main.cmx

La seule autre chose spéciale que nous devons faire est de fournir une commande de liaison personnalisée. Ceci est nécessaire car automake ne rassemblera pas la commande ocamlopt, la liste des objets et les bibliothèques "-cclib" dans le bon ordre autrement.

virt_customize_LINK = \
    $(top_builddir)/ocaml-link.sh -cclib '-lutils' -- ...

Les règles réelles, que vous pouvez examiner dans customize/Makefile.am, sont un peu plus compliquées que cela car elles doivent gérer :

  • La compilation pour le code octet ou le code natif.
  • Les règles de modèle nécessaires pour compiler les sources OCaml en objets.

1.

En raison de ces problèmes, nous remplaçons /dev/null par un fichier temporaire de taille non nulle. Cela ne devrait faire aucune différence car les utilisateurs ne sont pas censés essayer d'accéder à un lecteur nul.

Fichier lib/proto.c

C'est le code utilisé pour envoyer et recevoir des messages RPC et (pour certains types de messages) pour effectuer des transferts de fichiers. Ce code est piloté par les actions générées (lib/actions-*.c). Il y a cinq cas à considérer :

1.
Une fonction non démon (par exemple, "guestfs_set_verbose" dans guestfs(3)). Il n'y a pas de RPC du tout, tout est géré à l'intérieur de la bibliothèque.
2.
Un RPC simple (par exemple, "guestfs_mount" dans guestfs(3)). Nous écrivons la requête, puis lisons la réponse. La séquence des appels est : 
guestfs_int_send
guestfs_int_recv
3.
Un RPC avec des paramètres "FileIn" (par exemple, "guestfs_upload" dans guestfs(3)). Nous écrivons la requête, puis écrivons le(s) fichier(s), puis lisons la réponse. La séquence des appels est : 
guestfs_int_send
guestfs_int_send_file  (plusieurs fois possible)
guestfs_int_recv
4.
Un RPC avec des paramètres "FileOut" (par exemple, "guestfs_download" dans guestfs(3)). Nous écrivons la requête, puis lisons la réponse, puis lisons le(s) fichier(s). La séquence des appels est : 
guestfs_int_send
guestfs_int_recv
guestfs_int_recv_file  (plusieurs fois possible)
5.
Des paramètres "FileIn" et "FileOut". Il n'y a pas d'appels de ce type dans l'API actuelle, mais ils seraient implémentés comme une combinaison des cas 3 et 4.

Toutes les opérations de lecture/écriture/etc. sont effectuées en utilisant le module de connexion actuel ("g->conn"). Pendant les opérations, le module de connexion gère de manière transparente les messages de journalisation qui apparaissent sur la console.

    "__attribute__((cleanup))" de gcc
    et clang. L'usage typique est :


fn ()
{
  CLEANUP_FREE char *str = NULL;
  str = safe_asprintf (g, "foo");
  // str est libéré automatiquement quand la fonction retourne
}


Il y a quelques pièges à connaître avec le mécanisme
  de nettoyage :


    
  
  • Si une variable de nettoyage n'est pas initialisée, vous pouvez finir par appeler
      free(3) avec une valeur indéfinie, ce qui entraînera le plantage du programme.
      Pour cette raison, vous devriez généralement initialiser chaque variable de nettoyage avec
      quelque chose, ex. "NULL"
    • 
  
  • Ne marquez pas les variables contenant des valeurs de retour comme variables de nettoyage.
    • 
  
  • La fonction main() ne devrait pas utiliser de variables
      de nettoyage car elle est normalement terminée en appelant exit(3), et cela
      n'appelle pas les gestionnaires de nettoyage.
    • 



Les fonctions de ce fichier sont utilisées en interne par les
    macros "CLEANUP_*" . Ne les appelez pas
    directement.

Fonction
    "common/visit/visit.c:visit"


int
visit (guestfs_h *g, const char *dir, visitor_function f, void *opaque)


Visite chaque fichier et répertoire dans un système de fichiers guestfs, en commençant par "dir".


"dir" peut être
    "/" pour visiter tout le système de fichiers, ou peut
    être un sous-répertoire. Les liens symboliques ne sont pas suivis.


La fonction visiteuse "f" est
    appelée une fois pour chaque répertoire et chaque fichier. Les paramètres passés à
    "f" incluent le nom du répertoire courant,
    le nom du fichier courant (ou "NULL" lorsque
    nous visitons un répertoire), les
    "guestfs_statns" (permissions du fichier, etc.),
    et la liste des attributs étendus du fichier. La fonction visiteuse peut retourner -1, ce qui provoque l'arrêt de toute la récursion avec une erreur.


Un pointeur
    "opaque" est également passé à cette fonction, qui est transmis à la fonction visiteuse.
