NOM

guestfs-security - sécurité de libguestfs

DESCRIPTION

Cette page de manuel discute des implications de sécurité de l'utilisation de libguestfs, en particulier avec des invités ou des images disque non fiables ou malveillants.

SIGNALEMENT DES PROBLÈMES DE SÉCURITÉ

Si vous souhaitez signaler un problème de sécurité en privé, veuillez suivre la procédure de sécurité de Red Hat à l'adresse https://access.redhat.com/security/team/contact

Si le problème de sécurité n'est pas très grave, vous pouvez simplement signaler un bug (voir "BUGS" ci-dessous), ou envoyer un e-mail à notre liste de diffusion (https://lists.libguestfs.org). Vous n'avez pas besoin de vous abonner à la liste de diffusion pour envoyer un e-mail, mais il y aura un délai pendant que le message est modéré.

PROBLÈMES GÉNÉRAUX

Sécurité du montage des systèmes de fichiers

Vous ne devriez jamais monter un système de fichiers invité non fiable directement sur votre noyau hôte (par exemple, en utilisant loopback ou kpartx).

Lorsque vous montez un système de fichiers, des erreurs dans le système de fichiers du noyau (VFS) peuvent être exploitées par des attaquants créant un système de fichiers malveillant. Ces exploits sont très graves pour deux raisons. Premièrement, il existe un très grand nombre de pilotes de systèmes de fichiers dans le noyau, et beaucoup d'entre eux sont rarement utilisés et peu d'attention de la part des développeurs a été portée au code. L'espace utilisateur Linux aide les attaquants potentiels en détectant le type de système de fichiers et en choisissant automatiquement le bon pilote VFS, même si ce type de système de fichiers est inattendu. Deuxièmement, un exploit au niveau du noyau est comme un exploit root local (pire à certains égards), donnant un accès immédiat et total au système jusqu'au niveau du matériel.

Ces exploits peuvent être présents dans le noyau pendant très longtemps (https://lwn.net/Articles/538898/).

Libguestfs fournit une approche en couches pour vous protéger des exploits :

  système de fichiers non fiable
--------------------------------------
  noyau de l'appliance
--------------------------------------
  processus qemu s'exécutant en tant que non-root
--------------------------------------
  sVirt [si utilisation de libvirt + SELinux]
--------------------------------------
  noyau hôte

Nous exécutons un noyau Linux à l'intérieur d'une machine virtuelle qemu, s'exécutant généralement en tant qu'utilisateur non-root. L'attaquant devrait écrire un système de fichiers qui exploiterait d'abord le noyau, puis la virtualisation qemu (par exemple, un pilote qemu défectueux) ou le protocole libguestfs, et enfin, pour être aussi grave qu'un exploit du noyau hôte, il faudrait qu'il élève ses privilèges jusqu'à root. De plus, si vous utilisez le backend libvirt et SELinux, sVirt est utilisé pour confiner le processus qemu. Cette escalade multi-étapes, effectuée par un élément de données statique, est considérée comme extrêmement difficile à réaliser, bien que nous ne disions jamais 'jamais' à propos des problèmes de sécurité.

Les appelants peuvent également réduire la surface d'attaque en forçant le type de système de fichiers lors du montage (utiliser "guestfs_mount_vfs" dans guestfs(3)).

Considérations générales de sécurité

Soyez prudent avec tous les fichiers ou données que vous téléchargez depuis un invité (par "télécharger", nous entendons non seulement "guestfs_download" dans la commande guestfs(3) mais toute commande qui lit des fichiers, des noms de fichiers, des répertoires ou quoi que ce soit d'autre à partir d'une image disque). Un attaquant pourrait manipuler les données pour tromper votre programme et lui faire faire la mauvaise chose. Considérez des cas tels que :

  • les données (fichier etc) étant absentes
  • étant présentes mais vides
  • étant beaucoup plus grandes que la normale
  • contenant des données arbitraires sur 8 bits
  • étant dans un encodage de caractères inattendu
  • contenant des homoglyphes.

Sécurité du protocole

Le protocole est conçu pour être sécurisé, étant basé sur la RFC 4506 (XDR) avec une taille de message supérieure définie. Cependant, un programme qui utilise libguestfs doit également être prudent - par exemple, vous pouvez écrire un programme qui télécharge un binaire depuis une image disque et l'exécute localement, et aucune sécurité de protocole ne vous sauvera des conséquences.

Sécurité de l'inspection

Certaines parties de l'API d'inspection (voir "INSPECTION" dans guestfs(3)) retournent des chaînes de caractères non fiables directement de l'invité, et celles-ci peuvent contenir des données sur 8 bits. Les appelants doivent faire attention à les échapper avant de les imprimer dans un fichier structuré (par exemple, utiliser l'échappement HTML si vous créez une page Web).

La configuration de l'invité peut être modifiée de manière inhabituelle par l'administrateur de la machine virtuelle, et peut ne pas refléter la réalité (en particulier pour les invités non fiables ou activement malveillants). Par exemple, nous analysons le nom d'hôte à partir de fichiers de configuration tels que /etc/sysconfig/network que nous trouvons dans l'invité, mais l'administrateur de l'invité peut facilement manipuler ces fichiers pour fournir le mauvais nom d'hôte.

L'API d'inspection analyse la configuration de l'invité en utilisant deux bibliothèques externes : Augeas (configuration Linux) et hivex (Registre Windows). Les deux sont conçues pour être robustes face aux données malveillantes, bien que des attaques par déni de service soient toujours possibles, par exemple avec des fichiers de configuration surdimensionnés.

Exécution de commandes invitées non fiables

Soyez très prudent lorsque vous exécutez des commandes de l'invité. En exécutant une commande dans l'invité, vous donnez du temps CPU à un binaire que vous ne contrôlez pas, sous le même compte utilisateur que la bibliothèque, bien qu'encapsulé dans la virtualisation qemu. Plus d'informations et d'alternatives peuvent être trouvées dans "RUNNING COMMANDS" dans guestfs(3).

PROBLÈMES DE SÉCURITÉ HISTORIQUES DANS LIBGUESTFS

CVE-2010-3851

https://bugzilla.redhat.com/642934

Ce bug de sécurité concerne la détection automatique du format de disque que qemu effectue sur les images disque.

Une image disque brute est juste les octets bruts, il n'y a pas d'en-tête. D'autres images disque comme qcow2 contiennent un en-tête spécial. Qemu gère cela en recherchant l'un des en-têtes connus, et si aucun n'est trouvé, il suppose que l'image disque doit être brute.

Cela permet à un invité auquel on a donné une image disque brute d'écrire un autre en-tête. Au prochain démarrage (ou lorsque l'image disque est accédée par libguestfs), qemu effectuera une autodétection et pensera que le format de l'image disque est, par exemple, qcow2, basé sur l'en-tête écrit par l'invité.

En soi, cela ne serait pas un problème, mais qcow2 offre de nombreuses fonctionnalités, dont une qui permet à une image disque de faire référence à une autre image (appelée "disque de sauvegarde"). Il le fait en plaçant le chemin vers le disque de sauvegarde dans l'en-tête qcow2. Ce chemin n'est pas validé et pourrait pointer vers n'importe quel fichier hôte (par exemple, "/etc/passwd"). Le disque de sauvegarde est ensuite exposé à travers des "trous" dans l'image disque qcow2, qui est bien sûr entièrement sous le contrôle de l'attaquant.

Dans libguestfs, il est plutôt difficile d'exploiter cela sauf dans deux circonstances :

1.
Vous avez activé le réseau ou ouvert le disque en mode écriture.
2.
Vous exécutez également du code non fiable depuis l'invité (voir "RUNNING COMMANDS" dans guestfs(3)).

La façon d'éviter cela est de spécifier le format de disque attendu lors de l'ajout de disques (l'option facultative "format" à "guestfs_add_drive_opts" dans guestfs(3)). Vous devriez toujours le faire si le disque est au format brut, et c'est une bonne idée pour les autres cas également. (Voir aussi "DISK IMAGE FORMATS" dans guestfs(3)).

Pour les disques ajoutés depuis libvirt via des appels tels que "guestfs_add_domain" dans guestfs(3), le format est récupéré depuis libvirt et transmis.

NAME

guestfs-security

DESCRIPTION

This page lists security vulnerabilities that have been reported against the libguestfs library.

There is no specific security guestfs-security command. This page is documentation only.

REPORTING SECURITY PROBLEMS

Please report security issues to the libguestfs project via their bug tracker.

When reporting a security issue, please mention that it is a security issue. Please also include a Debian Security Advisory if possible.

GENERAL ISSUES

The libguestfs library is a collection of tools for accessing and modifying virtual machine disk images. Many of these tools are setuid root and are therefore potential targets for security vulnerabilities.

Libguestfs runs in its own process, which is forked from the calling process. When you call a libguestfs API function, the library forks a child process, which runs as the --guest-root user (or root if that is not specified). This child process performs the operation and then exits.

If libguestfs is running as setuid root, and the guest is running as root, this means that the guest can potentially gain root access to the host.

However, libguestfs has a number of security features that limit the damage that a compromised guest can do:

  • The guestfsd process is run inside a chroot jail.
  • The guestfsd process is run inside a namespace.
  • The guestfsd process is run with capabilities dropped.
  • The guestfsd process is run with SELinux confinement.
  • The guestfsd process is run with AppArmor confinement.

These security features are designed to prevent a compromised guest from escaping the jail and gaining access to the host. However, it is always possible that a vulnerability may exist that allows such an escape.

For more information, see guestfs-internals(1).

HISTORICAL SECURITY ISSUES IN LIBGUESTFS

This section lists historical security issues that have been found in libguestfs. This is not an exhaustive list.

CVE-2018-10931

https://cve.mitre.org/cgi-bin/cvename.cgi?name=CVE-2018-10931

A use-after-free vulnerability in the guestfs_send_fd function could be triggered by a malicious guest to cause a denial of service.

This vulnerability was fixed in libguestfs version 1.40.0.

Reported by Daniel Rosenberg.

See also: https://lists.gnu.org/archive/html/qemu-devel/2018-06/msg01012.html.

CVE-2022-2211

https://bugzilla.redhat.com/CVE-2022-2211

The "get_keys" function in libguestfs-common/options/keys.c collects those "--key" options from the command line into a new array that match a particular block device that's being decrypted for inspection. The function intends to size the result array such that potentially all "--key" options, plus a terminating "NULL" element, fit into it. The code mistakenly uses the "MIN" macro instead of "MAX", and therefore only one element is allocated before the "NULL" terminator.

Passing precisely two "--key ID:..." options on the command line for the encrypted block device "ID" causes "get_keys" to overwrite the terminating "NULL", leading to an out-of-bounds read in "decrypt_mountables", file libguestfs-common/options/decrypt.c.

Passing more than two "--key ID:..." options on the command line for the encrypted block device "ID" causes "get_keys" itself to perform out-of-bounds writes. The most common symptom is a crash with "SIGSEGV" later on.

This issue affects -- broadly speaking -- all libguestfs-based utilities that accept "--key", namely: "guestfish", "guestmount", "virt-cat", "virt-customize", "virt-diff", "virt-edit", "virt-get-kernel", "virt-inspector", "virt-log", "virt-ls", "virt-sparsify", "virt-sysprep", "virt-tail", "virt-v2v".
