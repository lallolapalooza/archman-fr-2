COMMANDE

S

Sans arguments, affiche l'état des sous-modules existants. Plusieurs sous-commandes sont disponibles pour effectuer des opérations sur les

sous-modules.

add [-b <branch>] [-f|--force] [--name <name>] [--reference <repository>] [--ref-format <format>] [--depth <depth>] [--] <repository> [<path>

]
Ajoute le dépôt donné comme sous-module à l'emplacement donné dans l'ensemble de modifications à committer à côté du projet courant : le projet courant est appelé le « superprojet ».

<repository> est l'URL du dépôt d'origine du nouveau sous-module. Il peut s'agir d'une URL absolue ou (si elle commence par ./ ou ../), de l'emplacement relatif au dépôt distant par défaut du superprojet (veuillez noter que pour spécifier un dépôt foo.git qui est situé juste à côté d'un superprojet bar.git, vous devrez utiliser ../foo.git au lieu de ./foo.git - comme on pourrait s'y attendre en suivant les règles des URL relatives - car l'évaluation des URL relatives dans Git est identique à celle des répertoires relatifs)

.

Le distant par défaut est le distant de la branche de suivi à distance de la branche courante. Si une telle branche de suivi à distance n'existe pas ou si le HEAD est détaché, « origin » est supposé être le distant par défaut. Si le superprojet n'a pas de distant par défaut configuré, le superprojet est son propre amont faisant autorité et le répertoire de travail courant est utilisé à la

place.

L'argument optionnel <path> est l'emplacement relatif où le sous-module cloné doit exister dans le superprojet. Si <path> n'est pas fourni, la partie canonique du dépôt source est utilisée (« repo » pour « /path/to/repo.git » et « foo » pour « host.xz:foo/.git »). Si <path> existe et est déjà un dépôt Git valide, il est mis en index pour commit sans clonage. Le <path> est également utilisé comme nom logique du sous-module dans ses entrées de configuration, sauf si --name est utilisé pour spécifier un nom

logique.

L'URL donnée est enregistrée dans .gitmodules pour l'usage des utilisateurs suivants qui clonent le superprojet. Si l'URL est donnée relativement au dépôt du superprojet, on suppose que les dépôts du superprojet et du sous-module seront conservés ensemble au même emplacement relatif, et seule l'URL du superprojet doit être fournie. git-submodule localisera correctement le sous-module en utilisant l'URL relative dans .gitmodu

les.

Si --ref-format <format> est spécifié, le format de stockage des refs des

sous-modules nouvellement clon
és sera défini en conséquence.

status [--cached] [--recursive] [--] [<path>...

]
Affiche l'état des sous-modules. Cela affichera le SHA-1 du commit actuellement extrait pour chaque sous-module, avec le chemin du sous-module et la sortie de git describe pour le SHA-1. Chaque SHA-1 pourra éventuellement être préfixé par - si le sous-module n'est pas initialisé, + si le commit du sous-module actuellement extrait ne correspond pas au SHA-1 trouvé dans l'index du dépôt conteneur et U si le sous-module a des conflits de fusion.

Si --cached est spécifié, cette commande affichera à la place le SHA-1 enregistré dans le superprojet pour chaque

sous-module.

Si --recursive est spécifié, cette commande récursera dans les sous-modules imbriqués et affichera également leur

état.

Si vous êtes seulement intéressé par les changements des sous-modules actuellement initialisés par rapport au commit enregistré dans l'index ou le HEAD, git-status(1) et git-diff(1) fourniront également cette information (et peuvent aus

si signaler les changements dans l'
arbre de travail d'un sous-module).

init [--] [<path>...

]
Initialise les sous-modules enregistrés dans l'index (qui ont été ajoutés et committés ailleurs) en définissant submodule.$name.url dans .git/config, en utilisant le même paramètre depuis .gitmodules comme modèle. Si l'URL est relative, elle sera résolue en utilisant le distant par défaut. S'il n'y a pas de distant par défaut, le dépôt courant sera supposé être l'amont.

Les arguments optionnels <path> limitent les sous-modules qui seront initialisés. Si aucun chemin n'est spécifié et que submodule.active a été configuré, les sous-modules configurés comme actifs seront initialisés, sinon tous les sous-modules sont

initialisés.

Cela copiera également la valeur de submodule.$name.update, si présente dans le .gitmodules, vers .git/config, mais (1) cette commande ne modifie pas les informations existantes dans .git/config, et (2) submodule.$name.update défini à une commande personnalisée n'est pas copié pour des raisons de

sécurité.

Vous pouvez ensuite personnaliser les URL de clonage des sous-modules dans .git/config pour votre configuration locale et passer à git submodule update ; vous pouvez aussi simplement utiliser git submodule update --init sans l'étape explicite init si vous n'avez pas l'intention de personnaliser les emplacements des

sous-modules.

Voir la sous-commande

add pour la définition
du distant par défaut.

deinit [-f|--force] (--all|[--] <path>...

)
Désenregistre les sous-modules donnés, c'est-à-dire supprime toute la section submodule.$name de .git/config ainsi que leur arbre de travail. Les appels ultérieurs à git submodule update, git submodule foreach et git submodule sync ignoreront tout sous-module désenregistré jusqu'à ce qu'il soit réinitialisé, utilisez donc cette commande si vous ne voulez plus avoir de copie locale du sous-module dans votre arbre de travail.

Lorsque la commande est exécutée sans spécificateur de chemin, elle échoue, au lieu de tout désinitialiser, pour éviter les

erreurs.

Si --force est spécifié, l'arbre de travail du sous-module sera supprimé même s'il contient des modifications

locales.

Si vous voulez vraiment supprimer un sous-module du dépôt et committer cela, utilisez git-rm(1) à la place. Voir gitsubmodules(7) pour les

options de
suppression.

(note : ce qui est dans le fichier .gitmodules est sans importance à ce stade ; voir git submodule init ci-dessus pour savoir comment .gitmodules est utilisé). foreach [--recursive]

<command>
Evaluates an arbitrary shell command in each checked out submodule. The command has access to the variables $name, $sm_path, $displaypath, $sha1 and $toplevel: $name is the name of the relevant submodule section in .gitmodules, $sm_path is the path of the submodule as recorded in the immediate superproject, $displaypath contains the relative path from the current working directory to the submodules root directory, $sha1 is the commit as recorded in the immediate superproject, and $toplevel is the absolute path to the top-level of the immediate superproject. Note that to avoid conflicts with $PATH on Windows, the $path variable is now a deprecated synonym of $sm_path variable. Any submodules defined in the superproject but not checked out are ignored by this command. Unless given --quiet, foreach prints the name of each submodule before evaluating the command. If --recursive is given, submodules are traversed recursively (i.e. the given shell command is evaluated in nested submodules as well). A non-zero return from the command in any submodule causes the processing to terminate. This can be overridden by adding || : to the end of the command.

NAME

git-submodule — manage submodule repository

SYNOPSIS

git submodule [--quiet] [--ignore-submodules[=]]
            [--rc.=] [--helper-status]
            [--progress] [--no-progress] [--all] [--recursive] [-j  | --jobs ]
            [--parent-update-direction ]
            {--add | --remove | --record | --update | --foreach | --sync} [...]

DESCRIPTION

This command manages submodules. A submodule is a Git repository embedded inside another Git repository.

The command can be used to add, remove, initialize, update, configure, and list submodules.

COMMANDS

The following commands are available:

--add

Add the current contents of the index in the specified path as a submodule. The submodule’s URL is read from the argument (or a .gitmodules file). The path must be empty and not tracked before adding the submodule.

--remove

Remove the submodule from the configuration, and unregisters the submodule’s repository in the index and worktree. The submodule’s directory will be removed. This command is not recursive by default.

--record

Record the current submodule HEAD revision in the index. This command is not recursive by default.

--update, --checkout

Update the registered submodules, and the working tree files should be updated to match the HEAD in the superproject. This command is not recursive by default.

--foreach

Execute the given command for each submodule. This command is recursive by default.

--sync

Synchronize the submodules' remote URL configuration setting between the superproject and the submodule working trees. For each submodule, the URL specified in the superproject’s .gitmodules file is copied to the submodule's .git/config. This command is not recursive by default.

OPTIONS

The following options are available:

--ignore-submodules[=]

Do not operate on submodules ignored according to .gitmodules(5). The default value for <when> is "untracked", which ignores submodules that are not tracked by Git. Other values are "dirty" (ignores submodules with local modifications) and "all" (ignores all submodules). "none" can be used to disable the effect of the ignore option.

--helper-status

This option is only valid for the update, sync and status commands. When the command is used in a submodule, the status of the submodule is written to standard output in the "porcelain" format. This option is intended for use by other Git commands.

--checkout

This option is only valid for the update command. Checkout the submodule at the commit recorded in the superproject. If the submodule's branch is specified in the .gitmodules file, it will be checked out and updated. Otherwise, a detached HEAD will be created. This is the default behavior.

--merge

This option is only valid for the update command. Merge the commit recorded in the superproject into the current branch of the submodule. If this option is given, the submodule’s HEAD will not be detached. If a merge failure prevents this process, you will have to resolve the resulting conflicts within the submodule with the usual conflict resolution tools. If the key submodule.$name.update is set to merge, this option is implicit.

--rebase

This option is only valid for the update command. Rebase the current branch onto the commit recorded in the superproject. If this option is given, the submodule’s HEAD will not be detached. If a merge failure prevents this process, you will have to resolve these failures with git-rebase(1). If the key submodule.$name.update is set to rebase, this option is implicit.

--init

This option is only valid for the update command. Initialize all submodules for which "git submodule init" has not been called so far before updating.

--name

This option is only valid for the add command. It sets the submodule’s name to the given string instead of defaulting to its path. The name must be valid as a directory name and may not end with a /.

--reference <repository>

This option is only valid for add and update commands. These commands sometimes need to clone a remote repository. In this case, this option will be passed to the git-clone(1) command.

NOTE: Do not use this option unless you have read the note for git-clone(1)'s --reference, --shared, and --dissociate options carefully.

--dissociate

This option is only valid for add and update commands. These commands sometimes need to clone a remote repository. In this case, this option will be passed to the git-clone(1) command.

NOTE: see the NOTE for the --reference option.

--recursive

This option is only valid for foreach, update, status and sync commands. Traverse submodules recursively. The operation is performed not only in the submodules of the current repo, but also in any nested submodules inside those submodules (and so on).

--depth

This option is valid for add and update commands. Create a shallow clone with a history truncated to the specified number of revisions. See git-clone(1)

--recommend-shallow, --no-recommend-shallow

This option is only valid for the update command. The initial clone of a submodule will use the recommended submodule.<name>.shallow as provided by the .gitmodules file by default. To ignore the suggestions use --no-recommend-shallow.

-j <n>, --jobs <n>

This option is only valid for the update command. Clone new submodules in parallel with as many jobs. Defaults to the submodule.fetchJobs option.

--single-branch, --no-single-branch

This option is only valid for the update command. Clone only one branch during update: HEAD or one specified by --branch.

<path>...

Paths to submodule(s). When specified this will restrict the command to only operate on the submodules found at the specified paths. (This argument is required with add).

FILES

When initializing submodules, a .gitmodules file in the top-level directory of the containing repository is used to find the url of each submodule. This file should be formatted in the same way as $GIT_DIR/config. The key to each submodule url is "submodule.$name.url". See gitmodules(5) for details.

gitsubmodules(7), gitmodules(5).
