DESCRIPTIO

N

Le format de pack Git est la façon dont Git stocke la plupart des données principales de son dépôt. Au cours de la vie d'un dépôt, les objets dispersés (s'il y en a) et les packs plus petits sont consolidés en des packs plus grands. Voir git-gc(1) et git-pack-obje

cts(1).

Le format de pack est également utilisé sur le réseau, voir par exemple gitprotocol-v2(5), ainsi que comme partie d'autres formats de conteneur dans le cas de gitformat-

bundl
e(5).

SOMMES DE CONTRÔLE ET IDENTIFIANTS

D'OBJETS

Dans un dépôt utilisant le SHA-1 traditionnel, les sommes de contrôle des packs, les sommes de contrôle des index et les identifiants d'objets (noms d'objets) mentionnés ci-dessous sont tous calculés à l'aide de SHA-1. De même, dans les dépôts SHA-256, ces valeurs sont calculées à l'aide de

SHA-256.

Les sommes de contrôle CRC32 sont toujours calculées sur l'objet packé entier, y compris

l'en-tête (type sur n octets et longueur) ; le nom de l'objet de base ou l'offset, le
cas échéant ; et l'objet compressé entier. L'algorithme CRC32 utilisé est celui de zlib.

Encodage des

objets

Contrairement aux objets dispersés, les objets packés n'ont pas de préfixe contenant le type, la taille et un octet NUL. Ceux-ci ne sont pas nécessaires car ils peuvent être déterminés par le type sur n octets et la longueur qui préfixent les données et sont donc omis des données compressées et

deltaïfées.

Le calcul de l'identifiant d'objet utilise touj

ours ce préfixe en le reconstruisant à part
ir du type et de la longueur selon les besoins.

Encodage de la

taille

Ce document utilise l'« encodage de taille » suivant pour les entiers non négatifs : à partir de chaque octet, les sept bits de poids faible sont utilisés pour former l'entier résultant. Tant que le bit de poids fort est 1, ce processus continue ; l'octet avec MSB 0 fournit les sept derniers bits. Les morceaux de sept bits sont concaténés. Les valeurs ultérieures sont plus

significatives.

Cet encodage de taille ne doit pas être confondu avec l'« encodage d'offset », qui est également utilisé dans ce

document.

Lors de l'encodage de la taille d'un objet non deltaïé dans un pack, la taille est celle d

e l'objet brut non compressé. Pour les objets deltaïés, c'est la taille du delta non comp
ressé. Le nom de l'objet de base ou l'offset n'est pas inclus dans le calcul de la taille.

Représentation

deltaïée

Conceptuellement, il n'y a que quatre types d'objets : commit, tree, tag et blob. Cependant, pour économiser de l'espace, un objet pourrait être stocké comme un « delta » d'un autre objet « de base ». Ces représentations se voient attribuer de nouveaux types ofs-delta et ref-delta, qui ne sont valables que dans un fichier

pack.

Tant ofs-delta que ref-delta stockent le « delta » à appliquer à un autre objet (appelé objet de base) pour reconstruire l'objet. La différence entre eux est que ref-delta encode directement le nom de l'objet de base. Si l'objet de base est dans le même pack, ofs-delta encode l'offset de l'objet de base dans le pack à la

place.

L'objet de base pourrait également être deltaïé s'il est dans le même pack. Ref-delta peut également faire référence à un objet à l'extérieur du pack (c'est-à-dire le fameux « pack mince »). Lorsqu'il est stocké sur disque cependant, le pack devrait être auto-suffisant pour éviter une dépendance

cyclique.

Les données delta commencent par la taille de l'objet de base et la taille de l'objet à reconstruire. Ces tailles sont encodées à l'aide de l'encodage de taille ci-dessus. Le reste des données delta est une séquence d'instructions pour reconstruire l'objet à partir de l'objet de base. Si l'objet de base est deltaïé, il doit d'abord être converti en forme canonique. Chaque instruction ajoute de plus en plus de données à l'objet cible jusqu'à ce qu'il soit complet. Il y a deux instructions prises en charge jusqu'à présent : une pour copier une plage d'octets depuis l'objet source et une pour insérer de nouvelles données intégrées dans l'instruction

elle-même.

Chaque instruction a une longueur variable. Le type d'instruction est déterminé par le septième bit du premier octet. Les diagrammes suivants suivent la convention de la RFC 1951 (format de données compressées Deflate)

Une solution est de faire occuper aux bits la même position dans l' index trié par oid stocké par le MIDX. Mais comme les oids sont essentiellement aléatoires, leurs bitmap de accessibilité résultants n'auraient aucune localité, et seraient donc mal compressés. (C'est la raison pour laquelle les bitmap mono-paquet utilisent l'ordre du paquet, et non l'ordre .idx, pour le même

objectif.

) Nous aimerions donc définir un ordre pour l'ensemble du MIDX basé sur l'ordre des paquets, qui a une bien meilleure localité (et se compresse donc plus efficacement). On peut considérer un pseudo-paquet créé par la concaténation de tous les paquets du MIDX.
