DESCRIPTIO

N

De nombreuses commandes Git de type porcelain prennent un mélange de drapeaux (c'est-à-dire des paramètres qui commencent par un tiret -) et de paramètres destinés à la commande git rev-list sous-jacente qu'elles utilisent en interne, ainsi que des drapeaux et paramètres pour les autres commandes qu'elles utilisent en aval de git rev-list. Le but principal de cette commande est de permettre aux programmes appelants de faire la distinction entre eux. Il existe quelques autres modes de fonctionnement qui n'ont rien à voir avec la « aide à l'analyse des options de ligne de commande »

ci-dessus.

Sauf indication contraire, la plupart des options et des modes de fonctionnement nécessi

tent d'exécuter cette commande à l'intérieur d'un dépôt git ou d'une arborescence de tra
vail qui est sous le contrôle d'un dépôt git, et vous donneront une erreur fatale sinon.

SPÉCIFICATION DES

RÉVISIONS

Un paramètre de révision <rev> nomme généralement, mais pas nécessairement, un objet commit. Il utilise ce qu'on appelle la syntaxe étendue SHA-1. Voici différentes façons d'écrire les noms d'objets. Les noms listés près de la fin de cette liste désignent des arbres et des blobs contenus dans un

commit.

Note

Ce document montre la syntaxe "brute" telle que vue par git. Le shell et

d'autres interfaces utilisateur peuvent nécessiter un encodage supplémentai
re pour protéger les caractères spéciaux et éviter la division des mots.

<sha1>, par exemple dae86e1950b1277e545cee180551750029cfe735, dae86

e
Le nom d'objet SHA-1 complet (chaîne hexadécimale de 40 octets), ou une sous-chaîne initiale qui est unique dans le dépôt. Par exemple dae86e1950b1277e545cee180551750029cfe735 et dae86e désignent tous deux le même objet commit s'il n'y a pas d'autre objet dans votre dépôt dont le nom d'objet commence par
dae86e.

<sortie de describe>, par exemple v1.7.4.

2-679-g3bee7fb
Sortie de git describe ; c'est-à-dire une étiquette la plus proche, éventuellement suivie d'un tiret et d'un nombre de commits, suivie d'un tiret, d'un g, et d'un nom d'objet
abrégé.

<nom de réf>, par exemple master, heads/master, refs/heads/maste

r
Un nom de référence symbolique. Par exemple master désigne généralement l'objet commit référencé par refs/heads/master. Si vous avez à la fois heads/master et tags/master, vous pouvez dire explicitement heads/master pour indiquer à Git lequel vous voulez dire. En cas d'ambiguïté, un <nom de réf> est désambiguïsé en prenant la première correspondance dans les règles suivantes :
1.Si $GIT_DIR/<nom de réf> existe, c'est ce que vous voulez dire (c'est généralement utile seulement pour HEAD, FETCH_HEAD, ORIG_HEAD, MERGE_HEAD, REBASE_HEAD, REVERT_HEAD, CHERRY_PICK_HEAD, BISECT_HEAD et AUTO_MERGE)

2.sinon, refs/<nom de réf> s'il existe

3.sinon, refs/tags/<nom de réf> s'il existe

Une référence suivie du suffixe @ avec une spécification de date encadrée par des accolades (par exemple {yesterday}, {il y a 1 mois 2 semaines 3 jours 1 heure 1 seconde} ou {1979-02-26 18:30:00}) spécifie la valeur de la référence à un moment antérieur. <rev>^[<n>], par ex. HEAD^, v1.5.

1^0
Un suffixe ^ à un paramètre de révision signifie le premier parent de cet objet commit. ^<n> signifie le <n>ème parent (c.-à-d. <rev>^ est équivalent à <rev>^1). Comme règle spéciale, <rev>^0 signifie le commit lui-même et est utilisé lorsque <rev> est le nom d'objet d'un objet tag qui fait référence à un objet
commit.

<rev>~[<n>], par ex. HEAD~,

master~3
Un suffixe ~ à un paramètre de révision signifie le premier parent de cet objet commit. Un suffixe ~<n> à un paramètre de révision signifie l'objet commit qui est l'ancêtre de <n>ème génération de l'objet commit nommé, en suivant uniquement les premiers parents. C.-à-d. <rev>~3 est équivalent à <rev>^^^ qui est équivalent à <rev>^1^1^1. Voir ci-dessous une illustration de l'utilisation de cette
forme.

<rev>^{<type>}, par ex. v0.99.

8^{commit}
Un suffixe ^ suivi d'un nom de type d'objet encadré par des accolades signifie déréférencer l'objet à <rev> récursivement jusqu'à ce qu'un objet de type <type> soit trouvé ou que l'objet ne puisse plus être déréférencé (auquel cas, erreur). Par exemple, si <rev> est un commit-ish, <rev>^{commit} décrit l'objet commit correspondant. De même, si <rev> est un tree-ish, <rev>^{tree} décrit l'objet tree correspondant. <rev>^0 est un raccourci pour <rev>^{commit}.

<rev>^{object} peut être utilisé pour s'assurer que <rev> nomme un objet qui existe, sans exiger que <rev> soit un tag, et sans déréférencer <rev> ; car un tag est déjà un objet, il n'a pas à être déréférencé même une fois pour obtenir un

objet.

<rev>^{tag} peut être utilisé pour s'assurer que <rev> identifie un

objet tag
existant.

<rev>^{}, par ex. v0.99.

8^{}
Un suffixe ^ suivi d'une paire d'accolades vide signifie que l'objet pourrait être un tag, et déréférencer le tag récursivement jusqu'à ce qu'un objet non-tag soit
trouvé.

<rev>^{/<texte>}, par ex. HEAD^{/fix nasty

bug}
Un suffixe ^ à un paramètre de révision, suivi d'une paire d'accolades contenant un texte commençant par une barre oblique, est identique à la syntaxe :/fix nasty bug ci-dessous sauf qu'elle retourne le commit correspondant le plus récent qui est atteignable depuis le <rev> avant ^
.

:/<texte>, par ex. :/fix nasty

bug
Deux-points, suivi d'une barre oblique, suivi d'un texte, nomme un commit dont le message de commit correspond à l'expression régulière spécifiée. Ce nom retourne le commit correspondant le plus récent qui est atteignable depuis n'importe quelle référence, y compris HEAD. L'expression régulière peut correspondre à n'importe quelle partie du message de commit. Pour correspondre aux messages commençant par une chaîne, on peut utiliser par ex. :/^foo. La séquence spéciale :/! est réservée pour les modificateurs de ce à quoi on correspond. :/!-foo effectue une correspondance négative, tandis que :/!!foo correspond au caractère littéral !, suivi de foo. Toute autre séquence commençant par :/! est réservée pour le moment. Selon le texte donné, les règles de découpage en mots du shell pourraient nécessiter un guillemetage
supplémentaire.

SPÉCIFICATION DES

PLAGES

Les commandes de parcours d'historique telles que git log opèrent sur un ensemble de commits, pas seulement sur un seul

commit.

Pour ces commandes, spécifier une seule révision, en utilisant la notation décrite dans la section précédente, signifie l'ensemble des commits atteignables depuis le commit

donné.

Spécifier plusieurs révisions signifie l'ensemble des commits atteignables depuis n'importe lequel des commits

donnés.

L'ensemble atteignable d'un commit est le commit lui-même et les commits dans sa chaîne

d'ascendance.

Il existe plusieurs notations pour spécifier un ensemble de commits connectés (appelé une "plage de révisions"), illustrées

ci-dessous.

Exclusions de

commits

Notation avec ^ (accent

circonflexe)
Pour exclure des commits atteignables depuis un commit, un préfixe ^ est utilisé. Par ex. ^r1 r2 signifie les commits atteignables depuis r2 mais exclut ceux atteignables depuis r1 (c.-à-d. r1 et ses
ancê
tres).

Notations de plage avec

points

La Notation de plage .. (deux

points)
L'opération d'ensemble ^r1 r2 apparaît si souvent qu'il existe un raccourci pour elle. Quand vous avez deux commits r1 et r2 (nommés selon la syntaxe expliquée dans SPÉCIFICATION DES RÉVISIONS ci-dessus), vous pouvez demander les commits atteignables depuis r2 en excluant ceux atteignables depuis r1 par ^r1 r2 et cela peut s'écrire r1..r
2.

La Notation de différence symétrique ... (trois

points)
Une notation similaire r1...r2 est appelée différence symétrique de r1 et r2 et est définie comme r1 r2 --not $(git merge-base --all r1 r2). C'est l'ensemble des commits atteignables depuis soit r1 (côté gauche) ou r2 (côté droit) mais pas des
deux.

Dans ces deux notations abrégées, vous pouvez omettre une extrémité et la laisser par défaut à HEAD. Par exemple, origin.. est un raccourci pour origin..HEAD et demande "Qu'ai-je fait depuis que j'ai bifurqué de la branche origin ?" De même, ..origin est un raccourci pour HEAD..origin et demande "Qu'a fait l'origin depuis que j'ai bifurqué d'eux ?" Notez que .. signifierait HEAD..HEAD qui est une plage vide à la fois atteignable et non atteignable depuis

HEAD.

Des commandes spécifiquement conçues pour prendre deux plages distinctes (par ex. "git range-diff R1 R2" pour comparer deux plages) existent, mais ce sont des exceptions. Sauf mention contraire, toutes les commandes "git" qui opèrent sur un ensemble de commits travaillent sur une seule plage de révisions. En d'autres termes, écrire deux "notations de plage à deux points" l'une à côté de l'autre, par

ex.

Autres notations abrégées <rev>^

Parent

Trois autres notations abrégées existent, particulièrement utiles pour les commits de fusion, pour nommer un ensemble formé par un commit et ses commits

parents.

La notation r1^@ signifie tous les parents de r1

.

La notation r1^! inclut le commit r1 mais exclut tous ses parents. Par elle-même, cette notation désigne le commit unique r1

.

La notation <rev>^-[<n>] inclut <rev> mais exclut le <n>ième parent (c'est-à-dire une abréviation pour <rev>^<n>..<rev>), avec <n> = 1 si non spécifié. C'est typiquement utile pour les commits de fusion où vous pouvez simplement passer <commit>^- pour obtenir tous les commits de la branche qui a été fusionnée dans le commit de fusion <commit> (y compris <commit> lui-même)

.

Alors que <rev>^<n> servait à spécifier un seul parent de commit, ces trois notations prennent également en compte ses parents. Par exemple, vous pouvez dire HEAD^2^@, cependant vous ne pouvez pas dire HEAD

PARSEOP

T

En mode --parseopt, git rev-parse aide à traiter les options pour offrir aux scripts shell les mêmes fonctionnalités que celles dont disposent les commandes internes C. Il fonctionne comme un normaliseur d'options (par exemple, sépare les valeurs agrégées des interrupteurs simples), un peu comme getopt(1)

.

Il prend sur l'entrée standard la spécification des options à analyser et comprendre, et renvoie sur la sortie standard une chaîne adaptée pour sh(1) eval afin de remplacer les arguments par des arguments normalisés. En cas d'erreur, il affiche le mode d'emploi sur le flux d'erreur standard et se termine avec le code

129.

Remarque : Assurez-vous de mettre le résultat entre guillemets lorsque vous le passez à eval. Voir un exemple

ci-dessous.

Entrée

Format

Le format d'entrée de git rev-parse --parseopt est entièrement textuel. Il a deux parties, séparées par une ligne contenant uniquement --. Les lignes avant le séparateur (il devrait y en avoir une ou plus) sont utilisées pour le mode d'emploi. Les lignes après le séparateur décrivent les

options.

Chaque ligne d'options a ce format

: 
<opt-spec><fla
gs>*<arg-hint>
? ESP+ aide LF

>

rrects.

•Utilisez = si l'option prend un
