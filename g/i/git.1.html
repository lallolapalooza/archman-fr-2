DESCRIPTIO

N

Git est un système de contrôle de révision rapide, évolutif et distribué avec un ensemble de commandes exceptionnellement riche qui fournit à la fois des opérations de haut niveau et un accès complet aux

internes.

Voir gittutorial(7) pour commencer, puis voir giteveryday(7) pour un ensemble minimal de commandes utiles. Le Manuel de l'utilisateur de Git[1] contient une introduction plus

approfondie.

Une fois que vous maîtrisez les concepts de base, vous pouvez revenir à cette page pour apprendre quelles commandes Git propose. Vous pouvez en apprendre davantage sur des commandes Git individuelles avec "git help commande". La page manuelle gitcli(7) vous donne un aperçu de la syntaxe des commandes en ligne de

commande.

Une copie formatée et hypertexte de la dernière documentation Git peut être consultée à l'adresse https://git.github.io/htmldocs/git.html ou https://git-

scm.com
/docs.

-v,

--version
Affiche la version de la suite Git à partir de laquelle le programme git provient.

Cette option est convertie en interne en git version ... et accepte les mêmes options que la commande git-version(1). Si --help est également donné, il prend le dessus sur --ver

-h,

--help
Affiche le synopsis et une liste des commandes les plus couramment utilisées. Si l'option --all ou -a est donnée, alors toutes les commandes disponibles sont imprimées. Si une commande Git est nommée, cette option affichera la page manuelle pour cette commande.

D'autres options sont disponibles pour contrôler la manière dont la page manuelle est affichée. Voir git-help(1) pour plus d'informations, car git --help ... est converti en interne en git help ..

.

-C

<chemin>
Exécute comme si git avait été démarré dans <chemin> au lieu du répertoire de travail courant. Lorsque plusieurs options -C sont données, chaque -C <chemin> non absolu suivant est interprété relativement au -C <chemin> précédent. Si <chemin> est présent mais vide, par exemple -C "", alors le répertoire de travail courant reste inchangé.

Cette option affecte les options qui attendent un nom de chemin comme --git-dir et --work-tree en ce sens que leur interprétation des noms de chemins sera faite relativement au répertoire de travail causé par l'option -C. Par exemple, les invocations suivantes sont équivalentes

: 
git --git-dir=a.git --
work-tree=b -C c status
git --git-dir=c/a.git
--work-tree=c/b status

-c <nom>

=<valeur>
Passe un paramètre de configuration à la commande. La valeur donnée remplacera les valeurs des fichiers de configuration. Le <nom> est attendu dans le même format que celui listé par git config (sous-clés séparées par des points).

Notez que l'omission du = dans git -c foo.bar ... est autorisée et définit foo.bar à la valeur booléenne true (tout comme [foo]bar le ferait dans un fichier de configuration). Inclure le signe égal mais avec une valeur vide (comme git -c foo.bar= ...) définit foo.bar à la chaîne vide que git config --type=bool convertira en fal

s
e.

--config-env=<nom>

=<envvar>
Comme -c <nom>=<valeur>, donne à la variable de configuration <nom> une valeur, où <envvar> est le nom d'une variable d'environnement à partir de laquelle récupérer la valeur. Contrairement à -c, il n'y a pas de raccourci pour définir directement la valeur à une chaîne vide ; à la place, la variable d'environnement elle-même doit être définie à la chaîne vide. C'est une erreur si <envvar> n'existe pas dans l'environnement. <envvar> ne peut pas contenir un signe égal pour éviter l'ambiguïté avec <nom> qui en contient un.

Ceci est utile dans les cas où vous souhaitez passer des options de configuration transitoires à git, mais que vous le faites sur des systèmes d'exploitation où d'autres processus pourraient être en mesure de lire votre ligne de commande (par exemple /proc/self/cmdline), mais pas votre environnement (par exemple /proc/self/environ). Ce comportement est la valeur par défaut sur Linux, mais peut ne pas l'être sur votre

système.

Notez que cela peut ajouter de la sécurité pour des variables telles que http.extraHeader où les informations sensibles font partie de la valeur, mais pas par exemple url.<base>.insteadOf où les informations sen

sibles peuvent fair

Réinitialiser, restaurer et

annuler

Il existe trois commandes avec des noms similaires : git reset, git restore et git revert

.
•git-revert(1) sert à créer un nouveau commit qui annule les changements effectués par d'autres
commits.
•git-restore(1) sert à restaurer des fichiers dans l'arbre de travail depuis l'index ou depuis un autre commit. Cette commande ne met pas à jour votre branche. La commande peut aussi être utilisée pour restaurer des fichiers dans l'index depuis un autre
commit.
•git-reset(1) sert à mettre à jour votre branche, en déplaçant le pointeur pour ajouter ou supprimer des commits de la branche. Cette opération modifie l'historique des commits.

git reset peut aussi être utilisé pour restaurer l'index, ce qui entre en conflit avec git res

DISCUSSION

More detail on the following is available from the Git concepts chapter of the user-manual[3] and gitcore-tutorial(7).

A Git project normally consists of a working directory with a ".git" subdirectory at the top level. The .git directory contains, among other things, a compressed object database representing the complete history of the project, an "index" file which links that history to the current contents of the working tree, and named pointers into that history such as tags and branch heads.

The object database contains objects of three main types: blobs, which hold file data; trees, which point to blobs and other trees to build up directory hierarchies; and commits, which each reference a single tree and some number of parent commits.

The commit, equivalent to what other systems call a "changeset" or "version", represents a step in the project’s history, and each parent represents an immediately preceding step. Commits with more than one parent represent merges of independent lines of development.

All objects are named by the SHA-1 hash of their contents, normally written as a string of 40 hex digits. Such names are globally unique. The entire history leading up to a commit can be vouched for by signing just that commit. A fourth object type, the tag, is provided for this purpose.

When first created, objects are stored in individual files, but for efficiency may later be compressed together into "pack files".

Named pointers called refs mark interesting points in history. A ref may contain the SHA-1 name of an object or the name of another ref (the latter is called a "symbolic ref"). SÉCURITÉ

Certaines options de configuration et fichiers de hooks peuvent amener Git à exécuter des commandes shell arbitraires. Comme la configuration et les hooks ne sont pas copiés lors d'un git clone, il est généralement sûr de cloner des dépôts distants dont le contenu n'est pas fiable, de les inspecter avec git log, etc.

Cependant, il n'est pas sûr d'exécuter des commandes Git dans un répertoire .git (ou l'arbre de travail qui l'entoure) lorsque ce répertoire .git provient lui-même d'une source non fiable. Les commandes contenues dans sa configuration et ses hooks sont exécutées de la manière habituelle.

Par défaut, Git refuse de s'exécuter lorsque le dépôt appartient à une autre personne que l'utilisateur exécutant la commande. Voir l'entrée pour safe.directory dans git-config(1). Bien que cela puisse vous protéger dans un environnement multi-utilisateur, notez que vous pouvez également acquérir des dépôts non fiables qui vous appartiennent (par exemple, si vous extrayez un fichier zip ou un tarball d'une source non fiable). Dans de tels cas, vous devriez d'abord « assainir » le dépôt non fiable.

Si vous avez un répertoire .git non fiable, vous devriez d'abord le cloner avec git clone --no-local pour obtenir une copie propre. Git restreint l'ensemble des options et des hooks qui seront exécutés par upload-pack, qui gère le côté serveur d'un clone ou d'un fetch, mais attention, la surface d'attaque contre upload-pack est grande, cela comporte donc certains risques. La chose la plus sûre est de servir le dépôt en tant qu'utilisateur non privilégié (soit via git-daemon(1), ssh, ou en utilisant d'autres outils pour changer d'ID utilisateur). Voir la discussion dans la section SECURITY de git-upload-pack(1).
