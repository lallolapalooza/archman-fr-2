NAME

gitsubmodules - gestionez les sous-modules dans Git

SYNOPSIS

git submodule

DESCRIPTION

Les sous-modules permettent à un dépôt Git d’en intégrer un autre dans un sous-répertoire. Les sous-modules vous permettent de garder un dépôt séparé tout en le fusionnant dans un autre dépôt.

Lors du clonage d’un dépôt contenant des sous-modules, les sous-modules ne seront pas extraits par défaut ; vous pouvez demander à clone de récursivement cloner les sous-modules. Les sous-commandes init et update de git submodule maintiendront les sous-modules extraits et à une révision appropriée dans votre arbre de travail. Alternativement, vous pouvez configurer submodule.recurse pour que checkout récursivement dans les sous-modules (notez que submodule.recurse affecte également d’autres commandes Git, voir git-config(1) pour une liste complète).

THE CONFIGURATION OF SUBMODULES

La configuration des sous-modules se fait dans un fichier .gitmodules (qui doit être validé dans le dépôt principal).

Ce fichier est partitionné en sections nommées [submodule "<name>"], où <name> est le nom du sous-module. Ce nom est aussi le nom du répertoire dans lequel le sous-module sera cloné.

Les champs valides sont :

path

Le chemin d’accès relatif depuis la racine du dépôt principal dans lequel le sous-module sera cloné. Ce champ est obligatoire et doit être unique.

url

L’URL du dépôt du sous-module. Ce champ est obligatoire.

branch

Si spécifié, le sous-module sera mis à jour à cette branche. Si ce champ n’est pas spécifié, la branche par défaut du sous-module sera utilisée (généralement la branche principale).

tag

Si spécifié, le sous-module sera mis à jour à ce tag. Si les champs branch et tag sont spécifiés, tag aura la priorité.

active

Si ce champ est défini sur true, le sous-module sera considéré comme actif. S’il est défini sur false, le sous-module sera considéré comme inactif. Ce champ peut également être défini dans le fichier de configuration du dépôt principal, tel que .git/config, pour l’activer ou le désactiver. Les sous-modules qui ne sont pas actifs ne seront pas récupérés ou mis à jour lors de la mise à jour du dépôt principal. La valeur par défaut est true. Pour plus de détails, voir ACTIVE SUBMODULES.

ignore

Ce champ peut être défini sur true, false, untracked, dirty, ou all. Voir git-submodule(1) pour plus de détails.

FORMS

Il existe trois manières de configurer les sous-modules :

1.
Via un fichier .gitmodules dans la racine du dépôt.
2.
Via une section [submodule] dans le fichier de configuration du dépôt principal (par exemple, .git/config).
3.
Via une section [submodule "<name>"] dans le fichier de configuration du dépôt principal.

Chaque section de configuration [submodule] et [submodule "<name>"] dans le fichier de configuration du dépôt principal remplace les paramètres correspondants du fichier .gitmodules.

ACTIVE SUBMODULES

Par défaut, tous les sous-modules sont actifs. La valeur par défaut pour le champ active est true.

Il y a trois façons de rendre un sous-module inactif :

(1)
Le champ active est explicitement défini sur false dans le fichier .gitmodules.
(2)
Le champ active est explicitement défini sur false dans le fichier de configuration du dépôt principal (par exemple, .git/config).
(3)
Le nom du sous-module est exclu dans un champ submodule.active dans le fichier de configuration du dépôt principal. Le champ submodule.active peut contenir une liste de noms de sous-modules ou de motifs de chemin d’accès (pathspecs). Les motifs de chemin d’accès peuvent être préfixés avec :(exclude) pour exclure les sous-modules correspondants.

L’ordre de priorité est (1) > (2) > (3). Cela signifie que si un sous-module est désactivé via (1) ou (2), il sera désactivé même s’il est activé via (3).

Dans l’exemple suivant, les sous-modules bar et baz sont actifs, bar grâce à (1) et baz grâce à (3). foo est inactif car (1) a la priorité sur (3).

Notez que (3) est un artefact historique et sera ignoré si (1) et (2) spécifient que le sous-module n’est pas actif. En d’autres termes, si nous avons défini submodule.<nom>.active sur false ou si le chemin du sous-module est exclu dans le pathspec de submodule.active, l’URL n’a aucune importance, qu’elle soit présente ou non. Ceci est illustré dans l’exemple suivant.

[submodule "foo"]
  active = true
  url = https://example.org/foo
[submodule "bar"]
  url = https://example.org/bar
[submodule "baz"]
  url = https://example.org/baz
[submodule "bob"]
  ignore = true
[submodule]
  active = b*
  active = :(exclude) baz

Ici, tous les sous-modules sauf baz (foo, bar, bob) sont actifs. foo grâce à son propre drapeau actif et tous les autres grâce au pathspec actif du sous-module, qui spécifie que tout sous-module commençant par b sauf baz est également actif, quelle que soit la présence du champ .url.

WORKFLOW FOR A THIRD PARTY LIBRARY

# Ajouter un sous-module
git submodule add <URL> <chemin>
# Mettre à jour occasionnellement le sous-module vers une nouvelle version :
git -C <chemin> checkout <nouvelle-version>
git add <chemin>
git commit -m "mise à jour du sous-module vers une nouvelle version"
# Voir la liste des sous-modules dans un super-projet
git submodule status
# Voir FORMS pour la suppression des sous-modules

WORKFLOW FOR AN ARTIFICIALLY SPLIT REPO

# Activer la récursivité pour les commandes pertinentes, de sorte que
# les commandes régulières récursent par défaut dans les sous-modules
git config --global submodule.recurse true
# Contrairement à la plupart des autres commandes ci-dessous, clone a toujours
# besoin de son propre drapeau recurse :
git clone --recurse <URL> <répertoire>
cd <répertoire>
# Se familiariser avec le code :
git grep foo
git ls-files --recurse-submodules

Note

git ls-files nécessite également son propre drapeau --recurse-submodules.

# Obtenir du nouveau code
git fetch
git pull --rebase
# Changer le répertoire de travail
git checkout
git reset

IMPLEMENTATION DETAILS

Lors du clonage ou de la récupération d’un dépôt contenant des sous-modules, les sous-modules ne seront pas extraits par défaut ; vous pouvez demander à clone de récursivement cloner les sous-modules. Les sous-commandes init et update de git submodule maintiendront les sous-modules extraits et à une révision appropriée dans votre arbre de travail. Alternativement, vous pouvez configurer submodule.recurse pour que checkout récursivement dans les sous-modules (notez que submodule.recurse affecte également d’autres commandes Git, voir git-config(1) pour une liste complète).
