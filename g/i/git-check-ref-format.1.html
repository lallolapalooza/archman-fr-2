NOM

git-check-ref-format - Vérifie qu'un nom de référence est bien formé

SYNOPSIS

git check-ref-format [--normalize]
       [--[no-]allow-onelevel] [--refspec-pattern]
       <nom-ref>
git check-ref-format --branch <nom-branche-raccourci>

DESCRIPTION

Vérifie si un nom-ref donné est acceptable, et se termine avec un statut non nul s'il ne l'est pas.

Une référence est utilisée dans Git pour spécifier des branches et des tags. Une tête de branche est stockée dans la hiérarchie refs/heads, tandis qu'un tag est stocké dans la hiérarchie refs/tags de l'espace de noms des références (typiquement dans les répertoires $GIT_DIR/refs/heads et $GIT_DIR/refs/tags ou, comme entrées dans le fichier $GIT_DIR/packed-refs si les références sont regroupées par git gc).

Git impose les règles suivantes sur la façon dont les références sont nommées :

1.Elles peuvent inclure une barre oblique / pour un regroupement hiérarchique (par répertoire), mais aucun composant séparé par une barre oblique ne peut commencer par un point . ni se terminer par la séquence .lock.
2.Elles doivent contenir au moins une /. Ceci impose la présence d'une catégorie comme heads/, tags/, etc., mais les noms réels ne sont pas restreints. Si l'option --allow-onelevel est utilisée, cette règle est ignorée.
3.Elles ne peuvent pas avoir deux points consécutifs .. n'importe où.
4.Elles ne peuvent pas contenir de caractères de contrôle ASCII (c'est-à-dire des octets dont les valeurs sont inférieures à \040, ou \177 DEL), d'espace, de tilde ~, de caret ^, ou de deux-points : n'importe où.
5.Elles ne peuvent pas contenir de point d'interrogation ?, d'astérisque *, ou de crochet ouvrant [ n'importe où. Voir l'option --refspec-pattern ci-dessous pour une exception à cette règle.
6.Elles ne peuvent pas commencer ou se terminer par une barre oblique / ni contenir de barres obliques consécutives (voir l'option --normalize ci-dessous pour une exception à cette règle).
7.Elles ne peuvent pas se terminer par un point ..
8.Elles ne peuvent pas contenir une séquence @{.
9.Elles ne peuvent pas être le caractère unique @.
10.Elles ne peuvent pas contenir de \.

Ces règles facilitent l'analyse des noms de références par les outils basés sur les scripts shell, l'expansion des chemins par le shell lorsqu'un nom de référence est utilisé sans guillemets (par erreur), et évitent également les ambiguïtés dans certaines expressions de noms de références (voir gitrevisions(7)) :

1.Un double point .. est souvent utilisé comme dans ref1..ref2, et dans certains contextes cette notation signifie ^ref1 ref2 (c'est-à-dire pas dans ref1 et dans ref2).
2.Un tilde ~ et un caret ^ sont utilisés pour introduire l'opération post-fixe *ieme parent* et *éplucher l'oignon*.
3.Un deux-points : est utilisé comme dans srcref:dstref pour signifier « utiliser la valeur de srcref et la stocker dans dstref » dans les opérations de fetch et de push. Il peut également être utilisé pour sélectionner un objet spécifique comme avec git cat-file : « git cat-file blob v1.3.3:refs.c ».
4.Le symbole arobase-parenthèse ouvrante @{ est utilisé comme une notation pour accéder à une entrée du reflog.

Avec l'option --branch, la commande prend un nom et vérifie s'il peut être utilisé comme un nom de branche valide (par exemple, lors de la création d'une nouvelle branche). Mais soyez prudent lors de l'utilisation de la syntaxe de checkout précédente qui peut faire référence à un état de HEAD détaché. La règle que git check-ref-format --branch $nom implémente peut être plus stricte que ce que dit git check-ref-format refs/heads/$nom (par exemple, un tiret peut apparaître au début d'un composant de référence, mais il est explicitement interdit au début d'un nom de branche). Lorsqu'il est exécuté avec l'option --branch dans un dépôt, l'entrée est d'abord développée pour la « syntaxe de checkout précédente » @{-n}. Par exemple, @{-1} est un moyen de faire référence à la dernière chose qui a été extraite en utilisant une opération « git switch » ou « git checkout ». Cette option devrait être utilisée par les porcelaines pour accepter cette syntaxe partout où un nom de branche est attendu, afin qu'ils puissent agir comme si vous aviez tapé le nom de la branche. À noter comme exception, « l'opération de checkout précédente » peut résulter en un nom d'objet commit lorsque la N-ième chose extraite n'était pas une branche.

OPTIONS

--allow-onelevel, --no-allow-onelevel

Contrôle si les noms de référence à un seul niveau sont acceptés (c'est-à-dire les noms de référence qui ne contiennent pas plusieurs composants séparés par /). La valeur par défaut est --no-allow-onelevel.

--refspec-pattern

Interprète le <nom-ref> comme un motif de nom de référence pour un refspec (tel qu'utilisé avec les dépôts distants). Si cette option est activée, le <nom-ref> est autorisé à contenir un seul * dans le refspec (par exemple, foo/bar*/baz ou foo/bar*baz/, mais pas foo/bar*/baz*).

--normalize

Normalise le nom-ref en supprimant les caractères de barre oblique (/) de début et en réduisant les séquences de barres obliques adjacentes entre les composants du nom en une seule barre oblique. Si le nom de référence normalisé est valide, l'imprime sur la sortie standard et se termine avec un statut de 0, sinon se termine avec un statut non nul. ( --print est une façon obsolète de dire --normalize.)

EXEMPLES

•Imprimer le nom de la dernière chose extraite : 
$ git check-ref-format --branch @{-1}
•Déterminer le nom de référence à utiliser pour une nouvelle branche : 
$ ref=$(git check-ref-format --normalize "refs/heads/$nouvellebranche")||
{ echo "nous n'aimons pas '$nouvellebranche' comme nom de branche." >&2 ; exit 1 ; }
