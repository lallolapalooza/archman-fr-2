NOM

git-read-tree - Lit les informations d'arbre dans l'index

SYNOPSIS

git read-tree [(-m [--trivial] [--aggressive] | --reset | --prefix=<préfixe>)
                [-u | -i]] [--index-output=<fichier>] [--no-sparse-checkout]
                (--empty | <tree-ish1> [<tree-ish2> [<tree-ish3>]])

DESCRIPTION

Lit les informations d'arbre données par <tree-ish> dans l'index, mais ne met pas à jour réellement aucun des fichiers qu'il « met en cache ». (voir : git-checkout-index(1))

De manière facultative, il peut fusionner un arbre dans l'index, effectuer une fusion rapide (c'est-à-dire à deux voies), ou une fusion à trois voies, avec le -m drapeau. Lorsqu'il est utilisé avec -m, le -u drapeau lui fait aussi mettre à jour les fichiers de l'arbre de travail avec le résultat de la fusion.

Seules les fusions triviales sont effectuées par git read-tree lui-même. Seuls les chemins en conflit seront dans un état non fusionné lorsque git read-tree se termine.

OPTIONS

-m

Effectuer une fusion, pas seulement une lecture. La commande refusera de s'exécuter si votre fichier d'index contient des entrées non fusionnées, indiquant que vous n'avez pas terminé une fusion précédente que vous avez commencée.

--reset

Identique à -m, sauf que les entrées non fusionnées sont écartées au lieu de provoquer une erreur. Lorsqu'il est utilisé avec -u, les mises à jour entraînant la perte de modifications de l'arbre de travail ou de fichiers ou répertoires non suivis n'interrompront pas l'opération.

-u

Après une fusion réussie, mettre à jour les fichiers de l'arbre de travail avec le résultat de la fusion.

-i

Habituellement, une fusion nécessite que le fichier d'index ainsi que les fichiers de l'arbre de travail soient à jour avec le commit de tête actuel, afin de ne pas perdre les modifications locales. Ce drapeau désactive la vérification avec l'arbre de travail et est destiné à être utilisé lors de la création d'une fusion d'arbres qui ne sont pas directement liés à l'état actuel de l'arbre de travail dans un fichier d'index temporaire.

-n, --dry-run

Vérifier si la commande échouerait, sans mettre à jour réellement l'index ou les fichiers de l'arbre de travail.

-v

Afficher la progression de l'extraction des fichiers.

--trivial

Restreindre la fusion à trois voies par git read-tree pour qu'elle n'ait lieu que s'il n'y a pas de fusion au niveau des fichiers requise, au lieu de résoudre la fusion pour les cas triviaux et de laisser les fichiers en conflit non résolus dans l'index.

--aggressive

Habituellement, une fusion à trois voies par git read-tree résout la fusion pour les cas vraiment triviaux et laisse les autres cas non résolus dans l'index, afin que les couches de porcelain puissent implémenter différentes politiques de fusion. Ce drapeau fait résoudre à la commande quelques cas de plus en interne :
•lorsqu'un côté supprime un chemin et que l'autre côté laisse le chemin non modifié. La résolution est de supprimer ce chemin.
•lorsque les deux côtés suppriment un chemin. La résolution est de supprimer ce chemin.
•lorsque les deux côtés ajoutent un chemin de manière identique. La résolution est d'ajouter ce chemin.

--prefix=<préfixe>

Conserver le contenu actuel de l'index, et lire le contenu de l'arbre nommé sous le répertoire à <préfixe>. La commande refusera d'écraser les entrées qui existaient déjà dans le fichier d'index original.

--index-output=<fichier>

Au lieu d'écrire les résultats dans $GIT_INDEX_FILE, écrire l'index résultant dans le fichier nommé. Pendant que la commande s'exécute, le fichier d'index original est verrouillé avec le même mécanisme que d'habitude. Le fichier doit permettre d'être renommé par rename(2) depuis un fichier temporaire créé à côté du fichier d'index habituel ; généralement, cela signifie qu'il doit se trouver sur le même système de fichiers que le fichier d'index lui-même, et vous devez avoir la permission d'écriture dans les répertoires où se trouvent le fichier d'index et le fichier de sortie de l'index.

--recurse-submodules, --no-recurse-submodules

Utiliser --recurse-submodules mettra à jour le contenu de tous les sous-modules actifs selon le commit enregistré dans le super-projet en appelant read-tree récursivement, et définira également le HEAD des sous-modules comme détaché à ce commit.

--no-sparse-checkout

Désactiver la prise en charge de l'extraction creuse même si core.sparseCheckout est vrai.

--empty

Au lieu de lire les objets d'arbre dans l'index, le vider simplement.

-q, --quiet

Silencieux, supprimer les messages de retour.

<tree-ish#>

L'identifiant du ou des objets d'arbre à lire/fusionner.

FUSION

Si -m est spécifié, git read-tree peut effectuer 3 types de fusion : une fusion d'arbre unique si un seul arbre est donné, une fusion rapide avec 2 arbres, ou une fusion à trois voies si 3 arbres ou plus sont fournis.

Fusion d'arbre unique

Si un seul arbre est spécifié, git read-tree fonctionne comme si l'utilisateur n'avait pas spécifié -m, sauf que si l'index original a une entrée pour un chemin donné, et que le contenu du chemin correspond à l'arbre lu, les informations stat du fichier d'index sont utilisées. (En d'autres termes, les stat() du fichier d'index priment sur celles de l'arbre fusionné).

Cela signifie que si vous faites un git read-tree -m <nouvelarbre> suivi d'un git checkout-index -f -u -a, le git checkout-index n'extraira que ce qui a réellement changé.

Cela est utilisé pour éviter les fausses correspondances inutiles lorsque git diff-files est exécuté après git read-tree.

Fusion de deux arbres

Typiquement, cela est invoqué comme git read-tree -m $H $M, où $H est le commit de tête du dépôt actuel, et $M est la tête d'un arbre externe, qui est simplement en avance sur $H (c'est-à-dire que nous sommes dans une situation de fusion rapide).

Lorsque deux arbres sont spécifiés, l'utilisateur dit à git read-tree ce qui suit :

1.L'index et l'arbre de travail actuels proviennent de $H, mais l'utilisateur peut y avoir apporté des modifications locales depuis $H.
2.L'utilisateur souhaite faire une fusion rapide vers $M.

Dans ce cas, la commande git read-tree -m $H $M s'assure qu'aucune modification locale n'est perdue à la suite de cette « fusion ». Voici les règles de « report », où « I » désigne l'index, « propre » signifie que l'index et l'arbre de travail coïncident, et « existe »/« rien » font référence à la présence d'un chemin dans le commit spécifié :

        I                   H        M        Résultat
       -------------------------------------------------------
     0  rien               rien     rien     (ne se produit pas)
     1  rien               rien     existe   utiliser M
     2  rien               existe   rien     supprimer le chemin de l'index
     3  rien               existe   existe,  utiliser M si « extraction initiale »,
                                     H == M   conserver l'index sinon
                                     existe,  échec
                                     H != M
        propre I==H  I==M
       ------------------
     4  oui   N/A   N/A     rien     rien     conserver l'index
     5  non   N/A   N/A     rien     rien     conserver l'index
     6  oui   N/A   oui     rien     existe   conserver l'index
     7  non   N/A   oui     rien     existe   conserver l'index
     8  oui   N/A   non     rien     existe   échec
     9  non   N/A   non     rien     existe   échec
     10 oui   oui   N/A     existe   rien     supprimer le chemin de l'index
     11 non   oui   N/A     existe   rien     échec
     12 oui   non   N/A     existe   rien     échec
     13 non   non   N/A     existe   rien     échec
        propre (H==M)
       ------
     14 oui                 existe   existe   conserver l'index
     15 non                 existe   existe   conserver l'index
        propre I==H  I==M (H!=M)
       ------------------
     16 oui   non   non     existe   existe   échec
     17 non   non   non     existe   existe   échec
     18 oui   non   oui     existe   existe   conserver l'index
     19 non   non   oui     existe   existe   conserver l'index
     20 oui   oui   non     existe   existe   utiliser M
     21 non   oui   non     existe   existe   échec

Dans tous les cas de « conserver l'index », l'entrée de l'index reste telle qu'elle était dans le fichier d'index original. Si l'entrée n'est pas à jour, git read-tree conserve la copie dans l'arbre de travail intacte lorsque sous le drapeau -u.

Lorsque cette forme de git read-tree réussit, vous pouvez voir quelles modifications « locales » que vous avez apportées ont été reportées en exécutant git diff-index --cached $M. Notez que cela ne correspond pas nécessairement à ce que git diff-index --cached $H aurait produit avant une telle fusion à deux arbres. C'est à cause des cas 18 et 19 — si vous aviez déjà les modifications dans $M (par exemple, vous les avez peut-être récupérées par e-mail sous forme de patch), git diff-index --cached $H vous aurait informé du changement avant cette fusion, mais il n'apparaîtrait pas dans la sortie de git diff-index --cached $M après la fusion à deux arbres.

Le cas 3 est un peu délicat et nécessite une explication. Le résultat de cette règle devrait logiquement être de supprimer le chemin si l'utilisateur a préparé la suppression du chemin, puis a basculé vers une nouvelle branche. Cependant, cela empêcherait le checkout initial de se produire, donc la règle est modifiée pour utiliser M (nouvel arbre) uniquement lorsque le contenu de l'index est vide. Sinon, la suppression du chemin est conservée tant que $H et $M sont identiques.

Fusion à 3 voies

Chaque entrée « index » possède deux bits d'état « stage ». Le stage 0 est le plus normal, et c'est le seul que vous verriez dans une utilisation normale.

Cependant, lorsque vous utilisez git read-tree avec trois arbres, le « stage » commence à 1.

Cela signifie que vous pouvez faire ceci :

$ git read-tree -m <arbre1> <arbre2> <arbre3>

et vous vous retrouverez avec un index contenant toutes les entrées de <arbre1> dans le « stage1 », toutes les entrées de <arbre2> dans le « stage2 », et toutes les entrées de <arbre3> dans le « stage3 ». Lors de la fusion d'une autre branche dans la branche courante, nous utilisons l'arbre de l'ancêtre commun comme <arbre1>, la tête de la branche courante comme <arbre2>, et la tête de l'autre branche comme <arbre3>.

De plus, git read-tree a une logique de cas spécial qui dit : si vous voyez un fichier qui correspond en tous points dans les états suivants, il se « réduit » en « stage0 » :

• les stages 2 et 3 sont identiques ; prenez l'un ou l'autre (cela ne fait aucune différence – le même travail a été effectué sur notre branche en stage 2 et sur leur branche en stage 3)
• les stages 1 et 2 sont identiques et le stage 3 est différent ; prenez le stage 3 (notre branche en stage 2 n'a rien fait depuis l'ancêtre en stage 1 tandis que leur branche en stage 3 y a travaillé)
• les stages 1 et 3 sont identiques et le stage 2 est différent ; prenez le stage 2 (nous avons fait quelque chose pendant qu'ils n'ont rien fait)

La commande git write-tree refuse d'écrire un arbre insensé, et elle se plaindra des entrées non fusionnées si elle voit une seule entrée qui n'est pas au stage 0.

Ok, tout cela ressemble à une collection de règles totalement insensées, mais c'est en fait exactement ce que vous voulez pour effectuer une fusion rapide. Les différents stages représentent l'« arbre résultat » (stage 0, alias « merged »), l'arbre d'origine (stage 1, alias « orig »), et les deux arbres que vous essayez de fusionner (stages 2 et 3 respectivement).

L'ordre des stages 1, 2 et 3 (donc l'ordre des trois arguments de ligne de commande <tree-ish>) est significatif lorsque vous démarrez une fusion à 3 voies avec un fichier d'index déjà rempli. Voici un aperçu du fonctionnement de l'algorithme :

• si un fichier existe sous un format identique dans les trois arbres, il sera automatiquement réduit à l'état « fusionné » par git read-tree.
• un fichier qui présente la moindre différence dans les trois arbres restera sous forme d'entrées distinctes dans l'index. Il appartient à la « politique de plomberie » de déterminer comment supprimer les stages non-0 et insérer une version fusionnée.
• le fichier d'index est sauvegardé et restauré avec toutes ces informations, donc vous pouvez fusionner les choses de manière incrémentielle, mais tant qu'il contient des entrées aux stages 1/2/3 (c'est-à-dire des « entrées non fusionnées »), vous ne pouvez pas écrire le résultat. L'algorithme de fusion devient donc très simple :
• vous parcourez l'index dans l'ordre, et ignorez toutes les entrées du stage 0, car elles ont déjà été traitées.
• si vous trouvez un « stage1 », mais pas de « stage2 » ou « stage3 » correspondant, vous savez qu'il a été supprimé des deux arbres (il n'existait que dans l'arbre d'origine), et vous supprimez cette entrée.
• si vous trouvez un « stage2 » et un « stage3 » correspondants, vous supprimez l'un d'eux et transformez l'autre en entrée de « stage0 ». Supprimez également toute entrée « stage1 » correspondante si elle existe... toutes les règles triviales normales...

Vous utiliseriez normalement git merge-index avec le fourni git merge-one-file pour effectuer cette dernière étape. Le script met à jour les fichiers dans l'arborescence de travail lors de la fusion de chaque chemin et à la fin d'une fusion réussie.

Lorsque vous démarrez une fusion à 3 voies avec un fichier d'index déjà rempli, il est supposé qu'il représente l'état des fichiers dans votre arborescence de travail, et vous pouvez même avoir des fichiers avec des modifications non enregistrées dans le fichier d'index. Il est en outre supposé que cet état est « dérivé » de l'arbre stage 2. La fusion à 3 voies refuse de s'exécuter si elle trouve une entrée dans le fichier d'index d'origine qui ne correspond pas au stage 2.

Ceci est fait pour vous éviter de perdre votre travail en cours et de mélanger vos modifications aléatoires dans un commit de fusion sans lien. Pour illustrer, supposons que vous partiez de ce qui a été commité en dernier dans votre dépôt :

$ JC=`git rev-parse --verify "HEAD^0"`
$ git checkout-index -f -u -a $JC

Vous effectuez des modifications aléatoires, sans exécuter git update-index. Et puis vous remarquez que la pointe de votre « upstream » a avancé depuis que vous avez récupéré chez lui :

$ git fetch git://.... linus
$ LT=`git rev-parse FETCH_HEAD`

Votre arborescence de travail est toujours basée sur votre HEAD ($JC), mais vous avez quelques modifications depuis. La fusion à trois voies s'assure que vous n'avez pas ajouté ou modifié d'entrées d'index depuis $JC, et si ce n'est pas le cas, elle fait ce qu'il faut. Donc, avec la séquence suivante :

$ git read-tree -m -u `git merge-base $JC $LT` $JC $LT
$ git merge-index git-merge-one-file -a
$ echo "Merge with Linus" | \
  git commit-tree `git write-tree` -p $JC -p $LT

ce que vous commiteriez est une fusion pure entre $JC et $LT sans vos modifications en cours, et votre arborescence de travail serait mise à jour avec le résultat de la fusion.

Cependant, si vous avez des modifications locales dans l'arborescence de travail qui seraient écrasées par cette fusion, git read-tree refusera de s'exécuter pour éviter que vos modifications ne soient perdues.

Autrement dit, il n'y a pas besoin de s'inquiéter de ce qui n'existe que dans l'arborescence de travail. Lorsque vous avez des modifications locales dans une partie du projet qui n'est pas impliquée dans la fusion, vos modifications n'interfèrent pas avec la fusion et sont conservées intactes. Lorsqu'elles interfèrent, la fusion ne démarre même pas (git read-tree se plaint bruyamment et échoue sans rien modifier). Dans un tel cas, vous pouvez simplement continuer à faire ce que vous étiez en train de faire, et lorsque votre arborescence de travail sera prête (c'est-à-dire que vous aurez terminé votre travail en cours), tentez à nouveau la fusion.

CHECKOUT SPARSE

Note : Les fonctionnalités skip-worktree dans git-update-index(1) et read-tree sont antérieures à l'introduction de git-sparse-checkout(1). Les utilisateurs sont encouragés à utiliser la commande sparse-checkout de préférence à ces commandes de plomberie pour les besoins liés au checkout sparse/skip-worktree. Cependant, les informations ci-dessous pourraient être utiles aux utilisateurs qui tentent de comprendre le style de modèle utilisé dans le mode non-cône de la commande sparse-checkout.

Le « checkout sparse » permet de peupler l'arborescence de travail de manière clairsemée. Il utilise le bit skip-worktree (voir git-update-index(1)) pour indiquer à Git si un fichier dans l'arborescence de travail mérite qu'on s'y intéresse.

git read-tree et d'autres commandes basées sur la fusion (git merge, git checkout...) peuvent aider à maintenir le bitmap skip-worktree et la mise à jour de l'arborescence de travail. $GIT_DIR/info/sparse-checkout est utilisé pour définir le bitmap de référence skip-worktree. Lorsque git read-tree doit mettre à jour l'arborescence de travail, il réinitialise le bit skip-worktree dans l'index en se basant sur ce fichier, qui utilise la même syntaxe que les fichiers .gitignore. Si une entrée correspond à un motif dans ce fichier, ou si l'entrée correspond à un fichier présent dans l'arborescence de travail, alors skip-worktree ne sera pas défini sur cette entrée. Sinon, skip-worktree sera défini.

Ensuite, il compare la nouvelle valeur skip-worktree avec la précédente. Si skip-worktree passe de défini à non défini, il rajoutera le fichier correspondant. S'il passe de non défini à défini, ce fichier sera supprimé.

Bien que $GIT_DIR/info/sparse-checkout soit généralement utilisé pour spécifier quels fichiers sont inclus, vous pouvez également spécifier quels fichiers ne sont *pas* inclus, en utilisant des motifs de négation. Par exemple, pour supprimer le fichier unwanted :

!unwanted

Une autre chose délicate est de re-peupler complètement l'arborescence de travail lorsque vous ne voulez plus du checkout sparse. Vous ne pouvez pas simplement désactiver le « checkout sparse » car les bits skip-worktree sont toujours dans l'index et votre arborescence de travail est toujours peuplée de manière clairsemée. Vous devriez re-peupler l'arborescence de travail avec le contenu du fichier $GIT_DIR/info/sparse-checkout comme suit :

Ensuite, vous pouvez désactiver le checkout sparse. Le support du checkout sparse dans git read-tree et les commandes similaires est désactivé par défaut. Vous devez activer core.sparseCheckout pour avoir le support du checkout sparse.
