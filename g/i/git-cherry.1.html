NOM

git-cherry - Trouver les commits qui n'ont pas encore été appliqués à l'amont

SYNTAXE

git cherry [-v] [<upstream> [<head> [<limit>]]]

DESCRIPTION

Détermine s'il existe des commits dans <head>..<upstream> qui sont équivalents à ceux de la plage <limit>..<head>.

Le test d'équivalence est basé sur la différence, après suppression des espaces et des numéros de ligne. git-cherry détecte donc quand des commits ont été "copiés" par le biais de git-cherry-pick(1), git-am(1) ou git-rebase(1).

Affiche le SHA1 de chaque commit dans <limit>..<head>, précédé de - pour les commits qui ont un équivalent dans <upstream>, et de + pour les commits qui n'en ont pas.

OPTIONS

-v

Affiche les sujets des commits à côté des SHA1.

<upstream>

Branche amont à rechercher pour les commits équivalents. Par défaut, il s'agit de la branche amont de HEAD.

<head>

Branche de travail ; par défaut, HEAD.

<limit>

Ne pas signaler les commits jusqu'à (et y compris) limit.

EXEMPLES

Flux de travail avec des patchs

git-cherry est fréquemment utilisé dans les flux de travail basés sur des patchs (voir gitworkflows(7)) pour déterminer si une série de patchs a été appliquée par le mainteneur en amont. Dans un tel flux de travail, vous pourriez créer et envoyer une branche de sujet comme ceci :

$ git checkout -b topic origin/master
# travailler et créer quelques commits
$ git format-patch origin/master
$ git send-email ... 00*

Plus tard, vous pouvez voir si vos modifications ont été appliquées en disant (toujours sur topic) :

$ git fetch  # mettre à jour votre notion de origin/master
$ git cherry -v

Exemple concret

Dans une situation où topic comprenait trois commits, et que le mainteneur en a appliqué deux, la situation pourrait ressembler à ceci :

$ git log --graph --oneline --decorate --boundary origin/master...topic
* 7654321 (origin/master) dernier commit en amont
[... extraits d'autres commits ...]
* cccc111 cherry-pick de C
* aaaa111 cherry-pick de A
[... extraits de nombreux autres événements ...]
| * cccc000 (topic) commit C
| * bbbb000 commit B
| * aaaa000 commit A
|/
o 1234567 point de branche

Dans de tels cas, git-cherry montre un résumé concis de ce qui doit encore être appliqué :

$ git cherry origin/master topic
- cccc000... commit C
+ bbbb000... commit B
- aaaa000... commit A

Ici, nous voyons que les commits A et C (marqués avec -) peuvent être supprimés de votre branche topic lorsque vous la réalignez sur origin/master, tandis que le commit B (marqué avec +) doit encore être conservé afin qu'il soit envoyé pour être appliqué à origin/master.

Utilisation d'une limite

La <limit> optionnelle est utile dans les cas où votre sujet repose sur d'autres travaux qui ne sont pas dans l'amont. En développant l'exemple précédent, cela pourrait ressembler à ceci :

$ git log --graph --oneline --decorate --boundary origin/master...topic
* 7654321 (origin/master) dernier commit en amont
[... extraits d'autres commits ...]
* cccc111 cherry-pick de C
* aaaa111 cherry-pick de A
[... extraits de nombreux autres événements ...]
| * cccc000 (topic) commit C
| * bbbb000 commit B
| * aaaa000 commit A
| * 0000fff (base) trucs non publiés F
[... extraits ...]
| * 0000aaa trucs non publiés A
|/
o 1234567 base de fusion entre l'amont et topic

En spécifiant base comme limite, vous pouvez éviter de lister les commits entre base et topic :

$ git cherry origin/master topic base
- cccc000... commit C
+ bbbb000... commit B
- aaaa000... commit A
