DESCRIPTIO

N

git-annex permet de gérer des fichiers avec git, sans ajouter le contenu des fichiers à git. Bien que cela puisse sembler paradoxal, c'est utile lorsqu'on traite des fichiers plus grands que ce que git peut facilement gérer actuellement, que ce soit en raison de limitations de la mémoire, du temps de calcul des sommes de contrôle, ou de l'espace

disque.

Même sans suivi du contenu des fichiers, pouvoir gérer des fichiers avec git, déplacer des fichiers et supprimer des fichiers avec des arbres de répertoires versionnés, et utiliser des branches et des clones distribués, sont toutes de très bonnes raisons d'utiliser git. Et les fichiers annexés peuvent coexister dans le même dépôt git avec des fichiers versionnés normalement, ce qui est pratique pour maintenir des documents, Makefiles, etc. associés aux fichiers annexés mais qui bénéficient d'un contrôle de révision

complet.

Lorsqu'un fichier est annexé, son contenu est déplacé dans un magasin clé-valeur, et un lien symbolique est créé qui pointe vers le contenu. Ce

s liens symboliques sont ajoutés à git et versionnés comme des fichiers normaux. Vous pouvez les déplacer, les supprimer, etc. Pousser vers un a
utre dépôt git rendra git-annex conscient du fichier annexé, et il pourra être utilisé pour récupérer son contenu depuis le magasin clé-valeur.

CONFIGURATION

Comme les autres commandes git, git-annex est configuré via .git/config. Ces paramètres, ainsi que les paramètres git config pertinents, sont ceux utilisés par git-annex.

(Certains de ces paramètres peuvent également être définis, pour tous les clones du dépôt, en utilisant git-annex-config. Voir sa page de manuel pour une liste.)

annex.uuid
Un UUID unique pour ce dépôt (défini automatiquement).
annex.backend
Nom du backend clé-valeur par défaut à utiliser lors de l'ajout de nouveaux fichiers au dépôt. Voir git-annex-backends(1) pour des informations sur les backends disponibles.
Ceci est remplacé par la configuration annex annex.backend dans les fichiers .gitattributes, et par l'option --backend.
(Ceci était auparavant nommé annex.backends, et cette valeur sera toujours utilisée si elle est définie.)
annex.securehashesonly
Défini sur vrai pour indiquer que le dépôt ne doit utiliser que des hachages cryptographiquement sécurisés (SHA2, SHA3) et non des hachages non sécurisés (MD5, SHA1) pour le contenu.
Lorsque ceci est défini, le contenu des fichiers utilisant des hachages cryptographiquement non sécurisés ne sera pas autorisé à être ajouté au dépôt.
De plus, git-annex fsck se plaindra de tout fichier présent dans le dépôt qui utilise des hachages non sécurisés. Et, git-annex import --no-content refusera d'importer des fichiers depuis des dépôts spéciaux utilisant des hachages non sécurisés.
Pour configurer le comportement dans les nouveaux clones du dépôt, ceci peut être défini en utilisant git-annex-config.
annex.maxextensionlength
Longueur maximale, en octets, de ce qui est considéré comme une extension de nom de fichier. Ceci est utilisé lors de l'ajout d'un fichier à un backend qui préserve les extensions de nom de fichier, et également lors de la génération d'une branche de visualisation.
La longueur par défaut est de 4, ce qui permet des extensions comme "jpeg". Le point avant l'extension n'est pas compté comme faisant partie de sa longueur.
annex.maxextensions
Nombre maximum d'extensions de nom de fichier à préserver lors de l'utilisation d'un backend qui préserve les extensions de nom de fichier, et également lors de la génération d'une branche de visualisation.
La valeur par défaut est 2, ce qui permet des extensions composées comme ".tar.gz". Lorsqu'elle est définie sur 1, seule la dernière extension est conservée, par exemple ".gz".
annex.diskreserve
Quantité d'espace disque à réserver. L'espace disque est vérifié lors du transfert de contenu annexé pour éviter de manquer d'espace, et un espace libre supplémentaire peut être réservé via cette option, pour laisser de la place à d'autres données (comme les journaux de commit git). Peut être spécifié avec des unités couramment utilisées, par exemple, "0.5 gb", "500M", ou "100 KiloBytes"
La réserve par défaut est de 100 mégaoctets.
annex.fullybalancedthreshhold
Configure le pourcentage de remplissage qu'un dépôt doit atteindre pour que l'expression de contenu préféré "fullybalanced" le considère comme plein. La valeur par défaut est 90.
annex.skipunknown
Défini sur vrai pour que les commandes comme "git-annex get" ignore silencieusement les éléments qui sont listés sur la ligne de commande, mais qui ne sont pas dans le git.
Défini sur faux pour que les commandes comme "git-annex get" échouent si elles doivent opérer sur des fichiers qui ne sont pas dans le git. (C'est le comportement par défaut dans les versions récentes de git-annex.)
Notez que, lorsque annex.skipunknown est faux, une commande comme "git-annex get ." échouera si aucun fichier du répertoire courant n'est dans le git. Les commandes comme "git-annex get foo/" échoueront si aucun fichier du répertoire n'est dans le git, mais si au moins un fichier l'est, elles ignoreront les autres fichiers qui ne le sont pas. Tout ceci est identique au comportement de "git-ls-files --error-unmatch".
Notez également que git-annex ignore les fichiers qui sont dans le git, mais ne sont pas des fichiers annexés ; ce paramètre n'affecte pas cela.
annex.largefiles
Utilisé pour configurer quels fichiers sont suffisamment grands pour être ajoutés à l'annexe. C'est une expression qui correspond aux gros fichiers, par exemple "include=*.mp3 or largerthan=500kb". Voir git-annex-matching-expression(1) pour des détails sur la syntaxe.
Remplace tous les attributs annex.largefiles dans les fichiers .gitattributes.
Pour configurer un annex.largefiles par défaut pour tous les clones du dépôt, cela peut être défini dans git-annex-config(1).
Ceci configure le comportement de git-annex et de git lors de l'ajout de fichiers au dépôt. Par défaut, git-annex add ajoute tous les fichiers à l'annexe (sauf les fichiers cachés et les fichiers dans les répertoires cachés), et git add ajoute les fichiers à git (sauf s'ils ont été ajoutés à l'annexe précédemment). Lorsque annex.largefiles est configuré, git annex add et git add ajouteront les gros fichiers correspondants à l'annexe, et les autres fichiers à git.
D'autres commandes git-annex respectent également annex.largefiles, notamment git annex import, git annex addurl, git annex importfeed, git annex assist, et git-annex assistant.
annex.dotfiles
Normalement, les fichiers cachés (dotfiles) et les fichiers à l'intérieur des répertoires cachés (dotdirs) sont supposés être des fichiers de configuration comme .gitignore, dont le contenu doit toujours faire partie du dépôt git, ils ne seront donc pas ajoutés à l'annexe. Définir annex.dotfiles sur vrai fait que ces fichiers sont ajoutés à l'annexe comme n'importe quel autre fichier.
Pour annexer seulement certains fichiers cachés, définissez ceci et configurez annex.largefiles pour correspondre à ceux que vous voulez. Par exemple, pour correspondre uniquement aux fichiers cachés se terminant par ".big"

git config annex.largefiles "(include=.*.big or include=*/.*.big) or (exclude=.* and exclude=*/.*)"
git config annex.dotfiles true
Pour configurer un annex.dotfiles par défaut pour tous les clones du dépôt, cela peut être défini dans git-annex-config(1).

Définir ceci sur faux empêchera git add d'ajouter des fichiers à l'annexe, malgré la configuration annex.largefiles.

Contrôle si les petits fichiers (fichiers ne correspondant pas à annex.largefiles, ou fichiers cachés) doivent être ajoutés à git par git annex add. La valeur par défaut est vraie ; définissez sur faux pour que les petits fichiers soient plutôt ignorés.

Les commandes comme git-annex add ajoutent par défaut les fichiers au dépôt sous forme verrouillée. Ceci peut les faire ajouter les fichiers sous forme déverrouillée, comme si git-annex-unlock(1) avait été exécuté sur les fichiers.
Ceci peut être défini sur "true" pour ajouter tout déverrouillé, ou cela peut être une expression plus complexe qui correspond aux fichiers par nom, taille ou contenu. Voir git-annex-matching-expression(1) pour des détails.
Pour configurer un annex.addunlocked par défaut pour tous les clones du dépôt, cela peut être défini dans git-annex-config(1).

fonctionner.

dépôt.

Lustre.

emptor.

Ceci est utile si le programme git-annex-shell est en dehors du PATH ou a un nom non standard.
remote.<name>.annex-ignore
S'il est défini sur true, empêche git-annex de stocker ou de récupérer le contenu des fichiers annexés sur ce distant par défaut. (Vous pouvez toujours demander son utilisation avec les options --from et --to.)
Ceci est utile, par exemple, si le distant est situé quelque part sans git-annex-shell. (Par exemple, s'il est sur GitHub). Ou, cela pourrait être utilisé si la connexion réseau entre deux dépôts est trop lente pour être utilisée normalement.

remote.<name>.annex-ignore-command
S'il est défini, la commande est exécutée, et si elle se termine avec un code non nul, c'est le même effet que la définition de annex-ignore à true. Cela permet de contrôler le comportement en fonction, par exemple, du réseau actuel.
remote.<name>.annex-sync
S'il est défini sur false, empêche git-annex sync (et git-annex pull, git-annex push, git-annex assist, et l'assistant git-annex) d'opérer sur ce distant par défaut.
remote.<name>.annex-sync-command
S'il est défini, la commande est exécutée, et si elle se termine avec un code non nul, c'est le même effet que la définition de annex-sync à false. Cela permet de contrôler le comportement en fonction, par exemple, du réseau actuel.
remote.<name>.annex-pull
S'il est défini sur false, empêche git-annex pull, git-annex sync, git-annex assist et l'assistant git-annex de jamais tirer (ou récupérer) du distant.
remote.<name>.annex-push
S'il est défini sur false, empêche git-annex push, git-annex sync, git-annex assist et l'assistant git-annex de jamais pousser vers le distant.
remote.<name>.annex-readonly
S'il est défini sur true, empêche git-annex d'apporter des modifications à un distant. Cela empêche git-annex sync et git-annex assist de pousser des modifications vers un dépôt git. Et cela empêche de stocker ou de supprimer des fichiers d'un distant en lecture seule.
remote.<name>.annex-verify, annex.verify
Par défaut, git-annex vérifie les sommes de contrôle des objets téléchargés à partir des distants. Si vous faites confiance à un distant et ne souhaitez pas le surcoût de ces sommes de contrôle, vous pouvez définir cette option sur false.
Notez que même lorsque cette option est définie sur false, git-annex effectue une vérification dans certains cas limites, où il est probable qu'un objet ait été téléchargé incorrectement, ou lorsque cela est nécessaire pour la sécurité.
remote.<name>.annex-fastcopy, annex.fastcopy
Défini sur "true" pour optimiser la copie de fichiers vers/depuis un distant.
Définir cela permet à cp d'utiliser l'appel système copy_file_range. (Lorsque la commande cp le supporte.) Le bénéfice dépend du système de fichiers. Par exemple, sur NFS, cela peut permettre une copie côté serveur. Sur ext4, cela évite une partie de la surcharge de transfert mémoire, mais le fichier doit toujours être copié. Il n'y a aucun bénéfice sur btrfs, car git-annex fait par défaut un reflinkage CoW (Copy-on-Write) équivalent et rapide sur btrfs.
Cela n'améliorera que peu la vitesse de copie lorsque git-annex doit lire le fichier copié pour le vérifier. Donc, pour une vitesse maximale, en plus de définir cette option, définissez remote.<name>.annex-verify ou annex.verify sur false.
Actuellement, définir cette option empêche la reprise des copies interrompues là où elles en étaient. Une copie interrompue sera relancée depuis le début.
remote.<name>.annex-tracking-branch
Ceci est destiné à être utilisé avec des distants spéciaux qui supportent les exportations et les importations.
Lorsqu'il est défini sur, par exemple, "master", cela indique à git-annex que vous souhaitez que le distant spécial suive cette branche.
Lorsqu'il est défini sur, par exemple, "master:subdir", le distant spécial ne suit que le sous-répertoire de cette branche.
Définir cela permet à d'autres commandes de fonctionner avec ces distants spéciaux : git-annex pull importera les modifications du distant et les fusionnera dans la annex-tracking-branch. Et git-annex push exportera les modifications vers le distant. Les commandes de plus haut niveau git-annex sync --content et git-annex assist importent et exportent les deux.
remote.<name>.annex-export-tracking
Nom obsolète pour remote.<name>.annex-tracking-branch. Sera toujours utilisé s'il est configuré et que remote.<name>.annex-tracking-branch ne l'est pas.
remote.<name>.annexUrl
Peut être utilisé pour spécifier une URL différente de l'URL normale remote.<name>.url pour que git-annex accède au distant. Similaire à pushUrl utilisé par git-push.
Lorsque ceci est défini sur une URL annex+http ou annex+https, cette URL est utilisée uniquement pour les opérations git-annex, et l'URL remote.<name>.url est utilisée pour les opérations git. Cela permet d'utiliser git-annex-p2phttp pour servir un dépôt git-annex sur http.
Lorsque ceci et remote.<name>.url contiennent le même nom d'hôte, et que ceci est une URL annex+http(s) et que l'autre est également une URL http(s), git-annex suppose que le même nom d'utilisateur et mot de passe peuvent être utilisés pour les deux URL. Lorsque la mise en cache des mots de passe est configurée, cela vous permet de n'être invité qu'une seule fois pour un mot de passe lors de l'utilisation de git et de git-annex. Voir gitcredentials(7) pour savoir comment configurer la mise en cache des mots de passe.

L'URL réécrite est utilisée par git-annex pour accéder au distant, et fonctionne de la même manière que remote.<name>.annexUrl, y compris la prise en charge des URL annex+http.
Notez que git-annex prend également en charge la configuration url.<base>.insteadOf de git. Lorsque les deux sont définies, l'URL du distant est d'abord réécrite par insteadOf, et cette URL réécrite peut ensuite être réécrite davantage en utilisant annexInsteadOf.

remote.<name>.annex-stalldetection, annex.stalldetection
La configuration de ceci permet de détecter et de gérer les transferts bloqués ou trop lents, de sorte qu'au lieu de rester bloqué, git-annex annulera l'opération bloquée. Le transfert sera considéré comme échoué, de sorte que les paramètres tels que annex.retry contrôleront l'action suivante.
Par défaut, la détection automatique des transferts qui sont probablement bloqués est activée, et il est suggéré de configurer ceci, mais les opérations bloquées ne sont pas annulées. Pour que cela fonctionne, un distant doit mettre à jour sa progression de manière cohérente. Les distants qui ne le font pas ne bénéficieront pas de la détection automatique des blocages. Et il peut s'écouler un certain temps avant que git-annex ne décide qu'un distant est réellement bloqué lors de l'utilisation de la détection automatique des blocages, car il doit être prudent quant à ce qui ressemble à un blocage.
Défini sur "false" pour éviter toute tentative de détection de blocage.
Pour détecter et annuler les transferts bloqués, définissez ceci sur une valeur de la forme "$montant/$périodetemps" qui spécifie la quantité de données que git-annex devrait s'attendre à voir circuler, minimum, sur une période donnée.
Par exemple, pour détecter des blocages purs où aucune donnée n'a été transférée après 30 secondes : git config annex.stalldetection "1KB/30s"
Ou, si vous avez une copie distante sur un lecteur USB capable normalement de plusieurs mégaoctets par seconde, mais qui a des secteurs défectueux où il se bloque longtemps, vous pourriez utiliser : git config remote.usbdrive.annex-stalldetection "1MB/1m"
Certaines copies distantes ne rapportent pas la progression du transfert, et les blocages ne peuvent pas être détectés lors de leur utilisation.
Certaines copies distantes ne rapportent la progression du transfert qu'occasionnellement, par exemple après chaque morceau. Pour éviter les timeouts erronés dans une telle situation, si la première mise à jour de progression met plus de temps à arriver que la période de temps configurée, la détection de blocage sera automatiquement ajustée pour utiliser une période de temps plus longue. Par exemple, si la première mise à jour de progression arrive après 10 minutes, mais que annex.stalldetection est "1MB/1m", elle sera traitée comme par exemple "30MB/30m".
La configuration de la détection de blocage peut amener git-annex à utiliser plus de ressources. Pour pouvoir annuler les blocages, git-annex doit exécuter les transferts dans des processus séparés (un par travail simultané). Il peut donc avoir besoin d'ouvrir plus de connexions à une copie distante que d'habitude, ou la communication avec ces processus peut le rendre un peu plus lent.

Détection de blocage pour les téléchargements depuis une copie distante.

Alors une commande comme git-annex get se rabattra sur le téléchargement depuis la copie distante à vitesse moyenne.

Généralement, ceci est configuré en exécutant git-annex-extendcluster.

Lorsque ceci est défini sur true, aucune information sur la copie distante ne sera enregistrée dans la branche git-annex. Ceci est principalement utile pour les copies distantes spéciales, et est défini lors de l'utilisation de git-annex-initremote(1) avec l'option --private.
remote.<nom>.annex-max-git-bundles, annex.max-git-bundles
Lors de l'utilisation de git-remote-annex pour stocker un dépôt git dans une copie distante spéciale, ce paramètre configure le nombre d'objets de bundle git séparés à stocker dans la copie distante spéciale avant de re-téléverser un seul bundle git contenant l'intégralité du dépôt git.
La valeur par défaut est 100, visant à éviter des re-téléversements fréquents, tout en empêchant un clone ou un fetch de devoir télécharger trop d'objets. Définir à 0 pour désactiver le re-téléversement.

Définir ceci sur true permet d'utiliser git-remote-annex pour pousser le dépôt git vers une copie distante spéciale cryptée.
Ceci n'est pas autorisé par défaut, car il est impossible de faire un git clone depuis une copie distante spéciale cryptée, car elle nécessite des clés de cryptage stockées sur la copie distante. Donc, soyez prudent si vous définissez ceci, et ne vous fiez pas à la copie distante spéciale cryptée comme seule copie de votre dépôt git.

Peut être utilisé pour indiquer à git-annex si une copie distante est un dépôt nu ou non. Normalement, git-annex le détermine automatiquement.

gitattributes

Le backend clé-valeur utilisé lors de l'ajout d'un nouveau fichier à l'annexe peut être configuré par type de fichier via les fichiers .gitattributes. Dans le fichier, l'attribut annex.backend peut être défini au nom du backend à utiliser. (Voir git-annex-backends(1) pour des informations sur les backends disponibles.) Par exemple, voici comment utiliser le backend WORM par défaut, mais le backend SHA256E pour les fichiers ogg

:


* annex.backend=WORM
*.ogg annex.

backend=SHA256E

Il existe un attribut annex.largefiles, qui est utilisé pour configurer quels fichiers sont assez grands pour être ajoutés à l'annexe. Puisque les attributs ne peuvent pas contenir d'espaces, il est difficile de l'utiliser pour des paramètres annex.largefiles plus complexes. Définir annex.largefiles dans git-annex-config(1) est une manière plus facile de le configurer pour toutes les clones du dépôt. Voir git-annex-matching-expression(1) pour des détails sur la

syntaxe.

Les paramètres numcopies et mincopies peuvent aussi être configurés par type de fichier via les attributs annex.numcopies et annex.mincopies dans les fichiers .gitattributes. Cela remplace les autres paramètres. Par exemple, cela rend deux copies nécessaires pour les fichiers wav et 3 copies pour les fichiers flac

:


*.wav annex.numcopies=2
*.flac annex.

numcopies=3

Ces paramètres sont pris en compte par git-annex chaque fois qu'il opère sur un fichier correspondant. Cependant, lors de l'utilisation de --all, --unused, ou --key pour spécifier les clés sur lesquelles opérer, git-annex opère sur des clés et non des fichiers, il ne prend donc pas en compte les paramètres de .gitattributes. Pour cette raison, les commandes git annex numcopies et git annex mincopies sont utiles pour configurer une valeur par défaut

globale.

Notez aussi que lors de l'utilisation des vues, seul le fichier .

gitattributes de premier niveau est préservé dans la vue, donc l
es autres paramètres dans d'autres fichiers n'auront aucun effet.
