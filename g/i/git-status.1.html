DESCRIPTIO

N

Affiche les chemins qui présentent des différences entre le fichier d'index et le commit HEAD actuel, les chemins qui présentent des différences entre l'arbre de travail et le fichier d'index, et les chemins de l'arbre de travail qui ne sont pas suivis par Git (et qui ne sont pas ignorés par gitignore(5)). Les premiers sont ceux que vous committeriez en exécutant git commit ; les deuxièmes et troisièmes sont ceux que vous pourriez committer en exécutant git add avant d'exécuter git comm

-u[<mode>], --untracked-files[=<mode>

Affiche les fichiers non suivis.

Le paramètre mode est utilisé pour spécifier le traitement des fichiers non suivis. Il est facultatif : il vaut par défaut all, et s'il est spécifié, il doit être collé à l'option (par ex. -uno, mais pas -u no)

Les options possibles sont

•no - N'affiche aucun fichier non

•normal - Affiche les fichiers et répertoires non

•all - Affiche également les fichiers individuels dans les répertoires non

Lorsque l'option -u n'est pas utilisée, les fichiers et répertoires non suivis sont affichés (c'est-à-dire la même chose que de spécifier normal), pour vous aider à ne pas oublier d'ajouter les fichiers nouvellement créés. Comme cela demande un effort supplémentaire pour trouver les fichiers non suivis dans le système de fichiers, ce mode peut prendre du temps dans un grand arbre de travail. Envisagez d'activer le cache non suivi et l'index divisé si pris en charge (voir git update-index --untracked-cache et git update-index --split-index), sinon vous pouvez utiliser no pour que git status retourne plus rapidement sans afficher les fichiers non suivis. Toutes les orthographes habituelles pour la valeur booléenne true sont considérées comme normal et false comme no

La valeur par défaut peut être modifiée à l'aide de la variable de configuration status.showUntrackedFiles documentée dans git-con

--ignore-submodules[=<when>

]
Ignore les changements des sous-modules lors de la recherche de changements. <when> peut être "none", "untracked", "dirty" ou "all", qui est la valeur par défaut. L'utilisation de "none" considérera le sous-module comme modifié lorsqu'il contient des fichiers non suivis ou modifiés ou que son HEAD diffère du commit enregistré dans le superprojet, et peut être utilisé pour remplacer tout paramètre de l'option ignore dans git-config(1) ou gitmodules(5). Lorsque "untracked" est utilisé, les sous-modules ne sont pas considérés comme sales lorsqu'ils ne contiennent que du contenu non suivi (mais ils sont quand même analysés pour du contenu modifié). L'utilisation de "dirty" ignore tous les changements de l'arbre de travail des sous-modules, seuls les changements des commits stockés dans le superprojet sont affichés (c'était le comportement avant 1.7.0). L'utilisation de "all" masque tous les changements des sous-modules (et supprime la sortie des résumés de sous-modules lorsque l'option de configuration status.submoduleSummary est définie)
.

SORTI

E

La sortie de cette commande est conçue pour être utilisée comme commentaire de modèle de commit. Le format long par défaut est conçu pour être lisible par l'homme, verbeux et descriptif. Son contenu et son format sont susceptibles de changer à tout

moment.

Les chemins mentionnés dans la sortie, contrairement à de nombreuses autres commandes Git, sont rendus relatifs au répertoire courant si vous travaillez dans un sous-répertoire (c'est fait exprès, pour faciliter le copier-coller). Voir l'option de configuration status.relativePaths

ci-dessous.

Format

court

Dans le format court, l'état de chaque chemin est affiché sous l'une de ces

formes 
XY PATH
X
Y ORIG_PAT
H -> PATH

où ORIG_PATH est l'origine du contenu renommé/copié. ORIG_PATH n'est affiché que lorsque l'entrée est renommée ou copiée. Le XY est un code d'état à deux

lettres.

Les champs (y compris le ->) sont séparés les uns des autres par une seule espace. Si un nom de fichier contient des espaces ou d'autres caractères non imprimables, ce champ sera mis entre guillemets à la manière d'une chaîne littérale C : entouré de guillemets doubles ASCII (34), et avec les caractères spéciaux intérieurs échappés par une barre oblique

inverse.

Il existe trois types d'états différents qui sont affichés à l'aide de ce format, et chacun utilise la syntaxe XY différemment

:
•Lorsqu'une fusion est en cours et que la fusion a réussi, ou en dehors d'une situation de fusion, X affiche l'état de l'index et Y affiche l'état de l'arbre de
travail.
•Lorsqu'un conflit de fusion s'est produit et n'a pas encore été résolu, X et Y affichent l'état introduit par chaque tête de la fusion, par rapport à l'ancêtre commun. Ces chemins sont dits non fusio
nnés.
•Lorsqu'un chemin n'est pas suivi, X et Y sont toujours identiques, car ils sont inconnus de l'index. ?? est utilisé pour les chemins non suivis. Les fichiers ignorés ne sont pas listés sauf si --ignored est utilisé ; si c'est le cas, les fichiers ignorés sont indiqués par !!
.

Notez que le terme fusion ici inclut également les rebase utilisant la stratégie de fusion par défaut, les cherry-picks, et tout autre processus utilisant le mécanisme de

fusion.

Format Porcelaine Version

1

Le format porcelaine version 1 est similaire au format court, mais il est garanti de ne pas changer de manière incompatible avec les versions antérieures de Git ou en fonction de la configuration de l'utilisateur. Cela le rend idéal pour l'analyse par des scripts. La description du format ci-dessus décrit également le format porcelaine, avec quelques exceptions

:
1.La configuration color.status de l'utilisateur n'est pas respectée ; la couleur sera toujours
désactivée.
2.La configuration status.relativePaths de l'utilisateur n'est pas respectée ; les chemins affichés seront toujours relatifs à la racine du
dépôt.

Il existe également un format -z alternatif recommandé pour l'analyse par machine. Dans ce format, le champ de statut est le même, mais certaines autres choses changent. D'abord, le -> est omis des entrées de renommage et l'ordre des champs est inversé (par ex. de -> vers devient vers de). Deuxièmement, un NUL (ASCII 0) suit chaque nom de fichier, remplaçant l'espace comme séparateur de champ et la nouvelle ligne de fin (mais un espace sépare toujours le champ de statut du premier nom de fichier). Troisièmement, les noms de fichiers contenant des caractères spéciaux ne sont pas mis en forme spécialement ; aucune mise entre guillemets ni échappement par antislash n'est

effectué.

Tous les changements de sous-module sont rapportés comme modifiés M au lieu de m ou d'un simple

?
.

Format Porcelaine Version

2

Le format version 2 ajoute des informations plus détaillées sur l'état de l'arbre de travail et des éléments modifiés. La version 2 définit également un ensemble extensible d'en-têtes facultatifs faciles à

analyser.

Les lignes d'en-tête commencent par "#" et sont ajoutées en réponse à des arguments spécifiques de la ligne de commande. Les analyseurs doivent ignorer les en-têtes qu'ils ne reconnaissent

pas.

CONFIGURATIO

N

La commande respecte color.status (ou status.color — elles signifient la même chose et la seconde est conservée pour la rétrocompatibilité) et color.status.<emplacement> pour coloriser sa

sortie.

Si la variable de configuration status.relativePaths est définie sur false, alors tous les chemins affichés sont relatifs à la racine du dépôt, et non au répertoire

courant.

Si status.submoduleSummary est défini sur un nombre non nul ou true (identique à -1 ou un nombre illimité), le résumé du sous-module sera activé pour le format long et un résumé des commits pour les sous-modules modifiés sera affiché (voir l'option --summary-limit de git-submodule(1)). Veuillez noter que la sortie de résumé de la commande status sera supprimée pour tous les sous-modules lorsque diff.ignoreSubmodules est défini sur all ou uniquement pour les sous-modules où submodule.<nomgt;.ignore=all. Pour voir également le résumé des sous-modules ignorés, vous pouvez soit utiliser l'option en ligne de commande --ignore-submodules=dirty, soit la commande git submodule summary, qui affiche une sortie

similaire mais ne tient pas
compte de ces paramètres.

ACTUALISATION EN

ARRIÈRE-PLAN

Par défaut, git status actualisera automatiquement l'index, mettant à jour les informations de statistiques en cache à partir de l'arbre de travail et en écrivant le résultat. L'écriture de l'index mis à jour est une optimisation qui n'est pas strictement nécessaire (status calcule les valeurs lui-même, mais les écrire ne sert qu'à éviter que des programmes ultérieurs ne répètent notre calcul). Lorsque status est exécuté en arrière-plan, le verrou détenu pendant l'écriture peut entrer en conflit avec d'autres processus simultanés, les faisant échouer. Les scripts exécutant status en arrière-plan devraient envisager d'utiliser git --no-optional-locks status (voir git(1) pour pl

us de dé
tails).

FICHIERS NON SUIVIS ET

PERFORMANCES

git status peut être très lent dans de grands arborescences de travail s'il doit rechercher des fichiers et répertoires non suivis. Il existe de nombreuses options de configuration pour accélérer cela, soit en évitant le travail, soit en utilisant les résultats en cache des commandes Git précédentes. Il n'existe pas un ensemble unique de paramètres optimaux adapté à tout le monde. Nous allons lister un résumé des options pertinentes pour vous aider, mais avant d'entrer dans le détail de la liste, vous voudrez peut-être exécuter git status à nouveau, car votre configuration met peut-être déjà en cache les résultats de git status, il pourrait donc être plus rapide lors des exécutions

suivantes.
•Le drapeau --untracked-files=no ou la configuration status.showUntrackedFiles=no (voir ci-dessus pour les deux) : indiquent que git status ne doit pas signaler les fichiers non suivis. C'est l'option la plus rapide. git status ne listera pas les fichiers non suivis, vous devez donc faire attention à vous souvenir si vous créez de nouveaux fichiers et à les ajouter manuellement avec git add
.
•advice.statusUoption=false (voir git-config(1)) : définir cette variable à false désactive le message d'avertissement donné lorsque l'énumération des fichiers non suivis prend plus de 2 secondes. Dans un grand projet, cela peut prendre plus de temps et l'utilisateur a peut-être déjà accepté ce compromis (par exemple, utiliser "-uno" peut ne pas être une option acceptable pour l'utilisateur), auquel cas, il n'y a pas lieu d'émettre le message d'avertissement, et dans un tel cas, désactiver l'avertissement peut être la meilleure
solution.
•core.untrackedCache=true (voir git-update-index(1)) : active la fonctionnalité de cache des fichiers non suivis et ne recherche que les répertoires qui ont été modifiés depuis la commande git status précédente. Git se souvient de l'ensemble des fichiers non suivis dans chaque répertoire et suppose que si un répertoire n'a pas été modifié, alors l'ensemble des fichiers non suivis qu'il contient n'a pas changé. C'est beaucoup plus rapide que d'énumérer le contenu de chaque répertoire, mais cela a tout de même un coût, car Git doit toujours rechercher l'ensemble des répertoires modifiés. Le cache des fichiers non suivis est stocké dans le fichier .git/index. La réduction du coût de la recherche des fichiers non suivis est partiellement compensée par la taille accrue de l'index et le coût de sa mise à jour. Ce temps de recherche réduit vaut généralement la taille
supplémentaire.
•core.untrackedCache=true et core.fsmonitor=true ou core.fsmonitor=<chemin-de-la-commande-hook> (voir git-update-index(1)) : active à la fois les fonctionnalités de cache des fichiers non suivis et de FSMonitor et ne recherche que les répertoires qui ont été modifiés depuis la commande git status précédente. C'est plus rapide que d'utiliser seulement le cache des fichiers non suivis, car Git peut aussi éviter de rechercher les répertoires modifiés. Git n'a qu'à énumérer l'ensemble exact des répertoires qui ont changé récemment. Bien que la fonctionnalité FSMonitor puisse être activée sans le cache des fichiers non suivis, les avantages sont fortement réduits dans ce
cas.

Notez qu'après avoir activé les fonctionnalités de cache des fichiers non suivis et/ou de FSMonitor il peut falloir quelques commandes git status pour que les différents caches soient préchauffés avant

que vous ne voyiez des temps d'e
xécution améliorés. C'est normal.
