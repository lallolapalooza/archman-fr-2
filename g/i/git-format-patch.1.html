--relative[=<chemin>], --no-relative

Lorsqu'il est exécuté depuis un sous-répertoire du projet, il peut être informé d'exclure les modifications extérieures au répertoire et d'afficher les noms de fichiers relatifs à celui-ci avec cette option. --textconv, --no-textconv

Autoriser (ou interdire) l'exécution de filtres de conversion de texte externes lors de la comparaison de fichiers binaires. Voir gitattributes(5) pour plus de détails. Comme les filtres textconv sont généralement une conversion unidirectionnelle, le diff résultant est adapté à la consommation humaine, mais ne peut pas être appliqué. Pour cette raison, les filtres textconv sont activés par défaut uniquement pour git-diff(1) et git-log(1), mais pas pour git-format-patch(1) ou les commandes de bas niveau de diff.

--ignore-submodules[=(none|untracked|dirty|all)]

Ignorer les modifications apportées aux sous-modules lors de la génération du diff. all est la valeur par défaut. L'utilisation de none considérera le sous-module modifié s'il contient des fichiers non suivis ou modifiés ou si son HEAD diffère du commit enregistré dans le super-projet et peut être utilisée pour remplacer tous les paramètres de l'option ignore dans git-config(1) ou gitmodules(5). Lorsque untracked est utilisé, les sous-modules ne sont pas considérés comme sales s'ils ne contiennent que du contenu non suivi (mais ils sont toujours analysés pour le contenu modifié). L'utilisation de dirty ignore toutes les modifications apportées à l'arborescence de travail des sous-modules, seules les modifications des commits stockés dans le super-projet sont affichées (c'était le comportement jusqu'à la version 1.7.0). L'utilisation de all masque toutes les modifications apportées aux sous-modules.

--dst-prefix=<prefix>

Afficher le préfixe de destination <prefix> donné au lieu de "b/".

--no-prefix

Ne pas afficher de préfixe source ou de destination.

--default-prefix

Utiliser les préfixes source et destination par défaut ("a/" et "b/"). Cela remplace les variables de configuration telles que diff.noprefix, diff.srcPrefix, diff.dstPrefix, et diff.mnemonicPrefix (voir git-config(1)).

--line-prefix=<prefix>

Ajouter un <prefix> supplémentaire à chaque ligne de sortie.

--ita-invisible-in-index

Par défaut, les entrées ajoutées par git add -N apparaissent comme un fichier vide existant dans git diff et un nouveau fichier dans git diff --cached. Cette option fait apparaître l'entrée comme un nouveau fichier dans git diff et comme inexistant dans git diff --cached. Cette option peut être annulée avec --ita-visible-in-index. Ces deux options sont expérimentales et pourraient être supprimées à l'avenir.

--max-depth=<profondeur>

Pour chaque pathspec donné sur la ligne de commande, descendre au maximum <profondeur> niveaux de répertoires. Une valeur de -1 signifie aucune limite. Ne peut pas être combiné avec des caractères génériques dans le pathspec. Étant donné un arbre contenant foo/bar/baz, la liste suivante montre les correspondances générées par chaque ensemble d'options :
•--max-depth=0 -- foo : foo
•--max-depth=1 -- foo : foo/bar
•--max-depth=1 -- foo/bar : foo/bar/baz
•--max-depth=1 -- foo foo/bar : foo/bar/baz
•--max-depth=2 -- foo : foo/bar/baz

Si aucun pathspec n'est donné, la profondeur est mesurée comme si toutes les entrées de niveau supérieur étaient spécifiées. Notez que c'est différent de mesurer à partir de la racine, dans la mesure où --max-depth=0 renverrait toujours foo. Cela vous permet de toujours limiter la profondeur tout en demandant un sous-ensemble des entrées de niveau supérieur.

Notez que cette option n'est prise en charge que pour les diffs entre objets de type arbre, pas contre l'index ou l'arborescence de travail.

Pour une explication plus détaillée de ces options courantes, voir également gitdiffcore(7).

DISCUSSIO

N

Le patch produit par git format-patch est au format de boîte aux lettres UNIX, avec un horodatage "magique" fixe pour indiquer que le fichier est produit par format-patch plutôt que par une vraie boîte aux lettres, comme ceci

: 
From 8f72bad1baf19a53459661343e21d6491c3908d3 Mon Sep 17 00:00:00 2001
From: Tony Luck <tony.luck@intel.com>
Date: Tue, 13 Jul 2010 11:42:54 -0700
Subject: [PATCH] =?UTF-8?q?[IA64]=20Put=20ia64=20config=20files=20on=20the=20?=
 =?UTF-8?q?Uwe=20Kleine-K=C3=B6nig=20diet?=
MIME-Version: 1.0
Content-Type: text/plain; charset=UTF-8
Content-Transfer-Encoding: 8bit
arch/arm config files were slimmed down using a python script
(See commit c2330e286f68f1c408b4aa6515ba49d57f05beae comment)
Do the same for ia64 so we can have sleek & trim looking
.
.
.

Typiquement, il sera placé dans le dossier des brouillons d'un MUA, modifié pour ajouter des commentaires pertinents qui ne devraient pas figurer dans le journal des modifications après les trois tirets, puis envoyé comme un message dont le corps, dans notre exemple, commence par "arch/arm config files were...". Du côté du destinataire, les lecteurs peuvent enregistrer les patches intéressants dans une boîte aux lettres UNIX et les appliquer avec git-am(

1).

Lorsqu'un patch fait partie d'une discussion en cours, le patch généré par git format-patch peut être ajusté pour tirer parti de la fonctionnalité git am --scissors. Après votre réponse à la discussion vient une ligne qui consiste uniquement en "-- >8 --" (ciseaux et perforation), suivie du patch avec les champs d'en-tête inutiles supprimés

: 
...
> So we should do such-and-such.
Makes sense to me.  How about this patch?
-- >8 --
Subject: [IA64] Put ia64 config files on the Uwe Kleine-König diet
arch/arm config files were slimmed down using a python script
.
.
.

Lors de l'envoi d'un patch de cette manière, il s'agit le plus souvent de votre propre patch, donc en plus du marqueur "From $SHA1 $magic_timestamp", vous devriez omettre les lignes From: et Date: du fichier de patch. Le titre du patch est probablement différent du sujet de la discussion à laquelle le patch répond, donc vous voudrez probablement conserver la ligne Subject:, comme dans l'exemple

ci-dessus.

Vérification de la corruption des

patches

De nombreux logiciels de messagerie, s'ils ne sont pas configurés correctement, corrompront les espaces. Voici deux types de corruption courants

:
•Des lignes de contexte vides qui n'ont aucun
espace.
•Des lignes de contexte non vides qui ont un espace supplémentaire au
début.

Une façon de tester si votre MUA est correctement configuré est

:
•Envoyez le patch à vous-même, exactement comme vous le feriez, sauf avec des lignes To: et Cc: qui ne contiennent ni la liste ni l'adresse du
mainteneur.
•Enregistrez ce patch dans un fichier au format de boîte aux lettres UNIX. Appelez-le a.patch, par
exemple.
•Appliquez-le : 
$ git fetch <project> master:test
-apply $ git switch test-apply $
git restore --source=HEAD --stag
ed --worktree :/ $ git am a.patch

S'il ne s'applique pas correctement, il peut y avoir plusieurs

raisons.
•Le patch lui-même ne s'applique pas proprement. C'est mauvais mais n'a pas grand-chose à voir avec votre MUA. Vous pourriez vouloir rebaser le patch avec git-rebase(1) avant de le régénérer dans ce
cas.
•Le MUA a corrompu votre patch ; "am" se plaindrait que le patch ne s'applique pas. Regardez dans le sous-répertoire .git/rebase-apply/ et voyez ce que contient le fichier de patch et vérifiez les motifs de corruption courants mentionnés
ci-dessus.
Pendant que vous y êtes, vérifiez aussi les fichiers info et final-commit. Si ce qui est dans final-commit n'est pas exactement ce que vous voudriez voir dans le message du journal des commits, il est très probable que le destinataire finira par édite
r manuellement le message du journal lors de l'application de votre patch. Des
choses comme "Hi, this is my first patch.\n" dans le courriel du patch devraie
nt venir après la ligne à trois tirets qui marque la fin du message de commit.

INFORMATIONS DE L'ARBRE DE

BASE

Le bloc d'informations de l'arbre de base est utilisé par les mainteneurs ou les testeurs tiers pour connaître l'état exact auquel la série de patches s'applique. Il se compose du commit de base, qui est un commit bien connu qui fait partie de la partie stable de l'historique du projet à partir de laquelle tout le monde travaille, et de zéro ou plusieurs patches prérequis, qui sont des patches bien connus en cours qui ne font pas encore partie du commit de base et qui doivent être appliqués par-dessus le commit de base dans l'ordre topologique avant que les patches puissent être

appliqués.

Le commit de base est affiché sous la forme "base-commit: " suivi du nom d'objet du commit en hexadécimal sur 40 caractères. Un patch prérequis est affiché sous la forme "prerequisite-patch-id: " suivi de l'identifiant de patch en hexadécimal sur 40 caractères, qui peut être obtenu en passant le patch par la commande git patch-id --stable

.

Imaginez que par-dessus le commit public P, vous avez appliqué des patches bien connus X, Y et Z de quelqu'un d'autre, puis construit votre série de trois patches A, B, C, l'historique ressemblerait à

: 
---P---X---Y---Z---A---B--
-
C

Avec git format-patch --base=P -3 C (ou des variantes de celui-ci, par ex. avec --cover-letter ou en utilisant Z..C au lieu de -3 C pour spécifier la plage), le bloc d'informations de l'arbre de base est affiché à la fin du premier message produit par la commande (soit le premier patch, soit la lettre de couverture), comme ceci

: 
base-commit: P
prerequisite-patch-id: X
prerequisite-patch-id: Y
prerequisite-patch-id:
Z

Pour une topologie non linéaire, telle

que 
---P---X---A---M-
--C \
/ Y---Z---B

Vous pouvez également utiliser git format-patch --base=P -3 C pour générer des patches pour A, B et C, et les identifiants pour P, X, Y, Z sont ajoutés à la fin du premier

message.

Si défini --base=auto dans la ligne de commande, le commit de base sera calculé automatiquement comme la base de fusion du commit de tête de la branche de suivi à distance et de la plage de révisions spécifiée dans la ligne de commande. Pour une branche locale, vous devez la faire suivre une branche distante par git branch --set-upstream-to avant

d'utiliser c
ette option.
