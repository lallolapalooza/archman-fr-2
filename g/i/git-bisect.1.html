Vous l'utilisez en indiquant d'abord un commit « mauvais » (bad) qui est connu pour contenir le bogue, et un commit « bon » (good) qui est connu pour être antérieur à l'introduction du bogue. Ensuite git bisect choisit un commit entre ces deux bornes et vous demande si le commit s électionné est « bon » ou « mauvais ». Il continue à réduire la plage jusqu'à trouver le commit exact qui a introduit le changement. En fait, git bisect peut être utilisé pour trouver le commit qui a changé n'importe quelle

Pour prendre en charge cet usage plus général, les termes « ancien » (old) et « nouveau » (new) peuvent être utilisés à la place de « bon » (good) et « mauvais » (bad), ou vous pouvez choisir vos propres termes. Bisect

skip

Au lieu de choisir vous-même un commit voisin, vous pouvez demander à Git de le faire pour vous en exécutant la commande

Bisect

run

Si vous avez un script qui peut dire si le code source courant est bon ou mauvais, vous pouvez faire une bissection en exécutant la commande

: 
$ git bisect
run my_scri
pt arguments

Notez que le script (my_script dans l'exemple ci-dessus) devrait se terminer avec le code 0 si le code source courant est bon/ancien, et se terminer avec un code entre 1 et 127 (inclus), sauf 125, si le code source courant est mauvais/nouveau

.

Tout autre code de sortie interrompra le processus de bissection. Il faut noter qu'un programme qui se termine via exit(-1) laisse $? = 255, (voir la page de manuel exit(3)), car la valeur est tronquée avec & 0377

.

Le code de sortie spécial 125 devrait être utilisé lorsque le code source courant ne peut pas être testé. Si le script se termine avec ce code, la révision courante sera sautée (voir git bisect skip ci-dessus). 125 a été choisi comme la valeur la plus élevée utilisable à cette fin, car 126 et 127 sont utilisés par les shells POSIX pour signaler des statuts d'erreur spécifiques (127 est pour commande non trouvée, 126 est pour commande trouvée mais non exécutable—ces détails n'ont pas d'importance, car ce sont des erreurs normales dans le script, en ce qui concerne bisect run

).

Vous trouverez souvent que pendant une session de bisect, vous voulez avoir des modifications temporaires (par exemple s/#define DEBUG 0/#define DEBUG 1/ dans un fichier d'en-tête, ou « la révision qui n'a pas ce commit a besoin de ce patch appliqué pour contourner un autre problème auquel cette bissection ne s'intéresse pas ») appliquées à la révision en cours de

test.

Pour faire face à une telle situation, après que le git bisect interne a trouvé la prochaine révision à tester, le script peut appliquer le patch avant de compiler, exécuter le vrai test, et ensuite décider si la révision (éventuellement avec le patch nécessaire) a passé le test, puis remettre l'arbre dans son état pristine. Enfin, le script devrait se terminer avec le statut du vrai test pour permettre à la git bisect run boucle de commande de dét

erminer le résult
at final de la s
ession de bisect.
