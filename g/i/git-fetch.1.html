DESCRIPTIO

N

Récupère les branches et/ou les étiquettes (collectivement, « références ») depuis un ou plusieurs autres dépôts, ainsi que les objets nécessaires pour compléter leurs historiques. Les branches de suivi à distance sont mises à jour (voir la description de <refspec> ci-dessous pour les moyens de contrôler ce comportement)

.

Par défaut, toute étiquette pointant vers les historiques en cours de récupération est également récupérée ; l'effet est de récupérer les étiquettes pointant vers les branches qui vous intéressent. Ce comportement par défaut peut être modifié en utilisant les options --tags ou --no-tags ou en configurant remote.<name>.tagOpt. En utilisant une refspec qui récupère explicitement les étiquettes, vous pouvez récupérer les étiquettes qui ne pointent pas vers des branches qui vous intéressent

également.

git fetch peut récupérer depuis un dépôt nommé unique ou une URL, ou depuis plusieurs dépôts à la fois si <groupe> est donné et qu'il existe une entrée remotes.<groupe> dans le fichier de configuration. (Voir git-config(1))

.

Quand aucun dépôt distant n'est spécifié, par défaut le dépôt distant origin sera utilisé, sauf s'il existe une branche amont configurée pour la branche

courante.

Les noms des références récupérées, ainsi que les noms d'objets vers lesquels elles pointent, sont écrits dans .git/FETCH_HEAD. Ces informations peuvent être utilisées par des scripts ou d'autres commandes git, telles que git-pu

ll(
1).

<repository

Le dépôt « distant » qui est la source d'une opération de récupération ou de tirage. Ce paramètre peut être soit une URL (voir la section GIT URLS ci-dessous) soit le nom d'un distant (voir la section REMOTES ci-dessous)

Un nom faisant référence à une liste de dépôts comme valeur de remotes.<group> dans le fichier de configuration. (Voir git-config(1))

<refspec

>
Spécifie quelles refs récupérer et quelles refs locales mettre à jour. Lorsqu'aucun <refspec> n'apparaît sur la ligne de commande, les refs à récupérer sont lues depuis les variables remote.<repository>.fetch à la place (voir BRANCHES DE SUIVI À DISTANCE CONFIGURÉES ci-dessous).

Le format d'un paramètre <refspec> est un plus optionnel +, suivi de la source <src>, suivi d'un deux-points :, suivi de la destination <dst>. Le deux-points peut être omis lorsque <dst> est vide. <src> est typiquement une ref, ou un motif glob avec une seule * qui est utilisé pour faire correspondre un ensemble de refs, mais cela peut aussi être un nom d'objet hexadécimal entièrement

écrit.

Un <refspec> peut contenir un * dans son <src> pour indiquer une simple correspondance de motif. Un tel refspec fonctionne comme un glob qui correspond à toute ref avec le motif. Un <refspec> de motif doit avoir un et un seul * à la fois dans le <src> et le <dst>. Il fera correspondre les refs à la destination en remplaçant le * par le contenu correspondant de la

source.

Si un refspec est préfixé par ^, il sera interprété comme un refspec négatif. Au lieu de spécifier quelles refs récupérer ou quelles refs locales mettre à jour, un tel refspec spécifiera plutôt les refs à exclure. Une ref sera considérée comme correspondante si elle correspond à au moins un refspec positif et ne correspond à aucun refspec négatif. Les refspecs négatifs peuvent être utiles pour restreindre la portée d'un refspec de motif afin qu'il n'inclue pas de refs spécifiques. Les refspecs négatifs peuvent eux-mêmes être des refspecs de motif. Cependant, ils ne peuvent contenir qu'un <src> et ne spécifient pas de <dst>. Les noms d'objets hexadécimaux entièrement écrits ne sont pas non plus pris en

charge.

tag <tag> signifie la même chose que refs/tags/<tag>:refs/tags/<tag> ; cela demande de récupérer tout jusqu'à l'étiquette

donnée.

La ref distante qui correspond à <src> est récupérée, et si <dst> n'est pas une chaîne vide, une tentative est faite pour mettre à jour la ref locale qui lui

correspond.

Que cette mise à jour soit autorisée sans --force dépend de l'espace de noms de refs vers lequel elle est récupérée, du type d'objet récupéré, et si la mise à jour est considérée comme un fast-forward. Généralement, les mêmes règles s'appliquent pour la récupération que pour le poussage, voir la section <refspec>... de git-push(1) pour savoir quelles elles sont. Les exceptions à ces règles particulières à git fetch sont notées

ci-dessous.

Jusqu'à la version 2.20 de Git, et contrairement au poussage avec git-push(1), toute mise à jour de refs/tags/* serait acceptée sans + dans le refspec (ou --force). Lors de la récupération, nous considérions de manière promiscue toutes les mises à jour d'étiquettes d'un distant comme des récupérations forcées. Depuis la version 2.20 de Git, la récupération pour mettre à jour refs/tags/* fonctionne de la même manière que lors du poussage. C'est-à-dire que toute mise à jour sera rejetée sans + dans le refspec (ou --forc

e).

Contrairement au poussage avec git-push(1), toute mise à jour en dehors de refs/{tags,heads}/* sera acceptée sans + dans le refspec (ou --force), que ce soit l'échange d'un objet arbre pour un objet blob, ou d'un commit pour un autre commit qui n'a pas le commit précédent comme ancêtre,

etc.

Contrairement au poussage avec h.1.fr'>git-push(1), il n'y a pas de configuration qui amendera ces règles, et rien de tel qu'un hook pre-fetch analogue au hook pre-receive.

Comme pour le push avec git-push(1), toutes les règles décrites ci-dessus concernant ce qui n'est pas autorisé en tant que mise à jour peuvent être ignorées en ajoutant un signe + optionnel au début d'un refspec (ou en utilisant l'option en ligne de commande --force). La seule exception est qu'aucune quantité de forçage ne permettra au namespace refs/heads/* d'accepter un objet non-commit.


Note
Lorsque la branche distante que vous souhaitez récupérer est connue pour être réinitialisée et rebasée régulièrement, il est attendu que sa nouvelle pointe ne descende pas de sa pointe précédente (telle qu'elle est stockée dans votre branche de suivi de branche distante la dernière fois que vous avez récupéré). Vous voudrez utiliser le signe + pour indiquer que des mises à jour non-fast-forward seront nécessaires pour de telles branches. Il n'y a aucun moyen de déterminer ou de déclarer qu'une branche sera rendue disponible dans un dépôt avec ce comportement ; l'utilisateur qui tire doit simplement savoir que c'est le modèle d'utilisation attendu pour une branche.

--stdin

Lit les refspecs, un par ligne, depuis stdin en plus de ceux fournis en tant qu'arguments. Le format "tag <nom>" n'est pas supporté.

URLS GIT

En général, les URL contiennent des informations sur le protocole de transport, l'adresse du serveur distant et le chemin d'accès au dépôt. Selon le protocole de transport, certaines de ces informations peuvent être absentes.

Git supporte les protocoles ssh, git, http et https (en outre, ftp et ftps peuvent être utilisés pour la récupération, mais c'est inefficace et déconseillé ; ne les utilisez pas).

Le transport natif (c'est-à-dire l'URL git://) n'effectue aucune authentification et doit être utilisé avec prudence sur les réseaux non sécurisés.

Les syntaxes suivantes peuvent être utilisées avec eux :

•ssh://[<user>@]<host>[:<port>]/<chemin-vers-repo-git>
•git://<host>[:<port>]/<chemin-vers-repo-git>
•http[s]://<host>[:<port>]/<chemin-vers-repo-git>
•ftp[s]://<host>[:<port>]/<chemin-vers-repo-git>

Une syntaxe alternative de type scp peut également être utilisée avec le protocole ssh :

•[<user>@]<host>:/<chemin-vers-repo-git>

Cette syntaxe n'est reconnue que s'il n'y a pas de barres obliques avant le premier deux-points. Cela permet de différencier un chemin local contenant un deux-points. Par exemple, le chemin local foo:bar pourrait être spécifié comme un chemin absolu ou ./foo:bar pour éviter d'être mal interprété comme une URL ssh.

Les protocoles ssh et git supportent en outre l'expansion de ~<username> :

•ssh://[<user>@]<host>[:<port>]/~<user>/<chemin-vers-repo-git>
•git://<host>[:<port>]/~<user>/<chemin-vers-repo-git>
•[<user>@]<host>:~<user>/<chemin-vers-repo-git>

Pour les dépôts locaux, également supportés nativement par Git, les syntaxes suivantes peuvent être utilisées :

•/chemin/vers/repo.git/
•file:///chemin/vers/repo.git/

Ces deux syntaxes sont principalement équivalentes, sauf lors du clonage, où la première implique l'option --local. Voir git-clone(1) pour les détails.

git clone, git fetch et git pull, mais pas git push, accepteront également un fichier bundle approprié. Voir git-bundle(1).

Lorsque Git ne sait pas comment gérer un certain protocole de transport, il tente d'utiliser le helper distant remote-<transport>, s'il en existe un. Pour demander explicitement un helper distant, la syntaxe suivante peut être utilisée :

•<transport>::<adresse>

où <adresse> peut être un chemin, un serveur et un chemin, ou une chaîne de caractères arbitraire de type URL reconnue par le helper distant spécifique invoqué. Voir gitremote-helpers(7) pour les détails.

S'il y a un grand nombre de dépôts distants aux noms similaires et que vous souhaitez utiliser un format différent pour eux (de sorte que les URL que vous utilisez seront réécrites en URL qui fonctionnent), vous pouvez créer une section de configuration de la forme :

        [url "<base-url-réelle>"]
                insteadOf = <base-url-alternative>

Par exemple, avec ceci :

        [url "git://git.host.xz/"]
                insteadOf = host.xz:/chemin/vers/
                insteadOf = work:

une URL comme "work:repo.git" ou comme "host.xz:/chemin/vers/repo.git" sera réécrite dans n'importe quel contexte qui prend une URL pour être "git://git.host.xz/repo.git".

Si vous souhaitez réécrire les URL uniquement pour les push, vous pouvez créer une section de configuration de la forme :

        [url "<base-url-réelle>"]
                pushInsteadOf = <base-url-alternative>

Par exemple, avec ceci :

        [url "ssh://example.org/"]
                pushInsteadOf = git://example.org/

une URL comme "git://example.org/chemin/vers/repo.git" sera réécrite en "ssh://example.org/chemin/vers/repo.git" pour les push, mais les pull utiliseront toujours l'URL d'origine.

•un fichier dans le répertoire $GIT_DIR/remotes, ou
•un fichier dans le répertoire $GIT_DIR/branches.

Tous ces éléments vous permettent également d'omettre le refspec de la ligne de commande car chacun contient un refspec que git utilisera par défaut.

Distant nommé dans le fichier de configuration

Vous pouvez choisir de fournir le nom d'un distant que vous aviez précédemment configuré en utilisant git-remote(1), git-config(1) ou même par une modification manuelle du fichier $GIT_DIR/config. L'URL de ce distant sera utilisée pour accéder au dépôt. Le refspec de ce distant sera utilisé par défaut lorsque vous ne fournissez pas de refspec sur la ligne de commande. L'entrée dans le fichier de configuration apparaîtrait comme suit :

        [remote "<nom>"]
                url = <URL>
                pushurl = <url_push>
                push = <refspec>
                fetch = <refspec>

La <url_push> est utilisée uniquement pour les push. Elle est facultative et utilise par défaut l'URL <URL>. Le push vers un distant affecte tous les pushurls définis ou toutes les URLs définies si aucun pushurls n'est défini. La récupération, cependant, ne récupérera que depuis la première URL définie si plusieurs URL sont définies.

Fichier nommé dans $GIT_DIR/remotes

Vous pouvez choisir de fournir le nom d'un fichier dans $GIT_DIR/remotes. L'URL de ce fichier sera utilisée pour accéder au dépôt. Le refspec de ce fichier sera utilisé par défaut lorsque vous ne fournissez pas de refspec sur la ligne de commande. Ce fichier doit avoir le format suivant :

        URL: l'un des formats d'URL ci-dessus
        Push: <refspec>
        Pull: <refspec>

Les lignes Push: sont utilisées par git push et les lignes Pull: sont utilisées par git pull et git fetch. Plusieurs lignes Push: et Pull: peuvent être spécifiées pour des mappages de branches supplémentaires.

Fichier nommé dans $GIT_DIR/branches

Vous pouvez choisir de fournir le nom d'un fichier dans $GIT_DIR/branches. L'URL de ce fichier sera utilisée pour accéder au dépôt. Ce fichier doit avoir le format suivant :

        <URL>#<head>

<URL> est requis ; #<head> est facultatif.

Selon l'opération, git utilisera l'un des refspecs suivants, si vous n'en fournissez pas sur la ligne de commande. <branche> est le nom de ce fichier dans $GIT_DIR/branches et <head> utilise par défaut master.

git fetch utilise :

        refs/heads/<head>:refs/heads/<branche>

git push utilise :

        HEAD:refs/heads/<head>

BRANCHES AMONT

Les branches dans Git peuvent avoir en option une branche distante amont. Git utilise par défaut la branche amont pour les opérations distantes, par exemple :

•C'est la valeur par défaut pour git pull ou git fetch sans arguments.
•C'est la valeur par défaut pour git push sans arguments, avec quelques exceptions. Par exemple, vous pouvez utiliser l'option branch.<nom>.pushRemote pour pousser vers un distant différent de celui d'où vous tirez, et par défaut avec push.default=simple, la branche amont que vous configurez doit avoir le même nom.
•Diverses commandes, y compris git checkout et git status, vous indiqueront combien de commits ont été ajoutés à votre branche actuelle et à l'amont depuis que vous en avez divergé, par exemple "Votre branche et origin/main ont divergé, et ont 2 et 3 commits différents respectivement".

L'amont est stockée dans .git/config, dans les champs "remote" et "merge". Par exemple, si main's upstream est origin/main :

[branch "main"]
   remote = origin
   merge = refs/heads/main

défaut.
•Si vous avez l'option de configuration push.autoSetupRemote définie, git push définira automatiquement la branche amont la première fois que vous poussez une
branche.
•Lors de la création d'une copie de travail d'une branche de suivi distant avec git checkout <branch>, une branche locale portant ce nom sera créée automatiquement et la branche amont sera définie sur la branche
