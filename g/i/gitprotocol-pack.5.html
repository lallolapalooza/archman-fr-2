NOM

gitprotocol-pack - Comment les packs sont transférés sur le réseau

SYNOPSIS

<protocole-sur-le-réseau>

DESCRIPTION

Git prend en charge le transfert de données sous forme de fichiers de packs via les transports ssh://, git://, http:// et file://. Il existe deux ensembles de protocoles, l'un pour envoyer des données d'un client vers un serveur et l'autre pour récupérer des données d'un serveur vers un client. Les trois transports (ssh, git, file) utilisent le même protocole pour transférer des données. http est documenté dans gitprotocol-http(5).

Les processus invoqués dans l'implémentation canonique de Git sont upload-pack côté serveur et fetch-pack côté client pour récupérer des données ; puis receive-pack côté serveur et send-pack côté client pour envoyer des données. Le protocole sert à ce qu'un serveur indique à un client ce qu'il possède actuellement, puis que les deux négocient la plus petite quantité de données à envoyer afin de mettre à jour complètement l'un ou l'autre.

FORMAT PKT-LINE

Les descriptions ci-dessous s'appuient sur le format pkt-line décrit dans gitprotocol-common(5). Lorsque la grammaire indique PKT-LINE(...), sauf indication contraire, les règles habituelles de pkt-line LF s'appliquent : l'expéditeur DOIT inclure un LF, mais le récepteur NE DOIT PAS se plaindre s'il est absent.

Un paquet d'erreur est un pkt-line spécial qui contient une chaîne d'erreur.

  ligne-erreur     =  PKT-LINE("ERR" ESP explanation-text)

Tout au long du protocole, là où PKT-LINE(...) est attendu, un paquet d'erreur PEUT être envoyé. Une fois ce paquet envoyé par un client ou un serveur, le processus de transfert de données défini dans ce protocole est terminé.

TRANSPORTS

Il existe trois transports sur lesquels le protocole de fichier de pack est initié. Le transport Git est un serveur simple et non authentifié qui prend la commande (presque toujours upload-pack, bien que les serveurs Git puissent être configurés pour être globalement inscriptibles, auquel cas l'initiation de receive-pack est également autorisée) avec laquelle le client souhaite communiquer, l'exécute et la connecte au processus demandeur.

Dans le transport SSH, le client exécute simplement le processus upload-pack ou receive-pack sur le serveur via le protocole SSH, puis communique avec ce processus invoqué via la connexion SSH.

Le transport file:// exécute le processus upload-pack ou receive-pack localement et communique avec lui via un tube.

PARAMÈTRES EXTRA

Le protocole fournit un mécanisme par lequel les clients peuvent envoyer des informations supplémentaires dans leur premier message au serveur. Ceux-ci sont appelés "Paramètres Supplémentaires", et sont supportés par les protocoles Git, SSH et HTTP.

Chaque Paramètre Supplémentaire prend la forme <clé>=<valeur> ou <clé>.

Les serveurs qui reçoivent de tels Paramètres Supplémentaires DOIVENT ignorer toutes les clés non reconnues. Actuellement, le seul Paramètre Supplémentaire reconnu est "version" avec une valeur de 1 ou 2. Voir gitprotocol-v2(5) pour plus d'informations sur le protocole version 2.

TRANSPORT GIT

Le transport Git commence par envoyer la commande et le dépôt sur le réseau en utilisant le format pkt-line, suivi d'un octet NUL et d'un paramètre d'hôte, terminé par un octet NUL.

0033git-upload-pack /project.git\0host=myserver.com\0

Le transport peut envoyer des Paramètres Supplémentaires en ajoutant un octet NUL supplémentaire, puis en ajoutant une ou plusieurs chaînes terminées par NUL :

003egit-upload-pack /project.git\0host=myserver.com\0\0version=1\0
git-proto-request = request-command SP pathname NUL
                    [ host-parameter NUL ] [ NUL extra-parameters ]
request-command   = "git-upload-pack" / "git-receive-pack" /
                    "git-upload-archive"   ; sensible à la casse
pathname          = *( %x01-ff ) ; exclure NUL
host-parameter    = "host=" hostname [ ":" port ]
extra-parameters  = 1*extra-parameter
extra-parameter   = 1*( %x01-ff ) NUL

host-parameter est utilisé pour l'hébergement virtuel basé sur le nom du démon Git. Voir l'option --interpolated-path de git daemon, avec les caractères de format %H/%CH.

Essentiellement, ce que le client Git fait pour se connecter à un processus upload-pack côté serveur via le protocole Git est ceci :

$ echo -e -n \
  "003agit-upload-pack /schacon/gitbook.git\0host=example.com\0" |
  nc -v example.com 9418

TRANSPORT SSH

L'initiation des processus upload-pack ou receive-pack via SSH consiste à exécuter le binaire sur le serveur via l'exécution à distance SSH. C'est essentiellement équivalent à exécuter ceci :

$ ssh git.example.com "git-upload-pack '/project.git'"

Pour qu'un serveur prenne en charge l'envoi et la réception Git pour un utilisateur donné via SSH, cet utilisateur doit être capable d'exécuter une ou les deux de ces commandes via le shell SSH qui lui est fourni à la connexion. Sur certains systèmes, cet accès shell est limité à la seule exécution de ces deux commandes, ou même d'une seule d'entre elles.

Dans une URI au format ssh://, le chemin est absolu dans l'URI, donc le / après le nom d'hôte (ou le numéro de port) est envoyé comme argument, qui est ensuite lu par le git-upload-pack distant exactement tel quel, donc c'est effectivement un chemin absolu dans le système de fichiers distant.

   git clone ssh://user@example.com/project.git
                |
                v
ssh user@example.com "git-upload-pack '/project.git'"

Dans une URI au format "user@host:path", le chemin est relatif au répertoire personnel de l'utilisateur, car le client Git exécutera :

   git clone user@example.com:project.git
                  |
                  v
ssh user@example.com "git-upload-pack 'project.git'"

L'exception est si un ~ est utilisé, auquel cas nous l'exécutons sans le / initial.

   ssh://user@example.com/~alice/project.git,
                  |
                  v
ssh user@example.com "git-upload-pack '~alice/project.git'"

Selon la valeur de la variable de configuration protocol.version, Git peut tenter d'envoyer des Paramètres Supplémentaires sous forme de chaîne séparée par des deux-points dans la variable d'environnement GIT_PROTOCOL. Ceci n'est fait que si la variable de configuration ssh.variant indique que la commande ssh supporte la transmission de variables d'environnement comme argument.

Quelques points à retenir ici :

•Le "nom de la commande" est orthographié avec un tiret (par exemple git-upload-pack), mais cela peut être remplacé par le client ;
•Le chemin du dépôt est toujours entouré de guillemets simples.

RÉCUPÉRATION DE DONNÉES DEPUIS UN SERVEUR

Lorsqu'un dépôt Git souhaite obtenir des données qu'un second dépôt possède, le premier peut récupérer (fetch) depuis le second. Cette opération détermine quelles données le serveur possède que le client n'a pas, puis diffuse ces données vers le client au format packfile.

NÉGOCIATION DU

PACKFILE

Après la découverte des références et des capacités, le client peut décider de terminer la connexion en envoyant un flush-pkt, indiquant au serveur qu'il peut maintenant se terminer proprement et se déconnecter, lorsqu'il n'a pas besoin de données de pack. Cela peut arriver avec la commande ls-remote, et peut aussi arriver lorsque le client est déjà à

jour.

Sinon, il entre dans la phase de négociation, où le client et le serveur déterminent quel est le packfile minimal nécessaire pour le transport, en disant au serveur quels objets il veut, ses objets superficiels (s'il y en a), et la profondeur de commit maximale qu'il veut (s'il y en a). Le client enverra aussi une liste des capacités qu'il veut voir prises en charge, parmi celles que le serveur a dit qu'il pouvait faire avec la première ligne w

ant. 
  upload-request    =  want-list
                       *shallow-line
                       *1depth-request
                       [filter-request]
                       flush-pkt
  want-list         =  first-want
*additional-want shallow-line = PKT-LINE("shallow" SP obj-id) depth-request = PKT-LINE("deepen" SP depth) / PKT-LINE("deepen-since" SP timestamp) / PKT-LINE(
"deepen-not" SP ref) first-want = PKT-LINE("want" SP obj-id SP capability-list) additional-want = PKT-LINE("want" SP obj-id) depth = 1*DIGIT filter-request = PKT-LINE("filter" SP filter-spec)

Les clients DOIVENT envoyer tous les obj-id qu'ils veulent de la phase de découverte des références sous forme de lignes want. Les clients DOIVENT envoyer au moins une commande want dans le corps de la requête. Les clients NE DOIVENT PAS mentionner un obj-id dans une commande want qui n'est pas apparu dans la réponse obtenue via la découverte des

refs.

Le client DOIT écrire tous les obj-id dont il n'a que des copies superficielles (ce qui signifie qu'il n'a pas les parents d'un commit) sous forme de lignes shallow afin que le serveur soit conscient des limitations de l'historique du

client.

Le client envoie maintenant la profondeur d'historique de commit maximale qu'il veut pour cette transaction, qui est le nombre de commits qu'il veut depuis le sommet de l'historique, s'il y en a, sous forme de ligne deepen. Une profondeur de 0 est la même chose que de ne pas faire de demande de profondeur. Le client ne veut pas recevoir de commits au-delà de cette profondeur, ni ne veut les objets nécessaires uniquement pour compléter ces commits. Les commits dont les parents ne sont pas reçus en conséquence sont définis comme superficiels et marqués comme tels sur le serveur. Cette information est renvoyée au client à l'étape

suivante.

Le client peut éventuellement demander à pack-objects d'omettre divers objets du packfile en utilisant l'une des plusieurs techniques de filtrage. Celles-ci sont destinées à être utilisées avec les opérations de clonage partiel et de récupération partielle. Un objet qui ne correspond pas à une valeur filter-spec est omis sauf s'il est explicitement demandé dans une ligne want. Voir rev-list pour les valeurs filter-spec

possibles.

Une fois que tous les want et 'shallow (et 'deepen optionnel) ont été transférés, les clients DOIVENT envoyer un flush-pkt, pour indiquer au côté serveur qu'ils ont terminé l'envoi de la

liste.

Sinon, si le client a envoyé une demande de profondeur positive, le serveur déterminera quels commits seront et ne seront pas superficiels et enverra cette information au client. Si le client n'a pas demandé de profondeur positive, cette étape est

ignorée. 
  shallow-update   =  *shallow-line
                      *unshallow-lin
e flush-pkt shallow-line = PKT-LINE("sha
llow" SP obj-id) unshallow-line = PKT-LINE("unshallow" SP obj-id)

Si le client a demandé une profondeur positive, le serveur calculera l'ensemble des commits qui ne sont pas plus profonds que la profondeur souhaitée. L'ensemble des commits commence aux want du

client.

Le serveur écrit des lignes shallow pour chaque commit dont les parents ne seront pas envoyés en conséquence. Le serveur écrit une ligne unshallow pour chaque commit que le client a indiqué comme superficiel, mais qui n'est plus superficiel à la profondeur actuellement demandée (c'est-à-dire que ses parents seront maintenant envoyés). Le serveur NE DOIT PAS marquer comme non superficiel quoi que ce soit que le client n'a pas indiqué comme

superficiel.

Maintenant le client enverra une liste des obj-id qu'il possède en utilisant des lignes have, afin que le serveur puisse faire un packfile qui ne contient que les objets dont le client a besoin. En mode multi_ack, l'implémentation canonique enverra jusqu'à 32 de ces lignes à la fois, puis enverra un flush-pkt. L'implémentation canonique passera ensuite immédiatement aux 32 suivantes, de sorte qu'il y ait toujours un bloc de 32 « en cours de transmission sur le fil » à la

fois. 
  upload-haves      =  have-list
                       compute-end
  have-list         =  *have-line
  have-line         =  PKT-LINE("have" SP obj-id)
  compute-end       =  flush-pkt /

Si le serveur lit des lignes have, il répondra alors en acquittant (ACK) les obj-id que le client a dit avoir et que le serveur a aussi. Le serveur acquittera les obj-id différemment selon le mode d'acquittement choisi par le

client.

En mode multi_ack

:
•le serveur répondra avec ACK obj-id continue pour tout commit
commun.
•une fois que le serveur a trouvé un commit de base commun acceptable et est prêt à faire un packfile, il acquittera aveuglément tous les obj-id des lignes have en les renvoyant au
client.
•le serveur enverra ensuite un NAK puis attendra une autre réponse du client — soit un done soit une autre liste de lignes h
ave.

En mode multi_ack_detailed

:
•le serveur différenciera les acquittements où il signale qu'il est prêt à envoyer des données avec des lignes ACK obj-id ready, et signalera les commits communs identifiés avec des lignes ACK obj-id c
ommon.

Sans multi_ack ni multi_ack_detailed

:
•upload-pack envoie "ACK obj-id" sur le premier objet commun qu'il trouve. Après cela, il ne dit plus rien jusqu'à ce que le client lui donne un
"done".
•upload-pack envoie "NAK" sur un flush-pkt si aucun objet commun n'a encore été trouvé. Si un objet a été trouvé, et qu'un ACK a donc déjà été envoyé, il reste silencieux sur le
flush-pkt.

Une fois que le client a obtenu suffisamment de réponses ACK pour déterminer que le serveur a suffisamment d'informations pour envoyer un packfile efficace (dans l'implémentation canonique, cela est déterminé lorsqu'il a reçu suffisamment d'ACK pour pouvoir colorer tout ce qui reste dans la file --date-order comme commun avec le serveur, ou que la file --date-order est vide), ou que le client décide qu'il veut abandonner (dans l'implémentation canonique, cela est déterminé lorsque le client envoie 256 lignes have sans qu'aucune d'elles ne soit acquittée par le serveur — ce qui signifie qu'il n'y a rien en commun et que le serveur devrait simplement envoyer tous ses objets), alors le client enverra une commande done. La commande done signale au serveur que le client est prêt à recevoir les données de son

packfile.

Cependant, la limite de 256 ne s'active que dans l'implémentation canonique du client si nous avons reçu au moins un "ACK %s continue" lors d'un tour précédent. Cela aide à garantir qu'au moins un ancêtre commun est trouvé avant que nous n'abandonnions

complètement.

Une fois que la ligne done est lue depuis le client, le serveur enverra soit un ACK obj-id final, soit un NAK. obj-id est le nom de l'objet du dernier commit déterminé comme commun. Le serveur n'envoie ACK après done que s'il y a au moins une base commune et que multi_ack ou multi_ack_detailed est activé. Le serveur envoie toujours NAK après done si aucune base commune n'a été

trouvée.

Au lieu d'un ACK ou d'un NAK, le serveur peut envoyer un message d'erreur (par exemple, s'il ne reconnaît pas un objet dans une ligne want reçue du client)

.

Ensuite, le serveur commencera à envoyer les données de son

PACKFILE

DATA

Maintenant que le client et le serveur ont terminé la négociation sur la quantité minimale de données qui doit être envoyée au client, le serveur construira et enverra les données requises au format

packfile.

Voir gitformat-pack(5) pour savoir à quoi ressemble réellement le

packfile.

Si side-band ou side-band-64k ont été spécifiées par le client, le serveur enverra les données du packfile

multiplexées.

Chaque paquet commence par la longueur de la ligne de paquet (packet-line) de la quantité de données qui suit, suivie d'un octet unique spécifiant la bande latérale (sideband) sur laquelle les données suivantes

arrivent.

En mode side-band, il enverra jusqu'à 999 octets de données plus 1 code de contrôle, pour un total de jusqu'à 1000 octets dans une pkt-line. En mode side-band-64k, il enverra jusqu'à 65519 octets de données plus 1 code de contrôle, pour un total de jusqu'à 65520 octets dans une

pkt-line.

L'octet de bande latérale sera un 1, 2 ou un 3. La bande latérale 1 contiendra les données du packfile, la bande latérale 2 sera utilisée pour les informations de progression que le client imprimera généralement sur stderr et la bande latérale 3 est utilisée pour les informations

d'erreur.

Si la capacité side-band n'a pas été spécifiée, le serveur dif

fusera l'intégralité du p
ackfile sans multiplexage.

ENVOI DE DONNÉES À UN

SERVEUR

L'envoi de données à un serveur invoquera le processus receive-pack sur le serveur, ce qui permettra au client de lui indiquer quelles références il doit mettre à jour, puis d'envoyer toutes les données dont le serveur aura besoin po

ur que ces nouvelles références soient complètes. Une fois que toutes les données sont reçues
et validées, le serveur mettra à jour ses références selon ce que le client a spécifié.

AUTHENTIFICATIO

N

Le protocole lui-même ne contient aucun mécanisme d'authentification. Cela doit être géré par le transport, comme SSH, avant que le processus receive-pack ne soit invoqué. Si receive-pack est configuré sur le transport Git, ces dépôts seront accessibles en écriture p

ar toute personne pouvant accéder à ce port
(9418), car ce transport n'est pas authentifié.

DÉCOUVERT DES

RÉFÉRENCES

La phase de découverte des références se fait presque de la même manière que dans le protocole de fetch. Chaque référence obj-id et nom sur le serveur est envoyé au format packet-line au client, suivi d'un flush-pkt. La seule vraie différence est que la liste des capacités est différente - les seules valeurs possibles sont report-status, report-status-v2, delete-refs, ofs-delta, atomic et push-option

s
.

Si l'extrémité réceptrice ne prend pas en charge delete-refs, l'extrémité émettrice NE DOIT PAS demander la commande

delete.

Si l'extrémité réceptrice ne prend pas en charge push-cert, l'extrémité émettrice NE DOIT PAS envoyer une commande push-cert. Lorsqu'une commande push-cert est envoyée, command-list NE DOIT PAS être envoyée ; les commandes enregistrées dans le certificat de push sont utilisées à la

place.

Le packfile NE DOIT PAS être envoyé si la seule commande utilisée est delete

.

Un packfile DOIT être envoyé si une commande create ou update est utilisée, même si le serveur poss déjà tous les objets nécessaires. Dans ce cas, le client DOIT envoyer un packfile vide. La seule fois où cela est susceptible de se produire est si le client crée une nouvelle branche ou une étiquette pointant vers un obj-id

existant.

Le serveur recevra le packfile, le décompressera, puis validera chaque référence mise à jour pour vérifier qu'elle n'a pas changé

pendant que la requête était en cours de traitement (l'obj-id est toujours le même que l'old-id), et il exécutera les hooks de
mise à jour pour s'assurer que la mise à jour est acceptable. Si tout cela est en ordre, le serveur mettra à jour les références.

RAPPORT

D'ÉTAT

Après avoir reçu les données du pack de l'émetteur, le récepteur envoie un rapport si la capacité report-status ou report-status-v2 est en vigueur. C'est une courte liste de ce qui s'est passé lors de cette mise à jour. Elle listera d'abord l'état de la décompression du packfile soit comme unpack ok ou unpack [error]. Ensuite, elle listera l'état pour chacune des références qu'elle a tenté de mettre à jour. Chaque ligne est soit ok [refname] si la mise à jour a réussi, soit ng [refname] [error] si la mise à jour a

échoué. 
  report-status     = unpack-status
                      1*(command-status)
                      flush-pkt
  unpack-status     = PKT-LINE(
"unpack" SP unpack-result) unpack-result = "ok" / error-msg command-status = command-ok / command-fail command-ok = PKT
-LINE("ok" SP refname) command-fail = PKT-LINE("ng" SP refname SP error-msg) error-msg = 1*(OCTET) ; où ce n'est pas "ok"

La capacité report-status-v2 étend le protocole en ajoutant de nouvelles lignes d'options afin de prendre en charge le signalement des références réécrites par le hook proc-receive. Le hook proc-receive peut traiter une commande pour une pseudo-référence qui peut créer ou mettre à jour une ou plusieurs références, et chaque référence peut avoir un nom différent, un new-oid différent, et un old-oid

différent. 
  report-status-v2  = unpack-status
                      1*(command-status-v2)
                      flush-pkt
  unpack-status     = PKT-LINE("unpack" SP unpack-result)
  unpack-result     = "ok" / error-msg
  command-status-v2 = command-ok-v2 / command-fail
  command-ok-v2     = command-ok
                      *option-line
  command-ok        = PKT-LINE("ok" SP refname)
  command-fail      = PKT-LINE("ng" SP refname SP error-msg)
  error-msg         = 1*(OCTET) ; où ce n'est pas "ok"
  option-line       = *1(option-refname)
                      *1(option-old-oid)
                      *1(option-new-oid)
                      *1(option-forced-update)
  option-refname    = PKT-LINE("option" SP "refname" SP refname)
  option-old-oid    = PKT-LINE("option" SP "old-oid" SP obj-id)
  option-new-oid    = PKT-LINE("option" SP "new-oid" SP obj-id)
  option-force      = PKT-LINE("option" SP
"forced-update"
)

Les mises à jour peuvent échouer pour un certain nombre de raisons. La référence peut avoir changé depuis que la phase de découverte des références a été initialement envoyée, ce qui signifie que quelqu'un a poussé entre-temps. La référence poussée pourrait être une référence non fast-forward et les hooks de mise à jour ou la configuration pourraient être configurés pour ne pas autoriser cela, etc. De plus, certaines références peuvent être mises à jour tandis que d'autres peuvent être

rejetées.
