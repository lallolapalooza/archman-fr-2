SYNOPSI

DESCRIPTIO

N

Supprime de l'index les fichiers correspondant au pathspec, ou de l'arbre de travail et de l'index. git rm ne supprimera pas un fichier uniquement de votre répertoire de travail. (Il n'existe pas d'option pour supprimer un fichier uniquement de l'arbre de travail tout en le conservant dans l'index ; utilisez /bin/rm si vous souhaitez le faire.) Les fichiers supprimés doivent être identiques à la pointe de la branche, et aucune mise à jour de leur contenu ne peut être mise en index, bien que ce comportement par défaut puisse être contourné avec l'option -f. Quand --cached est spécifié, le contenu mis en index doit correspondre soit à la pointe de la branche, soit au fichier sur le disque, permettant ainsi de supprimer le fichier uniquement de l'index. Lorsque des sparse-checkouts sont utilisés (voir git-sparse-checkout(1)), git rm ne supprimera que les chemins correspondant aux motifs de

sparse-checkout
.

OPTION

S

<pathspec>..

.
Fichiers à supprimer. Un nom de répertoire en tête (par ex. dir pour supprimer dir/file1 et dir/file2) peut être fourni pour supprimer tous les fichiers du répertoire, et récursivement tous les sous-répertoires, mais cela nécessite que l'option -r soit explicitement fournie.

La commande ne supprime que les chemins connus de

Git.

Les motifs de fichiers (globbing) s'appliquent au-delà des limites des répertoires. Ainsi, étant donnés deux répertoires d et d2, il y a une différence entre utiliser git rm 'd*' et git rm 'd/*', car la première supprimera aussi tout le répertoire d2

.

SUPPRESSION DES FICHIERS QUI ONT DISPARU DU SYSTÈME DE

FICHIERS

Il n'existe pas d'option pour git rm permettant de supprimer de l'index uniquement les chemins qui ont disparu du système de fichiers. Cependant, selon le cas d'usage, il existe plusieurs façons de le

faire.

Utiliser « git commit -a

»

Si vous souhaitez que votre prochaine validation enregistre toutes les modifications des fichiers suivis dans l'arbre de travail et enregistre toutes les suppressions de fichiers qui ont été supprimés de l'arbre de travail avec rm (par opposition à git rm), utilisez git commit -a, car il remarquera et enregistrera automatiquement toutes les suppressions. Vous pouvez aussi obtenir un effet similaire sans valider en utilisant git add -u

.

Utiliser « git add -A

»

Lorsque vous acceptez un nouveau lot de code pour une branche de fournisseur, vous voudrez probablement enregistrer à la fois la suppression de chemins et l'ajout de nouveaux chemins, ainsi que les modifications des chemins

existants.

Typiquement, vous supprimerez d'abord tous les fichiers suivis de l'arbre de travail en utilisant cette commande

: 
git ls-file
s -z | xar
gs -0 rm -f

puis vous décompresserez le nouveau code dans l'arbre de travail. Alternativement, vous pourriez rsync les changements dans l'arbre de

travail.

Après cela, la façon la plus simple d'enregistrer toutes les suppressions, ajouts et modifications dans l'arbre de travail est

: 
git
add
-A

Voir git-ad

1).

SOUS-MODULE

S

Seuls les sous-modules utilisant un gitfile (ce qui signifie qu'ils ont été clonés avec une version de Git 1.7.8 ou plus récente) seront supprimés de l'arbre de travail, car leur dépôt se trouve à l'intérieur du répertoire .git du superprojet. Si un sous-module (ou l'un de ceux imbriqués en lui) utilise encore un répertoire .git, git rm déplace le répertoire git du sous-module dans le répertoire git du superprojet pour protéger l'historique du sous-module. S'il existe, la sectionsubmodule. <name> dans le fichier gitmodules(5) sera également supprimée et ce fichier sera mis en index (sauf si --cache

d ou

-n sont utilisés). Un sous-module est considéré à jour lorsque

le

HEAD est le même que celui enregistré dans l'index, aucun fichier suivi n'est modifié et aucun fichier non suivi qui n'est pas ignoré n'est présent dans l'arbre de travail du sous-module. Les fichiers ignorés sont considérés comme sacrifiables et n'empêcheront pas la suppression de l'arbre de travail d'un sous-module. Si vous ne souhaitez que supprimer la copie locale d'un sous-module de votre arbre de travail sans valider la suppression, utilisez plutôt git-submodule(1) deinit. V
