DESCRIPTIO

N

Exécute des tâches pour optimiser les données du dépôt Git, accélérant ainsi les autres commandes Git et réduisant les besoins en stockage du

dépôt.

Les commandes Git qui ajoutent des données au dépôt, comme git add ou git fetch, sont optimisées pour une expérience utilisateur réactive. Ces commandes ne prennent pas le temps d'optimiser les données Git, car de telles optimisations sont proportionnelles à la taille totale du dépôt, alors que ces commandes utilisateur effectuent chacune une action relativement

petite.

La commande git maintenance offre de la flexibilité su

TÂCHE

S

commit-grap

h
Le travail commit-graph met à jour les fichiers commit-graph de manière incrémentielle, puis vérifie que les données écrites sont correctes. L'écriture incrémentielle est sûre à exécuter simultanément avec des processus Git concurrents car elle n'expirera pas les fichiers .graph qui se trouvaient dans le fichier commit-graph-chain précédent. Ils seront supprimés lors d'une exécution ultérieure en fonction du délai
d'expiration.

prefetc

h
La tâche prefetch met à jour le répertoire d'objets avec les derniers objets de tous les distants enregistrés. Pour chaque distant, une commande git fetch est exécutée. La spécification de référence (refspec) configurée est modifiée pour placer toutes les références demandées dans refs/prefetch/. De plus, les tags ne sont pas mis à jour.

Cela est fait pour éviter de perturber les branches de suivi des distants. Les utilisateurs finaux s'attendent à ce que ces références restent immobiles sauf s'ils initient un fetch. Cependant, avec la tâche prefetch, les objets nécessaires pour compléter un fetch réel ultérieur seraient déjà obtenus, rendant le fetch réel plus rapide. Dans le cas idéal, il deviendra simplement une mise à jour d'un ensemble de branches de suivi des distants sans aucun transfert

d'objet.

La configuration remote.<nom>.skipFetchAll peut être utilisée pour exc

lure un distant particu
lier du préchargement.

g

c
Nettoie les fichiers inutiles et optimise le dépôt local. "GC" signifie "garbage collection" (ramasse-miettes), mais cette tâche effectue de nombreuses sous-tâches plus petites. Cette tâche peut être coûteuse pour les grands dépôts, car elle regroupe tous les objets Git dans un seul fichier pack. Elle peut aussi être perturbante dans certaines situations, car elle supprime des données obsolètes. Voir git-gc(1) pour plus de détails sur la collecte des déchets dans
Git.

loose-object

s
Le travail loose-objects nettoie les objets détachés (loose) et les place dans des fichiers pack. Afin d'éviter les conditions de course avec des commandes Git concurrentes, il suit un processus en deux étapes. D'abord, il supprime tout objet détaché qui existe déjà dans un fichier pack ; les processus Git concurrents examineront le fichier pack pour les données de l'objet au lieu de l'objet détaché. Ensuite, il crée un nouveau fichier pack (commençant par "loose-") contenant un lot d'objets détachés.

La taille du lot est par défaut de cinquante mille objets pour empêcher le travail de prendre trop de temps sur un dépôt avec de nombreux objets détachés. Utilisez l' option de configuration maintenance.loose-objects.batchSize pour ajuster cette taille, y compris une valeur de 0 pour supprimer la

limite.

La tâche gc écrit les objets inaccessibles comme objets détachés pour être nettoyés par une étape ultérieure seulement s'ils ne sont pas réajoutés à un fichier pack ; pour cette raison, il n'est pas conseillé d'activer les tâches loose-objects et gc en mê

me te
mps.

incremental-repac

k
Le travail incremental-repack regroupe le répertoire d'objets en utilisant la fonctionnalité multi-pack-index. Afin d'éviter les conditions de course avec des commandes Git concurrentes, il suit un processus en deux étapes. D'abord, il appelle git multi-pack-index expire pour supprimer les fichiers pack non référencés par le fichier multi-pack-index. Ensuite, il appelle git multi-pack-index repack pour sélectionner plusieurs petits fichiers pack et les regrouper en un plus grand, puis met à jour les entrées multi-pack-index qui référencent les petits fichiers pack pour qu'elles référencent le nouveau fichier pack. Cela prépare ces petits fichiers pack à la suppression lors de la prochaine exécution de git multi-pack-index expire. La sélection des petits fichiers pack est telle que la taille attendue du grand fichier pack est au moins la taille du lot ; voir l' option --batch-size pour la sous-commande repack dans git-multi-pack-index(1). La taille de lot par défaut est zéro, qui est un cas spécial qui tente de regrouper tous les fichiers pack en un seul fichier
pack.

pack-ref

s
La tâche pack-refs collecte les fichiers de références détachées et les rassemble dans un seul fichier. Cela accélère les opérations qui doivent parcourir de nombreuses références. Voir git-pack-refs(1) pour plus
d'informations.

reflog-expir

e
La tâche reflog-expire supprime toute entrée dans le journal de références (reflog) plus ancienne que le seuil d'expiration. Voir git-reflog(1) pour plus
d'informations.

rerere-g

c
La tâche rerere-gc invoque la collecte des déchets pour les entrées obsolètes dans le cache rerere. Voir git-rerere(1) pour plus
d'informations.

worktree-prun

e
La tâche worktree-prune supprime les arbres de travail obsolètes ou cassés. Voir git-worktree(1) pour
plus d'inf
ormations.

DÉPANNAG

E

La commande git maintenance est conçue pour simplifier les modèles de maintenance de dépôt tout en minimisant le temps d'attente de l'utilisateur pendant les commandes Git. Diverses options de configuration sont disponibles pour permettre de personnaliser ce processus. Les options de maintenance par défaut se concentrent sur des opérations qui se terminent rapidement, même sur les grands

dépôts.

Les utilisateurs peuvent constater que certaines tâches de maintenance planifiées ne s'exécutent pas aussi fréquemment que prévu. Chaque commande git maintenance run prend un verrou sur la base d'objets du dépôt, et cela empêche d'autres commandes git maintenance run concurrentes de s'exécuter sur le même dépôt. Sans cette protection, des processus concurrents pourraient laisser le dépôt dans un état

imprévisible.

Le calendrier de maintenance en arrière-plan exécute les processus git maintenance run de manière horaire. Chaque exécution traite les tâches « horaires ». À minuit, ce processus exécute également les tâches « quotidiennes ». À minuit du premier jour de la semaine, ce processus exécute également les tâches « hebdomadaires ». Un seul processus parcourt chaque dépôt enregistré, effectuant les tâches planifiées pour cette fréquence. Les processus sont planifiés à une minute aléatoire de l'heure par client pour répartir la charge que plusieurs clients pourraient générer (par exemple, à partir du préchargement). Selon le nombre de dépôts enregistrés et leur taille, ce processus peut prendre plus d'une heure. Dans ce cas, plusieurs commandes git maintenance run peuvent s'exécuter sur le même dépôt en même temps, entrant en conflit sur le verrou de la base d'objets. Cela entraîne l'une des deux tâches qui ne s'exécute

pas.

Si vous constatez que certaines fenêtres de maintenance prennent plus d'une heure à se terminer, envisagez de réduire la complexité de vos tâches de maintenance. Par exemple, la tâche gc est beaucoup plus lente que la tâche incremental-repack. Cependant, cela a pour coût une base d'objets légèrement plus grande. Envisagez de déplacer les tâches plus coûteuses pour qu'elles s'exécutent moins

fréquemment.

Les utilisateurs expérimentés peuvent envisager de planifier leurs propres tâches de maintenance en utilisant un calendrier différent de celui disponible via git maintenance start et les options de configuration de Git. Ces utilisateurs doivent être conscients du verrou de la base d'objets et du comportement des commandes git maintenance run concurrentes. De plus, la commande git gc ne doit pas être combinée avec les commandes git maintenance run. git gc modifie la base d'objets mais ne prend pas le verrou de la même manière que git maintenance run. Si possible, utilisez git maintenance run --task=gc au lieu de git gc

.

Les sections suivantes décrivent les mécanismes mis en place pour exécuter la maintenance en arrière-plan par git maintenance start et comment l

es perso
nnaliser.

MAINTENANCE EN ARRIÈRE-PLAN SUR LES SYSTÈMES

POSIX

Le mécanisme standard pour planifier des tâches en arrière-plan sur les systèmes POSIX est cron(8). Cet outil exécute des commandes selon un calendrier donné. La liste actuelle des tâches planifiées par l'utilisateur peut être trouvée en exécutant crontab -l. Le calendrier écrit par git maintenance start est similaire à ceci

: 
# BEGIN GIT MAINTENANCE SCHEDULE
# The following schedule was created by Git
# Any edits made in this region might be
# replaced in the future by a Git command.
0 1-23 * * * "/<path>/gi
t" --exec-path="/<path>" for-each-repo --config=maintenance.repo maintenance run --schedule=hourly 0 0 * * 1-6 "/<path>/git" --exec-path="/<path>" for-each-repo --config=maintenance.rep
o maintenance run --schedule=daily 0 0 * * 0 "/<path>/git" --exec-path="/<path>" for-each-repo --config=maintenance.repo maintenance run --schedule=weekly # END GIT MAINTENANCE SCHEDULE

Les commentaires servent de région pour marquer le calendrier comme écrit par Git. Toute modification dans cette région sera complètement supprimée par git maintenance stop ou écrasée par git maintenance start

.

L'entrée crontab spécifie le chemin complet de l'exécutable git pour s'assurer que la commande git exécutée est la même que celle avec laquelle git maintenance start a été émise, indépendamment de PATH. Si le même utilisateur exécute git maintenance start avec plusieurs exécutables Git, alors seul le dernier exécutable est

utilisé.

Ces commandes utilisent git for-each-repo --config=maintenance.repo pour exécuter git maintenance run --schedule=<fréquence> sur chaque dépôt listé dans l'option de configuration à valeurs multiples maintenance.repo. Ceux-ci sont généralement chargés depuis la configuration globale spécifique à l'utilisateur. Le processus git maintenance détermine ensuite quelles tâches de maintenance sont configurées pour s'exécuter sur chaque dépôt avec chaque <fréquence> en utilisant les options de configuration maintenance.<task>.schedule. Ces valeurs sont chargées depuis les valeurs de configuration globales ou du

dépôt.

Si les valeurs de configuration sont insuffisantes pour obtenir le calendrier de maintenance en arrière-plan souhaité, vous pouvez créer votre propre calendrier. Si vous exécutez crontab -e, un éditeur se chargera avec votre calendrier cron spécifique à l'utilisateur. Dans cet éditeur, vous pouvez ajouter vos propres lignes de calendrier. Vous pourriez commencer par adapter le calendrier par défaut listé précédemment, ou vous pourriez lire la documentation de crontab(5) pour des techniques de planification avancées. Veuillez utiliser le chemin complet et les techniques --exec-path du calendrier par défaut pour vous assurer

que vous exécutez les bons bi
naires dans votre calendrier.

MAINTENANCE EN ARRIÈRE-PLAN SUR LES SYSTÈMES

MACOS

Bien que macOS prenne techniquement en charge cron, l'utilisation de crontab -e nécessite des privilèges élevés et le processus exécuté n'a pas un contexte utilisateur complet. Sans un contexte utilisateur complet, Git et ses assistants d'identification ne peuvent pas accéder aux identifiants stockés, donc certaines tâches de maintenance ne sont pas

fonctionnelles.

À la place, git maintenance start interagit avec l'outil launchctl, qui est la manière recommandée de planifier des tâches minutées dans macOS. Planifier la maintenance via git maintenance (start|stop) nécessite certaines fonctionnalités de launchctl disponibles

MAINTENANCE D'ARRIÈRE-PLAN SUR LES SYSTÈMES MACOS

Ce n'est possible qu'à partir de macOS 10.11.

Vos tâches planifiées spécifiques à l'utilisateur sont stockées sous forme de fichiers .plist au format XML dans ~/Library/LaunchAgents/. Vous pouvez voir les tâches actuellement enregistrées en utilisant la commande suivante :

$ ls ~/Library/LaunchAgents/org.git-scm.git*
org.git-scm.git.daily.plist
org.git-scm.git.hourly.plist
org.git-scm.git.weekly.plist

Une tâche est enregistrée pour chaque option --schedule=<fréquence>. Pour inspecter comment le format XML décrit chaque planification, ouvrez l'un de ces fichiers .plist dans un éditeur et inspectez l'élément <array> qui suit la clé <key>StartCalendarInterval</key>.

git maintenance start écrasera ces fichiers et enregistrera à nouveau les tâches avec launchctl, donc toute personnalisation doit être effectuée en créant vos propres fichiers .plist avec des noms distincts. De même, la commande git maintenance stop désenregistrera les tâches avec launchctl et supprimera les fichiers .plist.

Pour apporter des personnalisations plus avancées à vos tâches d'arrière-plan, consultez launchctl.plist(5) pour plus d'informations.

MAINTENANCE D'ARRIÈRE-PLAN SUR LES SYSTÈMES WINDOWS

Windows ne prend pas en charge cron et dispose à la place de son propre système pour la planification des tâches d'arrière-plan. La commande git maintenance start utilise la commande schtasks pour soumettre des tâches à ce système. Vous pouvez inspecter toutes les tâches d'arrière-plan à l'aide de l'application Planificateur de tâches. Les tâches ajoutées par Git portent des noms de la forme Git Maintenance (<fréquence>). L'interface graphique du Planificateur de tâches offre des moyens d'inspecter ces tâches, mais vous pouvez également exporter les tâches vers des fichiers XML et y consulter les détails.

Notez que, Git étant une application console, ces tâches d'arrière-plan créent une fenêtre de console visible par l'utilisateur actuel. Cela peut être modifié manuellement en sélectionnant l'option « Exécuter, que l'utilisateur soit connecté ou non » dans le Planificateur de tâches. Cette modification nécessite la saisie d'un mot de passe, c'est pourquoi git maintenance start ne la sélectionne pas par défaut.

Si vous souhaitez personnaliser les tâches d'arrière-plan, veuillez renommer les tâches afin que les appels futurs à git maintenance (start|stop) ne remplacent pas vos tâches personnalisées.

CONFIGURATION

Tout ce qui suit cette ligne dans cette section est inclus sélectivement de la documentation git-config(1). Le contenu est identique à ce qui s'y trouve :

maintenance.auto

Cette option de configuration booléenne contrôle si certaines commandes exécutent git maintenance run --auto après avoir effectué leur travail normal. Par défaut, sa valeur est true.

maintenance.autoDetach

De nombreuses commandes Git déclenchent une maintenance automatique après avoir écrit des données dans le dépôt. Cette option de configuration booléenne contrôle si cette maintenance automatique doit avoir lieu au premier plan ou si le processus de maintenance doit se détacher et continuer à s'exécuter en arrière-plan.

Si elle n'est pas définie, la valeur de gc.autoDetach est utilisée en secours. Par défaut, sa valeur est true si les deux ne sont pas définies, ce qui signifie que le processus de maintenance se détachera.

maintenance.strategy

Cette option de configuration de type chaîne de caractères permet de spécifier une des quelques stratégies recommandées pour la maintenance des dépôts. Cela affecte les tâches qui sont exécutées lors de git maintenance run, à condition qu'aucun argument --task=<tâche> ne soit fourni. Ce paramètre a un impact sur la maintenance manuelle, la maintenance automatique ainsi que la maintenance planifiée. Les tâches exécutées peuvent varier en fonction du type de maintenance.

La stratégie de maintenance peut être affinée en définissant maintenance.<tâche>.enabled et maintenance.<tâche>.schedule. Si elles sont définies, ces valeurs sont utilisées à la place des valeurs par défaut fournies par maintenance.strategy.

Les stratégies possibles sont :

•none : Cette stratégie implique qu'aucune tâche n'est exécutée. C'est la stratégie par défaut pour la maintenance planifiée.
•gc : Cette stratégie exécute la tâche gc. C'est la stratégie par défaut pour la maintenance manuelle.
•geometric : Cette stratégie effectue un reconditionnement géométrique des fichiers de paquets et maintient à jour les structures de données auxiliaires. La stratégie expire les données dans le reflog et supprime les arbres de travail qui ne peuvent plus être localisés. Lorsque la stratégie de reconditionnement géométrique déciderait de faire un reconditionnement tout-en-un, la stratégie génère alors un paquet de détritus pour tous les objets inaccessibles. Les objets qui font déjà partie d'un paquet de détritus seront expirés.

Cette stratégie de reconditionnement remplace entièrement la stratégie gc et est recommandée pour les grands dépôts. * incremental : Ce paramètre optimise pour effectuer de petites activités de maintenance qui ne suppriment aucune donnée. Il ne planifie pas la tâche gc, mais exécute les tâches prefetch et commit-graph toutes les heures, les tâches loose-objects et incremental-repack quotidiennement, et la tâche pack-refs hebdomadairement. La maintenance manuelle du dépôt utilise la tâche gc.

maintenance.<tâche>.enabled

Cette option de configuration booléenne contrôle si la tâche de maintenance nommée <tâche> est exécutée lorsqu'aucune option --task n'est spécifiée pour git maintenance run. Ces valeurs de configuration sont ignorées si une option --task est présente. Par défaut, seule maintenance.gc.enabled est vraie.

maintenance.<tâche>.schedule

Cette option de configuration contrôle si la tâche donnée <tâche> s'exécute ou non lors d'une commande git maintenance run --schedule=<fréquence>. La valeur doit être l'une des suivantes : « hourly », « daily », ou « weekly ».

maintenance.commit-graph.auto

Cette option de configuration entière contrôle la fréquence à laquelle la tâche commit-graph doit être exécutée dans le cadre de git maintenance run --auto. Si elle est à zéro, alors la tâche commit-graph ne s'exécutera pas avec l'option --auto. Une valeur négative forcera l'exécution de la tâche à chaque fois. Sinon, une valeur positive implique que la commande doit s'exécuter lorsque le nombre de commits atteignables qui ne sont pas dans le fichier commit-graph est au moins égal à la valeur de maintenance.commit-graph.auto. La valeur par défaut est 100.

maintenance.loose-objects.auto

Cette option de configuration entière contrôle la fréquence à laquelle la tâche loose-objects doit être exécutée dans le cadre de git maintenance run --auto. Si elle est à zéro, alors la tâche loose-objects ne s'exécutera pas avec l'option --auto. Une valeur négative forcera l'exécution de la tâche à chaque fois. Sinon, une valeur positive implique que la commande doit s'exécuter lorsque le nombre d'objets lâches est au moins égal à la valeur de maintenance.loose-objects.auto. La valeur par défaut est 100.

maintenance.loose-objects.batchSize

Cette option de configuration entière contrôle le nombre maximum d'objets lâches écrits dans un fichier de paquets lors de la tâche loose-objects. La valeur par défaut est cinquante mille. Utilisez la valeur 0 pour indiquer aucune limite.

maintenance.incremental-repack.auto

Cette option de configuration entière contrôle la fréquence à laquelle la tâche incremental-repack doit être exécutée dans le cadre de git maintenance run --auto. Si elle est à zéro, alors la tâche incremental-repack ne s'exécutera pas avec l'option --auto. Une valeur négative forcera l'exécution de la tâche à chaque fois. Sinon, une valeur positive implique que la commande doit s'exécuter lorsque le nombre de fichiers de paquets qui ne sont pas dans l'index multi-paquets est au moins égal à la valeur de maintenance.incremental-repack.auto. La valeur par défaut est 10.

maintenance.geometric-repack.auto

Cette option de configuration entière contrôle la fréquence à laquelle la tâche geometric-repack doit être exécutée dans le cadre de git maintenance run --auto. Si elle est à zéro, alors la tâche geometric-repack ne s'exécutera pas avec l'option --auto. Une valeur négative forcera l'exécution de la tâche à chaque fois. Sinon, une valeur positive implique que la commande doit s'exécuter soit lorsqu'il y a des fichiers de paquets qui doivent être fusionnés ensemble pour conserver la progression géométrique, soit lorsqu'il y a au moins autant d'objets lâches qui seraient écrits dans un nouveau fichier de paquets. La valeur par défaut est 100.

maintenance.geometric-repack.splitFactor

Cette option de configuration entière contrôle le facteur utilisé pour la séquence géométrique. Voir l'option --geometric= dans git-repack(1) pour plus de détails. La valeur par défaut est 2.

maintenance.reflog-expire.auto

Cette option de configuration entière contrôle la fréquence à laquelle la tâche reflog-expire doit être exécutée dans le cadre de git maintenance run --auto. Si elle est à zéro, alors la tâche reflog-expire ne s'exécutera pas avec l'option --auto. Une valeur négative forcera l'exécution de la tâche à chaque fois. Sinon, une valeur positive implique que la commande doit s'exécuter lorsque le nombre d'entrées de reflog expirées dans le reflog de « HEAD » est au moins égal à la valeur de maintenance.loose-objects.auto. La valeur par défaut est 100.

maintenance.rerere-gc.auto

Cette option de configuration entière contrôle la fréquence à laquelle la tâche rerere-gc doit être exécutée dans le cadre de git maintenance run --auto. Si elle est à zéro, alors la tâche rerere-gc ne s'exécutera pas avec l'option --auto. Une valeur négative forcera l'exécution de la tâche à chaque fois. Sinon, toute valeur positive implique que la commande s'exécutera lorsque le répertoire « rr-cache » existe et contient au moins une entrée, qu'elle soit obsolète ou non. Cette heuristique pourra être affinée à l'avenir. La valeur par défaut est 1.

maintenance.worktree-prune.auto

Cette option de configuration entière contrôle la fréquence à laquelle la tâche worktree-prune doit être exécutée dans le cadre de git maintenance run --auto. Si elle est à zéro, alors la tâche worktree-prune ne s'exécutera pas avec l'option --auto. Une valeur négative forcera l'exécution de la tâche à chaque fois. Sinon, une valeur positive implique que la commande doit s'exécuter lorsque le nombre d'arbres de travail supprimables dépasse la valeur. La valeur par défaut est 1.
