--no-track

Ne pas configurer la configuration "amont", même si la branch.autoSetupMerge variable de configuration est vraie.

--guess, --no-guess

Si <branch> n'est pas trouvé mais qu'il existe une branche de suivi dans exactement un distant (appelons-le <remote>) avec un nom correspondant, traiter cela comme équivalent à 
$ git checkout -b <branch> --track <remote>/<branch>

Si la branche existe dans plusieurs distants et que l'un d'entre eux est nommé par la checkout.defaultRemote variable de configuration, nous utiliserons celui-ci pour les besoins de la désambiguïsation, même si le <branch> n'est pas unique à travers tous les distants. Définissez-la par exemple à checkout.defaultRemote=origin pour toujours extraire les branches distantes de là si <branch> est ambigu mais existe sur le origin distant. Voir aussi checkout.defaultRemote dans git-config(1).

--guess est le comportement par défaut. Utilisez --no-guess pour le désactiver.

Le comportement par défaut peut être défini via la checkout.guess variable de configuration.

-l

Créer le reflog de la nouvelle branche ; voir git-branch(1) pour les détails.

-d, --detach

Plutôt que d'extraire une branche pour y travailler, extraire un commit pour inspection et expériences jetables. C'est le comportement par défaut de git checkout <commit> lorsque <commit> n'est pas un nom de branche. Voir la section "DETACHED HEAD" ci-dessous pour les détails.

--orphan <new-branch>

Créer une nouvelle branche non née, nommée <new-branch>, démarrée à partir de <start-point> et basculer vers elle. Le premier commit fait sur cette nouvelle branche n'aura aucun parent et il sera la racine d'une nouvelle histoire totalement déconnectée de toutes les autres branches et commits.

L'index et l'arbre de travail sont ajustés comme si vous aviez précédemment exécuté git checkout <start-point>. Cela vous permet de démarrer une nouvelle histoire qui enregistre un ensemble de chemins similaire à <start-point> en exécutant facilement git commit -a pour faire le commit racine.

Cela peut être utile lorsque vous voulez publier l'arbre d'un commit sans exposer son histoire complète. Vous pourriez vouloir faire cela pour publier une branche open source d'un projet dont l'arbre actuel est "propre", mais dont l'histoire complète contient des parties propriétaires ou autrement encombrées de code.

Si vous voulez démarrer une histoire déconnectée qui enregistre un ensemble de chemins totalement différent de celui de <start-point>, alors vous devriez effacer l'index et l'arbre de travail juste après la création de la branche orpheline en exécutant git rm -rf . depuis le niveau supérieur de l'arbre de travail. Ensuite vous serez prêt à préparer vos nouveaux fichiers, en repeuplant l'arbre de travail, en les copiant d'ailleurs, en extrayant une archive tar, etc.

--ignore-skip-worktree-bits

En mode sparse checkout, git checkout -- <path>... ne mettrait à jour que les entrées correspondant à <paths> et aux motifs sparse dans $GIT_DIR/info/sparse-checkout. Cette option ignore les motifs sparse et ajoute de retour tous les fichiers dans <path>....

-m, --merge

Lors du changement de branche, si vous avez des modifications locales à un ou plusieurs fichiers qui sont différents entre la branche actuelle et la branche vers laquelle vous basculez, la commande refuse de changer de branche afin de préserver vos modifications dans le contexte. Cependant, avec cette option, une fusion à trois voies entre la branche actuelle, le contenu de votre arbre de travail et la nouvelle branche est faite, et vous serez sur la nouvelle branche.

Lorsqu'un conflit de fusion se produit, les entrées d'index pour les chemins en conflit sont laissées non fusionnées, et vous devez résoudre les conflits et marquer les chemins résolus avec git add (ou git rm si la fusion doit résulter en la suppression du chemin).

Lors de l'extraction de chemins depuis l'index, cette option vous permet de recréer la fusion en conflit dans les chemins spécifiés. Cette option ne peut pas être utilisée lors de l'extraction de chemins depuis un tree-ish.

Lors du changement de branche avec --merge, les changements indexés peuvent être perdus.

--conflict=<style>

Identique à l'option --merge ci-dessus, mais change la façon dont les fragments en conflit sont présentés, en écrasant la merge.conflictStyle variable de configuration. Les valeurs possibles sont merge (par défaut), diff3, et zdiff3.

-p, --patch

Sélectionner interactivement les fragments dans la différence entre le <tree-ish> (ou l'index, si non spécifié) et l'arbre de travail. Les fragments choisis sont ensuite appliqués en inverse à l'arbre de travail (et si un <tree-ish> a été spécifié, à l'index).

Cela signifie que vous pouvez utiliser git checkout -p pour sélectionnellement abandonner des éditions de votre arbre de travail actuel. Voir la section "Interactive Mode" de git-add(1) pour apprendre à utiliser le mode --patch .

Notez que cette option utilise le mode sans superposition par défaut (voir aussi --overlay), et ne supporte actuellement pas le mode superposition.

-U<n>, --unified=<n>

Générer des diffs avec <n> lignes de contexte. Par défaut à diff.context ou 3 si l'option de configuration n'est pas définie.

--inter-hunk-context=<n>

Afficher le contexte entre les fragments de diff, jusqu'au <number> de lignes spécifié, fusionnant ainsi les fragments qui sont proches les uns des autres. Par défaut à diff.interHunkContext ou 0 si l'option de configuration n'est pas définie.

--ignore-other-worktrees

git checkout refuse lorsque la branche voulue est déjà extraire ou autrement en cours d'utilisation par un autre worktree. Cette option le fait extraire la branche quand même. En d'autres termes, la branche peut être en cours d'utilisation par plus d'un worktree.

--overwrite-ignore, --no-overwrite-ignore

Écraser silencieusement les fichiers ignorés lors du changement de branche. C'est le comportement par défaut. Utilisez --no-overwrite-ignore pour abandonner l' opération lorsque la nouvelle branche contient des fichiers ignorés.

--recurse-submodules, --no-recurse-submodules

Utiliser --recurse-submodules mettra à jour le contenu de tous les sous-modules actifs selon le commit enregistré dans le superprojet. Si des modifications locales dans un sous-module seraient écrasées, l'extraction échouera sauf si -f est utilisé. Si rien (ou --no-recurse-submodules) est utilisé, les arbres de travail des sous-modules ne seront pas mis à jour. Tout comme git-submodule(1), cela détachera le HEAD du sous-module.

--overlay, --no-overlay

Dans le mode superposition par défaut, git checkout ne supprime jamais de fichiers de l'index ou de l'arbre de travail. Lors de la spécification de --no-overlay, les fichiers qui apparaissent dans l'index et l'arbre de travail, mais pas dans <tree-ish> sont supprimés, pour les faire correspondre exactement à <tree-ish> .

--pathspec-from-file=<file>

Le pathspec est passé dans <file> au lieu des arguments de la ligne de commande. Si <file> est exactement - alors l'entrée standard est utilisée. Les éléments du pathspec sont séparés par LF ou CR/LF. Les éléments du pathspec peuvent être entre guillemets comme expliqué pour la variable de configuration core.quotePath (voir git-config(1)). Voir aussi --pathspec-file-nul et l'option globale --literal-pathspecs.

--pathspec-file-nul

Seulement significatif avec --pathspec-from-file. Les éléments du pathspec sont séparés par le caractère NUL et tous les autres caractères sont pris littéralement (y compris les sauts de ligne et les guillemets).

<branch>

Branche à extraire ; si elle fait référence à une branche (c'est-à-dire un nom qui, lorsqu'on lui préfixe "refs/heads/", est une ref valide), alors cette branche est extraite. Sinon, si elle fait référence à un commit valide, votre HEAD devient "détaché" et vous n'êtes plus sur aucune branche (voir ci-dessous pour les détails).

Vous pouvez utiliser la syntaxe @{-N} pour faire référence à la Nième dernière branche/commit extraite avec l'opération "git checkout". Vous pouvez aussi spécifier - qui est synonyme de @{-1}.

En tant que cas particulier, vous pouvez utiliser <rev-a>...<rev-b> comme raccourci pour la base de fusion de <rev-a> et <rev-b> s'il y a exactement une base de fusion. Vous pouvez omettre au plus un de <rev-a> et <rev-b>, auquel cas il vaut par défaut HEAD.

<new-branch>

Nom pour la nouvelle branche.

<start-point>

Le nom d'un commit à partir duquel démarrer la nouvelle branche ; voir git-branch(1) pour les détails. Par défaut à HEAD.

En tant que cas particulier, vous pouvez utiliser <rev-a>...<rev-b> comme raccourci pour la base de fusion de <rev-a> et <rev-b> s'il y a exactement une base de fusion. Vous pouvez omettre au plus un de <rev-a> et <rev-b>, auquel cas il vaut par défaut HEAD.

<tree-ish>

Arbre depuis lequel extraire (lorsque des chemins sont donnés). Si non spécifié, l'index sera utilisé.

En tant que cas particulier, vous pouvez utiliser <rev-a>...<rev-b> comme raccourci pour la base de fusion de <rev-a> et <rev-b> s'il y a exactement une base de fusion. Vous pouvez omettre au plus un de <rev-a> et <rev-b>, auquel cas il vaut par défaut HEAD.

--

Ne pas interpréter d'autres arguments comme des options.

<pathspec>...

Limite les chemins affectés par l'opération.

Pour plus de détails, voir l'entrée pathspec dans gitglossary(7).

DETACHED

HEAD

HEAD fait normalement référence à une branche nommée (par exemple, master). Pendant ce temps, chaque branche fait référence à un commit spécifique. Examinons un dépôt avec trois commits, dont l'un est tagué, et avec la branche master extraite :

           HEAD (fait référence à la branche 'master')
            |
            v
a---b---c  branche 'master' (fait référence au commit 'c')
    ^
    |
  tag 'v2.0' (fait référence au commit 'b')

Lorsqu'un commit est créé dans cet état, la branche est mise à jour pour faire référence au nouveau commit. Plus précisément, git commit crée un nouveau commit d, dont le parent est le commit c, puis met à jour la branche master pour qu'elle fasse référence au nouveau commit d. HEAD fait toujours référence à la branche master et fait donc indirectement référence au commit d :

$ éditer ; git ajouter ; git commit
               HEAD (fait référence à la branche 'master')
                |
                v
a---b---c---d  branche 'master' (fait référence au commit 'd')
    ^
    |
  tag 'v2.0' (fait référence au commit 'b')

Il est parfois utile de pouvoir extraire un commit qui n'est pas à la pointe d'une branche nommée, ou même de créer un nouveau commit qui n'est référencé par aucune branche nommée. Examinons ce qui se passe lorsque nous extrayons le commit b (nous montrons ici deux façons de procéder) :

$ git checkout v2.0  # ou
$ git checkout master^^
   HEAD (fait référence au commit 'b')
    |
    v
a---b---c---d  branche 'master' (fait référence au commit 'd')
    ^
    |
  tag 'v2.0' (fait référence au commit 'b')

Notez que quelle que soit la commande d'extraction utilisée, HEAD fait maintenant référence directement au commit b. C'est ce qu'on appelle l'état detached HEAD. Cela signifie simplement que HEAD fait référence à un commit spécifique, par opposition à une branche nommée. Voyons ce qui se passe lorsque nous créons un commit :

$ éditer ; git ajouter ; git commit
     HEAD (fait référence au commit 'e')
      |
      v
      e
     /
a---b---c---d  branche 'master' (fait référence au commit 'd')
    ^
    |
  tag 'v2.0' (fait référence au commit 'b')

Il y a maintenant un nouveau commit e, mais il n'est référencé que par HEAD. Nous pouvons bien sûr ajouter encore un autre commit dans cet état :

$ éditer ; git ajouter ; git commit
         HEAD (fait référence au commit 'f')
          |
          v
      e---f
     /
a---b---c---d  branche 'master' (fait référence au commit 'd')
    ^
    |
  tag 'v2.0' (fait référence au commit 'b')

En fait, nous pouvons effectuer toutes les opérations Git normales. Mais regardons ce qui se passe lorsque nous extrayons ensuite master :

$ git checkout master
               HEAD (fait référence à la branche 'master')
      e---f     |
     /          v
a---b---c---d  branche 'master' (fait référence au commit 'd')
    ^
    |
  tag 'v2.0' (fait référence au commit 'b')

Il est important de réaliser qu'à ce stade, rien ne fait référence au commit f. Finalement, le commit f (et par extension le commit e) sera supprimé par le processus de nettoyage de Git, à moins que nous ne créions une référence avant que cela ne se produise. Si nous ne nous sommes pas encore éloignés du commit f, l'une de ces commandes créera une référence à celui-ci :

$ git checkout -b foo  # ou "git switch -c foo"  (1)
$ git branch foo                                 (2)
$ git tag foo                                    (3)
1. crée une nouvelle branche foo, qui fait référence au commit f, puis met à jour HEAD pour qu'elle fasse référence à la branche foo. Autrement dit, nous ne serons plus dans l'état detached HEAD après cette commande.
2. crée de manière similaire une nouvelle branche foo, qui fait référence au commit f, mais laisse HEAD detached.
3. crée un nouveau tag foo, qui fait référence au commit f, laissant HEAD detached.

Si nous nous sommes éloignés du commit f, nous devons d'abord récupérer son nom d'objet (généralement en utilisant git reflog), puis nous pouvons créer une référence à celui-ci. Par exemple, pour voir les deux derniers commits auxquels HEAD a fait référence, nous pouvons utiliser l'une de ces commandes :

$ git reflog -2 HEAD # ou
$ git log -g -2 HEAD

DISAMBIGUATION DES ARGUMENTS

Lorsque vous exécutez git checkout <quelque chose>, Git essaie de deviner si <quelque chose> est destiné à être une branche, un commit ou un ensemble de fichiers, puis bascule vers cette branche ou ce commit, ou restaure les fichiers spécifiés.

En cas d'ambiguïté, Git traitera <quelque chose> comme une branche ou un commit, mais vous pouvez utiliser le double tiret -- pour forcer Git à traiter le paramètre comme une liste de fichiers et/ou de répertoires, comme ceci :

git checkout -- fichier.txt

EXEMPLES

1. Chemins d'accès

La séquence suivante extrait la branche master, ramène le Makefile à deux révisions précédentes, supprime hello.c par erreur et le récupère depuis l'index.

$ git checkout master             (1)
$ git checkout master~2 Makefile  (2)
$ rm -f hello.c
$ git checkout hello.c            (3)
1. changer de branche
2. prendre un fichier d'un autre commit
3. restaurer hello.c à partir de l'index

Si vous souhaitez extraire *tous* les fichiers source C de l'index, vous pouvez dire :

$ git checkout -- '*.c'

Notez les guillemets autour de *.c. Le fichier hello.c sera également extrait, même s'il n'est plus dans l'arbre de travail, car le globbing de fichiers est utilisé pour faire correspondre les entrées dans l'index (pas dans l'arbre de travail par le shell).

Si vous avez une branche malencontreuse nommée hello.c, cette étape serait confondue avec une instruction pour passer à cette branche. Vous devriez plutôt écrire :

$ git checkout -- hello.c

2. Fusionner

Après avoir travaillé sur la mauvaise branche, passer à la bonne branche se ferait en utilisant :

$ git checkout mytopic

Cependant, votre branche "erronée" et la branche mytopic correcte peuvent différer dans les fichiers que vous avez modifiés localement, auquel cas l'extraction ci-dessus échouerait comme suit :

$ git checkout mytopic
erreur : Vous avez des modifications locales sur 'frotz' ; passez à une autre branche.

Vous pouvez donner le drapeau -m à la commande, ce qui tenterait une fusion à trois voies :

$ git checkout -m mytopic
Fusion automatique de frotz

Après cette fusion à trois voies, les modifications locales ne sont *pas* enregistrées dans votre fichier d'index, donc git diff vous montrerait les modifications que vous avez apportées depuis la pointe de la nouvelle branche.

3. Conflit de fusion

Lorsqu'un conflit de fusion se produit lors du changement de branche avec l'option -m, vous verrez quelque chose comme ceci :

$ git checkout -m mytopic
Fusion automatique de frotz
ERREUR : Conflit de fusion dans frotz
fatal : l'outil de fusion a échoué

À ce stade, git diff affiche les modifications fusionnées proprement comme dans l'exemple précédent, ainsi que les modifications dans les fichiers en conflit. Modifiez et résolvez le conflit et marquez-le comme résolu avec git add comme d'habitude :

$ éditer frotz
$ git add frotz

CONFIGURATION

Tout ce qui suit cette ligne dans cette section est inclus sélectivement de la documentation de git-config(1). Le contenu est le même que celui qui s'y trouve :

checkout.defaultRemote

Lorsque vous exécutez git checkout <quelque chose> ou git switch <quelque chose> et que vous n'avez qu'un seul remote, il peut implicitement retomber sur l'extraction et le suivi par exemple de origin/<quelque chose>. Cela cesse de fonctionner dès que vous avez plus d'un remote avec une référence <quelque chose>. Ce paramètre permet de définir le nom d'un remote préféré qui devrait toujours l'emporter lors de la désambiguïsation. Le cas d'utilisation typique est de le définir sur origin.

Actuellement, cela est utilisé par git-switch(1) et git-checkout(1) lorsque git checkout <quelque chose> ou git switch <quelque chose> extrait la branche <quelque chose> sur un autre remote, et par git-worktree(1) lorsque git worktree add fait référence à une branche distante. Ce paramètre pourrait être utilisé pour d'autres commandes de type checkout ou des fonctionnalités à l'avenir.

checkout.guess

Fournit la valeur par défaut pour l'option --guess ou --no-guess dans git checkout et git switch. Voir git-switch(1) et git-checkout(1).

checkout.workers

Le nombre de processus parallèles à utiliser lors de la mise à jour de l'arbre de travail. La valeur par défaut est un, c'est-à-dire une exécution séquentielle. Si la valeur est définie sur moins d'un, Git utilisera autant de processus que le nombre de cœurs logiques disponibles. Ce paramètre et checkout.thresholdForParallelism affectent toutes les commandes qui effectuent une extraction. Par exemple, checkout, clone, reset, sparse-checkout, etc.

Note
L'extraction parallèle offre généralement de meilleures performances pour les dépôts situés sur des SSD ou sur NFS. Pour les dépôts sur des disques rotatifs et/ou des machines avec un petit nombre de cœurs, l'extraction séquentielle par défaut offre souvent de meilleures performances. La taille et le niveau de compression d'un dépôt peuvent également influencer les performances de la version parallèle.

checkout.thresholdForParallelism

Lors de l'exécution d'une extraction parallèle avec un petit nombre de fichiers, le coût de la création de sous-processus et de la communication inter-processus peut
l'emportent sur les gains de parallélisation. Ce paramètre vous permet de définir le nombre minimal de fichiers pour lesquels la vérification parallèle doit être tentée. La valeur par défaut est 100.
