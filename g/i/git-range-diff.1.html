GIT-RANGE-DIFF(1) Manuel Git GIT-RANGE-DIFF(1)

NOM

git-range-diff - Compare deux plages de commits (par exemple, deux versions d'une branche)

SYNTAXE

git range-diff [--color=[<quand>]] [--no-color] [<options-diff>]
        [--no-dual-color] [--creation-factor=<facteur>]
        [--left-only | --right-only] [--diff-merges=<format>]
        [--remerge-diff]
        ( <plage1> <plage2> | <rev1>...<rev2> | <base> <rev1> <rev2> )
        [[--] <chemin>...]

DESCRIPTION

Cette commande affiche les différences entre deux versions d'une série de patchs, ou plus généralement, deux plages de commits (en ignorant les commits de fusion).

En présence d'arguments <chemin>, ces plages de commits sont limitées en conséquence.

Pour ce faire, elle trouve d'abord des paires de commits de chaque plage de commits qui se correspondent. Deux commits sont dits correspondants lorsque la différence entre leurs patchs (c'est-à-dire les informations de l'auteur, le message de commit et le diff du commit) est raisonnablement petite par rapport à la taille des patchs. Voir « Algorithme » ci-dessous pour les détails.

Enfin, la liste des commits correspondants est affichée dans l'ordre de la deuxième plage de commits, les commits non correspondants étant insérés juste après que tous leurs ancêtres aient été affichés.

Il existe trois façons de spécifier les plages de commits :

•<plage1> <plage2> : Chaque plage de commits peut être de la forme <base>..<rev>, <rev>^! ou <rev>^-<n>. Voir SPÉCIFICATION DES PLAGES dans gitrevisions(7) pour plus de détails.
•<rev1>...<rev2>. Ceci est équivalent à <rev2>..<rev1> <rev1>..<rev2>.
•<base> <rev1> <rev2> : Ceci est équivalent à <base>..<rev1> <base>..<rev2>.

OPTIONS

--no-dual-color

Lorsque les diffs des commits diffèrent, `git range-diff` recrée la coloration des diffs d'origine, et ajoute des marqueurs de diff externes +/- avec un fond rouge/vert pour rendre plus facile la visualisation, par exemple, quand il y a eu un changement dans les lignes exactes ajoutées.

De plus, les lignes du diff des commits qui ne sont présentes que dans la première plage de commits sont affichées en « atténué » (cela peut être remplacé en utilisant le paramètre de configuration color.diff.<slot> où <slot> est l'un de contextDimmed, oldDimmed et newDimmed), et les lignes du diff des commits qui ne sont présentes que dans la seconde plage de commits sont affichées en gras (ce qui peut être remplacé en utilisant les paramètres de configuration color.diff.<slot> avec <slot> étant l'un de contextBold, oldBold ou newBold).

Ceci est connu sous le nom de « double coloration » par range-diff. Utilisez --no-dual-color pour revenir à la coloration de toutes les lignes selon les marqueurs de diff externes (et ignorer complètement le diff interne en ce qui concerne la couleur).

--creation-factor=<pourcentage>

Définit le facteur de correction pour le coût de création/suppression à <pourcentage>. La valeur par défaut est 60. Essayez une valeur plus grande si git range-diff considère à tort un changement majeur comme une réécriture totale (suppression d'un commit et ajout d'un autre), et une valeur plus petite dans le cas inverse. Voir la section « Algorithme » ci-dessous pour une explication de la raison pour laquelle cela est nécessaire.

--left-only

Supprime les commits qui manquent dans la première plage spécifiée (ou la plage « gauche » lorsque vous utilisez le format <rev1>...<rev2>).

--right-only

Supprime les commits qui manquent dans la seconde plage spécifiée (ou la plage « droite » lorsque vous utilisez le format <rev1>...<rev2>).

--diff-merges=<format>

Au lieu d'ignorer les commits de fusion, génère des diffs pour eux en utilisant l'option correspondante --diff-merges=<format> de git-log(1), et les inclut dans la comparaison.

Note : Dans le cas courant, le mode remerge sera le plus naturel à utiliser, car il affiche uniquement la différence par rapport à ce que le système de fusion de Git aurait produit. Autrement dit, si un commit de fusion est le résultat d'un git merge sans conflit, le mode remerge le représentera par un diff vide.

--remerge-diff

Option de commodité, équivalente à --diff-merges=remerge.

--notes[=<ref>], --no-notes

Cette option est transmise au programme git log (voir git-log(1)) qui génère les patchs.

<plage1> <plage2>

Compare les commits spécifiés par les deux plages, où <plage1> est considérée comme une version plus ancienne de <plage2>.

<rev1>...<rev2>

Équivalent à passer <rev2>..<rev1> et <rev1>..<rev2>.

<base> <rev1> <rev2>

Équivalent à passer <base>..<rev1> et <base>..<rev2>. Notez que <base> n'a pas besoin d'être le point de branche exact des branches. Par exemple : après avoir rebasé une branche my-topic, git range-diff my-topic@{u} my-topic@{1} my-topic montrerait les différences introduites par le rebase.

git range-diff accepte également les options de diff régulières (voir git-diff(1)), notamment les options --color=[<quand>] et --no-color. Ces options sont utilisées lors de la génération du « diff entre patchs », c'est-à-dire pour comparer l'auteur, le message de commit et le diff des commits anciens/nouveaux correspondants. Il n'existe actuellement aucun moyen de modifier la plupart des options de diff passées à git log lors de la génération de ces patchs.

STABILITÉ DE LA SORTIE

La sortie de la commande range-diff est sujette à modification. Elle est destinée à être une sortie lisible par l'homme (porcelaine), et non quelque chose qui peut être utilisé entre différentes versions de Git pour obtenir un range-diff textuellement stable (contrairement à l'option --stable de git-patch-id(1)). Il n'y a pas non plus d'équivalent de git-apply(1) pour range-diff, la sortie n'est pas destinée à être lisible par machine.

Ceci est particulièrement vrai lors du passage d'options de diff. Actuellement, certaines options comme --stat peuvent, par effet émergent, produire une sortie assez inutile dans le contexte de range-diff. Les futures versions de range-diff pourront interpréter ces options d'une manière spécifique à range-diff (par exemple, pour --stat produisant une sortie lisible résumant comment le stat du diff a changé).

CONFIGURATION

Cette commande utilise les paramètres diff.color.* et pager.range-diff (ce dernier est activé par défaut). Voir git-config(1).

Lorsque la sortie est dirigée vers un terminal, elle est colorée par défaut, tout comme la sortie normale de git diff. De plus, la première ligne (ajout d'un commit) est verte, la dernière ligne (suppression d'un commit) est rouge, la deuxième ligne (avec une correspondance parfaite) est jaune comme l'en-tête de commit de la sortie de git show, et la troisième ligne colore l'ancien commit en rouge, le nouveau en vert et le reste comme l'en-tête de commit de git show.

Un diff de diffs coloré naïvement est en fait un peu difficile à lire, car il colore les lignes entières en rouge ou en vert. La ligne qui a ajouté « What is unexpected » dans l'ancien commit, par exemple, est complètement rouge, même si l'intention de l'ancien commit était d'ajouter quelque chose.

Pour aider avec cela, range utilise le --dual-color mode par défaut. Dans ce mode, le diff de diffs conservera les couleurs du diff original, et préfixera les lignes avec des marqueurs -/+ dont le arrière-plan est rouge ou vert, pour rendre plus évident qu'ils décrivent comment le diff lui-même a changé.

ALGORITHME

L'idée générale est la suivante : nous générons une matrice de coût entre les commits des deux plages de commits, puis nous résolvons l'affectation de coût minimal.

La matrice de coût est remplie comme suit : pour chaque paire de commits, les deux diffs sont générés et le « diff de diffs » est généré, avec 3 lignes de contexte, puis le nombre de lignes de ce diff est utilisé comme coût.

Pour éviter les faux positifs (par exemple, lorsqu'un patch a été supprimé et qu'un patch sans rapport a été ajouté entre deux itérations de la même série de patches), la matrice de coût est étendue pour permettre cela, en ajoutant des entrées à coût fixe pour les suppressions/ajouts en bloc.

Exemple : Soient les commits 1--2 la première itération d'une série de patches et A--C la deuxième itération. Supposons que A est un cherry-pick de 2, et que C est un cherry-pick de 1 mais avec une petite modification (disons, une faute de frappe corrigée). Visualisons les commits comme un graphe biparti :

    1            A
    2            B
                 C

Nous cherchons une « meilleure » explication de la nouvelle série en termes de l'ancienne. Nous pouvons représenter une « explication » comme une arête dans le graphe :

    1            A
               /
    2 --------'  B
                 C

Cette explication est « gratuite » car il n'y a eu aucun changement. De même C pourrait être expliqué en utilisant 1, mais cela a un certain coût c>0 à cause de la modification :

    1 ----.      A
          |    /
    2 ----+---'  B
          |
          `----- C
          c>0

En termes mathématiques, ce que nous cherchons est une sorte de appariement biparti de coût minimal ; « 1 » est apparié à C à un certain coût, etc. Le graphe sous-jacent est en fait un graphe biparti complet ; le coût que nous associons à chaque arête est la taille du diff entre les patches des deux commits. Pour expliquer également les nouveaux commits, nous introduisons des nœuds fictifs des deux côtés :

    1 ----.      A
          |    /
    2 ----+---'  B
          |
    o     `----- C
          c>0
    o            o
    o            o

Le coût d'une arête o--C est la taille du Cdiff, modifié par un facteur d'ajustement qui devrait être inférieur à 100 %. Le coût d'une arête o--o est gratuit. Le facteur d'ajustement est nécessaire car même si 1 et C n'ont rien en commun, ils peuvent quand même partager quelques lignes vides et autres, ce qui peut rendre l'affectation 1--C, o--o légèrement moins chère que 1--o, o--C même si 1 et C n'ont rien en commun. Avec le facteur d'ajustement, nous exigeons une partie commune beaucoup plus grande pour considérer les patches comme correspondants.

Le temps total nécessaire pour calculer cet algorithme est le temps nécessaire pour calculer n+m diffs de commits puis n*m diffs de patches, plus le temps nécessaire pour calculer l'affectation de coût minimal entre n et m diffs. Git utilise une implémentation de l'algorithme de Jonker-Volgenant pour résoudre le problème d'affectation, qui a une complexité temporelle cubique. L'appariement trouvé dans ce cas ressemblera à ceci :

    1 ----.      A
          |    /
    2 ----+---'  B
       .--+-----'
    o -'  `----- C
          c>0
    o ---------- o
    o ---------- o
