DESCRIPTIO

N

Créer, décompresser et manipuler des fichiers « bundle ». Les bundles sont utilisés pour le transfert « hors ligne » d'objets Git sans un « serveur » actif de l'autre côté de la connexion

réseau.

Ils peuvent être utilisés pour créer des sauvegardes incrémentielles et complètes d'un dépôt (voir l'exemple de « sauvegarde complète » dans « EXEMPLES »), et pour relayer l'état des références d'un dépôt à un autre (voir le deuxième exemple)

.

Les commandes Git qui récupèrent ou « lisent » autrement via des protocoles tels que ssh:// et https:// peuvent également opérer sur des fichiers bundle. Il est possible git-clone(1) un nouveau dépôt à partir d'un bundle, d'utiliser git-fetch(1) pour récupérer depuis un bundle, et de lister les références qu'il contient avec git-ls-remote(1). Il n'y a pas de support « écriture » correspondant, c'est-à-dire qu'un git push vers un bundl

e n'est pas pr
is en charge.

FORMAT DU

BUNDLE

Les bundles sont des fichiers .pack (voir git-pack-objects(1)) avec un en-tête indiquant quelles références sont contenues dans le

bundle.

Comme le format d'archive pack lui-même, les bundles peuvent être autonomes, ou créés en utilisant des exclusions. Voir la section « PRÉREQUIS DES OBJETS »

ci-dessous.

Les bundles créés en utilisant des exclusions de révision sont des « packs fins » créés en utilisant l'option --thin de git-pack-objects(1), et décompressés en utilisant l'option --fix-thin de git-index-pa

ck(1).

Il n'existe pas d'option pour créer un « pack épais » lors de l'utilisation d'exclusions de révision, et les utilisateurs ne devraient pas se soucier de la différence. En utilisant des « packs fins », les bundles créés en utilisant des exclusions sont plus petits en taille. Le fait qu'ils soient « fins » sous le capot est simplement noté ici comme une curiosité, et comme une référence à d'autres

documentations.

Voir gitformat-bundle(5) pour plus de détails et la discussion du « pack fin » dans gitformat-pack(5) po

ur plus de
détails.

OPTION

S

create [options] <file> <git-rev-list-args

>
Utilisé pour créer un bundle nommé file. Cela nécessite les arguments <git-rev-list-args> pour définir le contenu du bundle. options contient les options spécifiques à la sous-commande git bundle create . Si file est -, le bundle est écrit sur
stdout.

verify

<file>
Utilisé pour vérifier qu'un fichier bundle est valide et qu'il s'appliquera proprement au dépôt actuel. Cela inclut des vérifications sur le format du bundle lui-même ainsi que la vérification que les commits prérequis existent et sont entièrement liés dans le dépôt actuel. Ensuite, git bundle imprime une liste de commits manquants, s'il y en a. Enfin, des informations sur des capacités supplémentaires, telles que « object filter », sont imprimées. Voir « Capabilities » dans gitformat-bundle(5) pour plus d'informations. Le code de sortie est zéro pour un succès, mais sera non nul si le fichier bundle est invalide. Si file est -, le bundle est lu depuis
stdin.

list-heads

<file>
Liste les références définies dans le bundle. Si suivi d'une liste de références, seules les références correspondant à celles données sont imprimées. Si file est -, le bundle est lu depuis
stdin.

unbundle

<file>
Passe les objets du bundle à git index-pack pour stockage dans le dépôt, puis imprime les noms de toutes les références définies. Si une liste de références est donnée, seules les références correspondant à celles de la liste sont imprimées. Cette commande est vraiment de la tuyauterie, destinée à être appelée uniquement par git fetch. Si file est -, le bundle est lu depuis
stdin.

<git-rev-list-args

>
Une liste d'arguments, acceptables par git rev-parse et git rev-list (et contenant une référence nommée, voir SPÉCIFICATION DES RÉFÉRENCES ci-dessous), qui spécifie les objets et références spécifiques à transporter. Par exemple, master~10..master fait en sorte que la référence master actuelle soit empaquetée avec tous les objets ajoutés depuis son 10e commit ancêtre. Il n'y a pas de limite explicite au nombre de références et d'objets qui peuvent être
empaquetés.

[<refname>...

]
Une liste de références utilisée pour limiter les références signalées comme disponibles. Cela est principalement utile pour git fetch, qui s'attend à recevoir uniquement les références demandées et pas nécessairement tout ce qui est dans le pack (dans ce cas, git bundle se comporte comme git fetch-
pack).

--progres

s
L'état de progression est rapporté sur le flux d'erreur standard par défaut lorsqu'il est attaché à un terminal, sauf si -q est spécifié. Ce drapeau force l'état de progression même si le flux d'erreur standard n'est pas dirigé vers un
terminal.

--version=<version

>
Spécifie la version du bundle. La version 2 est l'ancien format et ne peut être utilisée qu'avec des dépôts SHA-1 ; la version 3 plus récente contient des capacités qui permettent des extensions. La valeur par défaut est le format le plus ancien pris en charge, basé sur l'algorithme de hachage
utilisé.

-q,

--quiet
Ce drapeau fait en sorte que la com
mande ne rapporte pas sa progressi
on sur le flux d'erreur standard.

SPÉCIFICATION DES

RÉFÉRENCES

Les révisions doivent être accompagnées de noms de références pour être empaquetées dans un bundle. Alternativement --all peut être utilisé pour empaqueter toutes les

références.

Plus d'une référence peut être empaquetée, et plus d'un ensemble de objets prérequis peut être spécifié. Les objets empaquetés sont ceux qui ne sont pas contenus dans l'union des

prérequis.

La commande git bundle create résout les noms de références pour vous en utilisant les mêmes règles que git rev-parse --abbrev-ref=loose. Chaque prérequis peut être spécifié explicitement (par ex. ^master~10), ou implicitement (par ex. master~10..master, --since=10.days.ago maste

r).

Tous ces cas simples sont OK (en supposant que nous avons une branche « master » et « next »)

: 
$ git bundle create master.bundle master
$ echo master | git bundle create m
aster.bundle --stdin $ git bundle create master-and-next.bundle master next $
(echo master; echo next) | git bundle create master-and-next.bundle --stdin

Et ceux-ci aussi (et les mêmes mais avec --stdin omis)

: 
$ git bundle create recent-master.bundle mas
ter~10..master $ git bundle create recent-u
pdates.bundle master~10..master next~5..next

Un nom de révision ou une plage dont le côté droit ne peut pas être résolu en une référence n'est pas accepté

: 
$ git bundle create HEAD.bundle $(git rev-parse H
EAD) fatal: Refusing to create empty bundle. $ gi
t bundle create master-yesterday.bundle master~10.
.master~5 fatal: Refusing to create empty bundle.

PRÉREQUIS DES

OBJETS

Lors de la création de bundles, il est possible de créer un bundle autonome qui peut être décompressé dans un dépôt sans histoire commune, ainsi qu'en fournissant des révisions négatives pour exclure les objets nécessaires dans les parties précédentes de

l'histoire.

Fournir une révision telle que new à git bundle create créera un fichier bundle qui contient tous les objets accessibles depuis la révision new. Ce bundle peut être décompressé dans n'importe quel dépôt pour obtenir une histoire complète qui mène à la révision new

: 
$ git bundle
create ful
l.bundle new

Une plage de révisions telle que old..new produira un fichier bundle qui nécessitera que la révision old (et tous les objets accessibles depuis elle) existe pour que le bundle puisse être « décompresséuot;-able 

: 
$ git bundle
create full.bu
ndle old..new

Un bundle autonome sans aucun prérequis peut être extrait n'importe où, même dans un dépôt vide, ou être cloné (c'est-à-dire new, mais pas old..new

).

Il est préférable de faire preuve de prudence, ce qui peut entraîner la présence dans le fichier bundle d'objets déjà présents dans la destination, car ceux-ci sont ignorés lors de l'extraction à la

destination.

Si vous souhaitez fournir le même ensemble de références que celles qu'un clone direct depuis le dépôt source obtiendrait, utilisez --branches --tags pour les <git-rev-list

-args>.

La commande git bundle verify peut être utilisée pour vérifier si votre dép

ôt destinataire possède les commits pré
requis nécessaires pour un bundle.

EXEMPLE

S

Nous allons examiner deux cas 

:
1.Effectuer une sauvegarde complète d'un
dépôt
2.Transférer l'historique d'un dépôt vers une autre machine lorsque les deux machines n'ont pas de connexion
directe

Commençons par considérer une sauvegarde complète du dépôt. La commande suivante effectuera une sauvegarde complète du dépôt en ce sens que toutes les références sont incluses dans le bundle 

: 
$ git bundle
create backup
.bundle --all

Mais notez encore une fois que cela ne concerne que les références, c'est-à-dire que vous n'inclurez que les références et les commits qui y sont accessibles. Vous n'inclurez pas les autres états locaux, tels que le contenu de l'index, l'arbre de travail, le stash, la configuration du dépôt, les hooks,

etc.

Vous pouvez ensuite récupérer ce dépôt en utilisant par exemple git-clone(1) 

: 
$ git clone bac
kup.bundle <nouv
eau répertoire>

Pour l'exemple suivant, supposons que vous souhaitiez transférer l'historique d'un dépôt R1 sur la machine A vers un autre dépôt R2 sur la machine B. Pour une raison quelconque, la connexion directe entre A et B n'est pas autorisée, mais nous pouvons déplacer des données de A vers B via un mécanisme quelconque (CD, e-mail, etc.). Nous voulons mettre à jour R2 avec le développement effectué sur la branche master dans

R1.

Pour amorcer le processus, vous pouvez d'abord créer un bundle qui n'a aucun prérequis. Vous pouvez utiliser une étiquette pour vous souvenir du dernier commit traité, afin de faciliter la mise à jour ultérieure de l'autre dépôt avec un bundle incrémental 

: 
machineA$ cd R1
machineA$ git bund
le create file.bundle master machin
eA$ git tag -f lastR2bundle master

Ensuite, vous transférez file.bundle vers la machine cible B. Comme ce bundle ne nécessite aucun objet existant pour être extrait, vous pouvez créer un nouveau dépôt sur la machine B en le clonant depuis celui-ci 

: 
machineB$ git clone
-b master /home/me
/tmp/file.bundle R2

Cela définira un distant appelé « origin » dans le dépôt résultant qui vous permettra de récupérer et tirer depuis le bundle. Le fichier $GIT_DIR/config dans R2 contiendra une entrée comme celle-ci 

: 
[remote "origin"]
    url = /home/me/tmp/file.bundle
    fetch = refs/heads/*:refs/remotes/origin
/
*

Pour mettre à jour le dépôt résultant mine.git, vous pouvez récupérer ou tirer après avoir remplacé le bundle stocké dans /home/me/tmp/file.bundle par des mises à jour

incrémentales.

Après avoir travaillé un peu plus dans le dépôt original, vous pouvez créer un bundle incrémental pour mettre à jour l'autre dépôt 

: 
machineA$ cd R1
machineA$ git bundle cr
eate file.bundle lastR2bundle..master m
achineA$ git tag -f lastR2bundle master

Vous transférez ensuite le bundle vers l'autre machine pour remplacer /home/me/tmp/file.bundle, et tirez depuis

celui-ci. 
machineB$ c
d R2 machine
B$ git pull

Si vous savez jusqu'à quel commit le dépôt destinataire prévu doit avoir les objets nécessaires, vous pouvez utiliser cette information pour spécifier les prérequis, en donnant un point de coupure pour limiter les révisions et les objets qui entrent dans le bundle résultant. L'exemple précédent utilisait l'étiquette lastR2bundle à cette fin, mais vous pouvez utiliser toutes les autres options que vous donneriez à la commande git-log(1). Voici d'autres exemples 

:

Vous pouvez utiliser une étiquette présente dans les deux 

: 
$ git bundle c
reate mybundle
v1.0.0..master

Vous pouvez utiliser un prérequis basé sur le temps 

: 
$ git bundle crea
te mybundle --sin
ce=10.days master

Vous pouvez utiliser le nombre de commits 

: 
$ git bundle
create mybund
le -10 master

Vous pouvez exécuter git-bundle verify pour voir si vous pouvez extraire d'un bundle qui a été créé avec un prérequis 

: 
$ git bun
dle verify
mybundle

Cela listera les commits que vous devez avoir pour pouvoir extraire depuis le bundle et échouera si vous ne les avez

pas.

Un bundle du point de vue d'un dépôt destinataire est simplement comme un dépôt régulier depuis lequel il récupère ou tire. Vous pouvez, par exemple, faire correspondre des références lors de la récupération 

: 
$ git fetch
mybundle mas
ter:localRef

Vous pouvez aussi voir quelles références il propose 

: 
$ git
ls-rem
ote my
bundle

DISCUSSIO

N

Une manière naïve de faire une sauvegarde complète d'un dépôt est d'utiliser quelque chose comme cp -r <dépôt> <destination>. Cela est déconseillé car le dépôt pourrait être écrit pendant l'opération de copie. En conséquence, certains fichiers à <destination> pourraient être

corrompus.

C'est pourquoi il est recommandé d'utiliser les outils Git pour faire des sauvegardes de dépôts, soit avec cette commande, soit avec par exemple git-clone(1). Mais gardez à l'esprit que ces outils ne vous aideront pas à sauvegarder d'autres états que les références et les commits. En d'autres termes, ils ne vous aideront pas à sauvegarder le contenu de l'index, l'arbre de travail, le stash, la configuration du dépôt, les hooks,

etc.

Voir aussi gitfaq(7), section « TRANSFERS » pour une discussion des probl

èmes associés à la synchronisatio
n de fichiers entre systèmes.
