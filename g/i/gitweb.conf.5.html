DESCRIPTIO

N

Le script CGI gitweb permettant de consulter les dépôts Git sur le web utilise un fragment de script perl comme fichier de configuration. Vous pouvez définir des variables en utilisant «our $variable = valeur » ; le texte à partir d'un caractère « # » jusqu'à la fin de la ligne est ignoré. Voir perlsyn(1) pour plus de

détails.

Un exemple

: 
# gitweb configuration file for http://git.example
.org # our $projectroot = "/srv/git"; # FHS recom
mendation our $site_name = 'Example.org >> Repos';

Le fichier de configuration est utilisé pour remplacer les paramètres par défaut intégrés dans gitweb au moment où le script gitweb.cgi a été

généré.

Bien que l'on puisse modifier directement les paramètres de configuration dans le CGI gitweb lui-même, ces modifications seraient perdues lors d'une mise à jour. Les paramètres de configuration peuvent également être placés dans un fichier situé dans le même répertoire que le script CGI avec le nom par défaut gitweb_config.perl — permettant d'avoir plusieurs instances de gitweb avec des configurations différentes par l'utilisation de liens

symboliques.

Notez que certaines configurations peuvent être contrôlées au niveau de chaque dépôt plutôt qu'au niveau global de gitweb : voir la sous-section « Per-repository gitweb configuration » dans la page man gitwe

b(1
).

DISCUSSIO

N

Gitweb lit les données de configuration depuis les sources suivantes dans l'ordre suivant

:
•valeurs intégrées (certaines définies lors de la phase de compilation)
,
•fichier de configuration commun au niveau système (par défaut : /etc/gitweb-commo
n.conf),
•soit le fichier de configuration propre à l'instance (par défaut : gitweb_config.perl dans le même répertoire que gitweb installé), ou s'il n'existe pas, le fichier de configuration de secours au niveau système (par défaut : /etc/gitweb.
conf).

Les valeurs obtenues dans les fichiers de configuration ultérieurs remplacent les valeurs obtenues précédemment dans la séquence

ci-dessus.

Les emplacements du fichier de configuration commun au niveau système, du fichier de configuration de secours au niveau système et du fichier de configuration propre à l'instance sont définis à la compilation à l'aide des variables de configuration du Makefile de compilation, respectivement GITWEB_CONFIG_COMMON, GITWEB_CONFIG_SYSTEM et GITWEB_CONFIG

.

Vous pouvez également remplacer les emplacements des fichiers de configuration de gitweb à l'exécution en définissant les variables d'environnement suivantes : GITWEB_CONFIG_COMMON, GITWEB_CONFIG_SYSTEM et GITWEB_CONFIG à une valeur non

vide.

La syntaxe des fichiers de configuration est celle de Perl, car ces fichiers sont traités en les incluant comme des fragments de code Perl (le langage dans lequel gitweb lui-même est écrit). Les variables sont généralement définies en utilisant le qualificateur our (comme dans «our $variable = <valeur> ; ») pour éviter des erreurs de syntaxe si une nouvelle version de gitweb n'utilise plus une variable et cesse donc de la

déclarer.

Vous pouvez inclure un autre fichier de configuration à l'aide de la sous-routine read_config_file(). Par exemple, on peut souhaiter mettre la configuration de gitweb liée au contrôle d'accès pour la consultation des dépôts via Gitolite (un des outils de gestion de dépôts Git) dans un fichier séparé, par ex. dans /etc/gitweb-gitolite.conf. Pour l'inclure,

placez 
read_config_fil
e("/etc/gitweb-g
itolite.conf");

quelque part dans le fichier de configuration de gitweb utilisé, par ex. dans le fichier de configuration de gitweb propre à l'installation. Notez que read_config_file() vérifie lui-même que le fichier qu'il lit existe et ne fait rien s'il n'est pas trouvé. Il gère également les erreurs dans le fichier

inclus.

La configuration par défaut, sans aucun fichier de configuration, peut parfaitement convenir à certaines installations. Toutefois, un fichier de configuration est utile pour personnaliser ou ajuster le comportement de gitweb de nombreuses manières, et certaines fonctionnalités optionnelles ne seront pas présentes à moins d'être activées explicitement à l'aide de la variable configurable %features (voir aussi la section « Confi

guring gitweb fea
tures » ci-dessous).

$project_maxdept

h
Si la variable $projects_list n'est pas définie, gitweb scannera récursivement le système de fichiers à la recherche de dépôts Git. La variable $project_maxdepth est utilisée pour limiter la profondeur de parcours, par rapport à $projectroot (point de départ) ; cela signifie que les répertoires plus éloignés de $projectroot que $project_maxdepth seront ignorés.

C'est une optimisation purement de performance, initialement destinée à MacOS X, où la traversée récursive des répertoires est lente. Gitweb suit les liens symboliques, mais détecte les cycles, en ignorant tout fichier et répertoire en

La valeur par défaut de cette variable est déterminée par la variable de configuration GITWEB_PROJECT_MAXDEPTH, dont la

Trouver des

fichiers

Les variables de configuration suivantes indiquent à gitweb où trouver les fichiers. Les valeurs de ces variables sont des chemins sur le système de

fichiers.

$GI

T
Exécutable git de base à utiliser. Par défaut défini à $GIT_BINDIR/git, qui est à son tour défini par défaut à $(bindir)/git. Si vous utilisez Git installé depuis un paquet binaire, vous devriez généralement définir ceci à "/usr/bin/git". Cela peut simplement être "git" si votre serveur web a un PATH sensé ; d'un point de vue de la sécurité, il est préférable d'utiliser le chemin absolu vers le binaire git. Si vous avez plusieurs versions de Git installées, cela peut être utilisé pour choisir laquelle utiliser. Doit être défini (correctement) pour que gitweb puisse
fonctionner.

$mimetypes_fil

e
Fichier à utiliser pour la déduction (basée sur l'extension du nom de fichier) des types MIME avant d'essayer /etc/mime.types. NOTEZ que ce chemin, s'il est relatif, est pris comme relatif au dépôt Git courant, pas au script CGI. Si non défini, seul /etc/mime.types est utilisé (s'il est présent sur le système de fichiers). Si aucun fichier de types MIME n'est trouvé, la déduction du type MIME basée sur l'extension du fichier est désactivée. Non défini par
défaut.

$highlight_bi

n
Chemin vers l'exécutable highlight à utiliser (il doit être celui de http://andre-simon.de/zip/download.php en raison des hypothèses concernant les paramètres et la sortie). Par défaut défini à highlight ; définissez-le au chemin complet vers l'exécutable highlight s'il n'est pas installé dans le PATH de votre serveur web. Notez que la fonctionnalité highlight doit être définie pour que gitweb utilise réellement la coloration syntaxique.

NOTE : pour qu'un fichier soit coloré, son type de syntaxe doit être détecté et cette syntaxe doit être prise en charge par "highlight". La détection de syntaxe par défaut est minimale, et il existe de nombreux types de syntaxe pris en charge sans détection par défaut. Il y a trois options pour ajouter la détection de syntaxe. La première et la deuxième priorité sont %highlight_basename et %highlight_ext, qui détectent basé sur le nom de base (le nom de fichier complet, par exemple "Makefile") et l'extension (par exemple "sh"). Les clés de ces hachages sont respectivement le nom de base et l'extension, et la valeur pour une clé donnée est le nom de la syntaxe à passer via --syntax <syntax> à "highlight". La dernière priorité est la configuration "highlight" de expressions rationnelles Shebang pour détecter la langue basée sur la première ligne du fichier, (par exemple, en faisant correspondre la ligne "#!/bin/bash"). Voir la documentation de highlight et la configuration par défaut à /etc/highlight/filetypes.conf pour plus de

détails.

Par exemple, si les dépôts que vous hébergez utilisent l'extension "phtml" pour les fichiers PHP, et que vous voulez avoir une coloration syntaxique correcte pour ces fichiers, vous pouvez ajouter ce qui suit à la configuration de gitweb

: 
our %highl
ight_ext; $
highlight_
ext{'phtml'
} = 'php';

Les variables de configuration décrites ci-dessous configurent certains des liens de gitweb : leur cible et leur apparence (texte ou image), et où trouver les prérequis des pages (feuille de style, favicon, images, scripts). Habituellement, elles sont laissées à leurs valeurs par défaut, avec la possible exception de la variable @styl

@stylesheet

s
Liste des URIs des feuilles de style (relatives à l'URI de base d'une page). Vous pouvez spécifier plus d'une feuille de style, par exemple pour utiliser "gitweb.css" comme base avec des modifications spécifiques au site dans une feuille de style séparée pour faciliter la mise à jour de gitweb. Par exemple, vous pouvez ajouter une feuille de style du site en mettant

b-site.css";

dans le fichier de configuration de gitweb. Ces valeurs qui sont des chemins relatifs sont relatives à l'URI de base de

gitweb.

Cette liste devrait contenir l'URI de la feuille de style standard de gitweb. L'URI par défaut de la feuille de style de gitweb peut être définie au moment de la construction en utilisant la variable makefile GITWEB_CSS. Sa valeur par défaut est static/gitweb.css (ou static/gitweb.min.css si la variable CSSMIN est définie, c'est-à-dire si un minificateur CSS est utilisé pendant la construction)

.

Note : il existe aussi une variable de configuration $stylesheet héritée, qui était utilisée par les anciennes versions de gitweb. Si la variable $stylesheet est définie, seule la feuille de style

$log

o
Pointe vers l'endroit où vous avez mis git-logo.png sur votre serveur web, ou plus précisément l'URI générique du logo, taille 72x27). Cette image est affichée dans le coin supérieur droit de chaque page gitweb et utilisée comme logo pour le flux Atom. Relative à l'URI de base de gitweb (comme un chemin). Peut être ajustée lors de la construction de gitweb en utilisant la variable GITWEB_LOGO. Par défaut définie à static/git-lo

$favico

n
Pointe vers l'endroit où vous avez mis git-favicon.png sur votre serveur web, ou plus précisément l'URI générique du favicon, qui sera servi avec le type "image/png". Les navigateurs web qui prennent en charge les favicons (icônes de site web) peuvent les afficher dans la barre d'URL du navigateur et à côté du nom du site dans les favoris. Relative à l'URI de base de gitweb. Peut être ajustée au moment de la construction en utilisant la variable GITWEB_FAVICON. Par défaut définie à static/git-favi

$javascrip

t
Pointe vers l'endroit où vous avez mis gitweb.js sur votre serveur web, ou plus précisément l'URI du code JavaScript utilisé par gitweb. Relative à l'URI de base de gitweb. Peut être définie au moment de la construction en utilisant la variable de configuration de construction GITWEB_JS.

La valeur par défaut est soit static/gitweb.js, soit static/gitweb.min.js si la variable de construction JSMIN a été définie, c'est-à-dire si un minificateur JavaScript a été utilisé au moment de la construction. Notez que ce fichier unique est généré à partir d

k
Cible du lien d'accueil en haut de toutes les pages (la première partie de la vue "fil d'Ariane"). Par défaut, elle est définie à l'URI absolue d'une page courante (à la valeur de la variable $my_uri, ou à "/" si $my_uri est indéfinie ou est une chaîne vide)

$home_link_st

r
Étiquette du "lien d'accueil" en haut de toutes les pages, menant à $home_link (généralement la page principale de gitweb, qui contient la liste des projets). Elle est utilisée comme le premier composant du "fil d'Ariane" de gitweb : <home-link> / <project> / <action>. Peut être définie au moment de la construction en utilisant la variable GITWEB_HOME_LINK_STR. Par défaut, elle est définie à "projects", car ce lien mène à la liste des projets. Un autre choix populaire est de la définir au nom du site. Notez qu'elle est traitée comme du HTML brut, elle ne devrait donc pas être définie à partir de sources non

@extra_breadcrumb

s
Liens supplémentaires à ajouter au début du fil d'Ariane avant le lien d'accueil, vers des pages qui sont logiquement "au-dessus" de la liste des projets gitweb, comme l'organisation et le département qui hébergent le serveur gitweb. Chaque élément de la liste est une référence vers un tableau, dans lequel l'élément 0 est le texte du lien (équivalent à $home_link_str) et l'élément 1 est l'URL cible (équivalent à $home_link).

d'accueil.

Modifier le comportement de

gitweb

Ces variables de configuration contrôlent le comportement interne de

gitweb.

$default_blob_plain_mimetyp

e
Mime type par défaut pour la vue blob_plain (brut), si la vérification du mime type ne donne pas un autre type ; par défaut "text/plain". Gitweb devine le mime type d'un fichier à afficher en se basant sur l'extension de son nom de fichier, en utilisant $mimetypes_file (si défini et si le fichier existe) et /etc/mime.types (voir la page de manuel mime.types(5) ; seules les règles d'extension de nom de fichier sont prises en charge par gitweb)
.

$default_text_plain_charse

t
Jeu de caractères par défaut pour les fichiers texte. Si ce n'est pas défini, la configuration du serveur web sera utilisée. Non défini par
défaut.

$fallback_encodin

g
Gitweb suppose ce jeu de caractères lorsqu'une ligne contient des caractères non UTF-8. Le décodage de secours est utilisé sans vérification d'erreur, donc cela peut être même "utf-8". La valeur doit être un encodage valide ; voir la page de manuel Encoding::Supported(3pm) pour une liste. La valeur par défaut est "latin1", aussi connu sous le nom de
"iso-8859-1".

@diff_opt

s
Options de détection de renommage pour git-diff et git-diff-tree. La valeur par défaut est ('-M') ; définissez-la à ('-C') ou ('-C', '-C') pour détecter aussi les copies, ou définissez-la à () c'est-à-dire une liste vide si vous ne voulez pas de détection de renommage.

Notez que la détection de renommage et surtout de copie peut être assez gourmande en CPU. Notez aussi que les outils non-Git

peuvent avoir des problèmes avec les patchs générés avec les
options mentionnées ci-dessus, surtout s'ils impliquent des
copies de fichiers ('-C') ou des renommages en croix ('-B').

Quelques fonctionnalités et politiques

optionnelles

La plupart des fonctionnalités sont configurées via le hachage %feature ; cependant certaines fonctionnalités supplémentaires de gitweb peuvent être activées et configurées en utilisant les variables décrites ci-dessous. Cette liste, en plus des variables de configuration qui contrôlent l'apparence de gitweb, contient aussi des variables configurant le côté administratif de gitweb (par exemple la prévention du cross-site scripting ; certes cela a comme effet secondaire de modifier l'apparence des pages "summary", ou la limitation de la charge)

.

@git_base_url_lis

t
Liste des URL de base Git. Ces URL sont utilisées pour générer les URL décrivant d'où récupérer un projet, qui sont affichées sur la page de résumé du projet. L'URL complète de récupération est "$git_base_url/$project", pour chaque élément de cette liste. Vous pouvez configurer plusieurs URL de base (par exemple une pour le protocole git://, et une pour le protocole http://).

Notez que la configuration par dépôt peut être définie dans le fichier $GIT_DIR/cloneurl, ou comme valeurs de la variable de configuration multi-valuée gitweb.url dans la configuration du projet. La configuration par dépôt a la priorité sur la valeur composée à partir des éléments de @git_base_url_list et du nom du

projet.

Vous pouvez configurer une seule valeur (une seule entrée/élément dans cette liste) au moment de la compilation en définissant la variable de configuration GITWEB_BASE_URL au moment de la compilation. Par défaut, elle est définie à (), c'est-à-dire une lis

te vide. Cela signifie que gitweb n'essaiera pas de créer l'UR
L du projet (pour la récupération) à partir du nom du projet.

s
S'il faut activer le regroupement des projets par catégorie sur la page de liste des projets. La catégorie d'un projet est déterminée par le fichier $GIT_DIR/category ou la variable gitweb.category dans la configuration de chaque dépôt. Désactivé par défaut (défini à 0)
.

$project_list_default_categor

y
Catégorie par défaut pour les projets pour lesquels aucune n'est spécifiée. Si ceci est défini à la chaîne vide, de tels projets resteront sans catégorie et seront listés en haut, au-dessus des projets catégorisés. Utilisé seulement si les catégories de projet sont activées, ce qui signifie si $projects_list_group_categories est vrai. Par défaut défini à "" (chaîne vide)
.

$prevent_xs

s
Si vrai, certaines fonctionnalités de gitweb sont désactivées pour empêcher le contenu des dépôts de lancer des attaques de type cross-site scripting (XSS). Définissez ceci à vrai si vous ne faites pas confiance au contenu de vos dépôts. Faux par défaut (défini à 0)
.

$maxloa

d
Utilisé pour définir la charge maximale à laquelle nous répondrons encore aux requêtes gitweb. Si la charge du serveur dépasse cette valeur, gitweb renverra une erreur "503 Service Unavailable". La charge du serveur est considérée comme 0 si gitweb ne peut pas déterminer sa valeur. Actuellement, cela ne fonctionne que sur Linux, où cela utilise /proc/loadavg ; la charge y est le nombre de tâches actives sur le système — les processus qui sont réellement en cours d'exécution — moyenné sur la dernière minute.

Définissez $maxload à une valeur indéfinie (undef) pour désactiver cette foncti

onnalité. La valeur
par défaut est 300.

$omit_age_colum

n
Si vrai, omet la colonne avec la date du commit le plus récent sur la page de liste des projets. Cela peut économiser un peu d'E/S et un fork par
dépôt.

$omit_owne

r
Si vrai, empêche l'affichage des informations sur le propriétaire du
dépôt.

$per_request_confi

g
Si ceci est défini à une référence de code, il sera exécuté une fois pour chaque requête. Vous pouvez définir des parties de la configuration qui changent par session de cette manière. Par exemple, on pourrait utiliser le code suivant dans un fichier de configuration gitweb 
our $per_request_config = sub {
        $ENV{GL_USER} = $cgi->remote_user || "gitweb";
}
;

Si $per_request_config n'est pas une référence de code, il est interprété comme une valeur booléenne. S'il est vrai, gitweb traitera les fichiers de configuration une fois par requête, et s'il est faux, gitweb ne traitera les fichiers de configuration qu'une seule fois, à chaque fois qu'il est exécuté. Vrai par défaut (défini à 1)

.

NOTE : $my_url, $my_uri, et $base_url sont écrasées avec leurs valeurs par défaut avant chaque requête, donc si vous voulez les changer, assurez-vous de définir cette variable à vrai ou à une référence de code effectuant les changements

désirés.

CONFIGURATION DES FONCTIONNALITÉS DE

GITWEB

De nombreuses fonctionnalités de gitweb peuvent être activées (ou désactivées) et configurées en utilisant le hachage %feature. Les noms des fonctionnalités de gitweb sont les clés de ce

hachage.

Chaque élément du hachage %feature est une référence de hachage et a la structure suivante

: 
"<feature-name>" => {
        "sub" => <feature-sub-(subroutine)>,
        "override" => <allow-override-(boolean)>,
        "default" => [ <options>... ]
}
,

Certaines fonctionnalités ne peuvent pas être surchargées par projet. Pour ces fonctionnalités, la structure de l'élément approprié du hachage %feature a une forme plus simple

: 
"<feature-name>" => {
        "override" => 0,
        "default" => [ <options>... ]
}
,

Comme on peut le voir, il lui manque l'élément

'sub'.

La signification de chaque partie de la configuration de la fonctionnalité est décrite ci-dessous

:

defaul

t
Liste (référence de tableau) des paramètres de la fonctionnalité (s'il y en a), utilisée aussi pour basculer (activer ou désactiver) la fonctionnalité donnée.

Notez que c'est actuellement toujours une référence de tableau, même si la fonctionnalité n'accepte aucun paramètre de configuration, et 'default' est utilisée seulement pour l'activer ou la désactiver. Dans un tel cas, vous activez la fonctionnalité en définissant cet élément à [1], et vous la désactivez en le définissant à [0]. Voir aussi le passage sur la fonctionnalité "blame" dans la section

"Exemples".

Pour désactiver les fonctionnalités qui acceptent des paramètres (sont configurables), vous devez définir cet élément à une liste vide c'est-à-dire

[]
.

overrid

e
Si ce champ a une valeur vraie, alors la fonctionnalité donnée est surchargeable, ce qui signifie qu'elle peut être configurée (ou activée/désactivée) au niveau de chaque dépôt.

Habituellement, la fonctionnalité "<feature>" donnée est configurable via la variable de configuration gitweb.<feature> dans le fichier de configuration Git de chaque

dépôt.

Notez qu'aucune fonctionnalité

n'est surcharge
able par défaut.

su

b
Détail interne de l'implémentation. Ce qui est important, c'est que si ce champ n'est pas présent, alors la surcharge par dépôt pour la fonctionnalité donnée n'est pas prise en charge.

Vous n'aurez jamais besoin de

le changer dans le fichier de
configuration de gitweb.

blam

e
Active les vues de blob "blame" et "blame_incremental", montrant pour chaque ligne le dernier commit qui l'a modifiée ; voir git-blame(1). Cela peut être très gourmand en CPU et est donc désactivé par défaut.

snapsho

Active et configure l'action "snapshot", qui permet à l'utilisateur de télécharger une archive compressée de n'importe quel arbre ou commit, telle que produite par git-archive(1) et éventuellement compressée à nouveau. Cela peut potentiellement générer un trafic important si vous avez de gros projets.

La valeur 'default' est une liste de noms de formats de capture instantanée, définis dans le hash %known_snapshot_formats, que vous souhaitez proposer. Les formats pris en charge incluent "tgz", "tbz2", "txz" (archive tar compressée avec gzip/bzip2/xz) et "zip" ; veuillez consulter les sources de gitweb pour une liste définitive. Par défaut, seul "tgz" est

fork

s
Si cette fonctionnalité est activée, gitweb considère que les projets dans les sous-répertoires de la racine du projet (basename) sont des forks de projets existants. Pour chaque projet $projname.git, les projets dans le répertoire $projname/ et ses sous-répertoires ne seront pas affichés dans la liste principale des projets. À la place, un marqueur '+' est affiché à côté de $projname, qui renvoie à une vue "forks" listant tous les forks (tous les projets dans le sous-répertoire $projname/). De plus, une vue "forks" pour un projet est liée depuis la page de résumé du projet.

Si la liste des projets est prise depuis un fichier ($projects_list pointe vers un fichier), les forks ne sont reconnus que s'ils sont listés après le projet principal dans ce

fichier.

"$projectroot/$project"), %h en le hash actuel (paramètre gitweb 'h’) et ‘%b` en la base du hash actuel (paramètre gitweb 'hb’) ; ‘%%` se développe en
