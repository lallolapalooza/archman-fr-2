NOM

git-index-pack - Construire un fichier d'index de paquet pour une archive empaquetée existante

SYNOPIS

git index-pack [-v] [-o <index-file>] [--[no-]rev-index] <pack-file>
git index-pack --stdin [--fix-thin] [--keep] [-v] [-o <index-file>]
                  [--[no-]rev-index] [<pack-file>]

DESCRIPTION

Lit une archive empaquetée (.pack) depuis le fichier spécifié, construit un fichier d'index de paquet (.idx) pour celle-ci, et écrit éventuellement un index inversé (.rev) pour le paquet spécifié. L'archive empaquetée, avec l'index de paquet, peut alors être placée dans le répertoire objects/pack/ d'un dépôt Git.

OPTIONS

-v

Être verbeux sur ce qui se passe, y compris l'état d'avancement.

-o <index-file>

Écrit l'index de paquet généré dans le fichier spécifié. Sans cette option, le nom du fichier d'index de paquet est construit à partir du nom du fichier d'archive empaquetée en remplaçant .pack par .idx (et le programme échoue si le nom du fichier d'archive empaquetée ne se termine pas par .pack).

--rev-index, --no-rev-index

Lorsque ce drapeau est fourni, génère un index inversé (un fichier .rev) correspondant au paquet donné. Si --verify est donné, assure que l'index inversé existant est correct. Prend la priorité sur pack.writeReverseIndex.

--stdin

Lorsque ce drapeau est fourni, le paquet est lu depuis stdin à la place et une copie est ensuite écrite dans <pack-file>. Si <pack-file> n'est pas spécifié, le paquet est écrit dans le répertoire objects/pack/ du dépôt Git courant avec un nom par défaut déterminé par le contenu du paquet. Si <pack-file> n'est pas spécifié, envisagez d'utiliser --keep pour éviter une condition de concurrence entre ce processus et git repack.

--fix-thin

Corrige un paquet "mince" (thin) produit par git pack-objects --thin (voir git-pack-objects(1) pour les détails) en ajoutant les objets exclus sur lesquels les objets deltifiés sont basés au paquet. Cette option n'a de sens qu'en conjonction avec --stdin.

--keep

Avant de déplacer l'index vers sa destination finale, crée un fichier .keep vide pour le paquet associé. Cette option est généralement nécessaire avec --stdin pour éviter qu'un processus git repack simultané ne supprime le paquet et l'index nouvellement construits avant que les références ne puissent être mises à jour pour utiliser les objets contenus dans le paquet.

--keep=<msg>

Comme --keep, crée un fichier .keep avant de déplacer l'index vers sa destination finale. Cependant, au lieu de créer un fichier vide, place <msg> suivi d'un LF dans le fichier .keep. Le message <msg> peut être recherché ultérieurement dans tous les fichiers .keep pour localiser ceux qui ont dépassé leur utilité.

--index-version=<version>[,<offset>]

Ceci est destiné à être utilisé uniquement par la suite de tests. Il permet de forcer la version de l'index de paquet généré, et de forcer les entrées d'index 64 bits sur les objets situés au-dessus de l'offset donné.

--strict[=<msg-id>=<severity>...]

Se termine si le paquet contient des objets ou des liens cassés. Une liste optionnelle séparée par des virgules de <msg-id>=<severity> peut être passée pour changer la sévérité de certains problèmes potentiels, par exemple, --strict="missingEmail=ignore,badTagName=error". Voir l'entrée pour les options de configuration fsck.<msg-id> dans git-fsck(1) pour plus d'informations sur les valeurs possibles de <msg-id> et <severity>.

--progress-title

Réservé à un usage interne.

Définit le titre de la barre de progression. Le titre est "Receiving objects" (Réception des objets) par défaut et "Indexing objects" (Indexation des objets) lorsque --stdin est spécifié.

--check-self-contained-and-connected

Se termine si le paquet contient des liens cassés. Réservé à un usage interne.

--fsck-objects[=<msg-id>=<severity>...]

Se termine si le paquet contient des objets cassés, mais contrairement à --strict, ne s'arrête pas sur des liens cassés. Si le paquet contient un arbre pointant vers un blob .gitmodules qui n'existe pas, imprime le hachage de ce blob (pour que l'appelant le vérifie) après le hachage qui va dans le nom du fichier pack/idx (voir "NOTES").

Une liste optionnelle séparée par des virgules de <msg-id>=<severity> peut être passée pour changer la sévérité de certains problèmes potentiels, par exemple, --fsck-objects="missingEmail=ignore,badTagName=ignore". Voir l'entrée pour les options de configuration fsck.<msg-id> dans git-fsck(1) pour plus d'informations sur les valeurs possibles de <msg-id> et <severity>.

--threads=<n>

Spécifie le nombre de threads à lancer lors de la résolution des deltas. Cela nécessite que index-pack soit compilé avec pthreads, sinon cette option est ignorée avec un avertissement. Ceci est destiné à réduire le temps d'empaquetage sur les machines multiprocesseurs. La quantité de mémoire requise pour la fenêtre de recherche de deltas est cependant multipliée par le nombre de threads. Spécifier 0 fera que Git détectera automatiquement le nombre de CPU et utilisera un maximum de 3 threads.

--max-input-size=<size>

Se termine si le paquet est plus grand que <size>.

--object-format=<hash-algorithm>

Spécifie le format d'objet donné (algorithme de hachage) pour le paquet. Les valeurs valides sont sha1 et (si activé) sha256. La valeur par défaut est l'algorithme du dépôt courant (défini par extensions.objectFormat), ou sha1 si aucune valeur n'est définie ou en dehors d'un dépôt.

Cette option ne peut pas être utilisée avec --stdin.

Note : Actuellement, il n'y a pas d'interopérabilité entre les dépôts SHA-256 et les dépôts SHA-1.

Historiquement, nous avons averti que les dépôts SHA-256 pourraient plus tard nécessiter des changements incompatibles avec les versions antérieures lorsque nous introduirions de telles fonctionnalités d'interopérabilité. Aujourd'hui, nous ne nous attendons qu'à des changements compatibles. De plus, si de tels changements s'avèrent nécessaires, on peut s'attendre à ce que les dépôts SHA-256 créés avec Git actuel soient utilisables par les futures versions de Git sans perte de données.

--promisor[=<message>]

Avant de valider l'index de paquet, crée un fichier .promisor pour ce paquet. Particulièrement utile lors de l'écriture d'un paquet promisor avec --fix-thin, car le nom du paquet n'est définitif qu'une fois le paquet entièrement écrit. Si un <message> est fourni, alors ce contenu sera écrit dans le fichier .promisor pour référence future. Voir partial clone[1] pour plus d'informations.

De plus, s'il y a des objets dans le paquet donné qui référencent des objets non-promisors (dans le dépôt), repaquet ces objets non-promisors dans un paquet promisor. Cela évite une situation où un dépôt contient des objets non-promisors qui sont accessibles via des objets promisors.

Nécessite que <pack-file> ne soit pas spécifié.

NOTES

Une fois l'index créé, le hachage qui entre dans le nom du fichier pack/idx est imprimé sur stdout. Si --stdin a également été utilisé, ceci est préfixé par soit "pack\t", soit "keep\t" si un nouveau fichier .keep a été créé avec succès. Ceci est utile pour supprimer un fichier .keep utilisé comme verrou pour empêcher la concurrence avec git repack mentionnée ci-dessus.
