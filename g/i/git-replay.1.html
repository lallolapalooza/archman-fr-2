GIT-REPLAY(1) Manuel Git GIT-REPLAY(1)

NOM

git-replay - EXPÉRIMENTAL : Rejoue des commits sur une nouvelle base, fonctionne aussi avec les dépôts nus

SYNTAXE

(EXPÉRIMENTAL !) git replay ([--contained] --onto <nouvelle_base> | --advance <branche>) <plage_de_révisions>...

DESCRIPTION

Prend des plages de commits et les rejoue sur un nouvel emplacement. Laisse l'arbre de travail et l'index inchangés, et ne met à jour aucune référence. La sortie de cette commande est destinée à être utilisée comme entrée pour git update-ref --stdin, qui mettrait à jour les branches concernées (voir la section SORTIE ci-dessous).

CETTE COMMANDE EST EXPÉRIMENTALE. SON COMPORTEMENT PEUT CHANGER.

OPTIONS

--onto <nouvelle_base>

Point de départ auquel créer les nouveaux commits. Peut être n'importe quel commit valide, et pas seulement un nom de branche existant.

Lorsque --onto est spécifié, la commande update-ref (ou les commandes) dans la sortie mettra(ont) à jour la(les) branche(s) dans la plage de révisions pour pointer vers les nouveaux commits, similaire à la façon dont git rebase --update-refs met à jour plusieurs branches dans la plage affectée.

--advance <branche>

Point de départ auquel créer les nouveaux commits ; doit être un nom de branche.

Lorsque --advance est spécifié, la commande update-ref (ou les commandes) dans la sortie mettra(ont) à jour la branche passée en argument à --advance pour pointer vers les nouveaux commits (en d'autres termes, cela imite une opération de cherry-pick).

<plage_de_révisions>

Plage de commits à rejouer. Plus d'une <plage_de_révisions> peuvent être passées, mais en mode --advance <branche>, elles devraient avoir une seule pointe, de sorte qu'il soit clair où <branche> doit pointer. Voir « Spécifier des plages » dans git-rev-parse(1) et les options « Limiter les commits » ci-dessous.

Limiter les commits

En plus de spécifier une plage de commits qui devraient être listés en utilisant les notations spéciales expliquées dans la description, une limite de commits supplémentaire peut être appliquée.

L'utilisation de plusieurs options limite généralement davantage la sortie (par exemple, --since=<date1> limite aux commits plus récents que <date1>, et en l'utilisant avec --grep=<motif> limite davantage aux commits dont le message de log contient une ligne correspondant au <motif>), sauf indication contraire.

Notez que celles-ci sont appliquées avant les options d'ordre et de formatage des commits, comme --reverse.

-<nombre>, -n <nombre>, --max-count=<nombre>

Limite la sortie à <nombre> commits.

--skip=<nombre>

Ignore <nombre> commits avant de commencer à afficher la sortie des commits.

--since=<date>, --after=<date>

Affiche les commits plus récents que <date>.

--since-as-filter=<date>

Affiche tous les commits plus récents que <date>. Cela parcourt tous les commits dans la plage, plutôt que de s'arrêter au premier commit plus ancien que <date>.

--until=<date>, --before=<date>

Affiche les commits plus anciens que <date>.

--author=<motif>, --committer=<motif>

Limite la sortie des commits à ceux dont les lignes d'en-tête d'auteur/committer correspondent à l'expression régulière <motif>. Avec plusieurs --author=<motif>, les commits dont l'auteur correspond à l'un des <motif> sont choisis (similairement pour plusieurs --committer=<motif>).

--grep-reflog=<motif>

Limite la sortie des commits à ceux dont les entrées du reflog correspondent à l'expression régulière <motif>. Avec plusieurs --grep-reflog, les commits dont le message du reflog correspond à l'un des modèles donnés sont choisis. Il est erroné d'utiliser cette option à moins que --walk-reflogs ne soit en cours d'utilisation.

--grep=<motif>

Limite la sortie des commits à ceux dont le message de log correspond à l'expression régulière <motif>. Avec plusieurs --grep=<motif>, les commits dont le message correspond à l'un des <motif> sont choisis (mais voir --all-match).

Lorsque --notes est actif, le message des notes est comparé comme s'il faisait partie du message de log.

--all-match

Limite la sortie des commits à ceux qui correspondent à tous les --grep donnés, au lieu de ceux qui correspondent au moins à un.

--invert-grep

Limite la sortie des commits à ceux dont le message de log ne correspond pas au <motif> spécifié avec --grep=<motif>.

-i, --regexp-ignore-case

Fait correspondre les modèles de limitation d'expressions régulières sans tenir compte de la casse des lettres.

--basic-regexp

Considère les modèles de limitation comme des expressions régulières de base ; c'est le comportement par défaut.

-E, --extended-regexp

Considère les modèles de limitation comme des expressions régulières étendues au lieu des expressions régulières de base par défaut.

-F, --fixed-strings

Considère les modèles de limitation comme des chaînes fixes (n'interprète pas le modèle comme une expression régulière).

-P, --perl-regexp

Considère les modèles de limitation comme des expressions régulières compatibles Perl.

La prise en charge de ces types d'expressions régulières est une dépendance optionnelle à la compilation. Si Git n'a pas été compilé avec la prise en charge de celles-ci, fournir cette option provoquera son arrêt.

--remove-empty

Arrête lorsqu'un chemin donné disparaît de l'arbre.

--merges

Affiche uniquement les commits de fusion. C'est exactement la même chose que --min-parents=2.

--no-merges

N'affiche pas les commits ayant plus d'un parent. C'est exactement la même chose que --max-parents=1.

--min-parents=<nombre>, --max-parents=<nombre>, --no-min-parents, --no-max-parents

Affiche uniquement les commits qui ont au moins (ou au plus) ce nombre de commits parents. En particulier, --max-parents=1 est identique à --no-merges, --min-parents=2 est identique à --merges. --max-parents=0 donne tous les commits racine et --min-parents=3 toutes les fusions octopus.

--no-min-parents et --no-max-parents réinitialisent à nouveau ces limites (à aucune limite). Les formes équivalentes sont --min-parents=0 (tout commit a 0 ou plusieurs parents) et --max-parents=-1 (les nombres négatifs indiquent aucune limite supérieure).

--first-parent

Lors de la recherche des commits à inclure, suit uniquement le premier parent lors de la rencontre d'un commit de fusion. Cette option peut donner un meilleur aperçu lors de la visualisation de l'évolution d'une branche thématique particulière, car les fusions dans une branche thématique ne servent souvent qu'à s'ajuster aux mises à jour en amont de temps en temps, et cette option vous permet d'ignorer les commits individuels apportés dans votre historique par une telle fusion.

--exclude-first-parent-only

Lors de la recherche des commits à exclure (avec un préfixe ^), suit uniquement le premier parent lors de la rencontre d'un commit de fusion. Cela peut être utilisé pour trouver l'ensemble des modifications dans une branche thématique à partir du point où elle a divergé de la branche distante, étant donné que les fusions arbitraires peuvent constituer des modifications de branche thématique valides.

--not

Inverse la signification du préfixe ^ (ou de son absence) pour tous les spécificateurs de révision suivants, jusqu'au prochain --not. Lorsqu'il est utilisé sur la ligne de commande avant --stdin, les révisions passées via stdin n'en seront pas affectées. Inversement, lorsqu'il est passé via l'entrée standard, les révisions passées sur la ligne de commande n'en seront pas affectées.

--all

Prétend que tous les refs dans refs/, ainsi que HEAD, sont listés sur la ligne de commande comme <commit>.

--branches[=<motif>]

Prétend que tous les refs dans refs/heads sont listés sur la ligne

--tags[=<pattern>]

Faire comme si toutes les refs dans refs/tags étaient listées sur la ligne de commande comme <commit>. Si <pattern> est fourni, limiter les tags à ceux correspondant au motif de glob shell donné. Si le motif ne contient pas ?, *, ou [, /* à la fin est implicite.

--remotes[=<pattern>]

Faire comme si toutes les refs dans refs/remotes étaient listées sur la ligne de commande comme <commit>. Si <pattern> est fourni, limiter les branches de suivi de distants à celles correspondant au motif de glob shell donné. Si le motif ne contient pas ?, *, ou [, /* à la fin est implicite.

--glob=<glob-pattern>

Faire comme si toutes les refs correspondant au glob shell <glob-pattern> étaient listées sur la ligne de commande comme <commit>. Le préfixe refs/est automatiquement ajouté s'il est manquant. Si le motif ne contient pas ?, *, ou [, /* à la fin est implicite.

--exclude=<glob-pattern>

Ne pas inclure les refs correspondant à <glob-pattern> que l'option suivante --all, --branches, --tags, --remotes, ou --glob prendrait autrement en compte. Les répétitions de cette option accumulent les motifs d'exclusion jusqu'à la prochaine option --all, --branches, --tags, --remotes, ou --glob (les autres options ou arguments ne vident pas les motifs accumulés).

Les motifs fournis ne doivent pas commencer par refs/heads, refs/tags, ou refs/remotes lorsqu'ils sont appliqués à --branches, --tags, ou --remotesrespectivement, et ils doivent commencer par refs/ lorsqu'ils sont appliqués à --glob ou --all. Si un /* final est souhaité, il doit être donné explicitement.

--exclude-hidden=(fetch|receive|uploadpack)

Ne pas inclure les refs qui seraient masquées par git-fetch, git-receive-pack ou git-upload-pack en consultant la configuration appropriée fetch.hideRefs, receive.hideRefs ou uploadpack.hideRefs ainsi que transfer.hideRefs (voir git-config(1)). Cette option affecte la prochaine option pseudo-réf --all ou --glob et est effacée après leur traitement.

--reflog

Faire comme si tous les objets mentionnés par les reflogs étaient listés sur la ligne de commande comme <commit>.

--alternate-refs

Faire comme si tous les objets mentionnés comme pointes de ref des dépôts alternatifs étaient listés sur la ligne de commande. Un dépôt alternatif est tout dépôt dont le répertoire d'objets est spécifié dans objects/info/alternates. L'ensemble des objets inclus peut être modifié par core.alternateRefsCommand, etc. Voir git-config(1).

--single-worktree

Par défaut, tous les arbres de travail seront examinés par les options suivantes lorsqu'il y en a plus d'un (voir git-worktree(1)): --all, --reflog et --indexed-objects. Cette option les force à n'examiner que l'arbre de travail courant.

--ignore-missing

Lorsqu'un nom d'objet invalide est rencontré dans l'entrée, faire comme si la mauvaise entrée n'avait pas été donnée.

--bisect

Faire comme si la mauvaise ref de bissection refs/bisect/bad avait été listée et comme si elle était suivie de --not et des bonnes refs de bissection refs/bisect/good-* sur la ligne de commande.

--stdin

En plus d'obtenir les arguments de la ligne de commande, les lire aussi depuis l'entrée standard. Cela accepte les commits et les pseudo-options comme --all et --glob=. Lorsqu'un -- séparateur est vu, l'entrée suivante est traitée comme des chemins et utilisée pour limiter le résultat. Les drapeaux comme --not qui sont lus via l'entrée standard ne sont respectés que pour les arguments passés de la même manière et n'influenceront aucun argument de ligne de commande ultérieur.

--cherry-mark

Comme --cherry-pick (voir ci-dessous) mais marquer les commits équivalents avec = plutôt que de les omettre, et les non-équivalents avec +.

--cherry-pick

Omettre tout commit qui introduit le même changement qu'un autre commit de l'« autre côté » lorsque l'ensemble des commits est limité avec la différence symétrique.

Par exemple, si vous avez deux branches, A et B, une manière habituelle de lister tous les commits d'un seul côté est avec --left-right (voir l'exemple ci-dessous dans la description de l'option --left-right] ). Cependant, cela montre les commits qui ont été cherry-pickés depuis l'autre branche (par exemple, « 3rd on b » peut être cherry-pické depuis la branche A). Avec cette option, ces paires de commits sont exclues de la sortie.

--left-only, --right-only

Lister uniquement les commits du côté respectif d'une différence symétrique, c'est-à-dire seulement ceux qui seraient marqués < respectivement > par --left-right.

Par exemple, --cherry-pick --right-only A...B omet les commits de B qui sont dans A ou qui sont patch-équivalents à un commit dans A. En d'autres termes, cela liste les commits + de git cherry A B. Plus précisément, --cherry-pick --right-only --no-merges donne la liste exacte.

--cherry

Un synonyme pour --right-only --cherry-mark --no-merges; utile pour limiter la sortie aux commits de notre côté et marquer ceux qui ont été appliqués de l'autre côté d'une histoire ramifiée avec git log --cherry upstream...mybranch, similaire à git cherry upstream mybranch.

-g, --walk-reflogs

Au lieu de parcourir la chaîne d'ancêtres des commits, parcourir les entrées de reflog de la plus récente aux plus anciennes. Lorsque cette option est utilisée, vous ne pouvez pas spécifier de commits à exclure (c'est-à-dire, ^<commit>, <commit1>..<commit2>, et les notations <commit1>...<commit2> ne peuvent pas être utilisées).

Avec --pretty un format autre que oneline et reference (pour des raisons évidentes), cela fait que la sortie a deux lignes d'informations supplémentaires prises depuis le reflog. Le désignateur de reflog dans la sortie peut être affiché comme ref@{<Nth>} (où <Nth> est l'index inversement chronologique dans le reflog) ou comme ref@{<timestamp>} (avec le <timestamp> pour cette entrée), selon quelques règles :

1. Si le point de départ est spécifié comme ref@{<Nth>}, afficher le format d'index.
2. Si le point de départ a été spécifié comme ref@{now}, afficher le format d'horodatage.
3. Si aucun des deux n'a été utilisé, mais que --date a été donné sur la ligne de commande, afficher l'horodatage dans le format demandé par --date.
4. Sinon, afficher le format d'index.

Sous --pretty=oneline, le message de commit est préfixé avec cette information sur la même ligne. Cette option ne peut pas être combinée avec --reverse. Voir aussi git-reflog(1).

Sous --pretty=reference, cette information ne sera pas du tout affichée.

--merge

Afficher les commits touchant les chemins en conflit dans l'intervalle HEAD...<other>, où <other> est la première pseudo-réf existante dans MERGE_HEAD, CHERRY_PICK_HEAD, REVERT_HEAD ou REBASE_HEAD. Ne fonctionne que lorsque l'index a des entrées non fusionnées. Cette option peut être utilisée pour afficher les commits pertinents lors de la résolution des conflits d'une fusion à trois voies.

--boundary

Afficher les commits de frontière exclus. Les commits de frontière sont préfixés avec -.

Simplification de l'historique

Parfois, vous n'êtes intéressé que par des parties de l'historique, par exemple les commits modifiant un <chemin> particulier. Mais il y a deux parties de la Simplification de l'historique, une partie est la sélection des commits et l'autre est la manière de le faire, car il existe diverses stratégies pour simplifier l'historique.

Les options suivantes sélectionnent les commits à afficher :

<paths>

Les commits modifiant les <chemins> donnés sont sélectionnés.

--simplify-by-decoration

Les commits référencés par une branche ou un tag sont sélectionnés.

Notez que des commits supplémentaires peuvent être affichés pour donner un historique significatif.

Les options suivantes affectent la manière dont la simplification est effectuée :

Mode par défaut

Simplifie l'historique à l'historique le plus simple expliquant l'état final de l'arbre. Le plus simple parce qu'il élagues certaines branches secondaires si le résultat final est le même (c'est-à-dire fusionner des branches avec le même contenu)

--show-pulls

Inclure tous les commits du mode par défaut, mais aussi tous les commits de fusion qui ne sont pas TREESAME au premier parent mais qui sont TREESAME à un parent ultérieur. Ce mode est utile pour afficher les commits de fusion qui « ont introduit en premier » un changement dans une branche.

--full-history

Identique au mode par défaut, mais n'élagues pas certaines parties de l'historique.

--dense

Seuls les commits sélectionnés sont affichés, plus certains pour avoir un historique significatif.

--sparse

Tous les commits de l'historique simplifié sont affichés.

--simplify-merges

Option supplémentaire pour --full-history afin de supprimer certaines fusions inutiles de l'historique résultant, car aucun commit sélectionné ne contribue à cette fusion.

--ancestry-path[=<commit>]

Lorsqu'un intervalle de commits à afficher est donné (par ex. <commit1>..<commit2> ou <commit2> ^<commit1>), et un commit <commit> dans cet intervalle, afficher uniquement les commits de cet intervalle qui sont des ancêtres de <commit>, des descendants de <commit>, ou <commit> lui-même. Si aucun commit n'est spécifié, utiliser <commit1> (la partie exclue de l'intervalle) comme <commit>. Peut être passé plusieurs fois ; si c'est le cas, un commit est inclus s'il est l'un des commits donnés ou s'il est un ancêtre ou descendant de l'un d'entre eux.

Une explication plus détaillée suit.

Supposons que vous ayez spécifié foo comme <chemins>. Nous appellerons les commits qui modifient foo !TREESAME, et les autres TREESAME. (Dans un diff filtré pour foo, ils apparaissent différents et égaux, respectivement.)

Dans ce qui suit, nous ferons toujours référence au même exemple d'historique pour illustrer les différences entre les paramètres de simplification. Nous supposons que vous filtrez pour un fichier foo dans ce graphe de commits :

          .-A---M---N---O---P---Q
         /     /   /   /   /   /
        I     B   C   D   E   Y
         \   /   /   /   /   /
          `-------------'   X

La ligne horizontale d'historique A---Q est considérée comme le premier parent de chaque fusion. Les commits sont :

•I est le commit initial, dans lequel foo existe avec le contenu asdf, et un fichier quux existe avec le contenu quux. Les commits initiaux sont comparés à un arbre vide, donc I est !TREESAME.
•Dans A, foo contient juste foo.
•B contient le même changement que A. Sa fusion M est triviale et donc TREESAME avec tous ses parents.
•C ne change pas foo, mais sa fusion N le change en foobar, donc il n'est TREESAME avec aucun parent.
•D définit foo à baz. Sa fusion O combine les chaînes de N et D en foobarbaz; c'est-à-dire qu'il n'est TREESAME avec aucun parent.
•E change quux en xyzzy, et sa fusion P combine les chaînes en quux xyzzy. P est TREESAME avec O, mais pas avec E.
•X est un commit racine indépendant qui a ajouté un nouveau fichier side, et Y l'a modifié. Y est TREESAME avec X. Sa fusion Q a ajouté side à P, et Q est TREESAME avec P, mais pas avec Y.

rev-list parcourt l'historique à l'envers, incluant ou excluant les commits selon que --full-history et/ou la réécriture des parents (via --parents ou --children) sont utilisés. Les paramètres suivants sont disponibles.

Mode par défaut

Les commits sont inclus s'ils ne sont pas TREESAME avec aucun parent (bien que cela puisse être modifié, voir --sparse ci-dessous). Si le commit était une fusion, et qu'il était TREESAME avec un parent, suivre uniquement ce parent. (Même s'il y a plusieurs parents TREESAME, n'en suivre qu'un seul.) Sinon, suivre tous les parents.

Cela donne :

          .-A---N---O
         /     /   /
        I---------D

Remarquez comment la règle de ne suivre que le parent TREESAME, si un tel parent est disponible, a complètement éliminé B de la considération. C a été considéré via N, mais est TREESAME. Les commits racines sont comparés à un arbre vide, donc I est !TREESAME.

Les relations parent/enfant ne sont visibles qu'avec --parents, mais cela n'affecte pas les commits sélectionnés en mode par défaut, donc nous avons montré les lignes de parent.

--full-history sans réécriture des parents

Ce mode diffère du mode par défaut sur un point : suivre toujours tous les parents d'une fusion, même si elle est TREESAME avec l'un d'entre eux. Même si plus d'un côté de la fusion a des commits qui sont inclus, cela n'implique pas que la fusion elle-même l'est ! Dans l'exemple, nous obtenons 
        I  A  B  N  D  O  P  Q

M a été exclu car il est TREESAME avec ses deux parents. E, C et B ont tous été parcourus, mais seul B était !TREESAME, donc les autres n'apparaissent pas.

Remarquez que sans réécriture des parents, il n'est pas vraiment possible de parler des relations parent/enfant entre les commits, donc nous les montrons déconnectés.

--full-history avec réécriture des parents

Les commits ordinaires ne sont inclus que s'ils sont !TREESAME (bien que cela puisse être modifié, voir --sparse ci-dessous).

Les fusions sont toujours incluses. Cependant, leur liste de parents est réécrite : le long de chaque parent, élaguer les commits qui ne sont pas inclus eux-mêmes. Cela donne

          .-A---M---N---O---P---Q
         /     /   /   /   /
        I     B   /   D   /
         \   /   /   /   /
          `-------------'

Comparez avec --full-history sans réécriture ci-dessus. Remarquez que E a été élagué car il est TREESAME, mais la liste des parents de P a été réécrite pour contenir le parent E, I. La même chose s'est produite pour C et N, et X, Y et Q.

En plus des paramètres ci-dessus, vous pouvez modifier si TREESAME affecte l'inclusion :

--dense

Les commits qui sont parcourus sont inclus s'ils ne sont pas TREESAME avec aucun parent.

--sparse

Tous les commits qui sont parcourus sont inclus.

Remarquez que sans --full-history, cela simplifie toujours les fusions : si l'un des parents est TREESAME, nous ne suivons que celui-ci, donc les autres côtés de la fusion ne sont jamais parcourus.

--simplify-merges

D'abord, construire un graphe d'historique de la même manière que --full-history avec réécriture des parents le fait (voir ci-dessus).

Ensuite, simplifier chaque commit C en son remplaçant C' dans l'historique final selon les règles suivantes :

•Définir C' à C.
•Remplacer chaque parent P de C' par sa simplification P'. Dans le processus, abandonner les parents qui sont des ancêtres d'autres parents ou qui sont des commits racine TREESAME avec un arbre vide, et supprimer les doublons, mais faire attention à ne jamais abandonner tous les parents avec lesquels nous sommes TREESAME.
•Si après cette réécriture des parents, C' est un commit racine ou de fusion (a zéro ou >1 parents), un commit de limite, ou !TREESAME, il reste. Sinon, il est remplacé par son seul parent.

L'effet de cela est mieux montré en comparant avec --full-history avec réécriture des parents. L'exemple devient :

          .-A---M---N---O
         /     /       /
        I     B       D
         \   /       /
          `---------'

Remarquez les différences majeures dans N, P, et Q par rapport à --full-history:

•N's la liste des parents avait I supprimé, car c'est un ancêtre de l'autre parent M. Pourtant, N est resté car il est !TREESAME.
•P's la liste des parents avait de même I supprimé. P a ensuite été complètement supprimé, car il avait un parent et est TREESAME.
•Q's la liste des parents avait Y simplifié en X. X a ensuite été supprimé, car c'était une racine TREESAME. Q a ensuite été complètement supprimé, car il avait un parent et est TREESAME.

Un autre mode de simplification est disponible :

--ancestry-path[=<commit>]

Limiter les commits affichés à ceux qui sont un ancêtre de <commit>, ou qui sont un descendant de <commit>, ou qui sont <commit> lui-même.

Comme cas d'utilisation, considérez l'historique de commits suivant :

            D---E-------F
           /     \       \
          B---C---G---H---I---J
         /                     \
        A-------K---------------L--M

Un D..M régulier calcule l'ensemble des commits qui sont des ancêtres de M, mais exclut ceux qui sont des ancêtres de D. C'est utile pour voir ce qui s'est passé dans l'historique menant à M depuis D, dans le sens de « qu'est-ce que M a et qui n'existait pas dans D». Le résultat dans cet exemple serait tous les commits, sauf A et B (et D lui-même, bien sûr).

Lorsque nous voulons découvrir quels commits dans M sont contaminés par le bogue introduit par D et ont besoin d'être corrigés, cependant, nous pourrions vouloir n'afficher que le sous-ensemble de D..M qui sont réellement des descendants de D, c'est-à-dire en excluant C et K. C'est exactement ce que l'option --ancestry-path fait. Appliquée à la plage D..M , elle donne :

                E-------F
                 \       \
                  G---H---I---J
                               \
                                L--M

Nous pouvons aussi utiliser --ancestry-path=D au lieu de --ancestry-path ce qui signifie la même chose lorsqu'il est appliqué à la plage D..M mais est simplement plus explicite.

Si nous sommes plutôt intéressés par un sujet donné dans cette plage, et tous les commits affectés par ce sujet, nous pourrions vouloir n'afficher que le sous-ensemble de D..M qui contiennent ce sujet dans leur chemin d'ancêtres. Donc, en utilisant --ancestry-path=H D..M par exemple donnerait :

                E
                 \
              C---G---H---I---J
                               \
                                L--M

Alors que --ancestry-path=K D..M donnerait

                K---------------L--M

--date=<format>

Only takes effect for dates shown in human-readable format, such as when using --pretty. log.date config variable sets a default value for the log command’s --date option. By default, dates are shown in the original time zone (either committer’s or author’s). If -local is appended to the format (e.g., iso-local), the user’s local time zone is used instead.

--date=relative shows dates relative to the current time, e.g. “2 hours ago”. The -local option has no effect for --date=relative.

--date=local is an alias for --date=default-local.

--date=iso (or --date=iso8601) shows timestamps in a ISO 8601-like format. The differences to the strict ISO 8601 format are:

•a space instead of the T date/time delimiter
•a space between time and time zone
•no colon between hours and minutes of the time zone

--date=iso-strict (or --date=iso8601-strict) shows timestamps in strict ISO 8601 format.

--date=rfc (or --date=rfc2822) shows timestamps in RFC 2822 format, often found in email messages.

--date=short shows only the date, but not the time, in YYYY-MM-DD format.

--date=raw shows the date as seconds since the epoch (1970-01-01 00:00:00 UTC), followed by a space, and then the timezone as an offset from UTC (a + or - with four digits; the first two are hours, and the second two are minutes). I.e., as if the timestamp were formatted with strftime("%s %z")). Note that the -local option does not affect the seconds-since-epoch value (which is always measured in UTC), but does switch the accompanying timezone value.

--date=human shows the timezone if the timezone does not match the current time-zone, and doesn’t print the whole date if that matches (ie skip printing year for dates that are "this year", but also skip the whole date itself if it’s in the last few days and we can just say what weekday it was). For older dates the hour and minute is also omitted.

--date=unix shows the date as a Unix epoch timestamp (seconds since 1970). As with --raw, this is always in UTC and therefore -local has no effect.

--date=format:<format> feeds the <format> to your system strftime, except for %s, %z, and %Z, which are handled internally. Use --date=format:%c to show the date in your system locale’s preferred format. See the strftime(3) manual for a complete list of format placeholders. When using -local, the correct syntax is --date=format-local:<format>.

--date=default is the default format, and is based on ctime(3) output. It shows a single line with three-letter day of the week, three-letter month, day-of-month, hour-minute-seconds in "HH:MM:SS" format, followed by 4-digit year, plus timezone information, unless the local time zone is used, e.g. Thu Jan 1 00:00:00 1970 +0000.

OUTPUT

When there are no conflicts, the output of this command is usable as input to git update-ref --stdin. It is of the form:

update refs/heads/branch1 ${NEW_branch1_HASH} ${OLD_branch1_HASH}
update refs/heads/branch2 ${NEW_branch2_HASH} ${OLD_branch2_HASH}
update refs/heads/branch3 ${NEW_branch3_HASH} ${OLD_branch3_HASH}

where the number of refs updated depends on the arguments passed and the shape of the history being replayed. When using --advance, the number of refs updated is always one, but for --onto, it can be one or more (rebasing multiple branches simultaneously is supported).

EXIT STATUS

For a successful, non-conflicted replay, the exit status is 0. When the replay has conflicts, the exit status is 1. If the replay is not able to complete (or start) due to some kind of error, the exit status is something other than 0 or 1.

EXAMPLES

To simply rebase mybranch onto target:

$ git replay --onto target origin/main..mybranch
update refs/heads/mybranch ${NEW_mybranch_HASH} ${OLD_mybranch_HASH}

To cherry-pick the commits from mybranch onto target:

$ git replay --advance target origin/main..mybranch
update refs/heads/target ${NEW_target_HASH} ${OLD_target_HASH}

Note that the first two examples replay the exact same commits and on top of the exact same new base, they only differ in that the first provides instructions to make mybranch point at the new commits and the second provides instructions to make target point at them.

What if you have a stack of branches, one depending upon another, and you’d really like to rebase the whole set?

$ git replay --contained --onto origin/main origin/main..tipbranch
update refs/heads/branch1 ${NEW_branch1_HASH} ${OLD_branch1_HASH}
update refs/heads/branch2 ${NEW_branch2_HASH} ${OLD_branch2_HASH}
update refs/heads/tipbranch ${NEW_tipbranch_HASH} ${OLD_tipbranch_HASH}

When calling git replay, one does not need to specify a range of commits to replay using the syntax A..B; any range expression will do:

$ git replay --onto origin/main ^base branch1 branch2 branch3
update refs/heads/branch1 ${NEW_branch1_HASH} ${OLD_branch1_HASH}
update refs/heads/branch2 ${NEW_branch2_HASH} ${OLD_branch2_HASH}
update refs/heads/branch3 ${NEW_branch3_HASH} ${OLD_branch3_HASH}

This will simultaneously rebase branch1, branch2, and branch3, all commits they have since base, playing them on top of origin/main. These three branches may have commits on top of base that they have in common, but that does not need to be the case.
