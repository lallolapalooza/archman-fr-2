DESCRIPTIO

N

Étant donné un ou plusieurs commits existants, annule les changements introduits par les correctifs associés et enregistre de nouveaux commits qui les consignent. Cela nécessite que votre arbre de travail soit propre (pas de modifications par rapport au commit HEAD)

.

Note : git revert est utilisé pour enregistrer de nouveaux commits afin d'inverser l'effet de certains commits antérieurs (souvent seulement un commit défectueux). Si vous voulez jeter tous les changements non committés dans votre répertoire de travail, vous devriez voir git-reset(1), en particulier l'option --hard. Si vous voulez extraire des fichiers spécifiques tels qu'ils étaient dans un autre commit, vous devriez voir git-restore(1), en particulier l'option --source. Soyez prudent avec ces alternatives car toutes deux jetteront les changements non committés dans votre répertoire de

travail.

Voir « Reset, restore et revert » dans git(1) pour les différences

entre les tr
ois commandes.

OPTION

S

<commit>..

.
Commits à annuler. Pour une liste plus complète de façons de nommer les commits, voir gitrevisions(7). Des ensembles de commits peuvent aussi être donnés mais aucune traversée n'est effectuée par défaut, voir git-rev-list(1) et son option --no-walk
.

-e,

--edit
Avec cette option, git revert vous permettra d'éditer le message du commit avant de committer l'annulation. C'est le comportement par défaut si vous exécutez la commande depuis un
terminal.

-m parent-number, --mainline

parent-number
Habituellement, vous ne pouvez pas annuler une fusion car vous ne savez pas quel côté de la fusion doit être considéré comme la ligne principale. Cette option spécifie le numéro du parent (à partir de 1) de la ligne principale et permet à revert d'inverser le changement par rapport au parent spécifié.

Annuler un commit de fusion déclare que vous ne voulez jamais les changements d'arbre apportés par la fusion. Par conséquent, les fusions ultérieures n'apporteront que les changements d'arbre introduits par des commits qui ne sont pas des ancêtres de la fusion précédemment annulée. Cela peut ou non être ce que vous

voulez.

Voir revert-a-faulty-merge How-To

[1] pour plus
de détails.

--no-edi

t
Avec cette option, git revert ne démarrera pas l'éditeur de message de
commit.

--cleanup=<mode

>
Cette option détermine comment le message de commit sera nettoyé avant d'être transmis au mécanisme de commit. Voir git-commit(1) pour plus de détails. En particulier, si <mode> reçoit la valeur scissors, scissors sera ajouté à MERGE_MSG avant d'être transmis en cas de
conflit.

-n,

--no-commit
Habituellement, la commande crée automatiquement des commits avec des messages de journal indiquant quels commits ont été annulés. Ce drapeau applique les changements nécessaires pour annuler les commits nommés à votre arbre de travail et à l'index, mais ne crée pas les commits. De plus, quand cette option est utilisée, votre index n'a pas besoin de correspondre au commit HEAD. L'annulation est effectuée par rapport à l'état initial de votre index.

C'est utile quand vous annulez

l'effet de plusieurs commits
sur votre index d'un coup.

-S[<keyid>], --gpg-sign[=<keyid>],

--no-gpg-sign
Signe les commits avec GPG. L'argument keyid est optionnel et par défaut correspond à l'identité du committer ; s'il est spécifié, il doit être collé à l'option sans espace. --no-gpg-sign est utile pour contrer à la fois la variable de configuration commit.gpgSign et l'option --gpg-sign préc
édente.

-s,

--signoff
Ajoute un Signed-off-by trailer à la fin du message de commit. Voir l'option signoff dans git-commit(1) pour plus
d'informations.

--strategy=<strategy

>
Utilise la stratégie de fusion donnée. Ne devrait être utilisée qu'une fois. Voir la section MERGE STRATEGIES dans git-merge(1) pour les
détails.

-X<option>, --strategy-option=<option

>
Transmet l'option spécifique à la stratégie de fusion à la stratégie de fusion. Voir git-merge(1) pour les
détails.

--rerere-autoupdate, --no-rerere-autoupdat

e
Après que le mécanisme rerere réutilise une résolution enregistrée sur le conflit actuel pour mettre à jour les fichiers dans l'arbre de travail, lui permettre de mettre à jour également l'index avec le résultat de la résolution. --no-rerere-autoupdate est un bon moyen de revérifier ce que rerere a fait et de détecter des fusions erronées potentielles, avant de committer le résultat dans l'index avec une git add sépa
rée.

--referenc

e
Au lieu de commencer le corps du message de journal par « This reverts <full-object-name-of-the-commit-being-reverted>. », faites référence au commit en utilisant le format « --pretty=reference » (cf. git-log(1)). La variable de configuration revert.reference peut être utilisée po
ur activer cette
option par défaut.

EXEMPLE

S

git revert HEAD~

3
Annule les changements spécifiés par le quatrième commit le plus récent dans HEAD et crée un nouveau commit avec les changements
annulés.

git revert -n master~5..master~

2
Annule les changements effectués par les commits du cinquième commit le plus récent dans mas
ter (inclus) au troisième commit le plus récent dans master (inclus), mais ne crée aucun com
mit avec les changements annulés. L'annulation ne modifie que l'arbre de travail et l'index.

DISCUSSIO

N

Bien que git crée automatiquement un message de commit de base, il est fortement recommandé d'expliquer pourquoi le commit original est annulé. De plus, annuler à plusieurs reprises des annulations entraînera des lignes de sujet de plus en plus encombrantes, par exemple Reapply "Reapply "<original-subject>"". Veuillez envisager de ref

ormuler ces messages pour les r
endre plus courts et plus uniques.
