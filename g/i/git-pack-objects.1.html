DESCRIPTIO

N

Lit la liste d'objets depuis l'entrée standard et écrit soit une ou plusieurs archives compressées avec le nom de base spécifié sur le disque, soit une archive compressée sur la sortie

standard.

Une archive compressée est un moyen efficace de transférer un ensemble d'objets entre deux dépôts ainsi qu'un format d'archivage efficace pour l'accès. Dans une archive compressée, un objet est soit stocké en tant que tout compressé, soit comme différence par rapport à un autre objet. Ce dernier est souvent appelé un

delta.

Le format d'archive compressée (.pack) est conçu pour être autonome afin qu'il puisse être décompressé sans aucune information supplémentaire. Par conséquent, chaque objet dont dépend un delta doit être présent dans le

pack.

Un fichier d'index de pack (.idx) est généré pour un accès rapide et aléatoire aux objets du pack. Placer à la fois le fichier d'index (.idx) et l'archive compressée (.pack) dans le sous-répertoire pack/ de $GIT_OBJECT_DIRECTORY (ou n'importe lequel des répertoires de $GIT_ALTERNATE_OBJECT_DIRECTORIES) permet à Git de lire depuis l'archive de

pack.

La commande git unpack-objects peut lire l'archive compressée et étendre les objets contenus dans le pack au format « un fichier, un objet » ; cela

est généralement fait par les commandes de pull intelligent lorsqu'un pac
k est créé à la volée pour un transport réseau efficace par leurs pairs.

OPTION

S

base-nam

e
Écrit dans des paires de fichiers (.pack et .idx), en utilisant <base-name> pour déterminer le nom du fichier créé. Lorsque cette option est utilisée, les deux fichiers d'une paire sont écrits dans les fichiers <base-name>-<SHA-1>.{pack,idx}. <SHA-1> est un hachage basé sur le contenu du pack et est écrit sur la sortie standard de la
commande.

--stdou

t
Écrit le contenu du pack (ce qui aurait été écrit dans le fichier .pack) sur la sortie
standard.

--rev

s
Lit les arguments de révision depuis l'entrée standard, au lieu des noms d'objets individuels. Les arguments de révision sont traités de la même manière que git rev-list avec l'indicateur --objects utilise ses arguments de commit pour construire la liste des objets qu'il produit. Les objets de la liste résultante sont compressés. En plus des révisions, --not ou --shallow <SHA-1> sont également
acceptés.

--unpacke

d
Cela implique --revs. Lors du traitement de la liste des arguments de révision lus depuis l'entrée standard, limite les objets compressés à ceux qui ne sont pas déjà
compressés.

--al

l
Cela implique --revs. En plus de la liste des arguments de révision lus depuis l'entrée standard, fait comme si toutes les refs sous refs/ étaient spécifiées pour être
incluses.

--include-ta

g
Inclut les tags annotés non demandés si l'objet auquel ils font référence a été inclus dans le fichier de pack résultant. Cela peut être utile pour envoyer de nouveaux tags à des clients Git
natifs.

--stdin-packs[=<mode>

]
Lit les noms de base des fichiers de pack (par ex., pack-1234abcd.pack) depuis l'entrée standard, au lieu des noms d'objets ou des arguments de révision. Le pack résultant contient tous les objets listés dans les packs inclus (ceux ne commençant pas par ^), à l'exclusion de tout objet listé dans les packs exclus (commençant par ^).

Quand mode est « follow », les objets des packs non listés sur stdin reçoivent un traitement spécial. Les objets à l'intérieur des packs non listés seront inclus si ces objets sont (1) accessibles depuis les packs inclus, et (2) non trouvés dans aucun pack exclu. Ce mode est utile, par exemple, pour ressusciter des objets autrefois inaccessibles trouvés dans des packs de cruft afin de générer des packs qui sont fermés sous l'accessibilité jusqu'à l'ensemble défini par les packs

exclus.

Incompatible avec --revs, ou les options qui impliquent --revs (comme --all), à l'exception de --unpacked, qui

est com
patible.

--cruf

t
Compresse les objets inaccessibles dans un pack « cruft » séparé, désigné par l'existence d'un fichier .mtimes. Généralement utilisé par git repack --cruft. Les appelants fournissent une liste de noms de packs et indiquent quels packs resteront dans le dépôt, ainsi que quels packs seront supprimés (indiqué par le préfixe -). Le contenu du pack de cruft est tous les objets non contenus dans les packs survivants qui n'ont pas dépassé la période de grâce (voir --cruft-expiration ci-dessous), ou qui ont dépassé la période de grâce, mais sont accessibles depuis un autre objet qui ne l'a pas fait.

Lorsque l'entrée liste un pack contenant tous les objets accessibles (et liste tous les autres packs comme en attente de suppression), le pack de cruft correspondant contiendra tous les objets inaccessibles (avec une mtime plus récente que --cruft-expiration) ainsi que tous les objets inaccessibles dont la mtime est plus ancienne que --cruft-expiration, mais qui sont accessibles depuis un objet inaccessible dont la mtime est plus récente que --cruft-expir

ation).

Incompatible avec --unpack-unreachable, --keep-unreachable, --pack-loose-unreachable, --stdin-packs, ainsi que toute autre option qui implique --re

v
s.

--cruft-expiration=<approxidate

>
Si spécifié, les objets sont éliminés du pack de cruft s'ils ont une mtime plus ancienne que <approxidate>. Si non spécifié (et avec --cruft), alors aucun objet n'est
éliminé.

--window=<n>,

--depth=<n>
Ces deux options affectent la manière dont les objets contenus dans le pack sont stockés en utilisant la compression delta. Les objets sont d'abord triés internement par type, taille et éventuellement noms, et comparés aux autres objets dans --window pour voir si l'utilisation de la compression delta économise de l'espace. --depth limite la profondeur maximale du delta ; la rendre trop profonde affecte les performances côté décompresser, car les données delta doivent être appliquées autant de fois pour atteindre l'objet nécessaire.

La valeur par défaut de --window

est 10 et --depth est 50. La
profondeur maximale est 4095.

--window-memory=<n

>
Cette option fournit une limite supplémentaire en plus de --window ; la taille de la fenêtre sera réduite dynamiquement afin de ne pas occuper plus de <n> octets en mémoire. C'est utile dans les dépôts avec un mélange de grands et petits objets pour ne pas manquer de mémoire avec une grande fenêtre, mais pouvoir toujours profiter de la grande fenêtre pour les petits objets. La taille peut être suffixée par « k », « m » ou « g ». --window-memory=0 rend l'utilisation de la mémoire illimitée. La valeur par défaut est prise de la variable de configuration pack.windowM
emory.

--max-pack-size=<n

>
Dans des scénarios inhabituels, vous ne pourrez peut-être pas créer de fichiers plus grands qu'une certaine taille sur votre système de fichiers, et cette option peut être utilisée pour indiquer à la commande de diviser le fichier de pack de sortie en plusieurs fichiers de pack indépendants, chacun pas plus grand que la taille donnée. La taille peut être suffixée par « k », « m » ou « g ». La taille minimale autorisée est limitée à 1 MiB. La valeur par défaut est illimitée, sauf si la variable de configuration pack.packSizeLimit est définie. Notez que cette option peut résulter en un dépôt plus grand et plus lent ; voir la discussion dans pack.packSize
Limit.

--honor-pack-kee

p
Cet indicateur fait qu'un objet déjà dans un pack local qui a un fichier .keep est ignoré, même s'il aurait autrement été
compressé.

--keep-pack=<pack-name

>
Cet indicateur fait qu'un objet déjà dans le pack donné est ignoré, même s'il aurait autrement été compressé. <pack-name> est le nom du fichier de pack sans répertoire en tête (par ex. pack-123.pack). L'option peut être spécifiée plusieurs fois pour conserver plusieurs
packs.

--incrementa

l
Cet indicateur fait qu'un objet déjà dans un pack est ignoré même s'il aurait autrement été
compressé.

--loca

l
Cet indicateur fait qu'un objet emprunté à un dépôt alternatift stocké soit ignoré même s'il aurait pu être
empaqueté.

--non-empt

y
Ne crée une archive empaquetée que si elle contient au moins un
objet.

--progres

s
L'état de progression est rapporté sur le flux d'erreur standard par défaut lorsqu'il est attaché à un terminal, sauf si -q est spécifié. Ce drapeau force l'état de progression même si le flux d'erreur standard n'est pas dirigé vers un
terminal.

--all-progres

s
Lorsque --stdout est spécifié, le rapport de progression est affiché pendant les phases de comptage et de compression des objets mais est inhibé pendant la phase d'écriture. La raison est que dans certains cas, le flux de sortie est directement lié à une autre commande qui peut souhaiter afficher son propre état de progression au fur et à mesure qu'elle traite les données de pack entrantes. Ce drapeau est comme --progress sauf qu'il force le rapport de progression pour la phase d'écriture également, même si --stdout est
utilisé.

--all-progress-implie

d
Ceci est utilisé pour impliquer --all-progress chaque fois que l'affichage de progression est activé. Contrairement à --all-progress, ce drapeau ne force pas réellement d'affichage de progression par
lui-même.

-

q
Ce drapeau fait que la commande ne rapporte pas sa progression sur le flux d'erreur
standard.

--no-reuse-delt

a
Lors de la création d'une archive empaquetée dans un dépôt qui a des packs existants, la commande réutilise les deltas existants. Cela entraîne parfois un pack légèrement sous-optimal. Ce drapeau indique à la commande de ne pas réutiliser les deltas existants mais de les calculer à partir de
zéro.

--no-reuse-objec

t
Ce drapeau indique à la commande de ne pas réutiliser les données d'objets existants du tout, y compris les objets non deltaïsés, forçant la recompression de tout. Cela implique --no-reuse-delta. Utile uniquement dans le cas obscur où l'application forcée d'un niveau de compression différent sur les données empaquetées est
souhaitée.

--compression=<n

>
Spécifie le niveau de compression pour les données nouvellement compressées dans le pack généré. Si non spécifié, le niveau de compression du pack est d'abord déterminé par pack.compression, puis par core.compression, et par défaut à -1, la valeur par défaut de zlib, si aucun des deux n'est défini. Ajoutez --no-reuse-object si vous voulez forcer un niveau de compression uniforme sur toutes les données quelle que soit leur
source.

--sparse,

--no-sparse
Bascule l'algorithme "sparse" pour déterminer quels objets inclure dans le pack, lorsqu'il est combiné avec l'option "--revs". Cet algorithme ne parcourt que les arbres qui apparaissent dans les chemins qui introduisent de nouveaux objets. Cela peut avoir des avantages de performance significatifs lors du calcul d'un pack pour envoyer un petit changement. Cependant, il est possible que des objets supplémentaires soient ajoutés au fichier pack si les commits inclus contiennent certains types de renommages directs. Si cette option n'est pas incluse, elle prend par défaut la valeur de pack.useSparse, qui est vrai sauf indication
contraire.

--thi

n
Crée un pack "mince" en omettant les objets communs entre un émetteur et un récepteur afin de réduire le transfert réseau. Cette option n'a de sens qu'en conjonction avec --stdout.

Note : Un pack mince viole le format d'archive empaquetée en omettant les objets requis et est donc inutilisable par Git sans le rendre auto-contenu. Utilisez git index-pack --fix-thin (voir git-index-pack(1)) pour restau

rer la propriét
é auto-contenu.

--shallo

w
Optimise un pack qui sera fourni à un client avec un dépôt superficiel. Cette option, combinée avec --thin, peut résulter en un pack plus petit au détriment de la
vitesse.

--delta-base-offse

t
Une archive empaquetée peut exprimer l'objet de base d'un delta soit comme un nom d'objet de 20 octets, soit comme un décalage dans le flux, mais les anciennes versions de Git ne comprennent pas ce dernier. Par défaut, git pack-objects n'utilise que le premier format pour une meilleure compatibilité. Cette option permet à la commande d'utiliser le dernier format pour la compacité. Selon la longueur moyenne de la chaîne de deltas, cette option réduit généralement le fichier pack résultant de 3 à 5 pour cent.

Note : Les commandes porcelain telles que git gc (voir git-gc(1)), git repack (voir git-repack(1)) passent cette option par défaut dans Git moderne lorsqu'elles placent les objets de votre dépôt dans des fichiers pack. Il en va de même pour git bundle (voir git-bundle(1)) lorsq

u'il crée
un bundle.

--threads=<n

>
Spécifie le nombre de threads à lancer lors de la recherche des meilleures correspondances de delta. Cela nécessite que pack-objects soit compilé avec pthreads, sinon cette option est ignorée avec un avertissement. Cela vise à réduire le temps d'empaquetage sur les machines multiprocesseurs. La quantité de mémoire requise pour la fenêtre de recherche de delta est cependant multipliée par le nombre de threads. Spécifier 0 fera que Git détectera automatiquement le nombre de CPU et définira le nombre de threads en
conséquence.

]
Ceci est destiné à être utilisé uniquement par la suite de tests. Il permet de forcer la version pour l'index de pack généré, et de forcer des entrées d'index 64 bits sur les objets situés au-dessus du décalage
donné.

Une option de débogage pour aider au futur développement du "clone partiel". Cette option spécifie comment les objets manquants sont traités.

--name-hash-version=<n

>
Lors de la compression delta, Git regroupe les objets qui peuvent être similaires en se basant sur des heuristiques utilisant le chemin vers cet objet. Bien que le regroupement des objets par une correspondance exacte de chemin soit bon pour les chemins avec de nombreuses versions, il y a des avantages à trouver des paires de delta à travers différents chemins complets. Git collecte les objets par type puis par un "name hash" du chemin et ensuite par taille, espérant regrouper des objets qui se compresseront bien ensemble.

La version de name hash par défaut est 1, qui priorise la localité du hash en considérant les octets finaux du chemin comme fournissant la magnitude maximale à la fonction de hash. Cette version excelle dans la distinction des chemins courts et la recherche de renommages à travers les répertoires. Cependant, la fonction de hash dépend principalement des 16 derniers octets du chemin. S'il y a de nombreux chemins dans le dépôt qui ont les mêmes 16 derniers octets et ne diffèrent que par le répertoire parent, alors ce name-hash peut conduire à trop de collisions et provoquer de mauvais résultats. Pour le moment, cette version est requise lors de l'écriture de fichiers bitmap d'accessibilité avec --write-bitmap-index

.

La version de name hash 2 a des caractéristiques de localité similaires à la version 1, sauf qu'elle considère chaque composant de chemin séparément et superpose les hashes avec un décalage. Cela priorise toujours les octets finaux du chemin, mais "sale" aussi les bits inférieurs du hash en utilisant les noms des répertoires parents. Cette méthode permet certains des avantages de localité de la version 1 tout en brisant la plupart des collisions d'un fichier portant un nom similaire apparaissant dans de nombreux répertoires différents. Pour le moment, cette version n'est pas autorisée lors de l'écriture de fichiers bitmap d'accessibilité avec --write-bitmap-index et elle sera automatiquement changée en version 1

.

--path-wal

k

Cela a le potentiel d'améliorer la compression delta, en particulier en présence de noms de fichiers qui causent des collisions dans l'algorithme de name-hash par défaut de Git.

Incompatible avec --delta-islands, --shallow, ou --filter. L'option --use-bitmap-index sera ignorée en présence de --p

DELTA

ISLANDS

Lorsque c'est possible, pack-objects essaie de réutiliser les deltas existants sur disque pour éviter d'avoir à en chercher de nouveaux à la volée. C'est une optimisation importante pour servir les fetches, car cela signifie que le serveur peut éviter de décompresser la plupart des objets et envoyer directement les octets depuis le disque. Cette optimisation ne peut pas fonctionner lorsqu'un objet est stocké comme un delta contre une base que le récepteur n'a pas (et que nous n'envoyons pas déjà). Dans ce cas, le serveur "casse" le delta et doit en trouver un nouveau, ce qui a un coût CPU élevé. Il est donc important pour les performances que l'ensemble des objets dans les relations de delta sur disque corresponde à ce qu'un client

récupérerait.

Dans un dépôt normal, cela tend à fonctionner automatiquement. Les objets sont principalement accessibles depuis les branches et les tags, et c'est ce que les clients récupèrent. Tout delta que nous trouvons sur le serveur est probablement entre des objets que le client a ou aura.p>

Mais dans certaines configurations de dépôt, vous pouvez avoir plusieurs groupes de pointeurs de refs liés mais séparés, les clients tendant à récupérer ces groupes indépendamment. Par exemple, imaginez que vous hébergez plusieurs « forks » d'un dépôt dans un seul magasin d'objets partagé, et que vous laissez les clients les voir comme des dépôts séparés via GIT_NAMESPACE ou des dépôts séparés en utilisant le mécanisme des alternates. Un repack naïf peut trouver que le delta optimal pour un objet est contre une base qui ne se trouve que dans un autre fork. Mais lorsqu'un client récupère, il n'aura pas l'objet de base, et nous devrons trouver un nouveau delta à la

volée.

Une situation similaire peut exister si vous avez de nombreuses refs en dehors de refs/heads/ et refs/tags/ qui pointent vers des objets liés (par ex., refs/pull ou refs/changes utilisés par certains fournisseurs d'hébergement). Par défaut, les clients ne récupèrent que les heads et les tags, et les deltas contre des objets qui ne se trouvent que dans ces autres groupes ne peuvent pas être envoyés tels

quels.

Les îles de delta résolvent ce problème en vous permettant de regrouper vos refs en « îles » distinctes. Pack-objects calcule quels objets sont atteignables depuis quelles îles, et refuse de faire un delta depuis un objet A contre une base qui n'est pas présente dans toutes les îles de A. Cela résulte en des packs légèrement plus grands (car nous manquons certaines opportunités de delta), mais garantit qu'une récupération d'une île n'aura pas à recalculer des deltas à la volée à cause du franchissement des limites

d'îles.

Lors du repack avec des îles de delta, la fenêtre de delta a tendance à se boucher avec des candidats interdits par la configuration. Un repack avec une grande valeur de --window aide (et ne prend pas plus de temps qu'il ne le pourrait autrement car nous pouvons rejeter certaines paires d'objets basées sur les îles avant de faire tout calcul sur le contenu)

.

Les îles sont configurées via l'option pack.island, qui peut être spécifiée plusieurs fois. Chaque valeur est une expression régulière ancrée à gauche qui correspond aux noms de refs. Par exemple 

: 
[pack]
island =
refs/heads/ isl
and = refs/tags/

place les heads et les tags dans une île (dont le nom est la chaîne vide ; voir ci-dessous pour plus d'informations sur la nommage). Toute ref qui ne correspond pas à ces expressions régulières (par ex., refs/pull/123) n'est dans aucune île. Tout objet qui n'est atteignable que depuis refs/pull/ (mais pas depuis les heads ou les tags) n'est donc pas un candidat pour être utilisé comme base pour refs/heads/

.

Les refs sont regroupées en îles basées sur leurs « noms », et deux regex qui produisent le même nom sont considérées comme étant dans la même île. Les noms sont calculés à partir des regex en concaténant tous les groupes de capture de la regex, avec un - tiret entre chaque. (Et s'il n'y a pas de groupes de capture, alors le nom est la chaîne vide, comme dans l'exemple ci-dessus.) Cela vous permet de créer un nombre arbitraire d'îles. Seulement jusqu'à 14 groupes de capture de ce type sont supportés

cependant.

Par exemple, imaginez que vous stockez les refs pour chaque fork dans refs/virtual/ID, où ID est un identifiant numérique. Vous pourriez alors configurer 

: 
[pack]
island = refs/virtual/([0-9]+)/he
ads/ island = refs/virtual/([0-9]+)/tags
/ island = refs/virtual/([0-9]+)/(pull)/

Cela place les heads et les tags de chaque fork dans leur propre île (nommée "1234" ou similaire), et les refs de pull de chacun vont dans leur propre

"1234-pull".

Notez que nous choisissons une seule île pour chaque regex, en utilisant un ordonnan

cement "le dernier gagne" (ce qui permet à la configuration spécifique au dépôt de
prendre le dessus sur la configuration globale de l'utilisateur, et ainsi de suite).
