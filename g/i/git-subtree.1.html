NOM

git-subtree - Fusionner des sous-répertoires ensemble et diviser un dépôt en sous-répertoires

SYNTAXE

git subtree [<options>] -P <prefix> [-S[<keyid>]] add <commit-local>
git subtree [<options>] -P <prefix> [-S[<keyid>]] add <dépôt> <ref-distant>
git subtree [<options>] -P <prefix> [-S[<keyid>]] merge <commit-local> [<dépôt>]
git subtree [<options>] -P <prefix> [-S[<keyid>]] split [<commit-local>]
git subtree [<options>] -P <prefix> [-S[<keyid>]] pull <dépôt> <ref-distant>
git subtree [<options>] -P <prefix> [-S[<keyid>]] push <dépôt> <refspec>

DESCRIPTION

Les sous-répertoires (subtrees) permettent d'inclure des sous-projets dans un répertoire du projet principal, en incluant optionnellement tout l'historique du sous-projet.

Par exemple, vous pourriez inclure le code source d'une librairie comme sous-répertoire de votre application.

Les sous-répertoires ne doivent pas être confondus avec les sous-modules (submodules), qui sont destinés à la même tâche. Contrairement aux sous-modules, les sous-répertoires n'ont pas besoin de constructions spéciales (comme des fichiers .gitmodules ou des gitlinks) présents dans votre dépôt, et n'obligent pas les utilisateurs finaux de votre dépôt à faire quoi que ce soit de spécial ou à comprendre le fonctionnement des sous-répertoires. Un sous-répertoire est juste un répertoire qui peut être commit, branché et fusionné avec votre projet comme vous le souhaitez.

Ils ne doivent pas non plus être confondus avec l'utilisation de la stratégie de fusion subtree. La principale différence est que, en plus de fusionner l'autre projet en tant que sous-répertoire, vous pouvez également extraire l'intégralité de l'historique d'un sous-répertoire de votre projet et en faire un projet autonome. Contrairement à la stratégie de fusion subtree, vous pouvez alterner entre ces deux opérations. Si la librairie autonome est mise à jour, vous pouvez automatiquement fusionner les changements dans votre projet ; si vous mettez à jour la librairie à l'intérieur de votre projet, vous pouvez "diviser" les changements et les fusionner à nouveau dans le projet de la librairie.

Par exemple, si une librairie que vous avez créée pour une application devient utile ailleurs, vous pouvez en extraire tout l'historique et la publier comme son propre dépôt git, sans mélanger accidentellement l'historique de votre projet d'application.


Astuce

Afin de garder vos messages de commit propres, nous recommandons aux gens de séparer leurs commits entre les sous-répertoires et le projet principal autant que possible. C'est-à-dire, si vous apportez une modification qui affecte à la fois la librairie et l'application principale, commitez-la en deux parties. Ainsi, lorsque vous diviserez plus tard les commits de la librairie, leurs descriptions auront toujours du sens. Mais si cela n'est pas important pour vous, ce n'est pas nécessaire. git subtree laissera simplement de côté les parties du commit non liées à la librairie lorsqu'il les divisera dans le sous-projet plus tard.

COMMANDES

add <commit-local>, add <dépôt> <ref-distant>

Crée le sous-répertoire <prefix> en important son contenu à partir du <commit-local> ou du <dépôt> et <ref-distant> donnés. Un nouveau commit est automatiquement créé, rejoignant l'historique du projet importé avec le vôtre. Avec --squash, importe uniquement un seul commit du sous-projet, plutôt que son historique complet.

merge <commit-local> [<dépôt>]

Fusionne les changements récents jusqu'à <commit-local> dans le sous-répertoire <prefix>. Comme avec git merge normal, cela ne supprime pas vos propres changements locaux ; cela fusionne simplement ces changements dans le dernier <commit-local>. Avec --squash, crée un seul commit qui contient tous les changements, plutôt que de fusionner l'historique complet.

Si vous utilisez --squash, la direction de la fusion n'a pas toujours besoin d'être vers l'avant ; vous pouvez utiliser cette commande pour revenir dans le temps de v2.5 à v2.4, par exemple. Si votre fusion introduit un conflit, vous pouvez le résoudre des manières habituelles.

Lorsque vous utilisez --squash, et que la fusion précédente avec --squash a fusionné un tag annoté du dépôt subtree, ce tag doit être disponible localement. Si <dépôt> est spécifié, un tag manquant sera automatiquement récupéré de ce dépôt.

split [<commit-local>] [<dépôt>]

Extrait un nouvel historique de projet synthétique de l'historique du sous-répertoire <prefix> de <commit-local>, ou de HEAD si aucun <commit-local> n'est donné. Le nouvel historique n'inclut que les commits (y compris les fusions) qui ont affecté <prefix>, et chacun de ces commits a maintenant le contenu de <prefix> à la racine du projet au lieu d'être dans un sous-répertoire. Ainsi, l'historique nouvellement créé est adapté à l'exportation en tant que dépôt git séparé.

Après une division réussie, un seul ID de commit est imprimé sur stdout. Cela correspond au HEAD de l'arbre nouvellement créé, que vous pouvez manipuler comme vous le souhaitez.

Des divisions répétées de l'historique exactement identique sont garanties d'être identiques (c'est-à-dire de produire les mêmes IDs de commit) tant que les paramètres passés à split (comme --annotate) sont les mêmes. Pour cette raison, si vous ajoutez de nouveaux commits puis re-divisez, les nouveaux commits seront attachés comme commits au-dessus de l'historique que vous avez généré la dernière fois, donc git merge et les commandes similaires fonctionneront comme prévu.

Lorsqu'une fusion précédente avec --squash a fusionné un tag annoté du dépôt subtree, ce tag doit être disponible localement. Si <dépôt> est spécifié, un tag manquant sera automatiquement récupéré de ce dépôt.

pull <dépôt> <ref-distant>

Exactement comme merge, mais imite git pull en récupérant la référence donnée du dépôt distant spécifié.

push <dépôt> [+][<commit-local>:]<ref-distant>

Effectue un split en utilisant le sous-répertoire <prefix> de <commit-local> et effectue ensuite un git push pour envoyer le résultat au <dépôt> et <ref-distant>. Ceci peut être utilisé pour pousser votre sous-répertoire vers différentes branches du dépôt distant. Comme avec split, si aucun <commit-local> n'est donné, HEAD est utilisé. Le signe + optionnel au début est ignoré.

OPTIONS POUR TOUTES LES COMMANDES

-q, --quiet

Supprime les messages de sortie inutiles sur stderr.

-d, --debug

Produit encore plus de messages de sortie inutiles sur stderr.

-P <prefix>, --prefix=<prefix>

Spécifie le chemin dans le dépôt du sous-répertoire que vous voulez manipuler. Cette option est obligatoire pour toutes les commandes.

-S[<keyid>], --gpg-sign[=<keyid>], --no-gpg-sign

Signe les commits avec GPG. L'argument keyid est optionnel et par défaut, il utilise l'identité du committer ; --no-gpg-sign est utile pour annuler une option --gpg-sign donnée plus tôt dans la ligne de commande.

OPTIONS POUR ADD ET MERGE (AUSSI : PULL, SPLIT --REJOIN, ET PUSH --REJOIN)

Ces options pour add et merge peuvent également être données à pull (qui encapsule merge), split --rejoin (qui encapsule soit add soit merge selon le cas), et push --rejoin (qui encapsule split --rejoin).

--squash

Au lieu de fusionner l'historique complet du projet de sous-répertoire, produit uniquement un seul commit qui contient toutes les différences que vous souhaitez fusionner, puis fusionne ce nouveau commit dans votre projet.

Utiliser cette option aide à réduire le désordre dans le log. Les gens veulent rarement voir chaque changement qui s'est produit entre les versions v1.0 et v1.1 de la librairie qu'ils utilisent, étant donné qu'aucune des versions intermédiaires n'a jamais été incluse dans leur application.

L'utilisation de --squash aide également à éviter les problèmes lorsque le même sous-projet est inclus plusieurs fois dans le même projet, ou est supprimé puis ré-ajouté. Dans ce cas, il n'est pas logique de combiner les historiques de toute façon, car il n'est pas clair quelle partie de l'historique appartient à quel sous-répertoire.

De plus, avec --squash, vous pouvez passer d'une version à l'autre d'un sous-répertoire, plutôt que de strictement avancer. git subtree merge --squash ajuste toujours le sous-répertoire pour correspondre exactement au commit spécifié, même si l'atteinte de ce commit nécessiterait d'annuler certains changements ajoutés précédemment.

git-subtree(1) — pages de manuel Arch Linux

NAME

git-subtree - Gérer les sous-arborescences du projet

SYNOPSIS

git subtree add [--prefix=<prefix>] [--annotate=<annotation>] [--ignore-joins] [--onto=<onto>] [--rejoin] [--squash] <repository> [<ref>]

git subtree split [--prefix=<prefix>] [--annotate=<annotation>] [--ignore-joins] [--onto=<onto>] [--rejoin] [--branch=<branch>] [<commit>...]]

git subtree merge [--prefix=<prefix>] [--annotate=<annotation>] [--ignore-joins] [--onto=<onto>] [--rejoin] [--squash] <commit>...

git subtree push [--prefix=<prefix>] [--annotate=<annotation>] [--ignore-joins] [--onto=<onto>] [--rejoin] [--branch=<branch>] <repository> [<ref>]

DESCRIPTION

git subtree permet de gérer un projet comme une sous-arborescence d'un autre projet. Par exemple, si vous avez votre propre dépôt Git et que vous voulez inclure le dépôt Git d'une bibliothèque externe comme un sous-répertoire de votre dépôt, git subtree peut vous aider à le faire.

Cela vous permet de contribuer à la bibliothèque externe, puis de pousser vos modifications vers le dépôt externe. Inversement, vous pouvez tirer les modifications du dépôt externe dans votre propre dépôt.

L'idée est que la sous-arborescence est un dépôt Git normal, mais que ses modifications sont isolées dans un répertoire spécifique de votre dépôt principal. git subtree peut créer une nouvelle arborescence à partir d'un dépôt existant, ou extraire une partie d'un dépôt existant et la pousser vers un nouveau dépôt. Il peut également récupérer les modifications du dépôt externe et les fusionner dans votre dépôt principal.

COMMANDS

Les commandes disponibles sont :

  • add

    Ajoute une nouvelle sous-arborescence à partir d'un dépôt existant.

  • split

    Crée une nouvelle branche contenant uniquement l'historique de la sous-arborescence spécifiée.

  • merge

    Fusionne les modifications d'une sous-arborescence dans le dépôt principal.

  • pull

    Récupère les modifications d'un dépôt distant et les fusionne dans la sous-arborescence. C'est un raccourci pour git subtree merge avec un extrait du dernier commit.

  • push

    Pousse les modifications de la sous-arborescence vers un dépôt distant. C'est un raccourci pour git subtree split suivi d'un push.

OPTIONS FOR ALL COMMANDS

Ces options s'appliquent à toutes les commandes de git subtree.

-p <prefix>, --prefix=<prefix>

Spécifie le répertoire <prefix> qui contiendra la sous-arborescence. Ce répertoire sera créé s'il n'existe pas.

--squash

Effectue un squash de l'historique de la sous-arborescence en un seul commit lors de l'ajout ou de la fusion. Cela permet de garder l'historique du dépôt principal plus propre. Les modifications seront appliquées comme un nouveau commit unique dans le dépôt principal. Les commits originaux de la sous-arborescence ne sont pas ajoutés à l'historique du dépôt principal.

OPTIONS POUR SPLIT (ET AUSSI : PUSH)

Ces options pour split peuvent également être données à push (qui encapsule split).

--annotate=<annotation>

Lors de la génération d'un historique synthétique, ajoute <annotation> comme préfixe à chaque message de commit. Étant donné que nous créons de nouveaux commits avec le même message de commit, mais un contenu potentiellement différent, des commits originaux, cela peut aider à les différencier et à éviter la confusion.

Chaque fois que vous effectuez un split, vous devez utiliser la même <annotation>, sinon vous n'avez aucune garantie que le nouvel historique recréé sera identique à l'ancien. Cela empêchera la fusion de fonctionner correctement. git subtree essaie de faire en sorte que cela fonctionne quand même, en particulier si vous utilisez --rejoin, mais cela peut ne pas toujours être efficace.

-b <branch>, --branch=<branch>

Après la génération de l'historique synthétique, crée une nouvelle branche nommée <branch> qui contient le nouvel historique. Ceci est adapté pour un push immédiat vers un dépôt distant. <branch> ne doit pas exister au préalable.

--ignore-joins

Si vous utilisez --rejoin, git subtree tente d'optimiser sa reconstruction de l'historique pour générer uniquement les nouveaux commits depuis le dernier --rejoin. --ignore-joins désactive ce comportement, forçant la régénération de l'intégralité de l'historique. Dans un grand projet, cela peut prendre beaucoup de temps.

--onto=<onto>

Si votre sous-arborescence a été initialement importée en utilisant autre chose que git subtree, son historique peut ne pas correspondre à ce que git subtree attend. Dans ce cas, vous pouvez spécifier l'ID de commit <onto> qui correspond à la première révision de l'historique du sous-projet qui a été importée dans votre projet, et git subtree tentera de construire son historique à partir de là.

Si vous avez utilisé git subtree add, vous n'aurez jamais besoin de cette option.

--rejoin

Après le split, fusionne le nouvel historique synthétique créé dans votre projet principal. De cette façon, les futurs splits pourront rechercher uniquement la partie de l'historique qui a été ajoutée depuis le --rejoin le plus récent.

Si vos commits de split finissent par être fusionnés dans la sous-arborescence distante, et que vous souhaitez ensuite obtenir la dernière version distante, cela permettra à l'algorithme de fusion de git d'éviter plus intelligemment les conflits (car il sait que ces commits synthétiques font déjà partie du dépôt distant).

Malheureusement, l'utilisation de cette option entraîne que git log affiche une copie supplémentaire de chaque nouveau commit qui a été créé (l'original et le synthétique).

Si vous effectuez toutes vos fusions avec --squash, assurez-vous d'utiliser également --squash lorsque vous effectuez un split --rejoin.

EXEMPLE 1. COMMANDE ADD

Supposons que vous ayez un dépôt local auquel vous souhaitez ajouter une bibliothèque de fournisseur externe. Dans ce cas, nous allons ajouter le dépôt git-subtree comme sous-répertoire de votre dépôt git-extensions existant dans ~/git-extensions/ :

$ git subtree add --prefix=git-subtree --squash \
        git://github.com/apenwarr/git-subtree.git master

master doit être une référence distante valide et peut être un nom de branche différent

Vous pouvez omettre le drapeau --squash, mais cela augmentera le nombre de commits inclus dans votre dépôt local.

Nous avons maintenant un répertoire ~/git-extensions/git-subtree contenant le code de la branche master de git://github.com/apenwarr/git-subtree.git dans notre dépôt git-extensions.

EXEMPLE 2. EXTRACTION D'UNE SOUS-ARBORESCENCE AVEC COMMIT, MERGE ET PULL

Utilisons le dépôt du code source de git comme exemple. Tout d'abord, obtenez votre propre copie du dépôt git.git :

$ git clone git://git.kernel.org/pub/scm/git/git.git test-git
$ cd test-git

gitweb (commit 1130ef3) a été fusionné dans git à partir du commit 0a8f4f0, après quoi il n'a plus été maintenu séparément. Mais imaginons qu'il ait été maintenu séparément, et que nous voulions extraire les modifications de git apportées à gitweb depuis ce moment, pour les partager avec le dépôt distant. Vous pourriez faire ceci :

$ git subtree split --prefix=gitweb --annotate='(split) ' \
        0a8f4f0^.. --onto=1130ef3 --rejoin \
        --branch gitweb-latest
$ gitk gitweb-latest
$ git push git@github.com:whatever/gitweb.git gitweb-latest:master

(Nous utilisons 0a8f4f0^.. car cela signifie "toutes les modifications depuis 0a8f4f0 jusqu'à la version actuelle, y compris 0a8f4f0 lui-même.")

Si gitweb avait été initialement fusionné en utilisant git subtree add (ou si un split précédent avait déjà été effectué avec --rejoin spécifié), alors vous pouvez effectuer tous vos splits sans avoir à vous souvenir d'identifiants de commit étranges :

$ git subtree split --prefix=gitweb --annotate='(split) ' --rejoin \
        --branch gitweb-latest2

Et vous pouvez fusionner les modifications du dépôt distant aussi facilement :

$ git subtree pull --prefix=gitweb \
        git@github.com:whatever/gitweb.git master

Ou, en utilisant --squash, vous pouvez en fait revenir à une version antérieure de gitweb :

$ git subtree merge --prefix=gitweb --squash gitweb-latest~10

Puis faites quelques modifications :

$ date >gitweb/myfile
$ git add gitweb/myfile
$ git commit -m 'created myfile'

Et avancez à nouveau rapidement :

$ git subtree merge --prefix=gitweb --squash gitweb-latest

Et notez que votre modification est toujours intacte :

$ ls -l gitweb/myfile

Et vous pouvez l'extraire et examiner vos modifications par rapport au gitweb standard :

git log gitweb-latest..$(git subtree split --prefix=gitweb)

EXEMPLE 3. EXTRACTION D'UNE SOUS-ARBORESCENCE UTILISANT UNE BRANCHE

Supposons que vous ayez un répertoire source avec de nombreux fichiers et sous-répertoires, et que vous souhaitiez extraire le répertoire lib dans son propre projet git. Voici un moyen rapide de le faire :

D'abord, créez le nouveau dépôt où vous le souhaitez :

$ <aller à l'emplacement du nouveau dépôt>
$ git init --bare

De retour dans votre répertoire d'origine :

$ git subtree split --prefix=lib --annotate="(split)" -b split

Puis poussez la nouvelle branche vers le nouveau dépôt vide :

$ git push <nouveau-repo> split:master
