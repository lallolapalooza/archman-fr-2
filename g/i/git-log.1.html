NOM

git-log - Afficher les journaux de commits

SYNOPIS

git log [<options>] [<plage-de-révisions>] [[--] <chemin>...

DESCRIPTION

Affiche les journaux de commits.

Liste les commits qui sont atteignables en suivant les liens parent à partir des commits donnés, mais exclut les commits qui sont atteignables depuis ceux donnés avec un ^ devant eux. La sortie est donnée par défaut dans l'ordre chronologique inverse.

Vous pouvez considérer cela comme une opération d'ensemble. Les commits atteignables à partir de l'un des commits donnés sur la ligne de commande forment un ensemble, puis les commits atteignables à partir de l'un de ceux donnés avec ^ devant sont soustraits de cet ensemble. Les commits restants sont ce qui est sorti dans la sortie de la commande. Diverses autres options et paramètres de chemin peuvent être utilisés pour limiter davantage le résultat.

Ainsi, la commande suivante :

$ git log foo bar ^baz

signifie "lister tous les commits qui sont atteignables depuis foo ou bar, mais pas depuis baz".

Une notation spéciale "<commit1>..<commit2>" peut être utilisée comme raccourci pour "^<commit1> <commit2>". Par exemple, l'une ou l'autre des syntaxes suivantes peut être utilisée de manière interchangeable :

$ git log origin..HEAD
$ git log HEAD ^origin

Une autre notation spéciale est "<commit1>...<commit2>" qui est utile pour les fusions. L'ensemble résultant de commits est la différence symétrique entre les deux opérandes. Les deux commandes suivantes sont équivalentes :

$ git log A B --not $(git merge-base --all A B)
$ git log A...B

La commande prend des options applicables à la commande git-rev-list(1) pour contrôler ce qui est affiché et comment, et des options applicables à la commande git-diff(1) pour contrôler comment les changements introduits par chaque commit sont affichés.

OPTIONS

--follow

Continue de lister l'historique d'un fichier au-delà des renommages (ne fonctionne que pour un seul fichier).

--no-decorate, --decorate[=(short|full|auto|no)]

Affiche les noms de refs de tous les commits montrés. Les valeurs possibles sont : 
`short`;; les préfixes de noms de refs `refs/heads/`, `refs/tags/` et
        `refs/remotes/` ne sont pas imprimés.
`full`;; le nom de ref complet (y compris le préfixe) est imprimé.
`auto`:: si la sortie est dirigée vers un terminal, les noms de refs
        sont affichés comme si `short` avait été donné, sinon aucun nom
        de ref n'est affiché.

L'option --decorate est un raccourci pour --decorate=short. Par défaut, utilise la valeur de configuration de log.decorate si configuré, sinon, auto.

--decorate-refs=<motif>, --decorate-refs-exclude=<motif>

Pour chaque référence candidate, ne l'utilise pas pour la décoration si elle correspond à l'un des paramètres <motif> donnés à --decorate-refs-exclude ou si elle ne correspond à aucun des paramètres <motif> donnés à --decorate-refs. L'option de configuration log.excludeDecoration permet d'exclure les refs des décorations, mais un motif --decorate-refs explicite remplacera une coïncidence dans log.excludeDecoration.

Si aucune de ces options ou paramètres de configuration n'est donné, alors les références sont utilisées comme décoration si elles correspondent à HEAD, refs/heads/, refs/remotes/, refs/stash/, ou refs/tags/.

--clear-decorations

Lorsqu'elle est spécifiée, cette option efface toutes les options précédentes --decorate-refs ou --decorate-refs-exclude et assouplit le filtre de décoration par défaut pour inclure toutes les références. Cette option est supposée si la valeur de configuration log.initialDecorationSet est définie sur all.

--source

Affiche le nom de la ref donné sur la ligne de commande par laquelle chaque commit a été atteint.

--mailmap, --no-mailmap, --use-mailmap, --no-use-mailmap

Utilise le fichier mailmap pour mapper les noms et adresses e-mail des auteurs et des commiteurs vers des noms et adresses e-mail réels canoniques. Voir git-shortlog(1).

--full-diff

Sans ce drapeau, git log -p <chemin>... montre les commits qui touchent les chemins spécifiés, et les diffs concernant les mêmes chemins spécifiés. Avec ce drapeau, le diff complet est affiché pour les commits qui touchent les chemins spécifiés ; cela signifie que "<chemin>..." limite uniquement les commits, et ne limite pas le diff pour ces commits.

Notez que cela affecte tous les types de sortie basés sur le diff, par exemple ceux produits par --stat, etc.

--log-size

Inclut une ligne log taille <nombre> dans la sortie pour chaque commit, où <nombre> est la longueur du message de ce commit en octets. Destiné à accélérer les outils qui lisent les messages de log depuis la sortie de git log en leur permettant d'allouer de l'espace à l'avance.

-L<debut>,<fin>:<fichier>, -L:<nom-fonction>:<fichier>

Traque l'évolution de la plage de lignes donnée par <debut>,<fin>, ou par le motif regex <nom-fonction>, dans le <fichier>. Vous ne pouvez pas donner de limiteurs de spécification de chemin. Ceci est actuellement limité à une promenade commençant par une seule révision, c'est-à-dire que vous ne pouvez donner que zéro ou un argument de révision positif, et <debut> et <fin> (ou <nom-fonction>) doivent exister dans la révision de départ. Vous pouvez spécifier cette option plusieurs fois. Implique --patch. La sortie du patch peut être supprimée en utilisant --no-patch, mais d'autres formats de diff (à savoir --raw, --numstat, --shortstat, --dirstat, --summary, --name-only, --name-status, --check) ne sont actuellement pas implémentés.

<debut> et <fin> peuvent prendre l'une des formes suivantes :

•<nombre>

Si <debut> ou <fin> est un nombre, il spécifie un numéro de ligne absolu (les lignes sont comptées à partir de 1).

•/<regex>/

Cette forme utilisera la première ligne correspondant au <regex> POSIX donné. Si <debut> est un regex, il cherchera à partir de la fin de la précédente plage -L, le cas échéant, sinon à partir du début du fichier. Si <debut> est ^/<regex>/, il cherchera à partir du début du fichier. Si <fin> est un regex, il cherchera en commençant à la ligne donnée par <debut>.

•+<décalage> ou -<décalage>

Ceci n'est valide que pour <fin> et spécifiera un nombre de lignes avant ou après la ligne donnée par <debut>.

Si :<nom-fonction> est donné à la place de <debut> et <fin>, c'est une expression régulière qui dénote la plage allant de la première ligne de fonction correspondant à <nom-fonction>, jusqu'à la ligne de fonction suivante. :<nom-fonction> cherche à partir de la fin de la précédente plage -L, le cas échéant, sinon à partir du début du fichier. ^:<nom-fonction> cherche à partir du début du fichier. Les noms de fonctions sont déterminés de la même manière que git diff détermine les en-têtes de blocs de patch (voir Définir un en-tête de bloc personnalisé dans gitattributes(5)).

<plage-de-révisions>

Affiche uniquement les commits dans la plage de révisions spécifiée. Lorsqu'aucune <plage-de-révisions> n'est spécifiée, elle est par défaut HEAD (c'est-à-dire tout l'historique menant au commit actuel). origin..HEAD spécifie tous les commits atteignables depuis le commit actuel (c'est-à-dire HEAD), mais pas depuis origin. Pour une liste complète des façons d'épeler une <plage-de-révisions>, voir la section Spécification des plages de gitrevisions(7).

NAME

git-rev-list - Git revision list formatter

SYNOPSIS

git rev-list [<common-options>] [<revision-range>]
git rev-list [<common-options>] [<commit>... ] [<ref>...]

DESCRIPTION

Lists commit objects in reverse chronological order. The list of commit objects can be controlled by specifying various options and ranges.

The common options can also be given via standard input. This accepts commits and pseudo-options like --all and --glob=. When a -- separator is seen, the following input is treated as paths and used to limit the result. Flags like --not which are read via standard input are only respected for arguments passed in the same way and will not influence any subsequent command line arguments.

--cherry-mark

Like --cherry-pick (see below) but mark equivalent commits with = rather than omitting them, and inequivalent ones with +.

--cherry-pick

Omit any commit that introduces the same change as another commit on the “other side” when the set of commits are limited with symmetric difference.

For example, if you have two branches, A and B, a usual way to list all commits on only one side of them is with --left-right (see the example below in the description of the --left-right option). However, it shows the commits that were cherry-picked from the other branch (for example, “3rd on b” may be cherry-picked from branch A). With this option, such pairs of commits are excluded from the output.

--left-only, --right-only

List only commits on the respective side of a symmetric difference, i.e. only those which would be marked < resp. > by --left-right.

For example, --cherry-pick --right-only A...B omits those commits from B which are in A or are patch-equivalent to a commit in A. In other words, this lists the + commits from git cherry A B. More precisely, --cherry-pick --right-only --no-merges gives the exact list.

--cherry

A synonym for --right-only --cherry-mark --no-merges; useful to limit the output to the commits on our side and mark those that have been applied to the other side of a forked history with git log --cherry upstream...mybranch, similar to git cherry upstream mybranch.

-g, --walk-reflogs

Instead of walking the commit ancestry chain, walk reflog entries from the most recent one to older ones. When this option is used you cannot specify commits to exclude (that is, ^<commit>, <commit1>..<commit2>, and <commit1>...<commit2> notations cannot be used).

With --pretty format other than oneline and reference (for obvious reasons), this causes the output to have two extra lines of information taken from the reflog. The reflog designator in the output may be shown as ref@{<Nth>} (where <Nth> is the reverse-chronological index in the reflog) or as ref@{<timestamp>} (with the <timestamp> for that entry), depending on a few rules:

1.If the starting point is specified as ref@{<Nth>}, show the index format.
2.If the starting point was specified as ref@{now}, show the timestamp format.
3.If neither was used, but --date was given on the command line, show the timestamp in the format requested by --date.
4.Otherwise, show the index format.

Under --pretty=oneline, the commit message is prefixed with this information on the same line. This option cannot be combined with --reverse. See also git-reflog(1).

Under --pretty=reference, this information will not be shown at all.

--merge

Show commits touching conflicted paths in the range HEAD...<other>, where <other> is the first existing pseudoref in MERGE_HEAD, CHERRY_PICK_HEAD, REVERT_HEAD or REBASE_HEAD. Only works when the index has unmerged entries. This option can be used to show relevant commits when resolving conflicts from a 3-way merge.

--boundary

Output excluded boundary commits. Boundary commits are prefixed with -.

HISTORY SIMPLIFICATION

Sometimes you are only interested in parts of the history, for example the commits modifying a particular <path>. But there are two parts of History Simplification, one part is selecting the commits and the other is how to do it, as there are various strategies to simplify the history.

The following options select the commits to be shown:

<paths>

Commits modifying the given <paths> are selected.

--simplify-by-decoration

Commits that are referred by some branch or tag are selected.

Note that extra commits can be shown to give a meaningful history.

The following options affect the way the simplification is performed:

Default mode

Simplifies the history to the simplest history explaining the final state of the tree. Simplest because it prunes some side branches if the end result is the same (i.e. merging branches with the same content)

--show-pulls

Include all commits from the default mode, but also any merge commits that are not TREESAME to the first parent but are TREESAME to a later parent. This mode is helpful for showing the merge commits that "first introduced" a change to a branch.

--full-history

Same as the default mode, but does not prune some history.

--dense

Only the selected commits are shown, plus some to have a meaningful history.

--sparse

All commits in the simplified history are shown.

--simplify-merges

Additional option to --full-history to remove some needless merges from the resulting history, as there are no selected commits contributing to this merge.

--ancestry-path[=<commit>]

When given a range of commits to display (e.g. <commit1>..<commit2> or <commit2> ^<commit1>), and a commit <commit> in that range, only display commits in that range that are ancestors of <commit>, descendants of <commit>, or <commit> itself. If no commit is specified, use <commit1> (the excluded part of the range) as <commit>. Can be passed multiple times; if so, a commit is included if it is any of the commits given or if it is an ancestor or descendant of one of them.

A more detailed explanation follows.

Suppose you specified foo as the <paths>. We shall call commits that modify foo !TREESAME, and the rest TREESAME. (In a diff filtered for foo, they look different and equal, respectively.)

In the following, we will always refer to the same example history to illustrate the differences between simplification settings. We assume that you are filtering for a file foo in this commit graph:

          .-A---M---N---O---P---Q
         /     /   /   /   /   /
        I     B   C   D   E   Y
         \   /   /   /   /   /
          `-------------'   X

The horizontal line of history A---Q is taken to be the first parent of each merge. The commits are:

•I is the initial commit, in which foo exists with contents asdf, and a file quux exists with contents quux. Initial commits are compared to an empty tree, so I is !TREESAME.
•In A, foo contains just foo.
•B contains the same change as A. Its merge M is trivial and hence TREESAME to all parents.
•C does not change foo, but its merge N changes it to foobar, so it is not TREESAME to any parent.
•D sets foo to baz. Its merge O combines the strings from N and D to foobarbaz; i.e., it is not TREESAME to any parent.
•E changes quux to xyzzy, and its merge P combines the strings to quux xyzzy. P is TREESAME to O, but not to E.
•X is an independent root commit that added a new file side, and Y modified it. Y is TREESAME to X. Its merge Q added side to P, and Q is TREESAME to P, but not to Y.

rev-list walks backwards through history, including or excluding commits based on whether --full-history and/or parent rewriting (via --parents or --children) are used. The following settings are available.

Default mode

Commits are included if they are not TREESAME to any parent (though this can be changed, see --sparse below). If the commit was a merge, and it was TREESAME to one parent, follow only that parent. (Even if there are several TREESAME parents, follow only one of them.) Otherwise, follow all parents.

This results in:

          .-A---N---O
         /     /   /
        I---------D

Note how the rule to only follow the TREESAME parent, if one is available, removed B from consideration entirely. C was considered via N, but is TREESAME. Root commits are compared to an empty tree, so I is !TREESAME.

Parent/child relations are only visible with --parents, but that does not affect the commits selected in default mode, so we have shown the parent lines.

--full-history without parent rewriting

This mode differs from the default in one point: always follow all parents of a merge, even if it is TREESAME to one of them. Even if more than one side of the merge has commits that are included, this does not imply that the merge itself is! In the example, we get 
        I  A  N  D  O  P  Q

M was excluded because it is TREESAME to both parents. E, C and B were all walked, but only B was !TREESAME, so the others do not appear.

Avant de discuter d'une autre option, --show-pulls, nous devons créer un nouvel exemple

d'historique.

Un problème courant auquel les utilisateurs sont confrontés lorsqu'ils consultent un historique simplifié est qu'un commit qu'ils savent avoir modifié un fichier d'une manière ou d'une autre n'apparaît pas dans l'historique simplifié du fichier. Démontrons un nouvel exemple et montrons comment des options telles que --full-history et --simplify-merges fonctionnent dans ce cas

: 
          .-A---M-----C--N---O---P
         /     / \  \  \/   /   /
I B \ R-'`-Z' / \ / \/ /
\ / /\ / `---X--' `---Y--'

Pour cet exemple, supposons que I a créé file.txt qui a été modifié par A, B, et X de différentes manières. Les commits à parent unique C, Z, et Y ne changent pas file.txt. Le commit de fusion M a été créé en résolvant le conflit de fusion pour inclure les deux changements de A et B et n'est donc pas TREESAME avec l'un ou l'autre. Le commit de fusion R, cependant, a été créé en ignorant le contenu de file.txt à M et en prenant seulement le contenu de file.txt à X. Par conséquent, R est TREESAME avec X mais pas M. Enfin, la résolution de fusion naturelle pour créer N est de prendre le contenu de file.txt à R, donc N est TREESAME avec R mais pas C. Les commits de fusion O et P sont TREESAME avec leurs premiers parents, mais pas avec leurs seconds parents, Z et Y respectiv

ement.

Lors de l'utilisation du mode par défaut, N et R ont tous deux un parent TREESAME, donc ces arêtes sont parcourues et les autres sont ignorées. Le graphe d'historique résultant est

: 
        I-
-
-X

Lors de l'utilisation de --full-history, Git parcourt chaque arête. Cela découvrira les commits A et B et la fusion M, mais révélera aussi les commits de fusion O et P. Avec réécriture des parents, le graphe résultant est

: 
          .-A---M--------N---O---P
         /     / \  \  \/   /   /
I B \ R-'`--' / \ / \/ /
\ / /\ / `---X--' `------'

Ici, les commits de fusion O et P apportent un bruit supplémentaire, car ils n'ont en fait pas contribué à un changement de file.txt. Ils ont seulement fusionné un sujet basé sur une version plus ancienne de file.txt. C'est un problème courant dans les dépôts utilisant un flux de travail où de nombreux contributeurs travaillent en parallèle et fusionnent leurs branches de sujet le long d'un seul tronc : de nombreuses fusions sans rapport apparaissent dans les résultats de --full-history

.

Lors de l'utilisation de l'option --simplify-merges, les commits O et P disparaissent des résultats. C'est parce que les seconds parents réécrits de O et P sont accessibles à partir de leurs premiers parents. Ces arêtes sont supprimées et les commits ressemblent alors à des commits à parent unique qui sont TREESAME avec leur parent. Cela arrive aussi au commit N, résultant en une vue d'historique comme suit

: 
          .-A---M--.
         /     /    \
I B R \ / /
\ / / `---X--'

Dans cette vue, nous voyons tous les changements importants à parent unique de A, B, et X. Nous voyons aussi la fusion soigneusement résolue M et la fusion pas si soigneusement résolue R. C'est généralement suffisamment d'informations pour déterminer pourquoi les commits A et B « ont disparu » de l'historique dans la vue par défaut. Cependant, il y a quelques problèmes avec cette

approche.

Le premier problème est la performance. Contrairement à toute option précédente, l'option --simplify-merges nécessite de parcourir tout l'historique de commits avant de renvoyer un seul résultat. Cela peut rendre l'option difficile à utiliser pour les très grands

dépôts.

Le deuxième problème est celui de l'audit. Lorsque de nombreux contributeurs travaillent sur le même dépôt, il est important de savoir quels commits de fusion ont introduit un changement dans une branche importante. Le commit de fusion problématique R ci-dessus n'est probablement pas le commit de fusion qui a été utilisé pour fusionner dans une branche importante. À la place, la fusion N a été utilisée pour fusionner R et X dans la branche importante. Ce commit peut contenir des informations sur pourquoi le changement X a écrasé les changements de A et B dans son message de

commit.

--show-pull

s
En plus des commits montrés dans l'historique par défaut, affiche chaque commit de fusion qui n'est pas TREESAME avec son premier parent mais qui est TREESAME avec un parent ultérieur.

Lorsqu'un commit de fusion est inclus par --show-pulls, la fusion est traitée comme si elle avait « tiré » le changement d'une autre branche. Lors de l'utilisation de --show-pulls sur cet exemple (et aucune autre option), le graphe résultant est

: 
        I---
X---R
---N

Ici, les commits de fusion R et N sont inclus parce qu'ils ont tiré les commits X et R dans la branche de base, respectivement. Ces fusions sont la raison pour laquelle les commits A et B n'apparaissent pas dans l'historique par

défaut.

Lorsque --show-pulls est associé à --simplify-merges, le graphe inclut toutes les informations nécessaires

: 
          .-A---M--.   N
         /     /    \ /
I B R \ / /
\ / / `---X--'

N git-log(1)

Notez que comme M est accessible depuis R, l'arête de N à M a été simplifiée. Cependant, N apparaît toujours dans l'historique comme un commit important car il a « tiré » la modification R dans la branche principale.

L'option --simplify-by-decoration vous permet de voir uniquement la vue d'ensemble de la topologie de l'historique, en omettant les commits qui ne sont pas référencés par des tags. Les commits sont marqués comme !TREESAME (en d'autres termes, conservés après les règles de simplification de l'historique décrites ci-dessus) si (1) ils sont référencés par des tags, ou (2) ils modifient le contenu des chemins donnés sur la ligne de commande. Tous les autres commits sont marqués comme TREESAME (susceptibles d'être simplifiés).

Ordre des commits

Par défaut, les commits sont affichés dans l'ordre chronologique inverse.

--date-order

Affiche aucun parent avant que tous ses enfants ne soient affichés, mais sinon, affiche les commits dans l'ordre des horodatages des commits.

--author-date-order

Affiche aucun parent avant que tous ses enfants ne soient affichés, mais sinon, affiche les commits dans l'ordre des horodatages de l'auteur.

--topo-order

N'affiche aucun parent avant que tous ses enfants ne soient affichés, et évite d'afficher des commits de plusieurs lignes d'historique entremêlées.

Par exemple, dans un historique de commits comme celui-ci : 

    ---1----2----4----7
        \              \
         3----5----6----8---

où les chiffres indiquent l'ordre des horodatages des commits, git rev-list et ses semblables avec --date-order affichent les commits dans l'ordre des horodatages : 8 7 6 5 4 3 2 1.

Avec --topo-order , ils afficheraient 8 6 5 3 7 4 2 1 (ou 8 7 4 2 6 5 3 1) ; certains commits plus anciens sont affichés avant des commits plus récents afin d'éviter d'entremêler les commits de deux pistes de développement parallèles.

--reverse

Affiche les commits choisis pour être affichés (voir la section Limitation des commits ci-dessus) dans l'ordre inverse. Ne peut pas être combiné avec --walk-reflogs .

Parcours des objets

Ces options sont principalement destinées à l'empaquetage des dépôts Git.

--no-walk[=(sorted|unsorted)]

Affiche uniquement les commits donnés, mais ne parcourt pas leurs ancêtres. Cela n'a aucun effet si une plage est spécifiée. Si l'argument unsorted est donné, les commits sont affichés dans l'ordre où ils ont été donnés sur la ligne de commande. Sinon (si sorted ou aucun argument n'a été donné), les commits sont affichés dans l'ordre chronologique inverse par date de commit. Ne peut pas être combiné avec --graph .

--do-walk

Remplace un --no-walk précédent.

Formatage des commits

--pretty[=<format>], --format=<format>

Affiche joliment le contenu des journaux de commits dans un format donné, où <format> peut être l'un de oneline , short , medium , full , fuller , reference , email , raw , format:<string> et tformat:<string> . Lorsque <format> n'est pas l'un des éléments ci-dessus et contient %<placeholder> , il agit comme si --pretty=tformat:<format> avait été donné.

Note
vous pouvez spécifier le format de présentation par défaut dans la configuration du dépôt (voir git-config(1) ).

--abbrev-commit

Au lieu d'afficher le nom complet de l'objet commit hexadécimal en 40 octets, affiche un préfixe qui identifie l'objet de manière unique. L'option --abbrev=<n> (qui modifie également la sortie diff, si elle est affichée) peut être utilisée pour spécifier la longueur minimale du préfixe.

Cela devrait rendre --pretty=oneline beaucoup plus lisible pour les personnes utilisant des terminaux 80 colonnes.

--no-abbrev-commit

Affiche le nom complet de l'objet commit hexadécimal en 40 octets. Cela annule --abbrev-commit , qu'il soit explicite ou implicite par d'autres options telles que --oneline . Il remplace également la variable log.abbrevCommit .

--oneline

C'est un raccourci pour --pretty=oneline --abbrev-commit utilisés ensemble.

--encoding=<encoding>

Les objets commit enregistrent le codage des caractères utilisé pour le message de log dans leur en-tête d'encodage ; cette option peut être utilisée pour indiquer à la commande de recoder le message de log du commit dans le codage préféré de l'utilisateur. Pour les commandes non-plumbing, la valeur par défaut est UTF-8. Notez que si un objet prétend être encodé en X et que nous sortons en X , nous afficherons l'objet tel quel ; cela signifie que les séquences invalides dans le commit d'origine peuvent être copiées dans la sortie. De même, si iconv(3) ne parvient pas à convertir le commit, nous afficherons silencieusement l'objet d'origine tel quel.

--expand-tabs=<n>, --expand-tabs, --no-expand-tabs

Effectue une expansion de tabulations (remplace chaque tabulation par suffisamment d'espaces pour atteindre la colonne d'affichage suivante qui est un multiple de <n> ) dans le message de log avant de l'afficher dans la sortie. --expand-tabs est un raccourci pour --expand-tabs=8 , et --no-expand-tabs est un raccourci pour --expand-tabs=0 , qui désactive l'expansion des tabulations.

Par défaut, les tabulations sont étendues dans les formats de présentation qui indentent le message de log de 4 espaces (c'est-à-dire medium , qui est la valeur par défaut, full , et fuller ).

--notes[=<ref>]

Affiche les notes (voir git-notes(1) ) qui annotent le commit, lors de l'affichage du message de log du commit. C'est la valeur par défaut pour les commandes git log , git show et git whatchanged lorsqu'il n'y a pas d'option --pretty , --format , ou --oneline donnée sur la ligne de commande.

Avec un argument <ref> optionnel, utilise la référence pour trouver les notes à afficher. La référence peut spécifier le nom complet de la référence si elle commence par refs/notes/ ; si elle commence par notes/ , refs/ et sinon refs/notes/ est préfixé pour former le nom complet de la référence.

Plusieurs options --notes peuvent être combinées pour contrôler quelles notes sont affichées. Exemples : « --notes=foo » affichera uniquement les notes de refs/notes/foo ; « --notes=foo --notes » affichera les notes de « refs/notes/foo » et de la référence de notes par défaut.

--no-notes

N'affiche pas les notes. Cela annule l'option --notes ci-dessus, en réinitialisant la liste des références de notes à partir desquelles les notes sont affichées. Les options sont analysées dans l'ordre où elles sont données sur la ligne de commande, donc par exemple « --notes --notes=foo --no-notes --notes=bar » n'affichera que les notes de refs/notes/bar .

--show-notes-by-default

Affiche les notes par défaut sauf si des options pour afficher des notes spécifiques sont données.

--show-notes[=<ref>], --standard-notes, --no-standard-notes

Ces options sont dépréciées. Utilisez plutôt les options --notes/--no-notes ci-dessus.

--show-signature

Vérifie la validité d'un objet commit signé en passant la signature à gpg --verify et affiche le résultat.

--relative-date

Synonyme de --date=relative .

--date=<format>

N'a d'effet que pour les dates affichées dans un format lisible par l'homme, par exemple lors de l'utilisation de --pretty . La variable de configuration log.date définit une valeur par défaut pour l'option --date de la commande log . Par défaut, les dates sont affichées dans le fuseau horaire d'origine (celui du committer ou de l'auteur). Si -local est ajouté au format (par exemple, iso-local ), le fuseau horaire local de l'utilisateur est utilisé à la place.

--date=relative affiche les dates relatives à l'heure actuelle, par exemple « il y a 2 heures ». L'option -local n'a aucun effet pour --date=relative .

--date=local est un alias pour --date=default-local .

--date=iso (ou --date=iso8601 ) affiche les horodatages dans un format similaire à ISO 8601. Les différences par rapport au format strict ISO 8601 sont :

•un espace au lieu du délimiteur T date/heure
•un espace entre l'heure et le fuseau horaire
•pas de deux-points entre les heures et les minutes du fuseau horaire

--date=iso-strict (ou --date=iso8601-strict ) affiche les horodatages dans un format ISO 8601 strict.

--date=rfc (ou --date=rfc2822 ) affiche les horodatages dans le format RFC 2822, souvent trouvé dans les messages électroniques.

--date=short affiche seulement la date, mais pas l'heure, au format AAAA-MM-JJ .

Cependant, si l'option --combined-all-paths est fournie, au lieu d'un fichier de provenance/fichier de destination sur deux lignes, vous obtenez un en-tête fichier de provenance/fichier de destination sur N+1 lignes, où N est le nombre de parents dans le commit de fusion :

--- a/file
--- a/file
--- a/file
+++ b/file

Ce format étendu peut être utile si la détection de renommage ou de copie est active, pour vous permettre de voir le nom d'origine du fichier dans différents parents.

4.Le format de l'en-tête de chunk est modifié pour éviter que les gens ne l'utilisent accidentellement avec patch -p1. Le format de diff combiné a été créé pour la révision des changements de commit de fusion, et n'était pas destiné à être appliqué. La modification est similaire à la modification de l'en-tête index étendu : 
@@@ <plage-fichier-provenance> <plage-fichier-provenance> <plage-fichier-destination> @@@

Il y a (nombre de parents + 1) caractères @ dans l'en-tête de chunk pour le format de diff combiné.

Contrairement au format de diff unifié traditionnel, qui montre deux fichiers A et B avec une seule colonne ayant un préfixe - (moins — apparaît dans A mais supprimé dans B), + (plus — manquant dans A mais ajouté à B), ou " " (espace — inchangé), ce format compare deux ou plusieurs fichiers file1, file2,... avec un fichier X, et montre comment X diffère de chacun des fileN. Une colonne pour chacun des fileN est ajoutée à la ligne de sortie pour indiquer comment la ligne de X diffère de celle-ci.

Un caractère - dans la colonne N signifie que la ligne apparaît dans fileN mais pas dans le résultat. Un caractère + dans la colonne N signifie que la ligne apparaît dans le résultat, et fileN ne possède pas cette ligne (en d'autres termes, la ligne a été ajoutée, du point de vue de ce parent).

Dans l'exemple de sortie ci-dessus, la signature de la fonction a été modifiée dans les deux fichiers (d'où deux suppressions - des deux fichiers file1 et file2, plus ++ pour signifier qu'une ligne a été ajoutée n'apparaît dans ni file1 ni file2). De plus, huit autres lignes sont identiques à file1 mais n'apparaissent pas dans file2 (d'où le préfixe +).

Lorsqu'il est affiché par git diff-tree -c, il compare les parents d'un commit de fusion avec le résultat de la fusion (c'est-à-dire file1..fileN sont les parents). Lorsqu'il est affiché par git diff-files -c, il compare les deux parents de fusion non résolus avec le fichier de l'arbre de travail (c'est-à-dire file1 est le stade 2, alias "notre version", file2 est le stade 3, alias "leur version").

git log --no-merges

Afficher tout l'historique des commits, mais ignorer les fusions

git log v2.6.12.. include/scsi drivers/scsi

Afficher tous les commits depuis la version v2.6.12 qui ont modifié un fichier dans les sous-répertoires include/scsi ou drivers/scsi

git log --since="2 semaines il y a" -- gitk

Afficher les changements au cours des deux dernières semaines pour le fichier gitk. Le -- est nécessaire pour éviter toute confusion avec la branche nommée gitk

git log --name-status release..test

Afficher les commits qui sont dans la branche "test" mais pas encore dans la branche "release", ainsi que la liste des chemins modifiés par chaque commit.

git log --follow builtin/rev-list.c

Affiche les commits qui ont modifié builtin/rev-list.c, y compris les commits qui se sont produits avant que le fichier ne reçoive son nom actuel.

git log --branches --not --remotes=origin

Affiche tous les commits qui sont dans l'une des branches locales mais pas dans l'une des branches de suivi distant pour origin (ce que vous avez et qu'origin n'a pas).

git log master --not --remotes=*/master

Affiche tous les commits qui sont dans la branche master locale mais pas dans les branches master de dépôt distant.

git log -p -m --first-parent

Affiche l'historique incluant les diffs de changement, mais seulement du point de vue de la "branche principale", en ignorant les commits provenant de branches fusionnées, et en montrant les diffs complets des changements introduits par les fusions. git log -L '/int main/',/^}/:main.c

Montre comment la fonction main() dans le fichier main.c a évolué au fil du temps.

git log -3

Limite le nombre de commits à afficher à 3.

DISCUSSION

Git est, dans une certaine mesure, indépendant du codage de caractères.

•Le contenu des objets blob est une séquence d'octets non interprétée. Il n'y a pas de traduction de codage au niveau du cœur.
•Les noms de chemins sont codés en forme canonique C de normalisation UTF-8. Cela s'applique aux objets tree, au fichier d'index, aux noms de refs, ainsi qu'aux noms de chemins dans les arguments de ligne de commande, les variables d'environnement et les fichiers de configuration (.git/config (voir git-config(1)), gitignore(5), gitattributes(5) et gitmodules(5)).

Notez que Git, au niveau du cœur, traite les noms de chemins comme de simples séquences d'octets non NUL, il n'y a pas de conversions de codage de noms de chemins (sauf sur Mac et Windows). Par conséquent, l'utilisation de noms de chemins non ASCII fonctionnera la plupart du temps, même sur les plateformes et systèmes de fichiers qui utilisent des codages ASCII étendus hérités. Cependant, les dépôts créés sur de tels systèmes ne fonctionneront pas correctement sur les systèmes basés sur UTF-8 (par exemple, Linux, Mac, Windows) et vice versa. De plus, de nombreux outils basés sur Git supposent simplement que les noms de chemins sont en UTF-8 et ne parviendront pas à afficher correctement d'autres codages.
