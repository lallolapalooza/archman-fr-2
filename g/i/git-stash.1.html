NOM

git-stash - Mettre de côté les modifications dans un répertoire de travail sale

SYNOPSIS

git stash list [<options-log>]
git stash show [-u | --include-untracked | --only-untracked] [<options-diff>] [<stash>]
git stash drop [-q | --quiet] [<stash>]
git stash pop [--index] [-q | --quiet] [<stash>]
git stash apply [--index] [-q | --quiet] [<stash>]
git stash branch <nom-branche> [<stash>]
git stash [push [-p | --patch] [-S | --staged] [-k | --[no-]keep-index] [-q | --quiet]
             [-u | --include-untracked] [-a | --all] [(-m | --message) <message>]
             [--pathspec-from-file=<fichier> [--pathspec-file-nul]]
             [--] [<pathspec>...]]
git stash save [-p | --patch] [-S | --staged] [-k | --[no-]keep-index] [-q | --quiet]
           [-u | --include-untracked] [-a | --all] [<message>]
git stash clear
git stash create [<message>]
git stash store [(-m | --message) <message>] [-q | --quiet] <commit>
git stash export (--print | --to-ref <ref>) [<stash>...]
git stash import <commit>

DESCRIPTION

Utilisez git stash lorsque vous voulez enregistrer l'état actuel du répertoire de travail et de l'index, mais que vous voulez revenir à un répertoire de travail propre. La commande sauvegarde vos modifications locales et annule le répertoire de travail pour qu'il corresponde au commit HEAD.

Les modifications mises de côté par cette commande peuvent être listées avec git stash list, inspectées avec git stash show, et restaurées (potentiellement sur un autre commit) avec git stash apply. Appeler git stash sans aucun argument est équivalent à git stash push. Une mise de côté est par défaut répertoriée comme "WIP sur <nom-branche> ...", mais vous pouvez donner un message plus descriptif sur la ligne de commande lorsque vous en créez une.

La dernière mise de côté que vous avez créée est stockée dans refs/stash ; les mises de côté plus anciennes se trouvent dans le reflog de cette référence et peuvent être nommées en utilisant la syntaxe habituelle du reflog (par exemple, stash@{0} est la mise de côté créée le plus récemment, stash@{1} est celle d'avant, stash@{2.hours.ago} est également possible). Les mises de côté peuvent aussi être référencées en spécifiant simplement l'indice de la mise de côté (par exemple, l'entier <n> est équivalent à stash@{<n>}).

COMMANDES

push [-p | --patch] [-S | --staged] [-k | --[no-]keep-index] [-u | --include-untracked] [ -a | --all] [-q | --quiet] [(-m|--message) <message>] [--pathspec-from-file=<fichier> [--pathspec-file-nul]] [--] [<pathspec>...]

Sauvegarde vos modifications locales dans une nouvelle entrée de mise de côté et les annule jusqu'à HEAD (dans l'arbre de travail et dans l'index). La partie <message> est facultative et donne la description accompagnant l'état mis de côté.

Pour créer rapidement un instantané, vous pouvez omettre "push". Dans ce mode, les arguments autres que les options ne sont pas autorisés afin d'éviter qu'une sous-commande mal orthographiée ne crée une entrée de mise de côté indésirable. Les deux exceptions sont stash -p qui agit comme un alias pour stash push -p et les éléments de pathspec, qui sont autorisés après un double trait d'union -- pour la désambiguïsation.

save [-p | --patch] [-S | --staged] [-k | --[no-]keep-index] [-u | --include-untracked] [-a | --all] [-q | --quiet] [<message>]

Cette option est dépréciée au profit de git stash push. Elle diffère de "stash push" en ce qu'elle ne peut pas prendre de pathspec. Au lieu de cela, tous les arguments autres que les options sont concaténés pour former le message de mise de côté.

list [<options-log>]

Liste les entrées de mise de côté dont vous disposez actuellement. Chaque entrée de mise de côté est répertoriée avec son nom (par exemple, stash@{0} est l'entrée la plus récente, stash@{1} est celle d'avant, etc.), le nom de la branche qui était courante lorsque l'entrée a été créée, et une courte description du commit sur lequel l'entrée était basée. 
stash@{0}: WIP on submit: 6ebd0e2... Update git-stash documentation
stash@{1}: On master: 9cc0589... Add git-stash

La commande prend des options applicables à la commande git log pour contrôler ce qui est affiché et comment. Voir git-log(1).

show [-u | --include-untracked | --only-untracked] [<options-diff>] [<stash>]

Affiche les modifications enregistrées dans l'entrée de mise de côté sous forme de diff entre le contenu mis de côté et le commit d'origine lors de la création de l'entrée de mise de côté. Par défaut, la commande affiche le diffstat, mais elle acceptera tout format connu de git diff (par exemple, git stash show -p stash@{1} pour visualiser la deuxième entrée la plus récente sous forme de patch). Si aucune <option-diff> n'est fournie, le comportement par défaut sera donné par les variables de configuration stash.showStat et stash.showPatch. Vous pouvez également utiliser stash.showIncludeUntracked pour définir si --include-untracked est activé par défaut.

pop [--index] [-q | --quiet] [<stash>]

Supprime un seul état mis de côté de la liste des mises de côté et l'applique par-dessus l'état actuel de l'arbre de travail, c'est-à-dire effectue l'opération inverse de git stash push. Le répertoire de travail doit correspondre à l'index.

L'application de l'état peut échouer avec des conflits ; dans ce cas, il n'est pas supprimé de la liste des mises de côté. Vous devez résoudre les conflits manuellement et appeler git stash drop manuellement ensuite.

apply [--index] [-q | --quiet] [<stash>]

Comme pop, mais ne supprime pas l'état de la liste des mises de côté. Contrairement à pop, <stash> peut être n'importe quel commit qui ressemble à un commit créé par stash push ou stash create.

branch <nom-branche> [<stash>]

Crée et extrait une nouvelle branche nommée <nom-branche> à partir du commit sur lequel le <stash> a été créé à l'origine, applique les modifications enregistrées dans le <stash> au nouvel arbre de travail et index. Si cela réussit, et si <stash> est une référence de la forme stash@{<révision>}, elle supprime ensuite le <stash>.

Ceci est utile si la branche sur laquelle vous avez exécuté git stash push a suffisamment changé pour que git stash apply échoue en raison de conflits. Étant donné que l'entrée de mise de côté est appliquée par-dessus le commit qui était HEAD au moment où git stash a été exécuté, elle restaure l'état initial mis de côté sans conflits.

clear

Supprime toutes les entrées de mise de côté. Notez que ces entrées seront alors sujettes au nettoyage et pourraient être impossibles à récupérer (voir EXEMPLES ci-dessous pour une stratégie possible).

drop [-q | --quiet] [<stash>]

Supprime une seule entrée de mise de côté de la liste des entrées de mise de côté.

create

Crée une entrée de mise de côté (qui est un objet commit régulier) et retourne son nom d'objet, sans la stocker nulle part dans l'espace de noms des refs. Ceci est destiné à être utile pour les scripts. Ce n'est probablement pas la commande que vous voulez utiliser ; voir "push" ci-dessus.

store

Stocke une mise de côté donnée créée via git stash create (qui est un merge commit orphelin) dans la référence de mise de côté, mettant à jour le reflog de mise de côté. Ceci est destiné à être utile pour les scripts. Ce n'est probablement pas la commande que vous voulez utiliser ; voir "push" ci-dessus.

export ( --print | --to-ref <ref> ) [<stash>...]

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

Exporte les stash spécifiés, ou tous s'ils ne sont pas spécifiés, vers une chaîne de commits qui peut être transférée à l'aide des mécanismes normaux de fetch et push, puis importée à l'aide de la sous-commande
import.

import <commit

>
Importe les stash spécifiés depuis le commit spécifié, qui doit avoir été créé par export, et les ajoute à la liste des stash. Pour remplacer les stash existants, utilisez clear d
'abord.

DISCUSSIO

N

Une entrée de stash est représentée comme un commit dont l'arbre enregistre l'état du répertoire de travail, et dont le premier parent est le commit à HEAD lorsque l'entrée a été créée. L'arbre du deuxième parent enregistre l'état de l'index lorsque l'entrée est faite, et il est fait enfant du commit HEAD. Le graphe d'ascendance ressemble à ceci

: 
       .----W
/ / -
----H----I

où H est le commit HEAD, I est un commit qui enregistre l'état de l'index, et W est un commit qui enregistre

l'état de l'ar
bre de travail.

EXEMPLE

S

Tirer dans un arbre

sale
Quand vous êtes au milieu de quelque chose, vous apprenez qu'il y a des changements en amont qui sont possiblement pertinents pour ce que vous faites. Quand vos changements locaux n'entrent pas en conflit avec les changements en amont, un simple git pull vous permettra d'avancer.

Cependant, il y a des cas où vos changements locaux entrent en conflit avec les changements en amont, et git pull refuse d'écraser vos changements. Dans un tel cas, vous pouvez mettre vos changements en stash, effectuer un pull, puis restaurer le stash, comme ceci

: 
$ git pull
 ...
file foo
bar not up to date, cann
ot merge. $ git stash $
git pull $ git stash pop

Flux de travail

interrompu
Quand vous êtes au milieu de quelque chose, votre patron entre et exige que vous répariez quelque chose immédiatement. Traditionnellement, vous feriez un commit sur une branche temporaire pour mettre vos changements de côté, et retourneriez à votre branche originale pour faire le correctif d'urgence, comme ceci : 
# ... hack hack hack ...
$ git switch -c my_wip
$ git commit -a -m "WIP"
$ git switch master
$ edit emergency fix
$ git commit -a -m "Fix in a hurry"
$ git switch my_wip
$ git reset --soft HEAD^
# ... continue hacking .
.
.

Vous pouvez utiliser git stash pour simplifier ce qui précède, comme ceci

: 
# ... hack hack hack ...
$ git stash
$ edit emergency fix
$ git commit -a -m "Fix in a hurry"
$ git stash pop
# ... continue hacking
.
.
.

Tester des commits

partiels
Vous pouvez utiliser git stash push --keep-index quand vous voulez faire deux commits ou plus à partir des modifications dans l'arbre de travail, et que vous voulez tester chaque modification avant de commiter : 
# ... hack hack hack ...
$ git add --patch foo            # add just first part to the index
$ git stash push --ke
ep-index # save all other changes to the stash $ edit/build/test first part $ git commit -m 'First part' #
commit fully tested change $ git stash pop # prepare to work on all other changes # ... repeat abo
ve five steps until one commit remains ... $ edit/build/test remaining parts $ git commit foo -m 'Remaining parts'

Sauvegarder des changements non liés pour une utilisation

future
Quand vous êtes au milieu de changements massifs et que vous trouvez un problème sans rapport que vous ne voulez pas oublier de corriger, vous pouvez faire le(s) changement(s), les mettre en index, et utiliser git stash push --staged pour les mettre en stash pour une utilisation future. Cela est similaire à commiter les changements indexés, sauf que le commit se retrouve dans le stash et non sur la branche courante. 
# ... hack hack hack ...
$ git add --patch foo           # add unrelated changes to the index
$ git
stash push --staged # save these changes to the stash # ... hack hack hack, finish current cha
nges ... $ git commit -m 'Massive' # commit fully tested changes $ git switch fixup-branch
# switch to another branch $ git stash pop # to finish work on the saved changes

Récupérer des entrées de stash qui ont été effacées/déposées par

erreur
Si vous déposez ou effacez par erreur des entrées de stash, elles ne peuvent pas être récupérées par les mécanismes de sécurité normaux. Cependant, vous pouvez essayer l'incantation suivante pour obtenir une liste des entrées de stash qui sont toujours dans votre dépôt, mais qui ne sont plus accessibles :
