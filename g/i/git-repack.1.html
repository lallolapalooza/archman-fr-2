DESCRIPTIO

N

Cette commande est utilisée pour combiner tous les objets qui ne se trouvent actuellement pas dans un « pack » dans un pack. Elle peut aussi servir à réorganiser des packs existants en un seul pack plus

efficace.

Un pack est une collection d'objets, individuellement compressés, avec compression delta appliquée, stockés dans un seul fichier, avec un fichier d'index

associé.

Les packs sont utilisés pour réduire la charg

e sur les systèmes de miroir, les moteur
s de sauvegarde, le stockage sur disque, etc.

OPTION

S

-

a
Au lieu de compresser progressivement les objets non compressés, tout compresser dans un seul pack. Particulièrement utile lors de la compression d'un dépôt utilisé pour un développement privé. Utiliser avec -d. Cela nettoiera les objets que git prune laisse derrière lui, mais que git fsck --full --dangling montre comme orphelins.

Notez que les utilisateurs récupérant via des protocoles stupides devront récupérer le nouveau pack entier pour obtenir n'importe quel objet qu'il contient, peu importe combien d'autres objets de ce pack ils ont déjà

localement.

Les fichiers de pack promisor sont recompressés séparément : s'il existe des fichiers de pack

ayant un fichier « .promisor » associé, ces fichiers de pack seront recompressés dans un autre
pack séparé, et un fichier « .promisor » vide correspondant au nouveau pack séparé sera écrit.

-

A
Identique à -a, sauf si -d est utilisé. Dans ce cas, tout objet inatteignable dans un pack précédent devient un objet lâche, non compressé, au lieu de rester dans l'ancien pack. Les objets inatteignables ne sont jamais intentionnellement ajoutés à un pack, même lors de la recompression. Cette option empêche les objets inatteignables d'être immédiatement supprimés en restant dans l'ancien pack puis en étant supprimés. À la place, les objets lâches inatteignables seront élagués selon les règles normales d'expiration lors de la prochaine invocation de git gc. Voir git-gc(
1).

-

d
Après la compression, si les packs nouvellement créés rendent certains packs existants redondants, supprimer les packs redondants. Exécuter aussi git prune-packed pour supprimer les fichiers d'objets lâches
redondants.

--cruf

t
Identique à -a, sauf si -d est utilisé. Dans ce cas, tout objet inatteignable est compressé dans un pack cruft séparé. Les objets inatteignables peuvent être élagués en utilisant les règles normales d'expiration lors de la prochaine invocation de git gc (voir git-gc(1)). Incompatible avec -k
.

--cruft-expiration=<approxidate

>
Faire expirer immédiatement les objets inatteignables plus anciens que <approxidate> au lieu d'attendre la prochaine invocation de git gc. Utile uniquement avec --cruft -d
.

--max-cruft-size=<n

>
Remplace --max-pack-size pour les packs cruft. Hérite par défaut de la valeur de --max-pack-size (le cas échéant). Voir la documentation de --max-pack-size pour plus de
détails.

--combine-cruft-below-size=<n

>
Lors de la génération de packs cruft sans élagage, ne recompresser que les packs cruft existants dont la taille est strictement inférieure à <n>, où <n> représente un nombre d'octets, qui peut éventuellement être suffixé par « k », « m » ou « g ». Les packs cruft dont la taille est supérieure ou égale à <n> sont laissés tels quels et ne sont pas recompressés. Utile lorsque vous souhaitez éviter de recompresser de gros packs cruft dans des dépôts ayant beaucoup et/ou de gros objets
inatteignables.

--expire-to=<dir

>
Écrire un pack cruft contenant les objets élagués (le cas échéant) dans le répertoire <dir>. Cette option est utile pour conserver une copie de tout objet élagué dans un répertoire séparé comme sauvegarde. Utile uniquement avec --cruft -d
.

-

l
Passer l'option --local à git pack-objects. Voir git-pack-obje
cts(1).

-

f
Passer l'option --no-reuse-delta à git-pack-objects, voir git-pack-obje
cts(1).

-

F
Passer l'option --no-reuse-object à git-pack-objects, voir git-pack-obje
cts(1).

-q,

--quiet
Ne montrer aucune progression sur le flux d'erreur standard et passer l'option -q à git pack-objects. Voir git-pack-obje
cts(1).

-

n
Ne pas mettre à jour les informations du serveur avec git update-server-info. Cette option saute la mise à jour des fichiers de catalogue locaux nécessaires pour publier ce dépôt (ou une copie directe de celui-ci) via HTTP ou FTP. Voir git-update-server
-info(1).

--window=<n>,

--depth=<n>
Ces deux options affectent la manière dont les objets contenus dans le pack sont stockés en utilisant la compression delta. Les objets sont d'abord triés internement par type, taille et éventuellement noms, puis comparés aux autres objets dans --window pour voir si l'utilisation de la compression delta économise de l'espace. --depth limite la profondeur delta maximale ; la rendre trop profonde affecte les performances côté décompresseur, car les données delta doivent être appliquées autant de fois pour atteindre l'objet nécessaire.

La valeur par défaut de --window es

t 10 et celle de --depth est 50. L
a profondeur maximale est 4095.

--threads=<n

>
Cette option est transmise à git pack-objects
.

--window-memory=<n

>
Cette option fournit une limite supplémentaire en plus de --window ; la taille de la fenêtre sera dynamiquement réduite afin de ne pas occuper plus de <n> octets en mémoire. C'est utile dans les dépôts avec un mélange d'objets grands et petits pour ne pas manquer de mémoire avec une grande fenêtre, mais pouvoir toujours profiter de la grande fenêtre pour les petits objets. La taille peut être suffixée par « k », « m » ou « g ». --window-memory=0 rend l'utilisation de la mémoire illimitée. La valeur par défaut est prise de la variable de configuration pack.windowMemory. Notez que l'utilisation réelle de la mémoire sera la limite multipliée par le nombre de fils d'exécution utilisés par git-pack-obje
cts(1).

--max-pack-size=<n

>
Taille maximale de chaque fichier de pack de sortie. La taille peut être suffixée par « k », « m » ou « g ». La taille minimale autorisée est limitée à 1 Mio. Si spécifié, plusieurs fichiers de pack peuvent être créés, ce qui empêche aussi la création d'un index de bitmap. La valeur par défaut est illimitée, sauf si la variable de configuration pack.packSizeLimit est définie. Notez que cette option peut entraîner un dépôt plus volumineux et plus lent ; voir la discussion dans pack.packSize
Limit.

--filter=<filter-spec

>
Retirer du fichier de pack résultant les objets correspondant à la spécification de filtre et les placer dans un fichier de pack séparé. Notez que les objets utilisés dans le répertoire de travail ne sont pas filtrés. Ainsi, pour que la division fonctionne pleinement, il est préférable de l'effectuer dans un dépôt nu et d'utiliser les options -a et -d avec cette option. De plus, --no-write-bitmap-index (ou l'option de configuration repack.writebitmaps définie à false) devrait être utilisé, sinon l'écriture de l'index de bitmap échouera, car elle suppose un fichier de pack unique contenant tous les objets. Voir git-rev-list(1) pour les formes valides de <filter-s
pec>.

--filter-to=<dir

>
Écrire le pack contenant les objets filtrés dans le répertoire <dir>. Utile uniquement avec --filter. Cela peut être utilisé pour placer le pack dans un répertoire d'objets séparé accessible via le mécanisme d'alternates de Git. AVERTISSEMENT : Si le fichier de pack contenant les objets filtrés n'est pas accessible, le dépôt peut devenir corrompu car il pourrait être impossible d'accéder aux objets dans ce fichier de pack. Voir les sections objects et objects/info/alternates de gitrepository-la
yout(5).

-b, --write-bitmap-inde

x
Écrire un index de bitmap d'accessibilité dans le cadre de la recompression. Cela n'a de sens que lorsqu'il est utilisé avec -a, -A ou -m, car les bitmaps doivent pouvoir référencer tous les objets accessibles. Cette option remplace le paramètre de repack.writeBitmaps. Cette optionn'a aucun effet si plusieurs packfiles sont créés, sauf si un MIDX est écrit (auquel cas un bitmap multi-pack est créé)
.

--pack-kept-object

s
Inclure les objets des fichiers .keep lors du repack. Notez que nous ne supprimons toujours pas les packs .keep après la fin de pack-objects. Cela signifie que nous pouvons dupliquer des objets, mais cela rend l'option sûre à utiliser lorsqu'il y a des pushes ou fetchs concurrents. Cette option n'est généralement utile que si vous écrivez des bitmaps avec -b ou repack.writeBitmaps, car elle garantit que le packfile avec bitmap contient les objets
nécessaires.

--keep-pack=<pack-name

>
Exclure le pack donné du repack. C'est l'équivalent d'avoir un fichier .keep sur le pack. <pack-name> est le nom du fichier pack sans le répertoire parent (par ex. pack-123.pack). L'option peut être spécifiée plusieurs fois pour conserver plusieurs
packs.

--unpack-unreachable=<when

>
Lors du décompactage des objets inaccessibles, ne pas prendre la peine de décompacter les objets plus anciens que <when>. Cela peut être utilisé pour optimiser l'écriture des objets qui seraient immédiatement élagués par un suivant git prune
.

-k, --keep-unreachabl

e
Lorsqu'il est utilisé avec -ad, les objets inaccessibles des packs existants seront ajoutés à la fin du packfile au lieu d'être supprimés. De plus, les objets libres inaccessibles seront packés (et leurs équivalents libres supprimés)
.

-i,

--delta-islands
Passer l'option --delta-islands à git-pack-objects, voir git-pack-obje
cts(1).

-g<factor>, --geometric=<factor

>
Organiser la structure de pack résultante de sorte que chaque pack successif contienne au moins <factor> fois le nombre d'objets que le pack suivant le plus grand.

git repack garantit cela en déterminant une « coupe » de packfiles qui doivent être repackés en un seul afin de garantir une progression géométrique. Il choisit le plus petit ensemble de packfiles tel que le plus grand nombre possible de packfiles les plus grands (selon le nombre d'objets contenus dans ce pack) puissent rester

intacts.

Contrairement aux autres modes de repack, l'ensemble des objets à packer est déterminé de manière unique par l'ensemble des packs qui sont « regroupés » ; en d'autres termes, les packs déterminés comme devant être combinés afin de restaurer une progression

géométrique.

Les objets libres sont implicitement inclus dans ce « regroupement », sans tenir compte de leur accessibilité. Cela pourrait changer à

l'avenir.

Lors de l'écriture d'un bitmap multi-pack, git repack sélectionne le plus grand pack résultant comme pack préféré pour la sélection d'objets par le MIDX (voir git-multi-pa

ck-inde
x(1)).

-m,

--write-midx
Écrire un index multi-pack (voir git-multi-pack-index(1)) contenant les packs non
redondants.

--name-hash-version=<n

>
Fournir cet argument au processus git pack-objects sous-jacent. Voir git-pack-objects(1) pour tous les
détails.

--path-wal

k
Passer l'option --path-walk au processus git pack-objects sous-jacent. Voir git-pack-objects(1) po
ur tous l
es détails.

CONFIGURATIO

N

Diverses variables de configuration affectent le packing, voir git-config(1) (rechercher « pack » et « delta »)

.

Par défaut, la commande passe l'option --delta-base-offset à git pack-objects ; cela donne généralement des packs légèrement plus petits, mais les packs générés sont incompatibles avec les versions de Git antérieures à la version 1.4.4. Si vous devez partager votre dépôt avec de telles anciennes versions de Git, soit directement, soit via le protocole http « dumb », vous devez définir la variable de configuration repack.UseDeltaBaseOffset à « false ». L'accès repack. depuis les anciennes versions de Git via le protocole natif n'est pas affecté par cette option car la conversion est effectuée à la volée au besoin dans ce

cas.

La compression delta n'est pas utilisée sur les objets plus grands que la variable de configuration core.bigFileThreshold et sur les fichiers dont l'attribut delta est dé

fini à
false.
