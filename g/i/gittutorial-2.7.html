NOM

gittutorial-2 - Introduction au tutoriel de Git : partie deux

SYNOPSIS

git *

DESCRIPTION

Vous devriez parcourir gittutorial(7) avant de lire ce tutoriel.

Le but de ce tutoriel est d'introduire deux éléments fondamentaux de l'architecture de Git — la base de données d'objets et le fichier d'index — et de fournir au lecteur tout ce qui est nécessaire pour comprendre le reste de la documentation de Git.

LA BASE DE DONNÉES D'OBJETS GIT

Commençons un nouveau projet et créons un petit historique :

$ mkdir test-project
$ cd test-project
$ git init
Initialized empty Git repository in .git/
$ echo 'hello world' > file.txt
$ git add .
$ git commit -a -m "initial commit"
[master (root-commit) 54196cc] initial commit
 1 file changed, 1 insertion(+)
 create mode 100644 file.txt
$ echo 'hello world!' >file.txt
$ git commit -a -m "add emphasis"
[master c4d59f3] add emphasis
 1 file changed, 1 insertion(+), 1 deletion(-)

Que sont les 7 chiffres hexadécimaux que Git a renvoyés pour le commit ?

Nous avons vu dans la première partie du tutoriel que les commits ont des noms comme celui-ci. Il s'avère que chaque objet dans l'historique Git est stocké sous un nom hexadécimal à 40 chiffres. Ce nom est le hachage SHA-1 du contenu de l'objet ; entre autres, cela garantit que Git ne stockera jamais les mêmes données deux fois (puisque des données identiques reçoivent un nom SHA-1 identique), et que le contenu d'un objet Git ne changera jamais (car cela changerait également le nom de l'objet). Les chaînes hexadécimales de 7 caractères ici sont simplement l'abréviation de telles chaînes de 40 caractères. Les abréviations peuvent être utilisées partout où les chaînes de 40 caractères peuvent l'être, pourvu qu'elles soient non ambiguës.

On s'attend à ce que le contenu de l'objet commit que vous avez créé en suivant l'exemple ci-dessus génère un hachage SHA-1 différent de celui montré ci-dessus, car l'objet commit enregistre le moment où il a été créé et le nom de la personne effectuant le commit.

Nous pouvons interroger Git sur cet objet particulier avec la commande cat-file . Ne copiez pas les 40 chiffres hexadécimaux de cet exemple, mais utilisez ceux de votre propre version. Notez que vous pouvez le raccourcir à seulement quelques caractères pour éviter de taper les 40 chiffres hexadécimaux :

$ git cat-file -t 54196cc2
commit
$ git cat-file commit 54196cc2
tree 92b8b694ffb1675e5975148e1121810081dbdffe
author J. Bruce Fields <bfields@puzzle.fieldses.org> 1143414668 -0500
committer J. Bruce Fields <bfields@puzzle.fieldses.org> 1143414668 -0500
initial commit

Un arbre (tree) peut référencer un ou plusieurs objets "blob", chacun correspondant à un fichier. De plus, un arbre peut également référencer d'autres objets arbre, créant ainsi une hiérarchie de répertoires. Vous pouvez examiner le contenu de n'importe quel arbre en utilisant ls-tree (rappelez-vous qu'une portion initiale suffisamment longue du SHA-1 fonctionnera aussi) :

$ git ls-tree 92b8b694
100644 blob 3b18e512dba79e4c8300dd08aeb37f8e728b8dad    file.txt

Nous voyons ainsi que cet arbre contient un fichier. Le hachage SHA-1 est une référence vers les données de ce fichier :

$ git cat-file -t 3b18e512
blob

Un "blob" est simplement des données de fichier, que nous pouvons également examiner avec cat-file :

$ git cat-file blob 3b18e512
hello world

Notez qu'il s'agit des anciennes données du fichier ; l'objet que Git a nommé dans sa réponse à l'arbre initial était donc un arbre avec un instantané de l'état du répertoire qui a été enregistré par le premier commit.

Tous ces objets sont stockés sous leurs noms SHA-1 à l'intérieur du répertoire Git :

$ find .git/objects/
.git/objects/
.git/objects/pack
.git/objects/info
.git/objects/3b
.git/objects/3b/18e512dba79e4c8300dd08aeb37f8e728b8dad
.git/objects/92
.git/objects/92/b8b694ffb1675e5975148e1121810081dbdffe
.git/objects/54
.git/objects/54/196cc2703dc165cbd373a65a4dcf22d50ae7f7
.git/objects/a0
.git/objects/a0/423896973644771497bdc03eb99d5281615b51
.git/objects/d0
.git/objects/d0/492b368b66bdabf2ac1fd8c92b39d3db916e59
.git/objects/c4
.git/objects/c4/d59f390b9cfd4318117afde11d601c1085f241

et le contenu de ces fichiers n'est que des données compressées plus un en-tête identifiant leur longueur et leur type. Le type est soit un blob, un arbre, un commit, ou une étiquette (tag).

Le commit le plus simple à trouver est le commit HEAD, que nous pouvons trouver depuis .git/HEAD :

$ cat .git/HEAD
ref: refs/heads/master

Comme vous pouvez le voir, cela nous indique sur quelle branche nous nous trouvons actuellement, et cela en nommant un fichier sous le répertoire .git, qui contient lui-même un nom SHA-1 faisant référence à un objet commit, que nous pouvons examiner avec cat-file :

$ cat .git/refs/heads/master
c4d59f390b9cfd4318117afde11d601c1085f241
$ git cat-file -t c4d59f39
commit
$ git cat-file commit c4d59f39
tree d0492b368b66bdabf2ac1fd8c92b39d3db916e59
parent 54196cc2703dc165cbd373a65a4dcf22d50ae7f7
author J. Bruce Fields <bfields@puzzle.fieldses.org> 1143418702 -0500
committer J. Bruce Fields <bfields@puzzle.fieldses.org> 1143418702 -0500
add emphasis

L'objet "tree" ici fait référence au nouvel état de l'arbre :

$ git ls-tree d0492b36
100644 blob a0423896973644771497bdc03eb99d5281615b51    file.txt
$ git cat-file blob a0423896
hello world!

et l'objet "parent" fait référence au commit précédent :

$ git cat-file commit 54196cc2
tree 92b8b694ffb1675e5975148e1121810081dbdffe
author J. Bruce Fields <bfields@puzzle.fieldses.org> 1143414668 -0500
committer J. Bruce Fields <bfields@puzzle.fieldses.org> 1143414668 -0500
initial commit

L'objet arbre est l'arbre que nous avons examiné en premier, et ce commit est inhabituel en ce qu'il n'a aucun parent.

La plupart des commits n'ont qu'un seul parent, mais il est également courant qu'un commit ait plusieurs parents. Dans ce cas, le commit représente une fusion (merge), avec les références de parent pointant vers les extrémités des branches fusionnées.

En plus des blobs, des arbres et des commits, le seul type d'objet restant est une "étiquette" (tag), que nous ne discuterons pas ici ; voir git-tag(1) pour plus de détails.

Nous savons maintenant comment Git utilise la base de données d'objets pour représenter l'historique d'un projet :

•Les objets "commit" font référence à des objets "tree" représentant l'instantané d'un arbre de répertoires à un moment particulier de l'historique, et font référence à des commits "parent" pour montrer comment ils sont connectés dans l'historique du projet.
•Les objets "tree" représentent l'état d'un répertoire unique, associant les noms de répertoires à des objets "blob" contenant des données de fichier et des objets "tree" contenant des informations sur les sous-répertoires.
•Les objets "blob" contiennent des données de fichier sans aucune autre structure.
•Les références aux objets commit à l'extrémité de chaque branche sont stockées dans des fichiers sous .git/refs/heads/.
•Le nom de la branche actuelle est stocké dans .git/HEAD.

Notez, d'ailleurs, que beaucoup de commandes prennent un arbre comme argument. Mais comme nous pouvons le voir ci-dessus, un arbre peut être référencé de nombreuses façons différentes — par le nom SHA-1 de cet arbre, par le nom d'un commit qui fait référence à l'arbre, par le nom d'une branche dont l'extrémité fait référence à cet arbre, etc. — et la plupart de ces commandes peuvent accepter n'importe lequel de ces noms.

Dans les synopsis de commandes, le mot "tree-ish" est parfois utilisé pour désigner un tel argument.

LE FICHIER D'INDEX

L'outil principal que nous avons utilisé pour créer des commits est git-commit -a, qui crée un commit incluant tous les changements que vous avez apportés à votre arbre de travail. Mais que faire si vous voulez commiter des changements uniquement pour certains fichiers ? Ou uniquement certains changements pour certains fichiers ?

Si nous regardons la façon dont les commits sont créés en interne, nous verrons qu'il existe des façons plus flexibles de créer des commits.

En continuant avec notre test-project, modifions à nouveau file.txt :

$ echo "hello world, again" >>file.txt

mais cette fois-ci, au lieu de faire immédiatement le commit, faisons une étape intermédiaire, et demandons des diffs en cours de route pour garder une trace de ce qui se passe :

NOM


git-tutorial - Un tutoriel interactif pour Git






SYNOPSIS


git tutorial






DESCRIPTION


Ceci est un tutoriel interactif qui couvre les commandes de base de
    Git.


Pour l'exécuter, tapez simplement git tutorial dans votre
    terminal. Les instructions pour l'exécution sont les suivantes :




$ git tutorial
Git has a "tutorial" command that will walk you through the basics.
To run it, just type:
  git tutorial
and follow the instructions.





Ce tutoriel est une bonne introduction pour les débutants. Il vous
    guidera à travers les étapes fondamentales de l'utilisation de Git, telles que
    la création d'un dépôt, la modification de fichiers, l'ajout d'indices, la
    réalisation de commits, et la visualisation de l'historique.


Ce document n'est qu'une brève description du tutoriel. Pour une
    compréhension plus approfondie de Git et de ses commandes, vous devriez suivre
    le tutoriel lui-même et consulter les pages de manuel associées.


Le reste de ce document suppose que vous avez une connaissance
    préalable de ces commandes de base. Il approfondit certains des concepts
    sous-jacents de Git, en particulier la façon dont Git stocke les données.


Git gère les données comme une série d'instantanés. Fondamentalement,
    chaque fois que vous faites un commit, Git enregistre essentiellement un
    instantané de l'état de tous vos fichiers. Pour une efficacité accrue, si un
    fichier n'a pas été modifié depuis le dernier commit, Git ne stocke pas une
    nouvelle copie de ce fichier ; il enregistre plutôt un lien vers le fichier
    précédent qui était identique.


Ces instantanés sont stockés dans une base de données d'objets Git,
    qui est stockée dans le répertoire .git/objects de votre
    projet. Lorsque vous faites un git commit, Git crée un nouveau
    objet (généralement un objet blob pour un fichier, ou un objet
    tree pour un répertoire) pour chaque fichier modifié, et un nouvel
    objet tree qui pointe vers ces blobs et autres arbres, créant une
    structure arborescente qui représente l'instantané complet. L'objet commit
    qui en résulte pointe vers l'objet tree supérieur.


Ces objets sont stockés sous forme compressée à l'aide de zlib. Le nom
    du fichier est le premier SHA-1 des données, et le contenu du fichier est les
    données elles-mêmes, compressées.




LA BASE DE DONNÉES DES OBJETS GIT


Toute donnée que Git stocke (fichiers, répertoires, commits, tags)
    est stockée sous forme d'objet dans la base de données d'objets Git. Chaque
    objet est identifié par un hash SHA-1 de son contenu. Il existe quatre types
    d'objets :



  
blob

  
Représente le contenu d'un fichier.

  
tree

  
Représente le contenu d'un répertoire, sous la forme d'une liste de blobs
      et d'autres arbres, avec les permissions et les noms de fichiers.

  
commit

  
Représente un instantané de votre projet. Il contient un pointeur vers un
      objet tree (qui représente le répertoire racine de cet instantané),
      ainsi que des métadonnées telles que l'auteur, le committer, la date et le
      message de commit.

  
tag

  
Représente un point de référence dans l'historique, généralement utilisé
      pour marquer une version spécifique d'un projet.




Vous pouvez interagir avec ces objets directement à l'aide de la
    commande git cat-file.




$ echo "hello world!" >file.txt
$ git hash-object -w file.txt
49f61195531a68f059c13643892e39036a5a7221
$ git cat-file -t 49f6119
blob
$ git cat-file -p 49f6119
hello world!





Dans cet exemple, nous avons créé un fichier file.txt,
    utilisé git hash-object pour calculer son SHA-1 et le stocker
    dans la base de données d'objets Git (l'option -w le fait),
    puis utilisé git cat-file pour vérifier son type (blob)
    et son contenu.






LE FICHIER INDEX


Le fichier index, également connu sous le nom de zone de staging, sert
    d'intermédiaire entre votre répertoire de travail et la base de données d'objets
    Git. Il contient une liste des fichiers qui seront inclus dans le prochain
    commit.


Lorsque vous modifiez un fichier et que vous exécutez git add,
    vous ne modifiez pas directement le commit précédent. Au lieu de cela, vous
    mettez à jour le fichier index pour qu'il reflète les changements apportés au
    fichier dans votre répertoire de travail.




$ echo "hello world!" >file.txt
$ git add file.txt
$ git diff




Le dernier diff est vide, mais aucun nouveau commit n'a été effectué, et
    la tête ne contient toujours pas la nouvelle ligne :




$ git diff HEAD
diff --git a/file.txt b/file.txt
index a042389..513feba 100644
--- a/file.txt
+++ b/file.txt
@@ -1 +1,2 @@
 hello world!
+hello world, again





Ainsi, git diff compare par rapport à quelque chose d'autre que la
    tête. La chose par rapport à laquelle il compare est en fait le fichier index,
    qui est stocké dans .git/index dans un format binaire, mais dont le
    contenu peut être examiné avec ls-files :




$ git ls-files --stage
100644 513feba2e53ebbd2532419ded848ba19de88ba00 0	file.txt
$ git cat-file -t 513feba2
blob
$ git cat-file blob 513feba2
hello world!
hello world, again





Ainsi, ce que notre git add a fait, c'est stocker un nouveau blob
    et y placer une référence dans le fichier index. Si nous modifions à nouveau
    le fichier, nous verrons que les nouvelles modifications sont reflétées dans
    la sortie de git diff :




$ echo 'again?' >>file.txt
$ git diff
index 513feba..ba3da7b 100644
--- a/file.txt
+++ b/file.txt
@@ -1,2 +1,3 @@
 hello world!
 hello world, again
+again?





Avec les bons arguments, git diff peut également nous montrer la
    différence entre le répertoire de travail et le dernier commit, ou entre
    l'index et le dernier commit :




$ git diff HEAD
diff --git a/file.txt b/file.txt
index a042389..ba3da7b 100644
--- a/file.txt
+++ b/file.txt
@@ -1 +1,3 @@
 hello world!
+hello world, again
+again?
$ git diff --cached
diff --git a/file.txt b/file.txt
index a042389..513feba 100644
--- a/file.txt
+++ b/file.txt
@@ -1 +1,2 @@
 hello world!
+hello world, again





À tout moment, nous pouvons créer un nouveau commit en utilisant
    git commit (sans l'option « -a »), et vérifier que l'état commité
    n'inclut que les changements stockés dans le fichier index, pas le changement
    supplémentaire qui n'est encore que dans notre arbre de travail :




$ git commit -m "repeat"
$ git diff HEAD
diff --git a/file.txt b/file.txt
index 513feba..ba3da7b 100644
--- a/file.txt
+++ b/file.txt
@@ -1,2 +1,3 @@
 hello world!
 hello world, again
+again?





Ainsi, par défaut, git commit utilise l'index pour créer le
    commit, pas l'arbre de travail ; l'option « -a » pour commit lui indique de
    mettre d'abord à jour l'index avec tous les changements dans l'arbre de
    travail.


Enfin, il convient d'examiner l'effet de git add sur le
    fichier index :




$ echo "goodbye, world" >closing.txt
$ git add closing.txt




L'effet de git add a été d'ajouter une entrée au fichier
    index :




$ git ls-files --stage
100644 8b9743b20d4b15be3955fc8d5cd2b09cd2336138 0	closing.txt
100644 513feba2e53ebbd2532419ded848ba19de88ba00 0	file.txt





Et, comme vous pouvez le voir avec cat-file, cette nouvelle entrée
    fait référence au contenu actuel du fichier :




$ git cat-file blob 8b9743b2
goodbye, world





La commande status est un moyen utile d'obtenir un résumé
    rapide de la situation :




$ git status
On branch master
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
	new file:   closing.txt
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   file.txt





Puisque l'état actuel de closing.txt est mis en cache dans le fichier
    index, il est répertorié comme « Changes to be committed ». Puisque
    file.txt a des changements dans le répertoire de travail qui ne sont pas
    reflétés dans l'index, il est marqué « changed but not updated ». À ce stade,
    l'exécution de « git commit » créerait un commit qui ajouterait closing.txt
    (avec son nouveau contenu), mais qui ne modifierait pas file.txt.


Notez également qu'un git diff nu montre les changements
    apportés à file.txt, mais pas l'ajout de closing.txt, car la version de
    closing.txt dans le fichier index est identique à celle du répertoire de
    travail.


En plus d'être la zone de staging pour les nouveaux commits, le fichier
    index est également rempli à partir de la base de données d'objets lors de la
    récupération d'une branche, et est utilisé pour contenir les arbres impliqués
    dans une opération de fusion. Voir gitcore-tutorial(7) et les pages de manuel
    pertinentes pour plus de détails.






ET APRÈS ?


À ce stade, vous devriez connaître tout ce qui est nécessaire pour lire
    les pages de manuel de n'importe quelle commande Git ; un bon endroit pour
    commencer serait les commandes mentionnées dans giteveryday(7). Vous devriez être capable de trouver
    tout jargon inconnu dans gitglossary(7).


Le manuel de l'utilisateur Git fournit une introduction plus complète
    à Git.


gitcvs-migration(7) explique comment importer un dépôt CVS dans
    Git, et montre comment utiliser Git d'une manière similaire à CVS.


Pour des exemples intéressants d'utilisation de Git, voir les howtos.


Pour les développeurs Git, gitcore-tutorial(7) détaille les mécanismes de bas niveau de
    Git impliqués, par exemple, dans la création d'un nouveau commit.
