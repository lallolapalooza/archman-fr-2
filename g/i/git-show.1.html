•raw

Le format raw affiche le commit entier exactement tel qu'il est stocké dans l'objet commit. Notamment, les hashes sont affichés en entier, que --abbrev ou --no-abbrev soient utilisés, et les informations de parents montrent les vrais commits parents, sans tenir compte des grafts ou de la simplification de l'historique. Notez que ce format affecte la manière dont les commits sont affichés, mais pas la manière dont le diff est montré, par exemple avec git log --raw. Pour obtenir des noms d'objets complets dans un format de diff brut, utilisez --no-abbrev.

Note

Some placeholders may depend on other options given to the revision traversal engine. For example, the %g* reflog options will insert an empty string unless we are traversing reflog entries (e.g., by git log -g). The %d and %D placeholders will use the "short" decoration format if --decorate was not already provided on the command line.

The boolean options accept an optional value [=<bool-value>]. The values taken by --type=bool git-config(1), like yes and off, are all accepted. Giving a boolean option without =<value> is equivalent to giving it with =true.

If you add a + (plus sign) after % of a placeholder, a line-feed is inserted immediately before the expansion if and only if the placeholder expands to a non-empty string.

If you add a - (minus sign) after % of a placeholder, all consecutive line-feeds immediately preceding the expansion are deleted if and only if the placeholder expands to an empty string.

If you add a ' ' (space) after % of a placeholder, a space is inserted immediately before the expansion if and only if the placeholder expands to a non-empty string.

•tformat:

The tformat: format works exactly like format:, except that it provides "terminator" semantics instead of "separator" semantics. In other words, each commit has the message terminator character (usually a newline) appended, rather than a separator placed between entries. This means that the final entry of a single-line format will be properly terminated with a new line, just as the "oneline" format does. For example:

$ git log -2 --pretty=format:%h 4da45bef \
  | perl -pe '$_ .= " -- NO NEWLINE\n" unless /\n/'
4da45be
7134973 -- NO NEWLINE
$ git log -2 --pretty=tformat:%h 4da45bef \
  | perl -pe '$_ .= " -- NO NEWLINE\n" unless /\n/'
4da45be
7134973

In addition, any unrecognized string that has a % in it is interpreted as if it has tformat: in front of it. For example, these two are equivalent:

$ git log -2 --pretty=tformat:%h 4da45bef
$ git log -2 --pretty=%h 4da45bef

DISCUSSIO

N

Git est dans une certaine mesure agnostique quant à l'encodage des

caractères.
•Le contenu des objets blob est des séquences d'octets non interprétées. Il n'y a aucune traduction d'encodage au niveau du
noyau.
•Les noms de chemins sont encodés en UTF-8 normalisation forme C. Cela s'applique aux objets arbre, au fichier d'index, aux noms de refs, ainsi qu'aux noms de chemins dans les arguments de ligne de commande, les variables d'environnement et les fichiers de configuration (.git/config (voir git-config(1)), gitignore(5), gitattributes(5) et gitmodules(5)).

Notez qu'au niveau du noyau, Git traite les noms de chemins simplement comme des séquences d'octets non-NUL, il n'y a aucune conversion d'encodage des noms de chemins (sauf sur Mac et Windows). Par conséquent, l'utilisation de noms de c

hemins non-ASCII fonctionnera principalement même sur les plateformes et les systèmes de fichiers qui utilisent des encodages ASCII étendus hérités. Cependant, les dépôts créés sur de tels systèmes ne fonctionneront pas correctement su
r les systèmes basés sur UTF-8 (par ex. Linux, Mac, Windows) et vice versa. De plus, de nombreux outils basés sur Git supposent simplement que les noms de chemins sont en UTF-8 et échoueront à afficher correctement les autres encodages.
•Les messages de journal de commit sont typiquement encodés en UTF-8, mais d'autres encodages ASCII étendus sont également pris en charge. Cela inclut ISO-8859-x, CP125x et bien d'autres, mais pas UTF-16/32, EBCDIC et les encodages multioctets CJK (GBK, Shift-JIS, Big5, EUC-x, CP9xx etc.)
.

Bien que nous encouragions l'encodage des messages de journal de commit en UTF-8, à la fois le noyau et Git Porcelain sont conçus pour ne pas forcer UTF-8 sur les projets. Si tous les participants d'un projet particulier trouvent plus pratique d'utiliser des encodages hérités, Git ne l'interdit pas. Cependant, il y a quelques points à garder à

l'esprit.
1.git commit et git commit-tree émettent un avertissement si le message de journal de commit qui leur est donné ne ressemble pas à une chaîne UTF-8 valide, sauf si vous dites explicitement que votre projet utilise un encodage hérité. La manière de dire cela est d'avoir i18n.commitEncoding dans le fichier .git/config, comme ceci :

d. L'absence de cet en-tête implique que le m
