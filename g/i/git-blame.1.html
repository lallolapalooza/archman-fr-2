DESCRIPTIO

N

Annote chaque ligne du fichier donné avec les informations de la révision ayant modifié pour la dernière fois la ligne. Facultativement, commence l'annotation à partir de la révision

donnée.

Lorsqu'il est spécifié une ou plusieurs fois, -L restreint l'annotation aux lignes

demandées.

L'origine des lignes est automatiquement suivie à travers les renommages de fichiers entiers (actuellement, il n'existe pas d'option pour désactiver le suivi des renommages). Pour suivre les lignes déplacées d'un fichier à un autre, ou pour suivre les lignes copiées et collées depuis un autre fichier, etc., voir les -C et -M

options.

Le rapport ne vous dit rien sur les lignes qui ont été supprimées ou remplacées ; vous devez utiliser un outil tel que git diff ou l'interface « pickaxe » brièvement mentionnée dans le paragraphe

suivant.

En plus de prendre en charge l'annotation de fichiers, Git prend également en charge la recherche dans l'historique de développement pour savoir quand un extrait de code est apparu dans une modification. Cela permet de suivre quand un extrait de code a été ajouté à un fichier, déplacé ou copié entre des fichiers, et finalement supprimé ou remplacé. Cela fonctionne en recherchant une chaîne de texte dans le diff. Un petit exemple de l'interface pickaxe qui recherche blame_usa

ge : 
$ git log --pretty=oneline -S'blame_usage'
5
040f17eba15504bad66b14a645bddd9b015ebb7 blam
e -S <ancestry-file> ea4c7f9bf69e781dd0cd88d
2bccb2bf5cc15c9a7 git-blame: Make the output

-M[<num>

]
Détecte les lignes déplacées ou copiées dans un fichier. Lorsqu'un commit déplace ou copie un bloc de lignes (par exemple, le fichier original a A puis B, et le commit le change en B puis A), l'algorithme de blame traditionnel remarque seulement la moitié du déplacement et attribue généralement les lignes qui ont été déplacées vers le haut (c'est-à-dire B) au parent et attribue la faute aux lignes qui ont été déplacées vers le bas (c'est-à-dire A) au commit enfant. Avec cette option, les deux groupes de lignes sont attribués au parent en exécutant des passes d'inspection supplémentaires.

<num> est facultatif mais c'est la limite inférieure du nombre de caractère

s alphanumériques que Git doit détecter comme déplacés/copiés dans un fich
ier pour associer ces lignes au commit parent. La valeur par défaut est 20.

-C[<num>

]
En plus de -M, détecte les lignes déplacées ou copiées depuis d'autres fichiers modifiés dans le même commit. C'est utile lorsque vous réorganisez votre programme et déplacez du code entre les fichiers. Lorsque cette option est donnée deux fois, la commande recherche également les copies depuis d'autres fichiers dans le commit qui crée le fichier. Lorsque cette option est donnée trois fois, la commande recherche également les copies depuis d'autres fichiers dans n'importe quel commit.

<num> est facultatif mais c'est la limite inférieure du nombre de caractères alphanumériques que Git doit détecter comme déplacés/copiés entre les fichiers pour associer ces lignes au commit parent.ommit. Et la valeur par défaut est 40. S'il y a plus d'une option -C donnée, l'argument <num> de la dernière -C prend

ra ef
fet.

--ignore-rev

<rev>
Ignore les changements effectués par la révision lors de l'attribution du blame, comme si le changement n'avait jamais eu lieu. Les lignes qui ont été modifiées ou ajoutées par un commit ignoré seront attribuées au commit précédent qui a modifié cette ligne ou des lignes voisines. Cette option peut être spécifiée plusieurs fois pour ignorer plus d'une révision. Si l'option de configuration blame.markIgnoredLines est définie, alors les lignes qui ont été modifiées par un commit ignoré et attribuées à un autre commit seront marquées avec un ? dans la sortie du blame. Si l'option de configuration blame.markUnblamableLines est définie, alors ces lignes touchées par un commit ignoré que nous ne pouvons pas attribuer à une autre révision sont marquées avec un *. Dans les modes porcelain, nous imprimons ignored et unblamable sur une nouvelle ligne
respectivement.

LE FORMAT PAR

DÉFAUT

Lorsque ni l'option --porcelain ni --incremental n'est spécifiée, git blame produira une annotation pour chaque ligne avec

:
•le nom d'objet abrégé pour le commit d'où provient la ligne
;
•l'identifiant de l'auteur (par défaut le nom de l'auteur et la date, sauf si -s ou -e est spécifié) ;
et
•le numéro de
ligne

avant le c

ontenu de
la ligne.

LE FORMAT

PORCELAIN

Dans ce format, chaque ligne est sortie après un en-tête ; l'en-tête a au minimum la première ligne qui contient

:
•le SHA-1 de 40 octets du commit auquel la ligne est attribuée
;
•le numéro de ligne dans le fichier d'origine
;
•le numéro de ligne dans le fichier final
;
•sur une ligne qui commence un groupe de lignes d'un commit différent du précédent, le nombre de lignes dans ce groupe. Sur les lignes suivantes, ce champ est
absent.

Cette ligne d'en-tête est suivie par les informations suivantes au moins une fois pour chaque commit

:
•le nom de l'auteur ("author"), l'e-mail ("author-mail"), l'heure ("author-time") et le fuseau horaire ("author-tz") ; de même pour le
committer.
•le nom de fichier dans le commit auquel la ligne est
attribuée.
•la première ligne du message de journal du commit ("summary")
.

Le contenu de la ligne réelle est sorti après l'en-tête ci-dessus, préfixé par une TABULATION. Cela permet d'ajouter plus d'éléments d'en-tête plus

tard.

Le format porcelain supprime généralement les informations de commit qui ont déjà été vues. Par exemple, deux lignes attribuées au même commit seront toutes les deux affichées, mais les détails de ce commit ne seront affichés qu'une seule fois. Les informations spécifiques à des lignes individuelles ne seront pas regroupées, comme les révisions à marquer ignored ou unblamable. C'est plus efficace, mais peut nécessiter que le lecteur conserve plus d'état. L'option --line-porcelain peut être utilisée pour sortir les informations complètes du commit pour chaque ligne, permettant une utilisation plus simple (mais moins efficace) comme

: 
# compter le nombre de lignes attri
buées à chaque auteur git blame --l
ine-porcelain file | sed -n 's/^auth
or //p' | sort | uniq -c | sort -rn

SPÉCIFICATION DES

PLAGES

Contrairement à git blame et git annotate dans les anciennes versions de git, l'étendue de l'annotation peut être limitée à la fois aux plages de lignes et aux plages de révisions. L'option -L, qui limite l'annotation à une plage de lignes, peut être spécifiée plusieurs

fois.

Lorsque vous cherchez l'origine des lignes 40 à 60 du fichier foo, vous pouvez utiliser l'option -L comme ceci (elles signifient la même chose — les deux demandent 21 lignes à partir de la ligne 40)

: 
git blame -L 40
,60 foo git blam
e -L 40,+21 foo

De plus, vous pouvez utiliser une expression régulière pour spécifier la plage de lignes

: 
git blame -L
'/^sub hello
{/,/^}$/' foo

ce qui limite l'annotation au corps de la sous-routine hello

.

Lorsque vous n'êtes pas intéressé par les changements plus anciens que la version v2.6.18, ou les changements plus anciens que 3 semaines, vous pouvez utiliser des spécificateurs de plage de révisions similaires à git rev-l

ist : 
git blame v2.6.18..
-- foo git blame --
since=3.weeks -- foo

Lorsque des spécificateurs de plage de révisions sont utilisés pour limiter l'annotation, les lignes qui n'ont pas changé depuis la limite de la plage (soit le commit v2.6.18, soit le commit le plus récent qui a plus de 3 semaines dans l'exemple ci-dessus) sont attribuées au commit de limite de cette

plage.

Une manière particulièrement utile est de vérifier si un fichier ajouté contient des lignes créées par copier-coller à partir de fichiers existants. Parfois, cela indique que le développeur était négligent et n'a pas correctement refactorisé le code. Vous pouvez d'abord trouver le commit qui a introduit le fichier avec

: 
git log --diff-
filter=A --pret
ty=short -- foo

et ensuite annoter le changement entre ce commit et ses parents, en utilisant la notation commit^!

: 
git blame
-C -C -f
$commit
^! -- foo

SORTIE

INCRÉMENTALE

Lorsqu'elle est appelée avec l'option --incremental, la commande produit le résultat au fur et à mesure qu'il est construit. La sortie parlera généralement des lignes touchées par les commits les plus récents en premier (c'est-à-dire que les lignes seront annotées hors ordre) et est destinée à être utilisée par des visualiseurs

interactifs.

Le format de sortie est similaire au format Porcelain, mais il ne contient pas les lignes réelles du fichier qui est

annoté.
1.Chaque entrée de blame commence toujours par une ligne de : 
<40-byte-hex-sha1>
<sourceline> <resu
ltline> <num-lines>

Les numéros de l

igne sont compté
s à partir de 1.
2.La première fois qu'un commit apparaît dans le flux, diverses autres informations à son sujet sont imprimées avec une étiquette d'un mot au début de chaque ligne décrivant les informations supplémentaires du commit (auteur, e-mail, committer, dates, résumé, etc.)
.
3.Contrairement au format Porcelain, l'information du nom de fichier est toujours donnée et termine l'entrée : 
"filename" <whitespace-quoted-filename-goes-her
e
>

et il est donc vraiment très facile à analyser pour un analyseur orienté ligne et mot (ce qui devrait être assez naturel pour la plupart des langages de script)

.

Note
Pour ceux qui font de l'analyse : pour le rendre plus robuste, ignorez simplement toutes les lignes entre la première et
la dernière (les lignes "<sha1>" et "filename") où vous ne reconnaissez pas les mots d'étiquette (ou ne vous souciez pa
s de celui particulier) au début des lignes d'"information étendue". De cette façon, si des informations sont jamais aj
outées (comme l'encodage du commit ou des commentaires de commit étendus), un visualiseur de blame ne s'en souciera pas.

CONFIGURATIO

N

Tout ce qui se trouve sous cette ligne dans cette section est inclus sélectivement à partir de la documentation git-config(1). Le contenu est le même que celui qui s'y trouve

blame.

blankBoundary
Affiche un nom d'objet de commit vide pour les commits de limite dans git-blame(1). Cette option est par défaut à
false.

blame.

coloring
Cela détermine le schéma de coloration à appliquer à la sortie du blame. Il peut être repeatedLines, highlightRecent, ou none qui est la valeur par

blame.date

Spécifie le format utilisé pour afficher les dates dans git-blame(1). Si cette option n'est pas définie, le format iso est utilisé. Pour les valeurs prises en charge, voir la discussion de l'option --date dans git-log(1).

blame.showEmail

Affiche l'adresse e-mail de l'auteur au lieu de son nom dans git-blame(1). Cette option est fausse par défaut.

blame.showRoot

Ne traite pas les commits racines comme des frontières dans git-blame(1). Cette option est fausse par défaut.

blame.ignoreRevsFile

Ignore les révisions listées dans le fichier, une seule nom d'objet non abrégé par ligne, dans git-blame(1). Les espaces blancs et les commentaires commençant par # sont ignorés. Cette option peut être répétée plusieurs fois. Les noms de fichiers vides réinitialiseront la liste des révisions ignorées. Cette option sera traitée avant l'option en ligne de commande --ignore-revs-file.

blame.markUnblamableLines

Marque les lignes qui ont été modifiées par une révision ignorée que nous n'avons pas pu attribuer à un autre commit avec un * dans la sortie de git-blame(1).

blame.markIgnoredLines

Marque les lignes qui ont été modifiées par une révision ignorée que nous avons attribuée à un autre commit avec un ? dans la sortie de git-blame(1).
