NOM

gitformat-commit-graph - Format du graphe de commits Git

SYNOPSIS

$GIT_DIR/objects/info/commit-graph
$GIT_DIR/objects/info/commit-graphs/*

DESCRIPTION

Le graphe de commits Git stocke une liste d'identifiants de commits (OID) et quelques métadonnées associées, notamment :

•Le numéro de génération du commit.
•L'identifiant de l'arbre racine.
•La date du commit.
•Les parents du commit, stockés à l'aide de références positionnelles dans le fichier du graphe.
•Le filtre de Bloom des commits contenant les chemins modifiés entre le commit et son premier parent, si demandé.

Ces références positionnelles sont stockées sous forme d'entiers non signés de 32 bits correspondant à la position dans le tableau de la liste des identifiants de commits. En raison de certaines constantes spéciales que nous utilisons pour suivre les parents, nous pouvons stocker au maximum (1 << 30) + (1 << 29) + (1 << 28) - 1 (environ 1,8 milliard) de commits.

LE FORMAT DES FICHIERS COMMIT-GRAPH EST LE SUIVANT :

Afin de permettre des extensions qui ajoutent des données supplémentaires au graphe, nous organisons le corps en « morceaux » (chunks) et fournissons une table de recherche binaire au début du corps. L'en-tête inclut certaines valeurs, telles que le nombre de morceaux et le type de hachage.

Tous les nombres multi-octets sont en ordre d'octets réseau (network byte order).

EN-TÊTE :

Signature de 4 octets :
    La signature est : {'C', 'G', 'P', 'H'}
Numéro de version de 1 octet :
    Actuellement, la seule version valide est 1.
Version du hachage de 1 octet
    Nous déduisons la longueur du hachage (H) de cette valeur :
      1 => SHA-1
      2 => SHA-256
    Si le type de hachage ne correspond pas à l'algorithme de hachage du dépôt,
    le fichier commit-graph doit être ignoré avec un avertissement présenté à
    l'utilisateur.
Nombre (C) de « morceaux » (chunks) de 1 octet
Nombre (B) de graphes de commits de base de 1 octet
    Nous déduisons la longueur (H*B) du morceau de graphes de base
    de cette valeur.

TABLE DE RECHERCHE DES MORCEAUX :

(C + 1) * 12 octets listant la table des matières des morceaux :
    Les 4 premiers octets décrivent l'ID du morceau. La valeur 0 est une étiquette de terminaison.
    Les 8 autres octets fournissent l'offset en octets dans le fichier courant pour le début du morceau. (Les morceaux sont organisés de manière contiguë dans le fichier, vous pouvez donc déduire la longueur en utilisant la position du morceau suivant si nécessaire.) Chaque ID de morceau apparaît au plus une fois.
La TABLE DE RECHERCHE DES MORCEAUX correspond à la table des matières du
format de fichier basé sur les morceaux, voir linkgit:gitformat-chunk[5]
Les données restantes dans le corps sont décrites un morceau à la fois, et
ces morceaux peuvent être donnés dans n'importe quel ordre. Les morceaux sont
requis sauf indication contraire.

DONNÉES DES MORCEAUX :

Fanout des OIDs (ID : {O, I, D, F}) (256 * 4 octets) 

La i-ème entrée, F[i], stocke le nombre d'OIDs dont le premier
octet est inférieur ou égal à i. Ainsi, F[255] stocke le nombre total
de commits (N).

Recherche des OIDs (ID : {O, I, D, L}) (N * H octets) 

Les OIDs de tous les commits dans le graphe, triés par ordre croissant.

Données du Commit (ID : {C, D, A, T }) (N * (H + 16) octets)

•Les H premiers octets correspondent à l'OID de l'arbre racine.
•Les 8 octets suivants correspondent aux positions des deux premiers parents du i-ème commit. La valeur 0x70000000 est stockée s'il n'y a pas de parent à cette position. S'il y a plus de deux parents, la deuxième valeur a son bit le plus significatif activé et les autres bits stockent une position dans le morceau Liste des Arêtes Supplémentaires.
•Les 8 octets suivants stockent le niveau topologique (numéro de génération v1) du commit et l'heure du commit en secondes depuis l'EPOCH. Le numéro de génération utilise les 30 bits supérieurs des 4 premiers octets, tandis que l'heure du commit utilise les 32 bits des 4 octets suivants, ainsi que les 2 bits inférieurs du dernier octet, stockant le 33ème et le 34ème bit de l'heure du commit.

Données de Génération (ID : {G, D, A, 2 }) (N * 4 octets) [Optionnel]

•Cette liste de valeurs de 4 octets stocke les décalages corrigés de date de commit pour les commits, organisés dans le même ordre que le morceau de données du commit.
•Si le décalage corrigé de date de commit ne peut pas être stocké sur 31 bits, la valeur a son bit le plus significatif activé et les autres bits stockent la position du décalage corrigé de date de commit dans le morceau de Débordement des Données de Génération.
•Le morceau de Données de Génération n'est présent que lorsque le fichier commit-graph est écrit par des versions compatibles de Git et, en cas de chaînes de graphes de commits divisées, la couche supérieure contient également un morceau de Données de Génération.

Débordement des Données de Génération (ID : {G, D, O, 2 }) [Optionnel]

•Cette liste de valeurs de 8 octets stocke les décalages corrigés de date de commit pour les commits dont les décalages corrigés de date de commit ne peuvent pas être stockés sur 31 bits.
•Le morceau de Débordement des Données de Génération n'est présent que lorsque le morceau de Données de Génération est présent et qu'au moins un décalage corrigé de date de commit ne peut pas être stocké sur 31 bits.

Liste des Arêtes Supplémentaires (ID : {E, D, G, E}) [Optionnel] 

Cette liste de valeurs de 4 octets stocke les deuxième à n-ième parents pour
toutes les merges octopus. La valeur du second parent dans les données du commit stocke
une position dans cette liste ainsi que le bit le plus significatif activé. En partant de
cette position dans la liste, parcourez cette liste de positions de commits
pour les parents jusqu'à atteindre une valeur dont le bit le plus significatif
est activé. Les autres bits correspondent à la position du dernier parent.

Index du Filtre de Bloom (ID : {B, I, D, X}) (N * 4 octets) [Optionnel]

•La i-ème entrée, BIDX[i], stocke le nombre d'octets dans tous les filtres de Bloom des commits 0 à i (inclus) par ordre lexicographique. Le filtre de Bloom pour le i-ème commit s'étend de BIDX[i-1] à BIDX[i] (plus la longueur de l'en-tête), où BIDX[-1] est 0.
•Le morceau BIDX est ignoré si le morceau BDAT n'est pas présent.

Données du Filtre de Bloom (ID : {B, D, A, T}) [Optionnel]

•Il commence par un en-tête constitué de trois entiers non signés de 32 bits :
•La version de l'algorithme de hachage utilisé. Nous prenons actuellement en charge la valeur 2, qui correspond à la version 32 bits du hachage murmur3 implémentée exactement comme décrit dans https://en.wikipedia.org/wiki/MurmurHash#Algorithm et la technique de double hachage utilisant les valeurs de germe 0x293ae76f et 0x7e646e2 comme décrit dans https://doi.org/10.1007/978-3-540-30494-4_26 « Bloom Filters in Probabilistic Verification ». Les filtres de Bloom de version 1 contiennent un bug qui apparaît lorsque `char` est signé et que le dépôt contient des noms de chemin contenant des caractères >= 0x80 ; Git prend en charge leur lecture et leur écriture, mais cette capacité sera supprimée dans une future version de Git.
•Le nombre de fois qu'un chemin est haché et donc le nombre de positions de bits qui déterminent cumulativement si un fichier est présent dans le commit.
•Le nombre minimum de bits b par entrée dans le filtre de Bloom. Si le filtre contient n entrées, alors la taille du filtre est le nombre minimum de mots de 64 bits contenant n\*b bits.
•Le reste du morceau est la concaténation de tous les filtres de Bloom calculés pour les commits par ordre lexicographique.
•Note : Les commits sans modification ou avec plus de 512 modifications ont des filtres de Bloom de longueur un, avec soit tous les bits définis à zéro soit un respectivement.
•Le morceau BDAT est présent si et seulement si BIDX est présent.

Liste des Graphes de Base (ID : {B, A, S, E}) [Optionnel] 

Cette liste de hachages de H octets décrit un ensemble de B c
ommit-graph files that forment une chaîne de commit-graph. La position dans le graphe du ième commit dans le chunk OID Lookup de ce fichier est égale à i plus le nombre de commits dans tous les graphes de base. Si B est non nul, ce chunk doit exister.

NOTES HISTORIQUES

:
