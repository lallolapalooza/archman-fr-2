UTILISER GIT POUR LA

COLLABORATION

Supposons qu'Alice ait démarré un nouveau projet avec un dépôt Git dans /home/alice/project, et que Bob, qui a un répertoire personnel sur la même machine, souhaite y

contribuer.

Bob commence par

: 
bob$ git clone
/home/alice/
project myrepo

Cela crée un nouveau répertoire myrepo contenant un clone du dépôt d'Alice. Le clone est sur un pied d'égalité avec le projet original, possédant sa propre copie

INTERACTION AVEC LES DÉPÔTS DISTANTS

Lorsque vous travaillez sur un projet qui est également développé par d'autres personnes, vous devrez interagir avec le dépôt distant, qui est généralement un dépôt sur un serveur accessible via le réseau. Par exemple, disons qu'Alice et Bob travaillent ensemble sur le même projet. Alice a cloné le dépôt d'origine, puis a fait quelques modifications. Bob a également cloné le dépôt et a fait ses propres modifications.

Bob et Alice travaillent sur le même projet depuis les clônes qu'ils ont faits du dépôt d'origine. Leurs historiques locaux divergent. Chacun d'entre eux aura fait des commits locaux.

Maintenant, disons qu'Alice veut que Bob mette à jour son dépôt avec ses changements. Elle lui demande de faire un 'git pull' de son dépôt. Les dépôts distants sont accessibles par chemin d'accès local, URL, ou via SSH. Par exemple, si Alice a son dépôt sur le même système que Bob, elle peut lui demander de faire :

bob$ cd /home/bob/myrepo
bob$ git pull /home/alice/myrepo master

Ce qui suit l'opération ci-dessus, et est une opération commune. Alice a son propre dépôt : `/home/alice/myrepo`. Bob peut également demander à Alice de lui envoyer des modifications à l'aide d'un 'git fetch' de son dépôt, puis d'un 'git merge' de son propre dépôt. Elle peut le faire en faisant :

bob$ cd /home/bob/myrepo
bob$ git fetch /home/alice/myrepo master
bob$ git merge FETCH_HEAD

Le commande 'git pull' effectue en fait deux opérations : un 'git fetch' suivi d'un 'git merge'. Si Alice a des changements locaux qu'elle n'a pas encore commit, elle peut vouloir les commiter avant d'exécuter le 'git pull', car les changements locaux non commit peuvent interférer avec la fusion des changements apportés par Bob. Si elle a des changements locaux non commit qui entrent en conflit avec les changements de Bob, Git refusera de fusionner, et elle devra d'abord gérer ses changements locaux.

Alice peut examiner ce que Bob a fait sans fusionner en utilisant la commande 'git fetch'. Ceci permet à Alice d'examiner ce que Bob a fait, en utilisant un symbole spécial 'FETCH_HEAD', afin de déterminer s'il a quelque chose qui mérite d'être tiré, comme ceci :

alice$ git fetch /home/bob/myrepo master
alice$ git log -p HEAD..FETCH_HEAD

Cette opération est sûre même si Alice a des changements locaux non commit. La notation de plage 'HEAD..FETCH_HEAD' signifie "afficher tout ce qui est accessible depuis 'FETCH_HEAD' mais exclure tout ce qui est accessible depuis 'HEAD'". Alice sait déjà tout ce qui mène à son état actuel ('HEAD'), et examine ce que Bob a dans son état ('FETCH_HEAD') qu'elle n'a pas vu avec cette commande.

Si Alice veut visualiser ce que Bob a fait depuis que leurs historiques ont divergé, elle peut exécuter la commande suivante :

$ gitk HEAD..FETCH_HEAD

Ceci utilise la même notation de plage à deux points que nous avons vue précédemment avec 'git log'.

Alice peut vouloir voir ce que Bob et elle ont fait depuis qu'ils ont divergé. Elle peut utiliser la forme à trois points au lieu de la forme à deux points :

$ gitk HEAD...FETCH_HEAD

Ceci signifie "afficher tout ce qui est accessible depuis l'un ou l'autre, mais exclure tout ce qui est accessible depuis les deux".

Veuillez noter que ces notations de plage peuvent être utilisées avec 'gitk' et 'git log'.

Après avoir examiné ce que Bob a fait, s'il n'y a rien d'urgent, Alice peut décider de continuer à travailler sans récupérer les changements de Bob. Si l'historique de Bob contient quelque chose dont Alice aurait immédiatement besoin, Alice peut choisir de mettre de côté son travail en cours ('stash'), d'effectuer un 'pull', puis finalement de restaurer son travail ('unstash') par-dessus l'historique résultant.

Lorsque vous travaillez en groupe restreint et soudé, il n'est pas inhabituel d'interagir avec le même dépôt encore et encore. En définissant des raccourcis pour les dépôts *distants*, vous pouvez simplifier les choses :

alice$ git remote add bob /home/bob/myrepo

Avec cela, Alice peut effectuer la première partie de l'opération 'pull' seule en utilisant la commande 'git fetch' sans les fusionner avec sa propre branche, en utilisant :

alice$ git fetch bob

Contrairement à la forme longue, lorsque Alice récupère des changements de Bob en utilisant un raccourci de dépôt distant configuré avec 'git remote', ce qui a été récupéré est stocké dans une branche de suivi distante, dans ce cas 'bob/master'. Donc, après cela :

alice$ git log -p master..bob/master

affiche une liste de tous les changements que Bob a apportés depuis qu'il a bifurqué de la branche 'master' d'Alice.

Après avoir examiné ces changements, Alice pourrait fusionner les changements dans sa branche 'master' :

alice$ git merge bob/master

Cette *fusion* peut également être effectuée en *tirant depuis sa propre branche de suivi distante*, comme ceci :

alice$ git pull . remotes/bob/master

Notez que git pull fusionne toujours dans la branche actuelle, indépendamment de ce qui est donné d'autre dans la ligne de commande.

Plus tard, Bob peut mettre à jour son dépôt avec les derniers changements d'Alice en utilisant

bob$ git pull

Notez qu'il n'a pas besoin de spécifier le chemin d'accès au dépôt d'Alice ; lorsque Bob a cloné le dépôt d'Alice, Git a stocké l'emplacement de son dépôt dans la configuration du dépôt, et cet emplacement est utilisé pour les pulls :

bob$ git config --get remote.origin.url
/home/alice/project

(La configuration complète créée par 'git clone' est visible en utilisant 'git config -l', et la page man git-config(1) explique la signification de chaque option.)

Git conserve également une copie vierge de la branche 'master' d'Alice sous le nom 'origin/master' :

bob$ git branch -r
  origin/master

Si Bob décide plus tard de travailler depuis un autre hôte, il peut toujours effectuer des clones et des pulls en utilisant le protocole ssh :

bob$ git clone alice.org:/home/alice/project myrepo

Alternativement, Git a un protocole natif, ou peut utiliser http ; voir git-pull(1) pour les détails.

Git peut également être utilisé en mode similaire à CVS, avec un dépôt central auquel divers utilisateurs poussent des changements ; voir git-push(1) et gitcvs-migration(7).

EXPLORATION DE L'HISTORIQUE

L'historique Git est représenté par une série de commits interreliés. Nous avons déjà vu que la commande 'git log' peut lister ces commits. Notez que la première ligne de chaque entrée de 'git log' donne également un nom au commit :

$ git log
commit c82a22c39cbc32576f64f5c6b3f24b99ea8149c7
Author: Junio C Hamano <junkio@cox.net>
Date:   Tue May 16 17:18:22 2006 -0700
    merge-base: Clarify the comments on post processing.

Nous pouvons donner ce nom à 'git show' pour voir les détails de ce commit.

$ git show c82a22c39cbc32576f64f5c6b3f24b99ea8149c7

Mais il existe d'autres façons de faire référence aux commits. Vous pouvez utiliser n'importe quelle partie initiale du nom qui est suffisamment longue pour identifier le commit de manière unique :

$ git show c82a22c39c   # les premiers caractères du nom sont
                        # généralement suffisants
$ git show HEAD         # le sommet de la branche actuelle
$ git show experimental # le sommet de la branche "experimental"

Chaque commit a généralement un commit "parent" qui pointe vers l'état précédent du projet :

$ git show HEAD^  # pour voir le parent de HEAD
$ git show HEAD^^ # pour voir le grand-parent de HEAD
$ git show HEAD~4 # pour voir l'arrière-arrière-grand-parent de HEAD

Notez que les commits de fusion peuvent avoir plus d'un parent :

$ git show HEAD^1 # afficher le premier parent de HEAD (identique à HEAD^)
$ git show HEAD^2 # afficher le second parent de HEAD

Vous pouvez également donner vos propres noms aux commits ; après avoir exécuté

$ git tag v2.5 1b2e1d63ff

vous pouvez faire référence à '1b2e1d63ff' par le nom 'v2.5'. Si vous avez l'intention de partager ce nom avec d'autres personnes (par exemple, pour identifier une version de publication), vous devriez créer un objet "tag" et éventuellement le signer ; voir git-tag(1) pour les détails.

Toute commande Git qui a besoin de connaître un commit peut prendre n'importe lequel de ces noms. Par exemple :

$ git diff v2.5 HEAD     # comparer le HEAD actuel à v2.5
$ git branch stable v2.5 # démarrer une nouvelle branche nommée "stable"
                         # basée sur v2.5
$ git reset --hard HEAD^ # réinitialiser votre branche actuelle et votre
                         # répertoire de travail à leur état à HEAD^

Soyez prudent avec cette dernière commande : en plus de perdre tous les changements dans le répertoire de travail, elle supprimera également tous les commits ultérieurs de cette branche. Si cette branche est la seule branche contenant ces commits, ils seront perdus. De plus, n'utilisez pas 'git reset' sur une branche publiquement visible que d'autres développeurs récupèrent, car cela forcera des fusions inutiles pour les autres développeurs afin de nettoyer l'historique. Si vous avez besoin d'annuler des changements que vous avez poussés, utilisez plutôt 'git revert'.

La commande 'git grep' peut rechercher des chaînes dans n'importe quelle version de votre projet, donc

$ git grep "hello" v2.5

recherche toutes les occurrences de "hello" dans 'v2.5'.

Si vous omettez le nom du commit, 'git grep' recherchera dans tous les fichiers qu'il gère dans votre répertoire actuel. Donc

$ git grep "hello"

est un moyen rapide de rechercher uniquement les fichiers suivis par Git.

De nombreuses commandes Git prennent également des ensembles de commits, qui peuvent être spécifiés de plusieurs manières. Voici quelques exemples avec 'git log' :

$ git log v2.5..v2.6            # commits entre v2.5 et v2.6
$ git log v2.5..                # commits depuis v2.5
$ git log --since="2 weeks ago" # commits des 2 dernières semaines
$ git log v2.5.. Makefile       # commits depuis v2.5 qui modifient
                                # Makefile

Vous pouvez également donner à 'git log' une "plage" de commits où le premier n'est pas nécessairement un ancêtre du second ; par exemple, si les sommets des branches 'stable' et 'master' ont divergé d'un commit commun il y a quelque temps, alors

$ git log stable..master

listra les commits effectués dans la branche 'master' mais pas dans la branche stable, tandis que

$ git log master..stable

affichera la liste des commits effectués dans la branche stable mais pas dans la branche 'master'.

La commande 'git log' a une faiblesse : elle doit présenter les commits sous forme de liste. Lorsque l'historique a des lignes de développement qui ont divergé puis fusionné à nouveau, l'ordre dans lequel 'git log' présente ces commits n'a aucun sens.

La plupart des projets avec plusieurs contributeurs (comme le noyau Linux, ou Git lui-même) ont des fusions fréquentes, et 'gitk' fait un meilleur travail

de visualiser leur historique. Par

exemple, 
$ gitk --sin
ce="2 weeks a
go" drivers/

vous permet de parcourir tous les commits des 2 dernières semaines qui ont modifié des fichiers sous le répertoire drivers. (Note : vous pouvez ajuster les polices de gitk en maintenant la touche contrôle enfoncée tout en appuyant sur « - » ou « + ».

)

Enfin, la plupart des commandes qui prennent des noms de fichiers vous permettent éventuellement de faire précéder un nom de fichier par un commit, pour spécifier une version particulière du fichier

: 
$ git diff v2.
5:Makefile HE
AD:Makefile.in

Vous pouvez également utiliser git show pour voir un tel fichier

$ git

ÉTAPES

SUIVANTES

Ce tutoriel devrait suffire pour effectuer un contrôle de révision distribué de base pour vos projets. Cependant, pour comprendre pleinement la profondeur et la puissance de Git, vous devez comprendre deux idées simples sur lesquelles il est basé

:
•La base de données d'objets est le système plutôt élégant utilisé pour stocker l'historique de votre projet — fichiers, répertoires et
commits.
•Le fichier index est un cache de l'état d'un arborescence de répertoires, utilisé pour créer des commits, extraire des répertoires de travail et conserver les différentes arbres impliquées dans une
fusion.

La deuxième partie de ce tutoriel explique la base de données d'objets, le fichier index et quelques autres détails que vous aurez besoin de connaître pour tirer le meilleur parti de Git. Vous pouvez la trouver dans gittutorial

-2(7).

Si vous ne souhaitez pas continuer avec cela immédiatement, quelques autres digressions qui peuvent être intéressantes à ce stade sont

:
•git-format-patch(1), git-am(1) : Ceux-ci convertissent des séries de commits git en correctifs envoyés par courriel, et inversement, utile pour des projets tels que le noyau Linux qui reposent fortement sur les correctifs envoyés par
courriel.
•git-bisect(1) : Lorsqu'il y a une régression dans votre projet, une façon de retrouver le bogue est de parcourir l'historique pour trouver le commit exact qui en est responsable. git bisect peut vous aider à effectuer une recherche dichotomique pour ce commit. Il est assez intelligent pour effectuer une recherche quasi optimale même en cas d'historique non linéaire complexe avec de nombreuses branches
fusionnées.
•gitworkflows(7) : Donne un aperçu des flux de travail
recommandés.
•giteveryday(7) : Git au quotidien avec 20 commandes
environ.
