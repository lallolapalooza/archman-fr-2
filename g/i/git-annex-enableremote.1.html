NOM

git-annex-enableremote - permet à git-annex d'utiliser un dépôt distant

SYNOPSIS

git annex enableremote nom|uuid|desc [param=valeur ...]

DESCRIPTION

Permet l'utilisation d'un dépôt distant existant dans le dépôt actuel, qui a été configuré précédemment par git annex initremote exécuté dans une autre copie du dépôt.

Lors de l'activation d'un dépôt distant, spécifiez le même nom que celui utilisé lors de la configuration initiale de ce dépôt distant avec git annex initremote. Exécutez git annex enableremote sans aucun nom pour obtenir une liste des noms de dépôts distants. Vous pouvez également spécifier l'uuid ou la description du dépôt distant.

Certains types de dépôts distants spéciaux nécessitent que des paramètres soient spécifiés à chaque fois qu'ils sont activés. Par exemple, le dépôt distant de type répertoire nécessite un paramètre `directory=` à chaque fois. La commande vous demandera les paramètres requis que vous auriez omis.

Cette commande peut également être utilisée pour modifier la configuration d'un dépôt distant spécial existant, en spécifiant de nouvelles valeurs pour les paramètres qui sont habituellement définis lors de l'utilisation de `initremote`. (Cependant, certains paramètres tels que le schéma de chiffrement ne peuvent pas être modifiés une fois qu'un dépôt distant spécial a été créé.)

Les clés GPG avec lesquelles un dépôt distant spécial chiffré est chiffré peuvent être modifiées en utilisant les paramètres `keyid+=` et `keyid-=` . Ceux-ci ajoutent et suppriment respectivement des clés de la liste. Cependant, notez que la suppression d'une clé n'empêche pas nécessairement le propriétaire de la clé d'accéder aux données dans le dépôt distant spécial chiffré (ce qui est impossible par conception, à moins de supprimer le dépôt distant).

Un cas d'utilisation de `keyid-=` est de remplacer une clé révoquée par une nouvelle clé :


git annex enableremote mys3 keyid-=clef_revoquee keyid+=nouvelleclef

De plus, notez que pour les dépôts distants spéciaux chiffrés utilisant un chiffrement par clé publique simple (encryption=pubkey), l'ajout ou la suppression d'une clé n'a AUCUN effet sur les fichiers qui ont déjà été copiés vers le dépôt distant. Par conséquent, l'utilisation de `keyid+=` et `keyid-=` avec de tels dépôts doit être utilisée avec précaution et a peu de sens, sauf dans des cas comme l'exemple de clé révoquée ci-dessus.

Si vous vous lassez d'activer manuellement un dépôt distant spécial dans chaque nouvelle copie, vous pouvez passer `autoenable=true`. Ensuite, lorsque `git-annex-init(1)` est exécuté dans une nouvelle copie, il tentera d'activer le dépôt distant spécial. Bien sûr, cela fonctionne mieux lorsque le dépôt distant spécial n'a rien de particulier à faire pour être activé.

(Cette commande peut également être utilisée pour activer un dépôt git que `git-annex` a trouvé comme ne fonctionnant pas auparavant et qu'il a abandonné, en réglant remote.<nom>.annex-ignore.)

OPTIONS

--with-url
Ceci configure le dépôt distant avec une URL « annex:: », ce qui permet à git de lui pousser et d'en tirer des données, en utilisant git-remote-annex.
--json
Active la sortie JSON. Ceci est destiné à être analysé par des programmes qui utilisent git-annex.
--json-error-messages
Les messages qui seraient normalement affichés sur la sortie standard d'erreur sont inclus dans le JSON à la place.
Aussi, les options-communes-git-annex(1) peuvent être utilisées.
