NOM

git-send-pack(1) — Envoie des objets via le protocole Git vers un autre dépôt

SYNTAXE

git send-pack [--mirror] [--dry-run] [--force]
                [--receive-pack=<git-receive-pack>]
                [--verbose] [--thin] [--atomic]
                [--[no-]signed | --signed=(true|false|if-asked)]
                [<host>:]<répertoire> (--all | <ref>...)

DESCRIPTION

Normalement, vous devriez utiliser git push, qui est une enveloppe de plus haut niveau de cette commande, à la place. Voir git-push(1).

Invoque git-receive-pack sur un dépôt potentiellement distant, et le met à jour à partir du dépôt courant, en envoyant les refs nommées.

OPTIONS

--receive-pack=<git-receive-pack>

Chemin vers le programme git-receive-pack à l'extrémité distante. Parfois utile lors de l'envoi vers un dépôt distant via ssh, et que vous n'avez pas le programme dans un répertoire du $PATH par défaut.

--exec=<git-receive-pack>

Identique à --receive-pack=<git-receive-pack>.

--all

Au lieu de spécifier explicitement quelles refs mettre à jour, met à jour toutes les têtes qui existent localement.

--stdin

Prend la liste des refs depuis stdin, une par ligne. S'il y a des refs spécifiées sur la ligne de commande en plus de cette option, alors les refs de stdin sont traitées après celles de la ligne de commande.

Si --stateless-rpc est spécifié avec cette option, alors la liste des refs doit être au format packet (pkt-line). Chaque ref doit être dans un packet séparé, et la liste doit se terminer par un packet de flush.

--dry-run

Fait tout sauf envoyer réellement les mises à jour.

--force

Normalement, la commande refuse de mettre à jour une ref distante qui n'est pas un ancêtre de la ref locale utilisée pour la remplacer. Ce drapeau désactive la vérification. Cela signifie que le dépôt distant peut perdre des commits ; utilisez-le avec précaution.

--verbose

Exécute en mode verbeux.

--thin

Envoie un paquet « fin » (thin), qui enregistre les objets sous forme d'objets delta basés sur des objets non inclus dans le paquet afin de réduire le trafic réseau.

--atomic

Utilise une transaction atomique pour la mise à jour des refs. Si l'une des refs échoue à la mise à jour, alors l'ensemble du push échouera sans modifier aucune ref.

--signed, --no-signed, --signed=(true|false|if-asked)

Signe GPG la requête de push pour mettre à jour les refs côté réception, afin de permettre la vérification par les hooks et/ou l'enregistrement. Si false ou --no-signed, aucune signature ne sera tentée. Si true ou --signed, le push échouera si le serveur ne prend pas en charge les pushes signés. Si défini sur if-asked, signe si et seulement si le serveur prend en charge les pushes signés. Le push échouera également si l'appel réel à gpg --sign échoue. Voir git-receive-pack(1) pour les détails sur l'extrémité de réception.

--push-option=<chaîne>

Passe la chaîne spécifiée comme une option de push pour être consommée par les hooks du côté serveur. Si le serveur ne prend pas en charge les options de push, une erreur se produit. Voir git-push(1) et githooks(5) pour les détails.

<host>

Un hôte distant hébergeant le dépôt. Lorsque cette partie est spécifiée, git-receive-pack est invoqué via ssh.

<répertoire>

Le dépôt à mettre à jour.

<ref>...

Les refs distantes à mettre à jour.

SPECIFICATION DES REFS

Il existe trois façons de spécifier les refs à mettre à jour à l'extrémité distante.

Avec le drapeau --all, toutes les refs qui existent localement sont transférées à l'extrémité distante. Vous ne pouvez pas spécifier de <ref> si vous utilisez ce drapeau.

Sans --all et sans aucune <ref>, les têtes qui existent à la fois du côté local et du côté distant sont mises à jour.

Lorsque une ou plusieurs <ref> sont spécifiées explicitement (que ce soit sur la ligne de commande ou via --stdin), il peut s'agir d'un seul motif, ou d'une paire de tels motifs séparés par un deux-points ":" (cela signifie qu'un nom de ref ne peut pas contenir de deux-points). Un seul motif <nom> est simplement un raccourci pour <nom>:<nom>.

Chaque paire de motifs se compose du côté source (avant le deux-points) et du côté destination (après le deux-points). La ref à pousser est déterminée en trouvant une correspondance qui correspond au côté source, et où elle est poussée est déterminée en utilisant le côté destination. Les règles utilisées pour faire correspondre une ref sont les mêmes règles utilisées par git rev-parse pour résoudre un nom de ref symbolique. Voir git-rev-parse(1).

•C'est une erreur si <src> ne correspond pas exactement à une des refs locales.
•C'est une erreur si <dst> correspond à plus d'une ref distante.
•Si <dst> ne correspond à aucune ref distante, alors
•il doit commencer par "refs/"; <dst> est utilisé comme destination littéralement dans ce cas.
•<src> == <dst> et la ref qui a correspond à <src> ne doit pas exister dans l'ensemble des refs distantes ; la ref correspondant à <src> localement est utilisée comme nom de la destination.

Sans --force, la ref <src> est stockée à distance uniquement si <dst> n'existe pas, ou si <dst> est un sous-ensemble propre (c'est-à-dire un ancêtre) de <src>. Cette vérification, connue sous le nom de vérification « fast-forward », est effectuée pour éviter d'écraser accidentellement la ref distante et d'y perdre les commits des autres personnes.

Avec --force, la vérification fast-forward est désactivée pour toutes les refs.

Optionnellement, un paramètre <ref> peut être préfixé par un signe plus + pour désactiver la vérification fast-forward uniquement sur cette ref.
