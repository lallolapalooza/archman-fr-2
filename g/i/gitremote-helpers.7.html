DESCRIPTIO

N

Les programmes d'aide distants ne sont généralement pas utilisés directement par les utilisateurs finaux, mais sont invoqués par Git lorsqu'il doit interagir avec des dépôts distants que Git ne prend pas en charge nativement. Un aide donné implémentera un sous-ensemble des fonctionnalités documentées ici. Lorsque Git doit interagir avec un dépôt à l'aide d'un aide distant, il lance l'aide en tant que processus indépendant, envoie des commandes à l'entrée standard de l'aide et attend les résultats de la sortie standard de l'aide. Comme un aide distant s'exécute en tant que processus indépendant de Git, il n'est pas nécessaire de relier Git pour ajouter un nouvel aide, ni de lier l'aide avec l'implémentation de

Git.

Chaque aide doit prendre en charge la commande "capabilities", que Git utilise pour déterminer quelles autres commandes l'aide acceptera. Ces autres commandes peuvent être utilisées pour découvrir et mettre à jour les références distantes, transporter des objets entre la base de données d'objets et le dépôt distant, et mettre à jour le stockage d'objets

local.

Git est livré avec une famille d'aides distants "curl", qui gèrent divers protocoles de transport, tels que git-remote-http, git-remote-https, git-remote-ftp et git-remote-ftps. Ils implémentent les fonctionnalités fetch, option et pu

sh
.

INVOCATIO

N

Les programmes d'aide distants sont invoqués avec un ou (facultativement) deux arguments. Le premier argument spécifie un dépôt distant comme dans Git ; il s'agit soit du nom d'un distant configuré, soit d'une URL. Le second argument spécifie une URL ; elle est généralement de la forme <transport>://<adresse>, mais toute chaîne arbitraire est possible. La variable d'environnement GIT_DIR est configurée pour l'aide distant et peut être utilisée pour déterminer où stocker des données supplémentaires ou depuis quel répertoire invoquer des commandes Git

auxiliaires.

Lorsque Git rencontre une URL de la forme <transport>://<adresse>, où <transport> est un protocole qu'il ne peut pas gérer nativement, il invoque automatiquement git remote-<transport> avec l'URL complète comme second argument. Si une telle URL est rencontrée directement sur la ligne de commande, le premier argument est identique au second, et si elle est rencontrée dans un distant configuré, le premier argument est le nom de ce

distant.

Une URL de la forme <transport>::<adresse> indique explicitement à Git d'invoquer git remote-<transport> avec <adresse> comme second argument. Si une telle URL est rencontrée directement sur la ligne de commande, le premier argument est <adresse>, et si elle est rencontrée dans un distant configuré, le premier argument est le nom de ce

distant.

De plus, lorsqu'un distant configuré a remote.<nom>.vcs défini à <transport>, Git invoque explicitement git remote-<transport> avec <nom> comme premier argument. S'il est défini, le second argument est remote.<nom>.url ; sinon, le se

cond argume
nt est omis.

FORMAT

D'ENTRÉE

Git envoie à l'aide distant une liste de commandes sur l'entrée standard, une par ligne. La première commande est toujours la commande capabilities, en réponse à laquelle l'aide distant doit imprimer une liste des fonctionnalités qu'il prend en charge (voir ci-dessous) suivie d'une ligne vide. La réponse à la commande capabilities détermine quelles commandes Git utilise dans le reste du flux de

commandes.

Le flux de commandes est terminé par une ligne vide. Dans certains cas (indiqué dans la documentation des commandes concernées), cette ligne vide est suivie d'un charge utile dans un autre protocole (par exemple, le protocole de paquet), tandis que dans d'autres, elle indique la fin de

l'entrée.

s

On s'attend à ce que chaque aide distant ne prenne en charge qu'un sous-ensemble de commandes. Les opérations qu'un aide prend en charge sont déclarées à Git dans la réponse à la commande capabilities (voir COMMANDES, ci-dessous)

.

Dans ce qui suit, nous listons toutes les fonctionnalités définies et pour chacune, nous listons les commandes qu'un aide avec cette fonctionnalité doit

fournir.

bidi-impor

t
Cela modifie la capacité import. Les commandes fast-import cat-blob et ls peuvent être utilisées par les remote-helpers pour récupérer des informations sur les blobs et les arbres qui existent déjà en mémoire dans fast-import. Cela nécessite un canal de fast-import vers le remote-helper. S'il est annoncé en plus de "import", Git établit un pipe de fast-import vers l'entrée standard du remote-helper. Il en découle que Git et fast-import sont tous deux connectés à l'entrée standard du remote-helper. Comme Git peut envoyer plusieurs commandes au remote-helper, il est requis que les helpers utilisant bidi-import mettent en tampon toutes les commandes import d'un lot avant d'envoyer des données à fast-import. Cela permet d'éviter de mélanger les commandes et les réponses de fast-import sur l'entrée standard du
helper.

fetch <sha1>

<name>
Récupère l'objet donné, écrivant les objets nécessaires dans la base de données. Les commandes fetch sont envoyées en lot, une par ligne, terminées par une ligne vide. Produit une seule ligne vide lorsque toutes les commandes fetch du même lot sont terminées. Seuls les objets qui ont été rapportés dans la sortie de list avec un sha1 peuvent être récupérés de cette manière.

Peut éventuellement produire une ligne lock <file> indiquant le chemin complet d'un fichier sous $GIT_DIR/objects/pack qui conserve un pack jusqu'à ce que les références puissent être mises à jour convenablement. Le chemin doit se terminer par .keep. C'est un mécanisme pour nommer un tuple <pack,idx,keep> en donnant seulement la composante keep. Le pack conservé ne sera pas supprimé par un repack concurrent, même si ses objets peuvent ne pas être référencés jusqu'à ce que la récupération soit terminée. Le fichier .keep sera supprimé à la conclusion de la

récupération.

connecté.

Se connecte au service donné. L'entrée standard et la sortie standard du helper sont connectées au service spécifié (le préfixe git est inclus dans le nom du service, donc par exemple la récupération utilise git-upload-pack comme service) sur le côté distant. Après le saut de ligne terminant la réponse positive (vide), la sortie du service commence. Après la fin de la connexion, le remote helper se termine.

stateless-connect

<service>
Expérimental ; pour usage interne uniquement. Se connecte au service distant donné pour la communication en utilisant le protocole de transport version 2 de git. Les réponses valides à cette commande sont une ligne vide (connexion établie), fallback (pas de prise en charge du transport intelligent, revenir aux transports stupides) et simplement quitter avec un message d'erreur imprimé (impossible de se connecter, ne pas chercher à revenir en arrière). Après le saut de ligne terminant la réponse positive (vide), la sortie du service commence. Les messages (requête et réponse) doivent se composer de zéro ou plusieurs PKT-LINEs, terminés par un paquet de purge. Les messages de réponse auront alors un paquet de fin de réponse après le paquet de purge pour indiquer la fin d'une réponse. Le client ne doit pas s'attendre à ce que le serveur stocke un état entre les paires requête-réponse. Après la fin de la connexion, le remote helper se termine.

REF LIST ATTRIBUTES

La commande list produit une liste de refs dans laquelle chaque ref peut être suivie d'une liste d'attributs. Les attributs de liste de refs suivants sont définis.

unchanged

Cette ref n'a pas changé depuis la dernière importation ou récupération, bien que l'assistant ne puisse pas nécessairement déterminer quelle valeur cela a produite.

REF LIST KEYWORDS

La commande list peut produire une liste de paires clé-valeur. Les clés suivantes sont définies.

object-format

Les refs utilisent l'algorithme de hachage donné. Ce mot-clé n'est utilisé que si le serveur et le client prennent tous deux en charge l'extension object-format.

OPTIONS

Les options suivantes sont définies et (dans des circonstances appropriées) définies par Git si l'assistant distant possède la capacité option.

option verbosity <n>

Modifie la verbosité des messages affichés par l'assistant. Une valeur de 0 pour <n> signifie que les processus fonctionnent silencieusement, et que l'assistant ne produit que des messages d'erreur. 1 est le niveau de verbosité par défaut, et les valeurs supérieures de <n> correspondent au nombre de drapeaux -v passés sur la ligne de commande.

option progress {true|false}

Active (ou désactive) les messages de progression affichés par l'assistant de transport pendant une commande.

option depth <depth>

Approfondit l'historique d'un dépôt peu profond.

option deepen-since <timestamp>

Approfondit l'historique d'un dépôt peu profond en fonction de l'heure.

option deepen-not <ref>

Approfondit l'historique d'un dépôt peu profond en excluant la ref. Plusieurs options s'ajoutent.

option deepen-relative {true|false}

Approfondit l'historique d'un dépôt peu profond par rapport à la limite actuelle. Ne valide que lorsqu'il est utilisé avec "option depth".

option followtags {true|false}

Si activé, l'assistant doit automatiquement récupérer les objets de tag annotés si l'objet pointé par le tag a été transféré pendant la commande de récupération. Si le tag n'est pas récupéré par l'assistant, une deuxième commande de récupération sera généralement envoyée pour demander le tag spécifiquement. Certains assistants peuvent utiliser cette option pour éviter une deuxième connexion réseau.

option dry-run {true|false}

Si vrai, simule que l'opération s'est terminée avec succès, mais ne modifie pas réellement les données du dépôt. Pour la plupart des assistants, cela ne s'applique qu'à la commande push, si elle est prise en charge.

option servpath <chemin-entre-guillemets-style-c>

Définit le chemin du service (--upload-pack, --receive-pack etc.) pour la prochaine connexion. L'assistant distant peut prendre en charge cette option, mais ne doit pas s'appuyer sur le fait que cette option soit définie avant la requête de connexion.

option check-connectivity {true|false}

Demande à l'assistant de vérifier la connectivité d'un clonage.

option force {true|false}

Demande à l'assistant d'effectuer une mise à jour forcée. La valeur par défaut est false.

option cloning {true|false}

Notifie l'assistant qu'il s'agit d'une demande de clonage (c'est-à-dire que le dépôt actuel est garanti vide).

option update-shallow {true|false}

Permet d'étendre .git/shallow si les nouvelles refs l'exigent.

option pushcert {true|false}

Signe les push GPG.

option push-option <chaîne>

Transmet <chaîne> comme option de push. Comme l'option de push ne doit pas contenir de caractères LF ou NUL, la chaîne n'est pas encodée.

option from-promisor {true|false}

Indique que ces objets sont récupérés d'un promoteur.

option no-dependents {true|false}

Indique que seuls les objets souhaités doivent être récupérés, et non leurs dépendances.

option atomic {true|false}

Lors du push, demande au serveur distant de mettre à jour les refs dans une seule transaction atomique. En cas de succès, toutes les refs seront mises à jour, ou aucune ne le sera. Si le côté distant ne prend pas en charge cette capacité, le push échouera.

option object-format true

Indique que l'appelant souhaite que les informations sur l'algorithme de hachage soient renvoyées par le distant. Ce mode est utilisé lors de la récupération de refs.
