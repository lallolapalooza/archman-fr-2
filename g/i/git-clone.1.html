NOM

git-clone - Cloner un dépôt dans un nouveau répertoire

SYNTAXE

git clone [--template=<répertoire-modèle>]
          [-l] [-s] [--no-hardlinks] [-q] [-n] [--bare] [--mirror]
          [-o <nom>] [-b <nom>] [-u <upload-pack>] [--reference <dépôt>]
          [--dissociate] [--separate-git-dir <git-dir>]
          [--depth <profondeur>] [--[no-]single-branch] [--[no-]tags]
          [--recurse-submodules[=<pathspec>]] [--[no-]shallow-submodules]
          [--[no-]remote-submodules] [--jobs <n>] [--sparse] [--[no-]reject-shallow]
          [--filter=<spécification-filtre> [--also-filter-submodules]] [--] <dépôt>
          [<répertoire>]

DESCRIPTION

Clone un dépôt dans un répertoire nouvellement créé, crée des branches de suivi distantes pour chaque branche dans le dépôt cloné (visibles avec git branch --remotes), et crée et extrait une branche initiale qui est dérivée de la branche actuellement active du dépôt cloné.

Après le clonage, un simple git fetch sans arguments mettra à jour toutes les branches de suivi distantes, et un git pull sans arguments fusionnera en plus la branche master distante dans la master courante, le cas échéant (ceci est faux lorsque --single-branch est donné ; voir ci-dessous).

Cette configuration par défaut est réalisée en créant des références aux pointeurs de branches distantes sous refs/remotes/origin et en initialisant les variables de configuration remote.origin.url et remote.origin.fetch.

OPTIONS

-l, --local

Lorsque le dépôt à cloner se trouve sur une machine locale, ce drapeau contourne le mécanisme de transport normal « conscient de Git » et clône le dépôt en effectuant une copie de HEAD et de tout ce qui se trouve sous les répertoires objects et refs. Les fichiers sous le répertoire .git/objects/ sont liés en dur (hardlinked) pour économiser de l'espace lorsque possible.

Si le dépôt est spécifié comme un chemin local (par exemple, /chemin/vers/repo), c'est le comportement par défaut, et --local est essentiellement une opération nulle (no-op). Si le dépôt est spécifié comme une URL, alors ce drapeau est ignoré (et nous n'utilisons jamais les optimisations locales). Spécifier --no-local annulera le comportement par défaut lorsque /chemin/vers/repo est donné, en utilisant à la place le transport Git normal.

Si le répertoire $GIT_DIR/objects du dépôt contient des liens symboliques ou est un lien symbolique, le clonage échouera. C'est une mesure de sécurité pour empêcher la copie involontaire de fichiers par déréférencement de liens symboliques.

Cette option ne fonctionne pas avec les dépôts appartenant à d'autres utilisateurs pour des raisons de sécurité, et --no-local doit être spécifié pour que le clonage réussisse.

NOTE: cette opération peut entrer en concurrence avec des modifications concurrentes du dépôt source, similaire à l'exécution de cp -r <source> <destination> tout en modifiant <source>.

--no-hardlinks

Force le processus de clonage à partir d'un dépôt sur un système de fichiers local à copier les fichiers sous le répertoire .git/objects au lieu d'utiliser des liens en dur. Cela peut être souhaitable si vous essayez de faire une sauvegarde de votre dépôt.

-s, --shared

Lorsque le dépôt à cloner se trouve sur la machine locale, au lieu d'utiliser des liens en dur, configure automatiquement .git/objects/info/alternates pour partager les objets avec le dépôt source. Le dépôt résultant commence sans aucun objet propre.

NOTE: c'est une opération potentiellement dangereuse ; ne l'utilisez pas sauf si vous comprenez ce qu'elle fait. Si vous clonez votre dépôt en utilisant cette option puis supprimez des branches (ou utilisez toute autre commande Git qui rend un commit existant non référencé) dans le dépôt source, certains objets peuvent devenir non référencés (ou pendants). Ces objets peuvent être supprimés par les opérations Git normales (telles que git commit) qui appellent automatiquement git maintenance run --auto. (Voir git-maintenance(1).) Si ces objets sont supprimés et étaient référencés par le dépôt cloné, alors le dépôt cloné deviendra corrompu.

Notez que l'exécution de git repack sans l'option --local dans un dépôt cloné avec --shared copiera les objets du dépôt source dans un pack dans le dépôt cloné, supprimant les économies d'espace disque de clone --shared. Il est cependant sûr d'exécuter git gc, qui utilise l'option --local par défaut.

Si vous souhaitez rompre la dépendance d'un dépôt cloné avec --shared vis-à-vis de son dépôt source, vous pouvez simplement exécuter git repack -a pour copier tous les objets du dépôt source dans un pack dans le dépôt cloné.

--reference[-if-able] <dépôt>

Si la référence <dépôt> se trouve sur la machine locale, configure automatiquement .git/objects/info/alternates pour obtenir des objets à partir de la référence <dépôt>. Utiliser un dépôt déjà existant comme alternat nécessitera moins d'objets à copier à partir du dépôt en cours de clonage, réduisant les coûts de réseau et de stockage local. Lorsque vous utilisez --reference-if-able, un répertoire inexistant est ignoré avec un avertissement au lieu d'annuler le clonage.

NOTE: voir la NOTE pour l'option --shared, et aussi l'option --dissociate.

--dissociate

Emprunte les objets des dépôts de référence spécifiés avec les options --reference uniquement pour réduire le transfert réseau, et arrête d'emprunter à ces dépôts après la création du clone en effectuant les copies locales nécessaires des objets empruntés. Cette option peut également être utilisée lors du clonage local d'un dépôt qui emprunte déjà des objets à un autre dépôt — le nouveau dépôt empruntera des objets au même dépôt, et cette option peut être utilisée pour arrêter l'emprunt.

-q, --quiet

Fonctionne en mode silencieux. Le progrès n'est pas rapporté sur le flux d'erreur standard.

-v, --verbose

Fonctionne en mode verbeux. N'affecte pas le rapport de statut de progression sur le flux d'erreur standard.

--progress

Le statut de progression est rapporté sur le flux d'erreur standard par défaut lorsqu'il est attaché à un terminal, sauf si --quiet est spécifié. Ce drapeau force le statut de progression même si le flux d'erreur standard n'est pas redirigé vers un terminal.

--server-option=<option>

Transmet la chaîne donnée au serveur lors de la communication en utilisant le protocole version 2. La chaîne donnée ne doit pas contenir de caractère NUL ou LF. La manière dont le serveur gère les options serveur, y compris celles inconnues, est spécifique au serveur. Lorsque plusieurs options --server-option=<option> sont données, elles sont toutes envoyées à l'autre partie dans l'ordre où elles apparaissent sur la ligne de commande. Lorsqu'aucune option --server-option=<option> n'est donnée depuis la ligne de commande, les valeurs de la variable de configuration remote.<nom>.serverOption sont utilisées à la place.

-n, --no-checkout

Aucun checkout de HEAD n'est effectué après la fin du clonage.

--[no-]reject-shallow

Échoue si le dépôt source est un dépôt peu profond (shallow). La variable de configuration clone.rejectShallow peut être utilisée pour spécifier la valeur par défaut.

--bare

Crée un dépôt Git nu (bare). C'est-à-dire, au lieu de créer <répertoire> et de placer les fichiers administratifs dans <répertoire>/.git, fait du répertoire <répertoire> lui-même le $GIT_DIR. Ceci implique évidemment --no-checkout car il n'y a nulle part où extraire l'arborescence de travail. Les pointeurs de branches du distant sont également copiés directement dans les pointeurs de branches locales correspondants, sans les mapper à refs/remotes/origin/. Lorsque cette option est utilisée, ni les branches de suivi distantes ni les variables de configuration associées ne sont créées.

--sparse

Utilise un checkout dispersé (sparse-checkout), avec uniquement les fichiers dans le répertoire racine initialement présents. La commande git-sparse-checkout(1) peut

être utilisé pour agrandir le répertoire de travail au besoin.

--filter=<spécification-filtre>

Utilisez la fonctionnalité de clonage partiel et demandez au serveur d'envoyer un sous-ensemble d'objets atteignables selon un filtre d'objet donné. Lors de l'utilisation de --filter, la <spécification-filtre> fournie est utilisée pour le filtre de clonage partiel. Par exemple, --filter=blob:none filtrera tous les blobs (contenus de fichiers) jusqu'à ce qu'ils soient nécessaires par Git. De plus, --filter=blob:limit=<taille> filtrera tous les blobs dont la taille est au moins <taille>. Pour plus de détails sur les spécifications de filtre, consultez l'option --filter dans git-rev-list(1).

--also-filter-submodules

Applique également le filtre de clonage partiel à tous les sous-modules du dépôt. Nécessite --filter et --recurse-submodules. Ceci peut être activé par défaut en définissant l'option de configuration clone.filterSubmodules.

--mirror

Configurez un miroir du dépôt source. Cela implique --bare. Comparé à --bare, --mirror ne se contente pas de mapper les branches locales de la source vers les branches locales de la cible, il mappe toutes les références (y compris les branches de suivi à distance, les notes, etc.) et configure une référence de spécification telle que toutes ces références sont écrasées par une commande git remote update dans le dépôt cible.

-o <nom>, --origin <nom>

Au lieu d'utiliser le nom de la référence distante origin pour suivre le dépôt en amont, utilisez <nom>. Remplace clone.defaultRemoteName de la configuration.

-b <nom>, --branch <nom>

Au lieu de pointer le HEAD nouvellement créé vers la branche pointée par le HEAD du dépôt cloné, pointez vers la branche <nom> à la place. Dans un dépôt non nu, c'est la branche qui sera extraite. --branch peut également prendre des tags et détacher le HEAD à ce commit dans le dépôt résultant.

--revision=<rev>

Crée un nouveau dépôt et récupère l'historique menant à la révision donnée <rev> (et rien d'autre), sans créer de branche de suivi à distance, ni de branche locale, et détache le HEAD à <rev>. L'argument peut être un nom de référence (par exemple, refs/heads/main ou refs/tags/v1.0) qui se résout en un commit, ou un nom d'objet hexadécimal. Cette option est incompatible avec --branch et --mirror.

-u <upload-pack>, --upload-pack <upload-pack>

Lorsqu'il est donné, et que le dépôt à cloner est accédé via ssh, cela spécifie un chemin non par défaut pour la commande exécutée à l'autre extrémité.

--template=<répertoire-modèles>

Spécifie le répertoire à partir duquel les modèles seront utilisés ; (Voir la section « RÉPERTOIRE DE MODÈLES » de git-init(1).)

-c <clé>=<valeur>, --config <clé>=<valeur>

Définit une variable de configuration dans le dépôt nouvellement créé ; cela prend effet immédiatement après l'initialisation du dépôt, mais avant que l'historique distant ne soit récupéré ou que les fichiers ne soient extraits. La <clé> est dans le même format qu'attendu par git-config(1) (par exemple, core.eol=true). Si plusieurs valeurs sont données pour la même clé, chaque valeur sera écrite dans le fichier de configuration. Cela permet, par exemple, d'ajouter des spécifications de récupération de références supplémentaires à la référence distante origin.

En raison des limitations de l'implémentation actuelle, certaines variables de configuration ne prennent effet qu'après la récupération et l'extraction initiales. Les variables de configuration dont on sait qu'elles ne prennent pas effet sont : remote.<nom>.mirror et remote.<nom>.tagOpt. Utilisez les options correspondantes --mirror et --no-tags à la place.

--depth <profondeur>

Crée un clone superficiel avec un historique tronqué au nombre spécifié de commits. Implique --single-branch à moins que --no-single-branch ne soit donné pour récupérer les historiques près des extrémités de toutes les branches. Si vous souhaitez cloner les sous-modules superficiellement, passez également --shallow-submodules.

--shallow-since=<date>

Crée un clone superficiel avec un historique postérieur à la date spécifiée.

--shallow-exclude=<ref>

Crée un clone superficiel avec un historique, excluant les commits atteignables à partir d'une branche ou d'un tag distant spécifié. Cette option peut être spécifiée plusieurs fois.

--single-branch, --no-single-branch

Clone uniquement l'historique menant à l'extrémité d'une seule branche, soit spécifiée par l'option --branch, soit la branche principale vers laquelle le HEAD du dépôt distant pointe. Les récupérations ultérieures dans le dépôt résultant ne mettront à jour que la branche de suivi distante pour la branche pour laquelle cette option a été utilisée lors du clonage initial. Si le HEAD à distance ne pointait sur aucune branche lorsque le clone --single-branch a été effectué, aucune branche de suivi distante n'est créée.

--tags, --no-tags

Contrôle si les tags seront clonés ou non. Lorsque --no-tags est donné, l'option devient permanente en définissant la configuration remote.<remote>.tagOpt=--no-tags. Cela garantit que les futurs git pull et git fetch ne suivront aucun tag. Les récupérations de tags explicites ultérieures fonctionneront toujours (voir git-fetch(1)).

Par défaut, les tags sont clonés et passer --tags est donc généralement une opération nulle, sauf si cela annule un précédent --no-tags.

Peut être utilisé conjointement avec --single-branch pour cloner et maintenir une branche sans aucune référence autre qu'une seule branche clonée. Ceci est utile par exemple pour maintenir des clones minimaux de la branche par défaut de certains dépôts pour l'indexation de recherche.

--recurse-submodules[=<pathspec>]

Après la création du clone, initialise et clone les sous-modules en fonction du <pathspec> fourni. Si aucun =<pathspec> n'est fourni, tous les sous-modules sont initialisés et clonés. Cette option peut être donnée plusieurs fois pour des pathspecs composés de plusieurs entrées. Le clone résultant a submodule.active défini sur le pathspec fourni, ou "." (signifiant tous les sous-modules) si aucun pathspec n'est fourni.

Les sous-modules sont initialisés et clonés en utilisant leurs paramètres par défaut. Ceci est équivalent à exécuter git submodule update --init --recursive <pathspec> immédiatement après que le clone soit terminé. Cette option est ignorée si le dépôt cloné n'a pas d'arbre de travail/extraction (c'est-à-dire si --no-checkout/-n, --bare, ou --mirror est donné)

--shallow-submodules, --no-shallow-submodules

Tous les sous-modules qui sont clonés seront superficiels avec une profondeur de 1.

--remote-submodules, --no-remote-submodules

Tous les sous-modules qui sont clonés utiliseront l'état de la branche de suivi distante du sous-module pour mettre à jour le sous-module, plutôt que le SHA-1 enregistré du superprojet. Équivalent à passer --remote à git submodule update.

--separate-git-dir=<git-dir>

Au lieu de placer le dépôt cloné là où il est censé être, placez le dépôt cloné dans le répertoire spécifié, puis créez un lien symbolique Git indépendant du système de fichiers vers celui-ci. Le résultat est que le dépôt Git peut être séparé de l'arbre de travail.

--ref-format=<format-refs>

Spécifie le format de stockage des références donné pour le dépôt. Les valeurs valides sont :
•files pour les fichiers lâches avec refs packed. C'est le défaut.
•reftable pour le format reftable. Ce format est expérimental et ses détails internes sont sujets à changement.

-j <n>, --jobs <n>

Le nombre de sous-modules récupérés simultanément. Par défaut, c'est l'option submodule.fetchJobs.

<dépôt>

Le <dépôt> (éventuellement distant) à cloner. Voir la section URL GIT ci-dessous pour plus d'informations sur la spécification des dépôts.

<répertoire>

Le nom d'un nouveau répertoire dans lequel cloner. La partie "humaine" du dépôt source est utilisée si aucun <répertoire> n'est explicitement donné (repo pour /path/to/repo.git et foo pour host.xz:foo/.git). Le clonage dans un répertoire existant n'est autorisé que si le répertoire est vide.

--bundle-uri=<uri>

Avant de récupérer depuis la référence distante, récupère un bundle depuis l'URI donné <uri> et décompresse les données dans le dépôt local. Les références dans le bundle seront stockées sous l'espace de noms caché refs/bundle/*. Cette option est incompatible avec --depth, --shallow-since et --shallow-exclude.

URLS GIT

En général, les URL contiennent des informations sur le protocole de transport, l'adresse du serveur distant et le chemin vers le dépôt. Selon le protocole de transport, certaines de ces informations peuvent être absentes.

Git prend en charge les protocoles ssh, git, http et https (en outre, ftp et ftps peuvent être utilisés pour la récupération, mais c'est inefficace et déconseillé ; ne les utilisez pas).

Le transport natif (c'est-à-dire une URL git://) n'effectue aucune authentification et doit être utilisé avec prudence sur des réseaux non sécurisés.

Les syntaxes suivantes peuvent être utilisées avec eux :

•ssh://[<utilisateur>@]<hôte>[:<port>]/<chemin-vers-dépôt-git>
•git://<hôte>[:<port>]/<chemin-vers-dépôt-git>
•http[s]://<hôte>[:<port>]/<chemin-vers-dépôt-git>
•ftp[s]://<hôte>[:<port>]/<chemin-vers-dépôt-git>

Une syntaxe alternative de type scp peut également être utilisée avec le protocole ssh :

•[<utilisateur>@]<hôte>:/<chemin-vers-dépôt-git>

Cette syntaxe n'est reconnue que s'il n'y a pas de barres obliques avant le premier deux-points. Cela permet de différencier un chemin local d'unat contient un deux-points. Par exemple, le chemin local foo:bar peut être spécifié comme un chemin absolu ou ./foo:bar pour éviter qu'il soit interprété comme une url ssh.

Les protocoles ssh et git prennent en charge en outre l'expansion ~<username> :

•ssh://[<user>@]<host>[:<port>]/~<user>/<path-to-git-repo>
•git://<host>[:<port>]/~<user>/<path-to-git-repo>
•[<user>@]<host>:~<user>/<path-to-git-repo>

Pour les dépôts locaux, également pris en charge nativement par Git, les syntaxes suivantes peuvent être utilisées :

•/path/to/repo.git/
•file:///path/to/repo.git/

Ces deux syntaxes sont principalement équivalentes, sauf que la première implique l'option --local .

git clone, git fetch et git pull, mais pas git push, accepteront également un fichier bundle approprié. Voir git-bundle(1).

Lorsque Git ne sait pas comment gérer un certain protocole de transport, il tente d'utiliser l'assistant distant remote-<transport> , si celui-ci existe. Pour demander explicitement un assistant distant, la syntaxe suivante peut être utilisée :

•<transport>::<address>

où <address> peut être un chemin, un serveur et un chemin, ou une chaîne de caractères de type URL arbitraire reconnue par l'assistant distant spécifique invoqué. Voir gitremote-helpers(7) pour plus de détails.

S'il existe un grand nombre de dépôts distants portant des noms similaires et que vous souhaitez utiliser un format différent pour ceux-ci (de sorte que les URL que vous utilisez soient réécrites en URL fonctionnelles), vous pouvez créer une section de configuration de la forme :

        [url "<actual-url-base>"]
                insteadOf = <other-url-base>

Par exemple, avec ceci :

        [url "git://git.host.xz/"]
                insteadOf = host.xz:/path/to/
                insteadOf = work:

une URL comme "work:repo.git" ou comme "host.xz:/path/to/repo.git" sera réécrite dans tout contexte qui prend une URL pour être "git://git.host.xz/repo.git".

Si vous souhaitez réécrire les URL uniquement pour le push, vous pouvez créer une section de configuration de la forme :

        [url "<actual-url-base>"]
                pushInsteadOf = <other-url-base>

Par exemple, avec ceci :

        [url "ssh://example.org/"]
                pushInsteadOf = git://example.org/

une URL comme "git://example.org/path/to/repo.git" sera réécrite en "ssh://example.org/path/to/repo.git" pour les push, mais les pull utiliseront toujours l'URL originale.

EXEMPLES

•Cloner depuis l'amont : 
$ git clone git://git.kernel.org/pub/scm/.../linux.git my-linux
$ cd my-linux
$ make
•Créer un clone local empruntant au répertoire courant, sans effectuer de checkout : 
$ git clone -l -s -n . ../copy
$ cd ../copy
$ git show-branch
•Cloner depuis l'amont tout en empruntant à un répertoire local existant : 
$ git clone --reference /git/linux.git \
        git://git.kernel.org/pub/scm/.../linux.git \
        my-linux
$ cd my-linux
•Créer un dépôt nu pour publier vos changements au public : 
$ git clone --bare -l /home/proj/.git /pub/scm/proj.git
•Cloner un dépôt local depuis un utilisateur différent : 
$ git clone --no-local /home/otheruser/proj.git /pub/scm/proj.git

CONFIGURATION

Tout ce qui se trouve sous cette ligne dans cette section est inclus de manière sélective depuis la documentation git-config(1) . Le contenu est le même que celui qui s'y trouve :

init.templateDir

Spécifie le répertoire à partir duquel les modèles seront copiés. (Voir la section "TEMPLATE DIRECTORY" de git-init(1).)

init.defaultBranch

Permet de remplacer le nom de la branche par défaut, par exemple lors de l'initialisation d'un nouveau dépôt.

init.defaultObjectFormat

Permet de remplacer le format d'objet par défaut pour les nouveaux dépôts. Voir --object-format= dans git-init(1). L'option de ligne de commande et la variable d'environnement GIT_DEFAULT_HASH ont la priorité sur cette configuration.

init.defaultRefFormat

Permet de remplacer le format de stockage des refs par défaut pour les nouveaux dépôts. Voir --ref-format= dans git-init(1). L'option de ligne de commande et la variable d'environnement GIT_DEFAULT_REF_FORMAT ont la priorité sur cette configuration.

clone.defaultRemoteName

Le nom du distant à créer lors du clonage d'un dépôt. Par défaut, c'est origin. Cela peut être remplacé en passant l'option de ligne de commande --origin .

clone.rejectShallow

Refuse de cloner un dépôt s'il est peu profond (shallow) ; cela peut être remplacé en passant l'option --reject-shallow sur la ligne de commande.

clone.filterSubmodules

Si un filtre de clonage partiel est fourni (voir --filter dans git-rev-list(1)) et que --recurse-submodules est utilisé, applique également le filtre aux sous-modules.
