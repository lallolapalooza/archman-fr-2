NOM

gitrevisions - Spécification des révisions et des plages pour Git

SYNOPIS

gitrevisions

DESCRIPTION

De nombreuses commandes Git prennent des paramètres de révision en arguments. Selon la commande, ils désignent un commit spécifique ou, pour les commandes qui parcourent le graphe des révisions (comme git-log(1)), tous les commits qui sont atteignables depuis ce commit. Pour les commandes qui parcourent le graphe des révisions, on peut aussi spécifier explicitement une plage de révisions.

De plus, certaines commandes Git (comme git-show(1) et git-push(1)) peuvent également prendre des paramètres de révision qui désignent d'autres objets que des commits, par exemple des blobs (« fichiers ») ou des arbres (« répertoires de fichiers »).

SPÉCIFIER LES RÉVISIONS

Un paramètre de révision <rev> désigne généralement, mais pas nécessairement, un objet commit. Il utilise ce qu'on appelle une syntaxe SHA-1 étendue. Voici diverses façons d'écrire les noms d'objets. Ceux listés vers la fin de cette liste désignent des arbres et des blobs contenus dans un commit.


Note

Ce document montre la syntaxe « brute » telle que vue par git. Le shell et d'autres interfaces utilisateur pourraient nécessiter un guillemet supplémentaire pour protéger les caractères spéciaux et éviter la division des mots.

<sha1>, par exemple dae86e1950b1277e545cee180551750029cfe735, dae86e

Le nom d'objet SHA-1 complet (chaîne hexadécimale de 40 octets), ou une sous-chaîne initiale unique dans le dépôt. Par exemple, dae86e1950b1277e545cee180551750029cfe735 et dae86e désignent tous deux le même objet commit s'il n'y a pas d'autre objet dans votre dépôt dont le nom d'objet commence par dae86e.

<describeOutput>, par exemple v1.7.4.2-679-g3bee7fb

La sortie de git describe ; c'est-à-dire une balise la plus proche, éventuellement suivie d'un tiret et d'un nombre de commits, suivi d'un tiret, d'un g, et d'un nom d'objet abrégé.

<refname>, par exemple master, heads/master, refs/heads/master

Un nom de référence symbolique. Par exemple, master désigne généralement l'objet commit référencé par refs/heads/master. Si vous avez à la fois heads/master et tags/master, vous pouvez explicitement dire heads/master pour indiquer à Git lequel vous voulez. En cas d'ambiguïté, un <refname> est désambiguïsé en prenant la première correspondance dans les règles suivantes :
1.Si $GIT_DIR/<refname> existe, c'est ce que vous voulez (ceci est généralement utile uniquement pour HEAD, FETCH_HEAD, ORIG_HEAD, MERGE_HEAD, REBASE_HEAD, REVERT_HEAD, CHERRY_PICK_HEAD, BISECT_HEAD et AUTO_MERGE) ;
2.sinon, refs/<refname> s'il existe ;
3.sinon, refs/tags/<refname> s'il existe ;
4.sinon, refs/heads/<refname> s'il existe ;
5.sinon, refs/remotes/<refname> s'il existe ;
6.sinon, refs/remotes/<refname>/HEAD s'il existe.

HEAD

désigne le commit sur lequel vous avez basé les modifications dans l'arborescence de travail.

FETCH_HEAD

enregistre la branche que vous avez récupérée d'un dépôt distant lors de votre dernière invocation de git fetch.

ORIG_HEAD

est créé par les commandes qui déplacent votre HEAD de manière drastique (git am, git merge, git rebase, git reset), pour enregistrer la position du HEAD avant leur opération, afin que vous puissiez facilement ramener l'extrémité de la branche à l'état antérieur à leur exécution.

MERGE_HEAD

enregistre le ou les commits que vous fusionnez dans votre branche lorsque vous exécutez git merge.

REBASE_HEAD

pendant un rebase, enregistre le commit où l'opération est actuellement arrêtée, soit à cause de conflits, soit à cause d'une commande edit dans un rebase interactif.

REVERT_HEAD

enregistre le commit que vous annulez lorsque vous exécutez git revert.

CHERRY_PICK_HEAD

enregistre le commit que vous sélectionnez lorsque vous exécutez git cherry-pick.

BISECT_HEAD

enregistre le commit actuel à tester lorsque vous exécutez git bisect --no-checkout.

AUTO_MERGE

enregistre un objet arbre correspondant à l'état que la stratégie de fusion ort a écrit dans l'arborescence de travail lorsqu'une opération de fusion a entraîné des conflits.

Notez que l'un des cas refs/* ci-dessus peut provenir soit du répertoire $GIT_DIR/refs, soit du fichier $GIT_DIR/packed-refs. Bien que l'encodage des noms de référence ne soit pas spécifié, l'UTF-8 est préféré car certains traitements de sortie peuvent supposer que les noms de référence sont en UTF-8.

@

@ seul est un raccourci pour HEAD.

[<refname>]@{<date>}, par exemple master@{yesterday}, HEAD@{5 minutes ago}

Une référence suivie du suffixe @ avec une spécification de date entre accolades (par exemple, {yesterday}, {1 month 2 weeks 3 days 1 hour 1 second ago} ou {1979-02-26 18:30:00}) spécifie la valeur de la référence à un moment antérieur. Ce suffixe ne peut être utilisé immédiatement après un nom de référence et la référence doit avoir un journal existant ($GIT_DIR/logs/<ref>). Notez que cela recherche l'état de votre référence locale à un moment donné ; par exemple, ce qui se trouvait dans votre branche master locale la semaine dernière. Si vous souhaitez examiner les commits effectués pendant certaines périodes, consultez --since et --until.

<refname>@{<n>}, par exemple master@{1}

Une référence suivie du suffixe @ avec une spécification ordinale entre accolades (par exemple, {1}, {15}) spécifie la n-ième valeur antérieure de cette référence. Par exemple, master@{1} est la valeur immédiatement antérieure de master tandis que master@{5} est la 5ème valeur antérieure de master. Ce suffixe ne peut être utilisé immédiatement après un nom de référence et la référence doit avoir un journal existant ($GIT_DIR/logs/<refname>).

@{<n>}, par exemple @{1}

Vous pouvez utiliser la construction @ avec une partie de référence vide pour accéder à une entrée du reflog de la branche actuelle. Par exemple, si vous êtes sur la branche blabla alors @{1} signifie la même chose que blabla@{1}.

@{-<n>}, par exemple @{-1}

La construction @{-<n>} désigne le <n>-ième branche/commit consulté avant le courant.

[<branchname>]@{upstream}, par exemple master@{upstream}, @{u}

Une branche B peut être configurée pour se construire sur une branche X (configurée avec branch.<name>.merge) sur un distant R (configuré avec la branche X prise du distant R, généralement trouvée à refs/remotes/R/X.

[<branchname>]@{push}, par exemple master@{push}, @{push}

Le suffixe @{push} indique la branche « vers laquelle nous pousserions » si git push était exécuté pendant que branchname était sélectionné (ou le HEAD actuel s'il n'y a pas de branchname spécifié). Comme pour @{upstream}, nous indiquons la branche de suivi distant qui correspond à cette branche sur le distant.

Voici un exemple pour clarifier :

$ git config push.default current
$ git config remote.pushdefault myfork
$ git switch -c mybranch origin/master
$ git rev-parse --symbolic-full-name @{upstream}
refs/remotes/origin/master
$ git rev-parse --symbolic-full-name @{push}
refs/remotes/myfork/mybranch

Notez dans l'exemple que nous avons configuré un flux de travail triangulaire, où nous tirons d'un emplacement et poussons vers un autre. Dans un flux de travail non triangulaire, @{push} est identique à @{upstream}, et il n'y a pas besoin de lui.

Ce suffixe est également accepté lorsqu'il est écrit en majuscules, et signifie la même chose quelle que soit la casse.

<rev>^[<n>], par exemple HEAD^, v1.5.1^0

Un suffixe ^ à un paramètre de révision signifie le premier parent de cet objet commit. ^<n> signifie le <n>-ième parent (c'est-à-dire que <rev>^ est équivalent à <rev>^1). Comme règle spéciale, <rev>
;^0 désigne le commit lui-même et est utilisé lorsque <rev> est le nom d'objet d'un objet tag qui pointe vers un objet commit.

<rev>~[<n>], par ex. HEAD~,

master~3
Un suffixe ~ après un paramètre de révision désigne le premier parent de cet objet commit. Un suffixe ~<n> après un paramètre de révision désigne l'objet commit qui est l'ancêtre de <n>e génération de l'objet commit nommé, en suivant uniquement les premiers parents. C'est-à-dire que <rev>~3 est équivalent à <rev>^^^ qui est équivalent à <rev>^1^1^1. Voir ci-dessous une illustration de l'utilisation de cette
forme.

<rev>^{<type>}, par ex. v0.99.

8^{commit}
Un suffixe ^ suivi d'un nom de type d'objet entouré de crochets signifie déréférencer l'objet à <rev> récursivement jusqu'à ce qu'un objet de type <type> soit trouvé ou que l'objet ne puisse plus être déréférencé (auquel cas, erreur). Par exemple, si <rev> est un commit-ish, <rev>^{commit} décrit l'objet commit correspondant. De même, si <rev> est un tree-ish, <rev>^{tree} décrit l'objet tree correspondant. <rev>^0 est un raccourci pour <rev>^{commit}.

<rev>^{object} peut être utilisé pour s'assurer que <rev> nomme un objet qui existe, sans exiger que <rev> soit un tag, et sans déréférencer <rev> ; car un tag est déjà un objet, il n'a pas à être déréférencé même une fois pour obtenir un

objet.

<rev>^{tag} peut être utilisé pour garantir que <rev> identifie un

objet tag
existant.

<rev>^{}, par ex. v0.99.

8^{}
Un suffixe ^ suivi d'une paire de crochets vides signifie que l'objet pourrait être un tag, et déréférencer le tag récursivement jusqu'à ce qu'un objet non-tag soit
trouvé.

<rev>^{/<texte>}, par ex. HEAD^{/fix nasty

bug}
Un suffixe ^ après un paramètre de révision, suivi d'une paire de crochets contenant un texte précédé d'une barre oblique, est identique à la syntaxe :/fix nasty bug ci-dessous, sauf qu'il renvoie le commit correspondant le plus récent qui est atteignable depuis <rev> avant ^
.

:/<texte>, par ex. :/fix nasty

bug
Deux-points, suivis d'une barre oblique, suivis d'un texte, nomme un commit dont le message de commit correspond à l'expression régulière spécifiée. Ce nom renvoie le commit correspondant le plus récent qui est atteignable depuis n'importe quelle référence, y compris HEAD. L'expression régulière peut correspondre à n'importe quelle partie du message de commit. Pour correspondre aux messages commençant par une chaîne, on peut utiliser par ex. :/^foo. La séquence spéciale :/! est réservée pour les modificateurs de ce qui est recherché. :/!-foo effectue une correspondance négative, tandis que :/!!foo correspond à un caractère ! littéral, suivi de foo. Toute autre séquence commençant par :/! est réservée pour le moment. Selon le texte donné, les règles de découpage en mots du shell pourraient nécessiter un guillemetage
supplémentaire.

<rev>:<chemin>, par ex. HEAD:README, master:.

/README
Un suffixe : suivi d'un chemin nomme le blob ou le tree à l'indication donnée dans l'objet tree-ish nommé par la partie avant les deux-points. Un chemin commençant par ./ ou ../ est relatif au répertoire de travail courant. Le chemin donné sera converti pour être relatif au répertoire racine de l'arbre de travail. C'est surtout utile pour adresser un blob ou un tree à partir d'un commit ou d'un tree qui a la même structure d'arbre que l'arbre de
travail.

:[<n>:]<chemin>, par ex. :0:README, :

README
Deux-points, éventuellement suivis d'un numéro d'étage (0 à 3) et de deux-points, suivis d'un chemin, nomme un objet blob dans l'index à l'indication donnée. Un numéro d'étage manquant (et les deux-points qui le suivent) nomme une entrée d'étage 0. Lors d'une fusion, l'étage 1 est l'ancêtre commun, l'étage 2 est la version de la branche cible (généralement la branche courante), et l'étage 3 est la version de la branche qui est
fusionnée.

SPÉCIFICATION DES

INTERVALLES

Les commandes de parcours d'historique telles que git log opèrent sur un ensemble de commits, pas seulement sur un seul

commit.

Pour ces commandes, spécifier une seule révision, en utilisant la notation décrite dans la section précédente, signifie l'ensemble des commits atteignables depuis le commit

donné.

Spécifier plusieurs révisions signifie l'ensemble des commits atteignables depuis n'importe lequel des commits

donnés.

L'ensemble atteignable d'un commit est le commit lui-même et les commits de sa chaîne

d'ancêtres.

Il existe plusieurs notations pour spécifier un ensemble de commits connectés (appelé « intervalle de révisions »), illustrées

ci-dessous.

Exclusions de

commits

Notation ^<rev>

(circonflexe)
Pour exclure des commits atteignables depuis un commit, un préfixe ^ est utilisé. Par ex. ^r1 r2 signifie les commits atteignables depuis r2 mais exclut ceux qui sont atteignables depuis r1 (c'est-à-dire r1 et ses
ancê
tres).

Notations d'intervalle

pointillées

La Notation d'intervalle .. (deux

points)
La opération d'ensemble ^r1 r2 apparaît si souvent qu'il existe un raccourci pour elle. Lorsque vous avez deux commits r1 et r2 (nommés selon la syntaxe expliquée dans SPÉCIFICATION DES RÉVISIONS ci-dessus), vous pouvez demander les commits qui sont atteignables depuis r2 en excluant ceux qui sont atteignables depuis r1 par ^r1 r2 et cela peut être écrit r1..r
2.

La Notation de différence symétrique ... (trois

points)
Une notation similaire r1...r2 est appelée différence symétrique de r1 et r2 et est définie comme r1 r2 --not $(git merge-base --all r1 r2). C'est l'ensemble des commits qui sont atteignables depuis l'un des deux r1 (côté gauche) ou r2 (côté droit) mais pas des
deux.

Dans ces deux notations abrégées, vous pouvez omettre une extrémité et la laisser par défaut à HEAD. Par exemple, origin.. est un raccourci pour origin..HEAD et demande « Qu'ai-je fait depuis que j'ai bifurqué de la branche origin ? » De même, ..origin est un raccourci pour HEAD..origin et demande « Qu'a fait origin depuis que j'ai bifurqué d'eux ? » Notez que .. signifierait HEAD..HEAD qui est un intervalle vide à la fois atteignable et inatteignable depuis

HEAD.

Des commandes spécifiquement conçues pour prendre deux intervalles distincts (par ex. « git range-diff R1 R2 » pour comparer deux intervalles) existent, mais ce sont des exceptions. Sauf mention contraire, toutes les commandes « git » qui opèrent sur un ensemble de commits travaillent sur un seul intervalle de révisions. En d'autres termes, écrire deux « notations d'intervalle à deux points » l'une à côté de l'autre, par

ex. 
$ git log A..B C.
.
D

ne spécifie pas deux intervalles de révisions pour la plupart des commandes. Au lieu de cela, cela nommera un seul ensemble connecté de commits, c'est-à-dire ceux qui sont atteignables depuis B ou D mais qui ne sont atteignables ni depuis A ni depuis C. Dans une histoire linéaire comme celle-ci

:

-
D

parce que A et B sont atteignables depuis C, l'

intervalle de révisions spécifié par ces de
ux intervalles pointillés est un seul commit D.

Autres notations abrégées <rev>^ de

parent

Trois autres raccourcis existent, particulièrement utiles pour les commits de fusion, pour nommer un ensemble formé par un commit et ses commits

parents.

La notation r1^@ signifie tous les parents de r1

.

La notation r1^! inclut le commit r1 mais exclut tous ses parents. À elle seule, cette notation désigne le seul commit r1

.

La notation <rev>^-[<n>] inclut <rev> mais exclut le <n>e parent (c'est-à-dire un raccourci pour <rev>^<n>..<rev>), avec <n> = 1 si non donné. C'est généralement utile pour les commits de fusion où vous pouvez simplement passer <commit>^- pour obtenir tous les commits de la branche qui a été fusionnée dans le commit de fusion <commit> (y compris <commit> lui-même)

.

Alors que <rev>^<n> concernait la spécification d'un seul parent de commit, ces trois notations considèrent aussi ses parents. Par exemple, vous pouvez dire HEAD^2^@, cependant vous ne pouvez pas dire HEAD

^
@^
2.

RÉSUMÉ DES INTERVALLES DE

RÉVISIONS

<rev

>
Inclure les commits qui sont atteignables depuis <rev> (c'est-à-dire <rev> et ses ancêtres)
.

^<rev

>
Exclure les commits qui sont atteignables depuis <rev> (c'est-à-dire <rev> et ses ancêtres)
.

<rev1>..

<rev2>
Inclure les commits qui sont atteignables depuis <rev2> mais exclure ceux qui sont atteignables depuis <rev1>. Lorsque <rev1> ou <rev2> est omis, la valeur par défaut est HEAD
.

<rev1>...

<rev2>
Inclure les commits qui sont atteignables depuis <rev1> ou <rev2> mais exclure ceux qui sont atteignables depuis les deux. Lorsque <rev1> ou <rev2> est omis, la valeur par défaut est HEAD
.

<rev>^@, par ex. HEAD^

@
Un suffixe ^ suivi d'un arobase est identique à lister tous les parents de <rev> (c'est-à-dire, inclure tout ce qui est atteignable depuis ses parents, mais pas le commit lui-même)
.

<rev>^!, par ex. HEAD^

!
Un suffixe ^ suivi d'un point d'exclamation est identique à donner le commit <rev> et tous ses parents préfixés avec ^ pour les exclure (et leurs ancêtres)
.

<rev>^-<n>, par ex. HEAD^-,

HEAD^-2
Équivalent à <rev>^<n>..<rev>, avec <n> = 1 si non
donné.
