DESCRIPTIO

N

Cette commande simule le comportement de git-annex dans un réseau de dépôts, déterminant quels fichiers atteindraient quels dépôts selon la configuration du contenu préféré, numcopies, niveau de confiance,

etc.

L'entrée de la simulation est un fichier sim, et/ou des commandes sim qui sont exécutées après son démarrage. Celles-ci prennent la forme de "git annex sim command" avec la commande au même format utilisé dans le fichier sim (voir la liste des commandes sim ci-dessous). Par exemple, "git annex sim step 1" fait avancer la simulation d'un

pas.

La simulation conserve un journal pendant son exécution, qui contient l'ensemble des entrées de la simulation, ainsi que les actions effectuées dans la simulation et les résultats de la simulation. Utilisez "git-annex sim show" pour afficher le journal. Cela permet de relancer la même simulation ultérieurement, ainsi que d'analyser les résultats de la

simulation.

Utilisez "git annex sim end" pour terminer la simulation et

nettoyer.

Par commodité, pour exécuter une simulation depuis un fichier, puis l'arrêter, utilisez "git-annex sim run". S'il y a un problème lors de l'exécution de la simulation, il sera affiché avant qu'elle ne soit

arrêtée.

Notez que l'interruption de cette commande pendant son exécution peut laisser la simulation dans un é

tat incohérent. De même, l'exécution de plusieurs commandes sim en même temps peut causer des problè
mes, bien qu'il soit sûr d'exécuter "git annex sim visit" pendant l'exécution d'autres commandes sim.

LE FICHIER

SIM

Ce fichier texte est utilisé pour configurer la simulation et aussi pour rendre compte des résultats de la simulation. Chaque ligne prend la forme d'une commande suivie des paramètres de la commande. Les lignes commençant par "#" ou "--" sont des

commentaires.

Voici un exemple de fichier sim

:


# ajouter des dépôts à la simulation et les connecter en tant que distants
init foo
init bar
connect foo <->

bar


# ajouter un distant spécial
initremote baz
connect foo -> baz <-

bar


# configurer les dépôts
numcopies 2
group foo client
wanted foo standard
group bar archive
wanted bar standard
wanted baz include=*.

mp3


# ajouter les fichiers annexés de l'arbre de travail à la simulation, comme s'ils
# venaient d'être ajoutés au dépôt foo
addtree foo include=*.mp3
addtree foo include=*.jpg
addtree foo include=bigfiles

/


# ajouter des fichiers annexés simulés
add bigfile 100gb bar
add hugefile 10tb

foo


# faire avancer la simulation de dix pas
step

10


# retirer le distant bar de foo et voir si un nouveau fichier ajouté à foo atteint bar
disconnect foo -> bar
add foo.mp3 2mb foo
st

ep
5

COMMANDES

SIM

Voici l'ensemble complet des commandes qui peuvent être utilisées dans le fichier sim ainsi que passées à "git annex sim" pendant qu'une simulation est en

cours.
init
name
Initialiser un dépôt simulé, en lui donnant un nom qui sera utilisé dans la
simulation.
initremote
name
Initialiser un distant spécial
simulé.
use name here|remote|description|u
uid
Utiliser un dépôt existant dans la simulation, avec sa configuration existante (niveau de confiance, groupes, contenu préféré et requis, maxsize, et la configuration groupwanted de ses groupes)
.
Le dépôt reçoit un nom aux fins de la simulation. Le dépôt à utiliser peut être spécifié par nom de distant, uuid, etc. Exemple : "use myrepo
here"
visit repo
[command]
Exécute la commande shell spécifiée à l'intérieur du dépôt simulé et attend sa
fin.
Lorsqu'aucune commande shell n'est spécifiée, elle lance un shell
interactif.
La commande est exécutée dans un dépôt git dont la branche git-annex contient l'état de ce dépôt simulé. Cela permet d'exécuter n'importe quelles commandes git-annex, comme git-annex whereis pour examiner l'état de la simulation. Vous devriez éviter de faire des changements à l'état de
git-annex.
connect repo [<-|->|<->] repo [.
..]
Ajouter une connexion entre deux dépôts ou plus. La flèche indique dans quelle direction la connexion s'établit, et elle peut être bidirectionnelle. Par exemple, "connect foo -> bar" fait de bar un distant de foo, tandis que "connect foo <-> bar" fait de chacun le distant de l'autre. Une chaîne de connexions peut s'étendre à de nombreux dépôts, par ex. "connect foo -> bar -> baz ->
foo"
disconnect repo [<-|->|<->] repo [.
..]
Supprime les connexions entre
dépôts.
Par exemple, "disconnect foo -> bar" fait que foo n'a plus bar comme
distant.
addtree repo
expression
Ajoute des fichiers annexés du dépôt git à la simulation, les rendant présents dans le dépôt
spécifié.
L'expression est une expression de contenu préféré (voir git-annex-preferred-content(1)) spécifiant quels fichiers annexés ajouter. Bien qu'il soit possible d'inclure tous les fichiers ou un grand nombre de fichiers de cette façon, notez qu'il est souvent plus efficace de simuler une petite quantité de fichiers ayant les propriétés particulières qui vous
intéressent.
Lorsqu'elle est exécutée dans un sous-répertoire du dépôt, seuls les fichiers de ce sous-répertoire sont pris en compte pour
l'ajout.
Cela peut être utilisé plusieurs fois avec les mêmes fichiers, pour faire en sorte que plusieurs dépôts dans la simulation contiennent les mêmes
fichiers.
add filename size repo [repo .
..]
Créer un fichier annexé simulé avec le nom de fichier et la taille spécifiés, qui est présent dans le dépôt spécifié, ou
dépôts.
La taille peut être spécifiée en utilisant n'importe quelles unités habituelles, par ex. "10mb" ou "3.
3terabytes"
Le nom de fichier ne peut pas contenir
d'espace.
Cela met en index un fichier, de sorte que les commandes git-annex habituelles peuvent être utilisées pour interroger l'état du fichier annexé simulé. S'il existe déjà un fichier annexé portant ce nom, il sera écrasé avec le nouveau
fichier.
Notez que la simulation ne couvre pas l'ajout de fichiers en conflit à différents dépôts. Les fichiers dans la simulation sont les mêmes dans tous les dépôts
simulés.
addmulti N suffix minsize maxsize repo [repo .
..]
Ajouter plusieurs fichiers annexés simulés, avec des tailles aléatoires dans la plage entre minsize et
maxsize.
Les fichiers sont nommés en combinant le nombre, qui commence à 1 et va jusqu'à N, avec le
suffixe.
Par exemple
:

addmulti 100 testfile.jpg 100kb 10mb
foo
Cela ajoute des fichiers nommés "1testfile.jpg", "2testfile.jpg",
etc.
Notez que l'ajout d'un grand nombre de fichiers à la simulation peut la ralentir et lui faire utiliser beaucoup de
mémoire.
step
N
Faire avancer la simulation de ce nombre de
pas.
À chaque pas de la simulation, un fichier est soit transféré, soit supprimé, selon le contenu préféré et les autres
configurations.
S'il n'y a plus de fichiers pouvant être transférés ou supprimés selon la configuration actuelle, un message sera affiché pour indiquer que la simulation s'est
stabilisée.
Cela simule également l'exécution de git pull et git push dans chaque dépôt, si nécessaire pour trouver d'autres choses à
faire.
stepstable
N
Faire avancer la simulation de ce nombre de pas, à partir desquels elle devrait s'être
stabilisée.
Si la simulation ne se stabilise pas, la commande se terminera avec un état de sortie non
nul.
action repo getwanted
remote
Simule le dépôt obtenant les fichiers qu'il souhaite depuis le
remote.
action repo
dropunwanted
Simule le dépôt supprimant les fichiers qu'il ne souhaite pas, lorsqu'il est en mesure de vérifier qu'il existe suffisamment de copies sur les
remotes.
action repo dropunwantedfrom
remote
Simule le dépôt supprimant depuis le remote les fichiers que le remote ne souhaite pas, lorsqu'il est en mesure de vérifier qu'il existe suffisamment de
copies.
action repo sendwanted
remote
Simule le dépôt envoyant au remote les fichiers que celui-ci
souhaite.
action repo gitpush
remote
Simule le dépôt poussant la branche git-annex vers le
remote.
action repo gitpull
remote
Simule le dépôt tirant la branche git-annex depuis le
remote.
action repo pull
remote
Simule l'équivalent de git-annex-pull(1), en combinant les actions gitpull, getwanted et
dropunwanted.
action repo push
remote
Simule l'équivalent de git-annex-push(1) en combinant les actions sendwanted, dropunwantedfrom et
gitpush.
action repo sync
remote
Simule l'équivalent de git-annex-sync(1) en combinant les actions gitpull, getwanted, sendwanted, dropunwanted et
gitpush.
action [...] while action [.
..]
Simule l'exécution des deux actions de manière concurrente. Bien que la simulation ne simule en réalité qu'une seule chose à la fois, lorsque les actions opèrent chacune sur plusieurs fichiers, elles seront entrelacées
aléatoirement.
Un nombre quelconque d'actions peut être combiné de cette
manière.
Par exemple
:

action foo dropunwanted while action bar getwanted
foo
Dans cet exemple, bar peut ou non obtenir un fichier avant que foo ne le
supprime.
seed
N
Définit la graine aléatoire à un nombre donné. L'utilisation de cette option devrait rendre les résultats de la simulation déterministes. Le fichier sim de sortie contient toujours la graine aléatoire, afin qu'il puisse être utilisé pour rejouer la
simulation.
present repo
file
Cela indique l'état attendu de la simulation à ce point. Le dépôt devrait contenir le contenu du fichier. S'il ne le fait pas, la divergence sera indiquée sur la sortie d'erreur standard, et la commande git-annex sim finira par se terminer avec un code de sortie non
nul.
Ceci est ajouté au fichier sim de sortie au fur et à mesure que la simulation
s'exécute.
notpresent repo
file
Cela indique l'état attendu de la simulation à ce point. Le dépôt ne devrait pas contenir le contenu du fichier. S'il le contient, la divergence sera indiquée sur la sortie d'erreur standard, et la commande git-annex sim finira par se terminer avec un code de sortie non
nul.
Ceci est ajouté au fichier sim de sortie au fur et à mesure que la simulation
s'exécute.
numcopies
N
Définit le nombre de copies souhaité. C'est l'équivalent de git-annex-numcopies(1)
.
Notez que les autres configurations qui définissent numcopies, comme les fichiers .gitattributes, ne sont pas utilisées par la
simulation.
mincopies
N
Définit le nombre minimum de copies. C'est l'équivalent de git-annex-mincopies(1)
.
trustlevel repo trusted|untrusted|semitrusted|d
ead
Définit le niveau de confiance du dépôt. C'est l'équivalent de git-annex-trust(1), git-annex-untrust(1),
etc.
wanted repo
expression
Configure le contenu préféré d'un dépôt. C'est l'équivalent de git-annex-wanted(1)
.
required repo
expression
Configure le contenu requis d'un dépôt. C'est l'équivalent de git-annex-required(1)
.
groupwanted group
expression
Configure l'expression groupwanted. C'est l'équivalent de git-annex-groupwanted(1)
.
randomwanted repo term.
..
Configure le contenu préféré d'un dépôt avec une expression aléatoire générée en combinant une sélection aléatoire des termes fournis avec « and », « or » et « not
».
Par exemple, « randomwanted foo exclude=*.x include=*.x largerthan=100kb » pourrait générer l'expression « exclude=*.x or not largerthan=100kb and include=*.x » ou elle pourrait générer l'expression « include=*.x and exclude=*.
x »
randomrequired repo term.
..
Configure le contenu requis d'un dépôt avec une expression
aléatoire.
randomgroupwanted group term.
..
Configure le groupwanted avec une expression
aléatoire.
group repo
group
Ajoute un dépôt à un groupe. C'est l'équivalent de git-annex-group(1)
.
ungroup repo
group
Retire un dépôt d'un groupe. C'est l'équivalent de git-annex-ungroup(1)
.
metadata filename
expression
Modifie les métadonnées du fichier simulé. L'expression est au même format que l'option --set de la commande git-annex-metadata. Par exemple : metadata foo
year=2025
maxsize repo
size
Configure la taille maximale d'un dépôt. C'est l'équivalent de git-annex-maxsize(1)
.
rebalance
[on|off]
Définir « rebalance on » est l'équivalent de passer l'option --rebalance à git-annex. Définir « rebalance off » annule
cela.
Par exemple
:

maxsize foo 1tb
rebalance on
step 100
rebalance
off
clusternode name
repo
Simule un dépôt étant un nœud d'un cluster, qui peut être référencé en utilisant le nom
spécifié.
Plutôt que de simuler une passerelle de cluster comme une entité séparée, toute connexion à un nœud de cluster portant ce nom est traitée comme l'accès à ce dépôt via la même passerelle de
cluster.
Étant donné qu'une passerelle de cluster connaît toutes les modifications apportées aux nœuds via celle-ci, chaque dépôt ayant une connexion à un nœud de cluster connaîtra immédiatement les modifications apportées via ce nœud, sans avoir besoin d'un git pull
simulé.
Pour simuler un dépôt étant un nœud de plu
s d'un cluster, ou derrière plusieurs pass
erelles dans le même cluster, utilisez cett
e commande pour lui donner plusieurs noms.
