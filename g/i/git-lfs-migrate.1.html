NOM

git-lfs-migrate - Migrer l'historique vers ou depuis Git LFS

SYNTAXE

git lfs migrate <mode> [options] [--] [branche ...]

DESCRIPTION

Convertit les fichiers d'un dépôt Git en pointeurs Git LFS ou inversement, ou résume la taille des fichiers Git par type de fichier. Le mode import convertit les fichiers Git (c'est-à-dire les blobs) en Git LFS, tandis que le mode export fait l'inverse, et le mode info fournit un résumé informatif qui peut être utile pour décider quels fichiers importer ou exporter.

Dans tous les modes, par défaut git lfs migrate opère uniquement sur la branche actuellement clonée, et uniquement sur les fichiers (de toute taille et type) ajoutés dans des commits qui n'existent sur aucune branche distante. Plusieurs options sont disponibles pour outrepasser ces valeurs par défaut.

Lors de la conversion de fichiers vers ou depuis Git LFS, la commande git lfs migrate n'effectuera des modifications que sur votre dépôt local et votre copie de travail, jamais sur les dépôts distants. Ceci est intentionnel car les modes import et export sont généralement « destructeurs » dans le sens où ils réécrivent l'historique de votre Git, modifiant les commits et générant de nouveaux SHA de commit. (L'exception est le sous-mode d'importation « sans réécriture » ; voir IMPORTATION SANS RÉÉCRITURE D'HISTORIQUE pour plus de détails.)

Vous devriez donc toujours d'abord commiter ou stasher tout travail non commité avant d'utiliser les modes import ou export, puis valider le résultat de la migration avant de pousser les modifications vers vos dépôts distants, par exemple en exécutant le mode info et en examinant votre historique de commits réécrit.

Une fois que vous êtes satisfait des modifications, vous devrez forcer la mise à jour de l'historique Git de toutes les branches réécrites vers tous vos dépôts distants. C'est une étape qui doit être effectuée avec précaution, car vous allez modifier l'historique Git sur vos dépôts distants.

Pour examiner ou modifier des fichiers dans des branches autres que celle actuellement clonée, les références de branche peuvent être spécifiées directement, ou fournies dans une ou plusieurs options --include-ref. Elles peuvent également être exclues en les préfixant avec ^ ou en les fournissant dans des options --exclude-ref. Utilisez l'option --everything pour spécifier que toutes les références doivent être examinées, y compris toutes les références distantes. Voir RÉFÉRENCES INCLUSES ET EXCLUES pour plus de détails.

Pour les modes info et import, tous les types de fichiers sont considérés par défaut ; bien qu'utile en mode info, ce n'est souvent pas souhaitable lors de l'importation, donc soit des modèles de noms de fichiers (pathspecs) soit l'option --fixup devraient normalement être spécifiés dans ce cas. (Au moins un pathspec d'inclusion est requis pour le mode export.) Les pathspecs peuvent être définis à l'aide des options --include et --exclude (respectivement -I et -X pour les versions courtes), comme décrit dans INCLUSION ET EXCLUSION.

Comme l'utilisation typique de Git LFS dépend du suivi de types de fichiers spécifiques à l'aide de modèles de noms de fichiers définis dans des fichiers .gitattributes, la commande git lfs migrate examinera, créera et modifiera les fichiers .gitattributes si nécessaire. Les fichiers .gitattributes recevront toujours le mode d'autorisation de lecture/écriture par défaut (c'est-à-dire sans permissions d'exécution). Tout lien symbolique portant ce nom provoquera l'arrêt prématuré de la migration.

Le mode import (voir IMPORTATION) convertira les objets Git des types de fichiers spécifiés (par exemple, avec --include) en pointeurs Git LFS, et ajoutera des entrées pour ces types de fichiers aux fichiers .gitattributes, créant ces fichiers s'ils n'existent pas. Le résultat devrait être comme si les commandes git lfs track avaient été exécutées aux points de l'historique Git correspondant à l'apparition de chaque type de fichier converti. L'exception est si l'option --fixup est donnée, auquel cas le mode import examinera uniquement les fichiers .gitattributes existants, puis convertira les objets Git qui devraient être suivis par Git LFS mais ne le sont pas encore.

Le mode export (voir EXPORTATION) fonctionne comme l'opération inverse du mode import, convertissant tous les pointeurs Git LFS qui correspondent aux types de fichiers spécifiés avec --include, qui doit être spécifié au moins une fois. Notez que les entrées .gitattributes ne seront pas supprimées, ni les fichiers ; au lieu de cela, le mode export insère des entrées « ne pas suivre » similaires à celles créées par la commande git lfs untrack. L'option --remote est disponible en mode export pour spécifier le dépôt distant depuis lequel les objets Git LFS doivent être récupérés s'ils n'existent pas dans le cache local d'objets Git LFS ; si elle n'est pas fournie, origin est utilisé par défaut.

Le mode info (voir INFORMATIONS) résume par type de fichier (c'est-à-dire par extension de nom de fichier) le nombre total et la taille des fichiers dans un dépôt. Notez que, comme les deux autres modes, par défaut le mode info opère uniquement sur la branche actuellement clonée et uniquement sur les commits qui n'existent sur aucune branche distante, donc pour obtenir un résumé de l'ensemble du dépôt sur toutes les branches, utilisez l'option --everything. Si des objets ont déjà été convertis en pointeurs Git LFS, alors par défaut la taille des objets référencés est totalisée et rapportée séparément. Vous pouvez également choisir de les ignorer en utilisant --pointers=ignore ou de traiter les pointeurs comme des fichiers en utilisant --pointers=no-follow. (Cette dernière option est similaire à la manière dont les pointeurs Git LFS existants étaient gérés par le mode info dans les versions antérieures de Git LFS).

Lorsque vous utilisez l'option --everything, notez qu'elle signifie que tous les commits accessibles depuis toutes les références (locales et distantes) seront considérés, mais pas nécessairement tous les types de fichiers. Les modes import et info considèrent tous les types de fichiers par défaut, bien que les options --include et --exclude restreignent ce comportement.

Alors que l'option --everything signifie que tous les commits accessibles depuis n'importe quelle référence seront pris en compte pour la migration, après la migration seules les références locales seront mises à jour même lorsque --everything est spécifié. Cela garantit que les références distantes restent synchronisées avec leurs homologues distants. En d'autres termes, refs/heads/foo sera mis à jour avec l'option --everything, mais refs/remotes/origin/foo ne le sera pas, afin qu'elle reste synchronisée avec le dépôt distant jusqu'à ce que git push origin foo soit effectué. Après avoir vérifié que les résultats d'une migration avec --everything sont satisfaisants, il peut être pratique de pousser toutes les branches locales vers vos dépôts distants en utilisant l'option --all de git push.

Sauf si l'option --skip-fetch est fournie, git lfs migrate commence toujours par récupérer les listes de références mises à jour de tous les dépôts distants renvoyés par git remote, mais comme noté ci-dessus, après avoir apporté des modifications à votre historique Git lors de la conversion d'objets, il ne poussera jamais automatiquement ces modifications vers vos dépôts distants.

MODES

info

Afficher des informations sur la taille du dépôt. Voir INFORMATIONS.

import

Convertir les objets Git en pointeurs Git LFS. Voir IMPORTATION et IMPORTATION SANS RÉÉCRITURE D'HISTORIQUE.

export

Convertir les pointeurs Git LFS en objets Git. Voir EXPORTATION.

--skip-fetch


Suppose que l'ensemble connu des références distantes est complet, et ne doit pas être rafraîchi lors de la détermination de l'ensemble des commits « non poussés » à migrer. N'a aucun effet lorsqu'il est combiné avec --include-ref ou --exclude-ref.

--everything

Voir REFERENCES À INCLURE ET EXCLURE.

Note : Les références Git sont « sensibles à la casse » sur toutes les plateformes dans « packed from » (voir git-pack-refs(1)). Sur les systèmes de fichiers « insensibles à la casse », par exemple NTFS sous Windows ou APFS par défaut sous macOS, git-lfs-migrate(1) ne migrera que la première référence si deux références ou plus sont égales sauf pour les lettres majuscules/minuscules.

--yes

Suppose une réponse oui à toute demande, permettant une utilisation non interactive. Actuellement, la seule demande de ce type est celle demandant s'il faut écraser (détruire) les modifications dans la copie de travail. Ainsi, spécifier cette option peut entraîner une perte de données si vous ne faites pas attention.

[branch ...]

Migrer uniquement l'ensemble des branches listées. Si non fourni, git-lfs-migrate(1) migrera la branche actuellement vérifiée.

Les références commençant par ^ seront exclues, tandis que les branches qui ne commencent pas par ^ seront incluses.

Si --include-ref ou --exclude-ref est donné, la branche vérifiée ne sera pas ajoutée, mais les branches données explicitement le seront.

INFO

Le mode info résume les tailles des objets de fichiers présents dans l'historique Git. Il prend en charge toutes les options de base de migrate et les options supplémentaires suivantes :

--above=<size>

Ne compter que les fichiers dont la taille individuelle est supérieure à la taille donnée. La taille peut être spécifiée en nombre d'octets, ou en nombre suivi d'une unité de stockage, par exemple « 1b », « 20 Mo », « 3 To », etc.

Si un ensemble de fichiers partageant une extension commune ne contient aucun fichier dont la taille individuelle est supérieure à la valeur donnée par --above, aucune entrée pour cet ensemble ne sera affichée.

--top=<n>

Afficher uniquement les n premières entrées, triées selon le nombre total de fichiers correspondant au spec de chemin donné. Par défaut, seules les 5 premières entrées sont affichées. Lorsque des objets Git LFS existants sont trouvés, une ligne « Objets LFS » supplémentaire et distincte est générée en plus des n premières entrées, sauf si l'option --pointers est utilisée pour modifier ce comportement.

--unit=<unit>

Formater le nombre d'octets dans chaque entrée comme une quantité de l'unité de stockage fournie. Les unités valides incluent : * b, KiB, MiB, GiB, TiB, PiB - pour les unités de stockage IEC * o, Ko, Mo, Go, To, Po - pour les unités de stockage SI

Si aucune --unit n'est spécifiée, la plus grande unité qui peut contenir le nombre d'octets comptés comme une quantité entière est choisie.

--pointers=[follow|no-follow|ignore]

Traiter les pointeurs Git LFS existants dans l'historique selon l'une des trois alternatives. Dans le cas par défaut follow, si des pointeurs sont trouvés, un élément de ligne « Objets LFS » supplémentaire et distinct est généré, résumant le nombre total et la taille des objets Git LFS référencés par les pointeurs. Dans le cas ignore, les pointeurs sont simplement ignorés, tandis que le cas no-follow reproduit le comportement du mode info dans les anciennes versions de Git LFS et traite les pointeurs trouvés comme s'il s'agissait de fichiers ordinaires, de sorte que les totaux de sortie n'incluent que le contenu des pointeurs, pas le contenu des objets auxquels ils font référence.

--fixup

Déduire les filtres --include et --exclude par commit en fonction des fichiers .gitattributes dans un dépôt. En pratique, cette option compte tous les chemins de fichiers qui devraient être suivis par Git LFS conformément au(x) fichier(s) .gitattributes du dépôt, mais qui ne sont pas encore des pointeurs. Les fichiers .gitattributes ne sont pas signalés, contrairement à la sortie normale du mode info. Cette option est incompatible avec les filtres --include et --exclude explicitement donnés et avec tout réglage de --pointers autre que ignore, par conséquent --fixup implique --pointers=ignore s'il n'est pas explicitement défini.

Le format de la sortie montre le modèle de nom de fichier, la taille totale des objets de fichier (à l'exclusion de ceux en dessous du seuil --above, s'il y en a un), et le ratio du nombre de fichiers au-dessus du seuil par rapport au nombre total de fichiers ; ce ratio est également affiché en pourcentage. Par exemple :

*.gif               93 Mo   9480/10504 fichiers    90%
*.png               14 Mo    1732/1877 fichiers    92%

Par défaut, seules les cinq premières entrées sont affichées, mais --top permet de générer plus ou moins de sorties selon les besoins.

IMPORT

Le mode import migre les objets présents dans l'historique Git vers des fichiers pointeurs suivis et stockés avec Git LFS. Il prend en charge toutes les options de base de migrate et les options supplémentaires suivantes :

--verbose

Imprimer l'identifiant de commit et le nom de fichier des fichiers migrés sur STDOUT.

--above=<size>

Ne migrer que les fichiers dont la taille individuelle est supérieure à la taille donnée. La taille peut être spécifiée en nombre d'octets, ou en nombre suivi d'une unité de stockage, par exemple « 1b », « 20 Mo », « 3 To », etc. Cette option ne peut pas être utilisée avec les options --include, --exclude et --fixup.

--object-map=<path>

Écrire dans path un fichier avec le mappage de chaque commit réécrit. Le format du fichier est CSV avec le modèle suivant : ANCIEN-SHA,NOUVEAU-SHA

--no-rewrite

Migrer les objets vers Git LFS dans un nouveau commit sans réécrire l'historique Git. Veuillez noter que lorsque cette option est utilisée, la commande migrate import attendra une liste d'arguments différente, des options spécialisées deviendront disponibles, et les options de base de migrate seront ignorées. Voir IMPORT SANS RÉÉCRITURE DE L'HISTORIQUE.

--fixup

Déduire les filtres --include et --exclude par commit en fonction des fichiers .gitattributes dans un dépôt. En pratique, cette option importe tous les chemins de fichiers qui devraient être suivis par Git LFS conformément au(x) fichier(s) .gitattributes du dépôt, mais qui ne sont pas encore des pointeurs. Cette option est incompatible avec les filtres --include et --exclude explicitement donnés.

Si --no-rewrite n'est pas fourni et si --include ou --exclude (-I, -X, respectivement) sont donnés, le fichier .gitattributes sera modifié pour inclure tout nouveau modèle de chemin donné par ces indicateurs.

Si --no-rewrite n'est pas fourni et si aucun de ces indicateurs n'est donné, le fichier gitattributes sera modifié de manière incrémentielle pour inclure les nouvelles extensions de chemin au fur et à mesure qu'elles sont réécrites dans l'historique.

IMPORT SANS RÉÉCRITURE DE L'HISTORIQUE

Le mode import possède un sous-mode spécial activé par l'indicateur --no-rewrite. Ce sous-mode migrera les objets vers des pointeurs comme dans le mode import de base, mais le fera dans un nouveau commit sans réécrire l'historique Git. Lors de l'utilisation de ce sous-mode, les options de base de migrate, telles que --include-ref, seront ignorées, tout comme celles du mode import de base. La commande migrate prendra également une liste d'arguments différente. En conséquence de ces changements, --no-rewrite n'opérera que sur la branche actuelle - toute autre branche intéressée devra fusionner le commit généré. Les options migrate de base seront ignorées, ainsi que celles du mode import de base. La commande migrate prendra également une liste d'arguments différente.

Le sous-mode --no-rewrite prend en charge les options et arguments suivants :

-m <message>, --message=<message>

Spécifie un message de commit pour le nouveau commit créé.

[file ...]

La liste des fichiers à importer. Ces fichiers doivent être suivis par les modèles spécifiés dans les gitattributes.

Si --message est donné, le nouveau commit sera créé avec le message fourni. Si aucun message n'est donné, un message de commit sera généré en fonction des arguments de fichier.

EXPORT

Le mode export migre les fichiers pointeurs Git LFS présents dans l'historique Git hors de Git LFS, en les convertissant en leurs fichiers objets correspondants. Il prend en charge toutes les options de base de migrate et les options supplémentaires suivantes :

--verbose

Imprimer l'identifiant de commit et le nom de fichier des fichiers migrés sur STDOUT.

--object-map=<path>

Écrire dans path un fichier avec le mappage de chaque commit réécrit. Le format du fichier est CSV avec le modèle suivant : ANCIEN-SHA,NOUVEAU-SHA

--remote=<git-remote>

Télécharger les objets LFS depuis le git-remote fourni pendant l'export. S'il n'est pas fourni, utilise par défaut origine.

Le mode export nécessite au minimum un modèle fourni avec l'argument --include pour spécifier quels fichiers exporter. Les fichiers correspondant aux modèles --include seront supprimés de Git LFS, tandis que les fichiers correspondant aux modèles --exclude conserveront leur statut Git LFS. La commande export modifiera le fichier .gitattributes pour définir/annuler tout modèle de chemin de fichier comme indiqué par ces drapeaux.

INCLUDE ET EXCLUDE

Vous pouvez spécifier que git lfs migrate ne doit convertir que les fichiers dont le pathspec correspond aux modèles glob --include et ne correspond pas aux modèles glob --exclude, soit pour réduire le temps total de migration, soit pour ne migrer qu'une partie de votre dépôt. Plusieurs modèles peuvent être spécifiés en utilisant des virgules comme délimiteurs.

La mise en correspondance des modèles se fait de manière fonctionnellement équivalente au format de mise en correspondance des modèles de .gitattributes. En plus des correspondances simples d'extensions de fichiers (par exemple, .gif), les modèles peuvent également spécifier des chemins de répertoire, auquel cas le format chemin/* peut être utilisé pour une correspondance récursive.

Notez que cette forme de mise en correspondance de modèles pour les options --include et --exclude utilisées par la commande git lfs migrate est unique parmi la suite des commandes git lfs. D'autres commandes qui prennent également ces options, comme git lfs ls-files, utilisent plutôt la forme de mise en correspondance de modèles de gitignore(5).

REFERENCES INCLUDE ET EXCLUDE

Vous pouvez spécifier que git lfs migrate ne doit convertir que les fichiers ajoutés dans les commits accessibles depuis certaines références, à savoir celles définies à l'aide d'une ou plusieurs options --include-ref, et doit ignorer les fichiers dans les commits accessibles depuis les références définies dans les options --exclude-ref.

        D---E---F
       /         \
  A---B------C    refs/heads/my-feature
   \          \
    \          refs/heads/main
     \
      refs/remotes/origin/main

Dans la configuration ci-dessus, les commits suivants sont accessibles par chaque ref :

refs/heads/main:           C, B, A
refs/heads/my-feature:     F, E, D, B, A
refs/remote/origin/main:   A

Les options git lfs migrate suivantes incluraient donc les commits F, E, D, C et B, mais excluraient le commit A :

  --include-ref=refs/heads/my-feature
  --include-ref=refs/heads/main
  --exclude-ref=refs/remotes/origin/main

La présence du drapeau --everything indique que tous les commits accessibles depuis toutes les références locales et distantes doivent être migrés (mais notez que les références distantes elles-mêmes ne seront pas mises à jour).

EXEMPLES

Migrer les commits non poussés

Une utilisation courante de la commande migrate est de convertir de gros objets Git en LFS avant de pousser vos commits. Par défaut, elle ne scanne que les commits qui n'existent sur aucun distant, tant que le dépôt n'est pas nu.

Tout d'abord, exécutez git lfs migrate info pour lister les types de fichiers qui occupent le plus d'espace dans votre dépôt :

$ git lfs migrate info
Fetching remote refs: ..., done
Sorting commits: ..., done
Examining commits: 100% (1/1), done
*.mp3   284 MB    1/1 files(s)  100%
*.pdf   42 MB     8/8 files(s)  100%
*.psd   9.8 MB  15/15 files(s)  100%
*.ipynb 6.9 MB    6/6 files(s)  100%
*.csv   5.8 MB    2/2 files(s)  100%

Maintenant, vous pouvez exécuter git lfs migrate import pour convertir certains types de fichiers en LFS :

$ git lfs migrate import --include="*.mp3,*.psd"
Fetching remote refs: ..., done
Sorting commits: ..., done
Rewriting commits: 100% (1/1), done
  main  d2b959babd099fe70da1c1512e2475e8a24de163 -> 136e706bf1ae79643915c134e17a6c933fd53c61
Updating refs: ..., done

Si après conversion, vous constatez que certains fichiers dans votre répertoire de travail ont été remplacés par des pointeurs Git LFS, c'est normal, et les copies de travail de ces fichiers peuvent être régénérées avec leur contenu complet attendu en utilisant git lfs checkout.

Migrer l'historique local

Vous pouvez également migrer l'intégralité de l'historique de votre dépôt :

# Vérifier les gros fichiers et les objets Git LFS existants dans votre branche main locale
$ git lfs migrate info --include-ref=main
# Vérifier les gros fichiers et les objets Git LFS existants dans toutes les branches
$ git lfs migrate info --everything
# Vérifier les gros fichiers dans toutes les branches, en ignorant tout objet Git LFS existant,
# et en listant les 100 premiers résultats ou moins
$ git lfs migrate info --everything --pointers=ignore --top=100

Les mêmes drapeaux fonctionneront en mode import :

# Convertir tous les fichiers zip dans votre branche main
$ git lfs migrate import --include-ref=main --include="*.zip"
# Convertir tous les fichiers zip dans toutes les branches locales
$ git lfs migrate import --everything --include="*.zip"
# Convertir tous les fichiers de plus de 100 Ko dans toutes les branches locales
$ git lfs migrate import --everything --above=100Kb

Note : Cela nécessitera un push forcé vers tous les remotes Git existants. L'utilisation de l'option --all lors d'un push forcé peut être pratique si de nombreuses refs locales ont été mises à jour, par exemple, après une importation vers Git LFS avec l'option --everything.

Migrer sans réécriture de l'historique local

Vous pouvez également migrer des fichiers sans modifier l'historique existant de votre dépôt. Notez que dans les exemples ci-dessous, les fichiers dans les sous-répertoires ne sont pas inclus car ils ne sont pas explicitement spécifiés.

Sans message de commit spécifié :

$ git lfs migrate import --no-rewrite test.zip *.mp3 *.psd

Avec un message de commit spécifié :

$ git lfs migrate import --no-rewrite \
  -m "Importer test.zip, .mp3, .psd files dans la racine du dépôt" \
  test.zip *.mp3 *.psd

Migrer depuis Git LFS

Si vous ne souhaitez plus utiliser Git LFS pour tout ou partie de vos fichiers, vous pouvez utiliser le mode export pour reconvertir les objets Git LFS en blobs Git normaux.

Le mode export nécessite au moins un pathspec --include, et téléchargera tout objet non trouvé localement depuis votre distant Git origin, ou depuis le distant Git que vous spécifiez avec l'option --remote.

# Convertir tous les objets Git LFS zip en fichiers dans votre branche main
$ git lfs migrate export --include-ref=main --include="*.zip"
# Convertir tous les objets Git LFS zip en fichiers dans toutes les branches locales,
# en récupérant depuis le distant Git my-remote toute donnée d'objet non mise en cache localement
$ git lfs migrate export --everything --include="*.zip" --remote=my-remote
# Convertir tous les objets Git LFS en fichiers dans toutes les branches locales
$ git lfs migrate export --everything --include="*"

Note : Cela nécessitera un push forcé vers tous les remotes Git existants. L'utilisation de l'option --all lors d'un push forcé peut être pratique si de nombreuses refs locales ont été mises à jour, par exemple, après une exportation depuis Git LFS avec l'option --everything.
