base de données d'objets

Via le mécanisme des alternates, un dépôt peut hériter d'une partie de sa base de données d'objets d'une autre base de données d'objets, qui est appelée un « alternate »

dépôt

nu
Un dépôt nu est normalement un répertoire nommé de manière appropriée avec un suffixe .git qui ne contient pas de copie localement extraite de l'un des fichiers sous contrôle de révision. C'est-à-dire que tous les fichiers d'administration et de contrôle Git qui seraient normalement présents dans le sous-répertoire caché .git sont directement présents dans le répertoire dépôt.git à la place, et aucun autre fichier n'est présent et extrait. Généralement, les éditeurs de dépôts publics mettent à disposition des dépôts

branch

e
Une « branche » est une ligne de développement. Le commit le plus récent sur une branche est appelé le sommet de cette branche. Le sommet de la branche est référencé par une tête de branche, qui avance à mesure que du développement supplémentaire est fait sur la branche. Un seul dépôt Git peut suivre un nombre arbitraire de branches, mais votre arbre de travail n'est associé qu'à l'une d'entre elles (la branche « courante » ou « extraite »), et HEAD pointe vers cette
branche.

déréférence

r
En ce qui concerne une ref symbolique : l'action d'accéder à la référence vers laquelle pointe une ref symbolique. Le déréférencement récursif consiste à répéter le processus susmentionné sur la ref résultante jusqu'à ce qu'une référence non symbolique soit trouvée.

En ce qui concerne un objet tag : l'action d'accéder à l'objet vers lequel pointe un tag. Les tags sont déréférencés récursivement en répétant l'opération sur l'objet résultant jusqu'à ce que le résultat ait soit un type d'objet spécifié (le cas échéant) soit un type d'objet non « tag ». HEAD

détaché
Normalement, HEAD stocke le nom d'une branche, et les commandes qui opèrent sur l'historique que HEAD représente opèrent sur l'historique menant au sommet de la branche vers laquelle HEAD pointe. Cependant, Git permet aussi d'extraire un commit arbitraire qui n'est pas nécessairement le sommet d'une branche particulière. Le HEAD dans un tel état est appelé « détaché ».

Notez que les commandes qui opèrent sur l'historique de la branche courante (par ex. git commit pour construire un nouvel historique au-dessus de celle-ci) fonctionnent toujours lorsque le HEAD est détaché. Elles mettent à jour le HEAD pour pointer vers le sommet de l'historique mis à jour sans affecter aucune branche. Les commandes qui mettent à jour ou interrogent des informations à propos de la branche courante (par ex. git branch --set-upstream-to qui définit avec quelle branche de suivi à distance la branche courante s'intègre) ne

fonctionnent évidemment pas, car il n'y a pas de
branche courante (réelle) à interroger dans cet état.

Un fast-forward est un type spécial de fusion où vous avez une révision et vous « fusionnez » les changements d'une autre branche qui se trouvent être un descendant de ce que vous avez. Cela arrivera fréquemment sur une branche de suivi à distance d'un dépôt

merg

e
En tant que verbe : intégrer le contenu d'une autre branche (éventuellement issue d'un dépôt externe) dans la branche courante. Dans le cas où la branche fusionnée provient d'un dépôt différent, cela se fait en récupérant d'abord la branche distante puis en fusionnant le résultat dans la branche courante. Cette combinaison d'opérations de fetch et de merge est appelée un pull. La fusion est effectuée par un processus automatique qui identifie les changements effectués depuis que les branches ont divergé, puis applique tous ces changements ensemble. Dans les cas où les changements entrent en conflit, une intervention manuelle peut être nécessaire pour terminer la fusion.

En tant que nom : à moins qu'il ne s'agisse d'un fast-forward, une fusion réussie aboutit à la créati

pathspe

c
Motif utilisé pour limiter les chemins dans les commandes Git.

Les pathspecs sont utilisés sur la ligne de commande de "git ls-files", "git ls-tree", "git add", "git grep", "git diff", "git checkout", et de nombreuses autres commandes pour limiter la portée des opérations à un sous-ensemble de l'arbre ou de l'arbre de travail. Voir la documentation de chaque commande pour savoir si les chemins sont relatifs au répertoire courant ou au niveau supérieur. La syntaxe du pathspec est la suivante

:
•tout chemin correspond à
lui-même
•le pathspec jusqu'au dernier slash représente un préfixe de répertoire. La portée de ce pathspec est limitée à ce
sous-arbre.
•le reste du pathspec est un motif pour le reste du chemin. Les chemins relatifs au préfixe de répertoire seront comparés à ce motif en utilisant fnmatch(3) ; en particulier, * et ? peuvent correspondre aux séparateurs de
répertoire.

Par exemple, Documentation/*.jpg correspondra à tous les fichiers .jpg dans le sous-arbre Documentation, y compris Documentation/chapter_1/figure_1.

jpg.

Un pathspec qui commence par deux-points : a une signification spéciale. Dans la forme courte, les deux-points initiaux : sont suivis de zéro ou plusieurs lettres de "signature magique" (qui peuvent être éventuellement terminées par un autre deux-points :), et le reste est le motif à comparer au chemin. La "signature magique" se compose de symboles ASCII qui ne sont ni alphanumériques, ni des caractères spéciaux de glob ou de regex, ni deux-points. Les deux-points optionnels qui terminent la "signature magique" peuvent être omis si le motif commence par un caractère qui n'appartient pas à l'ensemble des symboles de "signature magique" et qui n'est pas un

deux-points.

Dans la forme longue, les deux-points initiaux : sont suivis d'une parenthèse ouvrante (, d'une liste séparée par des virgules de zéro ou plusieurs "mots magiques", et d'une parenthèse fermante ), et le reste est le motif à comparer au

chemin.

Un pathspec composé uniquement de deux-points signifie "il n'y a pas de pathspec". Cette forme ne doit pas être combinée avec d'autres

pathspecs.

glo

b
Git traite le motif comme un glob shell adapté à la consommation par fnmatch(3) avec l'indicateur FNM_PATHNAME : les jokers dans le motif ne correspondront pas à un / dans le chemin. Par exemple, "Documentation/*.html" correspond à "Documentation/git.html" mais pas à "Documentation/ppc/ppc.html" ou "tools/perf/Documentation/perf.html".

Deux astérisques consécutifs ("**") dans les motifs comparés à un chemin complet peuvent avoir une signification spéciale

:
•Un "**" initial suivi d'un slash signifie correspondre dans tous les répertoires. Par exemple, "**/foo" correspond au fichier ou répertoire "foo" n'importe où. "**/foo/bar" correspond au fichier ou répertoire "bar" n'importe où directement sous le répertoire "foo"
.
•Un "/**" final correspond à tout ce qui est à l'intérieur. Par exemple, "abc/**" correspond à tous les fichiers à l'intérieur du répertoire "abc", par rapport à l'emplacement du fichier .gitignore, avec une profondeur
infinie.
•Un slash suivi de deux astérisques consécutifs puis d'un slash correspond à zéro ou plusieurs répertoires. Par exemple, "a/**/b" correspond à "a/b", "a/x/b", "a/x/y/b" et ainsi de
suite.
•D'autres astérisques consécutifs sont considérés comme invalides.

peel

L'action de déréférencer récursivement un objet tag.

Avec l'option --pickaxe-all, il peut être utilisé pour visualiser l'ensemble complet des changements qui ont introduit ou supprimé, par exemple, une ligne de texte particulière. Voir git-diff(1).

Nom mignon pour le cœur de Git.

Nom mignon pour les programmes et suites de programmes qui dépendent du cœur de Git, présentant un accès de haut niveau au cœur de Git. Les porcelaines exposent davantage une interface SCM que les plomberies.

ref par-worktree

Refs qui sont par-worktree, plutôt que globales. Il s'agit actuellement uniquement de HEAD et de toutes les refs commençant par refs/bisect/, mais cela pourrait inclure ultérieurement d'autres refs inhabituelles.

pseudoref

Une ref qui a des sémantiques différentes des refs normales. Ces refs peuvent être lues via les commandes Git normales, mais ne peuvent pas être écrites par des commandes comme git-update-ref(1).

Les pseudorefs suivantes sont connues de Git :

•FETCH_HEAD est écrit par git-fetch(1) ou git-pull(1). Il peut faire référence à plusieurs ID d'objets. Chaque ID d'objet est annoté avec des métadonnées indiquant d'où il a été récupéré et son statut de récupération.
•MERGE_HEAD est écrit par git-merge(1) lors de la résolution de conflits de fusion. Il contient tous les ID de commit qui sont en cours de fusion.

pull

Tirer une branche signifie la récupérer et la fusionner. Voir aussi git-pull(1).

push

Pousser une branche signifie obtenir la ref de tête de la branche à partir d'un dépôt distant, déterminer si elle est un ancêtre de la ref de tête locale de la branche, et dans ce cas, placer tous les objets qui sont atteignables depuis la ref de tête locale et qui manquent dans le dépôt distant, dans la base de données d'objets distante, et mettre à jour la ref de tête distante. Si la tête distante n'est pas un ancêtre de la tête locale, la poussée échoue.

reachable

Tous les ancêtres d'un commit donné sont dits "atteignables" depuis ce commit. Plus généralement, un objet est atteignable depuis un autre si l'on peut passer de l'un à l'autre par une chaîne qui suit les tags vers ce qu'ils taguent, les commits vers leurs parents ou arbres, et les arbres vers les arbres ou blobs qu'ils contiennent.

bitmaps d'atteignabilité

Les bitmaps d'atteignabilité stockent des informations sur l'atteignabilité d'un ensemble sélectionné de commits dans un packfile, ou un index multi-pack (MIDX), pour accélérer la recherche d'objets. Les bitmaps sont stockés dans un fichier ".bitmap". Un dépôt ne peut avoir qu'un seul fichier bitmap en cours d'utilisation. Le fichier bitmap peut appartenir soit à un seul pack, soit à l'index multi-pack du dépôt (s'il existe).

rebase

Réappliquer une série de changements d'une branche à une base différente, et réinitialiser la tête de cette branche au résultat.

ref

Un nom qui pointe vers un nom d'objet ou une autre ref (cette dernière est appelée une ref symbolique). Pour plus de commodité, une ref peut parfois être abrégée lorsqu'elle est utilisée comme argument d'une commande Git ; voir gitrevisions(7) pour plus de détails. Les refs sont stockées dans le dépôt.

L'espace de noms des refs est hiérarchique. Les noms de refs doivent soit commencer par refs/, soit être situés à la racine de la hiérarchie. Dans ce dernier cas, leur nom doit suivre ces règles :

•Le nom ne contient que des caractères majuscules ou des tirets bas.
•Le nom se termine par "_HEAD" ou est égal à "HEAD".

Il existe quelques refs irrégulières à la racine de la hiérarchie qui ne correspondent pas à ces règles. La liste suivante est exhaustive et ne sera pas étendue à l'avenir :

•AUTO_MERGE
•BISECT_EXPECTED_REV
•NOTES_MERGE_PARTIAL
•NOTES_MERGE_REF
•MERGE_AUTOSTASH

Différentes sous-hiérarchies sont utilisées à des fins différentes. Par exemple, la hiérarchie refs/heads/ est utilisée pour représenter les branches locales, tandis que la hiérarchie refs/tags/ est utilisée pour représenter les tags locaux.

reflog

Un reflog montre l'"historique" local d'une ref. Autrement dit, il peut vous dire quelle était la 3ème dernière révision dans *ce* dépôt, et quel était l'état actuel dans *ce* dépôt, hier à 21h14. Voir git-reflog(1) pour plus de détails.

refspec

Un "refspec" est utilisé par fetch et push pour décrire le mappage entre la ref distante et la ref locale. Voir git-fetch(1) ou git-push(1) pour plus de détails.

dépôt distant

Un dépôt qui est utilisé pour suivre le même projet mais qui réside ailleurs. Pour communiquer avec des dépôts distants, voir fetch ou push.

branche de suivi distant

Une ref utilisée pour suivre les changements d'un autre dépôt. Elle ressemble typiquement à refs/remotes/foo/bar (indiquant qu'elle suit une branche nommée bar dans un dépôt distant nommé foo) et correspond au côté droit d'un refspec de récupération configuré. Une branche de suivi distant ne devrait pas contenir de modifications directes ni avoir de commits locaux effectués dessus.

dépôt

Une collection de refs avec une base de données d'objets contenant tous les objets qui sont atteignables depuis les refs, éventuellement accompagnés de métadonnées provenant d'un ou plusieurs porcelaines. Un dépôt peut partager une base de données d'objets avec d'autres dépôts via le mécanisme d'alternatives.

résoudre

L'action de corriger manuellement ce qu'une fusion automatique échouée a laissé derrière elle.

révision

Synonyme de commit (le nom).

rembobiner

Jeter une partie du développement, c'est-à-dire assigner la tête à une révision antérieure.

SCM

Gestion de code source (outil).

SHA-1

"Secure Hash Algorithm 1" ; une fonction de hachage cryptographique. Dans le contexte de Git, utilisé comme synonyme de nom d'objet.

clone superficiel

Principalement un synonyme de dépôt superficiel, mais l'expression rend plus explicite qu'il a été créé en exécutant la commande git clone --depth=...

dépôt superficiel

Un dépôt superficiel a un historique incomplet dont certains commits ont leurs parents cautérisés (en d'autres termes, Git est invité à prétendre que ces commits n'ont pas de parents, même s'ils sont enregistrés dans l'objet commit). Ceci est parfois utile lorsque vous ne vous intéressez qu'à l'historique récent d'un projet, même si l'historique réel enregistré dans le dépôt distant est beaucoup plus volumineux. Un dépôt superficiel est créé en donnant l'option --depth à git-clone(1), et son historique peut être approfondi ultérieurement avec git-fetch(1).

entrée de stash

Un objet utilisé pour stocker temporairement le contenu d'un répertoire de travail et d'un index modifiés pour une réutilisation future.

sous-module

Un dépôt qui contient l'historique d'un projet séparé à l'intérieur d'un autre dépôt (ce dernier étant appelé superprojet).

superprojet

Un dépôt qui référence des dépôts d'autres projets dans son arbre de travail en tant que sous-modules. Le superprojet connaît les noms (mais ne détient pas de copies) des objets commit des sous-modules contenus.

symref

Référence symbolique : au lieu de contenir l'ID SHA-1 lui-même, elle est du format ref: refs/quelque/chose et lorsqu'elle est référencée, elle se déréférence récursivement vers cette référence. HEAD est un excellent exemple de symref. Les références symboliques sont manipulées avec la commande git-symbolic-ref(1).

tag

Une ref dans l'espace de noms refs/tags/ qui pointe vers un objet de type arbitraire (typiquement un tag pointe vers un objet tag ou un objet commit). Contrairement à une tête, un tag n'est pas mis à jour par la commande commit. Un tag Git n'a rien à voir avec un tag Lisp (qui serait appelé un type d'objet dans le contexte de Git). Un tag est le plus souvent utilisé pour marquer un point particulier dans la chaîne d'ascendance des commits.

objet tag

Un objet contenant une ref pointant vers un autre objet, qui peut contenir un message tout comme un objet commit. Il peut également contenir une signature (PGP), auquel cas il est appelé un "objet tag signé".

branche thématique

Une branche Git normale utilisée par un développeur pour identifier une ligne de développement conceptuelle. Comme les branches sont très faciles et peu coûteuses, il est souvent souhaitable d'avoir plusieurs petites branches qui contiennent chacune des concepts très bien définis ou des changements incrémentiels mais liés.

trailer

Métadonnées clé-valeur. Les trailers se trouvent facultativement à la fin d'un message de commit. Peuvent être appelés "footers" ou "tags" dans d'autres communautés. Voir git-interpret-trailers(1).

arbre

Soit un arbre de travail, soit un objet arbre avec les objets blob et arbre dépendants (c'est-à-dire une représentation stockée d'un arbre de travail).

objet arbre

Un objet contenant une liste de noms de fichiers et de modes avec des refs vers les objets blob et/ou arbre associés. Un arbre est équivalent à un répertoire.

tree-ish (également treeish)

Un objet arbre ou un objet qui peut être récursivement déréférencé vers un objet arbre. Déréférencer un objet commit donne l'objet arbre correspondant au répertoire racine de la révision. Les éléments suivants sont tous des tree-ishes : un commit-ish, un objet arbre, un objet tag pointant vers un objet arbre, un objet tag pointant vers un objet tag pointant vers un objet arbre, etc.

unborn

HEAD peut pointer vers une branche qui n'existe pas encore et qui n'a encore aucun commit dessus, et une telle branche est appelée une branche "unborn". La manière la plus typique pour les utilisateurs de rencontrer une branche unborn est de créer un dépôt à neuf sans cloner depuis ailleurs. NAME

gitglossary - A Git glossary

SYNOPSIS

This document defines common Git terminology.

DESCRIPTION

This document defines common Git terminology.

author
The person who originally wrote or created the content of a commit.

bare repository
A repository that does not have a working tree. It is often used on servers as a central repository where developers push their changes to.

branch
A movable pointer to a commit. The HEAD pointer is usually a branch name. When you commit, the branch that is pointed to by HEAD is updated to point to the new commit.

commit
An entry in the Git history. It represents a snapshot of the repository at a certain point in time. Each commit has a unique SHA-1 identifier, a pointer to its parent commit(s), and metadata including the author, committer, timestamp, and a commit message.

committer
The person who applied a commit to the repository. This may be different from the author if the commit was cherry-picked, rebased, or otherwise modified by someone else.

detached HEAD
When the HEAD pointer points directly to a commit instead of a branch. This usually happens when you check out a specific commit or tag. Changes made in a detached HEAD state are not associated with any branch and can be lost if you later check out something else without creating a new branch.

dirty
A working tree is considered "dirty" if it contains modified files that have not been staged for commit or committed yet.

fetch
Download objects and refs from another repository. Fetching copies objects and refs from the source repository, but does not integrate them into your working tree or current branch.

gitattributes
A file that allows you to define attributes per path, which cause certain Git operations to behave differently depending on the file path. For example, you can specify how line endings should be handled for different files.

gitignore
A file that specifies intentionally untracked files that Git should ignore. These files will not show up in `git status` or be added to the index.

good commit
A commit that is known to be good, typically used in conjunction with `git bisect` to identify a commit that introduced a bug.

hash
See SHA-1.

HEAD
A special pointer that usually points to the currently checked-out branch. It represents the tip of your current working commit history.

index
Also known as the staging area. It's an intermediate area where you stage changes before committing them. The index holds information about the next commit to be created.

local repository
The Git repository that resides on your local machine.

merge
To integrate changes from one branch into another. Git creates a new commit (a "merge commit") that has two or more parent commits, representing the histories that were combined.

merge conflict
When Git cannot automatically merge branches because of conflicting changes in the same part of a file. You must manually resolve these conflicts.

object
The fundamental data structure in Git. There are four types of objects: blobs (file contents), trees (directory contents), commits, and tags.

orphan branch
A branch that does not share any history with other branches. It is created using `git checkout --orphan <branchname>`. New commits on an orphan branch will not have any parent commits. Some operations can get you on an unborn branch with their orphan option.

unmerged index
An index which contains unmerged index entries.

unreachable object
An object which is not reachable from a branch, tag, or any other reference.

upstream branch
The default branch that is merged into the branch in question (or the branch in question is rebased onto). It is configured via branch.<name>.remote and branch.<name>.merge. If the upstream branch of A is origin/B sometimes we say "A is tracking origin/B".

working tree
The tree of actual checked out files. The working tree normally contains the contents of the HEAD commit’s tree, plus any local changes that you have made but not yet committed.

worktree
A repository can have zero (i.e. bare repository) or one or more worktrees attached to it. One "worktree" consists of a "working tree" and repository metadata, most of which are shared among other worktrees of a single repository, and some of which are maintained separately per worktree (e.g. the index, HEAD and pseudorefs like MERGE_HEAD, per-worktree refs and per-worktree configuration file).
