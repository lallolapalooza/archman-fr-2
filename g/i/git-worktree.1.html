NOM

git-worktree - Gérer plusieurs arbres de travail

SYNOPIS

git worktree add [-f] [--detach] [--checkout] [--lock [--reason <chaîne>]]
                 [--orphan] [(-b | -B) <nouvelle-branche>] <chemin> [<commit-ish>]
git worktree list [-v | --porcelain [-z]]
git worktree lock [--reason <chaîne>] <arbre-travail>
git worktree move <arbre-travail> <nouveau-chemin>
git worktree prune [-n] [-v] [--expire <expiration>]
git worktree remove [-f] <arbre-travail>
git worktree repair [<chemin>...]
git worktree unlock <arbre-travail>

DESCRIPTION

Gérez plusieurs arbres de travail attachés au même dépôt. Un dépôt git peut supporter plusieurs arbres de travail, vous permettant de vérifier plusieurs branches simultanément. Avec git worktree add, un nouvel arbre de travail est associé au dépôt, ainsi que des métadonnées supplémentaires qui différencient cet arbre de travail des autres dans le même dépôt. L'arbre de travail, avec ces métadonnées, est appelé un "worktree".

Ce nouvel arbre de travail est appelé un "arbre de travail lié" par opposition à l'"arbre de travail principal" préparé par git-init(1) ou git-clone(1). Un dépôt a un arbre de travail principal (s'il ne s'agit pas d'un dépôt nu) et zéro ou plusieurs arbres de travail liés. Lorsque vous avez terminé avec un arbre de travail lié, supprimez-le avec git worktree remove.

Dans sa forme la plus simple, git worktree add <chemin> crée automatiquement une nouvelle branche dont le nom est le dernier composant de <chemin>, ce qui est pratique si vous prévoyez de travailler sur un nouveau sujet. Par exemple, git worktree add ../hotfix crée une nouvelle branche hotfix et la vérifie au chemin ../hotfix. Pour travailler sur une branche existante dans un nouvel arbre de travail, utilisez git worktree add <chemin> <branche>. D'autre part, si vous prévoyez simplement de faire des changements expérimentaux ou de tester sans perturber le développement existant, il est souvent pratique de créer un arbre de travail "jetable" non associé à une branche. Par exemple, git worktree add -d <chemin> crée un nouvel arbre de travail avec un HEAD détaché à la même validation que la branche actuelle.

Si un arbre de travail est supprimé sans utiliser git worktree remove, ses fichiers administratifs associés, qui résident dans le dépôt (voir "DÉTAILS" ci-dessous), seront éventuellement supprimés automatiquement (voir gc.worktreePruneExpire dans git-config(1)), ou vous pouvez exécuter git worktree prune dans l'arbre de travail principal ou dans n'importe quel arbre de travail lié pour nettoyer les fichiers administratifs obsolètes.

Si l'arbre de travail d'un arbre de travail lié est stocké sur un périphérique portable ou un partage réseau qui n'est pas toujours monté, vous pouvez empêcher que ses fichiers administratifs soient élagués en exécutant la commande git worktree lock, en spécifiant éventuellement --reason pour expliquer pourquoi l'arbre de travail est verrouillé.

COMMANDES

add <chemin> [<commit-ish>]

Crée un arbre de travail à <chemin> et y vérifie <commit-ish>. Le nouvel arbre de travail est lié au dépôt actuel, partageant tout sauf les fichiers spécifiques à l'arbre de travail tels que HEAD, index, etc. Par souci de commodité, <commit-ish> peut être un simple "-", synonyme de @{-1}.

Si <commit-ish> est un nom de branche (appelons-le <branche>) et qu'il n'est pas trouvé, et que ni -b, ni -B, ni --detach ne sont utilisés, mais qu'il existe une branche de suivi dans exactement un dépôt distant (appelons-le <remote>) avec un nom correspondant, alors cela est traité comme équivalent à :

$ git worktree add --track -b <branche> <chemin> <remote>/<branche>

Si la branche existe dans plusieurs dépôts distants et que l'un d'eux est nommé par la variable de configuration checkout.defaultRemote, nous l'utiliserons pour des raisons de désambiguïsation, même si <branche> n'est pas unique sur tous les dépôts distants. Définissez-la par exemple à checkout.defaultRemote=origin pour toujours vérifier les branches distantes de là si <branche> est ambiguë mais existe sur le dépôt distant origin. Voir également checkout.defaultRemote dans git-config(1).

Si <commit-ish> est omis et que ni -b, ni -B, ni --detach ne sont utilisés, alors, par commodité, le nouvel arbre de travail est associé à une branche (appelons-la <branche>) nommée d'après $(basename <chemin>). Si <branche> n'existe pas, une nouvelle branche basée sur HEAD est automatiquement créée comme si -b <branche> avait été donné. Si <branche> existe, elle sera vérifiée dans le nouvel arbre de travail, si elle n'est vérifiée nulle part ailleurs, sinon la commande refusera de créer l'arbre de travail (sauf si --force est utilisé).

Si <commit-ish> est omis, que --detach ou --orphan ne sont pas utilisés, et qu'il n'y a pas de branches locales valides (ou de branches distantes si --guess-remote est spécifié), alors, par commodité, le nouvel arbre de travail est associé à une nouvelle branche non née nommée <branche> (après $(basename <chemin>) si ni -b ni -B ne sont utilisés) comme si --orphan avait été passé à la commande. Dans le cas où le dépôt a un dépôt distant et que --guess-remote est utilisé, mais qu'aucune branche distante ou locale n'existe, la commande échoue avec un avertissement rappelant à l'utilisateur de récupérer depuis son dépôt distant d'abord (ou d'outrepasser en utilisant -f/--force).

list

Liste les détails de chaque arbre de travail. L'arbre de travail principal est listé en premier, suivi de chacun des arbres de travail liés. Les détails de sortie incluent si l'arbre de travail est nu, la révision actuellement vérifiée, la branche actuellement vérifiée (ou "HEAD détaché" s'il n'y en a pas), "verrouillé" si l'arbre de travail est verrouillé, "prunable" si l'arbre de travail peut être élagué par la commande prune.

lock

Si un arbre de travail se trouve sur un périphérique portable ou un partage réseau qui n'est pas toujours monté, verrouillez-le pour empêcher que ses fichiers administratifs ne soient élagués automatiquement. Cela empêche également son déplacement ou sa suppression. Vous pouvez facultativement spécifier une raison pour le verrouillage avec --reason.

move

Déplace un arbre de travail vers un nouvel emplacement. Notez que l'arbre de travail principal ou les arbres de travail liés contenant des sous-modules ne peuvent pas être déplacés avec cette commande. (La commande git worktree repair, cependant, peut rétablir la connexion avec les arbres de travail liés si vous déplacez l'arbre de travail principal manuellement.)

prune

Élague les informations d'arbre de travail dans $GIT_DIR/worktrees.

remove

Supprime un arbre de travail. Seuls les arbres de travail propres (aucun fichier non suivi et aucune modification dans les fichiers suivis) peuvent être supprimés. Les arbres de travail sales ou ceux contenant des sous-modules peuvent être supprimés avec --force. L'arbre de travail principal ne peut pas être supprimé.

repair [<chemin>...]

Répare les fichiers administratifs d'arbre de travail, si possible, s'ils sont devenus corrompus ou obsolètes en raison de facteurs externes.

Par exemple, si l'arbre de travail principal (ou le dépôt nu) est déplacé, les arbres de travail liés ne pourront pas le trouver. L'exécution de repair dans l'arbre de travail principal rétablira la connexion des arbres de travail liés vers l'arbre de travail principal.

De même, si l'arbre de travail d'un arbre de travail lié est déplacé sans utiliser git worktree move, l'arbre de travail principal (ou le dépôt nu) sera incapable de le trouver. L'exécution de repair dans l'arbre de travail récemment déplacé rétablira la connexion. Si plusieurs arbres de travail liés ont été déplacés, l'exécution de repair depuis n'importe quel arbre de travail en spécifiant le nouveau <chemin> de chaque arbre rétablira la connexion à tous les chemins spécifiés.

Si l'arbre de travail principal et les arbres de travail liés ont tous deux été déplacés ou copiés manuellement, alors l'exécution de repair dans l'arbre de travail principal et la spécification du nouveau <chemin> de chaque arbre de travail lié permettront de rétablir la connexion à tous les arbres de travail liés.

unlock

Supprime le verrou d'un arbre de travail, le rendant à nouveau susceptible d'être élagué ou déplacé.

OPTIONS

-f, --force

Force l'opération. Pour add, permet de vérifier une branche qui est déjà vérifiée ailleurs. Pour remove, supprime un arbre de travail même s'il contient des modifications non suivies ou des fichiers non suivis.

--detach

Crée un arbre de travail dans un état de HEAD détaché.

--checkout

Vérifie la branche ou le commit spécifié. Ceci est le comportement par défaut pour add, mais il peut être omis pour économiser de la bande passante lorsqu'il est combiné avec des branches distantes qui n'existent pas encore localement.

--lock

Verrouille le nouvel arbre de travail, empêchant son élagage automatique.

--reason <chaîne>

Explique pourquoi un arbre de travail est verrouillé.

--orphan

Crée un arbre de travail avec une branche naissante non liée à un commit parent.

-b <nouvelle-branche>

Crée une nouvelle branche nommée <nouvelle-branche> et la vérifie.

-B <nouvelle-branche>

Crée une nouvelle branche nommée <nouvelle-branche> et la vérifie. Si la branche existe déjà, elle sera réinitialisée au commit spécifié.

-v, --verbose

Plus verbeux. Pour list, affiche des informations supplémentaires. Pour prune, indique quels arbres de travail sont supprimés.

--porcelain

Sortie lisible par script pour list.

-z

Termine les entrées de sortie de list avec un octet nul au lieu d'un saut de ligne. Peut être utilisé avec --porcelain.

-n, --dry-run

Ne supprime rien, affiche seulement ce qui serait supprimé par prune.

--expire <expiration>

Utilisé avec prune pour spécifier une durée d'expiration pour les arbres de travail obsolètes. Voir la description de gc.worktreePruneExpire dans git-config(1) pour la syntaxe des durées.

FICHIERS GIT

$GIT_DIR/worktrees/

Ce répertoire contient des sous-répertoires, un pour chaque arbre de travail lié. Chaque sous-répertoire contient les fichiers administratifs de l'arbre de travail correspondant (par exemple, HEAD, index, etc.).

OPTIONS

-f, --force

Par défaut, add refuse de créer un nouvel espace de travail lorsque <commit-ish> est un nom de branche déjà extrait par un autre espace de travail, ou si <path> est déjà attribué à un espace de travail mais est manquant (par exemple, si <path> a été supprimé manuellement). Cette option outrepasse ces protections. Pour ajouter un chemin d'espace de travail manquant mais verrouillé, spécifiez --force deux fois.

move refuse de déplacer un espace de travail verrouillé à moins que --force ne soit spécifié deux fois. Si la destination est déjà attribuée à un autre espace de travail mais est manquante (par exemple, si <new-path> a été supprimé manuellement), alors --force permet le déplacement ; utilisez --force deux fois si la destination est verrouillée.

remove refuse de supprimer un espace de travail non nettoyé à moins que --force ne soit utilisé. Pour supprimer un espace de travail verrouillé, spécifiez --force deux fois.

-b <new-branch>, -B <new-branch>

Avec add, crée une nouvelle branche nommée <new-branch> à partir de <commit-ish>, et extrait <new-branch> dans le nouvel espace de travail. Si <commit-ish> est omis, il prend par défaut HEAD. Par défaut, -b refuse de créer une nouvelle branche si elle existe déjà. -B outrepasse cette protection, réinitialisant <new-branch> à <commit-ish>.

-d, --detach

Avec add, détache HEAD dans le nouvel espace de travail. Voir "HEAD DETACHÉ" dans git-checkout(1).

--checkout, --no-checkout

Par défaut, add extrait <commit-ish>, cependant, --no-checkout peut être utilisé pour supprimer l'extraction afin d'effectuer des personnalisations, telles que la configuration du sparse-checkout. Voir "Sparse checkout" dans git-read-tree(1).

--guess-remote, --no-guess-remote

Avec worktree add <path>, sans <commit-ish>, au lieu de créer une nouvelle branche à partir de HEAD, s'il existe une branche de suivi dans exactement un dépôt distant correspondant au nom de base de <path>, basez la nouvelle branche sur la branche de suivi distante, et marquez la branche de suivi distante comme "upstream" par rapport à la nouvelle branche.

Cela peut également être configuré comme comportement par défaut en utilisant l'option de configuration worktree.guessRemote.

--relative-paths, --no-relative-paths

Lie les espaces de travail en utilisant des chemins relatifs ou des chemins absolus (par défaut). Outrepasse l'option de configuration worktree.useRelativePaths, voir git-config(1).

Avec repair, les fichiers de liaison seront mis à jour s'il y a une incompatibilité absolue/relative, même si les liens sont corrects.

--track, --no-track

Lors de la création d'une nouvelle branche, si <commit-ish> est une branche, marquez-la comme "upstream" par rapport à la nouvelle branche. C'est le comportement par défaut si <commit-ish> est une branche de suivi distante. Voir --track dans git-branch(1) pour plus de détails.

--lock

Laisse l'espace de travail verrouillé après sa création. Ceci est l'équivalent de git worktree lock après git worktree add, mais sans condition de concurrence.

-n, --dry-run

Avec prune, ne supprime rien ; signale seulement ce qui serait supprimé.

--orphan

Avec add, rend le nouvel espace de travail et l'index vides, associant l'espace de travail à une nouvelle branche non née nommée <new-branch>.

--porcelain

Avec list, affiche dans un format facile à analyser pour les scripts. Ce format restera stable entre les versions de Git et indépendamment de la configuration de l'utilisateur. Il est recommandé de le combiner avec -z. Voir ci-dessous pour les détails.

-z

Termine chaque ligne par un caractère NUL plutôt qu'une nouvelle ligne lorsque --porcelain est spécifié avec list. Cela permet d'analyser la sortie lorsqu'un chemin d'espace de travail contient un caractère de nouvelle ligne.

-q, --quiet

Avec add, supprime les messages d'information.

-v, --verbose

Avec prune, signale toutes les suppressions.

Avec list, affiche des informations supplémentaires sur les espaces de travail (voir ci-dessous).

--expire <time>

Avec prune, n'expire que les espaces de travail inutilisés plus anciens que <time>.

Avec list, annote les espaces de travail manquants comme étant élaguables s'ils sont plus anciens que <time>.

--reason <string>

Avec lock ou avec add --lock, une explication de la raison pour laquelle l'espace de travail est verrouillé.

<worktree>

Les espaces de travail peuvent être identifiés par leur chemin, relatif ou absolu.

Si les derniers composants du chemin de l'espace de travail sont uniques parmi les espaces de travail, ils peuvent être utilisés pour identifier un espace de travail. Par exemple, si vous n'avez que deux espaces de travail, à /abc/def/ghi et /abc/def/ggg, alors ghi ou def/ghi suffisent pour pointer vers le premier espace de travail.

RÉFÉRENCES

Lorsque vous utilisez plusieurs espaces de travail, certaines références sont partagées entre tous les espaces de travail, mais d'autres sont spécifiques à un espace de travail individuel. Un exemple est HEAD, qui est différent pour chaque espace de travail. Cette section traite des règles de partage et de la manière d'accéder aux références d'un espace de travail depuis un autre.

En général, toutes les pseudo-références sont par espace de travail et toutes les références commençant par refs/ sont partagées. Les pseudo-références sont celles comme HEAD qui sont directement sous $GIT_DIR au lieu d'être dans $GIT_DIR/refs. Il y a cependant des exceptions : les références dans refs/bisect, refs/worktree et refs/rewritten ne sont pas partagées.

Les références qui sont par espace de travail peuvent toujours être accédées depuis un autre espace de travail via deux chemins spéciaux, main-worktree et worktrees. Le premier donne accès aux références par espace de travail de l'espace de travail principal, tandis que le second donne accès à tous les espaces de travail liés.

Par exemple, main-worktree/HEAD ou main-worktree/refs/bisect/good se résolvent à la même valeur que le HEAD et le refs/bisect/good de l'espace de travail principal, respectivement. De même, worktrees/foo/HEAD ou worktrees/bar/refs/bisect/bad sont les mêmes que $GIT_COMMON_DIR/worktrees/foo/HEAD et $GIT_COMMON_DIR/worktrees/bar/refs/bisect/bad.

Pour accéder aux références, il est préférable de ne pas regarder directement dans $GIT_DIR. Utilisez plutôt des commandes comme git-rev-parse(1) ou git-update-ref(1) qui géreront correctement les références.

FICHIER DE CONFIGURATION

Par défaut, le fichier config du dépôt est partagé entre tous les espaces de travail. Si les variables de configuration core.bare ou core.worktree sont présentes dans le fichier de configuration commun et que extensions.worktreeConfig est désactivé, elles ne s'appliqueront qu'à l'espace de travail principal.

Afin d'avoir une configuration spécifique à l'espace de travail, vous pouvez activer l'extension worktreeConfig, par exemple :

$ git config extensions.worktreeConfig true

Dans ce mode, la configuration spécifique reste dans le chemin indiqué par git rev-parse --git-path config.worktree. Vous pouvez ajouter ou mettre à jour la configuration dans ce fichier avec git config --worktree. Les anciennes versions de Git refuseront d'accéder aux dépôts avec cette extension.

Notez que dans ce fichier, l'exception pour core.bare et core.worktree a disparu. S'ils existent dans $GIT_DIR/config, vous devez les déplacer dans le fichier config.worktree de l'espace de travail principal. Vous pouvez également profiter de cette occasion pour revoir et déplacer d'autres configurations que vous ne souhaitez pas partager à tous les espaces de travail :

•core.worktree ne doit jamais être partagé.
•core.bare ne doit pas être partagé si la valeur est core.bare=true.
•core.sparseCheckout ne doit pas être partagé, à moins que vous ne soyez sûr d'utiliser toujours le sparse checkout pour tous les espaces de travail.

Voir la documentation de extensions.worktreeConfig dans git-config(1) pour plus de détails.

DÉTAILS

Chaque espace de travail lié possède un sous-répertoire privé dans le répertoire $GIT_DIR/worktrees du dépôt. Le nom du sous-répertoire privé est généralement le nom de base du chemin de l'espace de travail lié, éventuellement complété d'un numéro pour le rendre unique. Par exemple, lorsque $GIT_DIR=/path/main/.git la commande git worktree add /path/other/test-next next crée l'espace de travail lié dans /path/other/test-next et crée également un répertoire $GIT_DIR/worktrees/test-next (ou $GIT_DIR/worktrees/test-next1 si test-next est déjà pris).

Au sein d'un espace de travail lié, $GIT_DIR est défini pour pointer vers ce répertoire privé (par exemple, /path/main/.git/worktrees/test-next dans l'exemple) et $GIT_COMMON_DIR est défini pour pointer vers le $GIT_DIR de l'espace de travail principal (par exemple, /path/main/.git). Ces paramètres sont définis dans un fichier .git situé dans le répertoire racine de l'espace de travail lié.

La résolution des chemins via git rev-parse --git-path utilise soit $GIT_DIR soit $GIT_COMMON_DIR en fonction du chemin. Par exemple, dans l'espace de travail lié, git rev-parse --git-path HEAD renvoie /path/main/.git/worktrees/test-next/HEAD (pas /path/other/test-next/.git/HEAD ou /path/main/.git/HEAD) tandis que git rev-parse --git-path refs/heads/master utilise $GIT_COMMON_DIR et renvoie /path/main/.git/refs/heads/master, car les références sont partagées entre tous les espaces de travail, à l'exception de refs/bisect, refs/worktree et refs/rewritten.
