DESCRIPTIO

N

Cette commande possède un mode moderne --write-tree et un mode obsolète --trivial-merge. À l'exception de la section DESCRIPTION OBSOLÈTE à la fin, le reste de cette documentation décrit le mode moderne --write-tree

STATUT DE SORTIE

Pour une fusion réussie et sans conflit, le statut de sortie est 0. Lorsque la fusion présente des conflits, le statut de sortie est 1. Si la fusion ne peut pas être complétée (ou démarrée) en raison d'une erreur, le statut de sortie est différent de 0 ou 1 (et la sortie n'est pas spécifiée). Lorsque l'option -s --stdin est passée, le statut de retour est 0 pour les fusions réussies et conflictuelles, et différent de 0 ou 1 s'il ne peut pas compléter toutes les fusions demandées.

NOTES D'UTILISATION

Cette commande est destinée à être une plomberie de bas niveau, similaire à git-hash-object(1), git-mktree(1), git-commit-tree(1), git-write-tree(1), git-update-ref(1), et git-mktag(1). Ainsi, elle peut être utilisée dans le cadre d'une série d'étapes telles que :

vi message.txt
BRANCH1=refs/heads/test
BRANCH2=main
NEWTREE=$(git merge-tree --write-tree $BRANCH1 $BRANCH2) || {
    echo "Il y a eu des conflits..." 1>&2
    exit 1
}
NEWCOMMIT=$(git commit-tree $NEWTREE -F message.txt \
    -p $BRANCH1 -p $BRANCH2)
git update-ref $BRANCH1 $NEWCOMMIT

Notez que lorsque le statut de sortie est non nul, NEWTREE dans cette séquence contiendra beaucoup plus de sortie qu'un simple arbre.

Pour les conflits, la sortie inclut les mêmes informations que celles obtenues avec git(1) :

• ce qui serait écrit dans l'arbre de travail (l'OID de l'arbre racine)
• les étapes de plus haut niveau qui seraient écrites dans l'index (les informations de fichier en conflit)
• tous les messages qui auraient été imprimés sur la sortie standard (les messages informatifs)

FORMAT D'ENTRÉE

Le format d'entrée de git merge-tree --stdin est entièrement basé sur du texte. Chaque ligne a ce format :

[<commit-de-base> -- ]<branche1> <branche2>

Si une ligne est séparée par --, la chaîne avant le séparateur est utilisée pour spécifier une base de fusion pour la fusion et la chaîne après le séparateur décrit les branches à fusionner.

ERREURS À ÉVITER

NE PAS parcourir l'arbre racine résultant pour essayer de trouver quels fichiers sont en conflit ; analysez plutôt la section d'informations sur les fichiers en conflit. Non seulement l'analyse d'un arbre entier serait horriblement lente dans les grands dépôts, mais il existe de nombreux types de conflits qui ne peuvent pas être représentés par des marqueurs de conflit (modification/suppression, conflit de mode, fichier binaire modifié des deux côtés, conflits fichier/répertoire, diverses permutations de conflits de renommage, etc.).

NE PAS interpréter une liste d'informations de fichiers en conflit vide comme une fusion propre ; vérifiez le statut de sortie. Une fusion peut avoir des conflits sans que des fichiers individuels soient en conflit (il existe quelques types de conflits de renommage de répertoires qui entrent dans cette catégorie, et d'autres pourraient également être ajoutés à l'avenir).

NE PAS essayer de deviner ou de faire deviner les types de conflits à l'utilisateur à partir de la liste d'informations sur les fichiers en conflit. Les informations fournies sont insuffisantes pour le faire. Par exemple : les conflits Renommer/Renommer (1vers2) (les deux côtés ont renommé le même fichier différemment) entraîneront trois fichiers différents ayant des étapes de plus haut niveau (mais chacun n'a qu'une seule étape de plus haut niveau), sans moyen (sauf les messages informatifs) de déterminer quels trois fichiers sont liés. Les conflits fichier/répertoire entraînent également un fichier avec une seule étape de plus haut niveau. Les conflits potentiellement impliqués dans un renommage de répertoire (lorsque "merge.directoryRenames" est non défini ou défini sur "conflicts") entraînent également un fichier avec une seule étape de plus haut niveau. Dans tous les cas, la section des messages informatifs contient les informations nécessaires, bien qu'elle ne soit pas conçue pour être analysable par machine.

NE PAS supposer que chaque chemin des informations de fichiers en conflit, et les conflits logiques dans les messages informatifs ont une relation un-à-un, ni qu'il y a une relation un-à-plusieurs, ni une relation plusieurs-à-un. Des relations plusieurs-à-plusieurs existent, ce qui signifie que chaque chemin peut avoir plusieurs types de conflits logiques dans une seule fusion, et chaque type de conflit logique peut affecter plusieurs chemins.

NE PAS supposer que tous les noms de fichiers listés dans la section des messages informatifs avaient des conflits. Des messages peuvent être inclus pour des fichiers qui n'ont pas de conflits, tels que "Auto-fusion de <fichier>".

ÉVITEZ de prendre les OID des informations sur les fichiers en conflit et de les refusionner pour présenter les conflits à l'utilisateur. Cela entraînerait une perte d'informations. Au lieu de cela, recherchez la version du fichier trouvée dans l'OID de l'arbre racine et affichez celle-ci à la place. En particulier, cette dernière contiendra des marqueurs de conflit annotés avec la branche/le commit d'origine en cours de fusion et, si des renommages étaient impliqués, le nom de fichier d'origine. Bien que vous puissiez inclure la branche/le commit d'origine dans les annotations des marqueurs de conflit lors de la refusion, le nom de fichier d'origine n'est pas disponible à partir des informations sur les fichiers en conflit et vous perdriez donc des informations qui pourraient aider l'utilisateur à résoudre le conflit.

DESCRIPTION OBSOLÈTE

Conformément à la DESCRIPTION et contrairement au reste de cette documentation, cette section décrit le mode obsolète --trivial-merge.

Outre l'option facultative --trivial-merge, ce mode n'accepte aucune option.

Ce mode lit trois arbres (tree-ish) et affiche les résultats de fusion triviaux et les étapes conflictuelles sur la sortie standard dans un format semi-diff. Comme cela a été conçu pour que des scripts de niveau supérieur consomment et réintègrent les résultats dans l'index, il omet les entrées qui correspondent à <branche1>. Le résultat de cette seconde forme est similaire à ce que fait `git read-tree -m` en trois temps, mais au lieu de stocker les résultats dans l'index, la commande affiche les entrées sur la sortie standard.

Cette forme a non seulement une applicabilité limitée (une fusion triviale ne peut pas gérer les fusions de contenu de fichiers individuels, la détection de renommage, la gestion correcte des conflits répertoire/fichier, etc.), mais le format de sortie est également difficile à utiliser, et il sera généralement moins performant que la première forme même pour les fusions réussies (surtout si l'on travaille dans de grands dépôts).
