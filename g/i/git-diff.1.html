NOM

git-diff - Afficher les changements entre des commits, un commit et l'arborescence de travail, etc.

SYNTAXE

git diff [<options>] [<commit>] [--] [<chemin>...]
git diff [<options>] --cached [--merge-base] [<commit>] [--] [<chemin>...]
git diff [<options>] [--merge-base] <commit> [<commit>...] <commit> [--] [<chemin>...]
git diff [<options>] <commit>...<commit> [--] [<chemin>...]
git diff [<options>] <blob> <blob>
git diff [<options>] --no-index [--] <chemin> <chemin> [<pathspec>...]

DESCRIPTION

Affiche les changements entre l'arborescence de travail et l'index ou un arbre, les changements entre l'index et un arbre, les changements entre deux arbres, les changements résultant d'une fusion, les changements entre deux objets blob, ou les changements entre deux fichiers sur disque.

git diff [<options>] [--] [<chemin>...]

Cette forme permet de visualiser les changements que vous avez apportés par rapport à l'index (zone de staging pour le prochain commit). En d'autres termes, les différences sont ce que vous pourriez dire à Git d'ajouter à l'index, mais que vous ne l'avez pas encore fait. Vous pouvez mettre en scène ces changements en utilisant git-add(1).

git diff [<options>] --no-index [--] <chemin> <chemin> [<pathspec>...]

Cette forme permet de comparer les deux chemins donnés sur le système de fichiers. Vous pouvez omettre l'option --no-index en exécutant la commande dans une arborescence de travail contrôlée par Git et au moins un des chemins pointe à l'extérieur de l'arborescence de travail, ou lors de l'exécution de la commande en dehors d'une arborescence de travail contrôlée par Git. Cette forme implique --exit-code. Si les deux chemins pointent vers des répertoires, des spécifications de chemin supplémentaires peuvent être fournies. Celles-ci limiteront les fichiers inclus dans la différence. Toutes ces spécifications de chemin doivent être relatives car elles s'appliquent aux deux côtés de la différence.

git diff [<options>] --cached [--merge-base] [<commit>] [--] [<chemin>...]

Cette forme permet de visualiser les changements que vous avez mis en scène pour le prochain commit par rapport au <commit> nommé. Typiquement, vous voudrez comparer avec le dernier commit, donc si vous ne donnez pas <commit>, il prend par défaut la valeur HEAD. Si HEAD n'existe pas (par ex. branches non développées) et que <commit> n'est pas donné, cela montre tous les changements mis en scène. --staged est un synonyme de --cached.

Si --merge-base est donné, au lieu d'utiliser <commit>, utilisez la base de fusion de <commit> et de HEAD. git diff --cached --merge-base A est équivalent à git diff --cached $(git merge-base A HEAD).

git diff [<options>] [--merge-base] <commit> [--] [<chemin>...]

Cette forme permet de visualiser les changements que vous avez dans votre arborescence de travail par rapport au <commit> nommé. Vous pouvez utiliser HEAD pour le comparer avec le dernier commit, ou un nom de branche pour le comparer avec le sommet d'une autre branche.

Si --merge-base est donné, au lieu d'utiliser <commit>, utilisez la base de fusion de <commit> et de HEAD. git diff --merge-base A est équivalent à git diff $(git merge-base A HEAD).

git diff [<options>] [--merge-base] <commit> <commit> [--] [<chemin>...]

Ceci permet de visualiser les changements entre deux <commit> arbitraires.

Si --merge-base est donné, utilisez la base de fusion des deux commits pour le côté "avant". git diff --merge-base A B est équivalent à git diff $(git merge-base A B) B.

git diff [<options>] <commit> <commit>...<commit> [--] [<chemin>...]

Cette forme permet de visualiser les résultats d'un commit de fusion. Le premier <commit> listé doit être la fusion elle-même ; les deux commits ou plus suivants doivent être ses parents. Des façons pratiques de produire l'ensemble des révisions souhaitées sont d'utiliser les suffixes @ et ^!. Si A est un commit de fusion, alors git diff A A^@, git diff A^! et git show A donnent tous la même différence combinée.

git diff [<options>] <commit>..<commit> [--] [<chemin>...]

Ceci est synonyme de la forme précédente (sans le ..) pour visualiser les changements entre deux <commit> arbitraires. Si <commit> d'un côté est omis, il aura le même effet que l'utilisation de HEAD à la place.

git diff [<options>] <commit>...<commit> [--] [<chemin>...]

Cette forme permet de visualiser les changements sur la branche contenant et jusqu'au deuxième <commit>, en partant d'un ancêtre commun des deux <commit>. git diff A...B est équivalent à git diff $(git merge-base A B) B. Vous pouvez omettre l'un des <commit>, ce qui aura le même effet que l'utilisation de HEAD à la place.

Juste au cas où vous feriez quelque chose d'exotique, il faut noter que tous les <commit> décrits ci-dessus, sauf dans le cas de --merge-base et dans les deux dernières formes utilisant les notations .. et ..., peuvent être n'importe quel <arbre>. Un arbre d'intérêt est celui pointé par la référence nommée AUTO_MERGE, qui est écrite par la stratégie de fusion ort en cas de conflits de fusion (voir git-merge(1)). Comparer l'arborescence de travail avec AUTO_MERGE montre les changements que vous avez apportés jusqu'à présent pour résoudre les conflits textuels (voir les exemples ci-dessous).

Pour une liste plus complète des façons d'épeler <commit>, voir la section "SPÉCIFICATION DES RÉVISIONS" dans gitrevisions(7). Cependant, diff concerne la comparaison de deux points d'extrémité, pas de plages, et les notations de plage (<commit>..<commit> et <commit>...<commit>) ne signifient pas une plage telle que définie dans la section "SPÉCIFICATION DES PLAGES" de gitrevisions(7).

git diff [<options>] <blob> <blob>

Cette forme permet de visualiser les différences entre le contenu brut de deux objets blob.

OPTIONS

-p, -u, --patch

Génère un patch (voir la section "GÉNÉRATION DE TEXTE DE PATCH AVEC -P"). C'est l'option par défaut.

-s, --no-patch

Supprime toutes les sorties de la machinerie de diff. Utile pour les commandes comme git show qui affichent le patch par défaut pour masquer leur sortie, ou pour annuler l'effet d'options comme --patch, --stat plus tôt dans la ligne de commande dans un alias.

-U<n>, --unified=<n>

Génère des diffs avec <n> lignes de contexte au lieu des trois habituelles. Implique --patch.

--output=<fichier>

Sortie vers un fichier spécifique au lieu de stdout.

--output-indicator-new=<caractère>, --output-indicator-old=<caractère>, --output-indicator-context=<caractère>

Spécifie le caractère utilisé pour indiquer les lignes nouvelles, anciennes ou de contexte dans le patch généré. Normalement, ce sont +, - et ' ' respectivement.

--raw

Génère le diff au format brut.

--patch-with-raw

Synonyme de -p --raw.

--indent-heuristic

Active l'heuristique qui décale les limites des blocs de diff pour rendre les patchs plus faciles à lire. C'est le défaut.

--no-indent-heuristic

--minimal

Passe du temps supplémentaire pour s'assurer que la plus petite différence possible est produite.

--patience

Génère une différence en utilisant l'algorithme de "diff de patience".

--histogram

Génère une différence en utilisant l'algorithme de "diff d'histogramme".

--anchored=<texte>

Génère une différence en utilisant l'algorithme de "diff ancré".

Cette option peut être spécifiée plusieurs fois.

Si une ligne existe à la fois dans la source et la destination, n'existe qu'une seule fois et commence par <texte>, cet algorithme tente d'éviter qu'elle n'apparaisse comme une suppression ou une ajout dans la sortie. Il utilise l'algorithme de "diff de patience" en interne.

--diff-algorithm=(patience|minimal|histogram|myers)

Choisit un algorithme de différence. Les variantes sont les suivantes :

default, myers

L'algorithme de différence gourmand de base. Actuellement, c'est le défaut.

minimal

Passe du temps supplémentaire pour s'assurer que la plus petite différence possible est produite.

patience

Utilise l'algorithme "diff de patience" lors de la génération des patchs.

histogram

Cet algorithme étend l'algorithme de patience pour "prendre en charge les éléments communs de faible occurrence".

Par exemple, si vous avez configuré la variable diff.algorithm à une valeur non par défaut et que vous souhaitez utiliser celle par défaut, vous devez utiliser l'option --diff-algorithm=default.

--stat[=<largeur>[,<largeur-nom>[,<compte>]]]

Génère un diffstat. Par défaut, autant d'espace que nécessaire sera utilisé pour la partie nom de fichier, et le reste pour la partie graphique. La largeur maximale est par défaut la largeur du terminal, ou 80 colonnes si non connecté à un terminal, et peut être remplacée par <largeur>. La largeur de la partie nom de fichier peut être limitée en donnant une autre largeur <largeur-nom> après une virgule ou en définissant diff.statNameWidth=<largeur-nom>. La largeur de la partie graphique peut être limitée en utilisant --stat-graph-width=<largeur-graphique> ou en définissant diff.statGraphWidth=<largeur-graphique>. L'utilisation de --stat ou --stat-graph-width affecte toutes les commandes générant un graphique de statut, tandis que la définition de diff.statNameWidth ou diff.statGraphWidth n'affecte pas git format-patch. En donnant un troisième paramètre <compte>, vous pouvez limiter la sortie aux premiers <compte> lignes, suivies de ... s'il y en a plus.

Ces paramètres peuvent également être définis individuellement avec --stat-width=<largeur>, --stat-name-width=<largeur-nom> et --stat-count=<compte>.

--compact-summary

Affiche un résumé condensé des informations d'en-tête étendues telles que les créations ou suppressions de fichiers ("nouveau" ou "parti", éventuellement +l s'il s'agit d'un lien symbolique) et les changements de mode (+x ou -x pour ajouter ou supprimer respectivement le bit exécutable) dans le diffstat. L'information est placée entre la partie nom de fichier et la partie graphique. Implique --stat.

--numstat

Similaire à --stat, mais affiche le nombre de lignes ajoutées et supprimées en notation décimale et le chemin sans abréviation, pour le rendre plus lisible par machine. Pour les fichiers binaires, affiche deux - au lieu de dire 0 0.

--shortstat

Affiche uniquement la dernière ligne du format --stat contenant le nombre total de fichiers modifiés, ainsi que le nombre de lignes ajoutées et supprimées.

-X [<param>,...], --dirstat[=<param>,...]

Affiche la distribution de la quantité relative de changements pour chaque sous-répertoire. Le comportement de --dirstat peut être personnalisé en lui passant une liste de paramètres séparés par des virgules. Les valeurs par défaut sont contrôlées par la variable de configuration diff.dirstat (voir git-config(1)). Les paramètres suivants sont disponibles :

changes

Calcule les nombres dirstat en comptant les lignes qui ont été supprimées de la source, ou ajoutées à la destination. Cela ignore la quantité de mouvements de code purs à l'intérieur d'un fichier. En d'autres termes, réorganiser les lignes dans un fichier n'est pas autant compté que d'autres changements. C'est le comportement par défaut lorsqu'aucun paramètre n'est donné.

lines

Calcule les nombres dirstat en effectuant l'analyse régulière des différences basée sur les lignes, et en additionnant les nombres de lignes supprimées/ajoutées. (Pour les fichiers binaires, compte 64 octets à la place, car les fichiers binaires n'ont pas de concept naturel de lignes). C'est un comportement --dirstat plus coûteux que le comportement changes, mais il compte les lignes réorganisées dans un fichier autant que les autres changements. Le résultat est cohérent avec ce que vous obtenez des autres options --*stat.

files

Calcule les nombres dirstat en comptant le nombre de fichiers modifiés. Chaque fichier modifié compte de manière égale dans l'analyse dirstat. C'est le comportement --dirstat le moins coûteux en calcul, car il n'a pas du tout besoin de regarder le contenu du fichier.

cumulative

Compte les changements dans un sous-répertoire également pour le répertoire parent. Notez que lorsque vous utilisez cumulative, la somme des pourcentages signalés peut dépasser 100 %. Le comportement par défaut (non cumulatif) peut être spécifié avec le paramètre noncumulative.

<limite>

Un paramètre entier spécifie un seuil en pourcentage (3 % par défaut). Les répertoires contribuant moins que ce pourcentage de changements ne sont pas affichés dans la sortie.

Exemple : Ce qui suit comptera les fichiers modifiés, tout en ignorant les répertoires avec moins de 10 % du montant total de fichiers modifiés, et en accumulant les comptes des sous-répertoires dans les répertoires parents : --dirstat=files,10,cumulative.

--cumulative

Synonyme de --dirstat=cumulative.

--dirstat-by-file[=<param>,...]

Synonyme de --dirstat=files,<param>,....

--summary

Affiche un résumé condensé des informations d'en-tête étendues telles que les créations, renommages et changements de mode.

--patch-with-stat

Synonyme de -p --stat.

-z

Lorsque --raw, --numstat, --name-only ou --name-status a été donné, ne modifie pas les chemins et utilise des NULs comme terminateurs de champ de sortie.

Sans cette option, les chemins contenant des caractères "inhabituels" sont mis entre guillemets comme expliqué pour la variable de configuration core.quotePath (voir git-config(1)).

--name-only

Affiche uniquement le nom de chaque fichier modifié dans l'arbre post-image. Les noms de fichiers sont souvent encodés en UTF-8. Pour plus d'informations, consultez la discussion sur l'encodage dans la page de manuel de git-log(1).

--name-status

Affiche uniquement le(s) nom(s) et le statut de chaque fichier modifié. Voir la description de l'option --diff-filter pour la signification des lettres de statut. Tout comme --name-only, les noms de fichiers sont souvent encodés en UTF-8.

--submodule[=<format>]

Spécifie comment les différences dans les sous-modules sont affichées. Lorsque vous spécifiez --submodule=short, le format short est utilisé. Ce format affiche simplement les noms des commits au début et à la fin de la plage. Lorsque --submodule ou --submodule=log est spécifié, le format log est utilisé. Ce format liste les commits de la plage comme le fait git-submodule(1) summary. Lorsque --submodule=diff est spécifié, le format diff est utilisé. Ce format affiche une différence en ligne des changements dans le contenu du sous-module entre la plage de commits. Par défaut, diff.submodule ou le format short si l'option de configuration n'est pas définie.

--color[=<quand>]

Affiche la différence colorée. --color (c'est-à-dire sans =<quand>) est la même chose que --color=always. <quand> peut être l'un de always, never, ou auto. Il peut être modifié par les paramètres de configuration color.ui et color.diff.

--no-color

Désactive la différence colorée. Ceci peut être utilisé pour outrepasser les paramètres de configuration. C'est la même chose que --color=never.

--color-moved[=<mode>]

Les lignes de code déplacées sont colorées différemment. Il peut être modifié par le paramètre de configuration diff.colorMoved. Le <mode> vaut par défaut no si l'option n'est pas donnée et zebra si l'option sans mode est donnée. Le mode doit être l'un des suivants :

no

Les lignes déplacées ne sont pas mises en évidence.

default

Est un synonyme de zebra. Ceci pourrait changer pour un mode plus pertinent à l'avenir.

plain

Toute ligne qui est ajoutée dans un endroit et a été supprimée dans un autre endroit sera colorée avec color.diff.newMoved. De même, color.diff.oldMoved sera utilisée pour les lignes supprimées qui sont ajoutées ailleurs dans la différence. Ce mode détecte n'importe quelle ligne déplacée, mais il n'est pas très utile lors d'une revue pour déterminer si un bloc de code a été déplacé sans permutation.

blocks

Les blocs de texte déplacé d'au moins 20 caractères alphanumériques sont détectés de manière gourmande. Les blocs détectés sont peints en utilisant soit la couleur color.diff.(old|new)Moved. Les blocs adjacents ne peuvent pas être distingués.

zebra

Les blocs de texte déplacé sont détectés comme en mode blocks. Les blocs sont peints en utilisant soit la couleur color.diff.(old|new)Moved ou color.diff.(old|new)MovedAlternative. Le changement entre les deux couleurs indique qu'un nouveau bloc a été détecté.

dimmed-zebra

Similaire à zebra, mais une atténuation supplémentaire des parties non intéressantes du code déplacé est effectuée. Les lignes bordant deux blocs adjacents sont considérées comme intéressantes, le reste est non intéressant. dimmed_zebra est un synonyme obsolète.

-M[<n>], --find-renames[=<n>

]
Detect renames. If <n> is specified, it is a threshold on the similarity index (i.e. amount of addition/deletions compared to the file’s size). For example, -M90% means Git should consider a delete/add pair to be a rename if more than 90% of the file hasn’t changed. -l<num

>
The -M and -C options involve some preliminary steps that can detect subsets of renames/copies cheaply, followed by an exhaustive fallback portion that compares all remaining unpaired destinations to all relevant sources. (For renames, only remaining unpaired sources are relevant; for copies, all original sources are relevant.) For N sources and destinations, this exhaustive check is O(N^2). This option prevents the exhaustive portion of rename/copy detection from running if the number of source/destination files involved exceeds the specified number. Defaults to diff.renameLimit. Note that a value of 0 is treated as
unlimited.

--diff-filter=[(A|C|D|M|R|T|U|X|B)...[*]

]
Select only files that are Added (A), Copied (C), Deleted (D), Modified (M), Renamed (R), have their type (i.e. regular file, symlink, submodule, ...) changed (T), are Unmerged (U), are Unknown (X), or have had their pairing Broken (B). Any combination of the filter characters (including none) can be used. When * (All-or-none) is added to the combination, all paths are selected if there is any file that matches other criteria in the comparison; if there is no file that matches other criteria, nothing is selected.

Also, these upper-case letters can be downcased to exclude. E.g. --diff-filter=ad excludes added and deleted

paths.

Note that not all diffs can feature all types. Forinstance, les entrées copiées et renommées ne peuvent pas apparaître si la détection pour ces types est désactivée.

-S<chaîne>

Recherche les différences qui modifient le nombre d'occurrences de la <chaîne> spécifiée (c'est-à-dire ajout/suppression) dans un fichier. Destiné à l'usage du scripteur.

C'est utile lorsque vous recherchez un bloc de code exact (comme une structure) et que vous souhaitez connaître l'historique de ce bloc depuis sa création : utilisez la fonctionnalité de manière itérative pour renvoyer le bloc intéressant dans l'antécédent vers -S, et continuez jusqu'à obtenir la toute première version du bloc.

Les fichiers binaires sont également recherchés.

-G<expression_régulière>

Recherche les différences dont le texte du patch contient des lignes ajoutées/supprimées qui correspondent à <expression_régulière>.

+    return frotz(nitfol, two->ptr, 1, 0);

-O<fichier_ordre>

Contrôle l'ordre dans lequel les fichiers apparaissent dans la sortie. Ceci remplace la variable de configuration diff.orderFile (voir git-config(1)). Pour annuler diff.orderFile, utilisez -O/dev/null.

L'ordre de sortie est déterminé par l'ordre des motifs glob dans le <fichier_ordre>. Tous les fichiers dont les noms correspondent au premier motif sont affichés en premier, tous les fichiers dont les noms correspondent au second motif (mais pas au premier) sont affichés ensuite, et ainsi de suite. Tous les fichiers dont les noms ne correspondent à aucun motif sont affichés en dernier, comme s'il y avait un motif implicite de correspondance universelle à la fin du fichier. Si plusieurs noms de fichiers ont le même rang (ils correspondent au même motif mais pas aux motifs précédents), leur ordre de sortie relatif les uns par rapport aux autres est l'ordre normal.

Le <fichier_ordre> est analysé comme suit :

•Les lignes vides sont ignorées, elles peuvent donc être utilisées comme séparateurs pour la lisibilité.
•Les lignes commençant par un dièse (#) sont ignorées, elles peuvent donc être utilisées pour des commentaires. Ajoutez une barre oblique inversée (\) au début du motif s'il commence par un dièse.
•Chaque autre ligne contient un motif unique.

Les motifs ont la même syntaxe et sémantique que les motifs utilisés pour fnmatch(3) sans le drapeau FNM_PATHNAME, à l'exception qu'un nom de fichier correspond également à un motif si la suppression d'un nombre quelconque de composants finaux du nom de fichier correspond au motif. Par exemple, le motif "foo*bar" correspond à "fooasdfbar" et "foo/bar/baz/asdf" mais pas à "foobarx".

NAME

git-diff - Show changes between commits, commit and working tree, etc

SYNOPSIS

git diff [options] [<commit>] [-- [<path>>>...]]
git diff [options] <commit> <commit> [-- [<path>>>...]]
git diff [options] <commit>..<commit> [-- [<path>>>...]]
git diff [options] <blob> <blob>

DESCRIPTION

This command displays the changes between the specified commits or between a commit and the working tree. It can also display the changes between the index and the working tree. It is also the unified diff format when showing merges.

Use git diff (without any arguments) to show the differences between the working tree and the index. (git diff-index --cached --ignore-submodules HEAD)

Use git diff --cached (or git diff --staged) to show the differences between the index and the last commit (the same information that would be presented if you committed).

Use git diff <commit> to show the differences between the named commit and the working tree. (git diff-index --ignore-submodules <commit>)

Use git diff <commit1> <commit2> to show the differences between the two commits.

The other forms of invocation are similarly defined. See the EXAMPLES section for a few common use cases.

The command can also be used to compare arbitrary blobs, or a blob with a file in the working tree. This is mostly useful for scripting and is generally not used from the command line.

The diff output format can be controlled by the diff.algorithm configuration variable as specified in git-config(1).

TRAILER FORMAT

This command is often used to generate patches. The patch format is described by the file git.diff.format.txt.

diff --git a/file1 b/file2
index 1234567..abcdef0 100644
--- a/file1
+++ b/file2
@@ -1,5 +1,5 @@
 This is the first line.
-This line is removed.
+This line is added.
 This is the third line.
1.The first line is the magic hash mark "git diff". The command can be used to generate patches with this magic hash mark by specifying the -p option.

The second line is the same as the git-diff-index(1) and git-diff-tree(1) magic hash mark.

The following lines start with "--- a/" or "+++ b/". These lines are used to identify the original file and the new file.

The lines starting with '-' are the lines removed from the original file, and the lines starting with '+' are the lines added to the new file. Lines starting with ' ' are unchanged context lines. When the paths are determined to be renamed or copied, the core.quotePath configuration variable is used to decide how the pathnames are quoted.

2.All the file1 files in the output refer to files before the commit, and all the file2 files refer to files after the commit. It is incorrect to apply each change to each file sequentially. For example, this patch will swap a and b: 
diff --git a/a b/b
rename from a
rename to b
diff --git a/b b/a
rename from b
rename to a
3.Hunk headers mention the name of the function to which the hunk applies. See "Defining a custom hunk-header" in gitattributes(5) for details of how to tailor this to specific languages.

COMBINED DIFF FORMAT

Any diff-generating command can take the -c or --cc option to produce a combined diff when showing a merge. This is the default format when showing merges with git-diff(1) or git-show(1). Note also that you can give suitable --diff-merges option to any of these commands to force generation of diffs in a specific format.

A "combined diff" format looks like this:

diff --combined describe.c

+++ b/describe.c

1.It is preceded by a "git diff" header, that looks like this (when the -c option is used): 
diff --combined file

or like this (when the --cc option is used):

diff --cc file
2.It is followed by one or more extended header lines (this example shows a merge with two parents): 
index <hash>,<hash>..<hash>
mode <mode>,<mode>..<mode>
new file mode <mode>
deleted file mode <mode>,<mode>

The mode <mode>,<mode>..<mode> line appears only if at least one of the <mode> is different from the rest. Extended headers with information about detected content movement (renames and copying detection) are designed to work with the diff of two <tree-ish> and are not used by combined diff format.

3.It is followed by a two-line from-file/to-file header: 
--- a/file
+++ b/file

Similar to the two-line header for the traditional unified diff format, /dev/null is used to signal created or deleted files.

However, if the --combined-all-paths option is provided, instead of a two-line from-file/to-file, you get an N+1 line from-file/to-file header, where N is the number of parents in the merge commit:

--- a/file
--- a/file
--- a/file
+++ b/file

This extended format can be useful if rename or copy detection is active, to allow you to see the original name of the file in different parents.

4.Chunk header format is modified to prevent people from accidentally feeding it to patch -p1. Combined diff format was created for review of merge commit changes, and was not meant to be applied. The change is similar to the change in the extended index header: 
@@@ <from-file-range> <from-file-range> <to-file-range> @@@

There are (number of parents + 1) @ characters in the chunk header for combined diff format.

Unlike the traditional unified diff format, which shows two files A and B with a single column that has - (minus — appears in A but removed in B), + (plus — missing in A but added to B), or " " (space — unchanged) prefix, this format compares two or more files file1, file2,... with one file X, and shows how X differs from each of fileN. One column for each of fileN is prepended to the output line to note how X’s line is different from it.

A - character in the column N means that the line appears in fileN but it does not appear in the result. A + character in the column N means that the line appears in the result, and fileN does not have that line (in other words, the line was added, from the point of view of that parent).

In the above example output, the function signature was changed from both files (hence two - removals from both file1 and file2, plus ++ to mean one line that was added does not appear in either file1 or file2). Also, eight other lines are the same from file1 but do not appear in file2 (hence prefixed with +).

When shown by git diff-tree -c, it compares the parents of a merge commit with the merge result (i.e. file1..fileN are the parents). When shown by git diff-files -c, it compares the two unresolved merge parents with the working tree file (i.e. file1 is stage 2 aka "our version", file2 is stage 3 aka "their version").

OTHER DIFF FORMATS

The --summary option describes newly added, deleted, renamed and copied files. The --stat option adds diffstat(1) graph to the output. These options can be combined with other options, such as -p, and are meant for human consumption.

When showing a change that involves a rename or a copy, --stat output formats the pathnames compactly by combining common prefix and suffix of the pathnames. For example, a change that moves arch/i386/Makefile to arch/x86/Makefile while modifying 4 lines will be shown like this:

arch/{i386 => x86}/Makefile    |   4 +--

The --numstat option gives the diffstat(1) information but is designed for easier machine consumption. An entry in --numstat output looks like this:

1       2       README
3       1       arch/{i386 => x86}/Makefile

That is, from left to right:

1.the number of added lines;
2.a tab;
3.the number of deleted lines;
4.a tab;
5.pathname (possibly with rename/copy information);
6.a newline.

When -z output option is in effect, the output is formatted this way:

1       2       README NUL
3       1       NUL arch/i386/Makefile NUL arch/x86/Makefile NUL

That is:

1.the number of added lines;
2.a tab;
3.the number of deleted lines;
4.a tab;
5.a NUL (only exists if renamed/copied);
6.pathname in preimage;
7.a NUL (only exists if renamed/copied);
8.pathname in postimage (only exists if renamed/copied);
9.a NUL.

The extra NUL before the preimage path in renamed case is to allow scripts that read the output to tell if the current record being read is a single-path record or a rename/copy record without reading ahead. After reading added and deleted lines, reading up to NUL would yield the pathname, but if that is NUL, the record will show two paths.
