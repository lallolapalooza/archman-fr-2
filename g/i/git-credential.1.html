NOM

git-credential - Récupérer et stocker les identifiants utilisateur

SYNOPSIS

'git credential' (fill|approve|reject|capability)

DESCRIPTION

Git possède une interface interne pour stocker et récupérer des identifiants à partir d'aides spécifiques au système, ainsi que pour demander à l'utilisateur les noms d'utilisateur et les mots de passe. La commande git-credential expose cette interface aux scripts qui peuvent vouloir récupérer, stocker ou demander des identifiants de la même manière que Git. La conception de cette interface scriptable modélise l'API C interne ; voir credential.h pour plus d'informations sur les concepts.

git-credential prend une option « action » en ligne de commande (l'une parmi fill, approve ou reject) et lit une description d'identifiant sur l'entrée standard (voir FORMAT D'ENTRÉE/SORTIE).

Si l'action est fill, git-credential tentera d'ajouter les attributs « username » et « password » à la description en lisant les fichiers de configuration, en contactant les aides d'identifiants configurées, ou en demandant à l'utilisateur. Les attributs username et password de la description d'identifiant sont ensuite imprimés sur la sortie standard avec les attributs déjà fournis.

Si l'action est approve, git-credential enverra la description aux aides d'identifiants configurées, qui pourront stocker l'identifiant pour une utilisation ultérieure.

Si l'action est reject, git-credential enverra la description aux aides d'identifiants configurées, qui pourront effacer tous les identifiants stockés correspondant à la description.

Si l'action est capability, git-credential annoncera les capacités qu'il supporte sur la sortie standard.

Si l'action est approve ou reject, aucune sortie ne doit être émise.

UTILISATION TYPIQUE DE GIT CREDENTIAL

Une application utilisant git-credential utilisera généralement git credential en suivant ces étapes :

1. Générer une description d'identifiant basée sur le contexte.

Par exemple, si nous voulons un mot de passe pour https://example.com/foo.git, nous pourrions générer la description d'identifiant suivante (n'oubliez pas la ligne vide à la fin ; elle indique à git credential que l'application a fini de fournir toutes les informations qu'elle possède) :

protocol=https
host=example.com
path=foo.git
2. Demander à git-credential de nous fournir un nom d'utilisateur et un mot de passe pour cette description. Ceci est fait en exécutant git credential fill, en alimentant la description de l'étape (1) dans son entrée standard. La description complète de l'identifiant (y compris l'identifiant en soi, c'est-à-dire le login et le mot de passe) sera produite sur la sortie standard, comme ceci : 
protocol=https
host=example.com
username=bob
password=secr3t

Dans la plupart des cas, cela signifie que les attributs fournis en entrée seront répétés en sortie, mais Git peut également modifier la description de l'identifiant, par exemple en supprimant l'attribut path lorsque le protocole est HTTP(s) et que credential.useHttpPath est false.

Si git credential connaissait le mot de passe, cette étape n'aurait peut-être pas impliqué que l'utilisateur tape réellement ce mot de passe (l'utilisateur aurait pu taper un mot de passe pour déverrouiller le trouveau à la place, ou aucune interaction utilisateur n'aurait eu lieu si le trouveau était déjà déverrouillé) avant qu'il ne retourne password=secr3t.

3. Utiliser l'identifiant (par exemple, accéder à l'URL avec le nom d'utilisateur et le mot de passe de l'étape (2)), et voir s'il est accepté.
4. Rapporter le succès ou l'échec du mot de passe. Si l'identifiant a permis à l'opération de se terminer avec succès, alors il peut être marqué avec l'action « approve » pour indiquer à git credential de le réutiliser lors de sa prochaine invocation. Si l'identifiant a été rejeté pendant l'opération, utilisez l'action « reject » afin que git credential demande un nouveau mot de passe lors de sa prochaine invocation. Dans les deux cas, git credential devrait être alimenté avec la description de l'identifiant obtenue à l'étape (2) (qui contient également les champs fournis à l'étape (1)).

FORMAT ENTRÉE/SORTIE

git credential lit et/ou écrit (selon l'action utilisée) des informations d'identifiants dans son entrée/sortie standard. Ces informations peuvent correspondre soit à des clés pour lesquelles git credential obtiendra les informations de connexion (par exemple, hôte, protocole, chemin), soit aux données d'identifiants réelles à obtenir (nom d'utilisateur/mot de passe).

L'identifiant est divisé en un ensemble d'attributs nommés, avec un attribut par ligne. Chaque attribut est spécifié par une paire clé-valeur, séparée par un signe = (égal), suivie d'un saut de ligne.

La clé peut contenir n'importe quel octet sauf =, un saut de ligne ou NUL. La valeur peut contenir n'importe quel octet sauf un saut de ligne ou NUL. Une ligne, y compris le saut de ligne final, ne peut pas dépasser 65535 octets afin de permettre aux implémentations de parser efficacement.

Les attributs dont les clés se terminent par des crochets de tableau style C [] peuvent avoir plusieurs valeurs. Chaque instance d'un attribut à valeurs multiples forme une liste ordonnée de valeurs - l'ordre des attributs répétés définit l'ordre des valeurs. Un attribut à valeurs multiples vide (key[]=\n) agit pour effacer toutes les entrées précédentes et réinitialiser la liste.

Dans tous les cas, tous les octets sont traités tels quels (c'est-à-dire qu'il n'y a pas d'échappement, et on ne peut pas transmettre une valeur contenant un saut de ligne ou NUL). La liste des attributs est terminée par une ligne vide ou la fin du fichier.

Git comprend les attributs suivants :

protocol

Le protocole sur lequel l'identifiant sera utilisé (par exemple, https).

host

Le nom d'hôte distant pour un identifiant réseau. Ceci inclut le numéro de port s'il a été spécifié (par exemple, « example.com:8088 »).

path

Le chemin avec lequel l'identifiant sera utilisé. Par exemple, pour accéder à un dépôt https distant, ce sera le chemin du dépôt sur le serveur.

username

Le nom d'utilisateur de l'identifiant, si nous en avons déjà un (par exemple, provenant d'une URL, de la configuration, de l'utilisateur ou d'une aide exécutée précédemment).

password

Le mot de passe de l'identifiant, si nous demandons son stockage.

password_expiry_utc

Les mots de passe générés tels qu'un jeton d'accès OAuth peuvent avoir une date d'expiration. Lors de la lecture des identifiants depuis les aides, git credential fill ignore les mots de passe expirés. Représenté comme un temps Unix UTC, secondes depuis 1970.

oauth_refresh_token

Un jeton de rafraîchissement OAuth peut accompagner un mot de passe qui est un jeton d'accès OAuth. Les aides doivent traiter cet attribut comme confidentiel, tout comme l'attribut password. Git lui-même n'a aucun comportement spécial pour cet attribut.

url

Lorsque cet attribut spécial est lu par git credential, la valeur est analysée comme une URL et traitée comme si ses parties constitutives avaient été lues (par exemple, url=https://example.com se comporterait comme si protocol=https et host=example.com avaient été fournis). Cela peut aider les appelants à éviter d'analyser les URLs eux-mêmes.

Notez que la spécification d'un protocole est obligatoire et si l'URL ne spécifie pas de nom d'hôte (par exemple, « cert:///path/to/file ») l'identifiant contiendra un attribut hostname dont la valeur est une chaîne vide.

Les composants manquants dans l'URL (par exemple, il n'y a pas de nom d'utilisateur dans l'exemple ci-dessus) resteront non définis.

authtype

Ceci indique que le schéma d'authentification en question doit être utilisé. Les valeurs courantes pour HTTP et HTTPS incluent basic, bearer, et digest, bien que ce dernier soit non sécurisé et ne devrait pas être utilisé. Si credential est utilisé, cela peut être défini à une chaîne arbitraire appropriée au protocole en question (généralement HTTP).

Cette valeur ne doit pas être envoyée sauf si la capacité appropriée (voir ci-dessous) est fournie en entrée.

credential

L'identifiant pré-encodé, adapté au protocole en question (généralement HTTP). Si cette clé est envoyée, authtype est obligatoire, et username et password ne sont pas utilisés. Pour HTTP, Git concatène la valeur authtype et cette valeur avec un seul espace pour déterminer l'en-tête Authorization.

CAPACITÉ FORMAT

D'ENTRÉE/SORTIE

Pour git credential capability, le format est légèrement différent. D'abord, une annonce version 0 est faite pour indiquer la version actuelle du protocole, puis chaque capacité est annoncée avec une ligne comme capability authtype. Les assistants de crédentiels peuvent également implémenter ce format, à nouveau avec l'argument capability. Des lignes supplémentaires pourront être ajoutées à l'avenir ; les appelants doivent ignorer les lignes qu'ils ne comprennent

pas.

Parce qu'il s'agit d'une nouvelle partie du protocole d'assistant de crédentiels, les versions plus anciennes de Git, ainsi que certains assistants de crédentiels, peuvent ne pas le prendre en charge. Si un statut de sortie non nul est reçu, ou si la première ligne ne commence pas par le mot version et un espace, les appelants doivent supposer qu'aucune capacité n'est prise en

charge.

L'intention de ce format est de le différencier de la sortie de crédentiels de manière non ambiguë. Il est possible d'utiliser des assistants de crédentiels très simple

s (par ex., des scripts shell en ligne) qui produisent toujours une sortie identique. L'utilisation d'un format distinct permet aux utilisateurs de continuer à utiliser
cette syntaxe sans avoir à s'inquiéter de l'implémentation correcte des annonces de capacité ou de la confusion accidentelle des appelants interrogeant les capacités.
