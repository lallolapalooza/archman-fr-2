DESCRIPTIO

N

Cette commande est utilisée pour créer des checkouts épars, qui modifient l'arbre de travail pour ne contenir qu'un sous-ensemble des fichiers suivis au lieu de tous les fichiers suivis. Elle peut aussi changer le sous-ensemble de fichiers présents, ou annuler et revenir à l'état où tous les fichiers suivis sont présents dans la copie de

travail.

Le sous-ensemble de fichiers est choisi en fournissant une liste de répertoires en mode cone (par défaut), ou en fournissant une liste de motifs en mode

non-cone.

Lorsqu'un sparse-checkout est actif, les autres commandes Git se comportent un peu différemment. Par exemple, le changement de branche ne mettra pas à jour les chemins en dehors des répertoires/motifs du sparse-checkout, et git commit -a ne marquera pas comme supprimés les chemins en dehors des répertoires/motifs du sparse-checkout

.

Cela inclut l'interprétation des chemins commençant par une double guillemet (") comme des chaînes de caractères au format C. activé.

Ce mode a un certain nombre d'inconvénients, notamment le fait de ne pas fonctionner avec certaines options comme --sparse-index. Comme expliqué dans la section « Problèmes non-cone » ci-dessous, nous ne recommandons pas de

l'utiliser.

Utilisez l'option --[no-]sparse-index pour utiliser un index épars (par défaut, il n'est pas utilisé). Un index épars réduit la taille de l'index pour qu'il corresponde plus étroitement à votre définition de sparse-checkout. Cela peut offrir des avantages de performance significatifs pour des commandes comme git status ou git add. Cette fonctionnalité est encore expérimentale. Certaines commandes peuvent être plus lentes avec un index épars tant qu'elles ne sont pas correctement intégrées à la

fonctionnalité.

AVERTISSEMENT : L'utilisation d'un index épars nécessite de modifier l'index d'une manière qui n'est pas entièrement comprise par les outils externes. Si vous rencontrez des problèmes de compatibilité, exécutez git sparse-checkout init --no-sparse-index pour réécrire votre index afin qu'il ne soit pas épars. DÉTAILS INTERNES — CHECKOUT PARTIEL (SPARSE

CHECKOUT)

Le « checkout partiel » permet de remplir le répertoire de travail de manière partielle. Il utilise le bit skip-worktree (voir git-update-index(1)) pour indiquer à Git si un fichier dans le répertoire de travail mérite d'être examiné. Si le bit skip-worktree est défini et que le fichier n'est pas présent dans l'arbre de travail, alors son absence est ignorée. Git évitera de remplir le contenu de ces fichiers, ce qui rend le checkout partiel utile lorsqu'on travaille dans un dépôt avec beaucoup de fichiers, mais où seuls quelques-uns sont importants pour l'utilisateur

actuel.

Le fichier $GIT_DIR/info/sparse-checkout est utilisé pour définir le bitmap de référence skip-worktree. Lorsque Git met à jour le répertoire de travail, il met à jour les bits s

kip-worktree dans l'index en se basant sur ce fichier. Les fichiers correspondant a
ux motifs du fichier apparaîtront dans le répertoire de travail, et les autres non.

DÉTAILS INTERNES — PROBLÈMES DU MODE

NON-CÔNE

Le fichier $GIT_DIR/info/sparse-checkout rempli par les sous-commandes set et add est défini comme un ensemble de motifs (un par ligne) utilisant la même syntaxe que les fichiers .gitignore. En mode cône, ces motifs sont limités à la correspondance avec des répertoires (et les utilisateurs n'ont besoin que de fournir ou de voir des noms de répertoires), tandis qu'en mode non-cône, tout motif de style gitignore est autorisé. L'utilisation des motifs complets de style gitignore en mode non-cône présente un certain nombre d'inconvénients

:
•Fondamentalement, cela rend divers processus de mise à jour de l'arbre de travail (pull, merge, rebase, switch, reset, checkout, etc.) nécessiter O(N*M) correspondances de motifs, où N est le nombre de motifs et M est le nombre de chemins dans l'index. Cela ne passe pas bien à
l'échelle.
•Éviter le problème de mise à l'échelle doit se faire en limitant le nombre de motifs en spécifiant un nom de répertoire de tête ou un
glob.
•Passer des globs sur la ligne de commande est sujet aux erreurs car les utilisateurs peuvent oublier de citer le glob, ce qui fait que le shell l'étend en tous les fichiers correspondants et les passe tous individuellement à sparse-checkout set/add. Bien que cela puisse aussi être un problème avec par ex. « git grep -- *.c », les erreurs avec grep/log/status apparaissent dans la sortie immédiate. Avec sparse-checkout, l'erreur est enregistrée au moment où la commande sparse-checkout est exécutée et pourrait ne pas poser de problème jusqu'à ce que l'utilisateur change de branche ou fasse un rebase ou un merge plus tard, créant ainsi un décalage entre l'erreur de l'utilisateur et le moment où il a la chance de la détecter/remarquer
.
•Lié à l'élément précédent, sparse-checkout a une sous-commande add mais pas de sous-commande remove. Même si une sous-commande remove était ajoutée, annuler un glob accidentellement non cité risque de « supprimer trop de choses », car cela peut supprimer des entrées qui avaient été incluses avant l'ajout
accidentel.
•Le mode non-cône utilise des motifs de style gitignore pour sélectionner ce qu'il faut inclure (à l'exception des motifs négatifs), tandis que les fichiers .gitignore utilisent des motifs de style gitignore pour sélectionner ce qu'il faut exclure (à l'exception des motifs négatifs). La documentation sur les motifs de style gitignore ne parle généralement pas en termes de correspondance ou de non-correspondance, mais de ce que l'utilisateur veut « exclure ». Cela peut causer de la confusion pour les utilisateurs qui essaient d'apprendre à spécifier des motifs de sparse-checkout pour obtenir le comportement
désiré.
•Chaque autre sous-commande git qui souhaite fournir une « correspondance de motifs de chemin spéciale » d'une sorte ou d'une autre utilise des pathspecs, mais le mode non-cône de sparse-checkout utilise des motifs gitignore, ce qui semble
incohérent.
•Il a des cas limites où le « bon » comportement n'est pas clair. Deux exemples :

Premièrement, deux utilisateurs sont dans un sous-répertoire, et le premier

exécute 
git sparse-che
ckout set '/top
level-dir/*.c'

tandis que le second

exécute 
git sparse-c
heckout set
relative-dir

Ces arguments devraient-ils être translittérés

en 
current/subd
irectory/topl
evel-dir/*.c

e

t 
current/subdirectory/relative-d
i
r

avant d'être insérés dans le fichier sparse-checkout ? L'utilisateur qui a tapé la première commande est probablement conscient que les arguments de set/add doivent être des motifs en mode non-cône, et ne serait probablement pas content d'une telle translittération. Cependant, beaucoup de motifs de style gitignore sont juste des chemins, ce qui est peut-être ce à quoi pensait l'utilisateur qui a tapé la deuxième commande, et il serait mécontent si son argument n'était pas

translittéré.

Deuxièmement, sur quoi la complétion bash devrait-elle se baser pour les commandes set/add pour les utilisateurs en mode non-cône ? Si elle suggère des chemins, aggrave-t-elle le problème ci-dessus ? De plus, si elle suggère des chemins, que se passe-t-il si l'utilisateur a un fichier ou un répertoire dont le nom commence par un ! ou un # ou contient un *, \, ?, [, ou un ] dans son nom ? Et si elle suggère des chemins, complétera-t-elle « /pro » en « /proc » (dans le système de fichiers racine) plutôt qu'en « /progress.txt » dans le répertoire courant ? (Notez que les utilisateurs voudront probablement commencer les chemins par un / en mode non-cône, pour la même raison que les fichiers .gitignore en ont souvent un.) La complét

ion sur des fichiers ou des répertoires pourrait d

•La flexibilité excessive a rendu d'autres extensions essentiellement impraticables. --sparse-index est probablement impossible en mode non-cône ; même si c'est d'une manière ou d'une autre faisable, cela aurait été beaucoup plus de travail à implémenter et aurait peut-être été trop lent en pratique. Certaines idées pour ajouter un couplage entre les clones partiels et les checkouts partiels ne sont praticables qu'avec un ensemble de chemins plus restreint
également.

Pour toutes ces raisons, le mode no

n-cône est obsolète. Veuillez p
asser à l'utilisation du mode cône.

DÉTAILS INTERNES — GESTION DU MODE

CÔNE

Le « mode cône », qui est le par défaut, vous permet de spécifier uniquement quels répertoires inclure. Pour tout répertoire spécifié, tous les chemins sous ce répertoire seront inclus, et tous les chemins immédiatement sous les répertoires de tête (y compris le répertoire de premier niveau) seront également inclus. Ainsi, si vous spécifiez le répertoire Documentation/technical/, votre checkout partiel contiendra

:
•tous les fichiers du répertoire de premier
niveau
•tous les fichiers immédiatement sous
Documentation/
•tous les fichiers à toute profondeur sous Documentation/technical
/

De plus, en mode cône, même si aucun répertoire n'est spécifié, les fichiers du répertoire de premier niveau seront

inclus.

Lors du changement des motifs de sparse-checkout en mode cône, Git inspectera chaque répertoire suivi qui n'est pas dans le cône de sparse-checkout pour voir s'il contient des fichiers non suivis. Si tous ces fichiers sont ignorés en raison des motifs .gitignore, le répertoire sera supprimé. Si l'un des fichiers non suivis dans ce répertoire n'est pas ignoré, aucune suppression n'aura lieu dans ce répertoire et un message d'avertissement apparaîtra. Si ces fichiers sont importants, réinitialisez votre définition de sparse-checkout pour qu'ils soient inclus, utilisez git add et git commit pour les enregistrer, puis supprimez manuellement les fichiers restants pour vous assurer que Git peut se comporter de manière

optimale.

Voir aussi la section « Détails internes — Ensemble de motifs en mode cône » pour apprendre comment les répertoires sont transformés en interne en un sous-ensemble de l'ensemble complet de motifs de

sparse-checkout
.

DÉTAILS INTERNES — ENSEMBLE COMPLET DE

MOTIFS

L'ensemble complet de motifs permet des correspondances de motifs arbitraires et des règles d'inclusion/exclusion complexes. Celles-ci peuvent entraîner O(N*M) correspondances de motifs lors de la mise à jour de l'index, où N est le nombre de motifs et M est le nombre de chemins dans l'index. Pour contrer ce problème de performance, un ensemble de motifs plus restreint est autorisé lorsque core.sparseCheckoutCone est

activé.

Le fichier sparse-checkout utilise la même syntaxe que les fichiers .gitignore ; voir gitignore(5) pour les détails. Ici, cependant, les motifs sont généralement utilisés pour sélectionner quels fichiers inclure plutôt que quels fichiers exclure. (Cependant, cela peut être un peu déroutant puisque les motifs de style gitignore ont des négations définies par des motifs qui commencent par un !, donc vous pouvez aussi sélectionner des fichiers à ne pas inclure.

)

Par exemple, pour sélectionner tout, puis pour supprimer le fichier indésirable (afin que chaque fichier apparaisse dans votre arbre de travail à l'exception du fichier nommé indésirable)

: 
git sparse-checko
ut set --no-cone
'/*' '!unwanted'

Ces motifs sont simplement placés dans le $GIT_DIR/info/sparse-checkout tel quel, de sorte que le contenu de ce fichier à ce stade

serait 
/*
!
unwa
nted

Voir aussi la section « Sparse Checkout » de git-read-tree(1) pour en savoir plus sur les motifs de

style gitignore utilisé
s dans les sparse checkouts.

DÉTAILS — ENSEMBLE DE MOTIFS

CONE

En mode cone, seuls les répertoires sont acceptés, mais ils sont traduits dans les mêmes motifs de style gitignore que ceux utilisés dans l'ensemble complet de motifs. Nous désignons les motifs particuliers utilisés dans ces modes comme étant de l'un des deux types suivants

:
1.Récursif : Tous les chemins à l'intérieur d'un répertoire sont
inclus.
2.Parent : Tous les fichiers directement à l'intérieur d'un répertoire sont
inclus.

Puisque le mode cone inclut toujours les fichiers au niveau supérieur, lors de l'exécution de git sparse-checkout set sans répertoire spécifié, le répertoire de premier niveau est ajouté comme motif parent. À ce stade, le fichier sparse-checkout contient les motifs suivants

: 
/*
!/
*/

Cela signifie « inclure tout ce qui se trouve directement sous le répertoire de premier niveau, mais rien à aucun niveau inférieur à celui-ci.

»

Lorsque le mode cone est activé, la git sparse-checkout set sous-commande prend une liste de répertoires. La commande git sparse-checkout set A/B/C définit le répertoire A/B/C comme motif récursif, les répertoires A et A/B sont ajoutés comme motifs parents. Le fichier sparse-checkout résultant est

maintenant 
/*
!/*/
/A/
!/
A/*/ /A/B/ !/
A/B/*/ /A/B/C/

Ici, l'ordre compte, de sorte que les motifs négatifs sont annulés par les motifs positifs qui apparaissent plus bas dans le

fichier.

Sauf si core.sparseCheckoutCone est explicitement défini à false, Git analysera le fichier sparse-checkout en attendant des motifs de ces types. Git émettra un avertissement si les motifs ne correspondent pas. Si les motifs correspondent au format attendu, Git utilisera des algorithmes de hachage plus rapides pour calculer l'inclusion dans le sparse-checkout. S'ils ne correspondent pas, git se comportera comme si core.sparseCheckoutCone était false, quel que soit son

paramètre.

Dans le cas du mode cone, malgré le fait que des motifs complets soient écrits dans le fichier $GIT_DIR/info/sparse-checkout, la git sparse-checkout list sous-commande listera les répertoires qui définissent les motifs récursifs. Pour l'exemple de fichier sparse-checkout ci-dessus, la sortie est la suivante

: 
$ git spars
e-checkout
list A/B/C

Si core.ignoreCase=true, l'algorithme de correspondance de motifs utilisera une vérification insensible à la casse. Cela corrige les noms de fichiers dont la casse ne correspond pas dans la commande git sparse-checkout set pour reflét

er le cone attendu dans l
e répertoire de travail.

DÉTAILS —

SOUS-MODULES

Si votre dépôt contient un ou plusieurs sous-modules, les sous-modules sont peuplés en fonction des interactions avec la git commande submodule. Plus précisément, git submodule init -- <path> s'assurera que le sous-module à <path> est présent, tandis que git submodule deinit [-f] -- <path> supprimera les fichiers du sous-module à <path> (y compris tout fichier non suivi, modification non commitée et historique non poussé). De la même manière que sparse-checkout supprime des fichiers de l'arbre de travail mais laisse toujours des entrées dans l'index, les sous-modules déinitialisés sont supprimés du répertoire de travail mais ont toujours une entrée dans

l'index.

Puisque les sous-modules peuvent avoir des modifications non poussées ou des fichiers non suivis, les supprimer pourrait entraîner une perte de données. Ainsi, changer les règles d'inclusion/exclusion de sparse n'entraînera pas la suppression d'un sous-module déjà extrait de la copie de travail. Autrement dit, tout comme checkout n'entraînera pas la suppression ou l'initialisation automatique des sous-modules même lors du changement de branche entre des branches qui suppriment ou ajoutent des sous-modules, l'utilisation de sparse-checkout pour réduire ou étendre la portée des fichiers « intéressants » n'entraînera pas non plus la déinitialisation ou l'initialisation automatique des

sous-modules.

De plus, les faits ci-dessus signifient qu'il existe plusieurs raisons pour lesquelles des fichiers « suivis » peuvent être absents de la copie de travail : application du motif de sparsité par sparse-checkout, et état d'initialisation des sous-modules.
