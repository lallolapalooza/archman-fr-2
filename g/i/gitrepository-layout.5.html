NOM

gitrepository-layout - Disposition du dépôt Git

SYNTAXE

$GIT_DIR/*

DESCRIPTION

Un dépôt Git se présente sous deux formes différentes :

•un répertoire .git à la racine de l'arbre de travail ;
•un répertoire <projet>.git qui est un dépôt nu (c'est-à-dire sans son propre arbre de travail), généralement utilisé pour échanger des historiques avec d'autres en y poussant et en en extrayant.

Note : Vous pouvez également avoir un fichier texte simple .git à la racine de votre arbre de travail, contenant gitdir: <chemin> pour pointer vers le répertoire réel qui contient le dépôt. Ce mécanisme est appelé un gitfile et est généralement géré via les commandes git submodule et git worktree. Il est souvent utilisé pour l'arbre de travail d'un sous-module extrait, pour vous permettre dans le super-projet contenant de faire git checkout d'une branche qui n'a pas le sous-module. Le checkout doit supprimer l'intégralité de l'arbre de travail du sous-module, sans perdre le dépôt du sous-module.

Les éléments suivants peuvent exister dans un dépôt Git.

objects

Stockage des objets associé à ce dépôt. Normalement, un stockage d'objets est autonome (c'est-à-dire que tous les objets référencés par un objet trouvé dans celui-ci s'y trouvent également), mais il existe quelques façons de le violer.
1.Vous pouvez avoir un dépôt incomplet mais utilisable localement en créant un clone superficiel. Voir git-clone(1).
2.Vous pouvez utiliser les mécanismes objects/info/alternates ou $GIT_ALTERNATE_OBJECT_DIRECTORIES pour emprunter des objets à d'autres stockages d'objets. Un dépôt avec ce type de stockage d'objets incomplet n'est pas adapté à être publié pour une utilisation avec des transports muets, mais sinon il est correct tant que objects/info/alternates pointe vers les stockages d'objets dont il emprunte.

Ce répertoire est ignoré si $GIT_COMMON_DIR est défini et que "$GIT_COMMON_DIR/objects" sera utilisé à la place.

objects/[0-9a-f][0-9a-f]

Un nouvel objet est stocké dans son propre fichier. Les objets sont répartis sur 256 sous-répertoires en utilisant les deux premiers caractères du nom de l'objet sha1 pour maintenir le nombre d'entrées de répertoire dans objects lui-même à un niveau gérable. Les objets trouvés ici sont souvent appelés objets décompressés (ou légers).

objects/pack

Les packs (fichiers qui stockent de nombreux objets sous forme compressée, ainsi que des fichiers d'index pour permettre un accès aléatoire) se trouvent dans ce répertoire.

objects/info

Des informations supplémentaires sur le stockage des objets sont enregistrées dans ce répertoire.

objects/info/packs

Ce fichier est destiné à aider les transports muets à découvrir quels packs sont disponibles dans ce stockage d'objets. Chaque fois qu'un pack est ajouté ou supprimé, git update-server-info doit être exécuté pour maintenir ce fichier à jour si le dépôt est publié pour des transports muets. git repack le fait par défaut.

objects/info/alternates

Ce fichier enregistre les chemins vers les stockages d'objets alternatifs à partir desquels ce stockage d'objets emprunte des objets, un nom de chemin par ligne. Notez que non seulement les outils Git natifs l'utilisent localement, mais le téléchargeur HTTP essaie également de l'utiliser à distance ; cela fonctionnera généralement si vous avez des chemins relatifs (relatifs à la base de données d'objets, pas au dépôt !) dans votre fichier alternates, mais cela ne fonctionnera pas si vous utilisez des chemins absolus, sauf si le chemin absolu dans le système de fichiers et l'URL Web sont identiques. Voir également objects/info/http-alternates.

objects/info/http-alternates

Ce fichier enregistre les URL des stockages d'objets alternatifs à partir desquels ce stockage d'objets emprunte des objets, à utiliser lorsque le dépôt est récupéré via HTTP.

refs

Les références sont stockées dans des sous-répertoires de ce répertoire. La commande git prune sait préserver les objets accessibles depuis les références trouvées dans ce répertoire et ses sous-répertoires. Ce répertoire est ignoré (sauf refs/bisect, refs/rewritten et refs/worktree) si $GIT_COMMON_DIR est défini et que "$GIT_COMMON_DIR/refs" sera utilisé à la place.

refs/heads/nom

enregistre les objets commit de la pointe de l'arbre de la branche nom

refs/tags/nom

enregistre n'importe quel nom d'objet (pas nécessairement un objet commit, ou un objet tag qui pointe vers un objet commit).

refs/remotes/nom

enregistre les objets commit de la pointe de l'arbre des branches copiées d'un dépôt distant.

refs/replace/<obj-sha1>

enregistre le SHA-1 de l'objet qui remplace <obj-sha1>. Ceci est similaire à info/grafts et est utilisé et maintenu en interne par git-replace(1). De telles références peuvent être échangées entre dépôts alors que les greffons ne le peuvent pas.

packed-refs

enregistre les mêmes informations que refs/heads/, refs/tags/, et leurs similaires d'une manière plus efficace. Voir git-pack-refs(1). Ce fichier est ignoré si $GIT_COMMON_DIR est défini et que "$GIT_COMMON_DIR/packed-refs" sera utilisé à la place.

HEAD

Une référence symbolique (voir glossaire) vers l'espace de noms refs/heads/ décrivant la branche active actuellement. Cela n'a pas beaucoup de sens si le dépôt n'est associé à aucun arbre de travail (c'est-à-dire un dépôt nu), mais un dépôt Git valide doit avoir le fichier HEAD ; certains porcelaines peuvent l'utiliser pour deviner la branche "par défaut" désignée du dépôt (généralement master). Il est légal si la branche nommée nom n'existe pas (encore). Dans certaines configurations héritées, c'est un lien symbolique au lieu d'une référence symbolique qui pointe vers la branche actuelle.

HEAD peut également enregistrer directement un commit spécifique, au lieu d'être une référence symbolique pointant vers la branche actuelle. Un tel état est souvent appelé HEAD détaché. Voir git-checkout(1) pour les détails.

config

Fichier de configuration spécifique au dépôt. Ce fichier est ignoré si $GIT_COMMON_DIR est défini et que "$GIT_COMMON_DIR/config" sera utilisé à la place.

config.worktree

Fichier de configuration spécifique au répertoire de travail pour le répertoire de travail principal dans une configuration multi-répertoires de travail (voir git-worktree(1)).

branches

Une façon dépréciée de stocker des raccourcis à utiliser pour spécifier une URL pour git fetch, git pull et git push. Un fichier peut être stocké sous branches/<nom> et ensuite nom peut être donné à ces commandes à la place de l'argument dépôt. Voir la section REMOTES dans git-fetch(1) pour les détails. Ce mécanisme est obsolète et peu susceptible d'être trouvé dans les dépôts modernes. Ce répertoire est ignoré si $GIT_COMMON_DIR est défini et que "$GIT_COMMON_DIR/branches" sera utilisé à la place.

Git arrêtera de lire les remotes à partir de ce répertoire dans Git 3.0.

hooks

Les hooks sont des scripts de personnalisation utilisés par diverses commandes Git. Une poignée de hooks d'exemple sont installés lorsque git init est exécuté, mais tous sont désactivés par défaut. Pour les activer, le suffixe .sample doit être supprimé du nom du fichier en le renommant. Lisez githooks(5) pour plus de détails sur chaque hook. Ce répertoire est ignoré si $GIT_COMMON_DIR est défini et que "$GIT_COMMON_DIR/hooks" sera utilisé à la place.

common

Lorsque plusieurs arbres de travail sont utilisés, la plupart des fichiers dans $GIT_DIR sont par arbre de travail, à quelques exceptions connues près. Tous les fichiers sous common seront cependant partagés entre tous les arbres de travail.

index

Le fichier d'index actuel pour le dépôt. Il ne se trouve généralement pas dans un dépôt nu.

sharedindex.<SHA-1>

La partie d'index partagée, à référencer par $GIT_DIR/index et d'autres fichiers d'index temporaires. Valide uniquement en mode index divisé.

info

Des informations supplémentaires sur le dépôt sont enregistrées dans ce répertoire. Ce répertoire est ignoré si $GIT_COMMON_DIR est défini et que "$GIT_COMMON_DIR/info" sera utilisé à la place.

info/refs

Ce fichier aide les transports muets à découvrir quelles références sont disponibles dans ce dépôt. Si le dépôt est publié pour des transports muets, ce fichier doit être régénéré par git update-server-info chaque fois qu'une balise ou une branche est créée ou modifiée. Ceci est normalement fait à partir du hook hooks/update, q
qui est exécuté par la git-receive-pack commande lorsque vous git push dans le dépôt.

info/grafts

Ce fichier enregistre des informations d'ascendance fictives de commit, pour faire semblant que l'ensemble des parents qu'un commit possède est différent de la façon dont le commit a été réellement créé. Un enregistrement par ligne décrit un commit et ses parents fictifs en listant leurs noms d'objets hexadécimaux de 40 octets séparés par un espace et terminés par un saut de ligne.

Notez que le mécanisme des greffes est obsolète et peut entraîner des problèmes lors du transfert d'objets entre des dépôts ; voir git-replace(1) pour un système plus flexible et robuste pour faire la même chose.

info/exclude

Ce fichier, par convention parmi les Porcelains, stocke la liste des motifs d'exclusion. .gitignore est le fichier d'ignorance par répertoire. git status, git add, git rm et git clean le consultent mais les commandes Git de base ne le consultent pas. Voir aussi : gitignore(5).

info/attributes

Définit quels attributs attribuer à un chemin, similaire aux fichiers .gitattributes par répertoire. Voir aussi : gitattributes(5).

info/sparse-checkout

Ce fichier stocke les motifs de extraction creuse. Voir aussi : git-read-tree(1).

remotes

Stocke des raccourcis pour les URL et des noms de références par défaut à utiliser lors de l'interaction avec des dépôts distants via les commandes git fetch, git pull et git push . Voir la section REMOTES dans git-fetch(1) pour plus de détails. Ce mécanisme est hérité et peu susceptible d'être trouvé dans les dépôts modernes. Ce répertoire est ignoré si $GIT_COMMON_DIR est défini et "$GIT_COMMON_DIR/remotes" sera utilisé à la place.

Git cessera de lire les distants depuis ce répertoire dans Git 3.0.

logs

Les enregistrements des modifications apportées aux références sont stockés dans ce répertoire. Voir git-update-ref(1) pour plus d'informations. Ce répertoire est ignoré (sauf logs/HEAD) si $GIT_COMMON_DIR est défini et "$GIT_COMMON_DIR/logs" sera utilisé à la place.

logs/refs/heads/name

Enregistre toutes les modifications apportées à la pointe de la branche nommée name.

logs/refs/tags/name

Enregistre toutes les modifications apportées à l'étiquette nommée name.

shallow

Ceci est similaire à info/grafts mais est utilisé et maintenu en interne par le mécanisme de clonage superficiel. Voir l'option --depth de git-clone(1) et git-fetch(1). Ce fichier est ignoré si $GIT_COMMON_DIR est défini et "$GIT_COMMON_DIR/shallow" sera utilisé à la place.

commondir

Si ce fichier existe, $GIT_COMMON_DIR (voir git(1)) sera défini sur le chemin spécifié dans ce fichier s'il n'est pas explicitement défini. Si le chemin spécifié est relatif, il est relatif à $GIT_DIR. Le dépôt avec commondir est incomplet sans le dépôt pointé par "commondir".

modules

Contient les dépôts git des sous-modules.

worktrees

Contient les données administratives pour les arbres de travail liés. Chaque sous-répertoire contient la partie de l'arbre de travail liée. Ce répertoire est ignoré si $GIT_COMMON_DIR est défini, auquel cas "$GIT_COMMON_DIR/worktrees" sera utilisé à la place.

worktrees/<id>/gitdir

Un fichier texte contenant le chemin absolu vers le fichier .git qui pointe ici. Ceci est utilisé pour vérifier si le dépôt lié a été supprimé manuellement et qu'il n'est plus nécessaire de conserver ce répertoire. Le mtime de ce fichier doit être mis à jour chaque fois que le dépôt lié est accédé.

worktrees/<id>/locked

Si ce fichier existe, l'arbre de travail lié peut être sur un support portable et ne pas être disponible. La présence de ce fichier empêche worktrees/<id> d'être élagué automatiquement ou manuellement par git worktree prune. Le fichier peut contenir une chaîne expliquant pourquoi le dépôt est verrouillé.

worktrees/<id>/config.worktree

Fichier de configuration spécifique au répertoire de travail.

VERSIONS DE FORMAT DE DÉPÔT GIT

Chaque dépôt git est marqué avec une version numérique dans la clé core.repositoryformatversion de son fichier config . Cette version spécifie les règles pour opérer sur les données du dépôt sur disque. Une implémentation de git qui ne comprend pas une version particulière annoncée par un dépôt sur disque NE DOIT PAS opérer sur ce dépôt ; le faire risque non seulement de produire des résultats incorrects, mais aussi de perdre réellement des données.

En raison de cette règle, les augmentations de version doivent être gardées à un minimum absolu. Nous préférons généralement ces stratégies :

•augmenter les numéros de version de format de fichiers de données individuels (par ex., index, fichiers pack, etc.). Cela ne restreint les incompatibilités qu'à ces fichiers.
•introduire de nouvelles données qui se dégradent gracieusement lorsqu'elles sont utilisées par d'anciens clients (par ex., les fichiers bitmap de pack sont ignorés par les anciens clients, qui ne profitent tout simplement pas de l'optimisation qu'ils fournissent).

Une augmentation de version de format de dépôt entier ne devrait faire partie que d'un changement qui ne peut pas être versionné indépendamment. Par exemple, si l'on devait changer les règles d'accessibilité des objets, ou les règles de verrouillage des références, cela nécessiterait une augmentation de la version de format du dépôt.

Notez que cela ne s'applique qu'à l'accès direct au contenu disque du dépôt. Un ancien client qui ne comprend que le format 0 peut toujours se connecter via git:// à un dépôt utilisant le format 1, tant que le processus serveur comprend le format 1.

La stratégie préférée pour déployer une augmentation de version (que ce soit pour l'ensemble du dépôt ou pour un fichier unique) est d'apprendre à git à lire le nouveau format, et permettre d'écrire le nouveau format avec un commutateur de configuration ou une option de ligne de commande (pour l'expérimentation ou pour ceux qui ne se soucient pas de la rétrocompatibilité avec les anciennes versions de git). Ensuite, après une longue période permettant à la capacité de lecture de devenir courante, nous pouvons passer à l'écriture du nouveau format par défaut.

Les versions de format actuellement définies sont :

Version 0

C'est le format défini par la version initiale de git, incluant mais sans s'y limiter le format du répertoire du dépôt, du fichier de configuration du dépôt, et du stockage des objets et des références. Spécifier le comportement complet de git dépasse le cadre de ce document.

Version 1

Ce format est identique à la version 0, avec les exceptions suivantes :

1.Lors de la lecture de la variable core.repositoryformatversion , une implémentation de git qui supporte la version 1 DOIT aussi lire toutes les clés de configuration trouvées dans la section extensions du fichier de configuration.
2.Si un dépôt de version 1 spécifie des clés extensions.* que le git en cours d'exécution n'a pas implémentées, l'opération NE DOIT PAS continuer. De même, si la valeur d'une clé connue n'est pas comprise par l'implémentation, l'opération NE DOIT PAS continuer.

Notez que si aucune extension n'est spécifiée dans le fichier de configuration, alors core.repositoryformatversion DEVRAIT être défini à 0 (le définir à 1 n'apporte aucun avantage, et rend le dépôt incompatible avec les anciennes implémentations de git).

Les extensions définies sont données dans la section extensions.* de git-config(1). Toute implémentation souhaitant définir une nouvelle extension devrait en faire une note là-bas, afin de revendiquer le nom.
