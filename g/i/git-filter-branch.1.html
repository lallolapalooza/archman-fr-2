AVERTISSEME

NT

git filter-branch comporte une pléthore de pièges qui peuvent produire des altérations non évidentes de la réécriture d'historique souhaitée (et peuvent vous laisser peu de temps pour enquêter sur de tels problèmes, car ses performances sont abyssales). Ces problèmes de sécurité et de performance ne peuvent pas être corrigés de manière rétrocompatible et, par conséquent, son utilisation n'est pas recommandée. Veuillez utiliser un outil de filtrage d'historique alternatif tel que git filter-repo[1]. Si vous devez toujours utiliser git filter-branch, veuillez lire attentivement la section intitulée « SÉCURITÉ » (et la section intitulée « PERFORMANCES ») po

ur connaître les mines terres de filter-branch, puis éviter vigo
ureusement autant que possible les dangers qui y sont énumérés.

DESCRIPTIO

N

Vous permet de réécrire l'historique des révisions Git en réécrivant les branches mentionnées dans les <options-rev-list>, en appliquant des filtres personnalisés à chaque révision. Ces filtres peuvent modifier chaque arbre (par ex. supprimer un fichier ou exécuter une réécriture perl sur tous les fichiers) ou des informations sur chaque commit. Sinon, toutes les informations (y compris les dates de commit originales ou les informations de fusion) seront

préservées.

La commande ne réécrira que les références positives mentionnées dans la ligne de commande (par ex. si vous passez a..b, seul b sera réécrit). Si vous ne spécifiez aucun filtre, les commits seront re-commités sans aucun changement, ce qui n'aurait normalement aucun effet. Néanmoins, cela peut être utile à l'avenir pour compenser certains bugs de Git ou autres, par conséquent un tel usage est

autorisé.

NOTE : Cette commande prend en compte le fichier .git/info/grafts et les références dans l'espace de noms refs/replace/. Si vous avez des grafts ou des références de remplacement définis, l'exécution de cette commande les rendra

permanents.

AVERTISSEMENT ! L'historique réécrit aura des noms d'objets différents pour tous les objets et ne convergera pas avec la branche originale. Vous ne pourrez pas facilement pousser et distribuer la branche réécrite par-dessus la branche originale. Veuillez ne pas utiliser cette commande si vous ne connaissez pas toutes ses implications, et évitez de l'utiliser de toute façon si un simple commit unique suffirait à résoudre votre problème. (Voir la section « RÉCUPÉRATION APRÈS UNE REBASE EN AMONT » dans git-rebase(1) pour plus d'informations sur la réécriture d'historique publié.

)

Vérifiez toujours que la version réécrite est correcte : les références originales, si elles diffèrent des réécrites, seront stockées dans l'espace de noms refs/original/

.

Notez que, comme cette opération est très coûteuse en E/S, il peut être judicieux de rediriger le répertoire temporaire hors du disque avec l'option -d, par ex. sur tmpfs. On rapporte que l'accélération est très

perceptible.

Filtre

s

Les filtres sont appliqués dans l'ordre listé ci-dessous. L'argument <commande> est toujours évalué dans le contexte du shell à l'aide de la commande eval (avec la notable exception du filtre de commit, pour des raisons techniques). Auparavant, la variable d'environnement $GIT_COMMIT sera définie pour contenir l'identifiant du commit en cours de réécriture. De plus, GIT_AUTHOR_NAME, GIT_AUTHOR_EMAIL, GIT_AUTHOR_DATE, GIT_COMMITTER_NAME, GIT_COMMITTER_EMAIL et GIT_COMMITTER_DATE sont extraits du commit actuel et exportés dans l'environnement, afin d'affecter les identités de l'auteur et du committer du commit de remplacement créé par git-commit-tree(1) après l'exécution des

filtres.

Si une quelconque évaluation de <commande> renvoie un code de sortie non nul, l'ensemble de l'opération sera

annulé.

Une fonction map est disponible qui prend un argument « sha1 id original » et renvoie un « sha1 id réécrit » si le commit a déjà été réécrit, et « sha1 id original » sinon ; la fonction map peut renvoyer plusieurs identifiants su

r des lignes séparées
si votre filtre de commit
a émis plusieurs commits.

OPTION

S

--setup

<commande>
Ceci n'est pas un vrai filtre exécuté pour chaque commit mais une configuration unique juste avant la boucle. Par conséquent, aucune variable spécifique à un commit n'est encore définie. Les fonctions ou variables définies ici peuvent être utilisées ou modifiées dans les étapes de filtrage suivantes, à l'exception du filtre de commit, pour des raisons
techniques.

--subdirectory-filter

<répertoire>
Ne considère que l'historique qui touche le sous-répertoire donné. Le résultat contiendra ce répertoire (et seulement lui) comme racine du projet. Implique la section intitulée « Remapper à l'ancêtre »
.

--env-filter

<commande>
Ce filtre peut être utilisé si vous devez seulement modifier l'environnement dans lequel le commit sera effectué. Plus précisément, vous pourriez vouloir réécrire les variables d'environnement nom/courriel/date de l'auteur/committer (voir git-commit-tree(1) pour les détails)
.

--tree-filter

<commande>
C'est le filtre pour réécrire l'arbre et son contenu. L'argument est évalué dans le shell avec le répertoire de travail défini à la racine de l'arbre extrait. Le nouvel arbre est ensuite utilisé tel quel (les nouveaux fichiers sont ajoutés automatiquement, les fichiers disparus sont supprimés automatiquement - ni les fichiers .gitignore ni aucune autre règle d'ignorance N'ONT AUCUN EFFET !)
.

--index-filter

<commande>
C'est le filtre pour réécrire l'index. Il est similaire au filtre d'arbre mais n'extrait pas l'arbre, ce qui le rend beaucoup plus rapide. Souvent utilisé avec git rm --cached --ignore-unmatch ..., voir EXEMPLES ci-dessous. Pour les cas compliqués, voir git-update-in
dex(1).

--parent-filter

<commande>
C'est le filtre pour réécrire la liste des parents du commit. Il recevra la chaîne de parents sur stdin et doit renvoyer la nouvelle chaîne de parents sur stdout. La chaîne de parents est au format décrit dans git-commit-tree(1) : vide pour le commit initial, "-p parent" pour un commit normal et "-p parent1 -p parent2 -p parent3 ..." pour un commit de
fusion.

--msg-filter

<commande>
C'est le filtre pour réécrire les messages de commit. L'argument est évalué dans le shell avec le message de commit original sur l'entrée standard ; sa sortie standard est utilisée comme nouveau message de
commit.

--commit-filter

<commande>
C'est le filtre pour effectuer le commit. Si ce filtre est spécifié, il sera appelé à la place de la commande git commit-tree, avec des arguments de la forme "<ID_ARBRE> [(-p <ID_COMMIT_PARENT>)...]" et le message de journal sur stdin. L'identifiant du commit est attendu sur stdout.

En tant qu'extension spéciale, le filtre de commit peut émettre plusieurs identifiants de commit ; dans ce cas, les enfants réécrits du commit original auront tous comme parents ces

identifiants.

Vous pouvez utiliser la fonction de commodité map dans ce filtre, et d'autres fonctions de commodité aussi. Par exemple, appeler skip_commit "$@" laissera de côté le commit actuel (mais pas ses changements ! Si vous voulez cela, utilisez plutôt git rebase)

.

Vous pouvez aussi utiliser git_commit_non_empty_tree "$@" au lieu de git commit-tree "$@" si vous ne souhaitez pas conserver les commits a

vec un seul parent et qui n'app
ortent aucun changement à l'arbre.

--tag-name-filter

<commande>
C'est le filtre pour réécrire les noms de tags. Lorsqu'il est passé, il sera appelé pour chaque référence de tag qui pointe vers un objet réécrit (ou vers un objet tag qui pointe vers un objet réécrit). Le nom de tag original est passé via l'entrée standard, et le nouveau nom de tag est attendu sur la sortie standard.

Les tags originaux ne sont pas supprimés, mais peuvent être écrasés ; utilisez "--tag-name-filter cat" pour simplement mettre à jour les tags. Dans ce cas, soyez très prudent et assurez-vous d'avoir une sauvegarde des anciens tags au cas où la conversion aurait mal

tourné.

Réécriture correcte des tags objets est pris en charge. Si l'étiquette a un message attaché, un nouvel objet tag sera créé avec le même message, auteur et horodatage. Si l'étiquette a une signature attachée, la signature sera supprimée. Il est par définition impossible de préserver les

signatures. La raison pour laquelle c'est « presque » correct est que, idéalement, si l'étiquette n'a pas changé (pointe vers le même objet, a le même nom, etc.), elle devrait conserver toute signature. Ce n'est pas le cas, les signatures seront toujours suppr
imées, acheteur méfiez-vous. Il n'y a également aucun support pour changer l'auteur ou l'horodatage (ou le message de l'étiquette pour cette affaire). Les étiquettes qui pointent vers d'autres étiquettes seront réécrites pour pointer vers le commit sous-jacent.

--prune-empt

y
Certains filtres généreront des commits vides qui laissent l'arbre intact. Cette option indique à git-filter-branch de supprimer de tels commits s'ils ont exactement un ou zéro parent non élagué ; les commits de fusion resteront donc intacts. Cette option ne peut pas être utilisée avec --commit-filter, bien que le même effet puisse être obtenu en utilisant la fonction git_commit_non_empty_tree fournie dans un filtre de
commit.

--original

<namespace>
Utilisez cette option pour définir l'espace de noms où les commits originaux seront stockés. La valeur par défaut est refs/original
.

-d

<directory>
Utilisez cette option pour définir le chemin du répertoire temporaire utilisé pour la réécriture. Lors de l'application d'un filtre d'arbre, la commande doit temporairement extraire l'arbre dans un répertoire, ce qui peut consommer un espace considérable dans le cas de grands projets. Par défaut, elle le fait dans le répertoire .git-rewrite/ mais vous pouvez remplacer ce choix par ce
paramètre.

-f,

--force
git filter-branch refuse de démarrer avec un répertoire temporaire existant ou quand il y a déjà des refs commençant par refs/original/, sauf si
forcé.

--state-branch

<branch>
Cette option fera en sorte que la correspondance des anciens objets vers les nouveaux soit chargée depuis la branche nommée au démarrage et sauvegardée comme un nouveau commit sur cette branche à la sortie, permettant le traitement incrémental de grands arbres. Si <branch> n'existe pas, elle sera
créée.

<rev-list options>..

.
Arguments pour git rev-list. Toutes les refs positives incluses par ces options sont réécrites. Vous pouvez également spécifier des options telles que --all, mais vous devez utiliser -- pour les séparer des options
de

git filter-branch. Implique la section intitulée « Remap to ancestor

».

En utilisant des arguments de git-rev-list(1), par exemple des délimiteurs de chemin, vous pouvez limiter l'ensemble des révisions qui sont réécrites. Cependant, les refs positives sur la ligne de commande sont distinguées : nous ne les laissons pas être exclues par de tels délimiteurs. À cette fin, elles sont plutôt réécrites pour pointer vers l'ancêtre le plus proche qui n'a pas été exclu. CODE

LISTE DE CONTRÔLE POUR RÉDUIRE UN

DÉPÔT

git-filter-branch peut être utilisé pour se débarrasser d'un sous-ensemble de fichiers, généralement avec une combinaison de --index-filter et --subdirectory-filter. Les gens s'attendent à ce que le dépôt résultant soit plus petit que l'original, mais vous avez besoin de quelques étapes de plus pour le rendre réellement plus petit, car Git essaie fort de ne pas perdre vos objets jusqu'à ce que vous lui disiez de le faire. Assurez-vous d'abord que

:
•Vous avez vraiment supprimé toutes les variantes d'un nom de fichier, si un blob a été déplacé au cours de sa durée de vie. git log --name-only --follow --all -- filename peut vous aider à trouver les
renommages.
•Vous avez vraiment filtré toutes les refs : utilisez --tag-name-filter cat -- --all lors de l'appel
de

git-filter-branch

.
Ensuite, il y a deux façons d'obtenir un dépôt plus petit. Une manière plus sûre est de cloner, ce qui garde votre original intact. •Clonez-le avec git clone file:///chemin/vers/le/dépôt. Le clone n'aura pas les objets supprimés. Voir git-clone(1). (Notez que cloner avec un chemin simple crée juste des liens physiques vers tout !
)

Si vous ne voulez vraiment pas le cloner, pour quelque raison que ce soit, vérifiez plutôt les points suivants (dans cet ordre). C'est une approche très destructive, alors faites une sauvegarde ou revenez au clonage. Vous avez été

averti.
•Supprimez les refs originales sauvegardées par git-filter-branch : dites git for-each-ref--format="%( refname)" refs/original/ | xargs -n 1 >git update-ref -d. •Faire expirer tous les
reflogs avec
git reflog expire --expire=now --all. •Collecter les ordures (garbage collect) de tous les objets non
référencés avec
git gc --prune=now (ou si votre git-gc n'est pas assez récent pour supporter les arguments de --prune, utilisez git repack -ad; git prune à la place). PERFORMANCE Les performances de git-filter-branch sont extrêmement lentes ; sa conception rend impossible pour une implémentation rétrocompatible d'être
jamais
rapide :

•Lors de l'édition des fichiers, git-filter-branch, par conception, extrait chaque commit tel qu'il existait dans le dépôt original. Si

votre dépôt a

10^5 fichiers

et
10^5 commits, mais que chaque commit ne modifie que cinq fichiers, alors git-filter-branch vous fera faire 10^10 modifications, alors qu'il n'y a (au plus) que 5*10^5 blobs
uniques.
•Si vous essayez de tricher et de faire en sorte que git-filter-branch ne travaille que sur les fichiers modifiés dans un commit, alors deux choses se produisent
•vous rencontrez des problèmes avec les suppressions chaque fois que l'utilisateur essaie simplement de renommer des fichiers (parce que tenter de supprimer des fichiers qui n'existent pas ressemble à une opération sans effet ; il faut une certaine ruse pour remapper les suppressions lors des renommages de fichiers lorsque les renommages se font via une shell arbitraire fournie par
l'utilisateur)
•même si vous réussissez la ruse de remappage des suppressions pour les renommages, vous violez toujours techniquement la rétr
ocompatibilité car les utilisateurs sont autorisés à filtrer les fichiers de manière à dépendre de la topologie des commits au
lieu de filtrer uniquement en fonction du contenu ou des noms des fichiers (bien que cela n'ait pas été observé en pratique).
•Même si vous n'avez pas besoin d'éditer des fichiers mais que vous voulez simplement, par exemple, en renommer ou en supprimer certains et ainsi éviter d'extraire chaque fichier (c'est-à-dire que vous pouvez utiliser --index-filter), vous transmettez toujours des extraits de shell pour vos filtres. Cela signifie que pour chaque commit, vous devez avoir un dépôt git préparé où ces filtres peuvent être exécutés. C'est une configuration
importante.
•De plus, plusieurs fichiers supplémentaires sont créés ou mis à jour par commit par git-filter-branch. Certains d'entre eux servent à prendre en charge les fonctions de commodité fournies par git-filter-branch (comme map()), tandis que d'autres servent à suivre l'état interne (mais pourraient aussi avoir été accessibles par les filtres de l'utilisateur ; l'un des tests de non-régression de git-filter-branch le fait). Cela revient essentiellement à utiliser le système de fichiers comme mécanisme de communication inter-processus (IPC) entre git-filter-branch et les filtres fournis par l'utilisateur. Les disques ont tendance à être un mécanisme IPC lent, et l'écriture de ces fichiers représente également effectivement un point de synchronisation forcé entre des processus séparés que nous rencontrons avec chaque
commit.
•Les commandes shell fournies par l'utilisateur impliqueront probablement un pipeline de commandes, entraînant la création de nombreux processus par commit. La création et l'exécution d'un autre processus prend un temps très variable entre les systèmes d'exploitation, mais sur n'importe quelle plateforme, c'est très lent par rapport à l'appel d'une
fonction.
•git-filter-branch lui-même est écrit en shell, ce qui est un peu lent. C'est le seul problème de performance qui pourrait être corrigé de manière rétrocompatible, mais comparé aux problèmes ci-dessus qui sont intrinsèques à la conception de git-filter-branch, le langage de l'outil lui-même est un problème relativement mineur.
•Note de côté : Malheureusement, les gens ont tendance à se focaliser sur l'aspect écrit en shell et demandent périodiquement si git-filter-branch pourrait être réécrit dans un autre langage pour résoudre les problèmes de performance. Non seulement cela ignore les problèmes intrinsèques plus importants de la conception, mais cela aiderait moins que vous ne l'espérez : si git-filter-branch lui-même n'était pas en shell, alors les fonctions de commodité (map(), skip_commit(), etc.) et l' argument --setup ne pourraient plus être exécutés une seule fois au début du programme mais devr
aient plutôt être préfixés à chaque filtre utili
sateur (et donc ré-exécutés avec chaque commit).

L' outil git filter-repo[1] est une alternative à git-filter-branch qui ne souffre pas de ces problèmes de performance ou des problèmes de sécurité (mentionnés ci-dessous). Pour ceux qui ont des outils existants qui reposent sur git-filter-branch, git filter-repo fournit également filter-lamely[2], un remplacement direct de git-filter-branch (avec quelques réserves). Bien que filter-lamely souffre

de tous les mêmes problèmes de sécurité que git-filter-bran
ch, il atténue au moins un peu les problèmes de performance.

SÉCURIT

É

git-filter-branch est truffé de pièges entraînant divers moyens de corrompre facilement des dépôts ou de se retrouver avec un désastre pire que celui avec lequel on a commencé

:
•Quelqu'un peut avoir un ensemble de « filtres qui fonctionnent et sont testés » qu'il documente ou fournit à un collègue, qui les exécute alors sur un autre OS où les mêmes commandes ne fonctionnent pas/ne sont pas testées (certains exemples dans la page de manuel de git-filter-branch sont aussi affectés par cela). Les différences entre les environnements utilisateur BSD et GNU peuvent vraiment être pénibles. Si on a de la chance, des messages d'erreur sont émis. Mais tout aussi probablement, les commandes ne font pas le filtrage demandé, ou corrompent silencieusement en faisant un changement indésirable. Le changement indésirable peut n'affecter que quelques commits, donc ce n'est pas nécessairement évident non plus. (Le fait que les problets ne soient pas nécessairement évidents signifie qu'ils risquent de passer inaperçus jusqu'à ce que l'historique réécrit soit utilisé pendant un certain temps, à partir du moment où il est vraiment difficile de justifier une autre journée de drapeau pour une autre réécriture.
)
•Les noms de fichiers avec des espaces sont souvent mal gérés par les extraits de shell car ils causent des problèmes pour les pipelines de shell. Tout le monde ne connaît pas find -print0, xargs -0, git-ls-files -z, etc. Même les personnes qui connaissent ces commandes peuvent supposer que ces drapeaux ne sont pas pertinents parce que quelqu'un d'autre a renommé ces fichiers dans leur dépôt avant que la personne faisant le filtrage ne rejoigne le projet. Et souvent, même ceux qui savent gérer les arguments avec des espaces peuvent ne pas le faire simplement parce qu'ils n'ont pas l'état d'esprit de penser à tout ce qui pourrait mal
tourner.
•Les noms de fichiers non-ascii peuvent être silencieusement supprimés même s'ils se trouvent dans un répertoire souhaité. Ne conserver que les chemins voulus se fait souvent à l'aide de pipelines comme git ls-files | grep -v ^WANTED_DIR/ | xargs git rm. ls-files ne mettra les noms de fichiers entre guillemets que si nécessaire, donc les gens peuvent ne pas remarquer que l'un des fichiers n'a pas correspondu au regex (au moins pas avant qu'il ne soit beaucoup trop tard). Oui, quelqu'un qui connaît core.quotePath peut éviter cela (sauf s'ils ont d'autres caractères spéciaux comme \t, \n, ou "), et les personnes qui utilisent ls-files -z avec autre chose que grep peuvent éviter cela, mais cela ne signifie pas qu'elles le
feront.
•De même, lors du déplacement de fichiers, on peut constater que des noms de fichiers avec des caractères non-ascii ou spéciaux se retrouvent dans un autre répertoire, un répertoire qui inclut un caractère double guillemet. (C'est techniquement le même problème que ci-dessus avec le guillemetage, mais peut-être une manière différente et intéressante dont il peut et s'est manifesté comme un problème.
)
•Il est beaucoup trop facile de mélanger par erreur l'ancien et le nouvel historique. C'est encore possible avec n'importe quel outil, mais git-filter-branch l'invite presque. Si on a de la chance, le seul inconvénient est que les utilisateurs sont frustrés de ne pas savoir comment réduire leur dépôt et supprimer les anciennes choses. Si on a de la malchance, ils fusionnent l'ancien et le nouvel historique et se retrouvent avec de multiples « copies » de chaque commit, certaines ayant des fichiers indésirables ou sensibles et d'autres non. Cela arrive de plusieurs manières différentes :
•le défaut de ne faire qu'une réécriture partielle de l'historique (--all n'est pas la valeur par défaut et peu d'exemples le
montrent)
•le fait qu'il n'y ait pas de nettoyage automatique après
l'exécution
•le fait que --tag-name-filter (lorsqu'il est utilisé pour renommer des tags) ne supprime pas les anciens tags mais en ajoute simplement de nouveaux avec le nouveau
nom
•le fait que peu d'informations éducatives soient fournies pour informer les utilisateurs des ramifications d'une réécriture et comment éviter de mélanger l'ancien et le nouvel historique.
Par exemple, cette page de manuel discute de la façon dont les utilisateurs doivent comprendre qu'ils doivent rebaser leurs changements pour toutes leurs branches au-dessus du nouvel histori
que (ou supprimer et re-cloner), mais ce n'est qu'une des multiples préoccupations à considérer. Voir la section « DISCUSSION » de la page de manuel de git filter-repo pour plus de détails.
•Les tags annotés peuvent être accidentellement convertis en tags légers, en raison de l'un des deux problèmes suivants :
•Quelqu'un peut faire une réécriture d'historique, réaliser qu'il a fait une erreur, restaurer depuis les sauvegardes dans refs/original/, puis refaire sa commande git-filter-branch. (La sauvegarde dans refs/original/ n'est pas une vraie sauvegarde ; elle dé-référence les tags d'abord.
)
•Exécuter git-filter-branch avec soit --tags soit --all dans vos <rev-list-options>. Afin d
e conserver les tags annotés en tant qu'annotés, vous devez utiliser --tag-name-filter (et
ne devez pas avoir restauré depuis refs/original/ dans une réécriture précédemment ratée).
•Tous les messages de commit qui spécifient un encodage seront corrompus par la réécriture ; git-filter-branch ignore l'encodage, prend les octets originaux, et les transmet à commit-tree sans lui indiquer le bon encodage. (Cela se produit que --msg-filter soit utilisé ou non.
)
•Les messages de commit (même s'ils sont tous en UTF-8) deviennent corrompus par défaut en raison de leur absence de mise à jour — toute référence à d'autres empreintes de commit dans les messages de commit fera désormais référence à des commits qui n'existent
plus.
•Il n'y a aucune fonctionnalité pour aider les utilisateurs à trouver les saletés indésirables qu'ils devraient supprimer, ce qui signifie qu'ils ont beaucoup plus de chances d'avoir des nettoyages incomplets ou partiels qui entraînent parfois de la confusion et des gens perdant du temps à essayer de comprendre. (Par exemple, les gens ont tendance à chercher simplement de gros fichiers à supprimer au lieu de gros répertoires ou extensions, et une fois qu'ils le font, plus tard, les gens utilisant le nouveau dépôt qui parcourent l'historique remarqueront un répertoire d'artefacts de build qui a certains fichiers mais pas d'autres, ou un cache de dépendances (node_modules ou similaire) qui n'aurait jamais pu être fonctionnel car il lui manque certains fichiers.
)
•Si --prune-empty n'est pas spécifié, alors le processus de filtrage peut créer des hordes de commits vides
confus
•Si --prune-empty est spécifié, alors les commits vides placés intentionnellement d'avant l'opération de filtrage sont également élagués au lieu d'élaguer seulement les commits qui sont devenus vides en raison des règles de
filtrage.
•Si --prune-empty est spécifié, parfois des commits vides sont manqués et laissés quand même (un bug plutôt rare, mais cela arrive...
)
•Un problème mineur, mais les utilisateurs qui ont pour objectif de mettre à jour tous les noms et emails dans un dépôt peuvent être conduit à --env-filter qui ne mettra à jour que les auteurs et les committeurs, omettant les taggers.
•Si l'utilisateur fournit un --tag-name-filter qui mappe plusieurs balises vers le même nom, aucun avertissement ou erreur n'est fourni ; git-filter-branch écrase simplement chaque balise dans un ordre prédéfini non documenté résultant en une seule balise à la fin. (Un test de régression git-filter-branch nécessite ce comportement surprenant.)

De plus, les mauvaises performances de git-filter-branch conduisent souvent à des problèmes de sécurité :

•Trouver le bon snippet shell pour filtrer comme vous le souhaitez est parfois difficile, sauf si vous ne faites qu'une modification triviale telle que la suppression de quelques fichiers. Malheureusement, les gens apprennent souvent si le snippet est correct ou incorrect en l'essayant, mais la correction ou l'erreur peut varier en fonction de circonstances spéciales (espaces dans les noms de fichiers, noms de fichiers non ASCII, noms d'auteurs ou e-mails étranges, fuseaux horaires invalides, présence de greffons ou d'objets de remplacement, etc.), ce qui signifie qu'ils peuvent devoir attendre longtemps, rencontrer une erreur, puis redémarrer. Les performances de git-filter-branch sont si mauvaises que ce cycle est douloureux, réduisant le temps disponible pour vérifier attentivement (sans parler de ce que cela fait à la patience de la personne qui réécrit, même si elle a techniquement plus de temps disponible). Ce problème est encore plus aggravé car les erreurs de filtres cassés peuvent ne pas s'afficher pendant longtemps et/ou se perdre dans une mer de sortie. Même pire, les filtres cassés résultent souvent en des réécritures incorrectes silencieuses.
•Pour couronner le tout, même lorsque les utilisateurs trouvent enfin des commandes qui fonctionnent, ils veulent naturellement les partager. Mais ils peuvent ne pas savoir que leur dépôt n'avait pas certains cas spéciaux que le dépôt de quelqu'un d'autre possède. Donc, lorsqu'une autre personne avec un dépôt différent exécute les mêmes commandes, elle rencontre les problèmes ci-dessus. Ou, l'utilisateur exécute simplement des commandes qui ont été effectivement validées pour des cas spéciaux, mais il les exécute sur un système d'exploitation différent où cela ne fonctionne pas, comme noté ci-dessus.
