NOM

git-fast-import - Backend pour l'importation rapide de données Git

SYNOPSIS

frontend | git fast-import [<options>]

DESCRIPTION

Ce programme n'est généralement pas ce que l'utilisateur final souhaite exécuter directement. La plupart des utilisateurs finaux souhaitent utiliser l'un des programmes frontend existants, qui analyse un type spécifique de source étrangère et transmet le contenu qui y est stocké à git fast-import.

fast-import lit un flux mixte de commandes et de données depuis l'entrée standard et écrit directement un ou plusieurs fichiers pack dans le dépôt courant. Lorsque la fin de fichier (EOF) est reçue sur l'entrée standard, fast-import écrit les références de branche et d'étiquette mises à jour, mettant à jour complètement le dépôt courant avec les données nouvellement importées.

Le backend fast-import lui-même peut importer dans un dépôt vide (un dépôt qui a déjà été initialisé par git init) ou mettre à jour de manière incrémentielle un dépôt existant déjà peuplé. Que les imports incrémentiels soient pris en charge ou non à partir d'une source étrangère particulière dépend du programme frontend utilisé.

OPTIONS

--force

Force la mise à jour des branches existantes modifiées, même si cela entraînerait la perte de commits (car le nouveau commit ne contient pas l'ancien commit).

--quiet

Désactive la sortie affichée par --stats, ce qui fait que fast-import est généralement silencieux en cas de succès. Cependant, si le flux d'importation contient des directives destinées à afficher une sortie utilisateur (par exemple des directives progress ), les messages correspondants seront toujours affichés.

--stats

Affiche quelques statistiques de base sur les objets créés par fast-import, les fichiers pack dans lesquels ils ont été stockés et la mémoire utilisée par fast-import pendant cette exécution. L'affichage de cette sortie est actuellement activé par défaut, mais peut être désactivé avec --quiet.

--allow-unsafe-features

De nombreuses options de ligne de commande peuvent être fournies dans le flux fast-import lui-même en utilisant les commandes feature ou option . Cependant, certaines de ces options sont dangereuses (par exemple, permettre à fast-import d'accéder au système de fichiers en dehors du dépôt). Ces options sont désactivées par défaut, mais peuvent être autorisées en fournissant cette option sur la ligne de commande. Cela n'a actuellement d'effet que sur les commandes de fonctionnalité export-marks, import-markset import-marks-if-exists .

N'activez cette option que si vous faites confiance au programme qui génère le flux fast-import ! Cette option est activée automatiquement pour les helpers distants qui utilisent la capacité import , car ils sont déjà autorisés à exécuter leur propre code.

--signed-tags=(verbatim|warn-verbatim|warn-strip|strip|abort)

Spécifie comment gérer les étiquettes signées. Se comporte de la même manière que l'option du même nom dans git-fast-export(1), sauf que la valeur par défaut est verbatim (au lieu de abort).

--signed-commits=(verbatim|warn-verbatim|warn-strip|strip|abort)

Spécifie comment gérer les commits signés. Se comporte de la même manière que l'option du même nom dans git-fast-export(1), sauf que la valeur par défaut est verbatim (au lieu de abort).

Options pour les frontends

--cat-blob-fd=<fd>

Écrit les réponses aux requêtes get-mark, cat-blobet ls vers le descripteur de fichier <fd> au lieu de stdout. Permet de séparer la sortie progress destinée à l'utilisateur final des autres sorties.

--date-format=<fmt>

Spécifie le type de dates que le frontend fournira à fast-import dans les commandes author, committer et tagger . Voir « Formats de date » ci-dessous pour plus de détails sur les formats pris en charge et leur syntaxe.

--done

Se termine avec une erreur s'il n'y a pas de commande done à la fin du flux. Cette option peut être utile pour détecter des erreurs qui font que le frontend se termine avant d'avoir commencé à écrire un flux.

Emplacements des fichiers de marques

--export-marks=<file>

Vide la table interne des marques dans <file> lorsque l'opération est terminée. Les marques sont écrites une par ligne sous la forme :markid SHA-1. Les frontends peuvent utiliser ce fichier pour valider les imports après leur achèvement, ou pour sauvegarder la table des marques entre des exécutions incrémentielles. Comme <file> n'est ouvert et tronqué qu'au point de contrôle (ou à l'achèvement), le même chemin peut également être donné en toute sécurité à --import-marks.

--import-marks=<file>

Avant de traiter toute entrée, charge les marques spécifiées dans <file>. Le fichier d'entrée doit exister, doit être lisible et doit utiliser le même format que celui produit par --export-marks. Plusieurs options peuvent être fournies pour importer plus d'un ensemble de marques. Si une marque est définie avec des valeurs différentes, le dernier fichier l'emporte.

--import-marks-if-exists=<file>

Comme --import-marks mais au lieu de générer une erreur, ignore silencieusement le fichier s'il n'existe pas.

--relative-marks, --no-relative-marks

Après avoir spécifié --relative-marks, les chemins spécifiés avec --import-marks= et --export-marks= sont relatifs à un répertoire interne du dépôt courant. Dans git-fast-import, cela signifie que les chemins sont relatifs au répertoire .git/info/fast-import. Cependant, d'autres importateurs peuvent utiliser un emplacement différent.

Les marques relatives et non relatives peuvent être combinées en entrelaçant --(no-)-relative-marks avec les options --(import|export)-marks=.

Réécriture des sous-modules

--rewrite-submodules-from=<name>:<file>, --rewrite-submodules-to=<name>:<file>

Réécrit les identifiants d'objet du sous-module spécifié par <name> à partir des valeurs utilisées dans le fichier from <file> vers celles utilisées dans le fichier to <file>. Les marques from doivent avoir été créées par git fast-export, et les marques to doivent avoir été créées par git fast-import lors de l'importation de ce même sous-module.

<name> peut être n'importe quelle chaîne arbitraire ne contenant pas de caractère deux-points, mais la même valeur doit être utilisée avec les deux options lors de la spécification de marques correspondantes. Plusieurs sous-modules peuvent être spécifiés avec des valeurs différentes pour <name>. Il est une erreur de ne pas utiliser ces options par paires correspondantes.

Ces options sont principalement utiles lors de la conversion d'un dépôt d'un algorithme de hachage à un autre ; sans elles, fast-import échouera s'il rencontre un sous-module car il n'a aucun moyen d'écrire l'identifiant d'objet dans le nouvel algorithme de hachage.

Réglage des performances et de la compression

--active-branches=<n>

Nombre maximal de branches à maintenir actives simultanément. Voir « Utilisation de la mémoire » ci-dessous pour plus de détails. La valeur par défaut est 5.

--big-file-threshold=<n>

Taille maximale d'un blob pour lequel fast-import tentera de créer un delta, exprimée en octets. La valeur par défaut est 512m (512 Mio). Certains importateurs peuvent souhaiter abaisser cette valeur sur les systèmes ayant une mémoire limitée.

--depth=<n>

Profondeur de delta maximale, pour la délimitation des blobs et des arbres. La valeur par défaut est 50.

--export-pack-edges=<file>

Après la création d'un fichier pack, écrit une ligne de données dans <file> listant le nom de fichier du fichier pack et le dernier commit de chaque branche qui y a été écrit. Cette information peut être utile après l'importation de projets dont l'ensemble total d'objets dépasse la limite de 4 Gio pour les fichiers pack, car ces commits peuvent être utilisés comme points de limite lors des appels à git pack-objects.

--max-pack-size=<n>

Taille maximale de chaque fichier pack de sortie. La valeur par défaut est illimitée.

fastimport.unpackLimit

Voir git-config(1)

PERFORMANCES

La conception de fast-import lui permet d'importer de grands projets avec une utilisation minimale de la mémoire et un temps de traitement minimal. En supposant que le frontend est capable de suivre fast-import et de lui fournir un flux constant de données, les temps d'importation pour des projets contenant plus de 10 ans d'historique et00 000+ commits individuels sont généralement terminés en seulement 1 à 2 heures sur du matériel assez modeste (~2 000 USD en 2007).

La plupart des goulots d'étranglement semblent être dans l'accès aux données sources étrangères (la source ne peut tout simplement pas extraire les révisions assez rapidement) ou dans les E/S disque (fast-import écrit aussi vite que le disque peut absorber les données). Les importations seront plus rapides si les données sources sont stockées sur un disque différent de celui du dépôt Git de destination (en raison d'une moindre contention d'E/S).

COUT DEVELOPPEMENT

Une interface typique pour fast-import pèse environ 200 lignes de code Perl/Python/Ruby. La plupart des développeurs ont été capables de créer des importateurs fonctionnels en seulement quelques heures, même s'il s'agit de leur première exposition à fast-import, et parfois même à Git. C'est une situation idéale, étant donné que la plupart des outils de conversion sont à usage unique (utilisés une fois, et jamais regardés en arrière).

OPERATION PARALLELE

Comme git push ou git fetch, les importations gérées par fast-import peuvent être exécutées en parallèle avec des invocations de git repack -a -d ou git gc, ou toute autre opération Git (y compris git prune, car les objets lâches ne sont jamais utilisés par fast-import).

fast-import ne verrouille pas les références de branche ou de tag sur lesquelles il opère activement. Après l'importation, pendant sa phase de mise à jour des références, fast-import teste chaque référence de branche existante pour vérifier que la mise à jour sera une mise à jour en avance rapide (le commit stocké dans la référence est contenu dans le nouvel historique du commit à écrire). Si la mise à jour n'est pas une mise à jour en avance rapide, fast-import sautera la mise à jour de cette référence et affichera un message d'avertissement. fast-import tentera toujours de mettre à jour toutes les références de branche, et ne s'arrêtera pas à la première erreur.

Les mises à jour de branches peuvent être forcées avec --force, mais il est recommandé de ne l'utiliser que sur un dépôt autrement silencieux. L'utilisation de --force n'est pas nécessaire pour une importation initiale dans un dépôt vide.

DISCUSSION TECHNIQUE

fast-import suit un ensemble de branches en mémoire. N'importe quelle branche peut être créée ou modifiée à tout moment pendant le processus d'importation en envoyant une commande commit sur le flux d'entrée. Cette conception permet à un programme frontal de traiter un nombre illimité de branches simultanément, générant des commits dans l'ordre où ils sont disponibles à partir des données sources. Elle simplifie également considérablement les programmes frontaux.

fast-import n'utilise ni ne modifie le répertoire de travail courant, ni aucun fichier à l'intérieur. (Il met cependant à jour le dépôt Git courant, tel que référencé par GIT_DIR.) Par conséquent, une interface d'importation peut utiliser le répertoire de travail à ses propres fins, telles que l'extraction des révisions de fichiers à partir de la source étrangère. Cette ignorance du répertoire de travail permet également à fast-import de fonctionner très rapidement, car il n'a pas besoin d'effectuer d'opérations coûteuses de mise à jour de fichiers lors du passage d'une branche à l'autre.

FORMAT ENTREE

À l'exception des données de fichiers bruts (que Git n'interprète pas), le format d'entrée de fast-import est basé sur du texte (ASCII). Ce format textuel simplifie le développement et le débogage des programmes frontaux, en particulier lorsqu'un langage de plus haut niveau comme Perl, Python ou Ruby est utilisé.

fast-import est très strict quant à son entrée. Lorsque nous disons SP ci-dessous, nous entendons exactement une espace. De même, LF signifie un (et un seul) saut de ligne et HT un (et un seul) tabulation horizontale. Fournir des caractères d'espacement supplémentaires entraînera des résultats inattendus, tels que des noms de branches ou de fichiers avec des espaces en début ou en fin de nom, ou une terminaison prématurée de fast-import lorsqu'il rencontre une entrée inattendue.

COMMENTAIRES FLUX

Pour faciliter le débogage des interfaces, fast-import ignore toute ligne qui commence par # (dièse/crochet ASCII) jusqu'à la fin de ligne incluse LF. Une ligne de commentaire peut contenir n'importe quelle séquence d'octets qui ne contient pas de LF et peut donc être utilisée pour inclure des informations de débogage détaillées qui peuvent être spécifiques à l'interface et utiles lors de l'inspection d'un flux de données fast-import.

FORMATS DATE

Les formats de date suivants sont pris en charge. Une interface doit sélectionner le format qu'elle utilisera pour cette importation en passant le nom du format dans l'option de ligne de commande --date-format=<fmt>.

raw

C'est le format natif de Git et il est constitué de <temps> SP <offutc>. C'est également le format par défaut de fast-import, si --date-format n'a pas été spécifié.

Le temps de l'événement est spécifié par <temps> comme le nombre de secondes depuis l'époque UNIX (minuit, 1er janvier 1970, UTC) et est écrit sous forme d'entier décimal ASCII.

Le décalage local est spécifié par <offutc> comme un décalage positif ou négatif par rapport à l'UTC. Par exemple, EST (qui est 5 heures derrière l'UTC) serait exprimé en <tz> par « -0500 » tandis que UTC est « +0000 ». Le décalage local n'affecte pas <temps>; il est utilisé uniquement comme conseil pour aider les routines de formatage à afficher l'horodatage.

Si le décalage local n'est pas disponible dans le matériel source, utilisez « +0000 », ou le décalage local le plus courant. Par exemple, de nombreuses organisations ont un dépôt CVS qui n'a jamais été accédé que par des utilisateurs situés dans le même lieu et le même fuseau horaire. Dans ce cas, un décalage raisonnable par rapport à l'UTC pourrait être supposé.

Contrairement au format rfc2822, ce format est très strict. Toute variation de format fera rejeter la valeur par fast-import, et certaines vérifications de bon sens sur les valeurs numériques peuvent également être effectuées.

raw-permissive

C'est la même chose que raw sauf qu'aucune vérification de bon sens sur l'époque numérique et le décalage local n'est effectuée. Cela peut être utile lors de la tentative de filtrage ou d'importation d'un historique existant avec, par exemple, des valeurs de fuseau horaire incorrectes.

rfc2822

C'est le format de date standard tel que décrit par la RFC 2822.

Un exemple de valeur est « Tue Feb 6 11:22:18 2007 -0500 ». L'analyseur Git est précis, mais un peu tolérant. C'est le même analyseur utilisé par git am lors de l'application de patchs reçus par email.

Certaines chaînes malformées peuvent être acceptées comme dates valides. Dans certains de ces cas, Git sera toujours capable d'obtenir la date correcte à partir de la chaîne malformée. Il existe également certains types de chaînes malformées que Git analysera mal, tout en les considérant valides. Les chaînes sérieusement malformées seront rejetées.

Contrairement au format raw ci-dessus, les informations de fuseau horaire/décalage UTC contenues dans une chaîne de date RFC 2822 sont utilisées pour ajuster la valeur de la date à l'UTC avant le stockage. Il est donc important que ces informations soient aussi précises que possible.

Si le matériel source utilise des dates de style RFC 2822, l'interface doit laisser fast-import gérer l'analyse et la conversion (plutôt que d'essayer de le faire elle-même) car l'analyseur Git a été bien testé sur le terrain.

Les interfaces devraient préférer le format raw si le matériel source utilise déjà le format époque UNIX, peut être contraint à donner des dates dans ce format, ou si son format est facilement convertible. Il n'y a aucune ambiguïté dans l'analyse.

now

Utilise toujours l'heure et le fuseau horaire actuels. Le littéral now doit toujours être fourni pour <quand>.

C'est un format jouet. L'heure et le fuseau horaire actuels de ce système sont toujours copiés dans la chaîne d'identité au moment où elle est créée par fast-import. Il n'y a aucun moyen de spécifier une heure ou un fuseau horaire différent.

Ce format particulier est fourni car il est court à implémenter et peut être utile à un processus qui souhaite créer un nouveau commit immédiatement, sans avoir besoin d'utiliser un répertoire de travail ou git update-index.

Si des commandes distinctes author et committer sont utilisées dans un commit, les horodatages peuvent ne pas correspondre, car l'horloge système sera interrogée deux fois (une fois pour chaque commande). La seule façon de s'assurer que les informations d'identité de l'auteur et du committer ont le même horodatage est d'omettre author (copiant ainsi de committer) ou d'utiliser un format de date autre que now.

COMMANDES

fast-import accepte plusieurs commandes pour mettre à jour le dépôt courant et contrôler le processus d'importation courant. Une discussion plus détaillée (avec exemples) de chaque commande suit plus loin.

commit

Crée une nouvelle branche ou met à jour une branche existante en créant un nouveau commit et en mettant à jour la branche pour qu'elle pointe vers le commit nouvellement créé.

tag

Crée un objet tag annoté à partir d'un commit ou d'une branche existante. Les tags légers ne sont pas pris en charge par cette commande, car ils ne sont pas recommandés pour enregistrer des points dans le temps significatifs.

reset

Réinitialise une branche existante (ou une nouvelle branche) à une révision spécifique. Cette commande doit être utilisée pour changer une branche à une révision spécifique sans y faire de commit.

blob

Convertit les données de fichier brutes en un blob, pour une utilisation ultérieure dans une commande commit. Cette commande est facultative et n'est pas nécessaire pour effectuer une importation.

alias

Enregistre qu'une marque fait référence à un objet donné sans d'abord créer de nouvel objet. L'utilisation de --import-marks et la référence à des marques manquantes entraîneront l'échec de fast-import, donc les alias peuvent fournir un moyen de définir des commits autrement élagués à une valeur valide (par exemple, l'ancêtre non élagué le plus proche).

checkpoint

Force fast-import à fermer le fichier pack courant, à générer son checksum SHA-1 unique et son index, et à démarrer un nouveau fichier pack. Cette commande est facultative et n'est pas nécessaire pour effectuer une importation.

progress

Fait en sorte que fast-import répète toute la ligne sur sa propre sortie standard. Cette commande est facultative et n'est pas nécessaire pour effectuer une importation.

done

Marque la fin du flux. Cette commande est facultative sauf si la fonctionnalité done a été demandée en utilisant l'option de ligne de commande --done ou la commande feature done.

get-mark

Demande à fast-import d'imprimer le SHA-1 correspondant à une marque sur le descripteur de fichier défini avec --cat-blob-fd, ou sur stdout s'il n'est pas spécifié.

PLANTAGE

Si fast-import reçoit une entrée invalide, il se terminera avec un code de sortie non nul et créera un rapport de plantage au niveau supérieur du dépôt Git dans lequel il importait. Les rapports de plantage contiennent un instantané de l'état interne de fast-import ainsi que les commandes les plus récentes ayant conduit au

plantage.

Toutes les commandes récentes (y compris les commentaires de flux, les changements de fichiers et les commandes progress) sont montrées dans l'historique des commandes du rapport de plantage, mais les données de fichiers brutes et les messages de commit sont exclus du rapport de plantage. Cette exclusion économise de l'espace dans le fichier de rapport et réduit la quantité de tamponnement que fast-import doit effectuer pendant

l'exécution.

Cela permet au développeur du frontend d' inspecter l'état du dépôt et de reprendre l'importation à partir du point où elle a planté. Les branches et étiquettes modifiées ne sont pas mises à jour pendant un plantage, car l'importation n'a pas abouti avec succès. Les informations sur les branches et les étiquettes peuvent être trouvées dans le rapport de plantage et doivent être appliquées manuellement si la

ASTUCES ET

CONSEILS

Les conseils et astuces suivants ont été recueillis auprès de divers utilisateurs de fast-import, et sont proposés ici comme

suggestions.

Utiliser une marque par commitLors d'une conversion de dépôt, utiliser une marque unique par commit ( mark : <n>) et fournir l'option --export-marks sur la ligne de commande. fast-import déversera un fichier listant chaque marque et le SHA-1 de l'objet Git qui lui correspond. Si le frontend peut relier les marques au dépôt source, il est facile de vérifier l'exactitude et l'exhaustivité de l'importation en comparant chaque commit Git à la révision source

correspondante.

En provenance d'un système tel que Perforce ou Subversion, cela devrai

t être assez simple, car la marque fast-import peut aussi être le
numéro de changeset Perforce ou le numéro de révision Subversion.

Sauter librement entre les

branches

Ne cherchez pas à optimiser le frontend pour rester sur une seule branche à la fois pendant une importation. Bien que cela puisse être légèrement plus rapide pour fast-import, cela tend à augmenter considérablement la complexité du code du

frontend.

La LRU des branches intégrée à fast-import tend à se comporter très bien, et le co

ût d'activation d'une branche inactive est si faible que le fait de sauter d'une
branche à l'autre n'a pratiquement aucun impact sur les performances de l'importation.

Gérer les

renommages

Lors de l'importation d'un fichier ou d'un répertoire renommé, supprimez simplement les

anciens noms et modifiez les nouveaux noms lors du commit correspondant. Git effectue la
détection des renommages a posteriori, plutôt que de manière explicite lors d'un commit.

Utiliser des branches de correction de tag

Certains autres systèmes de gestion de versions permettent à l'utilisateur de créer un tag à partir de plusieurs fichiers qui ne proviennent pas du même commit/ensemble de modifications. Ou de créer des tags qui sont un sous-ensemble des fichiers disponibles dans le dépôt.

Importer ces tels quels dans Git est impossible sans faire au moins un commit qui « corrige » les fichiers pour qu'ils correspondent au contenu du tag. Utilisez la commande reset de fast-import pour réinitialiser une branche factice en dehors de votre espace de branches normal au commit de base du tag, puis faites un ou plusieurs commits de correction de fichiers, et enfin étiquetez la branche factice.

Par exemple, comme toutes les branches normales sont stockées sous refs/heads/ nommez la branche de correction de tag TAG_FIXUP. De cette façon, il est impossible que la branche de correction utilisée par l'importeur entre en conflit d'espace de noms avec les vraies branches importées depuis la source (le nom TAG_FIXUP n'est pas refs/heads/TAG_FIXUP).

Lorsque vous faites des commits de correction, envisagez d'utiliser merge pour connecter le ou les commits qui fournissent les révisions de fichiers à la branche de correction. Cela permettra à des outils comme git blame de suivre l'historique réel des commits et d'annoter correctement les fichiers sources.

Une fois que fast-import se termine, le frontend devra faire rm .git/TAG_FIXUP pour supprimer la branche factice.

Importer maintenant, repacker plus tard

Dès que fast-import se termine, le dépôt Git est complètement valide et prêt à l'emploi. En général, cela ne prend qu'un très court instant, même pour des projets considérablement grands (plus de 100 000 commits).

Cependant, le repacker du dépôt est nécessaire pour améliorer la localité des données et les performances d'accès. Cela peut aussi prendre des heures sur des projets extrêmement grands (surtout si -f et un paramètre --window important sont utilisés). Comme le repacker est sûr à exécuter en parallèle des lecteurs et des écrivains, lancez le repacker en arrière-plan et laissez-le se terminer quand il se terminera. Il n'y a aucune raison d'attendre pour explorer votre nouveau projet Git !

Si vous choisissez d'attendre le repacker, n'essayez pas de lancer des benchmarks ou des tests de performance avant que le repacker ne soit terminé. fast-import produit des fichiers pack sous-optimaux qui ne sont tout simplement jamais vus dans les situations d'utilisation réelles.

Repacker des données historiques

Si vous repackez des données importées très anciennes (par exemple plus anciennes que l'année dernière), envisagez de dépenser un peu de temps CPU supplémentaire et de fournir --window=50 (ou plus) lorsque vous lancez git repack. Cela prendra plus de temps, mais produira aussi un fichier pack plus petit. Vous n'avez besoin de fournir cet effort qu'une seule fois, et tout le monde utilisant votre projet bénéficiera du dépôt plus petit.

Inclure quelques messages de progression

De temps en temps, faites émettre par votre frontend un message progress à fast-import. Le contenu des messages est entièrement libre, donc une suggestion serait de sortir le mois et l'année courants chaque fois que la date du commit courant passe au mois suivant. Vos utilisateurs se sentiront mieux en sachant combien du flux de données a été traité.

OPTIMISATION DES FICHIERS PACK

Lors de l'empaquetage d'un blob, fast-import tente toujours de le délter contre le dernier blob écrit. Sauf si c'est spécifiquement arrangé par le frontend, ce ne sera probablement pas une version antérieure du même fichier, donc le delta généré ne sera pas le plus petit possible. Le fichier pack résultant sera compressé, mais ne sera pas optimal.

Les frontends qui ont un accès efficace à toutes les révisions d'un fichier unique (par exemple en lisant un fichier RCS/CVS ,v) peuvent choisir de fournir toutes les révisions de ce fichier comme une séquence de commandes blob consécutives. Cela permet à fast-import de délter les différentes révisions de fichier les unes contre les autres, économisant de l'espace dans le fichier pack final. Les marques peuvent être utilisées pour identifier plus tard des révisions de fichier individuelles pendant une séquence de commandes commit .

Le ou les fichiers pack créés par fast-import n'encouragent pas de bons schémas d'accès au disque. Cela est dû au fait que fast-import écrit les données dans l'ordre où elles sont reçues sur l'entrée standard, alors que Git organise généralement les données dans les fichiers pack pour faire apparaître les données les plus récentes (pointe actuelle) avant les données historiques. Git regroupe aussi les commits ensemble, accélérant la traversée des révisions grâce à une meilleure localité du cache.

Pour cette raison, il est fortement recommandé que les utilisateurs repackent le dépôt avec git repack -a -d après la fin de fast-import, permettant à Git de réorganiser les fichiers pack pour un accès aux données plus rapide. Si les deltas de blobs sont sous-optimaux (voir ci-dessus), alors ajouter aussi l'option -f pour forcer le recalcul de tous les deltas peut réduire significativement la taille du fichier pack final (30 à 50 % plus petit peut être tout à fait typique).

Au lieu de lancer git repack vous pouvez aussi lancer git gc --aggressive, qui optimisera aussi d'autres choses après un import (par exemple empaqueter les refs détachées). Comme noté dans la section « AGGRESSIVE » de git-gc(1) l'option --aggressive trouvera de nouveaux deltas avec l'option -f de git-repack(1). Pour les raisons élaborées ci-dessus, utiliser --aggressive après un fast-import est l'un des rares cas où c'est connu pour valoir le coup.

UTILISATION DE LA MÉMOIRE

Il y a un certain nombre de facteurs qui affectent la quantité de mémoire dont fast-import a besoin pour effectuer un import. Comme les sections critiques du cœur de Git, fast-import utilise ses propres allocateurs de mémoire pour amortir les surcoûts associés à malloc. En pratique, fast-import tend à amortir les surcoûts de malloc à 0, en raison de son utilisation d'allocations de blocs larges.

par objet

fast-import maintient une structure en mémoire pour chaque objet écrit dans cette exécution. Sur un système 32 bits, la structure fait 32 octets, sur un système 64 bits, la structure fait 40 octets (en raison de la taille plus grande des pointeurs). Les objets dans la table ne sont pas désalloués avant que fast-import ne se termine. Importer 2 millions d'objets sur un système 32 bits nécessitera environ 64 Mio de mémoire.

La table d'objets est en réalité une table de hachage indexée sur le nom de l'objet (le SHA-1 unique). Cette configuration de stockage permet à fast-import de réutiliser un objet existant ou déjà écrit et d'éviter d'écrire des doublons dans le fichier pack de sortie. Les blobs en double sont étonnamment courants dans un import, généralement en raison des fusions de branches dans la source.

par marque

Les marques sont stockées dans un tableau creux, utilisant 1 pointeur (4 octets ou 8 octets, selon la taille du pointeur) par marque. Bien que le tableau soit creux, les frontends sont toujours fortement encouragés à utiliser des marques entre 1 et n, où n est le nombre total de marques requises pour cet import.

par branche

Les branches sont classées comme actives et inactives. L'utilisation mémoire des deux classes est significativement différente.

Les branches inactives sont stockées dans une structure qui utilise 96 ou 120 octets (systèmes 32 bits ou 64 bits respectivement), plus la longueur du nom de la branche (généralement sous 200 octets), par branche. fast-import gérera facilement jusqu'à 10 000 branches inactives en moins de 2 Mio de mémoire.

Les branches actives ont le même surcoût que les branches inactives, mais contiennent aussi des copies de chaque arbre qui a été récemment modifié sur cette branche. Si le sous-arbre include n'a pas été modifié depuis que la branche est devenue active, son contenu ne sera pas chargé en mémoire, mais si le sous-arbre src a été modifié par un commit depuis que la branche est devenue active, alors son contenu sera chargé en mémoire.

Comme les branches actives stockent des métadonnées sur les fichiers contenus sur cette branche, leur taille de stockage en mémoire peut croître à une taille considérable (voir ci-dessous).

fast-import déplace automatiquement les branches actives au statut inactif basé sur un simple algorithme de remplacement par le moins récemment utilisé. La chaîne LRU est mise à jour à chaque commande commit . Le nombre maximum de branches actives peut être augmenté ou diminué sur la ligne de commande avec --active-branches=.

par arbre actif

Les arbres (alias répertoires) n'utilisent que 12 octets de mémoire en plus de la mémoire requise pour leurs entrées (voir « par entrée de fichier active » ci-dessous). Le coût d'un arbre est virtuellement de 0, car son surcoût s'amortit sur les entrées de fichiers individuelles.

par entrée de fichier active

Les fichiers (et les pointeurs vers les sous-arbres) dans les arbres actifs nécessitent 52 ou 64 octets (plateformes 32/64 bits) par entrée. Pour économiser de l'espace, les noms de fichiers et d'arbres sont regroupés dans une table de chaînes commune, permettant au nom de fichier « Makefile » d'utiliser seulement 16 octets (après avoir inclus le surcoût de l'en-tête de chaîne) peu importe combien de fois il apparaît dans le projet.

La LRU des branches actives, couplée au regroupement des noms de fichier et au chargement paresseux des sous-arbres, permet à fast-import d'importer efficacement des projets avec 2 000+ branches et 45 114+ fichiers avec une empreinte mémoire très limitée (moins de 2,7 Mio par branche active).

SIGNAUX

Envoyer SIGUSR1 au processus git fast-import termine le fichier pack courant plus tôt, simulant une commande checkpoint . L'opérateur impatient peut utiliser cette fonctionnalité pour jeter un coup d'œil aux objets et aux refs d'un import en cours, au prix d'un temps d'exécution supplémentaire et d'une compression moins bonne.
