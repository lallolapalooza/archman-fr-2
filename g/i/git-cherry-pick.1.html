NOM

git-cherry-pick - Appliquer les changements introduits par certains commits existants

SYNOPSIS

git cherry-pick [--edit] [-n] [-m <parent-number>] [-s] [-x] [--ff]
                  [-S[<keyid>]] <commit>...
git cherry-pick (--continue | --skip | --abort | --quit)

DESCRIPTION

Étant donné un ou plusieurs commits existants, appliquer le changement que chacun introduit, en enregistrant un nouveau commit pour chacun. Cela nécessite que votre arbre de travail soit propre (pas de modifications par rapport au commit HEAD).

Lorsqu'il n'est pas évident de savoir comment appliquer un changement, ce qui suit se produit :

1.La branche courante et le pointeur HEAD restent sur le dernier commit effectué avec succès.
2.La référence CHERRY_PICK_HEAD est définie pour pointer vers le commit qui a introduit le changement difficile à appliquer.
3.Les chemins où le changement a été appliqué sans conflit sont mis à jour à la fois dans le fichier d'index et dans votre arbre de travail.
4.Pour les chemins en conflit, le fichier d'index enregistre jusqu'à trois versions, comme décrit dans la section « TRUE MERGE » de git-merge(1). Les fichiers de l'arbre de travail incluront une description du conflit entourée par les marqueurs de conflit habituels <<<<<<< et >>>>>>>.
5.Aucune autre modification n'est effectuée.

Voir git-merge(1) pour quelques conseils sur la résolution de tels conflits.

OPTIONS

<commit>...

Commits à cherry-pick. Pour une liste plus complète des façons d'écrire les commits, voir gitrevisions(7). Des ensembles de commits peuvent être passés mais aucune traversée n'est effectuée par défaut, comme si l'option --no-walk était spécifiée, voir git-rev-list(1). Notez que spécifier une plage passera tous les arguments <commit>... à une seule traversée de révisions (voir un exemple plus loin qui utilise maint master..next).

-e, --edit

Avec cette option, git cherry-pick vous permettra d'éditer le message du commit avant de le committer.

--cleanup=<mode>

Cette option détermine comment le message du commit sera nettoyé avant d'être transmis au mécanisme de commit. Voir git-commit(1) pour plus de détails. En particulier, si le <mode> reçoit la valeur scissors, des ciseaux seront ajoutés à MERGE_MSG avant d'être transmis en cas de conflit.

-x

Lors de l'enregistrement du commit, ajouter une ligne disant « (cherry picked from commit ...) » au message du commit original afin d'indiquer depuis quel commit ce changement a été cherry-pické. Cela n'est fait que pour les cherry-picks sans conflit. N'utilisez pas cette option si vous cherry-pické depuis votre branche privée car l'information est inutile pour le destinataire. Si en revanche vous cherry-pické entre deux branches publiquement visibles (par ex. rétroporter un correctif vers une branche de maintenance d'une ancienne version depuis une branche de développement), ajouter cette information peut être utile.

-r

Autrefois, la commande faisait par défaut le -x décrit ci-dessus, et -r servait à le désactiver. Maintenant, le défaut est de ne pas faire -x donc cette option est sans effet.

-m <parent-number>, --mainline <parent-number>

Habituellement, vous ne pouvez pas cherry-pick une fusion car vous ne savez pas quel côté de la fusion doit être considéré comme la ligne principale. Cette option spécifie le numéro du parent (à partir de 1) de la ligne principale et permet à cherry-pick de rejouer le changement par rapport au parent spécifié.

-n, --no-commit

Habituellement, la commande crée automatiquement une séquence de commits. Ce drapeau applique les changements nécessaires pour cherry-pick chaque commit nommé vers votre arbre de travail et l'index, sans effectuer aucun commit. De plus, lorsque cette option est utilisée, votre index n'a pas besoin de correspondre au commit HEAD. Le cherry-pick est effectué par rapport à l'état initial de votre index.

C'est utile lorsque vous appliquez l'effet de plusieurs commits à votre index en une seule fois.

-s, --signoff

Ajouter un marqueur Signed-off-by à la fin du message du commit. Voir l'option signoff dans git-commit(1) pour plus d'informations.

-S[<keyid>], --gpg-sign[=<keyid>], --no-gpg-sign

Signer les commits avec GPG. L'argument keyid est optionnel et par défaut correspond à l'identité du committer ; s'il est spécifié, il doit être collé à l'option sans espace. --no-gpg-sign est utile pour annuler à la fois la variable de configuration commit.gpgSign et les --gpg-signprécédents.

--ff

Si le HEAD courant est le même que le parent du commit cherry-pické, alors un avance rapide (fast forward) vers ce commit sera effectué.

--allow-empty

Par défaut, cherry-pick un commit vide échouera, indiquant qu'une invocation explicite de git commit --allow-empty est requise. Cette option remplace ce comportement, permettant aux commits vides d'être préservés automatiquement lors d'un cherry-pick. Notez que lorsque « --ff » est en vigueur, les commits vides qui remplissent l'exigence de « fast-forward » seront conservés même sans cette option. Notez également que l'utilisation de cette option ne conserve que les commits qui étaient initialement vides (c.-à-d. le commit enregistrait le même arbre que son parent). Les commits qui deviennent vides en raison d'un commit précédent feront échouer le cherry-pick. Pour forcer l'inclusion de ces commits, utilisez --empty=keep.

--allow-empty-message

Par défaut, cherry-pick un commit avec un message vide échouera. Cette option remplace ce comportement, permettant de cherry-pick des commits avec des messages vides.

--empty=(drop|keep|stop)

Comment gérer les commits cherry-pickés qui sont redondants avec des changements déjà présents dans l'historique courant.

drop

Le commit sera abandonné.

keep

Le commit sera conservé. Implique --allow-empty.

stop

Le cherry-pick s'arrêtera lorsque le commit sera appliqué, vous permettant d'examiner le commit. C'est le comportement par défaut.

Notez que --empty=drop et --empty=stop ne spécifient que comment gérer un commit qui n'était pas initialement vide, mais qui est devenu vide en raison d'un commit précédent. Les commits qui étaient initialement vides feront toujours échouer le cherry-pick à moins que l'un de --empty=keep ou --allow-empty ne soit spécifié.

--keep-redundant-commits

Synonyme déprécié pour --empty=keep.

--strategy=<strategy>

Utiliser la stratégie de fusion donnée. Ne devrait être utilisé qu'une seule fois. Voir la section MERGE STRATEGIES dans git-merge(1) pour les détails.

-X<option>, --strategy-option=<option>

Passer l'option spécifique à la stratégie de fusion à la stratégie de fusion. Voir git-merge(1) pour les détails.

--rerere-autoupdate, --no-rerere-autoupdate

Après que le mécanisme rerere réutilise une résolution enregistrée sur le conflit courant pour mettre à jour les fichiers dans l'arbre de travail, lui permettre de mettre à jour également l'index avec le résultat de la résolution. --no-rerere-autoupdate est un bon moyen de vérifier ce que rerere a fait et de détecter d'éventuelles fusions erronées, avant de committer le résultat dans l'index avec un git addséparé.

SOUS-COMMANDES DU SÉQUENCEUR

--continue

Continuer l'opération en cours en utilisant les informations dans .git/sequencer. Peut être utilisé pour continuer après avoir résolu les conflits dans un cherry-pick ou revert échoué.

--skip

Ignorer le commit courant et continuer avec le reste de la séquence.

--quit

Oublier l'opération en cours. Peut être utilisé pour effacer l'état du séquenceur après un cherry-pick ou revert échoué.

--abort

Annuler l'opération et revenir à l'état d'avant la séquence.

EXEMPLES

git cherry-pick master

Appliquer le changement introduit par le commit à l'extrémité de la branche master et crée un nouveau commit avec ce changement.

git cherry-pick ..master, git cherry-pick ^HEAD master

Applique les changements introduits par tous les commits qui sont des ancêtres de master mais pas de HEAD pour produire de nouveaux commits.

git cherry-pick maint next ^master, git cherry-pick maint master..next

Applique les changements introduits par tous les commits qui sont des ancêtres de maint ou next, mais pas de master ou de ses ancêtres. Notez que ce dernier ne signifie pas maint et tout ce qui se trouve entre master et next; plus précisément, maint ne sera pas utilisé s'il est inclus dans master.

git cherry-pick master~4 master~2

Applique les changements introduits par le cinquième et le troisième dernier commits pointés par master et crée 2 nouveaux commits avec ces changements.

git cherry-pick -n master~1 next

Applique à l'arbre de travail et à l'index les changements introduits par le deuxième dernier commit pointé par master et par le dernier commit pointé par next, mais ne crée aucun commit avec ces changements.

git cherry-pick --ff ..next

Si l'historique est linéaire et que HEAD est un ancêtre de next, met à jour l'arbre de travail et avance le pointeur HEAD pour correspondre à next. Sinon, applique les changements introduits par ces commits qui sont dans next mais pas dans HEAD à la branche actuelle, en créant un nouveau commit pour chaque nouveau changement.

git rev-list --reverse master -- README | git cherry-pick -n --stdin

Applique les changements introduits par tous les commits sur la branche master qui ont touché README à l'arbre de travail et à l'index, afin que le résultat puisse être inspecté et transformé en un seul nouveau commit si cela convient.

La séquence suivante tente de rétroporter un patch, abandonne parce que le code auquel le patch s'applique a trop changé, puis réessaie, cette fois avec plus de soin pour faire correspondre les lignes de contexte.

$ git cherry-pick topic^             (1)
$ git diff                           (2)
$ git cherry-pick --abort            (3)
$ git cherry-pick -Xpatience topic^  (4)
1. applique le changement qui serait affiché par git show topic^. Dans cet exemple, le patch ne s'applique pas proprement, donc des informations sur le conflit sont écrites dans l'index et l'arbre de travail et aucun nouveau commit n'est créé.
2. résume les changements à réconcilier
3. annule le cherry-pick. En d'autres termes, revient à l'état d'avant le cherry-pick, en préservant toutes les modifications locales que vous aviez dans l'arbre de travail.
4. essaie d'appliquer le changement introduit par topic^ à nouveau, en passant du temps supplémentaire pour éviter les erreurs basées sur la correspondance incorrecte des lignes de contexte.
