NOM

git-commit-graph - Écrire et vérifier les fichiers commit-graph de Git

SYNOPSIS

git commit-graph verify [--object-dir <dir>] [--shallow] [--[no-]progress]
git commit-graph write [--object-dir <dir>] [--append]
                        [--split[=<strategy>]] [--reachable | --stdin-packs | --stdin-commits]
                        [--changed-paths] [--[no-]max-new-filters <n>] [--[no-]progress]
                        <split-options>

DESCRIPTION

Gérer le fichier commit-graph sérialisé.

OPTIONS

--object-dir

Utiliser le répertoire donné pour l'emplacement des fichiers pack et du fichier commit-graph. Ce paramètre existe pour spécifier l'emplacement d'un alternat qui ne possède que le répertoire d'objets, et non un répertoire .git complet. Le fichier commit-graph est censé se trouver dans le répertoire <dir>/info et les fichiers pack sont censés se trouver dans <dir>/pack. Si le répertoire ne peut pas être converti en chemin absolu, ou ne correspond à aucun répertoire d'objets connu, git commit-graph ... se terminera avec un code de sortie non nul.

--progress, --no-progress

Activer/désactiver explicitement l'affichage de la progression. Si aucune des deux options n'est spécifiée, la progression est affichée si la sortie d'erreur standard est connectée à un terminal.

COMMANDES

write

Écrire un fichier commit-graph à partir des commits trouvés dans les fichiers pack. Si l'option de configuration core.commitGraph est désactivée, alors cette commande affichera un avertissement, puis retournera un succès sans écrire de fichier commit-graph.

Avec l'option --stdin-packs , générer le nouveau graphe de commits en parcourant uniquement les objets des index de pack spécifiés. (Ne peut être combinée avec --stdin-commits ou --reachable.)

Avec l'option --stdin-commits , générer le nouveau graphe de commits en parcourant les commits à partir des commits spécifiés sur l'entrée standard sous la forme d'une liste d'OID en hexadécimal, un OID par ligne. Les OID qui résolvent vers des éléments qui ne sont pas des commits (soit directement, soit en déballant des étiquettes) sont ignorés silencieusement. Les OID malformés, ou qui n'existent pas, génèrent une erreur. (Ne peut être combinée avec --stdin-packs ou --reachable.)

Avec l'option --reachable , générer le nouveau graphe de commits en parcourant les commits à partir de toutes les références. (Ne peut être combinée avec --stdin-commits ou --stdin-packs.)

Avec l'option --append , inclure tous les commits qui sont présents dans le fichier commit-graph existant.

Avec l'option --changed-paths , calculer et écrire des informations sur les chemins modifiés entre un commit et son premier parent. Cette opération peut prendre du temps sur les grands dépôts. Elle fournit des gains de performance significatifs pour obtenir l'historique d'un répertoire ou d'un fichier avec git log -- <path>. Si cette option est donnée, les futurs écritures de commit-graph supposeront automatiquement que cette option était voulue. Utiliser --no-changed-paths pour arrêter de stocker ces données. --changed-paths est impliqué par la configuration commitGraph.changedPaths=true.

Avec l'option --max-new-filters=<n> , générer au plus n nouveaux filtres de Bloom (si --changed-paths est spécifié). Si n vaut -1, aucune limite n'est appliquée. Seuls les commits présents dans la nouvelle couche comptent pour cette limite. Pour rétroactivement calculer des filtres de Bloom sur des couches antérieures, il est conseillé d'utiliser --split=replace. Remplace la configuration commitGraph.maxNewFilters .

Avec l'option --split[=<strategy>] , écrire le commit-graph sous la forme d'une chaîne de plusieurs fichiers commit-graph stockés dans <dir>/info/commit-graphs. Les couches de commit-graph sont fusionnées en fonction de la stratégie et des autres options de fractionnement. Les nouveaux commits non déjà présents dans le commit-graph sont ajoutés dans un nouveau fichier « tip ». Ce fichier est fusionné avec le fichier existant si les conditions de fusion suivantes sont remplies :

•Si --split=no-merge est spécifié, une fusion n'est jamais effectuée, et les options restantes sont ignorées. --split=replace remplace la chaîne existante par une nouvelle. Un --split simple renvoie aux options restantes. (Notez que la fusion d'une chaîne de graphes de commits remplace la chaîne existante par une chaîne de longueur 1 où le premier et unique incrémental contient l'intégralité du graphe).
•Si --size-multiple=<X> n'est pas spécifié, faire en sorte que X soit égal à 2. Si le nouveau fichier tip aurait N commits et le tip précédent a M commits et que X] fois N est supérieur à M, fusionner plutôt les deux fichiers en un seul fichier.
•Si --max-commits=<M> est spécifié avec M un entier positif, et que le nouveau fichier tip aurait plus de M commits, alors fusionner plutôt le nouveau tip avec le tip précédent.

Enfin, si --expire-time=<datetime> n'est pas spécifié, faire en sorte que datetime soit l'heure actuelle. Après avoir écrit le commit-graph fractionné, supprimer tous les commit-graph inutilisés dont l'heure de modification est antérieure à datetime.

verify

Lire le fichier commit-graph et vérifier son contenu par rapport à la base de données d'objets. Utilisé pour vérifier les données corrompues.

Avec l'option --shallow , vérifier uniquement le fichier commit-graph de pointe dans une chaîne de commit-graph fractionnés.

EXEMPLES

•Écrire un fichier commit-graph pour les commits empaquetés dans votre répertoire local .git . 
$ git commit-graph write
•Écrire un fichier commit-graph, en étendant le fichier commit-graph actuel en utilisant les commits dans <pack-index>. 
$ echo <pack-index> | git commit-graph write --stdin-packs
•Écrire un fichier commit-graph contenant tous les commits accessibles. 
$ git show-ref -s | git commit-graph write --stdin-commits
•Écrire un fichier commit-graph contenant tous les commits du fichier commit-graph actuel ainsi que ceux accessibles depuis HEAD. 
$ git rev-parse HEAD | git commit-graph write --stdin-commits --append

CONFIGURATION

Tout ce qui se trouve sous cette ligne dans cette section est inclus sélectivement depuis la documentation git-config(1) . Le contenu est identique à celui qui s'y trouve :

commitGraph.generationVersion

Spécifie le type de version de numéro de génération à utiliser lors de l'écriture ou de la lecture du fichier commit-graph. Si la version 1 est spécifiée, les dates de commit corrigées ne seront ni écrites ni lues. Par défaut à 2.

commitGraph.maxNewFilters

Spécifie la valeur par défaut pour l'option --max-new-filters de git commit-graph write (cf., git-commit-graph(1)).

commitGraph.changedPaths

Si vrai, alors git commit-graph write calculera et écrira les filtres de Bloom des chemins modifiés par défaut, équivalent à passer --changed-paths. Si faux ou non défini, les filtres de Bloom des chemins modifiés seront écrits lors de git commit-graph write seulement si les filtres existent déjà dans le fichier commit-graph actuel. Cela correspond au comportement par défaut de git commit-graph write sans aucune option --[no-]changed-paths . Pour réécrire un fichier commit-graph sans aucun filtre, utiliser l'option --no-changed-paths . L'option de ligne de commande --[no-]changed-paths a toujours la priorité sur cette configuration. Par défaut non défini.

commitGraph.readChangedPaths

Obsolète. Équivalent à commitGraph.changedPathsVersion=-1 si vrai, et commitGraph.changedPathsVersion=0 si faux. (Si commitGraph.changedPathVersion est également défini, commitGraph.changedPathsVersion a la priorité.)

commitGraph.changedPathsVersion

Spécifie la version des filtres de Bloom des chemins modifiés que Git lira et écrira. Peut être -1, 0, 1 ou 2. Notez que les valeurs supérieures à 1 peuvent être incompatibles avec les anciennes versions de Git qui ne comprennent pas encore ces versions. Soyez prudent lorsque vous travaillez dans un environnement à versions mixtes.

Par défaut à -1.

Si -1, Git utilisera la version des filtres de Bloom des chemins modifiésm filtres dans le dépôt, par défaut 1 s'il n'y en a aucun.

Si 0, Git ne lira aucun filtre Bloom, et écrira des filtres Bloom de version 1 lorsqu'il sera invité à écrire.

Si 1, Git ne lira que des filtres Bloom de version 1, et écrira des filtres Bloom de version 1.

Si 2, Git ne lira que des filtres Bloom de version 2, et écrira des filtres Bloom de version 2.

Voir git-commit-graph(1) pour plus d'informations.
