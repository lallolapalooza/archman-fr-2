NOM

gitmodules - Définition des propriétés des sous-modules

SYNTAXE

$GIT_WORK_TREE/.gitmodules

DESCRIPTION

Le fichier .gitmodules, situé dans le répertoire racine d'un arbre de travail Git, est un fichier texte dont la syntaxe correspond aux exigences de git-config(1).

Le fichier contient une sous-section par sous-module, et la valeur de la sous-section est le nom du sous-module. Le nom est défini sur le chemin où le sous-module a été ajouté, sauf s'il a été personnalisé avec l'option --name de git submodule add. Chaque section de sous-module contient également les clés requises suivantes :

submodule.<nom>.path

Définit le chemin, relatif au répertoire racine de l'arbre de travail Git, où le sous-module est censé être décompressé. Le nom du chemin ne doit pas se terminer par un /. Tous les chemins de sous-modules doivent être uniques dans le fichier .gitmodules.

submodule.<nom>.url

Définit une URL à partir de laquelle le dépôt du sous-module peut être cloné. Il peut s'agir d'une URL absolue prête à être passée à git-clone(1) ou (si elle commence par ./ ou ../) d'un emplacement relatif au dépôt d'origine du superprojet.

De plus, il existe un certain nombre de clés optionnelles :

submodule.<nom>.update

Définit la procédure de mise à jour par défaut pour le sous-module nommé, c'est-à-dire comment le sous-module est mis à jour par la commande git submodule update dans le superprojet. Ceci est uniquement utilisé par git submodule init pour initialiser la variable de configuration du même nom. Les valeurs autorisées ici sont checkout, rebase, merge ou none, mais pas !command (pour des raisons de sécurité). Voir la description de la commande update dans git-submodule(1) pour plus de détails.

submodule.<nom>.branch

Un nom de branche distante pour suivre les mises à jour dans le sous-module en amont. Si l'option n'est pas spécifiée, elle utilise par défaut la HEAD distante. Une valeur spéciale de . est utilisée pour indiquer que le nom de la branche dans le sous-module doit être le même que le nom de la branche actuelle dans le dépôt actuel. Voir la documentation de --remote dans git-submodule(1) pour les détails.

submodule.<nom>.fetchRecurseSubmodules

Cette option peut être utilisée pour contrôler la récupération récursive de ce sous-module. Si cette option est également présente dans l'entrée du sous-module dans .git/config du superprojet, le réglage à cet endroit remplacera celui trouvé dans .gitmodules. Les deux réglages peuvent être remplacés en ligne de commande en utilisant l'option --[no-]recurse-submodules pour git fetch et git pull.

submodule.<nom>.ignore

Définit dans quelles circonstances git status et la famille diff montrent un sous-module comme modifié. Les valeurs suivantes sont prises en charge :

all

Le sous-module ne sera jamais considéré comme modifié (mais apparaîtra néanmoins dans la sortie de status et commit lorsqu'il aura été mis en scène).

dirty

Toutes les modifications apportées à l'arbre de travail du sous-module seront ignorées, seules les différences commises entre la HEAD du sous-module et son état enregistré dans le superprojet seront prises en compte.

untracked

Seuls les fichiers non suivis dans les sous-modules seront ignorés. Les différences commises et les modifications des fichiers suivis s'afficheront.

none

Aucune modification des sous-modules n'est ignorée, toutes les différences commises, et les modifications des fichiers suivis et non suivis s'affichent. C'est l'option par défaut.

Si cette option est également présente dans l'entrée du sous-module dans .git/config du superprojet, le réglage à cet endroit remplacera celui trouvé dans .gitmodules.

Les deux réglages peuvent être remplacés en ligne de commande en utilisant l'option --ignore-submodules. Les commandes git submodule ne sont pas affectées par ce réglage.

submodule.<nom>.shallow

Lorsqu'elle est définie sur true, un clone de ce sous-module sera effectué en tant que clone peu profond (avec une profondeur d'historique de 1) à moins que l'utilisateur ne demande explicitement un clone non peu profond.

NOTES

Git n'autorise pas que le fichier .gitmodules dans un arbre de travail soit un lien symbolique, et refusera de décompresser une telle entrée d'arbre. Cela maintient la cohérence du comportement lorsqu'on accède au fichier depuis l'index ou un arbre par rapport au système de fichiers, et aide Git à appliquer de manière fiable les vérifications de sécurité du contenu du fichier.

EXEMPLES

Considérez le fichier .gitmodules suivant :

[submodule "libfoo"]
        path = include/foo
        url = git://foo.com/git/lib.git
[submodule "libbar"]
        path = include/bar
        url = git://bar.com/git/lib.git

Ceci définit deux sous-modules, libfoo et libbar. Ceux-ci sont censés être décompressés dans les chemins include/foo et include/bar, et pour les deux sous-modules une URL est spécifiée qui peut être utilisée pour cloner les sous-modules.
