DESCRIPTIO

N

Un fichier gitattributes est un simple fichier texte qui attribue des attributs à des noms de

chemins.

Chaque ligne dans un fichier gitattributes a la forme

: 
motif attr1 attr2 .
.
.

C'est-à-dire un motif suivi d'une liste d'attributs, séparés par des espaces. Les espaces en début et en fin de ligne sont ignorés. Les lignes commençant par # sont ignorées. Les motifs commençant par une double quote sont échappés au style C. Lorsque le motif correspond au chemin en question, les attributs listés sur la ligne sont attribués au

chemin.

Chaque attribut peut se trouver dans l'un de ces états pour un chemin donné

:

Défini

(Set)
Le chemin a l'attribut avec la valeur spéciale "true" ; ceci est spécifié en listant uniquement le nom de l'attribut dans la liste
d'attributs.

Non défini

(Unset)
Le chemin a l'attribut avec la valeur spéciale "false" ; ceci est spécifié en listant le nom de l'attribut préfixé d'un tiret - dans la liste
d'attributs.

Défini avec une valeur (Set to a

value)
Le chemin a l'attribut avec la valeur de chaîne spécifiée ; ceci est spécifié en listant le nom de l'attribut suivi d'un signe égal = et de sa valeur dans la liste
d'attributs.

Non spécifié

(Unspecified)
Aucun motif ne correspond au chemin, et rien n'indique si le chemin a ou n'a pas l'attribut ; l'attribut pour le chemin est dit Non
spécifié.

Lorsque plus d'un motif correspond au chemin, une ligne ultérieure l'emporte sur une ligne antérieure. Ce remplacement se fait attribut par

attribut.

Les règles selon lesquelles le motif correspond aux chemins sont les mêmes que dans les fichiers .gitignore (voir gitignore(5)), avec quelques exceptions

:
•les motifs négatifs sont
interdits
•les motifs qui correspondent à un répertoire ne correspondent pas récursivement aux chemins à l'intérieur de ce répertoire (donc utiliser la syntaxe avec barre oblique finale chemin/ est inutile dans un fichier d'attributs ; utiliser chemin/** à la
place)

Lorsqu'il décide quels attributs sont assignés à un chemin, Git consulte le fichier $GIT_DIR/info/attributes (qui a la priorité la plus élevée), le fichier .gitattributes situé dans le même répertoire que le chemin en question, et ses répertoires parents jusqu'à la racine de l'arbre de travail (plus le répertoire contenant .gitattributes est éloigné du chemin en question, plus sa priorité est faible). Enfin, les fichiers globaux et système sont pris en compte (ils ont la priorité la plus faible)

.

Lorsque le fichier .gitattributes est absent de l'arbre de travail, le chemin dans l'index est utilisé comme solution de repli. Pendant le processus de checkout, .gitattributes dans l'index est utilisé, puis le fichier dans l'arbre de travail est utilisé comme solution de

repli.

Si vous souhaitez n'affecter qu'un seul dépôt (c'est-à-dire assigner des attributs à des fichiers particuliers au flux de travail d'un utilisateur pour ce dépôt), alors les attributs doivent être placés dans le fichier $GIT_DIR/info/attributes. Les attributs qui doivent être versionnés et distribués à d'autres dépôts (c'est-à-dire les attributs d'intérêt pour tous les utilisateurs) doivent aller dans les fichiers .gitattributes. Les attributs qui doivent affecter tous les dépôts d'un utilisateur unique doivent être placés dans un fichier spécifié par l'option de configuration core.attributesFile (voir git-config(1)). Sa valeur par défaut est $XDG_CONFIG_HOME/git/attributes. Si $XDG_CONFIG_HOME n'est pas défini ou est vide, $HOME/.config/git/attributes est utilisé à la place. Les attributs pour tous les utilisateurs d'un système doivent être placés dans le fichier $(prefix)/etc/gitattributes

.

Parfois, vous aurez besoin de remplacer un paramètre d'un attribut pour un chemin à l'état Non spécifié. Cela peut être fait en listant le nom de l'attribut préfixé d'un point d'exclamation

!
.

Conversion de fin de ligne

Bien que Git laisse normalement le contenu des fichiers intact, il peut être configuré pour normaliser les fins de ligne en LF dans le dépôt et, éventuellement, pour les convertir en CRLF lors du checkout de fichiers.

Si vous souhaitez simplement avoir des fins de ligne CRLF dans votre répertoire de travail, quel que soit le dépôt avec lequel vous travaillez, vous pouvez définir la variable de configuration « core.autocrlf » sans utiliser d'attributs.

[core]
        autocrlf = true

Cela ne force pas la normalisation des fichiers texte, mais garantit que les fichiers texte que vous introduisez dans le dépôt auront leurs fins de ligne normalisées en LF lors de leur ajout, et que les fichiers déjà normalisés dans le dépôt resteront normalisés.

Si vous souhaitez vous assurer que tous les contributeurs qui introduisent des fichiers texte dans le dépôt normalisent leurs fins de ligne, vous pouvez définir l'attribut text sur « auto » pour *tous* les fichiers.

*       text=auto

Les attributs permettent un contrôle granulaire de la manière dont les fins de ligne sont converties. Voici un exemple qui fera en sorte que Git normalise les fichiers .txt, .vcproj et .sh, s'assure que les fichiers .vcproj aient des CRLF et les fichiers .sh des LF dans le répertoire de travail, et empêche la normalisation des fichiers .jpg, quel que soit leur contenu.

*               text=auto
*.txt           text
*.vcproj        text eol=crlf
*.sh            text eol=lf
*.jpg           -text

Note

Lorsque la conversion text=auto est activée dans un projet multiplateforme utilisant push et pull vers un dépôt central, les fichiers texte contenant des CRLF doivent être normalisés.

À partir d'un répertoire de travail propre :

$ echo "* text=auto" >.gitattributes
$ git add --renormalize .
$ git status        # Affiche les fichiers qui seront normalisés
$ git commit -m "Introduction de la normalisation des fins de ligne"

Si des fichiers qui ne devraient pas être normalisés apparaissent dans git status, désactivez leur attribut text avant d'exécuter git add -u.

manual.pdf      -text

Inversement, la normalisation peut être activée manuellement pour les fichiers texte que Git ne détecte pas.

weirdchars.txt  text

Si core.safecrlf est défini sur « true » ou « warn », Git vérifie si la conversion est réversible pour le paramètre actuel de core.autocrlf. Pour « true », Git rejette les conversions non réversibles ; pour « warn », Git imprime seulement un avertissement mais accepte une conversion non réversible. Les déclencheurs de sécurité empêchent une telle conversion sur les fichiers dans l'arborescence de travail, mais il y a quelques exceptions. Même si...

•git add ne touche pas les fichiers dans l'arborescence de travail, le prochain checkout le fera, donc les déclencheurs de sécurité s'appliquent ;
•git apply pour mettre à jour un fichier texte avec un patch touche les fichiers dans l'arborescence de travail, mais l'opération concerne des fichiers texte et la conversion CRLF vise à corriger les incohérences de fins de ligne, donc la sécurité ne se déclenche pas ;
•git diff ne touche pas les fichiers dans l'arborescence de travail, il est souvent exécuté pour inspecter les modifications que vous prévoyez d'ajouter ensuite avec git add. Pour attraper les problèmes potentiels tôt, les déclencheurs de sécurité s'appliquent.

working-tree-encoding

Git reconnaît les fichiers encodés en ASCII ou dans l'un de ses superset (par exemple, UTF-8, ISO-8859-1, ...) comme des fichiers texte. Les fichiers encodés dans certaines autres encodages (par exemple, UTF-16) sont interprétés comme binaires et par conséquent les outils de traitement de texte intégrés à Git (par exemple, git diff) ainsi que la plupart des interfaces web Git ne visualisent pas le contenu de ces fichiers par défaut.

Dans ces cas, vous pouvez indiquer à Git l'encodage d'un fichier dans le répertoire de travail avec l'attribut working-tree-encoding. Si un fichier avec cet attribut est ajouté à Git, Git réencode le contenu de l'encodage spécifié vers UTF-8. Enfin, Git stocke le contenu encodé en UTF-8 dans sa structure de données interne (appelée « l'index »). Lors du checkout, le contenu est réencodé vers l'encodage spécifié.

Veuillez noter que l'utilisation de l'attribut working-tree-encoding peut présenter plusieurs écueils :

•Les implémentations Git alternatives (par exemple, JGit ou libgit2) et les anciennes versions de Git (depuis mars 2018) ne prennent pas en charge l'attribut working-tree-encoding. Si vous décidez d'utiliser l'attribut working-tree-encoding dans votre dépôt, il est fortement recommandé de vous assurer que tous les clients travaillant avec le dépôt le prennent en charge.

Par exemple, les fichiers de ressources Microsoft Visual Studio (*.rc) ou les fichiers de script PowerShell (*.ps1) sont parfois encodés en UTF-16. Si vous déclarez les *.ps1 comme fichiers UTF-16 et que vous ajoutez foo.ps1 avec un client Git prenant en charge working-tree-encoding, alors foo.ps1 sera stocké en interne en UTF-8. Un client sans prise en charge de working-tree-encoding effectuera le checkout de foo.ps1 en tant que fichier encodé en UTF-8. Cela causera généralement des problèmes pour les utilisateurs de ce fichier.

Si un client Git qui ne prend pas en charge l'attribut working-tree-encoding ajoute un nouveau fichier bar.ps1, alors bar.ps1 sera stocké « tel quel » en interne (dans cet exemple, probablement en UTF-16). Un client prenant en charge working-tree-encoding interprétera le contenu interne comme de l'UTF-8 et tentera de le convertir en UTF-16 lors du checkout. Cette opération échouera et provoquera une erreur.

•La réencodage du contenu vers des encodages non UTF peut provoquer des erreurs, car la conversion pourrait ne pas être sûre pour un aller-retour UTF-8. Si vous suspectez que votre encodage n'est pas sûr pour l'aller-retour, ajoutez-le à core.checkRoundtripEncoding pour que Git vérifie l'encodage aller-retour (voir git-config(1)). SHIFT-JIS (jeu de caractères japonais) est connu pour avoir des problèmes d'aller-retour avec UTF-8 et est vérifié par défaut.
•Le réencodage du contenu nécessite des ressources qui pourraient ralentir certaines opérations Git (par exemple, git checkout ou git add).

Utilisez l'attribut working-tree-encoding uniquement si vous ne pouvez pas stocker un fichier en encodage UTF-8 et si vous souhaitez que Git puisse traiter le contenu comme du texte.

Par exemple, utilisez les attributs suivants si vos fichiers *.ps1 sont encodés en UTF-16 avec une marque d'ordre des octets (BOM) et que vous souhaitez que Git effectue une conversion automatique des fins de ligne basée sur votre plateforme.

*.ps1           text working-tree-encoding=UTF-16

Utilisez les attributs suivants si vos fichiers *.ps1 sont encodés en UTF-16 little endian sans BOM et que vous souhaitez que Git utilise les fins de ligne Windows dans le répertoire de travail (utilisez UTF-16LE-BOM au lieu de UTF-16LE si vous souhaitez UTF-16 little endian avec BOM). Veuillez noter qu'il est fortement recommandé de définir explicitement les fins de ligne avec eol si l'attribut working-tree-encoding est utilisé pour éviter toute ambiguïté.

*.ps1           text working-tree-encoding=UTF-16LE eol=crlf

Vous pouvez obtenir une liste de tous les encodages disponibles sur votre plateforme avec la commande suivante :

iconv --list

Si vous ne connaissez pas l'encodage d'un fichier, vous pouvez utiliser la commande file pour deviner l'encodage :

file foo.ps1

ident

Lorsque l'attribut ident est défini pour un chemin, Git remplace $Id$ dans l'objet blob par $Id:, suivi du nom de l'objet blob hexadécimal de 40 caractères, suivi d'un signe dollar $ lors du checkout. Toute séquence d'octets commençant par $Id: et se terminant par $ dans le fichier de l'arborescence de travail est remplacée par $Id$ lors du check-in.

filter

Un attribut filter peut être défini sur une valeur chaîne qui nomme un pilote de filtre spécifié dans la configuration.

Un pilote de filtre se compose d'une commande clean et d'une commande smudge, dont l'une ou l'autre peut être laissée non spécifiée. Lors du checkout, lorsque la commande smudge est spécifiée, la commande reçoit l'objet blob via son entrée standard, et sa sortie standard est utilisée pour mettre à jour le fichier de l'arborescence de travail. De même, la commande clean est utilisée pour convertir le contenu du fichier de l'arborescence de travail lors du check-in. Par défaut, ces commandes traitent un seul blob et se terminent. Si un filtre de process de longue durée est utilisé à la place des filtres clean et/ou smudge, alors Git peut traiter tous les blobs avec une seule invocation de commande de filtre pour toute la durée d'une seule commande Git, par exemple git add --all. Si un filtre de process de longue durée est configuré, il a toujours la priorité sur un filtre de blob unique configuré. Voir la section ci-dessous pour la description du protocole utilisé pour communiquer avec un filtre de process.

Une utilisation du filtrage de contenu est de traiter le contenu dans une forme plus pratique pour la plateforme, le système de fichiers et l'utilisateur. Pour ce mode de fonctionnement, l'expression clé ici est « plus pratique » et non « transformer quelque chose d'inutilisable en utilisable ». En d'autres termes, l'intention est que si quelqu'un désactive la définition du pilote de filtre, ou n'a pas le programme de filtre approprié, le projet devrait toujours être utilisable.

Une autre utilisation du filtrage de contenu est de stocker du contenu qui ne peut pas être utilisé directement dans le dépôt (par exemple, un UUID qui fait référence au vrai contenu stocké en dehors de Git, ou un contenu chiffré) et de le transformer en une forme utilisable lors du checkout (par exemple, télécharger le contenu externe, ou déchiffrer le contenu chiffré).

Ces deux filtres se comportent différemment, et par défaut, un filtre est considéré comme le premier, traitant le contenu pour le rendre plus pratique. Une définition de pilote de filtre manquante dans la configuration, ou un pilote de filtre qui se termine avec un statut non nul, n'est pas une erreur mais fait du filtre un simple passage sans opération.

Vous pouvez déclarer qu'un filtre transforme un contenu qui est en soi inutilisable en un contenu utilisable en définissant la variable de configuration filter.<driver>.required sur true.

Remarque : Chaque fois que le filtre clean est modifié, le dépôt doit être renormalisé : $ git add --renormalize .

Par exemple, dans .gitattributes, vous affecteriez l'attribut filter pour les chemins.

*.c     filter=indent

Ensuite, vous définiriez une configuration "filter.indent.clean" et "filter.indent.smudge" dans votre .git/config pour spécifier une paire de commandes pour modifier le contenu des programmes C lorsque les fichiers source sont archivés ("clean" est exécuté) et extraits (aucun changement n'est effectué car la commande est "cat").

[filter "indent"]
        clean = indent
        smudge = cat

Pour de meilleurs résultats, clean ne devrait pas modifier sa sortie davantage s'il est exécuté deux fois ("clean→clean" devrait

Voici le contenu traduit en français, en conservant la structure du fichier : be equivalent to "nettoyer"), et plusieurs commandes nettoyer ne doivent pas altérer la sortie de nettoyer (« nettoyer→nettoyer→nettoyer » devrait être équivalent à « nettoyer »). Voir la section sur la fusion ci-dessous. » »

Le filtre « indent » se comporte bien à cet égard : il ne modifiera pas les entrées déjà correctement indentées. Dans ce cas, l'absence de filtre de nettoyage signifie que le filtre de nettoyage *doit* accepter sa propre sortie sans la modifier.

Si un filtre *doit* réussir pour rendre utilisables les contenus stockés, vous pouvez déclarer que le filtre est requis, dans la configuration :

[filter « crypt »]
        clean = openssl enc ...
        smudge = openssl enc -d ...
        required

La séquence « %f » sur la ligne de commande du filtre est remplacée par le nom du fichier sur lequel le filtre travaille. Un filtre peut l'utiliser dans la substitution de mots-clés. Par exemple :

[filter « p4 »]
        clean = git-p4-filter --clean %f
        smudge = git-p4-filter --smudge %f

Notez que « %f » est le nom du chemin sur lequel on travaille. Selon la version qui est filtrée, le fichier correspondant sur le disque peut ne pas exister ou peut avoir un contenu différent. Ainsi, les commandes de nettoyage et de nettoyage ne devraient pas essayer d'accéder au fichier sur le disque, mais agir uniquement comme filtres sur le contenu qui leur est fourni en entrée standard.

Processus de filtre à longue exécution

Si la commande de filtre (une valeur de chaîne) est définie via filter.<driver>.process alors Git peut traiter tous les blobs avec une seule invocation de filtre pour toute la durée d'une commande Git unique. Ceci est réalisé en utilisant le protocole de processus à longue exécution (décrit dans Documentation/technical/long-running-process-protocol.adoc).

Lorsque Git rencontre le premier fichier qui doit être nettoyé ou nettoyé, il démarre le filtre et effectue la poignée de main. Dans la poignée de main, le message de bienvenue envoyé par Git est « git-filter-client », seule la version 2 est prise en charge, et les capacités prises en charge sont « clean », « smudge » et « delay ».

Ensuite, Git envoie une liste de paires « clé=valeur » terminées par un paquet de flush. La liste contiendra au moins la commande de filtre (basée sur les capacités prises en charge) et le chemin du fichier à filtrer par rapport à la racine du dépôt. Juste après le paquet de flush, Git envoie le contenu divisé en zéro ou plusieurs paquets pkt-line et un paquet de flush pour terminer le contenu. Veuillez noter que le filtre ne doit envoyer aucune réponse avant d'avoir reçu le contenu et le paquet de flush final. Notez également que la « valeur » d'une paire « clé=valeur » peut contenir le caractère « = » tandis que la clé ne contiendrait jamais ce caractère.

packet:          git> command=smudge
packet:          git> pathname=path/testfile.dat
packet:          git> 0000
packet:          git> CONTENT
packet:          git> 0000

Le filtre est censé répondre avec une liste de paires « clé=valeur » terminées par un paquet de flush. Si le filtre ne rencontre pas de problèmes, la liste doit contenir un statut « success ». Juste après ces paquets, le filtre est censé envoyer le contenu en zéro ou plusieurs paquets pkt-line et un paquet de flush à la fin. Enfin, une deuxième liste de paires « clé=valeur » terminées par un paquet de flush est attendue. Le filtre peut modifier le statut dans la deuxième liste ou conserver le statut tel quel avec une liste vide. Veuillez noter que la liste vide doit être terminée par un paquet de flush dans tous les cas.

packet:          git< status=success
packet:          git< 0000
packet:          git< SMUDGED_CONTENT
packet:          git< 0000
packet:          git< 0000  # liste vide, conserver « status=success » inchangé !»

Si le contenu du résultat est vide, le filtre est censé répondre avec un statut « success » et un paquet de flush pour signaler le contenu vide.

packet:          git< status=success
packet:          git< 0000
packet:          git< 0000  # contenu vide !
packet:          git< 0000  # liste vide, conserver « status=success » inchangé !»

Dans le cas où le filtre ne peut pas ou ne veut pas traiter le contenu, il est censé répondre avec un statut « error ».

packet:          git< status=error
packet:          git< 0000

Si le filtre rencontre une erreur pendant le traitement, il peut alors envoyer le statut « error » après que le contenu a été (partiellement ou complètement) envoyé.

packet:          git< status=success
packet:          git< 0000
packet:          git< HALF_WRITTEN_ERRONEOUS_CONTENT
packet:          git< 0000
packet:          git< status=error
packet:          git< 0000

Dans le cas où le filtre ne peut pas ou ne veut pas traiter le contenu ainsi que tout contenu futur pendant toute la durée du processus Git, il est censé répondre avec un statut « abort » à tout moment du protocole.

packet:          git< status=abort
packet:          git< 0000

Git n'arrête ni ne redémarre le processus de filtre au cas où le statut « error »/« abort » est défini. Cependant, Git définit son code de sortie conformément au drapeau filter.<driver>.required, imitant le comportement du mécanisme filter.<driver>.clean / filter.<driver>.smudge.

Si le filtre meurt pendant la communication ou n'adhère pas au protocole, alors Git arrêtera le processus de filtre et le redémarrera avec le prochain fichier qui doit être traité. Selon le drapeau filter.<driver>.required, Git interprétera cela comme une erreur.

Délai

Si le filtre prend en charge la capacité « delay », alors Git peut envoyer le drapeau « can-delay » après la commande de filtre et le chemin d'accès. Ce drapeau indique que le filtre peut retarder le filtrage du blob actuel (par exemple, pour compenser les latences réseau) en répondant sans contenu mais avec le statut « delayed » et un paquet de flush.

packet:          git> command=smudge
packet:          git> pathname=path/testfile.dat
packet:          git> can-delay=1
packet:          git> 0000
packet:          git> CONTENT
packet:          git> 0000
packet:          git< status=delayed
packet:          git< 0000

Si le filtre prend en charge la capacité « delay », il doit alors prendre en charge la commande « list_available_blobs ». Si Git envoie cette commande, alors le filtre est censé retourner une liste de chemins représentant les blobs qui ont été retardés précédemment et qui sont maintenant disponibles. La liste doit être terminée par un paquet de flush suivi d'un statut « success » qui est également terminé par un paquet de flush. Si aucun blob pour les chemins retardés n'est encore disponible, alors le filtre est censé bloquer la réponse jusqu'à ce qu'au moins un blob devienne disponible. Le filtre peut indiquer à Git qu'il n'a plus de blobs retardés en envoyant une liste vide. Dès que le filtre répond avec une liste vide, Git arrête de demander. Tous les blobs que Git n'a pas reçus à ce stade sont considérés comme manquants et entraîneront une erreur.

packet:          git> command=list_available_blobs
packet:          git> 0000
packet:          git< pathname=path/testfile.dat
packet:          git< pathname=path/otherfile.dat
packet:          git< 0000
packet:          git< status=success
packet:          git< 0000

Après que Git a reçu les chemins, il demandera à nouveau les blobs correspondants. Ces demandes contiennent un chemin d'accès et une section de contenu vide. Le filtre est censé répondre avec le contenu nettoyé de la manière habituelle comme expliqué ci-dessus.

packet:          git> command=smudge
packet:          git> pathname=path/testfile.dat
packet:          git> 0000
packet:          git> 0000  # contenu vide !
packet:          git< status=success
packet:          git< 0000
packet:          git< SMUDGED_CONTENT
packet:          git< 0000
packet:          git< 0000  # liste vide, conserver « status=success » inchangé !»

Exemple

Une implémentation de démonstration de filtre à longue exécution peut être trouvée dans contrib/long-running-filter/example.pl situé dans le dépôt principal de Git. Si vous développez votre propre processus de filtre à longue exécution, la variable d'environnement GIT_TRACE_PACKET peut être très utile pour le débogage (voir git(1)).

Veuillez noter que vous ne pouvez pas utiliser une commande existante filter.<driver>.clean ou filter.<driver>.smudge avec filter.<driver>.process car les deux premières utilisent un protocole de communication inter-processus différent de ce dernier.

Interaction entre les attributs de validation/extraction

Dans le chemin de code de validation, le fichier de l'espace de travail est d'abord converti avec le pilote filter (s'il est spécifié et que le pilote correspondant est défini), puis le résultat est traité avec ident (s'il est spécifié), puis enfin avec text (là encore, s'il est spécifié et applicable).

Dans le chemin de code d'extraction, le contenu du blob est d'abord converti avec text, puis ident et alimenté à filter.

Fusion des branches avec des attributs de validation/extraction différents

Si vous avez ajouté des attributs à un fichier qui provoquent la modification du format canonique du dépôt pour ce fichier, comme l'ajout d'un filtre de nettoyage/nettoyage ou des attributs text/eol/ident, la fusion de quoi que ce soit où l'attribut n'est pas en place provoquerait normalement des conflits de fusion.

Pour éviter ces conflits de fusion inutiles, Git peut être invité à exécuter une extraction et une validation virtuelles des trois étapes de chaque fichier qui nécessite une fusion de contenu à trois voies, en définissant la variable de configuration merge.renormalize. Cela empêche les modifications causées par la conversion de validation de provoquer des conflits de fusion fallacieux lorsqu'un fichier converti est fusionné avec un fichier non converti.

Tant qu'un « nettoyage→nettoyage » produit le même résultat qu'un « nettoyage » même sur les fichiers déjà nettoyés, cette stratégie résoudra automatiquement tous les conflits liés aux filtres. Les filtres qui n'agissent pas de cette manière peuvent causer des conflits de fusion supplémentaires qui doivent être résolus manuellement.

uts macro ne peuvent être que "Set" (définis), bien que définir un tel attribut puisse avoir l'effet de défin
ir ou d'annuler d'autres attributs ou même de retourner d'autres attributs à l'état "Unspecified" (non spécifié).

DÉFINITION DES ATTRIBUTS

MACRO

Les attributs macro personnalisés ne peuvent être définis que dans des fichiers gitattributes de premier niveau ($GIT_DIR/info/attributes, le fichier .gitattributes à la racine de l'arbre de travail, ou les fichiers gitattributes globaux ou système), pas dans les fichiers .gitattributes des sous-répertoires de l'arbre de travail. L'attribut macro intégré "binary" est équivalent à

: 
[attr]bi
nary -di
ff -mer
ge -text

NOTE

S

Git ne suit pas les liens symboliques lors de l'accès à un fichier .gitattributes dans l'arbre de travail. Cela maintient un comportement cohérent lorsque le

fichier est accédé depuis l'index ou un arbre par r
apport à l'accès depuis le système de fichiers.

EXEMPLE

S

Si vous avez ces trois fichiers gitattributes

: 
(dans $GIT_DIR/info/attributes)
a*      foo !bar -baz
(da
ns .gitattributes) abc foo bar baz (dans t/.gitattribu
tes) ab* merge=filfre abc -foo -bar *.c frotz

les attributs donnés au chemin t/abc sont calculés comme suit

:
1.En examinant t/.gitattributes (qui est dans le même répertoire que le chemin en question), Git trouve que la première ligne correspond. attribut merge est défini. Il trouve également que la deuxième ligne correspond, et les attributs foo et bar sont
annulés.
2.Puis il examine .gitattributes (qui est dans le répertoire parent), et trouve que la première ligne correspond, mais le fichier t/.gitattributes a déjà décidé comment les attributs merge, foo et bar devraient être donnés à ce chemin, il laisse donc foo et bar annulés. L'attribut baz est
défini.
3.Finalement il examine $GIT_DIR/info/attributes. Ce fichier est utilisé pour remplacer les paramètres dans l'arbre. La première ligne correspond, et foo est défini, bar est revenu à l'état non spécifié, et baz est
annulé.

En résultat, l'attribution des attributs à t/abc devient

: 
foo     défini à true
bar     non
spécifié baz défini à false
merge défini à la valeur de cha
îne "filfre" frotz non spécifié
