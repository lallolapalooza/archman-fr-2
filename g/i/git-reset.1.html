DESCRIPTIO

N

Dans les trois premières formes, copie des entrées de <tree-ish> vers l'index. Dans la dernière forme, définit la tête de la branche courante (HEAD) à <commit>, modifiant éventuellement l'index et l'arbre de travail pour correspondre. Le <tree-ish>/<commit> vaut par défaut HEAD dans toutes les

formes.

git reset [-q] [<tree-ish>] [--] <pathspec>..., git reset [-q] [--pathspec-from-file=<file> [--pathspec-file-nul]] [<tree-i

sh>]
Ces formes réinitialisent les entrées d'index pour tous les chemins qui correspondent à <pathspec> à leur état à <tree-ish>. (Cela n'affecte ni l'arbre de travail ni la branche courante.)

Cela signifie que git reset <pathspec> est l'opposé de git add <pathspec>. Cette commande est équivalente à git restore [--source=<tree-ish>] --staged <pathspec>...

.

Après avoir exécuté git reset <pathspec> pour mettre à jour l'entrée d'index, vous pouvez utiliser git-restore(1) pour extraire le contenu de l'index vers l'arbre de travail. Alternativement, en utilisant git-restore(1) et en spécifiant un commit avec --source, vous pouvez copier le contenu d'un chemin d'un

commit vers l'index et l'arbre
de travail en une seule fois.

git reset (--patch | -p) [<tree-ish>] [--] [<pathspec>...

]
Sélectionne interactivement les blocs dans la différence entre l'index et <tree-ish> (par défaut HEAD). Les blocs choisis sont appliqués en sens inverse à l'index.

Cela signifie que git reset -p est l'opposé de git add -p, c'est-à-dire que vous pouvez l'utiliser pour réinitialiser sélectivement des blocs. Voir la section « Interactive Mode » de git-add(1) pour apprendre à utiliser le mode -

-pat

git reset [<mode>] [<commi

t>]
Cette forme réinitialise la tête de la branche courante à <commit> et met éventuellement à jour l'index (en le réinitialisant à l'arbre de <commit>) et l'arbre de travail selon <mode>. Avant l'opération, ORIG_HEAD est défini à la pointe de la branche courante. Si <mode> est omis, la valeur par défaut est --mixed. Le <mode> doit être l'une des valeurs suivantes :

--sof

t
Ne touche ni au fichier d'index ni à l'arbre de travail (mais réinitialise la tête à <commit>, comme tous les modes le font). Cela laisse tous vos fichiers modifiés en « Changes to be committed », comme git status le
dirait.

--mixe

d
Réinitialise l'index mais pas l'arbre de travail (c'est-à-dire que les fichiers modifiés sont préservés mais pas marqués pour le commit) et rapporte ce qui n'a pas été mis à jour. C'est l'action par défaut.

Si -N est spécifié, les chemins supprimés sont marqués comme intention d'ajout (voir git-ad

d(1
)).

--har

d
Réinitialise l'index et l'arbre de travail. Toutes les modifications des fichiers suivis dans l'arbre de travail depuis <commit> sont annulées. Tout fichier ou répertoire non suivi qui se trouve sur le chemin d'écriture de fichiers suivis est simplement
supprimé.

--merg

e
Réinitialise l'index et met à jour les fichiers dans l'arbre de travail qui sont différents entre <commit> et HEAD, mais conserve ceux qui sont différents entre l'index et l'arbre de travail (c'est-à-dire qui ont des modifications qui n'ont pas été ajoutées). Si un fichier qui est différent entre <commit> et l'index a des modifications non indexées, la réinitialisation est annulée.

En d'autres termes, --merge fait quelque chose comme un git read-tree -u -m <commit>, mais conserve les

entrées d'index
non fusionnées.

--kee

p
Réinitialise les entrées d'index et met à jour les fichiers dans l'arbre de travail qui sont différents entre <commit> et HEAD. Si un fichier qui est différent entre <commit> et HEAD a des modifications locales, la réinitialisation est
annulée.

--recurse-submodules, --no-recurse-submodule

s
Lorsque l'arbre de travail est mis à jour, l'utilisation de ‘--recurse-submodules` réinitialisera également récursivement l'arbre de travail de tous les sous-modules actifs selon le commit enregistré dans le superprojet, définissant également le HEAD des sous-modules c

git reset --merge est destiné à être utilisé lors d'une réinitialisation à partir d'un merge en conflit. Toute opération de fusion garantit que le fichier de l'arbre de travail impliqué dans le merge n'a pas de modification locale par rapport à l'index avant qu'elle ne commence, et qu'elle écrit le résultat dans l'arbre de travail. Donc, si nous voyons une différence entre l'index et la cible, ainsi qu'entre l'index et l'arbre de travail, cela signifie que nous ne réinitialisons pas à partir d'un état laissé par une opération de fusion après un échec en raison d'un conflit. C'est pourquoi nous interdisons l'option --merge dans ce

cas.

git reset --keep est destiné à être utilisé lors de la suppression de certains des derniers commits de la branche actuelle tout en conservant les modifications dans l'arbre de travail. S'il pouvait y avoir des conflits entre les modifications du commit que nous voulons supprimer et les modifications de l'arbre de travail que nous voulons conserver, la réinitialisation est interdite. C'est pourquoi elle est interdite s'il y a à la fois des modifications entre l'arbre de travail et le HEAD, et entre le HEAD et la cible. Par sécurité, elle est également interdite en présence d'entrées non

fusionnées.
