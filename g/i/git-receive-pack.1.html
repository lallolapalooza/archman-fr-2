NOM

git-receive-pack - Reçoit ce qui est poussé dans le dépôt

SYNOPSIS

git receive-pack <git-dir>

DESCRIPTION

Invoqué par git send-pack et met à jour le dépôt avec les informations transmises depuis l'extrémité distante.

Cette commande n'est généralement pas invoquée directement par l'utilisateur final. L'interface utilisateur pour le protocole se trouve du côté git send-pack et le programme associé est destiné à être utilisé pour pousser des mises à jour vers un dépôt distant. Pour les opérations de récupération, voir git-fetch-pack(1).

La commande permet la création et l'avance rapide (fast-forward) des références sha1 (têtes/tags) sur l'extrémité distante (strictement parlant, c'est l'extrémité locale git-receive-pack qui s'exécute, mais pour l'utilisateur assis à l'extrémité send-pack, cela met à jour le dépôt distant. Confus ?)

Il existe d'autres exemples concrets d'utilisation des crochets update et post-update dans le répertoire Documentation/howto.

git-receive-pack prend en compte l'option de configuration receive.denyNonFastForwards, qui lui indique si les mises à jour d'une référence doivent être refusées si elles ne sont pas des avances rapides.

Un certain nombre d'autres options de configuration receive.* sont disponibles pour ajuster son comportement, voir git-config(1).

OPTIONS

<git-dir>

Le dépôt dans lequel synchroniser.

--http-backend-info-refs

Utilisé par git-http-backend(1) pour servir les requêtes $GIT_URL/info/refs?service=git-receive-pack. Voir --http-backend-info-refs dans git-upload-pack(1).

--skip-connectivity-check

Contourne les vérifications de connectivité qui valident l'existence de tous les objets dans la fermeture transitive des objets accessibles. Cette option est destinée aux opérateurs de serveur qui souhaitent implémenter leur propre validation de connectivité des objets en dehors de Git. C'est utile dans les cas où le côté serveur connaît des informations supplémentaires sur la manière dont Git est utilisé et peut donc s'appuyer sur certaines garanties pour calculer plus efficacement la connectivité des objets que Git lui-même ne peut fournir. L'utilisation de cette option sans un mécanisme externe fiable pour assurer la connectivité complète des objets accessibles risque de corrompre le dépôt et ne devrait pas être utilisée dans le cas général.

CROCHET PRE-RECEIVE

Avant qu'une référence ne soit mise à jour, si le fichier $GIT_DIR/hooks/pre-receive existe et est exécutable, il sera invoqué une fois sans paramètres. L'entrée standard du crochet sera une ligne par référence à mettre à jour :

sha1-ancien SP sha1-nouveau SP nom-référence LF

La valeur de nom-référence est relative à $GIT_DIR ; par exemple pour la tête master c'est "refs/heads/master". Les deux valeurs sha1 avant chaque nom-référence sont les noms d'objet pour le nom-référence avant et après la mise à jour. Les références à créer auront sha1-ancien égal à 0{40}, tandis que les références à supprimer auront sha1-nouveau égal à 0{40}, sinon sha1-ancien et sha1-nouveau devraient être des objets valides dans le dépôt.

Lors de l'acceptation d'un push signé (voir git-push(1)), le certificat de push signé est stocké dans un blob et une variable d'environnement GIT_PUSH_CERT peut être consultée pour obtenir son nom d'objet. Voir la description du crochet post-receive pour un exemple. De plus, le certificat est vérifié à l'aide de GPG et le résultat est exporté avec les variables d'environnement suivantes :

GIT_PUSH_CERT_SIGNER

Le nom et l'adresse e-mail du propriétaire de la clé qui a signé le certificat de push.

GIT_PUSH_CERT_KEY

L'identifiant de clé GPG de la clé qui a signé le certificat de push.

GIT_PUSH_CERT_STATUS

L'état de la vérification GPG du certificat de push, utilisant le même mnémonique que celui utilisé dans le format %G? de la famille de commandes git log (voir git-log(1)).

GIT_PUSH_CERT_NONCE

La chaîne nonce que le processus a demandé au signataire d'inclure dans le certificat de push. Si cela ne correspond pas à la valeur enregistrée dans l'en-tête "nonce" du certificat de push, cela peut indiquer que le certificat est valide mais qu'il est rejoué depuis une session "git push" séparée.

GIT_PUSH_CERT_NONCE_STATUS

UNSOLICITED

"git push --signed" a envoyé un nonce alors que nous ne lui avions pas demandé d'en envoyer un.

MISSING

"git push --signed" n'a envoyé aucun en-tête nonce.

BAD

"git push --signed" a envoyé un nonce erroné.

OK

"git push --signed" a envoyé le nonce que nous lui avions demandé d'envoyer.

SLOP

"git push --signed" a envoyé un nonce différent de celui que nous lui avions demandé d'envoyer maintenant, mais dans une session précédente. Voir GIT_PUSH_CERT_NONCE_SLOP variable d'environnement.

GIT_PUSH_CERT_NONCE_SLOP

"git push --signed" a envoyé un nonce différent de celui que nous lui avions demandé d'envoyer maintenant, mais dans une session différente dont l'heure de début diffère de ce nombre de secondes par rapport à la session en cours. N'a de sens que lorsque GIT_PUSH_CERT_NONCE_STATUS indique SLOP. Lire aussi à propos de la variable receive.certNonceSlop dans git-config(1).

Ce crochet est appelé avant que tout nom-référence ne soit mis à jour et avant que toutes les vérifications d'avance rapide ne soient effectuées.

Si le crochet pre-receive se termine avec un état de sortie non nul, aucune mise à jour ne sera effectuée, et les crochets update, post-receive et post-update ne seront pas non plus invoqués. Cela peut être utile pour abandonner rapidement si la mise à jour ne doit pas être prise en charge.

Voir les notes sur l'environnement de quarantaine ci-dessous.

CROCHET UPDATE

Avant que chaque référence ne soit mise à jour, si le fichier $GIT_DIR/hooks/update existe et est exécutable, il est invoqué une fois par référence, avec trois paramètres :

$GIT_DIR/hooks/update nom-référence sha1-ancien sha1-nouveau

Le paramètre nom-référence est relatif à $GIT_DIR ; par exemple pour la tête master c'est "refs/heads/master". Les deux arguments sha1 sont les noms d'objet pour le nom-référence avant et après la mise à jour. Notez que le crochet est appelé avant que le nom-référence ne soit mis à jour, donc soit sha1-ancien est 0{40} (signifiant qu'il n'existe pas encore de telle référence), soit il devrait correspondre à ce qui est enregistré dans nom-référence.

Le crochet devrait se terminer avec un état non nul s'il souhaite refuser la mise à jour de la référence nommée. Sinon, il devrait se terminer avec zéro.

L'exécution réussie (un état de sortie nul) de ce crochet ne garantit pas que la référence sera effectivement mise à jour, c'est seulement un prérequis. En tant que tel, ce n'est pas une bonne idée d'envoyer des notifications (par exemple par e-mail) depuis ce crochet. Envisagez plutôt d'utiliser le crochet post-receive.

CROCHET POST-RECEIVE

Après que toutes les références aient été mises à jour (ou qu'une mise à jour ait été tentée), si une mise à jour de référence a réussi, et si le fichier $GIT_DIR/hooks/post-receive existe et est exécutable, il sera invoqué une fois sans paramètres. L'entrée standard du crochet sera une ligne pour chaque référence mise à jour avec succès :

sha1-ancien SP sha1-nouveau SP nom-référence LF

La valeur de nom-référence est relative à $GIT_DIR ; par exemple pour la tête master c'est "refs/heads/master". Les deux valeurs sha1 avant chaque nom-référence sont les noms d'objet pour le nom-référence avant et après la mise à jour. Les références qui ont été créées auront sha1-ancien égal à 0{40}, tandis que les références qui ont été supprimées auront sha1-nouveau égal à 0{40}, sinon sha1-ancien et sha1-nouveau devraient être des objets valides dans le dépôt.

Les variables d'environnement GIT_PUSH_CERT* peuvent être inspectées, tout comme dans le crochet pre-receive après l'acceptation d'un push signé.

En utilisant ce crochet, il est facile de générer des courriels décrivant les mises à jour du dépôt. NOM


git-receive-pack - Reçoit des paquets Git d'une autre source






SYNTAXE


git receive-pack <directory>
git receive-pack --stateless-rpc <directory>
git receive-pack --stateless-rpc-stdin <directory>






DESCRIPTION


Lit les objets et les références envoyés depuis git-send-pack
    (ou une implémentation compatible) et met à jour le référentiel local en
    conséquence. Ce programme est généralement utilisé par le démon git-daemon(1), ou sur une connexion SSH.


Le répertoire spécifié est celui où le référentiel Git est stocké.




OPTIONS


--stateless-rpc, --stateless-rpc-stdin


Ces options sont utilisées pour implémenter le protocole RPC sans
    état Git, généralement sur HTTP(S). Elles ne doivent pas être utilisées dans
    les scénarios SSH ou de démon.








HOOKS


Avant que git-receive-pack ne mette à jour une référence, il
    exécute un script de hook receive-pack (ou pre-receive). Après
    que toutes les références ont été mises à jour, il exécute un script de hook
    post-receive.




PRE-RECEIVE HOOK


Le hook pre-receive est exécuté avant que tout objet ou
    référence ne soit mis à jour. Il reçoit l'entrée standard sous la forme
    d'une liste de lignes, chacune décrivant une mise à jour de référence
    proposée :




<old-sha1> <new-sha1> <ref-name>




Les anciens et nouveaux SHA-1 sont des chaînes de 40 caractères
    hexadécimaux. Une valeur de 0 représente un SHA-1 nul (par exemple, lors de la
    création ou de la suppression d'une branche).


Le hook pre-receive peut être utilisé pour empêcher certaines
    mises à jour d'être acceptées. Par exemple, vous pourriez vouloir refuser
    toute poussée qui supprime des commits (c'est-à-dire, lorsque
    <old-sha1> est une chaîne non nulle et <new-sha1> est 0, ou
    lorsque <new-sha1> est un ancêtre de <old-sha1>).


Si le hook pre-receive se termine avec un code de sortie
    non nul, aucune référence n'est mise à jour et git-receive-pack se
    termine sans succès. La sortie standard du hook est ignorée.


Il est possible que le hook pre-receive ne reçoive pas
    l'ancien SHA-1 de la référence, car la référence pourrait ne pas encore
    exister (par exemple, lors de la création d'une nouvelle branche). Dans ce
    cas, l'ancien SHA-1 sera affiché comme une chaîne de zéros.


La valeur de l'environnement GIT_DIR est définie sur le
    référentiel de destination.


Les objets recus sont d'abord stockés dans un répertoire
    temporaire (quarantaine) avant que le hook pre-receive ne soit
    exécuté. Si le hook réussit, les objets sont déplacés vers le répertoire
    principal des objets et les références sont mises à jour. Si le hook échoue,
    les objets du répertoire temporaire sont supprimés.


Les mises à jour de référence effectuées par le hook
    pre-receive lui-même ne sont pas autorisées et seront automatiquement
    rejetées.






UPDATE HOOK


Pour chaque référence qui est mise à jour, un hook
    update est appelé. Il reçoit le nom de la référence et le SHA-1 de
    l'ancienne et de la nouvelle référence sur la ligne de commande.




git update   




Ceci est une copie du hook pre-receive pour chaque référence.
    Il est appelé après que le hook pre-receive a réussi, mais avant que
    les références ne soient écrites sur le disque. Il est possible de modifier
    le SHA-1 de la nouvelle référence sur la ligne de commande, ce qui permet de
    changer la cible de la mise à jour.


Si le hook update se termine avec un code de sortie non
    nul, la mise à jour de cette référence spécifique échoue, mais les autres
    mises à jour des références se poursuivent.


Le hook update est rarement utilisé, car le hook
    pre-receive peut examiner toutes les mises à jour proposées en une seule
    fois et les rejeter toutes si nécessaire.






POST-RECEIVE HOOK


Après que toutes les mises à jour ont été effectuées, le hook
    post-receive est exécuté. Il reçoit l'entrée standard sous la forme
    d'une liste de lignes, chacune décrivant une mise à jour de référence qui a
    eu lieu :




<old-sha1> <new-sha1> <ref-name>




Le hook post-receive ne peut pas être utilisé pour empêcher
    les mises à jour de référence. Il est généralement utilisé pour des tâches
    post-mise à jour, comme la notification de systèmes externes ou la mise à jour
    d'index de recherche.


L'exit code de ce hook est ignoré.


Les hooks de ce type sont généralement nommés d'après le nom
    du référentiel qu'ils affectent. Par exemple, si le référentiel est
    stocké dans /srv/git/project.git, le hook pourrait être
    /srv/git/project.git/hooks/post-receive.


L'exemple suivant envoie par courrier électronique une liste des
    commits poussés pour chaque référence mise à jour :




#!/bin/sh
#
# post-receive hook to email commit list for each updated ref.
#

while read oldrev newrev refname
do
        # Only report on branches that were actually updated
        if [ "$oldrev" = "$newrev" ]; then
                continue
        fi

        # Determine if it's a new branch or an existing one
        if [ zeros = "$oldrev" ]; then
                oval="new ref"
                nval="$newrev"
                echo "New branch '$refname' created."
        else
                oval="$oldrev"
                nval="$newrev"
                echo "Changes to branch '$refname':"
        fi

        # List commits on the branch, unless it's a new branch
        if [ "new ref" = "$oval" ]; then
                echo "New commits:"
                git rev-list --pretty "$nval"
        else
                echo "New commits:"
                git rev-list --pretty "$nval" "^$oval"
        fi |
        mail -s "Changes to ref $ref" commit-list@mydomain
done
# log signed push certificate, if any
if test -n "${GIT_PUSH_CERT-}" && test ${GIT_PUSH_CERT_STATUS} = G
then
        (
                echo expected nonce is ${GIT_PUSH_NONCE}
                git cat-file blob ${GIT_PUSH_CERT}
        ) | mail -s "push certificate from $GIT_PUSH_CERT_SIGNER" push-log@mydomain
fi
exit 0




L'exit code de cette invocation de hook est ignoré, cependant un
    code de sortie non nul générera un message d'erreur.


Notez qu'il est possible que refname n'ait pas de sha1-new
    lorsque ce hook s'exécute. Cela peut facilement se produire si un autre
    utilisateur modifie la référence après qu'elle a été mise à jour par
    git-receive-pack, mais avant que le hook n'ait pu l'évaluer. Il
    est recommandé que les hooks s'appuient sur sha1-new plutôt que sur la
    valeur actuelle de refname.






POST-UPDATE HOOK


Après tout autre traitement, si au moins une référence a été mise à
    jour, et si le fichier $GIT_DIR/hooks/post-update existe et est exécutable,
    alors post-update sera appelé avec la liste des références qui ont été
    mises à jour. Ceci peut être utilisé pour implémenter des tâches de nettoyage
    à l'échelle du référentiel.


L'exit code de cette invocation de hook est ignoré ; la seule
    chose qu'il reste à git-receive-pack à faire à ce stade est de se
    terminer de toute façon.


Ce hook peut être utilisé, par exemple, pour exécuter
    git update-server-info si le référentiel est empaqueté et est servi via
    un transport "dumb".




#!/bin/sh
exec git update-server-info










QUARANTINE ENVIRONMENT


Lorsque receive-pack prend des objets, ils sont placés dans un
    répertoire temporaire "quarantaine" dans le répertoire
    $GIT_DIR/objects et ne sont migrés dans le magasin d'objets principal
    qu'après que le hook pre-receive a terminé. Si la poussée échoue
    avant cela, le répertoire temporaire est entièrement supprimé.


Cela a quelques effets visibles par l'utilisateur et des
    caveats :


 1. Les poussées qui échouent en raison de problèmes
    avec le paquet entrant, d'objets manquants, ou à cause du hook
    pre-receive ne laisseront aucune donnée sur disque. C'est généralement
    utile pour éviter que les poussées échouées répétées ne remplissent votre
    disque, mais cela peut rendre le débogage plus difficile.


 2. Tout objet créé par le hook pre-receive
    sera créé dans le répertoire de quarantaine (et ne sera migré que s'il
    réussit).


 3. Le hook pre-receive NE DOIT PAS mettre
    à jour de références pour pointer vers des objets en quarantaine. D'autres
    programmes accédant au référentiel ne pourront pas voir les objets (et si le
    hook pre-receive échoue, ces références deviendraient corrompues). Par
    sécurité, toutes les mises à jour de référence depuis
    pre-receive sont automatiquement rejetées.
