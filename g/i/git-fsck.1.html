OPTION

S

<objet

>
Un objet à traiter comme la tête d'une trace d'inaccessibilité.

Si aucun objet n'est donné, git fsck utilise par défaut le fichier d'index, toutes les références SHA-1 dans le espace de noms refs, et tous les reflogs (

sauf si --no-reflogs est
spécifié) comme têtes.

--unreachabl

e
Affiche les objets qui existent mais qui ne sont pas accessibles depuis aucun des nœuds de
référence.

--dangling,

--no-dangling
Affiche les objets qui existent mais qui ne sont jamais utilisés directement (par défaut). --no-dangling peut être utilisé pour omettre cette information de la
sortie.

--roo

t
Signale les nœuds
racines.

--tag

s
Signale les étiquettes (tags)
.

--cach

e
Considère tout objet enregistré dans l'index également comme un nœud tête pour une trace d'inaccessibilité
.

--no-reflog

s
Ne considère pas comme accessibles les commits qui ne sont référencés que par une entrée dans un reflog. Cette option est destinée uniquement à rechercher des commits qui se trouvaient autrefois dans une référence mais qui n'y sont plus, mais qui sont toujours dans le reflog
correspondant.

--ful

l
Vérifie non seulement les objets dans GIT_OBJECT_DIRECTORY ($GIT_DIR/objects), mais aussi ceux trouvés dans les pools d'objets alternatifs listés dans GIT_ALTERNATE_OBJECT_DIRECTORIES ou $GIT_DIR/objects/info/alternates, et dans les archives Git compressées trouvées dans $GIT_DIR/objects/pack et les sous-répertoires de paquets correspondants dans les pools d'objets alternatifs. C'est maintenant le comportement par défaut ; vous pouvez le désactiver avec
--no-full.

--connectivity-onl

y
Vérifie uniquement la connectivité des objets accessibles, en s'assurant que tout objet référencé par une étiquette, un commit ou un arbre accessible est présent. Cela accélère l'opération en évitant de lire complètement les blobs (bien qu'il vérifie toujours que les blobs référencés existent). Cela détectera la corruption dans les commits et les arbres, mais n'effectuera aucune vérification sémantique (par ex., pour les erreurs de format). La corruption des objets blob ne sera pas détectée du tout.

Les étiquettes, commits et arbres inaccessibles seront également parcourus pour trouver les extrémités des segments suspendus de l'historique. Utilisez --no-dangling si vous ne vous souciez pas de cet

te sortie et souhaite
z l'accélérer davantage.

--stric

t
Active une vérification plus stricte, notamment pour détecter un mode de fichier enregistré avec le bit g+w défini, qui a été créé par de plus anciennes versions de Git. Les dépôts existants, y compris le noyau Linux, Git lui-même et les dépôts sparses, contiennent des anciens objets qui déclenchent cette vérification, mais il est recommandé de vérifier les nouveaux projets avec ce
drapeau.

--verbos

e
Être
bavard.

--lost-foun

d
Écrit les objets suspendus dans .git/lost-found/commit/ ou .git/lost-found/other/, selon le type. Si l'objet est un blob, le contenu est écrit dans le fichier, plutôt que son nom
d'objet.

--name-object

s
Lors de l'affichage des noms des objets accessibles, en plus du SHA-1, affiche également un nom qui décrit comment ils sont accessibles, compatible avec git-rev-parse(1), par ex. HEAD@{1234567890}~25^2:
src/.

--progress,

--no-progress
L'état de progression est rapporté sur le flux d'erreur standard par défaut lorsqu'il est attaché à un terminal, sauf si --no-progress ou --verbose est spécifié. --progress force l'état de progression même si le flux d'erreur standard n'est pas dirigé vers un
terminal.

--references,

--no-references
Contrôle s'il faut vérifier la cohérence de la base de données des références via git refs verify. Voir git-refs(1) pour les détails. Le comportement par dé
faut est de vérifier la base
de données des références.

fsck.

<msg-id>
Lors de fsck, Git peut trouver des problèmes avec des données héritées qui ne seraient pas générées par les versions actuelles de git et qui ne seraient pas envoyées sur le réseau si transfer.fsckObjects était défini. Cette fonctionnalité est destinée à prendre en charge le travail avec des dépôts hérités contenant de telles données.

Définir fsck.<msg-id> sera pris en compte par git-fsck(1), mais pour accepter les pushes de telles données, définissez receive.fsck.<msg-id> à la place, ou pour cloner ou récupérer ces données, définissez fetch.fsck.<msg-i

d>.

Le reste de la documentation discute de fsck.* par souci de concision, mais la même chose s'applique aux variables correspondantes receive.fsck.* et fetch.fsck.

*.

Contrairement à des variables comme color.ui et core.editor, les variables receive.fsck.<msg-id> et fetch.fsck.<msg-id> ne reviendront pas à la configuration fsck.<msg-id> si elles ne sont pas définies. Pour configurer uniformément les mêmes paramètres fsck dans différentes circonstances, les trois doivent être définies aux mêmes

valeurs.

Lorsque fsck.<msg-id> est défini, les erreurs peuvent être converties en avertissements et vice versa en configurant le paramètre fsck.<msg-id> où <msg-id> est l'identifiant de message fsck et la valeur est l'une des suivantes : error, warn ou ignore. Par commodité, fsck préfixe l'erreur/l'avertissement avec l'identifiant de message, par ex. "missingEmail: invalid author/committer line - missing email" signifie que définir fsck.missingEmail = ignore cachera ce

problème.

En général, il est préférable d'énumérer les objets existants ayant des problèmes avec fsck.skipList, plutôt que de lister le type de dommages que ces objets problématiques partagent pour les ignorer, car faire ce dernier permettra à de nouveaux cas des mêmes dommages de passer

inaperçus.

Définir une valeur fsck.<msg-id> inconnue fera échouer fsck, mais faire de même pour receive.fsck.<msg-id> et fetch.fsck.<msg-id> ne fera qu'afficher un avertissement de

git.

Voir la section Fsck Messages de git-fsck(1) pour les valeurs prises en charge de <msg

-id
>.

fsck.

skipList
Le chemin vers une liste de noms d'objets (c.-à-d. un SHA-1 non abrégé par ligne) qui sont connus pour être cassés de manière non fatale et doivent être ignorés. Sur les versions de Git 2.20 et ultérieures, les commentaires (#), les lignes vides et tout espace en début et en fin sont ignorés. Tout autre contenu qu'un SHA-1 par ligne provoquera une erreur sur les versions plus anciennes.

Cette fonctionnalité est utile lorsqu'un projet établi doit être accepté malgré des commits précoces contenant des erreurs qui peuvent être ignorées en toute sécurité, comme des adresses e-mail de committeur invalides. Remarque : les objets corrompus ne peuvent pas être ignorés avec ce

paramètre.

Comme fsck.<msg-id>, cette variable a des variantes correspondantes receive.fsck.skipList et fetch.fsck.sk

ipList.

Contrairement à des variables comme color.ui et core.editor, les variables receive.fsck.skipList et fetch.fsck.skipList ne reviendront pas à la configuration fsck.skipList si elles ne sont pas définies. Pour configurer uniformément les mêmes paramètres fsck dans différentes circonstances, les trois doivent être définies aux mêmes

valeurs.

Les anciennes versions de Git (avant 2.20) documentaient que la liste des noms d'objets devait être triée. Ce n'a jamais été une exigence ; les noms d'objets pouvaient

apparaître dans n'importe quel ordre, mais lors de la lecture de la liste, nous suivions si la liste était triée aux fins d'une implémentation de recherche binaire in
terne, qui pouvait économiser du travail avec une liste déjà triée. À moins que vous n'ayez une liste énorme, il n'y avait aucune raison de prendre la peine de trier l
a liste à l'avance. Après la version 2.20 de Git, une implémentation de hachage est utilisée à la place, il n'y a donc plus de raison de trier la liste à l'avance.

DISCUSSIO

N git-fsck teste la validité SHA-1 et la cohérence générale des objets, et effectue un suivi complet de l'accessibilité résultante et de tout le reste. Il affiche toute corruption qu'il trouve (objets manquants ou corrompus), et si vous utilisez l'option --unreachable, il affichera également les objets qui existent mais qui ne sont accessibles depuis aucun des nœuds d'en-tête spécifiés (ou l'ensemble par défaut, comme mentionné ci-dessus)

.

Tout objet corrompu devra être retrouvé dans des sauvegardes ou d'autres archives (c'est-à-dire, vous pouvez simplement les supprimer et effectuer un rsync avec un autre site dans l'espoir que quelqu'un d'autre ait l'objet que vous avez corrompu)

.

Si core.commitGraph est vrai, le fichier commit-graph sera également inspecté à l'aide de git commit-graph verify. Voir git-commit

-grap
h(1).

EXTRAITS

unreachable <type>

<object>
L'objet <type> <object> n'est en fait référencé directement ou indirectement dans aucun des arbres ou commits vus. Cela peut signifier qu'il y a un autre nœud racine que vous ne spécifiez pas ou que l'arbre est corrompu. Si vous n'avez pas manqué un nœud racine, vous pouvez aussi bien supprimer les nœuds inaccessibles car ils ne peuvent pas être
utilisés.

<object>
L'objet <type> <object> est référencé mais n'est pas présent dans la base de
données.

dangling <type>

<object>
L'objet <type> <object> est présent dans la base de données mais n'est jamais utilisé directement. Un commit orphelin pourrait être un nœud
racine.

<object>
La base de données contient un objet dont le hash ne corr
espond pas à la valeur de l'objet dans la base de données
. Cela indique un problème grave d'intégrité des données.
