NOM

git-rerere - Réutiliser les résolutions enregistrées des fusions conflictuelles

SYNOPSIS

git rerere [clear | forget <pathspec>... | diff | status | remaining | gc]

DESCRIPTION

Dans un flux de travail employant des branches thématiques relativement durables, le développeur doit parfois résoudre les mêmes conflits encore et encore jusqu'à ce que les branches thématiques soient terminées (soit fusionnées dans la branche "release", soit envoyées et acceptées en amont).

Cette commande aide le développeur dans ce processus en enregistrant les résultats des fusions automatiques conflictuelles et les résultats de résolution manuelle correspondants lors de la fusion manuelle initiale, et en appliquant les résolutions manuelles précédemment enregistrées à leurs résultats de fusion automatique correspondants.


Note

Vous devez définir la variable de configuration rerere.enabled afin d'activer cette commande.

COMMANDES

Normalement, git rerere est exécuté sans arguments ni intervention de l'utilisateur. Cependant, il possède plusieurs commandes qui lui permettent d'interagir avec son état de travail.

clear

Réinitialise les métadonnées utilisées par rerere si une résolution de fusion doit être abandonnée. Appeler git am [--skip|--abort] ou git rebase [--skip|--abort] invoquera automatiquement cette commande.

forget <pathspec>

Réinitialise les résolutions de conflit que rerere a enregistrées pour le conflit actuel dans <pathspec>.

diff

Affiche les différences pour l'état actuel de la résolution. Il est utile pour suivre ce qui a changé pendant que l'utilisateur résout les conflits. Des arguments supplémentaires sont directement transmis à la commande diff du système installée dans PATH.

status

Imprime les chemins avec des conflits dont la résolution de fusion sera enregistrée par rerere.

remaining

Imprime les chemins avec des conflits qui n'ont pas été résolus automatiquement par rerere. Cela inclut les chemins dont les résolutions ne peuvent pas être suivies par rerere, comme les sous-modules conflictuels.

gc

Élague les enregistrements des fusions conflictuelles qui ont eu lieu il y a longtemps. Par défaut, les conflits non résolus plus anciens que 15 jours et les conflits résolus plus anciens que 60 jours sont élagués. Ces valeurs par défaut sont contrôlées respectivement via les variables de configuration gc.rerereUnresolved et gc.rerereResolved.

DISCUSSION

Lorsque votre branche thématique modifie une zone qui se chevauche et que votre branche maître (ou amont) a touchée depuis que votre branche thématique s'en est séparée, vous pourriez vouloir la tester avec la dernière version du maître, même avant que votre branche thématique ne soit prête à être envoyée en amont :

              o---*---o topic
             /
    o---o---o---*---o---o master

Pour un tel test, vous devez fusionner le maître et le sujet d'une manière ou d'une autre. Une façon de le faire est de tirer le maître dans la branche thématique :

        $ git switch topic
        $ git merge master
              o---*---o---+ topic
             /           /
    o---o---o---*---o---o master

Les commits marqués de * touchent la même zone dans le même fichier ; vous devez résoudre les conflits lors de la création du commit marqué de +. Ensuite, vous pouvez tester le résultat pour vous assurer que votre travail en cours fonctionne toujours avec ce qui se trouve dans le dernier maître.

Après cette fusion de test, il y a deux façons de continuer votre travail sur le sujet. Le plus simple est de construire sur le commit de fusion de test +, et lorsque votre travail dans la branche thématique est enfin prêt, fusionnez la branche thématique dans le maître, et/ou demandez à l'amont de tirer de vous. À ce moment-là, cependant, le maître ou l'amont pourraient avoir été avancés depuis la fusion de test +, auquel cas le graphe de commit final ressemblerait à ceci :

        $ git switch topic
        $ git merge master
        $ ... travail sur les branches topic et master
        $ git switch master
        $ git merge topic
              o---*---o---+---o---o topic
             /           /         \
    o---o---o---*---o---o---o---o---+ master

Cependant, lorsque votre branche thématique est de longue durée, elle finirait par avoir de nombreuses telles fusions de "test du maître" dessus, ce qui encombrerait inutilement l'historique de développement. Les lecteurs de la liste de diffusion du noyau Linux se souviendront peut-être que Linus s'est plaint de ces fusions de test trop fréquentes lorsqu'un mainteneur de sous-système a demandé de tirer d'une branche pleine de "fusions inutiles".

Alternativement, pour garder la branche thématique exempte de fusions de test, vous pourriez supprimer la fusion de test et continuer à construire sur le sommet avant la fusion de test :

        $ git switch topic
        $ git merge master
        $ git reset --hard HEAD^ ;# remonter la fusion de test
        $ ... travail sur les branches topic et master
        $ git switch master
        $ git merge topic
              o---*---o-------o---o topic
             /                     \
    o---o---o---*---o---o---o---o---+ master

Cela ne laisserait qu'un seul commit de fusion lorsque votre branche thématique sera enfin prête et fusionnée dans la branche maître. Cette fusion vous obligerait à résoudre le conflit, introduit par les commits marqués de *. Cependant, ce conflit est souvent le même conflit que vous avez résolu lorsque vous avez créé la fusion de test que vous avez supprimée. git rerere vous aide à résoudre cette fusion finale conflictuelle en utilisant les informations de votre résolution manuelle antérieure.

L'exécution de la commande git rerere immédiatement après une fusion automatique conflictuelle enregistre les fichiers de l'arbre de travail conflictuels, avec les marqueurs de conflit habituels <<<<<<<, =======, et >>>>>>> dedans. Plus tard, après avoir terminé de résoudre les conflits, l'exécution de git rerere à nouveau enregistrera l'état résolu de ces fichiers. Supposons que vous ayez fait cela lors de la création de la fusion de test du maître dans la branche thématique.

La prochaine fois, après avoir vu la même fusion automatique conflictuelle, l'exécution de git rerere effectuera une fusion à trois voies entre la fusion automatique conflictuelle antérieure, la résolution manuelle antérieure et la fusion automatique conflictuelle actuelle. Si cette fusion à trois voies se résout proprement, le résultat est écrit dans votre fichier de l'arbre de travail, vous n'avez donc pas à la résoudre manuellement. Notez que git rerere laisse le fichier d'index inchangé, vous devez donc toujours effectuer les vérifications finales avec git diff (ou git diff -c) et git add lorsque vous êtes satisfait.

Par souci de commodité, git merge invoque automatiquement git rerere à la sortie avec une fusion automatique échouée et git rerere enregistre la résolution manuelle lorsqu'il s'agit d'un nouveau conflit, ou réutilise la résolution manuelle précédente lorsqu'il ne s'agit pas d'un nouveau conflit. git commit invoque également git rerere lors de la validation d'un résultat de fusion. Ce que cela signifie, c'est que vous n'avez rien de spécial à faire vous-même (en plus d'activer la variable de configuration rerere.enabled).

Dans notre exemple, lorsque vous effectuez la fusion de test, la résolution manuelle est enregistrée, et elle sera réutilisée lorsque vous effectuerez la fusion réelle plus tard avec le maître et la branche thématique mis à jour, tant que la résolution enregistrée est toujours applicable.

Les informations que git rerere enregistre sont également utilisées lors de l'exécution de git rebase. Après avoir supprimé la fusion de test et continué le développement sur la branche thématique :

              o---*---o-------o---o topic
             /
    o---o---o---*---o---o---o---o   master
        $ git rebase master topic
                                  o---*---o-------o---o topic
                                 /
    o---o---o---*---o---o---o---o   master

vous pourriez exécuter git rebase master topic, pour vous mettre à jour avant que votre sujet ne soit prêt à être envoyé en amont. Cela entraînerait le retour à une fusion à trois voies, et cela entrerait en conflit de la même manière que la fusion de test que vous avez résolue précédemment. git rerere sera exécuté par git rebase pour vous aider à résoudre ce conflit.

[NOTE] git rerere s'appuie sur les marqueurs de conflit dans le fichier pour détecter le conflit. Si le fichier contient déjà des lignes qui ressemblent aux lignes avec des marqueurs de conflit, git rerere peut ne pas réussir à enregistrer une résolution de conflit. Pour contourner ce problème, le paramètre conflict-marker-size dans gitattributes(5) peut être utilisé.

NOM

git - Système de contrôle de version distribué

SYNOPSIS

git [<options>] <commande> [<options>] [<arguments>]

DESCRIPTION

Git est un système de contrôle de version distribué, gratuit et open-source, conçu pour gérer tous types de projets, qu'ils soient petits ou très grands, avec une rapidité et une efficacité exceptionnelles.

Il excelle dans les opérations qui nécessitent des branchements et des fusions rapides, et permet de suivre les modifications apportées à un ensemble de fichiers au fil du temps.

COMMANDES

Git dispose d'un grand nombre de commandes pour gérer les dépôts, les commits, les branches, les fusions, etc.

Quelques commandes courantes incluent :

  • git init : Initialise un dépôt Git vide.
  • git clone : Clone un dépôt existant.
  • git add : Ajoute des modifications à l'index.
  • git commit : Enregistre les modifications dans le dépôt.
  • git status : Affiche l'état de l'espace de travail et de l'index.
  • git diff : Affiche les différences entre les commits, les branches, l'index, etc.
  • git log : Affiche l'historique des commits.
  • git branch : Liste, crée ou supprime des branches.
  • git merge : Fusionne une ou plusieurs branches dans la branche actuelle.
  • git pull : Récupère les modifications d'un dépôt distant et les fusionne.
  • git push : Envoie les commits locaux vers un dépôt distant.

Pour une liste complète des commandes et de leurs options, consultez la documentation de Git.

DISCUSSION

Git est l'un des systèmes de contrôle de version les plus populaires et les plus utilisés aujourd'hui. Sa flexibilité et sa puissance en font un outil indispensable pour le développement logiciel.
