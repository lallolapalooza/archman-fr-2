DESCRIPTIO

N

Affiche les changements pour les paires de fichiers fournies sur stdin. L'entrée de cette commande doit être au format de sortie brute terminé par NUL tel que généré par des commandes comme git diff-tree -z -r --raw. Par défaut, les diffs générés sont calculés et affichés au format patch lorsque stdin se

ferme.

Un octet NUL unique peut être écrit sur stdin entre les lignes d'entrée brutes pour calculer les diffs des paires de fichiers jusqu'à ce point au lieu d'attendre la fermeture de stdin. Un octet NUL est également écrit dans la sortie pour délimiter ces lots de

diffs.

L'utilisation de cette commande permet de diviser le pipeline de diff traditionnel en étapes séparées où diff-pairs agit comme la phase de sortie. D'autres commandes, comme diff-tree, peuvent servir de frontend pour calculer le format de diff brut utilisé comme

entrée.

Au lieu de calculer les diffs via git diff-tree -p -M en une seule étape, diff-tree peut calculer les paires de fichiers et les informations de renommage sans les diffs de blobs. Cette sortie peut être transmise à diff-pairs pour générer les diffs de blobs sous-jacents comme dans l'exemple suivant

: 
git diff-tree -z
-r -M $a $b | g
it diff-pairs -z

Calculer le diff de l'arbre à l'avance avec les informations de renommage permet à la sortie de patch de diff-pairs d'être calculée progressivement au cours de plusieurs invocations

potentielles.

Les pathspecs ne sont actuellement pas pris en charge par diff-pairs. La limitation par pathspec doit être effectuée par la commande amont générant les diffs bruts utilisés comme

entrée.

Les objets tree ne sont actuellement pas pris en charge en entrée et sont

rejetés.

Les identifiants d'objets abrégés dans l'entrée de diff-pairs ne sont pas pris en charge. Les identifiants d'objets en sortie peuvent être abrégés à l'aide de l'option --ab

bre

Découpe les changements de réécriture complète en paires de suppression et création. Cela sert à deux objectifs :

Cela affecte la manière dont un changement qui constitue une réécriture totale d'un fichier est présenté, non pas comme une série de suppressions et d'insertions mélangées avec quelques lignes qui se trouvent correspondre textuellement en tant que contexte, mais comme une suppression unique de tout l'ancien contenu suivie d'une insertion unique de tout le nouveau, et le nombre <m> contrôle cet aspect de l'option -B (par défaut 60 %). -B/70% indique que moins de 30 % de l'original doit rester dans le résultat pour que Git le considère comme une réécriture totale (c'est-à-dire que sinon le patch résultant sera une série de suppressions et d'insertions mélangées avec des lignes de contexte)

-M[<n>], --find-renames[=<n>

Détecte les renommages. Si <n> est spécifié, c'est un seuil sur l'indice de similarité (c'est-à-dire le montant des ajouts/suppressions par rapport à la taille du fichier). -l<num

>
Les options -M et -C impliquent certaines étapes préliminaires qui peuvent détecter à bon marché des sous-ensembles de renommages/copies, suivies d'une partie de repli exhaustive qui compare toutes les destinations non appariées restantes à toutes les sources pertinentes. (Pour les renommages, seules les sources non appariées restantes sont pertinentes ; pour les copies, toutes les sources originales sont pertinentes.) Pour N sources et destinations, cette vérification exhaustive est en O(N^2). Cette option empêche la partie exhaustive de la détection de renommage/copie de s'exécuter si le nombre de fichiers source/destination impliqués dépasse le nombre spécifié. Par défaut, c'est diff.renameLimit. Notez qu'une valeur de 0 est traitée comme
illimitée.

--diff-filter=[(A|C|D|M|R|T|U|X|B)...[*]

]

Toute combinaison des caractères de filtre (y compris aucun) peut être utilisée. De plus, ces lettres majuscules peuvent être mises en minuscules pour exclure. Par exemple, --diff-filter=ad exclut les chemins ajoutés et

supprimés.

Notez que tous les diffs ne peuvent pas présenter tous les types
