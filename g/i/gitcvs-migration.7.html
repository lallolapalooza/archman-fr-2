DESCRIPTIO

N

Git diffère de CVS en ce que chaque arbre de travail contient un dépôt avec une copie complète de l'historique du projet, et aucun dépôt n'est intrinsèquement plus important qu'un autre. Cependant, vous pouvez émuler le modèle CVS en désignant un dépôt partagé unique avec lequel les gens peuvent se synchroniser ; ce document explique comment faire

cela.

Une certaine familiarité de base avec Git est requise. Avoir parcouru gittutorial(7) et gitglossary(7) devr

ait être
suffisant.

Dans la commande git push ci-dessus, nous spécifions le nom de la branche distante à mettre à jour (master). Si nous l'omettons, git push essaie de mettre à jour toutes les branches dans le dépôt distant qui ont le même nom qu'une branche dans le dépôt local. CONFIGURATION D'UN DÉPÔT

PARTAGÉ

Nous supposons que vous avez déjà créé un dépôt Git pour votre projet, possiblement créé à partir de zéro ou d'une archive tar (voir gittutorial(7)), ou importé depuis un dépôt CVS existant (voir la section suivante)

.

Supposons que votre dépôt existant soit à /home/alice/myproject. Créez un nouveau dépôt « nu » (un dépôt sans arbre de travail) et récupérez votre projet dedans

: 
$ mkdir /pub/my-repo.git
$ cd /pub/my-repo.
git $ git --bare init --shared $ git --bar
e fetch /home/alice/myproject master:master

Ensuite, donnez à chaque membre de l'équipe un accès en lecture/écriture à ce dépôt. Une façon simple de faire cela est de donner à tous les membres de l'équipe un accès ssh à la machine où le dépôt est hébergé. Si vous ne voulez pas leur donner un shell complet sur la machine, il existe un shell restreint qui ne permet aux utilisateurs que de faire des pushes et pulls Git ; voir git-shell

(1).

Mettez tous les committers dans le même groupe, et rendez le dépôt inscriptible par ce groupe

: 
$ chgrp -R
$group /pub/
my-repo.git

Assurez-vous que les committers ont un umask d'au plus 027,

de sorte que les répertoires qu'ils créent soient inscr
iptibles et parcourables par les autres membres du groupe.

IMPORTATION D'UNE ARCHIVE

CVS

Note

Ces instructions utilisent le script git-cvsimport qui est livré avec git, mais d'autres importateurs peuvent fournir de meilleurs résultats. Voir la note dans git-cvsimport(1) pou

r d'autre
s options.

D'abord, installez la version 2.1 ou supérieure de cvsps depuis https://github.com/andreyvit/cvsps et assurez-vous qu'il est dans votre PATH. Puis allez dans un répertoire de travail CVS extrait du projet qui vous intéresse et exécutez git-cvsimport(1)

: 
$ git cvsimpor
t -C <destina
tion> <module>

Cela place une archive Git du module CVS nommé dans le répertoire <destination>, qui sera créé si

nécessaire.

L'importation extrait de CVS chaque révision de chaque fichier. Selon le rapport, cvsimport peut faire en moyenne une vingtaine de révisions par seconde, donc pour un projet de taille moyenne cela ne devrait pas prendre plus de quelques minutes. Les projets plus grands ou les dépôts distants peuvent prendre plus de

temps.

La branche principale est stockée dans la branche Git nommée origin, et les branches CVS supplémentaires sont stockées dans des branches Git avec les mêmes noms. La version la plus récente de la branche principale est aussi laissée extraite sur la branche master, donc vous pouvez commencer à ajouter vos propres changements

immédiatement.

L'importation est incrémentale, donc si vous l'appelez à nouveau le mois prochain, elle récupérera toutes les mises à jour CVS qui ont été faites entre-temps. Pour que cela fonctionne, vous ne devez pas modifier les branches importées ; créez plutôt de nouvelles branches pour vos propres changements, et fusionnez les branches importées au

besoin.

Si vous voulez un dépôt partagé, vous devrez faire un clonage nu du répertoire i

mporté, comme décrit ci-dessus. Traitez ensuite le répertoire importé comme un a
utre clonage de développement aux fins de fusion des importations incrémentales.

GESTION AVANCÉE DES DÉPÔTS

PARTAGÉS

Git vous permet de spécifier des scripts appelés « hooks » à exécuter à certains points. Vous pouvez les utiliser, par exemple, pour envoyer tous les commits du dépôt partagé à une liste de diffusion. Voir githooks

(5).

Vous pouvez imposer des permissions plus fines en utilisant les hooks d'update. Voir Controlling access to bran

ches using upd
ate hooks[1].

MODÈLES DE DÉVELOPPEMENT

ALTERNATIFS

Les utilisateurs de CVS sont habitués à donner à un groupe de développeurs un accès en commit à un dépôt commun. Comme nous l'avons vu, c'est aussi possible avec Git. Cependant, la nature distribuée de Git permet d'autres modèles de développement, et vous voudrez peut-être d'abord considérer si l'un d'eux pourrait mieux convenir à votre

projet.

Par exemple, vous pouvez choisir une seule personne pour maintenir le dépôt public principal du projet. Les autres développeurs clonent alors ce dépôt et chacun travaille dans son propre clonage. Quand ils ont une série de changements dont ils sont satisfaits, ils demandent au mainteneur de tirer depuis la branche contenant les changements. Le mainteneur examine leurs changements et les tire dans le dépôt principal, depuis lequel les autres développeurs tirent au besoin pour rester coordonnés. Le noyau Linux et d'autres projets utilisent des variantes de ce

modèle.

Avec un petit groupe, les développeurs peuvent simpl

ement tirer les changements depuis les dépôts d
es autres sans avoir besoin d'un mainteneur central.
