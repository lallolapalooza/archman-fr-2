SPÉCIFICATION DE CLIENT La spécification de client p4 est maintenue avec la commande p4 client et contient, entre autres champs, une View qui spécifie comment le dépôt est mappé dans le dépôt client. Les commandes clone et sync peuvent consulter la spécification de client lorsque l'option --use-client-spec est donnée ou lorsque la variable useClientSpec est vraie. Après git p4 clone, la variable useClientSpec est automatiquement définie dans le fichier de configuration du dépôt. Cela permet aux futures commandes git p4 submit de fonctionner correctement ; la commande submit ne consulte que la variable et n'a pas d'option de ligne de commande.

La

syntaxe complète d'une vue p4 est documentée dans p4 help views. git p4 ne connaît qu'un sous-ensemble de la syntaxe de vue. Il comprend les correspondances multi-lignes, les superpositions avec +, les exclusions avec - et les guillemets autour des espaces. Parmi les caractères génériques possibles, git p4 ne gère que ... , et seulement lorsqu'ilest à la fin du chemin. git p4 se plaindra s'il rencontre un caractère générique non géré.

Des bugs existent dans l'implémentation des mappages de chevauchement. Si plusieurs chemins de dépôt sont mappés via des superpositions au même emplacement dans le dépôt, git p4 peut en choisir un incorrect. C'est difficile à résoudre sans dédier une spécification client juste pour git p4.

Le nom du client peut être donné à git p4 de plusieurs manières. La variable git-p4.client a la priorité si elle existe. Sinon, les mécanismes normaux de p4 pour déterminer le client sont utilisés : la variable d'environnement P4CLIENT, un fichier référencé par P4CONFIG, ou le nom d'hôte local.

DÉTECTION DES BRANCHES

P4 n'a pas le même concept de branche que Git. Au lieu de cela, p4 organise son contenu sous forme d'arborescence de répertoires, où par convention, différentes branches logiques se trouvent à des emplacements différents dans l'arborescence. La commande p4 branch est utilisée pour maintenir les mappages entre différentes zones de l'arborescence et indiquer le contenu lié. git p4 peut utiliser ces mappages pour déterminer les relations de branche.

Si vous avez un dépôt où toutes les branches d'intérêt existent comme sous-répertoires d'un seul chemin de dépôt, vous pouvez utiliser --detect-branches lors du clonage ou de la synchronisation pour que git p4 trouve automatiquement les sous-répertoires dans p4 et les génère comme branches dans Git.

Par exemple, si la structure du dépôt P4 est :

//depot/main/...
//depot/branch1/...

Et que "p4 branch -o branch1" affiche une ligne View ressemblant à :

//depot/main/... //depot/branch1/...

Alors cette commande git p4 clone :

git p4 clone --detect-branches //depot@all

produit une branche séparée dans refs/remotes/p4/ pour //depot/main, appelée master, et une pour //depot/branch1 appelée depot/branch1.

Cependant, il n'est pas nécessaire de créer des branches dans p4 pour pouvoir les utiliser comme des branches. Comme il est difficile d'inférer les relations de branche automatiquement, un paramètre de configuration Git git-p4.branchList peut être utilisé pour identifier explicitement les relations de branche. C'est une liste de paires "source:destination", comme une simple spécification de branche p4, où "source" et "destination" sont les éléments de chemin dans le dépôt p4. L'exemple ci-dessus reposait sur la présence de la branche p4. Sans branches p4, le même résultat sera obtenu avec :

git init depot
cd depot
git config git-p4.branchList main:branch1
git p4 clone --detect-branches //depot@all .

PERFORMANCE

Le mécanisme fast-import utilisé par git p4 crée un fichier pack pour chaque invocation de git p4 sync. Normalement, le nettoyage de Git (git-gc(1)) compresse automatiquement ces fichiers en moins de fichiers pack, mais une invocation explicite de git repack -adf peut améliorer les performances.

VARIABLES DE CONFIGURATION

Les paramètres de configuration suivants peuvent être utilisés pour modifier le comportement de git p4. Ils se trouvent tous dans la section git-p4.

Variables générales

git-p4.user

Utilisateur spécifié comme option pour toutes les commandes p4, avec -u <user>. La variable d'environnement P4USER peut être utilisée à la place.

git-p4.password

Mot de passe spécifié comme option pour toutes les commandes p4, avec -P <password>. La variable d'environnement P4PASS peut être utilisée à la place.

git-p4.port

Port spécifié comme option pour toutes les commandes p4, avec -p <port>. La variable d'environnement P4PORT peut être utilisée à la place.

git-p4.host

Hôte spécifié comme option pour toutes les commandes p4, avec -h <host>. La variable d'environnement P4HOST peut être utilisée à la place.

git-p4.client

Client spécifié comme option pour toutes les commandes p4, avec -c <client>, y compris la spécification client.

git-p4.retries

Spécifie le nombre de tentatives pour réexécuter une commande p4 (notamment, p4 sync) si le réseau expire. La valeur par défaut est 3. Définissez la valeur à 0 pour désactiver les tentatives ou si votre version de p4 ne prend pas en charge les tentatives (avant 2012.2).

Variables de clonage et de synchronisation

git-p4.syncFromOrigin

Étant donné que l'importation de commits à partir d'autres dépôts Git est beaucoup plus rapide que leur importation à partir de p4, un mécanisme existe pour trouver les changements p4 d'abord dans les remotes Git. Si des branches existent sous refs/remote/origin/p4, elles seront récupérées et utilisées lors de la synchronisation depuis p4. Cette variable peut être définie sur false pour désactiver ce comportement.

git-p4.branchUser

Une phase de détection de branche consiste à examiner les branches p4 pour trouver de nouvelles branches à importer. Par défaut, toutes les branches sont inspectées. Cette option limite la recherche aux seules branches appartenant à l'utilisateur spécifié dans la variable.

git-p4.branchList

Liste des branches à importer lorsque la détection de branche est activée. Chaque entrée doit être une paire de noms de branche séparés par un deux-points (:). Cet exemple déclare que branchA et branchB ont été créées à partir de main : 
git config       git-p4.branchList main:branchA
git config --add git-p4.branchList main:branchB

git-p4.ignoredP4Labels

Liste des étiquettes p4 à ignorer. Ceci est construit automatiquement au fur et à mesure que des étiquettes non importables sont découvertes.

git-p4.importLabels

Importe les étiquettes p4 dans git, comme avec --import-labels.

git-p4.labelImportRegexp

Seules les étiquettes p4 correspondant à cette expression régulière seront importées. La valeur par défaut est [a-zA-Z0-9_\-.]+$.

git-p4.useClientSpec

Spécifie que la spécification client p4 doit être utilisée pour identifier les chemins de dépôt p4 d'intérêt. Ceci est équivalent à spécifier l'option --use-client-spec. Voir la section "CLIENT SPEC" ci-dessus. Cette variable est booléenne, pas le nom d'un client p4.

git-p4.pathEncoding

Perforce conserve le codage d'un chemin tel qu'il est donné par le système d'exploitation d'origine. Git attend des chemins codés en UTF-8. Utilisez cette configuration pour indiquer à git-p4 quel codage Perforce a utilisé pour les chemins. Ce codage est utilisé pour transcoder les chemins en UTF-8. Par exemple, Perforce sous Windows utilise souvent "cp1252" pour coder les noms de chemin. Si cette option est transmise à une demande de clonage p4, elle est conservée dans le nouveau dépôt git résultant.

git-p4.metadataDecodingStrategy

Perforce conserve le codage des descriptions de changelists et des noms complets des utilisateurs tels qu'ils sont stockés par le client sur un système d'exploitation donné. Le client p4 utilise le codage local du système d'exploitation, de sorte que différents utilisateurs peuvent finir par stocker différentes descriptions de changelists ou noms complets d'utilisateurs dans différents codages, dans le même dépôt. Git tolère les codages incohérents/incorrects dans les messages de commit et les noms d'auteur, mais s'attend à ce qu'ils soient spécifiés en utf-8. git-p4 peut utiliser trois stratégies de décodage différentes pour gérer l'incertitude de codage dans Perforce : passthrough transmet simplement les octets d'origine de Perforce à git, créant des données utilisables mais mal codées lorsque les données Perforce ne sont pas encodées en utf-8. strict s'attend à ce que les données Perforce soient encodées en utf-8 et échoue à importer lorsque ce n'est pas le cas. fallback tente d'interpréter les données comme utf-8, et sinon se rabat sur un codage secondaire - par défaut le codage windows courant cp-1252 - avec les octets de plage supérieure échappés si le décodage avec le codage de secours échoue également. Sous python2, la stratégie par défaut est passthrough pour des raisons historiques, et sous python3, la valeur par défaut est fallback. Lorsque strict est sélectionné et que le décodage échoue, le message d'erreur proposera de modifier ce paramètre de configuration comme solution de contournement. Si cette option est transmise à une demande de clonage p4, elle est conservée dans le nouveau dépôt git résultant.

git-p4.metadataFallbackEncoding

Spécifie le codage de secours à utiliser lors du décodage des noms d'auteurs et des descriptions de changelists Perforce en utilisant la stratégie fallback (voir git-p4.metadataDecodingStrategy). Le codage de secours ne sera utilisé que lorsque le décodage en utf-8 échoue. Cette option est par défaut cp1252, un codage windows courant. Si cette option est transmise à une demande de clonage p4, elle est conservée dans le nouveau dépôt git résultant.

git-p4.largeFileSystem

Spécifie le système utilisé pour les fichiers volumineux (binaires). Veuillez noter que les systèmes de fichiers volumineux ne prennent pas en charge la commande git p4 submit. Seul Git LFS est implémenté pour le moment (voir https://git-lfs.github.com/ pour plus d'informations). Téléchargez et installez l'extension de ligne de commande Git LFS pour utiliser cette option et configurez-la comme suit : 
git config       git-p4.largeFileSystem GitLFS

git-p4.largeFileExtensions

Tous les fichiers correspondant à une extension de fichier dans la liste seront traités par le système de fichiers volumineux. Ne préfixez pas les extensions avec ..

git-p4.largeFileThreshold

Tous les fichiers dont la taille non compressée dépasse le seuil seront traités par le système de fichiers volumineux. Par défaut, le seuil est défini en octets. Ajoutez le suffixe k, m ou g pour changer l'unité.

git-p4.largeFileCompressedThreshold

Tous les fichiers dont la taille compressée dépasse le seuil seront traités par le système de fichiers volumineux. Cette option peut ralentir votre processus de clonage/synchronisation. Par défaut, le seuil est défini en octets. Ajoutez le suffixe k, m ou g pour changer l'unité.

git-p4.largeFilePush

Variable booléenne qui définit si les fichiers volumineux sont automatiquement poussés vers un serveur.

git-p4.keepEmptyCommits

Une changelist ne contenant que des fichiers exclus sera importée comme un commit vide si cette option booléenne est définie sur true.

git-p4.mapUser

Mappe un utilisateur P4 vers un nom et une adresse e-mail dans Git. Utilisez une chaîne avec le format suivant pour créer un mappage : 
git config --add git-p4.mapUser "p4user = First Last <mail@address.com>"

Un mappage remplacera toute information utilisateur provenant de P4. Des mappages pour plusieurs utilisateurs P4 peuvent être définis.

VARIABLES DE CONFIGURATION

git-p4.detectRenames

Détecte les renommages. Voir git-diff(1). Ceci peut être vrai, faux, ou un score tel qu'attendu par git diff -M.

git-p4.detectCopies

Détecte les copies. Voir git-diff(1). Ceci peut être vrai, faux, ou un score tel qu'attendu par git diff -C.

git-p4.detectCopiesHarder

Détecte les copies de manière plus approfondie. Voir git-diff(1). Un booléen.

git-p4.preserveUser

Lors de la soumission, réattribue les modifications pour refléter l'auteur Git, indépendamment de qui invoque git p4 submit.

git-p4.allowMissingP4Users

Lorsque preserveUser est vrai, git p4 échoue normalement s'il ne trouve pas d'utilisateur dans la table des utilisateurs p4. Ce paramètre soumet le changement quoi qu'il arrive.

git-p4.skipSubmitEdit

Le processus de soumission invoque l'éditeur avant chaque changement p4 soumis. Si ce paramètre est vrai, cependant, l'étape d'édition est ignorée.

git-p4.skipSubmitEditCheck

Après avoir édité le message de changement p4, git p4 vérifie que la description a bien été modifiée en examinant l'heure de modification du fichier. Cette option désactive ce test.

git-p4.allowSubmit

Par défaut, n'importe quelle branche peut être utilisée comme source pour une opération git p4 submit. Cette variable de configuration, si elle est définie, autorise uniquement les branches nommées à être utilisées comme sources de soumission. Les noms de branches doivent être les noms courts (sans "refs/heads/"), et doivent être séparés par des virgules (","), sans espaces.

git-p4.skipUserNameCheck

Si l'utilisateur exécutant git p4 submit n'existe pas dans la table des utilisateurs p4, git p4 s'arrête. Cette option peut être utilisée pour forcer la soumission quoi qu'il arrive.

git-p4.attemptRCSCleanup

Si activé, git p4 submit tentera de nettoyer les mots-clés RCS ($Header$, etc). Ceux-ci causeraient sinon des conflits de fusion et empêcheraient la soumission d'avoir lieu. Cette option doit être considérée comme expérimentale pour le moment.

git-p4.exportLabels

Exporte les tags Git vers des labels p4, conformément à --export-labels.

git-p4.labelExportRegexp

Seuls les labels p4 correspondant à cette expression régulière seront exportés. La valeur par défaut est [a-zA-Z0-9_\-.]+$.

git-p4.conflict

Spécifie le comportement de soumission lorsqu'un conflit avec p4 est trouvé, conformément à --conflict. Le comportement par défaut est ask.

git-p4.disableRebase

Ne pas rebaser l'arbre contre p4/master après une soumission.

git-p4.disableP4Sync

Ne pas synchroniser p4/master avec Perforce après une soumission. Implique git-p4.disableRebase.

DÉTAILS D'IMPLÉMENTATION

•Les changements de p4 sont importés en utilisant Git fast-import.
•Le clonage ou la synchronisation ne nécessite pas de client p4 ; le contenu des fichiers est collecté à l'aide de p4 print.
•La soumission nécessite un client p4, qui n'est pas au même endroit que le dépôt Git. Les patchs sont appliqués, un par un, à ce client p4 et soumis à partir de là.
•Chaque commit importé par git p4 contient une ligne à la fin du message de log indiquant l'emplacement du dépôt p4 et le numéro de changement. Cette ligne est utilisée par les opérations ultérieures de git p4 sync pour savoir quels changements p4 sont nouveaux.
