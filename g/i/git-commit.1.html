DESCRIPTIO

N

Créer un nouveau commit contenant le contenu actuel de l'index et le message de journal donné décrivant les modifications. Le nouveau commit est un enfant direct de HEAD, généralement l'extrémité de la branche actuelle, et la branche est mise à jour pour pointer vers lui (sauf si aucune branche n'est associée à l'arbre de travail, auquel cas HEAD est « détaché » comme décrit dans git-checkout(1))

.

Le contenu à committer peut être spécifié de plusieurs manières

:
1.en utilisant git-add(1) pour ajouter progressivement les modifications à l'index avant d'utiliser la commande commit (Remarque : même les fichiers modifiés doivent être « ajoutés »)
;
2.en utilisant git-rm(1) pour supprimer des fichiers de l'arbre de travail et de l'index, à nouveau avant d'utiliser la commande commit
;
3.en listant des fichiers comme arguments de la commande commit (sans --interactive ni --patch), auquel cas le commit ignorera les modifications préparées dans l'enregistrement, et enregistrera à la place le contenu actuel des fichiers listés (qui doivent déjà être connus de Git)
;
4.en utilisant l'option -a avec la commande commit pour « ajouter » automatiquement les modifications de tous les fichiers connus (c'est-à-dire tous les fichiers déjà listés dans l'index) et pour « rm » automatiquement les fichiers de l'index qui ont été supprimés de l'arbre de travail, puis effectuer le commit réel
;
5.en utilisant les options --interactive ou --patch avec la commande commit pour décider un par un quels fichiers ou fragments doivent faire partie du commit en plus du contenu de l'index, avant de finaliser l'opération. Voir la section « Interactive Mode » de git-add(1) pour savoir comment utiliser ces
modes.

L'option --dry-run peut être utilisée pour obtenir un résumé de ce qui est inclus par l'une des méthodes ci-dessus pour le prochain commit en donnant le même ensemble de paramètres (options et chemins)

.

Si vous faites un commit et que vous trouvez ensuite immédiatement une erreur, vous pouvez vous en remettre avec git res

e

Créer un nouveau commit qui « corrige » <commit> lorsqu'il est appliqué avec git rebase --autosquash. Un simple --fixup=<commit> crée un commit « fixup! » qui change le contenu de <commit> mais laisse son message de journal intact. --fixup=amend:<commit> est similaire mais crée un commit « amend! » qui remplace également le message de journal de <commit> par le message de journal du commit « amend! ». --fixup=reword:<commit> crée un commit « amend! » qui remplace le message de journal de <commit> par son propre message de journal mais ne fait aucune modification au contenu de <commit>.

Le commit créé par un simple --fixup=<commit> a un titre composé de « fixup! » suivi du titre de <commit>, et est reconnu spécialement par git rebase --autosquash. L'option -m peut être utilisée pour compléter le message de journal du commit créé, mais le commentaire supplémentaire sera jeté une fois que le commit « fixup! » sera écrasé dans <commit> par git rebase --autosquash

Le commit créé par --fixup=amend:<commit> est similaire mais son titre est préfixé de « amend! » à la place. Le message de journal de <commit> est copié dans le message de journal du commit « amend! » et ouvert dans un éditeur pour pouvoir être affiné. Lorsque git rebase --autosquash écrase le commit « amend! » dans <commit>, le message de journal de <commit> est remplacé par le message de journal affiné du commit « amend! ». C'est une erreur si le message de journal du commit « amend! » est vide, sauf si --allow-empty-message est

spécifié.

--fixup=reword:<commit> est l'abréviation de --fixup=amend:<commit> --only. Il crée un commit « amend! » avec seulement un message de journal (ignorant toute modification préparée dans l'index). Lorsqu'il est écrasé par git rebase --autosquash, il remplace le message de journal de <commit> sans faire aucune autre

modification.

EXEMPLE

S

Lorsque vous enregistrez votre propre travail, le contenu des fichiers modifiés dans votre arbre de travail est temporairement stocké dans une zone de préparation appelée l'« index » avec git add. Un fichier peut être restauré, uniquement dans l'index mais pas dans l'arbre de travail, à celui du dernier commit avec git restore --staged <file>, ce qui annule effectivement git add et empêche les modifications de ce fichier de participer au prochain commit. Après avoir construit l'état à committer de manière incrémentielle avec ces commandes, git commit (sans aucun paramètre de chemin) est utilisé pour enregistrer ce qui a été mis en préparation jusqu'à présent. C'est la forme la plus basique de la commande. Un exemple

: 
$ edit hello.c
$ git
rm goodbye.c $ git add
hello.c $ git commit

Au lieu de mettre les fichiers en préparation après chaque modification individuelle, vous pouvez indiquer à git commit de remarquer les modifications des fichiers dont le contenu est suivi dans votre arbre de travail et d'effectuer les git add et git rm correspondants pour vous. C'est-à-dire, cet exemple fait la même chose que l'exemple précédent s'il n'y a pas d'autre modification dans votre arbre de travail

: 
$ edit hello.c
$ rm goodbye.c
$ git commit -a

La commande git commit -a examine d'abord votre arbre de travail, remarque que vous avez modifié hello.c et supprimé goodbye.c, et effectue les git add et git rm nécessaires pour

vous.

Après avoir mis en préparation les modifications de nombreux fichiers, vous pouvez modifier l'ordre dans lequel les modifications sont enregistrées en donnant des noms de chemins à git commit. Lorsque des noms de chemins sont donnés, la commande effectue un commit qui n'enregistre que les modifications apportées aux chemins nommés

: 
$ edit hello.c hello.h
$ git
add hello.c hello.h $ edit M
akefile $ git commit Makefile

Cela crée un commit qui enregistre la modification de Makefile. Les modifications mises en préparation pour hello.c et hello.h ne sont pas incluses dans le commit résultant. Cependant, leurs modifications ne sont pas perdues — elles sont toujours en préparation et simplement retenues. Après la séquence ci-dessus, si vous faites

: 
$ gi
t co
mmit

ce deuxième commit enregistrerait les modifications de hello.c et hello.h comme

prévu.

Après qu'une fusion (initiée par git merge ou git pull) s'arrête en raison de conflits, les chemins fusionnés proprement sont déjà mis en préparation pour être committés pour vous, et les chemins en conflit sont laissés dans un état non fusionné. Vous devrez d'abord vérifier quels chemins sont en conflit avec git status et après les avoir corrigés manuellement dans votre arbre de travail, vous mettrez le résultat en préparation comme d'habitude avec git add

: 
$ git status | grep unmerg
ed unmerged: hello.c $ edit
hello.c $ git add hello.c

Après avoir résolu les conflits et mis le résultat en préparation, git ls-files -u ne mentionnerait plus le chemin en conflit. Lorsque vous avez terminé, exécutez git commit pour enregistrer finalement la fusion

: 
$ gi
t co
mmit

Comme dans le cas d'enregistrer vos propres modifications, vous pouvez utiliser l'option -a pour économiser de la saisie. Une différence est que lors de la résolution d'une fusion, vous ne pouvez pas utiliser git commit avec des noms de chemins pour modifier l'ordre dans lequel les modifications sont committées, car la fusion doit être enregistrée comme un seul commit. En fait, la commande refuse de s'exécuter si des noms de chemins sont donnés (mais voir l'option -i

)
.

FORMATS DE

DATE

Les variables d'environnement GIT_AUTHOR_DATE et GIT_COMMITTER_DATE prennent en charge les formats de date suivants

:

Format interne de

Git
Il s'agit de <unix-timestamp> <time-zone-offset>, où <unix-timestamp> est le nombre de secondes depuis l'époque UNIX. <time-zone-offset> est un décalage positif ou négatif par rapport à UTC. Par exemple CET (qui est en avance d'une heure sur UTC) est +0100
.

RFC

2822
Le format de date standard tel que décrit par la RFC 2822, par exemple Thu, 07 Apr 2005 22:13:13 +0200
.

ISO

8601
Heure et date spécifiées par la norme ISO 8601, par exemple 2005-04-07T22:13:13. L'analyseur accepte également un espace à la place du caractère T. Les parties fractionnaires d'une seconde seront ignorées, par exemple 2005-04-07T22:13:13.019 sera traité comme 2005-04-07T22:13:13.

Note
De plus, la partie date est acceptée dans les formats suivants : YYYY.MM.DD, MM/DD/YYYY et DD.MM.
YY
YY.

En plus de reconnaître tous les formats de date ci-dessus, l'option --date essaiera également de donner du sens à d'autres formats de date plus centrés sur l'humain, tels que des dates relatives comme « hier » ou « vendredi dernier à midi

»

DISCUSSIO

N

Bien que non requis, il est bon de commencer le message de commit par une seule ligne courte (pas plus de 50 caractères) résumant le changement, suivie d'une ligne vide puis d'une description plus détaillée. Le texte jusqu'à la première ligne vide dans un message de commit est traité comme le titre du commit, et ce titre est utilisé dans l'ensemble de Git. Par exemple, git-format-patch(1) transforme un commit en courriel, et il utilise le titre sur la ligne Subject et le reste du commit dans le

corps.

Git est dans une certaine mesure agnostique quant à l'encodage de

caractères.
•Le contenu des objets blob est des séquences d'octets non interprétées. Il n'y a pas de traduction d'encodage au niveau du
noyau.
•Les noms de chemins sont encodés en UTF-8 forme de normalisation C. Cela s'applique aux objets arbre, au fichier index, aux noms de références, ainsi qu'aux noms de chemins dans les arguments de ligne de commande, les variables d'environnement et les fichiers de configuration (.git/config (voir git-config(1)), gitignore(5), gitattributes(5) et gitmodules(5)).

Notez qu'au niveau du noyau, Git traite les noms de chemins simplement comme des séquences d'octets non-NUL, il n'y a pas de conversions d'encodage de noms de chemins (sauf sur Mac et Windows). Par conséquent, l'utilisation de noms de

chemins non-ASCII fonctionnera principalement même sur les plateformes et les systèmes de fichiers qui utilisent des encodages ASCII étendus hérités. Cependant, les dépôts créés sur de tels systèmes ne fonctionneront pas correctement s
ur les systèmes basés sur UTF-8 (par ex. Linux, Mac, Windows) et vice versa. De plus, de nombreux outils basés sur Git supposent simplement que les noms de chemins sont en UTF-8 et échoueront à afficher correctement d'autres encodages.
•Les messages de journal de commit sont généralement encodés en UTF-8, mais d'autres encodages ASCII étendus sont également pris en charge. Cela inclut ISO-8859-x, CP125x et beaucoup d'autres, mais pas UTF-16/32, EBCDIC et les encodages multi-octets CJK (GBK, Shift-JIS, Big5, EUC-x, CP9xx etc.)
.

Bien que nous encouragions l'encodage des messages de journal de commit en UTF-8, à la fois le noyau et Git Porcelain sont conçus pour ne pas forcer UTF-8 sur les projets.
