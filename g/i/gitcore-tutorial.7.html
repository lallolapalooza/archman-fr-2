GIT

Créer un nouveau dépôt Git n'a jamais été aussi simple : tous les dépôts Git commencent vides, et la seule chose que vous ayez à faire est de trouver un sous-répertoire que vous souhaitez utiliser comme arbre de travail - soit un répertoire vide pour un projet totalement nouveau, soit un arbre de travail existant que vous souhaitez importer dans

VALIDATION DE L'ÉTAT

GIT

Maintenant, nous voulons passer à l'étape suivante dans Git, qui consiste à prendre les fichiers que Git connaît dans l'index, et à les valider comme un arbre réel. Nous faisons cela en deux phases : créer un objet tree, et valider cet objet tree en tant qu' objet commit avec une explication de ce que l'arbre représentait, ainsi que des informations sur la façon dont nous en sommes arrivés à cet

état.

Créer un objet tree est trivial, et se fait avec git write-tree. Il n'y a pas d'options ni d'autres entrées : git write-tree prendra l'état actuel de l'index, et écrira un objet qui décrit tout cet index. En d'autres termes, nous relions maintenant tous les noms de fichiers différents à leur contenu (et à leurs permissions), et nous créons l'équivalent d'un objet "répertoire" Git

: 
$ git
write
-tree

et cela ne fera qu'afficher le nom de l'arbre résultant, dans ce cas (si vous avez fait exactement ce que j'ai décrit) cela devrait

qui est un autre nom d'objet incompréhensible. Encore une fois, si vous le voulez, vous pouvez utiliser git cat-file -t 8988d... pour voir que cette fois l'objet n'est pas un objet "blob", mais un objet "tree" (vous pouvez aussi utiliser git cat-file pour afficher réellement le contenu brut de l'objet, mais vous verrez principalement un désordre binaire, donc c'est moins intéressant)

.

Cependant — normalement vous n'utiliseriez jamais git write-tree tout seul, parce que normalement vous validez toujours un arbre dans un objet commit en utilisant la commande git commit-tree. En fait, il est plus facile de ne pas utiliser git write-tree tout seul du tout, mais de simplement passer son résultat en argument à git commit-

tree.

git commit-tree prend normalement plusieurs arguments — il veut connaître le parent d'un commit, mais puisque c'est le tout premier commit dans ce nouveau dépôt, et qu'il n'a pas de parents, nous n'avons besoin que de passer le nom d'objet de l'arbre. Cependant, git commit-tree veut aussi recevoir un message de commit sur son entrée standard, et il écrira le nom d'objet résultant du commit sur sa sortie

standard.

Et c'est ici que nous créons le fichier .git/refs/heads/master qui est pointé par HEAD. Ce fichier doit contenir la référence au sommet de l'arbre de la branche master, et puisque c'est exactement ce que git commit-tree crache, nous pouvons faire tout cela avec une séquence de commandes shell simples

cho 'Initial commit' | git commit-tree
$tree) $ git update-ref HEAD $commit

Dans ce cas, cela crée un commit totalement nouveau qui n'est lié à rien d'autre. Normalement, vous ne faites cela qu'une seule fois pour un projet, et tous les commits ultérieurs seront parentés sur un commit

antérieur.

Encore une fois, normalement vous ne feriez jamais cela à la main. Il y a un script utile appelé git commit qui fera tout cela pour vous. Vous auriez donc pu simplement écrire git commit à la place, et il aurait

CHANGEMENT

Rappelez-vous comment nous avons fait le git update-index sur le fichier hello et ensuite nous avons changé hello après, et nous pourrions comparer le nouvel état de hello avec l'état que nous avions enregistré dans le fichier index

?

De plus, rappelez-vous comment j'ai dit que git write-tree écrit le contenu du fichier index dans l'arbre, et donc ce que nous venons de valider était en fait le contenu original du fichier hello, pas les nouveaux. Nous l'avons fait exprès, pour montrer la différence entre l'état de l'index, et l'état dans l'arbre de travail, et comment ils ne doivent pas nécessairement correspondre, même lorsque nous validons des

choses.

Comme avant, si nous faisons git diff-files -p dans notre projet git-tutorial, nous verrons toujours la même différence que la dernière fois : le fichier index n'a pas changé par l'acte de valider quoi que ce soit. Cependant, maintenant que nous avons validé quelque chose, nous pouvons aussi apprendre à utiliser une nouvelle commande : git diff-i

ndex.

Contrairement à git diff-files, qui montrait la différence entre le fichier index et l'arbre de travail, git diff-index montre les différences entre un arbre validé et soit le fichier index, soit l'arbre de travail. En d'autres termes, git diff-index veut un arbre à comparer, et avant que nous fassions le commit, nous ne pouvions pas faire cela, parce que nous n'avions rien à

comparer.

Mais maintenant nous pouvons

faire 
$ git di
ff-index
-p HEAD

(où -p a la même signification que dans git diff-files), et cela nous montrera la même différence, mais pour une raison totalement différente. Maintenant nous comparons l'arbre de travail non pas au fichier index, mais à l'arbre que nous venons d'écrire. Il se trouve que ces deux-là sont évidemment les mêmes, donc nous obtenons le même

résultat.

Encore une fois, parce que c'est une opération courante, vous pouvez aussi simplement l'abréger

avec 
$ git
diff
HEAD

ce qui finira par faire ce qui précède pour

vous.

En d'autres termes, git diff-index compare normalement un arbre à l'arbre de travail, mais lorsqu'on lui donne l' indicateur --cached, il est dit de comparer plutôt avec le seul contenu du cache d'index, et d'ignorer complètement l'état actuel de l'arbre de travail. Puisque nous venons d'écrire le fichier index vers HEAD, faire git diff-index --cached -p HEAD devrait donc retourner un ensemble vide de différences, et c'est exactement ce qu'il

fait.

Notez

que git diff-index utilise vraiment toujours l'index pour ses comparaisons, et dire qu'il compare un arbre à l'arbre de travail n'est donc pas strictement exact. En particulier, la liste des fichiers à comparer (les "métadonnées") vient toujours du fichier index, que l' indicateur --cached soit utilisé ou non. L' indicateur --cached ne détermine vraiment que si le contenu des fichiers à comparer provient de l'arbre de travail ou

non.

Cela n'est pas difficile à comprendre, dès que vous réalisez que Git ne connaît simplement jamais (ou ne se soucie pas) des fichiers qui ne lui sont pas explicitement signalés. Git n'ira jamais chercher des fichiers à comparer, il attend que vous lui disi

ez quels sont les fichiers, et c'
est à cela que sert l'index.

Cependant, notre prochaine étape est de valider le changement que nous avons fait, et encore une fois, pour comprendre ce qui se passe, gardez à l'esprit la différence entre "contenu de l'arbre de travail", "fichier index" et "arbre validé". Nous avons des changements dans l'arbre de travail que nous voulons valider, et nous devons toujours passer par le fichier index, donc la première chose que nous devons faire est de mettre à jour le cache d'index

$ git up
date-ind
ex hello

(notez comment nous n'avons pas eu besoin de l' indicateur --add cette fois, puisque Git connaissait déjà le fichier)

.

Notez ce qui arrive aux différentes versions git diff-* ici. Après que nous ayons mis à jour hello dans l'index, git diff-files -p ne montre plus de différences, mais git diff-index -p HEAD montre toujours que l' état actuel est différent de l'état que nous avons validé. En fait, maintenant git diff-index montre la même différence que nous utilisions l' indicateur --cached ou non, puisque maintenant l'index est cohérent avec l'arbre de

travail.

Maintenant, puisque nous avons mis à jour hello dans l'index, nous pouvons valider la nouvelle version. Nous pourrions le faire en écrivant l'arbre à la main à nouveau, et en validant l'arbre (cette fois nous devrions utiliser l' indicateur -p HEAD pour dire à commit que HEAD était le parent du nouveau commit, et que ce n'était plus un commit initial), mais vous l'avez déjà fait une fois, donc utilisons simplement le script utile cette fois-ci :p>

INSPECTER LES

CHANGEMENTS

Bien que créer des changements soit utile, c'est encore plus utile si vous pouvez dire plus tard ce qui a changé. La commande la plus utile pour cela est un autre membre de la famille diff, à savoir git diff-

tree.

git diff-tree peut recevoir deux arbres arbitraires, et il vous dira les différences entre eux. Peut-être encore plus couramment, cependant, vous pouvez lui donner un seul objet commit, et il déterminera lui-même le parent de ce commit, et affichera la différence directement. Ainsi, pour obtenir le même diff que nous avons déjà vu plusieurs fois, nous pouvons maintenant

faire 
$ git di
ff-tree
-p HEAD

(encore, -p signifie afficher la différence sous forme de patch lisible par un humain), et il affichera ce que le dernier commit (dans HEAD) a réellement

changé.

ÉTIQUETER UNE

VERSION

Dans Git, il y a deux types d'étiquettes (tags), une "légère", et une "étiquette

annotée".

Une étiquette "légère" n'est techniquement rien de plus qu'une branche, sauf que nous la mettons dans le sous-répertoire .git/refs/tags/ au lieu de l'appeler un head. Ainsi la forme la plus simple d'étiquette n'implique rien de plus

que 
$ git t
ag my-fi
rst-tag

qui écrit simplement le HEAD actuel dans le fichier .git/refs/tags/my-first-tag, après quoi vous pouvez utiliser ce nom symbolique pour cet état particulier. Vous pouvez, par exemple,

faire 
$ git di
ff my-f
irst-tag

pour comparer votre état actuel avec cette étiquette, ce qui à ce stade sera évidemment un diff vide, mais si vous continuez à développer et commiter des choses, vous pouvez utiliser votre étiquette comme "point d'ancrage" pour voir ce qui a changé depuis que vous l'avez

créée.

Une "étiquette annotée" est en fait un vrai objet Git, et contient non seulement un pointeur vers l'état que vous voulez étiqueter, mais aussi un petit nom d'étiquette et un message, ainsi qu'en option une signature PGP qui dit que oui, vous avez vraiment créé cette étiquette. Vous créez ces étiquettes annotées avec soit le drapeau -a ou le drapeau -s avec git ta

g : 
$ git t
ag -s <t
agname>

qui signera le HEAD actuel (mais vous pouvez aussi lui donner un autre argument qui spécifie la chose à étiqueter, par ex., vous auriez pu étiqueter le point mybranch actuel en utilisant git tag <tagname> mybranc

h).

Vous ne faites normalement des étiquettes signées que pour les versions majeures ou des choses comme ça, tandis que les étiquett

es légères sont utiles pour tout marquage que vous voulez faire — chaque fois que vous décidez de vouloir vous souvenir d'u
n certain point, créez simplement une étiquette privée pour lui, et vous avez un joli nom symbolique pour l'état à ce point.

COPIER LES

DÉPÔTS

Les dépôts Git sont normalement totalement auto-suffisants et relocalisables. Contrairement à CVS, par exemple, il n'y a pas de notion séparée de "dépôt" et "arbre de travail". Un dépôt Git est normalement l'arbre de travail, avec les informations Git locales cachées dans le sous-répertoire .git. Il n'y a rien d'autre. Ce que vous voyez est ce que vous

avez.

Note

Vous pouvez dire à Git de séparer les informations internes Git du répertoire qu'il suit, mais nous allons ignorer cela pour l'instant : ce n'est pas comm

ent fonctionnent les projets normaux, et c'est vraiment seulement destiné à des usages spéciaux. Ainsi le modèle mental de "les informations Git sont toujo
urs directement liées à l'arbre de travail qu'elles décrivent" peut ne pas être techniquement 100% exact, mais c'est un bon modèle pour tout usage normal.

Cela a deux implications

:
•si vous vous ennuyez du dépôt de tutoriel que vous avez créé (ou si vous avez fait une erreur et voulez tout recommencer), vous pouvez simplement faire 
$ rm -r
f git-t
utorial

et il sera disparu. Il n'y a pas de dépôt

externe, et il n'y a pas d'historiqu
e en dehors du projet que vous avez créé.

DÉPÔT

Plus tôt, nous avons vu qu'un fichier sous .git/objects/??/ est stocké pour chaque objet Git que vous créez. Cette représentation est efficace à créer de manière atomique et sûre, mais pas très pratique pour le transport sur le réseau. Puisque les objets Git sont immuables une fois créés, il existe un moyen d'optimiser le stockage en les « compressant ensemble ». La

commande 
$ gi
t re
pack

le fera pour vous. Si vous avez suivi les exemples du tutoriel, vous auriez accumulé environ 17 objets dans les répertoires .git/objects/??/ jusqu'à présent. git repack vous indique combien d'objets il a compressés, et stocke le fichier compressé dans le répertoire .git/objects/pack

.

Note

Vous verrez deux fichiers, pack-*.pack et pack-*.idx, dans le répertoire .git/objects/pack. Ils sont étroitement liés l'un à l'autre, et si vous les copiez jamais à la main dans un dépôt différent pour quelque raison que ce soit, vous

devez vous assurer de les copier ensemble. Le premier contient toutes les donnée
s des objets dans le pack, et le second contient l'index pour l'accès aléatoire.

Si vous êtes paranoïaque, exécuter la commande git verify-pack détecterait si vous avez un pack corrompu, mais ne vous inquiétez pas trop. Nos programmes sont toujours parfaits ;-)

.

Une fois que vous avez compressé les objets, vous n'avez plus besoin de laisser les objets non compressés qui sont contenus dans le fichier

pack.

les supprimerait pour

vous.

Vous pouvez essayer d'exécuter find .git/objects -type f avant et après avoir exécuté git prune-packed si vous êtes curieux. Aussi git count-objects vous indiquerait combien d'objets non compressés il y a dans votre dépôt et combien d'espace ils

consomment.

Note

git pull est légèrement lourd pour le transport HTTP, car un dépôt compressé peut contenir relativement peu d'objets dans un pack relativement g

rand. Si vous attendez beaucoup de tirages HTTP depuis votre dépôt pub
lic, vous pourriez vouloir recompresser et élaguer souvent, ou jamais.

Si vous exécutez git repack à nouveau à ce moment, il dira « Rien de nouveau à compresser. ». Une fois que vous continuez votre développement et accumulez les modifications, exécuter git repack créera un nouveau pack, contenant les objets créés depuis que vous avez compressé votre dépôt la dernière fois. Nous recommandons que vous compressiez votre projet peu après l'importation initiale (sauf si vous démarrez votre projet de zéro), puis exécutez git repack de temps en temps, selon l'activité de votre

projet.

Quand un dépôt est synchronisé via git push et git pull, les objets compressés dans le dépôt source sont habituellement stockés non compressés dans la destination. Bien que cela vous permette d'utiliser diff

érentes stratégies de compression aux deux extrémités, cela signifie aussi que
vous pourriez avoir besoin de recompresser les deux dépôts de temps en temps.

RASSEMBLER VOTRE TRAVAIL

Il est probable que vous travaillerez sur plus d'une chose à la fois. Il est facile de gérer ces tâches plus ou moins indépendantes en utilisant des branches avec Git.

Nous avons déjà vu comment fonctionnent les branches, avec l'exemple « amusement et travail » utilisant deux branches. L'idée est la même s'il y a plus de deux branches. Disons que vous avez commencé à partir de la tête « master », et que vous avez du nouveau code dans la branche « master », et deux corrections indépendantes dans les branches « commit-fix » et « diff-fix » :

$ git show-branch
! [commit-fix] Corriger la normalisation du message de commit.
 ! [diff-fix] Corriger la détection de renommage.
  * [master] Version candidate #1
---
 +  [diff-fix] Corriger la détection de renommage.
 +  [diff-fix~1] Meilleur algorithme de sous-chaîne commune.
+   [commit-fix] Corriger la normalisation du message de commit.
  * [master] Version candidate #1
++* [diff-fix~2] Imprimer joliment les messages.

Les deux corrections sont bien testées, et à ce stade, vous voulez les fusionner toutes les deux. Vous pourriez fusionner diff-fix d'abord, puis commit-fix ensuite, comme ceci :

$ git merge -m "Fusionner la correction de diff-fix" diff-fix
$ git merge -m "Fusionner la correction de commit-fix" commit-fix

Ce qui résulterait en :

$ git show-branch
! [commit-fix] Corriger la normalisation du message de commit.
 ! [diff-fix] Corriger la détection de renommage.
  * [master] Fusionner la correction de commit-fix
---
  - [master] Fusionner la correction de commit-fix
+ * [commit-fix] Corriger la normalisation du message de commit.
  - [master~1] Fusionner la correction de diff-fix
 +* [diff-fix] Corriger la détection de renommage.
 +* [diff-fix~1] Meilleur algorithme de sous-chaîne commune.
  * [master~2] Version candidate #1
++* [master~3] Imprimer joliment les messages.

Cependant, il n'y a aucune raison particulière de fusionner d'abord une branche et ensuite l'autre, alors que vous avez un ensemble de modifications véritablement indépendantes (si l'ordre avait de l'importance, alors elles ne sont pas indépendantes par définition). Vous pourriez plutôt fusionner ces deux branches dans la branche actuelle en une seule fois. Commençons d'abord par annuler ce que nous venons de faire et recommencer. Nous voudrions récupérer la branche master avant ces deux fusions en la réinitialisant à master~2 :

$ git reset --hard master~2

Vous pouvez vous assurer que git show-branch correspond à l'état avant ces deux git merge que vous venez de faire. Ensuite, au lieu d'exécuter deux commandes git merge d'affilée, vous fusionneriez ces deux têtes de branche (ceci est connu sous le nom de création d'un Octopus) :

$ git merge commit-fix diff-fix
$ git show-branch
! [commit-fix] Corriger la normalisation du message de commit.
 ! [diff-fix] Corriger la détection de renommage.
  * [master] Fusion Octopus des branches 'diff-fix' et 'commit-fix'
---
  - [master] Fusion Octopus des branches 'diff-fix' et 'commit-fix'
+ * [commit-fix] Corriger la normalisation du message de commit.
 +* [diff-fix] Corriger la détection de renommage.
 +* [diff-fix~1] Meilleur algorithme de sous-chaîne commune.
  * [master~1] Version candidate #1
++* [master~2] Imprimer joliment les messages.

Notez que vous ne devriez pas faire d'Octopus juste parce que vous le pouvez. Un octopus est une chose valide à faire et rend souvent l'historique des commits plus facile à visualiser si vous fusionnez plus de deux modifications indépendantes en même temps. Cependant, si vous avez des conflits de fusion avec l'une des branches que vous fusionnez et que vous devez les résoudre manuellement, cela indique que le développement effectué dans ces branches n'était pas indépendant après tout, et vous devriez fusionner deux à la fois, en documentant comment vous avez résolu les conflits, et la raison pour laquelle vous avez préféré les modifications apportées d'un côté par rapport à l'autre. Sinon, cela rendrait l'historique du projet plus difficile à suivre, pas plus facile.
