NOM

git-annotate - Annoter les lignes d'un fichier avec les informations de commit

SYNOPSIS

git annotate [<options>] [<rev-opts>] [<rev>] [--] <file>

DESCRIPTION

Annote chaque ligne du fichier donné avec les informations du commit qui a introduit la ligne. Annote éventuellement à partir d'une révision donnée.

La seule différence entre cette commande et git-blame(1) est qu'elles utilisent des formats de sortie légèrement différents, et que cette commande existe uniquement pour la rétrocompatibilité afin de prendre en charge les scripts existants, et fournir un nom de commande plus familier pour les personnes provenant d'autres systèmes de gestion de code source.

OPTIONS

-b

Affiche un SHA-1 vide pour les commits de limite. Cela peut aussi être contrôlé via l'option de configuration blame.blankBoundary .

--root

Ne traite pas les commits racine comme des limites. Cela peut aussi être contrôlé via l'option de configuration blame.showRoot .

--show-stats

Inclut des statistiques supplémentaires à la fin de la sortie de blame.

-L <start>,<end>, -L :<funcname>

Annote uniquement la plage de lignes donnée par <start>,<end>, ou par l'expression régulière du nom de fonction <funcname>. Peut être spécifié plusieurs fois. Les plages qui se chevauchent sont autorisées.

<start> et <end> sont optionnels. -L <start> ou -L <start>, s'étend de <start> jusqu'à la fin du fichier. -L ,<end> s'étend du début du fichier jusqu'à <end>.

<start> et <end> peuvent prendre l'une de ces formes :

•<number>

Si <start> ou <end> est un nombre, il spécifie un numéro de ligne absolu (les lignes sont comptées à partir de 1).

•/<regex>/

Cette forme utilisera la première ligne correspondant à l'expression POSIX <regex>donnée. Si <start> est une expression régulière, la recherche se fera à partir de la fin de la plage -L précédente, s'il y en a une, sinon à partir du début du fichier. Si <start> est ^/<regex>/, la recherche se fera à partir du début du fichier. Si <end> est une expression régulière, la recherche commencera à la ligne donnée par <start>.

•+<offset> ou -<offset>

Cela n'est valide que pour <end> et spécifiera un nombre de lignes avant ou après la ligne donnée par <start>.

Si :<funcname> est donné à la place de <start> et <end>, c'est une expression régulière qui désigne la plage allant de la première ligne funcname qui correspond à <funcname>, jusqu'à la prochaine ligne funcname. :<funcname> recherche à partir de la fin de la plage -L] précédente, s'il y en a une, sinon à partir du début du fichier. ^:<funcname> recherche à partir du début du fichier. Les noms de fonction sont déterminés de la même manière que git diff détermine les en-têtes de blocs de patch (voir Définir un en-tête de bloc personnalisé dans gitattributes(5)).

-l

Affiche la révision longue (Par défaut : désactivé).

-t

Affiche l'horodatage brut (Par défaut : désactivé).

-S <revs-file>

Utilise les révisions du fichier revs-file au lieu d'appeler git-rev-list(1).

--reverse <rev>..<rev>

Parcourt l'historique vers l'avant au lieu de vers l'arrière. Au lieu de montrer la révision dans laquelle une ligne est apparue, cela montre la dernière révision dans laquelle une ligne a existé. Cela nécessite une plage de révisions de la forme DÉBUT..FIN où le chemin vers blame existe dans DÉBUT. git blame --reverse DÉBUT est interprété comme git blame --reverse DÉBUT..HEAD par commodité.

--first-parent

Suit uniquement le premier commit parent lorsqu'un commit de fusion est rencontré. Cette option peut être utilisée pour déterminer quand une ligne a été introduite dans une branche d'intégration particulière, plutôt que quand elle a été introduite dans l'historique en général.

-p, --porcelain

Affiche dans un format conçu pour la consommation par machine.

--line-porcelain

Affiche le format porcelain, mais produit les informations de commit pour chaque ligne, et pas seulement la première fois qu'un commit est référencé. Implique --porcelain.

--incremental

Affiche le résultat de manière incrémentielle dans un format conçu pour la consommation par machine.

--encoding=<encoding>

Spécifie l'encodage utilisé pour produire les noms d'auteur et les résumés de commit. Le définir à none fait que la sortie de blame contient des données non converties. Pour plus d'informations, voir la discussion sur l'encodage dans la page man git-log(1) .

--contents <file>

Annote en utilisant le contenu du fichier nommé, à partir de <rev> s'il est spécifié, et de HEAD sinon. Vous pouvez spécifier - pour faire lire la commande depuis l'entrée standard pour le contenu du fichier.

--date <format>

Spécifie le format utilisé pour produire les dates. Si --date n'est pas fourni, la valeur de la variable de configuration blame.date est utilisée. Si la variable de configuration blame.date n'est pas non plus définie, le format iso est utilisé. Pour les valeurs prises en charge, voir la discussion de l'option --date dans git-log(1).

--progress, --no-progress

L'état de progression est rapporté sur le flux d'erreur standard par défaut lorsqu'il est attaché à un terminal. Ce drapeau active le rapport de progression même s'il n'est pas attaché à un terminal. Ne peut pas utiliser --progress en même temps que --porcelain ou --incremental.

-M[<num>]

Détecte les lignes déplacées ou copiées dans un fichier. Quand un commit déplace ou copie un bloc de lignes (par ex. le fichier original a A puis B, et le commit le change en B puis A), l'algorithme de blame traditionnel ne remarque que la moitié du déplacement et attribue généralement les lignes qui ont été déplacées vers le haut (c.-à-d. B) au parent et attribue la responsabilité aux lignes qui ont été déplacées vers le bas (c.-à-d. A) au commit enfant. Avec cette option, les deux groupes de lignes sont attribués au parent en exécutant des passes d'inspection supplémentaires.

<num> est optionnel mais c'est la borne inférieure du nombre de caractères alphanumériques que Git doit détecter comme déplacés/copiés dans un fichier pour associer ces lignes au commit parent. La valeur par défaut est 20.

-C[<num>]

En plus de -M, détecte les lignes déplacées ou copiées depuis d'autres fichiers qui ont été modifiés dans le même commit. C'est utile quand vous réorganisez votre programme et déplacez du code entre les fichiers. Quand cette option est donnée deux fois, la commande recherche en plus les copies depuis d'autres fichiers dans le commit qui crée le fichier. Quand cette option est donnée trois fois, la commande recherche en plus les copies depuis d'autres fichiers dans n'importe quel commit.

<num> est optionnel mais c'est la borne inférieure du nombre de caractères alphanumériques que Git doit détecter comme déplacés/copiés entre les fichiers pour associer ces lignes au commit parent. Et la valeur par défaut est 40. S'il y a plus d'une -C option donnée, l'argument <num> du dernier -C prendra effet.

--ignore-rev <rev>

Ignore les changements faits par la révision lors de l'attribution du blame, comme si le changement n'avait jamais eu lieu. Les lignes qui ont été changées ou ajoutées par un commit ignoré seront attribuées au commit précédent qui a changé cette ligne ou les lignes voisines. Cette option peut être spécifiée plusieurs fois pour ignorer plus d'une révision. Si l'option de configuration blame.markIgnoredLines est définie, alors les lignes qui ont été changées par un commit ignoré et attribuées à un autre commit seront marquées avec un ? dans la sortie de blame. Si l'option de configuration blame.markUnblamableLines est définie, alors ces lignes touchées par un commit ignoré que nous n'avons pas pu attribuer à une autre révision sont marquées avec un *. Dans les modes porcelain, nous imprimons ignored et unblamable sur une nouvelle ligne respectivement.

--ignore-revs-file <file>

Ignore les révisions listées dans file, qui doit être dans le même format qu'un fsck.skipList. Cette option peut être répétée, et ces fichiers seront traités après tous les fichiers spécifiés avec l'option de configuration blame.ignoreRevsFile . Un nom de fichier vide, "",t de révisions à partir des fichiers précédemment traités.

--color-lines

Colorie différemment les annotations de lignes dans le format par défaut si elles proviennent du même commit que la ligne précédente. Cela facilite la distinction des blocs de code introduits par différents commits. La couleur par défaut est le cyan et peut être ajustée à l'aide de l'option de configuration color.blame.repeatedLines .

--color-by-age

Colorie les annotations de lignes en fonction de l'ancienneté de la ligne dans le format par défaut. L'option de configuration color.blame.highlightRecent contrôle la couleur utilisée pour chaque plage d'ancienneté.

-h

Affiche le message d'aide.
