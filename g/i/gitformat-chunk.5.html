NOM

gitformat-chunk - Formats de fichiers basés sur des blocs

SYNOPIS

Utilisé par gitformat-commit-graph(5) et le format « MIDX » (voir la documentation du format de paquet dans gitformat-pack(5)).

DESCRIPTION

Certains formats de fichiers dans Git utilisent un concept commun de « blocs » (chunks) pour décrire des sections du fichier. Cela permet un accès structuré à un grand fichier en analysant une petite « table des matières » pour les données restantes. Ce format commun est utilisé par les fichiers commit-graph et multi-pack-index. Voir le format multi-pack-index dans gitformat-pack(5) et le format commit-graph dans gitformat-commit-graph(5) pour savoir comment ils utilisent les blocs pour décrire des données structurées.

Un format de fichier basé sur des blocs commence par des informations d'en-tête spécifiques à ce format. Cet en-tête doit contenir suffisamment d'informations pour identifier le type de fichier, la version du format et le nombre de blocs dans le fichier. À partir de ces informations, le fichier peut déterminer le début de la région basée sur des blocs.

La région basée sur des blocs commence par une table des matières décrivant où chaque bloc commence et se termine. Elle se compose de (C+1) lignes de 12 octets chacune, où C est le nombre de blocs. Considérez le tableau suivant :

| ID du bloc (4 octets) | Décalage du bloc (8 octets) |
|---------------------|-----------------------------|
| ID[0]               | OFFSET[0]                   |
| ...                 | ...                         |
| ID[C]               | OFFSET[C]                   |
| 0x0000              | OFFSET[C+1]                 |

Chaque ligne se compose d'un identifiant de bloc (ID) de 4 octets et d'un décalage de 8 octets. Chaque entier est stocké en ordre d'octet réseau.

L'identifiant de bloc ID[i] est une étiquette pour les données stockées dans ce fichier de OFFSET[i] (inclus) à OFFSET[i+1] (exclus). Ainsi, la taille du i-ème bloc est égale à la différence entre `OFFSET[i+1] et OFFSET[i]. Cela nécessite que les données des blocs apparaissent de manière contiguë dans le même ordre que la table des matières.

La dernière entrée de la table des matières doit être quatre octets nuls. Cela confirme que la table des matières se termine et fournit le décalage de la fin des données basées sur des blocs.

Note : Le format basé sur des blocs s'attend à ce que le fichier contienne au moins un hash final après OFFSET[C+1].

Les fonctions de manipulation des formats de fichiers basés sur des blocs sont déclarées dans chunk-format.h. L'utilisation de ces méthodes fournit des vérifications supplémentaires qui aident les développeurs lors de la création de nouveaux formats de fichiers.

ÉCRITURE DES FORMATS DE FICHIER BASÉS SUR DES BLOCS

Pour écrire un format de fichier basé sur des blocs, créez un struct chunkfile en appelant init_chunkfile() et passez un pointeur vers un struct hashfile. L'appelant est responsable de l'ouverture du hashfile et de l'écriture des informations d'en-tête afin que le format du fichier soit identifiable avant le début du format basé sur des blocs.

Ensuite, appelez add_chunk() pour chaque bloc destiné à l'écriture. Cela remplit le chunkfile avec des informations sur l'ordre et la taille de chaque bloc à écrire. Fournissez un pointeur de fonction chunk_write_fn pour effectuer l'écriture des données du bloc sur demande.

Appelez write_chunkfile() pour écrire la table des matières dans le hashfile, suivie de chaque bloc. Cela vérifiera que chaque bloc a écrit la quantité de données attendue afin que la table des matières soit correcte.

Enfin, appelez free_chunkfile() pour libérer les données du struct chunkfile. L'appelant est responsable de la finalisation du hashfile en écrivant le hash final et en fermant le fichier.

LECTURE DES FORMATS DE FICHIER BASÉS SUR DES BLOCS

Pour lire un format de fichier basé sur des blocs, le fichier doit être ouvert en tant que région mappée en mémoire. L'API de format de bloc s'attend à ce que l'intégralité du fichier soit mappée en tant que région mémoire contiguë.

Initialisez un pointeur vers un struct chunkfile avec init_chunkfile(NULL).

Après avoir lu les informations d'en-tête depuis le début du fichier, y compris le nombre de blocs, appelez read_table_of_contents() pour remplir le struct chunkfile avec la liste des blocs, leurs décalages et leurs tailles.

Extrayez les informations des données pour chaque bloc en utilisant pair_chunk() ou read_chunk():

•pair_chunk() assigne à un pointeur donné l'emplacement à l'intérieur du fichier mappé en mémoire correspondant au décalage de ce bloc. Si le bloc n'existe pas, le pointeur n'est pas modifié.
•read_chunk() prend un pointeur de fonction chunk_read_fn et l'appelle avec le pointeur initial et les informations de taille appropriés. La fonction n'est pas appelée si le bloc n'existe pas. Utilisez cette méthode pour lire les blocs si vous avez besoin d'effectuer une analyse immédiate ou si vous avez besoin d'exécuter une logique basée sur la taille du bloc.

Après avoir appelé ces méthodes, appelez free_chunkfile() pour libérer les données du struct chunkfile. Cela ne fermera pas la région mappée en mémoire. Les appelants sont censés conserver la propriété de ces données pendant la période pendant laquelle les pointeurs dans la région sont nécessaires.

EXEMPLES

Ces formats de fichiers utilisent l'API de format de bloc et peuvent servir d'exemples pour de futurs formats :

•commit-graph : voir write_commit_graph_file() et parse_commit_graph() dans commit-graph.c pour savoir comment l'API de format de bloc est utilisée pour écrire et analyser le format de fichier commit-graph documenté dans le format de fichier commit-graph de gitformat-commit-graph(5).
•multi-pack-index : voir write_midx_internal() et load_multi_pack_index() dans midx.c pour savoir comment l'API de format de bloc est utilisée pour écrire et analyser le format de fichier multi-pack-index documenté dans la section du format de fichier multi-pack-index de gitformat-pack(5).
