NOM

git-rebase - Réappliquer les commits sur une autre base

SYNTAXE

git rebase [-i | --interactive] [<options>] [--exec <cmd>]
        [--onto <nouvelle_base> | --keep-base] [<upstream> [<branche>]]
git rebase [-i | --interactive] [<options>] [--exec <cmd>] [--onto <nouvelle_base>]
        --root [<branche>]
git rebase (--continue|--skip|--abort|--quit|--edit-todo|--show-current-patch)

DESCRIPTION

Transplante une série de commits sur un point de départ différent. Vous pouvez également utiliser git rebase pour réordonner ou combiner des commits : voir le MODE INTERACTIF ci-dessous pour savoir comment faire.

Par exemple, imaginez que vous ayez travaillé sur la branche topic dans cet historique, et que vous souhaitiez rattraper le travail effectué sur la branche master.

          A---B---C topic
         /
    D---E---F---G master

Vous voulez transplanter les commits que vous avez faits sur topic depuis qu'elle a divergé de master (c'est-à-dire A, B et C), par-dessus la branche master actuelle. Vous pouvez le faire en exécutant git rebase master pendant que la branche topic est sélectionnée. Si vous souhaitez rebaser topic alors que vous êtes sur une autre branche, git rebase master topic est un raccourci pour git checkout topic && git rebase master.

                  A'--B'--C' topic
                 /
    D---E---F---G master

En cas de conflit de fusion lors de ce processus, git rebase s'arrêtera au premier commit problématique et laissera des marqueurs de conflit. Si cela se produit, vous pouvez faire l'une de ces choses :

1.Résolvez le conflit. Vous pouvez utiliser git diff pour trouver les marqueurs (<<<<<<) et effectuer des modifications pour résoudre le conflit. Pour chaque fichier modifié, vous devez indiquer à Git que le conflit a été résolu. Vous pouvez marquer le conflit comme résolu avec git add <nom_fichier>. Après avoir résolu tous les conflits, vous pouvez continuer le processus de rebasage avec 
git rebase --continue
2.Arrêtez l'opération git rebase et remettez votre branche dans son état d'origine avec 
git rebase --abort
3.Ignorez le commit qui a causé le conflit de fusion avec 
git rebase --skip

Si vous ne spécifiez pas d'<upstream> sur lequel baser, l'amont configuré dans les options branch.<nom>.remote et branch.<nom>.merge sera utilisé (voir git-config(1) pour les détails) et l'option --fork-point sera présumée. Si vous n'êtes actuellement sur aucune branche ou si la branche actuelle n'a pas d'amont configuré, le rebasage échouera.

Voici une description simplifiée de ce que fait git rebase <upstream> :

1.Créez une liste de tous les commits sur votre branche actuelle depuis qu'elle a divergé de <upstream> et qui n'ont pas de commit équivalent dans <upstream>.
2.Sélectionnez <upstream> avec l'équivalent de git checkout --detach <upstream>.
3.Réappliquez les commits, un par un, dans l'ordre. Cela ressemble à l'exécution de git cherry-pick <commit> pour chaque commit. Voir REBASAGE DES FUSIONS pour savoir comment les fusions sont gérées.
4.Mettez à jour votre branche pour qu'elle pointe vers le commit final avec l'équivalent de git checkout -B <branche>.

Note

Au démarrage du rebasage, ORIG_HEAD est défini pour pointer vers le commit à la pointe de la branche à rebaser. Cependant, ORIG_HEAD n'est pas garanti de pointer toujours vers ce commit à la fin du rebasage si d'autres commandes modifiant ORIG_HEAD (comme git reset) sont utilisées pendant le rebasage. La pointe de branche précédente, cependant, est accessible via le reflog de la branche actuelle (c'est-à-dire @{1}, voir gitrevisions(7).

We can get this using the following command:

Another example of --onto option is to rebase part of a branch. If we have the following situation:

                            H---I---J topicB
                           /
                  E---F---G  topicA
                 /
    A---B---C---D  master

then the command

git rebase --onto master topicA topicB

would result in:

                 H'--I'--J'  topicB
                /
                | E---F---G  topicA
                |/
    A---B---C---D  master

This is useful when topicB does not depend on topicA.

A range of commits could also be removed with rebase. If we have the following situation:

    E---F---G---H---I---J  topicA

then the command

git rebase --onto topicA~5 topicA~3 topicA

would result in the removal of commits F and G:

    E---H'---I'---J'  topicA

This is useful if F and G were flawed in some way, or should not be part of topicA. Note that the argument to --onto and the <upstream> parameter can be any valid commit-ish.

OPTIONS DE MODE

Les options de cette section ne peuvent pas être utilisées avec une autre option, ni entre elles :

--continue

Redémarre le processus de rebasage après avoir résolu un conflit de fusion.

--skip

Redémarre le processus de rebasage en ignorant le patch actuel.

--abort

Annule l'opération de rebasage et réinitialise HEAD à la branche d'origine. Si <branche> a été fournie au démarrage de l'opération de rebasage, alors HEAD sera réinitialisé à <branche>. Sinon, HEAD sera réinitialisé à son état au moment du démarrage de l'opération de rebasage.

--quit

Annule l'opération de rebasage mais HEAD n'est pas réinitialisé à la branche d'origine. L'index et l'arbre de travail sont également laissés inchangés. Si une entrée d'attache temporaire a été créée en utilisant --autostash, elle sera sauvegardée dans la liste des attaches.

--edit-todo

Modifie la liste des tâches pendant un rebasage interactif.

--show-current-patch

Affiche le patch actuel lors d'un rebasage interactif ou lorsque le rebasage s'arrête à cause de conflits. C'est l'équivalent de git show REBASE_HEAD.

DIFFÉRENCES COMPORTEMENTALES

git rebase possède deux backends principaux : apply et merge. (Le backend apply était auparavant connu sous le nom de backend am, mais le nom prêtait à confusion car il ressemble à un verbe au lieu d'un nom. De plus, le backend merge était auparavant connu sous le nom de backend interactif, mais il est maintenant utilisé aussi pour les cas non interactifs. Les deux ont été renommés en fonction de fonctionnalités de bas niveau qui les sous-tendaient.) Il existe quelques différences subtiles dans la manière dont ces deux backends se comportent :

Commits vides

Le backend apply rejette malheureusement les commits intentionnellement vides, c'est-à-dire les commits qui ont commencé vides, bien que ceux-ci soient rares en pratique. Il rejette également les commits qui deviennent vides et n'a aucune option pour contrôler ce comportement.

Le backend merge conserve les commits intentionnellement vides par défaut (bien qu'avec -i ils soient marqués comme vides dans l'éditeur de la liste des tâches, ou ils peuvent être supprimés automatiquement avec --no-keep-empty).

Similaire au backend apply, par défaut le backend merge rejette les commits qui deviennent vides sauf si -i/--interactive est spécifié (auquel cas il s'arrête et demande à l'utilisateur quoi faire). Le backend merge a également une option --empty=(drop|keep|stop) pour changer le comportement de gestion des commits qui deviennent vides.

Détection de renommage de répertoire

En raison de l'absence d'informations d'arbre précises (résultant de la construction d'ancêtres factices avec les informations limitées disponibles dans les correctifs), la détection de renommage de répertoire est désactivée dans le backend apply. La désactivation de la détection de renommage de répertoire signifie que si un côté de l'historique renomme un répertoire

répertoire et l'autre ajoute de nouveaux fichiers à l'ancien répertoire, alors les nouveaux fichiers seront laissés derrière dans l'ancien répertoire sans aucun avertissement au moment du rebase indiquant que vous pourriez vouloir déplacer ces fichiers vers le nouveau

répertoire.

La détection de renommage de répertoire fonctionne avec le backend merge pour vous fournir

des avertissements
dans de tels cas.

Context

e

Le backend apply fonctionne en créant une séquence de patches (en appelant format-patch en interne), puis en appliquant les patches en séquence (en appelant am en interne). Les patches sont composés de multiples hunks, chacun avec des numéros de ligne, une région de contexte, et les changements réels. Les numéros de ligne doivent être pris avec un certain décalage, car l'autre côté aura probablement inséré ou supprimé des lignes plus tôt dans le fichier. La région de contexte est censée aider à trouver comment ajuster les numéros de ligne afin de appliquer les changements aux bonnes lignes. Cependant, si plusieurs zones du code ont les mêmes lignes de contexte environnantes, la mauvaise peut être choisie. Il existe des cas réels où cela a causé des commits à être réappliqués incorrectement sans conflits signalés. Régler diff.context à une valeur plus grande peut prévenir ce type de problèmes, mais augmente la chance de conflits erronés (car cela nécessitera plus de lignes de contexte correspondant pour appliquer)

.

Le backend merge fonctionne avec une copie complète de chaque

fichier pertinent, l'isol

Le mécanisme de fusion (git merge et git pull commandes) permet au backend stratégies de fusion d'être choisies avec l'option -s. Certaines stratégies peuvent aussi prendre leurs propres options, qui peuvent être passées en donnant -X<option> arguments à git merge et/ou git pull

or

t
C'est la stratégie de fusion par défaut lors du pull ou de la fusion d'une branche. Cette stratégie ne peut résoudre que deux têtes en utilisant un algorithme de fusion 3-way. Quand il y a plus d'un ancêtre commun pouvant être utilisé pour la fusion 3-way, elle crée un arbre fusionné des ancêtres communs et utilise cela comme arbre de référence pour la fusion 3-way. Il a été rapporté que cela résulte en moins de conflits de fusion sans causer de fausses fusions par des tests faits sur de vrais commits de fusion pris de l'historique de développement du noyau Linux 2.6. De plus, cette stratégie peut détecter et gérer les fusions impliquant des renommages. Elle n'utilise pas les copies détectées. Le nom de cet algorithme est un acronyme ("Ostensibly Recursive’s Twin") et vient du fait qu'il a été écrit comme un remplacement pour l'algorithme par défaut précédent, recursive.

Dans le cas où le chemin est un sous-module, si le commit de sous-module utilisé d'un côté de la fusion est un descendant du commit de sous-module utilisé de l'autre côté de la fusion, Git essaie d'avance rapide vers le descendant. Sinon, Git traitera ce cas comme un conflit, suggérant comme résolution un commit de sous-module qui est descendant des commits en conflit, si un

existe.

RÉCUPÉRATION À PARTIR D'UNE REBASE

AMONT

Rebaser (ou toute autre forme de réécriture) une branche sur laquelle d'autres ont basé leur travail est une mauvaise idée : quiconque en aval est forcé de corriger manuellement son historique. Cette section explique comment effectuer la correction du point de vue de l'aval. La vraie correction, cependant, serait devoid rebase en amont à la

base.

Pour illustrer, supposez que vous vous trouviez dans une situation où quelqu'un développe une branche sous-système, et que vous travaillez sur un sujet qui dépend de ce sous-système. Vous pourriez vous retrouver avec un historique comme celui-ci

: 
    o---o---o---o---o---o---o---o  master
         \
o---o---o---o---o sous-système
\ *---*---* sujet

         \
\ o---o---o---o---o o'--o'--o'--o'--o' sous-système
\ *---*---* sujet

Si vous continuez maintenant le développement comme d'habitude, et finissez par fusionner sujet dans sous-système, les commits de sous-système resteront dupliqués à jamais

: 
    o---o---o---o---o---o---o---o  master
         \                       \
          o--
-o---o---o---o o'--o'--o'--o'--o'--M sous-système \
/ *---*---*-..........-*--* sujet

De telles duplications sont généralement mal vues car elles encombrent l'historique, le rendant plus difficile à suivre. Pour nettoyer les choses, vous devez transplanter les commits sur sujet vers la nouvelle pointe de sous-système, c'est-à-dire rebase sujet. Cela devient un effet domino : quiconque est en aval de sujet est forcé de rebase aussi, et ainsi de suite

!

Il existe deux types de correctifs, discutés dans les sous-sections suivantes

:

Cas facile : Les changements sont littéralement les

mêmes.
Cela se produit si le rebase du sous-système était un simple rebase et n'avait pas de
conflits.

Cas difficile : Les changements ne sont pas les

mêmes.
Cela se produit si le rebase du sous-système avait des conflits, ou a utilisé --interactive pour omettre, éditer, squash ou fixup des commits ; ou si l'amont a utilisé l'une des commandes commit --amend, reset, ou une commande de réécriture complète de l'historique comme filter-rep
o[2].

Le cas

facile

Ne fonctionne que si les changements (patch IDs basés sur le contenu du diff) sur sous-système sont littéralement les mêmes avant et après le rebase que ceux que sous-système a

faits.

Dans ce cas, le correctif est facile car git rebase sait ignorer les changements déjà présents dans le nouvel amont (sauf si --reapply-cherry-picks est spécifié). Donc si vous dites (en supposant que vous êtes sur sujet

Le cas

difficile

Les choses deviennent plus compliquées si les changements de sous-système ne correspondent pas exactement à ceux d'avant le

Bien qu'une « récupération en cas facile » semble parfois réussie même dans le cas difficile, elle peut avoir des conséquences imprévues. Par exemple, un commit qui a été supprimé via git rebase --interactive sera ressus

La commande de rebase interactive a été conçue à l'origine pour gérer des séries de patches individuelles. Dans l'exemple suivant, le développeur travaille sur une branche de sujet qui refactorise la façon dont les boutons sont définis, et sur une autre branche de sujet qui utilise cette refactorisation pour implémenter un bouton « Signaler un bug ». La commande label associe un label au HEAD courant lorsque cette commande est exécutée. Ces labels sont créés comme des refs locales à l'arbre de travail (refs/rewritten/<label>) qui seront supprimées lorsque le rebase se termine. Ainsi, les opérations de rebase dans plusieurs arbres de travail liés au même dépôt ne se gênent pas les unes les autres. Si la commande label échoue, elle est immédiatement replanifiée, avec un message utile indiquant comment

procéder.

La commande reset réinitialise le HEAD, l'index et l'arbre de travail à la révision spécifiée. Elle est similaire à un exec git reset --hard <label>, mais refuse d'écraser les fichiers non suivis. Si la commande reset échoue, elle est immédiatement replanifiée, avec un message utile indiquant comment éditer la liste todo (cela se produit généralement quand une commande reset a été insérée manuellement dans la liste todo et contient une faute de frappe)

.

La commande merge fusionnera la ou les révisions spécifiées dans ce qui est HEAD à ce moment-là. Avec -C <commit-original>, le message de commit de la fusion spécifiée sera utilisé. Lorsque le -C est changé en -c minuscule, le message sera ouvert dans un éditeur après une fusion réussie afin que l'utilisateur puisse

l'éditer.

Si une commande merge échoue pour toute autre raison que des conflits de fusion (c'est-à-dire lorsque l'opération de fusion n'a même pas commencé), elle est immédiatement

replanifiée.

Par défaut, la commande merge utilisera la stratégie de fusion ort pour les fusions régulières, et octopus pour les fusions octopus. fusionner.

CONFIGURATION

Les options suivantes peuvent être configurées dans git-config(1) et sont disponibles sous la section rebase.

rebase.backend

Backend par défaut à utiliser pour le rebasage. Les choix possibles sont apply ou merge. À l'avenir, si le backend merge acquiert toutes les capacités restantes du backend apply, ce paramètre pourra ne plus être utilisé.

rebase.stat

Indique s'il faut afficher un diffstat de ce qui a changé en amont depuis le dernier rebasage. Par défaut, c'est faux.

rebase.autoSquash

Si défini à vrai, active par défaut l'option --autosquash de git-rebase(1) en mode interactif. Ceci peut être outrepassé avec l'option --no-autosquash.

rebase.autoStash

Lorsque défini à vrai, crée automatiquement une entrée de stash temporaire avant le début de l'opération et l'applique après la fin de l'opération. Cela signifie que vous pouvez exécuter rebase sur un arbre de travail sale. Cependant, utilisez avec prudence : l'application finale du stash après un rebasage réussi pourrait entraîner des conflits non triviaux. Cette option peut être outrepassée par les options --no-autostash et --autostash de git-rebase(1). Par défaut, c'est faux.

rebase.updateRefs

Si défini à vrai, active l'option --update-refs par défaut.

rebase.missingCommitsCheck

Si défini à "warn", git rebase -i affichera un avertissement si des commits sont supprimés (par exemple, une ligne a été supprimée), mais le rebasage continuera. S'il est défini à "error", il affichera l'avertissement précédent et arrêtera le rebasage. git rebase --edit-todo pourra alors être utilisé pour corriger l'erreur. S'il est défini à "ignore", aucune vérification n'est effectuée. Pour supprimer un commit sans avertissement ni erreur, utilisez la commande drop dans la liste des tâches. Par défaut, c'est "ignore".

rebase.instructionFormat

Une chaîne de format, telle que spécifiée dans git(1), à utiliser pour la liste des tâches pendant un rebasage interactif. Le format aura automatiquement le hash du commit préfixé au format.

rebase.abbreviateCommands

Si défini à vrai, git rebase utilisera des noms de commandes abrégés dans la liste des tâches, ce qui donnera quelque chose comme ceci : 
        p deadbee La description d'une ligne du commit
        p fa1afe1 La description d'une ligne du commit suivant
        ...

au lieu de :

        pick deadbee La description d'une ligne du commit
        pick fa1afe1 La description d'une ligne du commit suivant
        ...

Par défaut, c'est faux.

rebase.rescheduleFailedExec

Planifie automatiquement les commandes exec qui ont échoué. Ceci n'a de sens qu'en mode interactif (ou lorsqu'une option --exec a été fournie). Ceci est identique à la spécification de l'option --reschedule-failed-exec.

rebase.forkPoint

Si défini à faux, utilise l'option --no-fork-point par défaut.

rebase.rebaseMerges

Indique si et comment l'option --rebase-merges doit être définie par défaut. Peut être rebase-cousins, no-rebase-cousins, ou une valeur booléenne. Définir à vrai ou à no-rebase-cousins est équivalent à --rebase-merges=no-rebase-cousins, définir à rebase-cousins est équivalent à --rebase-merges=rebase-cousins, et définir à faux est équivalent à --no-rebase-merges. Passer --rebase-merges sur la ligne de commande, avec ou sans argument, outrepassera toute configuration rebase.rebaseMerges.

rebase.maxLabelLength

Lors de la génération de noms d'étiquettes à partir des sujets de commits, tronque les noms à cette longueur. Par défaut, les noms sont tronqués à un peu moins que NAME_MAX (pour permettre par exemple l'écriture de fichiers .lock pour les refs lâches correspondantes).

sequence.editor

Éditeur de texte utilisé par git rebase -i pour éditer le fichier d'instructions de rebasage. La valeur est destinée à être interprétée par le shell lorsqu'elle est utilisée. Elle peut être outrepassée par la variable d'environnement GIT_SEQUENCE_EDITOR. Lorsqu'elle n'est pas configurée, l'éditeur de message de commit par défaut est utilisé à la place.
