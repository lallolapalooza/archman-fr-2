DESCRIPTIO

Compare le contenu et le mode des blobs trouvés dans un objet arbre avec les fichiers suivis correspondants dans

l'arbre de travail, ou avec les chemins correspondants dans l'index. Lorsque des arguments <path> sont présent
s, compare uniquement les chemins correspondant à ces motifs. Sinon, tous les fichiers suivis sont comparés.

--summar

y lass="Bd-indent">Afficher un résumé condensé des informations d'en-tête étendues telles que les créations, renommages et changements de mode.

--patch-with-stat

Synonyme de -p --stat.

-z

Lorsque --raw, --numstat, --name-only ou --name-status ont été donnés, ne pas transformer les chemins et utiliser NULs comme terminaisons de champ de sortie.

Sans cette option, les chemins avec des caractères "inhabituels" sont cités comme expliqué pour la variable de configuration core.quotePath (voir git-config(1)).

--name-only

Afficher uniquement le nom de chaque fichier modifié dans l'arbre post-image (état après modification). Les noms de fichiers sont souvent encodés en UTF-8. Pour plus d'informations, voir la discussion sur l'encodage dans la page de manuel de git-log(1).

--name-status

Afficher uniquement le(s) nom(s) et le statut de chaque fichier modifié. Voir la description de l'option --diff-filter pour ce que signifient les lettres de statut. Tout comme --name-only, les noms de fichiers sont souvent encodés en UTF-8.

--submodule[=<format>]

Spécifie comment afficher les différences dans les sous-modules. Lors de la spécification de --submodule=short, le format short est utilisé. Ce format affiche uniquement les noms des commits au début et à la fin de la plage. Lorsque --submodule ou --submodule=log est spécifié, le format log est utilisé. Ce format liste les commits dans la plage comme le fait le résumé de git-submodule(1). Lorsque --submodule=diff est spécifié, le format diff est utilisé. Ce format affiche un diff en ligne des changements dans le contenu du sous-module entre la plage de commits. La valeur par défaut est diff.submodule ou le format short si l'option de configuration est non définie.

--color[=<when>]

Afficher le diff en couleur. --color (c'est-à-dire sans =<when>) est équivalent à --color=always. <when> peut être always, never, ou auto.

--no-color

Désactiver le diff en couleur. C'est équivalent à --color=never.

--color-moved[=<mode>]

Les lignes de code déplacées sont colorées différemment. Le <mode> est no par défaut si l'option n'est pas donnée et zebra si l'option est donnée sans mode. Le mode doit être l'un des suivants :

no

Les lignes déplacées ne sont pas mises en évidence.

default

Est un synonyme de zebra. Cela pourrait changer pour un mode plus pertinent à l'avenir.

plain

Toute ligne ajoutée à un endroit et supprimée à un autre sera colorée avec color.diff.newMoved. De même, color.diff.oldMoved sera utilisée pour les lignes supprimées qui sont ajoutées ailleurs dans le diff. Ce mode détecte toute ligne déplacée, mais il n'est pas très utile lors d'une revue pour déterminer si un bloc de code a été déplacé sans permutation.

blocks

Des blocs de texte déplacé d'au moins 20 caractères alphanumériques sont détectés de manière gourmande. Les blocs détectés sont peints en utilisant la couleur color.diff.(old|new)Moved. Les blocs adjacents ne peuvent pas être différenciés.

zebra

Des blocs de texte déplacé sont détectés comme en mode blocks. Les blocs sont peints en utilisant soit la couleur color.diff.(old|new)Moved, soit color.diff.(old|new)MovedAlternative. Le changement entre les deux couleurs indique qu'un nouveau bloc a été détecté.

dimmed-zebra

Similaire à zebra, mais un estompage supplémentaire des parties non intéressantes du code déplacé est effectué. Les lignes frontalières de deux blocs adjacents sont considérées comme intéressantes, le reste est non intéressant. dimmed_zebra est un synonyme obsolète.

--no-color-moved

Désactiver la détection de déplacement. Ceci peut être utilisé pour outrepasser les paramètres de configuration. C'est équivalent à --color-moved=no.

--color-moved-ws=<mode>,...

Configure comment les espaces blancs sont ignorés lors de la détection de déplacement pour --color-moved. Ces modes peuvent être donnés sous forme de liste séparée par des virgules :

no

Ne pas ignorer les espaces blancs lors de la détection de déplacement.

ignore-space-at-eol

Ignorer les changements d'espaces blancs en fin de ligne.

ignore-space-change

Ignorer les changements dans la quantité d'espaces blancs. Ceci ignore les espaces blancs en fin de ligne et considère toutes les autres séquences d'un ou plusieurs caractères d'espaces blancs comme équivalentes.

ignore-all-space

Ignorer les espaces blancs lors de la comparaison des lignes. Ceci ignore les différences même si une ligne a des espaces blancs là où l'autre ligne n'en a pas.

allow-indentation-change

Ignorer initialement tout espace blanc dans la détection de mouvement, puis regrouper les blocs de code déplacé uniquement en un bloc si le changement d'espace blanc est le même par ligne. Ceci est incompatible avec les autres modes.

--no-color-moved-ws

Ne pas ignorer les espaces blancs lors de la détection de déplacement. Ceci peut être utilisé pour outrepasser les paramètres de configuration. C'est équivalent à --color-moved-ws=no.

--word-diff[=<mode>]

Par défaut, les mots sont délimités par des espaces blancs ; voir --word-diff-regex ci-dessous. Le <mode> est plain par défaut et doit être l'un des suivants :

color

Mettre en évidence les mots modifiés en utilisant uniquement les couleurs. Implique --color.

plain

Afficher les mots comme [-supprimé-] et {ajouté}. Ne fait aucune tentative pour échapper les délimiteurs s'ils apparaissent dans l'entrée, donc la sortie peut être ambiguë.

porcelain

Utiliser un format spécial basé sur les lignes, destiné à la consommation par script. Les séquences ajoutées/supprimées/inchangées sont imprimées dans le format de diff unifié habituel, commençant par un caractère +/-/` ` au début de la ligne et s'étendant jusqu'à la fin de la ligne. Les nouvelles lignes dans l'entrée sont représentées par un tilde ~ sur une ligne séparée.

none

Désactiver à nouveau le diff de mots.

Notez que malgré le nom du premier mode, la couleur est utilisée pour mettre en évidence les parties modifiées dans tous les modes si elle est activée.

--word-diff-regex=<regex>

Utiliser <regex> pour décider de ce qu'est un mot, au lieu de considérer les séquences de non-espaces blancs comme un mot. Implique également --word-diff sauf s'il était déjà activé.

Chaque correspondance non chevauchante de la <regex> est considérée comme un mot. Tout ce qui se trouve entre ces correspondances est considéré comme un espace blanc et est ignoré (!) aux fins de la recherche de différences. Vous pourriez vouloir ajouter |[^[:space:]] à votre expression régulière pour vous assurer qu'elle correspond à tous les caractères non blancs. Une correspondance qui contient une nouvelle ligne est silencieusement tronquée (!) à la nouvelle ligne.

Par exemple, --word-diff-regex=. traitera chaque caractère comme un mot et, par conséquent, affichera les différences caractère par caractère.

L'expression régulière peut également être définie via un pilote de diff ou une option de configuration, voir gitattributes(5) ou git-config(1). La donner explicitement remplace tout pilote de diff ou paramètre de configuration. Les pilotes de diff remplacent les paramètres de configuration.

--color-words[=<regex>]

Équivalent à --word-diff=color plus (si une regex a été spécifiée) --word-diff-regex=<regex>.

--no-renames

Désactiver la détection de renommage, même lorsque le fichier de configuration le spécifie par défaut.

--rename-empty, --no-rename-empty

Indique s'il faut utiliser des blobs vides comme source de renommage.

--check

Avertir si des modifications introduisent des marqueurs de conflit ou des erreurs d'espaces blancs. Ce qui est considéré comme des erreurs d'espaces blancs est contrôlé par la configuration core.whitespace. Par défaut, les espaces blancs en fin de ligne (y compris les lignes constituées uniquement d'espaces blancs) et un caractère espace immédiatement suivi d'un caractère tabulation dans l'indentation initiale de la ligne sont considérés comme des erreurs d'espaces blancs. Se termine avec un statut non nul si des problèmes sont trouvés. Non compatible avec --exit-code.

--ws-error-highlight=<kind>

Mettre en évidence les erreurs d'espaces blancs dans les lignes de context, old (anciennes) ou new (nouvelles) du diff. Plusieurs valeurs sont séparées par des virgules, none réinitialise les valeurs précédentes, default réinitialise la liste à new et all est un raccourci pour old,new,context. Lorsque cette option n'est pas donnée, et que la variable de configuration diff.wsErrorHighlight n'est pas définie, seules les erreurs d'espaces blancs dans les lignes new sont mises en évidence. Les erreurs d'espaces blancs sont colorées avec color.diff.whitespace.

--full-index

Au lieu de la première poignée de caractères, afficher les noms complets des objets blob pré- et post-image sur la ligne "index" lors de la génération de la sortie au format patch.

--binary

En plus de --full-index, générer un diff binaire qui peut être appliqué avec git-apply. Implique --patch.

--abbrev[=<n>]

Au lieu d'afficher le nom hexadécimal complet de l'objet de 40 octets dans le format brut du diff et les lignes d'en-tête de diff-tree, afficher le plus court préfixe d'au moins <n> chiffres hexadécimaux qui identifie de manière unique l'objet. Dans le format de sortie de diff-patch, --full-index a une priorité plus élevée, c'est-à-dire que si --full-index est spécifié, les noms complets des blobs seront affichés indépendamment de --abbrev. Un nombre de chiffres non par défaut peut être spécifié avec --abbrev=<n>.

-B[<n>][/<m>], --break-rewrites[=[<n>][/<m>]]

Diviser les modifications de réécriture complète en paires de suppression et de création. Ceci a deux objectifs :

Cela affecte la manière dont un changement qui équivaut à une réécriture totale d'un fichier n'est pas considéré comme une série de suppressions et d'insertions mélangées avec très peu de lignes qui correspondent textuellement comme contexte, mais comme une seule suppression de tout l'ancien suivi d'une seule insertion de tout le nouveau, et le nombre <m> contrôle cet aspect de l'option -B (par défaut 60%). -B/70% spécifie que moins de 30% de l'original doit rester dans le résultat pour que Git le considère comme une réécriture totale (c'est-à-dire autrement le résultatpatch sera une série de suppressions et d'insertions mélangées avec des lignes de contexte)

.

Lorsqu'il est utilisé avec -M, un fichier entièrement réécrit est également considéré comme source d'un renommage (habituellement -M ne considère comme source d'un renommage qu'un fichier qui a disparu), et le nombre <n> contrôle cet aspect de l'option -B (par défaut à 50%). -B20% spécifie qu'un changement avec addition et suppression représentant 20% ou plus de la taille

du fichier est éligible pour être pris comme so
urce possible d'un renommage vers un autre fichier.

-M[<n>], --find-renames[=<n>

]
Détecte les renommages. Si <n> est spécifié, il s'agit d'un seuil sur l'indice de similarité (c'est-à-dire le montant des additions/suppressions par rapport à la taille du fichier). Par exemple, -M90% signifie que Git doit considérer une paire suppression/addition comme un renommage si plus de 90% du fichier n'a pas changé. Sans un %, le nombre doit être lu comme une fraction, avec un point décimal devant lui. C'est-à-dire, -M5 devient 0.5, et est donc identique à -M50%. De même, -M05 est identique à -M5%. Pour limiter la détection aux renommages exacts, utilisez -M100%. L'indice de similarité par défaut est
50%.

-C[<n>], --find-copies[=<n>

]
Détecte les copies ainsi que les renommages. Voir aussi --find-copies-harder. Si <n> est spécifié, il a la même signification que pour -M<n>
.

--find-copies-harde

r
Pour des raisons de performance, par défaut, l'option -C trouve les copies uniquement si le fichier original de la copie a été modifié dans le même ensemble de changements. Ce drapeau fait inspecter les fichiers non modifiés comme candidats pour la source d'une copie. Il s'agit d'une opération très coûteuse pour les grands projets, utilisez-la donc avec précaution. Spécifier plus d'une fois l'option -C a le même
effet.

-D, --irreversible-delet

e
Omet l'image préalable pour les suppressions, c'est-à-dire n'affiche que l'en-tête mais pas le diff entre l'image préalable et /dev/null. Le patch résultant n'est pas destiné à être appliqué avec patch ou git apply ; c'est uniquement pour les personnes qui veulent se concentrer sur la revue du texte après le changement. De plus, la sortie manque évidemment d'informations suffisantes pour appliquer un tel patch à l'envers, même manuellement, d'où le nom de l'option.

Lorsqu'il est utilisé avec -B, omet également l'image préalable dans la partie suppression d'une paire suppression/créati

on
.

-l<num

>
Les options -M et -C impliquent certaines étapes préliminaires qui peuvent détecter à moindre coût des sous-ensembles de renommages/copies, suivies d'une partie de repli exhaustive qui compare toutes les destinations restantes non appariées à toutes les sources pertinentes. (Pour les renommages, seules les sources restantes non appariées sont pertinentes ; pour les copies, toutes les sources originales sont pertinentes.) Pour N sources et destinations, cette vérification exhaustive est en O(N^2). Cette option empêche la partie exhaustive de la détection de renommage/copie de s'exécuter si le nombre de fichiers source/destination impliqués dépasse le nombre spécifié. Par défaut à diff.renameLimit. Notez qu'une valeur de 0 est traitée comme
illimitée.

--diff-filter=[(A|C|D|M|R|T|U|X|B)...[*]

]
Sélectionne uniquement les fichiers qui sont Ajoutés (A), Copiés (C), Supprimés (D), Modifiés (M), Renommés (R), dont le type (c'est-à-dire fichier régulier, lien symbolique, sous-module, ...) a changé (T), sont Non fusionnés (U), sont Inconnus (X), ou dont l'appariement a été Rompu (B). Toute combinaison des caractères de filtre (y compris aucun) peut être utilisée. Lorsque * (Tous ou aucun) est ajouté à la combinaison, tous les chemins sont sélectionnés s'il y a un fichier qui correspond aux autres critères dans la comparaison ; s'il n'y a pas de fichier qui correspond aux autres critères, rien n'est sélectionné.

De plus, ces lettres majuscules peuvent être mises en minuscules pour exclure. Par exemple, --diff-filter=ad exclut les chemins ajoutés et

supprimés.

Notez que tous les diffs ne peuvent pas présenter tous les type

s. Par exemple, les entrées copiées et renommées ne peuvent
pas apparaître si la détection de ces types est désactivée.

-S<string

>
Recherche les différences qui changent le nombre d'occurrences de la <string> spécifiée (c'est-à-dire addition/suppression) dans un fichier. Destiné à l'usage des scripteurs.

C'est utile lorsque vous cherchez un bloc de code exact (comme une struct) et que vous voulez connaître l'historique de ce bloc depuis sa création : utilisez la fonctionnalité de manière itérative pour renvoyer le bloc intéressant de l'image préalable dans -S, et continuez jusqu'à obtenir la toute première version du

bloc.

Les fichiers bin

--pickaxe-al

l

g>.

--pickaxe-rege

x
Traite la <string> donnée à -S comme une expression rationnelle POSIX étendue à faire

Le NUL supplémentaire avant le chemin de l'image préalable dans le cas d'un renommage permet aux scripts lisant la sortie de déterminer si l'enregistrement en cours de lecture est un enregistrement à chemin unique ou un enregistrement de renommage/copie sans avoir à lire en avance. Après avoir lu les lignes ajoutées et supprimées, lire jusqu'au NUL fournirait le chemin, mais si c'est un NUL, l'enregistrement

montrera de

MODES

D'UTILISATION

Vous pouvez choisir de faire entièrement confiance au fichier d'index (en utilisant l'indicateur --cached) ou demander à la logique de diff d'afficher tout fichier qui ne correspond pas à l'

état stat comme étant "changé provisoirement"
. Ces deux opérations sont très utiles en effet.

MODE EN

CACHE

Si --cached est spécifié, cela vous permet de demander

: 
montre-moi les différences entre HEAD
et le contenu actuel de l'index (celui
que j'écrirais avec 'git write-tree')

Par exemple, supposons que vous avez travaillé dans votre répertoire de travail, mis à jour certains fichiers dans l'index et que vous êtes prêt à committer. Vous voulez voir exactement ce que vous allez committer, sans avoir à écrire un nouvel objet arbre et le comparer de cette manière, et pour cela, vous faites

simplement 
git diff-
index --ca
ched HEAD

Exemple : supposons que j'ai renommé commit.c en git-commit.c, et que j'ai fait un update-index pour que cela prenne effet dans le fichier d'index. git diff-files ne montrerait rien du tout, car le fichier d'index correspond à mon répertoire de travail. Mais faire un git diff-index le montre

: 
torvalds@ppc970:~/git> git diff-index --cached HEAD
:100644 000000 4161aecc6700a2eb579e842af
0b7f22b98443f74 0000000000000000000000000000000000000000 D commit.c :000000 100644 0000000
000000000000000000000000000000000 4161aecc6700a2eb579e842af0b7f22b98443f74 A git-commit.c

Vous voyez facilement que ce qui précède est un

renommage.

En fait, git diff-index --cached devrait toujours être entièrement équivalent à faire git write-tree et comparer le résultat. Sauf que celui-ci est bien plus pratique dans le cas où vous voulez juste vérifier où vous en

êtes.

Ainsi, faire un git diff-index --cached est fondamentalement très utile lorsque vous vous demandez "qu'ai-je déjà

marqué pour être committé, et quelle est
la différence avec un arbre précédent".

MODE SANS

CACHE

Le mode "sans cache" adopte une approche différente, et est potentiellement le plus utile des deux en ce que ce qu'il fait ne peut pas être émulé avec un git write-tree + git diff-tree. C'est donc le mode par défaut. La version sans cache pose la question

: 
montre-moi les différences entre HEAD et l
'arbre actuellement coché - contenu de l'
index _et_ fichiers qui ne sont pas à jour

ce qui est évidemment une question très utile aussi, car elle vous dit ce que vous pourriez committer. Encore une fois, la sortie correspond exactement à la sortie de git diff-tree -r, mais avec une

nuance.

La nuance est que si un fichier ne correspond pas à l'index, nous n'avons pas de stockage de référence pour lui, et nous utilisons le sha1 magique "tous zéros" pour l'indiquer. Supposons donc que vous ayez édité kernel/sched.c, mais que vous n'ayez pas encore fait de git update-index dessus - il n'y a pas d'"objet" associé au nouvel état, et vous obtenez

: 
torvalds@ppc970:~/v2.6/linux> git dif
f-index --abbrev HEAD :100644 100644
7476bb5ba 000000000 M kernel/sched.c

c'est-à-dire, cela montre que l'arbre a changé, et que kernel/sched.c n'est pas à jour et peut contenir de nouvelles choses. Le sha1 tous zéros signifie que pour obtenir le vrai diff, vous devez regarder l'objet dans le répertoire de travail directement plutôt que de faire un diff d'objet à

objet.

Note

Comme avec les autres commandes de ce type, git diff-index ne regarde pas réellement le contenu du fichier. Il se peut donc que kernel/sched.c n'ait pas réellement changé, et que ce soit simplement parce que vous l'avez touché. Dans les deux cas, c'est une note indiquant que vous devez git update-index pour

synchronis
er l'index.

Note

Vous pouvez avoir un mélange de fichiers affichés comme "a été mis à jour" et "est

encore sale dans le répertoire de travail" ensemble. Vous pouvez toujours dire qu
el fichier est dans quel état, car les "a été mis à jour" affichent un sha1 valide
, et les "pas en phase avec l'index" auront toujours le sha1 spécial tous zéros.
