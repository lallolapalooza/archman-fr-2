NOM

git-commit-tree - Crée un nouvel objet commit

SYNOPSIS

git commit-tree <arbre> [(-p <parent>)...]
git commit-tree [(-p <parent>)...] [-S[<keyid>]] [(-m <message>)...]
                  [(-F <fichier>)...] <arbre>

DESCRIPTION

Ceci n'est généralement pas ce qu'un utilisateur final souhaite exécuter directement. Voir git-commit(1) à la place.

Crée un nouvel objet commit basé sur l'objet arbre fourni et émet l'identifiant du nouvel objet commit sur la sortie standard. Le message du journal est lu depuis l'entrée standard, sauf si les options -m ou -F sont fournies.

Les options -m et -F peuvent être fournies un nombre quelconque de fois, dans n'importe quel ordre. Le message du journal du commit sera composé dans l'ordre dans lequel les options sont données.

Un objet commit peut avoir un nombre quelconque de parents. Avec exactement un parent, il s'agit d'un commit ordinaire. Avoir plus d'un parent fait du commit une fusion entre plusieurs lignes d'historique. Les commits initiaux (racine) n'ont pas de parents.

Alors qu'un arbre représente un état particulier d'un répertoire de travail, un commit représente cet état dans le « temps » et explique comment y parvenir.

Normalement, un commit identifierait un nouvel état « HEAD » et bien que Git ne se soucie pas de l'endroit où vous enregistrez la note sur cet état, en pratique nous avons tendance à simplement écrire le résultat dans le fichier vers lequel pointe .git/HEAD, afin que nous puissions toujours voir quel était le dernier état committé.

OPTIONS

<arbre>

Un objet arbre existant.

-p <parent>

Chaque -p indique l'identifiant d'un objet commit parent.

-m <message>

Un paragraphe dans le message du journal du commit. Cela peut être donné plus d'une fois et chaque <message> devient son propre paragraphe.

-F <fichier>

Lit le message du journal du commit depuis le fichier donné. Utilisez - pour lire depuis l'entrée standard. Cela peut être donné plus d'une fois et le contenu de chaque fichier devient son propre paragraphe.

-S[<keyid>], --gpg-sign[=<keyid>], --no-gpg-sign

Signe les commits avec GPG. L'argument keyid est facultatif et par défaut correspond à l'identité du committer ; s'il est spécifié, il doit être collé à l'option sans espace. --no-gpg-sign est utile pour annuler une --gpg-sign option donnée précédemment sur la ligne de commande.

INFORMATIONS SUR LE COMMIT

Un commit encapsule :

•tous les identifiants des objets parents
•le nom, l'e-mail et la date de l'auteur
•le nom et l'e-mail du committer et l'heure du commit.

Un commentaire de commit est lu depuis l'entrée standard. Si une entrée de journal des modifications n'est pas fournie via une redirection « < », git commit-tree attendra simplement qu'une entrée soit saisie et terminée avec ^D.

FORMATS DE DATE

Les variables d'environnement GIT_AUTHOR_DATE et GIT_COMMITTER_DATE prennent en charge les formats de date suivants :

Format interne de Git

Il est <horodatage-unix> <décalage-fuseau-horaire>, où <horodatage-unix> est le nombre de secondes depuis l'époque UNIX. <décalage-fuseau-horaire> est un décalage positif ou négatif par rapport à UTC. Par exemple CET (qui est en avance d'une heure sur UTC) est +0100.

RFC 2822

Le format de date standard tel que décrit par la RFC 2822, par exemple Thu, 07 Apr 2005 22:13:13 +0200.

ISO 8601

Heure et date spécifiées par la norme ISO 8601, par exemple 2005-04-07T22:13:13. L'analyseur accepte également un espace à la place du T caractères. Les parties fractionnaires d'une seconde seront ignorées, par exemple 2005-04-07T22:13:13.019 sera traité comme 2005-04-07T22:13:13.

Note
De plus, la partie date est acceptée dans les formats suivants : AAAA.MM.JJ, MM/JJ/AAAA et JJ.MM.AAAA.

DISCUSSION

Git est dans une certaine mesure agnostique quant à l'encodage des caractères.

•Le contenu des objets blob est des séquences d'octets non interprétées. Il n'y a pas de traduction d'encodage au niveau du noyau.
•Les noms de chemins sont encodés en UTF-8 normalisation forme C. Cela s'applique aux objets arbre, au fichier d'index, aux noms de références, ainsi qu'aux noms de chemins dans les arguments de ligne de commande, les variables d'environnement et les fichiers de configuration (.git/config (voir git-config(1)), gitignore(5), gitattributes(5) et gitmodules(5)).

Notez qu'au niveau du noyau, Git traite les noms de chemins simplement comme des séquences d'octets non-NUL, il n'y a pas de conversions d'encodage des noms de chemins (sauf sur Mac et Windows). Par conséquent, l'utilisation de noms de chemins non-ASCII fonctionnera principalement même sur les plateformes et les systèmes de fichiers qui utilisent des encodages ASCII étendus hérités. Cependant, les dépôts créés sur de tels systèmes ne fonctionneront pas correctement sur les systèmes basés sur UTF-8 (par ex. Linux, Mac, Windows) et vice versa. De plus, de nombreux outils basés sur Git supposent simplement que les noms de chemins sont en UTF-8 et ne parviendront pas à afficher correctement les autres encodages.

•Les messages du journal des commits sont généralement encodés en UTF-8, mais d'autres encodages ASCII étendus sont également pris en charge. Cela inclut ISO-8859-x, CP125x et bien d'autres, mais pas UTF-16/32, EBCDIC et les encodages multioctets CJK (GBK, Shift-JIS, Big5, EUC-x, CP9xx etc.).

Bien que nous encouragions à ce que les messages du journal des commits soient encodés en UTF-8, à la fois le noyau et les outils de haut niveau de Git sont conçus pour ne pas forcer UTF-8 sur les projets. Si tous les participants d'un projet particulier trouvent plus pratique d'utiliser des encodages hérités, Git ne l'interdit pas. Cependant, il y a quelques points à garder à l'esprit.

1.git commit et git commit-tree émettent un avertissement si le message du journal du commit qui leur est donné ne ressemble pas à une chaîne UTF-8 valide, sauf si vous dites explicitement que votre projet utilise un encodage hérité. La façon de dire cela est d'avoir i18n.commitEncoding dans le .git/config fichier, comme ceci : 
[i18n]
        commitEncoding = ISO-8859-1

Les objets commit créés avec le paramètre ci-dessus enregistrent la valeur de i18n.commitEncoding dans leur encoding en-tête. Cela est fait pour aider les autres personnes qui les regarderont plus tard. L'absence de cet en-tête implique que le message du journal du commit est encodé en UTF-8.

2.git log, git show, git blame et les commandes similaires regardent l' encoding en-tête d'un objet commit et essaient de re-coder le message du journal en UTF-8 sauf indication contraire. Vous pouvez spécifier l'encodage de sortie souhaité avec i18n.logOutputEncoding dans le .git/config fichier, comme ceci : 
[i18n]
        logOutputEncoding = ISO-8859-1

Si vous n'avez pas cette variable de configuration, la valeur de i18n.commitEncoding est utilisée à la place.

Notez que nous avons délibérément choisi de ne pas re-coder le message du journal du commit lorsqu'un commit est fait pour forcer UTF-8 au niveau de l'objet commit, car le re-codage en UTF-8 n'est pas nécessairement une opération réversible.
