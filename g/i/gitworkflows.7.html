Gestion des branches pour une

version

En supposant que vous utilisez l'approche de fusion discutée ci-dessus, lorsque vous publiez votre projet, vous devrez effectuer un travail supplémentaire de gestion des

branches.

Une version fonctionnelle est créée à partir de la branche master, car master suit les commits qui doivent figurer dans la prochaine version

fonctionnelle.

La branche master doit être un sur-ensemble de maint. Si cette condition n'est pas remplie, alors maint contient certains commits qui ne sont pas inclus dans master. Les correctifs représentés par ces commits ne seront donc pas inclus dans votre version

fonctionnelle.

Pour vérifier que master est bien un sur-ensemble de maint, utilisez git log

:

Exemple 5. Vérifier que master est un sur-ensemble de main

t

git log master..main

t

Cette commande ne doit lister aucun commit. Sinon, extrayez master et fusionnez maint en

elle.

Vous pouvez maintenant procéder à la création de la version fonctionnelle. Appliquez une étiquette à l'extrémité de master indiquant la version de la publication

:

Exemple 6. Étiquetage de la

publication

git tag -s -m "Git X.Y.Z" vX.Y.Z maste

r

Vous devez pousser la nouvelle étiquette vers un serveur Git public (voir « WORKFLOWS DISTRIBUTÉS » ci-dessous). Cela rend l'étiquette disponible pour les autres personnes qui suivent votre projet. La poussée peut aussi déclencher un hook post-update pour effectuer des tâches liées à la publication, comme la création d'archives de distribution et de pages de documentation

préformatées.

De même, pour une version de maintenance, maint suit les commits à publier. Par conséquent, dans les étapes ci-dessus, étiquetez et poussez simplement maint au lieu de mast

e
r.

Gestion des branches de maintenance après une version

fonctionnelle

Après une version fonctionnelle, vous devez gérer vos branches de

maintenance.

Tout d'abord, si vous souhaitez continuer à publier des correctifs de maintenance pour la version fonctionnelle réalisée avant la plus récente, vous devez créer une autre branche pour suivre les commits de cette version

précédente.

Pour ce faire, la branche de maintenance actuelle est copiée dans une autre branche nommée avec le numéro de version précédente (par exemple maint-X.Y.(Z-1) où X.Y.Z est la version actuelle)

.

Exemple 7. Copier

maint

git branch maint-X.Y.(Z-1) main

t

La branche maint doit maintenant être avancée rapidement jusqu'au code nouvellement publié afin que les correctifs de maintenance puissent être suivis pour la version actuelle

:

Exemple 8. Mettre à jour maint vers la nouvelle

version
•git checkout main
t
•git merge --ff-only maste
r

Si la fusion échoue car ce n'est pas un avancement rapide, il est possible que certains correctifs sur maint aient été manqués dans la version fonctionnelle. Cela ne se produira pas s

i le contenu des branches a été vérifi
é comme décrit dans la section précédente.

Gestion des branches next et seen après une version

fonctionnelle

Après une version fonctionnelle, la branche d'intégration next peut éventuellement être rembobinée et reconstruite à partir de l'extrémité de master en utilisant les sujets survivants sur next

:

Exemple 9. Rembobiner et reconstruire

next
•git switch -C next maste
r
•git merge ai/topic_in_next
1
•git merge ai/topic_in_next
2
•..
.

L'avantage de faire cela est que l'historique de next sera propre. Par exemple, certains sujets fusionnés dans next ont pu sembler prometteurs au début, mais ont ensuite été jugés indésirables ou prématurés. Dans un tel cas, le sujet est annulé dans next mais le fait demeure dans l'historique qu'il a été une fois fusionné et annulé. En recréant next, vous donnez à une nouvelle incarnation de ces sujets une feuille vierge pour réessayer, et une version fonctionnelle est un bon point dans l'historique pour le

faire.

Si vous faites cela, vous devriez faire une annonce publique indiquant que next a été rembobinée et

reconstruite.

Le même processus de rembobinage et de reconstruction peut être suivi pour seen. Une annonce publique n'est pas nécessaire car seen est une branch

e jetable,

WORKFLOWS

DISTRIBUTÉS

Après la dernière section, vous devriez savoir comment gérer les sujets. En général, vous ne serez pas la seule personne à travailler sur le projet, vous devrez donc partager votre

travail.

Grosso modo, il existe deux workflows importants : merge et patch. La différence importante est que le workflow merge peut propager l'historique complet, y compris les fusions, tandis que les patches ne le peuvent pas. Les deux workflows peuvent être utilisés en parallèle : dans git.git, seuls les responsables de sous-systèmes utilisent le workflow merge, tandis que tout le monde envoie des

patches.

Notez que le ou les responsables peuvent imposer des restrictions, telles que des exigences « Signed-off-by », auxquelles tous les commits/patches soumis pour inclusion doivent se conformer. Consultez la documentation de votre projet pour plus

d'informations.

Workflow

merge

Le workflow merge fonctionne en copiant des branches entre l'amont et l'aval. L'amont peut fusionner les contributions dans l'historique officiel ; l'aval base son travail sur l'historique

officiel.

Il existe trois outils principaux pouvant être utilisés pour cela

:
•git-push(1) copie vos branches vers un dépôt distant, généralement vers un que toutes les parties impliquées peuvent lire
;
•git-fetch(1) qui copie les branches distantes vers votre dépôt ;
et
•git-pull(1) qui fait le fetch et la fusion en une seule
fois.

Notez le dernier point. Ne utilisez pas git pull sauf si vous voulez réellement fusionner la branche

distante.

Obtenir des changements est facile

:

Exemple 10. Push/pull : Publier des

branches/sujets

git push <remote> <branch> et dites à tout le monde où ils peuvent faire du

fetch.

Vous devrez toujours informer les gens par d'autres moyens, comme le courrier. (Git fournit git-request-pull(1) pour envoyer des requêtes pull préformatées aux responsables amont afin de simplifier cette tâche.

)

Si vous voulez simplement obtenir les copies les plus récentes des branches d'intégration, rester à jour est facile aussi

:

Exemple 11. Push/pull : Rester à

jour

Utilisez git fetch <remote> ou git remote update pour rester à

jour.

Puis simplement créez des branches de sujets à partir des remotes stables comme expliqué

précédemment.

Si vous êtes un responsable et souhaitez fusionner les branches de sujets d'autres personnes vers les branches d'intégration, ils enverront généralement une requête pour cela par courrier. Une telle requête ressemble

à 
Please pull
from <U
RL> <branch>

Dans ce cas, git pull peut faire le fetch et la fusion en une seule fois, comme

suit.

Exemple 12. Push/pull : Fusionner des sujets

distants

git pull <URL> <branch

>

Occasionnellement, le responsable peut rencontrer des conflits de fusion lorsqu'il essaie de tirer des changements depuis l'aval. Dans ce cas, il peut demander à l'aval de faire la fusion et de résoudre les conflits lui-même (peut-être qu'il saura mieux comment les résoudre). C'est l'un des rares cas où l'aval doit fusionner

depuis
l'amont.

Workflow

patch

Si vous êtes un contributeur qui envoie des changements vers l'amont sous forme d'e-mails, vous devriez utiliser des branches de sujets comme d'habitude (voir ci-dessus). Puis utilisez git-format-patch(1) pour générer les e-mails correspondants (fortement recommandé par rapport au formatage manuel car cela facilite la vie du responsable)

.

Exemple 13. format-patch/am : Publier des

branches/sujets
•git format-patch -M upstream..topic pour les transformer en fichiers de patch
préformatés
•git send-email --to=<recipient> <patches
>

Consultez les pages de manuel git-format-patch(1) et git-send-email(1) pour des notes d'utilisation supplémentaires

.

Si le responsable vous dit que votre patch ne s'applique plus à l'amont actuel, vous devrez faire un rebase de votre sujet (vous ne pouvez pas utiliser une fusion car vous ne pouvez pas faire format-patch sur des fusions)

:

Exemple 14. format-patch/am : Garder les sujets à

jour

git pull --rebase <URL> <branch

>

Vous pouvez ensuite corriger les conflits pendant le rebase. Vous n'avez probablement pas publié votre sujet autrement que par courrier, le rebase n'est donc pas un

problème.

Si vous recevez une telle série de patches (en tant que responsable, ou peut-être en tant que lecteur de la liste de diffusion où elle a été envoyée), enregistrez les mails dans des fichiers, créez une nouvelle branche de sujet et utilisez git am pour importer les commits

:

Exemple 15. format-patch/am : Importer des

patches

git am < patc

h

Une fonctionnalité à signaler est la fusion à trois voies, qui peut aider si vous rencontrez des conflits : git am -3 utilisera les informations d'index contenues dans les patches pour déterminer la base de fusion. Voir git-am(1) pour

d'aut
res op
tions.
