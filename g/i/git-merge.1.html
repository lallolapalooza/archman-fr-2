Cette option peut être utilisée pour outrepasser cette sécurité lors de la fusion d'historiques de deux projets qui ont débuté indépendamment. Comme il s'agit d'une occasion très rare, aucune variable de configuration pour l'activer par défaut n'existe ni n'existera.

-m <msg>

Définit le message de commit à utiliser pour le commit de fusion (dans le cas où un est créé).

Si --log est spécifié, un journal abrégé des commits en cours de fusion sera ajouté au message spécifié.

La commande git fmt-merge-msg peut être utilisée pour fournir un bon défaut pour les invocations automatisées de git merge. Le message automatisé peut inclure la description de la branche.

-F <file>, --file=<file>

Lit le message de commit à utiliser pour le commit de fusion (dans le cas où un est créé).

Si --log est spécifié, un journal abrégé des commits en cours de fusion sera ajouté au message spécifié.

--rerere-autoupdate, --no-rerere-autoupdate

Après que le mécanisme rerere a réutilisé une résolution enregistrée sur le conflit actuel pour mettre à jour les fichiers dans l'arbre de travail, lui permet également de mettre à jour l'index avec le résultat de la résolution. --no-rerere-autoupdate est un bon moyen de vérifier ce que rerere a fait et de détecter les éventuelles erreurs de fusion, avant de commiter le résultat dans l'index avec un git add séparé.

--overwrite-ignore, --no-overwrite-ignore

Écrase silencieusement les fichiers ignorés du résultat de la fusion. C'est le comportement par défaut. Utilisez --no-overwrite-ignore pour abandonner.

--abort

Annule le processus de résolution de conflit en cours et tente de reconstruire l'état de pré-fusion. Si une entrée autostash est présente, appliquez-la à l'arbre de travail.

S'il y avait des modifications non commitées dans l'arbre de travail lors du début de la fusion, git merge --abort sera dans certains cas incapable de reconstruire ces modifications. Il est donc recommandé de toujours commiter ou stasher vos modifications avant d'exécuter git merge.

git merge --abort est équivalent à git reset --merge lorsque MERGE_HEAD est présent, sauf si MERGE_AUTOSTASH est également présent, auquel cas git merge --abort applique l'entrée de stash à l'arbre de travail tandis que git reset --merge enregistrera les modifications stashess dans la liste de stash.

--quit

Oublie la fusion en cours. Laisse l'index et l'arbre de travail tels quels. Si MERGE_AUTOSTASH est présent, l'entrée de stash sera enregistrée dans la liste de stash.

--continue

Après qu'une fusion git merge s'arrête en raison de conflits, vous pouvez conclure la fusion en exécutant git merge --continue (voir la section "COMMENT RÉSOLVER LES CONFLITS" ci-dessous).

VÉRIFICATIONS PRÉ-FUSION

Avant d'appliquer des modifications externes, vous devez mettre votre propre travail en bonne forme et le commiter localement, de sorte qu'il ne soit pas écrasé en cas de conflits. Voir également git-stash(1). git pull et git merge s'arrêteront sans rien faire lorsque des modifications locales non commitées chevaucheront des fichiers que git pull / git merge pourraient avoir besoin de mettre à jour.

Pour éviter d'enregistrer des modifications non liées dans le commit de fusion, git pull et git merge s'arrêteront également s'il y a des modifications enregistrées dans l'index par rapport au commit HEAD. (Des exceptions spécifiques et étroites à cette règle peuvent exister en fonction de la stratégie de fusion utilisée, mais en général, l'index doit correspondre à HEAD.)

Si tous les commits nommés sont déjà des ancêtres de HEAD, git merge sortira tôt avec le message "Already up to date."

FUSION RAPIDE

Souvent, la tête de branche actuelle est un ancêtre du commit nommé. C'est le cas le plus courant, surtout lorsqu'il est invoqué depuis git pull : vous suivez un dépôt distant, vous n'avez effectué aucun commit local, et maintenant vous voulez vous mettre à jour vers une révision distante plus récente. Dans ce cas, un nouveau commit n'est pas nécessaire pour stocker l'historique combiné ; au lieu de cela, HEAD (ainsi que l'index) est mis à jour pour pointer vers le commit nommé, sans créer de commit de fusion supplémentaire.

Ce comportement peut être supprimé avec l'option --no-ff.

VRAIE FUSION

Sauf dans une fusion rapide (voir ci-dessus), les branches à fusionner doivent être liées par un commit de fusion qui a les deux comme parents.

Une version fusionnée réconciliant les modifications de toutes les branches à fusionner est committée, et votre HEAD, votre index et votre arbre de travail sont mis à jour vers celle-ci. Il est possible d'avoir des modifications dans l'arbre de travail tant qu'elles ne se chevauchent pas ; la mise à jour les préservera.

Lorsqu'il n'est pas évident de réconcilier les modifications, il se passe ce qui suit :

1.Le pointeur HEAD reste le même.
2.La référence MERGE_HEAD est définie pour pointer vers l'autre tête de branche.
3.Les chemins qui ont fusionné proprement sont mis à jour à la fois dans le fichier d'index et dans votre arbre de travail.
4.Pour les chemins conflictuels, le fichier d'index enregistre jusqu'à trois versions : l'étape 1 stocke la version de l'ancêtre commun, l'étape 2 de HEAD, et l'étape 3 de MERGE_HEAD (vous pouvez inspecter les étapes avec git ls-files -u). Les fichiers de l'arbre de travail contiennent le résultat de l'opération de fusion ; c'est-à-dire les résultats de fusion à 3 voies avec les marqueurs de conflit familiers <<< === >>>.
5.Une référence nommée AUTO_MERGE est écrite, pointant vers un arbre correspondant au contenu actuel de l'arbre de travail (y compris les marqueurs de conflit pour les conflits textuels). Notez que cette référence n'est écrite que lorsque la stratégie de fusion ort est utilisée (par défaut).
6.Aucune autre modification n'est apportée. En particulier, les modifications locales que vous aviez avant de commencer la fusion resteront les mêmes et les entrées d'index correspondantes resteront telles quelles, c'est-à-dire correspondant à HEAD.

Si vous avez tenté une fusion qui a entraîné des conflits complexes et que vous souhaitez recommencer, vous pouvez récupérer avec git merge --abort.

FUSION D'UNE BALISE

Lors de la fusion d'une balise annotée (et éventuellement signée), Git crée toujours un commit de fusion même si une fusion rapide est possible, et le modèle de message de commit est préparé avec le message de la balise. De plus, si la balise est signée, la vérification de la signature est rapportée comme un commentaire dans le modèle de message. Voir également git-tag(1).

Lorsque vous souhaitez simplement vous intégrer au travail menant au commit qui se trouve être balisé, par exemple pour synchroniser avec un point de publication distant, vous ne voudrez peut-être pas créer de commit de fusion inutile.

Dans un tel cas, vous pouvez "déballer" vous-même la balise avant de la fournir à git merge, ou passer --ff-only lorsque vous n'avez aucun travail personnel. par exemple

git fetch origin
git merge v1.2.3^0
git merge --ff-only v1.2.3

COMMENT LES CONFLITS SONT PRÉSENTÉS

STRATÉGIES DE FUSIONLe mécanisme de fusion (les commandes git merge et git pull) permet de choisir les stratégies de fusion du backend avec l'option -s. Certaines stratégies peuvent également prendre leurs propres options, qui peuvent être passées en donnant les arguments -X<option> à git merge et/ou git pull

.

or

t
C'est la stratégie de fusion par défaut lors du retrait ou de la fusion d'une branche. Cette stratégie ne peut résoudre que deux têtes en utilisant un algorithme de fusion à trois voies. Lorsqu'il y a plus d'un ancêtre commun pouvant être utilisé pour la fusion à trois voies, elle crée un arbre fusionné des ancêtres communs et l'utilise comme arbre de référence pour la fusion à trois voies. Des tests effectués sur des commits de fusion réels issus de l'historique de développement du noyau Linux 2.6 ont montré que cela entraîne moins de conflits de fusion sans provoquer de mauvaises fusions. De plus, cette stratégie peut détecter et gérer les fusions impliquant des renommages. Elle n'utilise pas les copies détectées. Le nom de cet algorithme est un acronyme (« Ostensibly Recursive’s Twin ») et vient du fait qu'il a été écrit comme un remplacement de l'algorithme par défaut précédent, recursive.

Dans le cas où le chemin est un sous-module, si le commit du sous-module utilisé d'un côté de la fusion est un descendant du commit du sous-module utilisé de l'autre côté de la fusion, Git tente d'avancer rapidement jusqu'au descendant. Sinon, Git traitera ce cas comme un conflit, en suggérant comme résolution un commit de sous-module qui est un descendant des commits en conflit, s'il en existe

un.

conflictStyle
Spécifie le style dans lequel les blocs en conflit sont écrits dans les fichiers de l'arbre de travail lors d'une fusion. La valeur par défaut est "merge", qui affiche un marqueur de conflit <<<<<<<, les changements effectués par un côté, un marqueur =======, les changements effectués par l'autre côté, puis un marqueur >>>>>>>. Un style alternatif, "diff3", ajoute un marqueur ||||||| et le texte original avant le marqueur =======. Le style "merge" tend à produire des régions de conflit plus petites que diff3, à la fois en raison de l'exclusion du texte original, et parce que lorsqu'un sous-ensemble de lignes correspond des deux côtés, elles sont simplement extraites de la région de conflit. Un autre style alternatif, "zdiff3", est similaire à diff3 mais supprime les lignes correspondantes des deux côtés de la région de conflit lorsque ces lignes correspondantes apparaissent près du début ou de la fin d'une région de
conflit.
