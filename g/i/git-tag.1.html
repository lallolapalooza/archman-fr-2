DISCUSSIO

N

À propos du

re-taggage

Que faire si vous avez taggé le mauvais commit et que vous souhaitez re-taguer

?

Si vous n'avez rien poussé, re-taguez simplement. Utilisez -f pour remplacer l'ancien. Et c'est

terminé.

Mais si vous avez poussé des choses (ou si d'autres peuvent simplement lire votre dépôt directement), alors d'autres auront déjà vu l'ancien tag. Dans ce cas, vous pouvez faire l'une des deux choses suivantes

:
1.La chose sensée. Admettez simplement que vous avez fait une erreur et utilisez un nom différent. D'autres ont déjà vu un nom de tag, et si vous gardez le même nom, vous pourriez vous retrouver dans la situation où deux personnes ont toutes les deux "version X", mais qu'elles ont en fait des "X" différents. Appelez-le donc "X.1" et c'est
terminé.
2.La chose folle. Vous voulez vraiment appeler la nouvelle version "X" aussi, même si d'autres ont déjà vu l'ancienne. Utilisez donc simplement git tag -f à nouveau, comme si vous n'aviez pas déjà publié
l'ancien.

Cependant, Git ne change pas (et ne devrait pas changer) les tags dans le dos des utilisateurs. Donc, si quelqu'un a déjà l'ancien tag, faire un git pull sur votre arbre ne devrait pas simplement lui faire écraser

l'ancien.

Si quelqu'un a obtenu un tag de release de votre part, vous ne pouvez pas simplement changer le tag pour lui en mettant à jour le vôtre. C'est un problème de sécurité majeur, car les gens DOIVENT pouvoir faire confiance à leurs noms de tags. Si vous voulez vraiment faire la chose folle, vous devez simplement l'avouer et dire aux gens que vous avez fait une erreur. Vous pouvez le faire en faisant une annonce très publique en disant

: 
Ok, j'ai fait une erreur, et j'ai poussé une version
antérieure taguée comme X. J'ai ensuite corrigé quelque chose, et re-taggé
l'arbre *corrigé* comme X à nouveau.
Si vous avez le mauv
ais tag et que vous voulez le nouveau, veuillez supprimer l'ancien et récupérer le nouveau en faisant : git tag -d X git fetch origin tag X pour obtenir mon tag mis à jou
r. Vous pouvez vérifier quel tag vous avez en faisant git rev-parse X qui devrait retourner 0123456789abcdef.. si vous avez la nouvelle version. Désolé pour la gêne occasionnée.

Cela semble un peu compliqué ? C'est normal. Il n'y a aucun moyen de "corriger" cela automatiquement de manière c

orrecte. Les gens doivent savoir qu
e leurs tags ont peut-être été modifiés.

À propos du suivi

automatique

Si vous suivez l'arbre de quelqu'un d'autre, vous utilisez très probablement des branches de suivi distant (par ex. refs/remotes/origin/master). Vous voulez généralement les tags de l'autre

bout.

D'un autre côté, si vous faites un fetch parce que vous souhaitez une fusion ponctuelle avec quelqu'un d'autre, vous ne voulez généralement pas récupérer les tags de là-bas. Cela arrive plus souvent aux personnes proches du sommet, mais pas seulement à elles. De simples mortels qui se tirent mutuellement ne souhaitent pas nécessairement récupérer automatiquement les tags d'ancrage privé de l'autre

personne.

Souvent, les messages "please pull" sur la liste de diffusion fournissent simplement deux informations : une URL de dépôt et un nom de branche ; ceci est conçu pour être facilement copié-collé à la fin d'une ligne de commande git fetch

: 
Linus, please pull from
        git://git..../proj.git master
to get the following updates.
.
.

devient

: 
$ git pull gi
t://git..../pr
oj.git master

Dans un tel cas, vous ne voulez pas suivre automatiquement les tags de l'autre

personne.

Un aspect important de Git est sa nature distribuée, ce qui signifie largement qu'il n'y a pas de notion inhérente de "amont" ou "aval" dans le système. En apparence, l'exemple ci-dessus pourrait sembler indiquer que l'espace de noms des tags appartient à l'élite des personnes et que les tags ne circulent que vers le bas, mais ce n'est pas le cas. Cela montre seulement que le schéma d'utilisation détermine qui est intéressé par les tags de

qui.

Un pull ponctuel est le signe qu'un historique de commits traverse maintenant la frontière entre un cercle de personnes (par ex. "les personnes principalement intéressées par la partie réseau du noyau") qui peuvent avoir leur propre ensemble de tags (par ex. "c'est le troisième candidat de release du groupe réseau à être proposé pour la consommation générale avec la release 2.6.21") et un autre cercle de personnes (par ex. "les personnes qui intègrent diverses améliorations de sous-systèmes"). Ces dernières ne sont généralement pas intéressées par les tags détaillés utilisés en interne dans le premier groupe (c'est ce que signifie "interne"). C'est pourquoi il est souhaitable de ne pas suivre les tags automatiquement dans ce

cas.

Il est tout à fait possible que, parmi les personnes du domaine réseau, elles souhaitent échanger les tags internes à l

eur groupe, mais dans ce flux de travail, elles suivent très probablement les progrès des autres en ayant des bran
ches de suivi distant. Encore une fois, l'heuristique pour suivre automatiquement de tels tags est une bonne chose.

À propos de la datation des

tags

Si vous avez importé des changements depuis un autre VCS et souhaitez ajouter des tags pour les releases majeures de votre travail, il est utile de pouvoir spécifier la date à intégrer dans l'objet tag ; de telles données dans l'objet tag affectent, par exemple, l'ordre des tags dans l'interface

FORMATS DE

DATE

Les variables d'environnement GIT_AUTHOR_DATE et GIT_COMMITTER_DATE prennent en charge les formats de date suivants

:

Format interne de

Git
C'est <unix-timestamp> <time-zone-offset>, où <unix-timestamp> est le nombre de secondes depuis l'époque UNIX. <time-zone-offset> est un décalage positif ou négatif par rapport à UTC. Par exemple CET (qui est en avance d'une heure sur UTC) est +0100
.

RFC

2822
Le format de date standard tel que décrit par la RFC 2822, par exemple Thu, 07 Apr 2005 22:13:13 +0200
.

ISO

8601
Heure et date spécifiées par la norme ISO 8601, par exemple 2005-04-07T22:13:13. L'analyseur accepte également un espace à la place du caractère T. Les parties fractionnelles d'une seconde seront ignorées, par exemple 2005-04-07T22:13:13.019 sera traité comme 2005-04-07T22:13:13.

Note
De plus, la partie date est acceptée dans les formats suivants : YYYY.MM.DD, MM/DD/YYYY et DD.M
M.Y
YY
Y.
