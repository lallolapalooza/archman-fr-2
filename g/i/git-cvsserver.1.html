DESCRIPTIO

N

Cette application est une couche d'émulation CVS pour

Git.

Elle est très fonctionnelle. Cependant, toutes les méthodes ne sont pas implémentées, et pour les méthodes qui le sont, tous les commutateurs ne sont pas

implémentés.

Des tests ont été effectués à la fois avec le client CVS en lig

ne de commande et avec le plugin CVS d'Eclipse. La plupart d
es fonctionnalités fonctionnent bien avec ces deux clients.

LIMITATION

S

Les clients CVS ne peuvent ni étiqueter, ni créer de branche, ni effectuer de fusions

Git.

git-cvsserver mappe les branches Git aux modules CVS. C'est très différent de ce que la plupart des utilisateu

rs de CVS s'attendraient à voir, car en CVS les modules
représentent généralement un ou plusieurs répertoires.

BASE DE

DONNÉES

git-cvsserver utilise une base de données par tête Git (c'est-à-dire module CVS) pour stocker des informations sur le dépôt afin de maintenir des numéros de révision CVS cohérents. La base de données doit être mise à jour (c'est-à-dire écrite) après chaque

commit.

Si le commit est effectué directement en utilisant git (par opposition à l'utilisation de git-cvsserver), la mise à jour devra se faire lors du prochain accès au dépôt par git-cvsserver, indépendamment de la méthode d'accès et de l'opération

demandée.

Cela signifie que même si vous n'offrez qu'un accès en lecture (par exemple en utilisant la méthode pserver), git-cvsserver devrait avoir un accès en écriture à la base de données pour fonctionner de manière fiable (sinon, vous devez vous assurer que la base de données est à jour à chaque fois que git-cvsserver est exécuté)

.

Par défaut, il utilise des bases de données SQLite dans le répertoire Git, nommées gitcvs.<nom-du-module>.sqlite. Notez que l'arrière-plan SQLite crée des fichiers temporaires dans le même répertoire que le fichier de la base de données lors de l'écriture, il pourrait donc ne pas suffire d'accorder aux utilisateurs utilisant git-cvsserver un accès en écriture au fichier de la base de données sans leur donnant aussi un accès en écriture au répertoire. La base

de

données ne peut pas être régénérée de manière fiable sous une forme cohérente après que la branche qu'elle suit a changé. Exemple : Pour les branches fusionnées, git-cvsserver ne suit qu'une seule branche de développement, et après une git merge, une base de données mise à jour de manière incrémentale peut suivre une branche différente d'une base de données régénérée à partir de zéro, ce qui provoque des numéros de révision CVS incohérents. git-cvsserver n'a aucun moyen de savoir quelle branche il aurait choisie s'il avait été exécuté de manière incrémentale avant la fusion. Donc, si vous devez régénérer la base de données entièrement ou partiellement (à partir d'une vieille sauvegarde), vous devriez vous méfier des bac à

sable

CVS préexistants. Vous pouvez configurer le backend de la base de données avec les variables

prises en charge, y compris checkout, diff, status, update, log, add, remove, commit. La plupart des arguments de commande CVS qui lisent des étiquettes CVS ou des numéros de révision (typiquement -r) fonctionnent, et prennent aussi en charge n'importe quelle refspec git (étiquette, branche, ID de commit, etc). Cependant, les numéros de révision CVS pour les branches non par défaut ne sont pas bien émulés, et cvs log n'affiche pas du tout les étiquettes ou les branches. (Les numéros de révision CVS des branches non principales ressemblent superficiellement aux numéros de

révision

CVS, mais ils encodent en fait directement un ID de commit git, plutôt que de représenter le nombre de révisions depuis le point de branchement.) Notez qu'il y a deux façons de faire le checkout d'une branche particulière. Comme décrit ailleurs sur cette page, le paramètre "module" de cvs checkout est interprété comme un nom de branche, et il devient la branche principale. Elle reste la branche principale pour un bac à sable donné même si vous rendez temporairement une autre branche collante avec cvs update -r. Alternativement, l'argument -r peut indiquer une autre branche à réellement décocher, même si le module est toujours la branche "principale". Compromis (tels qu'implémentés actuellement) : Chaque nouveau "module" crée une nouvelle base de données sur disque avec un historique pour le module donné, et une fois la base de données créée, les opérations sur cette branche principale sont rapides. Ou alternativement

,

-r ne prend pas d'espace disque supplémentaire, mais peut être nettement plus lent pour de nombreuses opérations, comme cvs update. Si vous voulez référencer une refspec git qui contient des caractères qui ne sont pas autorisés par CVS, vous avez deux options. Premièrement, il se peut que cela fonctionne directement en fournissant la refspec git à l'argument CVS -r approprié ; certains clients CVS ne semblent pas faire beaucoup de vérifications de cohérence sur l'argument. Deuxièmement, si cela échoue, vous pouvez utiliser un mécanisme d'échappement de caractères spécial qui n'utilise que des caractères valides dans les étiquettes CVS. Une séquence de 4 ou 5 caractères de la forme (tiret bas ("_"), tiret ("-"), un ou deux caractères, et tiret ("-")) peut encoder divers caractères basés sur les une ou deux lettres : "s" pour slash ("/"), "p" pour point ("."), "u" pour tiret bas ("_"), ou deux chiffres

hexadécimaux

pour n'importe quelle valeur d'octet (typiquement un nombre ASCII, ou peut-être une partie d'un caractère encodé en UTF-8). Les opérations de surveillance héritées ne sont
