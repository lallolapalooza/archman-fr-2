NOM

git-lfs-prune - Supprime les anciens fichiers LFS du stockage local

SYNOPSIS

git lfs prune [options]

DESCRIPTION

Supprime les copies locales des fichiers LFS anciens, libérant ainsi de l'espace disque. La commande Prune fonctionne en énumérant tous les objets stockés localement, puis en supprimant ceux qui ne sont référencés par au moins UN des éléments suivants :

•le checkout actuel
•toutes les stashes existantes
•une 'branche récente' ; voir FICHIERS RÉCENTS
•un 'commit récent' sur la branche actuelle ou des branches récentes ; voir FICHIERS RÉCENTS
•un commit qui n'a pas été poussé ; voir FICHIERS LFS NON POUSSÉS
•tout autre checkout de worktree ; voir git-worktree(1)

En termes généraux, prune supprimera les fichiers que vous n'utilisez pas actuellement et qui ne sont pas 'récents', tant qu'ils ont été poussés, c'est-à-dire que la copie locale n'est pas la seule.

Le reflog n'est pas considéré, seulement les commits. Par conséquent, les objets LFS qui ne sont référencés que par des commits orphelins sont toujours supprimés.

Note : vous ne devriez pas exécuter git lfs prune si vous avez différents dépôts partageant le même répertoire de stockage personnalisé ; voir git-lfs-config(5) pour plus de détails sur l'option lfs.storage.

Dans votre configuration Git ou dans un fichier .lfsconfig, vous pouvez définir lfs.fetchexclude à une liste de chemins séparés par des virgules. Si lfs.fetchexclude est défini, alors tous les fichiers Git LFS dont les chemins correspondent à l'un d'entre eux seront purgés à moins qu'ils ne soient référencés par une stash ou un commit non poussé. Les chemins sont mis en correspondance à l'aide de motifs de caractères génériques comme spécifié dans gitignore(5).

OPTIONS

--dry-run, -d

Ne supprime rien en réalité, se contente de signaler ce qui aurait été fait

--force, -f

Purger tous les objets sauf ceux non poussés, y compris les objets requis pour les refs actuellement checkoutées. Implique --recent.

--recent

Purger même les objets qui seraient normalement préservés par les options de configuration spécifiées ci-dessous dans FICHIERS RÉCENTS.

--verify-remote, -c

Contacter le dépôt distant et vérifier que des copies des fichiers accessibles que nous allions supprimer existent bien avant de les supprimer. Voir VÉRIFIER LE DÉPÔT DISTANT.

--no-verify-remote

Désactive la vérification du dépôt distant si lfs.pruneverifyremotealways était activé dans les paramètres. Voir VÉRIFIER LE DÉPÔT DISTANT.

--verify-unreachable

Lors de l'exécution de --verify-remote, contacter le dépôt distant et vérifier également les objets inaccessibles. Voir VÉRIFIER LE DÉPÔT DISTANT.

--no-verify-unreachable

Désactive la vérification des fichiers inaccessibles depuis le dépôt distant si lfs.pruneverifyunreachablealways était activé dans les paramètres. Voir VÉRIFIER LE DÉPÔT DISTANT.

--when-unverified=<halt,continue>

Lorsque --verify-remote ne peut pas vérifier un objet sur le dépôt distant, soit arrêter l'exécution, soit continuer la suppression des objets vérifiés. Voir VÉRIFIER LE DÉPÔT DISTANT.

--verbose, -v

Rapporter le détail complet de ce qui est/serait supprimé.

FICHIERS RÉCENTS

Prune ne supprimera pas les fichiers LFS référencés par des commits 'récents', au cas où vous voudriez les réutiliser sans avoir à les télécharger. La définition de 'récent' est dérivée de celle utilisée par git-lfs-fetch(1) pour télécharger les objets récents avec l'option --recent, avec un décalage d'un certain nombre de jours (3 par défaut) pour garantir que nous conservons toujours les fichiers que vous téléchargez pendant quelques jours.

Voici les paramètres git-config(1) qui contrôlent ce comportement :

•lfs.pruneoffsetdays Le nombre de jours supplémentaires ajoutés aux paramètres de récupération des objets récents lors de leur utilisation pour décider quand purger. Ainsi, pour qu'une référence soit considérée comme suffisamment ancienne pour être purgée, elle doit avoir ce nombre de jours de plus que la référence la plus ancienne qui serait téléchargée via git lfs fetch --recent. Uniquement utilisé si le paramètre de jours pertinent pour la récupération des objets récents est non nul. Par défaut, 3 jours.
•lfs.fetchrecentrefsdays lfs.fetchrecentremoterefs lfs.fetchrecentcommitsdays Ces paramètres ont la même signification que git-lfs-fetch(1) avec l'option --recent, ils sont utilisés comme base pour le décalage ci-dessus. Tout ce qui sort de cette fenêtre décalée est considéré comme suffisamment ancien pour être purgé. Si une valeur en jours est zéro, cette condition n'est pas du tout utilisée pour conserver les objets et ils seront purgés.

FICHIERS LFS NON POUSSÉS

Lorsque la seule copie d'un fichier LFS est locale, et qu'elle est toujours accessible depuis une référence, ce fichier ne peut jamais être purgé, quelle que soit son ancienneté.

Pour déterminer si un fichier LFS a été poussé, nous vérifions la différence entre les refs locales et les refs distantes ; là où la ref locale est en avance, tous les fichiers LFS référencés dans ces commits sont non poussés et ne seront pas supprimés. Cela fonctionne car le hook pré-push de LFS garantit toujours que les fichiers LFS sont poussés avant que la branche distante ne soit mise à jour.

Voir DÉPÔT DISTANT PAR DÉFAUT, pour quel dépôt distant est considéré comme 'poussé' aux fins de la purge.

VÉRIFIER LE DÉPÔT DISTANT

L'option --verify-remote appelle le dépôt distant pour s'assurer que toutes les copies des fichiers LFS accessibles à supprimer ont des copies sur le dépôt distant avant de les supprimer réellement.

Habituellement, la vérification effectuée par FICHIERS LFS NON POUSSÉS est suffisante pour déterminer que les fichiers ont été poussés, mais si vous voulez être plus sûr au détriment d'une charge supplémentaire, vous pouvez faire en sorte que prune appelle réellement l'API du dépôt distant et vérifie la présence des fichiers que vous êtes sur le point de supprimer localement. Voir DÉPÔT DISTANT PAR DÉFAUT pour le dépôt qui sera vérifié.

Vous pouvez rendre ce comportement par défaut en définissant lfs.pruneverifyremotealways à true.

En plus de la charge supplémentaire liée à l'appel du dépôt distant, l'utilisation de cette option oblige également prune à distinguer les fichiers totalement inaccessibles (par exemple, ceux qui ont été ajoutés à l'index mais jamais commités, ou référencés uniquement par des commits orphelins) des fichiers qui sont toujours référencés, mais par des commits qui peuvent être purgés. Cela augmente la durée du processus de purge.

Si vous souhaitez également vérifier les objets inaccessibles, définissez l'option --verify-unreachable.

Vous pouvez vérifier les objets inaccessibles par défaut en définissant lfs.pruneverifyunreachablealways à true.

Par défaut, --verify-remote arrête l'exécution si un fichier ne peut pas être vérifié. Définissez --when-unverified=continue pour ne pas arrêter l'exécution mais continuer à supprimer tous les objets qui peuvent être vérifiés.

DÉPÔT DISTANT PAR DÉFAUT

Lors de l'identification des FICHIERS LFS NON POUSSÉS et de l'exécution de VÉRIFIER LE DÉPÔT DISTANT, un seul dépôt distant, 'origin', est normalement utilisé comme référence. Ce dépôt distant unique est considéré comme canonique ; même si vous utilisez plusieurs dépôts distants, vous voudrez probablement conserver vos copies locales jusqu'à ce qu'elles aient atteint ce dépôt. 'origin' est utilisé par défaut car ce sera généralement un dépôt central principal, ou votre fork de celui-ci - dans les deux cas, c'est une sauvegarde valide de votre travail. Si origin n'existe pas, alors par défaut rien ne sera purgé car tout est traité comme 'non poussé'.

Vous pouvez modifier le dépôt distant via la configuration git : lfs.pruneremotetocheck. Définissez-le sur un nom de dépôt distant différent pour vérifier celui-ci au lieu de 'origin'.
