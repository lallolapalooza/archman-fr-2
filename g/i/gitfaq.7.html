Comment synchroniser une arborescence de travail entre systèmes

?
D'abord, décidez si vous voulez vraiment faire cela. Git fonctionne mieux lorsque vous poussez ou récupérez votre travail en utilisant les commandes typiques git push et git fetch et n'est pas conçu pour partager une arborescence de travail entre systèmes. C'est potentiellement risqué et dans certains cas peut causer une corruption du dépôt ou une perte de données.

Habituellement, cela causera git status de devoir relire chaque fichier dans l'arborescence de travail. De plus, le modèle de sécurité de Git ne permet pas de partager une arborescence de travail entre utilisateurs non fiables, il n'est donc sûr de synchroniser une arborescence de travail que si elle ne sera utilisée que par un seul utilisateur sur toutes les

machines.

Il est important de ne pas utiliser un service de synchronisation cloud pour synchroniser une partie d'un dépôt Git, car cela peut causer une corruption, telle que des objets manquants, des fichiers modifiés ou ajoutés, des refs cassées, et une grande variété d'autres problèmes. Ces services ont tendance à synchroniser fichier par fichier en continu et ne comprennent pas la structure d'un dépôt Git. C'est particulièrement mauvais s'ils synchronisent le dépôt au milieu de sa mise à jour, car cela est très susceptible de causer des mises à jour incomplètes ou partielles et donc une perte de

données.

Un exemple du type de corruption qui peut survenir est des conflits sur l'état des refs, de sorte que les deux côtés se retrouvent avec des commits différents sur une branche que l'autre n'a pas. Cela peut entraîner que des objets importants deviennent non référencés et soient éventuellement supprimés par git gc, causant une perte de

données.

Par conséquent, il est préférable de pousser votre travail vers soit l'autre système soit un serveur central en utilisant le mécanisme normal de push et pull. Cependant, cela ne préserve pas toujours des données importantes, comme les stash, certaines personnes préfèrent donc partager une arborescence de travail entre

systèmes.

Si vous faites cela, l'approche recommandée est d'utiliser rsync -a --delete-after (idéalement avec une connexion chiffrée comme avec ssh) sur la racine du dépôt. Vous devez vous assurer de plusieurs choses lorsque vous faites cela

:
•Si vous avez des worktrees supplémentaires ou un répertoire Git séparé, ils doivent être synchronisés en même temps que l'arborescence de travail principale et le
dépôt.
•Vous êtes à l'aise avec le fait que le répertoire de destination soit une copie exacte du répertoire source, supprimant toute donnée qui s
'y trouve déjà.
•Le dépôt (y compris tous les worktrees et le répertoire Git) est dans un état au repos pendant la durée du transfert (c'est- à-dire qu'aucune opération de quelque type que ce soit n'est en cours, y compris les opérations en arrière-plan comme git gc et les opérations invoquées par votre éditeur).

Sachez que même avec ces recommandations, synchroniser de cette manière comporte certains risques car cela contourne le contrôle d'intégrité normal de Git pour les dépôts, il est donc conseillé d'avoir des sauvegardes. Vous pourriez aussi vouloir faire un git fsck pour vérifier l'intégrité de v

os données sur le
système de de
stination après la
synchronisation.

COURANTS

J'ai fait une erreur dans le dernier commit. Comment le changer

?
Vous pouvez faire le changement approprié dans votre arborescence de travail, exécuter git add <fichier> ou git rm <fichier>, selon le cas, pour le mettre en staging, puis git commit --amend. Votre changement sera inclus dans le commit, et on vous demandera d'éditer le message du commit à nouveau ; si vous souhaitez utiliser le message original tel quel, vous pouvez utiliser l'option --no-edit en plus de git commit, ou simplement enregistrer et quitter lorsque votre éditeur
s'ouvre.

J'ai fait un changement avec un bug et il a été inclus dans la branche principale. Comment devrais-je l'annuler

?
La façon habituelle de gérer cela est d'utiliser git revert. Cela préserve l'historique selon lequel le changement original a été fait et était une contribution précieuse, mais introduit aussi un nouveau commit qui annule ces changements car l'original avait un problème. Le message du commit du revert indique le commit qui a été reverté et est généralement édité pour inclure une explication sur la raison pour laquelle le revert a été
fait.

Comment ignorer les changements d'un fichier suivi

?
Git ne fournit pas de moyen de faire cela. La raison est que si Git a besoin d'écraser ce fichier, comme lors d'un checkout, il ne sait pas si les changements du fichier sont précieux et doivent être conservés, ou s'ils sont non pertinents et peuvent être détruits en toute sécurité. Par conséquent, il doit prendre la voie sûre et toujours les préserver.

C'est tentant d'essayer d'utiliser certaines fonctionnalités de git update-index, à savoir les bits assume-unchanged et skip-worktree, mais ceux-ci ne fonctionnent pas correctement à cette fin et ne devraient pas être utilisés de cette

manière.

Si votre objectif est de modifier un fichier de configuration, il peut souvent être utile d'avoir un fichier versionné dans le dépôt qui est un modèle ou un ensemble de valeurs par défaut qui peut ensuite être copié à côté et modifié selon le cas. Ce deuxième fichier, modifié, est généralement ignoré pour éviter de le commiter accidentellemen

t
.

J'ai demandé à Git d'ignorer divers fichiers, mais ils sont toujours

suivis
Un fichier gitignore garantit que certains fichiers qui ne sont pas suivis par Git restent non suivis. Cependant, parfois des fichiers particuliers peuvent avoir été suivis avant de les ajouter dans le .gitignore, ils restent donc toujours suivis. Pour ne plus suivre et ignorer des fichiers/patterns, utilisez git rm --cached <fichier/pattern> et ajoutez un pattern à .gitignore qui correspond au <fichier>. Voir gitignore(5) pour les
détails.

Comment savoir si je dois faire un fetch ou un pull

?
Un fetch stocke une copie des derniers changements du dépôt distant, sans modifier l'arborescence de travail ou la branche courante. Vous pouvez ensuite à votre loisir inspecter, merger, rebaser par-dessus, ou ignorer les changements amont. Un pull consiste en un fetch suivi immédiatement soit par un merge soit par un rebase. Voir git-pull
(1).

Puis-je utiliser un proxy avec Git

?
Oui, Git supporte l'utilisation de proxies. Git respecte les variables d'environnement standard http_proxy, https_proxy, et no_proxy couramment utilisées sur Unix, et il peut aussi être configuré avec http.proxy et des options similaires pour HTTPS (voir git-config(1)). Les options http.proxy et connexes peuvent être personnalisées sur la base d'un pattern par URL. De plus, Git peut en théorie fonctionner normalement avec des proxies transparents présents sur le réseau.

Pour SSH, Git peut supporter un proxy en utilisant le ProxyCommand d'OpenSSH. Les outils couramment utilisés incluent netcat et socat. Cependant, ils doivent être configurés pour ne pas se terminer lorsqu'ils voient un EOF sur l'entrée standard, ce qui signifie généralement que netcat nécessitera -q et socat nécessitera un timeout avec quelque chose comme -t 10. C'est requis parce que la façon dont le serveur SSH de Git sait que plus aucune requête ne sera faite est un EOF sur l'entrée standard, mais lorsque cela se produit, le serveur n'a peut-être pas encore traité la requête finale, donc abandonner la connexion à ce moment-là interromprait cette

requête.

Un exemple d'entrée de configuration dans ~/.ssh/config avec un proxy HTTP pourrait ressembler à ceci

: 
Host git.example.org
    User git
ProxyCommand socat -t 10 - PROXY:pr
oxy.example.org:%h:%p,proxyport=8080

Notez que dans tous les cas, pour que Git fonctionne correctement, le proxy doit être complètement transparent. Le proxy ne peut pas modifier, altérer, ou mettre en tampon

la connexion de quelque manière que ce soit, sinon Git échouera presque certainement. Notez que de nombreux proxies, y compris de nombreuses middleboxes TLS, des programmes ant
ivirus et pare-feu Windows autres que Windows Defender et Windows Firewall, et des proxies de filtrage ne répondent pas à ce standard, et en résultat finissent par cass
er Git. En raison des nombreux rapports de problèmes et de leur mauvais historique de sécurité, nous déconseillons l'utilisation de ces classes de logiciels et d'appareils.

MERGE ET

REBASE

Quels types de problèmes peuvent survenir lors du merge de branches longues avec des squash merges

?
En général, il y a une variété de problèmes qui peuvent survenir lors de l'utilisation de squash merges pour merger deux branches plusieurs fois. Ceux-ci peuvent inclure le fait de voir des commits supplémentaires dans la sortie de git log, avec une GUI, ou lors de l'utilisation de la notation ... pour exprimer une plage, ainsi que la possibilité de devoir re-résoudre les conflits encore et encore.

Lorsque Git fait un merge normal entre deux branches, il considère exactement trois points : les deux branches et un troisième commit, appelé le merge base, qui est généralement l'ancêtre commun des commits. Le résultat du merge est la somme des changements entre le merge base et chaque tête. Lorsque vous mergez deux branches avec un commit de merge régulier, cela résulte en un nouveau commit qui finira par être un merge base lorsqu'elles sont mergées à nouveau, car il y a maintenant un nouvel ancêtre commun. Git n'a pas à considérer les changements qui ont eu lieu avant le merge base, vous n'avez donc pas à re-résoudre des conflits que vous avez résolus

auparavant.

Lorsque vous effectuez un squash merge, un commit de merge n'est pas créé ; à la place, les changements d'un côté sont appliqués en tant que commit régulier de l'autre côté. Cela signifie que le merge base de ces branches n'aura pas changé, et donc lorsque Git va effectuer son prochain merge, il considère tous les changements qu'il a considérés la dernière fois plus les nouveaux changements. Cela signifie que des conflits peuvent devoir être re-résolus. De même, tout ce qui utilise la notation ... dans git diff, git log, ou une GUI affichera tous les changements depuis le merge base

original.

Par conséquent, si vous voulez merger deux branches

longues à plusieurs reprises, il est préférab
le d'utiliser toujours un commit de merge régulier.

Si je fais un changement sur deux branches mais le revert sur l'une, pourquoi le merge de ces branches inclut-il le changement

?
Par défaut, lorsque Git fait un merge, il utilise une stratégie appelée la stratégie ort, qui fait un merge triway sophistiqué. Dans un tel cas, lorsque Git effectue le merge, il considère exactement trois points : les deux têtes et un troisième point, appelé le merge base, qui est généralement l' ancêtre commun de ces commits. Git ne considère pas l'historique ou les commits individuels qui ont eu lieu sur ces branches.

Par conséquent, si les deux côtés ont une modification et que l'un des côtés a annulé cette modification, le résultat est d'inclure la modification. C'est parce que le code a changé d'un côté et qu'il n'y a pas de changement net de l'autre, et dans ce scénario, Git adopte le changement.

Si cela pose problème, vous pouvez faire un rebase à la place, en réorganisant la branche avec l'annulation sur l'autre branche. Un rebase dans ce scénario annulera le changement, car un rebase applique chaque commit individuel, y compris l'annulation. Notez que les rebases réécrivent l'historique, vous devriez donc éviter de réorganiser les branches publiées à moins que vous ne soyez certain d'être à l'aise avec cela. Voir la section NOTES dans git-rebase(1) pour plus de détails.

HOOKS

Comment utiliser les hooks pour empêcher les utilisateurs de faire certains changements ?

Le seul endroit sûr pour apporter ces changements est sur le dépôt distant (c'est-à-dire le serveur Git), généralement dans le hook pre-receive ou dans un système d'intégration continue (CI). Ce sont les emplacements où la politique peut être appliquée efficacement.

Il est courant d'essayer d'utiliser les hooks pre-commit (ou, pour les messages de commit, les hooks commit-msg) pour vérifier ces éléments, ce qui est excellent si vous travaillez en tant que développeur solo et souhaitez que l'outil vous aide. Cependant, l'utilisation de hooks sur une machine de développeur n'est pas efficace en tant que contrôle de politique car un utilisateur peut contourner ces hooks avec --no-verify sans être remarqué (parmi d'autres moyens). Git suppose que l'utilisateur contrôle ses dépôts locaux et n'essaie pas de l'empêcher ou de le signaler.

De plus, certains utilisateurs avancés trouvent que les hooks pre-commit entravent les flux de travail qui utilisent des commits temporaires pour préparer le travail en cours ou qui créent des commits de correction, il est donc préférable de pousser ces types de vérifications sur le serveur de toute façon.

PROBLÈMES INTER-PLATEFORMES

Je suis sous Windows et mes fichiers texte sont détectés comme binaires.

Git fonctionne mieux lorsque vous stockez des fichiers texte en UTF-8. De nombreux programmes sous Windows prennent en charge l'UTF-8, mais certains ne le font pas et utilisent uniquement le format UTF-16 little-endian, que Git détecte comme binaire. Si vous ne pouvez pas utiliser l'UTF-8 avec vos programmes, vous pouvez spécifier un encodage de copie de travail qui indique dans quel encodage vos fichiers doivent être extraits, tout en stockant ces fichiers en UTF-8 dans le dépôt. Cela permet à des outils comme git-diff(1) de fonctionner comme prévu, tout en permettant à vos outils de fonctionner.

Pour ce faire, vous pouvez spécifier un modèle gitattributes(5) avec l'attribut working-tree-encoding. Par exemple, le modèle suivant définit tous les fichiers C pour utiliser UTF-16LE-BOM, qui est un encodage courant sous Windows :

*.c     working-tree-encoding=UTF-16LE-BOM

Vous devrez exécuter git add --renormalize pour que cela prenne effet. Notez que si vous apportez ces modifications à un projet utilisé sur plusieurs plateformes, vous voudrez probablement les faire dans un fichier de configuration par utilisateur ou dans celui de $GIT_DIR/info/attributes, car le faire dans un fichier .gitattributes dans le dépôt s'appliquera à tous les utilisateurs du dépôt.

Voir l'entrée suivante pour des informations sur la normalisation des fins de ligne, et voir gitattributes(5) pour plus d'informations sur les fichiers d'attributs.

Je suis sous Windows et git diff affiche mes fichiers avec un ^M à la fin.

Par défaut, Git s'attend à ce que les fichiers soient stockés avec des fins de ligne Unix. En tant que tel, le retour chariot (^M) qui fait partie d'une fin de ligne Windows est affiché car il est considéré comme un espace blanc final. Git, par défaut, n'affiche les espaces blancs finaux que sur les nouvelles lignes, pas sur celles existantes.

Vous pouvez stocker les fichiers dans le dépôt avec des fins de ligne Unix et les convertir automatiquement aux fins de ligne de votre plateforme. Pour ce faire, définissez l'option de configuration core.eol sur native et consultez la question sur les paramètres de stockage recommandés pour savoir comment configurer les fichiers comme texte ou binaire.

Vous pouvez également contrôler ce comportement avec le paramètre core.whitespace si vous ne souhaitez pas supprimer les retours chariot de vos fins de ligne.

Pourquoi ai-je un fichier qui est toujours modifié ?

En interne, Git stocke toujours les noms de fichiers sous forme de séquences d'octets et n'effectue aucun encodage ni aucune mise en casse. Cependant, Windows et macOS effectuent tous deux une mise en casse des noms de fichiers par défaut. Par conséquent, il est possible de se retrouver avec plusieurs fichiers ou répertoires dont les noms ne diffèrent que par la casse. Git peut gérer cela sans problème, mais le système de fichiers ne peut stocker qu'un seul de ces fichiers. Ainsi, lorsque Git lit l'autre fichier pour voir son contenu, il apparaît comme modifié.

Il est préférable de supprimer l'un des fichiers afin de n'avoir qu'un seul fichier. Vous pouvez le faire avec des commandes comme celles qui suivent (en supposant deux fichiers AFile.txt et afile.txt) sur un arbre de travail autrement propre :

$ git rm --cached AFile.txt
$ git commit -m 'Supprimer les fichiers conflictuels en casse'
$ git checkout .

Cela évite de toucher le disque, mais supprime le fichier supplémentaire. Votre projet peut préférer adopter une convention de nommage, telle que des noms entièrement en minuscules, pour éviter que ce problème ne se reproduise ; une telle convention peut être vérifiée à l'aide d'un hook pre-receive ou dans le cadre d'un système d'intégration continue (CI).

Il est également possible que des fichiers perpétuellement modifiés apparaissent sur n'importe quelle plateforme si un filtre de nettoyage ou d'encrassement est utilisé sur votre système mais qu'un fichier a été précédemment validé sans exécuter le filtre de nettoyage ou d'encrassement. Pour corriger cela, exécutez ce qui suit sur un arbre de travail autrement propre :

$ git add --renormalize .

Quelle est la méthode recommandée pour stocker les fichiers dans Git ?

Bien que Git puisse stocker et gérer n'importe quel fichier de n'importe quel type, certains paramètres fonctionnent mieux que d'autres. En général, nous recommandons que les fichiers texte soient stockés en UTF-8 sans marque d'ordre des octets (BOM) avec des fins de ligne LF (style Unix). Nous recommandons également l'utilisation de l'UTF-8 (à nouveau, sans BOM) dans les messages de commit. Ce sont les paramètres qui fonctionnent le mieux sur toutes les plateformes et avec des outils tels que git diff et git merge.

De plus, si vous avez le choix entre des formats de stockage basés sur du texte ou non textuels, nous recommandons de stocker les fichiers au format texte et, si nécessaire, de les transformer dans l'autre format. Par exemple, un dump SQL basé sur du texte avec un enregistrement par ligne fonctionnera beaucoup mieux pour le diff et la fusion qu'un fichier de base de données réel. De même, les formats basés sur du texte tels que Markdown et AsciiDoc fonctionneront mieux que les formats binaires tels que Microsoft Word et PDF.

De même, le stockage de dépendances binaires (par exemple, bibliothèques partagées ou fichiers JAR) ou de produits de compilation dans le dépôt n'est généralement pas recommandé. Les dépendances et les produits de compilation sont mieux stockés sur un serveur d'artefacts ou de paquets avec uniquement des références, des URL et des hachages stockés dans le dépôt.

Nous recommandons également de définir un fichier gitattributes(5) pour marquer explicitement quels fichiers sont du texte et lesquels sont binaires. Si vous souhaitez que Git devine, vous pouvez définir l'attribut text=auto.

Avec les fichiers texte, Git s'assurera généralement que des fins de ligne LF sont utilisées dans le dépôt. Les variables de configuration core.autocrlf et core.eol spécifient la convention de fin de ligne suivie lors de l'extraction de tout fichier texte. Vous pouvez également utiliser l'attribut eol (par exemple, eol=crlf) pour remplacer quels fichiers reçoivent quel traitement de fin de ligne.

Par exemple, en général, les fichiers shell doivent avoir des fins de ligne LF et les fichiers batch doivent avoir des fins de ligne CRLF, donc ce qui suit pourrait être approprié dans certains projets :

# Par défaut, deviner.
*       text=auto
# Marquer tous les fichiers C comme texte.
*.c     text
# Assurer que tous les fichiers shell ont des fins de ligne LF et tous les fichiers batch des fins de ligne CRLF
# dans l'arbre de travail et que les deux ont des LF dans le dépôt.
*.sh text eol=lf
*.bat text eol=crlf
# Marquer tous les fichiers JPEG comme binaires.
*.jpg   binary

Ces paramètres aident les outils à choisir le bon format pour la sortie, telle que les correctifs, et entraînent l'extraction des fichiers avec la fin de ligne appropriée pour la plateforme.
