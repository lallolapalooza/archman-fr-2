NOM

git-notes - Ajouter ou inspecter des notes d'objets

SYNOPSIS

git notes [list [<objet>]]
git notes add [-f] [--allow-empty] [--[no-]separator | --separator=<coupure-paragraphe>] [--[no-]stripspace] [-F <fichier> | -m <msg> | (-c | -C) <objet>] [-e] [<objet>]
git notes copy [-f] ( --stdin | <objet-source> [<objet-destination>] )
git notes append [--allow-empty] [--[no-]separator | --separator=<coupure-paragraphe>] [--[no-]stripspace] [-F <fichier> | -m <msg> | (-c | -C) <objet>] [-e] [<objet>]
git notes edit [--allow-empty] [<objet>] [--[no-]stripspace]
git notes show [<objet>]
git notes merge [-v | -q] [-s <stratégie> ] <ref-notes>
git notes merge --commit [-v | -q]
git notes merge --abort [-v | -q]
git notes remove [--ignore-missing] [--stdin] [<objet>...]
git notes prune [-n] [-v]
git notes get-ref

DESCRIPTION

Ajoute, supprime ou lit des notes attachées à des objets, sans toucher aux objets eux-mêmes.

Par défaut, les notes sont sauvegardées et lues depuis refs/notes/commits, mais ce défaut peut être outrepassé. Voir les sections OPTIONS, CONFIGURATION et ENVIRONNEMENT ci-dessous. Si ce ref n'existe pas, il sera créé silencieusement lorsqu'il sera nécessaire pour stocker une note.

Une utilisation typique des notes est de compléter un message de commit sans modifier le commit lui-même. Les notes peuvent être affichées par git log en même temps que le message de commit original. Pour distinguer ces notes du message stocké dans l'objet commit, les notes sont indentées comme le message, après une ligne non indentée disant "Notes (<nom-ref>):" (ou "Notes:" pour refs/notes/commits).

Les notes peuvent également être ajoutées aux patchs préparés avec git format-patch en utilisant l'option --notes. Ces notes sont ajoutées comme un commentaire de patch après une ligne de séparation à trois tirets.

Pour changer quelles notes sont affichées par git log, voir la discussion sur notes.displayRef dans CONFIGURATION.

Voir la configuration notes.rewrite.<commande> pour une manière de transporter les notes à travers les commandes qui réécrivent les commits.

SOUS-COMMANDES

list

Liste l'objet de notes pour un objet donné. Si aucun objet n'est donné, affiche une liste de tous les objets de notes et les objets qu'ils annotent (au format "<objet-note> <objet-annoté>"). C'est la sous-commande par défaut si aucune sous-commande n'est donnée.

add

Ajoute des notes pour un objet donné (par défaut HEAD). Échoue si l'objet a déjà des notes (utilisez -f pour écraser les notes existantes). Cependant, si vous utilisez add de manière interactive (en utilisant un éditeur pour fournir le contenu des notes), alors - au lieu d'échouer - les notes existantes seront ouvertes dans l'éditeur (comme la sous-commande edit). Si vous spécifiez plusieurs options -m et -F, une ligne vide sera insérée entre les messages. Utilisez l'option --separator pour insérer d'autres délimiteurs. Vous pouvez utiliser -e pour éditer et affiner les messages fournis par les options -m et -F interactivement (en utilisant un éditeur) avant d'ajouter la note.

copy

Copie les notes du premier objet sur le second objet (par défaut HEAD). Échoue si le second objet a déjà des notes, ou si le premier objet n'en a aucune (utilisez -f pour écraser les notes existantes sur le second objet). Cette sous-commande est équivalente à : git notes add [-f] -C $(git notes list <objet-source>) <objet-destination>

En mode --stdin, prend des lignes au format

<objet-source> ESP <objet-destination> [ ESP <reste> ] LF

depuis l'entrée standard, et copie les notes de chaque <objet-source> vers son correspondant <objet-destination>. (Le <reste> optionnel est ignoré afin que la commande puisse lire l'entrée donnée au hook post-rewrite.)

--stdin ne peut pas être combiné avec des noms d'objets donnés sur la ligne de commande.

append

Ajoute de nouveaux messages par -m ou -F à une note existante, ou les ajoute comme une nouvelle note si aucune n'existe, pour l'objet (par défaut HEAD). Lors de l'ajout à une note existante, une ligne vide est ajoutée avant chaque nouveau message comme séparateur inter-paragraphe. Le séparateur peut être personnalisé avec l'option --separator. Édite les notes à ajouter fournies par les options -m et -F avec -e interactivement (en utilisant un éditeur) avant d'ajouter la note.

edit

Édite les notes pour un objet donné (par défaut HEAD).

show

Affiche les notes pour un objet donné (par défaut HEAD).

merge

Fusionne le ref de notes donné dans le ref de notes actuel. Cela tentera de fusionner les changements effectués par le ref de notes donné (appelé "distant") depuis la base de fusion (s'il y en a une) dans le ref de notes actuel (appelé "local").

Si des conflits surviennent et qu'une stratégie pour résoudre automatiquement les notes conflictuelles (voir la section "STRATÉGIES DE FUSION DE NOTES") n'est pas donnée, le résolveur manuel est utilisé. Ce résolveur checkout les notes conflictuelles dans un espace de travail spécial (.git/NOTES_MERGE_WORKTREE), et demande à l'utilisateur de résoudre manuellement les conflits là-bas. Une fois terminé, l'utilisateur peut soit finaliser la fusion avec git notes merge --commit, soit abandonner la fusion avec git notes merge --abort.

remove

Supprime les notes pour les objets donnés (par défaut HEAD). Lorsque zéro ou un objet est donné sur la ligne de commande, ceci est équivalent à spécifier un message de note vide à la sous-commande edit.

En mode --stdin, supprime également les noms d'objets donnés sur l'entrée standard. En d'autres termes, --stdin peut être combiné avec des noms d'objets de la ligne de commande.

prune

Supprime toutes les notes pour des objets non existants/non atteignables.

get-ref

Affiche le ref de notes actuel. Ceci fournit un moyen facile de récupérer le ref de notes actuel (par exemple, depuis des scripts).

OPTIONS

-f, --force

Lors de l'ajout de notes à un objet qui a déjà des notes, écrase les notes existantes (au lieu d'échouer).

-m <msg>, --message=<msg>

Utilise le message de note donné (au lieu de demander). Si plusieurs options -m sont données, leurs valeurs sont concaténées comme des paragraphes séparés.

-F <fichier>, --file=<fichier>

Prend le message de note du fichier donné. Utilisez - pour lire le message de note depuis l'entrée standard.

-C <objet>, --reuse-message=<objet>

Utilise l'objet blob donné (par exemple, une autre note) comme message de note. (Utilisez git notes copy <objet> à la place pour copier des notes entre objets.) Implique --no-stripspace car le comportement par défaut est de copier le message verbatim.

-c <objet>, --reedit-message=<objet>

Comme -C, mais avec -c l'éditeur est appelé, afin que l'utilisateur puisse modifier davantage le message de note.

--allow-empty

Autorise le stockage d'un objet de note vide. Le comportement par défaut est de supprimer automatiquement les notes vides.

--separator=<coupure-paragraphe>, --separator, --no-separator

Spécifie une chaîne utilisée comme séparateur inter-paragraphe personnalisé (une nouvelle ligne est ajoutée à la fin si nécessaire). Si --no-separator

>, aucun séparateur ne sera ajouté entre les paragraphes. La valeur par défaut est une ligne vide.

--stripspace, --no-stripspace

Nettoyer les espaces. Plus précisément (voir git-stripspace(1)) :
•supprimer les espaces de fin de ligne de toutes les lignes
•réduire plusieurs lignes vides consécutives à une seule ligne vide
•supprimer les lignes vides du début et de la fin de l'entrée
•ajouter un \n manquant à la dernière ligne si nécessaire.

--stripspace est la valeur par défaut, sauf pour -C/--reuse-message. Cependant, gardez à l'esprit que cela dépend de l'ordre des options similaires. Par exemple, pour -C <object> -m<message>, --stripspace sera utilisé car la valeur par défaut pour -m remplace le -Cprécédent. C'est une limitation connue qui pourra être corrigée à l'avenir.

--ref=<ref>

Manipuler l'arbre de notes dans <ref>. Cela remplace GIT_NOTES_REF et la configuration core.notesRef . La ref spécifie le nom complet de la ref lorsqu'elle commence par refs/notes/; lorsqu'elle commence par notes/, refs/ et sinon refs/notes/ sont préfixés pour former le nom complet de la ref.

--ignore-missing

Ne pas considérer comme une erreur la demande de suppression de notes d'un objet qui n'a pas de notes attachées.

--stdin

Valide uniquement pour remove et copy. Voir les sous-commandes respectives.

-n, --dry-run

Ne rien supprimer ; simplement rapporter les noms d'objets dont les notes seraient supprimées.

-s <strategy>, --strategy=<strategy>

Lors de la fusion de notes, résoudre les conflits de notes en utilisant la stratégie donnée. Les stratégies suivantes sont reconnues : manual (par défaut), ours, theirs, union et cat_sort_uniq. Cette option remplace le paramètre de configuration notes.mergeStrategy . Voir la section « NOTES MERGE STRATEGIES » ci-dessous pour plus d'informations sur chaque stratégie de fusion de notes.

--commit

Finaliser une git notes mergeen cours. Utilisez cette option lorsque vous avez résolu les conflits que git notes merge a stockés dans .git/NOTES_MERGE_WORKTREE. Cela modifie le commit de fusion partielle créé par git notes merge (stocké dans .git/NOTES_MERGE_PARTIAL) en ajoutant les notes dans .git/NOTES_MERGE_WORKTREE. La ref de notes stockée dans le symref .git/NOTES_MERGE_REF est mise à jour vers le commit résultant.

--abort

Annuler/réinitialiser une git notes mergeen cours, c'est-à-dire une fusion de notes avec conflits. Cela supprime simplement tous les fichiers liés à la fusion de notes.

-q, --quiet

Lors de la fusion de notes, opérer silencieusement.

-v, --verbose

Lors de la fusion de notes, être plus verbeux. Lors de l'élagage des notes, rapporter tous les noms d'objets dont les notes sont supprimées.

DISCUSSION

Les notes de commit sont des blobs contenant des informations supplémentaires sur un objet (généralement des informations pour compléter le message d'un commit). Ces blobs proviennent des refs de notes. Une ref de notes est généralement une branche qui contient des « fichiers » dont les chemins sont les noms d'objets pour les objets qu'ils décrivent, avec quelques séparateurs de répertoires inclus pour des raisons de performance [1].

Chaque changement de note crée un nouveau commit à la ref de notes spécifiée. Vous pouvez donc inspecter l'historique des notes en invoquant, par exemple, git log -p notes/commits. Actuellement, le message de commit enregistre uniquement l'opération qui a déclenché la mise à jour, et l'auteurship du commit est déterminé selon les règles habituelles (voir git-commit(1)). Ces détails peuvent changer à l'avenir.

Il est également permis à une ref de notes de pointer directement vers un objet arbre, auquel cas l'historique des notes peut être lu avec git log -p -g <refname>.

STRATÉGIES DE FUSION DES NOTES

La stratégie de fusion de notes par défaut est manual, qui extrait les notes en conflit dans un arbre de travail spécial pour résoudre les conflits de notes (.git/NOTES_MERGE_WORKTREE), et instructe l'utilisateur de résoudre les conflits dans cet arbre de travail. Une fois terminé, l'utilisateur peut soit finaliser la fusion avec git notes merge --commit, soit annuler la fusion avec git notes merge --abort.

Les utilisateurs peuvent sélectionner une stratégie de fusion automatisée parmi les suivantes en utilisant soit l'option -s/--strategy soit en configurant notes.mergeStrategy en conséquence :

ours résout automatiquement les notes en conflit en faveur de la version locale (c'est-à-dire la ref de notes actuelle).

theirs résout automatiquement les conflits de notes en faveur de la version distante (c'est-à-dire la ref de notes donnée qui est fusionnée dans la ref de notes actuelle).

union résout automatiquement les conflits de notes en concaténant les versions locale et distante.

cat_sort_uniq est similaire à union, mais en plus de concaténer les versions locale et distante, cette stratégie trie également les lignes résultantes et supprime les lignes en double du résultat. Cela est équivalent à appliquer le pipeline shell « cat | sort | uniq » aux versions locale et distante. Cette stratégie est utile si les notes suivent un format basé sur les lignes où l'on veut éviter les lignes en double dans le résultat de la fusion. Notez que si la version locale ou distante contient des lignes en double avant la fusion, celles-ci seront également supprimées par cette stratégie de fusion de notes.

EXEMPLES

Vous pouvez utiliser les notes pour ajouter des annotations avec des informations qui n'étaient pas disponibles au moment où un commit a été écrit.

$ git notes add -m 'Tested-by: Johannes Sixt <j6t@kdbg.org>' 72a144e2
$ git show -s 72a144e
[...]
    Signed-off-by: Junio C Hamano <gitster@pobox.com>
Notes:
    Tested-by: Johannes Sixt <j6t@kdbg.org>

En principe, une note est un blob Git régulier, et tout type de format (ou non) est accepté. Vous pouvez créer des notes de manière sûre pour les binaires à partir de fichiers arbitraires en utilisant git hash-object:

$ cc *.c
$ blob=$(git hash-object -w a.out)
$ git notes --ref=built add --allow-empty -C "$blob" HEAD

(Vous ne pouvez pas simplement utiliser git notes --ref=built add -F a.out HEAD car ce n'est pas sûr pour les binaires.) Bien sûr, cela n'a pas beaucoup de sens d'afficher des notes non au format texte avec git log, donc si vous utilisez de telles notes, vous aurez probablement besoin d'écrire des outils spécialisés pour faire quelque chose d'utile avec elles.

CONFIGURATION

core.notesRef

Ref de notes à lire et manipuler au lieu de refs/notes/commits. Doit être un nom de ref non abrégé. Ce paramètre peut être remplacé par l'environnement et la ligne de commande.

Tout ce qui se trouve au-dessus de cette ligne dans cette section n'est pas inclus à partir de la documentation git-config(1) . Le contenu qui suit est identique à ce qui s'y trouve :

notes.mergeStrategy

Quelle stratégie de fusion choisir par défaut lors de la résolution des conflits de notes. Doit être l'une des suivantes : manual, ours, theirs, union, ou cat_sort_uniq. La valeur par défaut est manual. Voir la section « NOTES MERGE STRATEGIES » de git-notes(1) pour plus d'informations sur chaque stratégie.

Ce paramètre peut être remplacé en passant l'option --strategy à git-notes(1).

notes.<name>.mergeStrategy

Quelle stratégie de fusion choisir lors d'une fusion de notes dans refs/notes/<name>. Cela remplace la stratégie plus générale notes.mergeStrategy. Voir la section « NOTES MERGE STRATEGIES » dans git-notes(1) pour plus d'informations sur les stratégies disponibles.

notes.displayRef

Quelle ref (ou refs, si un glob est spécifié ou spécifié plus d'une fois), en plus de celle définie par défaut par core.notesRef ou GIT_NOTES_REF, lire les notes lors de l'affichage des messages de commit avec la git log famille de commandes.

Ce paramètre peut être remplacé avec la variable d'environnement GIT_NOTES_DISPLAY_REF , qui doit être une liste de refs ou de globs séparés par des deux-points.

Un avertissement sera émis pour les refs qui n'existent pas, mais un glob qui ne correspond à aucune ref est ignoré silencieusement.

Ce paramètre peut être désactivé avec l'option --no-notes de la famille de commandes git-log(1) , ou avec l'option --notes=<ref> acceptée par ces commandes.

La valeur effective de core.notesRef (éventuellement remplacée par GIT_NOTES_REF) est également ajoutée implicitement à la liste des refs à afficher.

notes.rewrite.<command>

Lors de la réécriture de commits avec <command> (actuellement amend ou rebase), si cette variable est false, git ne copiera pas les notes de l'original vers le commit réécrit. La valeur par défaut est true. Voir aussi notes.rewriteRef ci-dessous.

Ce paramètre peut être remplacé avec la variable d'environnement GIT_NOTES_REWRITE_REF , qui doit être une liste de refs ou de globs séparés par des deux-points.

notes.rewriteMode

Lors de la copie des notes pendant une réécriture (voir l'option notes.rewrite.<command> ), détermine quoi faire si le commit cible a déjà une note. Doit être l'une des suivantes : overwrite, concatenate, cat_sort_uniq, ou ignore. La valeur par défaut est concatenate.

Ce paramètre peut être remplacé avec la variable d'environnement GIT_NOTES_REWRITE_MODE .

notes.rewriteRef

Lors de la copie des notes pendant une réécriture, spécifie la ref (entièrement qualifiée) dont les notes doivent être copiées. Peut être un glob, auquel cas les notes dans toutes les refs correspondantes seront copiées. Vous pouvez également spécifier cette configuration plusieurs fois.

N'a pas de valeur par défaut ; vous devez configurer cette variable pour activer la réécriture des notes. Définissez-la à refs/notes/commits pour activer la réécriture des notes de commit par défaut.

Peut être remplacé par la variable d'environnement GIT_NOTES_REWRITE_REF . Voir notes.rewrite.<command> ci-dessus pour une description plus détaillée de son format.

ENVIRONNEMENT

GIT_NOTES_REF

Quelle ref utiliser pour manipuler les notes, au lieu de refs/notes/commits. Cela remplace le paramètre core.notesRef .

GIT_NOTES_DISPLAY_REF

Liste de refs ou de motifs séparés par des deux-points indiquant quelles refs, en plus de celle définie par défaut dans core.notesRef ou GIT_NOTES_REF, utiliser pour lire les notes lors de l'affichage des messages de commit. Cela remplace le paramètre notes.displayRef .

Un avertissement sera émis pour les refs qui n'existent pas, mais un motif qui ne correspond à aucune ref est ignoré silencieusement.

GIT_NOTES_REWRITE_MODE

Lors de la copie des notes pendant une réécriture, que faire si la commit cible possède déjà une note. Doit être l'une des valeurs overwrite, concatenate, cat_sort_uniq, ou ignore. Cela remplace le paramètre core.rewriteMode .

GIT_NOTES_REWRITE_REF

Lors de la réécriture de commits, quelles notes copier de la commit originale vers la commit réécrite. Doit être une liste de refs ou de motifs séparés par des deux-points.

Si cette variable n'est pas définie dans l'environnement, la liste des notes à copier dépend des paramètres notes.rewrite.<command> et notes.rewriteRef .
