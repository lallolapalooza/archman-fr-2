NOM

git-switch - Change de branche

SYNOPSIS

git switch [<options>] [--no-guess] <branch>
git switch [<options>] --detach [<start-point>]
git switch [<options>(-c|-C) <new-branch> [<start-point>]
git switch [<options>] --orphan <new-branch>

DESCRIPTION

Change pour une branche spécifiée. L'arbre de travail et l'index sont mis à jour pour correspondre à la branche. Tous les nouveaux commits seront ajoutés à la pointe de cette branche.

Une nouvelle branche peut éventuellement être créée avec -c, -C, automatiquement à partir d'une branche distante du même nom (voir --guess), ou détacher l'arbre de travail de toute branche avec --detach, en même temps que le changement.

Le changement de branche ne nécessite pas un index et un arbre de travail propres (c'est-à-dire sans différences par rapport à HEAD). L'opération est cependant interrompue si elle entraîne la perte de modifications locales, sauf indication contraire avec --discard-changes ou --merge.

OPTIONS

<branch>

Branche vers laquelle changer.

<new-branch>

Nom de la nouvelle branche.

<start-point>

Le point de départ de la nouvelle branche. Spécifier un <start-point> vous permet de créer une branche basée sur un autre point de l'historique que celui vers lequel HEAD pointe actuellement. (Ou, dans le cas de --detach, vous permet d'inspecter et de vous détacher d'un autre point.)

Vous pouvez utiliser la syntaxe @{-<N>} pour vous référer à la <N>-ème dernière branche/commit vers laquelle vous avez changé en utilisant git switch ou git checkout . Vous pouvez aussi spécifier - qui est synonyme de @{-1}. Cela est souvent utilisé pour changer rapidement entre deux branches, ou pour annuler un changement de branche par erreur.

Dans un cas particulier, vous pouvez utiliser <rev-a>...<rev-b> comme raccourci pour la base de fusion de <rev-a> et <rev-b> s'il y a exactement une base de fusion. Vous pouvez omettre au plus l'un de <rev-a> et <rev-b>, auquel cas il vaut par défaut HEAD.

-c <new-branch>, --create <new-branch>

Crée une nouvelle branche nommée <new-branch> commençant à <start-point> avant de changer pour la branche. C'est l'équivalent transactionnel de 
$ git branch <new-branch>
$ git switch <new-branch>

c'est-à-dire que la branche n'est pas réinitialisée/créée sauf si git switch réussit (par exemple, lorsque la branche est utilisée dans un autre arbre de travail, non seulement la branche actuelle reste la même, mais la branche n'est pas réinitialisée au point de départ non plus).

-C <new-branch>, --force-create <new-branch>

Similaire à --create sauf que si <new-branch> existe déjà, elle sera réinitialisée à <start-point>. C'est un raccourci pratique pour : 
$ git branch -f _<new-branch>_
$ git switch _<new-branch>_

-d, --detach

Change pour un commit pour l'inspection et des expériences jetables. Voir la section « DETACHED HEAD » dans git-checkout(1) pour plus de détails.

--guess, --no-guess

Si <branch> n'est pas trouvée mais qu'il existe une branche de suivi dans exactement un distant (appelons-le <remote>) avec un nom correspondant, cela est traité comme équivalent à 
$ git switch -c <branch> --track <remote>/<branch>

Si la branche existe dans plusieurs distants et que l'un d'entre eux est nommé par la variable de configuration checkout.defaultRemote , nous utiliserons celui-ci pour les besoins de la désambiguïsation, même si <branch> n'est pas unique parmi tous les distants. Définissez-la par exemple à checkout.defaultRemote=origin pour toujours extraire les branches distantes de là si <branch> est ambiguë mais existe sur le distant origin . Voir aussi checkout.defaultRemote dans git-config(1).

--guess est le comportement par défaut. Utilisez --no-guess pour le désactiver.

Le comportement par défaut peut être défini via la variable de configuration checkout.guess .

-f, --force

Un alias pour --discard-changes.

--discard-changes

Continue même si l'index ou l'arbre de travail diffère de HEAD. L'index et l'arbre de travail sont restaurés pour correspondre à la cible du changement. Si --recurse-submodules est spécifié, le contenu des sous-modules est également restauré pour correspondre à la cible du changement. Cela sert à jeter les modifications locales.

-m, --merge

Si vous avez des modifications locales sur un ou plusieurs fichiers qui sont différents entre la branche actuelle et la branche vers laquelle vous changez, la commande refuse de changer de branche afin de préserver vos modifications dans le contexte. Cependant, avec cette option, une fusion à trois voies entre la branche actuelle, le contenu de votre arbre de travail et la nouvelle branche est effectuée, et vous serez sur la nouvelle branche.

Lorsqu'un conflit de fusion se produit, les entrées d'index pour les chemins en conflit sont laissées non fusionnées, et vous devez résoudre les conflits et marquer les chemins résolus avec git add (ou git rm si la fusion doit entraîner la suppression du chemin).

--conflict=<style>

Identique à l'option --merge ci-dessus, mais change la manière dont les fragments en conflit sont présentés, en remplaçant la variable de configuration merge.conflictStyle . Les valeurs possibles sont merge (par défaut), diff3, et zdiff3.

-q, --quiet

Silencieux, supprime les messages de retour.

--progress, --no-progress

L'état de progression est rapporté sur le flux d'erreur standard par défaut lorsqu'il est attaché à un terminal, sauf si --quiet est spécifié. Ce drapeau active le rapport de progression même s'il n'est pas attaché à un terminal, quel que soit --quiet.

-t, --track[ (direct|inherit)]

Lors de la création d'une nouvelle branche, configure le paramètre « amont ». -c est impliqué. Voir --track dans git-branch(1) pour plus de détails.

Si aucune option -c n'est donnée, le nom de la nouvelle branche sera dérivé de la branche de suivi distante, en regardant la partie locale du refspec configuré pour le distant correspondant, puis en supprimant la partie initiale jusqu'au « * ». Cela nous indique d'utiliser hack comme branche locale lors du ramification à partir de origin/hack (ou remotes/origin/hack, ou même refs/remotes/origin/hack). Si le nom donné n'a pas de barre oblique, ou si la déduction ci-dessus résulte en un nom vide, la déduction est interrompue. Vous pouvez donner explicitement un nom avec -c dans un tel cas.

--no-track

Ne configure pas le paramètre « amont », même si la variable de configuration branch.autoSetupMerge est vraie.

--orphan <new-branch>

Crée une nouvelle branche non née, nommée <new-branch>. Tous les fichiers suivis sont supprimés.

--ignore-other-worktrees

git switch refuse lorsque la référence voulue est déjà extraite par un autre arbre de travail. Cette option le fait extraire la référence quand même. En d'autres termes, la référence peut être détenue par plus d'un arbre de travail.

--recurse-submodules, --no-recurse-submodules

Utiliser --recurse-submodules mettra à jour le contenu de tous les sous-modules actifs selon le commit enregistré dans le superprojet. Si rien n'est utilisé (ou --no-recurse-submodules), les arbres de travail des sous-modules ne seront pas mis à jour. Tout comme git-submodule(1), cela détachera le HEAD des sous-modules.

EXEMPLES

La commande suivante change pour la branche « master » :

$ git switch master

Après avoir travaillé dans la mauvaise branche, changer pour la bonne branch se ferait en utilisant :

$ git switch mytopic

Cependant, votre branche « fausse » et la branche « mytopic » correcte peuvent différer dans des fichiers que vous avez modifiés localement, auquel cas le switch ci-dessus échouerait comme ceci :

$ git switch mytopic
error: You have local changes to 'frotz'; not switching branches.

Vous pouvez passer le -m drapeau à la commande, qui essaierait une fusion à trois voies :

$ git switch -m mytopic
Auto-merging frotz

Après cette fusion à trois voies, les modifications locales sont pas enregistrées dans votre fichier d'index, donc git diff vous montrerait les changements que vous avez faits depuis l'extrémité de la nouvelle branche.

Pour revenir à la branche précédente avant que nous ne passions à mytopic (c'est-à-dire la branche « master ») :

$ git switch -

Vous pouvez faire pousser une nouvelle branche à partir de n'importe quel commit. Par exemple, passez à «HEAD~3» et créez la branche «fixup» :

$ git switch -c fixup HEAD~3
Switched to a new branch 'fixup'

Si vous voulez démarrer une nouvelle branche à partir d'une branche distante du même nom :

$ git switch new-topic
Branch `new-topic` set up to track remote branch `new-topic` from `origin`
Switched to a new branch `new-topic`

Pour extraire le commit HEAD~3 pour inspection ou expérience temporaire sans créer une nouvelle branche :

$ git switch --detach HEAD~3
HEAD is now at 9fc9555312 Merge branch 'cc/shared-index-permbits'

S'il s'avère que ce que vous avez fait vaut la peine d'être conservé, vous pouvez toujours créer un nouveau nom pour cela (sans changer de branche) :

$ git switch -c good-surprises

CONFIGURATION

Tout ce qui se trouve sous cette ligne dans cette section est inclus sélectivement à partir de la git-config(1) documentation. Le contenu est le même que ce qui s'y trouve :

checkout.defaultRemote

Lorsque vous exécutez git checkout <something> ou git switch <something> et que vous n'avez qu'un seul distant, il peut implicitement revenir à l'extraction et au suivi de par ex. origin/<something>. Cela cesse de fonctionner dès que vous avez plus d'un distant avec une référence <something> . Ce paramètre permet de définir le nom d'un distant préféré qui devrait toujours gagner en cas de désambiguïsation. Le cas d'utilisation typique est de le définir à origin.

Actuellement, cela est utilisé par git-switch(1) et git-checkout(1] lorsque git checkout <something> ou git switch <something> extraira la branche <something> sur un autre distant, et par git-worktree(1) lorsque git worktree add fait référence à une branche distante. Ce paramètre pourrait être utilisé pour d'autres commandes ou fonctionnalités de type extraction à l'avenir.

checkout.guess

Fournit la valeur par défaut pour l'option --guess ou --no-guess dans git checkout et git switch. Voir git-switch(1) et git-checkout(1).

checkout.workers

Le nombre de travailleurs parallèles à utiliser lors de la mise à jour de l'arbre de travail. La valeur par défaut est un, c'est-à-dire une exécution séquentielle. Si défini à une valeur inférieure à un, Git utilisera autant de travailleurs que le nombre de cœurs logiques disponibles. Ce paramètre et checkout.thresholdForParallelism affectent toutes les commandes qui effectuent une extraction. Par ex. checkout, clone, reset, sparse-checkout, etc.

Note
L'extraction parallèle offre généralement de meilleures performances pour les dépôts situés sur SSD ou via NFS. Pour les dépôts sur disques tournants et/ou les machines avec un petit nombre de cœurs, l'extraction séquentielle par défaut fonctionne souvent mieux. La taille et le niveau de compression d'un dépôt peuvent également influencer la performance de la version parallèle.

checkout.thresholdForParallelism

Lors de l'exécution d'une extraction parallèle avec un petit nombre de fichiers, le coût de la création de sous-processus et de la communication inter-processus peut l'emporter sur les gains de parallélisation. Ce paramètre vous permet de définir le nombre minimum de fichiers pour lesquels une extraction parallèle devrait être tentée. La valeur par défaut est 100.
