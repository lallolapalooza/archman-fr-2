DESCRIPTIO

N

Les hooks sont des programmes que vous pouvez placer dans un répertoire de hooks pour déclencher des actions à certains moments de l'exécution de git. Les hooks dont le bit exécutable n'est pas défini sont

ignorés.

Par défaut, le répertoire de hooks est $GIT_DIR/hooks, mais cela peut être modifié via la variable de configuration core.hooksPath (voir git-config(1))

.

Avant qu'Git n'invoque un hook, il change son répertoire de travail vers soit $GIT_DIR dans un dépôt nu, soit la racine de l'arbre de travail dans un dépôt non nu. Une exception concerne les hooks déclenchés lors d'un push (pre-receive, update, post-receive, post-update, push-to-checkout) qui sont toujours exécutés dans

$GIT_DIR.

Les variables d'environnement, telles que GIT_DIR, GIT_WORK_TREE, etc., sont exportées afin que les commandes Git exécutées par le hook puissent localiser correctement le dépôt. Si votre hook a besoin d'invoquer des commandes Git dans un dépôt étranger ou dans un arbre de travail différent du même dépôt, il doit effacer ces variables d'environnement afin qu'elles n'interfèrent pas avec les opérations Git à l'emplacement étranger. Par exemple

: 
local_desc=$(git describe)
foreign_des
c=$(unset $(git rev-parse --local-env-v
ars); git -C ../foreign-repo describe)

Les hooks peuvent recevoir leurs arguments via l'environnement, les arguments de la ligne de commande et stdin. Voir la documentation de chaque hook ci-dessous pour plus de

détails.

git init peut copier les hooks vers le nouveau dépôt, selon sa configuration. Voir la section « TEMPLATE DIRECTORY » dans git-init(1) pour plus de détails. Quand le reste de ce document fait référence aux « hooks par défaut », il s'agit du modèle par défaut livré avec

Git.

reference-transactio

n

Ce hook est invoqué par toute commande Git qui effectue des mises à jour de références. Il s'exécute chaque fois qu'une transaction de référence est préparée, committée ou annulée et peut donc être appelé plusieurs fois. Le hook prend également en charge les mises à jour de références

symboliques.

Le hook prend exactement un argument, qui est l'état actuel dans lequel se trouve la transaction de référence donnée

:
•« prepared » : toutes les mises à jour de références ont été mises en file d'attente dans la transaction et les références ont été verrouillées sur le
disque.
•« committed » : la transaction de référence a été committée et toutes les références ont maintenant leur nouvelle valeur
respective.
•« aborted » : la transaction de référence a été annulée, aucun changement n'a été effectué et les verrous ont été
libérés.

Pour chaque mise à jour de référence qui a été ajoutée à la transaction, le hook reçoit sur l'entrée standard une ligne au format

: 
<old-value> SP
<new-value> SP
<ref-name> LF

où <old-value> est l'ancien nom d'objet passé à la transaction de référence, <new-value> est le nouveau nom d'objet à stocker dans la référence et <ref-name> est le nom complet de la référence. Lors d'une mise à jour forcée de la référence quelle que soit sa valeur actuelle ou lorsque la référence doit être créée à nouveau, <old-value> est le nom d'objet composé de zéros. Pour distinguer ces cas, vous pouvez inspecter la valeur actuelle de <ref-name> via git rev-parse

.

Pour les mises à jour de références symboliques, les champs <old-value> et <new-value> peuvent désigner des références au lieu d'objets. Une référence sera désignée avec un préfixe ref:, comme ref:<ref-targ

et>.

Le code de sortie du hook est ignoré pour tout état sauf l'état « prepared ».

Dans l'état « prepared », un code de sortie non nul causera l'annulation de l
a transaction. Le hook ne sera pas appelé avec l'état « aborted » dans ce cas.

t

Ce hook est invoqué par git-receive-pack(1) lorsqu'il réagit à git push et met à jour une ou plusieurs références dans son dépôt, et lorsque la tentative de push vise à mettre à jour la branche actuellement extraite et que la variable de configuration receive.denyCurrentBranch est définie à updateInstead. Un tel push est refusé par défaut si l'arbre de travail et l'index du dépôt distant présentent une différence quelconque par rapport au commit actuellement extrait ; lorsque l'arbre de travail et l'index correspondent tous deux au commit actuel, ils sont mis à jour pour correspondre à la pointe nouvellement poussée de la branche. Ce hook est destiné à être utilisé pour remplacer le comportement par

défaut.

Le hook reçoit le commit avec lequel la pointe de la branche actuelle va être mise à jour. Il peut se terminer avec un code de sortie non nul pour refuser le push (dans ce cas, il ne doit pas modifier l'index ni l'arbre de travail). Ou il peut effectuer les modifications nécessaires à l'arbre de travail et à l'index pour les amener à l'état souhaité lorsque la pointe de la branche actuelle est mise à jour vers le nouveau commit, et se terminer avec un code de sortie

zéro.

Par exemple, le hook peut simplement exécuter git read-tree -u -m HEAD "$1" afin d'émuler git fetch qui est exécuté dans la direction inverse avec git push, car la forme à deux arbres de git read-tree -u -m est essentiellement la même que git switch ou git checkout qui change de branche tout en conservant les changements locaux dans l'ar

bre de travail qui n'entrent pas en conflit
avec la différence entre les branches.

Le hook reçoit sur stdin une liste des commits réécrits, au

format 
<old-object-name> SP
<new-object-name> [
SP <extra-info> ] LF

Le extra-info dépend à nouveau de la commande. S'il est vide, le SP précédent est également omis. Actuellement, aucune commande ne passe de extra-info

.

Le hook s'exécute toujours après que la copie automatique des notes (voir « notes.rewrite.<command> » dans git-config(1)) a eu lieu, et a donc accès à ces

notes.

GIT_SENDEMAIL_FILE_COUNTE

fsmonitor-watchma

n

Ce hook est invoqué lorsque l'option de configuration core.fsmonitor est défini à .git/hooks/fsmonitor-watchman ou .git/hooks/fsmonitor-watchmanv2 selon la version du hook à

utiliser.

La version 1 prend deux arguments, une version (1) et le temps en nanosec écoulés depuis minuit, le 1er janvier

1970.

La version 2 prend deux arguments, une version (2) et un jeton qui est utilisé pour identifier les changements depuis le jeton. Pour watchman, il s'agit d'un identifiant d'horloge. Cette version doit écrire sur stdout le nouveau jeton suivi d'un NUL avant la liste des

fichiers.

Le hook doit écrire sur stdout la liste de tous les fichiers du répertoire de travail qui ont pu changer depuis le temps demandé. La logique doit être inclusive afin de ne manquer aucun changement potentiel. Les chemins doivent être relatifs à la racine du répertoire de travail et être séparés par un seul

NUL.

Il est acceptable d'inclure des fichiers qui n'ont pas réellement changé. Tous les changements, y compris les fichiers nouvellement créés et supprimés, doivent être inclus. Lorsque des fichiers sont renommés, l'ancien et le nouveau nom doivent être

inclus.

Git limitera les fichiers dont il vérifie les changements ainsi que les répertoires dans lesquels il recherche les fichiers non suivis en fonction des noms de chemins

fournis.

Une manière optimisée de dire à Git « tous les fichiers ont changé » est de renvoyer le nom de fichier /

.

Le code de sortie détermine si Git utilisera les données du

hook pour limiter sa recherche. En cas d'erreur, il revie
ndra à la vérification de tous les fichiers et dossiers.
