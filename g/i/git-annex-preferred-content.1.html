DESCRIPTIO

N

Chaque dépôt a un paramètre de contenu préféré, qui spécifie le contenu que le dépôt souhaite avoir présent. Ces paramètres peuvent être configurés en utilisant git annex vicfg ou git annex wanted. Ils sont utilisés par l' option --auto, par git annex sync --content, par les clusters, et par l'assistant

git-annex.

Bien que le contenu préféré exprime une préférence, il peut être contourné en utilisant simplement git annex drop. D'autre part, les paramètres de contenu requis sont appliqués ; git annex drop refusera de supprimer un fichier si cela violerait ses paramètres de contenu requis. Le contenu requis d'un dépôt peut être configuré en utilisant git annex vicfg ou git annex

requ
ired.

SYNTAX

E

Les expressions de contenu préféré utilisent une syntaxe similaire à celle de git-annex-matching-options(1), sans les tirets. Par exemple

:


exclude=archive/* and (include=*.mp3 or smallerthan=1mb

)

L'idée est que vous écrivez une expression à laquelle les fichiers sont appariés. Si un fichier correspond, le dépôt souhaite stocker son contenu. S'il ne correspond pas, le dépôt souhaite supprimer son contenu (s'il y a suffisamment d'ailleurs ailleurs pour permettre de le retirer)

.

Une expression de contenu préféré vid

e est traitée de la même manière
qu'un contenu préféré non configuré.

EXPRESSION

S
include=glob / exclude=gl
ob
Fait correspondre les fichiers à inclure, ou à
exclure.
Alors que les options de ligne de commande --include=glob et --exclude=glob font correspondre les fichiers par rapport au répertoire courant, les expressions de contenu préféré font correspondre les fichiers par rapport à la racine du dépôt
git.
Un glob est quelque chose comme foo.* ou b?r. Les globs peuvent aussi contenir des classes de caractères, comme foo[Bb]ar, ainsi que des classes de caractères POSIX supplémentaires comme [[:space:]]. Ce qui est utile, car un glob dans une expression de contenu préféré ne peut pas contenir d'espaces. Voir la page man glob(7) pour plus d'informations sur les
globs.
Par exemple, supposons que vous placez les fichiers dans des répertoires archive lorsque vous en avez fini avec eux. Vous pourriez alors configurer votre ordinateur portable pour qu'il préfère ne pas conserver ces fichiers, comme ceci : exclude=*/archiv
e/*
Lorsqu'un sous-répertoire est exporté ou importé vers un distant spécial (voir git-annex-export(1) et git-annex-import(1)), ceux-ci sont appariés par rapport à la racine du
sous-répertoire.
Notez que, lorsqu'une commande est exécutée avec l' option --all, ou dans un dépôt nu, aucun nom de fichier n'est associé à un objet annexé, et donc "include=" et "exclude=" ne correspondront
pas.
copies=numb
er
Fait correspondre uniquement les fichiers que git-annex croit avoir le nombre de copies spécifié, ou plus. Notez qu'il ne vérifie pas les distants pour s'assurer que les copies existent
toujours.
Pour décider si le contenu doit être supprimé, git-annex évalue l'expression de contenu préféré en supposant que le contenu a *déjà* été supprimé. Si le contenu ne serait alors pas souhaité, la suppression peut être effectuée. Ainsi, par exemple, copies=2 dans une expression de contenu préféré permet la suppression du contenu uniquement lorsqu'il y a actuellement 3 copies de celui-ci, y compris le dépôt depuis lequel il est supprimé. C'est différent de l'exécution de git annex drop --copies=2, qui supprimera les fichiers qui ont actuellement 2
copies.
copies=trustlevel:
number
Fait correspondre uniquement les fichiers que git-annex croit avoir le nombre de copies spécifié, sur des distants avec le niveau de confiance spécifié. Par exemple, copies=trusted:
2
Pour faire correspondre n'importe quel niveau de confiance égal ou supérieur à un niveau donné, utilisez trustlevel+. Par exemple, copies=semitrusted+:
2
copies=groupname:
number
Fait correspondre uniquement les fichiers que git-annex croit avoir le nombre de copies spécifié, sur des distants dans le groupe spécifié. Par exemple, copies=archive:
2
Les expressions de contenu préféré n'ont pas d'équivalent à l' option --in, mais les groupes peuvent accomplir des choses similaires. Vous pouvez ajouter des dépôts à des groupes, et faire correspondre les groupes dans une expression de contenu préféré. Ainsi, plutôt que --in=usbdrive, mettez toutes les clés USB dans un groupe "transfer", et utilisez copies=transfer:
1

ber
Fait correspondre uniquement les fichiers que git-annex croit nécessiter le nombre ou plus de copies supplémentaires à faire pour satisfaire leurs paramètres
numcopies.
approxlackingcopies=num

Fait en sorte que le contenu soit souhaité s'il est présent, mais pas
autrement.
Cela vous laisse le soin d'utiliser git-annex manuellement pour déplacer le contenu. Vous pouvez utiliser ceci pour éviter que les paramètres de contenu préféré n'affectent un sous-répertoire. Par exemple : auto/* or (include=ad-hoc/* and
present)
Notez que not present n'est pas une chose raisonnable à mettre dans une expression de contenu préféré. Cela indique d'obtenir le contenun'est pas présent, mais alors supprimez-le ! Si cela se retrouve d'une manière ou d'une autre dans une expression de contenu préféré, git-annex reconnaîtra que l'expression de contenu préféré n'est pas stable, et la fera en sorte qu'elle ne corresponde
jamais.
inpreferredd

Le contenu est préféré s'il se trouve dans un répertoire (situé n'importe où dans l'arborescence) portant un nom
particulier.
Le nom du répertoire peut être configuré en utilisant git annex enableremote $remote preferreddir=$dirn
ame
(Si aucun nom de répertoire n'est configuré, il utilise "public" par défaut.
)
Notez que, lorsqu'une commande est exécutée avec l'option --all, ou dans un dépôt nu, aucun nom de fichier n'est associé à un objet annexé, et donc "inpreferreddir" ne correspondra
pas.
standa
rd
git-annex est livré avec des expressions de contenu préféré intégrées, qui peuvent être utilisées avec des dépôts qui sont dans certains groupes standard tels que "client" et
"transfer".
Lorsqu'un dépôt est exactement dans un tel groupe, vous pouvez utiliser le mot-clé "standard" dans son expression de contenu préféré, pour correspondre à tout contenu auquel l'expression du groupe
correspond.
Le plus souvent, l'expression de contenu préféré entière est simplement "standard". Mais, vous pouvez faire des choses plus compliquées, par exemple : standard or include=otherdi
r/*
groupwant
ed
Le mot-clé "groupwanted" peut être utilisé pour faire référence à une expression de contenu préféré qui est associée à un groupe, à condition qu'il y ait exactement une telle expression parmi les groupes auxquels un dépôt appartient. C'est comme le mot-clé "standard", mais vous pouvez configurer les expressions de contenu préféré en utilisant git annex group
wanted.
Lors de la rédaction d'une expression de contenu préféré groupwanted, vous pouvez utiliser tous les mots-clés documentés ici, y compris "standard". (Mais pas "groupwanted".
)
Par exemple, pour faire une variante de l'expression de contenu préféré standard client qui ne veut pas de fichiers dans le répertoire "out", vous pourriez exécuter : git annex groupwanted client "standard and
exclude=out/*"
Ensuite, les dépôts qui sont dans le groupe client et dont l'expression de contenu préféré est définie sur "groupwanted" utiliseront cela, tandis que les autres dépôts client dont l'expression de contenu préféré est définie sur "standard" utiliseront l'expression
standard.
Ou, vous pourriez créer un nouveau groupe, avec votre propre expression de contenu préféré personnalisée adaptée à vos besoins, et chaque dépôt que vous mettez dans ce groupe et dont le contenu préféré est défini sur "groupwanted"
l'utilisera.
Par exemple, le groupe archive ne veut archiver qu'une copie de chaque fichier, répartie parmi tous les dépôts du groupe. Voici comment configurer un groupe nommé redundantarchive, qui veut plutôt contenir 3 copies de chaque fichier
:

git annex groupwanted redundantarchive "not (copies=redundantarchive:3)"
for repo in foo bar baz; do
git annex group $repo redundantarchive
git annex wanted $repo groupwanted
don

unus

Correspond uniquement aux clés que git annex unused a déterminées comme étant
inutilisées.
C'est lié à l'option --unused. Cependant, mettre unused dans une expression de contenu préféré ne fait pas considérer ces clés inutilisées à git-annex. Donc lorsque git-annex ne vérifie que les expressions de contenu préféré contre les fichiers dans le dépôt (qui sont évidemment utilisés), unused dans une expression de contenu préféré ne correspondra à
rien.
Donc quand unused est-il utile dans une expression de contenu préféré
?
En utilisant git annex sync --content --all opérera sur tous les fichiers, y compris les inutilisés, et prendra unused dans les expressions de contenu préféré en
compte.
L'assistant git-annex recherche périodiquement les fichiers inutilisés, et les déplace vers un dépôt dont l'expression de contenu préféré dit qu'il les veut. (Ou, si annex.expireunused est défini, il peut simplement les supprimer.
)
balanced=groupname[:number|:
lackingcopies]
Le contenu est équilibré uniformément parmi les dépôts du
groupe.
Le nombre est le nombre de dépôts dans le groupe qui voudront chaque fichier. Lorsqu'il n'est pas spécifié, la valeur par défaut est
1.
Par exemple, "balanced=backup:2", lorsqu'il y a 3 membres du groupe backup, fera que chaque dépôt backup voudra 2/3 des
fichiers.
Utiliser "lackingcopies" plutôt qu'un nombre fait que chaque fichier est équilibré parmi autant de dépôts dans le groupe que nécessaire pour satisfaire sa configuration numcopies. Par ex., "balanced=backup:lackingcopies", lorsque numcopies est 3 et qu'il y a 1 autre copie, se comportera de la même manière que "balanced=backup:
2".
Pour que l'équilibrage fonctionne, chaque dépôt du groupe devrait avoir son contenu préféré défini sur la même expression. Utiliser groupwanted est une bonne façon de faire
cela.
Les tailles des fichiers ne sont pas prises en compte, il est donc possible qu'un dépôt reçoive des fichiers plus grands que d'habitude et se remplisse donc avant les autres dépôts. Mais les fichiers ne sont désirés que par les dépôts qui ont assez d'espace libre pour les contenir. Donc une fois qu'un dépôt est plein, les dépôts restants auront les fichiers supplémentaires équilibrés parmi eux. Pour que git-annex sache quand un dépôt est plein, vous devez utiliser git-annex-maxsize(1) pour spécifier la taille de chaque dépôt dans le
groupe.
Cela évite généralement de déplacer des fichiers entre les dépôts, même si cela signifie que les choses ne sont pas équilibrées de manière optimale. Certaines des façons dont cela peut déséquilibrer incluent l'ajout d'un nouveau dépôt au groupe, ou un fichier copié dans plus de dépôts dans le groupe que le nombre spécifié, ou certains dépôts qui se
remplissent.
Exécuter des commandes git-annex avec l'option --rebalance fera que cette expression se comporte plutôt comme l'expression fullybalanced, qui fera que les dépôts voudront déplacer des fichiers autour si nécessaire afin d'être complètement
équilibrés.
Utiliser ceci dans une expression de contenu préféré fait que git-annex doit faire un travail supplémentaire pour suivre le niveau de remplissage des dépôts. Habituellement cela n'affectera pas beaucoup les performances. Cependant, la première fois que git-annex traite cette expression dans un dépôt git donné, il devra calculer les tailles de tous les dépôts, ce qui peut être lent lorsqu'il y a beaucoup de fichiers. Lorsque cela fait faire beaucoup de travail à git-annex, il affichera "(calculating repository sizes)
".
Notez que not balanced n'est pas une chose raisonnable à utiliser dans une expression de contenu préféré pour les mêmes raisons que not pres
ent.
fullybalanced=groupname[:number|:
lackingcopies]
C'est comme balanced, mais permet de déplacer du contenu entre les dépôts du groupe à tout moment pour le garder complètement
équilibré.
Normalement "balanced=groupname:number" est la même chose que "(fullybalanced=groupname:number and not copies=groupname:number) or
present"
Lorsque l'option --rebalance est utilisée, balanced est la même chose que fullybalance
d.
Lorsque le nombre spécifié est supérieur à 1, et que trop de dépôts dans le groupe sont plus de 90% pleins (comme configuré par annex.fullybalancedthreshhold), cela se comporte comme fullysizebal
anced.
Par exemple, fullybalanced=foo:3, lorsque le groupe foo a 5 dépôts, deux à 50% pleins et trois à 99% pleins, fera que du contenu se déplacera des dépôts pleins vers les autres. Déplacer du contenu comme cela est coûteux, mais cela permet à de nouveaux fichiers de continuer à être stockés sur le nombre spécifié de
dépôts.
sizebalanced=groupname[:number|:
lackingcopies]
Distribue le contenu parmi les dépôts du groupe, gardant les dépôts proportionnellement
pleins.
Le nombre est le nombre de dépôts dans le groupe qui voudront chaque fichier. Lorsqu'il n'est pas spécifié, la valeur par défaut est
1.
Pour que cela fonctionne, vous devez utiliser git-annex-maxsize(1) pour spécifier la taille de chaque dépôt dans le groupe. Lorsque le maxsize d'un dépôt n'a pas été spécifié, il ne voudra aucun
fichier.
Par exemple, si un dépôt dans le groupe a une taille maximale de 100 gb avec 60 gb utilisés, et qu'un autre a une taille maximale de 50 gb avec 25 gb utilisés, le plus petit voudra des fichiers (qui tiennent en lui), et le plus grand ne voudra aucun fichier (qui tiendrait dans le plus petit) jusqu'à ce que le plus petit soit également
plein.
Notez qu'une fois qu'un dépôt contient un fichier, il continuera de le vouloir, même s'il est plus plein que les autres dépôts. C'est pour éviter les allers-retours dans le déplacement des
fichiers.
C'est plus susceptible de déséquilibrer que l'expression balanced= , parce que git-annex n'a pas toujours une connaissance cohérente du niveau de remplissage des dépôts. Considérez par exemple si un ordinateur portable et un ordinateur de bureau envoient chacun un nouveau fichier au groupe. Ils choisiront tous les deux le dépôt qui était le moins plein, mais cela signifie que les deux fichiers vont dans le même dépôt, alors qu'une meilleure solution aurait pu être d'envoyer le fichier plus petit vers un autre dépôt. Lors de l'utilisation de balanced= dans la même situation, il est moins probable qu'un dépôt veuille les deux
fichiers.

équilibrés.

sent.

TEST

S

Pour vérifier en ligne de commande quels fichiers correspondent aux paramètres de contenu préféré d'un dépôt, vous pouvez utiliser les options --want-get et

--want-drop.

Par exemple, git annex find --want-get --not --in . trouvera tous les fichiers que git annex get --auto souhaitera récupérer, et git annex find --want-drop --in . trouvera tous les fichiers que git annex drop --auto souhaitera

supprimer.

L'option --explain peut être utilisée pour comprendre pourquoi une expression complexe de contenu préféré correspond ou ne correspond pas. L'expression sera affichée, chaque terme étant suivi de "[TRUE]" ou "[FALSE]" pour indiquer la valeur. Les termes non pertinents seront omis de l'explication, par exemple "exclude=* and copies=1" sera affiché comme "exclu

de=*[F
ALSE]"
