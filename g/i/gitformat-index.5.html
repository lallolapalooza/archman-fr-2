gitformat-index - Format de l'index Git

SYNOPSIS

$GIT_DIR/index

DESCRIPTION

Format de l'index Git

ENTRÉE D'INDEX

Les entrées d'index sont triées en ordre croissant sur le champ nom,
interprété comme une chaîne d'octets non signés (c'est-à-dire l'ordre de
memcmp(), sans localisation, sans traitement spécial du séparateur de
répertoire '/'). Les entrées portant le même nom sont triées par leur champ
de niveau.
Une entrée d'index représente généralement un fichier. Cependant, si le
sparse-checkout est activé en mode cône (`core.sparseCheckoutCone` est activé)
et que l'extension `extensions.sparseIndex` est activée, l'index peut contenir
des entrées pour des répertoires en dehors de la définition du
sparse-checkout. Ces entrées ont le mode `040000`, incluent le bit
`SKIP_WORKTREE`, et le chemin se termine par un séparateur de répertoire.
secondes de ctime sur 32 bits, dernière fois où les métadonnées d'un
  fichier ont changé
  ce sont des données stat(2)
fractions de nanosecondes de ctime sur 32 bits
  ce sont des données stat(2)
secondes de mtime sur 32 bits, dernière fois où les données d'un
  fichier ont changé
  ce sont des données stat(2)
fractions de nanosecondes de mtime sur 32 bits
  ce sont des données stat(2)
dev sur 32 bits
  ce sont des données stat(2)
ino sur 32 bits
  ce sont des données stat(2)
mode sur 32 bits, divisé en (bits de haut en bas)
16 bits inutilisés, doivent être à zéro
type d'objet sur 4 bits
  les valeurs valides en binaire sont 1000 (fichier ordinaire), 1010 (lien
  symbolique) et 1110 (gitlink)
3 bits inutilisés, doivent être à zéro
permissions unix sur 9 bits. Seuls 0755 et 0644 sont valides pour les
fichiers ordinaires. Les liens symboliques et les gitlinks ont la valeur 0
dans ce champ.
uid sur 32 bits
  ce sont des données stat(2)
gid sur 32 bits
  ce sont des données stat(2)
taille du fichier sur 32 bits
  C'est la taille sur disque issue de stat(2), tronquée à 32 bits.
Nom de l'objet pour l'objet représenté
Un champ « flags » de 16 bits divisé en (bits de haut en bas)
drapeau assume-valid sur 1 bit
drapeau étendu sur 1 bit (doit être à zéro en version 2)
niveau sur 2 bits (pendant une fusion)
longueur du nom sur 12 bits si la longueur est inférieure à 0xFFF ;
sinon 0xFFF est stocké dans ce champ.
(Version 3 ou ultérieure) Un champ de 16 bits, uniquement applicable si
le « drapeau étendu » ci-dessus vaut 1, divisé en (bits de haut en bas).
1 bit réservé pour l'avenir
drapeau skip-worktree sur 1 bit (utilisé par le sparse checkout)
drapeau intent-to-add sur 1 bit (utilisé par « git add -N »)
13 bits inutilisés, doivent être à zéro
Nom de chemin de l'entrée (longueur variable) relatif au répertoire de
  niveau supérieur (sans barre oblique initiale). '/' est utilisé comme
  séparateur de chemin. Les composants de chemin spéciaux « . », « .. » et
  « .git » (sans guillemets) sont interdits. La barre oblique finale est
  également interdite.
L'encodage exact n'est pas défini, mais les caractères '.' et '/' sont
encodés en ASCII 7 bits et l'encodage ne peut pas contenir d'octet NUL
(c'est-à-dire, c'est un chemin UNIX).
(Version 4) En version 4, le nom de chemin de l'entrée est compressé par
préfixe par rapport au nom de chemin de l'entrée précédente (la toute première
entrée est encodée comme si le nom de chemin de l'entrée précédente était une
chaîne vide). Au début d'une entrée, un entier N en codage de largeur variable
(le même codage que celui de l'offset pour les entrées de paquet OFS_DELTA ;
voir linkgit:gitformat-pack[5]) est stocké, suivi d'une chaîne S terminée par
NUL. En supprimant N octets de la fin du nom de chemin de l'entrée précédente
et en les remplaçant par la chaîne S, on obtient le nom de chemin de cette
entrée.
1 à 8 octets nul si nécessaire pour aligner l'entrée sur un multiple de
huit octets tout en gardant le nom terminé par NUL.
(Version 4) En version 4, le remplissage après le nom de chemin n'existe
pas.
L'interprétation des entrées d'index en mode index scindé est
complètement différente. Voir ci-dessous pour les détails.

EXTENSIONS

Cache tree

Puisque l'index n'enregistre pas d'entrées pour les répertoires, les
entrées de cache ne peuvent pas décrire des objets arbre qui existent déjà dans
la base d'objets pour les régions de l'index qui sont inchangées par rapport à
un commit existant. L'extension cache tree stocke une structure arbre récursive
qui décrit les arbres qui existent déjà et correspondent exactement aux sections
des entrées de cache. Cela accélère la génération d'objets arbre à partir de
l'index pour un nouveau commit en ne calculant que les arbres qui sont «
nouveaux » pour ce commit. Cela aide aussi lors de la comparaison de l'index à
un autre arbre, comme `HEAD^{tree}`, car des sections de l'index peuvent être
ignorées quand une comparaison d'arbres démontre l'égalité.
La structure arbre récursive utilise des nœuds qui stockent un nombre
d'entrées de cache, une liste de sous-nœuds, et un identifiant d'objet (OID).
L'OID référence l'arbre existant pour ce nœud, s'il est connu pour exister. Les
sous-nœuds correspondent aux sous-répertoires qui ont eux-mêmes des nœuds de
cache tree. Le nombre d'entrées de cache correspond au nombre d'entrées de
cache dans l'index qui décrivent des chemins à l'intérieur du répertoire de cet
arbre.
L'extension suit toute la structure de répertoires dans l'extension cache
tree, mais celle-ci est généralement plus petite que la liste complète des
entrées de cache.
Quand un chemin est mis à jour dans l'index, Git invalide tous les nœuds
de l'arbre de cache récursif correspondant aux répertoires parents de ce chemin.
Nous stockons ces nœuds d'arbre comme étant « invalides » en utilisant « -1 »
comme nombre d'entrées de cache. Les nœuds invalides stockent toujours une
plage d'entrées d'index, permettant à Git de concentrer ses efforts lors de la
reconstruction d'un arbre de cache complet.
La signature de cette extension est { 'T', 'R', 'E', 'E' }.
Une série d'entrées remplit toute l'extension ; chacune consiste en :
•composant de chemin terminé par NUL (relatif à son répertoire parent) ;
•nombre en décimal ASCII d'entrées dans l'index qui sont couvertes par l'arbre que cette entrée représente (entry_count) ;
•un espace (ASCII 32) ;
•nombre en décimal ASCII qui représente le nombre de sous-arbres que cet arbre possède ;
•un saut de ligne (ASCII 10) ; et
•nom de l'objet qui résulterait de l'écriture de cette plage d'index en tant qu'arbre. 
Une entrée peut être dans un état invalidé et est représentée par un
nombre négatif dans le champ entry_count. Dans ce cas, il n'y a pas de
nom d'objet et l'entrée suivante commence immédiatement après le saut
de ligne. Lors de l'écriture d'une entrée invalide, -1 doit toujours être
utilisé comme entry_count.
Les entrées sont écrites dans un ordre descendant, en profondeur. La
première entrée représente le niveau racine du dépôt, suivie par le
premier sous-arbre -- appelons-le A -- du niveau racine (avec son nom
relatif au niveau racine), suivie par le premier sous-arbre de A (avec
son nom relatif à A), et ainsi de suite. Le nombre spécifié de sous-arbres
indique quand le niveau actuel de la pile récursive est terminé.

Résoudre l'annulation

Un conflit est représenté dans l'index par un ensemble d'entrées de
niveau supérieur. Lorsqu'un conflit est résolu (par exemple avec "git
add path"), ces entrées de niveau supérieur seront supprimées et une
entrée de niveau 0 avec la résolution appropriée sera ajoutée.
Lorsque ces entrées de niveau supérieur sont supprimées, elles sont
sauvegardées dans l'extension de résolution d'annulation, afin que les
conflits puissent être recréés (par exemple avec "git checkout -m"),
au cas où les utilisateurs voudraient refaire une résolution de conflit
à partir de zéro.
La signature de cette extension est { 'R', 'E', 'U', 'C' }.
Une série d'entrées remplit l'extension entière ; chacune d'elles
consiste en :
•Le chemin d'accès NUL-terminé que l'entrée décrit (relatif à la racine du dépôt, c'est-à-dire le chemin d'accès complet) ;
•Trois nombres octaux ASCII NUL-terminés, le mode d'entrée des entrées aux niveaux 1 à 3 (un niveau manquant est représenté par "0" dans ce champ) ; et
•Au plus trois noms d'objet de l'entrée aux niveaux 1 à 3 (rien n'est écrit pour un niveau manquant).

Index divisé

En mode d'index divisé, la majorité des entrées d'index peuvent être
stockées dans un fichier séparé. Cette extension enregistre les changements
à apporter par-dessus cela pour produire l'index final.
La signature de cette extension est { 'l', 'i', 'n', 'k' }.
L'extension consiste en :
•Le hachage du fichier d'index partagé. Le chemin du fichier d'index partagé est $GIT_DIR/sharedindex.<hash>. Si tous les bits sont à zéro, l'index ne nécessite pas de fichier d'index partagé.
•Un bitmap de suppression encodé en ewah, chaque bit représente une entrée dans l'index partagé. Si un bit est défini, son entrée correspondante dans l'index partagé sera supprimée de l'index final. Notez que, comme une opération de suppression modifie les positions des entrées d'index, mais que nous avons besoin des positions d'origine lors de la phase de remplacement, il est préférable de simplement marquer les entrées pour suppression, puis d'effectuer une suppression en masse après le remplacement.
•Un bitmap de remplacement encodé en ewah, chaque bit représente une entrée dans l'index partagé. Si un bit est défini, son entrée correspondante dans l'index partagé sera remplacée par une entrée dans ce fichier d'index. Toutes les entrées remplacées sont stockées dans l'ordre trié dans cet index. Le premier bit "1" dans le bitmap de remplacement correspond à la première entrée d'index, le deuxième bit "1" à la deuxième entrée, et ainsi de suite. Les entrées remplacées peuvent avoir des noms de fichier vides pour économiser de l'espace. 
Les entrées d'index restantes après les entrées remplacées seront ajoutées
à l'index final. Ces entrées ajoutées sont également triées par nom d'entrée,
puis par niveau.

CACHE DES FICHIERS NON SUIVIS

Le cache des fichiers non suivis sauvegarde la liste des fichiers non suivis
et les données nécessaires pour vérifier le cache. La signature de cette
extension est { 'U', 'N', 'T', 'R' }.
L'extension commence par
•Une séquence de chaînes NUL-terminées, précédée par la taille de la séquence en encodage de largeur variable. Chaque chaîne décrit l'environnement dans lequel le cache peut être utilisé.
•Les données stat de $GIT_DIR/info/exclude. Voir la section "Entrée d'index" du champ ctime jusqu'à "taille du fichier".
•Les données stat de core.excludesFile
•dir_flags 32 bits (voir la structure dir_struct)
•Le hachage de $GIT_DIR/info/exclude. Un hachage nul signifie que le fichier n'existe pas.
•Le hachage de core.excludesFile. Un hachage nul signifie que le fichier n'existe pas.
•La chaîne NUL-terminée du nom du fichier d'exclusion par répertoire. C'est généralement ".gitignore".
•Le nombre de blocs de répertoires suivants, encodage de largeur variable. Si ce nombre est zéro, l'extension se termine ici avec un NUL suivant.
•Un nombre de blocs de répertoires dans l'ordre de parcours en profondeur, chacun consistant en
•Le nombre d'entrées non suivies, encodage de largeur variable.
•Le nombre de blocs de sous-répertoires, encodage de largeur variable.
•Le nom du répertoire terminé par NUL.
•Un nombre de noms de fichiers/répertoires non suivis terminés par NUL.

Les données restantes de chaque bloc de répertoire sont groupées par type :

•Un bitmap ewah, le n-ième bit indique si le n-ième répertoire a des entrées de cache non suivies valides.
•Un bitmap ewah, le n-ième bit enregistre le bit "check-only" de read_directory_recursive() pour le n-ième répertoire.
•Un bitmap ewah, le n-ième bit indique si les données de hachage et stat sont valides pour le n-ième répertoire et existent dans les données suivantes.
•Un tableau de données stat. La n-ième donnée correspond au n-ième bit "un" dans le bitmap ewah précédent.
•Un tableau de hachages. Le n-ième hachage correspond au n-ième bit "un" dans le bitmap ewah précédent.
•Un NUL.

CACHE DU MONITEUR DE SYSTÈME DE FICHIERS

Le cache du moniteur de système de fichiers suit les fichiers pour lesquels
le hook core.fsmonitor nous a informé de changements. La signature de cette
extension est { 'F', 'S', 'M', 'N' }.
L'extension commence par
•Un numéro de version 32 bits : les versions prises en charge actuellement sont 1 et 2.
•(Version 1) Une heure 64 bits : les données de l'extension reflètent tous les changements jusqu'à l'heure donnée, qui est stockée comme les nanosecondes écoulées depuis minuit, le 1er janvier 1970.
•(Version 2) Une chaîne de caractères nulle terminée : un jeton opaque défini par l'application du moniteur de système de fichiers. Les données de l'extension reflètent tous les changements relatifs à ce jeton.
•La taille du bitmap 32 bits : la taille du bitmap CE_FSMONITOR_VALID.
•Un bitmap ewah, le n-ième bit indique si la n-ième entrée d'index n'est pas CE_FSMONITOR_VALID.

FIN DE L'ENTRÉE D'INDEX

La Fin de l'Entrée d'Index (EOIE) est utilisée pour localiser la fin des
entrées d'index de longueur variable et le début des extensions. Le code peut
profiter de cela pour localiser rapidement les extensions d'index sans avoir
à parcourir toutes les entrées d'index.
Comme elle doit pouvoir être chargée avant les entrées de cache de longueur
variable et d'autres extensions d'index, cette extension doit être écrite en
dernier. La signature de cette extension est { 'E', 'O', 'I', 'E' }.
L'extension consiste en :
•Un décalage 32 bits vers la fin des entrées d'index
•Un hachage sur les types d'extension et leurs tailles (mais pas leur contenu). Par exemple, si nous avons une extension "TREE" de N octets, une extension "REUC" de M octets, suivie de "EOIE", alors le hachage serait : 
Hash("TREE" + <représentation-binaire-de-N> +
        "REUC" + <représentation-binaire-de-M>)

TABLE DES DÉCALAGES DES ENTRÉES D'INDEX

La Table des Décalages des Entrées d'Index (IEOT) est utilisée pour aider
à gérer le coût CPU du chargement de l'index en permettant le multithreading
du processus de conversion des entrées de cache du format sur disque au format
en mémoire. La signature de cette extension est { 'I', 'E', 'O', 'T' }.
L'extension consiste en :
•Un numéro de version 32 bits (actuellement 1)
•Un nombre d'entrées de décalage d'index, chacune consistant en :
•Un décalage 32 bits depuis le début du fichier jusqu'à la première entrée de cache dans ce bloc d'entrées.
•Un compte 32 bits d'entrées de cache dans ce bloc

ENTRÉES DE RÉPERTOIRE ÉPARSES

Lors de l'utilisation du checkout éparse en mode cône, certains répertoires
entiers dans l'index peuvent être résumés en pointant vers un objet arbre
au lieu de la liste complète des chemins d'accès à l'intérieur de cet arbre.
Un index contenant de telles entrées est un "index éparse". Les versions
d'index 4 et inférieures n'ont pas été implémentées en pensant à de telles
entrées. Ainsi, pour ces versions, un index contenant des entrées de répertoire
éparses inclura cette extension avec la signature { 's', 'd', 'i', 'r' }.
Comme l'extension d'index divisé, les outils doivent éviter d'interagir avec
un index éparse à moins qu'ils ne comprennent cette extension.
