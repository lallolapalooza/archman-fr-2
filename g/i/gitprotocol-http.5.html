NOM

gitprotocol-http - Protocoles basés sur HTTP de Git

SYNTAXE

<protocole-sur-le-fil>

DESCRIPTION

Git prend en charge deux protocoles de transfert basés sur HTTP. Un protocole « dumb » (bête) qui ne nécessite qu'un serveur HTTP standard côté serveur de la connexion, et un protocole « smart » (intelligent) qui nécessite un CGI adapté à Git (ou un module serveur). Ce document décrit les deux protocoles.

Par conception, les clients intelligents peuvent mettre à niveau automatiquement les URL du protocole « dumb » vers des URL « smart ». Cela permet à tous les utilisateurs d'avoir la même URL publiée, et aux pairs de sélectionner automatiquement le transport le plus efficace dont ils disposent.

FORMAT DES URL

Les URL pour les dépôts Git accédés par HTTP utilisent la syntaxe standard des URL HTTP documentée par la RFC 1738, donc elles sont de la forme :

http://<hôte>:<port>/<chemin>?<partie-recherche>

Dans cette documentation, le substitut $GIT_URL représentera l'URL du dépôt http:// saisie par l'utilisateur.

Les serveurs DOIVENT gérer toutes les requêtes aux emplacements correspondant à $GIT_URL, car les protocoles HTTP « smart » et « dumb » utilisés par Git fonctionnent en ajoutant des composants de chemin supplémentaires à la fin de la chaîne $GIT_URL fournie par l'utilisateur.

Un exemple de client « dumb » demandant un objet lâche :

$GIT_URL:     http://example.com:8080/git/repo.git
URL demandée :  http://example.com:8080/git/repo.git/objects/d0/49f6c27a2244e12041955e262a404c7faba355

Un exemple de requête « smart » vers une passerelle « catch-all » :

$GIT_URL:     http://example.com/daemon.cgi?svc=git&q=
URL demandée :  http://example.com/daemon.cgi?svc=git&q=/info/refs&service=git-receive-pack

Un exemple de requête vers un sous-module :

$GIT_URL:     http://example.com/git/repo.git/path/submodule.git
URL demandée :  http://example.com/git/repo.git/path/submodule.git/info/refs

Les clients DOIVENT supprimer un / final, s'il est présent, de la chaîne $GIT_URL fournie par l'utilisateur pour éviter que des jetons de chemin vides (//) n'apparaissent dans toute URL envoyée à un serveur. Les clients compatibles DOIVENT développer $GIT_URL/info/refs en foo/info/refs et non en foo//info/refs.

AUTHENTIFICATION

L'authentification HTTP standard est utilisée si une authentification est nécessaire pour accéder à un dépôt, et PEUT être configurée et appliquée par le logiciel serveur HTTP.

Étant donné que les dépôts Git sont accessibles par des composants de chemin standard, les administrateurs de serveur PEUVENT utiliser des permissions basées sur les répertoires au sein de leur serveur HTTP pour contrôler l'accès au dépôt.

Les clients DEVRAIENT prendre en charge l'authentification Basic telle que décrite par la RFC 2617. Les serveurs DEVRAIENT prendre en charge l'authentification Basic en s'appuyant sur le serveur HTTP placé devant le logiciel serveur Git.

Les serveurs NE DEVRAIENT PAS exiger de cookies HTTP pour l'authentification ou le contrôle d'accès.

Les clients et les serveurs PEUVENT prendre en charge d'autres formes courantes d'authentification basée sur HTTP, telles que l'authentification Digest.

SSL

Les clients et les serveurs DEVRAIENT prendre en charge SSL, en particulier pour protéger les mots de passe lors de l'utilisation de l'authentification HTTP Basic.

ETAT DE SESSION

Le protocole Git sur HTTP (un peu comme HTTP lui-même) est sans état du point de vue du serveur HTTP. Tout état DOIT être conservé et géré par le processus client. Cela permet un équilibrage de charge simple en mode « round-robin » côté serveur, sans avoir à se soucier de la gestion de l'état.

Les clients NE DOIVENT PAS exiger de gestion d'état côté serveur pour fonctionner correctement.

Les serveurs NE DOIVENT PAS exiger de cookies HTTP pour fonctionner correctement. Les clients PEUVENT stocker et transmettre des cookies HTTP lors du traitement des requêtes, tel que décrit par la RFC 2616 (HTTP/1.1). Les serveurs DOIVENT ignorer tout cookie envoyé par un client.

TRAITEMENT GENERAL DES REQUETES

Sauf indication contraire, tous les comportements HTTP standard DEVRAIENT être supposés par le client et le serveur. Cela inclut (mais sans s'y limiter) :

S'il n'y a pas de dépôt à $GIT_URL, ou si la ressource pointée par un emplacement correspondant à $GIT_URL n'existe pas, le serveur NE DOIT PAS répondre avec une réponse 200 OK. Un serveur DEVRAIT répondre avec 404 Not Found, 410 Gone, ou tout autre code de statut HTTP approprié qui n'implique pas que la ressource existe comme demandé.

S'il y a un dépôt à $GIT_URL, mais que l'accès n'est pas actuellement autorisé, le serveur DOIT répondre avec le code de statut HTTP 403 Forbidden.

Les serveurs DEVRAIENT prendre en charge HTTP 1.0 et HTTP 1.1. Les serveurs DEVRAIENT prendre en charge le codage par morceaux (chunked encoding) pour les corps de requêtes et de réponses.

Les clients DEVRAIENT prendre en charge HTTP 1.0 et HTTP 1.1. Les clients DEVRAIENT prendre en charge le codage par morceaux pour les corps de requêtes et de réponses.

Les serveurs PEUVENT renvoyer des en-têtes ETag et/ou Last-Modified.

Les clients PEUVENT revalider les entités mises en cache en incluant les en-têtes de requête If-Modified-Since et/ou If-None-Match.

Les serveurs PEUVENT renvoyer 304 Not Modified si les en-têtes pertinents apparaissent dans la requête et que l'entité n'a pas changé. Les clients DOIVENT traiter 304 Not Modified comme 200 OK en réutilisant l'entité mise en cache.

Les clients PEUVENT réutiliser une entité mise en cache sans revalidation si l'en-tête Cache-Control et/ou Expires permet la mise en cache. Les clients et les serveurs DOIVENT suivre la RFC 2616 pour les contrôles de cache.

DECOUVERTE DES REFERENCES

Tous les clients HTTP DOIVENT commencer un échange de fetch ou de push en découvrant les références disponibles sur le dépôt distant.

Clients Dumb

Les clients HTTP qui ne prennent en charge que le protocole « dumb » DOIVENT découvrir les références en effectuant une requête pour le fichier spécial info/refs du dépôt.

Les clients HTTP « dumb » DOIVENT effectuer une requête GET vers $GIT_URL/info/refs, sans aucun paramètre de recherche / requête.

C: GET $GIT_URL/info/refs HTTP/1.0
S: 200 OK
S:
S: 95dcfa3633004da0049d3d0fa03f80589cbcaf31  refs/heads/maint
S: d049f6c27a2244e12041955e262a404c7faba355  refs/heads/master
S: 2cb58b79488a98d2721cea644875a8dd0026b115  refs/tags/v1.0
S: a3c2e2402b99163d1d59756e5f207ae21cccba4c  refs/tags/v1.0^{}

Le Content-Type de l'entité info/refs renvoyée DEVRAIT être text/plain ; charset=utf-8, mais PEUT être n'importe quel type de contenu. Les clients NE DOIVENT PAS tenter de valider le Content-Type renvoyé. Les serveurs « dumb » NE DOIVENT PAS renvoyer un type de retour commençant par application/x-git-.

Les en-têtes Cache-Control PEUVENT être renvoyés pour désactiver la mise en cache de l'entité renvoyée.

Lors de l'examen de la réponse, les clients DEVRAIENT uniquement examiner le code de statut HTTP. Les réponses valides sont 200 OK, ou 304 Not Modified.

Le contenu renvoyé est un fichier texte formaté UNIX décrivant chaque référence et sa valeur connue. Le fichier DEVRAIT être trié par nom selon l'ordre de locale C. Le fichier NE DEVRAIT PAS inclure la référence par défaut nommée HEAD.

info_refs   =  *( ref_record )
ref_record  =  any_ref / peeled_ref
any_ref     =  obj-id HTAB refname LF
peeled_ref  =  obj-id HTAB refname LF
               obj-id HTAB refname "^{}" LF

Clients Smart

Les clients HTTP qui prennent en charge le protocole « smart » (ou les deux protocoles « smart » et « dumb ») DOIVENT découvrir les références en effectuant une requête paramétrée pour le fichier info/refs du dépôt.

La requête DOIT contenir exactement un paramètre de requête, service=$nom_service, où $nom_service DOIT être le nom du service que le client souhaite contacter pour terminer l'opération. La requête NE DOIT PAS contenir de paramètres de requête supplémentaires.

C: GET $GIT_URL/info/refs?service=git-upload-pack HTTP/1.0

réponse du serveur « dumb » :

S: 200 OK
S:
S: 95dcfa3633004da0049d3d0fa03f80589cbcaf31  refs/heads/maint
S: d049f6c27a2244e12041955e262a404c7faba355  refs/heads/master
S: 2cb58b79488a98d2721cea644875a8dd0026b115  refs/tags/v1.0
S: a3c2e2402b99163d1d59756e5f207ae21cccba4c  refs/tags/v1.0^{}

réponse du serveur « smart » :

S: 200 OK
S: Content-Type: application/x-git-upload-pack-advertisement
S: Cache-Control: no-cache
S:
S: 001e# service=git-upload-pack\n
S: 0000
S: 004895dcfa3633004da0049d3d0fa03f80589cbcaf31 refs/heads/maint\0multi_ack\n
S: 003fd049f6c27a2244e12041955e262a404c7faba355 refs/heads/master\n
S: 003c2cb58b79488a98d2721cea644875a8dd0026b115 refs/tags/v1.0\n
S: 003fa3c2e2402b99163d1d59756e5f207ae21cccba4c refs/tags/v1.0^{}\n
S: 0000

Le client peut envoyer des Paramètres Supplémentaires (voir gitprotocol-pack(5)) sous forme de chaîne séparée par des deux-points dans l'en-tête HTTP Git-Protocol.

Utilise l'option --http-backend-info-refs de git-upload-pack(1).

Réponse du serveur « dumb »

Les serveurs « dumb » DOIVENT répondre avec le format de réponse du serveur « dumb ».

Voir la section précédente sur les clients « dumb » pour une description plus détaillée de la réponse du serveur « dumb ».

Réponse du serveur « smart »

Si le serveur ne reconnaît pas le nom de service demandé, ou si le nom de service demandé a été désactivé par l'administrateur du serveur, le serveur DOIT répondre avec le code de statut HTTP 403 Forbidden .

Sinon, les serveurs « smart » DOIVENT répondre avec le format de réponse du serveur « smart » pour le nom de service demandé.

Les en-têtes Cache-Control devraient être utilisés pour désactiver la mise en cache de l'entité retournée.

Le Content-Type DOIT être application/x-$servicename-advertisement. Les clients devraient revenir au protocole « dumb » si un autre type de contenu est renvoyé. Lors du retour au protocole « dumb », les clients ne devraient PAS effectuer une requête supplémentaire vers $GIT_URL/info/refs, mais devraient plutôt utiliser la réponse déjà en main. Les clients NE DOIVENT PAS continuer s'ils ne prennent pas en charge le protocole « dumb ».

Les clients DOIVENT valider que le code de statut est soit 200 OK soit 304 Not Modified.

Les clients DOIVENT valider que les cinq premiers octets de l'entité de la réponse correspondent à l'expression régulière ^[0-9a-f]{4}#. Si ce test échoue, les clients NE DOIVENT PAS continuer.

Les clients DOIVENT analyser l'intégralité de la réponse comme une séquence d'enregistrements pkt-line.

Les clients DOIVENT vérifier que le premier pkt-line est # service=$servicename. Les serveurs DOIVENT définir $servicename comme la valeur du paramètre de requête. Les serveurs devraient inclure un LF à la fin de cette ligne. Les clients DOIVENT ignorer un LF à la fin de la ligne.

Les serveurs DOIVENT terminer la réponse avec le marqueur pkt-line magique 0000 end

La réponse retournée est un flux pkt-line décrivant chaque ref et sa valeur connue. Le flux devrait être trié par nom selon l'ordre de la locale C. Le flux devrait inclure la ref par défaut nommée HEAD comme première ref. Le flux DOIT inclure les déclarations de capacités derrière un NUL sur la première ref.

La réponse retournée contient "version 1" si "version=1" a été envoyé comme Paramètre Supplémentaire.

smart_reply     =  PKT-LINE("# service=$servicename" LF)
                   "0000"
                   *1("version 1")
                   ref_list
                   "0000"
ref_list        =  empty_list / non_empty_list
empty_list      =  PKT-LINE(zero-id SP "capabilities^{}" NUL cap-list LF)
non_empty_list  =  PKT-LINE(obj-id SP name NUL cap_list LF)
                   *ref_record
cap-list        =  capability *(SP capability)
capability      =  1*(LC_ALPHA / DIGIT / "-" / "_")
LC_ALPHA        =  %x61-7A
ref_record      =  any_ref / peeled_ref
any_ref         =  PKT-LINE(obj-id SP name LF)
peeled_ref      =  PKT-LINE(obj-id SP name LF)
                   PKT-LINE(obj-id SP name "^{}" LF

SERVICE INTELLIGENT GIT-UPLOAD-PACK

Ce service lit depuis le dépôt pointé par $GIT_URL.

Les clients DOIVENT d'abord effectuer la découverte des refs avec $GIT_URL/info/refs?service=git-upload-pack.

C: POST $GIT_URL/git-upload-pack HTTP/1.0
C: Content-Type: application/x-git-upload-pack-request
C:
C: 0032want 0a53e9ddeaddad63ad106860237bbf53411d11a7\n
C: 0032have 441b40d833fdfa93eb2908e52742248faf0ee993\n
C: 0000
S: 200 OK
S: Content-Type: application/x-git-upload-pack-result
S: Cache-Control: no-cache
S:
S: ....ACK %s, continue
S: ....NAK

Les clients NE DOIVENT PAS réutiliser ni revalider une réponse mise en cache. Les serveurs DOIVENT inclure des en-têtes Cache-Control suffisants pour empêcher la mise en cache de la réponse.

Les serveurs devraient prendre en charge toutes les capacités définies ici.

Les clients DOIVENT envoyer au moins une commande "want" dans le corps de la requête. Les clients NE DOIVENT PAS référencer un identifiant dans une commande "want" qui n'est pas apparu dans la réponse obtenue par la découverte des refs, sauf si le serveur annonce la capacité allow-tip-sha1-in-want ou allow-reachable-sha1-in-want.

compute_request   =  want_list
                     have_list
                     request_end
request_end       =  "0000" / "done"
want_list         =  PKT-LINE(want SP cap_list LF)
                     *(want_pkt)
want_pkt          =  PKT-LINE(want LF)
want              =  "want" SP id
cap_list          =  capability *(SP capability)
have_list         =  *PKT-LINE("have" SP id LF)

L'algorithme de négociation

Le calcul pour sélectionner le pack minimal se déroule comme suit (C = client, S = serveur) :

étape d'initialisation :

C : Utiliser la découverte des refs pour obtenir les refs annoncées.

C : Placer tout objet vu dans l'ensemble advertised.

C : Construire un ensemble vide, common, pour contenir les objets qui sont plus tard déterminés comme étant présents des deux côtés.

C : Construire un ensemble, want, des objets de advertised que le client veut récupérer, basé sur ce qu'il a vu lors de la découverte des refs.

C : Démarrer une file d'attente, c_pending, ordonnée par heure de commit (en extrayant le plus récent en premier). Ajouter toutes les refs du client. Quand un commit est extrait de la file, ses parents devraient être automatiquement réinsérés. Les commits NE DOIVENT entrer dans la file qu'une seule fois.

une étape de calcul :

C : Envoyer une requête $GIT_URL/git-upload-pack :

C: 0032want <want-#1>...............................
C: 0032want <want-#2>...............................
....
C: 0032have <common-#1>.............................
C: 0032have <common-#2>.............................
....
C: 0032have <have-#1>...............................
C: 0032have <have-#2>...............................
....
C: 0000

Le flux est organisé en « commandes », chaque commande apparaissant seule dans un pkt-line. Dans une ligne de commande, le texte précédant le premier espace est le nom de la commande, et le reste de la ligne jusqu'au premier LF est la valeur. Les lignes de commande sont terminées par un LF comme dernier octet de la valeur du pkt-line.

Les commandes DOIVENT apparaître dans l'ordre suivant, si elles apparaissent du tout dans le flux de requête :

•"want"
•"have"

Le flux est terminé par un flush pkt-line (0000).

Une seule commande "want" ou "have" DOIT avoir un nom d'objet au format hexadécimal comme valeur. Plusieurs noms d'objets DOIVENT être envoyés en envoyant plusieurs commandes. Les noms d'objets DOIVENT être donnés en utilisant le format d'objet négocié via la capacité object-format (SHA-1 par défaut).

La liste have est créée en extrayant les 32 premiers commits de c_pending. Moins peuvent être fournis si c_pending se vide.

Si le client a envoyé 256 commits "have" et n'en a pas encore reçu un en retour de s_common, ou si le client a vidé c_pending , il devrait inclure une commande "done" pour informer le serveur qu'il ne continuera pas :

C: 0009done

S : Analyser la requête git-upload-pack :

Vérifier que tous les objets dans want sont directement accessibles depuis les refs.

Le serveur PEUT remonter dans l'historique ou à travers le reflog pour permettre des requêtes légèrement obsolètes.

Si aucun objet "want" n'est reçu, envoyer une erreur : À FAIRE : Définir l'erreur si aucune ligne "want" n'est demandée.

Si un objet "want" n'est pas accessible, envoyer une erreur : À FAIRE : Définir l'erreur si un "want" invalide est demandé.

Créer une liste vide, s_common.

Si "have" a été envoyé :

Parcourir les objets dans l'ordre fourni par le client.

Pour chaque objet, si le serveur a l'objet accessible depuis une ref, l'ajouter à s_common. Si un commit est ajouté à s_common, ne pas ajouter d'ancêtres, même s'ils apparaissent aussi dans have.

S : Envoyer la réponse git-upload-pack :

Si le serveur a trouvé un ensemble fermé d'objets à packer ou si la requête se termine par "done", il répond avec le pack. À FAIRE : Documenter la réponse basée sur le pack

S: PACK...

Le flux retourné est le protocole side-band-64k pris en charge par le service git-upload-pack, et le pack est intégré dans le flux 1. Les messages de progression côté serveur PEUVENT apparaître dans le flux 2.

Ici, un « ensemble fermé d'objets » est défini comme ayant au moins un chemin de chaque "want" à au moins un objet "common".

Si le serveur a besoin de plus d'informations, il répond avec une réponse de statut continue : À FAIRE : Documenter la réponse non-pack

C : Analyser la réponse d'upload-pack : À FAIRE : Documenter l'analyse de la réponse

Effectuer une autre étape de calcul.

SERVICE INTELLIGENT GIT-RECEIVE-PACK

Ce service litrom le dépôt pointé par $GIT_URL.

Les clients DOIVENT d'abord effectuer la découverte des refs avec $GIT_URL/info/refs?service=git-receive-pack.

C: POST $GIT_URL/git-receive-pack HTTP/1.0
C: Content-Type: application/x-git-receive-pack-request
C:
C: ....0a53e9ddeaddad63ad106860237bbf53411d11a7 441b40d833fdfa93eb2908e52742248faf0ee993 refs/heads/maint\0 report-status
C: 0000
C: PACK....
S: 200 OK
S: Content-Type: application/x-git-receive-pack-result
S: Cache-Control: no-cache
S:
S: ....

Les clients NE DOIVENT PAS réutiliser ni revalider une réponse mise en cache. Les serveurs DOIVENT inclure des en-têtes Cache-Control suffisants pour empêcher la mise en cache de la réponse.

Les serveurs DEVRAIENT prendre en charge toutes les capacités définies ici.

Les clients DOIVENT envoyer au moins une commande dans le corps de la requête. Dans la partie commande du corps de la requête, les clients DEVRAIENT envoyer l'identifiant obtenu lors de la découverte des refs comme old_id.

update_request  =  command_list
                   "PACK" <binary-data>
command_list    =  PKT-LINE(command NUL cap_list LF)
                   *(command_pkt)
command_pkt     =  PKT-LINE(command LF)
cap_list        =  *(SP capability) SP
command         =  create / delete / update
create          =  zero-id SP new_id SP name
delete          =  old_id SP zero-id SP name
update          =  old_id SP new_id SP name
