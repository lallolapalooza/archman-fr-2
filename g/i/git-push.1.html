NOM

git-push - Mettre à jour les références distantes ainsi que les objets associés

SYNOPSIS

git push [--all | --branches | --mirror | --tags] [--follow-tags] [--atomic] [-n | --dry-run] [--receive-pack=<git-receive-pack>]
           [--repo=<dépôt>] [-f | --force] [-d | --delete] [--prune] [-q | --quiet] [-v | --verbose]
           [-u | --set-upstream] [-o <chaîne> | --push-option=<chaîne>]
           [--[no-]signed|--signed=(true|false|if-asked)]
           [--force-with-lease[=<nom-ref>[:<attendu>]] [--force-if-includes]]
           [--no-verify] [<dépôt> [<refspec>...]]

DESCRIPTION

Met à jour une ou plusieurs branches, étiquettes ou autres références dans un dépôt distant depuis votre dépôt local, et envoie toutes les données nécessaires qui ne sont pas déjà sur le dépôt distant.

La manière la plus simple de pousser est git push <distant> <branche>. git push origin main poussera la branche locale main vers la branche main sur le dépôt distant nommé origin.

L'argument <dépôt> vaut par défaut le dépôt distant configuré pour la branche actuelle, ou origin s'il n'y a pas de dépôt distant configuré.

Pour décider quelles branches, étiquettes ou autres refs pousser, Git utilise (par ordre de priorité) :

1.L'argument <refspec> (par exemple main dans git push origin main) ou les options --all, --mirror, ou --tags
2.La configuration remote.*.push pour le dépôt vers lequel vous poussez
3.La configuration push.default. La valeur par défaut est push.default=simple, qui poussera vers une branche portant le même nom que la branche actuelle. Voir la section CONFIGURATION ci-dessous pour plus d'informations sur push.default.

git push peut échouer si vous n'avez pas défini de dépôt distant pour la branche actuelle, en fonction de ce à quoi push.default est configuré. Voir la section BRANCHES DISTANTES ci-dessous pour savoir comment définir et utiliser les dépôts distants.

Vous pouvez faire des choses intéressantes dans un dépôt chaque fois que vous y poussez, en y configurant des hooks (crochets). Voir la documentation de git-receive-pack(1).

OPTIONS

<dépôt>

Le dépôt « distant » qui est la destination d'une opération de push. Cet argument peut être une URL (voir la section URL GIT ci-dessous) ou le nom d'un dépôt distant (voir la section DÉPÔTS DISTANTS ci-dessous).

<refspec>...

Spécifie quelle référence de destination doit être mise à jour avec quel objet source.

Le format d'un refspec est [+]<src>[:<dst>], par exemple main, main:other, ou HEAD^:refs/heads/main.

<src> est souvent le nom de la branche locale à pousser, mais il peut s'agir de toute « expression SHA-1 » arbitraire (voir gitrevisions(7)).

<dst> détermine quelle référence mettre à jour du côté distant. Il doit s'agir du nom d'une branche, d'une étiquette ou d'une autre référence, pas d'une expression arbitraire.

Le signe + est facultatif et fait la même chose que --force.

Vous pouvez écrire un refspec en utilisant la forme entièrement développée (par exemple refs/heads/main:refs/heads/main) qui spécifie la source et la destination exactes, ou avec une forme plus courte (par exemple main ou main:other). Voici les règles pour l'expansion des refspecs, ainsi que diverses autres formes spéciales de refspecs :

•<src> sans :<dst> signifie mettre à jour la même référence que <src>, à moins que la configuration remote.<dépôt>.push ne spécifie un <dst> différent. Par exemple, si main est une branche, alors le refspec main s'étend en main:refs/heads/main.
•Si <dst> fait référence sans ambiguïté à une ref sur le dépôt distant <dépôt>, alors développez-la à cette ref. Par exemple, si v1.0 est une étiquette sur le dépôt distant, alors HEAD:v1.0 s'étend en HEAD:refs/tags/v1.0.
•Si <src> résout en une ref commençant par refs/heads/ ou refs/tags/, alors ajoutez ceci au début de <dst>. Par exemple, si main est une branche, alors main:other s'étend en main:refs/heads/other
•Le refspec spécial : (ou +: pour autoriser les mises à jour non-fast-forward) demande à Git de pousser les branches « correspondantes » : pour chaque branche qui existe côté local, le côté distant est mis à jour si une branche du même nom existe déjà du côté distant.
•<src> peut contenir un * pour indiquer une correspondance de motif simple. Cela fonctionne comme un glob qui correspond à n'importe quelle ref correspondant au motif. Il ne doit y avoir qu'un seul * dans <src> et <dst>. Il mappera les refs à la destination en remplaçant le * par le contenu correspondant de la source. Par exemple, refs/heads/*:refs/heads/* poussera toutes les branches.
•Une refspec commençant par ^ est une refspec négative. Elle spécifie les refs à exclure. Une ref sera considérée comme correspondante si elle correspond à au moins une refspec positive et ne correspond à aucune refspec négative. Les refspecs négatives peuvent être des refspecs par motif. Elles ne doivent contenir qu'un <src>. Les noms d'objets hexadécimaux entièrement orthographiés ne sont pas non plus pris en charge. Par exemple, git push origin 'refs/heads/*' '^refs/heads/dev-*' poussera toutes les branches sauf celles commençant par dev-
•Si <src> est vide, il supprime la ref <dst> du dépôt distant. Par exemple, git push origin :dev supprimera la branche dev.
•tag <étiquette> s'étend en refs/tags/<étiquette>:refs/tags/<étiquette>. Il s'agit techniquement d'une syntaxe spéciale pour git push et non d'un refspec, car dans git push origin tag v1.0 les arguments tag et v1.0 sont séparés.
•Si le refspec ne peut pas être développé sans ambiguïté, une erreur sera renvoyée indiquant ce qui a été tenté, et en fonction de la configuration advice.pushUnqualifiedRefname (voir git-config(1)) suggérera le namespace refs/ que vous auriez pu vouloir pousser vers.

Toutes les mises à jour ne sont pas autorisées : voir la section RÈGLES DE PUSH ci-dessous pour les détails.

--all, --branches

Pousse toutes les branches (c'est-à-dire les refs sous refs/heads/) ; ne peut pas être utilisé avec d'autres <refspec>.

--prune

Supprime les branches distantes qui n'ont pas de contrepartie locale. Par exemple, une branche distante tmp sera supprimée si une branche locale du même nom n'existe plus. Cela respecte également les refspecs, par exemple git push --prune distant refs/heads/*:refs/tmp/* s'assurera que la ref distante refs/tmp/foo sera supprimée si refs/heads/foo n'existe pas.

--mirror

Au lieu de nommer chaque ref à pousser, spécifie que toutes les refs sous refs/ (ce qui inclut, mais sans s'y limiter, refs/heads/, refs/remotes/ et refs/tags/) doivent être mises en miroir dans le dépôt distant. Les refs locales nouvellement créées seront poussées vers l'extrémité distante, les refs mises à jour localement seront forcées sur l'extrémité distante, et les refs supprimées seront retirées de l'extrémité distante. C'est la valeur par défaut si l'option de configuration remote.<distant>.mirror est définie.

-n, --dry-run

Fait tout sauf envoyer réellement les mises à jour.

--porcelain

Produit une sortie lisible par machine. La ligne de statut de sortie pour chaque ref sera séparée par des tabulations et envoyée à stdout au lieu de stderr. Les noms symboliques complets des refs seront donnés.

-d, --delete

Toutes les refs listées sont supprimées du dépôt distant. C'est la même chose que de préfixer toutes les refs par un deux-points.

--tags

Toutes les refs sous refs/tags sont poussées, en plus des refspecs explicitement listées sur la ligne de commande.

--follow-tags

Pousse toutes les refs qui seraient poussées sans cette option, et pousse également les étiquettes annotées dans refs/tags qui manquent sur le dépôt distant mais qui pointent vers des commits atteignables depuis les refs poussées. Ceci peut également être spécifié avec la variable de configuration push.followTags. Pour plus d'informations, voir push.followTags dans git-config(1).

git-push(1)

--signed, --no-signed, --signed=(true|false|if-asked)

GPG signe la requête de push pour mettre à jour les références du côté réception, afin qu'elles puissent être vérifiées par les hooks et/ou enregistrées. Si false ou --no-signed, aucune signature ne sera tentée. Si true ou --signed, le push échouera si le serveur ne supporte pas les pushes signés. S'il est défini à if-asked, signe si et seulement si le serveur supporte les pushes signés. Le push échouera également si l'appel réel à gpg --sign échoue. Voir git-receive-pack(1) pour les détails du côté réception.

--atomic, --no-atomic

Utilise une transaction atomique côté distant si disponible. Soit toutes les références sont mises à jour, soit en cas d'erreur, aucune référence n'est mise à jour. Si le serveur ne supporte pas les pushes atomiques, le push échouera.

-o <option>, --push-option=<option>

Transmet la chaîne de caractères donnée au serveur, qui la passe aux hooks pre-receive ainsi qu'à post-receive. La chaîne de caractères donnée ne doit pas contenir de caractère NUL ou LF. Lorsque plusieurs --push-option=<option> sont données, elles sont toutes envoyées à l'autre partie dans l'ordre où elles apparaissent dans la ligne de commande. Lorsqu'aucune --push-option=<option> n'est donnée depuis la ligne de commande, les valeurs de la variable de configuration push.pushOption sont utilisées à la place.

--receive-pack=<git-receive-pack>, --exec=<git-receive-pack>

Chemin vers le programme git-receive-pack côté distant. Parfois utile lorsqu'on fait un push vers un dépôt distant via ssh, et que le programme ne se trouve pas dans un répertoire du $PATH par défaut.

--force-with-lease, --no-force-with-lease, --force-with-lease=<refname>, --force-with-lease=<refname>:<expect>

Habituellement, « git push » refuse de mettre à jour une référence distante qui n'est pas un ancêtre de la référence locale utilisée pour la remplacer.

Cette option remplace cette restriction si la valeur actuelle de la référence distante est la valeur attendue. « git push » échoue sinon.

Imaginez que vous devez réécrire ce que vous avez déjà publié. Vous devrez outrepasser la règle « doit être un fast-forward » afin de remplacer l'historique que vous aviez initialement publié par l'historique réécrit. Si quelqu'un d'autre s'est basé sur votre historique d'origine pendant que vous réécriviez, le bout de la branche à distance peut avoir avancé avec son commit, et un --force aveugle fera perdre son travail.

Cette option vous permet de dire que vous vous attendez à ce que l'historique que vous mettez à jour soit celui que vous avez réécrit et que vous souhaitez remplacer. Si la référence distante pointe toujours vers le commit que vous avez spécifié, vous pouvez être sûr que personne d'autre n'a rien fait à cette référence. C'est comme prendre un « bail » sur la référence sans la verrouiller explicitement, et la référence distante n'est mise à jour que si le « bail » est toujours valide.

--force-with-lease seul, sans spécifier les détails, protégera toutes les références distantes qui vont être mises à jour en exigeant que leur valeur actuelle soit identique à celle de la branche de suivi distante que nous avons pour elles.

--force-with-lease=<refname>, sans spécifier la valeur attendue, protégera la référence nommée (seule), si elle doit être mise à jour, en exigeant que sa valeur actuelle soit identique à celle de la branche de suivi distante que nous avons pour elle.

--force-with-lease=<refname>:<expect> protégera la référence nommée (seule), si elle doit être mise à jour, en exigeant que sa valeur actuelle soit identique à la valeur spécifiée <expect> (qui peut être différente de la branche de suivi distante que nous avons pour la refname, ou nous n'avons même pas besoin d'avoir une telle branche de suivi distante lorsque cette forme est utilisée). Si <expect> est une chaîne vide, alors la référence nommée ne doit pas exister.

Notez que toutes les formes autres que --force-with-lease=<refname>:<expect> qui spécifient explicitement la valeur actuelle attendue de la référence sont encore expérimentales et leurs sémantiques peuvent changer à mesure que nous acquérons de l'expérience avec cette fonctionnalité.

« --no-force-with-lease » annulera toutes les --force-with-lease précédentes sur la ligne de commande.

Remarque générale sur la sécurité : fournir cette option sans valeur attendue, c'est-à-dire sous la forme --force-with-lease ou --force-with-lease=<refname>, interagit très mal avec tout ce qui exécute implicitement git fetch sur la branche distante à pusher en arrière-plan, par exemple git fetch origin dans votre dépôt via cron.

La protection qu'elle offre par rapport à --force est de garantir que les changements ultérieurs sur lesquels votre travail n'était pas basé ne sont pas écrasés, mais cela est trivialement contourné si un processus d'arrière-plan met à jour les références. Nous n'avons rien d'autre que les informations de suivi distant comme heuristique pour les références que vous êtes censé avoir vues et que vous êtes prêt à écraser.

Si votre éditeur ou un autre système exécute git fetch en arrière-plan pour vous, une façon d'atténuer cela est simplement de configurer une autre branche distante :

git remote add origin-push $(git config remote.origin.url)
git fetch origin-push

Maintenant, lorsque le processus d'arrière-plan exécute git fetch origin, les références sur origin-push ne seront pas mises à jour, et donc des commandes comme :

git push --force-with-lease origin-push

Échoueront à moins que vous n'exécutiez manuellement git fetch origin-push. Cette méthode est bien sûr entièrement contournée par quelque chose qui exécute git fetch --all, dans ce cas, vous devrez soit le désactiver, soit faire quelque chose de plus fastidieux comme :

git fetch              # mettre à jour 'master' depuis la branche distante
git tag base master    # marquer notre point de base
git rebase -i master   # réécrire certains commits
git push --force-with-lease=master:base master:master

C'est-à-dire créer une étiquette base pour les versions du code source distant que vous avez vues et que vous êtes prêt à écraser, puis réécrire l'historique, et enfin forcer le push des changements vers master si la version distante est toujours à base, indépendamment de ce que votre remotes/origin/master local a été mis à jour vers en arrière-plan.

Alternativement, spécifier --force-if-includes comme option auxiliaire avec --force-with-lease[=<refname>] (c'est-à-dire sans indiquer à quel commit exact la référence distante doit pointer, ou quelles références distantes sont protégées) au moment du « push » vérifiera si les mises à jour des références de suivi distant qui ont pu être mises à jour implicitement en arrière-plan sont intégrées localement avant d'autoriser une mise à jour forcée.

-f, --force

Habituellement, git push refuse de mettre à jour une branche qui n'est pas un ancêtre du commit qui est poussé.

Ce drapeau désactive cette vérification, ainsi que les autres vérifications de sécurité dans PUSH RULES ci-dessous, et les vérifications de --force-with-lease. Il peut entraîner la perte de commits dans le dépôt distant ; utilisez-le avec précaution.

Notez que --force s'applique à toutes les références qui sont poussées, donc l'utiliser avec push.default défini à matching ou avec plusieurs destinations de push configurées avec remote.*.push peut écraser des références autres que la branche courante (y compris des références locales qui sont strictement en retard par rapport à leur contrepartie distante). Pour forcer un push sur une seule branche, utilisez un + devant la refspec à pusher (par exemple, git push origin +master pour forcer un push sur la branche master). Voir la section <refspec>... ci-dessus pour plus de détails.

--force-if-includes, --no-force-if-includes

Force une mise à jour uniquement si le bout de la référence de suivi distant a été intégré localement.

Cette option active une vérification qui s'assure que le bout de la référence de suivi distant est accessible depuis l'une des entrées du « reflog » de la branche locale basée sur elle pour une réécriture. La vérification garantit que toutes les mises à jour de la branche distante ont été incorporées localement en rejetant la mise à jour forcée si ce n'est pas le cas.

Si l'option est passée sans spécifier --force-with-lease, ou spécifiée avec --force-with-lease=<refname>:<expect>, c'est une « no-op » (pas d'opération).

Spécifier --no-force-if-includes désactive ce comportement.

--repo=<repository>

Cette option est équivalente à l'argument <repository>. Si les deux sont spécifiés, l'argument de la ligne de commande a la priorité.

-u, --set-upstream

Pour chaque branche qui est à jour ou qui a été poussée avec succès, ajoute une référence de suivi (upstream), utilisée par git-pull(1) sans argument et d'autres commandes. Pour plus d'informations, voir branch.<name>.merge dans git-config(1).

--thin, --no-thin

Ces options sont passées à git-send-pack(1). Un transfert fin réduit considérablement la quantité de données envoyées lorsque l'expéditeur et le destinataire partagent de nombreux objets en commun. La valeur par défaut est --thin.

-q, --quiet

Supprime toute sortie, y compris la liste des références mises à jour, sauf en cas d'erreur. La progression n'est pas signalée sur le flux d'erreur standard.

-v, --verbose

Exécute en mode verbeux.

--progress

Le statut de progression est signalé sur le flux d'erreur standard par défaut lorsqu'il est connecté à un terminal, sauf si -q est spécifié. Ce drapeau force l'affichage de la progression même si le flux d'erreur standard n'est pas dirigé vers un terminal.

--no-recurse-submodules, --recurse-submodules=check|on-demand|only|no

Peut être utilisé pour s'assurer que tous les commits de sous-modules utilisés par les révisions à pusher sont disponibles sur une branche de suivi distante. Si check est utilisé, Git vérifiera que tous les commits de sous-modules qui ont changé dans les révisions à pusher sont disponibles sur au moins un distant du sous-module. Si des commits sont manquants, le push sera annulé et le programme se terminera avec un statut non nul. Si on-demand est utilisé, tous les sous-modules qui ont changé dans les révisions à pusher seront poussés. Si on-demand n'a pas pu pusher toutes les révisions nécessaires, il sera également annulé et le programme se terminera avec un statut non nul. Si only est utilisé, tous les sous-modules seront poussés tandis que le super-projet restera non poussé. Une valeur de no ou l'utilisation de --no-recurse-submodules peut être utilisée pour remplacer la variable de configuration push.recurseSubmodules lorsqu'aucune récursion de sous-module n'est requise.

Lors de l'utilisation de on-demand ou only, si un sous-module a une configuration "push.recurseSubmodules={on-demand,only}" ou "submodule.recurse", des recursions supplémentaires

on se produira. Dans ce cas, « only » est traité comme « on-demand

».

--no-verify
Active ou désactive le hook pre-push (voir githooks(5)). La valeur par défaut est --verify, donnant au hook la possibilité d'empêcher le push. Avec --no-verify, le hook est complètement
contourné.

SÉCURIT

É

Les protocoles de fetch et de push ne sont pas conçus pour empêcher l'une des parties de voler des données de l'autre dépôt qui n'étaient pas destinées à être partagées. Si vous avez des données privées dont vous devez protéger un pair malveillant, votre meilleure option est de les stocker dans un autre dépôt. Cela s'applique aux clients comme aux serveurs. En particulier, les espaces de noms sur un serveur ne sont pas efficaces pour le contrôle d'accès en lecture ; vous ne devriez accorder l'accès en lecture à un espace de noms qu'à des clients auxquels vous feriez confiance pour l'accès en lecture à l'ensemble du

dépôt.

Les vecteurs d'attaque connus sont les suivants

:
1.La victime envoie des lignes "have" annonçant les IDs des objets qu'elle possède et qui ne sont pas explicitement destinés à être partagés mais qui peuvent être utilisés pour optimiser le transfert si le pair les possède également. L'attaquant choisit un ID d'objet X à voler et envoie une référence vers X, mais n'est pas tenu d'envoyer le contenu de X car la victime le possède déjà. La victime croit alors que l'attaquant possède X, et elle envoie le contenu de X à l'attaquant plus tard. (Cette attaque est la plus simple à réaliser pour un client sur un serveur, en créant une référence vers X dans l'espace de noms auquel le client a accès puis en la récupérant. La manière la plus probable pour un serveur de la réaliser sur un client est de "fusionner" X dans une branche publique et d'espérer que l'utilisateur effectue un travail supplémentaire sur cette branche et la pousse de retour vers le serveur sans remarquer la fusion.
)
2.Comme dans #1, l'attaquant choisit un ID d'objet X à voler. La victime envoie un objet Y que l'attaquan
t possède déjà, et l'attaquant prétend faussement posséder X et pas Y, de sorte que la victime envoie
Y comme un delta par rapport à X. Le delta révèle les régions de X qui sont similaires à Y à l'attaquant.
