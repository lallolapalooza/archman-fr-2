le contenu ou les déta

DESCRIPTIO

N

Affiche le contenu ou d'autres propriétés telles que la taille, le type ou les informations de delta d'un ou plusieurs

objets.

Cette commande peut fonctionner dans deux modes, selon qu'une option de la famille --batch est spécifiée ou

non.

En mode non par lot, la commande fournit des informations sur un objet nommé sur la ligne de

commande.

En mode par lot, les a

rguments sont lus dep
uis l'entrée standard.

OPTION

S

<objet

>
Le nom de l'objet à afficher. Pour une liste plus complète des façons d'écrire les noms d'objets, voir la section « SPECIFYING REVISIONS » dans gitrevision
s(7).

-

t
Au lieu du contenu, affiche le type d'objet identifié par <obje
t>.

-

s
Au lieu du contenu, affiche la taille de l'objet identifié par <objet>. Si utilisé avec l'option --use-mailmap, affichera la taille de l'objet mis à jour après le remplacement des identités à l'aide du mécanisme
mailmap.

-

e
Se termine avec un code de sortie nul si <objet> existe et est un objet valide. Si <objet> est dans un format invalide, se termine avec un code de sortie non nul et émet une erreur sur
stderr.

-

p
Affiche le contenu de <objet> de manière formatée en fonction de son
type.

<type

>
En général, cela correspond au type réel de <objet>, mais il est également permis de demander un type qui peut être trivialment déréférencé à partir du <objet> donné. Un exemple est de demander un « tree » avec <objet> étant un objet commit qui le contient, ou de demander un « blob » avec <objet> étant un objet tag qui pointe vers
lui.

--mailmap, --no-mailmap, --use-mailmap, --no-use-mailma

p
Utilise le fichier mailmap pour faire correspondre les noms et adresses e-mail de l'auteur, du committer et du tagger aux noms et adresses e-mail canoniques. Voir git-shortlo
g(1).

--textcon

v
Affiche le contenu tel que transformé par un filtre textconv. Dans ce cas, <objet> doit être de la forme <tree-ish>:<path>, ou :<path> afin d'appliquer le filtre au contenu enregistré dans l'index à <path
>.

--filter

s
Affiche le contenu tel que converti par les filtres configurés dans l'arbre de travail courant pour le <path> donné (c'est-à-dire les filtres smudge, la conversion de fin de ligne, etc.). Dans ce cas, <objet> doit être de la forme <tree-ish>:<path>, ou :<path
>.

--filter=<filter-spec>,

--no-filter
Omet des objets de la liste des objets imprimés. Cela ne peut être utilisé qu'en combinaison avec l'un des modes par lot. Les objets exclus qui ont été explicitement demandés via l'un des modes par lot qui lisent les objets via l'entrée standard (--batch, --batch-check) seront signalés comme « filtered ». Les objets exclus en mode --batch-all-objects ne seront pas du tout imprimés. Le <filter-spec> peut être l'un des suivants :

La forme --filter=blob:none omet tous les

blobs.

La forme --filter=blob:limit=<n>[kmg] omet les blobs de taille d'au moins n octets ou unités. n peut être zéro. Les suffixes k, m et g peuvent être utilisés pour nommer les unités en KiB, MiB ou GiB. Par exemple, blob:limit=1k est identique à blob:limit=

1024.

La forme --filter=object:type=(tag|commit|tree|blob) omet

tous les objets qui ne
sont pas du type demandé.

--path=<path

>
Pour utilisation avec --textconv ou --filters, afin de permettre de spécifier un nom d'objet et un chemin séparément, par exemple lorsqu'il est difficile de déterminer la révision d'où provient le
blob.

--batch, --batch=<format

>
Affiche les informations et le contenu de l'objet pour chaque objet fourni sur stdin. Ne peut pas être combiné avec d'autres options ou arguments sauf --textconv, --filters ou --use-mailmap.
•Lorsqu'il est utilisé avec --textconv ou --filters, les lignes d'entrée doivent spécifier le chemin, séparé par des espaces. Voir la section SORTIE PAR LOT ci-dessous pour plus de
détails.
•Lorsqu'il est utilisé avec --use-mailmap, pour les objets commit et tag, la partie contenu de la sortie montre les identités remplacées à l'aide du mécanisme mailmap, tand
is que la partie informations de la sortie montre la taille de l'objet c
omme si elle avait effectivement enregistré les identités de remplacement.

--batch-check, --batch-check=<format

>
Affiche les informations de l'objet pour chaque objet fourni sur stdin. Ne peut pas être combiné avec d'autres options ou arguments sauf --textconv, --filters ou --use-mailmap.
•Lorsqu'il est utilisé avec --textconv ou --filters, les lignes d'entrée doivent spécifier le chemin, séparé par des espaces. Voir la section SORTIE PAR LOT ci-dessous pour plus de
détails.
•Lorsqu'il est utilisé avec --use-mailmap, pour les objets commit et tag, les informations de l'objet imprimées montrent la tail
le de l'objet comme si les identités enregistrées
avaient été remplacées par le mécanisme mailmap.

--batch-command, --batch-command=<format

>
Entre dans un mode de commande qui lit les commandes et arguments depuis stdin. Ne peut être combiné qu'avec --buffer, --textconv, --use-mailmap ou --filters.
•Lorsqu'il est utilisé avec --textconv ou --filters, les lignes d'entrée doivent spécifier le chemin, séparé par des espaces. Voir la section SORTIE PAR LOT ci-dessous pour plus de
détails.
•Lorsqu'il est utilisé avec --use-mailmap, pour les objets commit et tag, la commande contents montre les identités remplacées à l'aide du mécanisme mailmap, tandis que la commande info montre la taille de l'objet comme si elle avait effectivement enregistré les identités de
remplacement.

--batch-command reconnaît les commandes suivantes

:

contents

<objet>
Affiche le contenu de l'objet pour la référence d'objet <objet>. Cela correspond à la sortie de --batch
.

info

<objet>
Affiche les informations de l'objet pour la référence d'objet <objet>. Cela correspond à la sortie de --batch-check
.

flus

h
Utilisé avec --buffer pour exécuter toutes les commandes précédentes émises depuis le début ou depuis la dernière commande flush émise. Lorsque --buffer est utilisé, aucune sortie ne sera produite jusqu'à ce qu'un flush soit émis. Lorsque --buffer n'est pas utilisé, les commandes sont vidées à chaque fois sans émettre flu
s
h.

--batch-all-object

s
Au lieu de lire une liste d'objets sur stdin, effectue l'opération par lot demandée sur tous les objets du dépôt et tous les magasins d'objets alternatifs (pas seulement les objets accessibles). Requiert que --batch ou --batch-check soit spécifié. Par défaut, les objets sont visités dans l'ordre trié par leurs hachages ; voir aussi --unordered ci-dessous. Les objets sont présentés tels quels, sans respecter le mécanisme « replace » de git-replac
e(1).

--buffe

r
Normalement, la sortie par lot est vidée après chaque objet est affiché, de sorte qu'un processus peut lire et écrire de manière interactive avec cat-file. Avec cette option, la sortie utilise le tampon stdio normal ; c'est beaucoup plus efficace lors de l'invocation de --batch-check ou --batch-command sur un grand nombre
d'objets.

--unordere

d
Lorsque --batch-all-objects est utilisé, visite les objets dans un ordre qui peut être plus efficace pour accéder au contenu des objets que l'ordre des hachages. Les détails exacts de l'ordre ne sont pas spécifiés, mais si vous n'exigez pas un ordre spécifique, cela devrait généralement donner une sortie plus rapide, surtout avec --batch. Notez que cat-file affichera quand même chaque objet une seule fois, même s'il est stocké plusieurs fois dans le
dépôt.

--follow-symlink

s
Avec --batch ou --batch-check, suivre les liens symboliques à l'intérieur du dépôt lors de la demande d'objets avec des expressions SHA-1 étendues de la forme tree-ish:path-in-tree. Au lieu de fournir des informations sur le lien lui-même, fournir des informations sur l'objet lié. Si un lien symbolique pointe en dehors du tree-ish (par exemple, un lien vers /foo ou un lien de niveau racine vers ../foo), la partie du lien qui se trouve en dehors de l'arbre sera imprimée.

Cette option ne fonctionne pas (actuellement) correctement lorsqu'un objet dans l'index est spécifié (par exemple, :link au lieu de HEAD:link) plutôt que celui de

l'arbre.

Cette option ne peut pas (actuellement) être utilisée sauf si --batch ou --batch-check est

utilisé.

Par exemple, considérons un dépôt git contenant

: 
f: un fichier contenant "hello\n"
link: un lien symbolique ve
rs f dir/link: un lien symbolique vers ../f plink: un lien sy
mbolique vers ../f alink: un lien symbolique vers /etc/passwd

Pour un fichier normal f, echo HEAD:f | git cat-file --batch impri

merait 
ce013625030ba8db
a906f756967f9e9
ca394464a blob 6

Et echo HEAD:link | git cat-file --batch --follow-symlinks imprimerait la même chose, comme le ferait HEAD:dir/link, car ils pointent tous les deux vers HEAD:

f.

Sans --follow-symlinks, ceux-ci imprimeraient des données sur le lien symbolique lui-même. Dans le cas de HEAD:link, vous

verriez 
4d1ae35ba2c8ec71
2fa2a379db44ad6
39ca277bd blob 1

Tous les deux plink et alink pointent en dehors de l'arbre, ils imprimeraient donc respectivement

: 
symli
nk 4
../f 
symlin
k 11
/etc/
passwd

Z
N'a de sens qu'avec --batch, --batch-check ou --batch-command ; l'entrée et la sortie sont délimitées par NUL au lieu d'être délimitées par des sauts de
ligne.

-

z
N'a de sens qu'avec --batch, --batch-check ou --batch-command ; l'entrée est délimitée par NUL au lieu d'être délimitée par des sauts de ligne. Cette option est dépréciée au profit de -Z car la sortie pourr
ait sinon ê
tre ambiguë.

Si -e est spécifié, aucune sortie, sauf si le <object> est

SORTIE PAR

LOT

Si --batch ou --batch-check est donné, cat-file lira les objets depuis stdin, un par ligne, et imprimera des informations à leur sujet dans le même ordre que celui dans lequel ils ont été lus. Par défaut, toute la ligne est considérée comme un objet, comme si elle était fournie à git-rev-par

se(1).

Lorsque --batch-command est donné, cat-file lira des commandes depuis stdin, une par ligne, et imprimera des informations basées sur la commande donnée. Avec --batch-command, la commande info suivie d'un objet imprimera des informations sur l'objet de la même manière que --batch-check le ferait, et la commande contents suivie d'un objet imprime le contenu de la même manière que --batch le

ferait.

Vous pouvez spécifier les informations affichées pour chaque objet en utilisant un <format> personnalisé. Le <format> est copié littéralement vers stdout pour chaque objet, avec les espaces réservés de la forme %(atom) développés, suivis d'un saut de ligne. Les atomes disponibles sont

:

objectnam

e
La représentation hexadécimale complète du nom de
l'objet.

objecttyp

e
Le type de l'objet (le même que ce que cat-file -t rapporte)
.

objectmod

e
Si l'objet spécifié a des informations de mode (comme une entrée d'arbre ou d'index), le mode exprimé comme un entier octal. Sinon, chaîne
vide.

objectsiz

e
La taille, en octets, de l'objet (la même que ce que cat-file -s rapporte)
.

objectsize:

disk
La taille, en octets, que l'objet occupe sur le disque. Voir la note sur les tailles sur disque dans la section AVERTISSEMENTS
ci-dessous.

deltabas

e
Si l'objet est stocké comme un delta sur disque, ceci se développe en la représentation hexadécimale complète du nom de l'objet de base du delta. Sinon, se développe en l'OID nul (tous des zéros). Voir AVERTISSEMENTS ci
-dessous.

res

t
Si cet atome est utilisé dans la chaîne de sortie, les lignes d'entrée sont divisées à la première limite d'espace blanc. Tous les caractères avant cet espace blanc sont considérés comme étant le nom de l'objet ; les caractères après cette première série d'espaces blancs (c'est-à-dire le « reste » de la ligne) sont produits à la place de l'atome %(rest
).

Si aucun format n'est spécifié, le format par défaut est %(objectname) %(objecttype) %(objectsi

ze).

Si --batch est spécifié, ou si --batch-command est utilisé avec la commande contents, les informations sur l'objet sont suivies du contenu de l'objet (consistant en %(objectsize) octets), suivi d'un saut de

ligne.

Par exemple, --batch sans un format personnalisé produirait

: 
<oid> SP <type
> SP <size> LF
<contents> LF

Alors que --batch-check='%(objectname) %(objecttype)' produirait

: 
<oid>
SP <ty
pe> LF

:

> SP mis

Si un nom est spécifié sur stdin qui est filtré via --filter=, alors cat-file ignorera tout format personnalisé et imprimera

: 
<object>

Si un nom est spécifié qui pourrait faire référence à plus d'un objet (un sha court ambigu), alors cat-file ignorera tout format personnalisé et imprimera

: 
<object>

guous LF

Si un nom est spécifié qui fait référence à une entrée de sous-module dans un arbre et que l'objet cible n'existe pas dans le dépôt, alors cat-file ignorera tout format personnalisé et imprimera (avec l'identifiant de l'objet du sous-module)

: 
<oid> S
P submo
dule LF

Si --follow-symlinks est utilisé, et qu'un lien symbolique dans le dépôt pointe en dehors du dépôt, alors cat-file ignorera tout format personnalisé et imprimera

: 
symlink SP
<size> LF <
symlink> LF

Le lien symbolique sera soit absolu (commençant par un /), soit relatif à la racine de l'arbre. Par exemple, si dir/link pointe vers ../../foo, alors <symlink> sera ../foo. <size> est la taille du lien symbolique en

octets.

Si --follow-symlinks est utilisé, les messages d'erreur suivants seront affichés

AVERTISSEMEN

TS

Notez que les tailles des objets sur disque sont rapportées avec précision, mais il convient d'être prudent dans les conclusions tirées sur les refs ou les objets responsables de l'utilisation du disque. La taille d'un objet non-delta compressé peut être beaucoup plus grande que la taille des objets qui sont delta contre lui, mais le choix de l'objet qui est la base et de celui qui est le delta est arbitraire et est sujet à changer lors d'un

repack.

Notez également que plusieurs copies d'un objet peuvent être présen

tes dans la base de données d'objets ; dans ce cas, il n'est pas dé
fini quelle taille de copie ou quelle base de delta sera rapportée.
