-M[<n>], --find-renames[=<n>]

Détecte les renommages. Si <n> est spécifié, il s'agit d'un seuil sur l'indice de similarité (c'est-à-dire la quantité d'ajouts/suppressions par rapport à la taille du fichier). Par exemple, -M90 % signifie que Git doit considérer une paire de suppression/ajout comme un renommage si plus de 90 % du fichier n'a pas changé. Sans signe %, le nombre doit être lu comme une fraction, avec un point décimal avant. Par exemple, -M5 devient 0,5, et est donc identique à -M50 %. De même, -M05 est identique à -M5 %. Pour limiter la détection aux renommages exacts, utilisez -M100 %. L'indice de similarité par défaut est 50 %.

-C[<n>], --find-copies[=<n>]

Détecte les copies ainsi que les renommages. Voir également --find-copies-harder. Si <n> est spécifié, il a la même signification que pour -M<n>.

--find-copies-harder

Pour des raisons de performance, par défaut, l'option -C trouve les copies uniquement si le fichier original de la copie a été modifié dans le même changeset. Ce drapeau fait que la commande inspecte les fichiers non modifiés comme candidats pour la source de la copie. C'est une opération très coûteuse pour les grands projets, utilisez-la donc avec prudence. Donner plus d'une option -C a le même effet.

-D, --irreversible-delete

Omet le préimage pour les suppressions, c'est-à-dire qu'il affiche uniquement l'en-tête mais pas la différence entre la préimage et /dev/null. Le patch résultant n'est pas destiné à être appliqué avec patch ou git apply ; il s'adresse uniquement aux personnes qui souhaitent se concentrer sur la révision du texte après le changement. De plus, la sortie manque évidemment d'informations suffisantes pour appliquer un tel patch en sens inverse, même manuellement, d'où le nom de l'option.

Lorsqu'elle est utilisée avec -B, omet également la préimage dans la partie suppression d'une paire suppression/création.

-l<num>

Les options -M et -C impliquent certaines étapes préliminaires qui peuvent détecter des sous-ensembles de renommages/copies à faible coût, suivies d'une partie exhaustive de comparaison de toutes les destinations restantes non appariées avec toutes les sources pertinentes. (Pour les renommages, seules les sources restantes non appariées sont pertinentes ; pour les copies, toutes les sources originales sont pertinentes.) Pour N sources et destinations, cette vérification exhaustive est en O(N^2). Cette option empêche la partie exhaustive de la détection de renommage/copie de s'exécuter si le nombre de fichiers source/destination impliqués dépasse le nombre spécifié. Par défaut, il utilise diff.renameLimit. Notez qu'une valeur de 0 est traitée comme illimitée.

--diff-filter=[(A|C|D|M|R|T|U|X|B)...[*]]

Sélectionne uniquement les fichiers qui sont Ajoutés (A), Copiés (C), Supprimés (D), Modifiés (M), Renommés (R), dont le type (c'est-à-dire fichier ordinaire, lien symbolique, sous-module, ...) a été modifié (T), sont Non fusionnés (U), sont Inconnus (X), ou dont le pairage a été rompu (B). Toute combinaison de caractères de filtrage (y compris aucun) peut être utilisée. Lorsque * (Tout ou rien) est ajouté à la combinaison, tous les chemins sont sélectionnés s'il y a un fichier qui correspond aux autres critères de comparaison ; s'il n'y a aucun fichier qui correspond aux autres critères, rien n'est sélectionné.

De plus, ces lettres majuscules peuvent être mises en minuscules pour exclure. Par exemple, --diff-filter=ad exclut les chemins ajoutés et supprimés.

Notez que tous les diffs ne peuvent pas présenter tous les types. Par exemple, les entrées copiées et renommées ne peuvent pas apparaître si la détection pour ces types est désactivée.

-S<chaîne>

Recherche les différences qui modifient le nombre d'occurrences de la <chaîne> spécifiée (c'est-à-dire ajout/suppression) dans un fichier. Destiné à l'usage du scripteur.

C'est utile lorsque vous recherchez un bloc de code exact (comme une structure), et que vous voulez connaître l'historique de ce bloc depuis sa création : utilisez la fonctionnalité de manière itérative pour renvoyer le bloc intéressant de la préimage à -S, et continuez jusqu'à obtenir la toute première version du bloc.

Les fichiers binaires sont également recherchés.

-G<regex>

Recherche les différences dont le texte du patch contient des lignes ajoutées/supprimées qui correspondent à <regex>.

Pour illustrer la différence entre -S<regex> --pickaxe-regex et -G<regex>, considérez un commit avec le diff suivant dans le même fichier :

+    return frotz(nitfol, two->ptr, 1, 0);
...
-    hit = frotz(nitfol, mf2.ptr, 1, 0);

Alors que git log -G"frotz\(nitfol" affichera ce commit, git log -S"frotz\(nitfol" --pickaxe-regex ne le fera pas (car le nombre d'occurrences de cette chaîne n'a pas changé).

À moins que --text ne soit fourni, les patchs de fichiers binaires sans filtre textconv seront ignorés.

Voir l'entrée pickaxe dans gitdiffcore(7) pour plus d'informations.

--find-object=<object-id>

Recherche les différences qui modifient le nombre d'occurrences de l'objet spécifié. Similaire à -S, seul l'argument diffère en ce qu'il ne recherche pas une chaîne spécifique mais un identifiant d'objet spécifique.

L'objet peut être un blob ou un commit de sous-module. Il implique l'option -t dans git-log pour trouver également les arbres.

--pickaxe-all

Lorsque -S ou -G trouve un changement, affiche tous les changements dans ce changeset, pas seulement les fichiers qui contiennent le changement de <chaîne>.

--pickaxe-regex

Traite la <chaîne> donnée à -S comme une expression régulière étendue POSIX à faire correspondre.

-O<fichier_ordre>

Contrôle l'ordre dans lequel les fichiers apparaissent dans la sortie. Ceci remplace la variable de configuration diff.orderFile (voir git-config(1)). Pour annuler diff.orderFile, utilisez -O/dev/null.

L'ordre de sortie est déterminé par l'ordre des motifs glob dans <fichier_ordre>. Tous les fichiers dont les noms correspondent au premier motif sont affichés en premier, tous les fichiers dont les noms correspondent au second motif (mais pas au premier) sont affichés ensuite, et ainsi de suite. Tous les fichiers dont les noms ne correspondent à aucun motif sont affichés en dernier, comme s'il y avait un motif implicite de correspondance universelle à la fin du fichier. Si plusieurs noms de fichiers ont le même rang (ils correspondent au même motif mais à aucun motif précédent), leur ordre de sortie relatif est l'ordre normal.

<fichier_ordre> est analysé comme suit :

•Les lignes vides sont ignorées, elles peuvent donc être utilisées comme séparateurs pour la lisibilité.
•Les lignes commençant par un dièse (« # ») sont ignorées, elles peuvent donc être utilisées pour des commentaires. Ajoutez une barre oblique inverse ("\") au début du motif s'il commence par un dièse.
•Chaque autre ligne contient un motif unique.

Les motifs ont la même syntaxe et sémantique que les motifs utilisés pour fnmatch(3) sans le drapeau FNM_PATHNAME, à l'exception qu'un nom de chemin correspond également à un motif si la suppression d'un nombre quelconque de composantes finales du nom de chemin correspond au motif. Par exemple, le motif "foo*bar" correspond à "fooasdfbar" et "foo/bar/baz/asdf" mais pas à "foobarx".

7134973

FORMAT DE SORTIE BRUTE


Le format de sortie brut de git-diff-index,
    git-diff-tree, git-diff-files et git diff
    --raw sont très similaires.


Ces commandes comparent toutes deux ensembles de choses ; ce qui est
    comparé diffère :


git-diff-index <tree-ish>


compare le <tree-ish> et les fichiers sur le
  système de fichiers.


git-diff-index --cached <tree-ish>


compare le <tree-ish> et l'index.


git-diff-tree [-r] <tree-ish-1>
    <tree-ish-2> [<pattern>...]


compare les arbres nommés par les deux arguments.


git-diff-files [<pattern>...]


compare l'index et les fichiers sur le système de fichiers.


La commande git-diff-tree commence sa sortie en imprimant le
    hachage de ce qui est comparé. Après cela, toutes les commandes impriment une
    ligne de sortie par fichier modifié.


Une ligne de sortie est formatée de cette manière :




in-place edit  :100644 100644 bcd1234 0123456 M file0
copy-edit      :100644 100644 abcd123 1234567 C68 file1 file2
rename-edit    :100644 100644 abcd123 1234567 R86 file1 file3
create         :000000 100644 0000000 1234567 A file4
delete         :100644 000000 1234567 0000000 D file5
unmerged       :000000 000000 0000000 0000000 U file6




C'est-à-dire, de la gauche vers la droite :


 1.un deux-points.


 2.mode pour « src » ; 000000 si création ou
  non fusionné.


 3.une espace.


 4.mode pour « dst » ; 000000 si suppression ou
  non fusionné.


 5.une espace.


 6.sha1 pour « src » ; 0{40} si création ou
  non fusionné.


 7.une espace.


 8.sha1 pour « dst » ; 0{40} si suppression, non fusionné
  ou « arbre de travail désynchronisé avec l'index ».


 9.une espace.


10.statut, suivi d'un nombre de « score »
  optionnel.


11.un tabulateur ou un NUL lorsque l'option -z est utilisée.


12.chemin pour « src »


13.un tabulateur ou un NUL lorsque l'option -z est utilisée ; n'existe
  que pour C ou R.


14.chemin pour « dst » ; n'existe que pour C ou
  R.


15.un LF ou un NUL lorsque l'option -z est utilisée, pour
  terminer l'enregistrement.


Les lettres de statut possibles sont :


•A: ajout d'un fichier


•C: copie d'un fichier vers un nouveau


•D: suppression d'un fichier


•M: modification du contenu ou du mode d'un
  fichier


•R: renommage d'un fichier


•T: changement du type de fichier (fichier
  régulier, lien symbolique ou sous-module)


•U: le fichier est non fusionné (vous devez
  terminer la fusion avant de pouvoir le committer)


•X: type de changement « inconnu » (très
  probablement un bogue, veuillez le signaler)


Les lettres de statut C et R sont toujours suivies d'un score
    (indiquant le pourcentage de similarité entre la source et la cible du
    déplacement ou de la copie). La lettre de statut M peut être suivie d'un score
    (indiquant le pourcentage de dissimilarité) pour les réécritures de fichiers.


Le sha1 pour « dst » est affiché comme tous des 0 si un fichier
    sur le système de fichiers est désynchronisé avec l'index.


Exemple :




:100644 100644 5be4a4a 0000000 M file.c




Sans l'option -z , les noms de chemins avec des caractères « inhabituels »
    sont mis entre guillemets comme expliqué pour la variable de configuration
    core.quotePath (voir git-config(1)). En utilisant -z , le nom de fichier est
    imprimé tel quel et la ligne est terminée par un octet NUL.






FORMAT DE DIFF POUR LES FUSIONS


git-diff-tree, git-diff-files et git-diff
    --raw peuvent prendre les options -c ou --cc pour générer une sortie de diff
    aussi pour les commits de fusion. La sortie diffère du format décrit ci-dessus de
    la manière suivante :


 1.il y a un deux-points pour chaque parent


 2.il y a plus de modes « src » et de
  sha1 « src »


 3.le statut est la concaténation des caractères de statut pour chaque
  parent


 4.pas de nombre de « score » optionnel


 5.nom(s) de chemin du fichier séparés par des tabulateurs


Pour -c et --cc, seul le chemin de destination ou final est
    affiché même si le fichier a été renommé sur un côté de l'historique. Avec
    --combined-all-paths, le nom du chemin dans chaque parent est affiché,
    suivi du nom du chemin dans le commit de fusion.


Exemples pour -c et --cc sans
    --combined-all-paths:




::100644 100644 100644 fabadb8 cc95eb0 4866510 MM       desc.c
::100755 100755 100755 52b7a2d 6d1ac04 d2ac7d7 RM       bar.sh
::100644 100644 100644 e07d6c5 9042e82 ee91881 RR       phooey.c




Exemples lorsque --combined-all-paths est ajouté à
    -c ou --cc:




::100644 100644 100644 fabadb8 cc95eb0 4866510 MM       desc.c  desc.c  desc.c
::100755 100755 100755 52b7a2d 6d1ac04 d2ac7d7 RM       foo.sh  bar.sh  bar.sh
::100644 100644 100644 e07d6c5 9042e82 ee91881 RR       fooey.c fuey.c  phooey.c




Notez que le diff combiné ne liste que les fichiers qui ont été
    modifiés par rapport à tous les parents.
