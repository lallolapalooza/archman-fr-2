<refspec>

Spécifie quels refs récupérer et quels refs locaux mettre à jour. Lorsque aucun <refspec> n'apparaît sur la ligne de commande, les refs à récupérer sont lus à partir des variables remote.<dépôt>.fetch à la place (voir la section "BRANCHES DE SUIVI CONFIGURÉES" dans git-fetch(1).

Le format d'un paramètre <refspec> est un signe plus optionnel +, suivi de la source <src>, suivi de deux-points :, suivi de la destination <dst>. Les deux-points peuvent être omis lorsque <dst> est vide. <src> est typiquement un ref, ou un motif glob avec une seule étoile * utilisé pour faire correspondre un ensemble de refs, mais cela peut aussi être un nom d'objet hexadécimal complet.

Un <refspec> peut contenir une * dans son <src> pour indiquer une correspondance de motif simple. Un tel refspec fonctionne comme un glob qui correspond à n'importe quel ref avec le motif. Un <refspec> de motif doit avoir une et une seule * dans le <src> et le <dst>. Il mappera les refs vers la destination en remplaçant le * par le contenu correspondant de la source.

Si un refspec est préfixé par ^, il sera interprété comme un refspec négatif. Plutôt que de spécifier quels refs récupérer ou quels refs locaux mettre à jour, un tel refspec spécifiera plutôt les refs à exclure. Un ref sera considéré comme correspondant s'il correspond à au moins un refspec positif et ne correspond à aucun refspec négatif. Les refspecs négatifs peuvent être utiles pour restreindre la portée d'un refspec de motif afin qu'il n'inclue pas de refs spécifiques. Les refspecs négatifs peuvent eux-mêmes être des refspecs de motif. Cependant, ils ne peuvent contenir qu'un <src> et ne spécifient pas de <dst>. Les noms d'objets hexadécimaux entièrement épelés ne sont pas non plus pris en charge.

tag <tag> signifie la même chose que refs/tags/<tag>:refs/tags/<tag> ; il demande la récupération de tout jusqu'au tag donné.

Le ref distant qui correspond à <src> est récupéré, et si <dst> n'est pas une chaîne vide, une tentative est faite pour mettre à jour le ref local qui y correspond.

Le fait que cette mise à jour soit autorisée sans --force dépend de l'espace de noms du ref vers lequel elle est récupérée, du type d'objet récupéré, et si la mise à jour est considérée comme un fast-forward. En général, les mêmes règles s'appliquent pour la récupération que pour le push, voir la section <refspec>... de git-push(1) pour connaître ces règles. Les exceptions à ces règles spécifiques à git fetch sont notées ci-dessous.

Jusqu'à la version 2.20 de Git, et contrairement au push avec git-push(1), toutes les mises à jour de refs/tags/* étaient acceptées sans + dans le refspec (ou --force). Lors de la récupération, nous considérions de manière promiscueuse toutes les mises à jour de tags d'une source distante comme des récupérations forcées. Depuis la version 2.20 de Git, la récupération pour mettre à jour refs/tags/* fonctionne de la même manière qu'en poussant. C'est-à-dire que toutes les mises à jour seront rejetées sans + dans le refspec (ou --force).

Contrairement au push avec git-push(1), toutes les mises à jour en dehors de refs/{tags,heads}/* seront acceptées sans + dans le refspec (ou --force), qu'il s'agisse d'échanger, par exemple, un objet arbre contre un blob, ou un commit contre un autre commit qui n'a pas le commit précédent comme ancêtre, etc.

Contrairement au push avec git-push(1), il n'y a pas de configuration qui modifiera ces règles, ni rien de tel qu'un hook pre-fetch analogue au hook pre-receive.

Comme pour le push avec git-push(1), toutes les règles décrites ci-dessus concernant ce qui n'est pas autorisé comme mise à jour peuvent être outrepassées en ajoutant un + optionnel au début d'un refspec (ou en utilisant l'option de ligne de commande --force). La seule exception est qu'aucune quantité de forçage ne fera accepter à l'espace de noms refs/heads/* un objet non-commit.


Remarque
Lorsque la branche distante que vous souhaitez récupérer est connue pour être régulièrement réinitialisée et rebasée, il est attendu que sa nouvelle pointe ne descende pas de sa pointe précédente (telle que stockée dans votre branche de suivi distant lors de votre dernière récupération). Vous voudrez utiliser le signe + pour indiquer que des mises à jour non-fast-forward seront nécessaires pour de telles branches. Il n'y a aucun moyen de déterminer ou de déclarer qu'une branche sera disponible dans un dépôt avec ce comportement ; l'utilisateur qui tire doit simplement savoir que c'est le modèle d'utilisation attendu pour une branche.

Remarque
Il y a une différence entre lister plusieurs <refspec> directement sur la ligne de commande git pull et avoir plusieurs entrées remote.<dépôt>.fetch dans votre configuration pour un <dépôt> et exécuter une commande git pull sans aucun paramètre explicite de <refspec>. Les <refspec> listés explicitement sur la ligne de commande sont toujours fusionnés dans la branche actuelle après la récupération. En d'autres termes, si vous listez plus d'un ref distant, git pull créera une fusion Octopus. D'autre part, si vous ne listez aucun paramètre <refspec> explicite sur la ligne de commande, git pull récupérera tous les <refspec> qu'il trouve dans la configuration remote.<dépôt>.fetch et ne fusionnera que le premier <refspec> trouvé dans la branche actuelle. En effet, créer une fusion Octopus à partir de refs distants est rarement fait, tandis que suivre plusieurs pointes distantes en une seule fois en récupérant plus d'une est souvent utile.

COMPORTEMENT PAR DÉFAUT

Souvent, les gens utilisent git pull sans fournir de paramètre. Traditionnellement, cela équivalait à dire git pull origin. Cependant, lorsque la configuration branch.<nom>.remote est présente sur la branche <nom>, cette valeur est utilisée à la place de origin.

Afin de déterminer quelle URL utiliser pour récupérer, la valeur de la configuration remote.<origin>.url est consultée et s'il n'y a pas une telle variable, la valeur de la ligne URL: dans $GIT_DIR/remotes/<origin> est utilisée.

Afin de déterminer quelles branches distantes récupérer (et stocker éventuellement dans les branches de suivi distant) lorsque la commande est exécutée sans aucun refspec sur la ligne de commande, les valeurs de la variable de configuration remote.<origin>.fetch sont consultées, et s'il n'y en a pas, $GIT_DIR/remotes/<origin> est consulté et ses lignes Pull: sont utilisées. En plus des formats de refspec décrits dans la section OPTIONS, vous pouvez avoir un refspec par caractères génériques qui ressemble à ceci :

refs/heads/*:refs/remotes/origin/*

Un refspec par caractères génériques doit avoir un RHS non vide (c'est-à-dire qu'il doit stocker ce qui a été récupéré dans les branches de suivi distant), et son LHS et son RHS doivent se terminer par /*. Ce qui précède spécifie que toutes les branches distantes sont suivies à l'aide de branches de suivi distant dans la hiérarchie refs/remotes/origin/ sous le même nom.

La règle pour déterminer quelle branche distante fusionner après la récupération est un peu complexe, afin de ne pas casser la compatibilité ascendante.

Si des refspecs explicites ont été donnés sur la ligne de commande de git pull, elles sont toutes fusionnées.

Lorsqu'aucun refspec n'a été donné sur la ligne de commande, alors git pull utilise le refspec de la configuration ou de $GIT_DIR/remotes/<origin>. Dans de tels cas, les règles suivantes s'appliquent :

1.Si la configuration branch.<nom>.merge pour la branche actuelle <nom> existe, c'est le nom de la branche sur le site distant qui est fusionnée.
2.Si le refspec est un refspec par caractères génériques, rien n'est fusionné.
3.Sinon, la branche distante du premier refspec est fusionnée.

EXEMPLES

•Mettez à jour les branches de suivi distant du répertoire que vous avez cloné, puis fusionnez l'une d'elles dans votre branche actuelle : 
$ git pull
$ git pull origin

Normalement, la branche fusionnée est la HEAD du dépôt distant, mais le choix est déterminé par les options branch.<nom>.remote et branch.<nom>.merge ; voir git-config(1) pour plus d'informations.

•Fusionnez la branche distante next dans la branche actuelle : 
$ git pull origin next

Cela laisse une copie temporaire de next dans FETCH_HEAD, et met à jour la branche de suivi distant origin/next. La même chose peut être faite en appelant fetch et merge :

$ git fetch origin
$ git merge origin/next

Si vous avez essayé un pull qui a entraîné des conflits complexes et que vous souhaitiez recommencer, vous pouvez récupérer avec git reset.

SÉCURITÉ

Les protocoles de fetch et de push ne sont pas conçus pour empêcher une partie de voler des données à l'autre dépôt qui n'était pas destinée à être partagée. Si vous avez des données privées que vous devez protéger contre un pair malveillant, votre meilleure option est de les stocker dans un autre dépôt. Cela s'applique aux clients et aux serveurs. En particulier, les espaces de noms sur un serveur ne sont pas efficaces pour le contrôle d'accès en lecture ; vous ne devriez accorder l'accès en lecture à un espace de noms qu'aux clients auxquels vous feriez confiance pour un accès en lecture à l'ensemble du dépôt.

Les vecteurs d'attaque connus sont les suivants :

1.La victime envoie des lignes "have" annonçant les identifiants des objets qu'elle possède et qui ne sont pas explicitement destinés à être partagés mais qui peuvent être utilisés pour optimiser le transfert si le pair les possède également. L'attaquant choisit un ID d'objet X à voler et envoie une référence vers X, mais n'est pas obligé d'envoyer le contenu de X car la victime le possède déjà. Maintenant, la victime pense que l'attaquant possède X, et elle renvoie le contenu de X à l'attaquant plus tard. (Cette attaque est la plus simple pour un client à effectuer sur un serveur, en créant une référence vers X dans l'espace de noms auquel le client a accès et en le récupérant. La manière la plus probable pour un serveur de l'effectuer sur un client est de "fusionner" X dans une branche publique et d'espérer que l'utilisateur effectue un travail supplémentaire sur cette branche et la pousse vers le serveur sans remarquer la fusion.)
2.Comme dans le point 1, l'attaquant choisit un ID d'objet X à voler. La victime envoie un objet Y que l'attaquant possède déjà, et l'attaquant prétend faussement posséder X et non Y, donc la victime envoie Y comme delta par rapport à X. Le delta révèle à l'attaquant des régions de X qui sont similaires à Y.

BOGUES

L'utilisation de --recurse-submodules ne peut actuellement récupérer que les nouveaux commits dans les sous-modules déjà extraits. Lorsque, par exemple, upstream a ajouté un nouveau sous-module dans les commits nouvellement récupérés du superprojet, le sous-module lui-même ne peut pas être récupéré, ce qui rend impossible son extraction ultérieure sans avoir à refaire une récupération. Cela devrait être corrigé dans une future version de Git.
