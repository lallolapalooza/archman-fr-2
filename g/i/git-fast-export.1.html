DESCRIPTIO

N

Ce programme exporte les révisions données dans un format adapté pour être envoyé via un pipe vers git fast-im

port.

Vous pouvez l'utiliser comme alternative lisible par l'humain à un bundle (voir git-bundle(1)), ou comme format pouvant être modifié avant d'être transmis à git fast-import afin de réécrire l'historique (une fonctionnalité utilisée par des outils comme git filt

er-re
po).

OPTION

S

--progress=<n

>
Insère des instructions de progression tous les <n> objets, à afficher par git fast-import pendant
l'importation.

--signed-tags=(verbatim|warn-verbatim|warn-strip|strip|abort

)
Spécifie comment gérer les tags signés. Puisque toute transformation après l'export (ou pendant l'export, comme l'exclusion de révisions) peut modifier les empreintes signées, les signatures peuvent devenir invalides.

Lorsqu'on demande abort (qui est la valeur par défaut), ce programme se terminera par une erreur en rencontrant un tag signé. Avec strip, les tags seront rendus non signés silencieusement, avec warn-strip ils seront rendus non signés mais un avertissement sera affiché, avec verbatim, ils seront exportés silencieusement et avec warn-verbatim (ou warn, un synonyme déprécié), ils seront exportés, mais vous verrez un avertissement. verbatim et warn-verbatim ne devraient être utilisés que si vous savez qu'aucune transformation affectant les tags ou tout commit dans leur historique ne s

era effectuée par vous, par fast-export ou par fast-import, ou si vou
s ne vous souciez pas que le tag résultant ait une signature invalide.

--signed-commits=(verbatim|warn-verbatim|warn-strip|strip|abort

)
Spécifie comment gérer les commits signés. Se comporte exactement comme --signed-tags, mais pour les commits. La valeur par défaut est strip, ce qui est le même comportement que les versions antérieures de cette commande sans cette option.

Lorsqu'ils sont exportés, les signatures commencent par

:

gpgsig <git-hash-algo> <signature-format

>

où <git-hash-algo> est l'empreinte d'objet Git, donc soit "sha1" ou "sha256", et <signature-format> est le type de signature, donc "openpgp", "x509", "ssh" ou

"unknown".

Par exemple, une signature OpenPGP sur un commit SHA-1 commence par gpgsig sha1 openpgp, tandis qu'une signature SSH sur un commit SHA-256 commence par gpgsig sha256 ssh

.

Bien que toutes les signatures d'un commit soient exportées, un importateur peut choisir de n'en accepter que certaines. Par exemple git-fast-import(1) stocke actuellement au plus une signature par algorithme de hachage Git dans chaque

commit.

Note
Ceci est hautement expérimental et le for
mat du flux de données peut changer dans l
e futur sans garantie de compatibilité.

--tag-of-filtered-object=(abort|drop|rewrite

)
Spécifie comment gérer les tags dont l'objet tagué est filtré. Puisque les révisions et les fichiers à exporter peuvent être limités par chemin, les objets tagués peuvent être complètement filtrés.

Lorsqu'on demande abort (qui est la valeur par défaut), ce programme se terminera par une erreur en rencontrant un tel tag. Avec drop, il omettra de tels tags de la sortie. Avec rewrite, si l'objet tagué est un commit, il réécrira le tag pour taguer un commit ancêtre (via la réécriture des parents ; voir git-rev-

list(
1)).

-M,

-C
Effectue la détection de déplacement et/ou de copie, comme décrit dans la page man git-diff(1), et l'utilise pour générer des commandes de renommage et de copie dans le dump de sortie.

Notez que les versions antérieures de cette comma

nde ne se plaignaient pas et produisaient des
résultats incorrects si vous donniez ces options.

--export-marks=<file

>
Exporte la table interne des marques vers <file> lorsque c'est terminé. Les marques sont écrites une par ligne sous la forme :markid SHA-1. Seules les marques pour les révisions sont exportées ; les marques pour les blobs sont ignorées. Les backends peuvent utiliser ce fichier pour valider les imports après leur achèvement, ou pour sauvegarder la table des marques entre des exécutions incrémentielles. Comme <file> n'est ouvert et tronqué qu'à la fin, le même chemin peut aussi être donné en toute sécurité à --import-marks. Le fichier ne sera pas écrit si aucun nouvel objet n'a été
marqué/exporté.

--import-marks=<file

>
Avant de traiter toute entrée, charge les marques spécifiées dans <file>. Le fichier d'entrée doit exister, doit être lisible et doit utiliser le même format que celui produit par
--export-marks.

--mark-tag

s
En plus d'étiqueter les blobs et les commits avec des identifiants de marques, étiquette aussi les tags. Ceci est utile en conjonction avec --export-marks et --import-marks, et est aussi utile (et nécessaire) pour l'export de tags imbriqués. Cela ne nuit pas aux autres cas et devrait être la valeur par défaut, mais de nombreux frontaux de fast-import ne sont pas préparés à accepter des tags avec des identifiants de marques.

Tout commit (ou tag) qui a déjà été marqué ne sera pas exporté à nouveau. Si le bac

kend utilise un fichier --import-marks similaire, cela permet un export incrémentiel
bidirectionnel du dépôt en conservant les marques identiques entre les exécutions.

--fake-missing-tagge

r
Certains anciens dépôts ont des tags sans tagueur. Le protocole fast-import était assez strict à ce sujet et ne l'autorisait pas. Donc un tagueur fictif est créé pour pouvoir fast-importer la
sortie.

--use-done-featur

e
Commence le flux avec une strophe feature done, et le termine avec une commande
done.

--no-dat

a
Saute la sortie des objets blobs et fait plutôt référence aux blobs via leur empreinte SHA-1 originale. Ceci est utile lors de la réécriture de la structure de répertoires ou de l'historique d'un dépôt sans toucher au contenu des fichiers individuels. Notez que le flux résultant ne peut être utilisé que par un dépôt qui contient déjà les objets
nécessaires.

--full-tre

e
Cette option fera émettre à fast-export une directive "deleteall" pour chaque commit suivie d'une liste complète de tous les fichiers du commit (par opposition à simplement lister les fichiers qui sont différents du premier parent du commit)
.

--anonymiz

e
Anonymise le contenu du dépôt tout en conservant la forme de l'historique et de l'arbre stocké. Voir la section sur L'ANONYMISATION ci
-dessous.

--anonymize-map=<from>[:<to>

]
Convertit le jeton <from> en <to> dans la sortie anonymisée. Si <to> est omis, mappe <from> vers lui-même (c.-à-d., ne l'anonymise pas). Voir la section sur L'ANONYMISATION ci
-dessous.

--reference-excluded-parent

s
Par défaut, l'exécution d'une commande telle que git fast-export master~5..master n'inclura pas le commit master~5 et fera que master~4 n'aura plus master~5 comme parent (bien que l'ancien master~4 et le nouveau master~4 auront tous les mêmes fichiers). Utilisez --reference-excluded-parents pour que le flux fasse plutôt référence aux commits dans la plage d'historique exclue par leur sha1sum. Notez que le flux résultant ne peut être utilisé que par un dépôt qui contient déjà les commits parents
nécessaires.

--show-original-id

s
Ajoute une directive supplémentaire à la sortie pour les commits et les blobs, original-oid <SHA1SUM>. Bien que de telles directives seront probablement ignorées par des importateurs comme git-fast-import, cela peut être utile pour des filtres intermédiaires (par ex. pour réécrire les messages de commit qui font référence à d'anciens commits, ou pour filtrer des blobs par identifiant)
.

--reencode=(yes|no|abort

)
Spécifie comment gérer l'en-tête d'encodage dans les objets commit. Lorsqu'on demande abort (qui est la valeur par défaut), ce programme se terminera par une erreur en rencontrant un tel objet commit. Avec yes, le message de commit sera ré-encodé en UTF-8. Avec no, l'encodage d'origine sera
préservé.

--refspe

c
Applique le refspec spécifié à chaque ref exporté. Plusieurs peuvent être
spécifiés.

[<git-rev-list-args>...

]
Une liste d'arguments, acceptés par git rev-parse et git rev-list, qui spécifie les objets et références spécifiques à exporter. Par exemple, master~10..master fait exporter la référence master actuelle avec tous les objets ajoutés depuis son 10e commit ancêtre et (sauf si l'option --reference-excluded-parents est spécifiée) tous le
s fichiers communs à
master~9 et master~10.

EXEMPLE

S 
$ git fast-export --al
l | (cd /empty/reposito
ry && git fast-import)

Cela exportera l'intégralité du dépôt et l'importera dans le dépôt existant vide. À part le réencodage des commits qui ne sont pas en UTF-8, il s'agirait d'un miroir

un-à-un. 
$ git fast-export master~5..master |
sed "s|refs/heads/master|refs/h
eads/other|" | git fast-import

Cela crée une nouvelle branche appelée other à partir de master~5..master (c'est-à-dire si master a un historique linéaire, cela prendra les 5 derniers commits)

.

Notez que cela suppose qu'aucun des blobs et messages de commit référencés par cette plage de révisions ne contient la chaîne refs/heads/maste

r
.

ANONYMISATIO

N

Si l'option --anonymize est donnée, git essaiera de supprimer toutes les informations d'identification du dépôt tout en conservant suffisamment des motifs de l'arbre et de l'historique originaux pour reproduire certains bugs. L'objectif est qu'un bug git trouvé sur un dépôt privé persiste dans le dépôt anonymisé, et que ce dernier puisse être partagé avec les développeurs de git pour aider à résoudre le

bug.

Avec cette option, git remplacera tous les noms de références, chemins, contenus de blobs, messages de commits et d'étiquettes, noms et adresses courriel dans la sortie par des données anonymisées. Deux occurrences de la même chaîne seront remplacées de manière équivalente (par exemple, deux commits avec le même auteur auront le même auteur anonymisé dans la sortie, mais ne ressembleront en rien à la chaîne d'auteur originale). Les relations entre les commits, les branches et les étiquettes sont conservées, ainsi que les horodatages des commits (mais les messages de commit et les noms de références ne ressemblent en rien aux originaux). La composition relative de l'arbre est conservée (par exemple, si vous avez un arbre racine avec 10 fichiers et 3 arbres, la sortie en aura autant), mais leurs noms et le contenu des fichiers seront

remplacés.

Si vous pensez avoir trouvé un bug git, vous pouvez commencer par exporter un flux anonymisé de l'intégralité du dépôt

: 
$ git fast-expor
t --anonymize --
all >anon-stream

Confirmez ensuite que le bug persiste dans un dépôt créé à partir de ce flux (beaucoup de bugs ne persisteront pas, car ils dépendent vraiment du contenu exact du dépôt)

: 
$ git init anon-repo
$ cd anon-repo
$ git fast-import <../anon-stream
$ ... testez votre bug .
.
.

Si le dépôt anonymisé montre le bug, il peut être utile de partager anon-stream avec un rapport de bug habituel. Notez que le flux anonymisé se compresse très bien, donc il est recommandé de le compresser avec gzip. Si vous voulez examiner le flux pour vérifier qu'il ne contient aucune donnée privée, vous pouvez le parcourir directement avant de l'envoyer. Vous pouvez aussi essayer

: 
$ perl -pe 's/\d+
/X/g' <anon-stream
| sort -u | less

ce qui affiche toutes les lignes uniques (avec les nombres convertis en « X », pour fusionner « User 0 », « User 1 », etc. en « User X »). Cela produit une sortie beaucoup plus petite, et il est généralement facile de confirmer rapidement qu'il n'y a pas de données privées dans le

flux.

Reproduire certains bugs peut nécessiter de référencer des commits ou des chemins particuliers, ce qui devient difficile après que les noms de références et les chemins ont été anonymisés. Vous pouvez demander qu'un jeton particulier soit laissé tel quel ou mappé vers une nouvelle valeur. Par exemple, si vous avez un bug qui se reproduit avec git rev-list sensitive -- secret.c, vous pouvez exécuter

: 
$ git fast-export --anonymize --all \
--anonymize-map=sensitive:foo \ --a
nonymize-map=secret.c:bar.c \ >stream

Après avoir importé le flux, vous pouvez alors exécuter git rev-list foo -- bar.c dans le dépôt

anonymisé.

Notez que les chemins et les noms de références sont divisés en jetons aux limites des barres obliques. La commande ci-dessus anonymiserait subdir/secret.c en quelque chose comme path123/bar.c ; vous pourriez alors rechercher bar.c dans le dépôt anonymisé pour déterminer le nom de chemin

final.

Pour simplifier la référence du nom de chemin final, vous pouvez mapper chaque composant de chemin ; ainsi, si vous anonymisez aussi subdir en publicdir, alors le nom de chemin final serait publicdi

r/ba
r.c.

LIMITATION

S

Puisque git fast-import ne peut pas étiqueter des arbres, vous ne pourrez pas exporter complètement

le dépôt linux.git, car il contient une éti
quette référençant un arbre au lieu d'un commit.
