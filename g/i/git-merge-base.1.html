NOM

git-merge-base - Trouver les meilleurs ancêtres communs possibles pour une fusion

SYNTAXE

git merge-base [-a | --all] <commit> <commit>...
git merge-base [-a | --all] --octopus <commit>...
git merge-base --is-ancestor <commit> <commit>
git merge-base --independent <commit>...
git merge-base --fork-point <ref> [<commit>]

DESCRIPTION

git merge-base trouve le ou les meilleurs ancêtres communs entre deux commits à utiliser dans une fusion à trois voies. Un ancêtre commun est meilleur qu'un autre ancêtre commun si ce dernier est un ancêtre du premier. Un ancêtre commun qui n'a pas d'ancêtre commun meilleur est un meilleur ancêtre commun, c'est-à-dire une base de fusion. Notez qu'il peut y avoir plus d'une base de fusion pour une paire de commits.

MODES OPÉRATOIRES

Dans le cas spécial le plus courant, spécifier seulement deux commits sur la ligne de commande signifie calculer la base de fusion entre les deux commits donnés.

Plus généralement, parmi les deux commits à partir desquels calculer la base de fusion, l'un est spécifié par le premier argument de commit sur la ligne de commande ; l'autre commit est un commit (potentiellement hypothétique) qui est une fusion de tous les commits restants sur la ligne de commande.

En conséquence, la base de fusion n'est pas nécessairement contenue dans chacun des arguments de commit si plus de deux commits sont spécifiés. Ceci est différent de git-show-branch(1) lorsqu'il est utilisé avec l'option --merge-base.

--octopus

Calcule les meilleurs ancêtres communs de tous les commits fournis, en préparation d'une fusion à n voies. Ceci imite le comportement de git show-branch --merge-base.

--independent

Au lieu d'afficher les bases de fusion, affiche un sous-ensemble minimal des commits fournis avec les mêmes ancêtres. En d'autres termes, parmi les commits donnés, liste ceux qui ne sont pas accessibles depuis un autre. Ceci imite le comportement de git show-branch --independent.

--is-ancestor

Vérifie si le premier <commit> est un ancêtre du second <commit>, et sort avec le statut 0 si c'est vrai, ou avec le statut 1 sinon. Les erreurs sont signalées par un statut non nul qui n'est pas 1.

--fork-point

Trouve le point auquel une branche (ou toute histoire menant à <commit>) s'est séparée d'une autre branche (ou de toute référence) <ref>. Ceci ne cherche pas seulement l'ancêtre commun des deux commits, mais prend également en compte le reflog de <ref> pour voir si l'histoire menant à <commit> s'est séparée d'une ancienne incarnation de la branche <ref> (voir la discussion sur ce mode ci-dessous).

OPTIONS

-a, --all

Affiche toutes les bases de fusion pour les commits, au lieu d'une seule.

DISCUSSION

Étant donné deux commits A et B, git merge-base A B affichera un commit qui est accessible depuis A et B par la relation parent.

Par exemple, avec cette topologie :

         o---o---o---B
        /
---o---1---o---o---o---A

la base de fusion entre A et B est 1.

Étant donné trois commits A, B et C, git merge-base A B C calculera la base de fusion entre A et un commit hypothétique M, qui est une fusion entre B et C. Par exemple, avec cette topologie :

       o---o---o---o---C
      /
     /   o---o---o---B
    /   /
---2---1---o---o---o---A

le résultat de git merge-base A B C est 1. Ceci parce que la topologie équivalente avec un commit de fusion M entre B et C est :

       o---o---o---o---o
      /                 \
     /   o---o---o---o---M
    /   /
---2---1---o---o---o---A

et le résultat de git merge-base A M est 1. Le commit 2 est également un ancêtre commun entre A et M, mais 1 est un meilleur ancêtre commun, car 2 est un ancêtre de 1. Par conséquent, 2 n'est pas une base de fusion.

Le résultat de git merge-base --octopus A B C est 2, car 2 est le meilleur ancêtre commun de tous les commits.

Lorsque l'historique implique des fusions croisées, il peut y avoir plus d'une meilleure base commune pour deux commits. Par exemple, avec cette topologie :

---1---o---A
    \ /
     X
    / \
---2---o---o---B

1 et 2 sont tous deux des bases de fusion de A et B. Aucun des deux n'est meilleur que l'autre (ce sont tous deux des meilleures bases de fusion). Lorsque l'option --all n'est pas donnée, il n'est pas spécifié laquelle des meilleures bases sera affichée.

Une astuce courante pour vérifier si un branchement est "fast-forward" entre deux commits A et B consiste (ou consistait du moins) à calculer la base de fusion entre A et B, et à vérifier si elle est identique à A, auquel cas A est un ancêtre de B. Vous verrez souvent cette astuce dans les anciens scripts.

A=$(git rev-parse --verify A)
if test "$A" = "$(git merge-base A B)"
then
        ... A est un ancêtre de B ...
fi

Dans git moderne, vous pouvez le dire de manière plus directe :

if git merge-base --is-ancestor A B
then
        ... A est un ancêtre de B ...
fi

à la place.

DISCUSSION SUR LE MODE FORK-POINT

Après avoir travaillé sur la branche topic créée avec git switch -c topic origin/master, l'historique de la branche de suivi distant origin/master peut avoir été rembobiné et reconstruit, conduisant à un historique de cette forme :

                 o---B2
                /
---o---o---B1--o---o---o---B (origin/master)
        \
         B0
          \
           D0---D1---D (topic)

où origin/master pointait auparavant sur les commits B0, B1, B2 et pointe maintenant sur B, et votre branche topic a été démarrée au-dessus lorsque origin/master était sur B0, et vous avez construit trois commits, D0, D1 et D, par-dessus. Imaginez que vous voulez maintenant rebaser le travail que vous avez effectué sur la branche topic au-dessus de origin/master mis à jour.

Dans un tel cas, git merge-base origin/master topic retournerait le parent de B0 dans l'image ci-dessus, mais B0^..D n'est pas la plage de commits que vous voudriez rejouer au-dessus de B (elle inclut B0, ce qui n'est pas ce que vous avez écrit ; c'est un commit que l'autre partie a abandonné lorsqu'elle a déplacé son pointeur de B0 à B1).

git merge-base --fork-point origin/master topic est conçu pour aider dans ce cas. Il prend en compte non seulement B, mais aussi B0, B1 et B2 (c'est-à-dire les anciennes extrémités des branches de suivi distant que le reflog de votre dépôt connaît) pour voir sur quel commit votre branche topic a été construite et trouve B0, vous permettant de rejouer uniquement les commits de votre branche topic, en excluant les commits que l'autre partie a ensuite abandonnés.

Donc

$ fork_point=$(git merge-base --fork-point origin/master topic)

trouvera B0, et

$ git rebase --onto origin/master $fork_point topic

rejouera D0, D1 et D au-dessus de B pour créer un nouvel historique de cette forme :

                 o---B2
                /
---o---o---B1--o---o---o---B (origin/master)
        \                   \
         B0                  D0'--D1'--D' (topic - mis à jour)
          \
           D0---D1---D (topic - ancien)

Une mise en garde est que les anciennes entrées du reflog dans votre dépôt peuvent être expirées par git gc. Si B0 n'apparaît plus dans le reflog de la branche de suivi distant origin/master, le mode --fork-point ne pourra évidemment pas le trouver et échouera, évitant de donner un résultat aléatoire et inutile (tel que le parent de B0, comme le fait la même commande sans l'option --fork-point).

De plus, la branche de suivi distant que vous utilisez avec le mode --fork-point doit être celle dont votre branche topic s'est séparée à son extrémité. Si vous vous êtes séparé d'un commit plus ancien que l'extrémité, ce mode ne fonctionnera pas comme prévu.
