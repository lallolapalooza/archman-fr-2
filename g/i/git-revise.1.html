NOM

git-revise - Mettre à jour, diviser et réorganiser efficacement les commits git

SYNOPIS

git revise [<options>] [<cible>]

DESCRIPTION

git revise est une sous-commande de git(1) pour mettre à jour, diviser et réorganiser efficacement les commits. Elle s'inspire fortement de git-rebase(1), mais essaie d'être plus efficace et ergonomique pour les flux de travail orientés piles de correctifs.

Par défaut, git revise appliquera les modifications indexées à <cible>, mettant à jour HEAD pour pointer vers l'historique révisé. Elle prend également en charge la division des commits et la reformulation des messages de commit.

Contrairement à git-rebase(1), git revise évite de modifier l'état du répertoire de travail et de l'index, effectuant toutes les fusions en mémoire, et ne les écrivant que lorsque c'est nécessaire. Cela lui permet d'être significativement plus rapide sur les grandes bases de code et d'éviter d'invalider les builds.

Si --autosquash ou --interactive est spécifié, l'argument <cible> peut être omis ou donné comme valeur spéciale :option:--root. S'il est omis, git revise considérera une plage de commits non publiés sur la branche actuelle. S'il est donné comme :option:--root, tous les commits, y compris le commit racine, seront considérés.

OPTIONS

Options générales

-a, --all
Indexe les modifications apportées aux fichiers suivis avant la révision.
-p, --patch
Indexe interactivement les fragments (hunks) du répertoire de travail avant la révision.
--no-index
Ignore les modifications indexées dans l'index.
--reauthor
Réinitialise l'auteur du commit cible à l'utilisateur actuel.
--ref <gitref>
Branche de travail à mettre à jour ; par défaut, HEAD.
-S, --gpg-sign, --no-gpg-sign
Signe les commits avec GPG. Remplace à la fois la configuration commit.gpgSign et revise.gpgSign de git.

Modes principaux de fonctionnement

-i, --interactive
Plutôt que d'appliquer les modifications indexées à <cible>, modifie une liste de tâches des actions à effectuer sur les commits après <cible>. Voir MODE INTERACTIF.
--autosquash, --no-autosquash
Plutôt que d'appliquer directement les modifications indexées à <cible>, effectue automatiquement les actions de correction (fixup) ou de fusionnement (squash) marquées avec fixup! ou squash! entre <cible> et HEAD actuel. Pour plus d'informations sur ce que font ces actions, voir MODE INTERACTIF.

Ces commits sont généralement créés avec git commit --fixup=<commit> ou git commit --squash=<commit>, et identifient la cible avec la première ligne de son message de commit.

Cette option peut être combinée avec --interactive pour modifier les tâches générées avant leur exécution.

Si l'option --autosquash est activée par défaut via une variable de configuration, l'option --no-autosquash peut être utilisée pour remplacer et désactiver ce réglage. Voir CONFIGURATION.

-c, --cut
Sélectionne interactivement des fragments (hunks) de <cible>. Les fragments choisis sont divisés en un deuxième commit immédiatement après la cible.

Après la division, les messages des deux commits sont modifiés.

Voir la section « Mode interactif » de git-add(1) pour savoir comment utiliser ce mode.

-e, --edit
Après avoir appliqué les modifications indexées, modifie le message du commit <cible>.

Cette option peut être combinée avec --interactive pour permettre la modification des messages de commit dans la liste des tâches. Pour plus d'informations, voir MODE INTERACTIF.

-m <msg>, --message <msg>
Utilise le <msg> donné comme nouveau message de commit pour <cible>. Si plusieurs options -m sont données, leurs valeurs sont concaténées comme paragraphes séparés.
--version
Affiche les informations de version et quitte.

CONFIGURATION

La configuration est gérée par git-config(1).

revise.autoSquash
Si défini à vrai, implique --autosquash chaque fois que --interactive est spécifié. Remplace par --no-autosquash. Par défaut, faux. Si non défini, la valeur de rebase.autoSquash est utilisée à la place.
revise.gpgSign
Si défini à vrai, signe les nouveaux commits avec GPG ; par défaut, faux. Ce paramètre remplace la configuration git originale commit.gpgSign et peut être remplacé par les options de ligne de commande --gpg-sign et --no-gpg-sign.

RÉSOLUTION DES CONFLITS

Lorsqu'un conflit est rencontré, git revise tentera de le résoudre automatiquement en utilisant les mécanismes standards de git. Si la résolution automatique échoue, l'utilisateur sera invité à les résoudre manuellement.

Il n'y a actuellement aucun support pour utiliser git-mergetool(1) pour résoudre les conflits.

Aucune tentative n'est faite pour détecter les renommages de fichiers ou de répertoires. git revise peut produire des résultats sous-optimaux en cas de renommages. Utilisez le mode interactif de git-rebase(1) lorsque le suivi des renommages est important.

NOTES

Un git revise réussi ajoutera une seule entrée au reflog, permettant de l'annuler avec git reset @{1}. Les commandes git revise infructueuses laisseront votre dépôt largement inchangé.

Aucun commit de fusion ne peut exister entre le commit cible et HEAD, car leur réécriture n'est pas supportée.

Voir git-rebase(1) pour plus d'informations sur les implications de la modification de l'historique d'un dépôt que vous partagez.

MODE INTERACTIF

git revise supporte un mode interactif inspiré du mode interactif de git-rebase(1).

Ce mode est démarré avec le dernier commit que vous souhaitez conserver "tel quel" :

git revise -i <commit-après-lequel>

La cible spéciale --root est disponible pour réviser tout jusqu'au commit racine :

git revise -i --root

Un éditeur sera lancé avec les commits de votre branche actuelle après le commit spécifié. Si l'index contient des modifications indexées mais non commitées, une entrée <git index> sera également présente.
