Réécriture des parents

--replace-refs {delete-no-add, delete-and-add, update-no-add, update-or-add, update-and-add, old-default}

Comment gérer les replace refs (voir git-replace(1)). Des replace refs peuvent être ajoutées pendant la réécriture de l'historique afin de permettre aux utilisateurs de passer les anciens IDs de commit (d'avant l'exécution de git-filter-repo) aux commandes git et que git sache comment traduire ces anciens IDs de commit vers les nouveaux IDs de commit (post-réécriture). De plus, les replace refs qui existaient avant la réécriture peuvent être soit supprimées soit mises à jour. Les choix à passer à --replace-refs doivent donc spécifier à la fois quoi faire avec les refs existantes et quoi faire avec les réécritures de commits. Ainsi update-and-add signifie mettre à jour les replace refs existantes, et pour toute réécriture de commit (même si elle est déjà pointée par une replace ref) ajouter une nouvelle référence refs/replace/ pour faire la correspondance de l'ancien ID de commit vers le nouvel ID de commit. Le défaut est update-no-add, ce qui signifie mettre à jour les replace refs existantes mais ne pas en ajouter de nouvelles. Il existe aussi une option spéciale old-default pour choisir le défaut utilisé dans les versions antérieures à git-filter-repo-2.45, à savoir update-and-add lors de la première exécution de git-filter-repo dans un dépôt et update-or-add si git-filter-repo est exécuté à nouveau sur un dépôt.

--prune-empty {always, auto, never}

S'il faut élaguer les commits vides. auto (le défaut) signifie n'élaguer que les commits qui deviennent vides (pas les commits qui étaient vides dans le dépôt original, à moins que leur parent n'ait été élagué). Quand le parent d'un commit est élagué, le premier ancêtre non élagué devient le nouveau parent.

--prune-degenerate {always, auto, never}

Comme les commits de fusion sont nécessaires pour la topologie de l'historique, ils sont généralement exemptés d'élagage. Cependant, ils peuvent devenir dégénérés avec l'élagage d'autres commits (ayant moins de deux parents, ayant un commit servant de parent aux deux, ou ayant un parent comme ancêtre de l'autre.) Si de tels commits de fusion n'ont aucun changement de fichier, ils peuvent être élagués. Le défaut (auto) est de n'élaguer que les commits de fusion vides qui deviennent dégénérés (pas ceux qui l'étaient déjà au départ).

--no-ff

Même si le premier parent est ou devient un ancêtre d'un autre parent, ne pas l'élaguer. Cela modifie le comportement de --prune-degenerate, et peut être utile dans les projets qui utilisent toujours merge --no-ff.

•Récupérer toutes les refs, afin que si des refs en dehors des branches et des tags référencent aussi les données sensibles, elles puissent être nettoyées aussi

  des changements non poussés) dans votre dépôt, sur n'importe quelle branche ou
  ref, cette étape de récupération peut les éliminer. Travailler dans un clone

•Suivre et signaler le(s) premier(s) commit(s) modifié(s)
•Suivre et signaler si des objets LFS deviennent orphelins à cause de la réécriture, afin qu'ils puissent être supprimés
•Fournir des instructions supplémentaires à la fin sur la façon de nettoyer le dépôt à partir duquel vous avez cloné, et les autres clones du dépôt

--no-fetch

Éviter l'étape de « récupération de toutes les refs » avec --sensitive-data-removal, et ainsi éviter d'écraser les changements locaux uniquement dans le dépôt, mais au risque de laisser les données sensibles dans d'autres refs du dépôt source. Cette option est implicite avec --partial ou toute option qui implique --partial.

--stdin

SORTIE

Chaque fois que filter-repo est exécuté, des fichiers sont créés dans le .git/filter-repo/ répertoire. Ces fichiers sont mis à jour ou écrasés à chaque exécution.

Carte des commits

Le $GIT_DIR/filter-repo/commit-map fichier contient une correspondance de la manière dont tous les commits ont été (ou n'ont pas été) modifiés.

•Un en-tête est la première ligne avec le texte "old" et "new"
•Les correspondances de commits ne sont dans aucun ordre particulier
•Tous les commits dans la portée de la réécriture seront listés, même les commits qui sont inchangés (par exemple parce que le commit est antérieur à l'introduction dans le dépôt des fichiers que l'opération de filtre supprime).
•Un hash tout à zéro, ou SHA nul, représente un objet inexistant. Lorsqu'il est dans la colonne "new", cela signifie que le commit a été entièrement supprimé.

Carte des références

Le $GIT_DIR/filter-repo/ref-map fichier contient une correspondance de quelles références locales ont été (ou n'ont pas été) modifiées.

•Un en-tête est la première ligne avec le texte "old", "new" et "ref"
•Les correspondances de références sont triées par ref
•Un hash tout à zéro, ou SHA nul, représente un objet inexistant. Lorsqu'il est dans la colonne "new", cela signifie que la ref a été entièrement supprimée.

Références modifiées

Le $GIT_DIR/filter-repo/changed-refs fichier contient une liste des refs qui ont été modifiées.

•Aucun en-tête n'est fourni
•Liste les sous-ensembles de refs de ref-map pour lesquels old != new
•Bien que non nécessaire car cela ne fournit aucune nouvelle information par rapport à ref-map, cela facilite la détermination rapide des refs qui ont été modifiées par la réécriture.

Premiers commits modifiés

Le $GIT_DIR/filter-repo/first-changed-commits contient une liste du ou des premiers commits modifiés par l'opération de filtrage. Ce sont les commits qui ont été réécrits et qui n'avaient aucun parent qui l'avait également été.

Ainsi, par exemple, si vous aviez les commits A1-B1-C1-D1-E1 avant d'exécuter git-filter-repo, et qu'ensuite vous aviez les commits A1-B2-C2-D2-E2, alors le fichier des premiers commits modifiés ne contiendrait qu'une seule ligne, qui serait le hash de B2.

Dans la plupart des cas, il n'y aura qu'un seul commit listé, mais si vous aviez plusieurs commits racines ou un historique non linéaire où les commits sur ces historiques divergents étaient les premiers modifiés, alors il pourrait y avoir plusieurs premiers commits modifiés et ils seront chacun listés sur des lignes séparées.

Déjà exécuté

Le $GIT_DIR/filter-repo/already_ran fichier contient un fichier enregistrant que git-filter-repo a été exécuté. Lorsque ce fichier est présent, les exécutions futures seront traitées comme une extension de l'opération de filtrage précédente.

Concrètement, cela signifie : * La vérification "Fresh Clone" est contournée

Cela est fait car les exécutions passées causeraient à ce que le dépôt
ne ressemble plus à une copie fraîche (fresh clone), et échouerait donc à la
vérification de copie fraîche, mais faire du filtrage via plusieurs invocations
de git-filter-repo est un cas d'utilisation prévu et pris en charge. Vous avez
déjà passé ou contourné la vérification "Fresh Clone" lors de votre première
exécution.
•Les fichiers commit-map et ref-map ci-dessus seront mis à jour plutôt que simplement réécrits. 
En d'autres termes, si la première invocation de filter-repo a réécrit
le commit A en commit B, et que la deuxième invocation de filter-repo a réécrit
le commit B en commit C, alors la deuxième exécution aurait une entrée "A C"
plutôt qu'une entrée "B C" pour le commit modifié.
•Le ou les premiers commits modifiés (rapportés lors de l'utilisation de l'option --sensitive-data-removal) seront le premier commit original modifié, et non le premier commit intermédiaire modifié. 
Plus en détail, si le dépôt avait originellement les commits suivants :
   A1-B1-C1-D1-E1
et que la première invocation de filter-repo a changé cela en
   A1-B1-C2-D2-E2
alors la première exécution signalerait "C1" comme premier commit modifié. Si
une deuxième exécution de filter-repo changeait cela en
   A1-B1-C2-D3-E3
alors elle signalerait "C1" comme premier commit modifié, et non "D2",
car elle compare aux commits originaux plutôt qu'aux intermédiaires.

Cependant, si le fichier already_ran existe mais est plus vieux d'un jour lorsque l'utilisateur invoque git-filter-repo, on lui demandera si la nouvelle exécution doit être considérée comme une continuation de la précédente. S'il ne répond pas par l'affirmative, les trois points ci-dessus ne s'appliqueront pas. Cette invite existe car les utilisateurs pourraient faire une réécriture d'historique dans un dépôt, l'oublier et laisser le répertoire $GIT_DIR/filter-repo traîner, puis, quelques mois ou années plus tard, avoir besoin de faire une autre réécriture. Si des commits ont été rendus publics et partagés à partir de la réécriture précédente, alors la prochaine exécution de filter-repo ne devrait pas être considérée comme une continuation de l'exécution de filtrage précédente.

Objets LFS originaux

Lors de l'exécution avec l'indicateur --sensitive-data-removal, et si LFS est utilisé par le dépôt, le $GIT_DIR/filter-repo/original_lfs_objects contient une liste des objets LFS référencés par le dépôt avant la réécriture, dans un ordre trié.

Objets LFS orphelins

Lors de l'exécution avec l'indicateur --sensitive-data-removal, et si LFS est utilisé par le dépôt, le $GIT_DIR/filter-repo/orphaned_lfs_objects contient une liste des objets LFS qui étaient référencés par le dépôt mais qui ne le sont plus après l'exécution de git-filter-repo. Les objets apparaissent dans un ordre trié.

VÉRIFICATION DE SÉCURITÉ DE COPIE FRAÎCHE ET --FORCE

Puisque filter-repo effectue une réécriture irréversible de l'historique, il est important d'éviter d'apporter des modifications à un dépôt pour lequel l'utilisateur n'a pas de bonne sauvegarde. Le mécanisme de défense principal est simplement d'éduquer les utilisateurs et de compter sur eux pour être de bons intendants de leurs données ; ainsi, il y a plusieurs avertissements dans la documentation sur la manière dont filter-repo réécrit l'historique.

Cependant, en guise de service aux utilisateurs, nous aimerions fournir une vérification de sécurité supplémentaire au-delà de la documentation. Il n'y a pas de bonne manière de vérifier si l'utilisateur a une bonne sauvegarde, mais nous pouvons poser une question connexe qui est un proxy imparfait mais tout à fait raisonnable : "Est-ce que ce dépôt est une copie fraîche ?" Malheureusement, c'est aussi une question à laquelle nous ne pouvons pas obtenir une réponse parfaite ; git ne fournit pas de moyen de répondre à cette question. Cependant, il y a environ une douzaine de choses que j'ai trouvées qui semblent toujours vraies pour les clones tout neufs (en supposant qu'ils sont soit des clones de dépôts distants, soit faits avec le --no-local indicateur), et je vérifie toutes ces choses.

Ces vérifications peuvent avoir à la fois des faux positifs et des faux négatifs. Quelqu'un pourrait avoir une sauvegarde parfaitement bonne de son dépôt sans que ce soit réellement une copie fraîche — mais il n'y a pas de moyen pour filter-repo de le savoir. Inversement, quelqu'un pourrait regarder toutes les choses que filter-repo vérifie dans ses vérifications de sécurité et ensuite ajuster son dépôt non sauvegardé pour satisfaire ces conditions (bien que cela demanderait un effort considérable, et il est astronomiquement improbable qu'un dépôt qui n'est pas une copie fraîche corresponde aléatoirement à tous les critères). En pratique, les vérifications de sécurité que filter-repo utilise semblent vraiment bonnes pour éviter que les gens n'exécutent accidentellement filter-repo sur un dépôt sur lequel ils ne devraient pas l'exécuter. Cela m'a même attrapé une fois alors que je voulais vraiment exécuter filter-repo mais que j'étais dans un répertoire différent de celui que je pensais.

En bref, c'est tout à fait bien d'utiliser '--force` pour contourner les vérifications de sécurité tant que vous êtes d'accord pour que filter-repo réécrive irréversiblement le contenu du dépôt courant. C'est une très mauvaise idée de prendre l'habitude de spécifier toujours --force; si vous le faites, un jour vous exécuterez une de vos commandes dans le mauvais répertoire comme je l'ai fait, et vous n'aurez plus la vérification de sécurité pour vous sauver. De plus, ce n'est définitivement PAS bien de recommander --force sur des forums, des sites de questions-réponses, ou par email à d'autres utilisateurs sans d'abord expliquer soigneusement que --force signifie mettre les données de vos dépôts en danger. Je suis particulièrement dérangé par les gens qui suggèrent l'indicateur quand il clairement n'est PAS nécessaire ; ils mettent inutilement les données des autres en danger.

POLYVALENCE

filter-repo a une hiérarchie de capacités sur le spectre allant des indicateurs de commodité faciles à utiliser qui effectuent des types de filtrage prédéfinis, aux choix qui offrent beaucoup de flexibilité pour contrôler la manière dont le filtrage se produit. Ce spectre inclut ce qui suit :

•Indicateurs de commodité qui rendent simples les types courants de réécriture d'historique (par exemple --path, --strip-blobs-bigger-than, --replace-text, --mailmap)
•Options qui sont des raccourcis pour d'autres ou qui offrent un plus grand contrôle que d'autres (par exemple --subdirectory-filter pourrait être écrit à l'aide à la fois d'une sélection de chemin (--path) et d'un renommage de chemin (--path-rename) ; --paths-from-file peut gérer toutes les autres options --path* et plus encore comme le renommage de chemins par expression régulière)
•Rappels python génériques pour gérer un certain type de données (les rappels filename, message, name, email et refname)
•Rappels python génériques pour gérer les objets git fondamentaux, permettant un plus grand contrôle sur la combinaison des types de données que l'objet contient (les rappels commit, tag, blob et reset)
•La capacité d'importer filter-repo comme un module dans un programme python et d'utiliser ses classes et fonctions pour un contrôle et une flexibilité encore plus grands tout en tirant parti de nombreuses capacités de base. On peut même utiliser cela pour écrire de nouveaux outils avec une interface complètement différente.

Pour plus d'informations sur les rappels (callbacks), consultez la section intitulée « CALLBACKS ». Pour des exemples de programmes Python qui importent filter-repo comme module pour créer de nouveaux outils de réécriture d'historique, consultez le répertoire contrib/filter-repo-demos/. Ce répertoire contient, entre autres exemples, une réimplémentation de git-filter-branch plus rapide que git-filter-branch, et une réimplémentation de BFG Repo Cleaner avec plusieurs corrections de bogues et de nouvelles fonctionnalités.

DISCUSSION

Utiliser filter-repo est relativement simple, mais la réécriture de l'historique fait partie d'une discussion plus large en termes de collaboration. Lorsque vous réécrivez l'historique, les anciens et les nouveaux historiques ne sont plus compatibles ; si vous poussez cet historique quelque part pour que d'autres le consultent, il semblera que vous ayez fait un rebase de toutes les branches et étiquettes. Assurez-vous de connaître la section « RECOVERING FROM UPSTREAM REBASE » de git-rebase(1) (et en particulier, « The hard case ») avant de continuer, en plus de cette section.

Les étapes pour utiliser git-filter-repo dans le cadre du processus plus large de réécriture d'historique sont approximativement les suivantes :

1.Créez un clone de votre dépôt. Vous pouvez passer --bare ou --mirror à git clone, si vous le préférez. Vous devriez passer --no-local si le dépôt que vous clonez se trouve sur le système de fichiers local. Évitez les autres drapeaux ; certains pourraient déconcerter la vérification du clone frais, et d'autres pourraient faire en sorte que des parties des données nécessaires à la réécriture soient manquantes.
2.(Facultatif) Exécutez git filter-repo --analyze. Cela créera un répertoire de rapports mentionnant plusieurs choses : (a) les chemins qui ont existé au fil du temps dans votre dépôt, (b) les renommages qui se sont produits dans votre dépôt et (c) les tailles des objets agrégées par chemin/répertoire/extension/blob-id. Ces informations peuvent être utiles pour choisir comment filtrer votre dépôt. Elles peuvent également être utiles pour relancer --analyze après le filtrage afin de vérifier que les changements semblent corrects.
3.Avant de réécrire l'historique de votre copie locale avec git-filter-repo, déterminez où vous pousserez l'historique réécrit lorsque vous aurez terminé. Dans le cas particulier où vous essayez de supprimer des données sensibles d'un dépôt existant, vous voudrez le pousser à l'endroit d'où vous l'avez cloné, ainsi que nettoyer toutes les autres copies/clones du dépôt. Si vous devez pousser vers le dépôt d'où vous avez cloné, vous voudrez utiliser l'option --sensitive-data-removal et consulter la section sur la suppression des données sensibles ci-dessous. Dans la plupart des cas où vous ne traitez pas de la suppression de données sensibles, vous voudrez pousser vers un nouveau dépôt, car :
•Même après avoir réécrit l'historique et l'avoir poussé en arrière, les personnes qui ont précédemment cloné le dépôt original auront l'ancien historique. S'ils exécutent simplement git pull && git push, cela fusionnera l'historique non réécrit avec le nouveau, résultant en ce qui ressemble à deux copies de chaque commit impliqué dans votre réécriture — une nouvelle copie de chaque commit contenant les nettoyages que vous avez effectués, et une ancienne copie de chaque commit qui n'a pas été nettoyée — fusionnées ensemble. Cela signifie que tout ce que vous avez soigneusement travaillé à retirer du dépôt a été repoussé. Vous êtes plus susceptible de réussir à vous assurer qu'ils ne repoussent pas les données non nettoyées si vous leur donnez simplement une nouvelle URL de dépôt et leur demandez de recloner.
•La réécriture de l'historique réécrira les étiquettes ; ceux qui ont déjà téléchargé les étiquettes n'obtiendront pas les étiquettes mises à jour même s'ils spécifient --tags à git fetch ou git pull (voir la section « On Re-tagging » de git-tag(1)). Chaque utilisateur essayant d'utiliser un clone existant devra supprimer de force toutes les étiquettes qu'il a déjà téléchargées avant de les récupérer à nouveau ; il pourrait être plus simple pour eux de simplement recloner, ce qu'ils sont plus susceptibles de faire avec une nouvelle URL de clone.
•La réécriture de l'historique peut supprimer certaines références (par ex. des branches qui ne contenaient que des fichiers que vous vouliez exciser de l'historique) ; sauf si vous exécutez git push avec les options --mirror ou --prune , ces références continueront d'exister sur le serveur. Si les gens fusionnent ensuite ces branches dans d'autres, alors les gens auront commencé à mélanger l'ancien et le nouvel historique. Si les utilisateurs avaient déjà cloné ces branches, les supprimer du serveur ne suffit pas ; vous devez demander à tous les utilisateurs de supprimer les branches locales basées sur ces références et d'exécuter fetch avec l'option --prune également. Recloner simplement à partir d'une nouvelle URL est plus facile.
•Le serveur peut ne pas vous permettre de forcer le push par-dessus certaines références. Par exemple, les systèmes de revue de code peuvent avoir des espaces de noms de références spéciaux (par ex. refs/changes/, refs/pull/, refs/merge-requests/) qu'ils ont verrouillés, et vous devrez d'une manière ou d'une autre empêcher les utilisateurs de fusionner ces historiques verrouillés (et donc non nettoyés) avec votre historique nettoyé. Chaque système de revue de code gère cela différemment (voir la section sur la suppression des données sensibles pour quelques liens).
4.Exécutez filter-repo avec vos options de filtrage souhaitées. De nombreux exemples sont donnés dans la section intitulée « EXAMPLES ». Pour les cas plus complexes, notez que le filtrage en plusieurs étapes (en exécutant plusieurs invocations de filter-repo en séquence) est pris en charge. Si quelque chose se passe mal ici, supprimez simplement votre clone et recommencez.
5.Poussez votre nouveau dépôt vers son nouveau foyer (notez que refs/remotes/origin/* auront été déplacées vers refs/heads/* comme première partie de filter-repo, vous pouvez donc gérer des branches normales au lieu de branches de suivi à distance).
6.(Facultatif) Quelques considérations supplémentaires
•filter-repo a une option --replace-refs pour permettre la création de références de remplacement (voir git-replace(1)) pour chaque ID de commit réécrit, vous permettant d'utiliser les anciens (non abrégés) hachages de commit dans la ligne de commande git pour référencer les commits nouvellement réécrits. Si vous voulez utiliser ces références de remplacement, poussez-les manuellement vers l'URL de clone pertinente et dites aux utilisateurs de les récupérer manuellement (par ex. en ajustant leur refspec de fetch, git config --add remote.origin.fetch +refs/replace/*:refs/replace/*). Malheureusement, les références de remplacement ne sont pas encore largement comprises ; des projets comme jgit et libgit2 ne les supportent pas et les gestionnaires de dépôts existants (par ex. Gerrit, GitHub, GitLab) ne comprennent pas encore les références de remplacement. Ainsi, on ne peut pas utiliser les anciens hachages de commit dans l'interface utilisateur de ces autres systèmes. Cela pourrait changer à l'avenir, mais les références de remplacement aident au moins les utilisateurs localement au sein de l'interface en ligne de commande git. De plus, soyez conscient que les commit-graphs sont excessivement prudents autour des références de remplacement et se désactivent complètement si l'une d'elles est présente, donc après un temps suffisant pour que les anciens IDs de commit deviennent moins pertinents, les utilisateurs pourraient vouloir supprimer localement les références de remplacement pour retrouver les accélérations des commit-graphs.

Pourquoi mon origin est-il supprimé ?

Lorsque vous réécrivez l'historique, tous les IDs de commit (à partir du premier où des changements sont effectués) sont modifiés. Même si vous pensez que vous n'avez pas modifié un commit intermédiaire, le fait que vous en ayez modifié un de ses ancêtres est également un changement qui compte et causera le changement de l'ID d'un commit. Malheureusement, il est beaucoup trop facile pour vous-même ou quelqu'un d'autre de fusionner par erreur le vieil historique laid que vous essayiez de réécrire avec le nouveau historique, résultant non seulement en le retour du vieil historique laid mais aussi en l'obtention de « deux copies » de chaque commit (à la fois un commit original et une alternative nettoyée), et donc en doublant le nombre de commits dans votre dépôt. En bref, vous vous retrouvez avec un désordre encore plus grand à nettoyer que celui avec lequel vous avez commencé.

Cela arrive fréquemment aux personnes utilisant git filter-branch ou BFG repo cleaner, et peut arriver aux personnes utilisant git filter-repo si elles insistent pour pousser vers le dépôt original. Exemples de façons dont vous pouvez obtenir un historique encore plus laid :

•à la ligne de commande (d'un autre clone du même dépôt d'avant le nettoyage) : git pull && git push
•dans une forge logicielle : « rouvrir une ancienne Pull-Request/Merge-Request/Code-Review et appuyer sur le bouton merge/submit »

Supprimer la origin distante et suggérer aux gens de pousser vers un nouveau dépôt (et s'assurer qu'ils disent aux autres de cloner le nouveau dépôt) est généralement une bonne contrainte pour éviter ces problèmes. Mais, si les gens veulent vraiment pousser vers le dépôt original malgré ces avertissements, c'est trivial à faire ; exécutez simplement :

•git remote add origin $ORIGINAL_CLONE_URL

et ensuite vous pouvez pousser (par ex. git push --force --branches --tags --prune). Puisque supprimer l'URL origin est une méthode si peu coûteuse pour potentiellement éviter de grands désordres, et que c'est si facile à contourner pour ceux qui veulent vraiment repousser par-dessus l'historique original, supprimer l'URL origin est une excellente mesure de sécurité que j'emploie.

Un dernier avertissement si vous voulez vraiment repousser vers le dépôt original : consultez la section suivante sur la suppression des données sensibles. Ce sont les étapes nécessaires lors du repoussement vers le dépôt original ; elles sont si complexes que je suppose qu'elles ne valent la peine que lorsque des données sensibles sont impliquées, mais vous pouvez choisir de les suivre pour d'autres types de réécritures aussi.

Suppression des données sensibles

La suppression des données sensibles est un type spécialisé de réécriture d'historique. Bien qu'il soit toujours très problématique de mélanger l'historique nettoyé avec l'historique non nettoyé, pour la suppression de données sensibles il est également mauvais de permettre à d'autres de continuer à consulter/cloner/récupérer l'historique non nettoyé du tout ; les utilisateurs ont souvent besoin d'essayer d'expurger également l'ancien historique.

Notez que si les données sensibles en question sont un jeton/mot de passe/identifiant/secret (comme c'est souvent le cas), il est important que vous révoquiez et rotiez d'abord cet identifiant. Une fois que l'identifiant est révoqué ou fait une rotation, il ne peut plus être utilisé pour l'accès. La révocation/rotation peut résoudre votre problème sans recourir à l'action lourde de réécriture et de purge de l'historique.

Pour les réécritures d'historique de suppression de données sensibles, il y a trois étapes de haut niveau :

•Réécrivez le dépôt localement, en utilisant git-filter-repo
•Assurez-vous que les autres copies sont nettoyées, y compris :
•le serveur d'où vous avez cloné
•les autres clones qui existent, comme ceux que vos collègues ont faits
•Prévenez les répétitions et évitez les futures fuites de données sensibles

Chacun sera discuté plus en détail ci-dessous.

NETTOYAGE DE DONNÉES SENSIBLES

Ceci est un guide sur la façon de supprimer des données sensibles de l'historique de votre dépôt Git. Ceci est très important pour des raisons de sécurité et de conformité.

IMPORTANT : Cette procédure est destructrice et peut entraîner une perte de données si elle n'est pas effectuée correctement. Assurez-vous de comprendre chaque étape avant de continuer. Il est fortement recommandé de travailler sur une copie de votre dépôt.

Avant de commencer

Avant de modifier l'historique de votre dépôt, assurez-vous de comprendre les implications :

•Les modifications apportées à l'historique réécrivent les commits. Cela signifie que tous les commits affectés auront de nouveaux identifiants (SHA).
•Tous les clones du dépôt qui n'ont pas été mis à jour avec le nouvel historique devront être mis à jour manuellement. Ne pas le faire peut entraîner des conflits et des données sensibles réintroduites dans le dépôt.

•Si vous travaillez dans un environnement collaboratif, vous devez coordonner ce processus avec votre équipe. Toute personne ayant un clone du dépôt devra suivre des étapes spécifiques pour nettoyer sa copie.

•Il est fortement recommandé de faire une sauvegarde complète de votre dépôt avant de commencer.

Utilisation de git-filter-repo

L'outil recommandé pour nettoyer l'historique est git-filter-repo. Il est plus rapide et plus sûr que les anciens outils comme BFG ou l'imprimante d'historique Git.

Si vous ne l'avez pas déjà, vous devrez l'installer :

pip install git-filter-repo

Une fois installé, vous pouvez commencer le processus de nettoyage.

Réécrire le dépôt localement, en utilisant git-filter-repo

La première étape consiste à réécrire une copie de votre dépôt localement à l'aide de git-filter-repo. Les commandes exactes à exécuter différeront en fonction de l'endroit où les données sensibles sont trouvées dans votre dépôt, mais voici quelques conseils généraux :

•Utilisez l'indicateur --sensitive-data-removal. Il fournira des informations supplémentaires utiles pour les autres étapes.
•Si les données sensibles constituent l'intégralité d'un ou plusieurs fichiers, et qu'aucune version de ces fichiers de l'historique ne doit être conservée dans votre dépôt, l'indicateur --invert-paths, associé à un ou plusieurs arguments --path, peut être utile.
•Si les données sensibles ne sont qu'une chaîne trouvée dans un ou plusieurs fichiers et que vous souhaitez remplacer cette chaîne sensible par autre chose tout en laissant le reste du ou des fichiers intacts, l'option --replace-text peut être utile.

Après avoir réécrit l'historique localement, assurez-vous de l'inspecter pour vérifier que les données sensibles ont été supprimées. Voici quelques commandes qui peuvent être utiles pour la vérification :

git log --all --name-status -- ${FICHIER_PROBLÉMATIQUE1} ${FICHIER_PROBLÉMATIQUE2}

ou

git log -S"${CHAÎNE_PROBLÉMATIQUE}" --all -p --

Si l'une de ces commandes révèle d'autres données sensibles, exécutez des commandes git-filter-repo supplémentaires pour nettoyer les données nécessaires avant de continuer.

Assurez-vous que les autres copies sont nettoyées : serveur principal

Nettoyer le dépôt à partir duquel vous avez cloné nécessite de forcer le push de votre historique réécrit par-dessus l'original. Vous devez forcer le push de tous les refs, pas seulement de votre branche actuelle. Vous pouvez utiliser la commande suivante pour ce faire (lisez la liste à puces juste après cette commande avant de l'exécuter) :

git push --force --mirror origin

Plusieurs commentaires sur cette commande :

•Si l'un de vos collègues a poussé des changements depuis que vous avez commencé, cette commande de force push supprimera ses changements.
•Il est probable que ce force push échoue à pousser certains refs, car la plupart des forges (Gerrit, GitHub, GitLab, etc.) vous empêchent de mettre à jour certains refs (par exemple, refs/changes/*, refs/pull/*, refs/merge-requests/*). Vous devrez suivre les instructions de ces forges pour mettre à jour ou supprimer les refs restants, et pour déclencher une récupération de place (garbage collection) de leur côté. Quelques exemples : (la documentation de GitLab sur la réduction de la taille du dépôt[1], ou la section « Supprimer complètement les données de GitHub » de la documentation de GitHub[2]).
•Si vous avez passé l'option --no-fetch à git-filter-repo (ou l'avez implicitement utilisée avec une autre option), vous devrez soit (1) abandonner l'option --mirror et déterminer vous-même quels refs ou refspecs pousser, soit (2) utiliser l'option --mirror et risquer de supprimer tous les refs que vous n'avez pas récupérés. De plus, si vous ne disposiez pas de certains refs que le serveur possédait et qui incluaient les données sensibles dans leur historique, vos seules options à ce stade pour nettoyer réellement les données sensibles du serveur sont soit de refaire votre réécriture à partir de zéro (et de vous assurer d'inclure les refs pertinents cette fois-ci), soit de supprimer ces refs sur le serveur.
•Oui, je sais que --mirror implique --force et que ce n'est pas nécessaire. J'ai inclus --force de toute façon comme un rappel visuel aux lecteurs que cela va écraser les changements sur le serveur.

De plus, si des objets LFS ont été orphelins par votre réécriture, ces objets contiennent probablement des données sensibles et doivent être supprimés/purgés du serveur LFS. Vous devrez demander au mainteneur du serveur LFS que vous utilisez comment supprimer/purger ces objets sur le serveur.

Assurez-vous que les autres copies sont nettoyées : clones des collègues

Une fois que vous avez nettoyé le serveur, le moyen le plus simple de nettoyer les autres clones est de faire en sorte que tout le monde supprime ses clones existants et en reclone.

Si ce n'est pas une option, vous devrez procéder avec prudence car un simple git pull && git push depuis un autre clone recontaminera le dépôt principal et rendra le désordre encore plus difficile à nettoyer. Pour éviter cela, avant de pousser depuis un autre clone, vous devrez leur faire nettoyer leur copie, comme détaillé ci-dessous.

Avant cela, je tiens à noter que vous ne devriez pas demander à d'autres développeurs d'essayer de nettoyer leur clone en exécutant les mêmes commandes git-filter-repo que vous avez exécutées. Bien que cela puisse parfois fonctionner, ce n'est généralement pas fiable. L'exécution des mêmes commandes git-filter-repo, même si elles sont identiques, peut entraîner l'obtention de nouveaux identifiants de commits différents de vos nouveaux identifiants, et vous vous retrouverez avec un désordre impliquant deux copies ou plus de chaque commit.

Au lieu de cela, les développeurs ayant d'autres clones du dépôt devraient suivre les étapes suivantes pour nettoyer leur copie s'ils ne veulent pas abandonner leur copie et en recloner :

•Supprimez toutes les étiquettes et exécutez git fetch --prune --tags. L'exécution de la commande fetch sans supprimer les étiquettes au préalable entraînera la conservation des anciennes étiquettes, ce qui maintiendra les données sensibles.
•Réintégrez tous les changements qu'ils ont sur n'importe quelle branche (ou autre ref) par-dessus le nouvel historique. Voir la section « RÉCUPÉRATION APRÈS UN REBASE EN AMONT » de git-rebase(1) (et en particulier, « Le cas difficile ») pour les instructions.
•Exécutez quelques étapes pour nettoyer l'historique avant le rebase (notez que la première étape supprime tous les reflogs, y compris toutes les entrées stash. C'est un coût élevé, mais nécessaire pour nettoyer les données sensibles) :
•git reflog expire --expire=now --all
•git gc --prune=now

Une fois ces étapes terminées, vous devez également vérifier que le clone ne contient plus de données sensibles (il est très facile de manquer quelque chose, ce qui vous expose au risque de recontaminer d'autres dépôts avec les données sensibles). Vous pouvez le faire en exécutant :

git cat-file -t ${HASH_DU_PREMIER_COMMIT_MODIFIÉ}

Où ${HASH_DU_PREMIER_COMMIT_MODIFIÉ} a été imprimé par git-filter-repo à la fin de son exécution (s'il y avait plus d'un « premier commit modifié », exécutez cette commande plusieurs fois, avec chaque hachage de commit). Si cette commande renvoie une erreur fatale, le commit a été correctement supprimé de ce dépôt. Si elle répond par « commit », l'objet existe toujours et vous devez redéfinir les étiquettes, rebaser toutes les branches/refs nécessaires, et refaire expirer les reflogs et refaire le gc. Si vous vous demandez quelles branches ou quels refs étaient problématiques et retenaient ${HASH_DU_PREMIER_COMMIT_MODIFIÉ}, alors en supposant que vous ayez effectué les tâches d'expiration des reflogs et de gc ci-dessus, la commande suivante devrait vous aider à trouver les branches/refs problématiques :

git for-each-ref --contains ${HASH_DU_PREMIER_COMMIT_MODIFIÉ}

De plus, rappelez-vous que la commande cat-file doit renvoyer une erreur fatale pour chaque ${HASH_DU_PREMIER_COMMIT_MODIFIÉ} impliqué s'il y en a plus d'un.

Une fois tout cela terminé, si des objets LFS ont été orphelins par la réécriture (ce dont vous serez informé si vous utilisez l'option --sensitive-data-removal lorsque vous exécutez git-filter-repo), vous devrez également supprimer ces objets LFS. Recherchez-les dans quelques répertoires sous .git/lfs/objects/, et supprimez-les.

Prévenir les répétitions et éviter les futures fuites de données sensibles

Plusieurs mesures peuvent être prises pour aider à éviter les problèmes répétés. Toutes ne peuvent pas s'appliquer à votre cas, mais plus il y en a, plus vous avez de chances d'éviter les problèmes.

Pour traiter la fuite de données sensibles existante :

•Comme il est très facile de recontaminer le dépôt à partir duquel vous avez cloné (il suffit qu'un collègue exécute git pull && git push depuis son clone créé avant votre nettoyage), soyez particulièrement vigilant dans l'exécution des étapes de nettoyage ci-dessus pour les autres clones afin de vous assurer qu'ils ont tous été nettoyés.
•Si vous avez un dépôt central vers lequel tout le monde pousse, recherchez des méthodes pour interdire que le ou les premiers commits modifiés soient (re)poussés vers votre dépôt. Malheureusement, peu de gestionnaires de dépôts disposent actuellement d'une telle capacité intégrée (voir la capacité ban-commit de Gerrit pour un tel exemple sur https://gerrit-review.googlesource.com/Documentation/cmd-ban-commit.html), mais certains peuvent vous permettre d'écrire vos propres hooks pre-receive qui rejettent les pushes contenant ces mauvais commits. (Astuce pro pour écrire un tel hook pre-receive : utilisez git cat-file -t ${MAUVAIS_COMMIT} comme vérification rapide avant de vérifier si une plage de révision entre <old-oid> et <new-oid> contient ${MAUVAIS_COMMIT})

Étapes pour aider à éviter d'autres fuites de données sensibles futures :

•Si des données sensibles sont susceptibles d'apparaître dans certains noms de fichiers qui ne devraient pas du tout être suivis dans git, ajoutez ces noms de fichiers à .gitignore pour réduire le risque que d'autres les ajoutent accidentellement.
•Évitez d'encoder en dur des secrets dans le code. Utilisez des variables d'environnement, des outils de gestion de configuration, ou des services de gestion de secrets comme Azure Key Vault, AWS Secrets Manager, ou HashiCorp Vault pour gérer et injecter des secrets à l'exécution.
•Créez un hook pre-commit pour rechercher les données sensibles avant qu'elles ne soient commitées ou poussées quelque part, ou utilisez un outil bien connu dans un hook pre-commit comme git-secrets ou gitleaks.

EXEMPLES

Filtrage basé sur les chemins

Pour ne conserver que le fichier README.md ainsi que les répertoires guides et tools/releases/ :

git filter-repo --path README.md --path guides/ --path tools/releases

Les noms de répertoires peuvent être donnés avec ou sans slash final, et tous les noms de fichiers sont relatifs au niveau supérieur du dépôt. Pour conserver tous les fichiers sauf ces chemins, ajoutez simplement --invert-paths :

git filter-repo --path README.md --path guides/ --path tools/releases --invert-paths

Si vous souhaitez avoir à la fois un filtre d'inclusion et un filtre d'exclusion, exécutez simplement filter-repo plusieurs fois. Par exemple, pour conserver le sous-répertoire src/main mais exclure les fichiers sous src/main nommés data, exécutez :

git filter-repo --path src/main/
git filter-repo --path-glob 'src/*/data' --invert-paths

Notez que l'astérisque (*) correspondra à plusieurs répertoires, donc

Filtrage basé sur les chemins

La deuxième commande supprimerait par exemple src/main/org/whatever/data. De plus, la deuxième commande seule supprimerait également par exemple src/not-main/foo/data, mais comme src/not-main/ a été supprimé par la première commande, ce n'est pas un problème. De plus, l'utilisation de guillemets autour de l'astérisque est parfois importante pour éviter l'expansion des jokers par le shell.

Vous pouvez également sélectionner des chemins par expression régulière (voir https://docs.python.org/3/library/re.html#regular-expression-syntax). Par exemple, pour inclure uniquement les fichiers du dépôt dont le nom est au format AAAA-MM-JJ.txt et qui se trouvent à au moins deux sous-répertoires de profondeur :

git filter-repo --path-regex '^.*/.*/[0-9]{4}-[0-9]{2}-[0-9]{2}.txt$'

Si vous souhaitez renommer deux répertoires (et éventuellement les fusionner s'ils sont tous deux renommés au même emplacement), utilisez --path-rename ; par exemple, pour renommer à la fois cmds/ et src/scripts/ en tools/ :

git filter-repo --path-rename cmds:tools --path-rename src/scripts/:tools/

Comme avec --path, les répertoires peuvent être spécifiés avec ou sans barre oblique finale pour --path-rename.

Si vous effectuez un --path-rename vers quelque chose qui était déjà utilisé, il sera silencieusement écrasé. Cependant, si vous essayez de renommer plusieurs fichiers vers le même emplacement (par exemple, src/scripts/run_release.sh et cmds/run_release.sh existaient tous deux et avaient un contenu différent avec les renommages ci-dessus), une erreur vous sera signalée. Si vous avez un tel cas, vous pourriez vouloir ajouter une autre commande de renommage pour déplacer l'un des chemins ailleurs où il n'y aura pas de collision :

git filter-repo --path-rename cmds/run_release.sh:tools/do_release.sh \
                --path-rename cmds/:tools/ \
                --path-rename src/scripts/:tools/

De plus, --path-rename soulève des problèmes d'ordre ; tous les arguments de chemin sont appliqués dans l'ordre. Ainsi, une commande comme

git filter-repo --path-rename sources/:src/main/ --path src/main/

aurait du sens, mais inverser les deux arguments n'en aurait pas (src/main/ est créé par le renommage, donc inverser les deux vous donnerait un dépôt vide). Notez également que le renommage de cmds/run_release.sh dans les exemples précédents a été effectué avant les autres renommages.

Notez que le renommage de chemins ne fait pas de filtrage de chemins, donc la commande suivante

git filter-repo --path src/main/ --path-rename tools/:scripts/

ne résulterait pas en la présence des répertoires tools ou scripts, car le seul filtre sélectionnait uniquement src/main/. Il est probable que vous préféreriez exécuter :

git filter-repo --path src/main/ --path tools/ --path-rename tools/:scripts/

Si vous préférez filtrer uniquement sur le nom de base, utilisez l'indicateur --use-base-name (bien que cela soit incompatible avec --path-rename). Par exemple, pour inclure uniquement les fichiers README.md et Makefile de n'importe quel répertoire :

git filter-repo --use-base-name --path README.md --path Makefile

Si vous vouliez supprimer tous les fichiers .DS_Store dans n'importe quel répertoire, vous pourriez soit utiliser :

git filter-repo --invert-paths --path '.DS_Store' --use-base-name

ou

git filter-repo --invert-paths --path-glob '*/.DS_Store' --path '.DS_Store'

(le --path-glob n'est pas suffisant en soi car il pourrait manquer un fichier .DS_Store de premier niveau ; de plus, alors que quelque chose comme --path-glob '*.DS_Store' contournerait ce problème, il sélectionnerait également des fichiers nommés foo.DS_Store ou bar/baz.DS_Store)

Enfin, voir également le --filename-callback dans la section intitulée « CALLBACKS ».

Filtrage basé sur plusieurs chemins

Si vous avez une longue liste de fichiers, de répertoires, de jokers ou d'expressions régulières à filtrer, vous pouvez les placer dans un fichier et utiliser --paths-from-file ; par exemple, avec un fichier nommé stuff-i-want.txt contenant :

# Les lignes vides et les lignes de commentaires sont ignorées.
# Exemples similaires à --path :
README.md
guides/
tools/releases
# Un exemple qui ressemble à --path-glob :
glob:*.py
# Un exemple qui ressemble à --path-regex :
regex:^.*/.*/[0-9]{4}-[0-9]{2}-[0-9]{2}.txt$
# Un exemple de renommage d'un chemin
tools/==>scripts/
# Un exemple d'utilisation d'une regex pour renommer un chemin
regex:(.*)/([^/]*)/([^/]*)\.text$==>\2/\1/\3.txt

alors vous pourriez exécuter

git filter-repo --paths-from-file stuff-i-want.txt

pour obtenir un dépôt contenant uniquement le fichier README.md de premier niveau, les répertoires guides/ et tools/releases/, tous les fichiers python, les fichiers dont le nom était au format AAAA-MM-JJ.txt à au moins deux sous-répertoires de profondeur, et qui renommerait tools/ en scripts/ et renommerait des fichiers comme foo/bar/baz.text en bar/foo/baz.txt. Notez les préfixes de ligne spéciaux glob: et regex: et la chaîne spéciale ==> indiquant les renommages.

Parfois, vous disposez d'un moyen de générer facilement tous les fichiers que vous souhaitez. Par exemple, si vous savez qu'aucun des fichiers actuellement suivis ne contient de nouvelles lignes ou de caractères spéciaux (voir core.quotePath de git config --help) de sorte que git ls-files afficherait tous les fichiers littéralement un par ligne, et que vous saviez que vous ne vouliez conserver que les fichiers actuellement suivis (supprimant ainsi de l'historique de toutes les commits les fichiers qui n'apparaissent que sur d'autres branches ou qui n'apparaissent que dans des commits plus anciens), vous pourriez utiliser une paire de commandes comme

git ls-files >../paths-i-want.txt
git filter-repo --paths-from-file ../paths-i-want.txt

De même, vous pourriez utiliser --paths-from-file pour supprimer de nombreux fichiers. Par exemple, vous pourriez exécuter git filter-repo --analyze pour obtenir des rapports, regarder dans l'un d'eux comme .git/filter-repo/analysis/path-deleted-sizes.txt et copier tous les noms de fichiers dans un fichier comme /tmp/files-i-dont-want-anymore.txt, puis exécuter

git filter-repo --invert-paths --paths-from-file /tmp/files-i-dont-want-anymore.txt

pour les supprimer tous.

Raccourcis basés sur les répertoires

Supposons que vous ayez une structure de répertoire comme la suivante :

module/
   foo.c
   bar.c
otherDir/
   blah.config
   stuff.txt
zebra.jpg

Si vous ne vouliez que le répertoire module/ et que vous vouliez qu'il devienne la nouvelle racine afin que votre nouvelle structure de répertoire ressemble à

foo.c
bar.c

alors vous pourriez exécuter :

git filter-repo --subdirectory-filter module/

Si vous vouliez tous les fichiers du dépôt d'origine, mais que vous vouliez déplacer tout sous un sous-répertoire nommé my-module/, de sorte que votre nouvelle structure de répertoire ressemble à

my-module/
   module/
      foo.c
      bar.c
   otherDir/
      blah.config
      stuff.txt
   zebra.jpg

alors vous exécuteriez plutôt

git filter-repo --to-subdirectory-filter my-module/

Filtrage basé sur le contenu

Si vous souhaitez filtrer tous les fichiers plus volumineux qu'une certaine taille, vous pouvez utiliser --strip-blobs-bigger-than avec une taille (les suffixes K, M et G sont reconnus), par exemple :

git filter-repo --strip-blobs-bigger-than 10M

Si vous souhaitez supprimer tous les fichiers avec des identifiants d'objet git (hachages) spécifiés, listez les hachages dans un fichier et exécutez

git filter-repo --strip-blobs-with-ids FICHIER_AVEC_IDS_DE_BLOBS_GIT

Si vous souhaitez modifier le contenu des fichiers, vous pouvez le faire sur la base d'une liste d'expressions dans un fichier, une par ligne. Par exemple, avec un fichier nommé expressions.txt contenant

p455w0rd
foo==>bar
glob:*666*==>
regex:\bdriver\b==>pilot
literal:MM/DD/YYYY==>YYYY-MM-DD
regex:([0-9]{2})/([0-9]{2})/([0-9]{4})==>\3-\1-\2

alors l'exécution

git filter-repo --replace-text expressions.txt

parcourra et remplacera p455w0rd par ***SUPPRIMÉ***, foo par bar, toute ligne contenant 666 par une ligne vide, le mot driver par pilot (mais pas s'il y a des lettres avant ou après ; par exemple, drivers ne sera pas modifié), remplacera le texte exact MM/DD/YYYY par YYYY-MM-DD et remplacera les chaînes de date du format MM/DD/YYYY par celles du format YYYY-MM-DD. Dans le fichier d'expressions, il y a quelques points à noter :

•Chaque ligne a un remplacement, donné par ce qui se trouve à droite de ==>. Si ==> n'apparaît pas sur la ligne, le remplacement par défaut est ***SUPPRIMÉ***.
•Les lignes peuvent commencer par literal:, glob: ou regex: pour spécifier s'il faut effectuer des correspondances de chaînes littérales, des jokers (voir https://docs.python.org/3/library/fnmatch.html) ou des expressions régulières (voir https://docs.python.org/3/library/re.html#regular-expression-syntax). Si aucun de ceux-ci n'est spécifié, literal: est supposé.
•Si plusieurs correspondances sont trouvées, toutes sont remplacées.
•Les jokers et les regex sont appliqués à l'ensemble du fichier, mais sans aucun drapeau spécial activé. Certains pourraient être intéressés par l'ajout de (?m) à la regex pour activer le mode MULTILIGNE, de sorte que ^ et $ correspondent aux débuts et fins de lignes plutôt qu'aux débuts et fins de fichier. Voir https://docs.python.org/3/library/re.html pour plus de détails.

Voir également le --blob-callback dans la section intitulée « CALLBACKS ».

Mise à jour des messages de commit/tag

Si vous souhaitez modifier les messages de commit ou de tag, vous pouvez le faire avec la même syntaxe que --replace-text, expliquée ci-dessus. Par exemple, avec un fichier nommé expressions.txt contenant

foo==>bar

alors l'exécution

git filter-repo --replace-message expressions.txt

remplacera foo dans les messages de commit ou de tag par bar.

Voir également le --message-callback dans la section intitulée « CALLBACKS ».

Pour renommer les balises, utilisez --tag-rename, par exemple :

git filter-repo --tag-rename foo:bar

Cela renommera toutes les balises commençant par foo pour qu'elles commencent maintenant par bar. L'un ou l'autre côté des deux-points pourrait être vide, par exemple :

Filtrage basé sur l'utilisateur et l'e-mail

Pour modifier le nom d'utilisateur et les e-mails des commits, vous pouvez créer un fichier mailmap dans le format accepté par git-shortlog(1). Par exemple, si vous avez un fichier nommé mon-mailmap, vous pouvez exécuter :

git filter-repo --mailmap mon-mailmap

et si le contenu actuel de ce fichier est le suivant (si le fichier mailmap spécifié est versionné, les versions historiques du fichier sont ignorées) :

Nom Pour Utilisateur <email@addre.ss>
<nouveau@ema.il> <ancien1@ema.il>
Nouveau Nom Et <nouveau@ema.il> <ancien2@ema.il>
Nouveau Nom Et <nouveau@ema.il> Ancien Nom Et <ancien3@ema.il>

nous pouvons mettre à jour le nom d'utilisateur et/ou les e-mails en fonction du mappage spécifié.

Voir aussi --name-callback et --email-callback dans la section « CALLBACKS ».

Réécriture des parents

Pour remplacer $commit_A par $commit_B (par exemple, faire en sorte que tous les commits qui avaient $commit_A comme parent aient maintenant $commit_B pour ce parent), et réécrire l'historique pour le rendre permanent :

git replace $commit_A $commit_B
git filter-repo --proceed

Pour créer un nouveau commit avec le même contenu que $commit_A, sauf avec des parents différents, puis remplacer $commit_A par le nouveau commit et réécrire l'historique pour le rendre permanent :

git replace --graft $commit_A $nouveau_parent_ou_parents
git filter-repo --proceed

L'option --proceed est nécessaire pour éviter de déclencher la vérification « aucun argument spécifié ». Notez que les anciennes versions de git-filter-repo nécessitaient de passer --force après la création d'un greffon pour éviter de déclencher la vérification « pas un clone frais » ; cette vérification a été modifiée pour supprimer cette utilisation excessive de --force.

Réécritures partielles de l'historique

Pour réécrire l'historique sur une seule branche (ce qui peut entraîner une absence d'historique commun avec d'autres branches), utilisez --refs. Par exemple, pour supprimer un fichier nommé extraneous.txt de la branche master :

git filter-repo --invert-paths --path extraneous.txt --refs master

Pour réécrire seulement quelques commits récents :

git filter-repo --invert-paths --path extraneous.txt --refs master~3..master

CALLBACKS

Pour plus de flexibilité, filter-repo vous permet de spécifier des fonctions en ligne de commande pour filtrer davantage toutes les modifications. Veuillez noter qu'il existe quelques mises en garde concernant la compatibilité de l'API pour ces fonctions de rappel dont vous devriez être conscient avant de les utiliser ; voir le commentaire « API BACKWARD COMPATIBILITY CAVEAT » près du début du code source de git-filter-repo.

La plupart des fonctions de rappel ont le même format général (l'exception est --file-info-callback qui sera notée plus tard). Pour un argument de ligne de commande comme

--foo-callback 'CORPS'

le code suivant sera compilé et appelé :

def foo_callback(foo):
  CORPS

Ainsi, il vous suffit de vous assurer que votre CORPS modifie et renvoie foo de manière appropriée. Une chose importante à noter pour tous les rappels est que filter-repo utilise des séquences d'octets (voir https://docs.python.org/3/library/stdtypes.html#bytes) partout au lieu de chaînes de caractères.

Il existe quatre rappels qui vous permettent d'opérer directement sur des objets bruts contenant des données faciles à écrire au format git-fast-import(1) :

--blob-callback
--commit-callback
--tag-callback
--reset-callback

Nous reviendrons sur ceux-ci plus tard car il est souvent préférable d'utiliser les autres rappels. Les autres rappels opèrent sur une petite partie des objets bruts ou sur des pièces de plusieurs types d'objets bruts (par exemple, noms d'auteur et noms de committer et noms de tagger à travers les commits et les tags, ou noms de références à travers les commits, tags et resets, ou messages à travers les commits et les tags). Les rappels de commodité sont :

--filename-callback
--message-callback
--name-callback
--email-callback
--refname-callback
--file-info-callback

Dans chacun, vous êtes censé simplement renvoyer une nouvelle valeur basée sur celle qui est passée. Par exemple,

git-filter-repo --name-callback 'return name.replace(b"Wiliam", b"William")'

entraînerait l'appel de la fonction suivante :

def name_callback(name):
  return name.replace(b"Wiliam", b"William")

Le rappel d'e-mail est très similaire :

git-filter-repo --email-callback 'return email.replace(b".cm", b".com")'

Le rappel de nom de référence est également similaire, mais notez que le nom de référence passé et retourné sont censés être entièrement qualifiés (par exemple, b« refs/heads/master » au lieu de simplement b« master » et b« refs/tags/v1.0.7 » au lieu de b« 1.0.7 ») :

git-filter-repo --refname-callback '
  # Changer par exemple refs/heads/master en refs/heads/prefix-master
  rdir,rpath = os.path.split(refname)
  return rdir + b"/prefix-" + rpath'

Le rappel de message est très similaire aux trois rappels précédents, bien qu'il opère sur une séquence d'octets qui est probablement plus longue qu'une seule ligne :

git filter-repo --message-callback '
  if b"Signed-off-by:" not in message:
    message += b"\nSigned-off-by: Moi Moi <moi@moi.moi>"
  return re.sub(b"[Ee]-?[Mm][Aa][Ii][Ll]", b"email", message)'

Le rappel de nom de fichier est un peu plus intéressant. Renvoyer None signifie que le fichier doit être supprimé de tous les commits, renvoyer le nom de fichier inchangé marque le fichier pour être conservé, et renvoyer un nom différent signifie que le fichier doit être renommé. Un exemple :

git filter-repo --filename-callback '
  if b"/src/" in filename:
    # Supprimer tous les fichiers avec un répertoire nommé "src" dans leur chemin
    # (sauf lorsque "src" apparaît au niveau supérieur).
    return None
  elif filename.startswith(b"tools/"):
    # Renommer tools/ -> scripts/misc/
    return b"scripts/misc/" + filename[6:]
  else:
    # Conserver le nom de fichier et ne pas le renommer
    return filename
  '

Le rappel d'informations sur les fichiers est plus complexe. Il est conçu pour être utilisé dans les cas où le filtrage dépend du nom de fichier et du contenu (et peut-être du mode). Il est appelé pour les modifications de fichiers autres que les suppressions (car les suppressions n'ont pas de contenu de fichier sur lequel opérer). Le rappel d'informations sur les fichiers prend quatre paramètres (nom de fichier, mode, id_blob, et valeur), et s'attend à en renvoyer trois (nom de fichier, mode, id_blob). Le nom de fichier est géré de manière similaire au rappel de nom de fichier ; il peut être utilisé pour renommer le fichier (ou défini sur None pour abandonner la modification). Le mode est une simple séquence d'octets (b« 100644 » pour les fichiers réguliers non exécutables, b« 100755 » pour les fichiers exécutables/scripts, b« 120000 » pour les liens symboliques, et b« 160000 » pour les sous-modules). L'id_blob est surtout utile en conjonction avec le paramètre value. Le paramètre value est une instance d'une classe qui possède les fonctions suivantes : value.get_contents_by_identifier(blob_id) → contents (séquence d'octets) value.get_size_by_identifier(blob_id) → taille_du_blob (int) value.insert_file_with_contents(contents) → blob_id value.is_binary(contents) → bool value.apply_replace_text(contents) → new_contents (séquence d'octets) et possède les données membres suivantes sur lesquelles vous pouvez écrire : value.data (dict). Ces fonctions vous permettent d'obtenir le contenu du fichier, ou sa taille, de créer un nouveau fichier dans le flux dont vous pouvez renvoyer l'id_blob, de vérifier si un contenu donné est binaire (en utilisant l'heuristique de la commande grep(1)), et d'appliquer les règles de remplacement de --replace-text (notez que --file-info-callback fait que les changements de --replace-text ne s'appliquent pas automatiquement). Vous pourriez l'utiliser par exemple pour appliquer les changements de --replace-text uniquement à certains types de fichiers et simultanément renommer les fichiers auxquels les changements s'appliquent :

git filter-repo --file-info-callback '
  if not filename.endswith(b".config"):
    # Ne faire aucune modification au fichier ; renvoyer tel quel
    return (filename, mode, blob_id)
  new_filename = filename[0:-7] + b".cfg"
  contents = value.get_contents_by_identifier(blob_id)
  new_contents = value.apply_replace_text(contents)
  new_blob_id = value.insert_file_with_contents(new_contents)
  return (new_filename, mode, new_blob_id)

Notez que si l'historique contient plusieurs révisions du même fichier (par exemple, s'il a été cherry-pické sur plusieurs branches ou s'il y a eu plusieurs annulations), --file-info-callback sera appelé plusieurs fois. Si vous souhaitez éviter de traiter le même fichier plusieurs fois, vous pouvez stocker les résultats de transformation dans le dictionnaire value.data. Par exemple, nous pourrions modifier l'exemple ci-dessus pour qu'il n'applique les transformations qu'aux ids_blob que nous n'avons pas encore vus :

git filter-repo --file-info-callback '
  if not filename.endswith(b".config"):
    # Ne faire aucune modification au fichier ; renvoyer tel quel
    return (filename, mode, blob_id)
  new_filename = filename[0:-7] + b".cfg"
  if blob_id in value.data:
    return (new_filename, mode, value.data[blob_id])
  contents = value.get_contents_by_identifier(blob_id)
  new_contents = value.apply_replace_text(contents)
  new_blob_id = value.insert_file_with_contents(new_contents)
  value.data[blob_id] = new_blob_id
  return (new_filename, mode, new_blob_id)

Un exemple alternatif pour --file-info-callback est de rendre tous les fichiers .sh exécutables et d'ajouter une ligne de fin supplémentaire aux fichiers .sh :

git filter-repo --file-info-callback '
  if not filename.endswith(b".sh"):
    # Ne faire aucune modification au fichier ; renvoyer tel quel
    return (filename, mode, blob_id)
  # Il n'y a que 4 modes valides
in git: # - 100644, pour les fichiers réguliers non exécutables # - 100755, pour les fichiers/scripts exécutables # - 120000, pour les liens symboliques # - 160000, pour les sous-modules new_mode = b"100755" contents = value.get_contents_by_identifier(blob_id) new_contents = contents + b"\n" new_blob_id = value.insert_file_with_contents(new_contents) return (filename, new_mode, new_blob_id)

Contrairement aux types de rappel précédents, les rappels blob, reset, tag et commit ne sont pas censés renvoyer une valeur, mais sont plutôt censés modifier l'objet qui leur est passé. Les champs principaux pour ces objets sont (sous réserve des réserves de compatibilité ascendante de l'API mentionnées précédemment) :

•Blob : original_id (hash d'origine) et data
•Reset : ref (nom de la référence) et from_ref (hash ou marque entière)
•Tag : ref, from_ref, original_id, tagger_name, tagger_email, tagger_date, message
•Commit : branch, original_id, author_name, author_email, author_date, committer_name, committer_email, committer_date, message, file_changes (liste d'objets FileChange, chacun contenant un type, filename, mode, et blob_id), parents (liste de hashes ou de marques entières)

Un exemple de chacun :

git filter-repo --blob-callback '
  if len(blob.data) > 25:
    # Marquer ce blob pour suppression de tous les commits
    blob.skip()
  else:
    blob.data = blob.data.replace(b"Hello", b"Goodbye")
  '
git filter-repo --reset-callback 'reset.ref = reset.ref.replace(b"master", b"dev")'
git filter-repo --tag-callback '
  if tag.tagger_name == b"Jim Williams":
    # Omettre cette étiquette
    tag.skip()
  else:
    tag.message = tag.message + b"\n\nTag of %s by %s on %s" % (tag.ref, tag.tagger_email, tag.tagger_date)'
git filter-repo --commit-callback '
  # Supprimer les fichiers exécutables ayant trois 6 dans leur nom (y compris
  # depuis les répertoires de premier niveau).
  # Aussi, annuler la suppression de sources/foo/bar.txt (les types de changement sont
  # soit b"D" (suppression) soit b"M" (ajout ou modification) ; les renommages sont
  # gérés en supprimant l'ancien fichier et en ajoutant un nouveau)
  commit.file_changes = [
         change for change in commit.file_changes
         if not (change.mode == b"100755" and
                 change.filename.count(b"6") == 3) and
            not (change.type == b"D" and
                 change.filename == b"sources/foo/bar.txt")]
  # Marquer tous les fichiers .sh comme exécutables ; les modes dans git sont toujours l'un de
  # 100644 (fichier normal), 100755 (exécutable), 120000 (lien symbolique), ou
  # 160000 (sous-module)
  for change in commit.file_changes:
    if change.filename.endswith(b".sh"):
      change.mode = b"100755"
  '

DÉTAILS INTERNES

Vous n'avez probablement pas besoin de lire cette section à moins que vous ne soyez simplement très curieux ou que vous essayez de faire une réécriture d'historique très complexe.

Comment filter-repo fonctionne

Grossièrement, filter-repo fonctionne en exécutant

git fast-export <options> | filter | git fast-import <options>

où filter-repo non seulement lance l'ensemble du pipeline mais sert aussi de filter au milieu. Cependant, filter-repo fait quelques actions supplémentaires afin d'en faire un outil de filtrage complet. Une séquence qui reflète plus précisément ce que filter-repo exécute est :

1.Vérifier que nous sommes dans une copie fraîche
2.git fetch -u . refs/remotes/origin/*:refs/heads/*
3.git remote rm origin
4.git fast-export --show-original-ids --reference-excluded-parents --fake-missing-tagger --signed-tags=strip --tag-of-filtered-object=rewrite --use-done-feature --no-data --reencode=yes --mark-tags --all | filter | git -c core.ignorecase=false fast-import --date-format=raw-permissive --force --quiet
5.git update-ref --no-deref --stdin, alimenté avec une liste de références à détruire, et une liste de références de remplacement à supprimer, créer ou mettre à jour.
6.git reset --hard
7.git reflog expire --expire=now --all
8.git gc --prune=now

Quelques notes ou exceptions sur chacune des étapes ci-dessus :

1.Si nous ne sommes pas dans une copie fraîche, les utilisateurs ne pourront pas se remettre de la situation s'ils ont utilisé la mauvaise commande ou ont exécuté dans le mauvais dépôt. (Bien que --force permette de contourner cette vérification, et qu'elle est également désactivée si vous avez déjà exécuté filter-repo une fois dans ce dépôt.)
2.T techniquement, nous utilisons en fait une commande git update-ref alimentée avec beaucoup d'entrée en raison du fait que les utilisateurs peuvent utiliser --force lorsque les branches locales peuvent ne pas correspondre aux branches distantes. Mais cette commande fetch saisit l'intention de manière succincte.
3.Nous ne voulons pas que les utilisateurs poussent accidentellement vers le dépôt original, comme discuté dans la section appelée « DISCUSSION ». Cela rappelle également aux utilisateurs que puisque l'historique a été réécrit, ce dépôt n'est plus compatible avec l'original. Enfin, un autre petit avantage est que cela permet aux utilisateurs de pousser avec l'option --mirror vers leur nouveau dépôt sans envoyer accidentellement les branches de suivi distant.
4.Certains de ces drapeaux sont toujours utilisés mais d'autres sont en fait conditionnels. Par exemple, les options --replace-text et --blob-callback de filter-repo doivent travailler sur les blobs donc --no-data ne peut pas être passé à fast-export. Mais quand nous n'avons pas besoin de travailler sur les blobs, passer --no-data accélère les choses. De plus, d'autres drapeaux peuvent changer la structure du pipeline également (par ex. --dry-run et --debug)
5.Nous utilisons cette étape pour écrire des références de remplacement permettant d'accéder aux nouveaux hashes de commit écrits en utilisant leurs anciens noms. Aussi, si des références ont été renommées par diverses étapes, nous devons supprimer les anciens noms de référence afin d'éviter de mélanger l'ancien et le nouvel historique.
6.Les utilisateurs ont aussi d'anciennes versions de fichiers dans leur arbre de travail et leur index ; nous voulons que ceux-ci soient nettoyés pour correspondre à l'historique réécrit également. Notez que cette étape est ignorée dans les dépôts nus.
7.Les reflogs conserveront l'ancien historique, donc nous devons les faire expirer.
8.Nous devons faire un gc pour éviter de mélanger le nouvel et l'ancien historique. De plus, cela réduit la taille du dépôt pour les utilisateurs, afin qu'ils n'aient pas à faire de travail supplémentaire. (Il est probable qu'ils n'aient réécrit que des arbres et des commits et peut-être quelques blobs, donc --aggressive n'est pas nécessaire et serait trop lent.)

Des informations sur ces étapes sont imprimées lorsque --debug est passé à filter-repo. Lors d'une --partial réécriture d'historique, les étapes 2, 3, 7 et 8 sont inconditionnellement ignorées, l'étape 5 est ignorée si --replace-refs est update-no-add, et seule la partie nuke-unused-refs de l'étape 5 est ignorée si --replace-refs est autre chose.

Limitations

Limitations héritées

Puisque git filter-repo appelle fast-export et fast-import pour faire une grande partie du travail difficile, il hérite des limitations de ces systèmes :

•les en-têtes de commit étendus, s'il y en a, sont supprimés
•les commits sont réécrits ce qui signifie qu'ils auront de nouveaux hashes ; par conséquent, les signatures sur les commits et les étiquettes ne peuvent pas continuer à fonctionner et sont simplement supprimées (ainsi les étiquettes signées deviennent des étiquettes annotées)
•les étiquettes de commits sont supportées. Avant git-2.24.0, les étiquettes de blobs et les étiquettes d'étiquettes ne sont pas supportées (fast-export planterait sur de telles étiquettes). Les étiquettes d'arbres ne sont supportées dans aucune version de git (puisque fast-export ignore les étiquettes d'arbres avec un avertissement et fast-import ne fournit aucun moyen de les importer).
•les étiquettes annotées et signées en dehors du namespace refs/tags/ ne sont pas supportées (leur emplacement sera altéré de manière étrange)
•fast-import plantera sur diverses formes d'entrée invalide, comme un fuseau horaire avec plus de quatre chiffres
•fast-export ne peut pas réencoder les messages de commit en UTF-8 si le message de commit n'est pas valide dans son encodage spécifié (dans de tels cas, il laissera le message de commit et l'en-tête d'encodage tranquilles).
•les commits sans auteur recevront un auteur correspondant au committer
•les étiquettes sans tagger recevront un tagger fictif
•les références qui incluent des cycles de commits dans leur historique (qui peuvent être créés avec git-replace(1)) ne seront pas signalées à l'utilisateur comme une erreur mais seront silencieusement supprimées par fast-export comme si la branche ou l'étiquette ne contenait aucun fichier intéressant

Il y a aussi quelques limitations dues à la conception de ces systèmes :

•Essayer d'insérer des fichiers supplémentaires dans le flux peut être délicat ; puisque fast-export ne liste les changements de fichiers dans une fusion que par rapport à son premier parent, si vous insérez des fichiers supplémentaires dans un commit qui est dans l'historique du deuxième (ou troisième ou quatrième) parent d'une fusion, alors vous devez aussi l'ajouter à la fusion manuellement. (De même, si vous changez quel parent est le premier parent dans un commit de fusion, vous devez mettre à jour manuellement la liste des changements de fichiers pour qu'elle soit relative au nouveau premier parent.)
•fast-export et fast-import travaillent avec le contenu exact des fichiers, pas avec des patches. (par ex. "Quel que soit le contenu actuel de ce fichier, mettez-le à jour pour avoir maintenant ces contenus") En raison de cela, supprimer les changements effectués dans un seul commit ou insérer des changements supplémentaires à un fichier dans un commit et s'attendre à ce qu'ils se propagent vers l'avant n'est pas quelque chose qui peut être fait avec ces outils. Utilisez git-rebase(1) pour cela.

Limitations intrinsèques

Certains types de filtrage ont des limitations qui affecteraient tout outil tentant de les effectuer ; le plus qu'un outil puisse faire est d'essayer de notifier l'utilisateur lorsqu'il détecte un problème :

•Lors de la réécriture des hashes de commit dans les messages de commit, il y a une variété de cas où le hash ne sera pas mis à jour (chaque fois que cela arrive, une note est écrite dans .git/filter-repo/suboptimal-issues) :
•si un hash de commit ne correspond pas à un commit dans l'ancien dépôt
•si un hash de commit correspond à un commit qui est élagué
•si un hash abrégé n'est pas unique
•Élagage d'engagements vides peut faire qu'un commit de fusion perd une lignée d'ascendance entière et devienne un non-fusion. Si le commit de fusion n'avait aucun changement, il peut aussi être élagué, mais s'il a encore des changements, il doit être conservé. Cela peut causer une légère confusion puisque le commit aura probablement un message de commit qui le fait ressembler à un commit de fusion même s'il ne l'est pas. (Chaque fois qu'un commit de fusion devient un commit de non-fusion, une note est écrite dans .git/filter-repo/suboptimal-issues)

Problèmes spécifiques à filter-repo

•Plusieurs dépôts dans le monde ont été observés qui utilisent un fuseau horaire erroné (+051800) ; une recherche sur google vous trouvera quelques rapports. Le fuseau horaire prévu n'était pas clair ou n'était pas toujours le même. Remplacé par un autre fuseau horaire erroné que fast-import acceptera (+0261).
•--path-rename peut entraîner des collisions de noms de chemins ; pour éviter des exigences de mémoire excessives liées au suivi des fichiers présents dans tous les commits ou à la recherche de quels fichiers existent avec soit chaque commit, soit chaque utilisation de --path-rename, nous disons simplement à l'utilisateur qu'il pourrait écraser d'autres changements s'il n'est pas prudent. Nous pouvons vérifier si l'écrasement provient d'un autre --path-rename sans trop de surcoût. (Peut-être que dans le futur il vaudrait le coup d'ajouter un mode lent à --path-repo qui ferait les vérifications plus exhaustives ?)
•Il n'y a pas de mécanisme pour contrôler directement quels drapeaux sont passés à fast-export (ou fast-import) ; seuls des drapeaux prédéfinis peuvent être activés ou désactivés comme effet secondaire d'autres options. Un contrôle direct aurait peu de sens car certaines options comme --full-tree nécessiteraient un code supplémentaire dans filter-repo (pour analyser de nouvelles directives), et d'autres telles que -M ou -C casseraient des hypothèses utilisées dans d'autres parties de filter-repo.
•Le filtrage de dépôt partiel, bien que supporté, va à l'encontre de la conception de filter-repo « éviter de mélanger l'ancienne et la nouvelle historique ». Ce support a nécessité des améliorations à git core également (par exemple, il dépend de l'option --reference-excluded-parents de fast-export qui a été ajoutée spécifiquement pour cet usage dans filter-repo). Les options --partial et --refs continueront d'être supportées car il y a des personnes avec des cas d'utilisation pour elles ; cependant, je suis préoccupé par le fait que cette incohérence concernant le mélange de l'ancienne et de la nouvelle historique semble susceptible de mener à des erreurs utilisateur. Pour l'instant, j'espère simplement que les longues explications des mises en garde dans la documentation de ces options suffisent à limiter de tels problèmes.

Commentaires sur la réversibilité

Certaines personnes sont intéressées par la réversibilité d'une réécriture ; par ex. réécrire l'historique, éventuellement ajouter quelques commits, puis annuler la réécriture et obtenir l'historique original en retour plus quelques nouveaux commits « non réécrits ». Évidemment, c'est impossible si votre réécriture implique de jeter des informations (par ex. filtrer des fichiers ou remplacer plusieurs chaînes différentes par ***REMOVED***), mais cela peut être possible avec certaines réécritures. filter-repo est probablement un mauvais choix pour ce type de flux de travail pour quelques raisons :

•la plupart des limitations héritées de fast-export et fast-import sont d'un type qui cause des problèmes de réversibilité
•les greffons et les refs de remplacement, s'ils sont présents, sont utilisés dans la réécriture et rendus permanents
•la réécriture des hachages de commits sera probablement réversible, mais il est possible que des hachages abrégés réécrits ne soient pas uniques même si les hachages abrégés originaux l'étaient.
•filter-repo utilise par défaut plusieurs formes de réécriture irréversibles que vous devrez peut-être désactiver (par ex. les deux derniers points ci-dessus ou le réencodage des messages de commits en UTF-8) ; il est possible que des formes supplémentaires de réécritures irréversibles soient ajoutées dans le futur.
•Je suppose que les gens utilisent filter-repo pour des conversions ponctuelles, pas pour des transferts de données continus. Je réserve explicitement le droit de changer n'importe quelle API dans filter-repo basé sur cette présomption (et un commentaire à cet effet se trouve à plusieurs endroits dans le code et les exemples). Vous avez été averti.
