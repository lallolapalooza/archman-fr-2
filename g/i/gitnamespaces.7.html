NOM

gitnamespaces - Espaces de noms Git

SYNOPIS

GIT_NAMESPACE=<espace_de_noms> git upload-pack
GIT_NAMESPACE=<espace_de_noms> git receive-pack

DESCRIPTION

Git prend en charge la division des références d'un dépôt unique en plusieurs espaces de noms, chacun ayant ses propres branches, étiquettes et HEAD. Git peut exposer chaque espace de noms comme un dépôt indépendant pour tirer et pousser, tout en partageant le magasin d'objets et en exposant toutes les références aux opérations telles que git-gc(1).

Le stockage de plusieurs dépôts comme espaces de noms d'un seul dépôt évite de stocker des copies dupliquées des mêmes objets, par exemple lors du stockage de plusieurs branches de la même source. Le mécanisme d'alternatives fournit un support similaire pour éviter les doublons, mais les alternatives n'empêchent pas la duplication entre les nouveaux objets ajoutés aux dépôts sans maintenance continue, tandis que les espaces de noms le font.

Pour spécifier un espace de noms, définissez la variable d'environnement GIT_NAMESPACE sur le nom de l'espace. Pour chaque espace de noms de refs, Git stocke les refs correspondantes dans un répertoire sous refs/namespaces/. Par exemple, GIT_NAMESPACE=foo stockera les refs sous refs/namespaces/foo/. Vous pouvez également spécifier des espaces de noms via l'option --namespace de git(1).

Notez que les espaces de noms contenant un / s'étendront à une hiérarchie d'espaces de noms ; par exemple, GIT_NAMESPACE=foo/bar stockera les refs sous refs/namespaces/foo/refs/namespaces/bar/. Cela fait que les chemins dans GIT_NAMESPACE se comportent de manière hiérarchique, de sorte que le clonage avec GIT_NAMESPACE=foo/bar produit le même résultat que le clonage avec GIT_NAMESPACE=foo et le clonage à partir de ce dépôt avec GIT_NAMESPACE=bar. Cela évite également l'ambiguïté avec des chemins d'espaces de noms étranges tels que foo/refs/heads/, qui pourraient autrement générer des conflits de répertoires/fichiers au sein du répertoire refs.

git-upload-pack(1) et git-receive-pack(1) réécrivent les noms des refs tels que spécifiés par GIT_NAMESPACE. git-upload-pack et git-receive-pack ignoreront toutes les références en dehors de l'espace de noms spécifié.

Le serveur HTTP intelligent, git-http-backend(1), transmettra GIT_NAMESPACE aux programmes backend ; voir git-http-backend(1) pour un exemple de configuration pour exposer les espaces de noms de dépôts comme des dépôts.

Pour un test local simple, vous pouvez utiliser git-remote-ext(1) :

git clone ext::'git --namespace=foo %s /tmp/prefixed.git'

SÉCURITÉ

Les protocoles de récupération et de poussée ne sont pas conçus pour empêcher une partie de voler des données de l'autre dépôt qui n'étaient pas censées être partagées. Si vous avez des données privées que vous devez protéger d'un pair malveillant, votre meilleure option est de les stocker dans un autre dépôt. Cela s'applique aux clients et aux serveurs. En particulier, les espaces de noms sur un serveur ne sont pas efficaces pour le contrôle d'accès en lecture ; vous ne devez accorder un accès en lecture à un espace de noms qu'aux clients auxquels vous feriez confiance pour un accès en lecture à l'ensemble du dépôt.

Les vecteurs d'attaque connus sont les suivants :

1.La victime envoie des lignes "have" annonçant les identifiants des objets qu'elle possède et qui ne sont pas explicitement destinés à être partagés mais peuvent être utilisés pour optimiser le transfert si le pair les possède également. L'attaquant choisit un identifiant d'objet X à voler et envoie une référence à X, mais n'est pas obligé d'envoyer le contenu de X car la victime le possède déjà. Maintenant, la victime croit que l'attaquant possède X, et il renverra le contenu de X à l'attaquant plus tard. (Cette attaque est plus simple à effectuer pour un client sur un serveur, en créant une référence à X dans l'espace de noms auquel le client a accès et en la récupérant. La manière la plus probable pour un serveur de l'effectuer sur un client est de "fusionner" X dans une branche publique et d'espérer que l'utilisateur effectuera des travaux supplémentaires sur cette branche et la poussera vers le serveur sans remarquer la fusion.)
2.Comme dans le cas no 1, l'attaquant choisit un identifiant d'objet X à voler. La victime envoie un objet Y que l'attaquant possède déjà, et l'attaquant prétend faussement posséder X et non Y, de sorte que la victime envoie Y comme delta par rapport à X. Le delta révèle des régions de X qui sont similaires à Y à l'attaquant.
