NOM

git-upload-pack - Envoyer des objets empaquetés à git-fetch-pack

SYNOPHIS

git-upload-pack [--[no-]strict] [--timeout=<n>] [--stateless-rpc]
                  [--advertise-refs] <répertoire>

DESCRIPTION

Invoqué par git fetch-pack, apprend quels objets l'autre partie manque, et les envoie après les avoir empaquetés.

Cette commande n'est généralement pas invoquée directement par l'utilisateur final. L'interface utilisateur du protocole se trouve du côté de git fetch-pack, et la paire de programmes est destinée à tirer les mises à jour d'un dépôt distant. Pour les opérations de poussée (push), voir git send-pack.

OPTIONS

--strict, --no-strict

N'essaie pas <répertoire>/.git/ si <répertoire> n'est pas un répertoire Git.

--timeout=<n>

Interrompt le transfert après <n> secondes d'inactivité.

--stateless-rpc

Effectue un seul cycle lecture-écriture avec stdin et stdout. Ceci correspond au modèle de traitement des requêtes HTTP POST où un programme peut lire la requête, écrire une réponse, et doit se terminer.

--http-backend-info-refs

Utilisé par git-http-backend(1) pour servir les requêtes $GIT_URL/info/refs?service=git-upload-pack. Voir "Smart Clients" dans gitprotocol-http(5) et "HTTP Transport" dans la documentation de gitprotocol-v2(5). Est également compris par git-receive-pack(1).

<répertoire>

Le dépôt à synchroniser.

ENVIRONNEMENT

GIT_PROTOCOL

Variable interne utilisée pour le handshake du protocole filaire. Les administrateurs serveur peuvent avoir besoin de configurer certains transports pour permettre le passage de cette variable. Voir la discussion dans git(1).

GIT_NO_LAZY_FETCH

Lors du clonage ou de la récupération d'un dépôt partiel (c'est-à-dire un dépôt lui-même cloné avec --filter), le upload-pack côté serveur peut avoir besoin de récupérer des objets supplémentaires de son amont pour compléter la requête. Par défaut, upload-pack refusera d'effectuer une telle récupération paresseuse, car git fetch peut exécuter des commandes arbitraires spécifiées dans la configuration et les hooks du dépôt source (et upload-pack essaie d'être sûr de s'exécuter même dans des répertoires .git non fiables).

Ceci est implémenté en demandant à upload-pack de définir interne la variable GIT_NO_LAZY_FETCH à 1. Si vous souhaitez la remplacer (car vous récupérez depuis un clone partiel, et que vous êtes sûr de lui faire confiance), vous pouvez explicitement définir GIT_NO_LAZY_FETCH à 0.

SÉCURITÉ

La plupart des commandes Git ne devraient pas être exécutées dans un répertoire .git non fiable (voir la section SÉCURITÉ dans git(1)). upload-pack essaie d'éviter toute option de configuration ou hook dangereux du dépôt qu'il sert, ce qui le rend sûr pour cloner un répertoire non fiable et exécuter des commandes sur le clone résultant.

Pour un niveau de sécurité supplémentaire, vous pourriez être en mesure d'exécuter upload-pack en tant qu'utilisateur alternatif. Les détails dépendront de la plateforme, mais sur de nombreux systèmes vous pouvez exécuter :

git clone --no-local --upload-pack='sudo -u nobody git-upload-pack' ...
