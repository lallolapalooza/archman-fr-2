NOM

rpc.gssd - démon RPCSEC_GSS

SYNTAXE

rpc.gssd [-DfMnlvrHC] [-k keytab] [-p pipefsdir] [-d ccachedir] [-t timeout] [-T timeout] [-U timeout] [-R realm]

INTRODUCTION

Le protocole RPCSEC_GSS, défini dans la RFC 5403, est utilisé pour fournir une sécurité forte aux protocoles basés sur RPC tels que NFS.

Avant d'échanger des requêtes RPC utilisant RPCSEC_GSS, un client RPC doit établir un contexte de sécurité GSS. Un contexte de sécurité est un état partagé de chaque côté d'un transport réseau qui permet les services de sécurité de l'API GSS.

Les contextes de sécurité sont établis à l'aide de crédentials de sécurité. Une credential accorde un accès temporaire à un service réseau sécurisé, tout comme un ticket de train accorde un accès temporaire pour utiliser un service ferroviaire.

Un utilisateur obtient généralement une credential en fournissant un mot de passe à la commande kinit(1), ou via une bibliothèque PAM lors de la connexion. Une credential acquise avec un principal utilisateur est connue sous le nom de credential utilisateur (voir kerberos(1) pour plus d'informations sur les principals).

Certaines opérations nécessitent une credential qui ne représente aucun utilisateur particulier ou qui représente la machine elle-même. Ce type de credential est appelée une credential machine.

Une machine établit sa credential machine à l'aide d'un principal de service dont le mot de passe chiffré est stocké dans un fichier local appelé keytab. Une credential machine reste effective sans intervention de l'utilisateur tant que la machine peut la renouveler.

Une fois obtenues, les credentials sont généralement stockées dans des fichiers temporaires locaux avec des noms de chemins bien connus.

DESCRIPTION

Pour établir des contextes de sécurité GSS à l'aide de ces fichiers de credentials, le client RPC du noyau Linux dépend d'un démon en espace utilisateur appelé rpc.gssd. Le démon rpc.gssd utilise le système de fichiers rpc_pipefs pour communiquer avec le noyau.

Credentials Utilisateur

Lorsqu'un utilisateur s'authentifie à l'aide d'une commande telle que kinit(1), la credential résultante est stockée dans un fichier dont le nom est construit à l'aide de l'UID de l'utilisateur.

Pour interagir avec un serveur NFS au nom d'un utilisateur particulier authentifié par Kerberos, le client RPC du noyau Linux demande à rpc.gssd d'initialiser un contexte de sécurité avec la credential dans le fichier de credential de cet utilisateur.

En général, les fichiers de credentials sont placés dans /tmp. Cependant, rpc.gssd peut rechercher des fichiers de credentials dans plusieurs répertoires. Voir la description de l'option -d pour plus de détails.

Credentials Machine

rpc.gssd recherche le keytab par défaut, /etc/krb5.keytab, dans l'ordre suivant pour trouver un principal et un mot de passe à utiliser lors de l'établissement de la credential machine. Pour la recherche, rpc.gssd remplace <hostname> et <REALM> par le nom d'hôte du système local et le royaume Kerberos.


<HOSTNAME>$@<REALM>
root/<hostname>@<REALM>
nfs/<hostname>@<REALM>
host/<hostname>@<REALM>
root/<anyname>@<REALM>
nfs/<anyname>@<REALM>
host/<anyname>@<REALM>

rpc.gssd sélectionne l'une des entrées <anyname> s'il ne trouve pas de principal de service correspondant au nom d'hôte local (par exemple, si DHCP attribue dynamiquement le nom d'hôte local). La facilité <anyname> permet l'utilisation du même keytab sur plusieurs systèmes. Cependant, l'utilisation du même principal de service pour établir une credential machine sur plusieurs machines peut créer des expositions de sécurité indésirables et n'est donc pas recommandée.

Notez que <HOSTNAME>$@<REALM> est un principal utilisateur qui permet Kerberized NFS lorsque le système local est joint à un domaine Active Directory à l'aide de Samba. Le keytab fournit le mot de passe pour ce principal.

Vous pouvez spécifier un keytab différent en utilisant l'option -k si /etc/krb5.keytab n'existe pas ou ne fournit pas l'un de ces principals.

Credentials pour UID 0

L'UID 0 est un cas spécial. Par défaut, rpc.gssd utilise les credentials machine du système pour les accès UID 0 qui nécessitent une authentification GSS. Cela limite les privilèges de l'utilisateur root lors de l'accès aux ressources réseau nécessitant une authentification.

Spécifiez l'option -n lors du démarrage de rpc.gssd si vous souhaitez forcer l'utilisateur root à obtenir une credential utilisateur plutôt que d'utiliser la credential machine du système local.

Lorsque -n est spécifié, le noyau continue à demander un contexte GSS établi avec une credential machine pour les opérations NFSv4, telles que SETCLIENTID ou RENEW, qui gèrent l'état. Si rpc.gssd ne parvient pas à obtenir une credential machine (par exemple, si le système local n'a pas de keytab), les opérations NFSv4 nécessitant des credentials machine échoueront.

Types de chiffrement

Un administrateur de royaume peut choisir d'ajouter des clés codées dans plusieurs types de chiffrement au keytab du système local. Par exemple, un principal de type host/ pourrait avoir des clés pour les types de chiffrement aes256-cts-hmac-sha1-96, aes128-cts-hmac-sha1-96, des3-cbc-sha1 et arcfour-hmac. Cela permet à rpc.gssd de choisir un type de chiffrement approprié pris en charge par le serveur NFS cible.

Ces types de chiffrement sont plus forts que les types de chiffrement DES simples hérités. Pour interopérer dans des environnements où les serveurs ne prennent en charge que des types de chiffrement faibles, vous pouvez restreindre votre client à utiliser uniquement les types de chiffrement DES simples en spécifiant l'option -l lors du démarrage de rpc.gssd.

OPTIONS

-D
Le nom du serveur passé à GSSAPI pour l'authentification est normalement le nom exactement comme demandé. Par exemple, pour NFS, il s'agit du nom du serveur dans la requête de montage "nom_serveur:/chemin". Ce n'est que si ce nom_serveur semble être une adresse IP (IPv4 ou IPv6) ou un nom non qualifié (sans points) qu'une recherche DNS inversée sera effectuée pour obtenir le nom canonique du serveur.

Si -D est présent, une recherche DNS inversée sera toujours utilisée, même si le nom du serveur ressemble à un nom canonique. Elle est donc nécessaire si des noms partiellement qualifiés ou non canoniques sont régulièrement utilisés.

L'utilisation de -D peut introduire une vulnérabilité de sécurité, il est donc recommandé de ne pas utiliser -D et d'utiliser toujours des noms canoniques lors de la demande de services.

-f
Exécute rpc.gssd en premier plan et envoie la sortie vers stderr (par opposition à syslogd)
-n
Lorsqu'elle est spécifiée, l'UID 0 est forcée à obtenir des credentials utilisateur qui sont utilisées à la place des credentials machine du système local.
-k keytab
Indique à rpc.gssd d'utiliser les clés trouvées dans keytab pour obtenir des credentials machine. La valeur par défaut est /etc/krb5.keytab.
-l
Lorsqu'elle est spécifiée, restreint rpc.gssd aux sessions utilisant des types de chiffrement faibles tels que des-cbc-crc. Cette option n'est disponible que lorsque la bibliothèque Kerberos du système local prend en charge des types de chiffrement configurables.
-p chemin
Indique à rpc.gssd où rechercher le système de fichiers rpc_pipefs. La valeur par défaut est /var/lib/nfs/rpc_pipefs.
-d chemin-recherche
Cette option spécifie une liste de répertoires séparés par des deux-points que rpc.gssd parcourt à la recherche de fichiers de credentials. La valeur par défaut est /tmp:/run/user/%U. La séquence littérale "%U" peut être spécifiée pour substituer l'UID de l'utilisateur pour lequel les credentials sont recherchées.
-M
Par défaut
ult, les identifiants de machine sont stockés dans des fichiers du premier répertoire du chemin de recherche des répertoires d'identifiants (voir l'option -d). Quand -M est défini, rpc.gssd stocke les identifiants de machine en mémoire à la place.
