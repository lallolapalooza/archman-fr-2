fonction gl_get_line() fait partie de la bibliothèque tecla (voir la page man libtecla(3)). Si l'utilisateur tape sur un terminal, chaque appel l'invite à saisir une ligne d'entrée, puis fournit des fonctionnalités d'édition interactives, similaires à celles du shell unix tcsh. En plus de l'édition de ligne de commande simple, elle prend en charge le rappel des lignes de commande précédemment saisies, la complétion des noms de fichiers avec la touche TAB, et l'expansion des jokers dans les noms de fichiers en ligne. La documentation des fonctionnalités d'édition de ligne de commande au niveau utilisateur et de toutes les options de configuration utilisateur se trouve dans la page man tecla(7). Cette page man concerne la documentation destinée aux programmeurs souhaitant utiliser cette bibliothèque dans leur application. UN E

LES FONCTIONS UTILISÉES DANS

L'EXEMPLE

Les descriptions des fonctions utilisées dans l'exemple sont les suivantes

: 
  GetLine *new_GetLine(size_t linelen, size_t

Cette fonction crée les ressources utilisées par la fonction gl_get_line() et retourne un pointeur opaque vers l'objet qui les contient. La longueur maximale d'une ligne d'entrée est spécifiée via l'argument linelen, et le nombre d'octets à allouer pour stocker les lignes d'historique est défini par l'argument histlen. Les lignes d'historique sont stockées bout à bout dans un seul tampon de cette taille. Notez que cela signifie que le nombre de lignes d'historique qui peuvent être stockées à un moment donné dépend des longueurs des lignes individuelles. Si vous souhaitez placer une limite supérieure au nombre de lignes pouvant être stockées, voir la fonction gl_limit_history() décrite plus tard. Si vous ne souhaitez pas d'historique du tout, spécifiez histlen comme zéro, et aucun tampon d'historique ne sera

alloué.

En cas d'erreur, un message est imprimé sur stderr et NULL est

retourné. 
  GetLine *del_GetLine(GetLine
*gl)

Cette fonction supprime les ressources qui ont été retournées par un appel précédent à new_GetLine(). Elle retourne toujours NULL (c'est-à-dire un objet supprimé). Elle ne fait rien si l'argument gl est NULL

  char *gl_get_line(GetLine *gl, const char *prompt,

;

La fonction gl_get_line() peut être appelée un nombre quelconque de fois pour lire la saisie de l'utilisateur. L'argument gl doit avoir été précédemment retourné par un appel à new_GetLine(). L'argument prompt doit être une chaîne normale terminée par NUL, spécifiant l'invite à présenter à l'utilisateur. Par défaut, les invites sont affichées littéralement, mais si elles sont activées avec la fonction gl_prompt_style() (voir plus tard), les invites peuvent contenir des directives pour souligner, passer en et sortir des polices en gras, ou activer et désactiver la mise en

évidence.

Si vous souhaitez spécifier le contenu initial de la ligne pour que l'utilisateur la modifie, transmettez la chaîne souhaitée via l'argument start_line. Vous pouvez ensuite spécifier le caractère de cette ligne où le curseur est initialement positionné sur, en utilisant l' argument start_pos. Cela doit être -1 si vous voulez que le curseur suive le dernier caractère de la ligne de début. Si vous ne voulez pas précharger la ligne de cette manière, envoyez start_line comme NULL, et définissez start_pos à -1. Notez que le pointeur de ligne renvoyé par un appel à gl_get_line() peut être transmis à l'appel suivant à gl_get_line() via le start_line. Cela permet à l'application de prendre la dernière ligne saisie, et si elle contient une erreur, de la présenter à nouveau à l'utilisateur pour réédition, avec le curseur initialement positionné à l'endroit où l'erreur a été

rencontrée.

La fonction gl_get_line() renvoie un pointeur vers la ligne saisie par l'utilisateur, ou NULL en cas d'erreur ou à la fin de l'entrée. Le pointeur renvoyé fait partie de l'objet ressource gl spécifié, et ne doit donc pas être libéré par l'appelant, ni supposé être invariable d'un appel au suivant. Lors de la lecture depuis un utilisateur sur un terminal, il y aura toujours un caractère de nouvelle ligne à la fin de la ligne renvoyée. Lorsque l'entrée standard provient d'un tube ou d'un fichier, il y aura de même une nouvelle ligne, sauf si la ligne d'entrée était trop longue pour être stockée dans le tampon interne. Dans ce dernier cas, vous devriez appeler gl_get_line() à nouveau pour lire le reste de la ligne. Notez que ce comportement rend gl_get_line() similaire à fgets(). En fait, lorsque stdin n'est pas connecté à un terminal,gl_get_line() appelle simplement fget

s(
).

SOURCES DE CONFIGURATION

ALTERNATIVES

Comme mentionné ci-dessus, par défaut les utilisateurs ont la possibilité de configurer le comportement de gl_get_line() via un fichier de configuration appelé .teclarc dans leurs répertoires personnels. Le fait que toutes les applications partagent ce même fichier de configuration est à la fois un avantage et un inconvénient. Dans la plupart des cas, c'est un avantage, car cela encourage l'uniformité, et dispense l'utilisateur de devoir configurer chaque application séparément. Dans certaines applications, cependant, ce seul moyen de configuration est un problème. C'est particulièrement vrai pour les logiciels embarqués, où il n'y a pas de système de fichiers pour lire un fichier de configuration, et aussi dans les applications où un choix radicalement différent de liaisons de touches est nécessaire pour émuler une interface de clavier héritée. Pour prendre en charge de tels cas, la fonction suivante permet à l'application de contrôler d'où les informations de configuration sont

lues. 
  int gl_configure_getline(GetLine *gl,
                           const char *app_string,
                           const char *app_file,
                           const char *user_file)
;

Elle permet aux commandes de configuration qui seraient normalement lues depuis le fichier ~/.teclarc d'un utilisateur, d'être lues depuis n'importe lequel ou aucun de : une chaîne, un fichier de configuration spécifique à l'application, et/ou un fichier de configuration spécifique à l'utilisateur. Si cette fonction est appelée avant le premier appel à gl_get_line(), le comportement par défaut de lecture de ~/.teclarc au premier appel à gl_get_line() est désactivé, de sorte que toute la configuration doit être réalisée en utilisant les sources de configuration spécifiées avec cette

fonction.

Si app_string != NULL, alors il est interprété comme une chaîne contenant une ou plusieurs commandes de configuration, séparées les unes des autres dans la chaîne par des caractères de nouvelle ligne intégrés. Si app_file != NULL alors il est interprété comme le chemin complet d'un fichier de configuration spécifique à l'application. Si user_file != NULL alors il est interprété comme le chemin complet d'un fichier de configuration spécifique à l'utilisateur, tel que ~/.teclarc. Par exemple, dans l'appel

suivant, 
  gl_configure_getline(gl, "edit-mode vi \n nobeep",
                           "/usr/share/myapp/teclarc",
                           "~/.teclarc")
;

l' argument app_string fait que l'application appelante démarre en mode d'édition vi, au lieu du mode emacs par défaut, et désactive l'utilisation de la cloche du terminal par la bibliothèque. Elle essaie ensuite de lire les commandes de configuration à l'échelle du système depuis un fichier facultatif appelé /usr/share/myapp/teclarc, puis lit enfin les commandes de configuration spécifiques à l'utilisateur depuis un fichier .teclarc facultatif dans le répertoire personnel de l'utilisateur. Notez que les arguments sont listés par ordre de priorité croissant, le contenu de app_string pouvant potentiellement être remplacé par des commandes dans app_file, et les commandes dans app_file pouvant potentiellement être remplacées par des commandes dans user_file

.

Vous pouvez appeler cette fonction autant de fois que nécessaire, les résultats étant cumulatifs, mais notez que les copies de tout nom de fichier spécifié via le app_file et user_file sont enregistrés en interne pour une utilisation ultérieure par la fonction de liaison de touches read-init-files ; si vous prévoyez d'appeler cette fonction plusieurs fois, assurez-vous que le dernier appel spécifie les noms de fichiers que vous souhaitez relire lorsque l'utilisateur demande la relecture des fichiers de

configuration.

Des séquences de touches individuelles peuvent également être liées et déliées à l'aide de la fonction gl_bind_keyseq()

  int gl_bind_keyseq(GetLine *gl, GlKeyOrigin origin,
                     const char *keyseq,
                     const char *action)

L' argument origin spécifie la priorité de la liaison, selon qui elle est établie, et doit être l'une des deux valeurs

suivantes. 
  GL_USER_KEY   -   L'utilisateur a demandé cette liaison de touches.
  GL_APP_KEY    -   Il s'agit d'une liaison par défaut définie par
l'application.

Lorsque des liaisons utilisateur et application pour une même séquence de touches ont été spécifiées, la liaison utilisateur a la priorité. La liaison de l'application est rétablie par la suite si la liaison de l'utilisateur est ultérieurement déliée soit par un autre appel à cette fonction, soit par un appel à gl_configure_ge

tline().

L' argument keyseq spécifie la séquence de touches à lier ou à délier, et est exprimé de la même manière que dans un fichier de configuration ~/.teclarc. L' argument action doit être soit une chaîne contenant le nom de l'action à laquelle lier la séquence de touches, soit il doit être NULL ou "" pour délier

la séquence
de touches.

COMPLÉTION DE MOTS

PERSONNALISÉE

Si dans votre application, vous souhaitez que la complétion par TAB complète d'autres éléments en plus ou à la place des noms de fichiers, vous pouvez organiser cela en enregistrant une fonction de rappel de complétion alternative, via un appel à la fonction gl_customize_c

ompletion(). 
  int gl_customize_completion(GetLine *gl, void *data,
                              CplMatchFn *match_fn)
;

L' argument data fournit un moyen à votre application de passer des informations arbitraires et spécifiques à l'application à la fonction de rappel. Celles-ci lui sont transmises à chaque fois qu'elle est appelée. Elle peut par exemple, pointer vers la table de symboles à partir de laquelle les complétions possibles doivent être recherchées. L' argument match_fn spécifie la fonction de rappel à appeler. Le type de fonction CplMatchFn est défini dans libtecla.h, tout comme une macro CPL_MATCH_FN() que vous pouvez utiliser pour déclarer et prototyper des fonctions de rappel. La déclaration et les responsabilités des fonctions de rappel sont décrites en détail dans la page de man cpl_complete_word(3)

.

En bref, la fonction de rappel est responsable de la recherche vers l'arrière dans la ligne d'entrée, en remontant depuis le point où l'utilisateur a appuyé sur TAB, pour trouver le début du mot en cours de complétion. Elle doit ensuite rechercher les complétions possibles de ce mot et les enregistrer une par une dans l'objet WordCompletion qui lui est passé en argument, en appelant la fonction cpl_add_completion(). Si la fonction de rappel souhaite fournir une complétion de nom de fichier en plus de ses propres complétions spécifiques, elle a la possibilité d'appeler elle-même la fonction de rappel de complétion de nom de fichier intégrée. Ceci est également documenté dans la page de man cpl_complete_word(3)

.

Notez que si vous souhaitez que gl_get_line() renvoie la ligne d'entrée actuelle lorsqu'une complétion réussie a été effectuée, vous pouvez organiser cela lorsque vous appelez cpl_add_completion(), en faisant du dernier caractère du suffixe de continuation un caractère de nouvelle ligne. Si vous faites cela, la ligne d'entrée sera mise à jour pour afficher la complétion, ainsi que tout suffixe de continuation jusqu'au caractère de nouvelle ligne, puis gl_get_line() renverra cette ligne

d'entrée.

Si, pour une raison quelconque, votre fonction de rappel doit écrire quelque chose sur le terminal, elle doit appeler gl_normal_io() avant de le faire. Cela commencera une nouvelle ligne après la ligne d'entrée actuellement en cours d'édition, rétablira les E/S normales du terminal, et indiquera à gl_get_line() que la ligne d'entrée devra

être redessinée lorsqu
e le rappel se termine.

AJOUT D'ACTIONS DE

COMPLÉTION

Dans la section précédente, la possibilité de personnaliser le comportement de la seule action de complétion par défaut, complete-word, a été décrite. Dans cette section, la possibilité d'installer des fonctions d'action supplémentaires, afin que différents types de complétion de mots puissent être liés à différentes séquences de touches, est décrite. Cela est réalisé en utilisant la fonction gl_completion_action()

. 
  int gl_completion_action(GetLine *gl,
                           void *data, CplMatchFn *match_fn,
                           int list_only, const char *name,
                           const char *keyseq)
;

Les arguments data et match_fn sont tels que décrits dans la page de man cpl_complete_word, et spécifient la fonction de rappel qui doit être invoquée pour identifier les complétions possibles. L' argument list_only détermine si l'action en cours de définition doit tenter de compléter le mot aussi loin que possible dans la ligne d'entrée avant d'afficher d'éventuelles complétions ambiguës, ou si elle doit simplement afficher la liste des complétions possibles sans toucher à la ligne d'entrée. La première option est sélectionnée en spécifiant une valeur de 0, et la seconde en spécifiant une valeur de 1. L' argument name spécifie le nom par lequel les fichiers de configuration et les futures invocations de cette fonction doivent se référer à l'action. Il doit s'agir soit du nom d'une action de complétion existante à modifier, soit d'un nouveau nom inutilisé pour une nouvelle action. Enfin, l' argument keyseq spécifie la séquence de touches par défaut à lier à l'action. Si c'est NULL, aucune nouvelle séquence de touches ne sera liée à

l'action.

Attention, pour que l'utilisateur puisse changer la séquence de touches liée aux actions installées de cette manière, lorsque vous appelez gl_completion_action() pour installer une action donnée pour la première fois, vous devez le faire entre l'appel à new_GetLine() et le premier appel à gl_get_line(). DÉFINITION D'ACTIONS

PERSONNALISÉES

Bien que les actions de liaison de touches intégrées soient suffisantes pour les besoins de la plupart des applications, une application spécialisée peut parfois avoir besoin de définir une ou plusieurs actions personnalisées, liées à des séquences de touches spécifiques à l'application. Par exemple, une application de vente bénéficierait d'une séquence de touches affichant le nom de la pièce correspondant à un numéro de pièce situé avant le curseur. Une telle fonctionnalité dépasse clairement le cadre des fonctions d'action intégrées. Ainsi, pour de tels cas particuliers, la fonction gl_register_action() est

fournie. 
  int gl_register_action(GetLine *gl, void *data,
			 GlActionFn *fn, const char *name,
			 const char *keyseq)
;

Cette fonction permet à l'application d'enregistrer une fonction externe, fn, qui sera ensuite appelée chaque fois que soit la séquence de touches spécifiée, keyseq, est saisie par l'utilisateur, soit l'utilisateur saisit une autre séquence de touches qu'il lie ensuite à l'action spécifiée, name, dans son fichier de configuration. L' argument data peut être un pointeur vers n'importe quoi que l'application souhaite faire passer à la fonction d'action, fn, chaque fois que cette fonction est

invoquée.

La fonction d'action, fn, doit être déclarée à l'aide de la macro suivante, qui est définie dans libtecl

a.h. 
  #define GL_ACTION_FN(fn) GlAfterAction (fn)(GetLine *gl, \
              void *data, int count, size_t curpos, \
              const char
*line)

Les arguments gl et data sont ceux qui ont été précédemment passés à gl_register_action() lorsque la fonction d'action a été enregistrée. L' argument count est un argument numérique que l'utilisateur a la possibilité de saisir à l'aide de l'action digit-argument, avant d'invoquer l'action. Si l'utilisateur n'entre pas de nombre, alors l' argument count est défini à 1. Nominalement, cet argument est interprété comme un nombre de répétitions, ce qui signifie que l'action doit être répétée ce nombre de fois. En pratique cependant, pour certaines actions, un nombre de répétitions n'a que peu de sens. Dans de tels cas, les actions peuvent soit simplement ignorer l' argument count, soit utiliser sa valeur à une autre

fin.

Une copie de la ligne d'entrée actuelle est passée dans l'argument en lecture seule line. La position actuelle du curseur dans cette chaîne est donnée par l'index contenu dans l' argument curpos. Notez que la manipulation directe de la ligne d'entrée et de la position du curseur n'est pas autorisée. En effet, les règles dictées par divers modes, tels que le mode vi par rapport au mode emacs, le mode sans écho, et le mode insertion par rapport au mode remplacement etc, rendent la tâche trop complexe pour un développeur d'application afin d'écrire une action d'édition conforme, tout en limitant les modifications futures des internes de gl_get_line(). Une solution potentielle à ce dilemme serait de permettre à la fonction d'action d'éditer la ligne en utilisant les actions d'édition existantes. Cela est actuellement à

l'étude.

Si la fonction d'action souhaite écrire du texte sur le terminal, sans que cela se mélange avec le texte affiché de la ligne d'entrée, ou lire depuis le terminal sans avoir à gérer les E/S brutes du terminal, alors avant de faire l'une ou l'autre de ces opérations, elle doit suspendre temporairement l'édition de ligne en appelant la fonction gl_normal_io(). Cette fonction vide toute sortie en attente vers le terminal, déplace le curseur au début de la ligne qui suit la dernière ligne du terminal de la ligne d'entrée, puis restaure le terminal à un état adapté à l'utilisation avec les fonctionnalités stdio de C. Cela inclut notamment la restauration du mappage normal de \n vers \r\n, et, en mode serveur, la restauration de la forme bloquante normale des E/S du terminal. Après avoir appelé cette fonction, la fonction d'action peut lire depuis et écrire vers le terminal sans craindre de créer un désordre. Il n'est pas nécessaire pour la fonction d'action de restaurer l'environnement d'édition original avant de se terminer. Cela est fait automatiquement par gl_get_line() après le retour de la fonction d'action. Voici un exemple simple d'une fonction d'action qui écrit la phrase "Hello world" sur une nouvelle ligne du terminal après la ligne en cours d'édition. Lorsque cette fonction se termine, la ligne d'entrée est redessinée sur la ligne qui suit la ligne "Hello world", et l'édition de ligne

reprend. 
  static GL_ACTION_FN(say_hello_fn)
  {
    if(gl_normal_io(gl))   /* Suspendre temporairement l'édition */
      return GLA_ABORT;
    printf("Hello world\n");
    return GLA_CONTINUE;
}

Les fonctions d'action doivent retourner l'une des valeurs suivantes, pour indiquer à gl_get_line() comment

procéder. 
  GLA_ABORT     -   Faire en sorte que gl_get_line() retourne NULL.
  GLA_RETURN    -   Faire en sorte que gl_get_line() retourne la
                    ligne d'entrée complétée.
  GLA_CONTINUE  -   Reprendre l'édition de la ligne de
commande.

Notez que le argument name de gl_register_action() spécifie le nom par lequel un utilisateur peut référencer l'action dans son fichier de configuration. Cela lui permet de réassocier l'action à une séquence de touches alternative. Pour que cela fonctionne, il est nécessaire d'appeler gl_register_action() entre l'appel à new_GetLine() et le premier appel à gl_get_

lin
e().

ARCHIVAGE MANUEL DE

L'HISTORIQUE

Par défaut, chaque fois qu'une ligne est saisie par l'utilisateur, elle est automatiquement ajoutée à la liste d'historique, juste avant que gl_get_line() retourne la ligne à l'appelant. C'est pratique pour la majorité des applications, mais il existe aussi des applications qui ont besoin d'un contrôle plus fin sur ce qui est ajouté à la liste d'historique. Dans de tels cas, l'ajout automatique des lignes saisies à la liste d'historique peut être désactivé en appelant la fonction gl_automatic

_history(). 
  int gl_automatic_history(GetLine *gl, int enable)
;

Si cette fonction est appelée avec son argument enable défini à 0, gl_get_line() n'archivera pas automatiquement les lignes saisies ultérieurement. L'archivage automatique peut être réactivé plus tard, en appelant à nouveau cette fonction, avec son argument enable défini à 1. Tant que l'archivage automatique de l'historique est désactivé, l'application appelante peut utiliser gl_append_history() pour ajouter des lignes à la liste d'historique selon les

besoins. 
  int gl_append_history(GetLine *gl, const char *line)
;

L' argument line spécifie la ligne à ajouter à la liste d'historique. Cela doit être une chaîne normale ' ' terminée. Si cette chaîne contient des caractères de nouvelle ligne, la ligne archivée dans la liste d'historique sera terminée par le premier d'entre eux. Sinon, elle sera terminée par le terminateur ' '. Si la ligne est plus longue que la longueur maximale de ligne d'entrée, qui a été spécifiée lorsque new_GetLine() a été appelée, lorsqu'elle sera rappelée, elle sera tronquée à la longueur réelle de la ligne gl_get_li

ne().

En cas de succès, gl_append_history() retourne 0. Sinon, elle retourne une valeur non nulle, et définit errno à l'une des valeurs

suivantes. 
   EINVAL  -  L'un des arguments passés à
              gl_append_history() était NULL.
   ENOMEM  -  La ligne spécifiée était plus longue que la taille allouée
              du tampon d'historique (comme spécifié lorsque
              new_GetLine() a été appelée), elle n'a donc pas pu être
archivée.

Une description textuelle de l'erreur peut être obtenue en appelant éventuellement gl_error_message(). Notez qu'après une telle erreur, la liste d'historique reste dans un état valide pour recevoir de nouvelles lignes d'historique, il y a donc peu d'inconvénient à simplement ignorer le statut de retour de gl_append_

CONFIGURATION DIVERSE DE

L'HISTORIQUE

Si vous souhaitez changer la taille du tampon d'historique qui a été initialement spécifiée dans l'appel à new_GetLine(), vous pouvez le faire avec la fonction gl_resize_history()

. 
  int gl_resize_history(GetLine *gl, size_t histlen)
;

L' argument histlen spécifie la nouvelle taille en octets, et si vous spécifiez 0, le tampon sera

supprimé.

Comme mentionné dans la discussion de new_GetLine(), le nombre de lignes qui peuvent être stockées dans le tampon d'historique dépend des longueurs des lignes individuelles. Par exemple, un tampon de 1000 octets pourrait tout aussi bien stocker 10 lignes de longueur moyenne de 100 octets, ou 2 lignes de longueur moyenne de 50 octets. Bien que le tampon ne soit jamais agrandi lorsque de nouvelles lignes sont ajoutées, une liste de pointeurs vers le tampon est agrandie si nécessaire pour accueillir le nombre de lignes actuellement stockées dans le tampon. Pour placer une limite supérieure sur le nombre de lignes dans le tampon, et ainsi un plafond sur la quantité de mémoire utilisée dans cette liste, vous pouvez appeler la gl_limit_history()

fonction. 
  void gl_limit_history(GetLine *gl, int max_lines)
;

Le max_lines doit être soit un nombre positif >= 0, spécifiant une limite supérieure sur le nombre de lignes dans le tampon, soit -1 pour annuler toute limite précédemment spécifiée. Lorsqu'une limite est en vigueur, seules les max_lines dernières lignes ajoutées sont conservées dans le tampon. Les lignes plus anciennes sont

supprimées.

. 
  void gl_clear_history(GetLine *gl, int all_groups)
;

L' argument all_groups indique à la fonction si elle doit supprimer uniquement les lignes associées au groupe d'historique courant (voir gl_group_history()), ou toutes les lignes historiques du

tampon.

La fonction gl_toggle_history() permet d'activer et de désactiver l'historique sans perdre le contenu actuel de la liste

d'historique. 
  void gl_toggle_history(GetLine *gl, int enable)
;

Régler l' argument enable à 0 désactive le mécanisme d'historique, et le régler à 1 le réactive. Lorsque l'historique est désactivé, aucune nouvelle ligne ne ser

a ajoutée à la liste d'historique, et les raccourcis clavier de recherche d
ans l'historique se comporteront comme si le tampon d'historique était vide.

CHANGER DE

TERMINAL

La fonction constructrice new_GetLine() suppose que l'entrée doit être lue depuis stdin et que la sortie est écrite vers stdout. La fonction suivante permet de basculer vers d'autres flux d'entrée et de

sortie. 
  int gl_change_terminal(GetLine *gl, FILE *input_fp,
                         FILE *output_fp, const char *term)
;

L' argument gl est l'objet qui a été renvoyé par new_GetLine(). L' argument input_fp spécifie le flux à lire, et output_fp spécifie le flux vers lequel écrire. Seulement si les deux font référence à un terminal, l'entrée interactive sur terminal sera activée. Sinon gl_get_line() appellera simplement fgets() pour lire la saisie de commande. Si les deux flux font référence à un terminal, alors ils doivent faire référence au même terminal, et le type de ce terminal doit être spécifié via l' argument term. La valeur de l' argument term est recherchée dans la base de données d'informations sur les terminaux (terminfo ou termcap), afin de déterminer quelles séquences de contrôle spéciales sont nécessaires pour contrôler divers aspects du terminal. new_GetLine() passe par exemple la valeur de retour de getenv("TERM") dans cet argument. Notez que si un ou les deux de input_fp et output_fp ne font pas référence à un terminal, il est légal de passer NULL au lieu d'un type de

terminal.

Notez que si vous souhaitez passer des descripteurs de fichier à gl_change_terminal(), vous pouvez le faire en créant des enveloppes de flux stdio à l'aide de la fonction POSIX fdop

en(

GESTION D'ÉVÉNEMENTS

EXTERNES

Par défaut, gl_get_line() ne renvoie rien tant qu'une ligne d'entrée complète n'a pas été saisie par l'utilisateur, ou qu'une erreur ne se produit pas. Dans les programmes qui doivent surveiller les E/S provenant d'autres sources que le terminal, il y a deux

options. 
  1. Utiliser les fonctions décrites dans la page de manuel
     gl_io_mode(3) pour basculer
     gl_get_line() en mode serveur non bloquant. Dans ce mode,
     gl_get_line() devient une fonction d'édition de ligne non bloquante et
     incrémentielle qui peut être appelée en toute sécurité depuis
     une boucle d'événements externe. Bien que ce soit une méthode très
     polyvalente, elle implique d'assumer certaines
     responsabilités qui sont normalement effectuées en coulisses par gl_get_line().
  2. Pendant que gl_get_line() attend la saisie au clavier
     de l'utilisateur, vous pouvez lui demander de surveiller également
     l'activité sur des descripteurs de fichier arbitraires, tels que
     des sockets réseau, des tuyaux (pipes), etc., et de lui faire appeler des
     fonctions de votre choix lorsque l'activité est détectée. Cela fonctionne sur
     tout système qui dispose de l'appel système select(), ce qui est le cas de la plupart, sinon de toutes les variantes
d'unix.

. 
  int gl_watch_fd(GetLine *gl, int fd, GlFdEvent event,
                  GlFdEventFn *callback, void *data)
;

Si cela renvoie une valeur non nulle, cela signifie soit que vos arguments sont invalides, soit que cette fonctionnalité n'est pas prise en charge sur le système

hôte.

L' argument fd est le descripteur de fichier à surveiller. L' argument event spécifie quel type d'activité est d'intérêt, choisi parmi les valeurs énumérées suivantes

: 
  GLFD_READ   -  Surveiller l'arrivée de données à lire.
  GLFD_WRITE  -  Surveiller la capacité d'écrire dans le descripteur
                 de fichier sans bloquer.
  GLFD_URGENT -  Surveiller l'arrivée de données urgentes
                 hors bande sur le descripteur de
fichier.

L' argument callback est la fonction à appeler lorsque l'activité sélectionnée est détectée. Elle doit être définie avec la macro suivante, qui est définie dans libtecla.

h. 
  #define GL_FD_EVENT_FN(fn) GlFdStatus (fn)(GetLine *gl, \
                                      void *data, int fd, \

L' argument data de la fonction gl_watch_fd() est passé à la fonction de rappel pour son propre usage, et peut pointer vers ce que vous voulez, y compris NULL. Le descripteur de fichier et l'argument event sont également passés à la fonction de rappel, ce qui permet potentiellement à la même fonction de rappel d'être enregistrée pour plus d'un type d'événement et/ou plus d'un descripteur de fichier. La valeur de retour de la fonction de rappel doit être l'une des valeurs

suivantes. 
  GLFD_ABORT    -  Dire à gl_get_line() d'interrompre. Lorsque cela
                   se produit, gl_get_line() renvoie
                   NULL, et un appel suivant à
                   gl_return_status() renverra

GESTION DES SIGNAUX PAR DÉFAUT

Par défaut, la fonction gl_get_line() intercepte un certain nombre de signaux. Ceci est particulièrement important pour les signaux qui termineraient le processus par défaut, car le terminal doit être restauré dans un état utilisable avant que cela ne se produise. Dans cette section, les signaux qui sont interceptés par défaut, et comment gl_get_line() y répond, sont décrits. Modifier ces valeurs par défaut est le sujet de la section suivante.

Lorsque le sous-ensemble de signaux suivant est intercepté, gl_get_line() restaure d'abord les paramètres du terminal et la gestion des signaux tels qu'ils étaient avant l'appel de gl_get_line(), renvoie le signal, pour permettre aux gestionnaires de signaux de l'application appelante de le gérer, puis si le processus existe toujours, gl_get_line() retourne NULL et définit errno comme spécifié ci-dessous.

 SIGINT  -  Ce signal est généré à la fois par la touche
            d'interruption du clavier (généralement ^C)
            et par la touche de rupture du clavier.
            errno=EINTR
 SIGHUP  -  Ce signal est généré lorsque le terminal de
            contrôle se ferme.
            errno=ENOTTY
 SIGPIPE -  Ce signal est généré lorsqu'un programme tente
            d'écrire dans un tuyau dont l'extrémité distante
            n'est lue par aucun processus. Cela peut se
            produire par exemple si vous avez appelé
            gl_change_terminal() pour rediriger la
            sortie vers un tuyau caché sous un pseudo
            terminal.
            errno=EPIPE
 SIGQUIT -  Ce signal est généré par la touche de sortie du
            clavier (généralement ^\).
            errno=EINTR
 SIGABRT -  Ce signal est généré par la fonction C standard,
            abort(). Par défaut, il termine le processus et
            génère une vidange mémoire (core dump).
            errno=EINTR
 SIGTERM -  C'est le signal par défaut que la commande
            UN*X kill envoie aux processus.
            errno=EINTR

Notez que dans le cas de tous les signaux ci-dessus, POSIX impose que par défaut, le processus soit terminé, avec l'ajout d'une vidange mémoire dans le cas du signal SIGQUIT. En d'autres termes, si l'application appelante ne remplace pas le gestionnaire par défaut en fournissant son propre gestionnaire de signaux, la réception du signal correspondant terminera l'application avant que gl_get_line() ne retourne.

Si gl_get_line() avorte avec errno défini sur EINTR, vous pouvez découvrir quel signal l'a fait avorter en appelant la fonction suivante.

  int gl_last_signal(const GetLine *gl);

Ceci retourne le code numérique (par exemple, SIGINT) du dernier signal reçu lors de l'appel le plus récent à gl_get_line(), ou -1 si aucun signal n'a été reçu.

Sur les systèmes qui le prennent en charge, lorsqu'un signal SIGWINCH (changement de fenêtre) est reçu, gl_get_line() interroge le terminal pour connaître sa nouvelle taille, redessine la ligne de saisie actuelle pour s'adapter à la nouvelle taille, puis retourne à l'attente d'une saisie clavier de l'utilisateur. Contrairement aux autres signaux, ce signal n'est pas renvoyé à l'application.

Enfin, les signaux suivants amènent gl_get_line() à restaurer d'abord le terminal et l'environnement des signaux à ce qui prévalait avant l'appel de gl_get_line(), puis à renvoyer le signal à l'application. Si le processus existe toujours après la livraison du signal, alors gl_get_line() rétablit ses propres gestionnaires de signaux, ramène le terminal en mode brut, rediffuse la ligne de saisie et recommence à attendre une saisie du terminal de la part de l'utilisateur.

 SIGCONT    -  Ce signal est généré lorsqu'un processus suspendu
               est repris.
 SIGPOLL    -  Sur les systèmes SVR4, ce signal notifie le
               processus d'un événement d'E/S asynchrone.
               Notez que sous 4.3+BSD, SIGIO et SIGPOLL sont
               identiques. Sur d'autres systèmes, SIGIO est
               ignoré par défaut, donc gl_get_line() ne
               l'intercepte pas par défaut.
 SIGPWR     -  Ce signal est généré lors d'une coupure de
               courant (probablement lorsque le système est
               sur un onduleur).
 SIGALRM    -  Ce signal est généré lorsqu'un minuteur
               expire.
 SIGUSR1    -  Un signal spécifique à l'application.
 SIGUSR2    -  Un autre signal spécifique à l'application.
 SIGVTALRM  -  Ce signal est généré lorsqu'un minuteur
               virtuel expire (voir man setitimer(2)).
 SIGXCPU    -  Ce signal est généré lorsqu'un processus
               dépasse sa limite de temps CPU souple.
 SIGXFSZ    -  Ce signal est généré lorsqu'un processus
               dépasse sa limite de taille de fichier souple.
 SIGTSTP    -  Ce signal est généré par la touche de mise en
               pause du terminal, qui est généralement ^Z,
               ou par la touche de mise en pause différée du
               terminal, qui est généralement ^Y.
 SIGTTIN    -  Ce signal est généré si le programme tente
               de lire depuis le terminal alors que le
               programme s'exécute en arrière-plan.
 SIGTTOU    -  Ce signal est généré si le programme tente
               d'écrire dans le terminal alors que le
               programme s'exécute en arrière-plan.

Évidemment, tous les signaux ci-dessus ne sont pas pris en charge sur tous les systèmes, donc le code pour les prendre en charge est compilé conditionnellement dans la bibliothèque tecla.

Notez que si SIGKILL ou SIGPOLL, qui par définition ne peuvent pas être interceptés, ou l'un des signaux d'exception générés par le matériel, tels que SIGSEGV, SIGBUS et SIGFPE, sont reçus et non gérés alors que gl_get_line() a le terminal en mode brut, le programme sera terminé sans que le terminal n'ait été restauré dans un état utilisable. En pratique, les shells de gestion de tâches réinitialisent généralement les paramètres du terminal lorsqu'un processus abandonne le terminal de contrôle, donc ce n'est qu'un problème avec les anciens shells.

GESTION PERSONNALISÉE DES SIGNAUX

La section précédente a énuméré les signaux que gl_get_line() intercepte par défaut, et a décrit comment il y répond. Cette section décrit comment ajouter et supprimer des signaux de la liste des signaux interceptés, et comment spécifier comment gl_get_line() doit répondre à un signal donné.

Si vous n'avez pas besoin que gl_get_line() fasse quoi que ce soit en réponse à un signal qu'il intercepte normalement, vous pouvez lui dire d'ignorer ce signal en appelant gl_ignore_signal().

  int gl_ignore_signal(GetLine *gl, int signo);

L'argument signo est le numéro du signal (par exemple, SIGINT) que vous souhaitez ignorer. Si le signal spécifié ne fait pas actuellement partie de ceux qui sont interceptés, cette fonction ne fait rien.

La fonction gl_trap_signal() vous permet soit d'ajouter un nouveau signal à la liste que gl_get_line() intercepte, soit de modifier la façon dont il répond.

nds à un signal qu'il intercepte déjà.

  int gl_trap_signal(GetLine *gl, int signo, unsigned flags,
                     GlAfterSignal after, int errno_value);

L'argument signo est le numéro du signal que vous souhaitez intercepter. L'argument flags est un ensemble d'indicateurs qui déterminent l'environnement dans lequel le gestionnaire de signaux de l'application est appelé. L'argument after indique à gl_get_line() ce qu'il faut faire après le retour du gestionnaire de signaux de l'application, et errno_value indique à gl_get_line() ce qu'il faut définir pour errno s'il est invité à abandonner.

L'argument flags est un OU bit à bit de zéro ou plus des énumérateurs suivants :

  GLS_RESTORE_SIG  -  Restaure l'environnement de signal
                      de l'appelant pendant la gestion
                      du signal.
  GLS_RESTORE_TTY  -  Restaure les paramètres du terminal
                      de l'appelant pendant la gestion
                      du signal.
  GLS_RESTORE_LINE -  Déplace le curseur au début de la
                      ligne suivant la ligne d'entrée
                      avant d'appeler le gestionnaire de
                      signaux de l'application.
  GLS_REDRAW_LINE  -  Redessine la ligne d'entrée au retour
                      du gestionnaire de signaux de
                      l'application.
  GLS_UNBLOCK_SIG  -  Normalement, si le programme appelant
                      a un signal bloqué (man sigprocmask),
                      gl_get_line() n'intercepte pas ce
                      signal. Cet indicateur demande à
                      gl_get_line() d'intercepter le
                      signal et de le débloquer pendant
                      la durée de l'appel à
                      gl_get_line().
  GLS_DONT_FORWARD -  Si cet indicateur est inclus, le signal
                      ne sera pas transmis au gestionnaire
                      de signaux du programme appelant.

Deux combinaisons d'indicateurs couramment utiles sont également énumérées comme suit :

  GLS_RESTORE_ENV   = GLS_RESTORE_SIG | GLS_RESTORE_TTY |
                      GLS_REDRAW_LINE
  GLS_SUSPEND_INPUT = GLS_RESTORE_ENV | GLS_RESTORE_LINE

Si votre gestionnaire de signaux, ou le gestionnaire de signaux par défaut du système pour ce signal, si vous ne l'avez pas remplacé, n'écrit jamais sur le terminal, ni ne suspend ou ne termine le programme appelant, alors vous pouvez sans risque définir l'argument flags sur 0.

Si votre gestionnaire de signaux écrit toujours sur le terminal, lit depuis celui-ci, ou suspend ou termine le programme, vous devez spécifier l'argument flags comme GL_SUSPEND_INPUT, afin que :

1. Le curseur ne soit pas laissé au milieu de la ligne
   d'entrée.
2. L'utilisateur puisse taper une entrée et que celle-ci
   soit échoée.
3. Vous n'ayez pas besoin de terminer chaque ligne de sortie
   avec \r\n, au lieu de seulement \n.

La combinaison GL_RESTORE_ENV est identique à GL_SUSPEND_INPUT, sauf qu'elle ne déplace pas le curseur, et si votre gestionnaire de signaux ne lit ni n'écrit quoi que ce soit sur le terminal, l'utilisateur ne verra aucune indication visible qu'un signal a été capturé. Cela peut être utile si vous avez un gestionnaire de signaux qui n'écrit que ponctuellement sur le terminal, où l'utilisation de GL_SUSPEND_LINE entraînerait une duplication inutile de la ligne d'entrée lorsque rien n'a été écrit sur le terminal. Un tel gestionnaire de signaux, lorsqu'il écrit sur le terminal, doit s'assurer de commencer une nouvelle ligne au début de sa première écriture, en écrivant une nouvelle ligne avant de retourner. Si le signal arrive pendant que l'utilisateur est en train de saisir une ligne qui n'occupe qu'une seule ligne de terminal, ou si le curseur se trouve sur la dernière ligne de terminal d'une ligne d'entrée plus longue, cela aura le même effet que GL_SUSPEND_INPUT. Sinon, il commencera à écrire sur une ligne qui contient déjà une partie de la ligne d'entrée affichée. Cela ne cause aucun problème, mais cela peut être un peu disgracieux, c'est pourquoi la combinaison GL_SUSPEND_INPUT est préférable si vous savez que vous allez toujours écrire sur le terminal.

L'argument after, qui détermine ce que gl_get_line() fait après le retour du gestionnaire de signaux de l'application (s'il retourne), peut prendre l'une des valeurs suivantes :

  GLS_RETURN   - Retourne la ligne d'entrée complétée, comme
                 si l'utilisateur avait appuyé sur la touche
                 Entrée.
  GLS_ABORT    - Provoque l'abandon de gl_get_line().
                 Lorsque cela se produit, gl_get_line()
                 retourne NULL, et un appel ultérieur à
                 gl_return_status() retournera
                 GLR_SIGNAL. Notez que si l'application
                 a besoin que errno ait toujours une
                 valeur significative lorsque
                 gl_get_line() retourne NULL,
                 la fonction de rappel doit définir
                 errno de manière appropriée.
  GLS_CONTINUE - Reprend l'édition de la ligne de commande.

L'argument errno_value est destiné à être combiné avec l'option GLS_ABORT, indiquant à gl_get_line() ce qu'il faut définir pour la variable standard errno avant de retourner NULL au programme appelant. Il peut cependant aussi être utilisé avec l'option GL_RETURN, au cas où vous souhaiteriez avoir un moyen de distinguer une ligne d'entrée saisie à l'aide de la touche Entrée, et une autre saisie par la réception d'un signal.

GESTION FIABLE DES SIGNALS

La gestion des signaux est étonnamment difficile à faire de manière fiable sans conditions de concurrence. Dans gl_get_line(), beaucoup de soin a été apporté pour permettre aux applications d'effectuer une gestion fiable des signaux autour de gl_get_line(). Cette section explique comment en tirer parti.

Comme exemple des problèmes qui peuvent survenir si l'application n'est pas écrite correctement, imaginez qu'une application ait un gestionnaire de signal SIGINT qui définit un drapeau global. Supposons maintenant que l'application teste ce drapeau juste avant d'appeler gl_get_line(). Si un signal SIGINT est reçu dans la petite fenêtre de temps entre l'instruction qui teste la valeur de ce drapeau et l'instruction qui appelle gl_get_line(), alors gl_get_line() ne verra pas le signal et ne sera pas interrompu. En conséquence, l'application ne pourra pas répondre au signal tant que l'utilisateur n'aura pas fini de saisir la ligne d'entrée et que gl_get_line() ne sera pas retourné. Selon l'application, cela peut ou peut ne pas être une catastrophe, mais au moins cela dérouterait l'utilisateur.

La manière d'éviter de tels problèmes est de faire ce qui suit.

1. Si nécessaire, utilisez la fonction gl_trap_signal() pour configurer gl_get_line() afin qu'il abandonne lors de la capture de signaux importants.

2. Configurez gl_get_line() de telle sorte que si l'un des signaux qu'il intercepte est bloqué lorsque gl_get_line() est appelé, il soit automatiquement débloqué pendant les moments où gl_get_line() attend des E/S. Cela peut être fait soit sur une base par signal, en appelant la fonction gl_trap_signal() et en spécifiant l'attribut GLS_UNBLOCK du signal, soit globalement en appelant la fonction gl_catch_blocked().

     void gl_catch_blocked(GetLine *gl);

Cette fonction ajoute simplement l'attribut GLS_UNBLOCK à tous les signaux qu'elle est actuellement configurée pour intercepter.

3. Juste avant d'appeler gl_get_line(), bloquez la remise de tous les signaux que gl_get_line() est configuré pour intercepter. Cela peut être fait en utilisant la fonction POSIX sigprocmask() en conjonction avec la fonction gl_list_signals().

      int gl_list_signals(GetLine *gl, sigset_t *set);

Cette fonction retourne l'ensemble des signaux qu'elle est actuellement configurée pour intercepter dans l'argument set, qui est dans le format requis par sigprocmask().

4. Dans l'exemple, on testerait maintenant le drapeau global que le gestionnaire de signaux définit, sachant qu'il n'y a plus de danger que ce drapeau soit à nouveau défini avant que gl_get_line() ne débloque ses signaux lors des E/S.

5. Finalement, gl_get_line() retourne, soit parce qu'un signal a été capturé, qu'une erreur s'est produite, ou que l'utilisateur a terminé la saisie de sa ligne.

6. On vérifierait alors à nouveau le drapeau de signal global, et s'il est défini, on y répondrait et on le mettrait à zéro.

7. Utiliser sigprocmask() pour débloquer les signaux qui ont été bloqués à l'étape 3.

La même technique peut être utilisée autour de certaines fonctions POSIX sensibles aux signaux, telles que sigsetjmp() et sigsuspend(), et en particulier, la première de ces deux fonctions peut être utilisée en conjonction avec siglongjmp() pour implémenter une gestion des signaux sans conditions de concurrence autour d'autres appels système de longue durée. La manière de le faire est expliquée ensuite, en montrant comment gl_get_line() parvient à intercepter de manière fiable les signaux autour des appels à des fonctions comme read() et select() sans conditions de concurrence.

La première chose que gl_get_line() fait, à chaque fois qu'il est appelé, est d'utiliser la fonction POSIX sigprocmask() pour bloquer la livraison de tous les signaux qu'il est actuellement configuré pour intercepter. Ceci est redondant si l'application les a déjà bloqués, mais cela ne fait pas de mal. Il annule cette étape juste avant de retourner.

Chaque fois que gl_get_line() a besoin d'appeler read() ou select() pour attendre une entrée de l'utilisateur, il appelle d'abord la fonction POSIX sigsetjmp(), en s'assurant de spécifier une valeur non nulle pour son argument savesigs. La raison de ce dernier argument deviendra claire sous peu.

Si sigsetjmp() retourne zéro, gl_get_line() fait alors ce qui suit.

a. Il utilise la fonction POSIX sigaction() pour enregistrer
   un gestionnaire de signaux temporaire pour tous les signaux
   qu'il est configuré pour intercepter. Ce gestionnaire de
   signaux fait deux choses.
   1. Il enregistre le numéro du signal reçu dans une variable
      au niveau du fichier.
   2. Il appelle ensuite la fonction POSIX siglongjmp()
      en utilisant le tampon passé à sigsetjmp() comme
      premier argument, et une valeur non nulle comme second
      argument.
   Lorsque ce gestionnaire de signaux est enregistré, le membre
   sa_mask de l'argument struct sigaction act de
   l'appel à sigaction() est configuré pour contenir tous
   les signaux que gl_get_line() intercepte. Cela garantit
   qu'un seul signal sera capturé à la fois par notre
   gestionnaire de signaux, ce qui garantit que plusieurs
   instances de notre gestionnaire de signaux ne se marchent
   pas sur les pieds.
b. Maintenant que le gestionnaire de signaux est configuré,
   gl_get_line() débloque tous les signaux qu'il est
   configuré pour intercepter.
c. Il appelle ensuite les appels système read() ou
   select() pour attendre l'entrée du clavier.
d. Si cet appel système retourne (c'est-à-dire qu'aucun signal
   n'est reçu), gl_get_line() bloque à nouveau la
   livraison des signaux d'intérêt.
e. Il rétablit ensuite les gestionnaires de signaux qui ont
   été déplacés par celui qui vient d'être installé.

Alternativement, si sigsetjmp() retourne une valeur non nulle, cela signifie que o

l'un des signaux piégés a été capturé pendant l'exécution des étapes ci-dessus. Lorsque cela se produit, gl_get_line() fait ce qui

suit.

Tout d'abord, notez que lorsqu'un appel à siglongjmp() provoque le retour de sigsetjmp(), à condition que l'argument savesigs de sigsetjmp() soit non nul, comme spécifié ci-dessus, le masque de traitement des signaux est restauré à l'état dans lequel il se trouvait lorsque sigsetjmp() a été appelé. C'est la différence importante entre sigsetjmp() et l'ancien et problématique setjmp(), et c'est l'ingrédient essentiel qui rend possible l'évitement des conditions de course dans la gestion des signaux. Grâce à cela, nous sommes garantis que tous les signaux que nous avons bloqués avant d'appeler sigsetjmp() sont de nouveau bloqués dès que n'importe quel signal est capturé. TAPEZ

Lors de la saisie d'informations sensibles, comme des mots de passe, il est préférable de ne pas faire écho sur le terminal du texte que vous saisissez. De plus, un tel texte ne devrait pas être enregistré dans la liste d'historique, car quelqu'un trouvant votre terminal sans surveillance pourrait alors le rappeler, ou quelqu'un fouillant dans vos répertoires pourrait le voir dans votre fichier d'historique. En gardant cela à l'esprit, la fonction gl_echo_mode() vous permet d'activer et de désactiver l'affichage et l'archivage de tout texte qui est saisi par la suite dans les appels à gl_get_li

ne(). 
  int gl_echo_mode(GetLine *gl, int enable)
;

L'argument enable spécifie si le texte saisi doit être visible ou non. S'il est 0, alors les lignes saisies par la suite ne seront pas visibles sur le terminal et ne seront pas enregistrées dans la liste d'historique. S'il est 1, alors les lignes saisies par la suite seront affichées au fur et à mesure de leur saisie, et à condition que l'historique n'ait pas été désactivé via un appel à gl_toggle_history(), elles seront également archivées dans la liste d'historique. Enfin, si l'argument enable est -1, alors le mode d'écho est laissé inchangé, ce qui vous permet d'interroger le paramètre actuel de manière non destructive via la valeur de retour. Dans tous les cas, la valeur de retour de la fonction est 0 si l'écho était désactivé avant l'appel de la fonction, et 1 s'il était

activé.

tabulation complétera votre préfixe de manière invisible aussi lo
in que possible, les complétions ambiguës ne seront pas affichées.

REQUÊTES À CARACTÈRE

UNIQUE

Utiliser gl_get_line() pour demander à l'utilisateur une réponse à un seul caractère est incommode pour l'utilisateur, car il doit appuyer sur la touche entrée ou retour avant que le caractère qu'il a tapé ne soit renvoyé au programme. C'est pourquoi la fonction gl_query_char() a été fournie pour des requêtes à un seul caractère comme

celle-ci. 
  int gl_query_char(GetLine *gl, const char *prompt,
                    char defchar)
;

Cette fonction affiche l'invite spécifiée au début d'une nouvelle ligne et attend que l'utilisateur tape un caractère. Lorsque l'utilisateur tape un caractère, gl_query_char() l'affiche à droite de l'invite, passe à la ligne suivante, puis renvoie le caractère au programme appelant. La valeur de retour de la fonction est le caractère qui a été tapé. Si la lecture a dû être interrompue pour une raison quelconque, EOF est renvoyé à la place. Dans ce dernier cas, l'application peut appeler gl_return_status(), précédemment documenté, pour savoir ce qui s'est mal passé. Cela pourrait, par exemple, avoir été la réception d'un signal, ou le déclenchement du minuteur d'inactivité

optionnel.

Si l'utilisateur appuie simplement sur entrée, la valeur de l'argument defchar est substituée. Cela signifie que lorsque l'utilisateur appuie sur nouvelle ligne ou retour, le caractère spécifié dans defchar est affiché après l'invite, comme si l'utilisateur l'avait tapé, ainsi que renvoyé à l'application appelante. Si un tel remplacement n'est pas important, passez simplement '0 comme valeur de defchar

.

Si le caractère saisi est un caractère non imprimable, il est affiché symboliquement. Par exemple, contrôle-A est affiché comme ^A, et les caractères au-delà de 127 sont affichés en octal, précédés d'une barre oblique

inverse.

Comme pour gl_get_line(), l'écho du caractère saisi peut être désactivé à l'aide de la fonction gl_echo_mode()

.

Si le processus appelant est suspendu pendant qu'il attend que l'utilisateur tape sa réponse, le curseur est déplacé sur la ligne suivant la ligne d'invite, puis lorsque le processus reprend, l'invite est réaffichée, et gl_query_char() reprend l'attente que l'utilisateur tape un

caractère.

Notez qu'en mode serveur non bloquant, (voir gl_io_mode(3)), si une ligne de saisie incomplète est en cours de lecture lorsque gl_query_char() est appelé, la ligne de saisie partielle est abandonnée et effacée du terminal avant que la nouvelle invite ne soit affichée. L'appel suivant à gl_get_line() commencera donc

à éditer une n
ouvelle ligne.

BRUTS

Cela signifie qu'elle peut être appelée non seulement entre les appels à gl_get_line(), mais aussi depuis des fonctions de rappel que l'application a enregistrées pour être appelées par gl_get_li

En cas de succès, la valeur de retour de gl_read_char() est le caractère qui a été lu. AFFICHAGE DYNAMIQUE DE TEXTE

Entre les appels à gl_get_line(), la fonction gl_display_text() fournit un moyen pratique d'afficher des paragraphes de texte, justifiés à gauche et répartis sur une ou plusieurs lignes du terminal selon les contraintes de la largeur actuelle du terminal. Des exemples d'utilisation de cette fonction se trouvent dans les programmes de démonstration, où elle est utilisée pour afficher des introductions. Dans ces exemples, l'utilisation avancée de préfixes, de suffixes et de lignes de remplissage optionnels pour dessiner une boîte autour du texte est également illustrée.

  int gl_display_text(GetLine *gl, int indentation,
                      const char *prefix,
                      const char *suffix, int fill_char,
                      int def_width, int start,
                      const char *string);

Si gl n'est pas actuellement connecté à un terminal, par exemple si la sortie d'un programme utilisant gl_get_line() est dirigée vers un autre programme ou redirigée vers un fichier, alors la valeur du paramètre def_width est utilisée comme largeur du terminal.

L'argument indentation spécifie le nombre de caractères à utiliser pour indenter chaque ligne de sortie. L'argument fill_char spécifie le caractère qui sera utilisé pour effectuer cette indentation.

L'argument prefix peut être soit NULL, soit une chaîne à placer au début de chaque nouvelle ligne (après toute indentation). De même, l'argument suffix peut être soit NULL, soit une chaîne à placer à la fin de chaque ligne. Le suffixe est placé au ras du bord droit du terminal, et tout espace entre son premier caractère et le dernier mot de cette ligne est rempli avec le caractère spécifié via l'argument fill_char. Normalement, le caractère de remplissage est un espace.

L'argument start indique à gl_display_text() combien de caractères ont déjà été écrits sur la ligne de terminal actuelle, et indique donc l'index de colonne de départ du curseur. Comme la valeur de retour de gl_display_text() est l'index de colonne de fin du curseur, en passant la valeur de retour d'un appel à l'argument start de l'appel suivant, un paragraphe qui est divisé entre plusieurs chaînes peut être composé en appelant gl_display_text() pour chaque portion successive du paragraphe. Notez que des caractères de nouvelle ligne littéraux sont nécessaires à la fin de chaque paragraphe pour forcer le démarrage d'une nouvelle ligne.

En cas d'erreur, gl_display_text() renvoie -1.

Sauf indication contraire, les fonctions de rappel, telles que les fonctions de rappel d'achèvement de tabulation et les fonctions de rappel d'événements, ne doivent pas appeler de fonctions de ce module. Les fonctions suivantes, cependant, sont conçues spécifiquement pour être utilisées par des fonctions de rappel.

Appeler la fonction gl_replace_prompt() depuis un rappel indique à gl_get_line() d'afficher une invite différente lorsque le rappel se termine. Sauf en mode serveur non bloquant, elle n'a aucun effet lorsqu'elle est utilisée entre les appels à gl_get_line(). En mode serveur non bloquant (voir la page de manuel gl_io_mode(3), lorsqu'elle est utilisée entre deux appels à gl_get_line() qui opèrent sur la même ligne d'entrée, la ligne d'entrée actuelle sera redessinée avec la nouvelle invite lors du prochain appel à gl_get_line().

JEUX DE CARACTÈRES INTERNATIONAUX

Depuis la version 1.4.0 de libtecla, gl_get_line() est compatible 8 bits. Cela signifie que tous les caractères 8 bits imprimables dans la locale actuelle de l'utilisateur sont maintenant affichés verbatim et inclus dans la ligne d'entrée retournée. En supposant que le programme appelant contient correctement un appel comme suit,

  setlocale(LC_CTYPE, "");

alors la locale actuelle est déterminée par la première des variables d'environnement LC_CTYPE, LC_ALL et LANG qui contient un nom de locale valide. Si aucune de ces variables n'est définie, ou si le programme néglige d'appeler setlocale, alors la locale par défaut C est utilisée, qui est le ASCII 7 bits américain. Sur la plupart des plateformes de type Unix, vous pouvez obtenir une liste des locales valides en tapant la commande :

  locale -a

à l'invite du shell. Une documentation supplémentaire sur la façon dont l'utilisateur peut utiliser cela pour saisir des caractères internationaux se trouve dans la page de manuel tecla(7).

SÉCURITÉ DES THREADS

Dans un programme multithread, vous devez utiliser la version libtecla_r.a de la bibliothèque. Celle-ci utilise des versions réentrantes des fonctions système, lorsque disponibles. Malheureusement, ni terminfo ni termcap n'ont été conçus pour être réentrantes, vous ne pouvez donc pas utiliser en toute sécurité les fonctions du module getline dans plusieurs threads (vous pouvez utiliser les modules distincts d'expansion de fichiers et de complétion de mots dans plusieurs threads, voir les pages de manuel correspondantes pour les détails). Cependant, en raison de l'utilisation de fonctions POSIX réentrantes pour la recherche de répertoires personnels, etc., il est sûr d'utiliser ce module à partir d'un seul thread d'un programme multithread, à condition que vos autres threads n'utilisent aucune fonction termcap ou terminfo.
