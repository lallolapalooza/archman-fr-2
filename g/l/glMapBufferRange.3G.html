NOM

glMapBufferRange, glMapNamedBufferRange - mapper tout ou partie du magasin de données d'un objet tampon dans l'espace d'adressage du client

SPÉCIFICATION

void *glMapBufferRange(GLenum target, GLintptr offset, GLsizeiptr length, GLbitfield access);

void *glMapNamedBufferRange(GLuint buffer, GLintptr offset, GLsizeiptr length, GLbitfield access);

PARAMÈTRES

target

Spécifie la cible à laquelle l'objet tampon est lié pour glMapBufferRange, qui doit être l'une des cibles de liaison de tampon du tableau suivant:
Cible de liaison de tampon Objectif
GL_ARRAY_BUFFER Attributs de sommet
GL_ATOMIC_COUNTER_BUFFER Stockage de compteurs atomiques
GL_COPY_READ_BUFFER Source de copie de tampon
GL_COPY_WRITE_BUFFER Destination de copie de tampon
GL_DISPATCH_INDIRECT_BUFFER Commandes de dispatch de calcul indirectes
GL_DRAW_INDIRECT_BUFFER Arguments de commande indirects
GL_ELEMENT_ARRAY_BUFFER Indices du tableau de sommets
GL_PIXEL_PACK_BUFFER Cible de lecture de pixel
GL_PIXEL_UNPACK_BUFFER Source de données de texture
GL_QUERY_BUFFER Tampon de résultat de requête
GL_SHADER_STORAGE_BUFFER Stockage en lecture/écriture pour les shaders
GL_TEXTURE_BUFFER Tampon de données de texture
GL_TRANSFORM_FEEDBACK_BUFFER Tampon de retour de transformation
GL_UNIFORM_BUFFER Stockage de bloc uniforme

buffer

Spécifie le nom de l'objet tampon pour glMapNamedBufferRange.

offset

Spécifie le décalage de départ dans le tampon de la plage à mapper.

length

Spécifie la longueur de la plage à mapper.

access

Spécifie une combinaison d'indicateurs d'accès indiquant l'accès souhaité à la plage mappée.

DESCRIPTION

glMapBufferRange et glMapNamedBufferRange mappent tout ou partie du magasin de données d'un objet tampon spécifié dans l'espace d'adressage du client. offset et length indiquent la plage de données dans l'objet tampon qui doit être mappée, en termes d'unités machine de base. access est un champ de bits contenant des indicateurs qui décrivent le mappage demandé. Ces indicateurs sont décrits ci-dessous.

Un pointeur vers le début de la plage mappée est retourné une fois que toutes les opérations en attente sur l'objet tampon sont terminées, et peut être utilisé pour modifier et/ou interroger la plage correspondante du magasin de données selon les bits d'indicateur suivants définis dans access :

•GL_MAP_READ_BIT indique que le pointeur retourné peut être utilisé pour lire les données de l'objet tampon. Aucune erreur GL n'est générée si le pointeur est utilisé pour interroger un mappage qui exclut cet indicateur, mais le résultat est indéfini et des erreurs système (y compris potentiellement la terminaison du programme) peuvent survenir.
•GL_MAP_WRITE_BIT indique que le pointeur retourné peut être utilisé pour modifier les données de l'objet tampon. Aucune erreur GL n'est générée si le pointeur est utilisé pour modifier un mappage qui exclut cet indicateur, mais le résultat est indéfini et des erreurs système (y compris potentiellement la terminaison du programme) peuvent survenir.
•GL_MAP_PERSISTENT_BIT indique que le mappage doit être effectué de manière persistante et que le client a l'intention de conserver et d'utiliser le pointeur retourné lors des opérations GL ultérieures. Il n'y a pas d'erreur à appeler des commandes de dessin (rendre) pendant que des tampons sont mappés à l'aide de cet indicateur. Il y a une erreur si cet indicateur est spécifié si le magasin de données du tampon n'a pas été alloué via un appel à la commande glBufferStorage() dans laquelle le GL_MAP_PERSISTENT_BIT a également été défini.
•GL_MAP_COHERENT_BIT indique qu'un mappage persistant doit également être cohérent. Les mappages cohérents garantissent que l'effet des écritures dans le magasin de données d'un tampon par le client ou le serveur deviendra éventuellement visible pour l'autre sans intervention supplémentaire de l'application. En l'absence de cet indicateur, les mappages persistants ne sont pas cohérents et les plages modifiées du magasin de tampon doivent être explicitement communiquées au GL, soit en démappant le tampon, soit via un appel à glFlushMappedBufferRange() ou glMemoryBarrier().

Les bits d'indicateurs *optionnels* suivants dans access peuvent être utilisés pour modifier le mappage :

•GL_MAP_INVALIDATE_RANGE_BIT indique que le contenu précédent de la plage spécifiée peut être rejeté. Les données dans cette plage sont indéfinies à l'exception des données écrites ultérieurement. Aucune erreur GL n'est générée si les opérations GL ultérieures accèdent à des données non écrites, mais le résultat est indéfini et des erreurs système (y compris potentiellement la terminaison du programme) peuvent survenir. Cet indicateur ne peut pas être utilisé en combinaison avec GL_MAP_READ_BIT.
•GL_MAP_INVALIDATE_BUFFER_BIT indique que le contenu précédent de l'ensemble du tampon peut être rejeté. Les données dans l'ensemble du tampon sont indéfinies à l'exception des données écrites ultérieurement. Aucune erreur GL n'est générée si les opérations GL ultérieures accèdent à des données non écrites, mais le résultat est indéfini et des erreurs système (y compris potentiellement la terminaison du programme) peuvent survenir. Cet indicateur ne peut pas être utilisé en combinaison avec GL_MAP_READ_BIT.
•GL_MAP_FLUSH_EXPLICIT_BIT indique qu'une ou plusieurs sous-plages discrètes du mappage peuvent être modifiées. Lorsque cet indicateur est défini, les modifications apportées à chaque sous-plage doivent être explicitement vidées en appelant glFlushMappedBufferRange(). Aucune erreur GL n'est générée si une sous-plage du mappage est modifiée et non vidée, mais les données dans la sous-plage correspondante du tampon sont indéfinies. Cet indicateur ne peut être utilisé qu'en conjonction avec GL_MAP_WRITE_BIT. Lorsque cette option est sélectionnée, le vidage est strictement limité aux régions qui sont explicitement indiquées avec des appels à glFlushMappedBufferRange() avant le démappage ; si cette option n'est pas sélectionnée, glUnmapBuffer() videra automatiquement toute la plage mappée lorsqu'elle sera appelée.
•GL_MAP_UNSYNCHRONIZED_BIT indique que le GL ne doit pas tenter de synchroniser les opérations en attente sur le tampon avant de retourner de glMapBufferRange ou glMapNamedBufferRange. Aucune erreur GL n'est générée si les opérations en attente qui utilisent ou modifient le tampon chevauchent la région mappée, mais le résultat de telles opérations précédentes et ultérieures est indéfini.

Si une erreur se produit, un pointeur NULL est retourné.

Si aucune erreur ne se produit, le pointeur retourné reflétera une allocation alignée sur la valeur de GL_MIN_MAP_BUFFER_ALIGNMENT unités machine de base. Soustraire offset de ce pointeur retourné produira toujours un multiple de la valeur de GL_MIN_MAP_BUFFER_ALIGNMENT.

Les valeurs de pointeur retournées ne peuvent pas être passées en paramètres aux commandes GL. Par exemple, elles ne peuvent pas être utilisées pour spécifier des pointeurs de tableau, ni pour spécifier ou interroger des données d'image de pixel ou de texture ; de telles actions produisent des résultats indéfinis, bien que les implémentations puissent ne pas vérifier un tel comportement pour des raisons de performance.

Les mappages vers les magasins de données des objets tampons peuvent avoir des caractéristiques de performance non standard. Par exemple, de tels mappages peuvent être marqués comme régions de mémoire non cachables, et dans ce cas, en lire peut être très lent. Pour garantir des performances optimales, le client doit utiliser le mappage d'une manière cohérente avec les valeurs de GL_BUFFER_USAGE pour l'objet tampon et de access. Utiliser un mappage d'une manière incohérente avec ces valeurs est susceptible d'être de plusieurs ordres de grandeur plus lent que d'utiliser la mémoire normale.

NOTES

L'alignement du pointeur retourné n'est garanti que si la version de la version GL est 4.2 ou supérieure. De plus, la cible GL_ATOMIC_COUNTER_BUFFER n'est acceptée que si la version GL est 4.2 ou supérieure.

Si le mappage est créé avec GL_MAP_PERSISTENT_BIT, le comportement du vidage est différent. Dans ce cas, les appels à glFlushMappedBufferRange() sont nécessaires pour synchroniser les modifications du côté client avec le GPU. Si GL_MAP_COHERENT_BIT est également défini, le système s'assure que les modifications sont visibles par le GPU sans vidage explicite.

Si un objet tampon est créé avec glBufferStorage() avec GL_MAP_PERSISTENT_BIT défini, il n'est pas possible de le mapper avec glMapBuffer().

Les requêtes de mappage à l'aide de flags tels que GL_MAP_INVALIDATE_RANGE_BIT ou GL_MAP_INVALIDATE_BUFFER_BIT ne peuvent pas être combinées avec GL_MAP_READ_BIT.

Les modifications apportées aux tampons mappés via GL_MAP_WRITE_BIT sans GL_MAP_FLUSH_EXPLICIT_BIT sont automatiquement vidées lors de l'appel à glUnmapBuffer().

glBufferData(3G), glBufferStorage(3G), glFlushMappedBufferRange(3G), glMapBuffer(3G), glMemoryBarrier(3G), glUnmapBuffer(3G)

ERREURS

GL_INVALID_ENUM est généré par glMapBufferRange si target n'est pas l'une des cibles de liaison de tampon listées ci-dessus.

GL_INVALID_OPERATION est généré par glMapBufferRange si zéro est lié à target.

GL_INVALID_OPERATION est généré par glMapNamedBufferRange si buffer n'est pas le nom d'un objet tampon existant.

GL_INVALID_VALUE est généré si offset ou length est négatif, si $offset + length$ est supérieur à la valeur de GL_BUFFER_SIZE pour l'objet tampon, ou si access a des bits définis autres que ceux définis ci-dessus.

GL_INVALID_OPERATION est généré pour l'une des conditions suivantes :

•length est zéro.
•L'objet tampon est déjà dans un état mappé.
Ni GL_MAP_READ_BIT ni GL_MAP_WRITE_BIT n'est défini.
•GL_MAP_READ_BIT est défini et l'un de GL_MAP_INVALIDATE_RANGE_BIT, GL_MAP_INVALIDATE_BUFFER_BIT ou GL_MAP_UNSYNCHRONIZED_BIT est défini.
•GL_MAP_FLUSH_EXPLICIT_BIT est défini et GL_MAP_WRITE_BIT n'est pas défini.
•L'un de GL_MAP_READ_BIT, GL_MAP_WRITE_BIT, GL_MAP_PERSISTENT_BIT, ou GL_MAP_COHERENT_BIT est défini, mais le même bit n'est pas inclus dans les indicateurs de stockage du tampon.

Aucune erreur n'est générée si la mémoire en dehors de la plage mappée est modifiée ou interrogée, mais le résultat est indéfini et des erreurs système (possiblement incluant l'interruption du programme) peuvent survenir.

INTERROGATIONS ASSOCIÉES

glGet() avec pname GL_MIN_MAP_BUFFER_ALIGNMENT. La valeur doit être une puissance de deux qui est au moins 64.
