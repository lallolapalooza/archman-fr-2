L

a

fonction gl_get_line() fait partie de la bibliothèque tecla (voir la page man libtecla(3)). Si l'utilisateur tape sur un terminal, chaque appel lui demande une ligne de saisie, puis fournit des fonctionnalités d'édition interactives, similaires à celles du shell unix tcsh. En plus de l'édition simple de ligne de commande, elle prend en charge le rappel des lignes de commande précédemment saisies, l'achèvement par TAB des noms de fichiers et l'expansion en ligne des caractères génériques des noms de fichiers. La documentation des fonctionnalités d'édition de ligne de commande au niveau utilisateur et de toutes les options de configuration utilisateur se trouve dans la page man tecla(7). Cette page man concerne la documentation destinée aux programmeurs souhaitant utiliser cette bibliothèque dans leur application. UN E

L'EXEMPLE

Les descriptions des fonctions utilisées dans l'exemple sont les suivantes

  GetLine *new_GetLine(size_t linelen, size_t

Cette fonction crée les ressources utilisées par la fonction gl_get_line() et renvoie un pointeur opaque vers l'objet qui les contient. La longueur maximale d'une ligne de saisie est spécifiée via l'argument linelen, et le nombre d'octets à allouer pour stocker les lignes d'historique est défini par l'argument histlen. Les lignes d'historique sont stockées bout à bout dans un tampon unique de cette taille. Notez que cela signifie que le nombre de lignes d'historique pouvant être stockées à un moment donné dépend des longueurs des lignes individuelles. Si vous souhaitez fixer une limite supérieure au nombre de lignes pouvant être stockées, voir la fonction gl_limit_history() décrite plus loin. Si vous ne voulez pas d'historique du tout, spécifiez histlen comme zéro, et aucun tampon d'historique ne sera

alloué.

En cas d'erreur, un message est imprimé sur stderr et NULL est

renvoyé.

*gl)

Cette fonction supprime les ressources qui ont été renvoyées par un appel précédent à new_GetLine(). Elle renvoie toujours NULL (c'est-à-dire un objet supprimé). Elle ne fait rien si l'argument gl est NULL

  char *gl_get_line(GetLine *gl, const char *prompt,

;

La fonction gl_get_line() peut être appelée un nombre quelconque de fois pour lire la saisie de l'utilisateur. L'argument gl doit avoir été précédemment renvoyé par un appel à new_GetLine(). L'argument prompt doit être une chaîne normale terminée par NUL, spécifiant l'invite à présenter à l'utilisateur. Par défaut, les invites sont affichées littéralement, mais si elles sont activées avec la fonction gl_prompt_style() (voir plus loin), les invites peuvent contenir des directives pour souligner, passer à et depuis des polices en gras, ou activer et désactiver la mise en

évidence.

Si vous souhaitez spécifier le contenu initial de la ligne, pour que l'utilisateur la modifie, transmettez la chaîne souhaitée via l'argument start_line. Vous pouvez ensuite spécifier le caractère de cette ligne où le curseur est initialement positionnéd over, using the start_pos argument. Cela devrait être -1 si vous voulez que le curseur suive le dernier caractère de la ligne de départ. Si vous ne voulez pas précharger la ligne de cette manière, envoyez start_line comme NULL, et définissez start_pos à -1. Notez que le pointeur de ligne retourné par un appel à gl_get_line() peut être transmis à l'appel suivant à gl_get_line() via le start_line. Cela permet à l'application de prendre la dernière ligne saisie, et si elle contient une erreur, de la présenter à nouveau à l'utilisateur pour réédition, avec le curseur initialement positionné à l'endroit où l'erreur a été

rencontrée.

La gl_get_line() fonction retourne un pointeur vers la ligne saisie par l'utilisateur, ou NULL en cas d'erreur ou à la fin de l'entrée. Le pointeur retourné fait partie de l'objet ressource gl spécifié, et ne devrait donc pas être free'd par l'appelant, ni supposé invariable d'un appel à l'autre. Lors de la lecture depuis un utilisateur sur un terminal, il y aura toujours un caractère de nouvelle ligne à la fin de la ligne retournée. Lorsque l'entrée standard provient d'un pipe ou d'un fichier, il y aura de même une nouvelle ligne, sauf si la ligne d'entrée était trop longue pour être stockée dans le tampon interne. Dans ce dernier cas, vous devriez appeler gl_get_line() à nouveau pour lire le reste de la ligne. Notez que ce comportement rend gl_get_line() similaire à fgets(). En fait, lorsque stdin n'est pas connecté à un terminal,gl_get_line() appelle simplement fget

s(
).

SOURCES DE CONFIGURATION

ALTERNATIVES

Comme mentionné ci-dessus, par défaut les utilisateurs ont la possibilité de configurer le comportement de gl_get_line() via un fichier de configuration appelé .teclarc dans leur répertoire personnel. Le fait que toutes les applications partagent ce même fichier de configuration est à la fois un avantage et un inconvénient. Dans la plupart des cas c'est un avantage, car cela encourage l'uniformité, et libère l'utilisateur de devoir configurer chaque application séparément. Dans certaines applications, cependant, ce seul moyen de configuration est un problème. C'est particulièrement vrai pour les logiciels embarqués, où il n'y a pas de système de fichiers pour lire un fichier de configuration, et aussi dans les applications où un choix radicalement différent de raccourcis clavier est nécessaire pour émuler une interface clavier héritée. Pour prendre en charge de tels cas, la fonction suivante permet à l'application de contrôler d'où les informations de configuration sont

lues. 
  int gl_configure_getline(GetLine *gl,
                           const char *app_string,
                           const char *app_file,
                           const char *user_file)
;

Elle permet aux commandes de configuration qui seraient normalement lues depuis le fichier ~/.teclarc d'un utilisateur, d'être lues depuis n'importe lequel ou aucun de : une chaîne, un fichier de configuration spécifique à l'application, et/ou un fichier de configuration spécifique à l'utilisateur. Si cette fonction est appelée avant le premier appel à gl_get_line(), le comportement par défaut de lecture de ~/.teclarc lors du premier appel à gl_get_line() est désactivé, donc toute configuration doit être réalisée en utilisant les sources de configuration spécifiées avec cette

fonction.

Si app_string != NULL, alors il est interprété comme une chaîne contenant une ou plusieurs commandes de configuration, séparées les unes des autres dans la chaîne par des caractères de nouvelle ligne intégrés. Si app_file != NULL alors il est interprété comme le chemin complet d'un fichier de configuration spécifique à l'application. Si user_file != NULL alors il est interprété comme le chemin complet d'un fichier de configuration spécifique à l'utilisateur, tel que ~/.teclarc. Par exemple, dans l'appel

suivant, 
  gl_configure_getline(gl, "edit-mode vi \n nobeep",
                           "/usr/share/myapp/teclarc",
                           "~/.teclarc")
;

l'argument app_string fait que l'application appelante démarre en mode d'édition vi, au lieu du mode emacs par défaut, et désactive l'utilisation de la cloche du terminal par la bibliothèque. Elle tente ensuite de lire les commandes de configuration à l'échelle du système depuis un fichier optionnel appelé /usr/share/myapp/teclarc, puis lit enfin les commandes de configuration spécifiques à l'utilisateur depuis un fichier .teclarc optionnel dans le répertoire personnel de l'utilisateur. Notez que les arguments sont listés par ordre de priorité croissant, avec le contenu de app_string potentiellement remplacé par des commandes dans app_file, et les commandes dans app_file potentiellement remplacées par des commandes dans user_file

.

Vous pouvez appeler cette fonction autant de fois que nécessaire, les résultats étant cumulatifs, mais notez que des copies de tout nom de fichier spécifié via le app_file et user_file sont enregistrés en interne pour une utilisation ultérieure par la fonction de liaison de touches read-init-files ; si vous prévoyez d'appeler cette fonction plusieurs fois, assurez-vous que le dernier appel spécifie les noms de fichiers que vous souhaitez relire lorsque l'utilisateur demande la relecture des fichiers de

configuration.

COMPLÉTION DE MOTS

PERSONNALISÉE

Si dans votre application, vous souhaitez que la complétion par TAB complète d'autres éléments en plus des noms de fichiers ou à leur place, vous pouvez organiser cela en enregistrant une fonction de rappel de complétion alternative, via un appel à la fonction gl_customize_c

ompletion(). 
  int gl_customize_completion(GetLine *gl, void *data,
                              CplMatchFn *match_fn)
;

L'argument data fournit un moyen à votre application de passer des informations arbitraires spécifiques à l'application à la fonction de rappel. Celles-ci sont transmises à la fonction de rappel à chaque fois qu'elle est appelée. Elle pourrait par exemple, pointer vers la table de symboles à partir de laquelle les complétions possibles doivent être recherchées. L'argument match_fn spécifie la fonction de rappel à appeler. Le type de fonction CplMatchFn est défini dans libtecla.h, tout comme une macro CPL_MATCH_FN() que vous pouvez utiliser pour déclarer et prototyper des fonctions de rappel. La déclaration et les responsabilités des fonctions de rappel sont décrites en profondeur dans la page de manuel cpl_complete_word(3)

.

En bref, la fonction de rappel est responsable de la recherche vers l'arrière dans la ligne d'entrée, en remontant depuis le point où l'utilisateur a appuyé sur TAB, pour trouver le début du mot en cours de complétion. Elle doit ensuite rechercher les complétions possibles de ce mot, et les enregistrer une par une dans l'objet WordCompletion qui lui est passé en argument, en appelant la fonction cpl_add_completion(). Si la fonction de rappel souhaite fournir la complétion de noms de fichiers en plus de ses propres complétions spécifiques, elle a la possibilité d'appeler elle-même la fonction de rappel de complétion de noms de fichiers intégrée. Ceci est également documenté dans la page de manuel cpl_complete_word(3)

.

Notez que si vous souhaitez que gl_get_line() renvoie la ligne d'entrée actuelle lorsqu'une complétion réussie a été effectuée, vous pouvez organiser cela lorsque vous appelez cpl_add_completion(), en faisant du dernier caractère du suffixe de continuation un caractère de nouvelle ligne. Si vous faites cela, la ligne d'entrée sera mise à jour pour afficher la complétion, avec tout suffixe de continuation jusqu'au caractère de nouvelle ligne, puis gl_get_line() renverra cette ligne

d'entrée.

Si, pour une raison quelconque, votre fonction de rappel doit écrire quelque chose sur le terminal, elle doit appeler gl_normal_io() avant de le faire. Cela commencera une nouvelle ligne après la ligne d'entrée actuellement en cours d'édition, rétablira l'E/S normale du terminal, et indiquera à gl_get_line() que la ligne d'entrée devra être red

essinée lorsque la fonctio
n de rappel retournera.

AJOUT D'ACTIONS DE

COMPLÉTION

Dans la section précédente, la capacité à personnaliser le comportement de la seule action de complétion par défaut, complete-word, a été décrite. Dans cette section, la capacité à installer des fonctions d'action supplémentaires, afin que différents types de complétion de mots puissent être liés à différentes séquences de touches, est décrite. Cela est réalisé en utilisant la fonction gl_completion_action()

. 
  int gl_completion_action(GetLine *gl,
                           void *data, CplMatchFn *match_fn,
                           int list_only, const char *name,
                           const char *keyseq)
;

Les arguments data et match_fn sont tels que décrits dans la page de manuel cpl_complete_word, et spécifient la fonction de rappel qui doit être invoquée pour identifier les complétions possibles. L'argument list_only détermine si l'action en cours de définition doit tenter de compléter le mot autant que possible dans la ligne d'entrée avant d'afficher toute complétion ambiguë possible, ou si elle doit simplement afficher la liste des complétions possibles sans toucher à la ligne d'entrée. La première option est sélectionnée en spécifiant une valeur de 0, et la seconde en spécifiant une valeur de 1. L'argument name spécifie le nom par lequel les fichiers de configuration et les futures invocations de cette fonction doivent se référer à l'action. Il doit s'agir soit du nom d'une action de complétion existante à modifier, soit d'un nouveau nom non utilisé pour une nouvelle action. Enfin, l'argument keyseq spécifie la séquence de touches par défaut à lier à l'action. Si c'est NULL, aucune nouvelle séquence de touches ne sera liée à

l'action.

Attention, pour que l'utilisateur puisse changer la séquence de touches liée aux actions installées de cette manière, lorsque vous appelez gl_completion_action() pour installer une action donnée pour la première fois, vous devez le faire entre l'appel à new_GetLine() et le premier appel à gl_get_line(). DÉFINITION D'ACTIONS

PERSONNALISÉES

Bien que les actions de liaison de touches intégrées soient suffisantes pour les besoins de la plupart des applications, une application spécialisée peut occasionnellement avoir besoin de définir une ou plusieurs actions personnalisées, liées à des séquences de touches spécifiques à l'application. Par exemple, une application de vente bénéficierait d'une séquence de touches affichant le nom de la pièce correspondant à un numéro de pièce précédant le curseur. Une telle fonctionnalité dépasse clairement le cadre des fonctions d'action intégrées. Ainsi, pour de tels cas particuliers, la fonction gl_register_action() est

fournie. 
  int gl_register_action(GetLine *gl, void *data,
			 GlActionFn *fn, const char *name,
			 const char *keyseq)
;

Cette fonction permet à l'application d'enregistrer une fonction externe, fn, qui sera ensuite appelée chaque fois que soit la séquence de touches spécifiée, keyseq, est saisie par l'utilisateur, soit l'utilisateur saisit toute autre séquence de touches qu'il lie ensuite à l'action spécifiée, name, dans son fichier de configuration. L'argument data peut être un pointeur vers n'importe quoi que l'application souhaite voir passer à la fonction d'action, fn, chaque fois que cette fonction est

invoquée.

La fonction d'action, fn, doit être déclarée en utilisant la macro suivante, qui est définie dans libtecl

a.h. 
  #define GL_ACTION_FN(fn) GlAfterAction (fn)(GetLine *gl, \
              void *data, int count, size_t curpos, \
              const char
*line)

Les arguments gl et data sont ceux qui ont été précédemment passés à gl_register_action() lorsque la fonction d'action a été enregistrée. L'argument count est un argument numérique que l'utilisateur a la possibilité de saisir en utilisant l'action digit-argument, avant d'invoquer l'action. Si l'utilisateur n'entre pas de nombre, alors l'argument count est défini à 1. Nominalement, cet argument est interprété comme un nombre de répétitions, signifiant que l'action doit être répétée ce nombre de fois. En pratique cependant, pour certaines actions, un nombre de répétitions a peu de sens. Dans de tels cas, les actions peuvent soit simplement ignorer l'argument count, soit utiliser sa valeur à une autre

fin.

Une copie de la ligne d'entrée actuelle est passée dans l'argument en lecture seule line. La position actuelle du curseur dans cette chaîne est donnée par l'index contenu dans l'argument curpos. Notez que la manipulation directe de la ligne d'entrée et de la position du curseur n'est pas autorisée. Cela est dû au fait que les règles dictées par divers modes, tels que le mode vi par rapport au mode emacs, le mode sans écho, et le mode insertion par rapport au mode surimpression etc, rendent la chose trop complexe pour qu'un développeur d'application écrive une action d'édition conforme, ainsi que pour limiter les changements futurs aux internes de gl_get_line(). Une solution potentielle à ce dilemme serait de permettre à la fonction d'action d'éditer la ligne en utilisant les actions d'édition existantes. Cela est actuellement à

l'étude.

Si la fonction d'action souhaite écrire du texte sur le terminal, sans que cela se mélange avec le texte affiché de la ligne d'entrée, ou lire depuis le terminal sans avoir à gérer l'E/S brute du terminal, alors avant de faire l'une ou l'autre de ces opérations, elle doit suspendre temporairement l'édition de ligne en appelant la fonction gl_normal_io(). Cette fonction vide toute sortie en attente vers le terminal, déplace le curseur au début de la ligne qui suit la dernière ligne du terminal de la ligne d'entrée, puis restaure le terminal à un état adapté à l'utilisation avec les fonctionnalités stdio de C. Ce dernier comprend des choses comme la restauration du mappage normal de \n vers \r\n, et, en mode serveur, la restauration de la forme bloquante normale de l'E/S du terminal. Après avoir appelé cette fonction, la fonction d'action peut lire depuis et écrire vers le terminal sans craindre de créer un désordre. Il n'est pas nécessaire pour la fonction d'action de restaurer l'environnement d'édition original avant de retourner. Cela est fait automatiquement par gl_get_line() après le retour de la fonction d'action. Voici un exemple simple d'une fonction d'action qui écrit la phrase "Hello world" sur une nouvelle ligne du terminal après la ligne en cours d'édition. Lorsque cette fonction retourne, la ligne d'entrée est redessinée sur la ligne qui suit la ligne "Hello world", et l'édition de ligne

reprend. 
  static GL_ACTION_FN(say_hello_fn)
  {
    if(gl_normal_io(gl))   /* Suspendre temporairement l'édition */
      return GLA_ABORT;
    printf("Hello world\n");
    return GLA_CONTINUE;
}

Les fonctions d'action doivent retourner l'une des valeurs suivantes, pour indiquer à gl_get_line() comment

procéder. 
  GLA_ABORT     -   Faire en sorte que gl_get_line() retourne NULL.
  GLA_RETURN    -   Faire en sorte que gl_get_line() retourne la
                    ligne d'entrée complétée.
  GLA_CONTINUE  -   Reprendre l'édition de la ligne de
commande.

Notez que le argument name de gl_register_action() spécifie le nom par lequel un utilisateur peut référencer l'action dans son fichier de configuration. Cela lui permet de réassocier l'action à une séquence de touches alternative. Pour que cela fonctionne, il est nécessaire d'appeler gl_register_action() entre l'appel à new_GetLine() et le premier appel à gl_get_

lin
e().

ARCHIVAGE MANUEL DE

L'HISTORIQUE

Par défaut, chaque fois qu'une ligne est saisie par l'utilisateur, elle est automatiquement ajoutée à la liste d'historique, juste avant que gl_get_line() retourne la ligne à l'appelant. C'est pratique pour la majorité des applications, mais il existe aussi des applications qui ont besoin d'un contrôle plus fin sur ce qui est ajouté à la liste d'historique. Dans de tels cas, l'ajout automatique des lignes saisies à la liste d'historique peut être désactivé en appelant la fonction gl_automatic

_history(). 
  int gl_automatic_history(GetLine *gl, int enable)
;

Si cette fonction est appelée avec son argument enable défini à 0, gl_get_line() n'archivera pas automatiquement les lignes saisies ultérieurement. L'archivage automatique peut être réactivé plus tard, en appelant à nouveau cette fonction, avec son argument enable défini à 1. Pendant que l'archivage automatique de l'historique est désactivé, l'application appelante peut utiliser gl_append_history() pour ajouter des lignes à la liste d'historique selon les

besoins. 
  int gl_append_history(GetLine *gl, const char *line)
;

L' argument line spécifie la ligne à ajouter à la liste d'historique. Cela doit être une chaîne normale terminée par ' '. Si cette chaîne contient des caractères de nouvelle ligne, la ligne archivée dans la liste d'historique sera terminée par le premier d'entre eux. Sinon, elle sera terminée par le terminateur ' '. Si la ligne est plus longue que la longueur maximale de ligne d'entrée, qui a été spécifiée lorsque new_GetLine() a été appelé, lorsque la ligne est rappelée, elle sera tronquée à la longueur réelle de la ligne gl_get_li

ne().

En cas de succès, gl_append_history() retourne 0. Sinon, elle retourne une valeur non nulle, et définit errno à l'une des valeurs

suivantes. 
   EINVAL  -  L'un des arguments passés à
              gl_append_history() était NULL.
   ENOMEM  -  La ligne spécifiée était plus longue que la taille allouée
              du tampon d'historique (telle que spécifiée lorsque
              new_GetLine() a été appelé), elle n'a donc pas pu être
archivée.

Une description textuelle de l'erreur peut être obtenue en appelant éventuellement gl_error_message(). Notez qu'après une telle erreur, la liste d'historique reste dans un état valide pour recevoir de nouvelles lignes d'historique, il y a donc peu d'inconvénient à simplement ignorer le statut de retour de gl_append_

CONFIGURATION DIVERSE DE

L'HISTORIQUE

Si vous souhaitez changer la taille du tampon d'historique qui a été initialement spécifiée dans l'appel à new_GetLine(), vous pouvez le faire avec la fonction gl_resize_history()

. 
  int gl_resize_history(GetLine *gl, size_t histlen)
;

L' argument histlen spécifie la nouvelle taille en octets, et si vous spécifiez cela comme 0, le tampon sera

supprimé.

Comme mentionné dans la discussion de new_GetLine(), le nombre de lignes qui peuvent être stockées dans le tampon d'historique dépend des longueurs des lignes individuelles. Par exemple, un tampon de 1000 octets pourrait tout aussi bien stocker 10 lignes de longueur moyenne de 100 octets, ou 2 lignes de longueur moyenne de 50 octets. Bien que le tampon ne soit jamais agrandi lorsque de nouvelles lignes sont ajoutées, une liste de pointeurs vers le tampon est agrandie si nécessaire pour accueillir le nombre de lignes actuellement stockées dans le tampon. Pour placer une limite supérieure sur le nombre de lignes dans le tampon, et donc un plafond sur la quantité de mémoire utilisée dans cette liste, vous pouvez appeler la gl_limit_history() fonction.

  void gl_limit_history(GetLine *gl, int max_lines);

Le max_lines doit être un nombre positif >= 0, spécifiant une limite supérieure au nombre de lignes dans le tampon, ou doit être -1 pour annuler toute limite spécifiée précédemment. Lorsqu'une limite est en vigueur, seules les max_lines lignes les plus récemment ajoutées sont conservées dans le tampon. Les anciennes lignes sont rejetées.

Pour rejeter des lignes du tampon d'historique, utilisez la fonction gl_clear_history().

  void gl_clear_history(GetLine *gl, int all_groups);

L'argument all_groups indique à la fonction s'il faut supprimer uniquement les lignes associées au groupe d'historique actuel (voir gl_group_history()), ou toutes les lignes historiques dans le tampon.

La fonction gl_toggle_history() vous permet d'activer ou de désactiver l'historique sans perdre le contenu actuel de la liste d'historique.

  void gl_toggle_history(GetLine *gl, int enable);

Définir l'argument enable à 0 désactive le mécanisme d'historique, et le définir à 1 le réactive. Lorsque l'historique est désactivé, aucune nouvelle ligne ne sera ajoutée à la liste d'historique, et les raccourcis clavier de recherche dans l'historique agiront comme s'il n'y avait rien dans le tampon d'historique.

CHANGEMENT DE TERMINAL

La fonction constructeur new_GetLine() suppose que l'entrée doit être lue depuis stdin et la sortie écrite sur stdout. La fonction suivante vous permet de passer à différents flux d'entrée et de sortie.

  int gl_change_terminal(GetLine *gl, FILE *input_fp,
                         FILE *output_fp, const char *term);

L'argument gl est l'objet retourné par new_GetLine(). L'argument input_fp spécifie le flux à lire, et output_fp spécifie le flux à écrire. Ce n'est que si les deux se réfèrent à un terminal que l'entrée interactive du terminal sera activée. Sinon, gl_get_line() appellera simplement fgets() pour lire l'entrée de commande. Si les deux flux se réfèrent à un terminal, ils doivent se référer au même terminal, et le type de ce terminal doit être spécifié via l'argument term. La valeur de l'argument term est recherchée dans la base de données d'informations de terminal (terminfo ou termcap), afin de déterminer quelles séquences de contrôle spéciales sont nécessaires pour contrôler divers aspects du terminal. new_GetLine(), par exemple, passe la valeur de retour de getenv("TERM") dans cet argument. Notez que si un ou les deux de input_fp et output_fp ne se réfèrent pas à un terminal, il est alors légal de passer NULL au lieu d'un type de terminal.

Notez que si vous souhaitez passer des descripteurs de fichiers à gl_change_terminal(), vous pouvez le faire en créant des enveloppes de flux stdio en utilisant la fonction POSIX fdopen().

GESTION DES ÉVÉNEMENTS EXTERNES

Par défaut, gl_get_line() ne retourne pas avant qu'une ligne d'entrée complète n'ait été saisie par l'utilisateur, ou qu'une erreur ne se produise. Dans les programmes qui doivent surveiller les E/S provenant d'autres sources que le terminal, il existe deux options.

  1. Utilisez les fonctions décrites dans la page de
     manuel gl_io_mode(3) pour passer
     gl_get_line() en mode serveur non bloquant. Dans ce mode,
     gl_get_line() devient une fonction d'édition de ligne non bloquante
     et incrémentale qui peut être appelée en toute sécurité à partir d'une
     boucle d'événements externe. Bien que ce soit une méthode très polyvalente,
     elle implique de prendre en charge certaines responsabilités qui sont
     normalement effectuées en coulisses par gl_get_line().
  2. Pendant que gl_get_line() attend une entrée au clavier de
     l'utilisateur, vous pouvez lui demander de surveiller également l'activité
     sur des descripteurs de fichiers arbitraires, tels que des sockets réseau,
     des pipes, etc., et de faire appel à des fonctions de votre choix lorsqu'une
     activité est détectée. Cela fonctionne sur tout système disposant de
     l'appel système select(), ce qui est la plupart, sinon la totalité,
     des saveurs d'Unix.

L'enregistrement d'un descripteur de fichier à surveiller par gl_get_line() implique d'appeler la fonction gl_watch_fd().

  int gl_watch_fd(GetLine *gl, int fd, GlFdEvent event,
                  GlFdEventFn *callback, void *data);

Si cela renvoie non zéro, cela signifie soit que vos arguments sont invalides, soit que cette fonctionnalité n'est pas prise en charge sur le système hôte.

L'argument fd est le descripteur de fichier à surveiller. L'argument event spécifie le type d'activité qui suscite de l'intérêt, choisi parmi les valeurs énumérées suivantes :

  GLFD_READ   - Surveiller l'arrivée de données à lire.
  GLFD_WRITE  - Surveiller la capacité d'écrire dans le descripteur
                de fichier sans bloquer.
  GLFD_URGENT - Surveiller l'arrivée de données urgentes hors bande
                sur le descripteur de fichier.

L'argument callback est la fonction à appeler lorsque l'activité sélectionnée est détectée. Elle doit être définie avec la macro suivante, définie dans libtecla.h.

  #define GL_FD_EVENT_FN(fn) GlFdStatus (fn)(GetLine *gl, \
                                      void *data, int fd, \
                                      GlFdEvent event)

L'argument data de la fonction gl_watch_fd() est transmis à la fonction de rappel pour son propre usage, et peut pointer vers n'importe quoi, y compris NULL. Le descripteur de fichier et l'argument d'événement sont également transmis à la fonction de rappel, ce qui permet potentiellement à la même fonction de rappel d'être enregistrée pour plus d'un type d'événement et/ou plus d'un descripteur de fichier. La valeur de retour de la fonction de rappel doit être l'une des valeurs suivantes.

  GLFD_ABORT    - Indiquer à gl_get_line() d'avorter. Lorsque cela
                   se produit, gl_get_line() renvoie
                   NULL, et un appel ultérieur à
                   gl_return_status() renverra
                   GLR_FDABORT. Notez que si l'application
                   a besoin que errno ait toujours une valeur
                   significative lorsque gl_get_line() renvoie
                   NULL, la fonction de rappel doit définir
                   errno de manière appropriée.
  GLFD_REFRESH  - Redessiner la ligne d'entrée puis continuer à
                   attendre l'entrée. Renvoyez ceci si votre
                   rappel a écrit sur le terminal.
  GLFD_CONTINUE - Continuer à attendre l'entrée, sans redessiner
                   la ligne.

Notez qu'avant d'appeler le rappel, gl_get_line() bloque la plupart des signaux et laisse ses propres gestionnaires de signaux installés, donc si vous avez besoin d'intercepter un signal particulier, vous devrez à la fois installer temporairement votre propre gestionnaire de signaux et débloquer le signal. Assurez-vous de rebloquer le signal (s'il était initialement bloqué) et de rétablir le gestionnaire de signaux d'origine, le cas échéant, avant de retourner.

La gestion des signaux est étonnamment difficile à réaliser de manière fiable sans conditions de course. l'utilisateur.

suit.

Tout d'abord, notez que lorsqu'un appel à siglongjmp() fait sigsetjmp() retourner, à condition que l'argument savesigs de sigsetjmp() ait été non nul, comme spécifié ci-dessus, le masque de traitement des signaux est restauré à l'état dans lequel il se trouvait lorsque sigsetjmp() a été appelé. C'est la différence importante entre sigsetjmp() et l'ancien setjmp() problématique, et c'est l'ingrédient essentiel qui rend possible l'évitement des conditions de course dans la gestion des signaux. Grâce à cela, nous sommes garantis que tous les signaux que nous avons bloqués avant d'appeler sigsetjmp() sont de nouveau bloqués dès qu'un signal est capturé. Les instructions suivantes, qui sont alors exécutées, sont ainsi garanties d'être exécutées sans qu'aucun autre signal ne soit

capturé.

1. Si tel est ordonné par les attributs de configuration de
gl_get_line() du signal qui a été capturé,
gl_get_line() restaure les attributs du terminal à
l'état dans lequel ils se trouvaient lorsque gl_get_line() a été
appelé. C'est particulièrement important pour les signaux qui
suspendent ou terminent le processus, car sinon le
terminal serait laissé dans un état

inutilisable.

2. Il réinstalle ensuite les gestionnaires de signaux de

l'application.

3. Il utilise ensuite la fonction raise()
de la bibliothèque standard C pour renvoyer à l'application le signal qui
a été

capturé.

3. Ensuite, il débloque la livraison du signal que nous venons de
envoyer. Cela fait que le signal qui vient d'être envoyé
via raise() est capturé par le gestionnaire de signal
original de l'application, qui peut maintenant le traiter comme il
le juge

approprié.

4. Si le gestionnaire de signal retourne (c'est-à-dire qu'il ne termine pas
le processus), gl_get_line() bloque de nouveau la livraison du
signal

ci-dessus.

5. Il annule ensuite toute action effectuée dans la première des
étapes ci-dessus, et réaffiche la ligne, si la configuration du signal
l'exige

.

6. gl_get_line() reprend alors soit la tentative de
lecture d'un caractère, soit l'abandon, en fonction de la
configuration du signal qui a été

capturé.

L'essentiel des étapes ci-dessus consiste à prendre des signaux livrés de manière asynchrone et à les traiter de manière synchrone, un à la fois, à un point du code où gl_get_line() a un contrôle com

plet sur son
environnement.

LA TAILLE DU

TERMINAL

Sur la plupart des systèmes, la combinaison de l'ioctl TIOCGWINSZ et du signal SIGWINCH est utilisée pour maintenir une idée précise de la taille du terminal. La taille du terminal est nouvellement interrogée à chaque fois que gl_get_line() est appelé et chaque fois qu'un signal SIGWINCH est

reçu.

Sur les quelques systèmes où ce mécanisme n'est pas disponible, au démarrage new_GetLine() cherche d'abord les variables d'environnement LINES et COLUMNS. Si celles-ci ne sont pas trouvées, ou si elles contiennent des valeurs inutilisables, alors si une base de données d'informations sur le terminal comme terminfo ou termcap est disponible, la taille par défaut du terminal est recherchée dans cette base de données. Si cela échoue également à fournir la taille du terminal, une taille par défaut de 80 colonnes sur 24 lignes est

utilisée.

Même sur les systèmes qui prennent en charge ioctl(TIOCGWINSZ), si le terminal se trouve à l'autre extrémité d'une ligne série, le pilote de terminal n'a généralement aucun moyen de détecter lorsqu'un redimensionnement se produit ou d'interroger quelle est la taille actuelle. Dans de tels cas, aucun SIGWINCH n'est envoyé au processus, et les dimensions retournées par ioctl(TIOCGWINSZ) ne sont pas correctes. La seule façon de gérer de tels cas est de fournir un moyen à l'utilisateur d'entrer une commande qui indique au système distant quelle est la nouvelle taille. Cette commande appellerait alors la fonction gl_set_term_size() pour informer gl_get_line() du changement de

taille. 
  int gl_set_term_size(GetLine *gl, int ncolumn, int nline)
;

Les arguments ncolumn et nline sont utilisés pour spécifier les nouvelles dimensions du terminal et ne doivent pas être inférieurs à 1. Sur les systèmes qui prennent en charge ioctl(TIOCGWINSZ), cette fonction appelle d'abord ioctl(TIOCSWINSZ) pour informer le pilote du terminal du changement de taille. En mode d'entrée/sortie serveur non bloquant, si une ligne est actuellement en cours de saisie, la ligne saisie est alors redessinée pour s'adapter à la taille modifiée. Enfin, les nouvelles valeurs sont enregistrées dans gl pour une utilisation future par gl_get_li

ne().

La fonction gl_terminal_size() vous permet d'interroger la taille actuelle du terminal et d'installer une taille de secours alternative pour les cas où la taille n'est pas disponible. Attention, la taille du terminal ne sera pas disponible si vous lisez depuis un tube ou un fichier, donc les valeurs par défaut peuvent être importantes même sur les systèmes qui prennent en charge des moyens de découvrir la taille du

terminal. 
  typedef struct {
    int nline;        /* Le terminal a nline lignes */
    int ncolumn;      /* Le terminal a ncolumn colonnes */
  } GlTerminalSize;
  GlTerminalSize gl_terminal_size(GetLine *gl,
                                  int def_ncolumn,
                                  int def_nline)
;

Cette fonction met d'abord à jour les dimensions de secours du terminal de gl_get_line(), puis enregistre ses résultats dans la valeur de

retour.

Les arguments def_ncolumn et def_nline spécifient le nombre par défaut de colonnes et de lignes du terminal à utiliser si la taille du terminal ne peut pas être déterminée via ioctl(TIOCGWINSZ) ou les variables

d'environnement
.

CACHER CE QUE VOUS

TAPEZ

Lors de la saisie d'informations sensibles, comme des mots de passe, il est préférable de ne pas faire écho sur le terminal du texte que vous saisissez. De plus, ce texte ne devrait pas être enregistré dans la liste d'historique, car quelqu'un trouvant votre terminal sans surveillance pourrait alors le rappeler, ou quelqu'un fouillant dans vos répertoires pourrait le voir dans votre fichier d'historique. En gardant cela à l'esprit, la fonction gl_echo_mode() vous permet d'activer et de désactiver l'affichage et l'archivage de tout texte qui est saisi par la suite dans les appels à gl_get_li

ne(). 
  int gl_echo_mode(GetLine *gl, int enable)
;

L'argument enable spécifie si le texte saisi doit être visible ou non. S'il est 0, les lignes saisies par la suite ne seront pas visibles sur le terminal et ne seront pas enregistrées dans la liste d'historique. S'il est 1, les lignes saisies par la suite seront affichées au fur et à mesure de leur saisie, et à condition que l'historique n'ait pas été désactivé par un appel à gl_toggle_history(), elles seront également archivées dans la liste d'historique. Enfin, si l'argument enable est -1, le mode d'écho est laissé inchangé, ce qui vous permet d'interroger le paramètre actuel de manière non destructive via la valeur de retour. Dans tous les cas, la valeur de retour de la fonction est 0 si l'écho était désactivé avant l'appel de la fonction, et 1 s'il était

activé.

Lorsque l'écho est désactivé, notez que même si l'achèvement par ta

bulation complétera votre préfixe de manière invisible autant
que possible, les complétions ambiguës ne seront pas affichées.

REQUÊTES À UN SEUL

CARACTÈRE

Utiliser gl_get_line() pour demander à l'utilisateur une réponse d'un seul caractère est incommode pour l'utilisateur, car il doit appuyer sur la touche entrée ou retour avant que le caractère qu'il a tapé soit renvoyé au programme. C'est pourquoi la fonction gl_query_char() a été fournie pour les requêtes à un seul caractère comme

celle-ci. 
  int gl_query_char(GetLine *gl, const char *prompt,
                    char defchar)
;

Cette fonction affiche l'invite spécifiée au début d'une nouvelle ligne et attend que l'utilisateur tape un caractère. Lorsque l'utilisateur tape un caractère, gl_query_char() l'affiche à droite de l'invite, passe à la ligne suivante, puis renvoie le caractère au programme appelant. La valeur de retour de la fonction est le caractère qui a été tapé. Si la lecture a dû être interrompue pour une raison quelconque, EOF est renvoyé à la place. Dans le dernier cas, l'application peut appeler la fonction précédemment documentée gl_return_status() pour savoir ce qui s'est mal passé. Cela pourrait, par exemple, être la réception d'un signal, ou le déclenchement du minuteur d'inactivité

optionnel.

Si l'utilisateur appuie simplement sur entrée, la valeur de l'argument defchar est substituée. Cela signifie que lorsque l'utilisateur appuie sur nouvelle ligne ou retour, le caractère spécifié dans defchar est affiché après l'invite, comme si l'utilisateur l'avait tapé, et est également renvoyé à l'application appelante. Si un tel remplacement n'est pas important, passez simplement '0 comme valeur de defchar

.

Si le caractère saisi est un caractère non imprimable, il est affiché symboliquement. Par exemple, contrôle-A est affiché comme ^A, et les caractères au-delà de 127 sont affichés en octal, précédés d'une barre oblique

inverse.

Comme avec gl_get_line(), l'écho du caractère saisi peut être désactivé à l'aide de la fonction gl_echo_mo

de().

Si le processus appelant est suspendu pendant qu'il attend que l'utilisateur tape sa réponse, le curseur est déplacé à la ligne suivant la ligne d'invite, puis lorsque le processus reprend, l'invite est réaffichée, et gl_query_char() reprend l'attente que l'utilisateur tape un

caractère.

Notez qu'en mode serveur non bloquant, (voir gl_io_mode(3)), si une ligne d'entrée incomplète est en cours de lecture lorsque gl_query_char() est appelée, la ligne d'entrée partielle est abandonnée et effacée du terminal avant que la nouvelle invite ne soit affichée. Le prochain appel à gl_get_line() commencera donc

à éditer une n
ouvelle ligne.

LIRE DES CARACTÈRES

BRUTS

Alors que la fonction gl_query_char() demande visiblement à l'utilisateur un caractère et affiche ce qu'il a tapé, la fonction gl_read_char() lit un caractère brut auprès de l'utilisateur, sans rien écrire sur le terminal ni perturber une ligne d'entrée incomplètement saisie. Cela signifie qu'elle peut être appelée non seulement entre les appels à gl_get_line(), mais aussi depuis des fonctions de rappel que l'application a enregistrées pour être appelées par gl_get_li

ne(). 
  int gl_read_char(GetLine *gl)
;

En cas de succès, la valeur de retour de gl_read_char() est le caractère qui a été lu. En cas d'échec, EOF est renvoyé, et la fonction gl_return_status() peut être appelée pour savoir ce qui s'est mal passé. Les possibilités incluent le déclenchement du minuteur d'inactivité optionnel, la réception d'un signal configuré pour interrompre gl_get_line(), ou le blocage des entrées/sorties du terminal, en mode d'entrée/sortie serveur non

bloquant.

Attention, certaines touches du clavier, comme les touches de fonction et les touches de direction, génèrent généralement au moins 3 caractères chacune, donc un seul appel à gl_read_char() ne't be enough to identify such keystrokes.

EFFACER LE TERMINAL

Le programme appelant peut effacer le terminal en appelant gl_erase_terminal(). En mode I/O serveur non bloquant, cette fonction prépare également la ligne d'entrée actuelle à être redessinée à partir de zéro lorsque gl_get_line() sera appelée la prochaine fois.

  int gl_erase_terminal(GetLine *gl);

AFFICHAGE DYNAMIQUE DE TEXTE

Entre les appels à gl_get_line(), la fonction gl_display_text() fournit un moyen pratique d'afficher des paragraphes de texte, justifiés à gauche et répartis sur une ou plusieurs lignes du terminal conformément aux contraintes de la largeur actuelle du terminal. Des exemples d'utilisation de cette fonction se trouvent dans les programmes de démonstration, où elle est utilisée pour afficher des introductions. Dans ces exemples, l'utilisation avancée de préfixes, suffixes et lignes pleines optionnels pour dessiner un cadre autour du texte est également illustrée.

  int gl_display_text(GetLine *gl, int indentation,
                      const char *prefix,
                      const char *suffix, int fill_char,
                      int def_width, int start,
                      const char *string);

Si gl n'est pas actuellement connecté à un terminal, par exemple si la sortie d'un programme utilisant gl_get_line() est redirigée vers un autre programme ou vers un fichier, alors la valeur du paramètre def_width est utilisée comme largeur du terminal.

L'argument indentation spécifie le nombre de caractères à utiliser pour indenter chaque ligne de sortie. L'argument fill_char spécifie le caractère qui sera utilisé pour effectuer cette indentation.

L'argument prefix peut être NULL, ou une chaîne de caractères à placer au début de chaque nouvelle ligne (après toute indentation). De même, l'argument suffix peut être NULL, ou une chaîne de caractères à placer à la fin de chaque ligne. Le suffixe est placé au ras du bord droit du terminal, et tout espace entre son premier caractère et le dernier mot de cette ligne est rempli avec le caractère spécifié via l'argument fill_char. Normalement, le caractère de remplissage est un espace.

L'argument start indique à gl_display_text() combien de caractères ont déjà été écrits sur la ligne actuelle du terminal, et indique ainsi l'indice de colonne de départ du curseur. Comme la valeur de retour de gl_display_text() est l'indice de colonne de fin du curseur, en passant la valeur de retour d'un appel à l'argument start de l'appel suivant, un paragraphe qui est divisé entre plusieurs chaînes peut être composé en appelant gl_display_text() pour chaque portion successive du paragraphe. Notez que des caractères de nouvelle ligne littéraux sont nécessaires à la fin de chaque paragraphe pour forcer le démarrage d'une nouvelle ligne.

En cas d'erreur, gl_display_text() retourne -1.

FONCTIONNALITÉS DE FONCTIONS DE RAPPEL

Sauf indication contraire, les fonctions de rappel, telles que les fonctions de rappel d'achèvement de tabulation et les fonctions de rappel d'événements, ne doivent appeler aucune fonction de ce module. Les fonctions suivantes, cependant, sont conçues spécifiquement pour être utilisées par des fonctions de rappel.

Appeler la fonction gl_replace_prompt() depuis une fonction de rappel indique à gl_get_line() d'afficher une invite différente lorsque la fonction de rappel retourne. Sauf en mode serveur non bloquant, elle n'a aucun effet si elle est utilisée entre les appels à gl_get_line(). En mode serveur non bloquant (voir la page man gl_io_mode(3)), lorsqu'elle est utilisée entre deux appels à gl_get_line() qui opèrent sur la même ligne d'entrée, la ligne d'entrée actuelle sera redessinée avec la nouvelle invite lors du prochain appel à gl_get_line().

  void gl_replace_prompt(GetLine *gl, const char *prompt);

JEUX DE CARACTÈRES INTERNATIONAUX

Depuis la version 1.4.0 de libtecla, gl_get_line() est propre aux 8 bits. Cela signifie que tous les caractères 8 bits qui sont imprimables dans la locale actuelle de l'utilisateur sont maintenant affichés tels quels et inclus dans la ligne d'entrée retournée. En supposant que le programme appelant contient correctement un appel comme suit,

  setlocale(LC_CTYPE, "");

alors la locale actuelle est déterminée par la première des variables d'environnement LC_CTYPE, LC_ALL, et LANG, qui est trouvée pour contenir un nom de locale valide. Si aucune de ces variables n'est définie, ou si le programme omet d'appeler setlocale, alors la locale par défaut C est utilisée, qui est l'ASCII 7 bits américain. Sur la plupart des plateformes de type Unix, vous pouvez obtenir une liste des locales valides en tapezant la commande :

  locale -a

à l'invite du shell. Une documentation plus détaillée sur la façon dont l'utilisateur peut utiliser cela pour saisir des caractères internationaux se trouve dans la page man tecla(7).

SÉCURITÉ DES THREADS

Dans un programme multi-thread, vous devriez utiliser la version libtecla_r.a de la bibliothèque. Celle-ci utilise des versions réentrantes des fonctions système, lorsque disponibles. Malheureusement, ni terminfo ni termcap n'ont été conçus pour être réentrants, vous ne pouvez donc pas utiliser en toute sécurité les fonctions du module getline dans plusieurs threads (vous pouvez utiliser les modules distincts d'expansion de fichiers et d'achèvement de mots dans plusieurs threads, voir les pages man correspondantes pour plus de détails). Cependant, en raison de l'utilisation de fonctions réentrantes POSIX pour la recherche de répertoires personnels, etc., il est sûr d'utiliser ce module à partir d'un seul thread d'un programme multi-thread, à condition que vos autres threads n'utilisent aucune fonction termcap ou terminfo.
