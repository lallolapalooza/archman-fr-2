L

fonction gl_get_line() fait partie de la bibliothèque tecla (voir la page man libtecla(3)). Si l'utilisateur saisit du texte sur un terminal, chaque appel l'invite à saisir une ligne d'entrée, puis fournit des fonctionnalités d'édition interactives, similaires à celles du shell unix tcsh. En plus de l'édition de ligne de commande simple, elle prend en charge le rappel des lignes de commande précédemment saisies, la complétion des noms de fichiers avec la touche TAB, et l'expansion des caractères génériques dans les noms de fichiers en ligne. La documentation des fonctionnalités d'édition de ligne de commande au niveau utilisateur et de toutes les options de configuration utilisateur se trouve dans la page man tecla(7). Cette page man concerne la documentation destinée aux programmeurs souhaitant utiliser cette bibliothèque dans leur application. UN E

LES FONCTIONS UTILISÉES DANS

L'EXEMPLE

Les descriptions des fonctions utilisées dans l'exemple sont les suivantes

: 
  GetLine *new_GetLine(size_t linelen, size_t
histlen)

Cette fonction crée les ressources utilisées par la fonction gl_get_line() et retourne un pointeur opaque vers l'objet qui les contient. La longueur maximale d'une ligne d'entrée est spécifiée via l'argument linelen, et le nombre d'octets à allouer pour stocker les lignes d'historique est défini par l'argument histlen. Les lignes d'historique sont stockées bout à bout dans un seul tampon de cette taille. Notez que cela signifie que le nombre de lignes d'historique pouvant être stockées à un moment donné dépend de la longueur des lignes individuelles. Si vous souhaitez placer une limite supérieure au nombre de lignes pouvant être stockées, voir la fonction gl_limit_history() décrite plus tard. Si vous ne voulez pas d'historique du tout, spécifiez histlen comme zéro, et aucun tampon d'historique ne sera

alloué.

En cas d'erreur, un message est affiché sur stderr et NULL est

retourné. 
  GetLine *del_GetLine(GetLine
*gl)

Cette fonction supprime les ressources qui ont été retournées par un appel précédent à new_GetLine(). Elle retourne toujours NULL (c'est-à-dire un objet supprimé). Elle ne fait rien si l'argument gl est NULL

. 
  char *gl_get_line(GetLine *gl, const char *prompt,
                   const char *start_line, int start_pos)
;

La fonction gl_get_line() peut être appelée un nombre quelconque de fois pour lire la saisie de l'utilisateur. L'argument gl doit avoir été précédemment retourné par un appel à new_GetLine(). L'argument prompt doit être une chaîne normale terminée par NUL, spécifiant l'invite à présenter à l'utilisateur. Par défaut, les invites sont affichées littéralement, mais si elles sont activées avec la fonction gl_prompt_style() (voir plus loin), les invites peuvent contenir des directives pour souligner, basculer entre les polices normales et en gras, ou activer et désactiver la mise en

évidence.

Si vous souhaitez spécifier le contenu initial de la ligne pour que l'utilisateur la modifie, transmettez la chaîne souhaitée via l'argument start_line. Vous pouvez ensuite spécifier le caractère de cette ligne où le curseur est initialement positionné sur, en utilisant l' argument start_pos. Cela doit être -1 si vous voulez que le curseur suive le dernier caractère de la ligne de début. Si vous ne voulez pas précharger la ligne de cette manière, envoyez start_line comme NULL, et définissez start_pos à -1. Notez que le pointeur de ligne retourné par un appel à gl_get_line() peut être transmis à l'appel suivant à gl_get_line() via le start_line. Cela permet à l'application de prendre la dernière ligne saisie et, si elle contient une erreur, de la présenter à nouveau à l'utilisateur pour réédition, avec le curseur initialement positionné là où l'erreur a été

rencontrée.

La fonction gl_get_line() renvoie un pointeur vers la ligne saisie par l'utilisateur, ou NULL en cas d'erreur ou à la fin de l'entrée. Le pointeur renvoyé fait partie de l'objet ressource gl spécifié, et ne doit donc pas être libéré par l'appelant, ni supposé inchangé d'un appel à l'autre. Lors de la lecture depuis un utilisateur sur un terminal, il y aura toujours un caractère de nouvelle ligne à la fin de la ligne renvoyée. Lorsque l'entrée standard provient d'un pipe ou d'un fichier, il y aura de même une nouvelle ligne, sauf si la ligne d'entrée était trop longue pour être stockée dans le tampon interne. Dans ce dernier cas, vous devriez appeler gl_get_line() à nouveau pour lire le reste de la ligne. Notez que ce comportement rend gl_get_line() similaire à fgets(). En fait, lorsque stdin n'est pas connecté à un terminal,gl_get_line() appelle simplement fget

s(
).

SOURCES DE CONFIGURATION

ALTERNATIVES

Comme mentionné ci-dessus, par défaut les utilisateurs ont la possibilité de configurer le comportement de gl_get_line() via un fichier de configuration appelé .teclarc dans leurs répertoires personnels. Le fait que toutes les applications partagent ce même fichier de configuration est à la fois un avantage et un inconvénient. Dans la plupart des cas, c'est un avantage, car cela encourage l'uniformité et dispense l'utilisateur de devoir configurer chaque application séparément. Dans certaines applications, cependant, ce seul moyen de configuration pose problème. C'est particulièrement vrai pour les logiciels embarqués, où il n'y a pas de système de fichiers pour lire un fichier de configuration, et aussi dans les applications où un choix radicalement différent de mappage des touches est nécessaire pour émuler une interface clavier héritée. Pour prendre en charge de tels cas, la fonction suivante permet à l'application de contrôler d'où les informations de configuration sont

lues. 
  int gl_configure_getline(GetLine *gl,
                           const char *app_string,
                           const char *app_file,
                           const char *user_file)
;

Elle permet aux commandes de configuration qui seraient normalement lues depuis le fichier ~/.teclarc de l'utilisateur, d'être lues depuis n'importe lequel ou aucun de : une chaîne, un fichier de configuration spécifique à l'application, et/ou un fichier de configuration spécifique à l'utilisateur. Si cette fonction est appelée avant le premier appel à gl_get_line(), le comportement par défaut de lecture de ~/.teclarc au premier appel à gl_get_line() est désactivé ; toute la configuration doit donc être réalisée en utilisant les sources de configuration spécifiées avec cette

fonction.

Si app_string != NULL, alors il est interprété comme une chaîne contenant une ou plusieurs commandes de configuration, séparées les unes des autres dans la chaîne par des caractères de nouvelle ligne intégrés. Si app_file != NULL alors il est interprété comme le chemin complet d'un fichier de configuration spécifique à l'application. Si user_file != NULL alors il est interprété comme le chemin complet d'un fichier de configuration spécifique à l'utilisateur, tel que ~/.teclarc. Par exemple, dans l'appel

suivant, 
  gl_configure_getline(gl, "edit-mode vi \n nobeep",
                           "/usr/share/myapp/teclarc",
                           "~/.teclarc")
;

l' argument app_string fait démarrer l'application appelante en mode d'édition vi, au lieu du mode emacs par défaut, et désactive l'utilisation de la cloche du terminal par la bibliothèque. Elle tente ensuite de lire les commandes de configuration à l'échelle du système depuis un fichier facultatif appelé /usr/share/myapp/teclarc, puis lit enfin les commandes de configuration spécifiques à l'utilisateur depuis un fichier .teclarc facultatif dans le répertoire personnel de l'utilisateur. Notez que les arguments sont listés par ordre de priorité croissante, le contenu de app_string pouvant potentiellement être remplacé par des commandes dans app_file, et les commandes dans app_file pouvant potentiellement être remplacées par des commandes dans user_file

.

Vous pouvez appeler cette fonction autant de fois que nécessaire, les résultats étant cumulatifs, mais notez que les copies de tout nom de fichier spécifié via l' app_file et user_file sont enregistrés en interne pour une utilisation ultérieure par la fonction de liaison de touche read-init-files ; si vous prévoyez d'appeler cette fonction plusieurs fois, assurez-vous que le dernier appel spécifie les noms de fichiers que vous souhaitez relire lorsque l'utilisateur demande la relecture des fichiers de

configuration.

Des séquences de touches individuelles peuvent également être liées et déliées à l'aide de la fonction gl_bind_keyseq()

  int gl_bind_keyseq(GetLine *gl, GlKeyOrigin origin,
                     const char *keyseq,
                     const char *action)
;

L' argument origin spécifie la priorité de la liaison, selon le destinataire pour lequel elle est établie, et doit être l'une des deux valeurs

suivantes. 
  GL_USER_KEY   -   L'utilisateur a demandé cette liaison de touche.
  GL_APP_KEY    -   Il s'agit d'une liaison par défaut définie par
l'application.

Lorsque des liaisons utilisateur et application ont été spécifiées pour une même séquence de touches, la liaison utilisateur prime. La liaison de l'application est rétablie ultérieurement si la liaison de l'utilisateur est déliée plus tard, soit par un autre appel à cette fonction, soit par un appel à gl_configure_ge

L' argument keyseq spécifie la séquence de touches à lier ou à délier, et est exprimée de la même manière que dans un fichier de configuration ~/.teclarc . L' argument action doit être soit une chaîne contenant le nom de l'action à laquelle lier la séquence de touches, soit il doit être NULL ou "" pour délier

la séquence
de touches.

COMPLÉTION DE MOTS

PERSONNALISÉE

Si, dans votre application, vous souhaitez que la complétion par TAB complète d'autres éléments en plus des noms de fichiers, ou à leur place, vous pouvez organiser cela en enregistrant une fonction de rappel de complétion alternative, au moyen d'un appel à la fonction gl_customize_c

ompletion(). 
  int gl_customize_completion(GetLine *gl, void *data,
                              CplMatchFn *match_fn)
;

L' argument data fournit un moyen pour votre application de passer des informations arbitraires, spécifiques à l'application, à la fonction de rappel. Celles-ci sont transmises à la fonction de rappel à chaque fois qu'elle est appelée. Elles pourraient, par exemple, pointer vers la table de symboles à partir de laquelle les complétions possibles doivent être recherchées. L' argument match_fn spécifie la fonction de rappel à appeler. Le type de fonction CplMatchFn est défini dans libtecla.h , tout comme une macro CPL_MATCH_FN() que vous pouvez utiliser pour déclarer et prototyper des fonctions de rappel. La déclaration et les responsabilités des fonctions de rappel sont décrites en profondeur dans la page de manuel cpl_complete_word(3)

.

En bref, la fonction de rappel est responsable de la recherche vers l'arrière dans la ligne d'entrée, en remontant à partir du point où l'utilisateur a appuyé sur TAB, pour trouver le début du mot en cours de complétion. Elle doit ensuite rechercher les complétions possibles de ce mot et les enregistrer une par une dans l'objet WordCompletion qui lui est passé en argument, en appelant la fonction cpl_add_completion(). Si la fonction de rappel souhaite fournir la complétion de noms de fichiers en plus de ses propres complétions spécifiques, elle a la possibilité d'appeler elle-même la fonction de rappel de complétion de noms de fichiers intégrée. Ceci est également documenté dans la page de manuel cpl_complete_word(3)

.

Notez que si vous souhaitez que gl_get_line() retourne la ligne d'entrée actuelle lorsqu'une complétion réussie a été effectuée, vous pouvez organiser cela lorsque vous appelez cpl_add_completion(), en faisant du dernier caractère du suffixe de continuation un caractère de nouvelle ligne. Si vous faites cela, la ligne d'entrée sera mise à jour pour afficher la complétion, ainsi que tout suffixe de continuation jusqu'au caractère de nouvelle ligne, puis gl_get_line() retournera cette ligne

d'entrée.

Si, pour une raison quelconque, votre fonction de rappel doit écrire quelque chose sur le terminal, elle doit appeler gl_normal_io() avant de le faire. Cela commencera une nouvelle ligne après la ligne d'entrée actuellement en cours d'édition, rétablira l'E/S normale du terminal, et indiquera à gl_get_line() que la ligne d'entrée devra être red

essinée lorsque la fonctio
n de rappel retournera.

AJOUT D'ACTIONS DE

COMPLÉTION

Dans la section précédente, la capacité à personnaliser le comportement de la seule action de complétion par défaut, complete-word, a été décrite. Dans cette section, la capacité à installer des fonctions d'action supplémentaires, afin que différents types de complétion de mots puissent être liés à différentes séquences de touches, est décrite. Ceci est réalisé en utilisant la fonction gl_completion_action()

. 
  int gl_completion_action(GetLine *gl,
                           void *data, CplMatchFn *match_fn,
                           int list_only, const char *name,
                           const char *keyseq)
;

Les arguments data et match_fn sont tels que décrits dans la page de manuel cpl_complete_word, et spécifient la fonction de rappel qui doit être invoquée pour identifier les complétions possibles. L'argument list_only détermine si l'action en cours de définition doit tenter de compléter le mot aussi loin que possible dans la ligne d'entrée avant d'afficher d'éventuelles complétions ambiguës, ou si elle doit simplement afficher la liste des complétions possibles sans toucher à la ligne d'entrée. La première option est sélectionnée en spécifiant une valeur de 0, et la seconde en spécifiant une valeur de 1. L' argument name spécifie le nom par lequel les fichiers de configuration et les futures invocations de cette fonction doivent se référer à l'action. Ceci doit être soit le nom d'une action de complétion existante à modifier, soit un nouveau nom non utilisé pour une nouvelle action. Enfin, l' argument keyseq spécifie la séquence de touches par défaut à lier à l'action. Si ceci est NULL, aucune nouvelle séquence de touches ne sera liée à

l'action.

Attention, pour que l'utilisateur puisse changer la séquence de touches liée aux actions installées de cette manière, lorsque vous appelez gl_completion_action() pour installer une action donnée pour la première fois, vous devriez le faire entre l'appel à new_GetLine() et le premier appel à gl_get_line(). Sinon, lorsque le fichier de configuration de l'utilisateur sera lu lors du premier appel à gl_get_line(), le nom de votre action supplémentaire ne sera pas connu, et toute référence à celle-ci dans le fichier de configuration générera une

DÉFINITION D'ACTIONS

PERSONNALISÉES

Bien que les actions de liaison de touches intégrées soient suffisantes pour les besoins de la plupart des applications, une application spécialisée peut occasionnellement avoir besoin de définir une ou plusieurs actions personnalisées, liées à des séquences de touches spécifiques à l'application. Par exemple, une application de vente bénéficierait d'une séquence de touches qui afficherait le nom de la pièce correspondant à un numéro de pièce situé avant le curseur. Une telle fonctionnalité dépasse clairement le cadre des fonctions d'action intégrées. Ainsi, pour de tels cas particuliers, la fonction gl_register_action() est

fournie. 
  int gl_register_action(GetLine *gl, void *data,
			 GlActionFn *fn, const char *name,
			 const char *keyseq)
;

Cette fonction permet à l'application d'enregistrer une fonction externe, fn, qui sera par la suite appelée chaque fois que soit la séquence de touches spécifiée, keyseq, est saisie par l'utilisateur, soit que l'utilisateur saisisse toute autre séquence de touches qu'il lie par la suite au nom d'action spécifié, name, dans son fichier de configuration. L'argument data peut être un pointeur vers n'importe quoi que l'application souhaite voir passer à la fonction d'action, fn, chaque fois que cette fonction est

invoquée.

La fonction d'action, fn, devrait être déclarée à l'aide de la macro suivante, qui est définie dans libtecl

a.h. 
  #define GL_ACTION_FN(fn) GlAfterAction (fn)(GetLine *gl, \
              void *data, int count, size_t curpos, \
              const char
*line)

Les arguments gl et data sont ceux qui ont été précédemment passés à gl_register_action() lorsque la fonction d'action a été enregistrée. L'argument count est un argument numérique que l'utilisateur a la possibilité de saisir à l'aide de l'action digit-argument, avant d'invoquer l'action. Si l'utilisateur n'entre pas de nombre, alors l'argument count est défini à 1. Nominalement, cet argument est interprété comme un nombre de répétitions, ce qui signifie que l'action devrait être répétée ce nombre de fois. En pratique, cependant, pour certaines actions, un nombre de répétitions a peu de sens. Dans de tels cas, les actions peuvent soit simplement ignorer l'argument count, soit utiliser sa valeur à une autre

fin.

Une copie de la ligne d'entrée actuelle est passée dans l'argument en lecture seule line. La position actuelle du curseur dans cette chaîne est donnée par l'index contenu dans l'argument curpos. Notez que la manipulation directe de la ligne d'entrée et de la position du curseur n'est pas autorisée. C'est parce que les règles dictées par divers modes, tels que le mode vi par rapport au mode emacs, le mode sans écho, et le mode insertion par rapport au mode surimpression, etc., rendent trop complexe pour un développeur d'application d'écrire une action d'édition conforme, et contraignent également les changements futurs des internes de gl_get_line(). Une solution potentielle à ce dilemme serait de permettre à la fonction d'action d'éditer la ligne à l'aide des actions d'édition existantes. Cela est actuellement à

l'étude.

Si la fonction d'action souhaite écrire du texte sur le terminal, sans que cela se mélange avec le texte affiché de la ligne d'entrée, ou lire du terminal sans avoir à gérer l'E/S brute du terminal, alors avant de faire l'une ou l'autre de ces opérations, elle doit suspendre temporairement l'édition de ligne en appelant la fonction gl_normal_io(). Cette fonction vide toute sortie en attente vers le terminal, déplace le curseur au début de la ligne suivant la dernière ligne du terminal de la ligne d'entrée, puis restaure le terminal à un état adapté à l'utilisation avec les fonctions stdio de C. Ce dernier comprend des choses comme la restauration du mappage normal de \n vers \r\n, et, en mode serveur, la restauration de la forme d'E/S de terminal bloquante normale. Après avoir appelé cette fonction, la fonction d'action peut lire et écrire sur le terminal sans craindre de créer un désordre. Il n'est pas nécessaire pour la fonction d'action de restaurer l'environnement d'édition original avant de retourner. Cela est fait automatiquement par gl_get_line() après le retour de la fonction d'action. Voici un exemple simple d'une fonction d'action qui écrit la phrase « Hello world » sur une nouvelle ligne du terminal après la ligne en cours d'édition. Lorsque cette fonction retourne, la ligne d'entrée est redessinée sur la ligne suivant la ligne « Hello world », et l'édition de ligne

reprend. 
  static GL_ACTION_FN(say_hello_fn)
  {
    if(gl_normal_io(gl))   /* Suspendre temporairement l'édition */
      return GLA_ABORT;
    printf("Hello world\n");
    return GLA_CONTINUE;
}

Les fonctions d'action doivent retourner l'une des valeurs suivantes, pour indiquer à gl_get_line() comment

procéder. 
  GLA_ABORT     -   Fait en sorte que gl_get_line() retourne NULL.
  GLA_RETURN    -   Fait en sorte que gl_get_line() retourne la
                    ligne d'entrée complétée.
  GLA_CONTINUE  -   Reprend l'édition de la ligne de
commande.

Notez que le argument name de gl_register_action() spécifie le nom par lequel un utilisateur peut référencer l'action dans son fichier de configuration. Cela lui permet de relier l'action à une séquence de touches alternative. Pour que cela fonctionne, il est nécessaire d'appeler gl_register_action() entre l'appel à new_GetLine() et le premier appel à gl_get_

lin
e().

ARCHIVAGE MANUEL DE

L'HISTORIQUE

Par défaut, chaque fois qu'une ligne est saisie par l'utilisateur, elle est automatiquement ajoutée à la liste d'historique, juste avant que gl_get_line() retourne la ligne à l'appelant. C'est pratique pour la majorité des applications, mais il existe aussi des applications qui ont besoin d'un contrôle plus fin sur ce qui est ajouté à la liste d'historique. Dans de tels cas, l'ajout automatique des lignes saisies à la liste d'historique peut être désactivé en appelant la fonction gl_automatic

  int gl_automatic_history(GetLine *gl, int enable)

Si cette fonction est appelée avec son argument enable défini à 0, gl_get_line() n'archivera pas automatiquement les lignes saisies ultérieurement. L'archivage automatique peut être réactivé plus tard, en appelant à nouveau cette fonction, avec son argument enable défini à 1. Tant que l'archivage automatique de l'historique est désactivé, l'application appelante peut utiliser gl_append_history() pour ajouter des lignes à la liste d'historique selon les

besoins. 
  int gl_append_history(GetLine *gl, const char *line)
;

L' argument line spécifie la ligne à ajouter à la liste d'historique. Cela doit être une chaîne normale terminée par ' '. Si cette chaîne contient des caractères de nouvelle ligne, la ligne archivée dans la liste d'historique sera terminée par le premier d'entre eux. Sinon, elle sera terminée par le terminateur ' '. Si la ligne est plus longue que la longueur maximale de ligne d'entrée, qui a été spécifiée lorsque new_GetLine() a été appelé, lorsque la ligne est rappelée, elle sera tronquée à la longueur réelle de la ligne de gl_get_li

ne().

En cas de succès, gl_append_history() retourne 0. Sinon, elle retourne une valeur non nulle, et définit errno à l'une des valeurs

suivantes.

              gl_append_history() était NULL.
   ENOMEM  -  La ligne spécifiée était plus longue que la taille allouée
              du tampon d'historique (telle que spécifiée lorsque
              new_GetLine() a été appelé), elle n'a donc pas pu être
archivée.

Une description textuelle de l'erreur peut être obtenue éventuellement en appelant gl_error_message(). La fonction constructrice new_GetLine() suppose que l'entrée doit être lue depuis stdin, et que la sortie est écrite vers stdout. La fonction suivante permet de basculer vers d'autres flux d'entrée et de

     polyvalente, elle implique d'assumer certaines

GESTION FIABLE DES SIGNAUX

La gestion des signaux est étonnamment difficile à faire de manière fiable sans conditions de concurrence. Dans gl_get_line(), beaucoup de soin a été apporté pour permettre aux applications d'effectuer une gestion fiable des signaux autour de gl_get_line(). Cette section explique comment en tirer parti.

Comme exemple des problèmes qui peuvent survenir si l'application n'est pas écrite correctement, imaginez qu'une application ait un gestionnaire de signaux SIGINT qui définit un drapeau global. Supposons maintenant que l'application teste ce drapeau juste avant d'invoquer gl_get_line(). Si un signal SIGINT est reçu dans la petite fenêtre de temps entre l'instruction qui teste la valeur de ce drapeau et l'instruction qui appelle gl_get_line(), alors gl_get_line() ne verra pas le signal et ne sera pas interrompu. En conséquence, l'application ne pourra pas répondre au signal jusqu'à ce que l'utilisateur ait fini de saisir la ligne d'entrée et que gl_get_line() revienne. Selon l'application, cela peut ou non être une catastrophe, mais au moins cela laisserait l'utilisateur perplexe.

La façon d'éviter de tels problèmes est de faire ce qui suit.

1. Si nécessaire, utilisez la fonction gl_trap_signal() pour configurer gl_get_line() afin qu'il avorte lorsque des signaux importants sont capturés.

2. Configurez gl_get_line() de telle sorte que si l'un des signaux qu'il capture est bloqué lors de l'appel à gl_get_line(), il sera automatiquement débloqué pendant les moments où gl_get_line() attend des E/S. Cela peut être fait soit sur une base de signal par signal, en appelant la fonction gl_trap_signal() et en spécifiant l'attribut GLS_UNBLOCK du signal, soit globalement en appelant la fonction gl_catch_blocked().

     void gl_catch_blocked(GetLine *gl);

Cette fonction ajoute simplement l'attribut GLS_UNBLOCK à tous les signaux qu'elle est actuellement configurée pour piéger.

3. Juste avant d'appeler gl_get_line(), bloquez la délivrance de tous les signaux que gl_get_line() est configuré pour piéger. Cela peut être fait en utilisant la fonction POSIX sigprocmask() en conjonction avec la fonction gl_list_signals().

      int gl_list_signals(GetLine *gl, sigset_t *set);

Cette fonction retourne l'ensemble des signaux qu'elle est actuellement configurée pour capturer dans l'argument set, qui est dans le format requis par sigprocmask().

4. Dans l'exemple, vous testeriez maintenant le drapeau global que le gestionnaire de signaux définit, sachant qu'il n'y a plus de danger que ce drapeau soit défini à nouveau tant que gl_get_line() ne débloque pas ses signaux pendant les E/S.

5. Finalement, gl_get_line() revient, soit parce qu'un signal a été capturé, qu'une erreur s'est produite, soit que l'utilisateur a fini de saisir sa ligne d'entrée.

6. Maintenant, vous testeriez à nouveau le drapeau de signal global et, s'il est défini, vous y répondriez et remettriez le drapeau à zéro.

7. Utilisez sigprocmask() pour débloquer les signaux qui étaient bloqués à l'étape 3.

La même technique peut être utilisée autour de certaines fonctions POSIX sensibles aux signaux, telles que sigsetjmp() et sigsuspend(), et en particulier, la première de ces deux fonctions peut être utilisée en conjonction avec siglongjmp() pour implémenter une gestion des signaux sans condition de concurrence autour d'autres appels système de longue durée. La manière de le faire est expliquée ensuite, en montrant comment gl_get_line() parvient à piéger de manière fiable les signaux autour des appels à des fonctions comme read() et select() sans conditions de concurrence.

La première chose que gl_get_line() fait, chaque fois qu'elle est appelée, est d'utiliser la fonction POSIX sigprocmask() pour bloquer la délivrance de tous les signaux qu'elle est actuellement configurée pour attraper. Ceci est redondant si l'application les a déjà bloqués, mais cela ne fait aucun mal. Elle annule cette étape juste avant de retourner.

Chaque fois que gl_get_line() doit appeler read() ou select() pour attendre une entrée de l'utilisateur, elle appelle d'abord la fonction POSIX sigsetjmp(), en s'assurant de spécifier une valeur non nulle pour son argument savesigs. La raison de ce dernier argument deviendra claire bientôt.

Si sigsetjmp() retourne zéro, gl_get_line() fait alors ce qui suit.

a. Elle utilise la fonction POSIX
   sigaction()
   pour enregistrer un gestionnaire de signaux temporaire pour tous les signaux
   qu'elle est configurée pour attraper. Ce gestionnaire de signaux fait deux choses.
   1. Il enregistre le numéro du signal reçu dans une variable au niveau du fichier.
   2. Il appelle ensuite la fonction POSIX
      siglongjmp()
      en utilisant le tampon qui a été passé à
      sigsetjmp()
      comme premier argument, et une valeur non nulle comme second argument.
   Lorsque ce gestionnaire de signaux est enregistré, le membre
   sa_mask
   de l'argument
   struct sigaction act
   de l'appel à
   sigaction()
   est configuré pour contenir tous les signaux que
   gl_get_line()
   capture. Cela garantit qu'un seul signal sera capturé à la fois par notre
   gestionnaire de signaux, ce qui garantit que plusieurs instances de notre
   gestionnaire de signaux ne se marcheront pas sur les pieds.
b. Maintenant que le gestionnaire de signaux est configuré,
   gl_get_line()
   débloque tous les signaux qu'elle est configurée pour attraper.
c. Elle appelle ensuite les appels système
   read()
   ou
   select()
   pour attendre une entrée du clavier.
d. Si cet appel système retourne (c'est-à-dire qu'aucun signal n'est reçu),
   gl_get_line()
   bloque à nouveau la délivrance des signaux d'intérêt.
e. Elle rétablit ensuite les gestionnaires de signaux qui ont été remplacés par
   celui qui vient d'être installé.

Alternativement, si sigsetjmp() retourne une valeur non nulle, cela signifie que o

l'un des signaux piégés a été capturé pendant l'exécution des étapes ci-dessus. Lorsque cela se produit, gl_get_line() fait ce qui

suit.

Tout d'abord, notez que lorsqu'un appel à siglongjmp() provoque le retour de sigsetjmp(), à condition que l'argument savesigs de sigsetjmp() soit non nul, comme spécifié ci-dessus, le masque de traitement des signaux est restauré à l'état dans lequel il se trouvait lorsque sigsetjmp() a été appelé. C'est la différence importante entre sigsetjmp() et l'ancien setjmp() problématique, et c'est l'ingrédient essentiel qui permet d'éviter les conditions de course dans la gestion des signaux. Grâce à cela, nous sommes garantis que tous les signaux que nous avons bloqués avant d'appeler sigsetjmp() sont de nouveau bloqués dès qu'un signal est capturé. Les instructions suivantes, qui sont alors exécutées, sont ainsi garanties de s'exécuter sans qu'aucun autre signal ne soit

capturé.

1. Si tel est l'instruction donné par les attributs de configuration de
gl_get_line() du signal qui a été capturé,
gl_get_line() restaure les attributs du terminal à
l'état dans lequel ils se trouvaient lorsque gl_get_line() a été
appelé. C'est particulièrement important pour les signaux qui
suspendent ou terminent le processus, car sinon le
terminal serait laissé dans un état

inutilisable.

2. Il réinstalle ensuite les gestionnaires de signaux de

l'application.

3. Il utilise ensuite la fonction raise()
de la bibliothèque standard C pour renvoyer à l'application le signal qui
a été

capturé.

3. Ensuite, il débloque la livraison du signal que nous venons de
envoyer. Cela a pour résultat que le signal qui vient d'être envoyé
via raise() est capturé par le gestionnaire de signal
original de l'application, qui peut maintenant le traiter comme il
l'entend

.

4. Si le gestionnaire de signal retourne (c'est-à-dire s'il ne termine pas
le processus), gl_get_line() bloque à nouveau la livraison du
signal

ci-dessus.

5. Il annule ensuite toute action effectuée dans la première des
étapes ci-dessus, et réaffiche la ligne, si la configuration du signal
l'exige

6. gl_get_line() reprend alors soit la tentative de
lecture d'un caractère, soit l'abandon, en fonction de la
configuration du signal qui a été

LA TAILLE DU

TERMINAL

Sur la plupart des systèmes, la combinaison de l'ioctl TIOCGWINSZ et du signal SIGWINCH est utilisée pour maintenir une idée précise de la taille du terminal. La taille du terminal est à nouveau interrogée à chaque fois que gl_get_line() est appelé et chaque fois qu'un signal SIGWINCH est

reçu.

Sur les quelques systèmes où ce mécanisme n'est pas disponible, au démarrage new_GetLine() cherche d'abord les variables d'environnement LINES et COLUMNS. Si celles-ci ne sont pas trouvées, ou si elles contiennent des valeurs inutilisables, alors si une base de données d'informations sur le terminal comme terminfo ou termcap est disponible, la taille par défaut du terminal est recherchée dans cette base de données. Si cela ne permet pas non plus de fournir la taille du terminal, une taille par défaut de 80 colonnes sur 24 lignes est

utilisée.

Même sur les systèmes qui prennent en charge ioctl(TIOCGWINSZ), si le terminal se trouve à l'autre extrémité d'une ligne série, le pilote de terminal n'a généralement aucun moyen de détecter quand un redimensionnement se produit ou d'interroger la taille actuelle. Dans de tels cas, aucun SIGWINCH n'est envoyé au processus, et les dimensions retournées par ioctl(TIOCGWINSZ) ne sont pas correctes. La seule façon de gérer de tels cas est de fournir un moyen à l'utilisateur d'entrer une commande qui indique au système distant quelle est la nouvelle taille. Cette commande appellerait alors la fonction gl_set_term_size() pour informer gl_get_line() du changement de

taille. 
  int gl_set_term_size(GetLine *gl, int ncolumn, int nline)
;

Les arguments ncolumn et nline sont utilisés pour spécifier les nouvelles dimensions du terminal et ne doivent pas être inférieurs à 1. Sur les systèmes qui prennent en charge ioctl(TIOCGWINSZ), cette fonction appelle d'abord ioctl(TIOCSWINSZ) pour informer le pilote du terminal du changement de taille. En mode E/S de serveur non bloquant, si une ligne est actuellement en cours de saisie, la ligne d'entrée est alors redessinée pour s'adapter à la taille modifiée. Enfin, les nouvelles valeurs sont enregistrées dans gl pour une utilisation future par gl_get_li

ne().

La fonction gl_terminal_size() vous permet d'interroger la taille actuelle du terminal et d'installer une taille de secours alternative pour les cas où la taille n'est pas disponible. Attention, la taille du terminal ne sera pas disponible lors de la lecture depuis un tube ou un fichier, de sorte que les valeurs par défaut peuvent être importantes même sur les systèmes qui prennent en charge des moyens de découvrir la taille du

terminal. 
  typedef struct {
    int nline;        /* Le terminal a nline lignes */
    int ncolumn;      /* Le terminal a ncolumn colonnes */
  } GlTerminalSize;
  GlTerminalSize gl_terminal_size(GetLine *gl,
                                  int def_ncolumn,
                                  int def_nline)
;

Cette fonction met d'abord à jour les dimensions de secours du terminal de gl_get_line(), puis enregistre ses résultats dans la valeur de

retour.

Les arguments def_ncolumn et def_nline spécifient le nombre par défaut de colonnes et de lignes du terminal à utiliser si la taille du terminal ne peut pas être déterminée via ioctl(TIOCGWINSZ) ou les variables

d'environnement
.

CACHER CE QUE VOUS

TAPEZ

Lors de la saisie d'informations sensibles, comme des mots de passe, il est préférable de ne pas faire écho sur le terminal du texte que vous saisissez. De plus, ce texte ne devrait pas être enregistré dans la liste d'historique, car quelqu'un trouvant votre terminal sans surveillance pourrait alors le rappeler, ou quelqu'un fouillant dans vos répertoires pourrait le voir dans votre fichier d'historique. En gardant cela à l'esprit, la fonction gl_echo_mode() vous permet d'activer et de désactiver l'affichage et l'archivage de tout texte qui est saisi par la suite dans les appels à gl_get_li

ne(). 
  int gl_echo_mode(GetLine *gl, int enable)
;

L'argument enable spécifie si le texte saisi doit être visible ou non. S'il est 0, les lignes saisies par la suite ne seront pas visibles sur le terminal et ne seront pas enregistrées dans la liste d'historique. S'il est 1, les lignes d'entrée suivantes seront affichées au fur et à mesure de leur saisie et, à condition que l'historique n'ait pas été désactivé via un appel à gl_toggle_history(), elles seront également archivées dans la liste d'historique. Enfin, si l'argument enable est -1, le mode d'écho est laissé inchangé, ce qui vous permet d'interroger le paramètre actuel de manière non destructive via la valeur de retour. Dans tous les cas, la valeur de retour de la fonction est 0 si l'écho était désactivé avant l'appel de la fonction, et 1 s'il était

activé.

Lorsque l'écho est désactivé, notez que même si l'achèvement par

tabulation complétera votre préfixe de manière invisible aussi loi
n que possible, les complétions ambiguës ne seront pas affichées.

REQUÊTES À CARACTÈRE

UNIQUE

Utiliser gl_get_line() pour demander à l'utilisateur une réponse d'un seul caractère est gênant pour l'utilisateur, car il doit appuyer sur la touche entrée ou retour avant que le caractère qu'il a tapé ne soit renvoyé au programme. C'est pourquoi la fonction gl_query_char() a été fournie pour les requêtes à un seul caractère comme

celle-ci. 
  int gl_query_char(GetLine *gl, const char *prompt,
                    char defchar)
;

Cette fonction affiche l'invite spécifiée au début d'une nouvelle ligne et attend que l'utilisateur tape un caractère. Lorsque l'utilisateur tape un caractère, gl_query_char() l'affiche à droite de l'invite, passe à la ligne suivante, puis renvoie le caractère au programme appelant. La valeur de retour de la fonction est le caractère qui a été tapé. Si la lecture a dû être interrompue pour une raison quelconque, EOF est renvoyé à la place. Dans ce dernier cas, l'application peut appeler la fonction précédemment documentée gl_return_status() pour savoir ce qui s'est mal passé. Il peut s'agir, par exemple, de la réception d'un signal ou de l'expiration du minuteur d'inactivité

optionnel.

Si l'utilisateur appuie simplement sur entrée, la valeur de l'argument defchar est substituée. Cela signifie que lorsque l'utilisateur appuie sur nouvelle ligne ou retour, le caractère spécifié dans defchar est affiché après l'invite, comme si l'utilisateur l'avait tapé, et est également renvoyé à l'application appelante. Si un tel remplacement n'est pas important, passez simplement '0 comme valeur de defchar

.

Si le caractère saisi est un caractère non imprimable, il est affiché symboliquement. Par exemple, contrôle-A est affiché comme ^A, et les caractères au-delà de 127 sont affichés en octal, précédés d'une barre oblique

inverse.

Comme pour gl_get_line(), l'écho du caractère saisi peut être désactivé à l'aide de la fonction gl_echo_mode()

.

Si le processus appelant est suspendu pendant qu'il attend que l'utilisateur tape sa réponse, le curseur est déplacé sur la ligne suivant la ligne d'invite, puis lorsque le processus reprend, l'invite est réaffichée, et gl_query_char() reprend l'attente que l'utilisateur tape un

caractère.

Notez qu'en mode serveur non bloquant, (voir gl_io_mode(3)), si une ligne d'entrée incomplète est en cours de lecture lorsque gl_query_char() est appelé, la ligne d'entrée partielle est abandonnée et effacée du terminal avant que la nouvelle invite ne soit affichée. L'appel suivant à gl_get_line() commencera donc

à éditer une n
ouvelle ligne.

LIRE DES CARACTÈRES

BRUTS

Alors que la fonction gl_query_char() invite visiblement l'utilisateur à entrer un caractère et affiche ce qu'il a tapé, la fonction gl_read_char() lit un caractère du clavier de l'utilisateur, sans rien écrire sur le terminal ni perturber une ligne d'entrée incomplète. Cela signifie qu'elle peut être appelée non seulement entre les appels à gl_get_line(), mais aussi depuis des fonctions de rappel que l'application a enregistrées pour être appelées par gl_get_li

ne(). 
  int gl_read_char(GetLine *gl)
;

En cas de succès, la valeur de retour de gl_read_char() est le caractère qui a été lu. En cas d'échec, EOF est renvoyé, et la fonction gl_return_status() peut être appelée pour savoir ce qui s'est mal passé. Les possibilités incluent l'expiration du minuteur d'inactivité optionnel, la réception d'un signal configuré pour interrompre gl_get_line(), ou le blocage des E/S du terminal, en mode E/S de serveur non

bloquant.

Attention, certaines touches du clavier, comme les touches de fonction et les touches de direction, génèrent généralement au moins 3 caractères chacune, de sorte qu'un seul appel à gl_read_char() net be enough t

o identify suc
h keystrokes.

AFFICHER DU TEXTE DE MANIÈRE

DYNAMIQUE

Entre les appels à gl_get_line(), la fonction gl_display_text() fournit un moyen pratique d'afficher des paragraphes de texte, justifiés à gauche et répartis sur une ou plusieurs lignes du terminal en fonction des contraintes de la largeur actuelle du terminal. Des exemples d'utilisation de cette fonction se trouvent dans les programmes de démonstration, où elle est utilisée pour afficher des introductions. Dans ces exemples, l'utilisation avancée de préfixes, suffixes et lignes de remplissage optionnels pour dessiner un cadre autour du texte est également

illustrée. 
  int gl_display_text(GetLine *gl, int indentation,
                      const char *prefix,
                      const char *suffix, int fill_char,
                      int def_width, int start,
                      const char *string)
;

Si gl n'est pas actuellement connecté à un terminal, par exemple si la sortie d'un programme qui utilise gl_get_line() est acheminée via un pipe vers un autre programme ou redirigée vers un fichier, alors la valeur du paramètre def_width est utilisée comme largeur du

terminal.

L' argument indentation spécifie le nombre de caractères à utiliser pour indenter chaque ligne de sortie. L' argument fill_char spécifie le caractère qui sera utilisé pour effectuer cette

indentation.

L' argument prefix peut être soit NULL, soit une chaîne à placer au début de chaque nouvelle ligne (après toute indentation). De même, l' argument suffix peut être soit NULL, soit une chaîne à placer à la fin de chaque ligne. Le suffixe est placé à fleur du bord droit du terminal, et tout espace entre son premier caractère et le dernier mot de cette ligne est rempli par le caractère spécifié via l'argument fill_char. Normalement, le caractère de remplissage est une

espace.

L' argument start indique à gl_display_text() combien de caractères ont déjà été écrits sur la ligne de terminal actuelle, et indique donc l'index de colonne de départ du curseur. Puisque la valeur de retour de gl_display_text() est l'index de colonne de fin du curseur, en passant la valeur de retour d'un appel à l'argument start de l'appel suivant, un paragraphe qui est interrompu entre plus d'une chaîne peut être composé en appelant gl_display_text() pour chaque portion successive du paragraphe. Notez que des caractères de retour à la ligne littéraux sont nécessaires à la fin de chaque paragraphe pour forcer le début d'une nouvelle

ligne.

En cas d'erreur, gl_display_tex

t() renv
oie -1.

JEUX DE CARACTÈRES

INTERNATIONAUX

Depuis la version 1.4.0 de libtecla, gl_get_line() est propre aux 8 bits. Cela signifie que tous les caractères sur 8 bits qui sont imprimables dans la locale actuelle de l'utilisateur sont maintenant affichés tels quels et inclus dans la ligne d'entrée renvoyée. En supposant que le programme appelant contient correctement un appel comme le

suivant, 
  setlocale(LC_CTYPE, "")
;

alors la locale actuelle est déterminée par la première des variables d'environnement LC_CTYPE, LC_ALL, et LANG, dont on trouve qu'elle contient un nom de locale valide. Si aucune de ces variables n'est définie, ou si le programme néglige d'appeler setlocale, alors la locale par défaut C est utilisée, qui est l'ASCII 7 bits américain. Sur la plupart des plateformes de type unix, vous pouvez obtenir une liste des locales valides en tapant la commande

: 
  locale
-a

à l'invite du shell. Une documentation supplémentaire sur la manière dont l'utilisateur peut utiliser cela pour saisir des caractères internationaux se trouve dans la page de manu

el tec
la(7).

THREADS

Dans un programme multi-thread, vous devriez utiliser la version libtecla_r.a de la bibliothèque. Celle-ci utilise des versions réentrantes des fonctions système, lorsqu'elles sont disponibles. Malheureusement, ni terminfo ni termcap n'ont été conçus pour être réentrants, vous ne p

ndant, en raison de l'utilisation de fonctions POSIX réentrantes pour la recherche des répertoires personnels etc., il est sûr d'utiliser ce module depuis un seul thread d'un programme multi-thread, à condition que vos autres threads n'utilisent aucune fonction termcap ou terminfo.
