DESCRIPTION

La fonction gl_get_line() fait partie de la bibliothèque tecla (voir la page de manuel libtecla(3)). Si l'utilisateur tape au terminal, chaque appel lui demande une ligne d'entrée, puis fournit des installations d'édition interactives, similaires à celles du shell tcsh de unix. En plus de l'édition simple de ligne de commande, elle prend en charge le rappel des lignes de commande précédemment saisies, l'achèvement par TAB des noms de fichiers et le développement de motifs de noms de fichiers en ligne. La documentation des fonctionnalités d'édition de ligne de commande au niveau utilisateur et de toutes les options de configuration utilisateur se trouve dans la page de manuel tecla(7). Cette page de manuel concerne la documentation pour les programmeurs intéressés par l'utilisation de cette bibliothèque dans leur application.

UN EXEMPLE

Ce qui suit montre un exemple complet d'utilisation de la fonction gl_get_line() pour obtenir des entrées de l'utilisateur :

  #include <stdio.h>
  #include <locale.h>
  #include <libtecla.h>
  int main(int argc, char *argv[])
  { 
    char *line;    /* La ligne que l'utilisateur a tapée */
    GetLine *gl;   /* L'objet de ressources gl_get_line() */
    setlocale(LC_CTYPE, ""); /* Adopter le choix de l'utilisateur */
                             /* de jeu de caractères. */
    gl = new_GetLine(1024, 2048);
    if(!gl)
      return 1;
    while((line=gl_get_line(gl, "$ ", NULL, -1)) != NULL &&
           strcmp(line, "exit\n") != 0)
      printf("Vous avez tapé : %s\n", line);
    gl = del_GetLine(gl);
    return 0;
  }

Dans l'exemple, d'abord les ressources nécessaires à la fonction gl_get_line() sont créées en appelant new_GetLine(). Ceci alloue la mémoire utilisée dans les appels ultérieurs à la fonction gl_get_line(), y compris le tampon d'historique pour l'enregistrement des lignes précédemment saisies. Ensuite, une ou plusieurs lignes sont lues depuis l'utilisateur, jusqu'à ce qu'une erreur se produise, ou que l'utilisateur tape exit. Enfin, les ressources qui ont été allouées par new_GetLine(), sont retournées au système en appelant del_GetLine(). Notez l'utilisation de la valeur de retour NULL de del_GetLine() pour rendre gl NULL. C'est une mesure de sécurité. Si le programme tente ensuite de passer gl à gl_get_line(), cette fonction se plaindra et retournera une erreur, au lieu d'essayer d'utiliser l'objet ressource supprimé.

LES FONCTIONS UTILISÉES DANS L'EXEMPLE

Les descriptions des fonctions utilisées dans l'exemple sont les suivantes :

  GetLine *new_GetLine(size_t linelen, size_t histlen)

Cette fonction crée les ressources utilisées par la fonction gl_get_line() et retourne un pointeur opaque vers l'objet qui les contient. La longueur maximale d'une ligne d'entrée est spécifiée via l'argument linelen, et le nombre d'octets à allouer pour stocker les lignes d'historique est défini par l'argument histlen. Les lignes d'historique sont stockées côte à côte dans un seul tampon de cette taille. Notez que cela signifie que le nombre de lignes d'historique pouvant être stockées à tout moment dépend de la longueur des lignes individuelles. Si vous souhaitez définir une limite supérieure au nombre de lignes pouvant être stockées, consultez la fonction gl_limit_history() décrite plus loin. Si vous ne voulez pas d'historique du tout, spécifiez histlen comme zéro, et aucun tampon d'historique ne sera alloué.

En cas d'erreur, un message est imprimé sur stderr et NULL est retourné.

  GetLine *del_GetLine(GetLine *gl)

Cette fonction supprime les ressources qui ont été retournées par un appel précédent à new_GetLine(). Elle retourne toujours NULL (c'est-à-dire un objet supprimé). Elle ne fait rien si l'argument gl est NULL.

  char *gl_get_line(GetLine *gl, const char *prompt,
                   const char *start_line, int start_pos);

La fonction gl_get_line() peut être appelée un nombre quelconque de fois pour lire des entrées de l'utilisateur. L'argument gl doit avoir été précédemment retourné par un appel à new_GetLine(). L'argument prompt doit être une chaîne de caractères normale terminée par NUL, spécifiant l'invite à présenter à l'utilisateur. Par défaut, les invites sont affichées littéralement, mais si elles sont activées avec la fonction gl_prompt_style() (voir plus loin), les invites peuvent contenir des directives pour souligner, passer du texte normal au texte en gras ou vice versa, ou activer et désactiver la mise en surbrillance.

Si vous souhaitez spécifier le contenu initial de la ligne, que l'utilisateur pourra modifier, passez la chaîne désirée via l'argument start_line. Vous pouvez ensuite spécifier quel caractère de cette ligne le curseur est initialement positionné

If you don't want to preload the line in this manner, send start_line as NULL, and set start_pos to -1. Note that the line pointer returned by one call to gl_get_line() can be passed back to the next call to gl_get_line() via the start_line. This allows the application to take the last entered line, and if it contains an error, to then present it back to the user for re-editing, with the cursor initially positioned where the error was encountered.

The gl_get_line() function returns a pointer to the line entered by the user, or NULL on error or at the end of the input. The returned pointer is part of the specified gl resource object, and thus should not be free'd by the caller, or assumed to be unchanging from one call to the next. When reading from a user at a terminal, there will always be a newline character at the end of the returned line. When standard input is being taken from a pipe or a file, there will similarly be a newline unless the input line was too long to store in the internal buffer. In the latter case you should call gl_get_line() again to read the rest of the line. Note that this behavior makes gl_get_line() similar to fgets(). In fact when stdin isn't connected to a terminal,gl_get_line() just calls fgets().

ÉTAT DE RETOUR DE GL_GET_LINE

Comme décrit ci-dessus, la fonction gl_get_line() a deux valeurs de retour possibles ; un pointeur vers la ligne d'entrée complétée, ou NULL. Des informations supplémentaires sur ce qui a causé le retour de gl_get_line() sont disponibles à la fois en inspectant errno, et en appelant la fonction gl_return_status() .

  GlReturnStatus gl_return_status(GetLine *gl);

Voici les valeurs énumérées possibles que cette fonction retourne.

  GLR_NEWLINE     -  Le dernier appel à gl_get_line()
                     a retourné avec succès une ligne d'entrée
                     complétée.
  GLR_BLOCKED     -  gl_get_line() était en mode serveur non-bloquant
                     et est retourné tôt pour éviter de bloquer le
                     processus en attendant les E/S du terminal. La fonction
                     gl_pending_io() peut être utilisée pour voir quel type
                     d'E/S
                     gl_get_line() attendait. (voir la page de
                     man gl_io_mode(3) pour plus de détails).
  GLR_SIGNAL      -  Un signal a été capté par
                     gl_get_line() qui avait une disposition après-signal de
                     GLS_ABORT (voir gl_trap_signal()).
  GLR_TIMEOUT     -  Le minuteur d'inactivité a expiré pendant que
                     gl_get_line() attendait une entrée, et la fonction de rappel
                     de délai d'attente a retourné GLTO_ABORT. Voir gl_inactivity_timeout() pour des informations sur les délais d'attente.
  GLR_FDABORT     -  Un rappel d'E/S d'application a retourné
                     GLFD_ABORT (voir gl_watch_fd()).
  GLR_EOF         -  Fin de fichier atteinte. Cela peut se
                     produire lorsque l'entrée provient d'un fichier ou
                     d'un tube, au lieu du terminal. Cela se produit aussi
                     si l'utilisateur invoque les actions
                     list-or-eof ou del-char-or-list-or-eof
                     au début d'une nouvelle ligne.
  GLR_ERROR       -  Une erreur inattendue a causé
                     gl_get_line() d'interrompre (consultez
                     errno et/ou
                     gl_error_message() pour plus de détails).

Quand gl_return_status() retourne GLR_ERROR, et que la valeur de errno n'est pas suffisante pour expliquer ce qui s'est passé, vous pouvez utiliser la fonction gl_error_message() pour demander une description de la dernière erreur survenue.

  const char *gl_error_message(GetLine *gl, char *buff,
                               size_t n);

La valeur de retour est un pointeur vers le message survenu. Si l'argument buff est NULL, ce sera un pointeur vers un tampon dans gl, dont la valeur changera probablement au prochain appel à toute fonction associée à gl_get_line(). Sinon, si un argument non-NULL buff est fourni, le message d'erreur, y compris le terminateur '\0' , sera écrit dans les premiers n éléments de ce tampon, et la valeur de retour sera un pointeur vers le premier élément de ce tampon. Si le message ne tient pas dans le tampon fourni, il sera tronqué pour tenir.

SOURCES DE CONFIGURATION ALTERNATIVES

Comme mentionné ci-dessus, par défaut les utilisateurs ont la possibilité de configurer le comportement de gl_get_line() via un fichier de configuration appelé .teclarc dans leurs répertoires personnels. Le fait que toutes les applications partagent ce même fichier de configuration est à la fois un avantage et un inconvénient. Dans la plupart des cas c'est un avantage, car cela encourage l'uniformité et libère l'utilisateur de devoir configurer chaque application séparément. Dans certaines applications, cependant, ce moyen unique de configuration pose problème. C'est particulièrement vrai pour les logiciels embarqués, où il n'y a pas de système de fichiers pour lire un fichier de configuration, et aussi dans les applications où un choix radicalement différent de mappages de touches est nécessaire pour émuler une interface de clavier héritée. Pour prendre en charge de tels cas, la fonction suivante permet à l'application de contrôler d'où les informations de configuration sont lues.

  int gl_configure_getline(GetLine *gl,
                           const char *app_string,
                           const char *app_file,
                           const char *user_file);

Elle permet aux commandes de configuration qui seraient normalement lues depuis le fichier ~/.teclarc d'un utilisateur, d'être lues depuis un ou plusieurs, ou aucun, de : une chaîne, un fichier de configuration spécifique à l'application, et/ou un fichier de configuration spécifique à l'utilisateur. Si cette fonction est appelée avant le premier appel à gl_get_line(), le comportement par défaut de lire ~/.teclarc au premier appel à gl_get_line() est désactivé ; toute la configuration doit donc être réalisée en utilisant les sources de configuration spécifiées avec cette fonction.

Si app_string != NULL, alors elle est interprétée comme une chaîne contenant une ou plusieurs commandes de configuration, séparées les unes des autres dans la chaîne par des caractères de retour à la ligne incorporés. Si app_file != NULL alors elle est interprétée comme le chemin complet d'un fichier de configuration spécifique à l'application. Si user_file != NULL alors elle est interprétée comme le chemin complet d'un fichier de configuration spécifique à l'utilisateur, tel que ~/.teclarc. Par exemple, dans l'appel suivant,

  gl_configure_getline(gl, "edit-mode vi \n nobeep",
                           "/usr/share/myapp/teclarc",
                           "~/.teclarc");

l'argument app_string fait que l'application appelante démarre en mode d'édition vi, au lieu du mode emacs par défaut, et désactive l'utilisation de la cloche du terminal par la bibliothèque. Elle essaie ensuite de lire des commandes de configuration à l'échelle du système depuis un fichier facultatif appelé /usr/share/myapp/teclarc, puis lit enfin des commandes de configuration spécifiques à l'utilisateur depuis un fichier .teclarc facultatif dans le répertoire personnel de l'utilisateur. Notez que les arguments sont listés par ordre de priorité croissante, le contenu de app_string pouvant être potentiellement remplacé par des commandes dans app_file, et les commandes dans app_file pouvant être potentiellement remplacées par des commandes dans user_file.

Vous pouvez appeler cette fonction autant de fois que nécessaire, les résultats étant cumulatifs, mais notez que les copies de tout nom de fichier spécifié via le app_file et user_file sont enregistrés en interne pour une utilisation ultérieure par la read-init-files fonction de liaison de touche ; si vous prévoyez d'appeler cette fonction plusieurs fois, assurez-vous que le dernier appel spécifie les noms de fichiers que vous souhaitez relire lorsque l'utilisateur demande que les fichiers de configuration soient relus.

Les séquences de touches individuelles peuvent également être liées et déliées à l'aide de la gl_bind_keyseq() fonction.

  int gl_bind_keyseq(GetLine *gl, GlKeyOrigin origin,
                     const char *keyseq,
                     const char *action);

L' origin argument spécifie la priorité de la liaison, selon qui elle est établie, et doit être l'une des deux valeurs suivantes.

  GL_USER_KEY   -   L'utilisateur a demandé cette liaison de touche.
  GL_APP_KEY    -   Ceci est une liaison par défaut définie par
                    l'application.

Lorsque des liaisons utilisateur et application pour une même séquence de touches ont été spécifiées, la liaison utilisateur a la priorité. La liaison de l'application est rétablie ultérieurement si la liaison de l'utilisateur est déliée plus tard via un autre appel à cette fonction, ou un appel à gl_configure_getline().

L' keyseq argument spécifie la séquence de touches à lier ou à délier, et est exprimée de la même manière que dans un ~/.teclarc fichier de configuration. L' action argument doit soit être une chaîne contenant le nom de l'action à laquelle lier la séquence de touches, ou il doit être NULL ou "" pour délier la séquence de touches.

COMPLÉTION DE MOTS PERSONNALISÉE

Si dans votre application, vous souhaitez que la complétion par TAB complète d'autres choses en plus des noms de fichiers ou à leur place, vous pouvez organiser cela en enregistrant une fonction de rappel de complétion alternative, via un appel à la gl_customize_completion() fonction.

  int gl_customize_completion(GetLine *gl, void *data,
                              CplMatchFn *match_fn);

L' data argument fournit un moyen pour votre application de passer des informations arbitraires, spécifiques à l'application, à la fonction de rappel. Celles-ci sont passées à la fonction de rappel à chaque fois qu'elle est appelée. Elle pourrait par exemple, pointer vers la table de symboles à partir de laquelle les complétions possibles doivent être recherchées. L' match_fn argument spécifie la fonction de rappel à appeler. Le type de fonction CplMatchFn est défini dans libtecla.h, tout comme une macro CPL_MATCH_FN() que vous pouvez utiliser pour déclarer et prototyper des fonctions de rappel. La déclaration et les responsabilités des fonctions de rappel sont décrites en profondeur dans la page de manuel cpl_complete_word(3).

En bref, la fonction de rappel est responsable de la recherche vers l'arrière dans la ligne d'entrée, en remontant depuis le point où l'utilisateur a appuyé sur TAB, pour trouver le début du mot en cours de complétion. Elle doit ensuite rechercher les complétions possibles de ce mot, et les enregistrer une par une dans l'objet WordCompletion qui lui est passé en argument, en appelant la cpl_add_completion() fonction. Si la fonction de rappel souhaite fournir une complétion de nom de fichier en plus de ses propres complétions spécifiques, elle a la possibilité d'appeler elle-même la fonction de rappel de complétion de nom de fichier intégrée. Ceci est également documenté dans la cpl_complete_word(3) page de manuel.

Notez que si vous souhaitez que gl_get_line() retourne la ligne d'entrée actuelle lorsqu'une complétion réussie a été effectuée, vous pouvez organiser cela lorsque vous appelez cpl_add_completion(), en faisant du dernier caractère du suffixe de continuation un caractère de nouvelle ligne. Si vous faites cela, la ligne d'entrée sera mise à jour pour afficher la complétion, avec tout suffixe de continuation jusqu'au caractère de nouvelle ligne, puis gl_get_line() retournera cette ligne d'entrée.

Si, pour une raison quelconque, votre fonction de rappel doit écrire quelque chose sur le terminal, elle doit appeler gl_normal_io() avant de le faire. Cela commencera une nouvelle ligne après la ligne d'entrée actuellement en cours d'édition, rétablira l'E/S normale du terminal, et indiquera à gl_get_line() que la ligne d'entrée devra être redessinée lorsque la fonction de rappel retournera.

AJOUTER DES ACTIONS DE COMPLÉTION

Dans la section précédente, la capacité de personnaliser le comportement de la seule action de complétion par défaut, complete-word, a été décrite. Dans cette section, la capacité d'installer des fonctions d'action supplémentaires, afin que différents types de complétion de mots puissent être liés à différentes séquences de touches, est décrite. Ceci est réalisé en utilisant la gl_completion_action() fonction.

  int gl_completion_action(GetLine *gl,
                           void *data, CplMatchFn *match_fn,
                           int list_only, const char *name,
                           const char *keyseq);

Les arguments data et match_fn sont comme décrits dans la page de manuel cpl_complete_word , et spécifient la fonction de rappel qui doit être invoquée pour identifier les complétions possibles. L' list_only argument détermine si l'action qui est en cours de définition doit tenter de compléter le mot aussi loin que possible dans la ligne d'entrée avant d'afficher toute complétion ambiguë possible, ou si elle doit simplement afficher la liste des complétions possibles sans toucher à la ligne d'entrée. La première option est sélectionnée en spécifiant une valeur de 0, et la seconde en spécifiant une valeur de 1. L' name argument spécifie le nom par lequel les fichiers de configuration et les futures invocations de cette fonction doivent faire référence à l'action. Cela doit soit être le nom d'une action de complétion existante à modifier, ou un nouveau nom non utilisé pour une nouvelle action. Enfin, l' keyseq argument spécifie la séquence de touches par défaut à lier à l'action. Si c'est NULL, aucune nouvelle séquence de touches ne sera liée à l'action.

Attention, pour que l'utilisateur puisse changer la séquence de touches liée aux actions installées de cette manière, lorsque vous appelez gl_completion_action() pour installer une action donnée pour la première fois, vous devriez le faire entre l'appel à new_GetLine() et le premier appel à gl_get_line(). Sinon, lorsque le fichier de configuration de l'utilisateur est lu lors du premier appel à gl_get_line(), le nom de votre action supplémentaire ne sera pas connu, et toute référence à elle dans le fichier de configuration générera une erreur.

Comme discuté pour gl_customize_completion(), si votre fonction de rappel, pour une raison quelconque, doit écrire quoi que ce soit sur le terminal, elle doit appeler gl_normal_io() avant de le faire.

DÉFINIR DES ACTIONS PERSONNALISÉES

Bien que les actions de liaison de touches intégrées soient suffisantes pour les besoins de la plupart des applications, parfois une application spécialisée peut avoir besoin de définir une ou plusieurs actions personnalisées, liées à des séquences de touches spécifiques à l'application. Par exemple, une application de vente bénéficierait d'avoir une séquence de touches qui affichait le nom de la pièce correspondant à un numéro de pièce précédant le curseur. Une telle fonctionnalité est clairement au-delà du champ d'application des fonctions d'action intégrées. Ainsi, pour de tels cas particuliers, la gl_register_action() fonction est fournie.

  int gl_register_action(GetLine *gl, void *data,
			 GlActionFn *fn, const char *name,
			 const char *keyseq);

Cette fonction permet à l'application d'enregistrer une fonction externe, fn, qui sera ensuite appelée chaque fois que soit la séquence de touches spécifiée, keyseq, est saisie par l'utilisateur, ou que l'utilisateur saisit toute autre séquence de touches que l'utilisateur lie ensuite au nom d'action spécifié, name, dans son fichier de configuration. L' data argument peut être un pointeur vers n'importe quoi que l'application souhaite voir passer à la fonction d'action, fn, chaque fois que cette fonction est invoquée.

La fonction d'action, fn, devrait être déclarée en utilisant la macro suivante, qui est définie dans libtecla.h.

  #define GL_ACTION_FN(fn) GlAfterAction (fn)(GetLine *gl, \
              void *data, int count, size_t curpos, \
              const char *line)

Les arguments gl et data sont ceux qui ont été précédemment passés à gl_register_action() lorsque la fonction d'action a été enregistrée. L' count argument est un argument numérique que l'utilisateur a la possibilité de saisir en utilisant l'action digit-argument , avant d'invoquer l'action. Si l'utilisateur n'entre pas de nombre, alors l' count argument est défini à 1. Nominalement, cet argument est interprété comme un nombre de répétitions, signifiant que l'action devrait être répétée ce nombre de fois. En pratique cependant, pour certaines actions un nombre de répétitions n'a que peu de sens. Dans de tels cas, les actions peuvent soit simplement ignorer l' count argument, ou utiliser sa valeur à une fin différente.

Une copie de la ligne d'entrée actuelle est passée dans l'argument en lecture seule line . La position actuelle du curseur dans cette chaîne est donnée par l'index contenu dans l' curpos argument. Notez que la manipulation directe de la ligne d'entrée et de la position du curseur n'est pas autorisée. C'est parce que les règles dictées par divers modes, comme le mode vi versus le mode emacs, le mode sans écho, et le mode insertion versus le mode sur frappe etc, rendent cela trop complexe pour qu'un développeur d'application puisse écrire une action d'édition conforme, ainsi que pour contraindre les changements futurs aux internes de gl_get_line(). Une solution potentielle à ce dilemme serait de permettre à la fonction d'action d'éditer la ligne en utilisant les actions d'édition existantes. Ceci est actuellement à l'étude.

Si la fonction d'action souhaite écrire du texte sur le terminal, sans que cela se mélange avec le texte affiché de la ligne d'entrée, ou lire depuis le terminal sans avoir à gérer l'E/S brute du terminal, alors avant de faire l'une de ces opérations, elle doit temporairement suspendre l'édition de ligne en appelant la gl_normal_io() fonction. Cette fonction vide toute sortie en attente vers le terminal, déplace le curseur au début de la ligne qui suit la dernière ligne du terminal de la ligne d'entrée, puis restaure le terminal à un état adapté à l'utilisation avec les fonctionnalités stdio du C. Ce dernier inclut des choses comme restaurer le mappage normal de \n vers \r\n, et, en mode serveur, restaurer la forme bloquante normale de l'E/S du terminal. Après avoir appelé cette fonction, la fonction d'action peut lire depuis et écrire vers le terminal sans crainte de créer un désordre. Il n'est pas nécessaire pour la fonction d'action de restaurer l'environnement d'édition original avant de retourner. Cela est fait automatiquement par gl_get_line() après le retour de la fonction d'action. Voici un exemple simple d'une fonction d'action qui écrit la phrase "Hello world" sur une nouvelle ligne du terminal après la ligne en cours d'édition. Lorsque cette fonction retourne, la ligne d'entrée est redessinée sur la ligne qui suit la ligne "Hello world", et l'édition de ligne reprend.

  static GL_ACTION_FN(say_hello_fn)
  {
    if(gl_normal_io(gl))   /* Suspendre temporairement l'édition */
      return GLA_ABORT;
    printf("Bonjour le monde\n");
    return GLA_CONTINUE;
  }

Les fonctions d'action doivent renvoyer l'une des valeurs suivantes, pour indiquer à gl_get_line() comment procéder.

  GLA_ABORT     -   Faire retourner NULL à gl_get_line().
  GLA_RETURN    -   Faire retourner à gl_get_line() la
                    ligne d'entrée complétée.
  GLA_CONTINUE  -   Reprendre l'édition de la ligne de commande.

Notez que l'argument name de gl_register_action() spécifie le nom par lequel un utilisateur peut faire référence à l'action dans son fichier de configuration. Cela lui permet de remapper l'action à une séquence de touches alternative. Pour que cela fonctionne, il est nécessaire d'appeler gl_register_action() entre l'appel à new_GetLine() et le premier appel à gl_get_line().

FICHIERS HISTORIQUES

Pour sauvegarder le contenu du tampon d'historique avant de quitter votre application, et le restaurer ensuite lors du prochain démarrage de l'application, les fonctions suivantes sont fournies.

 int gl_save_history(GetLine *gl, const char *filename,
                     const char *comment, int max_lines);
 int gl_load_history(GetLine *gl, const char *filename,
                     const char *comment);

L'argument filename spécifie le nom à donner au fichier d'historique lors de la sauvegarde, ou le nom d'un fichier d'historique existant, lors du chargement. Il peut contenir des expressions de répertoire personnel et de variables d'environnement, telles que "~/.myapp_history" ou "$HOME/.myapp_history".

Avec chaque ligne d'historique, des informations supplémentaires à son sujet, telles que quand elle a été entrée par l'utilisateur, et quel est son niveau d'imbrication, sont enregistrées comme un commentaire précédant la ligne dans le fichier d'historique. L'écriture de ces informations en tant que commentaires permet au fichier d'historique de servir également de fichier de commandes, au cas où vous souhaiteriez rejouer une session entière à l'aide de celui-ci. Comme les préfixes de commentaires diffèrent selon les langages, l'argument comment est fourni pour spécifier le préfixe de commentaire. Par exemple, si votre application était un shell unix, tel que le shell bourne, vous spécifieriez "#" ici. Quel que soit le caractère de commentaire que vous choisissez, vous devez spécifier le même préfixe à gl_load_history() que celui que vous avez utilisé lorsque vous avez appelé gl_save_history() pour écrire le fichier d'historique.

L'argument max_lines doit être -1 pour spécifier que toutes les lignes de la liste d'historique doivent être sauvegardées, ou un nombre positif spécifiant un plafond sur le nombre de lignes les plus récentes à sauvegarder.

Les deux fonctions renvoient une valeur non nulle en cas d'erreur, après avoir écrit un message d'erreur sur stderr. Notez que gl_load_history() ne considère pas la non-existence d'un fichier comme une erreur.

LISTES HISTORIQUES MULTIPLES

Si votre application utilise un seul objet GetLine pour entrer de nombreux types différents de lignes d'entrée, vous pourriez souhaiter que gl_get_line() distingue les différents types de lignes dans la liste d'historique, et ne rappelle que les lignes qui correspondent au type de ligne actuel. Pour répondre à cette exigence, gl_get_line() marque les lignes enregistrées dans la liste d'historique avec un identifiant entier choisi par l'application. Initialement, cet identifiant est réglé à 0 par new_GetLine(), mais il peut être modifié ultérieurement en appelant gl_group_history().

  int gl_group_history(GetLine *gl, unsigned id);

L'identifiant entier id peut être n'importe quel nombre choisi par l'application, mais notez que gl_save_history() et gl_load_history() préservent l'association entre les identifiants et les lignes d'entrée historiques entre les invocations du programme, vous devriez donc choisir des identifiants fixes pour les différents types de lignes utilisés par votre application.

Chaque fois que gl_get_line() ajoute une nouvelle ligne d'en- trée à la liste d'historique, l'identifiant d'historique actuel est enregistré avec elle, et lorsqu'il est demandé de rappeler une ligne d'entrée historique, il ne rappelle que les lignes marquées avec l'identifiant actuel.

AFFICHAGE DE L'HISTORIQUE

La liste d'historique peut être affichée en appelant gl_show_history().

  int gl_show_history(GetLine *gl, FILE *fp,
                      const char *fmt,
                      int all_groups,
                      int max_lines);

Ceci affiche le contenu actuel de la liste d'historique sur le flux de sortie stdio fp. Si l'argument max_lines est supérieur ou égal à zéro, alors pas plus que ce nombre de lignes les plus récentes ne sera affiché. Si l'argument all_groups est non nul, les lignes de tous les groupes d'historique sont affichées. Sinon, seules celles du groupe d'historique actuellement sélectionné sont affichées. L'argument de chaîne de format, fmt, détermine comment la ligne est affichée. Il peut contenir des caractères arbitraires qui sont écrits tels quels, entrelacés avec l'un des directifs de format suivants :

  %D  -  La date à laquelle la ligne a été initialement
         entrée, formatée comme 2001-11-20.
  %T  -  L'heure de la journée à laquelle la ligne a été
         entrée, formatée comme 23:59:59.
  %N  -  Le numéro séquentiel d'entrée de la ligne dans
         le tampon d'historique.
  %G  -  Le numéro du groupe d'historique auquel la
         ligne appartient.
  %%  -  Un caractère % littéral.
  %H  -  La ligne d'historique elle-même.

Ainsi, une chaîne de format comme "%D %T %H0 produirait quelque chose comme :

  2001-11-20 10:23:34  Bonjour le monde

Notez l'inclusion d'un caractère de nouvelle ligne explicite dans la chaîne de format.

RECHERCHE DANS L'HISTORIQUE

La fonction gl_lookup_history() permet à l'application appelante de rechercher des lignes dans la liste d'historique.

  typedef struct {
    const char *line;    /* La ligne historique */
                         /*  demandée. */
    unsigned group;      /* Le groupe d'historique auquel */
                         /*  la ligne appartient. */
    time_t timestamp;    /* La date et l'heure auxquelles */
                         /*  la ligne a été initialement */
                         /*  entrée. */
  } GlHistoryLine;
  int gl_lookup_history(GetLine *gl, unsigned long id,
                        GlHistoryLine *hline);

L'argument id indique quelle ligne rechercher, où la première ligne entrée dans la liste d'historique après l'appel à new_GetLine() est désignée par 0, et les lignes entrées subsquemment sont désignées par des nombres successivement plus grands. Notez que la plage des lignes actuellement préservées dans la liste d'historique peut être interrogée en appelant la fonction gl_range_of_history(), décrite plus loin. Si la ligne demandée se trouve dans la liste d'historique, les détails de la ligne sont enregistrés dans la variable pointée par l'argument hline, et 1 est retourné. Sinon, 0 est retourné, et la variable pointée par hline reste inchangée.

Attention, la chaîne retournée dans hline->line fait partie du tampon d'historique, elle ne doit donc pas être modifiée par l'appelant, et sera recyclée lors du prochain appel à toute fonction prenant gl comme argument. Par conséquent, vous devriez faire une copie privée de cette chaîne si vous avez besoin de la conserver.

ARCHIVAGE MANUEL DE L'HISTORIQUE

Par défaut, chaque fois qu'une ligne est entrée par l'utilisateur, elle est automatiquement ajoutée à la liste d'historique, juste avant que gl_get_line() ne renvoie la ligne à l'appelant. C'est pratique pour la majorité des applications, mais il existe aussi des applications qui ont besoin d'un contrôle plus fin sur ce qui est ajouté à la liste d'historique. Dans de tels cas, l'ajout automatique des lignes entrées à la liste d'historique peut être désactivé en appelant la fonction gl_automatic_history().

  int gl_automatic_history(GetLine *gl, int enable);

Si cette fonction est appelée avec son argument enable réglé à 0, gl_get_line() n'archivera pas automatiquement les lignes entrées par la suite. L'archivage automatique peut être réactivé plus tard, en appelant à nouveau cette fonction, avec son argument enable réglé à 1. Tant que l'archivage automatique de l'historique est désactivé, l'application appelante peut utiliser gl_append_history() pour ajouter des lignes à la liste d'historique au besoin.

  int gl_append_history(GetLine *gl, const char *line);

L'argument line spécifie la ligne à ajouter à la liste d'historique. Il doit s'agir d'une chaîne normale terminée par ' '. Si cette chaîne contient des caractères de nouvelle ligne, la ligne qui sera archivée dans la liste d'historique sera terminée par le premier de ces caractères. Sinon, elle sera terminée par le terminateur ' '. Si la ligne est plus longue que la longueur maximale de ligne d'entrée, qui a été spécifiée lors de l'appel à new_GetLine(), lorsqu'elle sera rappelée, elle sera tronquée à la longueur de ligne réelle de gl_get_line().

En cas de succès, gl_append_history() renvoie 0. Sinon, elle renvoie une valeur non nulle, et définit errno à l'une des valeurs suivantes.

   EINVAL  -  Un des arguments passés à
              gl_append_history() était NULL.
   ENOMEM  -  La ligne spécifiée était plus longue que la
              taille allouée du tampon d'historique (comme
              spécifié lors de l'appel à new_GetLine()),
              elle n'a donc pas pu être archivée.

Une description textuelle de l'erreur peut éventuellement être obtenue en appelant gl_error_message(). Notez qu'après une telle erreur, la liste d'historique reste dans un état valide pour recevoir de nouvelles lignes d'historique, il y a donc peu de risque à ignorer simplement le statut de retour de gl_append_history().

CONFIGURATION DIVERS DE L'HISTORIQUE

Si vous souhaitez modifier la taille du tampon d'historique qui a été spécifiée à l'origine dans l'appel à new_GetLine(), vous pouvez le faire avec la fonction gl_resize_history().

  int gl_resize_history(GetLine *gl, size_t histlen);

L'argument histlen spécifie la nouvelle taille en octets, et si vous la spécifiez comme 0, le tampon sera supprimé.

Comme mentionné dans la discussion de new_GetLine(), le nombre de lignes qui peuvent être stockées dans le tampon d'historique dépend des longueurs des lignes individuelles. Par exemple, un tampon de 1000 octets pourrait aussi bien stocker 10 lignes de longueur moyenne 100 octets, ou 2 lignes de longueur moyenne 50 octets. Bien que le tampon ne soit jamais agrandi lorsque de nouvelles lignes sont ajoutées, une liste de pointeurs dans le tampon est agrandie lorsque nécessaire pour accueillir le nombre de lignes actuellement stockées dans le tampon. Pour placer une limite supérieure sur le nombre de lignes dans le tampon, et donc un plafond sur la quantité de mémoire utilisée dans cette liste, vous pouvez appeler gl_limit_

history() fonction.

  void gl_limit_history(GetLine *gl, int max_lines);

Le max_lines doit être soit un nombre positif >= 0, spécifiant une limite supérieure au nombre de lignes dans le tampon, ou être -1 pour annuler toute limite précédemment spécifiée. Lorsqu'une limite est en vigueur, seules les max_lines lignes les plus récemment ajoutées sont conservées dans le tampon. Les lignes plus anciennes sont écartées.

Pour écarter des lignes de l'historique, utilisez la gl_clear_history() fonction.

  void gl_clear_history(GetLine *gl, int all_groups);

L' all_groups argument indique à la fonction si elle doit supprimer uniquement les lignes associées au groupe d'historique courant (voir gl_group_history()), ou toutes les lignes historiques du tampon.

La gl_toggle_history() fonction permet d'activer et de désactiver l'historique sans perdre le contenu actuel de la liste d'historique.

  void gl_toggle_history(GetLine *gl, int enable);

Régler l' enable argument à 0 désactive le mécanisme d'historique, et le régler à 1 le réactive. Lorsque l'historique est désactivé, aucune nouvelle ligne ne sera ajoutée à la liste d'historique, et les raccourcis clavier de recherche dans l'historique se comporteront comme si le tampon d'historique était vide.

INTERROGER L'INFORMATION D'HISTORIQUE

L'état configuré de la liste d'historique peut être interrogé avec la gl_history_state() fonction.

  typedef struct {
    int enabled;     /* Vrai si l'historique est activé */
    unsigned group;  /* Le groupe d'historique courant */
    int max_lines;   /* La limite supérieure actuelle sur le */
                     /*  nombre de lignes dans la liste */
                     /*  d'historique, ou -1 si illimitée. */
  } GlHistoryState;
  void gl_state_of_history(GetLine *gl,
                           GlHistoryState *state);

Au retour, les informations d'état sont enregistrées dans la variable pointée par l' state argument.

La gl_range_of_history() fonction renvoie le nombre et l'étendue des lignes dans la liste d'historique.

typedef struct {
  unsigned long oldest;  /* Le numéro d'entrée séquentiel */
                         /*  de la ligne la plus ancienne */
                         /*  de la liste d'historique. */
  unsigned long newest;  /* Le numéro d'entrée séquentiel */
                         /*  de la ligne la plus récente */
                         /*  de la liste d'historique. */
  int nlines;            /* Le nombre de lignes dans la */
                         /*  liste d'historique. */
} GlHistoryRange;
void gl_range_of_history(GetLine *gl, GlHistoryRange *range);

Les valeurs de retour sont enregistrées dans la variable pointée par l' range argument. Si le membre nlines de cette structure est supérieur à zéro, alors les membres oldest et newest indiquent l'étendue des lignes dans la liste, et newest=oldest+nlines-1. Sinon ils sont tous les deux à zéro.

La gl_size_of_history() fonction renvoie la taille totale du tampon d'historique et la quantité du tampon actuellement occupée.

  typedef struct {
    size_t size;      /* La taille du tampon d'historique */
                      /*  (octets). */
    size_t used;      /* Le nombre d'octets du */
                      /*  tampon d'historique qui sont */
                      /*  actuellement occupés. */
  } GlHistorySize;
  void gl_size_of_history(GetLine *gl, GlHistorySize *size);

Au retour, les informations de taille sont enregistrées dans la variable pointée par l' size argument.

CHANGER DE TERMINAL

Le new_GetLine() constructeur suppose que l'entrée doit être lue depuis stdin, et que la sortie est écrite vers stdout. La fonction suivante permet de basculer vers d'autres flux d'entrée et de sortie.

  int gl_change_terminal(GetLine *gl, FILE *input_fp,
                         FILE *output_fp, const char *term);

L' gl argument est l'objet qui a été renvoyé par new_GetLine(). L' input_fp argument spécifie le flux à lire, et output_fp spécifie le flux vers lequel écrire. Seulement si les deux font référence à un terminal, l'entrée interactive du terminal sera activée. Sinon gl_get_line() appellera simplement fgets() pour lire la commande en entrée. Si les deux flux font référence à un terminal, alors ils doivent faire référence au même terminal, et le type de ce terminal doit être spécifié via l' term argument. La valeur de l' term argument est recherchée dans la base de données d'informations sur le terminal (terminfo ou termcap), afin de déterminer quelles séquences de contrôle spéciales sont nécessaires pour contrôler les différents aspects du terminal. new_GetLine() par exemple, passe la valeur de retour de getenv("TERM") dans cet argument. Notez que si un ou les deux de input_fp et output_fp ne font pas référence à un terminal, il est légal de passer NULL au lieu d'un type de terminal.

Notez que si vous souhaitez passer des descripteurs de fichier à gl_change_terminal(), vous pouvez le faire en créant des enveloppes de flux stdio en utilisant la fonction POSIX fdopen() .

GESTION DES ÉVÉNEMENTS EXTERNES

Par défaut, gl_get_line() ne retourne pas tant qu'une ligne d'entrée complète n'a pas été saisie par l'utilisateur, ou qu'une erreur ne se produit pas. Dans les programmes qui doivent surveiller les entrées/sorties provenant d'autres sources que le terminal, il existe deux options.

  1. Utiliser les fonctions décrites dans la
     gl_io_mode(3) page de manuel pour basculer
     gl_get_line() en mode serveur non bloquant. Dans ce mode,
     gl_get_line() devient une fonction d'édition de ligne non bloquante et incrémentale
     qui peut être appelée en toute sécurité depuis
     une boucle d'événements externe. Bien que ce soit une méthode très
     polyvalente, elle implique d'assumer certaines
     responsabilités qui sont normalement effectuées en coulisses par gl_get_line().
  2. Pendant que gl_get_line() attend une entrée clavier
     de l'utilisateur, vous pouvez lui demander de surveiller également
     l'activité sur des descripteurs de fichier arbitraires, tels que
     des sockets réseau, des tuyaux (pipes), etc., et de faire en sorte qu'elle appelle des
     fonctions de votre choix lorsque l'activité est détectée. Cela fonctionne sur
     tout système qui possède l'appel système select() ,
     ce qui est le cas de la plupart, sinon de toutes les variantes d'unix.

L'enregistrement d'un descripteur de fichier à surveiller par gl_get_line() implique d'appeler la gl_watch_fd() fonction.

  int gl_watch_fd(GetLine *gl, int fd, GlFdEvent event,
                  GlFdEventFn *callback, void *data);

Si cela renvoie une valeur non nulle, cela signifie que soit vos arguments sont invalides, soit cette fonctionnalité n'est pas prise en charge sur le système hôte.

L' fd argument est le descripteur de fichier à surveiller. L' event argument spécifie quel type d'activité est d'intérêt, choisi parmi les valeurs énumérées suivantes :

  GLFD_READ   -  Surveiller l'arrivée de données à lire.
  GLFD_WRITE  -  Surveiller la possibilité d'écrire dans le descripteur
                 de fichier sans bloquer.
  GLFD_URGENT -  Surveiller l'arrivée de données urgentes
                 hors bande sur le descripteur de fichier.

L' callback argument est la fonction à appeler lorsque l'activité sélectionnée est détectée. Elle doit être définie avec la macro suivante, qui est définie dans libtecla.h.

  #define GL_FD_EVENT_FN(fn) GlFdStatus (fn)(GetLine *gl, \
                                      void *data, int fd, \
                                      GlFdEvent event)

L' data argument de la gl_watch_fd() fonction est passé à la fonction de rappel pour son propre usage, et peut pointer vers n'importe quoi que vous voulez, y compris NULL. Le descripteur de fichier et l'argument event sont également passés à la fonction de rappel, ce qui permet potentiellement à la même fonction de rappel d'être enregistrée pour plus d'un type d'événement et/ou plus d'un descripteur de fichier. La valeur de retour de la fonction de rappel doit être l'une des valeurs suivantes.

  GLFD_ABORT    -  Dire à gl_get_line() d'interrompre. Quand cela
                   se produit, gl_get_line() renvoie
                   NULL, et un appel suivant à
                   gl_return_status() renverra
                   GLR_FDABORT. Notez que si
                   l'application a besoin que errno ait toujours
                   une valeur significative lorsque
                   gl_get_line() renvoie NULL,
                   la fonction de rappel doit régler
                   errno de manière appropriée.
  GLFD_REFRESH  -  Redessiner la ligne d'entrée puis continuer
                   à attendre les entrées. Renvoyer cela si
                   votre fonction de rappel a écrit sur le terminal.
  GLFD_CONTINUE -  Continuer à attendre les entrées, sans
                   redessiner la ligne.

Notez qu'avant d'appeler la fonction de rappel, gl_get_line() bloque la plupart des signaux, et laisse ses propres gestionnaires de signal installés, donc si vous avez besoin de capter un signal particulier, vous devrez à la fois installer temporairement votre propre gestionnaire de signal, et débloquer le signal. Assurez-vous de re-bloquer le signal (s'il était initialement bloqué) et de réinstaller le gestionnaire de signal original, s'il y en a un, avant de retourner.

Si la fonction de rappel a besoin de lire ou d'écrire sur le terminal, elle devrait idéalement d'abord appeler gl_normal_io(gl) pour suspendre temporairement l'édition de ligne. Cela restaurera le terminal en mode canonique, entrées/sorties bloquantes, et déplacera le curseur au début d'une nouvelle ligne du terminal. Plus tard, lorsque la fonction de rappel retourne, gl_get_line() remarquera que gl_normal_io() a été appelée, réaffichera la ligne d'entrée et reprendra l'édition. Par défaut, la fonction gl_get_line() intercepte un certain nombre de signaux. C'est particulièrement important pour les signaux qui, par défaut, termineraient le processus, car le terminal doit être restauré dans un état utilisable avant que cela ne se produise.             errno=EINTR

            se termine.
            errno=ENOTTY
 SIGPIPE -  Ce signal est généré quand un programme tente
            d'écrire dans un pipe dont l'extrémité distante n'est lue

            si vous avez appelé gl_change_terminal() pour
            rediriger la sortie vers un pipe caché sous un pseudo

            errno=EPIPE

Si vous n'avez pas besoin que gl_get_line() fasse quoi que ce soit en réponse à un signal qu'il intercepte normalement, vous pouvez dire à gl_get_line() d'ignorer ce signal en appelant gl_ignore_signal().

L'argument signo est le numéro du signal (ex. SIGINT) que vous voulez voir ignoré. Si le signal spécifié n'est actuellement pas l'un de ceux qui sont interceptés, cette fonction ne fait rien.

La fonction gl_trap_signal() vous permet soit d'ajouter un nouveau signal à la liste que gl_get_line() intercepte, soit de modifier comment il

gl_trap_signal

This function is used to configure gl_get_line() to handle signals. This can be useful if you want to abort from gl_get_line() if the user presses certain keys, or if you want to prevent signals from interrupting the editing of the line.

  int gl_trap_signal(GetLine *gl, int signo, unsigned flags,
                     GlAfterSignal after, int errno_value);

The signo argument is the number of the signal that you wish to have trapped. The flags argument is a set of flags which determine the environment in which the application's signal handler is invoked, the after argument tells gl_get_line() what to do after the application's signal handler returns, and errno_value tells gl_get_line() what to set errno to if told to abort.

The flags argument is a bitwise OR of zero or more of the following enumerators:

  GLS_RESTORE_SIG  -  Restore the caller's signal
                      environment while handling the
                      signal.
  GLS_RESTORE_TTY  -  Restore the caller's terminal settings
                      while handling the signal.
  GLS_RESTORE_LINE -  Move the cursor to the start of the
                      line following the input line before
                      invoking the application's signal
                      handler.
  GLS_REDRAW_LINE  -  Redraw the input line when the
                      application's signal handler returns.
  GLS_UNBLOCK_SIG  -  Normally, if the calling program has
                      a signal blocked (man sigprocmask),
                      gl_get_line() does not trap that
                      signal. This flag tells gl_get_line()
                      to trap the signal and unblock it for
                      the duration of the call to
                      gl_get_line().
  GLS_DONT_FORWARD -  If this flag is included, the signal
                      will not be forwarded to the signal
                      handler of the calling program.

Two commonly useful flag combinations are also enumerated as follows:

  GLS_RESTORE_ENV   = GLS_RESTORE_SIG | GLS_RESTORE_TTY |
                      GLS_REDRAW_LINE
  GLS_SUSPEND_INPUT = GLS_RESTORE_ENV | GLS_RESTORE_LINE

If your signal handler, or the default system signal handler for this signal, if you haven't overridden it, never either writes to the terminal, nor suspends or terminates the calling program, then you can safely set the flags argument to 0.

If your signal handler always writes to the terminal, reads from it, or suspends or terminates the program, you should specify the flags argument as GL_SUSPEND_INPUT, so that:

1. The cursor doesn't get left in the middle of the input
   line.
2. So that the user can type in input and have it echoed.
3. So that you don't need to end each output line with
   \r\n, instead of just \n.

The GL_RESTORE_ENV combination is the same as GL_SUSPEND_INPUT, except that it doesn't move the cursor, and if your signal handler doesn't read or write anything to the terminal, the user won't see any visible indication that a signal was caught. This can be useful if you have a signal handler that only occasionally writes to the terminal, where using GL_SUSPEND_LINE would cause the input line to be unnecessarily duplicated when nothing had been written to the terminal. Such a signal handler, when it does write to the terminal, should be sure to start a new line at the start of its first write, by writing a new line before returning. If the signal arrives while the user is entering a line that only occupies a signal terminal line, or if the cursor is on the last terminal line of a longer input line, this will have the same effect as GL_SUSPEND_INPUT. Otherwise it will start writing on a line that already contains part of the displayed input line. This doesn't do any harm, but it looks a bit ugly, which is why the GL_SUSPEND_INPUT combination is better if you know that you are always going to be writting to the terminal.

The after argument, which determines what gl_get_line() does after the application's signal handler returns (if it returns), can take any one of the following values:

  GLS_RETURN   - Return the completed input line, just as
                 though the user had pressed the return
                 key.
  GLS_ABORT    - Cause gl_get_line() to abort. When
                 this happens, gl_get_line() returns
                 NULL, and a following call to
                 gl_return_status() will return
                 GLR_SIGNAL. Note that if the
                 application needs errno always to
                 have a meaningful value when
                 gl_get_line() returns NULL,
                 the callback function should set
                 errno appropriately.
  GLS_CONTINUE - Resume command line editing.

The errno_value argument is intended to be combined with the GLS_ABORT option, telling gl_get_line() what to set the standard errno variable to before returning NULL to the calling program. It can also, however, be used with the GL_RETURN option, in case you wish to have a way to distinguish between an input line that was entered using the return key, and one that was entered by the receipt of a signal.

RELIABLE SIGNAL HANDLING

Signal handling is suprisingly hard to do reliably without race conditions. In gl_get_line() a lot of care has been taken to allow applications to perform reliable signal handling around gl_get_line(). This section explains how to make use of this.

As an example of the problems that can arise if the application isn't written correctly, imagine that one's application has a SIGINT signal handler that sets a global flag. Now suppose that the application tests this flag just before invoking gl_get_line(). If a SIGINT signal happens to be received in the small window of time between the statement that tests the value of this flag, and the statement that calls gl_get_line(), then gl_get_line() will not see the signal, and will not be interrupted. As a result, the application won't be able to respond to the signal until the user gets around to finishing entering the input line and gl_get_line() returns. Depending on the application, this might or might not be a disaster, but at the very least it would puzzle the user.

The way to avoid such problems is to do the following.

1. If needed, use the gl_trap_signal() function to configure gl_get_line() to abort when important signals are caught.

2. Configure gl_get_line() such that if any of the signals that it catches are blocked when gl_get_line() is called, they will be unblocked automatically during times when gl_get_line() is waiting for I/O. This can be done either on a per signal basis, by calling the gl_trap_signal() function, and specifying the GLS_UNBLOCK attribute of the signal, or globally by calling the gl_catch_blocked() function.

     void gl_catch_blocked(GetLine *gl);

This function simply adds the GLS_UNBLOCK attribute to all of the signals that it is currently configured to trap.

3. Just before calling gl_get_line(), block delivery of all of the signals that gl_get_line() is configured to trap. This can be done using the POSIX sigprocmask() function in conjunction with the gl_list_signals() function.

      int gl_list_signals(GetLine *gl, sigset_t *set);

This function returns the set of signals that it is currently configured to catch in the set argument, which is in the form required by sigprocmask().

4. In the example, one would now test the global flag that the signal handler sets, knowing that there is now no danger of this flag being set again until gl_get_line() unblocks its signals while performing I/O.

5. Eventually gl_get_line() returns, either because a signal was caught, an error occurred, or the user finished entering their input line.

6. Now one would check the global signal flag again, and if it is set, respond to it, and zero the flag.

7. Use sigprocmask() to unblock the signals that were blocked in step 3.

The same technique can be used around certain POSIX signal-aware functions, such as sigsetjmp() and sigsuspend(), and in particular, the former of these two functions can be used in conjunction with siglongjmp() to implement race-condition free signal handling around other long-running system calls. The way to do this, is explained next, by showing how gl_get_line() manages to reliably trap signals around calls to functions like read() and select() without race conditions.

The first thing that gl_get_line() does, whenever it is called, is to use the POSIX sigprocmask() function to block the delivery of all of the signals that it is currently configured to catch. This is redundant if the application has already blocked them, but it does no harm. It undoes this step just before returning.

Whenever gl_get_line() needs to call read() or select() to wait for input from the user, it first calls the POSIX sigsetjmp() function, being sure to specify a non-zero value for its savesigs argument. The reason for the latter argument will become clear shortly.

If sigsetjmp() returns zero, gl_get_line() then does the following.

a. It uses the POSIX sigaction() function to register
   a temporary signal handler to all of the signals that it
   is configured to catch. This signal handler does two
   things.
   1. It records the number of the signal that was received
      in a file-scope variable.
   2. It then calls the POSIX siglongjmp()
      function using the buffer that was passed to
      sigsetjmp() for its first argument, and
      a non-zero value for its second argument.
   When this signal handler is registered, the sa_mask
   member of the struct sigaction act argument of the
   call to sigaction() is configured to contain all of
   the signals that gl_get_line() is catching. This
   ensures that only one signal will be caught at once by
   our signal handler, which in turn ensures that multiple
   instances of our signal handler don't tread on each
   other's toes.
b. Now that the signal handler has been set up,
   gl_get_line() unblocks all of the signals that it
   is configured to catch.
c. It then calls the read() or select() system
   calls to wait for keyboard input.
d. If this system call returns (ie. no signal is received),
   gl_get_line() blocks delivery of the signals of
   interest again.
e. It then reinstates the signal handlers that were
   displaced by the one that was just installed.

Alternatively, if sigsetjmp() returns non-zero, this means that

que l'un des signaux interceptés a été capturé pendant l'exécution des étapes ci-dessus. Lorsque cela se produit, gl_get_line() fait ce qui suit.

Tout d'abord, notez que lorsqu'un appel à siglongjmp() provoque sigsetjmp() le retour, à condition que l'argument savesigs de sigsetjmp() était non nul, comme spécifié ci-dessus, le masque de traitement des signaux est restauré à l'état dans lequel il se trouvait lorsque sigsetjmp() a été appelé. C'est la différence importante entre sigsetjmp() et l'ancien setjmp()problématique, et c'est l'ingrédient essentiel qui permet d'éviter les conditions de course dans la gestion des signaux. Grâce à cela, nous sommes garantis que tous les signaux que nous avons bloqués avant d'appeler sigsetjmp() sont de nouveau bloqués dès qu'un signal est capturé. Les instructions suivantes, qui sont alors exécutées, sont donc garanties de s'exécuter sans qu'aucun autre signal ne soit capturé.

1. Si tel est l'instruction donnée par les gl_get_line() attributs de configuration
du signal qui a été capturé,
gl_get_line() restaure les attributs du terminal à
l'état dans lequel ils se trouvaient lorsque gl_get_line() a été

suspendent ou terminent le processus, car sinon le

2. Il réinstalle ensuite les gestionnaires de signaux de l'application.

3. Il utilise ensuite la fonction raise()
de la bibliothèque standard C pour renvoyer à l'application le signal qui
a été capturé.

3. Ensuite, il débloque la livraison du signal que nous venons de
envoyer. Cela entraîne la capture du signal qui vient d'être envoyé

original de l'application, qui peut maintenant le traiter comme il
le juge approprié.

4. Si le gestionnaire de signal retourne (c'est-à-dire qu'il ne termine pas
le processus), gl_get_line() bloque à nouveau la livraison du
signal ci-dessus.

5. Il annule ensuite toute action effectuée lors de la première des
étapes ci-dessus, et réaffiche la ligne, si la configuration du
signal l'exige.

6. gl_get_line() reprend alors la tentative de
lecture d'un caractère, ou interrompt, en fonction de la
configuration du signal qui a été capturé.

Ce que font essentiellement les étapes ci-dessus, c'est prendre des signaux livrés de manière asynchrone et les traiter de manière synchrone, un à la fois, à un point du code où gl_get_line() a un contrôle complet sur son environnement.

LA TAILLE DU TERMINAL

Sur la plupart des systèmes, la combinaison de l'ioctl TIOCGWINSZ et du signal SIGWINCH est utilisée pour maintenir une idée précise de la taille du terminal. La taille du terminal est requise à nouveau chaque fois que gl_get_line() est appelé et chaque fois qu'un SIGWINCH signal est reçu.

Sur les quelques systèmes où ce mécanisme n'est pas disponible, au démarrage new_GetLine() cherche d'abord les variables d'environnement LINES et COLUMNS . Si elles ne sont pas trouvées, ou si elles contiennent des valeurs inutilisables, alors si une base de données d'informations sur le terminal comme terminfo ou termcap est disponible, la taille par défaut du terminal est recherchée dans cette base de données. Si cela ne permet pas non plus d'obtenir la taille du terminal, une taille par défaut de 80 colonnes par 24 lignes est utilisée.

Même sur les systèmes qui prennent en charge ioctl(TIOCGWINSZ), si le terminal se trouve à l'autre bout d'une ligne série, le pilote du terminal n'a généralement aucun moyen de détecter quand un redimensionnement se produit ou de demander la taille actuelle. Dans de tels cas, aucun SIGWINCH n'est envoyé au processus, et les dimensions renvoyées par ioctl(TIOCGWINSZ) ne sont pas correctes. La seule façon de gérer ces cas est de fournir un moyen à l'utilisateur d'entrer une commande qui indique au système distant la nouvelle taille. Cette commande appellerait alors la fonction gl_set_term_size() pour informer gl_get_line() du changement de taille.

  int gl_set_term_size(GetLine *gl, int ncolumn, int nline);

Les arguments ncolumn et nline sont utilisés pour spécifier les nouvelles dimensions du terminal, et ne doivent pas être inférieurs à 1. Sur les systèmes qui prennent en charge ioctl(TIOCGWINSZ), cette fonction appelle d'abord ioctl(TIOCSWINSZ) pour informer le pilote du terminal du changement de taille. En mode E/S serveur non bloquant, si une ligne est actuellement en cours de saisie, la ligne d'entrée est alors redessinée pour s'adapter à la taille modifiée. Enfin, les nouvelles valeurs sont enregistrées dans gl pour une utilisation future par gl_get_line().

La fonction gl_terminal_size() vous permet de demander la taille actuelle du terminal et d'installer une taille de secours alternative pour les cas où la taille n'est pas disponible. Attention, la taille du terminal ne sera pas disponible si vous lisez depuis un pipe ou un fichier, donc les valeurs par défaut peuvent être importantes même sur les systèmes qui prennent en charge des moyens de découvrir la taille du terminal.

  typedef struct {
    int nline;        /* Le terminal a nline lignes */
    int ncolumn;      /* Le terminal a ncolumn colonnes */
  } GlTerminalSize;
  GlTerminalSize gl_terminal_size(GetLine *gl,
                                  int def_ncolumn,
                                  int def_nline);

Cette fonction met d'abord à jour les dimensions de secours du terminal de gl_get_line(), puis enregistre ses résultats dans la valeur de retour.

Les arguments def_ncolumn et def_nline spécifient le nombre par défaut de colonnes et de lignes du terminal à utiliser si la taille du terminal ne peut pas être déterminée via ioctl(TIOCGWINSZ) ou les variables d'environnement.

CACHER CE QUE VOUS TAPEZ

Lors de la saisie d'informations sensibles, telles que des mots de passe, il est préférable de ne pas faire écho sur le terminal du texte que vous saisissez. De plus, ce texte ne devrait pas être enregistré dans la liste d'historique, car quelqu'un trouvant votre terminal sans surveillance pourrait alors le rappeler, ou quelqu'un fouillant dans vos répertoires pourrait le voir dans votre fichier d'historique. En gardant cela à l'esprit, la fonction gl_echo_mode() vous permet d'activer et de désactiver l'affichage et l'archivage de tout texte qui est saisi par la suite dans les appels à gl_get_line().

  int gl_echo_mode(GetLine *gl, int enable);

L'argument enable spécifie si le texte saisi doit être visible ou non. S'il est 0, les lignes saisies par la suite ne seront pas visibles sur le terminal et ne seront pas enregistrées dans la liste d'historique. S'il est 1, les lignes d'entrée suivantes seront affichées au fur et à mesure de leur saisie et, à condition que l'historique n'ait pas été désactivé via un appel à gl_toggle_history(), elles seront également archivées dans la liste d'historique. Enfin, si l'argument enable est -1, le mode d'écho est laissé inchangé, ce qui vous permet de demander de manière non destructive le paramètre actuel via la valeur de retour. Dans tous les cas, la valeur de retour de la fonction est 0 si l'écho était désactivé avant l'appel de la fonction, et 1 s'il était activé.

Lorsque l'écho est désactivé, notez que même si la complétion par tabulation complétera de manière invisible votre préfixe aussi loin que possible, les complétions ambiguës ne seront pas affichées.

REQUÊTES À UN SEUL CARACTÈRE

Utiliser gl_get_line() pour demander à l'utilisateur une réponse d'un seul caractère est inconfortable pour l'utilisateur, car il doit appuyer sur la touche entrée ou retour avant que le caractère qu'il a tapé ne soit renvoyé au programme. C'est pourquoi la fonction gl_query_char() a été fournie pour les requêtes d'un seul caractère comme celle-ci.

  int gl_query_char(GetLine *gl, const char *prompt,
                    char defchar);

Cette fonction affiche l'invite spécifiée au début d'une nouvelle ligne et attend que l'utilisateur tape un caractère. Lorsque l'utilisateur tape un caractère, gl_query_char() l'affiche à droite de l'invite, passe à la ligne suivante, puis renvoie le caractère au programme appelant. La valeur de retour de la fonction est le caractère qui a été tapé. Si la lecture a dû être interrompue pour une raison quelconque, EOF est renvoyé à la place. Dans ce dernier cas, l'application peut appeler la fonction gl_return_status()documentée précédemment pour savoir ce qui s'est mal passé. Cela pourrait, par exemple, avoir été la réception d'un signal ou le déclenchement du minuteur d'inactivité optionnel.

Si l'utilisateur appuie simplement sur entrée, la valeur de l'argument defchar est substituée. Cela signifie que lorsque l'utilisateur appuie sur nouvelle ligne ou retour, le caractère spécifié dans defcharest affiché après l'invite, comme si l'utilisateur l'avait tapé, et est également renvoyé à l'application appelante. Si un tel remplacement n'est pas important, passez simplement '0 comme valeur de defchar.

Si le caractère saisi est un caractère non imprimable, il est affiché symboliquement. Par exemple, contrôle-A est affiché comme ^A, et les caractères au-delà de 127 sont affichés en octal, précédés d'une barre oblique inverse.

Comme avec gl_get_line(), l'écho du caractère saisi peut être désactivé à l'aide de la fonction gl_echo_mode() .

Si le processus appelant est suspendu pendant qu'il attend que l'utilisateur tape sa réponse, le curseur est déplacé sur la ligne suivant la ligne d'invite, puis lorsque le processus reprend, l'invite est réaffichée, et gl_query_char() reprend l'attente de la saisie d'un caractère par l'utilisateur.

Notez qu'en mode serveur non bloquant, (voir gl_io_mode(3)), si une ligne d'entrée incomplète est en cours de lecture lorsque gl_query_char() est appelé, la ligne d'entrée partielle est ignorée et effacée du terminal avant que la nouvelle invite ne soit affichée. L'appel suivant à gl_get_line() commencera donc à éditer une nouvelle ligne.

LIRE DES CARACTÈRES BRUTS

Alors que la fonction gl_query_char() invite visiblement l'utilisateur à saisir un caractère et affiche ce qu'il a tapé, la fonction gl_read_char() lit un caractère de signal auprès de l'utilisateur, sans rien écrire sur le terminal ni perturber une ligne d'entrée incomplète. Cela signifie qu'elle peut être appelée non seulement entre les appels à gl_get_line(), mais aussi depuis des fonctions de rappel que l'application a enregistrées pour être appelées par gl_get_line().

  int gl_read_char(GetLine *gl);

En cas de succès, la valeur de retour de gl_read_char() est le caractère qui a été lu. En cas d'échec, EOF est renvoyé, et la fonction gl_return_status() peut être appelée pour savoir ce qui s'est mal passé. Les possibilités incluent le déclenchement du minuteur d'inactivité optionnel, la réception d'un signal configuré pour interrompre gl_get_line(), ou le blocage des E/S du terminal, en mode E/S serveur non bloquant.

Attention, certaines touches du clavier, telles que les touches de fonction et les touches de curseur, génèrent généralement au moins 3 caractères chacune, donc un seul appel à gl_read_char()

NETTOYAGE DU TERMINAL

Le programme appelant peut nettoyer le terminal en appelant gl_erase_terminal(). En mode serveur I/O non bloquant, cette fonction prépare également le redessin de la ligne d'entrée actuelle depuis le début lors du prochain appel à gl_get_line().

  int gl_erase_terminal(GetLine *gl);

AFFICHAGE DYNAMIQUE DE TEXTE

Entre les appels à gl_get_line(), la fonction gl_display_text() offre un moyen pratique d'afficher des paragraphes de texte, justifiés à gauche et répartis sur une ou plusieurs lignes du terminal selon les contraintes de la largeur actuelle du terminal. Des exemples d'utilisation de cette fonction se trouvent dans les programmes de démonstration, où elle est utilisée pour afficher des introductions. Dans ces exemples, l'utilisation avancée de préfixes, suffixes et lignes de remplissage optionnels pour dessiner une boîte autour du texte est également illustrée.

  int gl_display_text(GetLine *gl, int indentation,
                      const char *prefix,
                      const char *suffix, int fill_char,
                      int def_width, int start,
                      const char *string);

Si gl n'est pas actuellement connecté à un terminal, par exemple si la sortie d'un programme utilisant gl_get_line() est redirigée vers un autre programme ou un fichier, alors la valeur du paramètre def_width est utilisée comme largeur du terminal.

L'argument indentation spécifie le nombre de caractères à utiliser pour indenter chaque ligne de sortie. L'argument fill_char spécifie le caractère qui sera utilisé pour effectuer cette indentation.

L'argument prefix peut être NULL, ou une chaîne à placer au début de chaque nouvelle ligne (après toute indentation). Similairement, l'argument suffix peut être NULL, ou une chaîne à placer à la fin de chaque ligne. Le suffixe est placé juste au bord droit du terminal, et tout espace entre son premier caractère et le dernier mot de la ligne est rempli avec le caractère spécifié via l'argument fill_char. Normalement, le caractère de remplissage est un espace.

L'argument start indique à gl_display_text() combien de caractères ont déjà été écrits sur la ligne actuelle du terminal, et indique donc l'indice de colonne de départ du curseur. Comme la valeur de retour de gl_display_text() est l'indice de colonne de fin du curseur, en passant la valeur de retour d'un appel à l'argument start du prochain appel, un paragraphe divisé en plusieurs chaînes peut être composé en appelant gl_display_text() pour chaque portion successive du paragraphe. Notez que des caractères de nouvelle ligne littéraux sont nécessaires à la fin de chaque paragraphe pour forcer le démarrage d'une nouvelle ligne.

En cas d'erreur, gl_display_text() retourne -1.

FONCTIONNALITÉS DE FONCTIONS DE RAPPEL

Sauf indication contraire, les fonctions de rappel, telles que les fonctions de rappel de complétion par tabulation et les fonctions de rappel d'événements, ne doivent pas appeler de fonctions de ce module. Les fonctions suivantes, cependant, sont conçues spécifiquement pour être utilisées par des fonctions de rappel.

Appeler la fonction gl_replace_prompt() depuis une fonction de rappel indique à gl_get_line() d'afficher une invite différente lorsque la fonction de rappel retourne. Sauf en mode serveur non bloquant, cela n'a aucun effet lorsqu'il est utilisé entre les appels à gl_get_line(). En mode serveur non bloquant (voir la page de manuel gl_io_mode(3), lorsqu'il est utilisé entre deux appels à gl_get_line() qui opèrent sur la même ligne d'entrée, la ligne d'entrée actuelle sera redessinée avec la nouvelle invite lors du prochain appel à gl_get_line().

  void gl_replace_prompt(GetLine *gl, const char *prompt);

JEUX DE CARACTÈRES INTERNATIONAUX

Depuis la version 1.4.0 de libtecla, gl_get_line() est propre aux 8 bits. Cela signifie que tous les caractères 8 bits imprimables dans la locale actuelle de l'utilisateur sont maintenant affichés tels quels et inclus dans la ligne d'entrée retournée. En supposant que le programme appelant contient correctement un appel comme le suivant,

  setlocale(LC_CTYPE, "");

alors la locale actuelle est déterminée par la première des variables d'environnement LC_CTYPE, LC_ALL et LANG, qui contient un nom de locale valide. Si aucune de ces variables n'est définie, ou si le programme néglige d'appeler setlocale, alors la locale par défaut C est utilisée, qui est l'ASCII américain 7 bits. Sur la plupart des plateformes de type Unix, vous pouvez obtenir une liste des locales valides en tapant la commande :

  locale -a

à l'invite du shell. Une documentation plus détaillée sur la manière dont l'utilisateur peut utiliser cela pour saisir des caractères internationaux se trouve dans la page de manuel tecla(7).

SÉCURITÉ DES THREADS

Dans un programme multi-threadé, vous devriez utiliser la version libtecla_r.a de la bibliothèque. Celle-ci utilise des versions réentrantes des fonctions système, lorsque disponibles. Malheureusement, ni terminfo ni termcap n'ont été conçus pour être réentrantes, vous ne pouvez donc pas utiliser en toute sécurité les fonctions du module getline dans plusieurs threads (vous pouvez utiliser les modules distincts d'expansion de fichiers et de complétion de mots dans plusieurs threads, voir les pages de manuel correspondantes pour plus de détails). Cependant, en raison de l'utilisation de fonctions réentrantes POSIX pour la recherche de répertoires personnels, etc., il est sûr d'utiliser ce module à partir d'un seul thread d'un programme multi-threadé, à condition que vos autres threads n'utilisent aucune fonction termcap ou terminfo.
