L

fonction gl_get_line() fait partie de la bibliothèque tecla (voir la page de manuel libtecla(3)). Si l'utilisateur tape sur un terminal, chaque appel lui demande une ligne de saisie, puis fournit des fonctionnalités d'édition interactives, similaires à celles du shell unix tcsh. En plus de l'édition simple de ligne de commande, elle prend en charge le rappel des lignes de commande précédemment saisies, l'achèvement par TAB des noms de fichiers et l'expansion des caractères génériques dans les noms de fichiers en ligne. La documentation des fonctionnalités d'édition de ligne de commande au niveau utilisateur et de toutes les options de configuration utilisateur se trouve dans la page de manuel tecla(7). Cette page de manuel concerne la documentation destinée aux programmeurs souhaitant utiliser cette bibliothèque dans leur application. UN E

LES FONCTIONS UTILISÉES DANS

L'EXEMPLE

Les descriptions des fonctions utilisées dans l'exemple sont les suivantes

: 
  GetLine *new_GetLine(size_t linelen, size_t
histlen)

Cette fonction crée les ressources utilisées par la fonction gl_get_line() et renvoie un pointeur opaque vers l'objet qui les contient. La longueur maximale d'une ligne de saisie est spécifiée via l'argument linelen, et le nombre d'octets à allouer pour stocker les lignes d'historique est défini par l'argument histlen. Les lignes d'historique sont stockées bout à bout dans un seul tampon de cette taille. Notez que cela signifie que le nombre de lignes d'historique pouvant être stockées à un moment donné dépend des longueurs des lignes individuelles. Si vous souhaitez fixer une limite supérieure au nombre de lignes pouvant être stockées, voir la fonction gl_limit_history() décrite plus loin. Si vous ne voulez pas d'historique du tout, spécifiez histlen comme zéro, et aucun tampon d'historique ne sera

alloué.

En cas d'erreur, un message est imprimé sur stderr et NULL est

renvoyé. 
  GetLine *del_GetLine(GetLine
*gl)

Cette fonction supprime les ressources qui ont été renvoyées par un appel précédent à new_GetLine(). Elle renvoie toujours NULL (c'est-à-dire un objet supprimé). Elle ne fait rien si l'argument gl est NULL

. 
  char *gl_get_line(GetLine *gl, const char *prompt,
                   const char *start_line, int start_pos)
;

La fonction gl_get_line() peut être appelée un nombre quelconque de fois pour lire la saisie de l'utilisateur. L'argument gl doit avoir été précédemment renvoyé par un appel à new_GetLine(). L'argument prompt doit être une chaîne normale terminée par NUL, spécifiant l'invite à présenter à l'utilisateur. Par défaut, les invites sont affichées littéralement, mais si activées avec la fonction gl_prompt_style() (voir plus loin), les invites peuvent contenir des directives pour souligner, passer en police grasse et en revenir, ou activer et désactiver la mise en

évidence.

Si vous souhaitez spécifier le contenu initial de la ligne pour que l'utilisateur la modifie, transmettez la chaîne souhaitée via l'argument start_line. Vous pouvez ensuite spécifier le caractère de cette ligne où le curseur est initialementned sur, en utilisant l'argument start_pos. Cela devrait être -1 si vous souhaitez que le curseur suive le dernier caractère de la ligne de départ. Si vous ne souhaitez pas précharger la ligne de cette manière, envoyez start_line comme NULL et définissez start_pos sur -1. Notez que le pointeur de ligne retourné par un appel à gl_get_line() peut être transmis à l'appel suivant à gl_get_line() via start_line. Cela permet à l'application de prendre la dernière ligne entrée et, si elle contient une erreur, de la présenter à l'utilisateur pour réédition, avec le curseur initialement positionné là où l'erreur a été rencontrée.

La fonction gl_get_line() retourne un pointeur vers la ligne entrée par l'utilisateur, ou NULL en cas d'erreur ou à la fin de l'entrée. Le pointeur retourné fait partie de l'objet ressource gl spécifié et ne doit donc pas être libéré par l'appelant, ni présumé inchangé d'un appel à l'autre. Lors de la lecture auprès d'un utilisateur à un terminal, il y aura toujours un caractère de nouvelle ligne à la fin de la ligne retournée. Lorsque l'entrée standard est issue d'un pipe ou d'un fichier, il y aura de même une nouvelle ligne, sauf si la ligne d'entrée était trop longue pour être stockée dans le tampon interne. Dans ce dernier cas, vous devriez appeler gl_get_line() à nouveau pour lire le reste de la ligne. Notez que ce comportement rend gl_get_line() similaire à fgets(). En fait, lorsque stdin n'est pas connecté à un terminal, gl_get_line() appelle simplement fgets().

SOURCES DE CONFIGURATION ALTERNATIVES

Comme mentionné ci-dessus, par défaut, les utilisateurs ont la possibilité de configurer le comportement de gl_get_line() via un fichier de configuration appelé .teclarc dans leur répertoire personnel. Le fait que toutes les applications partagent ce même fichier de configuration est à la fois un avantage et un inconvénient. Dans la plupart des cas, c'est un avantage, car cela favorise l'uniformité et libère l'utilisateur de la nécessité de configurer chaque application séparément. Dans certaines applications, cependant, ce moyen unique de configuration pose un problème. C'est particulièrement vrai pour les logiciels embarqués, où il n'y a pas de système de fichiers pour lire un fichier de configuration, et aussi dans les applications où un choix radicalement différent de raccourcis clavier est nécessaire pour émuler une interface clavier héritée. Pour répondre à de tels cas, la fonction suivante permet à l'application de contrôler d'où proviennent les informations de configuration.

  int gl_configure_getline(GetLine *gl,
                           const char *app_string,
                           const char *app_file,
                           const char *user_file);

Elle permet aux commandes de configuration qui seraient normalement lues à partir du fichier ~/.teclarc de l'utilisateur, d'être lues à partir de n'importe lequel ou d'aucun des éléments suivants : une chaîne, un fichier de configuration spécifique à l'application et/ou un fichier de configuration spécifique à l'utilisateur. Si cette fonction est appelée avant le premier appel à gl_get_line(), le comportement par défaut de lecture de ~/.teclarc lors du premier appel à gl_get_line() est désactivé, donc toute la configuration doit être effectuée à l'aide des sources de configuration spécifiées avec cette fonction.

Si app_string != NULL, il est interprété comme une chaîne contenant une ou plusieurs commandes de configuration, séparées les unes des autres dans la chaîne par des caractères de nouvelle ligne intégrés. Si app_file != NULL, il est interprété comme le chemin d'accès complet d'un fichier de configuration spécifique à l'application. Si user_file != NULL, il est interprété comme le chemin d'accès complet d'un fichier de configuration spécifique à l'utilisateur, tel que ~/.teclarc. Par exemple, dans l'appel suivant,

  gl_configure_getline(gl, "edit-mode vi \n nobeep",
                           "/usr/share/myapp/teclarc",
                           "~/.teclarc");

l'argument app_string amène l'application appelante à démarrer en mode d'édition vi, au lieu du mode emacs par défaut, et désactive l'utilisation de la sonnerie du terminal par la bibliothèque. Elle tente ensuite de lire les commandes de configuration système à partir d'un fichier optionnel appelé /usr/share/myapp/teclarc, puis lit enfin les commandes de configuration spécifiques à l'utilisateur à partir d'un fichier .teclarc optionnel dans le répertoire personnel de l'utilisateur. Notez que les arguments sont listés par ordre croissant de priorité, le contenu de app_string étant potentiellement remplacé par des commandes dans app_file, et les commandes dans app_file étant potentiellement remplacées par des commandes dans user_file.

Vous pouvez appeler cette fonction autant de fois que nécessaire, les résultats étant cumulatifs, mais notez que des copies de tous les noms de fichiers spécifiés via la

app_file et user_file sont enregistrés en interne pour une utilisation ultérieure par la fonction de liaison de touche read-init-files ; si vous prévoyez d'appeler cette fonction plusieurs fois, assurez-vous que le dernier appel spécifie les noms de fichiers que vous souhaitez relire lorsque l'utilisateur demande que les fichiers de configuration soient

relus.

COMPLÉTION DE MOTS

PERSONNALISÉE

Si dans votre application, vous souhaitez que la complétion par TAB complète d'autres choses en plus des noms de fichiers ou à leur place, vous pouvez organiser cela en enregistrant une fonction de rappel de complétion alternative, via un appel à la fonction gl_customize_c

ompletion(). 
  int gl_customize_completion(GetLine *gl, void *data,
                              CplMatchFn *match_fn)
;

L' argument data fournit un moyen à votre application de passer des informations arbitraires, propres à l'application, à la fonction de rappel. Celles-ci lui sont transmises à chaque fois qu'elle est appelée. Elle pourrait par exemple, pointer vers la table des symboles à partir de laquelle les complétions possibles doivent être recherchées. L' argument match_fn spécifie la fonction de rappel à appeler. Le type de fonction CplMatchFn est défini dans libtecla.h, tout comme une macro CPL_MATCH_FN() que vous pouvez utiliser pour déclarer et prototyper des fonctions de rappel. La déclaration et les responsabilités des fonctions de rappel sont décrites en détail dans la page de manuel cpl_complete_word(3)

.

En bref, la fonction de rappel est responsable de la recherche vers l'arrière dans la ligne d'entrée, en remontant depuis le point où l'utilisateur a appuyé sur TAB, pour trouver le début du mot en cours de complétion. Elle doit ensuite rechercher les complétions possibles de ce mot, et les enregistrer une par une dans l' objet WordCompletion qui lui est passé en argument, en appelant la fonction cpl_add_completion(). Si la fonction de rappel souhaite fournir la complétion de noms de fichiers en plus de ses propres complétions spécifiques, elle a la possibilité d'appeler elle-même la fonction de rappel de complétion de noms de fichiers intégrée. Ceci est également documenté dans la page de manuel cpl_complete_word(3)

.

Notez que si vous souhaitez que gl_get_line() renvoie la ligne d'entrée actuelle lorsqu'une complétion réussie a été effectuée, vous pouvez organiser cela lorsque vous appelez cpl_add_completion(), en faisant du dernier caractère du suffixe de continuation un caractère de nouvelle ligne. Si vous faites cela, la ligne d'entrée sera mise à jour pour afficher la complétion, ainsi que tout suffixe de continuation jusqu'au caractère de nouvelle ligne, puis gl_get_line() renverra cette ligne

d'entrée.

Si, pour une raison quelconque, votre fonction de rappel a besoin d'écrire quelque chose sur le terminal, elle doit appeler gl_normal_io() avant de le faire. Cela commencera une nouvelle ligne après la ligne d'entrée actuellement en cours d'édition, rétablira les E/S normales du terminal, et indiquera à gl_get_line() que la ligne d'entrée devra

être redessinée lorsque
le rappel se terminera.

AJOUT D'ACTIONS DE

COMPLÉTION

Dans la section précédente, la capacité à personnaliser le comportement de la seule action de complétion par défaut, complete-word, a été décrite. Dans cette section, la capacité à installer des fonctions d'action supplémentaires, afin que différents types de complétion de mots puissent être liés à différentes séquences de touches, est décrite. Cela est réalisé en utilisant la fonction gl_completion_action()

. 
  int gl_completion_action(GetLine *gl,
                           void *data, CplMatchFn *match_fn,
                           int list_only, const char *name,
                           const char *keyseq)
;

Les arguments data et match_fn sont tels que décrits dans la page de manuel cpl_complete_word, et spécifient la fonction de rappel qui doit être invoquée pour identifier les complétions possibles. L' argument list_only détermine si l'action en cours de définition doit tenter de compléter le mot aussi loin que possible dans la ligne d'entrée avant d'afficher d'éventuelles complétions ambiguës, ou si elle doit simplement afficher la liste des complétions possibles sans toucher à la ligne d'entrée. La première option est sélectionnée en spécifiant une valeur de 0, et la seconde en spécifiant une valeur de 1. L' argument name spécifie le nom par lequel les fichiers de configuration et les futures invocations de cette fonction doivent se référer à l'action. Il doit s'agir soit du nom d'une action de complétion existante à modifier, soit d'un nouveau nom non utilisé pour une nouvelle action. Enfin, l' argument keyseq spécifie la séquence de touches par défaut à lier à l'action. Si celui-ci est NULL, aucune nouvelle séquence de touches ne sera liée à

l'action.

Attention, pour que l'utilisateur puisse changer la séquence de touches liée aux actions installées de cette manière, lorsque vous appelez gl_completion_action() pour installer une action donnée pour la première fois, vous devez le faire entre l'appel à new_GetLine() et le premier appel à gl_get_line(). erreur.

Comme discuté pour gl_customize_completion(), si votre fonction de rappel, pour une raison quelconque, doit écrire quoi que ce soit sur le terminal, elle doit appeler gl_normal_io() a

vant de l
e faire.

DÉFINITION D'ACTIONS

PERSONNALISÉES

Bien que les actions de liaison de touches intégrées soient suffisantes pour les besoins de la plupart des applications, une application spécialisée peut parfois avoir besoin de définir une ou plusieurs actions personnalisées, liées à des séquences de touches propres à l'application. Par exemple, une application de vente bénéficierait d'une séquence de touches affichant le nom de la pièce correspondant à un numéro de pièce situé avant le curseur. Une telle fonctionnalité dépasse clairement le cadre des fonctions d'action intégrées. Ainsi, pour de tels cas particuliers, la fonction gl_register_action() est

fournie. 
  int gl_register_action(GetLine *gl, void *data,
			 GlActionFn *fn, const char *name,
			 const char *keyseq)
;

Cette fonction permet à l'application d'enregistrer une fonction externe, fn, qui sera ensuite appelée chaque fois que soit la séquence de touches spécifiée, keyseq, est saisie par l'utilisateur, soit l'utilisateur saisit toute autre séquence de touches qu'il lie ensuite au nom d'action spécifié, name, dans son fichier de configuration. L' argument data peut être un pointeur vers n'importe quoi que l'application souhaite voir transmis à la fonction d'action, fn, chaque fois que cette fonction est

invoquée.

La fonction d'action, fn, doit être déclarée à l'aide de la macro suivante, qui est définie dans libtecl

a.h. 
  #define GL_ACTION_FN(fn) GlAfterAction (fn)(GetLine *gl, \
              void *data, int count, size_t curpos, \
              const char
*line)

Les arguments gl et data sont ceux qui ont été précédemment passés à gl_register_action() lorsque la fonction d'action a été enregistrée. L' argument count est un argument numérique que l'utilisateur a la possibilité de saisir à l'aide de l' action digit-argument, avant d'invoquer l'action. Si l'utilisateur n'entre pas de nombre, alors l' argument count est défini à 1. Nominalement, cet argument est interprété comme un nombre de répétitions, ce qui signifie que l'action doit être répétée ce nombre de fois. En pratique cependant, pour certaines actions, un nombre de répétitions a peu de sens. Dans de tels cas, les actions peuvent soit simplement ignorer l' argument count, soit utiliser sa valeur à une autre

fin.

Une copie de la ligne d'entrée actuelle est passée dans l'argument en lecture seule line. La position actuelle du curseur dans cette chaîne est donnée par l'index contenu dans l' argument curpos. Notez que la manipulation directe de la ligne d'entrée et de la position du curseur n'est pas autorisée. C'est parce que les règles dictées par divers modes, tels que le mode vi par rapport au mode emacs, le mode sans écho, et le mode insertion par rapport au mode surimpression etc, rendent la tâche trop complexe pour qu'un développeur d'application puisse écrire une action d'édition conforme, et contraignent également les changements futurs à l'intérieur de gl_get_line(). Une solution potentielle à ce dilemme serait de permettre à la fonction d'action d'éditer la ligne en utilisant les actions d'édition existantes. Cela est actuellement à

l'étude.

Si la fonction d'action souhaite écrire du texte sur le terminal, sans que cela se mélange avec le texte affiché de la ligne d'entrée, ou lire depuis le terminal sans avoir à gérer les E/S brutes du terminal, alors avant de faire l'une ou l'autre de ces opérations, elle doit suspendre temporairement l'édition de ligne en appelant la fonction gl_normal_io(). Cette fonction vide toute sortie en attente vers le terminal, déplace le curseur au début de la ligne qui suit la dernière ligne du terminal de la ligne d'entrée, puis restaure le terminal à un état adapté à une utilisation avec les fonctions stdio C. Ce dernier inclut des choses comme la restauration du mappage normal de \n vers \r\n, et, en mode serveur, la restauration de la forme bloquante normale des E/S du terminal. Après avoir appelé cette fonction, la fonction d'action peut lire depuis et écrire vers le terminal sans crainte de créer un désordre. Il n'est pas nécessaire pour la fonction d'action de restaurer l'environnement d'édition original avant de se terminer. Cela est fait automatiquement par gl_get_line() après le retour de la fonction d'action. Voici un exemple simple de fonction d'action qui écrit la phrase « Hello world » sur une nouvelle ligne du terminal après la ligne en cours d'édition. Lorsque cette fonction se termine, la ligne d'entrée est redessinée sur la ligne qui suit la ligne « Hello world », et l'édition de ligne

reprend. 
  static GL_ACTION_FN(say_hello_fn)
  {
    if(gl_normal_io(gl))   /* Suspendre temporairement l'édition */
      return GLA_ABORT;
    printf("Hello world\n");
    return GLA_CONTINUE;
}

Les fonctions d'action doivent retourner l'une des valeurs suivantes, pour indiquer à gl_get_line() comment

procéder. 
  GLA_ABORT     -   Faire en sorte que gl_get_line() retourne NULL.
  GLA_RETURN    -   Faire en sorte que gl_get_line() retourne la
                    ligne d'entrée complétée.
  GLA_CONTINUE  -   Reprendre l'édition de la ligne de
commande.

Notez que le argument name de gl_register_action() spécifie le nom par lequel un utilisateur peut référencer l'action dans son fichier de configuration. Cela lui permet de relier l'action à une séquence de touches alternative. Pour que cela fonctionne, il est nécessaire d'appeler gl_register_action() entre l'appel à new_GetLine() et le premier appel à gl_get_

lin
e().

ARCHIVAGE MANUEL DE

L'HISTORIQUE

Par défaut, chaque fois qu'une ligne est saisie par l'utilisateur, elle est automatiquement ajoutée à la liste d'historique, juste avant que gl_get_line() retourne la ligne à l'appelant. C'est pratique pour la majorité des applications, mais il existe aussi des applications nécessitant un contrôle plus fin sur ce qui est ajouté à la liste d'historique. Dans de tels cas, l'ajout automatique des lignes saisies à la liste d'historique peut être désactivé en appelant la fonction gl_automatic

_history(). 
  int gl_automatic_history(GetLine *gl, int enable)
;

Si cette fonction est appelée avec son argument enable défini à 0, gl_get_line() n'archivera pas automatiquement les lignes saisies ultérieurement. L'archivage automatique peut être réactivé plus tard, en appelant à nouveau cette fonction, avec son argument enable défini à 1. Tant que l'archivage automatique de l'historique est désactivé, l'application appelante peut utiliser gl_append_history() pour ajouter des lignes à la liste d'historique selon les

besoins. 
  int gl_append_history(GetLine *gl, const char *line)
;

L' argument line spécifie la ligne à ajouter à la liste d'historique. Cela doit être une chaîne normale terminée par ' '. Si cette chaîne contient des caractères de nouvelle ligne, la ligne archivée dans la liste d'historique sera terminée par le premier d'entre eux. Sinon, elle sera terminée par le terminateur ' '. Si la ligne est plus longue que la longueur maximale de ligne d'entrée, qui a été spécifiée lorsque new_GetLine() a été appelé, lorsqu'elle sera rappelée, elle sera tronquée à la longueur réelle de la ligne gl_get_li

ne().

En cas de succès, gl_append_history() retourne 0. Sinon, elle retourne une valeur non nulle et définit errno à l'une des valeurs

suivantes. 
   EINVAL  -  L'un des arguments passés à
              gl_append_history() était NULL.
   ENOMEM  -  La ligne spécifiée était plus longue que la taille
              allouée du tampon d'historique (telle que spécifiée
              lors de l'appel à new_GetLine()), elle n'a donc pas pu
              être
archivée.

Une description textuelle de l'erreur peut être obtenue en appelant éventuellement gl_error_message(). Notez qu'après une telle erreur, la liste d'historique reste dans un état valide pour recevoir de nouvelles lignes d'historique, il y a donc peu d'inconvénient à simplement ignorer le statut de retour de gl_append_

CONFIGURATION DIVERSE DE

L'HISTORIQUE

Si vous souhaitez changer la taille du tampon d'historique qui a été initialement spécifiée dans l'appel à new_GetLine(), vous pouvez le faire avec la fonction gl_resize_history()

. 
  int gl_resize_history(GetLine *gl, size_t histlen)
;

L' argument histlen spécifie la nouvelle taille en octets, et si vous spécifiez 0, le tampon sera

supprimé.

Comme mentionné dans la discussion de new_GetLine(), le nombre de lignes qui peuvent être stockées dans le tampon d'historique dépend des longueurs des lignes individuelles. Par exemple, un tampon de 1000 octets pourrait tout aussi bien stocker 10 lignes de longueur moyenne de 100 octets, ou 2 lignes de longueur moyenne de 50 octets. Bien que le tampon ne soit jamais agrandi lorsque de nouvelles lignes sont ajoutées, une liste de pointeurs vers le tampon est agrandie si nécessaire pour accueillir le nombre de lignes actuellement stockées dans le tampon. Pour placer une limite supérieure au nombre de lignes dans le tampon, et donc un plafond sur la quantité de mémoire utilisée par cette liste, vous pouvez appeler la gl_limit_history() function.

  void gl_limit_history(GetLine *gl, int max_lines);

Le max_lines doit être un nombre positif >= 0, spécifiant une limite supérieure au nombre de lignes dans le tampon, ou -1 pour annuler toute limite précédemment spécifiée. Lorsqu'une limite est en vigueur, seules les max_lines lignes les plus récemment ajoutées sont conservées dans le tampon. Les anciennes lignes sont supprimées.

Pour supprimer des lignes du tampon d'historique, utilisez la fonction gl_clear_history().

  void gl_clear_history(GetLine *gl, int all_groups);

L'argument all_groups indique à la fonction s'il faut supprimer uniquement les lignes associées au groupe d'historique actuel (voir gl_group_history()) ou toutes les lignes historiques du tampon.

La fonction gl_toggle_history() vous permet d'activer et de désactiver l'historique sans perdre le contenu actuel de la liste d'historique.

  void gl_toggle_history(GetLine *gl, int enable);

Définir l'argument enable à 0 désactive le mécanisme d'historique, et le définir à 1 le réactive. Lorsque l'historique est désactivé, aucune nouvelle ligne ne sera ajoutée à la liste d'historique, et les raccourcis clavier de recherche d'historique agiront comme s'il n'y avait rien dans le tampon d'historique.

CHANGEMENT DES TERMINAUX

La fonction constructeur new_GetLine() suppose que l'entrée doit être lue depuis stdin, et la sortie écrite vers stdout. La fonction suivante vous permet de basculer vers différents flux d'entrée et de sortie.

  int gl_change_terminal(GetLine *gl, FILE *input_fp,
                         FILE *output_fp, const char *term);

L'argument gl est l'objet renvoyé par new_GetLine(). L'argument input_fp spécifie le flux à lire, et output_fp spécifie le flux à écrire. Ce n'est que si les deux font référence à un terminal que l'entrée interactive du terminal sera activée. Sinon, gl_get_line() appellera simplement fgets() pour lire l'entrée de la commande. Si les deux flux font référence à un terminal, ils doivent faire référence au même terminal, et le type de ce terminal doit être spécifié via l'argument term. La valeur de l'argument term est recherchée dans la base de données d'informations de terminal (terminfo ou termcap), afin de déterminer quelles séquences de contrôle spéciales sont nécessaires pour contrôler divers aspects du terminal. new_GetLine(), par exemple, passe la valeur de retour de getenv("TERM") dans cet argument. Notez que si un ou les deux de input_fp et output_fp ne font pas référence à un terminal, alors il est légal de passer NULL au lieu d'un type de terminal.

Notez que si vous souhaitez passer des descripteurs de fichiers à gl_change_terminal(), vous pouvez le faire en créant des wrappers de flux stdio en utilisant la fonction POSIX fdopen().

GESTION DES ÉVÉNEMENTS EXTERNES

Par défaut, gl_get_line() ne retourne pas tant qu'une ligne complète n'a pas été entrée par l'utilisateur, ou qu'une erreur ne se produit pas. Dans les programmes qui doivent surveiller les E/S provenant d'autres sources que le terminal, il existe deux options.

  1. Utilisez les fonctions décrites dans la page de manuel
     gl_io_mode(3) pour passer
     gl_get_line() en mode serveur non bloquant. Dans ce mode,
     gl_get_line() devient une fonction de montage de ligne
     non bloquante et incrémentielle qui peut être appelée en toute
     sécurité depuis une boucle d'événements externe. Bien que ce soit
     une méthode très polyvalente, elle implique d'assumer certaines
     responsabilités qui sont normalement gérées en coulisses par
     gl_get_line().
  2. Pendant que gl_get_line() attend une entrée clavier de
     l'utilisateur, vous pouvez lui demander de surveiller également
     l'activité sur des descripteurs de fichiers arbitraires, tels que
     des sockets réseau, des pipes, etc., et de faire appel à des
     fonctions de votre choix lorsque de l'activité est détectée. Cela
     fonctionne sur tout système disposant de l'appel système
     select(), ce qui est la plupart, sinon la totalité, des
     variantes d'unix.

L'enregistrement d'un descripteur de fichier à surveiller par gl_get_line() implique l'appel de la fonction gl_watch_fd().

  int gl_watch_fd(GetLine *gl, int fd, GlFdEvent event,
                  GlFdEventFn *callback, void *data);

Si cela renvoie une valeur non nulle, cela signifie que soit vos arguments sont invalides, soit cette fonctionnalité n'est pas prise en charge sur le système hôte.

L'argument fd est le descripteur de fichier à surveiller. L'argument event spécifie le type d'activité qui suscite l'intérêt, choisi parmi les valeurs énumérées suivantes :

  GLFD_READ   -  Surveiller l'arrivée de données à lire.
  GLFD_WRITE  -  Surveiller la capacité d'écrire sur le descripteur
                 de fichier sans bloquer.
  GLFD_URGENT -  Surveiller l'arrivée de données urgentes hors bande
                 sur le descripteur de fichier.

L'argument callback est la fonction à appeler lorsque l'activité sélectionnée est détectée. Elle doit être définie avec la macro suivante, qui est définie dans libtecla.h.

  #define GL_FD_EVENT_FN(fn) GlFdStatus (fn)(GetLine *gl, \
                                      void *data, int fd, \
                                      GlFdEvent event)

L'argument data de la fonction gl_watch_fd() est transmis à la fonction de rappel pour son propre usage, et peut pointer vers n'importe quoi, y compris NULL. Le descripteur de fichier et l'argument d'événement sont également transmis à la fonction de rappel, ce qui permet potentiellement d'enregistrer la même fonction de rappel pour plus d'un type d'événement et/ou plus d'un descripteur de fichier. La valeur de retour de la fonction de rappel doit être l'une des valeurs suivantes.

  GLFD_ABORT    -  Demander à gl_get_line() d'avorter. Lorsque cela
                   se produit, gl_get_line() renvoie
                   NULL, et un appel ultérieur à
                   gl_return_status() renverra
                   GLR_FDABORT. Notez que si l'application a
                   besoin que errno ait toujours une valeur
                   significative lorsque gl_get_line() renvoie
                   NULL, la fonction de rappel doit définir
                   errno de manière appropriée.
  GLFD_REFRESH  -  Redessiner la ligne d'entrée puis continuer
                   à attendre l'entrée. Renvoyer ceci si
                   votre rappel a écrit sur le terminal.
  GLFD_CONTINUE -  Continuer à attendre l'entrée, sans
                   redessiner la ligne.

Notez qu'avant d'appeler le rappel, gl_get_line() bloque la plupart des signaux et laisse ses propres gestionnaires de signaux installés, donc si vous avez besoin d'intercepter un signal particulier, vous devrez à la fois installer temporairement votre propre gestionnaire de signaux et débloquer le signal. Assurez-vous de rebloquer le signal (s'il était initialement bloqué) et de rétablir le gestionnaire de signaux d'origine, le cas échéant, avant de revenir.

L'argument data est ignoré dans ce cas.

SIGNAUX

La gestion des signaux est étonnamment difficile à réaliser de manière fiable sans conditions de course. Dans gl_get_line(), beaucoup d'attention a été portée pour permettre aux applications d'effectuer une gestion fiable des signaux autour de gl_get_line(). Cette section explique comment en tirer

parti.

À titre d'exemple des problèmes qui peuvent survenir si l'application n'est pas écrite correctement, imaginez qu'une application ait un gestionnaire de signal SIGINT qui définit un drapeau global. Supposons maintenant que l'application teste ce drapeau juste avant d'invoquer gl_get_line(). En conséquence, l'application ne pourra pas répondre au signal tant que l'utilisateur n'aura pas terminé la saisie de la ligne et que gl_get_line() ne sera pas retourné. Selon l'application, cela peut ou non être une catastrophe, mais au minimum cela déroutera

l'utilisateur.

La manière d'éviter ces problèmes est de faire ce qui

suit.

1. Si nécessaire, utilisez la fonction gl_trap_signal() pour
configurer gl_get_line() pour interrompre lorsque des signaux
importants sont

interceptés.

2. Configurez gl_get_line() de sorte que si l'un des
signaux qu'il intercepte est bloqué lorsque
gl_get_line() est appelé, il sera débloqué
automatiquement pendant les périodes où gl_get_line()
attend une E/S. Cela peut être fait soit

;

intercepter

configurée pour intercepter. Cela peut être fait en utilisant la fonction POSIX

   déplacés par celui qui vient d'être

L'une des façons dont le programme peut se retrouver dans un état incohérent est qu'un signal soit intercepté pendant que les étapes ci-dessus s'exécutent. Lorsque cela se produit, gl_get_line() procède comme suit.

Tout d'abord, il faut noter que lorsqu'un appel à siglongjmp() provoque le retour de sigsetjmp(), à condition que l'argument savesigs de sigsetjmp() ait été différent de zéro, comme spécifié ci-dessus, le masque de traitement des signaux est restauré à son état au moment de l'appel à sigsetjmp(). C'est la différence importante entre sigsetjmp() et l'ancien setjmp() problématique, et c'est l'ingrédient essentiel qui permet d'éviter les conditions de concurrence dans la gestion des signaux. De ce fait, nous sommes assurés que tous les signaux que nous avions bloqués avant d'appeler sigsetjmp() sont de nouveau bloqués dès qu'un signal est capturé. Les déclarations suivantes, qui sont ensuite exécutées, sont donc garanties d'être exécutées sans qu'aucun signal supplémentaire ne soit capturé.

1. Si les attributs de configuration de gl_get_line() du signal capturé l'indiquent,
gl_get_line() restaure les attributs du terminal à l'état
où ils se trouvaient lors de l'appel à gl_get_line(). Ceci est
particulièrement important pour les signaux qui suspendent ou
terminent le processus, car sinon le terminal serait laissé dans un
état inutilisable.

2. Il réinstalle ensuite les gestionnaires de signaux de l'application.

3. Il utilise ensuite la fonction raise() de la
bibliothèque C standard pour renvoyer le signal capturé à
l'application.

3. Ensuite, il débloque la réception du signal que nous venons d'envoyer. Cela a pour conséquence que le signal qui vient d'être envoyé via raise() est capturé par le gestionnaire de signaux d'origine de l'application, qui peut maintenant le gérer comme bon lui semble.

4. Si le gestionnaire de signaux retourne (c'est-à-dire qu'il ne
termine pas le processus), gl_get_line() rebloque la réception
du signal ci-dessus.

5. Il annule ensuite toute action effectuée dans la première des étapes ci-dessus, et redessine la ligne, si la configuration du signal le demande.

6. gl_get_line() reprend ensuite soit la tentative de
lecture d'un caractère, soit l'abandon, en fonction de la
configuration du signal capturé.

Ce que font les étapes ci-dessus en substance, c'est de traiter les signaux délivrés de manière asynchrone de manière synchrone, un par un, à un point du code où gl_get_line() a un contrôle total sur son environnement.

LA TAILLE DU TERMINAL

Sur la plupart des systèmes, la combinaison de l'ioctl TIOCGWINSZ et du signal SIGWINCH est utilisée pour maintenir une idée précise de la taille du terminal. La taille du terminal est interogée à nouveau chaque fois que gl_get_line() est appelé et chaque fois qu'un signal SIGWINCH est reçu.

Sur les quelques systèmes où ce mécanisme n'est pas disponible, au démarrage, new_GetLine() recherche d'abord les variables d'environnement LINES et COLUMNS. Si celles-ci ne sont pas trouvées, ou si elles contiennent des valeurs inutilisables, alors si une base de données d'informations sur le terminal comme terminfo ou termcap est disponible, la taille par défaut du terminal est recherchée dans cette base de données. Si cela échoue également à fournir la taille du terminal, une taille par défaut de 80 colonnes par 24 lignes est utilisée.

Même sur les systèmes qui prennent en charge ioctl(TIOCGWINSZ), si le terminal se trouve à l'autre extrémité d'une ligne série, le pilote de terminal n'a généralement aucun moyen de détecter quand un redimensionnement se produit ou de demander quelle est la taille actuelle. Dans de tels cas, aucun SIGWINCH n'est envoyé au processus, et les dimensions renvoyées par ioctl(TIOCGWINSZ) ne sont pas correctes. La seule façon de gérer de telles situations est de fournir un moyen à l'utilisateur d'entrer une commande qui indique au système distant quelle est la nouvelle taille. Cette commande appellerait alors la fonction gl_set_term_size() pour informer gl_get_line() du changement de taille.

  int gl_set_term_size(GetLine *gl, int ncolumn, int nline);

Les arguments ncolumn et nline sont utilisés pour spécifier les nouvelles dimensions du terminal, et ne doivent pas être inférieurs à 1. Sur les systèmes qui prennent en charge ioctl(TIOCSWINSZ), cette fonction appelle d'abord ioctl(TIOCSWINSZ) pour informer le pilote de terminal du changement de taille. En mode d'E/S serveur non bloquant, si une ligne est actuellement en cours de saisie, la ligne d'entrée est alors redessinée pour s'adapter à la taille modifiée. Enfin, les nouvelles valeurs sont enregistrées dans gl pour une utilisation future par gl_get_line().

La fonction gl_terminal_size() vous permet de connaître la taille actuelle du terminal et d'installer une taille de secours alternative pour les cas où la taille n'est pas disponible. Attention, la taille du terminal ne sera pas disponible si vous lisez depuis un pipe ou un fichier, donc les valeurs par défaut peuvent être importantes même sur les systèmes qui prennent en charge des moyens de connaître la taille du terminal.

  typedef struct {
    int nline;        /* Le terminal a nline lignes */
    int ncolumn;      /* Le terminal a ncolumn colonnes */
  } GlTerminalSize;
  GlTerminalSize gl_terminal_size(GetLine *gl,
                                  int def_ncolumn,
                                  int def_nline);

Cette fonction met d'abord à jour les dimensions du terminal de secours de gl_get_line(), puis enregistre ses découvertes dans la valeur de retour.

Les arguments def_ncolumn et def_nline spécifient le nombre par défaut de colonnes et de lignes de terminal à utiliser si la taille du terminal ne peut pas être déterminée via ioctl(TIOCGWINSZ) ou les variables d'environnement.

CACHER CE QUE VOUS TAPEZ

Lors de la saisie d'informations sensibles, telles que des mots de passe, il est préférable de ne pas afficher le texte que vous saisissez sur le terminal. De plus, ce texte ne doit pas être enregistré dans la liste d'historique, car quelqu'un qui trouverait votre terminal sans surveillance pourrait le rappeler, ou quelqu'un qui fouillerait dans vos répertoires pourrait le voir dans votre fichier d'historique. Dans cet esprit, la fonction gl_echo_mode() vous permet d'activer et de désactiver l'affichage et l'archivage de tout texte saisi ultérieurement dans les appels à gl_get_line().

  int gl_echo_mode(GetLine *gl, int enable);

L'argument enable spécifie si le texte saisi doit être visible ou non. S'il est égal à 0, les lignes saisies ultérieurement ne seront pas visibles sur le terminal et ne seront pas enregistrées dans la liste d'historique. S'il est égal à 1, les lignes d'entrée suivantes s'afficheront au fur et à mesure de leur saisie, et à condition que l'historique n'ait pas été désactivé via un appel à gl_toggle_history(), elles seront également archivées dans la liste d'historique. Enfin, si l'argument enable est égal à -1, le mode d'écho reste inchangé, ce qui vous permet de consulter le réglage actuel de manière non destructive via la valeur de retour. Dans tous les cas, la valeur de retour de la fonction est 0 si l'écho était désactivé avant l'appel de la fonction, et 1 s'il était activé.

Lorsque l'écho est désactivé, notez que bien que la complétion par tabulation complètera invisiblement votre préfixe autant que possible, les complétions ambiguës ne seront pas affichées.

QUERIES DE CARACTERE UNIQUE

Utiliser gl_get_line() pour demander à l'utilisateur une réponse sur un seul caractère est peu pratique pour l'utilisateur, car il doit appuyer sur la touche entrée ou retour avant que le caractère tapé ne soit renvoyé au programme. Ainsi, la fonction gl_query_char() a été fournie pour les requêtes sur un seul caractère comme celle-ci.

  int gl_query_char(GetLine *gl, const char *prompt,
                    char defchar);

Cette fonction affiche l'invite spécifiée au début d'une nouvelle ligne, et attend que l'utilisateur tape un caractère. Lorsque l'utilisateur tape un caractère, gl_query_char() l'affiche à droite de l'invite, démarre une nouvelle ligne, puis renvoie le caractère au programme appelant. La valeur de retour de la fonction est le caractère qui a été tapé. Si la lecture a dû être interrompue pour une raison quelconque, EOF est renvoyé à la place. Dans ce dernier cas, l'application peut appeler gl_return_status(), documenté précédemment, pour savoir ce qui s'est mal passé. Cela pourrait, par exemple, avoir été la réception d'un signal, ou le dépassement du délai d'inactivité optionnel.

Si l'utilisateur appuie simplement sur entrée, la valeur de l'argument defchar est substituée. Cela signifie que lorsque l'utilisateur appuie sur nouvelle ligne ou retour, le caractère spécifié dans defchar est affiché après l'invite, comme s'il l'avait tapé, ainsi que renvoyé à l'application appelante. Si un tel remplacement n'est pas important, il suffit de passer '0 comme valeur de defchar.

Si le caractère saisi est un caractère non imprimable, il est affiché symboliquement. Par exemple, control-A est affiché comme ^A, et les caractères au-delà de 127 sont affichés en octal, précédés d'un antislash.

Comme avec gl_get_line(), l'écho du caractère saisi peut être désactivé à l'aide de la fonction gl_echo_mode().

Si le processus appelant est suspendu en attendant que l'utilisateur tape sa réponse, le curseur est déplacé sur la ligne suivant la ligne d'invite, puis lorsque le processus reprend, l'invite est redessinée, et gl_query_char() reprend l'attente que l'utilisateur tape un caractère.

Notez qu'en mode serveur non bloquant, (voir gl_io_mode(3)), si une ligne d'entrée incomplète est en cours de lecture lorsque gl_query_char() est appelé, la ligne d'entrée partielle est discardée, et effacée du terminal, avant que la nouvelle invite ne soit affichée. Le prochain appel à gl_get_line() commencera donc l'édition d'une nouvelle ligne.

LECTURE DE CARACTERES BRUTS

Alors que la fonction gl_query_char() invite visiblement l'utilisateur à entrer un caractère et affiche ce qu'il a tapé, la fonction gl_read_char() lit un caractère du signal de l'utilisateur, sans rien écrire sur le terminal, ni perturber aucune ligne d'entrée incomplètement saisie. Cela signifie qu'elle peut être appelée non seulement entre les appels à gl_get_line(), mais aussi à partir de fonctions de rappel que l'application a enregistrées pour être appelées par gl_get_line().

  int gl_read_char(GetLine *gl);

En cas de succès, la valeur de retour de gl_read_char() est le caractère lu. En cas d'échec, EOF est renvoyé, et la fonction gl_return_status() peut être appelée pour savoir ce qui s'est mal passé. Les possibilités incluent le dépassement du délai d'inactivité optionnel, la réception d'un signal configuré pour interrompre gl_get_line(), ou le blocage des E/S du terminal, en mode d'E/S serveur non bloquant.

INTERNATIONAUX

Depuis la version 1.4.0 de libtecla, gl_get_line() est propre aux 8 bits. Cela signifie que tous les caractères sur 8 bits imprimables dans la locale actuelle de l'utilisateur sont désormais affichés tels quels et inclus dans la ligne d'entrée renvoyée. En supposant que le programme appelant contient correctement un appel comme

celui-ci,

Si aucune de ces variables n'est définie, ou si le programme néglige d'appeler setlocale, alors la locale par défaut C est utilisée, qui est l'ASCII 7 bits américain. Sur la plupart des plateformes de type unix, vous pouvez obtenir une liste des locales valides en tapant la commande

SÉCURITÉ DES

THREADS

Dans un programme multi-thread, vous devriez utiliser la version libtecla_r.a de la bibliothèque. Celle-ci utilise des versions réentrantes des fonctions système, lorsqu'elles sont disponibles. Malheureusement, ni terminfo ni termcap n'ont été conçus pour être réentrants, vous ne

pouvez donc pas utiliser en toute sécurité les fonctions du module getline dans plusieurs threads (vous pouvez utiliser les modules distincts d'expansion de fichiers et de complétion de mots dans plusieurs threads, voir les pages de manuel correspondantes pour plus de détails). Cepend
