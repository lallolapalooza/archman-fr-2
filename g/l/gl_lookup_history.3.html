DESCRIPTION

La fonction gl_get_line() fait partie de la bibliothèque tecla (voir la page de manuel libtecla(3)). Si l'utilisateur tape au terminal, chaque appel lui demande une ligne d'entrée, puis offre des fonctionnalités d'édition interactive, similaires à celles du shell tcsh de l'unix. En plus de l'édition simple de ligne de commande, elle prend en charge le rappel des lignes de commande précédemment entrées, la complétion par TAB des noms de fichiers, et l'expansion en ligne des jokers des noms de fichiers. La documentation des fonctionnalités d'édition de ligne de commande au niveau utilisateur et de toutes les options de configuration utilisateur se trouve dans la page de manuel tecla(7). Cette page de manuel concerne la documentation pour les programmeurs intéressés par l'utilisation de cette bibliothèque dans leur application.

UN EXEMPLE

Ce qui suit montre un exemple complet d'utilisation de la fonction gl_get_line() pour obtenir une entrée de l'utilisateur :

  #include <stdio.h>
  #include <locale.h>
  #include <libtecla.h>
  int main(int argc, char *argv[])
  { 
    char *line;    /* La ligne que l'utilisateur a tapée */
    GetLine *gl;   /* L'objet de ressources gl_get_line() */
    setlocale(LC_CTYPE, ""); /* Adopter le choix de l'utilisateur */
                             /* de l'ensemble de caractères. */
    gl = new_GetLine(1024, 2048);
    if(!gl)
      return 1;
    while((line=gl_get_line(gl, "$ ", NULL, -1)) != NULL &&
           strcmp(line, "exit\n") != 0)
      printf("Vous avez tapé : %s\n", line);
    gl = del_GetLine(gl);
    return 0;
  }

Dans l'exemple, d'abord les ressources nécessaires aux fonction gl_get_line() sont créées en appelant new_GetLine(). Cela alloue la mémoire utilisée dans les appels ultérieurs à la fonction gl_get_line(), y compris le tampon d'historique pour enregistrer les lignes entrées précédemment. Ensuite, une ou plusieurs lignes sont lues depuis l'utilisateur, jusqu'à ce qu'une erreur survienne, ou que l'utilisateur tape exit. Puis enfin, les ressources qui ont été allouées par new_GetLine() sont retournées au système en appelant del_GetLine(). Notez l'utilisation de la valeur de retour NULL de del_GetLine() pour rendre gl NULL. Ceci est une mesure de sécurité. Si le programme tente ensuite de passer gl à gl_get_line(), ladite fonction se plaindra et renverra une erreur, au lieu de tenter d'utiliser l'objet de ressource supprimé.

LES FONCTIONS UTILISÉES DANS L'EXEMPLE

Les descriptions des fonctions utilisées dans l'exemple sont les suivantes :

  GetLine *new_GetLine(size_t linelen, size_t histlen)

Cette fonction crée les ressources utilisées par la fonction gl_get_line() et renvoie un pointeur opaque vers l'objet qui les contient. La longueur maximale d'une ligne d'entrée est spécifiée via l'argument linelen, et le nombre d'octets à allouer pour stocker les lignes d'historique est défini par l'argument histlen. Les lignes d'historique sont stockées côte à côte dans un seul tampon de cette taille. Notez que cela signifie que le nombre de lignes d'historique qui peuvent être stockées à tout moment dépend des longueurs des lignes individuelles. Si vous souhaitez placer une limite supérieure sur le nombre de lignes qui peuvent être stockées, voyez la fonction gl_limit_history() décrite plus tard. Si vous ne souhaitez pas d'historique du tout, spécifiez histlen comme zéro, et aucun tampon d'historique ne sera alloué.

En cas d'erreur, un message est affiché sur stderr et NULL est renvoyé.

  GetLine *del_GetLine(GetLine *gl)

Cette fonction supprime les ressources qui ont été renvoyées par un appel précédent à new_GetLine(). Elle renvoie toujours NULL (c'est-à-dire un objet supprimé). Elle ne fait rien si l'argument gl est NULL.

  char *gl_get_line(GetLine *gl, const char *prompt,
                   const char *start_line, int start_pos);

La fonction gl_get_line() peut être appelée un nombre quelconque de fois pour lire l'entrée de l'utilisateur. L'argument gl doit avoir été précédemment renvoyé par un appel à new_GetLine(). L'argument prompt doit être une chaîne normale terminée par NUL, spécifiant l'invite à présenter à l'utilisateur. Par défaut, les invites sont affichées littéralement, mais si elles sont activées avec la fonction gl_prompt_style() (voir plus loin), les invites peuvent contenir des directives pour faire du soulignement, passer des polices en gras et revenir en arrière, ou activer et désactiver la mise en surbrillance.

Si vous souhaitez spécifier le contenu initial de la ligne, que l'utilisateur pourra éditer, passez la chaîne souhaitée via l'argument start_line. Vous pouvez ensuite spécifier à quel caractère de cette ligne le curseur est initialement positionné.

The gl_get_line() function returns a pointer to the line entered by the user, or NULL on error or at the end of the input. When standard input is being taken from a pipe or a file, there will similarly be a newline unless the input line was too long to store in the internal buffer. SOURCES DE CONFIGURATION

ALTERNATIVES

Comme mentionné ci-dessus, par défaut les utilisateurs ont la possibilité de configurer le comportement de gl_get_line() via un fichier de configuration appelé .teclarc dans leur répertoire personnel. Le fait que toutes les applications partagent ce même fichier de configuration est à la fois un avantage et un inconvénient. Dans la plupart des cas, c'est un avantage, car cela encourage l'uniformité et libère l'utilisateur de devoir configurer chaque application séparément. Dans certaines applications, cependant, ce seul moyen de configuration pose problème. C'est particulièrement vrai pour les logiciels embarqués, où il n'y a pas de système de fichiers pour lire un fichier de configuration, et aussi dans les applications où un choix radicalement différent de mappage de touches est nécessaire pour émuler une interface de clavier héritée. Pour prendre en charge de tels cas, la fonction suivante permet à l'application de contrôler d'où les informations de configuration sont

lues. 
  int gl_configure_getline(GetLine *gl,
                           const char *app_string,
                           const char *app_file,
                           const char *user_file)
;

Elle permet aux commandes de configuration qui seraient normalement lues depuis le fichier ~/.teclarc de l'utilisateur, d'être lues depuis une chaîne, un fichier de configuration spécifique à l'application, et/ou un fichier de configuration spécifique à l'utilisateur, ou aucun de ceux-ci. Si cette fonction est appelée avant le premier appel à gl_get_line(), le comportement par défaut de lecture de ~/.teclarc lors du premier appel à gl_get_line() est désactivé ; toute la configuration doit donc être réalisée à l'aide des sources de configuration spécifiées avec cette

fonction.

Si app_string != NULL, alors il est interprété comme une chaîne contenant une ou plusieurs commandes de configuration, séparées les unes des autres dans la chaîne par des caractères de nouvelle ligne incorporés. Si app_file != NULL alors il est interprété comme le chemin complet d'un fichier de configuration spécifique à l'application. Si user_file != NULL alors il est interprété comme le chemin complet d'un fichier de configuration spécifique à l'utilisateur, tel que ~/.teclarc. Par exemple, dans l'appel

suivant, 
  gl_configure_getline(gl, "edit-mode vi \n nobeep",
                           "/usr/share/myapp/teclarc",
                           "~/.teclarc")
;

l'argument app_string fait démarrer l'application appelante en mode d'édition vi, au lieu du mode emacs par défaut, et désactive l'utilisation de la cloche du terminal par la bibliothèque. Elle tente ensuite de lire les commandes de configuration système depuis un fichier optionnel appelé /usr/share/myapp/teclarc, puis lit enfin les commandes de configuration spécifiques à l'utilisateur depuis un fichier .teclarc optionnel dans le répertoire personnel de l'utilisateur. Notez que les arguments sont listés par ordre de priorité croissante, le contenu de app_string pouvant être potentiellement remplacé par les commandes dans app_file, et les commandes dans app_file pouvant être potentiellement remplacées par les commandes dans user_file

.

Vous pouvez appeler cette fonction autant de fois que nécessaire, les résultats étant cumulatifs, mais notez que des copies de tout nom de fichier spécifié via app_file et les arguments user_file sont enregistrés en interne pour une utilisation ultérieure par la fonction de liaison de touches read-init-files, donc si vous prévoyez d'appeler cette fonction plusieurs fois, assurez-vous que le dernier appel spécifie les noms de fichiers que vous souhaitez relire lorsque l'utilisateur demande que les fichiers de configuration soient relus.

Des séquences de touches individuelles peuvent également être liées et déliées à l'aide de la fonction gl_bind_keyseq().

  int gl_bind_keyseq(GetLine *gl, GlKeyOrigin origin,
                     const char *keyseq,
                     const char *action);

L'argument origin spécifie la priorité de la liaison, selon la personne pour qui elle est établie, et doit être l'une des deux valeurs suivantes.

  GL_USER_KEY   -   L'utilisateur a demandé cette liaison de touches.
  GL_APP_KEY    -   Il s'agit d'une liaison par défaut définie par l'application.

Lorsque les liaisons utilisateur et application pour une séquence de touches donnée ont été spécifiées, la liaison utilisateur a la priorité. La liaison de l'application est ensuite rétablie si la liaison de l'utilisateur est ultérieurement déliée via un autre appel à cette fonction, ou un appel à gl_configure_getline().

L'argument keyseq spécifie la séquence de touches à lier ou à délier, et est exprimé de la même manière que dans un fichier de configuration ~/.teclarc. L'argument action doit être soit une chaîne contenant le nom de l'action à laquelle lier la séquence de touches, soit NULL ou "" pour délier la séquence de touches.

COMPLETION DE MOTS PERSONNALISÉE

Si dans votre application, vous souhaitez que la complétion TAB complète d'autres éléments en plus des noms de fichiers ou à la place de ceux-ci, vous pouvez organiser cela en enregistrant une fonction de rappel de complétion alternative, via un appel à la fonction gl_customize_completion().

  int gl_customize_completion(GetLine *gl, void *data,
                              CplMatchFn *match_fn);

L'argument data permet à votre application de transmettre des informations arbitraires spécifiques à l'application à la fonction de rappel. Celles-ci sont transmises au rappel chaque fois qu'il est appelé. Il pourrait par exemple pointer vers la table des symboles à partir de laquelle les complétions possibles doivent être recherchées. L'argument match_fn spécifie la fonction de rappel à appeler. Le type de fonction CplMatchFn est défini dans libtecla.h, tout comme une macro CPL_MATCH_FN() que vous pouvez utiliser pour déclarer et prototyper des fonctions de rappel. La déclaration et les responsabilités des fonctions de rappel sont décrites en détail dans la page de manuel cpl_complete_word(3).

En bref, la fonction de rappel est responsable de regarder en arrière dans la ligne d'entrée, en arrière depuis le point où l'utilisateur a appuyé sur TAB, pour trouver le début du mot en cours de complétion. Elle doit ensuite rechercher les complétions possibles de ce mot, et les enregistrer une par une dans l'objet WordCompletion qui lui est passé en argument, en appelant la fonction cpl_add_completion(). Si la fonction de rappel souhaite fournir la complétion de noms de fichiers en plus de ses propres complétions spécifiques, elle a la possibilité d'appeler elle-même la fonction de rappel de complétion de noms de fichiers intégrée. Ceci est également documenté dans la page de manuel cpl_complete_word(3).

Notez que si vous souhaitez que gl_get_line() retourne la ligne d'entrée actuelle lorsqu'une complétion réussie a été effectuée, vous pouvez organiser cela lorsque vous appelez cpl_add_completion(), en faisant du dernier caractère du suffixe de continuation un caractère de nouvelle ligne. Si vous faites cela, la ligne d'entrée sera mise à jour pour afficher la complétion, ainsi que tout suffixe de continuation jusqu'au caractère de nouvelle ligne, puis gl_get_line() retournera cette ligne d'entrée.

Si, pour une raison quelconque, votre fonction de rappel doit écrire quelque chose sur le terminal, elle doit appeler gl_normal_io() avant de le faire. Cela commencera une nouvelle ligne après la ligne en cours d'édition, rétablira l'E/S normales du terminal et indiquera à gl_get_line() que la ligne d'entrée devra être redessinée au retour de la fonction de rappel.

AJOUT D'ACTIONS DE COMPLETION

Dans la section précédente, la capacité de personnaliser le comportement de la seule action de complétion par défaut, complete-word, a été décrite. Dans cette section, la capacité d'installer des fonctions d'action supplémentaires, de sorte que différents types de complétion de mots puissent être liés à différentes séquences de touches, est décrite. Ceci est réalisé en utilisant la fonction gl_completion_action().

  int gl_completion_action(GetLine *gl,
                           void *data, CplMatchFn *match_fn,
                           int list_only, const char *name,
                           const char *keyseq);

Les arguments data et match_fn sont tels que décrits dans la page de manuel cpl_complete_word, et spécifient la fonction de rappel qui devrait être invoquée pour identifier les complétions possibles. L'argument list_only détermine si l'action en cours de définition doit tenter de compléter le mot autant que possible dans la ligne d'entrée avant d'afficher toute complétion ambiguë possible, ou si elle doit simplement afficher la liste des complétions possibles sans toucher à la ligne d'entrée. La première option est sélectionnée en spécifiant une valeur de 0, et la seconde en spécifiant une valeur de 1. L'argument name spécifie le nom par lequel les fichiers de configuration et les invocations ultérieures de cette fonction doivent faire référence à l'action. Il doit s'agir soit du nom d'une action de complétion existante à modifier, soit d'un nouveau nom inutilisé pour une nouvelle action. Enfin, l'argument keyseq spécifie la séquence de touches par défaut à laquelle lier l'action. Si c'est NULL, aucune nouvelle séquence de touches ne sera liée à l'action.

Attention, pour que l'utilisateur puisse modifier la séquence de touches liée aux actions installées de cette manière, lorsque vous appelez gl_completion_action() pour installer une action donnée pour la première fois, vous devez le faire entre l'appel à new_GetLine() et le premier appel à gl_get_line(). Sinon, lorsque le fichier de configuration de l'utilisateur sera lu lors du premier appel à gl_get_line(), le nom de votre action supplémentaire ne sera pas connu, et toute référence à celui-ci dans le fichier de configuration générera une erreur.

Comme discuté pour gl_customize_completion(), si votre fonction de rappel, pour une raison quelconque, doit écrire quoi que ce soit sur le terminal, elle doit appeler gl_normal_io() avant de le faire.

DÉFINITION D'ACTIONS PERSONNALISÉES

Bien que les actions de liaison de touches intégrées soient suffisantes pour les besoins de la plupart des applications, une application spécialisée peut occasionnellement avoir besoin de définir une ou plusieurs actions personnalisées, liées à des séquences de touches spécifiques à l'application. Par exemple, une application de vente bénéficierait d'une séquence de touches qui afficherait le nom de la pièce correspondant à un numéro de pièce précédant le curseur. Une telle fonctionnalité dépasse clairement la portée des fonctions d'action intégrées. Ainsi, pour de tels cas spéciaux, la fonction gl_register_action() est fournie.

  int gl_register_action(GetLine *gl, void *data,
			 GlActionFn *fn, const char *name,
			 const char *keyseq);

Cette fonction permet à l'application d'enregistrer une fonction externe, fn, qui sera ensuite appelée chaque fois que la séquence de touches spécifiée, keyseq, est entrée par l'utilisateur, ou que l'utilisateur entre toute autre séquence de touches que l'utilisateur lie ensuite à l'action spécifiée, name, dans son fichier de configuration. L'argument data peut être un pointeur vers tout ce que l'application souhaite transmettre à la fonction d'action, fn, chaque fois que cette fonction est invoquée.

La fonction d'action, fn, doit être déclarée en utilisant la macro suivante, qui est définie dans libtecla.h.

  #define GL_ACTION_FN(fn) GlAfterAction (fn)(GetLine *gl, \
              void *data, int count, size_t curpos, \
              const char *line)

Les arguments gl et data sont ceux qui ont été précédemment passés à gl_register_action() lors de l'enregistrement de la fonction d'action. L'argument count est un argument numérique que l'utilisateur a la possibilité d'entrer en utilisant l'action digit-argument, avant d'invoquer l'action. Si l'utilisateur n'entre pas de nombre, l'argument count est défini sur 1. Nominalement, cet argument est interprété comme un compteur de répétition, ce qui signifie que l'action doit être répétée autant de fois. En pratique cependant, pour certaines actions, un compteur de répétition a peu de sens. Dans de tels cas, les actions peuvent simplement ignorer l'argument count, ou utiliser sa valeur à une fin différente.

Une copie de la ligne d'entrée actuelle est passée dans l'argument line, en lecture seule. La position actuelle du curseur dans cette chaîne est donnée par l'indice contenu dans l'argument curpos. Notez que la manipulation directe de la ligne d'entrée et de la position du curseur n'est pas autorisée. En effet, les règles dictées par divers modes, tels que le mode vi par rapport au mode emacs, le mode sans écho, et le mode d'insertion par rapport au mode de surécriture, etc., rendent trop complexe pour un développeur d'application l'écriture d'une action d'édition conforme, tout en contraignant les modifications futures des détails internes de gl_get_line(). Une solution potentielle à ce dilemme serait de permettre à la fonction d'action de modifier la ligne en utilisant les actions d'édition existantes. Ceci est actuellement à l'étude.

Si la fonction d'action souhaite écrire du texte sur le terminal, sans que cela ne se mélange avec le texte affiché de la ligne d'entrée, ou lire à partir du terminal sans avoir à gérer l'E/S brutes du terminal, alors avant de faire l'une de ces opérations, elle doit suspendre temporairement l'édition de ligne en appelant la fonction gl_normal_io(). Cette fonction vide toute sortie en attente vers le terminal, déplace le curseur au début de la ligne qui suit la dernière ligne du terminal de la ligne d'entrée, puis rétablit le terminal dans un état approprié pour une utilisation avec les installations C stdio. Ce dernier comprend des éléments tels que le rétablissement du mappage normal de \n à \r\n, et, en mode serveur, le rétablissement de la forme de blocage normale des E/S du terminal. Après avoir appelé cette fonction, la fonction d'action peut lire et écrire sur le terminal sans craindre de créer un désordre. Il n'est pas nécessaire pour la fonction d'action de rétablir l'environnement d'édition d'origine avant de retourner. Ceci est fait automatiquement par gl_get_line() après le retour de la fonction d'action. Ce qui suit est un exemple simple de fonction d'action qui écrit la phrase "Hello world" sur une nouvelle ligne de terminal après la ligne en cours d'édition. Au retour de cette fonction, la ligne d'entrée est redessinée sur la ligne qui suit la ligne "Hello world", et l'édition de ligne reprend.

Par défaut, chaque fois qu'une ligne est saisie par l'utilisateur, elle est automatiquement ajoutée à la liste d'historique, juste avant que gl_get_line() retourne la ligne à l'appelant. TRAITEMENT FIABLE DES

SIGNAUX

Le traitement des signaux est étonnamment difficile à faire de manière fiable sans conditions de course. Dans gl_get_line(), beaucoup de soin a été apporté pour permettre aux applications d'effectuer un traitement fiable des signaux autour de gl_get_line(). Cette section explique comment en tirer

parti.

À titre d'exemple des problèmes qui peuvent survenir si l'application n'est pas écrite correctement, imaginez qu'une application ait un gestionnaire de signal SIGINT qui définit un drapeau global. Supposons maintenant que l'application teste ce drapeau juste avant d'invoquer gl_get_line(). Si un signal SIGINT est reçu dans la petite fenêtre de temps entre l'instruction qui teste la valeur de ce drapeau et l'instruction qui appelle gl_get_line(), alors gl_get_line() ne verra pas le signal et ne sera pas interrompu. En conséquence, l'application ne pourra pas répondre au signal tant que l'utilisateur n'aura pas fini de saisir la ligne de saisie et que gl_get_line() n'aura pas retourné. Selon l'application, cela peut ou non être un désastre, mais au minimum cela dérouterait

l'utilisateur.

La manière d'éviter ces problèmes est de faire ce qui

suit.

1. Si nécessaire, utilisez la fonction gl_trap_signal() pour
configurer gl_get_line() pour interrompre lorsque des signaux importants
sont

captés.

2. Configurez gl_get_line() de sorte que si l'un des
signaux qu'il capture est bloqué lorsque
gl_get_line() est appelé, il sera débloqué
automatiquement pendant les moments où gl_get_line()
attend des E/S. Cela peut être fait soit
signal par signal, en appelant la
fonction gl_trap_signal() et en spécifiant l'attribut
GLS_UNBLOCK du signal, soit globalement en
appelant la fonction gl_catch_blocked()

;

à tous les signaux qu'elle est actuellement configurée pour
piéger

.

3. Juste avant d'appeler gl_get_line(), bloquez la livraison
de tous les signaux que gl_get_line() est
configuré pour piéger. Cela peut être fait en utilisant la fonction POSIX
sigprocmask() en conjonction avec la
fonction gl_list_signals()

La même technique peut être utilisée autour de certaines fonctions POSIX sensibles aux signaux, telles que sigsetjmp() et sigsuspend(), et en particulier, la première de ces deux fonctions peut être utilisée en conjonction avec siglongjmp() pour implémenter un traitement des signaux sans conditions de course autour d'autres appels système longs. La manière de le faire est expliquée ensuite, en montrant comment gl_get_line() parvient à piéger fiablement les signaux autour d'appels à des fonctions comme read() et select() sans conditions de

course.

La première chose que gl_get_line() fait, chaque fois qu'elle est appelée, est d'utiliser la fonction POSIX sigprocmask() pour bloquer la livraison de tous les signaux qu'elle est actuellement configurée pour capturer. C'est redondant si l'application les a déjà bloqués, mais cela ne fait aucun mal. Elle annule cette étape juste avant de

retourner.

Chaque fois que gl_get_line() doit appeler read() ou select() pour attendre une saisie de l'utilisateur, elle appelle d'abord la fonction POSIX sigsetjmp(), en s'assurant de spécifier une valeur non nulle pour son argument savesigs. La raison de ce dernier argument deviendra claire sous

peu.

Si sigsetjmp() retourne zéro, gl_get_line() fait alors ce qui

suit. 
a. Elle utilise la fonction POSIX sigaction() pour enregistrer
   un gestionnaire de signal temporaire pour tous les signaux qu'elle
   est configurée pour piéger. Ce gestionnaire de signal fait deux
   choses.
   1. Il enregistre le numéro du signal reçu
      dans une variable de portée fichier.
   2. Il appelle ensuite la fonction POSIX siglongjmp()
      en utilisant le tampon qui a été passé à
      sigsetjmp() comme premier argument, et
      une valeur non nulle comme second argument.
   Lorsque ce gestionnaire de signal est enregistré, le membre sa_mask
   de l'argument struct sigaction act de
   l'appel à sigaction() est configuré pour contenir tous
   les signaux que gl_get_line() capture. Cela
   garantit qu'un seul signal sera capté à la fois par
   notre gestionnaire de signal, ce qui à son tour garantit que les
   instances multiples de notre gestionnaire de signal ne se gênent pas.
b. Maintenant que le gestionnaire de signal a été configuré,
   gl_get_line() débloque tous les signaux qu'elle
   est configurée pour piéger.
c. Elle appelle ensuite les appels système read() ou select() pour attendre une saisie au clavier.
d. Si cet appel système retourne (c.-à-d. aucun signal n'est reçu),
   gl_get_line() bloque à nouveau la livraison des signaux
   d'intérêt.

   déplacés par celui qui vient d'être
installé.

suit.

Tout d'abord, notez que lorsqu'un appel à siglongjmp() provoque le retour de sigsetjmp(), à condition que l'argument savesigs de sigsetjmp() ait été non nul, comme spécifié ci-dessus, le masque de traitement des signaux est restauré à l'état dans lequel il se trouvait lorsque sigsetjmp() a été appelé. C'est la différence importante entre sigsetjmp() et l'ancien setjmp() problématique, et c'est l'ingrédient essentiel qui rend possible l'évitement des conditions de course dans la gestion des signaux. En raison de cela, nous sommes garantis que tous les signaux que nous avons bloqués avant d'appeler sigsetjmp() sont de nouveau bloqués dès qu'un signal est capturé. capturé.

appelé. C'est particulièrement important pour les signaux qui

terminal serait laissé dans un état

inutilisable.

l'application.

a été

capturé.

3. Ensuite, il débloque la livraison du signal que nous venons d'
envoyer. Cela entraîne la capture du signal qui vient d'être envoyé

original de l'application, qui peut maintenant le traiter comme il

4. Si le gestionnaire de signal retourne (c'est-à-dire s'il ne termine pas

Sur la plupart des systèmes, la combinaison de l' ioctl TIOCGWINSZ et du signal SIGWINCH est utilisée pour maintenir une idée précise de la taille du terminal. La taille du terminal est interrogée à nouveau chaque fois que gl_get_line() est appelé et à chaque fois qu'un signal SIGWINCH

est

reçu. Sur les quelques systèmes où ce mécanisme n'est pas disponible, au démarrage, new_GetLine() cherche d'abord les variables d'environnement LINES et COLUMNS. Si celles-ci ne sont pas trouvées, ou si elles contiennent des valeurs inutilisables, alors si une base de données d'informations sur le terminal comme terminfo ou termcap est disponible, la taille par défaut du terminal est recherchée dans cette base de données. Si cela ne permet pas non plus d'obtenir la taille du terminal, une taille par défaut de 80 colonnes par 24 lignes est

utilisée.

Même sur les systèmes qui prennent en charge ioctl(TIOCGWINSZ), si le terminal se trouve à l'autre bout d'une ligne série, le pilote du terminal n'a généralement aucun moyen de détecter quand un redimensionnement se produit ou d'interroger la taille actuelle. Dans de tels cas, aucun SIGWINCH n'est envoyé au processus, et les dimensions retournées par ioctl(TIOCGWINSZ) ne sont pas correctes. La seule façon de gérer de tels cas est de fournir un moyen à l'utilisateur d'entrer une commande qui indique au système distant quelle est la nouvelle taille. Cette commande appellerait alors la fonction gl_set_term_size() pour informer gl_get_line(

) 
  du changement de taille.
int gl_set_term_size(GetLine *gl, int ncolumn, int nline)
;

Les arguments ncolumn et nline sont utilisés pour spécifier les nouvelles dimensions du terminal et ne doivent pas être inférieurs à 1. Sur les systèmes qui prennent en charge ioctl(TIOCGWINSZ), cette fonction appelle d'abord ioctl(TIOCSWINSZ) pour informer le pilote du terminal du changement de taille. En mode E/S serveur non bloquant, si une ligne est actuellement en cours de saisie, la ligne saisie est alors redessinée pour s'adapter à la taille modifiée. Enfin, les nouvelles valeurs sont enregistrées dans gl pour une utilisation future par gl_get_li

ne().

La fonction gl_terminal_size() vous permet d'interroger la taille actuelle du terminal et d'installer une taille de secours alternative pour les cas où la taille n'est pas disponible. Attention, la taille du terminal ne sera pas disponible lors de la lecture depuis un pipe ou un fichier, de sorte que les valeurs par défaut peuvent être importantes même sur les systèmes qui prennent en charge des moyens de déterminer la taille du

terminal. 
  typedef struct {
    int nline;        /* Le terminal a nline lignes */
    int ncolumn;      /* Le terminal a ncolumn colonnes */

                                  int def_ncolumn,

;

Cette fonction met d'abord à jour les dimensions de secours du terminal de gl_get_line(), puis enregistre ses résultats dans la valeur de

retour.

Les arguments def_ncolumn et def_nline spécifient le nombre par défaut de colonnes et de lignes du terminal à utiliser si la taille du terminal ne peut pas être déterminée via ioctl(TIOCGWINSZ) ou les variables

d'environnement

CACHER CE QUE VOUS

TAPEZ

Lors de la saisie d'informations sensibles, comme les mots de passe, il est préférable que le texte que vous saisissez ne soit pas affiché en écho sur le terminal. De plus, un tel texte ne devrait pas être enregistré dans la liste d'historique, car quelqu'un trouvant votre terminal sans surveillance pourrait alors le rappeler, ou quelqu'un fouillant dans vos répertoires pourrait le voir dans votre fichier d'historique. En tenant compte de cela, la fonction gl_echo_mode() vous permet d'activer et de désactiver l'affichage et l'archivage de tout texte qui est saisi par la suite dans les appels à gl_get_li

ne(). 
  int gl_echo_mode(GetLine *gl, int enable)
;

L' argument enable spécifie si le texte saisi doit être visible ou non. S'il est 0, les lignes saisies par la suite ne seront pas visibles sur le terminal et ne seront pas enregistrées dans la liste d'historique. S'il est 1, les lignes d'entrée suivantes seront affichées au fur et à mesure de leur saisie et, à condition que l'historique n'ait pas été désactivé via un appel à gl_toggle_history(), elles seront également archivées dans la liste d'historique. Enfin, si l' argument enable est -1, le mode d'écho est laissé inchangé, ce qui vous permet d'interroger le paramètre actuel de manière non destructive via la valeur de retour. Dans tous les cas, la valeur de retour de la fonction est 0 si l'écho était désactivé avant l'appel de la fonction, et 1 s'il était

activé.

Lorsque l'écho est désactivé, notez que même si la complétion par

tabulation complétera votre préfixe de manière invisible aussi lo
in que possible, les complétions ambiguës ne seront pas affichées.

REQUÊTES À UN SEUL

CARACTÈRE

Utiliser gl_get_line() pour demander à l'utilisateur une réponse d'un seul caractère est gênant pour l'utilisateur, car il doit appuyer sur la touche entrée ou retour avant que le caractère qu'il a tapé ne soit renvoyé au programme. C'est pourquoi la fonction gl_query_char() a été fournie pour les requêtes d'un seul caractère comme

celle-ci. 
  int gl_query_char(GetLine *gl, const char *prompt,
                    char defchar)
;

Cette fonction affiche l'invite spécifiée au début d'une nouvelle ligne et attend que l'utilisateur tape un caractère. Lorsque l'utilisateur tape un caractère, gl_query_char() l'affiche à droite de l'invite, passe à la ligne suivante, puis renvoie le caractère au programme appelant. La valeur de retour de la fonction est le caractère qui a été tapé. Si la lecture a dû être interrompue pour une raison quelconque, EOF est renvoyé à la place. Dans ce dernier cas, l'application peut appeler la fonction précédemment documentée gl_return_status() pour savoir ce qui s'est mal passé. Il peut s'agir, par exemple, de la réception d'un signal ou du déclenchement du minuteur d'inactivité

optionnel.

Si l'utilisateur appuie simplement sur entrée, la valeur de l' argument defchar est substituée. Cela signifie que lorsque l'utilisateur appuie sur newline ou return, le caractère spécifié dans defchar est affiché après l'invite, comme si l'utilisateur l'avait tapé, et est également renvoyé à l'application appelante. Si un tel remplacement n'est pas important, passez simplement '0 comme valeur de defchar

.

Si le caractère saisi est un caractère non imprimable, il est affiché symboliquement. Par exemple, control-A est affiché comme ^A, et les caractères au-delà de 127 sont affichés en octal, précédés d'une barre oblique

inverse.

Comme pour gl_get_line(), l'écho du caractère saisi peut être désactivé à l'aide de la fonction gl_echo_mode()

.

Si le processus appelant est suspendu pendant qu'il attend que l'utilisateur tape sa réponse, le curseur est déplacé sur la ligne suivant la ligne d'invite, puis lorsque le processus reprend, l'invite est réaffichée, et gl_query_char() reprend l'attente que l'utilisateur tape un

caractère.

Notez qu'en mode serveur non bloquant, (voir gl_io_mode(3)), si une ligne d'entrée incomplète est en cours de lecture lorsque gl_query_char() est appelé, la ligne d'entrée partielle est abandonnée et effacée du terminal avant que la nouvelle invite ne soit affichée. Le prochain appel à gl_get_line() commencera donc

à éditer une n
ouvelle ligne.

LIRE DES CARACTÈRES

BRUTS

Alors que la fonction gl_query_char() invite visiblement l'utilisateur à entrer un caractère et affiche ce qu'il a tapé, la fonction gl_read_char() lit un caractère brut de l'utilisateur, sans rien écrire sur le terminal ni perturber une ligne d'entrée incomplète. Cela signifie qu'elle peut être appelée non seulement entre les appels à gl_get_line(), mais aussi depuis les fonctions de rappel que l'application a enregistrées pour être appelées par gl_get_li

ne(). 
  int gl_read_char(GetLine *gl)
;

En cas de succès, la valeur de retour de gl_read_char() est le caractère qui a été lu. En cas d'échec, EOF est renvoyé, et la fonction gl_return_status() peut être appelée pour savoir ce qui s'est mal passé. Les possibilités incluent le déclenchement du minuteur d'inactivité optionnel, la réception d'un signal configuré pour interrompre gl_get_line(), ou le blocage des E/S du terminal en mode E/S serveur non

bloquant.

Attention, certaines touches du clavier, comme les touches de fonction et les touches de curseur, génèrent généralement au moins 3 caractères chacune, de sorte qu'un seul appel à gl_read_char() nen't être suffisant

pour identifier
de telles frappes.

AFFICHAGE DYNAMIQUE DE

TEXTE

Entre les appels à gl_get_line(), la fonction gl_display_text() fournit un moyen pratique d'afficher des paragraphes de texte, justifiés à gauche et répartis sur une ou plusieurs lignes du terminal en fonction des contraintes de la largeur courante du terminal. Des exemples d'utilisation de cette fonction se trouvent dans les programmes de démonstration, où elle est utilisée pour afficher des introductions. Dans ces exemples, l'utilisation avancée de préfixes, suffixes et lignes de remplissage optionnels pour dessiner un cadre autour du texte est également

illustrée. 
  int gl_display_text(GetLine *gl, int indentation,
                      const char *prefix,
                      const char *suffix, int fill_char,
                      int def_width, int start,
                      const char *string)
;

Si gl n'est pas actuellement connecté à un terminal, par exemple si la sortie d'un programme qui utilise gl_get_line() est acheminée par canal vers un autre programme ou redirigée vers un fichier, alors la valeur du paramètre def_width est utilisée comme largeur du

terminal.

L' argument indentation spécifie le nombre de caractères à utiliser pour indenter chaque ligne de sortie. L' argument fill_char spécifie le caractère qui sera utilisé pour effectuer cette

indentation.

L' argument prefix peut être soit NULL, soit une chaîne à placer au début de chaque nouvelle ligne (après toute indentation). De même, l' argument suffix peut être soit NULL, soit une chaîne à placer à la fin de chaque ligne. Le suffixe est placé à fleur du bord droit du terminal, et tout espace entre son premier caractère et le dernier mot de cette ligne est rempli par le caractère spécifié via l' argument fill_char. Normalement, le caractère de remplissage est une

espace.

L' argument start indique à gl_display_text() combien de caractères ont déjà été écrits sur la ligne de terminal courante, et indique ainsi l'index de colonne de départ du curseur. Puisque la valeur de retour de gl_display_text() est l'index de colonne de fin du curseur, en passant la valeur de retour d'un appel à l'argument start de l'appel suivant, un paragraphe qui est réparti sur plus d'une chaîne peut être composé en appelant gl_display_text() pour chaque portion successive du paragraphe. Notez que des caractères de saut de ligne littéraux sont nécessaires à la fin de chaque paragraphe pour forcer le début d'une nouvelle

ligne.

En cas d'erreur, gl_display_tex

t() renv
oie -1.

INTERNATIONAUX

Depuis la version 1.4.0 de libtecla, gl_get_line() est propre aux 8 bits. Cela signifie que tous les caractères sur 8 bits qui sont imprimables dans la locale courante de l'utilisateur sont désormais affichés verbatim et inclus dans la ligne de saisie renvoyée. En supposant que le programme appelant contient correctement un appel comme le

suivant,

;

Si aucune de ces variables n'est définie, ou si le programme néglige d'appeler setlocale, alors la locale par défaut C est utilisée, qui est l'ASCII 7 bits américain. Sur la plupart des plateformes de type unix, vous pouvez obtenir une liste des locales valides en tapant la commande

: 
  locale
-a

à l'invite du shell. Une documentation supplémentaire sur la manière dont l'utilisateur peut utiliser cela pour saisir des caractères internationaux se trouve dans la page de manu
