L

fonction gl_get_line() fait partie de la bibliothèque tecla (voir la page man libtecla(3)). Si l'utilisateur tape sur un terminal, chaque appel l'invite à saisir une ligne d'entrée, puis fournit des fonctionnalités d'édition interactives, similaires à celles du shell unix tcsh. En plus de l'édition simple de ligne de commande, elle prend en charge le rappel des lignes de commande précédemment saisies, l'achèvement par TAB des noms de fichiers et l'expansion des caractères génériques dans les noms de fichiers en ligne. La documentation des fonctionnalités d'édition de ligne de commande au niveau utilisateur ainsi que de toutes les options de configuration utilisateur se trouve dans la page man tecla(7). Cette page man concerne la documentation destinée aux programmeurs souhaitant utiliser cette bibliothèque dans leur application. UN E

LES FONCTIONS UTILISÉES DANS

L'EXEMPLE

Les descriptions des fonctions utilisées dans l'exemple sont les suivantes

: 
  GetLine *new_GetLine(size_t linelen, size_t
histlen)

Cette fonction crée les ressources utilisées par la fonction gl_get_line() et renvoie un pointeur opaque vers l'objet qui les contient. La longueur maximale d'une ligne d'entrée est spécifiée via l'argument linelen, et le nombre d'octets à allouer pour stocker les lignes d'historique est défini par l'argument histlen. Les lignes d'historique sont stockées bout à bout dans un seul tampon de cette taille. Notez que cela signifie que le nombre de lignes d'historique pouvant être stockées à un moment donné dépend des longueurs des lignes individuelles. Si vous voulez placer une limite supérieure au nombre de lignes pouvant être stockées, voir la fonction gl_limit_history() décrite plus loin. Si vous ne voulez pas d'historique du tout, spécifiez histlen comme zéro, et aucun tampon d'historique ne sera

alloué.

En cas d'erreur, un message est imprimé vers stderr et NULL est

renvoyé. 
  GetLine *del_GetLine(GetLine
*gl)

Cette fonction supprime les ressources qui ont été renvoyées par un appel précédent à new_GetLine(). Elle renvoie toujours NULL (c'est-à-dire un objet supprimé). Elle ne fait rien si l'argument gl est NULL

. 
  char *gl_get_line(GetLine *gl, const char *prompt,
                   const char *start_line, int start_pos)
;

La fonction gl_get_line() peut être appelée un nombre quelconque de fois pour lire la saisie de l'utilisateur. L'argument gl doit avoir été précédemment renvoyé par un appel à new_GetLine(). L'argument prompt devrait être une chaîne normale terminée par NUL, spécifiant l'invite à présenter à l'utilisateur. Par défaut, les invites sont affichées littéralement, mais si activées avec la fonction gl_prompt_style() (voir plus loin), les invites peuvent contenir des directives pour souligner, basculer vers et depuis les polices en gras, ou activer et désactiver la mise en

évidence.

Si vous voulez spécifier le contenu initial de la ligne pour que l'utilisateur la modifie, passez la chaîne souhaitée via l'argument start_line. Vous pouvez ensuite spécifier le caractère de cette ligne où le curseur est initialement positionnéd over, en utilisant l'argument start_pos. Celui-ci doit être à -1 si vous souhaitez que le curseur suive le dernier caractère de la ligne de départ. Si vous ne souhaitez pas précharger la ligne de cette manière, envoyez start_line comme NULL, et définissez start_pos à -1. Notez que le pointeur de ligne renvoyé par un appel à gl_get_line() peut être renvoyé à l'appel suivant à gl_get_line() via start_line. Cela permet à l'application de prendre la dernière ligne entrée, et si elle contient une erreur, de la présenter à nouveau à l'utilisateur pour réédition, avec le curseur initialement positionné là où l'erreur a été rencontrée.

La fonction gl_get_line() renvoie un pointeur vers la ligne entrée par l'utilisateur, ou NULL en cas d'erreur ou à la fin de l'entrée. Le pointeur renvoyé fait partie de l'objet ressource gl spécifié, et ne doit donc pas être libéré par l'appelant, ni supposé être inchangé d'un appel à l'autre. Lors de la lecture auprès d'un utilisateur à un terminal, il y aura toujours un caractère de nouvelle ligne à la fin de la ligne renvoyée. Lorsque l'entrée standard est prise à partir d'un pipe ou d'un fichier, il y aura de même une nouvelle ligne, sauf si la ligne d'entrée était trop longue pour être stockée dans le tampon interne. Dans ce dernier cas, vous devriez appeler gl_get_line() à nouveau pour lire le reste de la ligne. Notez que ce comportement rend gl_get_line() similaire à fgets(). En fait, lorsque stdin n'est pas connecté à un terminal, gl_get_line() appelle simplement fgets().

SOURCES DE CONFIGURATION ALTERNATIVES

Comme mentionné ci-dessus, par défaut, les utilisateurs ont la possibilité de configurer le comportement de gl_get_line() via un fichier de configuration appelé .teclarc dans leur répertoire personnel. Le fait que toutes les applications partagent ce même fichier de configuration est un avantage et un inconvénient. Dans la plupart des cas, c'est un avantage, car cela favorise l'uniformité et évite à l'utilisateur d'avoir à configurer chaque application séparément. Dans certaines applications, cependant, ce moyen unique de configuration pose un problème. Ceci est particulièrement vrai pour les logiciels embarqués, où il n'y a pas de système de fichiers pour lire un fichier de configuration, et également dans les applications où un choix radicalement différent de raccourcis clavier est nécessaire pour émuler une interface clavier héritée. Pour répondre à de tels cas, la fonction suivante permet à l'application de contrôler d'où proviennent les informations de configuration.

  int gl_configure_getline(GetLine *gl,
                           const char *app_string,
                           const char *app_file,
                           const char *user_file);

Elle permet aux commandes de configuration qui seraient normalement lues à partir du fichier ~/.teclarc de l'utilisateur, d'être lues à partir de tout ou partie de : une chaîne, un fichier de configuration spécifique à l'application, et/ou un fichier de configuration spécifique à l'utilisateur. Si cette fonction est appelée avant le premier appel à gl_get_line(), le comportement par défaut de lecture de ~/.teclarc lors du premier appel à gl_get_line() est désactivé, donc toute configuration doit être réalisée à l'aide des sources de configuration spécifiées avec cette fonction.

Si app_string != NULL, alors il est interprété comme une chaîne contenant une ou plusieurs commandes de configuration, séparées les unes des autres dans la chaîne par des caractères de nouvelle ligne intégrés. Si app_file != NULL alors il est interprété comme le chemin d'accès complet d'un fichier de configuration spécifique à l'application. Si user_file != NULL alors il est interprété comme le chemin d'accès complet d'un fichier de configuration spécifique à l'utilisateur, tel que ~/.teclarc. Par exemple, dans l'appel suivant,

  gl_configure_getline(gl, "edit-mode vi \n nobeep",
                           "/usr/share/myapp/teclarc",
                           "~/.teclarc");

l'argument app_string fait que l'application appelante démarrera en mode d'édition vi, au lieu du mode emacs par défaut, et désactive l'utilisation de la sonnerie du terminal par la bibliothèque. Elle tente ensuite de lire les commandes de configuration à l'échelle du système à partir d'un fichier optionnel appelé /usr/share/myapp/teclarc, puis lit enfin les commandes de configuration spécifiques à l'utilisateur à partir d'un fichier optionnel .teclarc dans le répertoire personnel de l'utilisateur. Notez que les arguments sont listés par ordre croissant de priorité, le contenu de app_string pouvant être remplacé par les commandes dans app_file, et les commandes dans app_file pouvant être remplacées par les commandes dans user_file.

Vous pouvez appeler cette fonction autant de fois que nécessaire, les résultats étant cumulatifs, mais notez que des copies de tous les noms de fichiers spécifiés via l'argument de l'application

p_file et user_file sont enregistrés en interne pour une utilisation ultérieure par la fonction de liaison de touches read-init-files ; si vous prévoyez d'appeler cette fonction plusieurs fois, assurez-vous que le dernier appel spécifie les noms de fichiers que vous souhaitez relire lorsque l'utilisateur demande que les fichiers de configuration soient

relus.

COMPLÉTION DE MOTS

PERSONNALISÉE

Si dans votre application, vous souhaitez que la complétion par TAB complète d'autres éléments en plus des noms de fichiers ou à leur place, vous pouvez organiser cela en enregistrant une fonction de rappel de complétion alternative, via un appel à la fonction gl_customize_c

ompletion(). 
  int gl_customize_completion(GetLine *gl, void *data,
                              CplMatchFn *match_fn)
;

L'argument data fournit un moyen à votre application de passer des informations arbitraires spécifiques à l'application à la fonction de rappel. Celles-ci sont transmises à la fonction de rappel à chaque fois qu'elle est appelée. Elle peut par exemple, pointer vers la table de symboles à partir de laquelle les complétions possibles doivent être recherchées. L'argument match_fn spécifie la fonction de rappel à appeler. Le type de fonction CplMatchFn est défini dans libtecla.h, tout comme une macro CPL_MATCH_FN() que vous pouvez utiliser pour déclarer et prototyper des fonctions de rappel. La déclaration et les responsabilités des fonctions de rappel sont décrites en profondeur dans la page de manuel cpl_complete_word(3)

.

En bref, la fonction de rappel est responsable de la recherche en arrière dans la ligne d'entrée, en remontant depuis le point où l'utilisateur a appuyé TAB, pour trouver le début du mot en cours de complétion. Elle doit ensuite rechercher les complétions possibles de ce mot, et les enregistrer une par une dans l'objet WordCompletion qui lui est passé comme argument, en appelant la fonction cpl_add_completion(). Si la fonction de rappel souhaite fournir la complétion de noms de fichiers en plus de ses propres complétions spécifiques, elle a la possibilité d'appeler elle-même la fonction de rappel de complétion de noms de fichiers intégrée. Ceci est également documenté dans la page de manuel cpl_complete_word(3)

.

Notez que si vous souhaitez que gl_get_line() renvoie la ligne d'entrée actuelle lorsqu'une complétion réussie a été effectuée, vous pouvez organiser cela lorsque vous appelez cpl_add_completion(), en faisant que le dernier caractère du suffixe de continuation soit un caractère de nouvelle ligne. Si vous faites cela, la ligne d'entrée sera mise à jour pour afficher la complétion, ainsi que tout suffixe de continuation jusqu'au caractère de nouvelle ligne, puis gl_get_line() renverra cette ligne

d'entrée.

Si, pour une raison quelconque, votre fonction de rappel doit écrire quelque chose sur le terminal, elle doit appeler gl_normal_io() avant de le faire. Cela commencera une nouvelle ligne après la ligne d'entrée actuellement en cours d'édition, rétablira l'E/S normale du terminal, et indiquera à gl_get_line() que la ligne d'entrée devra être r

edessinée lorsque la fonc
tion de rappel retournera.

AJOUT D'ACTIONS DE

COMPLÉTION

Dans la section précédente, la capacité de personnaliser le comportement de la seule action de complétion par défaut, complete-word, a été décrite. Dans cette section, la capacité d'installer des fonctions d'action supplémentaires, afin que différents types de complétion de mots puissent être liés à différentes séquences de touches, est décrite. Cela est réalisé en utilisant la fonction gl_completion_action()

. 
  int gl_completion_action(GetLine *gl,
                           void *data, CplMatchFn *match_fn,
                           int list_only, const char *name,
                           const char *keyseq)
;

Les arguments data et match_fn sont tels que décrits dans la page de manuel cpl_complete_word, et spécifient la fonction de rappel qui doit être invoquée pour identifier les complétions possibles. L'argument list_only détermine si l'action qui est en cours de définition doit tenter de compléter le mot autant que possible dans la ligne d'entrée avant d'afficher d'éventuelles complétions ambiguës, ou si elle doit simplement afficher la liste des complétions possibles sans toucher à la ligne d'entrée. La première option est sélectionnée en spécifiant une valeur de 0, et la seconde en spécifiant une valeur de 1. L'argument name spécifie le nom par lequel les fichiers de configuration et les futures invocations de cette fonction doivent se référer à l'action. Il doit soit être le nom d'une action de complétion existante à modifier, soit être un nouveau nom non utilisé pour une nouvelle action. Enfin, l'argument keyseq spécifie la séquence de touches par défaut à lier à l'action. Si ceci est NULL, aucune nouvelle séquence de touches ne sera liée à

l'action.

Attention, pour que l'utilisateur puisse changer la séquence de touches liée aux actions installées de cette manière, lorsque vous appelez gl_completion_action() pour installer une action donnée pour la première fois, vous devriez le faire entre l'appel à new_GetLine() et le premier appel à gl_get_line(). Sinon, lorsque le fichier de configuration de l'utilisateur est lu lors du premier appel à gl_get_line(), le nom de votre action supplémentaire ne sera pas connu, et toute référence à celle-ci dans le fichier de configuration générera une

erreur.

Comme discuté pour gl_customize_completion(), si votre fonction de rappel, pour une raison quelconque, doit écrire quoi que ce soit sur le terminal, elle doit appeler gl_normal_io() a

vant de l
e faire.

DÉFINITION D'ACTIONS

PERSONNALISÉES

Bien que les actions de liaison de touches intégrées soient suffisantes pour les besoins de la plupart des applications, une application spécialisée peut parfois avoir besoin de définir une ou plusieurs actions personnalisées, liées à des séquences de touches spécifiques à l'application. Par exemple, une application de vente bénéficierait d'une séquence de touches qui affichait le nom de la pièce correspondant à un numéro de pièce situé avant le curseur. Une telle fonctionnalité dépasse clairement le cadre des fonctions d'action intégrées. Ainsi, pour de tels cas particuliers, la fonction gl_register_action() est

fournie. 
  int gl_register_action(GetLine *gl, void *data,
			 GlActionFn *fn, const char *name,
			 const char *keyseq)
;

Cette fonction permet à l'application d'enregistrer une fonction externe, fn, qui sera ensuite appelée chaque fois que soit la séquence de touches spécifiée, keyseq, est saisie par l'utilisateur, soit l'utilisateur saisit une autre séquence de touches qu'il lie ensuite au nom d'action spécifié, name, dans son fichier de configuration. L'argument data peut être un pointeur vers n'importe quoi que l'application souhaite voir passer à la fonction d'action, fn, chaque fois que cette fonction est

invoquée.

La fonction d'action, fn, devrait être déclarée à l'aide de la macro suivante, qui est définie dans libtecl

a.h. 
  #define GL_ACTION_FN(fn) GlAfterAction (fn)(GetLine *gl, \
              void *data, int count, size_t curpos, \
              const char
*line)

Les arguments gl et data sont ceux qui ont été précédemment passés à gl_register_action() lorsque la fonction d'action a été enregistrée. L'argument count est un argument numérique que l'utilisateur a la possibilité de saisir en utilisant l'action digit-argument, avant d'invoquer l'action. Si l'utilisateur n'entre pas de nombre, alors l'argument count est défini à 1. Nominalement, cet argument est interprété comme un nombre de répétitions, ce qui signifie que l'action devrait être répétée ce nombre de fois. En pratique, cependant, pour certaines actions, un nombre de répétitions a peu de sens. Dans de tels cas, les actions peuvent soit simplement ignorer l'argument count, soit utiliser sa valeur à une autre

fin.

Une copie de la ligne d'entrée actuelle est passée dans l'argument en lecture seule line. La position actuelle du curseur dans cette chaîne est donnée par l'index contenu dans l'argument curpos. Notez que la manipulation directe de la ligne d'entrée et de la position du curseur n'est pas autorisée. Cela est parce que les règles dictées par divers modes, tels que le mode vi par rapport au mode emacs, le mode sans écho, et le mode insertion par rapport au mode surimpression etc, rendent la tâche trop complexe pour un développeur d'application d'écrire une action d'édition conforme, ainsi que de contraindre les changements futurs aux internes de gl_get_line(). Une solution potentielle à ce dilemme serait de permettre à la fonction d'action d'éditer la ligne en utilisant les actions d'édition existantes. Cela est actuellement à

l'étude.

Si la fonction d'action souhaite écrire du texte sur le terminal, sans que cela se mélange avec le texte affiché de la ligne d'entrée, ou lire depuis le terminal sans avoir à gérer l'E/S brute du terminal, alors avant de faire l'une ou l'autre de ces opérations, elle doit suspendre temporairement l'édition de ligne en appelant la fonction gl_normal_io(). Cette fonction vide toute sortie en attente vers le terminal, déplace le curseur au début de la ligne qui suit la dernière ligne du terminal de la ligne d'entrée, puis restaure le terminal à un état qui convient à l'utilisation avec les fonctionnalités stdio du C. Ce dernier inclut des choses comme la restauration du mappage normal de \n vers \r\n, et, en mode serveur, la restauration de la forme bloquante normale de l'E/S du terminal. Après avoir appelé cette fonction, la fonction d'action peut lire depuis et écrire vers le terminal sans crainte de créer un désordre. Il n'est pas nécessaire pour la fonction d'action de restaurer l'environnement d'édition original avant de retourner. Cela est fait automatiquement par gl_get_line() après le retour de la fonction d'action. Ce qui suit est un exemple simple d'une fonction d'action qui écrit la phrase "Hello world" sur une nouvelle ligne du terminal après la ligne en cours d'édition. Lorsque cette fonction retourne, la ligne d'entrée est redessinée sur la ligne qui suit la ligne "Hello world", et l'édition de ligne

reprend. 
  static GL_ACTION_FN(say_hello_fn)
  {
    if(gl_normal_io(gl))   /* Suspendre temporairement l'édition */
      return GLA_ABORT;
    printf("Bonjour le monde\n");
    return GLA_CONTINUE;
  }

Les fonctions d'action doivent retourner l'une des valeurs suivantes, pour indiquer à gl_get_line() comment procéder.

  GLA_ABORT     -   Faire retourner NULL à gl_get_line().
  GLA_RETURN    -   Faire retourner à gl_get_line() la
                    ligne d'entrée terminée.
  GLA_CONTINUE  -   Reprendre l'édition de ligne de commande.

Notez que l'argument name de gl_register_action() spécifie le nom par lequel un utilisateur peut faire référence à l'action dans son fichier de configuration. Cela lui permet de reconfigurer l'action avec une séquence de touches alternative. Pour que cela fonctionne, il est nécessaire d'appeler gl_register_action() entre l'appel à new_GetLine() et le premier appel à gl_get_line().

FICHIERS HISTORIQUES

Pour enregistrer le contenu du tampon d'historique avant de quitter votre application, et les restaurer ultérieurement lors du prochain démarrage de l'application, les fonctions suivantes sont fournies.

 int gl_save_history(GetLine *gl, const char *filename,
                     const char *comment, int max_lines);
 int gl_load_history(GetLine *gl, const char *filename,
                     const char *comment);

L'argument filename spécifie le nom à donner au fichier d'historique lors de l'enregistrement, ou le nom d'un fichier d'historique existant lors du chargement. Il peut contenir des expressions de répertoire personnel et de variables d'environnement, telles que "~/.myapp_history" ou "$HOME/.myapp_history".

Avec chaque ligne d'historique, des informations supplémentaires à son sujet, telles que la date à laquelle elle a été entrée par l'utilisateur, et son niveau d'imbrication, sont enregistrées sous forme de commentaire précédant la ligne dans le fichier d'historique. L'écriture de ces informations sous forme de commentaire permet au fichier d'historique de servir également de fichier de commandes, au cas où vous souhaiteriez rejouer une session entière à partir de celui-ci. Les préfixes de commentaire différant selon les langages, l'argument comment est fourni pour spécifier le préfixe de commentaire. Par exemple, si votre application était un shell Unix, comme le shell Bourne, vous spécifieriez "#" ici. Quel que soit le caractère de commentaire choisi, vous devez spécifier le même préfixe à gl_load_history() que celui utilisé lors de l'appel à gl_save_history() pour écrire le fichier d'historique.

L'argument max_lines doit être -1 pour spécifier que toutes les lignes de la liste d'historique doivent être enregistrées, ou un nombre positif spécifiant un plafond sur le nombre de lignes les plus récentes à enregistrer.

Les deux fonctions retournent une valeur non nulle en cas d'erreur, après avoir écrit un message d'erreur sur stderr. Notez que gl_load_history() ne considère pas la non-existence d'un fichier comme une erreur.

LISTES HISTORIQUES MULTIPLES

Si votre application utilise un seul objet GetLine pour entrer de nombreux types de lignes d'entrée différents, vous pourriez souhaiter que gl_get_line() distingue les différents types de lignes dans la liste d'historique, et ne rappelle que les lignes correspondant au type de ligne actuel. Pour répondre à cette exigence, gl_get_line() marque les lignes enregistrées dans la liste d'historique avec un identifiant entier choisi par l'application. Initialement, cet identifiant est défini à 0 par new_GetLine(), mais il peut être modifié ultérieurement en appelant gl_group_history().

  int gl_group_history(GetLine *gl, unsigned id);

L'identifiant entier id peut être n'importe quel nombre choisi par l'application, mais notez que gl_save_history() et gl_load_history() préservent l'association entre les identifiants et les lignes d'entrée historiques entre les invocations du programme, vous devriez donc choisir des identifiants fixes pour les différents types de lignes utilisés par votre application.

Chaque fois que gl_get_line() ajoute une nouvelle ligne d'entrée à la liste d'historique, l'identifiant d'historique actuel est enregistré avec elle, et lorsqu'il est demandé de rappeler une ligne d'entrée historique, il ne rappelle que les lignes marquées avec l'identifiant actuel.

AFFICHAGE DE L'HISTORIQUE

La liste d'historique peut être affichée en appelant gl_show_history().

  int gl_show_history(GetLine *gl, FILE *fp,
                      const char *fmt,
                      int all_groups,
                      int max_lines);

Ceci affiche le contenu actuel de la liste d'historique sur le flux de sortie stdio fp. Si l'argument max_lines est supérieur ou égal à zéro, alors pas plus que ce nombre de lignes les plus récentes ne sera affiché. Si l'argument all_groups est non nul, les lignes de tous les groupes d'historique sont affichées. Sinon, seules celles du groupe d'historique actuellement sélectionné sont affichées. L'argument chaîne de format, fmt, détermine comment la ligne est affichée. Il peut contenir des caractères arbitraires qui sont écrits tels quels, intercalés avec les directives de format suivantes :

  %D  -  La date à laquelle la ligne a été initialement
         entrée, formatée comme 2001-11-20.
  %T  -  L'heure de la journée à laquelle la ligne a été
         entrée, formatée comme 23:59:59.
  %N  -  Le numéro séquentiel d'entrée de la ligne dans
         le tampon d'historique.
  %G  -  Le numéro du groupe d'historique auquel la
         ligne appartient.
  %%  -  Un caractère % littéral.
  %H  -  La ligne d'historique elle-même.

Ainsi, une chaîne de format comme "%D %T %H\n" produirait quelque chose comme :

  2001-11-20 10:23:34  Bonjour le monde

Notez l'inclusion d'un caractère de nouvelle ligne explicite dans la chaîne de format.

RECHERCHE DANS L'HISTORIQUE

La fonction gl_lookup_history() permet à l'application appelante de rechercher des lignes dans la liste d'historique.

  typedef struct {
    const char *line;    /* La ligne historique */
                         /*  demandée. */
    unsigned group;      /* Le groupe d'historique auquel */
                         /*  la ligne appartient. */
    time_t timestamp;    /* La date et l'heure auxquelles */
                         /*  la ligne a été initialement */
                         /*  entrée. */
  } GlHistoryLine;
  int gl_lookup_history(GetLine *gl, unsigned long id,
                        GlHistoryLine *hline);

L'argument id indique quelle ligne rechercher, où la première ligne entrée dans la liste d'historique après l'appel à new_GetLine() est désignée par 0, et les lignes entrées successivement sont désignées par des nombres croissants. Notez que la plage des lignes actuellement conservées dans la liste d'historique peut être interrogée en appelant la fonction gl_range_of_history(), décrite plus loin. Si la ligne demandée se trouve dans la liste d'historique, les détails de la ligne sont enregistrés dans la variable pointée par l'argument hline, et 1 est retourné. Sinon, 0 est retourné, et la variable pointée par hline n'est pas modifiée.

Attention, la chaîne retournée dans hline->line fait partie du tampon d'historique, elle ne doit donc pas être modifiée par l'appelant, et sera réutilisée lors du prochain appel à toute fonction qui prend gl comme argument. Par conséquent, vous devriez faire une copie privée de cette chaîne si vous avez besoin de la conserver.

ARCHIVAGE MANUEL DE L'HISTORIQUE

Par défaut, chaque fois qu'une ligne est entrée par l'utilisateur, elle est automatiquement ajoutée à la liste d'historique, juste avant que gl_get_line() ne retourne la ligne à l'appelant. Ceci est pratique pour la majorité des applications, mais il existe également des applications qui nécessitent un contrôle plus fin sur ce qui est ajouté à la liste d'historique. Dans de tels cas, l'ajout automatique des lignes entrées à la liste d'historique peut être désactivé en appelant la fonction gl_automatic_history().

  int gl_automatic_history(GetLine *gl, int enable);

Si cette fonction est appelée avec son argument enable mis à 0, gl_get_line() n'archivera pas automatiquement les lignes entréés par la suite. L'archivage automatique peut être réactivé plus tard, en appelant à nouveau cette fonction, avec son argument enable mis à 1. Pendant que l'archivage automatique de l'historique est désactivé, l'application appelante peut utiliser gl_append_history() pour ajouter des lignes à la liste d'historique au besoin.

  int gl_append_history(GetLine *gl, const char *line);

L'argument line spécifie la ligne à ajouter à la liste d'historique. Ce doit être une chaîne normale terminée par ' '. Si cette chaîne contient des caractères de nouvelle ligne, la ligne qui sera archivée dans la liste d'historique sera terminée par le premier de ces caractères. Sinon, elle sera terminée par le terminateur ' '. Si la ligne est plus longue que la longueur maximale de ligne d'entrée, qui a été spécifiée lors de l'appel à new_GetLine(), alors, lors de son rappel, elle sera tronquée à la longueur de ligne actuelle de gl_get_line().

En cas de succès, gl_append_history() retourne 0. Sinon, elle retourne une valeur non nulle, et définit errno à l'une des valeurs suivantes.

   EINVAL  -  Un des arguments passés à
              gl_append_history() était NULL.
   ENOMEM  -  La ligne spécifiée était plus longue que la taille allouée
              du tampon d'historique (telle que spécifiée lors de
              l'appel à new_GetLine()), donc elle n'a pas pu être
              archivée.

Une description textuelle de l'erreur peut éventuellement être obtenue en appelant gl_error_message(). Notez qu'après une telle erreur, la liste d'historique reste dans un état valide pour recevoir de nouvelles lignes d'historique, il y a donc peu de danger à simplement ignorer le statut de retour de gl_append_history().

CONFIGURATION DIVERS DE L'HISTORIQUE

Si vous souhaitez modifier la taille du tampon d'historique qui a été initialement spécifiée dans l'appel à new_GetLine(), vous pouvez le faire avec la fonction gl_resize_history().

  int gl_resize_history(GetLine *gl, size_t histlen);

L'argument histlen spécifie la nouvelle taille en octets, et si vous la spécifiez comme 0, le tampon sera supprimé.

Comme mentionné dans la discussion sur new_GetLine(), le nombre de lignes pouvant être stockées dans le tampon d'historique dépend des longueurs des lignes individuelles. Par exemple, un tampon de 1000 octets pourrait stocker 10 lignes de longueur moyenne de 100 octets, ou 2 lignes de longueur moyenne de 50 octets. Bien que le tampon ne soit jamais étendu lors de l'ajout de nouvelles lignes, une liste de pointeurs dans le tampon est étendue si nécessaire pour accueillir le nombre de lignes actuellement stockées dans le tampon. Pour placer une limite supérieure sur le nombre de lignes dans le tampon, et donc un plafond sur la quantité de mémoire utilisée dans cette liste, vous pouvez appeler gl_limit_histo

ry() fonction.

  void gl_limit_history(GetLine *gl, int max_lines);

La valeur de max_lines doit être un nombre positif >= 0, spécifiant une limite supérieure au nombre de lignes dans le tampon, ou être -1 pour annuler toute limite spécifiée précédemment. Lorsqu'une limite est en vigueur, seules les max_lines lignes ajoutées le plus récemment sont conservées dans le tampon. Les anciennes lignes sont supprimées.

Pour supprimer des lignes du tampon d'historique, utilisez la fonction gl_clear_history().

  void gl_clear_history(GetLine *gl, int all_groups);

L'argument all_groups indique à la fonction s'il faut supprimer uniquement les lignes associées au groupe d'historique actuel (voir gl_group_history()) ou toutes les lignes historiques du tampon.

La fonction gl_toggle_history() vous permet d'activer ou de désactiver l'historique sans perdre le contenu actuel de la liste d'historique.

  void gl_toggle_history(GetLine *gl, int enable);

Définir l'argument enable à 0 désactive le mécanisme d'historique, et le définir à 1 le réactive. Lorsque l'historique est désactivé, aucune nouvelle ligne n'est ajoutée à la liste d'historique, et les raccourcis clavier de recherche d'historique agissent comme s'il n'y avait rien dans le tampon d'historique.

INTERROGATION DES INFORMATIONS D'HISTORIQUE

L'état configuré de la liste d'historique peut être interrogé avec la fonction gl_history_state().

  typedef struct {
    int enabled;     /* Vrai si l'historique est activé */
    unsigned group;  /* Le groupe d'historique actuel */
    int max_lines;   /* La limite supérieure actuelle du */
                     /*  nombre de lignes dans la liste */
                     /*  d'historique, ou -1 si illimitée. */
  } GlHistoryState;
  void gl_state_of_history(GetLine *gl,
                           GlHistoryState *state);

Au retour, les informations d'état sont enregistrées dans la variable pointée par l'argument state.

La fonction gl_range_of_history() renvoie le nombre et la plage des lignes dans la liste d'historique.

typedef struct {
  unsigned long oldest;  /* Le numéro d'entrée séquentiel */
                         /*  de la ligne la plus ancienne */
                         /*  dans la liste d'historique. */
  unsigned long newest;  /* Le numéro d'entrée séquentiel */
                         /*  de la ligne la plus récente */
                         /*  dans la liste d'historique. */
  int nlines;            /* Le nombre de lignes dans la */
                         /*  liste d'historique. */
} GlHistoryRange;
void gl_range_of_history(GetLine *gl, GlHistoryRange *range);

Les valeurs de retour sont enregistrées dans la variable pointée par l'argument range. Si le membre nlines de cette structure est supérieur à zéro, alors les membres oldest et newest indiquent la plage des lignes dans la liste, et newest=oldest+nlines-1. Sinon, ils sont tous deux à zéro.

La fonction gl_size_of_history() renvoie la taille totale du tampon d'historique et la quantité du tampon actuellement occupée.

  typedef struct {
    size_t size;      /* La taille du tampon d'historique */
                      /*  (octets). */
    size_t used;      /* Le nombre d'octets du tampon */
                      /*  d'historique actuellement */
                      /*  occupés. */
  } GlHistorySize;
  void gl_size_of_history(GetLine *gl, GlHistorySize *size);

Au retour, les informations de taille sont enregistrées dans la variable pointée par l'argument size.

CHANGEMENT DE TERMINAL

La fonction constructeur new_GetLine() suppose que l'entrée doit être lue depuis stdin et la sortie écrite sur stdout. La fonction suivante vous permet de passer à différents flux d'entrée et de sortie.

  int gl_change_terminal(GetLine *gl, FILE *input_fp,
                         FILE *output_fp, const char *term);

L'argument gl est l'objet retourné par new_GetLine(). L'argument input_fp spécifie le flux à lire, et output_fp spécifie le flux à écrire. Ce n'est que si les deux font référence à un terminal que l'entrée de terminal interactive sera activée. Sinon, gl_get_line() appellera simplement fgets() pour lire l'entrée de commande. Si les deux flux font référence à un terminal, alors ils doivent faire référence au même terminal, et le type de ce terminal doit être spécifié via l'argument term. La valeur de l'argument term est recherchée dans la base de données d'informations de terminal (terminfo ou termcap), afin de déterminer quelles séquences de contrôle spéciales sont nécessaires pour contrôler divers aspects du terminal. new_GetLine(), par exemple, passe la valeur de retour de getenv("TERM") dans cet argument. Notez que si un ou les deux de input_fp et output_fp ne font pas référence à un terminal, alors il est légal de passer NULL à la place d'un type de terminal.

Notez que si vous souhaitez passer des descripteurs de fichiers à gl_change_terminal(), vous pouvez le faire en créant des wrappers de flux stdio en utilisant la fonction POSIX fdopen().

GESTION DES ÉVÉNEMENTS EXTERNES

Par défaut, gl_get_line() ne retourne pas tant qu'une ligne d'entrée complète n'a pas été saisie par l'utilisateur, ou qu'une erreur ne se produit. Dans les programmes qui doivent surveiller les E/S d'autres sources que le terminal, il existe deux options.

  1. Utilisez les fonctions décrites dans la page de manuel
     gl_io_mode(3) pour basculer
     gl_get_line() en mode serveur non bloquant. Dans ce mode,
     gl_get_line() devient une fonction d'édition de ligne
     non bloquante et incrémentale qui peut être appelée en toute
     sécurité depuis une boucle d'événements externe. Bien que ce
     soit une méthode très polyvalente, elle implique de prendre en
     charge certaines responsabilités qui sont normalement gérées
     en coulisses par gl_get_line().
  2. Pendant que gl_get_line() attend une entrée clavier de
     l'utilisateur, vous pouvez lui demander de surveiller également
     l'activité sur des descripteurs de fichiers arbitraires, tels que
     des sockets réseau, des pipes, etc., et de faire appel à des
     fonctions de votre choix lorsqu'une activité est détectée. Cela
     fonctionne sur tout système disposant de l'appel système
     select(), ce qui est la plupart, sinon la totalité, des
     flavors d'unix.

L'enregistrement d'un descripteur de fichier à surveiller par gl_get_line() implique d'appeler la fonction gl_watch_fd().

  int gl_watch_fd(GetLine *gl, int fd, GlFdEvent event,
                  GlFdEventFn *callback, void *data);

Si cela renvoie une valeur non nulle, cela signifie que soit vos arguments sont invalides, soit cette fonctionnalité n'est pas prise en charge sur le système hôte.

L'argument fd est le descripteur de fichier à surveiller. L'argument event spécifie le type d'activité qui suscite de l'intérêt, choisi parmi les valeurs énumérées suivantes :

  GLFD_READ   -  Surveiller l'arrivée de données à lire.
  GLFD_WRITE  -  Surveiller la capacité d'écrire sur le descripteur
                 de fichier sans bloquer.
  GLFD_URGENT -  Surveiller l'arrivée de données urgentes
                 hors bande sur le descripteur de fichier.

L'argument callback est la fonction à appeler lorsque l'activité sélectionnée est détectée. Elle doit être définie avec la macro suivante, qui est définie dans libtecla.h.

  #define GL_FD_EVENT_FN(fn) GlFdStatus (fn)(GetLine *gl, \
                                      void *data, int fd, \
                                      GlFdEvent event)

L'argument data de la fonction gl_watch_fd() est transmis à la fonction de rappel pour son propre usage, et peut pointer vers n'importe quoi, y compris NULL. Le descripteur de fichier et l'argument d'événement sont également transmis à la fonction de rappel, ce qui permet potentiellement à la même fonction de rappel d'être enregistrée pour plus d'un type d'événement et/ou plus d'un descripteur de fichier. La valeur de retour de la fonction de rappel doit être l'une des valeurs suivantes.

  GLFD_ABORT    -  Indiquer à gl_get_line() d'avorter. Lorsque cela
                   se produit, gl_get_line() renvoie
                   NULL, et un appel ultérieur à
                   gl_return_status() renverra
                   GLR_FDABORT. Notez que si l'application
                   a besoin que errno ait toujours une valeur
                   significative lorsque gl_get_line() renvoie
                   NULL, la fonction de rappel doit définir
                   errno de manière appropriée.
  GLFD_REFRESH  -  Redessiner la ligne d'entrée puis continuer
                   à attendre une entrée. Retournez ceci si
                   votre rappel a écrit sur le terminal.
  GLFD_CONTINUE -  Continuer à attendre une entrée, sans
                   redessiner la ligne.

Notez qu'avant d'appeler le rappel, gl_get_line() bloque la plupart des signaux et laisse ses propres gestionnaires de signaux installés, donc si vous avez besoin de capturer un signal particulier, vous devrez à la fois installer temporairement votre propre gestionnaire de signaux et débloquer le signal. Assurez-vous de rebloquer le signal (s'il était initialement bloqué) et de rétablir le gestionnaire de signaux d'origine, le cas échéant, avant de retourner.

Si la fonction de rappel doit lire ou écrire sur le terminal, elle devrait idéalement appeler d'abord gl_normal_io(gl) pour suspendre temporairement l'édition de ligne. Cela restaurera le terminal en mode canonique avec E/S bloquantes, et déplacera le curseur au début d'une nouvelle ligne de terminal. Plus tard, lorsque le rappel retournera, gl_get_line() remarquera que gl_normal_io() a été appelé, réaffichera la ligne d'entrée et reprendra l'édition. Notez que dans ce cas, les valeurs de retour, GLFD_REFRESH et GLFD_CONTINUE sont équivalentes.

Pour prendre en charge les cas où la fonction de rappel appelle une fonction tierce qui écrit occasionnellement et de manière imprévisible sur le terminal, la conversion automatique de "0 en "0 est réactivée avant que la fonction de rappel ne soit appelée. Si le rappel sait que la fonction tierce a écrit sur le terminal, elle devrait alors retourner la valeur de retour GLFD_REFRESH, pour indiquer à gl_get_line() de réafficher la ligne d'entrée.

Pour supprimer une fonction de rappel que vous avez précédemment enregistrée pour un descripteur de fichier et un événement donnés, appelez simplement gl_watch_fd() avec les mêmes descripteurs de fichier et arguments event, mais avec un argument callback de 0. L'argument data est ignoré dans ce cas.

DÉFINITION D'UN DÉLAI D'INACTIVITÉ

Sur les systèmes disposant de l'appel système select(), la fonction gl_inactivity_timeout() peut être utilisée pour définir ou annuler un délai d'inactivité. L'inactivité dans ce cas fait référence à la fois à l'entrée clavier et aux E/S sur tous les descripteurs de fichiers enregistrés par des appels précédents et ultérieurs à gl_watch_fd(). Sur les systèmes atypiques qui ne disposent pas de select(), cet appel n'a aucun effet.

  int gl_i
nactivity_timeout(GetLine *gl, GlTimeoutFn *callback, void *data, unsigned long sec, unsigned long nsec);

Le délai d'attente est spécifié sous la forme d'un nombre entier de secondes et d'un nombre entier de nanosecondes, via les arguments sec et nsec respectivement. Par la suite, chaque fois qu'aucune activité n'est constatée pendant cette période, la fonction spécifiée via l'argument callback est appelée. L'argument data de gl_inactivity_timeout() est passé tel quel à cette fonction de rappel chaque fois qu'elle est invoquée, et peut ainsi être utilisé pour passer des informations arbitraires spécifiques à l'application au rappel. La macro suivante est fournie dans libtecla.h pour que les applications l'utilisent afin de déclarer et prototyper les fonctions de rappel de délai d'attente.

  #define GL_TIMEOUT_FN(fn) \
               GlAfterTimeout (fn)(GetLine *gl, void *data)

Au retour, la fonction de rappel de l'application est censée retourner l'un des énumérateurs suivants pour indiquer à gl_get_line() comment procéder après que le délai d'attente a été géré par la fonction de rappel.

  GLTO_ABORT    -  Indiquer à gl_get_line() d'avorter. Lorsque
                   cela se produit, gl_get_line() retournera
                   NULL, et un appel ultérieur à
                   gl_return_status() retournera
                   GLR_TIMEOUT. Notez que si l'application
                   a besoin que errno ait toujours une valeur
                   significative lorsque gl_get_line() retourne
                   NULL, la fonction de rappel doit définir
                   errno de manière appropriée.
  GLTO_REFRESH  -  Redessiner la ligne de saisie, puis continuer
                   à attendre l'entrée. Vous devez retourner
                   cette valeur si votre fonction de rappel a écrit
                   dans le terminal sans avoir d'abord appelé
                   gl_normal_io(gl).
  GLTO_CONTINUE -  En mode d'E/S bloquant normal, continuer à
                   attendre l'entrée, sans redessiner la
                   ligne de saisie de l'utilisateur.
                   En mode d'E/S serveur non bloquant (voir
                   gl_io_mode(3)), faire en sorte que gl_get_line()
                   agisse comme si l'E/S était bloquée. Cela
                   signifie que gl_get_line() retournera
                   immédiatement NULL, et qu'un appel
                   ultérieur à gl_return_status()
                   retournera GLR_BLOCKED.

Notez qu'avant d'appeler la fonction de rappel, gl_get_line() bloque la plupart des signaux et laisse ses propres gestionnaires de signaux installés. Ainsi, si vous avez besoin d'intercepter un signal particulier, vous devrez à la fois installer temporairement votre propre gestionnaire de signaux et débloquer le signal. Assurez-vous de rebloquer le signal (s'il était initialement bloqué) et de rétablir le gestionnaire de signaux d'origine, le cas échéant, avant de retourner.

Si la fonction de rappel doit lire ou écrire dans le terminal, elle devrait idéalement appeler d'abord gl_normal_io(gl) pour suspendre temporairement l'édition de ligne. Cela restaurera le terminal en mode canonique, E/S bloquantes, et déplacera le curseur au début d'une nouvelle ligne de terminal. Plus tard, lorsque la fonction de rappel retournera, gl_get_line() remarquera que gl_normal_io() a été appelé, rediffusera la ligne de saisie et reprendra l'édition. Notez que dans ce cas, les valeurs de retour, GLTO_REFRESH et GLTO_CONTINUE, sont équivalentes.

Pour prendre en charge les cas où la fonction de rappel appelle une fonction tierce qui écrit occasionnellement et de manière imprévisible dans le terminal, la conversion automatique de "0 en "0 est réactivée avant l'appel de la fonction de rappel. Si la fonction de rappel sait que la fonction tierce a écrit dans le terminal, elle devrait alors retourner la valeur de retour GLTO_REFRESH, pour indiquer à gl_get_line() de rediffuser la ligne de saisie.

Notez que bien que l'argument de délai d'attente inclue une composante en nanosecondes, peu d'horloges d'ordinateur ont actuellement des résolutions inférieures à quelques millisecondes, donc demander moins de quelques millisecondes équivaut à demander zéro seconde sur de nombreux systèmes. Si cela pose problème, vous devriez baser votre choix de délai d'attente sur la résolution réelle de l'horloge hôte (par exemple, en appelant sysconf(_SC_CLK_TCK)).

Pour désactiver les délais d'attente, appelez simplement gl_inactivity_timeout() avec un argument callback de 0. L'argument data est ignoré dans ce cas.

PRISE EN CHARGE DES SIGNAUX PAR DÉFAUT

Par défaut, la fonction gl_get_line() intercepte un certain nombre de signaux. Ceci est particulièrement important pour les signaux qui, par défaut, termineraient le processus, car le terminal doit être restauré dans un état utilisable avant que cela ne se produise. Dans cette section, les signaux qui sont piégés par défaut, et la manière dont gl_get_line() y répond, sont décrits. La modification de ces valeurs par défaut fait l'objet de la section suivante.

Lorsque le sous-ensemble de signaux suivant est capturé, gl_get_line() restaure d'abord les paramètres du terminal et la gestion des signaux tels qu'ils étaient avant l'appel de gl_get_line(), renvoie le signal, pour permettre aux gestionnaires de signaux de l'application appelante de le gérer, puis si le processus existe toujours, gl_get_line() retourne NULL et définit errno comme spécifié ci-dessous.

 SIGINT  -  Ce signal est généré à la fois par la touche
            d'interruption du clavier (généralement ^C) et
            par la touche d'interruption (break) du
            clavier.
            errno=EINTR
 SIGHUP  -  Ce signal est généré lorsque le terminal de
            contrôle se termine.
            errno=ENOTTY
 SIGPIPE -  Ce signal est généré lorsqu'un programme tente
            d'écrire dans un tuyau dont l'extrémité distante
            n'est lue par aucun processus. Cela peut se
            produire par exemple si vous avez appelé
            gl_change_terminal() pour rediriger la
            sortie vers un tuyau caché sous un pseudo-terminal.
            errno=EPIPE
 SIGQUIT -  Ce signal est généré par la touche d'abandon
            du clavier (généralement ^\).
            errno=EINTR
 SIGABRT -  Ce signal est généré par la fonction standard
            C, abort(). Par défaut, il termine le processus
            et génère un core dump.
            errno=EINTR
 SIGTERM -  C'est le signal par défaut que la commande UN*X
            kill envoie aux processus.
            errno=EINTR

Notez que dans le cas de tous les signaux ci-dessus, POSIX impose que par défaut le processus soit terminé, avec l'ajout d'un core dump dans le cas du signal SIGQUIT. En d'autres termes, si l'application appelante ne remplace pas le gestionnaire par défaut en fournissant son propre gestionnaire de signaux, la réception du signal correspondant terminera l'application avant que gl_get_line() ne retourne.

Si gl_get_line() avorte avec errno défini sur EINTR, vous pouvez savoir quel signal l'a fait avorter en appelant la fonction suivante.

  int gl_last_signal(const GetLine *gl);

Ceci retourne le code numérique (par exemple, SIGINT) du dernier signal reçu lors du dernier appel à gl_get_line(), ou -1 si aucun signal n'a été reçu.

Sur les systèmes qui le supportent, lorsqu'un signal SIGWINCH (changement de fenêtre) est reçu, gl_get_line() interroge le terminal pour connaître sa nouvelle taille, redessine la ligne de saisie actuelle pour s'adapter à la nouvelle taille, puis retourne à l'attente de l'entrée clavier de l'utilisateur. Contrairement aux autres signaux, ce signal n'est pas renvoyé à l'application.

Enfin, les signaux suivants amènent gl_get_line() à d'abord restaurer le terminal et l'environnement de signal à ce qui prévalait avant l'appel de gl_get_line(), puis à renvoyer le signal à l'application. Si le processus existe toujours après la livraison du signal, alors gl_get_line() rétablit ses propres gestionnaires de signaux, remet le terminal en mode brut, rediffuse la ligne de saisie et recommence à attendre l'entrée terminale de l'utilisateur.

 SIGCONT    -  Ce signal est généré lorsqu'un processus suspendu
               est repris.
 SIGPOLL    -  Sur les systèmes SVR4, ce signal notifie le
               processus d'un événement d'E/S asynchrone. Notez
               que sous 4.3+BSD, SIGIO et SIGPOLL sont les
               mêmes. Sur d'autres systèmes, SIGIO est ignoré
               par défaut, donc gl_get_line() ne le piège
               pas par défaut.
 SIGPWR     -  Ce signal est généré lorsqu'une panne de courant
               se produit (probablement lorsque le système est
               sur un UPS).
 SIGALRM    -  Ce signal est généré lorsqu'un minuteur
               expire.
 SIGUSR1    -  Un signal spécifique à l'application.
 SIGUSR2    -  Un autre signal spécifique à l'application.
 SIGVTALRM  -  Ce signal est généré lorsqu'un minuteur
               virtuel expire (voir man setitimer(2)).
 SIGXCPU    -  Ce signal est généré lorsqu'un processus
               dépasse sa limite de temps CPU souple.
 SIGXFSZ    -  Ce signal est généré lorsqu'un processus
               dépasse sa limite de taille de fichier souple.
 SIGTSTP    -  Ce signal est généré par la touche de suspension
               du terminal, qui est généralement ^Z, ou la
               touche de suspension de terminal retardée, qui
               est généralement ^Y.
 SIGTTIN    -  Ce signal est généré si le programme tente
               de lire depuis le terminal pendant que le
               programme s'exécute en arrière-plan.
 SIGTTOU    -  Ce signal est généré si le programme tente
               d'écrire dans le terminal pendant que le
               programme s'exécute en arrière-plan.

Évidemment, tous les signaux ci-dessus ne sont pas pris en charge sur tous les systèmes, de sorte que le code pour les prendre en charge est compilé conditionnellement dans la bibliothèque tecla.

Notez que si SIGKILL ou SIGPOLL, qui par définition ne peuvent pas être capturés, ou l'un des signaux d'exception générés par le matériel, tels que SIGSEGV, SIGBUS et SIGFPE, sont reçus et non gérés pendant que gl_get_line() a le terminal en mode brut, le programme sera terminé sans que le terminal n'ait été restauré dans un état utilisable. En pratique, les shells de contrôle de tâches réinitialisent généralement les paramètres du terminal lorsqu'un processus abandonne le terminal de contrôle, ce qui ne pose donc problème qu'avec les anciens shells.

PRISE EN CHARGE PERSONNALISÉE DES SIGNAUX

La section précédente a listé les signaux que gl_get_line() intercepte par défaut, et a décrit comment il y répond. Cette section décrit comment ajouter et supprimer des signaux de la liste des signaux piégés, et comment spécifier comment gl_get_line() doit répondre à un signal donné.

Si vous n'avez pas besoin que gl_get_line() fasse quoi que ce soit en réponse à un signal qu'il intercepte normalement, vous pouvez lui demander d'ignorer ce signal en appelant gl_ignore_signal().

  int gl_ignore_signal(GetLine *gl, int signo);

L'argument signo est le numéro du signal (par exemple, SIGINT) que vous souhaitez ignorer. Si le signal spécifié ne fait pas partie de ceux actuellement piégés, cette fonction ne fait rien.

La fonction gl_trap_signal() vous permet soit d'ajouter un nouveau signal à la liste que gl_get_line() intercepte, soit de modifier la manière dont il réagit

onds à un signal qu'il intercepte déjà.

  int gl_trap_signal(GetLine *gl, int signo, unsigned flags,
                     GlAfterSignal after, int errno_value);

L'argument signo est le numéro du signal que vous souhaitez intercepter. L'argument flags est un ensemble de drapeaux qui déterminent l'environnement dans lequel le gestionnaire de signaux de l'application est appelé, l'argument after indique à gl_get_line() ce qu'il faut faire après le retour du gestionnaire de signaux de l'application, et errno_value indique à gl_get_line() ce qu'il faut définir pour errno s'il doit être avorté.

L'argument flags est un OU bit à bit de zéro ou plus des énumérateurs suivants :

  GLS_RESTORE_SIG  - Restaurer l'environnement de signal
                      de l'appelant lors du traitement du
                      signal.
  GLS_RESTORE_TTY  - Restaurer les paramètres du terminal de
                      l'appelant lors du traitement du
                      signal.
  GLS_RESTORE_LINE - Déplacer le curseur au début de la ligne
                      qui suit la ligne d'entrée avant d'appeler
                      le gestionnaire de signaux de
                      l'application.
  GLS_REDRAW_LINE  - Redessiner la ligne d'entrée lorsque le
                      gestionnaire de signaux de
                      l'application retourne.
  GLS_UNBLOCK_SIG  - Normalement, si le programme appelant a
                      un signal bloqué (man sigprocmask),
                      gl_get_line() n'intercepte pas ce
                      signal. Ce drapeau indique à
                      gl_get_line() d'intercepter le signal
                      et de le débloquer pendant la durée de
                      l'appel à gl_get_line().
  GLS_DONT_FORWARD - Si ce drapeau est inclus, le signal ne
                      sera pas transmis au gestionnaire de
                      signaux du programme appelant.

Deux combinaisons de drapeaux couramment utiles sont également énumérées comme suit :

  GLS_RESTORE_ENV   = GLS_RESTORE_SIG | GLS_RESTORE_TTY |
                      GLS_REDRAW_LINE
  GLS_SUSPEND_INPUT = GLS_RESTORE_ENV | GLS_RESTORE_LINE

Si votre gestionnaire de signaux, ou le gestionnaire de signaux par défaut du système pour ce signal, si vous ne l'avez pas remplacé, n'écrit jamais sur le terminal, ni ne suspend ou ne termine le programme appelant, alors vous pouvez définir l'argument flags sur 0 en toute sécurité.

Si votre gestionnaire de signaux écrit toujours sur le terminal, en lit, ou suspend ou termine le programme, vous devriez spécifier l'argument flags comme GL_SUSPEND_INPUT, afin que :

1. Le curseur ne soit pas laissé au milieu de la ligne
   d'entrée.
2. L'utilisateur puisse taper des entrées et qu'elles soient
   affichées.
3. Vous n'ayez pas besoin de terminer chaque ligne de sortie
   avec \r\n, au lieu de seulement \n.

La combinaison GL_RESTORE_ENV est identique à GL_SUSPEND_INPUT, à l'exception qu'elle ne déplace pas le curseur, et si votre gestionnaire de signaux ne lit ni n'écrit rien sur le terminal, l'utilisateur ne verra aucune indication visible qu'un signal a été attrapé. Cela peut être utile si vous avez un gestionnaire de signaux qui écrit occasionnellement sur le terminal, où l'utilisation de GL_SUSPEND_LINE provoquerait la duplication inutile de la ligne d'entrée lorsqu'aucun texte n'a été écrit sur le terminal. Un tel gestionnaire de signaux, lorsqu'il écrit sur le terminal, doit s'assurer de commencer une nouvelle ligne au début de sa première écriture, en écrivant une nouvelle ligne avant de retourner. Si le signal arrive pendant que l'utilisateur saisit une ligne qui n'occupe qu'une ligne de terminal, ou si le curseur se trouve sur la dernière ligne de terminal d'une ligne d'entrée plus longue, cela aura le même effet que GL_SUSPEND_INPUT. Sinon, il commencera à écrire sur une ligne qui contient déjà une partie de la ligne d'entrée affichée. Cela ne pose aucun problème, mais cela semble un peu disgracieux, c'est pourquoi la combinaison GL_SUSPEND_INPUT est meilleure si vous savez que vous allez toujours écrire sur le terminal.

L'argument after, qui détermine ce que gl_get_line() fait après le retour du gestionnaire de signaux de l'application (s'il retourne), peut prendre l'une des valeurs suivantes :

  GLS_RETURN   - Retourner la ligne d'entrée complétée, comme
                 si l'utilisateur avait appuyé sur la touche
                 entrée.
  GLS_ABORT    - Provoquer l'abandon de gl_get_line().
                 Lorsque cela se produit, gl_get_line()
                 retourne NULL, et un appel ultérieur à
                 gl_return_status() retournera
                 GLR_SIGNAL. Notez que si
                 l'application a besoin que errno ait
                 toujours une valeur significative lorsque
                 gl_get_line() retourne NULL, la
                 fonction de rappel devrait définir
                 errno de manière appropriée.
  GLS_CONTINUE - Reprendre l'édition de la ligne de commande.

L'argument errno_value est destiné à être combiné avec l'option GLS_ABORT, indiquant à gl_get_line() quelle valeur définir pour la variable standard errno avant de retourner NULL au programme appelant. Il peut cependant également être utilisé avec l'option GL_RETURN, au cas où vous souhaiteriez avoir un moyen de distinguer entre une ligne d'entrée qui a été entrée en utilisant la touche retour, et une qui a été entrée suite à la réception d'un signal.

GESTION FIABLE DES SIGNALS

La gestion des signaux est étonnamment difficile à réaliser de manière fiable sans conditions de concurrence. Dans gl_get_line(), beaucoup de précautions ont été prises pour permettre aux applications d'effectuer une gestion fiable des signaux autour de gl_get_line(). Cette section explique comment en tirer parti.

Comme exemple des problèmes qui peuvent survenir si l'application n'est pas écrite correctement, imaginez qu'une application ait un gestionnaire de signaux SIGINT qui définit un drapeau global. Supposons maintenant que l'application teste ce drapeau juste avant d'appeler gl_get_line(). Si un signal SIGINT est reçu dans la petite fenêtre de temps entre l'instruction qui teste la valeur de ce drapeau et l'instruction qui appelle gl_get_line(), alors gl_get_line() ne verra pas le signal et ne sera pas interrompu. Par conséquent, l'application ne pourra pas répondre au signal tant que l'utilisateur n'aura pas terminé la saisie de la ligne d'entrée et que gl_get_line() ne sera pas retourné. Selon l'application, cela peut être un désastre ou non, mais au moins cela dérouterait l'utilisateur.

La façon d'éviter de tels problèmes est de faire ce qui suit.

1. Si nécessaire, utilisez la fonction gl_trap_signal() pour configurer gl_get_line() afin qu'il s'arrête lorsque des signaux importants sont attrapés.

2. Configurez gl_get_line() de telle sorte que si l'un des signaux qu'il attrape est bloqué lorsque gl_get_line() est appelé, ils soient automatiquement débloqués pendant les périodes où gl_get_line() attend des E/S. Cela peut être fait soit sur une base par signal, en appelant la fonction gl_trap_signal() et en spécifiant l'attribut GLS_UNBLOCK du signal, soit globalement en appelant la fonction gl_catch_blocked().

     void gl_catch_blocked(GetLine *gl);

Cette fonction ajoute simplement l'attribut GLS_UNBLOCK à tous les signaux qu'elle est actuellement configurée pour intercepter.

3. Juste avant d'appeler gl_get_line(), bloquez la livraison de tous les signaux que gl_get_line() est configuré pour intercepter. Cela peut être fait en utilisant la fonction POSIX sigprocmask() en conjonction avec la fonction gl_list_signals().

      int gl_list_signals(GetLine *gl, sigset_t *set);

Cette fonction retourne l'ensemble des signaux qu'elle est actuellement configurée pour attraper dans l'argument set, qui est dans le format requis par sigprocmask().

4. Dans l'exemple, on testerait maintenant le drapeau global que le gestionnaire de signaux définit, sachant qu'il n'y a plus aucun danger que ce drapeau soit défini à nouveau jusqu'à ce que gl_get_line() débloque ses signaux lors des E/S.

5. Finalement, gl_get_line() retourne, soit parce qu'un signal a été attrapé, qu'une erreur s'est produite, soit que l'utilisateur a terminé la saisie de sa ligne d'entrée.

6. Maintenant, on vérifierait à nouveau le drapeau de signal global, et s'il est défini, on y répondrait et on le mettrait à zéro.

7. Utiliser sigprocmask() pour débloquer les signaux qui ont été bloqués à l'étape 3.

La même technique peut être utilisée autour de certaines fonctions POSIX sensibles aux signaux, telles que sigsetjmp() et sigsuspend(), et en particulier, la première de ces deux fonctions peut être utilisée en conjonction avec siglongjmp() pour implémenter une gestion des signaux sans conditions de concurrence autour d'autres appels système de longue durée. La manière de faire cela est expliquée ensuite, en montrant comment gl_get_line() parvient à intercepter de manière fiable les signaux autour des appels à des fonctions telles que read() et select() sans conditions de concurrence.

La première chose que fait gl_get_line(), chaque fois qu'il est appelé, est d'utiliser la fonction POSIX sigprocmask() pour bloquer la livraison de tous les signaux qu'il est actuellement configuré pour intercepter. Ceci est redondant si l'application les a déjà bloqués, mais cela ne fait aucun mal. Il annule cette étape juste avant de retourner.

Chaque fois que gl_get_line() doit appeler read() ou select() pour attendre une entrée de l'utilisateur, il appelle d'abord la fonction POSIX sigsetjmp(), en veillant à spécifier une valeur non nulle pour son argument savesigs. La raison de ce dernier argument deviendra claire sous peu.

Si sigsetjmp() retourne zéro, gl_get_line() fait alors ce qui suit.

a. Il utilise la fonction POSIX sigaction() pour enregistrer
   un gestionnaire de signaux temporaire pour tous les signaux
   qu'il est configuré pour intercepter. Ce gestionnaire de
   signaux fait deux choses.
   1. Il enregistre le numéro du signal reçu dans une variable
      au niveau du fichier.
   2. Il appelle ensuite la fonction POSIX siglongjmp()
      en utilisant le tampon passé à sigsetjmp() pour
      son premier argument, et une valeur non nulle pour son
      second argument.
   Lorsque ce gestionnaire de signaux est enregistré, le membre
   sa_mask de l'argument struct sigaction act de
   l'appel à sigaction() est configuré pour contenir tous
   les signaux que gl_get_line() intercepte. Cela garantit
   que seul un signal sera attrapé à la fois par notre
   gestionnaire de signaux, ce qui garantit que plusieurs
   instances de notre gestionnaire de signaux ne se gênent pas
   mutuellement.
b. Maintenant que le gestionnaire de signaux a été mis en place,
   gl_get_line() débloque tous les signaux qu'il est
   configuré pour intercepter.
c. Il appelle ensuite les appels système read() ou
   select() pour attendre une entrée du clavier.
d. Si cet appel système retourne (c'est-à-dire qu'aucun signal
   n'est reçu), gl_get_line() rebloque la livraison des
   signaux d'intérêt.
e. Il rétablit ensuite les gestionnaires de signaux qui ont
   été déplacés par celui qui vient d'être installé.

Alternativement, si sigsetjmp() retourne une valeur non nulle, cela signifie que

l'un des signaux piégés a été capturé pendant l'exécution des étapes ci-dessus. Lorsque cela se produit, gl_get_line() fait ce qui

suit.

Tout d'abord, notez que lorsqu'un appel à siglongjmp() provoque le retour de sigsetjmp(), à condition que l'argument savesigs de sigsetjmp() ait été non nul, comme spécifié ci-dessus, le masque de traitement des signaux est restauré à l'état dans lequel il se trouvait lorsque sigsetjmp() a été appelé. C'est la différence importante entre sigsetjmp() et l'ancien setjmp() problématique, et c'est l'ingrédient essentiel qui rend possible l'évitement des conditions de course dans la gestion des signaux. Grâce à cela, nous sommes garantis que tous les signaux que nous avons bloqués avant d'appeler sigsetjmp() sont de nouveau bloqués dès qu'un signal est capturé. Les instructions suivantes, qui sont alors exécutées, sont donc garanties de s'exécuter sans qu'aucun autre signal ne soit

capturé.

1. Si tel est l'instruction donné par les attributs de configuration de gl_get_line()
du signal qui a été capturé,
gl_get_line() restaure les attributs du terminal à
l'état dans lequel ils se trouvaient lorsque gl_get_line() a été
appelé. C'est particulièrement important pour les signaux qui
suspendent ou terminent le processus, car sinon le
terminal serait laissé dans un état

inutilisable.

2. Il réinstalle ensuite les gestionnaires de signaux de

l'application.

3. Il utilise ensuite la fonction raise()
de la bibliothèque standard C pour renvoyer à l'application le signal qui
a été

capturé.

3. Ensuite, il débloque la livraison du signal que nous venons de
envoyer. Cela a pour résultat que le signal qui vient d'être envoyé
via raise(), est capturé par le gestionnaire de signal
original de l'application, qui peut maintenant le traiter comme il
le juge

approprié.

4. Si le gestionnaire de signal retourne (c'est-à-dire qu'il ne termine pas
le processus), gl_get_line() bloque de nouveau la livraison du
signal

ci-dessus.

5. Il annule ensuite toute action effectuée dans la première des
étapes ci-dessus, et réaffiche la ligne, si la configuration du signal
l'exige

.

6. gl_get_line() reprend alors la tentative de
lecture d'un caractère, ou interrompt, en fonction de la
configuration du signal qui a été

capturé.

Ce que font essentiellement les étapes ci-dessus, c'est prendre des signaux délivrés de manière asynchrone et les traiter de manière synchrone, un à la fois, à un point du code où gl_get_line() a un contrôle com

plet sur son
environnement.

LA TAILLE DU

TERMINAL

Sur la plupart des systèmes, la combinaison de l'ioctl TIOCGWINSZ et du signal SIGWINCH est utilisée pour maintenir une idée précise de la taille du terminal. La taille du terminal est à nouveau interrogée à chaque fois que gl_get_line() est appelé et chaque fois qu'un signal SIGWINCH est

reçu.

Sur les quelques systèmes où ce mécanisme n'est pas disponible, au démarrage new_GetLine() cherche d'abord les variables d'environnement LINES et COLUMNS. Si celles-ci ne sont pas trouvées, ou si elles contiennent des valeurs inutilisables, alors si une base de données d'informations sur le terminal comme terminfo ou termcap est disponible, la taille par défaut du terminal est recherchée dans cette base de données. Si cela échoue également à fournir la taille du terminal, une taille par défaut de 80 colonnes par 24 lignes est

utilisée.

Même sur les systèmes qui prennent en charge ioctl(TIOCGWINSZ), si le terminal est à l'autre bout d'une ligne série, le pilote de terminal n'a généralement aucun moyen de détecter quand un redimensionnement se produit ou d'interroger quelle est la taille actuelle. Dans de tels cas, aucun SIGWINCH n'est envoyé au processus, et les dimensions retournées par ioctl(TIOCGWINSZ) ne sont pas correctes. La seule façon de gérer de tels cas est de fournir un moyen à l'utilisateur d'entrer une commande qui indique au système distant quelle est la nouvelle taille. Cette commande appellerait alors la fonction gl_set_term_size() pour informer gl_get_line() du changement de

taille. 
  int gl_set_term_size(GetLine *gl, int ncolumn, int nline)
;

Les arguments ncolumn et nline sont utilisés pour spécifier les nouvelles dimensions du terminal, et ne doivent pas être inférieurs à 1. Sur les systèmes qui prennent en charge ioctl(TIOCGWINSZ), cette fonction appelle d'abord ioctl(TIOCSWINSZ) pour informer le pilote du terminal du changement de taille. En mode E/S serveur non bloquant, si une ligne est actuellement en cours de saisie, la ligne saisie est alors redessinée pour s'adapter à la taille modifiée. Enfin, les nouvelles valeurs sont enregistrées dans gl pour une utilisation future par gl_get_li

ne().

La fonction gl_terminal_size() vous permet d'interroger la taille actuelle du terminal, et d'installer une taille de secours alternative pour les cas où la taille n'est pas disponible. Attention, la taille du terminal ne sera pas disponible lors de la lecture depuis un tube ou un fichier, donc les valeurs par défaut peuvent être importantes même sur les systèmes qui prennent en charge des moyens de découvrir la taille du

terminal. 
  typedef struct {
    int nline;        /* Le terminal a nline lignes */
    int ncolumn;      /* Le terminal a ncolumn colonnes */
  } GlTerminalSize;
  GlTerminalSize gl_terminal_size(GetLine *gl,
                                  int def_ncolumn,
                                  int def_nline)
;

Cette fonction met d'abord à jour les dimensions de secours du terminal de gl_get_line(), puis enregistre ses résultats dans la valeur de

retour.

Les arguments def_ncolumn et def_nline spécifient le nombre par défaut de colonnes et de lignes du terminal à utiliser si la taille du terminal ne peut pas être déterminée via ioctl(TIOCGWINSZ) ou les variables

d'environnement
.

CACHER CE QUE VOUS

TAPEZ

Lors de la saisie d'informations sensibles, telles que des mots de passe, il est préférable de ne pas avoir le texte que vous saisissez affiché en écho sur le terminal. De plus, un tel texte ne devrait pas être enregistré dans la liste d'historique, car quelqu'un trouvant votre terminal sans surveillance pourrait alors le rappeler, ou quelqu'un fouillant dans vos répertoires pourrait le voir dans votre fichier d'historique. En gardant cela à l'esprit, la fonction gl_echo_mode() vous permet d'activer et de désactiver l'affichage et l'archivage de tout texte qui est saisi par la suite dans les appels à gl_get_li

ne(). 
  int gl_echo_mode(GetLine *gl, int enable)
;

L' argument enable spécifie si le texte saisi doit être visible ou non. S'il est 0, alors les lignes saisies par la suite ne seront pas visibles sur le terminal, et ne seront pas enregistrées dans la liste d'historique. S'il est 1, alors les lignes saisies par la suite seront affichées au fur et à mesure de leur saisie, et à condition que l'historique n'ait pas été désactivé via un appel à gl_toggle_history(), elles seront également archivées dans la liste d'historique. Enfin, si l' argument enable est -1, alors le mode d'écho est laissé inchangé, ce qui vous permet d'interroger le paramètre actuel de manière non destructive via la valeur de retour. Dans tous les cas, la valeur de retour de la fonction est 0 si l'écho était désactivé avant l'appel de la fonction, et 1 s'il était

activé.

Lorsque l'écho est désactivé, notez que bien que la complétion

par tabulation complétera invisiblement votre préfixe autant q
ue possible, les complétions ambiguës ne seront pas affichées.

REQUÊTES À CARACTÈRE

UNIQUE

Utiliser gl_get_line() pour demander à l'utilisateur une réponse d'un seul caractère est incommode pour l'utilisateur, car il doit appuyer sur la touche entrée ou retour avant que le caractère qu'il a tapé soit renvoyé au programme. C'est pourquoi la fonction gl_query_char() a été fournie pour des requêtes à caractère unique comme

celle-ci. 
  int gl_query_char(GetLine *gl, const char *prompt,
                    char defchar)
;

Cette fonction affiche l'invite spécifiée au début d'une nouvelle ligne, et attend que l'utilisateur tape un caractère. Lorsque l'utilisateur tape un caractère, gl_query_char() l'affiche à droite de l'invite, commence une nouvelle ligne, puis renvoie le caractère au programme appelant. La valeur de retour de la fonction est le caractère qui a été tapé. Si la lecture a dû être interrompue pour une raison quelconque, EOF est renvoyé à la place. Dans ce dernier cas, l'application peut appeler la fonction gl_return_status() précédemment documentée, pour savoir ce qui s'est mal passé. Cela aurait pu être, par exemple, la réception d'un signal, ou le déclenchement du minuteur d'inactivité

optionnel.

Si l'utilisateur appuie simplement sur entrée, la valeur de l' argument defchar est substituée. Cela signifie que lorsque l'utilisateur appuie sur nouvelle ligne ou retour, le caractère spécifié dans defchar est affiché après l'invite, comme si l'utilisateur l'avait tapé, ainsi que renvoyé à l'application appelante. Si un tel remplacement n'est pas important, passez simplement '0 comme valeur de defchar

.

Si le caractère saisi est un caractère non imprimable, il est affiché symboliquement. Par exemple, contrôle-A est affiché comme ^A, et les caractères au-delà de 127 sont affichés en octal, précédés d'une barre oblique

inverse.

Comme avec gl_get_line(), l'écho du caractère saisi peut être désactivé en utilisant la fonction gl_echo_mode()

.

Si le processus appelant est suspendu pendant qu'il attend que l'utilisateur tape sa réponse, le curseur est déplacé à la ligne suivant la ligne d'invite, puis lorsque le processus reprend, l'invite est réaffichée, et gl_query_char() reprend l'attente que l'utilisateur tape un

caractère.

Notez qu'en mode serveur non bloquant, (voir gl_io_mode(3)), si une ligne de saisie incomplète est en cours de lecture lorsque gl_query_char() est appelé, la ligne de saisie partielle est abandonnée, et effacée du terminal, avant que la nouvelle invite ne soit affichée. Le prochain appel à gl_get_line() commencera donc

à éditer une n
ouvelle ligne.

LIRE DES CARACTÈRES

BRUTS

Alors que la fonction gl_query_char() demande visiblement à l'utilisateur un caractère, et affiche ce qu'il a tapé, la fonction gl_read_char() lit un caractère brut de l'utilisateur, sans rien écrire sur le terminal, ni perturber une ligne de saisie incomplète. Cela signifie qu'elle peut être appelée non seulement entre les appels à gl_get_line(), mais aussi depuis des fonctions de rappel que l'application a enregistrées pour être appelées par gl_get_li

ne(). 
  int gl_read_char(GetLine *gl)
;

En cas de succès, la valeur de retour de gl_read_char() est le caractère qui a été lu. En cas d'échec, EOF est renvoyé, et la fonction gl_return_status() peut être appelée pour savoir ce qui s'est mal passé. Les possibilités incluent le déclenchement du minuteur d'inactivité optionnel, la réception d'un signal configuré pour interrompre gl_get_line(), ou le blocage des E/S du terminal, en mode E/S serveur non

bloquant.

Attention, certaines touches du clavier, telles que les touches de fonction et les touches de curseur, génèrent généralement au moins 3 caractères chacune, donc un seul appel à gl_read_char() ne'ne suffira pas pour identifier de telles frappes au clavier.

EFFACER LE TERMINAL

Le programme appelant peut effacer le terminal en appelant gl_erase_terminal(). En mode serveur I/O non bloquant, cette fonction prépare également la ligne d'entrée actuelle à être redessinée à partir de zéro lors du prochain appel à gl_get_line().

  int gl_erase_terminal(GetLine *gl);

AFFICHER DU TEXTE DYNAMIQUEMENT

Entre deux appels à gl_get_line(), la fonction gl_display_text() offre un moyen pratique d'afficher des paragraphes de texte, justifiés à gauche et répartis sur une ou plusieurs lignes de terminal selon les contraintes de la largeur actuelle du terminal. Des exemples d'utilisation de cette fonction se trouvent dans les programmes de démonstration, où elle est utilisée pour afficher des introductions. Dans ces exemples, l'utilisation avancée de préfixes, suffixes et lignes de remplissage optionnels pour dessiner une boîte autour du texte est également illustrée.

  int gl_display_text(GetLine *gl, int indentation,
                      const char *prefix,
                      const char *suffix, int fill_char,
                      int def_width, int start,
                      const char *string);

Si gl n'est pas actuellement connecté à un terminal, par exemple si la sortie d'un programme utilisant gl_get_line() est dirigée vers un autre programme ou redirigée vers un fichier, alors la valeur du paramètre def_width est utilisée comme largeur du terminal.

L'argument indentation spécifie le nombre de caractères à utiliser pour indenter chaque ligne de sortie. L'argument fill_char spécifie le caractère qui sera utilisé pour effectuer cette indentation.

L'argument prefix peut être soit NULL, soit une chaîne à placer au début de chaque nouvelle ligne (après toute indentation). De même, l'argument suffix peut être soit NULL, soit une chaîne à placer à la fin de chaque ligne. Le suffixe est placé à l'extrême droite du terminal, et tout espace entre son premier caractère et le dernier mot de cette ligne est rempli avec le caractère spécifié via l'argument fill_char. Normalement, le caractère de remplissage est un espace.

L'argument start indique à gl_display_text() combien de caractères ont déjà été écrits sur la ligne de terminal actuelle, et indique donc l'indice de colonne de départ du curseur. Comme la valeur de retour de gl_display_text() est l'indice de colonne de fin du curseur, en passant la valeur de retour d'un appel à l'argument start de l'appel suivant, un paragraphe réparti sur plusieurs chaînes peut être composé en appelant gl_display_text() pour chaque portion successive du paragraphe. Notez que des caractères de nouvelle ligne littéraux sont nécessaires à la fin de chaque paragraphe pour forcer le démarrage d'une nouvelle ligne.

En cas d'erreur, gl_display_text() renvoie -1.

FONCTIONNALITES DE FONCTION DE RAPPEL

Sauf indication contraire, les fonctions de rappel, telles que les fonctions de rappel de complétion par tabulation et les fonctions de rappel d'événements, ne doivent appeler aucune fonction de ce module. Les fonctions suivantes, cependant, sont conçues spécifiquement pour être utilisées par des fonctions de rappel.

Appeler la fonction gl_replace_prompt() à partir d'une fonction de rappel indique à gl_get_line() d'afficher une invite différente lorsque la fonction de rappel retourne. Sauf en mode serveur non bloquant, elle n'a aucun effet si elle est utilisée entre deux appels à gl_get_line(). En mode serveur non bloquant (voir la page de manuel gl_io_mode(3), lorsqu'elle est utilisée entre deux appels à gl_get_line() qui opèrent sur la même ligne d'entrée, la ligne d'entrée actuelle sera redessinée avec la nouvelle invite lors du prochain appel à gl_get_line().

  void gl_replace_prompt(GetLine *gl, const char *prompt);

JEUX DE CARACTERES INTERNATIONAUX

Depuis la version 1.4.0 de libtecla, gl_get_line() est propre aux 8 bits. Cela signifie que tous les caractères 8 bits imprimables dans la locale actuelle de l'utilisateur sont maintenant affichés tels quels et inclus dans la ligne d'entrée retournée. En supposant que le programme appelant contient correctement un appel comme suit,

  setlocale(LC_CTYPE, "");

alors la locale actuelle est déterminée par la première des variables d'environnement LC_CTYPE, LC_ALL, et LANG, qui est trouvée contenir un nom de locale valide. Si aucune de ces variables n'est définie, ou si le programme néglige d'appeler setlocale, alors la locale par défaut C est utilisée, qui est le ASCII 7 bits US. Sur la plupart des plateformes de type Unix, vous pouvez obtenir une liste des locales valides en tapant la commande :

  locale -a

à l'invite du shell. Une documentation supplémentaire sur la façon dont l'utilisateur peut utiliser cela pour saisir des caractères internationaux se trouve dans la page de manuel tecla(7).

SECURITE DES THREADS

Dans un programme multi-threadé, vous devriez utiliser la version libtecla_r.a de la bibliothèque. Celle-ci utilise des versions réentrantes des fonctions système, lorsque disponibles. Malheureusement, ni terminfo ni termcap n'ont été conçus pour être réentrantes, vous ne pouvez donc pas utiliser en toute sécurité les fonctions du module getline dans plusieurs threads (vous pouvez utiliser les modules séparés d'expansion de fichiers et de complétion de mots dans plusieurs threads, voir les pages de manuel correspondantes pour plus de détails). Cependant, en raison de l'utilisation de fonctions réentrantes POSIX pour la recherche de répertoires personnels, etc., il est sûr d'utiliser ce module à partir d'un seul thread d'un programme multi-threadé, à condition que vos autres threads n'utilisent aucune fonction termcap ou terminfo.
