DESCRIPTIO

N

La fonction gl_get_line() fait partie de la bibliothèque tecla (voir la page man libtecla(3)). Si l'utilisateur tape sur un terminal, chaque appel lui demande une ligne de saisie, puis fournit des fonctionnalités d'édition interactives, similaires à celles du shell unix tcsh. En plus de l'édition simple de ligne de commande, elle prend en charge le rappel des lignes de commande précédemment saisies, l'achèvement par TAB des noms de fichiers et l'expansion en ligne des caractères génériques des noms de fichiers. La documentation des fonctionnalités d'édition de ligne de commande au niveau utilisateur et de toutes les options de configuration utilisateur se trouve dans la page man tecla(7). Cette page man concerne la documentation destinée aux pro

grammeurs souhaitant utiliser cette
bibliothèque dans leur application.

UN

EXEMPLE

L'exemple suivant montre un exemple complet d'utilisation de la fonction gl_get_line() pour obtenir une saisie de l'utilisateur

: 
  #include <stdio.h>
  #include <locale.h>
  #include <libtecla.h>
  int main(int argc, char *argv[])
  { 
    char *line;    /* La ligne que l'utilisateur a tapée */
    GetLine *gl;   /* L'objet ressource gl_get_line() */
    setlocale(LC_CTYPE, ""); /* Adopter le choix de l'utilisateur */
                             /* concernant le jeu de caractères. */
    gl = new_GetLine(1024, 2048);
    if(!gl)
      return 1;
    while((line=gl_get_line(gl, "$ ", NULL, -1)) != NULL &&
           strcmp(line, "exit\n") != 0)
      printf("Vous avez tapé : %s\n", line);
    gl = del_GetLine(gl);
    return 0;
}

Dans l'exemple, d'abord les ressources nécessaires par la fonction gl_get_line() sont créées en appelant new_GetLine(). Cela alloue la mémoire utilisée lors des appels ultérieurs à la fonction gl_get_line(), y compris le tampon d'historique pour enregistrer les lignes précédemment saisies. Ensuite, une ou plusieurs lignes sont lues auprès de l'utilisateur, jusqu'à ce qu'une erreur survienne ou que l'utilisateur tape exit. Enfin, les ressources qui ont été allouées par new_GetLine() sont rendues au système en appelant del_GetLine(). Notez l'utilisation de la valeur de retour NULL de del_GetLine() pour rendre gl NULL. C'est une précaution de sécurité. Si le programme essaie ensuite de passer gl à gl_get_line(), ladite fonction se plaindra et renverra une erreu

r, au lieu d'essayer d'util
iser l'objet ressource supprimé.

LES FONCTIONS UTILISÉES DANS

L'EXEMPLE

Les descriptions des fonctions utilisées dans l'exemple sont les suivantes

: 
  GetLine *new_GetLine(size_t linelen, size_t
histlen)

Cette fonction crée les ressources utilisées par la fonction gl_get_line() et renvoie un pointeur opaque vers l'objet qui les contient. La longueur maximale d'une ligne de saisie est spécifiée via l'argument linelen, et le nombre d'octets à allouer pour stocker les lignes d'historique est défini par l'argument histlen. Les lignes d'historique sont stockées bout à bout dans un seul tampon de cette taille. Notez que cela signifie que le nombre de lignes d'historique pouvant être stockées à un moment donné dépend des longueurs des lignes individuelles. Si vous souhaitez placer une limite supérieure au nombre de lignes pouvant être stockées, voir la fonction gl_limit_history() décrite plus loin. Si vous ne voulez pas d'historique du tout, spécifiez histlen à zéro, et aucun tampon d'historique ne sera

alloué.

En cas d'erreur, un message est imprimé sur stderr et NULL est

renvoyé. 
  GetLine *del_GetLine(GetLine
*gl)

Cette fonction supprime les ressources qui ont été renvoyées par un appel précédent à new_GetLine(). Elle renvoie toujours NULL (c'est-à-dire un objet supprimé). Elle ne fait rien si l'argument gl est NULL

. 
  char *gl_get_line(GetLine *gl, const char *prompt,
                   const char *start_line, int start_pos)
;

La fonction gl_get_line() peut être appelée un nombre quelconque de fois pour lire la saisie de l'utilisateur. L'argument gl doit avoir été précédemment renvoyé par un appel à new_GetLine(). L'argument prompt doit être une chaîne normale terminée par NUL, spécifiant l'invite à présenter à l'utilisateur. Par défaut, les invites sont affichées littéralement, mais si elles sont activées avec la fonction gl_prompt_style() (voir plus loin), les invites peuvent contenir des directives pour souligner, passer à et depuis des polices en gras, ou activer et désactiver la mise en

évidence.

Si vous souhaitez spécifier le contenu initial de la ligne pour que l'utilisateur la modifie, passez la chaîne souhaitée via l'argument start_line. Vous pouvez ensuite spécifier le caractère de cette ligne où le curseur est initialementen par l'un des arguments start_line ou start_pos. Cela devrait être -1 si vous voulez que le curseur suive le dernier caractère de la ligne de départ. Si vous ne voulez pas précharger la ligne de cette manière, envoyez start_line comme NULL et définissez start_pos à -1. Notez que le pointeur de ligne renvoyé par un appel à gl_get_line() peut être renvoyé à l'appel suivant à gl_get_line() via start_line. Cela permet à l'application de prendre la dernière ligne saisie et, si elle contient une erreur, de la présenter à l'utilisateur pour la rééditer, le curseur étant initialement positionné là où l'erreur a été rencontrée.

La fonction gl_get_line() renvoie un pointeur vers la ligne saisie par l'utilisateur, ou NULL en cas d'erreur ou à la fin de la saisie. Le pointeur renvoyé fait partie de l'objet ressource gl spécifié, et ne doit donc pas être libéré par l'appelant, ni supposé être inchangé d'un appel à l'autre. Lors de la lecture à partir d'un utilisateur au terminal, il y aura toujours un caractère de nouvelle ligne à la fin de la ligne renvoyée. Lorsque l'entrée standard est récupérée à partir d'un tube ou d'un fichier, il y aura de même une nouvelle ligne, sauf si la ligne d'entrée était trop longue pour être stockée dans le tampon interne. Dans ce dernier cas, vous devriez appeler gl_get_line() à nouveau pour lire le reste de la ligne. Notez que ce comportement rend gl_get_line() similaire à fgets(). En fait, lorsque stdin n'est pas connecté à un terminal, gl_get_line() appelle simplement fgets().

  const char *gl_error_message(GetLine *gl, char *buff,

La valeur de retour est un pointeur vers le message qui s'est produit. Si le message ne rentre pas dans le tampon fourni, il sera tronqué pour s'y adapter.

SOURCES DE CONFIGURATION ALTERNATIVES

Comme mentionné ci-dessus, par défaut, les utilisateurs ont la possibilité de configurer le comportement de gl_get_line() via un fichier de configuration appelé .teclarc dans leur répertoire personnel. Le fait que toutes les applications partagent ce même fichier de configuration est un avantage et un inconvénient. Dans la plupart des cas, c'est un avantage, car cela favorise l'uniformité et libère l'utilisateur de la nécessité de configurer chaque application séparément. Dans certaines applications, cependant, ce moyen unique de configuration pose problème. Ceci est particulièrement vrai pour les logiciels embarqués, où il n'y a pas de système de fichiers pour lire un fichier de configuration, et également pour les applications où un choix radicalement différent de raccourcis clavier est nécessaire pour émuler une interface clavier héritée. Pour répondre à de tels cas, la fonction suivante permet à l'application de contrôler d'où proviennent les informations de configuration.

  int gl_configure_getline(GetLine *gl,
                           const char *app_string,
                           const char *app_file,
                           const char *user_file);

Elle permet aux commandes de configuration qui seraient normalement lues à partir du fichier ~/.teclarc de l'utilisateur, d'être lues à partir d'une chaîne, d'un fichier de configuration spécifique à l'application, et/ou d'un fichier de configuration spécifique à l'utilisateur, ou d'aucun d'entre eux. Si cette fonction est appelée avant le premier appel à gl_get_line(), le comportement par défaut de lecture de ~/.teclarc lors du premier appel à gl_get_line() est désactivé, donc toute la configuration doit être effectuée à l'aide des sources de configuration spécifiées avec cette fonction.

Si app_string != NULL, alors il est interprété comme une chaîne contenant une ou plusieurs commandes de configuration, séparées les unes des autres dans la chaîne par des caractères de nouvelle ligne intégrés. Si app_file != NULL, alors il est interprété comme le chemin d'accès complet d'un fichier de configuration spécifique à l'application. Si user_file != NULL, alors il est interprété comme le chemin d'accès complet d'un fichier de configuration spécifique à l'utilisateur, tel que ~/.teclarc. Par exemple, dans l'appel suivant,

  gl_configure_getline(gl, "edit-mode vi \n nobeep",
                           "/usr/share/myapp/teclarc",
                           "~/.teclarc");

l'argument app_string fait que l'application appelante commence en mode d'édition vi, au lieu du mode emacs par défaut, et désactive l'utilisation de la cloche du terminal par la bibliothèque. Elle tente ensuite de lire les commandes de configuration système à partir d'un fichier optionnel appelé /usr/share/myapp/teclarc, puis lit enfin les commandes de configuration spécifiques à l'utilisateur à partir d'un fichier .teclarc optionnel dans le répertoire personnel de l'utilisateur. Notez que les arguments sont listés par ordre de priorité croissant, le contenu de app_string étant potentiellement remplacé par des commandes dans app_file, et les commandes dans app_file étant potentiellement remplacées par des commandes dans user_file.

Vous pouvez appeler cette fonction autant de fois que nécessaire, les résultats étant cumulatifs, mais notez que des copies de tous les noms de fichiers spécifiés via le

>app_file et user_file sont enregistrés en interne pour une utilisation ultérieure par la fonction de liaison de touches read-init-files ; si vous prévoyez d'appeler cette fonction plusieurs fois, assurez-vous que le dernier appel spécifie les noms de fichiers que vous souhaitez relire lorsque l'utilisateur demande la relecture des fichiers de

configuration.

COMPLÉTION DE MOTS

PERSONNALISÉE

Si dans votre application, vous souhaitez que la complétion par TAB complète d'autres éléments en plus ou à la place des noms de fichiers, vous pouvez organiser cela en enregistrant une fonction de rappel de complétion alternative, au moyen d'un appel à la fonction gl_customize_c

ompletion(). 
  int gl_customize_completion(GetLine *gl, void *data,
                              CplMatchFn *match_fn)
;

L'argument data fournit un moyen à votre application de passer des informations arbitraires spécifiques à l'application à la fonction de rappel. Celles-ci lui sont transmises à chaque fois qu'elle est appelée. Elle peut par exemple pointer vers la table de symboles à partir de laquelle les complétions possibles doivent être recherchées. L'argument match_fn spécifie la fonction de rappel à appeler. Le type de fonction CplMatchFn est défini dans libtecla.h, de même qu'une macro CPL_MATCH_FN() que vous pouvez utiliser pour déclarer et prototyper des fonctions de rappel. La déclaration et les responsabilités des fonctions de rappel sont décrites en détail dans la page de manuel cpl_complete_word(3)

.

En bref, la fonction de rappel est chargée de parcourir la ligne d'entrée vers l'arrière, à partir du point où l'utilisateur a appuyé sur TAB, pour trouver le début du mot en cours de complétion. Elle doit ensuite rechercher les complétions possibles de ce mot et les enregistrer une par une dans l'objet WordCompletion qui lui est passé en argument, en appelant la fonction cpl_add_completion(). Si la fonction de rappel souhaite fournir une complétion de noms de fichiers en plus de ses propres complétions spécifiques, elle a la possibilité d'appeler elle-même la fonction de rappel de complétion de noms de fichiers intégrée. Ceci est également documenté dans la page de manuel cpl_complete_word(3)

.

Notez que si vous souhaitez que gl_get_line() renvoie la ligne d'entrée actuelle lorsqu'une complétion réussie a été effectuée, vous pouvez organiser cela lorsque vous appelez cpl_add_completion(), en faisant du dernier caractère du suffixe de continuation un caractère de nouvelle ligne. Si vous faites cela, la ligne d'entrée sera mise à jour pour afficher la complétion, ainsi que tout suffixe de continuation jusqu'au caractère de nouvelle ligne, puis gl_get_line() renverra cette ligne

d'entrée.

Si, pour une raison quelconque, votre fonction de rappel doit écrire quelque chose sur le terminal, elle doit appeler gl_normal_io() avant de le faire. Cela commencera une nouvelle ligne après la ligne d'entrée actuellement en cours d'édition, rétablira les E/S normales du terminal, et indiquera à gl_get_line() que la ligne d'entrée devra être red

essinée lorsque la fonctio
n de rappel retournera.

AJOUT D'ACTIONS DE

COMPLÉTION

Dans la section précédente, la capacité à personnaliser le comportement de la seule action de complétion par défaut, complete-word, a été décrite. Dans cette section, la capacité à installer des fonctions d'action supplémentaires, afin que différents types de complétion de mots puissent être liés à différentes séquences de touches, est décrite. Cela est réalisé en utilisant la fonction gl_completion_action()

. 
  int gl_completion_action(GetLine *gl,
                           void *data, CplMatchFn *match_fn,
                           int list_only, const char *name,
                           const char *keyseq)
;

Les arguments data et match_fn sont tels que décrits dans la page de manuel cpl_complete_word, et spécifient la fonction de rappel qui doit être invoquée pour identifier les complétions possibles. L'argument list_only détermine si l'action en cours de définition doit tenter de compléter le mot aussi loin que possible dans la ligne d'entrée avant d'afficher d'éventuelles complétions ambiguës, ou si elle doit simplement afficher la liste des complétions possibles sans toucher à la ligne d'entrée. La première option est sélectionnée en spécifiant une valeur de 0, et la seconde en spécifiant une valeur de 1. L'argument name spécifie le nom par lequel les fichiers de configuration et les futures invocations de cette fonction doivent se référer à l'action. Il doit s'agir soit du nom d'une action de complétion existante à modifier, soit d'un nouveau nom non utilisé pour une nouvelle action. Enfin, l'argument keyseq spécifie la séquence de touches par défaut à laquelle lier l'action. Si c'est NULL, aucune nouvelle séquence de touches ne sera liée à

l'action.

Attention : pour que l'utilisateur puisse changer la séquence de touches liée aux actions installées de cette manière, lorsque vous appelez gl_completion_action() pour installer une action donnée pour la première fois, vous devez le faire entre l'appel à new_GetLine() et le premier appel à gl_get_line(). Sinon, lorsque le fichier de configuration de l'utilisateur est lu lors du premier appel à gl_get_line(), le nom de votre action supplémentaire ne sera pas connu, et toute référence à elle dans le fichier de configuration générera une

erreur.

Comme discuté pour gl_customize_completion(), si votre fonction de rappel, pour une raison quelconque, doit écrire quelque chose sur le terminal, elle doit appeler gl_normal_io() a

vant de l
e faire.

DÉFINITION D'ACTIONS

PERSONNALISÉES

Bien que les actions de liaison de touches intégrées soient suffisantes pour les besoins de la plupart des applications, une application spécialisée peut occasionnellement avoir besoin de définir une ou plusieurs actions personnalisées, liées à des séquences de touches spécifiques à l'application. Par exemple, une application de vente bénéficierait d'une séquence de touches affichant le nom de la pièce correspondant à un numéro de pièce situé avant le curseur. Une telle fonctionnalité dépasse clairement le cadre des fonctions d'action intégrées. Ainsi, pour ces cas particuliers, la fonction gl_register_action() est

fournie. 
  int gl_register_action(GetLine *gl, void *data,
			 GlActionFn *fn, const char *name,
			 const char *keyseq)
;

Cette fonction permet à l'application d'enregistrer une fonction externe, fn, qui sera par la suite appelée chaque fois que soit la séquence de touches spécifiée, keyseq, est saisie par l'utilisateur, soit l'utilisateur saisit une autre séquence de touches qu'il lie par la suite au nom d'action spécifié, name, dans son fichier de configuration. L'argument data peut être un pointeur vers n'importe quoi que l'application souhaite voir passer à la fonction d'action, fn, chaque fois que cette fonction est

invoquée.

La fonction d'action, fn, doit être déclarée à l'aide de la macro suivante, qui est définie dans libtecl

a.h. 
  #define GL_ACTION_FN(fn) GlAfterAction (fn)(GetLine *gl, \
              void *data, int count, size_t curpos, \
              const char
*line)

Les arguments gl et data sont ceux qui ont été passés précédemment à gl_register_action() lorsque la fonction d'action a été enregistrée. L'argument count est un argument numérique que l'utilisateur a la possibilité de saisir à l'aide de l'action digit-argument, avant d'invoquer l'action. Si l'utilisateur n'entre pas de nombre, alors l'argument count est défini à 1. Nominalement, cet argument est interprété comme un nombre de répétitions, ce qui signifie que l'action doit être répétée ce nombre de fois. En pratique, cependant, pour certaines actions, un nombre de répétitions n'a que peu de sens. Dans de tels cas, les actions peuvent soit simplement ignorer l'argument count, soit utiliser sa valeur à une autre

fin.

Une copie de la ligne d'entrée actuelle est passée dans l'argument en lecture seule line. La position actuelle du curseur dans cette chaîne est donnée par l'index contenu dans l'argument curpos. Notez que la manipulation directe de la ligne d'entrée et de la position du curseur n'est pas autorisée. En effet, les règles dictées par divers modes, tels que le mode vi par rapport au mode emacs, le mode sans écho, et le mode insertion par rapport au mode surimpression, etc., rendent la tâche trop complexe pour un développeur d'application afin d'écrire une action d'édition conforme, et contraignent également les changements futurs aux internes de gl_get_line(). Une solution potentielle à ce dilemme serait de permettre à la fonction d'action d'éditer la ligne à l'aide des actions d'édition existantes. Cela est actuellement à

l'étude.

Si la fonction d'action souhaite écrire du texte sur le terminal, sans que cela se mélange avec le texte affiché de la ligne d'entrée, ou lire depuis le terminal sans avoir à gérer les E/S brutes du terminal, alors avant de faire l'une ou l'autre de ces opérations, elle doit suspendre temporairement l'édition de ligne en appelant la fonction gl_normal_io(). Cette fonction vide toute sortie en attente vers le terminal, déplace le curseur au début de la ligne suivant la dernière ligne du terminal de la ligne d'entrée, puis restaure le terminal à un état adapté à l'utilisation avec les fonctionnalités stdio de C. Cela inclut notamment la restauration du mappage normal de \n vers \r\n, et, en mode serveur, la restauration de la forme bloquante normale des E/S du terminal. Après avoir appelé cette fonction, la fonction d'action peut lire depuis et écrire vers le terminal sans craindre de créer un désordre. Il n'est pas nécessaire pour la fonction d'action de restaurer l'environnement d'édition original avant de retourner. Cela est fait automatiquement par gl_get_line() après le retour de la fonction d'action. Voici un exemple simple d'une fonction d'action qui écrit la phrase "Hello world" sur une nouvelle ligne du terminal après la ligne en cours d'édition. Lorsque cette fonction retourne, la ligne d'entrée est redessinée sur la ligne suivant la ligne "Hello world", et l'édition de ligne

reprend. 
  static GL_ACTION_FN(say_hello_fn)
  {
    if(gl_normal_io(gl))   /* Suspendre temporairement l'édition */
      return GLA_ABORT;
    printf("Bonjour le monde\n");
    return GLA_CONTINUE;
  }

Les fonctions d'action doivent retourner l'une des valeurs suivantes, pour indiquer à gl_get_line() comment procéder.

  GLA_ABORT     -   Cause gl_get_line() à retourner NULL.
  GLA_RETURN    -   Cause gl_get_line() à retourner la
                    ligne de saisie terminée.
  GLA_CONTINUE  -   Reprendre l'édition de ligne de commande.

Notez que l'argument name de gl_register_action() spécifie le nom par lequel un utilisateur peut faire référence à l'action dans son fichier de configuration. Cela lui permet de réaffecter l'action à une autre séquence de touches. Pour que cela fonctionne, il est nécessaire d'appeler gl_register_action() entre l'appel à new_GetLine() et le premier appel à gl_get_line().

FICHIERS HISTORIQUES

Pour sauvegarder le contenu du tampon d'historique avant de quitter votre application, et le restaurer ensuite lorsque vous redémarrez l'application, les fonctions suivantes sont fournies.

 int gl_save_history(GetLine *gl, const char *filename,
                     const char *comment, int max_lines);
 int gl_load_history(GetLine *gl, const char *filename,
                     const char *comment);

L'argument filename spécifie le nom à donner au fichier d'historique lors de la sauvegarde, ou le nom d'un fichier d'historique existant lors du chargement. Il peut contenir des expressions de répertoire personnel et de variables d'environnement, telles que "~/.myapp_history" ou "$HOME/.myapp_history".

Avec chaque ligne d'historique, des informations supplémentaires à son sujet, telles que quand elle a été entrée par l'utilisateur et quel est son niveau d'imbrication, sont enregistrées sous forme de commentaire précédant la ligne dans le fichier d'historique. L'écriture sous forme de commentaire permet au fichier d'historique de servir également de fichier de commandes, au cas où vous souhaiteriez rejouer une session entière en l'utilisant. Comme les préfixes de commentaires diffèrent selon les langages, l'argument comment est fourni pour spécifier le préfixe de commentaire. Par exemple, si votre application était un shell Unix, tel que le shell Bourne, vous spécifieriez "#" ici. Quel que soit le caractère de commentaire que vous choisissez, vous devez spécifier le même préfixe à gl_load_history() que celui utilisé lors de l'appel à gl_save_history() pour écrire le fichier d'historique.

L'argument max_lines doit être -1 pour spécifier que toutes les lignes de la liste d'historique doivent être enregistrées, ou un nombre positif spécifiant un plafond sur le nombre de lignes les plus récentes à enregistrer.

Les deux fonctions retournent une valeur non nulle en cas d'erreur, après avoir écrit un message d'erreur sur stderr. Notez que gl_load_history() ne considère pas la non-existence d'un fichier comme une erreur.

LISTES HISTORIQUES MULTIPLES

Si votre application utilise un seul objet GetLine pour entrer de nombreux types de lignes de saisie différents, vous voudrez peut-être que gl_get_line() distingue les différents types de lignes dans la liste d'historique, et ne rappelle que les lignes qui correspondent au type de ligne actuel. Pour répondre à cette exigence, gl_get_line() marque les lignes enregistrées dans la liste d'historique avec un identifiant entier choisi par l'application. Initialement, cet identifiant est défini à 0 par new_GetLine(), mais il peut être modifié ultérieurement en appelant gl_group_history().

  int gl_group_history(GetLine *gl, unsigned id);

L'identifiant entier id peut être n'importe quel nombre choisi par l'application, mais notez que gl_save_history() et gl_load_history() préservent l'association entre les identifiants et les lignes d'entrée historiques entre les invocations de programme, vous devriez donc choisir des identifiants fixes pour les différents types de lignes d'entrée utilisés par votre application.

Chaque fois que gl_get_line() ajoute une nouvelle ligne de saisie à la liste d'historique, l'identifiant d'historique actuel est enregistré avec elle, et lorsqu'il est demandé de rappeler une ligne d'entrée historique, il ne rappelle que les lignes marquées avec l'identifiant actuel.

AFFICHAGE DE L'HISTORIQUE

La liste d'historique peut être affichée en appelant gl_show_history().

  int gl_show_history(GetLine *gl, FILE *fp,
                      const char *fmt,
                      int all_groups,
                      int max_lines);

Ceci affiche le contenu actuel de la liste d'historique sur le flux de sortie stdio fp. Si l'argument max_lines est supérieur ou égal à zéro, alors pas plus que ce nombre de lignes les plus récentes ne sera affiché. Si l'argument all_groups est différent de zéro, les lignes de tous les groupes d'historique sont affichées. Sinon, seules celles du groupe d'historique actuellement sélectionné sont affichées. L'argument de chaîne de format, fmt, détermine comment la ligne est affichée. Il peut contenir des caractères arbitraires qui sont écrits tels quels, entrelacés avec les directives de format suivantes :

  %D  -  La date à laquelle la ligne a été initialement
         saisie, formatée comme 2001-11-20.
  %T  -  L'heure de la journée à laquelle la ligne a été
         saisie, formatée comme 23:59:59.
  %N  -  Le numéro d'entrée séquentiel de la ligne dans
         le tampon d'historique.
  %G  -  Le numéro du groupe d'historique auquel
         la ligne appartient.
  %%  -  Un caractère % littéral.
  %H  -  La ligne d'historique elle-même.

Ainsi, une chaîne de format comme **" %D %T %H\n" ** produirait quelque chose comme :

  2001-11-20 10:23:34  Bonjour le monde

Notez l'inclusion d'un caractère de nouvelle ligne explicite dans la chaîne de format.

RECHERCHE DANS L'HISTORIQUE

La fonction gl_lookup_history() permet à l'application appelante de rechercher des lignes dans la liste d'historique.

  typedef struct {
    const char *line;    /* La ligne historique */
                         /*  demandée. */

                         /*  la ligne appartient. */
    time_t timestamp;    /* La date et l'heure auxquelles */
                         /*  la ligne a été initialement */
                         /*  saisie. */
  } GlHistoryLine;

L'argument id indique quelle ligne rechercher, où la première ligne entrée dans la liste d'historique après l'appel à new_GetLine() est désignée par 0, et les lignes entrées par la suite sont désignées par des nombres successivement plus élevés. ARCHIVAGE MANUEL DE L'HISTORIQUE

Par défaut, chaque fois qu'une ligne est entrée par l'utilisateur, elle est automatiquement ajoutée à la liste d'historique, juste avant que gl_get_line() ne retourne la ligne à l'appelant. C'est pratique pour la majorité des applications, mais il existe aussi des applications qui nécessitent un contrôle plus fin sur ce qui est ajouté à la liste d'historique. Dans de tels cas, l'ajout automatique des lignes entrées à la liste d'historique peut être désactivé en appelant la fonction gl_automatic_history().

  int gl_automatic_history(GetLine *gl, int enable);

Si cette fonction est appelée avec son argument enable réglé sur 0, gl_get_line() n'archivera pas automatiquement les lignes entrées par la suite. L'archivage automatique peut être réactivé plus tard, en appelant à nouveau cette fonction, avec son argument enable réglé sur 1. Tant que l'archivage automatique de l'historique est désactivé, l'application appelante peut utiliser gl_append_history() pour ajouter des lignes à la liste d'historique au besoin.

  int gl_append_history(GetLine *gl, const char *line);

L'argument line spécifie la ligne à ajouter à la liste d'historique. Il doit s'agir d'une chaîne normale terminée par **' '**. Si cette chaîne contient des caractères de nouvelle ligne, la ligne qui sera archivée dans la liste d'historique sera terminée par le premier d'entre eux. Sinon, elle sera terminée par le terminateur **' '**. Si la ligne est plus longue que la longueur maximale de ligne de saisie spécifiée lors de l'appel à new_GetLine(), elle sera tronquée à la longueur de ligne réelle de gl_get_line() lorsqu'elle sera rappelée.

En cas de succès, gl_append_history() retourne 0. Sinon, elle retourne une valeur non nulle et définit errno à l'une des valeurs suivantes.

   EINVAL  -  L'un des arguments passés à
              gl_append_history() était NULL.
   ENOMEM  -  La ligne spécifiée était plus longue que la taille allouée
              du tampon d'historique (telle que spécifiée lors de
              l'appel à new_GetLine()), elle n'a donc pas pu être
              archivée.

Une description textuelle de l'erreur peut éventuellement être obtenue en appelant gl_error_message(). Notez qu'après une telle erreur, la liste d'historique reste dans un état valide pour recevoir de nouvelles lignes d'historique, il y a donc peu de risque à simplement ignorer le statut de retour de gl_append_history().

CONFIGURATION DIVERSES DE L'HISTORIQUE

Si vous souhaitez modifier la taille du tampon d'historique qui a été spécifiée à l'origine dans l'appel à new_GetLine(), vous pouvez le faire avec la fonction gl_resize_history().

  int gl_resize_history(GetLine *gl, size_t histlen);

L'argument histlen spécifie la nouvelle taille en octets, et si vous la spécifiez à 0, le tampon sera supprimé.

Comme mentionné dans la discussion sur new_GetLine(), le nombre de lignes pouvant être stockées dans le tampon d'historique dépend de la longueur des lignes individuelles. Par exemple, un tampon de 1000 octets pourrait tout aussi bien stocker 10 lignes de longueur moyenne de 100 octets, ou 2 lignes de longueur moyenne de 50 octets. Bien que le tampon ne soit jamais étendu lors de l'ajout de nouvelles lignes, une liste de pointeurs dans le tampon est étendue si nécessaire pour accueillir le nombre de lignes actuellement stockées dans le tampon. Lorsqu'une limite est en vigueur, seules les max_lines lignes les plus récemment ajoutées sont conservées dans le tampon. Les lignes plus anciennes sont

La fonction constructrice new_GetLine() suppose que l'entrée doit être lue depuis stdin, et que la sortie est écrite vers stdout. La fonction suivante vous permet de basculer vers d'autres flux d'entrée et de

SIGNAUX

Par défaut, la fonction gl_get_line() intercepte un certain nombre de signaux. C'est particulièrement important pour les signaux qui, par défaut, termineraient le processus, puisque le terminal doit être restauré à un état utilisable avant que cela ne se produise. Dans cette section, les signaux qui sont interceptés par défaut, et comment gl_get_line() y répond, sont décrits. Changer ces valeurs par défaut est le sujet de la section

suivante.

Quand le sous-ensemble suivant de signaux est capté, gl_get_line() restaure d'abord les paramètres du terminal et la gestion des signaux à l'état dans lequel ils se trouvaient avant que gl_get_line() n'ait été appelé, renvoie le signal, pour permettre aux gestionnaires de signaux de l'application appelante de le traiter, puis si le processus existe toujours, gl_get_line() retourne NULL et définit errno comme spécifié

ci-dessous. 
 SIGINT  -  Ce signal est généré à la fois par la touche
            d'interruption du clavier (généralement ^C), et la touche
            de pause du clavier.
            errno=EINTR
 SIGHUP  -  Ce signal est généré quand le terminal de contrôle
            se termine.
            errno=ENOTTY
 SIGPIPE -  Ce signal est généré quand un programme tente
            d'écrire dans un pipe dont l'extrémité distante n'est pas lue
            par aucun processus. Cela peut se produire par exemple
            si vous avez appelé gl_change_terminal() pour
            rediriger la sortie vers un pipe caché sous un pseudo
            terminal.
            errno=EPIPE
 SIGQUIT -  Ce signal est généré par la touche quit du clavier
            (généralement ^\).
            errno=EINTR
 SIGABRT -  Ce signal est généré par la fonction standard C,
            abort(). Par défaut, elle termine à la fois
            le processus et génère un core dump.
            errno=EINTR
 SIGTERM -  C'est le signal par défaut que la commande UN*X
            kill envoie aux processus.
errno=EINTR

Notez que dans le cas de tous les signaux ci-dessus, POSIX mandate que par défaut le processus soit terminé, avec en plus un core dump dans le cas du signal SIGQUIT. En d'autres termes, si l'application appelante ne remplace pas le gestionnaire par défaut en fournissant son propre gestionnaire de signal, la réception du signal correspondant terminera l'application avant que gl_get_line() ne

retourne.

Si gl_get_line() interrompt avec errno défini à EINTR, vous pouvez découvrir quel signal a causé l'interruption, en appelant la fonction

suivante. 
  int gl_last_signal(const GetLine *gl)
;

Elle retourne le code numérique (ex. SIGINT) du dernier signal qui a été reçu lors du dernier appel à gl_get_line(), ou -1 si aucun signal n'a été

reçu.

Sur les systèmes qui le supportent, quand un signal SIGWINCH (changement de fenêtre) est reçu, gl_get_line() interroge le terminal pour connaître sa nouvelle taille, redessine la ligne d'entrée actuelle pour s'adapter à la nouvelle taille, puis retourne attendre la saisie clavier de l'utilisateur. Contrairement aux autres signaux, ce signal n'est pas renvoyé à

l'application.

Enfin, les signaux suivants font en sorte que gl_get_line() restaure d'abord le terminal et l'environnement des signaux à l'état qui prévalait avant que gl_get_line() n'ait été appelé, puis renvoie le signal à l'application. Si le processus existe toujours après que le signal a été délivré, alors gl_get_line() rétablit ensuite ses propres gestionnaires de signaux, passe le terminal en mode brut, redessine la ligne d'entrée, et retourne attendre la saisie terminal de

l'utilisateur. 
 SIGCONT    -  Ce signal est généré quand un processus suspendu
               est repris.
 SIGPOLL    -  Sur les systèmes SVR4, ce signal notifie le
               processus d'un événement E/S asynchrone. Notez
               que sous 4.3+BSD, SIGIO et SIGPOLL sont
               identiques. Sur d'autres systèmes, SIGIO est ignoré
               par défaut, donc gl_get_line() ne l'intercepte pas
               par défaut.
 SIGPWR     -  Ce signal est généré quand une panne de courant
               se produit (vraisemblablement quand le système est sur
               un onduleur).
 SIGALRM    -  Ce signal est généré quand un minuteur
               expire.
 SIGUSR1    -  Un signal spécifique à l'application.
 SIGUSR2    -  Un autre signal spécifique à l'application.
 SIGVTALRM  -  Ce signal est généré quand un minuteur virtuel
               expire (voir man setitimer(2)).
 SIGXCPU    -  Ce signal est généré quand un processus
               dépasse sa limite de temps CPU souple.
 SIGXFSZ    -  Ce signal est généré quand un processus
               dépasse sa limite de taille de fichier souple.
 SIGTSTP    -  Ce signal est généré par la touche de suspension
               du terminal, qui est généralement ^Z, ou la
               touche de suspension différée du terminal, qui est
               généralement ^Y.
 SIGTTIN    -  Ce signal est généré si le programme
               tente de lire depuis le terminal pendant que le
               programme s'exécute en arrière-plan.
 SIGTTOU    -  Ce signal est généré si le programme
               tente d'écrire sur le terminal pendant que le
               programme s'exécute en
arrière-plan.

Évidemment, tous les signaux ci-dessus ne sont pas supportés sur tous les systèmes, donc le code pour les supporter est compilé conditionnellement dans la bibliothèque

tecla.

tâches réinitialisent généralement les paramètres du terminal quand un processus cède
le terminal de contrôle, donc ce n'est un problème qu'avec les shells plus anciens.

GESTION PERSONNALISÉE DES

SIGNAUX

La section précédente a listé les signaux que gl_get_line() intercepte par défaut, et a décrit comment il y répond. Cette section décrit comment à la fois ajouter et retirer des signaux de la liste des signaux interceptés, et comment spécifier comment gl_get_line() devrait répondre à un signal

donné.

Si vous n'avez pas besoin que gl_get_line() fasse quoi que ce soit en réponse à un signal qu'il intercepte normalement, vous pouvez indiquer à gl_get_line() d'ignorer ce signal en appelant gl_ignore_sig

nal(). 
  int gl_ignore_signal(GetLine *gl, int signo)
;

L'argument signo est le numéro du signal (ex. SIGINT) que vous voulez voir ignoré. Si le signal spécifié n'est pas actuellement l'un de ceux qui sont interceptés, cette fonction ne fait

rien.

La fonction gl_trap_signal() vous permet soit d'ajouter un nouveau signal à la liste que gl_get_line() intercepte, soit de modifier comment ilesponds à un signal qu'il intercepte déjà.

  int gl_trap_signal(GetLine *gl, int signo, unsigned flags,
                     GlAfterSignal after, int errno_value);

L'argument signo est le numéro du signal que vous souhaitez intercepter. L'argument flags est un ensemble de drapeaux qui déterminent l'environnement dans lequel le gestionnaire de signaux de l'application est appelé, l'argument after indique à gl_get_line() ce qu'il doit faire après le retour du gestionnaire de signaux de l'application, et errno_value indique à gl_get_line() ce qu'il doit définir pour errno en cas d'interruption.

L'argument flags est un OU bit à bit de zéro ou plusieurs des énumérations suivantes :

  GLS_RESTORE_SIG  -  Restaure l'environnement de signal
                      de l'appelant lors de la gestion
                      du signal.
  GLS_RESTORE_TTY  -  Restaure les paramètres du terminal
                      de l'appelant lors de la gestion
                      du signal.
  GLS_RESTORE_LINE -  Déplace le curseur au début de la
                      ligne suivant la ligne d'entrée avant
                      d'appeler le gestionnaire de signaux
                      de l'application.
  GLS_REDRAW_LINE  -  Redessine la ligne d'entrée lorsque
                      le gestionnaire de signaux de
                      l'application retourne.
  GLS_UNBLOCK_SIG  -  Normalement, si le programme appelant
                      a un signal bloqué (man sigprocmask),
                      gl_get_line() n'intercepte pas ce
                      signal. Ce drapeau indique à
                      gl_get_line() d'intercepter le signal
                      et de le débloquer pendant la durée
                      de l'appel à gl_get_line().
  GLS_DONT_FORWARD -  Si ce drapeau est inclus, le signal
                      ne sera pas transmis au gestionnaire
                      de signaux du programme appelant.

Deux combinaisons de drapeaux couramment utiles sont également énumérées comme suit :

  GLS_RESTORE_ENV   = GLS_RESTORE_SIG | GLS_RESTORE_TTY |
                      GLS_REDRAW_LINE
  GLS_SUSPEND_INPUT = GLS_RESTORE_ENV | GLS_RESTORE_LINE

Si votre gestionnaire de signaux, ou le gestionnaire de signaux par défaut du système pour ce signal, si vous ne l'avez pas remplacé, n'écrit jamais sur le terminal, ni ne suspend ou termine le programme appelant, alors vous pouvez définir l'argument flags sur 0 en toute sécurité.

Si votre gestionnaire de signaux écrit toujours sur le terminal, y lit, ou suspend ou termine le programme, vous devez spécifier l'argument flags comme GL_SUSPEND_INPUT, afin que :

1. Le curseur ne soit pas laissé au milieu de la ligne d'entrée.
2. L'utilisateur puisse taper une entrée et qu'elle soit échoée.
3. Vous n'ayez pas besoin de terminer chaque ligne de sortie avec
   \r\n, au lieu de simplement \n.

La combinaison GL_RESTORE_ENV est identique à GL_SUSPEND_INPUT, à la différence qu'elle ne déplace pas le curseur, et si votre gestionnaire de signaux n'écrit ni ne lit rien sur le terminal, l'utilisateur ne verra aucune indication visible qu'un signal a été intercepté. Cela peut être utile si vous avez un gestionnaire de signaux qui écrit occasionnellement sur le terminal, où l'utilisation de GL_SUSPEND_LINE entraînerait une duplication inutile de la ligne d'entrée lorsqu'rien n'a été écrit sur le terminal. Un tel gestionnaire de signaux, lorsqu'il écrit sur le terminal, doit s'assurer de commencer une nouvelle ligne au début de sa première écriture, en écrivant une nouvelle ligne avant de retourner. Si le signal arrive pendant que l'utilisateur saisit une ligne qui n'occupe qu'une seule ligne de terminal, ou si le curseur se trouve sur la dernière ligne de terminal d'une ligne d'entrée plus longue, cela aura le même effet que GL_SUSPEND_INPUT. Sinon, il commencera à écrire sur une ligne qui contient déjà une partie de la ligne d'entrée affichée. Cela ne pose aucun problème, mais c'est un peu inesthétique, c'est pourquoi la combinaison GL_SUSPEND_INPUT est préférable si vous savez que vous allez toujours écrire sur le terminal.

L'argument after, qui détermine ce que gl_get_line() fait après le retour du gestionnaire de signaux de l'application (s'il retourne), peut prendre l'une des valeurs suivantes :

  GLS_RETURN   - Retourne la ligne d'entrée complétée, comme
                 si l'utilisateur avait appuyé sur la touche
                 retour.
  GLS_ABORT    - Provoque l'interruption de gl_get_line().
                 Lorsque cela se produit, gl_get_line()
                 retourne NULL, et un appel ultérieur à
                 gl_return_status() retournera
                 GLR_SIGNAL. Notez que si l'application a
                 besoin que errno ait toujours une valeur
                 significative lorsque gl_get_line()
                 retourne NULL, la fonction de rappel
                 devrait définir errno de manière
                 appropriée.
  GLS_CONTINUE - Reprend l'édition de ligne de commande.

L'argument errno_value est destiné à être combiné avec l'option GLS_ABORT, indiquant à gl_get_line() quelle valeur définir pour la variable standard errno avant de retourner NULL au programme appelant. Il peut cependant être utilisé avec l'option GL_RETURN, au cas où vous souhaiteriez un moyen de distinguer une ligne d'entrée saisie à l'aide de la touche retour, et une autre saisie suite à la réception d'un signal.

GESTION FIABLE DES SIGNAUX

La gestion des signaux est étonnamment difficile à réaliser de manière fiable sans conditions de concurrence. Dans gl_get_line(), beaucoup de soin a été apporté pour permettre aux applications d'effectuer une gestion fiable des signaux autour de gl_get_line(). Cette section explique comment en tirer parti.

À titre d'exemple des problèmes qui peuvent survenir si l'application n'est pas écrite correctement, imaginez que votre application ait un gestionnaire de signaux SIGINT qui définit un drapeau global. Supposons maintenant que l'application teste ce drapeau juste avant d'appeler gl_get_line(). Si un signal SIGINT se produit dans la petite fenêtre de temps entre l'instruction qui teste la valeur de ce drapeau et l'instruction qui appelle gl_get_line(), alors gl_get_line() ne verra pas le signal et ne sera pas interrompu. En conséquence, l'application ne pourra pas répondre au signal tant que l'utilisateur n'aura pas fini de saisir la ligne d'entrée et que gl_get_line() ne sera pas retourné. Selon l'application, cela pourrait être une catastrophe ou non, mais au minimum, cela laisserait l'utilisateur perplexe.

La façon d'éviter de tels problèmes est de faire ce qui suit.

1. Si nécessaire, utilisez la fonction gl_trap_signal() pour configurer gl_get_line() afin qu'il s'interrompe lors de la réception de signaux importants.

2. Configurez gl_get_line() de telle sorte que si l'un des signaux qu'il intercepte est bloqué lorsque gl_get_line() est appelé, ils soient automatiquement débloqués pendant les périodes où gl_get_line() attend des E/S. Cela peut être fait soit sur une base par signal, en appelant la fonction gl_trap_signal() et en spécifiant l'attribut GLS_UNBLOCK du signal, soit globalement en appelant la fonction gl_catch_blocked().

     void gl_catch_blocked(GetLine *gl);

Cette fonction ajoute simplement l'attribut GLS_UNBLOCK à tous les signaux qu'elle est actuellement configurée pour intercepter.

3. Juste avant d'appeler gl_get_line(), bloquez la livraison de tous les signaux que gl_get_line() est configuré pour intercepter. Cela peut être fait à l'aide de la fonction POSIX sigprocmask() en conjonction avec la fonction gl_list_signals().

      int gl_list_signals(GetLine *gl, sigset_t *set);

Cette fonction retourne l'ensemble des signaux qu'elle est actuellement configurée pour intercepter dans l'argument set, qui est dans le format requis par sigprocmask().

4. Dans l'exemple, vous testeriez maintenant le drapeau global que le gestionnaire de signaux définit, sachant qu'il n'y a plus de danger que ce drapeau soit défini à nouveau tant que gl_get_line() ne débloque pas ses signaux lors des E/S.

5. Finalement, gl_get_line() retourne, soit parce qu'un signal a été intercepté, qu'une erreur s'est produite, soit que l'utilisateur a terminé la saisie de sa ligne d'entrée.

6. Vous vérifieriez alors à nouveau le drapeau de signal global, et s'il est défini, vous y répondriez et mettriez le drapeau à zéro.

7. Utilisez sigprocmask() pour débloquer les signaux qui ont été bloqués à l'étape 3.

La même technique peut être utilisée autour de certaines fonctions POSIX conscientes des signaux, telles que sigsetjmp() et sigsuspend(), et en particulier, la première de ces deux fonctions peut être utilisée en conjonction avec siglongjmp() pour implémenter une gestion de signaux sans conditions de concurrence autour d'autres appels système de longue durée. La manière de procéder est expliquée ensuite, en montrant comment gl_get_line() parvient à intercepter les signaux de manière fiable autour des appels à des fonctions telles que read() et select() sans conditions de concurrence.

La première chose que fait gl_get_line(), chaque fois qu'il est appelé, est d'utiliser la fonction POSIX sigprocmask() pour bloquer la livraison de tous les signaux qu'il est actuellement configuré pour intercepter. C'est redondant si l'application les a déjà bloqués, mais cela ne cause aucun problème. Il annule cette étape juste avant de retourner.

Chaque fois que gl_get_line() a besoin d'appeler read() ou select() pour attendre une entrée de l'utilisateur, il appelle d'abord la fonction POSIX sigsetjmp(), en veillant à spécifier une valeur non nulle pour son argument savesigs. La raison de ce dernier argument deviendra claire sous peu.

Si sigsetjmp() retourne zéro, gl_get_line() fait alors ce qui suit.

a. Il utilise la fonction POSIX sigaction() pour enregistrer
   un gestionnaire de signaux temporaire pour tous les signaux
   qu'il est configuré pour intercepter. Ce gestionnaire de
   signaux fait deux choses.
   1. Il enregistre le numéro du signal reçu dans une variable
      au niveau du fichier.
   2. Il appelle ensuite la fonction POSIX siglongjmp()
      en utilisant le tampon passé à sigsetjmp() comme
      premier argument, et une valeur non nulle pour le second
      argument.
   Lorsque ce gestionnaire de signaux est enregistré, le membre
   sa_mask de l'argument struct sigaction act de
   l'appel à sigaction() est configuré pour contenir tous
   les signaux que gl_get_line() intercepte. Cela garantit
   qu'un seul signal sera capturé à la fois par notre gestionnaire
   de signaux, ce qui garantit que plusieurs instances de notre
   gestionnaire de signaux ne se marchent pas sur les pieds.
b. Maintenant que le gestionnaire de signaux est configuré,
   gl_get_line() débloque tous les signaux qu'il est
   configuré pour intercepter.
c. Il appelle ensuite les appels système read() ou
   select() pour attendre une entrée clavier.
d. Si cet appel système retourne (c'est-à-dire qu'aucun signal n'est reçu),
   gl_get_line() rebloque les signaux d'intérêt.
e. Il rétablit ensuite les gestionnaires de signaux qui ont été
   déplacés par celui qui vient d'être installé.

Alternativement, si sigsetjmp() retourne une valeur non nulle, cela signifie qu'il

à l'un des signaux interceptés a été capturé pendant l'exécution des étapes ci-dessus. Lorsque cela se produit, gl_get_line() fait ce qui

suit.

Tout d'abord, notez que lorsqu'un appel à siglongjmp() provoque le retour de sigsetjmp(), à condition que l'argument savesigs de sigsetjmp() ait été non nul, comme spécifié ci-dessus, le masque de traitement des signaux est restauré à l'état dans lequel il se trouvait lorsque sigsetjmp() a été appelé. C'est la différence importante entre sigsetjmp() et l'ancien setjmp() problématique, et c'est l'ingrédient essentiel qui permet d'éviter les conditions de course dans la gestion des signaux. AFFICHAGE DYNAMIQUE DE TEXTE

Entre les appels à gl_get_line(), la fonction gl_display_text() offre un moyen pratique d'afficher des paragraphes de texte, alignés à gauche et répartis sur une ou plusieurs lignes de terminal conformément aux contraintes de la largeur actuelle du terminal. Des exemples d'utilisation de cette fonction se trouvent dans les programmes de démonstration, où elle est utilisée pour afficher des introductions. Dans ces exemples, l'utilisation avancée de préfixes, de suffixes et de lignes de remplissage optionnels pour dessiner une boîte autour du texte est également illustrée.

  int gl_display_text(GetLine *gl, int indentation,
                      const char *prefix,
                      const char *suffix, int fill_char,
                      int def_width, int start,
                      const char *string);

Si gl n'est pas actuellement connecté à un terminal, par exemple si la sortie d'un programme utilisant gl_get_line() est redirigée vers un autre programme ou vers un fichier, alors la valeur du paramètre def_width est utilisée comme largeur du terminal.

L'argument indentation spécifie le nombre de caractères à utiliser pour indenter chaque ligne de sortie. L'argument fill_char spécifie le caractère qui sera utilisé pour effectuer cette indentation.

L'argument prefix peut être soit NULL, soit une chaîne à placer au début de chaque nouvelle ligne (après toute indentation). De même, l'argument suffix peut être soit NULL, soit une chaîne à placer à la fin de chaque ligne. Le suffixe est placé juste contre le bord droit du terminal, et tout espace entre son premier caractère et le dernier mot de cette ligne est rempli avec le caractère spécifié par l'argument fill_char. Normalement, le caractère de remplissage est un espace.

L'argument start indique à gl_display_text() combien de caractères ont déjà été écrits sur la ligne de terminal actuelle, et indique donc l'index de colonne de départ du curseur. Étant donné que la valeur de retour de gl_display_text() est l'index de colonne de fin du curseur, en passant la valeur de retour d'un appel à l'argument start de l'appel suivant, un paragraphe qui est divisé entre plusieurs chaînes peut être composé en appelant gl_display_text() pour chaque portion successive du paragraphe. Notez que des caractères de nouvelle ligne littéraux sont nécessaires à la fin de chaque paragraphe pour forcer le démarrage d'une nouvelle ligne.

En cas d'erreur, gl_display_text() retourne -1.

FACILITÉS DE FONCTION DE RAPPEL

Sauf indication contraire, les fonctions de rappel, telles que les fonctions de rappel de complétion par tabulation et les fonctions de rappel d'événements, ne doivent pas appeler de fonctions de ce module. Les fonctions suivantes, cependant, sont conçues spécifiquement pour être utilisées par des fonctions de rappel.

Appeler la fonction gl_replace_prompt() à partir d'une fonction de rappel indique à gl_get_line() d'afficher une invite différente lorsque la fonction de rappel retourne. Sauf en mode serveur non bloquant, elle n'a aucun effet si elle est utilisée entre les appels à gl_get_line(). En mode serveur non bloquant (voir la page de manuel gl_io_mode(3), lorsqu'elle est utilisée entre deux appels à gl_get_line() qui opèrent sur la même ligne d'entrée, la ligne d'entrée actuelle sera redessinée avec la nouvelle invite lors du prochain appel à gl_get_line().

  void gl_replace_prompt(GetLine *gl, const char *prompt);

JEUX DE CARACTÈRES INTERNATIONAUX

Depuis la version 1.4.0 de libtecla, gl_get_line() est propre sur 8 bits. Cela signifie que tous les caractères 8 bits qui sont imprimables dans la locale actuelle de l'utilisateur sont maintenant affichés tels quels et inclus dans la ligne d'entrée retournée. En supposant que le programme appelant contient correctement un appel tel que le suivant,

  setlocale(LC_CTYPE, "");

alors la locale actuelle est déterminée par la première des variables d'environnement LC_CTYPE, LC_ALL, et LANG, qui est trouvée pour contenir un nom de locale valide. Si aucune de ces variables n'est définie, ou si le programme néglige d'appeler setlocale, alors la locale par défaut C est utilisée, qui est l'ASCII 7 bits américain. Sur la plupart des plateformes de type Unix, vous pouvez obtenir une liste des locales valides en tapant la commande :

  locale -a

à l'invite du shell. Une documentation supplémentaire sur la manière dont l'utilisateur peut utiliser cela pour saisir des caractères internationaux se trouve dans la page de manuel tecla(7).

SÉCURITÉ DES THREADS

Dans un programme multi-threadé, vous devriez utiliser la version libtecla_r.a de la bibliothèque. Celle-ci utilise des versions réentrantes des fonctions système, lorsque disponibles. Malheureusement, ni terminfo ni termcap n'ont été conçus pour être réentrants, vous ne pouvez donc pas utiliser en toute sécurité les fonctions du module getline dans plusieurs threads (vous pouvez utiliser les modules d'expansion de fichiers et de complétion de mots séparés dans plusieurs threads, voir les pages de manuel correspondantes pour plus de détails). Cependant, en raison de l'utilisation de fonctions réentrantes POSIX pour la recherche de répertoires personnels, etc., il est sûr d'utiliser ce module à partir d'un seul thread d'un programme multi-threadé, à condition que vos autres threads n'utilisent aucune fonction termcap ou terminfo.
