L

a

fonction gl_get_line() fait partie de la bibliothèque tecla (voir la page man libtecla(3)). Si l'utilisateur tape sur un terminal, chaque appel lui demande une ligne de saisie, puis fournit des fonctionnalités d'édition interactives, similaires à celles du shell unix tcsh. En plus de l'édition simple de ligne de commande, elle prend en charge le rappel des lignes de commande précédemment saisies, la complétion des noms de fichiers avec la touche TAB, et l'expansion des caractères génériques dans les noms de fichiers en ligne. La documentation des fonctionnalités d'édition de ligne de commande au niveau utilisateur ainsi que de toutes les options de configuration utilisateur se trouve dans la page man tecla(7). Cette page man concerne la documentation destinée aux programmeurs souhaitant utiliser cette bibliothèque dans leur application. UN E

L'EXEMPLE

Les descriptions des fonctions utilisées dans l'exemple sont les suivantes

  GetLine *new_GetLine(size_t linelen, size_t

Cette fonction crée les ressources utilisées par la fonction gl_get_line() et retourne un pointeur opaque vers l'objet qui les contient. alloué.

Cette fonction supprime les ressources qui ont été retournées par un appel précédent à new_GetLine(). Elle retourne toujours NULL (c'est-à-dire un objet supprimé). Elle ne fait rien si l'argument gl est NULL

  char *gl_get_line(GetLine *gl, const char *prompt,

La fonction gl_get_line() peut être appelée un nombre quelconque de fois pour lire la saisie de l'utilisateur. L'argument gl doit avoir été précédemment retourné par un appel à new_GetLine(). L'argument prompt doit être une chaîne normale terminée par NUL, spécifiant le invite à présenter à l'utilisateur. Par défaut, les invites sont affichées littéralement, mais si activées avec la fonction gl_prompt_style() (voir plus loin), les invites peuvent contenir des directives pour souligner, passer en caractères gras et en revenir, ou activer et désactiver la mise en

évidence.

Si vous souhaitez spécifier le contenu initial de la ligne pour que l'utilisateur la modifie, passez la chaîne souhaitée via l'argument start_line. Vous pouvez ensuite spécifier le caractère de cette ligne où le curseur est initialementioned over, using the start_pos argument. This should be -1 if you want the cursor to follow the last character of the start line. If you don't want to preload the line in this manner, send start_line as NULL, and set start_pos to -1. Note that the line pointer returned by one call to gl_get_line() can be passed back to the next call to gl_get_line() via the start_line. This allows the application to take the last entered line, and if it contains an error, to then present it back to the user for re-editing, with the cursor initially positioned where the error was

encountered.

La fonction gl_get_line() renvoie un pointeur vers la ligne saisie par l'utilisateur, ou NULL en cas d'erreur ou à la fin de la saisie. Le pointeur renvoyé fait partie de l'objet ressource gl spécifié et ne doit donc pas être libéré par l'appelant, ni supposé inchangé d'un appel au suivant. Lors de la lecture depuis un utilisateur sur un terminal, il y aura toujours un caractère de nouvelle ligne à la fin de la ligne renvoyée. Lorsque l'entrée standard provient d'un tube ou d'un fichier, il y aura également une nouvelle ligne, sauf si la ligne d'entrée était trop longue pour être stockée dans le tampon interne. Dans ce dernier cas, vous devriez appeler gl_get_line() à nouveau pour lire le reste de la ligne. Notez que ce comportement rend gl_get_line() similaire à fgets(). En fait, lorsque stdin n'est pas connecté à un terminal,gl_get_line() appelle simplement fget

s(

SOURCES DE CONFIGURATION

ALTERNATIVES

Comme mentionné ci-dessus, par défaut les utilisateurs ont la possibilité de configurer le comportement de gl_get_line() via un fichier de configuration appelé .teclarc dans leurs répertoires personnels. Le fait que toutes les applications partagent ce même fichier de configuration est à la fois un avantage et un inconvénient. Dans la plupart des cas, c'est un avantage, car cela encourage l'uniformité et libère l'utilisateur de devoir configurer chaque application séparément. Dans certaines applications, cependant, ce moyen unique de configuration pose problème. C'est particulièrement vrai pour les logiciels embarqués, où il n'y a pas de système de fichiers pour lire un fichier de configuration, et aussi dans les applications où un choix radicalement différent de mappage des touches est nécessaire pour émuler une interface clavier héritée. Pour prendre en charge de tels cas, la fonction suivante permet à l'application de contrôler d'où les informations de configuration sont

lues. 
  int gl_configure_getline(GetLine *gl,
                           const char *app_string,
                           const char *app_file,
                           const char *user_file)
;

Elle permet aux commandes de configuration qui seraient normalement lues depuis le fichier ~/.teclarc de l'utilisateur, d'être lues depuis une chaîne, un fichier de configuration spécifique à l'application, et/ou un fichier de configuration spécifique à l'utilisateur, ou d'aucun de ces éléments. Si cette fonction est appelée avant le premier appel à gl_get_line(), le comportement par défaut de lecture de ~/.teclarc lors du premier appel à gl_get_line() est désactivé ; toute la configuration doit donc être réalisée à l'aide des sources de configuration spécifiées avec cette

fonction.

Si app_string != NULL, alors il est interprété comme une chaîne contenant une ou plusieurs commandes de configuration, séparées les unes des autres dans la chaîne par des caractères de nouvelle ligne intégrés. Si app_file != NULL alors il est interprété comme le chemin complet d'un fichier de configuration spécifique à l'application. Si user_file != NULL alors il est interprété comme le chemin complet d'un fichier de configuration spécifique à l'utilisateur, tel que ~/.teclarc. Par exemple, dans l'appel

suivant, 
  gl_configure_getline(gl, "edit-mode vi \n nobeep",
                           "/usr/share/myapp/teclarc",
                           "~/.teclarc")
;

l'argument app_string fait démarrer l'application appelante en mode d'édition vi, au lieu du mode emacs par défaut, et désactive l'utilisation de la cloche du terminal par la bibliothèque. Elle tente ensuite de lire les commandes de configuration au niveau système depuis un fichier facultatif appelé /usr/share/myapp/teclarc, puis lit enfin les commandes de configuration spécifiques à l'utilisateur depuis un fichier .teclarc facultatif dans le répertoire personnel de l'utilisateur. Notez que les arguments sont listés par ordre de priorité croissante, le contenu de app_string pouvant potentiellement être remplacé par des commandes dans app_file, et les commandes dans app_file pouvant potentiellement être remplacées par des commandes dans user_file

.

Vous pouvez appeler cette fonction autant de fois que nécessaire, les résultats étant cumulatifs, mais notez que des copies de tout nom de fichier spécifié via le <b>app_file et user_file sont enregistrés en interne pour une utilisation ultérieure par la fonction de liaison de touches read-init-files ; si vous prévoyez d'appeler cette fonction plusieurs fois, assurez-vous que le dernier appel spécifie les noms de fichiers que vous souhaitez relire lorsque l'utilisateur demande que les fichiers de configuration soient

relus.

COMPLÉTION DE MOTS

PERSONNALISÉE

Si dans votre application, vous souhaitez que la complétion par TAB complète d'autres éléments en plus des noms de fichiers ou à leur place, vous pouvez organiser cela en enregistrant une fonction de rappel de complétion alternative, via un appel à la fonction gl_customize_c

ompletion(). 
  int gl_customize_completion(GetLine *gl, void *data,
                              CplMatchFn *match_fn)
;

L'argument data fournit un moyen à votre application de passer des informations arbitraires spécifiques à l'application à la fonction de rappel. Celles-ci sont transmises à la fonction de rappel à chaque fois qu'elle est appelée. Elle peut par exemple, pointer vers la table de symboles à partir de laquelle les complétions possibles doivent être recherchées. L'argument match_fn spécifie la fonction de rappel à appeler. Le type de fonction CplMatchFn est défini dans libtecla.h, tout comme une macro CPL_MATCH_FN() que vous pouvez utiliser pour déclarer et prototyper des fonctions de rappel. La déclaration et les responsabilités des fonctions de rappel sont décrites en profondeur dans la page de man cpl_complete_word(3)

.

En bref, la fonction de rappel est responsable de la recherche vers l'arrière dans la ligne d'entrée, en remontant depuis le point où l'utilisateur a appuyé sur TAB, pour trouver le début du mot en cours de complétion. Elle doit ensuite rechercher les complétions possibles de ce mot et les enregistrer une par une dans l'objet WordCompletion qui lui est passé en argument, en appelant la fonction cpl_add_completion(). Si la fonction de rappel souhaite fournir une complétion de nom de fichier en plus de ses propres complétions spécifiques, elle a la possibilité d'appeler elle-même la fonction de rappel de complétion de nom de fichier intégrée. Ceci est également documenté dans la page de man cpl_complete_w

ord(3).

Notez que si vous souhaitez que gl_get_line() renvoie la ligne d'entrée actuelle lorsqu'une complétion réussie a été effectuée, vous pouvez organiser cela lorsque vous appelez cpl_add_completion(), en faisant du dernier caractère du suffixe de continuation un caractère de nouvelle ligne. Si vous faites cela, la ligne d'entrée sera mise à jour pour afficher la complétion, ainsi que tout suffixe de continuation jusqu'au caractère de nouvelle ligne, puis gl_get_line() renverra cette ligne

d'entrée.

Si, pour une raison quelconque, votre fonction de rappel doit écrire quelque chose sur le terminal, elle doit appeler gl_normal_io() avant de le faire. Cela commencera une nouvelle ligne après la ligne d'entrée actuellement en cours d'édition, rétablira les E/S normales du terminal, et indiquera à gl_get_line() que la ligne d'entrée devra être r

edessinée lorsque la fonc
tion de rappel retournera.

AJOUTER DES ACTIONS DE

COMPLÉTION

Dans la section précédente, la capacité à personnaliser le comportement de la seule action de complétion par défaut, complete-word, a été décrite. Dans cette section, la capacité à installer des fonctions d'action supplémentaires, afin que différents types de complétion de mots puissent être liés à différentes séquences de touches, est décrite. Cela est réalisé en utilisant la fonction gl_completion_action()

. 
  int gl_completion_action(GetLine *gl,
                           void *data, CplMatchFn *match_fn,
                           int list_only, const char *name,
                           const char *keyseq)
;

Les arguments data et match_fn sont tels que décrits dans la page de man cpl_complete_word, et spécifient la fonction de rappel qui doit être invoquée pour identifier les complétions possibles. L'argument list_only détermine si l'action en cours de définition doit tenter de compléter le mot aussi loin que possible dans la ligne d'entrée avant d'afficher d'éventuelles complétions ambiguës, ou si elle doit simplement afficher la liste des complétions possibles sans toucher à la ligne d'entrée. La première option est sélectionnée en spécifiant une valeur de 0, et la seconde en spécifiant une valeur de 1. L'argument name spécifie le nom par lequel les fichiers de configuration et les futures invocations de cette fonction doivent se référer à l'action. Il doit s'agir soit du nom d'une action de complétion existante à modifier, soit d'un nouveau nom non utilisé pour une nouvelle action. Enfin, l'argument keyseq spécifie la séquence de touches par défaut à laquelle lier l'action. Si c'est NULL, aucune nouvelle séquence de touches ne sera liée à

l'action.

Attention, pour que l'utilisateur puisse changer la séquence de touches liée aux actions installées de cette manière, lorsque vous appelez gl_completion_action() pour installer une action donnée pour la première fois, vous devriez le faire entre l'appel à new_GetLine() et le premier appel à gl_get_line(). Sinon, lorsque le fichier de configuration de l'utilisateur est lu lors du premier appel à gl_get_line(), le nom de votre action supplémentaire ne sera pas connu, et toute référence à celle-ci dans le fichier de configuration générera une

erreur.

vant de l

DÉFINIR DES ACTIONS

PERSONNALISÉES

Bien que les actions de liaison de touches intégrées soient suffisantes pour les besoins de la plupart des applications, une application spécialisée peut parfois avoir besoin de définir une ou plusieurs actions personnalisées, liées à des séquences de touches spécifiques à l'application. Par exemple, une application de vente bénéficierait d'une séquence de touches affichant le nom de la pièce correspondant à un numéro de pièce situé avant le curseur. Une telle fonctionnalité dépasse clairement le cadre des fonctions d'action intégrées. Ainsi, pour de tels cas particuliers, la fonction gl_register_action() est

fournie. 
  int gl_register_action(GetLine *gl, void *data,
			 GlActionFn *fn, const char *name,
			 const char *keyseq)
;

Cette fonction permet à l'application d'enregistrer une fonction externe, fn, qui sera ensuite appelée chaque fois que soit la séquence de touches spécifiée, keyseq, est saisie par l'utilisateur, soit l'utilisateur saisit une autre séquence de touches qu'il lie ensuite à le nom d'action spécifié, name, dans son fichier de configuration. L'argument data peut être un pointeur vers n'importe quoi que l'application souhaite voir transmis à la fonction d'action, fn, chaque fois que cette fonction est

invoquée.

La fonction d'action, fn, devrait être déclarée en utilisant la macro suivante, qui est définie dans libtecl

a.h. 
  #define GL_ACTION_FN(fn) GlAfterAction (fn)(GetLine *gl, \
              void *data, int count, size_t curpos, \
              const char
*line)

Les arguments gl et data sont ceux qui ont été précédemment passés à gl_register_action() lorsque la fonction d'action a été enregistrée. L'argument count est un argument numérique que l'utilisateur a la possibilité de saisir en utilisant l'action digit-argument, avant d'invoquer l'action. Si l'utilisateur n'entre pas de nombre, alors l'argument count est défini à 1. Nominalement, cet argument est interprété comme un nombre de répétitions, signifiant que l'action doit être répétée ce nombre de fois. En pratique cependant, pour certaines actions, un nombre de répétitions n'a que peu de sens. Dans de tels cas, les actions peuvent soit simplement ignorer l'argument count, ou utiliser sa valeur à une autre

fin.

Une copie de la ligne d'entrée actuelle est passée dans l'argument en lecture seule line. La position actuelle du curseur dans cette chaîne est donnée par l'index contenu dans l'argument curpos. Notez que la manipulation directe de la ligne d'entrée et de la position du curseur n'est pas autorisée. C'est parce que les règles dictées par divers modes, comme le mode vi par rapport au mode emacs, le mode sans écho, et le mode insertion par rapport au mode surimpression etc, rendent la tâche trop complexe pour un développeur d'application d'écrire une action d'édition conforme, tout en limitant les changements futurs aux internes de gl_get_line(). Une solution potentielle à ce dilemme serait de permettre à la fonction d'action d'éditer la ligne en utilisant les actions d'édition existantes. Cela est actuellement à

l'étude.

Si la fonction d'action souhaite écrire du texte sur le terminal, sans que cela se mélange avec le texte affiché de la ligne d'entrée, ou lire depuis le terminal sans avoir à gérer les E/S brutes du terminal, alors avant de faire l'une ou l'autre de ces opérations, elle doit suspendre temporairement l'édition de ligne en appelant la fonction gl_normal_io(). Cette fonction vide toute sortie en attente vers le terminal, déplace le curseur au début de la ligne qui suit la dernière ligne du terminal de la ligne d'entrée, puis restaure le terminal à un état adapté à l'utilisation avec les fonctionnalités stdio C. Cela inclut des choses comme la restauration du mappage normal de \n vers \r\n, et, en mode serveur, la restauration de la forme bloquante normale des E/S du terminal. Après avoir appelé cette fonction, la fonction d'action peut lire depuis et écrire vers le terminal sans craindre de faire un désordre. Il n'est pas nécessaire pour la fonction d'action de restaurer l'environnement d'édition original avant de retourner. Cela est fait automatiquement par gl_get_line() après le retour de la fonction d'action. Voici un exemple simple d'une fonction d'action qui écrit la phrase "Hello world" sur une nouvelle ligne du terminal après la ligne en cours d'édition. Lorsque cette fonction retourne, la ligne d'entrée est redessinée sur la ligne qui suit la ligne "Hello world", et l'édition de ligne

reprend. 
  static GL_ACTION_FN(say_hello_fn)
  {
    if(gl_normal_io(gl))   /* Suspendre temporairement l'édition */
      return GLA_ABORT;
    printf("Hello world\n");
    return GLA_CONTINUE;
}

Les fonctions d'action doivent retourner l'une des valeurs suivantes, pour indiquer à gl_get_line() comment

procéder. 
  GLA_ABORT     -   Faire en sorte que gl_get_line() retourne NULL.
  GLA_RETURN    -   Faire en sorte que gl_get_line() retourne la
                    ligne d'entrée complétée.
  GLA_CONTINUE  -   Reprendre l'édition de la ligne de
commande.

Notez que l'argument name de gl_register_action() spécifie le nom par lequel un utilisateur peut référencer l'action dans son fichier de configuration. Cela lui permet de réassocier l'action à une séquence de touches alternative. Pour que cela fonctionne, il est nécessaire d'appeler gl_register_action() entre l'appel à new_GetLine() et le premier appel à gl_get_

lin
e().

ARCHIVAGE MANUEL DE

L'HISTORIQUE

Par défaut, chaque fois qu'une ligne est saisie par l'utilisateur, elle est automatiquement ajoutée à la liste d'historique, juste avant que gl_get_line() retourne la ligne à l'appelant. C'est pratique pour la majorité des applications, mais il existe aussi des applications nécessitant un contrôle plus fin sur ce qui est ajouté à la liste d'historique. Dans de tels cas, l'ajout automatique des lignes saisies à la liste d'historique peut être désactivé en appelant la fonction gl_automatic

  int gl_automatic_history(GetLine *gl, int enable)
;

Si cette fonction est appelée avec son argument enable défini à 0, gl_get_line() n'archivera pas automatiquement les lignes saisies ultérieurement. L'archivage automatique peut être réactivé plus tard, en appelant à nouveau cette fonction, avec son argument enable défini à 1. Pendant que l'archivage automatique de l'historique est désactivé, l'application appelante peut utiliser gl_append_history() pour ajouter des lignes à la liste d'historique selon les

besoins. 
  int gl_append_history(GetLine *gl, const char *line)
;

L'argument line spécifie la ligne à ajouter à la liste d'historique. Cela doit être une chaîne normale terminée par ' '. Si cette chaîne contient des caractères de nouvelle ligne, la ligne archivée dans la liste d'historique sera terminée par le premier d'entre eux. Sinon, elle sera terminée par le terminateur ' '. Si la ligne est plus longue que la longueur maximale de ligne d'entrée, qui a été spécifiée lorsque new_GetLine() a été appelée, lorsque la ligne sera rappelée, elle sera tronquée à la longueur réelle de la ligne de gl_get_li

ne().

En cas de succès, gl_append_history() retourne 0. Sinon, elle retourne une valeur non nulle, et définit errno à l'une des valeurs

suivantes. 
   EINVAL  -  L'un des arguments passés à
              gl_append_history() était NULL.
   ENOMEM  -  La ligne spécifiée était plus longue que la taille
              allouée du tampon d'historique (telle que spécifiée lorsque
              new_GetLine() a été appelée), elle n'a donc pas pu être
archivée.

Une description textuelle de l'erreur peut être obtenue en appelant éventuellement gl_error_message(). Notez qu'après une telle erreur, la liste d'historique reste dans un état valide pour recevoir de nouvelles lignes d'historique, il y a donc peu d'inconvénient à simplement ignorer le statut de retour de gl_append_

CHANGER DE

TERMINAL

La fonction constructeur new_GetLine() suppose que l'entrée doit être lue depuis stdin, et que la sortie est écrite vers stdout. La fonction suivante permet de basculer vers des flux d'entrée et de sortie

Cela ne fait aucun mal, mais cela a un peu un air laid, ce qui explique pourquoi la combinaison GL_SUSPEND_INPUT est préférable si vous savez que vous allez toujours écrire sur le

terminal.

TRAITEMENT FIABLE DES

SIGNAUX

Le traitement des signaux est étonnamment difficile à réaliser de manière fiable sans conditions de course. Dans gl_get_line(), beaucoup d'attention a été portée pour permettre aux applications d'effectuer un traitement fiable des signaux autour de gl_get_line(). Cette section explique comment tirer parti de

cela.

À titre d'exemple des problèmes qui peuvent survenir si l'application n'est pas écrite correctement, imaginez qu'une application ait un gestionnaire de signal SIGINT qui définit un drapeau global. Supposons maintenant que l'application teste ce drapeau juste avant d'invoquer gl_get_line(). Si un signal SIGINT est reçu dans la petite fenêtre de temps entre l'instruction qui teste la valeur de ce drapeau et l'instruction qui appelle gl_get_line(), alors gl_get_line() ne verra pas le signal et ne sera pas interrompu. En conséquence, l'application ne pourra pas répondre au signal tant que l'utilisateur n'aura pas terminé la saisie de la ligne et gl_get_line() n'aura pas retourné. Selon l'application, cela peut ou non être un désastre, mais au minimum cela déroutera

l'utilisateur.

La manière d'éviter ces problèmes est de faire ce qui

suit.

1. Si nécessaire, utilisez la fonction gl_trap_signal() pour
configurer gl_get_line() afin qu'il interrompe lorsque des
signaux importants sont

interceptés.

automatiquement pendant les périodes où gl_get_line()
attend une entrée/sortie. Cela peut être fait soit

   d'intérêt.

Sur la plupart des systèmes, la combinaison de l'ioctl TIOCGWINSZ et du signal SIGWINCH est utilisée pour maintenir une idée précise de la taille du terminal. La taille du terminal est interrogée à nouveau chaque fois que gl_get_line() est appelée et à chaque réception d'un signal SIGWINCH.

Sur les quelques systèmes où ce mécanisme n'est pas disponible, au démarrage, new_GetLine() recherche d'abord les variables d'environnement LINES et COLUMNS. Si celles-ci ne sont pas trouvées, ou si elles contiennent des valeurs inutilisables, alors si une base de données d'informations de terminal comme terminfo ou termcap est disponible, la taille par défaut du terminal est recherchée dans cette base de données. Si cela échoue également à fournir la taille du terminal, une taille par défaut de 80 colonnes par 24 lignes est utilisée.

Même sur les systèmes qui prennent en charge ioctl(TIOCGWINSZ), si le terminal se trouve à l'autre bout d'une ligne série, le pilote de terminal n'a généralement aucun moyen de détecter quand un redimensionnement se produit ou de demander quelle est la taille actuelle. Dans de tels cas, aucun SIGWINCH n'est envoyé au processus, et les dimensions renvoyées par ioctl(TIOCGWINSZ) ne sont pas correctes. La seule façon de gérer de telles instances est de fournir un moyen à l'utilisateur de saisir une commande qui indique au système distant quelle est la nouvelle taille. Cette commande appellerait alors la fonction gl_set_term_size() pour informer gl_get_line() du changement de taille.

  int gl_set_term_size(GetLine *gl, int ncolumn, int nline);

Les arguments ncolumn et nline sont utilisés pour spécifier les nouvelles dimensions du terminal, et ne doivent pas être inférieurs à 1. Sur les systèmes qui prennent en charge ioctl(TIOCGWINSZ), cette fonction appelle d'abord ioctl(TIOCSWINSZ) pour informer le pilote de terminal du changement de taille. En mode d'E/S serveur non bloquant, si une ligne est actuellement en cours de saisie, la ligne de saisie est alors redessinée pour s'adapter à la taille modifiée. Enfin, les nouvelles valeurs sont enregistrées dans gl pour une utilisation future par gl_get_line().

La fonction gl_terminal_size() vous permet d'interroger la taille actuelle du terminal et d'installer une taille de secours alternative pour les cas où la taille n'est pas disponible. Attention, la taille du terminal ne sera pas disponible lors de la lecture à partir d'un pipe ou d'un fichier, de sorte que les valeurs par défaut peuvent être importantes même sur les systèmes qui prennent en charge les moyens de connaître la taille du terminal.

  typedef struct {
    int nline;        /* Le terminal a nline lignes */
    int ncolumn;      /* Le terminal a ncolumn colonnes */
  } GlTerminalSize;
  GlTerminalSize gl_terminal_size(GetLine *gl,
                                  int def_ncolumn,
                                  int def_nline);

Cette fonction met d'abord à jour les dimensions du terminal de secours de gl_get_line(), puis enregistre ses découvertes dans la valeur de retour.

Les arguments def_ncolumn et def_nline spécifient le nombre par défaut de colonnes et de lignes de terminal à utiliser si la taille du terminal ne peut pas être déterminée via ioctl(TIOCGWINSZ) ou les variables d'environnement.

MASQUER CE QUE VOUS TAPEZ

Lors de la saisie d'informations sensibles, telles que des mots de passe, il est préférable de ne pas afficher le texte que vous saisissez sur le terminal. De plus, un tel texte ne doit pas être enregistré dans la liste d'historique, car quelqu'un trouvant votre terminal sans surveillance pourrait alors le rappeler, ou quelqu'un fouillant dans vos répertoires pourrait le voir dans votre fichier d'historique. Dans cet esprit, la fonction gl_echo_mode() vous permet d'activer et de désactiver l'affichage et l'archivage de tout texte saisi ultérieurement dans les appels à gl_get_line().

  int gl_echo_mode(GetLine *gl, int enable);

L'argument enable spécifie si le texte saisi doit être visible ou non. S'il est à 0, alors les lignes saisies ultérieurement ne seront pas visibles sur le terminal, et ne seront pas enregistrées dans la liste d'historique. S'il est à 1, alors les lignes saisies ultérieures seront affichées au fur et à mesure de leur saisie, et à condition que l'historique n'ait pas été désactivé via un appel à gl_toggle_history(), elles seront également archivées dans la liste d'historique. Enfin, si l'argument enable est à -1, alors le mode d'écho est laissé inchangé, ce qui vous permet d'interroger le réglage actuel de manière non destructive via la valeur de retour. Dans tous les cas, la valeur de retour de la fonction est 0 si l'écho a été désactivé avant que la fonction ne soit appelée, et 1 s'il était activé.

Lorsque l'écho est désactivé, notez que bien que la complétion par tabulation complétera invisiblement votre préfixe autant que possible, les complétions ambiguës ne seront pas affichées.

INTERROGATIONS POUR UN SEUL CARACTÈRE

Utiliser gl_get_line() pour demander à l'utilisateur une réponse d'un seul caractère est gênant pour l'utilisateur, car il doit appuyer sur la touche Entrée ou Retour avant que le caractère qu'il a tapé ne soit renvoyé au programme. Ainsi, la fonction gl_query_char() a été fournie pour des requêtes de caractères uniques comme celle-ci.

  int gl_query_char(GetLine *gl, const char *prompt,
                    char defchar);

Cette fonction affiche l'invite spécifiée au début d'une nouvelle ligne, et attend que l'utilisateur tape un caractère. Lorsque l'utilisateur tape un caractère, gl_query_char() l'affiche à droite de l'invite, commence une nouvelle ligne, puis renvoie le caractère au programme appelant. La valeur de retour de la fonction est le caractère qui a été tapé. Si la lecture a dû être interrompue pour une raison quelconque, EOF est renvoyé à la place. Dans ce dernier cas, l'application peut appeler la fonction précédemment documentée gl_return_status(), pour savoir ce qui s'est mal passé. Il pourrait s'agir, par exemple, de la réception d'un signal, ou du déclenchement de la minuterie d'inactivité optionnelle.

Si l'utilisateur appuie simplement sur Entrée, la valeur de l'argument defchar est substituée. Cela signifie que lorsque l'utilisateur appuie sur Nouvelle ligne ou Retour, le caractère spécifié dans defchar est affiché après l'invite, comme si l'utilisateur l'avait tapé, et est également renvoyé à l'application appelante. Si un tel remplacement n'est pas important, passez simplement '0 comme valeur de defchar.

Si le caractère saisi est un caractère non imprimable, il est affiché symboliquement. Par exemple, control-A est affiché comme ^A, et les caractères au-delà de 127 sont affichés en octal, précédés d'une barre oblique inverse.

Comme avec gl_get_line(), l'écho du caractère saisi peut être désactivé à l'aide de la fonction gl_echo_mode().

Si le processus appelant est suspendu en attendant que l'utilisateur tape sa réponse, le curseur est déplacé sur la ligne suivant la ligne d'invite, puis lorsque le processus reprend, l'invite est redressée, et gl_query_char() reprend l'attente que l'utilisateur tape un caractère.

Notez qu'en mode serveur non bloquant (voir gl_io_mode(3)), si une ligne d'entrée incomplète est en cours de lecture lorsque gl_query_char() est appelée, la ligne d'entrée partielle est ignorée, et effacée du terminal, avant que la nouvelle invite ne soit affichée. Le prochain appel à gl_get_line() commencera donc l'édition d'une nouvelle ligne.

LECTURE DE CARACTÈRES BRUTS

Alors que la fonction gl_query_char() invite visiblement l'utilisateur à saisir un caractère et affiche ce qu'il a tapé, la fonction gl_read_char() lit un caractère de signal de l'utilisateur, sans rien écrire sur le terminal, ni perturber une ligne d'entrée partiellement saisie. Cela signifie qu'elle peut être appelée non seulement entre des appels à gl_get_line(), mais aussi depuis des fonctions de rappel que l'application a enregistrées pour être appelées par gl_get_line().

  int gl_read_char(GetLine *gl);

En cas de succès, la valeur de retour de gl_read_char() est le caractère lu. En cas d'échec, EOF est renvoyé, et la fonction gl_return_status() peut être appelée pour savoir ce qui s'est mal passé. Les possibilités incluent le déclenchement de la minuterie d'inactivité optionnelle, la réception d'un signal configuré pour interrompre gl_get_line(), ou le blocage des E/S du terminal, en mode E/S serveur non bloquant.

Entre les appels à gl_get_line(), la fonction gl_display_text() fournit un moyen pratique d'afficher des paragraphes de texte, justifiés à gauche et répartis sur une ou plusieurs lignes du terminal selon les contraintes de la largeur courante du terminal. Des exemples d'utilisation de cette fonction se trouvent dans les programmes de démonstration, où elle est utilisée pour afficher des introductions. Dans ces exemples, l'utilisation avancée de préfixes, suffixes et lignes de remplissage optionnels pour dessiner un cadre autour du texte est également

L' argument indentation spécifie le nombre de caractères à utiliser pour indenter chaque ligne de sortie. L' argument fill_char spécifie le caractère qui sera utilisé pour effectuer cette

JEUX DE CARACTÈRES

INTERNATIONAUX

Depuis la version 1.4.0 de libtecla, gl_get_line() est propre aux 8 bits. Cela signifie que tous les caractères 8 bits imprimables dans la locale actuelle de l'utilisateur sont désormais affichés tels quels et inclus dans la ligne de saisie renvoyée. En supposant que le programme appelant contient correctement un appel comme le

suivant, 
  setlocale(LC_CTYPE, "")
;

alors la locale courante est déterminée par la première des variables d'environnement LC_CTYPE, LC_ALL et LANG dont on trouve qu'elle contient un nom de locale valide. Si aucune de ces variables n'est définie, ou si le programme néglige d'appeler setlocale, alors la locale par défaut C est utilisée, qui est l'ASCII 7 bits américain. Sur la plupart des plateformes de type unix, vous pouvez obtenir une liste des locales valides en tapant la commande

: 
  locale
-a

à l'invite du shell. Une documentation supplémentaire sur la manière dont l'utilisateur peut utiliser cela pour saisir des caractères internationaux se trouve dans la page de manuel tecl

SÉCURITÉ DES

THREADS

Dans un programme multi-thread, vous devriez utiliser la version libtecla_r.a de la bibliothèque. Celle-ci utilise des versions réentrantes des fonctions système, lorsqu'elles sont disponibles. Malheureusement, ni terminfo ni termcap n'ont été conçus pour être réentrants, vous ne

pouvez donc pas utiliser en toute sécurité les fonctions du module getline dans plusieurs threads (vous pouvez utiliser les modules séparés d'expansion de fichiers et de complétion de mots dans plusieurs threads, voir les pages de manuel correspondantes pour plus de détails). Cepen
dant, en raison de l'utilisation de fonctions POSIX réentrantes pour la recherche de répertoires personnels, etc., il est sûr d'utiliser ce module depuis un seul thread d'un programme multi-thread, à condition que vos autres threads n'utilisent aucune fonction termcap ou terminfo.
