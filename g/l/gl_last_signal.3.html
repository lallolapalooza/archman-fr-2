DESCRIPTION

La fonction gl_get_line() fait partie de la bibliothèque tecla (voir la page de manuel libtecla(3)). Si l'utilisateur tape au terminal, chaque appel lui présente une ligne d'entrée, puis fournit des facilités d'édition interactives, similaires à celles du shell UNIX tcsh. En plus de l'édition de ligne de commande simple, elle prend en charge le rappel des lignes de commande précédemment saisies, la complétion par TAB des noms de fichiers, et l'expansion des noms de fichiers par jokers en ligne. La documentation des fonctionnalités d'édition de ligne de commande au niveau utilisateur et de toutes les options de configuration utilisateur se trouve dans la page de manuel tecla(7). Cette page de manuel se concentre sur la documentation pour les programmeurs intéressés par l'utilisation de cette bibliothèque dans leur application.

UN EXEMPLE

Ce qui suit montre un exemple complet d'utilisation de la fonction gl_get_line() pour obtenir une entrée de l'utilisateur :

  #include <stdio.h>
  #include <locale.h>
  #include <libtecla.h>
  int main(int argc, char *argv[])
  { 
    char *line;    /* La ligne que l'utilisateur a tapée */
    GetLine *gl;   /* L'objet ressource de gl_get_line() */
    setlocale(LC_CTYPE, ""); /* Adopter le choix de l'utilisateur */
                             /* de jeu de caractères. */
    gl = new_GetLine(1024, 2048);
    if(!gl)
      return 1;
    while((line=gl_get_line(gl, "$ ", NULL, -1)) != NULL &&
           strcmp(line, "exit\n") != 0)
      printf("Vous avez tapé : %s\n", line);
    gl = del_GetLine(gl);
    return 0;
  }

Dans l'exemple, d'abord les ressources nécessaires à la fonction gl_get_line() sont créées en appelant new_GetLine(). Cela alloue la mémoire utilisée dans les appels ultérieurs à la fonction gl_get_line(), y compris le tampon d'historique pour enregistrer les lignes précédemment saisies. Ensuite, une ou plusieurs lignes sont lues depuis l'utilisateur, jusqu'à ce qu'une erreur survienne, ou que l'utilisateur tape exit. Puis, enfin, les ressources qui ont été allouées par new_GetLine() sont retournées au système en appelant del_GetLine(). Notez l'utilisation de la valeur de retour NULL de del_GetLine() pour rendre gl NULL. C'est une précaution de sécurité. Si le programme tente ensuite de passer gl à gl_get_line(), ladite fonction se plaindra et retournera une erreur, au lieu de tenter d'utiliser l'objet ressource supprimé.

LES FONCTIONS UTILISÉES DANS L'EXEMPLE

Les descriptions des fonctions utilisées dans l'exemple sont les suivantes :

  GetLine *new_GetLine(size_t linelen, size_t histlen)

Cette fonction crée les ressources utilisées par la fonction gl_get_line() et retourne un pointeur opaque vers l'objet qui les contient. La longueur maximale d'une ligne d'entrée est spécifiée via l'argument linelen, et le nombre d'octets à allouer pour stocker les lignes d'historique est défini par l'argument histlen. Les lignes d'historique sont stockées bout à bout dans un seul tampon de cette taille. Notez que cela signifie que le nombre de lignes d'historique qui peuvent être stockées à tout moment dépend des longueurs des lignes individuelles. Si vous voulez placer une limite supérieure au nombre de lignes qui peuvent être stockées, voir la fonction gl_limit_history() décrite plus loin. Si vous ne voulez pas d'historique du tout, spécifiez histlen comme zéro, et aucun tampon d'historique ne sera alloué.

En cas d'erreur, un message est affiché sur stderr et NULL est retourné.

  GetLine *del_GetLine(GetLine *gl)

Cette fonction supprime les ressources retournées par un appel précédent à new_GetLine(). Elle retourne toujours NULL (c'est-à-dire un objet supprimé). Elle ne fait rien si l'argument gl est NULL.

  char *gl_get_line(GetLine *gl, const char *prompt,
                   const char *start_line, int start_pos);

La fonction gl_get_line() peut être appelée un nombre quelconque de fois pour lire l'entrée de l'utilisateur. L'argument gl doit avoir été précédemment retourné par un appel à new_GetLine(). L'argument prompt doit être une chaîne normale terminée par NUL, spécifiant l'invite à présenter à l'utilisateur. Par défaut, les invites sont affichées littéralement, mais si elles sont activées avec la fonction gl_prompt_style() (voir plus loin), les invites peuvent contenir des directives pour faire du soulignement, passer du gras et revenir à la police normale, ou activer et désactiver la mise en évidence.

Si vous souhaitez spécifier le contenu initial de la ligne, que l'utilisateur peut modifier, passez la chaîne souhaitée via l'argument start_line. Vous pouvez ensuite spécifier à quel caractère de cette ligne le curseur est initialement positionné

Si vous ne voulez pas précharger la ligne de cette manière, envoyez start_line comme NULL, et définissez start_pos à -1. Notez que le pointeur de ligne retourné par un appel à gl_get_line() peut être passé à l'appel suivant à gl_get_line() via le start_line. Cela permet à l'application de prendre la dernière ligne saisie, et si elle contient une erreur, de la présenter à nouveau à l'utilisateur pour réédition, avec le curseur initialement positionné à l'endroit où l'erreur a été rencontrée.

La gl_get_line() fonction retourne un pointeur vers la ligne saisie par l'utilisateur, ou NULL en cas d'erreur ou à la fin de l'entrée. Le pointeur retourné fait partie de l'objet ressource gl spécifié, et ne doit donc pas être libéré par l'appelant, ni supposé invariable d'un appel au suivant. Lors de la lecture depuis un utilisateur sur un terminal, il y a toujours un caractère de nouvelle ligne à la fin de la ligne retournée. Lorsque l'entrée standard provient d'un pipe ou d'un fichier, il y aura de même une nouvelle ligne, sauf si la ligne d'entrée était trop longue pour être stockée dans le tampon interne. Dans ce dernier cas, vous devriez appeler gl_get_line() à nouveau pour lire le reste de la ligne. Notez que ce comportement rend gl_get_line() similaire à fgets(). En fait, lorsque stdin n'est pas connecté à un terminal,gl_get_line() appelle simplement fgets().

L'ÉTAT DE RETOUR DE GL_GET_LINE

Comme décrit ci-dessus, la gl_get_line() fonction a deux valeurs de retour possibles ; un pointeur vers la ligne d'entrée complétée, ou NULL. Des informations supplémentaires sur ce qui a causé gl_get_line() de retourner sont disponibles à la fois en inspectant errno, et en appelant la gl_return_status() fonction.

  GlReturnStatus gl_return_status(GetLine *gl);

Voici les valeurs énumérées possibles que cette fonction retourne.

  GLR_NEWLINE     -  Le dernier appel à gl_get_line()
                     a retourné avec succès une ligne d'entrée
                     complétée.
  GLR_BLOCKED     -  gl_get_line() était en mode serveur non-bloquant
                     et est retourné tôt pour
                     éviter de bloquer le processus pendant
                     l'attente d'E/S sur le terminal. La
                     gl_pending_io() fonction peut être
                     utilisée pour voir quel type d'E/S
                     gl_get_line() attendait.
                     (voir la gl_io_mode(3) page de manuel
                     pour les détails).
  GLR_SIGNAL      -  Un signal a été intercepté par
                     gl_get_line() qui avait une
                     disposition après-signal de
                     GLS_ABORT (Voir gl_trap_signal()).
  GLR_TIMEOUT     -  Le minuteur d'inactivité a expiré pendant que
                     gl_get_line() attendait une
                     entrée, et la fonction de rappel de délai d'attente a retourné GLTO_ABORT.
                     Voir gl_inactivity_timeout() pour
                     des informations sur les délais d'attente.
  GLR_FDABORT     -  Un rappel d'E/S d'application a retourné
                     GLFD_ABORT (voir gl_watch_fd()).
  GLR_EOF         -  Fin de fichier atteinte. Cela peut se produire
                     lorsque l'entrée provient d'un fichier ou d'un
                     pipe, au lieu du terminal. Cela se produit aussi
                     si l'utilisateur invoque les
                     list-or-eof ou del-char-or-list-or-eof
                     actions au début d'une nouvelle ligne.

                     gl_get_line() d'interrompre (consultez
                     errno et/ou
                     gl_error_message() pour les détails.

Quand gl_return_status() retourne GLR_ERROR, et que la valeur de errno n'est pas suffisante pour expliquer ce qui s'est passé, vous pouvez utiliser la fonction gl_error_message() pour demander une description de la dernière erreur survenue.

  const char *gl_error_message(GetLine *gl, char *buff,
                               size_t n);

La valeur de retour est un pointeur vers le message survenu. Si l' buff argument est NULL, ce sera un pointeur vers un tampon à l'intérieur de gl, dont la valeur changera probablement au prochain appel à toute fonction associée à gl_get_line(). Sinon, si un argumentNULL buff non- est fourni, le message d'erreur, y compris le terminateur '\0' , sera écrit dans les premiers n éléments de ce tampon, et la valeur de retour sera un pointeur vers le premier élément de ce tampon. Si le message ne tient pas dans le tampon fourni, il sera tronqué pour tenir.

                        sont incluses dans les chaînes d'invite, sont

SOURCES DE CONFIGURATION ALTERNATIVES

Comme mentionné ci-dessus, par défaut les utilisateurs ont la possibilité de configurer le comportement de gl_get_line() via un fichier de configuration appelé .teclarc dans leurs répertoires personnels. Le fait que toutes les applications partagent ce même fichier de configuration est à la fois un avantage et un inconvénient. Dans la plupart des cas c'est un avantage, car cela encourage l'uniformité, et libère l'utilisateur de la nécessité de configurer chaque application séparément. Dans certaines applications, cependant, ce seul moyen de configuration est un problème. C'est particulièrement vrai pour les logiciels embarqués, où il n'y a pas de système de fichiers pour lire un fichier de configuration, et aussi dans les applications où un choix radicalement différent de mappages de touches est nécessaire pour émuler une interface clavier héritée. Pour prendre en charge de tels cas, la fonction suivante permet à l'application de contrôler d'où les informations de configuration sont lues.

  int gl_configure_getline(GetLine *gl,
                           const char *app_string,
                           const char *app_file,
                           const char *user_file);

Elle permet aux commandes de configuration qui seraient normalement lues depuis le fichier ~/.teclarc d'un utilisateur, d'être lues depuis n'importe lequel ou aucun parmi, une chaîne, un fichier de configuration spécifique à l'application, et/ou un fichier de configuration spécifique à l'utilisateur. Si cette fonction est appelée avant le premier appel à gl_get_line(), le comportement par défaut de lecture de ~/.teclarc au premier appel à gl_get_line() est désactivé, donc toute configuration doit être réalisée en utilisant les sources de configuration spécifiées avec cette fonction.

Si app_string != NULL, alors elle est interprétée comme une chaîne contenant une ou plusieurs commandes de configuration, séparées les unes des autres dans la chaîne par des caractères de nouvelle ligne intégrés. Si app_file != NULL alors elle est interprétée comme le chemin complet d'un fichier de configuration spécifique à l'application. Si user_file != NULL alors elle est interprétée comme le chemin complet d'un fichier de configuration spécifique à l'utilisateur, tel que ~/.teclarc. Par exemple, dans l'appel suivant,

  gl_configure_getline(gl, "edit-mode vi \n nobeep",
                           "/usr/share/myapp/teclarc",
                           "~/.teclarc");

l' app_string argument fait que l'application appelante démarre en mode d'édition vi, au lieu du mode emacs par défaut, et désactive l'utilisation de la cloche du terminal par la bibliothèque. Elle tente ensuite de lire les commandes de configuration à l'échelle du système depuis un fichier optionnel appelé /usr/share/myapp/teclarc, puis lit enfin les commandes de configuration spécifiques à l'utilisateur depuis un fichier .teclarc optionnel dans le répertoire personnel de l'utilisateur. Notez que les arguments sont listés par ordre de priorité croissante, avec le contenu de app_string potentiellement remplacé par des commandes dans app_file, et les commandes dans app_file potentiellement remplacées par des commandes dans user_file.

Vous pouvez appeler cette fonction autant de fois que nécessaire, les résultats étant cumulatifs, mais notez que les copies de tout nom de fichier spécifié via app_fichier et user_file sont enregistrés en interne pour une utilisation ultérieure par la read-init-files fonction de liaison de touches ; si vous prévoyez d'appeler cette fonction plusieurs fois, assurez-vous que le dernier appel spécifie les noms de fichiers que vous souhaitez relire lorsque l'utilisateur demande la relecture des fichiers de configuration.

Des séquences de touches individuelles peuvent également être liées et déliées à l'aide de la gl_bind_keyseq() fonction.

  int gl_bind_keyseq(GetLine *gl, GlKeyOrigin origin,
                     const char *keyseq,
                     const char *action);

L' origin argument spécifie la priorité de la liaison, selon qui elle est établie, et doit être l'une des deux valeurs suivantes.

  GL_USER_KEY   -   L'utilisateur a demandé cette liaison de touches.
  GL_APP_KEY    -   Il s'agit d'une liaison par défaut définie par
                    l'application.

Lorsque des liaisons utilisateur et application ont été spécifiées pour une même séquence de touches, la liaison utilisateur prime. La liaison de l'application est rétablie ultérieurement si la liaison utilisateur est déliée plus tard, soit via un autre appel à cette fonction, soit via un appel à gl_configure_getline().

L' keyseq argument spécifie la séquence de touches à lier ou à délier, et est exprimée de la même manière que dans un fichier de configuration ~/.teclarc . L' action argument doit être soit une chaîne contenant le nom de l'action à laquelle lier la séquence de touches, soit NULL ou "" pour délier la séquence de touches.

COMPLÉTION DE MOTS PERSONNALISÉE

Si dans votre application, vous souhaitez que la complétion par TAB complète d'autres éléments en plus des noms de fichiers, ou à la place de ceux-ci, vous pouvez le faire en enregistrant une fonction de rappel de complétion alternative, via un appel à la gl_customize_completion() fonction.

  int gl_customize_completion(GetLine *gl, void *data,
                              CplMatchFn *match_fn);

L' data argument fournit un moyen à votre application de passer des informations arbitraires spécifiques à l'application à la fonction de rappel. Celles-ci sont transmises à la fonction de rappel à chaque fois qu'elle est appelée. Elles pourraient par exemple pointer vers la table de symboles à partir de laquelle les complétions possibles doivent être recherchées. L' match_fn argument spécifie la fonction de rappel à appeler. Le type de fonction CplMatchFn est défini dans libtecla.h, tout comme une macro CPL_MATCH_FN() que vous pouvez utiliser pour déclarer et prototyper des fonctions de rappel. La déclaration et les responsabilités des fonctions de rappel sont décrites en détail dans la page de manuel cpl_complete_word(3).

En bref, la fonction de rappel est responsable de la recherche vers l'arrière dans la ligne d'entrée, à partir du point où l'utilisateur a appuyé sur TAB, pour trouver le début du mot en cours de complétion. Elle doit ensuite rechercher les complétions possibles de ce mot et les enregistrer une par une dans l'objet WordCompletion qui lui est passé en argument, en appelant la cpl_add_completion() fonction. Si la fonction de rappel souhaite fournir une complétion de nom de fichier en plus de ses propres complétions spécifiques, elle a la possibilité d'appeler elle-même la fonction de rappel de complétion de nom de fichier intégrée. Ceci est également documenté dans la page de manuel cpl_complete_word(3) .

Notez que si vous souhaitez que gl_get_line() retourne la ligne d'entrée actuelle lorsqu'une complétion réussie a été effectuée, vous pouvez le faire lorsque vous appelez cpl_add_completion(), en faisant du dernier caractère du suffixe de continuation un caractère de nouvelle ligne. Si vous faites cela, la ligne d'entrée sera mise à jour pour afficher la complétion, ainsi que tout suffixe de continuation jusqu'au caractère de nouvelle ligne, puis gl_get_line() retournera cette ligne d'entrée.

Si, pour une raison quelconque, votre fonction de rappel doit écrire quelque chose sur le terminal, elle doit appeler gl_normal_io() avant de le faire. Cela démarrera une nouvelle ligne après la ligne d'entrée actuellement en cours d'édition, rétablira l'E/S normale du terminal, et indiquera à gl_get_line() que la ligne d'entrée devra être redessinée lorsque la fonction de rappel retournera.

AJOUTER DES ACTIONS DE COMPLÉTION

Dans la section précédente, la capacité à personnaliser le comportement de la seule action de complétion par défaut, complete-word, a été décrite. Dans cette section, la capacité à installer des fonctions d'action supplémentaires, afin que différents types de complétion de mots puissent être liés à différentes séquences de touches, est décrite. Ceci est réalisé en utilisant la gl_completion_action() fonction.

  int gl_completion_action(GetLine *gl,
                           void *data, CplMatchFn *match_fn,
                           int list_only, const char *name,
                           const char *keyseq);

Les data et match_fn arguments sont comme décrits dans la page de manuel cpl_complete_word , et spécifient la fonction de rappel qui doit être invoquée pour identifier les complétions possibles. L' list_only argument détermine si l'action en cours de définition doit tenter de compléter le mot aussi loin que possible dans la ligne d'entrée avant d'afficher les complétions ambiguës possibles, ou si elle doit simplement afficher la liste des complétions possibles sans toucher à la ligne d'entrée. La première option est sélectionnée en spécifiant une valeur de 0, et la seconde en spécifiant une valeur de 1. L' name argument spécifie le nom par lequel les fichiers de configuration et les futures invocations de cette fonction doivent se référer à l'action. Cela doit être soit le nom d'une action de complétion existante à modifier, soit un nouveau nom non utilisé pour une nouvelle action. Enfin, l' keyseq argument spécifie la séquence de touches par défaut à lier à l'action. Si ceci est NULL, aucune nouvelle séquence de touches ne sera liée à l'action.

Attention, pour que l'utilisateur puisse changer la séquence de touches liée aux actions installées de cette manière, lorsque vous appelez gl_completion_action() pour installer une action donnée pour la première fois, vous devriez le faire entre l'appel à new_GetLine() et le premier appel à gl_get_line(). Sinon, lorsque le fichier de configuration de l'utilisateur est lu lors du premier appel à gl_get_line(), le nom de votre action supplémentaire ne sera pas connu, et toute référence à celle-ci dans le fichier de configuration générera une erreur.

Comme discuté pour gl_customize_completion(), si votre fonction de rappel, pour une raison quelconque, doit écrire quoi que ce soit sur le terminal, elle doit appeler gl_normal_io() avant de le faire.

DÉFINIR DES ACTIONS PERSONNALISÉES

Bien que les actions de liaison de touches intégrées soient suffisantes pour les besoins de la plupart des applications, il arrive occasionnellement qu'une application spécialisée ait besoin de définir une ou plusieurs actions personnalisées, liées à des séquences de touches spécifiques à l'application. Par exemple, une application de vente bénéficierait d'une séquence de touches qui afficherait le nom de la pièce correspondant à un numéro de pièce précédant le curseur. Une telle fonctionnalité dépasse clairement le cadre des fonctions d'action intégrées. Ainsi, pour ces cas particuliers, la gl_register_action() fonction est fournie.

  int gl_register_action(GetLine *gl, void *data,
			 GlActionFn *fn, const char *name,
			 const char *keyseq);

Cette fonction permet à l'application d'enregistrer une fonction externe, fn, qui sera par la suite appelée chaque fois que soit la séquence de touches spécifiée, keyseq, est saisie par l'utilisateur, soit que l'utilisateur saisit toute autre séquence de touches qu'il lie ensuite au nom d'action spécifié, name, dans son fichier de configuration. L' data argument peut être un pointeur vers n'importe quoi que l'application souhaite voir passer à la fonction d'action, fn, chaque fois que cette fonction est invoquée.

La fonction d'action, fn, devrait être déclarée à l'aide de la macro suivante, qui est définie dans libtecla.h.

  #define GL_ACTION_FN(fn) GlAfterAction (fn)(GetLine *gl, \
              void *data, int count, size_t curpos, \
              const char *line)

Les gl et data arguments sont ceux qui ont été précédemment passés à gl_register_action() lorsque la fonction d'action a été enregistrée. L' count argument est un argument numérique que l'utilisateur a la possibilité de saisir à l'aide de l'action digit-argument , avant d'invoquer l'action. Si l'utilisateur n'entre pas de nombre, alors l' count argument est défini à 1. Nominalement, cet argument est interprété comme un nombre de répétitions, ce qui signifie que l'action devrait être répétée ce nombre de fois. En pratique, cependant, pour certaines actions, un nombre de répétitions n'a que peu de sens. Dans de tels cas, les actions peuvent soit simplement ignorer l' count argument, soit utiliser sa valeur à une autre fin.

Une copie de la ligne d'entrée actuelle est passée dans l'argument en lecture seule line . La position actuelle du curseur dans cette chaîne est donnée par l'index contenu dans l' curpos argument. Notez que la manipulation directe de la ligne d'entrée et de la position du curseur n'est pas autorisée. C'est parce que les règles dictées par les différents modes, comme le mode vi par rapport au mode emacs, le mode sans écho, et le mode insertion par rapport au mode surfrappe etc, rendent trop complexe pour un développeur d'application d'écrire une action d'édition conforme, ainsi qu'elles contraignent les changements futurs aux internes de gl_get_line(). Une solution potentielle à ce dilemme serait de permettre à la fonction d'action d'éditer la ligne à l'aide des actions d'édition existantes. Ceci est actuellement à l'étude.

Si la fonction d'action souhaite écrire du texte sur le terminal, sans que cela se mélange avec le texte affiché de la ligne d'entrée, ou lire depuis le terminal sans avoir à gérer l'E/S brute du terminal, alors avant de faire l'une ou l'autre de ces opérations, elle doit suspendre temporairement l'édition de ligne en appelant la gl_normal_io() fonction. Cette fonction vide toute sortie en attente vers le terminal, déplace le curseur au début de la ligne suivant la dernière ligne du terminal de la ligne d'entrée, puis restaure le terminal à un état adapté à l'utilisation avec les fonctions stdio de C. Ce dernier comprend des choses comme la restauration du mappage normal de \n vers \r\n, et, en mode serveur, la restauration de la forme bloquante normale de l'E/S du terminal. Après avoir appelé cette fonction, la fonction d'action peut lire depuis et écrire vers le terminal sans crainte de créer un désordre. Il n'est pas nécessaire pour la fonction d'action de restaurer l'environnement d'édition original avant de retourner. Cela est fait automatiquement par gl_get_line() après le retour de la fonction d'action. Voici un exemple simple d'une fonction d'action qui écrit la phrase "Hello world" sur une nouvelle ligne du terminal après la ligne en cours d'édition. Lorsque cette fonction retourne, la ligne d'entrée est redessinée sur la ligne suivant la ligne "Hello world", et l'édition de ligne reprend.

  static GL_ACTION_FN(say_hello_fn)
  {
    if(gl_normal_io(gl))   /* Suspendre temporairement l'édition */
      return GLA_ABORT;
    printf("Bonjour le monde\n");
    return GLA_CONTINUE;
  }

Les fonctions d'action doivent renvoyer l'une des valeurs suivantes, afin de dire à gl_get_line() comment procéder.

  GLA_ABORT     -   Fait retourner NULL à gl_get_line().
  GLA_RETURN    -   Fait retourner à gl_get_line() la
                    ligne d'entrée complétée.
  GLA_CONTINUE  -   Reprend l'édition de ligne de commande.

Notez que l'argument name de gl_register_action() spécifie le nom par lequel un utilisateur peut faire référence à l'action dans son fichier de configuration. Cela lui permet de remapper l'action à une séquence de touches alternative. Pour que cela fonctionne, il est nécessaire d'appeler gl_register_action() entre l'appel à new_GetLine() et le premier appel à gl_get_line().

FICHIERS HISTORIQUES

Pour sauvegarder le contenu du tampon d'historique avant de quitter votre application, et le restaurer ensuite lors de la prochaine exécution de l'application, les fonctions suivantes sont fournies.

 int gl_save_history(GetLine *gl, const char *filename,
                     const char *comment, int max_lines);
 int gl_load_history(GetLine *gl, const char *filename,
                     const char *comment);

L'argument filename spécifie le nom à donner au fichier d'historique lors de la sauvegarde, ou le nom d'un fichier d'historique existant, lors du chargement. Il peut contenir des expressions de répertoire personnel et de variables d'environnement, telles que "~/.myapp_history" ou "$HOME/.myapp_history".

Avec chaque ligne d'historique, des informations supplémentaires à son sujet, telles que la date de saisie par l'utilisateur et son niveau d'imbrication, sont enregistrées comme commentaire précédant la ligne dans le fichier d'historique. L'écriture sous forme de commentaire permet au fichier d'historique de servir également de fichier de commandes, au cas où vous souhaiteriez rejouer une session entière en l'utilisant. Comme les préfixes de commentaire diffèrent selon les langages, l'argument comment est fourni pour spécifier le préfixe de commentaire. Par exemple, si votre application était un shell Unix, comme le shell Bourne, vous spécifieriez "#" ici. Quelle que soit la valeur choisie pour le caractère de commentaire, vous devez spécifier le même préfixe à gl_load_history() que celui utilisé lors de l'appel à gl_save_history() pour écrire le fichier d'historique.

L'argument max_lines doit être -1 pour spécifier que toutes les lignes de la liste d'historique doivent être sauvegardées, ou un nombre positif spécifiant un plafond sur le nombre de lignes les plus récentes à sauvegarder.

Les deux fonctions renvoient une valeur non nulle en cas d'erreur, après avoir écrit un message d'erreur sur stderr. Notez que gl_load_history() ne considère pas la non-existence d'un fichier comme une erreur.

LISTES HISTORIQUES MULTIPLES

Si votre application utilise un seul objet GetLine pour saisir de nombreux types de lignes différents, vous voudrez peut-être que gl_get_line() distingue les différents types de lignes dans la liste d'historique, et ne rappelle que les lignes qui correspondent au type de ligne actuel. Pour répondre à cette exigence, gl_get_line() marque les lignes enregistrées dans la liste d'historique avec un identifiant entier choisi par l'application. Initialement, cet identifiant est défini à 0 par new_GetLine(), mais il peut être modifié ultérieurement en appelant gl_group_history().

  int gl_group_history(GetLine *gl, unsigned id);

L'identifiant entier id peut être n'importe quel nombre choisi par l'application, mais notez que gl_save_history() et gl_load_history() préservent l'association entre les identifiants et les lignes d'entrée historiques entre les invocations de programme, vous devriez donc choisir des identifiants fixes pour les différents types de lignes utilisés par votre application.

Chaque fois que gl_get_line() ajoute une nouvelle ligne d'entrée à la liste d'historique, l'identifiant d'historique actuel est enregistré avec elle, et lorsqu'on lui demande de rappeler une ligne d'entrée historique, il ne rappelle que les lignes marquées avec l'identifiant actuel.

AFFICHAGE DE L'HISTORIQUE

La liste d'historique peut être affichée en appelant gl_show_history().

  int gl_show_history(GetLine *gl, FILE *fp,
                      const char *fmt,
                      int all_groups,
                      int max_lines);

Ceci affiche le contenu actuel de la liste d'historique dans le flux de sortie stdio fp. Si l'argument max_lines est supérieur ou égal à zéro, alors pas plus que ce nombre de lignes les plus récentes ne seront affichées. Si l'argument all_groups est différent de zéro, les lignes de tous les groupes d'historique sont affichées. Sinon, seules celles du groupe d'historique actuellement sélectionné sont affichées. L'argument de chaîne de format, fmt, détermine comment la ligne est affichée. Il peut contenir des caractères arbitraires qui sont écrits tels quels, entrelacés avec l'une des directives de format suivantes :

  %D  -  La date à laquelle la ligne a été saisie à l'origine,
         formatée comme 2001-11-20.
  %T  -  L'heure de la journée à laquelle la ligne a été saisie,
         formatée comme 23:59:59.
  %N  -  Le numéro d'entrée séquentiel de la ligne dans
         le tampon d'historique.
  %G  -  Le numéro du groupe d'historique auquel
         la ligne appartient.
  %%  -  Un caractère % littéral.
  %H  -  La ligne d'historique elle-même.

Ainsi, une chaîne de format comme ""%D %T %H\n"" produirait quelque chose comme :

  2001-11-20 10:23:34  Bonjour le monde

Notez l'inclusion d'un caractère de nouvelle ligne explicite dans la chaîne de format.

RECHERCHE DANS L'HISTORIQUE

La fonction gl_lookup_history() permet à l'application appelante de rechercher des lignes dans la liste d'historique.

    const char *line;    /* La ligne historique */
                         /*  demandée. */

L'argument id indique quelle ligne rechercher, où la première ligne saisie dans la liste d'historique après l'appel à new_GetLine() est désignée par 0, et les lignes saisies ultérieurement sont désignées par des nombres successivement plus élevés. Vous devriez donc en faire une copie privée si vous avez besoin de la conserver.

ARCHIVAGE MANUEL DE L'HISTORIQUE

Par défaut, chaque fois qu'une ligne est saisie par l'utilisateur, elle est automatiquement ajoutée à la liste d'historique, juste avant que gl_get_line() ne renvoie la ligne à l'appelant. C'est pratique pour la majorité des applications, mais il existe aussi des applications qui nécessitent un contrôle plus précis sur ce qui est ajouté à la liste d'historique. Dans de tels cas, l'ajout automatique des lignes saisies à la liste d'historique peut être désactivé en appelant la fonction gl_automatic_history().

  int gl_automatic_history(GetLine *gl, int enable);

Si cette fonction est appelée avec son argument enable réglé sur 0, gl_get_line() n'archivera pas automatiquement les lignes saisies par la suite. L'archivage automatique peut être réactivé plus tard, en rappelant cette fonction, avec son argument enable réglé sur 1. Tant que l'archivage automatique de l'historique est désactivé, l'application appelante peut utiliser gl_append_history() pour ajouter des lignes à la liste d'historique au besoin.

  int gl_append_history(GetLine *gl, const char *line);

L'argument line spécifie la ligne à ajouter à la liste d'historique. Il doit s'agir d'une chaîne normale terminée par ' '. Si cette chaîne contient des caractères de nouvelle ligne, la ligne qui sera archivée dans la liste d'historique sera terminée par le premier de ces caractères. Sinon, elle sera terminée par le terminateur ' '. Si la ligne est plus longue que la longueur maximale de ligne d'entrée, qui a été spécifiée lors de l'appel à new_GetLine(), lors de son rappel, elle sera tronquée à la longueur de ligne réelle de gl_get_line().

En cas de succès, gl_append_history() renvoie 0. Sinon, elle renvoie une valeur non nulle et définit errno à l'une des valeurs suivantes.

   EINVAL  -  L'un des arguments passés à
              gl_append_history() était NULL.
   ENOMEM  -  La ligne spécifiée était plus longue que la taille allouée
              du tampon d'historique (comme spécifié lors de
              l'appel à new_GetLine()), elle n'a donc pas pu être
              archivée.

Une description textuelle de l'erreur peut éventuellement être obtenue en appelant gl_error_message(). Notez qu'après une telle erreur, la liste d'historique reste dans un état valide pour recevoir de nouvelles lignes d'historique, il y a donc peu de danger à ignorer simplement le statut de retour de gl_append_history().

GESTION PAR DÉFAUT DES SIGNAUX


Par défaut, la fonction gl_get_line() intercepte un certain
    nombre de signaux. Ceci est particulièrement important pour les signaux qui
    termineraient le processus par défaut, car le terminal doit être restauré
    dans un état utilisable avant que cela ne se produise. Dans cette section, les
    signaux qui sont interceptés par défaut, et comment gl_get_line() y répond,
    sont décrits. La modification de ces valeurs par défaut est le sujet de la
    section suivante.


Lorsque le sous-ensemble de signaux suivant est intercepté,
    gl_get_line() restaure d'abord les paramètres du terminal et la gestion des
    signaux tels qu'ils étaient avant l'appel de gl_get_line(), renvoie le
    signal, pour permettre aux gestionnaires de signaux de l'application appelante
    de le gérer, puis si le processus existe toujours, gl_get_line() retourne
    NULL et définit errno comme spécifié ci-dessous.


 SIGINT  -  Ce signal est généré à la fois par la touche
            d'interruption du clavier (généralement ^C)
            et par la touche break du clavier.
            errno=EINTR
 SIGHUP  -  Ce signal est généré lorsque le terminal de
            contrôle se ferme.
            errno=ENOTTY
 SIGPIPE -  Ce signal est généré lorsqu'un programme tente
            d'écrire dans un tube dont l'extrémité distante
            n'est lue par aucun processus. Cela peut se
            produire, par exemple, si vous avez appelé
            gl_change_terminal() pour rediriger la
            sortie vers un tube caché sous un pseudo-terminal.
            errno=EPIPE
 SIGQUIT -  Ce signal est généré par la touche d'arrêt du
            clavier (généralement ^\).
            errno=EINTR
 SIGABRT -  Ce signal est généré par la fonction C standard,
            abort(). Par défaut, il termine le processus et
            génère un vidage mémoire (core dump).
            errno=EINTR
 SIGTERM -  C'est le signal par défaut que la commande kill
            UN*X envoie aux processus.
            errno=EINTR


Notez que dans le cas de tous les signaux ci-dessus, POSIX exige
    que par défaut le processus soit terminé, avec l'ajout d'un vidage mémoire
    dans le cas du signal SIGQUIT. En d'autres termes, si l'application
    appelante ne remplace pas le gestionnaire par défaut en fournissant son propre
    gestionnaire de signaux, la réception du signal correspondant terminera
    l'application avant que gl_get_line() ne retourne.


Si gl_get_line() avorte avec errno défini sur EINTR, vous pouvez
    découvrir quel signal a provoqué son avortement en appelant la fonction
    suivante.


  int gl_last_signal(const GetLine *gl);


Ceci retourne le code numérique (par exemple, SIGINT) du dernier
    signal reçu lors de l'appel le plus récent à gl_get_line(), ou -1 si
    aucun signal n'a été reçu.


Sur les systèmes qui le prennent en charge, lorsqu'un signal SIGWINCH
    (changement de fenêtre) est reçu, gl_get_line() interroge le terminal pour
    connaître sa nouvelle taille, redessine la ligne d'entrée actuelle pour
    s'adapter à la nouvelle taille, puis retourne à l'attente de l'entrée du
    clavier de l'utilisateur. Contrairement aux autres signaux, ce signal n'est
    pas renvoyé à l'application.


Enfin, les signaux suivants font que gl_get_line() restaure
    d'abord le terminal et l'environnement de signal à ce qui prévalait avant que
    gl_get_line() ne soit appelé, puis renvoie le signal à l'application. Si le
    processus existe toujours après la délivrance du signal, alors
    gl_get_line() rétablit ses propres gestionnaires de signaux, remet le
    terminal en mode brut, rediffuse la ligne d'entrée, et retourne à l'attente
    de l'entrée du terminal de la part de l'utilisateur.


 SIGCONT    -  Ce signal est généré lorsqu'un processus suspendu
               est repris.
 SIGPOLL    -  Sur les systèmes SVR4, ce signal notifie le
               processus d'un événement d'E/S asynchrones.
               Notez que sous 4.3+BSD, SIGIO et SIGPOLL sont
               identiques. Sur d'autres systèmes, SIGIO est
               ignoré par défaut, donc gl_get_line()
               ne l'intercepte pas par défaut.
 SIGPWR     -  Ce signal est généré lors d'une panne de courant
               (probablement lorsque le système est sur un UPS).
 SIGALRM    -  Ce signal est généré lorsqu'un minuteur expire.
 SIGUSR1    -  Un signal spécifique à l'application.
 SIGUSR2    -  Un autre signal spécifique à l'application.
 SIGVTALRM  -  Ce signal est généré lorsqu'un minuteur virtuel
               expire (voir man setitimer(2)).
 SIGXCPU    -  Ce signal est généré lorsqu'un processus dépasse
               sa limite de temps CPU souple.
 SIGXFSZ    -  Ce signal est généré lorsqu'un processus dépasse
               sa limite souple de taille de fichier.
 SIGTSTP    -  Ce signal est généré par la touche de suspension
               du terminal, qui est généralement ^Z, ou la touche
               de suspension retardée du terminal, qui est
               généralement ^Y.
 SIGTTIN    -  Ce signal est généré si le programme tente de lire
               depuis le terminal pendant que le programme s'exécute
               en arrière-plan.
 SIGTTOU    -  Ce signal est généré si le programme tente d'écrire
               sur le terminal pendant que le programme s'exécute
               en arrière-plan.


Évidemment, tous les signaux ci-dessus ne sont pas pris en charge sur
    tous les systèmes, de sorte que le code pour les prendre en charge est
    compilé conditionnellement dans la bibliothèque tecla.


Notez que si SIGKILL ou SIGPOLL, qui par définition ne peuvent
    pas être interceptés, ou l'un des signaux d'exception générés par le matériel,
    tels que SIGSEGV, SIGBUS et SIGFPE, sont reçus et non gérés
    alors que gl_get_line() a le terminal en mode brut, le programme sera
    terminé sans que le terminal n'ait été restauré dans un état utilisable. En
    pratique, les shells de contrôle de job restaurent généralement les paramètres
    du terminal lorsqu'un processus abandonne le terminal de contrôle, donc ce n'est
    qu'un problème avec les anciens shells.

    lit, ou suspend ou termine le programme, vous devez spécifier l'argument
    flags comme GL_SUSPEND_INPUT, afin que :


1. Le curseur ne reste pas au milieu de la ligne d'entrée.
2. L'utilisateur puisse taper des entrées et qu'elles soient
   échoées.
3. Vous n'ayez pas besoin de terminer chaque ligne de sortie avec
   \r\n, au lieu de simplement \n.

    GL_SUSPEND_LINE entraînerait la duplication inutile de la ligne
    d'entrée lorsque rien n'a été écrit sur le terminal. Un tel gestionnaire de

    train de saisir une ligne qui n'occupe qu'une seule ligne de terminal, ou si le
    curseur se trouve sur la dernière ligne de terminal d'une ligne d'entrée plus

    commencera à écrire sur une ligne qui contient déjà une partie de la ligne
    d'entrée affichée. Cela ne cause aucun dommage, mais cela semble un peu laid,
    c'est pourquoi la combinaison GL_SUSPEND_INPUT est meilleure si vous
    savez que vous allez toujours écrire sur le terminal.

    retourne), peut prendre l'une des valeurs suivantes :


  GLS_RETURN   - Retourne la ligne d'entrée complétée, comme

                 retour.

GESTION DES SIGNAUX FIABLE


La gestion des signaux est étonnamment difficile à réaliser de
    manière fiable sans conditions de concurrence. Dans gl_get_line(),
    beaucoup de soin a été apporté pour permettre aux applications d'effectuer une
    gestion fiable des signaux autour de gl_get_line(). Cette section
    explique comment en tirer parti.


Comme exemple des problèmes qui peuvent survenir si l'application
    n'est pas écrite correctement, imaginez que votre application ait un gestionnaire
    de signaux SIGINT qui définit un drapeau global. Supposons maintenant que
    l'application teste ce drapeau juste avant d'appeler gl_get_line().
    Si un signal SIGINT est reçu dans la petite fenêtre de temps entre
    l'instruction qui teste la valeur de ce drapeau et l'instruction qui appelle
    gl_get_line(), alors gl_get_line() ne verra pas le signal
    et ne sera pas interrompu. Par conséquent, l'application ne pourra pas
    répondre au signal tant que l'utilisateur n'aura pas terminé la saisie de la
    ligne d'entrée et que gl_get_line() ne sera pas retourné. Selon
    l'application, cela peut être un désastre ou non, mais au moins cela
    déconcertera l'utilisateur.


La façon d'éviter de tels problèmes est de faire ce qui suit.


1. Si nécessaire, utilisez la fonction gl_trap_signal() pour
  

   configurer gl_get_line() afin qu'il avorte lors de la
  

   capture de signaux importants.


2. Configurez gl_get_line() de telle sorte que si l'un des
  

   signaux qu'il capture est bloqué lorsque
  

   gl_get_line() est appelé, il soit automatiquement
  

   débloqué pendant les périodes où gl_get_line()
  

   attend une E/S. Cela peut être fait soit
  

   par signal, en appelant la fonction
  

   gl_trap_signal() et en spécifiant l'attribut
  

   GLS_UNBLOCK du signal, soit globalement en appelant
  

   la fonction gl_catch_blocked().


     void gl_catch_blocked(GetLine *gl);



  

   Cette fonction ajoute simplement l'attribut
  

   GLS_UNBLOCK à tous les signaux qu'elle est
  

   actuellement configurée pour piéger.


3. Juste avant d'appeler gl_get_line(), bloquez la
  

   livraison de tous les signaux que
  

   gl_get_line() est configuré pour piéger. Cela
  

   peut être fait à l'aide de la fonction POSIX
  

   sigprocmask() en conjonction avec la fonction
  

   gl_list_signals().


      int gl_list_signals(GetLine *gl, sigset_t *set);



  

   Cette fonction retourne l'ensemble des signaux qu'elle
  

   est actuellement configurée pour capturer dans
  

   l'argument set, qui est dans le format requis par
  

   sigprocmask().


4. Dans l'exemple, vous testeriez maintenant le drapeau global
  

   que le gestionnaire de signaux définit, sachant qu'il n'y a
  

   plus aucun danger que ce drapeau soit à nouveau défini avant
  

   que gl_get_line() ne débloque ses signaux lors de
  

   l'exécution des E/S.


5. Finalement, gl_get_line() retourne, soit parce qu'un
  

   signal a été capturé, une erreur s'est produite, soit
  

   l'utilisateur a terminé la saisie de sa ligne d'entrée.


6. Vous vérifieriez maintenant à nouveau le drapeau de signal
  

   global, et s'il est défini, vous y répondriez et
  

   remettriez le drapeau à zéro.


7. Utilisez sigprocmask() pour débloquer les signaux qui
  

   étaient bloqués à l'étape 3.


La même technique peut être utilisée autour de certaines fonctions
    POSIX sensibles aux signaux, telles que sigsetjmp() et
    sigsuspend(), et en particulier, la première de ces deux fonctions peut
    être utilisée en conjonction avec siglongjmp() pour implémenter une
    gestion des signaux sans condition de concurrence autour d'autres appels système
    de longue durée. La manière de faire cela est expliquée ensuite, en montrant
    comment gl_get_line() parvient à piéger de manière fiable les signaux
    autour des appels à des fonctions comme read() et select() sans
    conditions de concurrence.


La première chose que gl_get_line() fait, chaque fois qu'il est
    appelé, est d'utiliser la fonction POSIX sigprocmask() pour bloquer la
    livraison de tous les signaux qu'il est actuellement configuré pour capturer.
    Ceci est redondant si l'application les a déjà bloqués, mais cela ne fait aucun
    mal. Il annule cette étape juste avant de retourner.


Chaque fois que gl_get_line() a besoin d'appeler read()
    ou select() pour attendre une entrée de l'utilisateur, il appelle
    d'abord la fonction POSIX sigsetjmp(), en veillant à spécifier une
    valeur non nulle pour son argument savesigs. La raison de ce dernier
    argument deviendra claire sous peu.


Si sigsetjmp() retourne zéro, gl_get_line() fait
    alors ce qui suit.


a. Il utilise la fonction POSIX sigaction() pour enregistrer
   un gestionnaire de signaux temporaire pour tous les signaux
   qu'il est configuré pour piéger. Ce gestionnaire de signaux
   fait deux choses.
   1. Il enregistre le numéro du signal reçu dans une variable
      de portée fichier.
   2. Il appelle ensuite la fonction POSIX siglongjmp()
      en utilisant le tampon passé à sigsetjmp() comme
      premier argument, et une valeur non nulle comme second
      argument.
   Lorsque ce gestionnaire de signaux est enregistré, le membre
   sa_mask de l'argument struct sigaction act de
   l'appel à sigaction() est configuré pour contenir tous
   les signaux que gl_get_line() capture. Cela garantit
   qu'un seul signal sera capturé à la fois par notre gestionnaire
   de signaux, ce qui garantit que plusieurs instances de notre
   gestionnaire de signaux ne se gêneront pas mutuellement.
b. Maintenant que le gestionnaire de signaux est configuré,
   gl_get_line() débloque tous les signaux qu'il est
   configuré pour piéger.
c. Il appelle ensuite les appels système read() ou
   select() pour attendre une entrée du clavier.
d. Si cet appel système retourne (c'est-à-dire qu'aucun signal
   n'est reçu), gl_get_line() rebloque les signaux
   d'intérêt.
e. Il réinstalle ensuite les gestionnaires de signaux qui ont
   été déplacés par celui qui vient d'être installé.


Alternativement, si sigsetjmp() retourne une valeur non
    nulle, cela signifie que lors

e des signaux piégés a été capturé pendant l'exécution des étapes ci-dessus. Lorsque cela se produit, gl_get_line() fait ce qui suit.


Tout d'abord, notez que lorsqu'un appel à siglongjmp() provoque le retour de
    sigsetjmp() , à condition que l'argument savesigs de
    sigsetjmp() ait été non nul, comme spécifié ci-dessus, le masque de traitement des signaux
    est restauré à l'état dans lequel il se trouvait lorsque sigsetjmp() a été appelé. C'est la
    différence importante entre sigsetjmp() et l'ancien
    setjmp()problématique, et c'est l'élément essentiel qui rend possible
    l'évitement des conditions de course dans la gestion des signaux. En raison de cela, nous sommes garantis
    que tous les signaux que nous avons bloqués avant d'appeler sigsetjmp()
    sont de nouveau bloqués dès qu'un signal est capturé. Les instructions suivantes,
    qui sont alors exécutées, sont donc garanties d'être exécutées sans qu'aucun
    autre signal ne soit capturé.


1. Si tel est l'instruction donnée par les gl_get_line() attributs de
  

   configuration du signal qui a été capturé,
  

   gl_get_line() restaure les attributs du terminal à
  

   l'état dans lequel ils se trouvaient lorsque gl_get_line() a été
  

   appelé. C'est particulièrement important pour les signaux qui
  

   suspendent ou terminent le processus, car sinon le
  

   terminal serait laissé dans un état inutilisable.


2. Il réinstalle ensuite les gestionnaires de signaux de l'application.


3. Il utilise ensuite la fonction raise()
  

   de la bibliothèque standard C pour renvoyer à l'application le signal qui
  

   a été capturé.


3. Ensuite, il débloque la livraison du signal que nous venons de
  

   envoyer. Cela a pour résultat que le signal qui vient d'être envoyé
  

   via raise(), est capturé par le gestionnaire de signal
  

   original de l'application, qui peut maintenant le traiter comme il
  

   le juge approprié.


4. Si le gestionnaire de signal retourne (c'est-à-dire qu'il ne termine pas
  

   le processus), gl_get_line() bloque de nouveau la livraison du
  

   signal ci-dessus.


5. Il annule ensuite toutes les actions effectuées dans la première des
  

   étapes ci-dessus, et réaffiche la ligne, si la
  

   configuration du signal l'exige.


6. gl_get_line() reprend alors la tentative de
  

   lecture d'un caractère, ou interrompt, en fonction de la
  

   configuration du signal qui a été capturé.


Ce que font essentiellement les étapes ci-dessus, c'est prendre des signaux
    livrés de manière asynchrone et les traiter de manière synchrone, un à la fois, à un point
    du code où gl_get_line() a un contrôle complet sur son
    environnement.






LA   TAILLE DU TERMINAL


Sur la plupart des systèmes, la combinaison de TIOCGWINSZ ioctl et
    du SIGWINCH signal est utilisée pour maintenir une idée précise de la
    taille du terminal. La taille du terminal est requise à nouveau chaque fois que
    gl_get_line() est appelé et chaque fois qu'un SIGWINCH signal est
    reçu.


Sur les quelques systèmes où ce mécanisme n'est pas disponible, au
    démarrage new_GetLine() cherche d'abord les LINES et
    COLUMNS variables d'environnement. Si elles ne sont pas trouvées, ou si elles contiennent
    des valeurs inutilisables, alors si une base de données d'informations sur le terminal comme terminfo ou
    termcap est disponible, la taille par défaut du terminal est recherchée dans cette
    base de données. Si cela échoue également à fournir la taille du terminal, une taille par défaut de
    80 colonnes par 24 lignes est utilisée.


Même sur les systèmes qui prennent en charge ioctl(TIOCGWINSZ), si le
    terminal est à l'autre bout d'une ligne série, le pilote du terminal n'a généralement
    aucun moyen de détecter quand un redimensionnement se produit ou de demander quelle est la taille
    actuelle. Dans de tels cas, aucun SIGWINCH n'est envoyé au processus, et les
    dimensions renvoyées par ioctl(TIOCGWINSZ) ne sont pas correctes. La seule façon
    de gérer de tels cas est de fournir un moyen à l'utilisateur de saisir une commande
    qui indique au système distant quelle est la nouvelle taille. Cette commande appellerait alors la fonction gl_set_term_size() pour informer gl_get_line()
    du changement de taille.


  int gl_set_term_size(GetLine *gl, int ncolumn, int nline);


Les ncolumn et nline arguments sont utilisés pour spécifier
    les nouvelles dimensions du terminal, et ne doivent pas être inférieurs à 1. Sur les systèmes
    qui prennent en charge ioctl(TIOCGWINSZ), cette fonction appelle d'abord
    ioctl(TIOCSWINSZ) pour informer le pilote du terminal du changement de
    taille. En mode E/S serveur non bloquant, si une ligne est actuellement en cours de saisie,
    la ligne d'entrée est alors redessinée pour s'adapter à la taille modifiée. Enfin, les
    nouvelles valeurs sont enregistrées dans gl pour une utilisation future par
  gl_get_line().


La fonction gl_terminal_size() vous permet de demander la
    taille actuelle du terminal, et d'installer une taille de secours alternative pour
    les cas où la taille n'est pas disponible. Attention, la taille du terminal ne sera pas
    disponible si vous lisez depuis un pipe ou un fichier, donc les valeurs par défaut peuvent être
    importantes même sur les systèmes qui prennent en charge des moyens de découvrir la taille
    du terminal.


  typedef struct {
    int nline;        /* Le terminal a nline lignes */
    int ncolumn;      /* Le terminal a ncolumn colonnes */
  } GlTerminalSize;
  GlTerminalSize gl_terminal_size(GetLine *gl,
                                  int def_ncolumn,
                                  int def_nline);


Cette fonction met d'abord à jour les gl_get_line()dimensions de secours
    du terminal, puis enregistre ses résultats dans la valeur de retour.


Les def_ncolumn et def_nline spécifient le
    nombre par défaut de colonnes et de lignes du terminal à utiliser si la taille du terminal ne peut pas être
    déterminée via ioctl(TIOCGWINSZ) ou les variables d'environnement.






CACHER   CE QUE VOUS TAPEZ


Lors de la saisie d'informations sensibles, comme les mots de passe, il est préférable
    de ne pas faire écho sur le terminal du texte que vous saisissez.
    De plus, ce texte ne devrait pas être enregistré dans la liste d'historique, car
    quelqu'un trouvant votre terminal sans surveillance pourrait alors le rappeler, ou quelqu'un
    fouillant dans vos répertoires pourrait le voir dans votre fichier d'historique. En
    gardant cela à l'esprit, la fonction gl_echo_mode() vous permet d'activer et de
    désactiver l'affichage et l'archivage de tout texte qui est saisi par la suite dans
    les appels à gl_get_line().


  int gl_echo_mode(GetLine *gl, int enable);


L' enable argument spécifie si le texte saisi doit être
    visible ou non. S'il est 0, alors les lignes saisies par la suite ne seront
    pas visibles sur le terminal, et ne seront pas enregistrées dans la liste
    d'historique. S'il est 1, alors les lignes d'entrée suivantes seront affichées à
    mesure qu'elles sont saisies, et à condition que l'historique n'ait pas été désactivé via un
    appel à gl_toggle_history(), elles seront également archivées dans la
    liste d'historique. Enfin, si l' enable argument est -1, alors le
    mode d'écho est laissé inchangé, ce qui vous permet de demander de manière non destructive
    le réglage actuel via la valeur de retour. Dans tous les cas, la valeur de retour de la
    fonction est 0 si l'écho était désactivé avant que la fonction ne soit
    appelée, et 1 s'il était activé.


Lorsque l'écho est désactivé, notez que même si la complétion par tabulation
    complétera de manière invisible votre préfixe aussi loin que possible, les complétions
    ambiguës ne seront pas affichées.






INTERROGATIONS   À UN SEUL CARACTÈRE


Utiliser gl_get_line() pour interroger l'utilisateur pour une réponse d'un seul
    caractère, est inconfortable pour l'utilisateur, car il doit appuyer sur la touche entrée
    ou retour avant que le caractère qu'il a tapé ne soit renvoyé au
    programme. C'est pourquoi la fonction gl_query_char() a été fournie pour les
    interrogations à un seul caractère comme celle-ci.


  int gl_query_char(GetLine *gl, const char *prompt,
                    char defchar);


Cette fonction affiche l'invite spécifiée au début d'une nouvelle
    ligne, et attend que l'utilisateur tape un caractère. Lorsque l'utilisateur tape un
    caractère, gl_query_char() l'affiche à droite de l'invite,
    démarre une nouvelle ligne, puis renvoie le caractère au programme appelant. La
    valeur de retour de la fonction est le caractère qui a été tapé. Si la lecture
    a dû être interrompue pour une raison quelconque, EOF est renvoyé à la place. Dans ce
    dernier cas, l'application peut appeler la fonction
    gl_return_status()précédemment documentée, pour savoir ce qui s'est mal passé. Cela pourrait, par
    exemple, être la réception d'un signal, ou le déclenchement du minuteur d'inactivité
    optionnel.


Si l'utilisateur appuie simplement sur entrée, la valeur de l' defchar
    argument est substituée. Cela signifie que lorsque l'utilisateur appuie soit sur nouvelle ligne
    soit sur retour, le caractère spécifié dans defchar, est affiché après
    l'invite, comme si l'utilisateur l'avait tapé, ainsi que renvoyé à
    l'application appelante. Si un tel remplacement n'est pas important, passez simplement
    '0 comme valeur de defchar.


Si le caractère saisi est un caractère non imprimable, il est
    affiché symboliquement. Par exemple, contrôle-A est affiché comme ^A, et
    les caractères au-delà de 127 sont affichés en octal, précédés d'une barre oblique inverse.


Comme avec gl_get_line(), l'écho du caractère saisi peut
    être désactivé en utilisant la fonction gl_echo_mode() .


Si le processus appelant est suspendu pendant qu'il attend que l'utilisateur
    tape sa réponse, le curseur est déplacé sur la ligne suivant la ligne d'invite,
    puis lorsque le processus reprend, l'invite est réaffichée, et
    gl_query_char() reprend l'attente que l'utilisateur tape un caractère.


Notez qu'en mode serveur non bloquant, (voir gl_io_mode(3)), si une
    ligne d'entrée incomplète est en cours de lecture lorsque
    gl_query_char() est appelé, la ligne d'entrée partielle est abandonnée, et
    effacée du terminal, avant que la nouvelle invite ne soit affichée. Le prochain appel
    à gl_get_line() commencera donc à éditer une nouvelle ligne.






LIRE   DES CARACTÈRES BRUTS


Alors que la fonction gl_query_char() invite visiblement l'utilisateur à saisir un
    caractère, et affiche ce qu'il a tapé, la
    fonction gl_read_char() lit un caractère de signal auprès de l'utilisateur,
    sans écrire quoi que ce soit sur le terminal, ou de perturber une ligne d'entrée
    incomplète. Cela signifie qu'elle peut être appelée non seulement entre les
    appels à gl_get_line(), mais aussi depuis des fonctions de rappel que
    l'application a enregistrées pour être appelées par gl_get_line().


  int gl_read_char(GetLine *gl);


En cas de succès, la valeur de retour de gl_read_char() est le
    caractère qui a été lu. En cas d'échec, EOF est renvoyé, et la
    fonction gl_return_status() peut être appelée pour savoir ce qui s'est mal passé. Les possibilités incluent le déclenchement du minuteur d'inactivité optionnel, la
    réception d'un signal configuré pour interrompre gl_get_line(), ou le blocage des E/S
    du terminal, en mode E/S serveur non bloquant.


Attention, certaines touches du clavier, comme les touches de fonction et
    les touches de curseur, génèrent généralement au moins 3 caractères chacune, donc un seul appel à gl_read_char() ne suffire pour identifier de telles frappes.






EFFACER   LE TERMINAL


Le programme appelant peut effacer le terminal en appelant
    gl_erase_terminal(). En mode d'E/S serveur non bloquant, cette fonction
    prévoit également que la ligne de saisie courante soit redessinée à
    zéro lorsque
    gl_get_line() est appelée à nouveau.


  int gl_erase_terminal(GetLine *gl);






AFFICHER   DU TEXTE DE MANIÈRE DYNAMIQUE


Entre les appels à gl_get_line(), la fonction
    gl_display_text() fournit un moyen pratique d'afficher
    des paragraphes de texte, justifiés à gauche et répartis sur une ou
    plusieurs lignes du terminal selon les contraintes de la largeur courante
    du terminal. Des exemples d'utilisation de cette fonction se trouvent dans
    les programmes de démonstration, où elle est utilisée pour afficher des
    introductions. Dans ces exemples, l'utilisation avancée de préfixes,
    suffixes et lignes de remplissage optionnels pour dessiner une boîte autour
    du texte est également illustrée.


  int gl_display_text(GetLine *gl, int indentation,
                      const char *prefix,
                      const char *suffix, int fill_char,
                      int def_width, int start,
                      const char *string);


Si gl n'est pas actuellement connecté à un terminal, par exemple
    si la sortie d'un programme qui utilise gl_get_line() est acheminée par pipe vers un
    autre programme ou redirigée vers un fichier, alors la valeur du paramètre
    def_width est utilisée comme largeur du terminal.


L'argument indentation spécifie le nombre de caractères
    à utiliser pour indenter chaque ligne de sortie. L'argument fill_char spécifie
    le caractère qui sera utilisé pour effectuer cette indentation.


L'argument prefix peut être soit NULL, soit une
    chaîne à placer au début de chaque nouvelle ligne (après toute indentation).
    De même, l'argument suffix peut être soit NULL, soit une
    chaîne à placer à la fin de chaque ligne. Le suffixe est placé à fleur du
    bord droit du terminal, et tout l'espace entre son premier caractère et le
    dernier mot de cette ligne est rempli par le caractère spécifié via
    l'argument fill_char . Normalement, le caractère de remplissage est une espace.


L'argument start indique à gl_display_text() combien de
    caractères ont déjà été écrits sur la ligne de terminal courante, et lui
    indique donc l'index de la colonne de départ du curseur. Puisque la valeur
    de retour de
    gl_display_text() est l'index de la colonne de fin du curseur, en
    passant la valeur de retour d'un appel à l'argument start de l'appel suivant, un paragraphe qui est réparti sur plus d'une chaîne
    peut être composé en appelant gl_display_text() pour chaque portion successive du
    paragraphe. Notez que des caractères de saut de ligne littéraux sont
    nécessaires à la fin de chaque paragraphe pour forcer le début d'une
    nouvelle ligne.


En cas d'erreur, gl_display_text() renvoie -1.






FONCTIONNALITÉS   DE FONCTIONS DE RAPPEL


Sauf indication contraire, les fonctions de rappel, telles que les
    rappels de complétion par tabulation et les rappels d'événements, ne
    devraient appeler aucune fonction de ce module. Les fonctions suivantes,
    cependant, sont conçues spécifiquement pour être utilisées par des
    fonctions de rappel.


Appeler la fonction gl_replace_prompt() depuis un rappel indique à gl_get_line() d'afficher une invite différente lorsque le rappel
    se termine. Excepté en mode serveur non bloquant, cela n'a aucun effet si
    elle est utilisée entre des appels à gl_get_line(). En mode serveur non bloquant (voir la page de manuel
    gl_io_mode(3) , lorsqu'elle est utilisée entre deux appels à
    gl_get_line() qui opèrent sur la même ligne de saisie, la ligne de saisie
    courante sera redessinée avec la nouvelle invite lors de l'appel suivant à
    gl_get_line().


  void gl_replace_prompt(GetLine *gl, const char *prompt);






JEUX   DE CARACTÈRES INTERNATIONAUX


Depuis la version 1.4.0 de libtecla, gl_get_line() est propre aux 8 bits.
    Cela signifie que tous les caractères 8 bits imprimables dans la locale
    actuelle de l'utilisateur sont désormais affichés tels quels et inclus dans
    la ligne de saisie renvoyée. En supposant que le programme appelant inclut
    correctement un appel comme celui suivant,


  setlocale(LC_CTYPE, "");


alors la locale courante est déterminée par la première des
    variables d'environnement LC_CTYPE, LC_ALL, et LANG, qui
    est trouvée contenir un nom de locale valide. Si aucune de ces variables
    n'est définie, ou si le programme néglige d'appeler setlocale, alors la
    locale par défaut
    C est utilisée, qui est l'ASCII 7 bits américain. Sur la plupart des
    plateformes de type unix, vous pouvez obtenir une liste des locales valides
    en tapant la commande :


  locale -a


à l'invite du shell. Une documentation supplémentaire sur la manière
    dont l'utilisateur peut utiliser ceci pour saisir des caractères
    internationaux se trouve dans la page de manuel
    tecla(7) .






SÉCURITÉ   DES THREADS


Dans un programme multi-thread, vous devriez utiliser la version
    libtecla_r.a de la bibliothèque. Celle-ci utilise des versions réentrantes
    des fonctions système, lorsque cela est disponible. Malheureusement, ni
    terminfo ni termcap n'ont été conçus pour être réentrants, vous ne pouvez
    donc pas utiliser en toute sécurité les fonctions du module getline dans
    plusieurs threads (vous pouvez utiliser les modules séparés d'expansion de
    fichiers et de complétion de mots dans plusieurs threads, voir les pages de
    manuel correspondantes pour les détails). Cependant, en raison de
    l'utilisation de fonctions POSIX réentrantes pour la recherche de répertoires
    personnels, etc., il est sûr d'utiliser ce module depuis un seul thread
    d'un programme multi-thread, à condition que vos autres threads
    n'utilisent aucune fonction termcap ou terminfo.
