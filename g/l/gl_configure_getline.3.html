DESCRIPTIO

N

La fonction gl_get_line() fait partie de la bibliothèque tecla (voir la page man libtecla(3)). Si l'utilisateur tape sur un terminal, chaque appel lui demande une ligne de saisie, puis fournit des fonctionnalités d'édition interactives, similaires à celles du shell unix tcsh. En plus de l'édition simple de ligne de commande, elle prend en charge le rappel des lignes de commande précédemment saisies, la complétion des noms de fichiers avec la touche TAB, et l'expansion des caractères génériques des noms de fichiers en ligne. La documentation des fonctionnalités d'édition de ligne de commande au niveau utilisateur et de toutes les options de configuration utilisateur peut être trouvée dans la page man tecla(7). Cette page man concerne la documentation destinée aux pro

grammeurs souhaitant utiliser cette
bibliothèque dans leur application.

UN

EXEMPLE

L'exemple suivant montre un exemple complet de la façon d'utiliser la fonction gl_get_line() pour obtenir une saisie de l'utilisateur

: 
  #include <stdio.h>
  #include <locale.h>
  #include <libtecla.h>
  int main(int argc, char *argv[])
  { 
    char *line;    /* La ligne que l'utilisateur a tapée */
    GetLine *gl;   /* L'objet ressource gl_get_line() */
    setlocale(LC_CTYPE, ""); /* Adopter le choix de l'utilisateur */
                             /* concernant le jeu de caractères. */
    gl = new_GetLine(1024, 2048);
    if(!gl)
      return 1;
    while((line=gl_get_line(gl, "$ ", NULL, -1)) != NULL &&
           strcmp(line, "exit\n") != 0)
      printf("Vous avez tapé : %s\n", line);
    gl = del_GetLine(gl);
    return 0;
}

Dans l'exemple, d'abord les ressources nécessaires par la fonction gl_get_line() sont créées en appelant new_GetLine(). Cela alloue la mémoire utilisée lors des appels ultérieurs à la fonction gl_get_line(), y compris le tampon d'historique pour enregistrer les lignes précédemment saisies. Ensuite, une ou plusieurs lignes sont lues auprès de l'utilisateur, jusqu'à ce qu'une erreur survienne, ou que l'utilisateur tape exit. Enfin, les ressources qui ont été allouées par new_GetLine() sont rendues au système en appelant del_GetLine(). Notez l'utilisation de la valeur de retour NULL de del_GetLine() pour rendre gl NULL. C'est une précaution de sécurité. Si le programme tente ultérieurement de passer gl à gl_get_line(), ladite fonction se plaindra et retournera une err

eur, au lieu de tenter d'util
iser l'objet ressource supprimé.

La fonction gl_get_line() peut être appelée un nombre quelconque de fois pour lire la saisie de l'utilisateur. L'argument gl doit avoir été précédemment retourné par un appel à new_GetLine(). L'argument prompt doit être une chaîne normale terminée par NUL, spécifiant le invite à présenter à l'utilisateur. Par défaut, les invites sont affichées littéralement, mais si elles sont activées avec la fonction gl_prompt_style() (voir plus tard), les invites peuvent contenir des directives pour souligner, passer en et sortir des polices en gras, ou activer et désactiver la

surbrillance.

Vous pouvez ensuite spécifier le caractère de cette ligne où le curseur est initialementioned over, using the start_pos argument. This should be -1 if you want the cursor to follow the last character of the start line. If you don't want to preload the line in this manner, send start_line as NULL, and set start_pos to -1. Note that the line pointer returned by one call to gl_get_line() can be passed back to the next call to gl_get_line() via the start_line. This allows the application to take the last entered line, and if it contains an error, to then present it back to the user for re-editing, with the cursor initially positioned where the error was

encountered.

La fonction gl_get_line() renvoie un pointeur vers la ligne saisie par l'utilisateur, ou NULL en cas d'erreur ou à la fin de l'entrée. Le pointeur renvoyé fait partie de l'objet ressource gl spécifié, et ne doit donc pas être libéré par l'appelant, ni supposé inchangé d'un appel au suivant. Lors de la lecture depuis un utilisateur sur un terminal, il y aura toujours un caractère de nouvelle ligne à la fin de la ligne renvoyée. Lorsque l'entrée standard provient d'un pipe ou d'un fichier, il y aura également une nouvelle ligne, sauf si la ligne d'entrée était trop longue pour être stockée dans le tampon interne. Dans ce dernier cas, vous devriez appeler gl_get_line() à nouveau pour lire le reste de la ligne. Notez que ce comportement rend gl_get_line() similaire à fgets(). En fait, lorsque stdin n'est pas connecté à un terminal,gl_get_line() appelle simplement fget

s(
).

SOURCES DE CONFIGURATION

ALTERNATIVES

Comme mentionné ci-dessus, par défaut les utilisateurs ont la possibilité de configurer le comportement de gl_get_line() via un fichier de configuration appelé .teclarc dans leur répertoire personnel. Le fait que toutes les applications partagent ce même fichier de configuration est à la fois un avantage et un inconvénient. Dans la plupart des cas, c'est un avantage, car cela encourage l'uniformité et libère l'utilisateur de devoir configurer chaque application séparément. Dans certaines applications, cependant, ce moyen unique de configuration pose problème. C'est particulièrement vrai pour les logiciels embarqués, où il n'y a pas de système de fichiers pour lire un fichier de configuration, et aussi dans les applications où un choix radicalement différent de mappage des touches est nécessaire pour émuler une interface clavier héritée. Pour prendre en charge de tels cas, la fonction suivante permet à l'application de contrôler d'où les informations de configuration sont

lues. 
  int gl_configure_getline(GetLine *gl,
                           const char *app_string,
                           const char *app_file,
                           const char *user_file)
;

Elle permet aux commandes de configuration qui seraient normalement lues depuis le fichier ~/.teclarc de l'utilisateur, d'être lues depuis une ou plusieurs, ou aucune, des sources suivantes : une chaîne, un fichier de configuration spécifique à l'application, et/ou un fichier de configuration spécifique à l'utilisateur. Si cette fonction est appelée avant le premier appel à gl_get_line(), le comportement par défaut de lecture de ~/.teclarc lors du premier appel à gl_get_line() est désactivé ; toute la configuration doit donc être réalisée à l'aide des sources de configuration spécifiées avec cette

fonction.

Si app_string != NULL, alors il est interprété comme une chaîne contenant une ou plusieurs commandes de configuration, séparées les unes des autres dans la chaîne par des caractères de nouvelle ligne intégrés. Si app_file != NULL alors il est interprété comme le chemin complet d'un fichier de configuration spécifique à l'application. Si user_file != NULL alors il est interprété comme le chemin complet d'un fichier de configuration spécifique à l'utilisateur, tel que ~/.teclarc. Par exemple, dans l'appel

suivant, 
  gl_configure_getline(gl, "edit-mode vi \n nobeep",
                           "/usr/share/myapp/teclarc",
                           "~/.teclarc")
;

l'argument app_string fait démarrer l'application appelante en mode d'édition vi, au lieu du mode emacs par défaut, et désactive l'utilisation de la cloche du terminal par la bibliothèque. Elle tente ensuite de lire les commandes de configuration globales depuis un fichier optionnel appelé /usr/share/myapp/teclarc, puis lit enfin les commandes de configuration spécifiques à l'utilisateur depuis un fichier .teclarc optionnel dans le répertoire personnel de l'utilisateur. Notez que les arguments sont listés par ordre de priorité croissante, le contenu de app_string pouvant potentiellement être remplacé par les commandes dans app_file, et les commandes dans app_file pouvant potentiellement être remplacées par les commandes dans user_file

.

Vous pouvez appeler cette fonction autant de fois que nécessaire, les résultats étant cumulatifs, mais notez que des copies de tout nom de fichier spécifié via leb>app_file et user_file sont enregistrés en interne pour une utilisation ultérieure par la fonction de liaison de touches read-init-files ; si vous prévoyez d'appeler cette fonction plusieurs fois, assurez-vous que le dernier appel spécifie les noms de fichiers que vous souhaitez relire lorsque l'utilisateur demande la relecture des fichiers de

configuration.

COMPLÉTION DE MOTS

PERSONNALISÉE

Si dans votre application, vous souhaitez que la complétion par TAB complète d'autres éléments en plus ou à la place des noms de fichiers, vous pouvez organiser cela en enregistrant une fonction de rappel de complétion alternative, via un appel à la fonction gl_customize_c

ompletion(). 
  int gl_customize_completion(GetLine *gl, void *data,
                              CplMatchFn *match_fn)
;

L'argument data fournit un moyen à votre application de passer des informations arbitraires spécifiques à l'application à la fonction de rappel. Celles-ci lui sont transmises à chaque fois qu'elle est appelée. Elle peut par exemple, pointer vers la table de symboles à partir de laquelle les complétions possibles doivent être recherchées. L'argument match_fn spécifie la fonction de rappel à appeler. Le type de fonction CplMatchFn est défini dans libtecla.h, tout comme une macro CPL_MATCH_FN() que vous pouvez utiliser pour déclarer et prototyper des fonctions de rappel. La déclaration et les responsabilités des fonctions de rappel sont décrites en profondeur dans la page de manuel cpl_complete_word(3)

.

En bref, la fonction de rappel est responsable de la recherche vers l'arrière dans la ligne d'entrée, à partir du point où l'utilisateur a appuyé sur TAB, pour trouver le début du mot en cours de complétion. Elle doit ensuite rechercher les complétions possibles de ce mot et les enregistrer une par une dans l'objet WordCompletion qui lui est passé en argument, en appelant la fonction cpl_add_completion(). Si la fonction de rappel souhaite fournir la complétion de noms de fichiers en plus de ses propres complétions spécifiques, elle a la possibilité d'appeler elle-même la fonction de rappel de complétion de noms de fichiers intégrée. Ceci est également documenté dans la page de manuel cpl_complete_word(3)

.

Notez que si vous souhaitez que gl_get_line() retourne la ligne d'entrée actuelle lorsqu'une complétion réussie a été effectuée, vous pouvez organiser cela lorsque vous appelez cpl_add_completion(), en faisant du dernier caractère du suffixe de continuation un caractère de nouvelle ligne. Si vous faites cela, la ligne d'entrée sera mise à jour pour afficher la complétion, avec tout suffixe de continuation jusqu'au caractère de nouvelle ligne, puis gl_get_line() retournera cette ligne

d'entrée.

Si, pour une raison quelconque, votre fonction de rappel doit écrire quelque chose sur le terminal, elle doit appeler gl_normal_io() avant de le faire. Cela commencera une nouvelle ligne après la ligne d'entrée actuellement en cours d'édition, rétablira l'E/S normale du terminal, et indiquera à gl_get_line() que la ligne d'entrée devra

être redessinée lorsqu
e le rappel retournera.

AJOUT D'ACTIONS DE

COMPLÉTION

Dans la section précédente, la capacité de personnaliser le comportement de la seule action de complétion par défaut, complete-word, a été décrite. Dans cette section, la capacité d'installer des fonctions d'action supplémentaires, afin que différents types de complétion de mots puissent être liés à différentes séquences de touches, est décrite. Ceci est réalisé en utilisant la fonction gl_completion_action()

. 
  int gl_completion_action(GetLine *gl,
                           void *data, CplMatchFn *match_fn,
                           int list_only, const char *name,
                           const char *keyseq)
;

Les arguments data et match_fn sont tels que décrits dans la page de manuel cpl_complete_word, et spécifient la fonction de rappel qui doit être invoquée pour identifier les complétions possibles. L'argument list_only détermine si l'action en cours de définition doit tenter de compléter le mot aussi loin que possible dans la ligne d'entrée avant d'afficher d'éventuelles complétions ambiguës, ou si elle doit simplement afficher la liste des complétions possibles sans toucher à la ligne d'entrée. La première option est sélectionnée en spécifiant une valeur de 0, et la seconde en spécifiant une valeur de 1. L'argument name spécifie le nom par lequel les fichiers de configuration et les futures invocations de cette fonction doivent se référer à l'action. Cela doit être soit le nom d'une action de complétion existante à modifier, soit un nouveau nom inutilisé pour une nouvelle action. Enfin, l'argument keyseq spécifie la séquence de touches par défaut à lier à l'action. Si c'est NULL, aucune nouvelle séquence de touches ne sera liée à

l'action.

Attention, pour que l'utilisateur puisse changer la séquence de touches liée aux actions installées de cette manière, lorsque vous appelez gl_completion_action() pour installer une action donnée pour la première fois, vous devriez le faire entre l'appel à new_GetLine() et le premier appel à gl_get_line(). DÉFINITION D'ACTIONS

PERSONNALISÉES

Bien que les actions de liaison de touches intégrées soient suffisantes pour les besoins de la plupart des applications, une application spécialisée peut parfois avoir besoin de définir une ou plusieurs actions personnalisées, liées à des séquences de touches spécifiques à l'application. Par exemple, une application de vente bénéficierait d'une séquence de touches affichant le nom de la pièce correspondant à un numéro de pièce situé avant le curseur. Une telle fonctionnalité dépasse clairement le cadre des fonctions d'action intégrées. Ainsi, pour ces cas particuliers, la fonction gl_register_action() est

fournie. 
  int gl_register_action(GetLine *gl, void *data,
			 GlActionFn *fn, const char *name,
			 const char *keyseq)
;

Cette fonction permet à l'application d'enregistrer une fonction externe, fn, qui sera ensuite appelée chaque fois que soit la séquence de touches spécifiée, keyseq, est saisie par l'utilisateur, soit l'utilisateur saisit une autre séquence de touches qu'il lie ensuite à la nom d'action spécifié, name, dans son fichier de configuration. L'argument data peut être un pointeur vers n'importe quoi que l'application souhaite voir transmis à la fonction d'action, fn, chaque fois que cette fonction est

invoquée.

La fonction d'action, fn, devrait être déclarée à l'aide de la macro suivante, qui est définie dans libtecl

a.h. 
  #define GL_ACTION_FN(fn) GlAfterAction (fn)(GetLine *gl, \
              void *data, int count, size_t curpos, \
              const char
*line)

Les arguments gl et data sont ceux qui ont été précédemment passés à gl_register_action() lorsque la fonction d'action a été enregistrée. L'argument count est un argument numérique que l'utilisateur a la possibilité de saisir à l'aide de l'action digit-argument, avant d'invoquer l'action. Si l'utilisateur n'entre pas de nombre, alors l'argument count est défini à 1. Nominalement, cet argument est interprété comme un nombre de répétitions, signifiant que l'action doit être répétée ce nombre de fois. En pratique cependant, pour certaines actions un nombre de répétitions a peu de sens. Dans de tels cas, les actions peuvent soit simplement ignorer l'argument count, ou utiliser sa valeur à une autre

fin.

Une copie de la ligne d'entrée actuelle est passée dans l'argument en lecture seule line. La position actuelle du curseur dans cette chaîne est donnée par l'index contenu dans l'argument curpos. Notez que la manipulation directe de la ligne d'entrée et de la position du curseur n'est pas autorisée. C'est parce que les règles dictées par divers modes, tels que le mode vi par rapport au mode emacs, le mode sans écho, et le mode insertion par rapport au mode surimpression etc, rendent trop complexe pour un développeur d'application d'écrire une action d'édition conforme, tout en limitant les changements futurs aux internes de gl_get_line(). Une solution potentielle à ce dilemme serait de permettre à la fonction d'action d'éditer la ligne en utilisant les actions d'édition existantes. Cela est actuellement à

l'étude.

Si la fonction d'action souhaite écrire du texte sur le terminal, sans que cela se mélange avec le texte affiché de la ligne d'entrée, ou lire depuis le terminal sans avoir à gérer l'E/S brute du terminal, alors avant de faire l'une de ces opérations, elle doit suspendre temporairement l'édition de ligne en appelant la fonction gl_normal_io(). Cette fonction vide toute sortie en attente vers le terminal, déplace le curseur au début de la ligne qui suit la dernière ligne du terminal de la ligne d'entrée, puis restaure le terminal dans un état adapté à l'utilisation avec les fonctionnalités stdio C. Cela inclut des choses comme la restauration du mappage normal de \n vers \r\n, et, en mode serveur, la restauration de la forme bloquante normale de l'E/S du terminal. Après avoir appelé cette fonction, la fonction d'action peut lire depuis et écrire vers le terminal sans craindre de créer un désordre. Il n'est pas nécessaire pour la fonction d'action de restaurer l'environnement d'édition original avant de retourner. Cela est fait automatiquement par gl_get_line() après le retour de la fonction d'action. Voici un exemple simple d'une fonction d'action qui écrit la phrase "Hello world" sur une nouvelle ligne du terminal après la ligne en cours d'édition. Lorsque cette fonction retourne, la ligne d'entrée est redessinée sur la ligne qui suit la ligne "Hello world", et l'édition de ligne

reprend. 
  static GL_ACTION_FN(say_hello_fn)
  {
    if(gl_normal_io(gl))   /* Suspendre temporairement l'édition */
      return GLA_ABORT;
    printf("Hello world\n");
    return GLA_CONTINUE;
}

Les fonctions d'action doivent retourner l'une des valeurs suivantes, pour indiquer à gl_get_line() comment

procéder. 
  GLA_ABORT     -   Faire en sorte que gl_get_line() retourne NULL.
  GLA_RETURN    -   Faire en sorte que gl_get_line() retourne la
                    ligne d'entrée complétée.
  GLA_CONTINUE  -   Reprendre l'édition de la ligne de
commande.

Notez que le argument name de gl_register_action() spécifie le nom par lequel un utilisateur peut référencer l'action dans son fichier de configuration. Cela lui permet de réassocier l'action à une séquence de touches alternative. Pour que cela fonctionne, il est nécessaire d'appeler gl_register_action() entre l'appel à new_GetLine() et le premier appel à gl_get_

lin
e().

ARCHIVAGE MANUEL DE

L'HISTORIQUE

Par défaut, chaque fois qu'une ligne est saisie par l'utilisateur, elle est automatiquement ajoutée à la liste d'historique, juste avant que gl_get_line() retourne la ligne à l'appelant. C'est pratique pour la majorité des applications, mais il existe aussi des applications qui ont besoin d'un contrôle plus fin sur ce qui est ajouté à la liste d'historique. Dans de tels cas, l'ajout automatique des lignes saisies à la liste d'historique peut être désactivé en appelant la fonction gl_automatic

_history(). 
  int gl_automatic_history(GetLine *gl, int enable)
;

Si cette fonction est appelée avec son argument enable défini à 0, gl_get_line() n'archivera pas automatiquement les lignes saisies ultérieurement. L'archivage automatique peut être réactivé plus tard, en appelant à nouveau cette fonction, avec son argument enable défini à 1. Pendant que l'archivage automatique de l'historique est désactivé, l'application appelante peut utiliser la fonction gl_append_history() pour ajouter des lignes à la liste d'historique selon les

besoins. 
  int gl_append_history(GetLine *gl, const char *line)
;

L' argument line spécifie la ligne à ajouter à la liste d'historique. Cela doit être une chaîne normale terminée par ' '. Si cette chaîne contient des caractères de nouvelle ligne, la ligne qui sera archivée dans la liste d'historique sera terminée par le premier d'entre eux. Sinon, elle sera terminée par le terminateur ' '. Si la ligne est plus longue que la longueur maximale de ligne d'entrée, qui a été spécifiée lorsque new_GetLine() a été appelé, lorsque la ligne est rappelée, elle sera tronquée à la longueur réelle de la ligne gl_get_li

ne().

Si la réussite, gl_append_history() retourne 0. Sinon, elle retourne une valeur non nulle, et définit errno à l'une des valeurs

suivantes. 
   EINVAL  -  L'un des arguments passés à
              gl_append_history() était NULL.
   ENOMEM  -  La ligne spécifiée était plus longue que la taille
              allouée du tampon d'historique (telle que spécifiée lorsque
              new_GetLine() a été appelé), elle ne pouvait donc pas être
archivée.

Une description textuelle de l'erreur peut être obtenue en appelant gl_error_message(). Notez qu'après une telle erreur, la liste d'historique reste dans un état valide pour recevoir de nouvelles lignes d'historique, il y a donc peu d'inconvénient à simplement ignorer le statut de retour de gl_append_

L'HISTORIQUE

CHANGER DE

TERMINAL

Le constructeur new_GetLine() suppose que l'entrée doit être lue depuis stdin, et que la sortie est écrite vers stdout. La fonction suivante vous permet de basculer vers d'autres flux d'entrée et de

GESTION FIABLE DES

SIGNAUX

La gestion des signaux est étonnamment difficile à faire de manière fiable sans conditions de course. Dans gl_get_line(), beaucoup de soin a été pris pour permettre aux applications d'effectuer une gestion fiable des signaux autour de gl_get_line(). Cette section explique comment tirer parti de

cela.

À titre d'exemple des problèmes qui peuvent survenir si l'application n'est pas écrite correctement, imaginez que votre application ait un gestionnaire de signal SIGINT qui définit un drapeau global. Supposons maintenant que l'application teste ce drapeau juste avant d'invoquer gl_get_line(). Si un signal SIGINT se trouve être reçu dans la petite fenêtre de temps entre l'instruction qui teste la valeur de ce drapeau, et l'instruction qui appelle gl_get_line(), alors gl_get_line() ne verra pas le signal, et ne sera pas interrompu. En conséquence, l'application ne pourra pas répondre au signal tant que l'utilisateur n'aura pas terminé la saisie de la ligne et que gl_get_line() ne sera pas retourné. Selon l'application, cela pourrait ou non être un désastre, mais au minimum cela dérangerait

l'utilisateur.

La manière d'éviter ces problèmes est de faire ce qui

suit.

1. Si nécessaire, utilisez la fonction gl_trap_signal() pour
configurer gl_get_line() afin qu'il interrompe lorsque des
signaux importants sont

interceptés.

2. Configurez gl_get_line() de sorte que si l'un des
signaux qu'il intercepte est bloqué lorsque
gl_get_line() est appelé, il sera débloqué
automatiquement pendant les périodes où gl_get_line()
attend des entrées/sorties. Cela peut être fait soit
signal par signal, en appelant la fonction
gl_trap_signal(), et en spécifiant l'attribut
GLS_UNBLOCK du signal, soit globalement en
appelant la fonction gl_catch_bloc

     void gl_catch_blocked(GetLine *gl)
;


Cette fonction ajoute simplement l'attribut GLS_UNBLOCK
à tous les signaux qu'elle est actuellement configurée pour
piéger

.

3. Juste avant d'appeler gl_get_line(), bloquez la délivrance
de tous les signaux que gl_get_line() est
configuré pour piéger. Cela peut être fait en utilisant la fonction POSIX
sigprocmask() en conjonction avec la fonction
gl_list_sign

;


Cette fonction retourne l'ensemble des signaux qu'elle est
actuellement configurée pour intercepter dans l'argument set,
qui est sous la forme requise par sigprocma

4. Dans l'exemple, on testerait maintenant le drapeau global que

gl_get_line() ne débloque ses signaux lors de l'exécution

ligne.

La même technique peut être utilisée autour de certaines fonctions POSIX sensibles aux signaux, telles que sigsetjmp() et sigsuspend(), et en particulier, la première de ces deux fonctions peut être utilisée en conjonction avec siglongjmp() pour implémenter une gestion de signal sans conditions de course autour d'autres appels système longs. La manière de faire cela est expliquée ensuite, en montrant comment gl_get_line() parvient à piéger fiablement les signaux autour d'appels à des fonctions comme read() et select() sans conditions de

course.

La première chose que gl_get_line() fait, chaque fois qu'il est appelé, est d'utiliser la fonction POSIX sigprocmask() pour bloquer la délivrance de tous les signaux qu'il est actuellement configuré pour intercepter. Cela est redondant si l'application les a déjà bloqués, mais cela ne fait aucun mal. Il défaît cette étape juste avant de

retourner.

Chaque fois que gl_get_line() a besoin d'appeler read() ou select() pour attendre des entrées de l'utilisateur, il appelle d'abord la fonction POSIX sigsetjmp(), en s'assurant de spécifier une valeur non nulle pour son argument savesigs. La raison de ce dernier argument deviendra claire

bientôt.

Si sigsetjmp() retourne zéro, gl_get_line() fait alors ce qui

suit. 
a. Il utilise la fonction POSIX sigaction() pour enregistrer
   un gestionnaire de signal temporaire pour tous les signaux qu'il
   est configuré pour intercepter. Ce gestionnaire de signal fait deux
   choses.
   1. Il enregistre le numéro du signal reçu
      dans une variable de portée fichier.
   2. Il appelle ensuite la fonction POSIX siglongjmp()
      en utilisant le tampon qui a été passé à
      sigsetjmp() comme premier argument, et
      une valeur non nulle comme second argument.
   Lorsque ce gestionnaire de signal est enregistré, le membre sa_mask
   de l'argument struct sigaction act de
   l'appel à sigaction() est configuré pour contenir tous
   les signaux que gl_get_line() intercepte. Cela
   garantit qu'un seul signal sera intercepté à la fois par
   notre gestionnaire de signal, ce qui à son tour garantit que
   plusieurs instances de notre gestionnaire de signal ne se
   marchent pas sur les pieds.
b. Maintenant que le gestionnaire de signal a été configuré,
   gl_get_line() débloque tous les signaux qu'il
   est configuré pour intercepter.

   les entrées du clavier.

   d'intérêt.

   déplacés par celui qui vient d'être
installé.

Sur la plupart des systèmes, la combinaison de l'ioctl TIOCGWINSZ et du signal SIGWINCH est utilisée pour maintenir une idée précise de la taille du terminal. La taille du terminal est nouvellement interrogée à chaque fois que gl_get_line() est appelé et à chaque fois qu'un signa

et

Si elles ne sont pas trouvées, ou si elles contiennent des valeurs inutilisables, alors si une base de données d'informations sur le terminal comme terminfo ou termcap est disponible, la taille par défaut du terminal est recherchée dans cette base de données. Si cela échoue également à fournir la taille du terminal, une taille par défaut de 80 colonnes par 24 lignes est utilisée. Même sur les systèmes qui prennent en charge ioctl(TIOCGWINSZ), si le terminal se trouve à l'autre bout d'une ligne série, le pilote du terminal n'a généralement aucun moyen de détecter quand un redimensionnement se produit ou d'interroger la taille actuelle. Dans de tels cas, aucun SIGWINCH n'est envoyé au processus, et les dimensions retournées par ioctl(TIOCGWINSZ) ne sont pas correctes. La seule façon de gérer de tels cas est de fournir un moyen à l'utilisateur d'entrer une commande qui indique au système distant quelle est la nouvelle taille. Cette commande appellerait alors la fonction gl_set_term_size() pour

CACHER CE QUE VOUS TAPEZ Lors de la saisie d'informations sensibles, telles que des mots de passe, il est préférable de ne pas faire écho sur le terminal du texte que vous saisissez. De plus, ce texte ne devrait pas être enregistré dans la liste d'historique, car quelqu'un trouvant votre terminal sans surveillance pourrait alors le rappeler, ou quelqu'un fouillant dans vos répertoires pourrait le voir dans votre fichier d'historique. En gardant cela à l'esprit, la fonction gl_echo_mode() vous permet d'activer et de désactiver l'affichage et l'archivage de tout texte qui est saisi ultérieurement dans

les appels à 
  gl_get_line()
.

int gl_echo_mode(GetLine *gl, int enable); L'argument enable spécifie si le texte saisi doit être visible ou non. S'il est 0, alors les lignes saisies ultérieurement ne seront pas visibles sur le terminal, et ne seront pas enregistrées dans la liste d'historique. S'il est 1, alors les lignes saisies ultérieurement seront affichées au fur et à mesure de leur saisie, et à condition que l'historique n'ait pas été désactivé via un appel à gl_toggle_history(), elles seront également archivées dans la liste d'historique. Enfin, si l'argument enable est -1, alors le mode d'écho est laissé inchangé, ce qui vous permet d'interroger le paramètre actuel de manière non destructive via la valeur de retour. Dans tous les cas, la valeur de retour de la fonction est 0 si l'écho était désactivé avant l'appel de la fonction,

et

1 s'il

était
activé.

Lorsque l'écho est désactivé, notez que même si la complétion par tabulation complétera votre préfixe de manière invisible aussi loin que possible, les complétions ambiguës ne seront pas

affichées.

REQUÊTES À CARACTÈRE UNIQUE Utiliser gl_get_line() pour demander à l'utilisateur une réponse d'un seul caractère est incommode pour l'utilisateur, car il doit appuyer sur la touche entrée ou retour avant que le caractère qu'il a tapé soit renvoyé au programme. C'est pourquoi

la 
  fonction gl_query_char() a été fournie pour les requêtes à un seul caractère comme
celle-ci.

int gl_query_char(GetLine *gl, const char *prompt, char defchar); Cette fonction affiche l'invite spécifiée au début d'une nouvelle ligne, et attend que l'utilisateur tape un caractère. Lorsque l'utilisateur tape un caractère, gl_query_char() l'affiche à droite de l'invite, passe à la ligne suivante, puis renvoie le caractère au programme appelant. La valeur de retour de la fonction est le caractère qui a été tapé. Si la lecture a dû être interrompue pour une raison quelconque, EOF est renvoyé à la place. Dans ce dernier cas, l'application peut appeler la fonction gl_return_status() précédemment documentée, pour savoir ce qui s'est mal passé. Cela aurait pu être, par exemple, la réception d'un signal, ou le déclenchement du minuteur d'inactivité

optionnel.

Si l'utilisateur appuie simplement sur entrée, la valeur de l'argument defchar est substituée. Cela signifie que lorsque l'utilisateur appuie sur nouvelle ligne ou retour, le caractère spécifié dans defchar est affiché après l'invite, comme si l'utilisateur l'avait tapé, ainsi qu'être renvoyé à l'application appelante. Si un tel remplacement n'est pas important, passez simplement '0 comme valeur de defchar

.

Si le caractère saisi est un caractère non imprimable, il est affiché symboliquement. Par exemple, contrôle-A est affiché comme ^A, et les caractères au-delà de 127 sont affichés en octal, précédés d'une barre oblique

inverse.

Comme avec gl_get_line(), l'écho du caractère saisi peut être désactivé en utilisant la fonction gl_echo_mode()

.

Si le processus appelant est suspendu pendant qu'il attend que l'utilisateur tape sa réponse, le curseur est déplacé à la ligne suivant la ligne d'invite, puis lorsque le processus reprend, l'invite est réaffichée, et gl_query_char() reprend l'attente que l'utilisateur tape un

caractère.

Notez qu'en mode serveur non bloquant, (voir gl_io_mode(3)), si une ligne de saisie incomplète est en cours de lecture lorsque gl_query_char() est appelé, la ligne de saisie partielle est abandonnée, et effacée du terminal, avant que la nouvelle invite ne soit affichée. Le prochain appel à gl_get_line() commencera donc

à éditer une n
ouvelle ligne.

BRUTS

Alors que la fonction gl_query_char() invite visiblement l'utilisateur à saisir un caractère, et affiche ce qu'il a tapé, la fonction gl_read_char() lit un caractère de signal de l'utilisateur, sans rien écrire sur le terminal, ni perturber une ligne de saisie incomplète. Cela signifie qu'elle peut être appelée non seulement entre les appels à gl_get_line(), mais aussi depuis des fonctions de rappel que l'application a enregistrées pour être appelées par gl_get_li

ne().

;

En cas de succès, la valeur de retour de gl_read_char() est le caractère qui a été lu. En cas d'échec, EOF est renvoyé, et la fonction gl_return_status() peut être appelée pour savoir ce qui s'est mal passé. Les possibilités incluent le déclenchement du minuteur d'inactivité optionnel, la réception d'un signal configuré pour interrompre gl_get_line(), ou le blocage des E/S du terminal, en mode E/S serveur non

bloquant.

AFFICHAGE DYNAMIQUE DE TEXTE

Entre les appels à gl_get_line(), la fonction gl_display_text() offre un moyen pratique d'afficher des paragraphes de texte, justifiés à gauche et répartis sur une ou plusieurs lignes de terminal selon les contraintes de la largeur actuelle du terminal. Des exemples d'utilisation de cette fonction se trouvent dans les programmes de démonstration, où elle est utilisée pour afficher des introductions. Dans ces exemples, l'utilisation avancée de préfixes, de suffixes et de lignes de remplissage optionnels pour dessiner une boîte autour du texte est également illustrée.

  int gl_display_text(GetLine *gl, int indentation,
                      const char *prefix,
                      const char *suffix, int fill_char,
                      int def_width, int start,
                      const char *string);

Si gl n'est actuellement pas connecté à un terminal, par exemple si la sortie d'un programme utilisant gl_get_line() est redirigée vers un autre programme ou vers un fichier, alors la valeur du paramètre def_width est utilisée comme largeur du terminal.

L'argument indentation spécifie le nombre de caractères à utiliser pour indenter chaque ligne de sortie. L'argument fill_char spécifie le caractère qui sera utilisé pour effectuer cette indentation.

L'argument prefix peut être NULL, ou une chaîne à placer au début de chaque nouvelle ligne (après toute indentation). De même, l'argument suffix peut être NULL, ou une chaîne à placer à la fin de chaque ligne. Le suffixe est placé au ras du bord droit du terminal, et tout espace entre son premier caractère et le dernier mot de cette ligne est rempli avec le caractère spécifié via l'argument fill_char. Normalement, le caractère de remplissage est un espace.

L'argument start indique à gl_display_text() le nombre de caractères déjà écrits sur la ligne de terminal actuelle, et indique donc l'indice de la colonne de départ du curseur. Étant donné que la valeur de retour de gl_display_text() est l'indice de la colonne de fin du curseur, en passant la valeur de retour d'un appel à l'argument start du prochain appel, un paragraphe divisé en plusieurs chaînes peut être composé en appelant gl_display_text() pour chaque portion successive du paragraphe. Notez que des caractères de nouvelle ligne littéraux sont nécessaires à la fin de chaque paragraphe pour forcer le démarrage d'une nouvelle ligne.

En cas d'erreur, gl_display_text() retourne -1.

FACILITÉS DE FONCTIONS DE RAPPEL

Sauf indication contraire, les fonctions de rappel, telles que les fonctions de rappel de complétion de tabulation et les fonctions de rappel d'événements, ne doivent appeler aucune fonction de ce module. Les fonctions suivantes, cependant, sont conçues spécifiquement pour être utilisées par les fonctions de rappel.

Appeler la fonction gl_replace_prompt() à partir d'un rappel indique à gl_get_line() d'afficher une invite différente lorsque le rappel se termine. Sauf en mode serveur non bloquant, elle n'a aucun effet lorsqu'elle est utilisée entre les appels à gl_get_line(). En mode serveur non bloquant (voir la page de manuel gl_io_mode(3), lorsqu'elle est utilisée entre deux appels à gl_get_line() qui opèrent sur la même ligne d'entrée, la ligne d'entrée actuelle sera redessinée avec la nouvelle invite lors du prochain appel à gl_get_line().

  void gl_replace_prompt(GetLine *gl, const char *prompt);

JEUX DE CARACTÈRES INTERNATIONAUX

Depuis la version 1.4.0 de libtecla, gl_get_line() est compatible avec les 8 bits. Cela signifie que tous les caractères 8 bits imprimables dans la locale actuelle de l'utilisateur sont maintenant affichés verbatim et inclus dans la ligne d'entrée retournée. En supposant que le programme appelant contient correctement un appel tel que le suivant,

  setlocale(LC_CTYPE, "");

alors la locale actuelle est déterminée par la première des variables d'environnement LC_CTYPE, LC_ALL, et LANG, qui est trouvée pour contenir un nom de locale valide. Si aucune de ces variables n'est définie, ou si le programme néglige d'appeler setlocale, alors la locale par défaut C est utilisée, qui est l'ASCII 7 bits américain. Sur la plupart des plateformes de type Unix, vous pouvez obtenir une liste des locales valides en tapant la commande :

  locale -a

à l'invite du shell. D'autres informations sur la manière dont l'utilisateur peut utiliser ceci pour entrer des caractères internationaux se trouvent dans la page de manuel tecla(7).

SÉCURITÉ DES THREADS

Dans un programme multi-threadé, vous devez utiliser la version libtecla_r.a de la bibliothèque. Celle-ci utilise des versions réentrantes des fonctions système, lorsque disponibles. Malheureusement, ni terminfo ni termcap n'ont été conçus pour être réentrants, vous ne pouvez donc pas utiliser en toute sécurité les fonctions du module getline dans plusieurs threads (vous pouvez utiliser les modules séparés d'expansion de fichiers et de complétion de mots dans plusieurs threads, voir les pages de manuel correspondantes pour les détails). Cependant, en raison de l'utilisation de fonctions réentrantes POSIX pour la recherche de répertoires personnels, etc., il est sûr d'utiliser ce module à partir d'un seul thread d'un programme multi-threadé, à condition que vos autres threads n'utilisent aucune fonction termcap ou terminfo.
