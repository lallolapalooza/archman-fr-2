N

glBufferStorage et glNamedBufferStorage créent un nouveau magasin de données immuable. Pour glBufferStorage, l'objet tampon actuellement lié à target sera initialisé. Pour glNamedBufferStorage, buffer est le nom de l'objet tampon qui sera configuré. La taille du magasin de données est spécifiée par size. Si des données initiales sont disponibles, leur adresse peut être fournie dans data. Sinon, pour créer un magasin de données non initialisé, data devrait être NULL

GL_DYNAMIC_STORAGE_BI

T
Le contenu du magasin de données peut être mis à jour après la création par des appels à glBufferSubData(). Si ce bit n'est pas défini, le contenu du tampon ne peut pas être mis à jour directement par le client. L'argument data peut être utilisé pour spécifier le contenu initial du magasin de données du tampon indépendamment de la présence de GL_DYNAMIC_STORAGE_BIT. Indépendamment de la présence de ce bit, les tampons peuvent toujours être mis à jour par des appels côté serveur tels que glCopyBufferSubData() et glClearBufferSu
bData().

GL_MAP_READ_BI

T
Le magasin de données peut être mappé par le client pour un accès en lecture et un pointeur dans l'espace d'adressage du client est obtenu à partir duquel on peut
lire.

GL_MAP_WRITE_BI

T
Le magasin de données peut être mappé par le client pour un accès en écriture et un pointeur dans l'espace d'adressage du client est obtenu à travers lequel on peut
écrire.

GL_MAP_PERSISTENT_BI

T
Le client peut demander que le serveur lise depuis ou écrive dans le tampon pendant qu'il est mappé. Le pointeur du client vers le magasin de données reste valide tant que le magasin de données est mappé, même pendant l'exécution de commandes de dessin ou de
dispatch.

GL_MAP_COHERENT_BI

T
L'accès partagé aux tampons qui sont simultanément mappés pour un accès client et utilisés par le serveur sera cohérent, tant que cette mappage est effectué en utilisant glMapBufferRange(). C'est-à-dire que les données écrites dans le magasin par le client ou le serveur seront immédiatement visibles pour l'autre sans aucune action supplémentaire de l'application. En particulier,
•Si GL_MAP_COHERENT_BIT n'est pas défini et le client effectue une écriture suivie d'un appel à la commande glMemoryBarrier() avec le GL_CLIENT_MAPPED_BUFFER_BARRIER_BIT défini, alors dans les commandes suivantes le serveur verra les
écritures.
•Si GL_MAP_COHERENT_BIT est défini et le client effectue une écriture, alors dans les commandes suivantes le serveur verra les
écritures.
•Si GL_MAP_COHERENT_BIT n'est pas défini et le serveur effectue une écriture, l'application doit appeler glMemoryBarrier() avec le GL_CLIENT_MAPPED_BUFFER_BARRIER_BIT défini puis appeler glFenceSync() avec GL_SYNC_GPU_COMMANDS_COMPLETE (ou glFinish). Alors le CPU verra les écritures après que la synchronisation est

NAME

glBufferStorage - allocate and initialize a buffer object's immutable storage

C SPECIFICATION

    void glBufferStorage(
        GLenum target,
        GLsizeiptr size,
        const void *data,
        GLbitfield flags
    );

PARAMETERS

target
Specifies the target buffer object. The symbolic constant must be GL_ARRAY_BUFFER, GL_ATOMIC_COUNTER_BUFFER, GL_COPY_READ_BUFFER, GL_COPY_WRITE_BUFFER, GL_DRAW_INDIRECT_BUFFER, GL_ELEMENT_ARRAY_BUFFER, GL_PIXEL_PACK_BUFFER, GL_PIXEL_UNPACK_BUFFER, GL_QUERY_BUFFER, GL_SHADER_STORAGE_BUFFER, GL_TEXTURE_BUFFER, GL_TRANSFORM_FEEDBACK_BUFFER, or GL_UNIFORM_BUFFER.
size
Specifies the size, in basic memory units, of the buffer object to be created.
data
Specifies the source of data to be copied into the newly created buffer object. If NULL, then no data is copied. Otherwise, a pointer to an array of <size> basic memory units is taken as the source of the data.
flags
A bitwise combination of buffer object creation flags. The allowed flags are: GL_DYNAMIC_STORAGE_BIT, GL_MAP_COHERENT_BIT, GL_MAP_INVALIDATE_BUFFER_BIT, GL_MAP_INVALIDATE_RANGE_BIT, GL_MAP_FLUSH_EXPLICIT_BIT, and GL_CLIENT_STORAGE_BIT.

DESCRIPTION

glBufferStorage creates a new buffer object of the specified target, and allocates and initializes its immutable storage. This function can be used to create the buffer object's storage exactly once. Subsequent calls to glBufferStorage for a buffer object that has already had its immutable storage created will result in a GL_INVALID_OPERATION error.

The size parameter specifies the size of the new buffer object in basic memory units. If size is negative, an GL_INVALID_VALUE error is generated.

If data is not NULL, then the contents of the newly allocated buffer object memory are initialized with the contents of the array pointed to by data. The array must contain at least size basic memory units. If data is NULL, then the initial contents of the buffer object are immutable and undefined.

The flags parameter is a bitmask indicating how the buffer object's storage can be accessed. The flags are:

GL_DYNAMIC_STORAGE_BIT
If this flag is set, then the buffer's storage is mutable. This means that the buffer may be re-sized or re-initialized using commands like glBufferSubData or glBufferData. If this flag is not set, the buffer's storage is immutable, and attempting to resize or re-initialize it will result in an error. Note that if GL_DYNAMIC_STORAGE_BIT is not specified, then glBufferStorage will also implicitly specify GL_MAP_COHERENT_BIT.
GL_MAP_COHERENT_BIT
If this flag is set, buffer object memory may be accessed coherently through memory mapping operations. Coherent memory mapping guarantees that writes made to the buffer object memory are visible to all processors. This flag is implicitly set if GL_DYNAMIC_STORAGE_BIT is not set.
GL_MAP_INVALIDATE_BUFFER_BIT
If this flag is set, then the buffer's memory may be discarded and re-initialized. This flag is meaningful only when combined with GL_DYNAMIC_STORAGE_BIT.
GL_MAP_INVALIDATE_RANGE_BIT
If this flag is set, then portions of the buffer's memory may be discarded and re-initialized. This flag is meaningful only when combined with GL_DYNAMIC_STORAGE_BIT.
GL_MAP_FLUSH_EXPLICIT_BIT
If this flag is set, then explicit calls to glFlushMappedBufferRange are required to make writes to the buffer visible to the OpenGL pipeline. This flag is meaningful only when combined with GL_DYNAMIC_STORAGE_BIT.
GL_CLIENT_STORAGE_BIT
If this flag is set, then the buffer data may be stored in client-side memory. This can potentially improve performance by avoiding copies of the data to graphics memory.

The buffer object becomes mutable (i.e., its contents may be modified) if and only if the GL_DYNAMIC_STORAGE_BIT is specified when the buffer is created.

A buffer object can have its immutable storage created only once. Subsequent calls to glBufferStorage for a buffer object that has already had its immutable storage created will result in a GL_INVALID_OPERATION error. A call to glBufferStorage will create immutable storage if the GL_DYNAMIC_STORAGE_BIT flag is not specified.

NOTES

The buffer object's immutable storage is created when glBufferStorage is called. This means that the buffer object will have a fixed size and cannot be reallocated or reinitialized by subsequent calls to glBufferData or glBufferSubData, unless the GL_DYNAMIC_STORAGE_BIT flag is specified.

If the GL_DYNAMIC_STORAGE_BIT flag is not specified, then the buffer object's storage is immutable. This means that the buffer object cannot be re-sized or re-initialized using commands like glBufferSubData or glBufferData.

If the GL_DYNAMIC_STORAGE_BIT flag is not specified, then the buffer object's storage is also implicitly mapped coherently. This means that buffer object memory may be accessed coherently through memory mapping operations. Coherent memory mapping guarantees that writes made to the buffer object memory are visible to all processors.

GL_INVALID_OPERATION is generated if the buffer object named by target is not a valid buffer object name.

GL_INVALID_OPERATION is generated if the buffer object named by target has immutable storage and either GL_DYNAMIC_STORAGE_BIT is not specified, or if GL_DYNAMIC_STORAGE_BIT is specified but the buffer is being modified by a previous call to glBufferSubData.

GL_INVALID_OPERATION is generated if the buffer object named by target has immutable storage and GL_DYNAMIC_STORAGE_BIT is not specified, and a subsequent call to glBufferStorage is made on the same buffer.
