NOM

glib-mkenums - utilitaire de génération de descriptions d'énumérations en langage C

SYNOPSIS

glib-mkenums [OPTION…] [FICHIER…]

DESCRIPTION

glib-mkenums est un petit utilitaire qui analyse le code C pour extraire les définitions d'énumérations et produit des descriptions d'énumérations basées sur des modèles de texte spécifiés par l'utilisateur. Typiquement, vous pouvez utiliser cet outil pour générer des types d'énumération pour le système de types GType, pour les propriétés GObject et le marshalling de signaux ; de plus, vous pouvez l'utiliser pour générer les valeurs d'énumération des schémas GSettings.

glib-mkenums prend une liste de fichiers de code C valides en entrée. Les options spécifiées contrôlent le texte généré, en substituant divers mots-clés entourés de @ dans les modèles.

Depuis la version 2.74, GLib fournit les G_DEFINE_ENUM_TYPE et G_DEFINE_FLAGS_TYPE macros de préprocesseur C. Ces macros peuvent être utilisées pour définir un GType pour les projets qui ont peu, de petits types d'énumération sans passer par les complexités de la génération de code au moment de la compilation.

PRODUCTION SUBSTITUTIONS DE TEXTE

Certains mots-clés entourés de @ seront substitués dans le texte émis. Pour les exemples de substitution des mots-clés ci-dessous, la définition d'énumération suivante est supposée :

typedef enum
{
  PREFIX_THE_XVALUE    = 1 << 3,
  PREFIX_ANOTHER_VALUE = 1 << 4
} PrefixTheXEnum;

@EnumName@

Le nom de l'énumération en cours de traitement, les noms d'énumération sont supposés être correctement espacés et utiliser une capitalisation mixte pour séparer les mots (par ex. PrefixTheXEnum).

@enum_name@

Le nom de l'énumération avec les mots en minuscules et séparés par des soulignés (par ex. prefix_the_xenum).

@ENUMNAME@

Le nom de l'énumération avec les mots en majuscules et séparés par des soulignés (par ex. PREFIX_THE_XENUM).

@ENUMSHORT@

Le nom de l'énumération avec les mots en majuscules et séparés par des soulignés, préfixe supprimé (par ex. THE_XENUM).

@ENUMPREFIX@

Le préfixe du nom de l'énumération (par ex. PREFIX).

@VALUENAME@

Le nom de la valeur d'énumération en cours de traitement avec les mots en majuscules et séparés par des soulignés, c'est la notation littérale supposée des valeurs d'énumération dans les sources C (par ex. PREFIX_THE_XVALUE).

@valuenick@

Un surnom pour la valeur d'énumération en cours de traitement, celui-ci est généralement généré en supprimant les mots de préfixe communs de toutes les valeurs d'énumération de l'énumération courante, les mots sont en minuscules et les soulignés sont remplacés par un tiret (par ex. the-xvalue).

@valuenum@

La valeur entière pour la valeur d'énumération en cours de traitement. Si l'évaluation échoue alors glib-mkenums se terminera avec un code d'erreur, mais cela n'arrive que si @valuenum@ apparaît dans votre modèle de production de valeur. (Depuis : 2.26)

@type@

Cela est substitué soit par « enum » ou « flags », selon que les définitions de valeurs d'énumération contiennent des opérateurs de décalage de bits (par ex. flags).

@Type@

Identique à @type@ avec la première lettre en majuscule (par ex. Flags).

@TYPE@

Identique à @type@ avec toutes les lettres en majuscules (par ex. FLAGS).

@filename@

Le chemin complet du fichier d'entrée en cours de traitement (par ex. /build/environment/project/src/foo.h).

@basename@

Le nom de base du fichier d'entrée en cours de traitement (par ex. foo.h). Typiquement, vous voudrez utiliser @basename@ à la place de @filename@ dans vos modèles, pour améliorer la reproductibilité de la compilation. (Depuis : 2.22)

EXTENSIONS TRIGRAPHES

Certains commentaires C sont traités spécialement dans les définitions d'énumération analysées, de tels commentaires commencent par la séquence trigraphe /*< et se terminent par la séquence trigraphe >*/.

Les options suivantes peuvent être spécifiées par définition d'énumération :

skip

Indique que cette définition d'énumération doit être ignorée.

flags

Indique que cette énumération doit être traitée comme une définition de drapeaux.

underscore_name

Spécifie la séparation des mots utilisée dans la *_get_type() fonction. Par exemple, /*< underscore_name=gnome_vfs_uri_hide_options >*/.

since

Spécifie l'étiquette de version qui sera utilisée pour substituer le @enumsince@ mot-clé dans le modèle, utile pour documenter les méthodes générées à partir des énumérations (par ex. Since: @enumsince@). (Depuis : 2.66)

Les options suivantes peuvent être spécifiées par définition de valeur :

skip

Indique que la valeur doit être ignorée.

nick

Spécifie le surnom autrement généré automatiquement.

Exemples :

typedef enum /*< skip >*/
{
  PREFIX_FOO
} PrefixThisEnumWillBeSkipped;
typedef enum /*< flags,prefix=PREFIX,since=1.0 >*/
{
  PREFIX_THE_ZEROTH_VALUE,   /*< skip >*/
  PREFIX_THE_FIRST_VALUE,
  PREFIX_THE_SECOND_VALUE,
  PREFIX_THE_THIRD_VALUE,    /*< nick=the-last-value >*/
} PrefixTheFlagsEnum;

OPTIONS

--fhead <TEXTE>

Émet TEXTE avant le traitement des fichiers d'entrée.

Vous pouvez spécifier cette option plusieurs fois, et le TEXTE sera concaténé.

Lorsqu'elle est utilisée avec un fichier modèle, TEXTE sera préfixé à la section file-header du modèle.

--fprod <TEXTE>

Émet TEXTE chaque fois qu'un nouveau fichier d'entrée est traité.

Vous pouvez spécifier cette option plusieurs fois, et le TEXTE sera concaténé.

Lorsqu'elle est utilisée avec un fichier modèle, TEXTE sera ajouté à la section file-production du modèle.

--ftail <TEXTE>

Émet TEXTE après que tous les fichiers d'entrée ont été traités.

Vous pouvez spécifier cette option plusieurs fois, et le TEXTE sera concaténé.

Lorsqu'elle est utilisée avec un fichier modèle, TEXTE sera ajouté à la section file-tail du modèle.

--eprod <TEXTE>

Émet TEXTE chaque fois qu'une énumération est rencontrée dans les fichiers d'entrée.

--vhead <TEXTE>

Émet TEXTE avant d'itérer sur l'ensemble des valeurs d'une énumération.

Vous pouvez spécifier cette option plusieurs fois, et le TEXTE sera concaténé.

Lorsqu'elle est utilisée avec un fichier modèle, TEXTE sera préfixé à la section value-header du modèle.

--vprod <TEXTE>

Émet TEXTE pour chaque valeur d'une énumération.

Vous pouvez spécifier cette option plusieurs fois, et le TEXTE sera concaténé.

Lorsqu'elle est utilisée avec un fichier modèle, TEXTE sera ajouté à la section value-production du modèle.

--vtail <TEXTE>

Émet TEXTE après avoir itéré sur toutes les valeurs d'une énumération. s="Pp">Vous pouvez spécifier cette option plusieurs fois, et le TEXTE sera concaténé.

Lorsqu'il est utilisé avec un fichier de modèle, TEXTE sera ajouté à la section value-tail du modèle.

--comments <TEXTE>

Modèle pour les commentaires générés automatiquement, la valeur par défaut (pour les générations de code C) est "/* @comment@ */".

--template <FICHIER>

Lire les modèles depuis le fichier donné. Les modèles sont encadrés par des commentaires C spécialement formatés : 
/*** BEGIN section ***/
/*** END section ***/

section peut être file-header, file-production, file-tail, enumeration-production, value-header, value-production, value-tail ou comment.

--identifier-prefix <PRÉFIXE>

Indique quelle portion du nom de l'énumération doit être interprétée comme le préfixe (par exemple le Gtk dans GtkDirectionType). Normalement, cela est déterminé automatiquement, mais vous devrez peut-être remplacer la valeur par défaut si votre espace de noms est capitalisé de manière inhabituelle.

--symbol-prefix <PRÉFIXE>

Indique quel préfixe doit être utilisé pour correspondre au préfixe d'identifiant dans les noms de fonctions C associés (par exemple le gtk dans gtk_direction_type_get_type). De manière équivalente, il s'agit de la version en minuscules du composant préfixe des noms de valeurs d'énumération (par exemple le GTK dans GTK_DIR_UP). La valeur par défaut est le préfixe d'identifiant, converti en minuscules.

--help

Afficher une aide brève et quitter.

--version

Afficher la version et quitter.

--output <FICHIER>

Écrire la sortie dans FICHIER au lieu de la sortie standard.

@RSPFILE

Lorsqu'il est passé comme unique argument, lire et analyser les arguments réels depuis RSPFILE. Utile sur les systèmes avec une limite de longueur de ligne de commande faible. Par exemple, Windows a une limite de 8191 caractères.

UTILISATION DES MODÈLES

Au lieu de passer les différentes sections du fichier généré à la ligne de commande de glib-mkenums, il est fortement recommandé d'utiliser un fichier de modèle, en particulier pour générer des sources C.

Un fichier de modèle d'en-tête C ressemblera typiquement à ceci :

/*** BEGIN file-header ***/
#pragma once
/* Include the main project header */
#include "project.h"
G_BEGIN_DECLS
/*** END file-header ***/
/*** BEGIN file-production ***/
/* enumerations from "@basename@" */
/*** END file-production ***/
/*** BEGIN value-header ***/
GType @enum_name@_get_type (void) G_GNUC_CONST;
#define @ENUMPREFIX@_TYPE_@ENUMSHORT@ (@enum_name@_get_type ())
/*** END value-header ***/
/*** BEGIN file-tail ***/
G_END_DECLS
/*** END file-tail ***/

Un fichier de modèle de source C ressemblera typiquement à ceci :

/*** BEGIN file-header ***/
#include "config.h"
#include "enum-types.h"
/*** END file-header ***/
/*** BEGIN file-production ***/
/* enumerations from "@basename@" */
/*** END file-production ***/
/*** BEGIN value-header ***/
GType
@enum_name@_get_type (void)
{
  static GType static_g_@type@_type_id = 0;
  if (g_once_init_enter_pointer (&static_g_@type@_type_id))
    {
      static const G@Type@Value values[] = {
/*** END value-header ***/
/*** BEGIN value-production ***/
        { @VALUENAME@, "@VALUENAME@", "@valuenick@" },
/*** END value-production ***/
/*** BEGIN value-tail ***/
        { 0, NULL, NULL }
      };
      GType g_@type@_type_id =
        g_@type@_register_static (g_intern_static_string ("@EnumName@"), values);
      g_once_init_leave_pointer (&static_g_@type@_type_id, g_@type@_type_id);
    }
  return static_g_@type@_type_id;
}
/*** END value-tail ***/

Les fichiers de modèle sont plus faciles à modifier et à mettre à jour, et peuvent être utilisés pour générer différents types de sorties en utilisant la même ligne de commande ou les mêmes outils pendant la compilation.

UTILISATION DE GLIB-MKENUMS AVEC MESON

Meson prend en charge la génération de types d'énumération en utilisant glib-mkenums directement dans son module gnome

. Dans votre fichier meson.build vous appellerez généralement la méthode gnome.mkenums_simple()

pour générer des types d'énumération idiomatiques
    à partir d'une liste d'en-têtes à inspecter :

project_headers = [ 'project-foo.h', 'project-bar.h', 'project-baz.h', ] gnome = import('gnome') enum_files = gnome.mkenums_simple('enum-types', sources: project_headers, ) La variable enum_files

contiendra un tableau de deux éléments dans l'ordre suivant :
1.
une cible de compilation pour le fichier source
2.

une cible de compilation pour le fichier d'en-tête

Vous devriez utiliser les objets retournés pour fournir une dépendance à
    chaque autre cible de compilation qui référence le fichier source ou d'en-tête ; par
    exemple, si vous utilisez le source pour construire une bibliothèque :

mainlib = library('project', sources: project_sources + enum_files, … )

De plus, si vous incluez le fichier d'en-tête généré
    dans une cible de compilation qui dépend de la bibliothèque que vous venez de construire, vous devez
    vous assurer que la dépendance interne inclut l'en-tête généré en tant que
    fichier source requis :

mainlib_dep = declare_dependency(sources: enum_files[1], link_with: mainlib) Vous ne devriez pas inclure le fichier source généré également, sinon il sera compilé séparément pour chaque cible qui en dépend, causant des échecs de compilation. Pour en savoir plus sur pourquoi tout cela est requis, veuillez consulter l'entrée de FAQ Meson correspondantehttps://mesonbuild.com/FAQ.html#how-do-i-tell-meson-that-my-sources-use-generated-headers

. Si vous générez des fichiers d'en-tête et de source C qui nécessitent des modèles spéciaux, vous pouvez utiliser gnome.mkenums()

pour fournir ces
    en-têtes, par exemple :

enum_files = gnome.mkenums('enum-types', sources: project_headers, h_template: 'enum-types.h.in', c_template: 'enum-types.c.in', install_header: true, ) Pour plus d'informations, voir la documentation de Meson https://mesonbuild.com/Gnome-module.html#gnomegenmarshal pourgnome.mkenums()

.

UTILISATION DE GLIB-MKENUMS AVEC AUTOTOOLS Afin d'utiliser glib-mkenums dans votre projet lors de l'utilisation d'Autotools comme système de compilation, vous devrez d'abord modifier votre fichier configure.ac pour vous assurer de trouver la commande appropriée en utilisantpkg-config

, de manière similaire à la façon dont vous découvrez les indicateurs
    du compilateur et de l'éditeur de liens pour GLib :

PKG_PROG_PKG_CONFIG([0.28]) PKG_CHECK_VAR([GLIB_MKENUMS], [glib-2.0], [glib_mkenums]) Dans votre fichier Makefile.am

vous utiliserez généralement des règles comme
    celles-ci :

# A list of headers to inspect project_headers = \ project-foo.h \ project-bar.h \ project-baz.h enum-types.h: $(project_headers) enum-types.h.in $(AM_V_GEN)$(GLIB_MKENUMS) \ --template=enum-types.h.in \ --output=$@ \ $(project_headers) enum-types.c: $(project_headers) enum-types.c.in enum-types.h $(AM_V_GEN)$(GLIB_MKENUMS) \ --template=enum-types.c.in \ --output=$@ \ $(project_headers) # Build the enum types files before every other target BUILT_SOURCES += enum-types.h enum-types.c CLEANFILES += enum-types.h enum-types.c EXTRA_DIST += enum-types.h.in enum-types.c.in Dans l'exemple ci-dessus, nous avons une variable appelée project_headers où nous référençons tous les fichiers d'en-tête que nous voulons inspecter pour générer les GTypes d'énumération. Dans la règle enum-types.h nous utilisons glib-mkenums avec un modèle appelé enum-types.h.in afin de générer le fichier d'en-tête ; de manière similaire, dans la règleenum-types.c

nous utilisons un modèle appelé

enum-types.c.in

.
