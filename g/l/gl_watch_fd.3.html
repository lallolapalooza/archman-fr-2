L

a

fonction gl_get_line() fait partie de la bibliothèque tecla (voir la page man libtecla(3)). Si l'utilisateur tape sur un terminal, chaque appel l'invite à saisir une ligne d'entrée, puis fournit des fonctionnalités d'édition interactives, similaires à celles du shell tcsh unix. En plus de l'édition simple de ligne de commande, elle prend en charge le rappel des lignes de commande précédemment saisies, l'achèvement par TAB des noms de fichiers et l'expansion des caractères génériques dans les noms de fichiers en ligne. La documentation des fonctionnalités d'édition de ligne de commande au niveau utilisateur ainsi que de toutes les options de configuration utilisateur se trouve dans la page man tecla(7). Cette page man concerne la documentation destinée aux programmeurs souhaitant utiliser cette bibliothèque dans leur application. UN E

LES FONCTIONS UTILISÉES DANS

L'EXEMPLE

Les descriptions des fonctions utilisées dans l'exemple sont les suivantes

: 
  GetLine *new_GetLine(size_t linelen, size_t
histlen)

Cette fonction crée les ressources utilisées par la fonction gl_get_line() et renvoie un pointeur opaque vers l'objet qui les contient. La longueur maximale d'une ligne d'entrée est spécifiée via l'argument linelen, et le nombre d'octets à allouer pour stocker les lignes d'historique est défini par l'argument histlen. Les lignes d'historique sont stockées bout à bout dans un seul tampon de cette taille. Notez que cela signifie que le nombre de lignes d'historique pouvant être stockées à un moment donné dépend des longueurs des lignes individuelles. Si vous souhaitez placer une limite supérieure au nombre de lignes pouvant être stockées, voir la fonction gl_limit_history() décrite plus loin. Si vous ne voulez pas d'historique du tout, spécifiez histlen comme zéro, et aucun tampon d'historique ne sera

alloué.

En cas d'erreur, un message est imprimé sur stderr et NULL est

renvoyé. 
  GetLine *del_GetLine(GetLine
*gl)

Cette fonction supprime les ressources qui ont été renvoyées par un appel précédent à new_GetLine(). Elle renvoie toujours NULL (c'est-à-dire un objet supprimé). Elle ne fait rien si l'argument gl est NULL

. 
  char *gl_get_line(GetLine *gl, const char *prompt,
                   const char *start_line, int start_pos)
;

La fonction gl_get_line() peut être appelée un nombre quelconque de fois pour lire la saisie de l'utilisateur. L'argument gl doit avoir été précédemment renvoyé par un appel à new_GetLine(). L'argument prompt doit être une chaîne normale terminée par NUL, spécifiant l'invite à présenter à l'utilisateur. Par défaut, les invites sont affichées littéralement, mais si activées avec la fonction gl_prompt_style() (voir plus loin), les invites peuvent contenir des directives pour souligner, passer aux polices en gras et en revenir, ou activer et désactiver la mise en

évidence.

Si vous souhaitez spécifier le contenu initial de la ligne pour que l'utilisateur la modifie, transmettez la chaîne souhaitée via l'argument start_line. Vous pouvez ensuite spécifier le caractère de cette ligne sur lequel le curseur est initialement positionnér, à l'aide de l'argument start_pos. Cela doit être -1 si vous voulez que le curseur suive le dernier caractère de la ligne de départ. Si vous ne voulez pas précharger la ligne de cette manière, envoyez start_line comme NULL, et définissez start_pos à -1. Notez que le pointeur de ligne retourné par un appel à gl_get_line() peut être transmis à l'appel suivant à gl_get_line() via start_line. Cela permet à l'application de prendre la dernière ligne saisie et, si elle contient une erreur, de la présenter à nouveau à l'utilisateur pour réédition, avec le curseur initialement positionné à l'endroit où l'erreur a été

rencontrée.

La fonction gl_get_line() retourne un pointeur vers la ligne saisie par l'utilisateur, ou NULL en cas d'erreur ou à la fin de l'entrée. Le pointeur retourné fait partie de l'objet ressource gl spécifié, et ne doit donc pas être libéré par l'appelant, ni supposé inchangé d'un appel à l'autre. Lors de la lecture depuis un utilisateur sur un terminal, il y aura toujours un caractère de nouvelle ligne à la fin de la ligne retournée. Lorsque l'entrée standard provient d'un pipe ou d'un fichier, il y aura de même une nouvelle ligne, sauf si la ligne d'entrée était trop longue pour être stockée dans le buffer interne. Dans ce dernier cas, vous devriez appeler gl_get_line() à nouveau pour lire le reste de la ligne. Notez que ce comportement rend gl_get_line() similaire à fgets(). En fait, lorsque stdin n'est pas connecté à un terminal,gl_get_line() appelle simplement fget

s(
).

SOURCES DE CONFIGURATION

ALTERNATIVES

Comme mentionné ci-dessus, par défaut les utilisateurs ont la possibilité de configurer le comportement de gl_get_line() via un fichier de configuration appelé .teclarc dans leurs répertoires personnels. Le fait que toutes les applications partagent ce même fichier de configuration est à la fois un avantage et un inconvénient. Dans la plupart des cas, c'est un avantage, car cela encourage l'uniformité et libère l'utilisateur de devoir configurer chaque application séparément. Dans certaines applications, cependant, ce moyen unique de configuration est un problème. C'est particulièrement vrai pour les logiciels embarqués, où il n'y a pas de système de fichiers pour lire un fichier de configuration, et aussi dans les applications où un choix radicalement différent de mappages de touches est nécessaire pour émuler une interface clavier héritée. Pour prendre en charge de tels cas, la fonction suivante permet à l'application de contrôler d'où les informations de configuration sont

lues. 
  int gl_configure_getline(GetLine *gl,
                           const char *app_string,
                           const char *app_file,
                           const char *user_file)
;

Elle permet aux commandes de configuration qui seraient normalement lues depuis le fichier ~/.teclarc de l'utilisateur, d'être lues depuis une chaîne, un fichier de configuration spécifique à l'application, et/ou un fichier de configuration spécifique à l'utilisateur, ou aucun de ceux-ci. Si cette fonction est appelée avant le premier appel à gl_get_line(), le comportement par défaut de lecture de ~/.teclarc au premier appel à gl_get_line() est désactivé ; toute la configuration doit donc être réalisée en utilisant les sources de configuration spécifiées avec cette

fonction.

Si app_string != NULL, alors il est interprété comme une chaîne contenant une ou plusieurs commandes de configuration, séparées les unes des autres dans la chaîne par des caractères de nouvelle ligne intégrés. Si app_file != NULL, alors il est interprété comme le chemin complet d'un fichier de configuration spécifique à l'application. Si user_file != NULL, alors il est interprété comme le chemin complet d'un fichier de configuration spécifique à l'utilisateur, tel que ~/.teclarc. Par exemple, dans l'appel

suivant, 
  gl_configure_getline(gl, "edit-mode vi \n nobeep",
                           "/usr/share/myapp/teclarc",
                           "~/.teclarc")
;

l'argument app_string fait démarrer l'application appelante en mode d'édition vi, au lieu du mode emacs par défaut, et désactive l'utilisation de la cloche du terminal par la bibliothèque. Elle tente ensuite de lire les commandes de configuration valables pour tout le système depuis un fichier optionnel appelé /usr/share/myapp/teclarc, puis lit enfin les commandes de configuration spécifiques à l'utilisateur depuis un fichier .teclarc optionnel dans le répertoire personnel de l'utilisateur. Notez que les arguments sont listés par ordre de priorité croissante, le contenu de app_string pouvant être potentiellement remplacé par les commandes dans app_file, et les commandes dans app_file pouvant être potentiellement remplacées par les commandes dans user_file

.

Vous pouvez appeler cette fonction autant de fois que nécessaire, les résultats étant cumulatifs, mais notez que des copies de tout nom de fichier spécifié via app_file et les arguments user_file sont enregistrés en interne pour une utilisation ultérieure par la fonction de raccourci clavier read-init-files. Ainsi, si vous prévoyez d'appeler cette fonction plusieurs fois, assurez-vous que le dernier appel spécifie les noms de fichiers que vous souhaitez relire lorsque l'utilisateur demande la relecture des fichiers de configuration.

Les séquences de touches individuelles peuvent également être liées et déliées à l'aide de la fonction gl_bind_keyseq().

  int gl_bind_keyseq(GetLine *gl, GlKeyOrigin origin,
                     const char *keyseq,
                     const char *action);

L'argument origin spécifie la priorité de la liaison, selon la personne pour qui elle est établie, et doit être l'une des deux valeurs suivantes.

  GL_USER_KEY   -   L'utilisateur a demandé cette liaison de touche.
  GL_APP_KEY    -   Il s'agit d'une liaison par défaut définie par
                    l'application.

Lorsque des liaisons utilisateur et application pour une séquence de touches donnée ont été spécifiées, la liaison utilisateur a la priorité. La liaison de l'application est ensuite rétablie si la liaison de l'utilisateur est ultérieurement déliée via une autre fonction de ce type, ou un appel à gl_configure_getline().

L'argument keyseq spécifie la séquence de touches à lier ou à délier, et est exprimé de la même manière que dans un fichier de configuration ~/.teclarc. L'argument action doit soit être une chaîne contenant le nom de l'action à laquelle lier la séquence de touches, soit être NULL ou "" pour délier la séquence de touches.

COMPLETION DE MOTS PERSONNALISÉE

Si dans votre application, vous souhaitez que la complétion TAB complète d'autres éléments en plus des noms de fichiers ou à la place de ceux-ci, vous pouvez organiser cela en enregistrant une fonction de rappel de complétion alternative, via un appel à la fonction gl_customize_completion().

  int gl_customize_completion(GetLine *gl, void *data,
                              CplMatchFn *match_fn);

L'argument data permet à votre application de passer des informations arbitraires et spécifiques à l'application à la fonction de rappel. Ceci est passé à la fonction de rappel à chaque fois qu'elle est appelée. Il pourrait par exemple pointer vers la table des symboles à partir de laquelle les complétions possibles doivent être recherchées. L'argument match_fn spécifie la fonction de rappel à appeler. Le type de fonction CplMatchFn est défini dans libtecla.h, tout comme une macro CPL_MATCH_FN() que vous pouvez utiliser pour déclarer et prototyper des fonctions de rappel. La déclaration et les responsabilités des fonctions de rappel sont décrites en détail dans la page de manuel cpl_complete_word(3).

En bref, la fonction de rappel est responsable de regarder en arrière dans la ligne d'entrée, avant le point où l'utilisateur a appuyé sur TAB, pour trouver le début du mot en cours de complétion. Elle doit ensuite rechercher les complétions possibles de ce mot, et les enregistrer une par une dans l'objet WordCompletion qui lui est passé en argument, en appelant la fonction cpl_add_completion(). Si la fonction de rappel souhaite fournir la complétion de noms de fichiers en plus de ses propres complétions spécifiques, elle a la possibilité d'appeler elle-même la fonction de rappel de complétion intégrée de noms de fichiers. Ceci est également documenté dans la page de manuel cpl_complete_word(3).

Notez que si vous souhaitez que gl_get_line() renvoie la ligne d'entrée actuelle lorsqu'une complétion réussie a été effectuée, vous pouvez organiser cela lorsque vous appelez cpl_add_completion(), en faisant du dernier caractère du suffixe de continuation un caractère de nouvelle ligne. Si vous faites cela, la ligne d'entrée sera mise à jour pour afficher la complétion, ainsi que tout suffixe de continuation jusqu'au caractère de nouvelle ligne, puis gl_get_line() renverra cette ligne d'entrée.

Si, pour une raison quelconque, votre fonction de rappel doit écrire quelque chose sur le terminal, elle doit appeler gl_normal_io() avant de le faire. Cela commencera une nouvelle ligne après la ligne actuellement éditée, rétablira les E/S normales du terminal et indiquera à gl_get_line() que la ligne d'entrée devra être redessinée lors du retour de la fonction de rappel.

AJOUT D'ACTIONS DE COMPLETION

Dans la section précédente, la possibilité de personnaliser le comportement de la seule action de complétion par défaut, complete-word, a été décrite. Dans cette section, la possibilité d'installer des fonctions d'action supplémentaires, afin que différents types de complétion de mots puissent être liés à différentes séquences de touches, est décrite. Ceci est réalisé en utilisant la fonction gl_completion_action().

  int gl_completion_action(GetLine *gl,
                           void *data, CplMatchFn *match_fn,
                           int list_only, const char *name,
                           const char *keyseq);

Les arguments data et match_fn sont tels que décrits dans la page de manuel cpl_complete_word, et spécifient la fonction de rappel qui doit être invoquée pour identifier les complétions possibles. L'argument list_only détermine si l'action en cours de définition doit tenter de compléter le mot autant que possible dans la ligne d'entrée avant d'afficher les complétions ambiguës possibles, ou si elle doit simplement afficher la liste des complétions possibles sans toucher à la ligne d'entrée. La première option est sélectionnée en spécifiant une valeur de 0, et la seconde en spécifiant une valeur de 1. L'argument name spécifie le nom par lequel les fichiers de configuration et les invocations futures de cette fonction devront faire référence à l'action. Il doit s'agir soit du nom d'une action de complétion existante à modifier, soit d'un nouveau nom inutilisé pour une nouvelle action. Enfin, l'argument keyseq spécifie la séquence de touches par défaut à laquelle lier l'action. Si c'est NULL, aucune nouvelle séquence de touches ne sera liée à l'action.

Attention, pour que l'utilisateur puisse changer la séquence de touches liée aux actions installées de cette manière, lorsque vous appelez gl_completion_action() pour installer une action donnée pour la première fois, vous devriez le faire entre l'appel à new_GetLine() et le premier appel à gl_get_line(). Sinon, lorsque le fichier de configuration de l'utilisateur sera lu lors du premier appel à gl_get_line(), le nom de votre action supplémentaire ne sera pas connu, et toute référence à celle-ci dans le fichier de configuration générera une erreur.

Comme discuté pour gl_customize_completion(), si votre fonction de rappel, pour une raison quelconque, a besoin d'écrire quoi que ce soit sur le terminal, elle doit appeler gl_normal_io() avant de le faire.

DÉFINITION D'ACTIONS PERSONNALISÉES

Bien que les actions de liaison de touches intégrées suffisent aux besoins de la plupart des applications, il arrive parfois qu'une application spécialisée doive définir une ou plusieurs actions personnalisées, liées à des séquences de touches spécifiques à l'application. Par exemple, une application de vente bénéficierait d'avoir une séquence de touches qui afficherait le nom de la pièce correspondant à un numéro de pièce précédant le curseur. Une telle fonctionnalité dépasse clairement la portée des fonctions d'action intégrées. C'est pourquoi, pour de tels cas spéciaux, la fonction gl_register_action() est fournie.

  int gl_register_action(GetLine *gl, void *data,
			 GlActionFn *fn, const char *name,
			 const char *keyseq);

Cette fonction permet à l'application d'enregistrer une fonction externe, fn, qui sera ensuite appelée chaque fois que la séquence de touches spécifiée, keyseq, sera entrée par l'utilisateur, ou que l'utilisateur entrera toute autre séquence de touches que l'utilisateur liera ensuite au nom d'action spécifié, name, dans son fichier de configuration. L'argument data peut être un pointeur vers tout ce que l'application souhaite passer à la fonction d'action, fn, chaque fois que cette fonction est invoquée.

La fonction d'action, fn, doit être déclarée en utilisant la macro suivante, qui est définie dans libtecla.h.

  #define GL_ACTION_FN(fn) GlAfterAction (fn)(GetLine *gl, \
              void *data, int count, size_t curpos, \
              const char *line)

Les arguments gl et data sont ceux qui ont été précédemment passés à gl_register_action() lors de l'enregistrement de la fonction d'action. L'argument count est un argument numérique que l'utilisateur a la possibilité d'entrer à l'aide de l'action digit-argument, avant d'invoquer l'action. Si l'utilisateur n'entre pas de nombre, alors l'argument count est défini à 1. Nominalement, cet argument est interprété comme un compteur de répétition, signifiant que l'action doit être répétée autant de fois. En pratique cependant, pour certaines actions, un compteur de répétition a peu de sens. Dans de tels cas, les actions peuvent simplement ignorer l'argument count, ou utiliser sa valeur à une fin différente.

Une copie de la ligne d'entrée actuelle est passée dans l'argument en lecture seule line. La position actuelle du curseur dans cette chaîne est donnée par l'indice contenu dans l'argument curpos. Notez que la manipulation directe de la ligne d'entrée et de la position du curseur n'est pas autorisée. C'est parce que les règles dictées par divers modes, tels que le mode vi par rapport au mode emacs, le mode sans écho, et le mode insertion par rapport au mode écrasement, etc., rendent trop complexe pour un développeur d'application l'écriture d'une action d'édition conforme, tout en limitant les modifications futures des détails internes de gl_get_line(). Une solution potentielle à ce dilemme serait de permettre à la fonction d'action d'éditer la ligne en utilisant les actions d'édition existantes. Ceci est actuellement à l'étude.

Si la fonction d'action souhaite écrire du texte sur le terminal, sans que cela ne se mélange avec le texte affiché de la ligne d'entrée, ou lire depuis le terminal sans avoir à gérer les E/S brutes du terminal, alors avant de faire l'une ou l'autre de ces opérations, elle doit temporairement suspendre l'édition de ligne en appelant la fonction gl_normal_io(). Cette fonction vide toute sortie en attente vers le terminal, déplace le curseur au début de la ligne qui suit la dernière ligne de terminal de la ligne d'entrée, puis rétablir le terminal dans un état adapté à une utilisation avec les fonctions stdio C. Ce dernier comprend des choses telles que le rétablissement du mappage normal de \n à \r\n, et, en mode serveur, le rétablissement de la forme de blocage normale des E/S du terminal. Après avoir appelé cette fonction, la fonction d'action peut lire et écrire sur le terminal sans craindre de créer un désordre. Il n'est pas nécessaire que la fonction d'action rétablisse l'environnement d'édition d'origine avant de retourner. Ceci est fait automatiquement par gl_get_line() après le retour de la fonction d'action. Ce qui suit est un exemple simple d'une fonction d'action qui écrit la phrase "Hello world" sur une nouvelle ligne de terminal après la ligne en cours d'édition. Lorsque cette fonction retourne, la ligne d'entrée est redessinée sur la ligne qui suit la ligne "Hello world", et l'édition de ligne reprend.

  {

io(gl)) /* Suspendre temporairement l'édition */ return GLA_ABORT; printf("Hello world\n"); return GLA_CONTINUE; }

  GLA_ABORT     -   Faire en sorte que gl_get_line() retourne NULL.
  GLA_RETURN    -   Faire en sorte que gl_get_line() retourne la

ARCHIVAGE MANUEL DE

L'HISTORIQUE

Par défaut, chaque fois qu'une ligne est saisie par l'utilisateur, elle est automatiquement ajoutée à la liste d'historique, juste avant que gl_get_line() retourne la ligne à l'appelant. C'est pratique pour la majorité des applications, mais il existe aussi des applications qui ont besoin d'un contrôle plus fin sur ce qui est ajouté à la liste d'historique. Dans de tels cas, l'ajout automatique des lignes saisies à la liste d'historique peut être désactivé en appelant la fonction gl_automatic_hi

story(). 
  int gl_automatic_history(GetLine *gl, int enable)
;

Si cette fonction est appelée avec son argument enable défini à 0, gl_get_line() n'archivera pas automatiquement les lignes saisies ultérieurement. L'archivage automatique peut être réactivé plus tard, en appelant à nouveau cette fonction, avec son argument enable défini à 1. Tant que l'archivage automatique de l'historique est désactivé, l'application appelante peut utiliser la fonction gl_append_history() pour ajouter des lignes à la liste d'historique selon les

besoins. 
  int gl_append_history(GetLine *gl, const char *line)
;

L'argument line spécifie la ligne à ajouter à la liste d'historique. Cela doit être une chaîne normale ' ' terminée. Si cette chaîne contient des caractères de nouvelle ligne, la ligne qui sera archivée dans la liste d'historique sera terminée par le premier d'entre eux. Sinon, elle sera terminée par le délimiteur ' '. Si la ligne est plus longue que la longueur maximale de ligne d'entrée, qui a été spécifiée lorsque new_GetLine() a été appelée, lorsque la ligne sera rappelée, elle sera tronquée à la longueur réelle de la ligne de gl_get_li

ne().

En cas de succès, gl_append_history() retourne 0. Sinon, elle retourne une valeur non nulle, et définit errno à l'une des valeurs

suivantes. 
   EINVAL  -  L'un des arguments passés à
              gl_append_history() était NULL.
   ENOMEM  -  La ligne spécifiée était plus longue que la taille allouée
              du tampon d'historique (telle que spécifiée lors de l'appel à
              new_GetLine()), elle n'a donc pas pu être
archivée.

Une description textuelle de l'erreur peut être obtenue éventuellement en appelant gl_error_message(). Notez qu'après une telle erreur, la liste d'historique reste dans un état valide pour recevoir de nouvelles lignes d'historique, il n'y a donc que peu d'inconvénient à simplement ignorer le statut de retour de gl_append_

La fonction constructrice new_GetLine() suppose que l'entrée doit être lue depuis stdin, et que la sortie est écrite vers stdout. La fonction suivante permet de basculer vers d'autres flux d'entrée et de

sortie.

terminal.

GESTION PERSONNALISÉE DES SIGNAUX

La section précédente a listé les signaux que gl_get_line() capture par défaut, et a décrit comment il y répond. Cette section décrit comment ajouter et supprimer des signaux de la liste des signaux capturés, et comment spécifier comment gl_get_line() doit répondre à un signal donné.

Si vous n'avez pas besoin que gl_get_line() fasse quoi que ce soit en réponse à un signal qu'il capture normalement, vous pouvez lui indiquer de l'ignorer en appelant gl_ignore_signal().

  int gl_ignore_signal(GetLine *gl, int signo);

L'argument signo est le numéro du signal (par exemple, SIGINT) que vous souhaitez ignorer. Si le signal spécifié ne fait pas actuellement partie de ceux qui sont capturés, cette fonction ne fait rien.

La fonction gl_trap_signal() vous permet soit d'ajouter un nouveau signal à la liste que gl_get_line() capture, soit de modifier la façon dont il y répond.

gl_trap_signal

The gl_trap_signal function configures gl_get_line to trap a signal.

  int gl_trap_signal(GetLine *gl, int signo, unsigned flags,
                     GlAfterSignal after, int errno_value);

The argument signo is the number of the signal that you wish to have trapped. The argument flags is a set of flags which determine the environment in which the application's signal handler is invoked, the argument after tells gl_get_line() what to do after the application's signal handler returns, and errno_value tells gl_get_line() what to set errno to if told to abort.

The argument flags is a bitwise OR of zero or more of the following enumerators:

  GLS_RESTORE_SIG  -  Restore the caller's signal
                      environment while handling the
                      signal.
  GLS_RESTORE_TTY  -  Restore the caller's terminal settings
                      while handling the signal.
  GLS_RESTORE_LINE -  Move the cursor to the start of the
                      line following the input line before
                      invoking the application's signal
                      handler.
  GLS_REDRAW_LINE  -  Redraw the input line when the
                      application's signal handler returns.
  GLS_UNBLOCK_SIG  -  Normally, if the calling program has
                      a signal blocked (man sigprocmask),
                      gl_get_line() does not trap that
                      signal. This flag tells gl_get_line()
                      to trap the signal and unblock it for
                      the duration of the call to
                      gl_get_line().
  GLS_DONT_FORWARD -  If this flag is included, the signal
                      will not be forwarded to the signal
                      handler of the calling program.

Two commonly useful flag combinations are also enumerated as follows:

  GLS_RESTORE_ENV   = GLS_RESTORE_SIG | GLS_RESTORE_TTY |
                      GLS_REDRAW_LINE
  GLS_SUSPEND_INPUT = GLS_RESTORE_ENV | GLS_RESTORE_LINE

If your signal handler, or the default system signal handler for this signal, if you haven't overridden it, never either writes to the terminal, nor suspends or terminates the calling program, then you can safely set the argument flags to 0.

If your signal handler always writes to the terminal, reads from it, or suspends or terminates the program, you should specify the argument flags as GL_SUSPEND_INPUT, so that:

1. The cursor doesn't get left in the middle of the input
   line.
2. So that the user can type in input and have it echoed.
3. So that you don't need to end each output line with
   \r\n, instead of just \n.

The combination GL_RESTORE_ENV is the same as GL_SUSPEND_INPUT, except that it doesn't move the cursor, and if your signal handler doesn't read or write anything to the terminal, the user won't see any visible indication that a signal was caught. This can be useful if you have a signal handler that only occasionally writes to the terminal, where using GL_SUSPEND_LINE would cause the input line to be unnecessarily duplicated when nothing had been written to the terminal. Such a signal handler, when it does write to the terminal, should be sure to start a new line at the start of its first write, by writing a new line before returning. If the signal arrives while the user is entering a line that only occupies a signal terminal line, or if the cursor is on the last terminal line of a longer input line, this will have the same effect as GL_SUSPEND_INPUT. Otherwise it will start writing on a line that already contains part of the displayed input line. This doesn't do any harm, but it looks a bit ugly, which is why the combination GL_SUSPEND_INPUT is better if you know that you are always going to be writting to the terminal.

The argument after, which determines what gl_get_line() does after the application's signal handler returns (if it returns), can take any one of the following values:

  GLS_RETURN   - Return the completed input line, just as
                 though the user had pressed the return
                 key.
  GLS_ABORT    - Cause gl_get_line() to abort. When
                 this happens, gl_get_line() returns
                 NULL, and a following call to
                 gl_return_status() will return
                 GLR_SIGNAL. Note that if the
                 application needs errno always to
                 have a meaningful value when
                 gl_get_line() returns NULL,
                 the callback function should set
                 errno appropriately.
  GLS_CONTINUE - Resume command line editing.

The argument errno_value is intended to be combined with the option GLS_ABORT, telling gl_get_line() what to set the standard errno variable to before returning NULL to the calling program. It can also, however, be used with the option GL_RETURN, in case you wish to have a way to distinguish between an input line that was entered using the return key, and one that was entered by the receipt of a signal.

GESTION FIABLE DES SIGNAUX

La gestion des signaux est étonnamment difficile à réaliser de manière fiable sans conditions de concurrence (race conditions). Dans gl_get_line(), beaucoup de soin a été apporté pour permettre aux applications d'effectuer une gestion fiable des signaux autour de gl_get_line(). Cette section explique comment en tirer parti.

Comme exemple des problèmes qui peuvent survenir si l'application n'est pas écrite correctement, imaginez qu'une application ait un gestionnaire de signal SIGINT qui définit un drapeau global. Supposons maintenant que l'application teste ce drapeau juste avant d'appeler gl_get_line(). Si un signal SIGINT est reçu dans la petite fenêtre de temps entre l'instruction qui teste la valeur de ce drapeau et l'instruction qui appelle gl_get_line(), alors gl_get_line() ne verra pas le signal et ne sera pas interrompu. Par conséquent, l'application ne pourra pas répondre au signal tant que l'utilisateur n'aura pas terminé la saisie de la ligne et que gl_get_line() ne sera pas revenu. Selon l'application, cela peut être une catastrophe ou non, mais au moins cela puzzlera l'utilisateur.

La façon d'éviter de tels problèmes est de faire ce qui suit.

1. Si nécessaire, utilisez la fonction gl_trap_signal() pour
configurer gl_get_line() pour qu'il
s'arrête lorsque des signaux importants sont interceptés.

2. Configurez gl_get_line() de telle sorte que si l'un des
signaux qu'il intercepte est bloqué lorsque
gl_get_line() est appelé, ils soient débloqués
automatiquement pendant les moments où gl_get_line()
attend une E/S. Cela peut être fait soit
par signal, en appelant la fonction
gl_trap_signal() et en spécifiant
l'attribut GLS_UNBLOCK du signal, soit globalement en
appelant la fonction gl_catch_blocked().

     void gl_catch_blocked(GetLine *gl);


Cette fonction ajoute simplement l'attribut
GLS_UNBLOCK à tous les signaux qu'elle est actuellement configurée pour
intercepter.

3. Juste avant d'appeler gl_get_line(), bloquez la livraison
de tous les signaux que gl_get_line() est
configuré pour intercepter. Cela peut être fait en utilisant la fonction POSIX
sigprocmask() en conjonction avec la fonction
gl_list_signals().

Cette fonction retourne l'ensemble des signaux qu'elle est
actuellement configurée pour attraper dans l'argument
set, qui est dans le format requis par
sigprocmask().

4. Dans l'exemple, on testerait maintenant le drapeau global que
le gestionnaire de signaux définit, sachant qu'il n'y a plus de

LA TAILLE DU

TERMINAL

Sur la plupart des systèmes, la combinaison de l'ioctl TIOCGWINSZ et du signal SIGWINCH est utilisée pour maintenir une idée précise de la taille du terminal. La taille du terminal est nouvellement interrogée à chaque fois que gl_get_line() est appelé et à chaque fois qu'un signal SIGWINCH est

reçu.

Sur les quelques systèmes où ce mécanisme n'est pas disponible, au démarrage new_GetLine() cherche d'abord les variables d'environnement LINES et COLUMNS. Si celles-ci ne sont pas trouvées, ou si elles contiennent des valeurs inutilisables, alors si une base de données d'informations sur le terminal comme terminfo ou termcap est disponible, la taille par défaut du terminal est recherchée dans cette base de données. Si cela échoue également à fournir la taille du terminal, une taille par défaut de 80 colonnes par 24 lignes est

utilisée.

Même sur les systèmes qui prennent en charge ioctl(TIOCGWINSZ), si le terminal est à l'autre bout d'une ligne série, le pilote du terminal n'a généralement aucun moyen de détecter quand un redimensionnement se produit ou d'interroger la taille actuelle. Dans de tels cas, aucun SIGWINCH n'est envoyé au processus, et les dimensions retournées par ioctl(TIOCGWINSZ) ne sont pas correctes. La seule façon de gérer de tels cas est de fournir un moyen à l'utilisateur de saisir une commande qui indique au système distant quelle est la nouvelle taille. Cette commande appellerait alors la fonction gl_set_term_size() pour informer gl_get_line() du changement de

taille. 
  int gl_set_term_size(GetLine *gl, int ncolumn, int nline)
;

Les arguments ncolumn et nline sont utilisés pour spécifier les nouvelles dimensions du terminal et ne doivent pas être inférieurs à 1. Sur les systèmes qui prennent en charge ioctl(TIOCGWINSZ), cette fonction appelle d'abord ioctl(TIOCSWINSZ) pour informer le pilote du terminal du changement de taille. En mode d'E/S serveur non bloquant, si une ligne est en cours de saisie, la ligne d'entrée est alors redessinée pour s'adapter à la taille modifiée. Enfin, les nouvelles valeurs sont enregistrées dans gl pour une utilisation future par gl_get_li

ne().

La fonction gl_terminal_size() vous permet d'interroger la taille actuelle du terminal et d'installer une taille de secours alternative pour les cas où la taille n'est pas disponible. Attention, la taille du terminal ne sera pas disponible lors de la lecture depuis un tube ou un fichier, de sorte que les valeurs par défaut peuvent être importantes même sur les systèmes qui prennent en charge des moyens de découvrir la taille du

terminal. 
  typedef struct {
    int nline;        /* Le terminal a nline lignes */
    int ncolumn;      /* Le terminal a ncolumn colonnes */
  } GlTerminalSize;
  GlTerminalSize gl_terminal_size(GetLine *gl,
                                  int def_ncolumn,
                                  int def_nline)
;

Cette fonction met d'abord à jour les dimensions de secours du terminal de gl_get_line(), puis enregistre ses résultats dans la valeur de

retour.

Les def_ncolumn et def_nline spécifient le nombre par défaut de colonnes et de lignes du terminal à utiliser si la taille du terminal ne peut pas être déterminée via ioctl(TIOCGWINSZ) ou les variables

d'environnement
.

CACHER CE QUE VOUS

TAPEZ

Lors de la saisie d'informations sensibles, comme les mots de passe, il est préférable de ne pas faire écho sur le terminal du texte que vous saisissez. De plus, ce texte ne devrait pas être enregistré dans la liste d'historique, car quelqu'un trouvant votre terminal sans surveillance pourrait alors le rappeler, ou quelqu'un fouillant dans vos répertoires pourrait le voir dans votre fichier d'historique. En gardant cela à l'esprit, la fonction gl_echo_mode() vous permet d'activer et de désactiver l'affichage et l'archivage de tout texte qui est saisi par la suite dans les appels à gl_get_li

ne(). 
  int gl_echo_mode(GetLine *gl, int enable)
;

L'argument enable spécifie si le texte saisi doit être visible ou non. S'il est 0, les lignes saisies par la suite ne seront pas visibles sur le terminal et ne seront pas enregistrées dans la liste d'historique. S'il est 1, les lignes d'entrée suivantes seront affichées au fur et à mesure de leur saisie et, à condition que l'historique n'ait pas été désactivé via un appel à gl_toggle_history(), elles seront également archivées dans la liste d'historique. Enfin, si l'argument enable est -1, le mode d'écho est laissé inchangé, ce qui vous permet d'interroger le paramètre actuel de manière non destructive via la valeur de retour. Dans tous les cas, la valeur de retour de la fonction est 0 si l'écho était désactivé avant l'appel de la fonction, et 1 s'il était

activé.

Lorsque l'écho est désactivé, notez que même si la complétion par

tabulation complétera votre préfixe de manière invisible aussi lo
in que possible, les complétions ambiguës ne seront pas affichées.

INTERROGATIONS À UN SEUL

CARACTÈRE

Utiliser gl_get_line() pour demander à l'utilisateur une réponse d'un seul caractère est incommode pour l'utilisateur, car il doit appuyer sur la touche entrée ou retour avant que le caractère qu'il a tapé ne soit renvoyé au programme. C'est pourquoi la fonction gl_query_char() a été fournie pour les interrogations à un seul caractère comme

celle-ci. 
  int gl_query_char(GetLine *gl, const char *prompt,
                    char defchar)
;

Cette fonction affiche l'invite spécifiée au début d'une nouvelle ligne et attend que l'utilisateur tape un caractère. Lorsque l'utilisateur tape un caractère, gl_query_char() l'affiche à droite de l'invite, démarre une nouvelle ligne, puis renvoie le caractère au programme appelant. La valeur de retour de la fonction est le caractère qui a été tapé. Si la lecture a dû être interrompue pour une raison quelconque, EOF est renvoyé à la place. Dans ce dernier cas, l'application peut appeler la fonction précédemment documentée gl_return_status() pour savoir ce qui s'est mal passé. Cela pourrait, par exemple, avoir été la réception d'un signal ou le déclenchement du minuteur d'inactivité

optionnel.

Si l'utilisateur appuie simplement sur entrée, la valeur de l'argument defchar est substituée. Cela signifie que lorsque l'utilisateur appuie sur nouvelle ligne ou retour, le caractère spécifié dans defchar est affiché après l'invite, comme si l'utilisateur l'avait tapé, et est également renvoyé à l'application appelante. Si un tel remplacement n'est pas important, passez simplement '0 comme valeur de defchar

.

Si le caractère saisi est un caractère non imprimable, il est affiché symboliquement. Par exemple, contrôle-A est affiché comme ^A, et les caractères au-delà de 127 sont affichés en octal, précédés d'une barre oblique

inverse.

Comme pour gl_get_line(), l'écho du caractère saisi peut être désactivé à l'aide de la fonction gl_echo_mode()

.

Si le processus appelant est suspendu pendant qu'il attend que l'utilisateur tape sa réponse, le curseur est déplacé sur la ligne suivant la ligne d'invite, puis lorsque le processus reprend, l'invite est réaffichée, et gl_query_char() reprend l'attente que l'utilisateur tape un

caractère.

Notez qu'en mode serveur non bloquant, (voir gl_io_mode(3)), si une ligne d'entrée incomplète est en cours de lecture lorsque gl_query_char() est appelé, la ligne d'entrée partielle est abandonnée et effacée du terminal avant que la nouvelle invite ne soit affichée. L'appel suivant à gl_get_line() commencera donc

à éditer une n
ouvelle ligne.

LIRE DES CARACTÈRES

BRUTS

Alors que la fonction gl_query_char() demande visuellement à l'utilisateur un caractère et affiche ce qu'il a tapé, la fonction gl_read_char() lit un caractère brut de l'utilisateur, sans rien écrire sur le terminal ni perturber une ligne d'entrée incomplète. Cela signifie qu'elle peut être appelée non seulement entre les appels à gl_get_line(), mais aussi depuis des fonctions de rappel que l'application a enregistrées pour être appelées par gl_get_li

ne(). 
  int gl_read_char(GetLine *gl)
;

En cas de succès, la valeur de retour de gl_read_char() est le caractère qui a été lu. En cas d'échec, EOF est renvoyé, et la fonction gl_return_status() peut être appelée pour savoir ce qui s'est mal passé. Les possibilités incluent le déclenchement du minuteur d'inactivité optionnel, la réception d'un signal configuré pour interrompre gl_get_line(), ou le blocage des E/S du terminal, en mode d'E/S serveur non

bloquant.

Attention, certaines touches du clavier, comme les touches de fonction et les touches de curseur, génèrent généralement au moins 3 caractères chacune, de sorte qu'un seul appel à gl_read_char() ne sera pas suffisante pour

identifier de
telles frappes.

AFFICHAGE DYNAMIQUE DE

TEXTE

Entre les appels à gl_get_line(), la fonction gl_display_text() fournit un moyen pratique d'afficher des paragraphes de texte, justifiés à gauche et répartis sur une ou plusieurs lignes du terminal, selon les contraintes de la largeur courante du terminal. Des exemples d'utilisation de cette fonction se trouvent dans les programmes de démonstration, où elle est utilisée pour afficher des introductions. Dans ces exemples, l'utilisation avancée de préfixes, suffixes et lignes de remplissage optionnels pour dessiner un cadre autour du texte est également

illustrée. 
  int gl_display_text(GetLine *gl, int indentation,
                      const char *prefix,
                      const char *suffix, int fill_char,
                      int def_width, int start,
                      const char *string)
;

Si gl n'est pas actuellement connecté à un terminal, par exemple si la sortie d'un programme utilisant gl_get_line() est acheminée vers un autre programme ou redirigée vers un fichier, alors la valeur du paramètre def_width est utilisée comme largeur du

terminal.

L'argument indentation spécifie le nombre de caractères à utiliser pour indenter chaque ligne de sortie. L'argument fill_char spécifie le caractère qui sera utilisé pour effectuer cette

indentation.

L'argument prefix peut être soit NULL, soit une chaîne à placer au début de chaque nouvelle ligne (après toute indentation). De même, l'argument suffix peut être soit NULL, soit une chaîne à placer à la fin de chaque ligne. Le suffixe est placé à fleur du bord droit du terminal, et tout espace entre son premier caractère et le dernier mot de cette ligne est rempli par le caractère spécifié via l'argument fill_char. Normalement, le caractère de remplissage est une

espace.

L'argument start indique à gl_display_text() combien de caractères ont déjà été écrits sur la ligne de terminal courante, et indique ainsi l'indice de colonne de départ du curseur. Puisque la valeur de retour de gl_display_text() est l'indice de colonne de fin du curseur, en passant la valeur de retour d'un appel à l'argument start de l'appel suivant, un paragraphe qui est réparti sur plus d'une chaîne peut être composé en appelant gl_display_text() pour chaque portion successive du paragraphe. Notez que des caractères de nouvelle ligne littéraux sont nécessaires à la fin de chaque paragraphe pour forcer le début d'une nouvelle

ligne.

En cas d'erreur, gl_display_tex

t() renv
oie -1.

FONCTIONNALITÉS DE FONCTIONS DE

RAPPEL

Sauf indication contraire, les fonctions de rappel, telles que les rappels de complétion par tabulation et les rappels d'événements, ne doivent appeler aucune fonction de ce module. Les fonctions suivantes, cependant, sont conçues spécifiquement pour être utilisées par les fonctions de

rappel.

Appeler la fonction gl_replace_prompt() depuis un rappel indique à gl_get_line() d'afficher un prompt différent lorsque le rappel se termine. Sauf en mode serveur non bloquant, cela n'a aucun effet si utilisé entre des appels à gl_get_line(). En mode serveur non bloquant (voir la page de manuel gl_io_mode(3), lorsqu'il est utilisé entre deux appels à gl_get_line() qui opèrent sur la même ligne d'entrée, la ligne d'entrée courante sera redessinée avec le nouveau prompt lors de l'appel suivant à gl_get_li

ne().

JEUX DE CARACTÈRES

INTERNATIONAUX

Depuis la version 1.4.0 de libtecla, gl_get_line() est propre aux 8 bits. Cela signifie que tous les caractères sur 8 bits imprimables dans la locale actuelle de l'utilisateur sont désormais affichés tels quels et inclus dans la ligne d'entrée renvoyée. En supposant que le programme appelant contient correctement un appel comme

celui-ci, 
  setlocale(LC_CTYPE, "")
;

alors la locale courante est déterminée par la première des variables d'environnement LC_CTYPE, LC_ALL et LANG, dont on trouve qu'elle contient un nom de locale valide. Si aucune de ces variables n'est définie, ou si le programme néglige d'appeler setlocale, alors la locale par défaut C est utilisée, qui est l'ASCII 7 bits américain. Sur la plupart des plateformes de type unix, vous pouvez obtenir une liste des locales valides en tapant la commande

: 
  locale
-a

à l'invite du shell. Une documentation supplémentaire sur la manière dont l'utilisateur peut utiliser cela pour saisir des caractères internationaux se trouve dans la page de manuel tecl

a(7
).

SÉCURITÉ DES

THREADS

Dans un programme multi-thread, vous devriez utiliser la version libtecla_r.a de la bibliothèque. Celle-ci utilise des versions réentrantes des fonctions système, lorsque cela est disponible. Malheureusement, ni terminfo ni termcap n'ont été conçus pour être réentrants, vous ne po

uvez donc pas utiliser en toute sécurité les fonctions du module getline dans plusieurs threads (vous pouvez utiliser les modules séparés d'expansion de fichiers et de complétion de mots dans plusieurs threads, voir les pages de manuel correspondantes pour les détails). Cepen
dant, en raison de l'utilisation de fonctions POSIX réentrantes pour la recherche de répertoires personnels, etc., il est sûr d'utiliser ce module depuis un seul thread d'un programme multi-thread, à condition que vos autres threads n'utilisent aucune fonction termcap ou terminfo.
