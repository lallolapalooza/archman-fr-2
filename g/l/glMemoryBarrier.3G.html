NOM

glMemoryBarrier - définit une barrière ordonnant les transactions mémoire

SPÉCIFICATION C

void glMemoryBarrier(GLbitfield barriers);

void glMemoryBarrierByRegion(GLbitfield barriers);

PARAMÈTRES

barriers

Spécifie les barrières à insérer.

Pour glMemoryBarrier, doit être une combinaison bit à bit de GL_VERTEX_ATTRIB_ARRAY_BARRIER_BIT, GL_ELEMENT_ARRAY_BARRIER_BIT, GL_UNIFORM_BARRIER_BIT, GL_TEXTURE_FETCH_BARRIER_BIT, GL_SHADER_IMAGE_ACCESS_BARRIER_BIT, GL_COMMAND_BARRIER_BIT, GL_PIXEL_BUFFER_BARRIER_BIT, GL_TEXTURE_UPDATE_BARRIER_BIT, GL_BUFFER_UPDATE_BARRIER_BIT, GL_FRAMEBUFFER_BARRIER_BIT, GL_TRANSFORM_FEEDBACK_BARRIER_BIT, GL_ATOMIC_COUNTER_BARRIER_BIT, ou GL_SHADER_STORAGE_BARRIER_BIT.

Pour glMemoryBarrierByRegion, doit être une combinaison bit à bit de GL_ATOMIC_COUNTER_BARRIER_BIT, ou GL_FRAMEBUFFER_BARRIER_BIT, GL_SHADER_IMAGE_ACCESS_BARRIER_BIT, GL_SHADER_STORAGE_BARRIER_BIT. GL_TEXTURE_FETCH_BARRIER_BIT, ou GL_UNIFORM_BARRIER_BIT.

Si la valeur spéciale GL_ALL_BARRIER_BITS est spécifiée, toutes les barrières supportées pour la commande correspondante seront insérées.

DESCRIPTION POUR GLMEMORYBARRIER

glMemoryBarrier définit une barrière ordonnant les transactions mémoire émises avant la commande par rapport à celles émises après la barrière. Aux fins de cet ordonnancement, les transactions mémoire effectuées par les shaders sont considérées comme émises par la commande de rendu qui a déclenché l'exécution du shader. barriers est un champ de bits indiquant l'ensemble des opérations qui sont synchronisées avec les écritures des shaders ; les bits utilisés dans barriers sont les suivants :

GL_VERTEX_ATTRIB_ARRAY_BARRIER_BIT

Si défini, les données de sommet provenant des objets de tampon après la barrière reflèteront les données écrites par les shaders avant la barrière. L'ensemble des objets de tampon affectés par ce bit est dérivé des liaisons d'objets de tampon utilisées pour les attributs de sommet génériques dérivés des liaisons GL_VERTEX_ATTRIB_ARRAY_BUFFER.

GL_ELEMENT_ARRAY_BARRIER_BIT

Si défini, les indices de tableau de sommets provenant des objets de tampon après la barrière reflèteront les données écrites par les shaders avant la barrière. Les objets de tampon affectés par ce bit sont dérivés de la liaison GL_ELEMENT_ARRAY_BUFFER.

GL_UNIFORM_BARRIER_BIT

Les uniformes de shader provenant des objets de tampon après la barrière reflèteront les données écrites par les shaders avant la barrière.

GL_TEXTURE_FETCH_BARRIER_BIT

Les lectures de textures par les shaders, y compris les lectures à partir de la mémoire d'objets de tampon via des textures de tampon, après la barrière reflèteront les données écrites par les shaders avant la barrière.

GL_SHADER_IMAGE_ACCESS_BARRIER_BIT

Les accès mémoire utilisant les fonctions intégrées de chargement, de stockage et atomiques d'images de shader émises après la barrière reflèteront les données écrites par les shaders avant la barrière. De plus, les stockages et les opérations atomiques d'images émises après la barrière ne s'exécuteront pas avant que tous les accès mémoire (par exemple, chargements, stockages, lectures de texture, lectures de sommet) initiés avant la barrière ne soient terminés.

GL_COMMAND_BARRIER_BIT

Les données de commande provenant des objets de tampon par les commandes Draw*Indirect après la barrière reflèteront les données écrites par les shaders avant la barrière. Les objets de tampon affectés par ce bit sont dérivés de la liaison GL_DRAW_INDIRECT_BUFFER.

GL_PIXEL_BUFFER_BARRIER_BIT

Les lectures et écritures d'objets de tampon via les liaisons GL_PIXEL_PACK_BUFFER et GL_PIXEL_UNPACK_BUFFER (via glReadPixels(), glTexSubImage1D(), etc.) après la barrière reflèteront les données écrites par les shaders avant la barrière. De plus, les écritures de tampon émises après la barrière attendront la fin de toutes les écritures de shader initiées avant la barrière.

GL_TEXTURE_UPDATE_BARRIER_BIT

Les écritures dans une texture via glTex(Sub)Image*, glCopyTex(Sub)Image*, glCompressedTex(Sub)Image*, et les lectures via glGetTexImage() après la barrière reflèteront les données écrites par les shaders avant la barrière. De plus, les écritures de texture provenant de ces commandes émises après la barrière ne s'exécuteront pas avant que toutes les écritures de shader initiées avant la barrière ne soient terminées.

GL_BUFFER_UPDATE_BARRIER_BIT

Les lectures ou écritures via glBufferSubData(), glCopyBufferSubData(), ou glGetBufferSubData(), ou vers la mémoire d'objets de tampon mappée par glMapBuffer() ou glMapBufferRange() après la barrière reflèteront les données écrites par les shaders avant la barrière. De plus, les écritures via ces commandes émises après la barrière attendront la fin de toutes les écritures de shader sur la même mémoire initiées avant la barrière.

GL_CLIENT_MAPPED_BUFFER_BARRIER_BIT

L'accès par le client aux régions mappées persistantes des objets de tampon reflètera les données écrites par les shaders avant la barrière. Notez que cela peut entraîner des opérations de synchronisation supplémentaires.

GL_FRAMEBUFFER_BARRIER_BIT

Les lectures et écritures via les pièces jointes d'objets de trame après la barrière reflèteront les données écrites par les shaders avant la barrière. De plus, les écritures de trame émises après la barrière attendront la fin de toutes les écritures de shader émises avant la barrière.

GL_TRANSFORM_FEEDBACK_BARRIER_BIT

Les écritures via les liaisons de rétroaction de transformation après la barrière reflèteront les données écrites par les shaders avant la barrière. De plus, les écritures de rétroaction de transformation émises après la barrière attendront la fin de toutes les écritures de shader émises avant la barrière.

GL_ATOMIC_COUNTER_BARRIER_BIT

Les accès aux compteurs atomiques après la barrière reflèteront les écritures avant la barrière.

GL_SHADER_STORAGE_BARRIER_BIT

Les accès aux blocs de stockage de shader après la barrière reflèteront les écritures avant la barrière.

GL_QUERY_BUFFER_BARRIER_BIT

Les écritures d'objets de tampon via la liaison GL_QUERY_BUFFER après la barrière reflèteront les données écrites par les shaders avant la barrière. De plus, les écritures d'objets de tampon émises après la barrière attendront la fin de toutes les écritures de shader initiées avant la barrière.

Si barriers est GL_ALL_BARRIER_BITS, les accès mémoire des shaders seront synchronisés par rapport à toutes les opérations décrites ci-dessus.

Les implémentations peuvent mettre en cache la mémoire des objets de tampon et des images de texture qui pourraient être écrits par les shaders dans plusieurs caches ; par exemple, il peut y avoir des caches séparés pour les textures, les lectures de sommet, et un ou plusieurs caches pour les accès mémoire des shaders. Les implémentations ne sont pas tenues de maintenir la cohérence de ces caches avec les écritures mémoire des shaders. Les stockages émis par une invocation peuvent ne pas être immédiatement observables par d'autres étapes du pipeline ou d'autres invocations de shader car la valeur stockée peut rester dans un cache local au processeur exécutant le stockage, ou parce que les données écrasées par le stockage sont toujours dans un cache ailleurs dans le système. Lorsque glMemoryBarrier est appelé, le GL vide et/ou invalide tous les caches pertinents pour les opérations spécifiées par le paramètre barriers afin d'assurer un ordonnancement cohérent des opérations de part et d'autre de la barrière.

Pour permettre aux invocations de shader indépendantes de communiquer par des lectures et écritures vers une adresse mémoire commune, les variables d'image dans le langage de shader OpenGL peuvent être déclarées comme "cohérentes". La mémoire des objets de tampon ou des images de texture accédée via ces variables ne peut être mise en cache que si les caches sont automatiquement mis à jour en raison des stockages émis par toute autre invocation de shader. Si la même adresse est accédée en utilisant des variables cohérentes et non cohérentes, les accès utilisant des variables déclarées comme cohérentes observeront les résultats stockés en utilisant des variables cohérentes dans d'autres invocations. L'utilisation de variables déclarées comme "cohérentes" garantit uniquement que les résultats des stockages seront immédiatement visibles aux invocations de shader utilisant des variables similairement déclarées ; l'appel de glMemoryBarrier est nécessaire pour s'assurer que les stockages sont visibles aux autres opérations.

Les directives suivantes peuvent être utiles pour choisir quand utiliser les accès mémoire cohérents et quand utiliser des barrières.

NAME

glMemoryBarrier, glMemoryBarrierByRegion - control memory synchronization

C SPECIFICATION

void glMemoryBarrier(GLbitfield barriers);

void glMemoryBarrierByRegion(GLbitfield barriers);

PARAMETERS

barriers
A bitmask specifying the memory transactions to be synchronized. For glMemoryBarrier, this may be any combination of GL_VERTEX_ATTRIB_ARRAY_BARRIER_BIT, GL_ELEMENT_ARRAY_BARRIER_BIT, GL_UNIFORM_BARRIER_BIT, GL_TEXTURE_FETCH_BARRIER_BIT, GL_SHADER_IMAGE_ACCESS_BARRIER_BIT, GL_COMMAND_BARRIER_BIT, GL_PIXEL_BUFFER_BARRIER_BIT, GL_TEXTURE_UPDATE_BARRIER_BIT, GL_BUFFER_UPDATE_BARRIER_BIT, GL_CLIENT_MAPPED_BUFFER_BARRIER_BIT, GL_FRAMEBUFFER_BARRIER_BIT, GL_TRANSFORM_FEEDBACK_BARRIER_BIT, GL_ATOMIC_COUNTER_BARRIER_BIT, GL_QUERY_BUFFER_BARRIER_BIT, and GL_SHADER_STORAGE_BARRIER_BIT. It may also be GL_ALL_BARRIER_BITS.
For glMemoryBarrierByRegion, see the DESCRIPTION section.

DESCRIPTION FOR GLMEMORYBARRIER

Memory barriers are used to ensure that memory operations performed by different shader stages, or between the application and the shader, are visible in a consistent order. In modern GPUs, many operations, including memory reads and writes, may be executed out-of-order or buffered to improve performance. Memory barriers provide a mechanism to control the ordering and visibility of these operations.

The various bits in the barriers argument specify which memory transactions should be synchronized:

GL_VERTEX_ATTRIB_ARRAY_BARRIER_BIT
Controls the ordering of buffer updates and fetches of vertex attributes.
GL_ELEMENT_ARRAY_BARRIER_BIT
Controls the ordering of buffer updates and fetches of indices for drawing commands.
GL_UNIFORM_BARRIER_BIT
Controls the ordering of buffer updates and fetches of uniform variables.
GL_TEXTURE_FETCH_BARRIER_BIT
Controls the ordering of buffer updates and fetches of texture data.
GL_SHADER_IMAGE_ACCESS_BARRIER_BIT
Controls the ordering of image loads and stores.
GL_COMMAND_BARRIER_BIT
Controls the ordering of drawing commands.
GL_PIXEL_BUFFER_BARRIER_BIT
Controls the ordering of pixel buffer operations.
GL_TEXTURE_UPDATE_BARRIER_BIT
Controls the ordering of texture updates.
GL_BUFFER_UPDATE_BARRIER_BIT
Controls the ordering of buffer updates.
GL_CLIENT_MAPPED_BUFFER_BARRIER_BIT
Controls the ordering of operations on client-mapped buffers.
GL_FRAMEBUFFER_BARRIER_BIT
Controls the ordering of framebuffer operations.
GL_TRANSFORM_FEEDBACK_BARRIER_BIT
Controls the ordering of transform feedback operations.
GL_ATOMIC_COUNTER_BARRIER_BIT
Controls the ordering of atomic counter operations.
GL_QUERY_BUFFER_BARRIER_BIT
Controls the ordering of query buffer operations.
GL_SHADER_STORAGE_BARRIER_BIT
Controls the ordering of shader storage buffer operations.
GL_ALL_BARRIER_BITS
Synchronizes all memory transactions.
•Data that are read-only or constant may be accessed without using coherent variables or calling MemoryBarrier(). Updates to the read-only data via API calls such as glBufferSubData will invalidate shader caches implicitly as required.
•Data that are shared between shader invocations at a fine granularity (e.g., written by one invocation, consumed by another invocation) should use coherent variables to read and write the shared data.
•Data written by one shader invocation and consumed by other shader invocations launched as a result of its execution ("dependent invocations") should use coherent variables in the producing shader invocation and call memoryBarrier() after the last write. The consuming shader invocation should also use coherent variables.
•Data written to image variables in one rendering pass and read by the shader in a later pass need not use coherent variables or memoryBarrier(). Calling glMemoryBarrier with the SHADER_IMAGE_ACCESS_BARRIER_BIT set in barriers between passes is necessary.
•Data written by the shader in one rendering pass and read by another mechanism (e.g., vertex or index buffer pulling) in a later pass need not use coherent variables or memoryBarrier(). Calling glMemoryBarrier with the appropriate bits set in barriers between passes is necessary.

DESCRIPTION FOR GLMEMORYBARRIERBYREGION

glMemoryBarrierByRegion behaves as described above for glMemoryBarrier, with two differences:

First, it narrows the region under consideration so that only reads and writes of prior fragment shaders that are invoked for a smaller region of the framebuffer will be completed/reflected prior to subsequent reads and writes of following fragment shaders. The size of the region is implementation-dependent and may be as small as one framebuffer pixel.

Second, it only applies to memory transactions that may be read by or written by a fragment shader. Therefore, only the barrier bits

•GL_ATOMIC_COUNTER_BARRIER_BIT
•GL_FRAMEBUFFER_BARRIER_BIT
•GL_SHADER_IMAGE_ACCESS_BARRIER_BIT
•GL_SHADER_STORAGE_BARRIER_BIT
•GL_TEXTURE_FETCH_BARRIER_BIT
•GL_UNIFORM_BARRIER_BIT

are supported.

When barriers is GL_ALL_BARRIER_BITS, shader memory accesses will be synchronized relative to all these barrier bits, but not to other barrier bits specific to glMemoryBarrier. This implies that reads and writes for scatter/gather-like algorithms may or may not be completed/reflected after a glMemoryBarrierByRegion command. However, for uses such as deferred shading, where a linked list of visible surfaces with the head at a framebuffer address may be constructed, and the entirety of the list is only dependent on previous executions at that framebuffer address, glMemoryBarrierByRegion may be significantly more efficient than glMemoryBarrier.

NOTES

GL_SHADER_STORAGE_BARRIER_BIT is available only if the GL version is 4.3 or higher.

GL_QUERY_BUFFER_BARRIER_BIT is available only if the GL version is 4.4 or higher.

ERRORS

GL_INVALID_VALUE is generated if barriers is not the special value GL_ALL_BARRIER_BITS, and has any bits set other than those described above for glMemoryBarrier or glMemoryBarrierByRegion respectively.
