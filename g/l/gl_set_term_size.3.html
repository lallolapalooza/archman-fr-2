fonction gl_get_line() fait partie de la bibliothèque tecla (voir la page de manuel libtecla(3)). Si l'utilisateur tape sur un terminal, chaque appel lui demande une ligne de saisie, puis fournit des fonctionnalités d'édition interactives, similaires à celles du shell unix tcsh. En plus de l'édition de ligne de commande simple, elle prend en charge le rappel des lignes de commande précédemment saisies, la complétion des noms de fichiers avec la touche TAB, et l'expansion des caractères génériques dans les noms de fichiers en ligne. La documentation des fonctionnalités d'édition de ligne de commande au niveau utilisateur et de toutes les options de configuration utilisateur se trouve dans la page de manuel tecla(7). Cette page de manuel concerne la documentation destinée aux programmeurs souhaitant utiliser cette bibliothèque dans leur application. UN E

LES FONCTIONS UTILISÉES DANS

L'EXEMPLE

Les descriptions des fonctions utilisées dans l'exemple sont les suivantes

  GetLine *new_GetLine(size_t linelen, size_t

Cette fonction crée les ressources utilisées par la fonction gl_get_line() et retourne un pointeur opaque vers l'objet qui les contient. La longueur maximale d'une ligne de saisie est spécifiée via l'argument linelen, et le nombre d'octets à allouer pour stocker les lignes d'historique est défini par l'argument histlen. Les lignes d'historique sont stockées bout à bout dans un seul tampon de cette taille. Notez que cela signifie que le nombre de lignes d'historique qui peuvent être stockées à un moment donné dépend des longueurs des lignes individuelles. Si vous souhaitez placer une limite supérieure au nombre de lignes pouvant être stockées, voir la fonction gl_limit_history() décrite plus tard. Si vous ne voulez pas d'historique du tout, spécifiez histlen comme zéro, et aucun tampon d'historique ne sera

alloué.

En cas d'erreur, un message est affiché sur stderr et NULL est

retourné. 
  GetLine *del_GetLine(GetLine
*gl)

Cette fonction supprime les ressources qui ont été retournées par un appel précédent à new_GetLine(). Elle retourne toujours NULL (c'est-à-dire un objet supprimé). Elle ne fait rien si l'argument gl est NULL

  char *gl_get_line(GetLine *gl, const char *prompt,

;

La fonction gl_get_line() peut être appelée un nombre quelconque de fois pour lire la saisie de l'utilisateur. L'argument gl doit avoir été précédemment retourné par un appel à new_GetLine(). L'argument prompt doit être une chaîne normale terminée par NUL, spécifiant l'invite à présenter à l'utilisateur. Par défaut, les invites sont affichées littéralement, mais si elles sont activées avec la fonction gl_prompt_style() (voir plus tard), les invites peuvent contenir des directives pour souligner, passer en et hors des polices en gras, ou activer et désactiver la mise en

évidence.

Si vous souhaitez spécifier le contenu initial de la ligne pour que l'utilisateur la modifie, passez la chaîne souhaitée via l'argument start_line. Vous pouvez ensuite spécifier le caractère de cette ligne où le curseur est initialement positionnéd sur, en utilisant l'argument start_pos. Cela doit être -1 si vous voulez que le curseur suive le dernier caractère de la ligne de départ. Si vous ne voulez pas précharger la ligne de cette manière, envoyez start_line comme NULL, et définissez start_pos à -1. Notez que le pointeur de ligne retourné par un appel à gl_get_line() peut être transmis à l'appel suivant à gl_get_line() via le paramètre start_line. Cela permet à l'application de prendre la dernière ligne saisie et, si elle contient une erreur, de la présenter à nouveau à l'utilisateur pour la rééditer, avec le curseur initialement positionné à l'endroit où l'erreur a été

rencontrée.

La fonction gl_get_line() retourne un pointeur vers la ligne saisie par l'utilisateur, ou NULL en cas d'erreur ou à la fin de l'entrée. Le pointeur retourné fait partie de l'objet ressource gl spécifié, et ne doit donc pas être libéré par l'appelant, ni supposé inchangé d'un appel à l'autre. Lors de la lecture depuis un utilisateur sur un terminal, il y aura toujours un caractère de nouvelle ligne à la fin de la ligne retournée. Lorsque l'entrée standard provient d'un pipe ou d'un fichier, il y aura de même une nouvelle ligne, sauf si la ligne d'entrée était trop longue pour être stockée dans le tampon interne. Dans ce dernier cas, vous devriez appeler gl_get_line() à nouveau pour lire le reste de la ligne. Notez que ce comportement rend gl_get_line() similaire à fgets(). En fait, lorsque stdin n'est pas connecté à un terminal,gl_get_line() appelle simplement fget

s(
).

SOURCES DE CONFIGURATION

ALTERNATIVES

Comme mentionné ci-dessus, par défaut les utilisateurs ont la possibilité de configurer le comportement de gl_get_line() via un fichier de configuration appelé .teclarc dans leurs répertoires personnels. Le fait que toutes les applications partagent ce même fichier de configuration est à la fois un avantage et un inconvénient. Dans la plupart des cas, c'est un avantage, car cela encourage l'uniformité et libère l'utilisateur de la nécessité de configurer chaque application séparément. Dans certaines applications, cependant, ce seul moyen de configuration pose problème. C'est particulièrement vrai pour les logiciels embarqués, où il n'y a pas de système de fichiers pour lire un fichier de configuration, et aussi dans les applications où un choix radicalement différent de mappage de touches est nécessaire pour émuler une interface clavier héritée. Pour prendre en charge de tels cas, la fonction suivante permet à l'application de contrôler d'où les informations de configuration sont

lues. 
  int gl_configure_getline(GetLine *gl,
                           const char *app_string,
                           const char *app_file,
                           const char *user_file)
;

Elle permet aux commandes de configuration qui seraient normalement lues depuis le fichier ~/.teclarc de l'utilisateur, d'être lues depuis une ou plusieurs, ou aucune, des sources suivantes : une chaîne, un fichier de configuration spécifique à l'application, et/ou un fichier de configuration spécifique à l'utilisateur. Si cette fonction est appelée avant le premier appel à gl_get_line(), le comportement par défaut de lecture de ~/.teclarc au premier appel à gl_get_line() est désactivé ; toute la configuration doit donc être réalisée en utilisant les sources de configuration spécifiées avec cette

fonction.

Si app_string != NULL, alors il est interprété comme une chaîne contenant une ou plusieurs commandes de configuration, séparées les unes des autres dans la chaîne par des caractères de nouvelle ligne intégrés. Si app_file != NULL alors il est interprété comme le chemin complet d'un fichier de configuration spécifique à l'application. Si user_file != NULL alors il est interprété comme le chemin complet d'un fichier de configuration spécifique à l'utilisateur, tel que ~/.teclarc. Par exemple, dans l'appel

suivant, 
  gl_configure_getline(gl, "edit-mode vi \n nobeep",
                           "/usr/share/myapp/teclarc",
                           "~/.teclarc")
;

l'argument app_string fait démarrer l'application appelante en mode d'édition vi, au lieu du mode emacs par défaut, et désactive l'utilisation de la cloche du terminal par la bibliothèque. Elle tente ensuite de lire les commandes de configuration globales depuis un fichier optionnel appelé /usr/share/myapp/teclarc, puis lit enfin les commandes de configuration spécifiques à l'utilisateur depuis un fichier .teclarc optionnel dans le répertoire personnel de l'utilisateur. Notez que les arguments sont listés par ordre de priorité croissante, le contenu de app_string pouvant être potentiellement remplacé par des commandes dans app_file, et les commandes dans app_file pouvant être potentiellement remplacées par des commandes dans user_file

.

Vous pouvez appeler cette fonction autant de fois que nécessaire, les résultats étant cumulatifs, mais notez que des copies de tout nom de fichier spécifié via le paramètre app_file et user_file sont enregistrés en interne pour une utilisation ultérieure par la fonction de liaison de touches read-init-files ; si vous prévoyez d'appeler cette fonction plusieurs fois, assurez-vous que le dernier appel spécifie les noms de fichiers que vous souhaitez relire lorsque l'utilisateur demande que les fichiers de configuration soient

relus.

COMPLÉTION DE MOTS

PERSONNALISÉE

Si dans votre application, vous souhaitez que la complétion par TAB complète d'autres éléments en plus des noms de fichiers ou à leur place, vous pouvez organiser cela en enregistrant une fonction de rappel de complétion alternative, via un appel à la fonction gl_customize_c

ompletion(). 
  int gl_customize_completion(GetLine *gl, void *data,
                              CplMatchFn *match_fn)
;

L'argument data fournit un moyen à votre application de passer des informations arbitraires et spécifiques à l'application à la fonction de rappel. Celles-ci lui sont transmises à chaque fois qu'elle est appelée. Elles pourraient par exemple, pointer vers la table de symboles à partir de laquelle les complétions possibles doivent être recherchées. L'argument match_fn spécifie la fonction de rappel à appeler. Le type de fonction CplMatchFn est défini dans libtecla.h, tout comme une macro CPL_MATCH_FN() que vous pouvez utiliser pour déclarer et prototyper des fonctions de rappel. La déclaration et les responsabilités des fonctions de rappel sont décrites en profondeur dans la page de man cpl_complete_word(3)

.

En bref, la fonction de rappel est responsable de la recherche vers l'arrière dans la ligne d'entrée, à partir du point où l'utilisateur a appuyé sur TAB, pour trouver le début du mot en cours de complétion. Elle doit ensuite rechercher les complétions possibles de ce mot et les enregistrer une par une dans l'objet WordCompletion qui lui est passé en argument, en appelant la fonction cpl_add_completion(). Si la fonction de rappel souhaite fournir la complétion de noms de fichiers en plus de ses propres complétions spécifiques, elle a la possibilité d'appeler elle-même la fonction de rappel de complétion de noms de fichiers intégrée. Ceci est également documenté dans la page de man cpl_complete_w

ord(3).

Notez que si vous souhaitez que gl_get_line() retourne la ligne d'entrée actuelle lorsqu'une complétion réussie a été effectuée, vous pouvez organiser cela lorsque vous appelez cpl_add_completion(), en faisant du dernier caractère du suffixe de continuation un caractère de nouvelle ligne. Si vous faites cela, la ligne d'entrée sera mise à jour pour afficher la complétion, avec tout suffixe de continuation jusqu'au caractère de nouvelle ligne, puis gl_get_line() retournera cette ligne

d'entrée.

Si, pour une raison quelconque, votre fonction de rappel doit écrire quelque chose sur le terminal, elle doit appeler gl_normal_io() avant de le faire. Cela commencera une nouvelle ligne après la ligne d'entrée actuellement en cours d'édition, rétablira l'E/S normale du terminal, et indiquera à gl_get_line() que la ligne d'entrée devra

être redessinée lorsqu
e le rappel retournera.

AJOUT D'ACTIONS DE

COMPLÉTION

Dans la section précédente, la capacité à personnaliser le comportement de la seule action de complétion par défaut, complete-word, a été décrite. Dans cette section, la capacité à installer des fonctions d'action supplémentaires, afin que différents types de complétion de mots puissent être liés à différentes séquences de touches, est décrite. Cela est réalisé en utilisant la fonction gl_completion_action()

. 
  int gl_completion_action(GetLine *gl,
                           void *data, CplMatchFn *match_fn,
                           int list_only, const char *name,
                           const char *keyseq)
;

Les arguments data et match_fn sont tels que décrits dans la page de man cpl_complete_word, et spécifient la fonction de rappel qui doit être invoquée pour identifier les complétions possibles. L'argument list_only détermine si l'action qui est en cours de définition doit tenter de compléter le mot le plus loin possible dans la ligne d'entrée avant d'afficher les complétions ambiguës possibles, ou si elle doit simplement afficher la liste des complétions possibles sans toucher à la ligne d'entrée. La première option est sélectionnée en spécifiant une valeur de 0, et la seconde en spécifiant une valeur de 1. L'argument name spécifie le nom par lequel les fichiers de configuration et les futures invocations de cette fonction doivent se référer à l'action. Cela doit être soit le nom d'une action de complétion existante à modifier, soit un nouveau nom inutilisé pour une nouvelle action. Enfin, l'argument keyseq spécifie la séquence de touches par défaut à lier à l'action. Si c'est NULL, aucune nouvelle séquence de touches ne sera liée à

Attention, pour que l'utilisateur puisse changer la séquence de touches liée aux actions installées de cette manière, lorsque vous appelez gl_completion_action() pour installer une action donnée pour la première fois, vous devriez le faire entre l'appel à new_GetLine() et le premier appel à gl_get_line(). DÉFINITION D'ACTIONS

PERSONNALISÉES

Bien que les actions de liaison de touches intégrées soient suffisantes pour les besoins de la plupart des applications, une application spécialisée peut parfois avoir besoin de définir une ou plusieurs actions personnalisées, liées à des séquences de touches spécifiques à l'application. Par exemple, une application de vente bénéficierait d'une séquence de touches qui affichait le nom de la pièce correspondant à un numéro de pièce situé avant le curseur. Une telle fonctionnalité dépasse clairement le cadre des fonctions d'action intégrées. Ainsi, pour de tels cas particuliers, la fonction gl_register_action() est

fournie. 
  int gl_register_action(GetLine *gl, void *data,
			 GlActionFn *fn, const char *name,
			 const char *keyseq)
;

Cette fonction permet à l'application d'enregistrer une fonction externe, fn, qui sera ensuite appelée chaque fois que soit la séquence de touches spécifiée, keyseq, est saisie par l'utilisateur, soit l'utilisateur saisit une autre séquence de touches qu'il lie ensuite à l'action spécifiée, name, dans son fichier de configuration. L'argument data peut être un pointeur vers n'importe quoi que l'application souhaite voir transmis à la fonction d'action, fn, chaque fois que cette fonction est

invoquée.

La fonction d'action, fn, devrait être déclarée en utilisant la macro suivante, qui est définie dans libtecl

a.h. 
  #define GL_ACTION_FN(fn) GlAfterAction (fn)(GetLine *gl, \
              void *data, int count, size_t curpos, \
              const char
*line)

Les arguments gl et data sont ceux qui ont été précédemment passés à gl_register_action() lorsque la fonction d'action a été enregistrée. L'argument count est un argument numérique que l'utilisateur a la possibilité de saisir en utilisant l'action digit-argument, avant d'invoquer l'action. Si l'utilisateur n'entre pas de nombre, alors l'argument count est défini à 1. Nominalement, cet argument est interprété comme un nombre de répétitions, ce qui signifie que l'action doit être répétée ce nombre de fois. En pratique, cependant, pour certaines actions un nombre de répétitions n'a que peu de sens. Dans de tels cas, les actions peuvent soit simplement ignorer l'argument count, soit utiliser sa valeur à une autre

fin.

Une copie de la ligne d'entrée actuelle est passée dans l'argument en lecture seule line. La position actuelle du curseur dans cette chaîne est donnée par l'index contenu dans l'argument curpos. Notez que la manipulation directe de la ligne d'entrée et de la position du curseur n'est pas autorisée. C'est parce que les règles dictées par divers modes, tels que le mode vi par rapport au mode emacs, le mode sans écho, et le mode d'insertion par rapport au mode de remplacement etc, rendent la tâche trop complexe pour un développeur d'application afin d'écrire une action d'édition conforme, ainsi que de contraindre les changements futurs aux internes de gl_get_line(). Une solution potentielle à ce dilemme serait de permettre à la fonction d'action d'éditer la ligne en utilisant les actions d'édition existantes. Cela est actuellement à

l'étude.

Si la fonction d'action souhaite écrire du texte sur le terminal, sans que cela se mélange avec le texte affiché de la ligne d'entrée, ou lire depuis le terminal sans avoir à gérer l'E/S brute du terminal, alors avant de faire l'une de ces opérations, elle doit suspendre temporairement l'édition de ligne en appelant la fonction gl_normal_io(). Cette fonction vide toute sortie en attente vers le terminal, déplace le curseur au début de la ligne qui suit la dernière ligne du terminal de la ligne d'entrée, puis restaure le terminal à un état qui convient à l'utilisation avec les fonctions stdio du C. Ce dernier comprend des choses comme la restauration du mappage normal de \n vers \r\n, et, en mode serveur, la restauration de la forme bloquante normale de l'E/S du terminal. Après avoir appelé cette fonction, la fonction d'action peut lire depuis et écrire vers le terminal sans craindre de créer un désordre. Il n'est pas nécessaire pour la fonction d'action de restaurer l'environnement d'édition original avant de retourner. Cela est fait automatiquement par gl_get_line() après le retour de la fonction d'action. Voici un exemple simple d'une fonction d'action qui écrit la phrase "Hello world" sur une nouvelle ligne du terminal après la ligne en cours d'édition. Lorsque cette fonction retourne, la ligne d'entrée est redessinée sur la ligne qui suit la ligne "Hello world", et l'édition de ligne

reprend. 
  static GL_ACTION_FN(say_hello_fn)
  {
    if(gl_normal_io(gl))   /* Suspendre temporairement l'édition */
      return GLA_ABORT;
    printf("Hello world\n");
    return GLA_CONTINUE;
}

Les fonctions d'action doivent retourner l'une des valeurs suivantes, pour indiquer à gl_get_line() comment

procéder. 
  GLA_ABORT     -   Faire en sorte que gl_get_line() retourne NULL.
  GLA_RETURN    -   Faire en sorte que gl_get_line() retourne la
                    ligne d'entrée complétée.
  GLA_CONTINUE  -   Reprendre l'édition de la ligne de
commande.

Notez que le argument name de gl_register_action() spécifie le nom par lequel un utilisateur peut référencer l'action dans son fichier de configuration. Cela lui permet de relier l'action à une séquence de touches alternative. Pour que cela fonctionne, il est nécessaire d'appeler gl_register_action() entre l'appel à new_GetLine() et le premier appel à gl_get_

lin
e().

ARCHIVAGE MANUEL DE

L'HISTORIQUE

Par défaut, chaque fois qu'une ligne est saisie par l'utilisateur, elle est automatiquement ajoutée à la liste d'historique, juste avant que gl_get_line() retourne la ligne à l'appelant. C'est pratique pour la majorité des applications, mais il y a aussi des applications qui ont besoin d'un contrôle plus fin sur ce qui est ajouté à la liste d'historique. Dans de tels cas, l'ajout automatique des lignes saisies à la liste d'historique peut être désactivé en appelant la fonction gl_automatic

_history(). 
  int gl_automatic_history(GetLine *gl, int enable)
;

Si cette fonction est appelée avec son argument enable défini à 0, gl_get_line() n'archivera pas automatiquement les lignes saisies ultérieurement. L'archivage automatique peut être réactivé plus tard, en appelant cette fonction à nouveau, avec son argument enable défini à 1. Pendant que l'archivage automatique de l'historique est désactivé, l'application appelante peut utiliser la gl_append_history() pour ajouter des lignes à la liste d'historique selon les

besoins. 
  int gl_append_history(GetLine *gl, const char *line)
;

L' argument line spécifie la ligne à ajouter à la liste d'historique. Cela doit être une chaîne normale terminée par ' '. Si cette chaîne contient des caractères de nouvelle ligne, la ligne qui sera archivée dans la liste d'historique sera terminée par le premier d'entre eux. Sinon elle sera terminée par le terminateur ' '. Si la ligne est plus longue que la longueur maximale de ligne d'entrée, qui a été spécifiée lorsque new_GetLine() a été appelé, quand la ligne sera rappelée, elle sera tronquée à la gl_get_line() longueur de ligne

réelle.

Si réussi, gl_append_history() retourne 0. Sinon elle retourne une valeur non nulle, et définit errno à l'une des valeurs

suivantes. 
   EINVAL  -  L'un des arguments passés à
              gl_append_history() était NULL.
   ENOMEM  -  La ligne spécifiée était plus longue que la taille
              allouée du tampon d'historique (comme spécifié quand
              new_GetLine() a été appelé), donc elle n'a pas pu être
archivée.

Une description textuelle de l'erreur peut être obtenue optionnellement en appelant gl_error_message(). Notez qu'après une telle erreur, la liste d'historique reste dans un état valide pour recevoir de nouvelles lignes d'historique, donc il y a peu de mal à simplement ignorer le statut de retour de gl_append_

CONFIGURATION DIVERSE DE

L'HISTORIQUE

Si vous souhaitez changer la taille du tampon d'historique qui a été initialement spécifiée dans l'appel à new_GetLine(), vous pouvez le faire avec la fonction gl_resize_history()

  int gl_resize_history(GetLine *gl, size_t histlen)

  void gl_limit_history(GetLine *gl, int max_lines)

La fonction constructeur new_GetLine() suppose que l'entrée doit être lue depuis stdin, et que la sortie est écrite vers stdout. La fonction suivante vous permet de basculer vers d'autres flux d'entrée et de

     une boucle d'événements externe. Bien que ce soit une méthode très
     polyvalente, elle implique d'assumer certaines
     responsabilités qui sont normalement effectuées en coulisses par gl_get_line().

     clavier de l'utilisateur, vous pouvez lui demander de surveiller également

terminal.

TRAITEMENT FIABLE DES

SIGNAUX

Le traitement des signaux est étonnamment difficile à faire de manière fiable sans conditions de course. Dans gl_get_line(), beaucoup de soins ont été pris pour permettre aux applications d'effectuer un traitement fiable des signaux autour de gl_get_line(). Cette section explique comment tirer parti de

cela.

À titre d'exemple des problèmes qui peuvent survenir si l'application n'est pas écrite correctement, imaginez que votre application ait un gestionnaire de signal SIGINT qui définit un drapeau global. Supposons maintenant que l'application teste ce drapeau juste avant d'invoquer gl_get_line(). Si un signal SIGINT est reçu dans la petite fenêtre de temps entre l'instruction qui teste la valeur de ce drapeau et l'instruction qui appelle gl_get_line(), alors gl_get_line() ne verra pas le signal et ne sera pas interrompu. Par conséquent, l'application ne pourra pas répondre au signal tant que l'utilisateur n'aura pas fini de saisir la ligne de saisie et que gl_get_line() n'aura pas retourné. Selon l'application, cela peut être ou non un désastre, mais au minimum cela dérouterait

l'utilisateur.

La manière d'éviter ces problèmes est de faire ce qui

suit.

1. Si nécessaire, utilisez la fonction gl_trap_signal() pour
configurer gl_get_line() pour interrompre lorsque des signaux
importants sont

interceptés.

2. Configurez gl_get_line() de sorte que si l'un des
signaux qu'il intercepte est bloqué quand
gl_get_line() est appelé, il sera débloqué
automatiquement pendant les moments où gl_get_line()
attend une E/S. Cela peut être fait soit
signal par signal, en appelant la
fonction gl_trap_signal(), et en spécifiant l'attribut
GLS_UNBLOCK du signal, soit globalement en
appelant la fonction gl_catch_blocked()

. 
     void gl_catch_blocked(GetLine *gl)
;


Cette fonction ajoute simplement l'attribut GLS_UNBLOCK
à tous les signaux qu'elle est actuellement configurée pour
piéger

.

3. Juste avant d'appeler gl_get_line(), bloquez la délivrance
de tous les signaux que gl_get_line() est
configurée pour piéger. Cela peut être fait en utilisant la fonction POSIX
sigprocmask() en conjonction avec la
fonction gl_list_signals()

. 
      int gl_list_signals(GetLine *gl, sigset_t *set)
;


Cette fonction retourne l'ensemble des signaux qu'elle est
actuellement configurée pour intercepter dans l'argument set,
qui est sous la forme requise par sigprocma

sk().

4. Dans l'exemple, on testerait maintenant le drapeau global que
le gestionnaire de signal définit, sachant qu'il n'y a maintenant plus
de danger que ce drapeau soit défini à nouveau avant que
gl_get_line() ne débloque ses signaux lors de l'exécution
d'E/S

.

5. Finalement gl_get_line() retourne, soit parce qu'un
signal a été intercepté, une erreur s'est produite, ou l'utilisateur
a terminé la saisie de sa

ligne.

6. Maintenant, on vérifierait à nouveau le drapeau global de signal, et s'il
est défini, on y répondrait, et on remettrait le drapeau à

zéro.

7. Utilisez sigprocmask() pour débloquer les signaux qui ont été
bloqués à l'étape

3.

La même technique peut être utilisée autour de certaines fonctions POSIX conscientes des signaux, telles que sigsetjmp() et sigsuspend(), et en particulier, la première de ces deux fonctions peut être utilisée en conjonction avec siglongjmp() pour implémenter un traitement des signaux sans conditions de course autour d'autres appels système longs. La manière de faire cela est expliquée ensuite, en montrant comment gl_get_line() parvient à piéger fiablement les signaux autour d'appels à des fonctions comme read() et select() sans conditions de

course.

La première chose que gl_get_line() fait, chaque fois qu'elle est appelée, est d'utiliser la fonction POSIX sigprocmask() pour bloquer la délivrance de tous les signaux qu'elle est actuellement configurée pour intercepter. Cela est redondant si l'application les a déjà bloqués, mais cela ne fait aucun mal. Elle annule cette étape juste avant de

retourner.

Chaque fois que gl_get_line() doit appeler read() ou select() pour attendre une saisie de l'utilisateur, elle appelle d'abord la fonction POSIX sigsetjmp(), en s'assurant de spécifier une valeur non nulle pour son argument savesigs. La raison de ce dernier argument deviendra claire

bientôt.

Si sigsetjmp() retourne zéro, gl_get_line() fait alors ce qui

suit. 
a. Elle utilise la fonction POSIX sigaction() pour enregistrer
   un gestionnaire de signal temporaire pour tous les signaux qu'elle
   est configurée pour piéger. Ce gestionnaire de signal fait deux
   choses.
   1. Il enregistre le numéro du signal reçu
      dans une variable de portée fichier.
   2. Il appelle ensuite la fonction POSIX siglongjmp()
      en utilisant le tampon qui a été passé à
      sigsetjmp() comme premier argument, et
      une valeur non nulle comme second argument.
   Quand ce gestionnaire de signal est enregistré, le membre sa_mask
   de l'argument struct sigaction act de l'appel à sigaction() est configuré pour contenir tous
   les signaux que gl_get_line() intercepte. Cela
   garantit qu'un seul signal sera intercepté à la fois par
   notre gestionnaire de signal, ce qui à son tour garantit que
   plusieurs instances de notre gestionnaire de signal ne se
   marchent pas sur les pieds.
b. Maintenant que le gestionnaire de signal a été configuré,
   gl_get_line() débloque tous les signaux qu'elle
   est configurée pour piéger.
c. Elle appelle ensuite les appels système read() ou select() pour attendre une saisie au clavier.
d. Si cet appel système retourne (c.-à-d. aucun signal n'est reçu),
   gl_get_line() bloque à nouveau la délivrance des signaux
   d'intérêt.
e. Elle rétablit ensuite les gestionnaires de signal qui ont été
   déplacés par celui qui vient d'être
installé.

Alternativement, si sigsetjmp() retourne non nul, cela signifie l'un des signaux interceptés a été capturé pendant l'exécution des étapes ci-dessus. Lorsque cela se produit, gl_get_line() effectue ce qui

suit.

Tout d'abord, notez que lorsqu'un appel à siglongjmp() provoque le retour de sigsetjmp(), à condition que l'argument savesigs de sigsetjmp() ait été non nul, comme spécifié ci-dessus, le masque de traitement des signaux est restauré à l'état où il se trouvait lorsque sigsetjmp() a été appelé. C'est la différence importante entre sigsetjmp() et l'ancien setjmp() problématique, et c'est l'élément essentiel qui rend possible l'évitement des conditions de course dans la gestion des signaux. Grâce à cela, nous sommes garantis que tous les signaux que nous avons bloqués avant d'appeler sigsetjmp() sont de nouveau bloqués dès qu'un signal est capturé. Les instructions suivantes, qui sont alors exécutées, sont donc garanties d'être exécutées sans qu'aucun autre signal ne soit

capturé.

1. Si cela lui est demandé par les attributs de configuration de
gl_get_line() du signal qui a été capturé,
gl_get_line() restaure les attributs du terminal à
l'état dans lequel ils se trouvaient lorsque gl_get_line() a été
appelé. C'est particulièrement important pour les signaux qui
suspendent ou terminent le processus, car sinon le
terminal serait laissé dans un état

inutilisable.

2. Il réinstalle ensuite les gestionnaires de signaux de

l'application.

3. Il utilise ensuite la fonction raise()
de la bibliothèque standard C pour renvoyer à l'application le signal qui
a été

3. Ensuite, il débloque la livraison du signal que nous venons de

original de l'application, qui peut maintenant le traiter comme il

Il annule ensuite toute action effectuée dans la première des

LA TAILLE DU

TERMINAL

Sur la plupart des systèmes, la combinaison de l'ioctl TIOCGWINSZ et du signal SIGWINCH est utilisée pour maintenir une idée précise de la taille du terminal. La taille du terminal est de nouveau interrogée à chaque fois que gl_get_line() est appelé et chaque fois qu'un signal SIGWINCH est

reçu.

Sur les quelques systèmes où ce mécanisme n'est pas disponible, au démarrage new_GetLine() cherche d'abord les variables d'environnement LINES et COLUMNS. Si elles ne sont pas trouvées, ou si elles contiennent des valeurs inutilisables, alors si une base de données d'informations sur le terminal comme terminfo ou termcap est disponible, la taille par défaut du terminal est recherchée dans cette base de données. Si cela ne permet pas non plus d'obtenir la taille du terminal, une taille par défaut de 80 colonnes par 24 lignes est

utilisée.

Même sur les systèmes qui prennent en charge ioctl(TIOCGWINSZ), si le terminal se trouve à l'autre extrémité d'une ligne série, le pilote du terminal n'a généralement aucun moyen de détecter quand un redimensionnement se produit ou d'interroger la taille actuelle. Dans de tels cas, aucun SIGWINCH n'est envoyé au processus, et les dimensions renvoyées par ioctl(TIOCGWINSZ) ne sont pas correctes. La seule façon de gérer de tels cas est de fournir un moyen à l'utilisateur de saisir une commande qui indique au système distant la nouvelle taille. Cette commande appellerait alors la fonction gl_set_term_size() pour informer gl_get_line() du changement de

taille. 
  int gl_set_term_size(GetLine *gl, int ncolumn, int nline)
;

Les arguments ncolumn et nline sont utilisés pour spécifier les nouvelles dimensions du terminal, et ne doivent pas être inférieurs à 1. Sur les systèmes qui prennent en charge ioctl(TIOCGWINSZ), cette fonction appelle d'abord ioctl(TIOCSWINSZ) pour informer le pilote du terminal du changement de taille. En mode E/S serveur non bloquant, si une ligne est actuellement en cours de saisie, la ligne saisie est alors redessinée pour s'adapter à la taille modifiée. Enfin, les nouvelles valeurs sont enregistrées dans gl pour une utilisation future par gl_get_li

ne().

La fonction gl_terminal_size() vous permet d'interroger la taille actuelle du terminal, et d'installer une taille de secours alternative pour les cas où la taille n'est pas disponible. Attention, la taille du terminal ne sera pas disponible si vous lisez depuis un pipe ou un fichier, de sorte que les valeurs par défaut peuvent être importantes même sur les systèmes qui prennent en charge des moyens de découvrir la taille du

terminal. 
  typedef struct {
    int nline;        /* The terminal has nline lines */
    int ncolumn;      /* The terminal has ncolumn columns */
  } GlTerminalSize;
  GlTerminalSize gl_terminal_size(GetLine *gl,
                                  int def_ncolumn,
                                  int def_nline)
;

Cette fonction met d'abord à jour les dimensions de secours du terminal

de

gl_get_line(), puis enregistre ses résultats dans la valeur de retour. Les arguments def_ncolumn et def_nline spécifient le nombre par défaut de colonnes et de lignes du t

erminal à utiliser si la taille du te
rminal ne peut pas être déterminée via

ioctl(TIOCGWINSZ) ou les variables

d'environnement.

CACHER CE QUE VOUS TAPEZ Lors de la saisie d'informations sensibles, comme les mots de passe, il est préférable de ne pas faire écho sur le terminal du texte que vous saisissez. De plus, un tel texte ne devrait pas être enregistré dans la liste d'historique, car quelqu'un trouvant votre terminal sans surveillance pourrait alors le rappeler, ou quelqu'un fouillant dans vos répertoires pourrait le voir dans votre fichier d'historique. En tenant compte de cela, la fonction gl_echo_mode() vous permet d'activer et de désactiver l'affichage et l'archivage de tout texte qui est saisi par la suite dans

les appels à 
  gl_get_line()
.

int gl_echo_mode(GetLine *gl, int enable); L' argument enable spécifie si le texte saisi doit être visible ou non. S'il vaut 0, les lignes saisies par la suite ne seront pas visibles sur le terminal, et ne seront pas enregistrées dans la liste d'historique. S'il vaut 1, les lignes saisies par la suite seront affichées au fur et à mesure de leur saisie, et à condition que l'historique n'ait pas été désactivé via un appel à gl_toggle_history(), elles seront également archivées dans la liste d'historique. Enfin, si l' argument enable vaut -1, le mode d'écho est laissé inchangé, ce qui vous permet d'interroger de manière non destructive le réglage actuel via la valeur de retour. Dans tous les cas, la valeur de retour de la fonction est 0 si l'écho était désactivé avant l'appel de la fonction,

et

1 s'il

était
activé.

Lorsque l'écho est désactivé, notez que même si l'achèvement par tabulation complétera votre préfixe de manière invisible aussi loin que possible, les complétions ambiguës ne seront pas

affichées.

REQUÊTES À UN SEUL CARACTÈRE Utiliser gl_get_line() pour demander à l'utilisateur une réponse d'un seul caractère est incommode pour l'utilisateur, car il doit appuyer sur la touche entrée ou retour avant que le caractère qu'il a tapé ne soit renvoyé au programme. C'est pourquoi

la 
  fonction gl_query_char() a été fournie pour
    les requêtes à un seul caractère comme
celle-ci.

int gl_query_char(GetLine *gl, const char *prompt, char defchar); Cette fonction affiche l'invite spécifiée au début d'une nouvelle ligne, et attend que l'utilisateur tape un caractère. Lorsque l'utilisateur tape un caractère, gl_query_char() l'affiche à droite de l'invite, passe à la ligne suivante, puis renvoie le caractère au programme appelant. La valeur de retour de la fonction est le caractère qui a été tapé. Si la lecture a dû être abandonnée pour une raison quelconque, EOF est renvoyé à la place. Dans ce dernier cas, l'application peut appeler la fonction précédemment

documentée

gl_return_status(), pour savoir ce qui s'est mal passé. Cela pourrait, par exemple, être la réception d'un signal, ou le déclenchement du minuteur d'inactivité optionnel. Si l'utilisateur appuie simplement sur entrée, la valeur de l' argument defchar est substituée. Cela signifie que lorsque l'utilisateur appuie sur newline ou sur retour, le caractère spécifié dans defchar est affiché après l'invite, comme si l'utilisateur l'avait tapé, et est également renvoyé à l'application appelante. Si un tel remplacement n'est pas important, passez simplement '0 comme val

eur de

defchar

.

Si le caractère saisi est un caractère non imprimable, il est affiché symboliquement. Par exemple, control-A est affiché comme ^A, et les caractères au-delà de 127 sont affichés en octal, précédés d'une barre oblique inverse. Comme avec gl_get_line(), l'écho du caractère saisi peut être désactivé à l'aide de

la

fonction gl_echo_mode(). Si le processus appelant est suspendu pendant qu'il attend que l'utilisateur tape sa réponse, le curseur est déplacé sur la ligne suivant la ligne d'invite, puis lorsque le processus reprend, l'invite est réaffichée,

et

gl_query_char() reprend l'attente que l'utilisateur tape un caractère. Notez qu'en mode serveur non bloquant, (voir gl_io_mode(3)), si une ligne d'entrée incomplète est en cours de lecture lorsque gl_query_char() est appelé, la ligne d'entrée partielle est abandonnée et effacée du terminal, avant que la nouvelle invite ne soit affichée. Le prochain

appel
à

gl_get_line() commencera donc à éditer une nouvelle

ligne.

LECTURE DE CARACTÈRES BRUTS Alors que la fonction gl_query_char() invite visiblement l' utilisateur à saisir un caractère, et affiche ce qu'il a tapé, la fonction gl_read_char() lit un caractère de signal auprès de l'utilisateur, sans rien écrire sur le terminal, ni perturber une ligne d'entrée incomplètement saisie. Cela signifie qu'elle peut être appelée non seulement entre les appels à gl_get_line(), mais aussi depuis des fonctions de rappel que l' application a enregistrées pour être

appelées par 
  gl_get_line()
.

int gl_read_char(GetLine *gl); En cas de succès, la valeur de retour de gl_read_char() est le caractère qui a été lu. En cas d'échec, EOF est renvoyé, et la fonction gl_return_status() peut être appelée pour savoir ce qui s'est mal passé. Les possibilités incluent le déclenchement du minuteur d'inactivité optionnel, la réception d'un signal configuré pour interrompre gl_get_line(), ou le blocage des E/S du terminal, en mode E/S serveur non

bloquant.

Attention, certaines touches du clavier, comme les touches de fonction et les touches de curseur, génèrent généralement au moins 3 caractères chacune, de sorte qu'un seul appel à gl_read_char() ne't be enough t

o identify su
ch keystrokes.

AFFICHER DU TEXTE DE MANIÈRE

DYNAMIQUE

Entre les appels à gl_get_line(), la fonction gl_display_text() fournit un moyen pratique d'afficher des paragraphes de texte, justifiés à gauche et répartis sur une ou plusieurs lignes du terminal en fonction des contraintes de la largeur courante du terminal. Des exemples d'utilisation de cette fonction se trouvent dans les programmes de démonstration, où elle est utilisée pour afficher des introductions. Dans ces exemples, l'utilisation avancée de préfixes, suffixes et lignes de remplissage facultatifs pour dessiner un cadre autour du texte est également

illustrée. 
  int gl_display_text(GetLine *gl, int indentation,
                      const char *prefix,
                      const char *suffix, int fill_char,
                      int def_width, int start,
                      const char *string)
;

Si gl n'est pas actuellement connecté à un terminal, par exemple si la sortie d'un programme qui utilise gl_get_line() est acheminée via un tube vers un autre programme ou redirigée vers un fichier, alors la valeur du paramètre def_width est utilisée comme largeur du

terminal.

L'argument indentation spécifie le nombre de caractères à utiliser pour indenter chaque ligne de sortie. L'argument fill_char spécifie le caractère qui sera utilisé pour effectuer cette

indentation.

L'argument prefix peut être soit NULL, soit une chaîne à placer au début de chaque nouvelle ligne (après toute indentation). De même, l'argument suffix peut être soit NULL, soit une chaîne à placer à la fin de chaque ligne. Le suffixe est placé aligné à droite du terminal, et tout espace entre son premier caractère et le dernier mot de cette ligne est rempli par le caractère spécifié via l'argument fill_char. Normalement, le caractère de remplissage est une

espace.

L'argument start indique à gl_display_text() combien de caractères ont déjà été écrits sur la ligne de terminal courante, et indique ainsi l'index de colonne de départ du curseur. Puisque la valeur de retour de gl_display_text() est l'index de colonne de fin du curseur, en passant la valeur de retour d'un appel à l'argument start de l'appel suivant, un paragraphe réparti sur plus d'une chaîne peut être composé en appelant gl_display_text() pour chaque portion successive du paragraphe. Notez que des caractères de saut de ligne littéraux sont nécessaires à la fin de chaque paragraphe pour forcer le début d'une nouvelle

ligne.

En cas d'erreur, gl_display_tex

t() renv
oie -1.

JEUX DE CARACTÈRES

INTERNATIONAUX

Depuis la version 1.4.0 de libtecla, gl_get_line() est propre aux 8 bits. Cela signifie que tous les caractères 8 bits imprimables dans la locale actuelle de l'utilisateur sont désormais affichés verbatim et inclus dans la ligne de saisie renvoyée. En supposant que le programme appelant contient correctement un appel comme

celui-ci, 
  setlocale(LC_CTYPE, "")
;

alors la locale actuelle est déterminée par la première des variables d'environnement LC_CTYPE, LC_ALL, et LANG, dont on trouve qu'elle contient un nom de locale valide. Si aucune de ces variables n'est définie, ou si le programme néglige d'appeler setlocale, alors la locale par défaut C est utilisée, qui est l'ASCII 7 bits américain. Sur la plupart des plates-formes de type unix, vous pouvez obtenir une liste des locales valides en tapant la commande

: 
  locale
-a

à l'invite du shell. Une documentation supplémentaire sur la manière dont l'utilisateur peut utiliser cela pour saisir des caractères internationaux se trouve dans la page de manu

el tec
la(7).

SÉCURITÉ DES

THREADS

Dans un programme multi-thread, vous devriez utiliser la version libtecla_r.a de la bibliothèque. Celle-ci utilise des versions réentrantes des fonctions système, lorsqu'elles sont disponibles. Malheureusement, ni terminfo ni termcap n'ont été conçus pour être réentrants, vous ne

pouvez donc pas utiliser en toute sécurité les fonctions du module getline dans plusieurs threads (vous pouvez utiliser les modules séparés d'expansion de fichier et de complétion de mots dans plusieurs threads, voir les pages de manuel correspondantes pour plus de détails). Cepend
ant, en raison de l'utilisation de fonctions POSIX réentrantes pour la recherche des répertoires personnels, etc., il est sûr d'utiliser ce module depuis un seul thread d'un programme multi-thread, à condition que vos autres threads n'utilisent aucune fonction termcap ou terminfo.
