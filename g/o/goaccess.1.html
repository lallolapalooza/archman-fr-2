DESCRIPTIO

N

GoAccess est un analyseur de journaux web en temps réel open source et un visualiseur interactif qui s'exécute dans un terminal sur les systèmes *nix ou via votre navigateur

.

Il fournit des statistiques HTTP rapides et précieuses pour les administrateurs système qui ont besoin d'un rapport visuel du serveur à la

volée.

GoAccess analyse le fichier de journal web spécifié et affiche les données dans le terminal X. Les fonctionnalités incluent

:
Statistiques générales
:
Ce panneau donne un résumé de plusieurs métriques, telles que le nombre de requêtes valides et invalides, le temps pris pour analyser l'ensemble de données, les visiteurs uniques, les fichiers demandés, les fichiers statiques (CSS, ICO, JPG, etc.), les référents HTTP, les erreurs 404, la taille du fichier de journal analysé et la consommation de bande
passante.
Visiteurs
uniques
Ce panneau affiche des métriques telles que les hits, les visiteurs uniques et la bande passante cumulée par date. Les requêtes HTTP contenant la même IP, la même date et le même user agent sont considérées comme un visiteur unique. Par défaut, il inclut les robots d'indexation/les
araignées.
Optionnellement, la spécificité de la date peut être définie au niveau de l'heure en utilisant --date-spec=hr, ce qui affichera des dates telles que 05/Jun/2016:16, ou au niveau de la minute produisant 05/Jun/2016:16:59. C'est idéal si vous souhaitez suivre votre trafic quotidien au niveau de l'heure ou de la
minute.
Fichiers
demandés
Ce panneau affiche les fichiers (non statiques) les plus demandés sur votre serveur web. Il montre les hits, les visiteurs uniques et le pourcentage, ainsi que la bande passante cumulée, le protocole et la méthode de requête
utilisée.
Fichiers statiques
demandés
Liste les fichiers statiques les plus fréquents tels que les types de fichiers JPG, CSS, SWF, JS, GIF et PNG, avec les mêmes métriques que le panneau précédent. Des fichiers statiques supplémentaires peuvent être ajoutés au fichier de
configuration.
404 ou
Introuvable
Affiche les mêmes métriques que les panneaux de requêtes précédents, cependant, ses données contiennent toutes les pages qui n'ont pas été trouvées sur le serveur, ou communément connues sous le nom de code de statut
404.
Hôt
es
Ce panneau contient des informations détaillées sur les hôtes eux-mêmes. C'est idéal pour repérer les robots d'indexation agressifs et identifier qui consomme votre bande passante.

Développer le panneau peut afficher plus d'informations telles que le résultat de la résolution DNS inverse de l'hôte, le pays d'origine et la ville. Si l' argument -a est activé, une liste de user agents peut être affichée

--ws-auth=<jwt[:secret]> | jwt:verify:secret
Active l'authentification WebSocket à l'aide d'un jeton Web JSON (JWT). Cette option prend en charge deux formats selon que le JWT est généré localement ou récupéré et vérifié extérieurement :
<jwt[:secret]> : Spécifie un JWT statique pour l'authentification WebSocket, avec un secret optionnel pour la génération ou la validation locale. Si seul « jwt » est fourni (par exemple, --ws-auth=jwt), GoAccess génère un JWT en utilisant un secret provenant de la variable d'environnement GOACCESS_WSAUTH_SECRET ou un secret par défaut compatible HS256 si non défini. Si un secret est inclus (par exemple, --ws-auth=jwt:monsecret), il est utilisé directement comme clé de signature HS256 ou lu à partir d'un fichier si la valeur est un chemin valide (par exemple, --ws-auth=jwt:/chemin/vers/secret.key).
jwt:verify:secret : Active la vérification d'un JWT récupéré extérieurement (par exemple, via --ws-auth-url). Le mot-clé « verify » indique que le JWT est fourni par une source externe, et le secret doit être spécifié pour la validation. Le secret peut être une clé HS256 directe (par exemple, --ws-auth=jwt:verify:monsecret), un chemin de fichier (par exemple, --ws-auth=jwt:verify:/chemin/vers/secret.key), ou un nom de variable d'environnement (par exemple, --ws-auth=jwt:verify:$JWT_SECRET). Ce format est requis lors de l'utilisation de --ws-auth-url et éventuellement de --ws-auth-refresh-url pour récupérer et vérifier les JWT à partir des points d'accès externes.
Lorsque cette option est utilisée, le rapport HTML ne chargera pas les données analysées initiales. Au lieu de cela, il n'affichera le rapport que si l'authentification réussit, garantissant un accès sécurisé aux données en temps réel.
Le système traite cette option comme suit :
Pour <jwt[:secret]> : Si aucun secret n'est fourni, GoAccess génère un JWT localement en utilisant la variable d'environnement GOACCESS_WSAUTH_SECRET ou un secret par défaut. Si un secret est spécifié, il est utilisé pour signer le JWT (directement ou à partir d'un fichier).
Pour jwt:verify:secret : Le secret est obligatoire et utilisé pour vérifier les JWT récupérés extérieurement. Il doit correspondre à la clé de signature utilisée par le serveur d'authentification externe (par exemple, à --ws-auth-url).
Nécessite de compiler GoAccess avec --with-openssl.
--ws-auth-expire=<secondes>
Définit le délai après lequel le JWT expire. Par défaut, il est de 8 heures (28800 secondes) si non spécifié.
Uniquement disponible pour les JWT générés localement.
Les utilisateurs peuvent spécifier le délai d'expiration dans différents formats. La valeur est convertie en secondes pour la validation d'expiration du JWT. Formats pris en charge :
  • "3600" -> 3600 secondes
  • "120s" -> 2 minutes
  • "24h" -> 24 heures = 86 400 secondes
  • "10m" -> 10 minutes = 600 secondes
  • "10d" -> 10 jours = 864 000 secondes
Le délai d'expiration contrôle la durée pendant laquelle le JWT reste valide après son émission, garantissant des connexions WebSocket sécurisées.
--ws-auth-url=<url>
Spécifie l'URL à partir de laquelle GoAccess récupère le JWT initial pour authentifier la connexion WebSocket.
Lorsque cette option est utilisée, GoAccess envoie une requête GET à l'URL spécifiée pour récupérer un JWT initial. La réponse doit être un objet JSON contenant les champs status, access_token, refresh_token et expires_in.
Exemple : --ws-auth-url=https://site.com/api/get-auth-token
Lors de la récupération du jeton, GoAccess utilise { credentials: 'include' } dans le cadre de la requête pour récupérer en toute sécurité le jeton d'accès en fonction de la session d'authentification existante de l'utilisateur dans votre système, garantissant ainsi que la récupération du jeton est sûre tant que vos utilisateurs sont authentifiés.
Cette option vous permet d'intégrer votre système d'authentification existant au tableau de bord GoAccess, en utilisant des points d'accès de récupération de jetons.
--ws-auth-refresh-url=<url>
Spécifie l'URL à partir de laquelle GoAccess récupère un nouveau JWT lorsque le jeton actuel est sur le point d'expirer.
GoAccess rafraîchit proactivement le JWT 60 secondes avant expiration en envoyant une requête POST avec le refresh_token à cette URL. Si elle n'est pas fournie, elle utilise par défaut la même URL que --ws-auth-url.
Exemple : --ws-auth-refresh-url=https://site.com/api/refresh-token
Le format de réponse doit correspondre à celui de l'URL d'authentification initiale.

Flux d'authentification WebSocket

GoAccess offre des options d'authentification flexibles, prenant en charge les approches sans état et avec état. Dans l'approche sans état, le jeton de rafraîchissement est obtenu sans cookies ni protection CSRF ; votre backend valide la signature du jeton de rafraîchissement et émet un nouveau jeton d'accès. Alternativement, l'approche avec état permet à la récupération initiale d'émettre des JWT ainsi qu'un `csrf_token`, qui est stocké dans la session. DESCRIPTION

GoAccess is an open source real-time web log analyzer. It provides fast and visual web server log analysis. This tool provides Apache, Nginx, Amazon CloudFront, IIS and custom log formats on your terminal in real time.

It depends on ncurses for the terminal interface. For the real-time HTML report, you will need:

  • Boost.Numpy (C++ library)
  • libconfig
  • libGeoIP (optional, for GeoIP localization)
  • libz
  • libpcre

It also requires make, gcc or clang, and autoconf.

GoAccess can parse access logs with the following formats:

  • Common Log Format (CLF)
  • Combined Log Format
  • DigitaMeia Log Format
  • Amazon CloudFront (with date and time)
  • Amazon CloudFront (with date)
  • IIS Log Format
  • Custom Log format
  • JSON Log format

For more information about log formats, see log formats.

STORAGE

GoAccess has the ability to store the data and restore it later. This can be useful for processing large log files that might take a long time to parse. It can also be used for incremental log processing.

It uses the --persist and --restore options to manage the storage.

CONFIGURATION

GoAccess can be configured using a configuration file. The default location is ~/.goaccessrc. You can also specify a different configuration file using the -c option.

The configuration file allows you to set various options, such as log file format, date format, and ignored fields.

For more information about the configuration file, see configuration.

CUSTOM LOG/DATE FORMAT

If your log format is not among the predefined ones, you can define your own using the --log-format option. For example:

# goaccess access.log --log-format="%h %u %geo.country %d:%t %r %s %&lt;%{Referer}i> %U"

The date and time format can also be customized using --datetime-format. For example, for Apache logs:

# goaccess access.log --log-format="%h %l %u %t %r %s %b %{Referer}i %{User-agent}i" --datetime-format="%d/%b/%Y:%H:%M:%S %z"

For more details on log and date format specifiers, refer to the GoAccess Log Formats documentation.

INTERACTIVE MENU

GoAccess offers an interactive menu to configure various settings. You can access it by running GoAccess without any arguments:

# goaccess

This will open a text-based user interface where you can select your log file format, date format, and other options.

EXAMPLES

REAL-TIME HTML REPORT

To generate a real-time HTML report with the WebSocket server listening on port 9870:

# goaccess access.log -o report.html --real-time-html --port=9870

And to bind the WebSocket server to a different address other than 0.0.0.0, you can specify it as:

# goaccess access.log -o report.html --real-time-html --addr=127.0.0.1

Note: To output real time data over a TLS/SSL connection, you need to use --ssl-cert=<cert.crt> and --ssl-key=<priv.key>.

WORKING WITH DATES

Another useful pipe would be filtering dates out of the web log

The following will get all HTTP requests starting on 05/Dec/2010 until the end of the file.

# sed -n '/05Dec2010/,$ p' access.log | goaccess -a -

or using relative dates such as yesterdays or tomorrows day:

# sed -n '/'$(date '+%d%b%Y' -d '1 week ago')'/,$ p' access.log | goaccess -a -

If we want to parse only a certain time-frame from DATE a to DATE b, we can do:

# sed -n '/5Nov2010/,/5Dec2010/ p' access.log | goaccess -a -

If we want to preserve only certain amount of data and recycle storage, we can keep only a certain number of days. For instance to keep & show the last 5 days:

# goaccess access.log --keep-last=5

VIRTUAL HOSTS

Assuming your log contains the virtual host (server blocks) field. For instance:

vhost.com:80 10.131.40.139 - - [02/Mar/2016:08:14:04 -0600] "GET /shop/bag-p-20 HTTP/1.1" 200 6715 "-" "Apache (internal dummy connection)"

And you would like to append the virtual host to the request in order to see which virtual host the top urls belong to

awk '$8=$1$8' access.log | goaccess -a -

To exclude a list of virtual hosts you can do the following:

# grep -v "`cat exclude_vhost_list_file`" vhost_access.log | goaccess -

FILES & STATUS CODES

To parse specific pages, e.g., page views, html, htm, php, etc. within a request:

# awk '$7~/.html|.htm|.php/' access.log | goaccess -

Note, $7 is the request field for the common and combined log format, (without Virtual Host), if your log includes Virtual Host, then you probably want to use $8 instead. It's best to check which field you are shooting for, e.g.:

# tail -10 access.log | awk '{print $8}'

Or to parse a specific status code, e.g., 500 (Internal Server Error):

# awk '$9~/500/' access.log | goaccess -

SERVER

Also, it is worth pointing out that if we want to run GoAccess at lower priority, we can run it as:

# nice -n 19 goaccess -f access.log -a

and if you don't want to install it on your server, you can still run it from your local machine:

# ssh -n root@server 'tail -f /var/log/apache2/access.log' | goaccess -

Note: SSH requires -n so GoAccess can read from stdin. Also, make sure to use SSH keys for authentication as it won't work if a passphrase is required.

INCREMENTAL LOG PROCESSING

GoAccess has the ability to process logs incrementally through its internal storage and dump its data to disk. It works in the following way:

1
A dataset must be persisted first with --persist, then the same dataset can be loaded with
2
--restore. If new data is passed (piped or through a log file), it will append it to the original dataset.

NOTES

GoAccess keeps track of inodes of all the files processed (assuming files will stay on the same partition), in addition, it extracts a snippet of data from the log along with the last line parsed of each file and the timestamp of the last line parsed. e.g., inode:29627417|line:20012|ts:20171231235059

First it compares if the snippet matches the log being parsed, if it does, it assumes the log hasn't changed dramatically, e.g., hasn't been truncated. If the inode does not match the current file, it parses all lines. If the current file matches the inode, it then reads the remaining lines and updates the count of lines parsed and the timestamp. As an extra precaution, it won't parse log lines with a timestamp ≤ than the one stored.

Piped data works based off the timestamp of the last line read. For instance, it will parse and discard all incoming entries until it finds a timestamp >= than the one stored.

For instance:

// last month access log
# goaccess access.log.1 --persist

then, load it with

// append this month access log, and preserve new data
# goaccess access.log --restore --persist

To read persisted data only (without parsing new data)

# goaccess --restore

NOTES

Each active panel has a total of 366 items or 50 in the real-time HTML report. The number of items is customizable using max-items Note that HTML, CSV and JSON output allow a maximum number greater than the default value of 366 items per panel.

A hit is a request (line in the access log), e.g., 10 requests = 10 hits. HTTP requests with the same IP, date, and user agent are considered a unique visit.

If you want to enable dual-stack support, please use --addr=:: instead of the default --addr=0.0.0.0.

The generated report will attempt to reconnect to the WebSocket server after 1 second with exponential backoff. It will attempt to connect 20 times.
