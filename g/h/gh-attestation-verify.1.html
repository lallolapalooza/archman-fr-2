GH-ATTESTATION-VERIFY(1) Manuel de l'interface de ligne de commande GitHub GH-ATTESTATION-VERIFY(1)

NOM

gh-attestation-verify - Vérifier l'intégrité d'un artefact à l'aide d'attestations

SYNOPIS

gh attestation verify [<chemin-fichier> | oci://<uri-image>] [--owner | --repo] [indicateurs]

DESCRIPTION

Vérifie l'intégrité et la provenance d'un artefact à l'aide de ses attestations signées cryptographiquement associées.

Comprendre la Vérification

Une attestation est une déclaration (c'est-à-dire une déclaration de provenance) faite par un acteur (c'est-à-dire un workflow GitHub Actions) concernant un sujet (c'est-à-dire un artefact).

Afin de vérifier une attestation, vous devez fournir un artefact et valider : * l'identité de l'acteur qui a produit l'attestation * le type de prédicat d'attestation attendu (la nature de la déclaration)

Par défaut, cette commande applique le type de prédicat https://slsa.dev/provenance/v1. Pour vérifier d'autres types de prédicats d'attestation, utilisez l'indicateur --predicate-type.

L'"identité de l'acteur" se compose de : * le dépôt ou le propriétaire du dépôt auquel l'artefact est lié * le workflow Actions qui a produit l'attestation (également appelé workflow
signataire)

Cette identité est ensuite validée par rapport aux champs SourceRepository, SourceRepositoryOwner et SubjectAlternativeName (SAN) du certificat de l'attestation, entre autres.

Il vous appartient de décider avec quelle précision vous souhaitez appliquer cette identité.

Au minimum, cette commande nécessite l'un ou l'autre des indicateurs suivants : * l'indicateur --owner (par ex. --owner github), ou * l'indicateur --repo (par ex. --repo github/example)

Plus vous spécifiez l'identité avec précision, plus vous aurez de contrôle sur les garanties de sécurité offertes par le processus de vérification.

Idéalement, le chemin du workflow signataire est également validé à l'aide des indicateurs --signer-workflow ou --cert-identity.

Veuillez noter : si votre attestation a été générée via un workflow réutilisable, c'est ce workflow réutilisable qui est le signataire dont l'identité doit être validée. Dans ce cas, vous devez utiliser soit l'indicateur --signer-workflow, soit l'indicateur --signer-repo.

Pour plus d'options, consultez les autres indicateurs disponibles.

Chargement des Artefacts et des Attestations

Pour spécifier l'artefact, cette commande nécessite : * un chemin d'accès au fichier d'un artefact, ou * une URI d'image conteneur (par ex. oci://<uri-image>)
* (notez que si vous fournissez une URL OCI, vous devez déjà être authentifié auprès de son registre de conteneurs)

Par défaut, cette commande tentera de récupérer les attestations pertinentes via l'API GitHub en utilisant les valeurs fournies à --owner ou --repo.

Pour récupérer plutôt les attestations depuis le registre OCI de votre artefact, utilisez l'indicateur --bundle-from-oci.

Pour une vérification hors ligne à l'aide d'attestations stockées sur disque (cf. la commande download), fournissez un chemin à l'indicateur --bundle.

Application de Politiques Supplémentaires

Avec l'indicateur --format=json, en cas de vérification réussie, cette commande produira un tableau JSON contenant une entrée par attestation vérifiée.

Cette sortie peut ensuite être utilisée pour une application de politiques supplémentaire, c'est-à-dire en la redirigeant vers un moteur de politiques.

Chaque objet du tableau contient deux propriétés : * un objet attestation, qui contient le paquet qui a été vérifié * un objet verificationResult, qui est une représentation analysée du contenu
du paquet qui a été vérifié.

Dans l'objet verificationResult, vous trouverez : * signature.certificate, qui est une représentation analysée du certificat X.509 intégré dans l'attestation, * verifiedTimestamps, un tableau d'objets indiquant quand l'attestation
a été constatée par un journal de transparence ou une autorité de timestamping * statement, qui contient le tableau subject référençant les artefacts,
le champ predicateType, et l'objet predicate qui contient des métadonnées supplémentaires, souvent contrôlables par l'utilisateur

IMPORTANT : veuillez noter que seules les propriétés signature.certificate et verifiedTimestamps contiennent des valeurs qui ne peuvent pas être manipulées par le workflow qui a initialement généré l'attestation.

Lors de l'utilisation d'attestations créées dans GitHub Actions, le contenu de signature.certificate est directement extrait du jeton OpenID Connect généré par GitHub. Le contenu du tableau verifiedTimestamps provient des timestamps signés issus soit d'un journal de transparence, soit d'une autorité de timestamping – et ne peuvent pas non plus être falsifiés par les utilisateurs.

Lors de la conception d'une application de politiques utilisant cette sortie, une attention particulière doit être accordée à l'examen du contenu de la propriété statement.predicate : si un attaquant accédait au contexte d'exécution de votre workflow, il pourrait alors falsifier le contenu de statement.predicate.

Pour atténuer ce vecteur d'attaque, envisagez d'utiliser un "builder de confiance" : lors de la génération d'un artefact, faites en sorte que la construction et la signature de l'attestation se produisent dans un workflow réutilisable dont l'exécution ne peut pas être influencée par les entrées fournies par le workflow appelant.

Voir ci-dessus concernant --signer-workflow.

OPTIONS

-b, --bundle <chaîne>
Chemin d'accès au paquet sur disque, soit un seul paquet dans un fichier JSON, soit un fichier de lignes JSON avec plusieurs paquets
--bundle-from-oci
Lors de la vérification d'une image OCI, récupère le paquet d'attestation depuis le registre OCI au lieu de GitHub
--cert-identity <chaîne>
Force la correspondance exacte du SubjectAlternativeName du certificat avec la valeur fournie
-i, --cert-identity-regex <chaîne>
Force la correspondance de l'expression régulière fournie avec le SubjectAlternativeName du certificat
--cert-oidc-issuer <chaîne> (par défaut "https://token.actions.githubusercontent.com")
Force la correspondance de l'émetteur du jeton OIDC avec la valeur fournie
--custom-trusted-root <chaîne>
Chemin d'accès à un fichier trusted_root.jsonl ; probablement pour une vérification hors ligne
--deny-self-hosted-runners
Échoue à la vérification pour les attestations générées sur des runners auto-hébergés
-d, --digest-alg <chaîne> (par défaut "sha256")
L'algorithme utilisé pour calculer un digest de l'artefact : {sha256|sha512}
--format <chaîne>
Format de sortie : {json}
--hostname <chaîne>
Configure l'hôte à utiliser
-q, --jq <expression>
Filtre la sortie JSON à l'aide d'une expression jq
-L, --limit <entier> (par défaut 30)
Nombre maximum d'attestations à récupérer
--no-public-good
Ne pas vérifier les attestations signées avec l'instance Sigstore public good
-o, --owner <chaîne>
Organisation GitHub pour restreindre la recherche d'attestations
--predicate-type <chaîne> (par défaut "https://slsa.dev/provenance/v1")
Force la correspondance du type de prédicat des attestations vérifiées avec la valeur fournie
-r, --repo <chaîne>
Dépôt GitHub pour restreindre la recherche d'attestations
--repo-owner <chaîne>
Propriétaire du dépôt GitHub pour restreindre la recherche d'attestations
--sigstore-identity <string>
Force la correspondance de l'identité du signataire Sigstore avec la valeur fournie
--sigstore-identity-regex <string>
Force la correspondance de l'expression régulière fournie avec l'identité du signataire Sigstore
--signer-workflow <string>
Chemin d'accès du workflow GitHub Actions qui a produit l'attestation. Par exemple, .github/workflows/release.yml@refs/tags/v1.0.0
--signer-repo <string>
Dépôt GitHub où le workflow signataire est hébergé. Par exemple, owner/repo
-t, --token <string>
Authentification à utiliser pour l'API GitHub
--verbose-timestamps
Inclure les timestamps vérifiés dans la sortie JSON
-h, --help
Aide pour gh attestation verify
-p, --prompt
Se connecter et authentifier en utilisant le navigateur

EXEMPLE

# Vérifier un artefact téléchargé sur le dépôt github/docs
gh attestation verify ./my-binary --repo github/docs --owner github

# Vérifier une image OCI dans le registre GitHub
gh attestation verify oci://ghcr.io/owner/image:latest --repo owner/repo

# Vérifier en utilisant un chemin de workflow spécifique et un dépôt de signature
gh attestation verify ./my-binary --repo github/docs --signer-workflow .github/workflows/build.yml --signer-repo github/actions

# Vérifier et sortir au format JSON pour une analyse ultérieure
gh attestation verify ./my-binary --repo github/docs --format json | jq .

EXEMPLE

# Vérifier un artefact lié à un dépôt
$ gh attestation verify example.bin --repo github/example
# Vérifier un artefact lié à une organisation
$ gh attestation verify example.bin --owner github
# Vérifier un artefact et afficher le résultat complet de la vérification
$ gh attestation verify example.bin --owner github --format json
# Vérifier une image OCI à l'aide d'attestations stockées sur disque
$ gh attestation verify oci://<uri-image> --owner github --bundle sha256:foo.jsonl
# Vérifier un artefact signé avec un workflow réutilisable
$ gh attestation verify example.bin --owner github --signer-repo actions/example
