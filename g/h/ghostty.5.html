Pour configurer Ghostty, vous devez utiliser un fichier de configuration. La configuration via une interface graphique est prévue mais n'est pas encore prise en charge. Le fichier de configuration doit être placé dans $XDG_CONFIG_HOME/ghostty/config, qui correspond par défaut à ~/.config/ghostty/config si l'environnement XDG n'est pas

défini.

Si vous utilisez macOS, le fichier de configuration peut aussi être placé dans $HOME/Library/Application Support/com.mitchellh.ghostty/config. C'est l'emplacement de configuration par défaut pour macOS. Il sera recherché avant tous les emplacements d'environnement XDG listés

ci-dessus.

Vous pouvez consulter toutes les options de configuration disponibles et leur documentation en exécutant la commande ghostty +show-config --default --docs. Notez que cela produira la configuration par défaut complète avec la documentation sur la sortie standard, vous voudrez donc peut-être la rediriger vers un visualiseur de pages, un éditeur,

etc.

Remarque : vous verrez beaucoup de configurations vides étranges comme font-family =. C'est une syntaxe valide pour spécifier le comportement par défaut (aucune valeur). Le +show-config l'affiche pour qu'il soit clair que la clé utilise sa valeur par défaut et aussi pour avoir quelque chose auquel attacher le commentaire de

documentation.

Vous pouvez également consulter et lire toutes les options de configuration disponibles dans la structure Config du code source. Les clés disponibles sont exactement les clés de configuration, et leurs valeurs possibles sont généralement documentées dans les commentaires. Vous pouvez aussi rechercher les fichiers de configuration publics de nombreux utilisateurs de Ghostty pour trouver des exemples et de

l'inspiration.

Erreurs de

configuration

Si votre fichier de configuration contient des erreurs, Ghostty fait de son mieux pour les ignorer et continuer. Les erreurs de configuration apparaissent actuellement dans le journal. Le journal est écrit directement sur stderr, il vous appartient donc de trouver comment y accéder sur votre système (pour l'instant). Sur macOS, vous pouvez également utiliser l'utilitaire en ligne de commande système log avec log stream --level debug --predicate

'subsystem=="com.
mitchellh.ghostty"'.

Débogage de la

configuration

Vous pouvez vérifier que la configuration est correctement chargée en consultant la sortie de débogage de Ghostty. La documentation sur la façon de consulter la sortie de débogage se trouve dans la section « building Ghostty » à la fin du

README.

Dans la sortie de débogage, vous devriez voir dans les 20 premières lignes environ des messages concernant le chargement (ou le non-chargement) d'un fichier de configuration, ainsi que toutes les erreurs qu'il a pu rencontrer. Les erreurs de configuration sont également affichées dans une fenêtre dédiée, à la fois sur macOS et sur Linux (GTK). Ghostty ne considère pas les erreurs de configuration comme fatales et utilisera les valeurs par défaut pour les clés

erronées.

input
Données à envoyer en entrée à la commande au démarrage.

La command configurée sera lancée en utilisant les règles habituelles, puis les données spécifiées comme cette entrée seront écrites dans le pty avant que toute autre entrée ne puisse être fournie.

Les octets sont envoyés tels quels, sans encodage supplémentaire. Par conséquent, soyez prudent avec les entrées qui peuvent contenir des caractères de contrôle, car cela pourrait être utilisé pour exécuter des programmes dans un shell.

Le format de cette valeur est :

•
raw:<chaîne> - Envoie du texte brut tel quel. Utilise la syntaxe des littéraux de chaîne Zig, vous pouvez donc spécifier des caractères de contrôle et d'autres échappements standards.
•
path:<chemin> - Lit un chemin de fichier et envoie le contenu. Le chemin doit pointer vers un fichier de longueur finie. Par exemple, n'utilisez pas un périphérique tel que /dev/stdin ou /dev/urandom, car cela bloquerait le démarrage du terminal indéfiniment. Les fichiers sont limités à 10 Mo pour éviter une utilisation excessive de la mémoire. Si vous avez des fichiers plus volumineux, vous devriez écrire un script pour lire le fichier et l'envoyer au terminal.

Si aucun préfixe valide n'est trouvé, il est supposé être une entrée raw:. C'est un choix ergonomique pour vous permettre de simplement écrire input = "Hello, world!" (un cas courant) sans avoir à préfixer chaque valeur avec raw:.

Cela peut être répété plusieurs fois pour envoyer plus de données. Les données sont concaténées directement sans aucun caractère séparateur entre elles (par exemple, pas de nouvelle ligne).

Si l'une des sources d'entrée n'existe pas, aucune entrée ne sera envoyée. Les sources d'entrée ne sont vérifiées qu'au démarrage du terminal, donc les chemins manquants n'apparaîtront pas dans la validation de la configuration.

Changer cette configuration au moment de l'exécution n'affectera que les nouveaux terminaux.

keybind
Liaisons de touches. Le format est trigger=action. Les déclencheurs en double écraseront les valeurs définies précédemment. La liste des actions est disponible dans la documentation ou à l'aide de la commande ghostty
+list-
actions.

Déclencheur : liste de touches et de modificateurs séparés par +. Exemple : ctrl+a, ctrl+shift+b, up

.

Si la touche est un unique codepoint Unicode, le déclencheur correspondra à toutes les pressions qui produisent ce codepoint. Ceux-ci sont affectés par les dispositions de clavier. Par exemple, a correspondra à la touche a d'un clavier QWERTY, mais correspondra à la touche q d'un clavier AZERTY (en supposant une disposition physique US)

.

Pour les codepoints Unicode, la correspondance se fait en comparant l'ensemble des modificateurs avec le codepoint non modifié. Le codepoint non modifié est parfois appelé « caractère non shifté » dans d'autres logiciels, mais tous les modificateurs sont considérés, pas seulement shift. Par exemple, ctrl+a correspondra à a mais pas à ctrl+shift+a (qui est A sur un clavier US)

.

De plus, la correspondance des codepoints ne distingue pas la casse et le codepoint non modifié est toujours plié en casse pour la comparaison. Par conséquent, ctrl+A configuré correspondra lorsque ctrl+a est pressé. Notez que cela signifie que certaines combinaisons de touches sont impossibles selon la disposition du clavier. Par exemple, ctrl+_ est impossible sur un clavier US car _ est shift+- et ctrl+shift+- n'est pas égal à ctrl+_ (car les modificateurs ne correspondent pas !). Plus de détails sur les combinaisons de touches impossibles peuvent être trouvés dans cette excellente source écrite par les développeurs de Qt : https://doc.qt.io/qt-6/qkeysequence.html#keyboard-layout-issue

s

Les codes de touches physiques peuvent être spécifiés en utilisant n'importe lequel des codes de touches tels que spécifiés par la spécification W3C. Par exemple, KeyA correspondra à la touche physique a d'un clavier US standard quelle que soit la disposition du clavier. Ceux-ci sont sensibles à la

casse.

Pour des raisons esthétiques, les codes w3c prennent également en charge le snake case. Par exemple, key_a est équivalent à KeyA. Les seules exceptions sont les touches de fonction, par ex.F1 est f1 (sans souligné). C'est une conséquence du fait que notre code interne utilise le snake case mais est intentionnellement pris en charge et testé, il est donc sûr de l'utiliser. Cela permet une liaison entièrement en minuscules ce que je trouve plus esthétiquement

plaisantes.

Les touches de fonction telles que insert, up, f5, etc. sont également spécifiées en utilisant les touches telles que définies par la spécification W3C liée

précédemment.

Les touches physiques ont toujours une priorité plus élevée que les codepoints Unicode, donc si vous spécifiez à la fois a et KeyA, la touche physique sera toujours utilisée, quel que soit l'ordre dans lequel elles sont

configurées.

Les modificateurs valides sont shift, ctrl (alias : control), alt (alias : opt, option), et super (alias : cmd, command). Vous pouvez utiliser le modificateur ou l'alias. Lors du débogage des raccourcis clavier, le modificateur non aliasé sera toujours utilisé dans la

sortie.

Remarque : La touche fn ou « globe » sur les claviers n'est pas prise en charge en tant que modificateur. C'est une limitation des systèmes d'exploitation et des boîtes à outils GUI utilisés par

Ghostty.

macos-titlebar-style
Le style de la barre de titre macOS. Les valeurs disponibles sont : “native”, “transparent”, “tabs” et “hidden”.

Le style “native” utilise la barre de titre native de macOS sans aucune personnalisation. La barre de titre correspondra à votre thème de fenêtre (voir window-theme).

Le style “transparent” est identique à “native”, mais la barre de titre sera transparente et laissera apparaître la couleur de fond de votre fenêtre. Cela crée une apparence de fenêtre plus fluide, mais ressemble un peu moins à une application macOS typique et peut ne pas bien fonctionner avec tous les thèmes.

Le style “transparent” se mettra également à jour en temps réel pour les changements dynamiques de la couleur de fond de la fenêtre, par exemple via OSC 11. Pour rendre cela plus esthétique, cela ne se produit que si le terminal est une fenêtre, un onglet ou une division qui borde le haut de la fenêtre. Cela évite une apparence inégale où la couleur de la barre de titre change mais que tous les terminaux du haut ne correspondent pas.

Le style “tabs” est une barre de titre entièrement personnalisée qui intègre la barre d'onglets dans la barre de titre. Cette barre de titre correspond toujours à la couleur de fond du terminal. Il existe quelques limitations à ce style : Sur macOS 13 et versions inférieures, l'état enregistré de la fenêtre ne restaurera pas correctement les onglets. macOS 14 n'a pas ce problème et toute autre version de macOS n'a pas été testée.

Le style “hidden” masque la barre de titre. Contrairement à window-decoration = false, cependant, il ne supprime pas le cadre de la fenêtre et ne lui donne pas de coins carrés. La modification vers ou depuis cette option à l'exécution peut affecter les fenêtres existantes de manière erratique.

Lorsque “hidden”, la zone supérieure de la barre de titre ne peut plus être utilisée pour déplacer la fenêtre. Pour déplacer la fenêtre, vous pouvez utiliser Option+clic sur les zones redimensionnables du cadre pour déplacer la fenêtre. Il s'agit d'un comportement standard de macOS et non de quelque chose que Ghostty active.

La valeur par défaut est “transparent”. C'est un choix subjectif, mais je pense que c'est le plus esthétique et que cela fonctionne dans la plupart des cas.

La modification de cette option à l'exécution ne s'applique qu'aux nouvelles fenêtres.

•
Standard U.S.
•
International U.S.
