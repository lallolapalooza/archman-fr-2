DESCRIPTIO

N

Le programme gtlssh-keygen est utilisé pour faciliter la gestion des clés pour

gtlssh.

Généralement, lorsque vous commencez à utiliser gtlssh sur un système, vous

exécuteriez


gtlssh-keygen

keygen

et il créerait les clés pour vous. Vous devriez faire de même sur tout système cible auquel vous souhaitez vous connecter avec gtlssh. Copiez ensuite le fichier default.crt de votre répertoire $HOME/.gtlssh vers le répertoire $HOME/.gtlssh/allowed_certs de la cible. Exécutez

ensuite


gtlssh

rehash

sur le système cible pour générer les hachages. Après cela, vous devriez pouvoir vous connecter sans mot de

passe.

Lorsque vous devez régénérer vos clés, vous

exécutez


gtlssh-keygen

keygen

à nouveau. Il vous demandera si vous souhaitez les remplacer. Si vous remplacez les clés, les anciennes clés seront sauvegardées avec un « .1 » ajouté au nom du fichier. Une fois les clés remplacées, vous devez pousser les nouvelles clés vers tous vos systèmes cibles. Vous pouvez

exécuter


gtlssh-keygen pushcert cible1 [cible2 [....]

]

pour mettre à jour les clés sur toutes ces cibles. Il utilis

era les anciennes identifiants (avec le « .1 » ajouté)
pour ce faire, donc cela devrait fonctionner facilement.

DIFFÉRENCES PAR RAPPORT À

SSH

Contrairement à ssh, les clés ssl ont une durée de validité. Par défaut, gtlssh crée des clés avec une durée de vie d'un an, bien que vous puissiez modifier cela. Bien que ce soit un peu ennuyeux, c'est une bonne idée de remplacer vos clés périodiquement, vous pouvez donc considérer cela comme un

avantage.

gtlssh vous permet de créer des clés pour des cibles spécifiques et de les utiliser automatiquement. Supposons, par exemple, que vous souhaitiez utiliser une clé différente pour vous connecter à la cible abc.my.domain. Vous feriez

:


gtlssh-keygen keygen abc.my.

domain

et il créerait une clé et un certificat dans le répertoire .gtlssh/keycerts avec les noms abc.my.domain.crt et abc.my.domain.key. Vous devriez copier ce certificat (et non default.crt) vers votre cible distante. gtlssh verrait que ces clés sont présentes et les utiliserait automatiquement lorsque vous vous connecteriez à abc.my.domain. La commande pushcert comprend cela aussi, et gérera le push des clés appropriées lorsque vous poussez vers abc.my.

domain.

Vous pouvez également ajouter des ports à la génération de clés, et

il ne les utilisera que si vous vous connectez à la cible spéci
fique sur le port spécifique. Cela peut être utile pour ser2net.

HACKS

WINDOWS

gtlsshd fonctionnera sur Windows, et cela fonctionnera plus ou moins sans mot de passe, mais certaines choses ne fonctionneront pas car la connexion n'a pas d'identifiants stockés, et il est incapable de créer un jeton lié pour les connexions d'administration vous ne pouvez donc pas faire de choses d'administration

.

Pour contourner ce problème et permettre toujours les connexions par certificat, vous pouvez utiliser la commande storepw de gt

lssh-keygen pour stocker votre mot de passe dans votre répertoire .gtlssh. Ce n'est pas idéal, mais vos clés privées y sont dé
jà, donc ce n'est pas très grave. Les administrateurs de votre système pourront voir votre mot de passe, soyez donc averti.

COMMAND

Les commandes sont

:
keygen [-p <port>]
[nomhôte]
Configuration du répertoire de base (s'il n'est pas déjà configuré) et création des clés. Si rien n'est spécifié, crée la clé par défaut dans <basedir>/default.key et <basedir>/default.crt. Sinon, crée les clés sous la forme <keydir>/<hôte>[,<port>].key et <keydir>/<hôte>[,<port>].
crt.
set
up
Comme keygen, mais ne prend aucune option et ne crée que le certificat par
défaut.
rehash [répertoire [répertoire [...
]]]
La bibliothèque openssl utilisée par gtlssh exige que les certificats dans une bibliothèque soient hachés pour qu'elle puisse les trouver. Cette commande refait les hachages dans les répertoires indiqués. Si aucun répertoire n'est spécifié, elle refait les hachages de <basedir>/allowed_certs et <basedir>/server_certs.

Notez que si vous ajoutez des clés à ces répertoires, vous devez les rehacher sinon elles ne fonctionneront

pas.

rehash supprimera automatiquement tous

les certificats
qui ont expiré.
addallow [-i] <nomhôte>
<fichier>
Ajoute le fichier indiqué comme certificat public autorisé pour le nom d'hôte indiqué. Il installera ce fichier dans le répertoire <basedir>/allowed_certs avec le nom « hôte.crt ». Il rehachera également le répertoire. Si -i est spécifié, l'entrée provient de l'entrée standard et le fichier n'est ni requis ni utilisé. Si le fichier de destination existe déjà, il sera renommé « hôte.crt.1.crt
».
pushcert [-n <nom> ] [-p <port>] <nomhôte> [[-p <port>] <nomhôte> [..
.]]
Place le certificat local pour l'hôte indiqué sur l'hôte distant afin qu'il puisse être utilisé pour la connexion. Il utilise les anciens identifiants (identifiants avec .1 ajouté au nom, selon keygen) s'ils sont présents. C'est utile si vous avez mis à jour votre certificat et devez en envoyer un nouveau à certains hôtes distants. Il trouve le nom du certificat comme décrit dans la commande keygen. Si d'anciens identifiants existent, il les utilisera pour se connecter avec gtlssh et envoyer le certificat. Sinon, il utilisera les identifiants par défaut et espérera le meilleur, probablement utile seulement si les mots de passe sont acceptés. Cela ne fonctionne que pour un retour en arrière de keygen ; si vous avez exécuté la commande keygen deux fois pour l'hôte, vous devrez transférer le certificat manuellement. Par défaut, l'identifiant sur l'hôte distant est nommé selon la sortie de 'hostname -f' sur la machine locale, -n remplace
cela.
store
pw
Windows uniquement, voir « HACKS WINDOWS » ci-dessus pour plus de détails. Demande votre mot de passe à stocker dans votre répertoire .
gtlssh.
serverk
ey
Crée des clés pour le serveur, généralement dans /etc/gtlssh/gtlsshd.key et /etc/gtlssh/gtlsshd.crt. Vous devez généralement être root pour faire cela. Utilisé pour la configuration initiale de gtlsshd.

Si vous spécifiez un nom de clé, le nom commun utilisé pour la clé sera "<keyname>.<hostname>" par défaut, sauf si vous le définissez avec --commonname. Si vous ne spécifiez pas de nom de clé (par défaut gtlsshd), le nom commun est simplement le nom d'hôte. Cela évite le problème suivant.

..

NOTE : Si vous exécutez plusieurs serveurs sur le même système, vous devez avoir un nom commun différent pour chacun. Certaines versions d'openssl examineront un autre certificat avec le même nom commun dans le cadre de la même chaîne de certificats et vous obtiendrez un

échec :


authority and subject key identifier

mismatch

Ainsi, si par exemple vous exécutez ser2net et gtlsshd sur le même système, ils doivent avoir des noms communs

différents.

Sur Windows, vous devez supprimer toutes les autorisations du fichier de clé sauf pour SYSTEM et Administrator. Si gtlssh ne s'exécute pas, c'est la première chose à vérifier. (Vous pouvez obtenir une console SYSTEM comme décrit ci-dessous et exécuter "gtlssh -d" et il vous donnera une erreur, cela est utile pour le débogage.) Le programme ne fait pas encore cela par défaut, malheureusement. Vous devrez configurer le fichier en tant que SYSTEM pour faire cela. La procédure

est :

Exécutez une console

administrateur.

Exécutez "psexec -sid cmd" pour exécuter une console en tant que

SYSTEM.

Exécutez

"explorer".

Allez dans le fichier de clé dans

l'explorateur, faites un clic dr
oit dessus, et choisissez
Propriétés, puis Sécurité, puis v
ous pouvez le modifier depuis là.
