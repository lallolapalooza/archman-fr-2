DESCRIPTIO

N

Cette structure fournit une abstraction pour la bibliothèque gensio qui lui permet de fonctionner avec diverses bibliothèques d'événements. Elle fournit les fonctions de base suivantes

:
allocation de mémoire - Allouer et libérer de la
mémoire.
mutex - Fournir une exclusion
mutuelle.
rappels de gestionnaires de fichiers - Permet de surveiller les descripteurs de
fichiers
et de signaler lorsque des E/S sont prêtes sur
ceux-ci.
minuteurs - Appeler des rappels après l'écoulement d'un certain
temps.
exécuteurs - Exécuter une fonction dans un nouveau contexte d'exécution. Appeler des
rappels
directement à partir de fonctions utilisateur peut entraîner des blocages, cela fournit un moyen d'appeler des rappels depuis un contexte
séparé.
attente - Attendre que des opérations se produisent tout en exécutant les minuteurs, les
exécuteurs
et en surveillant les descripteurs de
fichiers.
journalisation - Permettre à la bibliothèque gensio de générer des journaux pour signaler des
problèmes.

Ce document décrit les fonctions publiques que les utilisateurs peuvent utiliser. Un gestionnaire OS a de nombreuses autres fonctions destinées à être utilisées par les gensios, celles-ci sont documentées dans le fichier d'inclusion des fonctions

OS.

Le problème de base est qu'il existe diverses bibliothèques de gestion d'événements (Tcl/Tk, glib, Xlib, personnalisées, etc.) et vous voudrez peut-être intégrer la bibliothèque gensio avec l'une d'entre elles. Même si c'est un peu pénible de devoir en passer une de celles-ci autour, cela ajoute la flexibilité

nécessaire.

gensio_default_os_hnd (Obsolète) fournit un moyen d'obtenir le gestionnaire de fonctions OS par défaut pour la plateforme. La même valeur sera retournée à chaque fois, un seul est créé. Vous devriez généralement utiliser celui-ci sauf si vous avez un besoin spécial comme documenté ci-dessus. Son utilisation est maintenant découragée en général. Avoir deux parties indépendantes d'un système partager des fonctions OS sans le savoir est susceptible de mener à des problèmes. Si un programme sait qu'il est la seule chose à l'utiliser, alors c'est acceptable pour l'instant, mais cela sera obsolète à un certain

moment.

gensio_alloc_os_funcs alloue un nouveau gestionnaire de fonctions OS pour la plateforme, pour Unix ou Windows. Plusieurs gestionnaires OS peuvent être utilisés pour gérer différentes E/S à différentes priorités. Lorsque vous créez un gensio, tous les rappels d'E/S seront gérés par le gestionnaire OS utilisé pour le créer. Ainsi, vous pouvez exécuter différents gestionnaires OS dans des fils d'exécution de différentes priorités pour exécuter différents gensios à différentes priorités. Sinon, il n'y a pas beaucoup de raison d'en avoir plus

d'un.

Le paramètre wake_sig n'est pas utilisé sur Windows. Pour les systèmes Unix, ce signal est utilisé pour signaler à d'autres processus qui peuvent être en attente qu'ils doivent se réveiller. Cela sert à réveiller un processus en attente sur un attente, et sert à signaler à tous les processus en attente si un minuteur est ajouté qui est antérieur à tout autre minuteur, afin qu'ils puissent ajuster leurs

attentes.

Si vous exécutez votre programme dans un seul thread, vous pouvez passer zéro en toute sécurité dans ce paramètre. Si vous passez autre chose que zéro, cela configurera ce signal en le retirant du sigmask et en installant un gestionnaire pour

celui-ci.

Si votre application est multi-thread (ou, plus précisément, si votre application a plusieurs threads qui font des appels à gensio), vous devez passer un signal valide dans celui-ci, et vous devez configurer un gestionnaire vide pour ce signal, et le signal doit être bloqué dans tous les threads qui appellent une fonction d'attente. Vous ne devriez pas utiliser ce signal pour autre chose. La fonction qui alloue un gestionnaire de signal bloquera le signal dans le thread appelant, et ce sigmask est transmis aux autres threads qu'elle crée. Mais si vous avez alloué des threads avant d'allouer les os funcs, vous devez vous assurer que ces autres threads ont ce signal

bloqué.

Vous pouvez passer GENSIO_OS_FUNCS_DEFAULT_THREAD_SIGNAL pour prendre le gestionnaire de signal par défaut, qui est

SIGUSR1.

Sur unix, la fonction gensio_os_proc_setup gère toute la configuration de signal mentionnée ci-dessus pour vous (blocage des signaux, configuration du gestionnaire de signal), pour le signal de réveil comme ci-dessus et aussi pour quelques autres signaux comme SIGTERM, SIGCHILD, SIGPIPE, et d'autres. Vous devriez généralement l'utiliser à moins que vous n'ayez des besoins particuliers. Elle effectue également la configuration nécessaire sur

Windows.

De plus, si vous passez une valeur différente à gensio_default_os_hnd par rapport à la première que vous avez passée, elle retournera GE_INVAL. Vous pouvez passer des valeurs différentes aux appels gensio_unix_funcs_alloc, et elle les utilisera, mais il n'y a pas beaucoup d'intérêt à cela. Les os funcs pour Unix peuvent partager un gestionnaire de signal. Et il n'y a pas beaucoup d'intérêt à avoir plusieurs os funcs de toute

façon.

gensio_os_thread_setup est très similaire à gensio_os_proc_setup, mais elle ne configure que les gestionnaires de signal et le blocage des signaux pour le signal de réveil, elle ne fait pas les autres configurations. Elle vous permet d'intégrer un thread dans gensio qui n'a pas été créé par gensio. Elle effectue également certaines configurations nécessaires sur Windows pour le thread. Si vous n'avez pas de besoins de gestion de signal, vous pouvez généralement utiliser celle-ci à la place de gensio_os_proc_setup(). Si vous avez des besoins de gestion de signal, un thread devrait appeler gensio_os_proc_setup() et tous les autres threads devraient appeler cette fonction s'ils n'ont pas été créés par

gensio.

gensio_unix_funcs_alloc et gensio_win_funcs_alloc allouent les os funcs normales pour les systèmes basés sur Unix et Windows,

respectivement.

Le paramètre sel pour Unix vous permet de créer votre propre objet sélecteur et de le passer au gestionnaire OS. Passer NULL fera qu'il allouera son propre objet sélecteur. Voir le fichier include selector.h pour les

détails.

La valeur wake_sig est un signal utilisé par les fonctions OS pour la communication interne entre threads. Si vous exécutez une application multi-thread, vous devez fournir un signal valide que vous n'utilisez pas à d'autres fins, généralement SIGUSR1 ou SIGUSR2. Vous pouvez utiliser GENSIO_DEF_WAKE_SIG qui est zéro sur Windows et SIGUSR1 sur

Unix.

La fonction gensio_os_proc_setup effectue toute la configuration standard pour un processus. Vous devriez presque certainement utiliser cette fonction. Sur Windows, cela configure quelques éléments de base pour que l'enregistrement de terminaison fonctionne, mais sur Unix, cela fait toute la configuration de gestion des signaux, de sorte que vous n'ayez pas à faire toutes les choses mentionnées ci-dessus. Cela bloquera SIGPIPE (parce que ceux-ci arrivent quand les connexions meurent et la plupart des applications ne s'en soucient pas), SIGCHLD (ceux-ci arrivent pour les gensios stdio et pty), et le wake_sig si celui-ci est défini. Elle installe également des gestionnaires de signal pour SIGCHLD et le wake_sig (si défini) et configure un masque de

signal.

Pour Unix, c'est généralement ce que vous voulez, vous ne voulez pas que SIGPIPE fasse de mauvaises choses et avoir SIGCHLD réveiller une attente peut accélérer les choses un peu quand on attend des sous-programmes

.

Si vous utilisez la fonction OS gensio_os_funcs_wait_intr_sigmask, vous devez y passer la valeur proc_data retournée par gensio_os_proc_setup. Si vous voulez modifier le masque de signal d'attente, vous pouvez utiliser gensio_os_proc_unix_get_wait_sigset pour récupérer un pointeur vers celui-ci et le

modifier.

Notez que si vous appelez ceci plus d'une fois sans appeler gensio_os_proc_cleanup entre les deux, elle retournera GE_INUSE

.

La fonction gensio_os_proc_cleanup annule toutes les modifications que gensio_os_proc_setup fait, ainsi que la désinscription de tous les gestionnaires de signal effectués par les appels register. Sur Unix, elle restaure le masque de signal et les gestionnaires de signal qu'elle a définis à leurs valeurs précédentes. Sur Windows, elle supprime les gestionnaires

enregistrés.

La fonction gensio_os_new_thread démarre un nouveau thread à start_func en passant la valeur de données donnée. Elle retourne un thread_id que vous devez passer à la fonction d'attente. Ce sont juste des threads génériques de base, vous pouvez utiliser vos fonctions OS si vous avez besoin de plus de contrôle sur les threads. Si vous utilisez des threads, assurez-vous de voir les notes ci-dessus sur leur configuration correcte. Cela doit être appelé depuis un thread qui est déjà

configuré.

La fonction gensio_os_wait_thread attend qu'un thread s'arrête. Notez qu'elle ne cause pas l'arrêt du thread, elle attend qu'il s'arrête. Vous devez provoquer vous-même l'arrêt du

thread.

La fonction gensio_os_proc_register_term_handler passe un gestionnaire à appeler lorsqu'une terminaison (SIGINT, SIGQUIT, SIGTERM sur Unix, gestionnaire de contrôle de console ou WM_CLOSE sur Windows) est reçue par le processus. Définissez handler à NULL pour désactiver. Si vous faites cela sur Unix, les signaux seront bloqués sauf lors d'un appel d'attente ou de service. Appelez cela avant de démarrer tout autre thread pour qu'ils héritent du bon

sigmask.

La fonction gensio_os_proc_register_reload_handler définit la fonction à appeler lorsqu'un rechargement est demandé par le système d'exploitation (SIGHUP sur Unix). Définissez handler à NULL pour désactiver. Sur Unix, cela fera que SIGHUP sera bloqué sauf lors d'un appel d'attente ou de service. Appelez cela avant de démarrer tout autre thread pour qu'ils héritent du bon

sigmask.

La fonction gensio_os_proc_register_winsize_handler définit la fonction à appeler lorsqu'un changement de taille de fenêtre de console est demandé par le système d'exploitation (SIGWINCH sur Unix, à travers l'interface console sur Windows). Elle fournira les nouveaux paramètres de taille. Définissez handler et console_iod à NULL pour désactiver. Notez que le gestionnaire sera appelé avec les paramètres de taille de fenêtre actuels après que ceci soit appelé. Cela peut être appelé après que les threads aient démarré, le masque de signal SIGWINCH est configuré par défaut dans gensio_os_proc_setup sur les systèmes

*nix.

gensio_os_funcs_zalloc alloue un bloc de mémoire et le met à zéro. La bibliothèque gensio a son propre allocateur/désallocateur qui est utilisé dans les tests pour suivre si toutes les données allouées sont libérées lorsque les tests se terminent, et pour détecter les erreurs de débordement mémoire, de sous-dépassement et d'utilisation après libération. Retourne NULL si la mémoire ne peut pas être allouée. Utilisez gensio_os_funcs_zfree pour libérer la mémoire

allouée.

gensio_os_funcs_alloc_lock alloue un mutex qui peut être utilisé pour le verrouillage par l'utilisateur. Utilisez gensio_os_funcs_lock et gensio_os_funcs_unlock pour verrouiller/déverrouiller le mutex. Le gensio_os_funcs_free_lock s'assurera que le verrou n'est pas verrouillé et libérera les données associées au verrou. Notez que même pour les os funcs qui n'implémentent pas de verrous, cela implémentera un compteur pour s'assurer que tous les verrous sont

équilibrés.

gensio_os_funcs_get_monotonic_time retourne une valeur de temps de l'horloge monotone utilisée pour gensio_os_start_timer_abs. Elle peut également être utilisée comme une horloge monotone standard, mais ce n'est pas une horloge murale de quelque sorte que ce

soit.

gensio_os_funcs_set_vlog doit être appelé par l'utilisateur pour définir une fonction de gestion de journal pour les os funcs. Si quelque chose se passe mal en interne dans la bibliothèque gensio, cette fonction de journal sera appelée pour signaler le

problème.

Les minuteurs sont alloués avec gensio_os_funcs_alloc_timer. Quand le minuteur expire, les gestionnaires seront appelés avec les données cb_data données. Cela retournera NULL si le minuteur ne peut pas être alloué. Les minuteurs ne sont pas en cours d'exécution lorsqu'ils sont alloués, ils doivent être démarrés avec gensio_os_funcs_start_timer, ou gensio_os_funcs_start_timer_abs. Le premier démarre un minuteur relatif à l'heure actuelle. Le second démarre un minuteur basé sur une horloge monotone, voir gensio_os_funcs_get_monotonic_time pour les détails. Celles-ci retourneront GE_INUSE si le minuteur était déjà en cours d'exécution. Pour arrêter un minuteur, appelez soit gensio_os_funcs_stop_timer, soit gensio_os_funcs_stop_timer_with_done. Ces deux retournent GE_TIMEDOUT si le minuteur n'est pas en cours d'exécution. Le premier n'a aucun moyen de s'assurer que le minuteur a fini d'exécuter ses gestionnaires ; le gestionnaire du minuteur peut encore être actif quand il retourne. S'il ne retourne pas d'erreur, le second appellera la fonction done_handler quand le minuteur est complètement arrêté et que tous les gestionnaires sont terminés. Le second retourne aussi GE_INUSE si le minuteur a déjà été arrêté mais que le gestionnaire de fin n'a pas encore été appelé. Notez que vous ne pouvez pas redémarrer le minuteur jusqu'à ce que le gestionnaire de fin soit appelé. Et enfin, pour libérer un minuteur, utilisez gensio_os_funcs_free_timer. Le minuteur ne devrait pas être en cours d'exécution quand vous appelez

cela.

Les runners sont un peu comme des minuteurs à temps zéro, ils seront juste appelés immédiatement. Ils sont utiles pour s'échapper des situations de verrouillage profond où vous voulez faire quelque chose au contexte de base. Utilisez gensio_os_funcs_alloc_runner pour en allouer un. Elle retourne NULL si le runner ne peut pas être alloué. gensio_os_funcs_run fait que le gestionnaire est appelé. Elle retourne GE_INUSE si le runner est actuellement déjà planifié pour être exécuté. Et gensio_os_funcs_free_runner libère le runner. Il ne devrait pas être actuellement planifié pour

s'exécuter.

gensio_os_funcs_service fournit la fonction de service principale pour exécuter les minuteurs, les runners, la gestion d'E/S, etc. Si elle est interrompue par un signal (sur Unix), elle retourne GE_INTERRUPTED. Si timeout n'est pas NULL, c'est une durée relative d'attente et cela retournera GE_TIMEDOUT si le délai expire. Notez que pour de longs délais (jours), cela peut retourner tôt sur certains os funcs, alors ne comptez pas là-dessus pour le chronométrage. Quand cela retourne, le délai sera mis à jour avec le temps restant, même en cas de délai anticipé. Généralement, vous n'utilisez pas cette fonction, vous utilisez plutôt les

attentes.

Appelez gensio_os_funcs_handle_fork dans la fonction enfant après un fork (Unix uniquement). Cela nettoie diverses choses et prépare la bibliothèque gensio à être utilisée après un fork. Si cela retourne une erreur, il est probable que la bibliothèque gensio soit inutilisable dans

l'enfant.

Les attentes sont utilisées pour attendre que des choses se produisent. Quand la chose se produit, ce code devrait appeler wake pour réveiller l'attente. Le service normal des tiers, des runners, de l'E/S, etc. se fait pendant l'attente. Les attentes et les réveils sont basés sur un compteur, si vous appelez wake avant l'attente c'est ok, le réveil sera en attente quand l'attente se produit. Si vous appelez wake 3 fois, il y a 3 réveils en attente. Pour allocapour créer un waiter, appelez gensio_os_funcs_alloc_waiter. Elle renvoie NULL si elle ne peut pas allouer le waiter. gensio_os_funcs_wait attend count réveils et renvoie ensuite zéro. Si timeout est NULL, elle attend indéfiniment. Sinon, si le délai expire, elle renvoie GE_TIMEDOUT et le délai est mis à jour avec le temps restant. Si ce délai expire, aucun réveil n'est « consommé » par la fonction ; si certains réveils sont seulement en attente, ils le restent. gensio_os_funcs_wait_intr est comme gensio_os_funcs_wait, sauf que si un signal est reçu (Unix uniquement), elle renverra GE_INTERRUPTED. gensio_os_funcs_wait_intr_sigmask est comme gensio_os_funcs_wait_intr mais permet d'installer un masque de signals spécifié par l'utilisateur (Unix uniquement). Voir gensio_os_proc_setup pour les détails. Pour envoyer un réveil unique à un waiter, utilisez gensio_os_funcs_wake. Et, bien sûr, appelez gensio_os_funcs_free_waiter pour libérer un

waiter.

Un os funcs possède un pointeur void unique dans lequel l'utilisateur peut installer certaines données pour son propre usage. Utilisez gensio_os_funcs_set_data pour définir ces données et gensio_os_funcs_get_da

ta pour les
récupérer.
