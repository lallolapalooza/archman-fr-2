ÉVÉNEMENTS SYNCHRONES

Par défaut.

STDOUT

Pour chaque fichier traité, get écrira sur la sortie standard le SID accédé et le nombre de lignes récupérées du fichier SCCS, dans le format suivant:

"%s\n%d lignes\n", <SID>, <nombre de lignes>

Si l'option -e est utilisée, le SID du delta à créer apparaîtra après le SID accédé et avant le nombre de lignes générées, dans la locale POSIX:

"%s\nNouveau delta %s\n%d lignes\n", <SID accédé>,
    <SID à créer>, <nombre de lignes>

S'il y a plus d'un fichier nommé ou si un répertoire ou l'entrée standard est nommé, chaque chemin sera écrit avant chacune des lignes affichées dans l'un des formats précédents:

"\n%s:\n", <chemin>

Si l'option -L est utilisée, un résumé des deltas sera écrit en suivant le format spécifié ci-dessous pour les fichiers-l.

Si l'option -i est utilisée, les deltas inclus seront listés après la notation, dans la locale POSIX:

"Inclus:\n"

Si l'option -x est utilisée, les deltas exclus seront listés après la notation, dans la locale POSIX:

"Exclus:\n"

Si les options -p ou -L sont spécifiées, la sortie standard consistera en le texte récupéré du fichier SCCS.

STDERR

La sortie d'erreur standard sera utilisée uniquement pour les messages de diagnostic, sauf si les options -p ou -L sont spécifiées, auquel cas elle inclura tous les messages informatifs normalement envoyés à la sortie standard.

FICHIERS DE SORTIE

Plusieurs fichiers auxiliaires peuvent être créés par get. Ces fichiers sont connus génériquement sous les noms de fichier-g, fichier-l, fichier-p, et fichier-z. La lettre avant le <trait d'union> est appelée le tag. Un nom de fichier auxiliaire sera formé à partir du nom du fichier SCCS: l'application s'assurera que la dernière composante de tous les noms de fichiers SCCS est de la forme s.nom-module; les fichiers auxiliaires seront nommés en remplaçant le s initial par le tag. Le fichier-g fera exception à ce schéma: le fichier-g est nommé en supprimant le préfixe s.. Par exemple, pour s.xyz.c, les noms de fichiers auxiliaires seraient xyz.c, l.xyz.c, p.xyz.c, et z.xyz.c, respectivement.

Le fichier-g, qui contient le texte généré, sera créé dans le répertoire courant (sauf si l'option -p est utilisée). Un fichier-g sera créé dans tous les cas, qu'un certain nombre de lignes de texte aient été générées ou non par get. Il sera possédé par l'utilisateur réel. Si l'option -k est utilisée ou implicite, le fichier-g sera écrivable par le propriétaire uniquement (lecture seule pour tous les autres); sinon, il sera en lecture seule. Seul l'utilisateur réel doit avoir la permission d'écriture dans le répertoire courant.

Le fichier-l contiendra une table indiquant quels deltas ont été appliqués pour générer le texte récupéré. Le fichier-l sera créé dans le répertoire courant si l'option -l est utilisée; il sera en lecture seule et possédé par l'utilisateur réel. Seul l'utilisateur réel doit avoir la permission d'écriture dans le répertoire courant.

Les lignes du fichier-l auront le format suivant:

"%c%c%c %s\t%s %s\n", <code1>, <code2>, <code3>,
    <SID>, <date-heure>, <login>

où les entrées sont:

<code1>
Un <espace> si le delta a été appliqué; '*' sinon.
<code2>
Un <espace> si le delta a été appliqué ou n'a pas été appliqué et a été ignoré; '*' si le delta n'a pas été appliqué et n'a pas été ignoré.
<code3>
Un caractère indiquant une raison spéciale pour laquelle le delta a été appliqué ou non:
I
Inclus.
X
Exclus.
C
Coupé (par une option -c).
<date-heure>
Date et heure (utilisant le format de la spécification de conversion %y/%m/%d %T de l'utilitaire date) de création.
<login>
Nom de connexion de la personne qui a créé le delta.

Les commentaires et les données MR suivront sur les lignes suivantes, indentés d'un <tab>. Une ligne vide terminera chaque entrée.

Le fichier-p sera utilisé pour transmettre les informations résultant d'un get avec l'option -e à delta. Son contenu sera également utilisé pour empêcher une exécution ultérieure de get avec l'option -e pour le même SID jusqu'à ce que delta soit exécuté ou que le drapeau d'édition conjoint, j, soit défini dans le fichier SCCS. Le fichier-p sera créé dans le répertoire contenant le fichier SCCS et l'application s'assurera que l'utilisateur effectif a la permission d'écriture dans ce répertoire. Il sera écrivable par le propriétaire uniquement, et possédé par l'utilisateur effectif. Chaque ligne du fichier-p aura le format suivant:

"%s %s %s %s%s%s\n", <SID du fichier-g>,
    <SID du nouveau delta>, <nom de connexion de l'utilisateur réel>,
    <date-heure>, <valeur-i>, <valeur-x>

où <valeur-i> utilise le format "" si aucune option -i n'a été spécifiée, et utilisera le format:

" -i%s", <argument-option -i>

si une option -i a été spécifiée et <valeur-x> utilise le format "" si aucune option -x n'a été spécifiée, et utilisera le format:

" -x%s", <argument-option -x>

si une option -x a été spécifiée. Il peut y avoir un nombre arbitraire de lignes dans le fichier-p à tout moment; aucune deux lignes ne doit avoir le même nouveau SID de delta.

Le fichier-z servira de mécanisme de verrouillage contre les mises à jour simultanées. Son contenu sera l'ID de processus binaire de la commande (c'est-à-dire get) qui l'a créé. Le fichier-z sera créé dans le répertoire contenant le fichier SCCS pendant la durée de get. Les mêmes restrictions de protection que celles du fichier-p s'appliqueront au fichier-z. Le fichier-z sera créé en lecture seule.
