DESCRIPTIO

N

getopt est utilisé pour séparer (analyser) les options dans les lignes de commande afin de faciliter leur traitement par les procédures du shell, et pour vérifier la validité des options. Il utilise les routines GNU getopt(3) pour ce

faire.

Les paramètres avec lesquels getopt est appelé peuvent être divisés en deux parties : les options qui modifient la manière dont getopt effectuera l'analyse (les options et optstring dans le SYNOPSIS), et les paramètres qui doivent être analysés (parameters dans le SYNOPSIS). La deuxième partie commence au premier paramètre non-option qui n'est pas un argument d'option, ou après la première occurrence de '--'. Si aucune option '-o' ou '--options' n'est trouvée dans la première partie, le premier paramètre de la deuxième partie est utilisé comme chaîne d'options

courtes.

Si la variable d'environnement GETOPT_COMPATIBLE est définie, ou si le premier paramètre n'est pas une option (ne commence pas par un '-', le premier format dans le SYNOPSIS), getopt générera une sortie compatible avec celle des autres versions de getopt(1). Il effectuera toujours le réarrangement des paramètres et reconnaîtra les arguments optionnels (voir la section COMPATIBILITÉ pour plus d'informations)

.

Les implémentations traditionnelles de getopt(1) sont incapables de gérer les espaces blancs et les autres caractères spéciaux (propres au shell) dans les arguments et les paramètres non-options. Pour résoudre ce problème, cette implémentation peut générer une sortie entre guillemets qui doit être à nouveau interprétée par le shell (généralement en utilisant la commande eval). Cela a pour effet de préserver ces caractères, mais vous devez appeler getopt d'une manière qui n'est plus compatible avec les autres versions (le deuxième ou le troisième format dans le SYNOPSIS). Pour déterminer si cette version améliorée de getopt(1) est installée, une option de test spéciale (-T) peut être

ut
ilisée.

ANALYSE Cette section spécifie le format de la deuxième partie des paramètres de getopt (les parameters dans leSYNOPSIS). La section suivante ( SORTIE) décrit la sortie qui est générée. Ces paramètres sont généralement ceux avec lesquels une fonction de shell était appelée. Il faut veiller à ce que chaque paramètre avec lequel la fonction de shell était appelée corresponde à exactement un paramètre dans la liste de paramètres de getopt (voir les EXEMPLES). Toute l'analyse est effectuée par les routines

GNU

getopt(3)

.

Les paramètres sont analysés de gauche à droite. Chaque paramètre est classé comme une option courte, une option longue, un argument d'option ou un paramètre non-option.Une option courte simple est un ' -' suivi d'un caractère d'option courte, à l'exception des caractères ':', ';' et '?', car ils sont réservés

par

getopt(3). Si l'option a un argument obligatoire, il peut être écrit directement après le caractère d'option ou comme le paramètre suivant (c'est-à-dire, séparé par un espace blanc sur la ligne de commande). Si l'option a un argument optionnel, il doit être écrit directement après le caractère d'option s'il est présent.Il est possible de spécifier plusieurs options courtes après un seul

'

-', à condition que toutes (sauf éventuellement la dernière) n'aient pas d'arguments obligatoires ou optionnels.Une option longue commence normalement par '--' suivi du nom de l'option longue. Si l'option a un argument obligatoire, il peut être écrit directement après le nom de l'option longue, séparé par '=', ou comme l'argument suivant (c'est-à-dire, séparé par un espace blanc sur la ligne de commande). Si l'option a un argument optionnel, il doit être écrit directement après le nom de l'option longue, séparé par '=', s'il est présent (si vous ajoutez le ' =' mais rien derrière, il est interprété comme si aucun argument n'était présent ; c'est un léger bug, voir

la

section BUGS). Les options longues peuvent être abrégées, à condition que l'abréviation ne soit pas ambiguë.Chaque paramètre ne commençant pas par un '-', et n'étant pas un argument obligatoire d'une option précédente, est un paramètre non-option. Chaque paramètre après un paramètre ' --' est toujours interprété comme un paramètre non-option. Si la variable d'environnementPOSIXLY_CORRECT est définie, ou si la c

haîne d'options court
es commençait par un '

+', tous les paramètres restants sont interprétés comme des paramètres non-options dès que le premier paramètre

non-option est trouvé.

SORTIE Une sortie est générée pour chaque élément décrit dans la section précédente. La sortie est produite dans le même ordre que celui où les éléments sont spécifiés dans l'entrée, à l'exception des paramètres non-options. La sortie peut être produite en mode compatible (non entre guillemets), ou de manière à ce que les espaces blancs et les autres caractères spéciaux dans les arguments et les paramètres non-options soient préservés (voir GUILLEMETS). Lorsque la sortie est traitée dans le script shell, elle semble être composée d'éléments distincts qui peuvent être traités un par un (en utilisant la commande shift dans la plupart des langages shell). Cela est imparfait en mode non entre guillemets, car les éléments peuvent être divisés à des endroits inattendus s'ils contiennent des espaces blancs ou des caractères

spéciaux.

S'il y a des problèmes d'analyse des paramètres, par exemple parce qu'un argument requis est introuvable ou qu'une option n'est pas reconnue, une erreur sera signalée sur stderr, il n'y aura aucune sortie pour l'élément fautif, et un code d'erreur non nul sera

retourné.

Pour une option courte, un seul '-' et le caractère de l'option sont générés comme un seul paramètre. Si l'option a un argument, le paramètre suivant sera l'argument. Si l'option accepte un argument facultatif, mais qu'aucun n'a été trouvé, le paramètre suivant sera généré mais sera vide en mode entre guillemets, mais aucun second paramètre ne sera généré en mode non entre guillemets (compatible). Notez que de nombreuses autres implémentations de getopt(1) ne prennent pas en charge les arguments

facultatifs.

Si plusieurs options courtes ont été spécifiées après un seul '-', chacune sera présente dans la sortie sous forme de paramètre

séparé.

Pour une option longue, '--' et le nom complet de l'option sont générés comme un seul paramètre. Cela est fait que l'option ait été abrégée ou spécifiée avec un seul '-' dans l'entrée. Les arguments sont traités comme pour les options

courtes.

Normalement, aucune sortie de paramètres non-option n'est générée tant que toutes les options et leurs arguments n'ont pas été générés. Ensuite, '--' est généré comme un seul paramètre, et après lui, les paramètres non-option dans l'ordre où ils ont été trouvés, chacun comme un paramètre séparé. Seulement si le premier caractère de la chaîne d'options courtes était un '-', la sortie des paramètres non-option est générée à l'endroit où ils sont trouvés dans l'entrée (cela n'est pas pris en charge si le premier format de la SYNOPSIS est utilisé ; dans ce cas, toutes les occurrences précédentes de '-' et '+' sont i

gnoré
es).

ENTRE

GUILLEMETS

En mode compatibilité, les espaces blancs ou les caractères « spéciaux » dans les arguments ou les paramètres non-option ne sont pas traités correctement. Comme la sortie est fournie au script shell, le script ne sait pas comment il doit diviser la sortie en paramètres séparés. Pour contourner ce problème, cette implémentation offre la possibilité de mettre entre guillemets. L'idée est que la sortie est générée avec des guillemets autour de chaque paramètre. Lorsque cette sortie est à nouveau fournie au shell (généralement par une commande shell eval), elle est correctement divisée en paramètres

séparés.

La mise entre guillemets n'est pas activée si la variable d'environnement GETOPT_COMPATIBLE est définie, si la première forme de la SYNOPSIS est utilisée, ou si l'option '-u' est

trouvée.

Différents shells utilisent différentes conventions de mise entre guillemets. Vous pouvez utiliser l'option '-s' pour sélectionner le shell que vous utilisez. Les shells suivants sont actuellement pris en charge : 'sh', 'bash', 'csh' et 'tcsh'. En fait, seules deux « variantes » sont distinguées : les conventions de mise entre guillemets de type sh et celles de type

csh. Il est probable que si vous utilisez un autre langage de sc
ript shell, l'une de ces variantes puisse toujours être utilisée.

MODES DE

SCAN

Le premier caractère de la chaîne d'options courtes peut être un '-' ou un '+' pour indiquer un mode de scan spécial. Si la première forme d'appel dans la SYNOPSIS est utilisée, ils sont ignorés ; la variable d'environnement POSIXLY_CORRECT est toutefois toujours

examinée.

Si le premier caractère est '+', ou si la variable d'environnement POSIXLY_CORRECT est définie, l'analyse s'arrête dès que le premier paramètre non-option (c'est-à-dire un paramètre qui ne commence pas par un '-') qui n'est pas un argument d'option est trouvé. Les paramètres restants sont tous interprétés comme des paramètres

non-option.

Si le premier caractère est un '-', les paramètres non-option sont sortis à l'endroit où ils sont trouvés ; en fonctionnement normal, ils sont tous regroupés à la fin de la sortie après qu'un paramètre '--' a été généré. Notez que ce paramètre '--' est toujours généré, mais il sera to

ujours le dernier par
amètre dans ce mode.

COMPATIBILIT

É

Cette version de getopt(1) est écrite pour être aussi compatible que possible avec les autres versions. Habituellement, vous pouvez simplement les remplacer par cette version sans aucune modification, et avec quelques

avantages.

Si le premier caractère du premier paramètre de getopt n'est pas un '-', getopt passe en mode compatibilité. Il interprétera son premier paramètre comme la chaîne d'options courtes, et tous les autres arguments seront analysés. Il continuera à faire le mélange des paramètres (c'est-à-dire que tous les paramètres non-option sont sortis à la fin), sauf si la variable d'environnement POSIXLY_CORRECT est définie, auquel cas, getopt préfixera automatiquement les options courtes d'un '+'

.

La variable d'environnement GETOPT_COMPATIBLE force getopt à passer en mode compatibilité. Définir à la fois cette variable d'environnement et POSIXLY_CORRECT offre une compatibilité à 100 % pour les programmes « difficiles ». Habituellement, cependant, aucune des deux n'est

nécessaire.

En mode compatibilité, les caractères '-' et '+' initiaux dans la chaîne d'

options courtes
sont ignorés.

CODES DE

RETOUR

getopt retourne le code d'erreur 0 pour une analyse réussie, 1 si getopt(3) retourne des erreurs, 2 s'il ne comprend pas ses propres paramètres, 3 si une erreur interne se produit comme un manque de mémoire, et 4 s'il est appelé avec -T

.

BOGUE

S

getopt(3) peut analyser des options longues avec des arguments facultatifs auxquels un argument facultatif vide est donné (mais ne peut pas le faire pour les options courtes). Ce getopt(1) traite les arguments facultatifs vides comme s'ils n'étaient pas

présents.

La syntaxe si vous ne voulez aucune variable d'

option courte n'est pas très intuitive (vous dev
ez les définir explicitement à la chaîne vide).
