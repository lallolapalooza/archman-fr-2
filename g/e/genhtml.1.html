Couverture

différentielle

La couverture différentielle compare deux versions du code source - la version de référence et la version actuelle - ainsi que les résultats de couverture de chacune pour segmenter le code en

catégories.

Pour créer un rapport de couverture différentielle, genhtml

requiert
1

2

Les tracefile_pattern et baseline-file sont traités comme des motifs globules qui correspondent à un ou plusieurs

fichiers.

La différence de couverture entre l'ensemble des fichiers de trace et des fichiers de référence est classée ligne par ligne en catégories basées sur les changements de 2 aspects

:
1
.
Résultats des tests de couverture : une ligne de code peut être testée (1), non testée (0), ou inutilisée (#). Une ligne inutilisée est une ligne de code source qui n'a pas de données de couverture associées, par exemple en raison d'une instruction #ifdef désactivée.
2
.
Modifications du code source : une ligne peut être inchangée, ajoutée (+ =>), ou supprimée (=> -). Notez que le format diff-file utilisé par genhtml signale les changements de lignes comme la suppression de l'ancienne ligne et l'ajout de la nouvelle ligne.

Ci-dessous se trouvent les 12 catégories résultantes, triées par priorité (en supposant que le code non testé est plus intéressant que le code testé, et que le nouveau code est plus intéressant que l'ancien code)

:
UNC
Code nouveau non couvert (+ => 0) : le code nouvellement ajouté n'est pas testé.

LB

C
Perte de couverture de référence (1 => 0) : le code inchangée n'est plus testé.

UI

C
Code inclus non couvert (# => 0) : le code précédemment inutilisé n'est pas testé.

UB

C
Code de référence non couvert (0 => 0) : le code inchangée n'était pas testé avant, il n'est pas testé maintenant.

GB

C
Gain de couverture de référence (0 => 1) : le code inchangée est testé maintenant.

GI

C
Gain de couverture inclus (# => 1) : le code précédemment inutilisé est testé maintenant.

GN

C
Gain de couverture nouveau (+ => 1) : le code nouvellement ajouté est testé.

CB

C
Code de référence couvert (1 => 1) : le code inchangée était testé avant et l'est toujours.

EU

B
Référence non couverte exclue (0 => #) : le code précédemment non testé est inutilisé maintenant.

EC

B
Référence couverte exclue (1 => #) : le code précédemment testé est inutilisé maintenant.

DU

B
Référence non couverte supprimée (0 => -) : le code précédemment non testé a été supprimé.

Binning par date et

propriétaire

Le binning par date annote les rapports de couverture avec des informations sur l'âge du dernier changement pour distinguer le code récemment ajouté ou modifié qui n'a pas été testé du code plus ancien, supposé stable, qui n'est pas testé non plus. Le binning par propriétaire ajoute une annotation identifiant l'auteur des

changements.

Les rapports sur l'âge et la propriété peuvent être utilisés pour renforcer les efforts de l'équipe afin de maintenir une bonne discipline de couverture en mettant en évidence les défauts de couverture dans le code récemment modifié, même en l'absence de données de couverture de

référence.

Pour activer le binning par date et propriétaire, l'option --annotate-script doit être utilisée pour spécifier un script qui fournit des informations sur l'âge et la propriété des lignes de code

source.

Pour chaque ligne source, l'âge is l'intervalle depuis la date de modification la plus récente et le propriétaire est l'identité utilisateur responsable de la modification la plus récente de cette

ligne.

Les totaux globaux de couverture de lignes et les décomptes pour chacune des 12 catégories de classification sont collectés pour chacune des plages d'âge spécifiées (voir l'option --date-bins,

ci-des
sous).

Considérations

supplémentaires

Si l'option --criteria-script est utilisée, genhtml utilisera le script référencé pour déterminer si vos critères de couverture ont été satisfaits - et retournera un statut non nul et affichera un message si les critères ne sont pas

satisfaits.

L'option --version-script est utilisée pour vérifier que les versions de code source identiques/compatibles sont affichées comme celles utilisées pour capturer les données de couverture, ainsi que pour vérifier que le même code source a été utilisé pour capturer les informations de couverture qui isera fusionné et pour vérifier que la version source utilisée pour les opérations de filtrage est compatible avec la version utilisée pour générer les

données.

Les fichiers de sortie HTML sont créés dans le répertoire de travail courant sauf si l'option --output-directory est utilisée. Si tracefile ou baseline-file se termine par ".gz", il est supposé être compressé en GZIP et l'outil gunzip sera utilisé pour le décompresser de manière

transparente.

Notez que tous les fichiers de code source doivent être présents et lisibles à l'emplacement exact du système de fichier où ils ont été compilés, et que toutes les références de chemin dans les fichiers de données d'entrée ".info" et "diff" doivent correspondre exactement (c'est-à-dire une correspondance de chaîne exacte)

.

De plus, les scripts --version-script, --annotate-script et --criteria-script utilisent les mêmes chaînes de chemins. Cependant, consultez les options --substitute et --resolve-script pour un mécanisme permettant d'ajuster les chemins extraits afin qu'ils correspondent à votre disposition de sources et/ou de contrôle de

révision.

Vous pouvez utiliser l'option de configuration check_exisitence_before_callback pour indiquer à l'outil de vérifier que le fichier existe avant d'appeler le rappel --version-script ou --annotate-script. Consultez le manuel lcovrc(5) pour p
