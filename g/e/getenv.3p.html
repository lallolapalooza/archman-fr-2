getenv(3p)

GETENV(3P) Manuel du programmeur POSIX GETENV(3P)

PROLOG

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consultez la page de manuel Linux correspondante pour les détails du comportement sous Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

getenv — obtenir la valeur d'une variable d'environnement

SYNOPIS

#include <stdlib.h>
char *getenv(const char *name);

DESCRIPTION

La fonctionnalité décrite sur cette page de référence est alignée sur la norme ISO C. Tout conflit entre les exigences décrites ici et la norme ISO C est involontaire. Ce volume de POSIX.1‐2017 s'en remet à la norme ISO C.

La fonction getenv() recherche dans l'environnement du processus appelant (voir le volume Définitions de base de POSIX.1‐2017, Chapitre 8, Variables d'environnement) la variable d'environnement name si elle existe et retourne un pointeur vers la valeur de la variable d'environnement. Si la variable d'environnement spécifiée ne peut pas être trouvée, un pointeur nul est retourné. L'application doit s'assurer de ne pas modifier la chaîne pointée par la fonction getenv().

Le pointeur de chaîne retourné peut être invalidé ou le contenu de la chaîne peut être écrasé par un appel ultérieur à getenv(), setenv(), unsetenv(),
ou (si pris en charge) putenv(), mais ils ne seront pas affectés par un appel à toute autre fonction de ce volume de POSIX.1‐2017.

Le pointeur de chaîne retourné peut également être invalidé si le thread appelant est terminé.

La fonction getenv() n'a pas besoin d'être thread-safe.

VALEUR DE RETOUR

En cas d'achèvement réussi, getenv() retourne un pointeur vers une chaîne contenant la valeur du nom spécifié. Si le nom spécifié ne peut pas être trouvé dans l'environnement du processus appelant, un pointeur nul est retourné.

ERREURS

Aucune erreur n'est définie.

Les sections suivantes sont informatives.

EXEMPLES

Obtenir la valeur d'une variable d'environnement

L'exemple suivant obtient la valeur de la variable d'environnement HOME.

#include <stdlib.h>
...
const char *name = "HOME";
char *value;
value = getenv(name);

UTILISATION PAR L'APPLICATION

Aucune.

RATIONALE

La fonction clearenv() a été envisagée mais rejetée. La fonction putenv() a maintenant été incluse pour l'alignement avec la Single UNIX Specification.

La fonction getenv() n'est intrinsèquement pas thread-safe car elle retourne une valeur pointant vers des données statiques.

Les applications conformes sont tenues de ne pas modifier directement les pointeurs auxquels environ pointe, mais d'utiliser uniquement les fonctions setenv(), unsetenv(), et putenv(), ou l'affectation à environ elle-même, pour manipuler l'environnement du processus. Cette contrainte permet à l'implémentation de gérer correctement la mémoire qu'elle alloue. Cela permet à l'implémentation de libérer tout espace qu'elle a alloué aux chaînes (et peut-être à leurs pointeurs) stockées dans environ lorsque unsetenv() est appelé. Une procédure de démarrage du runtime C (celle qui appelle main() et initialise peut-être environ) peut également initialiser un indicateur indiquant qu'aucun environnement n'a encore été copié dans un stockage alloué, ou que le tableau séparé n'a pas encore été initialisé. Si l'application passe à un nouvel environnement complet en attribuant une nouvelle valeur à environ, cela peut être détecté par getenv(), setenv(), unsetenv(), ou putenv() et l'implémentation peut alors se réinitialiser en fonction du nouvel environnement. (Cela peut inclure la copie des chaînes d'environnement dans un nouveau tableau et l'affectation de environ pour pointer vers celui-ci.)

En fait, pour de meilleures performances de getenv(), les implémentations qui ne fournissent pas putenv() pourraient également maintenir une copie séparée de l'environnement dans une structure de données qui pourrait être recherchée beaucoup plus rapidement (comme une table de hachage indexée, ou un arbre binaire), et mettre à jour à la fois celle-ci et la liste linéaire à environ lorsque setenv() ou unsetenv() est invoqué. Dans les implémentations qui fournissent putenv(), une telle copie pourrait encore valoir la peine mais devrait permettre le fait que les applications peuvent modifier directement le contenu des chaînes d'environnement ajoutées avec putenv(). Par exemple, si une chaîne d'environnement trouvée en recherchant la copie est une chaîne ajoutée à l'aide de putenv(), l'implémentation devrait vérifier que la chaîne dans environ a toujours le même nom (et la même valeur, si la copie inclut des valeurs), et lorsque la recherche de la copie ne produit aucun résultat, l'implémentation devrait alors rechercher chaque chaîne d'environnement dans environ qui a été ajoutée à l'aide de putenv() au cas où l'une d'elles aurait changé de nom et correspondrait maintenant. Ainsi, chaque utilisation de putenv() pour ajouter à l'environnement réduirait l'avantage de vitesse d'avoir la copie.

Les performances de getenv() peuvent être importantes pour les applications qui ont un grand nombre de variables d'environnement. Typiquement, les applications de ce type utilisent l'environnement comme une base de données de ressources de paramètres configurables par l'utilisateur. Le fait que ces variables se trouvent dans l'environnement shell de l'utilisateur signifie généralement que tout autre programme qui utilise des variables d'environnement (comme ls, qui tente d'utiliser COLUMNS), ou vraiment presque n'importe quel utilitaire (LANG, LC_ALL, etc.) est également ralenti par la recherche linéaire à travers les variables.

Une implémentation qui maintient des structures de données séparées, ou même une qui gère la mémoire qu'elle consomme, n'est actuellement pas requise car il a été jugé qu'elle réduirait le consensus parmi les implémenteurs qui ne souhaitent pas modifier leurs implémentations historiques.

DIRECTIONS FUTURES

Une version future pourrait ajouter une ou plusieurs fonctions pour accéder et modifier l'environnement de manière thread-safe.
