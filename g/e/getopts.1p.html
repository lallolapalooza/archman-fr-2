DESCRIPTIO

N

L'utilité getopts doit récupérer les options et les arguments d'option à partir d'une liste de paramètres. Elle doit prendre en charge les directives de syntaxe des utilités 3 à 10 incluses, décrites dans le volume des définitions de base de POSIX.1‐2017, Section 12.2, Directives de syntaxe d

es utilités.

Chaque fois qu'elle est invoquée, l'utilité getopts doit placer la valeur de l'option suivante dans la variable shell spécifiée par l'opérande name et l'index de l'argument suivant à traiter dans la variable shell OPTIND. Chaque fois que le shell est invoqué, OPTIND doit être initialisée à

1.

Lorsque l'option requiert un argument d'option, l'utilité getopts doit le placer dans la variable shell OPTARG. Si aucune option n'a été trouvée, ou si l'option trouvée n'a pas d'argument d'option, OPTARG doit être

déréglée.

Si un caractère d'option non contenu dans l'opérande optstring est trouvé là où un caractère d'option est attendu, la variable shell spécifiée par name doit être définie sur le caractère <question-mark>('?'). Dans ce cas, si le premier caractère de optstring est un <colon>(':'), la variable shell OPTARG doit être définie sur le caractère d'option trouvé, mais aucune sortie ne doit être écrite sur l'erreur standard ; sinon, la variable shell OPTARG doit être déréglée et un message de diagnostic doit être écrit sur l'erreur standard. Cette condition doit être considérée comme une erreur détectée dans la manière dont les arguments ont été présentés à l'application appelante, mais ne doit pas être une erreur dans le traitement de getopts

.

Si un argument d'option est manquant

:
*
Si le premier caractère de optstring est un <colon>, la variable shell spécifiée par name doit être définie sur le caractère <colon> et la variable shell OPTARG doit être définie sur le caractère d'option
trouvé.
*
Sinon, la variable shell spécifiée par name doit être définie sur le caractère <question-mark>, la variable shell OPTARG doit être déréglée et un message de diagnostic doit être écrit sur l'erreur standard. Cette condition doit être considérée comme une erreur détectée dans la manière dont les arguments ont été présentés à l'application appelante, mais ne doit pas être une erreur dans le traitement de getopts ; un message de diagnostic doit être écrit co
mme indiqué, mais le statut
de sortie doit être zéro.

Lorsque la fin des options est rencontrée, l'utilité getopts doit se terminer avec une valeur de retour supérieure à zéro ; la variable shell OPTIND doit être définie sur l'index du premier opérande, ou la valeur "$#"+1 s'il n'y a pas d'opérandes ; la variable name doit être définie sur le caractère <question-mark>. L'un des éléments suivants doit identifier la fin des options : le premier argument "--" qui n'est pas un argument d'option, la découverte d'un argument qui n'est pas un argument d'option et qui ne commence pas par un '-', ou la rencontre d'une

erreur.

Les variables shell OPTIND et OPTARG doivent être locales à l'appelant de getopts et ne doivent pas être exportées par

défaut.

La variable shell spécifiée par l'opérande name, OPTIND et OPTARG doivent affecter l'environnement d'exécution du shell courant ; voir Section 2.12, Environnement d'exécuti

on du shell.

Si l'application définit OPTIND à la valeur 1, un nouveau jeu de paramètres peut être utilisé : soit les paramètres positionnels courants, soit de nouvelles valeurs arg. Toute autre tentative d'invoquer getopts plusieurs fois dans un seul environnement d'exécution de shell avec des paramètres (paramètres positionnels ou opérandes arg) qui ne sont pas identiques dans toutes les invocations, ou avec une valeur OPTIND modifiée pour être une valeur autre

que 1, produit des ré
sultats indéterminés.

optstri
ng
Une chaîne contenant les caractères d'option reconnus par l'utilité appelant getopts. Si un caractère est suivi d'un <colon>, l'option doit s'attendre à avoir un argument, qui doit être fourni comme argument séparé. Les applications doivent spécifier un caractère d'option et son argument d'option comme arguments séparés, mais getopts doit interpréter les caractères suivant un caractère d'option nécessitant des arguments comme un argument que cela soit fait ou non. Un argument d'option nul explicite n'a pas besoin d'être reconnu s'il n'est pas fourni comme argument séparé lorsque getopts est invoqué. (Voir aussi la fonction getopt() définie dans le volume des interfaces système de POSIX.1‐2017.) Les caractères <question-mark> et <colon> ne doivent pas être utilisés comme caractères d'option par une application. L'utilisation d'autres caractères d'option non alphanumériques produit des résultats indéterminés. Si l'argument d'option n'est pas fourni comme argument séparé du caractère d'option, la valeur dans OPTARG doit être dépouillée du caractère d'option et du '-'. Le premier caractère dans optstring détermine comment getopts se comporte si un caractère d'option est inconnu ou si un argument d'option est
