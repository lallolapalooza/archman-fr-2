Si keepalive est activé, définit la valeur de TCP_KEEPIDLE pour les systèmes qui la supportent. Une valeur de -1 signifie que soit le système ne la supporte pas, soit une erreur s'est produite lors de la tentative de récupération de la valeur par défaut.

Si keepalive est activé, définit la valeur de TCP_KEEPINTVL pour les systèmes qui la supportent. Une valeur de -1 signifie que soit le système ne la supporte pas, soit une erreur s'est produite lors de la tentative de récupération de la valeur par défaut.
--keepalive-count arg (=-1)
Si keepalive est activé, définit la valeur de TCP_KEEPCNT pour les systèmes qui la supportent. Une valeur de -1 signifie que soit le système ne la supporte pas, soit une erreur s'est produite lors de la tentative de récupération de la valeur par défaut.

DESCRIPTION

Gearman fournit un cadre d'application générique pour déléguer du travail à d'autres machines ou processus mieux adaptés pour effectuer ce travail. Il permet de travailler en parallèle, d'équilibrer la charge de traitement et d'appeler des fonctions entre différents langages. Il peut être utilisé dans une variété d'applications, des sites web à haute disponibilité au transport d'événements de réplication de base de données. En d'autres termes, c'est le système nerveux de la communication de traitement distribué. Quelques points forts de Gearman

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

:
  • Open Source - C'est gratuit ! (dans les deux sens du terme) Gearman possède une communauté open source active et facile à rejoindre si vous avez besoin d'aide ou si vous souhaitez
    • contribuer.
  • Multi-langages - Il existe des interfaces pour plusieurs langages, et cette liste est en croissance. Vous avez également la possibilité d'écrire des applications hétérogènes avec des clients soumettant du travail dans un langage et des workers réalisant ce travail dans un
    • autre.
  • Flexible - Vous n'êtes pas lié à un modèle de conception spécifique. Vous pouvez rapidement assembler des applications distribuées en utilisant le modèle de votre choix, l'une des options étant

  • Rapide - Gearman possède un protocole et une interface simples avec un nouveau serveur optimisé en C pour minimiser la surcharge de votre

Modèle de

threads

L'option -t de gearmand vous permet de spécifier plusieurs threads d'E/S, ceci est activé par défaut. Il y a actuellement trois types de threads dans le serveur de jobs

:

Thread d'écoute et de gestion - seulement un - thread d'E/S - peut en avoir plusieurs - thread de traitement - seulement

un

Quand aucune option -t n'est donnée ou quand -t 0 est donné, les trois types de threads se produisent au sein d'un seul thread. Quand -t 1 est donné, il y a un thread pour l'écoute/la gestion et un thread pour l'E/S et le traitement. Quand -t 2 est donné, il y a un thread pour chaque type de thread ci-dessus. Pour toutes les valeurs de l'option -t supérieures à 2, plus de threads d'E/S sont

créés.

Le thread d'écoute et de gestion est principalement responsable de l'acceptation de nouvelles connexions et de l'assignation de ces connexions à un thread d'E/S (s'il y en a plusieurs). Il coordonne également le démarrage et l'arrêt au sein du serveur. Ce thread aura une instance de libevent pour gérer les événements de socket et les signaux sur un pipe interne. Ce pipe est utilisé pour réveiller le thread ou pour coordonner

l'arrêt.

Le thread d'E/S est responsable de l'exécution des appels système de lecture et d'écriture sur les sockets et de l'analyse initiale des paquets. Une fois le paquet analysé, il est mis dans une file d'attente asynchrone pour le thread de traitement (chaque thread a sa propre file, il y a donc très peu de contention). Chaque thread d'E/S a sa propre instance de libevent pour gérer les événements de socket et les signaux sur un pipe interne, comme le thread

d'écoute.

Le thread de traitement ne devrait contenir aucun appel système (à l'exception du brk() occasionnel pour plus de mémoire), et gère les différentes listes et tables de hachage utilisées pour suivre les clés uniques, les références de jobs, les fonctions et les files de jobs. Tous les paquets qui doivent être renvoyés aux connexions sont mis dans une file d'attente asynchrone pour le thread d'E/S. Le thread d'E/S les récupérera et les renverra sur le socket connecté. Tous les paquets passent par le thread de traitement car il contient les informations nécessaires pour traiter les paquets. Cela est dû à la nature complexe des différentes listes et tables de hachage. Si plusieurs threads les modifiaient, la surcharge de verrouillage causerait probablement de pires performances que de les garder dans un seul thread (et compliquerait aussi le code). À l'avenir, plus de travail pourrait être déplacé vers les threads d'E/S, et le thread de traitement pourrait conserver une fonctionnalité minimale pour gérer ces tables et listes. Jusqu'ici, cela n'a pas été un goulot d'étranglement significatif, une machine Intel à 16 cœurs est capable de traiter plus de 50k jobs par

seconde.

Files d'attente

persistantes

À l'intérieur du serveur de jobs Gearman, toutes les files de jobs sont stockées en mémoire. Cela signifie que si un serveur redémarre ou plante avec des jobs en attente, ceux-ci seront perdus et ne seront jamais exécutés par un worker. Des files d'attente persistantes ont été ajoutées pour permettre aux jobs d'arrière-plan d'être stockés dans une file durable externe afin qu'ils puissent survivre aux redémarrages et aux plantages du serveur. La file persistante n'est activée que pour les jobs d'arrière-plan car les jobs de premier plan ont un client attaché. Si un serveur de jobs disparaît, le client peut le détecter et redémarrer le job de premier plan ailleurs (ou renvoyer une erreur à l'appelant d'origine). Les jobs d'arrière-plan, en revanche, n'ont pas de client attaché et sont simplement censés être exécutés lorsqu'ils sont

soumis.

La file d'attente persistante fonctionne en appelant une fonction de rappel de module juste avant de mettre un nouveau job dans la file interne des jobs en attente d'exécution. Cela permet au module de stocker le job sur le point d'être exécuté de manière persistante afin qu'il puisse être rejoué plus tard lors d'un redémarrage. Une fois qu'il est stocké via le module, le job est mis sur la file active des jobs exécutables, réveillant les workers disponibles si nécessaire. Une fois que le job a été terminé avec succès par un worker, une autre fonction de rappel de module est appelée pour informer le module que le job est terminé et peut être supprimé. Si un serveur de jobs plante ou redémarre entre ces deux appels pour un job, les jobs sont rechargés lors du prochain démarrage du serveur de jobs. Lorsque le serveur de jobs démarre, il appellera une fonction de rappel de rejeu dans le module pour fournir une liste de tous les jobs qui n'étaient pas terminés. Cela est utilisé pour remplir la file mémoire interne des jobs à exécuter. Une fois ce rejeu terminé, le serveur de jobs termine son initialisation et les jobs sont maintenant exécutables dès que les workers se connectent (la file devrait être dans le même état que lors de la plantage). Ces jobs sont supprimés de la file persistante lorsqu'ils sont terminés, comme d'habitude. NOTE : La suppression de jobs depuis le stockage de la file persistante ne les supprimera pas de la file en mémoire tant que le serveur est en cours

d'exécution.

Les files sont implémentées en utilisant une interface modulaire, il est donc facile d'ajouter de nouveaux magasins de données pour la file

persistante.

Un module de file persistante est activé en passant l'option -q ou –queue-type à gearmand. Exécutez gearmand –hel

p pour voir quels modules de file sont pris en charge sur votre système. S'il vous manque des options pour l
'un que vous souhaitez utiliser, vous devrez installer toutes les dépendances puis recompiler le paquet gearmand.

Protocoles

étendus

L'interface de plugin de protocole vous permet de prendre en charge les fonctions d'envoi et de récept

ion de paquets, vous permettant de remplir les tampons comme requis par le protocole. Les fonctions de
lecture et d'écriture principales peuvent (et doivent) être utilisées par le plugin de protocole.

HTT

P

Ce plugin de protocole vous permet de faire correspondre des requêtes HTTP à des jobs Gearman. Il ne fournit actuellement que la soumission de jobs par le client, mais il pourrait être étendu pour prendre en charge d'autres types de requêtes à l'avenir. Le plugin peut gérer à la fois les données GET et POST, ces dernières étant utilisées pour envoyer une charge de travail au serveur de jobs. L'URL demandée est traduite en la fonction

appelée.

Par exemple, la requête

: 
POST /reverse
HTTP/1.1 Cont
ent-Length: 1
2 Hello world!
