DESCRIPTIO

N

gensio est l'abréviation de GENeral Stream Input Output (Entrée/Sortie de flux générale). Il fournit une abstraction pour toutes sortes d'E/S de flux, et rend même certaines E/S de paquets semblables à des E/S de flux (comme UDP). En particulier, gensio facilite la création de connexions chiffrées et

authentifiées.

La bibliothèque gensio spécifie une connexion (gensio) à l'aide d'un format de chaîne de caractères. Cela se compose d'un type de gensio et d'options facultatives entre parenthèses. Pour un gensio terminal (celui qui se trouve au bas de la pile), il peut prendre d'autres options séparées par une virgule. Pour les gensios de filtre (ceux qui ne sont pas au bas de la pile), un autre gensio doit être spécifié après la virgule. Par exemple

:
seriald
ev,/de
v/ttyS0

spécifie un gensio de port série. Ou

:

f=100),loca
lhost,4000

spécifie une connexion TCP avec un tampon de lecture de 100 octets, pour se connecter au port 4000 sur localhost. Ou

:
telnet,t
cp,localh
ost,4000

spécifie un filtre telnet au-dessus d'une connexion

TCP.

Lorsque vous spécifiez un gensio, vous pouvez ajouter des guillemets (simples ou doubles) pour supprimer la signification spéciale de certains caractères, afin que vous puissiez avoir des virgules dans les options, etc. Ils peuvent aussi être échappés avec un «\». Par exemple, si vous spécifiez une laddr dans une adresse sctp, vous devez faire ceci. L'adresse suivante

:

alhost,4001),
localhost,3023

Les gensios accepteurs, les gensios utilisés pour accepter des connexions, par opposition aux gensios de connexion, sont spécifiés de la même manière. Chaque type individuel peut varier, et certains gensios ne sont que des gensios de connexion. Les options peuvent varier entre les gensios accepteurs et de connexion de même type. Par exemple, un gensio TCP acceptant n'a pas forcément besoin d'un nom d'hôte, mais un gensio de connexion en a

besoin.

Lorsqu'un gensio accepteur reçoit une connexion, il crée un gensio accepté. Cela fonctionne principalement comme un gensio de connexion, sauf que certaines fonctions peuvent être limitées. Vous ne pourrez peut-être pas fermer puis rouvrir un gensio

accepté.

La bibliothèque gensio a le concept de client et de serveur. Les gensios acceptés sont généralement considérés comme des serveurs. Les gensios de connexion sont généralement considérés comme des clients. Certains gensios peuvent permettre de surcharger

cela.

Un gensio peut être fiable ou non. Un gensio fiable délivrera de manière fiable toutes les données dans l'ordre, comme TCP. Un gensio qui n'est pas fiable peut perdre des données ou les délivrer hors de l'ordre, comme UDP. Cela peut être interrogé avec gensio_is_reliable()

.

Un gensio peut être à paquets ou non. Un gensio à paquets fera correspondre exactement les écritures et les lectures. Ainsi, si vous écrivez 15 octets d'un côté, une lecture de 15 octets pour ces données apparaîtra de l'autre côté. Un gensio qui n'est pas à paquets ne respectera pas les limites d'écriture ; cette écriture de 15 octets peut entraîner plusieurs lectures ou être combinée avec une autre écriture pour plus de 15 octets. Les E/S à paquets nécessitent une utilisation minutieuse pour fonctionner correctement. Si le gensio n'a pas la place pour un autre paquet, une écriture réussira mais écrira 0 octet. Sinon, si vous écrivez plus qu'une taille de paquet, il ne prendra que le nombre d'octets qui peuvent tenir dans un paquet, il tronquera donc. C'est utile si vous voulez diffuser sur une interface à paquets, mais si vous voulez vraiment des paquets, vous devez vous assurer que toutes les tailles sont correctement définies. En particulier, vous devez définir la taille de lecture et d'écriture max à la même valeur. Vous devez vérifier lors des écritures qu'elles ont écrit toutes les données. Vous pouvez gérer des lectures partielles, si vous le souhaitez, mais vous n'obtiendrez le reste du paquet que lors de la deuxième lecture et des

suivantes.

Un gensio peut être orienté message. Cette implémentation est empruntée à SCTP (même si ce n'est pas vraiment pris en charge sur Linux pour le moment). Cela signifie essentiellement que vous pouvez marquer explicitement les limites de message lors de l'envoi de données, et que cette marque explicite sera définie côté lecture. Vous faites cela en ajoutant un auxdata «eom» à l'écriture ; la fin de cette écriture est supposée être la fin d'un message. Si l'écriture n'accepte pas toutes les données, le «eom» est ignoré, vous devez réécrire les données restantes avec «eom» défini. Vous pouvez également faire une écriture partielle de messages et définir «eom» à la fin. Côté réception, «eom» sera défini lorsque la fin d'un message est délivrée. Les données délivrées dans le rappel de réception ne seront que les données de ce message. Si l'utilisateur n'accepte pas toutes les données, les données restantes dans le message sont à nouveau présentées à l'utilisateur avec «eom»

défini.

Flux et

Certains gensios prennent en charge le concept de flux et/ou de

Un flux est délivré dans le cadre du flux de données normal d'un gensio. Le flux «default» sera traité normalement. Tous les autres flux auront «stream=<x>» donné dans l'auxdata pour spécifier sur quel flux écrire ou quel flux a été lu. Les flux ne peuvent pas être contrôlés individuellement en

Un canal est un flux de données comme un flux, mais il peut être contrôlé individuellement en débit. Il apparaît comme un nouveau gensio dans le rappel GENSIO_EVENT_NEW_CHANNEL. Vous pouvez créer un canal avec gensio_alloc_channel() puis l'ouvrir avec gensio_open(). Une fois ouvert, un canal fonctionne comme un gensio normal. Si vous fermez le canal principal d'un gensio, les autres canaux resteront ouverts ; les ressources du canal principal seront toujours conservées jusqu'à ce que tous les canaux soient

fermés.

CRYPTOGRAPHIE À CLÉ

PUBLIQUE

Les gensios ssl et certauth utilisent la cryptographie à clé publique. Cette section donne un petit aperçu du fonctionnement de cela. Vous pouvez ignorer cette section en toute sécurité si vous comprenez déjà ces

concepts.

La cryptographie à clé publique est utilisée pour authentifier et chiffrer les informations au début d'une session. C'est une opération assez coûteuse et n'est généralement pas utilisée pour chiffrer les informations après le

début.

En cryptographie à clé publique, vous avez trois éléments de base : une clé privée, un certificat (ou clé publique), et une autorité de certification (CA)

.

La clé privée est ce qu'elle est : privée. Vous n'envoyez même pas votre clé privée à une autorité de certification pour la signature de votre certificat. Gardez-la privée, non lisible par les autres. Protégez-la ; si elle devient connue, votre certificat devient inutile pour vous, n'importe qui peut usurper votre

identité.

Le certificat est la clé publique, et est mathémattiquement associée à une seule clé privée. C'est simplement que, publique, tout le monde peut l'utiliser pour vérifier que vous possédez la clé privée en vous demandant de signer certaines données. Les données du certificat (comme le Common Name) font partie du certificat. Si ces données sont modifiées, la validation du certificat

échouera.

L'AC est généralement un tiers de confiance qui vous valide et signe votre certificat (généralement moyennant des frais). Les AC émettent leurs propres certificats publics qui sont bien connus et généralement disponibles sur votre système. Les certificats de l'AC sont utilisés pour prouver que votre certificat est

valide.

SIGNATUR

E

Le processus de signature a déjà été mentionné, mais pas décrit. Fondamentalement, vous utilisez votre clé privée pour générer une valeur sur certaines données fournies qui prouve que vous possédez la clé privée. Le certificat est utilisé pour vérifier mathématiquement la

signature.

Deux choses sont normalement faites avec cela

:

Dans un échange de clé publique, l'entité souhaitant être autorisée envoie un certificat. L'entité autorisante parcourra son AC à la recherche d'un certificat qui a signé le certificat envoyé. Si l'entité autorisante trouve un certificat qui peut être utilisé pour valider le certificat envoyé, le certificat envoyé est

valide.

Après cela, l'entité autorisante envoie certaines données généralement aléatoires à l'autre entité. L'autre entité prendra ces données, peut-être certaines autres données importantes qu'elle veut s'assurer ne pas être modifiées lors du transfert, et signera ces données. Elle renvoie la signature à l'entité autorisante. L'entité autorisante peut alors utiliser les données et la signature pour valider que l'entité émettrice possède la clé privée associée au

certificat.

C'est fondamentalement le fonctionnement de https. Notez que c'est le client web qui authentifie le serveur web, et non l'inverse. Cela prouve que vous vous connectez à l'entité que vous prétendez être. L'authentification d'un client web auprès du serveur web est généralement effectuée via un mécanisme différent (bien que l'SSL/TLS utilisé par le gensio ssl ait un moyen de le faire, il n'est généralement pas utilisé à cette fin)

.

Dans le scénario du serveur web, les données du certificat (spécifiquement le Common Name et le Subject

Alternate Name) doivent correspondre au nom de la page web à laquelle vous vous connectez. Les gensios ss
l et certauth ne font pas cette authentification, c'est à l'utilisateur de le faire si c'est nécessaire.

CHIFFREMEN

T

Le certificat peut être utilisé pour chiffrer des données qui ne peuvent être déchiffrées qu'avec la clé privée. Lors de l'établissement d'une connexion chiffrée, cela est généra

lement utilisé pour transférer une clé de cryptographie symétrique d'une entité à une autre (de l'entité autorisante à l'entité requérante dans le cas ci-dessus). Vous pourriez c
hiffrer toutes les données avec la clé publique, mais cela est très coûteux et dans notre exemple ci-dessus nécessiterait des certificats et des clés privées aux deux extrémités.

CERTIFICATS

AUTO-SIGNÉS

Il est possible de créer un certificat qui peut agir comme sa propre autorité de certification. C'est ainsi que fonctionne ssh. Vous créez une clé publique et une clé privée. Vous placez la clé publique dans le répertoire .ssh/authorized_keys sur les systèmes où vous souhaitez vous connecter. Le certificat agit à la fois comme la clé publique (comme partie du transfert initial) et comme l'AC (dans le répertoire authorized_keys) pour autoriser votre utilisation du système auquel vous vous

connectez.

ssh stocke également les endroits auxquels il s'est connecté dans .ssh/known_hosts, qui est l'AC dans la direction opposée. C'est pourquoi il vous demande si vous ne vous êtes jamais connecté à un système auparavant, il n'a pas la clé dans son AC. Ou pourquoi, si vous vous connectez à un système auquel vous vous êtes connecté auparavant et que les certificats ne correspondent pas ou échouent à la validation, il se

plaint.

Donc, si vous utilisez des certificats auto-signés, vous devez faire attention à ne mett

re dans l'AC que ceux en lesquels vous avez confiance. C'est évidemment pas possible da
ns un grand système comme le World Wide Web, d'où la création d'AC tierces de confiance.

CONFIANCE ET

CRYPTOGRAPHIE

Les discussions ci-dessus mentionnent la confiance plusieurs fois. La cryptographie n'élimine pas le besoin de confiance. Elle rend simplement la confiance plus pratique. Si quelqu'un vous envoie un certificat, vous devez valider que c'est bien lui qui vous a envoyé le certificat, et qu'il n'a pas été modifié en transit. Si vous ajoutez ce certificat à votre AC, vous faites confiance au certificat, et vous feriez mieux de vous assurer (avec des empreintes, généralement, voir la documentation openssl pour plus de détails) qu'il provient d'une entité de

confiance.

La partie la plus difficile de la cryptographie en général est la gestion des clés. Casser des algorithmes cryptographiques est vraiment difficile. Amener les gens à divulguer des clés privées ou à utiliser les mauvaises clés est beaucoup plus

facile.

Notez qu'un seul nom d'hôte peut résulter en plus d'une adresse. Par exemple, il peut avoir à la fois une adresse IPv4 et une adresse IPv6. Celles-ci sont traitées comme plusieurs noms d'hôtes. De cette façon, il acceptera à la fois les connexions IPv4 et IPv6. IPv4.

SCTP implémente l'algorithme de Nagle par défaut, ce qui peut mal interagir si sack_freq est défini à plus de un. Donc vous êtes bloqué en attendant le sack_delay où le sack sera envoyé et relancera les

choses.

connecting = sound[(options)],

<device>

Le gensio sound donne accès aux périphériques sonores de la plateforme. C'est un gensio inhabituel à bien des égards. Il n'est pas très utile pour le fonctionnement de streaming normal. C'est néanmoins une opération de streaming, il s'inscrit donc dans le cadre. Mais pour éviter les sous-dépassements et les dépassements, le flux doit être continuellement fourni ou

consommé.

Le flux est constitué d'octets de données binaires dans l'ordre d'octets de l'hôte. Si l'interface sonore de bas niveau utilise un différent ordre d'octets, il est converti vers l'ordre de l'hôte dans le gensio. Le gensio peut aussi convertir les types de données. Si vous demandez un format float et que le pilote de bas niveau ne peut faire que des entiers, le gensio fera la conversion pour vous. Chaque élément de données (octet, int16, etc.) est appelé un échantillon. Ainsi, le pilote a un format utilisateur (ce que l'utilisateur voit) et un format PCM (ce que le pilote utilise)

.

Un flux a un certain nombre de canaux, au moins un. Le stéréo, par exemple, a deux canaux. Une trame se compose d'échantillons pour tous les canaux. Les trames sont toujours entrelacées ; les canaux individuels apparaissent comme des éléments de données successifs dans le flux. Ainsi, en stéréo, sample1 est le canal 1 de la première trame, sample2 est le canal 2 de la première trame, sample 3 est le canal 1 de la deuxième trame,

etc.

Un tampon est un ensemble de trames. La taille d'un tampon est spécifiée en trames, pas en octets. Les lectures sont toujours fournies en blocs de la taille du tampon. Si vous ne consommez pas toutes les données d'un tampon, il vous donnera le reste du tampon à la lecture suivante, jusqu'à ce que le tampon soit consommé. Les écritures peuvent être faites de n'importe quelle taille, mais il est généralement plus efficace d'écrire toujours des blocs de la taille du

tampon.

Un nombre de tampons peut aussi être spécifié. Vous voulez généralement un nombre suffisamment grand pour que les données puissent être écrites sans délai dans le périphérique si le programme ralentit un peu, mais pas trop grand pour ne pas introduire de retard si vous voulez changer les données

écrites.

Un gensio sonore peut avoir une entrée, une sortie, ou les deux. Vous spécifiez lequel vous voulez en définissant le nombre de canaux à une valeur non nulle. La plupart des paramètres peuvent être préfixés par "in" ou "out" pour spécifier que le paramètre ne s'applique qu'au périphérique d'entrée et de sortie. Sans ce préfixe, il s'appliquera à la fois à l'entrée et à la sortie. Notez que les flux d'entrée et de sortie sont complètement indépendants ; ils peuvent avoir des types, formats, débits, etc.

différents.

Différentes interfaces sonores sont disponibles sur les plateformes. Pour Linux, les interfaces alsa et file sont disponibles, et éventuellement portaudio, selon la compilation. Sur Windows, les interfaces win et file sont disponibles et éventuellement portaudio. Sur Macos, portaudio et file sont

disponibles.

Le périphérique est spécifié sur la ligne de commande. Le nom dépend du système. Pour alsa, le nom doit correspondre exactement à la première ligne de la sortie de la liste aplay/gsound. Vous pouvez utiliser "aplay -L" ou "arecord -L" pour lister les périphériques d'entrée et de sortie disponibles. Ou vous pouvez utiliser le programme "gsound

-L".

Pour Windows et portaudio, le nom doit simplement correspondre à une partie du nom du périphérique. Les noms Windows commencent toujours par un chiffre. Ainsi, par exemple, si la sortie de "gsound -L" sur votre plateforme Windows est

Unlike normal file descriptors, when you fork with a gensio, you now have two unassociated copies of the gensios. So if you do operations on one, it might mess up the other. that.

fork.

Then after you fork, you should

o
)

call:

Another issue with forking on Linux is epoll. An epoll fd is not duplicated on a fork, both forks get the same epoll fd. If you close the epoll fd in one for,

one). It will handle any cleanup required after the fork. Other systems may require other cleanups after a fork, so you should always call this after a fork.
