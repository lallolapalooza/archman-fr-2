DESCRIPTIO

N

L'application getscu implémente un SCU pour la classe de service Interrogation/Récupération. getscu prend en charge la fonctionnalité de récupération à l'aide du message C-GET. Elle envoie des clés de requête à un SCP et attend des réponses contenant des images ou d'autres objets DICOM envoyés via C-STORE. Comme l'exige le service DICOM, C-GET et les messages C-STORE associés sont traités sur la même association. Par conséquent, les objets ne peuvent être reçus que par getscu lui-même et ne peuvent pas être envoyés à un tiers (movescu serait l'outil a

pproprié pour
cette tâche).

NOTE

S

Chaque fichier fourni sur la ligne de commande sera envoyéau SCP comme partie d'une requête C-GET. Le fichier de requête doit être un jeu de données DICOM valide contenant la partie jeu de données d'un message C-GET-RQ. Le fichier de requête pourrait, par exemple, être créé avec l'utilitaire dump2dcm à partir d'un script comme le suivant

: 
# demander toutes les images pour le patient avec ID=PAT001
(0008,0052) CS [PATIENT]     # QueryRetrieveLevel
(0010,0020) LO [PAT001]      #
PatientID

Une autre possibilité est d'utiliser l'outil dcmodify pour créer un fichier à partir de zéro en utilisant l'option --create-file avec des appels successifs à l'option --insert. Des attributs individuels peuvent être modifiés ou complétés en utilisant l'option -k (ou --key). Par exemple la commande

: 
getscu -k "0010,0020=PAT002" caesar 5678 patqry.
dcm

envoyée au SCP caesar sur le port TCP/IP 5678, fera que tout attribut PatientID dans patqry.dcm aura la valeur 'PAT002'. Si un tel attribut est présent, il sera remplacé ; s'il est absent, il sera inséré. L'option -k peut être présente plusieurs fois. La partie valeur (après le '=') peut être absente, ce qui fera que l'attribut sera envoyé avec une longueur nulle. Il est également possible de spécifier des séquences, des éléments et des attributs imbriqués en utilisant l'option -k. Dans ces cas, une notation de « chemin » spéciale doit être utilisée. Les détails se trouvent dans la documentation de

dcmodify.

Si aucun fichier n'est spécifié sur la ligne de commande, la requête doit être spécifiée complètement avec une ou plusieurs options -k. Si plusieurs fichiers de requête sont fournis, getscu enverra plusieurs requêtes C-GET au

SCP.

Problèmes

connus

getscu est destiné à être utilisé comme outil de test pour les développeurs de logiciels DICOM. Le fichier de clés de requête doit être créé manuellement en se basant sur le contenu du

SCP.

C-GET n'est pas pris en charge par tous les SCP de requête/restauration. Le protocole C-MOVE qui est implémenté par l'outil movescu est plus couramment trouvé dans la

pratique.

L'application getscu ne fait aucune tentative pour empêcher les requêtes incorrectes. En particulier, les clés de requête d'une requête C-MOVE ne devraient contenir que l'

attribut QueryRetrieveLevel et un ou plusieurs des soi-disant « attributs de cl
é unique » (PatientID, StudyInstanceUID, SeriesInstanceUID et SOPInstanceUID).

JOURNALISATI

ON

Le niveau de sortie de journalisation des différentes outils en ligne de commande et des bibliothèques sous-jacentes peut être spécifié par l'utilisateur. Par défaut, seules les erreurs et les avertissements sont écrits sur le flux d'erreur standard. En utilisant l'option --verbose, des messages informatifs tels que les détails de traitement sont également rapportés. L'option --debug peut être utilisée pour obtenir plus de détails sur l'activité interne, par exemple à des fins de débogage. D'autres niveaux de journalisation peuvent être sélectionnés à l'aide de l'option --log-level. En mode --quiet, seules les erreurs fatales sont rapportées. En cas d'événements d'erreur aussi graves, l'application se terminera généralement. Pour plus de détails sur les différents niveaux de journalisation, voir la documentation du module

"oflog".

Si la sortie de journalisation doit être écrite dans un fichier (avec rotation optionnelle des journaux), dans syslog (Unix) ou dans le journal des événements (Windows), l'option --log-config peut être utilisée. Ce fichier de configuration permet également de diriger uniquement certains messages vers un flux de sortie particulier et de filtrer certains messages en fonction du module ou de l'application où ils sont générés. Un exemple de fichier de configuration est fourni dans <etcdir>/l

ogger
.cfg.

LIGNE DE

COMMANDE

Tous les outils en ligne de commande utilisent la notation suivante pour les paramètres : les crochets entourent les valeurs facultatives (0-1), trois points de suspension indiquent que plusieurs valeurs sont autorisées (1-n), une combinaison des deux signifie de 0 à n

valeurs.

Les options de ligne de commande sont distinguées des paramètres par un signe '+' ou '-' en tête, respectivement. Habituellement, l'ordre et la position des options de ligne de commande sont arbitraires (c'est-à-dire qu'elles peuvent apparaître n'importe où). Cependant, si des options sont mutuellement exclusives, la plus à droite est utilisée. Ce comportement est conforme aux règles d'évaluation standard des shells Unix

courants.

De plus, un ou plusieurs fichiers de commande peuvent être spécifiés en utilisant le signe '@' comme préfixe au nom de fichier (par exemple @command.txt). Un tel argument de commande est remplacé par le contenu du fichier texte correspondant (plusieurs espaces blancs sont traités comme un seul séparateur s'ils n'apparaissent pas entre deux guillemets) avant toute autre évaluation. Veuillez noter qu'un fichier de commande ne peut pas contenir un autre fichier de commande. Cette approche simple mais efficace permet de résumer des combinaisons courantes d'options/paramètres et évite des lignes de commande longues et déroutantes (un exemple est fourni dans le fichier <datadir>/du

mppat
.txt).

ENVIRONNEMEN

T

L' utilitaire getscu essaiera de charger les dictionnaires de données DICOM spécifiés dans la variable d'environnement DCMDICTPATH. Par défaut, c'est-à-dire si la variable d'environnement DCMDICTPATH n'est pas définie, le fichier <datadir>/dicom.dic sera chargé, sauf si le dictionnaire est intégré à l'application (par défaut sous Windows)

.

Le comportement par défaut devrait être préféré et la variable d'environnement DCMDICTPATH ne devrait être utilisée que lorsque des dictionnaires de données alternatifs sont nécessaires. La variable d'environnement DCMDICTPATH a le même format que la variable PATH du shell Unix en ce sens qu'un deux-points (":") sépare les entrées. Sur les systèmes Windows, un point-virgule (";") est utilisé comme séparateur. Le code du dictionnaire de données essaiera de charger chaque fichier spécifié dans la variable d'environnement DCMDICTPATH. C'est une erreur si aucun dic

tionnaire de données
ne peut être chargé.
