DESCRIPTIO

N

Les appels aux fonctions getdns nécessitent un contexte DNS, qui est un groupe de paramètres de l'API affectant la manière dont les appels DNS sont effectués. Pour la plupart des applications, un contexte par défaut est

suffisant.

Pour créer un nouveau contexte DNS, utilisez la fonction

:

getdns_return_t getdns_context_create (getdns_context_t *context, bool
set_from_os)

L'appel à getdns_context_create renvoie immédiatement un contexte qui peut être utilisé avec d'autres appels d'API ; ce contexte contient les valeurs par défaut de l'API. La plupart des applications voudront que set_from_os soit défini à

true.

Pour nettoyer le contexte, y compris le nettoyage de toutes les transactions en attente qui ont été appelées à l'aide de ce contexte, utilisez la fonction

:

void getdns_context_destroy (getdns_context_t
context)

Lorsque getdns_context_destroy() se termine, l'application sait que toutes les transactions en attente associées à ce contexte auront été appelées ; les rappels qui n'avaient pas été appelés avant que getdns_context_destroy() soit appelé le seront avec un callback_type de GETDNS_CALLBACK_CANCEL. getdns_context_destroy() se termine après que tout le nettoyage nécessaire a été effectué et que les rappels ont été

faits.

Si vous utilisez getdns de manière multi-thread, vous utilisez alors bien sûr la bibliothèque OpenSSL sous-jacente de manière multi-thread et la version de cette bibliothèque utilisée peut avoir des exigences à ce sujet. Vous devrez peut-être fournir une ou deux fonctions pour lui permettre de fonctionner correctement. Par exemple, avant d'appeler getdns_context_create(), vous devrez peut-être utiliser les fonctions openssl CRYPTO_set_id_callback et CRYPTO_set_locking_callback pour configurer le fonctionnement asynchrone (l'application appelle ces fonctions une fois pour l'initialisation). Openssl 1.0.0 ou ultérieur utilise la fonction CRYPTO_THREADID_set_callback

.

context Utilisé pour renvoyer le pointeur vers une structure opaque. L'appelant passe l'adresse d'un pointeur (déclaré : getdns_context *context ; passé sous la forme &context) qui sera rempli en résultat du retour de la fonction. Le résultat est un contexte nouvellement alloué et initialisé (s'il n'y a pas d'erreurs). Dans la fonction getdns_destroy_context, c'est le contexte dont la mémoire associée sera

libérée.

set_from_os Si set_from_os vaut 0, l'appelant doit fournir des serveurs de noms de transfert s'il fonctionne en mode stub. Si set_from_os vaut 1, les fichiers système sont utilisés pour initialiser le contexte. /etc/resolv.conf est utilisé pour remplir les transferts lorsque l'on fonctionne comme résolveur stub (seules les lignes "nameserver" sont reconnues). Si set_from_os vaut 1, les entrées de /etc/hosts sont préférées avant de recourir à une requête DNS. Les erreurs dans les fichiers système n'empêcheront pas la construction du

contexte.

userarg Dans le cas d'utilisation étendu, cet argument est passé inchangé à chacune des fonctions de gestion de mémoire chaque fois qu'elles sont

appelées.

malloc La fonction qui sera utilisée pour créer les dictionnaires de réponse (et les membres à l'intérieur des dictionnaires de réponse). Par défaut, le malloc du système est

utilisé.

realloc La fonction qui sera utilisée pour créer les dictionnaires de réponse (et les membres à l'intérieur des dictionnaires de réponse). Par défaut, le realloc du système est

utilisé.

free La fonction qui sera utilisée pour libérer le stockage des dictionnaires de réponse (et les

membres à l'intérieur des dictionnaires de rép
onse). Par défaut, le free du système est utilisé.

DESCRIPTION

(LONGUE)

De nombreux appels dans l'API DNS nécessitent un contexte DNS. Un contexte DNS contient les informations dont l'API a besoin pour traiter les appels DNS, telles que les emplacements des serveurs DNS amont, les ancres de confiance DNSSEC, etc. La structure interne du contexte DNS est opaque et peut être différente sur chaque système d'exploitation. Lorsqu'un contexte est passé à une fonction, il doit s'agir d'un contexte alloué ; le contexte ne doit pas être

NULL.

Une application typique utilisant cette API n'a pas besoin de savoir quoi que ce soit sur les contextes. Fondamentalement, l'application crée un contexte par défaut, l'utilise dans les fonctions qui nécessitent un contexte, puis le désalloue lorsqu'elle a terminé. La manipulation des contextes est disponible pour les programmes plus conscients du DNS, mais est peu susceptible d'intéresser les applications qui veulent simplement les résultats des recherches d'enregistrements A, AAAA, SRV et

PTR.

On s'attend à ce que les contextes dans les implémentations de l'API ne soient pas nécessairement sûrs pour les threads, mais qu'ils ne soient pas hostiles aux threads. Un contexte ne devrait pas être utilisé par plusieurs threads : créez un nouveau contexte pour l'utiliser sur un autre thread. Il est tout à fait acceptable qu'une application ait de nombreux contextes, et certaines applications gourmandes en DNS voudront certainement en avoir plusieurs même si l'application utilise un seul

thread.

Lorsque le contexte est utilisé dans l'API pour la première fois et que set_from_os vaut 1, l'API commence à remplacer certaines des valeurs par des valeurs du système d'exploitation, telles que celles qui seraient trouvées dans res_query(3), /etc/resolv.co

nf, etc., puis poursuit avec la nouvelle fonction. Certains utilisateurs avancés ne voudront pas que l'API change les valeurs vers les valeurs par défaut du système d'exploitation ; si set_from_os vaut 0, l'API ne fera aucune mise à jour des valeurs initiale
s basées sur les changements dans le système d'exploitation. Par exemple, cela peut être utile si l'API agit comme un résolveur stub qui utilise un résolveur récursif amont spécifique choisi par l'application, et non celui qui pourrait provenir de DHCP.
