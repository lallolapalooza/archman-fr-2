GETMSG(3P) Manuel du programmeur POSIX GETMSG(3P)

PROLOGUE

Cette page manuelle fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consultez la page man correspondante de Linux pour les détails du comportement de Linux), ou l'interface peut ne pas être implémentée sur Linux.

NOM

getmsg, getpmsg — recevoir le message suivant d'un fichier STREAMS (STREAMS)

SYNOPSIS

#include <stropts.h>
int getmsg(int fildes, struct strbuf *restrict ctlptr,
    struct strbuf *restrict dataptr, int *restrict flagsp);
int getpmsg(int fildes, struct strbuf *restrict ctlptr,
    struct strbuf *restrict dataptr, int *restrict bandp,
    int *restrict flagsp);

DESCRIPTION

La getmsg() fonction doit récupérer le contenu d'un message situé en tête de la file d'attente de lecture de la tête STREAM associée à un fichier STREAMS et placer le contenu dans un ou plusieurs tampons. Le message contient soit une partie de données, soit une partie de contrôle, ou les deux. La partie de données et la partie de contrôle du message doivent être placées dans des tampons séparés, comme décrit ci-dessous. La sémantique de chaque partie est définie par l'émetteur du message.

La getpmsg() fonction doit être équivalente à getmsg(), sauf qu'elle offre un contrôle plus fin sur la priorité des messages reçus. Sauf indication contraire, toutes les exigences sur getmsg() s'appliquent également à getpmsg().

L'argument fildes spécifie un descripteur de fichier référençant un fichier basé sur STREAMS.

Les arguments ctlptr et dataptr pointent chacun vers une structure strbuf , dans laquelle le membre buf pointe vers un tampon dans lequel les données ou les informations de contrôle doivent être placées, et le membre maxlen indique le nombre maximal d'octets que ce tampon peut contenir. Au retour, le membre len doit contenir le nombre d'octets de données ou d'informations de contrôle effectivement reçus. Le membre len doit être défini à 0 s'il y a une partie de contrôle ou de données de longueur nulle, et len doit être défini à -1 s'il n'y a pas de données ni d'informations de contrôle dans le message.

Lorsque getmsg() est appelé, flagsp doit pointer vers un entier qui indique le type de message que le processus est capable de recevoir. Cela est décrit plus en détail ci-dessous.

L'argument ctlptr est utilisé pour contenir la partie de contrôle du message, et dataptr est utilisé pour contenir la partie de données du message. Si ctlptr (ou dataptr) est un pointeur nul ou si le membre maxlen vaut -1, la partie de contrôle (ou de données) du message ne doit pas être traitée et doit être laissée sur la file d'attente de lecture de la tête STREAM, et si ctlptr (ou dataptr) n'est pas un pointeur nul, len doit être défini à -1. Si le membre maxlen est défini à 0 et qu'il y a une partie de contrôle (ou de données) de longueur nulle, cette partie de longueur nulle doit être retirée de la file d'attente de lecture et len doit être défini à 0. Si le membre maxlen est défini à 0 et qu'il y a plus de 0 octet d'informations de contrôle (ou de données), ces informations doivent être laissées sur la file d'attente de lecture et len doit être défini à 0. Si le membre maxlen dans ctlptr (ou dataptr) est inférieur à la partie de contrôle (ou de données) du message, maxlen octets doivent être récupérés. Dans ce cas, le reste du message doit être laissé sur la file d'attente de lecture de la tête STREAM et une valeur de retour non nulle doit être fournie.

Par défaut, getmsg() doit traiter le premier message disponible sur la file d'attente de lecture de la tête STREAM. Cependant, un processus peut choisir de récupérer uniquement les messages de haute priorité en définissant l'entier pointé par flagsp à RS_HIPRI. Dans ce cas, getmsg() ne doit traiter le message suivant que s'il s'agit d'un message de haute priorité. Lorsque l'entier pointé par flagsp vaut 0, tout message disponible doit être récupéré. Dans ce cas, au retour, l'entier pointé par flagsp doit être défini à RS_HIPRI si un message de haute priorité a été récupéré, ou à 0 sinon.

Pour getpmsg(), les indicateurs sont différents. L'argument flagsp pointe vers un masque de bits avec les indicateurs mutuellement exclusifs suivants définis : MSG_HIPRI, MSG_BAND et MSG_ANY. Comme getmsg(), getpmsg() doit traiter le premier message disponible sur la file d'attente de lecture de la tête STREAM. Un processus peut choisir de récupérer uniquement les messages de haute priorité en définissant l'entier pointé par flagsp à MSG_HIPRI et l'entier pointé par bandp à 0. Dans ce cas, getpmsg() ne doit traiter le message suivant que s'il s'agit d'un message de haute priorité. De manière similaire, un processus peut choisir de récupérer un message d'une bande de priorité particulière en définissant l'entier pointé par flagsp à MSG_BAND et l'entier pointé par bandp à la bande de priorité d'intérêt. Dans ce cas, getpmsg() ne doit traiter le message suivant que s'il est dans une bande de priorité égale à, ou supérieure à, l'entier pointé par bandp, ou s'il s'agit d'un message de haute priorité. Si un processus veut obtenir le premier message de la file d'attente, l'entier pointé par flagsp doit être défini à MSG_ANY et l'entier pointé par bandp doit être défini à 0. Au retour, si le message récupéré était un message de haute priorité, l'entier pointé par flagsp doit être défini à MSG_HIPRI et l'entier pointé par bandp doit être défini à 0. Sinon, l'entier pointé par flagsp doit être défini à MSG_BAND et l'entier pointé par bandp doit être défini à la bande de priorité du message.

Si O_NONBLOCK n'est pas défini, getmsg() et getpmsg() doivent bloquer jusqu'à ce qu'un message du type spécifié par flagsp soit disponible en tête de la file d'attente de lecture de la tête STREAM. Si O_NONBLOCK est défini et qu'un message du type spécifié n'est pas présent en tête de la file d'attente de lecture, getmsg() et getpmsg() doivent échouer et définir errno à [EAGAIN].

Si un déconnexion (hangup) se produit sur le STREAM à partir duquel les messages sont récupérés, getmsg() et getpmsg() doivent continuer à fonctionner normalement, comme décrit ci-dessus, jusqu'à ce que la file d'attente de lecture de la tête STREAM soit vide. Ensuite, ils doivent retourner 0 dans les membres len de ctlptr et dataptr.

VALEUR DE RETOUR

Lors de l'achèvement réussi, getmsg() et getpmsg() doivent retourner une valeur non négative. Une valeur de 0 indique qu'un message complet a été lu avec succès. Une valeur de retour MORECTL indique que plus d'informations de contrôle attendent d'être récupérées. Une valeur de retour MOREDATA indique que plus de données attendent d'être récupérées. Une valeur de retour correspondant au OU logique bit à bit de MORECTL et MOREDATA indique que les deux types d'informations restent. Les appels suivants à getmsg() et getpmsg() doivent récupérer le reste du message. Cependant, si un message de priorité supérieure est arrivé sur la file d'attente de lecture de la tête STREAM, l'appel suivant à getmsg() ou getpmsg() doit récupérer ce message de priorité supérieure avant de récupérer le reste du message précédent.

Si la partie de contrôle de haute priorité du message est consommée, le message doit être remis sur la file d'attente comme un message normal de bande 0. Les appels suivants à getmsg() et getpmsg() doivent récupérer le reste du message. Si, cependant, un message de priorité arrive ou existe déjà sur la tête STREAM, l'appel suivant à getmsg() ou getpmsg() doit récupérer le message de priorité supérieure avant de récupérer le reste du message qui a été remis.

En cas d'échec, getmsg() et getpmsg() doivent retourner -1 et définir errno pour indiquer l'erreur.

ERREURS

Les fonctions getmsg() et getpmsg() doivent échouer si :

EAGAIN
L'indicateur O_NONBLOCK est défini et aucun message n'est disponible.
EBADF
L'argument fildes n'est pas un descripteur de fichier valide ouvert en lecture.
EBADMSG
Le message en file d'attente à lire n'est pas valide pour getmsg() ou getpmsg() ou un descripteur de fichier en attente est à la tête du STREAM.
EINTR
Un signal a été capturé pendant getmsg() ou getpmsg().
EINVAL
Une valeur illégale a été spécifiée par flagsp, ou le STREAM ou le multiplexeur référencé par fildes est lié (directement ou indirectement) en aval d'un multiplexeur.>
ENOSTR
Un flux n'est pas associé à fildes.

De plus, getmsg() et getpmsg() échoueront si la tête du flux avait traité une erreur asynchrone avant l'appel. Dans ce cas, la valeur de errno ne reflète pas le résultat de getmsg() ou getpmsg() mais reflète l'erreur précédente.

EXEMPLES

Obtenir un message quelconque

Dans l'exemple suivant, la valeur de fd est supposée faire référence à un fichier STREAMS ouvert. L'appel à getmsg() récupère tout message disponible sur la file d'attente de lecture de la tête de flux associée, renvoyant des informations de contrôle et de données aux tampons pointés par ctrlbuf et databuf, respectivement.

#include <stropts.h>
...
int fd;
char ctrlbuf[128];
char databuf[512];
struct strbuf ctrl;
struct strbuf data;
int flags = 0;
int ret;
ctrl.buf = ctrlbuf;
ctrl.maxlen = sizeof(ctrlbuf);
data.buf = databuf;
data.maxlen = sizeof(databuf);
ret = getmsg (fd, &ctrl, &data, &flags);

Obtenir le premier message de la file

Dans l'exemple suivant, l'appel à getpmsg() récupère le premier message disponible sur la file d'attente de lecture de la tête de flux associée.

#include <stropts.h>
...
int fd;
char ctrlbuf[128];
char databuf[512];
struct strbuf ctrl;
struct strbuf data;
int band = 0;
int flags = MSG_ANY;
int ret;
ctrl.buf = ctrlbuf;
ctrl.maxlen = sizeof(ctrlbuf);
data.buf = databuf;
data.maxlen = sizeof(databuf);
ret = getpmsg (fd, &ctrl, &data, &band, &flags);
