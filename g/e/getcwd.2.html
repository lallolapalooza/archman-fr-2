getcwd(3) Manuel des fonctions de bibliothèque getcwd(3)

NOM

getcwd, getwd, get_current_dir_name - obtenir le répertoire de travail actuel

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNOPSIS

#include <unistd.h>
char *getcwd(char *buf, size_t size);
char *get_current_dir_name(void);
[[deprecated]] char *getwd(char buf[PATH_MAX]);
Macros de test de fonctionnalités pour glibc (voir feature_test_macros(7)):

get_current_dir_name():

    _GNU_SOURCE

getwd():

    Depuis glibc 2.12:
        (_XOPEN_SOURCE >= 500) && ! (_POSIX_C_SOURCE >= 200809L)
            || /* glibc >= 2.19: */ _DEFAULT_SOURCE
            || /* glibc <= 2.19: */ _BSD_SOURCE
    Avant glibc 2.12:
        _BSD_SOURCE || _XOPEN_SOURCE >= 500

DESCRIPTION

Ces fonctions retournent une chaîne terminée par un caractère nul contenant un chemin absolu qui est le répertoire de travail actuel du processus appelant. Le chemin est retourné comme résultat de la fonction et via l'argument buf, si présent.

La fonction getcwd() copie un chemin absolu du répertoire de travail actuel dans le tableau pointé par buf, qui a une longueur de size.

Si la longueur du chemin absolu du répertoire de travail actuel, y compris l'octet nul de terminaison, dépasse size octets, NULL est retourné, et errno est défini à ERANGE ; une application doit vérifier cette erreur et allouer un tampon plus grand si nécessaire.

En tant qu'extension à la norme POSIX.1-2001, getcwd() de glibc alloue le tampon dynamiquement en utilisant malloc(3) si buf est NULL. Dans ce cas, le tampon alloué a la longueur size sauf si size est zéro, auquel cas buf est alloué aussi grand que nécessaire. L'appelant doit free(3) le tampon retourné.

get_current_dir_name() utilisera malloc(3) pour allouer un tableau suffisamment grand pour contenir le chemin absolu du répertoire de travail actuel. Si la variable d'environnement PWD est définie et que sa valeur est correcte, alors cette valeur sera retournée. L'appelant doit free(3) le tampon retourné.

getwd() n'utilise pas malloc(3) de mémoire. L'argument buf doit être un pointeur vers un tableau d'au moins PATH_MAX octets. Si la longueur du chemin absolu du répertoire de travail actuel, y compris l'octet nul de terminaison, dépasse PATH_MAX octets, NULL est retourné et errno est défini à ENAMETOOLONG. (Notez que sur certains systèmes, PATH_MAX peut ne pas être une constante de compilation ; de plus, sa valeur peut dépendre du système de fichiers, voir pathconf(3).) Pour des raisons de portabilité et de sécurité, l'utilisation de getwd() est déconseillée.

VALEUR DE RETOUR

En cas de succès, ces fonctions retournent un pointeur vers une chaîne contenant le chemin du répertoire de travail actuel. Dans le cas de getcwd() et getwd(), c'est la même valeur que buf.

En cas d'échec, ces fonctions retournent NULL, et errno est défini pour indiquer l'erreur. Le contenu du tableau pointé par buf est indéfini en cas d'erreur.

ERREURS

EACCES
La permission de lire ou de rechercher un composant du nom de fichier a été refusée.
EFAULT
buf pointe vers une adresse invalide.
EINVAL
L'argument size est zéro et buf n'est pas un pointeur nul.
EINVAL
getwd(): buf est NULL.
ENAMETOOLONG
getwd(): La taille de la chaîne de chemin absolu terminée par un caractère nul dépasse PATH_MAX octets.
ENOENT
Le répertoire de travail actuel a été désinstallé.
ENOMEM
Pas assez de mémoire.
ERANGE
L'argument size est inférieur à la longueur du chemin absolu du répertoire de travail, y compris l'octet nul de terminaison. Vous devez allouer un tableau plus grand et réessayer.

VERSIONS

POSIX.1-2001 laisse le comportement de getcwd() non spécifié si buf est NULL.

POSIX.1-2001 ne définit aucune erreur pour getwd().

VERSIONS

Différences entre la bibliothèque C et le noyau

Sous Linux, le noyau fournit un appel système getcwd(), que les fonctions décrites dans cette page utiliseront si possible. L'appel système prend les mêmes arguments que la fonction de bibliothèque du même nom, mais est limité à retourner au maximum PATH_MAX octets. (Avant Linux 3.12, la limite de la taille du chemin retourné était la taille de page du système. Sur de nombreuses architectures, PATH_MAX et la taille de page du système sont tous deux de 4096 octets, mais quelques architectures ont une taille de page plus grande.) Si la longueur du chemin du répertoire de travail actuel dépasse cette limite, alors l'appel système échoue avec l'erreur ENAMETOOLONG. Dans ce cas, les fonctions de bibliothèque reviennent à une implémentation alternative (plus lente) qui retourne le chemin complet.

Suite à un changement dans Linux 2.6.36, le chemin retourné par l'appel système getcwd() sera préfixé par la chaîne "(unreachable)" si le répertoire courant n'est pas sous la racine du processus courant (par exemple, parce que le processus a défini une nouvelle racine de système de fichiers à l'aide de chroot(2) sans changer son répertoire courant vers la nouvelle racine). Un tel comportement peut aussi être causé par un utilisateur non privilégié en changeant le répertoire courant dans un autre espace de noms de montage. Lors du traitement de chemins provenant de sources non fiables, les appelants des fonctions décrites dans cette page (avant glibc 2.27) ou l'appel système brut getcwd() devraient envisager de vérifier si le chemin retourné commence par '/' ou '(' pour éviter de mal interpréter un chemin inaccessible comme un chemin relatif.

HISTORIQUE

getcwd()
POSIX.1-2001.
getwd()
POSIX.1-2001, mais marqué LEGACY. Supprimé dans POSIX.1-2008. Utiliser getcwd() à la place.

Sous Linux, ces fonctions utilisent l'appel système getcwd() (disponible depuis Linux 2.1.92). Sur les anciens systèmes, elles interrogeaient /proc/self/cwd. Si le système de fichiers d'appel système et le système de fichiers proc sont absents, une implémentation générique est appelée. Ce n'est que dans ce cas que ces appels peuvent échouer sous Linux avec EACCES

NOTES

Ces fonctions sont souvent utilisées pour enregistrer l'emplacement du répertoire de travail courant afin de pouvoir y revenir plus tard. Ouvrir le répertoire courant (".") et appeler fchdir(2) pour revenir est généralement une alternative plus rapide et plus fiable lorsque suffisamment de descripteurs de fichiers sont disponibles, en particulier sur les plateformes autres que Linux.

BUGS

Depuis la modification du noyau Linux 2.6.36 qui a ajouté "(unreachable)" dans les circonstances décrites ci-dessus, l'implémentation glibc de getcwd() n'a pas été conforme à POSIX et a retourné un chemin relatif alors que le contrat de l'API exige un chemin absolu. Avec glibc 2.27 et plus tard, cela est corrigé ; appeler getcwd() à partir d'un tel chemin résultera maintenant en une erreur avec ENOENT.
