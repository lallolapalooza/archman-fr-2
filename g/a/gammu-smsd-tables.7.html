gammu-smsd-tables - description des tables pour les backends de base de données de

gammu-smsd(1)

Les backends eux-mêmes sont décrits dans leurs sections, ce document décrit la structure générale de la base de données et les tables

requises.

Plusieurs démons SMS peuvent partager une base de données unique. Si vous ne spécifiez pas PhoneID dans leur configuration, tous sont traités de la même manière et vous n'avez aucune garantie sur celui qui enverra le message sortant. Si vous configurez PhoneID et l'utilisez lors de l'insertion du message dans la table outbox (gammu-smsd-inject fait cela), chaque démon SMS

aura une file d'attente outbox s
éparée. Voir aussi smsd-multi.

SQL

Pour envoyer un message, vous pouvez soit utiliser gammu-smsd-inject, qui fait toute la magie pour vous, soit insérer le message manuellement. L'exemple le plus simple est un message texte court

:

Injection d'un message long à l'aide de

SQL

L'insertion de messages multiparties est un peu plus délicate, vous devez également construire l'en-tête UDH et le stocker sous forme hexadécimale dans le champ UDH. À moins que vous n'ayez une bonne raison de le faire manuellement, utilisez gammu-smsd-inject, la bibliothèque C (SMSD_InjectSMS()) ou la bibliothèque Python (gammu.smsd.SMSD.InjectSMS())

.

Pour un message texte long, l'UDH commence par 050003 suivi d'un octet servant de référence de message (vous pouvez y mettre n'importe quelle valeur hexadécimale, mais elle devrait être différente pour chaque message, D3 dans l'exemple suivant), d'un octet pour le nombre de messages (02 dans l'exemple, il devrait être unique pour chaque message que vous envoyez au même numéro de téléphone) et d'un octet pour le numéro du message courant (01 pour le premier message, 02 pour le deuxième, etc.)

.

Dans la plupart des cas, le message multipartie doit être de classe

1.

:
