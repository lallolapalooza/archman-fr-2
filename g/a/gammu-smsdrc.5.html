StatusFrequency
Le nombre de secondes entre l'actualisation du statut du téléphone (batterie, signal) stocké dans la mémoire partagée et potentiellement dans les backends de service. Utilisez 0 pour désactiver.

Vous pourriez vouloir augmenter cette valeur pour un débit plus élevé.

La valeur par défaut est 60.

LoopSleep
Le nombre de secondes pendant lesquelles SMSD dormira avant de vérifier une activité. Veuillez noter qu'en définissant cette valeur à plus de 1, cela aura des effets sur d'autres configurations basées sur le temps, car elles seront effectivement arrondies à des multiples de cette valeur.

Définir cette valeur à 0 désactive le sommeil. Veuillez noter que cela pourrait faire que Gammu consomme beaucoup de puissance CPU car il s'agira effectivement d'une boucle active.

Ce sommeil n'est utilisé que si la boucle principale (envoi et réception de messages) prend moins de temps que la durée définie. Par exemple, si vous définissez LoopSleep à 5 secondes et que l'envoi de messages prend 10 secondes, aucun sommeil ne sera effectué lors de l'itération d'envoi de messages. De plus, le temps de sommeil est réduit par le temps déjà traité.

La valeur par défaut est 1.

MultipartTimeout
Le nombre de secondes pendant lesquelles SMSD attendra toutes les parties d'un message multipart. Si toutes les parties n'arrivent pas à temps, les parties seront traitées comme des messages distincts.

La valeur par défaut est 600 (10 minutes).

CheckSecurity
Si le téléphone doit vérifier s'il souhaite entrer un code PIN.

La valeur par défaut est 1 (activé).

HangupCalls
Nouveau dans la version 1.34.0.

Si les appels entrants doivent être raccrochés automatiquement.

La valeur par défaut est 0 (désactivé).

CheckBattery
Si l'état de la batterie du téléphone doit être vérifié périodiquement.

La valeur par défaut est 1 (activé).

CheckSignal
Si le niveau du signal doit être vérifié périodiquement.

La valeur par défaut est 1 (activé).

CheckNetwork
Nouveau dans la version 1.37.90.

Si l'état du réseau doit être vérifié périodiquement.

Si le téléphone n'est pas rapporté comme étant sur le réseau, SMSD essaie de l'allumer.

La valeur par défaut est 1 (activé).

ResetFrequency
Le nombre de secondes entre chaque réinitialisation logicielle préventive afin de minimiser les cas de téléphones bloqués, par exemple, les Nokia 5110 se figent parfois dans un état où seule la suppression de la batterie le rendra à nouveau fonctionnel.

La valeur par défaut est 0 (non utilisé).

HardResetFrequency
Nouveau dans la version 1.28.92.

Pour certains téléphones, une réinitialisation matérielle signifie la suppression de toutes les données qu'ils contiennent. Utilisez ResetFrequency à la place, sauf si vous savez ce que vous faites.

Le nombre de secondes entre chaque réinitialisation matérielle préventive afin de minimiser les cas de téléphones bloqués.

La valeur par défaut est 0 (non utilisé).

DeliveryReportDelay
Délai en secondes pendant lequel le rapport de livraison est encore considéré comme valide. Ceci dépend du dysfonctionnement de votre réseau (le rapport de livraison devrait avoir le même horodatage que le message envoyé). Augmentez cette valeur si les rapports de livraison ne correspondent pas aux messages envoyés.

La valeur par défaut est 600 (10 minutes).

PhoneID
Chaîne d'informations sur le téléphone utilisé pour l'envoi/la réception. Cela peut être utile si vous souhaitez exécuter plusieurs démons SMS (voir Modems multiples).

Lorsque vous définissez PhoneID, tous les messages (y compris ceux injectés) seront marqués par cette chaîne (stockée en tant qu'ID d'expéditeur dans la base de données) et cela permet à plusieurs démons SMS de partager une seule base de données.

Le démon SMSD dans ce cas n'enverra les messages de la boîte d'envoi qu'avec un ID d'expéditeur correspondant ou vide.

Cette option n'a en fait aucun effet avec gammu-smsd-files.

SMSC
Nouveau dans la version 1.36.2.

Numéro SMSC à utiliser pour envoyer des messages si non spécifié dans le message (voir les options de gammu-smsd-inject).

Dans la plupart des cas, vous n'avez pas besoin de ce réglage car Gammu essaie de lire le SMSC correct depuis le téléphone, mais cela échoue parfois (essayez gammu getsmsc).

RunOnReceive
Exécute un programme après la réception d'un message.

Ce paramètre est exécuté via le shell, vous devrez donc peut-être échapper certains caractères spéciaux et vous pouvez inclure n'importe quel nombre de paramètres. De plus, des paramètres avec les identifiants des messages reçus sont ajoutés à la ligne de commande. Les identifiants dépendent du backend de service utilisé, il s'agit généralement de l'ID de la ligne insérée pour les backends de base de données ou du nom du fichier pour les backends basés sur des fichiers.

Gammu SMSD attend que le script se termine. Si vous faites quelque chose qui prend du temps, SMSD ne recevra pas de nouveaux messages. Cependant, pour limiter les problèmes causés par cette situation, le temps d'attente est limité à deux minutes. Après ce délai, SMSD continuera son fonctionnement normal et pourrait exécuter à nouveau votre script.

Le processus dispose de nombreuses informations sur le message reçu dans l'environnement, consultez gammu-smsd-run pour plus de détails.

RunOnFailure
Nouveau dans la version 1.28.93.

Exécute un programme en cas d'échec.

Cela peut être utilisé pour réagir de manière proactive à certains échecs ou pour détecter interactivement l'échec de l'envoi d'un message.

Le programme recevra un paramètre optionnel, qui peut actuellement être INIT (ce qui signifie un échec lors de l'initialisation du téléphone) ou l'ID du message, qui indiquerait une erreur lors de l'envoi du message.

NOTE :

L'environnement avec le message (comme dans RunOnReceive) n'est pas passé à la commande.
RunOnSent
Nouveau dans la version 1.36.4.

Exécute un programme après l'envoi d'un message.

Le programme recevra en paramètre optionnel un identifiant de message et l'environnement avec les détails du message comme décrit dans gammu-smsd-run.

RunOnIncomingCall
Nouveau dans la version 1.38.5.

Exécute un programme après avoir annulé un appel entrant.

Le programme recevra un paramètre avec le numéro de téléphone de l'appel. Cela nécessite que HangupCalls soit activé.

OPTIONS DES BACKENDS DE BASE DE DONNÉES

Tous les backends DBI, ODBC, MYSQL et PGSQL (voir gammu-smsd-mysql, gammu-smsd-odbc, gammu-smsd-pgsql, gammu-smsd-dbi pour leur documentation) prennent en charge les mêmes options pour configurer la connexion à une base de données :

User
Nom d'utilisateur utilisé pour la connexion à une base de données.
Password
Mot de passe utilisé pour la connexion à une base de données.
Host
Adresse du serveur de base de données. Elle peut également contenir le port ou le chemin du socket après un point-virgule, par exemple localhost:/path/to/socket ou 192.168.1.1:8000.

Pour ODBC, ceci est utilisé comme nom de la source de données.

NOTE :

Certains serveurs de bases de données différencient l'utilisation de localhost (pour utiliser le socket local) et 127.0.0.1 (pour utiliser la connexion TCP/IP locale). Assurez-vous que vos paramètres SMSD correspondent à ceux du serveur de base de données.

Nouveau depuis la version 1.28.92.

PC
Obsolète depuis la version 1.28.92 : Veuillez utiliser Host à la place.

Synonyme de Host, conservé pour la compatibilité ascendante.

Database
Nom de la base de données (ou du schéma) à utiliser et où SMSD peut trouver ses tables.

Veuillez noter que vous devez créer les tables dans cette base de données avant d'utiliser gammu-smsd. Les fichiers SQL pour créer les tables nécessaires sont inclus dans la documentation des backends de base de données individuels : gammu-smsd-mysql, gammu-smsd-odbc, gammu-smsd-pgsql, gammu-smsd-dbi

SkipSMSCNumber
Lorsque vous envoyez des SMS depuis certains centres SMS, vous pouvez recevoir des rapports de livraison provenant d'un autre numéro de centre SMS. Vous pouvez définir ici le numéro de ce centre SMS que vous utilisez, et Gammu ne vérifiera pas son numéro lors de l'attribution des rapports aux SMS envoyés.
Driver
Dialecte SQL à utiliser. Ceci est particulièrement utile avec gammu-smsd-odbc où SMSD ne sait pas à quel serveur il communique réellement.

Valeurs possibles :

  • mysql - MySQL
  • pgsql - PostgreSQL
  • sqlite - SQLite
  • mssql - Microsoft SQL Server
  • sybase - Sybase
  • access - Microsoft Access
  • oracle - Oracle
  • odbc - ODBC générique

Nouveau depuis la version 1.28.93.

VOIR AUSSI :

Vous pouvez également personnaliser complètement les requêtes SQL utilisées, comme décrit dans Requêtes SQL.
DriversPath
Chemin où sont stockés les pilotes DBI, il n'est généralement pas nécessaire de le définir si vos pilotes sont correctement installés.
DBDir
Répertoire de base de données pour certains pilotes DBI (actuellement seulement sqlite). Définissez ici le chemin où les fichiers de base de données sqlite sont stockés.

Options du backend Fichiers

Le backend FILES accepte les options de configuration suivantes. Voir gammu-smsd-files pour une description plus détaillée du backend de service. Veuillez noter que tous les chemins doivent contenir un séparateur de chemin final (/ sur les systèmes Unix) :

InboxPath
Où sont stockés les SMS reçus.

Par défaut : répertoire courant.

OutboxPath
Où doivent être placés les SMS à envoyer.

Par défaut : répertoire courant.

SentSMSPath
Où sont placés les SMS transmis. Si ce chemin est le même que OutboxPath, les messages transmis sont supprimés.

Par défaut : suppression des messages transmis.

ErrorSMSPath
Où sont placés les SMS ayant rencontré une erreur lors de la transmission.

Par défaut : identique à SentSMSPath.

InboxFormat
Le format dans lequel le SMS sera stocké : detail, unicode, standard.

detail
Format utilisé pour la sauvegarde des messages par gammu, voir gammu-smsbackup.
unicode
Texte du message stocké en unicode (UTF-16)
standard
Texte du message stocké dans le jeu de caractères système

Les paramètres standard et unicode ne s'appliquent pas aux messages 8 bits, qui sont toujours écrits bruts tels qu'ils sont reçus avec l'extension .bin.

Par défaut : unicode.

NOTE :

En format detail, toutes les parties du message sont stockées dans un seul fichier, pour tous les autres, chaque partie du message est enregistrée séparément.
OutboxFormat
Le format dans lequel les messages créés par gammu-smsd-inject seront stockés, il accepte les mêmes valeurs que InboxFormat.

Par défaut : detail si Gammu est compilé avec les fonctions de sauvegarde, sinon unicode.

TransmitFormat
Le format pour la transmission du SMS : auto, unicode, 7bit.

Cette option n'est utilisée que si OutboxFormat n'est pas défini sur detail. Dans ce cas, le codage spécifié dans le message est utilisé (vous pouvez le spécifier à gammu-smsd-inject).

Par défaut : auto.

FILTRAGE DES MESSAGES

SMSD permet de traiter uniquement un sous-ensemble limité des messages entrants. Vous pouvez définir des filtres pour le numéro de l'expéditeur dans les sections [include_numbers] et [exclude_numbers] ou en utilisant les directives IncludeNumbersFile et ExcludeNumbersFile.

Si la section [include_numbers] existe, toutes les valeurs (les clés sont ignorées) sont utilisées comme numéros de téléphone autorisés et aucun autre message n'est traité. D'autre part, dans [exclude_numbers], vous pouvez spécifier les numéros que vous souhaitez ignorer.

Les listes des deux sources sont fusionnées. S'il y a un numéro dans la liste d'inclusion, seule la liste d'inclusion est utilisée et seuls les messages de cette liste sont acceptés. Si la liste d'inclusion est vide, la liste d'exclusion peut être utilisée pour ignorer les messages provenant de certains numéros. Si les deux listes sont vides, tous les messages sont acceptés.

Des règles de filtrage similaires peuvent être utilisées pour le filtrage des numéros de centre SMS, elles utilisent simplement un ensemble différent d'options de configuration - les sections [include_smsc] et [exclude_smsc] ou les directives IncludeSMSCFile et ExcludeSMSCFile.

EXEMPLES

Un exemple plus complet est disponible dans la documentation de Gammu. Veuillez noter que pour simplifier, les exemples suivants n'incluent pas la section [gammu], vous pouvez consulter gammurc pour quelques exemples de ce à quoi cela peut ressembler.

Service Fichiers

Le fichier de configuration SMSD pour le backend FILES pourrait ressembler à ceci :

[smsd]
Service = files
PIN = 1234
LogFile = syslog
InboxPath = /var/spool/sms/inbox/
OutboxPath = /var/spool/sms/outbox/
SentSMSPath = /var/spool/sms/sent/
ErrorSMSPath = /var/spool/sms/error/

Service MySQL

Si vous souhaitez utiliser le backend MYSQL, vous aurez besoin de quelque chose comme ceci :

[smsd]
Service = sql
Driver = native_mysql
PIN = 1234
LogFile = syslog
User = smsd
Password = smsd
PC = localhost
Database = smsd

DBI service utilisant SQLite

Pour le backend gammu-smsd-dbi, dans ce cas particulier SQLite :

[smsd]
Service = sql
Driver = sqlite3
DBDir = /var/lib/sqlite3
Database = smsd.db

ODBC service utilisant MySQL

Pour le backend gammu-smsd-odbc, dans ce cas particulier en utilisant le DSN serveur smsd :

[smsd]
Service = sql
Driver = odbc
Host = smsd

La définition du DSN (dans ~/.odbc.ini sur UNIX) pour utiliser le serveur MySQL ressemblerait à ceci :

[smsd]
Description         = MySQL
Driver              = MySQL
Server              = 127.0.0.1
Database            = smsd
Port                =
Socket              =
Option              =
Stmt                =
[smsdsuse]
Driver              = MySQL ODBC 3.51.27r695 Driver
DATABASE            = smsd
SERVER              = 127.0.0.1

Filtrage des numéros

Traiter uniquement les messages provenant du numéro 123456 :

[include_numbers]
number1 = 123456

Ne pas traiter les messages provenant du numéro maléfique 666 :

[exclude_numbers]
number1 = 666

Débogage

Activation du débogage :

[smsd]
debuglevel = 255
logfile = smsd.log

Modems multiples

Vous pouvez exécuter n'importe quel nombre d'instances SMSD et elles peuvent même partager la même base de données backend. Pour router les messages, vous devez définir un PhoneID différent pour chaque instance et définir la colonne SenderID dans la table outbox.

L'exemple suivant montre la configuration pour deux modems, mais vous pouvez avoir n'importe quel nombre d'instances SMSD. La seule limitation est la performance de votre matériel, en particulier si tous les modems sont connectés via USB.

Configuration pour le premier SMSD :

[gammu]
device = /dev/ttyACM0
connection = at
[smsd]
Service = sql
Driver = native_mysql
PIN = 1234
LogFile = syslog
User = smsd
Password = smsd
PC = localhost
Database = smsd
PhoneID = first

Configuration pour le second SMSD :

[gammu]
device = /dev/ttyACM1
connection = at
[smsd]
Service = sql
Driver = native_mysql
PIN = 1234
LogFile = syslog
User = smsd
Password = smsd
PC = localhost
Database = smsd
PhoneID = second

Vous pouvez ensuite démarrer deux instances séparées de SMSD :

gammu-smsd -c /chemin/vers/first-smsdrc
gammu-smsd -c /chemin/vers/second-smsdrc
