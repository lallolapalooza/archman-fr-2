GDNSD-PLUGIN-SIMPLEFO(8) gdnsd GDNSD-PLUGIN-SIMPLEFO(8)

NOM

gdnsd-plugin-simplefo - plugin gdnsd pour la bascule d'adresse primaire->secondaire simple

SYNTAXE

Fragment de configuration gdnsd d'exemple utilisant ce plugin :

plugins => {
  simplefo => {
    service_types => [ www ],
    pubwww => {
      primary => 192.0.2.1
      secondary => 192.0.2.100
    }
    www6 => {
      primary => 2001:DB8::1
      secondary => 2001:DB8::100
    }
    mixed => {
      service_types => [ www, xmpp ]
      addrs_v4 => {
        primary => 192.0.2.1
        secondary => 192.0.2.100
      }
      addrs_v6 => {
        service_types => up
        primary => 2001:DB8::1
        secondary => 2001:DB8::100
      }
    }
  }
}

RR de fichier de zone d'exemple :

www 180 DYNA simplefo!pubwww
www6 180 DYNA simplefo!www6
mix 180 DYNA simplefo!mixed

DESCRIPTION

gdnsd-plugin-simplefo est conçu pour effectuer une bascule simple actif/passif entre une adresse primaire et une adresse secondaire. L'état des adresses est vérifié à l'aide de la surveillance standard des "service_types" de gdnsd. Si vous avez besoin d'une liste de bascule de plus de deux adresses, le plugin "metafo" est plus approprié.

CONFIGURATION DE PLUGIN AU NIVEAU SUPÉRIEUR

Au niveau supérieur de la stanza de configuration du plugin, le paramètre spécial "service_types" est supporté. Ceci définit les "service_types" par ressource par défaut pour toutes les ressources. Le "service_types" par défaut est "[ up ]", ce qui les définit tous statiquement sur "UP".

Le reste des entrées de hachage au niveau supérieur sont les noms des ressources que vous définissez. Chaque ressource reçoit sa propre stanza de configuration de hachage pour contenir les informations d'adresse spécifiques à la ressource.

CONFIGURATION DE RESSOURCE

Au sein d'une ressource, "service_types" est à nouveau supporté, pour définir le ou les types de service surveillés pour cette ressource spécifique.

Si "addrs_v4" est défini, il doit s'agir d'un hachage contenant deux clés : "primary" et "secondary", chacune ayant une valeur d'adresse IPv4 sous forme de chaîne.

De même, si "addrs_v6" est défini, il doit s'agir d'un hachage contenant deux clés : "primary" et "secondary", chacune ayant une valeur d'adresse IPv6 sous forme de chaîne.

Si aucun de ces deux sous-stanzas n'est défini, vous devez définir une paire unique d'adresses "primary" et "secondary" pour l'ensemble de la ressource. Celles-ci peuvent être de n'importe quelle famille d'adresses, tant qu'elles sont toutes deux de la même famille.

Lorsque "addrs_v4" et/ou "addrs_v6" sont utilisés, "service_types" peut également être remplacé à l'intérieur de chacun, pour un comportement différent par famille d'adresses (par exemple, forcer un protocole toujours actif/inactif).

MÉCANIQUES OPÉRATIONNELLES

Pour chaque famille d'adresses pour laquelle vous avez fourni des données, la logique suivante est appliquée indépendamment :

  • Tout d'abord, l'état surveillé le plus mauvais de toutes les vérifications "service_types" pour l'adresse primaire est obtenu. Si cet état est "UP", l'adresse primaire est utilisée.
  • Si l'adresse primaire était "DOWN", l'adresse secondaire est vérifiée : Si la secondaire est "UP", elle sera utilisée. Si la secondaire est également "DOWN", alors la primaire est utilisée.
  • Dans tout cas autre que l'adresse primaire étant exactement "UP", le TTL de la réponse RR-set du fichier de zone sera divisé par deux pour les deux familles d'adresses.

Si les deux "primary" et "secondary" étaient "DOWN" pour l'une ou l'autre famille d'adresses, ce plugin signalera une défaillance totale de la ressource à tout module amont (geoip ou metafo). La réduction du TTL ne se produit qu'une seule fois pour tous les RR d'adresses, même si les deux familles avaient une primaire non "UP".
