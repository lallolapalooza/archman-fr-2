SYNOPSI

S

Exemple de configuration de plugin

: 
service_types => {
  wget_ssl_index => {
    plugin => "extmon",
    timeout => 15,
    interval => 30,
    cmd => ["/usr/bin/wget", "-T", "3", "-q", "-O", "/dev/null", "https://%%ITEM%%/index.html"]
  },
  svc_alwaysok => {
    plugin => "extmon",
    timeout => 1,
    direct => true,
    cmd => ["/bin/sh", "-c", "exit 0"]
  },
  svc_alwaysfail_via_timeout => {
    plugin => "extmon",
    timeout => 2,
    max_proc => 10,
    cmd => ["/bin/sh", "-c", "sleep 5"]
  }
}
# optionnel, si le chemin d'installation déroute le démon...
plugins => {
  extmon => { helper_path => "/usr/lib/gdnsd/gdnsd_extmon_helper" }
}

CONFIGURATION -

GLOBALE

Ce sont des paramètres globaux au plugin qui sont configurés dans "plugins => { extmon => {

... } }".
helper_pa
th
Chemin de fichier chaîne, optionnel.

Normalement, ce plugin localisera avec succès son binaire auxiliaire gdnsd_extmon_helper dans le répertoire libexec d'installation à /usr/lib/gdnsd/gdnsd_extmon_helper. Si pour une raison quelconque il ne peut pas le faire, par exemple en

raison d'une installation déplacée, vous pouvez définir i
ci un chemin complet explicite vers l'auxiliaire.
helper_failure_act
ion
Chaîne, soit "stasis" ou "kill_daemon". La valeur par défaut est "stasis".

Ceci configure le comportement du plugin si le processus auxiliaire gdnsd_extmon_helper meurt de manière inattendue, ce qui empêche la collecte de toute mise à jour d'état de surveillance légitime

ultérieure.

Quel que soit ce paramètre, il y aura au moins un message syslog indiquant

l'échec.

S'il est défini à "stasis", tous les états surveillés sont laissés en l'état sans aucune mise à jour ultérieure. L'inconvénient est que, sauf si quelqu'un remarque le message syslog, ce mode d'échec est difficile à

détecter.

S'il est défini à "kill_daemon", tout le

démo
n gdnsd écho
uera de man
ière fatale.

CONFIGURATION - PAR TYPE DE

SERVICE

Les paramètres universels et neutres du plugin service_type s'appliquent tous dans leur sens habituel : "up_thresh", "ok_thresh", "down_thresh", "interval", "plugin", et "timeout". Voir gdnsd.config(5) pour des informations de base à ce sujet. Ce qui suit est spécifique à ce plugin "extmon"

:
cm
d
Tableau d'une ou plusieurs chaînes, requis.

Ceci définit la commande et les arguments à exécuter pour la vérification de surveillance. Le tableau est passé directement à execv() pour exécution (avec réutilisation du premier élément comme chemin d'exécution). Si vous avez besoin d'utiliser les fonctionnalités du shell, commencez la liste d'arguments par par exemple ""/bin/sh", "-c", .

..".

Toutes les chaînes d'arguments sont recherchées pour la chaîne magique "%%ITEM%%" (qui peut apparaître plusieurs fois par argument). Partout où cette chaîne magique est trouvée, l'adresse IP ou le texte CNAME de la ressource surveillée sera substitué à sa

place.

La commande doit se terminer avec une

valeur de sortie de zéro pour le succ
ès ou non nulle pour l'échec.
dire
ct
Booléen, false par défaut.

Normalement, les résultats de extmon sont traités par la même machine à états anti-flap utilisée pour les moniteurs traditionnels comme les plugins de surveillance HTTP et TCP. Cela signifie que les résultats sont soumis aux différents seuils ("ok_thresh", "up_thresh", "down_thresh") et il peut prendre un certain temps pour qu'un nouvel état persistant affecte réellement la

résolution.

Si "direct" est défini à "true", les résultats de la surveillance de extmon sont appliqués directement et immédiatement comme état final des ressources surveillées après chaque vérification de surveillance. Si votre commande oscille entre succès et échec à chaque exécution, l'

état interne oscillera aussi, et les changements résultants dans la résolution aussi. Utile si extmon collecte en fait l'
état d'un environnement de surveillance externe complexe qui a déjà pris en charge des choses comme les mesures anti-flap.
max_pr
oc
Entier, 0 par défaut (illimité).

Le nombre maximal de processus à lancer

simultanément.

Ceci définit la limite sur le nombre de commandes concurrentes q

ui seront exécutées. Si la limite est dépassée, les comm
andes excédentaires sont replanifiées pour 0,1 seconde pl
us tard. Après quelques exécutions, les processus seront réparti
s suffisamment pour s'exécuter sans atteindre la limite.

ENVIRONNEMENT

D'EXÉCUTION

Le plugin lance un binaire auxiliaire gdnsd_extmon_helper lors du démarrage du démon, et cet auxiliaire effectue les exécutions réelles des commandes à l'exécution. Il gère les délais d'attente et les intervalles et renvoie les résultats au plugin via un pipe. Cette communication est unidirectionnelle à l'exécution (pas de trafic démon -> auxiliaire) pour des raisons de sécurité (pour aider à garantir qu'un démon compromis ne peut pas facilement utiliser l'auxiliaire pour perturber l'exécution des commandes externes). Cette séparation empêche également une classe de bugs fonctionnels et de sécurité liés à la combinaison de pthreads à l'exécution avec le fork systématique pour exécuter les processus

enfants.

Les scripts exécutés s'exécuteront avec le même identifiant utilisateur que le démon utilise normalement pour abandonner ses

privilèges.

Les descripteurs stdout, stdin et stderr seront généralement définis sur /dev/null. stdout et stderr peuvent être ouverts sur le tty courant si le démon principal a été démarré en mode de débogage en avant-plan via "-f st

ar
t".
