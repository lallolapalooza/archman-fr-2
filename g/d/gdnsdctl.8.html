NOM

gdnsdctl - Client de socket de contrôle pour gdnsd

SYNOPSIS

Utilisation : gdnsdctl [-c /etc/gdnsd] [-s <IP:port>] [-D] [-l] [-t 47] [-o] [-i] <action> [...]
  -c - Répertoire de configuration (par défaut /etc/gdnsd), pour trouver le chemin du socket de contrôle UNIX
  -s - Adresse du socket de contrôle TCP
  -D - Activer la sortie de débogage verbeuse
  -l - Envoyer les journaux à syslog plutôt qu'à stderr
  -t - Délai d'attente en secondes (par défaut 47, plage 5 - 300)
  -o - Mode à exécution unique : ne pas réessayer les échecs temporaires (erreurs de communication, remplacement en cours)
  -i - Ignorer l'absence d'un démon en cours d'exécution pour stop, reload-zones, replace,
       et acme-dns-01-flush, signalant le succès au lieu de l'échec dans ces cas.
Actions :
  stop - Arrête le démon en cours d'exécution
  reload-zones - Recharge les données de zone du démon en cours d'exécution
  replace - Demande au démon de générer un remplaçant qui le prendra en charge (met à jour le code, la configuration, les données de zone)
  status - Vérifie l'état du démon en cours d'exécution
  stats - Exporte les statistiques JSON du démon en cours d'exécution
  states - Exporte les états surveillés en JSON
  acme-dns-01 - Crée des charges utiles ACME DNS-01 à partir d'arguments supplémentaires :
                <nom> <charge_utile> <nom> <charge_utile> ... [max %u charges utiles]
  acme-dns-01-flush - Vide (supprime) toutes les charges utiles ACME DNS-01 ajoutées ci-dessus

DESCRIPTION

gdnsdctl est le client de socket de contrôle canonique pour gdnsd. Toutes les opérations décrites ci-dessus sont synchrones et signalent le succès en quittant avec le code de sortie zéro, ou l'échec avec un code non nul.

En général, gdnsd et gdnsdctl prennent en charge l'exécution concurrente d'actions différentes de plusieurs acteurs sur un seul démon, et tout devrait finalement signaler fidèlement le succès sans aucun bogue causé par des conditions de course, s'il n'y a pas d'autres problèmes.

C'est-à-dire que, par exemple, les choses devraient être fiables si votre gestion de configuration exécute régulièrement "gdnsdctl replace" pour les mises à jour de configuration, et qu'un autre outil exécute indépendamment régulièrement "gdnsdctl reload-zones" alors qu'il met à jour les données de zonefile, pendant qu'un troisième ensemble d'outils fait des commandes "gdnsdctl acme-dns-01" , même si les 3 commandes entrent en collision avec un timing presque parfait. Finalement, les 3 commandes "gdnsdctl" se termineront, et l'état résultant contiendra toutes les mises à jour de configuration, de données de zone et de défi.

C'est également vrai pour de multiples exécutions indépendantes et superposées de la même action, comme de multiples requêtes "reload-zones" se déroulant en parallèle, ou de multiples requêtes "acme-dns-01" .

OPTIONS DE LIGNE DE COMMANDE

-c
Définit le répertoire de configuration, par défaut /etc/gdnsd. Cela est utilisé pour trouver et analyser le fichier de configuration du démon principal, au cas où il définit un "run_dir"non par défaut, ce qui changerait l'emplacement du chemin du socket de contrôle UNIX du démon.
-s
Cela indique à gdnsdctl de se connecter au démon via un socket de contrôle TCP au lieu du socket de domaine UNIX local habituel. Voir la documentation gdnsd.config(5) à propos de "tcp_control" pour plus d'informations sur la configuration du côté serveur de cela.
-D
Active la sortie de journalisation de niveau débogage supplémentaire selon les besoins.
-l
Envoie la sortie du journal à syslog plutôt qu'à stderr par défaut.
-t
Définit le délai d'attente en secondes (par défaut 47) pour l'exécution entière. C'est appliqué via un minuteur SIGALRM au niveau du processus, mais il peut dépasser légèrement le temps prévu dans des cas limites.
-o
Mode à exécution unique. Normalement, gdnsdctl réessaiera de manière persistante d'exécuter l'action dans des conditions d'échec temporaire. Les conditions d'échec temporaire se produisent lorsque le démon est en plein milieu d'une opération "replace" , ou lorsqu'une erreur de communication se produit après que la connexion a été initialement établie (ce qui pourrait être le résultat d'un mauvais timing avec l'ancien démon qui s'arrête pendant une opération "replace" ). Cela désactive les nouvelles tentatives et promeut toutes les erreurs temporaires (réessayables) en erreurs fatales (immédiatement fatales).
-i
Mode ignorer-démon-mort. Normalement, toutes les actions échouent si aucun démon n'est actuellement en cours d'exécution. Avec ce drapeau défini, si le démon n'est pas actuellement en cours d'exécution, mais que l'action fait partie de l'ensemble limité où l'intention serait fidèlement reflétée par un futur démarrage du démon, gdnsdctl renverra une valeur de sortie réussie malgré l'absence d'un démon en cours d'exécution.

L'ensemble de commandes qui prennent actuellement en compte "-i" est : "reload-zones", "stop", "acme-dns-01-flush", et "replace".

Actions

stop
Arrête de manière synchrone le démon en cours d'exécution. Un code de sortie zéro signifie que le démon a été observé s'arrêtant comme commandé.

Avec "-i", un code de sortie zéro peut aussi signifier que le démon n'était déjà pas en cours d'exécution, ce qui rend "gdnsdctl -i stop" un arrêt idempotent.

reload-zones
Recharge de manière synchrone les zonefiles du démon. Un code de sortie zéro indique que l'opération s'est terminée avec succès et que les nouvelles données sont visibles pour les clients.

Avec "-i", un code de sortie zéro peut aussi signifier que le démon n'était pas en cours d'exécution (s'il est démarré à l'avenir, les zonefiles récemment mis à jour seraient en vigueur).

replace
Demande au démon en cours d'exécution de générer une instance de remplacement de lui-même. Cela peut être utilisé pour les mises à jour du code du démon et/ou les changements de configuration. La séquence "replace" est destinée à avoir un impact opérationnel minimal du point de vue de la plupart des gens : elle est exempte de conditions de course, les requêtes ne sont ni perdues ni abandonnées et il n'y a pas d'interruption dans le traitement des requêtes. Les données de statistiques sont transmises sans couture de l'ancienne instance à la nouvelle, comme toute donnée de défi ACME DNS-01 éphémère. Le socket de contrôle reste disponible pour de nouvelles connexions en tout temps, mais le traitement réel des nouvelles connexions est retardé pendant un court instant.

Les commandes des clients de socket de contrôle déjà connectés (comme gdnsdctl) peuvent être refusées avec une réponse d'échec temporaire pendant des fenêtres de temps critiques de la séquence de remplacement, mais gdnsdctl attendra et les réessaiera par la suite.

Le démon de remplacement est initialement exécuté en tant qu'enfant du démon en cours d'exécution et hérite donc de nombreux attributs de son environnement d'exécution. Les anciens et nouveaux daemons coordonnent un processus de transfert via une connexion de socket de contrôle inter-daemons. Le processus de transfert fait de son mieux pour s'assurer que si le nouveau démon échoue à n'importe quelle étape du démarrage, l'ancien démon peut continuer ses opérations comme avant.

Les sockets d'écoute DNS sont transférés de manière superposée : il y aura une brève fenêtre de temps où les requêtes des clients peuvent être routées vers l'un ou l'autre des daemons au hasard, mais il ne devrait jamais y avoir de fenêtre où le service est indisponible. Le socket de contrôle lui-même est transféré de manière synchrone : l'ancien démon arrête d'accepter de nouvelles connexions avant que le nouveau démon commence à les accepter, et l'ancien démon reprend l'acceptation si le nouveau démon ne réussit pas complètement.

Une fois que l'ancien démon affirme que le processus de remplacement a été réussi, gdnsdctl surveillera la sortie de l'ancien démon puis établira une nouvelle connexion au socket de contrôle du nouveau démon et vérifiera son statut. Si tout cela est réussi, la commande replace finira par quitter avec le statut zéro. Elle quittera avec un statut non nul si une partie de cette opération échoue pour une raison quelconque, ce qui devrait dans la plupart des cas concevables laisser le démon existant pleinement fonctionnel.

Toutes les autres opérations gdnsdctl modifiant l'état du démon (tout sauf les actions en lecture seule "status", "stats", et &quot;states") qui pourraient être initiés séparément et simultanément sont explicitement bloqués par le démon pendant que la partie critique de la séquence de transfert de remplacement est en cours. gdnsdctl réessaiera par défaut une action de manière répétée jusqu'à ce que la remplacement se termine et laisse passer l'action, ou jusqu'à ce qu'elle atteigne le "-t" délai d'attente. L'option "-o" désactive ces réessais, ce qui fera échouer immédiatement les actions de gdnsdctl modifiant l'état pendant la fenêtre critique de remplacement.

Normalement, cette commande échouera s'il n'y a pas de démon en cours d'exécution. Cependant, avec "-i", le code de sortie zéro peut aussi signifier que le démon n'était pas en cours d'exécution (s'il est démarré dans le futur, la configuration ou le binaire récemment mis à jour qui a déclenché la volonté d'exécuter la requête "replace" serait alors en vigueur).

Le système de réessais fonctionne aussi pour "replace" par rapport à "replace" : si vous exécutez simultanément plusieurs commandes "gdnsdctl replace" , une avancera en premier et les autres attendront dans des boucles de réessai pour prendre chacune leur tour en remplaçant le démon de manière sériée jusqu'à ce qu'elles l'aient toutes fait avec succès, à moins que leur gdnsdctl "-t" délai d'attente n'expire d'abord (chaque nouveau démon mettra un certain temps à démarrer, selon le nombre de fichiers de zones et la complexité de la configuration).

status
Vérifie l'état du démon en cours d'exécution, en rapportant son PID et sa version vers stderr.
stats
Vide les statistiques JSON du démon en cours d'exécution vers stdout.
states
Vide les états JSON surveillés de tous les moniteurs de santé de service configurés.
acme-dns-01
Injecte des charges utiles de réponse de défi ACME DNS-01 temporaires telles que définies par https://tools.ietf.org/html/draft-ietf-acme-acme-14 dans le démon en cours d'exécution. Ceci est destiné à l'intégration avec des scripts ou des services qui génèrent des certificats signés à partir d'une autorité de certification compatible ACME.

Deux arguments de ligne de commande ou plus sont requis, par paires de "name" et "payload", où "name" est un nom de domaine valide et "payload" est la charge utile de réponse du défi (qui, en tant que sortie SHA-256 encodée en base64url, devrait faire 43 octets et ne contenir que des caractères alphanumériques plus "-" et "_"). Un maximum de 100 charges utiles séparées peuvent être spécifiées dans une seule invocation de gdnsdctl.

Cet exemple...

gdnsdctl acme-dns-01 example.org 0123456789012345678901234567890123456789012 www.example.org ABCDEFGHIJKLMNOPQRSTUVWXYZ-abcdefghijklmnop

... fait en sorte que le démon réponde temporairement aux requêtes "TXT" pour le nom "_acme-challenge.example.org." avec la première charge utile ci-dessus, et de même avec la deuxième charge utile pour "_acme-challenge.www.example.org.".

Les réponses de charge utile de défi injectées par cette commande expirent automatiquement après un court délai. La valeur par défaut est de 10 minutes, et est configurable via l'option de configuration "acme_challenge_ttl". Le TTL DNS réel émis avec les réponses "TXT" a pour valeur par défaut zéro (ce qui est fortement recommandé !) et est contrôlé par l'option distincte "acme_challenge_dns_ttl".

L'injection de réponses pour des noms de domaine qui ne sont pas dans le périmètre d'une des zones configurées statiquement réussira, mais la réponse à de telles requêtes sera toujours "REFUSED" (jusqu'à ce qu'une telle zone apparaisse plus tard, si jamais).

Si plus d'une charge utile est configurée pour un nom donné (dans la même commande, ou dans des commandes séparées à moins d'une fenêtre TTL d'intervalle), plusieurs enregistrements TXT seront émis. S'il existe des données TXT configurées statiquement à partir de fichiers de zones à un nom "_acme-challenge" en conflit, les RR TXT statiques seront aussi servis à côté de toute donnée provenant de ce mécanisme.

En tant qu'implémentation détaillable (particularité ?) de ce mécanisme, tout RR statique de fichier de zones ayant une première étiquette de "_acme-challenge" verra automatiquement ses TTL forcés à la valeur de "acme_challenge_dns_ttl" quel que soit le TTL spécifié dans le fichier de zones. C'était la façon la plus simple de garantir que nous ne servons jamais de valeurs TTL mélangées dans un seul RR-set d'enregistrements TXT, ce qui est interdit par la RFC 2181.

Les données injectées par ce mécanisme persistent à travers les opérations de "replace" du démon, mais pas à travers un arrêt complet "stop" du démon. Elles persistent aussi à travers les rechargements de données de zones, et dans le cas où des données sont injectées pour une zone inexistante qui entre ensuite en existence par un rechargement, le défi commencera à fonctionner après le rechargement.

acme-dns-01-flush
Vide immédiatement toutes les données de charge utile injectées ci-dessus avant leur expiration naturelle. Principalement utile pour les tests ou pour nettoyer des erreurs, mais certaines intégrations avec de grands volumes de défis à pics pourraient souhaiter vider les données explicitement à des moments où il n'y a pas de défis DNS-01 en attente.

C'est une autre commande qui prend en compte l'option "-i" : si "-i" est spécifié et que le démon n'est pas en cours d'exécution, cette commande signalera le succès, car un démon mort n'a pas de données de défi à vider.

CODE DE SORTIE

En général, toutes les opérations se terminent avec le code de sortie zéro si et seulement si l'opération réussit. Les erreurs et la plupart des autres sorties vont vers stderr, sauf dans le cas des vidages de données JSON, qui vont vers stdout.
