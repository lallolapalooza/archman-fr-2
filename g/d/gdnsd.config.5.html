tcp_timeo
ut
Entier en secondes, défaut 37, min 5, max 1800.

Ceci détermine le délai d'inactivité côté client pour les connexions TCP, qui est envoyé par le serveur aux clients applicables prenant en charge des mécanismes de signalisation comme RFC 7828 EDNS TCP Keepalive ou RFC 8490 DNS Stateful Operations

(DSO).

Il existe un délai d'attente côté serveur correspondant qui détermine quand gdnsd abandonnera un client qu'il considère comme délinquant (un client qui maintient une connexion ouverte trop longtemps sans respecter aucun délai d'inactivité côté client signalé). Le délai côté serveur est le double du délai côté client (ce qui équivaut à un défaut de 74, min 10, max

3600).

Notez que dans le cas commun/typique de clients et de connexions bien comportés, sur un serveur Linux (où nous utilisons TCP_DEFER_ACCEPT) ou un serveur BSD prenant en charge les filtres d'acceptation "dnsready" ou "dataready", lorsqu'une nouvelle connexion arrive, nous recevons immédiatement la première requête et renvoyons la réponse sans aucune possibilité de retards comptant comme temps d'inactivité, sans réentrer dans la boucle d'événements générale où le temps d'inactivité est traité ou où d'autres nouvelles connexions pourraient

arriver.

L'inactivité d'un client n'est réinitialisée qu'après qu'il a terminé chaque transaction complète (nous envoye une requête complète, et notre réponse complète est écrite dans au moins le tampon d'écriture local). L'impossibilité d'écrire immédiatement une réponse complète dans les tampons TCP locaux du serveur (généralement parce que le client a une fenêtre de réception trop petite et/ou n'accuse pas réception de plusieurs réponses précédentes) entraîne une terminaison immédiate de la connexion. Les connexions clients bien comportées qui ne s'interrompent pas au milieu d'une transaction ne deviennent des connexions inactives (susceptibles de terminaison pour inactivité) que pendant les périodes d'inactivité entre les transactions après leur première transaction, et pour les clients moins bien comportés, le minuteur d'inactivité aide à contrôler l'impact de schémas similaires aux attaques de lecture/écriture

lentes.

Le serveur enverra les informations edns TCP keepalive aux clients avec toutes les réponses où c'est légal (la requête a utilisé EDNS sur TCP, et DSO n'est pas encore établi). La valeur du délai sera envoyée avec la valeur fixe configurée ici jusqu'à ce que le serveur commence à s'arrêter, auquel point la valeur zéro est envoyée dans de telles réponses dans une tentative d'obtenir que les clients ferment

proprement.

Les clients qui établissent DSO via le TLV Keepalive recevront le même délai côté client que le délai d'inactivité DSO, avec l'intervalle DSO KeepAlive défini à Infinite (cela signifie que nous ne demandons pas au

client d'envoyer jamais de pings keepalive artificiels, et notre délai côté client s'applique à l'intervalle entre les vraies transactions de requêtes DNS dans la session). Les clients DSO recevront également des i
nformations meilleures et plus opportunes lorsque le serveur s'arrête ou est remplacé (nous pouvons pousser des messages DSO unidirectionnels immédiats vers eux en leur demandant de fermer leur session proprement).

Entier, par défaut 2, min 1, max 1024. Lorsque les fichiers de zone RFC1035 standard sont (re)chargés, jusqu'à ce nombre de threads éphémères seront créés en parallèle pour aider à les charger et les analyser plus rapidement.

La manière dont le travail est réparti entre les threads est relativement naïve : au fur et à mesure que le répertoire des zones sur le système de fichiers est parcouru à la recherche des noms de fichiers de zone, les noms sont divisés également en N listes de travail distinctes (une par thread), puis tous les threads sont lancés et travaillent en parallèle sur leurs propres listes fixes, avec le raccordement final des données de zone dans l'arbre racine se faisant de manière sérielle dans le thread principal des zones au fur et à mesure que chaque thread worker se termine. Dans le cas où le nombre total de fichiers de zone est inférieur au nombre de threads configuré, les threads en excès ne sont pas

lancés.

Cette stratégie simple fonctionne généralement bien pour de grands nombres de fichiers de zone où les coûts d'analyse par fichier de zone sont approximativement égaux, mais dans les cas où une minorité de fichiers de zone prennent beaucoup plus de temps à analyser que les autres, cela ne produira pas toujours un résultat très « équitable » (certains threads peuvent s'exécuter beaucoup plus longtemps que

d'autres).

Notez qu'en général, l'amélioration des performances d'E/S de la lecture des fichiers de zone depuis le disque (par ex. les mettre sur un SSD) tend à aider plus que la parallélisation ici, bien que les deux combinés soient encore

RFC 7871 (edns-client-subnet) le recommande en fait pour au moins les réponses différenciées par sous-réseau, car sinon il est ambigu lequel des multiples enregistrements de section de réponse s'applique au scoping du sous-réseau, et les caches doivent inévitablement adopter une vue pessimiste et fragmenter les entrées de cache par sous-réseau inutilement. De plus, si c'était le comportement fixe du serveur, plutôt que configurable, cela simplifierait considérablement le code et rendrait les recherches plus efficaces (ces gains ne sont pas réalisés par la version optionnelle expérimentale)

autoritative.

SERVICE_TYPE

S

service_types est utilisé en conjonction avec certains plugins gdnsd. Si vous n'utilisez pas un tel plugin, vous pouvez ignorer cette section en toute sécurité et l'omettre de votre

configuration.

Le hash service_types contient des définitions génériques pour la manière de surveiller un type de service donné, indépendamment de toute adresse ou nom d'hôte spécifique pour ce

service.

Il y a deux service_types triviaux définis internément sous les noms "up" et "down", qui ne font aucune surveillance réelle et définissent simplement l'état surveillé de manière permanente à "UP" ou "DOWN". "up" est le service_type par défaut quand aucun service_type n'est

spécifié.

Dans la définition d'un service_type, il y a plusieurs paramètres génériques liés au timing et à l'anti-flap, ainsi que des paramètres spécifiques au plugin qui varient selon le

plugin.

Un type de service ne spécifie cependant pas un nom ou une adresse pour une instance spécifique d'un service. Celles-ci apparaîtraient sur une base par adresse dans la configuration d'un plugin de résolution plus bas dans la section "plugins", et la configuration du plugin référencerait alors un type de service nommé à utiliser lors de la surveillance de ladite

adresse.

Un service surveillé via ces mécanismes est toujours soit dans l'état "UP" ou "DOWN" à l'exécution du point de vue de la surveillance. L'état "UP" est maintenu face à des échecs intermittents ou isolés jusqu'à ce que les seuils d'anti-flap soient dépassés et que l'état passe à "DOWN"

.

Tous les services surveillés pour les plugins ont également leur état rapporté à côté du rapport de statistiques standard de gdnsd, servi par le serveur HTTP intégré (le port par défaut est 3506)

.

SYNTAXE DE BAS

NIVEAU

Au niveau le plus bas, la syntaxe des fichiers de configuration de gdnsd ressemble grossièrement à une structure de données Perl anonyme (utilisant la syntaxe de référence). Il y a trois types de données de base pour les valeurs : des hashes ordonnés (tableaux associatifs mappant des clés à des valeurs), des tableaux ordonnés de valeurs, et des chaînes simples. Les hashes et les tableaux peuvent être imbriqués à une profondeur arbitraire. En général, les espaces sont facultatifs. Les commentaires sur une seule ligne dans les styles shell ("#") et zonefile DNS (";") sont autorisés. Ils vont jusqu'à la fin de la ligne courante et sont considérés comme des espaces par

l'analyseur.

Un hash est entouré d'accolades ("{" et "}"). Les clés sont séparées de leurs valeurs soit par "=>" soit "=" (à votre discrétion stylistique). Les clés de hash suivent les mêmes règles que les valeurs de chaîne simple. Les valeurs de hash peuvent être des chaînes simples, des tableaux, ou des hashes. Les paires clé/valeur peuvent optionnellement avoir une virgule finale pour la clarté stylistique et la

séparation.

Un tableau est entouré de crochets ("[" et "]"). Les valeurs peuvent être des chaînes simples, des tableaux, ou des hashes. Les valeurs peuvent optionnellement avoir une virgule finale pour le

style.

Les chaînes (et donc les clés) peuvent être écrites à la fois sous forme entre guillemets et non entre guillemets. Dans la forme entre guillemets, la chaîne est entourée de guillemets doubles ("""), et peut contenir n'importe quelle valeur d'octet littérale (même du binaire/utf-8, ou NUL) sauf """ ou "\". Ces deux caractères doivent être échappés par "\", c'est-à-dire "\"" et "\\"

.

Dans la forme non entre guillemets, il n'y a pas de guillemets environnants, et l'ensemble autorisé de caractères non échappés est davantage restreint. Ce qui suit n'est pas autorisé : "][}{;#,"=\" (c'est-à-dire, crochets, accolades, points-virgules, dièses, virgules, guillemets doubles, signes égaux, et barres obliques inverses). De plus, le premier caractère ne peut pas être un "$" (signe dollar)

.

Les deux formes utilisent les mêmes règles d'échappement, qui sont les mêmes règles d'échappement standard RFC utilisées dans les fichiers de zone. Les échappements commencent toujours par "\". "\" suivi de n'importe quel octet unique autre qu'un chiffre (0 - 9) est interprété comme cet octet. "\" suivi de exactement 3 chiffres interprète ces chiffres comme la valeur entière décimale non signée de l'octet désiré (la valeur à 3 chiffres ne peut pas dépasser 255

).

Pour illustrer l'échappement et le guillemetage, les ensembles suivants d'exemples de chaînes montrent différentes encodages de la même valeur analysée

: 
example
"example"
ex\097mpl\e
"ex\097mpl\e"
internal\"doublequote
"internal\"doublequote"
white\ space
"white space"
"braces{every[where]oh}my"
braces\{every\[where\]oh\}my
"\\==="
"\092==="
"\092\=\=\="
\\\=\=\=
\092\=\=\=

Le niveau supérieur du fichier de configuration est un hash implicite sans accolades par défaut, mais peut aussi être unn tableau délimité par des crochets carrés. Ce n'est pas légal pour le fichier de configuration principal de gdnsd, mais cela pourrait être utile dans les fichiers inclus (voir ci-dessous).

En règle générale, partout où la syntaxe de niveau supérieur autorise un tableau de valeurs, vous pouvez substituer une seule valeur. Le code le traitera comme s'il s'agissait d'un tableau de longueur 1.

Lorsque nous faisons référence dans d'autres sections ci-dessus à une valeur comme étant un "Entier" (ou un autre type scalaire spécifique), nous faisons référence aux contraintes sur le contenu de la valeur de chaîne de caractères. Toutes les valeurs scalaires sont des chaînes de caractères. Les valeurs "booléennes" sont des chaînes de caractères qui ont la valeur "true" ou "false", dans n'importe quelle combinaison de majuscules ou minuscules.

Exemple 1 (simple et propre):

options = {
  listen = [ 192.0.2.1, 192.0.2.2 ],
}

Exemple 2 (flèches grasses, pas de virgules, quelques guillemets arbitraires):

"options" => {
  listen => [ 192.0.2.1 192.0.2.2 ]
}

Exemple 3 (compressé et laid):

options={listen=[192.0.2.1 192.0.2.2]}

INCLUSION D'AUTRES FICHIERS

vscf dispose maintenant d'un mécanisme pour les fichiers de configuration inclus. La syntaxe est

$include{dir/file} # fichier unique doit exister
$include{dir/*}   # pas ok s'il n'y a pas de fichiers correspondants
$include{dir}     # ok s'il n'y a pas de fichiers dans le répertoire

où le chemin peut utiliser les mêmes types d'échappement et/ou de doubles guillemets que les données de chaîne scalaire normales. Les espaces entre le chemin et les crochets environnants sont facultatifs. Les espaces entre $include et le suivant "{" ne sont pas autorisés. Si le chemin est relatif (ne commence pas par /), il est interprété comme étant relatif au répertoire contenant le fichier parent. Les inclusions peuvent imbriquer d'autres inclusions à une profondeur arbitraire.

Le chemin est normalement traité comme un glob, permettant l'inclusion de plusieurs fichiers. Lorsqu'il est utilisé comme glob, il doit y avoir au moins une correspondance - ce sera une erreur s'il n'y a pas de fichiers correspondants. Cependant, si "path" n'est pas un glob et nomme explicitement un répertoire **existant**, il sera traité comme s'il s'agissait d'un glob de tous les fichiers dans ce répertoire en ajoutant "/*", et il ne sera pas une erreur s'il n'y a pas de fichiers dans ce répertoire (aucune correspondance pour le glob).

Gardez à l'esprit qu'au niveau supérieur de tout fichier vscf donné (même les fichiers inclus), le fichier doit syntaxiquement être soit un hash implicite, soit un tableau explicite, délimité par des crochets carrés.

L'instruction d'inclusion peut être utilisée dans deux contextes distincts dans la structure syntaxique d'un fichier de configuration:

Contexte de Valeur
L'instruction d'inclusion peut remplacer n'importe quelle valeur entière (c'est-à-dire le côté droit d'une entrée de table de hachage ou un membre d'un tableau) par son propre contenu, qui est soit un hash, soit un tableau. Notez qu'il n'y a pas de mécanisme pour aplatir le tableau d'un fichier inclus dans le tableau parent (l'ensemble du tableau inclus serait un seul élément de tableau dans le tableau parent). Également, l'inclusion de plusieurs fichiers dans une seule instruction (nom de répertoire ou modèle de glob) n'est pas autorisée dans le contexte de valeur. Exemples : 
configuration principale :
  options => { écouter => $include{foo} }
foo :
  [ 127.0.0.1, 127.0.0.2 ]
configuration principale :
  plugins => $include{ "bar" }
bar :
  geoip => { ... }
  extmon => { ... }
Contexte de Fusion de Hash
L'instruction d'inclusion peut également apparaître dans un hash où une clé serait normalement attendue. Dans ce cas, le fichier inclus doit être sous forme de hash (plutôt que de tableau) au niveau supérieur, et son contenu est fusionné dans le hash parent. La fusion est superficielle et les clés conflictuelles ne sont pas autorisées. Exemple : 
configuration principale :
  options => { ... },
  plugins => {
      extmon => { ... },
      $include{geoip.cfg},
      $include{plugins.d},
  }
geoip.cfg :
  geoip => { ... }
plugins.d/foo :
  weighted => { ... }
  simplefo => { ... }
plugins.d/bar :
  metafo => { ... }
