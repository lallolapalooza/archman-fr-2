NOM

gdnsd-plugin-weighted - plugin gdnsd implémentant les enregistrements « weighted »

SYNTAXE

Configuration d'exemple de plugin :

plugins => {
  weighted => {
    multi = faux # par défaut
    service_types = up
    up_thresh => 0.5 # par défaut
    corpwww => {
      lb01 = [ lb01.example.org., 99 ]
      lb02 = [ lb02.example.org., 15 ]
      lb03 = [ lb03.example.org., 1 ]
    }
    frontwww6 => {
      service_types = up
      multi = vrai
      wwwhost01 = [ 2001:db8::123, 4 ]
      wwwhost02 = [ 2001:db8::456, 1 ]
      wwwhost03 = [ 2001:db8::789, 2 ]
    }
    pubwww => {
      service_types = [ web_check, foo ]
      up_thresh => 0.01,
      pubhost01 = [ 192.0.2.1, 44 ]
      pubhost02 = [ 192.0.2.2, 11 ]
      pubhost03 = [ 192.0.2.3, 11 ]
      pubhost04 = [ 192.0.2.4, 11 ]
    }
    cdnwww => {
      service_types = web_check
      datacenter1 => {
        d1-lb1 = [ 127.0.0.1, 2 ]
        d1-lb2 = [ 127.0.0.2, 2 ]
      }
      datacenter2 => {
        d2-lb1 = [ 127.0.0.3, 2 ]
        d2-lb2 = [ 127.0.0.4, 2 ]
        d2-lb3 = [ 127.0.0.5, 1 ]
      }
    }
    mixed => {
      multi => faux,
      addrs_v4 => {
        lb1 = [ 127.0.0.3, 2 ]
        lb2 = [ 127.0.0.4, 2 ]
      }
      addrs_v6 => {
        multi => vrai
        www6set1 = {
          lb01 => [ 2001:db8::123, 4 ]
          lb02 => [ 2001:db8::456, 1 ]
        }
        www6set2 = {
          lb01 => [ 2001:db8::789, 4 ]
          lb02 => [ 2001:db8::ABC, 1 ]
        }
      }
    }
    cn => {
      service_types = my_cn_check
      foo = [ lb01.example.org., 99 ]
      bar = [ lb02.example.org., 15 ]
    }
  }
}

RR de fichier de zone référençant le ci-dessus, dans example.com :

www.corp   300 DYNC weighted!corpwww
www6.front 300 DYNA weighted!frontwww6
www        300 DYNC weighted!pubwww
cdn        300 DYNA weighted!cdnwww
mixed-a    300 DYNA weighted!mixed
cnames     300 DYNC weighted!cn

DESCRIPTION

gdnsd-plugin-weighted peut être utilisé pour retourner un (ou un sous-ensemble) de plusieurs enregistrements d'adresse, ou un de plusieurs enregistrements CNAME basé sur des probabilités dynamiques pondérées.

CONFIGURATION - NIVEAU SUPÉRIEUR

Au niveau supérieur, il existe trois clés de paramètres spéciales : "service_types", "up_thresh", et "multi". "multi" est ignoré pour les ressources basées sur CNAME. Toutes ces clés sont héritées et peuvent être remplacées au niveau de la ressource et au niveau de la famille d'adresses.

"service_types" définit la manière dont les adresses ou CNAME applicables sont surveillés. Le "service_types" par défaut au niveau supérieur est "up", qui est un type de service intégré fourni par gdnsd. Pour plus d'informations sur la configuration des types de services non par défaut, consultez la documentation principale de gdnsd.config(5).

"multi" est un booléen qui peut être "vrai" ou "faux", et vaut par défaut "faux". "multi" contrôle le comportement de l'algorithme de sélection des adresses de réponse, décrit en détail plus loin.

"up_thresh" définit une fraction flottante des poids d'adresse sommés dans la plage "(0.0 - 1.0]", valant par défaut 0.5, et est utilisé pour influencer le comportement en cas d'échec/de basculement.

À l'exception de ces trois clés, les autres clés de niveau supérieur sont les noms de vos ressources, et leurs valeurs sont la configuration de chaque ressource.

CONFIGURATION - PAR RESSOURCE

À l'intérieur de la configuration d'une ressource donnée, à nouveau les trois paramètres liés aux adresses "services_types", "multi", et "up_thresh" peuvent être spécifiés pour remplacer leurs paramètres par ressource.

Il existe deux modes de configuration de base dans une ressource :

1) Sous-sections explicites d'adresses par famille. Dans ce mode, la ressource contient une ou plusieurs des clés "addrs_v4" et "addrs_v6". Généralement, on utilise les deux ensemble, car il est plus simple d'utiliser la deuxième option lors de la configuration d'une seule famille d'adresses.

Le contenu de chaque sous-section configure les RR de réponse du type d'adresse donné pour cette ressource, et les 3 paramètres de comportement "service_types", "multi", et "up_thresh" peuvent également être remplacés par famille d'adresses.

2) Détection automatique au niveau supérieur d'une seule famille d'adresses ou de CNAME. Dans ce mode, vous pouvez configurer le niveau supérieur d'une ressource avec des entrées directes, à condition qu'elles correspondent à un ensemble d'un seul type : toutes les adresses IPv4, toutes les adresses IPv6, ou tous les CNAME, et le type sera auto-détecté.

Les ressources contenant des listes pondérées de CNAME plutôt que des adresses ne peuvent être utilisées qu'avec des enregistrements "DYNC" dans les fichiers de zone, tandis que celles qui contiennent uniquement des adresses peuvent être utilisées avec des enregistrements "DYNC" ou "DYNA".

CONFIGURATION - CNAMES

Lors de la configuration des cnames, la valeur de chaque élément doit être "[ CNAME, POIDS ]", et la ressource sera utile pour les enregistrements de zone "DYNC", résolvant en un enregistrement CNAME pondéré dans les réponses. L'algorithme de sélection basé sur les poids et les résultats de surveillance est tel que décrit ci-dessous pour les adresses dans le CAS UNIQUE NON GROUPÉ, car les groupes de CNAME ne peuvent pas être configurés et l'option "multi" ne leur est pas valide.

Les données CNAME doivent être entièrement qualifiées (se terminant par "."), et un "DYNC" ne peut pas être utilisé pour émettre un CNAME qui pointe dans la même zone qui contenait le "DYNC".

CONFIGURATION - ADRESSES

À l'exception du fait que "addrs_v4" et "addrs_v6" doivent contenir uniquement des adresses de la famille correcte (ou dans le cas de détection automatique au niveau supérieur, les entrées de niveau supérieur doivent être toutes de la même famille), les deux sous-sections se comportent identiquement. Lorsqu'elles sont toutes deux présentes, elles sont toutes deux utilisées dans chaque réponse "DYNA" (car gdnsd inclut toujours les enregistrements de famille opposée dans la section Additionnelle des requêtes A/AAAA).

Dans chaque type de famille d'adresses, il existe deux dimensions binaires différentes (multi -> vrai/faux, et groupé vs non groupé) sur lesquelles la configuration et le comportement reposent, conduisant à quatre cas possibles différents : unique non groupé, multiple non groupé, unique groupé et multiple groupé. Chacun sera discuté en détail ci-dessous :

LE CAS UNIQUE NON GROUPÉ

C'est le cas le plus simple. Le code détecte ce cas lorsqu'il voit que "multi" est faux (par défaut), et que les valeurs des clés sont des tableaux plutôt que des sous-hashes. Chaque clé de hash est une étiquette d'adresse, et chaque valeur est un tableau de "[ IPADDR, POIDS ]".

Lors de la réponse à une requête dans ce cas, les poids sont d'abord convertis en poids dynamiques. Le poids dynamique d'une adresse est son poids configuré si l'état surveillé est "UP", ou zéro si l'état surveillé est "DOWN". Les poids dynamiques sont sommés pour produire un total de poids dynamique, puis une seule adresse à laquelle répondre est choisie parmi l'ensemble, chaque adresse ayant les probabilités "poids_dynamique_adresse / total_poids_dynamique".
