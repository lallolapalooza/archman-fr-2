DESCRIPTIO

N

gdnsd-plugin-multifo est conçu pour effectuer un regroupement de basculement multi-adresses, tous actifs. Fondamentalement, pour chaque nom de ressource configuré, vous fournissez une liste étiquetée d'adresses. multifo surveille ces adresses selon "service_types", et répond aux requêtes d'adresses "DYNA" en utilisant le sous-ensemble non"DOWN". Le code principal de gdnsd effectuera une rotation round-robin des enregistrements l

ors de leur sortie, comme il le fait pour tous
les ensembles d'enregistrements d'adresses RR.

CONFIGURATION DU PLUGIN DE NIVEAU

SUPÉRIEUR

Au niveau supérieur de la strophe de configuration du plugin, trois paramètres spéciaux "up_thresh", "service_types" et "ignore_health" sont pris en charge. Ceux-ci définissent les options par défaut par ressource du même nom pour toutes les ressources qui ne les définissent pas

explicitement.

Les autres entrées de hachage au niveau supérieur sont les noms des ressources que v

ous définissez. Chaque ressource reçoit son propre hachage de configuration contenan
t les paramètres spécifiques à la ressource ainsi que les données d'adresse réelles.

CONFIGURATION DES

RESSOURCES

Au sein d'une ressource, vous avez deux options de base. Vous pouvez soit spécifier directement un ensemble de paires "label => address" qui sont toutes de la même famille (IPv4 ou IPv6), soit vous pouvez utiliser les sous-stanzas "addrs_v4" et/ou "addrs_v6" pour spécifier une ou les deux familles dans la même

ressource.

Les paramètres "up_thresh", "service_types" et "ignore_health" sont hérités à travers chaque niveau et peuvent être remplacés à n'importe quel niveau (même par famille d'adresses)

:
up_thre
sh
Flottant, valeur par défaut 0.5, plage (0.0 - 1.0]. Ceci configure le seuil "up_thresh" par ressource. Plus de détails dans "SEUIL DE DISPONIBILITÉ"
ci-dessous.
service_typ
es
Tableau de chaînes, ou chaîne unique. Par défaut "default". Ceci définit les service_types surveillés pour cette ressource. Si un tableau de plus d'un élément est fourni, tous seront surveillés pour chaque adresse, et l'état surveillé net sera le minimum (le pire) de l'ensemble. Voir gdnsd.config(8) pour plus de détails sur les
service_types.

th
Booléen, valeur par défaut false. S'il est défini à true, la santé des adresses individuelles n'affectera pas si multifo les ajoute à l'ensemble des adresses de sortie, mais elle sera toujours vérifiée et utilisée pour le calcul "up_thresh" qui est consommé par les méta-plugins comme geoip et metafo, qui

CONFIGURATION

RACCOURCIE

Si vous n'avez aucun paramètre (service_types, up_thresh, ignore_health) à configurer dans une strophe donnée (configuration directe de ressource à famille unique, ou addrs_v[46]), et que vous ne vous souciez pas des étiquettes descriptives par adresse utilisées dans la surveillance, vous pouvez remplacer le hachage par un tableau d'adresses. Les étiquettes seront générées pour vous sous forme d'une série d'entiers commençant par 1. Par exemple, ce qui suit est équivalent

: 
res1 => { addrs_v4 => [ 192.0.2.1, 192.0.2.2 ] }
res1 => { addrs_v4 => { 1 => 192.0.2.1, 2 => 192.0.2.2 }
}

MÉCANISMES

OPÉRATIONNELS

Toutes les adresses de toutes les ressources sont surveillées en utilisant les "service_types" hérités par famille d'adresses spécifiés (par défaut, ce serait le moniteur virtuel statique "up"). Lorsque le démon principal demande une recherche d'enregistrements d'adresses d'une famille donnée sur l'une des ressources de ce plugin, il suit essentiellement le processus suivant pour déterminer l'ensemble des adresses de réponse pour cette famille d'adresses : 1) Ajouter toutes les adresses non-DOWN à l'ensemble de résultats. 2) Si l'ensemble des adresses non-DOWN échoue au test up_thresh, ajouter *toutes* les adresses à l'ensemble de résultats comme solution de repli. 3) Si une adresse est dans l'état DOWN, diviser par deux le TTL spécifié dans le fichier de

zone.

Si "ignore_health" est true, toutes les adresses sont ajoutées à l'ensemble de résultats indépendamment de la santé, mais les effets up_thresh et TTL se produisent toujours, et l'état final au niveau de la ressource reflète toujours l'état global comme il le serait sans "ignore_health"

.

Ce processus est répété indépendamment pour chacun des sous-ensembles d'adresses IPv4 et I

Pv6, dans le cas où une ressource a les deux familles d'adresses configurées (le TTL n'est
divisé par deux qu'une seule fois, bien sûr). Les détails sur le test up_thresh suivent :

SEUIL DE

DISPONIBILITÉ

S'il n'y a pas assez d'adresses UP pour passer le seuil (par famille d'adresses), toutes les adresses (d'une famille d'adresses donnée) seront retournées comme solution de

repli.

Le seuil est implémenté mathématiquement comme dans le pseudo-code suivant "if(non_down >= ceil(thresh * total)) threshold_passed;". Par exemple, si thresh est à la valeur par défaut de 0.5, et qu'il y a 3 adresses IPv4 au total, alors 2 d'entre elles doivent être non-down pour passer le seuil. Le résultat net est qu'avec le seuil par défaut, le plugin ne retournera jamais une adresse isolée unique à partir d'un ensemble de 3. Il retournera soit les 3, soit il retournera 2/3 si une seule adresse de l'ensemble a

échoué.

Lorsque le test de seuil échoue (et que toutes les adresses sont retournées) pour l'une ou l'autre famille d'adresses, l'échec total au niveau de la ressource sera également signalé à tout méta-plugin amont applicable tel que metafo ou

geoip.

Règles générales pour les résultats de la formule up_thresh

:
  • Un seuil de 1.0 ne passera que si toutes les adresses sont non-down. C'est en grande partie inutile, vous feriez aussi bien de ne rien surveiller et de configurer ces adresses comme un ensemble statique dans un fichier de
    • zone.
  • Un seuil de 0.01 passera même si une seule adresse est vivante et ne retournera que cette adresse, même si c'est par exemple la seule restante sur
    • 40.
  • Parce qu'un seuil de 0.0 est illégal, si tou
    • tes les adresses sont down, le seuil échoue
ra toujours, retournant toutes les adresses.
