NAME

gdaladdo - Construit ou reconstruit des images de survol.

SYNOPSIS

Usage: gdaladdo [--help] [--long-usage] [--help-general]
                [-r nearest|average|rms|gauss|bilinear|cubic|cubicspline|lanczos|average_magphase|mode]
                [-ro] [--quiet] [-b <band>]... [-oo <NAME=VALUE>]...
                [-minsize <val>]
                [[-clean]|[--partial-refresh-from-source-timestamp]|
                [--partial-refresh-from-projwin <ulx> <uly> <lrx> <lry>]|
                [--partial-refresh-from-source-extent <filename1>[,<filenameN>]...]]
                filename [<level>]...

DESCRIPTION

L'utilitaire gdaladdo peut être utilisé pour construire ou reconstruire des images de survol pour la plupart des formats de fichiers supportés, en utilisant l'une des plusieurs algorithmes de sous-échantillonnage.

--help
Affiche ce message d'aide et quitte.
--help-general
Donne un bref message d'utilisation pour les options de ligne de commande GDAL génériques et quitte.
-r {nearest|average|rms|gauss|bilinear|cubic|cubicspline|lanczos|average_magphase|mode}
Sélectionne un algorithme de rééchantillonnage. La valeur par défaut est nearest, ce qui n'est généralement pas approprié si une précision sub-pixel est souhaitée.

À partir de GDAL 3.9, lors du rafraîchissement de survols TIFF existants, la méthode précédemment utilisée, telle qu'indiquée dans l'élément de métadonnées RESAMPLING du survol, sera utilisée si -r n'est pas spécifié.

Les méthodes disponibles sont :

nearest applique un rééchantillonneur par plus proche voisin (échantillonnage simple).

average calcule la moyenne de tous les pixels contribuant non-NODATA. À partir de GDAL 3.1, il s'agit d'une moyenne pondérée tenant compte correctement du poids des pixels sources ne contribuant pas entièrement au pixel cible.

rms calcule la racine carrée moyenne / moyenne quadratique de tous les pixels contribuant non-NODATA (GDAL >= 3.3)

gauss applique un noyau Gaussien avant de calculer le survol, ce qui peut conduire à de meilleurs résultats que la moyenne simple dans le cas, par exemple, de bords nets avec des contrastes élevés ou des motifs bruyants. Les valeurs de niveau conseillées devraient être 2, 4, 8, ... de sorte qu'un noyau Gaussien de rééchantillonnage 3x3 soit sélectionné.

bilinear applique un noyau de convolution bilinéaire.

cubic applique un noyau de convolution cubique.

cubicspline applique un noyau de convolution B-Spline.

lanczos applique un noyau de convolution sinc fenêtré par Lanczos.

average_magphase moyenne les données complexes dans l'espace amplitude/phase.

mode sélectionne la valeur qui apparaît le plus souvent parmi tous les points échantillonnés.

-b <band>
Sélectionne une bande d'entrée band pour la génération de survols. La numérotation des bandes commence à 1. Plusieurs options -b peuvent être utilisées pour sélectionner un ensemble de bandes d'entrée pour générer les survols.
-ro
Ouvre le jeu de données en mode lecture seule, afin de générer un survol externe (pour GeoTIFF en particulier).
-clean
Supprime tous les survols.
-oo <NAME>=<VALUE>
Option d'ouverture du jeu de données (spécifique au format)
-minsize <val>
Largeur ou hauteur maximale du plus petit niveau de survol. Ne prend en compte que si les niveaux explicites ne sont pas spécifiés. La valeur par défaut est 256.
--partial-refresh-from-source-timestamp
Ajouté dans la version 3.8.

Cette option effectue un rafraîchissement partiel des survols existants, lorsque <filename> est un fichier VRT avec un survol externe. Elle vérifie l'horodatage de modification de toutes les sources du VRT et régénère le survol pour les zones correspondant aux sources dont l'horodatage est plus récent que le survol externe du VRT. Par défaut, tous les niveaux de survol existants seront rafraîchis, sauf si des niveaux explicites sont spécifiés. Voir Exemple 7.

--partial-refresh-from-projwin <ulx> <uly> <lrx> <lry>
Ajouté dans la version 3.8.

Cette option effectue un rafraîchissement partiel des survols existants, dans la région d'intérêt spécifiée par les coordonnées géoréférencées où <ulx> est la valeur X du coin supérieur gauche, <uly> est la valeur Y du coin supérieur gauche, <lrx> est la valeur X du coin inférieur droit et <lry> est la valeur Y du coin inférieur droit. Par défaut, tous les niveaux de survol existants seront rafraîchis, sauf si des niveaux explicites sont spécifiés.

--partial-refresh-from-source-extent <filename1>[,<filenameN>]...
Ajouté dans la version 3.8.

Cette option effectue un rafraîchissement partiel des survols existants, dans la région d'intérêt spécifiée par un ou plusieurs noms de fichiers (noms séparés par des virgules). Notez que les noms de fichiers sont uniquement utilisés pour déterminer les régions d'intérêt à rafraîchir. Les pixels sources de référence sont ceux du jeu de données principal. Par défaut, tous les niveaux de survol existants seront rafraîchis, sauf si des niveaux explicites sont spécifiés. Voir Exemple 8.

<filename>
Le fichier pour lequel construire les survols (ou dont les survols doivent être supprimés).
<levels>
Une liste de niveaux de survol entiers à construire. Ignoré avec l'option -clean.
Les niveaux ne sont plus requis pour construire des survols. Dans ce cas, les facteurs de puissance de deux de survol appropriés seront sélectionnés jusqu'à ce que le plus petit survol soit plus petit que la valeur de l'option -minsize.

À partir de GDAL 3.9, s'il existe déjà des survols, les niveaux correspondants seront utilisés pour les rafraîchir si aucun niveau explicite n'est spécifié.

gdaladdo respectera correctement les tuples NODATA_VALUES (métadonnées spéciales du jeu de données) afin que seul un triplet RVB donné (dans le cas d'une image RVB) soit considéré comme la valeur nodata et non chaque valeur du triplet indépendamment par bande.

La sélection d'une valeur de niveau comme 2 entraîne le calcul d'un niveau de survol dont la résolution est 1/2 (dans chaque dimension) de celle de la couche de base. Si le fichier possède des niveaux de survol existants à un niveau sélectionné, ces niveaux seront recalculés et réécrits sur place.

Pour les survols GeoTIFF internes (ou les survols externes au format GeoTIFF), notez que -clean ne réduit pas la taille du fichier. Une exécution ultérieure de gdaladdo avec des niveaux de survol entraînera l'expansion du fichier, plutôt que la réutilisation de l'espace des survols précédemment supprimés. Si vous souhaitez simplement modifier la méthode de rééchantillonnage sur un fichier qui a déjà des survols calculés, vous n'avez pas besoin de nettoyer les survols existants.

Certains pilotes de format ne supportent pas du tout les survols. De nombreux pilotes de format stockent les survols dans un fichier secondaire avec l'extension .ovr, qui est en fait au format TIFF. Par défaut, le pilote GeoTIFF stocke les survols en interne dans le fichier sur lequel on opère (s'il est accessible en écriture), à moins que l'option -ro ne soit spécifiée.

La plupart des pilotes supportent également un format de survol alternatif utilisant le format Erdas Imagine. Pour l'activer, utilisez l'option de configuration USE_RRD=YES (Exemple 5). Cela placera les survols dans un fichier .aux associé, adapté à une utilisation directe avec Imagine ou ArcGIS ainsi qu'avec les applications GDAL. (par exemple, --config USE_RRD YES)

GESTION DES VALEURS NODATA / DES MASQUES DE VALIDITÉ DE LA SOURCE PENDANT LE RÉÉCHANTILLONNA

GE

Les valeurs invalides dans les pixels source, qu'elles soient identifiées par une valeur nodata définée dans les métadonnées de la bande source, un masque de bande, une bande alpha, ne seront pas utilisées lors du rééchantillonnage

.
orphe
lin

La manière dont cela est pris en compte dépend du noyau de rééchantillonnage

:
  • pour le rééchantillonnage au plus proche, pour chaque pixel cible, l'un des pixels source potentiellement contributeurs est sélectionné (d'une manière spécifique à l'implémentation). Sa valeur est utilisée telle quelle, qu'elle soit valide ou
    • invalide.
  • pour bilinéaire, cubique, cubique-spline et lanczos, pour chaque pixel cible, les poids des pixels source contributeurs sont mis à zéro pour les ignorer lorsqu'ils sont masqués. Il y a une spécificité supplémentaire pour le cubique : étant donné que certains des poids du noyau sont négatifs, une telle stratégie pourrait conduire à un fort dépassement/sous-dépassement lorsqu'il y a une alternance de pixels valides et invalides. Par conséquent, si dans l'une ou l'autre direction (horizontale ou verticale), le nombre maximal de pixels source valides dans chaque dimension est inférieur au rayon du noyau de rééchantillonnage, le pixel cible est considéré comme
    • nodata.
  • pour les autres méthodes de rééchantillonnage, le
    • s pixels source contribuant au pixel cible
sont ignorés s'ils sont masqués. Seuls les pixels
valides sont pris en compte. S'il n'y en a
aucun, le pixel cible est considéré comme nodata.
