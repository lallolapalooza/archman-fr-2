NOM

gdnsd-plugin-metafo - plugin gdnsd pour le méta-basculement d'adresses

SYNOPSIS

Exemple minimal de fichier de configuration gdnsd utilisant ce plugin :

plugins => {
  metafo => {
    resources => {
      prod_www => {
        datacenters => [ dc-01, dc-02, dc-03 ]
        dcmap => {
          dc-01 => 192.0.2.1
          dc-02 => { lb01 => 192.0.2.2, lb02 => 192.0.2.3 }
          dc-03 => [ 192.0.2.4, 192.0.2.5, 192.0.2.6 ]
        }
      },
      prod_foo => {
        datacenters => [ dc-01, dc-02, dc-bk ]
        dcmap => {
          dc-01 => { lb01 => 192.0.1.1, lb02 => 192.0.1.2 }
          dc-02 => [ 192.0.5.1, 192.0.5.2, 192.0.5.3 ]
          dc-bk => fallback.static.cname.example.org.
        }
      }
    }
  }
}

Exemple d'enregistrements RR de zone dans la zone example.com :

www      600 DYNA metafo!prod_www
www-dc01 600 DYNA metafo!prod_www/dc-01
foo      700 DYNC metafo!prod_foo

DESCRIPTION

gdnsd-plugin-metafo est un méta-plugin. Il effectue un basculement d'adresses ordonné statiquement entre plusieurs « datacenters » (qui peuvent correspondre ou non à de vrais centres de données, il s'agit simplement d'une étiquette pratique). Chaque centre de données est défini en termes d'autres plugins tels que « multifo », « weighted », etc, comme décrit ci-dessous.

CONFIGURATION - NIVEAU SUPÉRIEUR

Le niveau supérieur de la configuration du plugin metafo (c'est-à-dire « plugins => { metafo => { ... } } ») ne prend en charge qu'une seule clé fixe et obligatoire, « resources », dont la valeur doit être un hash. Le contenu de « resources » est une clé par ressource nommée, la valeur définissant cette ressource.

Toute autre clé présente au niveau supérieur sera héritée à l'intérieur de chaque hash par ressource à l'intérieur de la section « resources » , servant de valeurs par défaut pour chaque ressource pour tout ce qui n'est pas défini explicitement là-bas, comme expliqué ci-dessous.

CONFIGURATION - RESSOURCES

Toutes les clés à l'intérieur de la section resources représentent des ressources nommées, qui peuvent être référencées par des RR « DYNA » dans les fichiers de zone (par exemple « www DYNA metafo!resource_name »). La valeur de chaque ressource doit être un hash clé-valeur configurant la ressource elle-même. Exemple structurel léger :

plugins => {
  metafo => {
    resources => { resA => { ... }, resB => { ... } }
  }
}

Au sein d'une ressource, il n'y a que trois clés spécifiquement significatives :

« datacenters = [ A, B, C, ... ] »
Tableau de noms de centres de données, requis. C'est l'ensemble des étiquettes de noms de centres de données utilisés pour cette ressource, dans l'ordre dans lequel ils seront vérifiés pour le basculement.
« dcmap = { ... } »
Hash, requis. Le « dcmap » est un hash clé-valeur où les clés doivent être exactement la liste des centres de données définis dans la liste « datacenters » de cette ressource, et les valeurs définissent la configuration d'adresse de chaque centre de données. Un autre exemple structurel minimal jusqu'à ce niveau : 
plugins => {
  metafo => {
    resources => {
      resA => {
        datacenters => [ dc01, dc02 ],
        dcmap => {
          dc01 => ???
          dc02 => ???
        }
      }
    }
  }
}

Il existe plusieurs formes que les valeurs par centre de données (« ??? » ci-dessus) peuvent prendre, documentées dans la section suivante.

« skip_first = true »
Si ce drapeau de configuration booléen est défini, le code du résolveur ignorera le premier centre de données lors de la résolution de cette ressource. C'est principalement utile dans le contexte du plugin geoip, et est discuté plus en détail là-bas.

Toutes les clés autres que « datacenters » et « dcmap » au niveau par ressource servent de valeurs par défaut héritées pour chaque configuration par centre de données à l'intérieur du « dcmap ».

RÉSOLUTION PAR CENTRE DE DONNÉES

La valeur des datacenters dans la section « dcmap » d'une ressource peut prendre plusieurs formes. Il est important de comprendre que, pour la plupart, plugin_metafo ne traite pas lui-même ce niveau de résultats, mais délègue plutôt le travail dans cette portée à d'autres plugins. Ces sous-plugins, à leur tour, notifient également metafo d'un échec complet à leur niveau, ce qui est l'information que metafo utilise pour savoir qu'il faut basculer vers le centre de données suivant dans la liste.

La manière la plus directe et évidente de faire cela est avec une référence directe de la forme « %plugin!resource », comme montré ici :

plugins => {
  metafo => {
    resources => {
      resA => {
        datacenters => [ dc1, dc2 ],
        dcmap => {
          dc1 => %multifo!res_mfo1
          dc2 => %multifo!res_mfo2
        }
      }
    }
  }
  multifo => {
    res_mfo1 => { lb01 => 192.0.2.1, lb02 => 192.0.2.3 }
    res_mfo2 => { lb01 => 192.0.2.111, lb02 => 192.0.2.113 }
  }
}

Cependant, pour simplifier les choses dans les cas simples, plugin_metafo peut synthétiser la configuration du plugin de niveau inférieur à partir d'un hash, comme ceci :

plugins => {
  metafo => {
    resources => {
      resA => {
        datacenters => [ dc1, dc2 ],
        dcmap => {
          dc1 => { plugin => multifo, lb01 => 192.0.2.1, lb02 => 192.0.2.3 }
          dc2 => { lb01 => 192.0.2.111, lb02 => 192.0.2.113 }
          # the above are effectively treated as:
          # dc1 => %multifo!metafo_resA_dc1
          # dc2 => %multifo!metafo_resA_dc2
        }
      }
    }
  }
  # below does not exist in your configfile, but is what plugin_metafo
  #   synthesizes to support the above:
  #multifo => {
  #  metafo_resA_dc1 => { lb01 => 192.0.2.1, lb02 => 192.0.2.3 }
  #  metafo_resA_dc2 => { lb01 => 192.0.2.111, lb02 => 192.0.2.113 }
  #}
}

Au sein d'un hash comme ci-dessus, la clé spéciale « plugin » sera extraite en interne et utilisée pour nommer le plugin pour lequel nous synthétisons la configuration. « plugin » vaut par défaut « multifo » s'il n'est pas spécifié. Notez que « plugin » pourrait aussi être spécifié au niveau de la ressource (juste à l'intérieur de la section « resA » ) pour changer la valeur par défaut pour toutes les entrées « dcmap » d'une ressource, et pourrait aussi être spécifié au niveau le plus externe (juste à l'intérieur de la section « metafo » ) pour changer la valeur par défaut pour toutes les ressources.

Le « plugin » hérité est aussi la valeur par défaut pour la forme de référence directe « %plugin!resource » discutée précédemment. Avec le bon nom de plugin par défaut, elle peut être raccourcie à simplement « !resource ».

Le même schéma d'héritage clé-valeur (niveau supérieur -> niveau par ressource -> niveau par centre de données) peut aussi être utilisé pour tout autre paramètre dans les configurations de ressources synthétisées spécifiques au(x) plugin(s) par centre de données que vous utilisez. Un exemple courant serait le paramètre « service_types » que possèdent la plupart des plugins qui prennent en charge les résultats d'adresses surveillées. Notez que ces autres valeurs (par exemple service_types) ne s'appliqueraient qu'aux ressources synthétisées, pas aux références directes comme « %multifo!foo », qui doivent être configurées entièrement séparément dans la configuration de ce plugin.

Il existe trois autres valeurs de raccourci possibles pour les datacenters : une adresse directe unique, un tableau d'adresses, ou un nom d'hôte CNAME unique. Si une adresse IP unique ou un tableau d'adresses IP sont spécifiés, plugin_metafo synthétisera un hash à partir d'elles avec le plugin forcé à « multifo » (puisqu'il ne peut pas connaître la syntaxe des hashes pour tous les autres plugins, qui peuvent différer), et leur donnera les étiquettes d'adresses 1, 2, etc.

Si la valeur d'un centre de données est un nom d'hôte CNAME unique, aucun sous-plugin n'est utilisé, et ce résultat CNAME est retourné directement. Notez gdnsd-plugin-metafo(8)

NAME

gdnsd-plugin-metafo - plug-in for meta-level configuration

SYNOPSIS

gdnsd-plugin-metafo

DESCRIPTION

This plugin provides a very simple mechanism for abstracting common configuration elements away from the zonefile, into a per-plugin configuration block.

Its primary purpose is to allow the creation of shared lists of IP addresses to be associated with arbitrary resource names.

CONFIGURATION - TOP-LEVEL

The "metafo" plugin takes no options in the top-level configuration block.

CONFIGURATION - RESOURCES

The "metafo" plugin supports a number of options in the per-resource configuration block. They are all optional:

plugin
Allows overriding the default plugin choice for resources synthesized by this plugin. The default is the plugin that is currently being configured.
service_types
A list of service types to associate with resources synthesized by this plugin. The default is "up".
datacenters
A list of datacenter names to synthesize resources for. For each name in the list, a resource named "%resource_name%/%datacenter_name%" will be synthesized. This allows you to map abstract resource names to specific datacenter IPs.
dcmap
A hash mapping datacenter names to resource configurations. The configuration may be any of the formats accepted by "gdnsd.config(5)", for instance:
          dc1 => { plugin => multifo, lb01 => 192.0.2.1, lb02 => 192.0.2.3 }
          dc2 => %multifo!bar
          dc3 => !foo # this assumes there is a plugin named 'foo'
          dc4 => 192.0.2.150
          dc5 => [ 192.0.2.180, 192.0.2.181 ]
          dc6 => last.resort.example.com.

A resource may have both "datacenters" and "dcmap" specified. If so, the "dcmap" entries take precedence. It is possible to specify a "plugin" and/or "service_types" within a "dcmap" entry. If specified, these override the global settings for that specific datacenter.

Synthesized resources will be configured to use "DYNC" RRs if the underlying plugin is configured to return dynamic data. Otherwise, they will be configured to use "DYNA" RRs.

Any resource listed in the "datacenters" or "dcmap" options will be implicitly added to the resource's list of "service_types". This means that any resource with such an entry can only be used with "DYNC" RRs, and not "DYNA" RRs (as is the case if any subplugin's configuration is capable of returning CNAME data).

A much more complete example, showing off most of the features above:

plugins => {
  metafo => {
    plugin => multifo # change default for all resources
    service_types => [ bar ] # default service_types for synthesized below
    resources => {
      resA => {
        plugin => multifo # change default for this resource
        service_types => [foo, bar] # services types for synthesized below:
        datacenters => [ dc1, dc2, dc3, dc4, dc5, dc6, dc7, dc8 ],
        dcmap => {
          dc1 => { plugin => multifo, lb01 => 192.0.2.1, lb02 => 192.0.2.3 }
          dc2 => { lb01 => 192.0.2.111, lb02 => 192.0.2.113 }
          dc3 => %simplefo!foo
          dc4 => { plugin => simplefo, primary => 192.0.2.100, secondary => 192.0.2.101 }
          dc5 => !bar
          dc6 => 192.0.2.150
          dc7 => [ 192.0.2.180, 192.0.2.181 ]
          dc8 => last.resort.example.com.
        }
      }
    }
  }
  # below, commented-out sections show configuration synthesized
  #   by plugin_metafo, whereas the rest are direct-references that
  #   had to be manually specified here:
  multifo => {
    # metafo_resA_dc1 => { lb01 => 192.0.2.1, lb02 => 192.0.2.3, service_types => [foo, bar] }
    # metafo_resA_dc2 => { lb01 => 192.0.2.111, lb02 => 192.0.2.113, service_types => [foo, bar] }
    bar => { asd => 192.0.2.77, xyz => 192.0.2.88 }
    # metafo_resA_dc6 => { 1 => 192.0.2.150, service_types => [foo, bar] }
    # metafo_resA_dc7 => { 1 => 192.0.2.180, 2 => 192.0.2.181, service_types => [foo, bar] }
  }
  simplefo => {
    foo => { primary => 192.0.2.80, secondary => 192.0.2.81 }
    # metafo_resA_dc4 => { primary => 192.0.2.100, secondary => 192.0.2.101, service_types => [foo, bar] }
  }
}

Note in the example above that "%multifo!bar" and "%simplefo!foo" would have had their default "service_types = up" rather than the one specified at the metafo level, because they were not synthesized. It would be up to you to keep all of the service_types in sync when using direct references.

SYNTHETIC PER-DATACENTER RESOURCES

This plugin will synthesize additional, per-datacenter resource names from your configuration. They are named as "resname/dcname". For example, if you define a metafo resource named "prodwww" with the datacenter list "[ pri, sec ]", the resource names "prodwww/pri" and "prodwww/sec" will be sythesized and can be used in zonefile records, e.g.:

www-backup 300 DYNA metafo!prodwww/sec

When used, these per-datacenter synthetic resource names cause a given lookup to skip the normal failover process and directly return results from that particular datacenter.
