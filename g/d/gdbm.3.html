DESCRIPTION

GNU dbm est une bibliothèque de routines qui gère des fichiers de données contenant des paires clé/donnée. L'accès fourni permet le stockage, la récupération et la suppression par clé, ainsi qu'un parcours non trié de toutes les clés. Un processus peut utiliser plusieurs fichiers de données simultanément.

Ouverture d'une base de données

Un processus qui ouvre un fichier gdbm est désigné comme "lecteur" ou "écrivain". Un seul écrivain peut ouvrir un fichier gdbm et plusieurs lecteurs peuvent l'ouvrir. Les lecteurs et les écrivains ne peuvent pas ouvrir le fichier gdbm simultanément. La procédure d'ouverture d'un fichier gdbm est la suivante :

GDBM_FILE gdbm_open (const char *name, int block_size,
int flags, int mode, void (*fatal_func)(const char *));
Name est le nom du fichier (le nom complet, gdbm n'ajoute aucun caractère à ce nom).
Block_size est la taille d'un transfert unique du disque vers la mémoire. Si la valeur est inférieure à 512, la taille du bloc du système de fichiers est utilisée à la place. La taille est ajustée pour que le bloc puisse contenir un nombre exact d'entrées de répertoire, de sorte que la taille effective du bloc puisse être légèrement supérieure à la valeur demandée. Cet ajustement est désactivé si le drapeau flags GDBM_BSEXACT est utilisé.
Le paramètre flags est un masque de bits, composé du mode d'accès et d'un ou plusieurs drapeaux modificateurs. Le bit du mode d'accès désigne le processus comme lecteur ou écrivain et doit être l'une des options suivantes :
GDBM_READER
lecteur
GDBM_WRITER
écrivain
GDBM_WRCREAT
écrivain - si la base de données n'existe pas, en créer une nouvelle
GDBM_NEWDB
écrivain - créer une nouvelle base de données, qu'elle existe déjà ou non
Des drapeaux supplémentaires (modificateurs) peuvent être combinés avec ces valeurs par un OU binaire. Ils ne sont pas tous pertinents avec tous les modes d'accès.
Les drapeaux valides pour n'importe quelle valeur du mode d'accès sont :
GDBM_CLOEXEC
Définir le descripteur de fichier de la base de données avec l'option close-on-exec.
GDBM_NOLOCK
Empêche la bibliothèque d'effectuer tout verrouillage sur le fichier de la base de données.
GDBM_NOMMAP
Indique à gdbm_open de désactiver l'utilisation de mmap(2).
GDBM_PREREAD
Lors du mappage du fichier GDBM en mémoire, lire son contenu immédiatement, au lieu de le faire à la demande (lecture prefault). Cela peut être avantageux si vous ouvrez une base de données en mode lecture seule et que vous allez effectuer de nombreuses recherches. Dans ce cas, la base de données entière sera lue en une seule fois et les recherches seront effectuées sur une copie en mémoire. En revanche, il ne faut pas utiliser GDBM_PREREAD si vous ouvrez une base de données (même en lecture seule) uniquement pour récupérer quelques clés.

Enfin, n'utilisez jamais GDBM_PREREAD lors de l'ouverture d'une base de données pour des mises à jour, en particulier pour des insertions : cela dégraderait les performances.

Ce drapeau n'a aucun effet si GDBM_NOMMAP est spécifié, ou si le système d'exploitation ne prend pas en charge la lecture prefault. Il est connu pour fonctionner sur les noyaux Linux et FreeBSD.

GDBM_XVERIFY
Active des vérifications de cohérence supplémentaires. Avec ce drapeau, les éventuelles corruptions de la base de données sont découvertes à l'ouverture de celle-ci, au lieu d'être lues lors de la lecture d'une structure corrompue pendant le fonctionnement normal. Cependant, sur de grandes bases de données, cela peut ralentir le processus d'ouverture.
Les drapeaux supplémentaires suivants sont valides lorsque la base de données est ouverte en écriture (GDBM_WRITER, GDBM_WRCREAT ou GDBM_NEWDB) :
GDBM_SYNC
Force la synchronisation de toutes les opérations de la base de données sur le disque.

NOTE : cette option entraîne une grave dégradation des performances et ne garantit pas nécessairement que l'état résultant de la base de données soit cohérent. Nous déconseillons donc son utilisation. Pour savoir comment assurer la cohérence de la base de données avec une charge de performance minimale, consultez la section TOLÉRANCE AUX PANNES ci-dessous.

GDBM_FAST
L'inverse de GDBM_SYNC : synchronise les écritures uniquement lorsque nécessaire. C'est le comportement par défaut. Ce drapeau est fourni uniquement pour la compatibilité avec les versions précédentes de GDBM.

Convention

d'appel

Toutes les fonctions GDBM prennent comme premier paramètre le descripteur de base de données (GDBM_FILE), retourné par gdbm_open, gdbm_fd_open, ou gdbm_open_ext

.

Toute valeur stockée dans la base de données GDBM est décrite par datum, un type agrégé défini comme

: 
typedef struct
{
  char *dptr;
  int   dsize;
} datum;

Le champ dptr pointe vers les données réelles. Son type est char * pour des raisons historiques. En fait, il aurait dû être typé void *. Les programmeurs sont libres de stocker des données de complexité arbitraire, à la fois scalaires et agrégées, dans ce

champ.

Le champ dsize contient le nombre d'octets stockés dans dptr

.

Le type datum est utilisé pour décrire à la fois les clés et le contenu (valeurs) dans la base de données. Les valeurs de ce type peuvent être passées en arguments ou retournées par des appels de fonction GDBM

.

Les fonctions GDBM qui retournent un datum indiquent un échec en définissant leur champ dptr à NULL

.

Les fonctions retournant une valeur entière indiquent le succès en retournant 0 et l'échec en retournant une valeur non nulle (la seule exception à cette règle est gdbm_exists, pour lequel la valeur de retour est inversée)

.

Si la valeur retournée indique un échec, la variable gdbm_errno contient une valeur entière indiquant ce qui s'est mal passé. Une valeur similaire est associée au descripteur dbf et peut être accessible en utilisant la fonction gdbm_last_errno. Immédiatement après le retour d'une fonction, les deux valeurs sont exactement égales. Des appels GDBM ultérieurs avec un autre dbf comme argument peuvent altérer la valeur de la variable globale gdbm_errno, mais la valeur retournée par gdbm_last_errno indiquera toujours le code d'erreur le plus récent survenu pour cette base de données particulière. Il est encouragé aux programmeurs d'utiliser ces codes d'erreur par base de

données.

Parfois, la raison réelle de l'échec peut être clarifiée en examinant la valeur système errno. Pour vous assurer que sa valeur est significative pour un code d'erreur GDBM donné, utilisez la fonction gdbm_check_syserr. La fonction prend le code d'erreur en argument et retourne 1 si errno est significatif pour cette erreur, ou 0 s'il est sans

rapport.

De manière similaire à gdbm_errno, la valeur errno la plus récente associée à une base de données particulière peut être obtenue en utilisant la fonction gdbm_last_syserr

.

La fonction gdbm_clear_error efface l'indicateur d'erreur (les codes d'erreur GDBM et système) associé à un descripteur de base de

données.

Certaines erreurs critiques laissent la base de données dans un état structurellement incohérent. Si cela se produit, tous les appels GDBM ultérieurs accédant à cette base de données échoueront avec le code d'erreur GDBM GDBM_NEED_RECOVERY (une fonction spéciale gdbm_needs_recovery est également fournie, qui retourne vrai si le descripteur de base de données donné en argument est structurellement incohérent). Pour ramener de telles bases de données à un état cohérent, utilisez la fonction gdbm_recover (voir ci-dessous)

.

L'erreur GDBM_NEED_RECOVERY ne peut pas être effacée en utilisant gdbm_clear_erro

r
.

TOLÉRANCE AUX

PANNES

Par défaut, GNU dbm ne protège pas l'intégrité de ses bases de données contre la corruption ou la destruction due à des pannes telles que les coupures de courant, les paniques du noyau du système d'exploitation ou les plantages de processus d'application. De telles pannes pourraient endommager ou détruire la base de données

sous-jacente.

À partir de la version 1.21, GNU dbm inclut un mécanisme qui, s'il est utilisé correctement, permet la récupération après panne vers un état cohérent de la base de données sous-jacente. Ce mécanisme nécessite la prise en charge du système d'exploitation et du système de fichiers et doit être demandé lorsque gdbm est compilé. Le mécanisme de tolérance aux pannes est une fonctionnalité « purement optionnelle », en ce sens qu'il n'a aucun effet quelconque, sauf sur les applications qui le demandent explicitement. Pour plus de détails, voir le chapitre Tolérance aux pannes dans le manuel

GD
BM.
