NOM

history - Enregistrement des articles Usenet actuels et récemment expirés

DESCRIPTION

Le fichier pathdb/history conserve un enregistrement de tous les articles actuellement stockés dans le système de news, ainsi que de ceux qui ont été reçus mais ont depuis expiré. Dans un environnement de production typique, ce fichier fera plusieurs mégaoctets.

Le fichier se compose de lignes de texte. Chaque ligne correspond à un article. Le fichier est normalement conservé trié dans l'ordre de réception des articles, bien que ce ne soit pas une exigence. innd ajoute une nouvelle ligne chaque fois qu'il classe un article, et expire construit une nouvelle version du fichier en supprimant les anciens articles et en purgant les anciennes entrées.

Chaque ligne se compose de deux ou trois champs séparés par une tabulation, indiqués ci-dessous par " \t " :

[hash] \t date
[hash] \t date \t @token@

Le champ hash est la représentation ASCII du hachage de l'identifiant de message (Message-ID). Il est directement utilisé comme clé pour le dbz.

Le champ date se compose de trois sous-champs séparés par un tilde. Tous les sous-champs sont la représentation textuelle du nombre de secondes écoulées depuis l'époque, c'est-à-dire un time_t comme dans gettimeofday(2). Le premier sous-champ est la date d'arrivée de l'article. Si des copies de l'article sont toujours présentes, le deuxième sous-champ est soit la valeur du champ d'en-tête Expires de l'article, soit un tiret si aucune date d'expiration n'a été spécifiée. Si un article a expiré, le deuxième sous-champ sera un tiret. Le troisième sous-champ est la valeur du champ d'en-tête Date de l'article, enregistrant quand l'article a été posté.

Le champ token est un jeton de l'article. Ce champ est vide si l'article a expiré.

Par exemple, un article dont l'identifiant de message était <7q2saq$sal$1@isrv4.pa.vix.com>, posté le 26 août 1999 08:02:34 GMT et reçu le 26 août 1999 08:06:54 GMT, pourrait avoir une ligne d'historique (divisée en trois lignes pour l'affichage) comme suit :

[E6184A5BC2898A35A3140B149DE91D5C] \t
    935678987~-~935678821 \t
    @030154574F00000000000007CE3B000004BA@

En plus du fichier texte, il existe une base de données dbz associée au fichier qui utilise le champ Message-ID comme clé pour déterminer le décalage dans le fichier texte où commence la ligne associée. Pour des raisons historiques, la clé inclut l'octet "\0" final (qui n'est pas stocké dans le fichier texte).
