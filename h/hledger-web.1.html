DESCRIPTIO

N

Ce manuel concerne l'interface web de hledger, version 1.51. Voir aussi le manuel de hledger pour les concepts communs et les formats de

fichiers.

hledger est un ensemble de programmes robuste, convivial et multiplateforme pour suivre l'argent, le temps ou toute autre marchandise, utilisant la comptabilité en partie double et un format de fichier simple et éditable. hledger est inspiré par et largement compatible avec ledger(1), et largement interconvertible avec beancount(1)

.

hledger-web est une application web simple pour parcourir et ajouter des transactions. Elle fournit une interface utilisateur plus conviviale que la CLI hledger ou l'interface TUI hledger-ui, affichant plus d'informations à la fois (comptes, le registre du compte courant, graphiques de balance) et permettant une saisie de données tenant compte de l'historique, une recherche interactive et l'ajout de

signets.

hledger-web vous permet également de partager un journal avec plusieurs utilisateurs, ou même avec le public. Il n'y a pas de contrôle d'accès, donc si vous en avez besoin, vous devriez le placer derrière un proxy web approprié. En guise de petite protection contre la perte de données lors de l'exécution d'une instance non protégée, il écrit une sauvegarde numérisée du fichier journal principal (uniquement) à chaque

modification.

Comme hledger, il lit depuis (et ajoute à) un fichier journal spécifié par la variable d'environnement LEDGER_FILE (par défaut $HOME/.hledger.journal) ; ou vous pouvez spécifier des fichiers avec les options -f. Il peut aussi lire des fichiers timeclock, des fichiers timedot, ou n'importe quel fichier CSV/SSV/TSV avec un champ date. (Voir hledger(1) -> Input pour plus de détails.

)

hledger-web peut être exécuté dans trois modes

:
•
mode --serve-browse (par défaut) : l'application sert l'interface web et l'API JSON, et ouvre votre navigateur web par défaut pour afficher l'application si possible, et se termine automatiquement après deux minutes d'inactivité (sans requête reçue et sans fenêtre de navigateur ouverte la visualisant)
.
•
--serve : l'application sert simplement l'interface web et l'API
JSON.
•
--serve-api : l'application se

Dans tous les cas, hledger-web s'exécut

OPTION

S

hledger-web fournit les options suivantes

: 
Drapeaux :
     --serve --server       servir et journaliser les requêtes, ne pas naviguer ni se terminer automatiquement
     --serve-api            comme --serve, mais ne servir que l'API web JSON,
                            pas l'interface web
     --allow=view|add|edit  définir le niveau d'accès de l'utilisateur pour modifier les données
(par défaut : `add`). Accepte aussi `sandstorm` pour une utilisation sur cette plateforme (lit les permissions depuis l'en-tête de requête `X-Sandstorm-Permissions`). --cors=ORIGIN autoriser les requêtes cross-origin depuis l'origine spécifiée ; défin
ir ORIGIN à "*" autorise les requêtes depuis n'importe quelle origine --host=IPADDR écouter sur cette adresse IP (par défaut : 127.0.0.1) --port=PORT écouter sur ce port TCP (par défaut : 5000) --socket=SOCKET écouter sur la socket unix donnée au lieu d'une adresse
IP et d'un port (uniquement unix ; implique --serve) --base-url=BASEURL définir l'URL de base (par défaut : http://IPADDR:PORT) --test exécuter les tests de hledger-web et quitter. Les arguments du moteur de test hspec peuvent suivre un --, ex : hledger-web --test --help

Par défaut, hledger-web n'écoute que sur l'adresse IP 127.0.0.1, qui n'est accessible que depuis la machine

locale.

Pour autoriser l'accès depuis l'extérieur, utilisez --host pour spécifier une adresse accessible depuis l'extérieur configurée sur cette machine. L'adresse spéciale 0.0.0.0 le fait écouter sur toutes les adresses de cette

machine.

De même, vous pouvez utiliser --port pour écouter sur un port TCP autre que 5000. C'est utile si vous voulez exécuter plusieurs instances de hledger-web sur une

machine.

Quand --socket est utilisé, hledger-web crée et communique via un fichier socket au lieu d'un port TCP. Cela peut être plus sécurisé, respecte les permissions de fichiers unix, et rend certains cas d'utilisation plus faciles, comme l'exécution d'instances par utilisateur derrière un proxy inverse nginx. (Ex : proxy_pass http://unix:/tmp/hledger/${remote_use

r}.socket;.)

Vous pouvez utiliser --base-url pour changer le protocole, le nom d'hôte, le port et le chemin qui apparaissent dans les hyperliens de hledger-web. C'est utile, par exemple, pour intégrer hledger-web dans un site web plus large. La valeur par défaut est http://HOST:PORT/ utilisant l'adresse hôte configurée du serveur et le port TCP (ou http://HOST si PORT est 80). Notez que cela affecte la génération d'URL mais pas l'analyse des

routes.

hledger-web affiche les comptes avec des soldes nuls par défaut (comme hledger-ui, et contrairement à hledger). En utilisant le drapeau -E/--empty, ce comportement sera inversé. Si vous voyez des comptes qui semblent avoir un solde nul, mais qui ne peuvent pas être masqués avec -E, c'est parce qu'ils ont un solde à coût mixte, qui ressemble à zéro lorsque les coûts sont masqués. (hledger-web n'affiche pas les coûts.

)

.

PERMISSION

S

Par défaut, hledger-web permet à toute personne qui peut y accéder de consulter le journal et d'ajouter de nouvelles transactions, mais pas de modifier les données

existantes.

Vous pouvez restreindre qui peut y accéder,

en
•
définissant l'adresse IP sur laquelle il écoute (voir --host ci-dessus). Par défaut, il écoute sur 127.0.0.1, accessible uniquement aux utilisateurs sur la machine
locale.
•
en le plaçant derrière un proxy d'authentification, comme caddy ou
apache
•
en le plaça
nt derrière
un pare-feu

Et vous pouvez restreindre ce que les utilisateurs qui y accèdent peuvent faire, en spécifiant l' option --allow=ACCESSLEVEL au démarrage. ACCESSLEVEL est l'un des suivants

:
•
view - permet de consulter le(s) fichier(s)
journal
•
add - permet aussi d'ajouter de nouvelles transactions au fichier journal
principal
•
edit - permet aussi d'éditer, de téléverser ou de télécharger le(s) fichier(s)
journal
•
sandstorm - (pour l'application Sandstorm de hledger-web :) permet l'un des niveaux parmi view, add, ou edit qui sont spécifiés dans l' en-tête HTTP X-Sandstorm-Permissio
n
s

Le niveau d'accès par défaut est ad

d

ÉDITION, TÉLÉVERSEMENT,

TÉLÉCHARGEMENT

Si vous activez la capacité manage mentionnée ci-dessus, vous verrez un nouveau bouton "clé à molette" à droite du formulaire de recherche. Cliquer dessus vous permettra d'éditer, de téléverser ou de télécharger le fichier journal ou tout fichier qu'il

inclut.

Notez que, contrairement à toute autre commande hledger, dans ce mode vous (ou tout visiteur) pouvez altérer ou effacer les fichiers de

données.

Normalement, chaque fois qu'un fichier est modifié de cette manière, hledger-web enregistre une sauvegarde numérotée (en supposant que les permissions de fichier le permettent, que le disque n'est pas plein, etc.) hledger-web n'est pas conscient des systèmes de contrôle de version, actuellement ; si vous en utilisez un, vous devrez organiser vous-même la validation des modifications (par ex. avec une tâche cron ou un observateur de fichiers comme entr)

.

Les modifications qui laisseraient le(s) fichier(s) journal non analy

sable ou non valide (par ex. avec des assertions de solde en échec
) sont empêchées. (Probablement. Cela nécessite un nouveau test.)

RECHARGEMEN

T

hledger-web détecte les modifications apportées aux fichiers par d'autres moyens (par ex. si vous l'éditez directement, en dehors de hledger-web), et il affichera les nouvelles données lorsque vous rechargez la page ou naviguez vers une nouvelle page. Si une modification rend un fichier non analysable, hledger-web affichera un message d'erreur jusqu'à ce que le fichier ait été

corrigé.

(Note : si vous consultez des fichiers montés depuis

une autre machine, assurez-vous que les horlog
es des deux machines sont à peu près synchronisées.)

DÉBOGAGE

Sortie de

débogage

Vous pouvez ajouter --debug[=N] à la ligne de commande pour journaliser la sortie de débogage. N varie de 1 (sortie minimale, la valeur par défaut) à 9 (sortie maximale). Typiquement, vous commenceriez avec 1 et augmenteriez jusqu'à obtenir suffisamment d'informations. La sortie de débogage va vers stderr, entremêlée avec les requêtes journalisées sur stdout. Pour capturer la sortie de débogage dans un fichier journal à la place, vous pouvez généralement rediriger stderr, par ex.
