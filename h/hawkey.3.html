Introductio

n

Ce document décrit les changements d'API dont les utilisateurs de la bibliothèque doivent être conscients avant de passer à chaque version respective. Notre plan est que le nombre de changements nécessitant une modification du code client soit réduit au minimum après que la bibliothèque ait atteint la version 1.0.

0.

Les éléments d'API dépréciés (classes, méthodes, etc.) sont désignés comme tels dans ce document. La première version où le support de ces éléments peut être entièrement abandonné doit être publiée au moins cinq mois après la publication de la version qui a annoncé la dépréciation et doit en même temps avoir, relativement à la version de dépréciation, soit

:
  • un numéro de version majeur plus élevé,
    • ou
  • un numéro de version mineur plus élevé,
    • ou
  • un numéro de patch qui est supérieur
    • d'au m
oins
cinq.

Ces critères sont susceptibles de se resserrer à l'avenir à mesure que hawkey

mûrit.

Les changements réels dans l'API sont ensuite également annoncés dans ce document. Les changements d'ABI, y compris les changements dans le nombre ou les types des paramètres des fonctions ou la suppression de symboles publics de libhawkey impliquent une augmentation d

e la version SONAME
de la bibliothèque.

Liaisons

Query.filter() renvoie maintenant une nouvelle instance de Query, identique à l'originale avec le nouveau filtrage appliqué. Cela permet une plus grande flexibilité dans la gestion des objets Query et ressemble à la manière dont les QuerySets se comportent dans

Django.

En pratique, le code suivant cessera de fonctionner comme prévu

# traitement de la requête

La sémantique originale est maintenant disponible via la méthode Query.filterm(), donc ce qui suit fonctionnera aussi

Dans Python, les accesseurs des instances Package pour les attributs de chaîne renvoient maintenant None au lieu de la chaîne vide si l'attribut est manquant (par exemple, si pkg.sourcerpm renvoie maintenant None si pkg est déjà un paquet rpm source)

Gestion des

erreurs

Lorsqu'une erreur ou un événement inattendu se produit pendant une routine Hawkey, une exception est levée

:
  • s'il s'agit d'une erreur générale qui pourrait être courante dans d'autres programmes Python, l'une des exceptions intégrées standard de Python est levée. Par exemple, IOError et TypeError peuvent être levés depuis
    • Hawkey.
  • les erreurs de programmation au sein de Hawkey qui causent des états inattendus ou invalides lèvent l' AssertionError standard. Celles-ci doivent être signalées comme des bugs contre
    • Hawkey.
  • les erreurs de programmation dues à une utilisation incorrecte de la bibliothèque produisent généralement hawkey.ValueException ou l'une de ses sous-classes, QueryException (Query mal formé) ou ArchException (architecture non reconnue)
    • .
  • parfois il y a un cas limite entre imputer l'erreur à un paramètre d'entrée ou à autre chose, au-delà du contrôle du programmeur. hawkey.RuntimeException est généralement utilisé dans ce
    • cas.
  • hawkey.ValidationException est levée lorsqu'un appel de fonction effectu
    • e un contrôle préliminaire ava
nt de procéder à l'opération princip
ale et que ce contrôle échoue.

JUSTIFICATION DE LA

CONCEPTION

Les Selectors ne sont pas des

Queries

Puisqu'à la fois une Query et un Selector servent à limiter l'ensemble de tous les paquets du Sack à un sous-ensemble, on pourrait suggérer que les deux concepts devraient être identiques et que, par exemple, les Queries devraient être utilisées pour les spécifications de Goal au lieu des Selectors

: 
// créer le sac, le goal, ...
HyQuery q = hy_query_create(sack);
hy_query_filter(q, HY_PKG_NAME, HY_EQ, "anaconda")
hy_goal_install_query
(
q
)

Cet arrangement était en fait utilisé dans hawkey avant la version 0.3.0, simplement parce que les Queries semblaient une structure pratique pour contenir ce type d'informations. C'était malheureusement déroutant pour les programmeurs : remarquez comment l'évaluation de la Query q produirait généralement plusieurs paquets (anaconda pour différentes architectures et ensuite différentes versions) mais d'une certaine manière, lorsque la même Query est passée aux méthodes du goal, elle résulte toujours en au plus un paquet sélectionné pour l'opération. C'est une discrepancy fondamentale. De plus, Query est universel et permet de limiter l'ensemble des paquets avec toutes sortes de critères, appariés de différentes manières (sous-chaînes, globbing, opération sur les ensembles) alors que les Selectors ne supportent que quelques-uns. Enfin, alors qu'une Query fraîche sans filtre appliqué correspond à tous les paquets du Sack, un Selector frais sans limites définies n'a aucun

sens.

Une alternative à l'introduction d'un concept complètement différent était d'ajouter une fonction constructeur séparée pour Query, une qui désignerait dès le départ la Query à n'accepter que des paramètres compatibles avec son objectif de devenir le sélecng element in a Goal operation (in Python this would probably be implemented as a subclass of Query). But that would break client's assumptions about Query (the unofficial C++ FAQ http://www.parashift.com/c++-faq/circle-ellipse.html takes up the topic)

.

Note d'implémentation : Les sélecteurs reflètent le type de spécifications qui peuvent être directement traduites en tâches Libsolv, sans rechercher en fait un paquet concret à y placer. En d'autres termes, les sélecteurs sont spécifiquement conçus pour ne pas itérer sur les données des paquets (à quelques exceptions près, comme la correspondance de motifs) comme le font les requêtes. Bien que Hawkey vise principalement à masquer les subtilités et les complexités de la bibliothèque sous-jacente, dans ce cas, les raisons combinées justifient une

concession.
