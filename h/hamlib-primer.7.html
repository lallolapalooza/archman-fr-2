HAMLIB-PRIMER(7) Manuel d'information Hamlib HAMLIB-PRIMER(7)

NOM

hamlib-primer - compilation et utilisation de la bibliothèque de contrôle de radio et de rotacteur

DESCRIPTION

Il existe plusieurs façons d'obtenir une installation fonctionnelle de Hamlib. Les sections suivantes traitent de l'installation à partir d'un gestionnaire de paquets, de la compilation à partir des sources et de l'installation des binaires fournis par le projet Hamlib sous Microsoft Windows®.

Installation de paquets binaires sous Linux et BSD

La manière la plus simple d'installer une version publiée de Hamlib sur une distribution basée sur Linux ou une variante BSD est d'utiliser le gestionnaire de paquets fourni. Bien que les gestionnaires de paquets varient selon la distribution (il est facile d'y inclure les variantes BSD), leur objectif final est de fournir des paquets logiciels prêts à l'emploi. Étant donné la grande variété de gestionnaires de paquets existants, il est préférable de recommander la documentation de votre distribution choisie comme guide.

Une variété de sources Hamlib

Les paquets de distribution sont le plus souvent des versions officielles de Hamlib et, dans certains cas, peuvent être assez anciens et manquer de support pour les radios ou les rotacteurs plus récents. Dans certains cas, le support est amélioré dans les backends existants de radio ou de rotacteur et les bogues sont corrigés dans les versions plus récentes. Souvent, pour obtenir le support amélioré/les corrections de bogues, la compilation à partir des sources sera nécessaire. Détendez-vous, ce n'est pas difficile. :-)

Le code source est disponible sous forme de versions officielles, d'instantanés de test, d'instantanés de développement quotidiens et de la pointe du développement directement depuis le dépôt Git. En règle générale, même les archives de pointe devraient se configurer et compiler sans erreur, bien que certains travaux d'implémentation puissent être en cours et être incomplets ou contenir des erreurs.

Obtenir les sources publiées

Les versions officielles des sources Hamlib, communément appelées tarballs, peuvent être trouvées sur la page Web des fichiers Hamlib de SourceForge.net. La version la plus récente est listée en premier.

Obtenir des instantanés des sources

Les candidats versions de test (RC) sont publiés pendant la période (souvent quelques semaines) précédant une version planifiée. À partir de la version 4.0, les RC sont hébergés sur la page Web des fichiers Hamlib de SourceForge.net. Les RC sont identifiés par le suffixe ~rcX où X est remplacé par un chiffre pour les candidats versions successifs.

Des instantanés quotidiens du dépôt de développement sont disponibles via le World Wide Web à partir des instantanés quotidiens Git de Hamlib. Ce ne sont pas des versions officielles mais elles sont fournies pour tester de nouvelles fonctionnalités et des corrections de bogues.

L'instantané de développement quotidien est créé et publié chaque jour vers 1030 UTC. Les instantanés quotidiens devraient compiler, mais parfois un bogue s'introduit qui empêche la compilation. Si cela se produit, veuillez le signaler à la liste de diffusion hamlib-developer.

Dépôt Git

Le dépôt source peut être cloné, ce qui copie le dépôt sur votre ordinateur, y compris son historique complet, ses branches et les informations de balisage de version. En d'autres termes, une fois la commande git(1) clone terminée, une copie complète du développement Hamlib sera sur votre ordinateur. Vous pouvez faire beaucoup de choses avec cela car rien n'est caché à la vue, l'intégralité de l'historique de Hamlib étant présente, depuis le tout premier commit jusqu'à maintenant. Aucune métadonnée n'est cachée sur un serveur central.

Pour cloner le dépôt, utilisez la commande suivante :


git clone https://git.code.sf.net/p/hamlib/code hamlib

ou :


git clone https://github.com/Hamlib/Hamlib.git

Il y a de fortes chances que vous souhaitiez exécuter la commande ci-dessus dans un sous-répertoire de votre répertoire personnel. Le répertoire hamlib sera créé par Git et la branche master sera extraite pour vous en tant que copie de travail. La branche master est l'une des plusieurs branches utilisées dans le développement de Hamlib. C'est la branche principale pour les nouvelles fonctionnalités et les corrections de bogues. La copie de travail contiendra la dernière révision de chaque fichier au moment du clonage. Les mises à jour ultérieures des développeurs nécessiteront l'utilisation d'une autre commande Git pour mettre à jour votre dépôt local.

Compilation à partir des sources

La compilation à partir des sources sera nécessaire pour diverses raisons. Peut-être que seule une ancienne version est fournie par votre distribution, ou vous souhaitez tester des modifications récentes de Hamlib — que ce soit un backend spécifique ou des changements d'API — et offrir un rapport aux développeurs, ou vous souhaitez participer au développement et offrir votre contribution au projet, ou vous souhaitez simplement apprendre à compiler un paquet relativement complet à partir des sources. Chacune de ces raisons est valable pour compiler à partir de l'archive du code source.

Avant d'aller plus loin, ce manuel suppose que vous êtes familiarisé avec le travail à partir de l'invite de commande dans l'environnement du Bourne shell d'un système de type Linux/BSD/Unix (les shells Bourne compatibles incluent bash(1), ksh(1), zsh(1), et plusieurs autres) soit dans une console virtuelle (un écran texte uniquement sans graphiques) soit dans un terminal d'un environnement de bureau (xterm(1), rxvt(1), konsole(1) (inclus avec le bureau KDE), gnome-terminal(1), xfce4-terminal(1), terminal(1) (inclus dans macOS), etc.). Si cela est nouveau pour vous, prenez le temps de lire sur l'utilisation du shell. Un bon tutoriel se trouve sur LinuxCommand.org qui propose également un livre approfondi qui peut être acheté ou téléchargé gratuitement (le projet Hamlib n'est pas associé ni n'a d'intérêt dans la vente de ce livre, il semble simplement s'agir d'un très bon effort de la part de son auteur).

Commençons.

Compilation des archives sources

Avant de continuer, il est essentiel de lire les informations contenues dans les fichiers README.md, INSTALL et README.betatester fournis dans le répertoire de haut niveau de Hamlib, qui sera nommé quelque chose comme hamlib-3.3~git où la partie ultérieure est la version publiée. Dans ce cas, 3.3~git indique qu'il s'agit d'un instantané de développement de la branche principale Git. Ces fichiers fournissent des informations détaillées pour compiler Hamlib et varient quelque peu d'une version à l'autre.

La compilation à partir d'une archive source, qu'il s'agisse d'une version officielle ou d'un instantané de test ou de développement quotidien, suit le même ensemble de commandes, connu sous le nom des trois étapes, chacune étant exécutée à partir du répertoire de haut niveau :


./configure
make
sudo make install

configure

La commande ./configure examine votre système et vérifie les paquets requis ou les options utiles pour compiler Hamlib. Le ./ en préfixe indique au shell de n'exécuter que la commande configure trouvée dans le répertoire courant. Il est toujours possible qu'une commande configure se trouve ailleurs et nous ne voulons pas exécuter celle-là !

Exécutez :


./configure

depuis le répertoire de haut niveau.

Note : Certaines distributions sont configurées de manière à ce que seules les commandes des répertoires listés dans la variable d'environnement PATH puissent être exécutées. Le ./ est nécessaire ou la commande configure ne sera pas exécutée car le répertoire courant (défini comme .) n'est pas dans le PATH. Ceci est considéré comme une fonctionnalité de sécurité par défaut afin que seuls les programmes fournis par la distribution soient exécutés. Le PATH peut être modifié

pour votre propre session, mais c'est un sujet pour la référence LinuxCommand.org ci-dessus.

Bien sûr, les choses sont généralement compliquées par des options et Hamlib ne fait pas exception. La bonne nouvelle est que les valeurs par défaut, c'est-à-dire sans options, fonctionnent bien dans la plupart des situations. Des options sont nécessaires pour activer la compilation de certaines parties de Hamlib, telles que les liaisons linguistiques. Les fonctionnalités optionnelles nécessitent généralement que davantage d'outils de développement soient installés. Les fichiers INSTALL et README.betatester dans le répertoire de niveau supérieur de Hamlib contiennent des détails sur les options disponibles pour cette version.

Une option utile est --prefix, qui indique à configure où dans la hiérarchie du système de fichiers Hamlib doit être installé. S'il n'est pas fourni, Hamlib sera installé dans la hiérarchie du système de fichiers /usr/local. Vous voudrez peut-être l'installer dans votre répertoire personnel à la place :


./configure --prefix=$HOME/local
Remarque : Pour vous entraîner, vous pouvez souhaiter commencer par utiliser l'option --prefix=$HOME/local pour installer les fichiers Hamlib dans votre répertoire personnel et éviter d'écraser toute version de Hamlib installée dans les répertoires système. Les exemples de code dans le reste de ce manuel supposeront que Hamlib a été installé dans $HOME/local.

En conséquence de cette option, tous les fichiers seront installés dans le répertoire local de votre répertoire personnel. local sera créé s'il n'existe pas lors de l'installation, ainsi que plusieurs autres répertoires à l'intérieur. L'installation dans votre répertoire personnel signifie que les privilèges de root, ou superutilisateur (administrateur), ne sont pas requis lors de l'exécution de make install. D'un autre côté, un travail supplémentaire sera nécessaire pour que d'autres programmes puissent utiliser la bibliothèque. Les utilitaires qui sont compilés dans le cadre du système de construction de Hamlib fonctionneront car ils sont liés à la bibliothèque installée sous local. Leur exécution nécessitera de déclarer le chemin complet :


local/bin/rigctl

ou de modifier la variable d'environnement PATH de votre shell (voir le site du tutoriel sur le shell ci-dessus).

Une autre option utile est --help, qui affichera plusieurs écrans d'options pour configure. Si vous êtes dans un environnement de bureau, la barre de défilement peut être utilisée pour remonter dans la sortie. Que ce soit dans un terminal ou une console virtuelle, Linux prend en charge la combinaison de touches Shift-PageUp pour remonter dans la sortie. Inversement, Shift-PageDown peut être utilisé pour descendre vers la fin de la sortie et l'invite du shell (Shift-FlècheHaut/Shift-FlècheBas peuvent également fonctionner pour faire défiler une ligne à la fois (dépend du terminal)).

Après un certain temps, selon votre ordinateur, et beaucoup de sortie d'écran, configure terminera son travail. Tant que les quelques lignes précédant l'invite du shell ne disent pas « error » ou un message d'échec similaire, Hamlib est prêt à être compilé. En cas d'erreur et si tous les paquets requis listés dans README.betatester ont été installés, veuillez demander de l'aide sur la liste de diffusion hamlib-developer.

make

La commande make(1) est responsable de l'exécution du compilateur, qui lit les fichiers source et, à partir des instructions qu'il y trouve, écrit des fichiers objet qui sont les instructions binaires que le processeur d'un ordinateur peut exécuter. make appelle ensuite l' éditeur de liens, qui assemble les fichiers objet dans le bon ordre pour créer les fichiers de bibliothèque Hamlib et ses programmes exécutables.

Exécutez :


make

depuis le répertoire de niveau supérieur.

Toute erreur qui amène make à s'arrêter prématurément est une raison pour poser une question à la liste de diffusion hamlib-developer.

En général, make prendra plus de temps que configure pour terminer son exécution. Comme il s'agit d'une commande système, et donc trouvée dans la variable d'environnement PATH du shell, préfixer make avec ./ provoquera une erreur « command not found » de la part du shell.

make install

En supposant que vous n'avez pas défini le préfixe d'installation dans votre répertoire personnel, des privilèges root (administrateur) seront nécessaires pour installer Hamlib dans les répertoires système. Deux méthodes populaires existent pour obtenir les privilèges root : su(1) et sudo(8). sudo est probablement le plus populaire de nos jours, en particulier lors de l'utilisation de la famille de distributions Ubuntu.

Exécutez :


sudo make install

ou :


$ su -l
Password:
# make install

en tant que root depuis le répertoire de niveau supérieur.

Remarque : La session shell est montrée pour illustrer le changement d'invite d'un compte utilisateur normal à un compte root.

L'option -l de su force un shell de connexion afin que les variables d'environnement telles que PATH soient correctement définies.

L'exécution de make install appellera l'installateur pour placer tous les fichiers nouvellement compilés et d'autres fichiers (comme ce document) dans des emplacements prédéterminés par l'option --prefix de configure dans la hiérarchie des répertoires (oui, c'est intentionnel et make ne lance pas les fichiers n'importe où !).

Une grande quantité de sortie d'écran sera générée. Les erreurs seront probablement plutôt tôt dans le processus et seront probablement liées au fait que votre nom d'utilisateur n'a pas les permissions d'écriture dans la structure des répertoires système.

ldconfig

Une fois l'installation terminée, une étape supplémentaire est requise si Hamlib n'a jamais été installé à partir d'une compilation locale auparavant. La commande ldconfig indique au chargeur de bibliothèques du système où trouver les bibliothèques Hamlib nouvellement installées. Elle devra également être exécutée avec des privilèges root :

Exécutez :


sudo ldconfig

en tant que root depuis n'importe quel répertoire ou en étant connecté en tant que root depuis ci-dessus.

Remarque : Les installations ultérieures de Hamlib ne nécessiteront pas d'exécuter ldconfig après chaque installation si une version plus récente de Hamlib n'a pas été installée, c'est-à-dire lors de la recompilation de la même version pendant le développement.

Sur certaines distributions, un peu de configuration sera nécessaire avant que ldconfig n'ajoute le logiciel compilé localement à sa base de données. Veuillez consulter la documentation de votre distribution.

Démarrage à partir d'un 'git clone'

Choisir de compiler à partir d'un git clone nécessite quelques outils de développement supplémentaires (vous remarquez un thème ici ?) comme détaillé dans README.developer. Les plus critiques seront les GNU Autotools (autoconf, automake, libtool, et plus) à partir desquels le système de construction composé de configure, des divers Makefile.in dans toute la structure des répertoires, et des Makefile finaux sont générés.

Dans le répertoire de niveau supérieur se trouve le script bootstrap à partir duquel le système de construction est démarré — le processus de génération du système de construction de Hamlib à partir de configure.ac et des divers Makefile.am. À son achèvement, le script configure sera présent pour configurer le système de construction.

Ensuite, configure est exécuté avec les options de construction nécessaires ( configure --help est utile) pour activer certaines fonctionnalités ou fournir des chemins pour localiser les dépendances de construction nécessaires, etc. Des variables d'environnement destinées au préprocesseur et/ou au compilateur peuvent également être définies sur la ligne de commande de configure.

Une fois la configuration terminée, la compilation peut se poursuivre avec l'étape make comme pour les tarballs sources ci-dessus. Ou alors configure --help peut être exécuté, et configure réexécuté avec des options spécifiques, auquel cas les Makefile seront régénérés et la compilation pourra reprendre avec la nouvelle configuration.

Autres cibles make

Outre make install, d'autres cibles existent lors de l'exécution de make. L'exécution de make clean depuis le répertoire de niveau supérieur supprime tous les fichiers objet et exécutables générés par l'exécution de make, libérant ainsi un espace disque considérable.

Remarque : Lors du développement de fichiers source individuels, il n'est pas nécessaire d'exécuter make clean à chaque fois avant make. Exécutez simplement make et seuls les fichiers modifiés et les objets qui en dépendent seront recompilés. Cela accélère considérablement le temps de développement.

Pour supprimer même les Makefile générés, exécutez make distclean depuis le répertoire de niveau supérieur. Après l'exécution de cette cible, configure devra être exécuté à nouveau pour régénérer les Makefile. Cette commande peut ne pas être aussi utile car les Makefile ne prennent pas beaucoup de place, cependant elle peut être utile pour reconstruire les Makefile lors de la modification d'un Makefile.am ou configure.ac pendant le développement du système de construction.

Arbres de construction parallèles

Une caractéristique du système de construction GNU utilisé par Hamlib est que les fichiers objet peuvent être conservés dans une structure de répertoires distincte des fichiers source. Bien que cela n'ait aucun effet sur les cibles make décrites ci-dessus, cela aide le développeur à trouver les fichiers dans l'arborescence des sources ! Une telle façon d'utiliser les constructions parallèles est décrite dans README.developer.

Les constructions parallèles peuvent être très utiles car un répertoire de construction peut être configuré pour une version et un autre répertoire de construction peut être configuré pour le débogage avec différentes options passées à configure depuis chaque répertoire. Les Makefile générés sont uniques à chaque répertoire de construction et n'interféreront pas les uns avec les autres.

Ajout de symboles de débogage

Lorsque des symboles de débogage supplémentaires sont nécessaires avec, par exemple, le débogueur GNU, gdb, les options de compilateur et d'éditeur de liens nécessaires sont passées comme variables d'environnement.

Exécutez :


../hamlib/configure CFLAGS="-ggdb3 -O0" CXXFLAGS="-ggdb3 -O0"depuis un répertoire de construction frère destiné à une construction de 
débogage.

L'option -ggdb3 indique au compilateur C, dans ce cas le
    GNU C Compiler, gcc, d'ajouter des symboles spéciaux utiles pour GDB, le débogueur
    GNU. L'option -O0 indique à gcc de désactiver toutes les
    optimisations, ce qui facilitera le suivi de certaines variables qui pourraient
    sinon être optimisées. CFLAGS et CXXFLAGS peuvent être définis
    indépendamment pour chaque 
compilateur.
