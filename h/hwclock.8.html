HWCLOCK(8) Administration système HWCLOCK(8)

NOM

hwclock - utilitaire d'horloge matérielle

SYNTAXE

hwclock [fonction] [option...]

DESCRIPTION

hwclock est un outil d'administration pour les horloges. Il peut : afficher l'heure de l'horloge matérielle ; régler l'horloge matérielle à une heure spécifiée ; régler l'horloge matérielle à partir de l'horloge système ; régler l'horloge système à partir de l'horloge matérielle ; compenser la dérive de l'horloge matérielle ; corriger la base de temps de l'horloge système ; régler le fuseau horaire du noyau, la base de temps NTP et l'époque (Alpha uniquement) ; et prédire les futures valeurs de l'horloge matérielle en fonction de son taux de dérive.

Depuis la version v2.26, des changements importants ont été apportés à la fonction --hctosys et à l'option --directisa, et une nouvelle option --update-drift a été ajoutée. Voir leurs descriptions respectives ci-dessous.

FONCTIONS

Les fonctions suivantes sont mutuellement exclusives, une seule peut être donnée à la fois. Si aucune n'est donnée, la valeur par défaut est --show.

-a, --adjust

Ajoute ou soustrait du temps à l'horloge matérielle pour compenser la dérive systématique depuis la dernière fois que l'horloge a été réglée ou ajustée. Voir la discussion ci-dessous, sous La fonction d'ajustement.

--getepoch ; --setepoch

Ces fonctions sont uniquement pour les machines Alpha, et ne sont disponibles que via le pilote RTC du noyau Linux.

Elles sont utilisées pour lire et régler la valeur de l'époque de l'horloge matérielle du noyau. L'époque est le nombre d'années après J.-C. auquel une valeur d'année zéro dans l'horloge matérielle fait référence. Par exemple, si le BIOS de la machine règle le compteur d'années dans l'horloge matérielle pour contenir le nombre d'années complètes depuis 1952, alors la valeur de l'époque de l'horloge matérielle du noyau doit être 1952.

La fonction --setepoch nécessite l'utilisation de l'option --epoch pour spécifier l'année. Par exemple :

hwclock --setepoch --epoch=1952

Le pilote RTC tente de deviner la valeur correcte de l'époque, donc il n'est peut-être pas nécessaire de la régler.

Cette valeur d'époque est utilisée chaque fois que hwclock lit ou règle l'horloge matérielle sur une machine Alpha. Pour les machines ISA, le noyau utilise l'époque fixe de l'horloge matérielle de 1900.

--param-get=paramètre ; --param-set=paramètre=valeur

Lit et règle le paramètre du RTC. Ceci est utile, par exemple, pour récupérer la fonctionnalité du RTC ou pour régler le mode de commutation de secours du RTC.

paramètre est soit une valeur numérique de paramètre RTC (voir include/uapi/linux/rtc.h dans le noyau) soit un alias. Voir --help pour une liste des alias valides. paramètre et valeur, s'ils sont préfixés par 0x, sont interprétés comme des valeurs hexadécimales, sinon décimales.

--predict

Prédit ce que lira l'horloge matérielle dans le futur en fonction de l'heure donnée par l'option --date et des informations dans /etc/adjtime. Ceci est utile, par exemple, pour tenir compte de la dérive lors du réglage d'un réveil d'horloge matérielle (également appelé alarme). Voir rtcwake(8).

N'utilisez pas cette fonction si l'horloge matérielle est modifiée par autre chose que la commande hwclock du système d'exploitation actuel, comme le "mode 11 minutes" ou le démarrage d'un autre système d'exploitation.

-r, --show ; --get

Lit l'horloge matérielle et affiche son heure sur la sortie standard au format ISO 8601. L'heure affichée est toujours en heure locale, même si vous conservez votre horloge matérielle en UTC. Voir l'option --localtime.

L'affichage de l'heure de l'horloge matérielle est la valeur par défaut lorsqu'aucune fonction n'est spécifiée.

La fonction --get applique également une correction de dérive à l'heure lue, en fonction des informations contenues dans /etc/adjtime. N'utilisez pas cette fonction si l'horloge matérielle est modifiée par autre chose que la commande hwclock du système d'exploitation actuel, comme le "mode 11 minutes" ou le démarrage d'un autre système d'exploitation.

-s, --hctosys

Règle l'horloge système à partir de l'horloge matérielle. L'heure lue à partir de l'horloge matérielle est compensée pour tenir compte de la dérive systématique avant d'être utilisée pour régler l'horloge système. Voir la discussion ci-dessous, sous La fonction d'ajustement.

L'horloge système doit être maintenue à la base de temps UTC pour que les applications de date et d'heure fonctionnent correctement en conjonction avec le fuseau horaire configuré pour le système. Si l'horloge matérielle est maintenue en heure locale, alors l'heure qui en est lue doit être décalée vers la base de temps UTC avant d'être utilisée pour régler l'horloge système. La fonction --hctosys fait cela en se basant sur les informations du fichier /etc/adjtime ou des arguments de ligne de commande --localtime et --utc. Remarque : aucun ajustement de l'heure d'été n'est effectué. Voir la discussion ci-dessous, sous LOCAL vs UTC.

Le noyau conserve également une valeur de fuseau horaire, la fonction --hctosys la règle au fuseau horaire configuré pour le système. Le fuseau horaire du système est configuré par la variable d'environnement TZ ou le fichier /etc/localtime, tels que tzset(3) les interpréterait. Le champ obsolète tz_dsttime de la valeur de fuseau horaire du noyau est réglé sur zéro. (Pour des détails sur ce que signifiait ce champ auparavant, voir settimeofday(2).)

Lorsqu'elle est utilisée dans un script de démarrage, faisant de la fonction --hctosys le premier appelant de settimeofday(2) au démarrage, elle réglera la base de temps "mode 11 minutes" de NTP via la variable du noyau persistent_clock_is_local. Si la configuration de base de temps de l'horloge matérielle est modifiée, un redémarrage est nécessaire pour informer le noyau. Voir la discussion ci-dessous, sous Synchronisation automatique de l'horloge matérielle par le noyau.

C'est une bonne fonction à utiliser dans l'un des scripts de démarrage du système avant que les systèmes de fichiers ne soient montés en lecture/écriture.

Cette fonction ne doit jamais être utilisée sur un système en cours d'exécution. Sauter le temps système provoquera des problèmes, tels que des horodatages de système de fichiers corrompus. De plus, si quelque chose a modifié l'horloge matérielle, comme le "mode 11 minutes" de NTP, alors --hctosys réglera mal l'heure en incluant la compensation de dérive.

La compensation de dérive peut être inhibée en réglant le facteur de dérive dans /etc/adjtime à zéro. Ce réglage sera persistant tant que l'option --update-drift n'est pas utilisée avec --systohc à l'arrêt (ou ailleurs). Une autre façon d'inhiber cela est d'utiliser l'option --noadjfile lors de l'appel de la fonction --hctosys. Une troisième méthode consiste à supprimer le fichier /etc/adjtime. Hwclock utilisera alors par défaut la base de temps UTC pour l'horloge matérielle. Si l'horloge matérielle fonctionne en heure locale, elle devra être définie dans le fichier. Ceci peut être fait en appelant hwclock --localtime --adjust ; lorsque le fichier n'est pas présent, cette commande n'ajustera pas réellement l'horloge, mais créera le fichier avec l'heure locale configurée, et un facteur de dérive de zéro.

Une condition dans laquelle l'inhibition de la correction de dérive de hwclock peut être souhaitée est le démarrage simultané de plusieurs systèmes d'exploitation. Si, pendant que cette instance de Linux est arrêtée, un autre système d'exploitation modifie la valeur de l'horloge matérielle, alors lorsque cette instance redémarre, la correction de dérive appliquée sera incorrecte.

Pour que la correction de dérive de hwclock fonctionne correctement, il est impératif que rien ne modifie l'horloge matérielle pendant que son instance Linux n'est pas en cours d'exécution.

--set

Règle l'horloge matérielle à l'heure donnée par l'option --date, et met à jour les horodatages dans /etc/adjtime. Avec l'option --update-drift également (re)calcule le facteur de dérive. Essayez sans l'option si --set échoue. Voir --update-drift ci-dessous.

--systz

C'est une alternative à la fonction --hctosys qui ne lit pas l'horloge matérielle ni ne règle l'horloge système ; par conséquent, il n'y a aucune correction de dérive. Elle est destinée à être utilisée dans un script de démarrage sur des systèmes avec des noyaux supérieurs à la version 2.6 où vous savez que l'horloge système a été réglée à partir de l'horloge matérielle par le noyau pendant le démarrage.

Elle effectue les actions suivantes qui sont détaillées ci-dessus dans la fonction --hctosys :

•Corrige la base de temps de l'horloge système en UTC si nécessaire. Seulement

y au lieu de l'accomplir en réglant l'horloge système, hwclock informe simplement le noyau et celui-ci gère le changement.
•Définit l'échelle de temps du mode « 11 minutes » NTP du noyau.
•Définit le fuseau horaire du noyau.

Les deux premiers ne sont disponibles qu'à l'appel initial de settimeofday(2) après le démarrage. Par conséquent, cette option n'a de sens que lorsqu'elle est utilisée dans un script de démarrage. Si la configuration de l'échelle de temps de l'horloge matérielle est modifiée, un redémarrage serait nécessaire pour en informer le noyau.

-w, --systohc

Règle l'horloge matérielle à partir de l'horloge système et met à jour les horodatages dans /etc/adjtime. Avec l'option --update-drift également, (re)calcule le facteur de dérive. Essayez sans l'option si --systohc échoue. Voir --update-drift ci-dessous.

--vl-read, --vl-clear

Certains périphériques RTC sont capables de surveiller la tension de la batterie de secours et fournissent ainsi un moyen à l'utilisateur de savoir que la batterie doit être remplacée. La fonction --vl-read récupère les informations de faible tension et décode le résultat sous forme lisible par l'homme. La fonction --vl-clear réinitialise les informations de faible tension, ce qui est nécessaire pour certains périphériques RTC après le remplacement de la batterie.

Consultez include/uapi/linux/rtc.h du noyau pour plus de détails sur les informations qui peuvent être retournées. Notez que tous les périphériques RTC ne disposent pas de cette capacité de surveillance, et tous les pilotes ne prennent pas nécessairement en charge la lecture des informations.

-h, --help

Affiche le texte d'aide et quitte.

-V, --version

Affiche la version et quitte.

OPTIONS

--adjfile=nom_de_fichier

Remplace le chemin par défaut du fichier /etc/adjtime.

--date=chaîne_de_date

Cette option doit être utilisée avec les fonctions --set ou --predict, sinon elle est ignorée.

hwclock --set --date='16:45'

hwclock --predict --date='2525-08-14 07:11:05'

L'argument doit être en heure locale, même si vous gardez votre horloge matérielle en UTC. Voir l'option --localtime. Par conséquent, l'argument ne doit pas contenir d'informations de fuseau horaire. Il ne doit pas non plus s'agir d'une heure relative comme « +5 minutes », car la précision de hwclock dépend de la corrélation entre la valeur de l'argument et le moment où la touche Entrée est enfoncée. Les fractions de seconde sont silencieusement ignorées. Cette option est capable de comprendre de nombreux formats d'heure et de date, mais les paramètres précédents doivent être respectés.

--delay=secondes

Cette option peut être utilisée pour remplacer le délai interne lors du réglage de l'heure de l'horloge. La valeur par défaut est 0,5 (500 ms) pour rtc_cmos, pour les autres types RTC le délai est de 0. Si le type RTC est impossible à déterminer (via sysfs), il est également par défaut à 0,5 pour être rétrocompatible.

Le délai par défaut de 500 ms est basé sur le matériel couramment utilisé compatible MC146818A (x86). Cette horloge matérielle ne peut être réglée qu'à une heure entière plus une demi-seconde. L'heure entière est requise car il n'y a pas d'interface pour régler ou obtenir des fractions de seconde. Le délai supplémentaire d'une demi-seconde est dû au fait que l'horloge matérielle se met à jour à la seconde suivante précisément 500 ms après avoir réglé la nouvelle heure. Malheureusement, ce comportement est spécifique au matériel et dans certains cas, un autre délai est requis.

-D, --debug

Utilise --verbose. L'option --debug a été dépréciée et pourrait être réattribuée ou supprimée dans une future version.

--directisa

Cette option est significative pour les machines compatibles ISA des familles x86 et x86_64. Pour les autres machines, elle n'a aucun effet. Cette option indique à hwclock d'utiliser des instructions d'E/S explicites pour accéder à l'horloge matérielle. Sans cette option, hwclock utilisera le fichier périphérique rtc, qu'il suppose être piloté par le pilote de périphérique RTC Linux. Depuis la version 2.26, il n'utilisera plus automatiquement directisa lorsque le pilote rtc est indisponible ; cela provoquait une condition dangereuse qui pouvait permettre à deux processus d'accéder à l'horloge matérielle en même temps. L'accès direct au matériel depuis l'espace utilisateur ne doit être utilisé que pour les tests, le dépannage et en dernier recours lorsque toutes les autres méthodes échouent. Voir l'option --rtc.

--epoch=année

Cette option est requise lors de l'utilisation de la fonction --setepoch. La valeur minimale de année est 1900. La valeur maximale dépend du système (ULONG_MAX - 1).

-f, --rtc=nom_de_fichier

Remplace le nom de fichier du périphérique rtc par défaut de hwclock. Sinon, il utilisera le premier trouvé dans cet ordre : /dev/rtc0, /dev/rtc, /dev/misc/rtc. Pour IA-64 : /dev/efirtc /dev/misc/efirtc

-l, --localtime; -u, --utc

Indique le système de temps auquel l'horloge matérielle est réglée.

L'horloge matérielle peut être configurée pour utiliser le système de temps UTC ou le système de temps local, mais rien dans l'horloge elle-même n'indique quelle alternative est utilisée. Les options --localtime ou --utc fournissent cette information à la commande hwclock. Si vous spécifiez la mauvaise (ou aucune des deux et prenez un mauvais défaut), la lecture et le réglage de l'horloge matérielle seront incorrects.

Si vous ne spécifiez ni --utc ni --localtime, alors celui qui a été donné en dernier avec une fonction de réglage (--set, --systohc, ou --adjust), tel qu'enregistré dans /etc/adjtime, sera utilisé. Si le fichier adjtime n'existe pas, le défaut est UTC.

Note : les changements d'heure d'été peuvent être incohérents lorsque l'horloge matérielle est conservée en temps local. Voir la discussion ci-dessous, sous LOCAL vs UTC.

--noadjfile

Désactive les fonctionnalités fournies par /etc/adjtime. hwclock ne lira ni n'écrira dans ce fichier avec cette option. Soit --utc soit --localtime doit être spécifié lors de l'utilisation de cette option.

--test

Ne modifie rien sur le système, c'est-à-dire les horloges ou /etc/adjtime (--verbose est implicite avec cette option).

--update-drift

Met à jour le facteur de dérive de l'horloge matérielle dans /etc/adjtime. Il ne peut être utilisé qu'avec --set ou --systohc.

Une période minimale de quatre heures entre les réglages est requise. Ceci afin d'éviter des calculs invalides. Plus la période est longue, plus le facteur de dérive résultant sera précis.

Cette option a été ajoutée dans la version 2.26, car il est typique que les systèmes appellent hwclock --systohc à l'arrêt ; avec le comportement précédent, cela recalculait automatiquement le facteur de dérive, ce qui causait plusieurs problèmes :

•Lors de l'utilisation de NTP avec un noyau en mode « 11 minutes », le facteur de dérive serait écrasé à près de zéro.
•Cela ne permettrait pas l'utilisation de la correction de dérive « à froid ». Avec la plupart des configurations, l'utilisation de la dérive « à froid » donnera des résultats favorables. Froid, signifie quand la machine est éteinte, ce qui peut avoir un impact significatif sur le facteur de dérive.
•Le (re)calcul du facteur de dérive à chaque arrêt donne des résultats sous-optimaux. Par exemple, si des conditions éphémères font que la machine est anormalement chaude, le calcul du facteur de dérive serait hors limites.
•Augmentation significative des temps d'arrêt du système (depuis la version 2.31, lorsque --update-drift n'est pas utilisé, le RTC n'est pas lu).

Le calcul du facteur de dérive par hwclock constitue un bon point de départ, mais pour des résultats optimaux, il devra probablement être ajusté en modifiant directement le fichier /etc/adjtime. Pour la plupart des configurations, une fois que le facteur de dérive optimal d'une machine est défini, il ne devrait pas avoir besoin d'être modifié. Par conséquent, l'ancien comportement de recalcul automatique de la dérive a été modifié et nécessite maintenant l'utilisation de cette option. Voir la discussion ci-dessous, sous La fonction d'ajustement.

Cette option nécessite de lire l'horloge matérielle avant de la régler. Si elle ne peut pas être lue, cette option entraînera l'échec des fonctions de réglage. Cela peut se produire, par exemple, si l'horloge matérielle est corrompue par une panne de courant. Dans ce cas, l'horloge doit d'abord être réglée sans cette option. Malgré le fait qu'elle ne fonctionne pas, le facteur de correction de dérive résultant serait de toute façon invalide.

-v, --verbose

Affiche plus de détails sur le fonctionnement interne de hwclock.

NOTES

Horloges dans un Système Linux

Il existe deux types d'horloges de date et d'heure :

L'Horloge Matérielle : Cette horloge est un périphérique matériel indépendant, avec son propre domaine d'alimentation (batterie, condensateur, etc.), qui fonctionne lorsque la machine est éteinte, voire débranchée.

Sur un système compatible ISA, cette horloge est spécifiée dans le cadre de la norme ISA. Un programme de contrôle peut lire ou régler cette horloge uniquement à la seconde entière, mais il peut aussi détecter les fronts des ticks d'horloge de 1 seconde, de sorte que l'horloge a en fait une précision virtuellement infinie.

Cette horloge est couramment appelée horloge matérielle, horloge temps réel, RTC, horloge BIOS et horloge CMOS. Horloge Matérielle, dans sa forme capitalisée, a été inventée pour être utilisée par hwclock. Le noyau Linux la désigne également comme horloge persistante.

Certains systèmes non-ISA ont quelques horloges temps réel dont une seule possède son propre domaine d'alimentation. Une puce d'horloge externe à très faible consommation, I2C ou SPI, peut être utilisée avec une batterie de secours comme horloge matérielle pour initialiser une horloge temps réel intégrée plus fonctionnelle qui est utilisée pour la plupart des autres usages.

L'Horloge Système : Cette horloge fait partie du noyau Linux et est pilotée par une interruption de minuterie. (Sur une machine ISA, l'interruption de minuterie fait partie de la norme ISA.) Elle n'a de sens que tant que Linux fonctionne sur la machine. L'heure système est le nombre de secondes depuis 00:00:00 le 1er janvier 1970 UTC (ou plus succinctement, le nombre de secondes depuis 1969 UTC). L'heure système n'est cependant pas un entier. Elle a une précision virtuellement infinie.

L'heure système est l'heure qui importe. Le but fondamental de l'Horloge Matérielle est de garder l'heure lorsque Linux n'est pas en cours d'exécution, afin que l'Horloge Système puisse être initialisée à partir de celle-ci au démarrage. Notez que sous DOS, pour lequel ISA a été conçu, l'Horloge Matérielle est la seule horloge temps réel.

Il est important que l'heure système ne présente aucune discontinuité, comme ce serait le cas si vous utilisiez le programme date(1) pouro le régler pendant que le système est en cours d'exécution. Vous pouvez cependant faire ce que vous voulez avec l'Horloge Matérielle pendant que le système tourne, et la prochaine fois que Linux démarrera, il le fera avec l'heure ajustée depuis l'Horloge Matérielle. Note : actuellement, ceci n'est pas possible sur la plupart des systèmes car hwclock --systohc est appelé à l'arrêt.

Le fuseau horaire du noyau Linux est défini par hwclock. Mais ne vous laissez pas tromper — presque personne ne se soucie du fuseau horaire que le noyau pense être le sien. À la place, les programmes qui se soucient du fuseau horaire (peut-être parce qu'ils veulent afficher une heure locale pour vous) utilisent presque toujours une méthode plus traditionnelle pour déterminer le fuseau horaire : Ils utilisent la variable d'environnement TZ ou le fichier /etc/localtime , comme expliqué dans la page de manuel pour tzset(3). Cependant, certains programmes et des parties périphériques du noyau Linux comme les systèmes de fichiers utilisent la valeur du fuseau horaire du noyau. Un exemple est le système de fichiers vfat. Si la valeur du fuseau horaire du noyau est fausse, le système de fichiers vfat signalera et définira des horodatages incorrects sur les fichiers. Un autre exemple est le 'mode 11 minutes' NTP du noyau. Si la valeur du fuseau horaire du noyau et/ou la variable persistent_clock_is_local sont incorrectes, alors l'Horloge Matérielle sera définie incorrectement par le 'mode 11 minutes'. Voir la discussion ci-dessous, sous Synchronisation automatique de l'Horloge Matérielle par le noyau.

hwclock définit le fuseau horaire du noyau à la valeur indiquée par TZ ou /etc/localtime avec les fonctions --hctosys ou --systz .

La valeur du fuseau horaire du noyau consiste en réalité en deux parties : 1) un champ tz_minuteswest indiquant de combien de minutes l'heure locale (non ajustée pour l'heure d'été) est en retard sur l'UTC, et 2) un champ tz_dsttime indiquant le type de convention d'heure d'été (DST) en vigueur dans la localité au moment présent. Ce deuxième champ n'est pas utilisé sous Linux et est toujours zéro. Voir aussi settimeofday(2).

Méthodes d'accès à l'Horloge Matérielle

hwclock utilise de nombreuses façons différentes d'obtenir et de définir les valeurs de l'Horloge Matérielle. La façon la plus normale est de faire des E/S sur le fichier spécial de périphérique rtc, qui est supposé être piloté par le pilote de périphérique rtc. De plus, les systèmes Linux utilisant le framework rtc avec udev sont capables de prendre en charge plusieurs Horloges Matérielles. Cela peut entraîner la nécessité de remplacer le périphérique rtc par défaut en en spécifiant un avec l'option --rtc .

Cependant, cette méthode n'est pas toujours disponible car les systèmes plus anciens ne possèdent pas de pilote rtc. Sur ces systèmes, la méthode d'accès à l'Horloge Matérielle dépend du matériel du système.

Sur un système compatible ISA, hwclock peut accéder directement aux registres de la "mémoire CMOS" qui constituent l'horloge, en effectuant des E/S sur les Ports 0x70 et 0x71. Il le fait avec des instructions d'E/S réelles et ne peut donc le faire que s'il s'exécute avec l'identifiant utilisateur effectif superutilisateur. Cette méthode peut être utilisée en spécifiant l'option --directisa .

C'est vraiment une mauvaise méthode d'accès à l'horloge, pour toutes les raisons pour lesquelles les programmes en espace utilisateur ne sont généralement pas censés faire d'E/S directes et désactiver les interruptions. hwclock la fournit pour les tests, le dépannage, et parce que c'est peut-être la seule méthode disponible sur les systèmes ISA qui n'ont pas de pilote de périphérique rtc fonctionnel.

La fonction d'ajustement

L'Horloge Matérielle n'est généralement pas très précise. Cependant, une grande partie de son imprécision est complètement prévisible - elle gagne ou perd la même quantité de temps chaque jour. C'est ce qu'on appelle la dérive systématique. hwclock's --adjust vous permet d'appliquer des corrections de dérive systématique à l'Horloge Matérielle.

Cela fonctionne comme ceci : hwclock conserve un fichier, /etc/adjtime, qui garde certaines informations historiques. C'est ce qu'on appelle le fichier adjtime.

Supposons que vous commenciez sans fichier adjtime. Vous émettez une commande hwclock --set pour régler l'Horloge Matérielle sur l'heure actuelle réelle. hwclock crée le fichier adjtime et y enregistre l'heure actuelle comme étant la dernière fois où l'horloge a été calibrée. Cinq jours plus tard, l'horloge a gagné 10 secondes, donc vous émettez une commande hwclock --set --update-drift pour la remettre en arrière de 10 secondes. hwclock met à jour le fichier adjtime pour indiquer l'heure actuelle comme étant la dernière fois où l'horloge a été calibrée, et enregistre 2 secondes par jour comme taux de dérive systématique. 24 heures passent, et puis vous émettez une commande hwclock --adjust . hwclock consulte le fichier adjtime et voit que l'horloge gagne 2 secondes par jour lorsqu'elle est laissée seule et qu'elle a été laissée seule pendant exactement un jour. Il soustrait donc 2 secondes de l'Horloge Matérielle. Il enregistre ensuite l'heure actuelle comme la dernière fois où l'horloge a été ajustée. Encore 24 heures passent et vous émettez à nouveau hwclock --adjust. hwclock fait la même chose : soustrait 2 secondes et met à jour le fichier adjtime avec l'heure actuelle comme la dernière fois où l'horloge a été ajustée.

Lorsque vous utilisez l'option --update-drift avec --set ou --systohc, le taux de dérive systématique est (re)calculé en comparant l'heure actuelle de l'Horloge Matérielle entièrement corrigée de la dérive avec la nouvelle heure définie, à partir de là il dérive le taux de dérive sur 24 heures basé sur l'horodatage de la dernière calibration du fichier adjtime. Ce facteur de dérive mis à jour est ensuite enregistré dans /etc/adjtime.

Une petite quantité d'erreur s'insinue lorsque l'Horloge Matérielle est réglée, donc --adjust s'abstient de faire tout ajustement qui est inférieur à 1 seconde. Plus tard, lorsque vous demandez à nouveau un ajustement, la dérive accumulée sera supérieure à 1 seconde et --adjust fera l'ajustement incluant toute quantité fractionnaire.

hwclock --hctosys utilise également les données du fichier adjtime pour compenser la valeur lue depuis l'Horloge Matérielle avant de l'utiliser pour régler l'Horloge Système. Il ne partage pas la limitation de 1 seconde de --adjust, et corrigera immédiatement les valeurs de dérive inférieures à la seconde. Il ne change pas l'heure de l'Horloge Matérielle ni le fichier adjtime. Cela peut éliminer la nécessité d'utiliser --adjust, sauf si autre chose sur le système a besoin que l'Horloge Matérielle soit compensée.

Le fichier Adjtime

Bien que nommé pour son objectif historique de contrôler uniquement les ajustements, il contient en réalité d'autres informations utilisées par hwclock d'une invocation à la suivante.

Le format du fichier adjtime est, en ASCII :

Ligne 1 : Trois nombres, séparés par des espaces : 1) le taux de dérive systématique en secondes par jour, décimal flottant ; 2) le nombre résultant de secondes depuis 1969 UTC de l'ajustement ou de la calibration les plus récents, entier décimal ; 3) zéro (pour compatibilité avec clock(8)) en décimal flottant.

Ligne 2 : Un nombre : le nombre résultant de secondes depuis 1969 UTC de la calibration la plus récente. Zéro s'il n'y a pas encore eu de calibration ou si il est connu que toute calibration précédente est sans objet (par exemple, parce que l'Horloge Matérielle a été trouvée, depuis cette calibration, ne pas contenir une heure valide). Ceci est un entier décimal.

Ligne 3 : "UTC" ou "LOCAL". Indique si l'Horloge Matérielle est réglée sur l'Heure Universelle Coordonnée ou l'heure locale. Vous pouvez toujours remplacer cette valeur avec des options sur la ligne de commande hwclock .

Vous pouvez utiliser un fichier adjtime qui a été utilisé précédemment avec le programme clock(8) avec hwclock.

Synchronisation automatique de l'Horloge Matérielle par le noyau

Vous devriez être conscient d'une autre façon dont l'Horloge Matérielle est maintenue synchronisée sur certains systèmes. Le noyau Linux a un mode dans lequel il copie l'Heure Système vers l'Horloge Matérielle toutes les 11 minutes. Ce mode est une option de compilation, donc tous les noyaux n'auront pas cette capacité. C'est un bon mode à utiliser lorsque vous utilisez quelque chose de sophistiqué comme NTP pour garder votre Horloge Système synchronisée. (NTP est une façon de garder votre Heure Système synchronisée soit avec un serveur de temps quelque part sur le réseau, soit avec une horloge radio reliée à votre système. Voir la RFC 1305.)

Si le noyau est compilé avec l'option 'mode 11 minutes', il sera actif lorsque la discipline d'horloge du noyau est dans un état synchronisé. Dans cet état, le bit 6 (le bit qui est défini dans le masque 0x0040) de la variable du noyau time_status est non défini. Cette valeur est produite comme la ligne 'status' des commandes adjtimex --print ou ntptime .

Il faut une influence extérieure, comme le démon NTP, pour mettre la discipline d'horloge du noyau dans un état synchronisé, et donc activer le 'mode 11 minutes'. Il peut être désactivé en exécutant n'importe quoi qui définit l'Heure Système à l'ancienne, y compris hwclock --hctosys. Cependant, si le démon NTP est toujours en cours d'exécution, il réactivera le 'mode 11 minutes' la prochaine fois qu'il synchronisera l'Heure Système.

Si votre système fonctionne avec le 'mode 11 minutes' activé, il peut avoir besoin d'utiliser soit --hctosys ou --systz dans un script de démarrage, surtout si l'Horloge Matérielle est configurée pour utiliser l'échelle de temps locale. À moins que le noyau soit informé de l'échelle de temps utilisée par l'Horloge Matérielle, il peut l'écraser avec la mauvaise. Le noyau utilise l'UTC par défaut.

La première commande en espace utilisateur qui définit l'Horloge Système informe le noyau de l'échelle de temps utilisée par l'Horloge Matérielle. Cela se produit via la variable du noyau persistent_clock_is_local . Si --hctosys ou --systz est le premier, il définira cette variable en fonction du fichier adjtime ou de l'argument de ligne de commande approprié. Notez que lorsque vous utilisez cette capacité et que la configuration de l'échelle de temps de l'Horloge Matérielle est modifiée, un redémarrage est nécessaire pour informer le noyau.

hwclock --adjust ne devrait pas être utilisé avec le 'mode 11 minutes' NTP.

Valeur du siècle de l'Horloge Matérielle ISA

Il existe une sorte de standard qui définit l'octet 50 de la mémoire CMOS sur une machine ISA comme un indicateur du siècle actuel. hwclock n'utilise pas et ne définit pas cet octet car il y a des machines qui ne définissent pas l'octet de cette façon, et ce n'est vraiment pas nécessaire de toute façon, puisque l'année du siècle fait bien le travail d'impliquer de quel siècle il s'agit.

Si vous avez une utilisation légitime pour un octet de siècle CMOS, contactez le hwclock mainteneur ; une option pourrait être appropriée.

Notez que cette section n'est pertinente que lorsque vous utilisez la méthode "direct ISA" pour accéder à l'Horloge Matérielle. ACPI fournit un moyen standard d'accéder auury values, lorsqu'ils sont pris en charge par le matériel.

CONFIGURATION DATE-HEURE

Garder l'heure sans synchronisation externe

Cette discussion est basée sur les conditions suivantes :

•Rien ne s'exécute qui modifie les horloges date-heure, comme un démon NTP ou une tâche cron.
•Le fuseau horaire du système est configuré pour l'heure locale correcte. Voir ci-dessous, sous POSIX vs 'RIGHT'.
•Tôt au démarrage, les commandes suivantes sont appelées, dans cet ordre : adjtimex --tick valeur --frequency valeur hwclock --hctosys
•Pendant l'arrêt, la commande suivante est appelée : hwclock --systohc
•Les systèmes sans adjtimex peuvent utiliser ntptime.

Que l'on maintienne une heure précise avec un démon NTP ou non, il est judicieux de configurer le système pour qu'il conserve raisonnablement bien la date et l'heure par lui-même.

La première étape pour y parvenir est d'avoir une compréhension claire de la situation globale. Il existe deux périphériques matériels complètement distincts fonctionnant à leur propre vitesse et dérivant de l'heure « correcte » à leurs propres rythmes. Les méthodes et logiciels de correction de dérive sont différents pour chacun d'eux. Cependant, la plupart des systèmes sont configurés pour échanger des valeurs entre ces deux horloges au démarrage et à l'arrêt. Désormais, les erreurs de maintien de l'heure de chaque périphérique sont transférées de l'un à l'autre. Tenter de configurer la correction de dérive pour un seul d'entre eux, et la dérive de l'autre sera superposée.

Ce problème peut être évité lors de la configuration de la correction de dérive pour l'horloge système en ne l'arrêtant tout simplement pas. Ceci, ainsi que le fait que toute la précision de hwclock (y compris le calcul des facteurs de dérive) dépend du bon taux de l'horloge système, signifie que la configuration de l'horloge système doit être effectuée en premier.

La dérive de l'horloge système est corrigée avec les options --tick et --frequency de la commande adjtimex(8). Ces deux options fonctionnent ensemble : tick est le réglage grossier et frequency est le réglage fin. (Pour les systèmes qui ne disposent pas du package adjtimex, ntptime -f ppm peut être utilisé à la place.)

Certaines distributions Linux tentent de calculer automatiquement la dérive de l'horloge système avec l'opération de comparaison d'adjtimex. Essayer de corriger une horloge dérivante en utilisant une autre horloge dérivante comme référence revient à un chien essayant d'attraper sa propre queue. Le succès peut arriver éventuellement, mais un grand effort et une grande frustration précéderont probablement cela. Cette automatisation peut produire une amélioration par rapport à aucune configuration, mais s'attendre à des résultats optimaux serait une erreur. Un meilleur choix pour une configuration manuelle serait les options --log d'adjtimex.

Il peut être plus efficace de simplement suivre la dérive de l'horloge système avec sntp, ou date -Ins et une horloge de précision, puis de calculer la correction manuellement.

Après avoir défini les valeurs de tick et de fréquence, continuez à tester et à affiner les ajustements jusqu'à ce que l'horloge système conserve une bonne heure. Voir adjtimex(2) pour plus d'informations et l'exemple démontrant les calculs manuels de dérive.

Une fois que l'horloge système fonctionne correctement, passez à l'horloge matérielle.

En règle générale, la dérive à froid fonctionnera mieux pour la plupart des cas d'utilisation. Cela devrait être vrai même pour les machines fonctionnant 24h/24 et 7j/7 dont l'arrêt normal consiste en un redémarrage. Dans ce cas, la valeur du facteur de dérive importe peu. Mais dans le cas rare où la machine est arrêtée pendant une période prolongée, la dérive à froid devrait donner de meilleurs résultats.

Étapes pour calculer la dérive à froid :

1

Assurez-vous que le démon NTP ne sera pas lancé au démarrage.

2

L'heure de l'horloge système doit être correcte à l'arrêt !

3

Arrêtez le système.

4

Laissez passer une période prolongée sans modifier l'horloge matérielle.

5

Démarrez le système.

6

Utilisez immédiatement hwclock pour régler l'heure correcte, en ajoutant l'option --update-drift.

Remarque : si l'étape 6 utilise --systohc, alors l'horloge système doit être correctement réglée (étape 6a) juste avant de le faire.

Le fait que hwclock calcule le facteur de dérive est un bon point de départ, mais pour des résultats optimaux, il faudra probablement l'ajuster en éditant directement le fichier /etc/adjtime. Continuez à tester et à affiner le facteur de dérive jusqu'à ce que l'horloge matérielle soit correctement corrigée au démarrage. Pour vérifier cela, assurez-vous d'abord que l'heure système est correcte avant l'arrêt, puis utilisez sntp, ou date -Ins et une horloge de précision, immédiatement après le démarrage.

LOCAL vs UTC

Garder l'horloge matérielle sur une échelle de temps locale entraîne des résultats incohérents en matière d'heure d'été :

•Si Linux fonctionne pendant un changement d'heure d'été, l'heure écrite dans l'horloge matérielle sera ajustée pour le changement.
•Si Linux ne fonctionne PAS pendant un changement d'heure d'été, l'heure lue de l'horloge matérielle NE sera PAS ajustée pour le changement.

L'horloge matérielle sur un système compatible ISA ne conserve qu'une date et une heure, elle n'a aucune notion de fuseau horaire ni d'heure d'été. Par conséquent, lorsque hwclock est informé qu'elle est en heure locale, il suppose qu'elle est à l'heure locale « correcte » et ne fait aucun ajustement à l'heure qui en est lue.

Linux gère les changements d'heure d'été de manière transparente uniquement lorsque l'horloge matérielle est conservée à l'échelle de temps UTC. Cela est rendu facile pour les administrateurs système car hwclock utilise l'heure locale pour sa sortie et comme argument de l'option --date.

Les systèmes POSIX, comme Linux, sont conçus pour que l'horloge système fonctionne à l'échelle de temps UTC. Le but de l'horloge matérielle est d'initialiser l'horloge système, donc la conserver également en UTC a du sens.

Linux tente cependant de s'adapter à ce que l'horloge matérielle soit à l'échelle de temps locale. Ceci est principalement destiné au double démarrage avec d'anciennes versions de MS Windows. À partir de Windows 7, la clé de registre RealTimeIsUniversal est censée fonctionner correctement afin que son horloge matérielle puisse être conservée en UTC.

POSIX vs 'DROIT'

Une discussion sur la configuration de la date et de l'heure serait incomplète sans aborder les fuseaux horaires, ceci est largement bien couvert par tzset(3). Un domaine qui semble ne pas avoir de documentation est le répertoire 'right' (droit) de la base de données des fuseaux horaires, parfois appelée tz ou zoneinfo.

Il existe deux bases de données distinctes dans le système zoneinfo, posix et 'right'. 'Right' (maintenant nommé zoneinfo-leaps) inclut les secondes intercalaires et posix ne le fait pas. Pour utiliser la base de données 'right', l'horloge système doit être réglée sur (UTC + secondes intercalaires), ce qui équivaut à (TAI - 10). Cela permet de calculer le nombre exact de secondes entre deux dates qui traversent une époque de seconde intercalaire. L'horloge système est ensuite convertie en heure civile correcte, y compris UTC, en utilisant les fichiers de fuseau horaire 'right' qui soustraient les secondes intercalaires. Remarque : cette configuration est considérée comme expérimentale et est connue pour présenter des problèmes.

Pour configurer un système afin qu'il utilise une base de données particulière, tous les fichiers situés dans son répertoire doivent être copiés à la racine de /usr/share/zoneinfo. Les fichiers ne sont jamais utilisés directement depuis les sous-répertoires posix ou 'right', par exemple, TZ='right/Europe/Dublin'. Cette habitude devenant si courante que le projet zoneinfo en amont a restructuré l'arborescence des fichiers du système en déplaçant les sous-répertoires posix et 'right' hors du répertoire zoneinfo et dans des répertoires frères :

/usr/share/zoneinfo, /usr/share/zoneinfo-posix, /usr/share/zoneinfo-leaps

Malheureusement, certaines distributions Linux reviennent à l'ancienne structure d'arborescence dans leurs paquets. Le problème des administrateurs système qui accèdent au sous-répertoire 'right' persiste donc. Cela entraîne la configuration du fuseau horaire du système pour inclure les secondes intercalaires alors que la base de données zoneinfo est toujours configurée pour les exclure. Ensuite, lorsqu'une application telle qu'une horloge mondiale a besoin du fichier de fuseau horaire South_Pole ; ou qu'un MTA de courrier électronique, ou hwclock a besoin du fichier de fuseau horaire UTC ; ils le récupèrent à la racine de /usr/share/zoneinfo, car c'est ce qu'ils sont censés faire. Ces fichiers excluent les secondes intercalaires, mais l'horloge système les inclut désormais, provoquant une conversion de temps incorrecte.

Tenter de mélanger et assortir des fichiers de ces bases de données distinctes ne fonctionnera pas, car chacune nécessite que l'horloge système utilise une échelle de temps différente. La base de données zoneinfo doit être configurée pour utiliser soit posix, soit 'right', comme décrit ci-dessus, ou en attribuant un chemin de base de données à la variable d'environnement TZDIR.
