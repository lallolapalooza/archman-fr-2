DESCRIPTIO

N

hping2 est un outil réseau capable d'envoyer des paquets TCP/IP personnalisés et d'afficher les réponses de la cible comme le fait le programme ping avec les réponses ICMP. hping2 gère la fragmentation, le corps et la taille arbitraires des paquets et peut être utilisé pour transférer des fichiers encapsulés sous des protocoles pris en charge. En utilisant hping2, vous êtes capable d'effectuer au moins les actions suivantes

:


- Tester les règles de pare-feu
- Balayage de ports avancé
- Tester les performances du réseau en utilisant différents protocoles,
tailles de paquets, TOS (type de service) et fragmentation.
- Découverte du MTU du chemin
- Transférer des fichiers entre des règles de pare-feu même vraiment fascistes.
rules.
- Traceroute sous différents protocoles.
- Utilisation de type Firewalk.
- Empreinte numérique du système d'exploitation distant.
- Audit de la pile TCP/IP.
- Beaucoup

d'autres.

C'est aussi un bon outil didactique pour apprendre TCP/IP. hping2 est développé et maintenu par antirez@invece.org et est sous licence G

PL version 2. Le développement est ouvert, vous pouvez donc m'envoy
er des correctifs, des suggestions et des insultes sans inhibitions.

SÉLECTION DU

PROTOCOLE

Le protocole par défaut est TCP, par défaut hping2 enverra des en-têtes tcp au port 0 de l'hôte cible avec une taille de fenêtre (winsize) de 64 sans aucun drapeau tcp activé. Souvent, c'est la meilleure façon de faire un 'ping caché', utile lorsque la cible est derrière un pare-feu qui rejette les ICMP. De plus, un tcp null-flag vers le port 0 a une bonne probabilité de ne pas être

journalisé.
-0
--rawip
Mode IP RAW, dans ce mode hping2 enverra un en-tête IP avec des données ajoutées avec --signature et/ou --file, voir aussi --ipproto qui vous permet de définir le champ de protocole
ip.
-1
--icmp
Mode ICMP, par défaut hping2 enverra un echo-request ICMP, vous pouvez définir d'autres type/code ICMP en utilisant les options --icmptype -
-icmpcode.
-2
--udp
Mode UDP, par défaut hping2 enverra udp au port 0 de l'hôte cible. Les options réglables de l'en-tête UDP sont les suivantes : --baseport, --destport,
--keep.
-8
--scan
Mode balayage, l'option attend un argument qui décrit les groupes de ports à balayer. Les groupes de ports sont séparés par des virgules : un nombre décrit un seul port, donc 1,2,3 signifie le port 1, 2 et 3. Les plages sont spécifiées en utilisant une notation début-fin, comme 1-1000, qui indique à hping de balayer les ports entre 1 et 1000 (inclus). Le mot spécial all est un alias pour 0-65535, tandis que le mot spécial known inclut tous les ports listés dans /etc/services.
Les groupes peuvent être combinés, donc la ligne de commande suivante balayera les ports entre 1 et 1000 ET le port 8888 ET les ports listés dans /etc/services : hping --scan 1-1000,8888,known -S target.host.com
Les groupes peuvent être niés (soustraits) en utilisant un caractère ! comme préfixe, donc la ligne de commande suivante balayera tous les ports NON listés dans /etc/services dans la plage 1-1024 : hping --scan '1-1024,!known' -S target.host.com
Gardez à l'esprit que bien que hping semble beaucoup plus comme un scanner de ports dans ce mode, la plupart des interrupteurs de hping sont toujours respectés, donc par exemple pour effectuer un balayage SYN vous devez spécifier l'option -S, vous pouvez changer la taille de la fenêtre TCP, le TTL, contrôler la fragmentation IP comme d'habitude, et ainsi de suite. La seule vraie différence est que lacomportements avancés de hping sont encapsulés dans un algorithme de scan.
Note technique : le mode scan utilise une conception à deux processus, avec une mémoire partagée pour la synchronisation. L'algorithme de scan n'est pas encore optimal, mais déjà assez rapide.
Astuce : contrairement à la plupart des scanners, hping affiche des informations intéressantes sur les paquets reçus, l'ID IP, la fenêtre TCP, le TTL, etc. N'oubliez pas de regarder ces informations supplémentaires lorsque vous effectuez un scan ! Parfois, elles révèlent des détails
intéressants.
-9 --listen
signature
Mode d'écoute de HPING2, avec cette option hping2 attend un paquet contenant signature et affiche à partir de signature jusqu'à la fin du paquet. Par exemple, si hping2 --listen TEST lit un paquet contenant 234-09sdflkjs45-TESThello_world, il affichera hello
_w
orl
d.

FORMAT DE SORTIE

TCP

Le format de sortie TCP standard est le suivant

:

len=46 ip=192.168.1.1 flags=RA DF seq=0 ttl=255 id=0 win=0 rtt=0.4

ms

len est la taille, en octets, des données capturées depuis la couche liaison de données, à l'exclusion de la taille de l'en-tête de la liaison de données. Cela peut ne pas correspondre à la taille du datagramme IP en raison du remplissage de la couche de transport de bas

niveau.

ip est l'adresse ip

source.

flags sont les drapeaux TCP, R pour RESET, S pour SYN, A pour ACK, F pour FIN, P pour PUSH, U pour URGENT, X pour le non standard 0x40, Y pour le non standard

0x80.

Si la réponse contient DF, le bit ne pas fragmenter de l'en-tête IP est

défini.

seq est le numéro de séquence du paquet, obtenu en utilisant le port source pour les paquets TCP/UDP, le champ de séquence pour les paquets

ICMP.

id est le champ IP

ID.

win est la taille de la fenêtre

TCP.

rtt est le temps d'aller-retour en

millisecondes.

Si vous exécutez hping en utilisant l'option -V de la ligne de commande, elle affichera des informations supplémentaires sur le paquet, exemple

:

urp=0

IP.

len.

TCP.

FORMAT DE SORTIE

ICMP

Un exemple de sortie ICMP est

:

ICMP Port Unreachable from ip=192.168.1.1 name=nano.marmoc.

net

C'est très simple à comprendre. Cela commence par la chaîne "ICMP" suivie de la description de l'erreur ICMP, Port Unreachable dans l'exemple. Le champ ip est l'adresse source IP du datagramme IP contenant l'erreur ICMP, le champ name est simplement l'adresse numérique résolue en un nom (une requête dns PTR) ou UNKNOWN si la résolution a

échoué.

Le format ICMP Time exceeded during transit ou reassembly est un peu différent

:

BOGUE

S

Même en utilisant les options --end et --safe pour transférer des fichiers, le paquet final sera complété avec des octets

0x00.

Les données sont lues sans tenir compte de l'alignement, mais l'alignement est appliqué dans les structures de données. Cela ne sera pas un problème sous i386 mais, bien que les en-têtes TCP/IP soient généralement alignés naturellement, cela peut créer des problèmes avec différents processeurs et des paquets erronés s'il y a un accès non aligné quelque part dans le code (normalement il n'y en a aucun)

.

le être un problème de solaris, comme indiqué dans la liste de diffusion tcpd
ump-workers, donc libpcap ne peut rien faire pour le gérer correctement.
