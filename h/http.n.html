COMMANDES

EXPORTÉES

Espace de noms http exporte les commandes config, formatQuery, geturl, quoteString, register, registerError, reset, unregister, et wait

.

Elle n'exporte pas les commandes cleanup, code, data, error, meta, ncode, size, ou status

.

DESCRIPTIO

N

Le paquet http fournit le côté client du protocole HTTP/1.1, tel que défini dans les RFC 7230 à RFC 7235, qui remplacent la RFC 2616. Le paquet implémente les opérations GET, POST et HEAD de HTTP/1.1. Il permet la configuration d'un hôte proxy pour traverser les pare-feu. Le paquet est compatible avec la politique de sécurité Safesock, il peut donc être utilisé par des applets non fiables pour récupérer des URL à partir d'un ensemble restreint d'hôtes. Ce paquet peut être étendu pour prendre en charge des protocoles de transport HTTP supplémentaires, tels que HTTPS, en fournissant une commande socket personnalisée, via ::http::reg

ister.

La procédure ::http::geturl effectue une transaction HTTP. Ses options déterminent si une transaction GET, POST ou HEAD est effectuée. La valeur de retour de ::http::geturl est un jeton pour la transaction. La valeur est également le nom d'un tableau dans l'espace de noms ::http qui contient des informations d'état sur la transaction. Les éléments de ce tableau sont décrits dans la section TABLEAU

D'ÉTAT.

Si l' option -command est spécifiée, alors l'opération HTTP est effectuée en arrière-plan. ::http::geturl retourne immédiatement après la génération de la requête HTTP et la fonction de rappel est invoquée lorsque la transaction est terminée. Pour que cela fonctionne, la boucle d'événements Tcl doit être active. Dans les applications Tk, c'est toujours le cas. Pour les applications purement Tcl, l'appelant peut utiliser ::http::wait après avoir appelé ::http::geturl pour démarrer la boucle

d'événements.

Remarque : La file d'attente d'événements est même utilisée sans l' option -command. En effet, des commandes arbitraires peuvent être traitées pendant que http::geturl

s'ex
écute.

ERREUR

S

La procédure ::http::geturl lèvera des erreurs dans les cas suivants : options de ligne de commande invalides, une URL invalide, une URL sur un hôte inexistant, ou une URL sur un mauvais port d'un hôte existant. Ces erreurs signifient qu'elle ne peut même pas commencer la transaction réseau. Elle lèvera aussi une erreur si elle rencontre une erreur d'E/S lors de l'écriture de l'en-tête de requête HTTP. Pour les appels ::http::geturl synchrones (où -command n'est pas spécifié), elle lèvera une erreur si elle rencontre une erreur d'E/S lors de la lecture des en-têtes de réponse HTTP ou des données. Parce que ::http::geturl ne retourne pas un token dans ces cas, elle effectue tous les nettoyages requis et il n'y a pas de problème de votre application devant appeler ::http::cle

anup.

Pour les appels ::http::geturl asynchrones, toutes les situations d'erreur ci-dessus s'appliquent, sauf que s'il y a une erreur lors de la lecture des en-têtes de réponse HTTP ou des données, aucune exception n'est levée. C'est parce qu'après l'écriture des en-têtes HTTP, ::http::geturl retourne, et le reste de la transaction HTTP se produit en arrière-plan. La commande de rappel peut vérifier si une erreur s'est produite lors de la lecture en appelant ::http::status pour vérifier le statut et si c'est error, en appelant ::http::error pour obtenir le message

d'erreur.

Alternativement, si le flux principal du programme atteint un point où il a besoin de connaître le résultat de la requête HTTP asynchrone, il peut appeler ::http::wait puis vérifier le statut et l'erreur, tout comme le rappel le

fait.

La commande ::http::geturl exécute les rappels -command, -handler, et -proxyfilter à l'intérieur d'une commande catch. Par conséquent, une erreur dans la commande de rappel n'appelle pas le gestionnaire bgerror. Lors du débogage de l'un de ces rappels, il peut être pratique de signaler des erreurs en utilisant une commande catch à l'intérieur de la commande de rappel elle-même, par exemple pour écrire un message d'erreur sur

stdout.

Dans tous les cas, vous devez toujours appeler ::http::cleanup pour supprimer le tableau d'état lorsque vous avez

terminé.

CONNEXIONS

PERSISTANTES

BASE

S

Voir la RFC 7230 Sec 6, qui remplace la RFC 2616 Sec 8.

1.

Une connexion persistante permet à plusieurs transactions HTTP/1.1 de être effectuées sur la même connexion TCP. Le pipelining permet à un client de faire plusieurs requêtes sur une connexion persistante sans attendre chaque réponse. Le serveur envoie les réponses dans le même ordre que les requêtes ont été

reçues.

Si une requête POST échoue à se terminer, généralement une confirmation de l'utilisateur est nécessaire avant de renvoyer la requête. L'utilisateur peut souhaiter vérifier si le serveur a été modifié par la requête POST échouée, avant de renvoyer la même requête à

nouveau.

Une requête HTTP utilisera un socket persistant si l'appel à http::geturl a l'option -keepalive true. Elle utilisera le pipelining là où c'est permis si l' option http::config -pipeline est booléenne true (sa valeur par défaut)

.

Le paquet http ne maintient pas plus d'une connexion persistante vers chaque serveur (c'est-à-dire chaque valeur de « domain:port »). Si http::geturl est appelé pour faire une requête sur une connexion persistante pendant que la connexion est occupée par une autre requête, la nouvelle requête sera mise en file d'attente jusqu'à ce que la connexion soit

libre.

Le paquet http ne prend pas en charge les connexions persistantes HTTP/1.0 contrôlées par l' en-tête Ke

ep-A
live.

CAS

SPÉCIAUX

Cette sous-section discute des questions liées à la fermeture de la connexion persistante par le serveur, à la nouvelle tentative automatique des requêtes échouées, au traitement spécial nécessaire pour les requêtes POST, et aux options pour gérer ces

cas.

Conformément à la RFC 7230, http::geturl ne fait pas de pipelining des requêtes qui utilisent la méthode POST. Si un POST utilise une connexion persistante et n'est pas la première requête sur cette connexion, http::geturl attend jusqu'à ce qu'il ait reçu la réponse de la requête précédente ; ou (si l'option http::config -postfresh est booléenne true) il utilise une nouvelle connexion pour chaque

POST.

Si le serveur traite un certain nombre de requêtes en pipeline et envoie un en-tête de réponse «Connection: close » avec l'une des réponses (autre que la dernière), alors les réponses suivantes sont non satisfaites. http::geturl renverra les requêtes non satisfaites à nouveau sur une nouvelle

connexion.

Une difficulté survient lorsqu'un client HTTP envoie une requête sur une connexion persistante qui est restée inactive pendant un certain temps. Le serveur HTTP peut fermer à moitié une connexion apparemment inactive pendant que le client envoie une requête, mais avant que la requête n'arrive au serveur : dans ce cas (un « événement de fermeture asynchrone ») la requête échouera. La difficulté survient parce que le client ne peut pas être certain si le POST a modifié l'état du serveur. Pour les requêtes HEAD ou GET, http::geturl ouvre une autre connexion et retransmet la requête échouée. Cependant, si la requête était un POST, la RFC 7230 interdit la nouvelle tentative automatique par défaut, suggérant soit une confirmation de l'utilisateur, soit une confirmation par un logiciel user-agent qui a une compréhension sémantique de l'application. L' option http::config -repost permet l'une ou l'autre

possibilité.

Les événements de fermeture asynchrone ne peuvent survenir que dans un court intervalle de temps. Le paquet http surveille chaque connexion persistante pour la fermeture par le serveur. Lors de la détection, la connexion est également fermée à l'extrémité client, et les requêtes suivantes utiliseront une nouvelle

connexion.

Si la commande http::geturl est appelée avec l'option -keepalive true, alors elle essaiera à la fois d'utiliser une connexion persistante existante (s'il y en a une disponible), et elle enverra au serveur un en-tête de requête «Connection: keep-alive » demandant à garder la connexion ouverte pour les requêtes

futures.

Les options http::config -pipeline, -postfresh, et -repost sont liées aux connexions

persistantes.

L'option -pipeline, si booléenne true, mettra en pipeline les requêtes GET et HEAD effectuées sur une connexion persistante. Les requêtes POST ne seront pas mises en pipeline - si le POST n'est pas la première transaction sur la connexion, sa requête ne sera pas envoyée jusqu'à ce que la réponse précédente ait terminé. Les requêtes GET et HEAD effectuées après un POST ne seront pas envoyées jusqu'à ce que la réponse POST ait été délivrée, et ne seront pas envoyées si le POST

échoue.

L'option -postfresh, si booléenne true, annulera l' option http::geturl -keepalive, et ouvrira toujours une nouvelle connexion pour une requête

POST.

L'option -repost, si true, permet la nouvelle tentative automatique d'une requête POST qui échoue parce qu'elle utilise une connexion persistante que le serveur a fermée à moitié (un « événement de fermeture asynchrone »). Les requêtes GET et HEAD suivantes dans un pipeline échoué seront également réessayées. L'option -repost ne doit être utilisée que si l'application comprend que la nouvelle tentative est appropriée - plus précisément, l'application doit

savoir que si le POST échoué a réuss
i à modifier l'état du serveur, un P
OST répété n'aurait aucun effet néfaste.

MISES À NIVEAU DE

PROTOCOLE

Les en-têtes client HTTP/1.1 Connection et Upgrade informent le serveur que le client souhaite changer le protocole utilisé sur la connexion existante (RFC 7230). Ce mécanisme peut être utilisé pour demander un WebSocket (RFC 6455), une version supérieure du protocole HTTP (HTTP 2), ou le chiffrement TLS. Si le serveur accepte la demande de mise à niveau, son code de réponse sera

101.

Pour demander une mise à niveau de protocole lors de l'appel de http::geturl, l' option -headers doit fournir des valeurs appropriées pour Connection et Upgrade, et l' option -command doit fournir une commande qui implémente le protocole demandé et peut également gérer la réponse du serveur si le serveur refuse la mise à niveau du protocole. Pour les demandes de mise à niveau http::geturl ignore la valeur de l'option -keepalive, et utilise toujours la valeur 0 afin que la demande de mise à niveau ne soit pas faite sur une connexion destinée à plusieurs requêtes

HTTP.

La bibliothèque Tcllib websocket implémente les WebSockets et fait les appels nécessaires aux commandes dans le paquet h

ttp.

Il n'y a actuellement aucune bibliothèque client Tcl native pour

HTTP/2.

Le mécanisme Upgrade n'est pas utilisé pour demander TLS dans les navigateurs web, parce que http et https sont servis sur des ports différents. Il est utilisé par des protocoles tels que l'Internet Printing Protocol (IPP) qui sont construits au-dessus de http(s) et utilisent le même numéro de port TCP pour à la fois le trafic sécurisé et non

sécurisé.

Dans les navigateurs, le chiffrement opportuniste est à la place implémenté par l'en-tête client Upgrade-Insecure-Requests. Si un service sécurisé est disponible, le code de réponse du serveur est une redirection 307, et l'en-tête de réponse Location spécifie l'URL cible. Le navigateur doit appeler http::geturl à nouveau afin de récupérer cette URL. Voir https://w3c.github.io/webappsec-upgrade-insecure-request
