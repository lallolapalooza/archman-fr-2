DESCRIPTION

Formats d'images disque

QEMU supporte de nombreux formats d'images qui peuvent être utilisés avec les VM ainsi qu'avec n'importe lequel des outils (comme qemu-img). Cela inclut les formats préférés raw et qcow2 ainsi que des formats qui sont supportés pour la compatibilité avec d'anciennes versions de QEMU ou d'autres hyperviseurs.

Selon le format de l'image, différentes options peuvent être passées à qemu-img create et qemu-img convert en utilisant l'option -o. Cette section décrit chaque format et les options qui sont supportées pour celui-ci.

raw
Format d'image disque brut. Ce format a l'avantage d'être simple et facilement exportable vers tous les autres émulateurs. Si votre système de fichiers supporte les trous (par exemple ext2 ou ext3 sous Linux ou NTFS sous Windows), seuls les secteurs écrits réserveront de l'espace. Utilisez qemu-img info pour connaître la taille réelle utilisée par l'image ou ls -ls sous Unix/Linux.

Options supportées :

preallocation
Mode de préallocation (valeurs autorisées : off, falloc, full). Le mode falloc préalloue de l'espace pour l'image en appelant posix_fallocate(). Le mode full préalloue de l'espace pour l'image en écrivant des données sur le stockage sous-jacent. Ces données peuvent être nulles ou non, selon l'emplacement de stockage.
qcow2
Format d'image QEMU, le format le plus polyvalent. Utilisez-le pour avoir des images plus petites (utile si votre système de fichiers ne supporte pas les trous, par exemple sous Windows), la compression basée sur zlib et le support de plusieurs snapshots de VM.

Options supportées :

compat
Détermine la version de qcow2 à utiliser. compat=0.10 utilise le format d'image traditionnel qui peut être lu par n'importe quel QEMU depuis 0.10. compat=1.1 active les extensions du format d'image que seuls QEMU 1.1 et plus récents comprennent (c'est la valeur par défaut). Entre autres, cela inclut les clusters nuls, qui permettent une copie efficace à la lecture pour les images éparses.
backing_file
Nom de fichier d'une image de base (voir la sous-commande create)
backing_fmt
Format de l'image de base
encryption
Cette option est obsolète et équivalente à encrypt.format=aes
encrypt.format
Si cette option est réglée sur luks, elle demande que la charge utile qcow2 (pas l'en-tête qcow2) soit chiffrée en utilisant le format LUKS. La phrase de passe à utiliser pour déverrouiller l'emplacement de clé LUKS est donnée par le paramètre encrypt.key-secret. Les paramètres de chiffrement LUKS peuvent être ajustés avec les autres paramètres encrypt.*.

Si cette option est réglée sur aes, l'image est chiffrée avec AES-CBC 128 bits. La clé de chiffrement est donnée par le paramètre encrypt.key-secret. Ce format de chiffrement est considéré comme défectueux selon les standards cryptographiques modernes, souffrant de plusieurs problèmes de conception :

  • Le chiffrement AES-CBC est utilisé avec des vecteurs d'initialisation prévisibles basés sur le numéro de secteur. Cela le rend vulnérable aux attaques par texte clair choisi qui peuvent révéler l'existence de données chiffrées.
  • La phrase de passe de l'utilisateur est directement utilisée comme clé de chiffrement. Une phrase de passe mal choisie ou courte compromettra la sécurité du chiffrement.
  • Dans le cas où la phrase de passe est compromise, il n'y a aucun moyen de changer la phrase de passe pour protéger les données dans d'anciennes images qcow. Les fichiers doivent être clonés, en utilisant une phrase de passe de chiffrement différente dans le nouveau fichier. Le fichier d'origine doit alors être effacé en toute sécurité en utilisant un programme comme shred, bien que même cela soit inefficace avec de nombreuses technologies de stockage modernes.

L'utilisation de ceci n'est plus supportée dans les émulateurs système. Le support ne subsiste que dans les utilitaires en ligne de commande, à des fins de libération de données et d'interopérabilité avec d'anciennes versions de QEMU. Le format luks devrait être utilisé à la place.

encrypt.key-secret
Fournit l'identifiant d'un objet secret contenant la phrase de passe (encrypt.format=luks) ou la clé de chiffrement (encrypt.format=aes).
encrypt.cipher-alg
Nom de l'algorithme de chiffrement et longueur de clé. Par défaut, il s'agit de aes-256. Utilisé uniquement lorsque encrypt.format=luks.
encrypt.cipher-mode
Nom du mode de chiffrement à utiliser. Par défaut, il s'agit de xts. Utilisé uniquement lorsque encrypt.format=luks.
encrypt.ivgen-alg
Nom de l'algorithme de génération de vecteur d'initialisation. Par défaut, il s'agit de plain64. Utilisé uniquement lorsque encrypt.format=luks.
encrypt.ivgen-hash-alg
Nom de l'algorithme de hachage à utiliser avec le générateur de vecteur d'initialisation (si nécessaire). Par défaut, sha256. Utilisé uniquement lorsque encrypt.format=luks.
encrypt.hash-alg
Nom de l'algorithme de hachage à utiliser pour l'algorithme PBKDF. Par défaut, sha256. Utilisé uniquement lorsque encrypt.format=luks.
encrypt.iter-time
Temps, en millisecondes, à utiliser pour l'algorithme PBKDF par emplacement de clé. Par défaut, 2000. Utilisé uniquement lorsque encrypt.format=luks.
cluster_size
Modifie la taille des clusters qcow2 (doit être comprise entre 512 octets et 2 Mo). Des tailles de clusters plus petites peuvent améliorer la taille du fichier image, tandis que des tailles de clusters plus grandes offrent généralement de meilleures performances.
preallocation
Mode de préallocation (valeurs autorisées : off, metadata, falloc, full). Une image avec métadonnées préallouées est initialement plus grande mais peut améliorer les performances lorsque l'image doit croître. Les préallocations falloc et full sont identiques aux options du format raw, mais configurent également les métadonnées.
lazy_refcounts
Si cette option est réglée sur on, les mises à jour des décomptes de références sont différées dans le but d'éviter les I/O de métadonnées et d'améliorer les performances. Ceci est particulièrement intéressant avec cache=writethrough qui ne regroupe pas les mises à jour de métadonnées. Le compromis est qu'après un crash de l'hôte, les tables de décomptes de références doivent être reconstruites, c'est-à-dire que lors de la prochaine ouverture, un qemu-img check -r all (automatique) est requis, ce qui peut prendre du temps.

Cette option ne peut être activée que si compat=1.1 est spécifié.

nocow
Si cette option est réglée sur on, elle désactivera le COW du fichier. Elle n'est valide que sur btrfs, sans effet sur d'autres systèmes de fichiers.

Btrfs

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

a des performances faibles lorsqu'il héberge un fichier image de VM, encore plus lorsque l'invité sur la VM utilise également btrfs comme système de fichiers. Désactiver COW est un moyen d'atténuer ces mauvaises performances. Généralement, il existe deux façons de désactiver COW sur btrfs :

  • Désactivez-le en montant avec nodatacow, puis tous les nouveaux fichiers créés seront NOCOW.
  • Pour un fichier vide, ajoutez l'attribut de fichier NOCOW. C'est ce que fait cette option.

Note : cette option n'est valide que pour les fichiers nouveaux ou vides. S'il existe un fichier existant qui est COW et qui a déjà des blocs de données, il ne peut pas être changé en NOCOW en définissant nocow=on. On peut exécuter lsattr filename pour vérifier si le drapeau NOCOW est défini ou non (un 'C' majuscule est le drapeau NOCOW).

qed
Ancien format d'image QEMU avec prise en charge des fichiers de base et des fichiers d'image compacts (lorsque votre système de fichiers ou votre support de transport ne prend pas en charge les trous).

Lors de la conversion d'images QED en qcow2, vous pourriez envisager d'utiliser l'option lazy_refcounts=on pour obtenir un comportement plus similaire à QED.

Options prises en charge :

backing_file
Nom du fichier d'une image de base (voir la sous-commande create).
backing_fmt
Format de fichier image du fichier de base (facultatif). Utile si le format ne peut pas être détecté automatiquement car il n'a pas d'en-tête, comme certains fichiers vhd/vpc.
cluster_size
Modifie la taille du cluster (doit être une puissance de 2 entre 4K et 64K). Des tailles de cluster plus petites peuvent améliorer la taille du fichier image, tandis que des tailles de cluster plus grandes offrent généralement de meilleures performances.
table_size
Modifie le nombre de clusters par table L1/L2 (doit être une puissance de 2 entre 1 et 16). Il n'y a normalement pas besoin de changer cette valeur, mais cette option peut être utilisée pour des tests de performance.
qcow
Ancien format d'image QEMU avec prise en charge des fichiers de base, des fichiers d'image compacts, du chiffrement et de la compression.

Options prises en charge :

backing_file
Nom du fichier d'une image de base (voir la sous-commande create)
encryption
Cette option est dépréciée et équivalente à encrypt.format=aes
encrypt.format
Si cette option est définie sur aes, l'image est chiffrée avec AES-CBC 128 bits. La clé de chiffrement est fournie par le paramètre encrypt.key-secret. Ce format de chiffrement est considéré comme défectueux selon les normes cryptographiques modernes, souffrant d'un certain nombre de problèmes de conception énumérés précédemment contre le format d'image qcow2.

Son utilisation n'est plus prise en charge dans les émulateurs système. La prise en charge ne subsiste que dans les utilitaires en ligne de commande, dans le but de libérer les données et d'assurer l'interopérabilité avec les anciennes versions de QEMU.

Les utilisateurs nécessitant un chiffrement natif devraient plutôt utiliser le format qcow2 avec encrypt.format=luks.

encrypt.key-secret
Fournit l'ID d'un objet secret qui contient la clé de chiffrement (encrypt.format=aes).
luks
Format de chiffrement LUKS v1, compatible avec Linux dm-Crypt/cryptsetup.

Options prises en charge :

key-secret
Fournit l'ID d'un objet secret qui contient la phrase secrète.
cipher-alg
Nom de l'algorithme de chiffrement et longueur de la clé. Actuellement, la valeur par défaut est aes-256.
cipher-mode
Nom du mode de chiffrement à utiliser. Actuellement, la valeur par défaut est xts.
ivgen-alg
Nom de l'algorithme de génération de vecteur d'initialisation. Actuellement, la valeur par défaut est plain64.
ivgen-hash-alg
Nom de l'algorithme de hachage à utiliser avec le générateur de vecteur d'initialisation (si nécessaire). La valeur par défaut est sha256.
hash-alg
Nom de l'algorithme de hachage à utiliser pour l'algorithme PBKDF. La valeur par défaut est sha256.
iter-time
Temps, en millisecondes, à utiliser pour l'algorithme PBKDF par slot de clé. La valeur par défaut est 2000.
vdi
Format d'image compatible avec VirtualBox 1.1.

Options prises en charge :

static
Si cette option est définie sur on, l'image est créée avec pré-allocation des métadonnées.
vmdk
Format d'image compatible avec VMware 3 et 4.

Options prises en charge :

backing_file
Nom du fichier d'une image de base (voir la sous-commande create).
compat6
Crée une image VMDK version 6 (au lieu de la version 4).
hwversion
Spécifie la version matérielle virtuelle du VMDK. Le drapeau Compat6 ne peut pas être activé si hwversion est spécifié.
subformat
Spécifie quel sous-format VMDK utiliser. Les options valides sont monolithicSparse (par défaut), monolithicFlat, twoGbMaxExtentSparse, twoGbMaxExtentFlat et streamOptimized.
vpc
Format d'image compatible VirtualPC (VHD).

Options prises en charge :

subformat
Spécifie quel sous-format VHD utiliser. Les options valides sont dynamic (par défaut) et fixed.
VHDX
Format d'image compatible Hyper-V (VHDX).

Options prises en charge :

subformat
Spécifie quel sous-format VHDX utiliser. Les options valides sont dynamic (par défaut) et fixed.
block_state_zero
Force l'utilisation de blocs de charge utile de type 'ZERO'. Peut être défini sur on (par défaut) ou off. Lorsqu'il est défini sur off, de nouveaux blocs seront créés comme PAYLOAD_BLOCK_NOT_PRESENT, ce qui signifie que les analyseurs sont libres de renvoyer des données arbitraires pour ces blocs. Ne pas définir sur off lors de l'utilisation de qemu-img convert avec subformat=dynamic.
block_size
Taille de bloc ; min 1 Mo, max 256 Mo. 0 signifie auto-calcul basé sur la taille de l'image.
log_size
Taille du journal ; min 1 Mo.

Utilisation des lecteurs hôtes

En plus des fichiers image disque, QEMU peut accéder directement aux périphériques hôtes. Nous décrivons ici l'utilisation pour la version de QEMU >= 0.8.3.

Linux

Sur Linux, vous pouvez utiliser directement le nom de fichier du périphérique hôte au lieu d'un nom de fichier d'image disque, à condition d'avoir suffisamment de privilèges pour y accéder. Par exemple, utilisez /dev/cdrom pour accéder au lecteur CD-ROM.

CD
Vous pouvez spécifier un périphérique CDROM même si aucun CDROM n'est chargé. QEMU dispose d'un code spécifique pour détecter l'insertion ou le retrait de CDROM. L'éjection de CDROM par le système d'exploitation invité est prise en charge. Actuellement, seuls les CD de données sont pris en charge.
Disquette
Vous pouvez spécifier un périphérique de disquette même si aucune disquette n'est chargée. Le retrait de disquette n'est actuellement pas détecté avec précision (si vous changez de disquette sans accéder à la disquette alors qu'elle n'est pas chargée, le système d'exploitation invité pensera que la même disquette est chargée). L'utilisation du périphérique de disquette de l'hôte est déconseillée et la prise en charge sera supprimée dans une future version.
Disques durs
Les disques durs peuvent être utilisés. Normalement, vous devez spécifier le disque entier (/dev/hdb au lieu de /dev/hdb1) afin que le système d'exploitation invité puisse le voir comme un disque partitionné. ATTENTION : Sauf si vous savez ce que vous faites, il est préférable de n'accéder en lecture seule qu'au disque dur, sinon vous pourriez corrompre vos données hôtes (utilisez l'option de ligne de commande -snapshot ou modifiez les permissions du périphérique en conséquence).
Périphériques de blocs zonés
Les périphériques de blocs zonés peuvent être transmis à l'invité si le contrôleur de stockage émulé prend en charge le stockage zoné. Utilisez --blockdev host_device, node-name=drive0,filename=/dev/nullb0,cache.direct=on pour transmettre /dev/nullb0 en tant que drive0.

Windows

CD
La syntaxe préférée est la lettre du lecteur (par exemple, d:). La syntaxe alternative \\.\d: est prise en charge. /dev/cdrom est pris en charge en tant qu'alias du premier lecteur CDROM.

Actuellement, il n'existe pas de code spécifique pour gérer les médias amovibles, il est donc préférable d'utiliser les commandes du moniteur change ou eject pour changer ou éjecter les médias.

Disques durs
Les disques durs peuvent être utilisés avec la syntaxe : \\.\PhysicalDriveN où N est le numéro du lecteur (0 est le premier disque dur).

ATTENTION : Sauf si vous savez ce que vous faites, il est préférable de n'accéder en lecture seule qu'au disque dur, sinon vous pourriez corrompre vos données hôtes (utilisez l'option de ligne de commande -snapshot afin que les modifications soient écrites dans un fichier temporaire).

Mac OS X

/dev/cdrom est un alias du premier CDROM.

Actuellement, il n'existe pas de code spécifique pour gérer les médias amovibles, il est donc préférable d'utiliser les commandes du moniteur change ou eject pour changer ou éjecter les médias.

Images de disques FAT virtuels

QEMU peut automatiquement créer une image de disque FAT virtuelle à partir d'une arborescence de répertoires. Pour l'utiliser, tapez simplement :

qemu-system-x86_64 linux.img -hdb fat:/my_directory

Vous aurez alors accès à tous les fichiers du répertoire /my_directory sans avoir à les copier dans une image disque ou à les exporter via SAMBA ou NFS. L'accès par défaut est en lecture seule.

Les disquettes peuvent être émulées avec l'option :floppy: :

qemu-system-x86_64 linux.img -fda fat:floppy:/my_directory

Une prise en charge en lecture/écriture est disponible pour les tests (stade bêta) avec l'option :rw: :

qemu-system-x86_64 linux.img -fda fat:floppy:rw:/my_directory

Ce que vous ne devriez jamais faire :

  • utiliser des noms de fichiers non-ASCII
  • utiliser "-snapshot" avec ":rw:"
  • s'attendre à ce que cela fonctionne lors du chargement d'une machine virtuelle
  • écrire dans le répertoire FAT sur le système hôte pendant son accès par le système invité

Accès NBD

QEMU peut accéder directement aux périphériques de blocs exportés en utilisant le protocole Network Block Device.

qemu-system-x86_64 linux.img -hdb nbd://my_nbd_server.mydomain.org:1024/

Si le serveur NBD est situé sur le même hôte, vous pouvez utiliser un socket Unix au lieu d'un socket inet :

qemu-system-x86_64 linux.img -hdb nbd+unix://?socket=/tmp/my_socket

Dans ce cas, le périphérique de bloc doit être exporté en utilisant qemu-nbd :

qemu-nbd --socket=/tmp/my_socket my_disk.qcow2

L'utilisation de qemu-nbd permet le partage d'un disque entre plusieurs invités :

qemu-nbd --socket=/tmp/my_socket --share=2 my_disk.qcow2

et ensuite vous pouvez l'utiliser avec deux invités :

qemu-system-x86_64 linux1.img -hdb nbd+unix://?socket=/tmp/my_socket
qemu-system-x86_64 linux2.img -hdb nbd+unix://?socket=/tmp/my_socket

Si le nbd-server utilise des exportations nommées (prise en charge depuis NBD 2.9.18, ou avec le serveur NBD intégré de QEMU), vous devez spécifier un nom d'exportation dans l'URI :

qemu-system-x86_64 -cdrom nbd://localhost/debian-500-ppc-netinst
qemu-system-x86_64 -cdrom nbd://localhost/openSUSE-11.1-ppc-netinst

La syntaxe d'URI pour NBD est prise en charge depuis QEMU 1.3. Une syntaxe alternative est également disponible. Voici quelques exemples de l'ancienne syntaxe :

qemu-system-x86_64 linux.img -hdb nbd:my_nbd_server.mydomain.org:1024
qemu-system-x86_64 linux2.img -hdb nbd:unix:/tmp/my_socket
qemu-system-x86_64 -cdrom nbd:localhost:10809:exportname=debian-500-ppc-netinst

LUNs iSCSI

iSCSI est un protocole populaire utilisé pour accéder aux périphériques SCSI sur un réseau informatique.

Il existe deux manières différentes d'utiliser les périphériques iSCSI par QEMU.

La première méthode consiste à monter le LUN iSCSI sur l'hôte, et à le faire apparaître comme tout autre périphérique SCSI ordinaire sur l'hôte, puis à accéder à ce périphérique comme un périphérique /dev/sd depuis QEMU. La manière de faire cela diffère selon les systèmes d'exploitation hôtes.

La seconde méthode implique l'utilisation de l'initiateur iSCSI intégré à QEMU. Cela fournit un mécanisme qui fonctionne de la même manière, quel que soit le système d'exploitation hôte sur lequel vous exécutez QEMU. Cette section décrira cette seconde méthode d'utilisation d'iSCSI avec QEMU.

Dans QEMU, les périphériques iSCSI sont décrits à l'aide d'URL iSCSI spéciales. Syntaxe de l'URL :

iscsi://[<username>[%<password>]@]<host>[:<port>]/<target-iqn-name>/<lun>

Le nom d'utilisateur et le mot de passe sont facultatifs et ne sont utilisés que si votre cible est configurée avec l'authentification CHAP pour le contrôle d'accès. Alternativement, le nom d'utilisateur et le mot de passe peuvent également être définis via des variables d'environnement pour éviter qu'ils n'apparaissent dans la liste des processus :

export LIBISCSI_CHAP_USERNAME=<username>
export LIBISCSI_CHAP_PASSWORD=<password>
iscsi://<host>/<target-iqn-name>/<lun>

Divers paramètres liés à la session peuvent être définis via des options spéciales, soit dans un fichier de configuration fourni via '-readconfig', soit directement sur la ligne de commande.

Si le nom de l'initiateur n'est pas spécifié, qemu utilisera un nom par défaut de 'iqn.2008-11.org.linux-kvm[:<uuid>'] où <uuid> est l'UUID de la machine virtuelle. Si l'UUID n'est pas spécifié, qemu utilisera 'iqn.2008-11.org.linux-kvm[:<name>'] où <name> est le nom de la machine virtuelle.

Définir un nom d'initiateur spécifique à utiliser lors de la connexion à la cible :

-iscsi initiator-name=iqn.qemu.test:my-initiator

Contrôler le type de résumé d'en-tête à négocier avec la cible :

-iscsi header-digest=CRC32C|CRC32C-NONE|NONE-CRC32C|NONE

Ceci peut également être défini via un fichier de configuration :

[iscsi]
  user = "CHAP username"
  password = "CHAP password"
  initiator-name = "iqn.qemu.test:my-initiator"
  # le résumé d'en-tête est l'un de CRC32C|CRC32C-NONE|NONE-CRC32C|NONE
  header-digest = "CRC32C"

Définir le nom de la cible permet différentes options pour différentes cibles :

[iscsi "iqn.target.name"]
  user = "CHAP username"
  password = "CHAP password"
  initiator-name = "iqn.qemu.test:my-initiator"
  # le résumé d'en-tête est l'un de CRC32C|CRC32C-NONE|NONE-CRC32C|NONE
  header-digest = "CRC32C"

Comment utiliser un fichier de configuration pour définir les options de configuration iSCSI :

cat >iscsi.conf <<EOF
[iscsi]
  user = "me"
  password = "my password"
  initiator-name = "iqn.qemu.test:my-initiator"
  header-digest = "CRC32C"
EOF
qemu-system-x86_64 -drive file=iscsi://127.0.0.1/iqn.qemu.test/1 \
  -readconfig iscsi.conf

Comment configurer une cible iSCSI simple sur loopback et y accéder via QEMU : cet exemple montre comment configurer une cible iSCSI avec un CDROM et un DISQUE en utilisant le logiciel cible STGT de Linux. Cette cible est disponible sur les systèmes basés sur Red Hat sous le nom de paquet 'scsi-target-utils'.

tgtd --iscsi portal=127.0.0.1:3260
tgtadm --lld iscsi --op new --mode target --tid 1 -T iqn.qemu.test
tgtadm --lld iscsi --mode logicalunit --op new --tid 1 --lun 1 \
    -b /IMAGES/disk.img --device-type=disk
tgtadm --lld iscsi --mode logicalunit --op new --tid 1 --lun 2 \
    -b /IMAGES/cd.iso --device-type=cd
tgtadm --lld iscsi --op bind --mode target --tid 1 -I ALL
qemu-system-x86_64 -iscsi initiator-name=iqn.qemu.test:my-initiator \
  -boot d -drive file=iscsi://127.0.0.1/iqn.qemu.test/1 \
  -cdrom iscsi://127.0.0.1/iqn.qemu.test/2

Images de disques GlusterFS

GlusterFS est un système de fichiers distribué en espace utilisateur.

Vous pouvez démarrer à partir de l'image disque GlusterFS avec la commande :

URI :

qemu-system-x86_64 -drive file=gluster[+TYPE]://[HOST}[:PORT]]/VOLUME/PATH
                             [?socket=...][,file.debug=9][,file.logfile=...]

JSON :

qemu-system-x86_64 'json:{"driver":"qcow2",
                         "file":{"driver":"gluster",
                                  "volume":"testvol","path":"a.img","debug":9,"logfile":"...",
                                  "server":[{"type":"tcp","host":"...","port":"..."},
                                            {"type":"unix","socket":"..."}]}}'

gluster est le protocole.

TYPE spécifie le type de transport utilisé pour se connecter au démon de gestion gluster (glusterd). Les types de transport valides sont tcp et unix. Sous forme d'URI, si un type de transport n'est pas spécifié, le type tcp est supposé.

HOST spécifie le serveur où réside la spécification du fichier de volume pour le volume donné. Il peut s'agir d'un nom d'hôte ou d'une adresse ipv4. Si le type de transport est unix, le champ HOST ne doit pas être spécifié. Au lieu de cela, le champ socket doit être rempli avec le chemin vers le socket de domaine Unix.

PORT est le numéro de port sur lequel glusterd écoute. Ceci est facultatif et, s'il n'est pas spécifié, il utilise par défaut le port 24007. Si le type de transport est unix, le PORT ne doit pas être spécifié.

VOLUME est le nom du volume gluster qui contient l'image disque.

PATH est le chemin vers l'image disque réelle qui réside sur le volume gluster.

debug est le niveau de journalisation du pilote de protocole gluster. Les niveaux de débogage vont de 0 à 9, 9 étant le plus verbeux et 0 représentant aucune sortie de débogage. Le niveau par défaut est 4. Les niveaux de journalisation actuels définis dans la source gluster sont 0 - None, 1 - Emergency, 2 - Alert, 3 - Critical, 4 - Error, 5 - Warning, 6 - Notice, 7 - Info, 8 - Debug, 9 - Trace.

logfile est une option de ligne de commande pour spécifier le chemin du fichier journal, ce qui permet de journaliser dans le fichier spécifié et également de conserver les journaux gfapi. Par défaut, il s'agit de la sortie d'erreur standard.

Vous pouvez créer une image disque GlusterFS avec la commande :

qemu-img create gluster://HOST/VOLUME/PATH SIZE

Exemples

qemu-system-x86_64 -drive file=gluster://1.2.3.4/testvol/a.img
qemu-system-x86_64 -drive file=gluster+tcp://1.2.3.4/testvol/a.img
qemu-system-x86_64 -drive file=gluster+tcp://1.2.3.4:24007/testvol/dir/a.img
qemu-system-x86_64 -drive file=gluster+tcp://[1:2:3:4:5:6:7:8]/testvol/dir/a.img
qemu-system-x86_64 -drive file=gluster+tcp://[1:2:3:4:5:6:7:8]:24007/testvol/dir/a.img
qemu-system-x86_64 -drive file=gluster+tcp://server.domain.com:24007/testvol/dir/a.img
qemu-system-x86_64 -drive file=gluster+unix:///testvol/dir/a.img?socket=/tmp/glusterd.socket
qemu-system-x86_64 -drive file=gluster://1.2.3.4/testvol/a.img,file.debug=9,file.logfile=/var/log/qemu-gluster.log
qemu-system-x86_64 'json:{"driver":"qcow2",
                         "file":{"driver":"gluster",
                                  "volume":"testvol","path":"a.img",
                                  "debug":9,"logfile":"/var/log/qemu-gluster.log",
                                  "server":[{"type":"tcp","host":"1.2.3.4","port":24007},
                                            {"type":"unix","socket":"/var/run/glusterd.socket"}]}}'
qemu-system-x86_64 -drive driver=qcow2,file.driver=gluster,file.volume=testvol,file.path=/path/a.img,
                                     file.debug=9,file.logfile=/var/log/qemu-gluster.log,
                                     file.server.0.type=tcp,file.server.0.host=1.2.3.4,file.server.0.port=24007,
                                     file.server.1.type=unix,file.server.1.socket=/var/run/glusterd.socket

Images disque Secure Shell (ssh)

Vous pouvez accéder aux images disque situées sur un serveur ssh distant en utilisant le protocole ssh :

qemu-system-x86_64 -drive file=ssh://[USER@]SERVER[:PORT]/PATH[?host_key_check=HOST_KEY_CHECK]

Syntaxe alternative utilisant les propriétés :

qemu-system-x86_64 -drive file.driver=ssh[,file.user=USER],file.host=SERVER[,file.port=PORT],file.path=PATH[,file.host_key_check=HOST_KEY_CHECK]

ssh est le protocole.

USER est l'utilisateur distant. S'il n'est pas spécifié, le nom d'utilisateur local est essayé.

SERVER spécifie le serveur ssh distant. N'importe quel serveur ssh peut être utilisé, mais il doit implémenter le protocole sftp-server. La plupart des systèmes Unix/Linux devraient fonctionner sans nécessiter de configuration supplémentaire.

PORT est le numéro de port sur lequel sshd écoute. Par défaut, le port ssh standard (22) est utilisé.

PATH est le chemin vers l'image disque.

Le paramètre facultatif HOST_KEY_CHECK contrôle la façon dont la clé de l'hôte distant est vérifiée. La valeur par défaut est yes, ce qui signifie utiliser le fichier local .ssh/known_hosts. Le régler sur no désactive la vérification des hôtes connus. Ou vous pouvez vérifier que la clé de l'hôte correspond à une empreinte spécifique. L'empreinte peut être fournie au format md5, sha1 ou sha256, cependant, il est fortement recommandé d'utiliser uniquement sha256, car les autres options sont considérées comme non sécurisées selon les normes modernes. La valeur de l'empreinte doit être fournie sous forme de chaîne codée en hexadécimal :

host_key_check=sha256:04ce2ae89ff4295a6b9c4111640bdcb3297858ee55cb434d9dd88796e93aa795

La chaîne de clé peut éventuellement contenir des séparateurs ":" entre chaque paire de chiffres hexadécimaux.

Le fichier $HOME/.ssh/known_hosts contient les clés d'hôte codées en base64. Celles-ci peuvent être converties dans le format requis pour QEMU à l'aide d'une commande telle que :

$ for key in `grep 10.33.8.112 known_hosts | awk '{print $3}'`
  do
    echo $key | base64 -d | sha256sum
  done
  6c3aa525beda9dc83eadfbd7e5ba7d976ecb59575d1633c87cd06ed2ed6e366f  -
  12214fd9ea5b408086f98ecccd9958609bd9ac7c0ea316734006bc7818b45dc8  -
  d36420137bcbd101209ef70c3b15dc07362fbe0fa53c5b135eba6e6afa82f0ce  -

Notez qu'il peut y avoir plusieurs clés présentes par hôte, chacune avec des chiffrements de clé différents. Il faut veiller à choisir l'empreinte de clé qui correspond au chiffrement que QEMU négociera avec le serveur distant.

Actuellement, l'authentification doit se faire via ssh-agent. D'autres méthodes d'authentification peuvent être prises en charge à l'avenir.

Remarque : de nombreux serveurs ssh ne prennent pas en charge une opération de type fsync. Le pilote ssh ne peut pas garantir que les demandes de vidage du disque sont respectées, et cela risque de corrompre le disque si le serveur distant ou le réseau tombe en panne pendant les écritures. Le pilote affichera un avertissement lorsque fsync n'est pas pris en charge :

warning: ssh server ssh.example.com:22 does not support fsync

Avec des versions suffisamment récentes de libssh et OpenSSH, fsync est pris en charge.

Images disque NVMe

Les contrôleurs de stockage NVM Express (NVMe) peuvent être accédés directement par un pilote en espace utilisateur dans QEMU. Cela contourne le système de fichiers et les couches de blocs du noyau hôte tout en conservant les fonctionnalités de la couche de blocs QEMU, telles que les travaux de blocs, la limitation du débit d'E/S, les formats d'image, etc. Les performances d'E/S disque sont généralement supérieures à celles de -drive file=/dev/sda en utilisant soit un pool de threads, soit linux-aio.

Le contrôleur sera exclusivement utilisé par le processus QEMU une fois démarré. Pour pouvoir partager le stockage entre plusieurs machines virtuelles et d'autres applications sur l'hôte, veuillez utiliser les protocoles basés sur des fichiers.

Avant de démarrer QEMU, liez le contrôleur NVMe hôte au pilote vfio-pci de l'hôte. Par exemple :

# modprobe vfio-pci
# lspci -n -s 0000:06:0d.0
06:0d.0 0401: 1102:0002 (rev 08)
# echo 0000:06:0d.0 > /sys/bus/pci/devices/0000:06:0d.0/driver/unbind
# echo 1102 0002 > /sys/bus/pci/drivers/vfio-pci/new_id
# qemu-system-x86_64 -drive file=nvme://HOST:BUS:SLOT.FUNC/NAMESPACE

Syntaxe alternative utilisant les propriétés :

qemu-system-x86_64 -drive file.driver=nvme,file.device=HOST:BUS:SLOT.FUNC,file.namespace=NAMESPACE

HOST:BUS:SLOT.FUNC est l'adresse du périphérique PCI du contrôleur NVMe sur l'hôte.

NAMESPACE est le numéro de l'espace de noms NVMe, en commençant par 1.

Verrouillage de fichier image disque

Par défaut, QEMU tente de protéger les fichiers image contre les accès simultanés imprévus, tant que cela est pris en charge par le pilote de protocole de bloc et le système d'exploitation hôte. Si plusieurs processus QEMU (y compris les émulateurs QEMU et les utilitaires) tentent d'ouvrir la même image avec des modes d'accès conflictuels, tous sauf le premier recevront une erreur.

Cette fonctionnalité est actuellement prise en charge par le protocole de fichier sous Linux avec l'API de verrouillage Open File Descriptor (OFD) et peut être configurée pour utiliser le verrouillage POSIX si l'hôte POSIX ne prend pas en charge le verrouillage OFD Linux.

Pour activer explicitement le verrouillage d'image, spécifiez "locking=on" dans les options du pilote de protocole de fichier. Si le verrouillage OFD n'est pas possible, un avertissement sera affiché et l'API de verrouillage POSIX sera utilisée. Dans ce cas, il y a un risque que le verrou soit silencieusement perdu lors de l'insertion à chaud et des travaux de blocs, en raison des limitations de l'API de verrouillage POSIX.

QEMU gère de manière transparente le transfert de verrouillage lors de la migration de stockage partagé. Pour les images de disque virtuelles partagées entre plusieurs machines virtuelles, l'option de périphérique "share-rw" doit être utilisée.

Par défaut, l'invité a un accès en écriture exclusif à son image disque. Si l'invité peut partager en toute sécurité l'image disque avec d'autres écrivains, le paramètre -device ...,share-rw=on peut être utilisé. Ceci n'est sûr que si l'invité exécute un logiciel, tel qu'un système de fichiers en cluster, qui coordonne les accès disque pour éviter la corruption.

Notez que share-rw=on déclare seulement la capacité de l'invité à partager le disque. Certaines fonctionnalités QEMU, telles que les formats de fichiers image, nécessitent un accès en écriture exclusif à l'image disque et cela n'est pas affecté par l'option share-rw=on.

Alternativement, le verrouillage peut être entièrement désactivé par l'option de périphérique de bloc "locking=off". Dans le comm

et de ligne, l'option est généralement sous la forme de "file.locking=off" car le pilote de protocole est normalement placé comme un enfant "file" sous un pilote de format. Par exemple :

-blockdev driver=qcow2,file.filename=/path/to/image,file.locking=off,file.driver=file

Pour vérifier si le verrouillage de l'image est actif, consultez la sortie de la commande "lslocks" sur l'hôte et vérifiez s'il y a des verrous détenus par le processus QEMU sur le fichier image. Plus d'un octet peut être verrouillé par l'instance QEMU, chaque octet reflétant une permission particulière qui est acquise ou protégée par le pilote de bloc en cours d'exécution.

Pilotes de filtre

QEMU prend en charge plusieurs pilotes de filtre, qui ne stockent aucune donnée, mais effectuent des tâches supplémentaires, en interceptant les requêtes io.

preallocate
Le pilote de filtre preallocate est destiné à être inséré entre les nœuds de format et de protocole et préalloue de l'espace supplémentaire (agrandissant le fichier de protocole) lorsque l'on écrit au-delà de la fin du fichier. Cela peut être utile pour les systèmes de fichiers avec une allocation lente.

Options prises en charge :

prealloc-align
Lors de la préallocation, aligner la longueur du fichier sur cette valeur (en octets), par défaut 1M.
prealloc-size
Quantité à préallouer (en octets), par défaut 128M.
