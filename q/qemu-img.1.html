NOM

qemu-img - utilitaire d'image disque QEMU

SYNOPIS

qemu-img [options standard] commande [options de commande]

DESCRIPTION

qemu-img permet de créer, convertir et modifier des images hors ligne. Il peut gérer tous les formats d'image pris en charge par QEMU.

Attention : N'utilisez jamais qemu-img pour modifier des images utilisées par une machine virtuelle en cours d'exécution ou par tout autre processus ; cela pourrait détruire l'image. De plus, sachez que l'interrogation d'une image en cours de modification par un autre processus peut entraîner un état incohérent.

OPTIONS

Options standard :

-h, --help
Afficher cette aide et quitter
-V, --version
Afficher les informations de version et quitter
-T, --trace [[enable=]MOTIF][,events=FICHIER][,file=FICHIER]
Spécifier les options de traçage.

[enable=]MOTIF

Activer immédiatement les événements correspondant au MOTIF (nom d'événement ou motif de globbing). Cette option n'est disponible que si QEMU a été compilé avec le backend de traçage simple, log ou ftrace. Pour spécifier plusieurs événements ou motifs, spécifiez l'option -trace plusieurs fois.

Utilisez -trace help pour afficher la liste des noms des points de traçage.

events=FICHIER

Activer immédiatement les événements listés dans FICHIER. Le fichier doit contenir un nom d'événement (tel que listé dans le fichier trace-events-all) par ligne ; les motifs de globbing sont également acceptés. Cette option n'est disponible que si QEMU a été compilé avec le backend de traçage simple, log ou ftrace.

file=FICHIER

Enregistrer les sorties de traçage dans FICHIER. Cette option n'est disponible que si QEMU a été compilé avec le backend de traçage simple.

Paramètres de commande :

NOMFICHIER est le nom d'un fichier image disque.

FMT est le format de l'image disque. Il est généralement deviné automatiquement. Voir ci-dessous pour une description des formats d'image disque pris en charge.

TAILLE est la taille de l'image disque en octets. Les suffixes facultatifs k ou K (kilooctet, 1024) M (mégaoctet, 1024k) et G (gigaoctet, 1024M) et T (téraoctet, 1024G) sont pris en charge. b est ignoré.

NOMFICHIER_SORTIE est le nom du fichier image disque de destination.

FORMAT_SORTIE est le format de destination.

OPTIONS est une liste d'options spécifiques au format, séparées par des virgules, au format nom=valeur. Utilisez -o help pour un aperçu des options prises en charge par le format utilisé ou consultez les descriptions des formats ci-dessous pour plus de détails.

PARAM_SNAPSHOT est un paramètre utilisé pour les snapshots internes, au format 'snapshot.id=[ID],snapshot.name=[NOM]' ou '[ID_OU_NOM]'.

--object OBJETDEF
est une définition d'objet créable par l'utilisateur QEMU. Consultez la page de manuel de qemu(1) pour une description des propriétés des objets. Le type d'objet le plus courant est un secret, utilisé pour fournir des mots de passe et/ou des clés de chiffrement.
--image-opts
Indique que le paramètre source NOMFICHIER doit être interprété comme une chaîne d'options complète, et non comme un simple nom de fichier. Ce paramètre est mutuellement exclusif avec le paramètre -f.
--target-image-opts
Indique que le(s) paramètre(s) NOMFICHIER_SORTIE doit être interprété comme une chaîne d'options complète, et non comme un simple nom de fichier. Ce paramètre est mutuellement exclusif avec le(s) paramètre(s) -O. Il est actuellement nécessaire d'utiliser également le paramètre -n pour éviter la création de l'image. Cette restriction peut être assouplie dans une future version.
--force-share (-U)
Si spécifié, qemu-img ouvrira l'image en mode partagé, permettant à d'autres processus QEMU de l'ouvrir en mode écriture. Par exemple, cela peut être utilisé pour obtenir des informations sur l'image (avec la sous-commande 'info'.
mmand) lorsque l'image est utilisée par un invité en cours d'exécution. Notez que cela pourrait produire des résultats incohérents en raison de modifications concurrentes des métadonnées, etc. Cette option n'est autorisée que lors de l'ouverture d'images en mode lecture seule.
--backing-chain
Énumérera les informations sur les fichiers de sauvegarde dans une chaîne d'images disque. Reportez-vous ci-dessous pour plus de détails.
-c
Indique que l'image cible doit être compressée (uniquement pour qcow/qcow2 et vmdk avec le sous-format streamOptimized).

Pour qcow2, l'algorithme de compression peut être spécifié avec l'option -o compression_type=... (voir ci-dessous).

-h
Avec ou sans commande, affiche l'aide et liste les formats pris en charge.
-p
Affiche la barre de progression (uniquement pour les commandes compare, convert et rebase). Si l'option -p n'est pas utilisée pour une commande qui la prend en charge, la progression est signalée lorsque le processus reçoit un signal SIGUSR1 ou SIGINFO.
-q
Mode silencieux - n'imprime aucune sortie (sauf les erreurs). Il n'y a pas de barre de progression si les options -q et -p sont utilisées simultanément.
-S SIZE
Indique le nombre consécutif d'octets qui doivent contenir uniquement des zéros pour que qemu-img crée une image éparse lors de la conversion. Cette valeur est arrondie à l'inférieur au plus proche multiple de 512 octets. Vous pouvez utiliser les suffixes de taille courants tels que k pour les kilo-octets.
-t CACHE
Spécifie le mode de cache à utiliser avec le fichier (de destination). Consultez la documentation de l'option -drive cache=... de l'émulateur pour connaître les valeurs autorisées.
-T SRC_CACHE
Spécifie le mode de cache à utiliser avec le(s) fichier(s) source. Consultez la documentation de l'option -drive cache=... de l'émulateur pour connaître les valeurs autorisées.

Paramètres pour la sous-commande compare :

-f
Format de la première image
-F
Format de la seconde image
-s
Mode strict - échoue en cas de taille d'image ou d'allocation de secteur différente.

Paramètres pour la sous-commande convert :

--bitmaps
Copie également tous les bitmaps persistants de la couche supérieure de la source.
-n
Ignore la création du volume cible.
-m
Nombre de coroutines parallèles pour le processus de conversion.
-W
Autorise les écritures désordonnées vers la destination. Cette option améliore les performances, mais est recommandée uniquement pour les périphériques pré-alloués tels que les périphériques hôtes ou d'autres périphériques de bloc bruts.
-C
Tente d'utiliser le déchargement de copie pour déplacer les données de l'image source vers la cible. Cela peut améliorer les performances si les données sont distantes, comme avec des backends NFS ou iSCSI, mais ne rendra pas automatiquement épars les secteurs nuls, et peut entraîner une image cible entièrement allouée en fonction du support de l'hôte pour obtenir des informations d'allocation.
-r
Limitation du débit pour le processus de conversion.
--salvage
Tente d'ignorer les erreurs d'E/S lors de la lecture. Sauf en mode silencieux (-q), les erreurs seront toujours imprimées. Les zones qui ne peuvent pas être lues depuis la source seront traitées comme contenant uniquement des zéros.
--target-is-zero
Suppose que la lecture de l'image de destination renverra toujours des zéros. Ce paramètre est mutuellement exclusif avec une image de destination qui possède un fichier de sauvegarde. Il est nécessaire d'utiliser également le paramètre -n pour ignorer la création de l'image.

Paramètres pour la sous-commande dd :

bs=BLOCK_SIZE
Définit la taille du bloc.
count=BLOCKS
Définit le nombre de blocs d'entrée à copier.
if=INPUT
Définit le fichier d'entrée.
of=OUTPUT
Définit le fichier de sortie.
skip=BLOCKS
Définit le nombre de blocs d'entrée à sauter.

Paramètres pour la sous-commande snapshot :

snapshot
Est le nom du snapshot à créer, appliquer ou supprimer.
-a
Applique un snapshot (rétablir le disque à l'état sauvegardé).
-c
Crée un snapshot.
-d
Supprime un snapshot.
-l
Liste tous les snapshots dans l'image donnée (action par défaut).

Description de la commande :

amend [--object OBJECTDEF] [--image-opts] [-p] [-q] [-f FMT] [-t CACHE] [--force] -o OPTIONS FILENAME
Modifie les OPTIONS spécifiques au format d'image pour le fichier image FILENAME. Tous les formats de fichier ne prennent pas en charge cette opération.

L'ensemble des options qui peuvent être modifiées dépend du format de l'image, mais notez que la modification de la relation de chaîne de sauvegarde doit plutôt être effectuée avec qemu-img rebase.

--force permet certaines opérations dangereuses. Actuellement pour -f luks, il permet d'effacer la dernière clé de chiffrement et d'écraser une clé de chiffrement active.

bench [-c COUNT] [-d DEPTH] [-f FMT] [--flush-interval=FLUSH_INTERVAL] [-i AIO] [-n] [--no-drain] [-o OFFSET] [--pattern=PATTERN] [-q] [-s BUFFER_SIZE] [-S STEP_SIZE] [-t CACHE] [-w] [-U] FILENAME
Exécute un test de performance simple d'E/S séquentielles sur l'image spécifiée. Si -w est spécifié, un test d'écriture est effectué, sinon un test de lecture est effectué.

Un nombre total de COUNT requêtes d'E/S est effectué, chacune de taille BUFFER_SIZE octets, et avec DEPTH requêtes en parallèle. La première requête commence à la position donnée par OFFSET, chaque requête suivante augmente la position actuelle de STEP_SIZE. Si STEP_SIZE n'est pas donné, BUFFER_SIZE est utilisé pour sa valeur.

Si FLUSH_INTERVAL est spécifié pour un test d'écriture, la file d'attente des requêtes est vidée et un flush est émis avant de nouvelles écritures lorsque le nombre de requêtes restantes est un multiple de FLUSH_INTERVAL. Si en plus --no-drain est spécifié, un flush est émis sans vider d'abord la file d'attente des requêtes.

Si -i est spécifié, l'option AIO peut être utilisée pour spécifier différents backends AIO : threads, native ou io_uring.

Si -n est spécifié, le backend AIO natif est utilisé si possible. Sur Linux, cette option ne fonctionne que si -t none ou -t directsync est également spécifié.

Pour les tests d'écriture, par défaut un tampon rempli de zéros est écrit. Ceci peut être remplacé par un octet de motif spécifié par PATTERN.

bitmap (--merge SOURCE | --add | --remove | --clear | --enable | --disable)... [-b SOURCE_FILE [-F SOURCE_FMT]] [-g GRANULARITY] [--object OBJECTDEF] [--image-opts | -f FMT] FILENAME BITMAP
Effectue une ou plusieurs modifications du bitmap persistant BITMAP dans l'image disque FILENAME. Les différentes modifications sont :

--add pour créer BITMAP, activé pour enregistrer les modifications futures.

--remove pour supprimer BITMAP.

--clear pour effacer BITMAP.

--enable pour changer BITMAP afin de commencer à enregistrer les modifications futures.

--disable pour changer BITMAP afin d'arrêter d'enregistrer les modifications futures.

--merge pour fusionner le contenu du bitmap SOURCE dans BITMAP.

Les options supplémentaires incluent -g qui définit une GRANULARITY non par défaut pour --add, et -b et -F qui sélectionnent un fichier source alternatif pour tous les bitmaps SOURCE utilisés par --merge.

Pour voir quels bitmaps sont présents dans une image, utilisez qemu-img info.

check [--object OBJECTDEF] [--image-opts] [-q] [-f FMT] [--output=OFMT] [-r [leaks | all]] [-T SRC_CACHE] [-U] FILENAME
Effectue un

Effectue une vérification de cohérence sur l'image disque FILENAME. La commande peut générer une sortie au format OFMT qui est soit human (lisible par l'homme), soit json. La sortie JSON est un objet de type QAPI ImageCheck.

Si -r est spécifié, qemu-img essaie de réparer les incohérences trouvées lors de la vérification. -r leaks répare uniquement les fuites de clusters, tandis que -r all corrige tous les types d'erreurs, avec un risque plus élevé de choisir la mauvaise correction ou de masquer une corruption déjà survenue.

Seuls les formats qcow2, qed, parallels, vhdx, vmdk et vdi prennent en charge les vérifications de cohérence.

Si l'image ne présente aucune incohérence, la vérification se termine avec le code de sortie 0. D'autres codes de sortie indiquent le type d'incohérence trouvé ou si une autre erreur s'est produite. Le tableau suivant résume tous les codes de sortie de la sous-commande check :

0
Vérification terminée, l'image est (maintenant) cohérente
1
Vérification non terminée en raison d'erreurs internes
2
Vérification terminée, l'image est corrompue
3
Vérification terminée, l'image a des clusters de fuite, mais n'est pas corrompue
63
Les vérifications ne sont pas prises en charge par le format de l'image

Si -r est spécifié, les codes de sortie représentant l'état de l'image font référence à l'état après (la tentative de) sa réparation. Autrement dit, un -r all réussi donnera le code de sortie 0, indépendamment de l'état de l'image avant.

commit [--object OBJECTDEF] [--image-opts] [-q] [-f FMT] [-t CACHE] [-b BASE] [-r RATE_LIMIT] [-d] [-p] FILENAME
Valide les modifications enregistrées dans FILENAME dans son image de base ou son fichier de support. Si le fichier de support est plus petit que le snapshot, le fichier de support sera redimensionné pour avoir la même taille que le snapshot. Si le snapshot est plus petit que le fichier de support, le fichier de support ne sera pas tronqué. Si vous souhaitez que le fichier de support corresponde à la taille du snapshot plus petit, vous pouvez le tronquer vous-même en toute sécurité une fois l'opération de commit terminée avec succès.

L'image FILENAME est vidée après la réussite de l'opération. Si vous n'avez plus besoin de FILENAME après coup et que vous avez l'intention de le supprimer, vous pouvez éviter de le vider en spécifiant l'option -d.

Si la chaîne de fichiers de support de l'image donnée FILENAME comporte plus d'une couche, le fichier de support dans lequel les modifications seront validées peut être spécifié comme BASE (qui doit faire partie de la chaîne de support de FILENAME). Si BASE n'est pas spécifié, le fichier de support immédiat de l'image supérieure (qui est FILENAME) sera utilisé. Notez qu'après une opération de commit, toutes les images entre BASE et l'image supérieure seront invalides et pourront renvoyer des données incorrectes lors de la lecture. Pour cette raison, -b implique -d (afin que l'image supérieure reste valide).

La limite de débit pour le processus de commit est spécifiée par -r.

compare [--object OBJECTDEF] [--image-opts] [-f FMT] [-F FMT] [-T SRC_CACHE] [-p] [-q] [-s] [-U] FILENAME1 FILENAME2
Vérifie si deux images ont le même contenu. Vous pouvez comparer des images avec des formats ou des configurations différents.

Le format est sondé, sauf si vous le spécifiez avec l'option -f (utilisée pour FILENAME1) et/ou -F (utilisée pour FILENAME2).

Par défaut, les images de tailles différentes sont considérées comme identiques si l'image la plus grande ne contient que des secteurs non alloués et/ou zéros dans la zone après la fin de l'autre image. De plus, si un secteur n'est pas alloué dans une image et ne contient que des octets nuls dans la seconde, il est considéré comme égal. Vous pouvez utiliser le mode Strict en spécifiant l'option -s. Lorsque la comparaison s'exécute en mode Strict, elle échoue si la taille de l'image diffère ou si un secteur est alloué dans une image et n'est pas alloué dans la seconde.

Par défaut, la comparaison affiche un message de résultat. Ce message affiche des informations indiquant que les deux images sont identiques ou la position du premier octet différent. De plus, le message de résultat peut signaler une différence de taille d'image si le mode Strict est utilisé.

Compare se termine avec le code 0 si les images sont égales et avec le code 1 si elles diffèrent. D'autres codes de sortie signifient qu'une erreur s'est produite pendant l'exécution et que la sortie d'erreur standard doit contenir un message d'erreur. Le tableau suivant résume tous les codes de sortie de la sous-commande compare :

0
Les images sont identiques (ou l'aide demandée a été affichée)
1
Les images diffèrent
2
Erreur à l'ouverture d'une image
3
Erreur lors de la vérification de l'allocation d'un secteur
4
Erreur lors de la lecture des données
convert [--object OBJECTDEF] [--image-opts] [--target-image-opts] [--target-is-zero] [--bitmaps [--skip-broken-bitmaps]] [-U] [-C] [-c] [-p] [-q] [-n] [-f FMT] [-t CACHE] [-T SRC_CACHE] [-O OUTPUT_FMT] [-b BACKING_FILE [-F BACKING_FMT]] [-o OPTIONS] [-l SNAPSHOT_PARAM] [-S SPARSE_SIZE] [-r RATE_LIMIT] [-m NUM_COROUTINES] [-W] FILENAME [FILENAME2 [...]] OUTPUT_FILENAME
Convertit l'image disque FILENAME ou un snapshot SNAPSHOT_PARAM en image disque OUTPUT_FILENAME en utilisant le format OUTPUT_FMT. Elle peut être éventuellement compressée (option -c) ou utiliser des options spécifiques au format comme le chiffrement (option -o).

Seuls les formats qcow et qcow2 prennent en charge la compression. La compression est en lecture seule. Cela signifie que si un secteur compressé est réécrit, il est réécrit comme des données non compressées.

La conversion d'images est également utile pour obtenir une image plus petite lors de l'utilisation d'un format redimensionnable comme qcow : les secteurs vides sont détectés et supprimés de l'image de destination.

SPARSE_SIZE indique le nombre consécutif d'octets (par défaut 4 Ko) qui doivent contenir uniquement des zéros pour que qemu-img crée une image éparse lors de la conversion. Si SPARSE_SIZE est 0, la source ne sera pas scannée pour les secteurs non alloués ou vides, et l'image de destination sera toujours entièrement allouée.

Vous pouvez utiliser l'option BACKING_FILE pour forcer la création de l'image de sortie comme une image en copie sur écriture de l'image de base spécifiée ; BACKING_FILE doit avoir le même contenu que l'image de base de l'entrée, cependant le chemin, le format de l'image (tel que donné par BACKING_FMT), etc. peuvent différer.

Si un nom de chemin relatif est donné, le fichier de support est recherché par rapport au répertoire contenant OUTPUT_FILENAME.

Si l'option -n est spécifiée, la création du volume cible sera ignorée. Ceci est utile pour les formats tels que rbd si le volume cible a déjà été créé avec des options spécifiques au site qui ne peuvent pas être fournies via qemu-img.

Les écritures désordonnées peuvent être activées avec -W pour améliorer les performances. Ceci est recommandé uniquement pour les périphériques pré-alloués comme les périphériques hôtes ou d'autres périphériques de bloc bruts. Les écritures désordonnées ne fonctionnent pas en combinaison avec la création d'images compressées.

NUM_COROUTINES spécifie combien de coroutines travaillent en parallèle pendant le processus de conversion (par défaut 8).

L'utilisation de --bitmaps demande que tous les bitmaps persistants présents dans l'original soient également copiés vers la destination. Si un bitmap est incohérent dans la source, la conversion échouera à moins que --skip-broken-bitmaps ne soit également spécifié pour ne copier que les bitmaps cohérents.

create [-f FMT] [-o FMT_OPTS] [-b BACKING_FILE [-B BACKING_FMT]] [-u] [-q] [--object OBJDEF] FILE [SIZE]
Crée la nouvelle image disque FILE d'une taille de SIZE et au format FMT. Selon le format de fichier, vous pouvez ajouter une ou plusieurs options FMT_OPTS qui activent des fonctionnalités supplémentaires de ce format.

Si l'option BACKING_FILE est spécifiée, l'image n'enregistrera que les différences par rapport à BACKING_FILE. Aucune taille ne doit être spécifiée dans ce cas. BACKING_FILE ne sera jamais modifié à moins que vous n'utilisiez la commande de moniteur commit (ou qemu-img commit).

Si un nom de chemin relatif est donné, le fichier de support est recherché par rapport au répertoire contenant FILE.

Notez qu'un fichier de support donné sera ouvert pour vérifier qu'il est valide. Utilisez l'option -u pour activer le mode de fichier de support non sécurisé, ce qui signifie que l'image sera créée même si le fichier de support associé ne peut pas être ouvert. Un fichier de support correspondant doit être créé ou des options supplémentaires doivent être utilisées pour rendre la spécification du fichier de support valide lorsque vous souhaitez utiliser une image créée de cette manière.

La taille peut également être spécifiée en utilisant l'option SIZE avec -o, elle n'a pas besoin d'être spécifiée séparément dans ce cas.

dd [--image-opts] [-U] [-f FMT] [-O OUTPUT_FMT] [bs=BLOCK_SIZE] [count=BLOCKS] [skip=BLOCKS] if=INPUT of=OUTPUT
dd copie du fichier INPUT vers le fichier OUTPUT en le convertissant du format FMT au format OUTPUT_FMT.

Les données sont par défaut lues et écrites en utilisant des blocs de 512 octets, mais cela peut être modifié en spécifiant BLOCK_SIZE. Si count=BLOCKS est spécifié, dd s'arrêtera de lire l'entrée après avoir lu BLOCKS blocs d'entrée.

La syntaxe de taille est similaire à la syntaxe de taille de dd(1).

info [--object OBJECTDEF] [--image-opts] [-f FMT] [--output=OFMT] [--backing-chain] [-U] FILENAME
Donne des informations sur l'image disque FILENAME. Utilisez-la en particulier pour connaître l'espace réservé sur le disque, qui peut être différent de la taille affichée. Si des snapshots de VM sont stockés dans l'image disque, ils sont également affichés.

Si une image disque a une chaîne de fichiers de support, des informations sur chaque image disque de la chaîne peuvent être énumérées récursivement en utilisant l'option --backing-chain.

Par exemple, si vous avez une chaîne d'images comme :

base.qcow2 <- snap1.qcow2 <- snap2.qcow2

re>

Pour énumérer les informations sur chaque image disque de la chaîne ci-dessus, en commençant par le haut jusqu'à la base, faites :

qemu-img info --backing-chain snap2.qcow2

La commande peut afficher le résultat dans le format OFMT qui est soit human soit json. La sortie JSON est un objet de type QAPI ImageInfo ; avec --backing-chain, c'est un tableau d'objets ImageInfo.

--output=human rapporte les informations suivantes (pour chaque image de la chaîne) :

image
Le nom du fichier image
format du fichier
Le format de l'image
taille virtuelle
La taille du disque invité
taille du disque
L'espace qu'occupe le fichier image sur le système de fichiers hôte (peut être affiché comme 0 si cette information n'est pas disponible, par exemple parce qu'il n'y a pas de système de fichiers)
taille du cluster
La taille du cluster du format d'image, le cas échéant
chiffré
Si l'image est chiffrée (présent uniquement si c'est le cas)
arrêt propre
Ceci est affiché comme non si l'image est sale et devra être automatiquement réparée la prochaine fois qu'elle sera ouverte dans qemu.
fichier de sauvegarde
Le nom du fichier de sauvegarde, le cas échéant
format du fichier de sauvegarde
Le format du fichier de sauvegarde, si l'image l'impose
liste des snapshots
Une liste de tous les snapshots internes
informations spécifiques au format
Informations supplémentaires dont la structure dépend du format de l'image. Cette section est une représentation textuelle de l'objet QAPI ImageInfoSpecific* respectif (par exemple, ImageInfoSpecificQCow2 pour les images qcow2).
map [--object OBJECTDEF] [--image-opts] [-f FMT] [--start-offset=OFFSET] [--max-length=LEN] [--output=OFMT] [-U] FILENAME
Dump les métadonnées de l'image FILENAME et de sa chaîne de fichiers de sauvegarde. En particulier, cette commande dump l'état d'allocation de chaque secteur de FILENAME, ainsi que le fichier le plus haut qui l'alloue dans la chaîne de fichiers de sauvegarde.

Deux formats d'options sont possibles. Le format par défaut (human) ne dump que les zones connues comme non nulles du fichier. Les parties connues comme nulles du fichier sont omises, tout comme les parties qui ne sont pas allouées dans toute la chaîne. La sortie de qemu-img identifiera un fichier d'où les données peuvent être lues, et le décalage dans le fichier. Chaque ligne inclura quatre champs, dont les trois premiers sont des nombres hexadécimaux. Par exemple, la première ligne de :

Offset          Length          Mapped to       File
0               0x20000         0x50000         /tmp/overlay.qcow2
0x100000        0x10000         0x95380000      /tmp/backing.qcow2

signifie que 0x20000 (131072) octets commençant à l'offset 0 dans l'image sont disponibles dans /tmp/overlay.qcow2 (ouvert en format raw) commençant à l'offset 0x50000 (327680). Les données qui sont compressées, chiffrées, ou autrement indisponibles en format brut provoqueront une erreur si le format human est utilisé. Notez que les noms de fichiers peuvent inclure des sauts de ligne, il n'est donc pas sûr d'analyser ce format de sortie dans des scripts.

Le format alternatif json retournera un tableau de dictionnaires au format JSON. Il inclura des informations similaires dans les champs start, length, offset ; il inclura également d'autres informations plus spécifiques :

  • champ booléen data : vrai si les secteurs contiennent des données réelles, faux si les secteurs sont soit non alloués, soit stockés sous forme de clusters tout nuls optimisés
  • champ booléen zero : vrai si l'on sait que les données sont nulles
  • champ booléen present : vrai si les données appartiennent à la chaîne de sauvegarde, faux si le rebasage de la chaîne de sauvegarde sur un fichier plus profond récupérerait les données du fichier plus profond ;
  • champ entier depth : la profondeur dans la chaîne de sauvegarde à laquelle les données ont été résolues ; par exemple, une profondeur de 2 fait référence au fichier de sauvegarde du fichier de sauvegarde de FILENAME.

En format JSON, le champ offset est optionnel ; il est absent dans les cas où le format human omettrait l'entrée ou se terminerait par une erreur. Si data est faux et que le champ offset est présent, les secteurs correspondants dans le fichier ne sont pas encore utilisés, mais ils sont pré-alloués.

Pour plus d'informations, consultez include/block/block.h dans le code source de QEMU.

measure [--output=OFMT] [-O OUTPUT_FMT] [-o OPTIONS] [--size N | [--object OBJECTDEF] [--image-opts] [-f FMT] [-l SNAPSHOT_PARAM] FILENAME]
Calcule la taille de fichier requise pour une nouvelle image. Ces informations peuvent être utilisées pour dimensionner correctement les volumes logiques ou les LUNs SAN pour l'image qui y sera placée. Les valeurs rapportées sont garanties d'être suffisamment grandes pour contenir l'image. La commande peut afficher le résultat dans le format OFMT qui est soit human soit json. La sortie JSON est un objet de type QAPI BlockMeasureInfo.

Si la taille N est donnée, agissez comme si vous créiez un nouveau fichier image vide en utilisant qemu-img create. Si FILENAME est donné, agissez comme si vous convertissiez un fichier image existant en utilisant qemu-img convert. Le format du nouveau fichier est donné par OUTPUT_FMT tandis que le format d'un fichier existant est donné par FMT.

Un snapshot dans une image existante peut être spécifié en utilisant SNAPSHOT_PARAM.

Les champs suivants sont rapportés :

taille requise: 524288
taille entièrement allouée: 1074069504
taille des bitmaps: 0

La taille requise est la taille du fichier de la nouvelle image. Elle peut être inférieure à la taille du disque virtuel si le format de l'image prend en charge une représentation compacte.

La taille entièrement allouée est la taille du fichier de la nouvelle image une fois que des données ont été écrites dans tous les secteurs. C'est la taille maximale que le fichier image peut occuper, à l'exception des snapshots internes, des bitmaps sales, des données vmstate et d'autres fonctionnalités avancées du format d'image.

La taille des bitmaps est la taille supplémentaire requise pour copier les bitmaps d'une image source en plus des données visibles par l'invité ; la ligne est omise si la source ou la destination manque de prise en charge des bitmaps, ou 0 si les bitmaps sont pris en charge mais qu'il n'y a rien à copier.

snapshot [--object OBJECTDEF] [-f FMT | --image-opts] [-U] [-q] [-l | -a SNAPSHOT | -c SNAPSHOT | -d SNAPSHOT] FILENAME
Liste, applique, crée ou supprime des snapshots dans l'image FILENAME.
rebase [--object OBJECTDEF] [--image-opts] [-U] [-q] [-f FMT] [-t CACHE] [-T SRC_CACHE] [-p] [-u] [-c] -b BACKING_FILE [-B BACKING_FMT] FILENAME
Modifie le fichier de sauvegarde d'une image. Seuls les formats qcow2 et qed prennent en charge la modification du fichier de sauvegarde.

Le fichier de sauvegarde est modifié pour devenir BACKING_FILE et (si le format d'image de FILENAME le supporte) le format du fichier de sauvegarde est modifié pour devenir BACKING_FMT. Si BACKING_FILE est spécifié comme "" (la chaîne vide), alors l'image est rebasée sur aucun fichier de sauvegarde (c'est-à-dire qu'elle existera indépendamment de tout fichier de sauvegarde).

Si un nom de chemin relatif est donné, le fichier de sauvegarde est recherché par rapport au répertoire contenant FILENAME.

CACHE spécifie le mode de cache à utiliser pour FILENAME, tandis que SRC_CACHE spécifie le mode de cache pour la lecture des fichiers de sauvegarde.

Il existe deux modes différents dans lesquels rebase peut fonctionner :

Mode sécurisé
C'est le mode par défaut et il effectue une véritable opération de rebasage. Le nouveau fichier de sauvegarde peut différer de l'ancien et qemu-img rebase veillera à ce que le contenu visible par l'invité de FILENAME reste inchangé.

Pour ce faire, tous les clusters qui diffèrent entre BACKING_FILE et l'ancien fichier de sauvegarde de FILENAME sont fusionnés dans FILENAME avant de réellement changer le fichier de sauvegarde. Avec l'option -c spécifiée, les clusters qui sont fusionnés (mais pas l'intégralité de l'image FILENAME) sont compressés lors de leur écriture.

Notez que le mode sécurisé est une opération coûteuse, comparable à la conversion d'une image. Elle ne fonctionne que si l'ancien fichier de sauvegarde existe toujours.

Mode non sécurisé
qemu-img utilise le mode non sécurisé si -u est spécifié. Dans ce mode, seul le nom et le format du fichier de sauvegarde de FILENAME sont modifiés sans aucune vérification du contenu du fichier. L'utilisateur doit veiller à spécifier le bon nouveau fichier de sauvegarde, sinon le contenu visible par l'invité de l'image sera corrompu.

Ce mode est utile pour renommer ou déplacer le fichier de sauvegarde ailleurs. Il peut être utilisé sans qu'un ancien fichier de sauvegarde soit accessible, c'est-à-dire que vous pouvez l'utiliser pour corriger une image dont le fichier de sauvegarde a déjà été déplacé/renommé.

Vous pouvez utiliser rebase pour effectuer une opération de "diff" sur deux images disque. Cela peut être utile lorsque vous avez copié ou cloné un invité, et que vous voulez revenir à une image fine au-dessus d'un modèle ou d'une image de base.

Disons que base.img a été cloné en modified.img en le copiant, et que l'invité modified.img a tourné, il y a donc maintenant quelques changements par rapport à base.img. Pour construire une image fine appelée diff.qcow2 qui ne contient que les différences, faites :

qemu-img create -f qcow2 -b modified.img diff.qcow2
qemu-img rebase -b base.img diff.qcow2

À ce stade, modified.img peut être disc

ardé, car base.img + diff.qcow2 contient la même information.

resize [--object OBJECTDEF] [--image-opts] [-f FMT] [--preallocation=PREALLOC] [-q] [--shrink] FICHIER [+ | -]TAILLE
Modifie l'image disque comme si elle avait été créée avec TAILLE.

Avant d'utiliser cette commande pour réduire une image disque, vous DEVEZ utiliser les outils de système de fichiers et de partitionnement à l'intérieur de la VM pour réduire les systèmes de fichiers et les tailles de partition alloués en conséquence. Ne pas le faire entraînera une perte de données !

Lors de la réduction des images, l'option --shrink doit être donnée. Cela informe qemu-img que l'utilisateur reconnaît toute perte de données au-delà de la fin de l'image tronquée.

Après avoir utilisé cette commande pour agrandir une image disque, vous devez utiliser les outils de système de fichiers et de partitionnement à l'intérieur de la VM pour commencer réellement à utiliser le nouvel espace sur le périphérique.

Lors de l'agrandissement d'une image, l'option --preallocation peut être utilisée pour spécifier comment la zone d'image supplémentaire doit être allouée sur l'hôte. Voir la description du format dans la section Notes pour connaître les valeurs autorisées. L'utilisation de cette option peut entraîner l'allocation de données légèrement plus importantes que nécessaire.

NOTES

Formats de fichiers image pris en charge :

raw

Format d'image disque brut (par défaut). Ce format a l'avantage d'être simple et facilement exportable vers tous les autres émulateurs. Si votre système de fichiers prend en charge les trous (par exemple dans ext2 ou ext3 sous Linux ou NTFS sous Windows), seuls les secteurs écrits réservent de l'espace. Utilisez qemu-img info pour connaître la taille réelle utilisée par l'image ou ls -ls sous Unix/Linux.

Options prises en charge :

preallocation
Mode de préallocation (valeurs autorisées : off, falloc, full). Le mode falloc préalloue de l'espace pour l'image en appelant posix_fallocate(). Le mode full préalloue de l'espace pour l'image en écrivant des données sur le stockage sous-jacent. Ces données peuvent être des zéros ou non, selon l'emplacement de stockage.

qcow2

Format d'image QEMU, le format le plus polyvalent. Utilisez-le pour avoir des images plus petites (utile si votre système de fichiers ne prend pas en charge les trous, par exemple sous Windows), le chiffrement AES optionnel, la compression basée sur zlib ou zstd, et la prise en charge de plusieurs instantanés de VM.

Options prises en charge :

compat
Détermine la version qcow2 à utiliser. compat=0.10 utilise le format d'image traditionnel qui peut être lu par n'importe quel QEMU depuis 0.10. compat=1.1 active les extensions de format d'image que seuls QEMU 1.1 et versions ultérieures comprennent (c'est la valeur par défaut). Entre autres, cela inclut les clusters de zéros, qui permettent une copie sur lecture efficace pour les images éparses.
backing_file
Nom de fichier d'une image de base (voir la sous-commande create)
backing_fmt
Format d'image de l'image de base
compression_type
Cette option configure quel algorithme de compression sera utilisé pour les clusters compressés sur l'image. Notez que la définition de cette option ne provoque pas encore l'écriture réellement compressée de l'image. Elle est le plus souvent utilisée avec l'option -c de qemu-img convert, mais peut également être utilisée avec le pilote de filtre compress ou les travaux de sauvegarde de blocs avec compression activée.

Les valeurs valides sont zlib et zstd. Pour les images qui utilisent compat=0.10, seule la compression zlib est disponible.

encryption
Si cette option est définie sur on, l'image est chiffrée avec AES-CBC 128 bits.

L'utilisation du chiffrement dans les images qcow et qcow2 est considérée comme défectueuse selon les normes cryptographiques modernes, souffrant d'un certain nombre de problèmes de conception :

  • Le chiffrement AES-CBC est utilisé avec des vecteurs d'initialisation prévisibles basés sur le numéro de secteur. Cela le rend vulnérable aux attaques par texte claire choisi qui peuvent révéler l'existence de données chiffrées.
  • La phrase secrète de l'utilisateur est directement utilisée comme clé de chiffrement. Une phrase secrète mal choisie ou courte compromettra la sécurité du chiffrement.
  • En cas de compromission de la phrase secrète, il n'est pas possible de changer la phrase secrète pour protéger les données dans les images qcow. Les fichiers doivent être clonés, en utilisant une phrase secrète de chiffrement différente dans le nouveau fichier. Le fichier d'origine doit ensuite être effacé en toute sécurité à l'aide d'un programme comme shred, bien que même cela soit inefficace avec de nombreuses technologies de stockage modernes.
  • Les vecteurs d'initialisation utilisés pour chiffrer les secteurs sont basés sur le numéro de secteur virtuel de l'invité, au lieu du secteur physique de l'hôte. Lorsqu'une image disque a plusieurs instantanés internes, cela signifie que les données de plusieurs secteurs physiques sont chiffrées avec le même vecteur d'initialisation. Avec le mode CBC, cela ouvre la possibilité d'attaques de filigrane si l'attaquant peut collecter plusieurs secteurs chiffrés avec le même VI et des données prévisibles. Avoir plusieurs images qcow2 avec la même phrase secrète expose également cette faiblesse car la phrase secrète est directement utilisée comme clé.

L'utilisation du chiffrement qcow / qcow2 est donc fortement déconseillée. Il est recommandé aux utilisateurs d'utiliser une technologie de chiffrement alternative, telle que le système dm-crypt / LUKS de Linux.

cluster_size
Modifie la taille du cluster qcow2 (doit être comprise entre 512 octets et 2 Mo). Des tailles de cluster plus petites peuvent améliorer la taille du fichier image, tandis que des tailles de cluster plus grandes offrent généralement de meilleures performances.
preallocation
Mode de préallocation (valeurs autorisées : off, metadata, falloc, full). Une image avec métadonnées préallouées est initialement plus grande mais peut améliorer les performances lorsque l'image a besoin de croître. Les préallocations falloc et full sont similaires aux mêmes options du format raw, mais configurent également les métadonnées.
lazy_refcounts
Si cette option est définie sur on, les mises à jour du compteur de références sont reportées dans le but d'éviter les I/O de métadonnées et d'améliorer les performances. Ceci est particulièrement intéressant avec cache=writethrough qui ne regroupe pas les mises à jour des métadonnées. Le compromis est qu'après un crash de l'hôte, les tables de comptage de références doivent être reconstruites, c'est-à-dire que lors de la prochaine ouverture, un qemu-img check -r all (automatique) est requis, ce qui peut prendre un certain temps.

Cette option ne peut être activée que si compat=1.1 est spécifié.

nocow
Si cette option est définie sur on, elle désactivera la copie sur écriture (COW) du fichier. Elle n'est valide que sur btrfs, sans effet sur les autres systèmes de fichiers.

Btrfs a de faibles performances lors de l'hébergement d'un fichier d'image de VM, encore plus lorsque l'invité sur la VM utilise également btrfs comme système de fichiers. Désactiver COW est un moyen d'atténuer ces mauvaises performances. Généralement, il existe deux façons de désactiver COW sur btrfs :

  • Désactivez-la en montant avec nodatacow, alors tous les nouveaux fichiers seront NOCOW
  • Pour un fichier vide, ajoutez l'attribut de fichier NOCOW. C'est ce que fait cette option.

Remarque : cette option n'est valide que pour les fichiers nouveaux ou vides. S'il existe un fichier existant qui est COW et contient déjà des blocs de données, il ne pourra pas être changé en NOCOW en définissant nocow=on. On peut exécuter lsattr filename pour vérifier si le drapeau NOCOW est défini ou non (un 'C' majuscule est le drapeau NOCOW).

data_file
Nom du fichier où toutes les données de l'invité seront stockées. Si cette option est utilisée, le fichier qcow2 ne contiendra que les métadonnées de l'image.

Remarque : une perte de données se produira si le nom de fichier fourni existe déjà lors de l'utilisation de cette option avec qemu-img create car qemu-img créera un nouveau fichier de données, écrasant le contenu d'origine du fichier. Pour simplement mettre à jour la référence pour pointer vers le fichier préexistant donné, utilisez qemu-img amend.

data_file_raw
Si cette option est définie sur on, QEMU gardera toujours le fichier de données externe cohérent en tant qu'image brute autonome en lecture seule.

Il le fait en transmettant toutes les écritures vers le fichier qcow2 au fichier de données brut, y compris leurs décalages. Par conséquent, les données visibles sur le nœud qcow2 (c'est-à-dire pour l'invité) à un certain décalage sont visibles au même décalage dans le fichier de données brut. Cela résulte en une image brute en lecture seule. Les écritures qui contournent les métadonnées qcow2 peuvent corrompre les métadonnées qcow2 car les écritures hors bande peuvent entraîner une désynchronisation des métadonnées avec l'image brute.

Si cette option est off, QEMU utilisera le fichier de données pour stocker les données de manière arbitraire. Le contenu du fichier n'aura aucun sens sans les métadonnées qcow2 accompagnant. L'endroit où les données seront écrites n'aura aucun rapport avec leur décalage tel que vu par l'invité, et certaines écritures (en particulier les écritures de zéros) peuvent ne pas être transmises au fichier de données du tout, mais seront uniquement gérées en modifiant les métadonnées qcow2.

Cette option ne peut être activée que si data_file est défini.

Autres

QEMU prend également en charge divers autres formats de fichiers image pour la compatibilité avec les anciennes versions de QEMU ou d'autres hyperviseurs, y compris VMDK, VDI, VHD (vpc), VHDX, qcow1 et QED. Pour une liste complète des formats pris en charge, voir qemu-img --help. Pour une description plus détaillée de ces formats, voir la documentation de référence des pilotes de bloc QEMU.

Le but principal des pilotes de bloc pour ces formats est la conversion d'images. Pour exécuter des VM, il est recommandé de convertir les images disque en format brut ou qcow2 afin d'obtenir de bonnes performances.
