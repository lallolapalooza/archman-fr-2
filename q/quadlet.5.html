podman-systemd.unit(5) Manuel des formats de fichiers podman-systemd.unit(5)

NOM

podman-systemd.unit - Unités systemd utilisant Podman Quadlet

SYNTAXE

nom.container, nom.volume, nom.network, nom.kube nom.image, nom.build nom.pod, nom.artifact

Chemin de recherche des unités rootful de Podman

Les fichiers Quadlet pour l'utilisateur root peuvent être placés dans les répertoires suivants, classés par ordre de priorité. Cela signifie que les quadlets portant le même nom trouvés dans /run ont la priorité sur ceux de /etc, ainsi que sur ceux de /usr :

Quadlets temporaires, généralement utilisés pour les tests :

•
/run/containers/systemd/

Quadlets définis par l'administrateur système :

•
/etc/containers/systemd/

Quadlets définis par la distribution :

•
/usr/share/containers/systemd/

Chemin de recherche des unités rootless de Podman

Les fichiers Quadlet pour les utilisateurs non-root peuvent être placés dans les répertoires suivants :

  • $XDG_RUNTIME_DIR/containers/systemd/
  • $XDG_CONFIG_HOME/containers/systemd/ ou ~/.config/containers/systemd/
  • /etc/containers/systemd/users/$(UID)
  • /etc/containers/systemd/users/

Utilisation des liens symboliques

Quadlet prend en charge l'utilisation de liens symboliques pour la base des chemins de recherche et à l'intérieur de ceux-ci.

DESCRIPTION

Podman permet de construire et de démarrer des conteneurs (et de créer des volumes) via systemd en utilisant un générateur systemd. Ces fichiers sont lus au démarrage (et lorsque systemctl daemon-reload est exécuté) et génèrent les fichiers d'unité de service systemd correspondants. Les unités systemd système et utilisateur sont supportées. Toutes les options et tables disponibles dans les fichiers d'unité systemd standard sont supportées. Par exemple, les options définies dans la table [Service] et les tables [Install] sont transmises directement à systemd et gérées par celui-ci. Voir la page man systemd.unit(5) pour plus d'informations.

Le générateur Podman lit les chemins de recherche ci-dessus et lit les fichiers avec les extensions .container, .volume, .network, .build, .pod, .kube et .artifact, et pour chaque fichier, il génère un fichier .service portant le même nom. Sachez que les services existants du fournisseur (c'est-à-dire dans /usr/) sont remplacés s'ils portent le même nom. Les fichiers d'unité générés peuvent être démarrés et gérés avec systemctl comme n'importe quel autre service systemd. systemctl {--user} list-unit-files liste les fichiers d'unité existants sur le système.

Les fichiers Podman utilisent le même format que les fichiers d'unité systemd classiques. Chaque type de fichier a une section personnalisée (par exemple, [Container]) qui est gérée par Podman, et toutes les autres sections sont transmises intactes, permettant l'utilisation de toutes les options de configuration systemd normales comme les dépendances ou les limites cgroup.

Les fichiers source prennent également en charge les "drop-ins" de la même manière que systemd. Pour un fichier source donné (foo.container), le répertoire .d correspondant (foo.container.d) sera scanné à la recherche de fichiers avec une extension .conf, qui seront ensuite fusionnés dans le fichier de base par ordre alphabétique. Les "drop-ins" de type principal (container.d) seront également inclus. Si l'unité contient des tirets ("-") dans son nom (foo-bar-baz.container), alors les répertoires de "drop-ins" générés en tronquant le nom après le tiret sont également recherchés (foo-.container.d et foo-bar-.container.d). Les fichiers "drop-in" portant le même nom plus loin dans la hiérarchie remplacent ceux plus haut (foo-bar-baz.container.d/10-override.conf remplace foo-bar-.container.d/10-override.conf, qui remplace foo-.service.d/10-override.conf, qui remplace container.d/10-override.conf). Le format de ces fichiers "drop-in" est le même que celui du fichier de base. Ceci est utile pour modifier ou ajouter des paramètres de configuration à une unité, sans avoir à modifier les fichiers d'unité.

Pour les conteneurs rootless, lorsque les administrateurs placent des fichiers Quadlet dans le répertoire /etc/containers/systemd/users, les sessions de tous les utilisateurs exécutent le Quadlet lorsque la session de connexion commence. Si l'administrateur place un fichier Quadlet dans le répertoire /etc/containers/systemd/users/${UID}/, alors seul l'utilisateur avec l'UID correspondant exécute le Quadlet lorsque la session de connexion démarre. Pour les fichiers d'unité placés dans des sous-répertoires de /etc/containers/systemd/user/${UID}/ et dans les autres chemins de recherche d'unités utilisateur, Quadlet recherchera et exécutera récursivement les fichiers d'unité présents dans ces sous-répertoires.

Notez que les unités Quadlet ne prennent pas en charge l'exécution en tant qu'utilisateur non-root en définissant les options systemd User, Group ou DynamicUser. Si vous souhaitez exécuter un Quadlet rootless, vous devrez créer l'utilisateur et ajouter le fichier d'unité à l'un des chemins de recherche d'unités rootless ci-dessus.

Note : Lorsque Quadlet démarre, Podman télécharge ou construit souvent une ou plusieurs images de conteneur, ce qui peut prendre considérablement de temps. Systemd limite par défaut le temps de démarrage des services à 90 secondes, ou échoue le service. Pré-télécharger l'image ou prolonger le temps de délai d'attente de systemd pour le service en utilisant l'option de service TimeoutStartSec peut résoudre le problème. Un mot de prudence : TimeoutStartSec n'est pas disponible pour les unités Type=oneshot. Référez-vous à systemd.service(5) pour plus d'informations sur la gestion des temps de démarrage longs pour les unités qui n'ont pas besoin de rester actives une fois leur processus principal terminé.

L'ajout du fragment suivant à un fichier Quadlet prolonge le délai d'attente de systemd à 15 minutes.

[Service]
TimeoutStartSec=900

Quadlet nécessite l'utilisation de cgroup v2, utilisez podman info --format {{.Host.CgroupsVersion}} pour vérifier sur le système.

Type de service

Par défaut, le champ Type de la section Service du fichier Quadlet n'a pas besoin d'être défini. Quadlet le définira sur notify pour les fichiers .container et .kube, forking pour les fichiers .pod, et oneshot pour les fichiers .volume, .network, .build, .image et .artifact.

Cependant, Type peut être explicitement défini sur oneshot pour les fichiers .container et .kube lorsqu'aucun conteneur n'est censé s'exécuter une fois que podman est sorti.

Lors de la définition de Type=oneshot, il est recommandé de définir également RemainAfterExit=yes pour éviter que l'état du service ne devienne inactive (dead). Cependant, lors de l'activation d'un service via une unité de minuterie, avoir RemainAfterExit=yes laisse le travail dans un état "démarré" ce qui empêche les activations ultérieures par la minuterie. Pour plus d'informations, voir la page man systemd.service(5).

Activation des fichiers d'unité

Les services créés par Podman sont considérés comme transitoires par systemd, ce qui signifie qu'ils n'ont pas les mêmes règles de persistance que les unités normales. En particulier, il n'est pas possible de les systemctl enable pour qu'ils soient automatiquement activés au prochain démarrage.

Pour compenser cela, le générateur applique manuellement la section [Install] des fichiers d'unité de définition de conteneur pendant la génération, de la même manière que systemctl enable le fait lorsqu'il est exécuté ultérieurement.

Par exemple, pour démarrer un conteneur au démarrage, ajoutez quelque chose comme ceci au fichier :

[Install]
WantedBy=default.target

Actuellement, seules les clés Alias, WantedBy, RequiredBy et UpheldBy sont prises en charge.

La section Install peut faire partie du fichier principal, ou elle peut être dans un fichier "drop-in" séparé comme décrit ci-dessus. Ce dernier permet d'installer une unité non activée et de l'activer ensuite en installant le "drop-in".

Fichiers modèles

name.service" lorsqu'ils sont en cours d'exécution, mais qui peuvent être instanciés plusieurs fois à partir d'un seul fichier "basename@.service". Les instances individuelles peuvent également être différentes en utilisant des fichiers de remplacement (drop-in) avec le nom d'instance complet.

Les Quadlets prennent en charge cela de deux manières. Tout d'abord, une unité quadlet avec une forme de modèle générera un service systemd avec une forme de modèle, et le service systemd modèle peut être utilisé comme un modèle régulier. Par exemple, "foo@.container" générera "foo@.service" et vous pourrez ensuite démarrer "systemctl start foo@bar.service".

Deuxièmement, si vous créez un lien symbolique comme "foo@instance.container", cela générera un fichier modèle instancié. Lors de la génération de ce fichier, quadlet lira les fichiers de remplacement à la fois dans le répertoire instancié (foo@instance.container.d) et dans le répertoire du modèle (foo@.container.d). Cela permet la personnalisation des instances individuelles.

Les fichiers modèles instanciés (comme foo@bar.container) peuvent être activés tout comme ceux qui ne sont pas des modèles. Cependant, les modèles (foo@.container) sont différents, car ils doivent être instanciés. Si la section [Install] contient une clé DefaultInstance=, alors cette instance sera activée, mais sinon, rien ne se passera et les options seront uniquement utilisées comme défaut pour les unités qui sont instanciées en utilisant des liens symboliques.

Un exemple de fichier modèle sleep@.container pourrait ressembler à ceci :

[Unit]
Description=Un conteneur endormi modèle
[Container]
Image=quay.io/fedora/fedora
Exec=sleep %i
[Service]
# Redémarre le service lorsque sleep se termine
Restart=always
[Install]
WantedBy=multi-user.target
DefaultInstance=100

Si cela est installé, alors au démarrage, il y aura un sleep@100.service en cours d'exécution qui dort pendant 100 secondes. Vous pouvez ensuite faire quelque chose comme systemctl start sleep@50.service pour démarrer une autre instance qui dort 50 secondes, ou alternativement un autre service peut le démarrer via une dépendance comme Wants=sleep@50.service.

De plus, si vous faites ln -s sleep@.container sleep@10.container, vous aurez également un sommeil de 10 secondes en cours d'exécution au démarrage. Et, si vous souhaitez que cette instance particulière s'exécute avec une autre image, vous pouvez créer un fichier de remplacement comme sleep@10.container.d/10-image.conf :

[Container]
Image=quay.io/centos/centos

Chemins relatifs

Afin de prendre en charge les spécificateurs systemd, Quadlet ne résout pas les chemins relatifs qui commencent par %. Pour résoudre un tel chemin, préfixez-le avec ./.

Par exemple, au lieu de EnvironmentFile=%n/env utilisez EnvironmentFile=./%n/env

Débogage des fichiers d'unité

Après avoir placé le fichier d'unité dans l'un des chemins de recherche des unités (mentionnés ci-dessus), vous pouvez le démarrer avec systemctl start {--user}. S'il échoue avec "Failed to start example.service: Unit example.service not found.", alors il est possible que vous ayez utilisé une syntaxe incorrecte ou que vous ayez utilisé une option d'une version plus récente de Podman Quadlet et que le générateur n'ait pas réussi à créer un fichier de service.

Visualisez les fichiers générés et/ou les messages d'erreur avec :

/usr/lib/systemd/system-generators/podman-system-generator {--user} --dryrun

Alternativement, affichez uniquement les erreurs avec :

systemd-analyze {--user} --generators=true verify example.service

Cette commande effectue également des vérifications supplémentaires sur l'unité de service générée. Pour plus de détails, consultez la page de manuel systemd-analyze(1).

Débogage d'un ensemble limité de fichiers d'unité

Si vous souhaitez déboguer un ensemble limité de fichiers d'unité, vous pouvez les copier dans un répertoire séparé et définir la variable d'environnement QUADLET_UNIT_DIRS sur ce répertoire lors de l'exécution de la commande ci-dessous :

QUADLET_UNIT_DIRS=<Répertoire> /usr/lib/systemd/system-generators/podman-system-generator {--user} --dryrun

Cela indiquera à Quadlet de rechercher les unités dans ce répertoire au lieu des répertoires courants et limitera ainsi la sortie aux seules unités que vous déboguez.

Dépendances réseau implicites

Quadlet ajoutera des dépendances sur network-online.target (en tant que root) ou podman-user-wait-network-online.service (en tant qu'utilisateur) en ajoutant les propriétés After= et Wants= à l'unité. Ceci afin de garantir que le réseau est accessible si une image doit être téléchargée et au moment où le conteneur est démarré.

Le cas spécial de l'unité podman-user-wait-network-online.service est nécessaire en tant qu'utilisateur car les unités utilisateur ne peuvent pas attendre les unités système (root), donc network-online.target n'y fait rien et est ignoré à la place. Comme cela a causé un nombre important de problèmes, nous avons décidé de contourner cela avec notre propre unité à usage spécial qui vérifie simplement si l'unité network-online.target est active avec systemctl is-active network-online.target.

Ce comportement peut être désactivé en ajoutant DefaultDependencies=false dans la section Quadlet. Notez que la section [Unit] de systemd a une option du même nom mais avec une signification différente.

Dépendance entre les unités Quadlet

Quadlet traduira automatiquement les dépendances, spécifiées dans les clés Wants, Requires, Requisite, BindsTo, PartOf, Upholds, Conflicts, Before et After de la section [Unit], entre différentes unités Quadlet.

Par exemple, l'unité fedora.container ci-dessous spécifie une dépendance sur l'unité basic.container.

[Unit]
After=basic.container
Requires=basic.container
[Container]
Image=registry.fedoraproject.org/fedora:41

Définition des noms de ressources

Les unités Quadlet permettent de définir les noms des ressources créées (par exemple, VolumeName pour les unités .volume ou PodName pour les unités .pod).

Notez que l'utilisation de spécificateurs systemd qui référencent l'unité de service générée (par exemple, $N) nuit à la capacité de Quadlet à établir des liens entre les ressources car ils sont traduits différemment dans chaque service.

Unités de conteneur [Container]

Les unités de conteneur sont nommées avec une extension .container et contiennent une section [Container] décrivant le conteneur qui est exécuté comme service. Le fichier de service résultant contient une ligne comme ExecStart=podman run … image-name, et la plupart des clés de cette section contrôlent les options de ligne de commande passées à Podman. Cependant, certaines options affectent également les détails de la façon dont systemd est configuré pour exécuter et interagir avec le conteneur.

Par défaut, le conteneur Podman porte le même nom que l'unité, mais avec un préfixe systemd-, c'est-à-dire qu'un fichier $name.container crée une unité $name.service et un conteneur Podman systemd-$name. L'option ContainerName permet de remplacer ce nom par défaut par un nom fourni par l'utilisateur.

Il n'y a qu'une seule clé requise, Image, qui définit l'image du conteneur exécuté par le service.

Description de la section [Container] :

AddCapability=

Ajoute ces capacités, en plus de l'ensemble de capacités par défaut de Podman, au conteneur.

Il s'agit d'une liste de capacités séparées par des espaces. Cette clé peut être listée plusieurs fois.

Par exemple :

AddCapability=CAP_DAC_OVERRIDE CAP_IPC_OWNER

AddDevice=

Ajoute un nœud de périphérique de l'hôte dans le conteneur. Le format est PÉRIPHÉRIQUE_HÔTE[:PÉRIPHÉRIQUE_CONTENEUR][:PERMISSIONS], où PÉRIPHÉRIQUE_HÔTE est le chemin du nœud de périphérique sur l'hôte, PÉRIPHÉRIQUE_CONTENEUR est le chemin du nœud de périphérique dans le conteneur, et PERMISSIONS est une liste de permissions combinant 'r' pour lecture, 'w' pour écriture, et 'm' pour mknod(2). Le préfixe - indique à Quadlet d'ajouter le périphérique uniquement s'il existe sur l'hôte.

Cette clé peut être listée plusieurs fois.

AddHost=

Ajoute un mappage hôte-IP à /etc/hosts. Le format est nom_hote:ip.

Équivalent à l'option --add-host de Podman. Cette clé peut être listée plusieurs fois.

Annotation=

Définit une ou plusieurs annotations OCI sur le conteneur. Le format est une liste d'éléments clé=valeur, similaire à Environment.

Cette clé peut être listée plusieurs fois.

AutoUpdate=

Indique si le conteneur sera mis à jour automatiquement (podman-auto-update(1)). Les valeurs suivantes sont prises en charge :

  • registry : Nécessite une référence d'image complètement qualifiée (par exemple, quay.io/podman/stable:latest) pour créer le conteneur. Cette vérification est nécessaire pour savoir quelle image vérifier et télécharger. Si un ID d'image a été utilisé, Podman ne sait plus quelle image vérifier/télécharger.
  • local : Indique à Podman de comparer l'image utilisée par un conteneur à l'image portant son nom brut dans le stockage local. Si une image est mise à jour localement, Podman redémarre simplement l'unité systemd qui exécute le conteneur.

CgroupsMode=

Le mode cgroups du conteneur Podman. Équivalent à l'option --cgroups de Podman.

Par défaut, le mode cgroups du conteneur créé par Quadlet est split, ce qui diffère du mode par défaut (enabled) utilisé par l'interface en ligne de commande de Podman.

Si le conteneur rejoint un pod (c'est-à-dire si Pod= est spécifié), vous voudrez peut-être changer ceci en no-conmon ou enabled afin que les limites de ressources cgroup au niveau du pod puissent prendre effet.

ContainerName=

Le nom (facultatif) du conteneur Podman. S'il n'est pas spécifié, la valeur par défaut systemd-%N est utilisée, ce qui est identique au nom du service mais avec un préfixe systemd- pour éviter les conflits avec les conteneurs gérés par l'utilisateur.

ContainersConfModule=

Charge le module containers.conf(5) spécifié. Équivalent à l'option --module de Podman.

Cette clé peut être listée plusieurs fois.

DNS=

Définit le résolveur/serveur de noms DNS à portée réseau pour les conteneurs de ce réseau.

Cette clé peut être listée plusieurs fois.

DNSOption=

Définit des options DNS personnalisées.

Cette clé peut être listée plusieurs fois.

DNSSearch=

Définit les domaines de recherche DNS personnalisés. Utilisez DNSSearch=. pour supprimer le domaine de recherche.

Cette clé peut être listée plusieurs fois.

DropCapability=

Supprime ces capacités de l'ensemble de capacités par défaut de Podman, ou all pour supprimer toutes les capacités.

Il s'agit d'une liste de capacités séparées par des espaces. Cette clé peut être listée plusieurs fois.

Par exemple :

DropCapability=CAP_DAC_OVERRIDE CAP_IPC_OWNER

Entrypoint=

Remplace l'ENTRYPOINT par défaut de l'image. Équivalent à l'option --entrypoint de Podman. Spécifiez plusieurs commandes en tant que chaîne JSON.

Environment=

Définit une variable d'environnement dans le conteneur. Utilise le même format que les services dans systemd et peut être listé plusieurs fois.

EnvironmentFile=

Utilise un fichier délimité par des lignes pour définir des variables d'environnement dans le conteneur. Le chemin peut être absolu ou relatif à l'emplacement du fichier d'unité. Cette clé peut être utilisée plusieurs fois, et l'ordre est conservé lors du passage à podman run.

EnvironmentHost=

Utilise l'environnement de l'hôte à l'intérieur du conteneur.

Exec=

Arguments supplémentaires pour le conteneur ; cela a exactement le même effet que de passer des arguments supplémentaires après une invocation de podman run <image> <arguments>.

Le format est identique à celui des lignes de commande systemd. Cependant, contrairement au scénario d'utilisation du verbe systemd ExecStart=, qui opère sur le système de fichiers racine ambiant, il est très courant que les images de conteneur aient leurs propres métadonnées ENTRYPOINT ou CMD avec lesquelles cela interagit.

L'attente par défaut pour de nombreuses images est que l'image inclue un ENTRYPOINT avec un binaire par défaut, et ce champ ajoutera des arguments à cet entrypoint.

Une autre façon de décrire cela est qu'il fonctionne de la même manière que le champ args dans un pod Kubernetes.

ExposeHostPort=

Expose un port, ou une plage de ports (par exemple, 50-59), de l'hôte au conteneur. Équivalent à l'option --expose de Podman.

Cette clé peut être listée plusieurs fois.

GIDMap=

Exécute le conteneur dans un nouvel espace de noms utilisateur en utilisant le mappage GID fourni. Équivalent à l'option --gidmap de Podman.

Cette clé peut être listée plusieurs fois.

GlobalArgs=

Cette clé contient une liste d'arguments passés directement entre podman et run dans le fichier généré. Elle peut être utilisée pour accéder à des fonctionnalités de Podman autrement non prises en charge par le générateur. Comme le générateur n'est pas conscient des interactions inattendues que ces arguments peuvent causer, il n'est pas recommandé d'utiliser cette option.

Le format est une liste d'arguments séparés par des espaces, qui peuvent éventuellement être échappés individuellement pour permettre l'inclusion d'espaces blancs et d'autres caractères de contrôle.

Cette clé peut être listée plusieurs fois.

Group=

Le GID (numérique) à utiliser à l'intérieur du conteneur. Il n'est pas nécessaire que cela corresponde au GID sur l'hôte, qui peut être modifié avec UserNS, mais si cela n'est pas spécifié, ce GID est également utilisé sur l'hôte.

Remarque : lorsque User= et Group= sont spécifiés, ils sont combinés en un seul argument --user USER:GROUP passé à Podman. L'utilisation de Group= sans User= entraînera une erreur.

GroupAdd=

Attribue des groupes supplémentaires à l'utilisateur principal s'exécutant dans le processus du conteneur. Prend également en charge le drapeau spécial keep-groups. Équivalent à l'option Podman --group-add.

HealthCmd=

Définit ou modifie une commande de vérification de santé pour un conteneur. Une valeur de none désactive les vérifications de santé existantes. Équivalent à l'option Podman --health-cmd.

HealthInterval=

Définit un intervalle pour les vérifications de santé. Un intervalle de disable ne mettra en place aucun minuteur automatique. Équivalent à l'option Podman --health-interval.

HealthLogDestination=

Définit la destination du journal de la vérification de santé. Chemin de répertoire, local ou events_logger (utilisation locale du fichier d'état du conteneur) (Défaut : local) Équivalent à l'option Podman --health-log-destination.

  • local : (défaut) Les journaux de vérification de santé sont stockés dans les conteneurs overlay. (Par exemple : $runroot/healthcheck.log)
  • directory : crée un fichier journal nommé <container-ID>-healthcheck.log contenant les journaux de vérification de santé dans le répertoire spécifié.
  • events_logger : le journal sera écrit avec le mécanisme de journalisation défini par events_logger. Il enregistre également le journal dans un répertoire par défaut, pour les performances sur un système avec un grand nombre de journaux.

HealthMaxLogCount=

Définit le nombre maximum de tentatives dans le fichier journal de vérification de santé. ('0' la valeur signifie un nombre infini de tentatives dans le fichier journal) (Défaut : 5 tentatives) Équivalent à l'option Podman --Health-max-log-count.

HealthMaxLogSize=

Définit la longueur maximale en caractères du journal de vérification de santé stocké. ("0" la valeur signifie une longueur de journal infinie) (Défaut : 500 caractères) Équivalent à l'option Podman --Health-max-log-size.

HealthOnFailure=

Action à entreprendre une fois que le conteneur passe à un état non sain. L'action "kill" en combinaison s'intègre mieux avec systemd. Une fois que le conteneur devient non sain, il est arrêté et systemd redémarre le service. Équivalent à l'option Podman --health-on-failure.

HealthRetries=

Le nombre de tentatives autorisées avant qu'une vérification de santé ne soit considérée comme non saine. Équivalent à l'option Podman --health-retries.

HealthStartPeriod=

Le temps d'initialisation nécessaire au démarrage d'un conteneur. Équivalent à l'option Podman --health-start-period.

HealthStartupCmd=

Définit une commande de vérification de santé au démarrage pour un conteneur. Équivalent à l'option Podman --health-startup-cmd.

HealthStartupInterval=

Définit un intervalle pour la vérification de santé au démarrage. Un intervalle de disable ne mettra en place aucun minuteur automatique. Équivalent à l'option Podman --health-startup-interval.

HealthStartupRetries=

Le nombre de tentatives autorisées avant que la vérification de santé au démarrage ne redémarre le conteneur. Équivalent à l'option Podman --health-startup-retries.

HealthStartupSuccess=

Le nombre d'exécutions réussies requis avant que la vérification de santé au démarrage ne réussisse et que la vérification de santé régulière ne commence. Équivalent à l'option Podman --health-startup-success.

HealthStartupTimeout=

Le temps maximum dont dispose une commande de vérification de santé au démarrage pour s'achever avant d'être marquée comme échouée. Équivalent à l'option Podman --health-startup-timeout.

HealthTimeout=

Le temps maximum autorisé pour terminer la vérification de santé avant qu'un intervalle ne soit considéré comme échoué. Équivalent à l'option Podman --health-timeout.

HostName=

Définit le nom d'hôte disponible à l'intérieur du conteneur. Équivalent à l'option Podman --hostname.

HttpProxy=

Contrôle si les variables d'environnement proxy (http_proxy, https_proxy, ftp_proxy, no_proxy) sont transmises du processus Podman vers le conteneur pendant les extractions et les constructions d'images.

Défini sur true pour activer l'héritage du proxy (comportement Podman par défaut) ou sur false pour le désactiver. Cette option est particulièrement utile sur les systèmes qui nécessitent une configuration proxy pour l'accès à Internet mais qui ne souhaitent pas que les paramètres proxy soient transmis au runtime du conteneur.

Équivalent à l'option Podman --http-proxy.

Image=

L'image à exécuter dans le conteneur. Il est recommandé d'utiliser un nom d'image entièrement qualifié plutôt qu'un nom court, pour des raisons de performance et de robustesse.

Le format du nom est le même que lorsqu'il est passé à podman pull. Il prend donc en charge l'utilisation de :tag ou de digests pour garantir la version spécifique de l'image.

Cas particuliers :

  • Si le nom de l'image se termine par .image, Quadlet utilisera l'image extraite par le fichier .image correspondant, et le service systemd généré contiendra une dépendance sur $name-image.service (ou le nom du service défini dans le fichier .image). Notez que le fichier .image correspondant doit exister.
  • Si le nom de l'image se termine par .build, Quadlet utilisera l'image construite par le fichier .build correspondant, et le service systemd généré contiendra une dépendance sur $name-build.service. Note : le fichier .build correspondant doit exister.

IP=

Spécifie une adresse IPv4 statique pour le conteneur, par exemple 10.88.64.128. Équivalent à l'option Podman --ip.

IP6=

Spécifie une adresse IPv6 statique pour le conteneur, par exemple fd46:db93:aa76:ac37::10. Équivalent à l'option Podman --ip6.

Label=

Définit une ou plusieurs étiquettes OCI sur le conteneur. Le format est une liste d'éléments clé=valeur, similaire à Environment.

Cette clé peut être listée plusieurs fois.

LogDriver=

Définit le pilote de journalisation utilisé par Podman lors de l'exécution du conteneur. Équivalent à l'option Podman --log-driver.

LogOpt=

Définit les options de journalisation (log-opt) utilisées par Podman lors de l'exécution du conteneur. Équivalent à l'option Podman --log-opt. Cette clé peut être listée plusieurs fois.

Mask=

Spécifie les chemins à masquer, séparés par deux points. Mask=/chemin/1:/chemin/2. Un chemin masqué ne peut pas être accédé à l'intérieur du conteneur.

Memory=

Spécifie la quantité de mémoire pour le conteneur.

Mount=

Attache un montage de système de fichiers au conteneur. Ceci est équivalent à l'option Podman --mount, et a généralement la forme type=TYPE,OPTION-SPÉCIFIQUE-AU-TYPE[,...].

Cas particuliers :

  • Pour type=volume, si source se termine par .volume, le volume nommé Podman généré par le fichier .volume correspondant est utilisé.
  • Pour type=image, si source se termine par .image, l'image générée par le fichier .image correspondant est utilisée.

Dans les deux cas, le service systemd généré contiendra une dépendance sur le service généré pour l'unité correspondante. Remarque : le fichier .volume ou .image correspondant doit exister.

Cette clé peut être listée plusieurs fois.

Network=

Spécifie un réseau personnalisé pour le conteneur. Ceci a le même format que l'option --network de podman run. Par exemple, utilisez host pour utiliser le réseau de l'hôte dans le conteneur, ou none pour ne pas configurer le réseau dans le conteneur.

Cas particuliers :

  • Si le nom du réseau se termine par .network, un réseau Podman appelé systemd-$name est utilisé, et le service systemd généré contiendra une dépendance sur $name-network.service. Un tel réseau peut être créé automatiquement en utilisant un fichier Quadlet $name.network. Remarque : le fichier .network correspondant doit exister.
  • Si le nom se termine par .container, le conteneur réutilisera la pile réseau d'un autre conteneur créé par $name.container. Le service systemd généré contiendra une dépendance sur $name.service. Remarque : le fichier .container correspondant doit exister.

Cette clé peut être listée plusieurs fois.

NetworkAlias=

Ajoute un alias propre à la portée du réseau pour le conteneur. Ceci a le même format que l'option --network-alias de podman run. Les alias peuvent être utilisés pour regrouper des conteneurs dans la résolution DNS : par exemple, définir NetworkAlias=web sur plusieurs conteneurs fera qu'une requête DNS pour web résoudra vers tous les conteneurs portant cet alias.

Cette clé peut être listée plusieurs fois.

NoNewPrivileges= (par défaut false)

Si activé, cela empêche les processus du conteneur d'acquérir des privilèges supplémentaires via des mécanismes tels que setuid et les capacités de fichier.

Notify= (par défaut false)

Par défaut, Podman est exécuté de telle sorte que la commande de notification de démarrage de systemd soit gérée par le runtime du conteneur. En d'autres termes, le service est considéré comme démarré lorsque le runtime du conteneur démarre le processus enfant dans le conteneur. Cependant, si l'application du conteneur prend en charge sd_notify,

alors définir Notify sur true passe les détails de notification au conteneur, lui permettant de notifier le démarrage par lui-même.

De plus, définir Notify sur healthy retardera les notifications de démarrage jusqu'à ce que le conteneur soit marqué comme sain, tel que déterminé par les vérifications de santé de Podman. Notez que cela nécessite la configuration d'une vérification de santé du conteneur, voir l'option HealthCmd pour plus d'informations.

PidsLimit=

Ajuste la limite de PIDs du conteneur. Ceci est équivalent à l'option Podman --pids-limit.

Pod=

Spécifie une unité Quadlet .pod à laquelle lier le conteneur. La valeur doit être sous la forme <nom>.pod et l'unité .pod doit exister.

Quadlet ajoutera tous les paramètres nécessaires pour lier le conteneur et le pod, ainsi que leurs services correspondants.

PodmanArgs=

Cette clé contient une liste d'arguments passés directement à la fin de la commande podman run dans le fichier généré (juste avant le nom de l'image sur la ligne de commande). Elle peut être utilisée pour accéder à des fonctionnalités de Podman non prises en charge par le générateur. Comme le générateur n'est pas conscient des interactions inattendues que ces arguments peuvent causer, il n'est pas recommandé d'utiliser cette option.

Le format est une liste d'arguments séparés par des espaces, qui peuvent éventuellement être échappés individuellement pour permettre l'inclusion d'espaces blancs et d'autres caractères de contrôle.

Cette clé peut être listée plusieurs fois.

PublishPort=

Expose un port, ou une plage de ports (par exemple, 50-59), du conteneur à l'hôte. Équivalent à l'option Podman --publish. Le format est similaire aux options Podman, c'est-à-dire sous la forme ip:hostPort:containerPort, ip::containerPort, hostPort:containerPort ou containerPort, où le nombre de ports hôtes et conteneurs doit être le même (dans le cas d'une plage).

Si l'IP est définie sur 0.0.0.0 ou n'est pas définie du tout, le port est lié à toutes les adresses IPv4 sur l'hôte ; utilisez [::] pour IPv6.

Notez que ne pas spécifier de port hôte signifie que Podman en sélectionne automatiquement un, et il peut être différent à chaque invocation du service. Cela rend cette option moins utile. Le port alloué peut être trouvé avec la commande podman port.

Cette clé peut être listée plusieurs fois.

Pull=

Définit la politique de récupération de l'image. Ceci est équivalent à l'option Podman --pull.

ReadOnly= (par défaut : false)

Si activé, rend l'image en lecture seule.

ReadOnlyTmpfs= (par défaut : true)

Si ReadOnly est défini sur true, monte un tmpfs en lecture-écriture sur /dev, /dev/shm, /run, /tmp, et /var/tmp.

ReloadCmd=

Ajoute une ligne ExecReload au Service qui exécute podman exec avec cette commande dans ce conteneur.

Pour exécuter le rechargement, tapez systemctl reload <Service>

Mutuellement exclusif avec ReloadSignal

ReloadSignal=

Ajoute une ligne ExecReload au Service qui exécute podman kill avec ce signal, qui envoie le signal au processus principal du conteneur.

Pour exécuter le rechargement, tapez systemctl reload <Service>

Mutuellement exclusif avec ReloadCmd

Retry=

Nombre de tentatives de récupération de l'image en cas d'erreur HTTP. Équivalent à l'option Podman --retry.

RetryDelay=

Délai entre les tentatives. Équivalent à l'option Podman --retry-delay.

Rootfs=

Le rootfs à utiliser pour le conteneur. Rootfs pointe vers un répertoire sur le système qui contient le contenu à exécuter dans le conteneur. Cette option est en conflit avec l'option Image.

Le format du rootfs est le même que lorsqu'il est passé à podman run --rootfs, il supporte donc également les montages overlay.

Note : Sur les systèmes SELinux, le rootfs doit avoir le bon label, qui est par défaut unconfined_u:object_r:container_file_t:s0.

RunInit= (par défaut : false)

Si activé, le conteneur dispose d'un processus d'initialisation minimal à l'intérieur du conteneur qui transmet les signaux et récupère les processus.

SeccompProfile=

Définit le profil seccomp à utiliser dans le conteneur. Si non défini, le profil par défaut de podman est utilisé. Définir sur le chemin d'un fichier JSON, ou sur unconfined pour désactiver les filtres seccomp.

Secret=

Utilise un secret Podman dans le conteneur, soit sous forme de fichier, soit de variable d'environnement. Ceci est équivalent à l'option Podman --secret et a généralement la forme secret[,opt=opt ...]

SecurityLabelDisable=

Désactive la séparation des labels pour le conteneur.

SecurityLabelFileType=

Définit le type de fichier de label pour les fichiers du conteneur.

SecurityLabelLevel=

Définit le niveau de label du processus pour les processus du conteneur.

SecurityLabelNested=

Permet aux SecurityLabels de fonctionner à l'intérieur du conteneur. Ceci permet la séparation des conteneurs créés à l'intérieur du conteneur.

SecurityLabelType=

Définit le type de label du processus pour les processus du conteneur.

ShmSize=

Taille de /dev/shm.

Ceci est équivalent à l'option Podman --shm-size et a généralement la forme nombre[unité]

StartWithPod=

Démarre le conteneur après la création du pod associé. Par défaut à true.

Si true, le conteneur sera démarré/arrêté/redémarré avec le pod.

Si false, le conteneur ne sera pas démarré lorsque le pod démarrera. Le conteneur sera arrêté avec le pod. Le redémarrage du pod redémarrera également le conteneur tant que le conteneur était également en cours d'exécution auparavant.

Notez que le conteneur peut toujours être démarré manuellement ou via une cible en configurant la section [Install]. Le pod sera démarré si nécessaire dans tous les cas.

StopSignal=

Signal pour arrêter un conteneur. Par défaut : SIGTERM.

Ceci est équivalent à l'option Podman --stop-signal.

StopTimeout=

Secondes d'attente avant d'arrêter de force le conteneur.

Notez que cette valeur doit être inférieure au délai d'attente réel de l'unité systemd pour s'assurer que la commande podman rm n'est pas arrêtée par systemd.

Ceci est équivalent à l'option Podman --stop-timeout.

SubGIDMap=

Exécute le conteneur dans un nouvel espace de noms utilisateur en utilisant le mapping dont le nom figure dans le fichier /etc/subgid. Équivalent à l'option Podman --subgidname.

SubUIDMap=

Exécute le conteneur dans un nouvel espace de noms utilisateur en utilisant le mapping dont le nom figure dans le fichier /etc/subuid. Équivalent à l'option Podman --subuidname.

Sysctl=

Configure les paramètres du noyau en espace de noms pour le conteneur. Le format est Sysctl=nom=valeur.

Il s'agit d'une liste de paramètres du noyau séparés par des espaces. Cette clé peut être listée plusieurs fois.

Par exemple :

Sysctl=net.ipv6.conf.all.disable_ipv6=1 net.ipv6.conf.all.use_tempaddr=1

Timezone= (si non défini, utilise la valeur par défaut configurée par le système)

Le fuseau horaire dans lequel exécuter le conteneur.

Tmpfs=

Monte un tmpfs dans le conteneur. Ceci est équivalent à l'option Podman --tmpfs, et a généralement la forme REPERTOIRE-CONTENEUR[:OPTIONS].

Cette clé peut être listée plusieurs fois.

UIDMap=

Exécute le conteneur dans un nouvel espace de noms utilisateur en utilisant le mapping UID fourni. Équivalent à l'option Podman --uidmap.

Cette clé peut être listée plusieurs fois.

Ulimit=

Options Ulimit. Définit les valeurs ulimits à l'intérieur du conteneur.

Cette clé peut être listée plusieurs fois.

Unmask=

Spécifie les chemins à démasquer séparés par deux-points. unmask=ALL ou /chemin/1:/chemin/2, ou chemins développés par le shell (/proc/*) :

Si défini sur ALL, Podman démasquera tous les chemins qui sont masqués ou rendus en lecture seule par défaut.

Les chemins masqués par défaut sont /proc/acpi, /proc/kcore, /proc/keys, /proc/latency_stats, /proc/sched_debug, /proc/scsi, /proc/timer_list, /proc/timer_stats, /sys/firmware, et /sys/fs/selinux.

Les chemins par défaut en lecture seule sont /proc/asound, /proc/bus, /proc/fs, /proc/irq, /proc/sys, /proc/sysrq-trigger, /sys/fs/cgroup.

User=

L'UID (numérique) sous lequel s'exécuter dans le conteneur. Il n'est pas nécessaire qu'il corresponde à l'UID sur l'hôte, qui peut être modifié avec UserNS, mais si ce dernier n'est pas spécifié, cet UID est également utilisé sur l'hôte.

Note : lorsque User= et Group= sont tous deux spécifiés, ils sont combinés en un seul argument --user USER:GROUP passé à Podman.

Définit le mode d'espace de noms utilisateur pour le conteneur. Ceci est équivalent à l'option Podman --userns et a généralement la forme MODE[:OPTIONS,...].

Volume=

Monte un volume dans le conteneur. Ceci est équivalent à l'option Podman --volume, et a généralement la forme [[VOLUME-SOURCE|REPERTOIRE-HOTE:]REPERTOIRE-CONTENEUR[:OPTIONS]].

Cas spécial :

•
Si VOLUME-SOURCE se termine par .volume, un volume nommé Podman
appelé systemd-$name est utilisé comme source, et le service systemd généré contient une dépendance sur $name-volume.service. Notez que le fichier .volume correspondant doit exister.

Cette clé peut être listée plusieurs fois.

WorkingDir=

Répertoire de travail à l'intérieur du conteneur.

Le répertoire de travail par défaut pour l'exécution des binaires dans un conteneur est le répertoire racine (/). Le développeur de l'image peut définir un répertoire de travail différent avec l'instruction WORKDIR. Cette option remplace le répertoire de travail en utilisant l'option -w.
