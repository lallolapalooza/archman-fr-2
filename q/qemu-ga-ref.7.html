NOM

qemu-ga-ref - Référence du protocole QEMU Guest Agent

Ce manuel décrit les commandes supportées par le protocole QEMU Guest Agent.

Pour trouver un élément particulier, veuillez consulter l'Index QGA <>.

La notation suivante est utilisée dans les exemples :

Exemple :
-> ... texte envoyé par le client (commandes) ...
<- ... texte envoyé par le serveur (réponses aux commandes et événements) ...

Le texte d'exemple est formaté pour la lisibilité. Cependant, dans une utilisation réelle du protocole, il est couramment émis sur une seule ligne.

Veuillez vous référer à la Spécification du protocole de machine QEMU <> pour le format général des commandes, des réponses et des événements.

Commande guest-sync-delimited (Depuis : 1.1)
Renvoie une valeur entière unique, et préfixe la réponse par un octet sentinelle (0xFF) que le client peut rechercher.

Ceci est utilisé par les clients communiquant avec l'agent invité sur le réseau pour s'assurer que le flux est synchronisé et ne contient pas de données obsolètes provenant d'un client précédent. Il doit être émis lors de la connexion initiale, et après tout délai d'attente côté client (y compris les délais d'attente pour recevoir une réponse à cette commande).

Après avoir émis cette requête, toutes les réponses de l'agent invité doivent être ignorées jusqu'à ce que la réponse contenant la valeur entière unique fournie par le client soit renvoyée. La réception de l'octet sentinelle 0xFF doit être traitée comme une indication que l'état du lexer/tokenizer/parser du client doit être vidé/réinitialisé en préparation de la réception fiable de la réponse suivante. Par optimisation, les clients peuvent choisir d'ignorer toutes les données jusqu'à ce qu'une valeur sentinelle soit reçue pour éviter le traitement inutile de données obsolètes.

De même, les clients doivent également précéder cette requête par un octet 0xFF pour s'assurer que l'agent invité vide toutes les données JSON partiellement lues d'une connexion client précédente.

Arguments
•
id (entier) -- entier 64 bits généré aléatoirement
Retour
entier -- L'identifiant entier unique passé par le client
Commande guest-sync (Depuis : 0.15.0)
Renvoie une valeur entière unique

Ceci est utilisé par les clients communiquant avec l'agent invité sur le réseau pour s'assurer que le flux est synchronisé et ne contient pas de données obsolètes provenant d'un client précédent. Toutes les réponses de l'agent invité doivent être ignorées jusqu'à ce que la valeur entière unique fournie soit renvoyée, et il appartient au client de gérer le texte JSON entier ou partiellement livré de manière à ce que cette réponse puisse être obtenue.

Dans les cas où une réponse partielle obsolète a été précédemment reçue par le client, cela ne peut pas toujours être fait de manière fiable. Un scénario particulier est lorsque les réponses de qemu-ga sont alimentées caractère par caractère dans un analyseur JSON. Dans ces situations, utiliser guest-sync-delimited peut être optimal.

Pour les clients qui récupèrent les réponses ligne par ligne et les convertissent en objets JSON, guest-sync devrait suffire, mais notez que dans les cas où le canal est sale, certaines tentatives d'analyse de la réponse peuvent entraîner une erreur de l'analyseur.

De tels clients doivent également précéder cette commande d'un octet 0xFF pour s'assurer que l'agent invité vide toutes les données JSON partiellement lues d'une session précédente.

Arguments
•
id (entier) -- entier 64 bits généré aléatoirement
Retour
entier -- L'identifiant entier unique passé par le client

Commande guest-set-time (Depuis : 1.5)
Définir l'heure de l'invité.

Lorsqu'un invité est mis en pause ou migré vers un fichier puis chargé à partir de ce fichier, le système d'exploitation invité ne sait pas qu'il y a eu un grand écart temporel. En fonction de la durée de cet écart, NTP pourrait ne pas être en mesure de resynchroniser l'invité.

Cette commande tente de définir l'heure système de l'invité à la valeur donnée, puis de définir l'horloge matérielle (RTC) à l'heure système actuelle. Cela facilitera la resynchronisation de l'invité sans attendre NTP. Si aucune heure n'est spécifiée, alors l'heure à définir est lue à partir de la RTC. Cependant, cela peut ne pas être supporté sur toutes les plateformes (par exemple, Windows). Si c'est le cas, il est conseillé aux utilisateurs de toujours passer une valeur.

Arguments
•
time (entier, optionnel) -- temps en nanosecondes, par rapport à l'Époque du 1970-01-01 en UTC.

Commande guest-shutdown (Depuis : 0.15.0)
Initie l'arrêt activé par l'invité. Remarque : il s'agit d'une demande d'arrêt asynchrone, sans garantie de succès de l'arrêt.
Arguments
•
mode (chaîne, optionnel) -- "halt", "powerdown" (par défaut), ou "reboot"

Cette commande NE renvoie PAS de réponse en cas de succès. La condition de succès est indiquée par la sortie de la VM avec un statut de sortie zéro ou, lors de l'exécution avec --no-shutdown, en émettant la commande QMP query-status <#command-QMP-run-state.query-status> pour confirmer que le statut de la VM est "shutdown".

Commande guest-fsfreeze-freeze (Depuis : 0.15.0)
Disponibilité : CONFIG_WIN32 ou CONFIG_FSFREEZE

Synchroniser et geler tous les systèmes de fichiers invités locaux et gelables. Si cette commande a réussi, vous pourrez appeler guest-fsfreeze-thaw plus tard pour les dégeler.

En cas d'erreur, tous les systèmes de fichiers seront décongelés. Si aucun système de fichiers n'est gelé à la suite de cet appel, guest-fsfreeze-status restera sur "thawed" (décongelé) et appeler guest-fsfreeze-thaw ne sera pas nécessaire.

Retour
int -- Nombre de systèmes de fichiers actuellement gelés.

Note :

Sous Windows, la commande est implémentée à l'aide d'une DLL auxiliaire du service de copie de volume (Volume Shadow-copy Service). L'état de gel est limité à 10 secondes par VSS.

Disponibilité : CONFIG_WIN32 ou CONFIG_FSTRIM

Commande guest-suspend-disk (Depuis : 1.1)
Disponibilité : CONFIG_LINUX ou CONFIG_WIN32

Suspend l'invité sur disque.

Cette commande tente de suspendre l'invité en utilisant trois stratégies, dans cet ordre :

  • hibernation systemd
  • pm-utils (via pm-hibernate)
  • écriture manuelle dans sysfs

Cette commande ne renvoie aucune réponse en cas de succès. Il y a une forte probabilité que la commande ait réussi si la VM se termine avec un code de sortie zéro ou, lorsqu'elle est exécutée avec --no-shutdown, en émettant la commande QMP query-status <#command-QMP-run-state.query-status> pour confirmer que le statut de la VM est « shutdown ». Cependant, la VM pourrait également se terminer (ou définir son statut sur « shutdown ») pour d'autres raisons.

Erreurs
•
Si la suspension sur disque n'est pas prise en charge, Unsupported

Note :

Il est fortement recommandé d'émettre la commande guest-sync avant d'envoyer des commandes lorsque l'invité reprend.
Commande guest-suspend-ram (Depuis : 1.1)
Disponibilité : CONFIG_LINUX ou CONFIG_WIN32

Suspend l'invité en RAM.

Cette commande tente de suspendre l'invité en utilisant trois stratégies, dans cet ordre :

  • hibernation systemd
  • pm-utils (via pm-hibernate)
  • écriture manuelle dans sysfs

IMPORTANT : guest-suspend-ram nécessite un support de réveil fonctionnel dans QEMU. Vous devriez vérifier que la commande QMP query-current-machine <#command-QMP-machine.query-current-machine> renvoie wakeup-suspend-support: true avant d'émettre cette commande. Ne pas le faire peut entraîner un invité suspendu que QEMU ne pourra pas réveiller, forçant l'utilisateur à réinitialiser l'invité pour le ramener.

Cette commande ne renvoie aucune réponse en cas de succès. Il existe deux options pour vérifier le succès :

1.
Attendre l'événement QMP SUSPEND <#event-QMP-run-state.SUSPEND> de QEMU
2.
Émettre la commande QMP query-status <#command-QMP-run-state.query-status> pour confirmer que le statut de la VM est « suspended »
Erreurs
•
Si la suspension en RAM n'est pas prise en charge, Unsupported

Note :

Il est fortement recommandé d'émettre la commande guest-sync avant d'envoyer des commandes lorsque l'invité reprend.

Commande guest-get-vcpus (Depuis : 1.5)
Disponibilité : CONFIG_LINUX ou CONFIG_WIN32

Ceci est une opération en lecture seule.

Commande guest-set-vcpus (Depuis : 1.5)
Disponibilité : CONFIG_LINUX

Tente de reconfigurer (actuellement : activer/désactiver) les processeurs logiques à l'intérieur de l'invité.

Arguments
•
vcpus ([GuestLogicalProcessor]) -- Les processeurs logiques à reconfigurer. Cette liste est traitée nœud par nœud, dans l'ordre. Dans chaque nœud, logical-id est utilisé pour rechercher le VCPU invité, pour lequel online spécifie l'état demandé. L'ensemble des logical-id distincts n'est requis que pour être un sous-ensemble des identifiants pris en charge par l'invité. Il n'y a aucune restriction sur la longueur de la liste ni sur la répétition du même logical-id (avec éventuellement un champ online différent). Idéalement, la liste d'entrée devrait décrire un sous-ensemble modifié de la valeur de retour de guest-get-vcpus.
Retour
int --

La longueur de la sous-liste initiale qui a été traitée avec succès. L'agent invité maximise cette valeur. Cas possibles :

  • 0 : si la liste vcpus était vide à l'entrée. L'état de l'invité n'a pas été modifié. Sinon,
  • < length(vcpus) : plus de zéro nœuds initiaux ont été traités, mais pas la totalité de la liste vcpus. L'état de l'invité a été modifié en conséquence. Pour récupérer l'erreur (en supposant qu'elle persiste), répétez l'appel en supprimant la sous-liste initiale traitée avec succès. Sinon,
  • length(vcpus) : appel réussi.
Erreurs
•
Si la reconfiguration du premier nœud dans vcpus a échoué. L'état de l'invité n'a pas été modifié.

Command guest-set-user-password (Depuis : 2.3)
Disponibilité: CONFIG_WIN32 ou CONFIG_LINUX ou CONFIG_FREEBSD.INDENT 7.0
Arguments
  • username (string) -- le compte utilisateur dont le mot de passe doit être modifié
  • password (string) -- la nouvelle chaîne de mot de passe, encodée en base64
  • crypted (boolean) -- true si le mot de passe est déjà crypté, false si brut

Si le drapeau crypted est vrai, il incombe à l'appelant de s'assurer que le schéma de chiffrement crypt() correct est utilisé. Cette commande ne tente pas d'interpréter ni de rapporter le schéma de chiffrement. Reportez-vous à la documentation du système d'exploitation invité en question pour déterminer ce qui est pris en charge.

Tous les systèmes d'exploitation invités ne prendront pas en charge l'utilisation du drapeau crypted, car ils peuvent nécessiter le mot de passe en clair

Le paramètre password doit toujours être encodé en base64 avant la transmission, même s'il est déjà crypté, pour garantir qu'il est sûr pour les 8 bits lorsqu'il est transmis en tant que JSON.

Command guest-set-memory-blocks (Depuis : 2.3)
