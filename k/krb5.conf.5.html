NOM

krb5.conf - Fichier de configuration Kerberos

Le fichier krb5.conf contient des informations de configuration Kerberos, y compris les emplacements des KDC et des serveurs d'administration pour les domaines Kerberos d'intérêt, les valeurs par défaut pour le domaine actuel et pour les applications Kerberos, ainsi que les correspondances entre noms d'hôtes et domaines Kerberos. Normalement, vous devriez installer votre fichier krb5.conf dans le répertoire /etc. Vous pouvez remplacer l'emplacement par défaut en définissant la variable d'environnement KRB5_CONFIG. Plusieurs noms de fichiers séparés par des deux-points peuvent être spécifiés dans KRB5_CONFIG ; tous les fichiers présents seront lus. À partir de la version 1.14, des noms de répertoires peuvent également être spécifiés dans KRB5_CONFIG ; tous les fichiers contenus dans le répertoire dont les noms sont constitués uniquement de caractères alphanumériques, de tirets ou de traits de soulignement seront lus.

STRUCTURE

Le fichier krb5.conf est structuré dans le style d'un fichier INI Windows. Les lignes commençant par '#' ou ';' (éventuellement après des espaces blancs initiaux) sont ignorées en tant que commentaires. Les sections sont précédées par le nom de la section, entre crochets. Chaque section peut contenir zéro ou plusieurs relations, sous la forme :

foo = bar

ou :

fubar = {
    foo = bar
    baz = quux
}

Placer un '*' après la parenthèse fermante d'un nom de section indique que la section est finalisée, ce qui signifie que si la même section apparaît dans un fichier ultérieur spécifié dans KRB5_CONFIG, elle sera ignorée. Une sous-section peut être marquée comme finalisée en plaçant un '*' après le nom de la balise ou l'accolade fermante.

Le fichier krb5.conf peut inclure d'autres fichiers en utilisant l'une des directives suivantes au début d'une ligne :

include FILENAME
includedir DIRNAME

FILENAME ou DIRNAME doit être un chemin absolu. Le fichier ou répertoire nommé doit exister et être lisible. L'inclusion d'un répertoire inclut tous les fichiers contenus dans le répertoire dont les noms sont constitués uniquement de caractères alphanumériques, de tirets ou de traits de soulignement. À partir de la version 1.15, les fichiers se terminant par ".conf" sont également inclus, à moins que le nom ne commence par ".". Les fichiers de profil inclus sont syntaxiquement indépendants de leurs parents, donc chaque fichier inclus doit commencer par un en-tête de section. À partir de la version 1.17, les fichiers sont lus par ordre alphanumérique ; dans les versions précédentes, ils peuvent être lus dans n'importe quel ordre.

Le fichier krb5.conf peut spécifier que la configuration doit être obtenue à partir d'un module chargeable, plutôt que du fichier lui-même, en utilisant la directive suivante au début d'une ligne avant tout en-tête de section :

module MODULEPATH:RESIDUAL

MODULEPATH peut être relatif au chemin de bibliothèque de l'installation krb5, ou il peut être un chemin absolu. RESIDUAL est transmis au module au moment de l'initialisation. Si krb5.conf utilise une directive module, kdc.conf(5) devrait également en utiliser une si elle existe.

SECTIONS

Le fichier krb5.conf peut contenir les sections suivantes :

[libdefaults] Paramètres utilisés par la bibliothèque Kerberos V5
[realms] Informations de contact et paramètres spécifiques au domaine
[domain_realm] Mappe les noms d'hôtes de serveur aux domaines Kerberos
[capaths] Chemins d'authentification pour les relations inter-domaines non hiérarchiques
[appdefaults] Paramètres utilisés par certaines applications Kerberos V5
[plugins] Contrôle l'enregistrement des modules plugins

De plus, krb5.conf peut inclure n'importe laquelle des relations décrites dans kdc.conf(5), mais ce n'est pas une pratique recommandée.

[libdefaults]

La section libdefaults peut contenir les relations suivantes :

allow_des3
Permet au KDC d'émettre des tickets avec des clés de session des3-cbc-sha1. Dans les futures versions, ce drapeau permettra l'utilisation de des3-cbc-sha1 à tous égards. La valeur par défaut pour cette balise est fausse. (Ajouté dans la version 1.21.)
allow_rc4
Permet au KDC d'émettre des tickets avec des clés de session arcfour-hmac. Dans les futures versions, ce drapeau permettra l'utilisation de arcfour-hmac à tous égards. La valeur par défaut pour cette balise est fausse. (Ajouté dans la version 1.21.)
allow_weak_crypto
Si ce drapeau est défini sur faux, alors les types de chiffrement faibles (comme noté dans Encryption_types de kdc.conf(5)) seront filtrés des listes default_tgs_enctypes, default_tkt_enctypes, et permitted_enctypes. La valeur par défaut pour cette balise est fausse.
canonicalize
Si ce drapeau est défini sur vrai, les demandes de tickets initiales au KDC demanderont la canonicalisation du nom de principal client, et les réponses avec des principaux clients différents du principal demandé seront acceptées. La valeur par défaut est fausse.
ccache_type
Ce paramètre détermine le format des types de cache de crédentials créés par kinit(1) ou d'autres programmes. La valeur par défaut est 4, ce qui représente le format le plus récent. Des valeurs plus petites peuvent être utilisées pour la compatibilité avec de très anciennes implémentations de Kerberos qui interagissent avec les caches de crédentials sur le même hôte.
clockskew
Définit la quantité maximale acceptable de décalage d'horloge en secondes que la bibliothèque tolérera avant de considérer qu'un message Kerberos est invalide. La valeur par défaut est 300 secondes, soit cinq minutes.

Le réglage de clockskew est également utilisé lors de l'évaluation des temps de début et d'expiration des tickets. Par exemple, les tickets qui ont atteint leur temps d'expiration peuvent toujours être utilisés (et renouvelés s'il s'agit de tickets renouvelables) s'ils ont été expirés pour une durée plus courte que le réglage clockskew.

default_ccache_name
Cette relation spécifie le nom du cache de crédentials par défaut. La valeur par défaut est FILE:/tmp/krb5cc_%{uid}. Cette relation est sujette à l'expansion des paramètres (voir ci-dessous). Nouveau dans la version 1.11.
default_client_keytab_name
Cette relation spécifie le nom du keytab par défaut pour l'obtention des crédentials client. La valeur par défaut est FILE:/var/lib/krb5/user/%{euid}/client.keytab. Cette relation est sujette à l'expansion des paramètres (voir ci-dessous). Nouveau dans la version 1.11.
default_keytab_name
Cette relation spécifie le nom du keytab par défaut à utiliser par les serveurs d'application tels que sshd. La valeur par défaut est FILE:/etc/krb5.keytab. Cette relation est sujette à l'expansion des paramètres (voir ci-dessous).
default_rcache_name
Cette relation spécifie le nom du cache de rejeu par défaut. La valeur par défaut est dfl:. Cette relation est sujette à l'expansion des paramètres (voir ci-dessous). Nouveau dans la version 1.18.
default_realm
Identifie le domaine Kerberos par défaut pour le client. Définissez sa valeur sur votre domaine Kerberos. Si cette valeur n'est pas définie, alors un domaine doit être spécifié avec chaque principal Kerberos lors de l'appel de programmes tels que kinit(1).

La section [domain_realm] fournit une transTraduction de la mise en page des hôtes en domaines Kerberos. Chaque étiquette est un nom de domaine, fournissant la traduction pour ce domaine et tous les sous-domaines. Si l'étiquette commence par un point (.) alors elle ne s'applique qu'aux sous-domaines. Le domaine Kerberos peut être identifié soit dans la section realms, soit à l'aide des enregistrements DNS SRV. Les noms d'étiquettes doivent être en minuscules. Par exemple :

[domain_realm]
    crash.mit.edu = TEST.ATHENA.MIT.EDU
    .dev.mit.edu = TEST.ATHENA.MIT.EDU
    mit.edu = ATHENA.MIT.EDU

mappe l'hôte avec le nom crash.mit.edu dans le domaine TEST.ATHENA.MIT.EDU. La deuxième entrée mappe tous les hôtes sous le domaine dev.mit.edu dans le domaine TEST.ATHENA.MIT.EDU, mais pas l'hôte avec le nom dev.mit.edu. Cet hôte correspond à la troisième entrée, qui mappe l'hôte mit.edu et tous les hôtes sous le domaine mit.edu qui ne correspondent pas à une règle précédente dans le domaine ATHENA.MIT.EDU.

Si aucune entrée de traduction ne s'applique à un nom d'hôte utilisé pour un principal de service lors d'une demande de ticket de service, la bibliothèque essaiera d'obtenir une référence vers le domaine approprié auprès du KDC du domaine client. Si cela échoue, le domaine de l'hôte est considéré comme la partie domaine du nom d'hôte convertie en majuscules, sauf si le paramètre realm_try_domains dans [libdefaults] provoque l'utilisation d'un domaine parent différent.

[capaths]

Afin d'effectuer une authentification inter-domaines directe (non hiérarchique), une configuration est nécessaire pour déterminer les chemins d'authentification entre les domaines.

Un client utilisera cette section pour trouver le chemin d'authentification entre son domaine et le domaine du serveur. Le serveur utilisera cette section pour vérifier le chemin d'authentification utilisé par le client, en examinant le champ transited du ticket reçu.

Il y a une étiquette pour chaque domaine client participant, et chaque étiquette a des sous-étiquettes pour chacun des domaines serveurs. La valeur des sous-étiquettes est un domaine intermédiaire qui peut participer à l'authentification inter-domaines. Les sous-étiquettes peuvent être répétées s'il y a plus d'un domaine intermédiaire. Une valeur de "." signifie que les deux domaines partagent directement des clés, et qu'aucun domaine intermédiaire ne devrait être autorisé à participer.

Seules les entrées qui seront nécessaires sur le client ou le serveur doivent être présentes. Un client a besoin d'une étiquette pour son domaine local avec des sous-étiquettes pour tous les domaines des serveurs auxquels il devra s'authentifier. Un serveur a besoin d'une étiquette pour chaque domaine des clients qu'il servira, avec une sous-étiquette du domaine serveur.

Par exemple, ANL.GOV, PNL.GOV et NERSC.GOV souhaitent tous utiliser le domaine ES.NET comme domaine intermédiaire. ANL a un sous-domaine TEST.ANL.GOV qui s'authentifiera avec NERSC.GOV mais pas avec PNL.GOV. La section [capaths] pour les systèmes ANL.GOV ressemblerait à ceci :

[capaths]
    ANL.GOV = {
        TEST.ANL.GOV = .
        PNL.GOV = ES.NET
        NERSC.GOV = ES.NET
        ES.NET = .
    }
    TEST.ANL.GOV = {
        ANL.GOV = .
    }
    PNL.GOV = {
        ANL.GOV = ES.NET
    }
    NERSC.GOV = {
        ANL.GOV = ES.NET
    }
    ES.NET = {
        ANL.GOV = .
    }

La section [capaths] du fichier de configuration utilisé sur les systèmes NERSC.GOV ressemblerait à ceci :

[capaths]
    NERSC.GOV = {
        ANL.GOV = ES.NET
        TEST.ANL.GOV = ES.NET
        TEST.ANL.GOV = ANL.GOV
        PNL.GOV = ES.NET
        ES.NET = .
    }
    ANL.GOV = {
        NERSC.GOV = ES.NET
    }
    PNL.GOV = {
        NERSC.GOV = ES.NET
    }
    ES.NET = {
        NERSC.GOV = .
    }
    TEST.ANL.GOV = {
        NERSC.GOV = ANL.GOV
        NERSC.GOV = ES.NET
    }

Lorsqu'une sous-étiquette est utilisée plus d'une fois dans une étiquette, les clients utilisent l'ordre des valeurs pour déterminer le chemin. L'ordre des valeurs n'a pas d'importance pour les serveurs.

[appdefaults]

Chaque étiquette dans la section [appdefaults] nomme une application Kerberos V5 ou une option utilisée par certaines applications Kerberos V5. La valeur de l'étiquette définit les comportements par défaut pour cette application.

Par exemple :

[appdefaults]
    telnet = {
        ATHENA.MIT.EDU = {
            option1 = false
        }
    }
    telnet = {
        option1 = true
        option2 = true
    }
    ATHENA.MIT.EDU = {
        option2 = false
    }
    option2 = true

Les quatre façons ci-dessus de spécifier la valeur d'une option sont présentées par ordre de priorité décroissante. Dans cet exemple, si telnet s'exécute dans le domaine EXAMPLE.COM, il devrait, par défaut, avoir option1 et option2 définis sur true. Cependant, un programme telnet dans le domaine ATHENA.MIT.EDU devrait avoir option1 défini sur false et option2 sur true. Tous les autres programmes dans ATHENA.MIT.EDU devraient avoir option2 défini sur false par défaut. Tous les programmes s'exécutant dans d'autres domaines devraient avoir option2 défini sur true.

La liste des options spécifiables pour chaque application se trouve dans les pages man de cette application. Les valeurs par défaut de l'application spécifiées ici sont remplacées par celles spécifiées dans la section realms.

[plugins]

  • interface pwqual
  • interface kadm5_hook
  • interfaces clpreauth et kdcpreauth

Les étiquettes de la section [plugins] peuvent être utilisées pour enregistrer des modules de plugin dynamiques et pour activer ou désactiver des modules. Toutes les interfaces pluggables de krb5 n'utilisent pas la section [plugins] ; celles qui le font sont documentées ici.

Nouveau dans la version 1.9.

Chaque interface pluggable correspond à une sous-section de [plugins]. Toutes les sous-sections prennent en charge les mêmes étiquettes :

disable
Cette étiquette peut avoir plusieurs valeurs. S'il y a des valeurs pour cette étiquette, alors les modules nommés seront désactivés pour l'interface pluggable.
enable_only
Cette étiquette peut avoir plusieurs valeurs. S'il y a des valeurs pour cette étiquette, alors seuls les modules nommés seront activés pour l'interface pluggable.
module
Cette étiquette peut avoir plusieurs valeurs. Chaque valeur est une chaîne de la forme nom_module:chemin_accès, ce qui provoque l'enregistrement de l'objet partagé situé à chemin_accès comme module dynamique nommé nom_module pour l'interface pluggable. Si chemin_accès n'est pas un chemin absolu, il sera traité comme relatif au paramètre plugin_base_dir de [libdefaults].

Pour les interfaces pluggables où l'ordre des modules est important, les modules enregistrés avec une étiquette module viennent normalement en premier, dans l'ordre où ils sont enregistrés, suivis par les modules intégrés dans l'ordre où ils sont documentés ci-dessous. Si des étiquettes enable_only sont utilisées, l'ordre de ces étiquettes remplace l'ordre normal des modules.

Les sous-sections suivantes sont actuellement prises en charge dans la section [plugins] :

ccselect interface

La sous-section ccselect contrôle les modules de sélection de cache de crédentiels au sein d'une collection de caches. En plus de tout module dynamique enregistré, les modules intégrés suivants existent (et peuvent être désactivés avec l'étiquette disable) :

k5identity
Utilise un fichier .k5identity dans le répertoire personnel de l'utilisateur pour sélectionner un principal client
realm
Utilise le domaine du service pour deviner un cache approprié dans la collection
hostname
Si le principal du service est basé sur l'hôte, utilise le nom d'hôte du service pour deviner un cache approprié dans la collection

pwqual interface

La sous-section pwqual contrôle les modules pour l'interface de qualité des mots de passe, qui est utilisée pour rejeter les mots de passe faibles lors des changements de mot de passe. Les modules intégrés suivants existent pour cette interface :

dict
Vérifie par rapport au fichier du dictionnaire du domaine
empty
Rejette les mots de passe vides
hesiod
Vérifie par rapport aux informations utilisateur stockées dans Hesiod (uniquement si Kerberos a été compilé avec le support Hesiod)
princ
Vérifie par rapport aux composants du nom du principal

kadm5_hook interface

L'interface kadm5_hook fournit aux plugins des informations sur la création de principaux, la modification, les changements de mot de passe et la suppression. Cette interface peut être utilisée pour écrire un plugin afin de synchroniser MIT Kerberos avec une autre base de données telle qu'Active Directory. Aucun plugin n'est intégré pour cette interface.

kadm5_auth interface

La section kadm5_auth (introduite dans la version 1.16) contrôle les modules pour l'interface d'autorisation kadmin, qui détermine si un principal client est autorisé à effectuer une opération kadmin. Les modules intégrés suivants existent pour cette interface :

acl
Ce module lit le fichier kadm5.acl(5) et autorise les opérations qui sont permises selon les règles du fichier.
self
Ce module autorise les opérations de libre-service, y compris les changements de mot de passe, la création de nouvelles clés aléatoires, la récupération de l'enregistrement du principal du client ou des attributs de chaîne, et la récupération de l'enregistrement de politique associé au principal client.

clpreauth et kdcpreauth interfaces

Les interfaces clpreauth et kdcpreauth permettent aux modules de plugin de fournir c

lient et les mécanismes de pré-authentification KDC. Les modules intégrés suivants existent pour ces interfaces :

pkinit
Ce module implémente le mécanisme de pré-authentification PKINIT.
encrypted_challenge
Ce module implémente le facteur FAST de défi chiffré.
encrypted_timestamp
Ce module implémente le mécanisme d'horodatage chiffré.

Interface hostrealm

La section hostrealm (introduite dans la version 1.12) contrôle les modules pour l'interface hôte-vers-domaine, ce qui affecte la correspondance locale des noms d'hôtes aux noms de domaines et le choix du domaine par défaut. Les modules intégrés suivants existent pour cette interface :

profile
Ce module consulte la section [domain_realm] du profil pour les correspondances autoritaires entre hôtes et domaines, et la variable default_realm pour le domaine par défaut.
dns
Ce module recherche les enregistrements DNS pour les correspondances de secours entre hôtes et domaines, ainsi que le domaine par défaut. Il ne fonctionne que si la variable dns_lookup_realm est définie sur true.
domain
Ce module applique des heuristiques pour les correspondances de secours entre hôtes et domaines. Il implémente la variable realm_try_domains et utilise le domaine parent en majuscules du nom d'hôte si cela ne produit pas de résultat.

Interface localauth

La section localauth (introduite dans la version 1.12) contrôle les modules pour l'interface d'autorisation locale, qui affecte la relation entre les principaux Kerberos et les comptes système locaux. Les modules intégrés suivants existent pour cette interface :

default
Ce module implémente le type DEFAULT pour les valeurs auth_to_local.
rule
Ce module implémente le type RULE pour les valeurs auth_to_local.
names
Ce module recherche une correspondance auth_to_local_names pour le nom du principal.
auth_to_local
Ce module traite les valeurs auth_to_local dans la section du domaine par défaut et applique la méthode par défaut s'il n'y a pas de valeurs auth_to_local.
k5login
Ce module autorise un principal à un compte local conformément au fichier .k5login(5) du compte.
an2ln
Ce module autorise un principal à un compte local si le nom du principal correspond au nom du compte local.

Interface certauth

La section certauth (introduite dans la version 1.16) contrôle les modules pour l'interface d'autorisation de certificats, qui détermine si un certificat est autorisé à pré-authentifier un utilisateur via PKINIT. Les modules intégrés suivants existent pour cette interface :

pkinit_san
Ce module autorise le certificat s'il contient un nom alternatif du sujet (SAN) PKINIT pour le principal client demandé, ou un SAN UPN Microsoft correspondant au principal si pkinit_allow_upn est défini sur true pour le domaine.
pkinit_eku
Ce module rejette le certificat s'il ne contient pas un attribut d'utilisation étendue de clé (EKU) cohérent avec la valeur pkinit_eku_checking pour le domaine.
dbmatch
Ce module autorise ou rejette le certificat selon qu'il correspond à l'attribut de chaîne pkinit_cert_match sur le principal client, si cet attribut est présent.

Spécification des informations d'identité PKINIT

La syntaxe pour spécifier les informations d'identité, de confiance et de révocation de clé publique pour PKINIT est la suivante :

FILE:nom_fichier[,nom_fichier_clé]
Cette option a un comportement dépendant du contexte.

Dans pkinit_identity ou pkinit_identities, nom_fichier spécifie le nom d'un fichier au format PEM contenant le certificat de l'utilisateur. Si nom_fichier_clé n'est pas spécifié, la clé privée de l'utilisateur est censée se trouver également dans nom_fichier. Sinon, nom_fichier_clé est le nom du fichier contenant la clé privée.

Dans pkinit_anchors ou pkinit_pool, nom_fichier est supposé être le nom d'un fichier de bundle d'autorité de certification (CA) de style OpenSSL.

DIR:nom_répertoire
Cette option a un comportement dépendant du contexte.

Dans pkinit_identity ou pkinit_identities, nom_répertoire spécifie un répertoire contenant des fichiers nommés *.crt et *.key où la première partie du nom de fichier est la même pour les paires correspondantes de fichiers de certificat et de clé privée. Lorsqu'un fichier se terminant par .crt est trouvé, un fichier correspondant se terminant par .key est supposé contenir la clé privée. Si aucun fichier de ce type n'est trouvé, le certificat du fichier .crt n'est pas utilisé.

Dans pkinit_anchors ou pkinit_pool, nom_répertoire est supposé être un répertoire de CA haché de style OpenSSL où chaque certificat de CA est stocké dans un fichier nommé hash-of-ca-cert.#. Cette infrastructure est encouragée, mais tous les fichiers du répertoire seront examinés et s'ils contiennent des certificats (au format PEM), ils seront utilisés.

Dans pkinit_revoke, nom_répertoire est supposé être un répertoire de CA haché de style OpenSSL où chaque liste de révocation est stockée dans un fichier nommé hash-of-ca-cert.r#. Cette infrastructure est encouragée, mais tous les fichiers du répertoire seront examinés et s'ils contiennent une liste de révocation (au format PEM), ils seront utilisés.

PKCS12:nom_fichier
nom_fichier est le nom d'un fichier au format PKCS #12, contenant le certificat et la clé privée de l'utilisateur.
PKCS11:[module_name=]nom_module[:slotid=id_slot][:token=label_token][:certid=id_cert][:certlabel=label_cert]
Tous les mots-clés/valeurs sont facultatifs. nom_module spécifie l'emplacement d'une bibliothèque implémentant PKCS #11. Si une valeur est rencontrée sans mot-clé, elle est supposée être le nom_module. Si aucun nom de module n'est spécifié, la valeur par défaut est opensc-pkcs11.so. slotid= et/ou token= peuvent être spécifiés pour forcer l'utilisation d'un lecteur de carte à puce ou d'un token particulier s'il y en a plus d'un disponible. certid= et/ou certlabel= peuvent être spécifiés pour forcer la sélection d'un certificat particulier sur l'appareil. Voir l'option de configuration pkinit_cert_match pour d'autres moyens de sélectionner un certificat particulier à utiliser pour PKINIT.
ENV:var_env
var_env spécifie le nom d'une variable d'environnement qui a été définie avec une valeur conforme à l'une des valeurs précédentes. Par exemple, ENV:X509_PROXY, où la variable d'environnement X509_PROXY a été définie sur FILE:/tmp/my_proxy.pem.

Options krb5.conf PKINIT

pkinit_anchors
Spécifie l'emplacement des certificats racines (ancres) approuvés que le client fait confiance pour signer les certificats KDC. Cette option peut être spécifiée plusieurs fois. Ces valeurs du fichier de configuration ne sont pas utilisées si l'utilisateur spécifie X509_anchors sur la ligne de commande.
pkinit_cert_match
Spécifie les règles de correspondance auxquelles le certificat client doit correspondre avant d'être utilisé pour tenter l'authentification PKINIT. Si un utilisateur dispose de plusieurs certificats disponibles (sur une carte à puce, ou via d'autres supports), un seul certificat doit être choisi avant de tenter l'authentification PKINIT. Cette option peut être spécifiée plusieurs fois. Tous les certificats disponibles sont vérifiés par rapport à chaque règle dans l'ordre jusqu'à ce qu'une correspondance d'un seul certificat soit trouvée.

Les chaînes de comparaison du sujet et de l'émetteur sont les représentations de chaîne RFC 2253 des valeurs DN du sujet et DN de l'émetteur du certificat.

La syntaxe des règles de correspondance est la suivante :

PKINIT OPTIONS

The following options are available for the pkinit component, which is used for certificate-based authentication.

pkinit_cert_match
This option specifies a set of criteria for matching a client certificate. The criteria are evaluated using a logical OR if no relation operator is specified, or using the specified relation operator. The default is &&.
[relation-operator]component-rule ...

where:

relation-operator
peut être soit &&, signifiant que toutes les règles de composant doivent correspondre, soit ||, signifiant qu'une seule règle de composant doit correspondre. La valeur par défaut est &&.
component-rule
peut être l'une des suivantes. Notez qu'il n'y a pas de ponctuation ou d'espace blanc entre les règles de composant.
<SUBJECT>regular-expression
<ISSUER>regular-expression
<SAN>regular-expression
<EKU>extended-key-usage-list
<KU>key-usage-list

extended-key-usage-list est une liste de valeurs Extended Key Usage requises, séparées par des virgules. Toutes les valeurs de la liste doivent être présentes dans le certificat. Les valeurs Extended Key Usage peuvent être :

  • pkinit
  • msScLogin
  • clientAuth
  • emailProtection

key-usage-list est une liste de valeurs Key Usage requises, séparées par des virgules. Toutes les valeurs de la liste doivent être présentes dans le certificat. Les valeurs Key Usage peuvent être :

  • digitalSignature
  • keyEncipherment

Exemples :

pkinit_cert_match = ||<SUBJECT>.*DoE.*<SAN>.*@EXAMPLE.COM
pkinit_cert_match = &&<EKU>msScLogin,clientAuth<ISSUER>.*DoE.*
pkinit_cert_match = <EKU>msScLogin,clientAuth<KU>digitalSignature
pkinit_eku_checking
Cette option spécifie quelle valeur Extended Key Usage le certificat KDC présenté au client doit contenir. (Notez que si le certificat KDC possède le SubjectAlternativeName pkinit encodé sous le nom Kerberos TGS, la vérification EKU n'est pas nécessaire car l'AC émettrice l'a certifié comme certificat KDC.) Les valeurs reconnues dans le fichier krb5.conf sont :
kpKDC
C'est la valeur par défaut et elle spécifie que le KDC doit avoir l'EKU id-pkinit-KPKdc tel que défini dans RFC 4556.
kpServerAuth
Si kpServerAuth est spécifié, un certificat KDC avec l'EKU id-kp-serverAuth sera accepté. Cette valeur d'utilisation de clé est utilisée dans la plupart des certificats serveur émis commercialement.
none
Si none est spécifié, alors le certificat KDC ne sera pas vérifié pour s'assurer qu'il a un EKU acceptable. L'utilisation de cette option n'est pas recommandée.
pkinit_dh_min_bits
Spécifie la taille de la clé Diffie-Hellman que le client tentera d'utiliser. Les valeurs acceptables sont 1024, 2048 et 4096. La valeur par défaut est 2048.
pkinit_identities
Spécifie l'emplacement (ou les emplacements) à utiliser pour trouver les informations d'identité X.509 de l'utilisateur. Si cette option est spécifiée plusieurs fois, chaque valeur est tentée dans l'ordre jusqu'à ce que des certificats soient trouvés. Notez que ces valeurs ne sont pas utilisées si l'utilisateur spécifie X509_user_identity sur la ligne de commande.
pkinit_kdc_hostname
La présence de cette option indique que le client est prêt à accepter un certificat KDC avec un SAN dNSName (Subject Alternative Name) plutôt que d'exiger le id-pkinit-san tel que défini dans RFC 4556. Cette option peut être spécifiée plusieurs fois. Sa valeur doit contenir le nom d'hôte acceptable pour le KDC (tel qu'il est contenu dans son certificat).
pkinit_pool
Spécifie l'emplacement des certificats intermédiaires qui peuvent être utilisés par le client pour compléter la chaîne de confiance entre un certificat KDC et une ancre de confiance. Cette option peut être spécifiée plusieurs fois.
pkinit_require_crl_checking
Le processus de vérification de certificat par défaut vérifiera toujours les informations de révocation disponibles pour voir si un certificat a été révoqué. Si une correspondance est trouvée pour le certificat dans une CRL, la vérification échoue. Si le certificat en cours de vérification n'est pas répertorié dans une CRL, ou s'il n'y a pas de CRL présente pour son AC émettrice, et que pkinit_require_crl_checking est faux, alors la vérification réussit.

Cependant, si pkinit_require_crl_checking est vrai et qu'aucune information CRL n'est disponible pour l'AC émettrice, alors la vérification échoue.

pkinit_require_crl_checking doit être défini sur vrai si la politique exige que des CRL à jour soient présentes pour chaque CA.

pkinit_revoke
Spécifie l'emplacement des informations de liste de révocation de certificats (CRL) à utiliser par le client lors de la vérification de la validité du certificat KDC présenté. Cette option peut être spécifiée plusieurs fois.

FICHIER KRB5.CONF D'EXEMPLE

Voici un exemple de fichier krb5.conf générique :

[libdefaults]
    default_realm = ATHENA.MIT.EDU
    dns_lookup_kdc = true
    dns_lookup_realm = false
[realms]
    ATHENA.MIT.EDU = {
        kdc = kerberos.mit.edu
        kdc = kerberos-1.mit.edu
        kdc = kerberos-2.mit.edu
        admin_server = kerberos.mit.edu
        primary_kdc = kerberos.mit.edu
    }
    EXAMPLE.COM = {
        kdc = kerberos.example.com
        kdc = kerberos-1.example.com
        admin_server = kerberos.example.com
    }
[domain_realm]
    mit.edu = ATHENA.MIT.EDU
[capaths]
    ATHENA.MIT.EDU = {
           EXAMPLE.COM = .
    }
    EXAMPLE.COM = {
           ATHENA.MIT.EDU = .
    }
