DESCRIPTIO

N

La commande keytool est un utilitaire de gestion des clés et des certificats. Elle permet aux utilisateurs d'administrer leurs propres paires de clés publique/privée et certificats associés pour une utilisation en auto-authentification (où un utilisateur s'authentifie auprès d'autres utilisateurs et services) ou pour des services d'intégrité et d'authentification des données, en utilisant des signatures numériques. La commande keytool permet également aux utilisateurs de mettre en cache les clés publiques (sous forme de certificats) de leurs pairs avec lesquels ils

communiquent.

Un certificat est une déclaration signée numériquement provenant d'une entité (personne, entreprise, etc.), qui indique que la clé publique (et certaines autres informations) d'une autre entité a une valeur particulière. Lorsque des données sont signées numériquement, la signature peut être vérifiée pour contrôler l'intégrité et l'authenticité des données. L'intégrité signifie que les données n'ont pas été modifiées ou falsifiées, et l'authenticité signifie que les données proviennent de l'individu qui prétend les avoir créées et

signées.

La commande keytool permet également aux utilisateurs d'administrer les clés secrètes et les phrases de passe utilisées dans le chiffrement et le déchiffrement symétriques (Data Encryption Standard). Elle peut aussi afficher d'autres informations relatives à la

sécurité.

La commande keytool stocke les clés et les certificats dans un magasin de clés (keystore)

.

La commande keytool utilise les propriétés de sécurité jdk.certpath.disabledAlgorithms et jdk.security.legacyAlgorithms pour déterminer quels algorithmes sont consi

dérés comme présentant un risque de sécurité. Elle émet des avertissements lorsque des algorithmes désactivés ou hérités sont utilisés. Les propriétés de sécurité jdk.
certpath.disabledAlgorithms et jdk.security.legacyAlgorithms sont définies dans le fichier java.security (situé dans le répertoire $JAVA_HOME/conf/security du JDK).

Utilisez la commande -gencert pour générer un certificat en réponse à un fichier de demande de certificat (qui peut être créé par la commande keytool -certreq). La commande lit la demande soit à partir de infile, soit, si omis, à partir de l'entrée standard, la signe à l'aide de la clé privée de l'alias, et produit le certificat X.509 dans outfile ou, s'il est omis, vers la sortie standard. Lorsque -rfc est spécifié, le format de sortie est PEM encodé en Base64 ; sinon, un DER binaire est créé.

La valeur -sigalg spécifie l'algorithme qui doit être utilisé pour signer le certificat. L'argument startdate est l'heure et la date de début de validité du certificat. L'argument days indique le nombre de jours pendant lesquels le certificat doit être considéré comme valide.

Lorsque dname est fourni, il est utilisé comme sujet du certificat généré. Sinon, celui de la demande de certificat est utilisé.

L'option -ext indique quelles extensions X.509 seront intégrées dans le certificat. Lisez Options de commande courantes pour la grammaire de -ext.

L'option -gencert vous permet de créer des chaînes de certificats. L'exemple suivant crée un certificat, e1, qui contient trois certificats dans sa chaîne de certificats.

Les commandes suivantes créent quatre paires de clés nommées ca, ca1, ca2 et e1 :


keytool -alias ca -dname CN=CA -genkeypair -keyalg rsa
keytool -alias ca1 -dname CN=CA -genkeypair -keyalg rsa
keytool -alias ca2 -dname CN=CA -genkeypair -keyalg rsa
keytool -alias e1 -dname CN=E1 -genkeypair -keyalg rsa

Les deux commandes suivantes créent une chaîne de certificats signés ; ca signe ca1 et ca1 signe ca2, qui sont toutes auto-émises :


keytool -alias ca1 -certreq |
    keytool -alias ca -gencert -ext san=dns:ca1 |
    keytool -alias ca1 -importcert
keytool -alias ca2 -certreq |
    keytool -alias ca1 -gencert -ext san=dns:ca2 |
    keytool -alias ca2 -importcert

La commande suivante crée le certificat e1 et le stocke dans le fichier e1.cert, qui est signé par ca2. Par conséquent, e1 devrait contenir ca, ca1 et ca2 dans sa chaîne de certificats :

keytool -alias e1 -certreq | keytool -alias ca2 -gencert > e1.cert

Utilisez la commande -genkeypair pour générer une paire de clés (une clé publique et la clé privée associée). Lorsque l'option -signer n'est pas spécifiée, la clé publique est encapsulée dans un certificat auto-signé X.509 v3 et stockée comme une chaîne de certificats à un seul élément. Lorsque l'option -signer est spécifiée, un nouveau certificat est généré et signé par le signataire désigné, puis stocké comme une chaîne de certificats à plusieurs éléments (contenant le certificat généré lui-même et la chaîne de certificats du signataire). La chaîne de certificats et la clé privée sont stockées dans une nouvelle entrée de keystore identifiée par son alias.

La valeur -keyalg spécifie l'algorithme à utiliser pour générer la paire de clés, et la valeur -keysize spécifie la taille de chaque clé à générer. La valeur -sigalg spécifie l'algorithme qui doit être utilisé pour signer le certificat. Cet algorithme doit être compatible avec la valeur -keyalg.

La valeur -groupname spécifie le groupe nommé (par exemple, le nom standard ou prédéfini d'une courbe elliptique) de la clé à générer. Seuls -groupname ou -keysize peuvent être spécifiés.

L'option -signer spécifie l'alias d'une PrivateKeyEntry pour le signataire qui existe déjà dans le keystore. Cette option est utilisée pour signer le certificat avec la clé privée du signataire. Ceci est particulièrement utile pour les algorithmes d'accord de clés (c'est-à-dire, la valeur -keyalg est XDH, X25519, X448 ou DH) car ces clés ne peuvent pas être utilisées pour des signatures numériques, et par conséquent un certificat auto-signé ne peut pas être créé.

La valeur -signerkeypass spécifie le mot de passe de la clé privée du signataire. Elle peut être spécifiée si la clé privée de l'entrée du signataire est protégée par un mot de passe différent du mot de passe du magasin.

La valeur -dname spécifie le Nom Distinctif X.500 à associer à la valeur de -alias. Si l'option -signer n'est pas spécifiée, les champs émetteur et sujet du certificat auto-signé sont remplis avec le nom distinctif spécifié. Si l'option -signer est spécifiée, le champ sujet du certificat est rempli avec le nom distinctif spécifié et le champ émetteur est rempli avec le champ sujet du certificat du signataire. Si aucun nom distinctif n'est fourni en ligne de commande, l'utilisateur est invité à le faire.

La valeur de -keypass est un mot de passe utilisé pour protéger la clé privée de la paire de clés générée. Si aucun mot de passe n'est fourni, l'utilisateur est invité à le faire. Si vous appuyez sur la touche Entrée à l'invite, le mot de passe de la clé sera défini sur le même mot de passe que celui du keystore. La valeur -keypass doit contenir au moins six caractères.

La valeur de -startdate spécifie l'heure d'émission du certificat, également connue sous le nom de valeur "Not Before" du champ Validity du certificat X.509.

La valeur de l'option peut être définie selon l'une de ces deux formes :

([+-]nnn[ymdHMS])+

[aaaa/mm/jj] [HH:MM:SS]

Avec la première forme, l'heure d'émission est décalée de la valeur spécifiée par rapport à l'heure actuelle. La valeur est une concaténation d'une séquence de sous-valeurs. À l'intérieur de chaque sous-valeur, le signe plus (+) signifie décalage vers l'avant, et le signe moins (-) signifie décalage vers l'arrière. L'heure à décaler est de nnn unités d'années, de mois, de jours, d'heures, de minutes ou de secondes (indiqué par un seul caractère y, m, d, H, M ou S respectivement). La valeur exacte de l'heure d'émission est calculée en utilisant la méthode java.util.GregorianCalendar.add(int field, int amount) sur chaque sous-valeur, de gauche à droite. Par exemple, l'heure d'émission peut être spécifiée par :


Calendar c = new GregorianCalendar();
c.add(Calendar.YEAR, -1);
c.add(Calendar.MONTH, 1);
c.add(Calendar.DATE, -1);
return c.getTime()

Avec la seconde forme, l'utilisateur définit l'heure d'émission exacte en deux parties, année/mois/jour et heure:minute:seconde (en utilisant le fuseau horaire local). L'utilisateur peut fournir une seule partie, ce qui signifie que l'autre partie est identique à la date (ou heure) actuelle. L'utilisateur doit fournir le nombre exact de chiffres indiqué dans la définition du format (en ajoutant des 0 si nécessaire). Lorsque la date et l'heure sont fournies, il y a un (et un seul) espace entre les deux parties. L'heure doit toujours être fournie au format 24 heures.

Lorsque l'option n'est pas fournie, la date de début est l'heure actuelle. L'option ne peut être fournie qu'une seule fois.

La valeur de date spécifie le nombre de jours (à partir de la date spécifiée par -startdate, ou de la date actuelle lorsque -startdate n'est pas spécifié) pendant lesquels le certificat doit être considéré comme valide.

Utilisez la commande -importcert pour lire le certificat ou la chaîne de certificats (cette dernière étant fournie dans une réponse au format PKCS#7 ou dans une séquence de certificats X.509) à partir de -file file, et la stocker dans l'entrée de keystore identifiée par -alias. Si -file file n'est pas spécifié, le certificat ou la chaîne de certificats est lu(e) à partir de l'entrée standard.

La commande keytool peut importer des certificats X.509 v1, v2 et v3, et des chaînes de certificats au format PKCS#7 composées de certificats de ce type. Les données à importer doivent être fournies soit au format d'encodage binaire, soit au format d'encodage imprimable (également appelé encodage Base64) tel que défini par la norme Internet RFC 1421. Dans ce dernier cas, l'encodage doit être délimité au début par une chaîne commençant par -----BEGIN, et délimité à la fin par une chaîne commençant par -----END.

Vous importez un certificat pour deux raisons : Pour l'ajouter à la liste des certificats de confiance, et pour importer une réponse de certificat reçue d'une autorité de certification (CA) suite à la soumission d'une demande de signature de certificat (CSR) à cette CA. Voir la commande -certreq dans Commandes pour la génération d'une demande de certificat.

Le type d'importation est indiqué par la valeur de l'option -alias. Si l'alias ne pointe pas vers une entrée de clé, la commande keytool suppose que vous ajoutez une entrée de certificat de confiance. Dans ce cas, l'alias ne doit pas déjà exister dans le keystore. Si l'alias existe, la commande keytool affiche une erreur car un certificat de confiance existe déjà pour cet alias, et n'importe pas le certificat. Si -alias pointe vers une entrée de clé, la commande keytool suppose que vous importez une réponse de certificat.

GÉNÉRATION DE LA PAIRE DE CLÉS

Créez un magasin de clés, puis générez la paire de clés.

Vous pouvez saisir la commande sur une seule ligne, comme suit :

keytool -genkeypair -dname "cn=monnom, ou=mongroupe, o=monentreprise, c=monpays" -alias entreprise -keyalg rsa -keypass motdepasse -keystore /chemin/vers/monmagasindeclefs -storepass motdepasse -validity 180

La commande crée le magasin de clés nommé monmagasindeclefs dans le répertoire courant (s'il n'existe pas déjà) et lui attribue le mot de passe spécifié par -keypass. Elle génère une paire de clés publique/privée pour l'entité dont le nom distinctif est monnom, mongroupe, monentreprise, et un code pays à deux lettres de monpays. Elle utilise l'algorithme de génération de clés RSA pour créer les clés ; les deux sont de 3072 bits.

La commande utilise l'algorithme de signature par défaut SHA384withRSA pour créer un certificat auto-signé qui inclut la clé publique et les informations de nom distinctif. Le certificat est valide pendant 180 jours et est associé à la clé privée dans une entrée de magasin de clés référencée par -alias entreprise. La clé privée se voit attribuer le mot de passe spécifié par -keypass.

La commande est significativement plus courte lorsque les valeurs par défaut des options sont acceptées. Dans ce cas, seul -keyalg est requis, et les valeurs par défaut sont utilisées pour les options non spécifiées qui ont des valeurs par défaut. Vous serez invité à fournir les valeurs requises. Vous pourriez avoir ce qui suit :

keytool -genkeypair -keyalg rsa

Dans ce cas, une entrée de magasin de clés avec l'alias mykey est créée, avec une nouvelle paire de clés générée et un certificat valide pendant 90 jours. Cette entrée est placée dans votre répertoire personnel dans un magasin de clés nommé .keystore. .keystore est créé s'il n'existe pas déjà. Vous serez invité à fournir les informations de nom distinctif, le mot de passe du magasin de clés et le mot de passe de la clé privée.

Remarque :

Le reste des exemples suppose que vous avez répondu aux invites avec des valeurs égales à celles spécifiées dans la première commande -genkeypair. Par exemple, un nom distinctif de cn=monnom, ou=mongroupe, o=monentreprise, c=monpays).

DEMANDE D'UN CERTIFICAT SIGNÉ PAR UNE AC

Remarque :

La génération de la paire de clés a créé un certificat auto-signé ; cependant, un certificat est plus susceptible d'être approuvé par d'autres s'il est signé par une AC.

Pour obtenir une signature d'AC, suivez ce processus :

1.
Générez une CSR :

keytool -certreq -file monnom.csr

Cela crée une CSR pour l'entité identifiée par l'alias par défaut mykey et place la demande dans le fichier nommé monnom.csr.

2.
Soumettez monnom.csr à une AC, telle que DigiCert.

L'AC vous authentifie, vous le demandeur (généralement hors ligne), et renvoie un certificat, signé par elle, qui authentifie votre clé publique. Dans certains cas, l'AC renvoie une chaîne de certificats, chacun authentifiant la clé publique du signataire du certificat précédent dans la chaîne.

IMPORTATION D'UN CERTIFICAT POUR L'AC

Pour importer un certificat pour l'AC, suivez ce processus :

1.
Avant d'importer la réponse de certificat d'une AC, vous avez besoin d'un ou plusieurs certificats de confiance, soit dans votre magasin de clés, soit dans le fichier de magasin de clés cacerts. Voir -importcert dans Commandes.
•
Si la réponse de certificat est une chaîne de certificats, alors vous avez besoin du certificat supérieur de la chaîne. Le certificat racine de l'AC qui authentifie la clé publique de l'AC.
•
Si la réponse de certificat est un certificat unique, alors vous avez besoin d'un certificat pour l'AC émettrice (celle qui l'a signé). Si ce certificat n'est pas auto-signé, alors vous avez besoin d'un certificat de son signataire, et ainsi de suite, jusqu'à un certificat racine d'AC auto-signé.

Le magasin de clés cacerts est fourni avec un ensemble de certificats racines émis par les AC du programme de certificats racines Oracle Java [http://www.oracle.com/technetwork/java/javase/javasecarootcertsprogram-1876540.html]. Si vous demandez un certificat signé à une AC, et qu'un certificat authentifiant la clé publique de cette AC n'a pas été ajouté à cacerts, alors vous devez importer un certificat de cette AC en tant que certificat de confiance.

Un certificat d'une AC est généralement auto-signé ou signé par une autre AC. S'il est signé par une autre AC, vous avez besoin d'un certificat qui authentifie la clé publique de cette AC.

Par exemple, vous avez obtenu un fichier X.cer d'une entreprise qui est une AC et le fichier est censé être un certificat auto-signé qui authentifie la clé publique de cette AC. Avant de l'importer en tant que certificat de confiance, vous devez vérifier la validité du certificat en :

1.
Le visualisant avec la commande keytool -printcert ou la commande keytool -importcert sans utiliser l'option -noprompt. Assurez-vous que les empreintes de certificat affichées correspondent aux empreintes attendues.
2.
Appelant la personne qui a envoyé le certificat et en comparant les empreintes que vous voyez avec celles qu'elle présente ou qu'un dépôt de clés publiques sécurisé affiche.

Ce n'est que lorsque les empreintes sont égales qu'il est assuré que le certificat n'a pas été remplacé pendant le transit par le certificat de quelqu'un d'autre (comme le certifica

te). Si une telle attaque a lieu et que vous n'avez pas vérifié le certificat avant de l'importer, vous feriez confiance à tout ce que l'attaquant a signé.

2.
Remplacez le certificat auto-signé par une chaîne de certificats, où chaque certificat de la chaîne authentifie la clé publique du signataire du certificat précédent dans la chaîne, jusqu'à une autorité de certification racine.

Si vous faites confiance à la validité du certificat, vous pouvez l'ajouter à votre magasin de clés en entrant la commande suivante :

keytool -importcert -alias alias -file *X*.cer`

Cette commande crée une entrée de certificat de confiance dans le magasin de clés à partir des données du fichier de certificat de l'AC et attribue les valeurs de alias à l'entrée.

IMPORTATION DE LA RÉPONSE DU CERTIFICAT DE L'AC

Après avoir importé un certificat qui authentifie la clé publique de l'AC à laquelle vous avez soumis votre demande de signature de certificat (ou s'il existe déjà un tel certificat dans le fichier cacerts), vous pouvez importer la réponse du certificat et remplacer votre certificat auto-signé par une chaîne de certificats.

La chaîne de certificats est l'un des éléments suivants :

•
Retournée par l'AC lorsque la réponse de l'AC est une chaîne.
•
Construite lorsque la réponse de l'AC est un certificat unique. Cette chaîne de certificats est construite en utilisant la réponse du certificat et les certificats de confiance disponibles soit dans le magasin de clés où vous importez la réponse, soit dans le fichier de magasin de clés cacerts.

Par exemple, si vous avez envoyé votre demande de signature de certificat à DigiCert, vous pouvez importer leur réponse en entrant la commande suivante :

Note :

Dans cet exemple, le certificat retourné est nommé DCmyname.cer.

keytool -importcert -trustcacerts -file DCmyname.cer

IMPORTATION DU KEYSTORE

Utilisez la commande importkeystore pour importer un magasin de clés entier dans un autre magasin de clés. Cela importe toutes les entrées du magasin de clés source, y compris les clés et les certificats, vers le magasin de clés de destination en une seule commande. Vous pouvez utiliser cette commande pour importer des entrées d'un type de magasin de clés différent. Lors de l'importation, toutes les nouvelles entrées dans le magasin de clés de destination auront les mêmes noms d'alias et mots de passe de protection (pour les clés secrètes et les clés privées). Si la commande keytool ne peut pas récupérer les clés privées ou les clés secrètes du magasin de clés source, elle vous demandera un mot de passe. Si elle détecte des doublons d'alias, elle vous demandera un nouvel alias, et vous pourrez spécifier un nouvel alias ou simplement permettre à la commande keytool d'écraser celui existant.

Par exemple, importez des entrées d'un type de magasin de clés JKS typique key.jks dans un magasin de clés matériel de type PKCS #11, en entrant la commande suivante :

keytool -importkeystore -srckeystore key.jks -destkeystore NONE -srcstoretype JKS -deststoretype PKCS11 -srcstorepass password -deststorepass password

La commande importkeystore peut également être utilisée pour importer une seule entrée d'un magasin de clés source vers un magasin de clés de destination. Dans ce cas, en plus des options que vous avez utilisées dans l'exemple précédent, vous devez spécifier l'alias que vous souhaitez importer. Avec l'option -srcalias spécifiée, vous pouvez également spécifier le nom de l'alias de destination, le mot de passe de protection pour une clé secrète ou privée, et le mot de passe de protection de destination comme suit :

keytool -importkeystore -srckeystore key.jks -destkeystore NONE -srcstoretype JKS -deststoretype PKCS11 -srcstorepass password -deststorepass password -srcalias myprivatekey -destalias myoldprivatekey -srckeypass password -destkeypass password -noprompt

Un magasin de clés est un dispositif de stockage pour les clés cryptographiques et les certificats.
Entrées du magasin de clés
Les magasins de clés peuvent avoir différents types d'entrées. Les deux types d'entrées les plus applicables pour la commande keytool comprennent les suivants :

Entrées de clés : Chaque entrée contient des informations de clé cryptographique très sensibles, stockées dans un format protégé pour empêcher tout accès non autorisé. Généralement, une clé stockée dans ce type d'entrée est une clé secrète, ou une clé privée accompagnée de la chaîne de certificats pour la clé publique correspondante. Voir Chaînes de certificats. La commande keytool peut gérer les deux types d'entrées, tandis que l'outil jarsigner ne gère que le dernier type d'entrée, c'est-à-dire les clés privées et leurs chaînes de certificats associées.

Entrées de certificats de confiance : Chaque entrée contient un seul certificat de clé publique appartenant à une autre partie. L'entrée est appelée certificat de confiance parce que le propriétaire du magasin de clés fait confiance au fait que la clé publique du certificat appartient à l'identité identifiée par le sujet (propriétaire) du certificat. L'émetteur du certificat le garantit en signant le certificat.

Alias de magasin de clés
Toutes les entrées du magasin de clés (entrées de clés et de certificats de confiance) sont accessibles via des alias uniques.

Un alias est spécifié lorsque vous ajoutez une entité au magasin de clés avec la commande -genseckey pour générer une clé secrète, la commande -genkeypair pour générer une paire de clés (clé publique et clé privée), ou la commande -importcert pour ajouter un certificat ou une chaîne de certificats à la liste des certificats de confiance. Les commandes keytool ultérieures doivent utiliser le même alias pour faire référence à l'entité.

Par exemple, vous pouvez utiliser l'alias duke pour générer une nouvelle paire de clés publique/privée et encapsuler la clé publique dans un certificat auto-signé avec la commande suivante. Voir Chaînes de certificats.

keytool -genkeypair -alias duke -keyalg rsa -keypass passwd

Cet exemple spécifie un passwd initial requis par les commandes ultérieures pour accéder à la clé privée associée à l'alias duke. Si vous souhaitez plus tard modifier le mot de passe de la clé privée de Duke, utilisez une commande telle que la suivante :

keytool -keypasswd -alias duke -keypass passwd -new newpasswd

Cela remplace le passwd initial par newpasswd. Un mot de passe ne doit pas être spécifié sur une ligne de commande ou dans un script, sauf à des fins de test, ou si vous êtes sur un système sécurisé. Si vous ne spécifiez pas une option de mot de passe requise sur une ligne de commande, vous serez invité à le faire.

CHAÎNES DE CLÉS

Chaîne de clés
La chaîne de clés est un ensemble de certificats qui est utilisé pour authentifier une clé publique. La chaîne commence par le certificat qui contient la clé publique que vous voulez authentifier. Le certificat suivant dans la chaîne est celui qui authentifie la clé publique du signataire du certificat précédent. La chaîne se termine par un certificat auto-signé qui contient la clé publique du propriétaire du certificat final.

Lors de la génération des clés, la chaîne contient généralement un seul élément, un certificat auto-signé. Voir -genkeypair dans Commandes. Un certificat auto-signé est un certificat pour lequel l'émetteur (signataire) est identique au sujet. Le sujet est l'entité dont la clé publique est authentifiée par le certificat. Lorsque la commande -genkeypair est appelée pour générer une nouvelle paire de clés publique/privée, elle encapsule également la clé publique dans un certificat auto-signé (sauf si l'option -signer est spécifiée).

Plus tard, après qu'une demande de signature de certificat (CSR) a été générée avec la commande -certreq et envoyée à une autorité de certification (CA), la réponse de la CA est importée avec -importcert, et le certificat auto-signé est remplacé par une chaîne de certificats. Au bas de la chaîne se trouve le certificat (réponse) délivré par la CA authentifiant la clé publique du sujet. Le certificat suivant dans la chaîne est celui qui authentifie la clé publique de la CA.

Dans de nombreux cas, il s'agit d'un certificat auto-signé, qui est un certificat de la CA authentifiant sa propre clé publique, et le dernier certificat de la chaîne. Dans d'autres cas, la CA peut renvoyer une chaîne de certificats. Dans ce cas, le certificat du bas de la chaîne est le même (un certificat signé par la CA, authentifiant la clé publique de l'entrée de clé), mais le deuxième certificat de la chaîne est un certificat signé par une autre CA qui authentifie la clé publique de la CA à laquelle vous avez envoyé la CSR. Le certificat suivant dans la chaîne est un certificat qui authentifie la clé de la deuxième CA, et ainsi de suite, jusqu'à ce qu'un certificat racine auto-signé soit atteint. Chaque certificat de la chaîne (après le premier) authentifie la clé publique du signataire du certificat précédent dans la chaîne.

De nombreuses CA ne renvoient que le certificat délivré, sans chaîne de support, en particulier lorsqu'il existe une hiérarchie plate (pas de CA intermédiaires). Dans ce cas, la chaîne de certificats doit être établie à partir d'informations de certificat de confiance déjà stockées dans le magasin de clés.

Un format de réponse différent (défini par la norme PKCS #7) inclut la chaîne de certificats de support en plus du certificat délivré. Les deux formats de réponse peuvent être gérés par la commande keytool.

Le certificat de la CA racine de niveau supérieur est auto-signé. Cependant, la confiance dans la clé publique de la racine ne provient pas du certificat racine lui-même, mais d'autres sources telles qu'un journal. En effet, n'importe qui pourrait générer un certificat auto-signé avec le nom distinctif, par exemple, de la CA racine DigiCert. La clé publique de la CA racine est largement connue. La seule raison pour laquelle elle est stockée dans un certificat est que c'est le format compris par la plupart des outils, donc le certificat dans ce cas n'est utilisé que comme véhicule pour transporter la clé publique de la CA racine. Avant d'ajouter le certificat de la CA racine à votre magasin de clés, vous devez le visualiser avec l'option -printcert et comparer l'empreinte affichée avec l'empreinte bien connue obtenue à partir d'un journal, de la page Web de la CA racine, etc.

Norme d'encodage de certificat Internet RFC 1421
Les certificats sont souvent stockés en utilisant le format d'encodage imprimable défini par la norme Internet RFC 1421, au lieu de leur encodage binaire. Ce format de certificat, également connu sous le nom d'encodage Base64, permet d'exporter facilement des certificats vers d'autres applications par e-mail ou via un autre mécanisme.

Les certificats lus par les commandes -importcert et -printcert peuvent être dans ce format ou encodés en binaire. La commande -exportcert produit par défaut un certificat en encodage binaire, mais produira un certificat en format d'encodage imprimable lorsque l'option -rfc est spécifiée.

La commande -list imprime par défaut l'empreinte SHA-256 d'un certificat. Si l'option -v est spécifiée, le certificat est imprimé dans un format lisible par l'homme. Si l'option -rfc est spécifiée, le certificat est produit au format d'encodage imprimable.

Dans son format d'encodage imprimable, le certificat encodé est délimité au début et à la fin par le texte suivant :


-----BEGIN CERTIFICATE-----
le certificat encodé va ici.
-----END CERTIFICATE-----
Noms distinctifs X.500
Les noms distinctifs X.500 sont utilisés pour identifier des entités, telles que celles nommées par les champs sujet et émetteur (signataire) des certificats X.509. La commande keytool prend en charge les sous-parties suivantes :
•
commonName : Le nom commun d'une personne telle que Susan Jones.
•
organizationUnit : Le nom de la petite organisation (telle qu'un département ou une division). Par exemple, Achats.
•
localityName : Le nom de la localité (ville), par exemple, Palo Alto.
•
stateName : Nom de l'état ou de la province, par exemple, Californie.
•
country : Code pays à deux lettres, par exemple, CH.

Lorsque vous fournissez une chaîne de nom distinctif comme valeur d'une option -dname, comme pour la commande -genkeypair, la chaîne doit être dans le format suivant :

CN=cName, OU=orgUnit, O=org, L=city, S=state, C=countryCode

Tous les éléments suivants représentent des valeurs réelles et les mots-clés précédents sont des abréviations pour les éléments suivants :


CN=commonName
OU=organizationUnit
O=organizationName
L=localityName
S=stateName
C=country

Une chaîne de nom distinctif d'exemple est :

CN=Mark Smith, OU=Java, O=Oracle, L=Cupertino, S=California, C=US

Une commande d'exemple utilisant une telle chaîne est :

keytool -genkeypair -dname "CN=Mark Smith, OU=Java, O=Oracle, L=Cupertino, S=California, C=US" -alias mark -keyalg rsa

La casse n'a pas d'importance pour les abréviations des mots-clés. Par exemple, CN, cn et Cn sont traités de la même manière.

L'ordre compte ; chaque sous-composant doit apparaître dans l'ordre désigné. Cependant, il n'est pas nécessaire d'avoir tous les sous-composants. Vous pouvez utiliser un sous-ensemble, par exemple :

CN=Smith, OU=Java, O=Oracle, C=US

Si une valeur de chaîne de nom distinctif contient une virgule, la virgule doit être échappée par un caractère antislash (\) lorsque vous spécifiez la chaîne sur une ligne de commande, comme ceci :

cn=Jack, ou=Java\, Product Development, o=Oracle, c=US

Il n'est jamais nécessaire de spécifier une chaîne de nom distinctif sur une ligne de commande. Lorsque le nom distinctif est nécessaire pour une commande, mais n'est pas fourni sur la ligne de commande, l'utilisateur est invité à saisir chacun des sous-composants. Dans ce cas, une virgule n'a pas besoin d'être échappée par un antislash (\).

VERIFYING THE CERTIFICATE FINGERPRINTS

Before you import a certificate, you should always verify its fingerprints. You can do this by using the -printcert command or the -importcert command without the -noprompt option. Ensure that the displayed certificate fingerprints match the expected ones. For example, suppose someone sends or emails you a certificate that you put it in a file named /tmp/cert. Before you consider adding the certificate to your list of trusted certificates, you can execute a -printcert command to view its fingerprints, as follows:


  keytool -printcert -file /tmp/cert
    Owner: CN=ll, OU=ll, O=ll, L=ll, S=ll, C=ll
    Issuer: CN=ll, OU=ll, O=ll, L=ll, S=ll, C=ll
    Serial Number: 59092b34
    Valid from: Thu Jun 24 18:01:13 PDT 2016 until: Wed Jun 23 17:01:13 PST 2016
    Certificate Fingerprints:
                   SHA-1: 20:B6:17:FA:EF:E5:55:8A:D0:71:1F:E8:D6:9D:C0:37:13:0E:5E:FE
                   SHA-256: 90:7B:70:0A:EA:DC:16:79:92:99:41:FF:8A:FE:EB:90:
                           17:75:E0:90:B2:24:4D:3A:2A:16:A6:E4:11:0F:67:A4

Then call or otherwise contact the person who sent the certificate and compare the fingerprints that you see with the ones that they show. Only when the fingerprints are equal is it guaranteed that the certificate wasn't replaced in transit with somebody else's certificate such as an attacker's certificate. If such an attack took place, and you didn't check the certificate before you imported it, then you would be trusting anything the attacker signed, for example, a JAR file with malicious class files inside.

Note:

It isn't required that you execute a -printcert command before importing a certificate. This is because before you add a certificate to the list of trusted certificates in the keystore, the -importcert command prints out the certificate information and prompts you to verify it. You can then stop the import operation. However, you can do this only when you call the -importcert command without the -noprompt option. If the -noprompt option is specified, then there is no interaction with the user.

PASSWORDS WARNING

Most commands that operate on a keystore require the store password. Some commands require a private/secret key password. Passwords can be specified on the command line in the -storepass and -keypass options. However, a password shouldn't be specified on a command line or in a script unless it is for testing, or you are on a secure system. When you don't specify a required password option on a command line, you are prompted for it.

CERTIFICATE CONFORMANCE WARNING

Internet X.509 Public Key Infrastructure Certificate and Certificate Revocation List (CRL) Profile [https://tools.ietf.org/rfc/rfc5280.txt] defined a profile on conforming X.509 certificates, which includes what values and value combinations are valid for certificate fields and extensions.

The keytool command doesn't enforce all of these rules so it can generate certificates that don't conform to the standard, such as self-signed certificates that would be used for internal testing purposes. Certificates that don't conform to the standard might be rejected by the JDK or other applications. Users should ensure that they provide the correct options for -dname, -ext, and so on.

IMPORT A NEW TRUSTED CERTIFICATE

Before you add the certificate to the keystore, the keytool command verifies it by attempting to construct a chain of trust from that certificate to a self-signed certificate (belonging to a root CA), using trusted certificates that are already available in the keystore.

If the -trustcacerts option was specified, then additional certificates are considered for the chain of trust, namely the certificates in a file named cacerts.

If the keytool command fails to establish a trust path from the certificate to be imported up to a self-signed certificate (either from the keystore or the cacerts file), then the certificate information is printed, and the user is prompted to verify it by comparing the displayed certificate fingerprints with the fingerprints obtained from some other (trusted) source of information, which might be the certificate owner. Be very careful to ensure the certificate is valid before importing it as a trusted certificate. The user then has the option of stopping the import operation. If the -noprompt option is specified, then there is no interaction with the user.

IMPORT A CERTIFICATE REPLY

When you import a certificate reply, the certificate reply is validated with trusted certificates from the keystore, and optionally, the certificates configured in the cacerts keystore file when the -trustcacerts option is specified.

The methods of determining whether the certificate reply is trusted are as follows:

•
If the reply is a single X.509 certificate, then the keytool command attempts to establish a trust chain, starting at the certificate reply and ending at a self-signed certificate (belonging to a root CA). The certificate reply and the hierarchy of certificates is used to authenticate the certificate reply from the new certificate chain of aliases. If a trust chain can't be established, then the certificate reply isn't imported. In this case, the keytool command doesn't print the certificate and prompt the user to verify it, because it is very difficult for a user to determine the authenticity of the certificate reply.
•
If the reply is a PKCS #7 formatted certificate chain or a sequence of X.509 certificates, then the chain is ordered with the user certificate first followed by zero or more CA certificates. If the chain ends with a self-signed root CA certificate and the-trustcacerts option was specified, the keytool command attempts to match it with any of the trusted certificates in the keystore or the cacerts keystore file. If the chain doesn't end with a self-signed root CA certificate and the -trustcacerts option was specified, the keytool command tries to find one from the trusted certificates in the keystore or the cacerts keystore file and add it to the end of the chain. If the certificate isn't found and the -noprompt option isn't specified, the information of the last certificate in the chain is printed, and the user is prompted to verify it.

If the public key in the certificate reply matches the user's public key already stored with alias, then the old certificate chain is replaced with the new certificate chain in the reply. The old chain can only be replaced with a valid keypass, and so the password used to protect the private key of the entry is supplied. If no password is provided, and the private key password is different from the keystore password, the user is prompted for it.

This command was named -import in earlier releases. This old name is still supported in this release. The new name, -importcert, is preferred.
