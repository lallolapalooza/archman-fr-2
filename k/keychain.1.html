NOM

keychain - Gestionnaire pour ssh-agent, gpg-agent et clés privées. Compatible avec les systèmes POSIX.

INTRODUCTION

Keychain vous aide à gérer les clés SSH et GPG de manière pratique et sécurisée. Il sert d'interface à "ssh-agent" et "ssh-add", mais vous permet d'avoir facilement un seul processus "ssh-agent" à longue durée de vie par système, plutôt que la norme d'un "ssh-agent" par session de connexion.

Cela réduit considérablement le nombre de fois où vous devez entrer votre phrase secrète. Avec "keychain", vous n'avez besoin d'entrer une phrase secrète qu'une seule fois à chaque redémarrage de votre machine locale. Keychain permet également aux tâches cron distantes de se connecter facilement et en toute sécurité à un processus "ssh-agent" à longue durée de vie, permettant à vos scripts de profiter des connexions par clé.

Keychain prend également en charge GnuPG 2.1 et versions ultérieures, et démarrera automatiquement gpg-agent si des clés GPG sont référencées sur la ligne de commande, et garantira que ces identifiants sont mis en cache en mémoire et disponibles pour utilisation.

Page d'accueil officielle du projet : https://github.com/danielrobbins/keychain.

COMPATIBILITÉ

Keychain prend en charge la plupart des systèmes d'exploitation de type UNIX et limite intentionnellement sa portée aux implémentations modernes et largement déployées d'OpenSSH et GnuPG.

  • Version minimale d'OpenSSH : 7.3

    OpenSSH 7.3 (publié le 2016-08-01) a introduit l'option "-G" (dump de configuration) utilisée par Keychain pour développer les clés étendues "host:" et la fonctionnalité "--confallhosts". Comme cette option est centrale à la découverte moderne des clés, Keychain cible officiellement OpenSSH 7.3 ou plus récent. Les versions antérieures (>=6.5) peuvent sembler fonctionner pour une utilisation basique (chargement de clés explicitement nommées) mais ne font pas partie de la matrice de test prise en charge.

    Les types de clés pris en charge sous la base de référence 7.3+ incluent RSA, ECDSA et Ed25519 (Ed25519 est apparu pour la première fois dans OpenSSH 6.5). Les clés DSA ont été désactivées par défaut en amont depuis OpenSSH 7.0 ; Keychain les listera ou les chargera toujours si elles sont explicitement activées et présentes, mais elles sont considérées comme obsolètes.

    Fonctionnalités exploitées d'OpenSSH :

    ssh -V            (détection de l'implémentation)
ssh -nG host      (développement de configuration pour les clés étendues host:)
ssh-agent -s      (sortie d'environnement compatible Bourne ; forcé en permanence)
ssh-agent -t      (durée de vie par défaut de la clé lors du lancement)
ssh-agent -a path (chemin explicite du socket lors de la demande)
ssh-add -l/-L     (lister les empreintes / clés publiques)
ssh-add -d/-D     (supprimer une / supprimer toutes les clés)
ssh-add -c        (mode confirmation)
ssh-add -t        (remplacement de la durée de vie par clé)
ssh-keygen -l -f  (extraction d'empreinte, gère SHA256 & MD5 obsolète)
Sockets d'agent transférés (adoptés optionnellement avec --ssh-allow-forwarded)
  • GnuPG / gpg-agent

    GnuPG 2.1 ou version ultérieure est requis pour l'intégration de gpg-agent. Keychain utilise "gpg-connect-agent" "GETINFO nom_socket" et "GETINFO nom_socket_ssh" pour détecter, adopter ou (optionnellement) lancer gpg-agent lors de son utilisation comme agent SSH via "--ssh-allow-gpg" ou "--ssh-spawn-gpg". Les versions antérieures de GnuPG (2.0.x) manquaient de prise en charge fiable du stockage de clés SSH et ne sont pas prises en charge.

  • Shells

    Le script Keychain lui-même nécessite un shell compatible POSIX / Bourne. Il génère des fichiers pid pour les shells Bourne ("...-sh"), csh/tcsh ("...-csh") et fish ("...-fish"). En interne, Keychain consomme désormais toujours la sortie canonique Bourne de ssh-agent (forcée avec "-s") et en dérive les autres formats de shell. Bash, ksh et zsh consomment les fichiers pid Bourne.

    Keychain est officiellement pris en charge sur Git Bash (MSYS2) pour Windows, y compris la gestion correcte des chemins de style Windows et des noms d'utilisateur contenant des espaces.

    Les fichiers pid csh/tcsh et fish sont toujours pris en charge pour la compatibilité descendante. Leur dépréciation est envisagée : un avertissement concernant leur suppression prévue sera annoncé au moins deux versions mineures avant tout changement.

  • Espaces dans HOME et les chemins

    Keychain 2.9.7+ gère correctement les répertoires personnels et les chemins de clés privées contenant des espaces. Toutes les variables de chemin dans les fichiers pid (SSH_AUTH_SOCK) sont entre guillemets pour garantir un analyse correct par les shells. L'implémentation utilise une approche robuste qui évalue la sortie de ssh-agent dans un sous-shell pour extraire directement les variables d'environnement, plutôt qu'une analyse fragile de chaînes. Cela garantit la compatibilité même si le format de sortie de ssh-agent change. La détection de la propriété des fichiers utilise le format de sortie ls défini par POSIX avec une logique pour analyser correctement les noms d'utilisateur contenant des espaces.

  • Anciennes / Autres implémentations SSH

    SunSSH (trouvé sur les anciennes versions d'Oracle Solaris) peut toujours fonctionner ; les chemins de code pour la détection de SunSSH sont conservés mais ne sont pas activement testés. Ils sont programmés pour être examinés et potentiellement supprimés après trois futures versions mineures, sauf si les retours de la communauté demandent leur conservation.

    L'implémentation commerciale historique ssh.com et son agent ne sont plus ciblés. S'ils sont détectés, le comportement peut revenir à un chargement de clés plus simple ; les fonctionnalités avancées (confirmation, analyse moderne des empreintes, développement d'hôtes) ne sont pas garanties. Le signalement d'une telle utilisation via les problèmes GitHub aidera à façonner les décisions futures de prise en charge.

  • Environnement utilisateur Systemd

    Sur les systèmes avec systemd --user, Keychain peut injecter "SSH_AUTH_SOCK" (et optionnellement "SSH_AGENT_PID") via "--systemd" pour une disponibilité plus large dans la session.

Résumé : Un environnement pris en charge est OpenSSH >= 7.3 plus (optionnellement) GnuPG >= 2.1, exécuté sous tout OS moderne de type UNIX avec un shell POSIX. Les versions antérieures ou les implémentations SSH non listées peuvent fonctionner pour des scénarios basiques mais sont hors du cadre officiel.

CYCLE DE VIE

En général, vous configurez keychain pour qu'il s'exécute lorsque vous vous connectez pour la première fois à un système. Si vous utilisez Bourne shell ou bash, vous créerez un fichier ~/.profile ou ~/.bash_profile et y inclurez la ligne suivante :

eval "$(keychain --eval id_rsa)"

Keychain démarrera ssh-agent s'il n'y en a pas déjà un en cours d'exécution. Keychain vérifie ensuite que vos clés privées (dans cet exemple, "id_rsa") sont chargées dans l'agent. Si ce n'est pas le cas, vous serez invité à entrer toute phrase secrète nécessaire pour les déchiffrer, afin qu'elles soient mises en cache en mémoire et disponibles pour utilisation.

En plus d'afficher des informations conviviales sur votre terminal, keychain écrira également des variables d'environnement importantes de ssh-agent, que le "$()" (vous pouvez aussi utiliser "``") capture, et le "eval" évalue, définissant ces variables dans votre shell actuel.

Ces variables d'environnement ssh-agent sont également écrites dans ~/.keychain/${HOSTNAME}-sh, de sorte que les connexions ultérieures et les shells non interactifs tels que les tâches cron puissent sourcer le fichier pour accéder à l'agent ssh en cours d'exécution et établir des connexions ssh sans mot de passe en utilisant les clés privées mises en cache -- même lorsque vous êtes

déconnecté. Ces fichiers sont collectivement appelés pidfiles.

Les fichiers clés spécifiés sur la ligne de commande seront recherchés dans le répertoire ~/.ssh/ , et keychain s'attendra à trouver le fichier de clé privée portant le même nom, ainsi qu'une ".pub" clé publique. Keychain vérifiera également si des clés GPG sont spécifiées et, le cas échéant, demandera les phrases de passe pour mettre en cache ces clés dans "gpg-agent".

Typiquement, les fichiers de clés privées SSH sont spécifiés par leur nom de fichier uniquement, sans chemin, bien qu'il soit possible de spécifier un chemin absolu ou relatif vers le fichier de clé privée. Les fichiers de clés privées peuvent être des liens symboliques vers la clé réelle, tant que votre système dispose de la commande "readlink" . Des fonctionnalités plus avancées sont également disponibles pour spécifier des clés -- voir les options --extended et --confallhosts pour plus d'informations.

De plus, pour les clés GPG spécifiées, des étapes similaires seront prises pour s'assurer que gpg-agent a la clé GPG en cache en mémoire et prête à l'emploi.

RATIONALISATION ET SIMPLIFICATION

Keychain 2.9.0 a été rationalisé, et avec cette maintenance, plusieurs options de ligne de commande ont été retirées car elles n'étaient pas complètement nécessaires. Cela simplifie l'utilisation de l'outil en le rendant plus intuitif. Les fichiers créés dans ~/.keychain ont également été nettoyés. Cette section détaille tous les changements importants.

CHANGEMENTS DES PIDFILES

"Pidfile" est le nom donné aux fichiers créés dans ~/.keychain qui peuvent ensuite être chargés par vos scripts pour accéder à un agent en cours d'exécution.

Lors de l'utilisation de gpg-agent pour les clés GPG, keychain ne créera plus de fichier ~/.keychain/${HOSTNAME}-sh-gpg pidfile. Ce fichier n'est plus nécessaire car le socket GPG canonique dans ~/.gnupg/ sera utilisé pour détecter le gpg-agent en cours d'exécution, ce qui est la convention moderne. GnuPG 2.1 et les versions ultérieures ont cessé d'utiliser des variables d'environnement pour trouver l'agent, nous suivons donc ce changement en amont.

DÉBOGAGE AMÉLIORÉ

Une nouvelle option --debug est maintenant disponible qui affichera des informations supplémentaires concernant les décisions de keychain sur la raison et la manière dont un agent a été trouvé -- ou non.

NOUVELLES (ET OBSOLÈTES) OPTIONS

Cette section fournit un aperçu des nouvelles options de ligne de commande et des options obsolètes. Pour plus de détails sur chaque option, voir la définition respective de l'option sous "OPTIONS".

Keychain 2.9.2

L'option "--confhost" est obsolète. Au lieu de "--confhost hostname", utilisez "--extended host:hostname". Ce format étendu permet de spécifier plusieurs clés de plusieurs types (SSH, GPG et SSH-depuis-nom-d'hôte) sur la ligne de commande ensemble. C'est également entièrement compatible avec "--confallhosts", et keychain dé-duplique maintenant la liste des clés à charger.

Keychain 2.9.1

Les options de courte durée "--ssh-wipe" et "--gpg-wipe" qui n'apparaissaient que dans la version 2.9.0 ont été remplacées par "--wipe qui" pour fonctionner de manière similaire à l'option "--stop" , et vous permet de spécifier "ssh", "gpg" ou "all".

Keychain 2.9.0

L'option "--agents" est maintenant obsolète. Keychain s'assurera toujours qu'un ssh-agent ou équivalent est en cours d'exécution, ou si "--ssh-spawn-gpg" est utilisé, potentiellement un gpg-agent dans le but de stocker des clés SSH si aucun ssh-agent en cours d'exécution n'est disponible. Pour simplement utiliser un gpg-agent si un est déjà en cours d'exécution, en revenant au lancement de ssh-agent si aucun agent n'est disponible, utilisez l'option "--ssh-allow-gpg" .

Spécifier une clé GPG sur la ligne de commande indiquera à keychain d'activer automatiquement les fonctionnalités de gpg-agent. Cela élimine une option que vous devez spécifier ("--agents ssh,gpg") lors de l'invocation de keychain, et pour beaucoup évitera de lancer un agent GPG que vous n'utilisez peut-être pas.

Spécifier l'option "--agents" affichera maintenant un avertissement indiquant qu'elle est obsolète, mais keychain ne s'interrompra pas.

L'option "--inherit" , qui prenait l'un des quatre arguments, est obsolète. Le comportement par défaut de keychain reste celui de préférer utiliser un ssh-agent ou équivalent référencé par son pidfile, en revenant à la recherche d'un ssh-agent dans son environnement. Par défaut, keychain n'utilisera pas un socket gpg-agent pour les clés SSH, sauf si au moins "--ssh-allow-gpg" est spécifié. De même, l'utilisation de toute connexion d'agent SSH transférée est désactivée par défaut et peut être activée via "--ssh-allow-forwarded". Encore une fois, voir la documentation complète de chaque option dans la section "OPTIONS".

Vous pouvez toujours influencer le comportement de keychain via l'option toujours présente "--noinherit" qui empêchera toute détection d'agents SSH existants via l'environnement.

L'option "--clear" est toujours disponible, mais n'est pas destinée à être une option "autonome", ce qui signifie qu'elle est utilisée pour effectuer un effacement initial des clés en cache avant de charger toute clé spécifiée lorsque Keychain est exécuté. Pour effectuer l'action unique d'effacer toutes les clés en cache, utilisez l'action "--wipe" . Pour supprimer une ou plusieurs clés privées SSH individuelles en cache, utilisez l'option "--ssh-rm" keyfile .

L'option "--stop" n'arrêtera maintenant que les processus ssh-agent en cours d'exécution, et prend toujours en charge trois options possibles : "mine", "others" et "all". Elle n'arrête plus les processus gpg-agent, qui ont tendance à être relancés automatiquement par les outils GPG, de sorte que tuer gpg-agent n'a généralement pas beaucoup de sens.

MEILLEURE INTÉGRATION DE GNUPG

Keychain peut maintenant utiliser un gpg-agent existant qui a été démarré dans votre environnement pour stocker des clés ssh, plutôt que de lancer son propre ssh-agent, en utilisant l'option "--ssh-allow-gpg" .

Si vous souhaitez que keychain lance gpg-agent au lieu de ssh-agent, et l'utilise pour stocker des clés SSH, spécifiez l'option "--ssh-spawn-gpg".

Sans l'une ou l'autre option, keychain n'utilisera pas un SSH_AUTH_SOCK fourni par gpg-agent, et lancera un processus ssh-agent officiel.

De plus, en coulisses, keychain utilise maintenant l'exécutable gpg-connect-agent pour redémarrer l'agent, obtenir les informations officielles de PID et de socket, etc.

Veuillez noter que bien que gpg-agent offre une compatibilité complète avec ssh-agent, son invite de mot de passe est gérée par pinentry et son magasin peut chiffrer vos clés en mémoire. Pour cette raison, considérez cette nouvelle fonctionnalité comme expérimentale, et utilisez les tickets GitHub pour signaler toute anomalie ou amélioration suggérée pour l'intégration de gpg-agent.

CHANGEMENTS D'AFFICHAGE

Lorsque keychain utilise gpg-agent pour le support GnuPG ou SSH, keychain affichera le fichier socket GnuPG dans sa sortie, plutôt que le PID. Puisque le fichier socket contient le chemin ~/.gnupg , cela vous communique que gpg-agent, et non ssh-agent, est actif. Si vous voyez un PID entier, cela signifie que ssh-agent est utilisé.

DÉMARRAGE RATIONALISÉ

Par défaut, keychain s'assurera toujours qu'un ssh-agent doit être démarré. Il ne démarrera un gpg-agent que si une clé GPG est référencée sur la ligne de commande.

Les versions modernes de gpg-agent prennent également en charge la mise en cache des clés SSH, ce qui lui permet d'être un remplacement direct pour ssh-agent. Avec keychain 2.9.0, une nouvelle option "--ssh-spawn-gpg" a été ajoutée, qui, lorsqu'elle est spécifiée, donnera à keychain la permission de lancer un gpg-agent à la place de ssh-agent.

OPTIMISATION DU CODE

Avec keychain 2.9.0, il y a eu un nettoyage de code significatif, réduisant la taille du script de 1500 lignes à environ 1100 lignes. De plus, le script est maintenant entièrement conforme à ShellCheck https://shellcheck.net, ce qui sera énormément utile pour assurer une compatibilité continue avec les shells POSIX à l'avenir.

ALGORITHME DE DÉTECTION ET DE DÉMARRAGE DE L'AGENT

Cette section documente l'algorithme officiel utilisé pour détecter et, si nécessaire, démarrer ssh-agent, afin de faciliter la compréhension ainsi que la maintenance du code par les développeurs.

DÉFINITIONS

Il existe plusieurs définitions importantes liées à l'algorithme :

1. L' agent, "ssh-agent", qui est un daemon à longue durée de vie. Cela peut aussi être "gpg-agent" dans certains cas, selon les options de ligne de commande.
2. L' agent hérité, qui est l'agent ou l'agent transféré qui n'a pas été démarré par keychain, mais qui est détecté dans l'environnement ou par d'autres moyens.
3. L' agent adopté, qui est un agent hérité dont les informations ont été persistées en étant écrites dans les pidfiles (voir ci-dessous).
4. Les variables d'environnement "SSH_AUTH_SOCK", qui pointe vers le fichier socket utilisé pour communiquer avec ssh-agent, et éventuellement "SSH_AGENT_PID", qui indique son ID de processus s'il s'exécute localement (bien que gpg-agent ne définisse pas "SSH_AGENT_PID", même s'il s'exécute localement.)
5. Le fichier ~/.keychain/${HOSTNAME}-sh et les fichiers associés, qui sont collectivement désignés sous le nom de "pidfiles". Les pidfiles sont utilisés pour stocker de manière persistante les environnements "SSH_AUTH_SOCK" et "SSH_AGENT_PID"

NAME

keychain

manage ssh-agent(1) and other agents

SYNOPSIS

keychain [options] [key...]

DESCRIPTION

The keychain utility is a helper script that is intended to simplify the process of managing ssh-agent(1) and gpg-agent(1) keys, and to automate the process of starting and adding keys to the running agent. Keychains maintains a pidfile for each agent type, in a standard location (~/.keychain/), which helps it to manage the agent, and to determine if it has already been started. Once started, keychain will then make environment variables, that are necessary to use the agent, available to your shell.

The script has been designed to integrate well with shell startup files, such as ~/.bash_profile, ~/.zprofile, and so forth. It works by printing shell commands to stdout, that can then be evaluated in the current shell using the `eval` shell command.

The following features are available:

Agent detection:
The script detects running ssh-agent and gpg-agent processes using information stored in pidfiles. If no agent is running, then it automatically starts one.
Key adding:
Keys are added to the agent using the ssh-add(1) utility. By default, keychain automatically adds keys found in ~/.ssh that are not passphrase protected. Keys that are passphrase protected can be added with the --confirm option.
Key management:
keychain can automatically add keys from a user's ~/.ssh/config file, as well as supporting explicit specification of keys on the command line.
Environment variables:
keychain prints shell commands to stdout for setting the SSH_AUTH_SOCK and SSH_AGENT_PID environment variables. These commands can be evaluated in the current shell using the `eval` shell command.
Script management:
keychain can also generate shell scripts for use by other scripts, as well as by keychain itself, formatted so that they can be "sourced" by shells of various types.
Command-line options:
Relevant command-line options affecting behavior, which include --noinherit, --ssh-allow-gpg, --ssh-spawn-gpg, and --ssh-allow-forwarded.

ALGORITHM OVERVIEW

When the keychain script is run, it will first attempt to find a running ssh-agent.

Phase 1: pidfile: To do this, it will first look for an existing pidfile. If one exists, it will be inspected and used to find a running agent, in alignment with specified command-line options. If this process is successful, a "keychain-spawned" agent is found and this process is complete. Otherwise, we continue to the next step.
Phase 2: environment: If keychain's pidfile did not yield a running agent, keychain looks at environment variables defined in the current environment. This step will be skipped if the --noinherit option is specified. If an agent is found that is in alignment with specified command-line options, it is considered "inherited" by keychain, and the process is complete. Otherwise, we continue to the next step.
Phase 3: spawn agent: In the absence of finding a keychain-spawned or existing agent that can be adopted, keychain will spawn a new ssh-agent, or a new gpg-agent if --ssh-spawn-gpg is specified and gpg-agent is available.
Final Phase: update pidfile: In addition, the pidfiles will be updated to reflect the keychain-spawned or "inherited" agent. An "inherited" agent, once written to the pidfile, is now considered to be "adopted".
Pidfile update exception: If the --ssh-allow-forwarded option was specified, and a forwarded SSH socket was found -- which is identified as a valid SSH socket defined in a "SSH_AUTH_SOCK" variable, which has no associated or valid "SSH_AGENT_PID" also defined in the environment and is also determined to not be the socket of any running gpg-agent -- then this agent will simply be used, but not persisted in any pidfile. This is because this SSH-supplied socket will disappear when the underlying SSH connection terminates, and thus it cannot be relied on to be available persistently.

THE QUICK SHORT-CIRCUIT

When the --quick option is specified, a special algorithm will run prior to the main agent-detection algorithm listed above. A pidfile, if it exists, will be evaluated as per Phase 1 of the main algorithm. If a valid running agent is found, it will be queried for valid keys. If at least one valid key is loaded into the agent, the quick start is considered successful, and keychain will skip the regular agent startup algorithm, and will use this found agent.

SUMMARY AND RATIONALE

The keychain ssh-agent detection and startup algorithm is somewhat sophisticated for a reason. There is an intention behind its behavior.

The algorithm has been specifically designed to prefer an agent spawned by keychain, or previously adopted, if that agent is currently available. This is by design, because other system software could spawn ssh-agent and/or gpg-agent processes, and we want keychain to not coerced into using these new agents which may suddenly appear in the environment unexpectedly when new desktop sessions start and in other circumstances. If keychain is too "suggestible", it will lose track of the agent which currently holds valid keys, which can result in unnecessary prompting for passphrases, and general confusion.

OPTIONS

--absolute
This option can be used with the --dir option, if you would like to specify a non-default directory to store pidfiles (defaults to ~/.keychain). When this option is used, the script does not automatically append /.keychain to the path, allowing you to use any arbitrary directory name for the storing of pidfiles. Please note that Keychain 2.9.3 adds some extra security checks related to directory and file permissions -- you must have exclusive ownership of any directory that keychain uses to store pidfiles, or keychain will abort.
--clear
When specified, this option adds an initial step prior to adding any keys to the agents of wiping all existing cached keys/passphrases. This is intended to be used alongside keychain --eval to ensure that only the specified keys are loaded, and that keychain should assume that you are an intruder until proven otherwise and force all interactive logins to specify valid passphrases. This option increases security and still allows your cron jobs to use your ssh keys when you're logged out.
--confallhosts
In addition to any keys specified on the command-line, this option will tell keychain to scour ~/.ssh/config for all private keys referenced in all "IdentityFile" lines, and load all keys for all hosts.
--confirm
Keys are subject to interactive confirmation by the SSH_ASKPASS program before being used for authentication. See the -c option for ssh-add(1).
--debug
Keychain 2.9.0 introduces the --debug option, which will output additional information related to how Keychain makes its agent-selection process. Specifically, it will output when an SSH_AUTH_SOCK is rejected because it is being supplied by gpg-agent -- and this is not allowed due to no --ssh-allow-gpg option, or when it is rejected because it appears to be from a forwarded SSH connection, and --ssh-allow-forwarded was not supplied.
--dir dirname
This option allows you to use another directory besides $HOME/.keychain for the storing of pidfiles. Please note that Keychain 2.9.3 adds some extra security checks related to directory and file permissions -- you must have exclusive ownership of any directory that keychain uses to store pidfiles, or the script will abort. Also see the --absolute option.
--env filename
After parsing options, keychain will load additional environment settings from "filename". By default, if "--env" is not given, then keychain will attempt to load from ~/.keychain/[hostname]-env or alternatively ~/.keychain/env. The purpose of this file is to override settings such as PATH, in case ssh is stored in a non-standard place.
--eval
Keychain will print lines to be evaluated in the shell on stdout. It respects the SHELL environment variable to determine if Bourne shell or C shell output is expected.
--extended
This enables extended command-line key processing with more features, and is a replacement for the old "--confhost" option. When specified, each key specified on the command-line must have a prefix to explicitly categorize it. SSH keys must have a prefix of "sshk:" immediately followed by the path or key name (the part after the "sshk:" is processed just like a SSH key is without the "--extended" option). GPG keys must be in the format "gpgk:" immediately followed by the 8 or 16-character fingerprint. If "host:<hostname>" is specified, then Keychain will extract the SSH configuration for the specified hostname, grab all identityfile options (private keys) specified, and these keys will be included in the set of keys to be loaded by keychain. This allows multiple keys of multiple types, including SSH-keys-by-host, to be specified together, which wasn't possible with "--confhost".
--gpg2
This option changes the default gpg calls to use gpg2 instead to support distributions such as Ubuntu which has both gpg and gpg2
-h --help
Show help that looks remarkably like this man-page. As of 2.6.10, help is sent to stdout so it can be easily piped to a pager.
--host name
Set alternate hostname for creation of pidfiles
--ignore-missing
Don't warn if some keys on the command-line can't be found. This is useful for situations where you have a shared .bash_profile, but your keys might not be available on every machine where keychain is run.
-l --list
List signatures of all active SSH keys, and exit, similar to "ssh-add -l".
-L --list-fp
List fingerprints of all active SSH keys, and exit, similar to "ssh-add -L".
--lockwait seconds
How long to wait for the lock to become available. Defaults to 5 seconds. Specify a value of zero or more. If the lock cannot be acquired within the specified number of seconds, then this keychain process will forcefully acquire the lock.
--noask
This option tells keychain do everything it normally does (ensure ssh-agent is running, set up the ~/.keychain/[hostname]-{c}sh files) except that it will not prompt you to add any of the keys you specified if they haven't yet been added to ssh-agent.
--nocolor
Disable color highlighting for non ANSI-compatible terms.

OPTIONS

--nogui
Ignore SSH_ASKPASS, s'il est défini. Cela obligera ssh-add à demander sur le terminal au lieu d'utiliser un programme graphique.
--noinherit
N'hérite d'aucun processus d'agent, ignorant le comportement par défaut qui consiste à hériter de tous les processus ssh-agent non transférés et de tous les processus gpg-agent existants. Voir également "ALGORITHME DE DÉTECTION ET DE DÉMARRAGE D'AGENT".
--nolock
N'essaie pas d'utiliser un fichier de verrouillage lors de la manipulation des fichiers, des PID et des clés.
--query
Keychain affichera des lignes au format CLÉ=valeur représentant les valeurs définies par les agents.
-Q --quick
Si un processus ssh-agent est en cours d'exécution, utilisez-le. Ne vérifiez pas la liste des clés, autre que de s'assurer qu'elle n'est pas vide. Cette option évite le verrouillage lorsque c'est possible, afin que plusieurs terminaux puissent être ouverts simultanément sans attendre les uns les autres. Voir la section "LE COURT-CIRCUIT RAPIDE" pour plus d'informations sur la façon dont cela s'intègre dans l'algorithme de démarrage global.
-q --quiet
N'affichez des messages qu'en cas d'avertissement, d'erreur ou d'interactivité requise. Depuis la version 2.6.10, cela supprime également les messages "Identités ajoutées" pour ssh-agent.
-k --stop which
Arrête les processus ssh-agent en cours d'exécution et quitte.

Notez que les versions précédentes de keychain (2.8.5 et antérieures) permettaient également d'arrêter gpg-agent. Cette fonctionnalité a été supprimée car ssh-agent et gpg-agent ont des philosophies de conception légèrement différentes et vous n'avez presque toujours qu'un seul gpg-agent en cours d'exécution à la fois. Utilisez "killall gpg-agent" si vous voulez vraiment arrêter gpg-agent. Cependant, comme cette option supprime également les fichiers PID, elle supprimera tous les processus gpg-agent adoptés par keychain qui étaient utilisés pour stocker des clés SSH.

Les valeurs suivantes sont valides pour "which", qui contrôle quels ssh-agents cibler :

all
Arrête tous les processus ssh-agent et quitte keychain immédiatement. Avant keychain-2.5.0, c'était le comportement de l'option nue "--stop".
others
Arrête les processus d'agent autres que ceux fournis par keychain. Avant keychain-2.5.0, keychain le faisait automatiquement. Le nouveau comportement nécessite que vous le spécifiiez explicitement si vous le souhaitez.
mine
Arrête les processus d'agent de keychain, en laissant les autres agents intacts.
--ssh-agent-socket path
Utilisez cette option pour spécifier le chemin du fichier socket que vous souhaitez que ssh-agent crée et utilise comme socket officiel. Par défaut, ssh-agent créera son propre fichier socket, généralement dans /tmp.
--ssh-allow-forwarded
Par défaut, keychain n'utilisera pas une connexion ssh-agent transférée, qui est un socket ssh-agent créé par SSH et n'ayant aucun processus local associé. Pour permettre à keychain d'utiliser une connexion ssh-agent transférée, spécifiez cette option. Si un socket transféré SSH est utilisé, il ne sera pas persistant dans les fichiers PID, car il n'est probablement pas disponible en dehors de la session SSH actuellement active.
--ssh-allow-gpg
Souhaitez-vous que keychain utilise un gpg-agent déjà en cours d'exécution pour stocker vos clés SSH, plutôt que d'en lancer un nouveau ? Cette option fait exactement cela. Lorsque cette option est spécifiée, keychain acceptera une variable d'environnement SSH_AUTH_SOCK dans son environnement, même si elle a été créée par gpg-agent. Les versions modernes de gpg-agent sont également capables de stocker des clés SSH. Par défaut, keychain a une vérification spéciale pour éviter d'utiliser un gpg-agent qui a défini la variable d'environnement SSH_AUTH_SOCK, et lancera plutôt son propre ssh-agent. Avec cette option activée, cette restriction est désactivée. Veuillez noter que cette option n'instruit pas keychain de lancer un gpg-agent pour stocker des clés SSH s'il n'y a pas d'agent disponible -- si vous voulez cela, voir l'option --ssh-spawn-gpg, ci-dessous.

NOTE ÉGALEMENT : Lorsqu'un gpg-agent est adopté pour les tâches ssh-agent de cette manière, le fichier PID ~/.keychain/${HOSTNAME}-sh sera mis à jour pour référencer le socket gpg-agent, afin qu'il soit utilisé de manière transparente par les futurs travaux cron nécessitant un ssh-agent, ainsi que par les futures invocations de keychain, tant que --ssh-allow-gpg ou --ssh-spawn-gpg (qui implique --ssh-allow-gpg) sont spécifiés.

--ssh-spawn-gpg
C'est l'option à utiliser si vous êtes vraiment favorable à l'utilisation de gpg-agent comme remplaçant de ssh-agent. Non seulement keychain utilisera un gpg-agent en cours d'exécution s'il en trouve un, comme avec --ssh-allow-gpg, mais s'il doit lancer un nouveau ssh-agent, il lancera un gpg-agent à sa place et l'utilisera à la place. Voir également les notes pour l'option --ssh-allow-gpg, car cette option implique également --ssh-allow-gpg.
--ssh-rm -r keys
Effectue uniquement l'action unique de suppression des clés mises en cache spécifiées de ssh-agent en cours d'exécution, puis quitte.
--systemd
Injecte des variables d'environnement dans la session utilisateur systemd.
--timeout minutes
Permet de définir un délai d'expiration pour les identités ajoutées à ssh-agent. Lorsque cette option est utilisée avec une invocation de keychain qui démarre ssh-agent lui-même, keychain utilise l'option appropriée de ssh-agent pour définir le délai d'expiration par défaut pour ssh-agent. L'option --timeout est également transmise aux invocations de ssh-add, de sorte que toutes les clés ajoutées à un ssh-agent en cours d'exécution seront configurées individuellement pour avoir le délai d'expiration spécifié, écrasant tout défaut de ssh-agent.

La plupart des utilisateurs peuvent simplement utiliser le délai d'expiration souhaité et obtenir le résultat voulu -- toutes les identités ayant le délai d'expiration spécifié, qu'elles aient été ajoutées par keychain ou non. Les utilisateurs plus avancés peuvent utiliser une seule invocation de keychain pour définir le délai d'expiration par défaut, et facultativement définir des délais d'expiration différents pour les clés ajoutées en utilisant une invocation ultérieure de keychain.

-V --version
Affiche les informations de version.
--wipe which
Effectue uniquement l'action unique de suppression de toutes les clés mises en cache de l'agent. Spécifiez 'ssh', 'gpg' ou 'all' pour les clés SSH, les clés GPG et tous les agents respectivement. Voir également l'action "--ssh-rm" et l'option "--clear".

EXEMPLES

Cet extrait devrait fonctionner dans la plupart des shells pour charger deux clés SSH et une clé GPG :

eval `keychain --eval id_rsa id_dsa 0123ABCD`

Pour le shell fish, utilisez le format suivant :

if status --is-interactive
    keychain --eval --quiet -Q id_rsa | source
end

Si vous rencontrez des problèmes avec cela en csh :

setenv SHELL /bin/csh
eval `keychain --eval id_rsa id_dsa 0123ABCD`

Ceci est équivalent pour les shells Bourne (y compris bash et zsh) mais n'utilise pas la fonctionnalité --eval de keychain :

keychain id_rsa id_dsa 0123ABCD
[ -z "$HOSTNAME" ] && HOSTNAME=`uname -n`
[ -f $HOME/.keychain/$HOSTNAME-sh ] && \
        . $HOME/.keychain/$HOSTNAME-sh

Ceci est équivalent pour le shell C (y compris tcsh) :

keychain id_rsa id_dsa 0123ABCD
host=`uname -n`
if (-f $HOME/.keychain/$host-csh) then
        source $HOME/.keychain/$host-csh
endif

De même, les commandes suivantes peuvent être utilisées en fish :

keychain id_rsa id_dsa 0123ABCD
test -z "$hostname"; and set hostname (uname -n)
if test -f "$HOME/.keychain/$hostname-fish"
    source $HOME/.keychain/$hostname-fish
end

Pour charger les variables keychain depuis un script (par exemple depuis cron) et abandonner à moins que id_dsa ne soit disponible :

# Charger les variables keychain et vérifier id_dsa
[ -z "$HOSTNAME" ] && HOSTNAME=`uname -n`
. $HOME/.keychain/$HOSTNAME-sh 2>/dev/null
ssh-add -l 2>/dev/null | grep -q id_dsa || exit 1
