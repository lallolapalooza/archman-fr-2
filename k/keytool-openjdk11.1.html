DESCRIPTION

La commande keytool est un utilitaire de gestion de clés et de certificats. Elle permet aux utilisateurs de gérer leurs propres paires de clés publique/privée et les chaînes de certificats associées pour l'auto-authentification (où l'utilisateur s'authentifie auprès d'autres utilisateurs et services) ou pour des services d'intégrité et d'authentification des données, à l'aide de signatures numériques. La commande keytool permet également aux utilisateurs de mettre en cache les clés publiques (sous forme de certificats) de leurs pairs communicants.

Un certificat est une déclaration signée numériquement par une entité (personne, entreprise, etc.), indiquant que la clé publique (et d'autres informations) d'une autre entité a une valeur particulière. (Voir Certificat.) Lorsque des données sont signées numériquement, la signature peut être vérifiée pour contrôler l'intégrité et l'authenticité des données. L'intégrité signifie que les données n'ont pas été modifiées ou falsifiées, et l'authenticité signifie que les données proviennent de celui qui prétend les avoir créées et signées.

La commande keytool permet également aux utilisateurs de gérer des clés secrètes et des mots de passe utilisés dans le chiffrement et le déchiffrement symétriques (DES).

La commande keytool stocke les clés et les certificats dans un magasin de clés. Voir Alias de magasin de clés.

NOTES SUR LES COMMANDES ET LES OPTIONS

Voir Commandes pour une liste et une description des diverses commandes.

•
Tous les noms de commandes et d'options sont précédés d'un signe moins (-).
•
Les options pour chaque commande peuvent être fournies dans n'importe quel ordre.
•
Tous les éléments qui ne sont pas en italique ou entre accolades ou crochets doivent apparaître tels quels.
•
Les accolades entourant une option signifient qu'une valeur par défaut sera utilisée lorsque l'option n'est pas spécifiée sur la ligne de commande. Voir Valeurs par défaut des options. Les accolades sont également utilisées autour des options -v, -rfc et -J, qui n'ont de sens que lorsqu'elles apparaissent sur la ligne de commande. Elles n'ont pas de valeurs par défaut autres que leur absence.
•
Les crochets entourant une option signifient que l'utilisateur est invité à fournir les valeurs lorsque l'option n'est pas spécifiée sur la ligne de commande. Pour l'option -keypass, si vous ne spécifiez pas l'option sur la ligne de commande, alors la commande keytool tente d'abord d'utiliser le mot de passe du magasin de clés pour récupérer la clé privée/secrète. Si cette tentative échoue, alors la commande keytool vous invite à entrer le mot de passe de la clé privée/secrète.
•
Les éléments en italique (valeurs d'option) représentent les valeurs réelles qui doivent être fournies. Par exemple, voici le format de la commande -printcert : 
keytool -printcert {-file cert_file} {-v}

Lorsque vous spécifiez une commande -printcert, remplacez cert_file par le nom de fichier réel, comme suit : keytool -printcert -file VScert.cer

•
Les valeurs d'option doivent être mises entre guillemets lorsqu'elles contiennent un espace.
•
L'option -help est la valeur par défaut. La commande keytool est la même que keytool -help.

OPTIONS COMMUNES

L'option -v peut apparaître pour toutes les commandes sauf -help. Lorsque l'option -v apparaît, elle signifie le mode verbeux, ce qui signifie que plus d'informations sont fournies dans la sortie.

Il existe également un argument -Jjavaoption qui peut apparaître pour n'importe quelle commande. Lorsque -Jjavaoption apparaît, la chaîne javaoption spécifiée est passée directement à l'interpréteur Java. Cette option ne contient aucun espace. Elle est utile pour ajuster l'environnement d'exécution ou l'utilisation de la mémoire. Pour une liste des options d'interpréteur possibles, tapez java -h ou java -X à la ligne de commande.

Ces options peuvent apparaître pour toutes les commandes opérant sur un magasin de clés :

-storepass[:env| :file] argument

Le mot de passe utilisé pour protéger l'intégrité du magasin de clés.

Si le modificateur env ou file n'est pas spécifié, alors le mot de passe a l'argument valeur, qui doit avoir au moins 6 caractères. Sinon, le mot de passe est récupéré comme suit :

•
env : Récupérer le mot de passe de la variable d'environnement nommée argument.
•
file : Récupérer le mot de passe du fichier nommé argument.

Note : Toutes les autres options nécessitant des mots de passe, telles que -keypass, -srckeypass, -destkeypass, -srcstorepass et -deststorepass, acceptent les modificateurs env et file. N'oubliez pas de séparer l'option de mot de passe et le modificateur par un deux-points (:).

Le mot de passe doit être fourni à toutes les commandes qui accèdent au contenu du magasin de clés. Pour de telles commandes, lorsque l'option -storepass n'est pas fournie sur la ligne de commande, l'utilisateur est invité à la saisir.

Lors de la récupération d'informations à partir du magasin de clés, le mot de passe est facultatif. Si aucun mot de passe n'est spécifié, l'intégrité des informations récupérées ne peut pas être vérifiée et un avertissement est affiché.

Soit vrai, soit faux. Cette valeur doit être spécifiée comme vrai lorsqu'un mot de passe doit être spécifié par le biais d'un chemin d'authentification protégé tel qu'un lecteur de carte à puce dédié. Comme deux magasins de clés sont impliqués dans la commande -importkeystore, les deux options suivantes -srcprotected et -destprotected sont fournies pour le magasin source et le magasin de destination respectivement.
-ext {nom{:critique} {=valeur}}

Désigne une extension de certificat X.509. L'option peut être utilisée dans -genkeypair et -gencert pour incorporer des extensions dans le certificat généré, ou dans -certreq pour indiquer les extensions demandées dans la demande de certificat. L'option peut apparaître plusieurs fois. L'argument nom peut être un nom d'extension pris en charge (voir Extensions nommées) ou un numéro OID arbitraire. L'argument valeur, lorsqu'il est fourni, désigne l'argument de l'extension. Lorsque valeur est omis, cela signifie que la valeur par défaut de l'extension ou que l'extension ne nécessite aucun argument. Le modificateur :critique, lorsqu'il est fourni, signifie que l'attribut isCritical de l'extension est vrai ; sinon, il est faux. Vous pouvez utiliser :c à la place de :critique.

EXTENSIONS NOMMÉES

La commande keytool prend en charge ces extensions nommées. Les noms ne sont pas sensibles à la casse).

BC ou BasicContraints
Valeurs : La forme complète est : ca:{vrai|faux}[,pathlen:<len>] ou <len>, ce qui est une abréviation pour ca:vrai,pathlen:<len>. Lorsque <len> est omis, vous obtenez ca:vrai.
KU ou KeyUsage
Valeurs : usage(,usage)*, où usage peut être l'un des digitalSignature, nonRepudiation (contentCommitment), keyEncipherment, dataEncipherment, keyAgreement, keyCertSign, cRLSign, encipherOnly, decipherOnly. L'argument usage peut être abrégé avec les premières lettres (dig pour digitalSignature) ou en style camelCase (dS pour digitalSignature ou cRLS pour cRLSign), tant qu'aucune ambiguïté n'est trouvée. Les valeurs usage sont sensibles à la casse.
EKU ou ExtendedKeyUsage
Valeurs : usage(,usage)*, où usage peut être l'un des anyExtendedKeyUsage, serverAuth, clientAuth, codeSigning, emailProtection, timeStamping, OCSPSigning, ou une chaîne OID. L'argument usage peut être abrégé avec les premières lettres ou en style camelCase, tant qu'aucune ambiguïté n'est trouvée. Les valeurs usage sont sensibles à la casse.
SAN ou SubjectAlternativeName
Valeurs : type:valeur(,type:valeur)*, où type peut être EMAIL, URI, DNS, IP, ou OID. L'argument valeur est la valeur au format chaîne pour le type.
IAN ou IssuerAlternativeName
Valeurs : Identique à SubjectAlternativeName.
SIA ou SubjectInfoAccess
Valeurs : méthode:type_emplacement:valeur_emplacement (,méthode:type_emplacement:valeur_emplacement)*, où méthode peut être timeStamping, caRepository ou tout OID. Les arguments type_emplacement et valeur_emplacement peuvent être tout type:valeur pris en charge par l'extension SubjectAlternativeName.
AIA ou AuthorityInfoAccess
Valeurs : Identique à SubjectInfoAccess. L'argument méthode peut être ocsp, caIssuers, ou tout OID.

Lorsque nom est un OID, la valeur est l'encodage DER en hexadécimal de extnValue pour l'extension, à l'exclusion des octets de type et de longueur OCTET STRING. Tout caractère supplémentaire autre que les nombres hexadécimaux standard (0-9, a-f, A-F) est ignoré dans la chaîne HEX. Par conséquent, 01:02:03:04 et 01020304 sont acceptés comme des valeurs identiques. Lorsqu'il n'y a pas de valeur, l'extension a un champ de valeur vide.

Un nom spécial honored, utilisé uniquement dans -gencert, indique comment les extensions incluses dans la demande de certificat doivent être honorées. La valeur de ce nom est une liste d'éléments séparés par des virgules : all (toutes les extensions demandées sont honorées), nom{:[critique|non-critique]} (l'extension nommée est honorée, mais en utilisant un attribut isCritical différent) et -nom (utilisé avec all, désigne une exception). Les extensions demandées ne sont pas honorées par défaut.

Si, en plus de l'option -ext honored, une autre option nommée ou OID -ext est fournie, cette extension est ajoutée à celles déjà honorées. Cependant, si ce nom (ou OID) apparaît également dans la valeur honorée, sa valeur et sa criticité remplacent celle de la demande.

L'extension subjectKeyIdentifier est toujours créée. Pour les certificats non auto-signés, l'extension authorityKeyIdentifier est créée.

Note : Les utilisateurs doivent être conscients que certaines combinaisons d'extensions (et d'autres champs de certificat) peuvent ne pas être conformes aux normes Internet. Voir Avertissement de conformité des certificats.

NAME
keytool




SYNOPSIS

keytool [options]
keytool -command [command options] [-Jjavaoption]





DESCRIPTION


The keytool utility is a keystore management tool.
It facilitates the management of a repository of keys and certificates,
called a keystore. The keys and certificates are mapped to aliases (strings).
The keystore can contain private keys, associated public-key certificates
and a "trusted certificate" chain, allowing an entity to import and export
digital certificates.


keytool is also used to generate new keys, to
import and export keys, to generate certificate signing requests (CSRs),
and to list or manipulate the entries in a keystore.


The keytool options are described in the following
sections:

-genkeypair

Generates a public/private key pair and stores it in the
keystore. The public key is contained in a self-signed certificate.


The key pair is generated using the public-key algorithm specified
by keyalg. The default is RSA. The keysize is specified by keysize.
The default is 2048.


The signing algorithm is specified by sigalg. The default
is SUN.java.security.Signature.SHA256withRSA.


The X.500 distinguished name is specified by dname.
For example: "CN=Fred, OU=Java, O=Sun, C=US".


The certificate is valid for the number of days specified by
validity. The default is 90.


If the keypass is not provided at the command line and
is different from the password used to protect the integrity of the keystore,

Imports a single entry or all entries from a source keystore
to a destination keystore.


When the -srcalias option is provided, the command
imports the single entry identified by the alias to the destination
keystore. If a destination alias is not provided with destalias,
then srcalias is used as the destination alias. If the source
entry is protected by a password, then srckeypass is used to
recover the entry. If srckeypass is not provided, then the
keytool command attempts to use srcstorepass to recover
the entry. If srcstorepass is either not provided or is
incorrect, then the user is prompted for a password. The destination
entry is protected with destkeypass. If destkeypass is not
provided, then the destination entry is protected with the source entry
password. For example, most third-party tools require storepass
and keypass in a PKCS #12 keystore to be the same. In order to
create a PKCS #12 keystore for these tools, always specify a
-destkeypass to be the same as -deststorepass.


If the -srcalias option is not provided, then all
entries in the source keystore are imported into the destination
keystore. Each destination entry is stored under the alias from the
source entry. If the source entry is protected by a password, then
srcstorepass is used to recover the entry. If srcstorepass
is either not provided or is incorrect, then the user is prompted for a
password. If a source keystore entry type is not supported in the
destination keystore, or if an error occurs while storing an entry into
the destination keystore, then the user is prompted whether to skip the
entry and continue or to quit. The destination entry is protected with
the source entry password.


If the destination alias already exists in the destination
keystore, then the user is prompted to either overwrite the entry or to
create a new entry under a different alias name.


If the -noprompt option is provided, then the user is

Entrées de certificat de confiance : Chaque entrée contient un certificat de clé publique unique appartenant à une autre partie. L'entrée est appelée certificat de confiance car le propriétaire du magasin de clés

fait confiance au fait que la clé publique dans le certificat appartient à l'identité identifiée par le
sujet (propriétaire) du certificat. L'émetteur du certificat garantit cela en signant le certificat.

Toutes les entrées du magasin de clés (entrées de clé et entrées de certificat de confiance) sont accessibles par le biais d'alias uniques.

Un alias est spécifié lorsque vous ajoutez une entité au magasin de clés avec la commande -genseckey pour générer une clé secrète, la commande -genkeypair pour générer une paire de clés (clé publique et privée) ou la commande -importcert pour ajouter un certificat ou une chaîne de certificats à la liste des certificats de confiance. Les commandes keytool suivantes doivent utiliser ce même alias pour faire référence à

l'entité.

Par exemple, vous pouvez utiliser l'alias duke pour générer une nouvelle paire de clés publique/privée et envelopper la clé publique dans un certificat auto-signé avec la commande suivante. Voir Chaînes de

certificats. 
keytool -genkeypair -alias duke -keypass
dukekeypasswd

Cet exemple spécifie un mot de passe initial de dukekeypasswd requis par les commandes suivantes pour accéder à la clé privée associée à l'alias duke. Si vous souhaitez plus tard changer le mot de passe de la clé privée de Duke, utilisez une commande telle que la

suivante : 
keytool -keypasswd -alias duke -keypass dukekeypasswd -new

Cela change le mot de passe de dukekeypasswd à newpass. Un mot de passe ne doit pas être spécifié sur une ligne de commande ou dans un script, sauf à des fins de test, ou si vous êtes sur un

système sécurisé. Si vous ne spécifiez pas une option de mot de pa
sse requise sur une ligne de commande, vous êtes invité à le saisir.
Implémentation du magasin de
clés
La classe KeyStore fournie dans le paquet java.security fournit des interfaces bien définies pour accéder et modifier les informations dans un magasin de clés. Il est possible qu'il existe plusieurs implémentations concrètes différentes, où chaque implémentation est celle d'un type particulier de magasin de clés.

Actuellement, deux outils en ligne de commande (keytool et jarsigner) et un outil basé sur une interface graphique nommé Policy Tool utilisent les implémentations de magasin de clés. Parce que la classe KeyStore est publique, les utilisateurs peuvent écrire des applications de sécurité supplémentaires qui l'

utilisent.

Il existe une implémentation par défaut intégrée, fournie par Oracle. Elle implémente le magasin de clés sous forme de fichier avec un type de magasin de clés propriétaire (format) nommé JKS. Elle protège chaque clé privée avec son mot de passe individuel, et protège également l'intégrité de l'ensemble du magasin de clés avec un mot de passe (possiblement

différent).

Les implémentations de magasin de clés sont basées sur des fournisseurs. Plus précisément, les interfaces d'application fournies par KeyStore sont implémentées en termes d'Interface de Fournisseur de Service (SPI). C'est-à-dire, qu'il existe une classe abstraite correspondante KeystoreSpi, également dans le paquet java.security, qui définit les méthodes de l'Interface de Fournisseur de Service que les fournisseurs doivent implémenter. Le terme fournisseur fait référence à un paquet ou à un ensemble de paquets qui fournissent une implémentation concrète d'un sous-ensemble de services pouvant être accessibles par l'API de sécurité Java. Pour fournir une implémentation de magasin de clés, les clients doivent implémenter un fournisseur et fournir une implémentation de sous-classe KeystoreSpi, comme décrit dans Comment implémenter un fournisseur dans l'architecture de cryptographie Java à l'adresse http://docs.oracle.com/javase/8/docs/technotes/guides/security/crypto/HowToImplAProvider.

html

Les applications peuvent choisir différents types d'implémentations de magasin de clés provenant de différents fournisseurs, en utilisant la méthode factory getInstance fournie dans la classe KeyStore. Un type de magasin de clés définit le stockage et le format des données des informations du magasin de clés, ainsi que les algorithmes utilisés pour protéger les clés privées/secrètes dans le magasin de clés et l'intégrité du magasin de clés. Les implémentations de magasin de clés de types différents ne sont pas

compatibles.

La commande keytool fonctionne avec toute implémentation de magasin de clés basée sur un fichier. Elle traite l'emplacement du magasin de clés qui lui est passé à la ligne de commande comme un nom de fichier et le convertit en un FileInputStream, à partir duquel elle charge les informations du magasin de clés.)La commande jarsigner peut lire un magasin de clés depuis n'importe quel emplacement pouvant être spécifié avec

une URL.

Pour keytool et jarsigner, vous pouvez spécifier un type de magasin de clés à la ligne de commande, avec l' option -storetype. Pour Policy Tool, vous pouvez spécifier un type de magasin de clés avec le menu Keys

tore.

Si vous ne spécifiez pas explicitement un type de magasin de clés, les outils choisissent une implémentation de magasin de clés en fonction de la valeur de la propriété keystore.type spécifiée dans le fichier de propriétés de sécurité. Le fichier de propriétés de sécurité est appelé java.security et se trouve dans le répertoire des propriétés de sécurité, java.home\lib\security sous Windows et java.home/lib/security sous Oracle Solaris, où java.home est le répertoire de l'environnement d'exécution. Le répertoire jre dans le SDK ou le répertoire de premier niveau de l'Environnement d'Exécution Java

(JRE).

Chaque outil obtient la valeur keystore.type puis examine tous les fournisseurs actuellement installés jusqu'à ce qu'il en trouve un qui implémente un magasin de clés de ce type. Il utilise ensuite l'implémentation de magasin de clés de ce fournisseur.La classe KeyStore définit une méthode statique nommée getDefaultType qui permet aux applications et aux applets de récupérer la valeur de la propriété keystore.type. La ligne de code suivante crée une instance du type de magasin de clés par défaut tel que spécifié dans la propriété keystore.

type :

sécurité :

Par exemple, si vous disposez d'un paquet de fournisseur qui fournit une implémentation de keystore pour un type de keystore appelé pkcs12, alors modifiez la ligne comme

suit : 
keystore.

Remarque : la casse n'a pas d'importance dans les désignations de type de keystore. Par exemple, JKS serait considéré comme identique

à
jks.

Un certificat (ou certificat de clé publique) est une déclaration signée numériquement provenant d'une entité (l'émetteur), affirmant que la clé publique et certaines autres informations d'une autre entité (le sujet) ont une valeur spécifique. Les termes suivants sont liés aux certificats :

Clés publiques : ce sont des nombres associés à une entité particulière, et destinés à être connus de tous ceux qui doivent avoir des interactions de confiance avec cette entité. Les clés publiques sont utilisées pour vérifier les

signatures.

Signé numériquement : si des données sont signées numériquement, elles sont stockées avec l'identité d'une entité et une signature qui prouve que cette entité connaît les données. Les données sont rendues infalsifiables en les signant avec la clé privée de

l'entité.

Identité : une manière connue d'adresser une entité. Dans certains systèmes, l'identité est la clé publique, et dans d'autres, elle peut être n'importe quoi, depuis un UID Oracle Solaris jusqu'à une adresse e-mail ou un nom distinctif

X.509.

Signature : une signature est calculée sur certaines données en utilisant la clé privée d'une entité. Le signataire, qui dans le cas d'un certificat est aussi appelé

l'émetteur.

Clés privées : ce sont des nombres, dont chacun ne doit être connu que de l'entité particulière dont il s'agit de la clé privée (c'est-à-dire qu'il doit rester secret). Les clés privées et publiques existent en paires dans tous les systèmes de cryptographie à clé publique (aussi appelés systèmes cryptographiques à clé publique). Dans un système cryptographique à clé publique typique, tel que DSA, une clé privée correspond à exactement une clé publique. Les clés privées sont utilisées pour calculer les

signatures.

Entité : une entité est une personne, une organisation, un programme, un ordinateur, une entreprise, une banque, ou autre chose à laquelle vous accordez un certain degré de

confiance.

La cryptographie à clé publique nécessite l'accès aux clés publiques des utilisateurs. Dans un environnement réseau à grande échelle, il est impossible de garantir que des relations antérieures entre les entités communicantes ont été établies ou qu'un référentiel de confiance existe avec toutes les clés publiques utilisées. Les certificats ont été inventés comme solution à ce problème de distribution de clés publiques. Désormais, une autorité de certification (CA) peut agir comme tiers de confiance. Les CA sont des entités telles que des entreprises qui sont habilitées à signer (émettre) des certificats pour d'autres entités. On suppose que les CA ne créent que des certificats valides et fiables car ils sont liés par des accords légaux. Il existe de nombreuses autorités de certification publiques, telles que VeriSign, Thawte, Entrust,

etc.

Vous pouvez également exploiter votre propre autorité de certification en utilisant des produits tels que Microsoft Certificate Server ou le produit Entrust CA pour votre organisation. Avec la commande keytool, il est possible d'afficher, d'importer et d'exporter des certificats. Il est également possible de générer des certificats

auto-signés.

La commande keytool gère actuellement les certificats

X.
509.
Certificats X.
509
La norme X.509 définit quelles informations peuvent figurer dans un certificat et décrit comment les écrire (le format de données). Toutes les données d'un certificat sont encodées avec deux normes connexes appelées ASN.1/DER. Abstract Syntax Notation 1 décrit les données. Les règles d'encodage définitif décrivent une seule manière de stocker et de transférer ces données.

Tous les certificats X.509 contiennent les données suivantes, en plus de la signature

:

Version : ceci identifie la version de la norme X.509 applicable à ce certificat, ce qui détermine quelles informations peuvent y être spécifiées. À ce jour, trois versions sont définies. La commande keytool peut importer et exporter les certificats v1, v2 et v3. Elle génère des certificats

v3.

X.509 version 1 est disponible depuis 1988, est largement déployée et est la plus

générique.

X.509 version 2 a introduit le concept d'identifiants uniques de sujet et d'émetteur pour gérer la possibilité de réutilisation des noms de sujet ou d'émetteur au fil du temps. La plupart des documents de profil de certificat recommandent fortement que les ne soient pas réutilisés et que les certificats ne doivent pas faire usage d'identifiants uniques. Les certificats de version 2 ne sont pas largement

utilisés.

X.509 version 3 est la plus récente (1996) et prend en charge la notion d'extensions où n'importe qui peut définir une extension et l'inclure dans le certificat. Certaines extensions courantes sont : KeyUsage (limite l'utilisation des clés à des fins particulières telles que signature seule) et AlternativeNames (permet à d'autres identités d'être également associées à cette clé publique, par exemple noms DNS, adresses e-mail, adresses IP). Les extensions peuvent être marquées critiques pour indiquer que l'extension doit être vérifiée et appliquée ou utilisée. Par exemple, si un certificat a l'extension KeyUsage marquée critique et définie sur keyCertSign, alors lorsque ce certificat est présenté lors d'une communication SSL, il doit être rejeté car l'extension du certificat indique que la clé privée associée ne doit être utilisée que pour signer des certificats et pas pour

SSL.

Numéro de série : l'entité qui a créé le certificat est responsable de lui attribuer un numéro de série pour le distinguer des autres certificats qu'elle émet. Ces informations sont utilisées de nombreuses manières. Par exemple, lorsqu'un certificat est révoqué, son numéro de série est placé dans une liste de révocation de certificats

(CRL).

Identifiant d'algorithme de signature : ceci identifie l'algorithme utilisé par la CA pour signer le

certificat.

Nom de l'émetteur : le nom distinctif X.500 de l'entité qui a signé le certificat. Voir Noms distinctifs X.500. Il s'agit généralement d'une CA. L'utilisation de ce certificat implique de faire confiance à l'entité qui a signé ce certificat. Dans certains cas, tels que les certificats de CA racine ou de premier niveau, l'émetteur signe son propre

certificat.

Période de validité : chaque certificat n'est valide que pour une durée limitée. Cette période est décrite par une date et heure de début et une date et heure de fin, et peut être aussi courte que quelques secondes ou presque aussi longue qu'un siècle. La période de validité choisie dépend d'un certain nombre de facteurs, tels que la force de la clé privée utilisée pour signer le certificat, ou le montant que l'on est prêt à payer pour un certificat. C'est la période pendant laquelle les entités peuvent se fier à la valeur publique, lorsque la clé privée associée n'a pas été

compromise.

Nom du sujet : le nom de l'entité dont le certificat identifie la clé publique. Ce nom utilise la norme X.500, il est donc destiné à être unique sur Internet. C'est le nom distinctif (DN) X.500 de l'entité. Voir Noms distinctifs X.500. Par

exemple, 
CN=Java Duke, OU=Java Software Division, O=Oracle Corporation,
C=US

Ceux-ci font référence au nom commun (CN), à l'unité organisationnelle (OU), à l'organisation (O) et au pays (C) du

sujet.

Informations sur la clé publique du sujet : il s'agit de la clé publique de l'entité nommée, avec un identifiant d'algorithme qui

spécifie à quel système cryptographique à clé publique cette
clé appartient et les paramètres de clé associés éventuels.
Chaînes de
certificats
La commande keytool peut créer et gérer des entrées de clé de keystore qui contiennent chacune une clé privée et une chaîne de certificats associée. Le premier certificat de la chaîne contient la clé publique qui correspond à la clé privée.

Lorsque les clés sont d'abord générées, la chaîne commence par contenir un seul élément, un certificat auto-signé. Voir -genkeypair dans Commandes. Un certificat auto-signé est un certificat pour lequel l'émetteur (signataire) est le même que le sujet. Le sujet est l'entité dont la clé publique est authentifiée par le certificat. Chaque fois que la commande -genkeypair est appelée pour générer une nouvelle paire de clés publique/privée, elle enveloppe également la clé publique dans un certificat

auto-signé.

Plus tard, après qu'une demande de signature de certificat (CSR) a été générée avec la commande -certreq et envoyée à une autorité de certification (CA), la réponse de la CA est importée avec -importcert, et le certificat auto-signé est remplacé par une chaîne de certificats. Voir les options -certreq et -importcert dans Commandes. Au bas de la chaîne se trouve le certificat (réponse) émis par la CA authentifiant la clé publique du sujet. Le certificat suivant dans la chaîne est celui qui authentifie la clé publique de

la CA.

Dans de nombreux cas, il s'agit d'un certificat auto-signé, qui est un certificat de la CA authentifiant sa propre clé publique, et le dernier certificat de la chaîne. Dans d'autres cas, la CA peut renvoyer une chaîne de certificats. Dans ce cas, le certificat du bas de la chaîne est le même (un certificat signé par la CA, authentifiant la clé publique de l'entrée de clé), mais le deuxième certificat de la chaîne est un certificat signé par une autre CA qui authentifie la clé publique de la CA à laquelle vous avez envoyé la CSR. Le certificat suivant dans la chaîne est un certificat qui authentifie la clé de la deuxième CA, et ainsi de suite, jusqu'à ce qu'un certificat racine auto-signé soit atteint. Chaque certificat de la chaîne (après le premier) authentifie la clé publique du signataire du certificat précédent dans la

chaîne.

De nombreuses CA ne renvoient que le certificat émis, sans chaîne de soutien, surtout lorsqu'il y a une hiérarchie plate (pas de CA intermédiaires). Dans ce cas, la chaîne de certificats doit être établie à partir des informations de certificats de confiance déjà stockées dans le

keystore.

Un format de réponse différent (défini par la norme PKCS #7) inclut la chaîne de certificats de soutien en plus du certificat émis. Les deux formats de réponse peuvent être gérés par la commande ke

ytool.

Le certificat de CA de premier niveau (racine) est auto-signé. Cependant, la confiance dans la clé publique de la racine ne provient pas du certificat racine lui-même, mais d'autres sources telles qu'un journal. C'est parce que n'importe qui pourrait générer un auto-certificat signé avec le nom distinctif de, par exemple, l'AC racine VeriSign. La clé publique de l'AC racine est largement connue. La seule raison pour laquelle elle est stockée dans un certificat est que c'est le format compris par la plupart des outils, donc le certificat dans ce cas n'est utilisé que comme moyen de transport de la clé publique de l'AC racine. Avant d'ajouter le certificat de l'AC racine à votre magasin de clés, vous devez l'afficher avec l'option -printcert et comparer l'empreinte numérique affichée avec l'empreinte numérique bien connue obtenue à partir d'un journal, de la page Web de l'AC racine, etc.

Le fichier de certificats cacerts
Un fichier de certificats nommé cacerts réside dans le répertoire des propriétés de sécurité, java.home\lib\security sous Windows et java.home/lib/security sous Oracle Solaris, où java.home est le répertoire de l'environnement d'exécution, qui serait le répertoire jre du SDK ou le répertoire de niveau supérieur du JRE.

Le fichier cacerts représente un magasin de clés système avec des certificats d'AC. Les administrateurs système peuvent configurer et gérer ce fichier avec la commande keytool en spécifiant jks comme type de magasin de clés. Le fichier de magasin de clés cacerts est fourni avec un ensemble par défaut de certificats d'AC racine. Vous pouvez lister les certificats par défaut avec la commande suivante :

keytool -list -keystore java.home/lib/security/cacerts

Le mot de passe initial du fichier de magasin de clés cacerts est changeit. Les administrateurs système doivent changer ce mot de passe et la permission d'accès par défaut de ce fichier lors de l'installation du SDK.

Remarque : Il est important de vérifier votre fichier cacerts. Étant donné que vous faites confiance aux AC du fichier cacerts en tant qu'entités pour signer et émettre des certificats à d'autres entités, vous devez gérer le fichier cacerts avec soin. Le fichier cacerts ne doit contenir que les certificats des AC auxquelles vous faites confiance. Il est de votre responsabilité de vérifier les certificats d'AC racine de confiance inclus dans le fichier cacerts et de prendre vos propres décisions de confiance.

Pour supprimer un certificat d'AC non fiable du fichier cacerts, utilisez l'option delete de la commande keytool. Vous pouvez trouver le fichier cacerts dans le répertoire d'installation du JRE. Contactez votre administrateur système si vous n'avez pas la permission de modifier ce fichier.

Norme d'encodage de certificats RFC 1421 de l'Internet
Les certificats sont souvent stockés en utilisant le format d'encodage imprimable défini par la norme RFC 1421 de l'Internet, au lieu de leur encodage binaire. Ce format de certificat, également connu sous le nom d'encodage Base64, facilite l'exportation de certificats vers d'autres applications par courrier électronique ou par un autre mécanisme.

Les certificats lus par les commandes -importcert et -printcert peuvent être dans ce format ou encodés en binaire. La commande -exportcert sort par défaut un certificat en encodage binaire, mais sortira un certificat en format d'encodage imprimable lorsque l'option -rfc est spécifiée.

La commande -list affiche par défaut l'empreinte SHA1 d'un certificat. Si l'option -v est spécifiée, le certificat est affiché dans un format lisible par l'homme. Si l'option -rfc est spécifiée, le certificat est sorti dans le format d'encodage imprimable.

Dans son format d'encodage imprimable, le certificat encodé est délimité au début et à la fin par le texte suivant :

-----BEGIN CERTIFICATE-----
le certificat encodé va ici.
-----END CERTIFICATE-----
Noms distinctifs X.500
Les noms distinctifs X.500 sont utilisés pour identifier des entités, telles que celles qui sont nommées par les champs subject (sujet) et issuer (émetteur) des certificats X.509. La commande keytool prend en charge les sous-parties suivantes :

commonName : Le nom commun d'une personne, tel que Susan Jones.

organizationUnit : Le nom de la petite organisation (tel qu'un département ou une division). Par exemple, Achats.

localityName : Le nom de la localité (ville), par exemple, Palo Alto.

stateName : Nom de l'État ou de la province, par exemple, Californie.

country : Code pays à deux lettres, par exemple, CH.

Lorsque vous fournissez une chaîne de nom distinctif comme valeur d'une option -dname, par exemple pour la commande -genkeypair, la chaîne doit être au format suivant :

CN=nomCommun, OU=unitéOrganisationnelle, O=organisation, L=ville, S=etat, C=codePays

Tous les éléments en italique représentent des valeurs réelles et les mots-clés précédents sont des abréviations pour les suivants :

CN=commonName
OU=organizationUnit
O=organizationName
L=localityName
S=stateName
C=country

Un exemple de chaîne de nom distinctif est :

CN=Mark Smith, OU=Java, O=Oracle, L=Cupertino, S=California, C=US

Un exemple de commande utilisant une telle chaîne est :

keytool -genkeypair -dname "CN=Mark Smith, OU=Java, O=Oracle, L=Cupertino,
S=California, C=US" -alias mark

La casse n'a pas d'importance pour les abréviations de mots-clés. Par exemple, CN, cn et Cn sont traités de la même manière.

L'ordre est important ; chaque sous-composant doit apparaître dans l'ordre désigné. Cependant, il n'est pas nécessaire d'avoir tous les sous-composants. Vous pouvez utiliser un sous-ensemble, par exemple :

CN=Steve Meier, OU=Java, O=Oracle, C=US

Si une chaîne de nom distinctif contient une virgule, alors la virgule doit être échappée par un caractère backslash (\) lorsque vous spécifiez la chaîne dans une ligne de commande, comme dans :

cn=Peter Schuster, ou=Java\, Product Development, o=Oracle, c=US

Il n'est jamais nécessaire de spécifier une chaîne de nom distinctif sur une ligne de commande. Lorsque le nom distinctif est nécessaire pour une commande, mais n'est pas fourni sur la ligne de commande, l'utilisateur est invité pour chacun des sous-composants. Dans ce cas, une virgule n'a pas besoin d'être échappée par un backslash (\).

AVERTISSEMENT RELATIF AUX MOTS DE PASSE

La plupart des commandes qui opèrent sur un magasin de clés nécessitent le mot de passe du magasin. Certaines commandes nécessitent un mot de passe de clé privée/secrète. Les mots de passe peuvent être spécifiés sur la ligne de commande dans le -storepass et -keypass. Cependant, un mot de passe ne doit pas être spécifié sur une ligne de commande ou dans un script, sauf s'il s'agit d'un test, ou si vous êtes s
