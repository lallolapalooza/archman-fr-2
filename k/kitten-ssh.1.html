Nom

kitten-ssh - Documentation de kitten

Aperçu

  • Intégration automatique du shell <#shell-integration> sur les hôtes distants
  • Clonage facile des configurations de shell/éditeur locales sur les hôtes distants
  • Réutilisation automatique des connexions existantes pour éviter la latence de configuration de la connexion
  • Rendre le binaire kitten disponible sur l'hôte distant à la demande
  • Changer facilement les couleurs du terminal lors de la connexion aux hôtes distants
  • Transfert automatique du socket de contrôle distant de kitty vers les hôtes configurés

Ajouté dans la version 0.25.0 : Intégration automatique du shell, transfert de fichiers et réutilisation des connexions

Ajouté dans la version 0.30.0 : Transfert automatique des sockets de contrôle distants

Le kitten ssh vous permet de vous connecter facilement à des hôtes distants et de configurer automatiquement l'environnement pour qu'il soit aussi confortable que votre shell local. Vous pouvez spécifier des variables d'environnement à définir sur l'hôte distant et des fichiers à y copier, rendant votre expérience distante identique à votre shell local. De plus, il configure automatiquement l'intégration du shell <#shell-integration> sur l'hôte distant et y copie la base de données terminfo de kitty.

Le kitten ssh est une fine enveloppe autour du programme de ligne de commande traditionnel ssh https://man.openbsd.org/ssh et prend en charge toutes les mêmes options, arguments et configurations. Dans les scénarios d'utilisation interactive, c'est un remplacement direct pour ssh. Pour l'essayer, exécutez simplement :

kitten ssh nom-hote-a-connecter

Vous devriez vous retrouver à une invite de shell sur l'hôte distant, avec l'intégration du shell activée. Si cela vous plaît, vous pouvez y ajouter un alias dans les fichiers rc de votre shell :

alias s="kitten ssh"

Ainsi, vous pouvez maintenant simplement taper s nomhote pour vous connecter.

Si vous définissez un mappage dans kitty.conf tel que :

map f1 new_window_with_cwd

Alors, appuyer sur F1 ouvrira une nouvelle fenêtre automatiquement connectée au même hôte en utilisant le kitten ssh, dans le même répertoire.

Le kitten ssh peut être configuré en utilisant le fichier ~/.config/kitty/ssh.conf où vous pouvez spécifier les variables d'environnement à définir sur l'hôte distant et les fichiers à copier de l'hôte local vers l'hôte distant. Regardons un exemple rapide :

# Copie les fichiers et répertoires nécessaires à la configuration de certains outils courants
copy .zshrc .vimrc .vim
# Définit quelques variables d'environnement
env SOME_VAR=x
# COPIED_VAR aura la même valeur sur l'hôte distant qu'en local
env COPIED_VAR=_kitty_copy_env_var_
# Crée des paramètres spécifiques à l'hôte
hostname someserver-*
copy env-files
env SOMETHING=else
hostname someuser@somehost
copy --dest=foo/bar some-file
copy --glob some/files.*

Voir ci-dessous pour les détails complets sur la syntaxe et les options de ssh.conf. De plus, vous pouvez passer des options de configuration en ligne de commande :

kitten ssh --kitten interpreter=python nomserveur

L'argument --kitten peut être spécifié plusieurs fois, avec des directives de ssh.conf. Celles-ci remplacent les options finales utilisées pour l'hôte correspondant, comme si elles avaient été ajoutées à la fin de la section correspondante pour cet hôte dans ssh.conf. Elles ne s'appliquent qu'à l'hôte auquel vous vous connectez via cette invocation, donc toutes les directives hostname sont ignorées.

Attention :

En raison des limitations de conception de SSH, toute frappe que vous effectuez avant l'apparition de l'invite du shell peut être perdue. Il est donc préférable de ne pas commencer à taper tant que vous ne voyez pas l'invite du shell. 😇

Un exemple concret

Supposons que vous vous connectiez fréquemment en SSH à un serveur de production et que vous souhaitiez configurer votre shell et votre éditeur avec vos paramètres personnalisés. Cependant, d'autres personnes pourraient également se connecter et vous ne voulez pas écraser leurs paramètres. Voici comment cela pourrait être réalisé en utilisant le kitten ssh avec zsh et vim comme shell et éditeur, respectivement :

# Ces paramètres s'appliquent aux serveurs de mon organisation
hostname myserver-*
# Configure zsh pour lire ses fichiers depuis my-conf/zsh
env ZDOTDIR=$HOME/my-conf/zsh
copy --dest my-conf/zsh/.zshrc .zshrc
copy --dest my-conf/zsh/.zshenv .zshenv
# Si vous utilisez d'autres fichiers d'initialisation zsh, ajoutez-les de manière similaire
# Configure vim pour lire sa configuration depuis my-conf/vim
env VIMINIT=$HOME/my-conf/vim/vimrc
env VIMRUNTIME=$HOME/my-conf/vim
copy --dest my-conf/vim .vim
copy --dest my-conf/vim/vimrc .vimrc

Comment ça fonctionne

Le kitten ssh fonctionne en faisant transmettre et exécuter un script d'amorçage POSIX sh (ou optionnellement Python) sur l'hôte distant par SSH en utilisant un interpréteur. Ce script lit les données de configuration sur le périphérique TTY, que kitty envoie sous forme de tarball compressé encodé en Base64. Le script l'extrait et place les fichiers et définit les variables d'environnement avant de lancer enfin le shell de connexion avec l'intégration du shell activée. Les données sont demandées par le kitten via le TTY avec un mot de passe unique aléatoire. kitty lit la demande et si le mot de passe correspond à un mot de passe pré-stocké en mémoire partagée sur le localhost par le kitten, la transmission est autorisée. Si votre version locale d'OpenSSH https://www.openssh.com/ est >= 8.4, les données sont transmises instantanément sans aucun délai aller-retour.

Note :

Lors de la connexion à des hôtes BSD, il est possible que le script d'amorçage échoue ou s'exécute lentement, car les shells par défaut sont handicapés de diverses manières. Votre meilleure option est d'installer Python à distance, de vous assurer que le shell de connexion est conforme à POSIX sh, et d'utiliser python comme interpréteur dans ssh.conf.

Note :

Cela peut fonctionner ou non lors de l'utilisation de multiplexeurs de terminaux, en fonction de leur capacité à transmettre les codes d'échappement et si les valeurs des variables d'environnement KITTY_PID <#envvar-KITTY_PID> et KITTY_WINDOW_ID <#envvar-KITTY_WINDOW_ID> sont correctes dans la session actuelle (elles peuvent être incorrectes lors de la connexion à une session tmux exécutée dans une autre fenêtre) et si le kitten ssh est exécuté dans la fenêtre active du multiplexeur.

Configuration du bootstrap de l'hôte

hostname
hostname *

Le nom d'hôte auquel les options suivantes s'appliquent. Un motif glob pour faire correspondre plusieurs hôtes peut être utilisé. Plusieurs noms d'hôte peuvent également être spécifiés, séparés par des espaces. Le nom d'hôte peut inclure un nom d'utilisateur optionnel sous la forme utilisateur@hôte. Lorsqu'il n'est pas spécifié, les options s'appliquent à tous les hôtes, jusqu'à ce que la première spécification de nom d'hôte soit trouvée. Notez que la correspondance du nom d'hôte se fait par rapport au nom que vous spécifiez sur la ligne de commande pour vous connecter à l'hôte distant. Si vous souhaitez inclure la même configuration de base pour de nombreux hôtes différents, vous pouvez le faire avec la directive include <#include>. Dans la version 0.28.0, le comportement de cette option a été légèrement modifié ; maintenant, lorsqu'un nom d'hôte est rencontré, toutes ses valeurs de configuration sont définies sur leurs valeurs par défaut au lieu d'être héritées d'un bloc de nom d'hôte correspondant précédent. En particulier, cela signifie que les noms d'hôte n'héritent pas des configurations, évitant ainsi des actions à distance difficiles à comprendre.

interpreter
interpreter sh

L'interpréteur à utiliser sur l'hôte distant. Doit être soit un shell conforme à POSIX, soit un exécutable python. Si le sh par défaut n'est pas disponible ou défectueux, l'utilisation d'un interpréteur alternatif peut être utile.

remote_dir
remote_dir .local/share/kitty-ssh-kitten

L'emplacement sur l'hôte distant où les fichiers nécessaires à ce kitten sont installés. Les chemins relatifs sont résolus par rapport à $HOME. Les chemins absolus

e chemins ont leur / de tête supprimé et sont également résolus par rapport à $HOME.

copier

Copie des fichiers et répertoires des hôtes locaux vers les hôtes distants. Les fichiers spécifiés sont supposés être relatifs au répertoire HOME et copiés dans le HOME sur l'hôte distant. Les répertoires sont copiés récursivement. Si des chemins absolus sont utilisés, ils sont copiés tels quels. Par exemple :

copier .vimrc .zshrc .config/some-dir

Utilisez --dest pour copier un fichier vers une autre destination sur l'hôte distant :

copier --dest some-other-name some-file

Des modèles glob peuvent être spécifiés pour copier plusieurs fichiers, avec --glob :

copier --glob images/*.png

Les fichiers peuvent être exclus lors de la copie avec --exclude :

copier --glob --exclude *.jpg --exclude *.bmp images/*

Les fichiers dont le nom distant correspond au modèle d'exclusion ne seront pas copiés. Pour plus de détails, voir La commande copy.

Environnement du shell de connexion

shell_integration
shell_integration hérité

Contrôle l'intégration du shell sur l'hôte distant. Voir Shell integration <#shell-integration> pour plus de détails sur le fonctionnement de ce paramètre. La valeur spéciale hérité signifie qu'il faut utiliser le paramètre de kitty.conf. Ce paramètre est utile pour remplacer l'intégration sur une base par hôte.

login_shell

Le shell de connexion à exécuter sur l'hôte distant. Par défaut, le shell de connexion du compte utilisateur distant est utilisé.

env

Spécifie les variables d'environnement à définir sur l'hôte distant. Utiliser le nom avec un signe égal (par exemple env VAR=) le définira à la chaîne vide. Spécifier uniquement le nom (par exemple env VAR) supprimera la variable de l'environnement du shell distant. La valeur spéciale _kitty_copy_env_var_ fera que la valeur de la variable sera copiée de l'environnement local. Les définitions sont traitées par ordre alphabétique. Notez que les variables d'environnement sont développées récursivement, par exemple :

env VAR1=a
env VAR2=${HOME}/${VAR1}/b

La valeur de VAR2 sera <chemin vers le répertoire home>/a/b.

cwd

Le répertoire de travail sur l'hôte distant vers lequel se déplacer. Les variables d'environnement dans cette valeur sont développées. Par défaut, il est vide, donc aucun changement n'est effectué, ce qui signifie généralement que le répertoire HOME est utilisé.

color_scheme

Spécifie un schéma de couleurs à utiliser lors de la connexion à l'hôte distant. Si cette option se termine par .conf, elle est supposée être le nom d'un fichier de configuration à charger depuis le répertoire de configuration de kitty, sinon elle est supposée être le nom d'un thème de couleurs à charger via le kitten de thèmes <>. Notez que seules les couleurs s'appliquant au texte/fond sont modifiées, les autres paramètres de configuration des fichiers .conf/thèmes sont ignorés.

remote_kitty
remote_kitty if-needed

Rend kitten disponible sur l'hôte distant. Utile pour exécuter des kittens tels que le kitten icat <> pour afficher des images ou le kitten de transfert de fichiers <> pour transférer des fichiers. Ne fonctionne que si l'hôte distant a une architecture pour laquelle des binaires kitten précompilés https://github.com/kovidgoyal/kitty/releases sont disponibles. Notez que kitten n'est pas réellement copié sur l'hôte distant, mais un petit script bootstrap est copié et téléchargera et exécutera kitten lorsque kitten sera exécuté pour la première fois sur l'hôte distant. Une valeur de if-needed signifie que kitten est installé uniquement s'il n'est pas déjà présent dans le PATH système. Une valeur de yes signifie que kitten est installé même s'il est déjà présent, et le kitten installé a la priorité. Enfin, no signifie qu'aucun kitten n'est installé sur l'hôte distant. Le kitten installé peut être mis à jour en exécutant : kitten update-self sur l'hôte distant.

Configuration SSH

share_connections
share_connections yes

Au sein d'une même instance kitty, toutes les connexions à un serveur particulier peuvent être partagées. Cela réduit la latence de démarrage pour les connexions ultérieures et signifie que vous n'avez à entrer le mot de passe qu'une seule fois. Sous le capot, il utilise les ControlMasters SSH et ceux-ci sont automatiquement nettoyés par kitty lorsqu'il se quitte. Vous pouvez mapper un raccourci à close_shared_ssh_connections <#action-close_shared_ssh_connections> pour déconnecter toutes les connexions partagées actives.

askpass
askpass unless-set

Contrôle le programme que SSH utilise pour demander les mots de passe ou la confirmation des clés d'hôte, etc. Par défaut, il utilise le askpass natif de kitty, à moins que la variable d'environnement SSH_ASKPASS <#envvar-SSH_ASKPASS> ne soit définie. Définissez cette option sur ssh pour ne pas interférer du tout avec le mécanisme askpass normal de ssh, ce qui signifie généralement que ssh demandera dans le terminal. Définissez-la sur native pour toujours utiliser l'implémentation askpass native intégrée de kitty. Notez que ne pas utiliser l'implémentation askpass de kitty signifie que SSH pourrait avoir besoin d'utiliser le terminal avant que la connexion ne soit établie, donc le kitten ne peut pas utiliser le terminal pour envoyer des données sans un aller-retour supplémentaire, ce qui augmente la latence initiale de connexion.

delegate

N'utilise pas le kitten SSH pour cet hôte. Exécute plutôt la commande spécifiée comme délégué. Par exemple, utiliser delegate ssh exécutera la commande ssh avec tous les arguments passés au kitten, à l'exception de ceux spécifiques à kitten. Ceci est utile si certains hôtes ne sont pas capables de supporter le kitten ssh.

forward_remote_control
forward_remote_control no

Transmet le socket de contrôle à distance de kitty à l'hôte distant. Cela permet d'utiliser les installations de contrôle à distance de kitty depuis l'hôte distant. AVERTISSEMENT : Cela permet à tout logiciel sur l'hôte distant d'avoir un accès complet à l'ordinateur local, donc ne le faites que pour des hôtes distants de confiance. Notez que cela ne fonctionne pas avec les sockets UNIX abstraits tels que @mykitty en raison des limitations de SSH. Cette option utilise la redirection de socket SSH pour rediriger le socket pointé par la variable d'environnement KITTY_LISTEN_ON <#envvar-KITTY_LISTEN_ON>.

Automatisation de l'askpass

password

Spécifie un mot de passe à utiliser lorsque SSH demande un mot de passe. Le format de la valeur est "backend:secret". Actuellement, seul le backend "text" est supporté, qui stocke le secret en texte brut dans le fichier de configuration. Par exemple :

password text:my_password

Si le préfixe du backend est omis, il est traité comme "text:" pour la compatibilité ascendante. Attention, stocker des mots de passe en texte brut est peu sûr.

totp_secret

Spécifie un secret partagé TOTP pour pré-remplir les codes à usage unique lorsque SSH les demande. Le format de la valeur est "backend:secret". Actuellement, seul le backend "text" est supporté. Par exemple :

totp_secret text:JBSWY3DPEHPK3PXP

Si le préfixe du backend est omis, il est traité comme "text:" pour la compatibilité ascendante.

totp_digits
totp_digits 6

Nombre de chiffres pour les codes TOTP générés. Par défaut, c'est 6.

totp_period
totp_period 30

Période de temps en secondes pour la validité du code TOTP. Par défaut, c'est 30.

La commande copy

copier [options] fichier-ou-repertoire-a-copier ...

Copie des fichiers et répertoires des hôtes locaux vers les hôtes distants. Les fichiers spécifiés sont supposés être relatifs au répertoire HOME et copiés dans le HOME sur l'hôte distant. Les répertoires sont copiés récursivement. Si des chemins absolus sont utilisés, ils sont copiés tels quels.

Options

--glob [=no]
Interprète les arguments de fichier comme des modèles glob. Le globbing est basé sur les caractères génériques standard avec l'ajout que /**/ correspond à n'importe quel nombre de répertoires. Voir la syntaxe détaillée htt kitten-ssh(1) — kitty documentation

Name

kitten-ssh - copier des fichiers vers des hôtes distants

Overview

Le kitten ssh est un outil de copie de fichiers basé sur SSH, similaire à scp(1). Il est conçu pour être une alternative plus simple et plus rapide à scp, en particulier pour le transfert de gros fichiers ou de nombreux petits fichiers.

Il supporte l'utilisation de jokers (wildcards) pour spécifier les fichiers à copier, ainsi que des options pour exclure des fichiers et contrôler le comportement des liens symboliques.

A real world example

Pour copier le répertoire ~/myproject vers le répertoire personnel de l'utilisateur user sur l'hôte myserver, vous pouvez utiliser la commande suivante :

kitten ssh myserver:~ user@~/myproject

Cette commande copiera le contenu de ~/myproject dans ~/myproject sur le serveur distant. Si vous souhaitez copier le répertoire lui-même, vous pouvez utiliser :

kitten ssh myserver:~ user@~/myproject/

Pour copier des fichiers spécifiques, vous pouvez utiliser des jokers :

kitten ssh myserver:~ user@~/source_files/*.txt

Cette commande copiera tous les fichiers se terminant par .txt dans le répertoire ~/source_files du serveur distant.

How it works

Le kitten ssh utilise la connexion SSH existante pour transférer les fichiers. Il peut soit utiliser scp en arrière-plan pour le transfert, soit utiliser un protocole de transfert de fichiers personnalisé optimisé pour kitty.

Lorsque vous spécifiez une destination sur l'hôte distant, elle est résolue par rapport au répertoire personnel de l'utilisateur distant. Si vous spécifiez un chemin absolu, il sera utilisé tel quel.

Host bootstrap configuration

Pour que le kitten ssh fonctionne, le serveur distant doit avoir le package kitty-terminfo installé. Ce package contient les informations de terminal nécessaires pour que kitty puisse s'afficher correctement sur le serveur distant.

Si le package kitty-terminfo n'est pas disponible sur le serveur distant, vous pouvez l'installer manuellement en suivant les instructions dans la section "Copying terminfo files manually" ci-dessous.

Login shell environment

Le kitten ssh tente de s'assurer que l'environnement du shell de connexion sur le serveur distant est correctement configuré pour kitty. Cela inclut la définition de variables d'environnement telles que TERM et d'autres variables spécifiques à kitty.

Si vous rencontrez des problèmes avec l'affichage de kitty sur le serveur distant, vérifiez que les variables d'environnement sont correctement définies dans votre shell de connexion.

Ssh configuration

Le kitten ssh utilise la configuration SSH trouvée dans votre fichier ~/.ssh/config. Cela inclut les informations d'authentification, les alias d'hôtes, et d'autres options de connexion SSH.

Assurez-vous que votre fichier ~/.ssh/config est correctement configuré pour l'hôte distant auquel vous souhaitez vous connecter.

Askpass automation

Si une authentification par mot de passe est requise, le kitten ssh peut utiliser un mécanisme d'automatisation "askpass" pour récupérer le mot de passe sans intervention manuelle. Cela est généralement géré par le système SSH sous-jacent.

Si vous utilisez des clés SSH pour l'authentification, vous ne devriez pas être invité à entrer un mot de passe.

The copy command

La syntaxe de base de la commande kitten ssh est la suivante :

kitten ssh [OPTIONS] HOST:SOURCE DEST

Où :

HOST
Le nom d'hôte ou l'adresse IP du serveur distant.
SOURCE
Le chemin du fichier ou du répertoire source sur l'hôte distant. Si l'hôte est omis, le fichier source est considéré comme étant local. Les chemins relatifs sont résolus par rapport au répertoire personnel de l'utilisateur distant.
DEST
Le chemin de destination sur l'hôte local ou distant. Les chemins relatifs sont résolus par rapport au répertoire personnel de l'utilisateur distant. Si DEST est omis, le chemin source local est utilisé comme destination distante.

Les options suivantes sont disponibles :

--glob <GLOB>
Un motif glob. Tous les fichiers qui correspondent à ce motif seront inclus dans la copie. Ceci est utile lorsque vous voulez copier uniquement un sous-ensemble de fichiers d'un répertoire. Voir la syntaxe détaillée https://github.com/bmatcuk/doublestar#patterns.
--dest <DEST>
La destination sur l'hôte distant pour copier. Les chemins relatifs sont résolus par rapport au répertoire HOME sur l'hôte distant. Lorsque cette option n'est pas spécifiée, le chemin du fichier local est utilisé comme destination distante (avec le répertoire HOME remplacé automatiquement par le HOME distant). Notez que les variables d'environnement et ~ ne sont pas développées.
--exclude <EXCLUDE>
Un motif glob. Les fichiers dont les noms correspondent à ce motif sont exclus du transfert. Utilisé uniquement lors de la copie de répertoires. Peut être spécifié plusieurs fois ; si l'un des motifs correspond, le fichier sera exclu. Si le motif inclut un /, il correspondra au chemin complet, pas seulement au nom du fichier. Dans de tels motifs, vous pouvez utiliser /**/ pour correspondre à zéro ou plusieurs répertoires. Par exemple, pour exclure un répertoire et tout ce qui se trouve en dessous, utilisez **/nom_de_repertoire. Voir la syntaxe détaillée https://github.com/bmatcuk/doublestar#patterns pour savoir comment les jokers correspondent.
--symlink-strategy <SYMLINK_STRATEGY>
Contrôle ce qui se passe si le chemin spécifié est un lien symbolique. La valeur par défaut est de préserver le lien symbolique, en le recréant sur la machine distante. Définir cette option sur resolve entraînera le suivi du lien symbolique et l'utilisation de sa cible comme fichier/répertoire à copier. La valeur de keep-path est la même que resolve, sauf que le chemin du fichier distant est dérivé du chemin du lien symbolique au lieu du chemin de la cible du lien symbolique. Notez que cette option ne s'applique pas aux liens symboliques rencontrés lors de la copie récursive de répertoires, ceux-ci sont toujours préservés. Défaut : preserve Choix : keep-path, preserve, resolve

Copying terminfo files manually

Parfois, le kitten ssh peut échouer, ou peut-être que vous n'aimez pas l'utiliser. Dans de tels cas, les fichiers terminfo peuvent être copiés manuellement vers un serveur avec la commande suivante en une seule ligne :

infocmp -a xterm-kitty | ssh myserver tic -x -o \~/.terminfo /dev/stdin

Si vous êtes derrière un proxy (comme Balabit) qui empêche cela, ou si vous vous connectez à macOS où tic ne prend pas en charge la lecture depuis STDIN, vous devez rediriger la première commande vers un fichier, copier ce fichier sur le serveur et exécuter tic manuellement. Si vous vous connectez à un système embarqué, Android ou un système qui n'a pas tic, copiez votre fichier terminfo local sur l'autre système en tant que ~/.terminfo/x/xterm-kitty.

Si le serveur exécute une distribution Linux relativement moderne et que vous y avez un accès root, vous pourriez simplement installer le package kitty-terminfo sur le serveur pour rendre les fichiers terminfo disponibles.

En réalité, la solution correcte pour cela serait de convaincre les mainteneurs d'OpenSSH de faire en sorte que ssh le fasse automatiquement, si possible, lors de la connexion à un serveur, afin que tous les terminaux fonctionnent de manière transparente.

Si le serveur exécute FreeBSD, ou un autre système qui dépend de termcap plutôt que de terminfo, vous devrez convertir le fichier terminfo sur votre machine locale en exécutant (sur la machine locale avec kitty) :

infocmp -CrT0 xterm-kitty

La sortie de cette commande est la description termcap, qui devrait être ajoutée à /usr/share/misc/termcap sur le serveur distant. Exécutez ensuite la commande suivante pour appliquer votre modification (sur le serveur) :

cap_mkdb /usr/share/misc/termcap
