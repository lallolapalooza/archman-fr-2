NOM

kubeadm join - Exécuter ceci sur toute machine que vous souhaitez joindre à un cluster existant

SYNTAXE

kubeadm join [OPTIONS]

DESCRIPTION

Lors de la jonction à un cluster initialisé avec kubeadm, nous devons établir une confiance bidirectionnelle. Ceci est divisé en découverte (faire confiance au plan de contrôle Kubernetes par le nœud) et amorçage TLS (faire confiance au nœud par le plan de contrôle Kubernetes).

Il existe 2 schémas principaux pour la découverte. Le premier consiste à utiliser un jeton partagé avec l'adresse IP du serveur API. Le second consiste à fournir un fichier - un sous-ensemble du fichier kubeconfig standard. Le fichier de découverte/kubeconfig prend en charge le jeton, les plugins d'authentification client-go ("exec"), "tokenFile" et "authProvider". Ce fichier peut être un fichier local ou téléchargé via une URL HTTPS. Les formes sont kubeadm join --discovery-token abcdef.1234567890abcdef 1.2.3.4:6443, kubeadm join --discovery-file chemin/vers/fichier.conf, ou kubeadm join --discovery-file https://url/file.conf. Une seule forme peut être utilisée. Si les informations de découverte sont chargées à partir d'une URL, HTTPS doit être utilisé. De plus, dans ce cas, le bundle CA installé sur l'hôte est utilisé pour vérifier la connexion.

Si vous utilisez un jeton partagé pour la découverte, vous devriez également passer l'indicateur --discovery-token-ca-cert-hash pour valider la clé publique de l'autorité de certification racine (CA) présentée par le plan de contrôle Kubernetes. La valeur de cet indicateur est spécifiée sous la forme " : ", où le type de hachage pris en charge est "sha256". Le hachage est calculé sur les octets de l'objet Subject Public Key Info (SPKI) (comme dans RFC7469). Cette valeur est disponible dans la sortie de "kubeadm init" ou peut être calculée à l'aide d'outils standard. L'indicateur --discovery-token-ca-cert-hash peut être répété plusieurs fois pour autoriser plus d'une clé publique.

Si vous ne connaissez pas le hachage de la clé publique de la CA à l'avance, vous pouvez passer l'indicateur --discovery-token-unsafe-skip-ca-verification pour désactiver cette vérification. Cela affaiblit le modèle de sécurité de kubeadm car d'autres nœuds peuvent potentiellement usurper l'identité du plan de contrôle Kubernetes.

Le mécanisme d'amorçage TLS est également piloté via un jeton partagé. Il est utilisé pour s'authentifier temporairement auprès du plan de contrôle Kubernetes afin de soumettre une demande de signature de certificat (CSR) pour une paire de clés créée localement. Par défaut, kubeadm configurera le plan de contrôle Kubernetes pour approuver automatiquement ces demandes de signature. Ce jeton est passé avec l'indicateur --tls-bootstrap-token abcdef.1234567890abcdef.

Souvent, le même jeton est utilisé pour les deux parties. Dans ce cas, l'indicateur --token peut être utilisé au lieu de spécifier chaque jeton individuellement.

La commande "join [api-server-endpoint]" exécute les phases suivantes :

preflight              Exécute les vérifications préliminaires de jonction
control-plane-prepare  Prépare la machine à héberger un plan de contrôle
  /download-certs        Télécharge les certificats partagés entre les nœuds du plan de contrôle depuis le Secret kubeadm-certs
  /certs                 Génère les certificats pour les nouveaux composants du plan de contrôle
  /kubeconfig            Génère le kubeconfig pour les nouveaux composants du plan de contrôle
  /control-plane         Génère les manifestes pour les nouveaux composants du plan de contrôle
kubelet-start          Écrit les paramètres kubelet, les certificats et démarre (ou redémarre) le kubelet
control-plane-join     Joins une machine en tant qu'instance de plan de contrôle
  /etcd                  Ajoute un nouveau membre etcd local
  /mark-control-plane    Marque un nœud comme étant un plan de contrôle
wait-control-plane     Attend le démarrage du plan de contrôle

OPTIONS

--apiserver-advertise-address="" Si le nœud doit héberger une nouvelle instance de plan de contrôle, l'adresse IP sur laquelle le serveur API annoncera qu'il écoute. S'il n'est pas défini, l'interface réseau par défaut sera utilisée.

--apiserver-bind-port=6443 Si le nœud doit héberger une nouvelle instance de plan de contrôle, le port sur lequel le serveur API doit se lier.

--certificate-key="" Utilisez cette clé pour décrypter les secrets de certificat téléchargés par init. La clé de certificat est une chaîne encodée en hexadécimal qui est une clé AES de 32 octets.

--config="" Chemin vers un fichier de configuration kubeadm.

--control-plane=false Crée une nouvelle instance de plan de contrôle sur ce nœud

--cri-socket="" Chemin vers le socket CRI pour se connecter. S'il est vide, kubeadm essaiera de détecter automatiquement cette valeur ; utilisez cette option uniquement si vous avez plus d'un CRI installé ou si vous avez un socket CRI non standard.

--discovery-file="" Pour la découverte basée sur fichier, un fichier ou une URL à partir desquels charger les informations du cluster.

--discovery-token="" Pour la découverte basée sur jeton, le jeton utilisé pour valider les informations du cluster récupérées auprès du serveur API.

--discovery-token-ca-cert-hash=[] Pour la découverte basée sur jeton, valide que la clé publique racine de la CA correspond à ce hachage (format : " : ").

--discovery-token-unsafe-skip-ca-verification=false Pour la découverte basée sur jeton, permet la jonction sans épinglage de --discovery-token-ca-cert-hash.

--dry-run=false N'appliquez aucun changement ; affichez simplement ce qui serait fait.

--ignore-preflight-errors=[] Une liste de vérifications dont les erreurs seront affichées comme avertissements. Exemple : 'IsPrivilegedUser,Swap'. La valeur 'all' ignore les erreurs de toutes les vérifications.

--node-name="" Spécifiez le nom du nœud.

--patches="" Chemin vers un répertoire contenant des fichiers nommés "cible[suffix][+patchtype].extension". Par exemple, "kube-apiserver0+merge.yaml" ou juste "etcd.json". "cible" peut être l'un de "kube-apiserver", "kube-controller-manager", "kube-scheduler", "etcd", "kubeletconfiguration", "corednsdeployment". "patchtype" peut être l'un de "strategic", "merge" ou "json" et ils correspondent aux formats de patch pris en charge par kubectl. Le "patchtype" par défaut est "strategic". "extension" doit être soit "json" soit "yaml". "suffix" est une chaîne optionnelle qui peut être utilisée pour déterminer quels patchs sont appliqués en premier par ordre alphabétique.

--skip-phases=[] Liste des phases à ignorer

--tls-bootstrap-token="" Spécifiez le jeton utilisé pour s'authentifier temporairement auprès du plan de contrôle Kubernetes lors de la jonction du nœud.

--token="" Utilisez ce jeton à la fois pour discovery-token et tls-bootstrap-token lorsque ces valeurs ne sont pas fournies.

OPTIONS HÉRITÉES DES COMMANDES PARENTES

--rootfs="" Le chemin vers le système de fichiers racine 'réel' de l'hôte. Cela amènera kubeadm à chrooter dans le chemin fourni.

--version=false --version, --version=raw affiche les informations de version et quitte ; --version=vX.Y.Z... définit la version rapportée
