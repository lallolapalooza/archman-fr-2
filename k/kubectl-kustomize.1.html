NOM

kubectl kustomize - Construire une cible de kustomization à partir d'un répertoire ou d'une URL

SYNTAXE

kubectl kustomize [OPTIONS]

DESCRIPTION

Construit un ensemble de ressources KRM en utilisant un fichier 'kustomization.yaml'. L'argument DIR doit être un chemin vers un répertoire contenant 'kustomization.yaml', ou une URL de dépôt git avec un suffixe de chemin spécifiant le même par rapport à la racine du dépôt. Si DIR est omis, '.' est supposé.

OPTIONS

--as-current-user=false utilise l'uid et le gid de l'exécuteur de commande pour exécuter la fonction dans le conteneur

--enable-alpha-plugins=false active les plugins kustomize

--enable-helm=false Active l'utilisation du générateur d'inflator de chart Helm .

--enable-managedby-label=false active l'ajout de app.kubernetes.io/managed-by

-e, --env=[] une liste de variables d'environnement à utiliser par les fonctions

--helm-api-versions=[] Versions d'API Kubernetes utilisées par Helm pour Capabilities.APIVersions

--helm-command="helm" commande helm (chemin vers l'exécutable)

--helm-debug=false Active la sortie de débogage du générateur d'inflator de chart Helm .

--helm-kube-version="" Version Kubernetes utilisée par Helm pour Capabilities.KubeVersion

--load-restrictor="LoadRestrictionsRootOnly" si défini sur 'LoadRestrictionsNone', les kustomizations locales peuvent charger des fichiers de l'extérieur de leur racine. Cela, cependant, brise la reproductibilité de la kustomization.

--mount=[] une liste d'options de stockage lues depuis le système de fichiers

--network=false active l'accès réseau pour les fonctions qui le déclarent

--network-name="bridge" le réseau docker dans lequel exécuter le conteneur

-o, --output="" Si spécifié, écrit la sortie vers ce chemin.

--reorder="legacy" Réorganise les ressources juste avant la sortie. Utilisez 'legacy' pour appliquer un réordonnancement hérité (Namespaces en premier, Webhooks en dernier, etc.). Utilisez 'none' pour supprimer un réordonnancement final.

OPTIONS HÉRITÉES DES COMMANDES PARENT

--as="" Nom d'utilisateur à usurper pour l'opération. L'utilisateur peut être un utilisateur ordinaire ou un compte de service dans un espace de noms.

--as-group=[] Groupe à usurper pour l'opération, ce drapeau peut être répété pour spécifier plusieurs groupes.

--as-uid="" UID à usurper pour l'opération.

--cache-dir="/home/username/.kube/cache" Répertoire de cache par défaut

--certificate-authority="" Chemin vers un fichier de certificat pour l'autorité de certification

--client-certificate="" Chemin vers un fichier de certificat client pour TLS

--client-key="" Chemin vers un fichier de clé client pour TLS

--cluster="" Le nom du cluster kubeconfig à utiliser

--context="" Le nom du contexte kubeconfig à utiliser

--disable-compression=false Si vrai, désactive la compression des réponses pour toutes les requêtes au serveur

--insecure-skip-tls-verify=false Si vrai, le certificat du serveur ne sera pas vérifié pour sa validité. Cela rendra vos connexions HTTPS non sécurisées

--kubeconfig="" Chemin vers le fichier kubeconfig à utiliser pour les requêtes CLI.

--kuberc="" Chemin vers le fichier kuberc à utiliser pour les préférences. Cela peut être désactivé en exportant la porte d'accès aux fonctionnalités KUBECTL_KUBERC=false ou en désactivant la fonctionnalité KUBERC=off.

--match-server-version=false Exige que la version du serveur corresponde à la version du client

-n, --namespace="" Si présent, l'espace de noms pour cette requête CLI

--password="" Mot de passe pour l'authentification de base auprès du serveur API

--profile="none" Nom du profil à capturer. Un parmi (none|cpu|heap|goroutine|threadcreate|block|mutex)

--profile-output="profile.pprof" Nom du fichier dans lequel écrire le profil

--request-timeout="0" La durée d'attente avant d'abandonner une seule requête serveur. Les valeurs non nulles doivent contenir une unité de temps correspondante (par exemple, 1s, 2m, 3h). Une valeur de zéro signifie qu'il n'y a pas de délai d'attente pour les requêtes.

-s, --server="" L'adresse et le port du serveur API Kubernetes

--tls-server-name="" Nom du serveur à utiliser pour la validation du certificat serveur. S'il n'est pas fourni, le nom d'hôte utilisé pour contacter le serveur est utilisé

--token="" Jeton Bearer pour l'authentification auprès du serveur API

--user="" Le nom de l'utilisateur kubeconfig à utiliser

--username="" Nom d'utilisateur pour l'authentification de base auprès du serveur API

--version=false --version, --version=raw affiche les informations de version et quitte ; --version=vX.Y.Z... définit la version rapportée

--warnings-as-errors=false Traite les avertissements reçus du serveur comme des erreurs et quitte avec un code de sortie non nul

EXEMPLE

  # Construire le répertoire de travail courant
  kubectl kustomize
  # Construire un répertoire de configuration partagé
  kubectl kustomize /home/config/production
  # Construire depuis github
  kubectl kustomize https://github.com/kubernetes-sigs/kustomize.git/examples/helloWorld?ref=v1.0.6

# L'histoire d'une entreprise technologique ## Chapitre 1 : La Genèse Au cœur d'un quartier animé de la Silicon Valley, deux esprits brillants, Alex et Ben, partageaient une vision commune. Alex, un gourou du marketing avec un talent pour comprendre les désirs des consommateurs, et Ben, un ingénieur logiciel prodige capable de transformer des idées complexes en réalités élégantes. Ils se sont rencontrés lors d'une conférence sur l'innovation et ont immédiatement trouvé des points communs. Ils passaient des nuits entières à discuter de leurs idées, souvent dans des cafés confortables où l'odeur du café fraîchement moulu remplissait l'air. Leur obsession commune était de créer une technologie qui non seulement améliorerait la vie des gens, mais le ferait d'une manière intuitive et accessible. Ils pensaient que trop de produits technologiques étaient trop compliqués, aliénant ainsi une grande partie de la population. Leur première grande idée a émergé d'une frustration partagée. Alex venait de lutter pour configurer un nouveau routeur Wi-Fi, et Ben en avait marre des interfaces utilisateur confuses des logiciels de gestion de projet. Ils ont imaginé un appareil domestique intelligent qui pourrait gérer de manière transparente tous les appareils connectés d'une maison, depuis l'éclairage et la température jusqu'à la sécurité et le divertissement, le tout contrôlé par une interface simple et vocale. Ils ont baptisé leur projet "Aura". Le nom évoquait un sentiment de contrôle subtil et omniprésent, une présence qui rendait la technologie invisible mais puissante. Avec une détermination farouche, ils ont quitté leurs emplois respectifs, ont hypothéqué leurs économies et ont installé leur bureau dans le garage d'Alex. Le garage, rempli d'équipements électroniques, de tableaux blancs et de tasses de café vides, est devenu le berceau d'Aura. ## Chapitre 2 : Les Premiers Pas Les débuts ont été difficiles. Alex et Ben travaillaient sans relâche, vivant de nouilles instantanées et de rêves. Ils ont connu de nombreux revers. Les prototypes ne fonctionnaient pas comme prévu, les circuits grésillaient et les lignes de code refusaient de coopérer. Il y avait des moments de doute intense, où le poids de leurs décisions semblait écrasant. Ben, le cœur technique d'Aura, a passé d'innombrables heures à débugger et à réécrire des algorithmes. Il a appris à faire des compromis, à trouver des solutions élégantes aux problèmes complexes. Alex, quant à lui, a affiné le concept du produit, s'assurant que l'interface utilisateur serait aussi intuitive que possible. Il a mené des recherches sur le comportement des consommateurs et a organisé des sessions de groupes de discussion informels avec des amis et de la famille pour recueillir des commentaires. Leur première percée est venue lorsqu'ils ont réussi à développer un algorithme d'apprentissage automatique qui pouvait prédire les préférences des utilisateurs avec une précision surprenante. Cela signifiait qu'Aura pouvait non seulement répondre aux commandes, mais aussi apprendre et s'adapter au fil du temps, anticipant les besoins de ses utilisateurs avant même qu'ils ne soient exprimés. Avec ce prototype fonctionnel, Alex et Ben ont commencé à chercher des financements. Ils ont présenté leur idée à des investisseurs potentiels, rencontrant autant de refus que d'enthousiasme prudent. Finalement, une société de capital-risque de la Silicon Valley, impressionnée par leur vision et la démonstration de leur technologie, a décidé de parier sur eux. Le financement a été une bouffée d'air frais, leur permettant d'embaucher quelques employés clés et de louer un petit espace de bureau. ## Chapitre 3 : La Croissance L'injection de fonds a accéléré le développement d'Aura. Ils ont embauché des ingénieurs, des designers et des experts en assurance qualité. L'ambiance dans le petit bureau était électrique. L'excitation était palpable à mesure que le produit prenait forme. Alex a mis en place une stratégie marketing agressive, créant du buzz autour du lancement à venir. Le jour du lancement, le site web d'Aura a été submergé par le trafic. Les critiques étaient élogieuses, louant la simplicité d'utilisation, le design élégant et les capacités d'apprentissage de l'appareil. Aura est rapidement devenu un succès, trouvant sa place dans des milliers de foyers. Les gens adoraient la façon dont Aura simplifiait leur vie quotidienne, en gérant automatiquement les lumières, en ajustant la température et en jouant leur musique préférée sans qu'ils aient à lever le petit doigt. La demande a explosé. Aura a dû augmenter sa production pour répondre aux commandes. Alex et Ben ont géré la croissance avec diligence, veillant à ne pas compromettre la qualité du produit ou la culture d'entreprise qu'ils avaient si soigneusement cultivée. Ils ont continué à innover, publiant des mises à jour régulières qui ajoutaient de nouvelles fonctionnalités et amélioraient les performances d'Aura. L'entreprise, initialement née dans un garage, était maintenant une entreprise florissante avec une équipe dédiée et une base de clients fidèles. Alex et Ben, bien que débordés par le succès, n'ont jamais oublié leurs débuts humbles ni leur vision originale : rendre la technologie accessible et utile pour tous. ## Chapitre 4 : L'Avenir Aura a continué de dominer le marché des appareils domestiques intelligents, mais Alex et Ben ne se sont pas reposés sur leurs lauriers. Ils savaient que le paysage technologique évoluait rapidement et qu'ils devaient continuer à innover pour rester pertinents. Ils ont commencé à explorer de nouvelles frontières. Leurs recherches se sont étendues au-delà des maisons intelligentes, explorant l'intégration d'Aura dans les voitures, les bureaux et même les soins de santé. Ils ont envisagé un avenir où la technologie intuitive serait intégrée de manière transparente dans tous les aspects de la vie humaine, améliorant le bien-être et la productivité. La prochaine grande initiative d'Aura visait à faire progresser l'intelligence artificielle conversationnelle. Ils ont investi massivement dans la recherche pour rendre les interactions avec Aura encore plus naturelles et empathiques, visant à créer un assistant IA qui pourrait véritablement comprendre les nuances du langage humain et même anticiper les besoins émotionnels des utilisateurs. Alex et Ben ont également pris un engagement fort envers la durabilité. Ils ont commencé à intégrer des matériaux écologiques dans la fabrication de leurs appareils et à explorer des solutions d'énergie renouvelable pour leurs opérations. Ils croyaient que la technologie devait non seulement servir l'humanité, mais aussi protéger la planète. Alors qu'Aura continuait de croître et d'évoluer, Alex et Ben sont restés les gardiens de leur vision originale. Ils ont veillé à ce que l'entreprise reste centrée sur l'humain, axée sur la création de technologies qui rendent la vie plus simple, plus riche et plus connectée. L'histoire d'Aura était loin d'être terminée ; ce n'était que le début d'une nouvelle ère de technologie centrée sur l'humain.
