keyrings - mécanisme de

gestion et de rétention
des clés dans le noyau

DESCRIPTIO

N

Le mécanisme de gestion des clés de Linux est principalement un moyen pour divers composants du noyau de conserver ou mettre en cache des données de sécurité, des clés d'authentification, des clés de chiffrement et d'autres données dans le

noyau.

Des interfaces d'appels système sont fournies afin que les programmes en espace utilisateur puissent gérer ces objets et utiliser également le mécanisme à leurs propres fins ; voir add_key(2), request_key(2) et keyctl(

2).

Une bibliothèque et quelques utilitaires en espace utilisateur sont fournis pour permettre l'accès au mécanisme. Voir keyctl(1), keyctl(3) et keyutils(7) pour plus

d'informations.

Clé

s

Une clé possède les attributs suivants

:
Numéro de série
(ID)
Il s'agit d'un identifiant entier unique par lequel une clé est référencée dans les appels système. Le numéro de série est parfois désigné de manière synonyme comme l'identifiant (ID) de la clé. Programmatiquement, les numéros de série des clés sont représentés à l'aide du type key_serial_
t.
Ty
pe
Le type d'une clé définit le genre de données qui peuvent être c
ontenues dans la clé, la manière dont le contenu proposé de la cl

Plusieurs types à usage général sont disponib
les, ainsi que certains types spécialisés déf

Description
(nom)
La description d'une clé est une chaîne imprimable utilisée comme terme de recherche pour la clé (en conjonction avec le type de clé) ainsi que comme nom d'affichage. Lors des recherches, la description peut correspondre partiellement ou
exactement.
Charge utile
(données)
La charge utile est le contenu réel d'une clé. Elle est généralement définie lors de la création d'une clé, mais il est possible que le noyau rappelle l'espace utilisateur pour terminer l'instanciation d'une clé si celle-ci n'était pas déjà connue du noyau lorsqu'elle a été demandée. Pour plus de détails, voir request_
key
(2).
La charge utile d'une clé peut être lue et mise
à jour si le type de clé le permet et si une au
torisation appropriée est accordée à l'appelant.
Droits
d'accès
Tout comme les fichiers, chaque clé possède un identifiant utilisateur propriétaire, un identifiant de groupe propriétaire et une étiquette de sécurité. Chaque clé possède également un ensemble de permissions, bien qu'il y en ait plus que pour un fichier UNIX normal, et il existe une catégorie supplémentaire (possesseur) en plus des catégories habituelles utilisateur, groupe et autres (voir Possession,
ci-des
sous).
Notez que les clés sont soumises au contrôle de quotas, car elles
nécessitent de la mémoire noyau non échangeable. L'identifiant
utilisateur propriétaire spécifie dont le quota doit être débité.
Date
d'expiration
Chaque clé peut avoir une date d'expiration définie. Lorsque ce moment est atteint, la clé est marquée comme expirée et les accès à celle-ci échouent avec l'erreur EKEYEXPIRED. Si elle n'est pas supprimée, mise à jour ou remplacée, alors, après un délai défini, une clé expirée est automatiquement supprimée (ramassée par le ramasse-miettes) avec tous les liens qui la référencent, et les tentatives d'accès à la clé échouent avec l'erreur ENOKE
Y.
Compteur de
références
Chaque clé possède un compteur de références. Les clés sont référencées pa
r les porte-clés, par les utilisateurs actuellement actifs et par les référ
ences d'identification d'un processus. Lorsque le compteur de références at
teint zéro, la clé est planifiée pour le ramassage par le ramasse-miettes.

Porte-clé

s

Comme mentionné précédemment, les porte-clés sont un type spécial de clés qui contiennent des liens vers d'autres clés (qui peuvent inclure d'autres porte-clés). Les clés peuvent être liées par plusieurs porte-clés. Les porte-clés peuvent être considérés comme analogues aux répertoires UNIX où chaque répertoire contient un ensemble de liens physiques vers des

fichiers.

Diverses opérations (appels système) ne peuvent être appliquées qu'aux porte-clés

Ajo

Une clé peut être ajoutée à un porte-clé par des appels système qui créent des clés. Cela empêche la nouvelle clé d'être immédiatement supprimée lorsque l'appel système libère sa dernière référence à la
clé.

on
Un lien peut être ajouté à un porte-clé pointant vers une clé déjà connue, à condition que cela ne crée pas un cycle
auto-référentiel.
Déconnex
ion
Un lien peut être retiré d'un porte-clé. Lorsque le dernier lien vers une clé est retiré, cette clé sera planifiée pour suppression par le
ramasse-miettes.
Vida

Tous les liens peuvent être retirés d'un
porte-clé.
Recherc
he
Un porte-clé peut être considéré comme la racine d'un arbre ou d'un sous-arbre où les p
orte-clés forment les branches et les non-porte-clés les feuilles. Cet arbre peut être
parcouru pour trouver une clé correspondant à un type et une description particuliers.

Voir keyctl_clear(3), keyctl_link(3), keyctl_search(3), et keyctl_unlink(3) pour

plus d'in

Ancrage des

clés

Pour empêcher une clé d'être collectée par le ramasse-miettes, elle doit être ancrée afin de maintenir son compteur de références élevé lorsqu'elle n'est pas activement utilisée par le

noyau.

Les trousseaux de clés sont utilisés pour ancrer d'autres clés : chaque lien est une référence sur une clé. Notez que les trousseaux de clés sont eux-mêmes des clés et sont donc également soumis à la même exigence d'ancrage pour empêcher leur collecte par le ramasse-miettes

.

Le noyau met à disposition un certain nombre de trousseaux de clés d'ancrage. Notez que certains de ces trousseaux ne seront créés qu'à leur premier

accès.
Trousseaux de clés de
processus
Les informations d'identification du processus elles-mêmes référencent des trousseaux de clés
avec des sémantiques spécifiques. Ces trousseaux sont épinglés tant que l'ensemble d'informat

Il existe trois trousseaux de clés avec des règles d'héritage/partage différentes : le session-keyring(7) (hérité et partagé par tous les processus enfants), le process-keyring(7) (partagé par tous les threads d'un processus) et le thread-keyring(7) (spécifique à un thread particulier)

En alternative à l'utilisation des identifiants réels des trousseaux, dans les appels à add_key(2), keyctl(2), et request_key(2), les valeurs spéciales de trousseau KEY_SPEC_SESSION_KEYRING, KEY_SPEC_PROCESS_KEYRING, et KEY_SPEC_THREAD_KEYRING peuvent être utilisées pour faire
référence aux instances propres

utilisateur

Le trousseau persistant permet, par exemple, aux scripts cron(8) d'utiliser des informations d'identification qui sont lai

Possessio

n

Le concept de possession est important pour comprendre le modèle de sécurité des trousseaux de clés. Qu'un thread possède une clé est déterminé par les règles suivantes

:
(1
)
Toute clé ou trousseau de clés qui n'accorde pas la permission de recherche à l'appelant est ignoré dans toutes les règles
suivantes.
(2
)
Un thread possède directement son session-keyring(7), process-keyring(7), et thread-keyring(7) car ces trousseaux sont référencés par ses informations
d'identification.
(3
)
Si un trousseau de clés est possédé, alors toute clé à laquelle il est lié est également
possédée.
(4
)
Si une clé à laquelle un trousseau de clés est lié est elle-même un trousseau de clés, alors la règle (3) s'applique
récursivement.
(5
)
Si un processus est rappelé par le noyau pour instancier une clé (voir request_key(2)), alors il possède également les trousseaux de clés du
demandeur comme dans la règle
(1) comme s'il était le demandeur.

Notez que la possession n'est pas une propriété fondamentale d'une clé, mais doit plutôt être calculée chaque fois que la clé est

nécessaire.

La possession est conçue pour permettre aux programmes avec bit set-user-ID exécutés depuis, par exemple, un shell d'utilisateur d'accéder aux clés de l'utilisateur. Accorder des permissions au possesseur de la clé tout en les refusant au propriétaire et au groupe de la clé permet de prévenir l'accès aux clés sur la base de la correspondance des UID et

GID.

Lorsqu'il crée le trousseau de session, pam_keyinit(8) ajoute un lien vers le user-keyring(7), rendant ainsi le trousseau de clés ut

ilisateur et tout ce qu'il c
ontient possédé par défaut.

Recherche de

clés

L'une des fonctionnalités clés de la gestion des clés de Linux est la capacité de trouver une clé qu'un processus conserve. L' appel système request_key(2) est le point d'accès principal pour les applications de l'espace utilisateur afin de trouver une clé. (En interne, le noyau a quelque chose de similaire disponible pour l'utilisation par les composants internes qui utilisent des clés.

)

L'algorithme de recherche fonctionne comme suit

:
(1
)
Les trousseaux de clés du processus sont recherchés dans l'ordre suivant : le thread-keyring(7) s'il existe, le process-keyring(7) s'il existe, puis soit le session-keyring(7) s'il existe, soit le user-session-keyring(7) si celui-ci
existe.
(2
)
Si l'appelant était un processus invoqué par le mécanisme de rappel request_key(2), alors les trousseaux de clés de l'appelant original de request_key(2) seront également
recherchés.
(3
)
La recherche dans un arbre de trousseaux de clés s'effectue en largeur (breadth-first) : chaque trousseau est d'abord recherché pour une correspondance, puis les trousseaux référencés par ce trousseau sont
recherchés.
(4
)
Si une clé correspondante valide est trouvée, la recherche se termine et cette clé est
retournée.
(5
)
Si une clé correspondante avec un état d'erreur attaché est trouvée, cet état d'erreur est noté et la recherche
continue.
(6
)
Si aucune clé correspondante valide n'est trouvée, le premier état d'erreur noté est retourné ; sinon, une erreur ENOKEY est
retou
rnée.

Il est également possible de rechercher un trousseau de clés spécifique, auquel cas seules les étapes (3) à (6)

s'appliquent.

Voir request_key(2) et keyctl_search(3) pour p

lus d'i
nformations.

Création de clés à la

demande

Si une clé ne peut être trouvée, request_key(2) créera, si un argument callout_info est fourni, une nouvelle clé puis effectuera un appel vers l'espace utilisateur pour instancier la clé. Cela permet de créer des clés selon les

besoins.

Typiquement, cela impliquera le noyau créant un nouveau processus qui exécute le programme request-key(8), qui exécutera ensuite le gestionnaire approprié en fonction de sa

configuration.

Le gestionnaire reçoit une clé d'autorisation spéciale qui lui permet, et à lui seul, d'instancier la nouvelle clé. Elle est également utilisée pour permettre aux recherches effectuées par le programme gestionnaire de rechercher également dans les trousseaux de clés du

demandeur.

Voir request_key(2), keyctl_assume_authority(3), keyctl_instantiate(3), keyctl_negate(3), keyctl_reject(3), request-key(8), et request-key.conf(5) po

ur plus d'in
formations.

Les champs affichés dans chaque ligne sont les suivants :
uid
L'identifiant de l'utilisateur.
usage
Il s'agit d'un compteur d'utilisation interne au noyau pour la structure du noyau utilisée pour enregistrer les utilisateurs clés.
nkeys/nikeys
Le nombre total de clés appartenant à l'utilisateur, et le nombre de ces clés qui ont été instanciées.
qnkeys/maxkeys
Le nombre de clés appartenant à l'utilisateur, et le nombre maximum de clés que l'utilisateur peut posséder.
qnbytes/maxbytes
Le nombre d'octets consommés dans les charges utiles des clés appartenant à cet utilisateur, et la limite supérieure du nombre d'octets dans les charges utiles de clés pour cet utilisateur.
/proc/sys/kernel/keys/gc_delay (depuis Linux 2.6.32)
La valeur de ce fichier spécifie l'intervalle, en secondes, après lequel les clés révoquées et expirées seront collectées. Le but de cet intervalle est qu'il y ait une fenêtre de temps pendant laquelle l'espace utilisateur peut voir une erreur (respectivement EKEYREVOKED et EKEYEXPIRED) qui indique ce qui est arrivé à la clé.
La valeur par défaut dans ce fichier est 300 (c'est-à-dire 5 minutes).
/proc/sys/kernel/keys/persistent_keyring_expiry (depuis Linux 3.13)
Ce fichier définit un intervalle, en secondes, auquel le minuteur d'expiration du keyring persistant est réinitialisé chaque fois que le keyring est accédé (via keyctl_get_persistent(3) ou l'opération keyctl(2) KEYCTL_GET_PERSISTENT).
La valeur par défaut dans ce fichier est 259200 (c'est-à-dire 3 jours).

Les fichiers suivants (qui sont inscriptibles par les processus privilégiés) sont utilisés pour appliquer des quotas sur le nombre de clés et le nombre d'octets de données qui peuvent être stockés dans les charges utiles des clés :

/proc/sys/kernel/keys/maxbytes (depuis Linux 2.6.26)
C'est le nombre maximum d'octets de données qu'un utilisateur non root peut détenir dans les charges utiles des clés appartenant à l'utilisateur.
La valeur par défaut dans ce fichier est 20 000.
/proc/sys/kernel/keys/maxkeys (depuis Linux 2.6.26)
C'est le nombre maximum de clés qu'un utilisateur non root peut posséder.
La valeur par défaut dans ce fichier est 200.
/proc/sys/kernel/keys/root_maxbytes (depuis Linux 2.6.26)
C'est le nombre maximum d'octets de données que l'utilisateur root (UID 0 dans l'espace de noms root) peut détenir dans les charges utiles des clés appartenant à root.
La valeur par défaut dans ce fichier est 25 000 000 (20 000 avant Linux 3.17).
/proc/sys/kernel/keys/root_maxkeys (depuis Linux 2.6.26)
C'est le nombre maximum de clés que l'utilisateur root (UID 0 dans l'espace de noms root) peut posséder.
La valeur par défaut dans ce fichier est 1 000 000 (200 avant Linux 3.17).

En ce qui concerne les keyrings, notez que chaque lien dans un keyring consomme 4 octets de la charge utile du keyring.
