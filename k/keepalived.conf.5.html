NOM

keepalived.conf - fichier de configuration pour Keepalived

Note :

Cette documentation DOIT être considérée comme LA source d'information exhaustive pour configurer Keepalived. Cette documentation est supportée et maintenue par l'Équipe Principale de Keepalived.

DESCRIPTION

keepalived.conf est le fichier de configuration qui décrit tous les mots-clés de Keepalived. Les mots-clés sont placés dans des hiérarchies de blocs et de sous-blocs, chaque niveau étant délimité par des paires de '{' et '}'.

Les commentaires commencent par '#' ou '!' jusqu'à la fin de la ligne et peuvent commencer n'importe où sur une ligne.

Le mot-clé 'include' et ses variantes permettent d'inclure d'autres fichiers de configuration à partir du fichier de configuration principal, ou à partir de fichiers inclus ultérieurement.

Le format de la directive include est :

include NOMFICHIER

NOMFICHIER peut être un chemin absolu ou relatif, et peut inclure des jokers, y compris des expressions entre accolades de style csh telles que "{foo/{,cat,dog},bar}" si glob() les supporte.

Après avoir ouvert un fichier inclus, le répertoire courant est défini sur le répertoire du fichier lui-même, de sorte que tout chemin relatif inclus à partir d'un fichier est relatif au répertoire du fichier incluant lui-même.

Les variantes de include ajoutent des vérifications d'inclusion supplémentaires au niveau actuel de include_check (voir ci-dessous). Les variantes sont :
includer NOMFICHIER - identique à include_check readable
includem NOMFICHIER - identique à include_check match
includew NOMFICHIER - identique à include_check wildcard_match
includeb NOMFICHIER - identique à include_check brace_match
includea NOMFICHIER - tous les contrôles include_check

NOTE : Si la fonction glob() de libc ne supporte pas GLOB_ALTDIRFUNC (par exemple, Musl libc comme sur Alpine Linux etc.), alors seules les options includea, includer et includew parmi les options ci-dessus fonctionneront.

Pourquoi voulons-nous autoriser les erreurs ? Supposons qu'une configuration ait des fichiers optionnels dans /etc/keepalived/conf.d, alors include_/etc/keepalived/conf.d/* pourrait être spécifié, mais cela ne devrait pas générer d'erreur s'il n'y a pas de fichiers dans le répertoire ; dans ce cas, includer devrait être utilisé. Sinon, il est logique d'utiliser includea.

La gestion de include ne fonctionnera pas si la ligne include utilise une configuration conditionnelle ou une substitution de paramètre, car la détection des mots-clés include est effectuée avant le traitement de la configuration conditionnelle et de la substitution de paramètre.

Le mot-clé include de base est conservé pour la compatibilité ascendante, car il ne produit pas d'erreurs de configuration si les fichiers ne peuvent pas être ouverts, etc.

SYNTAXE DES PARAMÈTRES

<BOOL> est l'un des on|off|true|false|yes|no
<TIMER> est une valeur de temps en secondes, y compris des fractions de seconde, par exemple 2.71828 ou 3 ; la résolution du timer est en microsecondes.

SCRIPTS

Trois types de scripts peuvent être configurés pour être exécutés.

(a) Scripts de notification qui sont exécutés lorsqu'une instance vrrp ou un groupe vrrp change d'état, ou qu'un quorum de serveur virtuel passe de l'état actif à inactif.

(b) Scripts de suivi vrrp qui provoqueront la désactivation des instances vrrp si elles se terminent avec un code de sortie non nul, ou si un poids est spécifié, ajouteront ou soustrairont ce poids à/de la priorité de cette instance vrrp.

(c) Scripts divers de vérification LVS qui provoqueront la mise en état inactif d'un serveur réel s'ils se terminent avec un statut non nul.

Par défaut, les scripts seront exécutés par l'utilisateur keepalived_script si cet utilisateur existe, sinon par root, mais pour chaque script, l'utilisateur/groupe sous lequel il doit être exécuté peut être spécifié.

Il y a des implications de sécurité importantes si les scripts sont exécutés avec des privilèges root, surtout si les scripts eux-mêmes sont modifiables ou remplaçables par un utilisateur non root. Par conséquent, des vérifications de sécurité sont effectuées au démarrage pour s'assurer que si un script est exécuté par root, il ne peut pas être modifié ou remplacé par un utilisateur non root.

Tous les scripts doivent être écrits de manière à se terminer à la réception d'un signal SIGTERM. Les scripts recevront SIGTERM si leur processus parent se termine, ou s'il s'agit d'un script dont keepalived attend le code de sortie et qu'il s'exécute trop longtemps.

Chaines entre guillemets

Les chaînes entre guillemets sont spécifiées entre des caractères " ou ' et les chaînes sont délimitées par des espaces. Dans les exemples ci-dessous, les caractères ´ ne font pas partie des chaînes et ne doivent pas être spécifiés :

´abcd" efg h jkl "mnop´
sera la chaîne unique : 
´abcd efg h jkl mnop´
alors que :

´abcd "efg h jkl" mnop´

sera les trois chaînes :

´abcd´, ´efg h jkl´ et ´mnop´
c'est-à-dire que les caractères " et ' sont supprimés et tout espace blanc intermédiaire est conservé.
Les chaînes entre guillemets peuvent également contenir des caractères échappés, comme dans le shell. \a, \b, \E, \f,
\n, \r, \t, \v, \nnn et \xXX (où nnn représente jusqu'à 3 chiffres octaux, et XX jusqu'à deux chiffres hexadécimaux) et \cC (qui produit la version de contrôle du caractère C) sont tous supportés. \C pour tout autre caractère C est simplement traité comme une version échappée du caractère C, donc \\ est un caractère \ et \" sera un caractère ", mais il ne commencera ni ne terminera une chaîne entre guillemets.
Pour spécifier des scripts avec des paramètres, les espaces non entre guillemets sépareront les paramètres.
S'il est nécessaire qu'un paramètre contienne un espace, il doit être entouré de guillemets simples ('). Par exemple

$SG_NAME=SG1
$INST=low
$USER=user
notify_master "/etc/keepalived/notify_event.sh ' espaces\\x20f\x69le ' '\"s p a c e \"' ${SG_NAME}.$INST master" $USER group

spécifie un script notify_master /etc/keepalived/notify_event.sh qui sera exécuté par l'utilisateur:groupe avec les paramètres

´ espaces\x20f\x69le ´, ´"s p a c e "´, ´SG1.low´ et ´master´

Le bloc linkbeat_interfaces permet de spécifier quelles interfaces doivent utiliser le sondage via MII, Ethtool ou le statut ioctl plutôt que de s'appuyer sur les mises à jour de statut netlink. Cela permet un contrôle plus granulaire de la définition globale linkbeat_use_polling

.

Cette option est préférée à l'utilisation dépréciée de linkbeat_use_polling dans un bloc vrrp_instance, car cette dernière ne permet que d'utiliser linkbeat sur l'interface de la vrrp_instance elle-même, alors que track_interface et virtual_ipaddresses et virtual_iproutes peuvent nécessiter la surveillance d'autres interfaces, qui peuvent avoir besoin d'utiliser le sondage

linkbeat.

Le type de sondage par défaut à utiliser est MII, sauf si ce n'est pas pris en charge, auquel cas ETHTOOL est utilisé, et si ce n'est pas pris en charge, alors le sondage ioctl. Le type de sondage préféré à utiliser peut être spécifié avec MII ou ETHTOOL ou IOCTL après le nom de l'interface, mais si ce type n'est pas pris en charge, un type pris en charge sera

utilisé.

La syntaxe pour linkbeat_interfaces est

: 
    linkbeat_interfaces {
        eth2
        enp2s0 ETHTOOL
}

Fichiers de

suivi

Ajoute un fichier à surveiller. Le fichier sera lu chaque fois qu'il est modifié. La valeur dans le fichier sera enregistrée pour toutes les instances VRRP, les groupes de synchronisation et les serveurs réels qui le surveillent. Notez que le fichier ne sera lu que si au moins une instance VRRP, un groupe de synchronisation ou un serveur réel le

surveille.

Une valeur sera lue comme un nombre en texte à partir du fichier. Si le poids configuré pour le track_file est 0, une valeur non nulle dans le fichier sera traitée comme un état d'échec, et une valeur zéro sera traitée comme un état OK, sinon la valeur sera multipliée par le poids configuré dans l'instruction

track_file.

Pour les instances VRRP, si le résultat est inférieur à -253, tout ce qui surveille le script passera à l'état de défaillance (le poids peut être 254 pour permettre une valeur négative lue depuis le fichier)

.

Si l'instance vrrp ou le groupe de synchronisation n'est pas le propriétaire de l'adresse et que le résultat est compris entre -253 et 253, le résultat sera ajouté à la priorité initiale de l'instance VRRP (une valeur négative réduira la priorité), bien que la priorité effective soit limitée à l'intervalle [1,254]. De même pour les serveurs

réels.

Si une instance vrrp utilisant un track_file est membre d'un groupe de synchronisation, sauf si sync_group_tracking_weight est défini sur le groupe, le poids 0 doit être défini. De même, si l'instance vrrp est le propriétaire de l'adresse, le poids 0 doit également être

défini.

Pour les serveurs réels surveillant le fichier, les limites des valeurs lues à partir du fichier de suivi sont 2147483648 à -2147483648. La valeur, une fois multipliée par le poids, sera ajoutée au poids IPVS du serveur réel. Si le résultat est <= à 2147483648, alors le vérificateur sera dans l'état

FAULT.

REMARQUE : les poidsr track_file pour les serveurs réels ne sont pas entièrement implémentés. En particulier, l'autorisation de poids 0, la gestion des valeurs calculées négatives et le rechargement.

La syntaxe pour le fichier de suivi est :
track_file <CHAÎNE> {	# vrrp_track_file est un synonyme déprécié
    # fichier à suivre (poids par défaut 1)
    file <CHAÎNE ENTRE GUILLEMETS>
    # poids par défaut facultatif
    weight <-2147483647..2147483647> [reverse]
    # créer le fichier et/ou initialiser la valeur
    # Cela provoque l'écriture de VALUE (par défaut 0) dans
    # le fichier spécifié au démarrage si le fichier n'existe pas,
    # sauf si overwrite est spécifié, auquel cas
    # le contenu de tout fichier existant sera écrasé avec
    # la valeur spécifiée.
    init_file [VALUE] [overwrite]
}

Suivi des processus VRRP

Le bloc de configuration ressemble à ceci :
    vrrp_track_process <CHAÎNE> {
        # processus à surveiller (avec des paramètres facultatifs)
        # Une chaîne entre guillemets est traitée comme un seul élément, donc si le premier élément
        # après le mot-clé process est entre guillemets, ce sera le nom de la commande.
        # Par exemple :
        #  process "/tmp/a b" param1 "param 2"
        # signifierait un processus nommé '/tmp/a b' (guillemets supprimés) avec 2 paramètres
        #  'param1' et 'param 2'.
        process <CHAÎNE>|<CHAÎNE ENTRE GUILLEMETS> [<CHAÎNE>|<CHAÎNE ENTRE GUILLEMETS> ...]
        # Si les paramètres correspondent, cela spécifie une correspondance partielle (c'est-à-dire que les n premiers paramètres correspondent exactement), ou une correspondance initiale, c'est-à-dire que le dernier paramètre peut être plus long que le paramètre configuré.
        # Pour spécifier qu'une commande ne doit avoir aucun paramètre, ne spécifiez
        # aucun paramètre, mais spécifiez param_match.
        param_match {initial|partial}
        # poids par défaut (par défaut est 0). Pour la description de reverse, voir track_process.
        # 'weight 0 reverse' fera que l'instance vrrp sera en panne lorsque le
        #   quorum sera actif, et vice versa.
	# Un poids non nul ajustera la priorité VRRP de l'instance VRRP de suivi,
	#   tandis qu'un poids de 0 fera passer l'instance VRRP à l'état FAULT si le
	#   processus de suivi est en état d'échec (voir ci-dessus pour l'effet de "reverse").
        weight <-254..254> [reverse]
        # nombre minimum de processus pour réussir (par défaut 1)
        quorum NUM
        # nombre maximum de processus pour réussir. Par exemple, définir
        #   cela sur 1 provoquerait un échec si deux instances du processus
        #   tournaient (mais attention aux forks - voir fork_delay ci-dessous).
        #   Définir cela sur 0 signifierait un échec si le processus correspondant était
        #   en cours d'exécution.
	#   La valeur par défaut est illimitée.
        quorum_max NUM
        # temps de délai après l'obtention du quorum de processus après un fork avant
        #   de considérer le processus comme actif (en fractions de seconde)
        #   Ceci est pour éviter les rebonds haut/bas pour fork/exec
        fork_delay SECS
        # temps de délai après la perte du quorum de processus avant
        #   de considérer le processus comme inactif (en fractions de seconde)
        #   Ceci est pour éviter les rebonds bas/haut après la terminaison/le refork du parent.
        terminate_delay SECS
        # cela définit fork_delay et terminate_delay
        delay SECS
        # Normalement, la chaîne de processus est comparée au nom du processus,
        #   comme indiqué sur la ligne Name: dans /proc/PID/status, sauf si
        #   des paramètres sont spécifiés.
        #   Cette option force la comparaison de la ligne de commande complète
        full_command
    }

Pour éviter d'avoir à exécuter fréquemment un script de suivi pour surveiller l'existence de processus (souvent haproxy ou nginx), vrrp_track_process peut surveiller si d'autres processus sont en cours d'exécution.

Une différence par rapport à pgrep est que track_process ne fait pas de correspondance d'expression régulière de la chaîne de commande, mais fait une correspondance exacte. 'pgrep ssh' correspondra à un processus sshd, ce track_process ne le fera pas (il est équivalent à pgrep ""^ssh$"").

Si full_command est utilisé (équivalent à pgrep -f), /proc/PID/cmdline est utilisé, mais toute mise à jour de cmdline ne sera pas détectée (un processus ne devrait normalement pas la modifier, bien que cela soit possible avec une grande prudence, par exemple systemd).

Avant Linux v3.2, track_process ne prend pas en charge la détection des modifications du nom d'un processus, car le noyau ne notifiait pas les modifications du nom du processus avant 3.2. La plupart des processus ne modifient pas leur nom, mais, par exemple, firefox crée des processus qui modifient leur nom en "Web Content". Le nom du processus mentionné ici est le contenu de /proc/PID/comm.

Le quorum est le nombre de processus correspondants qui doivent être exécutés pour un statut OK.

Le délai peut être utile s'il est anticipé qu'un processus peut être rechargé (arrêté et redémarré), et qu'il n'est pas souhaitable de faire monter et descendre une instance vrrp.

Un poids positif signifie qu'un statut OK ajoutera <poids> à la priorité de toutes les instances VRRP qui le surveillent. Inversement, un poids négatif sera soustrait de la priorité initiale en cas de processus insuffisants.

Si l'instance vrrp ou le groupe de synchronisation n'est pas le propriétaire de l'adresse et que le résultat est compris entre -253 et 253, le résultat sera ajouté à la priorité initiale de l'instance VRRP (une valeur négative réduira la priorité), bien que la priorité effective sera limitée à la plage [1,254].

Si une instance vrrp utilisant un track_process est membre d'un groupe de synchronisation, à moins que sync_group_tracking_weight ne soit défini sur le groupe, le poids 0 doit être défini. De même, si l'instance vrrp est le propriétaire de l'adresse, le poids 0 doit également être défini.

Raison de ne pas utiliser pgrep/pidof/killall et leurs équivalents :

Chaque fois que pgrep ou son équivalent est exécuté, il parcourt les répertoires /proc/[1-9][0-9]* et ouvre les fichiers pseudo status et cmdline dans chaque répertoire. Le fichier pseudo cmdline est mappé dans l'espace d'adressage du processus, donc si cette partie du processus est échangée, elle devra être récupérée de l'espace d'échange. pgrep etc incluent également les processus zombies alors que keepalived ne le fait pas, car ils ne sont pas en cours d'exécution.

Cette implémentation parcourt uniquement les répertoires /proc/[1-9][0-9]*/ au démarrage, et elle ne lira même pas les fichiers pseudo cmdline si 'full_command' n'est pas spécifié pour l'une des entrées vrrp_track_process. Après le démarrage, elle utilise le connecteur process_events kernel <-> userspace pour recevoir des notifications de modifications de processus. Si full_command est spécifié pour une instance track_process, le fichier pseudo cmdline devra être lu lors de la notification de la création du nouveau processus, mais à ce moment-là, il est très peu probable qu'il ait déjà été échangé.

Sur un système chargé avec un grand nombre de créations/terminaisons de processus, l'utilisation d'un track_script avec pgrep/pidof/killall peut être plus efficace, bien que ces processus soient inefficaces par rapport au minimum requis par keepalived.

L'utilisation de pgrep etc sur un système qui swappe peut avoir un impact négatif significatif sur les performances du système, en raison de la nécessité de récupérer la mémoire swappée depuis l'espace d'échange, entraînant ainsi un swappage supplémentaire.

CONFIGURATION BFD

Il s'agit d'une implémentation de la RFC5880 (Bidirectional forwarding detection), et elle peut être configurée pour fonctionner entre 2 instances keepalived, mais l'utilisation de track_bfds non pondérés entre une paire maître/sauvegarde d'instances VRRP signifie que l'instance VRRP ne pourra monter que si les deux instances VRRP fonctionnent, ce qui va quelque peu à l'encontre de l'objectif de VRRP.

Cette implémentation a été testée avec OpenBFDD (disponible à l'adresse https://github.com/dyninc/OpenBFDD).

La syntaxe pour l'instance bfd est :
bfd_instance <CHAÎNE> {
    # IP voisine BFD (synonyme neighbour_ip)
    neighbor_ip <ADRESSE IP>
    # IP source à utiliser (facultatif, sauf pour garantir que le port local est valide, il est requis)
    source_ip <ADRESSE IP>
    # Intervalle RX min requis, en ms (résolution microsecondes, par exemple 3.312)
    # (par défaut 10 ms)
    min_rx <DÉCIMAL>
    # Intervalle TX min souhaité, en ms (résolution microsecondes)
    # (par défaut 10 ms)
    min_tx <DÉCIMAL>
    # Intervalle TX inactif souhaité, en ms (résolution microsecondes)
    # (par défaut 1000 ms)
    idle_tx <DÉCIMAL>
    # Nombre de paquets manqués après lequel la session est déclarée en panne
    # (par défaut 5)
    multiplier <ENTIER>
    # Fonctionner en mode passif (par défaut actif)
    passive
    # TTL IPv4 sortant à utiliser (par défaut 255)
    ttl <ENTIER>
    # Hoplimit IPv6 sortant à utiliser (par défaut 64)
    hoplimit <ENTIER>
    # réduction maximale du ttl/hoplimit dans le paquet reçu (par défaut 0)
    # (255 désactive la vérification du nombre de sauts)
    max_hops <ENTIER>
    # La RFC 5883 spécifie que le port 4784 doit être utilisé pour le bfd multihop, plutôt que
    # le port 3784. La spécification de multihop active cette option, mais si plusieurs sauts
    # sont utilisés, max_hops (voir ci-dessus) devra également être configuré.
    multihop [<BOOL>]
    # Poids de suivi par défaut
    # Normalement, les poids positifs sont ajoutés à la priorité de l'instance vrrp lorsque
    # l'instance bfd est active, les poids négatifs réduisent la priorité lorsqu'elle est inactive.
    # Cependant, si reverse est spécifié, un poids positif diminue la priorité lorsque
    # le script est actif, et un poids négatif augmente la priorité lorsque le script est inactif.
    # 'weight 0 reverse' fera que l'instance vrrp sera en panne lorsque l'instance bfd
    # est active, et vice versa.
    # Poids  Reverse  Script actif   Script inactif
    #  +ve      Non	prio +		-
    #  -ve	Non	   -	     prio -
    #  +ve      Oui	prio -		-
    #  -ve	Oui	   -	     prio +
    weight <-253:253> [reverse]
    # Normalement, les notifications d'événements bfd sont envoyées aux processus VRRP et checker.
    # La spécification de vrrp ou checker provoquera l'envoi des notifications d'événements pour cette instance bfd uniquement
    # au processus spécifié
    vrrp
    checker
}

Groupe(s) de synchronisation

VRRP

Le groupe de synchronisation VRRP est une extension du protocole VRRP. Le but principal est de définir un ensemble d'instances VRRP pour les synchroniser afin que la transition d'une instance soit réfléchie sur les autres membres du

groupe.

De plus, il existe une fonctionnalité de notification améliorée pour capter les transitions d'état

fines.

Vous pouvez également définir plusieurs politiques de suivi pour forcer la transition d'état selon un événement tiers tel qu'une interface, des scripts, un fichier,

BFD.

Important : pour qu'un groupe de synchronisation fonctionne de manière fiable, il est vital que toutes les instances du groupe soient MASTER ou qu'elles soient toutes soit BACKUP ou FAULT. Une situation où certaines instances ont une priorité plus élevée sur la machine A et d'autres ont une priorité plus élevée sur la machine B conduira à des réélections constantes. Pour cette raison, lorsque des instances sont regroupées, tout script/fichier de suivi configuré contre les instances VRRP membres doit avoir leurs poids de suivi non définis (c'est-à-dire égaux à zéro). Tout suivi avec une priorité non nulle sera

ignoré. 
La syntaxe pour vrrp_sync_group est :
vrrp_sync_group <STRING> {
    group {
        # nom du vrrp_instance (voir ci-dessous)
        # Ensemble de chaînes VRRP_Instance
        <STRING>
        <STRING>
        ...
    }
    # Le suivi d'interface, de script, de fichier et de bfd du groupe de synchronisation mettra
    # à jour le statut/priorité de toutes les instances VRRP qui sont membres
    # du groupe de synchronisation.
    # 'weight 0 reverse' fera que l'instance vrrp sera en panne lorsque
    # l'interface est active, et vice versa.
    track_interface {
        eth0
        eth1
        eth2 weight <-253..253> [reverse]
        ...
    }
    # ajoute un script de suivi au groupe de synchronisation (<SCRIPT_NAME> est le nom
    # de l'entrée vrrp_script) passe à l'état FAULT si l'un d'entre eux tombe en panne
    # s'il n'est pas pondéré.
    # reverse inverse la direction de l'ajustement de la priorité.
    track_script {
        <SCRIPT_NAME>
        <SCRIPT_NAME> weight <-253..253> [reverse|noreverse]
    }
    # Fichiers dont nous surveillons l'état, la valeur est ajoutée à la priorité effective.
    # <STRING> est le nom d'un track_file
    # le poids par défaut est celui configuré dans track_file
    track_file {
        <STRING>
        <STRING> weight <-254..254> [reverse|noreverse]
        ...
    }
    # Processus à surveiller, le poids est ajouté à la priorité effective.
    # <STRING> est le nom d'un vrrp_track_process
    # le poids par défaut est celui configuré dans vrrp_track_process.
    # Voir vrrp_instance track_process pour la description du poids.
    track_process {
        <STRING>
        <STRING> weight <-254..254> [reverse|noreverse]
        ...
    }
    # Instances BFD que nous surveillons, la valeur est ajoutée à la priorité effective.
    # <STRING> est le nom d'une instance BFD
    track_bfd {
        <STRING>
        <STRING>
        <STRING> weight <INTEGER: -253..253> [reverse|noreverse]
        ...
    }
    # les scripts et alertes de notification sont facultatifs
    #
    # les noms de fichiers des scripts à exécuter lors des transitions peuvent être non quotés (si
    # c'est juste un nom de fichier) ou quotés (s'ils ont des paramètres)
    # Le nom d'utilisateur et le nom de groupe spécifient l'utilisateur et le groupe
    # sous lesquels les scripts doivent être exécutés. Si le nom d'utilisateur est
    # spécifié, le groupe par défaut est le groupe de l'utilisateur.
    # Si le nom d'utilisateur n'est pas spécifié, ils prennent par défaut les valeurs globales
    # script_user et script_group
    # pour la transition vers MASTER
    notify_master /path/to_master.sh [username [groupname]]

Instance(s)

VRRP

Une instance VRRP est la fonctionnalité clé du protocole VRRP. Elle définit et configure le comportement de VRRP pour s'exécuter sur une interface spécifique. Chaque instance VRRP est liée à une interface

unique. 
La syntaxe pour vrrp_instance est :
vrrp_instance <STRING> {

    # Si la priorité est 255, l'instance passera immédiatement
    # à MASTER si l'état MASTER est spécifié ; sinon l'instance
    # attendra entre 3 et 4 intervalles de publicité avant de pouvoir transitionner,
    # en fonction de la priorité.
    state MASTER

    #   les adresses unicast ne sont pas des adresses IPv6 de lien local (c'est

    #   l'interface sur laquelle elles doivent être configurées, sinon elles seront
    #   ajoutées à l'interface par défaut.

    # sur le macvlan.

    # macvlan, sauf si vmac_xmit_base est configuré.

    # et que cette vrrp_instance est une instance IPv4, l'utilisation

    # mises à jour au plus grand de leur paramètre actuel et
    # all.rp_filter, comme le sera default.rp_filter, et all.rp_filter
    # sera défini à 0.
    # Les paramètres d'origine sont restaurés à la terminaison.
    # NOTE 2 : Si vous utilisez use_vmac avec des pairs unicast,
    # vmac_xmit_base doit être défini.
    # L'adresse MAC peut être spécifiée avec seulement 5 octets, auquel cas
    # le virtual_router_id sera utilisé comme dernier octet.
    # Si netlink_notify_msg est spécifié, lorsque keepalived crée une interface macvlan

    # Si reverse est spécifié, l'addition/soustraction est inversée.
    # <STRING> est le nom d'un vrrp_track_process
    # weight a pour valeur par défaut le poids configuré dans vrrp_track_process
    track_process {
        <STRING>
        <STRING> weight <-254..254> [reverse|noreverse]
        ...
    }

    # sauf si reverse est spécifié, auquel cas la valeur est soustraite.
    # Les poids positifs sont ajoutés/soustraits lorsque l'instance bfd est active,
    # les poids négatifs sont soustraits/ajoutés lorsque l'instance bfd est inactive.
    # <STRING> est le nom d'une instance BFD
    track_bfd {
        <STRING>
        <STRING>

    # (puisque c'est du multicast, vrrpd recevra le paquet de réponse

    # optionnel
    mcast_src_ip <IPADDR>
    unicast_src_ip <IPADDR>

    # pour les annonces VRRP et pour écouter les annonces. Notez que si vous utilisez
    # plusieurs instances VRRP avec des VMAC et des adresses multicast différentes

    # Les adresses multicast IPv6 doivent être link-local, c'est-à-dire commencer par ffX2 :

    # l'instance en état de défaut

        # Seuls les huit (8) premiers caractères sont utilisés.
        auth_pass 1234
    }
    # adresses add|del lors du passage à MAÎTRE, à SECOURS.
    # Avec les mêmes entrées sur les autres machines,
    # la transition opposée se produira.
    # Pour virtual_ipaddress, virtual_ipaddress_excluded,
    #   virtual_routes et virtual_rules, la plupart des options
    #   correspondent aux options des commandes ip address/route/rule add.
    #   L'option track_group ne s'applique qu'aux adresses/règles/routes statiques.
    #   no_track est spécifique à keepalived et signifie que la
    #   vrrp_instance ne sortira pas de l'état maître
    #   si l'adresse/route/règle est supprimée et que l'adresse/route/règle
    #   ne sera pas rétablie jusqu'à ce que l'instance VRRP passe à nouveau
    #   en mode maître.
    # <LABEL> : est facultatif et crée un nom pour l'alias.
               Pour la compatibilité avec "ifconfig", il devrait
               être de la forme <realdev>:<anytext>, par exemple
               eth0:1 pour un alias sur eth0.
    # <SCOPE> : ("site"|"link"|"host"|"nowhere"|"global")
    # preferred_lft est défini à 0 pour déprécier les adresses IPv6 (c'est la
    # valeur par défaut si le masque d'adresse est /128). Utilisez "preferred_lft forever"
    # pour spécifier qu'une adresse /128 ne doit pas être dépréciée.
    # REMARQUE : il faut faire attention si dev est spécifié pour une adresse et que
    # votre réseau utilise des commutateurs avec apprentissage MAC. Le protocole VRRP garantit
    # que l'adresse MAC source de l'interface envoyant les publicités est
    # maintenue dans le cache MAC des commutateurs ; cependant, par défaut, cela
    # ne fonctionnera pas pour les MAC des VIPs/eVIPs configurées sur
    # des interfaces différentes de celle sur laquelle l'instance VRRP est
    # configurée, car l'interface, surtout s'il s'agit d'une interface VMAC,
    # n'enverra qu'avec l'adresse MAC de l'interface en réponse aux
    # requêtes ARP. Cela peut signifier que les adresses MAC des interfaces peuvent
    # expirer dans les caches MAC des commutateurs. Pour éviter cela, utilisez
    # les options garp_extra_if ou garp_extra_if_vmac pour envoyer périodiquement
    # des messages GARP/ND sur ces interfaces.
    virtual_ipaddress {
        <IPADDR>[/<MASK>] [brd <IPADDR>] [dev <STRING>] [use_vmac] [scope <SCOPE>]

                          [-nodad] [mngtmpaddr] [noprefixroute]
                          [autojoin] [no_track] [preferred_lft nn|forever]
        192.168.200.17/24 dev eth1
        192.168.200.18/24 dev eth2 label eth2:1
    }

    # Pour les cas avec un grand nombre (ex. 200) d'IP
    # sur la même interface. Pour diminuer le nombre
    # d'adresses envoyées dans les publicités, vous pouvez exclure
    # la plupart des IP des publicités.
    # Les IP sont ajoutées|supprimées comme pour virtual_ipaddress.
    # Peut également être utilisé si vous voulez pouvoir ajouter
    # un mélange d'adresses IPv4 et IPv6, car toutes
    # les adresses dans virtual_ipaddress doivent être de la
    # même famille.
    virtual_ipaddress_excluded {
        <IPADDR>[/<MASK>] [brd <IPADDR>] [dev <STRING>] [scope <SCOPE>]
                          [label <LABEL>] [peer <IPADDR>] [home]
                          [-nodad] [mngtmpaddr] [noprefixroute]
                          [autojoin] [no_track]
        <IPADDR>[/<MASK>] ...
        ...
    }

    # et la version 3 de VRRP indique explicitement que le nombre minimum d'adresses
    # est 1. Par conséquent, keepalived émet un avertissement si aucune VIP n'est configurée.
    # Il existe cependant des circonstances où il est utile de ne pas avoir de VIP, par
    # exemple avec des serveurs cloud, ex. AWS, où les adresses IP flottantes sont
    # gérées administrativement et ne sont pas configurées sur le serveur virtuel
    # cloud. Spécifier no_virtual_ipaddress supprime les avertissements pour l'absence de VIP,
    # et permet l'utilisation de VRRPv3 sans VIP.
    # AVERTISSEMENT - l'utilisation de ceci avec VRRPv3 constitue une violation de protocole et
    # peut ne pas fonctionner avec d'autres implémentations VRRP.
    no_virtual_ipaddress
    # Définir le drapeau promote_secondaries sur l'interface pour empêcher d'autres
    # adresses dans le même CIDR d'être supprimées lorsque l'une d'elles est supprimée.

    promote_secondaries

    # propriétaire de l'adresse, de recevoir les paquets adressés à une VIP. C'est le réglage

    # VRRPv2 (RFC 3768 ne définit pas de mode accept).
    # --
    # Accepter les paquets destinés à un non-propriétaire d'adresse
    accept
    # Rejeter les paquets destinés à un non-propriétaire d'adresse.
    no_accept

    # le rôle de maître, et permet à la machine de priorité inférieure de rester
    # maître.
    # REMARQUE : Pour que cela fonctionne, l'état initial ne doit pas être MAÎTRE.
    # --
    nopreempt
    # pour la rétrocompatibilité
    preempt

    #

    # Si strict_mode sans paramètre est spécifié, il est activé par défaut.
    strict_mode [<BOOL>]

    # LEVEL est un nombre dans la plage 0 à 4
    debug <LEVEL>

    notify_master <STRING>|<QUOTED-STRING> [username [groupname]]
    notify_backup <STRING>|<QUOTED-STRING> [usernom [nom_groupe]]

    notify_master_rx_lower_pri <CHAÎNE>|<CHAÎNE_ENTRE_GUILLEMETS> [nom_utilisateur [nom_groupe]]

    notify_priority_changes <BOOLÉEN>

    smtp_alert <BOOLÉEN>

    kernel_rx_buf_size

    # obsolète - utilisez le bloc linkbeat_interfaces à la place.
    linkbeat_use_polling

Antirebond de changement d'état de l'interface haut/bas


Si une interface utilisée (ou suivie) par une instance VRRP passe à l'état bas,
les instances VRRP passeront, par défaut, immédiatement à l'état FAULT, et lorsque
toutes les interfaces pertinentes seront de nouveau opérationnelles, les instances VRRP passeront
immédiatement à l'état BACKUP.


Cela peut poser des problèmes si les interfaces fluctuent, et donc des délais peuvent être spécifiés
entre le changement d'état de l'interface et la transition vers l'état FAULT/BACKUP. Si l'
interface revient à son état d'origine avant l'expiration du délai, aucune transition d'état VRRP associée
ne se produira.

interface_up_down_delays {
    ifname down_delay [up_delay]
    ifname2 down_delay [up_delay]
    ...
}
    Les délais sont spécifiés en secondes, avec une résolution en microsecondes, par
    exemple un délai de
    0.00001 signifie 10 microsecondes. Un délai de 0 signifie aucun délai dans le
    changement d'état. Le délai maximum pouvant être spécifié est de 255 secondes.
    Si up_delay est omis, il est défini de la même manière que le délai down.
    Le délai down sur une interface doit être inférieur à deux (ou plus précisément un
    de moins que down_timer_adverts (par défaut 3)) fois l'intervalle d'annonce de toute
    instance VRRP utilisant cette interface (sinon une instance de sauvegarde, tout
    en ne recevant pas d'annonces, peut expirer et devenir maître avant que cette
    instance ne transitionne vers l'état FAULT).
    Par conséquent, les délais haut/bas peuvent être dynamiquement réduits si une autre
    instance est maître avec un intervalle d'annonce plus court.
    Si l'instance VRRP utilise un VMAC, elle héritera des délais d'antirebond haut/bas
    de son interface parente.

CONFIGURATION LVS

contient des sous-blocs de Groupes de serveurs virtuels et Serveurs virtuels

Les sous-blocs contiennent des arguments pour configurer la fonctionnalité Linux IPVS (LVS). Une connaissance de ipvsadm(8) sera utile ici. La configuration de LVS est réalisée en définissant des groupes de serveurs virtuels, des serveurs virtuels et éventuellement une configuration SSL. Chaque serveur virtuel définit un ensemble de serveurs réels, vous pouvez attacher des vérificateurs d'état à chaque serveur réel. Keepalived dirigera alors l'opération LVS en maintenant dynamiquement la topologie.

Pour connaître les combinaisons de configuration valides, consultez la page de manuel ipvsadm(8).

Note: Là où une option peut être configurée pour un serveur virtuel, un serveur réel et éventuellement un vérificateur, le réglage du serveur virtuel est la valeur par défaut pour les serveurs réels, et le réglage du serveur réel est la valeur par défaut pour les vérificateurs.

Note: Les serveurs réels/désolés en tunnel peuvent différer de la famille d'adresses du serveur virtuel et les serveurs réels/désolés non en tunnel, qui doivent tous être identiques. Si un serveur virtuel utilise une fwmark, et que tous les serveurs réels/désolés sont en tunnel, la famille d'adresses du serveur virtuel sera la même que la famille d'adresses des serveurs réels/désolés s'ils sont tous identiques, sinon elle sera par défaut IPv4 (utilisez ip_family inet6 pour outrepasser cela).

Note: Le port du serveur virtuel ne peut être omis que si le service virtuel est persistant.

Groupe(s) de serveurs virtuels

Cette fonctionnalité offre un moyen de simplifier votre configuration en factorisant les définitions de serveurs virtuels. Si vous avez besoin de définir un ensemble de serveurs virtuels avec exactement la même topologie de serveurs réels, cette fonctionnalité rendra votre configuration beaucoup plus lisible, optimisera la duplication des serveurs virtuels IPVS si nftables_ipvs est utilisé, et optimisera la tâche de vérification d'état en ne lançant qu'un seul vérificateur d'état là où une déclaration de plusieurs serveurs virtuels lancerait un vérificateur d'état dédié pour chaque serveur réel, ce qui gaspillerait les ressources système.

Toute combinaison d'adresses IP, de plages d'adresses IP et de marques de pare-feu peut être utilisée, à condition que la famille des adresses IP du groupe de serveurs virtuels corresponde à la famille d'adresses IP de tous les serveurs réels de tout serveur virtuel utilisant le groupe de serveurs virtuels. La seule exception est que le groupe de serveurs virtuels peut être configuré avec des adresses et des fwmarks IPv4 et IPv6 à condition que tous les serveurs réels (et désolés) de tous les serveurs virtuels utilisant le groupe de serveurs virtuels utilisent le transfert par tunnel ; si des fwmarks sont spécifiés dans ce cas, la famille d'adresses doit être spécifiée (la seule exception est si le groupe de serveurs virtuels n'a pas d'adresses IP (c'est-à-dire uniquement des fwmarks) et que tous les serveurs réels/désolés sont en tunnel, il sera par défaut IPv4 ; il n'est pas recommandé de s'appuyer sur cela et les familles d'adresses des fwmarks doivent être configurées). L'utilisation de cette option est destinée aux très grands LVS, mais notez que cela peut créer un très grand nombre de serveurs virtuels à moins que nftables_ipvs ne soit utilisé. L'utilisation de nftables_ipvs est fortement recommandée en raison des optimisations et efficacités très significatives qu'elle offre.

NOTE: ne configurez pas plus d'un serveur virtuel TCP, un UDP et un SCTP avec la même famille d'adresses IP en utilisant le même groupe de serveurs virtuels (ou pour le dire autrement, n'ayez pas deux serveurs virtuels avec le même protocole et la même famille d'adresses utilisant le même groupe de serveurs virtuels) ; si tous les serveurs réels sont en tunnel, alors vous ne devez pas avoir de serveurs virtuels IPv4 et IPv6 avec le même protocole.

La syntaxe pour virtual_server_group est :
virtual_server_group <CHAÎNE> {
    # Adresse IP virtuelle et Port
    <IPADDR> [<PORT>]
    <IPADDR> [<PORT>]
    ...
    # <PLAGE_IPADDR> est l'une des formes suivantes (ou leurs équivalents IPv6)
    # XXX.YYY.ZZZ.WWW-VVV eg 192.168.200.1-10 (inclut .1 et .10)
    # AAA.BBB.CCC.DDD-EEE.FFF.GGG.HHH eg 192.168.200.250-192.168.201.10
    # III.JJJ.KKK.LLL/nn eg 192.168.202.8/29
    <PLAGE_IPADDR> [<PORT>] # Gamme VIP [VPORT]
    <PLAGE_IPADDR> [<PORT>]
    ...
    # Marque de pare-feu (fwmark)
    # inet/inet6 ne doit être spécifié que pour les groupes de serveurs virtuels
    # où tous les serveurs réels des serveurs virtuels sont en tunnel.
    fwmark <ENTIER>
    fwmark <ENTIER> [inet|inet6]
    ...
}

CONFIGURATION

AVANCÉE

L'analyseur de configuration a été étendu pour prendre en charge des fonctionnalités avancées telles q

ue la configuration conditionnelle et la substitution de paramètres. Ces fonctionnalités sont très uti
les pour tout environnement scripté où des modèles de configuration sont générés (centres de données).

Configuration conditionnelle et identifiant de

configuration

Le config-id par défaut est la première partie du nom du nœud telle que retournée par uname, et peut être remplacé par l'option de ligne de commande -i ou

--config-id.

Toute ligne de configuration commençant par '@' est une ligne de configuration conditionnelle. Le mot suivant immédiatement (c'est-à-dire sans aucun espace) le caractère '@' est comparé au config-id, et s'ils ne correspondent pas, la ligne de configuration est

ignorée.

Alternativement, '@^' est une comparaison négative, donc si le mot suivant immédiatement ne correspond PAS au config-id, la ligne de configuration EST

incluse.

Le but de cela est de permettre à un seul fichier de configuration d'être utilisé pour plusieurs systèmes, où les seules différences sont probablement le router_id, les priorités des instances vrrp, et éventuellement les noms d'interface et les adresses

unicast.

Par exemple

: 
    global_defs {
        @main   router_id main_router
        @backup router_id backup_router
    }
    ...
    vrrp_instance VRRP {
        ...
        @main    unicast_src_ip 1.2.3.4
        @backup  unicast_src_ip 1.2.3.5
        @backup2 unicast_src_ip 1.2.3.6
        unicast_peer {
            @^main    1.2.3.4
            @^backup  1.2.3.5
            @^backup2 1.2.3.6
        }
        ...
}

Si keepalived est invoqué avec -i main, alors le router_id sera défini à main_router, si inv

oqué avec -i backup, alors backup_router, si non invoqué avec -i, ou avec -i autre chose, a
lors le router_id ne sera pas défini. Les pairs unicast pour main seront 1.2.3.5 et 1.2.3.6.

Substitution de

paramètres

Des paramètres substituables peuvent être spécifiés. Le format pour définir un paramètre est

:

$PARAMETER=VALU

E

où il ne doit y avoir aucun espace avant le '=' et seul un espace blanc peut précéder le '$'. Les valeurs vides sont

autorisées.

Les noms de paramètres peuvent être composés de toute combinaison de A-Za-z0-9 et _, mais ne peuvent pas commencer par un chiffre. Les noms de paramètres commençant par un soulignement doivent être considérés comme des noms réservés que keepalived définira pour diverses options

prédéfinies.

Après qu'un paramètre a été défini, toute occurrence de $PARAMETER suivie d'un espace blanc, ou toute occurrence de ${PARAMETER} (qui n'a pas besoin d'être suivie d'un espace blanc) sera remplacée par

VALUE.

Le remplacement est récursif, de sorte que si une valeur de paramètre inclut elle-même un paramètre remplaçable, alors après la première substitution, le paramètre dans la valeur sera ensuite remplacé ; la substitution est faite au moment du remplacement et non au moment de la définition, donc par exemple

: 
    $ADDRESS_BASE=10.2.${ADDRESS_BASE_SUB}
    $ADDRESS_BASE_SUB=0
    ${ADDRESS_BASE}.100/32
    $ADDRESS_BASE_SUB=10
    ${ADDRESS_BASE}.100/32
    produira :
        10.2.0.100/32
        10.2.10.
100/32

Notez dans les exemples ci-dessus l'utilisation à la fois de ADDRESS_BASE et ADDRESS_BASE_SUB qui nécessitait des accolades ({}) puisque les paramètres n'étaient pas suivis d'un espace blanc (après la première substitution qui a produit 10.2.${ADDRESS_BASE_SUB}.100/32 le paramètre n'est toujours pas suivi d'un espace blanc)

.

Si un paramètre n'est pas défini, il ne sera pas remplacé du tout, donc par exemple ${UNDEF_PARAMETER} restera dans la configuration s'il est indéfini ; cela signifie que la configuration existante contenant un caractère '$' (par exemple dans une définition de script) ne sera pas modifiée tant que de nouvelles définitions de paramètres ne sont pas ajoutées à la

configuration.

La substitution de paramètres fonctionne en conjonction avec la configuration conditionnelle. Par exemple

: 
    @main $PRIORITY=240
    @backup $PRIORITY=200
    ...
    vrrp_instance VI_0 {
        priority $PRIORITY
    }
    produira :
        ...
        vrrp_instance VI_0 {
            priority 240
        }
        si le config_id est main.
    $IF_MAIN=@main
    $IF_MAIN priority 240
    produira :
        priority 240
        si le config_id est main et rien si le config_id n'est pas main,
        bien que l'on ne sache pas pourquoi quelqu'un voudrait utiliser cela plutôt que simplement la
        suite (mais toujours possible) :
            @main priority
240

'\'.

Blocs de

séquence

Une ligne commençant ~SEQ(var, start, step, end) fera en sorte que le reste de la ligne soit traité plusieurs fois, avec la variable $var initialement définie à start, puis $var sera incrémenté de step de manière répétée, en s'arrêtant lorsqu'il sera supérieur à end. step peut être omis, auquel cas il vaut par défaut 1 ou -1, selon que end est supérieur ou inférieur à start. start peut également être omis, auquel cas il vaut par défaut 1 si end > 0 ou -1 si end < 0. ~SEQx(...) est identique à ~SEQ(...), sauf que la variable $var sera formatée en hexadécimal, ce qui serait utile pour les adresses IPv6.

Note : Pour le moment, il est nécessaire d'utiliser des variables différentes pour le bloc ~SEQ de toute variable précédemment définie, y compris une utilisée comme variable dans un bloc ~SEQ précédent. Cela pourrait changer à l'avenir, ne vous fiez donc pas à une variable de bloc ~SEQ définie après la fin du bloc.

Exemples :

    ~SEQ(SUBNET, 0, 3) ip_address 10.0.${SUBNET}.1
    produirait :
        ip_address 10.0.0.1
        ip_address 10.0.1.1
        ip_address 10.0.2.1
        ip_address 10.0.3.1
et
    ~SEQx(SUBNET, 144, 16, 192) ip_address fe80::20:${SUBNET}:1
  ou mieux
    ~SEQx(SUBNET, 0x90, 0x10, 0xc0) ip_address fe80::20:${SUBNET}:1
    produirait :
        ip_address fe80::20:90:1
        ip_address fe80::20:a0:1
        ip_address fe80::20:b0:1
        ip_address fe80::20:c0:1
   Un autre exemple :
	virtual_ipaddress {
	    ~SEQx(AD2, 0x90, 0x10, 0xc0) ~SEQx(AD1, 0x12, -1, 0x0c) fe81::10:${AD2}:${AD1}
	}

Blocs de liste

Les blocs de liste sont similaires aux blocs de séquence, sauf que les valeurs à substituer dans la variable sont listées dans la spécification ~LST.

Une ligne commençant par ~LST(var, val1, val2, val3) fera que le reste de la ligne sera traité plusieurs fois, la variable $var étant initialement définie à val1, puis val2, et enfin val3. N'importe quel nombre de valeurs peut être spécifié, tant qu'au moins une valeur est présente (bien qu'une seule valeur serait inutile).

S'il est souhaité de substituer plusieurs variables à la fois, les variables et les valeurs doivent être entourées de blocs {...}. Par exemple :


~LST({IP, IP1}, {10,1},{20,4},{5,6},{12,8}) 192.168.${IP}.${IP1}

Il a été identifié que si proxy_arp et proxy_arp_pvlan sont activés sur une interface sur laquelle des VIP ou des eVIP sont configurés, cela peut entraîner des réponses incorrectes aux requêtes ARP, car le proxy répond aux requêtes ARP ainsi qu'à l'hôte keepalived. Les deux doivent être mis à 0 pour fonctionner correctement.
