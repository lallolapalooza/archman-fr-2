KADM5.ACL(5) MIT Kerberos KADM5.ACL(5)

NOM

kadm5.acl - Fichier ACL Kerberos

DESCRIPTION

Le démon kadmind(8) de Kerberos utilise un fichier de liste de contrôle d'accès (ACL) pour gérer les droits d'accès à la base de données Kerberos. Pour les opérations qui affectent les principaux, le fichier ACL contrôle également quels principaux peuvent opérer sur quels autres principaux.

L'emplacement par défaut du fichier ACL Kerberos est /var/lib/krb5kdc/kadm5.acl, sauf si cela est remplacé par la variable acl_file dans kdc.conf(5).

SYNTAXE

Les lignes vides et les lignes commençant par le signe dièse (#) sont ignorées. Les lignes contenant des entrées ACL ont le format :

principal  permissions  [principal_cible  [restrictions] ]

NOTE :

L'ordre des lignes dans le fichier ACL est important. La première entrée correspondante contrôlera l'accès pour un principal acteur sur un principal cible.
principal
(Nom de principal Kerberos partiellement ou entièrement qualifié.) Spécifie le principal dont les permissions sont à définir.

Chaque composant du nom peut être wildcardé en utilisant le caractère *.

permissions
Spécifie quelles opérations peuvent ou ne peuvent pas être effectuées par un principal correspondant à une entrée particulière. Il s'agit d'une chaîne d'un ou plusieurs des caractères suivants ou de leurs homologues en majuscules. Si le caractère est en majuscule, l'opération est interdite. Si le caractère est en minuscule, l'opération est autorisée.
a [Interdit] l'ajout de principaux ou de politiques
c [Interdit] le changement de mots de passe des principaux
d [Interdit] la suppression de principaux ou de politiques
e [Interdit] l'extraction des clés de principaux
i [Interdit] les interrogations sur les principaux ou les politiques
l [Interdit] le listage de tous les principaux ou politiques
m [Interdit] la modification de principaux ou de politiques
p [Interdit] la propagation de la base de données des principaux (utilisé dans incr_db_prop)
s [Interdit] la définition explicite de la clé pour un principal
x Abréviation pour admcilsp. Tous les privilèges (sauf e)
* Identique à x.

NOTE :

Le privilège extract n'est pas inclus dans le privilège joker ; il doit être attribué explicitement. Ce privilège permet à l'utilisateur d'extraire des clés de la base de données et doit être géré avec une extrême prudence pour éviter la divulgation de clés importantes comme celles des principaux kadmin/* ou krbtgt/*. L'attribut de principal lockdown_keys peut être utilisé pour empêcher l'extraction de clés de principaux spécifiques, quel que soit le privilège accordé.
principal_cible
(Optionnel. Nom de principal Kerberos partiellement ou entièrement qualifié.) Spécifie le principal sur lequel les permissions peuvent être appliquées. Chaque composant du nom peut être wildcardé en utilisant le caractère *.

principal_cible peut également inclure des références arrière à principal, où *numéro correspond au wildcard correspondant dans principal.

restrictions
(Optionnel) Une chaîne d'indicateurs. Les restrictions autorisées sont :
{+|-}nom_indicateur
l'indicateur est forcé à la valeur indiquée. Les indicateurs autorisés sont les mêmes que ceux de la variable default_principal_flags dans kdc.conf(5).
-clearpolicy
la politique est forcée à être vide.
-policy pol
la politique est forcée à être pol.
-{expire, pwexpire, maxlife, maxrenewlife} temps
(chaîne getdate) la valeur associée sera forcée à MIN(temps, valeur demandée).

Les indicateurs ci-dessus agissent comme des restrictions sur toute opération d'ajout ou de modification qui est autorisée par cette ligne ACL.

ATTENTION :

Si le fichier ACL kadmind est modifié, le démon kadmind doit être redémarré pour que les modifications prennent effet.

EXEMPLE

Voici un exemple de fichier kadm5.acl :

*/admin@ATHENA.MIT.EDU    *                               # ligne 1
joeadmin@ATHENA.MIT.EDU   ADMCIL                          # ligne 2
joeadmin/*@ATHENA.MIT.EDU i   */root@ATHENA.MIT.EDU       # ligne 3
*/root@ATHENA.MIT.EDU     ci  *1@ATHENA.MIT.EDU           # ligne 4
*/root@ATHENA.MIT.EDU     l   *                           # ligne 5
sms@ATHENA.MIT.EDU        x   * -maxlife 9h -postdateable # ligne 6

(ligne 1) Tout principal du royaume ATHENA.MIT.EDU avec une instance admin a tous les privilèges administratifs sauf l'extraction de clés.

(lignes 1-3) L'utilisateur joeadmin a toutes les permissions sauf l'extraction de clés avec son instance admin, joeadmin/admin@ATHENA.MIT.EDU (correspond à la ligne 1). Il n'a aucune permission du tout avec son instance nulle, joeadmin@ATHENA.MIT.EDU (correspond à la ligne 2). Ses instances root et autres instances non-admin, non-nulles (par exemple, extra ou dbadmin) ont des permissions d'interrogation sur tout principal ayant l'instance root (correspond à la ligne 3).

(ligne 4) Tout principal root dans ATHENA.MIT.EDU peut interroger ou changer le mot de passe de sa propre instance nulle, mais pas de toute autre instance nulle. (Ici, *1 désigne une référence arrière au composant correspondant au premier wildcard dans le principal acteur.)

(ligne 5) Tout principal root dans ATHENA.MIT.EDU peut générer la liste des principaux de la base de données et la liste des politiques de la base de données. Cette ligne est séparée de la ligne 4, car la permission de liste ne peut être accordée qu'globalement, pas à des principaux cibles spécifiques.

(ligne 6) Enfin, le principal du système de gestion de services sms@ATHENA.MIT.EDU a toutes les permissions sauf l'extraction de clés, mais tout principal qu'il crée ou modifie ne sera pas en mesure d'obtenir des tickets postdatables ou des tickets dont la durée de vie dépasse 9 heures.

NAME

kadm5.acl - Permissions file for kadmind

DESCRIPTION

The kadmind daemon uses the ACL file to determine which principals are allowed to perform which administrative operations. The ACL file is read once at startup by kadmind, and any changes made to it will not take effect until kadmind is restarted.

Each line in the ACL file is a comma-separated list of fields. A line may contain one or more of the following fields:

[principal]
The principal to which the ACL entry applies. If this field is omitted, the entry applies to all principals.
[expression]
The expression that the principal is allowed to execute. If this field is omitted, the entry applies to all operations.
[target principal]
The principal to which the operation applies. If this field is omitted, the entry applies to all principals.
[scope]
The scope of the operation. If this field is omitted, the entry applies to all scopes.

The following operations are recognized:

add
Add a principal or policy.
delete
Delete a principal or policy.
modify_principal
Modify a principal's attributes.
modify_policy
Modify a policy's attributes.
query
Query a principal or policy.
list
List principals or policies.
purge
Purge deleted principals or policies.
rename
Rename a principal or policy.
permissions
Read a principal's or policy's permissions.
unlock
Unlock a principal's account.
change_password
Change a principal's password.

The following scopes are recognized:

.*
All principals.
*.example.com
All principals in the example.com realm.
host/hostname.example.com
All principals for a specific host.

An entry in the ACL file takes the following form:

principal [expression [target_principal [scope]]] [...]

For example, the following entry allows the principal admin/admin@EXAMPLE.COM to perform any operation on any principal in the EXAMPLE.COM realm:

*/admin@EXAMPLE.COM		*	*	*

The following entry allows the principal karl/admin@EXAMPLE.COM to change the password of any principal in the EXAMPLE.COM realm:

karl/admin@EXAMPLE.COM		change_password	*	*

The following entry allows any principal to unlock their own account:

*				unlock	*	*

If no entry in the ACL file matches a given operation, the operation is denied.

SYNTAX

The ACL file is a text file with one entry per line. Each entry is a comma-separated list of fields. The fields are:

  • The principal name (e.g., user/instance@REALM). Wildcards are allowed.
  • The operation name.
  • The target principal name.
  • The scope.

The fields are optional and are processed in the order given. If a field is omitted, it is treated as a wildcard. For example, the following entry allows any principal to perform any operation on any principal:

*

The following entry allows the principal admin/admin@EXAMPLE.COM to perform any operation on any principal in the EXAMPLE.COM realm:

admin/admin@EXAMPLE.COM,*,*,*

EXAMPLE

# ACL file for kadmind






# Allow the principal 'admin/admin@EXAMPLE.COM' to do anything






admin/admin@EXAMPLE.COM		*	*	*












# Allow users in the 'admins' group to change passwords






*/admins@EXAMPLE.COM		change_password	*	*












# Allow any user to unlock their own account






*				unlock	*	*












# Deny all other operations






*				*	*	*








MODULE BEHAVIOR


The ACL file can coexist with other authorization modules in
    release 1.16 and later, as configured in the kadm5_auth
    section of krb5.conf(5). The ACL file will positively
    authorize operations according to the rules above, but will never
    authoritatively deny an operation, so other modules can authorize operations
    in addition to those authorized by the ACL file.


To operate without an ACL file, set the acl_file
    variable in kdc.conf(5) to the empty string with
    acl_file = "".

NOM


kadm5.acl - Fichier de permissions pour kadmind






DESCRIPTION


Le démon kadmind utilise le fichier ACL pour
    déterminer quels principaux sont autorisés à effectuer quelles opérations
    administratives. Le fichier ACL est lu une fois au démarrage par
    kadmind, et toute modification apportée ne prendra effet
    qu'après le redémarrage de kadmind.


Chaque ligne du fichier ACL est une liste de champs séparés par des
    virgules. Une ligne peut contenir un ou plusieurs des champs suivants :




[principal]


Le principal auquel s'applique l'entrée ACL. Si ce champ est omis, l'entrée
    s'applique à tous les principaux.


[expression]


L'expression que le principal est autorisé à exécuter. Si ce champ est omis,
    l'entrée s'applique à toutes les opérations.


[principal cible]


Le principal auquel s'applique l'opération. Si ce champ est omis, l'entrée
    s'applique à tous les principaux.


[portée]


La portée de l'opération. Si ce champ est omis, l'entrée s'applique à toutes
    les portées.




Les opérations suivantes sont reconnues :




add


Ajouter un principal ou une politique.


delete


Supprimer un principal ou une politique.


modify_principal


Modifier les attributs d'un principal.


modify_policy


Modifier les attributs d'une politique.


query


Interroger un principal ou une politique.


list


Lister les principaux ou les politiques.


purge


Purger les principaux ou les politiques supprimés.


rename


Renommer un principal ou une politique.


permissions


Lire les permissions d'un principal ou d'une politique.


unlock


Déverrouiller le compte d'un principal.


change_password


Changer le mot de passe d'un principal.




Les portées suivantes sont reconnues :




.*


Tous les principaux.


*.example.com


Tous les principaux dans le domaine example.com.


host/hostname.example.com


Tous les principaux pour un hôte spécifique.




Une entrée dans le fichier ACL prend la forme suivante :




principal [expression [principal_cible [portée]]] [...]




Par exemple, l'entrée suivante autorise le principal
    admin/admin@EXAMPLE.COM à effectuer toute opération sur tout
    principal dans le domaine EXAMPLE.COM :




*/admin@EXAMPLE.COM		*	*	*




L'entrée suivante autorise le principal
    karl/admin@EXAMPLE.COM à changer le mot de passe de tout
    principal dans le domaine EXAMPLE.COM :




karl/admin@EXAMPLE.COM		change_password	*	*




L'entrée suivante autorise tout principal à déverrouiller son propre
    compte :




*				unlock	*	*




Si aucune entrée dans le fichier ACL ne correspond à une opération
    donnée, l'opération est refusée.






SYNTAXE


Le fichier ACL est un fichier texte avec une entrée par ligne. Chaque
    entrée est une liste de champs séparés par des virgules. Les champs sont :


    

  • Le nom du principal (par exemple, utilisateur/instance@DOMAINE).
    Les caractères génériques sont autorisés.
    • 

  • Le nom de l'opération.
    • 

  • Le nom du principal cible.
    • 

  • La portée.
    • 



Les champs sont optionnels et sont traités dans l'ordre donné. Si un
    champ est omis, il est considéré comme un caractère générique. Par exemple,
    l'entrée suivante autorise tout principal à effectuer toute opération sur tout
    principal :




*




L'entrée suivante autorise le principal admin/admin@EXAMPLE.COM
    à effectuer toute opération sur tout principal dans le domaine
    EXAMPLE.COM :




admin/admin@EXAMPLE.COM,*,*,*








EXEMPLE




# Fichier ACL pour kadmind












# Autoriser le principal 'admin/admin@EXAMPLE.COM' à tout faire






admin/admin@EXAMPLE.COM		*	*	*












# Autoriser les utilisateurs du groupe 'admins' à changer de mot de passe






*/admins@EXAMPLE.COM		change_password	*	*












# Autoriser tout utilisateur à déverrouiller son propre compte






*				unlock	*	*












# Refuser toutes les autres opérations






*				*	*	*








COMPORTEMENT DU MODULE


Le fichier ACL peut coexister avec d'autres modules d'autorisation dans
    la version 1.16 et ultérieures, tel que configuré dans la section
    kadm5_auth de krb5.conf(5). Le fichier
    ACL autorisera positivement les opérations conformément aux règles ci-dessus,
    mais ne refusera jamais autoritativement une opération, de sorte que d'autres
    modules pourront autoriser des opérations en plus de celles autorisées par le
    fichier ACL.


Pour fonctionner sans fichier ACL, définissez la variable
    acl_file dans kdc.conf(5) à la chaîne
    vide avec acl_file = "".
