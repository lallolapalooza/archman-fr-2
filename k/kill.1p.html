EXEMPLE

S

L'une des commandes suivantes

: 
kill -9 100 -165
kil
l -s kill 100 -165 k
ill -s KILL 100 -165

envoie le signal SIGKILL au processus dont l'identifiant de processus est 100 et à tous les processus dont l'identifiant de groupe de processus est 165, en supposant que le processus émetteur a la permission d'envoyer ce signal aux processus spécifiés, et qu'ils

existent.

Le volume des Interfaces système de POSIX.1‐2017 et ce volume de POSIX.1‐2017 ne requièrent pas de numéros de signal spécifiques pour aucun signal_name. Même l'option -signal_number fournit des noms symboliques (bien que numériques) pour les signaux. Si un processus est terminé par un signal, son code de sortie indique le signal qui l'a tué, mais les valeurs exactes ne sont pas spécifiées. L'option kill -l, cependant, peut être utilisée pour convertir les numéros de signal décimaux et les valeurs de code de sortie en nom de signal. L'exemple suivant rapporte l'état d'une tâche terminée

: 
job
stat=$?
if [ $stat -eq 0 ]
then
    echo job completed successfull
y. elif [ $stat -gt 128 ] then echo job terminated by signal SIG$(
kill -l $stat). else echo job terminated with error code $stat. fi

Pour envoyer le signal par défaut à un groupe de processus (disons 123), une application doit utiliser une commande similaire à l'une des suivantes

: 
kill -T
ERM -12
3 kill
-- -123

JUSTIFICATIO

N

L'option -l provient du C shell, et est également implémentée dans le KornShell. La sortie du C shell peut se composer de plusieurs lignes de sortie car les noms de signaux ne tiennent pas toujours sur une seule ligne sur certains écrans de terminal. La sortie du KornShell incluait également les numéros de signal définis par l'implémentation et était considérée par les développeurs de la norme comme trop difficile à analyser commodément par les scripts. Le format de sortie spécifié a pour but non seulement d'accueillir la sortie historique du C shell, mais aussi de permettre un listage entièrement vertical ou entièrement horizontal sur les systèmes pour lesquels cela est

approprié.

Une proposition précoce a inventé le nom SIGNULL comme signal_name pour le signal 0 (utilisé par le volume des Interfaces système de POSIX.1‐2017 pour tester l'existence d'un processus sans lui envoyer un signal). Puisque le signal_name 0 peut être utilisé dans ce cas de manière non ambiguë, SIGNULL a été

supprimé.

Une proposition précoce exigeait également que les signal_names symboliques soient reconnus avec ou sans le préfixe SIG. Les versions historiques de kill n'ont pas écrit le préfixe SIG pour l' option -l et n'ont pas reconnu le préfixe SIG sur les signal_names. Puisque ni la portabilité des applications ni la facilité d'utilisation ne seraient améliorées en exigeant cette extension, elle n'est plus

requise.

Pour éviter l'ambiguïté d'un argument de nombre négatif initial spécifiant soit un numéro de signal soit un groupe de processus, POSIX.1‐2008 mandate qu'il soit toujours considéré comme le premier par les implémentations qui supportent l'option XSI. Elle exige également que les applications conformes utilisent toujours l' argument terminateur d'options "--" lors de la spécification d'un groupe de processus, sauf si une option est également

spécifiée.

L'option -s a été ajoutée en réponse à l'intérêt international pour fournir une forme de kill qui respecte les Lignes directrices de syntaxe des

utilitaires.

La notation d'identifiant de tâche (job ID) du contrôle de tâche n'est pas requise pour fonctionner comme prévu lorsque kill fonctionne dans son propre environnement d'exécution d'utilitaire. Dans l'un des exemples suivants

: 
nohup kill
%1 & system(
"kill %1");

le kill fonctionne dans un environnement différent et ne comp

rend pas comment le shell
a géré ses numéros de tâches.
