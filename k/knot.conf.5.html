NOM

knot.conf - fichier de configuration de Knot DNS

DESCRIPTION

Les fichiers de configuration de Knot DNS utilisent un format YAML simplifié. Simplifié signifie que toutes les fonctionnalités ne sont pas prises en charge.

Pour la description des éléments de configuration, nous devons déclarer la signification des symboles suivants :

  • INT – Entier
  • STR – Chaîne de caractères textuelle
  • HEXSTR – Chaîne hexadécimale (avec préfixe 0x)
  • BOOL – Valeur booléenne (on/off ou true/false)
  • TIME – Nombre de secondes, un entier avec un suffixe multiplicateur de temps possible (s ~ 1, m ~ 60, h ~ 3600, d ~ 24 * 3600, w ~ 7 * 24 * 3600, M ~ 30 * 24 * 3600, y ~ 365 * 24 * 3600)
  • SIZE – Nombre d'octets, un entier avec un suffixe multiplicateur de taille possible (B ~ 1, K ~ 1024, M ~ 1024^2 ou G ~ 1024^3)
  • BASE64 – Chaîne encodée en Base64
  • ADDR – Adresse IPv4 ou IPv6
  • DNAME – Nom de domaine
  • ... – Élément multi-valeur, l'ordre des valeurs est conservé
  • [ ] – Valeur optionnelle
  • | – Choix

La configuration se compose de plusieurs sections fixes et de sections de modules optionnelles. Il y a 17 sections fixes (module, server, xdp, control, log, statistics, database, keystore, key, remote, remotes, acl, submission, dnskey-sync, policy, template, zone). Les sections de modules sont préfixées par mod- (par exemple, mod-stats).

La plupart des sections (par exemple, zone) sont des séquences de blocs de paramètres. Chaque bloc de paramètres commence par un identifiant unique, qui peut être utilisé comme référence depuis d'autres sections (un tel identifiant doit être défini à l'avance).

Un élément multi-valeur peut être spécifié soit comme une séquence YAML :

address: [10.0.0.1, 10.0.0.2]

soit comme plusieurs éléments à valeur unique, chacun sur une ligne supplémentaire :

address: 10.0.0.1
address: 10.0.0.2

Si la valeur d'un élément contient des espaces ou d'autres caractères spéciaux, il est nécessaire d'encadrer cette valeur entre guillemets doubles " ".

Sauf indication contraire, un élément représentant un chemin de fichier ou de répertoire peut être défini soit comme un chemin absolu (commençant par /), soit comme un chemin relatif au même répertoire que la valeur par défaut de l'élément.

COMMENTAIRES

Un commentaire commence par un caractère # et est ignoré lors du traitement. De plus, chaque section de configuration ou bloc de séquence autorise un commentaire permanent via l'élément comment qui est stocké dans le serveur à côté de la configuration.

INCLUSION DE CONFIGURATION

Un autre fichier de configuration ou des fichiers, correspondant à un modèle, peuvent être inclus au niveau supérieur dans le fichier actuel.

include: STR

include

Un chemin ou un modèle correspondant spécifiant un ou plusieurs fichiers qui sont inclus à la place de l'option d'inclusion dans la configuration. Si le chemin n'est pas absolu, il est considéré comme relatif au fichier actuel. Le modèle peut être une chaîne de caractères arbitraire répondant aux exigences glob de POSIX, par exemple dir/*.conf. Les fichiers correspondants sont traités dans l'ordre trié.

Par défaut : non défini

EFFACEMENT DES SECTIONS DE CONFIGURATION

Il est possible d'effacer des sections de configuration spécifiées à des phases données de l'analyse de la configuration.

clear: STR

clear

Un modèle correspondant spécifiant les sections de configuration qui sont effacées lors de l'analyse de cet élément. Ceci permet de remplacer la configuration existante dans la base de données de configuration lors de l'inclusion d'un fichier de configuration ou garantit que certaines configurations n'étaient pas spécifiées dans des inclusions précédentes.

NOTE :

Pour la correspondance de modèle, la fonction POSIX fnmatch() est utilisée. Sous Linux, l'extension GNU FNM_EXTMATCH est activée, ce qui permet une correspondance de modèle étendue. Exemples :
  • clear: zone – Efface la section zone.
  • clear: mod-* – Efface toutes les sections de module.
  • clear: "[!z]*" – Efface toutes les sections ne commençant pas par la lettre z.
  • clear: !(zone) – (GNU uniquement) Efface toutes les sections sauf la section zone.
  • clear: @(zone|template) – (GNU uniquement) Efface les sections zone et template.

Par défaut : non défini

SECTION MODULE

Chargement dynamique des modules de configuration.

NOTE :

Si configuré avec le paramètre --with-moduledir=path non vide, tous les modules partagés dans ce répertoire seront automatiquement chargés.
module:
  - id: STR
    file: STR

id

Un identifiant de module sous la forme du préfixe mod- et du suffixe du nom du module.

file

Un chemin vers un fichier de bibliothèque partagée avec l'implémentation du module.

ATTENTION :

Si le chemin n'est pas absolu, la bibliothèque est recherchée dans l'ensemble des répertoires système. Voir man dlopen pour plus de détails.

Par défaut : ${libdir}/knot/modules-${version}/module_name.so (ou ${path}/module_name.so si configuré avec --with-moduledir=path)

Un utilisateur système avec un groupe système optionnel (user:group) sous lequel le serveur s'exécute après le démarrage et la liaison aux interfaces. Les capacités Linux sont utilisées si elles sont prises en charge.

Un emplacement de fichier PID.

La modification de ce paramètre nécessite le redémarrage du serveur Knot pour prendre effet.

Un nombre de processus UDP (threads) utilisés pour traiter les requêtes entrantes via UDP.

La modification de ce paramètre nécessite le redémarrage du serveur Knot pour prendre effet.

tcp-workers

Un nombre de processus TCP (threads) utilisés pour traiter les requêtes entrantes via TCP.

La modification de ce paramètre nécessite le redémarrage du serveur Knot pour prendre effet.

Défaut : égal au nombre de CPU en ligne, valeur par défaut d'au moins 10

background-workers

Un nombre de processus (threads) utilisés pour exécuter les opérations en arrière-plan (chargement de zone, mises à jour de zone, etc.).

La modification de ce paramètre nécessite le redémarrage du serveur Knot pour prendre effet.

Défaut : égal au nombre de CPU en ligne, valeur par défaut au maximum 10

async-start

Si activé, le serveur n'attend pas le chargement des zones et commence à répondre immédiatement avec des réponses SERVFAIL jusqu'à ce que la zone soit chargée.

Défaut : off

tcp-idle-timeout

Temps d'inactivité maximum (en secondes) entre les requêtes sur une connexion TCP entrante. Cela signifie que s'il n'y a aucune activité sur une connexion TCP entrante pendant cette limite, la connexion est fermée par le serveur.

Minimum : 1

Défaut : 10

tcp-io-timeout

Temps maximum (en millisecondes) pour recevoir ou envoyer un message DNS sur une connexion TCP entrante. Cela signifie que cette limite s'applique aux requêtes et réponses DNS normales, aux DDNS entrants et aux transferts de zone sortants. Le délai d'attente est mesuré à partir du moment où des données sont déjà disponibles pour traitement. Mettre à 0 pour infini.

Défaut : 500 (millisecondes)

ATTENTION :

Afin de réduire le risque d'attaques de type Slow Loris, il est recommandé de régler cette limite au plus bas possible sur les serveurs publics.

tcp-remote-io-timeout

Temps maximum (en millisecondes) pour recevoir ou envoyer un message DNS sur une connexion TCP sortante qui a déjà été établie vers un serveur distant configuré. Cela signifie que cette limite s'applique aux transferts de zone entrants, à l'envoi de NOTIFY, à la redirection DDNS et à la vérification ou poussée DS. Ce délai d'attente inclut le temps nécessaire à un aller-retour réseau et au traitement de la requête par le serveur distant. Mettre à 0 pour infini.

Défaut : 5000 (millisecondes)

tcp-reuseport

Si activé, chaque processus TCP écoute sur son propre socket et l'équilibrage de charge du noyau du système d'exploitation est utilisé via SO_REUSEPORT (ou SO_REUSEPORT_LB sous FreeBSD). En raison de l'absence d'un socket partagé, le serveur peut offrir un traitement plus rapide des requêtes sur TCP. Cependant, dans le cas de requêtes longues (par exemple, transferts de zone d'une zone TLD), la réutilisation des ports activée peut entraîner des requêtes clients retardées ou sans réponse. Il est donc conseillé d'utiliser cette option sur les serveurs secondaires.

NOTE :

Cette option est ignorée pour les sockets UNIX.

La modification de ce paramètre nécessite le redémarrage du serveur Knot pour prendre effet.

Défaut : off

tcp-fastopen

Si activé, utilise TCP Fast Open pour la communication TCP sortante (côté client) : transferts de zone entrants, envoi de NOTIFY, et redirection DDNS. Ce mode simplifie la négociation TCP et peut améliorer les performances réseau. TCP Fast Open pour la communication TCP entrante (côté serveur) n'est pas affecté par cette configuration car il est activé automatiquement si le système d'exploitation le prend en charge.

NOTE :

La prise en charge de TCP Fast Open doit également être activée au niveau du système d'exploitation :
  • Linux/macOS : assurez-vous que le paramètre du noyau net.ipv4.tcp_fastopen est 2 ou 3 pour le côté serveur, et 1 ou 3 pour le côté client.
  • FreeBSD : assurez-vous que le paramètre du noyau net.inet.tcp.fastopen.server_enable est 1 pour le côté serveur, et net.inet.tcp.fastopen.client_enable est 1 pour le côté client.

Défaut : off

quic-max-clients

Un nombre maximum de clients QUIC connectés en parallèle.

Voir aussi quic.

La modification de ce paramètre nécessite le redémarrage du serveur Knot pour prendre effet.

Minimum : 128

Défaut : 10000 (dix mille)

quic-outbuf-max-size

Taille mémoire cumulative maximale utilisée pour les tampons des messages envoyés non accusés de réception. Cette limite est par processus UDP.

NOTE :

Définir une valeur faible si peu de mémoire est disponible (en conjonction avec quic-max-clients car les connexions QUIC consomment beaucoup de mémoire). Définir une valeur élevée si des transferts de zone sortants de grandes zones via QUIC sont attendus.

La modification de ce paramètre nécessite le redémarrage du serveur Knot pour prendre effet.

Minimum : 1M (1 MiB)

Défaut : 100M (100 MiB)

quic-idle-close-timeout

Temps en secondes, après lequel toute connexion QUIC inactive est fermée gracieusement.

La modification de ce paramètre nécessite le redémarrage du serveur Knot pour prendre effet.

Minimum : 1

Défaut : 4

remote-pool-limit

Si différent de zéro, le serveur conservera jusqu'à ce nombre de connexions TCP sortantes ouvertes pour une utilisation ultérieure. Ceci est une optimisation pour éviter l'ouverture fréquente de connexions TCP vers le même serveur distant.

La modification de ce paramètre nécessite le redémarrage du serveur Knot pour prendre effet.

Défaut : 0

remote-pool-timeout

Le délai d'attente en secondes après lequel les connexions TCP sortantes inutilisées et maintenues ouvertes vers des serveurs distants sont fermées.

Défaut : 5

remote-retry-delay

Lorsqu'une tentative de connexion échoue vers une adresse distante, cette information sera conservée pendant la durée spécifiée (en millisecondes) et d'autres connexions vers la même adresse ne seront pas tentées. Cela évite les attentes répétitives jusqu'à l'expiration pour un serveur distant inaccessible.

Défaut : 0

socket-affinity

Si activé et si SO_REUSEPORT est disponible sous Linux, tous les sockets réseau configurés sont liés aux processus UDP et TCP afin d'augmenter les performances réseau. Ce mode n'est pas recommandé pour les configurations où le nombre de files d'attente de la carte réseau est inférieur au nombre de processus UDP ou TCP.

La modification de ce paramètre nécessite le redémarrage du serveur Knot pour prendre effet.

dbus-event

Spécification des états du serveur ou des zones qui émettent un signal D-Bus sur le bus système. Le nom du bus est cz.nic.knotd, le chemin de l'objet est /cz/nic/knotd, et le nom de l'interface est cz.nic.knotd.events.

Valeurs possibles :

  • none – Aucun signal n'est émis.
  • running – Deux signaux possibles sont émis :
  • started lorsque le serveur est démarré et que toutes les zones configurées (y compris les zones de catalogue et leurs membres) sont chargées ou démarrées avec succès.
  • stopped lorsque la séquence d'arrêt du serveur est initiée.
  • zone-updated – Le signal zone_updated est émis lorsqu'une zone a été mise à jour ; les paramètres du signal sont le nom de la zone et le numéro de série SOA de la zone.
  • keys-updated - Le signal keys_updated est émis lorsqu'un jeu de clés DNSSEC est mis à jour ; le paramètre du signal est le nom de la zone.
  • ksk-submission – Le signal zone_ksk_submission est émis s'il y a une KSK prête présente lorsque la zone est signée ; les paramètres du signal sont le nom de la zone, le tag de clé KSK et l'ID KASP KSK.
  • dnssec-invalid – Le signal zone_dnssec_invalid est émis lorsque la validation DNSSEC échoue ; les paramètres du signal sont le nom de la zone et les secondes restantes avant l'expiration d'un RRSIG.

REMARQUE :

Cette fonction nécessite systemd version 221 au minimum ou libdbus.

ASTUCE :

Quelques exemples de modèles de scripts peuvent être trouvés dans le dépôt du projet.

La modification de ce paramètre nécessite un redémarrage du serveur Knot pour prendre effet.

ATTENTION :

Lorsque vous modifiez des paramètres de configuration dynamiquement ou par rechargement du fichier de configuration, certains paramètres de la section XDP nécessitent un redémarrage du serveur Knot pour que les modifications prennent effet.

listen

Un ou plusieurs noms de périphériques réseau (par exemple, ens786f0) sur lesquels le Mode XDP est activé. Alternativement, une adresse IP peut être utilisée à la place d'un nom de périphérique, mais le serveur écoutera toujours sur toutes les adresses appartenant à la même interface ! Une spécification de port optionnelle (le port par défaut est 53) peut être ajoutée à chaque nom de périphérique ou adresse en utilisant le séparateur @.

La modification de ce paramètre nécessite un redémarrage du serveur Knot pour prendre effet.

ATTENTION :

Si les workers XDP traitent uniquement le trafic DNS régulier sur UDP, il est fortement recommandé d'écouter également sur les adresses destinées à offrir le service DNS, au moins pour satisfaire l'exigence DNS d'un TCP fonctionnel.

REMARQUE :

Le DDNS entrant via XDP n'est pas pris en charge. Le serveur répond toujours avec SERVFAIL.

Défaut : non défini

udp

Si activé, le DNS sur UDP est traité par les workers XDP.

La modification de ce paramètre nécessite un redémarrage du serveur Knot pour prendre effet.

Défaut : on

tcp

Si activé, le trafic DNS sur TCP est traité par les workers XDP.

Les limitations de la pile TCP :

  • Le contrôle de congestion n'est pas implémenté.
  • Les paquets perdus ne contenant pas de charge utile TCP peuvent ne pas être renvoyés.
  • Non optimisé pour les transferts de zones non triviales.

La modification de ce paramètre nécessite un redémarrage du serveur Knot pour prendre effet.

Défaut : off

quic

Si activé, le DNS sur QUIC est traité par les workers XDP.

La modification de ce paramètre nécessite un redémarrage du serveur Knot pour prendre effet.

Défaut : off

quic-port

Le DNS sur QUIC écoutera sur les interfaces configurées par listen, mais sur un port différent, configuré par cette option.

La modification de ce paramètre nécessite un redémarrage du serveur Knot pour prendre effet.

Défaut : 853

tcp-max-clients

Nombre maximum de clients TCP connectés en parallèle.

Minimum : 1024

Défaut : 1000000 (un million)

tcp-inbuf-max-size

Taille cumulative maximale de la mémoire utilisée pour les tampons des messages incomplets reçus.

Minimum : 1M (1 MiB)

Défaut : 100M (100 MiB)

tcp-outbuf-max-size

Taille cumulative maximale de la mémoire utilisée pour les tampons des messages envoyés non accusés de réception.

Minimum : 1M (1 MiB)

Défaut : 100M (100 MiB)

tcp-idle-close-timeout

Temps en secondes, après lequel toute connexion inactive est fermée gracieusement.

Minimum : 1

Défaut : 10

tcp-idle-reset-timeout

Temps en secondes, après lequel toute connexion inactive est fermée de force.

Minimum : 1

Défaut : 20

tcp-resend-timeout

Renvoyer les paquets de données sortants (avec la charge utile de réponse DNS) s'ils ne sont pas accusés de réception avant ce délai d'attente (en secondes).

Minimum : 1

Défaut : 5

route-check

Si activé, les informations de routage du système d'exploitation sont prises en compte lors du traitement de chaque paquet DNS entrant reçu sur l'interface XDP :

  • Si l'interface de sortie de la réponse DNS correspondante diffère de l'entrée, le paquet est traité normalement par les workers UDP/TCP (XDP n'est pas utilisé).
  • Si l'adresse de destination est blackholed, inaccessible ou interdite, le paquet DNS est abandonné sans aucune réponse.
  • L'adresse MAC de destination et la balise VLAN possible pour la réponse sont extraites du système de routage.

Si désactivé, le routage symétrique est appliqué. Cela signifie que l'adresse MAC source de la requête est utilisée comme adresse MAC de destination de la réponse. La balise VLAN possible est conservée.

La modification de ce paramètre nécessite le redémarrage du serveur Knot pour prendre effet.

NOTE :

Ce mode nécessite que le transfert soit activé sur l'interface de boucle locale (sysctl -w net.ipv4.conf.lo.forwarding=1 et sysctl -w net.ipv6.conf.lo.forwarding=1). Si le transfert est désactivé, tous les paquets DNS entrants sont abandonnés !

Seul le VLAN 802.1Q est pris en charge.

Par défaut : off

ring-size

Taille des anneaux RX, FQ, TX et CQ.

La modification de ce paramètre nécessite le redémarrage du serveur Knot pour prendre effet.

NOTE :

Cette valeur doit être au moins aussi élevée que la taille RX configurée du périphérique réseau en mode XDP.

Par défaut : 2048

busypoll-budget

Si défini sur une valeur positive, le busy polling préféré est activé avec le budget spécifié.

La modification de ce paramètre nécessite le redémarrage du serveur Knot pour prendre effet.

NOTE :

Le busy polling préféré nécessite également la définition de napi_defer_hard_irqs et gro_flush_timeout pour l'interface réseau appropriée. Par exemple : 
echo 2 | sudo tee /sys/class/net/<interface>/napi_defer_hard_irqs
echo 200000 | sudo tee /sys/class/net/<interface>/gro_flush_timeout

NOTE :

Une valeur recommandée se situe entre 8 et 64.

Par défaut : 0 (désactivé)

SECTION LOG

Le serveur peut être configuré pour enregistrer dans la sortie standard, la sortie d'erreur standard, syslog (ou le journal systemd si systemd est activé) ou dans un fichier arbitraire.

Il existe 6 niveaux de sévérité de journalisation :

  • critical – Erreur non récupérable entraînant l'arrêt du serveur.
  • error – Erreur récupérable, une action doit être entreprise.
  • warning – Avertissement pouvant nécessiter une action de l'utilisateur.
  • notice – Notification ou indice du serveur.
  • info – Message informatif.
  • debug – Message de débogage ou détaillé.

En l'absence de section log, les messages warning ou plus graves seront enregistrés dans la sortie d'erreur standard et dans syslog. Les messages info et notice seront enregistrés dans la sortie standard.

log:
  - target: stdout | stderr | syslog | STR
    server: critical | error | warning | notice | info | debug
    control: critical | error | warning | notice | info | debug
    zone: critical | error | warning | notice | info | debug
    quic: critical | error | warning | notice | info | debug
    any: critical | error | warning | notice | info | debug

target

Une sortie de journalisation.

Valeurs possibles :

  • stdout – Sortie standard.
  • stderr – Sortie d'erreur standard.
  • syslog – Syslog ou journal systemd.
  • file_name – Un fichier spécifique.

Avec la cible syslog, le service syslog est utilisé. Cependant, si Knot DNS a été compilé avec le support systemd et que le système d'exploitation a été démarré avec systemd, le journal systemd est utilisé pour la journalisation à la place de syslog.

Un file_name peut être spécifié comme un chemin absolu ou un chemin relatif au répertoire de démarrage de knotd.

SECTION ACL

Définitions des règles de liste de contrôle d'accès. Une règle ACL est une description d'une ou plusieurs actions autorisées (demande de transfert de zone, notification de changement de zone et mise à jour DNS dynamique) qui sont autorisées à être traitées ou refusées. Les requêtes qui ne nécessitent pas d'autorisation sont toujours autorisées.

acl:
  - id: STR
    address: ADDR[/INT] | ADDR-ADDR | STR ...
    key: key_id ...
    cert-key: BASE64 ...
    remote: remote_id | remotes_id ...
    action: query | notify | transfer | update ...
    protocol: udp | tcp | tls | quic ...
    deny: BOOL
    update-type: STR ...
    update-owner: key | zone | name
    update-owner-match: sub-or-equal | equal | sub | pattern
    update-owner-name: STR ...

id

Un identifiant de règle ACL.

address

Une liste ordonnée d'adresses IP, de chemins de sockets UNIX absolus, de sous-réseaux réseau ou de plages réseau. L'adresse source de la requête doit correspondre à l'un d'entre eux. Si cet élément n'est pas défini, la correspondance d'adresse n'est pas requise.

Par défaut : non défini

key

Une liste ordonnée de référencesvers des clés TSIG. La requête doit correspondre à l'une d'entre elles. Si cet élément n'est pas défini, l'authentification de transaction n'est pas utilisée.

Par défaut : non défini

cert-key

Une liste ordonnée de PIN de clé publique de certificat distant. Si la liste est non vide, la communication avec le distant n'est possible que via le protocole QUIC et un certificat pair est requis. La clé du certificat pair doit correspondre à l'un des PIN spécifiés.

Un PIN est un identifiant unique qui représente la clé publique du certificat pair. Il s'agit d'un hachage SHA-256 encodé en base64 de la clé publique. Cet identifiant reste le même lors du renouvellement d'un certificat.

Par défaut : non défini

remote

Une liste ordonnée de références remote et remotes. La requête doit correspondre à l'un des distants. Plus précisément, l'une des adresses du distant et la clé TSIG du distant si elle est configurée doivent correspondre.

NOTE :

Cette option ne peut pas être spécifiée en même temps que les options address, keyou protocol au sein d'un même élément ACL.

Par défaut : non défini

action

Une liste ordonnée d'actions autorisées ou refusées (types de requêtes).

Valeurs possibles :

  • query – Autorise une requête DNS normale. Comme les requêtes normales sont toujours autorisées, cette action n'est utile qu'en combinaison avec une clé TSIG.
  • notify – Autorise les notifications entrantes (NOTIFY).
  • transfer – Autorise le transfert de zone (AXFR, IXFR).
  • update – Autorise les mises à jour de zone (DDNS).

Par défaut : query

protocol

Liste des protocoles autorisés.

Valeurs possibles :

  • udp – Protocole UDP.
  • tcp – Protocole TCP.
  • tls – Protocole TLS.
  • quic – Protocole QUIC.

Par défaut : non défini (tous)

deny

Si activé, au lieu d'autoriser, refuse la combinaison correspondant aux éléments spécifiés.

Par défaut : désactivé

update-type

Une liste des types d'enregistrements de ressources autorisés dans une mise à jour de zone. Chaque enregistrement d'une mise à jour doit correspondre à l'un des types spécifiés.

Par défaut : non défini

update-owner

Cette option restreint les propriétaires possibles des enregistrements de ressources dans une mise à jour de zone en les comparant soit à l'identité de la clé TSIG , au nom de la zone actuelle, ou à une liste de noms de domaine donnée par l'option update-owner-name . La méthode de comparaison est donnée par l'option update-owner-match .

Valeurs possibles :

  • key — Le propriétaire de chaque RR mis à jour doit correspondre à l'identité de la clé TSIG si elle est utilisée.
  • name — Le propriétaire de chaque RR mis à jour doit correspondre à au moins un nom de la liste update-owner-name .
  • zone — Le propriétaire de chaque RR mis à jour doit correspondre au nom de la zone actuelle.

Par défaut : non défini

update-owner-match

Cette option définit comment les propriétaires des enregistrements de ressources dans une mise à jour sont comparés au(x) nom(s) de domaine défini(s) par l'option update-owner .

Valeurs possibles :

  • sub-or-equal — Le propriétaire de chaque RR dans une mise à jour doit être soit égal à, soit un sous-domaine d'au moins un nom de domaine défini par update-owner.
  • equal — Le propriétaire de chaque RR mis à jour doit être égal à au moins un nom de domaine défini par update-owner.
  • sub — Le propriétaire de chaque RR mis à jour doit être un sous-domaine de, mais NE DOIT PAS être égal à au moins un nom de domaine défini par update-owner.
  • pattern — Le propriétaire de chaque RR mis à jour doit correspondre à un motif spécifié par update-owner. Le motif peut être un FQDN ou un nom de domaine non-FQDN arbitraire. Si une étiquette est composée d'un seul caractère * (astérisque) , elle correspond à n'importe quelle étiquette. Plusieurs étiquettes astérisque peuvent être spécifiées.

Par défaut : sub-or-equal

update-owner-name

Une liste des propriétaires autorisés des RR dans une mise à jour de zone, utilisée avec update-owner défini à name. Chaque nom de propriétaire listé qui n'est pas un FQDN (c'est-à-dire qu'il ne se termine pas par un point) est considéré comme si le nom de la zone cible lui était appendé. Une telle spécification de nom de propriétaire relatif permet une meilleure réutilisabilité des règles ACL sur plusieurs zones.

Par défaut : non défini

Par défaut : calculé après le chargement de la zone

keytag-modulo

Spécifie que les étiquettes de clé (keytags) de toutes les clés générées doivent être congruentes selon le modulo spécifié. La valeur de l'option doit être une chaîne au format R/M, où R < M <= 256 sont des entiers positifs. Chaque fois qu'une clé DNSSEC est générée, il est assuré que keytag % M == R. Cela évite les conflits d'étiquettes de clé dans les configurations DNSSEC Offline KSK ou DNSSEC multi-signer (et potentiellement d'autres).

NOTE :

Ceci ne s'applique qu'aux clés nouvellement générées au moment de leur génération. Les clés antérieures à cette option et les clés importées d'ailleurs pourraient ne pas satisfaire la politique.

Une période (en secondes) entre la génération d'une KSK et l'initiation de la prochaine rotation.

NOTE :

Une valeur de zéro (alias infini) n'entraîne aucune rotation de KSK.

Ceci s'applique à la durée de vie des CSK si single-type-signing est activé.

Par défaut : 0 (infini)

zsk-lifetime

Une période (en secondes) entre l'activation d'une ZSK et l'initiation de la prochaine rotation.

NOTE :

Plus précisément, cette période est mesurée à partir du moment où une ZSK est activée, et après cela, une nouvelle ZSK est générée pour la remplacer lors de la rotation suivante.

En conséquence, en fonctionnement normal, cela se traduit par une période de génération de ZSK de zsk-lifetime + propagation-delay + dnskey_ttl.

Une valeur de zéro (alias infini) n'entraîne aucune rotation de ZSK.

Par défaut : 30d (30 jours)

delete-delay

Une fois qu'une clé (KSK ou ZSK) est remplacée et supprimée de la zone, conservez-la dans la base de données KASP pendant au moins cette période (en secondes) avant de la supprimer complètement. Cela peut être utile dans certains cas de dépannage nécessitant une résurrection.

Par défaut : 0

propagation-delay

Un délai supplémentaire ajouté pour chaque étape de rotation de clé. Cette valeur (en secondes) doit être suffisamment élevée pour couvrir la propagation des données du serveur primaire vers tous les serveurs secondaires, ainsi que la durée de la routine de signature elle-même et les éventuelles interruptions de l'infrastructure de signature et de propagation. En d'autres termes, ce délai doit garantir qu'à l'issue de cette période après un changement planifié de l'ensemble des clés, tous les serveurs secondaires accessibles publiquement serviront à coup sûr le nouvel ensemble DNSKEY RRSet.

NOTE :

A une influence sur la durée de vie de la clé ZSK.

Par défaut : 1h (1 heure)

rrsig-lifetime

Une période de validité (en secondes) des signatures nouvellement émises.

NOTE :

L'heure d'inception de la signature du RRSIG est définie 90 minutes dans le passé. Cette période n'est pas comptée dans la durée de vie de la signature.

Par défaut : 14d (14 jours)

Une période (en secondes) avant l'expiration d'une signature, la signature sera rafraîchie afin d'éviter des RRSIG expirés sur les serveurs secondaires ou dans les caches des résolveurs.

Par défaut : 0.1 * rrsig-lifetime + propagation-delay + zone-max-ttl

Si dnssec-validation est activé :

Par défaut : 1d (1 jour)

Une période (en secondes) au plus avant le temps de rafraîchissement de la signature, la signature pourrait être rafraîchie, afin de rafraîchir les RRSIG par lots plus importants sur une zone fréquemment mise à jour (éviter des événements de re-signature trop fréquents).

Par défaut : 1h (1 heure)

Références optionnelles remote et remotes vers le serveur DNS faisant autorité de la zone parente. cds-cdnskey-publish

Contrôle si et comment les enregistrements CDS et CDNSKEY doivent être publiés dans la zone.

Valeurs possibles :

  • none – Ne jamais publier d'enregistrements CDS ou CDNSKEY dans la zone.
  • delete-dnssec – Publier des enregistrements CDS et CDNSKEY spéciaux indiquant la désactivation de DNSSEC.
  • rollover – Publier des enregistrements CDS et CDNSKEY pour les KSK prêts et pas encore actifs (phase de soumission de la rotation KSK).
  • always – Toujours publier un enregistrement CDS et un enregistrement CDNSKEY pour le KSK actuel.
  • double-ds – Toujours publier jusqu'à deux enregistrements CDS et deux enregistrements CDNSKEY pour les KSK prêts et/ou actifs.

  • sha256
  • sha384

Par défaut : sha256

dnskey-management

Spécifie comment les RRSets DNSKEY, CDNSKEY et CDS à l'apex de la zone sont gérés lors de la (re)signature de la zone.

Valeurs possibles :

  • full – Lors de chaque (re)signature de zone, supprime tous les enregistrements DNSKEY, CDNSKEY et CDS inconnus et ne conserve que ceux qui sont liés aux clés de zone stockées dans la base de données KASP.
  • incremental – Conserve les enregistrements DNSKEY, CDNSKEY et CDS inconnus dans la zone et modifie les enregistrements gérés par le serveur de manière incrémentielle en employant les changements de la base de données KASP.

NOTE :

Prérequis pour incremental :
  • Le KSK hors ligne n'est pas pris en charge.
  • Le delete-delay est suffisamment long pour couvrir un éventuel arrêt du démon (par exemple, en raison d'une maintenance du serveur).
  • Suppression manuelle des clés avec keymgr évitée.

Sinon, certains enregistrements DNSKEY pourraient rester dans la zone, appartenant à des clés supprimées.

Par défaut : full

offline-ksk

Spécifie si la fonctionnalité KSK hors ligne est activée.

Par défaut : désactivé

unsafe-operation

Désactive certaines fonctionnalités de sécurité DNSSEC.

Valeurs possibles :

  • none – Rien n'est désactivé.
  • no-check-keyset – Ne vérifie pas les clés actives dans les algorithmes actuels. Cela peut entraîner une violation de la Section 2.2 de la RFC 4035.
  • no-update-dnskey – Ne maintient/met pas à jour les enregistrements DNSKEY, CDNSKEY et CDS à l'apex de la zone conformément à la base de données KASP. Laissez-les simplement tels qu'ils sont dans la zone.

Plusieurs valeurs peuvent être spécifiées.

Ce mode est destiné aux experts DNSSEC qui comprennent les conséquences correspondantes.

Par défaut : none

master-pin-tolerance

Si défini à une valeur non nulle sur un secondaire, toujours demander AXFR/IXFR au même primaire que la dernière fois, épinglant effectivement un primaire. Ce n'est que lorsqu'un autre primaire est mis à jour et que le courant est en retard pour la quantité de temps spécifiée (définie par cette option en secondes), passer au primaire mis à jour et forcer AXFR.

Cette option est utile lorsque plusieurs primaires peuvent avoir un historique de zone différent dans leurs journaux, ce qui rend dangereux de combiner des IXFR interchangés de différents primaires.

semantic-checks

Sélectionne si des vérifications sémantiques supplémentaires de la zone sont utilisées ou l'impact des vérifications obligatoires.

Il existe plusieurs vérifications obligatoires qui sont toujours activées et ne peuvent pas être désactivées. Une erreur dans une vérification obligatoire empêche la zone d'être chargée. La plupart des vérifications obligatoires peuvent être assouplies en définissant soft, ce qui permet à la zone d'être chargée même si la vérification échoue.

Si activé, des vérifications supplémentaires sont utilisées. Ces vérifications n'empêchent pas le chargement de la zone.

Les vérifications obligatoires sont appliquées aux fichiers de zone, aux transferts de zone, et aux mises à jour via l'interface de contrôle. Les vérifications supplémentaires ne sont appliquées qu'aux fichiers de zone !

Vérifications obligatoires :

  • Enregistrement SOA manquant au sommet de la zone (RFC 1034) (*)
  • Un enregistrement supplémentaire existe avec un enregistrement CNAME sauf pour RRSIG et NSEC (RFC 1034)
  • Plusieurs enregistrements CNAME avec le même propriétaire existent (RFC 1034)
  • Enregistrement DNAME ayant un enregistrement en dessous (RFC 6672)
  • Plusieurs enregistrements DNAME avec le même propriétaire existent (RFC 6672)
  • Enregistrement NS existe avec un enregistrement DNAME (RFC 6672)
  • Enregistrement DS existe au sommet de la zone (RFC 3658)

(*) La vérification marquée ne peut pas être assouplie par le mode soft. Toutes les autres vérifications obligatoires sont soumises au mode soft optionnel.

Vérifications supplémentaires :

  • Enregistrement NS manquant au sommet de la zone
  • Enregistrement glue A ou AAAA manquant
  • Enregistrement DS ou NSEC3PARAM invalide
  • Incohérence CDS ou CDNSKEY
  • Toutes les autres vérifications DNSSEC exécutées pendant dnssec-validation

NOTE :

Le mode soft permet à l'événement de rafraîchissement d'ignorer une réponse CNAME à une requête SOA (message malformé) et déclenche un amorçage de zone à la place.

Par défaut : désactivé

default-ttl

La valeur TTL par défaut si aucune n'est spécifiée dans un fichier de zone ou une insertion de zone utilisant la configuration dynamique.

AVERTISSEMENT :

Comme le changement de cette valeur peut entraîner des fichiers de zone analysés différemment, le numéro de série SOA de la zone correspondante doit être incrémenté avant de recharger ou de valider la configuration. Alternativement, définir zonefile-load à difference-no-serial garantit que la mise à jour de la zone résultante est correcte.

Par défaut : 3600

zonefile-sync

Le temps en secondes après lequel la zone actuelle en mémoire sera synchronisée avec un fichier de zone sur le disque (voir file). Le serveur servira la dernière zone même après un redémarrage en utilisant le journal de zone, mais le fichier de zone sur le disque ne sera synchronisé qu'après zonefile-sync le temps est expiré (ou après un flush manuel de zone). Ceci s'applique lorsque la zone est mise à jour via IXFR, DDNS ou une signature DNSSEC automatique. Afin de désactiver complètement la synchronisation automatique du fichier de zone, définissez la valeur à -1. Dans ce cas, il est toujours possible de forcer un flush manuel de zone en utilisant l'option -f .

NOTE :

Si vous servez de grandes zones avec des mises à jour fréquentes où la synchronisation immédiate avec un fichier de zone n'est pas souhaitable, augmentez la valeur.

Par défaut : 0 (immédiat)

zonefile-load

Sélectionne comment le contenu du fichier de zone est appliqué lors du chargement de la zone.

Valeurs possibles :

  • none – Le fichier de zone n'est pas du tout utilisé.
  • difference – Si le contenu de la zone est déjà disponible pendant le démarrage ou le rechargement du serveur, la différence est calculée entre lui et le contenu du fichier de zone. Cette différence est ensuite vérifiée pour des erreurs sémantiques et appliquée au contenu actuel de la zone.
  • difference-no-serial – Identique à difference, mais le numéro de série SOA dans le fichier de zone est ignoré, le serveur se charge d'incrémenter automatiquement le numéro de série.
  • whole – Le contenu de la zone est chargé depuis le fichier de zone.

Quand difference est configuré et qu'il n'y a pas encore de contenu de zone (démarrage à froid et pas de contenu de zone dans le journal), il se comporte de la même manière que whole.

Par défaut : whole

NOTE :

Voir Gestion du fichier de zone, du journal, des changements, des numéros de série pour des conseils sur la configuration de ces options et des options connexes afin d'assurer un fonctionnement fiable.

journal-content

Sélectionne comment le journal doit être utilisé pour stocker la zone et ses changements.

Valeurs possibles :

  • none – Le journal n'est pas du tout utilisé.
  • changes – L'historique des changements de la zone est stocké dans le journal.
  • all – Le contenu et l'historique de la zone sont stockés dans le journal.

Par défaut : changes

Il est recommandé d'envisager de purger le journal lorsque cette option est modifiée.

Politique de l'espace que le journal de la zone occupera dans la base de données du journal.

ixfr-benevolent

Si activé, les IXFR entrants sont appliqués même lorsqu'ils contiennent des suppressions d'enregistrements inexistants ou des ajouts d'enregistrements existants.

Défaut : off

Défaut : off

zone-max-size

Taille maximale de la zone. La taille est mesurée comme la taille des enregistrements de zone au format filaire sans compression. La limite est appliquée aux transferts de zone entrants et aux mises à jour dynamiques.

Pour les transferts incrémentaux (IXFR), la limite effective pour la taille totale des enregistrements dans le transfert est le double de la valeur configurée. Cependant, la taille finale de la zone doit satisfaire la valeur configurée.

Parallélise les procédures internes d'ajustement de zone en utilisant un nombre spécifié de threads. Ceci est utile avec des zones volumineuses avec NSEC3. L'accélération est observable au démarrage du serveur et lors du traitement du ré-salage NSEC3.

dnssec-signing

Si activé, le DNSSEC automatique pour la zone est activé.

Défaut : off

dnssec-validation

Si activé, le contenu de la zone est validé pour s'assurer qu'il est correctement signé (y compris la chaîne NSEC/NSEC3) avec des signatures DNSSEC chaque fois que la zone est chargée ou modifiée (y compris AXFR/IXFR).

Lorsque la validation échoue, la zone en cours de chargement ou la mise à jour en cours d'application est annulée avec une erreur, et soit aucun état de zone, soit l'état précédent de la zone est publié.

Liste des vérifications DNSSEC :

  • Chaque jeu d'enregistrements (RRSet) de zone est correctement signé par au moins une clé DNSKEY présente.
  • Pour chaque RRSIG, il y a au plus 3 DNSKEY non correspondantes avec le même keytag.
  • Le jeu d'enregistrements DNSKEY est signé par KSK.
  • Un enregistrement NSEC(3) existe pour chaque nom (sauf opt-out) avec une bitmap correcte.
  • Chaque enregistrement NSEC(3) est lié au suivant lexicographiquement.

La validation n'est pas affectée par la configuration de dnssec-policy, à l'exception de l'option signing-threads, qui spécifie le nombre de threads pour la validation parallèle, et de rrsig-refresh, qui définit l'intervalle minimal de validité RRSIG restant autorisé (sinon un avertissement est enregistré).

Les enregistrements NSEC3 redondants ou incorrects sont ignorés.

Ce mode n'est pas compatible avec dnssec-signing.

Défaut : non défini

Défaut : une politique imaginaire avec toutes les valeurs par défaut

Défaut : non défini

zonemd-verify

Défaut : off

À chaque mise à jour de zone, calculez ZONEMD et insérez-le dans la zone.

Valeurs possibles :

  • none – Aucune action concernant ZONEMD.
  • zonemd-sha384 – Générer ZONEMD en utilisant l'algorithme SHA384.
  • zonemd-sha512 – Générer ZONEMD en utilisant l'algorithme SHA512.
  • remove – Supprimer tout ZONEMD de l'apex de la zone.

Défaut : none

serial-policy

Spécifie comment le numéro de série de la zone est mis à jour après une mise à jour dynamique ou une signature DNSSEC automatique. Si le numéro de série est modifié par la mise à jour dynamique, aucune modification n'est apportée.

Valeurs possibles :

  • increment – Le numéro de série est incrémenté selon l'arithmétique des numéros de série.
  • unixtime – Le numéro de série est défini à l'heure Unix actuelle.
  • dateserial – Le numéro de série à 10 chiffres (AAAA MM JJ nn) est incrémenté, les 8 premiers chiffres correspondent à la date iso actuelle.

REMARQUE :

Si le numéro de série résultant pour unixtime ou dateserial est inférieur ou égal au numéro de série actuel (cela se produit par exemple lors de la migration depuis une autre politique ou lors de mises à jour fréquentes), le numéro de série est incrémenté à la place.

Pour éviter la confusion des utilisateurs, n'utilisez dateserial que si vous prévoyez au plus 100 mises à jour par jour et par zone, et unixtime seulement si vous prévoyez au plus une mise à jour par seconde et par zone.

Les zones de catalogue générées utilisent uniquement unixtime.

Défaut : increment (unixtime pour les zones de catalogue générées)

serial-modulo

La valeur de l'option est une chaîne composée de deux parties (sans séparateur entre elles), dont chacune est facultative.

La première partie spécifie que les numéros de série de zone doivent être congruents modulo la valeur spécifiée. Le format est R/M, où R < M <= 256 sont des entiers positifs. Chaque fois que le numéro de série de la zone est incrémenté, il est garanti que serial % M == R. Cela peut être utile dans le cas de plusieurs serveurs primaires incohérents, où des séquences de numéros de série de zone distinctes empêchent les IXFR inter-serveurs par tout secondaire.

REMARQUE :

Étant donné que le numéro de série de la zone s'incrémente effectivement toujours de M au lieu de 1, il n'est pas recommandé d'utiliser la politique de numéro de série dateserial, ni même unixtime, dans le cas d'une zone mise à jour rapidement.

La seconde partie spécifie un décalage numérique pour le numéro de série de zone généré. Le décalage est formaté comme un entier signé, y compris le signe (+ ou -). Il est principalement utile avec la politique de numéro de série unixtime, où le numéro de série de zone généré est décalé par rapport à l'heure Unix.

REMARQUE :

Afin d'assurer la politique congruente, cette option n'est autorisée qu'avec le DNSSEC activé et zonefile-load soit sur difference-no-serial, soit sur none.

Défaut : 0/1+0

catalog-role

Déclenche la fonctionnalité de catalogue de zones. Valeurs possibles :

  • none – Pas une zone de catalogue.
  • interpret – Une zone de catalogue qui est chargée à partir d'un fichier de zone ou XFR, et les zones membres doivent être configurées en fonction de son contenu.
  • generate – Une zone de catalogue dont le contenu est généré selon les zones membres attribuées.
  • member – Une zone membre attribuée à un catalogue généré.

NOTE :

Si défini sur generate, l'option zonefile-load n'a aucun effet car un fichier de zone n'est jamais chargé.
