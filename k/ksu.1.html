ksu(1)

Paquet: krb5

Licences: custom

KSU(1) Kerberos MIT KSU(1)

NOM

ksu - super-utilisateur Kerbérisé

SYNTAXE

ksu [ utilisateur_cible ] [ -n nom_principal_cible ] [ -c nom_cache_source ] [ -k ] [ -r temps ] [ -p | -P] [ -f | -F] [ -l durée_de_vie ] [ -z | Z ] [ -q ] [ -e commande [ arguments ... ] ] [ -a [ arguments ... ] ]

EXIGENCES

Doit avoir Kerberos version 5 installé pour compiler ksu. Doit avoir un serveur Kerberos version 5 en cours d'exécution pour utiliser ksu.

DESCRIPTION

ksu est une version Kerbérisée du programme su qui a deux missions : l'une est de changer de manière sécurisée l'ID utilisateur réel et effectif à celui de l'utilisateur cible, et l'autre est de créer un nouveau contexte de sécurité.

NOTE :

Par souci de clarté, toutes les références et attributs de l'utilisateur qui invoque le programme commenceront par « source » (par exemple, « utilisateur source », « cache source », etc.).

De même, toutes les références et attributs du compte cible commenceront par « cible ».

AUTHENTIFICATION

Pour remplir la première mission, ksu opère en deux phases : authentification et autorisation. La résolution du nom du principal cible est la première étape de l'authentification. L'utilisateur peut soit spécifier son nom de principal avec l'option -n (par exemple, -n jqpublic@USC.EDU) soit un nom de principal par défaut sera attribué en utilisant une heuristique décrite dans la section OPTIONS (voir l'option -n). Le nom d'utilisateur cible doit être le premier argument de ksu ; s'il n'est pas spécifié, root est la valeur par défaut. Si . est spécifié, alors l'utilisateur cible sera l'utilisateur source (par exemple, ksu .). Si l'utilisateur source est root ou si l'utilisateur cible est l'utilisateur source, aucune authentification ni autorisation n'a lieu. Sinon, ksu recherche un ticket Kerberos approprié dans le cache source.

Le ticket peut être destiné au serveur final ou un ticket d'octroi de ticket (TGT) pour le royaume du principal cible. Si le ticket pour le serveur final est déjà dans le cache, il est déchiffré et vérifié. S'il n'est pas dans le cache mais que le TGT l'est, le TGT est utilisé pour obtenir le ticket du serveur final. Le ticket du serveur final est alors vérifié. Si aucun des deux tickets n'est dans le cache, mais que ksu est compilé avec la définition GET_TGT_VIA_PASSWD, l'utilisateur sera invité à entrer un mot de passe Kerberos qui sera ensuite utilisé pour obtenir un TGT. Si l'utilisateur est connecté à distance et ne dispose pas d'un canal sécurisé, le mot de passe peut être exposé. Si aucun des deux tickets n'est dans le cache et que GET_TGT_VIA_PASSWD n'est pas défini, l'authentification échoue.

AUTORISATION

Cette section décrit l'autorisation de l'utilisateur source lorsque ksu est invoqué sans l'option -e. Pour une description de l'option -e, voir la section OPTIONS.

Après une authentification réussie, ksu vérifie si le principal cible est autorisé à accéder au compte cible. Dans le répertoire personnel de l'utilisateur cible, ksu tente d'accéder à deux fichiers d'autorisation : .k5login(5) et .k5users. Dans le fichier .k5login, chaque ligne contient le nom d'un principal autorisé à accéder au compte.

Par exemple :

jqpublic@USC.EDU
jqpublic/secure@USC.EDU
jqpublic/admin@USC.EDU

Le format de .k5users est le même, sauf que le nom du principal peut être suivi d'une liste de commandes que le principal est autorisé à exécuter (voir l'option -e dans la section OPTIONS pour plus de détails).

Ainsi, si le nom du principal cible est trouvé dans le fichier .k5login, l'utilisateur source est autorisé à accéder au compte cible. Sinon, ksu cherche dans le fichier .k5users. Si le nom du principal cible est trouvé sans commandes supplémentaires ou suivi uniquement de *, alors l'utilisateur source est autorisé. Si .k5login ou .k5users existent mais qu'une entrée appropriée pour le principal cible n'existe pas, l'accès est refusé. Si aucun des deux fichiers n'existe, alors le principal se verra accorder l'accès au compte selon les règles de mappage aname->lname. Sinon, l'autorisation échoue.

EXECUTION DU SHELL CIBLE

Après une authentification et une autorisation réussies, ksu procède de manière similaire à su. L'environnement n'est pas modifié à l'exception des variables USER, HOME et SHELL. Si l'utilisateur cible n'est pas root, USER est défini sur le nom d'utilisateur cible. Sinon, USER reste inchangé. HOME et SHELL sont tous deux définis sur les valeurs par défaut du compte de connexion cible. De plus, la variable d'environnement KRB5CCNAME est définie sur le nom du cache cible. L'ID utilisateur réel et effectif sont changés à ceux de l'utilisateur cible. Le shell de l'utilisateur cible est ensuite invoqué (le nom du shell est spécifié dans le fichier de mots de passe). Lors de la terminaison du shell, ksu supprime le cache cible (sauf si ksu est invoqué avec l'option -k). Ceci est implémenté en faisant d'abord un fork puis un exec, au lieu d'un simple exec, comme le fait su.

CREATION DUN NOUVEAU CONTEXTE DE SECURITE

ksu peut être utilisé pour créer un nouveau contexte de sécurité pour le programme cible (soit le shell cible, soit la commande spécifiée via l'option -e). Le programme cible hérite d'un ensemble d'identifiants de l'utilisateur source. Par défaut, cet ensemble inclut tous les identifiants du cache source plus tout identifiant supplémentaire obtenu lors de l'authentification. L'utilisateur source peut limiter les identifiants de cet ensemble en utilisant l'option -z ou -Z. -z restreint la copie des tickets du cache source au cache cible uniquement aux tickets où le client == le nom du principal cible. L'option -Z fournit à l'utilisateur cible un nouveau cache cible (aucun identifiant dans le cache). Notez que pour des raisons de sécurité, lorsque l'utilisateur source est root et l'utilisateur cible non-root, l'option -z est le mode de fonctionnement par défaut.

Bien qu'aucune authentification n'ait lieu si l'utilisateur source est root ou s'il est identique à l'utilisateur cible, des tickets supplémentaires peuvent toujours être obtenus pour le cache cible. Si -n est spécifié et qu'aucun identifiant ne peut être copié dans le cache cible, l'utilisateur source est invité à entrer un mot de passe Kerberos (sauf si -Z est spécifié ou si GET_TGT_VIA_PASSWD est indéfini). En cas de succès, un TGT est obtenu du serveur Kerberos et stocké dans le cache cible. Sinon, si aucun mot de passe n'est fourni (l'utilisateur appuie sur Entrée) ksu continue en mode opératoire normal (le cache cible ne contiendra pas le TGT désiré). Si le mauvais mot de passe est tapé, ksu échoue.

NOTE :

Lors de l'authentification, seuls les tickets qui ont pu être obtenus sans fournir de mot de passe sont mis en cache dans le cache source.

OPTIONS

-n nom_principal_cible
Spécifie un nom de principal cible Kerberos. Utilisé dans les phases d'authentification et d'autorisation de ksu.

Si ksu est invoqué sans -n, un nom de principal par défaut est attribué via l'heuristique suivante :

•
Cas 1 : l'utilisateur source n'est pas root.

Si l'utilisateur cible est l'utilisateur source, le nom du principal par défaut est défini sur le principal par défaut du cache source. Si le cache n'existe pas, alors le nom du principal par défaut est défini sur utilisateur_cible@royaume_local. Si les utilisateurs source et cible sont différents et que ni ~utilisateur_cible/.k5users ni ~utilisateur_cible/.k5login n'existent, alors le nom du principal par défaut est nom_utilisateur_cible@royaume_local. Sinon, en partant du premier principal listé ci-dessous, ksu vérifie si le principal est autorisé à accéder au compte cible et s'il existe un ticket légitime pour ce principal dans le cache source. Si les deux conditions sont remplies, ce principal devient le principal cible par défaut, sinon passez au principal suivant.

a.
principal par défaut du cache source
b.
utilisateur_cible@royaume_local
>
c.
source_user@local_realm

Si a-c échoue, essayez n'importe quel principal pour lequel il existe un ticket dans le cache source et qui est autorisé à accéder au compte cible. Si cela échoue, sélectionnez le premier principal autorisé à accéder au compte cible dans la liste ci-dessus. Si aucun n'est autorisé et que ksu est configuré avec PRINC_LOOK_AHEAD activé, sélectionnez le principal par défaut comme suit:

Pour chaque candidat dans la liste ci-dessus, sélectionnez un principal autorisé qui a le même nom de realm et dont la première partie du nom du principal est égale au préfixe du candidat. Par exemple, si le candidat a) est jqpublic@ISI.EDU et que jqpublic/secure@ISI.EDU est autorisé à accéder au compte cible, alors le principal par défaut est défini sur jqpublic/secure@ISI.EDU.

•
Cas 2: l'utilisateur source est root.

Si l'utilisateur cible n'est pas root, le nom du principal par défaut est target_user@local_realm. Sinon, si le cache source existe, le nom du principal par défaut est défini sur le principal par défaut du cache source. Si le cache source n'existe pas, le nom du principal par défaut est défini sur root\@local_realm.

-c nom_cache_source

Spécifie le nom du cache source (par exemple, -c FILE:/tmp/my_cache). Si l'option -c n'est pas utilisée, le nom est obtenu à partir de la variable d'environnement KRB5CCNAME. Si KRB5CCNAME n'est pas définie, le nom du cache source est défini sur krb5cc_<uid_source>. Le nom du cache cible est automatiquement défini sur krb5cc_<uid_cible>.(gen_sym()), où gen_sym génère un nouveau nombre tel que le cache résultant n'existe pas déjà. Par exemple: 
krb5cc_1984.2
-k
Ne pas supprimer le cache cible à la fin du shell cible ou d'une commande (commande -e). Sans -k, ksu supprime le cache cible.
-z
Restreindre la copie des tickets du cache source vers le cache cible aux seuls tickets où client == nom du principal cible. Utilisez l'option -n si vous souhaitez les tickets autres que le principal par défaut. Notez que l'option -z est mutuellement exclusive avec l'option -Z.
-Z
Ne copier aucun ticket du cache source vers le cache cible. Créez simplement un nouveau cache cible, où le nom du principal par défaut du cache est initialisé au nom du principal cible. Notez que l'option -Z est mutuellement exclusive avec l'option -z.
-q
Supprimer l'affichage des messages de statut.

Options de ticket d'octroi de ticket:

-l durée -r temps -p -P -f -F
Les options de ticket d'octroi de ticket s'appliquent uniquement au cas où il n'y a pas de tickets appropriés dans le cache pour authentifier l'utilisateur source. Dans ce cas, si ksu est configuré pour demander aux utilisateurs un mot de passe Kerberos (GET_TGT_VIA_PASSWD est défini), les options de ticket d'octroi de ticket spécifiées seront utilisées lors de l'obtention d'un ticket d'octroi de ticket auprès du serveur Kerberos.
-l durée
(chaîne de durée.) Spécifie la durée de vie demandée pour le ticket ; si cette option n'est pas spécifiée, la durée de vie par défaut du ticket (12 heures) est utilisée à la place.
-r temps
(chaîne de durée.) Spécifie que l'option renouvelable doit être demandée pour le ticket, et spécifie la durée de vie totale souhaitée du ticket.
-p
spécifie que l'option proxiable doit être demandée pour le ticket.
-P
spécifie que l'option proxiable ne doit pas être demandée pour le ticket, même si la configuration par défaut est de demander des tickets proxiables.
-f
l'option spécifie que l'option transférable doit être demandée pour le ticket.
-F
l'option spécifie que l'option transférable ne doit pas être demandée pour le ticket, même si la configuration par défaut est de demander des tickets transférables.
-e commande [arguments ... ]
ksu se comporte exactement comme s'il avait été appelé sans l'option -e, sauf qu'au lieu d'exécuter le shell cible, ksu exécute la commande spécifiée. Exemple d'utilisation:
ksu bob -e ls -lag

L'algorithme d'autorisation pour -e est le suivant:

Si l'utilisateur source est root ou si l'utilisateur source == l'utilisateur cible, aucune autorisation n'a lieu et la commande est exécutée. Si l'ID utilisateur source != 0, et que le fichier ~target_user/.k5users n'existe pas, l'autorisation échoue. Sinon, le fichier ~target_user/.k5users doit avoir une entrée appropriée pour que le principal cible soit autorisé.

Le format du fichier .k5users:

Une seule entrée de principal sur chaque ligne, qui peut être suivie d'une liste de commandes que le principal est autorisé à exécuter. Un nom de principal suivi d'un * signifie que l'utilisateur est autorisé à exécuter n'importe quelle commande. Ainsi, dans l'exemple suivant:

jqpublic@USC.EDU ls mail /local/kerberos/klist
jqpublic/secure@USC.EDU *
jqpublic/admin@USC.EDU

jqpublic@USC.EDU est uniquement autorisé à exécuter les commandes ls, mail et klist. jqpublic/secure@USC.EDU est autorisé à exécuter n'importe quelle commande. jqpublic/admin@USC.EDU n'est autorisé à exécuter aucune commande. Notez que jqpublic/admin@USC.EDU est autorisé à exécuter le shell cible (ksu normal, sans l'option -e) mais pas jqpublic@USC.EDU.

Les commandes listées après le nom du principal doivent être soit des chemins complets, soit simplement le nom du programme. Dans ce dernier cas, CMD_PATH spécifiant l'emplacement des programmes autorisés doit être défini au moment de la compilation de ksu. Quelle commande est exécutée?

Si l'utilisateur source est root ou si l'utilisateur cible est l'utilisateur source ou si l'utilisateur est autorisé à exécuter n'importe quelle commande (entrée *), alors la commande peut être un chemin complet ou relatif menant au programme cible. Sinon, l'utilisateur doit spécifier soit un chemin complet, soit simplement le nom du programme.

-a arguments
Spécifie les arguments à passer au shell cible. Notez que tous les drapeaux et paramètres suivant -a seront passés au shell, donc toutes les options destinées à ksu doivent précéder -a.

L'option -a peut être utilisée pour simuler l'option -e si elle est utilisée comme suit:

-a -c [commande [arguments]].

-c est interprété par le c-shell pour exécuter la commande.

INSTRUCTIONS D'INSTALLATION

ksu peut être compilé avec les quatre indicateurs suivants:

GET_TGT_VIA_PASSWD
Dans le cas où aucun ticket approprié n'est trouvé dans le cache source, l'utilisateur sera invité à entrer un mot de passe Kerberos. Le mot de passe est ensuite utilisé pour obtenir un ticket d'octroi de ticket du serveur Kerberos. Le danger de configurer ksu avec cette macro est si l'utilisateur source est connecté à distance et n'a pas de canal sécurisé, le mot de passe peut être exposé.
PRINC_LOOK_AHEAD
Lors de la résolution du nom du principal par défaut, PRINC_LOOK_AHEAD permet à ksu de trouver des noms de principaux dans le fichier .k5users comme décrit dans la section OPTIONS (voir l'option -n).
CMD_PATH
Spécifie une liste de répertoires contenant les programmes que les utilisateurs sont autorisés à exécuter (via le fichier .k5users).
HAVE_GETUSERSHELL
Si l'utilisateur source n'est pas root, ksu insiste pour que le shell de l'utilisateur cible invité soit un shell "légal". getusershell(3) est appelé pour obtenir les noms des shells "légaux". Notez que le shell de l'utilisateur cible est obtenu à partir du fichier passwd.

Configuration d'exemple:

KSU_OPTS = -DGET_TGT_VIA_PASSWD -DPRINC_LOOK_AHEAD -DCMD_PATH='"/bin /usr/ucb /local/bin"

ksu doit appartenir à root et avoir le bit set user id activé.

ksu tente d'obtenir un ticket pour le serveur final, tout comme telnet et rlogin kerberisés. Par conséquent, il doit y avoir une entrée pour le serveur dans la base de données Kerberos (par exemple, host/nii.isi.edu@ISI.EDU). Le fichier keytab doit être à un emplacement approprié.

EFFETS DE BORD

ksu supprime tous les tickets expirés du cache source.
