kernel-install est utilisé pour installer et supprimer des images de noyau et d'initrd [1] sur et depuis la partition de démarrage, désignée

kernel-install exécutera les fichiers exécutables (« plugins ») situés dans le répertoire /usr/lib/kernel/install.d/ et le répertoire d'administration local /etc/kernel/install.d/. Tous les fichiers sont triés collectivement et exécutés dans l'ordre lexicographique, quel que soit le répertoire dans lequel ils se trouvent. Cependant, les fichiers portant des noms identiques se remplacent mutuellement. Les fichiers de /etc/kernel/install.d/ ont la priorité sur les fichiers portant le même nom dans /usr/lib/kernel/install.d/. Cela peut être utilisé pour remplacer un exécutable fourni par le système par un fichier local si nécessaire ; un lien symbolique dans /etc/kernel/install.d/ portant le même nom qu'un exécutable dans /usr/lib/kernel/install.d/, pointant vers /dev/null, désactive complètement l'exécutable. Les exécutables doivent avoir l'extension « .install » ; les autres extensions sont ignorées. Un exécutable placé dans ces répertoires doit

retourner

OPTION

S

Les options suivantes sont prises en compte

:

--esp-path

=
Chemin vers la partition système EFI (ESP). Si non spécifié, /efi/, /boot/, et /boot/efi/ sont vérifiés à tour de rôle. Il est recommandé de monter la ESP sur /efi/, si
possible.

--boot-path

=
Chemin vers la partition du chargeur de démarrage étendu, telle que définie dans le Boot Loader Specification[2]. Si non spécifié, /boot/ est vérifié. Il est recommandé de monter la partition du chargeur de démarrage étendu sur /boot/, si

--make-entry-directory=yes|no|aut

o
Contrôle la création et la suppression du répertoire d'entrées de type #1 du Boot Loader Specification[2] sur le système de fichiers contenant des ressources telles que les images de noyau et d'initrd pendant add et remove, respectivement. Le répertoire est nommé d'après le jeton d'entrée et est placé immédiatement sous le répertoire racine de démarrage. Lorsqu'il est défini à "auto", le répertoire est créé ou supprimé uniquement lorsque la disposition d'installation est "bls". La valeur par défaut est "auto".

--entry-token

=
Contrôle comment nommer et identifier les entrées du chargeur de démarrage pour cette installation ou suppression de noyau. Prend comme argument l'une des valeurs "auto", "machine-id", "os-id", "os-image-id", ou une chaîne arbitraire préfixée par "literal:".

Si défini à machine-id, les entrées sont nommées d'après l'ID de machine du système en cours d'exécution (par ex. "b0e793a9baf14b5fa13ecbe84ff637ac"). Voir machine-id(5) pour des détails sur le concept et le fichier d'ID de

machine.

Si défini à os-id, les entrées sont nommées d'après l'ID du système d'exploitation du système en cours d'exécution, c'est-à-dire le champ ID= de os-release(5) (par ex. "fedora"). De même, si défini à os-image-id, les entrées sont nommées d'après l'ID de l'image du système d'exploitation du système en cours d'exécution, c'est-à-dire le champ IMAGE_ID= de os-release (par ex. "vendorx-cashier-system")

.

Si défini à auto (la valeur par défaut), le fichier /etc/kernel/entry-token (ou $KERNEL_INSTALL_CONF_ROOT/entry-token) sera lu s'il existe, et la valeur stockée sera utilisée. Sinon, si l'ID de machine locale est initialisé, il est utilisé. Sinon, IMAGE_ID= de os-release sera utilisé, s'il est défini. Sinon, ID= de os-release sera utilisé, s'il est défini. Sinon, un ID de machine généré aléatoirement est

utilisé.

L'utilisation de l'ID de machine pour nommer les entrées est généralement préférable, cependant il y a des cas où l'utilisation des autres identifiants est une bonne option. Plus précisément : si les données d'identification que l'ID de machine implique ne doivent pas être stockées sur la partition (non chiffrée) $BOOT_ROOT, ou si l'ID doit être généré au premier démarrage et n'est pas connu lorsque les entrées sont préparées. Notez que l'utilisation de l'ID de machine a l'avantage que plusieurs installations parallèles du même système d'exploitation peuvent coexister sur le même support, et qu'elles peuvent mettre à jour leurs entrées de chargeur de démarrage indépendamment. Lorsqu'un autre identifiant est utilisé (tel que l'ID du système d'exploitation ou l'ID de l'image du système d'exploitation), les installations parallèles du même système d'exploitation essaieraient d'utiliser le même nom d'entrée. Pour prendre en charge les installations parallèles, l'installateur doit utiliser un jeton d'entrée différent lors de l'ajout d'une deuxième

installation.

$KERNEL_INSTALL_MACHINE_ID est défini pour les plugins avec le machine-id souhaité à utiliser. C'est toujours un ID de 128 bits. Normalement, il est lu depuis /etc/machine-id, mais il peut aussi être remplacé via $MACHINE_ID (voir ci-dessous). S'il n'est pas spécifié via ces méthodes, une valeur de repli sera générée par kernel-install et utilisée pour une seule

invocation.

$KERNEL_INSTALL_ENTRY_TOKEN est défini pour les plugins avec le "jeton" d'entrée souhaité à utiliser. C'est un identifiant qui doit être utilisé pour identifier l'installation locale, et est souvent l'ID de machine, c'est-à-dire le même que $KERNEL_INSTALL_MACHINE_ID, mais pourrait aussi être un autre type d'identifiant, par exemple une chaîne fixe ou les valeurs ID=, IMAGE_ID= de /etc/os-release. La chaîne passée ici sera utilisée pour nommer les entrées du Boot Loader Specification, ou les répertoires dans lesquels l'image du noyau et les images du disque RAM initial sont

placées.

Notez que bien que $KERNEL_INSTALL_ENTRY_TOKEN et $KERNEL_INSTALL_MACHINE_ID soient souvent définis à la même valeur, ce dernier est garanti d'être un ID valide de 32 caractères en hexadécimal minuscule tandis que le premier peut être n'importe quelle chaîne courte. Le jeton d'entrée à utiliser est lu depuis /etc/kernel/entry-token, s'il existe. Sinon, quelques candidats possibles ci-dessous $BOOT sont vérifiés pour des répertoires d'entrées de type 1 du Boot Loader Specification, et si trouvé, le jeton d'entrée en est dérivé. Si ce n'est pas le cas, $KERNEL_INSTALL_MACHINE_ID est utilisé comme valeur de

repli.

$KERNEL_INSTALL_BOOT_ROOT est défini pour les plugins avec le chemin absolu du répertoire racine (point de montage, généralement) de la hiérarchie où les entrées du chargeur de démarrage, les images de noyau et les ressources associées doivent être placés. C'est généralement le chemin où la partition XBOOTLDR ou la ESP (partition système EFI) sont montées, et aussi conceptuellement appelé $BOOT. Peut être remplacé en définissant $BOOT_ROOT (voir ci-dessous)

.

$KERNEL_INSTALL_CONF_ROOT peut être défini pour remplacer l'emplacement des fichiers de configuration lus par kernel-install. Lorsqu'il est défini, install.conf, entry-token et d'autres fichiers seront lus depuis ce répertoire uniquement.
