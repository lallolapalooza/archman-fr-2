NOM

kmidiff - comparer les KMI des arbres du noyau Linux

kmidiff compare les interfaces binaires des modules du noyau (KMI) de deux arbres du noyau Linux. La KMI binaire est l'interface que le noyau Linux expose à ses modules. Les arbres qui nous intéressent ici sont le résultat de la compilation de l'arbre source du noyau Linux.

APPROCHE GÉNÉRALE

Un exemple de la manière de compiler votre noyau si vous souhaitez le comparer à un autre en utilisant kmidiff est le suivant :

git clone -b v4.5 git://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git linux/v4.5
cd linux/v4.5
make allyesconfig all

Ensuite, installez les modules dans un répertoire, par exemple, le sous-répertoire build/modules de votre arborescence source du noyau :

mkdir build/modules
make modules_install INSTALL_MOD_DIR=build/modules

Ensuite, construisez une liste des interfaces exportées par le noyau, que vous souhaitez comparer :

cat > kmi-whitelist << EOF
[kernel_4.5_kmi_whitelist]
 init_task
 schedule
 dev_queue_xmit
 __kmalloc
 printk
EOF

Supposons que vous ayez fait quelque chose de similaire pour la branche v4.6 du noyau Linux, vous avez maintenant ces deux répertoires : linux/v4.5 et linux/v4.6. Leurs modules sont présents dans les répertoires linux/v4.5/build/modules et linux/v4.6/build/modules.

Pour comparer leurs KMI, kmidiff a besoin de savoir où trouver les binaires vmlinux et leurs modules associés. Voici à quoi ressemblerait la ligne de commande :

kmidiff                                     \
  --kmi-whitelist  linux/v4.6/kmi-whitelist \
  --vmlinux1       linux/v4.5/vmlinux       \
  --vmlinux2       linux/v4.6/vmlinux       \
                   linux/v4.5/build/modules \
                   linux/v4.6/build/modules

Cet outil utilise la bibliothèque libabigail pour analyser le binaire ainsi que ses informations de débogage associées. Voici son mode de fonctionnement général.

Libabigail dispose alors de fonctionnalités pour générer des représentations textuelles des Corpus ABI, les comparer, analyser leurs changements et en faire rapport.

INVOQUER

Plus généralement, kmidiff est invoqué sous la forme :

kmidiff [options] <premier-repertoire-modules> <second-repertoire-modules>

ENVIRONNEMENT

Par défaut, kmidiff compare toutes les interfaces (fonctions et variables exportées) entre le noyau et ses modules. En pratique, cependant, certains utilisateurs pourraient vouloir comparer un sous-ensemble de ces interfaces.

Les utilisateurs peuvent alors définir une « liste blanche » des interfaces à comparer. Une telle liste blanche est juste un fichier au format « INI » qui ressemble à ceci :

[kernel_version_x86_64_whitelist]
  nom_fonction1
  nom_fonction2
  nom_variable_globale1
  ....

Notez que le nom de la section (le nom entre les deux crochets) de ce fichier INI doit simplement se terminer par la chaîne « whitelist ». Vous pouvez donc définir le nom que vous souhaitez, par exemple [kernel_46_x86_64_whitelist].

Ensuite, chaque ligne de ce fichier de liste blanche est le nom d'une fonction ou d'une variable exportée. Seules ces interfaces, ainsi que les types accessibles depuis leurs signatures, seront comparées par kmidiff récursivement.

OPTIONS

  • --help | -h

    Affiche une aide courte sur la commande et quitte.

  • --version | -v

    Affiche la version du programme et quitte.

  • --verbose

    Affiche des messages verbaux pendant l'exécution.

  • --debug-info-dir1 | --d1 <di-path1>

    Pour les cas où les informations de débogage pour les binaires du premier noyau Linux sont séparées dans des fichiers distincts, indique à kmidiff où trouver ces fichiers d'informations de débogage séparés.

    Notez que di-path doit pointer vers le répertoire racine sous lequel les informations de débogage sont organisées de manière arborescente. Sur les systèmes basés sur Red Hat, ce répertoire est généralement <root>/usr/lib/debug.

  • --debug-info-dir2 | --d2 <di-path2>

    Comme --debug-info-dir1, cette option indique à kmidiff où trouver les informations de débogage séparées pour les binaires du second noyau Linux.

  • --vmlinux1 | --l1 <chemin-vers-premier-vmlinux>

    Définit le chemin vers le premier binaire vmlinux à considérer. Ce doit être le binaire vmlinux décompressé compilé avec les informations de débogage.

  • --vmlinux2 | --l2 <chemin-vers-premier-vmlinux>

    Définit le chemin vers le second binaire vmlinux à considérer. Ce doit être le binaire vmlinux décompressé compilé avec les informations de débogage.

  • --kmi-whitelist | -w <chemin-vers-liste-blanche-interface>

    Définit le chemin vers la liste blanche des interfaces à comparer lors de la comparaison de l'interface du module du premier noyau avec celle du second noyau.

    Si cette option n'est pas fournie, *toutes* les interfaces exportées des deux noyaux sont comparées. Cela prend beaucoup de temps et n'est pas nécessairement pertinent car de nombreuses interfaces sont probablement censées voir leurs types accessibles changer.

    Par conséquent, assurez-vous toujours d'utiliser cette option, sauf si vous savez vraiment ce que vous faites.

  • --suppressions | --suppr <chemin-vers-suppressions>

    Utilise un fichier de spécification de suppression situé à chemin-vers-suppressions. Notez que cette option peut apparaître plusieurs fois sur la ligne de commande. Dans ce cas, tous les fichiers de spécification de suppression fournis sont pris en compte.

    Veuillez noter que, par défaut, si cette option n'est pas fournie, alors les *fichiers de spécification de suppression par défaut* sont chargés.

  • --no-change-categorization | -x

    Cette option désactive la catégorisation des changements en changements bénins et nuisibles. Notez que cette catégorisation est un prérequis pour le filtrage des changements, donc cette option désactive ce filtrage. L'objectif de cette option est d'accélérer l'exécution du programme dans les cas où le graphe de changements est énorme et où l'utilisateur s'intéresse uniquement à l'examen, par exemple, des changements de nœuds feuilles sans se soucier de leur impact potentiel sur les interfaces.

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

  • --btf
  • --impacted-interfaces | -i

    Indique quelles interfaces ont été impactées par chaque changement individuel de l'ABI.

  • --full-impact | -f

    Produit un rapport de changement qui montre l'impact complet de chaque changement sur les interfaces exportées. C'est le type de rapport par défaut produit par des outils tels que abidiff ou abipkgdiff.

  • --exported-interfaces-only

    C'est pourquoi cette option est activée par défaut.

  • --allow-non-exported-interfaces

    Le problème avec cette approche est cependant que l'analyse de toutes les interfaces visibles de l'extérieur de leur unité de traduction peut représenter une grande quantité de données, entraînant des opérations très lentes.

    Notez que cette option est désactivée par défaut.

  • --show-bytes

    Affiche les tailles et les décalages en octets, pas en bits. Cette option est activée par défaut.

  • --show-bits

    Affiche les tailles et les décalages en bits, pas en octets. Par défaut, les tailles et les décalages sont affichés en octets.

  • --show-hex

    Affiche les tailles et les décalages en base hexadécimale. Cette option est activée par défaut.

  • --show-dec

    Affiche les tailles et les décalages en base décimale.
