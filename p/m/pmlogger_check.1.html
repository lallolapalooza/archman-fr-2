PMLOGGER_CHECK(1) Manuel des commandes générales PMLOGGER_CHECK(1)

NOM

pmlogger_check - administration des fichiers d'archive Performance Co-Pilot

SYNOPIS

$PCP_BINADM_DIR/pmlogger_check [-CNnPpqsTV?] [-c control] [-l logfile]

DESCRIPTION

pmlogger_check et les outils associés pmlogger_daily(1) ainsi que les fichiers de contrôle associés (voir pmlogger.control(5)) peuvent être utilisés pour créer un régime personnalisé d'administration et de gestion pour les archives historiques de données de performance au sein de l'infrastructure Performance Co-Pilot (voir PCPIntro(1)).

pmlogger_check peut être exécuté à tout moment de la journée et est destiné à vérifier qu'un ensemble désiré de processus pmlogger(1) sont en cours d'exécution. Sinon, il (ré)démarre tout logger manquant. Par défaut, pmlogger_check appelle également pmlogger_daily(1) avec une option -K pour exécuter toute tâche de compression d'archive requise.

OPTIONS

-C
Cette option amène pmlogger_check à interroger les informations de niveau d'exécution du service système pour pmlogger, et à les utiliser pour déterminer s'il faut démarrer ou non les processus.
-c control, --control=control
pmlogger_check et pmlogger_daily(1) sont tous deux contrôlés par des fichiers de contrôle de logger PCP (voir pmlogger.control(5)) qui spécifient les instances de pmlogger à gérer. Le fichier de contrôle par défaut est $PCP_PMLOGGERCONTROL_PATH mais un autre peut être spécifié en utilisant l'option -c. Si le répertoire $PCP_PMLOGGERCONTROL_PATH.d (ou control.d de l'option -c) existe, alors le contenu de tout fichier de contrôle supplémentaire qu'il contient sera ajouté au fichier de contrôle principal (qui doit exister).
-l fichier, --logfile=fichier
Pour s'assurer que le courrier n'est pas envoyé involontairement lorsque ces scripts sont exécutés depuis cron(8) ou systemd(1), les diagnostics sont toujours envoyés aux fichiers journaux. Par défaut, ce fichier est $PCP_LOG_DIR/pmlogger/pmlogger_check.log mais cela peut être modifié en utilisant l'option -l. Si ce fichier journal fichier existe déjà lorsque le script démarre, il sera renommé avec un suffixe .prev (écrasant tout fichier journal précédemment sauvegardé) avant que les diagnostics ne soient générés vers le fichier journal. Les options -l et -t ne peuvent pas être utilisées ensemble.
-N, --showme
Cette option active un mode « montre-moi », où les actions sont affichées, mais non exécutées, dans le style de « make -n ». L'utilisation de -N conjointement avec -V maximise les capacités de diagnostic pour le débogage.
-n, --noerror
Force le statut de sortie à 0, sauf en cas d'erreurs catastrophiques. Utile lorsqu'appelé depuis une unité de service ou de temporisation systemd(1) afin que l'unité associée ne soit pas marquée comme échouée d'une manière qui empêcherait son exécution ultérieure par systemd(1).
-P, --only-primary
Si cette option est spécifiée pour pmlogger_check, seule l'entrée du logger primaire dans les fichiers de contrôle sera traitée. C'est l'opposé logique de l'option -p décrite ci-dessus et est destinée à être utilisée par les scripts RC qui ne démarrent que le logger primaire, tels que l'unité pmlogger.service. Les options -p et -P sont mutuellement exclusives.
-p, --skip-primary
Si cette option est spécifiée pour pmlogger_check, toute ligne des fichiers de contrôle pour le pmlogger *primaire* sera ignorée. Cette option est destinée aux environnements où un démon système, comme systemd(1), est responsable du contrôle (démarrage, arrêt, redémarrage, etc.) du pmlogger *primaire*.
-q, --quick
Si cette option est spécifiée pour pmlogger_check, le script effectuera un « démarrage rapide » en évitant tout traitement optionnel tel que l'appel à pmlogger_daily(1) pour effectuer des tâches de compression d'archive.
-s, --stop
L'utilisation de cette option fournit la fonctionnalité inverse de pmlogger_check, permettant à l'ensemble des processus pmlogger d'être proprement arrêté.
-T, --terse
Cette option de pmlogger_check produit une sortie moins verbeuse que par défaut. Ceci est le plus adapté pour une « ferme » de pmlogger où de nombreuses instances de pmlogger sont censées être en cours d'exécution.
-V, --verbose
L'option -V active le traçage verbeux. Par défaut, pmlogger_check ne génère aucune sortie sauf si une condition d'erreur ou d'avertissement est rencontrée. Une seconde option -V augmente la verbosité. L'utilisation de -N conjointement avec -V maximise les capacités de diagnostic pour le débogage.
-?, --help
Affiche le message d'utilisation et quitte.

CONFIGURATION

Consultez pmlogger.control(5) pour une description des fichiers de contrôle utilisés pour gérer quels instances de pmlogger et quelles archives sont gérées par pmlogger_check et pmlogger_daily(1).

L'utilitaire pmlogctl(1) peut invoquer pmlogger_check en utilisant la commande sudo(1) pour l'exécuter sous le compte ``pcp'' de l'utilisateur $PCP_USER. Si sudo est configuré avec l'option non standard requiretty (voir ci-dessous), pmlogger_check peut échouer à s'exécuter car il ne dispose pas d'un tty configuré. Ce problème peut être résolu en ajoutant une seconde ligne (développez $PCP_BINADM_DIR selon votre plateforme) au fichier de configuration /etc/sudoers comme suit :

Defaults requiretty
Defaults!$PCP_BINADM_DIR/pmlogger_check !requiretty

Notez que le compte PCP non privilégié sous lequel ces commandes s'exécutent utilise /sbin/nologin comme shell, donc l'option requiretty est inefficace ici et peut être désactivée en toute sécurité de cette manière.

FICHIERS

$PCP_VAR_DIR/config/pmlogger/config.default
emplacement du fichier de configuration pmlogger par défaut pour le logger primaire local, généralement généré automatiquement par pmlogconf(1).
$PCP_ARCHIVE_DIR/<hostname>
emplacement par défaut pour les archives des informations de performance collectées depuis l'hôte hostname
$PCP_ARCHIVE_DIR/<hostname>/lock
fichier de verrouillage transitoire pour garantir l'exclusion mutuelle pendant l'administration de pmlogger pour l'hôte hostname - s'il est présent, peut être supprimé en toute sécurité si ni pmlogger_daily(1) ni pmlogger_check ne sont en cours d'exécution
$PCP_ARCHIVE_DIR/<hostname>/Latest
folio d'archive PCP créé par mkaf(1) pour l'archive lancée le plus récemment contenant des métriques de performance de l'hôte hostname
$PCP_LOG_DIR/NOTICES
fichier de « notifications » PCP utilisé par pmie(1) et ses semblables
$PCP_LOG_DIR/pmlogger/pmlogger_check.log
si la précédente exécution de pmlogger_check a produit une sortie, elle est sauvegardée ici. Le cas normal est aucune sortie, auquel cas le fichier n'existe pas.
$PCP_ARCHIVE_DIR/SaveLogs
si ce répertoire existe, alors le fichier journal de l'argument -l de pmlogger_check sera sauvegardé dans ce répertoire avec le nom formaté <date>-pmlogger_check.log.<pid> Cela permet d'inspecter le fichier journal ultérieurement, même si plusieurs exécutions de pmlogger_check ont été lancées entre-temps. Parce que les outils d'administration d'archives PCP s'exécutent sous le compte $PCP_USER ``pcp'', $PCP_ARCHIVE_DIR/SaveLogs doit généralement appartenir à l'utilisateur ``pcp''.

$PCP_ARCHIVE_DIR/<hostname>/SaveLogs
si ce répertoire existe, alors le fichier journal de l'argument -l d'un pmlogger(1) nouvellement lancé pour hostname sera enregistré dans ce répertoire sous le nom archive.log où archive est le nom de base des fichiers d'archive PCP pmlogger(1) associés. Cela permet d'inspecter le fichier journal ultérieurement, même si plusieurs instances de pmlogger(1) pour hostname ont été lancées entre-temps. Comme les outils de gestion d'archives PCP s'exécutent sous le compte utilisateur PCP ``pcp'', $PCP_ARCHIVE_DIR/<hostname>/SaveLogs doit généralement appartenir à l'utilisateur ``pcp''.

ENVIRONNEMENT PCP

Les variables d'environnement commençant par le préfixe PCP_ sont utilisées pour paramétrer les noms de fichiers et de répertoires utilisés par PCP. Sur chaque installation, le fichier /etc/pcp.conf contient les valeurs locales de ces variables. La variable $PCP_CONF peut être utilisée pour spécifier un fichier de configuration alternatif, comme décrit dans pcp.conf(5).

Le comportement par défaut, lorsque la configuration de pmlogger(1) provient de pmlogconf(1), est de régénérer le fichier de configuration et de vérifier les modifications chaque fois que pmlogger(1) est démarré depuis pmlogger_check. Si la configuration du PMDA est stable, cela n'est pas nécessaire, et la définition de $PMLOGGER_CHECK_SKIP_LOGCONF à yes désactive la régénération et la vérification.
