DESCRIPTION

Pour les agents de domaine de métriques de performance (PMDA(3)) utilisant les protocoles PDU binaires pour communiquer avec pmcd(1), la routine pmdaMain fournit une implémentation générique de la boucle principale pilotée par les PDU.

dispatch décrit comment traiter chaque PDU entrant. C'est un vecteur de pointeurs de fonction, un par type de requête PDU, tel qu'utilisé dans l'interface DSO pour un PMDA, à savoir :

/*
 * Définitions d'interface pour les méthodes PMDA
 */
typedef struct {
    int domain;         /* ID du domaine de métriques de performance à définir/renvoyer ici */
    struct {
        unsigned int    pmda_interface: 8; /* Version de l'interface PMDA DSO */
        unsigned int    pmapi_version : 8; /* Version PMAPI */
        unsigned int    flags : 16;        /* Indicateurs de fonctionnalités optionnels */
    } comm;             /* informations de communication et de version à définir/renvoyer */
    int status;         /* état d'initialisation à renvoyer ici */
    union {
        struct {                              /* PMDA_INTERFACE_2 ou _3 */
            pmdaExt *ext;
            int (*profile)(pmProfile *, pmdaExt *);
            int (*fetch)(int, pmID *, pmResult **, pmdaExt *);
            int (*desc)(pmID, pmDesc *, pmdaExt *);
            int (*instance)(pmInDom, int, char *, pmInResult **, pmdaExt *);
            int (*text)(int, int, char **, pmdaExt *);
            int (*store)(pmResult *, pmdaExt *);
        } two, three;
        struct {                              /* PMDA_INTERFACE_4 ou _5 */
            pmdaExt *ext;
            int     (*profile)(pmProfile *, pmdaExt *);
            int     (*fetch)(int, pmID *, pmResult **, pmdaExt *);
            int     (*desc)(pmID, pmDesc *, pmdaExt *);
            int     (*instance)(pmInDom, int, char *, pmInResult **, pmdaExt *);
            int     (*text)(int, int, char **, pmdaExt *);
            int     (*store)(pmResult *, pmdaExt *);
            int     (*pmid)(char *, pmID *, pmdaExt *);
            int     (*name)(pmID, char ***, pmdaExt *);
            int     (*children)(char *, int, char ***, int **, pmdaExt *);
        } four, five;
        struct {                              /* PMDA_INTERFACE_6 */
            pmdaExt *ext;
            int     (*profile)(pmProfile *, pmdaExt *);
            int     (*fetch)(int, pmID *, pmResult **, pmdaExt *);
            int     (*desc)(pmID, pmDesc *, pmdaExt *);
            int     (*instance)(pmInDom, int, char *, pmInResult **, pmdaExt *);
            int     (*text)(int, int, char **, pmdaExt *);
            int     (*store)(pmResult *, pmdaExt *);
            int     (*pmid)(char *, pmID *, pmdaExt *);
            int     (*name)(pmID, char ***, pmdaExt *);
            int     (*children)(char *, int, char ***, int **, pmdaExt *);
            int     (*attribute)(int, int, const char *, int, pmdaExt *);
        } six;
    } version;
} pmdaInterface;

Cette structure a été étendue pour intégrer les multiples versions d'interface qui ont évolué au fil du temps. Pour pmdaMain, dispatch->domain et dispatch->status sont ignorés. Le champ comm.pmda_interface est utilisé pour déterminer l'interface utilisée par le PMDA. Le réglage de ce champ sur PMDA_INTERFACE_2 ou PMDA_INTERFACE_3 forcera pmdaMain à utiliser les rappels dans la structure version.two ou version.three. Un réglage de PMDA_INTERFACE_4 ou PMDA_INTERFACE_5 forcera pmdaMain à utiliser les rappels dans la structure version.four ou version.five, et de même un réglage PMDA_INTERFACE_6 forcera pmdaMain à utiliser les rappels dans la structure version.six. Toute autre valeur entraînera une erreur et la terminaison de pmdaMain.

Notez que l'utilisation de dispatch comme interface entre pmcd(1) et les méthodes du PMDA permet à chaque PMDA d'être implémenté comme s'il s'agissait d'une bibliothèque dynamique partagée (DSO), pmdaMain fournissant un wrapper pratique qui peut être utilisé pour convertir de l'interface DSO à l'interface PDU binaire (PMDA démon).

pmdaMain s'exécute dans une boucle continue, ne revenant que lorsqu'un fin de fichier est rencontrée sur le descripteur de fichier d'entrée PDU.

RAPPELS D'APPEL

En plus des rappels de traitement PDU individuels - pmdaProfile(3), pmdaFetch(3), pmdaDesc(3), pmdaInstance(3), pmdaText(3), pmdaStore(3), pmdaPMID(3), pmdaName(3), pmdaChildren(3), et pmdaAttribute(3), il existe d'autres rappels qui peuvent affecter ou informer tout le traitement PDU au sein d'un PMDA, à savoir check, done et end. Ces rappels doivent être définis avec pmdaSetCheckCallBack, pmdaSetDoneCallBack et pmdaSetEndContextCallBack.

Si check n'est pas null, il est appelé après la réception de chaque PDU (mais avant son traitement), et done est appelé après l'envoi de chaque PDU. Si check renvoie une valeur inférieure à zéro (typiquement PM_ERR_AGAIN), le traitement du PDU est ignoré et dans la plupart des cas, la valeur de retour est renvoyée comme PDU d'erreur à pmcd(1) - cela peut être utilisé pour les PMDA qui nécessitent une sorte de connexion différée ou de protocoles de reconnexion pour les sources sous-jacentes de métriques de performance, par exemple, un SGBD. L'indication d'erreur de check n'est pas renvoyée à pmcd(1) dans les cas où aucune няма d'accusé de réception n'est attendue, par exemple, pour un PDU_PROFILE.

Le rappel end permet à un PMDA de suivre l'état des clients individuels qui lui demandent d'effectuer des actions (traitement PDU). En utilisant pmdaGetContext, un PMDA peut déterminer, à tout moment, un identifiant entier qui identifie de manière unique les outils clients à l'extrémité distante de PMCD (pour les modes de contexte locaux, cet identifiant est toujours zéro). Ceci devient très important pour la gestion des métriques d'événements, où chaque événement doit être propagé une seule fois à chaque client intéressé. Il sous-tend également le mécanisme par lequel les informations de connexion sont passées au PMDA, telles que les informations d'identification (identifiants utilisateur et groupe) pour l'outil client.

Un dernier mécanisme de rappel est fourni pour gérer le pmResult construit pour un PDU_RESULT en réponse à une requête PDU_FETCH. Par défaut, pmdaMain libérera le pmResult une fois que le résultat aura été envoyé à pmcd(1). Pour certains PMDA, cela est inapproprié, par exemple, le pmResult est alloué statiquement, ou contient un hybride d'informations de tampon PDU épinglé et d'informations allouées dynamiquement. pmdaSetResultCallBack peut être utilisé pour définir un rappel alternatif de pmdaMain.

DIAGNOSTICS

Ces messages peuvent être ajoutés au fichier journal du PMDA :

PMDA interface version interface non supportée
La version interface n'est pas supportée par pmdaMain.
Type de PDU non reconnu
Le PMDA a reçu un PDU de pmcd qu'il ne reconnaît pas. Cela peut indiquer que le processus pmcd utilise une interface plus avancée que pmdaMain.

Si les options de contrôle de débogage de PMAPI(3) ont l'option ``libpmda'' activée, chaque PDU reçu est signalé dans le fichier journal du PMDA.
