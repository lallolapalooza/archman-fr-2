PMCD(1) Manuel des commandes générales PMCD(1)

NOM

pmcd - démon collecteur de métriques de performance

SYNTAXE

pmcd [-AfQSv?] [-c config] [-C nctx] [-D debug] [-H hostname] [-i ipaddress] [-l logfile] [-L bytes] [-M nmetric] [-[n|N] pmnsfile] [-p port[,port ...]] [-q timeout] [-s sockname] [-t timeout] [-T traceflag] [-U username] [-x file]

DESCRIPTION

pmcd est le collecteur utilisé par le Performance Co-Pilot (voir PCPIntro(1)) pour rassembler les métriques de performance sur un système. En règle générale, une instance de pmcd doit être en cours d'exécution sur un système pour que des métriques de performance soient disponibles pour le PCP.

pmcd accepte les connexions des applications clientes exécutées soit sur la même machine, soit à distance, et leur fournit des métriques et d'autres informations relatives de la machine sur laquelle pmcd s'exécute. pmcd délègue la plupart de ces requêtes à une collection d'agents de domaine de métriques de performance (ou simplement agents), où chaque agent est responsable d'un groupe particulier de métriques, connu sous le nom de domaine de l'agent. Par exemple, l'agent postgresql est responsable de la signalisation des informations relatives à la base de données PostgreSQL, telles que les comptes de transactions et de requêtes, les statistiques d'indexation et de réplication, etc.

Les agents peuvent être des processus démarrés par pmcd, des processus indépendants ou des objets partagés dynamiques (DSO, voir dlopen(3)) attachés à l'espace d'adressage de pmcd. La section de configuration ci-dessous décrit comment les connexions aux agents sont spécifiées.

Notez que si un échange PDU avec un agent expire, l'agent a enfreint l'exigence qu'il livre les métriques avec peu ou pas de délai. Ceci est considéré comme un échec de protocole et l'agent est déconnecté de pmcd. Toute requête ultérieure d'informations auprès de l'agent échouera avec un statut indiquant qu'aucun agent n'est disponible pour la fournir.

Il est possible de spécifier le contrôle d'accès à pmcd basé sur les utilisateurs, les groupes et les hôtes. Cela permet d'empêcher des utilisateurs, des groupes d'utilisateurs et certains hôtes d'accéder aux métriques fournies par pmcd et est décrit plus en détail dans la section de contrôle d'accès ci-dessous.

OPTIONS

Les options de ligne de commande disponibles sont :

-A
Désactive la publicité des services. Par défaut, pmcd annonce sa présence sur le réseau en utilisant tous les mécanismes disponibles (tels que Avahi/DNS-SD), aidant les outils de surveillance à distance à le trouver. Ces mécanismes sont désactivés avec cette option.
-c config, --config=config
Au démarrage, pmcd utilise un fichier de configuration provenant soit de $PCP_PMCDCONF_PATH, d'une variable de configuration dans /etc/pcp.conf, soit d'une variable d'environnement du même nom. Cependant, ces valeurs peuvent être remplacées par config en utilisant cette option. Le format de ce fichier de configuration est décrit ci-dessous.
-C nctx, --maxctx=nctx
Chaque client de pmcd peut créer un ou plusieurs contextes. Le nombre de contextes par client est limité à un maximum de 64 par défaut pour se défendre contre les attaques par déni de service par épuisement de mémoire et de descripteurs de fichiers. L'option -C peut être utilisée pour changer le maximum à nctx contextes.
-f, --foreground
Par défaut, pmcd est lancé comme un démon. L'option -f indique qu'il doit s'exécuter au premier plan. C'est particulièrement utile lorsqu'on essaie de diagnostiquer des problèmes avec des agents qui se comportent mal.
-H hostname, --hostname=hostname
Cette option peut être utilisée pour définir le nom d'hôte que pmcd utilisera pour représenter cette instance de lui-même. Ceci est utilisé par les outils clients comme pmlogger(1) lors de la signalisation sur l'hôte (éventuellement distant). Si cette option n'est pas définie, la métrique pmcd.hostname correspondra à celle renvoyée par pmhostname(1). Référez-vous à la page de manuel de cet outil pour connaître tous les détails sur la façon dont le nom d'hôte est évalué.
-i ipaddress, --interface=ipaddress
Cette option est généralement utilisée uniquement sur les hôtes ayant plus d'une interface réseau. Si aucune option -i n'est spécifiée, pmcd accepte les connexions faites à n'importe quelle adresse IP (Protocole Internet) de son hôte. L'option -i est utilisée pour spécifier explicitement une adresse IP sur laquelle les connexions doivent être acceptées. ipaddress doit être sous la forme dotted standard (par exemple, 100.23.45.6). L'option -i peut être utilisée plusieurs fois pour définir une liste d'adresses IP. Les connexions faites à d'autres adresses IP que possède l'hôte seront refusées. Ceci peut être utilisé pour limiter les connexions à une seule interface réseau si l'hôte est une passerelle réseau. Il est également utile si l'hôte prend en charge l'adresse IP d'un autre hôte défaillant. Dans une telle situation, seules les adresses IP standard de l'hôte doivent être fournies (pas celles héritées de l'hôte défaillant). Cela permet aux applications PCP de déterminer qu'un hôte a échoué, plutôt que de se connecter à l'hôte qui a pris l'identité de l'hôte défaillant.
-l logfile, --log=logfile
Par défaut, un fichier journal nommé pmcd.log est écrit dans le répertoire $PCP_LOG_DIR/pmcd. L'option -l provoque l'écriture du fichier journal dans logfile au lieu du défaut. Si le fichier journal ne peut pas être créé ou n'est pas accessible en écriture, la sortie est redirigée vers l'erreur standard.
-L bytes, --maxbytes=bytes
Les PDU reçus par pmcd des clients de surveillance sont limités à une taille maximale de 65536 octets par défaut pour se défendre contre les attaques par déni de service. L'option -L peut être utilisée pour changer la taille maximale des PDU entrants.
-M nmetric, --maxmetric=nmetric
Chaque fetch reçu par pmcd des clients de surveillance est limité à un maximum de 32768 métriques par défaut pour se défendre contre les attaques par déni de service par épuisement de la mémoire. L'option -M peut être utilisée pour changer le maximum à nmetric métriques.
-n pmnsfile, --namespace=pmnsfile
Normalement, pmcd charge l'espace de noms des métriques de performance (PMNS) par défaut depuis $PCP_VAR_DIR/pmns/root, cependant si l'option -n est spécifiée, un espace de noms alternatif est chargé depuis le fichier pmnsfile.
-N pmnsfile, --uniqnames=pmnsfile
Même fonction que -n, sauf pour la gestion des Identifiants de Métriques de Performance (PMID) dupliqués dans pmnsfile - les noms dupliqués sont autorisés avec -n mais ne sont pas autorisés avec -N.
-p port, --port=port
Spécifie le port sur lequel écouter. Par défaut, le port 44321 est utilisé.
-q timeout
Le protocole d'échange de version entre pmcd et l'agent (nouveau dans PCP 2.0 - introduit pour assurer la compatibilité ascendante) utilise ce délai d'attente pour spécifier combien de temps pmcd doit attendre avant de supposer qu'aucune réponse de version ne provient d'un agent. Si ce délai d'attente est atteint, l'agent est supposé être un agent qui ne comprend pas le protocole PCP 2.0. L'intervalle de délai d'attente par défaut est de trois secondes, mais l'option -q permet de spécifier un intervalle de délai d'attente alternatif (qui doit être supérieur à zéro). L'unité de timeout est en secondes. Alternativement, si -q n'est pas utilisé, la variable d'environnement PMCD_CREDS_TIMEOUT peut être utilisée pour définir l'intervalle de délai d'attente.
-Q, --remotecert
Exige que toutes les connexions clients distantes fournissent un certificat.
-s sockname, --socket=sockname
Spécifie le chemin d'un socket de domaine Unix local (uniquement pour les plates-formes prenant en charge cette famille de sockets). Le d
valeur par défaut est $PCP_RUN_DIR/pmcd.socket.
-S, --reqauth
Exiger que toutes les connexions client fournissent des informations d'identification utilisateur. Cela signifie que seuls les sockets de domaine Unix ou les connexions authentifiées sont autorisés (nécessite le support des sockets sécurisés). Si des exigences de contrôle d'accès par utilisateur ou par groupe sont spécifiées dans le fichier de configuration de pmcd, ce mode de fonctionnement est automatiquement activé, que le drapeau -S soit spécifié ou non.
-t délai
Pour empêcher les clients ou agents malveillants de bloquer l'ensemble du système de collecte de métriques de performance (PMCS), pmcd utilise des délais d'attente sur les échanges de PDU avec les clients et les agents exécutés en tant que processus. Par défaut, l'intervalle de délai d'attente est de cinq secondes. L'option -t permet de spécifier un intervalle de délai d'attente alternatif en secondes. Si délai est zéro, les délais d'attente sont désactivés. Il est presque impossible d'utiliser le débogueur interactivement sur un agent à moins que les délais d'attente n'aient été désactivés pour son pmcd "parent".

Une fois que pmcd est en cours d'exécution, le délai d'attente peut être modifié dynamiquement en stockant une valeur entière (le délai d'attente en secondes) dans la métrique pmcd.control.timeout via pmstore(1).

-T drapeau-trace, --trace=drapeau-trace
Pour aider au diagnostic d'erreurs pour les agents et/ou clients de pmcd qui ne se comportent pas correctement, un mécanisme de traçage d'événements interne est pris en charge dans pmcd. La valeur de drapeau-trace est interprétée comme un champ de bits avec les fonctions de contrôle suivantes :
1
activer le traçage des connexions client
2
activer le traçage des PDU
256
traçage des événements sans mise en mémoire tampon

Par défaut, le traçage des événements est mis en mémoire tampon à l'aide d'un tampon circulaire qui est écrasé au fur et à mesure que de nouveaux événements sont enregistrés. La taille par défaut du tampon contient les 20 derniers événements, bien que ce nombre puisse être remplacé en utilisant pmstore(1) pour modifier la métrique pmcd.control.tracebufs.

De même, une fois que pmcd est en cours d'exécution, le contrôle du traçage des événements peut être modifié dynamiquement en stockant 1 (activer) ou 0 (désactiver) dans les métriques pmcd.control.traceconn, pmcd.control.tracepdu et pmcd.control.tracenobuf. Ces métriques correspondent aux champs de bits associés à l'argument drapeau-trace de l'option -T.

Lorsqu'il fonctionne en mode avec mise en mémoire tampon, le tampon de traçage des événements sera vidé chaque fois qu'une connexion d'agent est terminée par pmcd, ou lorsque toute valeur est stockée dans la métrique pmcd.control.dumptrace via pmstore(1).

En mode sans mise en mémoire tampon, chaque événement sera signalé dès qu'il se produira.

-U nom-utilisateur, --username=UTILISATEUR
Compte utilisateur sous lequel exécuter pmcd. La valeur par défaut est le compte "pcp" non privilégié dans les versions actuelles de PCP, mais dans les versions plus anciennes, le compte superutilisateur ("root") était utilisé par défaut.
-v, --verify
Vérifie le fichier de configuration de pmcd, signale toute erreur puis se termine avec un statut indiquant le succès ou l'échec de la vérification.
-x fichier
Avant que le fichier-journal de pmcd ne puisse être ouvert, pmcd peut rencontrer une erreur fatale qui l'empêche de démarrer. Par défaut, la sortie décrivant cette erreur est envoyée à /dev/tty, mais elle peut être redirigée vers fichier.
-?, --help
Affiche le message d'utilisation et quitte.

CONFIGURATION

Au démarrage, pmcd recherche un fichier de configuration nommé $PCP_PMCDCONF_PATH. Ce fichier spécifie quels agents couvrent quels domaines de métriques de performance et comment pmcd doit prendre contact avec les agents. Une section optionnelle spécifiant les contrôles d'accès peut suivre les données de configuration des agents.

Attention : pmcd est généralement démarré dans le cadre de la séquence de démarrage et s'exécute initialement en tant que root. Le fichier de configuration peut contenir des commandes shell pour créer des agents, qui seront exécutées par root. Pour éviter les violations de sécurité, le fichier de configuration ne devrait être accessible en écriture qu'à root. L'utilisation de noms de chemins absolus est également recommandée.

La casse des mots réservés dans le fichier de configuration n'a pas d'importance, mais ailleurs, la casse est préservée.

Les lignes vides et les commentaires sont autorisés (voire encouragés) dans le fichier de configuration. Un commentaire commence par un caractère « # » et se termine à la fin de la ligne. Une ligne peut être continuée en s'assurant que le dernier caractère de la ligne est un « \ » (antislash). Un commentaire sur une ligne continuée se termine à la fin de la ligne continuée. Les espaces peuvent être inclus dans les éléments lexicaux en entourant l'élément entier de guillemets doubles. Un guillemet double précédé d'un antislash est toujours un guillemet double littéral. Un « # » entre guillemets doubles ou précédé d'un antislash est traité littéralement plutôt que comme un délimiteur de commentaire. Les éléments lexicaux et les séparateurs sont décrits plus en détail dans les sections suivantes.

CONFIGURATION DES AGENTS

Chaque ligne de la section de configuration des agents du fichier de configuration contient des détails sur la façon de connecter pmcd à l'un de ses agents et spécifie le domaine de métriques que l'agent gère. Un agent peut être attaché en tant que DSO, ou via un socket, ou une paire de pipes.

Chaque ligne de la section de configuration des agents du fichier de configuration doit être soit une spécification d'agent, soit un commentaire, soit une ligne vide. Les éléments lexicaux sont séparés par des espaces blancs, cependant une seule spécification d'agent ne peut pas être répartie sur plusieurs lignes sauf si un antislash est utilisé pour continuer la ligne.

Chaque spécification d'agent doit commencer par une étiquette textuelle (chaîne de caractères) suivie d'un entier dans la plage de 1 à 510. L'étiquette est une balise utilisée pour référencer l'agent et l'entier spécifie le domaine pour lequel l'agent fournit des données. Cet identifiant de domaine correspond à la partie domaine des PMID gérés par l'agent. Chaque agent doit avoir une étiquette et un identifiant de domaine uniques.

Pour les agents DSO, une ligne de la forme :

etiquette num-domaine dso point-entree chemin

doit apparaître. Où,

etiquette
est une chaîne identifiant l'agent
num-domaine
est un entier non signé spécifiant le domaine de l'agent dans la plage de 1 à 510
point-entree
est le nom d'une fonction d'initialisation qui sera appelée lors du chargement du DSO
chemin
désigne l'emplacement du DSO et ceci est censé être un chemin absolu. pmcd n'est capable de charger que les agents DSO qui ont le même simabi (Subprogram Interface Model ABI, ou conventions d'appel) que lui (c'est-à-dire qu'une seule des versions simabi sera applicable). La version simabi d'un pmcd en cours d'exécution peut être déterminée en récupérant pmcd.simabi. Alternativement, la commande file(1) peut être utilisée pour déterminer la version simabi à partir de l'exécutable pmcd.
Pour un chemin relatif, la variable d'environnement PMCD_PATH définit une liste de répertoires séparés par deux points (:) à rechercher lors de la tentative de localisation du DSO de l'agent. Le chemin de recherche par défaut est $PCP_SHARE_DIR/lib:/usr/pcp/lib.

Pour les agents fournissant des connexions socket, une ligne de la forme

etiquette num-domaine socket famille-addr adresse [ commande ]

doit apparaître. Où,

etiquette
est une chaîne identifiant l'agent
num-domaine
est un entier non signé spécifiant le domaine de l'agent dans la plage de 1 à 510
famille-addr
désigne si le socket est dans le domaine AF_INET, AF_INET6 ou AF_UNIX, et les valeurs correspondantes pour ce paramètre sont inet, ipv6 et unix respectivement.
adresse
spécifie l'adresse du socket dans la famille-addr précédemment spécifiée. Pour les sockets unix, l'adresse doit être le nom d'un socket d'agent sur l'hôte local (une adresse valide pour le domaine UNIX). Pour les sockets inet et ipv6, l'adresse peut être soit un numéro de port, soit un nom de port qui peut être utilisé pour se connecter à un agent sur l'hôte local. Il n'y a pas de syntaxe pour spécifier un agent sur un hôte distant car pmcd ne traite qu'avec les agents sur la même machine.
commande
est un paramètre optionnel utilisé pour spécifier une ligne de commande pour démarrer l'agent lorsque pmcd s'initialise. Si commande n'est pas présent, pmcd suppose que l'agent spécifié a déjà été créé. La commande est considérée comme commençant au premier caractère non blanc après l'adresse du socket et se terminant à la prochaine nouvelle ligne qui n'est pas précédée d'un antislash. Après un fork(2), la commande est passée sans modification à execve(2) pour instancier l'agent.

Pour les agents interagissant avec pmcd via stdin/stdout, une ligne de la forme :

etiquette num-domaine pipe protocole commande

doit apparaître. Où,

etiquette
est une chaîne identifiant l'agent
num-domaine
est un entier non signé spécifiant le domaine de l'agent
protocole
La valeur de ce paramètre doit être binary.
De plus, le protocole peut inclure le mot-clé notready pour indiquer que l'agent doit être marqué comme n'étant pas prêt à traiter les requêtes de pmcd. L'agent notifiera explicitement pmcd lorsqu'il sera prêt à traiter les requêtes en envoyant un PM_ERR_PMDAR
EADY PDU. Pour plus de détails sur ce protocole, y compris une description des paramètres IPC qui peuvent être spécifiés dans un script d'installation PMDA avec le paramètre ipc_prot, voir la section pertinente dans PMDA(3).
commande
spécifie une ligne de commande pour démarrer l'agent lorsque pmcd s'initialise. Notez que commande est obligatoire pour les agents basés sur des tuyaux. La commande est considérée comme commençant au premier caractère non blanc après le paramètre protocole et se terminant à la prochaine nouvelle ligne qui n'est pas précédée d'une barre oblique inverse. Après un fork(2), la commande est passée sans modification à execve(2) pour instancier l'agent.

CONFIGURATION DU CONTRÔLE D'ACCÈS

La section de contrôle d'accès du fichier de configuration est facultative, mais si elle est présente, elle doit suivre les données de configuration de l'agent. La casse des mots réservés est ignorée, mais ailleurs la casse est préservée. Les éléments lexicaux dans la section de contrôle d'accès sont séparés par des espaces blancs ou les caractères délimiteurs spéciaux : crochets (``['' et ``]''), accolades (``{'' et ``}''), deux-points (``:'' ), point-virgule (``;'' ) et virgule (``,'' ). Les caractères spéciaux ne sont pas traités comme spéciaux dans la section de configuration de l'agent. Les éléments lexicaux peuvent être mis entre guillemets (guillemets doubles) si nécessaire.

La section de contrôle d'accès du fichier doit commencer par une ligne de la forme :

[accès]

En plus de (ou à la place de) la section d'accès dans le fichier de configuration pmcd, les spécifications de contrôle d'accès sont également lues à partir d'un fichier portant le même nom que le fichier de configuration pmcd, mais avec '.access' ajouté au nom. Ce fichier facultatif ne doit pas contenir le mot-clé [accès].

Les espaces blancs au début et à la fin peuvent apparaître autour et à l'intérieur des crochets, et la casse du mot-clé accès est ignorée. Aucun autre texte ne peut apparaître sur la ligne sauf un commentaire final.

Après cette ligne, le reste du fichier de configuration doit contenir des lignes qui autorisent ou refusent les opérations à partir d'hôtes ou de groupes d'hôtes particuliers.

Il existe deux types d'opérations qui se produisent via pmcd :

fetch
permet la récupération d'informations depuis pmcd. Il peut s'agir d'informations sur une métrique (par exemple, sa description, son domaine d'instance, ses étiquettes ou son texte d'aide) ou d'une valeur pour une métrique. Voir pminfo(1) pour plus d'informations.
store
permet à pmcd d'être utilisé pour stocker des valeurs de métriques dans des agents qui autorisent les opérations de stockage. Il peut s'agir de la valeur réelle de la métrique (par exemple, réinitialiser un compteur à zéro). Alternativement, il peut s'agir d'une valeur utilisée par le PMDA pour introduire un changement dans certains aspects de la surveillance de cette métrique (par exemple, le filtrage des événements côté serveur) - éventuellement même uniquement pour l'outil client actif effectuant l'opération de stockage, et pas pour les autres. Voir pmstore(1) pour plus d'informations.

L'accès à pmcd peut être accordé de trois manières : par utilisateur, par groupe d'utilisateurs ou au niveau de l'hôte. Dans ce dernier cas, tous les utilisateurs d'un hôte reçoivent le même niveau d'accès, à moins que le mécanisme de contrôle d'accès par utilisateur ou par groupe ne soit également utilisé.

Les noms d'utilisateur et de groupe seront vérifiés en utilisant les fichiers locaux /etc/passwd et /etc/groups (ou un service d'annuaire alternatif), en utilisant les routines getpwent(3) et getgrent(3).

Les hôtes peuvent être identifiés par leur nom, leur adresse IP, leur adresse IPv6 ou par les spécifications d'hôtes spéciales « unix: » ou « local: ». « unix: » fait référence au socket de domaine Unix de pmcd, sur les plateformes prises en charge. « local: » est équivalent à spécifier « unix: » et « localhost ».

Des caractères génériques peuvent également être spécifiés en terminant l'identifiant de l'hôte par le caractère générique unique « * » en tant que dernier composant de l'adresse. Le caractère générique « .* » fait référence à toutes les adresses inet (IPv4). Le caractère générique « :* » fait référence à toutes les adresses IPv6. Si un caractère générique IPv6 contient un composant « :: », alors le « * » final fait référence uniquement aux 16 derniers bits de l'adresse, sinon il fait référence aux bits non spécifiés restants de l'adresse.

Le caractère générique « * » fait référence à tous les utilisateurs, groupes ou adresses d'hôtes, y compris « unix: ». Les noms d'utilisateurs, de groupes ou d'hôtes ne peuvent pas contenir de caractères génériques.

Les identifiants d'hôtes suivants sont tous valides :


boing
localhost
giggle.melbourne.sgi.com
129.127.112.2
129.127.114.*
129.*
.*
fe80::223:14ff:feaf:b62c
fe80::223:14ff:feaf:*
fe80:*
:*
"unix:"
"local:"
*

Les identifiants d'hôtes suivants ne sont pas valides :


*.melbourne
129.127.*.*
129.127.*.9
129.127*
fe80::223:14ff:*:*
fe80::223:14ff:*:b62c
fe80*

Le premier exemple n'est pas autorisé car seules les adresses IP (numériques) peuvent contenir un caractère générique. Le deuxième et le cinquième exemples ne sont pas valides car il y a plus d'un caractère générique. Le troisième et le sixième contiennent un caractère générique intégré, le quatrième et le septième ont un caractère générique qui n'est pas le dernier composant de l'adresse (les derniers composants sont 127* et fe80* respectivement).

Le nom localhost bénéficie d'un traitement spécial pour rendre le comportement des caractères génériques d'hôtes cohérent. Au lieu d'être 127.0.0.1 et ::1, il est mappé aux adresses inet et IPv6 primaires associées au nom de l'hôte sur lequel pmcd s'exécute. Attention à cela lorsque vous exécutez pmcd sur des hôtes multi-homed.

Les autorisations pour les utilisateurs, groupes ou hôtes sont accordées ou refusées en spécifiant des instructions de la forme :

allow users liste_utilisateurs : opérations ;
disallow users liste_utilisateurs : opérations ;
allow groups liste_groupes : opérations ;
disallow groups liste_groupes : opérations ;
allow hosts liste_hôtes : opérations ;
disallow hosts liste_hôtes : opérations ;
liste
liste_utilisateurs, liste_groupes et liste_hôtes sont des listes séparées par des virgules d'un ou plusieurs utilisateurs, groupes ou identifiants d'hôtes.
opérations
est une liste séparée par des virgules des types d'opérations décrits ci-dessus, all (qui autorise/refuse toutes les opérations), ou all except opérations (qui autorise/refuse toutes les opérations sauf celles listées).

Les formes plurielles ou singulières des mots-clés users, groups et hosts sont autorisées. Si ce mot-clé est omis, la valeur par défaut sera hosts. Ce comportement est uniquement destiné à la compatibilité descendante ; il est préférable d'être explicite.

Lorsqu'aucune instruction allow ou disallow spécifique ne s'applique à une opération, la valeur par défaut est d'autoriser l'opération de tous les utilisateurs, groupes et hôtes. Dans le cas trivial où il n'y a pas de section de contrôle d'accès dans le fichier de configuration, toutes les opérations de tous les utilisateurs, groupes et hôtes sont autorisées.

Si une nouvelle connexion à pmcd est tentée par un utilisateur, un groupe ou un hôte qui n'est pas autorisé à effectuer des opérations, la connexion sera fermée immédiatement après l'envoi d'une réponse d'erreur PM_ERR_PERMISSION au client tentant la connexion.

Les instructions avec le même niveau de caractère générique spécifiant des hôtes identiques ne peuvent pas se contredire. Par exemple, si un hôte nommé clank avait une adresse IP de 129.127.112.2, spécifier les deux règles suivantes serait erroné :


allow host clank : fetch, store;
disallow host 129.127.112.2 : all except fetch;

car elles font toutes deux référence au même hôte, mais divergent quant à savoir si l'opération fetch est autorisée depuis cet hôte.

Les instructions contenant des spécifications d'hôtes plus spécifiques remplacent celles moins spécifiques selon le niveau de caractère générique. Par exemple, une règle de la forme


allow host clank : all;

remplace


disallow host 129.127.112.* : all except fetch;

car la première contient un nom d'hôte spécifique (équivalent à une adresse IP complètement spécifiée), tandis que la seconde a un caractère générique. À son tour, cette dernière remplacerait


disallow host * : all;

Il est possible de limiter le nombre de connexions provenant d'un utilisateur, d'un groupe ou d'un hôte à pmcd. Cela peut être fait en ajoutant une clause de la forme

maximum n connections

à la liste opérations d'une instruction allow. Une telle clause ne peut pas être utilisée dans une instruction disallow. Ici, n est le nombre maximum de connexions qui seront acceptées de l'utilisateur, du groupe ou de l'hôte correspondant aux identifiants utilisés dans l'instruction.

Une instruction de contrôle d'accès avec une liste d'identifiants d'utilisateurs, de groupes ou d'hôtes est équivalente à un ensemble d'instructions de contrôle d'accès, chacune spécifiant un des identifiants de la liste et toutes avec les mêmes contrôles d'accès (permissions et limites de connexion). Un groupe doit être utilisé si vous voulez que les utilisateurs contribuent à une limite de connexion partagée. Un caractère générique doit être utilisé si vous voulez que les hôtes contribuent à une limite de connexion partagée.

Lorsqu'un nouveau client demande une connexion, et que pmcd a déterminé que le client est autorisé à se connecter, il recherche dans la liste correspondante des instructions de contrôle d'accès la correspondance la plus spécifique contenant une limite de connexion. Par souci de concision, cela sera appelé l'instruction limitative. S'il n'y a pas d'instruction limitative, la connexion du client est accordée. S'il existe une instruction limitative et que le nombre de clients pmcd dont l'ID utilisateur, l'ID groupe ou les adresses IP correspondent à l'identifiant de l'instruction limitative est inférieur à la limite de connexion de l'instruction, la connexion est autorisée. Sinon, la limite de connexion a été atteinte et le client se voit refuser la connexion.

Les contrôles d'accès par groupe et les caractères génériques dans les identifiants d'hôtes impliquent qu'une fois que pmcd accepte réellement une connexion d'un client, la connexion peut contribuer au compte de connexion actuel de plus d'une instruction de contrôle d'accès - l'hôte du client peut correspondre à plus d'une instruction de contrôle d'accès, et de même l'ID utilisateur peut être dans plus d'un gr

oup. Cela peut être important pour les futures demandes de connexion.

Notez que pmcd entre dans un mode où il fonctionne efficacement avec un niveau de sécurité plus élevé dès qu'une section de contrôle d'accès utilisateur ou groupe est ajoutée à la configuration. Dans ce mode, seules les connexions authentifiées sont autorisées - soit à partir d'une connexion authentifiée SASL, soit d'un socket de domaine Unix (qui transmet implicitement les informations d'identification du client). C'est le même mode qui est entré explicitement en utilisant l'option -S. En supposant que la permission est accordée, on peut déterminer si pmcd fonctionne dans ce mode en interrogeant la valeur de la métrique pmcd.feature.creds_required.

Notez également que, comme la plupart des sémantiques de correspondance spécifiques sont utilisées lors de la vérification de la limite de connexion, pour le cas du contrôle d'accès basé sur l'hôte, la priorité est donnée aux clients avec des identifiants d'hôte plus spécifiques. Il est également possible de dépasser les limites de connexion dans certaines situations. Considérez ce qui suit :

allow host clank : all, maximum 5 connections;
allow host * : all except store, maximum 2 connections;

Cela signifie que seulement 2 connexions client à la fois sont autorisées pour tous les hôtes autres que "clank", pour lequel 5 sont autorisés. Si un client de l'hôte "boing" est le premier à se connecter à pmcd, sa connexion est vérifiée par rapport à la seconde instruction (qui est la correspondance la plus spécifique avec une limite de connexion). Comme il n'y a pas d'autres clients, la connexion est acceptée et contribue à la limite pour uniquement la seconde instruction ci-dessus. Si le client suivant se connecte depuis "clank", sa connexion est vérifiée par rapport à la limite de la première instruction. Il n'y a pas d'autres connexions depuis "clank", donc la connexion est acceptée. Une fois cette connexion acceptée, elle compte pour les limites des DEUX instructions car "clank" correspond à l'identifiant d'hôte dans les deux instructions. Rappelez-vous que la décision d'accepter une nouvelle connexion est prise en utilisant uniquement l'instruction de contrôle d'accès la plus spécifique avec une limite de connexion. Maintenant, la limite de connexion pour la seconde instruction a été atteinte. Toutes les connexions provenant d'hôtes autres que "clank" seront refusées.

Si, au lieu de cela, pmcd sans clients voyait arriver trois connexions successives depuis "boing", les deux premières seraient acceptées et la troisième refusée. Après cela, si une connexion était demandée depuis "clank", elle serait acceptée. Elle correspond à la première instruction, qui est plus spécifique que la seconde, donc la limite de connexion dans la première est utilisée pour déterminer que le client a le droit de se connecter. Maintenant, 3 connexions contribuent à la limite de connexion de la seconde instruction. Même si la limite de connexion pour la seconde instruction a été dépassée, les connexions précédentes depuis "boing" sont maintenues. La limite de connexion n'est vérifiée qu'au moment où un client tente une connexion plutôt qu'elle n'est réévaluée chaque fois qu'un nouveau client se connecte à pmcd.

Ce système souple est conçu pour permettre d'imposer des limites raisonnables sur la base du premier arrivé, premier servi, avec des exceptions spécifiques.

Comme illustré par l'exemple ci-dessus, la connexion d'un client est honorée une fois qu'elle a été acceptée. Cependant, la reconfiguration de pmcd (voir la section suivante) réévalue tous les décomptes de connexions et entraînera la déconnexion des clients dont les limites de connexion ont été dépassées.

FENCING DES AGENTS

Empêcher l'échantillonnage pendant la vie d'un PMDA est parfois souhaitable, par exemple si cet échantillonnage a un impact sur des phases sensibles d'un travail planifié. Une « clôture » temporaire peut être levée pour bloquer tout accès client PMAPI à un ou plusieurs agents dans cette situation. Cette fonctionnalité est fournie par le PMDA PMCD intégré et la commande pmstore(1), comme suit :


# pmstore -i nfsclient,kvm pmcd.agent.fenced 1

Si la liste facultative d'agents séparés par des virgules est omise, tous les agents seront clôturés. Pour reprendre le fonctionnement normal, la « clôture » peut être levée comme suit :


# pmstore -i nfsclient,kvm pmcd.agent.fenced 0

La levée de la clôture pour tous les PMDA à la fois est effectuée en utilisant :


# pmstore pmcd.agent.fenced 0

Des privilèges élevés sont requis pour écrire dans la métrique pmcd.agent.fenced. Pour plus d'informations, consultez le texte d'aide associé à cette métrique, accessible via l'option -T, --helptext de pminfo(1).

RECONFIGURER PMCD

Si le fichier de configuration a été modifié ou si un agent ne répond pas parce qu'il s'est terminé ou que le PMNS a été modifié, pmcd peut être reconfiguré en lui envoyant un SIGHUP, comme suit :


# pmsignal -a -s HUP pmcd

Lorsque pmcd reçoit un SIGHUP, il vérifie les modifications dans le fichier de configuration. Si le fichier a été modifié, il est re-analysé et son contenu devient la nouvelle configuration. S'il y a des erreurs dans le fichier de configuration, la configuration existante est conservée et le contenu du fichier est ignoré. Les erreurs sont signalées dans le fichier journal de pmcd.

Il vérifie également le fichier PMNS et les fichiers d'étiquettes pour des modifications. Si l'un de ces fichiers a été modifié, le PMNS et/ou les étiquettes de contexte sont rechargés. L'utilisation de tail(1) sur le fichier journal est recommandée lors de la reconfiguration de pmcd.

Si la configuration d'un agent a changé (tout paramètre sauf l'étiquette de l'agent est différent), l'agent est redémarré. Les agents dont les configurations n'ont pas changé ne sont pas redémarrés. Tous les agents existants qui ne sont pas présents dans la nouvelle configuration sont terminés. Tous les agents décédés qui sont toujours répertoriés sont redémarrés.

Parfois, il est nécessaire de redémarrer un agent qui est toujours en cours d'exécution, mais qui fonctionne mal. Arrêtez simplement l'agent (par exemple en utilisant SIGTERM de pmsignal(1)), puis envoyez un SIGHUP à pmcd, ce qui entraînera le redémarrage de l'agent.

DÉMARRER ET ARRÊTER PMCD

Normalement, pmcd est démarré automatiquement au démarrage du système et arrêté lorsque le système est arrêté. Dans certaines circonstances, il est nécessaire de démarrer ou d'arrêter pmcd manuellement. Pour ce faire, il faut devenir superutilisateur et taper :


# $PCP_RC_DIR/pmcd start

pour démarrer pmcd, ou :


# $PCP_RC_DIR/pmcd stop

pour arrêter pmcd. Démarrer pmcd lorsqu'il est déjà en cours d'exécution équivaut à l'arrêter puis à le redémarrer.

Parfois, il peut être nécessaire de redémarrer pmcd pendant une autre phase du processus de démarrage. Les parties chronophages du processus de démarrage sont souvent mises en arrière-plan pour permettre au système de devenir disponible plus rapidement (par exemple, le montage de bases de données volumineuses). Si un agent géré par pmcd nécessite qu'une telle tâche soit terminée avant de pouvoir s'exécuter correctement, il est nécessaire de redémarrer ou de reconfigurer pmcd après la fin de la tâche. Prenons, par exemple, le cas du montage d'une base de données en arrière-plan lors du démarrage. Si le PMDA qui fournit les métriques sur la base de données ne peut pas fonctionner tant que la base de données n'est pas montée et disponible, mais que pmcd est démarré avant que la base de données ne soit prête, le PMDA échouera (cependant pmcd continuera de répondre aux requêtes de métriques provenant d'autres domaines). Si la base de données est initialisée en exécutant un script shell, l'ajout d'une ligne à la fin du script pour reconfigurer pmcd (en lui envoyant un SIGHUP) redémarrera le PMDA (s'il s'est terminé parce qu'il ne pouvait pas se connecter à la base de données). Si le PMDA ne s'est pas terminé dans une telle situation, il serait nécessaire de redémarrer pmcd car si le PMDA était toujours en cours d'exécution, pmcd ne le redémarrerait pas.

Normalement, pmcd écoute les connexions client sur le port TCP/IP numéro 44321 (enregistré à http://www.iana.org/). Les variables d'environnement PMCD_PORT ou l'option de ligne de commande -p peuvent être utilisées pour spécifier des numéros de port alternatifs lorsque pmcd est démarré ; dans chaque cas, la spécification est une liste séparée par des virgules d'un ou plusieurs numéros de port numériques. Si les deux méthodes sont utilisées ou si plusieurs options -p apparaissent sur la ligne de commande, pmcd écoutera sur l'union de l'ensemble des ports spécifiés via toutes les options -p et la variable d'environnement PMCD_PORT. Si des ports non par défaut sont utilisés avec pmcd, il faut veiller à ce que PMCD_PORT soit également défini dans l'environnement de toute application cliente qui se connectera à pmcd, ou que la syntaxe étendue de spécification d'hôte soit utilisée (voir PCPIntro(1) pour plus de détails).

LIMITATIONS

pmcd ne termine pas explicitement ses enfants (agents), il ferme seulement leurs pipes. Si un agent ne vérifie jamais un pipe fermé, il peut ne pas se terminer.

L'analyseur de fichier de configuration ne lit que les lignes de moins de 1200 caractères. Ceci est destiné à prévenir les accidents avec les fichiers binaires.

Les timeouts contrôlés par l'option -t s'appliquent à la communication IPC entre pmcd et les PMDA qu'il lance. Ceci est indépendant des paramètres des variables d'environnement PMCD_CONNECT_TIMEOUT et PMCD_REQUEST_TIMEOUT (voir PCPIntro(1)) qui peuvent être utilisés respectivement pour contrôler les timeouts des applications clientes tentant de se connecter à pmcd et tentant de recevoir des informations de pmcd.

DIAGNOSTICS

Si pmcd est déjà en cours d'exécution, le message "Error: OpenRequestSocket bind: Address may already be in use" apparaîtra. Cela peut également apparaître si pmcd a été arrêté avec une requête en attente d'un client. Dans ce cas, un socket de requête a été laissé en état TIME_WAIT et jusqu'à ce que le système le ferme (après une période de timeout), il ne sera pas possible d'exécuter pmcd.

En plus des indicateurs de débogage standard de PCP, voir pmdbg(1), pmcd utilise actuellement les options : appl0 pour le traçage des E/S et la terminaison des agents, appl1 pour le traçage du contrôle d'accès et appl2 pour le traçage du scanner et de l'analyseur de fichier de configuration.

pmcd(1) — Performance Co-Pilot

NAME

pmcd — Performance Metrics Collection Daemon

SYNOPSIS

pmcd [-c config] [-d debug] [-D debug] [-h] [-i] [-l logfile] [-p port] [-s socket] [-v]

DESCRIPTION

pmcd is the Performance Metrics Collection Daemon for Performance Co-Pilot (PCP). It acts as a central server, accepting connections from PCP clients (like pminfo(1), pmrep(1), pmstat(1), pmval(1), and the various PMDA performance metrics collection daemons).

It uses a hierarchical Performance Metrics Name Space (PMNS) to locate and describe the available metrics, and it uses the PMDA infrastructure to fetch performance metric values from the underlying system.

pmcd listens for incoming TCP/IP connections on a port defined by the PMCD_PORT environment variable (default 44321) or the -p option, and also listens for incoming Unix domain socket connections on a path defined by the PMCD_SOCKET environment variable or the -s option.

The default configuration file is pmcd.conf(5), but this may be overridden using the -c option.

The default debug log file is $PCP_LOG_DIR/pmcd/pmcd.log, but this may be overridden using the -l option.

OPTIONS

-c config
Use configuration file config instead of the default pmcd.conf(5).
-d debug
Enable debug level diagnostics. The level may be specified as an integer from 0 (no diagnostics) to 6 (maximum verbosity). Higher values may be enabled when using the -D option.
-D debug
Enable debug level diagnostics. This option may be used multiple times, or with a comma separated list of keywords, to enable specific debugging flags. See the DEBUGGING OPTIONS section below for details.
-h
Print a usage message and exit.
-i
Ignore the user and group specifications in the configuration file, and instead allow all clients to connect and access all metrics.
-l logfile
Use logfile instead of the default $PCP_LOG_DIR/pmcd/pmcd.log for logging messages.
-p port
Use TCP/IP port port instead of the default.
-s socket
Use Unix domain socket socket instead of the default.
-v
Print version information and exit.

CONFIGURATION

The behavior of pmcd is controlled by configuration files and environment variables.

$PCP_PMCD_CONF/pmcd.conf

This is the primary configuration file for pmcd. It contains directives that control how pmcd operates, including access control rules, agent invocation and network service configuration. See pmcd.conf(5) for a full description.

$PCP_RC_DIR/pmcd.options

This file may be used to specify command-line options to be passed to pmcd when it is launched from pmcd(1).

$PCP_SYSCONFIG_DIR/pmcd

Environment variables that will be set when pmcd executes. Only settings of the form "PMCD_VARIABLE=value" or "PCP_VARIABLE=value" are honoured.

$PCP_SYSCONF_DIR/labels.conf

Settings related to labels used globally throughout the PMCS.

$PCP_SYSCONF_DIR/labels

Directory of files containing the global metric labels that will be set for every client context created by pmcd. File names starting with a ``.'' are ignored, and files ending in ``.json'' are ``JSONB'' formatted name:value pairs. The merged set can be queried via the pmcd.labels metric. Context labels are applied universally to all metrics.

$PCP_SYSCONF_DIR/labels/optional

Directory of files containing the global metric labels that will be set for every client context created by pmcd, but which are flagged as optional. These labels are exactly the same as other context labels except that they are not used in time series identifier calculations.

./pmcd.log

(or $PCP_LOG_DIR/pmcd/pmcd.log when started automatically) All messages and diagnostics are directed here.

$PCP_RUN_DIR/pmcd.pid

Contains an ascii decimal representation of the process ID of pmcd, when it's running.

/etc/pcp/tls.conf

OpenSSL certificate configuration information file, used for optional Secure Socket Layer connections.

/etc/passwd

User names, user identifiers and primary group identifiers, used for access control specifications

/etc/groups

Group names, group identifiers and group members, used for access control specifications

ENVIRONMENT

The following variables are set in $PCP_SYSCONFIG_DIR/pmcd.

In addition to the PCP environment variables described in the PCP ENVIRONMENT section below, the PMCD_PORT variable is also recognised as the TCP/IP port for incoming connections (default 44321), and the PMCD_SOCKET variable is also recognised as the path to be used for the Unix domain socket.

If set to the value 1, the PMCD_LOCAL environment variable will cause pmcd to run in a localhost-only mode of operation, where it binds only to the loopback interface. The pmcd.feature.local metric can be queried to determine if pmcd is running in this mode.

The PMCD_MAXPENDING variable can be set to indicate the maximum length to which the queue of pending client connections may grow.

The PMCD_ROOT_AGENT variable controls whether or not pmcd or pmdaroot (when available), start subsequent PMDAs. When set to a non-zero value, pmcd will opt to have pmdaroot start, and stop, PMDAs.

The PMCD_RESTART_AGENTS variable determines the behaviour of pmcd in the presence of child PMDAs that have been observed to exit (this is a typical response in the presence of very large, usually domain-induced, PDU latencies). When set to a non-zero value, pmcd will attempt to restart such PMDAs once every minute. When set to zero, it uses the original behaviour of just logging the failure.

PCP ENVIRONMENT

Environment variables with the prefix PCP_ are used to parameterize the file and directory names used by PCP. On each installation, the file /etc/pcp.conf contains the local values for these variables. The $PCP_CONF variable may be used to specify an alternative configuration file, as described in pcp.conf(5).

For environment variables affecting PCP tools, see pmGetOptions(3).

appl4 timestamps for config file parsing

If set to the value 1, the PMCD_LOCAL environment variable will cause pmcd to run in a localhost-only mode of operation, where it binds only to the loopback interface. The pmcd.feature.local metric can be queried to determine if pmcd is running in this mode.

The PMCD_MAXPENDING variable can be set to indicate the maximum length to which the queue of pending client connections may grow.

The PMCD_ROOT_AGENT variable controls whether or not pmcd or pmdaroot (when available), start subsequent PMDAs. When set to a non-zero value, pmcd will opt to have pmdaroot start, and stop, PMDAs.

The PMCD_RESTART_AGENTS variable determines the behaviour of pmcd in the presence of child PMDAs that have been observed to exit (this is a typical response in the presence of very large, usually domain-induced, PDU latencies). When set to a non-zero value, pmcd will attempt to restart such PMDAs once every minute. When set to zero, it uses the original behaviour of just logging the failure.

PCP ENVIRONMENT

Environment variables with the prefix PCP_ are used to parameterize the file and directory names used by PCP. On each installation, the file /etc/pcp.conf contains the local values for these variables. The $PCP_CONF variable may be used to specify an alternative configuration file, as described in pcp.conf(5).

For environment variables affecting PCP tools, see pmGetOptions(3).

DEBUGGING OPTIONS

The -D or --debug option enables the output of additional diagnostics on stderr to help triage problems, although the information is sometimes cryptic and primarily intended to provide guidance for developers rather end-users. debug is a comma separated list of debugging options; use pmdbg(1) with the -l option to obtain a list of the available debugging options and their meaning.

Debugging options specific to pmcd are as follows:

Option Description
appl0 PDU level operations
appl1 access control specifications from the config file
appl2 lexical scanner in config file parser
appl3 client connections and disconnections
appl4 timestamps for config file parsing
appl5 attribute operations
appl6 global and PMDA state changes

FILES

$PCP_PMCD_CONF/pmcd.conf
Configuration file for pmcd. All the command line option lines should start with a hyphen as the first character.
$PCP_RC_DIR/pmcd.options
Command line options to be passed to pmcd when launched from $PCP_RC_DIR/pmcd. All the command line option lines should start with a hyphen as the first character.
$PCP_SYSCONFIG_DIR/pmcd
Environment variables that will be set when pmcd executes. Only settings of the form "PMCD_VARIABLE=value" or "PCP_VARIABLE=value" are honoured.
$PCP_SYSCONF_DIR/labels.conf
settings related to labels used globally throughout the PMCS.
$PCP_SYSCONF_DIR/labels
directory of files containing the global metric labels that will be set for every client context created by pmcd. File names starting with a ``.'' are ignored, and files ending in ``.json'' are ``JSONB'' formatted name:value pairs. The merged set can be queried via the pmcd.labels metric. Context labels are applied universally to all metrics.
$PCP_SYSCONF_DIR/labels/optional
directory of files containing the global metric labels that will be set for every client context created by pmcd, but which are flagged as optional. These labels are exactly the same as other context labels except that they are not used in time series identifier calculations.
./pmcd.log
(or $PCP_LOG_DIR/pmcd/pmcd.log when started automatically)
All messages and diagnostics are directed here.
$PCP_RUN_DIR/pmcd.pid
contains an ascii decimal representation of the process ID of pmcd, when it's running.
/etc/pcp/tls.conf
OpenSSL certificate configuration information file, used for optional Secure Socket Layer connections.
/etc/passwd
user names, user identifiers and primary group identifiers, used for access control specifications
/etc/groups
group names, group identifiers and group members, used for access control specifications
