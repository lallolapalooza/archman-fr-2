PMLOGREWRITE(1) Manuel des commandes générales PMLOGREWRITE(1)

NOM

pmlogrewrite - réécrire les archives Performance Co-Pilot

SYNTAXE

pmlogrewrite [-Cdiqsvw?] [-c config] [-D debug] [-V version] inlog [outlog]

DESCRIPTION

pmlogrewrite lit un ensemble d'archives Performance Co-Pilot (PCP) identifiées par inlog et crée une archive PCP dans outlog. Dans une utilisation normale, l'option -c sera utilisée pour nommer un ou plusieurs fichiers de configuration contenant des spécifications (voir la section SYNTAXE DES RÈGLES DE RÉÉCRITURE ci-dessous) décrivant comment les données et métadonnées de inlog doivent être transformées pour produire outlog.

Les utilisations typiques de pmlogrewrite seraient pour s'adapter à l'évolution des Agents de domaine de métriques de performance (PMDA) où les noms, métadonnées et sémantiques des métriques et de leurs domaines d'instance associés peuvent changer avec le temps, par exemple, promouvoir le type d'une métrique d'un entier 32 bits à un entier 64 bits, ou renommer un groupe de métriques. Référez-vous à la section EXEMPLES pour des cas d'utilisation supplémentaires.

pmlogrewrite peut également être utilisé pour supprimer des informations sensibles des archives PCP dans les situations où les archives doivent être expédiées à une autre organisation ou pour se conformer à des politiques de confidentialité ou des exigences législatives. Voir pmlogredact(1) pour un exemple d'utilisation de pmlogrewrite dans ce contexte.

pmlogrewrite est plus utile lorsque les changements de PMDA, ou les erreurs dans l'environnement de production, entraînent des archives qui ne peuvent pas être combinées avec pmlogextract(1). En pré-traitant les archives avec pmlogrewrite, les archives résultantes pourraient pouvoir être fusionnées avec pmlogextract(1).

L'entrée inlog doit être un ensemble d'archives PCP créées par pmlogger(1), ou potentiellement l'un des outils qui lisent et créent des archives PCP, par exemple pmlogextract(1) et pmlogreduce(1). inlog est une liste de noms séparés par des virgules, chacun pouvant être le nom de base d'une archive ou le nom d'un répertoire contenant une ou plusieurs archives.

Si aucune option -c n'est spécifiée, le comportement par défaut crée simplement outlog comme une copie de inlog. Ceci est un peu plus compliqué que cat(1), car chaque archive PCP est composée de plusieurs fichiers physiques.

Bien que pmlogrewrite puisse être utilisé pour réparer certains problèmes de cohérence des données dans les archives PCP, il existe également une classe de tâches de réparation qui ne peuvent pas être gérées par pmlogrewrite et pmloglabel(1) peut être un outil utile dans ces cas.

OPTIONS

Les options de ligne de commande disponibles sont :

-c config, --config=config
Si config est un fichier ou un lien symbolique, lire et analyser les règles de réécriture à partir de là. Si config est un répertoire, alors tous les fichiers ou liens symboliques dans ce répertoire (à l'exception de ceux commençant par un point ``.'') seront utilisés pour fournir les règles de réécriture. Plusieurs options -c sont autorisées.
-C, --check
Analyser les règles de réécriture et quitter. outlog n'est pas créé, donc cet argument de ligne de commande est facultatif avec -C. Lorsque -C est spécifié, cela active également -v et -w afin que tous les avertissements et messages détaillés soient affichés lors de l'analyse de config.
-d, --desperate
Mode désespéré. Normalement, si une erreur fatale se produit, toute trace de l'archive PCP partiellement écrite outlog est supprimée. Avec l'option -d, l'archive outlog partiellement créée n'est pas supprimée.
-i
Plutôt que de créer outlog, inlog est réécrit sur place lorsque l'option -i est utilisée. Une nouvelle archive est créée en utilisant des noms de fichiers temporaires, puis renommée en inlog de telle sorte que si des erreurs (pas des avertissements) sont rencontrées, inlog reste inchangé.
-q, --quick
Mode rapide, où s'il n'y a aucune action de réécriture à effectuer (aucune des données globales, domaines d'instances ou métriques de inlog ne sera modifiée), alors pmlogrewrite se terminera (avec le statut 0, donc succès) immédiatement après l'analyse du ou des fichiers de configuration et outlog ne sera pas créé.
-s, --scale
Lorsque les « unités » d'une métrique sont modifiées, si la dimension en termes d'espace, de temps et de compte est inchangée, alors le facteur d'échelle est modifié, par exemple de BYTE à KBYTE, ou MSEC-1 à USEC-1, ou le composite MBYTE.SEC-1 à KBYTE.USEC-1. La motivation peut être (a) que les métadonnées originales étaient incorrectes mais que les valeurs dans inlog sont correctes, ou (b) les métadonnées changent donc les valeurs doivent également changer. Le comportement par défaut de pmlogrewrite correspond au cas (a). Si le cas (b) s'applique, alors utilisez l'option -s et les valeurs de toutes les métriques dont le facteur d'échelle change dans chaque résultat seront re-calées. Pour un contrôle plus fin du re-calage des valeurs, référez-vous à l'option RESCALE pour la clause UNITS de la règle de réécriture de métrique décrite ci-dessous.
-v, --verbose
Activer le mode détaillé.
-V version, --version=version
Spécifie la version de l'archive PCP de sortie produite. Actuellement, les versions 2 et 3 du format d'archive sont prises en charge. La version de inlog doit être au moins version (donc une mise à niveau de version est autorisée, mais une rétrogradation de version ne l'est pas). Par défaut, en l'absence de l'option -V, la version de outlog est la même que la version de inlog.
-w, --warnings
Émettre des avertissements. Normalement, pmlogrewrite reste silencieux pour tout avertissement qui n'est pas fatal et on s'attend à ce que pour une archive donnée, certaines (ou même toutes) des spécifications de réécriture peuvent ne pas s'appliquer. Par exemple, les changements apportés à un PMDA peuvent être capturés dans un ensemble de règles de réécriture, mais une seule archive peut ne pas contenir toutes les métriques modifiées ni tous les domaines d'instances et/ou instances modifiés. Étant donné que ces cas sont attendus, ils n'empêchent pas l'exécution de pmlogrewrite, et les règles qui ne s'appliquent pas à inlog sont ignorées silencieusement par défaut. De même, certaines règles de réécriture peuvent n'entraîner aucun changement car les métadonnées dans inlog correspondent déjà à l'intention de la règle de réécriture pour corriger les données d'une version précédente d'un PMDA. Le drapeau -w force l'émission d'avertissements pour tous ces cas.
-?, --help
Afficher le message d'utilisation et quitter.

L'argument outlog est requis dans tous les cas, sauf lorsque -i est spécifié.

SYNTAXE DES RÈGLES DE RÉÉCRITURE

Un fichier de configuration contient zéro ou plusieurs règles de réécriture telles que définies ci-dessous.

Les mots-clés et les caractères de ponctuation spéciaux sont indiqués ci-dessous en police gras-italique et ne sont pas sensibles à la casse, donc METRIC, metric et Metric sont tous équivalents dans les règles de réécriture.

Le caractère « # » introduit un commentaire et le reste de la ligne est ignoré. Sinon, l'entrée est relativement libre avec des espaces blancs optionnels (espaces, tabulations ou nouvelles lignes) entre les éléments lexicaux des règles.

Une règle de réécriture globale a la forme :

GLOBAL { globalspec ... }

où globalspec est zéro ou plusieurs des clauses suivantes :

HOSTNAME -> hostname

Modifie les enregistrements d'étiquette dans l'archive PCP outlog, de sorte que les métriques apparaissent avoir été collectées depuis l'hôte hostname.

TIME -> delta

Les valeurs des métriques et les métadonnées du domaine d'instance dans une archive PCP portent des horodatages. Cette clause force tous les horodatages à être ajustés par delta, où delta est un signe optionnel « + » (th

e par défaut) ou `-'`, un nombre optionnel d'heures suivi de deux-points `:`, un nombre optionnel de minutes suivi de deux-points `:`, un nombre de secondes, une fraction optionnelle de secondes suivant un point `.`. L'exemple le plus simple serait `30` pour augmenter les estampilles temporelles de 30 secondes. Un exemple plus complexe serait `-23:59:59.999` pour déplacer les estampilles temporelles en arrière d'une milliseconde de moins qu'une journée.

TIMEZONE -> "timezone"
TZ -> "timezone"

Modifie les enregistrements d'étiquettes dans l'archive PCP outlog, de sorte que les métriques apparaîtront comme ayant été collectées à partir d'un hôte dont le fuseau horaire local est timezone. timezone doit être entouré de guillemets doubles, et doit être conforme aux règles de syntaxe valides pour les fuseaux horaires de la plateforme locale, généralement un format Posix TZ, par exemple AEST-10. Voir tzset(3) pour plus d'informations.

TZ est un alias pour TIMEZONE.

ZONEINFO -> "zoneinfo"

Modifie les enregistrements d'étiquettes dans l'archive PCP outlog, de sorte que les métriques apparaîtront comme ayant été collectées à partir d'un hôte dont le fuseau horaire local est zoneinfo. zoneinfo doit être entouré de guillemets doubles, et doit être conforme aux règles de syntaxe valides pour les fuseaux horaires zoneinfo de la plateforme locale, généralement deux-points suivis d'un chemin sous /usr/share/zoneinfo, par exemple :Africa/Timbuktu. Voir tzset(3) pour plus d'informations.

La clause zoneinfo n'est autorisée que si la version de l'archive de sortie est au moins 3.

FEATURES -> feature-bits

Modifie les enregistrements d'étiquettes dans l'archive PCP outlog, de sorte que les métriques apparaîtront comme ayant été collectées à partir d'un système avec un pmlogger(1) qui prend en charge les ``fonctionnalités'' définies par la valeur entière feature-bits, qui est formée en combinant par « OU » les drapeaux de fonctionnalités souhaités tels que définis dans LOGARCHIVE(5). Alternativement, feature-bits peut être spécifié en utilisant la ``macro'' BITS() qui prend une liste d'arguments séparés par des virgules d'entiers (dans la plage inclusive de 0 à 31) et définit les bits correspondants. Par exemple

features -> bits(31,7,1)

La clause features n'est autorisée que si la version de l'archive de sortie est au moins 3.

Une règle de réécriture indom modifie un domaine d'instances et a la forme :

INDOM domain.serial { indomspec ... }

où domain et serial identifient un ou plusieurs domaines d'instances existants de inlog - typiquement domain serait un entier dans la plage de 1 à 510 et serial serait un entier dans la plage de 0 à 4194304.

À titre de cas spécial, serial pourrait être un astérisque ``*'' ce qui signifie que la règle s'applique à chaque domaine d'instances ayant un numéro de domaine de domain.

Si un domaine d'instances désigné n'est pas dans inlog, la règle n'a aucun effet.

L'indomspec est zéro ou plus des clauses suivantes :

INAME "oldname" -> "newname"

L'instance identifiée par le nom d'instance externe oldname est renommée en newname. Les deux oldname et newname doivent être entourés de guillemets doubles.

À titre de cas spécial, le nouveau nom peut être le mot-clé DELETE (sans guillemets doubles), et alors l'instance oldname sera effacée de outlog, ce qui la retire des métadonnées du domaine d'instances et supprime toutes les valeurs de cette instance pour toutes les métriques associées.

Si les noms d'instances contiennent des espaces intégrés, des précautions particulières doivent être prises concernant la règle de nommage d'instance PCP qui traite la partie initiale non-espace du nom d'instance comme la portion unique du nom aux fins de la correspondance et de l'assurance de l'unicité au sein d'un domaine d'instances. Se référer à pmdaInstance(3) pour une discussion de ce problème.

À titre d'illustration, considérons le domaine d'instances hypothétique pour une métrique qui contient 2 instances avec les noms suivants :

red
eek urk

Alors certaines clauses INAME possibles pourraient être :

"eek" -> "yellow like a flower"
Acceptable, oldname "eek" correspond à l'instance "eek urk".
"red" -> "eek"
Erreur, newname "eek" correspond à l'instance existante "eek urk".
"eek urk" -> "red of another hue"
Erreur, newname "red of another hue" correspond à l'instance existante "red".

INAME REPLACE /pattern/ -> "replacement"

Chaque nom d'instance externe dans le domaine d'instances est mis en correspondance avec l'expression régulière pattern et lorsqu'une correspondance est trouvée, le nom est modifié en fonction des parties du nom correspondant à pattern et de la recette de replacement. pattern suit la syntaxe d'une expression régulière étendue Posix (voir regex(7)) et replacement suit la syntaxe de la commande s de sed(1), donc & et \1 à \9 peuvent être utilisés pour sélectionner tout ou sous-chaînes du nom d'instance qui correspondent à pattern.

Notez que la correspondance et le remplacement sont effectués au maximum une fois par nom d'instance externe, donc s'il y a des séquences répétées du nom qui correspondent à pattern, seule la **première** sera mise en correspondance et replacement appliquée.

pattern est normalement entouré de barres obliques (/) ou de guillemets doubles ("). Une échappement (\) peut être utilisé avant n'importe quel métacaractère décrit dans regex(3) pour spécifier un caractère littéral, par exemple \( ou \[ ou \+ ... Les délimiteurs environnants ne peuvent pas être échappés, donc pour intégrer une barre oblique littérale, utilisez des guillemets doubles comme délimiteur, ou vice versa.

replacement est normalement entouré de guillemets doubles (") ou de barres obliques (/). Une échappement (\) peut être utilisé avant & ou \ pour spécifier ces caractères littéralement. Les délimiteurs environnants ne peuvent pas être échappés, donc pour intégrer un guillemet double, utilisez des barres obliques comme délimiteur, ou vice versa.

Si les noms d'instances après remplacement contiennent des espaces intégrés, des précautions particulières doivent être prises concernant la règle de nommage d'instance PCP qui traite la partie initiale non-espace du nom d'instance comme la portion unique du nom aux fins de la correspondance et de l'assurance de l'unicité au sein d'un domaine d'instances. Se référer à pmdaInstance(3) pour une discussion de ce problème.

Voici quelques exemples :

{ iname replace /[a-z]*foo[a-z]*/ -> "FOO" }
remplace tout mot contenant "foo" par "FOO"
{ iname replace "([0-9]+) /.*/(.*)" -> "\1 \2" }
supprime un chemin de répertoire, donc le nom d'instance (pour l'une des métriques du PMDA proc) "2981799 /home/kenj/bin/foobar" deviendrait "2981799 foobar", masquant le répertoire personnel de l'utilisateur et implicitement le nom de connexion de l'utilisateur.

INAME REDACT

Remplace chaque nom d'instance externe dans le domaine d'instances par la chaîne "inst [redacted]" où inst est l'identifiant interne de l'instance au format ASCII.

INDOM -> newdomain.newserial

Modifie les métadonnées pour le domaine d'instances et chaque métrique associée au domaine d'instances. À titre de cas spécial, newserial pourrait être un astérisque ``*'' ce qui signifie utiliser serial de la règle de réécriture indom, bien que ce soit le plus utile lorsque serial est aussi un astérisque. Donc par exemple :

indom 29.* { indom -> 109.* }
déplacera tous les domaines d'instances du domaine 29 vers le domaine 109.

INDOM -> DUPLICATE newdomain.newserial

Un cas spécial de la clause INDOM précédente où le domaine d'instances est une copie du domaine d'instances domain.serial de la règle de réécriture indom, puis toutes les règles de mappage sont appliquées au domaine d'instances copié newdomain.newserial. Ceci est utile lorsqu'un PMDA est divisé et que le même domaine d'instances doit être répliqué pour le domaine domain et le domaine newdomain. Donc par exemple si les métriques foo.one et foo.two sont toutes deux définies sur le domaine d'instances 12.34, et foo.two est déplacé vers un autre PMDA en utilisant le domaine 27, alors les règles de réécriture suivantes pourraient être utilisées :

indom 12.34 { indom -> duplicate 27.34 }
metric foo.two { indom -> 27.34 pmid -> 27.*.* }

INST oldid -> newid

L'instance identifiée par l'identifiant interne de l'instance oldid est renumérotée en newid. Les deux oldid et newid sont des entiers dans la plage de 0 à 231-1.

À titre de cas spécial, newid peut être le mot-clé DELETE et alors l'instance oldid sera effacée de outlog, ce qui la retire des métadonnées du domaine d'instances et supprime toutes les valeurs de cette instance pour toutes les métriques associées.

Une règle de réécriture metric a la forme :

METRIC metricid { metricspec ... }

où metricid identifie une ou plusieurs métriques existantes de inlog en utilisant soit un nom de métrique, soit l'encodage interne pour le PMID d'une métrique comme domain.cluster.item. Dans ce dernier cas, typiquement domain serait un entier dans la plage de 1 à 510, cluster serait un entier dans la plage de 0 à 4095, et item serait un entier dans la plage

Le domaine de 0 à 1023.

Dans des cas spéciaux, item peut être un astérisque ``*'' ce qui signifie que la règle s'applique à chaque métrique dont le numéro de domaine est domain et le numéro de cluster est cluster, ou cluster peut être un astérisque ce qui signifie que la règle s'applique à chaque métrique dont le numéro de domaine est domain et le numéro d'élément est item, ou à la fois cluster et item peuvent être des astérisques, et la règle s'applique à chaque métrique dont le numéro de domaine est domain.

Si une métrique désignée n'est pas dans inlog, la règle n'a aucun effet.

Le metricspec est zéro ou plusieurs des clauses suivantes :

DELETE

La métrique est complètement supprimée de outlog, à la fois les métadonnées et toutes les valeurs dans les résultats sont expurgées.

INDOM -> newdomain.newserial [ pick ]

Modifie les métadonnées pour changer le domaine d'instance pour cette métrique. Le nouveau domaine d'instance doit exister dans outlog.

La clause facultative pick peut être utilisée pour sélectionner une valeur d'entrée, ou calculer une valeur agrégée à partir des instances dans un résultat d'entrée, ou assigner un identificateur d'instance interne à une seule valeur de sortie. Si aucune clause pick n'est spécifiée, le comportement par défaut est de copier toutes les valeurs d'entrée de chaque résultat d'entrée vers un résultat de sortie, cependant si le domaine d'instance d'entrée est singulier (indom PM_INDOM_NULL), alors la valeur de sortie unique doit se voir assigner un identificateur d'instance interne, qui est 0 par défaut, sauf s'il est remplacé par une clause INST ou INAME telle que définie ci-dessous.

Les choix pour pick sont les suivants :

OUTPUT FIRST
choisir la valeur de la première instance de chaque résultat d'entrée
OUTPUT LAST
choisir la valeur de la dernière instance de chaque résultat d'entrée
OUTPUT INST instid
choisir la valeur de l'instance avec l'identificateur d'instance interne instid de chaque résultat ; la séquence de règles de réécriture assure que le traitement OUTPUT se produit avant le re-numérotage des identificateurs d'instance issus d'une règle indom associée, donc instid doit être l'un des identificateurs d'instance internes qui apparaît dans inlog
OUTPUT INAME "name"
choisir la valeur de l'instance dont le nom d'instance externe est name de chaque résultat ; la séquence de règles de réécriture assure que le traitement OUTPUT se produit avant le renommage d'instance issu d'une règle indom associée, donc name doit être l'un des noms d'instance externes qui apparaît dans inlog
OUTPUT MIN
choisir la plus petite valeur dans chaque résultat (le type de métrique doit être numérique et l'instance de sortie sera 0 pour un domaine d'instance non singulier)
OUTPUT MAX
choisir la plus grande valeur dans chaque résultat (le type de métrique doit être numérique et l'instance de sortie sera 0 pour un domaine d'instance non singulier)
OUTPUT SUM
choisir la somme de toutes les valeurs dans chaque résultat (le type de métrique doit être numérique et l'instance de sortie sera 0 pour un domaine d'instance non singulier)
OUTPUT AVG
choisir la moyenne de toutes les valeurs dans chaque résultat (le type de métrique doit être numérique et l'instance de sortie sera 0 pour un domaine d'instance non singulier)

Si le domaine d'instance d'entrée est singulier (indom PM_INDOM_NULL), alors indépendamment de toute spécification pick, il y a au plus une valeur dans chaque résultat d'entrée et donc FIRST, LAST, MIN, MAX, SUM et AVG sont tous équivalents et l'identificateur d'instance de sortie sera 0.

En général, il est erroné de spécifier une action de réécriture pour les mêmes métadonnées ou valeurs de résultat plus d'une fois, par exemple plus d'une clause INDOM pour le même domaine d'instance. La seule exception est l'interaction possible entre les clauses INDOM dans les règles indom et metric. Par exemple, la métrique sample.bin est définie sur le domaine d'instance 29.2 dans inlog et ce qui suit est acceptable (bien que redondant) :

indom 29.* { indom -> 109.* }
metric sample.bin { indom -> 109.2 }
Cependant, ce qui suit est une erreur, car le domaine d'instance pour sample.bin a deux définitions contradictoires : 
indom 29.* { indom -> 109.* }
metric sample.bin { indom -> 123.2 }

INDOM -> NULL[ pick ]

La métrique (qui devait être précédemment définie sur un domaine d'instance) est modifiée pour devenir une métrique singulière. Cela implique un changement de métadonnées et la réduction de tous les résultats pour cette métrique afin que plusieurs valeurs deviennent une seule valeur.

La partie facultative pick de la clause définit comment la valeur unique pour chaque résultat doit être calculée et suit les mêmes règles que celles décrites pour le cas INDOM non-NULL ci-dessus.

En l'absence de pick, le défaut est OUTPUT FIRST.

NAME -> newname

Renomme la métrique dans les métadonnées de l'archive PCP qui prend en charge l'espace de noms des métriques de performance (PMNS). newname ne doit correspondre à aucun nom existant dans le PMNS de l'archive et doit suivre les règles syntaxiques pour les noms de métriques valides telles que décrites dans PMNS(5).

PMID -> newdomain.newcluster.newitem

Modifie les métadonnées et les résultats pour renuméroter le PMID de la métrique. Dans des cas spéciaux, newcluster peut être un astérisque ``*'' ce qui signifie utiliser le cluster de la règle de réécriture metric et/ou item peut être un astérisque ce qui signifie utiliser l'item de la règle de réécriture metric. Ceci est le plus utile lorsque cluster et/ou item est également un astérisque. Ainsi par exemple :

metric 30.*.* { pmid -> 123.*.* }
déplacera toutes les métriques du domaine 30 vers le domaine 123.

SEM -> newsem

Change la sémantique de la métrique. newsem doit être la partie XXX du nom de l'une des macros PM_SEM_XXX définies dans <pcp/pmapi.h> ou pmLookupDesc(3), par exemple COUNTER pour PM_TYPE_COUNTER.

Aucune réécriture de valeur de données n'est effectuée suite à la clause SEM, donc l'utilité est limitée aux cas où une version du PMDA associé exportait des sémantiques incorrectes pour la métrique. pmlogreduce(1) peut fournir une alternative dans les cas où une re-calcul des valeurs de résultats est souhaité.

TYPE -> newtype

Change le type de la métrique, ce qui modifie les métadonnées et peut changer le codage des valeurs dans les résultats. newtype doit être la partie XXX du nom de l'une des macros PM_TYPE_XXX définies dans <pcp/pmapi.h> ou pmLookupDesc(3), par exemple FLOAT pour PM_TYPE_FLOAT.

La conversion de type n'est prise en charge que dans les cas où l'ancien type de métrique est numérique, donc PM_TYPE_STRING, PM_TYPE_AGGREGATE, PM_TYPE_EVENT et PM_TYPE_HIGHRES_EVENT ne sont pas autorisés. De même, le nouveau type de métrique doit être numérique ou PM_TYPE_STRING. Même pour les cas numériques, certaines conversions peuvent produire des erreurs d'exécution, par exemple un dépassement d'entier, ou une tentative de réécrire une valeur négative dans un type non signé, ou une imprécision, par exemple lors de la conversion d'un float ou d'un double en chaîne.

TYPE IF oldtype -> newtype

Identique à la clause TYPE précédente, sauf que le type de la métrique n'est changé en newtype que si le type de la métrique dans inlog est oldtype.

Ceci est utile dans les cas où le type de metricid dans inlog peut dépendre de la plateforme et donc plus d'une règle de réécriture de type est nécessaire.

UNITS -> newunits [ RESCALE ]

newunits est six valeurs séparées par des virgules. Les 3 premières valeurs décrivent la dimension de la métrique selon les dimensions d'espace, de temps et de comptage ; ce sont des valeurs entières, généralement 0, 1 ou -1. Les 3 valeurs restantes décrivent l'échelle des valeurs de la métrique dans les dimensions d'espace, de temps et de comptage. Les valeurs d'échelle d'espace doivent être 0 (si la dimension d'espace est 0), sinon la partie XXX du nom de l'une des macros PM_SPACE_XXX, par exemple KBYTE pour PM_TYPE_KBYTE. Les valeurs d'échelle de temps doivent être 0 (si la dimension de temps est 0), sinon la partie XXX du nom de l'une des macros PM_TIME_XXX, par exemple SEC pour PM_TIME_SEC. Les valeurs d'échelle de comptage doivent être 0 (si la dimension de temps est 0), sinon ONE pour PM_COUNT_ONE.

Les macros PM_SPACE_XXX, PM_TIME_XXX et PM_COUNT_XXX sont définies dans <pcp/pmapi.h> ou pmLookupDesc(3).

Lorsque l'échelle est changée (mais la dimension est inchangée) le mot-clé facultatif RESCALE peut être utilisé pour choisir la ré-échelle des valeurs conformément à l'option de ligne de commande -s, mais appliquée uniquement à cette métrique.

VALUE REPLACE /pattern/ -> "replacement"

La valeur de chaque instance de la métrique est comparée à l'expression régulière pattern et lorsqu'une correspondance est trouvée, la valeur est modifiée en fonction des parties de la valeur correspondant à pattern et de la recette de replacement. pattern suit la syntaxe d'une expression régulière étendue Posix (voir regex(7)) et replacement suit la syntaxe de la commande s de sed(1), donc & et \1 à \9 peuvent être utilisés pour sélectionner tout ou sous-chaînes de la valeur qui correspondent à pattern.

Notez que th

- et de remplacement est effectué au plus une fois par valeur métrique, de sorte que si des séquences répétées de la valeur métrique correspondent à pattern, seule la **première** sera correspondue et replacement sera appliquée.

pattern est normalement entouré de barres obliques (/) ou de guillemets doubles ("). Un échappement (\) peut être utilisé avant n'importe quel métacaractère décrit dans regex(3) pour spécifier un caractère littéral, par exemple \( ou \[ ou \+ ... Les délimiteurs environnants ne peuvent pas être échappés, donc pour intégrer une barre oblique littérale, utilisez des guillemets doubles comme délimiteur, ou vice versa.

replacement est normalement entouré de guillemets doubles (") ou de barres obliques (/). Un échappement (\) peut être utilisé avant **&** ou **\** pour spécifier ces caractères littéralement. Les délimiteurs environnants ne peuvent pas être échappés, donc pour intégrer un guillemet double, utilisez des barres obliques comme délimiteur, ou vice versa.

Le mot-clé **REPLACE** est facultatif.

Cette clause ne peut être appliquée qu'aux métriques dont les valeurs sont de type **PM_TYPE_STRING**.

Voici quelques exemples :

{ value /.*/ -> "" }
supprimer la valeur partout
value "/.*/(.*)" -> "\1" }
supprime un chemin de répertoire, de sorte que la valeur métrique "mumble /home/kenj/bin/foobar fumble" deviendrait "mumble foobar fumble", cachant le répertoire personnel de l'utilisateur et implicitement son nom de connexion

Lors du changement du numéro de domaine pour un domaine de métrique ou d'instance, le nouveau numéro de domaine correspondra généralement au numéro de domaine d'un PMDA existant. Si ce n'est pas le cas, le nouveau numéro de domaine ne doit pas être choisi au hasard ; consultez **$PCP_VAR_DIR/pmns/stdpmid** pour connaître les numéros de domaine déjà attribués aux PMDA.

Une règle de réécriture **text** modifie un enregistrement de texte d'aide et a la forme :

**TEXT** textid [ texttype ] [ "textcontent" ] **{** textspec ... **}**

où textid identifie la métrique ou le domaine d'instance auquel le texte est actuellement associé, et est soit **METRIC** metricid, soit **INDOM** domain**.**serial.

metricid a la même forme et signification que pour une règle de réécriture **METRIC** (voir ci-dessus) et domain**.**serial a la même forme et signification que pour une règle de réécriture **INDOM** (voir ci-dessus).

Le texttype facultatif identifie le type de texte et peut être **ONELINE** pour sélectionner le texte d'aide sur une ligne, **HELP** pour sélectionner le texte d'aide complet, ou **ALL** ou un astérisque ``*'' pour sélectionner les deux types de texte d'aide. Si texttype n'est pas spécifié, la valeur par défaut est **ONELINE**.

Le textcontent facultatif restreint davantage les enregistrements de texte sélectionnés à ceux contenant le contenu spécifié. Les caractères tels que les guillemets doubles peuvent être échappés en les faisant précéder d'une barre oblique inverse ``\''.

Si un enregistrement d'aide désigné n'est pas dans inlog, la règle n'a aucun effet.

Le textspec est zéro ou plusieurs des clauses suivantes :

**DELETE**

Le texte sélectionné est complètement supprimé de outlog.

**INDOM** **->** newdomain**.**newserial

Réassocie le texte au domaine d'instance spécifié. En tant que cas spécial, newserial pourrait être un astérisque ``*'', ce qui signifie utiliser serial de la règle de réécriture **text**, bien que cela soit surtout utile lorsque serial est également un astérisque. Ainsi, par exemple :

Réassocie le texte à la métrique spécifiée. En tant que cas spéciaux, newcluster pourrait être un astérisque ``*'', ce qui signifie utiliser cluster de la règle de réécriture **text** et/ou item pourrait être un astérisque, ce qui signifie utiliser item de la règle de réécriture **text**. Ceci est surtout utile lorsque cluster et/ou item est également un astérisque. Ainsi, par exemple :

domain**.**serial a la même forme et signification que pour une règle de réécriture **INDOM** (voir ci-dessus).

pmlogrewrite(1) — Performance Co-Pilot — Arch Linux

NAME

pmlogrewrite — rewrite Performance Co-Pilot archive logs

SYNOPSIS

pmlogrewrite

[-c config] [-D debug] [-h] [-q] [-T trailer] [-v] [-?] <inlog> <outlog>

DESCRIPTION

pmlogrewrite is a utility to rewrite Performance Co-Pilot (PCP) archive logs. It can be used to change the metadata, such as metric descriptors, instance domains, help text, and metric value types, and also to change the PMID of individual metrics, and the domain number for instances of specific metrics. It is most often used to convert older archive logs to a new format after PMDA changes, or to change the metric value types to allow for longer term aggregation.

The rewriting rules are specified in a configuration file. The default configuration file is looked for in the current directory, or alternatively in the directory specified by the $PCP_LOG_DIR environment variable, as pmlogrewrite.conf.

OPTIONS

The following options are available:

-c config
Use the rewriting rules from the file named config, instead of the default pmlogrewrite.conf.
-D debug
Enable optional diagnostic output on stderr. debug is a comma-separated list of debugging options. Use pmdbg(1) with the -l option to obtain a list of the available debugging options and their meaning. The options specific to pmlogrewrite are described in the DEBUGGING OPTIONS section below.
-h
Print a usage summary and exit.
-q
Perform a quick exit from pmlogrewrite if no changes to the archive are needed. This is useful for the conversion of older archive logs to a new format after PMDA changes, when you want to convert old archives so that they can be processed alongside new archives.
-T trailer
Append the content of the file trailer to the output archive. This is useful for adding trailer metadata that is not present in the input archive, but is necessary for the output archive to be valid.
-v
Print the version number of pmlogrewrite and exit.
-?
Print the usage summary and exit.

REWRITING RULES SYNTAX

The rewriting rules are specified in a syntax that is a subset of the PMNS (Performance Metrics Name Space) syntax. The following constructs are supported:

metric [ pmid ] { ... }

This is a rule for rewriting a metric descriptor. The metric is a metric name (e.g. cpu.user), optionally followed by a PMID (e.g. cpu.user<1.0.0.1>). If the metric name is followed by a dot and asterisks (e.g. 60.*), then this rule applies to all metrics whose PMID begins with the specified prefix.

Inside the curly braces, a comma-separated list of one or more of the following rewrite clauses may appear:

pmid -> newpmid
Rewrite the PMID of the metric to newpmid.
type -> newtype
Rewrite the type of the metric to newtype. The standard PCP type names are recognised, e.g. U32, U64, FLOAT, DOUBLE, STRING.
help -> "new help text"
Rewrite the help text for the metric.
unit -> newunit
Rewrite the units for the metric. The format of newunit is the same as for the pmUnitsStr(3) function.
label labelname -> newlabelname
Rewrite the label labelname to newlabelname.
name -> newname
Rewrite the metric name to newname.
indom { ... }

This is a rule for rewriting an instance domain. The indom is an instance domain identifier (e.g. 60.2). If the instance domain identifier is followed by a dot and asterisks (e.g. 60.2.*), then this rule applies to all instances within that instance domain.

Inside the curly braces, a comma-separated list of one or more of the following rewrite clauses may appear:

inst inst -> newinst
Rewrite the instance identifier inst to newinst.
iname inst -> "new instname"
Rewrite the instance name for instance inst to newinstname.
indom -> newindom
Rewrite the instance domain identifier to newindom. This is only allowed if the instance domain is specified as a whole (e.g. indom 60.2 { indom -> 123.0 }).

A special case is when the value in a rewrite clause is an asterisk (e.g. pmid -> *). This means use the corresponding value from the original archive.

The pmid, type, unit, label, name, inst, iname, and indom clauses can be qualified with an optional regex(7) qualifier. For example:

metric cpu.user pm:1.1 { pmid pm:1.1.* -> pm:1.2.* }

This will rewrite all metrics with PMIDs starting with 1.1. to have PMIDs starting with 1.2..

INDOM -> newdomain.newserial

Re-associates the selected label(s) with the specified instance domain. As a special case, newserial could be an asterisk ``*'' which means use serial from the label rewriting rule, although this is most useful when serial is also an asterisk. So for example:

label indom 29.* { indom -> 109.* }
will re-associate all labels associated with instance domains from domain 29 to domain 109.

INSTANCES -> newdomain.newserial

This is the same as INDOM except that it re-associates the selected label(s) with the instances of the specified instance domain.

EXAMPLES

To promote the values of the per-disk IOPS metrics to 64-bit to allow aggregation over a long time period for capacity planning, or because the PMDA has changed to export 64-bit counters and we want to convert old archives so they can be processed alongside new archives.

metric disk.dev.read { type -> U64 }
metric disk.dev.write { type -> U64 }
metric disk.dev.total { type -> U64 }

The instances associated with the load average metric kernel.all.load could be renamed and renumbered by the rules below.

# for the Linux PMDA, the kernel.all.load metric is defined
# over instance domain 60.2
indom 60.2 {
    inst 1 -> 60 iname "1 minute" -> "60 second"
    inst 5 -> 300 iname "5 minute" -> "300 second"
    inst 15 -> 900 iname "15 minute" -> "900 second"
}

If we decide to split the ``proc'' metrics out of the Linux PMDA, this will involve changing the domain number for the PMID of these metrics and the associated instance domains. The rules below would rewrite an old archive to match the changes after the PMDA split.

# all Linux proc metrics are in 7 clusters
metric 60.8.* { pmid -> 123.*.* }
metric 60.9.* { pmid -> 123.*.* }
metric 60.13.* { pmid -> 123.*.* }
metric 60.24.* { pmid -> 123.*.* }
metric 60.31.* { pmid -> 123.*.* }
metric 60.32.* { pmid -> 123.*.* }
metric 60.51.* { pmid -> 123.*.* }
# only one instance domain for Linux proc metrics
indom 60.9 { indom -> 123.0 }

If the metric foo.count_em was exported as a native ``long'' then it could be a 32-bit integer on some platforms and a 64-bit integer on other platforms. Subsequent investigations show the value is in fact unsigned, so the following rules could be used.

metric foo.count_em {
	type if 32 -> U32
	type if 64 -> U64
}

DIAGNOSTICS

All error conditions detected by pmlogrewrite are reported on stderr with textual (if sometimes terse) explanation.

Should the input archive be corrupted (this can happen if the pmlogger instance writing the archive suddenly dies), then pmlogrewrite will detect and report the position of the corruption in the file, and any subsequent information from that archive will not be processed.

If the input archive contains no archive records then an ``empty archive'' warning is issued and no processing is performed.

If any error is detected, pmlogrewrite will exit with a non-zero status.

FILES

For each of the inlog and outlog archives, several physical files are used.

archive.meta
metadata (metric descriptions, instance domains, etc.) for the archive
archive.0
initial volume of metrics values (subsequent volumes have suffixes 1, 2, ...).
archive.index
temporal index to support rapid random access to the other files in the archive.

PCP ENVIRONMENT

Environment variables with the prefix PCP_ are used to parameterize the file and directory names used by PCP. On each installation, the file /etc/pcp.conf contains the local values for these variables. The $PCP_CONF variable may be used to specify an alternative configuration file, as described in pcp.conf(5).

For environment variables affecting PCP tools, see pmGetOptions(3).

DEBUGGING OPTIONS

The -D or --debug option enables the output of additional diagnostics on stderr to help triage problems, although the information is sometimes cryptic and primarily intended to provide guidance for developers rather end-users. debug is a comma separated list of debugging options; use pmdbg(1) with the -l option to obtain a list of the available debugging options and their meaning.

Debugging options specific to pmlogrewrite are as follows:

Option Description
appl0 archive reads and writes for data and metadata volumes
appl1 metadata changes (metric descriptors, instance domains, help text, metric labels)
appl2 metric value (pmResult) changes
appl3 -q handling and explanation of required changes that are the reason for not taking a quick exit
appl4 config file parser diagnostics
appl5 Rregex(7) matching for metric value changes and instance name changes
appl6 lexical scanner called from config file parser
appl7 temporal index generation diagnostics
