PMLOGGER.CONTROL(5) Manuel des formats de fichiers PMLOGGER.CONTROL(5)

NOM

pmlogger.control - fichiers de contrôle pour l'archivage avec Performance Co-Pilot

DESCRIPTION

L'archivage historique des données de performance pour Performance Co-Pilot (voir PCPIntro(1)) utilise pmlogger(1) et une ou plusieurs instances de pmlogger peuvent être gérées par pmlogger_check(1) et pmlogger_daily(1).

pmlogger_check(1) peut être exécuté à tout moment de la journée et est destiné à vérifier que l'ensemble désiré de processus pmlogger est en cours d'exécution. Sinon, il (re)démarre les processus de journalisation manquants. Par défaut, pmlogger_check(1) appelle également pmlogger_daily(1) avec une option -K pour exécuter les tâches requises de compression d'archives.

pmlogger_daily(1) est destiné à être exécuté une fois par jour, de préférence tôt le matin, dès que possible après minuit. Sa tâche est d'agréger, de faire pivoter et d'effectuer des tâches d'entretien générales pour un ou plusieurs ensembles d'archives PCP.

Tant pmlogger_check(1) que pmlogger_daily(1) opèrent sur une famille de fichiers de contrôle partagés, à savoir le fichier $PCP_PMLOGGERCONTROL_PATH et les fichiers du répertoire $PCP_PMLOGGERCONTROL_PATH.d. Ces fichiers ne doivent pas être inscriptibles par un utilisateur autre que root.

Les fichiers de contrôle doivent être personnalisés selon les règles suivantes qui définissent pour la version actuelle (1.1) du format des fichiers de contrôle.

1.
Les lignes commençant par un « # » sont des commentaires. Un cas spécial est celui des lignes commençant par « #! » ; ce sont des lignes de contrôle pour un pmlogger qui a été arrêté en utilisant pmlogctl(1).
2.
Les lignes commençant par un « $ » sont supposées être des affectations de variables d'environnement à la manière de sh(1), et tout le texte suivant le « $ » sera evalué par le script lisant le fichier de contrôle, et la variable correspondante exportée dans l'environnement. Ceci est particulièrement utile pour définir et exporter des variables dans l'environnement des scripts administratifs, par exemple : 

$ PMCD_CONNECT_TIMEOUT=20

Si la valeur à droite du « = » contient des espaces blancs, la valeur doit être entourée de guillemets doubles (") ou simples (').
3.
Il doit y avoir une ligne de version dans le fichier de contrôle de la forme : 

$version=1.1

Mais comme la seule version actuellement supportée est 1.1, cette déclaration ne fournit aucune valeur supplémentaire au-delà de la documentation.

4.
Les champs dans une ligne des fichiers de contrôle sont généralement séparés par un ou plusieurs espaces ou tabulations (bien que se référer à la description du champ directory ci-dessous pour quelques exceptions importantes).
5.
Il doit y avoir une ligne dans les fichiers de contrôle pour chaque instance de pmlogger avec au moins 4 champs de la forme : 

hôte primaire socks répertoire args ...

6.
Le champ hôte est le nom de l'hôte qui est la source des métriques de performance pour cette instance de pmlogger. Le mot réservé LOCALHOSTNAME sera remplacé par local: (donc connexion à pmcd(1) sur l'hôte local).
7.
Le champ primaire indique si cette instance de pmlogger est primaire (y) ou non (n). Comme le logger primaire doit s'exécuter sur l'hôte local, et qu'il ne peut y avoir qu'un seul logger primaire pour un hôte donné, ce champ ne peut être y que pour une seule instance de pmlogger, auquel cas le nom d'hôte doit être le nom de l'hôte local (ou LOCALHOSTNAME).
8.
Le champ socks indique si cette instance de pmlogger doit être démarrée sous le contrôle de pmsocks(1) pour se connecter à un pmcd(1) à travers un pare-feu (y ou n).
9.
Le champ directory est un nom de répertoire. Tous les fichiers d'archives associés à cette instance de pmlogger seront créés dans ce répertoire, et ce sera le répertoire courant pour l'exécution de tout programme requis pour maintenir ces archives. Une convention utile est que les archives du logger primaire pour l'hôte local nommé myhost sont maintenues dans le répertoire $PCP_ARCHIVE_DIR/myhost (c'est là que le script de démarrage pmlogger par défaut dans $PCP_RC_DIR/pmlogger créera les archives), tandis que les archives pour l'hôte distant mumble sont maintenues dans $PCP_ARCHIVE_DIR/mumble.
10.
Le champ directory peut contenir une syntaxe shell intégrée qui sera évaluée par sh(1) pour produire le nom réel du répertoire à utiliser. Les constructions autorisées sont :
  • Tout texte (y compris les espaces blancs) entouré de $( et ) sera interprété comme une commande shell.
  • Tout texte (y compris les espaces blancs) entouré de ` et ` (apostrophes inverses) sera interprété comme une commande shell.
  • Au sein d'une même ligne, un seul style de commande shell intégrée est autorisé, donc soit $(...) soit `...`, mais pas les deux.
  • Un guillemet double initial (") suivi d'un texte arbitraire (y compris les espaces blancs, mais excluant un guillemet double intégré) et d'un guillemet double final.
  • Une apostrophe simple initiale (') suivie d'un texte arbitraire (y compris les espaces blancs, mais excluant une apostrophe simple intégrée) et d'une apostrophe simple finale.
  • Tout mot contenant un $ (supposé introduire un nom de variable d'environnement).
11.
Dans le champ directory, le mot réservé LOCALHOSTNAME sera remplacé par le nom de l'hôte local. De même, les mots réservés PCP_ARCHIVE_DIR et PCP_LOG_DIR apparaissant n'importe où dans le champ directory seront remplacés par les valeurs des variables d'environnement correspondantes.
12.
Si le champ directory (après substitution shell éventuelle) commence par « + » alors cela indique que pmlogger(1) sera exécuté avec une option -R dans args pour « pousser » l'archive vers un serveur pmproxy(1) distant. Dans ce cas, aucun fichier d'archive n'est stocké localement, mais directory (après avoir retiré le « + » initial) est utilisé comme répertoire dans lequel le fichier journal de pmlogger (1) local sera stocké et potentiellement l'emplacement du fichier de configuration de pmlogger(1) (voir l'exemple ci-dessous).
13.
Le champ optionnel args et les champs restants sont interprétés comme des arguments à passer à pmlogger(1). Le plus souvent, il s'agirait au minimum de l'option -c pour spécifier les métriques à enregistrer et les fréquences d'enregistrement, et/ou -R dans le cas d'une archive « push ».

Les lignes de contrôle d'exemple suivantes spécifient un logger primaire sur l'hôte local (bozo), des loggers non primaires pour collecter et enregistrer les métriques de performance des hôtes wobbly, boing et de l'hôte local (c'est-à-dire bozo) et un logger qui pousse les archives vers le pmproxy(1) distant sur l'hôte grunt.

$version=1.1
bozo          y  n  $PCP_ARCHIVE_DIR/bozo   -c config.default
wobbly        n  n  "/store/wobbly/$(date +%Y)"  -c ./wobbly.config
boing         n  n  $PCP_ARCHIVE_DIR/boing   -c ./pmlogger.config
LOCALHOSTNAME n  n  /cluster/LOCALHOSTNAME   -c ./precious.config
LOCALHOSTNAME n  n  +PCP_ARCHIVE_DIR/remote -R http://grunt:44322 \
				-c ./remote.config

EXECUTION PROGRAMMÉE

L'exécution périodique de pmlogger_check(1) et pmlogger_daily(1) est contrôlée par systemd(1) ou cron(8).

Des entrées typiques de crontab(5) sont fournies dans $PCP_SYSCONF_DIR/pmlogger/crontab (sauf si elles sont déjà installées par défaut dans /etc/cron.d) et sont présentées ci-dessous.

# traitement quotidien des archives
14      0       *    *       *       $PCP_BINADM_DIR/pmlogger_daily
# toutes les 30 minutes, vérifier que les instances pmlogger s'exécutent
25,55   *       *       *       *       $PCP_BINADM_DIR/pmlogger_check

Lors de l'utilisation de systemd(1) sous Linux, aucune entrée crontab n'est nécessaire car le mécanisme de temporisation fourni par systemd est utilisé à la place pour obtenir la même période d'exécution que l'exemple crontab ci-dessus.

FICHIERS

$PCP_PMLOGGERCONTROL_PATH
le fichier de contrôle de pmlogger de PCP. Pour une nouvelle installation, ce fichier ne contient aucune ligne de contrôle de pmlogger(1) (les vrais fichiers de contrôle sont tous dans le répertoire $PCP_PMLOGGERCONTROL_PATH.d), mais ce fichier est toujours traité pour prendre en charge les configurations héritées qui s'y trouvent à partir des versions antérieures de PCP.
Attention : ce fichier ne doit pas être inscriptible par un utilisateur autre que root.
$PCP_PMLOGGERCONTROL_PATH.d
répertoire optionnel contenant des fichiers de contrôle supplémentaires de pmlogger de PCP, avec une ou plusieurs spécifications de pmlogger par fichier.
Attention : les fichiers ici ne doivent pas être inscriptibles par un utilisateur autre que root.
$PCP_SYSCONF_DIR/pmlogger/crontab
exemple de crontab pour l'exécution automatisée de scripts par $PCP_USER (ou root). N'existe que si la plateforme ne prend pas en charge le mécanisme /etc/cron.d.

ENVIRONNEMENT PCP

Les variables d'environnement dont le préfixe est PCP_ sont utilisées pour paramétrer les noms de fichiers et de répertoires utilisés par PCP. À chaque installation, le fichier /etc/pcp.conf contient les valeurs locales de ces variables. La variable $PCP_CONF peut être utilisée pour spécifier un fichier de configuration alternatif, comme décrit dans pcp.conf(5).
