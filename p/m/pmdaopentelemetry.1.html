PMDAOPENTELEMETRY(1) Manuel des commandes générales PMDAOPENTELEMETRY(1)

NOM

pmdaopentelemetry - PMDA OpenTelemetry

SYNTAXE

$PCP_PMDAS_DIR/opentelemetry/pmdaopentelemetry [-D] [-n] [-c config] [-d domaine] [-l fichier_log] [-r root] [-t timeout] [-u utilisateur]

DESCRIPTION

pmdaopentelemetry est un agent de domaine de métriques de performance (PMDA) qui crée dynamiquement des métriques PCP à partir de points d'accès OpenTelemetry configurés fournissant un accès basé sur HTTP aux métriques des applications.

Le répertoire config par défaut est $PCP_PMDAS_DIR/opentelemetry/config.d/, voir ``SOURCES DE CONFIGURATION'' ci-dessous. Le timeout par défaut pour la récupération des URL est de 2 secondes. L'utilisateur par défaut, s'il n'est pas spécifié avec l'option -u, est l'utilisateur "pcp". Si l'option -n est donnée, la liste des fichiers de configuration ne sera pas triée avant traitement. Cette liste est triée par défaut, mais cela peut être coûteux s'il y a un grand nombre de fichiers de configuration (URL et/ou scripts).

Si l'option -D est donnée, des messages de diagnostic supplémentaires seront écrits dans le fichier log du PMDA, qui est $PCP_LOG_DIR/pmcd/opentelemetry.log par défaut (voir aussi -l ci-dessous). De plus, la métrique opentelemetry.control.debug contrôle le même drapeau de débogage et peut être définie avec la commande suivante :

pmstore opentelemetry.control.debug valeur

où valeur est soit 1 (pour activer les messages de log détaillés) soit 0 (pour désactiver les messages de log détaillés). Ceci est particulièrement utile pour examiner les en-têtes http passés à chaque requête de récupération, les paramètres de filtre et d'autres détails de traitement qui sont journalisés lorsque le drapeau de débogage est activé.

L'option -d peut être utilisée pour remplacer le numéro de domaine de métriques de performance par défaut, qui est 164. Il est fortement recommandé de ne pas le changer. Le numéro de domaine doit être différent pour chaque PMDA sur le même hôte, et le même numéro de domaine doit être utilisé pour le PMDA pmdaopentelemetry sur tous les hôtes. Voir aussi l'option -r, qui permet de changer la racine de l'espace de noms dynamique par défaut de opentelemetry.

L'option -l peut être utilisée pour spécifier fichier_log comme destination des messages du PMDA au lieu de la destination par défaut, $PCP_LOG_DIR/pmcd/opentelemetry.log. À titre de cas spécial, fichier_log peut être "-" pour envoyer les messages au flux stderr à la place, par exemple -l-. Ce serait normalement le flux stderr du processus parent, pmcd(1), qui pourrait lui-même avoir redirigé son stderr. Cette redirection est normalement la plus utile dans un environnement conteneurisé, ou lors de l'utilisation de dbpmda(1).

L'option -r permet de changer la racine de l'espace de noms dynamique en root à partir de la valeur par défaut, opentelemetry. Conjointement avec d'autres options en ligne de commande, cela permet à pmdaopentelemetry d'être déployé comme un PMDA différent avec un espace de noms de métriques et un domaine de métriques distincts sur le même système hôte. Notez que tous les PMDA nécessitent un numéro de domaine unique, donc l'option -d doit également être spécifiée. L'utilisation de l'option -r peut également modifier les valeurs par défaut de certaines autres options en ligne de commande, par exemple le nom du fichier log par défaut et le répertoire de configuration par défaut.

SOURCES DE CONFIGURATION

Lors de son exécution, pmdaopentelemetry analyse périodiquement de manière récursive le répertoire $PCP_PMDAS_DIR/opentelemetry/config.d (ou le répertoire spécifié avec l'option -c), à la recherche de fichiers source d'URL (*.url) et de scripts ou binaires exécutables. Tous les fichiers qui n'ont pas le suffixe .url ou qui ne sont pas exécutables sont ignorés - cela permet d'avoir des fichiers de documentation tels que "README" et des définitions de fonctions de script "common" non exécutables sans qu'ils soient considérés comme des fichiers de configuration.

Un serveur distant n'a pas besoin d'être en ligne ou de rester en cours d'exécution - le PMDA tolère les URL distantes qui peuvent apparaître et disparaître au fil du temps. Le PMDA relaya les données et les métadonnées lorsqu'elles sont disponibles, et renverra des erreurs lorsqu'elles sont indisponibles. Les identifiants de métriques PCP, les identifiants de domaine d'instances internes et externes sont persistants et seront restaurés lorsque les sources de métriques individuelles deviendront disponibles et/ou lorsque le PMDA sera redémarré. De plus, le PMDA vérifie les dates de modification des répertoires et réanalysera les fichiers de configuration nouveaux ou modifiés dynamiquement. Il n'est *pas* nécessaire de redémarrer le PMDA lors de l'ajout, de la suppression ou de la modification de fichiers de configuration.

SOURCES URL

Chaque fichier avec le suffixe .url trouvé dans le répertoire de configuration ou un sous-répertoire contient une URL HTTP ou HTTPS complète à laquelle pmdaopentelemetry peut atteindre un point d'accès OpenTelemetry. L'accès aux fichiers locaux est également pris en charge avec une URL conventionnelle file:///somepath/somefile, dans lequel cas somepath/somefile doit contenir des données de métriques formatées en OpenTelemetry.

La première ligne d'un fichier de configuration .url doit être l'URL, comme décrit ci-dessus. Les lignes suivantes, s'il y en a, sont précédées d'un mot-clé qui peut être utilisé pour modifier la requête GET http. Un mot-clé doit se terminer par : (deux-points) et le texte s'étend jusqu'à la fin de la ligne. Les lignes de commentaire qui commencent par # et les lignes vides sont ignorées. Les seuls mots-clés actuellement pris en charge sont HEADER: et FILTER:.

HEADER: nom_en_tete: valeur ... jusqu'à la fin de la ligne
Ajoute le nom_en_tete et sa valeur aux en-têtes passés dans la requête GET http pour l'URL configurée. Un exemple de fichier de configuration qui fournit 3 en-têtes couramment utilisés et un jeton d'authentification pourrait être :


http://somehost/path/endpoint.html
# ceci est un commentaire
HEADER: Accept: text/html
HEADER: Keep-Alive: 300
HEADER: Connection: keep-alive
HEADER: Authorization: token ABCDEF1234567890

Comme mentionné ci-dessus, les valeurs des en-têtes s'étendent jusqu'à la fin de la ligne. Elles peuvent contenir n'importe quel caractère valide, y compris les deux-points. Les espaces multiples seront réduits à un seul espace, et les espaces de début et de fin seront supprimés. Une utilisation courante des en-têtes est de configurer un agent proxy et les paramètres variés qu'il peut exiger.

FILTRAGE DES MÉTRIQUES

Le filtrage des métriques est une fonctionnalité de fichier de configuration qui permet d'inclure ou d'exclure, c'est-à-dire de filtrer, les métriques ingérées. Ceci est utile car la plupart des points d'accès retournent plusieurs métriques, et généralement seulement quelques-unes sont intéressantes à des fins de surveillance. La syntaxe est :
FILTER: INCLUDE METRIC regex
ou
FILTER: EXCLUDE METRIC regex
Les noms de métriques créés dynamiquement qui correspondent à regex seront inclus ou exclus de l'espace de noms, selon ce qui est spécifié. Notez que seule la composante feuille du nom de la métrique (telle qu'ingérée depuis la source URL) est comparée au modèle regex. La règle simple est que le *premier motif de filtre correspondant* pour un nom de feuille de métrique donné est la règle qui prévaut. Si aucun motif de filtre ne correspond (ou s'il n'y a pas de filtres), alors la métrique est incluse par défaut, c'est-à-dire que le filtre par défaut si aucun n'est spécifié est FILTER: INCLUDE METRIC .* Ceci est rétrocompatible avec les versions plus anciennes du fichier de configuration qui ne prenaient pas en charge les filtres. Plusieurs lignes FILTER: seraient normalement utilisées, par exemple pour inclure certaines métriques mais exclure toutes les autres, utilisez FILTER: EXCLUDE METRIC .* comme dernier d'entre plusieurs filtres qui incluent les métriques désirées. Inversement, pour exclure certaines métriques mais inclure toutes les autres, utilisez FILTER: EXCLUDE METRIC regex. Dans ce cas, il n'est pas nécessaire (bien que cela ne nuise pas) de spécifier le dernier FILTER: INCLUDE METRIC .* car, comme indiqué ci-dessus, toute métrique qui ne correspond à aucun motif de filtre sera incluse par défaut.

FILTRAGE DES LABELS

Le filtrage des labels utilise une syntaxe et une sémantique FILTER: similaires au filtrage des métriques. FILTER: EXCLUDE LABEL regex supprimera tous les labels dont le nom correspond à regex de toutes les métriques définies par le fichier de configuration. Les mêmes règles que pour les filtres de métriques s'appliquent également aux filtres de labels - une règle implicite : FILTER: INCLUDE LABEL .* s'applique à tous les labels qui ne correspondent à aucune règle de filtre de label antérieure. Tous les labels inclus qui ne sont pas facultatifs (c'est-à-dire les labels *intrinsèques*) seront concaténés et utilisés pour la dénomination des instances externes. De plus, les labels non intrinsèques (c'est-à-dire les labels marqués comme **OPTIONAL**) auront le drapeau **PM_LABEL_OPTIONAL** défini dans les ensembles de labels retournés par les callbacks **notes**. Ce drapeau affecte la manière dont les labels sont utilisés dans certains clients. Pour plus de détails, voir pmLookupLabels(3) et les pages man associées pour plus de détails. Notez que les noms d'instance externes commencent par l'identifiant d'instance interne numérique unique suivi d'un espace, de sorte que les noms d'instance externes sont toujours uniques.

La prudence est de mise avec le filtrage des labels car, par défaut, tous les labels sont utilisés pour construire le nom de l'instance PCP. En excluant certains labels (ou en les rendant optionnels), les noms d'instance changeront. En excluant certains labels, différentes instances retournées par l'URL ou l'entrée de configuration scriptée pour la même métrique peuvent devenir des doublons. Lorsque de tels doublons se produisent, la dernière instance doublon retournée par l'URL du point d'accès ou le script prévaut sur toutes les instances précédentes. Pour ces raisons, il est recommandé de configurer les règles de filtrage des labels lors de la première définition du fichier de configuration, et de ne plus les modifier par la suite. Si une modification du filtrage des labels est requise, le fichier de configuration doit être renommé, ce qui définit effectivement une nouvelle métrique (ou un ensemble de métriques pairs telles que retournées par l'URL ou le script), avec la nouvelle dénomination d'instance (ou modifiée).

Les mots-clés non reconnus dans les fichiers de configuration sont signalés dans le fichier journal du PMDA mais ignorés par ailleurs.

SOURCES SCRIPTÉES

Les scripts exécutables présents dans le répertoire $PCP_PMDAS_DIR/opentelemetry/config.d ou ses sous-répertoires seront exécutés et le flux **stdout** contenant des données métriques au format OpenTelemetry sera analysé comme s'il provenait d'une URL ou d'un fichier. Le flux **stderr** d'un script sera envoyé au fichier journal du PMDA, qui, par défaut, peut être trouvé dans $(PCP_LOG_DIR)/pmcd/opentelemetry.log.

Notez que les sources scriptées ne prennent pas en charge le filtrage des labels ou des métriques (tel que décrit ci-dessus pour les sources d'URL) - elles peuvent simplement effectuer leur propre filtrage dans le script lui-même avec sed(1), awk(1), ou tout autre outil souhaité.

Pour plus de détails sur les formats d'exposition OpenTelemetry, voir https://github.com/open-telemetry/opentelemetry-proto/
blob/main/opentelemetry/proto/metrics/v1/metrics.proto.

CONSIDÉRATIONS SELinux

Les fichiers de configuration scriptés sont exécutés par le PMDA **pmdaopentelemetry** avec le même contexte et la même politique SELinux que le pmcd(1) local. Pour les scripts simples, cela convient normalement. Cependant, des erreurs AVC peuvent survenir pour les scripts qui effectuent des appels système ou de bibliothèque restreints par le contexte et les politiques SELinux en vigueur. Dans ces cas, il n'est pas possible d'accorder unilatéralement à **pmcd** ou à ses PMDA une politique d'exécution non restreinte. Dans ces cas spécifiques au site, il sera nécessaire de créer un module de politique SELinux local. Cela peut être fait en capturant l'enregistrement AVC à partir du journal d'audit local, en générant un module de politique local à l'aide de **audit2allow**, et en chargeant ensuite le nouveau module à l'aide de **semodule**, par exemple comme suit : 

    $ sudo grep '^type=AVC.*pcp' /var/log/audit/audit.log \
    | audit2allow -M mypolicy
    $ sudo semodule -i mypolicy.pp

Si ces politiques locales doivent être persistantes après les redémarrages, un petit script similaire à l'exemple ci-dessus peut être ajouté au fichier RC local de pmcd (généralement /etc/pcp/pmcd/rc.local). Pour plus de détails, voir audit2allow(1) et semodule(1).

NOMMAGE DES MÉTRIQUES

Toutes les métriques d'un fichier nommé JOB.* seront exportées en tant que métriques PCP avec le préfixe de nom de métrique opentelemetry.JOB. Par conséquent, le nom JOB doit être un nom valide non-feuille pour les noms de métriques PCP PMNS. Si le nom JOB a plusieurs composants séparés par des points, les noms PMNS résultants incluront ces composants et il faudra veiller à ce qu'il n'y ait pas de définitions qui se chevauchent, par exemple, les métriques retournées par JOB.response peuvent se chevaucher ou entrer en conflit avec les métriques retournées par JOB.response.time.

Les entrées de fichiers de configuration (URLs ou scripts) trouvées dans les sous-répertoires du répertoire de configuration entraîneront également des noms de métriques hiérarchiques. Par exemple, un fichier de configuration nommé $PCP_PMDAS_DIR/opentelemetry/config.d/mysource/latency/get.url entraînera la création de métriques (en récupérant cette URL source) sous opentelemetry.mysource.latency.get dans l'espace de noms PCP. Les scripts trouvés dans les sous-répertoires du répertoire de configuration entraînent de même des noms de métriques PCP hiérarchiques.

NOMS DE MÉTRIQUES DYNAMIQUES

Comme décrit ci-dessus, des modifications et de nouveaux ajouts peuvent être apportés aux fichiers du répertoire de configuration sans avoir à redémarrer le PMDA. Ces modifications sont détectées automatiquement et les noms de métriques PCP sous opentelemetry dans le PMNS seront mis à jour en conséquence, c'est-à-dire que de nouvelles métriques seront ajoutées dynamiquement et/ou des métriques existantes seront supprimées. De plus, **pmdaopentelemetry** respecte le protocole pmFetch(3) **PMCD_NAMES_CHANGE** introduit dans la version 4.0 de PCP. En particulier, si les métriques **opentelemetry** sont enregistrées par un pmlogger(1) de version 4.0 ou ultérieure de PCP, les nouvelles métriques qui apparaissent à la suite de modifications dans le répertoire de configuration du PMDA commenceront automatiquement à être enregistrées, à condition que la racine de l'espace de noms du PMDA **opentelemetry** soit configurée pour l'enregistrement dans le fichier de configuration de **pmlogger**. Voir pmlogger(1) pour les détails. Un exemple d'un tel fichier de configuration **pmlogger** est : 

log mandatory on 2 second {
	# log all metrics below the root of the opentelemetry namespace
	opentelemetry
}

MÉTA-DONNÉES

Les données métriques retournées par les fichiers de configuration URL ou scriptés peuvent contenir des méta-données qui peuvent être utilisées par le PMDA **opentelemetry** pour spécifier la sémantique, le type de données, la mise à l'échelle et les unités des métriques créées dynamiquement. Ces méta-données se trouvent pour chaque métrique sous l'en-tête de liste **metric** dans la structure de données JSON opentelemetry. Pour des informations supplémentaires sur les méta-données PCP, voir pmLookupDesc(3) et pmParseUnitsStr(3) et des exemples dans les fichiers de configuration expédiés.

Les méta-données doivent être fournies dans les données json par le point d'accès source opentelemetry (URL ou script). Une alternative est de les spécifier directement dans le fichier de configuration URL, ce qui présente l'avantage de ne pas avoir à modifier la source/le point d'accès si les méta-données sont incorrectes ou manquantes. Les méta-données spécifiées dans le fichier de configuration URL remplacent toutes les méta-données en ligne.

La syntaxe du fichier de configuration pour spécifier les méta-données est :
**MÉTA-DONNÉES :** regex type indom sémantique unités ... jusqu'à la fin de ligne
Où :
**MÉTA-DONNÉES :** est littéral
regex est une expression régulière étendue pour correspondre à un ou plusieurs noms de métriques retournés par l'URL,
type est l'un des types numériques PCP (**32**, **u32**, **64**, **u64**, **float** ou **double**),
indom est un nom de domaine d'instance arbitraire, ou **PM_INDOM_NULL**,
sémantique est soit **counter**, **instant** ou **discrete** et
unités est soit **none** soit une chaîne qui s'étend jusqu'à la fin de la ligne et qui est analysable par **pmParseUnitsStr(3)**, c'est-à-dire les unités, dimensions et mise à l'échelle à utiliser pour les métriques correspondantes.

Voici un exemple de fichier de configuration qui ingère des métriques depuis le point d'accès Grafana /metrics sur localhost, filtre toutes les métriques retournées par cette URL *sauf* **grafana_api_response_status_total**, puis spécifie que le *type* de métrique est un entier non signé de 32 bits avec un domaine d'instance non singulier nommé **response** et une sémantique **counter** avec des *unités* de **count**.

http://localhost:3000/metrics
**FILTER: INCLUDE METRIC grafana_api_response_status_total**
**FILTER: EXCLUDE METRIC .***
**METADATA: grafana_api_response_status_total u32 response counter count**

Notez que le nom dans le champ indom est actuellement ignoré, sauf s'il s'agit de **PM_INDOM_NULL**, auquel cas la métrique n'a pas de domaine d'instance (c'est-à-dire singulier), même si elle a des labels qui seraient autrement utilisés pour la dénomination d'instance.

MÉTRIQUES DE CONTRÔLE

Le PMDA maintient des métriques de contrôle spéciales, comme décrit ci-dessous. À l'exception de **opentelemetry.control.debug**, chacune de ces métriques a une instance pour chaque source de métrique configurée. Toutes ces métriques ont des valeurs entières avec une sémantique de compteur, sauf **opentelemetry.control.status**, qui a une valeur chaîne. Il est important de noter que la récupération de l'une des métriques **opentelemetry.control** ne mettra à jour les compteurs et les valeurs d'état que si l'URL correspondante est effectivement récupérée. Si l'URL source n'est pas récupérée, les valeurs des métriques de contrôle ne déclenchent pas de rafraîchissement et les valeurs de contrôle rapportées représentent la dernière récupération de chaque source correspondante.

Le domaine d'instance pour les métriques **opentelemetry.control** est ajusté dynamiquement à mesure que de nouvelles sources sont découvertes. S'il n'y a pas de sources configurées, les noms de métriques sont toujours définis mais le domaine d'instance sera vide et une récupération ne retournera aucune valeur.

opentelemetry.control.status
Une chaîne représentant le statut de la dernière récupération de la source correspondante. Ce sera généralement **success** pour un code de réponse http de 200. Cette métrique peut être utilisée pour la surveillance de la disponibilité du service - à condition, comme indiqué ci-dessus, que l'URL de la source correspondante soit également récupérée.
opentelemetry.control.status_code
Cette métrique est similaire à **opentelemetry.control.status** sauf qu'il s'agit du code de réponse entier de la dernière récupération. Une valeur de **200** signifie généralement

MÉTADONNÉES

opentelemetry.control.status
Indique le succès (0), l'échec (1) ou l'indétermination (2) de la dernière requête d'extraction pour une source donnée. Ce métrique peut être utilisé pour la surveillance de la disponibilité du service, avec les mêmes mises en garde que pour opentelemetry.control.status.
opentelemetry.control.calls
Nombre total de fois où chaque source de métrique configurée a été récupérée (si c'est une URL) ou exécutée (s'il s'agit d'un script), depuis le démarrage du PMDA. Ce métrique a une sémantique de compteur et serait normalement converti en débit/seconde par les outils clients.
opentelemetry.control.fetch_time
Temps total en millisecondes que chaque source de métrique configurée a pris pour retourner un document, hors temps d'analyse du document. Ce métrique a une sémantique de compteur et serait normalement converti en débit par les outils clients, mais il est également utile sous sa forme brute comme temps d'analyse accumulé depuis le démarrage du PMDA.
opentelemetry.control.parse_time
Temps total en millisecondes que chaque source de métrique configurée a pris pour analyser chaque document, hors temps de récupération du document. Ce métrique a une sémantique de compteur et serait normalement converti en débit par les outils clients, mais il est également utile sous sa forme brute comme temps d'analyse accumulé depuis le démarrage du PMDA.

Lorsqu'il est converti en débit, le métrique calls représente le débit moyen de récupération de chaque source sur l'intervalle d'échantillon (différence de temps entre les échantillons). Les compteurs fetch_time et parse_time, lorsqu'ils sont convertis en débit, représentent la latence moyenne de récupération et d'analyse (respectivement), pendant l'intervalle d'échantillon.

Le métrique opentelemetry.control.debug a une valeur unique, par défaut à 0. Si une valeur non nulle est stockée dans ce métrique à l'aide de pmstore(1), des messages de débogage supplémentaires seront écrits dans le fichier journal du PMDA.

LIMITATIONS

pmdaopentelemetry et les internes de libpcp imposent certaines contraintes numériques sur le nombre de sources (4095), de métriques (1024) au sein de chaque source, et d'instances pour chaque métrique (4194304).

INSTALLATION

Installez le PMDA OpenTelemetry en utilisant le script d'installation en tant que root :

# cd $PCP_PMDAS_DIR/opentelemetry
# ./Install

Pour désinstaller, les opérations suivantes doivent être effectuées en tant que root :

# cd $PCP_PMDAS_DIR/opentelemetry
# ./Remove

pmdaopentelemetry est lancé par pmcd(1) et ne doit jamais être exécuté directement. Les scripts d'installation et de désinstallation notifient pmcd lorsque l'agent est installé ou désinstallé.

Lorsque des scripts et des fichiers .url sont ajoutés, supprimés ou modifiés dans le répertoire de configuration, il n'est généralement pas nécessaire de redémarrer le PMDA - les changements seront détectés et gérés lors des requêtes ultérieures au PMDA.

ENVIRONNEMENT PCP

Les variables d'environnement avec le préfixe PCP_ sont utilisées pour paramétrer les noms de fichiers et de répertoires utilisés par PCP. Lors de chaque installation, le fichier /etc/pcp.conf contient les valeurs locales pour ces variables. La variable $PCP_CONF peut être utilisée pour spécifier un fichier de configuration alternatif, comme décrit dans pcp.conf(5).
