NOM

pmDiscoverSetup, pmDiscoverSetSlots, pmDiscoverSetEventLoop, pmDiscoverSetConfiguration, pmDiscoverSetMetricRegistry, pmDiscoverClose - services de découverte asynchrone d'archives et de leur contenu

C SYNTAXE

#include <pcp/pmwebapi.h>

pmDiscoverCallBacks *callbacks, void *arg);

int pmDiscoverSetSlots(pmDiscoverModule *module, void *slots);
int pmDiscoverSetEventLoop(pmDiscoverModule *module, void *uvloop);
int pmDiscoverSetConfiguration(pmDiscoverModule *module,
struct dict *config);

int pmDiscoverSetMetricRegistry(pmDiscoverModule *module,
struct mmv_registry *registry);

int pmDiscoverClose(pmDiscoverModule *module);

cc ... -lpcp_web

DESCRIPTION

Les fonctions pmDiscoverSetup et associées font partie intégrante de la bibliothèque d'API libpcp_web, telle qu'utilisée et décrite dans pmwebapi(3), pmproxy(1), pmseries(1) et ailleurs. Ces fonctions fournissent un mécanisme asynchrone piloté par événements pour découvrir automatiquement les archives PCP créées par pmlogger(1) et toute autre application capable d'écrire des archives PCP. Cela inclut pmrep(1) et d'autres applications utilisant l'API LOGIMPORT(3) pour importer des données de performance dans l'infrastructure PCP et écrire des archives PCP.

Les services d'API pmDiscover découvrent, surveillent et gèrent dynamiquement les répertoires d'archives PCP au fur et à mesure qu'elles sont créées, écrites, compressées et éventuellement supprimées. Le cycle de vie sous-jacent des archives est normalement géré par l'infrastructure de gestion des archives PCP (voir pmlogger_daily(1)). Les archives découvertes qui sont actives (en cours d'écriture) sont "traitées en continu" (log-tailed) pour extraire des données de performance quasi en temps réel, qui sont ensuite transmises via des rappels (callbacks) enregistrés pour un traitement ultérieur, par exemple pour ajouter les données à un serveur clé-valeur. Les archives qui sont compressées ou inactives sont suivies/surveillées mais ne sont pas traitées en continu - ceci est dû au fait que les archives compressées ne grossissent jamais et donc le traitement en continu ne découvrirait jamais de nouvelles données. Voir l'option --load dans pmseries(1) pour un mécanisme pris en charge pour ingérer des archives PCP précédemment collectées (inactives), compressées ou non, dans un serveur clé-valeur.

Les routines pmDiscover peuvent être configurées pour découvrir et surveiller automatiquement les archives PCP dans un ou plusieurs répertoires, tels que spécifiés dans pmDiscoverModule, qui est initialement configuré en appelant pmDiscoverSetConfiguration pour créer un module de type pmDiscoverModule, comme décrit ci-dessus. Le module résultant est ensuite passé à pmDiscoverSetup avec une structure initialisée de callbacks de type pmDiscoverCallBacks.

La configuration d'un module de découverte et de ses rappels impliquerait normalement la déclaration d'une instance de pmDiscoverSettings, par exemple :

#include <pcp/pmwebapi.h>
static pmDiscoverSettings someapp_discover = {
    .callbacks.on_source        = pmSomeappDiscoverSource,
    .callbacks.on_closed        = pmSomeappDiscoverClosed,
    .callbacks.on_labels        = pmSomeappDiscoverLabels,
    .callbacks.on_metric        = pmSomeappDiscoverMetric,
    .callbacks.on_values        = pmSomeappDiscoverValues,
    .callbacks.on_indom         = pmSomeappDiscoverInDom,
    .callbacks.on_text          = pmSomeappDiscoverText,
    .module.on_info             = someapp_logging_function,
};

Puis l'initialiser avec des appels d'API similaires aux suivants  :

pmDiscoverSetEventLoop(&someapp_discover.module, myevents);
pmDiscoverSetConfiguration(&someapp_discover.module, myconfig);
pmDiscoverSetMetricRegistry(&someapp_discover.module, metric_registry);
pmDiscoverSetup(&someapp_discover.module, &someapp_discover.callbacks, &privatedata);

Le code ci-dessus doit ensuite implémenter chacun des rappels déclarés, etc., pour effectuer ce qui est requis avec les données passées au rappel. Les prototypes de ces rappels se trouvent dans l'en-tête pmwebapi.h. Les rappels seront effectués de manière asynchrone, au fur et à mesure que les archives sont découvertes ou supprimées et que de nouvelles données sont écrites dans les fichiers de volume et de métadonnées des archives actives.

Dans le cas de pmproxy(1), des rappels sont enregistrés pour capturer les données de performance, qui sont ensuite envoyées à un serveur clé-valeur pour des requêtes de séries temporelles rapides et évolutives par les clients des services d'API REST PMWEBAPI(3). Ces clients incluent l'application pmseries(1) et pmproxy(1), qui est le serveur d'API REST backend pour grafana-pcp, une source de données native pour PCP dans grafana-server(1).

DIAGNOSTICS

Généralement zéro en cas de succès, ou en cas d'erreur un code de retour négatif, voir pmerr(1).

FICHIERS

Le répertoire d'archives par défaut est $PCP_ARCHIVE_DIR, qui est normalement /var/log/pcp/pmlogger. L'API descend récursivement dans tous les sous-répertoires et découvre également dynamiquement tous les nouveaux répertoires ou archives qui y sont trouvés.
