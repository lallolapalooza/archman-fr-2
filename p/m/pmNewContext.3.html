PMNEWCONTEXT(3) Manuel des fonctions de bibliothèque PMNEWCONTEXT(3)

NOM

pmNewContext - établir un nouveau contexte PMAPI

SYNTAXE C

#include <pcp/pmapi.h>

int pmNewContext(int type, const char *name);

cc ... -lpcp

DESCRIPTION

Une application utilisant l'interface de programmation d'application de métriques de performance (PMAPI) peut manipuler plusieurs contextes concurrents, chacun associé à une source de métriques de performance, par exemple pmcd(1) sur un certain hôte, ou un ensemble d'archives de métriques de performance tel que créé par pmlogger(1), ou une connexion autonome sur l'hôte local qui n'implique pas pmcd(1).

pmNewContext peut être utilisé pour établir un nouveau contexte. La source des métriques est identifiée par name, et peut être soit un nom d'hôte (type est PM_CONTEXT_HOST), soit une liste de noms séparés par des virgules faisant référence à un ensemble d'archives (type est PM_CONTEXT_ARCHIVE). Chaque élément de la liste peut être soit le nom de base commun à tous les fichiers physiques d'une archive, soit le nom d'un répertoire contenant des archives.

Pour un type de PM_CONTEXT_HOST, en plus d'identifier un hôte, le name peut également être utilisé pour encoder des informations optionnelles supplémentaires sous la forme d'un numéro de port pmcd(1), d'un nom d'hôte pmproxy(1) et d'un numéro de port proxy. Par exemple, le name "app23:14321,4321@firewall.example.com:11111" spécifie une connexion sur le port 14321 (ou le port 4321 si 14321 est indisponible) à pmcd(1) sur l'hôte app23 via le port 11111 à pmproxy(1) sur l'hôte firewall.example.com.

Alternativement, pour un type de PM_CONTEXT_HOST, name peut être unix: pour une connexion à un socket de domaine Unix authentifié à pmcd(1) sur localhost ou local: pour une connexion authentifiée à pmcd(1) sur localhost via un socket de domaine Unix si disponible, sinon via une connexion à un socket Internet à localhost. local: est le choix par défaut pour la plupart des applications lors de l'appel à pmNewContext pour établir un contexte pour pmcd(1) sur l'hôte local.

Pour un type de PM_CONTEXT_ARCHIVE, chaque élément de la liste de noms dans name peut également être le nom de l'un des fichiers physiques d'une archive, par exemple myarchive.meta (le fichier de métadonnées) ou myarchive.index (l'index temporel) ou myarchive.0 (le premier volume de données de l'archive) ou myarchive.0.bz2 ou myarchive.0.bz (le premier volume de données compressé avec bzip2(1)) ou myarchive.0.gz ou myarchive.0.Z ou myarchive.0.z (le premier volume de données compressé avec gzip(1)), myarchive.1 ou myarchive.3.bz2 ou myarchive.42.gz etc.

Si plusieurs archives sont spécifiées pour un type de PM_CONTEXT_ARCHIVE, il existe certaines restrictions sur les archives au sein de l'ensemble :

  • Les archives doivent toutes avoir été générées sur le même hôte.
  • Les archives ne doivent pas se chevaucher dans le temps.
  • Les archives doivent toutes avoir été créées en utilisant le même fuseau horaire.
  • Le PMID de chaque métrique doit être le même dans toutes les archives. Plusieurs PMIDs sont actuellement tolérés en utilisant le premier PMID défini pour chaque métrique et en ignorant les PMIDs suivants.
  • Le type de chaque métrique doit être le même dans toutes les archives.
  • Les sémantiques de chaque métrique doivent être les mêmes dans toutes les archives.
  • Les unités de chaque métrique doivent être les mêmes dans toutes les archives.
  • Le domaine d'instance de chaque métrique doit être le même dans toutes les archives.

Dans le cas où type est PM_CONTEXT_LOCAL, name est ignoré, et le contexte utilise une connexion autonome aux méthodes PMDA utilisées par pmcd(1). Le mécanisme de la bibliothèque utilise la même architecture de « plugin » qui opère entre pmcd(1) et les PMDA DSO, de sorte que les opérations impliquent des appels de fonction plutôt que le passage de messages IPC - pour les contextes PM_CONTEXT_LOCAL, cela peut signifier une latence plus faible pour des opérations comme pmFetch(3), mais au prix d'un temps d'initialisation plus long et d'éventuelles différences de contrôle d'accès par rapport à pmcd(1). Lorsque ce type de contexte est utilisé, la gamme de métriques de performance accessibles est limitée à celles des PMDA DSO définies dans le fichier de configuration de pmcd(1) /etc/pcp/pmcd/pmcd.conf, donc celles rapportées par la commande


$ awk '$3 == "dso" {print}' /etc/pcp/pmcd/pmcd.conf

ou alternativement rapportées par la commande


$ pminfo -f pmcd.agent.type | grep 'value 0'

Cela signifie généralement les PMDA exportant les métriques du système d'exploitation et les « pmcd », « pmproxy » et peut inclure d'autres comme « mmv ». Des PMDA DSO alternatifs peuvent être utilisés, voir pmSpecLocalPMDA(3).

Dans le cas où type est PM_CONTEXT_HOST, des indicateurs supplémentaires peuvent être ajoutés à type pour indiquer si la connexion à pmcd(1) doit être chiffrée (PM_CTXFLAG_SECURE), doit être chiffrée si possible (PM_CTXFLAG_RELAXED), est différée (PM_CTXFLAG_SHALLOW), doit utiliser l'authentification (PM_CTXFLAG_AUTH), doit être une connexion à un conteneur (PM_CTXFLAG_CONTAINER), ou si le descripteur de fichier utilisé pour communiquer avec pmcd(1) ne doit pas être partagé entre les contextes (PM_CTXFLAG_EXCLUSIVE). Les indicateurs PM_CTXFLAG_SHALLOW et PM_CTXFLAG_EXCLUSIVE sont maintenant obsolètes et ignorés.

Lorsque type est PM_CONTEXT_ARCHIVE, des indicateurs supplémentaires peuvent être ajoutés à type pour une gestion restreinte de l'archive adaptée aux applications qui sont conscientes de la structure des archives PCP, à savoir PM_CTXFLAG_NO_FEATURE_CHECK (ne pas vérifier la compatibilité des fonctionnalités pour les enregistrements d'étiquette d'archive), PM_CTXFLAG_METADATA_ONLY (ouvrir uniquement les métadonnées, pas le(s) volume(s) de données ni l'index) et PM_CTXFLAG_LAST_VOLUME (ouvrir l'archive au début du *dernier* volume de données, au lieu du début du *premier* volume de données par défaut).

Plusieurs indicateurs peuvent être spécifiés en combinant par « ou logique » les macros PM_CTXFLAG, mais toutes les combinaisons n'ont pas de sens, par exemple si PM_CTXFLAG_METADATA_ONLY et PM_CTXFLAG_LAST_VOLUME sont spécifiés, PM_CTXFLAG_METADATA_ONLY a la priorité.

Le profil d'instance initial est configuré pour sélectionner toutes les instances dans tous les domaines d'instance. Dans le cas d'un ensemble d'archives, l'heure de collecte initiale est également mise à zéro, de sorte qu'un appel initial à pmFetch(3) résultera en l'ensemble le plus ancien de métriques renvoyé à partir de l'ensemble d'archives.

Une fois établi, l'association entre un contexte et une source de métriques est fixe pour la durée de vie du contexte, cependant des routines sont fournies pour manipuler indépendamment le profil d'instance (voir pmAddProfile(3) et pmDelProfile(3)) et l'heure de collecte pour les archives (voir pmSetMode(3)).

pmNewContext renvoie un handle qui peut être utilisé avec des appels ultérieurs à pmUseContext(3).

Le nouveau contexte reste le contexte PMAPI actuel pour tous les appels ultérieurs dans la PMAPI, jusqu'à ce qu'un autre appel à pmNewContext(3) soit effectué, ou que le contexte soit explicitement changé avec un appel à pmDupContext(3) ou pmUseContext(3), ou détruit en utilisant pmDestroyContext(3).

Lorsqu'on tente de se connecter à un pmcd(1) distant sur une machine qui est en cours de démarrage, pmNewContext pourrait potentiellement bloquer pendant longtemps jusqu'à ce que la machine distante ait terminé son initialisation. pmNewContext abandonnera et renverra une erreur si la connexion n'a pas été établie après qu'un certain intervalle spécifié se soit écoulé. L'intervalle par défaut est de 5 secondes. Ceci peut être modifié en définissant PMCD_CONNECT_TIMEOUT dans l'environnement à un nombre réel de secondes pour le délai d'attente désiré. pmNewContext(3)

NAME

pmNewContext, pmDupContext, pmDestroyContext, pmUseContext, pmWhichContext, pmReconnectContext - create, duplicate, destroy, make current, find current, and reconnect a Performance Metrics Context

C SYNOPSIS

#include <pcp/pmapi.h>

int pmNewContext(int type, const char *uri, ...);
int pmDupContext(int ctxt);
int pmDestroyContext(int ctxt);
int pmUseContext(int ctxt);
int pmWhichContext(void);
int pmReconnectContext(int ctxt, const char *uri, ...);

DESCRIPTION

These routines are used to manage the Performance Metrics Application Program Interface (PMAPI) contexts. A PMAPI context is a connection to a source of performance metrics, which may be the current system, a remote system via the Performance Co-Pilot Performance Metrics Collection Daemon (PMCD), or a set of performance metrics archives. The PMAPI(3) functions operate within the context specified by the current context handle. Initially, and after pmCleanup(3), the current context is PM_CONTEXT_LOCAL, providing access to the performance metrics on the local host via the Performance Metrics Data Access Library (PMDAs) for the local host.

pmNewContext may be used to create a new PMAPI context. The type parameter specifies the context type:

PM_CONTEXT_LOCAL
Connect to the PMDAs for the local host. This is the default context and is used to access performance metrics directly from the kernel and other local system agents. The uri argument should be NULL.
PM_CONTEXT_HOST
Connect to a remote PMCD. The uri argument should be the hostname or IP address of the remote host. A port number may be specified as part of the URI, separated by a colon, e.g., "remote.server.com:44321". The default port is defined by the ENVIRONMENT variable PMCD_PORT, or 44321 if not specified. This connection is established using TCP/IP sockets.
PM_CONTEXT_ARCHIVE
Connect to a set of performance metrics archives. The uri argument should be the name of the directory containing the archives or the name of a single archive file. If uri is a directory, it is assumed to be a Performance Co-Pilot archive directory, and all archives within that directory will be used. The ... argument can be used to pass additional archive names or pointers to archive files. Archives are processed in the order specified, and are used to replay performance metrics data.

The pmNewContext function returns a context handle, which is a non-negative integer. This handle must be used in subsequent calls to other PMAPI functions that operate on this specific context. If an error occurs, a negative value is returned, indicating the error code.

pmDupContext duplicates an existing context handle ctxt. It returns a new handle that refers to the same context source. This can be useful for sharing a context among different parts of an application.

pmDestroyContext closes the connection associated with the context handle ctxt and frees any associated resources. The handle ctxt becomes invalid after this call.

pmUseContext sets the context handle ctxt as the current context for subsequent PMAPI calls. It returns the previous current context handle.

pmWhichContext returns the handle of the current context.

pmReconnectContext attempts to re-establish a connection to the context source specified by ctxt. This is typically used when a connection has been lost (e.g., due to network issues or PMCD restarts). The uri parameter can be used to specify a new connection point if necessary. If uri is NULL, it attempts to reconnect to the original connection point.

When using PM_CONTEXT_HOST, there may be significant latency in establishing the connection, especially across slower network links. The default connection timeout is controlled by the PMCD_CONNECT_TIMEOUT environment variable.

CAVEATS

When using a type of PM_CONTEXT_LOCAL, the operating system PMDA may export data structures directly from the kernel, which means that the pmNewContext caller should be an executable program compiled for the same object code format as the booted kernel.

In addition, applications using a PM_CONTEXT_LOCAL context must be single-threaded because the various DSO PMDAs may not be thread-safe. This restriction is enforced at the PMAPI(3), where routines may return the error code PM_ERR_THREAD if the library detects calls from more than one thread.

Applications that use gethostbyname(3) should exercise caution because the static fields in struct hostent may not be preserved across some PMAPI(3) calls. In particular, pmNewContext(3) and pmReconnectContext(3) both may call gethostbyname(3) internally.

DIAGNOSTICS

PM_ERR_PERMISSION

No permission to perform requested operation

PM_ERR_CONNLIMIT

PMCD connection limit for this host exceeded

PM_ERR_NOCONTEXT

Requested context type was not PM_CONTEXT_LOCAL, PM_CONTEXT_HOST or PM_CONTEXT_ARCHIVE.

PM_ERR_LOGOVERLAP

Archives overlap in time

PM_ERR_LOGHOST

Archives differ by host

PM_ERR_LOGCHANGETYPE

The type of a metric differs among archives

PM_ERR_LOGCHANGESEM

The semantics of a metric differs among archives

PM_ERR_LOGCHANGEINDOM

The instance domain of a metric differs among archives

PM_ERR_LOGCHANGEUNITS

The units of a metric differs among archives

ENVIRONMENT

PMCD_CONNECT_TIMEOUT
Timeout period (in seconds) for pmcd(1) connection attempts.
PMCD_PORT
TCP/IP port(s) for connecting to pmcd(1), historically was 4321 and more recently the officially registered port 44321; in the current release, pmcd listens on both these ports as a transitional arrangement. If used, should be set to a comma-separated list of numerical port numbers.
