NOM

pmdaCacheStore, pmdaCacheStoreKey, pmdaCacheLookup, pmdaCacheLookupName, pmdaCacheLookupKey, pmdaCacheOp, pmdaCachePurge, pmdaCachePurgeCallback, pmdaCacheResize - gérer un cache d'informations de domaine d'instances pour un PMDA

int op);

int pmdaCacheResize(pmInDom indom,

cc ... -lpcp_pmda -lpcp

DESCRIPTION

Les routines de la famille pmdaCache fournissent des services pour supporter la maintenance de domaines d'instances complexes pour les PMDA de Performance Co-Pilot. Il y a potentiellement un cache d'informations pour chaque domaine d'instances, et pour chaque instance le cache maintient :

  • nom d'instance externe (fourni par le PMDA)
  • identifiant d'instance interne (assigné par pmdaCacheStore ou calculé à partir d'un « hint » par pmdaCacheStoreKey)
  • état, où les instances actives sont visibles et font partie du domaine d'instances actuel, et les instances inactives sont cachées, mais pas oubliées ; pmdaCacheStore ou pmdaCacheStoreKey peuvent être utilisés pour changer l'état d'une instance
  • un pointeur opaque optionnel vers des données associées à l'instance, mais maintenues par le PMDA
  • une clé opaque optionnelle utilisée comme « hint » pour pmdaCacheStoreKey lors de l'estimation de l'identifiant d'instance interne initial
  • la dernière fois que le cache a été sauvegardé et que l'instance avait été marquée comme active à un moment donné depuis la dernière opération de chargement ou de sauvegarde du cache

Les sémantiques d'un domaine d'instances PCP nécessitent que plusieurs règles soient suivies, à savoir :

1.
Chaque identifiant d'instance interne doit être unique et dans l'intervalle 0 à 2^31 - 1. Cette règle est appliquée par la famille de routines pmdaCache.
2.
Le nom d'instance externe doit être unique. Lorsque le nom d'instance contient un espace, il est davantage contraint de telle sorte que le nom à gauche du premier espace (le nom court) doit également être unique. Voir la section CORRESPONDANCE DE NOM D'INSTANCE ci-dessous. Le PMDA doit respecter cette règle, la famille de routines pmdaCache détectera les tentatives de violation de cette règle.
3.
Là où un nom d'instance externe correspond à un objet ou une entité, il y a une attente que l'association entre le nom et l'objet soit fixe, par exemple ``/dev/hda'' est toujours le nom du même disque sur un système particulier. Cette règle est peut-être la responsabilité du PMDA, mais est souvent une caractéristique de l'environnement dans lequel le PMDA fonctionne.
4.
Il est préférable, bien que non obligatoire, que l'association entre un nom d'instance externe et un identifiant d'instance interne soit persistante. Cette règle est supportée par la famille de routines pmdaCache.
5.
Lorsque des clés opaques sont utilisées, les valeurs des clés doivent être uniques pour toutes les instances dans un domaine d'instances. Cette règle est appliquée par la famille de routines pmdaCache.

L'interface visible du cache est orientée vers le développeur de PMDA qui est le plus concerné par les noms des instances, tandis que les détails sur la façon dont le reste de l'infrastructure PCP attend que les identifiants d'instances internes soient gérés ne sont pas pertinents.

Les instances sont mises à jour dans le cache pour le domaine d'instances indom en appelant pmdaCacheStore ou pmdaCacheStoreKey avec le nom externe de l'instance passé via name. Le pointeur opaque private peut être utilisé pour associer des données supplémentaires à l'entrée dans le cache ; si aucune donnée de ce type n'est requise, private doit être NULL. Toute manipulation des données supplémentaires (y compris leur allocation ou libération) est la responsabilité de l'appelant du PMDA, car le cache maintient simplement le pointeur vers les données (passé via private).

La limite supérieure pour les identifiants alloués pour un cache indom donné peut être optionnellement réduite par défaut (2^31 - 1) à un maximum inférieur, en utilisant pmdaCacheResize. Ce maximum sera alors persisté et restauré de la manière habituelle, et peut ainsi être associé de manière permanente à un cache une fois défini. Ceci a des applications lors de l'utilisation de ces interfaces comme caches d'identifiants à usage général, et est moins applicable lorsqu'elles sont utilisées pour la mise en cache de domaines d'instances.

Dans les cas où le développeur de PMDA souhaite influencer l'allocation des identifiants d'instances internes, par exemple pour des domaines d'instances ayant plus d'une dimension naturelle, ou lorsqu'il y a un désir d'allouer le même identifiant d'instance à chaque démarrage du PMDA, même sur des hôtes différents, pmdaCacheStoreKey peut être utilisé. Dans ce cas, un « hint » initial pour l'identifiant d'instance est fourni sous forme de clé opaque via les keylen premiers octets de key (qui pourraient être de n'importe quel type de données, y compris des valeurs binaires) sinon si keylen est inférieur à 1 ou key est NULL alors name est utilisé comme « hint ». Le « hint » est haché pour produire un identifiant d'instance initial dans l'intervalle 0 à 2^31 - 1 (ou un maximum inférieur, s'il est défini). Si cet identifiant d'instance est déjà alloué, alors la valeur est re-hachée. Cette procédure est répétée jusqu'à ce qu'un identifiant d'instance non alloué soit trouvé, ou que pmdaCacheStoreKey échoue et retourne PM_ERR_GENERIC. Pour chaque domaine d'instances, le « hint » doit être unique pour toutes les instances, sinon pmdaCacheStoreKey retourne PM_ERR_INST.

L'argument flags contrôle comment l'instance doit être traitée dans le cache comme suit :

PMDA_CACHE_ADD
Insérer l'entrée dans le cache si elle n'y est pas déjà et la marquer comme active. Si l'entrée est déjà dans le cache, la marquer comme active.
PMDA_CACHE_HIDE
Marquer l'entrée dans le cache comme inactive, mais se souvenir des détails de l'association entre le nom d'instance externe et l'identifiant d'instance interne. Les entrées inactives seront cachées de la traversée du cache via les opérations PMDA_CACHE_WALK_NEXT, mais resteront visibles pour les requêtes pmdaCacheLookup, pmdaCacheLookupName et pmdaCacheLookupKey.
PMDA_CACHE_CULL
Supprimer l'entrée du cache.

En cas de succès, pmdaCacheStore ou pmdaCacheStoreKey retourneront l'identifiant d'instance interne de l'entrée de cache associée. Les identifiants d'instances valides sont garantis uniques et non négatifs. L'échec sera indiqué par une valeur négative (adaptée pour être décodée avec pmErrStr(3)) et très probablement PM_ERR_INST pour indiquer que l'instance demandée n'est pas dans le cache, ou -EINVAL pour indiquer une violation potentielle de la propriété d'unicité du nom court (voir la section CORRESPONDANCE DE NOM D'INSTANCE ci-dessous).

pmdaCacheLookup est utilisé pour rechercher les entrées dans le cache en se basant sur l'identifiant d'instance interne inst.

En cas de succès, la valeur de retour sera PMDA_CACHE_ACTIVE ou PMDA_CACHE_INACTIVE (selon l'état actif ou inactif de l'entrée du cache), name (si non NULL) et private (si non NULL) seront définis sur le nom d'instance externe et les données associées

L'échec de pmdaCacheLookup est indiqué par une valeur de retour négative adaptée au décodage avec pmErrStr(3).

L'interface pmdaCacheLookup est requise par le rappel de récupération (fetch callback) du PMDA, qui est enregistré via pmdaSetFetchCallBack(3). Ici, l'identifiant d'instance interne est passé au rappel de récupération pour identifier l'instance pour laquelle une valeur est requise. L'utilisation typique est montrée dans le fragment de code ci-dessous.

static int
foo_callback(pmdaMetric *mdesc, unsigned int inst, pmAtomValue *atom)
{
    mydata   *mdp;
    char     *name;
    int      sts;
    sts = pmdaCacheLookup(mdesc->m_desc.indom, inst, &name, (void **)&mdp);
    /*
     * on s'attend à ce que sts == PMDA_CACHE_ACTIVE sauf en cas d'événements cataclysmiques
     * utiliser mdp comme requis, name peut être utile pour le diagnostic
     */
    ...


pmdaCacheLookupName est utilisé pour rechercher les entrées dans le cache en se basant sur le nom d'instance externe name.

En cas de succès, la valeur de retour sera PMDA_CACHE_ACTIVE ou PMDA_CACHE_INACTIVE (selon l'état actif ou inactif de l'entrée du cache), inst (si non NULL) et private (si non NULL) seront définis sur l'identifiant d'instance interne et la zone de données supplémentaire associée fournie lors de la dernière activation de l'instance via pmdaCacheStore ou pmdaCacheStoreKey.

L'échec de pmdaCacheLookupName est indiqué par une valeur de retour négative adaptée au décodage avec pmErrStr(3).

L'interface pmdaCacheLookupName est utile pour les PMDA souhaitant mettre à jour un domaine d'instance basé sur les noms d'instance externes.

pmdaCacheLookupKey est utilisé pour rechercher les entrées dans le cache en se basant sur une clé opaque (ou "indice") précédemment utilisée dans un appel à pmdaCacheStoreKey. L'"indice" est fourni via les keylen premiers octets de key. Par symétrie avec pmdaCacheStoreKey, si keylen est inférieur à 1 ou si key est NULL, alors name est utilisé comme "indice" (bien que les résultats soient les mêmes qu'en appelant pmdaCacheLookupName dans ce cas).

En cas de succès, la valeur de retour sera PMDA_CACHE_ACTIVE ou PMDA_CACHE_INACTIVE (selon l'état actif ou inactif de l'entrée du cache), oname (si non NULL), inst (si non NULL) et private (si non NULL) seront définis sur le nom d'instance externe, l'identifiant d'instance interne et la zone de données supplémentaire associée fournie lors de la dernière activation de l'instance via pmdaCacheStore ou pmdaCacheStoreKey.

L'échec de pmdaCacheLookupKey est indiqué par une valeur de retour négative adaptée au décodage avec pmErrStr(3).

Pour éviter qu'un cache persistant ne croisse sans limite, pmdaCachePurge peut être utilisé pour supprimer toutes les entrées qui n'ont pas été actives au cours des recent dernières secondes. Pour des raisons de performance, la comptabilisation du temps est imprécise et les entrées sont horodatées au moment de la prochaine opération de sauvegarde du cache *après* que l'entrée ait été ajoutée ou marquée comme active (voir ci-dessous PMDA_CACHE_SAVE, PMDA_CACHE_WRITE et PMDA_CACHE_SYNC). En cas de succès, pmdaCachePurge retourne le nombre d'entrées supprimées, sinon, en cas d'erreur, la valeur de retour est négative (et adaptée au décodage avec pmErrStr(3)).

La fonction pmdaCachePurgeCallback est similaire à pmdaCachePurge, sauf qu'une fonction de *rappel* (callback) sera également appelée avec le pointeur de données *private* associé à l'entrée du cache à supprimer. Le rappel n'est pas effectué si *private est* NULL. Ceci serait typiquement utilisé pour libérer les données privées lorsque l'entrée associée est purgée dans les PMDA qui ne maintiennent pas séparément de références aux données privées.

pmdaCacheOp peut être utilisé pour effectuer des opérations supplémentaires sur le cache comme suit :

PMDA_CACHE_LOAD
Le cache peut être facultativement maintenu sous forme de fichier externe persistant, de sorte que le mappage des noms d'instance aux identifiants d'instance soit persistant à travers les exécutions d'un PMDA. Cette opération charge le cache depuis le fichier externe, puis toutes les nouvelles entrées du cache sont marquées comme inactives, et le pointeur de données supplémentaire est défini sur NULL. Les entrées chargées depuis le fichier externe sont vérifiées par rapport au contenu actuel du cache et si le nom d'instance et les identifiants d'instance correspondent, l'état dans le cache (actif ou inactif) n'est pas modifié. Si une discordance est trouvée (même nom d'instance et identifiant d'instance différent, ou même identifiant d'instance et nom d'instance différent, ou seulement une partie de l'identifiant d'instance, du nom d'instance et de l'"indice" correspondent), alors l'entrée du fichier externe est ignorée et un avertissement est émis sur stderr. Typiquement, un PMDA n'effectuerait cette opération qu'une seule fois par exécution.
PMDA_CACHE_SAVE
Si une instance a été ajoutée au domaine d'instance ou en a été supprimée depuis la dernière opération PMDA_CACHE_LOAD, PMDA_CACHE_SAVE, PMDA_CACHE_WRITE ou PMDA_CACHE_SYNC, l'*intégralité* du cache est écrite dans le fichier externe en une seule opération groupée. Cette opération est fournie pour les PMDA qui ne souhaitent *pas* utiliser pmdaCachePurge et veulent simplement que le fichier externe reflète l'ensemble des instances connues sans détails précis sur quand elles ont été marquées comme actives.

Retourne le nombre d'instances enregistrées dans le fichier externe, sinon 0 si le fichier externe était déjà à jour.

PMDA_CACHE_WRITE
Une variante de PMDA_CACHE_SAVE où l'*intégralité* du cache est inconditionnellement écrite dans le fichier externe en une seule opération groupée, indépendamment de toute opération de cache précédente ou de l'état du cache.
PMDA_CACHE_STRINGS
Annote ce cache comme étant un cache spécialisé utilisé pour la déduplication de chaînes dans les PMDA exportant un grand nombre de métriques à valeur de chaîne. Ceci peut être utilisé pour réduire l'empreinte mémoire du PMDA (les chaînes dupliquées convergent vers le même bucket et ne sont stockées en mémoire qu'une seule fois). Les comparaisons de clés ne sont pas terminées au premier espace mais toute la chaîne est utilisée pour la mise en correspondance. Ce sont des caches spécialisés qui ne sont pas utiles pour la gestion générale des domaines d'instance.
PMDA_CACHE_SYNC
Dans un domaine d'instance, si une instance a été ajoutée, supprimée, ou marquée comme active depuis la dernière opération PMDA_CACHE_LOAD, PMDA_CACHE_SAVE, PMDA_CACHE_WRITE ou PMDA_CACHE_SYNC, l'*intégralité* du cache est écrite dans le fichier externe en une seule opération groupée. Cette opération est similaire à PMDA_CACHE_SAVE, mais sauvegarde le domaine d'instance plus fréquemment, de sorte que les horodatages correspondent plus précisément aux sémantiques attendues par pmdaCachePurge.

Retourne le nombre d'instances enregistrées dans le fichier externe, sinon 0 si le fichier externe était déjà synchronisé.

PMDA_CACHE_CHECK
Retourne 1 si un cache existe pour le domaine d'instance spécifié, sinon 0.
PMDA_CACHE_REUSE
Lorsqu'une nouvelle instance est ajoutée au cache, la stratégie par défaut consiste à attribuer des identifiants d'instance de manière croissante et monotone. Une fois que la valeur maximale possible de l'identifiant d'instance a été attribuée, la stratégie change pour utiliser le prochain identifiant d'instance inutilisé à partir de 0. Appeler pmdaCacheOp avec PMDA_CACHE_REUSE force un changement irréversible vers une seconde stratégie (réutilisation) où le prochain identifiant d'instance non alloué sera utilisé. Cela peut être utile dans les cas où il y a un désir de limiter les identifiants d'instance alloués à des valeurs plus petites. La stratégie en vigueur sera sauvegardée et restaurée lors des opérations PMDA_CACHE_SAVE et PMDA_CACHE_LOAD. Si pmdaCacheStoreKey est jamais utilisé, le domaine d'instance associé sera changé en mode PMDA_CACHE_REUSE.
PMDA_CACHE_REORG
Réorganise le cache pour permettre une récupération plus rapide des entrées actives, au détriment d'une récupération plus lente des entrées inactives, et récupère toutes les entrées supprimées. Le cache peut être réorganisé en interne au fur et à mesure que les entrées sont ajoutées, donc cette opération n'est pas requise pour la plupart des PMDA.
PMDA_CACHE_WALK_REWIND
Prépare une traversée du cache dans l'ordre croissant des identifiants d'instance.
PMDA_CACHE_WALK_NEXT
Récupère le prochain identifiant d'instance actif du cache. Nécessite un appel préalable utilisant PMDA_CACHE_WALK_REWIND et retournera -1 lorsque toutes les instances auront été traitées.

Une seule traversée de cache peut être active à la fois ; les appels imbriqués à PMDA_CACHE_WALK_NEXT et PMDA_CACHE_WALK_REWIND s'interféreront mutuellement.

PMDA_CACHE_ACTIVE
Change chaque entrée inactive du cache pour qu'elle soit marquée comme active.
PMDA_CACHE_INACTIVE
Change chaque entrée active du cache pour qu'elle soit marquée comme inactive.
PMDA_CACHE_CULL
Supprime chaque entrée du cache.
PMDA_CACHE_SIZE
Retourne le nombre d'entrées dans le cache (inclut les entrées actives, inactives et celles qui ont été supprimées mais pas encore récupérées).
PMDA_CACHE_SIZE_ACTIVE
Retourne le nombre d'entrées actives dans le cache.
PMDA_CACHE_SIZE_INACTIVE
Retourne le nombre d'entrées inactives dans le cache.
PMDA_CACHE_DUMP
Affiche l'état actuel du cache sur stderr.
PMDA_CACHE_DUMP_ALL
Similaire à PMDA_CACHE_DUMP , mais aussi de décharger les structures de hachage internes utilisées pour le support de la recherche par nom d'instance, par identifiant d'instance et les statistiques de collision pour le hachage par « hint » de pmdaCacheStoreKey.

pmdaCacheOp retourne une valeur non négative en cas de succès, et l'échec est indiqué par une valeur de retour négative (adaptée au décodage avec pmErrStr(3)).

AUTRES CONSIDÉRATIONS

Lorsque les routines pmdaCache sont utilisées pour un domaine d'instance particulier, pmdaInstance(3) et l'énumération du domaine d'instance derrière pmdaFetch(3) tenteront d'extraire les informations du domaine d'instance à partir du cache, évitant ainsi de faire référence aux structures de données pmdaIndom qui ont été historiquement utilisées pour définir les domaines d'instance et servir les requêtes d'instance. Un PMDA peut adopter une approche hybride et choisir d'implémenter certains domaines d'instance via la méthode traditionnelle pmdaIndom, et d'autres via l'approche pmdaCache ; cependant, les tentatives de gestion du *même* domaine d'instance par les deux méthodes entraîneront la prédominance silencieuse de la méthode pmdaCache.

Si *toutes* les instances d'un PMDA doivent être gérées à partir d'un pmdaCache, alors un pmdaIndom n'est pas requis, et l'appel pmdaInit(3) devient


    pmdaInit(dp, NULL, 0, metrictab, nmetrics);

Cependant, le PMDA devra initialiser explicitement le champ indom de la pmDesc dans les entrées de *metrictab*, car cela ne peut pas être fait par pmdaInit(3) si *indomtab* contient des entrées manquantes pour les domaines d'instance maintenus dans le cache.

Indépendamment de la manière dont le domaine d'instance est maintenu, pour rafraîchir un domaine d'instance avant une récupération ou une opération sur le domaine d'instance, les méthodes standard d'un « wrapper » pour les méthodes pmdaInstance(3) et pmdaFetch(3) doivent être utilisées.

Se référer au code source du PMDA simple pour un exemple d'utilisation des routines pmdaCache.

Lors de l'utilisation de pmdaCacheStoreKey, si le désir est de s'assurer que le « hint » donné génère le même identifiant d'instance initial sur toutes les plateformes, alors l'appelant doit s'assurer que les problèmes d'endianness et de taille de mot sont pris en compte ; par exemple, si la structure de données naturelle utilisée pour la *clé* est un tableau d'entiers de 32 bits, alors htonl(3) doit être utilisé sur chaque élément du tableau avant d'appeler pmdaCacheStoreKey ou pmdaCacheLookupKey.

FICHIERS

La persistance du cache utilise des fichiers dont les noms sont construits à partir de l'*indom* dans le répertoire $PCP_VAR_DIR/config/pmda.
