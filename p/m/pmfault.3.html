PMFAULT(3) Manuel des fonctions de bibliothèque PMFAULT(3)

NOM

__pmFaultInject, __pmFaultSummary, PM_FAULT_POINT, PM_FAULT_RETURN, PM_FAULT_CHECK, PM_FAULT_CLEAR - Infrastructure d'injection de fautes pour le contrôle qualité

SYNTAXE C

#include <pcp/pmapi.h>
#include <pcp/fault.h>

void __pmFaultInject(const char *ident, int class);
void __pmFaultSummary(FILE *f);

PM_FAULT_POINT(ident, class);
PM_FAULT_RETURN(retvalue);
PM_FAULT_CHECK;
PM_FAULT_CLEAR;

cc -DPM_FAULT_INJECTION=1 ... -lpcp_fault

DESCRIPTION

Dans le cadre des changements pilotés par la couverture du contrôle qualité dans PCP 3.6, il est devenu apparent que nous avions besoin d'un moyen d'exercer les chemins de code "inhabituels" associés à la détection et à la récupération d'erreurs.

Les installations décrites ci-dessous fournissent une infrastructure de base pour l'injection de fautes (uniquement pour libpcp pour le moment, bien que le mécanisme soit beaucoup plus général et puisse être facilement étendu).

Une construction spéciale est requise pour créer libpcp_fault et le fichier d'en-tête <pcp/fault.h> associé. Une fois cela fait, de nouvelles applications de contrôle qualité peuvent être construites avec -DPM_FAULT_INJECTION=1 et/ou des applications existantes peuvent être exercées en présence d'injection de fautes en forçant libpcp_fault à être utilisée de préférence à libpcp, comme décrit ci-dessous.

Dans le code à tester, __pmFaultInject définit un point de faute où une faute de type class peut être injectée. ident est une chaîne de caractères permettant d'identifier de manière unique le point de faute dans tout le code source de PCP, donc quelque chose comme "libpcp/" __FILE__ ":<nombre>" fonctionne très bien. La chaîne ident détermine également si une faute sera injectée ou non au moment de l'exécution - voir la section CONTRÔLE À L'EXÉCUTION ci-dessous. class sélectionne un type de défaillance, en utilisant l'une des valeurs définies suivantes (cette liste pourrait bien s'allonger avec le temps) :

PM_FAULT_ALLOC
Provoquera l'échec du prochain appel à malloc(3), realloc(3) ou strdup(3), retournant NULL et définissant errno à ENOMEM. Nous pourrions étendre la couverture à toutes les routines liées à malloc, mais ces trois sont suffisantes pour couvrir la grande majorité des utilisations dans libpcp.
PM_FAULT_CALL
Provoquera l'échec du prochain appel à une routine instrumentée en retournant un code d'erreur (possiblement le nouveau code PM_ERR_FAULT). Le code d'erreur réel est défini dans la macro PM_FAULT_RETURN au début d'une routine instrumentée. Initialement, seuls __pmRegisterAnon(3) (retourne PM_ERR_FAULT), __pmGetPDU(3) (retourne PM_ERR_TIMEOUT) et __pmAllocResult(3) (retourne NULL) étaient instrumentés comme preuve de concept pour cette partie de l'installation, cependant d'autres routines pourraient avoir cette capacité d'injection de faute ajoutée au fil du temps.
PM_FAULT_MISC
La classe "autre", actuellement utilisée avec PM_FAULT_CHECK comme décrit ci-dessous.

Pour permettre à l'injection de fautes de coexister dans le code source de production, PM_FAULT_POINT est une macro qui n'émet aucun code par défaut, mais lorsque PM_FAULT_INJECTION est définie, cela devient un appel à __pmFaultInject. Partout dans libpcp, nous utilisons PM_FAULT_POINT et non __pmFaultInject afin que libpcp et libpcp_fault puissent être construits à partir du même code source.

De même, la macro PM_FAULT_RETURN n'émet aucun code à moins que PM_FAULT_INJECTION ne soit définie, auquel cas, si une faute de type PM_FAULT_CALL a été armée avec __pmFaultInject, la routine englobante retourne avec la valeur de fonction retvalue.

La macro PM_FAULT_CHECK retourne une valeur qui peut être 0 ou 1. Si PM_FAULT_INJECTION est définie, alors si une faute de type PM_FAULT_MISC a été armée avec __pmFaultInject, la valeur est 1 sinon elle est 0.

PM_FAULT_CHECK est le plus souvent utilisée conjointement avec la macro PM_FAULT_POINT avec la classe PM_FAULT_MISC pour armer potentiellement un déclencheur, puis tester PM_FAULT_CHECK et si cela a la valeur 1, alors la macro PM_FAULT_CLEAR est utilisée pour effacer toutes les fautes armées, et le code d'injection de faute est exécuté.

Ceci est illustré dans l'exemple ci-dessous de src/libpcp/src/exec.c :

    pid = fork();
    /* début du bloc d'injection de faute */
    PM_FAULT_POINT("libpcp/" __FILE__ ":4", PM_FAULT_MISC);
    if (PM_FAULT_CHECK) {
	PM_FAULT_CLEAR;
	if (pid > (pid_t)0)
	    kill(pid, SIGKILL);
	setoserror(EAGAIN);
	pid = -1;
    }
    /* fin du bloc d'injection de faute */

Un résumé des points de faute rencontrés et des fautes injectées est produit sur le flux stdio f par __pmFaultSummary.

Un traçage supplémentaire (via -Dfault ou pmDebugOptions.fault) et un nouveau code d'erreur PMAPI (PM_ERR_FAULT) sont également définis, bien que ceux-ci ne seront jamais vus ou utilisés que dans libpcp_fault. Si pmDebugOptions.fault est défini lors du premier appel à __pmFaultInject, alors __pmFaultSummary sera appelé automatiquement pour faire un rapport sur stderr à la sortie de l'application (via atexit(3)).

L'injection de fautes ne peut pas être imbriquée. Chaque appel à __pmFaultInject efface toute injection de faute précédente qui a été armée, mais pas encore exécutée.

L'infrastructure d'injection de fautes n'est pas thread-safe et ne doit être utilisée qu'avec des applications connues pour être monothread.

CONTRÔLE À L'EXÉCUTION

Par défaut, aucune injection de faute n'est activée à l'exécution, même lorsque __pmFaultInject est appelée.

Les fautes sont activées sélectivement à l'aide d'un fichier de contrôle, identifié par la variable d'environnement $PM_FAULT_CONTROL ; si elle n'est pas définie, aucune faute n'est activée.

Le fichier de contrôle (s'il existe) est lu la première fois que __pmFaultInject est appelé, et contient des lignes de la forme : ident op nombre
qui définissent des gardes d'injection de faute.

ident est une chaîne de point de faute (telle que définie par un appel à __pmFaultInject, ou plus couramment la macro PM_FAULT_POINT). Il faut donc avoir accès au code source de libpcp pour déterminer les chaînes ident disponibles et leurs sémantiques.

op est l'un des opérateurs de style C >=, >, ==, <, <=, != ou % et nombre est un entier non signé. op nombre est facultatif et la valeur par défaut est >0

La sémantique des gardes d'injection de faute est que chaque fois que __pmFaultInject est appelée pour un ident particulier, un compteur de déclenchement est incrémenté (le premier déclenchement est 1) ; si l'expression de style C compteur_de_déclenchement op nombre a la valeur 1 (donc vrai pour la plupart des ops, ou le reste est égal à 1 pour l'opérateur %), alors une faute du class défini pour le point de faute associé à ident sera armée, et exécutée dès que possible.

Dans le fichier de contrôle, les lignes vides sont ignorées et les lignes commençant par # sont traitées comme des commentaires.

Pour une application existante liée avec libpcp, l'injection de fautes peut toujours être utilisée en forçant libpcp_fault à être utilisée à la place de libpcp. L'exemple suivant montre comment cela peut être fait.

$ export PM_FAULT_CONTROL=/tmp/control
$ cat $PM_FAULT_CONTROL
# ok pour 2 déclenchements, puis injecter des erreurs

$ export LD_PRELOAD=/usr/lib/libpcp_fault.so

EXEMPLES

Se référer au code source de PCP et PCP QA.

Les définitions de macros se trouvent dans src/include/pcp/fault.h.

src/libpcp/src/fault.c contient toute l'implémentation sous-jacente.

src/libpcp_fault et src/libpcp_fault/src contiennent la recette et les Makefiles pour créer et installer libpcp_fault.so et <pcp/fault.h>.

PM_FAULT_RETURN a été initialement utilisé dans les fichiers source libpcp suivants : derive_parser.y.in, pdu.c et result.c.

PM_FAULT_POINT. a été initialement utilisé dans les fichiers source libpcp suivants : derive_parser.y.in, desc.c, e_indom.c, e_labels.c, err.c, events.c, exec.c, fetch.c, help.c, instance.c, interp.c, labels.c, logmeta.c, pmns.c, p_profile.c et store.c.

Le groupe de tests QA ``fault'' montre des exemples d'utilisation de fichiers de contrôle. Pour voir quels tests sont impliqués

$ cd qa
$ check -n -g fault

DIAGNOSTICS

Certaines erreurs non récupérables sont signalées sur stderr.

LD_PRELOAD
