PMDAOPENMETRICS(1) Manuel des commandes générales PMDAOPENMETRICS(1)

NOM

pmdaopenmetrics - PMDA OpenMetrics

SYNTAXE

$PCP_PMDAS_DIR/openmetrics/pmdaopenmetrics [-D] [-n] [-c config] [-d domaine] [-l fichier_journal] [-R delai_rafraichissement] [-r racine] [-t delai] [-u utilisateur]

DESCRIPTION

pmdaopenmetrics est un agent de domaine de métriques de performance (PMDA) qui crée dynamiquement des métriques PCP à partir de points d'accès OpenMetrics configurés, lesquels fournissent un accès basé sur HTTP aux métriques des applications. Le PMDA implémente essentiellement un pont entre Prometheus et PCP, permettant à PCP d'ingérer facilement des données de performance provenant de plus de 650 points d'accès enregistrés et de nombreux autres points d'accès spécifiques aux applications.

Le répertoire de configuration config par défaut est $PCP_PMDAS_DIR/openmetrics/config.d/, voir « SOURCES DE CONFIGURATION » ci-dessous. Le délai delai par défaut pour récupérer les URL est de 2 secondes. L'utilisateur utilisateur par défaut, s'il n'est pas spécifié avec l'option -u, est l'utilisateur courant. Si l'option -n est donnée, la liste des fichiers de configuration ne sera pas triée avant d'être traitée. Cette liste est triée par défaut, mais cela peut être coûteux s'il y a un grand nombre de fichiers de configuration (URL et/ou scripts).

Si l'option -D est donnée, des messages de diagnostic supplémentaires seront écrits dans le fichier journal du PMDA, qui est $PCP_LOG_DIR/pmcd/openmetrics.log par défaut (voir également ci-dessous -l). De plus, la métrique openmetrics.control.debug contrôle le même indicateur de débogage et peut être définie avec la commande suivante :

pmstore openmetrics.control.debug valeur

où valeur est soit 1 (pour activer les messages de journalisation verbeux) soit 0 (pour désactiver les messages de journalisation verbeux). Ceci est particulièrement utile pour examiner les en-têtes HTTP passés à chaque requête de récupération, les paramètres de filtrage et autres détails de traitement qui sont enregistrés lorsque l'indicateur de débogage est activé.

L'option -d peut être utilisée pour remplacer le numéro de domaine des métriques de performance par défaut, qui est 144. Il est fortement recommandé de ne pas le changer. Le numéro de domaine doit être différent pour chaque PMDA sur le même hôte, et le même numéro de domaine doit être utilisé pour le PMDA pmdaopenmetrics sur tous les hôtes. Voir également l'option -r, qui permet de changer la racine de l'espace de noms dynamique de openmetrics par défaut.

L'option -l peut être utilisée pour spécifier fichier_journal comme destination des messages du PMDA au lieu du défaut, $PCP_LOG_DIR/pmcd/openmetrics.log. Comme cas spécial, fichier_journal peut être "-" pour envoyer les messages au flux stderr à la place, par ex. -l-. Ce serait normalement le flux stderr du processus parent, pmcd(1), qui pourrait lui-même avoir redirigé son stderr. Cette redirection est normalement la plus utile dans un environnement conteneurisé, ou lors de l'utilisation de dbpmda(1).

L'option -r permet de changer la racine de l'espace de noms dynamique en racine à partir du défaut, openmetrics. En conjonction avec d'autres options de ligne de commande, cela permet à pmdaopenmetrics d'être déployé comme un PMDA différent avec un espace de noms de métriques et un domaine de métriques distincts sur le même système hôte. Notez que tous les PMDA nécessitent un numéro de domaine unique, donc l'option -d doit également être spécifiée. L'utilisation de l'option -r peut également changer les valeurs par défaut pour certaines autres options de ligne de commande, par ex. le nom du fichier journal par défaut et le répertoire de configuration par défaut.

L'option -R permet à l'utilisateur de configurer le délai, en secondes, entre les rafraîchissements du cluster. La valeur par défaut est de 10 secondes.

SOURCES DE CONFIGURATION

Lors de son exécution, pmdaopenmetrics analyse périodiquement de manière récursive le répertoire $PCP_PMDAS_DIR/openmetrics/config.d (ou le répertoire spécifié avec l'option -c), à la recherche de fichiers URL sources (*.url) et de scripts ou binaires exécutables. Tous les fichiers qui n'ont pas le suffixe .url ou qui ne sont pas exécutables sont ignorés - cela permet à des fichiers de documentation tels que "README" et des définitions de fonctions de script "common" non exécutables d'être présents sans être considérés comme des fichiers de configuration.

Un serveur distant n'a pas besoin d'être en ligne ou de rester opérationnel - le PMDA tolère les URL distantes qui peuvent apparaître et disparaître avec le temps. Le PMDA relaye les données et les métadonnées quand/si elles sont disponibles, et renvoie des erreurs quand/si elles sont hors ligne. Les identifiants de métriques PCP, les identifiants de domaine d'instance internes et externes sont persistants et seront restaurés lorsque les sources de métriques individuelles deviendront disponibles et/ou lorsque le PMDA sera redémarré. De plus, le PMDA vérifie les horodatages de modification des répertoires et analysera à nouveau dynamiquement les fichiers de configuration nouveaux ou modifiés. Il n'est *pas* nécessaire de redémarrer le PMDA lors de l'ajout, de la suppression ou de la modification des fichiers de configuration.

SOURCES URL

Chaque fichier avec le suffixe .url trouvé dans le répertoire de configuration ou un sous-répertoire contient une URL HTTP ou HTTPS complète à laquelle pmdaopenmetrics peut accéder à un point d'accès OpenMetrics. L'accès aux fichiers locaux est également pris en charge avec une URL conventionnelle file:///quelque/chemin/quelque/fichier, auquel cas quelque/chemin/quelque/fichier doit contenir des données au format OpenMetrics.

La première ligne d'un fichier de configuration .url doit être l'URL, comme décrit ci-dessus. Les lignes suivantes, le cas échéant, sont précédées d'un mot-clé qui peut être utilisé pour modifier la requête GET http. Un mot-clé doit se terminer par : (deux-points) et le texte s'étend jusqu'à la fin de la ligne. Les lignes de commentaire qui commencent par # et les lignes vides sont ignorées. Les seuls mots-clés actuellement pris en charge sont HEADER: et FILTER:.

HEADER: nom_en_tete: valeur ... jusqu'à la fin de la ligne
Ajoute nom_en_tete et sa valeur aux en-têtes passés dans la requête GET http pour l'URL configurée. Un exemple de fichier de configuration qui fournit 3 en-têtes couramment utilisés et un jeton d'authentification pourrait être :


http://somehost/path/endpoint.html
# ceci est un commentaire
HEADER: Accept: text/html
HEADER: Keep-Alive: 300
HEADER: Connection: keep-alive
HEADER: Authorization: token ABCDEF1234567890

Comme mentionné ci-dessus, les valeurs d'en-tête s'étendent jusqu'à la fin de la ligne. Elles peuvent contenir n'importe quels caractères valides, y compris des deux-points. Les espaces multiples seront réduits à un seul espace, et les espaces de début et de fin seront supprimés. Une utilisation courante des en-têtes est de configurer un agent proxy et les paramètres associés dont il peut avoir besoin.

FILTRAGE DE MÉTRIQUES

Le filtrage de métriques est une fonctionnalité du fichier de configuration qui permet d'inclure ou d'exclure les métriques ingérées, c'est-à-dire de les filtrer. C'est utile car la plupart des points d'accès renvoient plusieurs métriques, et généralement seules quelques-unes sont intéressantes à des fins de surveillance. La syntaxe est :
FILTER: INCLUDE METRIC regex
ou
FILTER: EXCLUDE METRIC regex
Les noms de métriques créés dynamiquement qui correspondent à regex seront inclus ou exclus de l'espace de noms, selon la spécification. Notez que seule la composante feuille du nom de métrique dans le PMNS (telle qu'ingérée depuis la source URL) est comparée au modèle regex. La règle simple est que le *premier* modèle de filtre correspondant pour une feuille de métrique donnée est celui qui prévaut. Si aucun modèle regex de filtre ne correspond (ou s'il n'y a pas de filtres), alors la métrique est incluse par défaut, c'est-à-dire que le filtre par défaut s'il n'y en a pas de spécifiés est FILTER: INCLUDE METRIC .* Ceci est rétrocompatible avec les versions antérieures du fichier de configuration qui ne prenaient pas en charge les filtres. Plusieurs lignes FILTER: seraient normalement utilisées, par ex. pour inclure certaines métriques mais en exclure toutes les autres, utilisez FILTER: EXCLUDE METRIC .* comme dernier d'une série de filtres qui incluent les métriques désirées. Inversement, pour exclure certaines métriques mais inclure toutes les autres, utilisez FILTER: EXCLUDE METRIC regex. Dans ce cas, il n'est pas nécessaire (bien que cela ne nuise pas) de spécifier le dernier FILTER: INCLUDE METRIC .* car, comme indiqué ci-dessus, toute métrique qui ne correspond à aucun modèle regex de filtre sera incluse par défaut.

FILTRAGE D'ÉTIQUETTES

Le filtrage d'étiquettes utilise une syntaxe et une sémantique FILTER: similaires au filtrage de métriques. FILTER: EXCLUDE LABEL regex supprimera toutes les étiquettes avec un nom d'étiquette

FILTRAGE DES LIBELLÉS

La mise en correspondance regex de toutes les métriques définies par le fichier de configuration. Les mêmes règles que pour les filtres de métriques s'appliquent également aux filtres de libellés - une règle implicite : FILTER: INCLUDE LABEL .* s'applique à tous les libellés qui ne correspondent à aucune règle de filtre de libellé antérieure. FILTER: OPTIONAL LABEL regex spécifie que les noms de libellés correspondants doivent être inclus dans les jeux de libellés de métriques retournés (c'est-à-dire inclus), mais ne doivent pas faire partie des noms d'instance externes. Tous les libellés inclus qui ne sont pas optionnels (c'est-à-dire les libellés intrinsèques) seront concaténés ensemble et utilisés pour la nomation d'instance externe. En outre, les libellés non intrinsèques (c'est-à-dire les libellés marqués comme OPTIONAL) auront le drapeau PM_LABEL_OPTIONAL défini dans les jeux de libellés retournés par les rappels notes. Ce drapeau affecte la manière dont les libellés sont utilisés dans certains clients. Pour plus de détails, consultez pmLookupLabels(3) et les pages de manuel associées pour plus de détails. Notez que les noms d'instance externes commencent par l'identifiant d'instance numérique interne unique suivi d'un espace, de sorte que les noms d'instance externes sont toujours uniques.

La prudence est de mise avec le filtrage des libellés car, par défaut, tous les libellés sont utilisés pour construire le nom d'instance PCP. En excluant certains libellés (ou en les rendant optionnels), les noms d'instance changeront. De plus, l'exclusion de tous les libellés pour une métrique particulière la transforme en singulière, c'est-à-dire sans domaine d'instance. En excluant certains libellés, différentes instances retournées par l'URL ou l'entrée de configuration scriptée pour la même métrique peuvent devenir des doublons. Lorsque de tels doublons se produisent, la dernière instance dupliquée retournée par le point de terminaison de l'URL ou le script prévaut sur les instances antérieures. Pour ces raisons, il est recommandé de configurer les règles de filtrage des libellés lors de la définition initiale du fichier de configuration, et de ne pas les modifier par la suite. Si une modification du filtrage des libellés est nécessaire, le fichier de configuration doit être renommé, ce qui définit effectivement une nouvelle métrique (ou un ensemble de métriques pairs telles que retournées par l'URL ou le script), avec la nouvelle nomenclature d'instance (ou modifiée).

Les mots-clés non reconnus dans les fichiers de configuration sont signalés dans le fichier journal du PMDA mais ignorés par ailleurs.

SOURCES SCRIPTÉES

Les scripts exécutables présents dans le répertoire $PCP_PMDAS_DIR/openmetrics/config.d ou ses sous-répertoires seront exécutés et le flux stdout contenant des données de métriques au format openmetrics sera analysé comme s'il provenait d'une URL ou d'un fichier. Le flux stderr d'un script sera envoyé au fichier journal du PMDA, qui, par défaut, peut être trouvé dans $(PCP_LOG_DIR)/pmcd/openmetrics.log.

Notez que les sources scriptées ne prennent pas en charge le filtrage de libellés ou de métriques (comme décrit ci-dessus pour les sources d'URL) - elles peuvent simplement effectuer leur propre filtrage dans le script lui-même avec sed(1), awk(1), ou tout autre outil souhaité.

Un exemple simple d'entrée de configuration scriptée suit : 

#! /bin/sh
awk '{
    print("# HELP loadavg charge moyenne locale")
    print("# TYPE loadavg gauge")
    printf("loadavg {interval=\"1-minute\"} %.2f\n", $1)
    printf("loadavg {interval=\"5-minute\"} %.2f\n", $2)
    printf("loadavg {interval=\"15-minute\"} %.2f\n", $3)
}' /proc/loadavg

Ce script produit les données de métriques au format OpenMetrics suivantes lorsqu'il est exécuté : 

# HELP loadavg charge moyenne locale
# TYPE loadavg gauge
loadavg {interval="1-minute"} 0.12
loadavg {interval="5-minute"} 0.27
loadavg {interval="15-minute"} 0.54

Si le script ci-dessus était enregistré et rendu exécutable dans un fichier nommé $PCP_PMDAS_DIR/openmetrics/config.d/local/system.sh, cela entraînerait la création d'une nouvelle métrique PCP nommée openmetrics.local.system.loadavg qui aurait trois instances pour les valeurs de charge moyenne actuelles : 1-minute, 5-minute et 15-minute.

Les entrées de configuration scriptées peuvent produire plus d'un nom de métrique feuille PCP. Par exemple, le script "system.sh" ci-dessus pourrait également exporter d'autres métriques telles que les statistiques du CPU, en lisant /proc/stat sur le système local. Ces métriques supplémentaires apparaîtraient comme des métriques pairs dans le même sous-arbre de métriques PCP. Dans le cas des compteurs de CPU, la définition du type de métrique devrait être counter, et non gauge. Pour plus de détails sur les formats d'exposition openmetrics, consultez https://github.com/OpenObservability/OpenMetrics/blob/master/specification/OpenMetrics.md.

CONSIDÉRATIONS SELinux

Les fichiers de configuration scriptés sont exécutés par le PMDA pmdaopenmetrics avec le même contexte et la même politique SELinux que le pmcd(1) local. Pour des scripts simples, tels que l'exemple de charge moyenne décrit ci-dessus, cela est normalement acceptable. Cependant, des erreurs AVC peuvent survenir pour les scripts qui effectuent des appels de bibliothèque ou système qui sont restreints par le contexte et les politiques SELinux en vigueur. Dans ces cas, il n'est pas possible d'accorder unilatéralement à pmcd ou à ses PMDA une politique d'exécution non restreinte. Dans ces cas spécifiques au site, il sera nécessaire de créer un module de politique SELinux local. Cela peut être fait en capturant l'enregistrement (ou les enregistrements) AVC du journal d'audit local, en générant un module de politique locale à l'aide de audit2allow, puis en chargeant le nouveau module à l'aide de semodule, par exemple comme suit : 

    $ sudo grep '^type=AVC.*pcp' /var/log/audit/audit.log \
    | audit2allow -M mypolicy
    $ sudo semodule -i mypolicy.pp

Si ces politiques locales doivent être persistantes après redémarrage, un script similaire à l'exemple ci-dessus peut être ajouté au fichier RC de pmcd local (typiquement /etc/pcp/pmcd/rc.local). Pour plus de détails, consultez audit2allow(1) et semodule(1).

NOMMAGE DES MÉTRIQUES

Toutes les métriques d'un fichier nommé JOB.* seront exportées en tant que métriques PCP avec le préfixe de nom de métrique openmetrics.JOB. Par conséquent, le nom JOB doit être un nom valide non feuille pour les noms de métriques PMNS de PCP. Si le nom JOB a plusieurs composants séparés par des points, les noms PMNS résultants incluront ces composants et il faudra veiller à ce qu'il n'y ait pas de définitions qui se chevauchent, par exemple, les métriques retournées par JOB.response peuvent se chevaucher ou entrer en conflit avec les métriques retournées par JOB.response.time.

Les entrées de fichier de configuration (URL ou scripts) trouvées dans les sous-répertoires du répertoire de configuration entraîneront également des noms de métriques hiérarchiques. Par exemple, un fichier de configuration nommé $PCP_PMDAS_DIR/openmetrics/config.d/mysource/latency/get.url entraînera la création de métriques (en récupérant cette URL source) sous openmetrics.mysource.latency.get dans l'espace de noms PCP. Les scripts trouvés dans les sous-répertoires du répertoire de configuration entraînent de même des noms de métriques PCP hiérarchiques.

NOMS DE MÉTRIQUES DYNAMIQUES

Comme décrit ci-dessus, des modifications et des ajouts peuvent être apportés aux fichiers du répertoire de configuration sans avoir à redémarrer le PMDA. Ces modifications sont détectées automatiquement et les noms de métriques PCP sous openmetrics dans le PMNS seront mis à jour en conséquence, c'est-à-dire que de nouvelles métriques seront ajoutées dynamiquement et/ou des métriques existantes seront supprimées. De plus, pmdaopenmetrics respecte le protocole PMCD_NAMES_CHANGE de pmFetch(3) introduit dans PCP version 4.0. En particulier, si les métriques openmetrics sont enregistrées par un pmlogger(1) version 4.0 ou ultérieure de PCP, les nouvelles métriques qui apparaissent suite à des modifications dans le répertoire de configuration du PMDA commenceront automatiquement à être enregistrées, à condition que la racine de l'espace de noms du PMDA openmetrics soit configurée pour l'enregistrement dans le fichier de configuration pmlogger. Voir pmlogger(1) pour les détails. Un exemple d'un tel fichier de configuration pmlogger est : 

log mandatory on 2 second {
	# enregistrer toutes les métriques sous la racine de l'espace de noms openmetrics
	openmetrics
}

MÉTA-DONNÉES

Les données de métriques retournées par les fichiers de configuration d'URL ou scriptés peuvent contenir des méta-données qui peuvent être utilisées par le PMDA openmetrics pour spécifier la sémantique, le type de données, l'échelle et les unités des métriques créées dynamiquement. Ces méta-données sont préfixées par # PCP5 ou # PCP dans les données de métriques ingérées. Pour plus d'informations sur les méta-données PCP, consultez pmLookupDesc(3) et pmParseUnitsStr(3) ainsi que les exemples dans les fichiers de configuration expédiés.

Les méta-données en ligne "PCP5" doivent être fournies par le point de terminaison de la source de métriques (URL ou script). Une alternative est de les spécifier directement dans le fichier de configuration de l'URL, ce qui présente l'avantage de ne pas avoir à modifier la source/le point de terminaison si les méta-données sont incorrectes ou manquantes. Les méta-données spécifiées dans le fichier de configuration de l'URL remplacent toutes les méta-données en ligne.

La syntaxe du fichier de configuration pour spécifier les méta-données est la suivante :
METADATA: regex type indom semantics units ... jusqu'à la fin de la ligne
Où :
METADATA: est littéral
regex est une expression régulière étendue pour faire correspondre un ou plusieurs noms de métriques retournés par l'URL,
type est l'un des types numériques PCP (32, u32, 64, u64, float ou double),
indom est un nom de domaine d'instance arbitraire, ou PM_INDOM_NULL,
semantics est soit counter, instant, soit discrete et
units est soit none, soit une chaîne de caractères allant jusqu'à la fin de la ligne qui peut être analysée par pmParseUnitsStr(3), c'est-à-dire les unités, dimensions et échelle à utiliser pour les métriques correspondantes.

Un exemple de fichier de configuration qui ingère des métriques à partir du point de terminaison de l'API Grafana /metrics sur localhost, filtre toutes les métriques retournées par cette URL sauf grafana_api_response_status_total, puis spécifie que le type de la métrique est un entier non signé de 32 bits avec un domaine d'instance non singulier nommé response et une sémantique counter avec des unités de count.

http://localhost:3000/metrics
FILTER: INCLUDE METRIC grafana_api_response_status_total
FILTER: EXCLUDE METRIC .*
METADATA: grafana_api_response_status_total u32 response counter count

NOM

pmdaopenmetrics - Agent PCP pour les métriques au format OpenMetrics

SYNTAXE

pmdaopenmetrics

DESCRIPTION

L'agent pmdaopenmetrics est un agent d'aide pour le Performance Co-Pilot (PCP) qui collecte des métriques à partir de sources au format OpenMetrics et les rend disponibles pour le système PCP.

Il peut récupérer des métriques à partir de divers endpoints HTTP/S ou en exécutant des scripts locaux qui produisent la sortie au format OpenMetrics.

SOURCES DE CONFIGURATION

Les sources à partir desquelles pmdaopenmetrics récupère les métriques sont configurées dans le répertoire $PCP_PMDAS_DIR/openmetrics/config.d/. Chaque fichier de ce répertoire décrit une source.

Les fichiers peuvent avoir deux extensions différentes : .url pour les sources basées sur HTTP/S, et .script pour les sources exécutables.

Chaque source peut avoir des filtres associés pour sélectionner ou modifier les métriques et leurs étiquettes.

SOURCES URL

Un fichier avec l'extension .url spécifie une URL à interroger. Le contenu du fichier est l'URL elle-même.

Par exemple, un fichier nommé my_service.url avec le contenu :

http://localhost:8080/metrics

indique à pmdaopenmetrics de récupérer les métriques depuis cette URL.

Des options supplémentaires peuvent être ajoutées à l'URL pour contrôler le comportement de récupération, comme les timeouts ou les en-têtes HTTP.

FILTRAGE DES METRIQUES

Pour chaque source, il est possible de spécifier des règles de filtrage pour les métriques. Ceci est fait en utilisant des fichiers associés avec les extensions .metricmap et .metricallow.

Le fichier .metricmap permet de mapper les noms de métriques OpenMetrics à des noms de métriques PCP. Il peut également être utilisé pour exclure des métriques.

Le fichier .metricallow contient une liste de modèles de noms de métriques qui seront autorisés. Si ce fichier est présent, seules les métriques correspondant aux modèles spécifiés seront collectées.

FILTRAGE DES ETIQUETTES

De manière similaire au filtrage des métriques, il est possible de filtrer les étiquettes associées aux métriques. Ceci est fait en utilisant des fichiers avec les extensions .labelmap et .labelallow.

Le fichier .labelmap permet de renommer ou de supprimer des étiquettes. Le fichier .labelallow permet de spécifier quels ensembles d'étiquettes sont autorisés pour une métrique donnée.

SOURCES BASEES SUR SCRIPT

Un fichier avec l'extension .script spécifie un script à exécuter. Le contenu du fichier est le chemin d'accès au script. Le script doit produire sa sortie sur stdout au format OpenMetrics.

Par exemple, un fichier nommé my_script.script avec le contenu :

/usr/local/bin/my_metrics_script.sh

indique à pmdaopenmetrics d'exécuter ce script et de traiter sa sortie.

Le script doit être exécutable et doit avoir les permissions nécessaires pour s'exécuter.

CONSIDERATIONS SELinux

Si SELinux est activé, des règles appropriées doivent être mises en place pour permettre à pmdaopenmetrics d'accéder aux fichiers de configuration et d'exécuter les scripts spécifiés. Le paquet selinux-policy-pcp peut fournir les politiques nécessaires.

NOMMAGE DES METRIQUES

Les noms de métriques PCP sont générés à partir des noms de métriques OpenMetrics. Les caractères non valides dans les noms de métriques PCP sont remplacés par des traits de soulignement (_). Les préfixes peuvent être ajoutés ou supprimés selon la configuration.

NOMS DE METRIQUES DYNAMIQUES

Les noms de métriques peuvent être dynamiques, en fonction des étiquettes associées aux métriques OpenMetrics. Le domaine d'instances est généré à partir des combinaisons d'étiquettes pour chaque métrique.

Si une métrique OpenMetrics n'a pas d'étiquettes, elle n'a pas de domaine d'instance (c'est-à-dire singulier), même si elle a des étiquettes qui seraient normalement utilisées pour nommer une instance.

METADATA

Les métadonnées des métriques OpenMetrics (type, help string) sont stockées et peuvent être consultées à l'aide des outils PCP standard.

METRIQUES DE CONTRÔLE

Le PMDA maintient des métriques de contrôle spéciales, comme décrit ci-dessous. En dehors de openmetrics.control.debug, chacune de ces métriques a une instance pour chaque source de métrique configurée. Toutes ces métriques ont des valeurs entières avec des sémantiques de compteur, sauf openmetrics.control.status, qui a une valeur chaîne de caractères. Il est important de noter que la récupération de l'une des métriques openmetrics.control ne mettra à jour les compteurs et les valeurs de statut que si l'URL correspondante est effectivement récupérée. Si l'URL source n'est pas récupérée, les valeurs des métriques de contrôle ne déclenchent pas de rafraîchissement et les valeurs de contrôle rapportées représentent la dernière récupération de chaque source correspondante.

Le domaine d'instance pour les métriques openmetrics.control est ajusté dynamiquement au fur et à mesure que de nouvelles sources sont découvertes. S'il n'y a pas de sources configurées, les noms des métriques sont toujours définis mais le domaine d'instance sera vide et une récupération ne retournera aucune valeur.

openmetrics.control.status
Une chaîne de caractères représentant l'état de la dernière récupération de la source correspondante. Ce sera généralement success pour un code de réponse http de 200. Cette métrique peut être utilisée pour la surveillance de la disponibilité des services - à condition, comme indiqué ci-dessus, que l'URL source correspondante soit également récupérée.
openmetrics.control.status_code
Cette métrique est similaire à openmetrics.control.status sauf qu'il s'agit du code de réponse entier de la dernière récupération. Une valeur de 200 signifie généralement le succès et toute autre valeur un échec. Cette métrique peut également être utilisée pour la surveillance de la disponibilité des services, avec les mêmes mises en garde que pour openmetrics.control.status.
openmetrics.control.calls
Nombre total de fois où chaque source de métrique configurée a été récupérée (s'il s'agit d'une URL) ou exécutée (s'il s'agit d'un script), depuis le démarrage du PMDA. Cette métrique a des sémantiques de compteur et serait normalement convertie en débit/seconde par les outils clients.
openmetrics.control.fetch_time
Temps total en millisecondes que chaque source de métrique configurée a mis pour retourner un document, excluant le temps de traitement du document. Cette métrique a des sémantiques de compteur et serait normalement convertie en débit par les outils clients, mais est également utile sous forme brute comme temps de traitement accumulé depuis le démarrage du PMDA.
openmetrics.control.parse_time
Temps total en millisecondes que chaque source de métrique configurée a mis pour traiter chaque document, excluant le temps de récupération du document. Cette métrique a des sémantiques de compteur et serait normalement convertie en débit par les outils clients, mais est également utile sous forme brute comme temps de traitement accumulé depuis le démarrage du PMDA.

Lorsqu'elle est convertie en débit, la métrique calls représente le débit moyen de récupération de chaque source sur l'intervalle d'échantillonnage (delta de temps entre les échantillons). Les compteurs fetch_time et parse_time, lorsqu'ils sont convertis en débit, représentent la latence moyenne de récupération et de traitement (respectivement), pendant l'intervalle d'échantillonnage.

La métrique openmetrics.control.debug a une valeur singulière, par défaut 0. Si une valeur non nulle est stockée dans cette métrique à l'aide de pmstore(1), des messages de débogage supplémentaires seront écrits dans le fichier journal du PMDA.

LIMITATIONS

pmdaopenmetrics et les internes de libpcp imposent certaines contraintes numériques sur le nombre de sources (4095), de métriques (1024) au sein de chaque source, et d'instances pour chaque métrique (4194304).

INSTALLATION

Installez le PMDA OpenMetrics en utilisant le script Install en tant que root :

# cd $PCP_PMDAS_DIR/openmetrics
# ./Install

Pour désinstaller, les opérations suivantes doivent être effectuées en tant que root :

# cd $PCP_PMDAS_DIR/openmetrics
# ./Remove

pmdaopenmetrics est lancé par pmcd(1) et ne doit jamais être exécuté directement. Les scripts Install et Remove notifient pmcd lorsque l'agent est installé ou supprimé.

Lorsque des scripts et des fichiers .url sont ajoutés, supprimés ou modifiés dans le répertoire de configuration, il n'est généralement pas nécessaire de redémarrer le PMDA - les modifications seront détectées et gérées lors des requêtes ultérieures au PMDA.

ENVIRONNEMENT PCP

Les variables d'environnement avec le préfixe PCP_ sont utilisées pour paramétrer les noms de fichiers et de répertoires utilisés par PCP. Lors de chaque installation, le fichier /etc/pcp.conf contient les valeurs locales pour ces variables. La variable $PCP_CONF peut être utilisée pour spécifier un fichier de configuration alternatif, comme décrit dans pcp.conf(5).
