PMFETCH(3) Manuel des fonctions de bibliothèque PMFETCH(3)

NOM

pmFetch - obtenir les valeurs des métriques de performance

SYNTAXE

#include <pcp/pmapi.h>

int pmFetch(int numpmid,


pmID *pmidlist, pmResult **result);

cc ... -lpcp

DESCRIPTION

Étant donné une liste d'identifiants de métriques de performance (PMID), par exemple construits par pmLookupName(3), via pmidlist et numpmid, récupérer les valeurs de ces métriques de performance.

Un appel à pmFetch est exécuté dans le contexte d'une source de métriques, d'un profil d'instance et d'un temps de collecte, précédemment établis par des appels aux fonctions de contexte et de profil appropriées, à savoir certaines parmi pmNewContext(3), pmDupContext(3), pmUseContext(3), pmAddProfile(3), pmDelProfile(3) et pmSetMode(3).

Le résultat principal de pmFetch est retourné dans l'argument result sous forme d'arbre, en utilisant les structures de données de composant suivantes ;

typedef struct {
      unsigned int vtype : 8;        /* type de valeur (identique à pmDesc.type) */
      unsigned int vlen : 24;        /* octets pour vtype/vlen + vbuf */
      char         vbuf[1];          /* une ou plusieurs valeurs */
} pmValueBlock;
typedef struct {
      int          inst;                 /* identifiant d'instance */
      union {
            pmValueBlock *pval;      /* pointeur vers le bloc de valeur */
            int          lval;       /* valeur entière in situ */
      } value;
} pmValue;
typedef struct {
      pmID      pmid;                /* identifiant de métrique */
      int       numval;              /* nombre de valeurs ou code d'erreur */
      int       valfmt;              /* style de valeur, in situ ou pointeur */
      pmValue   vlist[1];            /* ensemble d'instances/valeurs */
} pmValueSet;
/* Résultat retourné par pmFetch() */
typedef struct {
      struct timespec timestamp;     /* horodatage par le collecteur */
      int            numpmid;        /* nombre de PMID */
      pmValueSet     *vset[1];       /* ensemble d'ensembles de valeurs */
} pmResult;

Pour accueillir les métriques avec plusieurs instances de valeur, le champ numval indique combien de valeurs sont retournées pour chaque PMID demandé. Le champ valfmt dans la structure pmValueSet indique si les valeurs pour cette métrique sont stockées in situ dans le champ lval, c'est-à-dire une quantité entière de 32 bits (soit int, unsigned int, long ou unsigned long) ou si les valeurs sont conservées dans des structures pmValueBlock associées. La structure pmValueBlock est toujours utilisée pour les valeurs en virgule flottante (float ou double) et gère également des données binaires de taille arbitraire telles que les métriques de type "chaîne de caractères" et les métriques avec des types de données agrégés ou complexes. La longueur maximale d'un tampon pmValueBlock est de PM_VAL_VLEN_MAX octets. Si le format pmValueBlock est utilisé, le champ vtype indique le type de données de la valeur. Ce champ a la même interprétation que le champ type dans la structure pmDesc, voir pmLookupDesc(3).

Notez que la valeur in situ peut être un entier signé ou non signé de 32 bits, une valeur longue signée ou non signée de 32 bits (sur les plateformes 32 bits). Dans les cas spéciaux décrits ci-dessous, il peut également s'agir d'une valeur en virgule flottante de 32 bits. Si l'application a besoin de connaître le type d'une valeur in situ, ce qui est presque toujours le cas, il est nécessaire de récupérer le descripteur de la métrique et d'interpréter le champ type, comme décrit en détail dans pmLookupDesc(3). Lorsque le pmResult est reçu d'un pmcd PCP1.x, les valeurs in situ peuvent également être des valeurs en virgule flottante de 32 bits (de type PM_TYPE_FLOAT). Dans tous les cas, il est conseillé d'utiliser pmLookupDesc(3) pour récupérer le descripteur de la métrique et interpréter le champ type qui s'y trouve. Notez également que le PMAPI(3) traduira automatiquement du format PCP2.0 au format PCP1.x lorsqu'un client PCP1.x demande des valeurs en virgule flottante de 32 bits à un pmcd PCP2.0, mais la traduction inverse ne se produit pas (car le pmcd PCP2.0 ne peut pas distinguer automatiquement les valeurs en virgule flottante arbitraires de 32 bits des entiers de 32 bits).

Si une valeur (c'est-à-dire associée à une instance particulière) pour une métrique demandée est "indisponible" (au moment demandé), alors il n'y a pas de structure pmValue associée dans le result. S'il n'y a aucune valeur disponible pour une métrique, alors numval sera zéro et l'instance pmValue[] associée sera vide (valfmt est indéfini dans ces circonstances, cependant pmid sera correctement défini sur le PMID de la métrique sans valeurs).

En tant qu'extension de ce protocole, si le Système de Collecte des Métriques de Performance (PMCS) est en mesure de fournir une raison pour laquelle aucune valeur n'est disponible pour une métrique particulière, cela est codé comme un code d'erreur standard dans le numval correspondant. Comme les codes d'erreur sont tous négatifs, les valeurs d'une métrique demandée sont "indisponibles" si numval est inférieur ou égal à zéro. La valeur d'une métrique de performance peut être "indisponible" pour plusieurs raisons ; la liste suivante est illustrative mais non exhaustive : du logiciel pour le Domaine de Métriques de Performance associé

+
La collecte n'est pas actuellement activée dans le logiciel pour le Domaine de Métriques de Performance associé
+
Le PMID associé n'est pas connu
+
La configuration système actuelle n'inclut pas le composant matériel associé et/ou le module logiciel associé, par exemple, un disque n'est pas installé, ou hors ligne, ou Oracle n'est pas installé
+
La métrique est de celles pour lesquelles un profil d'instance est requis, et aucun n'a été fourni (il y a un petit nombre de métriques dans cette catégorie, typiquement celles avec des domaines d'instance très grands et/ou très dynamiques, et/ou des méthodes d'instanciation de métrique coûteuses).
+
Si le contexte actuel implique la récupération de métriques à partir d'une archive, les valeurs peuvent être indisponibles dans la région autour d'un enregistrement de <mark> (voir pmlogextract(1)) qui indique une discontinuité temporelle dans la série chronologique des valeurs de métriques.

En général, nous pourrions ne pas être en mesure de différencier les divers cas, et si la différenciation n'est pas possible, numval sera simplement zéro.

La définition de l'argument et les spécifications de résultat ont été construites pour garantir que pour chaque PMID dans la pmidlist demandée, il y a exactement un pmValueSet dans le result, et de plus, les PMID apparaissent exactement dans le même ordre dans pmidlist et result. Cela rend le nombre et l'ordre des entrées dans result complètement déterministes, et simplifie grandement la logique de programmation de l'application après l'appel à pmFetch.

La structure result retournée par pmFetch est allouée dynamiquement en utilisant une combinaison d'appels à malloc(3) et de stratégies d'allocation spécialisées, et doit être libérée lorsqu'elle n'est plus nécessaire en appelant pmFreeResult(3) - en aucun cas free(3) ne doit être appelé directement pour libérer cet espace.

Comme les conditions d'erreur courantes sont codées dans la structure de données result, nous nous attendons à ce que seuls des événements catastrophiques entraînent le retour d'une valeur d'erreur. Un exemple serait si la source des métriques était un hôte distant, et que cet hôte ou le PMCS sur cet hôte devenait inaccessible. Sinon, la valeur retournée par la fonction pmFetch sera non négative.

Si le contexte actuel implique la récupération de métriques à partir d'un démon collecteur de métriques de performance (PMCD), alors la valeur de retour peut être utilisée pour coder des changements hors bande dans l'état du PMCD et des agents de collecte de métriques de performance (PMDA) associés, sous forme d'un "ou" au niveau du bit des valeurs suivantes :

PMCD_RESTART_AGENT
Une tentative a été faite pour redémarrer au moins un PMDA défaillant.
PMCD_ADD_AGENT
Au moins un PMDA a été démarré.
PMCD_DROP_AGENT
PMCD a détecté la terminaison d'au moins un PMDA.
PMCD_AGENT_CHANGE
Une macro de commodité pour l'un des trois changements de PMDA.
PMCD_LABEL_CHANGE

pmFetch(3) — Performance Co-Pilot

NAME

pmFetch, pmFetchGroup, pmFetchNotify, pmFetchArchive, pmFetchSemanticPMID - fetch performance metric values

C SYNOPSIS

#include <pcp/pmapi.h>

int
pmFetch(
  pmContext *handle,
  pmInDom indom,
  pmInDom indomsel,
  int numpmid,
  pmPmtid *pmid,
  pmResult *result
);

int
pmFetchGroup(
  pmContext *handle,
  int numpmid,
  pmPmtid *pmid,
  pmResult *result
);

int
pmFetchNotify(
  pmContext *handle,
  pmInDom indom,
  pmInDom indomsel,
  int numpmid,
  pmPmtid *pmid,
  pmResult *result
);

int
pmFetchArchive(
  pmContext *handle,
  pmInDom indom,
  pmInDom indomsel,
  int numpmid,
  pmPmtid *pmid,
  pmResult *result
);

int
pmFetchSemanticPMID(
  pmContext *handle,
  pmInDom indom,
  pmInDom indomsel,
  int numspmid,
  pmSemanticPMID *spmid,
  pmResult *result
);

DESCRIPTION

The pmFetch function is the most primitive mechanism for fetching performance metric values from the Performance Co-Pilot (PCP) collector daemon (pmcd(1)) or from performance metric archives. The pmFetchGroup function is a simpler interface that is restricted to using the default instance domain for each metric.

The pmFetchNotify and pmFetchArchive functions are variants of pmFetch specifically designed for fetching data from performance metric archives. pmFetchNotify is intended for interactive clients that need to poll for data changes, while pmFetchArchive is for batch processing of archive data.

The pmFetchSemanticPMID function is a variant of pmFetch that allows fetching metrics using semantic Performance Metric Identifiers (PMIDs) instead of standard PMIDs. Semantic PMIDs provide a more abstract way to refer to metrics and can be resolved to one or more standard PMIDs by the PCP infrastructure.

The handle argument is a pointer to a valid performance metric context, previously created using pmNewContext(3) or pmUseContext(3).

The indom and indomsel arguments specify the instance domain and the instance domain selection to be used for fetching metric values. For most metrics, the instance domain is the same as the metric's PMID, and indomsel is set to PM_INDOM_NULL. However, some metrics may have separate instance domains, and specific instances within those domains may be selected using indomsel.

The numpmid argument is the number of performance metric identifiers in the pmid array. The pmid array contains the PMIDs of the metrics to be fetched.

The numspmid and spmid arguments for pmFetchSemanticPMID function specify the number and array of semantic PMIDs to be fetched.

The result argument is a pointer to a pmResult structure, which will be filled with the fetched metric values. The pmResult structure contains the following fields:

pm_result_timestamp
A struct timespec indicating the timestamp of the fetched data.
pm_result_numpmid
The number of performance metric values returned.
pm_result_pmid
An array of pmResultItem structures, each containing a performance metric value and its associated instance and status.

The pmResultItem structure contains the following fields:

pm_resultitem_pmid
The PMID of the performance metric.
pm_resultitem_inst
The instance identifier of the metric value.
pm_resultitem_value
A pmValue union containing the metric value in its appropriate type (e.g., integer, floating-point).
pm_resultitem_state
The state of the metric value (e.g., valid, unknown, stale).

The return value of pmFetch and its variants is typically 0 on success, or a negative error code on failure. However, the result structure may also contain status information that indicates changes in the performance metric namespace or the host environment. The following special status codes may be returned in the result structure:

PMCD_NAMES_CHANGE
PMCD has been informed that the namespace has been modified, such that new metrics have appeared or existing metrics have been removed.
PMCD_HOSTNAME_CHANGE
The hostname on the host where PMCD is running has changed. This may be the result of changes from temporary to permanent hostname after a system reboot or some subsequent explicit change to the system's hostname.

The default is to return zero to indicate no change in state, however the pmResult returned by pmFetch has the same interpretation independent of the return value being zero or greater than zero.

COMPATIBILITY

Prior to PCP 7.0 the timestamp field in the pmResult struct was a struct timeval. To support PMAPI transition, the old interface and semantics can be used if applications are recompiled with -DPMAPI_VERSION=2.

For a time in PCP 6.x there was a routine with the same semantics as the current pmFetch called pmFetchHighRes, and a struct with the same definition as the current pmResult struct called pmResultHighRes, although both are now deprecated and compile-time support for pmFetchHighRes (and the historically misnamed alias pmHighResFetch) and pmResultHighRes will be removed in a future release.

SEE ALSO

pmcd(1), pmAddProfile(3), PMAPI(3), pmDelProfile(3), pmDupContext(3), pmExtractValue(3), pmFetchArchive(3), pmFreeResult(3), pmGetInDom(3), pmLookupDesc(3), pmLookupLabels(3), pmLookupName(3), pmNewContext(3), pmSetMode(3), pmUseContext(3) and pmWhichContext(3).

Note that pmFetch is the most primitive method for fetching metric values from the PMCS. See the pmFetchGroup(3) API for a higher level method that insulates the user from the intricacies of looking up metric names and metadata, setting up instance profiles, pmResult traversal, conversions, and scaling.

DIAGNOSTICS

As mentioned above, pmFetch return error codes insitu in the argument result. If no result is returned, e.g. due to IPC failure using the current PMAPI context, or end of file on an archive, then these routines will return a negative error code which may be examined using pmErrStr(3).

PM_ERR_EOL
When fetching records from an archive, pmFetch returns this error code to indicate the end of the archive has been passed (or the start of the archive has been passed, if the direction of traversal is backwards in time). If the ``mode'' for the current PMAPI context (see pmSetMode(3)) is PM_MODE_INTERP then the time origin is advanced, even when this error code is returned. In this way applications that position the time outside the range defined by the records in the archive, and then commence to pmFetch will eventually see valid results once the time origin moves inside the temporal span of the archive.
-EAGAIN
If the current context involves fetching metrics from pmcd, then a return value of -EAGAIN indicates the caller has created too many contexts.

ENVIRONMENT

Many of the performance metrics exported from PCP agents have the semantics of counter meaning they are expected to be monotonically increasing. Under some circumstances, one value of these metrics may be smaller than the previously fetched value. This can happen when a counter of finite precision overflows, or when the PCP agent has been reset or restarted, or when the PCP agent is exporting values from some underlying instrumentation that is subject to some asynchronous discontinuity.

The environment variable PCP_COUNTER_WRAP may be set to indicate that all such cases of a decreasing ``counter'' should be treated as a counter overflow, and hence the values are assumed to have wrapped once in the interval between consecutive samples. This ``wrapping'' behavior was the default in earlier PCP versions, but by default has been disabled in PCP version 1.3 and later.
