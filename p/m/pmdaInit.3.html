PMDAINIT(3) Manuel des fonctions de bibliothèque PMDAINIT(3)

NOM

pmdaInit, pmdaRehash, pmdaSetData, pmdaExtGetData, pmdaExtSetData, pmdaSetFlags, pmdaSetCommFlags, pmdaExtSetFlags - initialiser un PMDA

SYNTAXE C

#include <pcp/pmapi.h>
#include <pcp/pmda.h>

void pmdaInit(pmdaInterface *dispatch,
pmdaIndom *indoms, int nindoms, pmdaMetric *metrics, int nmetrics);

void pmdaRehash(pmdaExt *pmda,
pmdaMetric *metrics, int nmetrics);

void pmdaSetFlags(pmdaInterface *dispatch, int flags);
void pmdaSetCommFlags(pmdaInterface *dispatch, int flags);
void pmdaExtSetFlags(pmdaExt *pmda, int flags);
void pmdaSetData(pmdaInterface *dispatch, void *data);
void pmdaExtSetData(pmdaExt *pmda, void *data);
void *pmdaExtGetData(pmdaExt *pmda);

cc ... -lpcp_pmda -lpcp

DESCRIPTION

pmdaInit initialise un PMDA afin qu'il soit prêt à recevoir des PDU de pmcd(1). La fonction attend en arguments la table des domaines d'instance (indoms) et la table de description des métriques (metrics) qui sont initialisées par le PMDA. Les arguments nindoms et nmetrics doivent être définis au nombre d'instances et de métriques dans les tables, respectivement.

Une grande partie de la structure pmdaInterface peut être initialisée automatiquement avec pmdaDaemon(3), pmdaGetOpt(3) et pmdaDSO(3). pmdaInit complète la phase d'initialisation du PMDA avec trois opérations. La première opération ajoute les numéros de domaine et d'instance aux tables d'instances et de métriques. Les métriques singulières (métriques sans domaine d'instance) devraient avoir le domaine d'instance PM_INDOM_NULL défini dans le champ indom de la structure pmDesc (voir pmLookupDesc(3)). Les métriques avec un domaine d'instance devraient définir ce champ à être le numéro de série du domaine d'instance dans la table indoms.

La table des domaines d'instance peut être rendue vide en définissant indoms à NULL et nindoms à 0. Cela permet à l'appelant de fournir des fonctions de rappel personnalisées pour Fetch et Instance. La table des métriques peut être rendue vide en définissant metrics à NULL et nmetrics à 0. Cela permet à l'appelant de fournir des fonctions de rappel personnalisées pour Fetch et Descripteur.

EXEMPLE

Par exemple, un PMDA a trois métriques : A, B et C, et deux domaines d'instance X et Y, avec deux instances dans chaque domaine d'instance. Les tables de description des domaines d'instance et des métriques pourraient être définies comme suit :

static pmdaInstid _X[] = {
    { 0, "X1" }, { 1, "X2" }
};
static pmdaInstid _Y[] = {
    { 0, "Y1" }, { 1, "Y2" }
};
static pmdaIndom indomtab[] = {
#define X_INDOM 0
    { X_INDOM, 2, _X },
#define Y_INDOM 3
    { Y_INDOM, 2, _Y }
};
static pmdaMetric metrictab[] = {
/* A */
    { (void *)0,
      { PMDA_PMID(0,0), PM_TYPE_U32, PM_INDOM_NULL, PM_SEM_INSTANT,
        { 0,0,0,0,0,0} }, },
/* B */
    { (void *)0,
      { PMDA_PMID(0,1), PM_TYPE_U32, X_INDOM, PM_SEM_INSTANT,
        { 0,0,0,0,0,0} }, },
/* C */
    { (void *)0,
      { PMDA_PMID(0,2), PM_TYPE_DOUBLE, Y_INDOM, PM_SEM_INSTANT,
        { 0,1,0,0,PM_TIME_SEC,0} }, }
};

La table de description des métriques définit la métrique A sans domaine d'instance, la métrique B avec le domaine d'instance X et la métrique C avec le domaine d'instance Y. La métrique C a des unités de secondes, tandis que les autres métriques n'ont pas d'unités (compteurs simples). pmdaInit prendra ces structures et attribuera le numéro de domaine PMDA(3) au champ it_indom de chaque domaine d'instance. Cet identifiant remplace également le champ indom de toutes les métriques qui ont ce domaine d'instance, afin qu'elles soient correctement associées.

La deuxième étape ouvre le fichier d'aide, s'il a été spécifié avec l'option de ligne de commande -h (voir pmdaGetOpt(3)) ou comme argument helptext pour pmdaDSO(3) ou pmdaDaemon(3).

La dernière étape consiste à préparer la stratégie de recherche de la table des métriques.

RECHERCHE DE MÉTRIQUE

Lorsque des requêtes de récupération et de descripteur sont faites au PMDA, chaque PMID demandé doit être mappé à une entrée de la table des métriques. Il existe actuellement trois stratégies pour effectuer ce mappage - direct, linéaire et haché. Chacune a son propre ensemble de compromis et une stratégie appropriée doit être sélectionnée pour chaque PMDA.

Si tous les numéros d'éléments PMID des métriques correspondent à la position dans la table metrics, alors le mappage direct est utilisé. C'est la plus efficace des fonctions de recherche car elle implique un index de tableau direct (aucune mémoire supplémentaire n'est nécessaire ni aucun surcoût de traitement supplémentaire). Si l'exigence de numérotation des PMID est satisfaite par le PMDA, c'est idéal. Cette stratégie peut être explicitement demandée en appelant pmdaSetFlags(pmda, PMDA_EXT_FLAG_DIRECT) avant d'appeler pmdaInit. Dans ce cas, si le mappage direct n'est pas possible (par exemple, en raison d'un oubli de la part du développeur du PMDA), un avertissement est enregistré et la stratégie linéaire est utilisée à la place.

La deuxième stratégie (recherche linéaire) est la stratégie par défaut, lorsqu'un mappage direct ne peut pas être établi. Elle offre une plus grande flexibilité dans le schéma de numérotation des PMID, car les numéros d'éléments du PMDA n'ont pas besoin d'être uniques (par conséquent, les numéros de cluster des PMID peuvent être utilisés plus librement, ce qui est souvent extrêmement pratique pour le développeur du PMDA). Cependant, la recherche implique une parcours linéaire depuis le début de la table des métriques jusqu'à ce qu'un PMID correspondant soit trouvé, pour chaque PMID demandé dans une requête.

La troisième stratégie (recherche par hachage) peut être demandée en appelant pmdaSetFlags(pmda, PMDA_EXT_FLAG_HASHED) avant d'appeler pmdaInit. Cette stratégie est la plus utile pour les PMDA avec un grand nombre de métriques (plusieurs centaines ou milliers). Ces PMDA utiliseront presque toujours le schéma de numérotation par cluster, donc le schéma de recherche directe devient inapproprié. Ils peuvent également être prêts à sacrifier une petite quantité de mémoire supplémentaire pour une table de hachage, mappant les PMID aux offsets de la table des métriques, afin d'accélérer les recherches dans leurs vastes tables de métriques.

Cette dernière stratégie peut également être utilisée par les PMDA qui servent des métriques numérotées dynamiquement. Dans ce cas, la fonction pmdaRehash doit être utilisée pour remplacer la table des métriques lorsque de nouvelles métriques deviennent disponibles, ou que des métriques existantes sont supprimées. Le mappage de hachage des PMID sera recalculé en même temps que la nouvelle table des métriques est installée.

CHANGEMENTS DE MÉTRIQUE

Les auteurs de PMDA doivent bien comprendre que les métadonnées des métriques individuelles sont fixes et ne devraient idéalement jamais changer. Dans la situation où les métadonnées sont incorrectes et sont mises à jour, un tel changement nécessite une correction des métriques enregistrées à l'aide de pmlogrewrite(1), et par conséquent doit être évité autant que possible.

Cependant, un PMDA peut prendre connaissance de nouvelles métriques de domaine au moment de l'exécution, et dans ce cas, il est idéal de les exporter immédiatement (sans aucun redémarrage du système collecteur). Dans cette situation, le PMDA peut informer tous les clients PMAPI en cours d'exécution qui ont peut-être déjà exploré l'espace de noms des métriques (par exemple, en utilisant pmTraversePMNS(3)) du changement dans l'espace de noms des métriques.

Ceci est réalisé en utilisant pmdaSetFlags(pmda, PMDA_EXT_NAMES_CHANGE) ce qui entraînera l'envoi de la notification de changement d'état PMCD_NAMES_CHANGE à chaque client PMAPI lors de la prochaine récupération. Si les métriques nouvellement découvertes ont des métadonnées d'étiquette associées, alors le drapeau PMDA_EXT_LABEL_CHANGE peut également être défini, ce qui entraînera également l'envoi de la notification PMCD_LABEL_CHANGE.

pmdaExtSetFlags est équivalent à pmdaSetFlags, et est fourni comme interface de commodité dans les situations où le pmdaExt est plus facilement disponible que la structure pmdaInterface.

pmdaInit(3)

NOM

pmdaInit - initialisation d'un adaptateur de métriques de Performance Co-Pilot

SYNTAXE C

#include <pmda.h>

void pmdaInit(pmdaDispatch *dispatch, int flags);

DESCRIPTION

La fonction pmdaInit est appelée par le code d'amorçage du PMDA lors de l'initialisation d'un adaptateur de métriques de Performance Co-Pilot (PMDA). Elle configure le PMDA pour les communications avec le programme pmcd(1). Le paramètre dispatch est un pointeur vers une structure pmdaDispatch qui doit être remplie par le PMDA. La structure pmdaDispatch contient des pointeurs vers les fonctions de rappel que le PMDA utilisera pour répondre aux demandes de Performance Co-Pilot.

Le paramètre flags est un entier de 32 bits qui peut contenir divers drapeaux de configuration. Les drapeaux actuellement reconnus sont :

PMDA_INTERFACE_1
Pour les PMDA utilisant les interfaces d'API des versions 1.x.
PMDA_INTERFACE_2
Pour les PMDA utilisant les interfaces d'API des versions 2.x.
PMDA_INTERFACE_3
Pour les PMDA utilisant les interfaces d'API des versions 3.x.
PMDA_INTERFACE_4
Pour les PMDA utilisant les interfaces d'API des versions 4.x.
PMDA_INTERFACE_5
Pour les PMDA utilisant les interfaces d'API des versions 5.x.
PMDA_INTERFACE_6
Pour les PMDA utilisant les interfaces d'API des versions 6.x.
PMDA_INTERFACE_7
Pour les PMDA utilisant les interfaces d'API des versions 7.x.
PMDA_USE_FALLBACK
Ce drapeau spécifie que le PMDA peut tolérer des métriques non enregistrées dans le PMNS (Performance Names Space). Ces métriques seront récupérées en utilisant un appel direct à la table des métriques au lieu d'utiliser le PMNS. Les métriques sont alors identifiées par leur numéro d'unité et leur numéro d'index.
PMDA_USE_PMNS_ORDER
Ce drapeau spécifie que le PMDA utilise le PMNS pour déterminer l'ordre des métriques.
PMDA_VALTYPE_NUMERIC
Indique que les valeurs de métriques sont numériques.

EXEMPLE

Voici un exemple simplifié d'initialisation d'un PMDA :

#include <pcp/pmda.h>

static pmdaDispatch my_dispatch;

void
my_init_pmda(void)
{
    /* Initialize the dispatch table with callback functions */
    my_dispatch.pmdaOpen      = my_open;
    my_dispatch.pmdaClose     = my_close;
    my_dispatch.pmdaFetch     = my_fetch;
    my_dispatch.pmdaStats     = my_stats;
    my_dispatch.pmdaChildren  = my_children;
    my_dispatch.pmdaDesc      = my_desc;
    my_dispatch.pmdaXdesc     = my_xdesc;
    my_dispatch.pmdaText      = my_text;
    my_dispatch.pmdaSetOpt    = my_setopt;
    my_dispatch.pmdaGetOpt    = my_getopt;
    my_dispatch.pmdaSetData   = my_setdata;
    my_dispatch.pmdaGetData   = my_getdata;
    my_dispatch.pmdaSetFlags  = my_setflags;

    /* Initialize the PMDA with the dispatch table and flags */
    pmdaInit(&my_dispatch, PMDA_INTERFACE_7 | PMDA_USE_PMNS_ORDER);
}

RECHERCHE DE MÉTRIQUES

La fonction pmdaInit initialise également le mécanisme de recherche des métriques. Si le drapeau PMDA_USE_PMNS_ORDER est défini, le PMDA utilisera le fichier PMNS pour rechercher les métriques. Sinon, il recherchera les métriques directement dans la table des métriques. Le mécanisme de recherche peut être configuré à l'aide des options de ligne de commande ou des appels à pmdaDSO(3).

CHANGEMENTS DE MÉTRIQUES

Le PMDA peut signaler des changements dans la disponibilité ou les propriétés des métriques en appelant la fonction pmdaSetFlags. Cette fonction peut être appelée à tout moment après l'initialisation réussie de pmdaInit. Les changements d'état sont communiqués au démon pmcd(1).

ATTRIBUTS DE COMMUNICATION

pmdaInit configure également les attributs de communication entre le PMDA et le démon pmcd(1) ou le client de contexte local. Les drapeaux valides sont PMDA_FLAG_AUTHORIZE (pour les attributs liés à l'authentification) et PMDA_FLAG_CONTAINER (pour les attributs liés au nom du conteneur).

DONNÉES PRIVÉES

Une facilité pour associer des données privées de PMDA à la structure pmdaExt est disponible. Cela permet à un PMDA d'associer un pointeur arbitraire (et généralement non global) à pmdaExt afin qu'il puisse être récupéré ultérieurement lors des rappels. Les interfaces pour définir ce pointeur sont pmdaSetData et pmdaExtSetData, et pmdaExtGetData pour le récupérer ultérieurement.

AVERTISSEMENT

Le PMDA doit utiliser PMDA_INTERFACE_2 ou une version ultérieure, comme spécifié dans l'appel à pmdaDSO(3) ou pmdaDaemon(3) pour utiliser pmdaInit.

Le PMDA doit utiliser PMDA_INTERFACE_7 ou une version ultérieure pour émettre des notifications de changement d'état en utilisant pmdaSetFlags ou pmdaExtSetFlags.

DIAGNOSTICS

pmdaInit définira dispatch->status à une valeur inférieure à zéro s'il y a une erreur qui empêcherait le PMDA(3) de fonctionner correctement. pmcd(1) terminera la connexion au PMDA(3) si cela se produit.

pmdaInit peut émettre l'un des messages suivants :

La version de l'interface PMDA interface n'est pas prise en charge
La version interface n'est pas prise en charge par pmdaInit.
Utilisation de pmdaFetch() mais le rappel de récupération n'est pas défini
Le rappel de récupération, pmdaFetch(3), nécessite un rappel supplémentaire fourni par pmdaSetFetchCallBack(3).
Domaine d'instance illégal inst pour la métrique pmid
Le domaine d'instance inst spécifié pour la métrique pmid n'est pas dans la plage de la table des domaines d'instance.
Aucun chemin de texte d'aide spécifié
Le rappel de texte d'aide, pmdaText(3), nécessite qu'un fichier de texte d'aide pour les métriques ait été ouvert, cependant aucun chemin vers le texte d'aide n'a été spécifié comme option de ligne de commande, ou comme argument à pmdaDSO(3) ou pmdaDaemon(3). Ce message est uniquement un avertissement.
Mappage direct pour les métriques désactivé à l'adresse num
Les numéros d'unité des métriques ne correspondaient pas à l'index de la table de description des métriques. Le mappage direct a échoué pour le numéro de métrique num dans la table metrics. C'est moins efficace mais pas fatal et le message n'est qu'un avertissement.
Mappage haché pour les métriques désactivé à l'adresse num
Une erreur d'allocation de mémoire s'est produite lors de la construction de la table de hachage pour indexer la table de description des métriques. Il s'agit d'un message d'avertissement non fatal - une solution de repli vers la recherche linéaire sera automatiquement effectuée si cette situation se présente.
