PMREGISTERDERIVED(3) Manuel des fonctions de bibliothèque PMREGISTERDERIVED(3)

NOM

pmRegisterDerived, pmRegisterDerivedMetric - enregistrer un nom et une définition de métrique dérivée globale

C SYNTAXE

#include <pcp/pmapi.h>

char *pmRegisterDerived(char *name, char *expr);
int pmRegisterDerivedMetric(char *name,
char *expr, char **errmsg);

cc ... -lpcp

DESCRIPTION

Les métriques dérivées offrent un moyen d'étendre l'espace de noms des métriques de performance (PMNS) avec de nouvelles métriques définies côté client PCP à l'aide d'expressions sur les métriques de performance existantes.

Les utilisations typiques seraient d'agréger un certain nombre de métriques similaires pour fournir une métrique de synthèse de plus haut niveau ou pour supporter la classe de métriques ``valeur delta a sur valeur delta b'' qui ne sont pas possibles dans les sémantiques de données de base de PCP. Un exemple de cette dernière classe serait la taille moyenne des I/O, définie comme

delta(disk.dev.total_bytes) / delta(disk.dev.total)
où les deux métriques disk.dev sont des compteurs, et ce qui est requis est d'échantillonner les deux métriques, de calculer la différence entre les valeurs actuelles et précédentes, puis de calculer le ratio de ces différences.

Les arguments de pmRegisterDerived sont le nom de la nouvelle métrique dérivée et expr est une expression définissant comment les valeurs de name doivent être calculées.

pmRegisterDerivedMetric est l'équivalent fonctionnel exact de pmRegisterDerived, sauf qu'il fournit un modèle simplifié de gestion des erreurs, où un message formaté est renvoyé via le paramètre errmsg.

La vérification syntaxique est effectuée au moment où pmRegisterDerived est appelée, mais la vérification sémantique est différée jusqu'à ce que chaque nouveau contexte PMAPI soit créé avec pmNewContext(3) ou rétabli avec pmReconnectContext(3), moment auquel le PMNS et les métadonnées sont disponibles pour permettre la vérification sémantique et la détermination des métadonnées des métriques dérivées.

Si pmRegisterDerived est appelée après l'ouverture d'un ou plusieurs contextes PMAPI, les métriques nouvellement enregistrées seront disponibles dans ces contextes. Cependant, l'utilisation la plus courante consisterait à effectuer tous les appels à pmRegisterDerived (éventuellement via pmLoadDerivedConfig(3)) ou pmRegisterDerivedMetric avant d'appeler pmNewContext(3).

Toutes les métriques dérivées globales définies sont disponibles dans tous les contextes PMAPI.

Il est également possible de définir des métriques dérivées par contexte une fois qu'un contexte PMAPI a été établi. Ces métriques dérivées sont privées au contexte dans lequel elles sont définies en utilisant les routines alliées pmAddDerived(3) et pmAddDerivedMetric(3).

Pour désenregistrer une métrique dérivée par nom, référez-vous à pmUnregisterDerived(3) qui supprime toutes les instances de la métrique dérivée dans tous les contextes, quelle que soit la manière dont la métrique dérivée a été définie.

name doit suivre les règles syntaxiques pour les noms de métriques de performance, à savoir un ou plusieurs composants séparés par un point (``.''), et chaque composant doit commencer par une lettre alphabétique suivie de zéro ou plusieurs caractères tirés des alphabets, des chiffres et du trait de soulignement (``_''). Pour plus de détails, référez-vous à PCPIntro(1) et PMNS(5).

name doit être unique parmi toutes les métriques dérivées et ne doit **pas** correspondre au nom d'une métrique régulière dans le PMNS. Il est acceptable que name partage une partie de son préfixe avec un sous-arbre existant du PMNS, par exemple la métrique de taille moyenne des I/O ci-dessus pourrait être nommée disk.dev.avgsz ce qui la placerait parmi les autres métriques disk.dev dans le PMNS. Alternativement, les métriques dérivées pourraient peupler leur propre sous-arbre du PMNS, par exemple la métrique de taille moyenne des I/O ci-dessus pourrait être nommée my.summary.disk.avgsz.

L'expression expr suit ces règles syntaxiques :

  • Les éléments terminaux sont soit des noms de métriques existantes, soit des constantes numériques. Les définitions récursives ne sont pas autorisées, donc seuls les noms de métriques régulières (pas d'autres métriques dérivées) peuvent être utilisés. Les constantes numériques sont soit des entiers contraints à la précision des entiers non signés 32 bits, soit des nombres à virgule flottante double précision.
  • Les opérateurs arithmétiques binaires habituels sont supportés, à savoir l'addition (``+''), la soustraction (``-''), la multiplication (``*'') et la division (``/'') avec les règles de précédence normales où la multiplication et la division ont une précédence plus élevée que l'addition et la soustraction, donc a+b*c est évalué comme a+(b*c).
  • La négation unaire peut être utilisée, par exemple -3*some.metric.
  • Les opérateurs relationnels de style C sont supportés, à savoir ``<'', ``<='', ``=='', ``>='', ``>'' et ``!=''. Les expressions relationnelles renvoient une valeur sous forme d'un nombre non signé 32 bits étant 0 pour faux et 1 pour vrai. Les règles de précédence des opérateurs attendues s'appliquent, donc les opérateurs arithmétiques ont une précédence plus élevée que les opérateurs relationnels, et a-b>c+d est évalué comme (a-b)>(c+d). Tous les opérateurs relationnels ont une précédence égale, donc l'expression (légèrement inhabituelle) impliquant des opérateurs relationnels consécutifs a>b!=c est évaluée comme (a>b)!=c.
  • Les opérateurs booléens de style C sont supportés, à savoir et (``&&'') et ou (``||''). Les expressions booléennes renvoient une valeur sous forme d'un nombre non signé 32 bits étant 0 pour faux et 1 pour vrai. Les règles de précédence des opérateurs attendues s'appliquent, donc les opérateurs relationnels ont une précédence plus élevée que les opérateurs booléens, et a>b*c&&d<=e+f est évalué comme (a>(b*c))&&(d<=(e+f)). Les deux opérateurs booléens ont une précédence égale, donc l'expression impliquant des opérateurs booléens consécutifs a>=b||b>c&&d!=e||f>g est évaluée comme (((a>=b)||(b>c))&&(d!=e))||(f>g).
  • De plus, l'opérateur ``!'' peut être utilisé pour nier une expression booléenne ou relationnelle, renvoyant une valeur sous forme d'un nombre non signé 32 bits étant 0 pour faux et 1 pour vrai. Les règles de précédence des opérateurs attendues s'appliquent, donc les opérateurs booléens (et relationnels) ont une précédence plus élevée que la négation booléenne, et !a>b||c<d est évalué comme !((a>b)||(c<d)), tandis que !a<b+c est évalué comme !(a<(b+c)).
  • Les expressions conditionnelles ternaires de style C sont supportées. En termes généraux, l'expression check ? foo : bar est évaluée comme foo (l'opérande ``vrai'') si check (le ``garde'') est vrai, sinon l'expression est évaluée à bar (l'opérande ``faux''). Des règles sémantiques spéciales s'appliquent à l'expression ``garde'' et aux deux autres expressions opérandes :
(a)
Chaque expression peut impliquer une valeur singulière ou un ensemble de valeurs (lorsque l'expression implique une ou plusieurs métriques avec un domaine d'instance).
(b)
Toutes les expressions avec un ensemble de valeurs doivent être définies sur le même domaine d'instance.
(c)
Les deux expressions opérandes doivent avoir les mêmes métadonnées, donc le même type de métrique, les mêmes sémantiques et les mêmes unités (dimension et échelle).
(d)
L'expression ``garde'' doit avoir une valeur arithmétique, relationnelle ou booléenne, de sorte qu'elle puisse être évaluée à 0 pour faux, sinon vrai.
(e)
Si l'expression ``garde'' a une valeur singulière et qu'une ou plusieurs des autres expressions opérandes impliquent un domaine d'instance, le ``garde'' s'applique à toutes les instances.
(f)
Si l'expression ``garde'' a un ensemble de valeurs et qu'une ou plusieurs des autres expressions opérandes impliquent un domaine d'instance, le ``garde'' est évalué une fois pour chaque instance (il doit y avoir un domaine d'instance conformément à la règle (b) ci-dessus).
(g)
Si l'une des expressions opérandes a une valeur singulière et l'autre a un ensemble de valeurs, et que la valeur singulière est sélectionnée en fonction de l'évaluation du ``garde'', alors le résultat est un ensemble de valeurs (toutes identiques) dont l'énumération des instances est prise de l'autre expression opérande. Par exemple, dans l'expression : disk.dev.total_bytes ? disk.dev.total_bytes / disk.dev.total : 0 si disk.dev.total_bytes est une métrique de compteur (qui ne peut jamais être nulle), cela n'aurait aucun sens. Mais si le ``garde'' était une expression booléenne qui pourrait être vraie ou fausse pour différentes instances, alors le résultat serait un ensemble de valeurs d'instances.

(h)
Comme cas particulier, l'une (mais pas les deux) des expressions foo ou bar peut être le constructeur spécial novalue(). Si novalue() doit être évalué, il ne retournera aucune valeur. L'utilisation la plus courante de novalue() est en conjonction avec defined() comme dans l'exemple suivant :

mumble = defined(abc.def) ? count(abc.def) : novalue()

Les métadonnées pour novalue() sont tirées de l'opérande pair de l'opérateur :, rendant les conditions (b) et (c) ci-dessus trivialement vraies ; si l'opérande pair ne peut pas être évalué, alors les métadonnées par défaut pour novalue() sont un entier discret singulier sans unités, et les conditions (b) et (c) sont levées.

Une extension de novalue() est novalue(<metadata>) où le <metadata> peut être spécifié en utilisant un ou plusieurs paramètres de la forme tag=valeur ou tag="valeur" comme décrit pour le constructeur mkconst() ci-dessous, par exemple :

novalue(type=float, semantics=instant, units="Kbytes/sec")

(i)
Comme cas supplémentaire, si vérifier est de la forme defined(somemetric), alors les références à des métriques non définies sont autorisées dans celui des deux (foo ou bar) qui n'est pas requis une fois que l'existence de somemetric a été établie. Ceci permet des utilisations de la forme :


fumble = defined(new.metric) ? new.metric : old.metric

ce qui est valide lorsque new.metric est défini et lorsque new.metric n'est pas défini, bien que cela signifie que les règles (b) et (c) sont assouplies dans ce cas, ce qui signifie en outre que novalue() peut ne pas avoir d'opérande pair pour fournir des métadonnées.

Une généralisation de cette construction est prise en charge pour tout vérifier qui peut être évalué statiquement, donc une expression booléenne impliquant des prédicats defined(), par exemple :

bar = !defined(a) || !defined(b) ? novalue() : a + b

•
La sélection d'une instance unique peut être spécifiée par la construction ``[nom_instance]'' qui peut être ajoutée à un nom de métrique ou à une expression entre parenthèses. Par exemple :

fw.bytes = network.interface.in.bytes[eth1] + \
  network.interface.out.bytes[eth1]

ou (de manière équivalente) :

fw.bytes = (network.interface.in.bytes + \
  network.interface.out.bytes)[eth1]

Tous les caractères entre ``['' et ``]'' sont considérés comme faisant partie du nom d'instance (externe), il faut donc faire attention à éviter tout espace blanc superflu. Une barre oblique inverse peut être utilisée comme préfixe d'échappement dans le cas (improbable) où le nom d'instance externe contient un ``]''.

•
Les constantes numériques peuvent également être spécifiées à l'aide du constructeur mkconst() qui prend un certain nombre d'arguments : le premier est une constante numérique (entière ou à virgule flottante), puis suivent un ou plusieurs paramètres de la forme tag=valeur ou tag="valeur" où les valeurs autorisées pour tag et valeur sont les suivantes :
tag valeur
type l'un des types de métriques numériques de <pcp/pmapi.h>, dépouillé du préfixe PM_TYPE_, donc 32, U32, 64, U64, FLOAT ou DOUBLE.
semantics l'un des types sémantiques de <pcp/pmapi.h>, dépouillé du préfixe PM_SEM_, donc COUNTER, INSTANT ou DISCRETE.
units une spécification de dimension et d'échelle (formant ensemble les unités), dans la syntaxe acceptée par pmParseUnitsStr(3).
meta un nom de métrique qui fournit les métadonnées de base pouvant être modifiées par d'autres paramètres

La valeur peut éventuellement être entourée de guillemets doubles, et peut apparaître dans n'importe quel mélange de majuscules et/ou minuscules. Le tag doit être en minuscules comme indiqué dans le tableau ci-dessus.

C'est plus utile lorsque la sémantique de l'expression nécessite de faire correspondre le type et/ou la sémantique et/ou les unités des opérandes, par ex.

idle = mem.util.free > mkconst(10485760, units=Kbyte)
avg_io_size = delta(disk.dev.total) == 0 ? \
mkconst(1.0, semantics=instant, units="kbyte / count") : \
delta(disk.dev.total_bytes) / delta(disk.dev.total)

•
Les expressions peuvent être mises à l'échelle à l'aide de la fonction rescale qui prend deux arguments. Le premier est une expression arithmétique à mettre à l'échelle, et le second sont les unités souhaitées après mise à l'échelle, qui est une valeur de chaîne dans la syntaxe acceptée par pmParseUnitsStr(3). Par exemple :

rescale(network.interface.total.bytes, "Mbytes/hour")

L'expression et les unités souhaitées doivent toutes deux avoir la même dimension, par exemple Espace=1, Temps=-1 et Compte=0 dans l'exemple ci-dessus.

    defined(x) Une valeur booléenne qui est vraie (``1'') si la métrique x est définie dans le PMNS, sinon fausse (``0''). Ainsi, tout changement ultérieur du PMNS après l'établissement du contexte PMAPI ne modifiera pas la valeur de cette fonction lors de l'évaluation de l'expression.

    min(x) Une instance singulière étant la valeur minimale sur toutes les instances pour la métrique x.

    Fonction Valeur
    instant(expr) Renvoie la valeur actuelle de l'expression, même si elle a la sémantique d'un compteur, c'est-à-dire PM_SEM_COUNTER. La sémantique de la métrique dérivée est basée sur la sémantique de l'expression expr ; si expr a la sémantique PM_SEM_COUNTER, la sémantique de instant(expr) est PM_SEM_INSTANT, sinon la sémantique de la métrique dérivée est la même que la sémantique de expr.
  • Les fonctions unaires suivantes renvoient des valeurs calculées à partir de la valeur d'une expression sur des échantillons consécutifs, ou des appels à pmFetch(3). L'expression (expr ci-dessous) peut impliquer une ou plusieurs métriques mais doit avoir une valeur arithmétique (entier de différentes tailles et signes, flottant ou double) pour toutes les instances.

Si expr est une expression à valeurs multiples, seules les instances qui apparaissent dans les deux échantillons apparaîtront dans le résultat.

Function Value
delta(expr) Retourne la différence de valeurs pour l'expression entre deux appels consécutifs à pmFetch(3). Il y a une valeur dans le résultat pour chaque instance qui apparaît dans l'échantillon actuel et le précédent. Si l'expression est non signée, alors le type du résultat est converti pour assurer autant de précision que possible, donc si l'expression est de type PM_TYPE_U32 alors le résultat est de type PM_TYPE_64, sinon si l'expression est de type PM_TYPE_U64 alors le résultat est de type PM_TYPE_DOUBLE. Sinon le type du résultat est le même que le type de l'expression.
rate(expr) Retourne la différence de valeurs pour l'expression entre deux appels consécutifs à pmFetch(3) divisée par le temps écoulé entre les appels à pmFetch(3). Les sémantiques de la métrique dérivée sont basées sur les sémantiques de l'expression avec la dimension dans le domaine time diminuée d'un et la mise à l'échelle si nécessaire dans le cas d'utilisation du temps où l'opérande est en unités de temps, et la métrique dérivée est sans unité. Il y a une valeur dans le résultat pour chaque instance qui apparaît dans l'échantillon actuel et le précédent, sauf dans le cas où l'expression a les sémantiques d'un compteur, c'est-à-dire PM_SEM_COUNTER, et que la valeur actuelle d'une instance est inférieure à la valeur précédente de la même instance, alors aucune valeur n'est retournée pour cette instance (cela correspond à un « compteur wrap » ou à un « compteur reset »). Ces règles imitent la conversion de taux appliquée aux métriques de compteur par des outils tels que pmval(1), pmie(1) et pmchart(1).
•
La fonction matchinst peut être utilisée pour sélectionner un sous-ensemble d'instances d'un domaine d'instance pour une métrique ou une expression. La fonction prend deux arguments :
(a)
Un filtre d'instance qui consiste en un opérateur de négation facultatif ``!'' suivi d'une expression régulière délimitée par des caractères ``/''. L'expression régulière suit la syntaxe des expressions régulières étendues POSIX telle que décrite dans regex(3). Une seule barre oblique inverse peut être utilisée pour échapper le délimiteur d'expression régulière ``/'', mais des doubles barres obliques inverses sont nécessaires pour échapper tout caractère spécial d'expression régulière, par exemple pour le cas (extrêmement improbable) où l'on souhaite faire correspondre des noms d'instance comme ``some*text/other[text]'' une expression régulière de la forme /some\\*text\/other\\[text]/ serait requise. Si présent, l'opérateur de négation inverse le sens du filtrage, donc toutes les instances ne correspondant pas à l'expression régulière seront sélectionnées.
(b)
Une métrique ou une expression qui doit être définie sur un domaine d'instance.

Par exemple, l'expression suivante aura les valeurs pour la métrique network.interface.in.bytes pour toutes les interfaces réseau sauf les périphériques de boucle et les ponts virtuels :

matchinst(!/^(lo)|(vbir)/, network.interface.in.bytes)

•
La fonction scalar peut être utilisée pour convertir une métrique ou une expression définie sur un domaine d'instance en une valeur scalaire qui peut être utilisée dans d'autres expressions. Par exemple :

net.in.bytes = scalar(network.interface.in.bytes[eth0]) + \
  scalar(network.interface.in.bytes[eth1])

Le domaine d'instance est supprimé des métadonnées du résultat et l'identifiant d'instance est supprimé de la valeur lors de la récupération.

Si la métrique ou l'expression implique plus d'une instance, le résultat est formé en choisissant la première instance - ceci est arbitraire et implique que la fonction scalar ne doit être utilisée que pour des métriques ou des expressions qui devraient contenir zéro ou une instance, par exemple la construction ``[nom_instance]'' ou la fonction matchinst avec un modèle qui correspond à une instance au maximum.

  • Les parenthèses peuvent être utilisées pour un groupement explicite.
  • Une ligne se terminant par ``\'' est traitée comme ``à suivre'' et la ligne suivante est ajoutée après avoir supprimé le ``\'' et le saut de ligne intégré.
  • Les lignes commençant par ``#'' sont traitées comme des commentaires et ignorées.
  • Les espaces blancs sont ignorés.

VÉRIFICATIONS ET RÈGLES SÉMANTIQUES

Il existe un certain nombre de conversions nécessaires pour déterminer les métadonnées d'une métrique dérivée et pour assurer la cohérence sémantique des expressions.

Dans une expression arithmétique ou une expression relationnelle, si les sémantiques des deux opérandes ne sont pas un compteur (c'est-à-dire PM_SEM_INSTANT ou PM_SEM_DISCRETE) alors le résultat aura les sémantiques PM_SEM_INSTANT, sauf si les deux opérandes sont PM_SEM_DISCRETE, auquel cas le résultat est également PM_SEM_DISCRETE.

Pour une expression arithmétique, la dimension de chaque opérande doit être la même. Pour une expression relationnelle, la dimension de chaque opérande doit être la même, sauf que les constantes numériques (sans dimension) sont autorisées, par exemple dans l'expression network.interface.in.drops > 0.

Pour éviter les combinaisons arbitraires et absurdes, certaines restrictions s'appliquent aux expressions qui combinent des métriques avec des sémantiques de compteur pour produire un résultat avec des sémantiques de compteur. Pour une expression arithmétique, si les deux opérandes ont les sémantiques d'un compteur, alors seule l'addition ou la soustraction est autorisée, ou si l'opérande gauche est un compteur et l'opérande droit ne l'est pas, alors seule la multiplication ou la division sont autorisées, ou si l'opérande gauche n'est pas un compteur et l'opérande droit est un compteur, alors seule la multiplication est autorisée.

Étant donné que les expressions relationnelles utilisent uniquement la valeur actuelle et produisent un résultat qui n'est pas un compteur, les deux opérandes d'une expression relationnelle peuvent être des compteurs.

Le mappage des pmUnits des métadonnées utilise les règles suivantes :

  • Si les deux opérandes ont une dimension de Compte et que les échelles ne sont pas les mêmes, utilisez l'échelle la plus grande et convertissez les valeurs de l'opérande avec l'échelle la plus petite.
  • Si les deux opérandes ont une dimension de Temps et que les échelles ne sont pas les mêmes, utilisez l'échelle la plus grande et convertissez les valeurs de l'opérande avec l'échelle la plus petite.
  • Si les deux opérandes ont une dimension d'Espace et que les échelles ne sont pas les mêmes, utilisez l'échelle la plus grande et convertissez les valeurs de l'opérande avec l'échelle la plus petite.
  • Pour l'addition et la soustraction, toutes les dimensions pour chacun des opérandes et le résultat sont identiques.
  • Pour la multiplication, les dimensions du résultat sont la somme des dimensions des opérandes.
  • Pour la division, les dimensions du résultat sont la différence des dimensions des opérandes.

La conversion d'échelle implique une division si la dimension est positive, sinon une multiplication si la dimension est négative. Si une conversion d'échelle est appliquée à l'un des opérandes, le résultat est promu au type PM_TYPE_DOUBLE.

En mettant tout cela ensemble dans un exemple, considérons la métrique dérivée définie comme suit :
x = network.interface.speed - delta(network.interface.in.bytes) / delta(sample.milliseconds)
Les paramètres de type, de dimension et d'échelle se propageraient dans l'arbre d'expression comme suit.

Expression Type Dimension & Échelle Facteur(s) d'échelle
sample.milliseconds DOUBLE milliseconde
delta(...) DOUBLE milliseconde
network...bytes U64 octet
delta(...) U64 octet
delta(...) / delta(...) DOUBLE octet/milliseconde /1048576 et *1000
network...speed FLOAT Mbyte/sec
x DOUBLE Mbyte/sec

Les expressions impliquant une sélection d'instance unique ou la fonction matchinst doivent être associées à des métriques sous-jacentes ayant un domaine d'instance. Ces constructeurs n'ont aucun sens pour les métriques singulières.

Étant donné que la vérification sémantique ne peut pas être effectuée au moment où pmRegisterDerived est appelé, les erreurs trouvées lors de la vérification sémantique (lorsque tout appel ultérieur à pmNewContext(3) ou pmReconnectContext(3) réussit) sont signalées à l'aide de pmprintf(3). operands
Pour une expression ternaire, l'opérande « vrai » et l'opérande « faux » doivent avoir exactement les mêmes métadonnées, donc le même type, la même sémantique, le même domaine d'instance et les mêmes unités (dimension et échelle).
Erreur sémantique : métrique dérivée <nom> : <opérande> <op> <opérande> : Les dimensions ne sont pas les mêmes
Les opérandes doivent avoir les mêmes unités (dimension et échelle) pour chacune des opérations d'addition, de soustraction, des opérateurs relationnels et des opérateurs logiques « et » ou « ou ».
Erreur sémantique : métrique dérivée <nom> : <opérande> <op> <opérande> : Opérateur illégal pour compteur et non-compteur
Seules la multiplication ou la division sont autorisées si l'opérande gauche a la sémantique d'un compteur et l'opérande droit n'est **pas** un compteur.
Erreur sémantique : métrique dérivée <nom> : <opérande> <op> <opérande> : Opérateur illégal pour compteurs
Si les deux opérandes ont la sémantique d'un compteur, seules l'addition ou la soustraction ont un sens, donc la multiplication et la division ne sont pas autorisées.
Erreur sémantique : métrique dérivée <nom> : <opérande> <op> <opérande> : Opérateur illégal pour non-compteur et compteur
Seule la multiplication est autorisée si l'opérande droit a la sémantique d'un compteur et l'opérande gauche n'est **pas** un compteur.
Erreur sémantique : métrique dérivée <métrique> <expr> RESCALE <unités> : Dimensions incompatibles
Les paramètres <expr> et <unités> de la fonction rescale doivent avoir la même dimension le long des axes Temps, Espace et Compte.
Erreur sémantique : métrique dérivée <nom> : Dimension temporelle incorrecte pour l'opérande
La conversion de taux à l'aide de la fonction rate() n'est possible que pour les métriques opérandes avec une dimension temporelle de 0 ou 1 (voir pmLookupDesc(3)). Si la dimension temporelle de la métrique opérande est 0, alors la métrique dérivée a une valeur « par seconde » (dimension temporelle de -1). Si la dimension temporelle de la métrique opérande est 1, alors la métrique dérivée a une valeur d'utilisation temporelle (dimension temporelle de 0).
Erreur sémantique : métrique dérivée <nom> : <fonction>(<opérande>) : Opérande non arithmétique pour la fonction
Les fonctions unaires ne sont définies que si l'opérande a un type arithmétique. De même, le premier argument de la fonction rescale doit être de type arithmétique.
Erreur sémantique : métrique dérivée <nom> : <expr> ? ... : Garde ternaire non arithmétique
La première expression d'un opérateur ternaire doit avoir un type arithmétique.
Erreur sémantique : métrique dérivée <nom> : ... - ... : Opérande non arithmétique pour la négation unaire
La négation unaire n'a de sens que si l'expression suivante est de type arithmétique.
Erreur sémantique : métrique dérivée <nom> : <opérande> <op> <opérande> : Type non arithmétique pour l'opérande <gauche ou droite>
Les opérateurs arithmétiques binaires ne sont autorisés qu'avec des opérandes de type arithmétique (entier de différentes tailles et signes, flottant ou double).
Erreur sémantique : métrique dérivée <nom> : <opérande> <op> <opérande> : Non-compteur et non sans dimension pour l'opérande <gauche ou droite>
Pour la multiplication ou la division ou l'un des opérateurs relationnels, si l'un des opérandes a la sémantique d'un compteur et l'autre a la sémantique d'un non-compteur (instantané ou discret), alors l'opérande non-compteur ne doit pas avoir d'unités (dimension et échelle).
Erreur sémantique : métrique dérivée <nom> : <expr> ? <expr> : <expr> : Garde ternaire non scalaire avec expressions scalaires
Si les opérandes « vrai » et « faux » d'une expression ternaire ont une valeur scalaire, alors l'expression « garde » doit également avoir une valeur scalaire.
Erreur sémantique : métrique dérivée <nom> : <expr> <op> <expr> : Les opérandes doivent avoir le même domaine d'instance
Pour tous les opérateurs binaires (arithmétiques et relationnels), si les deux opérandes ont des valeurs non scalaires, ils doivent être définis sur le même domaine d'instance.
Erreur sémantique : métrique dérivée <nom> : opérande <dnom> : Métrique dérivée imbriquée illégale
Une métrique dérivée (<dnom>) ne peut pas être imbriquée (c'est-à-dire utilisée) dans la définition d'une autre métrique dérivée (<nom>).
Erreur sémantique : métrique dérivée <nom> : <expr> <op> <expr> : Opérateur illégal pour non-compteurs
Les métriques avec la sémantique de compteur peuvent être ajoutées ou soustraites, mais <op> (division ou multiplication) n'est pas autorisé.
Erreur sémantique : métrique dérivée <nom> : opérande <bnom> : Métrique inconnue pour l'expression ternaire
Lorsqu'un nouveau contexte a été établi, la métrique <bnom> n'était pas dans le PMNS du nouveau contexte et <bnom> est un opérande requis dans la définition de la métrique dérivée <nom>.

PMID ET MASQUAGE

Au sein de PCP, chaque métrique se voit attribuer un identifiant unique de métrique de performance (PMID) et, en interne, un PMID est construit à partir de 3 champs : le numéro de domaine (de l'agent de domaine des métriques de performance, ou PMDA, associé), le numéro de cluster et le numéro d'élément. Les métriques dérivées utilisent le numéro de domaine réservé 511 et des PMIDs spéciaux comme décrit dans le tableau suivant, où le PMID est indiqué sous la forme domaine.cluster.élément :

Métrique dérivée PMID de démarrage Description
global 511.0.1 Les métriques se voient attribuer des PMIDs *ascendants* lorsqu'elles sont enregistrées via pmRegisterDerived ou pmRegister-DerivedMetric, ou pmLoad-DerivedConfig(3).
par contexte 511.2047.1023 Les métriques se voient attribuer des PMIDs *descendants* lorsqu'elles sont enregistrées via pmAddDerived(3) ou pmAddDerivedMetric(3).
re-mappé 511.c.i Lorsqu'une métrique dérivée est enregistrée dans une archive PCP par pmlogger(1) ou l'un des outils de création d'archives associés, le PMID de la métrique dérivée est re-mappé dans l'archive de sorte que *c* soit le cluster de la métrique dérivée plus 2048, et i soit l'élément de la métrique dérivée. Par exemple, une métrique dérivée avec le PMID 511.0.13 aura le PMID re-mappé 511.2048.13 dans une archive. Voir pmlogger(1) pour une discussion sur l'ajout de métriques dérivées à une archive PCP.

Pour les métriques de base d'un hôte ou d'un contexte d'archive, il est requis que chaque nom de métrique soit unique. NAME

pmRegisterDerived, pmAddDerived, pmAddDerivedMetric, pmUnregisterDerived - register and unregister derived performance metrics

C SYNOPSIS

#include <pcp/pmapi.h>


int pmRegisterDerived(
    const char *name,
    const char *expr,
    int flags
);
int pmAddDerived(
    const char *name,
    const char *expr
);
int pmAddDerivedMetric(
    const char *name,
    const char *expr,
    char **errmsg
);
int pmUnregisterDerived(
    const char *name
);

DESCRIPTION

Derived performance metrics allow applications to define new performance metrics based on expressions involving existing performance metrics. The performance metric name space (PMNS) is extended dynamically by registering derived metrics.

The pmRegisterDerived function registers a new derived metric with the name name, based on the expression expr, using the specified flags.

The pmAddDerived function is a simplified interface to pmRegisterDerived with flags set to 0. It is intended for use within performance metric collection daemons and other PCP applications that manage their own Performance Metric Name Space (PMNS).

The pmAddDerivedMetric function is similar to pmAddDerived, but provides more detailed error reporting. If an error occurs during parsing of the expression expr, it returns a dynamically allocated error message string via the errmsg parameter.

The pmUnregisterDerived function removes a previously registered derived metric named name.

The expr argument is a string defining the derived metric. It can contain references to other performance metrics (identified by their Performance Metric Identifier (PMID) or by their name), arithmetic operators (+,-,*,/), and function calls.

The performance metric names and names of derived metrics can be qualified with a context specifier, like a cluster name (for distributed metrics) or a specific instance. The context specifier is enclosed in square brackets, e.g. {@code [clustername]} or {@code [instance]}.

Supported operators and functions include:

Arithmetic
+ , - , * , / , % (modulo), ** (power)
Logical
&& (AND), || (OR), ! (NOT)
Comparison
< , <= , = = , != , >= , >
Bitwise
& (AND), | (OR), ^ (XOR), ~ (NOT), << (left shift), >> (right shift)
Functions
Function Syntax section provides more details.

Derived metrics can be defined in terms of other derived metrics, creating a hierarchy. The evaluation order is determined by the PCP archive or live source.

The flags argument to pmRegisterDerived can be a bitmask composed of the following values:

PM_DERIVE_GC
Perform garbage collection of unused derived metrics.
PM_DERIVE_LOCAL
Register the derived metric locally (only available within the current process).
PM_DERIVE_REPLACE
Replace an existing derived metric with the same name.

The context specifier can be one of the following:

{@code contextname[instance]}
e.g., {@code filesystem[root]}. The contextname is a cluster name, and instance is a cluster instance.
{@code [clustername]}
e.g., {@code [cluster1]}.
{@code [instance]}
e.g., {@code [cpu0]}.
{@code host[instance]}
e.g., {@code host[server1]}. This is a special context name referring to the host.

The context specifier can be omitted, in which case the metric is assumed to be global.

A derived metric is defined by a name and a value expression. The value expression can contain references to other performance metrics, constants, and functions.

The flags argument to pmRegisterDerived can be used to control the behavior of derived metrics, such as enabling garbage collection or specifying local registration.

SEMANTIC CHECKS AND RULES

The following rules are applied when evaluating derived metrics:

  • A base metric is a metric that is directly fetched from the system, not a derived metric.
  • A remapped metric is a derived metric that is defined as a direct copy of another metric (base or derived).
  • A derived metric is a metric that is defined by an expression involving more than just a single metric reference.

The following table summarizes the properties of derived metrics based on the presence of certain characteristics in their definition:

...               | ...     | ...      | ...            | ...

When masking happens, it is done silently. Most PCP applications support -Dderive on the command line and this pmdbg(1) debug option will report derived metric operations (including masking) on stderr.

EXPRESSION EVALUATION

The expression is evaluated using the current set of available metrics. If a metric used in the expression is not available, the expression evaluation fails.

Contexts are handled as follows: If an expression refers to a metric with a context (e.g., {@code cpu[0].user}), and the derived metric itself is defined with a context (e.g., {@code host[server1]}), the resulting metric will have the combined context (e.g., {@code host[server1]/cpu[0].user}). If the derived metric is defined globally, the context of the referenced metric is preserved.

The evaluation of derived metrics can introduce performance overhead. Care should be taken to define derived metrics efficiently.

FUNCTION SYNTAX

Derived metrics support a set of built-in functions for more complex calculations. The general syntax for function calls is:

function_name(argument1, argument2, ...)

Supported functions include:

rate(metric)
Computes the rate of change for a counter metric.
delta(metric)
Computes the difference between consecutive samples of a counter metric.
count(metric)
Returns the number of instances for a given metric.
first(metric)
Returns the value of the metric from the first sample.
last(metric)
Returns the value of the metric from the last sample.
prev(metric)
Returns the value of the metric from the previous sample.
time()
Returns the current time in seconds since the epoch.
stddev(metric)
Computes the standard deviation of the metric over a time window.
avg(metric)
Computes the average value of the metric over a time window.
min(metric)
Computes the minimum value of the metric over a time window.
max(metric)
Computes the maximum value of the metric over a time window.
percentile(metric, p)
Computes the p-th percentile of the metric over a time window.

Time window functions (stddev, avg, min, max, percentile) require a time interval specification, e.g., {@code stddev(metric, 60)} for a 60-second window.

Constants can be specified as integers (e.g., {@code 10}), floating-point numbers (e.g., {@code 3.14}), or in scientific notation (e.g., {@code 1.2e3}).

Metric names can be fully qualified with their PMID or their PMNS name. Context specifiers can be used to select specific instances or clusters.

PMIDS AND MASKING

Derived metrics are resolved to a set of PMIDs. When a derived metric is defined, PCP determines the underlying base PMIDs that constitute the expression. If the derived metric is context-specific, the context is used to filter the PMIDs.

Masking occurs when a derived metric definition causes one or more base metrics to be ignored or replaced. This can happen implicitly due to the definition of a derived metric that overrides a base metric, or explicitly through the use of masking operators or functions.

CAVEATS

Derived metrics are not available when using pmFetchArchive(3) as this routine does not use a target list of PMIDs that could be remapped (as is done for pmFetch(3)).

DIAGNOSTICS

On success, pmRegisterDerived returns NULL.

If a syntactic error is found at the time of registration, the value returned by pmRegisterDerived is a pointer into expr indicating where the error was found. To identify what the error was, the application should call pmDerivedErrStr(3) to retrieve the corresponding parser error message.

pmRegisterDerivedMetric returns 0 and errmsg is undefined if the parsing is successful.

If the given expr does not conform to the required syntax pmRegisterDerivedMetric returns -1 and a dynamically allocated error message string in errmsg. The error message is terminated with a newline and includes both the input name and expr, along with an indicator of the position at which the error was detected. e.g.

Error: pmRegisterDerivedMetric("my.disk.rates", ...) syntax error
4rat(disk.dev.read)
^

The position indicator line may be followed by an additional diagnostic line describing the nature of the error, when available.

In the case of an error, the pmRegisterDerivedMetric caller is responsible for calling free(3) to release the space allocated for errmsg.
