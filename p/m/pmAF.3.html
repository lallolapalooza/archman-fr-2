NOM

__pmAFsetup, __pmAFregister, __pmAFunregister, __pmAFblock, __pmAFunblock, __pmAFisempty - services de file d'attente d'événements pour les rappels asynchrones périodiques

C SYNOPIS

#include "pmapi.h"
#include "libpcp.h"

int __pmAFsetup(const struct timeval *start,
const struct timeval *delta, void *data, void (*func)(int, void *));

int __pmAFregister(const struct timeval *delta,
void *data, void (*func)(int, void *));

int __pmAFunregister(int afid);
void __pmAFblock(void);
void __pmAFunblock(void);
int __pmAFisempty(void);

cc ... -lpcp

AVERTISSEMENT

Cette documentation est destinée à un usage interne par les développeurs de Performance Co-Pilot (PCP).

Ces interfaces ne font pas partie des API PCP garanties pour rester fixes d'une version à l'autre, et elles peuvent ne pas fonctionner, ou fournir des sémantiques différentes, à l'avenir.

DESCRIPTION

Les routines implémentent une file d'attente d'événements et un cadre de rappels qui prend en charge l'évaluation périodique d'une série d'événements avec des fréquences variables pour les applications Performance Co-Pilot (PCP).

L'application pmlogger(1), le PMDA pmdatrace(1) et le PMDA pmdahotproc(1) sont les principaux utilisateurs de ces services.

Un événement est créé en appelant __pmAFsetup ou __pmAFregister et en cas de succès, la valeur de retour est un numéro d'événement supérieur à zéro. L'événement a des données d'événement associées identifiées par le pointeur opaque data. L'événement se produira avec une fréquence delta et chaque fois que l'événement se produira, la fonction func sera appelée avec le numéro d'événement et les données de l'événement comme arguments.

Si __pmAFsetup est utilisé, le premier événement est planifié pour le moment actuel plus start, sinon si __pmAFregister est utilisé, le premier événement est planifié pour le moment actuel plus delta.

func est appelée dans le contexte d'un gestionnaire de signal SIGALRM et les routines qui peuvent être appelées en toute sécurité depuis func sont donc limitées à l'ensemble dit async-signal-safe. En particulier, il ne doit y avoir aucun appel d'E/S standard ni aucun appel à l'une des routines de malloc(3) pour modifier l'état du tas. Se référer à la section Pointer to a Function du document POSIX.1-2013 sur https://pubs.opengroup.org/
onlinepubs/9699919799/functions/V2_chap02.html pour une description plus complète.

La classe de routines func la plus sûre et la plus simple est celle qui effectue un traitement minimal, définit un état global et retourne. Le travail réel associé à l'événement est effectué ultérieurement à partir de la boucle principale de l'application lorsque le changement d'état global est détecté.

Une fois que l'événement se produit et que le rappel a été exécuté, l'événement sera replanifié pour delta dans le futur, sauf si tous les champs de delta sont à zéro, auquel cas l'événement ne sera pas repl anifié (un événement « one trip »).

En interne, les événements sont traités de manière sérielle, il n'y a donc aucune possibilité de rappels imbriqués ou de rappels réentrants depuis les routines de gestion d'événements.

Étant donné un numéro d'événement afid, __pmAFunregister supprimera définitivement l'entrée correspondante de la file d'attente d'événements.

Pour contrôler le traitement de la file d'attente d'événements, __pmAFblock et __pmAFunblock peuvent être utilisés pour bloquer et débloquer explicitement la distribution des événements. Ceci est particulièrement utile lorsque l'appelant souhaite configurer un certain nombre d'événements via __pmAFsetup ou __pmAFregister et terminer la phase d'enregistrement avant que le premier rappel d'événement ne se produise.

Un appel à __pmAFisempty retourne 1 ou 0 selon que la file d'attente d'événements est vide ou non.

CAVEATS

Ces routines s'appuient sur setitimer(2) et manipulent la gestion des signaux SIGALRM, et sont donc probablement mal adaptées aux applications qui nécessitent un accès direct et concurrent à ces services et ressources.

Si les fonctions de rappel sont lentes ou retardées, il est possible que la planification des événements prenne du retard et ne rattrape jamais. Lorsque cela commence à se produire, les événements sont silencieusement ignorés et repl anifiés au plus tôt dans le futur selon le calendrier fixe défini par l'heure de l'appel à __pmAFsetup et la valeur des arguments start et delta (ou défini par l'heure de l'appel à __pmAFregister et la valeur de l'argument delta).

De plus, les sémantiques du ou des minuteurs d'intervalle et l'état global nécessaire pour prendre en charge ces services exigent que les applications appelant ces routines le fassent à partir d'un seul thread. Cette restriction est appliquée au niveau de la PMAPI(3), où les routines peuvent retourner le code d'erreur PM_ERR_THREAD si la bibliothèque détecte des appels provenant de plus d'un thread.

DIAGNOSTICS

__pmAFsetup, __pmAFregister et __pmAFunregister retournent des valeurs inférieures à zéro en cas d'erreur. Ce sont des codes d'erreur PCP, et ils peuvent être utilisés pour produire des messages d'erreur via pmErrStr(3).

Les routines prennent en charge le traçage de débogage PCP standard, et l'option af (ou -D af sur la ligne de commande) produira des diagnostics sur la sortie d'erreur standard qui retracent la mise en file d'attente et l'exécution des événements.
