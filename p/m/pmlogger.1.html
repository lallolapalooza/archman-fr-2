PMLOGGER(1) Manuel des commandes générales PMLOGGER(1)

NOM

pmlogger - créer une archive de métriques de performance

SYNTAXE

pmlogger [-CLNoPruy?] [-c fichier_conf] [-D debug] [-d répertoire] [-h hôte] [-H nom_hôte] [-I version] [-K spécification] [-l fichier_journal] [-m note] [-n fichier_pmns] [-p pid] [-s taille_fin] [-t intervalle] [-T heure_fin] [-U nom_utilisateur] [-v taille_volume] [-V version] [-x desc_fichier] [archive]

DESCRIPTION

pmlogger crée des archives de valeurs de métriques de performance qui peuvent être "rejouées" par d'autres outils de Performance Co-Pilot (voir PCPIntro(1)). Ces journaux constituent la base du paradigme vidéo et des services d'analyse de performance rétrospective courants dans la boîte à outils PCP.

L'argument obligatoire archive est soit le nom de base pour les fichiers physiques qui constituent une archive sur le système de fichiers local, soit le serveur HTTP distant qui recevra les données enregistrées.

L'argument local archive peut contenir des méta-caractères strftime(3), qui seront substitués avant la création des fichiers d'archive. Lorsque pmlogger est exécuté en tant que service (voir pmlogger_daily(1)), le modèle de nom de base d'archive standard est %Y%m%d.%H.%M.

La forme distante archive spécifie l'emplacement du serveur pmproxy(1) auquel les composants de l'archive sont envoyés pendant qu'ils sont générés par pmlogger. La valeur fournie doit contenir le protocole, le nom d'hôte et éventuellement le port, par exemple http://example.com:44322. Ce serveur pmproxy sélectionnera un nom d'archive basé sur l'heure de début, de manière similaire au modèle utilisé par défaut dans pmlogger_check(1).

L'option -V spécifie la version de l'archive générée. Par défaut, la version d'archive $PCP_ARCHIVE_VERSION (définie à 3 dans les versions actuelles de PCP) est utilisée, et les seules valeurs actuellement supportées pour version sont 2 ou 3.

Sauf indication contraire vers un autre hôte par l'option -h ou lors de l'utilisation directe des PMDA via l'option -o, pmlogger contactera le démon collecteur de métriques de performance (PMCD) sur l'hôte local et l'utilisera comme source des valeurs de métriques à enregistrer.

Pour supporter la flexibilité et le contrôle requis sur ce qui est enregistré et quand, pmlogger maintient un état d'enregistrement indépendant à deux niveaux pour chaque instance de chaque métrique de performance. Au premier niveau (obligatoire), l'enregistrement peut être activé (avec un intervalle associé entre les échantillons), ou désactivé ou peut-être. Dans ce dernier cas, le second niveau (advisory) d'enregistrement peut être activé (avec un intervalle associé entre les échantillons), ou désactivé.

Le niveau obligatoire permet une spécification universelle que certaines métriques doivent être enregistrées, ou ne doivent pas être enregistrées. L'état par défaut pour toutes les instances de toutes les métriques lorsque pmlogger démarre est obligatoire peut-être et advisory désactivé.

Utilisez pmlc(1) pour interroger et modifier l'état d'enregistrement une fois que pmlogger est en cours d'exécution.

Si l'état d'une métrique est obligatoire (activé ou désactivé) et qu'une demande est faite pour la changer en obligatoire peut-être, le nouvel état est obligatoire peut-être et advisory désactivé. Si l'état d'une métrique est déjà advisory (activé ou désactivé) et qu'une demande est faite pour la changer en obligatoire peut-être, l'état actuel est conservé.

Il n'est pas possible pour pmlogger d'enregistrer des instances spécifiques d'une métrique et toutes les instances de la même métrique simultanément. Si des instances spécifiques sont enregistrées et qu'une demande pour enregistrer toutes les instances est faite, alors toutes les instances de la métrique seront enregistrées conformément à la nouvelle demande, remplaçant toute demande d'enregistrement antérieure pour la métrique. Une demande pour enregistrer toutes les instances d'une métrique remplacera toute demande précédente pour enregistrer toutes les instances. Une demande pour enregistrer des instances spécifiques d'une métrique alors que toutes les instances sont déjà enregistrées est refusée. Pour ce faire, il faut d'abord désactiver l'enregistrement pour toutes les instances de la métrique. Dans chaque cas, la validité de la demande est vérifiée d'abord ; par exemple, une demande pour changer l'état d'enregistrement d'une métrique en advisory activé alors qu'elle est actuellement obligatoire désactivé n'est jamais autorisée (il est nécessaire de changer l'état en obligatoire peut-être d'abord).

Optionnellement, chaque système exécutant pmcd(1) peut également être configuré pour exécuter une instance ``primaire'' de pmlogger. Cette instance pmlogger est lancée par $PCP_RC_DIR/pmlogger, et est affectée par les fichiers $PCP_SYSCONF_DIR/pmlogger/control, $PCP_SYSCONF_DIR/pmlogger/control.d/*, (utilisez chkconfig(8), systemctl(1) ou des commandes similaires spécifiques à la plateforme pour activer ou désactiver l'instance primaire de pmlogger), $PCP_SYSCONFIG_DIR/pmlogger (paramètres des variables d'environnement pour l'instance primaire de pmlogger) $PCP_SYSCONF_DIR/pmlogger/pmlogger.options (options de ligne de commande passées à l'instance primaire de pmlogger) et $PCP_VAR_DIR/config/pmlogger/config.default (le fichier de configuration initial par défaut pour l'instance primaire de pmlogger).

L'instance primaire de pmlogger est identifiée par l'option -P. Il ne peut y avoir qu'une seule instance ``primaire'' de pmlogger par système. L'instance primaire de pmlogger (le cas échéant) doit s'exécuter sur le même hôte que le pmcd(1) auquel elle se connecte (le cas échéant), donc les options -h et -P sont mutuellement exclusives.

L'enregistrement de certaines métriques est possible même en l'absence d'un pmcd(1) local, en utilisant le mode de fonctionnement du "contexte local". Ceci est activé à l'aide de l'option -o, et amène pmlogger à utiliser les PMDA DSO locaux au lieu de communiquer avec pmcd(1). Lors de l'utilisation d'un contexte local, l'option -K peut être utilisée pour contrôler les PMDA DSO qui devraient être rendus accessibles. L'argument spécification respecte la syntaxe décrite dans pmSpecLocalPMDA(3). Plus d'une option -K peuvent être utilisées.

Lorsqu'elle est lancée en tant qu'instance non primaire, pmlogger se terminera immédiatement si le fichier de configuration ne planifie aucun enregistrement de métrique. L'option -L remplace ce comportement, et amène une instance non primaire de pmlogger à "persister", probablement en attendant une future re-configuration dynamique et un changement d'état via pmlc(1). pmlogger persistera également sans l'option -L si toutes les métriques à enregistrer sont enregistrées comme une seule fois. Lorsque les métriques une seule fois ont été enregistrées, un message d'avertissement sera généré indiquant que la file d'attente d'événements est vide et qu'aucun autre événement ne sera planifié.

Par défaut, tous les diagnostics et erreurs de pmlogger sont écrits dans le fichier pmlogger.log dans le répertoire où pmlogger est lancé. L'option -l peut être utilisée pour remplacer le comportement par défaut. Si le fichier journal ne peut pas être créé ou n'est pas inscriptible, la sortie est écrite sur la sortie d'erreur standard à la place. Si le fichier_journal pour l'option -l est "-" (c'est-à-dire -l-) alors les messages du journal sont écrits sur le flux de sortie standard. Ceci peut être particulièrement utile lors de l'exécution manuelle de pmlogger, plutôt que comme un démon de service.

L'option -N demande à pmlogger de notifier un gestionnaire de service, typiquement systemd(1), une fois qu'il a démarré et qu'il est sur le point de commencer à écrire des archives PCP. Cette option ne serait normalement utilisée que lorsque pmlogger est exécuté comme un service démon sous le contrôle d'un gestionnaire de service. Pour plus de détails, voir __pmServerNotifyServiceManagerReady(3) et systemd(1). Sur les plateformes qui n'utilisent pas un gestionnaire de service prenant en charge les notifications, l'option -N est essentiellement une opération nulle.

Si elle est spécifiée, l'option -s demande à pmlogger de se terminer après qu'une certaine taille en enregistrements, octets ou unités de temps ait été accumulée. Si taille_fin est un entier, alors taille_fin enregistrements seront écrits dans l'archive. Si taille_fin est un entier suffixé par b ou bytes alors taille_fin octets des données de l'archive seront écrits (notez, cependant, que les limites des enregistrements d'archive ne seront pas brisées et que cette limite peut donc être légèrement dépassée). D'autres unités de taille de fichier viables incluent : K, Kb, KiB, Kbyte, Kilobyte pour les kilo-octets et M, Mb, MiB.

/b>, Mbyte, Megabyte pour les mégaoctets et G, Gb, GiB, Gbyte, Gigabyte pour les gigaoctets. Ces unités peuvent être facultativement suffixées par un s et peuvent être en casse mixte. Alternativement, endsize peut être un entier ou un nombre à virgule flottante suffixé à l'aide d'une unité de temps comme décrit dans PCPIntro(1) pour l'argument interval (de l'option de ligne de commande standard PCP -t).

Quelques exemples de formats différents :
-s 100
-s 100bytes
-s 100K
-s 100Mb
-s 10Gbyte
-s 10mins
-s 1.5hours
Par défaut, pmlogger s'exécute indéfiniment.

L'option -r provoque l'affichage dans le fichier journal de la taille des enregistrements physiques pour chaque groupe de métriques et de la contribution attendue du groupe à la taille de l'archive PCP pour une journée complète de collecte. Ces informations sont affichées la première fois que chaque groupe est écrit avec succès dans l'archive.

L'option -U spécifie le compte utilisateur sous lequel exécuter pmlogger. Par défaut, il s'agit du compte utilisateur actuel pour une utilisation interactive. Lorsqu'il est exécuté en tant que démon, le compte non privilégié "pcp" est utilisé dans les versions actuelles de PCP, mais dans les anciennes versions, le compte superutilisateur ("root") était utilisé par défaut.

L'archive est potentiellement un ensemble de données multi-volumes, et l'option -v provoque le démarrage par pmlogger d'un nouveau volume après qu'une certaine taille en enregistrements, octets ou unités de temps ait été accumulée pour le volume courant. Le format de cette spécification de taille est identique à celui de l'option -s (voir ci-dessus). Par défaut, pmlogger crée une archive à volume unique. Des commutations de volume supplémentaires peuvent également être forcées de manière asynchrone en utilisant pmlc(1) ou en envoyant un signal SIGHUP à pmlogger (voir ci-dessous). Notez que si un changement de volume planifié est en cours en raison de l'option -v, ses compteurs seront réinitialisés après un changement asynchrone.

Indépendamment de toute option -v, chaque volume d'une archive est limité à un maximum de 2^31 octets, donc pmlogger créera automatiquement un nouveau volume pour l'archive avant que cette limite ne soit atteinte.

Normalement, pmlogger opère sur l'espace de noms distribué des métriques de performance (PMNS). Cependant, si l'option -n est spécifiée, un espace de noms PMNS local alternatif est chargé à partir du fichier pmnsfile.

Dans des circonstances normales, pmlogger s'exécute indéfiniment (sauf pour une option -s ou un signal de terminaison). L'option -T peut être utilisée pour limiter le temps d'exécution en utilisant le format de temps prescrit par PCPIntro(1). Le temps est interprété dans le fuseau horaire du serveur PMCD, sauf si l'option -y est donnée, auquel cas le fuseau horaire de cet hôte logger est utilisé.

Quelques exemples de formats différents :
-T 10mins
-T '@ 11:30'
De cela, on peut voir que -T 10mins et -s 10mins effectuent des actions identiques.

Alternativement, le temps d'exécution de pmlogger peut être limité à la durée de vie d'un autre processus en utilisant l'option -p ou --PID pour nommer le PID du processus d'intérêt. Dans ce cas, le pmlogger se terminera lorsque l'autre processus n'existera plus.

Lorsque pmlogger reçoit un signal SIGHUP, le volume courant de l'archive est fermé et un nouveau volume est ouvert. Ce mécanisme (ou le mécanisme alternatif via pmlc(1)) peut être utilisé pour gérer la croissance des fichiers d'archive - une fois qu'un volume de journal est fermé, ce fichier peut être archivé sans affecter le fonctionnement continu de pmlogger. Voir également l'option -v ci-dessus.

Lorsque pmlogger reçoit un signal SIGUSR2, l'archive courante est fermée et une nouvelle archive est ouverte. Pour que cela réussisse, l'argument archive original doit inclure des métacaractères strftime(3) (par exemple, %Y%m%d.%H.%M), sinon pmlogger se terminera car les fichiers d'archive existeront déjà et pmlogger n'écrasera pas les fichiers d'archive existants. Notez que SIGUSR2 déclenche le pmlogger à se réexécuter et à réanalyser tous les arguments originaux. Cela signifie que toutes les limites de temps relatives à son temps de terminaison ou à sa limite d'échantillonnage sont réinitialisées et recommencent. Cela n'affecte que les temps de terminaison relatifs, pas les temps absolus, par exemple, -T 5s est affecté, mais -T 5pm ne l'est pas.

Historiquement, les tampons de l'archive courante pouvaient être vidés sur disque en utilisant la commande flush de pmlc(1), ou en utilisant l'option -u. La version actuelle de pmlogger et les routines libpcp qui sous-tendent pmlogger utilisent inconditionnellement des écritures non tamponnées et un seul fwrite(3) pour chaque enregistrement logique écrit, et donc le "vidage" ne force aucune donnée supplémentaire à être écrite dans le système de fichiers. L'option -u et la commande flush de pmlc(1) sont conservées pour des raisons de compatibilité ascendante.

Lorsqu'il est lancé avec l'option -x, pmlogger acceptera des requêtes de contrôle asynchrones sur le descripteur de fichier fd. Cette option est uniquement destinée à être utilisée en interne par les applications PCP qui prennent en charge le "mode d'enregistrement en direct".

L'option -m permet d'ajouter la chaîne note au fichier de carte pour cette instance de pmlogger dans le répertoire $PCP_TMP_DIR/pmlogger. Ceci est actuellement utilisé en interne pour documenter le descripteur de fichier (fd) lorsque l'option -x est utilisée, ou pour indiquer que cette instance de pmlogger a été démarrée sous le contrôle de pmlogger_check(1) (-m pmlogger_check) ou a été réexécutée (voir execvp(3)) suite à la réception d'un signal SIGUSR2 comme décrit ci-dessus (-m reexec).

L'option -H permet de remplacer le nom d'hôte écrit dans l'étiquette d'archive. Ceci reflète l'option -H de pmcd(1), mais permet de la spécifier sur le processus pmlogger. Sans cette option, la valeur renvoyée par le pmcd(1) enregistré est utilisée.

L'option -C provoquera l'analyse du fichier de configuration et pmlogger se terminera ensuite sans créer d'archive de sortie. Ainsi, lorsque -C est spécifié, l'argument de ligne de commande archive n'est pas requis. Toute erreur dans le fichier de configuration est signalée.

L'option -d ou --directory peut être utilisée pour spécifier le répertoire où l'archive doit être créée. directory peut inclure des métacaractères de sh(1), tels que $(...) ou `...` ou $var et pmlogger les développera pour produire un chemin de répertoire final. Le chemin résultant doit être absolu, pas relatif. L'option -d est principalement destinée à être utilisée par pmlogger_check(1) et les utilisateurs normaux n'auraient généralement pas besoin d'utiliser cette option, car le répertoire pour archive est soit implicite par archive s'il contient des composants de répertoire, soit le répertoire courant par défaut.

SYNTAXE DU FICHIER DE CONFIGURATION

Le fichier de configuration peut être spécifié avec l'option -c. S'il ne l'est pas, les spécifications de configuration sont lues depuis l'entrée standard.

Si conffile n'existe pas, une recherche est effectuée dans le répertoire $PCP_VAR_DIR/config/pmlogger pour un fichier du même nom, et si ce fichier est trouvé, il est utilisé. Par exemple, si config.mumble n'existe pas dans le répertoire courant et que le fichier $PCP_VAR_DIR/config/pmlogger/config.mumble existe, alors -c config.mumble et -c $PCP_VAR_DIR/config/pmlogger/config.mumble sont équivalents.

La syntaxe du fichier de configuration est la suivante.

1.
Les mots sont séparés par des espaces blancs (espace, tabulation ou nouvelle ligne).
2.
Le symbole "#" (dièse) introduit un commentaire, et tout texte jusqu'à la prochaine nouvelle ligne est ignoré.
3.
Les mots clés (affichés en gras ci-dessous) doivent apparaître littéralement (c'est-à-dire en minuscules).
4.
Chaque spécification commence par le mot clé optionnel log, suivi de l'un des états mandatory on, mandatory off, mandatory maybe, advisory on ou advisory off.
5.
Pour les états on, un intervalle de journalisation doit suivre en utilisant la syntaxe "once", ou "default", ou "every N timeunits", ou simplement "N timeunits" - N est un entier non signé, et timeunits est l'un des mots clés msec, millisecond, sec, second, min, minute, hour ou la forme plurielle de l'un des précédents.

Les limitations internes exigent que l'intervalle soit inférieur à (environ) 74 heures. Une valeur d'intervalle de zéro est synonyme de once. Un intervalle de default signifie utiliser l'intervalle de journalisation par défaut de 60 secondes ; cette valeur par défaut peut être modifiée à interval avec l'option de ligne de commande -t.

L'argument interval suit la syntaxe décrite dans PCPIntro(1), et sous sa forme la plus simple peut être un entier non signé (les unités implicites dans ce cas sont les secondes).
6.
Après les spécifications d'état et d'intervalle éventuel vient un "{", suivi d'une liste d'une ou plusieurs spécifications de métriques et d'un "}" de fermeture. La liste est séparée par des espaces blancs (ou des virgules). S'il n'y a qu'une seule spécification de métrique dans la liste, les accolades sont facultatives.
7.
Une spécification de métrique consiste en un nom de métrique facultativement suivi d'un ensemble de noms d'instances. Le nom de la métrique suit les conventions de nommage standard de PCP, voir PMNS(5), et si le nom de la métrique est un nœud non feuille dans le PMNS (voir PMNS(5)), alors pmlogger descendra récursivement le PMNS et appliquera la spécification de journalisation à tous les noms de métriques descendants qui sont des nœuds feuilles dans le PMNS. L'ensemble des noms d'instances est un "[", suivi d'une liste d'un ou plusieurs noms, nombres ou chaînes séparés par des espaces (ou des virgules), et un "]" de fermeture. Les éléments de la liste qui sont des nombres sont supposés être des identifiants d'instance internes, les autres éléments sont supposés être des identifiants d'instance externes - voir pmGetInDom(3) pour plus d'informations.

Si aucun instance n'est donné, la spécification de journalisation est appliquée à toutes les instances de la métrique associée.

8.
Il peut y avoir un nombre arbitraire de spécifications de journalisation.
9.
À partir de la version 4.0 de PCP et ultérieurement, toute spécification de nom de métrique qui ne se résout pas en un nœud feuille dans le PMNS est ajoutée à une liste interne.

PMDAs can dynamically create new metrics below a dynamic root node in their PMNS, and send a notification to clients that the PMNS has changed, see pmdaExtSetFlags(3) and in particular the METRIC CHANGES section for API details. This mechanism is currently supported by pmdaopenmetrics(1) and pmdammv(1). When a fetch issued by pmlogger returns with the PMDA_EXT_NAMES_CHANGE flag set, pmlogger will traverse the internal list of possible dynamic subtree nodes and dynamically discover any new metrics. In effect, as of PCP version 4.0 and later, pmlogger can be configured to dynamically log new metrics that appear in the future, after the configuration file is initially parsed.

Following all of the logging specifications, there may be an optional access control section, introduced by the literal token [access]. Thereafter come access control rules that allow or disallow operations from particular hosts or groups of hosts.

The operations may be used to interrogate or control a running pmlogger using pmlc(1) and fall into the following classes:

enquire
interrogate the status of pmlogger and the metrics it is logging
advisory
Change advisory logging.
mandatory
Change mandatory logging.
all
All of the above.

Access control rules are of the form ``allow hostlist : operationslist ;'' and ``disallow hostlist : operationslist ;''.

The hostlist follows the syntax and semantics for the access control mechanisms used by PMCD and are fully documented in pmcd(1). An operationslist is a comma separated list of the operations advisory, mandatory, enquire and all.

A missing [access] section allows all access and is equivalent to allow * : all;.

The configuration (either from standard input or conffile) is initially scanned by pmcpp(1) with the options -rs and -I $PCP_VAR_DIR/config/pmlogger. This extends the configuration file syntax with include file processing (%include), a common location to search for include files ($PCP_VAR_DIR/config/pmlogger), macro definitions (%define), macro expansion (%name and %{name}) and conditional inclusion of lines (%ifdef name ... %else ... %endif and %ifndef name ... %else ... %endif).

OPTIONS

The available command line options are:

-c conffile, --config=conffile
Specify the conffile file to use.
-C, --check
Parse configuration and exit.
-h host, --host=host
Fetch performance metrics from pmcd(1) on host, rather than from the default localhost.
-H hostname, --labelhost=hostname
Specify the hostname to use instead of the one returned by pmcd(1).
-I version, --pmlc-ipc-version=version
Normally, pmlogger and pmlc(1) will autonegotiate a mutually acceptable version for their private IPC channel. Use -I to force pmlogger to offer (at most) version as the version to be used. This option may be required if pmlogger needs to be managed by an older version of pmlc(1) that fails to autonegotiate correctly.
-K spec, --spec-local=spec
When fetching metrics from a local context (see -o), the -K option may be used to control the DSO PMDAs that should be made accessible. The spec argument conforms to the syntax described in pmSpecLocalPMDA(3). More than one -K option may be used.
-l logfile, --log=logfile
Write all diagnostics to logfile instead of the default pmlogger.log.
-L, --linger
Run even if not the primary logger instance and nothing to log.
-m note, --note=note
Append note to the port map file for this instance.
-n pmnsfile, --namespace=pmnsfile
Load an alternative Performance Metrics Name Space (PMNS(5)) from the file pmnsfile.
-N, --notify
Notify service manager such as systemd(1) as needed.
-o, --local-PMDA
Use a local context to collect metrics from DSO PMDAs on the local host without PMCD. See also -K.
-p PID, --PID=PID
Log specified metrics for the lifetime of the process identified by PID.
-P, --primary
Run as primary logger instance. See above for more detailed description of this.
-r, --report
Report record sizes and archive growth rate.
-s endsize, --size=endsize
Terminate after archive size exceeds endsize.
-t interval, --interval=interval
Specify the logging interval. The default value is 60 seconds. Please refer to the ENVIRONMENT and FILES sections below regarding the PMLOGGER_INTERVAL environment variable and its impact on the default logging interval.
-T endtime, --finish=endtime
Specify the endtime when to end logging.
-u
Use unbuffered output. This is the default (so this option does nothing).
-U username, --username=username
When in daemon mode, run as user username.
-v volsize, --volsize=volsize
Switch volumes after reaching archive volume size volsize.
-V version, --version=version
Specify archive version. The default and the only accepted value is 2.
-x fd
Allow asynchronous control requests on the file descriptor fd.
-y
Use local timezone instead of the timezone from the pmcd(1) host.
-?, --help
Display usage message and exit.

EXEMPLES

For each PCP utility, there is a sample pmlogger configuration file that could be used to create an archive suitable for replaying with that tool (i.e. includes all of the performance metrics used by the tool). For a tool named foo this configuration file is located in $PCP_VAR_DIR/config/pmlogger/config.foo.

The following is a simple default configuration file for a primary pmlogger instance, and demonstrates most of the capabilities of the configuration specification language.


log mandatory on once { hinv.ncpu hinv.ndisk }
log mandatory on every 10 minutes {
    disk.all.write
    disk.all.read
    network.interface.in.packets [ "et0" ]
    network.interface.out.packets [ "et0" ]
    nfs.server.reqs [ "lookup" "getattr" "read" "write" ]
}
log advisory on every 30 minutes {
    environ.temp
    pmcd.pdu_in.total
    pmcd.pdu_out.total
}
%include "macros.default"
%ifdef %disk_detail
log mandatory on %disk_detail_freq {
    disk.dev
}
%endif
[access]
disallow * : all except enquire;
allow localhost : mandatory, advisory;

CHANGEMENTS DE NOM D'HÔTE

The hostname of the PMCD that is providing metrics to pmlogger is used in several ways.

PMCD's hostname (or the argument from the -H option) is included in the archive label and may be used to ensure that subsequent operations on multiple archives, e.g. pmlogextract(1), are only applied to archives from the same host.

For pmlogger instances using a local PMCD that are launched and managed by pmlogger_check(1) and pmlogger_daily(1), (or the systemd(1) or cron(8) services that use these scripts), the local hostname may also be used to construct the name of a directory where all the archives for the one host are stored, e.g. $PCP_ARCHIVE_DIR/<hostname>.

And PMCD's hostname is also stored in the archive via the pmcd.pmlogger.hostname metrqui est utilisé dans le cadre des vérifications pour assurer la continuité des données de performance après la rotation des archives nocturnes par pmlogger_daily(1).

Le nom d'hôte de l'hôte PMCD peut changer pendant le démarrage lorsque le système passe d'un nom d'hôte temporaire à un nom d'hôte persistant, ou par action administrative explicite après le démarrage du système. Lorsque cela se produit, pmlogger peut avoir besoin d'actions spéciales, en particulier si l'instance pmlogger a été lancée depuis pmlogger_check(1) ou pmlogger_daily(1), alors pmlogger doit se terminer. Dans des circonstances normales systemd(1) ou cron(8) lancera un nouveau pmlogger peu de temps après, et cette nouvelle instance pmlogger fonctionnera dans le contexte du nouveau nom d'hôte pour l'hôte où PMCD est en cours d'exécution.

MÉTRIQUES DÉRIVÉES

Comme décrit dans pmRegisterDerived(3), les métriques dérivées fournissent un mécanisme pour étendre le PMNS avec de nouvelles métriques définies côté client PCP en utilisant des expressions sur les métriques de performance existantes. Les métriques dérivées peuvent être incluses dans un fichier de configuration pmlogger, mais elles sont soumises à des règles de traitement spéciales.

Premièrement, les valeurs d'une métrique dérivée, pas les métriques opérandes dans l'expression de la métrique dérivée, sont stockées dans l'archive. Ceci est dû au fait que la définition d'une métrique dérivée existe indépendamment de pmlogger et de l'archive et peut être différente, ou ne pas exister du tout, lors de la relecture de l'archive.

Pour éviter toute ambiguïté lors de la relecture de l'archive, l'identifiant de métrique de performance (PMID) de chaque métrique dérivée est réécrit (ou « re-mappé ») pour indiquer qu'il s'agissait, mais n'est plus, une métrique dérivée ; référez-vous à pmRegisterDerived(3) pour une description détaillée du re-mappage des PMID.

DIAGNOSTICS

Les archives sont suffisamment précieuses pour que pmlogger ne tronque pas un fichier physique existant. Un message de la forme

...: "foo.index" déjà existant, non écrasé
...: Fichier existant
indique que cette situation s'est produite. Vous devez explicitement supprimer les fichiers et relancer pmlogger.

Il ne peut y avoir qu'une seule instance pmlogger primaire par hôte surveillé ; tenter d'enfreindre cette règle produit l'erreur :

pmlogger : il y a déjà un pmlogger primaire en cours d'exécution

Divers autres messages relatifs à la création et/ou suppression de fichiers dans $PCP_TMP_DIR/pmlogger suggèrent un problème de permission sur ce répertoire, ou l'apparition de fichiers indésirables.

ENVIRONNEMENT

Normalement pmlogger crée un socket pour recevoir des messages de contrôle de pmlc(1) sur le premier port TCP/IP disponible numéroté 4330 ou supérieur. La variable d'environnement PMLOGGER_PORT peut être utilisée pour spécifier un numéro de port de départ alternatif.

Si définie à la valeur 1, la variable d'environnement PMLOGGER_LOCAL amènera pmlogger à s'exécuter en mode opérationnel localhost uniquement, où il se liera uniquement à l'interface de bouclage.

La variable PMLOGGER_REQUEST_TIMEOUT peut être définie par des applications telles que pmlc(1) pour spécifier un délai d'attente en secondes pour les demandes de connexion au port de contrôle pmlogger. Si elle n'est pas définie, les connexions peuvent se bloquer indéfiniment. Cette variable ne serait normalement pas définie par pmlogger lui-même.

La variable PMLOGGER_MAXPENDING peut être définie pour indiquer la longueur maximale que la file d'attente des connexions pmlc en attente peut atteindre.

L'intervalle d'échantillonnage par défaut utilisé par pmlogger peut être défini à l'aide de la variable PMLOGGER_INTERVAL (si elle n'est pas définie, 60 secondes seront utilisées). La ligne de commande et les directives dans le fichier de configuration remplaceront cette valeur. Il s'agit d'un entier en secondes.

Sur les plateformes utilisant systemd(1), et lorsque l'option -N est donnée, la variable d'environnement NOTIFY_SOCKET serait normalement définie par le gestionnaire de service avant le lancement de pmlogger.

Deux variables d'environnement supplémentaires sont utilisées dans le cadre du passage de relais d'une instance pmlogger à la suivante lors d'une opération de re-exec, à savoir __PMLOGGER_REEXEC et __PMLOGGER_TZ. Les détails de leur utilisation sont un détail d'implémentation interne, mais les utilisateurs finaux devraient éviter d'utiliser des variables de ces noms dans l'environnement de leur shell.

ENVIRONNEMENT PCP

Les variables d'environnement avec le préfixe PCP_ sont utilisées pour paramétrer les noms de fichiers et de répertoires utilisés par PCP. Sur chaque installation, le fichier /etc/pcp.conf contient les valeurs locales pour ces variables. La variable $PCP_CONF peut être utilisée pour spécifier un fichier de configuration alternatif, comme décrit dans pcp.conf(5).

OPTIONS DE DÉBOGAGE

L'option -D ou --debug active la sortie de diagnostics supplémentaires sur stderr pour aider au dépannage, bien que les informations soient parfois cryptiques et principalement destinées à guider les développeurs plutôt que les utilisateurs finaux. debug est une liste d'options de débogage séparées par des virgules ; utilisez pmdbg(1) avec l'option -l pour obtenir une liste des options de débogage disponibles et leur signification.

Les options de débogage spécifiques à pmlogger sont les suivantes :

Option Description
appl0 PDUs de requête de contrôle vers et depuis pmlc(1)
appl1 échange d'identifiants
appl2 diagnostics de la boucle d'alarme (temporelle), travail de rappel et messages de mode de contrôle d'enregistrement
appl3 rappels de signaux et journalisation de sortie
appl4 horodatage des enregistrements dans le logfile lorsque les étapes clés sont atteintes
appl5 statistiques PDU après le traitement du fichier conffile
appl6 construction du cache de métadonnées à partir de conffile pour améliorer les performances de démarrage, travail de pass0()
appl7 suppression de la construction du cache de métadonnées, pass0() devient une opération nulle
appl8 mises à jour et requêtes hist_hash pour prendre en charge la commande query de pmlc(1)
