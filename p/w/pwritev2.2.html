readv(2) Manuel des appels système readv(2)

NOM

readv, writev, preadv, pwritev, preadv2, pwritev2 - lire ou écrire des données dans plusieurs tampons

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <sys/uio.h>
ssize_t readv(int fd, const struct iovec *iov, int iovcnt);
ssize_t writev(int fd, const struct iovec *iov, int iovcnt);
ssize_t preadv(int fd, const struct iovec *iov, int iovcnt,
                off_t offset);
ssize_t pwritev(int fd, const struct iovec *iov, int iovcnt,
                off_t offset);
ssize_t preadv2(int fd, const struct iovec *iov, int iovcnt,
                off_t offset, int flags);
ssize_t pwritev2(int fd, const struct iovec *iov, int iovcnt,
                off_t offset, int flags);
Exigences de Macro de Test de Fonctionnalité pour glibc (voir feature_test_macros(7)):

preadv(), pwritev():

    Depuis glibc 2.19:
        _DEFAULT_SOURCE
    glibc 2.19 et versions antérieures:
        _BSD_SOURCE

DESCRIPTION

L'appel système readv() lit iovcnt tampons à partir du fichier associé au descripteur de fichier fd dans les tampons décrits par iov ("scatter input").

L'appel système writev() écrit iovcnt tampons de données décrits par iov dans le fichier associé au descripteur de fichier fd ("gather output").

Le pointeur iov pointe vers un tableau de structures iovec, décrites dans iovec(3type).

L'appel système readv() fonctionne comme read(2) sauf que plusieurs tampons sont remplis.

L'appel système writev() fonctionne comme write(2) sauf que plusieurs tampons sont écrits.

Les tampons sont traités dans l'ordre du tableau. Cela signifie que readv() remplit complètement iov[0] avant de passer à iov[1], et ainsi de suite. (S'il n'y a pas assez de données, tous les tampons pointés par iov ne seront peut-être pas remplis.) De même, writev() écrit le contenu entier de iov[0] avant de passer à iov[1], et ainsi de suite.

Les transferts de données effectués par readv() et writev() sont atomiques : les données écrites par writev() sont écrites comme un seul bloc qui n'est pas mélangé avec les sorties des écritures d'autres processus ; de manière analogue, readv() est garanti de lire un bloc de données contigu du fichier, quelles que soient les opérations de lecture effectuées dans d'autres threads ou processus qui ont des descripteurs de fichier faisant référence à la même description de fichier ouverte (voir open(2)).

preadv() et pwritev()

L'appel système preadv() combine les fonctionnalités de readv() et pread(2). Il effectue la même tâche que readv(), mais ajoute un quatrième argument, offset, qui spécifie le décalage dans le fichier où l'opération de lecture doit être effectuée.

L'appel système pwritev() combine les fonctionnalités de writev() et pwrite(2). Il effectue la même tâche que writev(), mais ajoute un quatrième argument, offset, qui spécifie le décalage dans le fichier où l'opération d'écriture doit être effectuée.

Le décalage dans le fichier n'est pas modifié par ces appels système. Le fichier référencé par fd doit être capable de recherche.

preadv2() et pwritev2()

Ces appels système sont similaires aux appels preadv() et pwritev(), mais ajoutent un cinquième argument, flags, qui modifie le comportement de manière spécifique à l'appel.

Contrairement à preadv() et pwritev(), si l'argument offset est -1, alors le décalage actuel du fichier est utilisé et mis à jour.

L'argument flags contient un OR bit à bit de zéro ou plus des indicateurs suivants :

RWF_DSYNC (depuis Linux 4.7)
Fournit un équivalent par écriture du drapeau O_DSYNC de open(2). Cet indicateur n'est pertinent que pour pwritev2(), et son effet s'applique uniquement à la plage de données écrite par l'appel système.
RWF_HIPRI (depuis Linux 4.6)
Lecture/écriture haute priorité. Permet aux systèmes de fichiers basés sur des blocs d'utiliser le sondage du périphérique, ce qui offre une latence plus faible, mais peut utiliser des ressources supplémentaires. (Actuellement, cette fonctionnalité n'est utilisable qu'avec un descripteur de fichier ouvert à l'aide de l'indicateur O_DIRECT.)
RWF_SYNC (depuis Linux 4.7)
Fournit un équivalent par écriture du drapeau O_SYNC de open(2). Cet indicateur n'est pertinent que pour pwritev2(), et son effet s'applique uniquement à la plage de données écrite par l'appel système.
RWF_NOWAIT (depuis Linux 4.14)
Ne pas attendre les données qui ne sont pas immédiatement disponibles. Si cet indicateur est spécifié, l'appel système preadv2() retournera instantanément s'il devait lire des données depuis le stockage de fond ou attendre un verrou. Si des données ont été lues avec succès, il retournera le nombre d'octets lus. S'il n'y a eu aucune lecture d'octet, il retournera -1 et définira errno à EAGAIN (mais voir BUGS). Actuellement, cet indicateur n'est pertinent que pour preadv2().
RWF_APPEND (depuis Linux 4.16)
Fournit un équivalent par écriture du drapeau O_APPEND de open(2). Cet indicateur n'est pertinent que pour pwritev2(), et son effet s'applique uniquement à la plage de données écrite par l'appel système. L'argument offset n'affecte pas l'opération d'écriture ; les données sont toujours ajoutées à la fin du fichier. Cependant, si l'argument offset est -1, le décalage actuel du fichier est mis à jour.
RWF_NOAPPEND (depuis Linux 6.9)
Ne pas tenir compte du drapeau O_APPEND de open(2). Cet indicateur n'est pertinent que pour pwritev2(). Historiquement, Linux tenait compte du drapeau O_APPEND s'il était défini et ignorait l'argument offset, ce qui est un bug. Pour pwritev2(), l'argument offset est respecté comme prévu si le drapeau RWF_NOAPPEND est défini, comme si le drapeau O_APPEND n'était pas défini.
RWF_ATOMIC (depuis Linux 6.11)
Exige que les écritures dans les fichiers réguliers des systèmes de fichiers basés sur des blocs soient effectuées avec une protection contre les écritures en déchirement (torn-write protection). La protection contre les écritures en déchirement signifie qu'en cas de défaillance de courant ou autre défaillance matérielle, tout ou partie des données de l'écriture seront stockées, mais jamais un mélange d'anciennes et de nouvelles données. Cet indicateur n'est pertinent que pour pwritev2(), et son effet s'applique uniquement à la plage de données écrite par l'appel système. La longueur totale de l'écriture doit être une puissance de 2 et sa taille doit être comprise dans la plage [stx_atomic_write_unit_min, stx_atomic_write_unit_max]. L'écriture doit être effectuée à un décalage naturellement aligné dans le fichier par rapport à la longueur totale de l'écriture. Par exemple, une écriture de 32 Kio à un décalage de fichier de 32 Kio est autorisée, cependant une écriture de 32 Kio à un décalage de fichier de 48 Kio n'est pas autorisée. La limite supérieure de iovcnt pour pwritev2() est donnée par la valeur dans stx_atomic_write_segments_max. La protection contre les écritures en déchirement ne fonctionne qu'avec le drapeau O_DIRECT, c'est-à-dire que les écritures mises en tampon ne sont pas prises en charge. Pour garantir la cohérence de l'écriture entre l'état en mémoire du fichier et le périphérique de stockage, O_SYNC ou O_DSYNC doivent être spécifiés pour open(2). Les mêmes garanties d'E/S synchronisées que celles décrites dans open(2) sont fournies lorsque ces drapeaux ou leurs équivalents (par exemple, si RWF_SYNC est spécifié pour pwritev2()) sont utilisés.
RWF_DONTCACHE (depuis Linux 6.14)

pwritev2(2) — archlinux man pages

NAME

pwritev, pwritev2, preadv, preadv2 - I/O scatter/gather pour un descripteur de fichier à un offset spécifié

LIBRARY

Bibliothèque C standard (libc, -lc)

SYNOPSIS

#include <sys/uio.h>

ssize_t pwritev(int fd, const struct iovec *iov, int iovcnt, off_t offset);

ssize_t pwritev2(int fd, const struct iovec *iov, int iovcnt, off_t offset, unsigned int flags);

ssize_t preadv(int fd, const struct iovec *iov, int iovcnt, off_t offset);

ssize_t preadv2(int fd, const struct iovec *iov, int iovcnt, off_t offset, unsigned int flags);

DESCRIPTION

Les appels système readv() et writev() effectuent des opérations d'E/S sur un descripteur de fichier donné, fd, en lisant ou écrivant des données depuis ou vers des emplacements mémoire spécifiés par un tableau de structures iovec. Le tableau est décrit par iov et contient iovcnt éléments.

Les appels système preadv() et pwritev() sont identiques à readv() et writev() respectivement, mais ils effectuent l'opération à un décalage absolu spécifié par offset dans le fichier. Ils n'affectent pas le pointeur de fichier du descripteur de fichier. Les lectures et écritures sont atomiques par rapport aux autres opérations qui peuvent modifier le pointeur de fichier, comme lseek(2).

L'appel système preadv2() est identique à preadv(), mais accepte un argument supplémentaire flags qui modifie le comportement de l'opération. Les valeurs suivantes peuvent être définies dans flags :

RWF_APPEND
L'écriture se fait à la fin du fichier. Le décalage spécifié par offset est ignoré. Cette opération est atomique : le fichier est ouvert avec l'indicateur O_APPEND.
RWF_NOWAIT
L'opération est non bloquante. Si l'opération ne peut pas être terminée immédiatement (par exemple, si elle doit attendre des données ou de l'espace disque), elle renvoie immédiatement EAGAIN. Le succès ou l'échec de l'opération peut être déterminé ultérieurement en utilisant io_uring_enter(2) avec le drapeau IORING_ENTER_GETEVENTS.
RWF_DSYNC
Effectuer une écriture synchrone des données. L'écriture se termine une fois que les données ont été écrites sur le périphérique de stockage. Cela est similaire à open(2) avec O_DSYNC.
RWF_HIPRI
Marquer l'opération comme ayant une priorité élevée. Cela peut être utilisé pour gérer la qualité de service ; cependant, la sémantique exacte dépend du système de fichiers et du matériel sous-jacent.
RWF_SYNC
Effectuer une écriture synchrone des données et des métadonnées. L'écriture se termine une fois que les données et les métadonnées associées ont été écrites sur le périphérique de stockage. Cela est similaire à open(2) avec O_SYNC.
RWF_DONTCACHE
Les lectures ou écritures sur un fichier régulier purgeront le contenu mis en cache de la page une fois l'opération terminée. Ceci est différent des E/S mises en cache normales, où les données restent généralement en cache jusqu'à ce qu'elles soient récupérées en raison de la pression de la mémoire. Si des plages de l'E/S lue ou écrite étaient déjà en cache avant cette lecture ou écriture, alors ces plages ne seront pas purgées au moment de l'achèvement de l'E/S.

De plus, toute plage salie par une opération d'écriture avec RWF_DONTCACHE défini sera envoyée pour écriture. Ceci est similaire à l'appel de sync_file_range(2) avec SYNC_FILE_RANGE_WRITE pour démarrer l'écriture sur la plage donnée. RWF_DONTCACHE est un indice, ou un meilleur effort, où aucune garantie stricte n'est donnée sur l'état du cache de page une fois l'opération terminée.

S'il est utilisé sur un système de fichiers ou un périphérique de bloc qui ne le prend pas en charge, il renverra -1, et errno sera défini à EOPNOTSUPP.

RETURN VALUE

En cas de succès, readv(), preadv(), et preadv2() renvoient le nombre d'octets lus ; writev(), pwritev(), et pwritev2() renvoient le nombre d'octets écrits.

Notez qu'il ne s'agit pas d'une erreur pour un appel réussi de transférer moins d'octets que demandé (voir read(2) et write(2)).

En cas d'erreur, -1 est renvoyé, et errno est défini pour indiquer l'erreur.

ERRORS

Les erreurs sont celles données pour read(2) et write(2). De plus, preadv(), preadv2(), pwritev(), et pwritev2() peuvent également échouer pour les mêmes raisons que lseek(2). De plus, les erreurs suivantes sont définies :

EINVAL
La somme des valeurs iov_len déborde une valeur ssize_t.
EINVAL
Si RWF_ATOMIC est spécifié, la combinaison de la somme des valeurs iov_len et de la valeur offset n'est pas conforme aux règles de protection contre les écritures déchirées en longueur et en décalage.
EINVAL
Le nombre de vecteurs, iovcnt, est inférieur à zéro ou supérieur au maximum autorisé. Si RWF_ATOMIC est spécifié, ce maximum est donné par la valeur stx_atomic_write_segments_max de statx.
EOPNOTSUPP
RWF_DONTCACHE était défini dans flags et le fichier ne le prend pas en charge.
EOPNOTSUPP
Un drapeau inconnu est spécifié dans flags.

VERSIONS

C library/kernel differences

Les appels système bruts preadv() et pwritev() ont des signatures d'appel qui diffèrent légèrement de celles des fonctions d'enrobage de la bibliothèque C GNU correspondantes montrées dans le SYNOPSIS. Le dernier argument, offset, est décomposé par les fonctions d'enrobage en deux arguments dans les appels système :

unsigned long pos_l, unsigned long pos

Ces arguments contiennent, respectivement, les 32 bits de poids faible et de poids fort de offset.

Historical C library/kernel differences

Pour faire face au fait que IOV_MAX était si bas sur les premières versions de Linux, les fonctions d'enrobage de glibc pour readv() et writev() faisaient un travail supplémentaire si elles détectaient que l'appel système sous-jacent échouait parce que cette limite était dépassée. Dans le cas de readv(), la fonction d'enrobage allouait un tampon temporaire suffisamment grand pour tous les éléments spécifiés par iov, passait ce tampon dans un appel à read(2), copiait les données du tampon vers les emplacements spécifiés par les champs iov_base des éléments de iov, puis libérait le tampon. La fonction d'enrobage pour writev() effectuait la tâche analogue en utilisant un tampon temporaire et un appel à write(2).

Le besoin de cet effort supplémentaire dans les fonctions d'enrobage de glibc a disparu avec Linux 2.2 et les versions ultérieures. Cependant, glibc a continué à fournir ce comportement jusqu'à glibc 2.10. À partir de glibc 2.9, les fonctions d'enrobage ne fournissent ce comportement que si la bibliothèque détecte que le système exécute un noyau Linux plus ancien que Linux 2.6.18 (une version de noyau sélectionnée de manière arbitraire). Et depuis glibc 2.20 (qui nécessite un minimum de Linux 2.6.32), les fonctions d'enrobage de glibc invoquent toujours directement les appels système.

NOTES

POSIX.1 permet à une implémentation de limiter le nombre d'éléments qui peuvent être passés dans iov. Une implémentation peut annoncer sa limite en définissant IOV_MAX dans <limits.h> ou au moment de l'exécution via la valeur de retour de sysconf(_SC_IOV_MAX). Sur les systèmes Linux modernes, la limite est de 1024. À l'époque de Linux 2.0, cette limite était de 16.

BUGS

Linux 5.9 et Linux 5.10 ont un bug où preadv2() avec le drapeau RWF_NOWAIT peut renvoyer 0 même lorsqu'il n'est pas à la fin du fichier.

EXAMPLES

L'exemple de code suivant démontre l'utilisation de writev :


char          *str0 = "hello ";
char          *str1 = "world\n";
ssize_t       nwritten;
struct iovec  iov[2];
iov[0].iov_base = str0;
iov[0].iov_len = strlen(str0);
iov[1].iov_base = str1;
iov[1].iov_len = strlen(str1);
nwritten = writev(STDOUT_FILENO, iov, 2);
