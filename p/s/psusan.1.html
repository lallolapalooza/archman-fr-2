NOM

psusan - pseudo-SSH pour réseaux inintercepables, authentifiés séparément

SYNOPSIS

psusan [ options ]

DESCRIPTION

psusan est un programme serveur qui se comporte comme la couche de `connexion' la plus interne d'une session SSH, sans les deux couches de sécurité externes de chiffrement et d'authentification. Il fournit toutes les fonctionnalités post-authentification d'une connexion SSH :

•
choisir s'il faut exécuter une session de terminal interactive ou une seule commande spécifiée
•
plusieurs sessions de terminal à la fois (ou un mélange de celles-ci et de commandes spécifiées)
•
transfert de fichiers SFTP
•
toutes les options standard de transfert de port SSH
•
transfert X11
•
transfert d'agent SSH

Le hic, c'est que, comme il manque les couches externes de SSH, vous devez l'exécuter sur une sorte de canal de données déjà authentifié comme le bon utilisateur, et qui est déjà protégé à votre satisfaction contre l'écoute clandestine et le détournement de session. Une bonne règle empirique est que tout canal sur lequel vous étiez prêt à exécuter une session shell *nue*, vous pouvez y exécuter psusan à la place, ce qui ajoute toutes les commodités ci-dessus sans changer les propriétés de sécurité.

Le protocole que psusan utilise est également parlé par PuTTY, Plink, PSCP et PSFTP, si vous sélectionnez le type de protocole `Bare ssh-connection' ou l'option de ligne de commande -ssh-connection et spécifiez le chemin absolu du socket Unix-domaine approprié à la place d'un nom d'hôte.

EXEMPLES

L'idée d'un canal de données sécurisé et pré-authentifié semble étrange aux personnes qui pensent aux connexions *réseau*. Mais il existe de nombreux exemples dans le contexte d'un seul système Unix, et c'est là que psusan est généralement utile.

Docker

Un bon exemple est le canal console ou I/O standard menant à un conteneur ou à un système de virtualisation. Docker est un exemple familier. Si vous souhaitez démarrer un conteneur Docker et exécuter un shell directement à l'intérieur, vous pourriez dire quelque chose comme

docker run -i -t some:image

ce qui vous permettra d'exécuter une seule session shell à l'intérieur du conteneur, dans le même terminal à partir duquel vous avez démarré Docker.

Supposons que vous préfériez exécuter *plusieurs* sessions shell dans le même conteneur à la fois (peut-être pour que l'une d'elles puisse utiliser des outils de débogage pour examiner ce que fait l'autre). Et peut-être qu'à l'intérieur de ce conteneur, vous allez exécuter un programme auquel vous ne faites pas entièrement confiance avec un accès complet à votre réseau, mais vous êtes prêt à le laisser établir une ou deux connexions réseau spécifiques du type que vous pourriez configurer avec un transfert de port SSH.

Dans ce cas, vous pouvez supprimer l'option -t de cette ligne de commande Docker (qui signifie `allouer un périphérique de terminal'), et lui dire d'exécuter psusan à l'intérieur du conteneur :

docker run -i some:image /some/path/to/psusan

(Bien sûr, vous devrez vous assurer que psusan est installé quelque part à l'intérieur de l'image du conteneur.)

Si vous faites cela à partir d'une ligne de commande shell, vous verrez une ligne de bannière ressemblant à ceci :

SSHCONNECTION@putty.projects.tartarus.org-2.0-PSUSAN_Release_0.75

ce qui n'est pas particulièrement utile, sauf que cela vous indique que psusan a démarré avec succès.

Pour communiquer *utilement* avec ce serveur, vous pouvez configurer une session enregistrée PuTTY comme suit :

•
Définissez le protocole sur `Bare ssh-connection' (le protocole psusan).
•
Écrivez *quelque chose* dans la case du nom d'hôte. Cela apparaîtra dans la barre de titre de la fenêtre PuTTY (si vous utilisez PuTTY GUI), vous pourriez donc vouloir écrire quelque chose qui vous rappellera quel type de fenêtre il s'agit. Si vous n'avez pas d'avis, quelque chose de générique comme `dummy' fera l'affaire.
•
Dans le panneau de configuration `Proxy', définissez le type de proxy sur `Local', et entrez la commande `docker run' ci-dessus dans la zone de texte `Telnet command, or local proxy command'.
•
Dans le panneau de configuration `SSH', vous voudrez très probablement activer le partage de connexion. (Voir ci-dessous.)

Cela permet que lorsque PuTTY démarre, il exécute la commande Docker comme indiqué ci-dessus au lieu de faire une connexion réseau, et communique avec cette commande en utilisant le protocole de type SSH psusan.

L'effet est que vous obtiendrez toujours une session shell dans le contexte d'un conteneur Docker. Mais cette fois, il dispose de toutes les commodités SSH. Si vous activez également le partage de connexion dans le panneau de configuration `SSH', alors l'option `Duplicate Session' vous obtiendra un deuxième shell dans le *même* conteneur Docker (au lieu d'un shell principal dans une instance séparée). Vous pouvez transférer des fichiers depuis et vers le conteneur pendant son exécution en utilisant PSCP ou PSFTP ; vous pouvez transférer des ports réseau, des programmes X11 et/ou un agent SSH vers le conteneur.

Bien sûr, une autre façon de faire tout cela serait d'exécuter le protocole SSH *complet* sur le même canal. Cela implique plus de configuration : vous devez inventer une clé d'hôte SSH pour le conteneur, l'accepter dans le client, et gérer le fait qu'elle reste dans le cache des clés d'hôte de votre client lorsque le conteneur est supprimé. Et vous devez configurer des informations de connexion dans le conteneur : soit configurer un mot de passe, et le saisir dans le client, soit copier la moitié publique d'une clé SSH que vous aviez déjà. Et toutes ces précautions sont *inutiles*, car ce sont toutes des précautions que vous devez prendre lorsque la connexion entre deux systèmes passe par un réseau hostile. Dans ce cas, elle ne passe que par un canal IPC du noyau qui est garanti d'aller au bon endroit, donc ces précautions de sécurité sont redondantes, et elles n'ajoutent qu'une gêne.

User-mode Linux

User-mode Linux est un autre type de conteneur auquel vous pouvez vous connecter de la même manière. Voici un petit exemple concret.

La manière la *plus simple* d'exécuter UML est d'utiliser son type de système de fichiers `hostfs' pour donner au noyau invité accès au même système de fichiers virtuel que vous avez sur l'hôte. Par exemple, une ligne de commande comme celle-ci vous donne une invite de shell à l'intérieur d'une instance UML partageant votre système de fichiers existant :

linux mem=512M rootfstype=hostfs rootflags=/ rw init=/bin/bash

Si vous exécutez cela à une ligne de commande (en supposant que vous ayez un noyau UML disponible dans votre chemin sous le nom de `linux'), vous devriez voir de nombreux messages de démarrage du noyau, suivis d'une invite de shell ressemblant à

root@(none):/#

Pour convertir cela en une session UML basée sur psusan, nous devons ajuster la ligne de commande afin qu'au lieu d'exécuter bash, elle exécute psusan. Mais exécuter psusan directement n'est pas suffisant, car psusan dépendra d'une petite quantité de configuration, comme avoir /proc monté. Nous définissons donc le processus d'initialisation sur un script shell qui fera la configuration nécessaire et *ensuite* invoquera psusan.

De plus, exécuter psusan directement sur le périphérique console UML est une mauvaise idée, car le protocole binaire psusan sera mélangé avec les messages texte de la console. Il est donc préférable de rediriger la console de l'UML vers la sortie d'erreur standard du processus linux, et de mapper son entrée et sa sortie standard à un port série. La ligne de commande UML de remplacement pourrait donc ressembler à ceci :

linux mem=512M rootfstype=hostfs rootflags=/ rw \
    con=fd:2,fd:2 ssl0=fd:0,fd:1 init=/some/path/to/uml-psusan.sh

Et le script de configuration uml-psusan.sh pourrait ressembler à ceci :

#!/bin/bash
# Mise en place des pseudo-systèmes de fichiers vitaux
mount -t proc none /proc
mount -t devpts none /dev/pts
# Redirection des E/S vers le port série, mais la sortie d'erreur vers la console
exec 0<>/dev/ttyS0 1>&0 2>/dev/console
# Mise du port série en mode brut, pour exécuter un protocole binaire
stty raw -echo
# Choisir quel shell exécuter dans psusan
export&#x
00A0;SHELL=/bin/bash # Configurer un chemin par défaut export PATH=/usr/local/bin:/usr/local/sbin:/usr/bin:/usr/sbin:/bin:/sbin # Et maintenant, exécuter psusan sur le port série exec /home/simon/src/putty/misc/psusan

Configurez ensuite une session enregistrée PuTTY comme dans l'exemple Docker ci-dessus. Essentiellement, vous voudrez utiliser la commande linux ci-dessus comme commande proxy locale. Cependant, il est préférable de l'encapsuler dans setsid(1), car lorsque UML se termine, il tue tout son groupe de processus. Il est donc préférable que PuTTY ne fasse pas partie de ce groupe et qu'il ait la possibilité de s'arrêter proprement par lui-même. Vous finirez donc probablement par configurer la commande proxy pour qu'elle ressemble davantage à ceci :

setsid linux mem=512M rootfstype=hostfs rootflags=/ rw \
    con=fd:2,fd:2 ssl0=fd:0,fd:1 init=/some/path/to/uml-psusan.sh

Vous constaterez peut-étre aussi que vous devrez activer le contournement de bug qui indique que le serveur `Rejette les données envoyées avant son message d'accueil', car sinon le message d'accueil du protocole sortant de PuTTY peut êt;re perdu accidentellement pendant le démarrage de l'UML. (Voir le bug Debian #991958.)

Une fois que vous aurez fait cela, vous aurez une session PuTTY qui démarrera une instance UML propre lorsque vous l'exécuterez, et (si vous avez activé le partage de connexion) d'autres instances de la même session se connecteront à la même instance à nouveau.

Sous-système Windows pour Linux

Sous Windows, la manière par défaut d'utiliser WSL est d'exécuter le programme wsl, ou l'une de ses alias, dans une console Windows, soit en le lançant depuis une invite de commande existante, soit en utilisant un raccourci qui l'ouvre dans une nouvelle console. Cela vous donne un environnement de terminal Linux, mais dans une fenêt;re de console Windows.

Si vous préférez interagir avec le même environnement en utilisant PuTTY comme terminal (par exemple, si vous préférez les raccourcis souris de PuTTY pour copier-coller), vous pouvez le configurer en installant psusan dans l'environnement Linux, puis en configurant une session enregistrée PuTTY qui communique avec lui. Une bonne façon de faire cela est d'utiliser le nom de la distribution WSL comme `nom d'hôte' :

•
définissez la commande proxy locale sur `wsl -d %host /usr/local/bin/psusan' (ou partout où vous avez installé psusan dans le système Linux)
•
entrez le nom d'une distribution WSL particulière dans la zone du nom d'hôte. (Par exemple, si vous avez installé WSL Debian de la manière standard depuis le magasin Windows, ce sera simplement `Debian'.)
•
définissez le protocole sur `Connexion ssh nue', comme d'habitude.

Comme tous les autres exemples ici, cela vous permet également de transférer des ports entrants et sortants de l'environnement WSL (par exemple, exposer un service réseau WSL2 via le NAT interne de l'hyperviseur), de le transférer dans Pageant, et ainsi de suite.

Cygwin

Un autre environnement de type Unix sous Windows est Cygwin. Il est livré avec sa propre application de terminal graphique, mintty (qui se trouve êt;tre un dérivé de PuTTY) ; mais si vous préférez utiliser PuTTY lui-même pour communiquer avec vos sessions de terminal Cygwin, psusan peut aider.

Pour ce faire, vous devrez d'abord compiler les outils Unix de PuTTY dans Cygwin (via la méthode cmake habituelle). Ensuite, copiez le psusan.exe résultant dans le répertoire /bin de Cygwin. (Il doit êt;re dans ce répertoire pour que les programmes non-Cygwin puissent l'exécuter ; sinon, il ne pourra pas trouver la DLL Cygwin au démarrage.)

Configurez ensuite votre session enregistrée PuTTY comme suit :

•
définissez la commande proxy locale pour exécuter psusan.exe via son véritable chemin Windows. Vous pourriez aussi vouloir ajouter l'option --sessiondir afin que les sessions shell démarrent dans votre répertoire personnel Cygwin. Par exemple, vous pourriez utiliser la commande `c:\cygwin64\bin\psusan.exe --sessiondir /home/simon' (en changeant le nom du chemin et le nom d'utilisateur pour correspondre à votre configuration).
•
entrez n'importe quoi dans la zone du nom d'hôte ; `Cygwin' est probablement un bon choix
•
définissez le protocole sur `Connexion ssh nue', comme d'habitude.

Le transfert de ports n'est probablement pas très utile dans ce cas, car Cygwin partage le même espace de ports réseau que la machine hôte. Mais l'activation du transfert d'agent est utile, car le client SSH en ligne de commande de Cygwin peut alors communiquer avec Pageant sans aucune configuration supplémentaire.

schroot

Un autre exemple d'environnement de type conteneur est la disposition de système de fichiers alternative mise en place par schroot(1).

schroot est un autre programme qui, par défaut, exécute une session shell interactive dans le terminal depuis lequel vous l'avez lancé. Mais encore une fois, vous pouvez obtenir une connexion psusan dans l'environnement schroot en configurant une session enregistrée PuTTY dont la commande proxy locale est similaire à

schroot -c chroot-name /some/path/to/psusan

Selon la proportion de l'environnement chroot copiée de votre environnement principal, vous trouverez peut-êt;re que cela facilite, par exemple, l'exécution de programmes X11 dans le chroot qui ouvrent des fenêt;tres sur votre affichage X principal, ou le transfert de fichiers entrants et sortants du chroot.

Entre espaces de nom réseau

Si vous avez configuré plusieurs espaces de noms réseau sur un système Linux, avec des configurations TCP/IP différentes, alors psusan peut servir de passerelle pratique non privilégiée entre eux, si vous l'exécutez en tant qu'utilisateur non root dans l'espace de noms non par défaut de vos espaces, en écoutant les connexions sur un socket de domaine Unix.

Si vous le faites, cela vous donne un contrôle pratique sur les connexions réseau sortantes qui utilisent quelle configuration TCP/IP : vous pouvez utiliser PuTTY pour exécuter une session shell dans le contexte de l'autre espace de noms si vous voulez exécuter des commandes comme ping, ou vous pouvez configurer des transferts de ports individuels ou même un serveur SOCKS afin que les processus s'exécutant dans un espace de noms puissent envoyer leurs connexions réseau via l'autre.

Pour cette application, il est probablement plus pratique d'utiliser l'option --listen dans psusan, qui le fait fonctionner comme un serveur et écouter les connexions sur un socket de domaine Unix. Vous pouvez ensuite saisir ce nom de socket dans le champ de configuration du nom d'hôte de PuTTY (et sélectionner également l'option de protocole `Connexion ssh nue'), pour vous connecter à ce socket comme s'il s'agissait d'un client SSH.

Pourvu que le socket de domaine Unix soit à l'intérieur d'un répertoire auquel seul le bon utilisateur a accès, cela garantira que l'authentification se fait implicitement par le noyau Linux.

Entre identifiants utilisateur, via GNU userv

Si vous utilisez plusieurs identifiants utilisateur sur la même machine, par exemple à des fins de séparation des privilèges (exécuter un programme moins fiable avec des capacités limitées d'accès à tout votre matériel), alors vous avez probablement un compte `par défaut' ou le plus privilégié où vous exécutez votre session de connexion principale, et vous avez parfois besoin d'exécuter un shell dans un autre compte.

psusan peut êt;re utilisé comme canal d'accès entre les comptes, en utilisant GNU userv(1) comme transport. Dans le compte auquel vous voulez accéder, écrivez une stanza de configuration userv similaire à

if (glob service psusan & glob calling-user my-main-account-name)
   reset
   execute /some/path/to/psusan
fi

Cela donne à votre compte principal le droit d'exécuter la commande

userv my-sub-account-name psusan

et vous pouvez configurer ce nom de commande comme commande proxy locale PuTTY, de la même manière que la plupart des exemples précédents.

Bien sûr, il existe déjà de nombreuses façons d'accéder à un compte local depuis un autre, comme sudo. Un avantage de procéder ainsi est que vous n'avez pas besoin que l'administrateur système intervienne lorsque vous souhaitez modifier les contrôles d'accès (par exemple, modifier quels de vos comptes ont accès à un autre) : tant que vous avez un moyen quelconque d'accéder à chaque compte en premier lieu, et que userv est installé, vous pouvez apporter d'autres modifications de configuration sans avoir à déranger le superutilisateur.

Un autre avantage est que cela peut faciliter le transfert de fichiers entre les comptes. Si vous faites partie des personnes qui gardent vos répertoires personnels privés, il est difficile de copier un fichier d'un de vos comptes vers un autre en utilisant simplement la commande cp, car il n'y a aucun endroit pratique où le laisser dans un compte où l'autre peut le lire. Mais avec psusan sur userv, vous n'avez pas besoin d'un espace de système de fichiers partagé : vous pouvez transférer des fichiers en scp dans les deux sens sans aucune difficulté.

OPTIONS

Les options de ligne de commande prises en charge par psusan sont :

--listen nom-socket-unix
Exécute psusan en mode d'écoute. nom-socket-unix est le chemin d'accès d'un socket de domaine Unix sur lequel écouter. Vous devez vous assurer que ce chemin d'accès se trouve dans un répertoire dont les permissions de lecture et d'exécution sont restreintes uniquement à l'utilisateur (ou aux utilisateurs) auquel vous souhaitez autoriser l'accès à l'environnement dans lequel psusan s'exécute.

Le socket d'écoute doit êt;re un socket de domaine Unix. psusan ne fournit pas d'option pour fonctionner sur TCP/IP, car la nature non authentifiée du protocole le rendrait intrinsèquement sécurité non sûre.

--listen-once
En mode d'écoute, cette option fait en sorte que psusan n'attende qu'une seule connexion et se termine immédiatement après la fin de cette connexion.
--sessiondir chemin
Cette option définit le répertoire dans lequel les sessions shell et les sous-processus démarreront. Par défaut, il s'agit du répertoire de travail de psusan, mais dans certaines situations, il est plus facile de le changer avec une option de ligne de commande que d'encapsuler psusan dans un script qui change de répertoire avant de le lancer.
-v, --verbose
Cette option fait en sorte que psusan affiche des messages de journalisation détaillés sur son erreur standard. Ceci est probablement le plus utile en mode d'écoute.
-sshlog fichier-log
-sshrawlog journal
Ces options font que psusan enregistre les détails du protocole dans un fichier, de manière similaire aux options de journalisation de PuTTY et Plink.

-sshlog enregistre les paquets SSH décodés et d'autres événements (ceux que -v imprimerait). -sshrawlog enregistre en plus les données brutes du réseau, y compris le format des paquets externes et les salutations initiales.
