DEPUIS PSTOEDITQTGUI

PstoeditQtGui propose une alternative à l'opération par ligne de commande. L'interface graphique donne accès à presque toutes les options et fonctionnalités prises en charge par pstoedit. De plus, elle permet la conversion de plusieurs fichiers en un seul travail et offre également des raccourcis vers certains des périphériques de sortie de haut niveau de Ghostscript.

L'interface graphique est implémentée à l'aide de QT (https://www.qt.io).

Les différentes options proposées par pstoedit sont affichées dans différents onglets de l'interface graphique, classées par catégorie. Un lien vers une description plus détaillée de chaque option dans ce manuel est fourni avec chaque option dans l'interface graphique.

Remarque : Aucune des options n'est codée en dur ("hard coded") dans l'interface graphique. Au lieu de cela, les métadonnées sont récupérées de pstoedit lui-même. Ainsi, l'interface graphique est toujours à jour en ce qui concerne les options et les formats fournis par pstoedit.

DESCRIPTION

NIVEAU DE VERSION

Cette page de manuel documente la version 4.02 de pstoedit.

UTILISATION

pstoedit convertit les fichiers PostScript et PDF en divers formats de graphiques vectoriels. Les fichiers résultants peuvent être édités ou importés dans divers progiciels de dessin. Tapez

pstoedit -help

pour obtenir la liste des formats de sortie pris en charge. Pstoedit dispose d'un grand nombre de pilotes de format intégrés au binaire. Des pilotes supplémentaires peuvent être installés en tant que plugins et sont disponibles sur http://www.pstoedit.net/plugins/. Copiez simplement les plugins dans le même répertoire où le binaire pstoedit est installé ou - sur les systèmes de type Unix uniquement - alternativement dans le répertoire lib parallèlement au répertoire bin où pstoedit est installé.

Cependant, sauf si vous obtenez également une clé de licence pour les plugins, les pilotes supplémentaires déformeront légèrement les graphiques résultants. Voir la documentation fournie avec les plugins pour plus de détails.

PRINCIPE DE LA CONVERSION

pstoedit fonctionne en redéfinissant certains des opérateurs de dessin de base de PostScript, tels que stroke ou show (les bitmaps dessinées par l'opérateur image ne sont pas prises en charge par tous les formats de sortie.) Après avoir redéfini ces opérateurs, le fichier PostScript ou PDF à convertir est traité par un interpréteur PostScript, par exemple Ghostscript (gs(1)). Vous avez normalement besoin d'un interpréteur PostScript installé pour utiliser ce programme. Cependant, vous pouvez effectuer un traitement "back-end only" de fichiers suivant les conventions du format intermédiaire pstoedit en spécifiant l'option -bo. Voir "Formats disponibles et leurs options spécifiques" ci-dessous.

La sortie produite par l'interpréteur suite à la redéfinition des opérateurs de dessin est une sorte de fichier PostScript "plat" ne contenant que des opérations simples telles que moveto, lineto, show, etc. Vous pouvez visualiser ce fichier en utilisant l'option -f debug.

Cette sortie est lue par les fonctions de post-traitement de pstoedit et déclenche les fonctions de dessin dans le pilote de format de sortie sélectionné, parfois appelé aussi "back-end".

NOTES SUR GHOSTSCRIPT

Bien que pstoedit ait été conçu pour permettre l'utilisation de tout type d'interpréteur PostScript, il n'a été testé qu'en combinaison avec Ghostscript (https://ghostscript.com).

Jusqu'à la version 9.55 de Ghostscript, son interpréteur PDF était implémenté en PostScript lui-même. Cela permettait à pstoedit de traiter les fichiers PDF de la même manière que les fichiers PostScript, car les mêmes mécanismes pour intercepter les opérations de dessin pouvaient être utilisés.

Cependant, à partir de la version 9.56, l'interpréteur PDF de Ghostscript a été implémenté en C et, par conséquent, les interceptions utilisées par pstoedit ne sont plus efficaces lors du traitement des fichiers PDF.

Vous devez d'abord convertir le PDF en PostScript avant de pouvoir le convertir dans un autre format. Vous pouvez utiliser Ghostscript pour cela ou aussi utiliser le pilote gs:ps2write (-f gs:ps2write) de pstoedit.

OPTIONS

OPTIONS GENERALES

Les options suivantes sont disponibles :

[-include nom_fichier]

Cette option permet de spécifier un fichier PostScript supplémentaire qui sera exécuté juste avant la lecture de l'entrée normale. Ceci est utile pour inclure des paramètres de page spécifiques ou pour désactiver des opérateurs PostScript potentiellement dangereux, par exemple, file, renamefile ou deletefile.

[-xscale nombre]

mise à l'échelle par un facteur dans la direction x

[-yscale nombre]

mise à l'échelle par un facteur dans la direction y

[-xshift nombre]

décalage de l'image dans la direction x

[-yshift nombre]

décalage de l'image dans la direction y

[-centered]

centrer l'image avant la mise à l'échelle ou le décalage

[-minlinewidth nombre]

largeur de ligne minimale. Toutes les lignes plus fines que celle-ci seront dessinées avec cette largeur de ligne - en particulier les lignes de largeur zéro

[-pagenumberformat spécification du format du numéro de page]

spécification du format pour les numéros de page dans le nom de fichier si -split est utilisé. La spécification est utilisée pour créer le numéro de page en utilisant sprintf. La spécification ne doit pas inclure le % de début ni le d de fin. Par défaut, c'est une chaîne vide, ce qui résulte en un formatage du numéro de page en utilisant %d. Cela donne des numéros de page comme 1, 2, ..., 10. Parfois, vous pouvez vouloir une longueur fixe avec un zéro devant, donc vous pourriez spécifier 02, ce qui signifie 2 chiffres avec un zéro devant.

[-split]

Crée un nouveau fichier pour chaque page de l'entrée. Pour cela, le nom du fichier de sortie doit contenir un %d qui est remplacé par le numéro de page actuel. Cette option est automatiquement activée pour les formats de sortie qui ne prennent pas en charge plusieurs pages dans un même fichier, par exemple, f

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

OPTIONS GÉNÉRALES

Les options suivantes sont disponibles :

[-usebbfrominput]

Si spécifié, pstoedit utilise la BoundingBox telle qu'elle est (espérons-le) trouvée dans le fichier d'entrée au lieu de celle calculée par ses propres moyens.

[-page numéro de page]

Sélectionne une seule page d'un fichier PostScript ou PDF multipage.

[-rgb]

Depuis la version 3.30, pstoedit utilise les couleurs CMJN en interne. L'option -rgb active l'ancien comportement d'utilisation des valeurs RVB.

[-useagl]

utilise Adobe Glyph List au lieu de la table ISO Latin-1 (ceci est expérimental)

[-noclip]

n'utilise pas le découpage (pertinent uniquement si le format de sortie prend en charge le découpage).

[-rotate angle (0-360)]

Fait pivoter l'image de l'angle spécifié.

[-pagesize format de page]

définit la taille de la page pour le support de sortie. Cette option définit la taille de la page pour le support de sortie. Actuellement, elle n'est utilisée que par le pilote de format de sortie libplot, mais pourrait être utilisée par d'autres pilotes de format de sortie à l'avenir. La taille de la page est spécifiée en termes de noms de taille de page habituels, par exemple letter ou a4.

[-help]

affiche les informations d'aide

[-bo]

Vous pouvez exécuter le traitement du backend uniquement (sans la partie frontale de l'interpréteur PostScript) en exécutant d'abord pstoedit -f dump infile dumpfile, puis en exécutant pstoedit -f format -bo dumpfile outfile.

[-psarg chaîne d'arguments]

La chaîne fournie avec cette option est passée directement à Ghostscript lorsque Ghostscript est appelé pour traiter le fichier PostScript pour pstoedit. Par exemple : -psarg "-r300x300". Cela permet de modifier la résolution à 300x300 dpi. (Avec les anciennes versions de Ghostscript, la modification de la résolution de cette manière n'a d'effet que si l'option -dis est donnée.) Si vous souhaitez passer plusieurs options à Ghostscript, vous pouvez utiliser plusieurs options -psarg -psarg opt1 -psarg opt2 -psarg opt2. Consultez le manuel de Ghostscript pour d'autres options possibles.

[-pslanguagelevel Niveau 1, 2 ou 3 du langage PostScript à utiliser.]

Niveau 1, 2 ou 3 du langage PostScript à utiliser. Vous pouvez forcer Ghostscript en mode uniquement niveau 1 en utilisant -pslanguagelevel 1. Cela peut être utile par exemple si le fichier PostScript à convertir utilise des modèles de couleurs personnalisés spécifiques au niveau 2 qui ne sont pas pris en charge par pstoedit. Cependant, cela nécessite que le programme PostScript vérifie le niveau PostScript pris en charge par l'interpréteur et agisse en conséquence. Le niveau de langage par défaut est 3.

-f "format[:options]"

format de sortie cible reconnu par pstoedit. Comme d'autres pilotes de format peuvent être chargés dynamiquement, tapez pstoedit -help pour obtenir une liste complète des formats. Voir "Formats disponibles et leurs options spécifiques" ci-dessous pour une explication des [:options] de -f format. Si l'option de format n'est pas donnée, pstoedit essaie de deviner le format cible à partir du suffixe du nom du fichier de sortie. Cependant, dans de nombreux cas, il ne s'agit pas d'une correspondance unique, et pstoedit exige donc l'option -f.

[-gs chemin complet vers l'exécutable/DLL Ghostscript ou - pour Windows - juste un numéro de version (par exemple 10.01.0), auquel cas la version est utilisée pour rechercher le chemin dans le registre.]

indique à pstoedit quel exécutable/DLL Ghostscript utiliser - remplace la recherche interne par heuristique

[-gsregbase chemin de base du registre Ghostscript]

chemin du registre à utiliser comme chemin de base lors de la recherche de l'interpréteur Ghostscript. Cette option permet de spécifier une clé de registre sous HKLM/Software où rechercher les valeurs de clé, version et GS_DLL / GS_LIB de l'interpréteur GS. Exemple : "-gsregbase MyCompany" signifie que HKLM/Software/MyCompany/GPL Ghostscript serait recherché au lieu de HKLM/Software/GPL Ghostscript.

OPTIONS LIÉES À LA GESTION DU TEXTE ET DES POLICES

Les options suivantes sont disponibles :

[-df nom de police]

Parfois, les polices intégrées dans un programme PostScript n'ont pas de nom de police. Cela se produit, par exemple, dans les fichiers PostScript générés par dvips(1). Dans ce cas, pstoedit utilise une police de remplacement. Par défaut, il s'agit de Courier. Une autre police peut être spécifiée à l'aide de l'option -df. -df Helvetica fait remplacer toutes les polices sans nom par Helvetica.

[-nomaptoisolatin1]

Normalement, pstoedit mappe tous les codes de caractères à ceux définis par l'encodage ISO Latin1. Si vous spécifiez -nomaptoisolatin1, l'encodage du PostScript d'entrée est transmis inchangé à la sortie. Cela peut entraîner une sortie texte étrange, mais d'un autre côté, cela peut être le seul moyen de convertir correctement certaines polices. Essayez ce qui convient le mieux à votre cas concret.

[-pngimage nom de fichier]

principalement à des fins de débogage. Écrit également le résultat du traitement dans un fichier PNG

[-dt]

dessine le texte. Le texte est dessiné sous forme de polygones. Cela peut produire un fichier de sortie volumineux. Cette option est automatiquement activée si le format de sortie sélectionné ne prend pas en charge le texte, par exemple gnuplot(1).

[-adt]

dessine le texte automatiquement. Cette option active l'option -dt de manière sélective pour les polices qui ne semblent pas être des polices de texte normales, par exemple Symbol.

[-ndt]

ne jamais dessiner de texte. Désactive complètement l'heuristique utilisée par pstoedit pour décider quand "dessiner" le texte au lieu de l'afficher comme du texte. Cela peut produire des résultats incorrects, mais dans certains cas, cela peut néanmoins être utile. "À utiliser à vos propres risques".

[-dgbm]

expérimental - dessine également les bitmaps générés par les polices/glyphes

[-correctdefinefont]

Certains fichiers PostScript, par exemple ceux générés par ChemDraw, utilisent l'opérateur PostScript definefont d'une manière incompatible avec les hypothèses de pstoedit. La nouvelle police est définie en copiant une ancienne police sans modifier le nom de la police (FontName). Lorsque cette option est appliquée, des "correctifs" sont appliqués après un definefont afin de le rendre à nouveau compatible avec les hypothèses de pstoedit. Cette option n'est pas activée par défaut, car elle peut corrompre d'autres fichiers PostScript. Elle est uniquement testée avec des fichiers générés par ChemDraw.

[-pti]

texte de précision. Normalement, une chaîne de texte est dessinée telle qu'elle apparaît dans le fichier d'entrée. Cependant, dans certaines situations, cela peut entraîner des caractères mal positionnés. Ceci est dû aux limitations de la plupart des formats de sortie de pstoedit. Ils ne peuvent pas représenter du texte avec un espacement inter-lettres arbitraire, ce qui est facilement possible en PDF et PostScript. Avec -pta, chaque caractère d'une chaîne de texte est placé séparément. Avec -pti, cela n'est fait que dans les cas où il existe un espacement inter-lettres non nul. L'inconvénient du "texte de précision" est une taille de fichier plus importante et un texte difficile à modifier.

[-pta]

voir -pti

[-uchar caractère]

Parfois, pstoedit ne parvient pas à mapper un caractère de l'encodage utilisé par le fichier PostScript à l'encodage de la police du format cible. Dans ce cas, pstoedit remplace le caractère d'entrée par un caractère spécial afin de montrer tous les endroits qui n'ont pas pu être mappés correctement. Par défaut, il s'agit d'un "#". En utilisant l'option -uchar, il est possible de spécifier un autre caractère à utiliser à la place. Si vous souhaitez utiliser un espace, utilisez -uchar " ".

[-t2fontsast1]

Traite les polices de type 2 comme des polices de type 1. Les polices de type 2 apparaissent parfois comme des polices intégrées dans les fichiers PDF. En mode par défaut, le texte utilisant ces polices est dessiné sous forme de polygones car pstoedit suppose qu'une telle police n'est pas disponible sur la machine de l'utilisateur. Si cette option est définie, pstoedit suppose que l'encodage interne suit le même schéma qu'une police standard et génère une sortie texte normale. Cette hypothèse peut ne pas être vraie dans tous les cas. Mais il est presque impossible pour pstoedit de vérifier cette hypothèse - il devrait effectuer une sorte d'OCR.

[-nfr]

En mode normal, pstoedit remplace les polices bitmap par une police telle que définie par l'option -df. Ceci est fait car la plupart des formats de sortie ne peuvent pas gérer de telles polices. Ce comportement peut être désactivé en utilisant l'option -nfr, mais il dépend alors fortement de l'application qui lit le fichier généré pour savoir si le fichier est utilisable et correctement interprété ou non. Tout problème est alors hors du contrôle de pstoedit.

[-glyphs]

passe les noms des glyphes au pilote du format de sortie. Jusqu'à présent, aucun pilote de format de sortie n'utilise réellement les noms des glyphes, donc cela n'a aucun effet pour le moment. C'est une préparation pour un travail futur.

[-useoldnormalization]

Utilisez simplement cette option au cas où la nouvelle heuristique introduite en 3.5 ne produirait pas de résultats corrects - cependant, cette normalisation de l'encodage des polices sera toujours une approche de meilleure volonté car il n'y a pas de solution générale réelle avec un effort raisonnable

[-fontmap nom du fichier de mappage de polices pour pstoedit]

La carte de polices est un simple fichier texte contenant des lignes au format suivant :

nom_police_document nom_police_cible
Les lignes commençant par % sont considérées comme des commentaires.
Pour les noms de polices contenant des espaces, utilisez la notation "nom de police avec espaces".

Si un nom_police_cible commence par /, il est considéré comme un alias d'une entrée précédente.

Chaque nom de police trouvé dans le document est vérifié par rapport à ce mappage et s'il existe une entrée correspondante, le nouveau nom est utilisé pour la sortie.

Si l'option -fontmap n'est pas spécifiée, pstoedit recherche automatiquement le fichier drivername.fmp dans le répertoire d'installation et utilise ce fichier comme fichier de mappage de polices par défaut s'il est disponible.

e. Le répertoire d'installation est :

*
MS Windows : Le même répertoire où se trouve l'exécutable pstoedit
*
Unix :
Le répertoire d'installation par défaut. En cas d'échec, le répertoire <le répertoire où se trouve l'exécutable pstoedit> /../lib/

Le fichier mpost.fmp dans le répertoire misc de la distribution pstoedit est un fichier de mappage d'exemple avec des correspondances entre plus de 5000 noms de polices PostScript et leurs équivalents TeX. Ceci est utile car MetaPost est fréquemment utilisé avec TeX/LaTeX et ces programmes n'utilisent pas les noms de polices standard. Ce fichier et le pilote de format de sortie MetaPost sont fournis par Scott Pakin (scott+ps2ed_AT_pakin.org). Un autre exemple est wemf.fmp à utiliser sous Windows. Voir le répertoire misc de la distribution source de pstoedit. Après avoir chargé le fichier de mappage de polices implicite (basé sur le nom du pilote) ou explicite (basé sur l'option -fontmap), un fichier de mappage spécifique au système est recherché et chargé depuis le répertoire d'installation (unix.fmp ou windows.fmp). Ce fichier peut être utilisé pour rediriger certaines polices vers des noms spécifiques au système en utilisant la notation /AliasName décrite ci-dessus.

OPTIONS LIEES AU DESSIN

Les options suivantes sont disponibles :

[-nc]

pas de courbes. Normalement, pstoedit essaie de conserver les courbes de l'entrée et les transfère à la sortie si le format de sortie prend en charge les courbes. Si le format de sortie ne prend pas en charge les courbes, pstoedit remplace les courbes par une série de lignes (voir aussi l'option -flat). Cependant, dans certains cas, l'utilisateur peut souhaiter ce comportement également pour les formats de sortie qui prennent en charge les courbes à l'origine. Ceci peut être forcé via l'option -nc.

[-mergelines]

Certains formats de sortie permettent la représentation de polygones remplis avec des contours de couleur différente de la couleur de remplissage. Comme PostScript ne prend pas en charge cela directement avec les primitives de dessin standard, les programmes de dessin génèrent généralement deux objets (le contour et le polygone rempli) dans la sortie PostScript. pstoedit est capable de les recombiner, s'ils se suivent directement et que vous spécifiez -mergelines. Cependant, cette fusion n'est pas prise en charge par tous les formats de sortie en raison des restrictions du format cible.

[-filledrecttostroke]

Les rectangles remplis d'une couleur unie peuvent être convertis en une ligne tracée avec une épaisseur correspondant à la largeur du rectangle. Ceci est principalement intéressant pour les formats de sortie qui ne prennent pas en charge les polygones remplis du tout. Mais cela est limité aux rectangles uniquement, c'est-à-dire qu'il n'est pas pris en charge pour les polygones généraux.

[-mergetext]

Afin de produire une sortie texte agréable à regarder, les programmes générant des fichiers PostScript divisent souvent les mots en petits morceaux qui sont ensuite placés individuellement sur des positions adjacentes. Cependant, un tel texte divisé est difficile à éditer par la suite, il est donc parfois préférable de recombiner ces morceaux pour former un mot (ou même une séquence de mots). Pour cela, pstoedit met en œuvre une heuristique sur les morceaux de texte à considérer comme faisant partie d'un mot divisé. Ceci est basé sur la proximité géométrique des différentes parties et semble bien fonctionner jusqu'à présent. Mais il y a certainement des cas où cette heuristique simple échoue. Veuillez donc vérifier attentivement les résultats.

[-ssp]

simuler les sous-chemins. Plusieurs formats de sortie ne prennent pas en charge les chemins PostScript contenant des sous-chemins, c'est-à-dire des chemins avec des mouvements intermédiaires. Dans le cas normal, chaque sous-chemin est traité comme un chemin indépendant pour ces formats de sortie. Cela peut conduire à de mauvais résultats. Le cas le plus courant où cela se produit est si vous utilisez l'option -dt et affichez du texte avec des lettres comme e, o, ou b, c'est-à-dire des lettres qui ont un "trou". Lorsque l'option -ssp est définie, pstoedit essaie d'éliminer ces problèmes. Cependant, cette option est coûteuse en temps CPU !

[-sfill]

simuler le remplissage par des tracés individuels.

[-flat facteur de platitude]

Si le format de sortie ne prend pas en charge les courbes de la manière dont le fait PostScript ou si l'option -nc est spécifiée, toutes les courbes sont approximées par des lignes. En utilisant l'option -flat, on peut contrôler cette approximation. Ce paramètre est directement converti en une commande PostScript setflat. Des nombres plus élevés, par exemple 10, donnent des approximations plus grossières, des nombres plus bas, par exemple 0,1, donnent des approximations plus fines.

[-sclip]

simuler le découpage. La plupart des formats de sortie de pstoedit n'ont pas de support natif pour le découpage. Pour cela, pstoedit offre une option pour effectuer le découpage des graphiques directement sans passer le chemin de découpage au pilote de sortie. Cependant, cela entraîne le remplacement des courbes par de nombreux segments de ligne et donc des fichiers de sortie plus volumineux. Utilisez donc cette option uniquement si votre sortie est différente de l'entrée en raison du découpage. De plus, ce "découpage simulé" n'est pas exactement le même que défini dans PostScript. Il peut y avoir des lignes dessinées en double taille. De plus, le découpage du texte n'est pas pris en charge à moins que vous n'utilisiez également l'option -dt.

OPTIONS DE DIAGNOSTIC ET DE DEBOGAGE

Les options suivantes sont disponibles :

[-dis]

Ouvre un affichage pendant le traitement par Ghostscript. Certains fichiers ne fonctionnent correctement que de cette manière.

[-q]

mode silencieux - n'écrit pas le message de démarrage

[-nq]

pas de sortie de l'interpréteur PostScript. Normalement, Ghostscript se termine après le traitement du fichier d'entrée de pstoedit. Pour le débogage, il peut être utile d'éviter cela. Si vous le faites, vous devrez taper quit à l'invite GS> pour quitter Ghostscript.

[-v]

Active le mode verbeux. Des informations supplémentaires sont affichées pendant le traitement.

[-vl ]

Active le mode verbeux avec un niveau donné. Des informations supplémentaires sont affichées pendant le traitement.

[-nb]

Depuis la version 3.10, pstoedit utilise l'option -dDELAYBIND lors de l'appel de Ghostscript. Auparavant, l'option -dNOBIND était utilisée, mais cela causait parfois des problèmes si le fichier PostScript d'un utilisateur surchargeait un opérateur PostScript standard avec une sémantique totalement nouvelle, par exemple lt pour lineto au lieu de la signification standard de "inférieur à". En utilisant -nb, l'ancien style peut être réactivé au cas où -dDELAYBIND donnerait des résultats différents qu'auparavant. Dans un tel cas, veuillez également contacter l'auteur.

[-rdb]

Depuis la version 3.10, pstoedit utilise l'option -dDELAYBIND lors de l'appel de Ghostscript. Mais dans la version 9.22 de Ghostscript, cette option n'est plus prise en charge pour des raisons de sécurité. En solution de repli, cette version fournit l'option REALLYDELAYBIND et pstoedit peut l'utiliser si vous fournissez l'option -rdb. Utilisez ceci avec prudence car cela pourrait ouvrir des risques de sécurité, par exemple un fichier PostScript injectant du code malveillant dans les opérateurs PostScript standard. Cependant, ne pas utiliser cette option peut entraîner que certaines opérations de dessin PostScript ne soient pas vues par pstoedit, causant ainsi des artefacts manquants dans la sortie. Les versions ultérieures de Ghostscript prendront probablement à nouveau en charge -dDELAYBIND. Mais même dans ce cas, le risque de sécurité demeure. Soyez donc prudent avec les fichiers que vous traitez avec pstoedit et Ghostscript.

Si aucun fichier d'entrée ni de sortie n'est donné en argument, pstoedit fonctionne comme un filtre lisant depuis l'entrée standard et écrivant vers la sortie standard. NOTES SUR LES FORMATS ET PILOTES SPÉCIFIQUES

AUTOTRACE

pstoedit coopère avec autotrace. Autotrace peut désormais produire un fichier de vidage pour un traitement ultérieur par pstoedit en utilisant l'option -bo (backend uniquement). Autotrace est un programme écrit par un groupe autour de Martin Weber et peut être trouvé sur https://sourceforge.net/projects/autotrace/.

PS2AI

Le pilote de format de sortie ps2ai n'est pas un pilote de format de sortie natif de pstoedit. Il n'utilise pas le flattener PostScript de pstoedit, mais utilise le programme PostScript ps2ai.ps qui est installé dans le répertoire de distribution Ghostscript. Il est inclus pour fournir la même "apparence" pour la conversion vers AI. Cependant, de nombreux fichiers ne se convertissent pas bien, voire pas du tout, en utilisant ps2ai.ps. Un pilote pstoedit natif serait donc bien meilleur. Quelqu'un est-il intéressé par cela ? Le format AI est utilisable par exemple par Mayura Draw (http://www.mayura.com). Un pilote pour le format natif Mayura serait également apprécié.

Une alternative au pilote basé sur ps2ai est disponible via le format -f plot:ai si libplot(ter) est installé.

Vous devriez utiliser une version de Ghostscript supérieure ou égale à 6.00 pour utiliser le pilote de format de sortie ps2ai.

METAPOST

Notez que, pour autant que Scott le sache, MetaPost ne prend pas en charge l'eofill de PostScript. Le pilote de format de sortie MetaPost convertit simplement eofill en fill, et émet un avertissement si verbose est défini. Heureusement, très peu de programmes PostScript reposent sur la règle de remplissage pair-impair, même si beaucoup la spécifient.

Pour en savoir plus sur MetaPost, voir :

http://tug.org/metapost

CONTEXT FREE - CFDG

Le pilote pour le format CFDG (drvcfdg) définit une forme par page de PostScript, mais seule la première forme est réellement rendue (sauf si l'utilisateur édite le code CFDG généré, bien sûr). CFDG ne prend pas en charge la sortie multipage, donc c'est probablement une chose raisonnable à faire.

Pour en savoir plus sur Context Free, voir : http://www.contextfreeart.org/

LaTeX2E

*
L'environnement picture de LaTeX2e n'est pas très puissant. En conséquence, de nombreux éléments PostScript élémentaires sont ignorés -- remplissages, épaisseurs de lignes (en dehors de "thick" et "thin"), et motifs de tirets, pour n'en nommer que quelques-uns. De plus, les images complexes peuvent dépasser la capacité mémoire de TeX. (Le package eepic surmonte bon nombre de ces restrictions.)
*
Certains éléments PostScript ne sont pas directement pris en charge par "picture", mais peuvent être gérés par des packages externes. Si une figure utilise la couleur, le document de niveau supérieur devra faire un "\usepackage{color}" ou "\usepackage{xcolor}". Et si une figure contient du texte pivoté, le document de niveau supérieur devra faire un "\usepackage{rotating}".
*
Toutes les longueurs, coordonnées et tailles de police générées par le pilote de format de sortie sont en termes de \unitlength, donc la mise à l'échelle d'une figure se résume à faire un "\setlength{\unitlength}{...}".
*
Le pilote de format de sortie prend actuellement en charge une option spécifique au pilote de format de sortie, "integers", qui arrondit toutes les longueurs, coordonnées et tailles de police à l'entier le plus proche. Cela rend la modification manuelle de l'image un peu plus agréable.
*
Pourquoi ce pilote de format de sortie est-il utile ? Une réponse est la portabilité ; tout système LaTeX2e peut gérer l'environnement picture, même s'il ne peut pas gérer les graphiques PostScript. (pdfLaTeX vient à l'esprit ici.) Une deuxième réponse est que les images peuvent être facilement modifiées pour contenir n'importe quel code LaTeX2e arbitraire. Par exemple, le texte d'une figure peut être modifié pour contenir des mathématiques complexes, des alphabets non latins, des citations bibliographiques, ou -- la vraie raison pour laquelle Scott a écrit le pilote de format de sortie LaTeX2e -- des hyperliens vers le document environnant (avec l'aide du package hyperref).

CRÉATION D'UN NOUVEAU PILOTE DE FORMAT DE SORTIE

Pour implémenter un nouveau pilote de format de sortie, vous pouvez commencer par drvsampl.cpp et drvsampl.h. Voir aussi les commentaires dans drvbase.h et drvfuncs.h pour une explication des méthodes qui devraient être implémentées pour un nouveau pilote de format de sortie.

VARIABLES D'ENVIRONNEMENT

Un interpréteur PostScript par défaut à appeler par pstoedit est spécifié lors de la compilation. Vous pouvez remplacer la valeur par défaut en définissant la variable d'environnement GS sur le nom d'un interpréteur PostScript approprié.

Vous pouvez vérifier quel nom d'interpréteur PostScript a été compilé dans pstoedit en utilisant : pstoedit -help -v.

Voir le manuel Ghostscript pour les descriptions des variables d'environnement utilisées par Ghostscript, notamment GS_FONTPATH et GS_LIB ; d'autres variables d'environnement affectent également la sortie vers l'affichage, l'impression et le filtrage et le traitement supplémentaires. Voir la documentation connexe.

pstoedit alloue des fichiers temporaires en utilisant la fonction tempnam(3). Ainsi, l'emplacement des fichiers temporaires peut être contrôlé par d'autres variables d'environnement utilisées par cette fonction. Voir la page de manuel de tempnam(3) pour les descriptions des variables d'environnement utilisées. Sur les systèmes de type UNIX, il s'agit probablement de la variable TMPDIR, sur DOS/WINDOWS, soit TMP, soit TEMP.

DÉPANNAGE

Si vous avez des problèmes avec pstoedit, essayez d'abord de voir si Ghostscript affiche correctement votre fichier. Si oui, essayez pstoedit -f ps infile.ps testfile.ps et vérifiez si testfile.ps s'affiche toujours correctement à l'aide de Ghostscript. Si ce fichier ne s'affiche pas correctement, il semble y avoir un problème avec le frontal PostScript de pstoedit. Si ce fichier s'affiche correctement mais que la sortie pour un format spécifique est erronée, le problème se situe probablement dans le pilote de format de sortie pour le format spécifique. Dans tous les cas, envoyez les corrections de bugs et les rapports à l'auteur.

Un problème courant avec les fichiers PostScript est que le fichier PostScript redéfinit un des opérateurs PostScript standard de manière incohérente. Il n'y a aucun effet à cela si vous imprimez simplement le fichier car le "programme" PostScript d'origine utilise ces nouveaux opérateurs dans leur nouvelle signification et n'utilise plus les originaux. Cependant, lorsqu'il est exécuté sous le contrôle de pstoedit, ces opérateurs sont censés fonctionner avec leur sémantique d'origine.

J'ai jusqu'à présent vu des redéfinitions pour :

*
lt - "less-then" pour signifier "dessiner une ligne vers"
*
string - "créer un objet string" pour signifier "dessiner une chaîne"
*
length - "obtenir la longueur d'une chaîne par exemple" à une "constante flottante"

J'ai inclus des solutions de contournement pour ceux mentionnés ci-dessus, mais d'autres pourraient apparaître en plus de ceux-là.

RESTRICTIONS

*
Les polices non standard (par exemple, les polices bitmap TeX) sont mappées à une police par défaut qui peut être modifiée à l'aide de l'option -df. pstoedit choisit la taille de la police de remplacement de telle sorte que la largeur de la chaîne dans la police d'origine soit la même qu'avec la police de remplacement. Ceci est fait pour chaque fragment de texte affiché. Le support de l'encodage de caractères spéciaux est limité dans ce cas. Si un caractère ne peut pas être mappé dans le format cible, pstoedit affiche un '#' à la place. Voir aussi l'option -uchar.
*
pstoedit prend en charge les graphiques bitmap uniquement pour certains pilotes de format de sortie.
*
Certains pilotes de format de sortie, par exemple le pilote de format de sortie Gnuplot ou le pilote de format de sortie 3D (rpl, lwo, rib) ne prennent pas en charge le texte.
*
Pour la plupart des pilotes de format de sortie, pstoedit ne prend pas en charge le découpage (principalement en raison des limitations du format cible). Vous pouvez essayer d'utiliser l'option -sclip pour simuler le découpage. Cependant, cela ne fonctionne pas toujours comme prévu.
*
Note spéciale concernant les pilotes de format de sortie Java (java1 et java2). Les pilotes de format de sortie Java génèrent un fichier source Java qui nécessite d'autres fichiers pour être compilé et utilisable. Ces autres fichiers sont des classes Java (une applet et des classes de support) qui permettent de parcourir les pages individuelles d'un document PostScript converti. Cette applet peut être facilement activée à partir d'un document HTML. Voir les fichiers contrib/java/java1/readme_java1.txt ou contrib/java/java2/readme_java2.htm pour plus de détails.

1.
Pourquoi des lettres comme O ou B deviennent-elles étranges lorsqu'elles sont converties en TGIF/XFIG en utilisant l'option -dt ?

RESTRICTIONS

Most output format drivers do not support composite paths with intermediate gaps (moveto's) and second do not support very well the (eo)fill operators of PostScript (winding rule). For such objects pstoedit breaks them into smaller objects whenever such a gap is found. This results in the "hole" being filled with black color instead of being transparent. Since version 3.11 you can try the -ssp option in combination with the XFIG output format driver.

2.
Why does pstoedit produce ugly results from PostScript files generated by dvips?

This is because TeX documents usually use bitmap fonts. Such fonts cannot be used as native font in other format. So pstoedit replaces the TeX font with another native font. Of course, the replacement font will in most cases produce another look, especially if mathematical symbols are used. Try to use PostScript fonts instead of the bitmap fonts when generating a PostScript file from TeX or LaTeX.

pstoedit

pstoedit — convertit un fichier PostScript ou PDF en un autre format vectoriel

SYNTAX

pstoedit [-outputformat] [-outputformatoption[=value]] [-option[=value]] [inputfile [outputfile]]

DESCRIPTION

pstoedit est un programme qui convertit des fichiers PostScript ou PDF en d'autres formats vectoriels.

OPTIONS

pstoedit prend un certain nombre d'options pour contrôler le format de sortie et d'autres aspects de la conversion.

  • -<outputformat> : Spécifie le format de sortie (par exemple, -svg, -emf, -pdf).
  • -<outputformat>option[=value] : Options spécifiques au format de sortie. Par exemple, -svgscale=0.5 pour changer l'échelle du SVG.
  • -option[=value] : Options générales. Par exemple, -outputfile=output.txt pour spécifier le nom du fichier de sortie.

Pour une liste complète des formats de sortie et des options, consultez la page de manuel de pstoedit.

EXEMPLES

Pour convertir un fichier PostScript input.ps en SVG :

pstoedit input.ps output.svg

Pour convertir un fichier PDF document.pdf en EMF avec une mise à l'échelle de 50% :

pstoedit -emf -emfscale=0.5 document.pdf output.emf
