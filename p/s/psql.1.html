NOM

psql - terminal interactif PostgreSQL

SYNTAXE

psql [option...] [dbname [username]]

DESCRIPTION

psql est une interface en ligne de commande (terminal) pour PostgreSQL. Il vous permet de saisir interactivement des requêtes, de les soumettre à PostgreSQL et d'en voir les résultats. Alternativement, l'entrée peut provenir d'un fichier ou d'arguments de ligne de commande. De plus, psql fournit un certain nombre de méta-commandes et diverses fonctionnalités semblables à celles d'un shell pour faciliter l'écriture de scripts et l'automatisation d'une large gamme de tâches.

OPTIONS

-a
--echo-all

Imprime toutes les lignes d'entrée non vides sur la sortie standard au fur et à mesure de leur lecture. (Cela ne s'applique pas aux lignes lues interactivement.) Ceci est équivalent à la définition de la variable ECHO sur all.

-A
--no-align

Commute en mode de sortie non aligné. (Le mode de sortie par défaut est aligné.) Ceci est équivalent à \pset format unaligned.

-b
--echo-errors

Imprime les commandes SQL échouées sur la sortie d'erreur standard. Ceci est équivalent à la définition de la variable ECHO sur errors.

-c commande
--command=commande

Spécifie que psql doit exécuter la chaîne de commande donnée, commande. Cette option peut être répétée et combinée dans n'importe quel ordre avec l'option -f. Lorsque -c ou -f est spécifié, psql ne lit pas les commandes depuis l'entrée standard ; il se termine après avoir traité toutes les options -c et -f dans l'ordre.

commande doit être soit une chaîne de commande entièrement analysable par le serveur (c'est-à-dire, qu'elle ne contient pas de fonctionnalités spécifiques à psql), soit une seule commande commençant par une barre oblique inverse. Vous ne pouvez donc pas mélanger des commandes SQL et des méta-commandes psql au sein d'une option -c. Pour y parvenir, vous pouvez utiliser des options -c répétées ou envoyer la chaîne à psql par un tube, par exemple :

psql -c '\x' -c 'SELECT * FROM foo;'

ou

echo '\x \\ SELECT * FROM foo;' | psql

(\\ est la méta-commande de séparateur.)

Chaque chaîne de commande SQL passée à -c est envoyée au serveur en une seule requête. De ce fait, le serveur l'exécute comme une transaction unique, même si la chaîne contient plusieurs commandes SQL, à moins que des commandes BEGIN/COMMIT explicites ne soient incluses dans la chaîne pour les diviser en plusieurs transactions. (Voir la section 54.2.2.1 pour plus de détails sur la façon dont le serveur gère les chaînes multi-requêtes.)

Si vous ne souhaitez pas que plusieurs commandes soient exécutées en une seule transaction, utilisez des commandes -c répétées ou envoyez plusieurs commandes à l'entrée standard de psql, soit en utilisant `echo` comme illustré ci-dessus, soit via un here-document du shell, par exemple :

psql <<EOF
\x
SELECT * FROM foo;
EOF

--csv

Commute en mode de sortie CSV (Comma-Separated Values). Ceci est équivalent à \pset format csv.

-d dbname
--dbname=dbname

Spécifie le nom de la base de données à laquelle se connecter. Ceci est équivalent à spécifier dbname comme premier argument non optionnel sur la ligne de commande. Le dbname peut être une chaîne de connexion. Si c'est le cas, les paramètres de la chaîne de connexion remplaceront toute option de ligne de commande contradictoire.

-e
--echo-queries

Copie également toutes les commandes SQL envoyées au serveur sur la sortie standard. Ceci est équivalent à la définition de la variable ECHO sur queries.

-E
--echo-hidden

Affiche les requêtes réelles générées par \d et d'autres commandes en barre oblique inverse. Vous pouvez l'utiliser pour étudier les opérations internes de psql. Ceci est équivalent à la définition de la variable ECHO_HIDDEN sur on.

-f nomfichier
--file=nomfichier

Lit les commandes depuis le fichier nomfichier, plutôt que depuis l'entrée standard. Cette option peut être répétée et combinée dans n'importe quel ordre avec l'option -c. Lorsque -c ou -f est spécifié, psql ne lit pas les commandes depuis l'entrée standard ; il se termine après avoir traité toutes les options -c et -f dans l'ordre. Sauf pour cela, cette option est largement équivalente à la méta-commande \i.

Si nomfichier est - (un tiret), alors l'entrée standard est lue jusqu'à une indication EOF ou une méta-commande \q. Ceci peut être utilisé pour intercaler une entrée interactive avec une entrée provenant de fichiers. Notez cependant que Readline n'est pas utilisé dans ce cas (comme si -n avait été spécifié).

Utiliser cette option est subtilement différent de taper psql < nomfichier. En général, les deux feront ce que vous attendez, mais l'utilisation de -f active des fonctionnalités intéressantes comme les messages d'erreur avec numéros de ligne. Il y a aussi une légère possibilité que l'utilisation de cette option réduise la surcharge au démarrage. D'un autre côté, la variante utilisant la redirection d'entrée du shell garantit (en théorie) exactement le même résultat que si vous aviez tout entré manuellement.

-F séparateur
--field-separator=séparateur

Utilise séparateur comme séparateur de champ pour la sortie non alignée. Ceci est équivalent à \pset fieldsep ou \f.

-h nomhôte
--host=nomhôte

Spécifie le nom d'hôte de la machine sur laquelle le serveur s'exécute. Si la valeur commence par une barre oblique, elle est utilisée comme répertoire pour le socket de domaine Unix.

-H
--html

Commute en mode de sortie HTML. Ceci est équivalent à \pset format html ou à la commande \H.

-l
--list

Liste toutes les bases de données disponibles, puis quitte. Les autres options non liées à la connexion sont ignorées. Ceci est similaire à la méta-commande \list.

Lorsque cette option est utilisée, psql se connectera à la base de données `postgres`, à moins qu'une base de données différente ne soit nommée sur la ligne de commande (option -d ou argument non optionnel, éventuellement via une entrée de service, mais pas via une variable d'environnement).

-L nomfichier
--log-file=nomfichier

Écrit toute la sortie des requêtes dans le fichier nomfichier, en plus de la destination de sortie normale.

-n
--no-readline

N'utilise pas Readline pour l'édition de ligne et n'utilise pas l'historique des commandes (voir la section "Édition de ligne de commande" ci-dessous).

-o nomfichier
--output=nomfichier

Place toute la sortie des requêtes dans le fichier nomfichier. Ceci est équivalent à la commande \o.

-p port
--port=port

Spécifie le port TCP ou l'extension de fichier de socket de domaine Unix local sur lequel le serveur écoute les connexions. Par défaut, il prend la valeur de la variable d'environnement PGPORT ou, si elle n'est pas définie, le port spécifié lors de la compilation, généralement 5432.

-P affectation
--pset=affectation

Spécifie les options d'impression, dans le style de \pset. Notez qu'ici, vous devez séparer le nom et la valeur par un signe égal au lieu d'un espace. Par exemple, pour définir le format de sortie sur LaTeX, vous pouvez écrire -P format=latex.

-q
--quiet

Spécifie que psql doit faire son travail silencieusement. Par défaut, il imprime des messages de bienvenue et diverses informations de sortie. Si cette option est utilisée, rien de tout cela ne se produit. Ceci est utile avec l'option -c. Ceci est équivalent à la définition de la variable QUIET sur on.

-R séparateur
--record-separator=séparateur

Utilise séparateur comme séparateur d'enregistrement pour la sortie non alignée. Ceci est équivalent à \pset recordsep.

-s
--single-step

Exécute en mode pas à pas. Cela signifie que l'utilisateur est invité avant que chaque commande ne soit envoyée au serveur, avec la possibilité d'annuler l'exécution. Utilisez ceci pour déboguer des scripts.

-S
--single-line

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

>
Fonctionne en mode mono-ligne où un saut de ligne termine une commande SQL, comme le fait un point-virgule.

Note
Ce mode est fourni pour ceux qui insistent, mais il n'est pas forcément recommandé. En particulier, si vous mélangez des commandes SQL et des méta-commandes sur une ligne, l'ordre d'exécution peut ne pas toujours être clair pour un utilisateur inexpérimenté.

-t
--tuples-only

Désactive l'affichage des noms de colonnes, des pieds de page indiquant le nombre de lignes de résultat, etc. Ceci est équivalent à \t ou \pset tuples_only.

-T options_table
--table-attr=options_table

Spécifie les options à placer dans la balise de table HTML. Voir \pset tableattr pour plus de détails.

-U nom_utilisateur
--username=nom_utilisateur

Se connecte à la base de données en tant qu'utilisateur nom_utilisateur au lieu de l'utilisateur par défaut. (Vous devez avoir la permission de le faire, bien sûr.)

-v affectation
--set=affectation
--variable=affectation

Effectue une affectation de variable, comme la méta-commande \set. Notez que vous devez séparer le nom et la valeur, le cas échéant, par un signe égal sur la ligne de commande. Pour désaffecter une variable, omettez le signe égal. Pour affecter une variable avec une valeur vide, utilisez le signe égal mais omettez la valeur. Ces affectations sont effectuées lors du traitement de la ligne de commande, donc les variables qui reflètent l'état de la connexion seront écrasées plus tard.

-V
--version

Affiche la version de psql et quitte.

-w
--no-password

Ne jamais demander de mot de passe. Si le serveur nécessite une authentification par mot de passe et qu'un mot de passe n'est pas disponible à partir d'autres sources telles qu'un fichier .pgpass, la tentative de connexion échouera. Cette option peut être utile dans les travaux par lots et les scripts où aucun utilisateur n'est présent pour saisir un mot de passe.

Notez que cette option restera active pendant toute la session, et affecte donc l'utilisation de la méta-commande \connect ainsi que la tentative de connexion initiale.

-W
--password

Force psql à demander un mot de passe avant de se connecter à une base de données, même si le mot de passe ne sera pas utilisé.

Si le serveur nécessite une authentification par mot de passe et qu'un mot de passe n'est pas disponible à partir d'autres sources telles qu'un fichier .pgpass, psql demandera un mot de passe dans tous les cas. Cependant, psql perdra une tentative de connexion pour découvrir que le serveur veut un mot de passe. Dans certains cas, il est utile de taper -W pour éviter la tentative de connexion supplémentaire.

Notez que cette option restera active pendant toute la session, et affecte donc l'utilisation de la méta-commande \connect ainsi que la tentative de connexion initiale.

-x
--expanded

Active le mode de formatage de table étendu. Ceci est équivalent à \x ou \pset expanded.

-X
--no-psqlrc

Ne lit pas le fichier de démarrage (ni le fichier psqlrc système, ni le fichier ~/.psqlrc de l'utilisateur).

-z
--field-separator-zero

Définit le séparateur de champs pour la sortie non alignée à un octet nul. Ceci est équivalent à \pset fieldsep_zero.

-0
--record-separator-zero

Définit le séparateur d'enregistrements pour la sortie non alignée à un octet nul. Ceci est utile pour interagir, par exemple, avec xargs -0. Ceci est équivalent à \pset recordsep_zero.

-1
--single-transaction

Cette option ne peut être utilisée qu'en combinaison avec une ou plusieurs options -c et/ou -f. Elle fait émettre à psql une commande BEGIN avant la première option de ce type et une commande COMMIT après la dernière, encapsulant ainsi toutes les commandes dans une seule transaction. Si l'une des commandes échoue et que la variable ON_ERROR_STOP a été définie, une commande ROLLBACK est envoyée à la place. Cela garantit que soit toutes les commandes se terminent avec succès, soit aucune modification n'est appliquée.

Si les commandes elles-mêmes contiennent BEGIN, COMMIT ou ROLLBACK, cette option n'aura pas les effets désirés. De plus, si une commande individuelle ne peut pas être exécutée dans un bloc de transaction, spécifier cette option entraînera l'échec de toute la transaction.

-?
--help[=sujet]

Affiche l'aide sur psql et quitte. Le paramètre facultatif sujet (par défaut options) sélectionne quelle partie de psql est expliquée : commands décrit les commandes d'antislash de psql ; options décrit les options de ligne de commande qui peuvent être passées à psql ; et variables montre l'aide sur les variables de configuration de psql.

STATUT DE SORTIE

psql retourne 0 au shell s'il s'est terminé normalement, 1 si une erreur fatale de sa part se produit (par exemple, manque de mémoire, fichier introuvable), 2 si la connexion au serveur a mal tourné et que la session n'était pas interactive, et 3 si une erreur s'est produite dans un script et que la variable ON_ERROR_STOP a été définie.

UTILISATION

Connexion a une Base de Donnees

psql est une application client PostgreSQL standard. Pour se connecter à une base de données, vous devez connaître le nom de votre base de données cible, le nom d'hôte et le numéro de port du serveur, ainsi que le nom d'utilisateur de la base de données auquel vous souhaitez vous connecter. psql peut être informé de ces paramètres via des options de ligne de commande, à savoir -d, -h, -p et -U respectivement. Si un argument est trouvé qui n'appartient à aucune option, il sera interprété comme le nom de la base de données (ou le nom d'utilisateur de la base de données, si le nom de la base de données est déjà donné). Toutes ces options ne sont pas obligatoires ; il existe des valeurs par défaut utiles. Si vous omettez le nom d'hôte, psql se connectera via une socket Unix-domain à un serveur sur l'hôte local, ou via TCP/IP à localhost sur Windows. Le numéro de port par défaut est déterminé lors de la compilation. Comme le serveur de base de données utilise le même défaut, vous n'aurez pas à spécifier le port dans la plupart des cas. Le nom d'utilisateur de base de données par défaut est le nom d'utilisateur de votre système d'exploitation. Une fois que le nom d'utilisateur de la base de données est déterminé, il est utilisé comme nom de base de données par défaut. Notez que vous ne pouvez pas simplement vous connecter à n'importe quelle base de données sous n'importe quel nom d'utilisateur de base de données. Votre administrateur de base de données devrait vous avoir informé de vos droits d'accès.

Lorsque les défauts ne sont pas tout à fait corrects, vous pouvez gagner du temps en définissant les variables d'environnement PGDATABASE, PGHOST, PGPORT et/ou PGUSER sur des valeurs appropriées. (Pour des variables d'environnement supplémentaires, voir la section 32.15.) Il est également pratique d'avoir un fichier ~/.pgpass pour éviter d'avoir à taper régulièrement des mots de passe. Voir la section 32.16 pour plus d'informations.

Une autre façon de spécifier les paramètres de connexion est dans une chaîne conninfo ou une URI, qui est utilisée à la place d'un nom de base de données. Ce mécanisme vous donne un très large contrôle sur la connexion. Par exemple :

$ psql "service=myservice sslmode=require"
$ psql postgresql://dbmaster:5433/mydb?sslmode=require

Vous pouvez ainsi également utiliser LDAP pour la recherche de paramètres de connexion comme décrit dans la section 32.18. Voir la section 32.1.2 pour plus d'informations sur toutes les options de connexion disponibles.

Si la connexion n'a pas pu être établie pour une raison quelconque (par exemple, privilèges insuffisants, serveur non en cours d'exécution sur l'hôte cible, etc.), psql retournera une erreur et se terminera.

Si l'entrée standard et la sortie standard sont toutes deux un terminal, alors psql définit l'encodage client sur « auto », ce qui détectera l'encodage client approprié à partir des paramètres régionaux (variable d'environnement LC_CTYPE sur les systèmes Unix). Si cela ne fonctionne pas comme prévu, l'encodage client peut être remplacé en utilisant la variable d'environnement PGCLIENTENCODING.

Entree des Commandes SQL

En fonctionnement normal, psql fournit une invite avec le nom de la base de données à laquelle psql est actuellement connecté, suivi de la chaîne =>. Par exemple :

$ psql testdb
psql (18.1)
Tapez "help" pour de l'aide.
testdb=>

À l'invite, l'utilisateur peut taper des commandes SQL. Normalement, les lignes d'entrée sont envoyées au serveur lorsqu'un point-virgule terminant la commande est atteint. Une fin de ligne ne termine pas une commande. Ainsi, les commandes peuvent être réparties sur plusieurs lignes pour plus de clarté. Si la commande a été envoyée et exécutée sans erreur, les résultats de la commande sont affichés à l'écran.

Si des utilisateurs non fiables ont accès à une base de données qui n'a pas adopté un schéma d'utilisation sécurisé des schémas, commencez votre session en retirant les schémas inscriptibles publiquement de search_path. On peut ajouter l'option -csearch_path= à la chaîne de connexion ou exécuter SELECT pg_catalog.set_config('search_path', '', false) avant d'autres commandes SQL. Cette considération n'est pas spécifique à psql ; elle s'applique à toutes les interfaces pour l'exécution de commandes SQL arbitraires.

Chaque fois qu'une commande est exécutée, psql interroge également les événements de notification asynchrone générés par LISTEN et NOTIFY.

Alors que les commentaires de bloc de style C sont transmis au serveur pour traitement et suppression, les commentaires standard SQL sont supprimés par psql.

Meta-Commandes

Tout ce que vous entrez dans psql et qui commence par un antislash non cité est une méta-commande psql qui est traitée par psql lui-même. Ces commandes rendent psql plus utile pour l'administration ou le scripting. Les méta-commandes sont souvent appelées commandes slash ou antislash.

Le format d'une commande psql est l'antislash, suivi immédiatement d'un verbe de commande, puis des arguments éventuels. Les arguments sont séparés du verbe de commande et les uns des autres par n'importe quel nombre d'espaces blancs.

Pour inclure des espaces blancs dans un argument, vous pouvez le citer avec des apostrophes. Pour inclure une apostrophe dans un argument, écrivez deux apostrophes à l'intérieur du texte cité. Tout ce qui est contenu dans des apostrophes est en outre soumis à des substitutions de style C pour \n (nouvelle ligne), \t (tabulation), \b (retour arrière), \r (retour chariot), \f (saut de page), \chiffres (octal) et \xchiffres (hexadécimal). Un antislash précédant tout autre caractère dans un texte cité avec apostrophes cite ce caractère, quel qu'il soit.

Si un deux-points non cité (:) suivi d'un nom de variable psql apparaît dans un argument, il est remplacé par la valeur de la variable

ue, tel qu'il est décrit dans Interpolation SQL ci-dessous. Les formes :nom_variable et :"nom_variable" décrites là fonctionnent également. La syntaxe :{?nom_variable} permet de tester si une variable est définie. Elle est substituée par VRAI ou FAUX. L'échappement du deux-points avec une barre oblique inverse le protège de la substitution.

Dans un argument, le texte qui est entouré d'apostrophes inversées (`) est traité comme une ligne de commande qui est passée au shell. La sortie de la commande (avec toute nouvelle ligne finale supprimée) remplace le texte entouré d'apostrophes inversées. Dans le texte entouré d'apostrophes inversées, aucun traitement spécial d'échappement ou autre ne se produit, sauf que les apparitions de :nom_variable où nom_variable est un nom de variable psql sont remplacées par la valeur de la variable. De plus, les apparitions de :'nom_variable' sont remplacées par la valeur de la variable, correctement échappée pour devenir un seul argument de commande shell. (La dernière forme est presque toujours préférable, sauf si vous êtes très sûr de ce qui se trouve dans la variable.) Comme les caractères de retour chariot et de saut de ligne ne peuvent pas être échappés en toute sécurité sur toutes les plateformes, la forme :'nom_variable' affiche un message d'erreur et ne substitue pas la valeur de la variable lorsque de tels caractères apparaissent dans la valeur.

Certaines commandes prennent un identifiant SQL (tel qu'un nom de table) comme argument. Ces arguments suivent les règles de syntaxe SQL : les lettres non citées sont forcées en minuscules, tandis que les guillemets doubles (") protègent les lettres de la conversion de casse et permettent l'intégration d'espaces blancs dans l'identifiant. Dans les guillemets doubles, les guillemets doubles appariés sont réduits à un seul guillemet double dans le nom résultant. Par exemple, FOO"BAR"BAZ est interprété comme fooBARbaz, et "A weird"" name" devient A weird" name.

L'analyse des arguments s'arrête à la fin de la ligne, ou lorsqu'une autre barre oblique inverse non citée est trouvée. Une barre oblique inverse non citée est considérée comme le début d'une nouvelle méta-commande. La séquence spéciale \\ (deux barres obliques inverses) marque la fin des arguments et continue l'analyse des commandes SQL, le cas échéant. De cette façon, les commandes SQL et psql peuvent être librement mélangées sur une ligne. Mais dans tous les cas, les arguments d'une méta-commande ne peuvent pas dépasser la fin de la ligne.

Beaucoup de méta-commandes agissent sur le tampon de requête actuel. Celui-ci est simplement un tampon contenant tout texte de commande SQL qui a été tapé mais pas encore envoyé au serveur pour exécution. Cela inclura les lignes d'entrée précédentes ainsi que tout texte apparaissant avant la méta-commande sur la même ligne.

Beaucoup de méta-commandes permettent également d'ajouter x comme option. Cela provoquera l'affichage des résultats en mode étendu, comme si \x ou \pset expanded avait été utilisé.

Les méta-commandes suivantes sont définies :

\a

Si le format de sortie de table actuel est non aligné, il est échangé avec aligné. S'il n'est pas non aligné, il est défini sur non aligné. Cette commande est conservée pour la compatibilité ascendante. Voir \pset pour une solution plus générale.

\bind [ paramètre ] ...

Définit les paramètres de requête pour la prochaine exécution de requête, avec les paramètres spécifiés passés pour tous les espaces réservés de paramètres ($1 etc.).

Exemple :

INSERT INTO tbl1 VALUES ($1, $2) \bind 'première valeur' 'seconde valeur' \g

Cela fonctionne également pour les commandes d'exécution de requête autres que \g, telles que \gx et \gset.

Cette commande entraîne l'utilisation du protocole de requête étendu (voir Section 54.1.2), contrairement à l'opération psql normale, qui utilise le protocole de requête simple. Donc, cette commande peut être utile pour tester le protocole de requête étendu depuis psql. (Le protocole de requête étendu est utilisé même si la requête n'a pas de paramètres et que cette commande spécifie zéro paramètre.) Cette commande n'affecte que la prochaine requête exécutée ; toutes les requêtes ultérieures utiliseront le protocole de requête simple par défaut.

\bind_named nom_instruction [ paramètre ] ...

\bind_named est équivalent à \bind, sauf qu'il prend le nom d'une instruction préparée existante comme premier paramètre. Une chaîne vide dénote l'instruction préparée non nommée.

Exemple :

INSERT INTO tbls1 VALUES ($1, $2) \parse stmt1
\bind_named stmt1 'première valeur' 'seconde valeur' \g

Cette commande entraîne l'utilisation du protocole de requête étendu (voir Section 54.1.2), contrairement à l'opération psql normale, qui utilise le protocole de requête simple. Donc, cette commande peut être utile pour tester le protocole de requête étendu depuis psql.

\c ou \connect [ -reuse-previous=on|off ] [ nom_base [ nom_utilisateur ] [ hôte ] [ port ] | conninfo ]

Établit une nouvelle connexion à un serveur PostgreSQL. Les paramètres de connexion à utiliser peuvent être spécifiés soit en utilisant une syntaxe positionnelle (un ou plusieurs de nom de base de données, utilisateur, hôte et port), soit en utilisant une chaîne de connexion conninfo comme détaillé dans la Section 32.1.1. Si aucun argument n'est donné, une nouvelle connexion est établie en utilisant les mêmes paramètres qu'auparavant.

Spécifier l'un des nom_base, nom_utilisateur, hôte ou port comme - est équivalent à omettre ce paramètre.

La nouvelle connexion peut réutiliser les paramètres de connexion de la connexion précédente ; non seulement le nom de la base de données, l'utilisateur, l'hôte et le port, mais d'autres paramètres tels que sslmode. Par défaut, les paramètres sont réutilisés dans la syntaxe positionnelle, mais pas lorsqu'une chaîne conninfo est donnée. Passer un premier argument de -reuse-previous=on ou -reuse-previous=off remplace ce défaut. Si des paramètres sont réutilisés, alors tout paramètre non explicitement spécifié comme paramètre positionnel ou dans la chaîne conninfo est pris des paramètres de la connexion existante. Une exception est que si le paramètre hôte est modifié par rapport à sa valeur précédente en utilisant la syntaxe positionnelle, tout paramètre hostaddr présent dans les paramètres de la connexion existante est supprimé. De plus, tout mot de passe utilisé pour la connexion existante ne sera réutilisé que si les paramètres utilisateur, hôte et port ne sont pas modifiés. Lorsque la commande ne spécifie ni ne réutilise un paramètre particulier, la valeur par défaut libpq est utilisée.

Si la nouvelle connexion est établie avec succès, la connexion précédente est fermée. Si la tentative de connexion échoue (mauvais nom d'utilisateur, accès refusé, etc.), la connexion précédente sera conservée si psql est en mode interactif. Mais lors de l'exécution d'un script non interactif, l'ancienne connexion est fermée et une erreur est signalée. Cela peut ou peut ne pas terminer le script ; si ce n'est pas le cas, toutes les commandes d'accès à la base de données échoueront jusqu'à ce qu'une autre commande \connect soit exécutée avec succès. Cette distinction a été choisie comme commodité pour l'utilisateur contre les fautes de frappe d'une part, et comme mécanisme de sécurité pour que les scripts n'agissent pas accidentellement sur la mauvaise base de données d'autre part. Notez que chaque fois qu'une commande \connect tente de réutiliser des paramètres, les valeurs réutilisées sont celles de la dernière connexion réussie, pas celles de toute tentative échouée effectuée par la suite. Cependant, en cas d'échec d'un \connect non interactif, aucun paramètre ne peut être réutilisé plus tard, car le script s'attendrait probablement à ce que les valeurs de la \connect échouée soient réutilisées.

Exemples :

=> \c mydb myuser host.dom 6432
=> \c service=foo
=> \c "host=localhost port=5432 dbname=mydb connect_timeout=10 sslmode=disable"
=> \c -reuse-previous=on sslmode=require    -- ne change que sslmode
=> \c postgresql://tom@localhost/mydb?application_name=myapp

\copy { table [ ( liste_colonnes ) ] } de { 'nom_fichier' | programme 'commande' | stdin | pstdin } [ [ with ] ( option [, ...] ) ] [ where condition ]
\copy { table [ ( liste_colonnes ) ] | ( requête ) } vers { 'nom_fichier' | programme 'commande' | stdout | pstdout } [ [ with ] ( option [, ...] ) ]

Effectue une copie côté client (frontend). Il s'agit d'une opération qui exécute une commande SQL COPY, mais au lieu que le serveur lise ou écrive le fichier spécifié, psql lit ou écrit le fichier et achemine les données entre le serveur et le système de fichiers local. Cela signifie que l'accessibilité et les privilèges des fichiers sont ceux de l'utilisateur local, et non du serveur, et aucun privilège de superutilisateur SQL n'est requis.

Lorsque programme est spécifié, commande est exécutée par psql et les données passées depuis ou vers commande sont acheminées entre le serveur et le client. Encore une fois, les privilèges d'exécution sont ceux de l'utilisateur local, et non du serveur, et aucun privilège de superutilisateur SQL n'est requis.

Pour \copy ... from stdin, les lignes de données sont lues à partir de la même source qui a émis la commande, continuant jusqu'à une ligne contenant uniquement \. soit lue ou le flux atteigne EOF. Cette option est utile pour peupler les tables en ligne dans un fichier script SQL. Pour \copy ... to stdout, la sortie est envoyée au même endroit que la sortie de la commande psql, et le statut de la commande COPY count n'est pas imprimé (car il pourrait être confondu avec une ligne de données). Pour lire/écrire l'entrée ou la sortie standard de psql indépendamment de la source de commande actuelle ou de l'option \o, écrivez depuis pstdin ou vers pstdout.

La syntaxe de cette commande est similaire à celle de la commande SQL COPY. Toutes les options autres que la source/destination des données sont telles que spécifiées pour COPY. De ce fait, des règles d'analyse spéciales s'appliquent à la méta-commande \copy. Contrairement à la plupart des autres méta-commandes, lae tout le reste de la ligne est toujours considéré comme les arguments de \copy, et aucune interpolation de variable ni expansion de backquote ne sont effectuées dans les arguments.


Astuce
Une autre façon d'obtenir le même résultat que \copy ... to est d'utiliser la commande SQL COPY ... TO STDOUT et de la terminer avec \g nom_fichier ou \g |programme. Contrairement à \copy, cette méthode permet à la commande de s'étendre sur plusieurs lignes ; de plus, l'interpolation de variable et l'expansion de backquote peuvent être utilisées.

Astuce
Ces opérations ne sont pas aussi efficaces que la commande SQL COPY avec une source ou destination de fichier ou de programme, car toutes les données doivent transiter par la connexion client/serveur. Pour de grandes quantités de données, la commande SQL peut être préférable.

\crosstabview [ colV [ colH [ colD [ sortcolH ] ] ] ]

Exécute le buffer de requête actuel (comme \g) et affiche les résultats dans une grille croisée. La requête doit retourner au moins trois colonnes. La colonne de sortie identifiée par colV devient un en-tête vertical et la colonne de sortie identifiée par colH devient un en-tête horizontal. colD identifie la colonne de sortie à afficher dans la grille. sortcolH identifie une colonne de tri optionnelle pour l'en-tête horizontal.

Chaque spécification de colonne peut être un numéro de colonne (à partir de 1) ou un nom de colonne. Les règles habituelles de mise en casse et de mise entre guillemets SQL s'appliquent aux noms de colonnes. Si omis, colV est pris comme colonne 1 et colH comme colonne 2. colH doit être différent de colV. Si colD n'est pas spécifié, alors il doit y avoir exactement trois colonnes dans le résultat de la requête, et la colonne qui n'est ni colV ni colH est considérée comme colD.

L'en-tête vertical, affiché comme la colonne la plus à gauche, contient les valeurs trouvées dans la colonne colV, dans le même ordre que dans les résultats de la requête, mais avec les doublons supprimés.

L'en-tête horizontal, affiché comme la première ligne, contient les valeurs trouvées dans la colonne colH, avec les doublons supprimés. Par défaut, celles-ci apparaissent dans le même ordre que dans les résultats de la requête. Mais si l'argument optionnel sortcolH est donné, il identifie une colonne dont les valeurs doivent être des nombres entiers, et les valeurs de colH apparaîtront dans l'en-tête horizontal triées selon les valeurs correspondantes de sortcolH.

À l'intérieur de la grille croisée, pour chaque valeur distincte x de colH et chaque valeur distincte y de colV, la cellule située à l'intersection (x,y) contient la valeur de la colonne colD dans la ligne de résultat de la requête pour laquelle la valeur de colH est x et la valeur de colV est y. S'il n'y a pas de telle ligne, la cellule est vide. S'il y a plusieurs telles lignes, une erreur est signalée.

\if expression
\elif expression
\else
\endif

Ce groupe de commandes implémente des blocs conditionnels imbriquables. Un bloc conditionnel doit commencer par un \if et se terminer par un \endif. Entre les deux, il peut y avoir n'importe quel nombre de clauses \elif, qui peuvent éventuellement être suivies d'une seule clause \else. Des requêtes ordinaires et d'autres types de commandes backslash peuvent (et le font généralement) apparaître entre les commandes formant un bloc conditionnel.

Les commandes \if et \elif lisent leur (leurs) argument(s) et les évaluent comme une expression booléenne. Si l'expression renvoie vrai, le traitement continue normalement ; sinon, les lignes sont ignorées jusqu'à ce qu'un \elif, \else ou \endif correspondant soit atteint. Une fois qu'un test \if ou \elif a réussi, les arguments des commandes \elif ultérieures dans le même bloc ne sont pas évalués mais sont traités comme faux. Les lignes suivant un \else ne sont traitées que si aucun \if ou \elif correspondant antérieur n'a réussi.

L'argument expression d'une commande \if ou \elif est soumis à l'interpolation de variables et à l'expansion de backquotes, comme tout autre argument de commande backslash. Ensuite, il est évalué comme la valeur d'une variable d'option on/off. Ainsi, une valeur valide est toute correspondance insensible à la casse et sans ambiguïté avec l'un des éléments suivants : true, false, 1, 0, on, off, yes, no. Par exemple, t, T, et tR seront tous considérés comme vrais.

Les expressions qui ne s'évaluent pas correctement comme vrai ou faux généreront un avertissement et seront traitées comme fausses.

Les lignes ignorées sont analysées normalement pour identifier les requêtes et les commandes backslash, mais les requêtes ne sont pas envoyées au serveur, et les commandes backslash autres que les conditionnelles (\if, \elif, \else, \endif) sont ignorées. Les commandes conditionnelles ne sont vérifiées que pour une imbrication valide. Les références de variables dans les lignes ignorées ne sont pas développées, et l'expansion de backquotes n'est pas non plus effectuée.

Toutes les commandes backslash d'un bloc conditionnel donné doivent apparaître dans le même fichier source. Si EOF est atteint dans le fichier d'entrée principal ou dans un fichier inclus via \include avant que tous les blocs \if locaux n'aient été fermés, alors psql générera une erreur.

Voici un exemple :

-- vérifier l'existence de deux enregistrements distincts dans la base de données et stocker
-- les résultats dans des variables psql distinctes
SELECT
    EXISTS(SELECT 1 FROM customer WHERE customer_id = 123) as is_customer,
    EXISTS(SELECT 1 FROM employee WHERE employee_id = 456) as is_employee
\gset
\if :is_customer
    SELECT * FROM customer WHERE customer_id = 123;
\elif :is_employee
    \echo 'n'est pas un client mais est un employé'
    SELECT * FROM employee WHERE employee_id = 456;
\else
    \if yes
        \echo 'pas un client ou un employé'
    \else
        \echo 'ceci ne sera jamais imprimé'
    \endif
\endif

\lo_export loid filename

Lit l'objet volumineux avec l'OID loid à partir de la base de données et l'écrit dans filename. Notez que ceci est subtilement différent de la fonction serveur lo_export, qui agit avec les permissions de l'utilisateur sous lequel le serveur de base de données s'exécute et sur le système de fichiers du serveur.

Astuce
Utilisez \lo_list pour connaître l'OID de l'objet volumineux.

\lo_import filename [ comment ]

Stocke le fichier dans un objet volumineux PostgreSQL. Optionnellement, il associe le commentaire donné à l'objet. Exemple : 
foo=> \lo_import '/home/peter/pictures/photo.xcf' 'a picture of me'
lo_import 152801

La réponse indique que l'objet volumineux a reçu l'identifiant d'objet 152801, qui peut être utilisé pour accéder au nouvel objet volumineux créé à l'avenir. Pour des raisons de lisibilité, il est recommandé d'associer toujours un commentaire lisible par l'homme à chaque objet. Les OIDs et les commentaires peuvent être visualisés avec la commande \lo_list.

Notez que cette commande est subtilement différente de lo_import côté serveur car elle agit en tant qu'utilisateur local sur le système de fichiers local, plutôt qu'en tant qu'utilisateur du serveur et sur le système de fichiers du serveur.

\lo_list[x+]

Affiche une liste de tous les objets volumineux PostgreSQL actuellement stockés dans la base de données, ainsi que tous les commentaires qui leur ont été associés. Si x est ajouté au nom de la commande, les résultats sont affichés en mode étendu. Si + est ajouté au nom de la commande, chaque objet volumineux est listé avec ses permissions associées, le cas échéant.

\lo_unlink loid

Supprime l'objet volumineux avec l'OID loid de la base de données.

Astuce
Utilisez \lo_list pour fioutient l'OID du grand objet.

\o ou \out [ nom_fichier ]
\o ou \out [ |commande ]

Organise la sauvegarde des futurs résultats de requêtes dans le fichier nom_fichier ou le transfert des futurs résultats vers la commande shell commande. Si aucun argument n'est spécifié, la sortie de la requête est réinitialisée à la sortie standard.

Si l'argument commence par |, alors tout le reste de la ligne est considéré comme la commande à exécuter, et ni l'interpolation de variables ni l'expansion de guillemets inversés ne sont effectuées. Le reste de la ligne est simplement passé littéralement au shell.

“Résultats de requêtes” incluent toutes les tables, les réponses de commandes et les notifications obtenues du serveur de base de données, ainsi que la sortie de diverses commandes commençant par une barre oblique inverse qui interrogent la base de données (comme \d) ; mais pas les messages d'erreur.


Astuce
Pour intercaler du texte entre les résultats des requêtes, utilisez \qecho.

\p ou \print

Imprime le tampon de requête courant sur la sortie standard. Si le tampon de requête courant est vide, la requête exécutée le plus récemment est imprimée à la place.

\parse nom_instruction

Crée une instruction préparée à partir du tampon de requête courant, basée sur le nom d'un objet d'instruction préparée de destination. Une chaîne vide désigne l'instruction préparée sans nom.

Exemple :

SELECT $1 \parse stmt1

Cette commande provoque l'utilisation du protocole de requête étendue, contrairement à l'opération psql normale, qui utilise le protocole de requête simple. Un message Parse (F) sera émis par cette commande, elle peut donc être utile pour tester le protocole de requête étendue depuis psql. Cette commande n'affecte que la prochaine requête exécutée ; toutes les requêtes suivantes utiliseront par défaut le protocole de requête simple.

\password [ nom_utilisateur ]

Change le mot de passe de l'utilisateur spécifié (par défaut, l'utilisateur courant). Cette commande demande le nouveau mot de passe, le chiffre et l'envoie au serveur sous la forme d'une commande ALTER ROLE. Cela garantit que le nouveau mot de passe n'apparaît pas en clair dans l'historique des commandes, le journal du serveur, ou ailleurs.

\prompt [ texte ] nom

Invite l'utilisateur à fournir du texte, qui est assigné à la variable nom. Une chaîne d'invite optionnelle, texte, peut être spécifiée. (Pour les invites de plusieurs mots, entourez le texte de guillemets simples.)

Par défaut, \prompt utilise le terminal pour l'entrée et la sortie. Cependant, si le commutateur de ligne de commande -f a été utilisé, \prompt utilise l'entrée standard et la sortie standard.

\pset [ option [ valeur ] ]

Cette commande définit les options affectant la sortie des tables de résultats de requêtes. option indique quelle option doit être définie. La sémantique de valeur varie en fonction de l'option sélectionnée. Pour certaines options, omettre valeur provoque l'inversion ou la désactivation de l'option, comme décrit sous l'option particulière. Si aucun tel comportement n'est mentionné, alors omettre valeur affiche simplement le réglage actuel.

\pset sans aucun argument affiche l'état actuel de toutes les options d'impression.

Les options d'impression réglables sont :

border

La valeur doit être un nombre. En général, plus le nombre est élevé, plus les tables auront de bordures et de lignes, mais les détails dépendent du format particulier. En format HTML, cela se traduira directement par l'attribut border=... . Dans la plupart des autres formats, seuls les valeurs 0 (pas de bordure), 1 (lignes de division internes) et 2 (cadre de table) ont un sens, et les valeurs supérieures à 2 seront traitées de la même manière que border = 2. Les formats latex et latex-longtable permettent en plus une valeur de 3 pour ajouter des lignes de division entre les lignes de données.

columns

Définit la largeur cible pour le format enveloppé, ainsi que la limite de largeur pour déterminer si la sortie est suffisamment large pour nécessiter le pagineur ou passer à l'affichage vertical en mode automatique étendu. Zéro (par défaut) fait en sorte que la largeur cible soit contrôlée par la variable d'environnement COLUMNS, ou la largeur détectée de l'écran si COLUMNS n'est pas définie. De plus, si columns est zéro, le format enveloppé n'affecte que la sortie écran. Si columns est non nul, la sortie fichier et pipe est également enveloppée à cette largeur.

csv_fieldsep

Spécifie le séparateur de champ à utiliser dans le format de sortie CSV. Si le caractère séparateur apparaît dans la valeur d'un champ, ce champ est sorti entre guillemets doubles, suivant les règles CSV standard. Le défaut est une virgule.

expanded (ou x)

Si valeur est spécifiée, elle doit être on ou off, ce qui activera ou désactivera le mode étendu, ou auto. Si valeur est omise, la commande bascule entre les réglages on et off. Lorsque le mode étendu est activé, les résultats des requêtes sont affichés en deux colonnes, avec le nom de la colonne à gauche et les données à droite. Ce mode est utile si les données ne rentrent pas à l'écran en mode "horizontal" normal. En réglage auto, le mode étendu est utilisé chaque fois que la sortie de la requête a plus d'une colonne et est plus large que l'écran ; sinon, le mode régulier est utilisé. Le réglage auto n'est efficace que dans les formats aligné et enveloppé. Dans les autres formats, il se comporte toujours comme si le mode étendu était désactivé.

fieldsep

Spécifie le séparateur de champ à utiliser dans le format de sortie non aligné. Ainsi, on peut créer, par exemple, une sortie séparée par des tabulations, que d'autres programmes pourraient préférer. Pour définir une tabulation comme séparateur de champ, tapez \pset fieldsep '\t'. Le séparateur de champ par défaut est '|' (une barre verticale).

fieldsep_zero

Définit le séparateur de champ à utiliser dans le format de sortie non aligné comme un octet zéro.

footer

Si valeur est spécifiée, elle doit être on ou off, ce qui activera ou désactivera l'affichage du pied de page de la table (le compte (n lignes)). Si valeur est omise, la commande bascule l'affichage du pied de page on ou off.

format

Définit le format de sortie sur l'un des suivants : aligned, asciidoc, csv, html, latex, latex-longtable, troff-ms, unaligned, ou wrapped. Les abréviations uniques sont autorisées.

Le format aligned est la sortie texte standard, lisible par l'homme et bien formatée ; c'est le défaut.

Le format unaligned écrit toutes les colonnes d'une ligne sur une seule ligne, séparées par le séparateur de champ actif. Ceci est utile pour créer une sortie qui pourrait être destinée à être lue par d'autres programmes, par exemple, un format séparé par des tabulations ou des virgules. Cependant, le caractère séparateur de champ n'est pas traité spécialement s'il apparaît dans la valeur d'une colonne ; donc le format CSV peut être mieux adapté à de telles fins.

Le format csv

écrit les valeurs de colonnes séparées par des virgules, en appliquant les règles de mise entre guillemets décrites dans la RFC 4180. Cette sortie est compatible avec le format CSV de la commande COPY du serveur. Une ligne d'en-tête avec les noms de colonnes est générée sauf si le paramètre tuples_only est activé. Les titres et les pieds de page ne sont pas imprimés. Chaque ligne est terminée par le caractère de fin de ligne dépendant du système, qui est typiquement un seul saut de ligne (\n) pour les systèmes de type Unix ou une séquence retour chariot et saut de ligne (\r\n) pour Microsoft Windows. Les séparateurs de champs autres que la virgule peuvent être sélectionnés avec \pset csv_fieldsep.

Le format wrapped est comme aligned mais enveloppe les valeurs de données larges sur plusieurs lignes pour que la sortie rentre dans la largeur de colonne cible. La largeur cible est déterminée comme décrit sous l'option columns. Notez que psql n'essaiera pas d'envelopper les titres d'en-tête de colonne ; par conséquent, le format wrapped se comporte de la même manière que aligned si la largeur totale nécessaire pour les titres de colonne dépasse la cible.

Les formats asciidoc, html, latex, latex-longtable et troff-ms génèrent des tables destinées à être incluses dans des documents utilisant le langage de balisage respectif. Ce ne sont pas des documents complets ! Cela peut ne pas être nécessaire en HTML, mais en LaTeX, vous devez avoir un wrapper de document complet. Le format latex utilise l'environnement tabular de LaTeX. Le format latex-longtable nécessite les packages LaTeX longtable et booktabs.

linestyle

Définit le style de dessin des lignes de bordure sur ascii, old-ascii, ou unicode. Les abréviations uniques sont autorisées. (Cela signifie qu'une seule lettre suffit.) Le réglage par défaut est ascii. Cette option n'affecte que les formats de sortie aligné et enveloppé.

Le style ascii utilise des caractères ASCII simples. Les sauts de ligne dans les données sont affichés à l'aide d'un symbole + dans la marge droite. Lorsque le format enveloppé ramène des données d'une ligne à la suivante sans saut de ligne, un point (.) est affiché dans la marge droite de la première ligne, et à nouveau dans la marge gauche de la ligne suivante.

Le style old-ascii utilise des caractères ASCII simples, en utilisant le style de formatage utilisé dans PostgreSQL 8.4 et antérieur. Les sauts de ligne dans les données sont affichés à l'aide d'un symbole : à la place du séparateur de colonne de gauche. Lorsque les données sont enveloppées d'une ligne à la suivante sans saut de ligne, un symbole ; est utilisé à la place du séparateur de colonne de gauche.

Le style unicode utilise des caractères de dessin de boîte Unicode. Les sauts de ligne dans les données sont affichés à l'aide d'un symbole de retour chariot dans la marge droite. Lorsque les données sont enveloppées d'une ligne à la suivante sans saut de ligne, un symbole d'ellipse est affiché dans la marge droite de la première ligne, et à nouveau dans la marge gauche de la ligne suivante.

Lorsque le réglage de bordure est supérieur à zéro, l'option linestyle détermine également les caractères avec lesquels les lignes de bordure sont dessinées. Les caractères ASCII simples fonctionnent partout, mais les caractères Unicode ont une meilleure apparence sur les affichages qui les reconnaissent.

null

Définit la chaîne à imprimer à la place d'une valeur nulle. Le défaut est de n'imprimer rien, ce qui peut facilement être confondu avec une chaîne vide. Par exemple, on pourrait préférer \pset null '(null)'.

numericlocale

Si valeur est spécifiée, elle doit être on ou off, ce qui activera ou désactivera l'affichage d'un caractère spécifique à la locale pour séparer les groupes de chiffres à gauche du marqueur décimal. Si valeur est omise, la commande bascule entre la sortie numérique régulière et celle spécifique à la locale.

pager

Contrôle l'utilisation d'un programme de pagineur pour les sorties de requête et d'aide psql. Lorsque l'option pager est désactivée, le programme de pagineur n'est pas utilisé. Lorsque l'option pager est activée, le pagineur est utilisé lorsque c'est approprié, c'est-à-dire lorsque la sortie est destinée à un terminal et ne rentre pas à l'écran. L'option pager peut également être réglée sur always, ce qui fait que le pagineur est utilisé pour toutes les sorties de terminal, qu'elles rentrent ou non à l'écran. \pset pager sans valeur active ou désactive l'utilisation du pagineur.

Si la variable d'environnement PSQL_PAGER ou PAGER est définie, la sortie à paginer est canalisée vers le programme spécifié. Sinon, un programme par défaut dépendant de la plateforme (comme more) est utilisé.

Lorsque vous utilisez la commande \watch pour exécuter une requête de manière répétée, la variable d'environnement PSQL_WA

TCH_PAGER est utilisé pour trouver le programme pager à la place, sur les systèmes Unix. Ceci est configuré séparément car il peut confondre les pagers traditionnels, mais peut être utilisé pour envoyer la sortie vers des outils qui comprennent le format de sortie de psql (tel que pspg --stream).

pager_min_lines

Si pager_min_lines est réglé sur un nombre supérieur à la hauteur de la page, le programme pager ne sera pas appelé à moins qu'il y ait au moins ce nombre de lignes de sortie à afficher. Le réglage par défaut est 0.

recordsep

Spécifie le séparateur d'enregistrement (ligne) à utiliser dans le format de sortie non aligné. Le défaut est un caractère de nouvelle ligne.

recordsep_zero

Règle le séparateur d'enregistrement à utiliser dans le format de sortie non aligné sur un octet nul.

tableattr (ou T)

En format HTML, ceci spécifie les attributs à placer à l'intérieur de la balise table. Cela pourrait par exemple être cellpadding ou bgcolor. Notez que vous ne voudrez probablement pas spécifier border ici, car c'est déjà géré par \pset border. Si aucune valeur n'est donnée, les attributs de table sont désactivés.

En format latex-longtable, cela contrôle la largeur proportionnelle de chaque colonne contenant un type de données aligné à gauche. Il est spécifié comme une liste de valeurs séparées par des espaces blancs, par exemple '0.2 0.2 0.6'. Les colonnes de sortie non spécifiées utilisent la dernière valeur spécifiée.

title (ou C)

Définit le titre de la table pour toutes les tables imprimées ultérieurement. Ceci peut être utilisé pour donner des étiquettes descriptives à votre sortie. Si aucune valeur n'est donnée, le titre est désactivé.

tuples_only (ou t)

Si une valeur est spécifiée, elle doit être on ou off, ce qui activera ou désactivera le mode tuples seulement. Si la valeur est omise, la commande bascule entre la sortie normale et la sortie en mode tuples seulement. La sortie normale inclut des informations supplémentaires telles que les en-têtes de colonne, les titres et divers pieds de page. En mode tuples seulement, seules les données réelles de la table sont affichées.

unicode_border_linestyle

Définit le style de dessin de bordure pour le style de ligne unicode sur single ou double.

unicode_column_linestyle

Définit le style de dessin de colonne pour le style de ligne unicode sur single ou double.

unicode_header_linestyle

Définit le style de dessin d'en-tête pour le style de ligne unicode sur single ou double.

xheader_width

Définit la largeur maximale de l'en-tête pour la sortie étendue sur full (la valeur par défaut), column, page, ou une valeur entière.

full : l'en-tête étendu n'est pas tronqué et aura la largeur de la ligne de sortie la plus large.

column : tronque la ligne d'en-tête à la largeur de la première colonne.

page : tronque la ligne d'en-tête à la largeur du terminal.

valeur entière : spécifie la largeur maximale exacte de la ligne d'en-tête.

Des illustrations de l'apparence de ces différents formats peuvent être vues dans Exemples, ci-dessous.


Astuce
Il existe diverses commandes de raccourci pour \pset. Voir \a, \C, \f, \H, \t, \T, et \x.

\q ou \quit

Quitte le programme psql. Dans un fichier script, seule l'exécution de ce script est terminée.

\qecho texte [ ... ]

Cette commande est identique à \echo sauf que la sortie sera écrite dans le canal de sortie de requête, tel que défini par \o.

\r ou \reset

Réinitialise (efface) le tampon de requête.

\restrict restrict_key

Entre en mode "restreint" avec la clé fournie. Dans ce mode, la seule méta-commande autorisée est \unrestrict, pour quitter le mode restreint. La clé ne peut contenir que des caractères alphanumériques.

Cette commande est principalement destinée à être utilisée dans les dumps texte brut générés par pg_dump, pg_dumpall et pg_restore, mais elle peut être utile ailleurs.

\s [ nom_fichier ]

Imprime l'historique des commandes psql dans nom_fichier. Si nom_fichier est omis, l'historique est écrit sur la sortie standard (en utilisant le pager si approprié). Cette commande n'est pas disponible si psql a été compilé sans support Readline.

\set [ nom [ valeur [ ... ] ] ]

Définit la variable psql nom à valeur, ou si plus d'une valeur est donnée, à la concaténation de toutes. Si un seul argument est donné, la variable est définie sur une chaîne vide. Pour désactiver une variable, utilisez la commande \unset.

\set sans aucun argument affiche les noms et les valeurs de toutes les variables psql actuellement définies.

Les noms de variables valides peuvent contenir des lettres, des chiffres et des underscores. Voir Variables ci-dessous pour les détails. Les noms de variables sont sensibles à la casse.

Certaines variables sont spéciales, dans le sens où elles contrôlent le comportement de psql ou sont automatiquement définies pour refléter l'état de la connexion. Ces variables sont documentées dans Variables, ci-dessous.


Note
Cette commande n'est pas liée à la commande SQL SET.

\setenv nom [ valeur ]

Définit la variable d'environnement nom à valeur, ou si la valeur n'est pas fournie, désactive la variable d'environnement. Exemple : 
testdb=> \setenv PAGER less
testdb=> \setenv LESS -imx4F

\sf[+] description_fonction

Cette commande récupère et affiche la définition de la fonction ou procédure nommée, sous la forme d'une commande CREATE OR REPLACE FUNCTION ou CREATE OR REPLACE PROCEDURE. La définition est imprimée sur le canal de sortie de requête actuel, tel que défini par \o.

La fonction cible peut être spécifiée par son nom seul, ou par son nom et ses arguments, par exemple foo(integer, text). Les types d'arguments doivent être donnés s'il y a plus d'une fonction du même nom.

Si + est ajouté au nom de la commande, alors les lignes de sortie sont numérotées, la première ligne du corps de la fonction étant la ligne 1.

Contrairement à la plupart des autres méta-commandes, le reste de la ligne est toujours considéré comme l'argument(s) de \sf, et ni l'interpolation de variable ni l'expansion par backquote ne sont effectuées dans les arguments.

\sv[+] nom_vue

Cette commande récupère et affiche la définition de la vue nommée, sous la forme d'une commande CREATE OR REPLACE VIEW. La définition est imprimée sur le canal de sortie de requête actuel, tel que défini par \o.

Si + est ajouté au nom de la commande, alors les lignes de sortie sont numérotées à partir de 1.

Contrairement à la plupart des autres méta-commandes, le reste de la ligne est toujours considéré comme l'argument(s) de \sv, et ni l'interpolation de variable ni l'expansion par backquote ne sont effectuées dans les arguments.

\startpipeline
\sendpipeline
\syncpipeline
\endpipeline
\flushrequest
\flush
\getresults [ nombre_resultats ]

Ce groupe de commandes implémente le pipelining des instructions SQL. Un pipeline doit commencer par \startpipeline et se terminer par \endpipeline. Entre les deux, il peut y avoir n'importe quel nombre de commandes \syncpipeline, qui envoient un message de synchronisation sans terminer le pipeline en cours et sans vider le tampon d'envoi. En mode pipeline, les instructions sont envoyées au serveur sans attendre les résultats des instructions précédentes. Voir la Section 32.5 pour plus de détails.

Toutes les requêtes exécutées pendant qu'un pipeline est en cours utilisent le protocole de requête étendu. Les requêtes sont ajoutées au pipeline lorsqu'elles se terminent par un point-virgule. Les méta-commandes \bind, \bind_named, \close_prepared ou \parse peuvent être utilisées dans un pipeline en cours. Pendant qu'un pipeline est en cours, \sendpipeline ajoutera le tampon de requête actuel au pipeline. D'autres méta-commandes comme \g, \gx ou \gdesc ne sont pas autorisées en mode pipeline.

\flushrequest ajoute une commande flush au pipeline, permettant de lire les résultats avec \getresults sans émettre de synchronisation ou terminer le pipeline. \getresults poussera automatiquement les données non envoyées au serveur. \flush peut être utilisé pour pousser manuellement les données non envoyées.

\getresults accepte un paramètre optionnel nombre_resultats. S'il est fourni, seuls les nombre_resultats résultats en attente seront lus. S'il n'est pas fourni ou s'il est 0, tous les résultats en attente sont lus.

Lorsque le mode pipeline est actif, une variable de prompt dédiée est disponible pour indiquer l'état du pipeline. Voir %P pour plus de détails.

COPY n'est pas pris en charge en mode pipeline.

Exemple :

\startpipeline
SELECT * FROM pg_class;
SELECT 1 \bind \sendpipeline
\flushrequest
\getresults
\endpipeline

\t

Active ou désactive l'affichage des noms des colonnes de sortie et du pied de page avec le nombre de lignes. Cette commande est équivalente à \pset tuples_only et est fournie pour plus de commodité.

\T options_table

Spécifie les attributs à placer dans la balise table au format de sortie HTML. Cette commande est équivalente à \pset tableattr options_table.

\timing [ on | off ]

Avec un paramètre, active ou désactive l'affichage du temps nécessaire à chaque instruction SQL. Sans paramètre, bascule l'affichage entre activé et désactivé. L'affichage est en millisecondes ; les intervalles supérieurs à 1 seconde sont également affichés au format minutes:secondes, avec des champs heures et jours ajoutés si nécessaire.

\unrestrict restrict_key

Quitte le mode "restreint" (c'est-à-dire, où toutes les autres méta-commandes sont bloquées), à condition que la clé spécifiée corresponde à celle donnée à \restrict lorsque le mode restreint a été entré.

Cette commande est principalement destinée à être utilisée dans les dumps texte brut générés par pg_dump, pg_dumpall et pg_restore, mais elle peut être utile ailleurs.

\unset nom

Désactive (supprime) la variable psql nom.

La plupart des variables qui contrôlent le comportement de psql ne peuvent pas être désactivées ; au lieu de cela, une commande \unset est interprétée comme les définissant à leurs valeurs par défaut. Voir Variables ci-dessous.

\w ou \write nom_fichier
\w ou \write |commande

Écrit le tampon de requête actuel dans le fichier nom_fichier ou le redirige vers la commande shell commande. Si le tampon de requête actuel est vide, la requête exécutée le plus récemment est écrite à la place.

Si l'argument commence par |, alors tout le reste de la ligne est considéré comme la commande à exécuter, et ni l'interpolation de variable ni l'expansion par backquote ne sont effectuées. Le reste de la ligne est simplement transmis littéralement au shell.

\warn texte [ ... ]

Cette commande est identique à \echo sauf que la sortie sera écrite sur le canal d'erreur standard de psql, plutôt que sur la sortie standard.

\watch [ i[nterval]=seconds ] [ c[ount]=times ] [ m[in_rows]=rows ] [ seconds ]

Exécute de manière répétée le tampon de requête actuel (comme le fait \g) jusqu'à interruption, échec de la requête, atteinte de la limite de nombre d'exécutions (si spécifiée), ou jusqu'à ce que la requête ne renvoie plus le nombre minimum de lignes. Attend le nombre spécifié de secondes (par défaut 2) entre les exécutions. L'attente par défaut peut être modifiée avec la variable WATCH_INTERVAL. Pour des raisons de compatibilité ascendante, seconds peut être spécifié avec ou sans le préfixe interval=. Chaque résultat de requête est affiché avec un en-tête qui inclut la chaîne de titre \pset (le cas échéant), l'heure du début de la requête et l'intervalle de délai.

Si le tampon de requête actuel est vide, la dernière requête envoyée est réexécutée.

\x [ on | off | auto ]

Définit ou bascule le mode de formatage de table étendu. En tant que tel, il est équivalent à \pset expanded.

\z[Sx] [ pattern ]

Liste les tables, les vues et les séquences avec leurs privilèges d'accès associés. Si un pattern est spécifié, seules les tables, vues et séquences dont les noms correspondent au pattern sont listées. Par défaut, seuls les objets créés par l'utilisateur sont affichés ; fournissez un pattern ou le modificateur S pour inclure les objets système. Si x est ajouté au nom de la commande, les résultats sont affichés en mode étendu.

Ceci est un alias pour \dp (« display privileges »).

\! [ command ]

Sans argument, échappe vers un sous-shell ; psql reprend lorsque le sous-shell se termine. Avec un argument, exécute la commande shell command.

Contrairement à la plupart des autres méta-commandes, le reste de la ligne est toujours considéré comme les arguments de \!, et ni l'interpolation de variables ni l'expansion par guillemets inversés ne sont effectuées dans les arguments. Le reste de la ligne est simplement passé littéralement au shell.

\? [ topic ]

Affiche les informations d'aide. Le paramètre optionnel topic (par défaut commands) sélectionne quelle partie de psql est expliquée : commands décrit les commandes en antislash de psql ; options décrit les options de ligne de commande qui peuvent être passées à psql ; et variables montre l'aide sur les variables de configuration de psql.

\;

L'antislash-point-virgule n'est pas une méta-commande de la même manière que les commandes précédentes ; il ajoute simplement un point-virgule au tampon de requête sans aucun traitement supplémentaire.

Normalement, psql envoie une commande SQL au serveur dès qu'il atteint le point-virgule de fin de commande, même s'il reste une entrée sur la ligne actuelle. Ainsi, par exemple, en entrant

select 1; select 2; select 3;

cela entraînera l'envoi individuel des trois commandes SQL au serveur, chaque résultat étant affiché avant de passer à la commande suivante. Cependant, un point-virgule entré en tant que \; ne déclenchera pas le traitement de la commande, de sorte que la commande précédente et celle qui suit sont effectivement combinées et envoyées au serveur en une seule requête. Ainsi, par exemple

select 1\; select 2\; select 3;

résulte en l'envoi des trois commandes SQL au serveur en une seule requête, lorsque le point-virgule non précédé d'un antislash est atteint. Le serveur exécute une telle requête comme une transaction unique, à moins qu'il n'y ait des commandes BEGIN/COMMIT explicites incluses dans la chaîne pour la diviser en plusieurs transactions. (Voir la section 54.2.2.1 pour plus de détails sur la façon dont le serveur gère les chaînes de requêtes multiples.)

Patterns

Les diverses commandes \d acceptent un paramètre pattern pour spécifier les noms d'objets à afficher. Dans le cas le plus simple, un pattern est juste le nom exact de l'objet. Les caractères dans un pattern sont normalement mis en minuscules, tout comme dans les noms SQL ; par exemple, \dt FOO affichera la table nommée foo. Comme pour les noms SQL, placer des guillemets doubles autour d'un pattern arrête la mise en minuscules. Si vous devez inclure un caractère de guillemet double réel dans un pattern, écrivez-le comme une paire de guillemets doubles dans une séquence de guillemets doubles ; là encore, cela est conforme aux règles pour les identifiants SQL entre guillemets. Par exemple, \dt "FOO""BAR" affichera la table nommée FOO"BAR (pas foo"bar). Contrairement aux règles normales pour les noms SQL, vous pouvez placer des guillemets doubles autour d'une partie seulement d'un pattern, par exemple \dt FOO"FOO"BAR affichera la table nommée fooFOObar.

Lorsque le paramètre pattern est complètement omis, les commandes \d affichent tous les objets visibles dans le chemin de recherche de schéma actuel — cela équivaut à utiliser * comme pattern. (Un objet est dit visible si son schéma contenant est dans le chemin de recherche et qu'aucun objet du même type et nom n'apparaît plus tôt dans le chemin de recherche. Ceci équivaut à l'affirmation que l'objet peut être référencé par son nom sans qualification de schéma explicite.) Pour voir tous les objets de la base de données, quelle que soit leur visibilité, utilisez *.* comme pattern.

Dans un pattern, * correspond à n'importe quelle séquence de caractères (y compris aucune) et ? correspond à n'importe quel caractère unique. (Cette notation est comparable aux patterns de noms de fichiers du shell Unix.) Par exemple, \dt int* affiche les tables dont les noms commencent par int. Mais entre guillemets doubles, * et ? perdent leurs significations spéciales et sont simplement mis en correspondance littéralement.

Un pattern de relation contenant un point (.) est interprété comme un pattern de nom de schéma suivi d'un pattern de nom d'objet. Par exemple, \dt foo*.*bar* affiche toutes les tables dont le nom de table inclut bar et qui se trouvent dans des schémas dont le nom commence par foo. Lorsqu'aucun point n'apparaît, le pattern ne correspond qu'aux objets visibles dans le chemin de recherche de schéma actuel. Encore une fois, un point entre guillemets doubles perd sa signification spéciale et est mis en correspondance littéralement. Un pattern de relation contenant deux points (.) est interprété comme un nom de base de données suivi d'un pattern de nom de schéma suivi d'un pattern de nom d'objet. La partie nom de base de données ne sera pas traitée comme un pattern et doit correspondre au nom de la base de données actuellement connectée, sinon une erreur sera générée.

Un pattern de schéma contenant un point (.) est interprété comme un nom de base de données suivi d'un pattern de nom de schéma. Par exemple, \dn mydb.*foo* affiche tous les schémas dont le nom de schéma inclut foo. La partie nom de base de données ne sera pas traitée comme un pattern et doit correspondre au nom de la base de données actuellement connectée, sinon une erreur sera générée.

Les utilisateurs avancés peuvent utiliser des notations d'expressions régulières comme les classes de caractères, par exemple [0-9] pour correspondre à n'importe quel chiffre. Tous les caractères spéciaux des expressions régulières fonctionnent comme spécifié dans la section 9.7.3, à l'exception de . qui est pris comme séparateur comme mentionné ci-dessus, * qui est traduit en notation d'expression régulière .*, ? qui est traduit en ., et $ qui est mis en correspondance littéralement. Vous pouvez émuler ces caractères de pattern au besoin en écrivant ? pour ., (R+|) pour R*, ou (R|) pour R?. $ n'est pas nécessaire en tant que caractère d'expression régulière puisque le pattern doit correspondre à l'ensemble du nom, contrairement à l'interprétation habituelle des expressions régulières (en d'autres termes, $ est automatiquement ajouté à votre pattern). Écrivez * au début et/ou à la fin si vous ne souhaitez pas que le pattern soit ancré. Notez qu'entre guillemets doubles, tous les caractères spéciaux des expressions régulières perdent leurs significations spéciales et sont mis en correspondance littéralement. De plus, les caractères spéciaux des expressions régulières sont mis en correspondance littéralement dans les patterns de noms d'opérateurs (c'est-à-dire l'argument de \do).

Fonctionnalités avancées

Variables

psql offre des fonctionnalités de substitution de variables similaires aux shells Unix courants. Les variables sont simplement des paires nom/valeur, où la valeur peut être n'importe quelle chaîne de n'importe quelle longueur. Le nom doit être composé de lettres (y compris des lettres non latines), de chiffres et d'underscores.

Pour définir une variable, utilisez la méta-commande psql \set. Par exemple,

testdb=> \set foo bar

définit la variable foo à la valeur bar. Pour récupérer le contenu de la variable, préfixez le nom par deux-points, par exemple :

testdb=> \echo :foo
bar

Cela fonctionne aussi bien dans les commandes SQL régulières que dans les méta-commandes ; plus de détails dans l'interpolation SQL, ci-dessous.

Si vous appelez \set sans second argument, la variable est définie sur une chaîne vide. Pour supprimer (c'est-à-dire supprimer) une variable, utilisez la commande \unset. Pour afficher les valeurs de toutes les variables, appelez \set sans aucun argument.


Note

Les arguments de \set sont soumis aux mêmes règles de substitution qu'avec d'autres commandes. Ainsi, vous pouvez construire des références intéressantes comme \set :foo 'something' et obtenir des « liens symboliques » ou des « variables variables » de la renommée Perl ou PHP, respectivement. Malheureusement (ou heureusement ?), il n'y a aucun moyen de faire quoi que ce soit d'utile avec ces constructions. D'un autre côté, \set bar :foo est une manière parfaitement valide de copier une variable.

Un certain nombre de ces variables sont traitées spécialement par psql. Elles représentent certains réglages d'options qui peuvent être modifiés à l'exécution en changeant la valeur de la variable, ou représentent dans certains cas un état modifiable de psql. Par convention, tous les noms de variables traitées spécialement sont composés uniquement de lettres ASCII majuscules (et éventuellement de chiffres et d'underscores). Pour assurer une compatibilité maximale à l'avenir, évitez d'utiliser de tels noms de variables pour vos propres besoins.

Les variables qui contrôlent le comportement de psql ne peuvent généralement pas être supprimées ou définies sur des valeurs invalides. Une commande \unset est autorisée mais est interprétée comme définissant la variable à sa valeur par défaut. Une commande \set sans second argument est interprétée comme définissant la variable sur on, pour les variables de contrôle qui acceptent cette valeur, et est rejetée pour les autres. De plus, les variables de contrôle qui acceptent les valeurs on et off accepteront également d'autres orthographes courantes des valeurs booléennes, telles que true et false.

Interpolation SQL

Une caractéristique clé des variables psql est que vous pouvez les substituer ("interpoler") dans des instructions SQL régulières, ainsi que dans les arguments des méta-commandes. De plus, psql fournit des installations pour s'assurer que les valeurs de variables utilisées comme littéraux et identifiants SQL sont correctement citées. La syntaxe pour interpoler une valeur sans aucune citation consiste à préfixer le nom de la variable avec un deux-points (:). Par exemple,

testdb=> \set foo 'my_table'
testdb=> SELECT * FROM :foo;

interrogerait la table my_table. Notez que cela peut être dangereux : la valeur de la variable est copiée littéralement, elle peut donc contenir des guillemets déséquilibrés, ou même des commandes de barre oblique inverse. Vous devez vous assurer qu'elle a un sens là où vous la placez.

Lorsqu'une valeur doit être utilisée comme littéral ou identifiant SQL, il est plus sûr de la faire citer. Pour citer la valeur d'une variable comme littéral SQL, écrivez un deux-points suivi du nom de la variable entre guillemets simples. Pour citer la valeur comme identifiant SQL, écrivez un deux-points suivi du nom de la variable entre guillemets doubles. Ces constructions gèrent correctement les guillemets et autres caractères spéciaux intégrés dans la valeur de la variable. L'exemple précédent serait écrit plus sûrement de cette façon :

testdb=> \set foo 'my_table'
testdb=> SELECT * FROM :"foo";

L'interpolation de variable ne sera pas effectuée dans les littéraux et identifiants SQL cités. Par conséquent, une construction telle que ':foo' ne fonctionne pas pour produire un littéral cité à partir de la valeur d'une variable (et ce serait dangereux si cela fonctionnait, car cela ne gérerait pas correctement les guillemets intégrés dans la valeur).

Une utilisation de ce mécanisme consiste à copier le contenu d'un fichier dans une colonne de table. Chargez d'abord le fichier dans une variable, puis interpolez la valeur de la variable comme une chaîne citée :

testdb=> \set content `cat my_file.txt`
testdb=> INSERT INTO my_table VALUES (:'content');

(Notez que cela ne fonctionnera toujours pas si my_file.txt contient des octets NUL. psql ne prend pas en charge les octets NUL intégrés dans les valeurs de variables.)

Étant donné que les deux-points peuvent apparaître légalement dans les commandes SQL, une tentative apparente d'interpolation (c'est-à-dire :name, :'name', ou :"name") n'est pas remplacée à moins que la variable nommée ne soit actuellement définie. Dans tous les cas, vous pouvez échapper un deux-points avec une barre oblique inverse pour le protéger de la substitution.

La syntaxe spéciale :{?name} renvoie TRUE ou FALSE selon que la variable existe ou non, et est donc toujours substituée, sauf si le deux-points est échappé par une barre oblique inverse.

La syntaxe des deux-points pour les variables est la norme SQL pour les langages de requête intégrés, tels que ECPG. Les syntaxes des deux-points pour les tranches de tableaux et les transtypages sont des extensions PostgreSQL, qui peuvent parfois entrer en conflit avec l'utilisation standard. La syntaxe deux-points-citation pour échapper la valeur d'une variable en tant que littéral ou identifiant SQL est une extension psql.

Invite de commande

Les invites que psql émet peuvent être personnalisées selon vos préférences. Les trois variables PROMPT1, PROMPT2 et PROMPT3 contiennent des chaînes et des séquences d'échappement spéciales qui décrivent l'apparence de l'invite. L'invite 1 est l'invite normale qui est émise lorsque psql demande une nouvelle commande. L'invite 2 est émise lorsque plus d'entrée est attendue lors de la saisie de commandes, par exemple parce que la commande n'a pas été terminée par un point-virgule ou qu'une citation n'a pas été fermée. L'invite 3 est émise lorsque vous exécutez une commande SQL COPY FROM STDIN et que vous devez saisir une valeur de ligne sur le terminal.

La valeur de la variable d'invite sélectionnée est imprimée littéralement, sauf lorsqu'un signe de pourcentage (%) est rencontré. Selon le caractère suivant, d'autres textes sont substitués. Les substitutions définies sont :

%M

Le nom d'hôte complet (avec nom de domaine) du serveur de base de données, ou [local] si la connexion s'effectue via une socket de domaine Unix, ou [local:/dir/name], si la socket de domaine Unix n'est pas à l'emplacement par défaut compilé.

%m

Le nom d'hôte du serveur de base de données, tronqué au premier point, ou [local] si la connexion s'effectue via une socket de domaine Unix.

%>

Le numéro de port sur lequel le serveur de base de données écoute.

%n

Le nom de l'utilisateur de la session de base de données. (L'expansion de cette valeur peut changer pendant une session de base de données suite à la commande SET SESSION AUTHORIZATION.)

%s

Le nom du service.

%/

Le nom de la base de données actuelle.

%~

Comme %/, mais la sortie est ~ (tilde) si la base de données est votre base de données par défaut.

%#

Si l'utilisateur de la session est un superutilisateur de base de données, alors un #, sinon un >. (L'expansion de cette valeur peut changer pendant une session de base de données suite à la commande SET SESSION AUTHORIZATION.)

%p

L'ID de processus du backend actuellement connecté.

%P

Statut du pipeline : off lorsqu'il n'est pas dans un pipeline, on lorsqu'il est dans un pipeline en cours ou abort lorsqu'il est dans un pipeline abandonné.

%R

Dans l'invite 1, normalement =, mais @ si la session est dans une branche inactive d'un bloc conditionnel, ou ^ si en mode ligne unique, ou ! si la session est déconnectée de la base de données (ce qui peut arriver si \connect échoue). Dans l'invite 2, %R est remplacé par un caractère qui dépend de la raison pour laquelle psql attend plus d'entrée : - si la commande n'est tout simplement pas encore terminée, mais * s'il y a un commentaire /* ... */ inachevé, un guillemet simple s'il y a une chaîne citée inachevée, un guillemet double s'il y a un identifiant cité inachevé, un signe dollar s'il y a une chaîne citée par dollar inachevée, ou ( s'il y a une parenthèse gauche non appariée. Dans l'invite 3, %R ne produit rien.

%x

Statut de la transaction : une chaîne vide lorsqu'elle n'est pas dans un bloc de transaction, ou * lorsqu'elle est dans un bloc de transaction, ou ! lorsqu'elle est dans un bloc de transaction échoué, ou ? lorsque l'état de la transaction est indéterminé (par exemple, parce qu'il n'y a pas de connexion).

%l

Le numéro de ligne à l'intérieur de l'instruction actuelle, commençant à 1.

%digits

Le caractère avec le code octal indiqué est substitué.

%:name:

La valeur de la variable psql name. Voir Variables, ci-dessus, pour plus de détails.

%`command`

La sortie de command, similaire à la substitution ordinaire des "guillemets inversés".

%[ ... %]

Les invites peuvent contenir des caractères de contrôle de terminal qui, par exemple, changent la couleur, l'arrière-plan ou le style du texte de l'invite, ou changent le titre de la fenêtre du terminal. Pour que les fonctionnalités d'édition de ligne de Readline fonctionnent correctement, ces caractères de contrôle non imprimables doivent être désignés comme invisibles en les entourant de %[ et %]. Plusieurs paires de ceux-ci peuvent apparaître dans l'invite. Par exemple : 
testdb=> \set PROMPT1 '%[%033[1;33;40m%]%n@%/%R%[%033[0m%]%# '

résulte en une invite en gras (1;) jaune sur noir (33;40) sur les terminaux compatibles VT100 et capables de couleurs.

%w

Espace blanc de la même largeur que la sortie la plus récente de PROMPT1. Cela peut être utilisé comme paramètre PROMPT2, de sorte que les instructions multi-lignes soient alignées avec la première ligne, mais qu'il n'y ait pas d'invite secondaire visible.
Pour insérer un signe de pourcentage dans votre invite, écrivez %%. Les invites par défaut sont '%/%R%x%# ' pour les invites 1 et 2, et '>> ' pour l'invite 3.

Note

Cette fonctionnalité a été éhontément plagiée de tcsh.

Édition en ligne de commande

psql utilise la bibliothèque Readline ou libedit, si disponible, pour une édition et une récupération de ligne pratiques. L'historique des commandes est automatiquement sauvegardé à la sortie de psql et rechargé au démarrage de psql. Tapez la flèche vers le haut ou Ctrl-P pour récupérer les lignes précédentes.

Vous pouvez également utiliser la complétion par tabulation pour remplir les mots-clés partiellement tapés et les noms d'objets SQL dans de nombreux contextes (loin de tous). Par exemple, au début d'une commande, taper ins et appuyer sur TAB remplira insert into. Ensuite, taper quelques caractères d'un nom de table ou de schéma et appuyer sur TAB remplira le nom inachevé, ou offrira un menu de complétions possibles lorsqu'il y en a plus d'une. (Selon la bibliothèque utilisée, vous devrez peut-être appuyer sur TAB plusieurs fois pour obtenir un menu.)

La complétion par tabulation pour les noms d'objets SQL nécessite l'envoi de requêtes au serveur pour trouver les correspondances possibles. Dans certains contextes, cela peut interférer avec d'autres opérations. Par exemple, après BEGIN, il sera trop tard pour émettre SET TRANSACTION ISOLATION LEVEL si une requête de complétion par tabulation est émise entre-temps. Si vous ne souhaitez pas du tout de complétion par tabulation, vous pouvez la désactiver de manière permanente en plaçant ceci dans un fichier nommé .inputrc dans votre répertoire personnel :

$if psql
set disable-completion on
$endif

(Ce n'est pas une fonctionnalité de psql mais de Readline. Consultez sa documentation pour plus de détails.)

L'option de ligne de commande -n (--no-readline) peut également être utile pour désactiver l'utilisation de Readline pour une seule exécution de psql. Cela empêche la complétion par tabulation, l'utilisation ou l'enregistrement de l'historique des lignes de commande, et l'édition des commandes multi-lignes. C'est particulièrement utile lorsque vous devez copier-coller du texte contenant des caractères TAB.

FICHIERS

psqlrc et ~/.psqlrc

Sauf si l'option -X est passée, psql tente de lire et d'exécuter les commandes du fichier de démarrage système (psqlrc) puis du fichier de démarrage personnel de l'utilisateur (~/.psqlrc), après s'être connecté à la base de données mais avant d'accepter les commandes normales. Ces fichiers peuvent être utilisés pour configurer le client et/ou le serveur selon vos goûts, généralement avec les commandes \set et SET.

Le fichier de démarrage système s'appelle psqlrc. Par défaut, il est recherché dans le répertoire de « configuration système » de l'installation, qui est identifié de manière plus fiable en exécutant pg_config --sysconfdir. Généralement, ce répertoire sera ../etc/ par rapport au répertoire contenant les exécutables PostgreSQL. Le répertoire à rechercher peut être défini explicitement via la variable d'environnement PGSYSCONFDIR.

Le fichier de démarrage personnel de l'utilisateur s'appelle .psqlrc et est recherché dans le répertoire personnel de l'utilisateur appelant. Sous Windows, le fichier de démarrage personnel s'appelle à la place %APPDATA%\postgresql\psqlrc.conf. Dans les deux cas, ce chemin de fichier par défaut peut être remplacé en définissant la variable d'environnement PSQLRC.

Le fichier de démarrage système et le fichier de démarrage personnel de l'utilisateur peuvent être rendus spécifiques à la version de psql en ajoutant un tiret et l'identifiant de la version majeure ou mineure de PostgreSQL au nom du fichier, par exemple ~/.psqlrc-18 ou ~/.psqlrc-18.1. Le fichier correspondant le plus spécifiquement à la version sera lu de préférence à un fichier non spécifique à la version. Ces suffixes de version sont ajoutés après avoir déterminé le chemin du fichier comme expliqué ci-dessus.

.psql_history

L'historique des commandes est stocké dans le fichier ~/.psql_history, ou %APPDATA%\postgresql\psql_history sous Windows.

L'emplacement du fichier d'historique peut être défini explicitement via la variable psql HISTFILE ou la variable d'environnement PSQL_HISTORY.

NOTES

•psql fonctionne mieux avec les serveurs de la même version majeure ou d'une version antérieure. Les commandes backslash sont particulièrement susceptibles d'échouer si le serveur est d'une version plus récente que psql lui-même. Cependant, les commandes backslash de la famille \d devraient fonctionner avec les serveurs de versions antérieures à 9.2, bien que pas nécessairement avec les serveurs plus récents que psql lui-même. La fonctionnalité générale d'exécution de commandes SQL et d'affichage des résultats de requêtes devrait également fonctionner avec les serveurs d'une version majeure plus récente, mais cela ne peut être garanti dans tous les cas.

Si vous souhaitez utiliser psql pour vous connecter à plusieurs serveurs de différentes versions majeures, il est recommandé d'utiliser la version la plus récente de psql. Alternativement, vous pouvez conserver une copie de psql de chaque version majeure et vous assurer d'utiliser la version correspondant au serveur respectif. Mais en pratique, cette complication supplémentaire ne devrait pas être nécessaire.

•Avant PostgreSQL 9.6, l'option -c impliquait -X (--no-psqlrc) ; ce n'est plus le cas.
•Avant PostgreSQL 8.4, psql permettait au premier argument d'une commande backslash d'une seule lettre de commencer directement après la commande, sans espace blanc intermédiaire. Désormais, un certain espace blanc est requis.

NOTES POUR LES UTILISATEURS WINDOWS

psql est construit comme une « application console ». Étant donné que les fenêtres de console Windows utilisent un encodage différent de celui du reste du système, vous devez faire preuve d'une attention particulière lorsque vous utilisez des caractères 8 bits dans psql. Si psql détecte une page de code console problématique, il vous avertira au démarrage. Pour modifier la page de code de la console, deux choses sont nécessaires :

•Définissez la page de code en entrant cmd.exe /c chcp 1252. (1252 est une page de code appropriée pour l'allemand ; remplacez-la par votre valeur.) Si vous utilisez Cygwin, vous pouvez mettre cette commande dans /etc/profile.
•Définissez la police de la console sur Lucida Console, car la police raster ne fonctionne pas avec la page de code ANSI.

NAME¶

DESCRIPTION¶

psql is the interactive terminal application for PostgreSQL. It allows you to interactively issue commands to a PostgreSQL server, view the results, and perform database administration tasks. It can also be used as a scripting tool.
