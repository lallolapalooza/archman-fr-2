GUIDE UTILISATEUR

Démarrage rapide

Flask-SQLAlchemy simplifie l'utilisation de SQLAlchemy en gérant automatiquement la création, l'utilisation et le nettoyage des objets SQLAlchemy avec lesquels vous travailleriez normalement. Bien qu'elle ajoute quelques fonctionnalités utiles, elle fonctionne toujours comme SQLAlchemy.

Cette page vous guidera à travers l'utilisation de base de Flask-SQLAlchemy. Pour les capacités complètes et la personnalisation, consultez le reste de cette documentation, y compris la documentation de l'API de l'objet SQLAlchemy.

Consulter la documentation SQLAlchemy

Ce guide suppose que vous utilisez SQLAlchemy 2.x, qui dispose d'une nouvelle API pour définir des modèles et d'une meilleure prise en charge des indications de type Python et des classes de données. Si vous utilisez SQLAlchemy 1.x, consultez Démarrage rapide hérité.

Installation

$ pip install -U Flask-SQLAlchemy

Initialisation de l'extension

Créez d'abord l'objet db en utilisant le constructeur SQLAlchemy.

from flask import Flask
from flask_sqlalchemy import SQLAlchemy
from sqlalchemy.orm import DeclarativeBase
class Base(DeclarativeBase):
  pass
db = SQLAlchemy(model_class=Base)

Apprenez-en davantage sur la personnalisation de la classe de modèle de base dans Modèles et Tables.

À propos de l'objet SQLAlchemy

Une fois construit, l'objet db vous donne accès à la classe db.Model pour définir des modèles, et à db.session pour exécuter des requêtes.

L'objet SQLAlchemy prend également des arguments supplémentaires pour personnaliser les objets qu'il gère.

Configuration de l'extension

La prochaine étape consiste à connecter l'extension à votre application Flask. La seule configuration d'application Flask requise est la clé SQLALCHEMY_DATABASE_URI. Il s'agit d'une chaîne de connexion qui indique à SQLAlchemy quelle base de données connecter.

Créez votre objet d'application Flask, chargez toute configuration, puis initialisez la classe d'extension SQLAlchemy avec l'application en appelant db.init_app. Cet exemple se connecte à une base de données SQLite, qui est stockée dans le dossier d'instance de l'application.

# créer l'app
app = Flask(__name__)
# configurer la base de données SQLite, relative au dossier d'instance de l'app
app.config["SQLALCHEMY_DATABASE_URI"] = "sqlite:///project.db"
# initialiser l'app avec l'extension
db.init_app(app)

Voir Configuration pour une explication des chaînes de connexion et des autres clés de configuration utilisées.

Définir les modèles

Sous-classez db.Model pour définir une classe modèle. Le modèle générera un nom de table en convertissant le nom de classe CamelCase en snake_case.

from sqlalchemy import Integer, String
from sqlalchemy.orm import Mapped, mapped_column
class User(db.Model):
    id: Mapped[int] = mapped_column(Integer, primary_key=True)
    username: Mapped[str] = mapped_column(String, unique=True, nullable=False)
    email: Mapped[str] = mapped_column(String)

Voir Modèles et Tables pour plus d'informations sur la définition et la création de modèles et de tables.

Créer les tables

Après la définition de tous les modèles et tables, appelez SQLAlchemy.create_all() pour créer le schéma de table dans la base de données. Cela nécessite un contexte d'application. Puisque vous n'êtes pas dans une requête à ce stade, créez-en un manuellement.

with app.app_context():
    db.create_all()

Si vous définissez des modèles dans d'autres modules, vous devez les importer avant d'appeler create_all, sinon SQLAlchemy ne les connaîtra pas.

Interroger les données

Dans une vue Flask ou une commande CLI, vous pouvez utiliser db.session pour exécuter des requêtes et modifier les données du modèle.

SQLAlchemy définit automatiquement une méthode __init__ pour chaque modèle qui attribue les arguments nommés aux colonnes de la base de données correspondantes et à d'autres attributs.

db.session.add(obj) ajoute un objet à la session, prêt à être inséré. La modification des attributs d'un objet met à jour l'objet. db.session.delete(obj) supprime un objet. N'oubliez pas d'appeler db.session.commit() après avoir modifié, ajouté ou supprimé des données.

Quoi retenir

Pour la plupart, vous devriez utiliser SQLAlchemy comme d'habitude. L'instance de l'extension SQLAlchemy crée, configure et donne accès aux éléments suivants :

  • Classe de base déclarative de modèle SQLAlchemy.Model. Elle définit automatiquement le nom de la table au lieu d'avoir besoin de __tablename__.
  • SQLAlchemy.session est une session liée au contexte de l'application Flask actuelle. Elle est nettoyée après chaque requête.
  • SQLAlchemy.metadata et SQLAlchemy.metadatas donnent accès à chaque métadonnée définie dans la configuration.
  • SQLAlchemy.engine et SQLAlchemy.engines donnent accès à chaque moteur défini dans la configuration.
  • SQLAlchemy.create_all() crée toutes les tables.
  • Vous devez être dans un contexte d'application Flask actif pour exécuter des requêtes et accéder à la session et au moteur.

Configuration

Clés de configuration

La configuration est chargée depuis app.config de Flask lors de l'appel de SQLAlchemy.init_app(). La configuration n'est pas relue après cela. Par conséquent, toute configuration doit être effectuée avant d'initialiser l'application.

flask_sqlalchemy.config.SQLALCHEMY_DATABASE_URI
L'URI de connexion à la base de données utilisée pour le moteur par défaut. Il peut s'agir d'une chaîne de caractères ou d'une instance URL de SQLAlchemy. Voir ci-dessous et Configuration du moteur pour des exemples.

Au moins l'un de cet élément et de SQLALCHEMY_BINDS doit être défini.

Modifié dans la version 3.0 : Ne utilise plus par défaut une base de données SQLite en mémoire si non défini.

flask_sqlalchemy.config.SQLALCHEMY_ENGINE_OPTIONS
Un dictionnaire d'arguments à passer à sqlalchemy.create_engine() pour le moteur par défaut.

Cela prend la priorité sur l'argument engine_options de SQLAlchemy, qui peut être utilisé pour définir des options par défaut pour tous les moteurs.

Modifié dans la version 3.0 : Ne s'applique qu'au bind par défaut.

Ajouté dans la version 2.4.

flask_sqlalchemy.config.SQLALCHEMY_BINDS
Un dictionnaire mappant les clés de bind aux options du moteur. La valeur peut être une chaîne de caractères ou une instance URL de SQLAlchemy. Ou cela peut être un dictionnaire d'arguments, incluant la clé url, qui sera passé à sqlalchemy.create_engine(). La clé None peut être utilisée pour configurer le bind par défaut, mais SQLALCHEMY_ENGINE_OPTIONS et SQLALCHEMY_DATABASE_URI ont la priorité.

Au moins l'un de cet élément et de SQLALCHEMY_DATABASE_URI doit être défini.

Ajouté dans la version 0.12.

flask_sqlalchemy.config.SQLALCHEMY_ECHO
La valeur par défaut pour echo et echo_pool pour chaque moteur. Ceci est utile pour déboguer rapidement les connexions et les requêtes émises par SQLAlchemy.

Modifié dans la version 3.0 : Définit echo_pool en plus de echo.

flask_sqlalchemy.config.SQLALCHEMY_RECORD_QUERIES
Si activé, les informations sur chaque requête pendant une requête seront enregistrées. Utilisez get_recorded_queries() pour obtenir une liste des requêtes qui ont été émises pendant la requête.

Modifié dans la version 3.0 : Non activé automatiquement en mode débogage ou test.

flask_sqlalchemy.config.SQLALCHEMY_TRACK_MODIFICATIONS
Si activé, toutes les opérations insert, update et delete sur les modèles sont enregistrées, puis envoyées dans les signaux models_committed et before_models_committed lors de l'appel de session.commit().

Modifié dans la version 3.0 : Désactivé par défaut.

Ajouté dans la version 2.0.

Modifié dans la version 3.1 : Suppression de SQLALCHEMY_COMMIT_ON_TEARDOWN.

Modifié dans la version 3.0 : Suppression de SQLALCHEMY_NATIVE_UNICODE, SQLALCHEMY_POOL_SIZE, SQLALCHEMY_POOL_TIMEOUT, SQLALCHEMY_POOL_RECYCLE et SQLALCHEMY_MAX_OVERFLOW.

Options du pilote par défaut

Certaines options par défaut sont définies pour les moteurs SQLite et MySQL pour les rendre plus utilisables par défaut dans les applications web.

Les chemins de fichiers relatifs SQLite sont relatifs au chemin d'instance de Flask au lieu du répertoire de travail actuel. Les bases de données en mémoire utilisent un pool statique et check_same_thread pour fonctionner entre les requêtes.

Les serveurs MySQL (et MariaDB) sont configurés pour fermer les connexions inactives pendant 8 heures, ce qui peut entraîner une erreur comme 2013 : Connexion perdue au serveur MySQL pendant la requête. Une valeur par défaut de pool_recycle de 2 heures (7200 secondes) est utilisée pour recréer les connexions avant ce délai d'expiration.

Priorité de la configuration du moteur

Comme Flask-SQLAlchemy prend en charge plusieurs moteurs, il existe des règles pour savoir quelle configuration remplace une autre. La plupart des applications n'auront qu'une seule base de données et n'auront besoin d'utiliser que SQLALCHEMY_DATABASE_URI et SQLALCHEMY_ENGINE_OPTIONS.

  • Si l'argument engine_options est donné à SQLAlchemy, il définit les options par défaut pour tous les moteurs. SQLALCHEMY_ECHO définit la valeur par défaut pour echo et echo_pool pour tous les moteurs.
  • Les options pour chaque moteur dans SQLALCHEMY_BINDS remplacent ces valeurs par défaut.
  • SQLALCHEMY_ENGINE_OPTIONS remplace la clé None dans SQLALCHEMY_BINDS, et SQLALCHEMY_DATABASE_URI remplace la clé url dans les options de ce moteur.

Délais d'expiration

Certaines bases de données peuvent être configurées pour fermer les connexions inactives après un certain temps. MySQL et MariaDB sont configurés pour cela par défaut, mais les services de base de données peuvent également configurer ce type de limite. Cela peut entraîner une erreur telle que 2013 : Connexion perdue au serveur MySQL pendant la requête.

Si vous rencontrez cette erreur, essayez de définir pool_recycle dans les options du moteur à une valeur inférieure au délai d'expiration de la base de données.

Alternativement, vous pouvez essayer de définir pool_pre_ping si vous vous attendez à ce que la base de données ferme souvent les connexions, par exemple si elle fonctionne dans un conteneur qui peut redémarrer.

Modèles et tables

Utilisez la classe db.Model pour définir des modèles, ou la classe db.Table pour créer des tables. Les deux gèrent les clés de bind de Flask-SQLAlchemy pour s'associer à un moteur spécifique.

SQLAlchemy

This documentation assumes you are using SQLAlchemy 2.0 or later.

Initialisation de la classe de base

Créez une sous-classe de l'une de ces classes :

from sqlalchemy import MetaData
class Base(DeclarativeBase):
    metadata = MetaData(naming_convention={
        "ix": 'ix_%(column_0_label)s',
        "uq": "uq_%(table_name)s_%(column_0_name)s",
        "ck": "ck_%(table_name)s_%(constraint_name)s",
        "fk": "fk_%(table_name)s_%(column_0_name)s_%(referred_table_name)s",
        "pk": "pk_%(table_name)s"
    })

Initialiser l'extension

Une fois que vous avez défini une classe de base, créez l'objet db en utilisant le constructeur SQLAlchemy.

Créez une sous-classe de db.Model pour créer une classe de modèle. Contrairement à SQLAlchemy simple, le modèle de Flask-SQLAlchemy générera automatiquement un nom de table si __tablename__ n'est pas défini et qu'une colonne de clé primaire est définie.

from sqlalchemy.orm import Mapped, mapped_column
class User(db.Model):
    id: Mapped[int] = mapped_column(db.Integer, primary_key=True)
    username: Mapped[str] = mapped_column(db.String, unique=True, nullable=False)
    email: Mapped[str] = mapped_column(db.String)

La définition d'un modèle ne le crée pas dans la base de données. Utilisez create_all() pour créer les modèles et les tables après les avoir définis. Si vous définissez des modèles dans des sous-modules, vous devez les importer afin que SQLAlchemy les connaisse avant d'appeler create_all.

Créez des instances de db.Table pour définir des tables. La classe prend un nom de table, puis toutes les colonnes et autres parties de table comme les colonnes et les contraintes. Contrairement à SQLAlchemy simple, l'argument metadata n'est pas requis. Un metadata sera choisi en fonction de l'argument bind_key, ou la valeur par défaut sera utilisée.

Une raison courante de créer une table directement est de définir des relations plusieurs à plusieurs. La table d'association n'a pas besoin de sa propre classe de modèle, car elle sera accessible via les attributs de relation pertinents sur les modèles associés.

import sqlalchemy as sa
user_book_m2m = db.Table(
    "user_book",
    sa.Column("user_id", sa.ForeignKey(User.id), primary_key=True),
    sa.Column("book_id", sa.ForeignKey(Book.id), primary_key=True),
)

Réfléchir les tables

Si vous vous connectez à une base de données qui possède déjà des tables, SQLAlchemy peut détecter ce schéma et créer des tables avec des colonnes automatiquement. C'est ce qu'on appelle la réflexion. Ces tables peuvent également être assignées à des classes de modèles avec l'attribut __table__ au lieu de définir le modèle complet.

Appelez la méthode reflect() sur l'extension. Elle reflétera toutes les tables pour chaque clé de liaison. L'attribut tables de chaque metadata contiendra les objets de table détectés.

with app.app_context():
    db.reflect()
class User:
    __table__ = db.metadatas["auth"].tables["user"]

Dans la plupart des cas, il sera plus facile à maintenir de définir vous-même les classes de modèles. Vous n'avez besoin de définir que les modèles et les colonnes que vous utiliserez réellement, même si vous vous connectez à un schéma plus large. Les IDE connaîtront les attributs disponibles, et les outils de migration comme Alembic pourront détecter les changements et générer des migrations de schéma.

Modifier et interroger les données

Insertion, mise à jour, suppression

Pour insérer des données, passez l'objet modèle à db.session.add() :

user = User()
db.session.add(user)
db.session.commit()

Pour mettre à jour des données, modifiez les attributs des objets modèles :

user.verified = True
db.session.commit()

Pour supprimer des données, passez l'objet modèle à db.session.delete() :

db.session.delete(user)
db.session.commit()

Après avoir modifié les données, vous devez appeler db.session.commit() pour valider les modifications dans la base de données. Sinon, elles seront supprimées à la fin de la requête.

Requêtes pour les vues

Si vous écrivez une fonction de vue Flask, il est souvent utile de renvoyer une erreur 404 Not Found pour les entrées manquantes. Flask-SQLAlchemy fournit des méthodes de requête supplémentaires.

  • SQLAlchemy.get_or_404() lèvera une 404 si la ligne avec l'ID donné n'existe pas, sinon elle renverra l'instance.
  • SQLAlchemy.first_or_404() lèvera une 404 si la requête ne renvoie aucun résultat, sinon elle renverra le premier résultat.
  • SQLAlchemy.one_or_404() lèvera une 404 si la requête ne renvoie pas exactement un résultat, sinon elle renverra le résultat.
@app.route("/user-by-id/<int:id>")
def user_by_id(id):
    user = db.get_or_404(User, id)
    return render_template("show_user.html", user=user)
@app.route("/user-by-username/<username>")
def user_by_username(username):
    user = db.one_or_404(db.select(User).filter_by(username=username))
    return render_template("show_user.html", user=user)

Vous pouvez ajouter un message personnalisé à l'erreur 404 :

user = db.one_or_404(
    db.select(User).filter_by(username=username),
    description=f"Aucun utilisateur nommé '{username}'."
)

Si vous avez beaucoup de résultats, vous voudrez peut-être n'en afficher qu'un certain nombre à la fois, permettant à l'utilisateur de cliquer sur les liens suivant et précédent pour voir des pages de données. C'est parfois appelé pagination, et utilise le verbe paginate.

Widget de sélection de page

L'objet Pagination possède des attributs qui peuvent être utilisés pour créer un widget de sélection de page en parcourant les numéros de page et en vérifiant la page actuelle. iter_pages() produira jusqu'à trois groupes de nombres, séparés par None. Par défaut, il affiche 2 numéros de page à chaque extrémité, 2 numéros avant l'actuel, l'actuel, et 4 numéros après l'actuel. Par exemple, s'il y a 20 pages et que la page actuelle est la 7, les valeurs suivantes sont produites.

users.iter_pages()
[1, 2, None, 5, 6, 7, 8, 9, 10, 11, None, 19, 20]

Vous pouvez utiliser l'attribut total pour afficher le nombre total de résultats, et first et last pour afficher la plage d'éléments de la page actuelle.

Contexte d'application Flask

Un contexte d'application Flask actif est requis pour effectuer des requêtes et pour accéder à db.engine et db.session. En effet, la session est limitée au contexte afin qu'elle soit correctement nettoyée après chaque requête ou commande CLI.

Quelle que soit la manière dont une application est initialisée avec l'extension, elle n'est pas stockée pour une utilisation ultérieure. Au lieu de cela, l'extension utilise le proxy current_app de Flask pour obtenir l'application active, ce qui nécessite un contexte d'application actif.

Contexte automatique

Lorsque Flask traite une requête ou une commande CLI, un contexte d'application est automatiquement poussé. Par conséquent, vous n'avez rien de spécial à faire pour utiliser la base de données pendant les requêtes ou les commandes CLI.

Contexte manuel

Si vous essayez d'utiliser la base de données lorsqu'un contexte d'application n'est pas actif, vous verrez l'erreur suivante.

RuntimeError: Working outside of application context.
This typically means that you attempted to use functionality that needed
the current application. To solve this, set up an application context
with app.app_context(). See the documentation for more information.

Si vous vous trouvez dans une situation où vous avez besoin de la base de données et que vous n'avez pas de contexte, vous pouvez en pousser un avec app_context. C'est courant lorsque vous appelez db.create_all pour créer les tables, par exemple.

def create_app():
    app = Flask(__name__)
    app.config.from_object("project.config")
    import project.models
    with app.app_context():
        db.create_all()
    return app

Tests

Si vous testez votre application en utilisant le client de test Flask pour effectuer des requêtes vers vos points de terminaison, le contexte sera disponible dans le cadre de la requête. Si vous avez besoin de tester directement quelque chose concernant votre base de données ou vos modèles, plutôt que de passer par une requête, vous devez pousser manuellement un contexte.

Ne poussez un contexte que précisément où et pour la durée nécessaire à chaque test. Ne poussez pas un contexte globalement pour tous les tests, car cela pourrait interférer avec la manière dont la session est nettoyée.

def test_user_model(app):
    user = User()
    with app.app_context():
        db.session.add(user)
        db.session.commit()

Si vous vous retrouvez à écrire de nombreux tests comme celui-ci, vous pouvez utiliser une fixture pytest pour pousser un contexte pour un test spécifique.

import pytest
@pytest.fixture
def app_ctx(app):
    with app.app_context():
        yield
@pytest.mark.usefixtures("app_ctx")
def test_user_model():
    user = User()
    db.session.add(user)
    db.session.commit()

Bases de données multiples avec liaisons

SQLAlchemy peut se connecter à plusieurs bases de données simultanément. Il désigne différents moteurs comme des « liaisons » (binds). Flask-SQLAlchemy simplifie le fonctionnement des liaisons en associant chaque moteur à une courte chaîne de caractères, une « clé de liaison », puis en associant chaque modèle et table à une clé de liaison. La session choisira le moteur à utiliser pour une requête en fonction de la clé de liaison de l'élément interrogé. Si aucune clé de liaison n'est donnée, le moteur par défaut est utilisé.

Configuration des liaisons

La liaison par défaut est toujours configurée en définissant SQLALCHEMY_DATABASE_URI, et SQLALCHEMY_ENGINE_OPTIONS pour toute option de moteur. Des liaisons supplémentaires sont fournies dans SQLALCHEMY_BINDS, un dictionnaire mappant les clés de liaison aux URL de moteur. Pour spécifier des options de moteur pour une liaison, la valeur peut être un dictionnaire d'options de moteur avec la clé « url », au lieu d'une simple chaîne d'URL.

SQLALCHEMY_DATABASE_URI = "postgresql:///main"
SQLALCHEMY_BINDS = {
    "meta": "sqlite:////path/to/meta.db",
    "auth": {
        "url": "mysql://localhost/users",
        "pool_recycle": 3600,
    },
}

Définition des modèles et des tables avec des liaisons

Flask-SQLAlchemy créera des métadonnées et un moteur pour chaque liaison configurée. Les modèles et les tables ayant une clé de liaison seront enregistrés avec les métadonnées correspondantes, et la session les interrogera en utilisant le moteur correspondant.

Pour définir la liaison d'un modèle, définissez l'attribut de classe __bind_key__. Ne pas définir de clé de liaison équivaut à la définir sur None, la clé par défaut.

class User(db.Model):
    __bind_key__ = "auth"
    id = db.Column(db.Integer, primary_key=True)

Les modèles qui héritent de ce modèle partageront la même clé de liaison, ou pourront la remplacer.

Pour définir la liaison d'une table, passez l'argument de mot-clé bind_key.

user_table = db.Table(
    "user",
    db.Column("id", db.Integer, primary_key=True),
    bind_key="auth",
)

En fin de compte, la session recherche la clé de liaison dans les métadonnées associées au modèle ou à la table. Cette association se produit lors de la création. Par conséquent, changer la clé de liaison après la création d'un modèle ou d'une table n'aura aucun effet.

Accès aux métadonnées et aux moteurs

Vous pourriez avoir besoin d'inspecter les métadonnées ou le moteur d'une liaison. Notez que vous devez exécuter les requêtes via la session, et non directement sur le moteur.

Le moteur par défaut est SQLAlchemy.engine, et les métadonnées par défaut sont SQLAlchemy.metadata. SQLAlchemy.engines et SQLAlchemy.metadatas sont des dictionnaires mappant toutes les clés de liaison.

Création et suppression de tables

Les méthodes create_all() et drop_all() opèrent sur toutes les liaisons par défaut. L'argument bind_key de ces méthodes peut être une chaîne ou None pour opérer sur une seule liaison, ou une liste de chaînes ou None pour opérer sur un sous-ensemble de liaisons. Comme ces méthodes accèdent aux moteurs, elles doivent être appelées à l'intérieur d'un contexte d'application.

# créer les tables pour toutes les liaisons
db.create_all()
# créer les tables pour les liaisons par défaut et "auth"
db.create_all(bind_key=[None, "auth"])
# créer les tables pour la liaison "meta"
db.create_all(bind_key="meta")
# supprimer les tables pour la liaison par défaut
db.drop_all(bind_key=None)

Enregistrement des informations de requête

AVERTISSEMENT :

Cette fonctionnalité est destinée uniquement au débogage.

Flask-SQLAlchemy peut enregistrer certaines informations sur chaque requête exécutée pendant une requête. Ces informations peuvent ensuite être récupérées pour faciliter le débogage des performances. Par exemple, cela peut révéler qu'une relation a effectué trop de sélections individuelles, ou révéler une requête qui a pris beaucoup de temps.

Pour activer cette fonctionnalité, définissez SQLALCHEMY_RECORD_QUERIES sur True dans la configuration de l'application Flask. Utilisez get_recorded_queries() pour obtenir une liste d'objets d'informations de requête. Chaque objet possède les attributs suivants :

La chaîne SQL générée par SQLAlchemy avec des espaces réservés pour les paramètres.

Informations de chronométrage sur
lorsque la requête a commencé son exécution et lorsque les résultats ont été retournés. La précision et la valeur dépendent du système d'exploitation.

Le temps que la requête a pris en secondes.

Suivi des Modifications

ATTENTION :

Le suivi des modifications ajoute une surcharge significative. Dans la plupart des cas, vous obtiendrez de meilleurs résultats en utilisant directement les événements SQLAlchemy.

Flask-SQLAlchemy peut configurer sa session pour suivre les insertions, mises à jour et suppressions de modèles, puis envoyer un signal Blinker avec une liste de ces modifications soit avant, soit pendant les appels à session.flush() et session.commit().

Pour activer cette fonctionnalité, définissez SQLALCHEMY_TRACK_MODIFICATIONS dans la configuration de l'application Flask. Ensuite, ajoutez un écouteur à models_committed (émis après le commit) ou before_models_committed (émis avant le commit).

from flask_sqlalchemy.track_modifications import models_committed
def get_modifications(sender: Flask, changes: list[tuple[t.Any, str]]) -> None:
    ...
models_committed.connect(get_modifications)

Personnalisation Avancée

Les différents objets gérés par l'extension peuvent être personnalisés en passant des arguments au constructeur SQLAlchemy.

Classe de Modèle

Tous les modèles SQLAlchemy héritent d'une classe de base déclarative. Celle-ci est exposée comme db.Model dans Flask-SQLAlchemy, dont tous les modèles héritent. Elle peut être personnalisée en héritant de la classe par défaut et en passant la classe personnalisée à model_class.

L'exemple suivant donne à chaque modèle une clé primaire entière, ou une clé étrangère pour l'héritage de table joint.

NOTE :

Les clés primaires entières pour tout ne constituent pas nécessairement la meilleure conception de base de données (cela dépend des exigences de votre projet), il ne s'agit que d'un exemple.
from sqlalchemy import Integer, String, ForeignKey
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column, declared_attr
class Base(DeclarativeBase):
    @declared_attr.cascading
    @classmethod
    def id(cls):
        for base in cls.__mro__[1:-1]:
            if getattr(base, "__table__", None) is not None:
                    return mapped_column(ForeignKey(base.id), primary_key=True)
            else:
                return mapped_column(Integer, primary_key=True)
db = SQLAlchemy(app, model_class=Base)
class User(db.Model):
    name: Mapped[str] = mapped_column(String)
class Employee(User):
    title: Mapped[str] = mapped_column(String)

Modèles Abstraits et Mixins

Si un comportement n'est nécessaire que pour certains modèles et non pour tous, utilisez une classe de base de modèle abstraite pour personnaliser uniquement ces modèles. Par exemple, si certains modèles doivent suivre leur création ou leur mise à jour.

from datetime import datetime
from sqlalchemy import DateTime, Integer, String
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column, declared_attr
class TimestampModel(db.Model):
    __abstract__ = True
    created: Mapped[datetime] = mapped_column(DateTime, nullable=False, default=datetime.utcnow)
    updated: Mapped[datetime] = mapped_column(DateTime, default=datetime.utcnow, onupdate=datetime.utcnow)
class Author(db.Model):
    id: Mapped[int] = mapped_column(Integer, primary_key=True)
    username: Mapped[str] = mapped_column(String, unique=True, nullable=False)
class Post(TimestampModel):
    id: Mapped[int] = mapped_column(Integer, primary_key=True)
    title: Mapped[str] = mapped_column(String, nullable=False)

Cela peut également être fait avec une classe mixin, héritant séparément de db.Model.

class TimestampMixin:
    created: Mapped[datetime] = mapped_column(DateTime, nullable=False, default=datetime.utcnow)
    updated: Mapped[datetime] = mapped_column(DateTime, default=datetime.utcnow, onupdate=datetime.utcnow)
class Post(TimestampMixin, db.Model):
    id: Mapped[int] = mapped_column(Integer, primary_key=True)
    title: Mapped[str] = mapped_column(String, nullable=False)

Désactivation de la Génération des Noms de Table

Certains projets préfèrent définir manuellement __tablename__ pour chaque modèle plutôt que de s'appuyer sur la détection et la génération de Flask-SQLAlchemy. La manière simple d'y parvenir est de définir chaque __tablename__ et de ne pas modifier la classe de base. Cependant, la génération des noms de table peut être désactivée en définissant disable_autonaming=True dans le constructeur SQLAlchemy.

class Base(sa_orm.DeclarativeBase):
    pass
db = SQLAlchemy(app, model_class=Base, disable_autonaming=True)

Classe de Session

La classe Session de Flask-SQLAlchemy choisit le moteur à interroger en fonction de la clé de liaison associée au modèle ou à la table. Cependant, il existe d'autres stratégies, telles que le partitionnement horizontal, qui peuvent être implémentées avec une classe de session différente. La clé class_ de l'argument session_options de l'extension permet de modifier la classe de session.

Flask-SQLAlchemy passera toujours l'instance d'extension comme argument db à la session, elle doit donc l'accepter pour continuer à fonctionner. Cela peut être utilisé pour accéder à db.engines.

from sqlalchemy.ext.horizontal_shard import ShardedSession
from flask_sqlalchemy.session import Session
class CustomSession(ShardedSession, Session):
    ...
db = SQLAlchemy(session_options={"class_": CustomSession})

Classe de Requête

ATTENTION :

L'interface de requête est considérée comme obsolète dans SQLAlchemy. Cela inclut session.query, Model.query, db.Query et les relations lazy="dynamic". Préférez plutôt utiliser session.execute(select(...)).

Il est possible de personnaliser l'interface de requête utilisée par la session, les modèles et les relations. Cela peut être utilisé pour ajouter des méthodes de requête supplémentaires. Par exemple, vous pourriez ajouter une méthode get_or qui récupère une ligne ou retourne une valeur par défaut.

from flask_sqlalchemy.query import Query
class GetOrQuery(Query):
    def get_or(self, ident, default=None):
        out = self.get(ident)
        if out is None:
            return default
        return out
db = SQLAlchemy(query_class=GetOrQuery)
user = User.query.get_or(user_id, anonymous_user)

Le passage de l'argument query_class personnalisera db.Query, db.session.query, Model.query et les relations db.relationship(lazy="dynamic"). Il est également possible de personnaliser ces éléments par objet.

Pour personnaliser la propriété query d'un modèle spécifique, définissez l'attribut query_class sur la classe du modèle.

class User(db.Model):
    query_class = GetOrQuery

Pour personnaliser une relation dynamique spécifique, passez l'argument query_class à la relation.

db.relationship(User, lazy="dynamic", query_class=GetOrQuery)

Pour personnaliser uniquement session.query, passez la clé query_cls à l'argument session_options du constructeur.

db = SQLAlchemy(session_options={"query_cls": GetOrQuery})

Track Modifications

flask_sqlalchemy.track_modifications.models_committed
This Blinker signal is sent after the session is committed if there were changed models in the session.

The sender is the application that emitted the changes. The receiver is passed the changes argument with a list of tuples in the form (instance, operation). The operations are "insert", "update", and "delete".
