NAME

python-engineio - Documentation de python-engineio

Ce projet implémente des clients et serveurs Engine.IO basés sur Python qui peuvent fonctionner de manière autonome ou être intégrés à une variété de frameworks web et d'applications Python.

POUR COMMENCER

Qu'est-ce que Engine.IO ?

Engine.IO est un protocole de transport léger qui permet une communication bidirectionnelle en temps réel basée sur des événements entre des clients (typiquement, mais pas toujours, des navigateurs web) et un serveur. Les implémentations officielles des composants client et serveur sont écrites en JavaScript. Ce paquet fournit des implémentations Python des deux, chacune avec des variantes standard et pour asyncio.

Le protocole Engine.IO est extrêmement simple. Une fois qu'une connexion est établie entre un client et un serveur, l'un ou l'autre peut envoyer des « messages » à l'autre. Les gestionnaires d'événements fournis par les applications des deux côtés sont appelés lorsqu'un message est reçu, ou lorsqu'une connexion est établie ou interrompue.

Exemples de clients

L'exemple suivant montre un client Python simple :

import engineio
eio = engineio.Client()
@eio.on('connect')
def on_connect():
    print('connection established')
@eio.on('message')
def on_message(data):
    print('message received with ', data)
    eio.send({'response': 'my response'})
@eio.on('disconnect')
def on_disconnect():
    print('disconnected from server')
eio.connect('http://localhost:5000')
eio.wait()

Et voici un client similaire écrit en utilisant le client Engine.IO Javascript officiel :

<script src="/path/to/engine.io.js"></script>
<script>
    var socket = eio('http://localhost:5000');
    socket.on('open', function() { console.log('connection established'); });
    socket.on('message', function(data) {
        console.log('message received with ' + data);
        socket.send({response: 'my response'});
    });
    socket.on('close', function() { console.log('disconnected from server'); });
</script>

Fonctionnalités du client

  • Peut se connecter à d'autres serveurs compatibles Engine.IO autres que celui de ce paquet.
  • Compatible avec Python 3.6+.
  • Deux versions du client, une pour Python standard et une autre pour asyncio.
  • Utilise une architecture basée sur des événements implémentée avec des décorateurs qui masquent les détails du protocole.
  • Implémente les transports HTTP long-polling et WebSocket.

Exemples de serveur

L'application suivante est un exemple de base qui utilise le serveur asynchrone Eventlet :

import engineio
import eventlet
eio = engineio.Server()
app = engineio.WSGIApp(eio, static_files={
    '/': {'content_type': 'text/html', 'filename': 'index.html'}
})
@eio.on('connect')
def connect(sid, environ):
    print("connect ", sid)
@eio.on('message')
def message(sid, data):
    print("message ", data)
    eio.send(sid, 'reply')
@eio.on('disconnect')
def disconnect(sid):
    print('disconnect ', sid)
if __name__ == '__main__':
    eventlet.wsgi.server(eventlet.listen(('', 5000)), app)

Ci-dessous se trouve une application similaire, codée pour asyncio et le serveur web Uvicorn :

  • La classe engineio.Client() crée un client compatible avec la bibliothèque Python standard.
  • La classe engineio.AsyncClient() crée un client compatible avec le paquet asyncio.

Les méthodes des deux clients sont identiques, la seule différence étant que dans le client asyncio, la plupart des méthodes sont implémentées en tant que coroutines.

Installation

Pour installer le client Python standard avec ses dépendances, utilisez la commande suivante :

pip install "python-engineio[client]"

Si vous prévoyez plutôt d'utiliser le client asyncio, utilisez celui-ci :

pip install "python-engineio[asyncio_client]"

Création d'une instance de client

Pour instancier un client Engine.IO, créez simplement une instance de la classe de client appropriée :

import engineio
# Python standard
eio = engineio.Client()
# asyncio
eio = engineio.AsyncClient()

Définition des gestionnaires d'événements

Pour répondre aux événements déclenchés par la connexion ou le serveur, des fonctions de gestionnaire d'événements doivent être définies en utilisant le décorateur on :

@eio.on('connect')
def on_connect():
    print('I'm connected!')
@eio.on('message')
def on_message(data):
    print('I received a message!')
@eio.on('disconnect')
def on_disconnect(reason):
    print('I'm disconnected! reason:', reason)

Pour le serveur asyncio, les gestionnaires d'événements peuvent être des fonctions normales comme ci-dessus, ou peuvent également être des coroutines :

@eio.on('message')
async def on_message(data):
    print('I received a message!')

L'argument donné au décorateur on est le nom de l'événement. Les événements pris en charge sont connect, message et disconnect.

L'argument data passé au gestionnaire de l'événement 'message' contient des données spécifiques à l'application fournies par le serveur avec l'événement.

Connexion à un serveur

La connexion à un serveur est établie en appelant la méthode connect() :

eio.connect('http://localhost:5000')

Dans le cas du client asyncio, la méthode est une coroutine :

await eio.connect('http://localhost:5000')

Lors de la connexion, le serveur attribue au client un identifiant de session unique. L'application peut trouver cet identifiant dans l'attribut sid :

print('mon sid est', eio.sid)

Envoi de messages

Le client peut envoyer un message au serveur en utilisant la méthode send() :

eio.send({'foo': 'bar'})

Ou dans le cas de asyncio, sous forme de coroutine :

await eio.send({'foo': 'bar'})

L'unique argument passé à la méthode est la donnée qui est transmise au serveur. La donnée peut être de type str, bytes, dict ou list. Les données incluses dans les dictionnaires et les listes sont également limitées à ces types.

La méthode send() peut être invoquée à l'intérieur d'un gestionnaire d'événements en réponse à un événement serveur, ou dans toute autre partie de l'application, y compris dans des tâches d'arrière-plan.

Déconnexion du serveur

À tout moment, le client peut demander à être déconnecté du serveur en invoquant la méthode disconnect() :

eio.disconnect()

Pour le client asyncio, il s'agit d'une coroutine :

await eio.disconnect()

Gestion des tâches d'arrière-plan

Lorsqu'une connexion client au serveur est établie, quelques tâches d'arrière-plan sont lancées pour maintenir la connexion active et gérer les événements entrants. L'application s'exécutant dans le thread principal est libre de faire tout travail, car cela n'empêchera pas le fonctionnement du client Engine.IO.

Si l'application n'a rien à faire dans le thread principal et souhaite simplement attendre la fin de la connexion, elle peut appeler la méthode wait() :

eio.wait()

Ou dans la version asyncio :

await eio.wait()

Pour la commodité de l'application, une fonction d'aide est fournie pour démarrer une tâche d'arrière-plan personnalisée :

def my_background_task(my_argument)
    # faire du travail d'arrière-plan ici !
    pass
eio.start_background_task(my_background_task, 123)

Les arguments passés à cette méthode sont la fonction d'arrière-plan et tous les arguments positionnels ou par mot-clé pour invoquer la fonction.

Voici la version asyncio :

async def my_background_task(my_argument)
    # faire du travail d'arrière-plan ici !
    pass
eio.start_background_task(my_background_task, 123)

Notez que cette fonction n'est pas une coroutine, car elle n'attend pas la fin de la fonction d'arrière-plan, mais la fonction d'arrière-plan l'est.

La méthode sleep() est une deuxième fonction pratique fournie pour le bénéfice des applications travaillant avec leurs propres tâches d'arrière-plan :

eio.sleep(2)

Ou pour asyncio :

await eio.sleep(2)

L'unique argument passé à la méthode est le nombre de secondes pour dormir.

Débogage et dépannage

Pour vous aider à déboguer les problèmes, le client peut être configuré pour afficher des journaux dans le terminal :

import engineio
# Python standard
eio = engineio.Client(logger=True)
# asyncio
eio = engineio.AsyncClient(logger=True)

L'argument logger peut être défini sur True pour afficher les journaux dans stderr, ou sur un objet compatible avec le package logging de Python, où les journaux doivent être émis. Une valeur de False désactive la journalisation.

La journalisation peut aider à identifier la cause des problèmes de connexion, des déconnexions inattendues et d'autres problèmes.

LE SERVEUR ENGINE.IO

Ce package contient deux serveurs Engine.IO :

  • La classe engineio.Server() crée un serveur compatible avec la bibliothèque Python standard.
  • La classe engineio.AsyncServer() crée un serveur compatible avec le package asyncio.

Les méthodes des deux serveurs sont identiques, la seule différence étant que dans le serveur asyncio, la plupart des méthodes sont implémentées comme des coroutines.

Installation

Pour installer le serveur Python Engine.IO, utilisez la commande suivante :

pip install "python-engineio"

En plus du serveur, vous devrez choisir un framework ou un serveur asynchrone à utiliser avec lui. La liste des packages pris en charge est abordée dans la section Stratégies de déploiement.

Création d'une instance de serveur

Un serveur Engine.IO est une instance de la classe engineio.Server. Cette instance peut être transformée en une application WSGI standard en l'encapsulant avec la classe engineio.WSGIApp :

import engineio
# créer un serveur Engine.IO
eio = engineio.Server()
# encapsuler avec une application WSGI
app = engineio.WSGIApp(eio)

Pour les serveurs basés sur asyncio, la classe engineio.AsyncServer fournit la même fonctionnalité, mais dans un format convivial pour les coroutines. Si souhaité, la classe engineio.ASGIApp peut transformer le serveur en une application ASGI standard :

# créer un serveur Engine.IO
eio = engineio.AsyncServer()
# encapsuler avec une application ASGI
app = engineio.ASGIApp(eio)

Ces deux wrappers peuvent également agir comme des middlewares, transmettant tout trafic qui n'est pas destiné au serveur Engine.IO à une autre application. Cela permet aux serveurs Engine.IO de s'intégrer facilement dans des applications WSGI ou ASGI existantes :

from wsgi import app  # une application Flask, Django, etc.
app = engineio.WSGIApp(eio, app)

Servir des fichiers statiques

Le serveur Engine.IO peut être configuré pour servir des fichiers statiques aux clients. Ceci est particulièrement utile pour livrer des fichiers HTML, CSS et JavaScript aux clients lorsque ce package est utilisé sans framework compagnon.

Les fichiers statiques sont configurés avec un dictionnaire Python dans lequel chaque paire clé/valeur est une règle de mappage de fichier statique. Dans sa forme la plus simple, ce dictionnaire a une ou plusieurs URL de fichier statique comme clés, et les fichiers correspondants sur le serveur comme valeurs :

static_files = {
    '/': 'latency.html',
    '/static/engine.io.js': 'static/engine.io.js',
    '/static/style.css': 'static/style.css',
}

Avec cet exemple de configuration, lorsque le serveur reçoit une requête pour / (l'URL racine), il renverra le contenu du fichier latency.html dans le répertoire courant, et attribuera un type de contenu basé sur l'extension du fichier, dans ce cas text/html.

Les fichiers avec les extensions de fichier .html, .css, .js, .json, .jpg, .png, .gif et .txt sont automatiquement reconnus et se voient attribuer le type de contenu correct. Pour les fichiers avec d'autres extensions ou sans extension, le type de contenu application/octet-stream est utilisé par défaut.

Si désiré, un type de contenu explicite pour un fichier statique peut être donné comme suit :

static_files = {
    '/': {'filename': 'latency.html', 'content_type': 'text/plain'},
}

Il est également possible de configurer un répertoire entier en une seule règle, de sorte que tous les fichiers qu'il contient soient servis comme fichiers statiques :

static_files = {
    '/static': './public',
}

Dans cet exemple, tous les fichiers dont les URL commencent par /static seront servis directement depuis le dossier public dans le répertoire courant, donc par exemple, l'URL /static/index.html renverra le fichier local ./public/index.html et l'URL /static/css/styles.css renverra le fichier local ./public/css/styles.css.

Si une URL se terminant par un / est demandée, alors un nom de fichier par défaut index.html lui est ajouté. Dans l'exemple précédent, une requête pour l'URL /static/ renverrait le fichier local ./public/index.html. Le nom de fichier par défaut à servir pour les URL se terminant par une barre oblique peut être défini dans le dictionnaire des fichiers statiques avec une clé vide :

static_files = {
    '/static': './public',
    '': 'image.gif',
}

Avec cette configuration, une requête pour /static/ renverrait le fichier local ./public/image.gif. Un type de contenu non standard peut également être spécifié si nécessaire :

static_files = {
    '/static': './public',
    '': {'filename': 'image.gif', 'content_type': 'text/plain'},
}

Configuration des fichiers statiques

Le dictionnaire de configuration des fichiers statiques est passé comme argument static_files aux classes engineio.WSGIApp ou engineio.ASGIApp :

# pour les applications WSGI standard
eio = engineio.Server()
app = engineio.WSGIApp(eio, static_files=static_files)
# pour les applications ASGI basées sur asyncio
eio = engineio.AsyncServer()
app = engineio.ASGIApp(eio, static_files=static_files)

La priorité de routage dans ces deux classes est la suivante :

  • Tout d'abord, le chemin est vérifié par rapport au chemin Engine.IO.
  • Ensuite, le chemin est vérifié par rapport à la configuration des fichiers statiques, si elle est présente.
  • Si le chemin ne correspond pas au chemin Engine.IO ni à un fichier statique, le contrôle est passé à l'application secondaire si elle est configurée, sinon une erreur 404 est renvoyée.

Remarque : la diffusion de fichiers statiques est destinée à un usage de développement uniquement, et à ce titre, elle manque de fonctionnalités importantes telles que la mise en cache. Ne pas utiliser en production.

Définition des gestionnaires d'événements

Pour répondre aux événements déclenchés par la connexion ou le client, les fonctions de gestionnaire d'événements doivent être définies à l'aide du décorateur on :

@eio.on('connect')
def on_connect(sid):
    print('Un client s\'est connecté !')
@eio.on('message')
def on_message(sid, data):
    print('J\'ai reçu un message !')
@eio.on('disconnect')
def on_disconnect(sid, reason):
    print('Client déconnecté ! raison :', reason)

Pour le serveur asyncio, les gestionnaires d'événements peuvent être des fonctions normales comme ci-dessus, ou peuvent également être des coroutines :

@eio.on('message')
async def on_message(sid, data):
    print('J\'ai reçu un message !')

L'argument passé au décorateur on est le nom de l'événement. Les événements pris en charge sont connect, message et disconnect.

L'argument sid passé à tous les gestionnaires d'événements est un identifiant de connexion pour le client. Tous les événements d'un client utiliseront la même valeur sid.

Le gestionnaire connect est l'endroit où le serveur peut effectuer l'authentification. La valeur renvoyée par ce gestionnaire est utilisée pour déterminer si la connexion est acceptée ou rejetée. Lorsque le gestionnaire ne renvoie aucune valeur (ce qui est identique à renvoyer None) ou lorsqu'il renvoie True, la connexion est acceptée. Si le gestionnaire renvoie False ou un type de données compatible JSON (chaîne, entier, liste ou dictionnaire), la connexion est rejetée. Une connexion rejetée déclenche une réponse avec un code d'état 401.

L'argument data passé au gestionnaire d'événements 'message' contient des données spécifiques à l'application fournies par le client avec l'événement.

Le gestionnaire disconnect est appelé pour les déconnexions initiées par le client, les déconnexions initiées par le serveur ou les déconnexions accidentelles, par exemple en raison de pannes réseau. Le deuxième argument passé à ce gestionnaire fournit la raison de la déconnexion. Exemple :

@eio.on('disconnect')
def on_disconnect(sid, reason):
    if reason == eio.reason.CLIENT_DISCONNECT:
        print('le client est parti')
    elif reason == eio.reason.SERVER_DISCONNECT:
        print('le client a été expulsé')
    else:
        print(f'raison de la déconnexion : {reason}')

Envoi de messages

Le serveur peut envoyer un message à n'importe quel client à l'aide de la méthode send() :

eio.send(sid, {'foo': 'bar'})

Ou dans le cas d'asyncio, sous forme de coroutine :

await eio.send(sid, {'foo': 'bar'})

Le premier argument passé à la méthode est l'identifiant de connexion du client destinataire. Le deuxième argument sont les données qui sont transmises au serveur. Les données peuvent être de type str, bytes, dict ou list. Les données incluses dans les dictionnaires et les listes sont également limitées à ces types.

La méthode send() peut être appelée à l'intérieur d'un gestionnaire d'événements en réponse à un événement client, ou dans toute autre partie de l'application, y compris dans les tâches d'arrière-plan.

Sessions utilisateurs

Le serveur peut maintenir des informations spécifiques à l'application dans une session utilisateur dédiée à chaque client connecté. Les applications peuvent utiliser la session utilisateur pour enregistrer tous les détails sur l'utilisateur qui doivent être conservés pendant toute la durée de la connexion, tels que les noms d'utilisateur ou les identifiants d'utilisateur.

Les méthodes save_session() et get_session() sont utilisées pour stocker et récupérer des informations dans la session utilisateur :

@eio.on('connect')
def on_connect(sid, environ):
    username = authenticate_user(environ)
    eio.save_session(sid, {'username': username})
@eio.on('message')
def on_message(sid, data):
    session = eio.get_session(sid)
    print('message de ', session['username'])

Pour le serveur asyncio, ces méthodes sont des coroutines :

@eio.on('connect')
async def on_connect(sid, environ):
    username = authenticate_user(environ)
    await eio.save_session(sid, {'username': username})
@eio.on('message')
async def on_message(sid, data):
    session = await eio.get_session(sid)
    print('message de ', session['username'])

La session peut également être manipulée avec le gestionnaire de contexte session() :

@eio.on('connect')
def on_connect(sid, environ):
    username = authenticate_user(environ)
    with eio.session(sid) as session:
        session['username'] = username
@eio.on('message')
def on_message(sid, data):
    with eio.session(sid) as session:
        print('message de ', session['username'])

Pour le serveur asyncio, un gestionnaire de contexte asynchrone est utilisé :

@eio.on('connect')
def on_connect(sid, environ):
    username = authenticate_user(environ)
    async with eio.session(sid) as session:
        session['username'] = username
@eio.on('message')
def on_message(sid, data):
    async with eio.session(sid) as session:
        print('message de ', session['username'])

Remarque : le contenu de la session utilisateur est détruit lorsque le client se déconnecte.

Déconnexion d'un client

À tout moment, le serveur peut déconnecter un client du serveur en appelant la méthode disconnect() et en passant la valeur sid attribuée au client :

eio.disconnect(sid)

Pour le client asyncio, il s'agit d'une coroutine :

await eio.disconnect(sid)

Stratégies de déploiement

Les sections suivantes décrivent diverses stratégies de déploiement pour les serveurs Engine.IO.

Uvicorn, Daphne et autres serveurs ASGI

La classe engineio.ASGIApp est une application compatible ASGI qui peut transférer le trafic Engine.IO vers une instance engineio.AsyncServer :

eio = engineio.AsyncServer(async_mode='asgi')
app = engineio.ASGIApp(eio)

Si désiré, la classe engineio.ASGIApp peut transférer tout trafic qui n'est pas Engine.IO vers une autre application ASGI, ce qui permet de déployer une application web ASGI standard et le serveur Engine.IO en tant que bundle :

eio = engineio.AsyncServer(async_mode='asgi')
app = engineio.ASGIApp(eio, other_app)

L'instance ASGIApp est une instance ASGI entièrement conforme qui peut être déployée avec un serveur web compatible ASGI.

Eventlet avec Gunicorn

Une alternative à l'exécution du serveur WSGI eventlet comme ci-dessus est d'utiliser gunicorn, un serveur web Python complet. La commande pour lancer l'application sous gunicorn est montrée ci-dessous :

$ gunicorn -k eventlet -w 1 module:app

En raison des limitations de son algorithme d'équilibrage de charge, gunicorn ne peut être utilisé qu'avec un seul processus de travail, donc l'option -w 1 est requise. Notez qu'un seul travailleur eventlet peut gérer un grand nombre de clients concurrents.

Une autre limitation lors de l'utilisation de gunicorn est que le transport WebSocket n'est pas disponible, car ce transport nécessite des extensions au standard WSGI.

Note : Eventlet fournit une fonction monkey_patch() qui remplace toutes les fonctions bloquantes de la bibliothèque standard par des versions asynchrones équivalentes. Bien que python-engineio ne nécessite pas de monkey patching, d'autres bibliothèques telles que les pilotes de base de données en auront probablement besoin.

Notes de Scalabilité

Engine.IO est un protocole stateful, ce qui rend la mise à l'échelle horizontale plus difficile. Pour déployer un cluster de processus Engine.IO hébergés sur un ou plusieurs serveurs, les conditions suivantes doivent être remplies:

  • Chaque processus serveur Engine.IO doit pouvoir gérer plusieurs requêtes simultanément. Ceci est nécessaire car les clients en long-polling envoient deux requêtes en parallèle. Les processus workers qui ne peuvent gérer qu'une seule requête à la fois ne sont pas pris en charge.
  • Le répartiteur de charge doit être configuré pour toujours transférer les requêtes d'un client vers le même processus. Les répartiteurs de charge appellent cela sessions collantes, ou affinité de session.

Contrôles Inter-Domaines

Pour des raisons de sécurité, ce serveur applique par défaut une politique de même origine. Concrètement, cela signifie ce qui suit:

  • Si une requête HTTP ou WebSocket entrante inclut l'en-tête Origin, cet en-tête doit correspondre au schéma et à l'hôte de l'URL de connexion. En cas de non-concordance, une réponse avec un code d'état 400 est renvoyée et la connexion est rejetée.
  • Aucune restriction n'est imposée aux requêtes entrantes qui n'incluent pas l'en-tête Origin.

Si nécessaire, l'option cors_allowed_origins peut être utilisée pour autoriser d'autres origines. Cet argument peut être défini sur une chaîne de caractères pour définir une origine autorisée unique, ou sur une liste pour autoriser plusieurs origines. Une valeur spéciale de '*' peut être utilisée pour demander au serveur d'autoriser toutes les origines, mais cela doit être fait avec prudence, car cela pourrait rendre le serveur vulnérable aux attaques de falsification de requête inter-sites (CSRF).

class engineio.AsyncServer(async_mode=None, ping_interval=25, ping_timeout=20, max_http_buffer_size=1000000, allow_upgrades=True, http_compression=True, compression_threshold=1024, cookie=None, cors_allowed_origins=None, cors_credentials=True, logger=False, json=None, async_handlers=True, monitor_clients=None, transports=None, **kwargs)
Un serveur Engine.IO pour asyncio.

Cette classe implémente un serveur Engine.IO entièrement conforme avec la prise en charge des transports websocket et long-polling, compatible avec le framework asyncio sous Python 3.5 ou plus récent.

Paramètres
  • async_mode -- Le mode asynchrone à utiliser. Voir la section Déploiement de la documentation pour une description des options disponibles. Les modes asynchrones valides sont «aiohttp», «sanic», «tornado» et «asgi». Si cet argument n'est pas fourni, «aiohttp» est essayé en premier, suivi de «sanic», «tornado», et enfin «asgi». Le premier mode asynchrone qui a toutes ses dépendances installées est celui qui est choisi.
  • ping_interval -- L'intervalle en secondes auquel le serveur envoie un ping au client. La valeur par défaut est de 25 secondes. Pour un contrôle avancé, un tuple à deux éléments peut être donné, où le premier nombre est l'intervalle de ping et le second est une période de grâce ajoutée par le serveur.
  • ping_timeout -- Le temps en secondes pendant lequel le client attend la réponse du serveur avant de se déconnecter. La valeur par défaut est de 20 secondes.
  • max_http_buffer_size -- La taille maximale acceptée pour les messages entrants. La valeur par défaut est de 1 000 000 octets. Malgré son nom, la valeur définie dans cet argument est appliquée aux connexions HTTP long-polling et WebSocket.
  • allow_upgrades -- Permet ou non les mises à niveau de transport.
  • http_compression -- Compresse ou non les paquets lors de l'utilisation du transport de sondage.
  • compression_threshold -- Compresse les messages uniquement lorsque leur taille en octets est supérieure à cette valeur.
  • cookie -- S'il est défini sur une chaîne de caractères, il s'agit du nom du cookie HTTP que le serveur renvoie au client contenant l'ID de session du client. S'il est défini sur un dictionnaire, la clé 'name' contient le nom du cookie et d'autres clés définissent les attributs du cookie, où la valeur de chaque attribut peut être une chaîne de caractères, un appelable sans arguments, ou un booléen. S'il est défini sur None (par défaut), un cookie n'est pas envoyé au client.
  • cors_allowed_origins -- Origine ou liste d'origines autorisées à se connecter à ce serveur. Seule la même origine est autorisée par défaut. Définissez cet argument sur '*' ou ['*'] pour autoriser toutes les origines, ou sur [] pour désactiver la gestion CORS.
  • cors_credentials -- Les identifiants (cookies, authentification) sont-ils autorisés dans les requêtes vers ce serveur.
  • logger -- Pour activer la journalisation, définissez sur True ou passez un objet logger à utiliser. Pour désactiver la journalisation, définissez sur False. Notez que les erreurs fatales sont journalisées même lorsque logger est défini sur False.
  • json -- Un module json alternatif à utiliser pour encoder et décoder les paquets. Les modules json personnalisés doivent avoir des fonctions dumps et loads qui sont compatibles avec les versions de la bibliothèque standard.
  • async_handlers -- S'il est défini sur True, exécute les gestionnaires d'événements de message dans des threads non bloquants. Pour exécuter les gestionnaires de manière synchrone, définissez sur False. La valeur par défaut est True.
  • monitor_clients -- S'il est défini sur True, une tâche d'arrière-plan garantira la fermeture des clients inactifs. Définissez sur False pour désactiver la tâche de surveillance (non recommandé). La valeur par défaut est True.
  • transports -- La liste des transports autorisés. Les transports valides sont 'polling' et 'websocket'. La valeur par défaut est ['polling', 'websocket'].
  • kwargs -- Réservé pour les extensions futures, tous les paramètres supplémentaires donnés sous forme d'arguments de mot-clé seront silencieusement ignorés.

Ceci est un gestionnaire de contexte qui retourne le dictionnaire de session utilisateur pour le client. Toutes les modifications apportées à ce dictionnaire à l'intérieur du bloc du gestionnaire de contexte sont sauvegardées dans la session. Exemple d'utilisation :

@eio.on('connect')
def on_connect(sid, environ):
    username = authenticate_user(environ)
    if not username:
        return False
    with eio.session(sid) as session:
        session['username'] = username
@eio.on('message')
def on_message(sid, msg):
    async with eio.session(sid) as session:
        print('message reçu de ', session['username'])

Register an event handler.
Parameters

    print('Connection request')

    print('Received message: ', msg)
    eio.send(sid, 'response')

The handler function receives the sid (session ID) for the client as first argument. The 'connect' event handler receives the WSGI environment as a second argument, and can return False to reject the connection. The 'message' handler receives the message payload as a second argument. The 'disconnect' handler does not take a second argument.

class engineio.WSGIApp(engineio_app, wsgi_app=None, static_files=None, engineio_path='engine.io')¶
WSGI application middleware for Engine.IO.

This middleware dispatches traffic to an Engine.IO application. It can also serve a list of static files to the client, or forward unrelated HTTP traffic to another WSGI application.

Parameters
  • engineio_app -- The Engine.IO server. Must be an instance of the engineio.Server class.
  • wsgi_app -- The WSGI app that receives all other traffic.
  • static_files -- A dictionary with static file mapping rules. See the documentation for details on this argument.
  • engineio_path -- The endpoint where the Engine.IO application should be installed. The default value is appropriate for most cases.

Example usage:

import engineio
import eventlet
eio = engineio.Server()
app = engineio.WSGIApp(eio, static_files={
    '/': {'content_type': 'text/html', 'filename': 'index.html'},
    '/index.html': {'content_type': 'text/html',
                    'filename': 'index.html'},
})
eventlet.wsgi.server(eventlet.listen(('', 8000))), app)
