NOM

pythonperformancebenchmarksuite - Documentation de la suite de benchmarks de performance Python

Le projet pyperformance est destiné à être une source faisant autorité de benchmarks pour toutes les implémentations Python. L'accent est mis sur les benchmarks du monde réel, plutôt que sur les benchmarks synthétiques, en utilisant des applications complètes lorsque cela est possible.

  • Projet GitHub pyperformance https://github.com/python/pyperformance (code source, problèmes)
  • Télécharger pyperformance sur PyPI https://pypi.python.org/pypi/pyperformance

UTILISATION

Installation

Commande pour installer pyperformance :

python3 -m pip install pyperformance

La commande installe un nouveau programme pyperformance.

Si nécessaire, les dépendances pyperf et six sont installées automatiquement.

pyperformance fonctionne sur Python 3.6 et versions ultérieures, mais il peut fonctionner sur Python 3.4 et 3.5.

À l'exécution, les fichiers de développement Python (fichiers d'en-tête) peuvent être nécessaires pour installer certaines dépendances comme dulwich_log ou psutil, afin de compiler leur extension C. Commandes sous Fedora pour installer les dépendances :

  • Python 3 : sudo dnf install python3-devel
  • PyPy : sudo dnf install pypy-devel

Notes pour Windows

Sous Windows, pour permettre à pyperformance de compiler des dépendances à partir des sources comme greenlet, dulwich ou psutil, si vous souhaitez utiliser un python.exe compilé à partir des sources, vous ne devez pas utiliser python.exe directement. Au lieu de cela, vous devez exécuter la commande peu connue PC\layout pour créer une disposition de système de fichiers qui ressemble à une installation Python :

.\python.bat -m PC.layout --preset-default --copy installed -v

(Utilisez le drapeau --help pour plus d'informations sur PC\layout.)

Vous pouvez maintenant utiliser l'exécutable Python « installed » :

installed\python.exe -m pip install pyperformance
installed\python.exe -m pyperformance run ...

L'utilisation d'un exécutable Python *réellement* installé (par exemple via py) fonctionne également très bien.

Exécuter des benchmarks

Commandes pour comparer les performances de Python 3.6 et Python 3.7 :

pyperformance run --python=python3.6 -o py36.json
pyperformance run --python=python3.7 -o py37.json
pyperformance compare py36.json py37.json

Note : la syntaxe python3 -m pyperformance ... fonctionne également (ex : python3 -m pyperformance run -o py37.json), mais nécessite d'installer pyperformance sur chaque version de Python testée.

Les fichiers JSON sont produits par le module pyperf et peuvent donc être analysés à l'aide des commandes pyperf :

python3 -m pyperf show py36.json
python3 -m pyperf check py36.json
python3 -m pyperf metadata py36.json
python3 -m pyperf stats py36.json
python3 -m pyperf hist py36.json
python3 -m pyperf dump py36.json
(...)

Il est également possible d'utiliser pyperf pour comparer les résultats de deux fichiers JSON :

python3 -m pyperf compare_to py36.json py37.json --table

run

Exécute les benchmarks sur le python en cours.

Utilisation :

pyperformance run [-h] [-r] [-f] [--debug-single-value] [-v] [-m]
                     [--affinity CPU_LIST] [-o FILENAME]
                     [--append FILENAME] [--manifest MANIFEST]
                     [--timeout TIMEOUT] [-b BM_LIST]
                     [--inherit-environ VAR_LIST] [-p PYTHON]
                     [--hook HOOK]

options :

-h, --help            affiche ce message d'aide et quitte
-r, --rigorous        passe plus de temps à exécuter les tests pour obtenir des
                      résultats plus précis
-f, --fast            obtient des réponses rapides et approximatives
--debug-single-value  Debug : mode le plus rapide, calcule une seule valeur
-v, --verbose         affiche plus de sortie
-m, --track-memory    suit l'utilisation de la mémoire. Ne fonctionne que sous Linux.
--affinity CPU_LIST   spécifie l'affinité CPU pour les exécutions de benchmarks. De
                      cette façon, les benchmarks peuvent être forcés de s'exécuter
                      sur un CPU donné afin de minimiser la variation d'une
                      exécution à l'autre.
-o FILENAME, --output FILENAME
                      exécute les benchmarks sur un seul interpréteur et écrit le
                      benchmark dans FILENAME. Fournir uniquement le python de
                      référence, pas le python modifié.
--append FILENAME     ajoute des exécutions à un fichier existant, ou le crée s'il
                      n'existe pas
--timeout TIMEOUT     spécifie un délai d'attente en secondes pour une seule
                      exécution de benchmark (par défaut : désactivé)
--manifest MANIFEST   fichier manifest de benchmark à utiliser
-b BM_LIST, --benchmarks BM_LIST
                      liste de benchmarks séparés par des virgules à exécuter.
                      Peut contenir des arguments positifs et négatifs :
                      --benchmarks=run_this,also_this,-not_this. S'il n'y a pas
                      d'arguments positifs, nous exécuterons tous les benchmarks
                      sauf ceux spécifiés négativement. Sinon, nous exécuterons
                      uniquement les arguments positifs.
--inherit-environ VAR_LIST
                      liste de noms de variables d'environnement séparés par des
                      virgules qui sont hérités de l'environnement parent lors
                      de l'exécution des sous-processus de benchmarking.
-p PYTHON, --python PYTHON
                      exécutable Python (par défaut : utilise le Python en cours
                      d'exécution)
--same-loops SAME_LOOPS
                      utilise le même nombre de boucles qu'une exécution précédente
                      (c.-à-d. ne pas recalibrer). Doit être un chemin vers un
                      fichier .json d'une exécution précédente.
--hook HOOK
                      applique le hook pyperf donné lors de l'exécution des
                      benchmarks.

run

Exécuter des benchmarks Python.

Usage :

pyperformance run [-h] [--manifest MANIFEST] [-b BM_LIST] [--output OUTPUT]
                  [--inherit-environ VAR_LIST] [-p PYTHON]
                  [--duplicate DUPLICATE] [--fast-run] [--debug-single-sample]
                  [--debug-all-samples] [--trace] [--trace-setup]
                  [--append-timestamp] [--datetime DATE] [--runs RUNS]
                  [--inner-loops INNER_LOOPS] [--rigorous] [--tier1 TIER1]
                  [--tier2 TIER2] [--tier3 TIER3] [--tier4 TIER4]
                  [--remove-output] [--disable-track-memory]
                  [--track-memory] [--enable-memory-debug] [--memory-debug-file MEMORY_DEBUG_FILE]
                  [--memory-debug-verbose] [--memory-debug-threshold MEMORY_DEBUG_THRESHOLD]
                  [--stdout-csv] [--stdout-json] [--stdout-json-cols COL_LIST]

options :

--manifest MANIFEST   Fichier manifeste des benchmarks à utiliser.
-b BM_LIST, --benchmarks BM_LIST
                      Liste de benchmarks à exécuter, séparée par des virgules.
                      Peut contenir des arguments positifs et négatifs :
                      --benchmarks=run_this,also_this,-not_this. S'il n'y a
                      pas d'arguments positifs, tous les benchmarks seront
                      exécutés à l'exception de ceux spécifiés par les
                      arguments négatifs. Sinon, seuls les arguments
                      positifs seront exécutés.
--output OUTPUT       Nom du fichier de sortie (par défaut :
                      benchs.json).
--inherit-environ VAR_LIST
                      Liste de noms de variables d'environnement, séparés par
                      des virgules, qui sont héritées de l'environnement parent
                      lors de l'exécution des sous-processus de benchmarking.
-p PYTHON, --python PYTHON
                      Exécutable Python (par défaut : utiliser l'exécutable
                      Python en cours d'exécution).
--duplicate DUPLICATE Nombre de fois que chaque benchmark doit être dupliqué
                      (par défaut : 1).
--fast-run            Exécuter chaque benchmark une seule fois sans ajustement
                      du système.
--debug-single-sample
                      Exécuter chaque benchmark une seule fois, sans ajustement
                      du système, et sans dupliquer les échantillons.
--debug-all-samples   Exécuter chaque benchmark sans dupliquer les échantillons.
--trace               Activer le traçage pour les benchmarks.
--trace-setup         Activer le traçage pour la configuration des benchmarks.
--append-timestamp    Ajouter un horodatage au nom du fichier de sortie.
--datetime DATE       Utiliser la date spécifiée pour les résultats.
--runs RUNS           Nombre d'exécutions pour chaque benchmark (par défaut :
                      3).
--inner-loops INNER_LOOPS
                      Nombre de boucles internes pour chaque benchmark (par
                      défaut : 1).
--rigorous            Exécuter chaque benchmark plusieurs fois pour obtenir des
                      résultats plus précis.
--tier1 TIER1         Exécuter uniquement les benchmarks du niveau 1.
--tier2 TIER2         Exécuter uniquement les benchmarks du niveau 2.
--tier3 TIER3         Exécuter uniquement les benchmarks du niveau 3.
--tier4 TIER4         Exécuter uniquement les benchmarks du niveau 4.
--remove-output       Supprimer le fichier de sortie s'il existe déjà.
--disable-track-memory
                      Désactiver le suivi de la mémoire.
--track-memory        Activer le suivi de la mémoire.
--enable-memory-debug Activer le débogage de la mémoire.
--memory-debug-file MEMORY_DEBUG_FILE
                      Fichier de sortie pour le débogage de la mémoire.
--memory-debug-verbose
                      Mode verbeux pour le débogage de la mémoire.
--memory-debug-threshold MEMORY_DEBUG_THRESHOLD
                      Seuil pour le débogage de la mémoire.
--stdout-csv          Écrire les résultats au format CSV sur la sortie standard.
--stdout-json         Écrire les résultats au format JSON sur la sortie standard.
--stdout-json-cols COL_LIST
                      Liste des colonnes à inclure dans la sortie JSON, séparée
                      par des virgules. Format : trois colonnes CSV contenant
                      les temps d'exécution minimum pour chaque benchmark.

Environnement virtuel pyperformance

Pour exécuter les tests de performance, pyperformance crée d'abord un environnement virtuel. Il installe les exigences avec des versions fixes pour obtenir un environnement reproductible. Le Python système a des modules inconnus installés avec des versions inconnues, et peut avoir des fichiers .pth exécutés au démarrage de Python, ce qui peut modifier le comportement de Python ou du moins ralentir son démarrage.

Quel est l'objectif de pyperformance

Un test de performance est toujours écrit dans un but précis. Selon la manière dont le test est écrit et dont il est exécuté, le résultat peut être différent et donc avoir une signification différente.

La suite de tests de performance pyperformance a plusieurs objectifs :

  • Aider à détecter les régressions de performance dans une implémentation Python
  • Valider qu'un changement d'optimisation rend Python plus rapide et ne provoque pas de régressions de performance, ou seulement des régressions mineures
  • Comparer deux implémentations de Python, par exemple CPython et PyPy
  • Mettre en avant les performances de Python qui, idéalement, seraient représentatives des performances des applications exécutées en production

Ne pas désactiver le GC ni l'ASLR

Le module pyperf et les tests de performance pyperformance sont conçus pour produire des résultats reproductibles, mais pas au prix de l'exécution des tests dans un mode spécial qui ne serait pas utilisé pour exécuter des applications en production. Pour ces raisons, le ramasse-miettes de Python, la fonction de hachage aléatoire de Python et l'ASLR (Address Space Layout Randomization) du système ne sont pas désactivés. Les tests n'appellent pas non plus gc.collect() car CPython l'implémente avec arrêt du monde https://en.wikipedia.org/wiki/Tracing_garbage_collection#Stop-the-world_vs._incremental_vs._concurrent et donc les applications ne l'appellent pas pour ne pas tuer les performances.

Inclure les valeurs aberrantes et les pics

De plus, bien que la documentation pyperf explique comment réduire le bruit aléatoire du système et des autres applications, certains tests utilisent le système et peuvent donc obtenir des temps différents en fonction de la charge du système, des performances d'E/S, etc. Les valeurs aberrantes et les pics temporaires dans les résultats ne sont pas automatiquement supprimés : les valeurs sont résumées en calculant la moyenne (moyenne arithmétique) et l'écart type qui "contiennent" ces pics, au lieu d'utiliser la médiane et l'écart absolu médian par exemple, qui ignorent les valeurs aberrantes. C'est un choix délibéré car les applications exécutées en production sont impactées par de tels ralentissements temporaires causés par diverses choses comme un ramasse-miettes ou une compilation JIT.

Phases d'échauffement et état stable

Un problème limite concerne les "phases d'échauffement" des tests. Les premières valeurs de chaque processus travailleur sont toujours plus lentes : 10% plus lentes dans le meilleur des cas, elles peuvent être 1000% plus lentes ou plus sur PyPy. Actuellement (2017-04-14), pyperformance ignore les premières valeurs considérées comme phase d'échauffement jusqu'à ce qu'un test atteigne son "état stable". L'"état stable" peut inclure des pics temporaires toutes les 5 valeurs (par exemple, causés par le ramasse-miettes), et il peut toujours impliquer des optimisations supplémentaires du compilateur JIT mais avec un impact "faible" sur la moyenne de pyperformance.

Pour être clair, "échauffement" et "état stable" sont un travail en cours et un sujet très complexe, en particulier sur PyPy et son compilateur JIT.

Si --track_memory est passé, pyperformance échantillonnera en continu l'utilisation de la mémoire du test. Cela fonctionne actuellement uniquement sous Linux 2.6.16 et supérieur ou sous Windows avec PyWin32. telco

Benchmark Telco pour mesurer les performances des calculs décimaux :

  • http://speleotrove.com/decimal/telco.html
  • http://speleotrove.com/decimal/telcoSpec.html
  • Un indicateur de type d'appel, c, est défini à partir du bit le plus bas (le moins significatif) de la durée (d'où c est 0 ou 1).
  • Un tarif, r, est déterminé à partir du type d'appel. Les appels avec c=0 ont un tarif bas r : 0.0013 ; le reste (appels longue distance) ont un tarif « premium » r : 0.00894. (Les tarifs sont, très approximativement, en Euros ou dollars par seconde.)
  • Un prix, p, pour l'appel est ensuite calculé (p=r*n). Celui-ci est arrondi à exactement 2 décimales en utilisant round-half-even (arrondi bancaire au plus proche).
  • Une taxe de base, b, est calculée : b=p*0.0675 (6.75%). Celle-ci est tronquée à exactement 2 décimales (arrondi vers le bas), et la variable totale de taxe de base est ensuite incrémentée (sumB=sumB+b).
  • Pour les appels longue distance : une taxe de distance, d, est calculée : d=p*0.0341 (3.41%). Celle-ci est tronquée à exactement 2 décimales (arrondi vers le bas), puis la variable totale de taxe de distance est incrémentée (sumD=sumD+d).
  • Le prix total, t, est calculé (t=p+b, et, s'il s'agit d'un appel longue distance, t=t+d).
  • La variable des prix totaux est incrémentée (sumT=sumT+t).
  • Le prix total, t, est converti en chaîne de caractères, s.

Le benchmark Python est implémenté avec le module decimal.

Voir le module Python decimal (stdlib) https://docs.python.org/dev/library/decimal.html.

BENCHMARKS PERSONNALISÉS

pyperformance inclut son propre ensemble de benchmarks (voir Benchmarks <>). Cependant, il prend également en charge l'utilisation de benchmarks personnalisés.

Utilisation des Benchmarks Personnalisés

Pour utiliser des benchmarks personnalisés, vous devrez utiliser l'option de ligne de commande --manifest et fournir le chemin vers le fichier manifeste décrivant ces benchmarks.

Les Formats de Fichiers pyperformance

pyperformance utilise deux formats de fichiers pour identifier les benchmarks :

  • manifest - un ensemble de benchmarks
  • metadata - un benchmark unique

Pour chaque benchmark, il existe deux fichiers requis et plusieurs fichiers optionnels. Ces fichiers sont censés se trouver dans une structure de répertoire spécifique (sauf si personnalisée dans les métadonnées).

La structure (voir ci-dessous) est telle qu'il est facile de maintenir un benchmark (ou un ensemble de benchmarks) sur GitHub et de le distribuer sur PyPI. Elle simplifie également la publication des benchmarks d'un projet Python. L'alternative est de pointer les utilisateurs vers un dépôt.

Les benchmarks peuvent hériter des métadonnées d'autres fichiers de métadonnées. Ceci est utile pour conserver les métadonnées communes à un ensemble de benchmarks (par exemple, « version ») dans un seul fichier. De même, les benchmarks pour un projet Python peuvent hériter des métadonnées du fichier pyproject.toml du projet.

Parfois, un benchmark aura une ou plusieurs variantes qui s'exécuteront en utilisant le même script. Des variantes comme celles-ci sont prises en charge par pyperformance sans nécessiter beaucoup d'efforts supplémentaires.

Structure des Répertoires de Benchmark

Normalement, un benchmark est structuré comme suit :

bm_NOM/
   data/  # si nécessaire
   requirements.txt  # fichier de verrouillage, le cas échéant
   pyproject.toml
   run_benchmark.py

(Notez le préfixe « bm_ » sur le nom du répertoire.)

"pyproject.toml" contient les métadonnées. "run_benchmark.py" contient le code réel du benchmark. Les deux sont nécessaires.

pyperformance traite le fichier de métadonnées comme la source fondamentale d'informations sur un benchmark. Un manifeste pour un ensemble de benchmarks est effectivement une cartographie de noms vers des fichiers de métadonnées. Ainsi, un fichier de métadonnées est essentiel. Il peut être situé n'importe où sur le disque. Cependant, s'il n'est pas situé dans la structure décrite ci-dessus, alors les métadonnées doivent indiquer où trouver les autres fichiers.

En dehors de cela, seul un script de benchmark (par exemple, "run_benchmark.py" ci-dessus) est requis. Tous les autres fichiers sont optionnels.

Lorsqu'un benchmark a des variantes, chacune a son propre fichier de métadonnées à côté du "pyproject.toml" normal, nommé "bm_NOM.toml". (Notez le préfixe "bm_".) Le format des fichiers de métadonnées de variante est exactement le même. pyperformance les traite de la même manière, sauf que le "pyproject.toml" frère est hérité par défaut.

Fichiers Manifeste

Un fichier manifeste identifie un ensemble de benchmarks, ainsi que (optionnellement) comment ils doivent être regroupés. pyperformance utilise le manifeste pour déterminer quels benchmarks sont disponibles à exécuter (et donc lesquels exécuter par défaut).

Un manifeste ressemble normalement à ceci :

[benchmarks]
name        metafile
bench1      somedir/bm_bench1/pyproject.toml
bench2      somedir/pyproject.toml
bench3      ../anotherdir

La section "benchmarks" est une table avec des lignes de valeurs séparées par des tabulations. La valeur "name" est comment pyperformance identifiera le benchmark. La valeur "metafile" est où pyperformance cherchera les métadonnées du benchmark. Si un metafile est un répertoire, alors il recherche "pyproject.toml" dans ce répertoire.

Groupes de Benchmarks

L'autre secti

Groupes

Les sections[group ...] dans le fichier manifeste sont utilisées pour définir des groupes de benchmarks qui peuvent être exécutés ensemble. Les sections sont nommées après le nom du groupe, sauf pour le groupe par défaut, qui doit être nommé[group default].

Voici un exemple de la manière dont les groupes peuvent être utilisés dans le fichier manifeste:

[benchmarks]
name        metafile
bench1      somedir/bm_bench1
bench2      somedir/bm_bench2
bench3      anotherdir/mybench.toml
[groups]
tag1
tag2
[group default]
bench2
bench3
[group tricky]
bench2

La section "groups" spécifie les groupes disponibles qui peuvent être identifiés par des balises de benchmark (voir la section sur les balises dans les métadonnées ci-dessous). Toutes les autres sections de groupe dans le manifeste sont automatiquement ajoutées à la liste des groupes disponibles.

Si aucun groupe "default" n'est spécifié, alors un groupe est automatiquement ajouté avec tous les benchmarks de la section "benchmarks". S'il n'y a pas de section "groups" et aucune section de groupe individuelle (autre que "default"), alors l'ensemble de toutes les balises des benchmarks connus est traité comme "groups". Un groupe nommé "all" est également ajouté automatiquement et contient tous les benchmarks connus.

Les benchmarks peuvent être exclus d'un groupe en utilisant un préfixe - (moins). Tout benchmark déjà dans la liste (à ce moment) qui correspond sera retiré de la liste. Si la première entrée de la section est une exclusion, alors tous les benchmarks connus sont d'abord ajoutés à la liste avant que l'exclusion ne soit appliquée.

Par exemple:

[benchmarks]
name        metafile
bench1      somedir/bm_bench1
bench2      somedir/bm_bench2
bench3      anotherdir/mybench.toml
[group default]
-bench1

Cela signifie que par défaut, seuls "bench2" et "bench3" sont exécutés.

Fusion des Manifestes

Pour combiner des manifestes, utilisez la section [includes] dans le manifeste:

[includes]
project1/benchmarks/MANIFEST
project2/benchmarks/MANIFEST
<default>

Notez que <default> équivaut à inclure le fichier manifeste pour les benchmarks par défaut de pyperformance.

Une Suite de Benchmarks Locale

Souvent, un projet aura plus d'un benchmark qu'il traitera comme une suite. pyperformance gère cela sans travail supplémentaire.

Dans le répertoire contenant le fichier manifeste, placez tous les benchmarks. Ensuite, mettez <local> dans la colonne "metafile", comme ceci:

[benchmarks]
name        metafile
bench1      <local>
bench2      <local>
bench3      <local>
bench4      <local>
bench5      <local>

Il recherchera DIR/bm_NAME/pyproject.toml.

S'il y a également des variantes, identifiez le benchmark principal dans la valeur "metafile", comme ceci:

[benchmarks]
name        metafile
bench1      <local>
bench2      <local>
bench3      <local>
variant1    <local:bench3>
variant2    <local:bench3>

pyperformance recherchera DIR/bm_BASE/bm_NAME.toml, où "BASE" est la partie après "local:".

Une Suite de Benchmarks d'un Projet

Un projet Python peut identifier sa suite de benchmarks en plaçant le chemin du fichier manifeste dans le pyproject.toml de niveau supérieur du projet. Des manifestes supplémentaires peuvent également être identifiés:

[tool.pyperformance]
manifest = "..."
manifests = ["...", "..."]

(Rappel: il s'agit du pyproject.toml, pas du fichier manifeste.)

Fichiers de Métadonnées des Benchmarks

Le fichier de métadonnées d'un benchmark (généralement pyproject.toml) suit le format spécifié dans la PEP 621 https://www.python.org/dev/peps/pep-0621 et la PEP 518 https://www.python.org/dev/peps/pep-0518. Il existe donc deux sections prises en charge dans le fichier : "project" et "tool.pyperformance".

Un fichier de métadonnées typique ressemblera à ceci:

[project]
version = "0.9.1"
dependencies = ["pyperf"]
dynamic = ["name"]
[tool.pyperformance]
name = "my_benchmark"

Un fichier très détaillé pourrait ressembler à ceci:

[project]
name = "pyperformance_bm_json_dumps"
version = "0.9.1"
description = "Un benchmark pour json.dumps()"
requires-python = ">=3.8"
dependencies = ["pyperf"]
urls = {repository = "https://github.com/python/pyperformance"}
dynamic = ["version"]
[tool.pyperformance]
name = "json_dumps"
tags = "serialize"
runscript = "bench.py"
datadir = ".data-files/extras"
extra_opts = ["--special"]

Héritage

Pour qu'un benchmark hérite d'un autre (ou de métadonnées communes), le champ "inherits" est disponible:

[project]
dependencies = ["pyperf"]
dynamic = ["name", "version"]
[tool.pyperformance]
name = "my_benchmark"
inherits = "../common.toml"

Toutes les valeurs de l'une ou l'autre section des métadonnées héritées sont traitées comme des valeurs par défaut, sur lesquelles les métadonnées actuelles sont appliquées. Dans l'exemple ci-dessus, par exemple, une valeur pour "version" dans common.toml serait utilisée ici.

Si la valeur "inherits" est un répertoire (même pour ".."), alors "base.toml" dans ce répertoire sera hérité.

Pour les variantes, le pyproject.toml de base est la valeur par défaut pour "inherits".

Valeurs Déduites

Dans certaines situations, les valeurs omises seront déduites d'autres données disponibles (même pour les champs requis).

  • project.name <= tool.pyperformance.name
  • project.* <= métadonnées héritées (sauf "name" et "dynamic")
  • tool.pyperformance.name <= nom du fichier de métadonnées
  • tool.pyperformance.* <= métadonnées héritées (sauf "name" et "inherits")

Lorsque le nom est déduit du nom du fichier pour un benchmark de structure régulière, le préfixe "bm_" est supprimé du répertoire du benchmark. S'il s'agit d'une variante, ce préfixe est supprimé du nom du fichier de métadonnées, ainsi que de l'extension .toml.

La section [project]

champ type R T B D
project.name str X X
project.version ver X X X
project.dependencies [str] X
project.dynamic [str]

"R": requis "T": déduit de la section tool "B": déduit des métadonnées héritées "D": pour les benchmarks par défaut, déduit de pyperformance

"dynamic" est requis par la PEP 621 lorsque un champ sera rempli dynamiquement par l'outil. Ceci est particulièrement important pour les champs requis.

Tous les autres champs PEP 621 sont facultatifs (par exemple, requires-python = ">=3.8", {repository = "https://github.com/..."}).

La section [tool.pyperformance]

champ type R B F
tool.name str X X
tool.tags [str] X
tool.extra_opts [str] X
tool.inherits file
tool.runscript file X
tool.datadir file X

« R »: requis « B » : déduit des métadonnées héritées « F » : déduit du nom de fichier

  • tags : liste facultative de noms pour regrouper les benchmarks
  • extra_opts : liste facultative d'arguments à passer à tool.runscript
  • runscript : le script de benchmark à utiliser à la place de run_benchmark.py.

BENCHMARKS

Les benchmarks inclus sont catégorisés comme suit:

  • Modules natifs: benchmarks de différents modules natifs Python.
  • Python: benchmarks de différentes parties du langage Python lui-même.
  • Bibliothèques tierces: benchmarks de bibliothèques tierces couramment utilisées, comme Django, NumPy, Pillow, etc.

BENCHMARKS PERSONNALISÉS

Vous pouvez exécuter vos propres benchmarks en utilisant l'option --bench. Le chemin vers le répertoire contenant vos benchmarks doit être spécifié via l'option --bench-dir.

Les benchmarks personnalisés doivent être structurés dans des répertoires, chaque répertoire contenant un fichier run.py qui implémente la logique d'exécution du benchmark.

Historique

Le projet a été déplacé vers https://github.com/python/performance en août 2016. Les fichiers ont été réorganisés, les benchmarks ont été patchés pour utiliser le module perf afin d'exécuter les benchmarks dans plusieurs processus.

Le projet a été lancé en décembre 2008 par Collin Winter et Jeffrey Yasskin pour le projet Unladen Swallow. Le projet était hébergé sur https://hg.python.org/benchmarks jusqu'en février 2016.

Autres benchmarks Python :

  • CPython : speed.python.org https://speed.python.org/ utilise pyperf, pyperformance et Codespeed https://github.com/tobami/codespeed/ (application web Django)
  • PyPy : speed.pypy.org http://speed.pypy.org/ utilise les benchmarks PyPy https://bitbucket.org/pypy/benchmarks
  • Pyston : pyston-perf https://github.com/dropbox/pyston-perf et speed.pyston.org http://speed.pyston.org/
  • Benchmarks Numba http://numba.pydata.org/numba-benchmark/
  • Cython : Démos/benchmarks Cython https://github.com/cython/cython/tree/master/Demos/benchmarks
  • Pythran : numpy-benchmarks https://github.com/serge-sans-paille/numpy-benchmarks

Voir aussi la liste de diffusion Python speed https://mail.python.org/mailman/listinfo/speed et le module Python pyperf http://pyperf.readthedocs.io/ (utilisé par pyperformance).

pyperformance n'est pas encore optimisé pour PyPy : utilisez le projet PyPy benchmarks https://foss.heptapod.net/pypy/benchmarks à la place pour mesurer les performances de PyPy.
