NOM

Jedi est un outil d'analyse statique pour Python, généralement utilisé dans les plugins d'IDE/éditeurs. Jedi se concentre sur l'autocomplétion et la fonctionnalité "aller à". D'autres fonctionnalités incluent la refactorisation, la recherche de code et la recherche de références.

Voici un exemple simple de la fonctionnalité d'autocomplétion :

>>> import jedi
>>> source = '''
... import json
... json.lo'''
>>> script = jedi.Script(source, path='example.py')
>>> script
<Script: 'example.py' ...>
>>> completions = script.complete(3, len('json.lo'))
>>> completions
[<Completion: load>, <Completion: loads>]
>>> print(completions[0].complete)
ad
>>> print(completions[0].name)
load

Autocomplétion par tabulation dans le Shell Python

Jedi est une dépendance d'IPython. L'autocomplétion dans IPython est donc possible sans configuration supplémentaire.

Il existe deux options différentes pour utiliser l'autocomplétion Jedi dans votre interpréteur python. Une avec votre fichier personnalisé $HOME/.pythonrc.py et une autre qui utilise PYTHONSTARTUP.

Utilisation de PYTHONSTARTUP

Pour utiliser l'autocomplétion Jedi dans l'interpréteur Python, ajoutez ce qui suit dans la configuration de votre shell (par exemple, .bashrc). Cela ne fonctionne que sous Linux/Mac, car readli

ne n'est pas disponible sous Windows. Si vous souhaitez tout de même l'autocomplétion Jedi dans votre REPL, utilisez plutôt IPython :

export PYTHONSTARTUP="$(python -m jedi repl)"

Vous pourrez alors utiliser le compléteur Jedi dans votre interpréteur Python :

try:
    from jedi.utils import setup_readline
except ImportError:
    # Fallback to the stdlib readline completer if it is installed.
    # Taken from http://docs.python.org/2/library/rlcompleter.html
    print("Jedi is not installed, falling back to readline")
    try:
        import readline
        import rlcompleter
        readline.parse_and_bind("tab: complete")
    except ImportError:
        print("Readline is not installed either. No tab completion is enabled.")
else:
    setup_readline()

Cela utilisera le compléteur readline comme solution de secours si Jedi n'est pas installé. Le compléteur readline ne complétera que les noms dans l'espace de noms global, donc par exemple :

Fonctionnalités et Limitations

Les principaux appels API et fonctionnalités de Jedi sont :

  • Autocomplétion : Script.complete() ; Il est également possible de la faire fonctionner dans votre REPL (IPython, etc.)
  • Aller à/Inférence de type : Script.goto() et Script.infer()
  • Analyse statique : Script.get_names() et Script.get_syntax_errors()
  • Refactorisations : Script.rename(), Script.inline(), Script.extract_variable() et Script.extract_function()
  • Recherche de code : Script.search() et Project.search()

Fonctionnalités de base

  • Support de Python 3.6+
  • Ignore les erreurs de syntaxe et les indentations incorrectes
  • Peut gérer des structures de modules/fonctions/classes complexes
  • Excellent support pour virtualenv/venv
  • Fonctionne parfaitement avec les annotations de type de Python,
  • Comprend les fichiers stub
  • Peut inférer les arguments de fonction pour les docstrings sphinx, epydoc et numpydoc de base
  • Est globalement un logiciel très solide qui a été peaufiné pendant longtemps. Les rapports de bugs sont très appréciés et sont généralement corrigés en quelques semaines.

Fonctionnalités Python supportées

Jedi prend en charge de nombreuses fonctionnalités Python couramment utilisées :

  • builtins
  • returns, yields, yield from
  • affectations de tuples / indexation de tableaux / indexation de dictionnaires / déballage par étoile
  • instruction with / gestion des exceptions
  • *args / **kwargs
  • décorateurs / lambdas / fermetures
  • générateurs / itérateurs
  • descripteurs : property / staticmethod / classmethod / descripteurs personnalisés
  • quelques méthodes magiques : __call__, __iter__, __next__, __get__, __getitem__, __init__
  • list.append(), set.add(), list.extend(), etc.
  • compréhensions de liste (imbriquées) / expressions ternaires
  • imports relatifs
  • getattr() / __getattr__ / __getattribute__
  • annotations de fonction
  • modifications simples/typiques de sys.path
  • vérifications isinstance pour if/while/assert
  • packages de namespace (inclut pkgutil, pkg_resources et les namespaces PEP420)
  • support Django / Flask / Buildout
  • Comprend les fixtures Pytest

Limitations

En général, la limite de Jedi est assez haute, mais pour les très grands projets ou le code très complexe, Jedi arrête parfois intentionnellement l'inférence de type, pour éviter de planter pendant longtemps.

De plus, il existe certains motifs Python que Jedi ne prend pas en charge. Ceci est intentionnel et ci-dessous devrait être une liste complète :

  • Métaclasses arbitraires : Certaines métaclasses comme enums et dataclasses sont réimplémentées dans Jedi pour les faire fonctionner. La plupart du temps, les stubs sont suffisants pour que l'inférence de type fonctionne, même lorsque des métaclasses sont impliquées.
  • setattr(), __import__()
  • Écriture dans certains dicts : globals(), locals(), object.__dict__
  • Manipulations d'instances en dehors des variables d'instance sans utiliser de méthodes

Problèmes de performances

L'importation de numpy peut parfois être assez lente, tout comme le chargement des builtins la première fois. Si vous souhaitez accélérer les choses, vous pouvez précharger des bibliothèques dans Jedi, avec preload_module(). Cependant, une fois chargées, cela ne devrait plus poser de problème. Il en va de même pour les modules volumineux comme PySide, wx, tensorflow, pandas, etc.

Sécurité

Pour Script

La sécurité est un sujet important pour Jedi. Par défaut, aucun code n'est exécuté dans Jedi. Tant que vous écrivez du Python pur, tout est inféré statiquement. Si vous activez load_unsafe_extensions=True pour votre Project et que vous utilisez des modules intégrés (c_builtin), Jedi exécutera ces modules. Si vous ne faites pas confiance à une base de code, veuillez ne pas activer cette option. Elle pourrait entraîner une exécution de code arbitraire.

Pour Interpreter

Si vous souhaitez de la sécurité pour Interpreter, ne l'utilisez pas. Jedi exécute des propriétés et, en général, ne fait pas très attention à éviter l'exécution de code. C'est intentionnel : la plupart des gens font confiance aux bases de code qu'ils ont importées, car à ce stade, une base de code malveillante aurait déjà eu une exécution de code.

Aperçu de l'API

NOTE :

Cette documentation s'adresse principalement aux développeurs de plugins qui souhaitent améliorer leurs éditeurs/IDE avec Jedi.

L'API se compose de plusieurs parties différentes :

  • Les points d'entrée principaux pour la complétion/goto : Script et Interpreter. Si vous travaillez avec Jedi, vous voudrez comprendre ces classes en premier.
  • Classes de résultats de l'API
  • Prise en charge des versions Python/Virtualenv avec des fonctions telles que find_system_environments() et find_virtualenvs()
  • Une manière de travailler avec différents Dossiers / Projets

Script

class jedi.Script(code=None, *, path=None, environment=None, project=None)
Un Script est la base pour les complétions, goto ou tout ce que vous voulez faire avec Jedi. La contrepartie de cette classe est Interpreter, qui travaille avec des dictionnaires réels et peut fonctionner avec un REPL. Cette classe doit être utilisée lorsqu'un utilisateur édite du code dans un éditeur.

Vous pouvez soit utiliser le paramètre code, soit path pour lire un fichier. Habituellement, vous voudrez utiliser les deux (dans un éditeur).

Le sys.path du Script est très personnalisable :

  • Si project est fourni avec un sys_path, celui-ci sera utilisé.
  • Si environment est fourni, son sys.path sera utilisé (voir Environment.get_sys_path) ;
  • Sinon, sys.path correspondra à celui de l'environnement par défaut de Jedi, qui correspond généralement au chemin sys utilisé au moment de l'importation de Jedi.

La plupart des méthodes ont un paramètre line et un paramètre column. Les lignes dans Jedi sont toujours basées sur 1 et les colonnes sur 0. Pour éviter les répétitions, elles ne sont pas toujours documentées. Vous pouvez omettre line et column. Jedi effectuera alors simplement l'action que vous appelez à la fin du fichier. Si vous ne fournissez que la ligne, il complétera à la fin de cette ligne.

AVERTISSEMENT :

Par défaut, jedi.settings.fast_parser est activé, ce qui signifie que parso réutilise les modules (c'est-à-dire qu'ils ne sont pas immuables). Avec ce paramètre, Jedi n'est pas thread-safe et il n'est pas non plus sûr d'utiliser plusieurs instances de Script et ses définitions en même temps.

Si vous êtes un développeur de plugin normal, cela ne devrait pas poser de problème. C'est un problème pour les personnes qui font des choses plus complexes avec Jedi.

Paramètres
  • code (str) -- Le code source du fichier courant, séparé par des nouvelles lignes.
  • path (str ou pathlib.Path ou None) -- Le chemin du fichier dans le système de fichiers, ou '' s'il n'a pas encore été sauvegardé.
  • environment (Environment) -- Fournit un Environment prédéfini pour travailler avec une version Python spécifique ou un virtualenv.
  • project (Project) -- Fournit un Project pour s'assurer que la recherche de références fonctionne bien, car le bon dossier est recherché. Il existe également des moyens de modifier le chemin sys et d'autres choses.

    Interpreter

    classe jedi.Interpreter(code, namespaces, *, project=None, **kwds)
    API de Jedi pour les REPL Python.

    Implémente également toutes les méthodes présentes dans Script.

    En plus des complétions que les REPL normaux effectuent, comme str.upper, Jedi prend également en charge la complétion de code basée sur l'analyse statique du code. Par exemple, Jedi complétera str().upper.

    >>> from os.path import join
>>> namespace = locals()
>>> script = Interpreter('join("").up', [namespace])
>>> print(script.complete()[0].name)
upper

    Tous les arguments nommés sont identiques aux arguments de Script.

    Paramètres
    • code (str) -- Code à analyser.
    • namespaces (List[dict]) -- Une liste de dictionnaires d'espaces de noms tels que celui retourné par globals() et locals().

    Projets

    Les projets sont un moyen de gérer des projets Python au sein de Jedi. Pour des plugins plus simples, vous n'aurez peut-être pas besoin de gérer les projets, mais si vous souhaitez offrir plus de flexibilité à l'utilisateur pour définir les chemins système et les interpréteurs Python pour un projet, Project est le moyen idéal pour le permettre.

    Le noyau de Jedi

    Le noyau de Jedi se compose de trois parties :

    • Analyseur syntaxique
    • Inférence de types Python
    • API

    La plupart des gens s'intéressent probablement à l'inférence de types, car c'est là que toute la magie opère. Je dois d'abord introduire l'analyseur syntaxique, car jedi.inference l'utilise intensivement.

    Analyseur syntaxique

    Inférence de types du code python (inference/__init__.py)

    L'inférence de types du code Python dans Jedi repose sur trois hypothèses :

    • Le code utilise le moins d'effets de bord possible. Jedi comprend certaines modifications de listes/tuples/ensembles, mais il n'y a aucune garantie que Jedi détecte tout (par exemple, l'ajout à une liste dans différents modules).
    • Aucune magie n'est utilisée :
    • métaclasses
    • setattr() / __import__()
    • écritures dans globals(), locals(), object.__dict__
    •
    Le programmeur n'est pas un total connard, par exemple, comme celui-ci :-)

    L'algorithme réel est basé sur un principe que j'appelle l'inférence de types paresseuse. C'est-à-dire que le point d'entrée typique pour l'analyse statique est l'appel à infer_expr_stmt. Il existe une logique distincte pour l'autocomplétion dans l'API, l'état d'inférence concerne l'inférence d'une expression.

datetime.date.toda# <-- curseur ici

    Tout d'abord, ce module ne se soucie pas de la complétion. Il se soucie vraiment seulement de datetime.date. À la fin de la procédure, infer_expr_stmt renverra la classe date.

    Pour visualiser cela (simplifié) :

    • InferenceState.infer_expr_stmt ne fait pas grand-chose, car il n'y a pas d'affectation.
    • Context.infer_node se charge de résoudre le chemin pointillé
    • InferenceState.find_types recherche les définitions globales de datetime, qu'il trouve dans la définition d'une importation, en analysant l'arbre syntaxique.
    • En utilisant la logique d'importation, le module datetime est trouvé.
    • Maintenant, find_types est appelé à nouveau par infer_node pour trouver date à l'intérieur du module datetime.

    Maintenant, que se passerait-il si nous voulions datetime.date.foo.bar ? Deux appels supplémentaires à find_types. Cependant, le deuxième appel serait ignoré, car le premier ne renverrait rien (il n'y a pas d'attribut foo dans date).

    Que se passerait-il si l'importation contenait une autre ExprStmt comme celle-ci :

    from foo import bar
Date = bar.baz

    Eh bien... Vous avez compris. Juste une autre récursion infer_expr_stmt. C'est vraiment facile. Python peut évidemment devenir beaucoup plus compliqué que cela. Pour comprendre les affectations de tuples, les compréhensions de listes et tout le reste, beaucoup plus de code a dû être écrit.

    Jedi a été très bien testé, vous pouvez donc commencer à modifier le code. Il est préférable d'écrire votre propre test d'abord pour votre « nouvelle » fonctionnalité. N'ayez pas peur de casser des choses. Tant que les tests réussissent, vous devriez vous en sortir sans problème.

    Je dois mentionner maintenant que l'inférence de types paresseuse est vraiment bonne car elle n'infère que ce qui doit être inféré. Toutes les instructions et tous les modules qui ne sont pas utilisés sont simplement ignorés.

    Valeurs d'inférence (inference/base_value.py)

    Les vérifications de flux ne sont pas vraiment matures. Il n'y a qu'une vérification pour isinstance. Elle vérifierait si un flux a la forme if isinstance(a, type_or_tuple). Malheureusement, tout le reste est ignoré (par exemple, a == '' serait facile à vérifier -> a est une chaîne de caractères). Il y a un grand potentiel dans ces vérifications.

    Tests d'Intégration (run.py)

    Jedi est principalement testé par ce que j'appellerais des « tests d'intégration ». Ces tests vérifient l'inférence de type avec l'API publique. Cela a beaucoup de sens pour Jedi. De plus, il est difficile d'écrire des doctests/unittests pour les structures de données internes.

    Il existe différents types de tests :

    • completions / inférence #?
    • goto: #!
    • références : #<

    Comment exécuter les tests ?

    La plupart des cas de tests d'intégration se trouvent dans le répertoire test/completion et chaque cas de test commence par l'un de ces commentaires :

    • #? (completions / inférence)
    • #! (goto)
    • #< (références)

    Il existe également une prise en charge des bibliothèques tierces. Lors d'une exécution de test normale, elles ne sont pas exécutées, vous devez fournir une option --thirdparty.

    En plus des options -k et -m de pytest, vous pouvez utiliser l'option -T (--test-files`) pour spécifier quels cas de test doivent être exécutés. Elle prend le format ``FILE_NAME[:LINE[,LINE[,...]]] où FILE_NAME est un fichier dans test/completion et LINE est un numéro de ligne du commentaire de test. Voici quelques exemples :

    Exécuter les tests uniquement dans completion/basic.py et completion/imports.py :

    pytest test/test_integration.py -T basic.py -T imports.py

    Exécuter les tests aux lignes 4, 6 et 8 dans completion/basic.py :

    pytest test/test_integration.py -T basic.py:4,6,8

    Voir pytest --help pour plus d'informations.

    Si vous souhaitez déboguer un test, utilisez simplement l'option --pdb.

    Exécuteur de Tests Alternatif

    Si vous n'aimez pas la sortie de pytest, il existe un exécuteur de tests alternatif que vous pouvez démarrer en exécutant ./run.py. L'exemple ci-dessus pourrait être exécuté par :

    ./run.py basic 4 6 8 50-80

    L'avantage de cet exécuteur est sa simplicité et des rapports d'erreurs plus personnalisés.

    Tests d'Auto-Complétion

    Utilise un commentaire pour spécifier un test sur la ligne suivante. Le commentaire définit les complétions attendues. Le commentaire commence toujours par #?. La dernière ligne symbolise le curseur. Par exemple :

    #? ['upper']
a = 'foo'; a.upp

    Tests d'Inférence

    Les tests d'inférence se ressemblent beaucoup. La différence est que les tests d'inférence n'utilisent pas de parenthèses :

    #? int()
ab = 3; ab

    Tests de Goto

    Les tests Goto ressemblent à ceci :

    abc = 1
#! ['abc=1']
abc

    De plus, il est possible de spécifier la colonne en ajoutant un nombre, qui décrit la position du test (sinon, c'est juste la fin de la ligne) :

    #! 2 ['abc=1']
abc

    Tests de Références

    Les tests ressemblent à ceci :

    abc = 1
#< (1,0), (3,0)
abc

    Tests de Refactorisation (refactor.py)

    Les tests de refactorisation fonctionnent un peu comme les tests d'intégration. Mais l'idée est ici de comparer deux versions de code. Si vous souhaitez ajouter un nouveau cas de test, regardez les cas existants dans le dossier test/refactor et copiez-les.

    Un peu d'histoire

    Écrit par Dave.

    Mais en réalité, le nom n'a pas grand-chose à voir avec Star Wars. C'est une partie de mon deuxième prénom, Jedidjah.

    J'ai commencé Jedi en 2012, car il n'existait pas de bonnes solutions pour VIM. La plupart des solutions d'auto-complétion ne fonctionnaient tout simplement pas bien. La seule bonne solution était PyCharm. Mais j'aimais beaucoup mon bon vieux VIM. Il existait également une solution appelée Rope qui n'a pas du tout fonctionné pour moi. J'ai donc décidé d'écrire ma propre version d'un moteur de complétion.

    La première idée était d'exécuter du code non dangereux. Mais j'ai vite compris que cela ne fonctionnerait pas. J'ai donc commencé à construire un outil d'analyse statique. Le plus gros problème que j'ai eu à l'époque était que je ne savais rien des analyseurs syntaxiques. Je ne connaissais même pas le mot analyse statique. Il s'avère qu'ils sont le fondement d'un bon outil d'analyse statique. Je ne le savais pas bien sûr et j'ai essayé d'écrire ma propre version médiocre d'un analyseur syntaxique que j'ai fini par jeter deux ans plus tard.

    En raison de mon manque de connaissances, tout ce qui s'est passé entre 2012 et 2020 a essentiellement été du refactoring. J'ai réécrit les parties centrales de Jedi probablement 5 à 10 fois. La dernière grosse réécriture (que j'ai faite deux fois) a été l'inclusion du typage progressif et des stubs.

    J'ai appris à cette époque qu'il est crucial d'avoir une bonne compréhension de son problème. Sinon, on finit par le refaire. Je n'ai écrit que des fonctionnalités au début et à la fin. Tout le reste était de la correction de bugs et du refactoring. Cependant, maintenant je suis vraiment satisfait du résultat. Cela fonctionne bien, les corrections de bugs peuvent être rapides et c'est à peu près complet en termes de fonctionnalités.
