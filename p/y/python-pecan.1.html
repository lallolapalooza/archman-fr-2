NOM

pecan - Documentation Pecan

Pecan a été créé pour combler une lacune dans le monde des frameworks web Python – un framework très léger qui fournit un routage de style « object-dispatch ». Pecan ne vise pas à être un framework « full stack », et par conséquent n'inclut aucun support prêt à l'emploi pour des éléments tels que les sessions ou les bases de données (bien que des tutoriels soient inclus pour intégrer ceux-ci vous-même en quelques lignes de code seulement). Pecan se concentre plutôt sur HTTP lui-même.

Bien qu'il soit léger, Pecan offre un ensemble de fonctionnalités étendu pour construire des applications basées sur HTTP, notamment :

  • Dispatch d'objets pour un routage facile
  • Support complet des contrôleurs de style REST
  • Framework de sécurité extensible
  • Support extensible des langages de templating
  • Support JSON extensible
  • Configuration facile basée sur Python

INSTALLATION

Version stable

$ virtualenv pecan-env
$ cd pecan-env
$ source bin/activate

Les commandes ci-dessus créent un environnement virtuel et l' activent. Cela isolera les installations des dépendances de Pecan de vos paquets système, facilitant le débogage si nécessaire.

Ensuite, installons Pecan :

$ pip install pecan

Version de développement (instable)

Si vous souhaitez exécuter la dernière version de développement de Pecan, vous devrez installer git et cloner le dépôt depuis GitHub :

$ git clone https://github.com/pecan/pecan.git

En supposant que votre environnement virtuel soit toujours activé, appelez setup.py pour installer la version de développement :

$ cd pecan
$ python setup.py develop

La branche de développement master est volatile et n' est généralement pas recommandée pour une utilisation en production.

Alternativement, vous pouvez également installer directement depuis GitHub avec pip :

$ pip install -e git://github.com/pecan/pecan.git#egg=pecan

La racine de l'application

Le contrôleur racine est le point d'entrée de votre application. Vous pouvez le considérer comme analogue au chemin racine de l'URL de votre application (dans notre cas, http://localhost:8080/).

Voici à quoi il ressemble dans le modèle de projet (test_project.controllers.root.RootController) :

from pecan import expose
from webob.exc import status_map
class RootController(object):
    @expose(generic=True, template='index.html')
    def index(self):
        return dict()
    @index.when(method='POST')
    def index_post(self, q):
        redirect('https://pecan.readthedocs.io/en/latest/search.html?q=%s' % q)
    @expose('error.html')
    def error(self, status):
        try:
            status = int(status)
        except ValueError:
            status = 0
        message = getattr(status_map.get(status), 'explanation', '')
        return dict(status=status, message=message)

Notez que la méthode index() retourne un dictionnaire Python. Ce dictionnaire est utilisé comme espace de noms pour rendre le modèle spécifié (index.html) en HTML, et c'est le principal mécanisme par lequel les données sont transmises du contrôleur au modèle.

@index.when(method='POST')
def index_post(self, q):
    redirect('https://pecan.readthedocs.io/en/latest/search.html?q=%s' % q)

La méthode index_post() reçoit un argument POST HTTP (q). Comme l'argument method de @index.when() a été défini sur 'POST', toute requête POST HTTP à la racine de l'application (dans le projet d'exemple, une soumission de formulaire) sera acheminée vers cette méthode.

        status = int(status)
    except ValueError:
        status = 0
    message = getattr(status_map.get(status), 'explanation', '')
    return dict(status=status, message=message)

Enfin, nous avons la méthode error(), qui permet à l'application d'afficher des pages personnalisées pour certaines erreurs HTTP (404, etc.).

CONTRÔLEURS ET ROUTAGE

Pecan utilise une stratégie de routage appelée dispatch d'objet pour mapper une requête HTTP à un contrôleur, puis à la méthode à appeler. Le dispatch d'objet commence par diviser le chemin en une liste de composants, puis parcourt un chemin d'objet, en partant du contrôleur racine. Vous pouvez imaginer les contrôleurs de votre application comme un arbre d'objets (les branches de l'arbre d'objets correspondent directement aux chemins d'URL).

Regardons une application simple de librairie :

from pecan import expose
class BooksController(object):
    @expose()
    def index(self):
        return "Welcome to book section."
    @expose()
    def bestsellers(self):
        return "We have 5 books in the top 10."
class CatalogController(object):
    @expose()
    def index(self):
        return "Welcome to the catalog."
    books = BooksController()
class RootController(object):
    @expose()
    def index(self):
        return "Welcome to store.example.com!"
    @expose()
    def hours(self):
        return "Open 24/7 on the web."
    catalog = CatalogController()

Une requête pour /catalog/books/bestsellers de la librairie en ligne commencerait par Pecan décomposant la requête en catalog, books et bestsellers. Ensuite, Pecan rechercherait catalog sur le contrôleur racine. En utilisant l'objet catalog, Pecan rechercherait ensuite books, suivi de bestsellers. Que se passe-t-il si l'URL se termine par une barre oblique ? Pecan vérifiera la méthode index sur le dernier objet contrôleur.

Pour illustrer davantage, les chemins suivants :

└── /
    ├── /hours
    └── /catalog
         └── /catalog/books
            └── /catalog/books/bestsellers

sont acheminés vers les méthodes de contrôleur suivantes :

└── RootController.index
    ├── RootController.hours
    └── CatalogController.index
         └── BooksController.index
            └── BooksController.bestsellers

Exposition des contrôleurs

Vous indiquez à Pecan quelles méthodes d'une classe sont publiquement visibles via expose(). Si une méthode n'est *pas* décorée avec expose(), Pecan ne lui acheminera jamais de requête.

expose() peut être utilisé de diverses manières. Le cas le plus simple consiste à ne pas passer d'arguments. Dans ce scénario, le contrôleur retourne une chaîne représentant le corps de la réponse HTML.

from pecan import expose
class RootController(object):
    @expose()
    def hello(self):
        return 'Hello World'

Un cas d'utilisation plus courant consiste à *spécifier un modèle et un espace de noms* :

from pecan import expose
class RootController(object):
    @expose('html_template.mako')
    def hello(self):
        return {'msg': 'Hello!'}
<!-- html_template.mako -->
<html>
    <body>${msg}</body>
</html>

Pecan prend également en charge nativement un rendeur JSON spécial, qui traduit les espaces de noms des modèles en texte JSON rendu :

from pecan import expose
class RootController(object):
    @expose('json')
    def hello(self):
        return {'msg': 'Hello!'}

Les appels à expose() peuvent également être empilés, ce qui vous permet de sérialiser le contenu différemment en fonction de la manière dont il est demandé :

from pecan import expose
class RootController(object):
    @expose('json')
    @expose('text_template.mako', content_type='text/plain')
    @expose('html_template.mako')
    def hello(self):
        return {'msg': 'Hello!'}

Vous remarquerez que nous avons appelé expose() trois fois, avec des arguments différents.

@expose('json')

La première indique à Pecan de sérialiser l'espace de noms de réponse en utilisant la sérialisation JSON lorsque le client demande /hello.json ou si un en-tête Accept: application/json est présent.

@expose('text_template.mako', content_type='text/plain')

La seconde indique à Pecan d'utiliser le fichier de modèle text_template.mako lorsque

le client demande /hello.txt ou demande `text/plain` via un en-tête Accept.

@expose('html_template.mako')

Le troisième indique à Pecan d'utiliser le fichier de modèle html_template.mako lorsque le client demande /hello.html. Si le client demande /hello, Pecan utilisera le type de contenu text/html par défaut ; en l'absence d'un type de contenu explicite, Pecan suppose que le client souhaite du HTML.

Spécifier des segments de chemin explicites

Parfois, vous voudrez utiliser un segment de chemin dans votre routage qui ne fonctionne pas avec l'approche déclarative de Pecan en raison des restrictions de la syntaxe Python. Par exemple, si vous vouliez router pour un chemin qui inclut des tirets, comme /some-path/, ce qui suit n'est *pas* un Python valide :

class RootController(object):
    @pecan.expose()
    def some-path(self):
        return dict()

Pour contourner cela, Pecan vous permet de spécifier un segment de chemin explicite dans le décorateur expose() :

class RootController(object):
    @pecan.expose(route='some-path')
    def some_path(self):
        return dict()

Dans cet exemple, l'application Pecan répondra avec un HTTP 200 aux requêtes adressées à /some-path/, mais les requêtes adressées à /some_path/ entraîneront un HTTP 404.

route() peut également être utilisé explicitement comme alternative à l'argument route dans expose() :

class RootController(object):
    @pecan.expose()
    def some_path(self):
        return dict()
pecan.route('some-path', RootController.some_path)

Le routage vers des sous-contrôleurs peut être géré de manière similaire en utilisant route() :

class ChildController(object):
    @pecan.expose()
    def child(self):
        return dict()
class RootController(object):
    pass
pecan.route(RootController, 'child-path', ChildController())

Dans cet exemple, l'application Pecan répondra avec un HTTP 200 aux requêtes adressées à /child-path/child/.

Routage basé sur la méthode de requête

L'argument generic pour expose() permet de surcharger les URL en fonction de la méthode de requête. Dans l'exemple suivant, la même URL peut être desservie par deux méthodes différentes (une pour gérer le GET HTTP, une autre pour le POST HTTP) en utilisant des contrôleurs génériques :

from pecan import expose
class RootController(object):
    # HTTP GET /
    @expose(generic=True, template='json')
    def index(self):
        return dict()
    # HTTP POST /
    @index.when(method='POST', template='json')
    def index_POST(self, **kw):
        uuid = create_something()
        return dict(uuid=uuid)

Algorithme de routage de Pecan

Parfois, le routage standard par dispatch d'objets n'est pas adéquat pour router correctement une URL vers un contrôleur. Pecan fournit plusieurs moyens de court-circuiter le système de dispatch d'objets pour traiter les URL avec plus de contrôle, y compris les méthodes spéciales _lookup(), _default() et _route(). Définir ces méthodes sur vos objets contrôleurs offre une flexibilité supplémentaire pour traiter tout ou partie d'une URL.

Routage vers les sous-contrôleurs avec _lookup

La méthode spéciale _lookup() offre un moyen de traiter une partie d'une URL, puis de retourner un nouvel objet contrôleur vers lequel router pour le reste.

Une méthode _lookup() peut accepter un ou plusieurs arguments, segments du chemin de l'URL à traiter (séparés par /). _lookup() doit également accepter des arguments positionnels variables représentant le reste du chemin, et elle doit inclure toute partie du chemin qu'elle ne traite pas dans sa valeur de retour. L'exemple ci-dessous utilise une liste *remainder qui sera transmise au contrôleur retourné lorsque l'algorithme de dispatch d'objets continuera.

En plus d'être utilisée pour créer des contrôleurs dynamiquement, _lookup() est appelée en dernier recours, lorsqu'aucune autre méthode de contrôleur ne correspond à l'URL et qu'il n'y a pas de méthode _default().

from pecan import expose, abort
from somelib import get_student_by_name
class StudentController(object):
    def __init__(self, student):
        self.student = student
    @expose()
    def name(self):
        return self.student.name
class RootController(object):
    @expose()
    def _lookup(self, primary_key, *remainder):
        student = get_student_by_primary_key(primary_key)
        if student:
            return StudentController(student), remainder
        else:
            abort(404)

Une requête GET HTTP vers /8/name retournerait le nom de l'étudiant où primary_key == 8.

Replier avec _default

La méthode _default() est appelée en dernier recours lorsqu'aucune autre méthode de contrôleur ne correspond à l'URL via le dispatch d'objets standard.

from pecan import expose
class RootController(object):
    @expose()
    def english(self):
        return 'hello'
    @expose()
    def french(self):
        return 'bonjour'
    @expose()
    def _default(self):
        return 'Je ne peux pas dire bonjour dans cette langue'

Dans l'exemple ci-dessus, une requête à /spanish serait routée vers RootController._default().

Définir un routage personnalisé avec _route

La méthode _route() permet à un contrôleur de remplacer complètement le mécanisme de routage de Pecan. Pecan utilise lui-même la méthode _route() pour implémenter son RestController. Si vous souhaitez concevoir un système de routage alternatif basé sur Pecan, définir une classe de base contrôleur qui définit une méthode _route() vous permettra d'avoir un contrôle total.

INTERAGIR AVEC LES OBJETS DE REQUÊTE ET DE RÉPONSE

Pour chaque requête HTTP, Pecan maintient une référence locale au thread vers les objets de requête et de réponse, pecan.request et pecan.response. Ce sont des instances de pecan.Request et pecan.Response, respectivement, et elles peuvent être manipulées depuis le code du contrôleur Pecan :

@pecan.expose()
def login(self):
    assert pecan.request.path == '/login'
    username = pecan.request.POST.get('username')
    password = pecan.request.POST.get('password')
    pecan.response.status = 403
    pecan.response.text = 'Mauvaise connexion !'

Bien que Pecan abstrait une grande partie de la nécessité d'interagir directement avec ces objets, il peut y avoir des situations où vous souhaitez y accéder, telles que :

  • Inspecter les composants de l'URI
  • Déterminer des aspects de la requête, tels que l'adresse IP de l'utilisateur ou l'en-tête referer
  • Définir des en-têtes de réponse spécifiques
  • Rendre manuellement le corps de la réponse

Spécifier une réponse personnalisée

Définissez un code de réponse HTTP spécifique (tel que 203 Non Authoritative Information) en modifiant l'attribut status de l'objet de réponse.

from pecan import expose, response
class RootController(object):
    @expose('json')
    def hello(self):
        response.status = 203
        return {'foo': 'bar'}

Utilisez la fonction utilitaire abort() pour lever des erreurs HTTP.

from pecan import expose, abort
class RootController(object):
    @expose('json')
    def hello(self):
        abort(404)

abort() lève une instance de WSGIHTTPException qui est utilisée par Pecan pour rendre des corps de réponse par défaut pour les erreurs HTTP. Cette exception est stockée dans l'environnement de requête WSGI à pecan.original_exception, où elle peut être accédée plus tard dans le cycle de requête (par exemple, par d'autres middlewares ou des Documents d'erreur personnalisés).

Si vous souhaitez retourner une réponse explicite, vous pouvez le faire en utilisant Response :

from pecan import expose, Response
class RootController(object):
    @expose()
    def hello(self):
        return Response('Bonjour, Monde !', 202)

Étendre les objets de requête et de réponse de Pecan

Les implémentations de requête et de réponse fournies par WebOb sont puissantes, mais parfois, il peut être utile d'ajouter un comportement spécifique à l'application à votre requête et réponse (comme une analyse spécialisée des en-têtes de requête ou une sérialisation personnalisée du corps de réponse). Pour ce faire, définissez des classes personnalisées qui héritent de pecan.Request et pecan.Response, respectivement :

class MyRequest(pecan.Request):
    pass
class MyResponse(pecan.Response):
    pass

et modifiez la configuration de votre application pour les utiliser :

from myproject import MyRequest, MyResponse
app = {
    'root' : 'project.controllers.root.RootController',
    'modules' : ['project'],
    'static_root'   : '%(confdir)s/public',
    'template_path' : '%(confdir)s/project/templates',
    'request_cls': MyRequest,
    'response_cls': MyResponse
}

CONTROLLERS AND ROUTING

Mapping Arguments de Contrôleur

Dans Pecan, les variables HTTP GET et POST qui ne sont pas consommées pendant le processus de routage peuvent être transmises à la méthode du contrôleur en tant qu'arguments.

En fonction de la signature de la méthode, ces arguments peuvent être mappés explicitement à des arguments :

from pecan import expose
class RootController(object):
    @expose()
    def index(self, arg):
        return arg
    @expose()
    def kwargs(self, **kwargs):
        return str(kwargs)
$ curl http://localhost:8080/?arg=foo
foo
$ curl http://localhost:8080/kwargs?a=1&b=2&c=3
{u'a': u'1', u'c': u'3', u'b': u'2'}

ou peuvent être consommés positionnellement :

from pecan import expose
class RootController(object):
    @expose()
    def args(self, *args):
        return ','.join(args)
$ curl http://localhost:8080/args/one/two/three
one,two,three

Le même effet peut être obtenu avec les variables du corps de la requête POST HTTP :

from pecan import expose
class RootController(object):
    @expose()
    def index(self, arg):
        return arg
$ curl -X POST "http://localhost:8080/" -H "Content-Type: application/x-www-form-urlencoded" -d "arg=foo"
foo

Service de Fichiers Statiques

Pecan vous donne un accès direct à l'objet Request sous-jacent, servir un téléchargement de fichier statique est aussi simple que de définir la app_iter WSGI et de spécifier le type de contenu :

import os
from random import choice
from webob.static import FileIter
from pecan import expose, response
class RootController(object):
    @expose(content_type='image/gif')
    def gifs(self):
        filepath = choice((
            "/path/to/funny/gifs/catdance.gif",
            "/path/to/funny/gifs/babydance.gif",
            "/path/to/funny/gifs/putindance.gif"
        ))
        f = open(filepath, 'rb')
        response.app_iter = FileIter(f)
        response.headers[
            'Content-Disposition'
        ] = 'attachment; filename="%s"' % os.path.basename(f.name)

Si vous ne connaissez pas le type de contenu à l'avance (par exemple, si vous récupérez des fichiers et leurs types de contenu à partir d'une base de données), vous pouvez le spécifier via response.headers plutôt que dans le décorateur expose() :

import os
from mimetypes import guess_type
from webob.static import FileIter
from pecan import expose, response
class RootController(object):
    @expose()
    def download(self):
        f = open('/path/to/some/file', 'rb')
        response.app_iter = FileIter(f)
        response.headers['Content-Type'] = guess_type(f.name)
        response.headers[
            'Content-Disposition'
        ] = 'attachment; filename="%s"' % os.path.basename(f.name)

Détermination de l'URL d'un Contrôleur

Étant donné la capacité de routage à être radicalement modifiée à l'exécution, il n'est pas toujours possible de déterminer correctement un mappage entre une méthode de contrôleur et une URL.

Par exemple, dans le code suivant qui utilise _lookup() pour modifier le routage en fonction d'une condition :

from pecan import expose, abort
from somelib import get_user_region
class DefaultRegionController(object):
    @expose()
    def name(self):
        return "Default Region"
class USRegionController(object):
    @expose()
    def name(self):
        return "US Region"
class RootController(object):
    @expose()
    def _lookup(self, user_id, *remainder):
        if get_user_region(user_id) == 'us':
            return USRegionController(), remainder
        else:
            return DefaultRegionController(), remainder

Cette logique dépend de la géolocalisation d'un utilisateur donné et renvoie une classe complètement différente en fonction de la condition. Une fonction d'aide pour déterminer à quelle URL appartient USRegionController.name échouerait à le faire correctement.

ÉCRIRE DES SERVICES WEB RESTFUL AVEC DES CONTRÔLEURS GÉNÉRIQUES

Pecan simplifie les services web RESTful en fournissant un moyen de surcharger les URL en fonction de la méthode de requête. Pour la plupart des API, l'utilisation de définitions de contrôleurs génériques vous donne tout ce dont vous avez besoin pour construire des interfaces RESTful robustes (et est l'approche recommandée pour écrire des services web RESTful dans Pecan) :

from pecan import expose
from pecan.rest import RestController
from mymodel import Book
class BooksController(RestController):
    @expose()
    def get(self, id):
        book = Book.get(id)
        if not book:
            abort(404)
        return book.title

Nidification de RestController

Les instances de RestController peuvent être imbriquées afin que les ressources enfant reçoivent les paramètres nécessaires pour rechercher les ressources parentes.

Par exemple :

from pecan import expose
from pecan.rest import RestController
from mymodel import Author, Book
class BooksController(RestController):
    @expose()
    def get(self, author_id, id):
        author = Author.get(author_id)
        if not author_id:
            abort(404)
        book = author.get_book(id)
        if not book:
            abort(404)
        return book.title
class AuthorsController(RestController):
    books = BooksController()
    @expose()
    def get(self, id):
        author = Author.get(id)
        if not author:
            abort(404)
        return author.name
class RootController(object):
    authors = AuthorsController()

L'accès à /authors/1/books/2 invoque BooksController.get() avec author_id défini sur 1 et id défini sur 2.

Pour déterminer quels arguments sont associés à la ressource parente, Pecan examine les signatures des méthodes get_one() puis get(), dans cet ordre, dans le contrôleur parent. Si la ressource parente accepte un nombre variable d'arguments, Pecan lui passera tout jusqu'au nom du contrôleur de la ressource enfant (par exemple, books dans l'exemple ci-dessus).

Définir des actions personnalisées

En plus des méthodes par défaut définies ci-dessus, vous pouvez ajouter des comportements supplémentaires à un RestController en définissant un dictionnaire spécial _custom_actions.

Par exemple :

from pecan import expose
from pecan.rest import RestController
from mymodel import Book
class BooksController(RestController):
    _custom_actions = {
        'checkout': ['POST']
    }
    @expose()
    def checkout(self, id):
        book = Book.get(id)
        if not book:
            abort(404)
        book.checkout()

_custom_actions mappe les noms de méthodes à la liste des verbes HTTP valides pour ces actions personnalisées. Dans ce cas, checkout() prend en charge POST.

CONFIGURER LES APPLICATIONS PECAN

Pecan est très facile à configurer. Tant que vous suivez certaines conventions, l'utilisation, la définition et la gestion de la configuration devraient être très intuitives.

Les fichiers de configuration de Pecan sont en Python pur. Chaque "section" de la configuration est un dictionnaire attribué à un nom de variable dans le module de configuration.

Valeurs par défaut

Ci-dessous se trouve la liste complète des valeurs par défaut utilisées par le framework :

Une configuration d'application typique pourrait ressembler à ceci :

app = {
    'root' : 'project.controllers.root.RootController',
    'modules' : ['project'],
    'static_root'   : '%(confdir)s/public',
    'template_path' : '%(confdir)s/project/templates',

Examinons chaque valeur et sa signification :

modules
Une liste de modules dans lesquels pecan recherchera les applications. Généralement, cela devrait contenir un seul élément, le nom du package python de votre projet. Au moins un des modules listés doit contenir une fonction app.setup_app qui est appelée pour créer l'application WSGI. En d'autres termes, ce package doit être l'endroit où se trouve votre fichier app.py, et ce fichier doit contenir une fonction setup_app.
root
Le contrôleur racine de votre application. N'oubliez pas de fournir une chaîne représentant un chemin Python vers un appelable (par exemple, "yourapp.controllers.root.RootController").
static_root
Le répertoire où se trouvent vos fichiers statiques (par rapport à la racine du projet). Pecan est livré avec un middleware qui peut être utilisé pour servir des fichiers statiques (comme les fichiers CSS et Javascript) pendant le développement.
template_path
Pointe vers le répertoire où résident vos fichiers de modèle (par rapport à la racine du projet).
debug
Active la capacité d'afficher les traces dans le navigateur et de déboguer interactivement pendant le développement.

SÉCURITÉ ET AUTHENTIFICATION

Pecan ne fournit aucun support intégré pour l'authentification, mais il vous donne les outils nécessaires pour gérer l'authentification et l'autorisation comme bon vous semble.

Bases du décorateur secure

Vous pouvez envelopper des sous-arbres de contrôleurs entiers ou des appels de méthodes individuels avec des contrôles d'accès à l'aide du décorateur secure().

Pour décorer une méthode, utilisez un argument :

secure('<nom_méthode_vérification_permissions>')

Pour sécuriser une classe, appelez avec deux arguments :

secure(objet_instance, '<nom_méthode_vérification_permissions>')
from pecan import expose
from pecan.secure import secure
class HighlyClassifiedController(object):
    pass
class UnclassifiedController(object):
    pass
class RootController(object):
    @classmethod
    def check_permissions(cls):
        if user_is_admin():
            return True
        return False
    @expose()
    def index(self):
      #
      # Ce contrôleur est déverrouillé pour tout le monde,
      # et n'effectuera aucune vérification de sécurité.
      #
      return dict()
    @secure('check_permissions')
    @expose()
    def topsecret(self):
        #
        # Ce contrôleur est top-secret, et ne devrait
        # être accessible qu'aux administrateurs.
        #
        return dict()
    highly_classified = secure(HighlyClassifiedController(), 'check_permissions')
    unclassified = UnclassifiedController()

SecureController

Alternativement, la même fonctionnalité peut également être réalisée en héritant de SecureController de Pecan. Les implémentations de SecureController doivent étendre la méthode de classe check_permissions() pour renvoyer True si l'utilisateur a des permissions sur la branche du contrôleur et False s'il ne les a pas.

from pecan import expose
from pecan.secure import SecureController, unlocked
class HighlyClassifiedController(object):
    pass
class UnclassifiedController(object):
    pass
class RootController(SecureController):
    @classmethod
    def check_permissions(cls):
        if user_is_admin():
            return True
        return False
    @expose()
    @unlocked
    def index(self):
      #
      # Ce contrôleur est déverrouillé pour tout le monde,
      # et n'effectuera aucune vérification de sécurité.
      #
      return dict()
    @expose()
    def topsecret(self):
        #
        # Ce contrôleur est top-secret, et devrait
        # être accessible uniquement aux administrateurs.
        #
        return dict()
    highly_classified = HighlyClassifiedController()
    unclassified = unlocked(UnclassifiedController())

Notez également l'utilisation du décorateur unlocked() dans l'exemple ci-dessus, qui peut être utilisé de manière similaire pour déverrouiller explicitement un contrôleur pour un accès public sans aucune vérification de sécurité.

Écriture de méthodes d'authentification/autorisation

La méthode check_permissions() doit être utilisée pour déterminer l'authentification et l'autorisation de l'utilisateur. Le code que vous implémentez ici peut aller de simples assertions de session (l'utilisateur existant est authentifié en tant qu'administrateur) à la connexion à un service LDAP.

Plus sur secure

La méthode secure() a plusieurs utilisations avancées qui vous permettent de créer des politiques de sécurité robustes pour votre application.

Premièrement, vous pouvez passer via une chaîne le nom d'une méthode de classe ou d'une méthode d'instance du contrôleur à utiliser comme méthode check_permissions(). Les méthodes d'instance sont particulièrement utiles si vous souhaitez autoriser l'accès aux attributs d'une instance de modèle. Considérez le suivi

SÉCURITÉ

Les contrôleurs sécurisés sont un moyen de restreindre l'accès à certaines parties de votre application. Si une requête est faite pour une partie protégée de votre application, et que l'utilisateur n'est pas autorisé à y accéder, une erreur 403 sera renvoyée.

Vous pouvez utiliser le décorateur secure() pour marquer des méthodes spécifiques comme étant protégées. Par exemple:

from pecan import expose
from pecan.secure import secure
from myapp.session import get_current_user
from myapp.model import FileObject
class FileController(object):
    def __init__(self, name):
        self.file_object = FileObject(name)
    def read_access(self):
        self.file_object.read_access(get_current_user())
    def write_access(self):
        self.file_object.write_access(get_current_user())
    @secure('write_access')
    @expose()
    def upload_file(self):
        pass
    @secure('read_access')
    @expose()
    def download_file(self):
        pass
class RootController(object):
    @expose()
    def _lookup(self, name, *remainder):
        return FileController(name), remainder

La méthode secure() accepte également un argument de fonction. Lorsque vous passez une fonction, assurez-vous qu'elle est importée d'un autre fichier ou définie dans le même fichier avant la définition de la classe, sinon vous obtiendrez probablement une erreur lors de l'importation du module.

from pecan import expose
from pecan.secure import secure
from myapp.auth import user_authenitcated
class RootController(object):
    @secure(user_authenticated)
    @expose()
    def index(self):
        return 'Logged in'

Vous pouvez également utiliser la méthode secure() pour modifier le comportement d'un SecureController. Le décorer d'une méthode ou l'envelopper dans un sous-contrôleur indique à Pecan d'utiliser une fonction de sécurité autre que la méthode de contrôleur par défaut. Ceci est utile dans les situations où vous souhaitez un niveau ou un type de sécurité différent.

from pecan import expose
from pecan.secure import SecureController, secure
from myapp.auth import user_authenticated, admin_user
class ApiController(object):
    pass
class RootController(SecureController):
    @classmethod
    def check_permissions(cls):
        return user_authenticated()
    @classmethod
    def check_api_permissions(cls):
        return admin_user()
    @expose()
    def index(self):
        return 'logged in user'
    api = secure(ApiController(), 'check_api_permissions')

Dans l'exemple ci-dessus, pecan appellera uniquement admin_user() lorsqu'une requête sera faite pour /api/.

Contrôleurs Sécurisés Multiples

Les contrôleurs sécurisés peuvent être imbriqués pour fournir des niveaux de sécurité croissants sur les sous-contrôleurs. Dans l'exemple ci-dessous, lorsqu'une requête est faite pour /admin/index/, Pecan appelle d'abord check_permissions() sur le RootController, puis appelle check_permissions() sur le AdminController.

from pecan import expose
from pecan.secure import SecureController
from myapp.auth import user_logged_in, is_admin
class AdminController(SecureController):
    @classmethod
    def check_permissions(cls):
        return is_admin()
    @expose()
    def index(self):
        return 'admin dashboard'
class RootController(SecureController):
    @classmethod
    def check_permissions(cls):
        return user_logged_in
    @expose()
    def index(self):
        return 'user dashboard'

HOOKS DE PECAN

Bien qu'il soit facile d'utiliser des middleware WSGI avec Pecan, il peut être difficile (parfois impossible) d'accéder aux internes de Pecan à partir de middleware. Les Hooks Pecan sont un moyen d'interagir avec le framework, sans avoir à écrire de middleware séparé.

Les hooks vous permettent d'exécuter du code à des points clés tout au long du cycle de vie de votre requête :

  • on_route() : appelé avant que Pecan n'essaie de router une requête vers un contrôleur
  • before() : appelé après le routage, mais avant que le code du contrôleur ne soit exécuté
  • after() : appelé après que le code du contrôleur a été exécuté
  • on_error() : appelé lorsqu'une requête génère une exception

Implémentation d'un Hook Pecan

Dans l'exemple ci-dessous, un hook simple collectera des informations sur la requête et les affichera sur stdout.

Votre implémentation de hook doit importer PecanHook pour pouvoir l'utiliser comme classe de base. À partir de là, vous voudrez redéfinir les méthodes on_route(), before(), after() ou on_error() pour définir le comportement.

from pecan.hooks import PecanHook
class SimpleHook(PecanHook):
    def before(self, state):
        print "\nabout to enter the controller..."
    def after(self, state):
        print "\nmethod: \t %s" % state.request.method
        print "\nresponse: \t %s" % state.response.status

on_route(), before(), et after() reçoivent chacun un objet d'état partagé qui comprend des informations utiles, telles que les objets de requête et de réponse, et quel contrôleur a été sélectionné par le routage de Pecan :

class SimpleHook(PecanHook):
    def on_route(self, state):
        print "\nabout to map the URL to a Python method (controller)..."
        assert state.controller is None  # Routing hasn't occurred yet
        assert isinstance(state.request, webob.Request)
        assert isinstance(state.response, webob.Response)
        assert isinstance(state.hooks, list)  # A list of hooks to apply
    def before(self, state):
        print "\nabout to enter the controller..."
        if state.request.path == '/':
            #
            # `state.controller` is a reference to the actual
            # `@pecan.expose()`-ed controller that will be routed to
            # and used to generate the response body
            #
            assert state.controller.__func__ is RootController.index.__func__
            assert isinstance(state.arguments, inspect.Arguments)
            print state.arguments.args
            print state.arguments.varargs
            print state.arguments.keywords
        assert isinstance(state.request, webob.Request)
        assert isinstance(state.response, webob.Response)
        assert isinstance(state.hooks, list)

on_error() reçoit un objet d'état partagé et l'exception d'origine. Si un gestionnaire on_error() retourne un objet Response, cette réponse sera retournée à l'utilisateur final et aucun autre hook on_error() ne sera exécuté :

class CustomErrorHook(PecanHook):
    def on_error(self, state, exc):
        if isinstance(exc, SomeExceptionType):
            return webob.Response('Custom Error!', status=500)

Attacher les Hooks

Les hooks peuvent être attachés de manière globale au projet en spécifiant une liste de hooks dans le fichier de configuration de votre projet.

app = {
    'root' : '...'
    # ...
    'hooks': lambda: [SimpleHook()]
}

Les hooks peuvent également être appliqués sélectivement aux contrôleurs et à leurs sous-contrôleurs en utilisant l'attribut __hooks__ sur un ou plusieurs contrôleurs et en héritant de HookController.

from pecan import expose
from pecan.hooks import HookController
from my_hooks import SimpleHook
class SimpleController(HookController):
    __hooks__ = [SimpleHook()]
    @expose('json')
    def index(self):
        print "DO SOMETHING!"
        return dict()

Les hooks peuvent être hérités des classes parentes ou des mixins. Assurez-vous simplement d'hériter de HookController.

from pecan import expose
from pecan.hooks import PecanHook, HookController
class ParentHook(PecanHook):
    priority = 1
    def before(self, state):
        print "\nabout to enter the parent controller..."
class CommonHook(PecanHook):
    priority = 2
    def before(self, state):
        print "\njust a common hook..."
class SubHook(PecanHook):
    def before(self, state):
        print "\nabout to enter the subcontroller..."
class SubMixin(object):
    __hooks__ = [SubHook()]
# We'll use the same instance for both controllers,
# to avoid double calls
common = CommonHook()
class SubController(HookController, SubMixin):
    __hooks__ = [common]
    @expose('json')
    def index(self):
        print "\nI AM THE SUB!"
        return dict()
class RootController(HookController):
    __hooks__ = [common, ParentHook()]
    @expose('json')
    def index(self):
        print "\nI AM THE ROOT!"
        return dict()
    sub = SubController()

Voyons ce qui se passe lorsque nous exécutons l'application. D'abord en chargeant le contrôleur racine :

pecan serve config.py
serving on 0.0.0.0:8080 view at http://127.0.0.1:8080
GET / HTTP/1.1" 200
about to enter the parent controller...
just a common hook
I AM THE ROOT!

Puis en chargeant le sous-contrôleur :

pecan serve config.py
serving on 0.0.0.0:8080 view at http://127.0.0.1:8080
GET /sub HTTP/1.1" 200
about to enter the parent controller...
just a common hook
about to enter the subcontroller...
I AM THE SUB!

NOTE :

Assurez-vous de définir les bonnes valeurs de priorité pour les hooks imbriqués afin qu'ils soient exécutés dans l'ordre souhaité.

AVERTISSEMENT :

Deux hooks du même type seront ajoutés/exécutés deux fois, s'ils sont passés comme instances différentes à un contrôleur parent et enfant. S'ils sont passés comme une seule variable d'instance, ils seront appelés une fois pour les deux contrôleurs.

RequestViewerHook

Ce hook est utile à des fins de débogage. Il a accès à tous les attributs de l'objet response ainsi qu'à quelques autres spécifiques au framework.

Configuration de RequestViewerHook

Il existe plusieurs façons de configurer et d'exécuter correctement ce crochet. Cependant, il est utile de savoir qu'aucune configuration réelle n'est nécessaire pour qu'il soit opérationnel.

Par défaut, il affichera des informations sur les éléments suivants :

  • path : Affiche l'URL utilisée pour générer cette réponse
  • status : La réponse du serveur (par exemple, '200 OK')
  • method : La méthode de la requête (par exemple, 'GET', 'POST', 'PUT ou 'DELETE')

  • hooks : Tous les crochets utilisés dans l'application seront listés ici.

La configuration par défaut affichera ces valeurs dans le terminal via stdout et les ajoutera également aux en-têtes de réponse (sous la forme de X-Pecan-item_name).

Blacklisting de Certains Chemins

Il est parfois agaçant d'obtenir des informations sur chaque requête. Pour limiter la sortie, passez la liste des chemins d'URL pour lesquels vous ne souhaitez pas de données sous le nom de blacklist.

SERVEUR JSON

Pecan comprend un système simple et facile à utiliser pour générer et servir du JSON. Pour commencer, créez un fichier dans votre projet appelé json.py et importez-le dans le app.py de votre projet.

Votre module json contiendra une série de règles pour générer du JSON à partir des objets que vous retournez dans votre contrôleur.

Supposons que nous ayons un contrôleur dans notre application Pecan que nous voulons utiliser pour retourner une sortie JSON pour un objet User :

from myproject.lib import get_current_user
class UsersController(object):
    @expose('json')
    def current_user(self):
        '''
        retourne une instance de myproject.model.User qui représente
        l'authentification actuelle

JSONifier

Pecan, by default, will attempt to convert your controller's return values into JSON when the content type is set to JSON. It does this via the jsonify decorator and related utilities.

In order for this controller to function, Pecan will need to know how to convert the User object into data types compatible with JSON. One way to tell Pecan how to convert an object into JSON is to define a rule in your json.py:

from pecan.jsonify import jsonify
from myproject import model
@jsonify.register(model.User)
def jsonify_user(user):
    return dict(
        name = user.name,
        email = user.email,
        birthday = user.birthday.isoformat()
    )

In this example, when an instance of the model.User class is returned from a controller which is configured to return JSON, the jsonify_user() rule will be called to convert the object to JSON-compatible data. Note that the rule does not generate a JSON string, but rather generates a Python dictionary which contains only JSON friendly data types.

Alternatively, the rule can be specified on the object itself, by specifying a __json__() method in the class:

class User(object):
    def __init__(self, name, email, birthday):
        self.name = name
        self.email = email
        self.birthday = birthday
    def __json__(self):
        return dict(
            name = self.name,
            email = self.email,
            birthday = self.birthday.isoformat()
        )

The benefit of using a json.py module is having all of your JSON rules defined in a central location, but some projects prefer the simplicity of keeping the JSON rules attached directly to their model objects.

CONTEXT/THREAD-LOCALS VS. PASSAGE EXPLICITE D'ARGUMENTS

Dans n'importe quelle application Pecan, les objets de niveau module pecan.request et pecan.response sont des objets proxy qui font toujours référence à la requête et à la réponse traitées dans le thread courant.

Cette localité de thread garantit que vous pouvez accéder en toute sécurité à une référence globale de la requête et de la réponse en cours dans un environnement multithreadé sans avoir à passer constamment des références d'objets dans votre code ; c'est une fonctionnalité de Pecan qui rend l'écriture d'applications Web traditionnelles plus facile et moins verbeuse.

Certains estiment que les locals de thread sont trop implicites ou magiques, et que le passage explicite de références est beaucoup plus clair et plus facile à maintenir à long terme. De plus, l'implémentation par défaut fournie par Pecan utilise threading.local() pour associer ces objets proxy locaux au contexte à l'identifiant de thread du thread serveur courant. Dans les modèles de serveurs asynchrones - où de nombreuses tâches s'exécutent pendant de courtes périodes sur un seul thread partagé - le support de ce mécanisme implique le monkeypatching de threading.local() pour qu'il se comporte de manière locale aux greenlets.

Désactivation des Proxies Locaux de Thread

Si vous êtes certain de ne pas vouloir utiliser les locaux de contexte/thread dans votre projet, vous pouvez le faire en passant l'argument use_context_locals=False dans le fichier de configuration de votre application :

app = {
    'root': 'project.controllers.root.RootController',
    'modules': ['project'],
    'static_root': '%(confdir)s/public',
    'template_path': '%(confdir)s/project/templates',
    'debug': True,
    'use_context_locals': False
}

De plus, vous devrez mettre à jour tous vos contrôleurs Pecan pour qu'ils acceptent des arguments positionnels pour la requête et la réponse actuelles :

class RootController(object):
    @pecan.expose('json')
    def index(self, req, resp):
        return dict(method=req.method) # path: /
    @pecan.expose()
    def greet(self, req, resp, name):
        return name  # path: /greet/joe

Il est impératif que les arguments de requête et de réponse viennent après self et avant tout argument positionnel.

Écriture d'une Commande Pecan Personnalisée

À titre d'exemple, créons une commande qui peut être utilisée pour émettre une requête GET HTTP simulée à votre application et afficher le résultat. Son invocation depuis la ligne de commande pourrait ressembler à ceci :

$ pecan wget config.py /path/to/some/resource

Disons que vous avez une distribution avec un package nommé myapp, et qu'à l'intérieur de ce package se trouve un b

>wget.py module :

# myapp/myapp/wget.py
import pecan
from webtest import TestApp
class GetCommand(pecan.commands.BaseCommand):
    '''
    Émet une requête GET (simulée) et retourne le corps de la requête.
    '''
    arguments = pecan.commands.BaseCommand.arguments + ({
        'name': 'path',
        'help': 'le chemin URI de la ressource à demander'
    },)
    def run(self, args):
        super(GetCommand, self).run(args)
        app = TestApp(self.load_app())
        print app.get(args.path).body

Analysons ceci morceau par morceau.

Remplacement de la méthode run

Premièrement, nous héritons de BaseCommand et étendons la méthode run() pour :

  • Charger une application Pecan - load_app()
  • L'encapsuler dans un faux environnement WSGI - TestApp
  • Émettre une requête GET HTTP à son encontre - get()

Définition d'arguments personnalisés

L'attribut de classe arguments est utilisé pour définir les arguments de ligne de commande spécifiques à votre commande personnalisée. Vous remarquerez dans cet exemple que nous ajoutons à la liste d'arguments fournie par BaseCommand (qui fournit déjà un argument pour le config_file), plutôt que de la remplacer entièrement.

$ pecan -h
usage: pecan [-h] command ...
positional arguments:
  command
    wget        Émet une requête GET (simulée) et retourne le corps de la requête
    serve       Ouvre un shell interactif avec l'application Pecan chargée
    ...
$ pecan wget -h
usage: pecan wget [-h] config_file path
$ pecan wget config.py /path/to/some/resource

De plus, vous remarquerez que la première ligne de la docstring de GetCommand - Émet une requête GET (simulée) et retourne le corps de la requête - est automatiquement utilisée pour décrire la commande wget dans la sortie de $ pecan -h. Suivre cette convention vous permet d'intégrer facilement un résumé pour votre commande dans l'outil de ligne de commande Pecan.

Enregistrement d'une commande personnalisée

Maintenant que vous avez écrit votre commande personnalisée, vous devrez en informer le setup.py de votre distribution et le réinstaller. Dans le fichier setup.py de votre distribution, vous trouverez un appel à setup().

# myapp/setup.py
...
setup(
    name='myapp',
    version='0.1',
    author='Joe Somebody',
    ...
)

En supposant qu'il n'existe pas déjà, nous ajouterons l'argument entry_points à l'appel setup() et définirons une entrée [pecan.command] pour votre commande personnalisée :

# myapp/setup.py
...

    name='myapp',
    version='0.1',
    author='Joe Somebody',
    ...
    entry_points="""
    [pecan.command]
    wget = myapp.wget:GetCommand
    """
)

Une fois que vous avez fait cela, réinstallez votre projet en mode développement pour enregistrer le nouveau point d'entrée.

$ python setup.py develop

Ensuite, essayez.

$ pecan wget config.py /path/to/some/resource

import os
import cherrypy
from cheroot import wsgi
from cheroot.wsgi import PathInfoDispatcher
from pecan.deploy import deploy
simpleapp_wsgi_app = deploy('/chemin/vers/production_config.py')
public_path = os.path.abspath(os.path.join(os.path.dirname(__file__), 'public'))
# Une classe factice pour notre objet Root
# nécessaire pour certains mécanismes CherryPy
class Root(object):
    pass
def make_static_config(static_dir_name):
    """
    Toutes les configurations statiques personnalisées sont définies ici, comme la plupart sont communes,
    il est logique de les générer une seule fois.
    """
    static_path = os.path.join('/', static_dir_name)
    path = os.path.join(public_path, static_dir_name)
    configuration = {
        static_path: {
            'tools.staticdir.on': True,
            'tools.staticdir.dir': path
        }
    }
    return cherrypy.tree.mount(Root(), '/', config=configuration)
# En supposant que votre application dispose de médias sur différents chemins, comme 'css' et 'images'
application = PathInfoDispatcher({
    '/': simpleapp_wsgi_app,
    '/css': make_static_config('css'),
    '/images': make_static_config('images')
})
server = wsgi.Server(('0.0.0.0', 8080), application, server_name='simpleapp')
try:
    server.start()
except KeyboardInterrupt:
    print("Arrêt du serveur...")
    server.stop()

    # myapp/myapp/controllers/root.py
from pecan import expose
class RootController(object):
    @expose('index.html')
    def index(self, name='Joe'):

    class TestIndex(FunctionalTest):
    def test_index(self):
        resp = self.app.get('/')
        assert resp.status_int == 200
        assert 'Bonjour, Joe !' in resp.body

    def test_index(self):
        resp = self.app.get('/')
        assert resp.status_int == 200
        assert resp.namespace == {'name': 'Joe'}
        assert resp.template_name == 'index.html'

    Liaison au sein de l'Application

    Il existe plusieurs approches pour encapsuler les requêtes de votre application avec des appels aux fonctions de modèle appropriées. Une approche est le middleware WSGI. Nous recommandons également les Hooks Pecan. Pecan est livré avec TransactionHook, un hook qui peut être utilisé pour encapsuler les requêtes dans des transactions de base de données pour vous. Pour l'utiliser, incluez-le simplement dans le fichier app.py de votre projet et passez-lui un ensemble de fonctions liées à la liaison de base de données.

    from pecan import conf, make_app
from pecan.hooks import TransactionHook
from test_project import model
app = make_app(
    conf.app.root,
    static_root     = conf.app.static_root,
    template_path   = conf.app.template_path,
    debug           = conf.app.debug,
    hooks           = [
        TransactionHook(
            model.start,
            model.start_read_only,
            model.commit,
            model.rollback,
            model.clear
        )
    ]
)

    Dans l'exemple ci-dessus, lors des requêtes HTTP POST, PUT et DELETE, TransactionHook s'occupe de la transaction automatiquement en suivant ces règles :

    1.
    Avant que le routage du contrôleur ne soit déterminé, model.start() est appelé. Cette fonction doit se lier au moteur SQLAlchemy approprié et démarrer une transaction.
    2.
    Le code du contrôleur est exécuté et retourne.
    3.
    Si votre contrôleur ou le rendu du modèle échoue et lève une exception, model.rollback() est appelé et l'exception d'origine est relancée. Cela vous permet d'annuler votre transaction de base de données pour éviter de valider le travail lorsque des exceptions surviennent dans le code de votre application.
    4.
    Si le contrôleur retourne avec succès, model.commit() et model.clear() sont appelés.

    Lors des opérations idempotentes (comme les requêtes HTTP GET et HEAD), TransactionHook gère les transactions en suivant des règles différentes.

    1.
    model.start_read_only() est appelé. Cette fonction doit se lier à votre moteur SQLAlchemy.
    2.
    Le code du contrôleur est exécuté et retourne.
    3.
    Si le contrôleur retourne avec succès, model.clear() est appelé.

    Notez également qu'il existe un décorateur utile after_commit() fourni dans pecan.decorators -- Décorateurs Pecan.

    Séparation des Lectures et Écritures

    L'utilisation de la stratégie ci-dessus avec TransactionHook rend très simple la séparation des lectures et écritures de base de données en fonction des méthodes HTTP (c'est-à-dire, les requêtes GET/HEAD sont en lecture seule et seraient potentiellement routées vers un esclave de base de données en lecture seule, tandis que les requêtes POST/PUT/DELETE nécessitent des écritures et se lieraient toujours à une base de données maître avec des privilèges de lecture/écriture). Il est également possible d'étendre TransactionHook ou d'écrire votre propre implémentation de hook pour un contrôle plus affiné sur où et quand les liaisons de base de données sont appelées.

    En supposant une configuration maître/standby, où le maître accepte les requêtes d'écriture et le standby ne peut recevoir que des requêtes de lecture, une configuration Pecan pour SQLAlchemy pourrait être :

    # Spécification du Serveur
    ific Configurations server = { ... } # Configurations de l'application Pecan app = { ... } # Base de données maître sqlalchemy_w = { 'url': 'postgresql+psycopg2://root:@master_host/dbname', 'pool_recycle': 3600, 'encoding': 'utf-8' } # Base de données en lecture seule sqlalchemy_ro = { 'url': 'postgresql+psycopg2://root:@standby_host/dbname', 'pool_recycle': 3600, 'encoding': 'utf-8' }

    Compte tenu des paramètres de configuration uniques pour chaque base de données, les liaisons devraient changer par rapport à ce que le quickstart par défaut de Pecan fournit (voir la section init_model et Préparation de votre modèle) pour prendre en charge à la fois les requêtes en écriture et en lecture seule :

    from pecan import conf
from sqlalchemy import create_engine, MetaData
from sqlalchemy.orm import scoped_session, sessionmaker
Session = scoped_session(sessionmaker())
metadata = MetaData()
def init_model():
    conf.sqlalchemy_w.engine = _engine_from_config(conf.sqlalchemy_w)
    conf.sqlalchemy_ro.engine = _engine_from_config(conf.sqlalchemy_ro)
def _engine_from_config(configuration):
    configuration = dict(configuration)
    url = configuration.pop('url')
    return create_engine(url, **configuration)
def start():
    Session.bind = conf.sqlalchemy_w.engine
    metadata.bind = conf.sqlalchemy_w.engine
def start_read_only():
    Session.bind = conf.sqlalchemy_ro.engine
    metadata.bind = conf.sqlalchemy_ro.engine
def commit():
    Session.commit()
def rollback():
    Session.rollback()
def clear():
    Session.close()
def flush():
    Session.flush()

    DOCUMENTS D'ERREUR PERSONNALISÉS

    Dans cet article, nous allons configurer une application Pecan pour afficher une page d'erreur personnalisée chaque fois que le serveur renvoie un statut 404 Page Not Found.

    Cet article suppose que vous avez déjà créé une application de test comme décrit dans Créer votre première application Pecan.

    NOTE :

    Bien que cet exemple se concentre sur le message HTTP 404, la même technique peut être appliquée pour définir des actions personnalisées pour tous les codes de statut de réponse HTTP dans la plage 400 et 500. Il est fortement conseillé d'utiliser ce pouvoir avec discernement.

    Aperçu

    Pecan simplifie la personnalisation des documents d'erreur en deux étapes simples :

    • Configurer le routage des messages d'état HTTP que vous souhaitez gérer dans le fichier config.py de votre application
    • Écrire des contrôleurs personnalisés pour gérer les messages d'état que vous avez configurés

    Configurer le routage

    Configurerons notre application test_project pour router les messages HTTP 404 Page Not Found vers un contrôleur personnalisé.

    Tout d'abord, mettons à jour test_project/config.py pour spécifier un nouveau gestionnaire d'erreurs.

    # Configurations de l'application Pecan
app = {
    'root'            : 'test_project.controllers.root.RootController',
    'modules'         : ['test_project'],
    'static_root'     : '%(confdir)s/public',
    'template_path'   : '%(confdir)s/test_project/templates',
    'reload'          : True,
    'debug'           : True,
    # modifier la clé 'errors' pour diriger les codes de statut HTTP vers un
    # contrôleur personnalisé
    'errors'          : {
        #404           : '/error/404',
        404           : '/notfound',
        '__force_dict__' : True
    }
}

    Au lieu de la page d'erreur par défaut, Pecan routera maintenant les messages 404 vers la méthode du contrôleur notfound.

    Écrire des contrôleurs personnalisés

    Le moyen le plus simple d'implémenter le gestionnaire d'erreurs est de l'ajouter à la classe test_project.root.RootController (généralement dans test_project/controllers/root.py).

    from pecan import expose
from webob.exc import status_map
class RootController(object):
    @expose(generic=True, template='index.html')
    def index(self):
        return dict()
    @index.when(method='POST')
    def index_post(self, q):
        redirect('https://pecan.readthedocs.io/en/latest/search.html?q=%s' % q)
    ## gestion personnalisée des messages '404 Page Not Found'
    @expose('error.html')
    def notfound(self):
        return dict(status=404, message="test_project does not have this page")
    @expose('error.html')
    def error(self, status):
        try:
            status = int(status)
        except ValueError:
            status = 0
        message = getattr(status_map.get(status), 'explanation', '')
        return dict(status=status, message=message)

    Et c'est tout !

    Notez que le seul morceau de code que nous avons ajouté à notre RootController était :

    ## gestion personnalisée des messages '404 Page Not Found'
@expose('error.html')
def notfound(self):
    return dict(status=404, message="test_project does not have this page")

    Nous avons simplement exposé() le contrôleur notfound avec le modèle error.html (qui a été créé de manière pratique pour nous et placé sous test_project/templates/ lorsque nous avons créé test_project). Comme pour tout contrôleur Pecan, nous renvoyons un dictionnaire de variables pour l'interpolation par le moteur de rendu de modèle.

    Nous pouvons maintenant modifier le modèle d'erreur, ou en écrire un tout nouveau pour rendre la page d'état d'erreur 404 de test_project aussi jolie ou fantaisiste que nous le souhaitons.

Ceci est particulièrement utile pour les segments de chemin qui ne sont pas des identifiants Python valides (tels que les segments de chemin incluant certains caractères de ponctuation, comme /some/~path~/).
    • Ajout d'une nouvelle option de configuration, app.debugger, qui permet aux développeurs de spécifier un débogueur alternatif à pdb (par exemple, ipdb) lors du débogage interactif avec DebugMiddleware de pecan.

      • Il est maintenant possible de définir le niveau de journalisation sur DEBUG pour le développement.

      • Correction d'un bug de décodage dans la manière dont pecan gère certains segments de chemin d'URL et chaînes de requête cités.
      • Correction de plusieurs bugs dans la manière dont pecan gère les segments de chemin Unicode (par exemple, vous pouvez maintenant définir des routes pecan contenant des caractères emoji).
      • Correction de plusieurs bugs dans RestController qui le faisaient retourner HTTP 404 Not Found plutôt que HTTP 405 Method Not Allowed. De plus, RestController retourne maintenant des en-têtes Allow valides lorsque HTTP 405 Method Not Allowed est retourné.
      • Correction d'un bug qui permettait aux méthodes spéciales de pecan (_route, _lookup, _default) d'être marquées comme méthodes REST génériques.
      • Mise en évidence accrue dans la documentation de pecan du besoin de debug=False dans les déploiements de production.

    • Les requêtes HTTP POST sont composées de données non Unicode.
    • Les chemins de requête contiennent des caractères mal encodés en pourcentage, par exemple /some/path/%aa/.

    • Correction d'un bug qui empêchait les contrôleurs @exposed d'utiliser @staticmethod.
    • Correction d'un bug mineur dans le calcul des arguments du contrôleur.

      NOM

      python-pecan - Une bibliothèque Python pour le web

      SYNOPIS

      python-pecan

      DESCRIPTION

      Pecan est une petite bibliothèque Web Python. Elle est inspirée de Sinatra et de Cuba, qui sont des micro-frameworks Web pour Ruby et Python, respectivement. Pecan est très léger et fournit un moyen rapide et facile de construire des applications Web.

      CARACTÉRISTIQUES

      • Léger et rapide
      • Simple à utiliser
      • Extensible
      • S'intègre bien avec d'autres bibliothèques Python

      INSTALLATION

      Vous pouvez installer Pecan en utilisant pip :

      pip install pecan

      UTILISATION

      Voici un exemple simple d'application Web Pecan :

      from pecan import expose

@expose()
def index():
    return "Bonjour le monde!"

# Pour exécuter cette application, enregistrez-la dans un fichier (par exemple, app.py)
# et exécutez la commande suivante dans votre terminal :
# pecan serve app.py
