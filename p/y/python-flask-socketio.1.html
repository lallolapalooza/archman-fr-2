INTRODUCTION

Installation

Vous pouvez installer ce paquet de la manière habituelle en utilisant pip :

pip install flask-socketio

Prérequis

Flask-SocketIO est compatible avec Python 3.6+. Les services asynchrones sur lesquels ce paquet repose peuvent être choisis parmi trois options :

  • eventlet est l'option la plus performante, avec un support pour les transports long-polling et WebSocket.
  • gevent est pris en charge dans plusieurs configurations différentes. Le transport long-polling est entièrement pris en charge avec le paquet gevent, mais contrairement à eventlet, gevent n'a pas de support WebSocket natif. Pour ajouter le support de WebSocket, il existe actuellement deux options. L'installation du paquet gevent-websocket ajoute le support WebSocket à gevent, ou l'on peut utiliser le serveur web uWSGI, qui intègre des fonctionnalités WebSocket. L'utilisation de gevent est également une option performante, mais légèrement inférieure à eventlet.
  • Le serveur de développement Flask basé sur Werkzeug peut également être utilisé, avec la mise en garde que ce serveur web est uniquement destiné à des fins de développement, il ne doit donc être utilisé que pour simplifier le flux de travail de développement et non pour la production.

L'extension détecte automatiquement quel framework asynchrone utiliser en fonction de ce qui est installé. La préférence est donnée à eventlet, suivi de gevent. Pour le support WebSocket dans gevent, uWSGI est préféré, suivi de gevent-websocket. Si ni eventlet ni gevent ne sont installés, alors le serveur de développement Flask est utilisé.

DÉMARRAGE RAPIDE

Initialisation

Le code d'exemple suivant montre comment ajouter Flask-SocketIO à une application Flask :

from flask import Flask, render_template
from flask_socketio import SocketIO
app = Flask(__name__)
app.config['SECRET_KEY'] = 'secret!'
socketio = SocketIO(app)
if __name__ == '__main__':
    socketio.run(app)

Le style d'initialisation init_app() est également pris en charge. Pour démarrer le serveur web, exécutez simplement votre script. Notez la manière dont le serveur web est démarré. La fonction socketio.run() encapsule le démarrage du serveur web et remplace le démarrage du serveur de développement Flask standard app.run(). Lorsque l'application est en mode débogage, le serveur de développement Werkzeug est toujours utilisé et correctement configuré dans socketio.run(). En mode production, le serveur web eventlet est utilisé s'il est disponible, sinon le serveur web gevent est utilisé. Si eventlet et gevent ne sont pas installés, le serveur web de développement Werkzeug est utilisé.

La commande flask run introduite dans Flask 0.11 peut être utilisée pour démarrer un serveur de développement Flask-SocketIO basé sur Werkzeug, mais cette méthode de démarrage du serveur Flask-SocketIO n'est pas recommandée en raison du manque de support WebSocket. Les versions précédentes de ce paquet incluaient une version personnalisée de la commande flask run qui permettait l'utilisation de WebSocket sur les serveurs de production eventlet et gevent, mais cette fonctionnalité a été abandonnée au profit de la méthode de démarrage socketio.run(app) présentée ci-dessus, qui est plus robuste.

Gestion des erreurs

Flask-SocketIO peut également gérer les exceptions :

@socketio.on_error()        # Gère l'espace de noms par défaut
def error_handler(e):
    pass
@socketio.on_error('/chat') # Gère l'espace de noms '/chat'
def error_handler_chat(e):
    pass
@socketio.on_error_default  # Gère tous les espaces de noms sans gestionnaire d'erreur explicite
def default_error_handler(e):
    pass

Les fonctions de gestion des erreurs prennent l'objet exception comme argument.

Les arguments message et data de la requête actuelle peuvent également être inspectés avec la variable request.event, ce qui est utile pour la journalisation des erreurs et le débogage en dehors du gestionnaire d'événement :

from flask import request
@socketio.on("mon événement d'erreur")
def on_my_event(data):
    raise RuntimeError()
@socketio.on_error_default
def default_error_handler(e):
    print(request.event["message"]) # "mon événement d'erreur"
    print(request.event["args"])    # (data,)

Débogage et dépannage

Pour vous aider à déboguer les problèmes, le serveur peut être configuré pour afficher des journaux dans le terminal :

socketio = SocketIO(logger=True, engineio_logger=True)

L'argument logger contrôle la journalisation liée au protocole Socket.IO, tandis que engineio_logger contrôle les journaux provenant du transport Engine.IO de bas niveau. Ces arguments peuvent être définis sur True pour afficher les journaux dans stderr, ou sur un objet compatible avec le package logging de Python où les journaux doivent être émis. Une valeur de False désactive la journalisation.

La journalisation peut aider à identifier la cause des problèmes de connexion, des réponses 400, des mauvaises performances et d'autres problèmes.

NOTES D'IMPLÉMENTATION

Accès aux globaux de contexte de Flask

Les gestionnaires d'événements SocketIO sont différents des gestionnaires de routes, ce qui crée beaucoup de confusion quant à ce qui peut et ne peut pas être fait dans un gestionnaire SocketIO. La principale différence est que tous les événements SocketIO générés pour un client se produisent dans le contexte d'une seule requête de longue durée.

Malgré les différences, Flask-SocketIO tente de faciliter le travail avec les gestionnaires d'événements SocketIO en rendant l'environnement similaire à celui d'une requête HTTP normale. La liste suivante décrit ce qui fonctionne et ce qui ne fonctionne pas :

  • Un contexte d'application est poussé avant d'appeler un gestionnaire d'événements, rendant current_app et g disponibles pour le gestionnaire.
  • Un contexte de requête est également poussé avant d'appeler un gestionnaire, rendant également request et session disponibles. Mais notez que les événements WebSocket n'ont pas de requêtes individuelles associées, donc le contexte de requête qui a initié la connexion est poussé pour tous les événements qui sont dispatchés pendant la durée de la connexion.
  • Le global du contexte request est enrichi d'un membre sid qui est défini sur un identifiant de session unique pour la connexion. Cette valeur est utilisée comme une salle initiale où le client est ajouté.
  • Le global du contexte request est enrichi des membres namespace et event qui contiennent l'espace de noms actuellement géré et les arguments de l'événement. Le membre event est un dictionnaire avec les clés message et args.
  • Le global du contexte session se comporte différemment que dans les requêtes normales. Une copie de la session utilisateur au moment où la connexion SocketIO est établie est mise à disposition des gestionnaires appelés dans le contexte de cette connexion. Si un gestionnaire SocketIO modifie la session, la session modifiée sera préservée pour les futurs gestionnaires SocketIO, mais les gestionnaires de routes réguliers ne verront pas ces changements. Effectivement, lorsqu'un gestionnaire SocketIO modifie la session, un « fork » de la session est créé exclusivement pour ces gestionnaires. La raison technique de cette limitation est que pour sauvegarder la session utilisateur, un cookie doit être envoyé au client, ce qui nécessite une requête et une réponse HTTP, qui n'existent pas dans une connexion SocketIO. Lorsque vous utilisez des sessions côté serveur, comme celles fournies par les extensions Flask-Session ou Flask-KVSession, les modifications apportées à la session dans les gestionnaires de routes HTTP peuvent être vues par les gestionnaires SocketIO, tant que la session n'est pas modifiée dans les gestionnaires SocketIO.
  • Les hooks before_request et after_request ne sont pas appelés pour les gestionnaires d'événements SocketIO.
  • Les gestionnaires SocketIO peuvent accepter des décorateurs personnalisés, mais la plupart des décorateurs Flask ne seront pas appropriés pour un gestionnaire SocketIO, étant donné qu'il n'y a pas de concept d'objet Response pendant une connexion SocketIO.

Authentification

Un besoin courant des applications est de valider l'identité de leurs utilisateurs. Les mécanismes traditionnels basés sur les formulaires web et les requêtes HTTP ne peuvent pas être utilisés dans une connexion SocketIO, car il n'y a pas d'endroit pour envoyer des requêtes et des réponses HTTP. Si nécessaire, une application peut implémenter un formulaire de connexion personnalisé qui envoie les identifiants au serveur sous forme de message SocketIO lorsque le bouton de soumission est pressé par l'utilisateur.

Cependant, dans la plupart des cas, il est plus pratique d'effectuer le processus d'authentification traditionnel avant que la connexion SocketIO ne soit établie. L'identité de l'utilisateur peut alors être enregistrée dans la session utilisateur ou dans un cookie, et plus tard, lorsque la connexion SocketIO est établie, ces informations seront accessibles aux gestionnaires d'événements SocketIO.

Les révisions récentes du protocole Socket.IO incluent la capacité de passer un dictionnaire avec des informations d'authentification lors de la connexion. C'est un endroit idéal pour que le client inclue un jeton ou d'autres détails d'authentification. Si le client utilise cette capacité, le serveur fournira ce dictionnaire comme argument au gestionnaire d'événement connect, comme montré ci-dessus.

Utilisation de Flask-Login avec Flask-SocketIO

@socketio.on('connect')
def connect_handler():
    if current_user.is_authenticated:
        emit('my response',
             {'message': '{0} a rejoint'.format(current_user.name)},
             broadcast=True)
    else:
        return False  # non autorisé ici

Notez que le décorateur login_required ne peut pas être utilisé avec les gestionnaires d'événements SocketIO, mais un décorateur personnalisé qui déconnecte les utilisateurs non authentifiés peut être créé comme suit :

import functools
from flask import request
from flask_login import current_user
from flask_socketio import disconnect, emit
def authenticated_only(f):
    @functools.wraps(f)
    def wrapped(*args, **kwargs):
        if not current_user.is_authenticated:
            disconnect()
        else:
            return f(*args, **kwargs)
    return wrapped
@socketio.on('my event')
@authenticated_only
def handle_my_custom_event(data):
    emit('my response', {'message': '{0} a rejoint'.format(current_user.name)},
         broadcast=True)

DÉPLOIEMENT

Il existe de nombreuses options pour déployer un serveur Flask-SocketIO, allant du simple à l'incroyablement complexe. Dans cette section, les options les plus couramment utilisées sont décrites.

Serveur embarqué

La stratégie de déploiement la plus simple consiste à démarrer le serveur web en appelant socketio.run(app) comme montré dans les exemples précédents. Cela recherchera dans les paquets installés le meilleur serveur web disponible et démarrera l'application dessus. Les choix actuels de serveurs web évalués sont eventlet, gevent et le serveur de développement Flask.

Si eventlet ou gevent sont disponibles, socketio.run(app) démarre un serveur prêt pour la production en utilisant l'un de ces frameworks. Si aucun des deux n'est installé, alors le serveur web de développement Flask est utilisé, et dans ce cas, le serveur n'est pas destiné à être utilisé dans un déploiement de production.

Malheureusement, cette option n'est pas disponible lors de l'utilisation de gevent avec uWSGI. Voir la section uWSGI ci-dessous pour des informations sur cette option.

Serveur web Gunicorn

gunicorn --worker-class eventlet -w 1 module:app

Si vous préférez utiliser gevent, la commande pour démarrer le serveur est :

gunicorn -k gevent -w 1 module:app

Les applications Web créées avec Flask-SocketIO nécessitent un serveur Web pour être exécutées dans un environnement de production. Le serveur Web doit prendre en charge le protocole WebSocket. Les options les plus courantes sont Gunicorn et uWSGI.

Serveur Web Gunicorn

gunicorn -w 1 --threads 100 module:app

Dans toutes ces commandes, module est le module ou le package Python qui définit l'instance de l'application, et app est l'instance de l'application elle-même.

En raison de l'algorithme de répartition de charge limité utilisé par gunicorn, il n'est pas possible d'utiliser plus d'un processus worker lorsque l'on utilise ce serveur Web. Pour cette raison, tous les exemples ci-dessus incluent l'option -w 1.

Serveur Web uWSGI

Lors de l'utilisation du serveur uWSGI en combinaison avec gevent, le serveur Socket.IO peut tirer parti de la prise en charge native de WebSocket par uWSGI.

Une explication complète de la configuration et de l'utilisation du serveur uWSGI dépasse le cadre de cette documentation. Le serveur uWSGI est un package assez complexe qui offre un large ensemble d'options complètes. Il doit être compilé avec la prise en charge de WebSocket et SSL pour que le transport WebSocket soit disponible. À titre d'introduction, la commande suivante démarre un serveur uWSGI pour l'application d'exemple app.py sur le port 5000 :

$ uwsgi --http :5000 --gevent 1000 --http-websockets --master --wsgi-file app.py --callable app

Utilisation de nginx comme proxy inverse WebSocket

Il est possible d'utiliser nginx comme proxy inverse frontal qui transmet les requêtes à l'application. Cependant, seules les versions 1.4 et plus récentes de nginx prennent en charge le proxy du protocole WebSocket. Ci-dessous une configuration nginx de base qui proxy les requêtes HTTP et WebSocket :

server {
    listen 80;
    server_name _;
    location / {
        include proxy_params;
        proxy_pass http://127.0.0.1:5000;
    }
    location /static/ {
        alias <path-to-your-application>/static/;
        expires 30d;
    }
    location /socket.io {
        include proxy_params;
        proxy_http_version 1.1;
        proxy_buffering off;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "Upgrade";
        proxy_pass http://127.0.0.1:5000/socket.io;
    }
}

L'exemple suivant ajoute la prise en charge de la répartition de charge pour plusieurs serveurs Socket.IO :

upstream socketio_nodes {
    ip_hash;
    server 127.0.0.1:5000;
    server 127.0.0.1:5001;
    server 127.0.0.1:5002;
    # pour mettre à l'échelle l'application, ajoutez simplement plus de nœuds ici !
}
server {
    listen 80;
    server_name _;
    location / {
        include proxy_params;
        proxy_pass http://127.0.0.1:5000;
    }
    location /static/ {
        alias <path-to-your-application>/static/;
        expires 30d;
    }
    location /socket.io {
        include proxy_params;

        proxy_buffering off;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "Upgrade";
        proxy_pass http://socketio_nodes/socket.io;
    }
}

Bien que les exemples ci-dessus puissent fonctionner comme configuration initiale, gardez à l'esprit qu'une installation de production de nginx nécessitera une configuration plus complète couvrant d'autres aspects de déploiement tels que la prise en charge SSL.

Utilisation de plusieurs workers

Flask-SocketIO prend en charge plusieurs workers derrière un répartiteur de charge à partir de la version 2.0. Le déploiement de plusieurs workers permet aux applications utilisant Flask-SocketIO de répartir les connexions clients entre plusieurs processus et hôtes, et ainsi de passer à l'échelle pour prendre en charge un très grand nombre de clients concurrents.

Il y a deux exigences pour utiliser plusieurs workers Flask-SocketIO :

  • Le répartiteur de charge doit être configuré pour transmettre toutes les requêtes HTTP d'un client donné toujours au même worker. Ceci est parfois appelé "sessions collantes". Pour nginx, utilisez la directive ip_hash pour y parvenir. Gunicorn ne peut pas être utilisé avec plusieurs workers car son algorithme de répartition de charge ne prend pas en charge les sessions collantes.
  • Comme chacun des serveurs ne possède qu'un sous-ensemble des connexions clients, une file de messages telle que Redis ou RabbitMQ est utilisée par les serveurs pour coordonner des opérations complexes telles que la diffusion et les salles.

Lors de l'utilisation d'une file de messages, des dépendances supplémentaires doivent être installées :

  • Pour Redis, le package redis doit être installé (pip install redis).
  • Pour RabbitMQ, le package kombu doit être installé (pip install kombu).
  • Pour Kafka, le package kafka-python doit être installé (pip install kafka-python).
  • Pour d'autres files de messages prises en charge par Kombu, consultez la documentation Kombu pour savoir quelles dépendances sont nécessaires.
  • Si eventlet ou gevent sont utilisés, alors le "monkey patching" de la bibliothèque standard Python est normalement requis pour forcer le package de file de messages à utiliser des fonctions et des classes compatibles avec les coroutines.

Pour eventlet, le "monkey patching" est effectué avec :

import eventlet
eventlet.monkey_patch()

Pour gevent, vous pouvez effectuer le "monkey patching" de la bibliothèque standard avec :

from gevent import monkey
monkey.patch_all()

Dans les deux cas, il est recommandé d'appliquer le "monkey patching" au début de votre script principal, même avant vos imports.

Pour démarrer plusieurs serveurs Flask-SocketIO, vous devez d'abord vous assurer que le service de file de messages est en cours d'exécution. Pour démarrer un serveur Socket.IO et le connecter à la file de messages, ajoutez l'argument message_queue au constructeur SocketIO :

socketio = SocketIO(app, message_queue='redis://')

La valeur de l'argument message_queue est l'URL de connexion du service de file d'attente utilisé. Pour une file Redis fonctionnant sur le même hôte que le serveur, l'URL 'redis://' peut être utilisée. De même, pour une file RabbitMQ par défaut, l'URL 'amqp://' peut être utilisée. Pour Kafka, utilisez une URL kafka://. Le package Kombu a une section documentation qui décrit le format des URLs pour toutes les files prises en charge.

Émission depuis un processus externe

Pour de nombreux types d'applications, il est nécessaire d'émettre des événements depuis un processus autre que le serveur SocketIO, par exemple un worker Celery. Si le ou les serveurs SocketIO sont configurés pour écouter sur une file de messages comme montré dans la section précédente, alors tout autre processus peut créer sa propre instance SocketIO et l'utiliser pour émettre des événements de la même manière que le serveur.

Par exemple, pour une application qui s'exécute sur un serveur Web eventlet et utilise une file de messages Redis, le script Python suivant diffuse un événement à tous les clients :

socketio = SocketIO(message_queue='redis://')
socketio.emit('my event', {'data': 'foo'}, namespace='/test')

Lors de l'utilisation de l'instance SocketIO de cette manière, l'instance de l'application Flask n'est pas passée au constructeur.

L'argument channel de SocketIO peut être utilisé pour sélectionner un canal de communication spécifique via la file de messages. L'utilisation d'un nom de canal personnalisé est nécessaire lorsqu'il existe plusieurs services SocketIO indépendants partageant la même file.

Flask-SocketIO n'applique pas le monkey patching lorsque eventlet ou gevent sont utilisés. Mais lors de l'utilisation d'une file de messages, il est très probable que le package Python qui communique avec le service de file de messages se bloque si la bibliothèque standard Python n'est pas patchée.

Il est important de noter qu'un processus externe souhaitant se connecter à un serveur SocketIO n'a pas besoin d'utiliser eventlet ou gevent comme le serveur principal. Avoir un serveur utilisant un framework de coroutine, tandis qu'un processus externe ne pose pas de problème. Par exemple, les workers Celery n'ont pas besoin d'être configurés pour utiliser eventlet ou gevent simplement parce que le serveur principal le fait. Mais si votre processus externe utilise un framework de coroutine pour une raison quelconque, alors le monkey patching est probablement nécessaire, afin que la file de messages accède à des fonctions et des classes compatibles avec les coroutines.

Contrôles inter-origines

Pour des raisons de sécurité, ce serveur applique par défaut une politique de même origine. En pratique, cela signifie ce qui suit :

  • Si une requête HTTP ou WebSocket entrante inclut l'en-tête Origin, cet en-tête doit correspondre au schéma et à l'hôte de l'URL de connexion. En cas de non-concordance, une réponse avec un code d'état 400 est renvoyée et la connexion est rejetée.
  • Aucune restriction n'est imposée aux requêtes entrantes qui n'incluent pas l'en-tête Origin.

Si nécessaire, l'option cors_allowed_origins peut être utilisée pour autoriser d'autres origines. Cet argument peut être défini sur une chaîne pour définir une seule origine autorisée, ou sur une liste pour autoriser plusieurs origines. Une valeur spéciale de '*' peut être utilisée pour indiquer au serveur d'autoriser toutes les origines, mais cela doit être fait avec précaution, car cela pourrait rendre le serveur vulnérable aux attaques de falsification de requêtes inter-sites (CSRF).

MISE À NIVEAU VERS FLASK-SOCKETIO 5.X À PARTIR DES VERSIONS 4.X

Le protocole Socket.IO a récemment introduit une série de changements incompatibles avec les versions précédentes. Les versions 5.x de Flask-SocketIO ont adopté ces changements et, pour cette raison, elles ne peuvent être utilisées qu'avec des clients qui ont également été mis à jour

au version actuelle du protocole. En particulier, cela signifie que le client JavaScript doit être mis à niveau vers une version 3.x, et si votre client n'a pas été mis à niveau vers la dernière version du protocole Socket.IO, alors vous devez utiliser une version 4.x de Flask-SocketIO.

Les changements de protocole suivants sont importants, car ils peuvent affecter les applications existantes :

  • Le namespace par défaut '/' n'est plus connecté automatiquement, et est maintenant traité de la même manière que les autres namespaces.
  • Chaque connexion de namespace a sa propre valeur sid, différente des autres et différente du sid d'Engine.IO.
  • Flask-SocketIO utilise maintenant les mêmes valeurs d'intervalle de ping et de timeout que l'implémentation de référence JavaScript, qui sont respectivement de 25 et 5 secondes.
  • Le mécanisme de ping/pong a été inversé. Dans la version actuelle du protocole, le serveur émet un ping et le client répond par un pong.
  • La taille de charge utile autorisée par défaut pour les paquets de long-polling a été réduite de 100 Mo à 1 Mo.
  • Le cookie io n'est plus envoyé au client par défaut.

classe flask_socketio.SocketIO(app=None, **kwargs)
Crée un serveur Flask-SocketIO.
Paramètres
  • app -- L'instance de l'application Flask. Si l'instance de l'application n'est pas connue au moment de l'instanciation de cette classe, appelez socketio.init_app(app) une fois que l'instance de l'application est disponible.
  • manage_session -- Si défini à True, cette extension gère la session utilisateur pour les événements Socket.IO. Si défini à False, la gestion de session propre à Flask est utilisée. Lors de l'utilisation de sessions basées sur des cookies de Flask, il est recommandé de laisser cette valeur à True par défaut. Lors de l'utilisation de sessions côté serveur, un réglage à False permet de partager la session utilisateur entre les routes HTTP et les événements Socket.IO.
  • message_queue -- Une URL de connexion pour un service de file de messages que le serveur peut utiliser pour la communication multi-processus. Une file de messages n'est pas requise lors de l'utilisation d'un seul processus serveur.
  • channel -- Le nom du canal, lors de l'utilisation d'une file de messages. Si un canal n'est pas spécifié, un canal par défaut sera utilisé. Si plusieurs clusters de processus SocketIO doivent utiliser la même file de messages sans interférer les uns avec les autres, chaque cluster doit utiliser un canal différent.
  • path -- Le chemin où le serveur Socket.IO est exposé. Par défaut : 'socket.io'. Laissez ceci tel quel à moins que vous ne sachiez ce que vous faites.
  • resource -- Alias pour path.
  • kwargs -- Options du serveur Socket.IO et Engine.IO.

Les options du serveur Socket.IO sont détaillées ci-dessous :

Paramètres
  • client_manager -- Le gestionnaire de clients qui gérera la liste des clients. Lorsque ceci est omis, la liste des clients est stockée dans une structure en mémoire, donc l'utilisation de plusieurs serveurs connectés n'est pas possible. Dans la plupart des cas, cet argument n'a pas besoin d'être défini explicitement.
  • logger -- Pour activer la journalisation, définissez sur True ou passez un objet logger à utiliser. Pour désactiver la journalisation, définissez sur False. La valeur par défaut est False. Notez que les erreurs fatales seront journalisées même lorsque logger est False.
  • json -- Un module json alternatif à utiliser pour l'encodage et le décodage des paquets. Les modules json personnalisés doivent avoir des fonctions dumps et loads compatibles avec les versions de la bibliothèque standard. Pour utiliser le même encodeur et décodeur json qu'une application Flask, utilisez flask.json.
  • async_handlers -- Si défini à True, les gestionnaires d'événements pour un client sont exécutés dans des threads séparés. Pour exécuter les gestionnaires d'un client de manière synchrone, définissez sur False. La valeur par défaut est True.
  • always_connect -- Lorsque défini à False, les nouvelles connexions sont provisoires jusqu'à ce que le gestionnaire de connexion retourne autre chose que False, auquel cas elles sont acceptées. Lorsque défini à True, les connexions sont immédiatement acceptées, puis si le gestionnaire de connexion retourne False, une déconnexion est émise. Définissez à True si vous avez besoin d'émettre des événements depuis le gestionnaire de connexion et que votre client est confus lorsqu'il reçoit des événements avant l'acceptation de la connexion. Dans tous les autres cas, utilisez la valeur par défaut de False.

La configuration du serveur Engine.IO prend en charge les paramètres suivants :

Paramètres
  • async_mode -- Le mode asynchrone à utiliser. Voir la section Déploiement de la documentation pour une description des options disponibles. Les modes asynchrones valides sont threading, eventlet, gevent et gevent_uwsgi. Si cet argument n'est pas fourni, eventlet est essayé en premier, puis gevent_uwsgi, puis gevent, et enfin threading. Le premier mode asynchrone pour lequel toutes les dépendances sont installées est alors choisi.
  • ping_interval -- L'intervalle en secondes auquel le serveur envoie un ping au client. La valeur par défaut est de 25 secondes. Pour un contrôle avancé, un tuple de deux éléments peut être donné, où le premier nombre est l'intervalle de ping et le second est un délai de grâce ajouté par le serveur.
  • ping_timeout -- Le temps en secondes que le client attend la réponse du serveur avant de se déconnecter. La valeur par défaut est de 5 secondes.
  • max_http_buffer_size -- La taille maximale d'un message lors de l'utilisation du transport de polling. La valeur par défaut est de 1 000 000 octets.
  • allow_upgrades -- Indique s'il faut autoriser les mises à niveau de transport ou non. La valeur par défaut est True.
  • http_compression -- Indique s'il faut compresser les paquets lors de l'utilisation du transport de polling. La valeur par défaut est True.
  • compression_threshold -- Compresser les messages uniquement lorsque leur taille en octets est supérieure à cette valeur. La valeur par défaut est de 1024 octets.
  • cookie -- Si défini à une chaîne de caractères, c'est le nom du cookie HTTP que le serveur renvoie au client contenant l'identifiant de session du client. Si défini à un dictionnaire, la clé 'name' contient le nom du cookie et les autres clés définissent les attributs du cookie, où la valeur de chaque attribut peut être une chaîne de caractères, une fonction appelable sans arguments, ou un booléen. Si défini à None (par défaut), un cookie n'est pas envoyé au client.
  • cors_allowed_origins -- L'origine ou la liste des origines autorisées à se connecter à ce serveur. Seule la même origine est autorisée par défaut. Définissez cet argument à '*' pour autoriser toutes les origines, ou à [] pour désactiver la gestion CORS.
  • cors_credentials -- Indique si les identifiants (cookies, authentification) sont autorisés dans les requêtes vers ce serveur. La valeur par défaut est True.
  • monitor_clients -- Si défini à True, une tâche d'arrière-plan garantira que les clients inactifs sont fermés. Définissez à False pour désactiver la tâche de surveillance (non recommandé). La valeur par défaut est True.
  • engineio_logger -- Pour activer la journalisation d'Engine.IO, définissez sur True ou passez un objet logger à utiliser. Pour désactiver la journalisation, définissez sur False. La valeur par défaut est False. Notez que les erreurs fatales sont journalisées même lorsque engineio_logger est False.

@socketio.event

emit(event, *args, **kwargs)
Émet un événement SocketIO généré par le serveur.

Cette fonction émet un événement SocketIO vers un ou plusieurs clients connectés. Un objet JSON peut être attaché à l'événement en tant que charge utile. Cette fonction peut être utilisée en dehors d'un contexte d'événement SocketIO, elle est donc appropriée à utiliser lorsque le serveur est l'origine d'un événement, en dehors de tout contexte client, comme dans un gestionnaire de requêtes HTTP régulier ou une tâche d'arrière-plan. @app.route('/ping')

  • args -- Un dictionnaire avec les données JSON à envoyer en tant que charge utile.
  • namespace -- L'espace de noms sous lequel le message doit être envoyé. La valeur par défaut est l'espace de noms global.
  • to -- Envoyer le message à tous les utilisateurs de la salle donnée, ou à l'utilisateur avec l'ID de session donné. Si ce paramètre n'est pas inclus, l'événement est envoyé à tous les utilisateurs connectés.

  • skip_sid -- L'identifiant de session d'un client à ignorer lors de la diffusion ou de l'adressage d'une salle. Il est généralement défini à l'origine du message, afin que tous sauf ce client reçoivent le message. Pour ignorer plusieurs sid, passez une liste.
  • callback -- Si fourni, cette fonction sera appelée pour accuser réception de la réception du message par le client. Les arguments qui seront passés à la fonction sont ceux fournis par le client. Les fonctions de rappel ne peuvent être utilisées que lors de l'adressage d'un client individuel.
call(event, *args, **kwargs)
Émet un événement SocketIO et attend la réponse.

Cette méthode émet un signal avec un rappel et attend que le rappel soit appelé par le client avant de retourner. Si le rappel n'est pas appelé avant le délai imparti, une exception TimeoutError est levée. Si la connexion Socket.IO est interrompue pendant l'attente, cette méthode attend toujours jusqu'à ce que le délai spécifié soit atteint. Exemple :

def get_status(client, data):
    status = call('status', {'data': data}, to=client)
Paramètres
  • event -- Le nom de l'événement utilisateur à émettre.
  • args -- Un dictionnaire avec les données JSON à envoyer en tant que charge utile.
  • namespace -- L'espace de noms sous lequel le message doit être envoyé. La valeur par défaut est l'espace de noms global.
  • to -- L'identifiant de session du client destinataire.
  • timeout -- Le délai d'attente. Si le délai est atteint avant que le client n'accuse réception de l'événement, une exception TimeoutError est levée. La valeur par défaut est de 60 secondes.
  • ignore_queue -- Utilisé uniquement lorsqu'une file d'attente de messages est configurée. Si défini à True, l'événement est émis directement au client, sans passer par la file d'attente. C'est plus efficace, mais cela ne fonctionne que lorsqu'un seul processus serveur est utilisé, ou lorsqu'il y a un seul destinataire. Il est recommandé de toujours laisser ce paramètre avec sa valeur par défaut de False.
