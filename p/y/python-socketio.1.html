Ce projet implémente des clients et des serveurs Socket.IO qui peuvent s'exécuter de manière autonome ou être intégrés à divers frameworks Web Python.

DÉMARRAGE

Qu'est-ce que Socket.IO ?

Socket.IO est un protocole de transport qui permet une communication bidirectionnelle événementielle en temps réel entre des clients (généralement, mais pas toujours, des navigateurs Web) et un serveur. Les implémentations officielles des composants client et serveur sont écrites en JavaScript. Ce package fournit des implémentations Python des deux, chacune avec des variantes standard et asyncio.

Compatibilité des versions

Le protocole Socket.IO a connu plusieurs révisions, et certaines d'entre elles ont introduit des changements incompatibles avec les versions précédentes, ce qui signifie que le client et le serveur doivent utiliser des versions compatibles pour que tout fonctionne.

Si vous utilisez le client et le serveur Python, le moyen le plus simple de garantir la compatibilité est d'utiliser la même version de ce package pour le client et le serveur. Si vous utilisez ce package avec un client ou un serveur différent, vous devez vous assurer que les versions sont compatibles.

Exemples de clients

L'exemple suivant montre un client Python simple :

import socketio
sio = socketio.Client()
@sio.event
def connect():
    print('connection established')
@sio.event
def my_message(data):
    print('message received with ', data)
    sio.emit('my response', {'response': 'my response'})
@sio.event
def disconnect():
    print('disconnected from server')
sio.connect('http://localhost:5000')
sio.wait()

Ci-dessous se trouve un client similaire, codé pour asyncio (Python 3.5+ uniquement) :

import asyncio
import socketio
sio = socketio.AsyncClient()
@sio.event
async def connect():
    print('connection established')
@sio.event
async def my_message(data):
    print('message received with ', data)
    await sio.emit('my response', {'response': 'my response'})
@sio.event
async def disconnect():
    print('disconnected from server')
async def main():
    await sio.connect('http://localhost:5000')
    await sio.wait()
if __name__ == '__main__':
    asyncio.run(main())

Fonctionnalités du client

  • Peut se connecter à d'autres serveurs Socket.IO compatibles avec le serveur de référence Socket.IO JavaScript.
  • Compatible avec Python 3.8+.
  • Deux versions du client, une pour Python standard et une autre pour asyncio.
  • Utilise une architecture événementielle implémentée avec des décorateurs qui masquent les détails du protocole.
  • Implémente les transports HTTP long-polling et WebSocket.
  • Se reconnecte automatiquement au serveur si la connexion est perdue.

app = socketio.WSGIApp(sio, static_files={
    '/': {'content_type': 'text/html', 'filename': 'index.html'}

    print('disconnect ', sid)
if __name__ == '__main__':
    eventlet.wsgi.server(eventlet.listen(('', 5000)), app)

Installation

Pour installer le client Python standard ainsi que ses dépendances, utilisez la commande suivante :

pip install "python-socketio[client]"

Si vous prévoyez plutôt d'utiliser le client asyncio, utilisez ceci :

pip install "python-socketio[asyncio_client]"

Utilisation du client simple

L'avantage du client simple est qu'il abstrait la logique nécessaire pour maintenir une connexion Socket.IO. Ce client gère les déconnexions et reconnexions de manière totalement transparente, sans ajouter de complexité à l'application.

Création d'une instance de client

La façon la plus simple de créer un client Socket.IO est d'utiliser l'interface de gestionnaire de contexte :

import socketio
# Python standard
with socketio.SimpleClient() as sio:
    # ... se connecter à un serveur et utiliser le client
    # ... pas besoin de déconnecter manuellement !
# asyncio
async with socketio.AsyncSimpleClient() as sio:
    # ... se connecter à un serveur et utiliser le client
    # ... pas besoin de déconnecter manuellement !

Avec cette utilisation, le gestionnaire de contexte garantira que le client est correctement déconnecté avant de quitter le bloc with ou async with.

Si vous préférez, un client peut être instancié manuellement :

import socketio
# Python standard
sio = socketio.SimpleClient()
# asyncio
sio = socketio.AsyncSimpleClient()

Connexion à un serveur

La connexion à un serveur est établie en appelant la méthode connect() :

sio.connect('http://localhost:5000')

Dans le cas du client asyncio, la méthode est une coroutine :

await sio.connect('http://localhost:5000')

Par défaut, le client se connecte d'abord au serveur en utilisant le transport long-polling, puis tente de mettre à niveau la connexion pour utiliser WebSocket. Pour se connecter directement en utilisant WebSocket, utilisez l'argument transports :

sio.connect('http://localhost:5000', transports=['websocket'])

Lors de la connexion, le serveur attribue au client un identifiant de session unique. L'application peut trouver cet identifiant dans l'attribut sid :

print('mon sid est', sio.sid)

Le transport Socket.IO utilisé dans la connexion peut être obtenu à partir de l'attribut transport :

print('mon transport est', sio.transport)

Le transport est donné sous forme de chaîne de caractères et peut être soit 'websocket', soit 'polling'.

Support TLS/SSL

Le client prend en charge les connexions TLS/SSL. Pour l'activer, utilisez une URL de connexion https:// :

sio.connect('https://example.com')

Ou lors de l'utilisation d'asyncio :

await sio.connect('https://example.com')

Le client vérifie les certificats du serveur par défaut. Consultez la documentation du client piloté par événements pour savoir comment personnaliser ce comportement.

Émission d'événements

Le client peut émettre un événement vers le serveur en utilisant la méthode emit() :

sio.emit('mon message', {'foo': 'bar'})

Ou dans le cas d'asyncio, en tant que coroutine :

await sio.emit('mon message', {'foo': 'bar'})

Les arguments fournis à la méthode sont le nom de l'événement à émettre et les données optionnelles qui sont transmises au serveur. Les données peuvent être de type str, bytes, dict, list ou tuple. Lors de l'envoi d'une list ou d'un tuple, les éléments qu'ils contiennent doivent être de n'importe quel type autorisé, à l'exception des tuples. Lorsqu'un tuple est utilisé, les éléments du tuple seront transmis comme arguments individuels à la fonction de gestionnaire d'événements côté serveur.

Réception d'événements

Le client peut attendre que le serveur émette un événement avec la méthode receive() :

event = sio.receive()
print(f'événement reçu : "{event[0]}" avec les arguments {event[1:]}')

Lors de l'utilisation d'asyncio, cette méthode doit être attendue :

event = await sio.receive()
print(f'événement reçu : "{event[0]}" avec les arguments {event[1:]}')

La valeur de retour de receive() est une liste. Le premier élément de cette liste est le nom de l'événement, tandis que les éléments restants sont les arguments passés par le serveur.

Avec l'utilisation présentée ci-dessus, la méthode receive() ne retournera que lorsqu'un événement sera reçu du serveur. Un délai d'attente optionnel en secondes peut être passé pour éviter que le client n'attende indéfiniment :

from socketio.exceptions import TimeoutError
try:
    event = sio.receive(timeout=5)
except TimeoutError:
    print('délai d\'attente dépassé en attendant l\'événement')
else:
    print('événement reçu :', event)

Ou avec asyncio :

from socketio.exceptions import TimeoutError
try:
    event = await sio.receive(timeout=5)
except TimeoutError:
    print('délai d\'attente dépassé en attendant l\'événement')
else:
    print('événement reçu :', event)

Déconnexion du serveur

À tout moment, le client peut demander à être déconnecté du serveur en appelant la méthode disconnect() :

sio.disconnect()

Pour le client asyncio, il s'agit d'une coroutine :

await sio.disconnect()

Débogage et dépannage

Pour vous aider à déboguer les problèmes, le client peut être configuré pour afficher des journaux dans le terminal :

import socketio
# Python standard
sio = socketio.Client(logger=True, engineio_logger=True)
# asyncio
sio = socketio.AsyncClient(logger=True, engineio_logger=True)

L'argument logger contrôle la journalisation liée au protocole Socket.IO, tandis que engineio_logger contrôle les journaux provenant du transport de bas niveau Engine.IO. Ces arguments peuvent être définis sur True pour afficher les journaux sur stderr, ou sur un objet compatible avec le package logging de Python, vers lequel les journaux doivent être émis. Une valeur de False désactive la journalisation.

La journalisation peut aider à identifier la cause des problèmes de connexion, des déconnexions inattendues et d'autres problèmes.

Utilisation du client piloté par événements

Création d'une instance de client

Pour instancier un client Socket.IO, créez simplement une instance de la classe de client appropriée :

import socketio
# Python standard
sio = socketio.Client()
# asyncio
sio = socketio.AsyncClient()

Définition des gestionnaires d'événements

Le protocole Socket.IO est basé sur les événements. Lorsqu'un serveur souhaite communiquer avec un client, il émet un événement. Chaque événement a un nom et une liste d'arguments. Le client enregistre des fonctions de gestionnaire d'événements avec les décorateurs socketio.Client.event() <#socketio.Client.event> ou socketio.Client.on() <#socketio.Client.on> :

@sio.event
def message(data):
    print('J\'ai reçu un message !')
@sio.on('mon message')
def on_message(data):
    print('J\'ai reçu un message !')

Dans le premier exemple, le nom de l'événement est obtenu à partir du nom de la fonction gestionnaire. Le second exemple est légèrement plus verbeux, mais il permet au nom de l'événement d'être différent du nom de la fonction ou d'inclure des caractères illégaux dans les noms de fonction, tels que des espaces.

Pour le client asyncio, les gestionnaires d'événements peuvent être des fonctions normales comme ci-dessus, ou peuvent également être des coroutines :

@sio.event
async def message(data):
    print('J\'ai reçu un message !')

Si le serveur inclut des arguments avec un événement, ceux-ci sont passés à la fonction gestionnaire en tant qu'arguments.

Gestionnaires d'événements "catch-all" et de namespaces

Un gestionnaire d'événements "catch-all" est invoqué pour tous les événements qui n'ont pas de gestionnaire d'événements. Vous pouvez définir un gestionnaire "catch-all" en utilisant '*' comme nom d'événement :

@sio.on('*')
def any_event(event, sid, data):
     pass

Les serveurs asyncio peuvent également utiliser une coroutine :

@sio.on('*')
async def any_event(event, sid, data):
    pass

Un gestionnaire d'événements "catch-all" reçoit le nom de l'événement comme premier argument. Les arguments restants sont les mêmes que pour un gestionnaire d'événements régulier.

Les événements connect et disconnect doivent être définis explicitement et ne sont pas invoqués sur un gestionnaire d'événements "catch-all".

De même, un gestionnaire de namespaces "catch-all" est invoqué pour tous les namespaces connectés qui n'ont pas de gestionnaire d'événements explicitement défini. Comme pour les événements "catch-all", '*' est utilisé à la place d'un namespace :

@sio.on('my_event', namespace='*')
def my_event_any_namespace(namespace, sid, data):
    pass

Pour ces événements, le namespace est passé comme premier argument, suivi des arguments réguliers de l'événement.

Gestionnaires d'événements génériques

Il est possible de définir un gestionnaire « tout attraper » pour tous les événements sur tous les espaces de noms :

@sio.on('*', namespace='*')
def any_event_any_namespace(event, namespace, sid, data):
    pass

Les gestionnaires d'événements avec des événements et des espaces de noms génériques reçoivent le nom de l'événement et l'espace de noms comme premier et deuxième arguments.

Gestionnaires d'événements Connect, Connect Error et Disconnect

Les événements connect, connect_error et disconnect sont spéciaux ; ils sont appelés automatiquement lorsqu'un client se connecte ou se déconnecte du serveur :

@sio.event
def connect():
    print("Je suis connecté !")
@sio.event
def connect_error(data):
    print("La connexion a échoué !")
@sio.event
def disconnect(reason):
    print("Je suis déconnecté ! raison :", reason)

Le gestionnaire connect_error est appelé lorsqu'une tentative de connexion échoue. Si le serveur fournit des arguments, ceux-ci sont transmis au gestionnaire. Le serveur peut utiliser un argument pour fournir des informations au client concernant l'échec de la connexion.

Le gestionnaire disconnect est appelé pour les déconnexions initiées par l'application, les déconnexions initiées par le serveur ou les déconnexions accidentelles, par exemple en raison de pannes réseau. En cas de déconnexion accidentelle, le client tentera de se reconnecter immédiatement après avoir appelé le gestionnaire de déconnexion. Dès que la connexion est rétablie, le gestionnaire de connexion sera à nouveau appelé. Le gestionnaire reçoit un argument reason qui fournit la cause de la déconnexion :

@sio.event
def disconnect(reason):
    if reason == sio.reason.CLIENT_DISCONNECT:
        print('le client s\'est déconnecté')
    elif reason == sio.reason.SERVER_DISCONNECT:
        print('le serveur a déconnecté le client')
    else:
        print('raison de déconnexion :', reason)

Consultez l'attribut socketio.Client.reason <#socketio.Client.reason> pour une liste des raisons possibles de déconnexion.

Les événements connect, connect_error et disconnect doivent être définis explicitement et ne sont pas appelés sur un gestionnaire d'événements générique.

await sio.emit('my message', {'foo': 'bar'})

Rappels d'événements

Lorsqu'un serveur émet un événement vers un client, il peut éventuellement fournir une fonction de rappel, à appeler pour accuser réception du traitement de l'événement par le serveur. Bien que cela soit entièrement géré par le serveur, le client peut fournir une liste de valeurs de retour à transmettre à la fonction de rappel configurée par le serveur. Ceci est simplement réalisé en retournant les valeurs souhaitées de la fonction de gestionnaire :

@sio.event
def my_event(sid, data):
    # gérer le message
    return "OK", 123

De même, le client peut demander qu'une fonction de rappel soit appelée après que le serveur a traité un événement. La méthode socketio.Server.emit() <#socketio.Server.emit> possède un argument optionnel callback qui peut être défini sur un appelable. Si cet argument est fourni, l'appelable sera appelé après que le serveur a traité l'événement, et toutes les valeurs retournées par le gestionnaire du serveur seront passées comme arguments à cette fonction.

Espaces de noms

Le protocole Socket.IO prend en charge plusieurs connexions logiques, toutes multiplexées sur la même connexion physique. Les clients peuvent ouvrir plusieurs connexions en spécifiant un espace de noms différent pour chacune. Les espaces de noms utilisent une syntaxe de chemin commençant par une barre oblique. Une liste d'espaces de noms peut être fournie par le client dans l'appel connect(). Par exemple, cet exemple crée deux connexions logiques, la connexion par défaut plus une deuxième connexion sous l'espace de noms /chat :

sio.connect('http://localhost:5000', namespaces=['/chat'])

Pour définir des gestionnaires d'événements sur un espace de noms, l'argument namespace doit être ajouté au décorateur correspondant :

@sio.event(namespace='/chat')
def my_custom_event(sid, data):
    pass
@sio.on('connect', namespace='/chat')
def on_connect():
    print("Je suis connecté à l'espace de noms /chat !")

De même, le client peut émettre un événement vers le serveur sur un espace de noms en le fournissant dans l'appel emit() :

sio.emit('my message', {'foo': 'bar'}, namespace='/chat')

Si l'argument namespaces de l'appel connect() n'est pas fourni, tous les espaces de noms utilisés dans les gestionnaires d'événements sont automatiquement connectés.

Espaces de noms basés sur des classes

En alternative aux gestionnaires d'événements basés sur des décorateurs, les gestionnaires d'événements appartenant à un espace de noms peuvent être créés en tant que méthodes d'une sous-classe de socketio.ClientNamespace <#socketio.ClientNamespace> :

class MyCustomNamespace(socketio.ClientNamespace):
    def on_connect(self):
        pass
    def on_disconnect(self, reason):
        pass
    def on_my_event(self, data):
        self.emit('my_response', data)

Un gestionnaire d'espace de noms basé sur une classe qui capture tout peut être défini en passant '*' comme espace de noms lors de l'enregistrement :

sio.register_namespace(MyCustomNamespace('*'))

Lorsque des espaces de noms basés sur des classes sont utilisés, tous les événements reçus par le client sont distribués à une méthode nommée comme le nom de l'événement avec le préfixe on_. Par exemple, l'événement my_event sera géré par une méthode nommée on_my_event. Si un événement est reçu pour lequel aucune méthode correspondante n'est définie dans la classe de l'espace de noms, alors l'événement est ignoré. Tous les noms d'événements utilisés dans les espaces de noms basés sur des classes doivent utiliser des caractères qui sont légaux dans les noms de méthodes.

Pour simplifier l'utilisation des méthodes définies dans un espace de noms basé sur une classe, l'instance de l'espace de noms inclut des versions de plusieurs méthodes des classes socketio.Client <#socketio.Client> et socketio.AsyncClient <#socketio.AsyncClient> qui utilisent par défaut le bon espace de noms lorsque l'argument namespace n'est pas donné.

Dans le cas où un événement a un gestionnaire dans un espace de noms basé sur une classe, ainsi qu'un gestionnaire de fonction basé sur un décorateur, seul le gestionnaire de fonction autonome est invoqué.

Déconnexion du Serveur

À tout moment, le client peut demander à être déconnecté du serveur en appelant la méthode disconnect() :

sio.disconnect()

Pour le client asyncio, il s'agit d'une coroutine :

await sio.disconnect()

Gestion des Tâches en Arrière-plan

Lorsqu'une connexion client au serveur est établie, quelques tâches en arrière-plan sont lancées pour maintenir la connexion active et gérer les événements entrants. L'application s'exécutant sur le thread principal est libre de faire son travail, car cela n'empêchera pas le bon fonctionnement du client Socket.IO.

Si l'application n'a rien à faire sur le thread principal et souhaite simplement attendre la fin de la connexion avec le serveur, elle peut appeler la méthode wait() :

sio.wait()

Ou dans la version asyncio :

await sio.wait()

Pour la commodité de l'application, une fonction d'aide est fournie pour démarrer une tâche personnalisée en arrière-plan :

def my_background_task(my_argument):
    # faire un travail en arrière-plan ici !
    pass
task = sio.start_background_task(my_background_task, 123)

Les arguments passés à cette méthode sont la fonction d'arrière-plan et tous les arguments positionnels ou par mots-clés pour appeler la fonction.

Voici la version asyncio :

async def my_background_task(my_argument):
    # faire un travail en arrière-plan ici !
    pass
task = sio.start_background_task(my_background_task, 123)

Notez que cette fonction n'est pas une coroutine, car elle n'attend pas que la fonction d'arrière-plan se termine. La fonction d'arrière-plan doit être une coroutine.

La méthode sleep() est une deuxième fonction pratique fournie pour le bénéfice des applications travaillant avec leurs propres tâches d'arrière-plan :

sio.sleep(2)

Ou pour asyncio :

await sio.sleep(2)

Le seul argument passé à la méthode est le nombre de secondes pendant lesquelles dormir.

Débogage et Dépannage

Pour vous aider à déboguer les problèmes, le client peut être configuré pour afficher des journaux dans le terminal :

import socketio
# Python standard
sio = socketio.Client(logger=True, engineio_logger=True)
# asyncio
sio = socketio.AsyncClient(logger=True, engineio_logger=True)

L'argument logger contrôle la journalisation relative au protocole Socket.IO, tandis que engineio_logger contrôle les journaux provenant du transport Engine.IO de bas niveau. Ces arguments peuvent être définis sur True pour afficher les journaux sur stderr, ou sur un objet compatible avec le package logging de Python, vers lequel les journaux doivent être émis. Une valeur de False désactive la journalisation.

La journalisation peut aider à identifier la cause des problèmes de connexion, des déconnexions inattendues et d'autres problèmes.

LE SERVEUR SOCKET.IO

Ce package contient deux serveurs Socket.IO :

  • La classe socketio.Server() <#socketio.Server> crée un serveur compatible avec la bibliothèque standard Python.
  • La classe socketio.AsyncServer() <#socketio.AsyncServer> crée un serveur compatible avec le package asyncio.

Les méthodes des deux serveurs sont identiques, la seule différence étant que dans le serveur asyncio, la plupart des méthodes sont implémentées comme des coroutines.

Installation

Pour installer le serveur Socket.IO ainsi que ses dépendances, utilisez la commande suivante :

pip install python-socketio

Création d'une Instance de Serveur

Un serveur Socket.IO est une instance de la classe socketio.Server <#socketio.Server> :

import socketio
# créer un serveur Socket.IO
sio = socketio.Server()

Pour les serveurs basés sur asyncio, la classe socketio.AsyncServer <#socketio.AsyncServer> fournit la même fonctionnalité, mais dans un format adapté aux coroutines :

import socketio
# créer un serveur Socket.IO
sio = socketio.AsyncServer()

Exécution du Serveur

Pour exécuter l'application Socket.IO, il est nécessaire de configurer un serveur web pour recevoir les requêtes entrantes des clients et les transmettre à l'instance du serveur Socket.IO. Pour simplifier cette tâche, plusieurs intégrations sont disponibles, y compris le support des normes WSGI https://wsgi.readthedocs.io/en/latest/what.html et ASGI https://asgi.readthedocs.io/en/latest/.

Exécution en tant qu'Application WSGI

Pour configurer le serveur Socket.IO en tant qu'application WSGI, encapsulez l'instance du serveur avec la classe socketio.WSGIApp <#socketio.WSGIApp> :

# encapsuler avec une application WSGI
app = socketio.WSGIApp(sio)

L'application WSGI résultante peut être exécutée avec des serveurs WSGI compatibles tels que Werkzeug https://werkzeug.palletsprojects.com pour le développement et Gunicorn https://gunicorn.org/ pour la production.

Lors de la combinaison de Socket.IO avec une application web écrite avec un framework WSGI tel que Flask ou Django, la classe WSGIApp peut encapsuler les deux applications ensemble et router le trafic vers elles :

from mywebapp import app  # une application Flask, Django, etc.
app = socketio.WSGIApp(sio, app)

Exécution en tant qu'Application ASGI

Pour configurer le serveur Socket.IO en tant qu'application ASGI, encapsulez l'instance du serveur avec la classe socketio.ASGIApp <#socketio.ASGIApp> :

# encapsuler avec une application ASGI
app = socketio.ASGIApp(sio)

L'application ASGI résultante peut être exécutée avec un serveur web compatible ASGI, par exemple Uvicorn https://www.uvicorn.org/.

Socket.IO peut également être combiné avec une application web écrite avec un framework web ASGI tel que FastAPI. Dans ce cas, la classe ASGIApp peut encapsuler les deux applications ensemble et router le trafic vers elles :

from mywebapp import app  # une application FastAPI ou autre ASGI
app = socketio.ASGIApp(sio, app)

Service des Fichiers Statiques

Le serveur Socket.IO peut être configuré pour servir des fichiers statiques aux clients. Ceci est particulièrement utile pour livrer des fichiers HTML, CSS et JavaScript aux clients lorsque ce package est utilisé sans framework web compagnon.

Les fichiers statiques sont configurés avec un dictionnaire Python dans lequel chaque paire clé/valeur est une règle de mappage de fichier statique. Dans sa forme la plus simple, ce dictionnaire contient une ou plusieurs URL de fichiers statiques comme clés, et les fichiers correspondants sur le serveur comme valeurs :

static_files = {
    '/': 'latency.html',
    '/static/socket.io.js': 'static/socket.io.js',
    '/static/style.css': 'static/style.css',
}

Avec cet exemple de configuration, lorsque le serveur reçoit une requête pour / (l'URL racine), il retournera le contenu du fichier latency.html dans le répertoire courant, et attribuera un type de contenu basé sur l'extension du fichier, dans ce cas text/html.

Les fichiers avec les extensions de fichier .html, .css, .js, .json, .jpg, .png, .gif et .txt sont automatiquement reconnus et se voient attribuer le bon type de contenu. Pour les fichiers avec d'autres extensions ou sans extension, le type de contenu application/octet-stream est utilisé par défaut.

Si vous le souhaitez, un type de contenu explicite pour un fichier statique peut être donné comme suit :

static_files = {
    '/': {'filename': 'latency.html', 'content_type': 'text/plain'},
}

Il est également possible de configurer un répertoire entier en une seule r

ule, de sorte que tous les fichiers qu'il contient soient servis comme fichiers statiques :

static_files = {
    '/static': './public',
}

Dans cet exemple, tous les fichiers dont les URL commencent par /static seront servis directement depuis le dossier public du répertoire courant. Ainsi, par exemple, l'URL /static/index.html retournera le fichier local ./public/index.html et l'URL /static/css/styles.css retournera le fichier local ./public/css/styles.css.

Si une URL se terminant par un / est demandée, un nom de fichier par défaut index.html lui est ajouté. Dans l'exemple précédent, une requête pour l'URL /static/ retournerait le fichier local ./public/index.html. Le nom de fichier par défaut à servir pour les URL se terminant par une barre oblique peut être défini dans le dictionnaire des fichiers statiques avec une clé vide :

static_files = {
    '/static': './public',
    '': 'image.gif',
}

Avec cette configuration, une requête pour /static/ retournerait le fichier local ./public/image.gif. Un type de contenu non standard peut également être spécifié si nécessaire :

static_files = {
    '/static': './public',
    '': {'filename': 'image.gif', 'content_type': 'text/plain'},
}

Le dictionnaire de configuration des fichiers statiques est passé comme argument static_files aux classes socketio.WSGIApp ou socketio.ASGIApp :

# pour les applications WSGI standard
sio = socketio.Server()
app = socketio.WSGIApp(sio, static_files=static_files)
# pour les applications ASGI basées sur asyncio
sio = socketio.AsyncServer()
app = socketio.ASGIApp(sio, static_files=static_files)

La précédence du routage dans ces deux classes est la suivante :

  • Tout d'abord, le chemin est vérifié par rapport au point de terminaison Socket.IO.
  • Ensuite, le chemin est vérifié par rapport à la configuration des fichiers statiques, si elle est présente.
  • Si le chemin ne correspond pas au point de terminaison Socket.IO ni à un fichier statique, le contrôle est passé à l'application secondaire si elle est configurée, sinon une erreur 404 est renvoyée.

Note : Le service de fichiers statiques est destiné à un usage de développement uniquement et manque donc de fonctionnalités importantes telles que la mise en cache. Ne l'utilisez pas en production.

Événements

Le protocole Socket.IO est basé sur des événements. Lorsqu'un client souhaite communiquer avec le serveur, ou que le serveur souhaite communiquer avec un ou plusieurs clients, ils émettent un événement à l'autre partie. Chaque événement a un nom et une liste optionnelle d'arguments.

Écoute des événements

Pour recevoir des événements des clients, l'application serveur doit enregistrer des fonctions de gestionnaire d'événements. Ces fonctions sont appelées lorsque les événements correspondants sont émis par les clients. Pour enregistrer un gestionnaire pour un événement, les décorateurs socketio.Server.event() <#socketio.Server.event> ou socketio.Server.on() <#socketio.Server.on> sont utilisés :

@sio.event
def my_event(sid, data):
    pass
@sio.on('my custom event')
def another_event(sid, data):
    pass

Dans le premier exemple, le nom de l'événement est obtenu à partir du nom de la fonction gestionnaire. Le second exemple est légèrement plus verbeux, mais il permet que le nom de l'événement soit différent du nom de la fonction ou qu'il contienne des caractères illégaux dans les noms de fonctions, tels que des espaces.

Pour les serveurs asyncio, les gestionnaires d'événements peuvent optionnellement être fournis sous forme de coroutines :

@sio.event
async def my_event(sid, data):
    pass

L'argument sid passé à tous les gestionnaires est l'identifiant de session Socket.IO, un identifiant unique que Socket.IO attribue à chaque connexion client. Tous les événements envoyés par un client donné auront la même valeur sid.

Événements de connexion et de déconnexion

Les événements connect et disconnect sont spéciaux ; ils sont appelés automatiquement lorsqu'un client se connecte ou se déconnecte du serveur :

@sio.event
def connect(sid, environ, auth):
    print('connect ', sid)
@sio.event
def disconnect(sid, reason):
    print('disconnect ', sid, reason)

L'événement connect est l'endroit idéal pour effectuer l'authentification de l'utilisateur et toute correspondance nécessaire entre les entités utilisateur de l'application et le sid qui a été attribué au client.

En plus du sid, le gestionnaire de connexion reçoit environ comme argument, avec les informations de la requête au format WSGI standard, y compris les en-têtes HTTP. Le gestionnaire de connexion reçoit également l'argument auth avec les détails d'authentification passés par le client, ou None si le client n'a passé aucune authentification.

Après avoir inspecté les arguments, le gestionnaire d'événements de connexion peut retourner False pour refuser la connexion avec le client. Parfois, il est utile de passer des données au client qui est rejeté. Dans ce cas, au lieu de retourner False, une exception socketio.exceptions.ConnectionRefusedError <#socketio.exceptions.ConnectionRefusedError> peut être levée, et tous ses arguments seront envoyés au client avec le message de rejet :

from socketio.exceptions import ConnectionRefusedError
@sio.event
def connect(sid, environ, auth):
    raise ConnectionRefusedError('authentication failed')

Le gestionnaire de déconnexion reçoit le sid attribué au client et une raison, qui fournit la cause de la déconnexion :

@sio.event
def disconnect(sid, reason):
    if reason == sio.reason.CLIENT_DISCONNECT:
        print('le client s\'est déconnecté')
    elif reason == sio.reason.SERVER_DISCONNECT:
        print('le serveur a déconnecté le client')
    else:
        print('raison de déconnexion :', reason)

Voir l'attribut socketio.Server.reason <#socketio.Server.reason> pour une liste des raisons de déconnexion possibles.

Gestionnaires d'événements "catch-all"

Un gestionnaire d'événements "catch-all" est appelé pour tous les événements qui n'ont pas de gestionnaire d'événements. Vous pouvez définir un gestionnaire "catch-all" en utilisant '*' comme nom d'événement :

@sio.on('*')
def any_event(event, sid, data):
     pass

Les serveurs asyncio peuvent également utiliser une coroutine :

@sio.on('*')
async def any_event(event, sid, data):
    pass

Un gestionnaire d'événements "catch-all" reçoit le nom de l'événement comme premier argument. Les arguments restants sont les mêmes que pour un gestionnaire d'événements régulier.

Notez que les événements connect et disconnect doivent être définis explicitement et ne sont pas appelés par un gestionnaire d'événements "catch-all".

Émission d'événements aux clients

Socket.IO est un protocole bidirectionnel, donc à tout moment, le serveur peut envoyer un événement à ses clients connectés. La méthode socketio.Server.emit() <#socketio.Server.emit> est utilisée pour cette tâche :

sio.emit('my event', {'data': 'foobar'})

Le premier argument est le nom de l'événement, suivi d'une charge utile optionnelle de type str, bytes, list, dict ou tuple. Lors de l'envoi d'une list, dict ou tuple, les éléments sont également contraints aux mêmes types de données. Lorsqu'un tuple est envoyé, les éléments du tuple seront passés comme arguments multiples à la fonction de gestionnaire d'événements côté client.

L'exemple ci-dessus enverra l'événement à tous les clients connectés. Parfois, le serveur peut vouloir envoyer un événement à un seul client spécifique. Cela peut être réalisé en ajoutant un argument to à l'appel d'émission, avec le sid du client :

sio.emit('my event', {'data': 'foobar'}, to=user_sid)

L'argument to est utilisé pour identifier le client qui doit recevoir l'événement, et il est défini sur la valeur sid attribuée à la connexion de ce client avec le serveur. Lorsque to est omis, l'événement est diffusé à tous les clients connectés.

Accusés de réception d'événements

Lorsqu'un client envoie un événement au serveur, il peut optionnellement demander à recevoir un accusé de réception du serveur. L'envoi des accusés de réception est géré automatiquement par le serveur Socket.IO, mais la fonction de gestionnaire d'événements peut fournir une liste de valeurs qui seront transmises au client avec l'accusé de réception simplement en les retournant :

@sio.event
def my_event(sid, data):
    # gérer le message
    return "OK", 123  # <-- le client aura ces éléments comme accusé de réception

Demande d'accusés de réception du client

Similairement à la façon dont les clients peuvent demander des accusés de réception au serveur, lorsque le serveur émet à un seul client, il peut également demander au client d'accuser réception de l'événement et éventuellement de retourner une ou plusieurs valeurs en réponse.

Le serveur Socket.IO prend en charge deux façons de travailler avec les accusés de réception client. La méthode la plus pratique est de remplacer socketio.Server.emit() <#socketio.Server.emit> par socketio.Server.call() <#socketio.Server.call>. La méthode call() émettra l'événement, puis attendra que le client envoie un accusé de réception, retournant toutes les valeurs fournies par le client :

response = sio.call('my event', {'data': 'foobar'}, to=user_sid)

Une solution d'accusé de réception beaucoup plus primitive utilise des fonctions de rappel. La méthode socketio.Server.emit() <#socketio.Server.emit> possède un argument optionnel callback qui peut être défini sur un objet appelable. Si cet argument est fourni, l'objet appelable sera appelé après que le client a traité l'événement, et toutes les valeurs retournées par le client lui seront passées comme arguments à cette fonction :

def my_callback():
    print("callback invoked!")
sio.emit('my event', {'dat
a': 'foobar'}, to=user_sid, callback=my_callback)

Salons

Pour faciliter l'envoi d'événements à des groupes de clients liés par le serveur, l'application peut placer ses clients dans des « salons », puis adresser les messages à ces salons.

Dans les exemples précédents, l'argument to de la méthode socketio.SocketIO.emit() a été utilisé pour désigner un client spécifique comme destinataire de l'événement. L'argument to peut également recevoir le nom d'un salon, et tous les clients qui se trouvent dans ce salon recevront alors l'événement.

L'application peut créer autant de salons que nécessaire et gérer quels clients s'y trouvent à l'aide des méthodes socketio.Server.enter_room() <#socketio.Server.enter_room> et socketio.Server.leave_room() <#socketio.Server.leave_room>. Les clients peuvent se trouver dans autant de salons que nécessaire et peuvent être déplacés entre les salons si besoin.

@sio.event
def begin_chat(sid):
    sio.enter_room(sid, 'chat_users')
@sio.event
def exit_chat(sid):
    sio.leave_room(sid, 'chat_users')

Dans les applications de chat, il est souvent souhaitable qu'un événement soit diffusé à tous les membres du salon sauf un, qui est l'origine de l'événement, comme un message de chat. La méthode socketio.Server.emit() <#socketio.Server.emit> fournit un argument optionnel skip_sid pour indiquer un client qui doit être ignoré lors de la diffusion.

@sio.event
def my_message(sid, data):
    sio.emit('my reply', data, room='chat_users', skip_sid=sid)

Espaces de noms

Le protocole Socket.IO prend en charge plusieurs connexions logiques, toutes multiplexées sur la même connexion physique. Les clients peuvent ouvrir plusieurs connexions en spécifiant un espace de noms différent pour chacune. Un espace de noms est donné par le client sous forme de chemin suivant le nom d'hôte et le port. Par exemple, se connecter à http://example.com:8000/chat ouvrirait une connexion à l'espace de noms /chat.

Chaque espace de noms fonctionne indépendamment des autres, avec des identifiants de session (sids), des gestionnaires d'événements et des salons séparés. Les espaces de noms peuvent être définis directement dans les fonctions de gestion des événements, ou ils peuvent également être créés sous forme de classes.

Espaces de noms basés sur les décorateurs

Les espaces de noms basés sur les décorateurs sont des gestionnaires d'événements réguliers qui incluent l'argument namespace dans leur décorateur :

@sio.event(namespace='/chat')
def my_custom_event(sid, data):
    pass
@sio.on('my custom event', namespace='/chat')
def my_custom_event(sid, data):
    pass

Lors de l'envoi d'un événement, l'argument optionnel namespace est utilisé pour spécifier sur quel espace de noms l'envoyer. Lorsque l'argument namespace est omis, l'espace de noms Socket.IO par défaut, nommé /, est utilisé.

Il est important que les applications qui utilisent plusieurs espaces de noms spécifient le bon espace de noms lors de la configuration de leurs gestionnaires d'événements et de leurs salons à l'aide de l'argument optionnel namespace. Cet argument doit également être spécifié lors de l'envoi d'événements sous un espace de noms. La plupart des méthodes de la classe socketio.Server <#socketio.Server> possèdent l'argument optionnel namespace.

Espaces de noms basés sur des classes

Alternativement aux espaces de noms basés sur les décorateurs, les gestionnaires d'événements appartenant à un espace de noms peuvent être créés comme méthodes dans une sous-classe de socketio.Namespace <#socketio.Namespace> :

class MyCustomNamespace(socketio.Namespace):
    def on_connect(self, sid, environ):
        pass
    def on_disconnect(self, sid, reason):
        pass
    def on_my_event(self, sid, data):
        self.emit('my_response', data)
sio.register_namespace(MyCustomNamespace('/test'))

Pour les serveurs basés sur asyncio, les espaces de noms doivent hériter de socketio.AsyncNamespace <#socketio.AsyncNamespace>, et peuvent définir des gestionnaires d'événements comme des coroutines si désiré :

class MyCustomNamespace(socketio.AsyncNamespace):
    def on_connect(self, sid, environ):
        pass
    def on_disconnect(self, sid, reason):
        pass
    async def on_my_event(self, sid, data):
        await self.emit('my_response', data)
sio.register_namespace(MyCustomNamespace('/test'))

Lorsque des espaces de noms basés sur des classes sont utilisés, tous les événements reçus par le serveur sont distribués à une méthode nommée comme le nom de l'événement avec le préfixe on_. Par exemple, l'événement my_event sera géré par une méthode nommée on_my_event. Si un événement est reçu pour lequel aucune méthode correspondante n'est définie dans la classe d'espace de noms, l'événement est ignoré. Tous les noms d'événements utilisés dans les espaces de noms basés sur des classes doivent utiliser des caractères valides dans les noms de méthodes.

Pour faciliter l'utilisation des méthodes définies dans un espace de noms basé sur une classe, l'instance d'espace de noms inclut des versions de plusieurs méthodes des classes socketio.Server <#socketio.Server> et socketio.AsyncServer <#socketio.AsyncServer> qui, par défaut, utilisent le bon espace de noms lorsque l'argument namespace n'est pas fourni.

Dans le cas où un événement a un gestionnaire dans un espace de noms basé sur une classe, et aussi un gestionnaire de fonction basé sur un décorateur, seul le gestionnaire de fonction autonome est invoqué.

Il est important de noter que les espaces de noms basés sur des classes sont des singletons. Cela signifie qu'une seule instance d'une classe d'espace de noms est utilisée pour tous les clients, et par conséquent, une instance d'espace de noms ne peut pas être utilisée pour stocker des informations spécifiques au client.

Espaces de noms génériques

Semblablement aux gestionnaires d'événements génériques, un espace de noms « générique » peut être utilisé lors de la définition de gestionnaires d'événements pour tous les espaces de noms connectés qui n'ont pas de gestionnaire d'événements explicitement défini. Comme pour les événements génériques, '*' est utilisé à la place d'un espace de noms :

@sio.on('my_event', namespace='*')
def my_event_any_namespace(namespace, sid, data):
    pass

Pour ces événements, l'espace de noms est passé comme premier argument, suivi des arguments réguliers de l'événement.

Un gestionnaire d'espace de noms générique basé sur une classe peut être défini en passant '*' comme espace de noms lors de l'enregistrement :

sio.register_namespace(MyCustomNamespace('*'))

Un gestionnaire « générique » pour tous les événements sur tous les espaces de noms peut être défini comme suit :

@sio.on('*', namespace='*')
def any_event_any_namespace(event, namespace, sid, data):
    pass

Les gestionnaires d'événements avec des événements et des espaces de noms génériques reçoivent le nom de l'événement et l'espace de noms comme premier et deuxième arguments.

Sessions utilisateur

Le serveur peut maintenir des informations spécifiques à l'application dans une session utilisateur dédiée à chaque client connecté. Les applications peuvent utiliser la session utilisateur pour enregistrer tous les détails concernant l'utilisateur qui doivent être conservés pendant toute la durée de la connexion, tels que les noms d'utilisateur ou les identifiants utilisateur.

Les méthodes save_session() et get_session() sont utilisées pour stocker et récupérer des informations dans la session utilisateur :

@sio.event
def connect(sid, environ):
    username = authenticate_user(environ)
    sio.save_session(sid, {'username': username})
@sio.event
def message(sid, data):
    session = sio.get_session(sid)
    print('message from ', session['username'])

Pour le serveur asyncio, ces méthodes sont des coroutines :

@sio.event
async def connect(sid, environ):
    username = authenticate_user(environ)
    await sio.save_session(sid, {'username': username})
@sio.event
async def message(sid, data):
    session = await sio.get_session(sid)
    print('message from ', session['username'])

La session peut également être manipulée avec le gestionnaire de contexte session() :

@sio.event
def connect(sid, environ):
    username = authenticate_user(environ)
    with sio.session(sid) as session:
        session['username'] = username
@sio.event
def message(sid, data):
    with sio.session(sid) as session:
        print('message from ', session['username'])

Pour le serveur asyncio, un gestionnaire de contexte asynchrone est utilisé :

@sio.event
async def connect(sid, environ):
    username = authenticate_user(environ)
    async with sio.session(sid) as session:
        session['username'] = username
@sio.event
async def message(sid, data):
    async with sio.session(sid) as session:
        print('message from ', session['username'])

Les méthodes get_session(), save_session() et session() prennent un argument optionnel namespace. Si cet argument n'est pas fourni, la session est attachée à l'espace de noms par défaut.

Remarque : le contenu de la session utilisateur est détruit lorsque le client se déconnecte. En particulier, le contenu de la session utilisateur n'est pas conservé lorsqu'un client se reconnecte après une déconnexion inattendue du serveur.

Contrôles inter-origines

Pour des raisons de sécurité, ce serveur applique par défaut une politique de même origine. Concrètement, cela signifie ce qui suit :

  • Si une requête HTTP ou WebSocket entrante inclut l'en-tête Origin, cet en-tête doit correspondre au schéma et à l'hôte de l'URL de connexion. En cas de non-concordance, une réponse avec un code d'état 400 est renvoyée et la connexion est rejetée.
  • Aucune restriction n'est imposée aux requêtes entrantes qui n'incluent pas l'en-tête Origin.

Si nécessaire, l'option cors_allowed_origins peut être utilisée pour autoriser d'autres origines. Cet argument peut être défini à une chaîne de caractères pour définir une seule origine autorisée, ou à une liste pour autoriser plusieurs origines. Une valeur spéciale de '*' peut être utilisée pour indiquer au serveur d'autoriser toutes les origines, mais cela doit être fait avec prudence, car cela pourrait rendre le serveur vulnérable aux attaques par falsification de requête inter-sites (CSRF).

Surveillance et administration

Le serveur Socket.IO peut être configuré

Interface d'administration Socket.IO

Pour accepter des connexions de l'interface d'administration officielle de Socket.IO https://socket.io/docs/v4/admin-ui/. Cet outil fournit des informations en temps réel sur les clients actuellement connectés, les salles utilisées et les événements émis. Il permet également à un administrateur de manuellement émettre des événements, modifier les affectations de salles et déconnecter des clients. La version hébergée de cet outil est disponible à l'adresse https://admin.socket.io.

Étant donné que l'activation de cette fonctionnalité peut affecter les performances du serveur, elle est désactivée par défaut. Pour l'activer, appelez la méthode instrument() <#socketio.Server.instrument>. Par exemple :

import os
import socketio
sio = socketio.Server(cors_allowed_origins=[
    'http://localhost:5000',
    'https://admin.socket.io',
])
sio.instrument(auth={
    'username': 'admin',
    'password': os.environ['ADMIN_PASSWORD'],
})

Ceci configure le serveur pour accepter les connexions du client hébergé de l'interface d'administration. Les administrateurs peuvent alors ouvrir https://admin.socket.io dans leurs navigateurs web et se connecter avec le nom d'utilisateur admin et le mot de passe fourni par la variable d'environnement ADMIN_PASSWORD. Pour garantir que le frontend de l'interface d'administration est autorisé à se connecter, CORS est également configuré.

Consultez la documentation de référence pour en savoir plus sur les options de configuration supplémentaires disponibles.

Débogage et dépannage

Pour vous aider à déboguer les problèmes, le serveur peut être configuré pour afficher des journaux dans le terminal :

import socketio
# Python standard
sio = socketio.Server(logger=True, engineio_logger=True)
# asyncio
sio = socketio.AsyncServer(logger=True, engineio_logger=True)

L'argument logger contrôle la journalisation liée au protocole Socket.IO, tandis que engineio_logger contrôle les journaux provenant de la couche inférieure du transport Engine.IO. Ces arguments peuvent être définis sur True pour afficher les journaux dans stderr, ou sur un objet compatible avec le package logging de Python où les journaux doivent être émis. Une valeur de False désactive la journalisation.

La journalisation peut aider à identifier la cause des problèmes de connexion, des réponses 400, des mauvaises performances et d'autres problèmes.

Concurrence et intégration avec les serveurs web

Le serveur Socket.IO peut être configuré avec différents modèles de concurrence en fonction des besoins de l'application et du serveur web utilisé. Le modèle de concurrence est donné par l'argument async_mode dans le serveur. Par exemple :

sio = socketio.Server(async_mode='threading')

Les sous-sections suivantes décrivent les options de concurrence disponibles pour les serveurs synchrones et asynchrones.

Modes Standards

  • threading : le serveur utilisera les threads Python pour la concurrence et s'exécutera sur n'importe quel serveur WSGI multi-threadé. C'est le mode par défaut lorsque aucune autre bibliothèque de concurrence n'est installée.
  • gevent : le serveur utilisera des greenlets via la bibliothèque gevent http://www.gevent.org/ pour la concurrence. Un serveur web compatible avec gevent est requis.
  • gevent_uwsgi : une variation du mode gevent conçue pour fonctionner avec le serveur web uWSGI https://uwsgi-docs.readthedocs.io/en/latest/.
  • eventlet : le serveur utilisera des greenlets via la bibliothèque eventlet http://eventlet.net/ pour la concurrence. Un serveur web compatible avec eventlet est requis. L'utilisation d'eventlet n'est pas recommandée car ce projet est en mode maintenance.

Modes Asyncio

Les options asynchrones sont toutes basées sur le package asyncio https://docs.python.org/3/library/asyncio.html de la bibliothèque standard Python, avec des variations mineures en fonction de la plateforme de serveur web utilisée.

  • asgi : l'utilisation de n'importe quel serveur web ASGI https://asgi.readthedocs.io/en/latest/ est requise.
  • aiohttp : l'utilisation du framework et serveur web aiohttp http://aiohttp.readthedocs.io/ est requise.
  • tornado : l'utilisation du framework et serveur web Tornado http://www.tornadoweb.org/ est requise.
  • sanic : l'utilisation du framework et serveur web Sanic http://sanic.readthedocs.io/ est requise. Lors de l'utilisation de Sanic, il est recommandé d'utiliser le mode asgi à la place.

Stratégies de déploiement

Les sections suivantes décrivent une variété de stratégies de déploiement pour les serveurs Socket.IO.

Gunicorn

La stratégie de déploiement la plus simple pour le serveur Socket.IO consiste à utiliser le populaire serveur web Gunicorn http://gunicorn.org en mode multi-threadé. Le serveur Socket.IO doit être encapsulé par la classe socketio.WSGIApp <#socketio.WSGIApp>, afin qu'il soit compatible avec le protocole WSGI :

sio = socketio.Server(async_mode='threading')
app = socketio.WSGIApp(sio)

Si désiré, la classe socketio.WSGIApp peut transférer tout trafic qui n'est pas Socket.IO à une autre application WSGI, permettant ainsi de déployer une application web WSGI standard construite avec des frameworks tels que Flask ou Django et le serveur Socket.IO en un seul paquet :

sio = socketio.Server(async_mode='threading')
app = socketio.WSGIApp(sio, other_wsgi_app)

L'exemple suivant montre comment démarrer une application Socket.IO en utilisant la classe de travailleur threadé de Gunicorn :

$ gunicorn --workers 1 --threads 100 --bind 127.0.0.1:5000 module:app

Avec la configuration ci-dessus, le serveur sera capable de gérer près de 100 clients concurrents.

Il est également possible d'utiliser plus d'un processus de travailleur, mais cela nécessite deux exigences supplémentaires :

  • Les clients doivent se connecter directement via WebSocket. Le transport à interrogation longue est incompatible avec la façon dont Gunicorn équilibre la charge des requêtes entre les travailleurs. Pour désactiver l'interrogation longue dans le serveur, ajoutez transports=['websocket'] dans le constructeur du serveur. Les clients auront une option similaire pour initier la connexion avec WebSocket.
  • Les instances socketio.Server() <#socketio.Server> dans chaque travailleur doivent être configurées avec une file d'attente de messages pour permettre aux travailleurs de communiquer entre eux. Voir la section Utilisation d'une file d'attente de messages pour plus d'informations.

Lors de l'utilisation de plusieurs travailleurs, le nombre approximatif de connexions que le serveur pourra accepter peut être calculé comme le nombre de travailleurs multiplié par le nombre de threads par travailleur.

Notez que Gunicorn peut également être utilisé avec uvicorn, gevent et eventlet. Ces options sont discutées dans les sections appropriées ci-dessous.

Uvicorn (et autres serveurs web ASGI)

Lorsque vous travaillez avec un serveur Socket.IO asynchrone, la stratégie de déploiement la plus simple consiste à utiliser un serveur web ASGI tel que Uvicorn https://www.uvicorn.org/.

La classe socketio.ASGIApp est une application compatible ASGI qui peut transférer le trafic Socket.IO vers une instance socketio.AsyncServer :

sio = socketio.AsyncServer(async_mode='asgi')
app = socketio.ASGIApp(sio)

Si désiré, la classe socketio.ASGIApp peut transférer tout trafic qui n'est pas Socket.IO à une autre application ASGI, permettant ainsi de déployer une application web ASGI standard construite avec un framework tel que FastAPI et le serveur Socket.IO en un seul paquet :

sio = socketio.AsyncServer(async_mode='asgi')
app = socketio.ASGIApp(sio, other_asgi_app)

L'exemple suivant démarre l'application avec Uvicorn :

uvicorn --port 5000 module:app

Uvicorn peut également être utilisé via son travailleur Gunicorn :

gunicorn --workers 1 --worker-class uvicorn.workers.UvicornWorker --bind 127.0.0.1:5000

Voir la section Gunicorn ci-dessus pour plus d'informations sur l'utilisation de Gunicorn avec plusieurs travailleurs.

Hypercorn, Daphne et autres serveurs ASGI

Pour utiliser un serveur web ASGI autre que Uvicorn, configurez l'application pour ASGI comme indiqué ci-dessus pour Uvicorn, puis suivez la documentation de votre serveur web choisi pour démarrer l'application.

Aiohttp

Une autre option pour déployer un serveur Socket.IO asynchrone est d'utiliser le framework et serveur web Aiohttp http://aiohttp.readthedocs.io/. Les instances de la classe socketio.AsyncServer utiliseront automatiquement Aiohttp si la bibliothèque est installée. Pour demander explicitement son utilisation, l'option async_mode peut être spécifiée dans le constructeur :

sio = socketio.AsyncServer(async_mode='aiohttp')

Un serveur configuré pour Aiohttp doit être attaché à une application existante :

app = web.Application()
sio.attach(app)

L'application Aiohttp peut définir des routes régulières qui coexisteront avec le serveur Socket.IO. Un schéma typique consiste à ajouter des routes qui servent une application client et tous les fichiers statiques associés.

L'application Aiohttp est ensuite exécutée de la manière habituelle :

> 
if __name__ == '__main__':
    web.run_app(app)

Gevent

Lorsqu'un serveur Web multi-thread ne parvient pas à répondre aux exigences de concurrence et de scalabilité de l'application, une option à essayer est Gevent http://www.gevent.org. Gevent est une bibliothèque de concurrence basée sur les coroutines et les greenlets, qui sont nettement plus légers que les threads.

Les instances de la classe socketio.Server utiliseront automatiquement Gevent si la bibliothèque est installée. Pour demander explicitement la sélection de gevent, l'option async_mode peut être passée dans le constructeur :

sio = socketio.Server(async_mode='gevent')

Le serveur Socket.IO doit être encapsulé par la classe socketio.WSGIApp <#socketio.WSGIApp>, afin qu'il soit compatible avec le protocole WSGI :

app = socketio.WSGIApp(sio)

Si désiré, la classe socketio.WSGIApp peut transférer tout trafic qui n'est pas Socket.IO à une autre application WSGI, rendant possible le déploiement d'une application Web WSGI standard construite avec des frameworks tels que Flask ou Django et le serveur Socket.IO en un seul paquet :

sio = socketio.Server(async_mode='gevent')
app = socketio.WSGIApp(sio, other_wsgi_app)

Un serveur configuré pour Gevent est déployé comme une application WSGI ordinaire en utilisant le socketio.WSGIApp fourni :

from gevent import pywsgi
pywsgi.WSGIServer(('', 8000), app).serve_forever()

Gevent avec Gunicorn

Une alternative à l'exécution du serveur WSGI gevent comme ci-dessus est d'utiliser Gunicorn <gunicorn.org> avec son worker Gevent. La commande pour lancer l'application sous Gunicorn et Gevent est montrée ci-dessous :

$ gunicorn -k gevent -w 1 -b 127.0.0.1:5000 module:app

Voir la section Gunicorn ci-dessus pour des informations sur la façon d'utiliser Gunicorn avec plusieurs workers.

Gevent fournit une fonction monkey_patch() qui remplace toutes les fonctions bloquantes de la bibliothèque standard par des versions asynchrones équivalentes. Bien que le serveur Socket.IO ne nécessite pas de monkey patching, d'autres bibliothèques telles que les pilotes de base de données ou de file d'attente de messages en auront probablement besoin.

Gevent avec uWSGI

Lors de l'utilisation du serveur uWSGI en combinaison avec gevent, le serveur Socket.IO peut tirer parti du support natif WebSocket de uWSGI.

Les instances de la classe socketio.Server utiliseront automatiquement cette option pour les opérations asynchrones si gevent et uWSGI sont tous deux installés et eventlet n'est pas installé. Pour demander explicitement ce mode asynchrone, l'option async_mode peut être passée dans le constructeur :

# gevent avec uWSGI
sio = socketio.Server(async_mode='gevent_uwsgi')

Une explication complète de la configuration et de l'utilisation du serveur uWSGI dépasse le cadre de cette documentation. Le serveur uWSGI est un paquet assez complexe qui fournit un ensemble d'options large et complet. Il doit être compilé avec le support WebSocket et SSL pour que le transport WebSocket soit disponible. À titre d'introduction, la commande suivante démarre un serveur uWSGI pour l'exemple latency.py sur le port 5000 :

$ uwsgi --http :5000 --gevent 1000 --http-websockets --master --wsgi-file latency.py --callable app

Tornado

Les instances de la classe socketio.AsyncServer utiliseront automatiquement Tornado http://www.tornadoweb.org// si la bibliothèque est installée. Pour demander explicitement son utilisation, l'option async_mode peut être passée dans le constructeur :

sio = socketio.AsyncServer(async_mode='tornado')

Un serveur configuré pour Tornado doit inclure un gestionnaire de requête pour Socket.IO :

app = tornado.web.Application(
    [
        (r"/socket.io/", socketio.get_tornado_handler(sio)),
    ],
    # ... autres options de l'application
)

L'application Tornado peut définir d'autres routes qui coexisteront avec le serveur Socket.IO. Un modèle typique est d'ajouter des routes qui servent une application client et tous les fichiers statiques associés.

L'application Tornado est ensuite exécutée de la manière habituelle :

app.listen(port)
tornado.ioloop.IOLoop.current().start()

Eventlet

Remarque :

Eventlet n'est plus en développement actif et pour cette raison, la recommandation actuelle est de ne pas l'utiliser pour de nouveaux projets.

Eventlet http://eventlet.net/ est une bibliothèque de réseau concurrent haute performance pour Python qui utilise des coroutines, permettant d'écrire du code dans le même style que celui utilisé avec les fonctions bloquantes de la bibliothèque standard. Un serveur Socket.IO déployé avec eventlet a accès aux transports long-polling et WebSocket.

Les instances de la classe socketio.Server utiliseront automatiquement eventlet pour les opérations asynchrones si la bibliothèque est installée. Pour demander explicitement son utilisation, l'option async_mode peut être passée dans le constructeur :

sio = socketio.Server(async_mode='eventlet')

Un serveur configuré pour eventlet est déployé comme une application WSGI ordinaire en utilisant le socketio.WSGIApp fourni :

import eventlet
app = socketio.WSGIApp(sio)
eventlet.wsgi.server(eventlet.listen(('', 8000)), app)

Eventlet avec Gunicorn

Une alternative à l'exécution du serveur WSGI eventlet comme ci-dessus est d'utiliser gunicorn <gunicorn.org>, un serveur Web Python pur et complet. La commande pour lancer l'application sous gunicorn est montrée ci-dessous :

$ gunicorn -k eventlet -w 1 module:app

Voir la section Gunicorn ci-dessus pour des informations sur la façon d'utiliser Gunicorn avec plusieurs workers.

Eventlet fournit une fonction monkey_patch() qui remplace toutes les fonctions bloquantes de la bibliothèque standard par des versions asynchrones équivalentes. Bien que python-socketio ne nécessite pas de monkey patching, d'autres bibliothèques telles que les pilotes de base de données en auront probablement besoin.

Sanic

Remarque :

L'intégration Sanic n'a pas été mise à jour depuis longtemps. Il est actuellement recommandé de déployer une application Sanic avec l'intégration ASGI.

Utilisation d'une File de Messages

Lors du travail avec des applications distribuées, il est souvent nécessaire d'accéder à la fonctionnalité de Socket.IO à partir de plusieurs processus. Il existe deux cas d'utilisation spécifiques :

  • Les applications hautement disponibles peuvent vouloir utiliser la mise à l'échelle horizontale du serveur Socket.IO pour pouvoir gérer un très grand nombre de clients concurrents.
  • Les applications qui utilisent des files d'attente de travail comme Celery http://www.celeryproject.org/ peuvent avoir besoin d'émettre un événement à un client une fois qu'un travail de fond est terminé. L'endroit le plus pratique pour effectuer cette tâche est le processus worker qui a géré ce travail.

En solution aux problèmes ci-dessus, le serveur Socket.IO peut être configuré pour se connecter à une file de messages telle que Redis http://redis.io/ ou RabbitMQ https://www.rabbitmq.com/, afin de communiquer avec d'autres serveurs Socket.IO apparentés ou des workers auxiliaires.

Redis

Pour utiliser une file de messages Redis, un client Redis Python doit être installé :

# classe socketio.Server
pip install redis

La file d'attente Redis est configurée via les classes socketio.RedisManager <#socketio.RedisManager> et socketio.AsyncRedisManager <#socketio.AsyncRedisManager>. Ces classes se connectent directement au magasin Redis et utilisent la fonctionnalité pub/sub de la file d'attente :

# classe socketio.Server
mgr = socketio.RedisManager('redis://')
sio = socketio.Server(client_manager=mgr)
# classe socketio.AsyncServer
mgr = socketio.AsyncRedisManager('redis://')
sio = socketio.AsyncServer(client_manager=mgr)

L'argument client_manager indique au serveur de se connecter à la file de messages donnée et de coordonner avec d'autres processus connectés à la file d'attente.

Kombu

Kombu http://kombu.readthedocs.org/en/latest/ est un paquet Python qui fournit un accès à RabbitMQ et à de nombreuses autres files de messages. Il peut être installé avec pip :

pip install kombu

Pour utiliser RabbitMQ ou d'autres files compatibles avec le protocole AMQP, c'est la seule dépendance requise. Mais pour d'autres files de messages, Kombu peut nécessiter des paquets supplémentaires. Par exemple, pour utiliser une file d'attente Redis via Kombu, le paquet Python pour Redis doit également être installé :

pip install redis

La file d'attente est configurée via le socketio.KombuManager <#socketio.KombuManager> :

mgr = socketio.KombuManager('amqp://')
sio = socketio.Server(client_manager=mgr)

L'URL de connexion passée au constructeur de KombuManager est transmise directement à l'objet Connection de Kombu http://kombu.readthedocs.org/.

https://kombu.readthedocs.io/en/latest/userguide/connections.html, donc la documentation Kombu doit être consultée pour savoir comment construire l'URL correcte pour une file de messages donnée.

Notez que Kombu ne prend actuellement pas en charge asyncio, il ne peut donc pas être utilisé avec la classe socketio.AsyncServer <#socketio.AsyncServer>.

Kafka

Apache Kafka https://kafka.apache.org/ est pris en charge via le package kafka-python https://kafka-python.readthedocs.io/en/master/index.html :

pip install kafka-python

L'accès à Kafka est configuré via la classe socketio.KafkaManager <#socketio.KafkaManager> :

mgr = socketio.KafkaManager('kafka://')
sio = socketio.Server(client_manager=mgr)

Notez que Kafka ne prend actuellement pas en charge asyncio, il ne peut donc pas être utilisé avec la classe socketio.AsyncServer <#socketio.AsyncServer>.

AioPika

Une file de messages RabbitMQ est prise en charge dans les applications asyncio via le package AioPika https://aio-pika.readthedocs.io/en/latest/ : Il faut installer aio_pika avec pip :

pip install aio_pika

La file d'attente RabbitMQ est configurée via la classe socketio.AsyncAioPikaManager <#socketio.AsyncAioPikaManager> :

mgr = socketio.AsyncAioPikaManager('amqp://')
sio = socketio.AsyncServer(client_manager=mgr)

Déploiement de la file de messages pour la production

Pour un déploiement en production, quelques recommandations s'imposent pour sécuriser votre application.

Tout d'abord, la file de messages ne doit jamais écouter sur une interface réseau publique, afin de garantir que les clients externes ne s'y connectent jamais. Pour un déploiement sur un seul nœud, la file d'attente ne doit écouter que sur localhost. Pour un système multi-nœuds, l'utilisation d'un réseau privé (VPC), où la communication entre les serveurs peut se faire en privé, est fortement recommandée.

De plus, toutes les files de messages prennent en charge l'authentification et le chiffrement, ce qui peut renforcer la sécurité du déploiement. L'authentification garantit que seuls les serveurs Socket.IO et les processus associés y ont accès, tandis que le chiffrement empêche la collecte de données par un tiers qui écoute sur le réseau. Les identifiants d'accès peuvent être inclus dans les URL de connexion passées aux gestionnaires de clients.

Mise à l'échelle horizontale

Socket.IO est un protocole stateful, ce qui rend la mise à l'échelle horizontale plus difficile. Lors du déploiement d'un cluster de processus Socket.IO, tous les processus doivent se connecter à la file de messages en passant l'argument client_manager à l'instance du serveur. Cela permet aux workers de communiquer et de coordonner des opérations complexes telles que les diffusions.

Si le transport long-polling est utilisé, deux exigences supplémentaires doivent être satisfaites :

  • Chaque processus Socket.IO doit être capable de gérer plusieurs requêtes simultanément. Ceci est nécessaire car les clients en long-polling envoient deux requêtes en parallèle. Les processus workers qui ne peuvent gérer qu'une seule requête à la fois ne sont pas pris en charge.
  • Le répartiteur de charge doit être configuré pour transférer systématiquement les requêtes d'un client vers le même processus worker, afin que toutes les requêtes provenant d'un client soient gérées par le même nœud. Les répartiteurs de charge appellent cela des sessions persistantes, ou affinité de session.

Émission depuis des processus externes

Pour qu'un processus autre qu'un serveur se connecte à la file d'attente pour émettre un message, les mêmes classes de gestionnaires de clients peuvent être utilisées comme objets autonomes. Dans ce cas, l'argument write_only doit être défini sur True pour désactiver la création d'un thread d'écoute, ce qui n'a de sens que dans un serveur. Par exemple :

# se connecter à la file d'attente redis en tant que processus externe
external_sio = socketio.RedisManager('redis://', write_only=True)
# émettre un événement
external_sio.emit('my event', data={'foo': 'bar'}, room='my room')

Une limitation de l'objet gestionnaire de client en mode écriture seule est qu'il ne peut pas recevoir de rappels lors de l'émission. Lorsque le processus externe a besoin de recevoir des rappels, l'utilisation d'un client pour se connecter au serveur avec prise en charge de la lecture et de l'écriture est une meilleure option qu'un gestionnaire de client en mode écriture seule.

sio.on('message', message_handler)

Les arguments passés à la fonction de gestion dépendent du type d'événement :

  • Le gestionnaire d'événements 'connect' ne prend pas d'arguments.
  • Le gestionnaire d'événements 'disconnect' ne prend pas d'arguments.

    Les arguments passés à la fonction gestionnaire dépendent du type d'événement :

    • Le gestionnaire d'événements 'connect' reçoit l'identifiant de session (sid) du client et le dictionnaire d'environnement WSGI comme arguments.
    • Le gestionnaire 'disconnect' reçoit uniquement l'identifiant de session (sid) du client comme argument.
    • Le gestionnaire 'message' et les gestionnaires d'événements personnalisés reçoivent l'identifiant de session (sid) du client et la charge utile du message comme arguments. Toutes les valeurs retournées par un gestionnaire de message seront transmises à la fonction de rappel d'accusé de réception du client si elle existe.
    • Un gestionnaire d'événements générique reçoit le nom de l'événement comme premier argument, suivi des arguments spécifiques à l'événement.
    • Un gestionnaire d'événements d'espace de noms générique reçoit l'espace de noms comme premier argument, suivi des arguments spécifiques à l'événement.
    • Un gestionnaire d'événements d'espace de noms et d'événements génériques combiné reçoit le nom de l'événement comme premier argument et l'espace de noms comme deuxième argument, suivi des arguments spécifiques à l'événement.
