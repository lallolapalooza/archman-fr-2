NOM

pvmove — Déplacer les extents d'un volume physique vers un autre

SYNTAXE

pvmove args_positionnels
[ args_options ]
[ args_positionnels ]

DESCRIPTION

pvmove déplace les extents physiques alloués (PEs) d'un PV source vers un ou plusieurs PVs de destination. Vous pouvez éventuellement spécifier un LV source, auquel cas seuls les extents utilisés par ce LV seront déplacés vers des extents libres (ou spécifiés) sur le PV de destination. Si aucun PV de destination n'est spécifié, les règles d'allocation normales du VG sont utilisées.

Si pvmove est interrompu pour une raison quelconque (par exemple, une panne de la machine), relancez pvmove sans arguments de PV pour redémarrer toutes les opérations en cours depuis le dernier point de contrôle. Alternativement, utilisez l'option abort à tout moment pour annuler l'opération. L'emplacement résultant des LVs après une annulation dépend de l'utilisation ou non de l'option atomic.

Plusieurs pvmove peuvent s'exécuter simultanément s'ils déplacent des données depuis différents PVs sources, mais les pvmove supplémentaires ignoreront tous les LVs déjà en cours de modification, de sorte que certaines données pourraient ne pas être déplacées.

OPTIONS

--abort
Annuler toute opération pvmove en cours. Si un pvmove a été lancé avec l'option --atomic, tous les LVs resteront sur le PV source. Sinon, les segments qui ont été déplacés resteront sur le PV de destination, tandis que les segments non déplacés resteront sur le PV source.
--alloc contiguous|cling|cling_by_tags|normal|anywhere|inherit
Détermine la politique d'allocation lorsqu'une commande doit allouer des Extents Physiques (PEs) à partir du VG. Chaque VG et LV a une politique d'allocation qui peut être modifiée avec vgchange/lvchange, ou remplacée en ligne de commande. normal applique des règles de bon sens, comme ne pas placer de bandes parallèles sur le même PV. inherit applique la politique du VG à un LV. contiguous exige que les nouveaux PEs soient placés adjacents aux PEs existants. cling place les nouveaux PEs sur le même PV que les PEs existants dans la même bande du LV. S'il y a suffisamment de PEs pour une allocation, mais que normal ne les utilise pas, anywhere les utilisera même si cela réduit les performances, par exemple en plaçant deux bandes sur le même PV. Les arguments PV positionnels optionnels sur la ligne de commande peuvent également être utilisés pour limiter les PVs que la commande utilisera pour l'allocation. Voir lvm(8) pour plus d'informations sur l'allocation.
--atomic
Rend une opération pvmove atomique, garantissant que tous les LVs affectés sont déplacés vers le PV de destination, ou aucun si l'opération est annulée.
-A|--autobackup y|n
Spécifie si les métadonnées doivent être sauvegardées automatiquement après une modification. L'activation est fortement conseillée ! Voir vgcfgbackup(8) pour plus d'informations.
-b|--background
Si l'opération nécessite une surveillance, cette option fait que la commande retourne avant que l'opération ne soit terminée, et la surveillance s'effectue en arrière-plan.
--commandprofile Chaîne
Le profil de commande à utiliser pour la configuration de la commande. Voir lvm.conf(5) pour plus d'informations sur les profils.
--config Chaîne
Paramètres de configuration pour la commande. Ceux-ci remplacent les paramètres de lvm.conf(5). La chaîne d'arguments utilise le même format que lvm.conf(5), ou peut utiliser la syntaxe section/champ. Voir lvm.conf(5) pour plus d'informations sur la configuration.
-d|--debug ...
Définit le niveau de débogage. Répétez de 1 à 6 fois pour augmenter le détail des messages envoyés au fichier journal et/ou à syslog (si configuré).
--devices PV
Restreint les périphériques visibles et accessibles par la commande. Les périphériques non listés apparaîtront comme manquants. Cette option peut être répétée, ou accepte une liste de périphériques séparés par des virgules. Ceci remplace le fichier des périphériques.
--devicesfile Chaîne
Un fichier listant les périphériques que LVM doit utiliser. Le fichier doit exister dans /etc/lvm/devices/ et est géré avec la commande lvmdevices(8). Ceci remplace les paramètres devices/devicesfile et devices/use_devicesfile de lvm.conf(5).
--driverloaded y|n
Si défini sur non, la commande ne tentera pas d'utiliser device-mapper. Pour des tests et le débogage.
-h|--help
Affiche le texte d'aide.
-i|--interval Nombre
Rapporte la progression à intervalles réguliers.
--journal Chaîne
Enregistre des informations dans le journal systemd. Ces informations s'ajoutent aux informations activées par le paramètre log/journal de lvm.conf. command: enregistre des informations sur la commande. output: enregistre la sortie par défaut de la commande. debug: enregistre le débogage complet de la commande.
--lockopt Chaîne
Utilisé pour passer des options pour des cas spéciaux à lvmlockd. Voir lvmlockd(8) pour plus d'informations.
--longhelp
Affiche l'aide détaillée.
-n|--name Chaîne
Déplace uniquement les extents appartenant au LV nommé.
--nohints
N'utilise pas le fichier d'indices pour localiser les périphériques des PVs. Une commande peut lire plus de périphériques pour trouver les PVs lorsque les indices ne sont pas utilisés. La commande effectuera toujours une invalidation standard du fichier d'indices si nécessaire.
--nolocking
Désactive le verrouillage. Utiliser avec prudence, des commandes concurrentes peuvent produire des résultats incorrects.
--noudevsync
Désactive la synchronisation udev. Le processus n'attendra pas la notification de udev. Il continuera, indépendamment de tout traitement udev possible en arrière-plan.

OPTIONS

--allowprovenance
This option is intended to be used only when LVM metadata is copied from one VG to another (e.g., using vgcfgrestore(8)). It disables checks of the provenance (the UUID of the VG that created the metadata) and is intended to be used only when the provenance is expected to differ. This can be used to rename a VG if the VG name is kept and the VG UUID is changed.
--commandprofile String
The command profile to use for the operation. This profile provides information about which LVM commands can be run and what their default options are. See lvm.conf(5) for information on command profiles.
--config String
Allows for configuration data to be passed to the command. The data has to be in the LVM configuration format. See lvm.conf(5) for information about the expected format.
--debug
Enable detailed debugging output.
--devicesfile String

--driverloadedmodules String
Allows for the specification of loadable driver modules that should be loaded for the command. See lvm.conf(5) for information on the expected format.
--editll
When this option is used, LVM will attempt to edit the "ll" (logical link) metadata. This is only necessary when LVM is running without a running udev or has rules that ignore the devices LVM creates.
--metadataprofile String
The metadata profile to use for the operation. This profile provides information about how LVM metadata is stored and managed. See lvm.conf(5) for information on metadata profiles.
--partial
Allows processing of incomplete metadata. This can be useful when dealing with a damaged VG or when some PVs are missing. However, it may also lead to unpredictable behaviour if essential metadata is missing.
--profile String
An alias for --commandprofile or --metadataprofile, depending on the command.
-q|--quiet ...
Suppress output and log messages. Overrides --debug and --verbose. Repeat once to also suppress any prompts with answer 'no'.
--reportformat basic|json|json_std
Overrides current output format for reports which is defined globally by the report/output_format setting in lvm.conf(5). basic is the original format with columns and rows. If there is more than one report per command, each report is prefixed with the report name for identification. json produces report output in JSON format. json_std produces report output in JSON format which is more compliant with JSON standard. See lvmreport(7) for more information.
-t|--test
Run in test mode. Commands will not update metadata. This is implemented by disabling all metadata writing but nevertheless returning success to the calling function. This may lead to unusual error messages in multi-stage operations if a tool relies on reading back metadata it believes has changed but hasn't.
-v|--verbose ...
Set verbose level. Repeat from 1 to 4 times to increase the detail of messages sent to stdout and stderr.
--version
Display version information.
-y|--yes
Do not prompt for confirmation interactively but always assume the answer yes. Use with extreme caution. (For automatic no, see -qq.)

VARIABLES

PV
Physical Volume name, a device path under /dev. For commands managing physical extents, a PV positional arg generally accepts a suffix indicating a range (or multiple ranges) of physical extents (PEs). When the first PE is omitted, it defaults to the start of the device, and when the last PE is omitted it defaults to end.
Start and end range (inclusive): PV[:PE-PE] ...
Start and length range (counting from 0): PV[:PE+PE] ...
String
See the option description for information about the string content.
Size[UNIT]
Size is an input number that accepts an optional unit. Input units are always treated as base two values, regardless of capitalization, e.g. 'k' and 'K' both refer to 1024. The default input unit is specified by letter, followed by |UNIT. UNIT represents other possible input units: b|B is bytes, s|S is sectors of 512 bytes, k|K is KiB, m|M is MiB, g|G is GiB, t|T is TiB, p|P is PiB, e|E is EiB. (This should not be confused with the output control --units, where capital letters mean multiple of 1000.)

NOTES

pvmove works as follows:

1. A temporary 'pvmove' LV is created to store details of all the data movements required.

2. Every LV in the VG is searched for contiguous data that need moving according to the command line arguments. For each piece of data found, a new segment is added to the end of the pvmove LV. This segment takes the form of a temporary mirror to copy the data from the original location to a newly allocated location. The original LV is updated to use the new temporary mirror segment in the pvmove LV instead of accessing the data directly.

3. The VG metadata is updated on disk.

4. The first segment of the pvmove LV is activated and starts to mirror the first part of the data. Only one segment is mirrored at once as this is usually more efficient.

5. A daemon repeatedly checks progress at the specified time interval. When it detects that the first temporary mirror is in sync, it breaks that mirror so that only the new location for that data gets used and writes a checkpoint into the VG metadata on disk. Then it activates the mirror for the next segment of the pvmove LV.

6. When there are no more segments left to be mirrored, the temporary LV is removed and the VG metadata is updated so that the LVs reflect the new data locations.

Note that this new process cannot support the original LVM1 type of on-disk metadata. Metadata can be converted using vgconvert(8).

By default, pvmove will mirror an entire LV segment at once. If the process is interrupted (e.g. by a system crash or power failure) before the segment is fully mirrored, the entire segment must be mirrored again when pvmove is restarted. For very large segments, this can result in significant rework. The allocation/pvmove_max_segment_size_mb setting in lvm.conf(5) can be used to limit the maximum size of data mirrored in a single operation. When set to a non-zero value, pvmove will split large segments into smaller chunks of the specified size (in MiB), mirror each chunk, and update metadata between chunks. This ensures that at most one chunk needs to be re-mirrored after an interruption. For example, setting this to 10240 will limit each mirroring operation to 10 GiB. The default value of 0 means no limit - entire segments are mirrored at once.

If the --atomic option is used, a slightly different approach is used for the move. Again, a temporary 'pvmove' LV is created to store the details of all the data movements required. This temporary LV contains all the segments of the various LVs that need to be moved. However, in this case, an identical LV is allocated that contains the same number of segments and a mirror is created to copy the contents from the first temporary LV to the second. After a complete copy is made, the temporary LVs are removed, leaving behind the segments on the destination PV. If an abort is issued during the move, all LVs being moved will remain on the source PV.

EXAMPLES

Move all physical extents that are used by simple LVs on the specified PV to free physical extents elsewhere in the VG.
pvmove /dev/sdb1

Use a specific destination PV when moving physical extents.
pvmove /dev/sdb1 /dev/sdc1

Move extents belonging to a single LV.
pvmove -n lvol1 /dev/sdb1 /dev/sdc1

Rather than moving the contents of an entire device, it is possible to move a range of physical extents, for example numbers 1000 to 1999 inclusive on the specified PV.
pvmove /dev/sdb1:1000-1999

A range of physical extents to move can be specified as start+length. For example, starting from PE 1000. (Counting starts from 0, so this refers to the 1001st to the 2000th PE inclusive.)
pvmove /dev/sdb1:1000+1000

Move a range of physical extents to a specific PV (which must have sufficient free extents).
pvmove /dev/sdb1:1000-1999 /dev/sdc1

Move a range of physical extents to specific new extents on a new PV.
pvmove /dev/sdb1:1000-1999 /dev/sdc1:0-999

If the source and destination are on the same disk, the anywhere allocation policy is needed.
pvmove --alloc anywhere /dev/sdb1:1000-1999 /dev/sdb1:0-999

The part of a specific LV present within in a range of physical extents can also be picked out and moved.
pvmove -n lvol1 /dev/sdb1:1000-1999 /dev/sdc1
