NOM

perfdhcp - Outil d'évaluation comparative DHCP

SYNOPIS

perfdhcp [-1] [-4 | -6] [-A niveau-encapsulation] [-b base] [-B] [-c] [-C séparateur] [-d temps-perte] [-D max-perte] [-e type-bail] [-E décalage-temps] [-f taux-renouvellement] [-F taux-libération] [-g mode-thread] [-h] [-i] [-I décalage-ip] [-J fichier-liste-adresses-distantes] [-l adresse-locale|interface] [-L port-local] [-M fichier-liste-mac] [-n nb-requêtes] [-N port-distant] [-O décalage-aléatoire] [-o code,hexstring] [--or niveau-encapsulation:code,hexstring] [-p période-test] [-P préchargement] [-r taux] [-R nb-clients] [-s graine] [-S décalage-srvid] [--scenario nom] [-t rapport] [-T fichier-modèle] [-u] [-v] [-W temps-attente-sortie] [-w nom-script] [-x sélecteur-diagnostic] [-X décalage-xid] [serveur]

DESCRIPTION

perfdhcp est un outil d'évaluation comparative DHCP. Il offre un moyen de mesurer les performances des serveurs DHCP en générant une grande quantité de trafic à partir de plusieurs clients simulés. Il est capable de tester les serveurs IPv4 et IPv6, et fournit des statistiques concernant les temps de réponse et le nombre de requêtes qui sont perdues.

L'outil prend en charge deux scénarios différents, qui offrent des comportements à tester. Par défaut (le scénario de base), les tests sont exécutés en utilisant la séquence complète d'échange à quatre paquets (DORA pour DHCPv4, SARR pour DHCPv6). Une option est fournie pour exécuter les tests en utilisant l'échange initial à deux paquets (DO et SA) à la place. Il est également possible de configurer perfdhcp pour envoyer des messages RENEW et RELEASE DHCPv6 à un débit spécifié, en parallèle avec les échanges à quatre voies DHCPv6. Par défaut, si aucune réponse n'est reçue dans une seconde, une réponse est considérée comme perdue et perfdhcp continue avec d'autres transactions.

Un deuxième scénario, appelé avalanche, est sélectionné via --scenario avalanche. Il envoie d'abord le nombre de messages Discovery ou Solicit spécifié par l'option -R ; puis une retransmission (avec un mécanisme de retransmission exponentielle) est utilisée pour chaque client simulé, jusqu'à ce que toutes les requêtes soient répondues. Il génère un rapport lorsque tous les clients reçoivent leurs adresses, ou lorsqu'il est arrêté manuellement. Ce scénario tente de reproduire un cas où le serveur n'est pas en mesure de gérer le trafic assez rapidement. Les clients réels supposeront que le paquet ou la réponse a été perdu et retransmettront, augmentant encore le trafic DHCP. C'est parfois appelé un effet d'avalanche, d'où le nom du scénario. L'option -p est ignorée dans le scénario avalanche.

Lors de l'exécution d'un test de performance, perfdhcp échange des paquets avec le serveur testé aussi rapidement que possible, sauf si le paramètre -r est utilisé pour limiter le taux de requêtes. La durée du test peut être limitée en définissant un seuil sur le nombre de requêtes effectuées par perfdhcp, le temps écoulé, ou le nombre de requêtes perdues par le serveur.

MODÈLES

Pour permettre la personnalisation du contenu des paquets envoyés au serveur, perfdhcp permet la spécification de fichiers modèles qui déterminent le contenu des paquets. Par exemple, le paquet personnalisé peut contenir une option ORO DHCPv6 pour demander un ensemble d'options à retourner par le serveur, ou il peut contenir l'option Client FQDN pour demander au serveur d'effectuer des mises à jour DNS. Ceci peut être utilisé pour découvrir les goulets d'étranglement de performance pour différentes configurations de serveur (par exemple, DDNS activé ou désactivé).

Jusqu'à deux fichiers modèles peuvent être spécifiés sur la ligne de commande, chaque fichier représentant le contenu d'un type de paquet particulier, le type étant déterminé par le test effectué. Par exemple, lors du test de DHCPv6 :

  • Sans aucun fichier modèle spécifié sur la ligne de commande, perfdhcp génère les paquets Solicit et Request.
  • Avec un fichier modèle spécifié, ce fichier est utilisé comme modèle pour les paquets Solicit : perfdhcp génère les paquets Request.
  • Avec deux fichiers modèles donnés sur la ligne de commande, le premier est utilisé comme modèle pour les paquets Solicit, et le second comme modèle pour les paquets Request.

(Une détermination similaire s'applique aux paquets DHCPDISCOVER et DHCPREQUEST de DHCPv4.)

Le fichier modèle contient le paquet DHCP, représenté comme un flux de chiffres hexadécimaux ASCII ; il exclut tout en-tête de pile IP/UDP. Le fichier modèle ne doit pas contenir d'autres caractères que des chiffres hexadécimaux et des espaces. Les espaces sont ignorés lors de l'analyse du fichier modèle ; dans le fichier, 12B4 est identique à 12 B4, qui est identique à 1 2 B 4.

Les fichiers modèles doivent être utilisés conjointement avec les paramètres de la ligne de commande qui spécifient les décalages des champs de données modifiés dans les paquets sortants. Par exemple, le commutateur -E time-offset spécifie le décalage de l'option Elapsed Time de DHCPv6 dans le modèle de paquet. Si le décalage est spécifié, perfdhcp injecte la valeur actuelle du temps écoulé dans ce champ avant d'envoyer le paquet au serveur.

Dans de nombreux scénarios, perfdhcp a besoin de simuler plusieurs clients, chacun ayant un identifiant client unique. Puisque les paquets pour chaque client sont générés à partir du même fichier modèle, il est nécessaire de randomiser l'identifiant client (ou l'adresse MAC en DHCPv4) dans le paquet créé à partir de celui-ci. L'option -O random-offset permet de spécifier le décalage dans le modèle où la randomisation doit être effectuée. Il est important de noter que ce décalage pointe vers la fin (et non le début) de l'identifiant client (ou du champ d'adresse MAC). Le nombre d'octets randomisés dépend du nombre de clients simulés. Si le nombre de clients simulés est compris entre 1 et 255, un seul octet (vers lequel pointe le décalage de randomisation) est randomisé. Si le nombre de clients simulés est compris entre 256 et 65535, deux octets sont randomisés. Notez que les deux derniers octets de l'identifiant client sont randomisés dans ce cas : l'octet vers lequel pointe le paramètre de décalage de randomisation, et celui qui le précède (décalage de randomisation - 1). Si le nombre de clients simulés dépasse 65535, trois octets sont randomisés, et ainsi de suite.

perfdhcp peut simuler du trafic provenant de plusieurs sous-réseaux en activant l'option -J et en passant un chemin vers un fichier qui contient des adresses v4 ou v6 à utiliser comme relais dans les messages générés. Cela permet de tester un grand nombre de réseaux partagés Kea. Lors du test de DHCPv4, Kea doit être démarré avec la variable d'environnement KEA_TEST_SEND_RESPONSES_TO_SOURCE, pour forcer Kea à envoyer les messages générés à l'adresse source du paquet entrant.

Les modèles peuvent actuellement être utilisés pour générer les paquets envoyés au serveur dans les échanges à 4 voies, c'est-à-dire Solicit, Request (DHCPv6) et DHCPDISCOVER, DHCPREQUEST (DHCPv4). Ils ne peuvent pas être utilisés lors de l'envoi de paquets Renew ou DHCPRELEASE.

DESCRIPTION

The perfdhcp utility is a load testing tool for DHCP servers. It is designed to simulate a large number of clients requesting IP addresses from DHCP servers. It can be used for both DHCPv4 and DHCPv6 protocols.

The program sends out DHCP messages at a specified rate, and measures the server's response time. It can also simulate various client behaviors, such as requesting specific IP addresses or prefixes, and handling lease renewals and releases.

The program supports a wide range of options to customize the simulation, including specifying the number of clients, the rate of requests, the type of requests, and the protocol version (IPv4 or IPv6).

The program generates reports on the performance of the DHCP server, including the number of successful and failed requests, response times, and other relevant metrics.

-C client-hostname
Forces the client hostname to be client-hostname. This option is only valid for DHCPv4.
-D
Causes DHCPDISCOVER/DHCPREQUEST messages to be sent.
-d
Causes DHCPDISCOVER/DHCPREQUEST messages to be sent. This is a synonym for -D.
-E prefix-only|address-and-prefix
Specifies the type of IPv6 addresses or prefixes requested.

prefix-only: Only IPv6 prefixes are requested.

address-and-prefix: Both IPv6 addresses and prefixes are requested.

This option is only valid when -6 is specified.

-e prefix-only|address-and-prefix
Only IPv6 prefixes (prefix-only) or both IPv6 addresses and prefixes (address-and-prefix) are requested.
-f renew-rate
Specifies the rate at which DHCPv4 DHCPREQUEST or DHCPv6 Renew requests are sent to a server. This value is only valid when used in conjunction with the exchange rate (given by -r rate). Furthermore, the sum of this value and the release-rate (given by -F rate) must be equal to or less than the exchange rate.
-g thread-mode
Allows selection of thread-mode, which can be either single or multi. In multi-thread mode, packets are received in a separate thread, which allows better utilisation of CPUs. In a single-CPU system it is better to run in one thread, to avoid threads blocking each other. If more than one CPU is present in the system, multi-thread mode is the default; otherwise single-thread is the default.
-h
Prints help and exits.
-i
Performs only the initial part of the exchange: DISCOVER-OFFER if -4 is selected, Solicit-Advertise if -6 is chosen.

-i is incompatible with the following options: -1, -d, -D, -E, -S, -I and -F. In addition, it cannot be used with multiple instances of -O, -T, and -X.

-I iaid
Specifies the Identity Association identifier (IAID) for the client. This option is only valid for DHCPv6.
-J remote-address-list-file
Specifies a text file that includes multiple addresses, and is designed to test shared networks. If provided, perfdhcp randomly chooses one of the addresses for each exchange, to generate traffic from multiple subnets. When testing DHCPv4, it should be started with the KEA_TEST_SEND_RESPONSES_TO_SOURCE=ENABLE environment variable; otherwise, perfdhcp will not be able to receive responses.
-l local-addr|interface
For DHCPv4 operation, specifies the local hostname/address to use when communicating with the server. By default, the interface address through which traffic would normally be routed to the server is used. For DHCPv6 operation, specifies the name of the network interface through which exchanges are initiated.
-L local-port
Specifies the local port to use. This must be zero or a positive integer up to 65535. A value of 0 (the default) allows perfdhcp to choose its own port.
-M mac-list-file
Specifies a text file containing a list of MAC addresses, one per line. If provided, a MAC address is chosen randomly from this list for every new exchange. In DHCPv6, MAC addresses are used to generate DUID-LLs. This parameter must not be used in conjunction with the -b parameter.
-N remote-port
Specifies the remote port to use. This must be zero or a positive integer up to 65535. A value of 0 (the default) allows perfdhcp to choose the standard service port.
-O options

The options string should be a comma-separated list of option codes and their hexadecimal values. Forces perfdhcp to insert the specified extra option (or options if used several times) into packets being transmitted. The code specifies the option code and the hexstring is a hexadecimal string that defines the content of the option. Care should be taken as perfdhcp does not offer any kind of logic behind those options; they are simply inserted into packets and sent as is. Be careful not to duplicate options that are already inserted. For example, to insert client class identifier (option code 60) with a string "docsis", use "-o 60,646f63736973". The -o may be used multiple times. It is necessary to specify the protocol family (either -4 or -6) before using -o.
-P preload
Initiates preload exchanges back-to-back at startup. Must be 0 (the default) or a positive integer.
-p port
Specifies the destination port for DHCP messages. This must be a positive integer up to 65535. The default is 67 for DHCPv4 and 547 for DHCPv6.
-q count
Specifies the number of messages to send per client. The default is 1.
-r rate
Initiates the rate of DORA/SARR (or if -i is given, DO/SA) exchanges per second. A periodic report is generated showing the number of exchanges which were not completed, as well as the average response latency. The program continues until interrupted, at which point a final report is generated.
-R num-clients
Specifies how many different clients are used. With a value of 1 (the default), all requests appear to come from the same client. Must be a positive number.
-s seed
Specifies the seed for randomization, making runs of perfdhcp repeatable. This must be 0 or a positive integer. The value 0 means that a seed is not used; this is the default.
-S server-id
Specifies the server identifier to use in DHCP messages. This option is only valid for DHCPv4.

Specifies the type of scenario, and can be basic (the default) or avalanche.

-u

-v

Specifies the exit-wait-time parameter, which causes perfdhcp to wait for a certain amount of time after an exit condition has been met, to receive all packets without sending any new packets. EXIT STATUS

The perfdhcp utility exits with one of the following values:

0
Successful completion.
1
An error occurred.
2
The maximum number of exchanges was reached.

EXAMPLES

To test a DHCPv4 server with 1000 clients sending requests at a rate of 100 requests per second, use:

        perfdhcp -4 -r 100 -R 1000 server_ip

To test a DHCPv6 server with 500 clients sending rapid-commit requests at a rate of 50 requests per second, use:

        perfdhcp -6 -c -r 50 -R 500 server_ip

ERREURS

perfdhcp peut signaler les erreurs suivantes dans l'échange de paquets :

tooshort
Un message a été reçu qui était trop court.
orphans
Un message a été reçu qui ne correspond à aucun message envoyé au serveur (c'est-à-dire qu'il s'agit d'un message dupliqué, d'un message arrivé après un délai excessif, ou d'un message simplement non reconnu).
locallimit
Les limites du système local ont été atteintes lors de l'envoi d'un message.

2

Aucune défaillance générale dans l'opération, mais un ou plusieurs échanges n'ont pas abouti.

EXEMPLES D'UTILISATION

Voici un exemple qui simule le trafic DHCPv4 régulier de 100 périphériques DHCPv4 (-R 100), 10 paquets par seconde (-r 10), affiche les détails du taux de requêtes/réponses (-xi), affiche un rapport toutes les 2 secondes (-t 2) et envoie les paquets à l'IP 192.0.2.1 :

sudo perfdhcp -xi -t 2 -r 10 -R 100 192.0.2.1

Voici un cas similaire, mais pour DHCPv6. Notez que le protocole DHCPv6 utilise des adresses de lien local, l'interface (eth0 dans cet exemple) doit donc être spécifiée sur laquelle envoyer le trafic. all est un alias pratique pour All_DHCP_Relay_Agents_and_Servers (l'adresse multicast FF02::1:2). Il est également possible d'utiliser l'alias servers pour faire référence à All_DHCP_Servers (l'adresse multicast FF05::1:3). La valeur par défaut est all.

sudo perfdhcp -6 -xi -t 1 -r 1 -R 10 -l eth0 all

Les exemples suivants simulent un trafic DHCPv4 et DHCPv6 normal qui, après 3 secondes, commence à prétendre ne pas recevoir de réponses du serveur pendant 10 secondes. Le protocole DHCPv4 signale cela par un champ secs accru, tandis que DHCPv6 utilise l'option Elapsed Time. Dans les réseaux réels, cela indique que les clients ne reçoivent pas de réponses en temps voulu. Ceci peut être utilisé pour simuler certains scénarios HA, car Kea utilise le champ secs et la valeur de l'option Elapsed Time comme indicateurs que le partenaire HA ne répond pas. Lorsqu'activées avec -y et -Y, les valeurs secs et Elapsed Time augmentent régulièrement.

sudo perfdhcp -xi -t 1 -r 1 -y 10 -Y 3 192.0.2.1
sudo perfdhcp -6 -xi -t 1 -r 1 -y 10 -Y 3 2001:db8::1

DOCUMENTATION

Kea est fourni avec un manuel de référence étendu pour l'administrateur Kea qui couvre tous les aspects de l'exécution du logiciel Kea : compilation, installation, configuration, exemples de configuration, et bien plus encore. Kea dispose également d'un manuel des messages Kea, qui liste tous les messages possibles que Kea peut imprimer avec une brève description pour chacun d'eux. Les deux documents sont disponibles dans divers formats (.txt, .html, .pdf) avec la distribution Kea. La documentation Kea est disponible sur https://kea.readthedocs.io.

Le code source de Kea est documenté dans le guide du développeur Kea, disponible sur https://reports.kea.isc.org/dev_guide/.

Le site Web du projet Kea est disponible sur https://kea.isc.org.

LISTES DE DIFFUSION ET SUPPORT

Il existe deux listes de diffusion publiques disponibles pour le projet Kea. kea-users (kea-users at lists.isc.org) est destinée aux utilisateurs de Kea, tandis que kea-dev (kea-dev at lists.isc.org) est destinée aux développeurs de Kea, aux contributeurs potentiels et à d'autres utilisateurs avancés. Les deux listes sont disponibles sur https://lists.isc.org. La communauté fournit un support au mieux de ses capacités sur ces deux listes.

ISC fournit un support professionnel pour les services Kea. Voir https://www.isc.org/kea/ pour plus de détails.
