Paquets

Contrairement à Perl 4, où toutes les variables étaient dynamiques et partageaient un espace de noms global, causant des problèmes de maintenabilité, Perl 5 fournit deux mécanismes pour protéger le code contre l'écrasement de ses variables par d'autres codes : les variables à portée lexicale créées avec "my" ou "state" et les variables globales nommées, exposées via le pragma "vars", ou le mot-clé "our". Toute variable globale est considérée comme faisant partie d'un espace de noms et peut être accessible via une "forme pleinement qualifiée". Inversement, toute variable à portée lexicale est considérée comme faisant partie de cette portée lexicale et n'a pas de "forme pleinement qualifiée".

En perl, les espaces de noms sont appelés "paquets" et la déclaration "package" indique au compilateur quel espace de noms préfixer aux variables "our" et aux noms dynamiques non qualifiés. Cela protège contre les écrasements accidentels et fournit une interface pour écraser délibérément les variables globales dynamiques déclarées et utilisées dans d'autres portées ou paquets, lorsque c'est ce que vous voulez faire.

La portée de la déclaration "package" s'étend de la déclaration elle-même jusqu'à la fin du bloc englobant, de l'"eval", ou du fichier, le premier arrivé étant le premier servi (la même portée que les opérateurs my(), our(), state() et local(), et aussi l'effet de « l'alias de référence » expérimental, qui pourrait changer), ou jusqu'à la prochaine déclaration "package". Les identificateurs non qualifiés seront dans cet espace de noms, à l'exception de quelques identificateurs qui, s'ils sont non qualifiés, par défaut dans le paquet principal plutôt que dans celui courant, comme décrit ci-dessous. Une instruction "package" n'affecte que les symboles dynamiques globaux, y compris les noms de sous-programmes, et les variables sur lesquelles vous avez utilisé local(), mais *pas* les variables lexicales créées avec my(), our() ou state().

Typiquement, une déclaration "package" est la première déclaration dans un fichier inclus dans un programme par l'un des opérateurs "do", "require" ou "use". Vous pouvez basculer vers un paquet à plusieurs endroits : "package" n'a aucun effet au-delà de la spécification de la table de symboles que le compilateur utilisera pour les symboles dynamiques pour le reste de ce bloc ou jusqu'à la prochaine déclaration "package". Vous pouvez référencer des variables et des fichiers ouverts dans d'autres paquets en préfixant l'identificateur avec le nom du paquet et deux-points : $Paquet::Variable. Si le nom du paquet est nul, le paquet "main" est supposé. C'est-à-dire que $::sail est équivalent à $main::sail.

L'ancien délimiteur de paquet était une apostrophe, mais le double point est maintenant le délimiteur préféré, en partie parce qu'il est plus lisible par les humains, et en partie parce qu'il est plus lisible par les macros emacs. Il donne également aux programmeurs C++ l'impression de savoir ce qui se passe - contrairement à l'utilisation de l'apostrophe comme séparateur, qui était là pour donner aux programmeurs Ada l'impression de savoir ce qui se passe. Comme la syntaxe à l'ancienne est toujours prise en charge pour la compatibilité ascendante, si vous essayez d'utiliser une chaîne comme "Ceci est la maison de $proprietaire", vous accéderez à $proprietaire::s ; c'est-à-dire la variable $s dans le paquet "proprietaire", ce qui n'est probablement pas ce que vous vouliez. Utilisez des accolades pour désambiguïser, comme dans "Ceci est la maison de ${proprietaire}".

L'utilisation de "'" comme délimiteur de paquet peut être désactivée avec :

no feature 'apostrophe_as_package_separator';

et est également désactivée par "use v5.42;" ou une version ultérieure.

Les paquets peuvent eux-mêmes contenir des séparateurs de paquets, comme dans $EXTERNEUR::INTERNEUR::var. Cela n'implique cependant rien sur l'ordre des recherches de noms. Il n'y a pas de paquets relatifs : tous les symboles sont soit locaux au paquet courant, soit doivent être entièrement qualifiés depuis le nom du paquet externe vers le bas. Par exemple, il n'y a nulle part dans le paquet "EXTERNEUR" où $INTERNEUR::var fait référence à $EXTERNEUR::INTERNEUR::var. "INTERNEUR" fait référence à un paquet global totalement séparé. La coutume de traiter les noms de paquets comme une hiérarchie est très forte, mais le langage ne l'impose en aucun cas.

Seuls les identificateurs commençant par des lettres (ou un trait de soulignement) sont stockés dans la table de symboles d'un paquet. Tous les autres symboles sont conservés dans le paquet "main", y compris toutes les variables de ponctuation, comme $_. De plus, lorsqu'ils sont non qualifiés, les identificateurs STDIN, STDOUT, STDERR, ARGV, ARGVOUT, ENV, INC et SIG sont forcés d'être dans le paquet "main", même lorsqu'ils sont utilisés à des fins autres que leurs fonctions intégrées. Si vous avez un paquet appelé "m", "s", ou "y", alors vous ne pouvez pas utiliser la forme qualifiée d'un identificateur car il serait plutôt interprété comme une correspondance de modèle, une substitution, ou une translittération.

Les variables commençant par un trait de soulignement étaient autrefois forcées dans le paquet main, mais nous avons décidé qu'il était plus utile pour les auteurs de paquets de pouvoir utiliser un trait de soulignement initial pour indiquer les variables privées et les noms de méthodes. Cependant, les variables et fonctions nommées avec un seul "_", comme $_ et "sub _", sont toujours forcées dans le paquet "main". Voir également « La syntaxe des noms de variables » dans perlvar.

Les chaînes "eval" sont compilées dans le paquet dans lequel eval() a été compilé. (Les affectations à "$SIG{}", cependant, supposent que le gestionnaire de signaux spécifié est dans le paquet "main". Qualifiez le nom du gestionnaire de signaux si vous souhaitez avoir un gestionnaire de signaux dans un paquet.) Pour un exemple, examinez perldb.pl dans la bibliothèque Perl. Il bascule initialement vers le paquet "DB" afin que le débogueur n'interfère pas avec les variables du programme que vous essayez de déboguer. À divers moments, cependant, il bascule temporairement vers le paquet "main" pour évaluer diverses expressions dans le contexte du paquet "main" (ou d'où vous veniez). Voir perldebug.

Le symbole spécial "__PACKAGE__" contient le paquet courant, mais ne peut pas (facilement) être utilisé pour construire des noms de variables. Après que my($foo) ait caché la variable de paquet $foo, elle peut toujours être accédée, sans savoir dans quel paquet vous vous trouvez, comme "${__PACKAGE__.'::foo'}".

Voir perlsub pour d'autres problèmes de portée liés à my() et local(), et perlref concernant les fermetures (closures).

TYPEGLOBS

You use the *name typeglob notation.

local *main::foo    = *main::bar;

You can use this to print out all the variables in a package, for instance. The standard but antiquated dumpvar.pl library and the CPAN module Devel::Symdump make use of this.

The results of creating new symbol table entries directly or modifying any entries that are not already typeglobs are undefined and subject to change between releases of perl.

Assignment to a typeglob performs an aliasing operation, i.e.,

*dick = *richard;

causes variables, subroutines, formats, and file and directory handles accessible via the identifier "richard" also to be accessible via the identifier "dick". If you want to alias only a particular variable or subroutine, assign a reference instead:

*dick = \$richard;

Which makes $richard and $dick the same variable, but leaves @richard and @dick as separate arrays. Tricky, eh?

There is one subtle difference between the following statements:

*foo = *bar;
*foo = \$bar;

"*foo = *bar" makes the typeglobs themselves synonymous while "*foo = \$bar" makes the SCALAR portions of two distinct typeglobs refer to the same scalar value. This means that the following code:

$bar = 1;
*foo = \$bar;       # Make $foo an alias for $bar
{
    local $bar = 2; # Restrict changes to block
    print $foo;     # Prints '1'!
}

would print '1', because $foo holds a reference to the original $bar. The one that was stuffed away by local() and which will be restored when the block ends. Because variables are accessed through the typeglob, you can use "*foo = *bar" to create an alias which can be localized. (But be aware that this means you can't have a separate @foo and @bar, etc.)

What makes all of this important is that the Exporter module uses glob aliasing as the import/export mechanism. Whether or not you can properly localize a variable that has been exported from a module depends on how it was exported:

@EXPORT = qw($FOO); # Usual form, can't be localized
@EXPORT = qw(*FOO); # Can be localized

You can work around the first case by using the fully qualified name ($Package::FOO) where you need a local value, or by overriding it by saying "*FOO = *Package::FOO" in your script.

The "*x = \$y" mechanism may be used to pass and return cheap references into or from subroutines if you don't want to copy the whole thing. It only works when assigning to dynamic variables, not lexicals.

%some_hash = ();                    # can't be my()
*some_hash = fn( \%another_hash );
sub fn {
    local *hashsym = shift;
    # now use %hashsym normally, and you
    # will affect the caller's %another_hash
    my %nhash = (); # do what you want
    return \%nhash;
}

On return, the reference will overwrite the hash slot in the symbol table specified by the *some_hash typeglob. This is a somewhat tricky way of passing around references cheaply when you don't want to have to remember to dereference variables explicitly.

Another use of symbol tables is for making "constant" scalars.

*PI = \3.14159265358979;

Now you cannot alter $PI, which is probably a good thing all in all. This isn't the same as a constant subroutine, which is subject to optimization at compile-time. A constant subroutine is one prototyped to take no arguments and to return a constant expression. See perlsub for details on these. The "use constant" pragma is a convenient shorthand for these.

You can say *foo{PACKAGE} and *foo{NAME} to find out what name and package the *foo symbol table entry comes from. This may be useful in a subroutine that gets passed typeglobs as arguments:

sub identify_typeglob {
    my $glob = shift;
    print 'You gave me ', *{$glob}{PACKAGE},
        '::', *{$glob}{NAME}, "\n";
}
identify_typeglob *foo;
identify_typeglob *bar::baz;

This prints

You gave me main::foo
You gave me bar::baz

The *foo{THING} notation can also be used to obtain references to the individual elements of *foo. See perlref.

Subroutine definitions (and declarations, for that matter) need not necessarily be situated in the package whose symbol table they occupy. You can define a subroutine outside its package by explicitly qualifying the name of the subroutine:

package main;
sub Some_package::foo { ... }   # &foo defined in Some_package

This is just a shorthand for a typeglob assignment at compile time:

BEGIN { *Some_package::foo = sub { ... } }

and is not the same as writing:

{
    package Some_package;
    sub foo { ... }
}

In the first two versions, the body of the subroutine is lexically in the main package, not in Some_package. So something like this:

package main;
$Some_package::name = "fred";
$main::name = "barney";
sub Some_package::foo {
    print "in ", __PACKAGE__, ": \$name is '$name'\n";
}
Some_package::foo();

prints:

in main: $name is 'barney'

rather than:

in Some_package: $name is 'fred'

This also has implications for the use of the SUPER:: qualifier (see perlobj).

BEGIN, UNITCHECK, CHECK, INIT and END

Five specially named code blocks are executed at the beginning and at the end of a running Perl program. These are the "BEGIN", "UNITCHECK", "CHECK", "INIT", and "END" blocks.

These code blocks can be prefixed with "sub" to give the appearance of a subroutine (although this is not considered good style). One should note that these code blocks don't really exist as named subroutines (despite their appearance). The thing that gives this away is the fact that you can have more than one of these code blocks in a program, and they will get all executed at the appropriate moment. So you can't execute any of these code blocks by name.

A "BEGIN" code block is executed as soon as possible, that is, the moment it is completely defined, even before the rest of the containing file (or string) is parsed. You may have multiple "BEGIN" blocks within a file (or eval'ed string); they will execute in order of definition. Because a "BEGIN" code block executes immediately, it can pull in definitions of subroutines and such from other files in time to be visible to the rest of the compile and run time. Once a "BEGIN" has run, it is immediately undefined and any code it used is returned to Perl's memory pool.

An "END" code block is executed as late as possible, that is, after perl has finished running the program and just before the interpreter is being exited, even if it is exiting as a result of a die() function. (But not if it's morphing into another program via "exec", or being blown out of the water by a signal--you have to trap that yourself (if you can).) You may have multiple "END" blocks within a file--they will execute in reverse order of definition; that is: last in, first out (LIFO). "END" blocks are not executed when you run perl with the "-c" switch, or if compilation fails.

Note that "END" code blocks are not executed at the end of a string eval(): if any "END" code blocks are created in a string eval(), they will be executed just as any other "END" code block of that package in LIFO order just before the interpreter is being exited.

Inside an "END" code block, $? contains the value that the program is going to pass to exit(). You can modify $? to change the exit value of the program. Beware of changing $? by accident (e.g. by running something via "system").

Inside of a "END" block, the value of "${^GLOBAL_PHASE}" will be "END".

Similar to an "END" block are "defer" blocks, though they operate on the lifetime of individual block scopes, rather than the program as a whole. They are documented in "defer" in perlsyn.

"UNITCHECK", "CHECK" and "INIT" code blocks are useful to catch the transition between the compilation phase and the execution phase of the main program.

"UNITCHECK" blocks are run just after the unit which defined them has been compiled. The main program file and each module it loads are compilation units, as are string "eval"s, run-time code compiled using the "(?{ })" construct in a regex, calls to "do FILE", "require FILE", and code after the "-e" switch on the command line.

"BEGIN" and "UNITCHECK" blocks are not directly related to the phase of the interpreter. They can be created and executed during any phase.

"CHECK" code blocks are run just after the initial Perl compile phase ends and before the run time begins, in LIFO order. "CHECK" code blocks are used in the Perl compiler suite to save the compiled state of the program.

Inside of a "CHECK" block, the value of "${^GLOBAL_PHASE}" will be "CHECK".

"INIT" code blocks are run just after the initial Perl run time begins, in LIFO order. "INIT" code blocks are used in the Perl compiler suite to initialize the program's runtime state.

Inside of an "INIT" block, the value of "${^GLOBAL_PHASE}" will be "RUN".

Blocs spéciaux Perl

"BEGIN" blocks are run just before Perl starts compiling the code, in "last in, first out" (LIFO) order.

Inside of a "BEGIN" block, the value of "${^GLOBAL_PHASE}" will be "CHECK".

"INIT" blocks are run just before the Perl runtime begins execution, in "first in, first out" (FIFO) order.

Inside of an "INIT" block, the value of "${^GLOBAL_PHASE}" will be "INIT".

The "CHECK" and "INIT" blocks in code compiled by "require", string "do", or string "eval" will not be executed if they occur after the end of the main compilation phase; that can be a problem in mod_perl and other persistent environments which use those functions to load code at runtime.

When you use the -n and -p switches to Perl, "BEGIN" and "END" work just as they do in awk, as a degenerate case. Both "BEGIN" and "CHECK" blocks are run when you use the -c switch for a compile-only syntax check, although your main code is not.

The begincheck program makes it all clear, eventually:

#!/usr/bin/perl
# begincheck
print         "10. Ordinary code runs at runtime.\n";
END { print   "16.   So this is the end of the tale.\n" }
INIT { print  " 7. INIT blocks run FIFO just before runtime.\n" }
UNITCHECK {
  print       " 4.   And therefore before any CHECK blocks.\n"
}
CHECK { print " 6.   So this is the sixth line.\n" }
print         "11.   It runs in order, of course.\n";
BEGIN { print " 1. BEGIN blocks run FIFO during compilation.\n" }
END { print   "15.   Read perlmod for the rest of the story.\n" }
CHECK { print " 5. CHECK blocks run LIFO after all compilation.\n" }
INIT { print  " 8.   Run this again, using Perl's -c switch.\n" }
print         "12.   This is anti-obfuscated code.\n";
END { print   "14. END blocks run LIFO at quitting time.\n" }
BEGIN { print " 2.   So this line comes out second.\n" }
UNITCHECK {
 print " 3. UNITCHECK blocks run LIFO after each file is compiled.\n"
}
INIT { print  " 9.   You'll see the difference right away.\n" }
print         "13.   It only _looks_ like it should be confusing.\n";
__END__

Classes Perl

Il n'y a pas de syntaxe de classe stable en Perl, mais un paquet peut agir comme une classe s'il fournit des sous-routines pour agir comme des méthodes. Un tel paquet peut également dériver certaines de ses méthodes d'une autre classe (paquet) en listant le(s) autre(s) nom(s) de paquet dans son tableau global @ISA (qui doit être un global de paquet, pas un lexical).

Pour en savoir plus sur les paquets agissant comme des classes, consultez perlootut et perlobj. Pour en savoir plus sur la syntaxe de classe non encore stable, consultez perlclass.

Modules Perl

Un module est juste un ensemble de fonctions liées dans un fichier de bibliothèque, c'est-à-dire un paquet Perl portant le même nom que le fichier. Il est spécifiquement conçu pour être réutilisable par d'autres modules ou programmes. Il peut le faire en fournissant un mécanisme pour exporter certains de ses symboles dans la table des symboles de tout paquet l'utilisant, ou il peut fonctionner comme une définition de classe et rendre ses sémantiques disponibles implicitement par des appels de méthode sur la classe et ses objets, sans exporter explicitement quoi que ce soit. Ou il peut faire un peu des deux.

Par exemple, pour démarrer un module traditionnel non orienté objet appelé Some::Module, créez un fichier appelé Some/Module.pm et commencez avec ce modèle :

package Some::Module;  # suppose Some/Module.pm
use v5.36;
# Récupère la méthode d'importation d'Exporter pour exporter des fonctions et
# des variables
use Exporter 5.57 'import';
# définit la version pour la vérification de version
our $VERSION     = '1.00';
# Fonctions et variables exportées par défaut
our @EXPORT      = qw(func1 func2);
# Fonctions et variables pouvant être exportées optionnellement
our @EXPORT_OK   = qw($Var1 %Hashit func3);
# les globaux de paquet exportés vont ici
our $Var1    = '';
our %Hashit  = ();
# les globaux de paquet non exportés vont ici
# (ils sont toujours accessibles en tant que $Some::Module::stuff)
our @more    = ();
our $stuff   = '';
# les léxicaux privés au fichier vont ici, avant toute fonction qui les utilise
my $priv_var    = '';
my %secret_hash = ();
# voici une fonction privée au fichier sous forme de fermeture,
# appelable en tant que $priv_func->();
my $priv_func = sub {
    ...
};
# faites toutes vos fonctions, qu'elles soient exportées ou non;
# n'oubliez pas de mettre quelque chose d'intéressant dans les {} stubs
sub func1      { ... }
sub func2      { ... }
# celle-ci n'est pas toujours exportée, mais pourrait être appelée directement
# comme Some::Module::func3()
sub func3      { ... }
END { ... }       # code de nettoyage du module ici (destructeur global)
1;  # n'oubliez pas de retourner une valeur vraie depuis le fichier

Ensuite, déclarez et utilisez vos variables dans des fonctions sans aucune qualification. Consultez Exporter et perlmodlib pour plus de détails sur la mécanique et le style de création de modules.

Les modules Perl sont inclus dans votre programme en disant

use Module;

ou

use Module LIST;

Ceci est exactement équivalent à

BEGIN { require 'Module.pm'; 'Module'->import; }

ou

BEGIN { require 'Module.pm'; 'Module'->import( LIST ); }

Comme cas spécial

use Module ();

est exactement équivalent à

BEGIN { require 'Module.pm'; }

Tous les fichiers de module Perl ont l'extension .pm. L'opérateur "use" suppose cela, vous n'avez donc pas à épeler "Module.pm" entre guillemets. Cela aide également à différencier les nouveaux modules des anciens fichiers .pl et .ph. Les noms de modules sont également capitalisés, sauf s'ils fonctionnent comme des pragmas; les pragmas sont des directives de compilateur, et sont parfois appelés "modules pragmatiques" (ou même "pragmata" si vous êtes un classiciste).

Les deux instructions :

require SomeModule;
require "SomeModule.pm";

diffèrent l'une de l'autre de deux manières. Dans le premier cas, tous les doubles deux-points dans le nom du module, tels que "Some::Module", sont traduits en séparateur de répertoire de votre système, généralement "/". Le second cas ne le fait pas et devrait être spécifié littéralement. L'autre différence est que le premier "require" indique au compilateur que les utilisations de la notation d'objet indirect impliquant "SomeModule", comme dans "$ob = purge SomeModule", sont des appels de méthode, pas des appels de fonction. (Oui, cela peut vraiment faire une différence.)

Parce que l'instruction "use" implique un bloc "BEGIN", l'importation des sémantiques se produit dès que l'instruction "use" est compilée, avant que le reste du fichier ne soit compilé. C'est ainsi qu'elle peut fonctionner comme un mécanisme de pragma, et aussi comment les modules peuvent déclarer des sous-routines qui sont ensuite visibles comme des opérateurs de liste ou d'unicité pour le reste du fichier courant. Cela ne fonctionnera pas si vous utilisez "require" au lieu de "use". Avec "require", vous pouvez rencontrer ce problème:

require Cwd;                # rend Cwd:: accessible
$here = Cwd::getcwd();
use Cwd;                    # importe les noms de Cwd::
$here = getcwd();
require Cwd;                # rend Cwd:: accessible
$here = getcwd();           # oops! pas de main::getcwd()

En général, "use Module ()" est recommandé par rapport à "require Module", car il détermine la disponibilité du module au moment de la compilation, et non au milieu de l'exécution de votre programme. Une exception serait si deux modules tentaient chacun de "use" l'autre, et chacun appelait également une fonction de cet autre module. Dans ce cas, il est facile d'utiliser "require" à la place.

Les paquets Perl peuvent être imbriqués dans d'autres noms de paquets, nous pouvons donc avoir des noms de paquets contenant "::". Mais si nous utilisions ce nom de paquet directement comme nom de fichier, cela créerait des noms de fichiers difficiles à manipuler ou impossibles sur certains systèmes. Par conséquent, si le nom d'un module est, disons, "Text::Soundex", alors sa définition se trouve en fait dans le fichier de bibliothèque Text/Soundex.pm.

Les modules Perl ont toujours un fichier .pm, mais il peut également y avoir des exécutables liés dynamiquement (se terminant souvent par .so) ou des définitions de sous-routines auto-chargées (se terminant souvent par .al) associés au module. Si c'est le cas, ceux-ci seront entièrement transparents pour l'utilisateur du module. Il incombe au fichier .pm de charger (ou d'organiser le chargement automatique) toute fonctionnalité supplémentaire. Par exemple, bien que le module POSIX effectue à la fois le chargement dynamique et le chargement automatique, l'utilisateur peut simplement dire "use POSIX" pour tout obtenir.

Rendre votre module thread-safe

Perl prend en charge un type de threads appelé threads d'interpréteur (ithreads). Ces threads peuvent être utilisés explicitement et implicitement.

Les ithreads fonctionnent en clonant l'arbre de données afin qu'aucune donnée ne soit partagée entre les différents threads. Ces threads peuvent être utilisés en utilisant le module "threads" ou en faisant fork() sous win32 (faux support fork()). Lorsqu'un thread est cloné, toutes les données Perl sont clonées, mais les données non Perl ne peuvent pas être clonées automatiquement. Perl après 5.8.0 prend en charge la sous-routine spéciale "CLONE". Dans "CLONE", vous pouvez faire tout ce que vous devez faire, comme par exemple gérer le clonage de données non Perl, si nécessaire. "CLONE" sera appelé une fois en tant que méthode de classe pour chaque paquet qui l'a définie (ou dont il hérite). Il sera appelé dans le contexte du nouveau thread, de sorte que toutes les modifications sont apportées dans la nouvelle zone. Actuellement, CLONE est appelé sans paramètres autres que le nom du paquet invocant, mais le code ne doit pas supposer que cela restera inchangé, car il est probable qu'à l'avenir des paramètres supplémentaires seront passés pour donner plus d'informations sur l'état du clonage.

Si vous souhaitez CLONER tous les objets, vous devrez en garder une trace par paquet. Ceci est simplement fait en utilisant un hachage et Scalar::Util::weaken().

Perl après 5.8.7 prend en charge la sous-routine spéciale "CLONE_SKIP". Comme "CLONE", "CLONE_SKIP" est appelé une fois par paquet; h

Cependant, elle est appelée juste avant le début du clonage, et dans le contexte du thread parent. Si elle renvoie une valeur vraie, alors aucun objet de cette classe ne sera cloné ; ou plutôt, ils seront copiés comme des valeurs non validées et indéfinies. Par exemple : s'il y a deux références dans le parent vers un seul hash validé, alors il y aura deux références dans l'enfant vers une seule valeur scalaire indéfinie à la place. Cela fournit un mécanisme simple pour rendre un module thread-safe ; ajoutez simplement "sub CLONE_SKIP { 1 }" en haut de la classe, et DESTROY() ne sera maintenant appelé qu'une seule fois par objet. Bien sûr, si le thread enfant doit utiliser les objets, une approche plus sophistiquée est nécessaire.

Comme "CLONE", "CLONE_SKIP" est actuellement appelée sans aucun paramètre autre que le nom du package appelant, bien que cela puisse changer. De même, pour permettre une expansion future, la valeur de retour doit être une seule valeur 0 ou 1.
