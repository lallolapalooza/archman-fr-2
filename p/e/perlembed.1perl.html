Compiling your C program

If you have trouble compiling the scripts in this documentation, you're not alone. The cardinal rule: COMPILE THE PROGRAMS IN EXACTLY THE SAME WAY THAT YOUR PERL WAS COMPILED. (Sorry for yelling.)

Also, every C program that uses Perl must link in the perl library. What's that, you ask? Perl is itself written in C; the perl library is the collection of compiled C programs that were used to create your perl executable (/usr/bin/perl or equivalent). (Corollary: you can't use Perl from your C program unless Perl has been compiled on your machine, or installed properly--that's why you shouldn't blithely copy Perl executables from machine to machine without also copying the lib directory.)

When you use Perl from C, your C program will--usually--allocate, "run", and deallocate a PerlInterpreter object, which is defined by the perl library.

If your copy of Perl is recent enough to contain this documentation (version 5.002 or later), then the perl library (and EXTERN.h and perl.h, which you'll also need) will reside in a directory that looks like this:

/usr/local/lib/perl5/your_architecture_here/CORE

or perhaps just

/usr/local/lib/perl5/CORE

or maybe something like

/usr/opt/perl5/CORE

Execute this statement for a hint about where to find CORE:

perl -MConfig -e 'print $Config{archlib}'

Here's how you'd compile the example in the next section, "Adding a Perl interpreter to your C program", on my Linux box:

% gcc -O2 -Dbool=char -DHAS_BOOL -I/usr/local/include
-I/usr/local/lib/perl5/i586-linux/5.003/CORE
-L/usr/local/lib/perl5/i586-linux/5.003/CORE
-o interp interp.c -lperl -lm

(That's all one line.) On my DEC Alpha running old 5.003_05, the incantation is a bit different:

% cc -O2 -Olimit 2900 -I/usr/local/include
-I/usr/local/lib/perl5/alpha-dec_osf/5.00305/CORE
-L/usr/local/lib/perl5/alpha-dec_osf/5.00305/CORE -L/usr/local/lib
-D__LANGUAGE_C__ -D_NO_PROTO -o interp interp.c -lperl -lm

How can you figure out what to add? Assuming your Perl is post-5.001, execute a "perl -V" command and pay special attention to the "cc" and "ccflags" information.

You'll have to choose the appropriate compiler (cc, gcc, et al.) for your machine: "perl -MConfig -e 'print $Config{cc}'" will tell you what to use.

You'll also have to choose the appropriate library directory (/usr/local/lib/...) for your machine. If your compiler complains that certain functions are undefined, or that it can't locate -lperl, then you need to change the path following the "-L". If it complains that it can't find EXTERN.h and perl.h, you need to change the path following the "-I".

You may have to add extra libraries as well. Which ones? Perhaps those printed by

perl -MConfig -e 'print $Config{libs}'

Provided your perl binary was properly configured and installed the ExtUtils::Embed module will determine all of this information for you:

% cc -o interp interp.c `perl -MExtUtils::Embed -e ccopts -e ldopts`

If the ExtUtils::Embed module isn't part of your Perl distribution, you can retrieve it from https://metacpan.org/pod/ExtUtils::Embed (If this documentation came from your Perl distribution, then you're running 5.004 or better and you already have it.)

The ExtUtils::Embed kit on CPAN also contains all source code for the examples in this document, tests, additional examples and other information you may find useful.

Adding a Perl interpreter to your C program

In a sense, perl (the C program) is a good example of embedding Perl (the language), so I'll demonstrate embedding with miniperlmain.c, included in the source distribution. Here's a bastardized, non-portable version of miniperlmain.c containing the essentials of embedding:

#include <EXTERN.h>               /* from the Perl distribution     */
#include <perl.h>                 /* from the Perl distribution     */
static PerlInterpreter *my_perl;  /***    The Perl interpreter    ***/
int main(int argc, char **argv, char **env)
{
       PERL_SYS_INIT3(&argc,&argv,&env);
       my_perl = perl_alloc();
       perl_construct(my_perl);
       PL_exit_flags |= PERL_EXIT_DESTRUCT_END;
       perl_parse(my_perl, NULL, argc, argv, (char **)NULL);
       perl_run(my_perl);
       perl_destruct(my_perl);
       perl_free(my_perl);
       PERL_SYS_TERM();
       exit(EXIT_SUCCESS);
}

Notice that we don't use the "env" pointer. Normally handed to "perl_parse" as its final argument, "env" here is replaced by "NULL", which means that the current environment will be used.

The macros PERL_SYS_INIT3() and PERL_SYS_TERM() provide system-specific tune up of the C runtime environment necessary to run Perl interpreters; they should only be called once regardless of how many interpreters you create or destroy. Call PERL_SYS_INIT3() before you create your first interpreter, and PERL_SYS_TERM() after you free your last interpreter.

Since PERL_SYS_INIT3() may change "env", it may be more appropriate to provide "env" as an argument to perl_parse().

Also notice that no matter what arguments you pass to perl_parse(), PERL_SYS_INIT3() must be invoked on the C main() argc, argv and env and only once.

Mind that argv[argc] must be NULL, same as those passed to a main function in C.

Now compile this program (I'll call it interp.c) into an executable:

% cc -o interp interp.c `perl -MExtUtils::Embed -e ccopts -e ldopts`

After a successful compilation, you'll be able to use interp just like perl itself:

% interp
print "Pretty Good Perl \n";
print "10890 - 9801 is ", 10890 - 9801;
<CTRL-D>
Pretty Good Perl
10890 - 9801 is 1089

or

% interp -e 'printf("%x", 3735928559)'
deadbeef

You can also read and execute Perl statements from a file while in the midst of your C program, by placing the filename in argv[1] before calling perl_run.

Appel de sous-routines Perl depuis votre programme C

Pour appeler des sous-routines Perl individuelles, vous pouvez utiliser l'une des fonctions call_* documentées dans perlcall. Dans cet exemple, nous utiliserons « call_argv ».

Ceci est montré ci-dessous, dans un programme que j'appellerai showtime.c.

#include <EXTERN.h>
#include <perl.h>
static PerlInterpreter *my_perl;
int main(int argc, char **argv, char **env)
{
    char *args[] = { NULL };
    PERL_SYS_INIT3(&argc,&argv,&env);
    my_perl = perl_alloc();
    perl_construct(my_perl);
    perl_parse(my_perl, NULL, argc, argv, NULL);
    PL_exit_flags |= PERL_EXIT_DESTRUCT_END;
    /*** skipping perl_run() ***/
    call_argv("showtime", G_DISCARD | G_NOARGS, args);
    perl_destruct(my_perl);
    perl_free(my_perl);
    PERL_SYS_TERM();
    exit(EXIT_SUCCESS);
}

où showtime est une sous-routine Perl qui ne prend aucun argument (c'est le G_NOARGS) et pour laquelle j'ignorerai la valeur de retour (c'est le G_DISCARD). Ces drapeaux, et d'autres, sont discutés dans perlcall.

Je définirai la sous-routine showtime dans un fichier appelé showtime.pl :

print "I shan't be printed.";
sub showtime {
    print time;
}

Assez simple. Compilez et exécutez maintenant :

% cc -o showtime showtime.c \
    `perl -MExtUtils::Embed -e ccopts -e ldopts`
% showtime showtime.pl
818284590

affichant le nombre de secondes écoulées entre le 1er janvier 1970 (le début de l'époque Unix) et le moment où j'ai commencé à écrire cette phrase.

Dans ce cas particulier, nous n'avons pas à appeler perl_run, car nous avons défini le drapeau de sortie PL_exit_flag PERL_EXIT_DESTRUCT_END qui exécute les blocs END dans perl_destruct.

Si vous souhaitez passer des arguments à la sous-routine Perl, vous pouvez ajouter des chaînes à la liste « args » se terminant par « NULL » et passée à call_argv. Pour d'autres types de données, ou pour examiner les valeurs de retour, vous devrez manipuler la pile Perl. Ceci est démontré dans "Fiddling with the Perl stack from your C program".

Évaluation d'une instruction Perl depuis votre programme C

Perl fournit deux fonctions d'API pour évaluer des morceaux de code Perl. Ce sont "eval_sv" dans perlapi et "eval_pv" dans perlapi.

On peut arguer que ce sont les seules routines dont vous aurez jamais besoin pour exécuter des extraits de code Perl depuis votre programme C. Votre code peut être aussi long que vous le souhaitez ; il peut contenir plusieurs instructions ; il peut utiliser "use" dans perlfunc, "require" dans perlfunc, et "do" dans perlfunc pour inclure des fichiers Perl externes.

eval_pv nous permet d'évaluer des chaînes Perl individuelles, puis d'extraire des variables pour les convertir en types C. Le programme suivant, string.c, exécute trois chaînes Perl, en extrayant un « int » de la première, un « float » de la seconde, et un « char * » de la troisième.

#include <EXTERN.h>
#include <perl.h>
static PerlInterpreter *my_perl;
main (int argc, char **argv, char **env)
{
    char *embedding[] = { "", "-e", "0", NULL };
    PERL_SYS_INIT3(&argc,&argv,&env);
    my_perl = perl_alloc();
    perl_construct( my_perl );
    perl_parse(my_perl, NULL, 3, embedding, NULL);
    PL_exit_flags |= PERL_EXIT_DESTRUCT_END;
    perl_run(my_perl);
    /** Treat $x as an integer **/
    eval_pv("$x = 3; $x **= 2", TRUE);
    printf("x = %d\n", SvIV(get_sv("x", 0)));
    /** Treat $x as a float **/
    eval_pv("$x = 3.14; $x **= 2", TRUE);
    printf("x = %f\n", SvNV(get_sv("x", 0)));
    /** Treat $x as a string **/
    eval_pv(
      "$x = 'rekcaH lreP rehtonA tsuJ'; $x = reverse($x);", TRUE);
    printf("x = %s\n", SvPV_nolen(get_sv("x", 0)));
    perl_destruct(my_perl);
    perl_free(my_perl);
    PERL_SYS_TERM();
}

Toutes ces fonctions étranges avec sv dans leur nom aident à convertir les scalaires Perl en types C. Elles sont décrites dans perlguts et perlapi.

Si vous compilez et exécutez string.c, vous verrez les résultats de l'utilisation de SvIV() pour créer un « int », SvNV() pour créer un « float », et SvPV() pour créer une chaîne :

a = 9
a = 9.859600
a = Just Another Perl Hacker

Dans l'exemple ci-dessus, nous avons créé une variable globale pour stocker temporairement la valeur calculée de notre expression évaluée. Il est également possible et dans la plupart des cas une meilleure stratégie de récupérer la valeur de retour de eval_pv() à la place. Exemple :

...
SV *val = eval_pv("reverse 'rekcaH lreP rehtonA tsuJ'", TRUE);
printf("%s\n", SvPV_nolen(val));
...

De cette façon, nous évitons la pollution de l'espace de noms en ne créant pas de variables globales et nous avons également simplifié notre code.

Effectuer des correspondances et des substitutions Perl depuis votre programme C

La fonction eval_sv() nous permet d'évaluer des chaînes de code Perl, nous pouvons donc définir certaines fonctions qui l'utilisent pour se "spécialiser" dans les correspondances et les substitutions : match(), substitute(), et matches().

I32 match(SV *string, char *pattern);

Étant donné une chaîne et un motif (par exemple, « m/clasp/ » ou « /\b\w*\b/ », qui dans votre programme C pourrait apparaître comme "/\\b\\w*\\b/"), match() renvoie 1 si la chaîne correspond au motif et 0 sinon.

int substitute(SV **string, char *pattern);

Étant donné un pointeur vers un « SV » et une opération « =~ » (par exemple, « s/bob/robert/g » ou « tr[A-Z][a-z] »), substitute() modifie la chaîne dans le « SV » conformément à l'opération, renvoyant le nombre de substitutions effectuées.

SSize_t matches(SV *string, char *pattern, AV **matches);

Étant donné un « SV », un motif et un pointeur vers un « AV » vide, matches() évalue « $string =~ $pattern » dans un contexte de liste, et remplit matches avec les éléments du tableau, renvoyant le nombre de correspondances trouvées.

Voici un exemple de programme, match.c, qui utilise les trois (les longues lignes ont été coupées ici) :

#include <EXTERN.h>
#include <perl.h>
static PerlInterpreter *my_perl;
/** my_eval_sv(code, error_check)
** similar to eval_sv(),
** but we pop the return value off the stack
**/
SV* my_eval_sv(SV *sv, I32 croak_on_error)
{
    dSP;
    SV*retval;
    PUSHMARK(SP);
    eval_sv(sv, G_SCALAR);
    SPAGAIN;
    retval = POPs;
    PUTBACK;
    if (croak_on_error && SvTRUE(ERRSV))
       croak_sv(ERRSV);
    return retval;
}
/** match(string, pattern)
**
** Used for matches in a scalar context.
**
** Returns 1 if the match was successful; 0 otherwise.
**/
I32 match(SV *string, char *pattern)
{
    SV *command = newSV(0), *retval;
    sv_setpvf(command, "my $string = '%s'; $string =~ %s",
             SvPV_nolen(string), pattern);
    retval = my_eval_sv(command, TRUE);
    SvREFCNT_dec(command);
    return SvIV(retval);
}
/** substitute(string, pattern)
**
** Used for =~ operations that
** modify their left-hand side (s/// and tr///)
**
** Returns the number of successful matches, and
** modifies the input string if there were any.
**/
I32 substitute(SV **string, char *pattern)
{
    SV *command = newSV(0), *retval;
    sv_setpvf(command, "$string = '%s'; ($string =~ %s)",
             SvPV_nolen(*string), pattern);
    retval = my_eval_sv(command, TRUE);
    SvREFCNT_dec(command);
    *string = get_sv("string", 0);
    return SvIV(retval);
}
/** matches(string, pattern, matches)
**
** Used for matches in a list context.
**
** Returns the number of matches,
** and fills in **matches with the matching substrings
**/
SSize_t matches(SV *string, char *pattern, AV **match_list)
{
    SV *command = newSV(0);
    SSize_t num_matches;
    sv_setpvf(command, "my $string = '%s'; @array = ($string =~ %s)",
             SvPV_nolen(string), pattern);
    my_eval_sv(command, TRUE);
    SvREFCNT_dec(command);
    *match_list = get_av("array", 0);
    num_matches = av_top_index(*match_list) + 1;
    return num_matches;
}
main (int argc, char **argv, char **env)
{

    perl_parse(my_perl, NULL, 3, embedding, NULL);
    PL_exit_flags |= PERL_EXIT_DESTRUCT_END;
    text = newSV(0);
    sv_setpv(text, "When he is at a convenience store and the "
       "bill comes to some amount like 76 cents, Maynard is "
       "aware that there is something he *should* do, something "

Manipuler la pile Perl depuis votre programme C

Lorsqu'ils tentent d'expliquer les piles, la plupart des manuels d'informatique marmonnent quelque chose sur des colonnes de plateaux de cafétéria à ressort : la dernière chose que vous avez poussée sur la pile est la première chose que vous retirez. Cela suffira pour nos besoins : votre programme C poussera certains arguments sur « la pile Perl », fermera les yeux pendant qu'une magie opère, puis retirera les résultats – la valeur de retour de votre sous-routine Perl – de la pile.

Vous devrez d'abord savoir comment convertir entre les types C et les types Perl, avec newSViv() et sv_setnv() et newAV() et tous leurs amis. Ils sont décrits dans perlguts et perlapi.

Ensuite, vous devrez savoir comment manipuler la pile Perl. Ceci est décrit dans perlcall.

Une fois que vous aurez compris cela, l'intégration de Perl en C sera facile.

Comme C n'a pas de fonction intégrée pour l'exponentiation entière, rendons l'opérateur ** de Perl disponible (ce qui est moins utile qu'il n'y paraît, car Perl implémente ** avec la fonction C pow()). Je vais d'abord créer une fonction d'exponentiation stub dans power.pl :

sub expo {
    my ($x, $y) = @_;
    return $x ** $y;
}

Maintenant, je vais créer un programme C, power.c, avec une fonction PerlPower() qui contient toutes les astuces nécessaires pour pousser les deux arguments dans expo() et en retirer la valeur de retour. Respirez profondément...

#include <EXTERN.h>
#include <perl.h>
static PerlInterpreter *my_perl;
static void
PerlPower(int a, int b)
{
  dSP;                            /* initialise le pointeur de pile      */
  ENTER;                          /* tout ce qui est créé après ici */
  SAVETMPS;                       /* ... est une variable temporaire.   */
  PUSHMARK(SP);                   /* mémorise le pointeur de pile    */
  XPUSHs(sv_2mortal(newSViv(a))); /* pousse la base sur la pile  */
  XPUSHs(sv_2mortal(newSViv(b))); /* pousse l'exposant sur la pile  */
  PUTBACK;                      /* rend le pointeur de pile local global */
  call_pv("expo", G_SCALAR);      /* appelle la fonction             */
  SPAGAIN;                        /* rafraîchit le pointeur de pile         */
                                /* retire la valeur de retour de la pile */
  printf ("%d à la puissance %d est %d.\n", a, b, POPi);
  PUTBACK;
  FREETMPS;                       /* libère cette valeur de retour        */
  LEAVE;                       /* ... et les arguments "mortels" XPUSHés. */
}
int main (int argc, char **argv, char **env)
{
  char *my_argv[] = { "", "power.pl", NULL };
  PERL_SYS_INIT3(&argc,&argv,&env);
  my_perl = perl_alloc();
  perl_construct( my_perl );
  perl_parse(my_perl, NULL, 2, my_argv, (char **)NULL);
  PL_exit_flags |= PERL_EXIT_DESTRUCT_END;
  perl_run(my_perl);
  PerlPower(3, 4);                      /*** Calcule 3 ** 4 ***/
  perl_destruct(my_perl);
  perl_free(my_perl);
  PERL_SYS_TERM();
  exit(EXIT_SUCCESS);
}

Compilez et exécutez :

% cc -o power power.c `perl -MExtUtils::Embed -e ccopts -e ldopts`
% power
3 to the 4th power is 81.

Maintenir un interpréteur persistant

Lors du développement d'applications interactives et/ou potentiellement de longue durée, il est judicieux de maintenir un interpréteur persistant plutôt que d'allouer et de construire un nouvel interpréteur plusieurs fois. La raison principale est la vitesse : Perl ne sera chargé en mémoire qu'une seule fois.

Cependant, vous devez être plus prudent avec l'espace de noms et la portée des variables lors de l'utilisation d'un interpréteur persistant. Dans les exemples précédents, nous avons utilisé des variables globales dans le paquet par défaut "main". Nous savions exactement quel code serait exécuté et avons supposé que nous pouvions éviter les collisions de variables et la croissance excessive de la table des symboles.

Supposons que votre application soit un serveur qui exécutera occasionnellement du code Perl à partir d'un fichier arbitraire. Votre serveur ne sait pas quel code il va exécuter. Très dangereux.

Si le fichier est inclus par perl_parse(), compilé dans un interpréteur nouvellement construit, puis nettoyé avec perl_destruct() par la suite, vous êtes protégé de la plupart des problèmes d'espace de noms.

Une façon d'éviter les collisions d'espaces de noms dans ce scénario est de traduire le nom du fichier en un nom de paquet garanti unique, puis de compiler le code dans ce paquet en utilisant "eval" dans perlfunc. Dans l'exemple ci-dessous, chaque fichier ne sera compilé qu'une seule fois. Ou, l'application peut choisir de nettoyer la table des symboles associée au fichier après qu'elle ne soit plus nécessaire. En utilisant "call_argv" dans perlapi, nous appellerons la sous-routine "Embed::Persistent::eval_file" qui vit dans le fichier "persistent.pl" et passerons le nom du fichier et un indicateur booléen de nettoyage/mise en cache comme arguments.

Notez que le processus continuera de croître pour chaque fichier qu'il utilise. De plus, il peut y avoir des sous-routines "AUTOLOAD" et d'autres conditions qui provoquent la croissance de la table des symboles de Perl. Vous pourriez vouloir ajouter une logique qui suit la taille du processus, ou qui le redémarre après un certain nombre de requêtes, pour vous assurer que la consommation de mémoire est minimisée. Vous voudrez également encadrer vos variables avec "my" dans perlfunc autant que possible.

package Embed::Persistent;
#persistent.pl
use strict;
our %Cache;
use Symbol qw(delete_package);
sub valid_package_name {
    my($string) = @_;
    $string =~ s/([^A-Za-z0-9\/])/sprintf("_%2x",unpack("C",$1))/eg;
    # second pass only for words starting with a digit
    $string =~ s|/(\d)|sprintf("/_%2x",unpack("C",$1))|eg;
    # Dress it up as a real package name
    $string =~ s|/|::|g;
    return "Embed" . $string;
}
sub eval_file {
    my($filename, $delete) = @_;
    my $package = valid_package_name($filename);
    my $mtime = -M $filename;
    if(defined $Cache{$package}{mtime}
       &&
       $Cache{$package}{mtime} <= $mtime)
    {
       # nous avons déjà compilé cette sous-routine,
       # elle n'a pas été mise à jour sur disque, rien de plus à faire
       print STDERR "already compiled $package->handler\n";
    }
    else {
       local *FH;
       open FH, $filename or die "open '$filename' $!";
       local($/) = undef;
       my $sub = <FH>;
       close FH;
       # enveloppe le code dans une sous-routine à l'intérieur de notre paquet unique
       my $eval = qq{package $package; sub handler { $sub; }};
       {
           # cache nos variables dans ce bloc
           my($filename,$mtime,$package,$sub);
           eval $eval;
       }
       die $@ if $@;
       # cache-le sauf si nous nettoyons à chaque fois
       $Cache{$package}{mtime} = $mtime unless $delete;
    }
    eval {$package->handler;};
    die $@ if $@;
    delete_package($package) if $delete;
    # jetez un œil si vous voulez
    #print Devel::Symdump->rnew($package)->as_string, $/;
}
1;
__END__
/* persistent.c */
#include <EXTERN.h>
#include <perl.h>
/* 1 = nettoie la table des symboles du nom de fichier après chaque requête,
   0 = ne le fait pas
*/
#ifndef DO_CLEAN
#define DO_CLEAN 0
#endif
#define BUFFER_SIZE 1024
static PerlInterpreter *my_perl = NULL;
int
main(int argc, char **argv, char **env)
{
    char *embedding[] = { "", "persistent.pl", NULL };
    char *args[] = { "", DO_CLEAN, NULL };
    char filename[BUFFER_SIZE];
    int failing, exitstatus;
    PERL_SYS_INIT3(&argc,&argv,&env);
    if((my_perl = perl_alloc()) == NULL) {
       fprintf(stderr, "no memory!");
       exit(EXIT_FAILURE);
    }
    perl_construct(my_perl);
    PL_origalen = 1; /* n'autorise pas l'assignation de $0 à mettre à jour le
                        proctitle ou embedding[0] */
    failing = perl_parse(my_perl, NULL, 2, embedding, NULL);
    PL_exit_flags |= PERL_EXIT_DESTRUCT_END;
    if(!failing)
       failing = perl_run(my_perl);
    if(!failing) {
       while(printf("Enter file name: ") &&
             fgets(filename, BUFFER_SIZE, stdin)) {
           filename[strlen(filename)-1] = '\0'; /* supprime \n */
           /* appelle la sous-routine,
                    en lui passant le nom du fichier comme argument */
           args[0] = filename;
           call_argv("Embed::Persistent::eval_file",
                          G_DISCARD | G_EVAL, args);
           /* vérifie $@ */
           if(SvTRUE(ERRSV))
               fprintf(stderr, "eval error: %s\n", SvPV_nolen(ERRSV));
       }
    }
    PL_perl_destruct_level = 0;
    exitstatus = perl_destruct(my_perl);
    perl_free(my_perl);
    PERL_SYS_TERM();
    exit(exitstatus);
}

Compilez maintenant :

% cc -o persistent persistent.c \
       `perl -MExtUtils::Embed -e ccopts -e ldopts`

Exécution des blocs END

Traditionnellement, les blocs END étaient exécutés à la fin de perl_run. Cela pose des problèmes pour les applications qui n'appellent jamais perl_run. Depuis perl 5.7.2, vous pouvez spécifier "PL_exit_flags |= PERL_EXIT_DESTRUCT_END" pour obtenir le nouveau comportement. Cela active également l'exécution des blocs END si perl_parse échoue et que "perl_destruct" retournera la valeur de sortie.

Assignations de $0

Lorsqu'un script Perl attribue une valeur à $0, le runtime Perl tentera de faire apparaître cette valeur comme le nom du programme signalé par "ps" en mettant à jour la mémoire pointée par les argv passés à perl_parse() et en appelant également des fonctions d'API comme setproctitle() lorsque disponible. Ce behav

iour pourrait ne pas être approprié lors de l'intégration de Perl et peut être désactivé en attribuant la valeur 1 à la variable "PL_origalen" avant que perl_parse() ne soit appelée.

L'exemple persistent.c ci-dessus est, par exemple, susceptible de planter lors de l'affectation à $0 si l'affectation "PL_origalen = 1;" est supprimée. Ceci parce que Perl essaiera d'écrire dans la mémoire en lecture seule des chaînes "embedding[]".

Maintenance de plusieurs instances d'interpréteur

Certaines applications rares devront créer plus d'un interpréteur pendant une session. Une telle application pourrait sporadiquement décider de libérer les ressources associées à l'interpréteur.

Le programme doit veiller à ce que cela se produise avant la construction du prochain interpréteur. Par défaut, lorsque Perl n'est pas compilé avec des options spéciales, la variable globale "PL_perl_destruct_level" est définie sur 0, car un nettoyage supplémentaire n'est généralement pas nécessaire lorsqu'un programme ne crée qu'un seul interpréteur au cours de sa durée de vie.

Définir "PL_perl_destruct_level" à 1 rend tout parfaitement propre :

while(1) {
    ...
    /* réinitialiser les variables globales ici avec PL_perl_destruct_level = 1 */
    PL_perl_destruct_level = 1;
    perl_construct(my_perl);
    ...
    /* nettoyer et réinitialiser _tout_ pendant perl_destruct */
    PL_perl_destruct_level = 1;
    perl_destruct(my_perl);
    perl_free(my_perl);
    ...
    /* allons-y encore une fois ! */
}

Lorsque perl_destruct() est appelée, l'arbre syntaxique de l'interpréteur et les tables de symboles sont nettoyés, et les variables globales sont réinitialisées. La seconde affectation à "PL_perl_destruct_level" est nécessaire car perl_construct la réinitialise à 0.

Supposons maintenant que nous ayons plus d'une instance d'interpréteur en cours d'exécution en même temps. Ceci est réalisable, mais seulement si vous avez utilisé l'option de configuration "-Dusemultiplicity" ou l'une des options "-Dusethreads -Duseithreads" lors de la compilation de Perl. Par défaut, l'activation de l'une de ces options de configuration définit la variable globale par interpréteur "PL_perl_destruct_level" sur 1, de sorte qu'un nettoyage approfondi est automatique et que les variables de l'interpréteur sont correctement initialisées. Même si vous n'avez pas l'intention d'exécuter deux interpréteurs ou plus en même temps, mais de les exécuter séquentiellement, comme dans l'exemple ci-dessus, il est recommandé de compiler Perl avec l'option "-Dusemultiplicity" sinon certaines variables de l'interpréteur peuvent ne pas être correctement initialisées entre les exécutions consécutives et votre application peut planter.

(Il y avait auparavant deux formes de threads, avec "ithreads" apparaissant plus tard. Mais "ithreads" s'est avéré supérieur, et la prise en charge de l'ancien modèle a été supprimée dans Perl v5.10. Mais la documentation et le code n'ont jamais été purgés de la terminologie antérieure ; et peut-être qu'un nouveau modèle arrivera pour supplanter "ithreads", il semble donc préférable de conserver les deux. Si le modèle de threading utilisé ne vous préoccupe pas, utilisez simplement "usethreads" pour protéger votre code des changements futurs. Si votre code dépend du modèle "ithreads", utilisez "useithreads" pour vous assurer que vous obtiendrez toujours celui-ci. Cela s'applique également aux symboles du langage C "USE_THREADS" et "USE_ITHREADS".)

Voir aussi "Dealing with embedded perls and threads" dans perlclib.

Utiliser "-Dusethreads -Duseithreads" plutôt que "-Dusemultiplicity" est plus approprié si vous avez l'intention d'exécuter plusieurs interpréteurs simultanément dans différents threads, car cela active la prise en charge de l'édition de liens avec les bibliothèques de threads de votre système avec l'interpréteur.

Essayons :

#include <EXTERN.h>
#include <perl.h>
/* nous allons intégrer deux interpréteurs */
#define SAY_HELLO "-e", "print qq(Salut, je suis $^X\n)"
int main(int argc, char **argv, char **env)
{
    PerlInterpreter *one_perl, *two_perl;
    char *one_args[] = { "one_perl", SAY_HELLO, NULL };
    char *two_args[] = { "two_perl", SAY_HELLO, NULL };
    PERL_SYS_INIT3(&argc,&argv,&env);
    one_perl = perl_alloc();
    two_perl = perl_alloc();
    PERL_SET_CONTEXT(one_perl);
    perl_construct(one_perl);
    PERL_SET_CONTEXT(two_perl);
    perl_construct(two_perl);
    PERL_SET_CONTEXT(one_perl);
    perl_parse(one_perl, NULL, 3, one_args, (char **)NULL);
    PERL_SET_CONTEXT(two_perl);
    perl_parse(two_perl, NULL, 3, two_args, (char **)NULL);
    PERL_SET_CONTEXT(one_perl);
    perl_run(one_perl);
    PERL_SET_CONTEXT(two_perl);
    perl_run(two_perl);
    PERL_SET_CONTEXT(one_perl);
    perl_destruct(one_perl);
    PERL_SET_CONTEXT(two_perl);
    perl_destruct(two_perl);
    PERL_SET_CONTEXT(one_perl);
    perl_free(one_perl);
    PERL_SET_CONTEXT(two_perl);
    perl_free(two_perl);
    PERL_SYS_TERM();
    exit(EXIT_SUCCESS);
}

Notez les appels à PERL_SET_CONTEXT(). Ceux-ci sont nécessaires pour initialiser l'état global qui suit quel interpréteur est l'interpréteur "courant" dans le processus ou le thread particulier qui peut l'exécuter. Il doit toujours être utilisé si vous avez plus d'un interpréteur et que vous effectuez des appels API Perl sur les deux interpréteurs de manière intercalée.

PERL_SET_CONTEXT(interp) doit également être appelé chaque fois que "interp" est utilisé par un thread qui ne l'a pas créé (en utilisant soit perl_alloc(), soit le plus ésotérique perl_clone()).

Compilez comme d'habitude :

% cc -o multiplicity multiplicity.c \
 `perl -MExtUtils::Embed -e ccopts -e ldopts`

Exécutez-le, Exécutez-le :

% multiplicity
Salut, je suis one_perl
Salut, je suis two_perl

Utiliser des modules Perl, qui utilisent eux-mêmes des bibliothèques C, depuis votre programme C

Si vous avez joué avec les exemples ci-dessus et essayé d'intégrer un script qui use() un module Perl (comme Socket) qui utilise lui-même une bibliothèque C ou C++, cela s'est probablement passé ainsi :

Impossible de charger le module Socket, le chargement dynamique n'est pas disponible dans ce perl.
 (Vous devrez peut-être compiler un nouvel exécutable Perl qui prend en charge
 le chargement dynamique ou qui a le module Socket lié statiquement.)

Qu'est-ce qui ne va pas ?

Votre interpréteur ne sait pas comment communiquer avec ces extensions de lui-même. Un peu de colle aidera. Jusqu'à présent, vous appeliez perl_parse(), lui passant NULL comme deuxième argument :

perl_parse(my_perl, NULL, argc, my_argv, NULL);

C'est là que le code de colle peut être inséré pour créer le contact initial entre Perl et les routines C/C++ liées. Jetons un coup d'œil à quelques éléments de perlmain.c pour voir comment Perl fait cela :

static void xs_init (pTHX);
EXTERN_C void boot_DynaLoader (pTHX_ CV* cv);
EXTERN_C void boot_Socket (pTHX_ CV* cv);
EXTERN_C void
xs_init(pTHX)
{
       char *file = __FILE__;
       /* DynaLoader est un cas spécial */
       newXS("DynaLoader::boot_DynaLoader", boot_DynaLoader, file);
       newXS("Socket::bootstrap", boot_Socket, file);
}

En termes simples : pour chaque extension liée à votre exécutable Perl (déterminé lors de sa configuration initiale sur votre ordinateur ou lors de l'ajout d'une nouvelle extension), une sous-routine Perl est créée pour incorporer les routines de l'extension. Normalement, cette sous-routine est nommée Module::bootstrap() et est invoquée lorsque vous dites use Module. À son tour, cela se connecte à un XSUB, boot_Module, qui crée une contrepartie Perl pour chacun des XSUB de l'extension. Ne vous inquiétez pas de cette partie, laissez-la aux auteurs de xsubpp et des extensions. Si votre extension est chargée dynamiquement, DynaLoader crée Module::bootstrap() pour vous à la volée. En fait, si vous avez un DynaLoader fonctionnel, il est rarement nécessaire de lier statiquement d'autres extensions.

Une fois que vous avez ce code, insérez-le dans le deuxième argument de perl_parse() :

perl_parse(my_perl, xs_init, argc, my_argv, NULL);

Puis compilez :

% cc -o interp interp.c `perl -MExtUtils::Embed -e ccopts -e ldopts`
% interp
  use Socket;
  use SomeDynamicallyLoadedModule;
  print "Maintenant je peux utiliser les extensions !\n"'

ExtUtils::Embed peut également automatiser l'écriture du code de colle xs_init.

% perl -MExtUtils::Embed -e xsinit -- -o perlxsi.c
% cc -c perlxsi.c `perl -MExtUtils::Embed -e ccopts`
% cc -c interp.c  `perl -MExtUtils::Embed -e ccopts`
% cc -o interp perlxsi.o interp.o `perl -MExtUtils::Embed -e ldopts`

Consultez perlxs, perlclib, perlguts et perlapi pour plus de détails.

Utiliser Perl embarqué avec les locales POSIX

(Voir perllocale pour plus d'informations à ce sujet.) Lorsqu'un interpréteur Perl démarre normalement, il indique au système qu'il souhaite utiliser la locale par défaut du système. Il s'agit souvent, mais pas nécessairement, de la locale "C" ou "POSIX". En l'absence d'un "use locale" dans le code Perl, cela n'a généralement aucun effet (mais voir "Not within the scope of "use locale"" dans perllocale). De plus, il n'y a pas de problème si la locale que vous souhaitez utiliser dans votre Perl embarqué est la même que la locale par défaut du système. Cependant, cela ne fonctionne pas si vous avez configuré et souhaitez utiliser une locale qui n'est pas la locale par défaut du système. À partir de Perl v5.20, vous pouvez indiquer à l'interpréteur Perl embarqué que la locale est correctement configurée et qu'il doit sauter sa propre initialisation normale. Il saute si la variable d'environnement "PERL_SKIP_LOCALE_INIT" est définie (même si elle est définie sur 0 ou ""). Un Perl possédant cette capacité définira le symbole préprocesseur C "HAS_SKIP_LOCALE_INIT". Cela permet au code qui doit fonctionner avec plusieurs versions de Perl d'effectuer une sorte de solution de contournement lorsqu'il est confronté à une version antérieure de Perl.

Si votre programme utilise les fonctionnalités de locale multithread POSIX 2008, vous devez basculer vers la locale globale et la configurer correctement

avant de démarrer l'interpréteur Perl. Il passera alors correctement à l'utilisation des fonctions thread-safe.

Cacher Perl_

Si vous souhaitez masquer complètement les formes courtes de l'API publique de Perl, ajoutez -DPERL_NO_SHORT_NAMES aux drapeaux de compilation. Cela signifie que, par exemple, au lieu d'écrire

warn("%d bottles of beer on the wall", bottlecount);

vous devrez écrire la forme longue explicite

Perl_warn(aTHX_ "%d bottles of beer on the wall", bottlecount);

(Voir "Background and MULTIPLICITY" dans perlguts pour l'explication de "aTHX_". ) Masquer les formes courtes est très utile pour éviter toutes sortes de conflits gênants (préprocesseur C ou autres) avec d'autres progiciels (Perl définit environ 2400 API avec ces noms courts, à quelques centaines près, il y a donc certainement place pour des conflits.)

MORAL

Vous pouvez parfois *écrire du code plus rapidement* en C, mais vous pouvez toujours *écrire du code plus rapidement* en Perl. Parce que vous pouvez utiliser l'un à partir de l'autre, combinez-les comme vous le souhaitez.
