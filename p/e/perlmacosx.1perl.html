PERLMACOSX(1perl) Guide de référence du programmeur Perl PERLMACOSX(1perl)

NOM

perlmacosx - Perl sous Mac OS X

SYNTAXE

Ce document décrit brièvement Perl sous Mac OS X.

curl -O https://www.cpan.org/src/perl-5.42.0.tar.gz
tar -xzf perl-5.42.0.tar.gz
cd perl-5.42.0
./Configure -des -Dprefix=/usr/local/
make
make test
sudo make install

DESCRIPTION

La dernière version de Perl (5.42.0 à l'heure de la rédaction) se compile sans modification sous toutes les versions de Mac OS X à partir de 10.3 "Panther".

Pour compiler votre propre version de Perl, vous aurez besoin de 'make', qui fait partie des outils de développement d'Apple - également connus sous le nom d'Xcode. À partir de Mac OS X 10.7 "Lion" et versions ultérieures, il peut être téléchargé séparément sous le nom de bundle 'Command Line Tools' directement depuis https://developer.apple.com/downloads/ (vous aurez besoin d'un compte gratuit pour vous connecter), ou en tant que partie de la suite Xcode, disponible gratuitement sur l'App Store. Xcode est une application assez volumineuse, donc sauf si vous l'avez déjà ou la désirez vraiment, il est conseillé de télécharger séparément le bundle 'Command Line Tools' depuis le lien ci-dessus. Si vous souhaitez le faire depuis Xcode, allez dans Xcode -> Préférences -> Téléchargements et sélectionnez l'option 'Command Line Tools'.

Entre Mac OS X 10.3 "Panther" et 10.6 "Snow Leopard", le bundle 'Command Line Tools' s'appelait 'unix tools', et était généralement fourni avec les DVD d'installation de Mac OS.

Les versions antérieures de Mac OS X (10.2 "Jaguar" et plus anciennes) n'incluaient pas une libc entièrement thread-safe, donc le threading n'est pas entièrement pris en charge. De plus, les versions antérieures incluaient une libdb boguée, donc certains tests DB_File sont connus pour échouer sur ces versions.

Préfixe d'installation

L'emplacement d'installation par défaut pour cette version utilise la disposition de répertoires UNIX traditionnelle sous /usr/local. C'est l'emplacement recommandé pour la plupart des utilisateurs, et il laissera le Perl fourni par Apple et ses modules intacts.

L'utilisation d'un préfixe d'installation de '/usr' entraînera une disposition de répertoire qui reflète celle du Perl par défaut d'Apple, avec les modules principaux stockés dans '/System/Library/Perl/${version}', les modules CPAN stockés dans '/Library/Perl/${version}', et l'ajout de '/Network/Library/Perl/${version}' à @INC pour les modules stockés sur un serveur de fichiers et utilisés par plusieurs Mac.

Support SDK

D'abord, exportez le chemin du SDK dans l'environnement de construction :

export SDK=/Applications/Xcode.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX10.8.sdk

Veuillez vous assurer que la version du SDK (c'est-à-dire les numéros juste avant '.sdk') correspond à celle de votre système (dans ce cas, Mac OS X 10.8 "Mountain Lion"), car il est possible d'avoir plusieurs SDK installés. Assurez-vous également que le chemin existe sur votre système, et s'il n'existe pas, assurez-vous que le SDK est correctement installé, car il devrait être fourni avec le bundle 'Command Line Tools' mentionné ci-dessus. Enfin, si vous avez un ancien Mac OS X (10.6 "Snow Leopard" et versions antérieures) exécutant Xcode 4.2 ou une version inférieure, le chemin du SDK pourrait être quelque chose comme '/Developer/SDKs/MacOSX10.3.9.sdk'.

Vous pouvez utiliser le SDK en exportant quelques ajouts aux variables de configuration 'ccflags' et '..flags' de Perl :

./Configure -Accflags="-nostdinc -B$SDK/usr/include/gcc \
                       -B$SDK/usr/lib/gcc -isystem$SDK/usr/include \
                       -F$SDK/System/Library/Frameworks" \
            -Aldflags="-Wl,-syslibroot,$SDK" \
            -de

Support binaire universel

Remarque : À partir de Mac OS X 10.6 "Snow Leopard" et versions ultérieures, Apple ne prend en charge que le matériel basé sur Intel. Cela signifie que vous pouvez ignorer cette section en toute sécurité, sauf si vous possédez un ancien ordinateur Apple fonctionnant sur ppc ou si vous souhaitez créer un binaire perl rétrocompatible.

Vous pouvez compiler perl en tant que binaire universel (compilé pour ppc et intel). Dans Mac OS X 10.4 "Tiger", vous devez exporter la variante 'u' du SDK :

export SDK=/Developer/SDKs/MacOSX10.4u.sdk

Mac OS X 10.5 "Leopard" et versions ultérieures ne nécessitent pas la variante 'u'.

En plus des indicateurs de compilateur utilisés pour sélectionner le SDK, ajoutez également les indicateurs pour créer un binaire universel :

./Configure -Accflags="-arch i686 -arch ppc -nostdinc               \
                        -B$SDK/usr/include/gcc                      \
                       -B$SDK/usr/lib/gcc -isystem$SDK/usr/include  \
                       -F$SDK/System/Library/Frameworks"            \
            -Aldflags="-arch i686 -arch ppc -Wl,-syslibroot,$SDK"   \
            -de

Gardez à l'esprit que ces paramètres de compilateur et d'éditeur de liens seront également utilisés lors de la compilation des modules CPAN. Pour que les modules XS soient compilés en tant que binaire universel, les bibliothèques auxquelles ils sont liés doivent également être des binaires universels. Les bibliothèques système qu'Apple inclut avec le SDK 10.4u sont toutes universelles, mais les bibliothèques installées par l'utilisateur peuvent devoir être réinstallées en tant que binaires universels.

Support PPC 64 bits

Suivez les instructions dans INSTALL pour compiler perl avec la prise en charge des entiers 64 bits ("use64bitint") ou à la fois des entiers 64 bits et de l'adressage 64 bits ("use64bitall"). Dans ce dernier cas, le binaire résultant ne fonctionnera que sur des hôtes basés sur G5.

La prise en charge de l'adressage 64 bits est expérimentale : certains aspects de Perl peuvent être omis ou bogués. Notez les messages affichés par Configure pour plus d'informations. Veuillez utiliser https://github.com/Perl/perl5/issues pour soumettre un rapport de problème en cas de difficultés.

Lors de la compilation de modules 64 bits, il vous incombe de vous assurer que les bibliothèques externes et les frameworks liés fournissent une prise en charge 64 bits : s'ils ne le font pas, la compilation des modules peut sembler réussie, mais les tentatives d'utilisation du module entraîneront des erreurs de liaison dynamique à l'exécution, puis des échecs de test. Vous pouvez utiliser "file" pour découvrir les architectures prises en charge par une bibliothèque :

$ file libgdbm.3.0.0.dylib 
libgdbm.3.0.0.dylib: Mach-O fat file with 2 architectures
libgdbm.3.0.0.dylib (for architecture ppc):      Mach-O dynamically linked shared library ppc
libgdbm.3.0.0.dylib (for architecture ppc64):    Mach-O 64-bit dynamically linked shared library ppc64

Notez que ce problème empêche la compilation de nombreux modules CPAN spécifiques à Macintosh ("Mac::*"), car les frameworks Apple requis ne fournissent pas de prise en charge PPC64. De même, les téléchargements de Fink ou Darwinports ne fourniront probablement pas de prise en charge 64 bits ; les bibliothèques doivent être reconstruites à partir de la source avec les indicateurs de compilateur et d'éditeur de liens appropriés. Pour plus d'informations, consultez le Guide de transition 64 bits d'Apple à l'adresse https://developer.apple.com/library/archive/documentation/Darwin/Conceptual/64bitPorting/transition/transition.html.

libperl et préliaison

Mac OS X est livré avec une libperl chargée dynamiquement, mais la valeur par défaut pour cette version est de compiler une libperl statique. La raison en est la préliaison. Les bibliothèques dynamiques peuvent être préliées à une adresse mémoire spécifique afin de réduire le temps de chargement. Pour ce faire, il faut connaître l'emplacement et la taille de toutes les bibliothèques précédemment chargées. Apple collecte ces informations dans le cadre de son processus de construction global du système d'exploitation, et y a donc un accès facile lors de la compilation de Perl, mais les utilisateurs ordinaires devraient faire beaucoup d'efforts pour obtenir les informations nécessaires à la préliaison.

Vous pouvez outrepasser la valeur par défaut et compiler une libperl partagée si vous le souhaitez (Configure ... -Duseshrplib).

Avec Mac OS X 10.4 "Tiger" et versions ultérieures, il n'y a quasiment aucune pénalité de performance pour les bibliothèques non préliées. Les versions antérieures subiront un temps de chargement plus long que la bibliothèque statique, ou la bibliothèque dynamique préliée d'Apple.

Mise à jour du Perl d'Apple

En un mot : ne le faites pas, du moins pas sans une *très* bonne raison. Vos scripts peuvent aussi facilement commencer par "#!/usr/local/bin/p

erl" en tant que avec "#!/usr/bin/perl". Les scripts fournis par Apple et d'autres tiers dans le cadre de paquets d'installation et similaires n'ont généralement été testés qu'avec le /usr/bin/perl installé par Apple.

Si vous constatez que vous devez mettre à jour le Perl du système, une question qui mérite d'être prise en compte est celle des bibliothèques statiques par rapport aux bibliothèques dynamiques. Si vous mettez à niveau en utilisant la bibliothèque Perl statique par défaut, vous constaterez que la bibliothèque Perl dynamique fournie par Apple ne sera pas supprimée. Si les deux bibliothèques sont présentes lorsqu'une application qui lie contre libperl est construite, ld liera par défaut contre la bibliothèque dynamique. Donc, si vous avez besoin de remplacer la libperl dynamique d'Apple par une libperl statique, vous devez vous assurer de supprimer l'ancienne bibliothèque dynamique après avoir installé la mise à jour.

Problèmes connus

Si vous avez installé des bibliothèques supplémentaires telles que GDBM via Fink (en d'autres termes, vous avez des bibliothèques sous /sw/lib), ou libdlcompat vers /usr/local/lib, vous devrez peut-être être particulièrement prudent lors de l'exécution de Configure pour ne pas confondre Configure et Perl sur les bibliothèques à utiliser. Être confus se manifestera par exemple par des erreurs de "dyld" concernant des problèmes de symboles, par exemple lors de "make test". La meilleure solution est d'exécuter Configure comme suit :

Configure ... -Uloclibpth -Dlibpth=/usr/lib

pour que Configure ne recherche que dans les bibliothèques système. Si vous avez des répertoires de bibliothèques supplémentaires que vous souhaitez réellement utiliser (tels que les bibliothèques Berkeley DB plus récentes sur les systèmes pré-Panther), ajoutez-les à libpth :

Configure ... -Uloclibpth -Dlibpth='/usr/lib /opt/lib'

La valeur par défaut de la construction de Perl en mode statique peut causer des problèmes avec des applications complexes comme Tk : dans ce cas, envisagez de construire Perl en mode partagé

Configure ... -Duseshrplib

mais n'oubliez pas qu'il y a un coût de démarrage à payer dans ce cas (voir ci-dessus "libperl et Prebinding").

À partir de Tiger (Mac OS X 10.4), Apple a fourni des fichiers de localisation incorrects pour la locale eu_ES (Basque-Espagne). Dans les versions précédentes de Perl, cela entraînait des échecs dans le test lib/locale. Ces échecs ont été supprimés dans la version actuelle de Perl en faisant en sorte que le test ignore la locale incorrecte. Si vous avez besoin d'utiliser la locale eu_ES, vous devriez contacter le support Apple.

Cocoa

Il existe deux façons d'utiliser Cocoa depuis Perl. Le module PerlObjCBridge d'Apple, inclus avec Mac OS X, peut être utilisé par des scripts autonomes pour accéder aux classes et objets Foundation (c'est-à-dire non-GUI).

Une alternative est CamelBones, un framework qui permet d'accéder aux classes et objets Foundation et AppKit, afin de pouvoir construire des applications GUI complètes en Perl. CamelBones est disponible sur SourceForge, à l'adresse https://www.sourceforge.net/projects/camelbones/.

Démarrer de zéro

Malheureusement, il n'est pas si difficile de casser le Perl de Mac OS X d'une manière assez sévère. Si tout le reste échoue et que vous voulez vraiment, VRAIMENT, recommencer à zéro et supprimer même votre installation Perl d'Apple (qui est corrompue d'une manière ou d'une autre), les instructions suivantes devraient suffire. Veuillez réfléchir à deux fois avant de suivre ces instructions : elles sont très similaires à une chirurgie du cerveau sur soi-même. Sans anesthésie. Nous ne viendrons pas réparer votre système si vous faites cela.

Tout d'abord, débarrassez-vous de libperl.dylib :

# cd /System/Library/Perl/darwin/CORE
# rm libperl.dylib

Supprimez ensuite tous les fichiers .bundle trouvés n'importe où dans les dossiers :

/System/Library/Perl
/Library/Perl

Vous pouvez les trouver par exemple en utilisant :

# find /System/Library/Perl /Library/Perl -name '*.bundle' -print

Après cela, vous pouvez soit copier Perl de votre support système (vous aurez besoin au minimum de /System/Library/Perl et /usr/bin/perl), soit reconstruire Perl à partir du code source avec "Configure -Dprefix=/usr -Duseshrplib" NOTE : le "-Dprefix=/usr" pour remplacer le Perl du système fonctionne beaucoup mieux avec Perl 5.8.1 et versions ultérieures, dans Perl 5.8.0 les paramètres n'étaient pas tout à fait corrects.

"Pacifist" de CharlesSoft (https://www.charlessoft.com/) est un bon moyen d'extraire les binaires Perl des supports du système d'exploitation, sans avoir à réinstaller le système d'exploitation entier.
