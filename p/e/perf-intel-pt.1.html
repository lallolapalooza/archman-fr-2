NOM

perf-intel-pt - Support pour Intel Processor Trace dans les outils perf

SYNTAXE

perf record -e intel_pt//

DESCRIPTION

Intel Processor Trace (Intel PT) est une extension de l'architecture Intel qui collecte des informations sur l'exécution du logiciel, telles que le flux de contrôle, les modes d'exécution et les timings, et les formate en paquets binaires hautement compressés. Les détails techniques sont documentés dans les manuels du développeur des architectures Intel 64 et IA-32, chapitre 36 Intel Processor Trace.

Intel PT est pris en charge pour la première fois dans les processeurs Intel Core M et Intel Core de 5ème génération basés sur l'architecture code name Broadwell.

Les données de trace sont collectées par perf record et stockées dans le fichier perf.data. Voir ci-dessous pour les options de perf record.

Les données de trace doivent être décodées, ce qui implique de parcourir le code objet et de faire correspondre les paquets de données de trace. Par exemple, un paquet TNT indique seulement si une branche conditionnelle a été prise ou non, donc pour utiliser ce paquet, le décodeur doit savoir précisément quelle instruction était en cours d'exécution.

Le décodage se fait à la volée. Le décodeur produit des échantillons dans le même format que les échantillons produits par les événements matériels de perf, par exemple comme si les événements "instructions" ou "branches" avaient été enregistrés. Actuellement, 3 outils prennent en charge cela : perf script, perf report et perf inject. Voir ci-dessous pour plus d'informations sur l'utilisation de ces outils.

La principale caractéristique distinctive d'Intel PT est que le décodeur peut déterminer le flux exact de l'exécution du logiciel. Intel PT peut être utilisé pour comprendre pourquoi et comment un logiciel est arrivé à un certain point, ou s'est comporté d'une certaine manière. Le logiciel n'a pas besoin d'être recompilé, donc Intel PT fonctionne avec des builds de débogage ou de production, cependant les images exécutées sont nécessaires - ce qui pose un défi pour une utilisation dans des environnements JIT-compilés, ou avec du code auto-modifiant. De plus, les symboles doivent être fournis pour donner un sens aux adresses.

Une limitation d'Intel PT est qu'il produit d'énormes quantités de données de trace (des centaines de mégaoctets par seconde par cœur) qui prennent beaucoup de temps à décoder, par exemple deux ou trois ordres de grandeur plus longtemps qu'à collecter. Une autre limitation est l'impact sur les performances du traçage, quelque chose qui variera en fonction du cas d'utilisation et de l'architecture.

DEMARRAGE RAPIDE

Il est important de commencer petit. C'est parce qu'il est facile de capturer beaucoup plus de données qu'il n'en faut pour le traitement.

La chose la plus simple à faire avec Intel PT est le profilage en espace utilisateur de petits programmes. Les données sont capturées avec perf record, par exemple pour tracer ls en espace utilisateur uniquement :

perf record -e intel_pt//u ls

Et profilé avec perf report, par exemple :

perf report

Pour tracer également l'espace noyau, cela présente un problème, à savoir le code auto-modifiant du noyau. Une image noyau assez bonne est disponible dans /proc/kcore, mais pour obtenir une image précise, une copie de /proc/kcore doit être faite dans les mêmes conditions que la capture de données. perf record peut faire une copie de /proc/kcore si l'option --kcore est utilisée, mais l'accès à /proc/kcore est restreint, par exemple :

sudo perf record -o pt_ls --kcore -e intel_pt// -- ls

ce qui créera un répertoire nommé pt_ls et y placera le fichier perf.data (nommé simplement data) ainsi que des copies de /proc/kcore, /proc/kallsyms et /proc/modules. Les autres outils comprennent le format de répertoire, donc pour utiliser perf report, cela devient :

sudo perf report -i pt_ls

Comme les échantillons sont synthétisés après coup, la période d'échantillonnage peut être sélectionnée pour le rapport. Par exemple, échantillonner toutes les microsecondes :

sudo perf report pt_ls --itrace=i1usge

Voir les sections ci-dessous pour plus d'informations sur l'option --itrace.

Attention, plus la période est petite, plus il y a d'échantillons produits, et plus le traitement prend du temps.

Notez également que la granularité des informations de synchronisation d'Intel PT commencera à fausser la valeur statistique de l'échantillonnage à mesure que la période d'échantillonnage diminue.

Pour représenter le flux de contrôle du logiciel, des échantillons de "branches" sont produits. Par défaut, un échantillon de branche est synthétisé pour chaque branche individuelle. Pour avoir une idée des données disponibles, vous pouvez utiliser l'outil perf script avec toutes les options d'échantillonnage itrace, qui listera tous les échantillons.

perf record -e intel_pt//u ls
perf script --itrace=iybxwpe

Un champ intéressant qui n'est pas imprimé par défaut est flags (indicateurs), qui peut être affiché comme suit :

perf script --itrace=iybxwpe -F+flags

Les indicateurs sont "bcrosyiABExghDt", qui signifient branche, appel, retour, conditionnel, système, asynchrone, interruption, abandon de transaction, début de trace, fin de trace, en transaction, entrée VM, sortie VM, interruption désactivée, et basculement de désactivation d'interruption respectivement.

perf script prend également en charge des moyens de niveau supérieur pour afficher les traces d'instructions :

perf script --insn-trace=disasm

ou pour utiliser le désassembleur xed, qui nécessite l'installation de l'outil xed (voir XED ci-dessous) :

perf script --insn-trace --xed

L'affichage de toutes les instructions dans une longue trace peut être assez lent. Il est généralement préférable de commencer par un décodage de niveau supérieur, comme :

perf script --call-trace

ou

perf script --call-ret-trace

et ensuite sélectionner une plage de temps d'intérêt. La plage de temps peut alors être examinée en détail avec :

perf script --time starttime,stoptime --insn-trace=disasm

En examinant la trace, il est également utile de filtrer sur des CPU spécifiques en utilisant l'option -C

perf script --time starttime,stoptime --insn-trace=disasm -C 1

Afficher toutes les instructions dans la plage horaire sur le CPU 1.

Un autre champ intéressant qui n'est pas affiché par défaut est ipc (instructions par cycle), qui peut être affiché comme suit :

perf script --itrace=be -F+ipc

Il existe deux façons de calculer les instructions par cycle (IPC) en fonction de l'enregistrement.

Si le terme de configuration cyc (voir la section des termes de configuration ci-dessous) a été utilisé, alors les événements IPC et cycle sont calculés en utilisant le nombre de cycles des paquets CYC, sinon des paquets MTC sont utilisés - se référer au terme de configuration mtc. Lorsque MTC est utilisé, cependant, les valeurs sont moins précises car la synchronisation est moins précise.

Étant donné qu'Intel PT ne met pas à jour le nombre de cycles à chaque branche ou instruction, les valeurs seront souvent nulles. Lorsqu'il y a des valeurs, il s'agira du nombre d'instructions et du nombre de cycles depuis la dernière mise à jour, et représentent donc le nombre moyen de cycles par instruction depuis la dernière mise à jour pour ce type d'événement. Notez que l'IPC pour les événements "branches" est calculé séparément de l'IPC pour les événements "instructions".

Même avec le terme de configuration cyc, il est possible de produire des informations IPC pour chaque changement d'horodatage, mais au détriment de la précision. Ceci est sélectionné en spécifiant l'option A d'itrace. En raison de la granularité des horodatages, le nombre réel de cycles augmente même si le nombre de cycles rapporté n'augmente pas. Le nombre d'instructions est connu, mais si l'IPC est rapporté, le nombre de cycles peut être trop bas et donc l'IPC trop élevé. Notez que l'imprécision diminue à mesure que la période d'échantillonnage augmente, c'est-à-dire que si le nombre de cycles est trop bas d'un petit montant, cela devient moins significatif si le nombre de cycles est grand. Il peut également être utile d'utiliser l'option A en conjonction avec dlfilter-show-cycles.so pour fournir des informations sur les cycles de plus haute granularité.

Notez également que le nombre d'instructions IPC peut ou peut ne pas inclure l'instruction en cours. Si le nombre de cycles est associé à une branche asynchrone (par exemple, défaut de page ou interruption), alors le nombre d'instructions n'inclut pas l'instruction en cours, sinon il l'inclut. Ceci est cohérent avec le fait que cette instruction a été retirée ou non lorsque le nombre de cycles est mis à jour.

Autre remarque, dans le cas des événements "branches", les branches non prises ne sont pas actuellement échantillonnées, donc les valeurs IPC pour celles-ci n'apparaissent pas, par exemple un paquet CYC avec un paquet TNT qui commence par une branche non prise. Pour voir chaque valeur IPC possible, les événements "instructions" peuvent être utilisés, par exemple --itrace=i0ns

PERF RECORD

nouvel événement

Le pilote noyau Intel PT crée une nouvelle PMU pour Intel PT. Les événements PMU sont sélectionnés en fournissant le nom de la PMU suivi de la "config" séparée par des barres obliques. Une amélioration a été apportée pour permettre une "config" par défaut, par exemple l'option

-e intel_pt//

utilisera une valeur de configuration par défaut. Actuellement, c'est la même chose que

-e intel_pt/tsc,noretcomp=0/

ce qui est la même chose que

-e intel_pt/tsc=1,noretcomp=0/

Notez qu'il existe d'autres termes de configuration - voir la section des termes de configuration plus bas.

Les termes de configuration sont listés dans /sys/devices/intel_pt/format. Ce sont des champs de bits dans le membre config de la structure perf_event_attr qui est passée au noyau par l'appel système perf_event_open. Ils correspondent aux champs de bits dans le MSR IA32_RTIT_CTL. Voici une liste d'entre eux et leurs définitions :

$ grep -H . /sys/bus/event_source/devices/intel_pt/format/*
/sys/bus/event_source/devices/intel_pt/format/cyc:config:1
/sys/bus/event_source/devices/intel_pt/format/cyc_thresh:config:19-22
/sys/bus/event_source/devices/intel_pt/format/mtc:config:9
/sys/bus/event_source/devices/intel_pt/format/mtc_period:config:14-17
/sys/bus/event_source/devices/intel_pt/format/noretcomp:config:11
/sys/bus/event_source/devices/intel_pt/format/psb_period:config:24-27
/sys/bus/event_source/devices/intel_pt/format/tsc:config:10

Notez que la configuration par défaut doit être remplacée pour chaque terme, c'est-à-dire

-e intel_pt/noretcomp=0/

est la même chose que :

-e intel_pt/tsc=1,noretcomp=0/

Donc, pour désactiver les paquets TSC, utilisez :

-e intel_pt/tsc=0/

Il est également possible de spécifier explicitement la valeur de configuration :

-e intel_pt/config=0x400/

Notez que, comme avec tous les événements, l'événement est suffixé par des modificateurs d'événement :

u       espace utilisateur
k       noyau
h       hyperviseur
G       invité
H       hôte
p       ip précis

h, G et H sont pour la virtualisation qui ne sont pas utilisés par Intel PT. p n'est pas non plus pertinent pour Intel PT. Donc, seules les options u et k sont significatives pour Intel PT.

termes de configuration

Les termes de configuration sont des paramètres spécifiés avec l'option d'événement -e intel_pt//, par exemple :

-e intel_pt/cyc/

qui sélectionne le mode de précision cyclique. Chaque terme de configuration peut avoir une valeur qui vaut par défaut 1, donc ce qui précède est la même chose que :

-e intel_pt/cyc=1/

Certains termes sont définis par défaut, ils doivent donc être mis à 0 pour les désactiver. Par exemple, pour désactiver le traçage des branches :

-e intel_pt/branch=0/

Plusieurs termes de configuration sont séparés par des virgules, par exemple :

-e intel_pt/cyc,mtc_period=9/

Il existe également des termes de configuration communs, voir la documentation de perf-record(1).

Les termes de configuration Intel PT sont décrits ci-dessous.

tsc

Toujours pris en charge. Produit des paquets d'horodatage TSC pour fournir des informations de synchronisation. Dans certains cas, il est possible de décoder sans informations de synchronisation, par exemple un contexte par thread qui ne chevauche pas les cartes mémoire exécutables.

La configuration par défaut sélectionne tsc (c'est-à-dire tsc=1).

noretcomp

Toujours pris en charge. Désactive la "compression de retour" afin qu'un paquet TIP soit produit lors du retour d'une fonction. Provoque la production de plus de paquets mais peut rendre le décodage plus fiable.

La configuration par défaut ne sélectionne pas noretcomp (c'est-à-dire noretcomp=0).

psb_period

Permet de spécifier la fréquence des paquets PSB.

Le paquet PSB est un paquet de synchronisation qui fournit un point de départ pour le décodage ou la récupération d'erreurs.

La prise en charge de psb_period est indiquée par :

/sys/bus/event_source/devices/intel_pt/caps/psb_cyc

qui contient "1" si la fonctionnalité est prise en charge et "0" sinon.

Les valeurs valides sont données par :

/sys/bus/event_source/devices/intel_pt/caps/psb_periods

qui contient une valeur hexadécimale, dont les bits représentent les valeurs valides, par exemple, le bit 2 défini signifie que la valeur 2 est valide.

La valeur psb_period est convertie en nombre approximatif d'octets de trace entre les paquets PSB comme suit :

2 ^ (valeur + 11)

par exemple, la valeur 3 signifie 16 Ko d'octets entre les PSB.

Si une valeur invalide est entrée, le message d'erreur donnera une liste des valeurs valides, par exemple :

$ perf record -e intel_pt/psb_period=15/u uname
Invalid psb_period for intel_pt. Valid values are: 0-5

Si des paquets MTC sont sélectionnés, la configuration par défaut sélectionne une valeur de 3 (c'est-à-dire psb_period=3) ou la valeur inférieure la plus proche qui est prise en charge (0 est toujours pris en charge). Sinon, la valeur par défaut est 0.

Si le décodage est censé être fiable et que le tampon est grand, une grande période PSB peut être utilisée.

Comme un paquet TSC est produit avec PSB, la période PSB peut également affecter la granularité des informations de synchronisation en l'absence de MTC ou de CYC.

mtc

Produit des paquets de synchronisation MTC.

Les paquets MTC fournissent des informations de synchronisation plus granulaires que les paquets TSC. Les paquets MTC enregistrent le temps à l'aide de l'horloge à cristal matérielle (CTC) qui est liée aux paquets TSC à l'aide d'un paquet TMA.

La prise en charge de cette fonctionnalité est indiquée par :

/sys/bus/event_source/devices/intel_pt/caps/mtc

qui contient "1" si la fonctionnalité est prise en charge et "0" sinon.

La fréquence des paquets MTC peut également être spécifiée - voir mtc_period ci-dessous.

mtc_period

Spécifie la fréquence à laquelle les paquets MTC sont produits - voir mtc ci-dessus pour savoir comment déterminer si les paquets MTC sont pris en charge.

Les valeurs valides sont données par :

/sys/bus/event_source/devices/intel_pt/caps/mtc_periods

qui contient une valeur hexadécimale, dont les bits représentent les valeurs valides, par exemple, le bit 2 défini signifie que la valeur 2 est valide.

La valeur mtc_period est convertie en fréquence MTC comme suit :

Fréquence_CTC / (2 ^ valeur)

par exemple, la valeur 3 signifie un huitième de la fréquence CTC.

Où CTC est l'horloge à cristal matérielle, dont la fréquence peut être liée à TSC via les valeurs fournies dans cpuid leaf 0x15.

Si une valeur invalide est entrée, le message d'erreur donnera une liste des valeurs valides, par exemple :

$ perf record -e intel_pt/mtc_period=15/u uname
Invalid mtc_period for intel_pt. Valid values are: 0,3,6,9

La valeur par défaut est 3 ou la valeur inférieure la plus proche qui est prise en charge (0 est toujours pris en charge).

cyc

Produit des paquets de synchronisation CYC.

Les paquets CYC fournissent des informations de synchronisation encore plus granulaires que les paquets MTC et TSC. Un paquet CYC contient le nombre de cycles CPU depuis le dernier paquet CYC. Contrairement aux paquets MTC et TSC, les paquets CYC ne sont envoyés que lorsqu'un autre paquet est également envoyé.

La prise en charge de cette fonctionnalité est indiquée par :

/sys/bus/event_source/devices/intel_pt/caps/psb_cyc

qui contient "1" si la fonctionnalité est prise en charge et "0" sinon.

Le nombre de paquets CYC produits peut être réduit en spécifiant un seuil - voir cyc_thresh ci-dessous.

cyc_thresh

Spécifie la fréquence à laquelle les paquets CYC sont produits - voir cyc ci-dessus pour savoir comment déterminer si les paquets CYC sont pris en charge.

Les valeurs valides pour cyc_thresh sont données par :

/sys/bus/event_source/devices/intel_pt/caps/cycle_thresholds

qui contient une valeur hexadécimale, dont les bits représentent des valeurs valides, par exemple le bit 2 activé signifie que la valeur 2 est valide.

La valeur cyc_thresh représente le nombre minimum de cycles CPU qui doivent s'écouler avant qu'un paquet CYC ne puisse être envoyé. Le nombre de cycles CPU est :

2 ^ (valeur - 1)

par exemple, la valeur 4 signifie que 8 cycles CPU doivent s'écouler avant qu'un paquet CYC puisse être envoyé. Notez qu'un paquet CYC n'est toujours envoyé que lorsqu'un autre paquet est envoyé, pas par exemple tous les 8 cycles CPU.

Si une valeur invalide est saisie, le message d'erreur fournira une liste des valeurs valides, par exemple :

$ perf record -e intel_pt/cyc,cyc_thresh=15/u uname
Invalid cyc_thresh for intel_pt. Valid values are: 0-12

Les paquets CYC ne sont pas demandés par défaut.

pt

Spécifie le passage (pass-through) qui active le terme de configuration branch.

La configuration par défaut sélectionne pt s'il est disponible, donc un utilisateur n'aura jamais besoin de spécifier ce terme.

branch

Active le traçage des branches. Le traçage des branches est activé par défaut, donc pour le désactiver, utilisez branch=0.

La configuration par défaut sélectionne branch s'il est disponible.

ptw

Active les paquets PTWRITE qui sont produits lorsqu'une instruction ptwrite est exécutée.

La prise en charge de cette fonctionnalité est indiquée par :

/sys/bus/event_source/devices/intel_pt/caps/ptwrite

qui contient "1" si la fonctionnalité est prise en charge et "0" sinon.

En alternative, référez-vous à "PTWRITE émulé" plus loin.

fup_on_ptw

Active un paquet FUP pour suivre le paquet PTWRITE. Le paquet FUP fournit l'adresse de l'instruction ptwrite. En l'absence de fup_on_ptw, le décodeur utilisera l'adresse de la branche précédente si le traçage des branches est activé, sinon l'adresse sera zéro. Notez que fup_on_ptw fonctionnera même lorsque le traçage des branches est désactivé.

pwr_evt

Active les événements de puissance. Les événements de puissance fournissent des informations sur les changements d'état C du CPU.

La prise en charge de cette fonctionnalité est indiquée par :

/sys/bus/event_source/devices/intel_pt/caps/power_event_trace

qui contient "1" si la fonctionnalité est prise en charge et "0" sinon.

event

Active le traçage d'événements. Les événements fournissent des informations sur les événements asynchrones.

La prise en charge de cette fonctionnalité est indiquée par :

/sys/bus/event_source/devices/intel_pt/caps/event_trace

qui contient "1" si la fonctionnalité est prise en charge et "0" sinon.

notnt

Désactive les paquets TNT. Sans paquets TNT, il n'est pas possible de parcourir le code exécutable pour reconstruire le flux de contrôle, cependant les paquets FUP, TIP, TIP.PGE et TIP.PGD indiquent toujours un flux de contrôle asynchrone, et (si la compression des retours est désactivée - voir noretcomp) les instructions de retour. L'avantage de supprimer les paquets TNT est de réduire la taille de la trace et la surcharge de traçage correspondante.

La prise en charge de cette fonctionnalité est indiquée par :

/sys/bus/event_source/devices/intel_pt/caps/tnt_disable

qui contient "1" si la fonctionnalité est prise en charge et "0" sinon.

aux-action=start-paused

Démarre le traçage en pause, référez-vous à la section Pause ou reprise du traçage.

termes de configuration sur d'autres événements

Certaines fonctionnalités d'Intel PT fonctionnent avec d'autres événements, des fonctionnalités telles que l'échantillonnage de la zone AUX et le PEBS-via-PT. Dans ces cas, les autres événements peuvent avoir des termes de configuration ci-dessous :

aux-sample-size

Utilisé pour définir la taille de l'échantillon de la zone AUX, référez-vous à la section Option d'échantillonnage de la zone AUX.

aux-output

Utilisé pour sélectionner PEBS-via-PT, référez-vous à la section PEBS via Intel PT.

aux-action

Utilisé pour mettre en pause ou reprendre le traçage, référez-vous à la section Pause ou reprise du traçage.

Option d'échantillonnage de la zone AUX

Pour sélectionner "l'échantillonnage" d'Intel PT, l'option d'échantillonnage de la zone AUX peut être utilisée :

--aux-sample

Optionnellement, elle peut être suivie de la taille de l'échantillon en octets, par exemple :

--aux-sample=8192

De plus, l'événement Intel PT à échantillonner doit être défini, par exemple :

-e intel_pt//u

Les échantillons sur d'autres événements seront créés contenant des données Intel PT, par exemple, ce qui suit créera des échantillons Intel PT sur l'événement de branches manquées (branch-misses), notez que les événements doivent être regroupés en utilisant :

perf record --aux-sample -e '{intel_pt//u,branch-misses:u}'

Une alternative à --aux-sample est d'ajouter le terme de configuration aux-sample-size aux événements. Dans ce cas, le groupement est implicite, par exemple :

perf record -e intel_pt//u -e branch-misses/aux-sample-size=8192/u

est identique à :

perf record -e '{intel_pt//u,branch-misses/aux-sample-size=8192/u}'

mais permet également d'utiliser un filtre d'adresse, par exemple :

perf record -e intel_pt//u --filter 'filter * @/bin/ls' -e branch-misses/aux-sample-size=8192/u -- ls

Il est important de sélectionner une taille d'échantillon suffisamment grande pour contenir au moins un paquet PSB. Sinon, un avertissement sera affiché :

Intel PT sample size (%zu) may be too small for PSB period (%zu)

Le calcul utilisé pour cela est : si sample_size ≤ psb_period + 256, affichez l'avertissement. Lorsque l'échantillonnage est utilisé, psb_period est de 0 (2 Kio) par défaut.

La taille d'échantillon par défaut est de 4 Kio.

La taille de l'échantillon est passée dans aux_sample_size de la structure perf_event_attr. La taille de l'échantillon est limitée par la taille maximale de l'événement qui est de 64 Kio. Il est difficile de savoir à quel point l'événement pourrait être volumineux sans que l'échantillon de trace soit joint, mais l'outil valide que la taille de l'échantillon n'est pas supérieure à 60 Kio.

nouvelle option snapshot

La différence entre le traçage complet et le snapshot du point de vue du noyau est qu'en traçage complet, nous n'écrasons pas les données de trace que l'utilisateur n'a pas encore collectées (et l'a indiqué en avançant aux_tail), tandis qu'en mode snapshot, nous laissons la trace s'exécuter et écraser les anciennes données dans le tampon de sorte que chaque fois que quelque chose d'intéressant se produit, nous pouvons l'arrêter et capturer un snapshot de ce qui se passait autour de ce moment intéressant.

Pour sélectionner le mode snapshot, une nouvelle option a été ajoutée :

-S

Optionnellement, elle peut être suivie de la taille du snapshot, par exemple :

-S0x100000

La taille de snapshot par défaut est la taille de mmap d'auxtrace. Si ni la taille de mmap d'auxtrace ni la taille de snapshot ne sont spécifiées, alors la valeur par défaut est 4 Mio pour les utilisateurs privilégiés (ou si /proc/sys/kernel/perf_event_paranoid < 0), 128 Kio pour les utilisateurs non privilégiés. Si un utilisateur non privilégié ne spécifie pas de pages mmap, les pages mmap seront réduites comme décrit dans la nouvelle section sur l'option de taille de mmap d'auxtrace ci-dessous.

La taille du snapshot est affichée si l'option -vv est utilisée, par exemple :

Intel PT snapshot size: %zu

nouvelle option de taille de mmap d'auxtrace

La taille du tampon d'Intel PT est spécifiée par un ajout à l'option -m, par exemple :

-m,16

sélectionne une taille de tampon de 16 pages, c'est-à-dire 64 Kio.

Notez que la fonctionnalité existante de -m reste inchangée. La taille de mmap d'auxtrace est spécifiée par l'ajout facultatif d'une virgule et de la valeur.

La taille de mmap d'auxtrace par défaut pour Intel PT est de 4 Mio/taille de page pour les utilisateurs privilégiés (ou si /proc/sys/kernel/perf_event_paranoid < 0), 128 Kio pour les utilisateurs non privilégiés. Si un utilisateur non privilégié ne spécifie pas de pages mmap, les pages mmap seront réduites de la valeur par défaut de 512 Kio/taille de page à 256 Kio/taille de page, sinon l'utilisateur recevra probablement une erreur car il dépassera sa limite de mlock (mémoire maximale verrouillée telle qu'affichée dans /proc/self/limits). Notez que perf ne compte pas les premiers 512 Kio (en fait, /proc/sys/kernel/perf_event_mlock_kb moins 1 page) par CPU contre la limite mlock, donc un utilisateur non privilégié est autorisé à 512 Kio par CPU plus sa limite mlock (qui est de 64 Kio par défaut mais n'est pas multipliée par le nombre de CPU).

En mode de traçage complet, des puissances de deux sont autorisées pour la taille du tampon, avec une taille minimale de 2 pages. En mode snapshot ou en mode échantillonnage, c'est la même chose mais la taille minimale est de 1 page.

La taille de mmap et la taille de mmap d'auxtrace sont affichées si l'option -vv est utilisée, par exemple :

mmap length 528384
auxtrace mmap length 4198400

Modes de fonctionnement d'Intel PT

Intel PT peut être utilisé dans 3 modes : mode de traçage complet, mode échantillon, mode snapshot.

Le mode de traçage complet trace en continu, par exemple :

perf record -e intel_pt//u uname

Le mode échantillon attache un échantillon Intel PT à d'autres événements, par exemple :

perf record --aux-sample -e intel_pt//u -e branch-misses:u

Le mode snapshot capture les données disponibles lorsqu'un signal est envoyé ou qu'une commande de contrôle "snapshot" est émise. Par exemple, en utilisant un signal :

perf record -v -e intel_pt//u -S ./loopy 1000000000 &
[1] 11435
kill -USR2 11435
Recording AUX area tracing snapshot

Notez que le signal envoyé est SIGUSR2. Notez que "Recording AUX area tracing snapshot" est affiché parce que l'option -v est utilisée.

L'avantage d'utiliser la commande de contrôle "snapshot" est que l'accès est contrôlé par l'accès à un FIFO, par exemple :

$ mkfifo perf.control
$ mkfifo perf.ack
$ cat perf.ack &
[1] 15235
$ sudo ~/bin/perf record --control fifo:perf.control,perf.ack -S -e intel_pt//u -- sleep 60 &
[2] 15243
$ ps -e | grep perf
15244 pts/1    00:00:00
perf $ kill -USR2 15244 bash: kill: (15244) - Opération non autorisée $ echo snapshot > perf.control ack

Les 3 modes de fonctionnement d'Intel PT ne peuvent pas être utilisés ensemble.

Gestion des tampons

Il peut y avoir des limitations de tampon (c'est-à-dire une seule entrée ToPa) qui signifient que les tailles réelles de tampon sont limitées aux puissances de 2 jusqu'à 4 Mio (MAX_PAGE_ORDER). Afin de fournir d'autres tailles, et en particulier une taille arbitrairement grande, plusieurs tampons sont concaténés logiquement. Cependant, une interruption doit être utilisée pour passer d'un tampon à l'autre. Cela présente deux problèmes potentiels : a) l'interruption peut ne pas être gérée à temps, de sorte que le tampon actuel devient plein et certaines données de trace sont perdues. b) les interruptions peuvent ralentir le système et affecter les résultats de performance.

Si des données de trace sont perdues, le pilote définit truncated dans l'événement PERF_RECORD_AUX, que les outils signalent comme une erreur.

En mode de trace complète, le pilote attend que les données soient copiées avant d'autoriser le retour au début du tampon (logique). Si les données ne sont pas copiées assez rapidement, à nouveau truncated est défini dans l'événement PERF_RECORD_AUX. Si le pilote doit attendre, l'événement intel_pt est désactivé. Comme il est difficile de savoir quand cela se produit, les outils perf réactivent toujours l'événement intel_pt après avoir copié les données.

Intel PT et identifiants de construction

Par défaut, « perf record » post-traite le flux d'événements pour trouver tous les identifiants de construction des exécutables pour toutes les adresses échantillonnées. Délibérément, Intel PT n'est pas décodé à cette fin (cela prendrait trop de temps). Au lieu de cela, les identifiants de construction de tous les exécutables rencontrés (en raison d'événements mmap, comm ou task) sont inclus dans le fichier perf.data.

Pour voir les identifiants de construction inclus dans le fichier perf.data, utilisez la commande :

perf buildid-list

Si le fichier perf.data contient des données Intel PT, c'est équivalent à :

perf buildid-list --with-hits

Mode snapshot et désactivation des événements

Afin de réaliser un snapshot, l'événement intel_pt est désactivé à l'aide d'un IOCTL, à savoir PERF_EVENT_IOC_DISABLE. Cependant, cela peut également désactiver la collecte d'informations auxiliaires. Afin d'éviter cela, un événement logiciel factice a été introduit qui permet de continuer à enregistrer les événements de suivi (comme les mmap) pendant que intel_pt est désactivé. Ceci est important pour garantir des informations auxiliaires complètes afin de permettre le décodage des snapshots ultérieurs.

Un test a été créé pour cela. Pour trouver le test :

perf test list
...
23: Test using a dummy software event to keep tracking

Pour exécuter le test :

perf test 23
23: Test using a dummy software event to keep tracking     : Ok

modes de perf record (rien de nouveau ici)

perf record fonctionne essentiellement selon l'un des trois modes suivants : par thread, par CPU, uniquement la charge de travail.

Le mode « par thread » est sélectionné par -t ou par --per-thread (avec -p ou -u ou juste une charge de travail). Le mode « par CPU » est sélectionné par -C ou -a. Le mode « uniquement la charge de travail » est sélectionné en n'utilisant pas les autres options mais en fournissant une commande à exécuter (c'est-à-dire la charge de travail).

En mode par thread, une liste exacte de threads est tracée. Il n'y a pas d'héritage. Chaque thread a son propre tampon d'événements.

En mode par CPU, tous les processus (ou les processus du cgroup sélectionné, c'est-à-dire l'option -G, ou les processus sélectionnés avec -p ou -u) sont tracés. Chaque CPU a son propre tampon. L'héritage est autorisé.

En mode uniquement charge de travail, la charge de travail est tracée mais avec des tampons par CPU. L'héritage est autorisé. Notez que vous pouvez maintenant tracer une charge de travail en mode par thread en utilisant l'option --per-thread.

Utilisateurs privilégiés vs non privilégiés

À moins que /proc/sys/kernel/perf_event_paranoid ne soit défini sur -1, les utilisateurs non privilégiés ont des limites de mémoire imposées. Cela affecte les tailles de tampon qu'ils peuvent avoir, comme décrit ci-dessus.

Le noyau v4.2 a introduit la prise en charge d'un événement métadonnées de changement de contexte, PERF_RECORD_SWITCH, qui permet aux utilisateurs non privilégiés de voir quand leurs processus sont planifiés en dehors et en dedans, mais pas par qui, ce qui est réservé à PERF_RECORD_SWITCH_CPU_WIDE, qui n'est accessible que dans le contexte système entier, qui à son tour nécessite CAP_PERFMON ou CAP_SYS_ADMIN.

Veuillez consulter le commit 45ac1403f564 (« perf : Ajouter PERF_RECORD_SWITCH pour indiquer les changements de contexte ») pour plus d'informations.

PERF SCRIPT

Par défaut, perf script décode les données de trace trouvées dans le fichier perf.data. Ceci peut être contrôlé davantage par la nouvelle option --itrace.

Nouvelle option --itrace

Ne pas avoir d'option équivaut à

--itrace

qui, à son tour, équivaut à

--itrace=cepwxy

Les lettres sont :

i       synthétiser les événements « instructions »
y       synthétiser les événements « cycles »
b       synthétiser les événements « branches »
x       synthétiser les événements « transactions »
w       synthétiser les événements « ptwrite »
p       synthétiser les événements « power » (incluant les événements PSB)
c       synthétiser les événements branches (appels uniquement)
r       synthétiser les événements branches (retours uniquement)
o       synthétiser les événements PEBS-via-PT
I       synthétiser les événements Event Trace
e       synthétiser les événements d'erreur de traçage
d       créer un journal de débogage
g       synthétiser une chaîne d'appels (utiliser avec i ou x)
G       synthétiser une chaîne d'appels sur des enregistrements d'événements existants
l       synthétiser les entrées de branchement les plus récentes (utiliser avec i ou x)
L       synthétiser les entrées de branchement les plus récentes sur des enregistrements d'événements existants
s       ignorer le nombre initial d'événements
q       décodage plus rapide (moins détaillé)
A       IPC approximatif
Z       préférer ignorer les horodatages (décodage dit « sans horodatage »)

Les événements « instructions » ressemblent à ceux enregistrés par « perf record -e instructions ».

Les événements « cycles » ressemblent à ceux enregistrés par « perf record -e cycles » (c'est-à-dire par défaut). Notez que même avec les paquets CYC activés et aucun échantillonnage, ceux-ci ne sont pas entièrement précis, car les paquets CYC ne sont pas émis

d pour chaque instruction, uniquement lorsqu'un autre événement (comme une branche indirecte ou un paquet TNT représentant plusieurs branches) se produit, ce qui provoque l'émission d'un paquet. Par conséquent, il est plus efficace pour attribuer des cycles aux fonctions (et éventuellement aux blocs de base) qu'à des instructions individuelles, bien que ce ne soit même pas parfait pour les fonctions (bien que cela s'améliore si l'option noretcomp est active).

"Branches" les événements ressemblent à ceux enregistrés par "perf record -e branches". "c" et "r" peuvent être combinés pour obtenir des appels et des retours.

"Transactions" les événements correspondent au début ou à la fin des transactions. Le champ flags peut être utilisé dans perf script pour déterminer si l'événement est un début de transaction, une validation ou un abandon.

Notez que les événements "instructions", "cycles", "branches" et "transactions" dépendent des paquets de flux de code qui peuvent être désactivés en utilisant le terme de configuration "branch=0". Reportez-vous à la section des termes de configuration ci-dessus.

"ptwrite" les événements enregistrent la charge utile de l'instruction ptwrite et si "fup_on_ptw" a été utilisé. Les événements "ptwrite" dépendent des paquets PTWRITE qui ne sont enregistrés que si le terme de configuration "ptw" a été utilisé. Reportez-vous à la section des termes de configuration ci-dessus. Le champ "synth" de perf script affiche les informations "ptwrite" comme suit : "ip: 0 payload: 0x123456789abcdef0" où "ip" est 1 si "fup_on_ptw" a été utilisé.

"Power" les événements correspondent aux paquets d'événements d'alimentation et aux paquets CBR (core-to-bus ratio). Bien que les paquets CBR soient toujours enregistrés lorsque le traçage est activé, les paquets d'événements d'alimentation ne sont enregistrés que si le terme de configuration "pwr_evt" a été utilisé. Reportez-vous à la section des termes de configuration ci-dessus. Les événements d'alimentation enregistrent des informations sur les changements d'état C, tandis que le CBR est indicatif de la fréquence du processeur. Les champs "event,synth" de perf script affichent des informations comme suit :

cbr:  cbr: 22 freq: 2189 MHz (200%)
mwait:  hints: 0x60 extensions: 0x1
pwre:  hw: 0 cstate: 2 sub-cstate: 0
exstop:  ip: 1
pwrx:  deepest cstate: 2 last cstate: 2 wake reason: 0x4

Où :

"cbr" inclut la fréquence et le pourcentage de non-turbo maximum
"mwait" montre les indications et extensions mwait
"pwre" montre les transitions d'état C (vers un état C plus profond que C0) et
si elles sont initiées par le matériel
"exstop" indique que l'exécution s'est arrêtée et si l'IP a été enregistré
exactement,
"pwrx" indique le retour à C0

Pour plus de détails, consultez les Intel 64 and IA-32 Architectures Software Developer Manuals.

Les événements PSB indiquent quand un PSB+ s'est produit et aussi le décalage en octets dans la trace. L'émission d'un PSB+ peut entraîner un léger délai du processeur. Lors de l'analyse temporelle du code avec Intel PT, il est utile de savoir si une bulle temporelle a été causée par Intel PT ou non.

Les événements d'erreur indiquent où le décodeur a perdu la trace. Les événements d'erreur sont très importants. Les utilisateurs doivent savoir si ce qu'ils voient est une image complète ou non. L'option "e" peut être suivie de drapeaux qui affectent les erreurs qui seront ou non signalées. Chaque drapeau doit être précédé de + ou -. Les drapeaux pris en charge par Intel PT sont :

-o      Supprimer les erreurs de dépassement de capacité
-l      Supprimer les erreurs de perte de données de trace

Par exemple, pour les erreurs mais pas les erreurs de dépassement de capacité ou de perte de données :

--itrace=e-o-l

L'option "d" provoquera la création d'un fichier "intel_pt.log" contenant tous les paquets décodés et instructions. Notez que cette option ralentit le décodeur et que le fichier résultant peut être très volumineux. L'option "d" peut être suivie de drapeaux qui affectent les messages de débogage qui seront ou non enregistrés. Chaque drapeau doit être précédé de + ou -. Les drapeaux pris en charge par Intel PT sont :

-a      Supprimer l'enregistrement des événements perf
+a      Enregistrer tous les événements perf
+e      Sortir uniquement en cas d'erreurs de décodage (taille configurable)
+o      Sortir sur stdout au lieu de "intel_pt.log"

Par défaut, les événements perf enregistrés sont filtrés par les plages temporelles spécifiées, mais le drapeau +a remplace ce comportement. Le drapeau +e peut être utile pour analyser les erreurs. Par défaut, la taille du journal dans ce cas est de 16384 octets, mais elle peut être modifiée par perf-config(1) par exemple perf config itrace.debug-log-buffer-size=30000

De plus, la période de l'événement "instructions" peut être spécifiée. Par exemple :

--itrace=i10us

définit la période à 10us, c'est-à-dire qu'un échantillon d'instruction est synthétisé pour chaque 10 microsecondes de trace. Les alternatives à "us" sont "ms" (millisecondes), "ns" (nanosecondes), "t" (tics TSC) ou "i" (instructions).

"ms", "us" et "ns" sont convertis en tics TSC.

Les informations temporelles incluses avec Intel PT ne donnent pas le temps de chaque instruction. Par conséquent, à des fins d'échantillonnage, le décodeur estime le temps écoulé depuis le dernier paquet temporel en se basant sur 1 tic par instruction. L'heure de l'échantillon n'est **pas** ajustée et reflète la dernière valeur connue du TSC.

Pour Intel PT, la période par défaut est de 100us.

La régler sur une période nulle signifie "aussi souvent que possible".

Dans le cas d'Intel PT, cela équivaut à une période de 1 et une unité de instructions (c'est-à-dire --itrace=i1i).

De plus, la taille de la chaîne d'appels (par défaut 16, max. 1024) pour les événements d'instructions ou de transactions peut être spécifiée. Par exemple :

--itrace=ig32
--itrace=xg32

De plus, le nombre de dernières entrées de branche (par défaut 64, max. 1024) pour les événements d'instructions ou de transactions peut être spécifié. Par exemple :

--itrace=il10
--itrace=xl10

Notez que les dernières entrées de branche sont effacées pour chaque échantillon, il n'y a donc aucun chevauchement d'un échantillon à l'autre.

Les options G et L sont conçues en particulier pour le mode échantillon, et fonctionnent de manière similaire à g et l mais ajoutent la chaîne d'appels et la pile de branches aux autres événements sélectionnés au lieu d'événements synthétisés. Par exemple, pour enregistrer des événements de branche manquante pour ls, puis ajouter une chaîne d'appels dérivée de la trace Intel PT :

perf record --aux-sample -e '{intel_pt//u,branch-misses:u}' -- ls
perf report --itrace=Ge

Bien qu'en fait G soit une valeur par défaut pour perf report, c'est donc la même chose que juste :

perf report

Une mise en garde avec les options G et L est qu'elles fonctionnent mal avec "Large PEBS". Large PEBS signifie que les enregistrements PEBS seront accumulés par le matériel et écrits dans le tampon d'événements en une seule fois. Cela réduit les interruptions, mais peut donner des horodatages très tardifs. Parce que la trace Intel PT est synchronisée par des horodatages, les événements PEBS ne correspondent pas à la trace. Actuellement, Large PEBS n'est utilisé que dans certaines circonstances : - le matériel le prend en charge - PEBS est utilisé - la période de l'événement est spécifiée, au lieu de la fréquence - le type d'échantillon est limité aux drapeaux suivants : PERF_SAMPLE_IP | PERF_SAMPLE_TID | PERF_SAMPLE_ADDR | PERF_SAMPLE_ID | PERF_SAMPLE_CPU | PERF_SAMPLE_STREAM_ID | PERF_SAMPLE_DATA_SRC | PERF_SAMPLE_IDENTIFIER | PERF_SAMPLE_TRANSACTION | PERF_SAMPLE_PHYS_ADDR | PERF_SAMPLE_REGS_INTR | PERF_SAMPLE_REGS_USER | PERF_SAMPLE_PERIOD (et parfois) | PERF_SAMPLE_TIME Comme le mode échantillon Intel PT utilise un type d'échantillon différent de la liste ci-dessus, Large PEBS n'est pas utilisé avec le mode échantillon Intel PT. Pour éviter Large PEBS dans d'autres cas, évitez de spécifier la période de l'événement, c'est-à-dire évitez l'option perf record -c, l'option --count, ou le terme de configuration period.

Pour désactiver complètement le décodage de trace, utilisez l'option --no-itrace.

Il est également possible d'ignorer les événements générés (instructions, branches, transactions) au début. Ceci est utile pour ignorer le code d'initialisation.

--itrace=i0nss1000000

ignore les premiers millions d'instructions.

L'option q modifie la façon dont la trace est décodée. Le décodage est beaucoup plus rapide mais beaucoup moins détaillé. Spécifiquement, avec l'option q, le décodeur ne décode pas les paquets TNT et ne parcourt pas le code objet, mais obtient l'ip à partir des paquets FUP et TIP. L'option q peut être utilisée avec les options b et i, mais la période n'est pas utilisée. L'option q décode plus rapidement, mais n'est utile que si le flux de contrôle d'intérêt est représenté ou indiqué par les paquets FUP, TIP, TIP.PGE ou TIP.PGD (voir ci-dessous). Cependant, l'option q pourrait être utilisée pour trouver des plages temporelles qui pourraient ensuite être décodées entièrement en utilisant l'option --time.

Ce qui **ne sera pas** décodé avec l'option q (unique) :

•appels directs et sauts
•branches conditionnelles
•instructions non-branche

Ce qui **sera** décodé avec l'option q (unique) :

•branches asynchrones comme les interruptions
•branches indirectes
•adresse de retour de fonction **si** le terme de configuration noretcomp (voir section termes de configuration) a été utilisé
•début du traçage (flux de contrôle)
•fin du traçage (flux de contrôle), s'il n'est pas hors contexte
•événements d'alimentation, ptwrite, début et abandon de transaction
•pointeur d'instruction associé aux paquets PSB

Notez que l'option q ne spécifie pas les événements qui seront synthétisés, par exemple, l'option p doit également être utilisée pour afficher les événements d'alimentation.

Répéter l'option q (double-q, c'est-à-dire qq) entraîne un décodage encore plus rapide et encore moins de détails. Le décodeur ne décode que les paquets PSB étendus (PSB+), obtenant le pointeur d'instruction s'il y a un paquet FUP dans PSB+ (c'est-à-dire entre PSB et PSBEND). Notez que les paquets PSB se produisent régulièrement dans la trace en fonction du terme de configuration psb_period (voir section termes de configuration). Il y aura un paquet FUP si le PSB+ se produit pendant que le flux de contrôle est tracé.

Ce qui **ne sera pas** décodé avec l'option qq :

•tout sauf le pointeur d'instruction associé aux paquets PSB

Ce qui **sera** décodé avec l'option qq :

•pointeur d'instruction associé aux paquets PSB

L'option Z équivaut à avoir enregistré une trace sans TSC (c'est-à-dire terme de configuration tsc=0). Elle peut être utile pour éviter les problèmes d'horodatage lors du décodage d'une trace d'une machine virtuelle.

DLFILTERS

When tracing kernel code, or user code running in the kernel, Intel PT can trace code that is dynamically loaded using DL_CALLER or DL_CALLER2 or DL_PASS2 or DL_PASS3 or DL_PASS4 or DL_PASS5 or DL_PASS6 dlfilters. These are specified using the -d option to perf script or perf record.

For example, to trace kernel module dlfilter:

perf record -e intel_pt/dlfilter=kernel/u prog
perf script -d kernel

To trace only dlfilters that are part of the main executable:

perf record -e intel_pt/dlfilter=prog/u prog
perf script -d prog

To see a list of dlfilters:

perf script -v --list-dlfilters

See also perf-dlfilters(1)

dump option

perf script has an option (-D) to "dump" the events i.e. display the binary data.

When -D is used, Intel PT packets are displayed. The packet decoder does not pay attention to PSB packets, but just decodes the bytes - so the packets seen by the actual decoder may not be identical in places where the data is corrupt. One example of that would be when the buffer-switching interrupt has been too slow, and the buffer has been filled completely. In that case, the last packet in the buffer might be truncated and immediately followed by a PSB as the trace continues in the next buffer.

To disable the display of Intel PT packets, combine the -D option with --no-itrace.

PERF REPORT

By default, perf report will decode trace data found in the perf.data file. This can be further controlled by new option --itrace exactly the same as perf script, with the exception that the default is --itrace=igxe.

PERF INJECT

perf inject also accepts the --itrace option in which case tracing data is removed and replaced with the synthesized events. e.g.

PEBS VIA INTEL PT

Some hardware has the feature to redirect PEBS records to the Intel PT trace. Recording is selected by using the aux-output config term e.g.

perf record -c 10000 -e '{intel_pt/branch=0/,cycles/aux-output/ppp}' uname

Originally, software only supported redirecting at most one PEBS event because it was not able to differentiate one event from another. To overcome that, more recent kernels and perf tools add support for the PERF_RECORD_AUX_OUTPUT_HW_ID side-band event. To check for the presence of that event in a PEBS-via-PT trace:

perf script -D --no-itrace | grep PERF_RECORD_AUX_OUTPUT_HW_ID

To display PEBS events from the Intel PT trace, use the itrace o option e.g.

perf script --itrace=oe

TRACING VIRTUAL MACHINES (KERNEL ONLY)

Currently, kernel tracing is supported with either "timeless" decoding (i.e. no TSC timestamps) or VM Time Correlation. VM Time Correlation is an extra step using perf inject and requires unchanging VMX TSC Offset and no VMX TSC Scaling.

Other limitations and caveats

VMX controls may suppress packets needed for decoding resulting in decoding errors
VMX controls may block the perf NMI to the host potentially resulting in lost trace data
Guest kernel self-modifying code (e.g. jump labels or JIT-compiled eBPF) will result in decoding errors
Guest thread information is unknown
Guest VCPU is unknown but may be able to be inferred from the host thread
Callchains are not supported

TRAÇAGE D'ÉVÉNEMENTS

Le traçage d'événements enregistre des informations sur les événements asynchrones, par exemple les interruptions, les fautes, les sorties et entrées VM. Les informations sont enregistrées dans des paquets CFE et EVD, et le drapeau d'interruption est également enregistré sur le paquet MODE.Exec. Le paquet CFE contient un champ type pour identifier l'un des éléments suivants :

 1      INTR            interrupt, fault, exception, NMI
 2      IRET            interrupt return
 3      SMI             system management interrupt
 4      RSM             resume from system management mode
 5      SIPI            startup interprocessor interrupt
 6      INIT            INIT signal
 7      VMENTRY         VM-Entry
 8      VMEXIT          VM-Entry
 9      VMEXIT_INTR     VM-Exit due to interrupt
10      SHUTDOWN        Shutdown

Pour plus de détails, consultez les manuels Intel 64 and IA-32 Architectures Software Developer Manuals (version 076 ou ultérieure).

La capacité à effectuer le traçage d'événements est indiquée par le fichier /sys/bus/event_source/devices/intel_pt/caps/event_trace.

Le traçage d'événements est sélectionné pour l'enregistrement en utilisant le terme de configuration "event". par exemple.

perf record -e intel_pt/event/u uname

Les événements de traçage d'événements sont affichés en utilisant l'option I du traçage --itrace. par exemple.

perf script --itrace=Ie

perf script affiche les événements contenant le type CFE, le vecteur et les données de l'événement, sous la forme :

evt:   hw int            (t)  cfe: INTR IP: 1 vector: 3 PFA: 0x8877665544332211

Le drapeau IP indique si l'événement est lié à un IP, ce qui inclut tout cas où la génération de paquets de contrôle de flux est activée, ainsi que lorsque le bit IP du paquet CFE est défini.

perf script affiche les événements contenant les changements du drapeau d'interruption sous la forme :

iflag:   t                      IFLAG: 1->0 via branch

où "via branch" indique une branche (interruption ou retour d'interruption) et "non branch" indique une instruction telle que CFI, STI ou POPF).

De plus, l'état actuel du drapeau d'interruption est indiqué par la présence ou l'absence du drapeau "D" (interruption désactivée) du script perf. Si le drapeau d'interruption est modifié, alors le drapeau "t" est également inclus, c'est-à-dire.

        no flag, interrupts enabled IF=1
t       interrupts become disabled IF=1 -> IF=0
D       interrupts are disabled IF=0
Dt      interrupts become enabled  IF=0 -> IF=1

Le script intel-pt-events.py illustre comment accéder aux informations d'Event Trace à l'aide d'un script Python.

TNT DESACTIVATION

Les paquets TNT sont désactivés en utilisant le terme de configuration "notnt". par exemple.

perf record -e intel_pt/notnt/u uname

Dans ce cas, l'option --itrace q est forcée car la marche du code exécutable pour reconstruire le flux de contrôle n'est pas possible.

NOM

perf-intel-pt - Introduction à Intel® Processor Trace avec perf

DESCRIPTION

Intel® Processor Trace (Intel PT) est une fonctionnalité de trace matérielle qui fournit un enregistrement détaillé de l'exécution du code. Le projet perf peut utiliser Intel PT pour capturer ces traces.

Cette page de manuel décrit comment utiliser les outils perf pour interagir avec Intel PT.

CONFIGURATION AVEC PERF RECORD

Le principal outil utilisé pour capturer Intel PT est perf-record(1). Pour activer Intel PT, vous devez spécifier l'événement intel_pt. Vous pouvez également spécifier des filtres pour cibler des parties spécifiques de l'exécution. Voici quelques exemples de configuration :

$ perf record -e intel_pt//u -a -- sleep 10

Cet exemple enregistre la trace Intel PT pour l'ensemble du système (-a) pendant 10 secondes. Le filtre //u indique que la trace doit être effectuée pour les événements utilisateur. Pour inclure les événements du noyau, vous pouvez utiliser //k.

$ perf record -e intel_pt//k -a -- sleep 10

Pour enregistrer uniquement la trace du noyau, utilisez //k. Vous pouvez combiner les deux en omettant le filtre.

$ perf record -e intel_pt -a -- sleep 10

Vous pouvez également utiliser des filtres plus spécifiques pour cibler des processus ou des espaces de noms :

$ perf record -e intel_pt/pid=1234//u -- sleep 10

Ceci trace uniquement pour le processus avec PID 1234 dans l'espace utilisateur.

$ perf record -e intel_pt/tid=5678//u -- sleep 10

Ceci trace uniquement pour le thread avec TID 5678 dans l'espace utilisateur.

Utilisation de filtres pour des cœurs spécifiques :

$ perf record -e intel_pt/cpu=0//u -- sleep 10

Ceci trace uniquement pour le cœur 0 dans l'espace utilisateur.

Utilisation de filtres pour des cœurs et des PID spécifiques :

$ perf record -e intel_pt/cpu=0,pid=1234//u -- sleep 10

Ceci trace uniquement pour le PID 1234 sur le cœur 0 dans l'espace utilisateur.

Vous pouvez également utiliser des filtres pour exclure certains types d'événements. Par exemple, pour exclure les événements de branchement conditionnel et inconditionnel, vous pouvez utiliser =(br,call,ret,ind).

$ perf record -e intel_pt/=(br,call,ret,ind)//u -a -- sleep 10

Pour exclure tous les événements sauf les sauts inconditionnels :

$ perf record -e intel_pt/=(~...)//u -a -- sleep 10

Pour exclure tous les événements sauf les sauts conditionnels :

$ perf record -e intel_pt/=(~...,call,ret,ind)//u -a -- sleep 10

Pour exclure tous les événements sauf les sauts conditionnels et les appels :

$ perf record -e intel_pt/=(~...,ret,ind)//u -a -- sleep 10

Pour exclure tous les événements sauf les sauts conditionnels, les appels et les retours :

$ perf record -e intel_pt/=(~...)//u -a -- sleep 10

Notez que vous pouvez utiliser différentes combinaisons de filtres pour ajuster la quantité de données collectées.

TRAITEMENT DES DONNÉES AVEC PERF SCRIPT

perf-script(1) est utilisé pour traiter les fichiers de données enregistrés par perf-record(1). Pour afficher les données Intel PT, vous pouvez utiliser l'option --itrace.

$ perf script --itrace=ew

Cela affichera la trace des événements de début et de fin des instructions (execute/write).

Pour voir la trace des événements du noyau (kernel), utilisez --itrace=e.

$ perf script --itrace=e

Pour afficher les événements liés aux callsites, utilisez --itrace=c.

$ perf script --itrace=c

Pour afficher tous les événements de trace, utilisez --itrace=a.

$ perf script --itrace=a

Vous pouvez filtrer la sortie de perf-script(1) pour afficher uniquement les événements Intel PT.

$ perf script -e intel_pt

Le traitement des données Intel PT peut générer une grande quantité de données. Il est souvent nécessaire d'utiliser des filtres supplémentaires pour se concentrer sur les informations pertinentes.

INSTRUMENTATION SPÉCIFIQUE AVEC LA MACRO PERF_EMULATE_PTWRITE

La macro PERF_EMULATE_PTWRITE est utilisée pour insérer des instructions spécifiques dans le code afin de déclencher des événements Intel PT.

#define PERF_EMULATE_PTWRITE_8_BITS        "1: shl %rax\n"     \
                "   jc 1f\n"
/* Undefined instruction */
#define PERF_EMULATE_PTWRITE_UD2        ".byte 0x0f, 0x0b\n"
#define PERF_EMULATE_PTWRITE_MAGIC        PERF_EMULATE_PTWRITE_UD2 ".ascii \"perf,ptwrite  \"\n"
void perf_emulate_ptwrite(uint64_t x __attribute__ ((__unused__)))
{
         /* Assumes SysV ABI : x passed in rdi */
        __asm__ volatile (
                "jmp 1f\n"
                PERF_EMULATE_PTWRITE_MAGIC
                "1: mov %rdi, %rax\n"
                PERF_EMULATE_PTWRITE_8_BITS
                PERF_EMULATE_PTWRITE_8_BITS
                PERF_EMULATE_PTWRITE_8_BITS
                PERF_EMULATE_PTWRITE_8_BITS
                PERF_EMULATE_PTWRITE_8_BITS
                PERF_EMULATE_PTWRITE_8_BITS
                PERF_EMULATE_PTWRITE_8_BITS
                PERF_EMULATE_PTWRITE_8_BITS
                "1: ret\n"
        );
}

Par exemple, un programme de test avec la fonction ci-dessus :

#include <stdio.h>
#include <stdint.h>
#include <stdlib.h>
#include "perf_emulate_ptwrite.h"
int main(int argc, char *argv[])
{
        uint64_t x = 0;
        if (argc > 1)
                x = strtoull(argv[1], NULL, 0);
        perf_emulate_ptwrite(x);
        return 0;
}

MODE TUYAU

Le mode tuyau pose problème pour Intel PT et potentiellement d'autres utilisateurs d'auxtrace. Il n'est pas recommandé d'utiliser un tuyau comme sortie de données avec Intel PT pour la raison suivante.

Essentiellement, les tampons auxtrace ne se comportent pas comme les tampons d'événements perf réguliers. C'est parce que la tête et la queue sont mises à jour par le logiciel, mais dans le cas d'auxtrace, les données sont écrites par le matériel. Ainsi, la tête et la queue ne sont pas mises à jour à mesure que les données sont écrites.

Dans le cas d'Intel PT, la tête et la queue ne sont mises à jour que lorsque la trace est désactivée par logiciel, par exemple : - trace complète, système entier : lorsque le tampon dépasse le seuil - trace complète, pas système entier : lorsque le tampon dépasse le seuil ou lors des changements de contexte - mode instantané : comme ci-dessus mais aussi lorsqu'un instantané est pris - mode échantillon : comme ci-dessus mais aussi lorsqu'un échantillon est pris

Cela signifie que l'ordre des tours terminés ne fonctionne pas. Un tampon auxtrace peut apparaître avec des données qui remontent dans le temps, potentiellement jusqu'au tout début du traçage.

Pour un fichier perf.data, ce problème est résolu en parcourant la trace et en mettant en file d'attente les tampons auxtrace à l'avance.

Pour le mode tuyau, l'ordre des événements et des horodatages peut probablement être perturbé.

Avec les noyaux plus récents, il est possible d'utiliser d'autres événements sélectionnés pour mettre en pause ou reprendre le traçage Intel PT. Ceci est configuré en utilisant le terme de configuration "aux-action" :

"aux-action=pause" est utilisé avec les événements qui doivent mettre en pause le traçage Intel PT.

"aux-action=resume" est utilisé avec les événements qui doivent reprendre le traçage Intel PT.

"aux-action=start-paused" est utilisé avec l'événement Intel PT pour démarrer dans un état de pause.
