PERLREGUTS(1perl) Guide du programmeur Perl PERLREGUTS(1perl)

NOM

perlreguts - Description du moteur d'expressions régulières de Perl.

DESCRIPTION

Ce document tente d'apporter un peu de lumière sur les rouages du moteur d'expressions régulières et son fonctionnement. Le moteur d'expressions régulières représente une part importante de la base de code de Perl, mais il est relativement peu compris. Ce document est une modeste tentative pour remédier à cette situation. Il est issu de l'expérience de l'auteur, des commentaires dans le code source, d'autres papiers sur le moteur d'expressions régulières, des retours de la liste de diffusion perl5-porters, et sans doute d'autres sources.

AVIS ! Il doit être clairement compris que le comportement et les structures discutés ici représentent l'état du moteur tel que l'auteur l'a compris au moment de la rédaction. Ce n'est **PAS** une définition d'API, c'est purement un guide interne pour ceux qui veulent modifier le moteur d'expressions régulières ou comprendre son fonctionnement. Les lecteurs de ce document sont censés comprendre la syntaxe des expressions régulières de Perl et son utilisation en détail. Si vous voulez apprendre les bases des expressions régulières de Perl, consultez perlre. Et si vous voulez remplacer le moteur d'expressions régulières par le vôtre, consultez perlreapi.

APERÇU

Une note rapide sur les termes

Il y a débat pour savoir s'il faut dire "regexp" ou "regex". Dans ce document, nous utiliserons le terme "regex" sauf s'il y a une raison spéciale de ne pas le faire, auquel cas nous expliquerons pourquoi.

Lorsque nous parlons de regex, nous devons distinguer leur forme code source et leur forme interne. Dans ce document, nous utiliserons le terme "pattern" (motif) lorsque nous parlerons de leur forme textuelle, code source, et le terme "program" (programme) lorsque nous parlerons de leur représentation interne. Cela correspond aux termes *S-regex* et *B-regex* que Mark Jason Dominus emploie dans son papier sur "Rx" ([1] dans "REFERENCES").

Qu'est-ce qu'un moteur d'expressions régulières ?

Un moteur d'expressions régulières est un programme qui prend un ensemble de contraintes spécifiées dans un mini-langage, puis applique ces contraintes à une chaîne cible, et détermine si la chaîne satisfait ou non les contraintes. Voir perlre pour une définition complète du langage.

En termes moins grandiloquents, la première partie du travail consiste à transformer un motif en quelque chose que l'ordinateur peut utiliser efficacement pour trouver le point de correspondance dans la chaîne, et la seconde partie consiste à effectuer la recherche elle-même.

Pour ce faire, nous devons produire un programme en analysant le texte. Nous devons ensuite exécuter le programme pour trouver le point dans la chaîne qui correspond. Et nous devons faire le tout efficacement.

Structure d'un programme Regex

Haut niveau

Bien que ce soit un peu déroutant et que certaines personnes s'opposent à la terminologie, il est utile de jeter un coup d'œil à un commentaire qui figure dans regexp.h depuis des années :

Ceci est essentiellement un codage linéaire d'une machine à états finis non déterministe (également appelée cartes syntaxiques ou "forme normale de chemin de fer" dans la technologie d'analyse syntaxique).

Le terme "forme normale de chemin de fer" est un peu ésotérique, "diagramme/carte syntaxique", ou "diagramme/carte de chemin de fer" étant des termes plus courants. Néanmoins, cela fournit une image mentale utile d'un programme regex : chaque nœud peut être considéré comme une unité de voie, avec un point d'entrée unique et dans la plupart des cas un point de sortie unique (il y a des morceaux de voie qui se divisent, mais statistiquement pas beaucoup), et l'ensemble forme une disposition avec un point d'entrée et un point de sortie uniques. Le processus de correspondance peut être considéré comme une voiture qui se déplace le long de la voie, l'itinéraire particulier à travers le système étant déterminé par le caractère lu à chaque point de connexion possible. Une voiture peut tomber de la voie à n'importe quel point, mais elle ne peut avancer tant qu'elle correspond à la voie.

Ainsi, le motif "/foo(?:\w+|\d+|\s+)bar/" peut être considéré comme le diagramme suivant :

     [début]
        |
      <foo>
        |
  +-----+-----+
  |     |     |
<\w+> <\d+> <\s+>
  |     |     |
  +-----+-----+
        |
      <bar>
        |
      [fin]

La vérité est que les expressions régulières de Perl sont aujourd'hui beaucoup plus complexes que ce type de structure, mais le visualiser ainsi peut aider à s'orienter, et cela correspond assez étroitement à l'implémentation actuelle.

Pour être plus précis, nous dirons qu'un programme regex est un codage d'un graphe. Chaque nœud du graphe correspond à une partie du motif d'expression régulière d'origine, telle qu'une chaîne littérale ou une branche, et possède un pointeur vers les nœuds représentant le composant suivant à faire correspondre. Comme "nœud" et "opcode" ont déjà d'autres significations dans le code source de Perl, nous appellerons les nœuds d'un programme regex "regops".

Le programme est représenté par un tableau de structures "regnode", dont une ou plusieurs représentent un unique regop du programme. La structure "regnode" est la plus petite structure nécessaire, et possède une structure de champ qui est partagée avec toutes les autres structures plus grandes. (En dehors de ce document, le terme "regnode" est parfois utilisé pour signifier "regop", ce qui pourrait prêter à confusion.)

Les pointeurs "next" de tous les regops, sauf "BRANCH", implémentent la concaténation ; un pointeur "next" avec un "BRANCH" aux deux extrémités relie deux alternatives. [Ici, nous avons une des subtiles dépendances syntaxiques : un "BRANCH" individuel (par opposition à une collection d'entre eux) n'est jamais concaténé avec quoi que ce soit en raison de la précédence des opérateurs.]

L'opérande de certains types de regops est une chaîne littérale ; pour d'autres, c'est un regop menant à un sous-programme. En particulier, l'opérande d'un nœud "BRANCH" est le premier regop de la branche.

NOTE : Comme le suggère la métaphore du chemin de fer, ce n'est **pas** une structure arborescente : la queue de la branche se connecte à la chose qui suit l'ensemble des "BRANCH"es. C'est comme une seule ligne de voie ferrée qui se divise en entrant dans une gare ou un dépôt et qui se rejoint en sortant de l'autre côté.

Regops

La structure de base d'un regop est définie dans regexp.h comme suit :

struct regnode {
    U8  flags;    /* Divers usages, parfois écrasés */
    U8  type;     /* Valeur de l'opcode comme spécifié par regnodes.h */
    U16 next_off; /* Décalage en taille regnode */
};

D'autres structures de type "regnode" plus grandes sont définies dans regcomp.h. Elles sont presque comme des sous-classes en ce sens qu'elles ont les mêmes champs que "regnode", avec éventuellement des champs supplémentaires suivant dans la structure, et dans certains cas, le sens spécifique (et le nom) de certains des champs de base sont écrasés. Voici une description plus complète.

"regnode_1"
"regnode_2"
"regnode_1" les structures ont le même en-tête, suivi d'un seul argument de quatre octets ; "regnode_2" les structures contiennent deux arguments de deux octets à la place : 
regnode_1                U32 arg1;
regnode_2                U16 arg1;  U16 arg2;
"regnode_string"
"regnode_string" les structures, utilisées pour les chaînes littérales, suivent l'en-tête avec une longueur d'un octet, puis les données de la chaîne. Les chaînes sont complétées à la fin avec des octets zéro de sorte que la longueur totale du nœud soit un multiple de quatre octets : 
regnode_string           char string[1];
                         U8 str_len; /* écrase flags */
"regnode_charclass"
Les classes de caractères entre crochets sont représentées par des structures "regnode_charclass", qui ont un argument de quatre octets, puis un bitmap de 32 octets (256 bits) indiquant quels caractères de la plage Latin1 sont inclus dans la classe. 
regnode_charclass        U32 arg1;
                         char bitmap[ANYOF_BITMAP_SIZE];

REGNODE STRUCTURE

Les informations internes pour la compilation des expressions régulières se trouvent dans la structure "regnode". Celle-ci est définie dans regnodes.h et existe sous différentes formes pour s'adapter aux différents types d'opérateurs. La plupart des formes partagent un en-tête commun de 8 octets:

U32 op;      /* Opcode pour ce nœud. */
U32 len;     /* Longueur totale du nœud en octets. */

Le champ op est la clé qui détermine la taille et la signification du reste de la structure. Les informations propres à un opérateur sont stockées après cet en-tête commun. Par exemple, pour un nœud type EXACT, qui correspond à une correspondance littérale de chaîne, la structure est la suivante:

struct regnode_exact {
    U32 op;
    U32 len;
    U32 str_len;  /* La longueur de la chaîne correspondante. */
    char str[1];  /* Le début de la chaîne. */
};

Les attributs moins courants qui ne sont pas connus avant l'exécution, comme les attributs de Perl, sont stockés dans la "structure privée de Perl".

"regnode_charclass_posixl"
Il existe également une forme plus grande de structure de classe de caractères utilisée pour représenter les classes de caractères POSIX sous une correspondance "/l", appelée "regnode_charclass_posixl", qui possède une bitmap supplémentaire de 32 bits indiquant quelles classes de caractères POSIX ont été incluses. 
regnode_charclass_posixl U32 arg1;
                         char bitmap[ANYOF_BITMAP_SIZE];
                         U32 classflags;

regnodes.h définit un tableau appelé "PL_regnode_arg_len[]" qui donne la taille de chaque opcode en unités de "size regnode" (4 octets). Une macro est utilisée pour calculer la taille d'un nœud "EXACT" en fonction de son champ "str_len".

Les opcodes réguliers (regops) sont définis dans regnodes.h, qui est généré à partir de regcomp.sym par regcomp.pl. Actuellement, le nombre maximal possible d'opcodes réguliers distincts est limité à 256, dont environ un quart est déjà utilisé.

Un ensemble de macros facilite et rend plus cohérent l'accès aux champs. Il s'agit notamment de OP(), qui est utilisée pour déterminer le type d'une structure semblable à "regnode" ; NEXT_OFF(), qui est le décalage vers le nœud suivant (plus d'informations à ce sujet plus tard) ; ARG(), ARG1(), ARG2(), ARG_SET() et leurs équivalents pour lire et définir les arguments ; ainsi que STR_LEN(), STRING() et OPERAND() pour manipuler les chaînes et les types portant des opcodes réguliers.

Quel regnode est le prochain ?

Il existe deux concepts distincts de "prochain regnode" dans le moteur d'expressions régulières, et il est important de les distinguer dans votre réflexion car ils se chevauchent conceptuellement dans de nombreux endroits, mais là où ils ne se chevauchent pas, la différence est critique. Pour la majorité des types de regnodes, les deux concepts sont (presque) identiques en pratique. Les deux types sont "REGNODE_AFTER", qui est fortement utilisé pendant la compilation mais seulement occasionnellement pendant l'exécution, et "regnext", qui est fortement utilisé pendant l'exécution et seulement occasionnellement pendant la compilation.

"REGNODE_AFTER"
C'est le "regnode suivant positionnellement" dans le programme d'expression régulière compilé. Pour les types de regnodes plus petits, il s'agit de "regnode_ptr+1" en interne, mais comme les tailles des regnodes varient et peuvent changer avec le temps, nous proposons des macros qui masquent les détails complexes.

Il est fortement utilisé dans la phase de compilation mais n'est utilisé que par quelques types de regnodes sélectionnés dans la phase d'exécution. Il est également fortement utilisé dans le code pour afficher le programme d'expression régulière à des fins de débogage.

Il existe une sélection de macros qui peuvent être utilisées pour calculer cela aussi efficacement que possible en fonction des circonstances. La macro canonique est REGNODE_AFTER(), qui est la plus puissante et devrait gérer tous les cas que nous avons, mais est aussi potentiellement la plus lente. Il existe deux macros supplémentaires pour le cas spécial où vous SAVEZ que la taille actuelle du regnode est constante, et que vous connaissez son type ou son opcode. Dans ce cas, vous pouvez utiliser REGNODE_AFTER_opcode() ou REGNODE_AFTER_type().

Dans les anciennes versions du moteur d'expressions régulières, REGNODE_AFTER() s'appelait "NEXTOPER", mais cela s'est avéré confus et il a été renommé. Il existe également un REGNODE_BEFORE(), mais il est dangereux et ne doit pas être utilisé dans du nouveau code.

"regnext"
C'est le regnode auquel on peut accéder en sautant en avant de la valeur du membre NEXT_OFF() du regnode, ou dans quelques cas pour des sauts plus longs par le champ "arg1" de la structure "regnode_1". La sous-routine regnext() gère cela de manière transparente. Dans la majorité des cas, le "regnext" pour un regnode est le regnode qui devrait être exécuté après que le courant ait réussi à correspondre, mais dans certains cas, cela peut ne pas être vrai. Dans les types de regnodes de contrôle de boucle et de contrôle de branche, le regnext peut signifier quelque chose de spécial. Pour les nœuds BRANCH, le "regnext" est la prochaine branche qui doit être exécutée si la branche actuelle échoue à l'exécution, et certains regnodes de contrôle de boucle définissent le regnext pour être la fin de la boucle afin qu'ils puissent sauter à leur nettoyage si l'itération actuelle ne parvient pas à correspondre.

La plupart des types de regnodes ne créent pas de branche dans le flux d'exécution, et en mettant de côté les optimisations, les deux concepts de "suivant" sont les mêmes. Par exemple, le "regnext" et le "REGNODE_AFTER" d'un opcode SBOL sont les mêmes pendant la phase de compilation. Le principal endroit où ce n'est pas le cas est pour les regnodes "BRANCH" où le "REGNODE_AFTER" représente le début du motif dans la branche et le "regnext" représente la liaison vers la prochaine branche si celle-ci échoue à correspondre, ou 0 s'il s'agit de la dernière branche. La logique de boucle pour les quantificateurs utilise également de manière similaire la distinction entre les deux types, "REGNODE_AFTER" étant l'intérieur de la construction de boucle, et le "regnext" pointant à la fin de la boucle.

Pendant la compilation, le moteur peut ne pas connaître le regnext pour un nœud donné. Ainsi, pendant la compilation, "regnext" n'est utilisé que là où il doit l'être et où il est connu pour être correct. À la toute fin de la phase de compilation, nous parcourons le programme d'expression régulière et corrigeons les données regnext de manière appropriée, et effectuons également diverses optimisations qui peuvent entraîner la redondance de regnodes requis pendant la construction, ou nous pouvons remplacer un grand regnode par un beaucoup plus petit et combler l'écart avec des regnodes OPTIMISÉS. Ainsi, nous pourrions commencer par quelque chose comme ceci:

BRANCH
  EXACT "foo"
BRANCH
  EXACT "bar"
EXACT "!"

et le remplacer par quelque chose comme:

TRIE foo|bar
OPTIMIZED
OPTIMIZED
OPTIMIZED
EXACT "!"

le "REGNODE_AFTER" pour le nœud "TRIE" serait un nœud "OPTIMIZED", et en théorie le "regnext" serait le même que le "REGNODE_AFTER". Mais il serait inefficace d'exécuter le nœud OPTIMIZED comme un no-op trois fois, donc l'optimiseur corrige le "regnext" afin que de tels nœuds soient ignorés pendant la phase d'exécution.

Pendant les phases d'exécution, nous utilisons le regnext() presque exclusivement, et n'utilisons le "REGNODE_AFTER" que dans des cas spéciaux où il a une signification bien définie pour un type de regnode donné. Par exemple, /x+/ donne

PLUS
    EXACT "x"
END

le "regnext" du nœud "PLUS" est le nœud "END", et le "REGNODE_AFTER" du nœud "PLUS" est le nœud "EXACT". Le "regnext" et le "REGNODE_AFTER" du nœud "EXACT" sont le nœud "END".

Vue d'ensemble du processus

De manière générale, la correspondance d'une chaîne avec un motif implique les étapes suivantes :

A. Compilation
1. Analyse (Parsing)
2. Optimisation par balayage et analyse
B. Exécution
3. Optimisations de position de départ et de non-correspondance
4. Exécution du programme

L'endroit où ces étapes se produisent dans l'exécution réelle d'un programme Perl est déterminé par le fait que le motif implique ou non l'interpolation de variables de chaîne. Si une interpolation se produit, la compilation a lieu au moment de l'exécution. Si ce n'est pas le cas, la compilation est effectuée au moment de la compilation. (Le modificateur "/o" modifie cela, tout comme "qr//" dans une certaine mesure.) Le moteur ne s'en soucie pas vraiment.

Compilation

Ce code réside principalement dans regcomp.c, ainsi que dans les fichiers d'en-tête regcomp.h, regexp.h et regnodes.h.

La compilation commence par pregcomp(), qui est principalement un wrapper d'initialisation qui délègue le travail à deux autres routines pour la tâche principale : la première est reg(), qui est le point de départ de l'analyse ; la seconde, study_chunk(), est responsable de l'optimisation.

L'initialisation dans pregcomp() implique principalement la création et le remplissage de données d'une structure spéciale, "RExC_state_t" (définie dans regcomp.c). Presque toutes les routines utilisées en interne dans regcomp.h prennent un pointeur vers l'une de ces structures comme premier argument, avec le nom "pRExC_state". Cette structure est utilisée pour stocker l'état de compilation et contient de nombreux champs. De même, il existe de nombreuses macros qui opèrent sur cette variable : tout ce qui ressemble à "RExC_xxxx" est une macro qui opère sur ce pointeur/structure.

reg() est le début du processus d'analyse. Elle est responsable de l'analyse d'un morceau arbitraire de motif jusqu'à la fin de la chaîne, ou de la première parenthèse fermante qu'elle rencontre dans le motif. Cela signifie qu'elle peut être utilisée pour analyser l'expression régulière de niveau supérieur, ou toute section à l'intérieur d'une parenthèse de groupement. Elle gère également les "parenthèses spéciales" des expressions régulières de Perl. Par exemple, lors de l'analyse de "/x(?:foo)y/", reg() sera appelée à un moment donné pour analyser à partir de

le symbole "?" jusqu'à et y compris le ")".

De plus, reg() est responsable de l'analyse des une ou plusieurs branches du motif, et de leur « finalisation » en réglant correctement leurs pointeurs suivants. Pour effectuer l'analyse, elle appelle répétitivement regbranch(), qui est responsable de la gestion jusqu'au premier symbole "|" qu'elle rencontre.

regbranch() appelle à son tour regpiece(), qui gère les « choses » suivies d'un quantificateur. Pour analyser les « choses », regatom() est appelée. C'est la routine de plus bas niveau, qui analyse les chaînes constantes, les classes de caractères et les divers symboles spéciaux comme "$ ». Si regatom() rencontre un caractère « ( », elle appelle à son tour reg().

Il y avait autrefois deux passes principales impliquées dans l'analyse, la première pour calculer la taille du programme compilé, et la seconde pour le compiler réellement. Mais il n'y a plus qu'une seule passe principale, avec une estimation initiale grossière basée sur la longueur du motif d'entrée, qui est augmentée si nécessaire au fur et à mesure de l'analyse, et ensuite, réduite à la quantité réellement utilisée.

Cependant, il peut arriver que l'analyse doive être redémarrée au début lorsque diverses circonstances se produisent en cours de route. Un exemple est si le programme s'avère si volumineux que des sauts y sont présents et ne rentrent pas dans les 16 bits normaux disponibles. Il existe deux regops spéciaux qui peuvent contenir des destinations de saut plus grandes, BRANCHJ et LONGBRANCH. L'analyse est redémarrée, et ceux-ci sont utilisés à la place des plus courts normaux. Chaque fois qu'un redémarrage de l'analyse est requis, la fonction renvoie un échec et définit un indicateur quant à ce qui doit être fait. Ceci est transmis à la routine de niveau supérieur qui prend l'action appropriée et redémarre à partir de zéro. Dans le cas où des sauts plus longs sont nécessaires, le drapeau "RExC_use_BRANCHJ" est défini dans la structure "RExC_state_t", que les fonctions connaissent et inspectent avant de décider comment effectuer les sauts.

Dans la plupart des cas, la fonction qui découvre le problème définit l'indicateur causal et renvoie immédiatement un échec. « Complications d'analyse » contient un exemple explicite de la manière dont cela fonctionne. Dans d'autres cas, comme une référence avant à un regroupement parenthésé numéroté, nous devons terminer l'analyse pour savoir si ce regroupement numéroté apparaît réellement dans le motif. Dans ces cas, l'analyse est simplement refaite à la fin, en sachant combien de regroupements y apparaissent.

La routine regtail() est appelée par reg() et regbranch() afin de « définir le pointeur de queue » correctement. Lors de l'exécution, lorsque nous arrivons à la fin d'une branche, nous devons aller au nœud suivant les parenthèses de regroupement. Cependant, lors de l'analyse, nous ne savons pas où sera la fin tant que nous n'y sommes pas arrivés, donc lorsque nous y arrivons, nous devons revenir en arrière et mettre à jour les décalages comme il convient. "regtail" est utilisé pour faciliter cela.

Une subtilité du processus d'analyse signifie qu'un regex comme "/foo/" est initialement analysé en une alternance avec une seule branche. Ce n'est qu'après que l'optimiseur convertit les alternances à branche unique en une forme plus simple.

Graphe d'appel d'analyse et une grammaire

Le graphe d'appel ressemble à ceci :

reg()                        # analyse un regex de niveau supérieur, ou à l'intérieur de
                             # parenthèses
    regbranch()              # analyse une seule branche d'une alternance
        regpiece()           # analyse un motif suivi d'un quantificateur
            regatom()        # analyse un motif simple
                regclass()   #   utilisé pour gérer une classe
                reg()        #   utilisé pour gérer un sous-motif parenthésé
                ....
        ...
        regtail()            # finalise la branche
    ...
    regtail()                # finalise la séquence de branches. Attache la queue de chaque
                             # branche à la queue de la séquence
                             # (NOUVEAU) En mode Debug, il s'agit de
                             # regtail_study().

Une forme de grammaire pourrait ressembler à ceci :

atom  : constant | class
quant : '*' | '+' | '?' | '{min,max}'
_branch: piece
       | piece _branch
       | rien
branch: _branch
      | _branch '|' branch
group : '(' branch ')'
_piece: atom | group
piece : _piece
      | _piece quant

Complications d'analyse

L'implication de la description ci-dessus est qu'un motif contenant des parenthèses imbriquées entraînera un graphe d'appel qui cyclera à travers reg(), regbranch(), regpiece(), regatom(), reg(), regbranch() etc plusieurs fois, jusqu'à ce que le niveau d'imbrication le plus profond soit atteint. Toutes les routines ci-dessus renvoient un pointeur vers un "regnode", qui est généralement le dernier regnode ajouté au programme. Cependant, une complication est que reg() renvoie NULL pour l'analyse de la syntaxe "(?:)" pour les modificateurs intégrés, définissant l'indicateur "TRYAGAIN". "TRYAGAIN" se propage vers le haut jusqu'à ce qu'il soit capturé, dans certains cas par regatom(), mais sinon inconditionnellement par regbranch(). Par conséquent, il ne sera jamais renvoyé par regbranch() à reg(). Cet indicateur permet de détecter des motifs tels que "(?i)+" comme des erreurs (Le quantificateur suit rien dans le regex; marqué par <-- ICI dans m/(?i)+ <-- ICI /).

Une autre complication est que la représentation utilisée pour le programme diffère s'il doit stocker de l'Unicode, mais il n'est pas toujours possible de savoir avec certitude s'il le fait avant la moitié de l'analyse. La représentation Unicode du programme est plus volumineuse et ne peut pas être assortie aussi efficacement. (Voir « Support Unicode et localisation » ci-dessous pour plus de détails sur les raisons.) Si le motif contient de l'Unicode littéral, il est évident que le programme doit stocker de l'Unicode. Sinon, l'analyseur suppose avec optimisme que la représentation plus efficace peut être utilisée, et commence à dimensionner sur cette base. Cependant, s'il rencontre ensuite quelque chose dans le motif qui doit être stocké en tant qu'Unicode, comme une séquence d'échappement "\x{...}" représentant un littéral de caractère, cela signifie que toutes les tailles calculées précédemment doivent être refaites, en utilisant des valeurs appropriées pour la représentation Unicode. C'est une autre instance où l'analyse doit être redémarrée, et cela peut être fait immédiatement. La fonction renvoie un échec et définit l'indicateur "RESTART_UTF8" (encapsulé par l'utilisation de la macro "REQUIRE_UTF8"). Cette demande de redémarrage est propagée dans la chaîne d'appel de manière similaire, jusqu'à ce qu'elle soit « capturée » dans Perl_re_op_compile(), qui marque le motif comme contenant de l'Unicode et redémarre la passe de dimensionnement. Il est également possible que des constructions à l'intérieur de blocs de code d'exécution nécessitent une représentation Unicode, ce qui est signalé par le retour de S_compile_runtime_code() à Perl_re_op_compile() (retournant faux).

Le redémarrage était précédemment implémenté à l'aide d'un "longjmp" dans regatom() vers un "setjmp" dans Perl_re_op_compile(), mais cela s'est avéré problématique car cette dernière est une grande fonction contenant de nombreuses variables automatiques, qui interagissent mal avec le flux de contrôle émergent de "setjmp".

Optimisation et analyse par analyse visuelle (Peep-hole Optimisation and Analysis)

Le moteur d'expressions régulières peut être un outil lourd à manier. Sur de longues chaînes et des motifs complexes, il peut finir par avoir à faire beaucoup de travail pour trouver une correspondance, et encore plus pour décider qu'aucune correspondance n'est possible. Considérons une situation comme le motif suivant.

'ababababababababababab' =~ /(a|b)*z/

La partie "(a|b)*" peut correspondre à chaque caractère de la chaîne, puis échouer à chaque fois car il n'y a pas de "z" dans la chaîne. Il est donc évident que nous pouvons éviter d'utiliser le moteur regex sauf s'il y a un "z" dans la chaîne. De même dans un motif comme :

/foo(\w+)bar/

Dans ce cas, nous savons que la chaîne doit contenir un "foo" qui doit être suivi de "bar". Nous pouvons utiliser la correspondance Fast Boyer-Moore telle qu'implémentée dans fbm_instr() pour trouver l'emplacement de ces chaînes. Si elles n'existent pas, nous n'avons pas besoin de recourir au moteur regex, beaucoup plus coûteux. Mieux encore, si elles existent, nous pouvons utiliser leurs positions pour réduire l'espace de recherche que le moteur regex doit couvrir pour déterminer si le motif entier correspond.

Il existe divers aspects du motif qui peuvent être utilisés pour faciliter des optimisations dans ce sens :

  • chaînes fixes ancrées
  • chaînes fixes flottantes
  • exigences de longueur minimale et maximale
  • classe de départ
  • positions de début/fin de ligne

Une autre forme d'optimisation qui peut se produire est l'optimisation post-analyse "visuelle" (post-parse "peep-hole" optimisation), où des constructions inefficaces sont remplacées par des constructions plus efficaces. Les opérateurs réguliers "TAIL" utilisés pendant l'analyse pour marquer la fin des branches et la fin des groupes en sont des exemples. Ces opérateurs réguliers sont utilisés comme espaces réservés pendant la construction et "correspondent toujours", ils peuvent donc être "optimisés" en faisant pointer les éléments qui pointent vers le "TAIL" vers l'élément vers lequel le "TAIL" pointe, "sautant" ainsi le nœud.

Une autre optimisation qui peut se produire est la fusion d'"EXACT", où deux nœuds "EXACT" consécutifs sont fusionnés en un seul opérateur régulier. Une forme encore plus agressive de ceci est qu'une séquence de branche de la forme "EXACT BRANCH ... EXACT" peut être convertie en un opérateur régulier "TRIE-EXACT".

Tout cela se produit dans la routine study_chunk() qui utilise une structure spéciale "scan_data_t" pour stocker l'analyse qu'elle a effectuée, et effectue les optimisations "visuelles" au fur et à mesure.

Le code impliqué dans study_chunk() est extrêmement cryptique. Attention. :-)

Exécution

L'exécution d'une regex implique généralement deux phases, la première étant de trouver le point de départ dans la chaîne à partir duquel effectuer la correspondance, et la seconde étant d'exécuter l'interpréteur de regop.

Si nous pouvons déterminer qu'il n'y a pas de point de départ valide, nous n'exécutons pas l'interpréteur du tout. De même, si nous savons d'après la phase d'analyse que nous ne pouvons pas détecter de raccourci vers la position de départ, nous allons directement à l'interpréteur.

Les deux points d'entrée sont re_intuit_start() et pregexec(). Ces routines ont une relation quelque peu incestueuse avec un chevauchement de leurs fonctions, et pregexec() peut même appeler re_intuit_start() par elle-même. Néanmoins, d'autres parties du code perl peuvent faire appel à l'une ou à l'autre, ou aux deux.

L'exécution de l'interpréteur lui-même était autrefois récursive, mais grâce aux efforts de Dave Mitchell lors de la piste de développement 5.9.x, cela a changé : une pile interne est maintenant maintenue sur le tas et la routine est entièrement itérative. Cela peut être délicat car le code est assez conservateur quant à l'état qu'il stocke, avec pour résultat que deux lignes consécutives dans le code peuvent en réalité s'exécuter dans des contextes totalement différents en raison de la récursion simulée.

Position de départ et optimisations de non-correspondance

re_intuit_start() est responsable de la gestion des points de départ et des optimisations de non-correspondance telles que déterminées par les résultats de l'analyse effectuée par study_chunk() (et décrites dans "Optimisation et analyse par analyse visuelle").

La structure de base de cette routine consiste à essayer de trouver les points de départ et/ou de fin où le motif pourrait correspondre, et à s'assurer que la chaîne est suffisamment longue pour correspondre au motif. Elle essaie d'utiliser des méthodes plus efficaces sur des méthodes moins efficaces et peut impliquer une vérification croisée considérable des contraintes pour trouver l'endroit dans la chaîne qui correspond. Par exemple, elle peut essayer de déterminer qu'une chaîne fixe donnée doit non seulement être présente, mais se trouver à un certain nombre de caractères de la fin de la chaîne, ou autre.

Elle appelle plusieurs autres routines, telles que fbm_instr() qui effectue la correspondance Fast Boyer Moore et find_byclass() qui est responsable de la recherche du départ à l'aide du premier regop obligatoire dans le programme.

Lorsque les critères d'optimisation ont été satisfaits, reg_try() est appelée pour effectuer la correspondance.

Exécution du programme

pregexec() est le point d'entrée principal pour l'exécution d'une regex. Il contient le support pour l'initialisation de l'état de l'interpréteur regex, l'exécution de re_intuit_start() si nécessaire, et l'exécution de l'interpréteur sur la chaîne à partir de diverses positions de départ selon les besoins. Lorsqu'il est nécessaire d'utiliser l'interpréteur regex, pregexec() appelle regtry().

regtry() est le point d'entrée dans l'interpréteur regex. Il attend en arguments un pointeur vers une structure "regmatch_info" et un pointeur vers une chaîne. Il renvoie un entier 1 pour succès et un 0 pour échec

re. C'est essentiellement un wrapper de configuration autour de regmatch().

"regmatch" est la boucle récursive principale " du interpréteur. C'est essentiellement un grand switch qui implémente une machine à états, où les états possibles sont les regops eux-mêmes, plus un certain nombre d'états intermédiaires et d'échec supplémentaires. Quelques-uns des états sont implémentés sous forme de sous-routines, mais la majeure partie est du code inline.

DIVERS

Support Unicode et Localisation

Lorsqu'il s'agit de chaînes contenant des caractères qui ne peuvent pas être représentés à l'aide d'un jeu de caractères à huit bits, perl utilise une représentation interne qui est une version permissive de l'encodage UTF-8 de Unicode[2]. Elle utilise des octets uniques pour représenter les caractères de l'ensemble de caractères ASCII, et des séquences de deux octets ou plus pour tous les autres caractères. (Voir perlunitut pour plus d'informations sur la relation entre UTF-8 et l'encodage de perl, utf8. La différence n'est pas importante pour cette discussion.)

Quelle que soit la façon dont on la considère, le support Unicode sera une douleur dans un moteur d'expressions régulières. Les astuces qui peuvent convenir quand on a 256 caractères possibles ne s'étendent souvent pas pour gérer la taille de l'ensemble de caractères UTF-8. Les choses que l'on peut tenir pour acquises avec ASCII peuvent ne pas être vraies avec Unicode. Par exemple, en ASCII, il est sûr de supposer que "sizeof(char1) == sizeof(char2)", mais en UTF-8 ce n'est pas le cas. Le pliage des majuscules Unicode est beaucoup plus complexe que les règles simples de l'ASCII, et même lorsqu'on n'utilise pas Unicode mais seulement des encodages à un octet localisés, les choses peuvent devenir délicates (par exemple, LETTRE MINUSCULE ESPAGNOL SHARP S (U+00DF, ß;) devrait correspondre à 'SS' dans la correspondance insensible à la casse localisée).

Ce qui aggrave les choses, c'est que le support UTF-8 a été un ajout ultérieur au moteur d'expressions régulières (comme il l'a été pour perl) et cela a nécessairement rendu les choses beaucoup plus compliquées. Il est évidemment plus facile de concevoir un moteur d'expressions régulières en tenant compte de l'Unicode dès le départ que de l'adapter à un moteur qui ne l'a pas été.

Presque tous les regops qui impliquent de regarder la chaîne d'entrée ont deux cas, un pour UTF-8, et un pour non-UTF-8. En fait, c'est souvent plus complexe que cela, car le motif peut aussi être en UTF-8.

Il faut prendre soin lors des modifications pour s'assurer que l'on gère correctement UTF-8, à la fois au moment de la compilation et au moment de l'exécution, y compris lorsque la chaîne et le motif sont différents.

Structures de Base

La structure "regexp" décrite dans perlreapi est commune à tous les moteurs d'expressions régulières. Deux de ses champs sont destinés à l'usage privé du moteur d'expressions régulières qui a compilé le motif. Ce sont les membres "intflags" et pprivate. Le "pprivate" est un pointeur void vers une structure arbitraire dont l'utilisation et la gestion sont la responsabilité du moteur de compilation. perl ne modifiera jamais aucune de ces valeurs. Dans le cas du moteur par défaut, la structure pointée par "pprivate" s'appelle "regexp_internal".

Ses champs "pprivate" et "intflags" contiennent des données spécifiques à chaque moteur.

Il existe deux structures utilisées pour stocker une expression régulière compilée. L'une, la structure "regexp" décrite dans perlreapi, est remplie par le moteur actuellement utilisé et certains de ses champs sont lus par perl pour implémenter des choses telles que la conversion en chaîne de "qr//".

L'autre structure est pointée par le "pprivate" de la structure "regexp" et est, en plus de "intflags" dans la même structure, considérée comme la propriété du moteur d'expressions régulières qui a compilé l'expression régulière.

La structure regexp contient toutes les données dont perl a besoin pour travailler correctement avec l'expression régulière. Elle inclut des données sur les optimisations que perl peut utiliser pour déterminer si le moteur d'expressions régulières doit réellement être utilisé, et diverses autres informations de contrôle nécessaires pour exécuter correctement les motifs dans différents contextes, comme si le motif est ancré d'une manière ou d'une autre, ou quels indicateurs ont été utilisés lors de la compilation, ou si le programme contient des constructions spéciales dont perl doit être conscient.

De plus, elle contient deux champs destinés à l'usage privé du moteur d'expressions régulières qui a compilé le motif. Ce sont les membres "intflags" et pprivate. Le "pprivate" est un pointeur void vers une structure arbitraire dont l'utilisation et la gestion sont la responsabilité du moteur de compilation. perl ne modifiera jamais aucune de ces valeurs.

Comme mentionné précédemment, dans le cas des moteurs par défaut, le "pprivate" sera un pointeur vers une structure regexp_internal qui contient le programme compilé et toute donnée supplémentaire qui est privée à l'implémentation du moteur d'expressions régulières.

Structure "pprivate" de Perl

La structure suivante est utilisée comme structure "pprivate" par le moteur d'expressions régulières de perl. Puisqu'elle est spécifique à perl, elle n'a qu'une valeur curieuse pour les autres implémentations de moteurs.

typedef struct regexp_internal {
    regnode *regstclass;
    struct reg_data *data;
    struct reg_code_blocks *code_blocks;
    U32 proglen;
    U32 name_list_idx;
    regnode program[1];
} regexp_internal;

La description des attributs est la suivante :

"regstclass"
Regop spécial utilisé par re_intuit_start() pour vérifier si un motif peut correspondre à une certaine position. Par exemple, si le moteur d'expressions régulières sait que le motif doit commencer par un 'Z', il peut alors parcourir la chaîne jusqu'à ce qu'il en trouve un et lancer le moteur d'expressions régulières à partir de là. La routine qui gère cela s'appelle find_by_class(). Parfois, ce champ pointe vers un regop intégré au programme, et parfois il pointe vers un regop synthétique indépendant qui a été construit par l'optimiseur.
"data"
Ce champ pointe vers une structure "reg_data", qui est définie comme suit : 
struct reg_data {
    U32 count;
    U8 *what;
    void* data[1];
};

Cette structure est utilisée pour gérer les structures de données que le moteur d'expressions régulières doit gérer spécialement lors d'une opération de clonage ou de libération sur le produit compilé. Chaque élément du tableau de données a un élément correspondant dans le tableau 'what'. Lors de la compilation, les regops qui nécessitent des structures spéciales stockées ajouteront un élément à chaque tableau en utilisant la routine add_data(), puis stockeront l'indice dans le regop.

Dans les versions modernes de perl, le 0ème élément de cette structure est réservé et N'EST JAMAIS utilisé pour stocker quoi que ce soit d'utile. Ceci est pour permettre aux choses qui doivent indexer dans ce tableau de représenter "aucune valeur".

"code_blocks"
Cette structure optionnelle est utilisée pour gérer les constructions "(?{})" dans le motif. Elle est composée des structures suivantes : 
/* record the position of a (?{...}) within a pattern */
struct reg_code_block {
    STRLEN start;
    STRLEN end;
    OP     *block;
    REGEXP *src_regex;
};
/* array of reg_code_block's plus header info */
struct reg_code_blocks {
    int refcnt; /* we may be pointed to from a regex
                   and from the savestack */
    int  count; /* how many code blocks */
    struct reg_code_block *cb; /* array of reg_code_block's */
};
"proglen"
Stocke la longueur du programme compilé en unités de regops.
"name_list_idx"
C'est l'indice dans le tableau de données où est stocké un AV contenant les noms de tous les tampons de capture nommés dans le motif, s'il y en a. Ceci n'est utilisé que dans la version de débogage du moteur d'expressions régulières et lorsque RXp_PAREN_NAMES(prog) est vrai. Il sera 0 s'il n'y a pas de telles données.
"program"
Programme compilé. Intégré à la structure afin que toute la structure puisse être traitée comme un seul bloc.
