NOM

perlbug - comment soumettre des rapports de bugs sur Perl

SYNOPSIS

perlbug

perlbug [ -v ] [ -a adresse ] [ -s sujet ] [ -b corps | -f fichier_entree ] [ -F fichier_sortie ] [ -r adresse_retour ] [ -e editeur ] [ -c adresse_admin | -C ] [ -S ] [ -t ] [ -d ] [ -h ] [ -T ]

perlbug [ -v ] [ -r adresse_retour ]
[ -ok | -okay | -nok | -nokay ]

perlthanks

DESCRIPTION

Ce programme est conçu pour vous aider à générer des rapports de bugs (et des notes de remerciement) concernant perl5 et les modules qui l'accompagnent.

Dans la plupart des cas, vous pouvez simplement l'exécuter interactivement depuis une ligne de commande sans arguments spéciaux et suivre les invites.

Si vous avez trouvé un bug dans un port non standard (qui ne faisait pas partie de la distribution standard), une distribution binaire, ou un module non central (tel que Tk, DBI, etc.), veuillez consulter la documentation fournie avec cette distribution pour déterminer où signaler correctement les bugs.

Les rapports de bugs doivent être soumis au traqueur de problèmes GitHub à l'adresse https://github.com/Perl/perl5/issues. L'adresse perlbug@perl.org n'ouvre plus automatiquement de tickets. Vous pouvez utiliser cet outil pour composer votre rapport et l'enregistrer dans un fichier que vous pourrez ensuite soumettre au traqueur de problèmes.

Dans des cas extrêmes, perlbug peut ne pas fonctionner suffisamment bien sur votre système pour vous guider dans la composition d'un rapport de bug. Dans ce cas, vous pouvez utiliser perlbug -d ou perl -V pour obtenir des informations de configuration système à inclure dans votre rapport de problème.

Lors du signalement d'un bug, veuillez suivre cette liste de contrôle :

Quelle version de Perl utilisez-vous ?
Tapez "perl -v" à la ligne de commande pour le savoir.
Utilisez-vous la dernière version publiée de Perl ?
Consultez http://www.perl.org/ pour le savoir. Si vous n'utilisez pas la dernière version publiée, veuillez essayer de reproduire votre bug sur la dernière version stable.

Notez que les rapports concernant des bugs dans d'anciennes versions de Perl, en particulier ceux qui indiquent que vous n'avez pas également testé la version stable actuelle de Perl, recevront probablement moins d'attention de la part des bénévoles qui construisent et maintiennent Perl que les rapports concernant des bugs dans la version actuelle.

Êtes-vous sûr de ce que vous avez est un bug ?
Un nombre significatif de rapports de bugs que nous recevons s'avèrent être des fonctionnalités documentées de Perl. Assurez-vous que le problème que vous rencontrez n'est pas intentionnel en parcourant la documentation fournie avec la distribution Perl.

Compte tenu du volume de documentation Perl, ce n'est pas une tâche triviale, mais si vous pouvez indiquer une documentation qui suggère que le comportement que vous observez est incorrect, votre problème recevra probablement plus d'attention. Vous voudrez peut-être commencer par perldoc perltrap pour obtenir des pointeurs vers les pièges courants dans lesquels tombent les programmeurs Perl (nouveaux et expérimentés).

Si vous n'êtes pas sûr de la signification d'un message d'erreur que vous avez rencontré, perldoc perldiag pour une explication. Si le message n'est pas dans perldiag, il n'est probablement pas généré par Perl. Vous pourriez avoir de la chance en consultant la documentation de votre système d'exploitation à la place.

Si vous êtes sur une plateforme non-UNIX, consultez perldoc perlport, car certaines fonctionnalités peuvent ne pas être implémentées ou fonctionner différemment.

Vous pourrez peut-être déterminer ce qui ne va pas en utilisant le débogueur Perl. Pour plus d'informations sur l'utilisation du débogueur, consultez perldoc perldebug.

Avez-vous un cas de test approprié ?
Plus il est facile de reproduire votre bug, plus il est probable qu'il sera corrigé -- si personne ne peut reproduire votre problème, il ne sera probablement pas traité.

Un bon cas de test possède la plupart de ces attributs : un code court et simple ; peu de dépendances vis-à-vis de commandes externes, de modules ou de bibliothèques ; pas de code dépendant de la plateforme (sauf s'il s'agit d'un bug spécifique à une plateforme) ; une documentation claire et simple.

Un bon cas de test est presque toujours un bon candidat pour être inclus dans la suite de tests de Perl. Si vous avez le temps, envisagez de rédiger votre cas de test de manière à ce qu'il puisse être facilement inclus dans la suite de tests standard.

Avez-vous inclus toutes les informations pertinentes ?
Assurez-vous d'inclure les messages d'erreur **exacts**, le cas échéant. "Perl a donné une erreur" n'est pas un message d'erreur exact.

Si vous obtenez un vidage mémoire (ou équivalent), vous pouvez utiliser un débogueur (dbx, gdb, etc.) pour produire une trace de pile à inclure dans le rapport de bug.

NOTE : à moins que votre Perl n'ait été compilé avec des informations de débogage (souvent -g), la trace de pile sera probablement un peu difficile à utiliser car elle ne contiendra très probablement que les noms des fonctions et non leurs arguments. Si possible, recompilez votre Perl avec les informations de débogage et reproduisez le crash et la trace de pile.

Pouvez-vous décrire le bug en langage clair ?
Plus un bug reproductible est facile à comprendre, plus il est probable qu'il soit corrigé. Toute perspicacité que vous pouvez fournir sur le problème aidera grandement. En d'autres termes, essayez d'analyser le problème (dans la mesure de vos capacités) et rapportez vos découvertes.
Pouvez-vous corriger le bug vous-même ?
Si oui, c'est une excellente nouvelle ; les rapports de bugs avec des patchs recevront probablement beaucoup plus d'attention et d'intérêt que ceux sans patchs. Veuillez soumettre votre patch via le workflow de Pull Request de GitHub tel que décrit dans perldoc perlhack. Vous pouvez également envoyer des patchs à perl5-porters@perl.org. Lors de l'envoi d'un patch, créez-le en utilisant "git format-patch" si possible, bien qu'un diff unifié créé avec "diff -pu" fera presque aussi bien.

Votre patch pourra être renvoyé avec des demandes de modifications, ou des demandes d'explications plus détaillées sur votre correction.

Voici quelques conseils pour créer des patchs de haute qualité :

Assurez-vous que le patch n'est pas inversé (le premier argument de diff est généralement le fichier d'origine, le second argument votre fichier modifié). Assurez-vous de tester votre patch en l'appliquant avec "git am" ou le programme "patch" avant de l'envoyer. Essayez de suivre le même style que le code que vous essayez de patcher. Assurez-vous que votre patch fonctionne réellement ("make test", si la chose que vous patcher est couverte par la suite de tests de Perl).

Pouvez-vous utiliser "perlbug" pour soumettre une note de remerciement ?
Oui, vous pouvez le faire soit en utilisant l'option "-T", soit en appelant le programme sous le nom de "perlthanks". Les notes de remerciement sont bien. Elles font sourire.

Veuillez rendre le titre de votre problème informatif. "un bug" n'est pas informatif. Ni "perl plante" ni "AIDE !!!". Ceux-ci n'aident pas. Une description concise de ce qui ne va pas est acceptable.

Après avoir fait votre part, soyez prêt à attendre, à entendre dire que le bug est dans votre code, ou éventuellement à ne recevoir aucune réponse. Les bénévoles qui maintiennent Perl sont des gens occupés, donc si votre problème est un bug évident dans votre propre code, difficile à comprendre ou est un doublon d'un rapport existant, vous pourriez ne pas recevoir de réponse personnelle.

S'il est important pour vous que votre bug soit corrigé, surveillez le traqueur de problèmes (vous serez abonné aux notifications pour les problèmes que vous soumettez ou sur lesquels vous commentez) et les journaux de commits des versions de développement de Perl, et encouragez les mainteneurs avec des mots gentils ou des offres de boissons fraîches. OPTIONS

-a
Adresse à laquelle envoyer le rapport au lieu de le sauvegarder dans un fichier.
-b
Corps du rapport. S'il n'est pas inclus sur la ligne de commande, ou dans un fichier avec -f, vous aurez la possibilité de modifier le rapport.
-C
N'envoyer pas de copie à l'administrateur lors de l'envoi du rapport par courrier.
-c
Adresse à laquelle envoyer une copie du rapport lors de l'envoi du rapport par courrier. Par défaut, il s'agit de l'adresse de l'administrateur local de perl (enregistrée lors de la compilation de perl).
-d
Mode données (par défaut si vous redirigez ou transmettez une sortie). Ceci affiche vos données de configuration, sans sauvegarder ni envoyer de courrier. Vous pouvez utiliser cela avec -v pour obtenir des données plus complètes.
-e
Éditeur à utiliser.
-f
Fichier contenant le corps du rapport. Utilisez ceci pour envoyer rapidement un rapport préparé.
-F
Fichier dans lequel les résultats seront écrits. Par défaut, c'est perlbug.rep.
-h
Affiche un bref résumé des options.
-ok
Rapporter une compilation réussie sur ce système aux mainteneurs de Perl. Force -S et -C. Force et fournit les valeurs pour -s et -b. Ne demande une adresse de retour que si elle ne peut pas la deviner (pour une utilisation avec make). Respecte l'adresse de retour spécifiée avec -r. Vous pouvez utiliser ceci avec -v pour obtenir des données plus complètes. Ne crée un rapport que si ce système a moins de 60 jours.
-okay
Identique à -ok, sauf qu'il rapportera les systèmes plus anciens.
-nok
Rapporter une compilation non réussie sur ce système. Force -C. Force et fournit une valeur pour -s, puis vous demande de modifier le rapport et d'expliquer ce qui s'est mal passé. Alternativement, un rapport préparé peut être fourni en utilisant -f. Ne demande une adresse de retour que si elle ne peut pas la deviner (pour une utilisation avec make). Respecte l'adresse de retour spécifiée avec -r. Vous pouvez utiliser ceci avec -v pour obtenir des données plus complètes. Ne crée un rapport que si ce système a moins de 60 jours.
-nokay
Identique à -nok, sauf qu'il rapportera les systèmes plus anciens.
-p
Les noms d'un ou plusieurs fichiers de patchs ou d'autres pièces jointes textuelles à inclure avec le rapport. Les fichiers multiples doivent être séparés par des virgules.
-r
Votre adresse de retour. Le programme vous demandera de confirmer sa valeur par défaut si vous n'utilisez pas cette option.
-S
Sauvegarder ou envoyer le rapport sans demander de confirmation.
-s
Objet à inclure avec le rapport. Vous serez invité si vous n'en fournissez pas un sur la ligne de commande.
-t
Mode test. Permet de commander perlbug depuis un tuyau ou un fichier, à des fins de test.
-T
Envoyer un mot de remerciement au lieu d'un rapport de bogue.
-v
Inclure des données de configuration détaillées dans le rapport.
