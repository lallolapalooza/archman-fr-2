PERLUNIINTRO(1perl) Guide du programmeur Perl PERLUNIINTRO(1perl)

NOM

perluniintro - Introduction à Unicode dans Perl

DESCRIPTION

Ce document donne une idée générale d'Unicode et de son utilisation dans Perl. Voir "Ressources supplémentaires" pour des références plus approfondies sur Unicode.

Unicode

Unicode est une norme de jeu de caractères qui vise à codifier tous les systèmes d'écriture du monde, ainsi que de nombreux autres symboles.

Unicode et ISO/IEC 10646 sont des normes coordonnées qui unifient presque toutes les autres normes de jeux de caractères modernes, couvrant plus de 80 systèmes d'écriture et des centaines de langues, y compris toutes les langues modernes commercialement importantes. Tous les caractères des plus grands dictionnaires chinois, japonais et coréens y sont également encodés. Les normes couvriront éventuellement presque tous les caractères dans plus de 250 systèmes d'écriture et des milliers de langues. Unicode 1.0 est sorti en octobre 1991, et 6.0 en octobre 2010.

Un caractère Unicode est une entité abstraite. Il n'est pas lié à une largeur entière particulière, et encore moins au caractère C "char". Unicode est neutre vis-à-vis de la langue et de l'affichage : il ne code pas la langue du texte, et ne définit généralement pas les polices ou d'autres détails de mise en page graphique. Unicode opère sur des caractères et du texte construit à partir de ces caractères.

Unicode définit des caractères comme "LETTR CAPITALE LATINE A" ou "LETTR MINUSCULE GRECQUE ALPHA" et des nombres uniques pour ces caractères, dans ce cas 0x0041 et 0x03B1, respectivement. Ces nombres uniques sont appelés points de code. Un point de code est essentiellement la position du caractère dans l'ensemble de tous les caractères Unicode possibles, et donc dans Perl, le terme ordinal est souvent utilisé de manière interchangeable avec lui.

La norme Unicode préfère utiliser la notation hexadécimale pour les points de code. Si des nombres comme 0x0041 vous sont inconnus, jetez un œil à une section ultérieure, "Notation hexadécimale". La norme Unicode utilise la notation "U+0041 LATIN CAPITAL LETTER A", pour donner le point de code hexadécimal et le nom normatif du caractère.

Unicode définit également diverses propriétés pour les caractères, comme "majuscule" ou "minuscule", "chiffre décimal", ou "ponctuation" ; ces propriétés sont indépendantes des noms des caractères. De plus, diverses opérations sur les caractères comme la mise en majuscules, la mise en minuscules et la collation (tri) sont définies.

Un "caractère" logique Unicode peut en fait consister en plus d'un interne réel "caractère" ou point de code. Pour les langues occidentales, cela est correctement modélisé par un caractère de base (comme "LETTR CAPITALE LATINE A") suivi d'un ou plusieurs modificateurs (comme "ACCENT AIGU COMBINANT"). Cette séquence de caractère de base et de modificateurs est appelée une séquence de caractères combinants. Certaines langues non occidentales nécessitent des modèles plus complexes, de sorte qu'Unicode a créé le concept de cluster de graphèmes, qui a ensuite été affiné en cluster de graphèmes étendu. Par exemple, une syllabe coréenne Hangul est considérée comme un caractère logique unique, mais elle est le plus souvent constituée de trois caractères Unicode réels : une consonne initiale suivie d'une voyelle intérieure suivie d'une consonne finale.

Que l'on appelle ces clusters de graphèmes étendus des "caractères" dépend de votre point de vue. Si vous êtes programmeur, vous auriez probablement tendance à considérer chaque élément des séquences comme une unité, ou "caractère". Cependant, du point de vue de l'utilisateur, l'ensemble de la séquence pourrait être considéré comme un seul "caractère" car c'est probablement ce qu'il ressemble dans le contexte de la langue de l'utilisateur. Dans ce document, nous adoptons le point de vue du programmeur : un "caractère" est un point de code Unicode.

Pour certaines combinaisons de caractères de base et de modificateurs, il existe des caractères précomposés. Il existe un caractère unique équivalent, par exemple, pour la séquence "LETTR CAPITALE LATINE A" suivie de "ACCENT AIGU COMBINANT". Il s'appelle "LETTR CAPITALE LATINE A AVEC ACCENT AIGU". Ces caractères précomposés ne sont cependant disponibles que pour certaines combinaisons, et sont principalement destinés à prendre en charge les conversions aller-retour entre Unicode et les normes héritées (comme ISO 8859). L'utilisation de séquences, comme le fait Unicode, permet d'avoir besoin de moins de blocs de construction de base (points de code) pour exprimer beaucoup plus de clusters de graphèmes potentiels. Pour prendre en charge la conversion entre les formes équivalentes, diverses formes de normalisation sont également définies. Ainsi, "LETTR CAPITALE LATINE A AVEC ACCENT AIGU" est en Forme Normale Composée, (abrégée NFC), et la séquence "LETTR CAPITALE LATINE A" suivie de "ACCENT AIGU COMBINANT" représente le même caractère en Forme Normale Décomposée (NFD).

En raison de la compatibilité ascendante avec les encodages hérités, l'idée d'« un numéro unique pour chaque caractère » s'effondre un peu : il y a plutôt « au moins un numéro pour chaque caractère ». Le même caractère pourrait être représenté différemment dans plusieurs encodages hérités. Le contraire n'est pas vrai : certains points de code n'ont pas de caractère attribué. Premièrement, il y a des points de code non alloués dans des blocs autrement utilisés. Deuxièmement, il existe des caractères de contrôle Unicode spéciaux qui ne représentent pas de vrais caractères.

Lorsque Unicode a été conçu, on pensait que tous les caractères du monde pouvaient être représentés à l'aide d'un mot de 16 bits ; c'est-à-dire qu'un maximum de 0x10000 (ou 65 536) caractères serait nécessaire, de 0x0000 à 0xFFFF. Cela s'est vite avéré faux, et depuis Unicode 2.0 (juillet 1996), Unicode est défini jusqu'à 21 bits (0x10FFFF), et Unicode 3.1 (mars 2001) a défini les premiers caractères au-delà de 0xFFFF. Les 65 536 premiers caractères sont appelés le Plano 0, ou le Plano Multilingue de Base (BMP). Avec Unicode 3.1, 17 (oui, dix-sept) planos au total ont été définis - mais ils sont loin d'être remplis de caractères définis, pour l'instant.

Lorsqu'un nouveau langage est encodé, Unicode choisit généralement un "bloc" de points de code consécutifs non alloués pour ses caractères. Jusqu'à présent, le nombre de points de code dans ces blocs a toujours été divisible par 16. Les extras dans un bloc, non nécessaires pour le moment, restent non alloués, pour une croissance future. Mais il est arrivé qu'une version ultérieure ait besoin de plus de points de code que les extras disponibles, et qu'un nouveau bloc ait dû être alloué ailleurs, non contigu au premier, pour gérer le dépassement. Ainsi, il est devenu apparent très tôt que le "bloc" n'était pas un principe organisateur adéquat, et la propriété "Script" a été créée. (Plus tard, une propriété de script améliorée a également été ajoutée, la propriété "Script_Extensions".) Les points de code qui se trouvent dans des blocs de dépassement peuvent toujours avoir le même script que les originaux. Le concept de script correspond mieux aux langues naturelles : il y a le script "Latin", le script "Grec", et ainsi de suite ; et il existe plusieurs scripts artificiels, comme "Commun" pour les caractères utilisés dans plusieurs scripts, tels que les symboles mathématiques. Les scripts couvrent généralement des parties variées de plusieurs blocs. Pour plus d'informations sur les scripts, voir "Scripts" dans perlunicode. La division en blocs existe, mais elle est presque totalement accidentelle - un artefact de la façon dont les caractères ont été et sont encore alloués. (Notez que ce paragraphe a simplifié les choses pour que cela soit une introduction. Unicode n'encode pas réellement les langues, mais les systèmes d'écriture pour elles - leurs scripts ; et un script peut être utilisé par de nombreuses langues. Unicode code également des choses qui ne sont pas réellement liées aux langues, comme des symboles comme "ZONE D'EMBARGEMENT".)

Les points de code Unicode ne sont que des nombres abstraits. Pour saisir et sortir ces nombres abstraits, les nombres doivent être encodés ou sérialisés d'une manière ou d'une autre. Unicode définit plusieurs formes d'encodage de caractères, dont UTF-8 est le plus populaire. UTF-8 est un encodage de longueur variable qui encode les caractères Unicode en 1 à 4 octets. Les autres encodages incluent UTF-16 et UTF-32 et leurs variantes big- et

Support Unicode de Perl

Depuis Perl v5.6.0, Perl a la capacité de gérer l'Unicode nativement. Perl v5.8.0, cependant, est la première version recommandée pour un travail sérieux avec l'Unicode. La version de maintenance 5.6.1 a corrigé de nombreux problèmes de l'implémentation Unicode initiale, mais par exemple les expressions régulières ne fonctionnent toujours pas avec l'Unicode en 5.6.1. Perl v5.14.0 est la première version où le support Unicode est (presque) intégrable de manière transparente sans quelques pièges. (Il y a quelques exceptions. Premièrement, certaines différences dans quotemeta ont été corrigées à partir de Perl 5.16.0. Deuxièmement, certaines différences dans l'opérateur de plage ont été corrigées à partir de Perl 5.26.0. Troisièmement, certaines différences dans split ont été corrigées à partir de Perl 5.28.0.)

Pour activer ce support transparent, vous devez "use feature 'unicode_strings'" (ce qui est automatiquement sélectionné si vous "use v5.12" ou une version supérieure). Voir feature. (5.14 corrige également un certain nombre de bogues et d'écarts par rapport à la norme Unicode.)

Avant Perl v5.8.0, l'utilisation de "use utf8" était utilisée pour déclarer que les opérations dans le bloc ou le fichier courant seraient conscientes de l'Unicode. Ce modèle s'est avéré erroné, ou du moins maladroit : l'«unicité» est maintenant portée par les données, au lieu d'être attachée aux opérations. À partir de Perl v5.8.0, un seul cas reste où un "use utf8" explicite est nécessaire : si votre script Perl est lui-même encodé en UTF-8, vous pouvez utiliser l'UTF-8 dans vos noms d'identificateurs, et dans les littéraux de chaînes et d'expressions régulières, en disant "use utf8". Ce n'est pas le défaut car les scripts contenant des données 8 bits héritées se casseraient. Voir utf8.

Modèle Unicode de Perl

Perl prend en charge à la fois les chaînes de 8 bits natives avant 5.6, et les chaînes de caractères Unicode. Le principe général est que Perl essaie de conserver ses données sous forme d'octets sur 8 bits aussi longtemps que possible, mais dès que l'unicité ne peut être évitée, les données sont transparentement mises à niveau vers l'Unicode. Avant Perl v5.14.0, la mise à niveau n'était pas complètement transparente (voir « Le « bug Unicode » » dans perlunicode), et pour des raisons de compatibilité ascendante, la transparence complète n'est atteinte que si use feature 'unicode_strings' (voir feature) ou "use v5.12" (ou une version supérieure) est sélectionné.

En interne, Perl utilise actuellement soit le jeu de caractères 8 bits natif de la plateforme (par exemple Latin-1), soit l'UTF-8 par défaut, pour encoder les chaînes Unicode. Plus précisément, si tous les points de code de la chaîne sont inférieurs ou égaux à 0xFF, Perl utilise le jeu de caractères natif 8 bits. Sinon, il utilise l'UTF-8.

Un utilisateur de Perl n'a normalement pas besoin de connaître ni de se soucier de la manière dont Perl encode ses chaînes internes, mais cela devient pertinent lors de la sortie de chaînes Unicode vers un flux sans couche PerlIO (une avec l'encodage « par défaut »). Dans un tel cas, les octets bruts utilisés en interne (le jeu de caractères natif ou l'UTF-8, selon le cas pour chaque chaîne) seront utilisés, et un avertissement « Caractère large » sera émis si ces chaînes contiennent un caractère au-delà de 0x00FF.

Par exemple,

perl -e 'print "\x{DF}\n", "\x{0100}\x{DF}\n"'

produit un mélange assez inutile d'octets natifs et d'UTF-8, ainsi qu'un avertissement :

Caractère large dans print à ...

Pour sortir en UTF-8, utilisez la couche de sortie ":encoding" ou ":utf8". Préfixer

binmode(STDOUT, ":utf8");

à ce programme d'exemple garantit que la sortie est entièrement en UTF-8 et supprime l'avertissement du programme.

Vous pouvez activer l'UTF-8 automatique de vos descripteurs de fichiers standard, de la couche open() par défaut et de @ARGV en utilisant soit le commutateur de ligne de commande "-C", soit la variable d'environnement "PERL_UNICODE", voir perlrun pour la documentation du commutateur "-C".

Notez que cela signifie que Perl s'attend à ce que les autres logiciels fonctionnent de la même manière : si Perl a été amené à croire que STDIN devrait être en UTF-8, mais que le STDIN provenant d'une autre commande n'est pas en UTF-8, Perl se plaindra probablement de l'UTF-8 mal formé.

Toutes les fonctionnalités qui combinent l'Unicode et les E/S nécessitent également l'utilisation de la nouvelle fonctionnalité PerlIO. Presque toutes les plateformes Perl 5.8 utilisent PerlIO, cependant : vous pouvez vérifier si la vôtre l'utilise en exécutant « perl -V » et en recherchant "useperlio=define".

Unicode et EBCDIC

Perl 5.8.0 a ajouté le support de l'Unicode sur les plateformes EBCDIC. Ce support a été laissé de côté dans les versions ultérieures, mais a été rétabli dans la version 5.22. Le support Unicode est quelque peu plus complexe à implémenter car des conversions supplémentaires sont nécessaires. Voir perlebcdic pour plus d'informations.

Sur les plateformes EBCDIC, la forme d'encodage Unicode interne est UTF-EBCDIC au lieu d'UTF-8. La différence est qu'alors que l'UTF-8 est « sûr pour l'ASCII » dans le sens où les caractères ASCII sont encodés en UTF-8 tels quels, l'UTF-EBCDIC est « sûr pour l'EBCDIC », dans le sens où tous les caractères de base (y compris tous ceux qui ont des équivalents ASCII (comme "A", "0", "%", etc.)) sont identiques en EBCDIC et en UTF-EBCDIC. Souvent, la documentation utilisera le terme « UTF-8 » pour désigner également UTF-EBCDIC. C'est le cas dans ce document.

Créer de l'Unicode

Cette section s'applique entièrement aux Perl à partir de la v5.22. Diverses mises en garde pour les versions antérieures se trouvent dans la sous-section « Mises en garde sur les versions antérieures » ci-dessous.

Pour créer des caractères Unicode dans des littéraux, utilisez la notation "\N{...}" dans les chaînes entre guillemets doubles :

my $smiley_from_name = "\N{WHITE SMILING FACE}";
my $smiley_from_code_point = "\N{U+263a}";

De même, ils peuvent être utilisés dans des littéraux d'expressions régulières

$smiley =~ /\N{WHITE SMILING FACE}/;
$smiley =~ /\N{U+263a}/;

ou, à partir de la v5.32 :

$smiley =~ /\p{Name=WHITE SMILING FACE}/;
$smiley =~ /\p{Name=whitesmilingface}/;

À l'exécution, vous pouvez utiliser :

use charnames ();
my $hebrew_alef_from_name
                     = charnames::string_vianame("HEBREW LETTER ALEF");
my $hebrew_alef_from_code_point = charnames::string_vianame("U+05D0");

Naturellement, ord() fait l'inverse : il transforme un caractère en un point de code.

Il existe d'autres options d'exécution. Vous pouvez utiliser pack() :

my $hebrew_alef_from_code_point = pack("U", 0x05d0);

Ou vous pouvez utiliser chr(), bien que ce soit moins pratique dans le cas général :

$hebrew_alef_from_code_point = chr(utf8::unicode_to_native(0x05d0));
utf8::upgrade($hebrew_alef_from_code_point);

Les utf8::unicode_to_native() et utf8::upgrade() ne sont pas nécessaires si l'argument est supérieur à 0xFF, donc ce qui précède aurait pu être écrit comme

$hebrew_alef_from_code_point = chr(0x05d0);

puisque 0x5d0 est supérieur à 255.

"\x{}" et "\o{}" peuvent également être utilisés pour spécifier des points de code au moment de la compilation dans des chaînes de type guillemets doubles, mais, pour des raisons de compatibilité ascendante avec les anciens Perl, les mêmes règles s'appliquent qu'avec chr() pour les points de code inférieurs à 256.

utf8::unicode_to_native() est utilisé pour que le code Perl soit portable sur les plateformes EBCDIC. Vous pouvez l'omettre si vous êtes *vraiment* sûr que personne ne voudra jamais utiliser votre code sur une plateforme non-ASCII. Depuis Perl v5.22, les appels à cette fonction sur les plateformes ASCII sont optimisés pour être éliminés, donc il n'y a aucun impact sur les performances à l'ajouter. Ou vous pouvez simplement utiliser les autres constructions qui n'en ont pas besoin.

Voir « Ressources supplémentaires » pour savoir comment trouver tous ces noms et codes numériques.

Mises en garde sur les versions antérieures

Sur les plateformes EBCDIC, avant la v5.22, l'utilisation de "\N{U+...}" ne fonctionne pas correctement.

Avant la v5.16, l'utilisation de "\N{...}" avec un nom de caractère (par opposition à un point de code "U+...") nécessitait une "use charnames :full".

Avant la v5.14, il y avait quelques bogues dans "\N{...}" avec un nom de caractère (par opposition à un point de code "U+...").

charnames::string_vianame() a été introduit dans la v5.14. Avant cela, charnames::vianame() devrait fonctionner, mais seulement si l'argument est de la forme "U+...". Votre meilleure option alors pour l'Unicode à l'exécution par nom de caractère est probablement :

use charnames ();
my $hebrew_alef_from_name
                 = pack("U", charnames::vianame("HEBREW LETTER ALEF"));

Gérer l'Unicode

La gestion de l'Unicode est, pour la plupart, transparente : utilisez simplement les chaînes comme d'habitude. Les fonctions comme index(), length() et substr() fonctionneront sur les caractères Unicode ; les expressions régulières fonctionneront sur les caractères Unicode (voir perlunicode et perlretut).

Notez que Perl considère les clusters de graphèmes comme des caractères distincts, donc par exemple

print length("\N{LATIN CAPITAL LETTER A}\N{COMBINING ACUTE ACCENT}"),
      "\n";

imprimera 2, pas 1. La seule exception est que les expressions régulières ont "\X" pour faire correspondre un cluster de graphèmes étendu. (Ainsi, "\X" dans une expression régulière correspondrait à toute la séquence des deux caractères de l'exemple.)

La vie n'est cependant pas tout à fait aussi transparente lorsque l'on travaille avec des encodages hérités, des E/S et certains cas spéciaux :

Encodages hérités

Quand

vous combinez des données héritées et Unicode, les données héritées doivent être mises à niveau vers Unicode. Normalement, les données héritées sont considérées comme étant en ISO 8859-1 (ou EBCDIC, le cas échéant).

Le module "Encode" connaît de nombreux encodages et dispose d'interfaces pour effectuer des conversions entre ces encodages :

use Encode 'decode';
$data = decode("iso-8859-3", $data); # conversion depuis l'hérité

Entrées/Sorties Unicode

Normalement, l'écriture de données Unicode

print FH $some_string_with_unicode, "\n";

produit des octets bruts que Perl utilise pour encoder en interne la chaîne Unicode. L'encodage interne de Perl dépend du système ainsi que des caractères présents dans la chaîne au moment de l'opération. Si l'un des caractères a un point de code de 0x100 ou supérieur, un avertissement sera émis. Pour garantir que la sortie est explicitement rendue dans l'encodage souhaité et pour éviter l'avertissement, ouvrez le flux avec l'encodage désiré. Quelques exemples :

open FH, ">:utf8", "fichier";
open FH, ">:encoding(ucs2)",      "fichier";
open FH, ">:encoding(UTF-8)",     "fichier";
open FH, ">:encoding(shift_jis)", "fichier";

et sur des flux déjà ouverts, utilisez binmode() :

binmode(STDOUT, ":utf8");
binmode(STDOUT, ":encoding(ucs2)");
binmode(STDOUT, ":encoding(UTF-8)");
binmode(STDOUT, ":encoding(shift_jis)");

La correspondance des noms d'encodage est souple : la casse n'a pas d'importance, et de nombreux encodages ont plusieurs alias. Notez que la couche ":utf8" doit toujours être spécifiée exactement ainsi ; elle n'est *pas* sujette à la correspondance souple des noms d'encodage. Notez également qu'actuellement ":utf8" n'est pas sûr pour l'entrée, car il accepte les données sans valider qu'il s'agit bien de UTF-8 valide ; vous devriez plutôt utiliser :encoding(UTF-8) (avec ou sans trait d'union).

Voir PerlIO pour la couche ":utf8", PerlIO::encoding et Encode::PerlIO pour la couche :encoding(), et Encode::Supported pour les nombreux encodages pris en charge par le module "Encode".

La lecture d'un fichier dont on sait qu'il est encodé dans l'un des encodages Unicode ou hérités ne transforme pas magiquement les données en Unicode aux yeux de Perl. Pour ce faire, spécifiez la couche appropriée lors de l'ouverture des fichiers :

open(my $fh,'<:encoding(UTF-8)', 'nimportequoi');
my $line_of_unicode = <$fh>;
open(my $fh,'<:encoding(Big5)', 'nimportequoi');
my $line_of_unicode = <$fh>;

Les couches d'E/S peuvent également être spécifiées de manière plus flexible avec le pragma "open". Voir open, ou regardez l'exemple suivant.

use open ':encoding(UTF-8)'; # l'encodage par défaut en entrée/sortie sera
                             # UTF-8
open X, ">fichier";
print X chr(0x100), "\n";
close X;
open Y, "<fichier";
printf "%#x\n", ord(<Y>); # cela devrait afficher 0x100
close Y;

Avec le pragma "open", vous pouvez utiliser la couche ":locale".

BEGIN { $ENV{LC_ALL} = $ENV{LANG} = 'ru_RU.KOI8-R' }
# le :locale interrogera les variables d'environnement de locale comme
# LC_ALL
use open OUT => ':locale'; # russe parusse
open(O, ">koi8");
print O chr(0x430); # LETTRE MINUSCULE CYRILLIQUE A en Unicode = KOI8-R 0xc1
close O;
open(I, "<koi8");
printf "%#x\n", ord(<I>), "\n"; # cela devrait afficher 0xc1
close I;

Ces méthodes installent un filtre transparent sur le flux d'E/S qui convertit les données de l'encodage spécifié lors de leur lecture depuis le flux. Le résultat est toujours Unicode.

Le pragma open affecte tous les appels open() après le pragma en définissant les couches par défaut. Si vous souhaitez affecter uniquement certains flux, utilisez des couches explicites directement dans l'appel open().

Vous pouvez changer d'encodage sur un flux déjà ouvert en utilisant binmode() ; voir "binmode" in perlfunc.

Le ":locale" ne fonctionne actuellement pas avec open() et binmode(), uniquement avec le pragma "open". Les méthodes ":utf8" et :encoding(...) fonctionnent avec open(), binmode() et le pragma "open".

De même, vous pouvez utiliser ces couches d'E/S sur des flux de sortie pour convertir automatiquement Unicode vers l'encodage spécifié lors de son écriture dans le flux. Par exemple, le fragment de code suivant copie le contenu du fichier "text.jis" (encodé en ISO-2022-JP, alias JIS) vers le fichier "text.utf8", encodé en UTF-8 :

open(my $nihongo, '<:encoding(iso-2022-jp)', 'text.jis');
open(my $unicode, '>:utf8',                  'text.utf8');
while (<$nihongo>) { print $unicode $_ }

La dénomination des encodages, à la fois par open() et par le pragma "open", permet des noms flexibles : "koi8-r" et "KOI8R" seront tous deux compris.

Les encodages courants reconnus par l'ISO, le MIME, l'IANA et diverses autres organisations de normalisation sont reconnus ; pour une liste plus détaillée, voir Encode::Supported.

read() lit des caractères et retourne le nombre de caractères. seek() et tell() opèrent sur des comptes d'octets, tout comme sysseek().

sysread() et syswrite() ne doivent pas être utilisés sur des descripteurs de fichiers avec des couches d'encodage de caractères, ils se comportent mal, et ce comportement est déprécié depuis perl 5.24.

Notez qu'en raison du comportement par défaut de ne faire aucune conversion à l'entrée s'il n'y a pas de couche par défaut, il est facile d'écrire par erreur du code qui continue d'agrandir un fichier en encodant le contenu de manière répétée :

# AVERTISSEMENT DE CODE INCORRECT
open F, "fichier";
local $/; ## lire tout le fichier de caractères 8 bits
$t = <F>;
close F;
open F, ">:encoding(UTF-8)", "fichier";
print F $t; ## convertir en UTF-8 à la sortie
close F;

Si vous exécutez ce code deux fois, le contenu du *fichier* sera encodé deux fois en UTF-8. Un "use open ':encoding(UTF-8)'" aurait évité le bogue, ou l'ouverture explicite du *fichier* en entrée également en UTF-8.

NOTE : les fonctionnalités ":utf8" et ":encoding" ne fonctionnent que si votre Perl a été compilé avec PerlIO, ce qui est le défaut sur la plupart des systèmes.

Affichage de Unicode sous forme de Texte

Parfois, vous voudrez peut-être afficher des scalaires Perl contenant de l'Unicode sous forme de texte ASCII (ou EBCDIC) simple. La sous-routine suivante convertit son argument de sorte que les caractères Unicode avec des points de code supérieurs à 255 soient affichés sous la forme "\x{...}", les caractères de contrôle (comme "\n") soient affichés sous la forme "\x..", et les autres caractères tels quels :

sub nice_string {
       join("",
       map { $_ > 255                    # si caractère large...
             ? sprintf("\\x{%04X}", $_)  # \x{...}
             : chr($_) =~ /[[:cntrl:]]/  # sinon si caractère de contrôle...
               ? sprintf("\\x%02X", $_)  # \x..
               : quotemeta(chr($_))      # sinon cité ou tel quel
       } unpack("W*", $_[0]));           # dépaqueter les caractères Unicode
  }

Par exemple,

nice_string("foo\x{100}bar\n")

retourne la chaîne

'foo\x{0100}bar\x0A'

qui est prête à être imprimée.

("\\x{}" est utilisé ici au lieu de "\\N{}", car il est très probable que vous vouliez voir quelles sont les valeurs natives.)

Cas Particuliers

  • À partir de Perl 5.28, il est illégal pour les opérateurs bit à bit, tels que "~", d'opérer sur des chaînes contenant des points de code supérieurs à 255.
  • La fonction vec() peut produire des résultats surprenants si elle est utilisée sur des chaînes contenant des caractères avec des valeurs ordinales supérieures à 255. Dans ce cas, les résultats sont cohérents avec l'encodage interne des caractères, mais pas avec grand-chose d'autre. Ne le faites donc pas, et à partir de Perl 5.28, un message de dépréciation est émis si vous le faites, devenant illégal dans Perl 5.32.
  • Jeter un œil à l'encodage interne de Perl

    Les utilisateurs normaux de Perl ne devraient jamais se soucier de la manière dont Perl encode une chaîne Unicode particulière (car les moyens normaux d'accéder au contenu d'une chaîne avec Unicode - via l'entrée et la sortie - devraient toujours se faire via des couches d'E/S explicitement définies). Mais si vous devez le faire, il existe deux façons de regarder derrière le rideau.

    Une façon de regarder à l'intérieur de l'encodage interne des caractères Unicode est d'utiliser "unpack("C*", ...)" pour obtenir les octets de quel que soit l'encodage de la chaîne, ou "unpack("U0..", ...)" pour obtenir les octets de l'encodage UTF-8 :

    # cela affiche  c4 80  pour les octets UTF-8 0xc4 0x80
print join(" ", unpack("U0(H2)*", pack("U", 0x100))), "\n";

    Une autre façon serait d'utiliser le module Devel::Peek :

    perl -MDevel::Peek -e 'Dump(chr(0x100))'

    Cela affiche le drapeau "UTF8" dans FLAGS et les octets UTF-8 ainsi que les caractères Unicode dans "PV". Voir également plus loin dans ce document la discussion sur la fonction utf8::is_utf8().

    Cas et Normalisation

    • Comparaison de chaînes de caractères

      Par défaut, Perl compare les chaînes de caractères (par exemple, "a" vs "A") en se basant uniquement sur les points de code des caractères. Dans le cas ci-dessus, la réponse est non (car 0x0061 != 0x0041). Mais parfois, toutes les lettres MAJUSCULES A doivent être considérées comme égales, ou même les A de n'importe quel casse.

      La réponse longue est qu'il faut prendre en compte la normalisation des caractères et les problèmes de casse : voir Unicode::Normalize, Unicode Technical Report #15, Unicode Normalization Forms https://www.unicode.org/reports/tr15 et les sections sur le mappage des cas dans le Standard Unicode https://www.unicode.org.

      Depuis Perl 5.8.0, le pliage de casse « Full » de Case Mappings/SpecialCasing est implémenté, mais des bugs subsistent dans "qr//i" avec ceux-ci, la plupart corrigés par la version 5.14, et essentiellement entièrement par la version 5.18.

    • Collation des chaînes de caractères

      Les gens aiment voir leurs chaînes bien triées - ou comme on dit dans le jargon Unicode, collées. Mais là encore, que voulez-vous dire par coller ?

      (Est-ce que "LATIN CAPITAL LETTER A WITH ACUTE" vient avant ou après "LATIN CAPITAL LETTER A WITH GRAVE" ?)

      La réponse courte est que, par défaut, Perl compare les chaînes de caractères ("lt", "le", "cmp", "ge", "gt") en se basant uniquement sur les points de code des caractères. Dans le cas ci-dessus, la réponse est « après », puisque 0x00C1 > 0x00C0.

      La réponse longue est que « cela dépend », et une bonne réponse ne peut pas être donnée sans connaître (au minimum) le contexte linguistique. Voir Unicode::Collate, et Unicode Collation Algorithm https://www.unicode.org/reports/tr10/

    Divers

    • Plages et classes de caractères

      Les plages de caractères dans les classes de caractères entre crochets des expressions régulières (par exemple, "/[a-z]/") et dans l'opérateur "tr///" (également connu sous le nom de "y///") ne sont pas magiquement conscientes de Unicode. Ce que cela signifie, c'est que "[A-Za-z]" ne commencera pas magiquement à signifier « toutes les lettres alphabétiques » (non pas qu'il signifie cela même pour les caractères 8 bits ; pour ceux-ci, si vous utilisez des locales (perllocale), utilisez "/[[:alpha:]]/" ; et sinon, utilisez la propriété consciente des 8 bits "\p{alpha}").

      Toutes les propriétés qui commencent par "\p" (et son inverse "\P") sont en fait des classes de caractères conscientes de Unicode. Il y en a des dizaines, voir perluniprops.

      À partir de la v5.22, vous pouvez utiliser les points de code Unicode comme points de terminaison des plages de caractères dans les modèles d'expressions régulières, et la plage inclura tous les points de code Unicode qui se trouvent entre ces points de terminaison, inclus.

      qr/ [ \N{U+03} - \N{U+20} ] /xx

      inclut les points de code "\N{U+03}", "\N{U+04}", ..., "\N{U+20}".

      Cela fonctionne également pour les plages dans "tr///" à partir de Perl v5.24.

    • Conversions chaîne-nombre

      Unicode définit plusieurs autres caractères décimaux et numériques en plus des chiffres familiers de 0 à 9, tels que les chiffres arabes et indiens. Perl ne prend pas en charge la conversion chaîne-nombre pour des chiffres autres que les chiffres ASCII 0 à 9 (et les lettres ASCII "a" à "f" pour l'hexadécimal). Pour obtenir des conversions sûres à partir de n'importe quelle chaîne Unicode, utilisez « num() » dans Unicode::UCD.

    Questions Avec Réponses

    • Mes anciens scripts vont-ils casser ?

      Très probablement pas. À moins que vous ne génériez des caractères Unicode d'une manière ou d'une autre, le comportement précédent devrait être préservé. Le seul comportement qui a changé et qui pourrait commencer à générer de l'Unicode est l'ancien comportement de chr() où la fourniture d'un argument supérieur à 255 produisait un caractère modulo 255. chr(300), par exemple, était égal à chr(45) ou « - » (en ASCII), maintenant c'est LATIN CAPITAL LETTER I WITH BREVE.

    • Comment faire fonctionner mes scripts avec Unicode ?

      Très peu de travail devrait être nécessaire car rien ne change tant que vous ne générez pas de données Unicode. La chose la plus importante est d'obtenir les entrées en Unicode ; pour cela, voir la discussion précédente sur les E/S. Pour obtenir un support Unicode complet et transparent, ajoutez "use feature 'unicode_strings'" (ou "use v5.12" ou supérieur) à votre script.

    • Comment savoir si ma chaîne est en Unicode ?

      Vous ne devriez pas avoir à vous en soucier. Mais vous pourriez avoir à le faire si votre Perl est antérieur à 5.14.0 ou si vous n'avez pas spécifié "use feature 'unicode_strings'" ou use 5.012 (ou supérieur) car sinon les règles pour les points de code dans la plage 128 à 255 sont différentes selon que la chaîne qu'ils contiennent est en Unicode ou non. (Voir « When Unicode Does Not Happen » dans perlunicode.)

      Pour déterminer si une chaîne est en Unicode, utilisez :

      print utf8::is_utf8($string) ? 1 : 0, "\n";

      Mais notez que cela ne signifie pas que l'un des caractères de la chaîne est nécessairement codé en UTF-8, ni que l'un des caractères a des points de code supérieurs à 0xFF (255) ou même 0x80 (128), ni que la chaîne contient des caractères du tout. Tout ce que fait is_utf8() est de retourner la valeur du drapeau interne « utf8ness » attaché à $string. Si le drapeau est désactivé, les octets du scalaire sont interprétés comme un encodage d'un seul octet. Si le drapeau est activé, les octets du scalaire sont interprétés comme les points de code de caractères codés en UTF-8 (codage à longueur variable, potentiellement multi-octets). Les octets ajoutés à une chaîne codée en UTF-8 sont automatiquement mis à niveau vers UTF-8. Si des scalaires mixtes non-UTF-8 et UTF-8 sont fusionnés (interpolation entre guillemets doubles, concaténation explicite, ou substitution de paramètre printf/sprintf), le résultat sera codé en UTF-8 comme si des copies des chaînes d'octets avaient été mises à niveau vers UTF-8 : par exemple,

      $x = "ab\x80c";
$y = "\x{100}";
print "$x = $y\n";

      la chaîne de sortie sera codée en UTF-8 "ab\x80c = \x{100}\n", mais $x restera codé en octets.

      Parfois, vous pourriez vraiment avoir besoin de connaître la longueur en octets d'une chaîne plutôt que la longueur en caractères. Pour cela, utilisez le pragma "bytes" et la fonction length() :

      my $unicode = chr(0x100);
print length($unicode), "\n"; # affichera 1
use bytes;
print length($unicode), "\n"; # affichera 2
                              # (les 0xC4 0x80 de l'UTF-8)
no bytes;
    • Comment trouver l'encodage d'un fichier ?

      Vous pourriez essayer Encode::Guess, mais il présente un certain nombre de limitations.

    • Comment détecter des données qui ne sont pas valides dans un encodage particulier ?

      Utilisez le paquet "Encode" pour essayer de le décoder. Par exemple,

      use Encode 'decode';
if (eval { decode('UTF-8', $string, Encode::FB_CROAK); 1 }) {
    # $string est un UTF-8 valide
} else {
    # $string n'est pas un UTF-8 valide
}

      Ou utilisez "unpack" pour essayer de le décoder :

      use warnings;
@chars = unpack("C0U*", $string_of_bytes_that_I_think_is_utf8);

      En cas d'invalidité, un avertissement "Malformed UTF-8 character" est produit. Le « C0 » signifie « traiter la chaîne caractère par caractère ». Sans cela, "unpack("U*", ...)" fonctionnerait en mode "U0" (par défaut si la chaîne de format commence par "U") et retournerait les octets constituant l'encodage UTF-8 de la chaîne cible, ce qui fonctionnera toujours.

    • Comment convertir des données binaires dans un encodage particulier, ou vice versa ?

      Ceci n'est probablement pas aussi utile que vous pourriez le penser. Normalement, vous n'en aurez pas besoin.

      Dans un sens, ce que vous demandez n'a pas beaucoup de sens : les encodages sont pour les caractères, et les données binaires ne sont pas des « caractères », donc convertir des « données » dans un certain encodage n'a pas de sens à moins que vous ne sachiez dans quel jeu de caractères et quel encodage les données binaires se trouvent, auquel cas ce ne sont plus juste des données binaires, n'est-ce pas ?

      Si vous avez une séquence brute d'octets que vous savez devoir interpréter via un encodage particulier, vous pouvez utiliser "Encode" :

      use Encode 'from_to';
from_to($data, "iso-8859-1", "UTF-8"); # de latin-1 vers UTF-8

      L'appel à from_to() modifie les octets dans $data, mais rien de matériel quant à la nature de la chaîne n'a changé en ce qui concerne Perl. Avant et après l'appel, la chaîne $data contient juste un tas d'octets 8 bits. En ce qui concerne Perl, l'encodage de la chaîne reste « octets natifs système 8 bits ».

      Vous pourriez comparer cela à un module fictif « Translate » :

      use Translate;
my $phrase = "Yes";
Translate::from_to($phrase, 'english', 'deutsch');
## phrase contient maintenant "Ja"

      Le contenu de la chaîne change, mais pas la nature de la chaîne. Perl n'en sait pas plus après l'appel qu'avant que le contenu de la chaîne indique l'affirmation.

      Revenons à la conversion de données. Si vous avez (ou voulez) des données dans l'encodage 8 bits natif de votre système (par exemple, Latin-1, EBCDIC, etc.), vous pouvez utiliser pack/unpack pour convertir vers/depuis Unicode.

      $native_string  = pack("W*", unpack("U*&quo
      t;, $string_Unicode)); $string_Unicode = pack("U*", unpack("W*", $string_native));

      Si vous avez une séquence d'octets dont vous savez qu'elle est UTF-8 valide, mais que Perl ne le sait pas encore, vous pouvez convaincre Perl aussi :

      $Unicode = $octets;
utf8::decode($Unicode);

      ou :

      $Unicode = pack("U0a*", $octets);

      Vous pouvez trouver les octets qui composent une séquence UTF-8 avec

      @octets = unpack("C*", $string_Unicode)

      et vous pouvez créer de l'Unicode bien formé avec

      $string_Unicode = pack("U*", 0xff, ...)

    • Comment l'Unicode fonctionne-t-il avec les locales traditionnelles ?

      Si votre locale est une locale UTF-8, à partir de Perl v5.26, Perl fonctionne bien pour toutes les catégories ; avant cela, à partir de Perl v5.20, il fonctionne pour toutes les catégories sauf "LC_COLLATE", qui concerne le tri et l'opérateur "cmp". Mais notez que les modules standards "Unicode::Collate" et "Unicode::Collate::Locale" offrent des solutions beaucoup plus puissantes pour les problèmes de collation, et fonctionnent sur les versions antérieures.

      Pour les autres locales, à partir de Perl 5.16, vous pouvez spécifier

      use locale ':not_characters';

      pour que Perl fonctionne bien avec elles. Le hic est qu'il faut traduire de l'ensemble de caractères de la locale vers/depuis Unicode vous-même. Voir "Unicode I/O" ci-dessus pour comment

      use open ':locale';

      pour accomplir cela, mais tous les détails se trouvent dans "Unicode and UTF-8" dans perllocale, y compris les pièges qui se produisent si vous ne spécifiez pas ":not_characters".

    Notation hexadécimale

    La norme Unicode préfère utiliser la notation hexadécimale car elle montre plus clairement la division de l'Unicode en blocs de 256 caractères. L'hexadécimal est aussi simplement plus court que le décimal. Vous pouvez utiliser la notation décimale aussi, mais apprendre à utiliser l'hexadécimal rend la vie plus facile avec la norme Unicode. La notation "U+HHHH" utilise l'hexadécimal, par exemple.

    Le préfixe "0x" signifie un nombre hexadécimal, les chiffres sont 0-9 et a-f (ou A-F, la casse n'a pas d'importance). Chaque chiffre hexadécimal représente quatre bits, ou un demi-octet. "print 0x..., "\n"" affichera un nombre hexadécimal en décimal, et "printf "%x\n", $décimal" affichera un nombre décimal en hexadécimal. Si vous n'avez que les "chiffres hexadécimaux" d'un nombre hexadécimal, vous pouvez utiliser la fonction hex().

    print 0x0009, "\n";    # 9
print 0x000a, "\n";    # 10
print 0x000f, "\n";    # 15
print 0x0010, "\n";    # 16
print 0x0011, "\n";    # 17
print 0x0100, "\n";    # 256
print 0x0041, "\n";    # 65
printf "%x\n",  65;    # 41
printf "%#x\n", 65;    # 0x41
print hex("41"), "\n"; # 65

UNICODE DANS LES PERLS PLUS ANCIENS

Si vous ne pouvez pas mettre à niveau votre Perl vers la version 5.8.0 ou ultérieure, vous pouvez toujours effectuer un traitement Unicode en utilisant les modules "Unicode::String", "Unicode::Map8", et "Unicode::Map", disponibles sur CPAN. Si vous avez recode GNU installé, vous pouvez également utiliser le frontal Perl "Convert::Recode" pour les conversions de caractères.

Les conversions suivantes d'octets ISO 8859-1 (Latin-1) vers octets UTF-8 et retour sont rapides, le code fonctionne même avec les anciennes versions de Perl 5.

# ISO 8859-1 vers UTF-8
s/([\x80-\xFF])/chr(0xC0|ord($1)>>6).chr(0x80|ord($1)&0x3F)/eg;
# UTF-8 vers ISO 8859-1
s/([\xC2\xC3])([\x80-\xBF])/chr(ord($1)<<6&0xC0|ord($2)&0x3F)/eg;
