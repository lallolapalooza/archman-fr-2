PERF-PROBE(1) Manuel perf PERF-PROBE(1)

NOM

perf-probe - Définir de nouveaux points de trace dynamiques

SYNTAXE

perf probe [options] --add=PROBE [...]
ou
perf probe [options] PROBE
ou
perf probe [options] --del=[GROUPE:]EVENT [...]
ou
perf probe --list[=[GROUPE:]EVENT]
ou
perf probe [options] --line=LIGNE
ou
perf probe [options] --vars=POINT_DE_TRACE
ou
perf probe [options] --funcs
ou
perf probe [options] --definition=PROBE [...]

DESCRIPTION

Cette commande définit des événements de trace dynamiques, par symbole et registres sans debuginfo, ou par expressions C (numéros de ligne C, noms de fonctions C et variables locales C) avec debuginfo.

OPTIONS

-k, --vmlinux=CHEMIN

Spécifie le chemin du vmlinux qui contient le debuginfo (binaire Dwarf). Uniquement lorsque cette option est utilisée avec --definition, vous pouvez fournir un fichier vmlinux hors ligne.

-m, --module=NOM_MODULE|CHEMIN

Spécifie le nom du module dans lequel perf-probe recherche les points ou lignes de trace. Si un chemin vers le fichier du module est fourni, perf-probe le traite comme un module hors ligne (cela signifie que vous pouvez ajouter une trace sur un module qui n'est pas encore chargé).

-s, --source=CHEMIN

Spécifie le chemin vers les sources du noyau.

-v, --verbose

Soyez plus verbeux (affiche les arguments analysés, etc.). Ne peut pas être utilisé avec -q.

-q, --quiet

Ne pas afficher d'avertissements ou de messages. Ne peut pas être utilisé avec -v.

-a, --add=

Définit un événement de trace (voir SYNTAXE DE TRACE pour les détails).

-d, --del=

Supprime les événements de trace. Accepte les caractères génériques (*, ?) et les classes de caractères (par exemple [a-z], [!A-Z]).

-l, --list[=[GROUPE:]EVENT]

Liste les événements de trace actuels. Peut également accepter des motifs de filtrage de noms d'événements. Lorsqu'il est utilisé avec --cache, perf affiche toutes les traces mises en cache au lieu des traces actives.

-L, --line=

Affiche les lignes de code source qui peuvent être tracées. Nécessite un argument qui spécifie une plage du code source. (voir SYNTAXE DE LIGNE pour les détails)

-V, --vars=

Affiche les variables locales disponibles au point de trace donné. La syntaxe de l'argument est la même que la SYNTAXE DE TRACE, mais SANS ARGUMENTS.

--externs

(Uniquement pour --vars) Affiche les variables externes définies en plus des variables locales.

--no-inlines

(Uniquement pour --add) Recherche uniquement les fonctions non-inline. Les fonctions qui n'ont pas d'instances sont ignorées.

-F, --funcs[=FILTRE]

Affiche les fonctions disponibles dans le module ou le noyau donné. Avec -x/--exec, peut également lister les fonctions dans un exécutable utilisateur / bibliothèque partagée. Peut également accepter un argument de règle de FILTRE.

-D, --definition=

Affiche la définition de l'événement de trace convertie à partir de l'événement de trace donné au lieu de l'écrire dans tracing/[k,u]probe_events.

--filter=FILTRE

(Uniquement pour --vars et --funcs) Définit un filtre. FILTRE est une combinaison de motifs glob, voir MOTIF DE FILTRE pour les détails. Le FILTRE par défaut est "!k???tab_* & !crc_*" pour --vars, et "!_*" pour --funcs. Si plusieurs filtres sont spécifiés, seul le dernier filtre est utilisé.

-f, --force

Ajoute de force les événements portant le même nom.

-n, --dry-run

Exécution à blanc. Avec cette option, --add et --del n'exécutent pas les opérations réelles d'ajout et de suppression.

--cache

(Avec --add) Met en cache les traces. Tous les événements ajoutés avec succès sont également stockés dans le fichier de cache. (Avec --list) Affiche les traces mises en cache. (Avec --del) Supprime les traces mises en cache.

--max-probes=NOMBRE

Définit le nombre maximum de points de trace par événement. La valeur par défaut est 128.

--target-ns=PID : Obtient les informations de l'espace de noms de montage à partir du pid cible. Ceci est utilisé lors de la création d'une uprobe pour un processus résidant dans un espace de noms de montage différent de celui de l'utilitaire perf(1).

-x, --exec=CHEMIN

Spécifie le chemin du fichier exécutable ou de la bibliothèque partagée pour le traçage en espace utilisateur. Peut également être utilisé avec l'option --funcs.

--demangle

Démêle les symboles de l'application. --no-demangle est également disponible pour désactiver le démêlage.

--demangle-kernel

Démêle les symboles du noyau. --no-demangle-kernel est également disponible pour désactiver le démêlage du noyau.

En l'absence des options -m/-x, perf probe vérifie si le premier argument après les options est un nom de chemin absolu. Si c'est un chemin absolu, perf probe l'utilise comme module cible / binaire utilisateur cible à tracer.

SYNTAXE DE TRACE

Les points de trace sont définis par la syntaxe suivante.

1) Définir un événement basé sur le nom de la fonction
 [[GROUPE:]EVENEMENT=]FONCTION[@SRC][:NLIGNE|+OFFS]|%return|;PATRON [ARG ...]
2) Définir un événement basé sur le fichier source avec numéro de ligne
 [[GROUPE:]EVENEMENT=]SRC:NLIGNE [ARG ...]
3) Définir un événement basé sur le fichier source avec motif paresseux
 [[GROUPE:]EVENEMENT=]SRC;PATRON [ARG ...]
4) Événements SDT pré-définis ou événement mis en cache avec nom
 %[fournisseur_sdt:]EVENEMENT_SDT
 ou,
 fournisseur_sdt:EVENEMENT_SDT

EVENEMENT spécifie le nom du nouvel événement, s'il est omis, il sera défini avec le nom de la fonction tracée, et pour les traces de retour, un suffixe "__return" est automatiquement ajouté au nom de la fonction. Vous pouvez également spécifier un nom de groupe par GROUPE, s'il est omis, probe est utilisé pour kprobe et probe_<bin> est utilisé pour uprobe. Notez que l'utilisation d'un nom de groupe existant peut entrer en conflit avec d'autres événements. En particulier, l'utilisation du nom de groupe réservé aux modules du noyau peut masquer les événements intégrés dans les modules. FONCTION spécifie le nom d'une fonction tracée, et peut avoir l'une des options suivantes : +OFFS est le décalage à partir de l'adresse d'entrée de la fonction en octets, :NLIGNE est le numéro de ligne relatif par rapport à la ligne d'entrée de la fonction, et %return signifie que la fonction est tracée au retour. Et ;PATRON signifie un motif de correspondance paresseuse (voir CORRESPONDANCE PARESSEUSE). Notez que ;PATRON doit être la fin de la définition du point de trace. De plus, @SRC spécifie un fichier source qui contient cette fonction. Il est également possible de spécifier un point de trace par le numéro de ligne source ou par correspondance paresseuse en utilisant la syntaxe SRC:NLIGNE ou SRC;PATRON, où SRC est le chemin du fichier source, :NLIGNE est le numéro de ligne et ;PATRON est le motif de correspondance paresseuse. ARG spécifie les arguments de ce point de trace (voir ARGUMENT DE TRACE). EVENEMENT_SDT et FOURNISSEUR est le nom de l'événement pré-défini qui est défini par SDT (Statically Defined Tracing) utilisateur ou les traces pré-mises en cache avec un nom d'événement. Notez qu'avant d'utiliser l'événement SDT, le binaire cible (sur lequel les événements SDT sont définis) doit être analysé par perf-buildid-cache(1) pour que les événements SDT soient mis en cache.

Pour plus de détails sur le SDT, voir ci-dessous. https://sourceware.org/gdb/onlinedocs/gdb/Static-Probe-Points.html

CARACTERE ECHAPPE

Dans la syntaxe de trace, =, @, +, : et ; sont traités comme des caractères spéciaux. Vous pouvez utiliser une barre oblique inversée (\) pour échapper les caractères spéciaux. Ceci est utile si vous avez besoin de tracer des symboles versionnés spécifiques, comme les suffixes @GLIBC_..., ou également si vous devez spécifier un fichier source qui contient des caractères spéciaux. Notez que généralement une seule barre oblique inversée est consommée par le shell, vous devrez donc peut-être fournir une double barre oblique inversée (\\) ou envelopper le tout entre apostrophes ('AAA\@BBB'). Voir EXEMPLES comment c'est utilisé.

ARGUMENT DE TRACE

Chaque argument de trace suit la syntaxe ci-dessous.

[NOM=]VARIABLE_LOCALE|$valeur_retour|%REG|@SYMBOLE[:TYPE][@espace_utilisateur]

NOM spécifie le nom de cet argument (facultatif). Vous pouvez utiliser le nom d'une variable locale, d'un membre d'une structure de données locale (par exemple, var→champ, var.champ2), d'un tableau local avec un indice fixe (par exemple, tableau[1], var→tableau[0], var→pointeur[2]), ou le format d'argument de kprobe-tracer (par exemple, $retval, %ax, etc.). Notez que le nom de cet argument sera défini comme le dernier nom de membre si vous spécifiez un membre de structure de données locale (par exemple, champ2 pour var→champ

perf-probe(1) — perf — The Linux measurement suite

NAME

perf-probe - simple interface to kernel's tracepoint mechanism

SYNOPSIS

perf probe [OPTIONS] [-x PROBE_SYNTAX] PROBE_DEFINITION...

DESCRIPTION

The perf probe command is a simple interface to the kernel's tracepoint mechanism. It allows you to dynamically add probes to kernel functions, user-space functions, tracepoints, and kprobes. The probes can be used to record arguments, local variables, and other information at the probe point. The collected data can then be analyzed using other perf tools like perf-record and perf-report.

This command is useful for debugging and performance analysis, especially when you need to inspect the behavior of specific functions or code paths without modifying the source code or recompiling.

OPTIONS

The following options are available:

--add
Add probes. This is the default action if no action option is specified.
--del
Delete probes.
--list
List probes.
--cache
List probes and clear the cache.
--line
List probeable lines in functions.
-x PROBE_SYNTAX
Specify the executable or shared library to probe. If not specified, perf probe will try to probe the kernel.
--filter=FILTER_PATTERN
Filter variables to be recorded. See FILTER PATTERN section for detail.
--size=PROBE_SYNTAX
Specify the size of data to record for a probe. This is useful for recording structures or arrays.
--vars=PROBE_SYNTAX
Specify the variables to record. If not specified, all available variables will be recorded.
--fields=PROBE_SYNTAX
Specify the fields of a structure to record. This is useful for recording specific members of a structure.
--printf=PROBE_SYNTAX
Specify a printf-like format string to control the output of the probe. This allows for custom formatting of the recorded data.
--freq=PROBE_SYNTAX
Specify the frequency of probes. This is useful for reducing the overhead of tracing.
--log-level=PROBE_SYNTAX
Specify the log level for probe events. This allows filtering probe events based on their severity.
--target-ns=PROBE_SYNTAX
Specify the target namespace (PID) for probing. This is useful for probing processes in different namespaces.

PROBE SYNTAX

The probe syntax specifies the location and type of the probe. It follows the pattern:

[--] PROBE_LOCATION [PROBE_OPTIONS] [PROBE_ACTION]

PROBE_LOCATION can be:

  • A function name (e.g., schedule)
  • A tracepoint name (e.g., syscalls:sys_enter_read)
  • A user-space function name (e.g., /lib/libc.so.6:malloc)
  • A line number in a source file (e.g., /path/to/file.c:123)

PROBE_OPTIONS can include:

  • %REG: A register name (e.g., %rax, %rsp). Only valid on x86 systems.
  • @VAR: A local variable or function argument.
  • TYPE@VAR: A local variable or function argument with a specified type.
  • FILTER: A filter expression to limit when the probe is triggered.

PROBE_ACTION specifies what to do when the probe is triggered:

  • A list of variables to record.
  • A printf-like format string.

For example, schedule:10 cpu adds a probe to the 10th line of the schedule function and records the cpu variable.

ESCAPED CHARACTER

Some characters have special meaning in probe syntax and may need to be escaped with a backslash (\). These include:

  • *, ?, [, ]: Wildcards used in glob matching.
  • @: Used to denote variables or fields.
  • :: Used to separate function names from line numbers or file names from line numbers.
  • ,: Used to separate multiple arguments or probes.
  • (, ): Used for grouping expressions.
  • |, &: Used for boolean logic in filters.

For example, to probe a function named foo+bar, you would use foo\+bar.

PROBE ARGUMENT

Arguments to a probe can be specified in several ways:

  • NAME: The name of a variable or function parameter.
  • $vars: Expands to all local variables and function parameters accessible at the probe point.
  • $params: Expands to only the function parameters.
  • TYPENAME: Casts the type of the argument to TYPE. If omitted, perf probe tries to infer the type from debuginfo. Supported types include basic integer types (u8, u16, u32, u64, s8, s16, s32, s64), hexadecimal integers (x, x8, x16, x32, x64), signedness casting (u, s), strings ("string"), and bitfields.
  • %REG: On x86 systems, a shorthand for register names (e.g., %rax becomes %AX).
  • @userVAR: Treat the local variable VAR as a user-space memory address. Only valid for kprobe events.

Example: u64 my_var records the variable my_var as a 64-bit unsigned integer.

TYPES

The following types are supported for probe arguments:

  • Integer types: u8, u16, u32, u64 (unsigned) and s8, s16, s32, s64 (signed). These can be specified with decimal (default) or hexadecimal format (by using x prefix, e.g., x8, x16, x32, x64). The size can be auto-detected by omitting the number (e.g., u, s).
  • Hexadecimal integers: x, x8, x16, x32, x64.
  • Signedness casting: u, s.
  • String: string. Fetches a null-terminated string from kernel space. Fails if the string has been paged out. Valid only for char or unsigned char arrays or pointers.
  • Bitfield: b<bit-width>@<bit-offset>/<container-size>. Example: b8@10/32 extracts 8 bits starting from bit offset 10 within a 32-bit container.

LINE SYNTAX

Line ranges can be specified using the following syntax:

"FUNC[@SRC][:RLN[+NUM|-RLN2]]|SRC[:ALN[+NUM|-ALN2]]"

Where:

  • FUNC: Function name.
  • SRC: Source file path.
  • RLN: Relative line number from the start of the function.
  • ALN: Absolute line number in the source file.
  • NUM: Number of lines to include.
  • RLN2 / ALN2: End line number.

Examples:

  • schedule:10+20: Probe 20 lines starting from the 10th line of schedule.
  • /path/to/file.c:100-120: Probe lines 100 through 120 in /path/to/file.c.
  • my_func@my_file.c:5: Probe the 5th line of my_func in my_file.c.

LAZY MATCHING

Lazy matching allows for flexible probe point definitions by ignoring whitespace. It supports glob wildcards (*, ?) and character classes (e.g., [a-z]).

Example: a=* matches a=b, a = b, a == b, etc.

This feature helps maintain probe points even if minor code changes occur.

FILTER PATTERN

The filter pattern uses glob matching to filter variables. It supports:

  • Wildcards: *, ?.
  • Negation: ! prefix to exclude matches.
  • Boolean operators: & (AND), | (OR).
  • Grouping: (, ).

Example: --filter "foo* | bar*" shows variables starting with foo or bar.

Example: --filter "!foo* & *bar" shows variables that do not start with foo and end with bar. foobar would be filtered out.

EXAMPLES

Display probeable lines in schedule():

./perf probe --line schedule

Add a probe on the 12th line of schedule(), recording the cpu variable:

./perf probe schedule:12 cpu
or
./perf probe --add='schedule:12 cpu'

Add probes on all functions starting with schedule:

./perf probe schedule*
or
./perf probe --add='schedule*'

Add probes on lines in schedule() that call update_rq_clock():

./perf probe 'schedule;update_rq_clock*'
or
./perf probe --add='schedule;update_rq_clock*'

Delete all probes on schedule():

./perf probe --del='schedule*'

Add probes at zfree() function in /bin/zsh:

./perf probe -x /bin/zsh zfree or ./perf probe /bin/zsh zfree

Add probes at malloc() function in libc:

./perf probe -x /lib/libc.so.6 malloc or ./perf probe /lib/libc.so.6 malloc

Add a uprobe to a target process running in a different mount namespace:

./perf probe --target-ns <target pid> -x /lib64/libc.so.6 malloc

Add a USDT probe to a target process running in a different mount namespace:

./perf probe --target-ns <target pid> -x /usr/lib/jvm/java-1.8.0-openjdk-1.8.0.121-0.b13.el7_3.x86_64/jre/lib/amd64/server/libjvm.so %sdt_hotspot:thread__sleep__end

Add a probe on a specific versioned symbol by backslash escape:

./perf probe -x /lib64/libc-2.25.so 'malloc_get_state\@GLIBC_2.2.5'

Add a probe in a source file with special characters using backslash escape:

./perf probe -x /opt/test/a.out 'foo\+bar.c:4'

PERMISSIONS AND SYSCTL

Perf probe relies on ftrace (tracefs) and kallsyms (/proc/kallsyms), which require specific permissions and sysctl settings.

•Accessing tracefs and kallsyms typically requires root or privileged user. Therefore, commands like --add, --del, and --list (except for --cache) also require elevated privileges.
•System administrators can remount tracefs with 755 permissions (sudo mount -o remount,mode=755 /sys/kernel/tracing/) to allow unprivileged users to run perf probe --list.
•The sysctl setting /proc/sys/kernel/kptr_restrict affects kallsyms access. Setting it to 2 (restrict all users) prevents perf probe from retrieving necessary information. Set it to 1 (restrict non-CAP_SYSLOG users) for the commands mentioned above. User-space probes do not require kallsyms access, so this setting is only relevant for kernel function probing (kprobes).
•Perf probe reads vmlinux (for kernel) and/or debuginfo files (including user-space applications). Ensure that these files are readable by the user running the command.
