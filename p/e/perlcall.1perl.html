PERLCALL(1perl) Guide du programmeur Perl PERLCALL(1perl)

NOM

perlcall - Conventions d'appel de Perl depuis C

DESCRIPTION

Le but de ce document est de vous montrer comment appeler des sous-programmes Perl directement depuis C, c'est-à-dire comment écrire des callbacks (rappels).

En plus de discuter de l'interface C fournie par Perl pour écrire des callbacks, le document utilise une série d'exemples pour montrer comment l'interface fonctionne en pratique. De plus, certaines techniques de codage de callbacks sont abordées.

Les exemples où des callbacks sont nécessaires incluent :

  • Un gestionnaire d'erreurs :

    Vous avez créé une interface XSUB vers l'API C d'une application.

    Une fonctionnalité assez courante dans les applications est de permettre la définition d'une fonction C qui sera appelée chaque fois que quelque chose de grave se produit. Ce que nous aimerions, c'est pouvoir spécifier un sous-programme Perl qui sera appelé à la place.

  • Un programme événementiel :

    L'exemple classique d'utilisation de callbacks est l'écriture d'un programme événementiel, comme pour une application X11. Dans ce cas, vous enregistrez des fonctions à appeler chaque fois que des événements spécifiques se produisent, par exemple, un bouton de souris est pressé, le curseur entre dans une fenêtre ou un élément de menu est sélectionné.

Bien que les techniques décrites ici soient applicables lors de l'intégration de Perl dans un programme C, ce n'est pas l'objectif principal de ce document. D'autres détails doivent être pris en compte et sont spécifiques à l'intégration de Perl. Pour plus d'informations sur l'intégration de Perl dans C, référez-vous à perlembed.

Avant de vous lancer tête baissée dans le reste de ce document, il serait judicieux d'avoir lu les deux documents suivants : perlxs et perlguts.

LES FONCTIONS CALL

Bien que ce soit plus facile à expliquer à l'aide d'exemples, vous devez d'abord connaître quelques définitions importantes.

Perl dispose d'un certain nombre de fonctions C qui vous permettent d'appeler des sous-programmes Perl. Ce sont :

I32 call_sv(SV* sv, I32 flags);
I32 call_pv(char *subname, I32 flags);
I32 call_method(char *methname, I32 flags);
I32 call_argv(char *subname, I32 flags, char **argv);

La fonction clé est call_sv. Toutes les autres fonctions sont des wrappers assez simples qui facilitent l'appel de sous-programmes Perl dans des cas spéciaux. Au final, elles appelleront toutes call_sv pour invoquer le sous-programme Perl.

Toutes les fonctions call_* ont un paramètre "flags" qui est utilisé pour passer un masque de bits d'options à Perl. Ce masque de bits fonctionne de manière identique pour chacune des fonctions. Les paramètres disponibles dans le masque de bits sont discutés dans "VALEURS DES FLAGS".

Chacune des fonctions sera maintenant discutée tour à tour.

call_sv
call_sv prend deux paramètres. Le premier, "sv", est un SV*. Cela vous permet de spécifier le sous-programme Perl à appeler, soit sous forme de chaîne C (qui a été préalablement convertie en SV) soit sous forme de référence à un sous-programme. La section "Utilisation de call_sv" montre comment vous pouvez utiliser call_sv.
call_pv
La fonction call_pv est similaire à call_sv, sauf qu'elle attend que son premier paramètre soit un char* C identifiant le sous-programme Perl que vous souhaitez appeler, par exemple "call_pv(\"fred\", 0)". Si le sous-programme que vous souhaitez appeler se trouve dans un autre package, incluez simplement le nom du package dans la chaîne, par exemple "pkg::fred".
call_method
La fonction call_method est utilisée pour appeler une méthode d'une classe Perl. Le paramètre "methname" correspond au nom de la méthode à appeler. Notez que la classe à laquelle appartient la méthode est passée sur la pile Perl plutôt que dans la liste des paramètres. Cette classe peut être soit le nom de la classe (pour une méthode statique) soit une référence à un objet (pour une méthode virtuelle). Voir perlobj pour plus d'informations sur les méthodes statiques et virtuelles et "Utilisation de call_method" pour un exemple d'utilisation de call_method.
call_argv
call_argv appelle le sous-programme Perl spécifié par la chaîne C stockée dans le paramètre "subname". Elle prend également le paramètre habituel "flags". Le dernier paramètre, "argv", consiste en une liste de chaînes C se terminant par NULL, à passer comme paramètres au sous-programme Perl. Voir "Utilisation de call_argv".

Toutes ces fonctions retournent un entier. Il s'agit du nombre d'éléments retournés par le sous-programme Perl. Les éléments réels retournés par le sous-programme sont stockés sur la pile Perl.

En règle générale, vous devriez toujours vérifier la valeur de retour de ces fonctions. Même si vous vous attendez à un nombre particulier de valeurs retournées par le sous-programme Perl, rien n'empêche quelqu'un de faire quelque chose d'inattendu - ne dites pas que vous n'avez pas été prévenu.

VALEURS DES FLAGS

Le paramètre "flags" dans toutes les fonctions call_* est soit "G_VOID", "G_SCALAR", soit "G_LIST", qui indiquent le contexte d'appel, combinés par OU (OR) avec un masque de bits de n'importe quelle combinaison des autres symboles G_* définis ci-dessous.

G_VOID

Appelle le sous-programme Perl dans un contexte vide.

Ce flag a 2 effets :

1.
Il indique au sous-programme appelé qu'il s'exécute dans un contexte vide (s'il exécute wantarray, le résultat sera la valeur indéfinie).
2.
Il garantit que rien n'est effectivement retourné par le sous-programme.

La valeur retournée par la fonction call_* indique le nombre d'éléments retournés par le sous-programme Perl - dans ce cas, ce sera 0.

G_SCALAR

Appelle le sous-programme Perl dans un contexte scalaire. C'est le paramètre de contexte par défaut pour toutes les fonctions call_*.

Ce flag a 2 effets :

1.
Il indique au sous-programme appelé qu'il s'exécute dans un contexte scalaire (s'il exécute wantarray, le résultat sera faux).
2.
Il garantit qu'un seul scalaire est effectivement retourné par le sous-programme. Le sous-programme peut, bien sûr, ignorer wantarray et retourner une liste de toute façon. Si c'est le cas, seul le dernier élément de la liste sera retourné.

La valeur retournée par la fonction call_* indique le nombre d'éléments retournés par le sous-programme Perl - dans ce cas, ce sera soit 0, soit 1.

Si c'est 0, alors vous avez spécifié le flag G_DISCARD.

Si c'est 1, alors l'élément effectivement retourné par le sous-programme Perl sera stocké sur la pile Perl - la section "Retour d'un scalaire" montre comment accéder à cette valeur sur la pile. Rappelez-vous que quel que soit le nombre d'éléments retournés par le sous-programme Perl, seul le dernier sera accessible depuis la pile - considérez le cas où une seule valeur est retournée comme une liste avec un seul élément. Tous les autres éléments qui ont été retournés n'existeront pas lorsque le contrôle reviendra de la fonction call_*. La section "Retour d'une liste en contexte scalaire" montre un exemple de ce comportement.

G_LIST

Appelle le sous-programme Perl dans un contexte de liste. Avant la version 5.35.1 de Perl, cela s'appelait "G_ARRAY".

Comme pour G_SCALAR, ce flag a 2 effets :

1.
Il indique au sous-programme appelé qu'il s'exécute dans un contexte de liste (s'il exécute wantarray, le résultat sera vrai).
2.
Il garantit que tous les éléments retournés par le sous-programme seront accessibles lorsque le contrôle reviendra de la fonction call_*.

La valeur retournée par la fonction call_* indique le nombre d'éléments retournés par le sous-programme Perl.

Si c'est 0, alors vous avez spécifié le flag G_DISCARD.

Si ce n'est pas 0, alors il w

ill be a count of the number of items returned by the subroutine. These items will be stored on the Perl stack. The section "Returning a List of Values" gives an example of using the G_LIST flag and the mechanics of accessing the returned items from the Perl stack.

G_DISCARD

Par défaut, les fonctions call_* placent les éléments retournés par la sous-routine Perl sur la pile. Si vous ne vous intéressez pas à ces éléments, définir ce drapeau les fera automatiquement supprimer par Perl. Notez qu'il est toujours possible d'indiquer un contexte à la sous-routine Perl en utilisant soit G_SCALAR soit G_LIST.

Si vous ne définissez pas ce drapeau, il est alors *très* important de vous assurer que tous les temporaires (c'est-à-dire les paramètres passés à la sous-routine Perl et les valeurs retournées par la sous-routine) sont éliminés par vous-même. La section « Retourner un scalaire » donne des détails sur la manière d'éliminer explicitement ces temporaires et la section « Utiliser Perl pour éliminer les temporaires » discute des circonstances spécifiques où vous pouvez ignorer le problème et laisser Perl s'en occuper pour vous.

G_NOARGS

Chaque fois qu'une sous-routine Perl est appelée en utilisant l'une des fonctions call_*, il est supposé par défaut que des paramètres doivent être passés à la sous-routine. Si vous ne passez aucun paramètre à la sous-routine Perl, vous pouvez gagner un peu de temps en définissant ce drapeau. Il a pour effet de ne pas créer le tableau @_ pour la sous-routine Perl.

Bien que la fonctionnalité fournie par ce drapeau puisse sembler simple, elle ne doit être utilisée que s'il y a une bonne raison de le faire. La raison d'être prudent est que, même si vous avez spécifié le drapeau G_NOARGS, il est toujours possible que la sous-routine Perl qui a été appelée pense que vous lui avez passé des paramètres.

En fait, ce qui peut arriver, c'est que la sous-routine Perl que vous avez appelée puisse accéder au tableau @_ d'une sous-routine Perl précédente. Cela se produira lorsque le code qui exécute la fonction call_* a lui-même été appelé à partir d'une autre sous-routine Perl. Le code ci-dessous illustre cela

sub fred
  { print "@_\n"  }
sub joe
  { &fred }
&joe(1,2,3);

Cela imprimera

1 2 3

Ce qui s'est passé, c'est que "fred" accède au tableau @_ qui appartient à "joe".

G_EVAL

Il est possible que la sous-routine Perl que vous appelez se termine anormalement, par exemple en appelant explicitement die ou en n'existant pas réellement. Par défaut, lorsque l'un de ces événements se produit, le processus se termine immédiatement. Si vous souhaitez intercepter ce type d'événement, spécifiez le drapeau G_EVAL. Il placera un eval { } autour de l'appel de la sous-routine.

Chaque fois que le contrôle revient de la fonction call_*, vous devez vérifier la variable $@ comme vous le feriez dans un script Perl normal.

La valeur retournée par la fonction call_* dépend des autres drapeaux spécifiés et si une erreur s'est produite. Voici tous les différents cas possibles :

  • Si la fonction call_* retourne normalement, la valeur retournée est comme spécifié dans les sections précédentes.
  • Si G_DISCARD est spécifié, la valeur de retour sera toujours 0.
  • Si G_LIST est spécifié *et* qu'une erreur s'est produite, la valeur de retour sera toujours 0.
  • Si G_SCALAR est spécifié *et* qu'une erreur s'est produite, la valeur de retour sera 1 et la valeur au sommet de la pile sera undef. Cela signifie que si vous avez déjà détecté l'erreur en vérifiant $@ et que vous souhaitez que le programme continue, vous devez vous souvenir de dépiler l' undef de la pile.

Voir « Utilisation de G_EVAL » pour plus de détails sur l'utilisation de G_EVAL.

G_KEEPERR

L'utilisation du drapeau G_EVAL décrit ci-dessus définira toujours $@ : le nettoyant s'il n'y avait pas d'erreur, et le définissant pour décrire l'erreur s'il y avait une erreur dans le code appelé. C'est ce que vous voulez si votre intention est de gérer les erreurs potentielles, mais parfois vous voulez simplement intercepter les erreurs et les empêcher d'interférer avec le reste du programme.

Ce scénario sera principalement applicable au code destiné à être appelé à partir de destructeurs, de rappels asynchrones et de gestionnaires de signaux. Dans de telles situations, où le code appelé a peu de relation avec le contexte dynamique environnant, le programme principal doit être isolé des erreurs dans le code appelé, même si elles ne peuvent pas être gérées intelligemment. Il peut également être utile de faire cela avec du code pour les crochets "__DIE__" ou "__WARN__", et les fonctions "tie".

Le drapeau G_KEEPERR est destiné à être utilisé conjointement avec G_EVAL dans les fonctions call_* qui sont utilisées pour implémenter un tel code, ou avec "eval_sv". Ce drapeau n'a aucun effet sur les fonctions call_* lorsque G_EVAL n'est pas utilisé.

Lorsque G_KEEPERR est utilisé, toute erreur dans le code appelé terminera l'appel comme d'habitude, et l'erreur ne se propagera pas au-delà de l'appel (comme d'habitude pour G_EVAL), mais elle n'ira pas dans $@. Au lieu de cela, l'erreur sera convertie en un avertissement, préfixé par la chaîne "\t(in cleanup)". Ceci peut être désactivé en utilisant "no warnings 'misc'". S'il n'y a pas d'erreur, $@ ne sera pas effacé.

Notez que le drapeau G_KEEPERR ne se propage pas dans les evals internes ; ceux-ci peuvent toujours définir $@.

Le drapeau G_KEEPERR a été introduit dans la version 5.002 de Perl.

Voir « Utilisation de G_KEEPERR » pour un exemple de situation justifiant l'utilisation de ce drapeau.

Détermination du contexte

Comme mentionné ci-dessus, vous pouvez déterminer le contexte de la sous-routine en cours d'exécution en Perl avec wantarray. Le test équivalent peut être fait en C en utilisant la macro "GIMME_V", qui retourne "G_LIST" si vous avez été appelé dans un contexte de liste, "G_SCALAR" si dans un contexte scalaire, ou "G_VOID" si dans un contexte vide (c'est-à-dire que la valeur de retour ne sera pas utilisée). Une ancienne version dépréciée de cette macro s'appelle "GIMME" ; dans un contexte vide, elle retourne "G_SCALAR" au lieu de "G_VOID". Un exemple d'utilisation de la macro "GIMME_V" est montré dans la section « Utilisation de GIMME_V ».

EXEMPLES

Assez de théorie ! Voici quelques exemples.

Perl fournit de nombreuses macros pour aider à accéder à la pile Perl. Dans la mesure du possible, ces macros doivent toujours être utilisées lors de l'interfaçage avec les internes de Perl. Nous espérons que cela rendra le code moins vulnérable aux changements apportés à Perl à l'avenir.

Un autre point à noter est que dans la première série d'exemples, j'ai utilisé uniquement la fonction call_pv. Cela a été fait pour garder le code simple et vous introduire en douceur au sujet. Dans la mesure du possible, si le choix se situe entre l'utilisation de call_pv et call_sv, vous devriez toujours essayer d'utiliser call_sv. Voir « Utilisation de call_sv » pour plus de détails.

Aucun paramètre, rien retourné

Ce premier exemple trivial appellera une sous-routine Perl, PrintUID, pour afficher l'UID du processus.

sub PrintUID
{
    print "UID is $<\n";
}

et voici une fonction C pour l'appeler

static void
call_PrintUID()
{
    dSP;
    PUSHMARK(SP);
    call_pv("PrintUID", G_DISCARD|G_NOARGS);
}

Simple, hein ?

Quelques points à noter à propos de cet exemple :

1.
Ignorez "dSP" et PUSHMARK(SP) pour l'instant. Ils seront discutés dans le prochain exemple.
2.
Nous ne passons aucun paramètre à PrintUID, donc G_NOARGS peut être spécifié.
3.
Nous ne nous intéressons à rien de retourné par PrintUID, donc G_DISCARD est spécifié. Même si PrintUID était modifié pour retourner une ou plusieurs valeurs, le fait d'avoir spécifié G_DISCARD signifie qu'elles seront effacées au moment où le contrôle reviendra de call_pv.
4.
Comme call_pv est utilisé, la sous-routine Perl est spécifiée comme une chaîne C. Dans ce cas, le nom de la sous-routine a été "codé en dur" dans le code.
5.
Parce que nous avons spécifié G_DISCARD, il n'est pas nécessaire de vérifier la valeur retournée par call_pv. Elle sera toujours de 0.

Passage de paramètres

Faisons maintenant un exemple un peu plus complexe. Cette fois, nous voulons appeler une sous-routine Perl, "LeftString", qui prendra 2 paramètres - une chaîne ($s) et un entier ($n). La sous-routine imprimera simplement les $n premiers caractères de la chaîne.

La sous-routine Perl ressemblerait donc à ceci :

sub LeftString
{
    my($s, $n) = @_;
    print substr($s, 0, $n), "\n";
}

La fonction C requise pour appeler LeftString ressemblerait à ceci :

static void
call_LeftString(a, b)
char * a;
int b;
{
    dSP;
    ENTER;
    SAVETMPS;
    PUSHMARK(SP);
    EXTEND(SP, 2);
    PUSHs(sv_2mortal(newSVpv(a, 0)));
    PUSHs(sv_2mortal(newSViv(b)));
    PUTBACK;
    call_pv("LeftString", G_DISCARD);
    FREETMPS;
    LEAVE;
}

Voici quelques notes sur la fonction C call_LeftString.

1.
Les paramètres sont passés à la sous-routine Perl en utilisant la pile Perl. C'est le but du code commençant par la ligne "dSP" et se terminant par la ligne "PUTBACK". Le "dSP" déclare une copie locale du pointeur de pile. Cette copie locale doit **toujours** être accédée en tant que "SP".
2.
Si vous allez placer quelque chose dans la pile Perl, vous devez savoir où le placer. C'est le but de la macro "dSP"--elle déclare et initialise une copie locale du pointeur de pile Perl.

Toutes les autres macros qui seront utilisées dans cet exemple nécessitent que vous ayez utilisé cette macro.

L'exception à cette règle est si vous appelez une sous-routine Perl directement depuis une fonction XSUB. Dans ce cas, il n'est pas nécessaire d'utiliser explicitement la macro "dSP"--elle sera déclarée pour vous automatiquement.

3.
Tous les paramètres à empiler doivent être encadrés par les macros "PUSHMARK" et "PUTBACK". Le but de ces deux macros, dans ce contexte, est de compter automatiquement le nombre de paramètres que vous empilez. Ensuite, lorsque Perl crée le tableau @_ pour la sous-routine, il sait quelle taille lui donner.

La macro "PUSHMARK" indique à Perl de prendre note du pointeur de pile actuel. Même si vous ne passez aucun paramètre (comme dans l'exemple montré dans la section "Pas de paramètres, rien en retour"), vous devez quand même appeler la macro "PUSHMARK" avant de pouvoir appeler les fonctions call_*--Perl a toujours besoin de savoir qu'il n'y a pas de paramètres.

La macro "PUTBACK" ajuste la copie globale du pointeur de pile pour qu'elle soit identique à notre copie locale. Si nous ne faisions pas cela, call_pv ne saurait pas où se trouvent les deux paramètres que nous avons empilés--rappelez-vous que jusqu'à présent, toute la manipulation du pointeur de pile que nous avons faite concerne notre copie locale, pas la copie globale.

4.
Ensuite, nous arrivons à EXTEND et PUSHs. C'est là que les paramètres sont réellement empilés. Dans ce cas, nous empilons une chaîne de caractères et un entier.

Alternativement, vous pouvez utiliser la macro XPUSHs(), qui combine un "EXTEND(SP, 1)" et un PUSHs(). C'est moins efficace si vous empilez plusieurs valeurs.

Voir "XSUBs et la pile d'arguments" dans perlguts pour plus de détails sur le fonctionnement des macros PUSH.

5.
Parce que nous avons créé des valeurs temporaires (au moyen d'appels à sv_2mortal()), nous devrons nettoyer la pile Perl et disposer des SV mortels.

C'est le but de

ENTER;
SAVETMPS;

au début de la fonction, et

FREETMPS;
LEAVE;

à la fin. La paire "ENTER"/"SAVETMPS" crée une limite pour tous les temporaires que nous créons. Cela signifie que les temporaires que nous éliminons seront limités à ceux qui ont été créés après ces appels.

La paire "FREETMPS"/"LEAVE" éliminera toutes les valeurs retournées par la sous-routine Perl (voir l'exemple suivant), plus elle videra également les SV mortels que nous avons créés. Avoir "ENTER"/"SAVETMPS" au début du code garantit qu'aucun autre mortel ne sera détruit.

Considérez ces macros comme fonctionnant un peu comme "{" et "}" en Perl pour limiter la portée des variables locales.

Voir la section "Utilisation de Perl pour disposer des temporaires" pour des détails sur une alternative à l'utilisation de ces macros.

6.
Enfin, LeftString peut maintenant être appelé via la fonction call_pv. Le seul drapeau spécifié cette fois est G_DISCARD. Parce que nous passons 2 paramètres à la sous-routine Perl cette fois-ci, nous n'avons pas spécifié G_NOARGS.

Retourner un scalaire

Maintenant, voici un exemple de traitement des éléments retournés par une sous-routine Perl.

Voici une sous-routine Perl, Adder, qui prend 2 paramètres entiers et retourne simplement leur somme.

sub Adder
{
    my($x, $y) = @_;
    $x + $y;
}

Parce que nous nous intéressons maintenant à la valeur de retour de Adder, la fonction C requise pour l'appeler est maintenant un peu plus complexe.

static void
call_Adder(a, b)
int a;
int b;
{
    dSP;
    int count;
    ENTER;
    SAVETMPS;
    PUSHMARK(SP);
    EXTEND(SP, 2);
    PUSHs(sv_2mortal(newSViv(a)));
    PUSHs(sv_2mortal(newSViv(b)));
    PUTBACK;
    count = call_pv("Adder", G_SCALAR);
    SPAGAIN;
    if (count != 1)
        croak("Gros problème\n");
    printf ("La somme de %d et %d est %d\n", a, b, POPi);
    PUTBACK;
    FREETMPS;
    LEAVE;
}

Points à noter cette fois-ci

1.
Le seul drapeau spécifié cette fois était G_SCALAR. Cela signifie que le tableau @_ sera créé et que la valeur retournée par Adder existera toujours après l'appel à call_pv.
2.
Le but de la macro "SPAGAIN" est de rafraîchir la copie locale du pointeur de pile. Ceci est nécessaire car il est possible que la mémoire allouée à la pile Perl ait été réallouée pendant l'appel à call_pv.

Si vous utilisez le pointeur de pile Perl dans votre code, vous devez toujours rafraîchir la copie locale en utilisant SPAGAIN chaque fois que vous utilisez les fonctions call_* ou toute autre fonction interne de Perl.

3.
Bien qu'une seule valeur doive être retournée par Adder, il est quand même de bonne pratique de vérifier le code de retour de call_pv.

S'attendre à une seule valeur n'est pas tout à fait la même chose que savoir qu'il y en aura une. Si quelqu'un modifiait Adder pour retourner une liste et que nous ne vérifiions pas cette possibilité et n'agissions pas en conséquence, la pile Perl se retrouverait dans un état incohérent. C'est quelque chose que vous ne voulez *vraiment* jamais qu'il arrive.

4.
La macro "POPi" est utilisée ici pour dépiler la valeur de retour de la pile. Dans ce cas, nous voulions un entier, donc "POPi" a été utilisé.

Voici la liste complète des macros POP disponibles, ainsi que les types qu'elles retournent.

POPs        SV
POPp        pointeur (PV)
POPpbytex   pointeur vers des octets (PV)
POPn        double (NV)
POPi        entier (IV)
POPu        entier non signé (UV)
POPl        long
POPul       unsigned long

Comme ces macros ont des effets secondaires, ne les utilisez pas comme arguments de macros qui peuvent évaluer leurs arguments plusieurs fois, par exemple :

/* Mauvaise idée, ne faites pas ça */
STRLEN len;
const char *s = SvPV(POPs, len);

Utilisez plutôt une variable temporaire :

STRLEN len;
SV *sv = POPs;
const char *s = SvPV(sv, len);

ou une macro qui garantit qu'elle n'évaluera ses arguments qu'une seule fois :

STRLEN len;
const char *s = SvPVx(POPs, len);
5.
Le dernier "PUTBACK" est utilisé pour laisser la pile Perl dans un état cohérent avant de quitter la fonction. Ceci est nécessaire car lorsque nous avons dépilé la valeur de retour de la pile avec "POPi", cela n'a mis à jour que notre copie locale du pointeur de pile. Rappelez-vous, "PUTBACK" définit le pointeur de pile global pour qu'il soit identique à notre copie locale.

Retourner une liste de valeurs

Maintenant, étendons l'exemple précédent pour retourner à la fois la somme des paramètres et la différence.

Voici la sous-routine Perl

sub AddSubtract
{
   my($x, $y) = @_;
   ($x+$y, $x-$y);
}

et voici la fonction C

static void
call_AddSubtract(a, b)
int a;
int b;
{
    dSP;
    int count;
    ENTER;
    SAVETMPS;
    PUSHMARK(SP);
    EXTEND(SP, 2);
    PUSHs(sv_2mortal(newSViv(a)));
    PUSHs(sv_2mortal(newSViv(b)));
    PUTBACK;
    count = call_pv("AddSubtract", G_LIST);
    SPAGAIN;
    if (count != 2)
        croak("Gros problème\n");
    printf ("%d - %d = %d\n", a, b, POPi);
    printf ("%d + %d = %d\n", a, b, POPi);
    PUTBACK;
    FREETMPS;
    LEAVE;
}

Si call_AddSubtract est appelé ainsi

call_AddSubtract(7, 4);

alors voici la sortie

7 - 4 = 3
7 + 4 = 11

Notes

1.
Nous voulions un contexte de liste, donc G_LIST a été utilisé.
2.
Sans surprise, "POPi" est utilisé deux fois cette fois car nous récupérions 2 valeurs de la pile. La chose importante à noter est que lors de l'utilisation des macros "POP*", elles sortent de la pile dans l'ordre inverse.

Retourner une liste dans un contexte scalaire

Disons que la sous-routine Perl de la section précédente a été appelée dans un contexte scalaire, comme ceci

static void
call_AddSubScalar(a, b)
int a;
int b;
{
    dSP;
    int count;
    int i;
    ENTER;
    SAVETMPS;
    PUSHMARK(SP);
    EXTEND(SP, 2);
    PUSHs(sv_2mortal(newSViv(a)));
    PUSHs(sv_2mortal(newSViv(b)));
    PUTBACK;
    count = call_pv("AddSubtract", G_SCALAR);
    SPAGAIN;
    printf ("Éléments retournés = %d\n", count);
    for (i = 1; i <= count; ++i)
        printf ("Valeur %d = %d\n", i, POPi);
    PUTBACK;
    FREETMPS;
    LEAVE;
}

L'autre modification apportée est que call_AddSubScalar affichera le nombre d'éléments retournés par la sous-routine Perl et leur valeur (par souci de simplicité, il suppose qu'ils sont entiers). Donc, si call_AddSubScalar est appelé

call_AddSubScalar(7, 4);

alors la sortie sera

Éléments retournés = 1
Valeur 1 = 3

Dans ce cas, le point principal à noter est que seul le dernier élément de la liste est retourné par la sous-routine. AddSubtract a effectivement renvoyé des informations à call_AddSubScalar.

Retourner des données de Perl via la liste de paramètres

Il est également possible de retourner des valeurs directement via la liste de paramètres--qu'il soit réellement souhaitable de le faire est une autre question.

La sous-routine Perl, Inc, ci-dessous prend 2 paramètres et incrémente

rements chacun directement.

sub Inc
{
    ++ $_[0];
    ++ $_[1];
}

et voici une fonction C pour l'appeler.

static void
call_Inc(a, b)
int a;
int b;
{
    dSP;
    int count;
    SV * sva;
    SV * svb;
    ENTER;
    SAVETMPS;
    sva = sv_2mortal(newSViv(a));
    svb = sv_2mortal(newSViv(b));
    PUSHMARK(SP);
    EXTEND(SP, 2);
    PUSHs(sva);
    PUSHs(svb);
    PUTBACK;
    count = call_pv("Inc", G_DISCARD);
    if (count != 0)
        croak ("call_Inc: expected 0 values from 'Inc', got %d\n",
               count);
    printf ("%d + 1 = %d\n", a, SvIV(sva));
    printf ("%d + 1 = %d\n", b, SvIV(svb));
    FREETMPS;
    LEAVE;
}

Pour pouvoir accéder aux deux paramètres qui ont été empilés après leur retour de call_pv, il est nécessaire de noter leurs adresses - d'où les deux variables "sva" et "svb".

La raison pour laquelle cela est nécessaire est que la zone de la pile Perl qui les contenait aura très probablement été écrasée par autre chose au moment où le contrôle retourne de call_pv.

Utilisation de G_EVAL

Voici maintenant un exemple utilisant G_EVAL. Ci-dessous se trouve une sous-routine Perl qui calcule la différence de ses 2 paramètres. Si cela résultait en un résultat négatif, la sous-routine appelle die.

sub Subtract
{
    my ($x, $y) = @_;
    die "death can be fatal\n" if $x < $y;
    $x - $y;
}

et du C pour l'appeler

static void
call_Subtract(a, b)
int a;
int b;
{
    dSP;
    int count;
    SV *err_tmp;
    ENTER;
    SAVETMPS;
    PUSHMARK(SP);
    EXTEND(SP, 2);
    PUSHs(sv_2mortal(newSViv(a)));
    PUSHs(sv_2mortal(newSViv(b)));
    PUTBACK;
    count = call_pv("Subtract", G_EVAL|G_SCALAR);
    SPAGAIN;
    /* Check the eval first */
    err_tmp = ERRSV;
    if (SvTRUE(err_tmp))
    {
        printf ("Uh oh - %s\n", SvPV_nolen(err_tmp));
        POPs;
    }
    else
    {
      if (count != 1)
       croak("call_Subtract: wanted 1 value from 'Subtract', got %d\n",
             count);
        printf ("%d - %d = %d\n", a, b, POPi);
    }
    PUTBACK;
    FREETMPS;
    LEAVE;
}

Si call_Subtract est appelé ainsi

call_Subtract(4, 5)

ce qui suit sera imprimé

Uh oh - death can be fatal

Notes

1.
Nous voulons pouvoir intercepter le die, nous avons donc utilisé le drapeau G_EVAL. Ne pas spécifier ce drapeau signifierait que le programme se terminerait immédiatement à l'instruction die de la sous-routine Subtract.
2.
Le code 
err_tmp = ERRSV;
if (SvTRUE(err_tmp))
{
    printf ("Uh oh - %s\n", SvPV_nolen(err_tmp));
    POPs;
}

est l'équivalent direct de ce bout de Perl

print "Uh oh - $@\n" if $@;

"PL_errgv" est une globale perl de type "GV *" qui pointe vers l'entrée de la table des symboles contenant l'erreur. "ERRSV" fait donc référence à l'équivalent C de $@. Nous utilisons un temporaire local, "err_tmp", car "ERRSV" est une macro qui appelle une fonction, et SvTRUE(ERRSV) finirait par appeler cette fonction plusieurs fois.

3.
Notez que la pile est dépilée en utilisant "POPs" dans le bloc où SvTRUE(err_tmp) est vrai. Ceci est nécessaire car, chaque fois qu'une fonction call_* invoquée avec G_EVAL|G_SCALAR retourne une erreur, le sommet de la pile contient la valeur undef. Comme nous voulons que le programme continue après avoir détecté cette erreur, il est essentiel que la pile soit nettoyée en supprimant l'undef.

Utilisation de G_KEEPERR

Considérez cet exemple plutôt facétieux, où nous avons utilisé une version XS de l'exemple call_Subtract ci-dessus dans un destructeur :

package Foo;
sub new { bless {}, $_[0] }
sub Subtract {
    my($x,$y) = @_;
    die "death can be fatal" if $x < $y;
    $x - $y;
}
sub DESTROY { call_Subtract(5, 4); }
sub foo { die "foo dies"; }
package main;
{
    my $foo = Foo->new;
    eval { $foo->foo };
}
print "Saw: $@" if $@;             # should be, but isn't

Cet exemple ne parviendra pas à reconnaître qu'une erreur s'est produite à l'intérieur de l'"eval {}". Voici pourquoi : le code call_Subtract a été exécuté pendant que Perl nettoyait les temporaires lors de la sortie du bloc entre accolades externe, et comme call_Subtract est implémenté avec call_pv utilisant le drapeau G_EVAL, il a rapidement réinitialisé $@. Cela entraîne l'échec du test le plus externe pour $@, et par conséquent l'échec du piège d'erreur.

Ajouter le drapeau G_KEEPERR, de sorte que l'appel call_pv dans call_Subtract lise :

count = call_pv("Subtract", G_EVAL|G_SCALAR|G_KEEPERR);

préservera l'erreur et restaurera une gestion fiable des erreurs.

Utilisation de call_sv

Dans tous les exemples précédents, j'ai "codé en dur" le nom de la sous-routine Perl à appeler depuis C. La plupart du temps, cependant, il est plus pratique de pouvoir spécifier le nom de la sous-routine Perl depuis le script Perl, et vous voudrez utiliser call_sv.

Considérez le code Perl ci-dessous

sub fred
{
    print "Hello there\n";
}
CallSubPV("fred");

Voici un extrait de XSUB qui définit CallSubPV.

void
CallSubPV(name)
    char *  name
    CODE:
    PUSHMARK(SP);
    call_pv(name, G_DISCARD|G_NOARGS);

C'est bien pour ce que c'est. Le fait est que la sous-routine Perl peut être spécifiée comme une simple chaîne, cependant, Perl autorise les références aux sous-routines et les sous-routines anonymes. C'est là que call_sv est utile.

Le code ci-dessous pour CallSubSV est identique à CallSubPV à ceci près que le paramètre "name" est maintenant défini comme un SV* et nous utilisons call_sv au lieu de call_pv.

void
CallSubSV(name)
    SV *    name
    CODE:
    PUSHMARK(SP);
    call_sv(name, G_DISCARD|G_NOARGS);

Comme nous utilisons un SV pour appeler fred, les éléments suivants peuvent tous être utilisés :

CallSubSV("fred");
CallSubSV(\&fred);
$ref = \&fred;
CallSubSV($ref);
CallSubSV( sub { print "Hello there\n" } );

Comme vous pouvez le voir, call_sv vous donne beaucoup plus de flexibilité dans la manière dont vous pouvez spécifier la sous-routine Perl.

Vous devriez noter que, s'il est nécessaire de stocker le SV ("name" dans l'exemple ci-dessus) qui correspond à la sous-routine Perl afin qu'il puisse être utilisé plus tard dans le programme, il ne suffit pas de stocker une copie du pointeur vers le SV. Disons que le code ci-dessus avait été comme ceci :

static SV * rememberSub;
void
SaveSub1(name)
    SV *    name
    CODE:
    rememberSub = name;
void
CallSavedSub1()
    CODE:
    PUSHMARK(SP);
    call_sv(rememberSub, G_DISCARD|G_NOARGS);

La raison pour laquelle c'est faux est que, au moment où vous utilisez le pointeur "rememberSub" dans "CallSavedSub1", il peut ou peut ne pas pointer toujours vers la sous-routine Perl qui a été enregistrée dans "SaveSub1". Ceci est particulièrement vrai pour ces cas :

SaveSub1(\&fred);
CallSavedSub1();
SaveSub1( sub { print "Hello there\n" } );
CallSavedSub1();

Au moment où chacune des instructions "SaveSub1" ci-dessus a été exécutée, les SV* qui correspondaient aux paramètres n'existeront plus. Attendez-vous à un message d'erreur de Perl du type

Can't use an undefined value as a subroutine reference at ...

pour chacune des lignes "CallSavedSub1".

De même, avec ce code

$ref = \&fred;
SaveSub1($ref);
$ref = 47;
CallSavedSub1();

vous pouvez vous attendre à l'un de ces messages (ce que vous obtenez réellement dépend de la version de Perl que vous utilisez)

Not a CODE reference at ...
Undefined subroutine &main::47 called ...

La variable $ref peut avoir pointé vers la sous-routine "fred" chaque fois que l'appel à "SaveSub1" a été effectué, mais au moment où "CallSavedSub1" est appelée, elle contient maintenant l'entier 47. Parce que nous n'avons stocké qu'un pointeur vers le SV d'origine dans "SaveSub1", toute modification de $ref sera suivie par le pointeur "rememberSub". Cela signifie que chaque fois que "CallSavedSub1" est appelée, elle tentera d'exécuter le code référencé par le SV* "rememberSub". Dans ce cas, il fait maintenant référence à l'entier 47, attendez-vous donc à ce que Perl se plaigne bruyamment.

Un problème similaire mais plus subtil est illustré par ce code :

$ref = \&fred;
SaveSub1($ref);
$ref = \&joe;
CallSavedSub1();

Cette fois, chaque fois que "CallSavedSub1" est appelée, elle exécutera la sous-routine Perl "joe" (en supposant qu'elle existe) plutôt que "fred" comme demandé à l'origine dans l'appel à "SaveSub1".

Pour contourner ces problèmes, il est nécessaire de faire une copie complète du SV. Le code ci-dessous montre "SaveSub2" modifié pour ce faire.

/* this isn't thread-safe */
static SV * keepSub = (SV*)NULL;
void
SaveSub2(name)
    SV *    name
    CODE:
    /* Take a copy of the callback */
    if (keepSub == (SV*)NULL)
        /* First time, so create a new SV */
        keepSub = newSVsv(name);
    else
        /* Been here before, so overwrite */
        SvSetSV(keepSub, name);
void
CallSavedSub2()
    CODE:
    PUSHMARK(SP);
    call_sv(keepSub, G_DISCARD|G_NOARGS);

Pour éviter de créer un nouveau SV à chaque fois que "SaveSub2" est appelé, la fonction vérifie d'abord si elle a déjà été appelée. Sinon, de l'espace pour un nouveau SV est alloué et la référence à la sous-routine Perl "name" est copiée dans la variable "keepSub" en une seule opération en utilisant "newSVsv". Par la suite, chaque fois que "SaveSub2" est appelé

allé, la SV existante, "keepSub", est écrasée par la nouvelle valeur en utilisant "SvSetSV".

Note : l'utilisation d'une variable statique ou globale pour stocker la SV n'est pas thread-safe. Vous pouvez soit utiliser le mécanisme "MY_CXT" documenté dans "Stockage sécurisé des données statiques dans XS" dans perlxs, qui est rapide, soit stocker les valeurs dans des variables globales perl, en utilisant get_sv(), ce qui est beaucoup plus lent.

Utilisation de call_argv

Voici une sous-routine Perl qui affiche tous les paramètres qui lui sont passés.

sub PrintList
{
    my(@list) = @_;
    foreach (@list) { print "$_\n" }
}

Et voici un exemple de call_argv qui appellera PrintList.

static char * words[] = {"alpha", "beta", "gamma", "delta", NULL};
static void
call_PrintList()
{
    call_argv("PrintList", G_DISCARD, words);
}

Notez qu'il n'est pas nécessaire d'appeler "PUSHMARK" dans ce cas. C'est parce que call_argv le fera pour vous.

Utilisation de call_method

Considérez le code Perl suivant :

{
    package Mine;
    sub new
    {
        my($type) = shift;
        bless [@_]
    }
    sub Display
    {
        my ($self, $index) = @_;
        print "$index: $$self[$index]\n";
    }
    sub PrintID
    {
        my($class) = @_;
        print "This is Class $class version 1.0\n";
    }
}

Il implémente une classe très simple pour gérer un tableau. Outre le constructeur, "new", il déclare des méthodes, une statique et une virtuelle. La méthode statique, "PrintID", affiche simplement le nom de la classe et un numéro de version. La méthode virtuelle, "Display", affiche un seul élément du tableau. Voici un exemple entièrement en Perl de son utilisation.

$x = Mine->new('red', 'green', 'blue');
$x->Display(1);
Mine->PrintID;

affichera

1: green
This is Class Mine version 1.0

Appeler une méthode Perl depuis C est assez simple. Les éléments suivants sont requis :

  • Une référence à l'objet pour une méthode virtuelle ou le nom de la classe pour une méthode statique
  • Le nom de la méthode
  • Tout autre paramètre spécifique à la méthode

Voici un XSUB simple qui illustre les mécanismes d'appel des méthodes "PrintID" et "Display" depuis C.

void
call_Method(ref, method, index)
    SV *    ref
    char *  method
    int             index
    CODE:
    PUSHMARK(SP);
    EXTEND(SP, 2);
    PUSHs(ref);
    PUSHs(sv_2mortal(newSViv(index)));
    PUTBACK;
    call_method(method, G_DISCARD);
void
call_PrintID(class, method)
    char *  class
    char *  method
    CODE:
    PUSHMARK(SP);
    XPUSHs(sv_2mortal(newSVpv(class, 0)));
    PUTBACK;
    call_method(method, G_DISCARD);

Ainsi, les méthodes "PrintID" et "Display" peuvent être invoquées comme suit :

$x = Mine->new('red', 'green', 'blue');
call_Method($x, 'Display', 1);
call_PrintID('Mine', 'PrintID');

La seule chose à noter est que, dans les méthodes statiques et virtuelles, le nom de la méthode n'est pas passé via la pile - il est utilisé comme premier paramètre de call_method.

Utilisation de GIMME_V

Voici un XSUB trivial qui affiche le contexte dans lequel il s'exécute actuellement.

    U8 gimme = GIMME_V;
    if (gimme == G_VOID)
        printf ("Context is Void\n");
    else if (gimme == G_SCALAR)

Et voici du Perl pour le tester.

La sortie de cela sera

Utilisation de Perl pour la libération des temporaires

Dans les exemples donnés jusqu'à présent, tous les temporaires créés dans le rappel (c'est-à-dire les paramètres passés sur la pile à la fonction call_* ou les valeurs retournées via la pile) ont été libérés par l'une de ces méthodes :

  • Spécification du drapeau G_DISCARD avec call_*
  • Utilisation explicite de la paire "ENTER"/"SAVETMPS"--"FREETMPS"/"LEAVE"

Il existe une autre méthode qui peut être utilisée, à savoir laisser Perl s'en charger automatiquement chaque fois qu'il reprend le contrôle après la fin du rappel. Ceci est fait en n'utilisant simplement pas la séquence

ENTER;
SAVETMPS;
...
FREETMPS;
LEAVE;

dans le rappel (et en ne spécifiant bien sûr pas le drapeau G_DISCARD).

Si vous allez utiliser cette méthode, vous devez être conscient d'une possible fuite de mémoire qui peut survenir dans des circonstances très spécifiques. Pour expliquer ces circonstances, vous devez connaître un peu le flux de contrôle entre Perl et la routine de rappel.

Les exemples donnés au début du document (un gestionnaire d'erreurs et un programme événementiel) sont typiques des deux principaux types de flux de contrôle que vous êtes susceptible de rencontrer avec les rappels. Il y a une distinction très importante entre eux, alors faites attention.

Dans le premier exemple, un gestionnaire d'erreurs, le flux de contrôle pourrait être le suivant. Vous avez créé une interface vers une bibliothèque externe. Le contrôle peut atteindre la bibliothèque externe comme suit :

perl --> XSUB --> bibliothèque externe

Pendant que le contrôle est dans la bibliothèque, une condition d'erreur se produit. Vous avez précédemment configuré un rappel Perl pour gérer cette situation, elle sera donc exécutée. Une fois le rappel terminé, le contrôle reviendra à Perl.

Voici à quoi ressemblera le flux de contrôle dans cette situation :

perl --> XSUB --> bibliothèque externe
                  ...
                  erreur se produit
                  ...
                  bibliothèque externe --> call_* --> perl
                                                      |
perl <-- XSUB <-- bibliothèque externe <-- call_* <----+

Après le traitement de l'erreur à l'aide de call_*, le contrôle revient à Perl plus ou moins immédiatement.

Dans le diagramme, plus vous allez vers la droite, plus la portée est imbriquée. Ce n'est que lorsque le contrôle est de retour avec perl à l'extrême gauche du diagramme que vous êtes revenu à la portée englobante et que tous les temporaires que vous avez laissés traîner seront libérés.

Dans le second exemple, un programme événementiel, le flux de contrôle ressemblera davantage à ceci :

perl --> XSUB --> gestionnaire d'événements
                  ...
                  gestionnaire d'événements --> call_* --> perl
                                                   |
                  gestionnaire d'événements <-- call_* <----+
                  ...
                  gestionnaire d'événements --> call_* --> perl
                                                   |
                  gestionnaire d'événements <-- call_* <----+
                  ...
                  gestionnaire d'événements --> call_* --> perl
                                                   |
                  gestionnaire d'événements <-- call_* <----+

Dans ce cas, le flux de contrôle peut consister uniquement en la séquence répétée

gestionnaire d'événements --> call_* --> perl

pendant pratiquement toute la durée du programme. Cela signifie que le contrôle peut jamais revenir à la portée englobante en Perl à l'extrême gauche.

Alors quel est le gros problème ? Eh bien, si vous vous attendez à ce que Perl nettoie ces temporaires pour vous, vous pourriez attendre longtemps. Pour que Perl élimine vos temporaires, le contrôle doit revenir à la portée englobante à un moment donné. Dans le scénario événementiel, cela peut ne jamais se produire. Cela signifie qu'au fil du temps, votre programme créera de plus en plus de temporaires, dont aucun ne sera jamais libéré. Comme chacun de ces temporaires consomme de la mémoire, votre programme finira par consommer toute la mémoire disponible de votre système - boum !

Voici donc la conclusion : si vous êtes sûr que le contrôle reviendra rapidement à la portée Perl englobante après la fin de votre rappel, alors il n'est pas absolument nécessaire de disposer explicitement des temporaires que vous avez pu créer. Cela dit, si vous n'êtes pas du tout sûr de la marche à suivre, nettoyer de toute façon ne fait pas de mal.

Stratégies de stockage des informations de contexte de rappel

Potentiellement, l'un des problèmes les plus délicats à résoudre lors de la conception d'une interface de rappel est de déterminer comment stocker la correspondance entre la fonction de rappel C et son équivalent Perl.

Pour aider à comprendre pourquoi cela peut être un problème, considérez d'abord comment un rappel est configuré dans un environnement entièrement en C. Typiquement, une API C fournit une fonction pour enregistrer un rappel. Celle-ci attendra un pointeur vers une fonction comme l'un de ses paramètres. Ci-dessous, un appel à une fonction hypothétique "register_fatal" qui enregistre la fonction C à appeler lorsqu'une erreur fatale se produit.

register_fatal(cb1);

Le paramètre unique "cb1" est un pointeur vers une fonction, vous devez donc avoir défini "cb1" dans votre code, disons quelque chose comme ceci :

static void
cb1()
{
    printf ("Fatal Error\n");
    exit(1);
}

Maintenant, changez cela pour appeler une sous-routine Perl à la place

static SV * callback = (SV*)NULL;
static void
cb1()
{
    dSP;
    PUSHMARK(SP);
    /* Appelle la sous-routine Perl pour traiter le rappel */
    call_sv(callback, G_DISCARD);
}
void
register_fatal(fn)
    SV *    fn
    CODE:
    /* Se souvient de la sous-routine Perl */
    if (callback == (SV*)NULL)
        callback = newSVsv(fn);
    else
        SvSetSV(callback, fn);
    /* enregistre le rappel auprès de la bibliothèque externe */
    register_fatal(cb1);

où l'équivalent Perl de "register_fatal" et le rappel qu'elle enregistre, "pcb1", pourrait ressembler à ceci :

# Enregistre la sous-routine pcb1
register_fatal(\&pcb1);
sub pcb1
{
    die "I'm dying...\n";
}

La correspondance entre le rappel C et son équivalent Perl est stockée dans la variable globale

an class="Li">"callback".

Ce sera suffisant si vous avez seulement besoin d'avoir un rappel enregistré à la fois. Un exemple pourrait être un gestionnaire d'erreurs comme le code esquissé ci-dessus. N'oubliez cependant pas que les appels répétés à "register_fatal" remplaceront la fonction de rappel précédemment enregistrée par la nouvelle.

Disons par exemple que vous souhaitez interagir avec une bibliothèque qui permet des opérations d'E/S de fichiers asynchrones. Dans ce cas, vous pourriez être en mesure d'enregistrer un rappel chaque fois qu'une opération de lecture est terminée. Pour être utile, nous voulons pouvoir appeler des sous-routines Perl distinctes pour chaque fichier ouvert. Tel quel, l'exemple du gestionnaire d'erreurs ci-dessus ne serait pas suffisant car il n'autorise qu'un seul rappel à être défini à la fois. Ce dont nous avons besoin, c'est d'un moyen de stocker la correspondance entre le fichier ouvert et la sous-routine Perl que nous voulons appeler pour ce fichier.

Supposons que la bibliothèque d'E/S ait une fonction "asynch_read" qui associe une fonction C "ProcessRead" à un descripteur de fichier "fh" - cela suppose qu'elle a également fourni une routine pour ouvrir le fichier et obtenir ainsi le descripteur de fichier.

asynch_read(fh, ProcessRead)

Cela peut attendre la fonction C ProcessRead de cette forme

void
ProcessRead(fh, buffer)
int fh;
char *      buffer;
{
     ...
}

Pour fournir une interface Perl à cette bibliothèque, nous devons pouvoir mapper entre le paramètre "fh" et la sous-routine Perl que nous voulons appeler. Une table de hachage est un mécanisme pratique pour stocker cette correspondance. Le code ci-dessous montre une implémentation possible

static HV * Mapping = (HV*)NULL;
void
asynch_read(fh, callback)
    int     fh
    SV *    callback
    CODE:
    /* Si la table de hachage n'existe pas déjà, créez-la */
    if (Mapping == (HV*)NULL)
        Mapping = newHV();
    /* Sauvegardez la correspondance fh -> callback */
    hv_store(Mapping, (char*)&fh, sizeof(fh), newSVsv(callback), 0);
    /* Enregistrez auprès de la bibliothèque C */
    asynch_read(fh, asynch_read_if);

et "asynch_read_if" pourrait ressembler à ceci

static void
asynch_read_if(fh, buffer)
int fh;
char *      buffer;
{
    dSP;
    SV ** sv;
    /* Obtenez le rappel associé à fh */
    sv =  hv_fetch(Mapping, (char*)&fh , sizeof(fh), FALSE);
    if (sv == (SV**)NULL)
        croak("Erreur interne...\n");
    PUSHMARK(SP);
    EXTEND(SP, 2);
    PUSHs(sv_2mortal(newSViv(fh)));
    PUSHs(sv_2mortal(newSVpv(buffer, 0)));
    PUTBACK;
    /* Appelez la sous-routine Perl */
    call_sv(*sv, G_DISCARD);
}

Pour être complet, voici "asynch_close". Ceci montre comment supprimer l'entrée de la table de hachage "Mapping".

void
asynch_close(fh)
    int     fh
    CODE:
    /* Supprimez l'entrée de la table de hachage */
    (void) hv_delete(Mapping, (char*)&fh, sizeof(fh), G_DISCARD);
    /* Appelez maintenant le vrai asynch_close */
    asynch_close(fh);

Donc, l'interface Perl ressemblerait à ceci

sub callback1
{
    my($handle, $buffer) = @_;
}
# Enregistrez le rappel Perl
asynch_read($fh, \&callback1);
asynch_close($fh);

La correspondance entre le rappel C et Perl est stockée dans la table de hachage globale "Mapping" cette fois-ci. L'utilisation d'une table de hachage présente l'avantage distinct de permettre un nombre illimité de rappels à enregistrer.

Et si l'interface fournie par le rappel C ne contient pas de paramètre qui permet le mappage du descripteur de fichier à la sous-routine Perl ? Disons dans le package d'E/S asynchrones, la fonction de rappel reçoit uniquement le paramètre "buffer" comme ceci

void
ProcessRead(buffer)
char *      buffer;
{
    ...
}

Sans le descripteur de fichier, il n'y a aucun moyen simple de mapper du rappel C à la sous-routine Perl.

Dans ce cas, une façon possible de contourner ce problème est de pré-définir une série de fonctions C pour servir d'interface à Perl, ainsi

#define MAX_CB              3
#define NULL_HANDLE -1
typedef void (*FnMap)();
struct MapStruct {
    FnMap    Function;
    SV *     PerlSub;
    int      Handle;
  };
static void  fn1();
static void  fn2();
static void  fn3();
static struct MapStruct Map [MAX_CB] =
    {
        { fn1, NULL, NULL_HANDLE },
        { fn2, NULL, NULL_HANDLE },
        { fn3, NULL, NULL_HANDLE }
    };
static void
Pcb(index, buffer)
int index;
char * buffer;
{
    dSP;
    PUSHMARK(SP);
    XPUSHs(sv_2mortal(newSVpv(buffer, 0)));
    PUTBACK;
    /* Appelez la sous-routine Perl */
    call_sv(Map[index].PerlSub, G_DISCARD);
}
static void
fn1(buffer)
char * buffer;
{
    Pcb(0, buffer);
}
static void
fn2(buffer)
char * buffer;
{
    Pcb(1, buffer);
}
static void
fn3(buffer)
char * buffer;
{
    Pcb(2, buffer);
}
void
array_asynch_read(fh, callback)
    int             fh
    SV *    callback
    CODE:
    int index;
    int null_index = MAX_CB;
    /* Trouvez le même descripteur ou une entrée vide */
    for (index = 0; index < MAX_CB; ++index)
    {
        if (Map[index].Handle == fh)
            break;
        if (Map[index].Handle == NULL_HANDLE)
            null_index = index;
    }
    if (index == MAX_CB && null_index == MAX_CB)
        croak ("Trop de fonctions de rappel enregistrées\n");
    if (index == MAX_CB)
        index = null_index;
    /* Sauvegardez le descripteur de fichier */
    Map[index].Handle = fh;
    /* Mémorisez la sous-routine Perl */
    if (Map[index].PerlSub == (SV*)NULL)
        Map[index].PerlSub = newSVsv(callback);
    else
        SvSetSV(Map[index].PerlSub, callback);
    asynch_read(fh, Map[index].Function);
void
array_asynch_close(fh)
    int     fh
    CODE:
    int index;
    /* Trouvez le descripteur de fichier */
    for (index = 0; index < MAX_CB; ++ index)
        if (Map[index].Handle == fh)
            break;
    if (index == MAX_CB)
        croak ("impossible de fermer fh %d\n", fh);
    Map[index].Handle = NULL_HANDLE;
    SvREFCNT_dec(Map[index].PerlSub);
    Map[index].PerlSub = (SV*)NULL;
    asynch_close(fh);

Dans ce cas, les fonctions "fn1", "fn2", et "fn3" sont utilisées pour mémoriser la sous-routine Perl à appeler. Chacune des fonctions contient un index codé en dur distinct qui est utilisé dans la fonction "Pcb" pour accéder au tableau "Map" et appeler effectivement la sous-routine Perl.

Il y a des inconvénients évidents à cette technique.

Premièrement, le code est considérablement plus complexe qu'avec l'exemple précédent.

Deuxièmement, il existe une limite codée en dur (ici 3) au nombre de rappels qui peuvent exister simultanément. La seule façon d'augmenter la limite est de modifier le code pour ajouter plus de fonctions, puis de recompiler. Néanmoins, tant que le nombre de fonctions est choisi avec soin, cela reste une solution viable et dans certains cas, la seule disponible.

Pour résumer, voici un certain nombre de méthodes possibles à considérer pour stocker la correspondance entre C et le rappel Perl

1. Ignorer le problème - Permettre un seul rappel
Pour de nombreuses situations, comme l'interface avec un gestionnaire d'erreurs, cela peut être une solution parfaitement adéquate.
2. Créer une séquence de rappels - limite codée en dur
S'il est impossible de déterminer à partir des paramètres renvoyés par le rappel C quel est le contexte, vous devrez peut-être créer une séquence de fonctions d'interface de rappel C, et stocker des pointeurs vers chacune dans un tableau.
3. Utiliser un paramètre pour mapper au rappel Perl
Une table de hachage est un mécanisme idéal pour stocker la correspondance entre C et Perl.

Manipulation Alternative de la Pile

Bien que j'aie utilisé uniquement les macros "POP*" pour accéder aux valeurs renvoyées par les sous-routines Perl, il est également possible de contourner ces macros et de lire la pile en utilisant la macro "ST" (Voir perlxs pour une description complète de la macro "ST").

La plupart du temps, les macros "POP*" devraient être suffisantes ; le principal problème avec elles est qu'elles vous obligent à traiter les valeurs renvoyées en séquence. Ce n'est peut-être pas la méthode la plus appropriée pour traiter les valeurs dans certains cas. Ce que nous voulons, c'est pouvoir accéder à la pile de manière aléatoire. La macro "ST", telle qu'utilisée lors du codage d'une XSUB, est idéale à cet effet.

Le code ci-dessous est l'exemple donné dans la section "Retourner une liste de valeurs" recodé pour utiliser "ST" au lieu de "POP*".

static void
call_AddSubtract2(a, b)
int a;
int b;
{
    dSP;
    I32 ax;
    int count;
    ENTER;
    SAVETMPS;
    PUSHMARK(SP);
    EXTEND(SP, 2);
    PUSHs(sv_2mortal(newSViv(a)));
    PUSHs(sv_2mortal(newSViv(b)));
    PUTBACK;
    count = call_pv("AddSubtract", G_LIST);
    SPAGAIN;
    SP -= count;
    ax = (SP - PL_stack_base) + 1;
    if (count != 2)
        croak("Gros problème\n");
    printf ("%d + %d = %d\n", a, b, SvIV(ST(0)));
    printf ("%d - %d = %d\n", a, b, SvIV(ST(1)));
    PUTBACK;
    FREETMPS;
    LEAVE;
}

Remarques

1.
Notez qu'il était nécessaire de définir la variable "ax". C'est parce que la macro "ST" s'attend à ce qu'elle existe. Si nous étions dans une XSUB, il ne serait pas nécessaire de définir "ax" car elle est déjà définie pour nous.
2.
Le code 
SPAGAIN;
SP -= count;
ax = (SP - PL_stack_base) + 1;

configure la pile de manière à pouvoir utiliser la macro "ST".

3.
Contrairement au codage original de cet exemple, les valeurs renvoyées ne sont pas accédées dans l'ordre inverse. Ainsi ST(0) fait référence à la première valeur renvoyée par la sous-routine Perl et ST(count-1) à la dernière.

Créer et Appeler une Sous-routine Anonyme en C

Comme nous l'avons déjà montré, "call_sv" peut être utilisé pour invoquer une sous-routine anonyme. Cependant, notre exemple montrait un script Perl invoquant une XSUB pour effectuer cette opération. Voyons comment cela peut être fait dans notre code C :

...
SV *cvrv
   = eval_pv("sub {
               print 'Vous ne me trouverez pas à encombrer d\'espace de noms !'
              }", TRUE);
...
call_sv(cvrv, G_VOID|G_NOARGS);

"eval_pv" est utilisé pour compiler la sous-routine anonyme, qui sera également la valeur de retour (lisez-en plus sur i">"eval_pv" dans "eval_pv" dans perlapi). Une fois cette référence de code en main, elle peut être combinée avec tous les exemples précédents que nous avons montrés.

CALLBACKS LÉGERS

Parfois, vous devez invoquer la même sous-routine de manière répétée. Cela se produit généralement avec une fonction qui agit sur une liste de valeurs, comme la fonction intégrée de Perl sort(). Vous pouvez passer une fonction de comparaison à sort(), qui sera alors invoquée pour chaque paire de valeurs qui doit être comparée. Les fonctions first() et reduce() de List::Util suivent un schéma similaire.

Dans ce cas, il est possible d'accélérer la routine (souvent de manière substantielle) en utilisant l'API de rappel léger. L'idée est que le contexte d'appel ne doit être créé et détruit qu'une seule fois, et que la sous-routine peut être appelée arbitrairement de nombreuses fois entre les deux.

Il est d'usage de passer des paramètres en utilisant des variables globales (typiquement $_ pour un paramètre, ou $a et $b pour deux paramètres) plutôt que via @_. (Il est possible d'utiliser le mécanisme @_ si vous savez ce que vous faites, bien qu'il n'y ait pas encore d'API prise en charge pour cela. C'est aussi intrinsèquement plus lent.)

Le schéma des appels de macro est le suivant :

dMULTICALL;                 /* Déclarer les variables locales */
U8 gimme = G_SCALAR;        /* contexte de l'appel : G_SCALAR,
                             * G_LIST, ou G_VOID */
PUSH_MULTICALL(cv);         /* Configurer le contexte pour l'appel de cv,
                               et définir les variables locales en conséquence */
/* boucle */ {
    /* définir la ou les valeurs de vos variables paramètres */
    MULTICALL;              /* Effectuer l'appel réel */
} /* fin de la boucle */
POP_MULTICALL;              /* Démonter le contexte d'appel */

Pour des exemples concrets, voir l'implémentation des fonctions first() et reduce() de List::Util 1.18. Vous y trouverez également un fichier d'en-tête qui émule l'API multicall sur les anciennes versions de perl.
