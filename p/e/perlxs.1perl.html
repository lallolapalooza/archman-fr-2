NOM

perlxs - manuel de référence du langage XS

DESCRIPTION

Introduction

XS est un format de fichier de description d'interface utilisé pour créer une interface d'extension entre Perl et du code C (ou une bibliothèque C) que l'on souhaite utiliser avec Perl. L'interface XS est combinée à la bibliothèque pour créer une nouvelle bibliothèque qui peut ensuite être chargée dynamiquement ou liée statiquement à perl. La description de l'interface XS est écrite dans le langage XS et constitue le composant central de l'interface d'extension Perl.

Ce document décrit le langage XS, mais il est important de noter d'abord que le code XS a un accès complet aux appels système, y compris les fonctions de la bibliothèque C. Il a donc la capacité d'interférer avec ce que le cœur de Perl ou d'autres modules ont mis en place, tels que les gestionnaires de signaux ou les descripteurs de fichiers. Il pourrait perturber la mémoire, ou un nombre quelconque de choses nuisibles. Ne le faites pas. Plus de détails sont dans perlclib, que vous devriez lire avant d'écrire réellement du code XS de production.

Un XSUB forme l'unité de base de l'interface XS. Après compilation par le compilateur xsubpp, chaque XSUB correspond à une définition de fonction C qui fournira le pont entre les conventions d'appel Perl et les conventions d'appel C.

Le code de pontage extrait les arguments de la pile Perl, convertit ces valeurs Perl dans les formats attendus par une fonction C, appelle cette fonction C, puis transfère les valeurs de retour de la fonction C à Perl. Les valeurs de retour peuvent ici être une valeur de retour C conventionnelle ou des arguments de fonction C qui peuvent servir de paramètres de sortie. Ces valeurs de retour peuvent être renvoyées à Perl soit en les plaçant sur la pile Perl, soit en modifiant les arguments fournis du côté Perl.

Ce qui précède est une vue quelque peu simplifiée de ce qui se passe réellement. Comme Perl permet des conventions d'appel plus flexibles que C, les XSUB peuvent faire beaucoup plus en pratique, comme vérifier la validité des paramètres d'entrée, lancer des exceptions (ou retourner undef/liste vide) si la valeur de retour de la fonction C indique un échec, appeler différentes fonctions C en fonction du nombre et des types des arguments, fournir une interface orientée objet, etc.

Bien sûr, on pourrait écrire un tel code de pontage directement en C. Cependant, ce serait une tâche fastidieuse, surtout si l'on doit écrire du code de pontage pour plusieurs fonctions C, et/ou si l'on n'est pas suffisamment familiarisé avec la discipline de la pile Perl et d'autres arcanes similaires. XS vient à la rescousse ici : au lieu d'écrire ce code de pontage C en langage long, on peut écrire un description plus concise et abrégée de ce qui doit être fait par le pontage, et laisser le compilateur XS xsubpp s'occuper du reste.

Le langage XS permet de décrire le mappage entre la manière dont la routine C est utilisée et la manière dont la routine Perl correspondante est utilisée. Il permet également la création de routines Perl qui sont directement traduites en code C et qui ne sont pas liées à une fonction C préexistante. Dans les cas où l'interface C coïncide avec l'interface Perl, la déclaration XS est presque identique à une déclaration de fonction C (style K&R). Dans de telles circonstances, il existe un autre outil appelé "h2xs" qui est capable de traduire un fichier d'en-tête C entier en un fichier XS correspondant qui fournira un pont vers les fonctions/macros décrites dans le fichier d'en-tête.

Le compilateur XS s'appelle xsubpp. Ce compilateur crée les constructions nécessaires pour permettre à un XSUB de manipuler les valeurs Perl, et crée le pontage nécessaire pour permettre à Perl d'appeler le XSUB. Le compilateur utilise des typemaps pour déterminer comment mapper les paramètres de fonction C et les valeurs de sortie aux valeurs Perl et vice versa. Le typemap par défaut (qui est fourni avec Perl) gère de nombreux types C courants. Un typemap supplémentaire peut également être nécessaire pour gérer les structures et types spéciaux de la bibliothèque liée. Pour plus d'informations sur les typemaps, voir perlxstypemap.

Un fichier au format XS commence par une section de langage C qui se poursuit jusqu'à la première directive "MODULE =". D'autres directives XS et définitions XSUB peuvent suivre cette ligne. Le "langage" utilisé dans cette partie du fichier est généralement appelé langage XS. xsubpp reconnaît et ignore le POD (voir perlpod) dans les sections de langage C et XS, ce qui permet au fichier XS de contenir de la documentation intégrée.

Voir perlxstut pour un tutoriel sur l'ensemble du processus de création d'extension.

Note : Pour certaines extensions, le système SWIG de Dave Beazley peut fournir un mécanisme significativement plus pratique pour créer le code de pontage d'extension. Voir http://www.swig.org/ pour plus d'informations.

Pour des liaisons simples à des bibliothèques C ainsi qu'à d'autres bibliothèques de code machine, envisagez plutôt d'utiliser l'interface libffi beaucoup plus simple http://sourceware.org/libffi/ via des modules CPAN tels que FFI::Platypus ou FFI::Raw.

En route

De nombreux exemples suivants se concentreront sur la création d'une interface entre Perl et les fonctions de liaison de bibliothèques ONC+ RPC. La fonction rpcb_gettime() est utilisée pour démontrer de nombreuses fonctionnalités du langage XS. Cette fonction a deux paramètres ; le premier est un paramètre d'entrée et le second est un paramètre de sortie. La fonction retourne également une valeur de statut.

bool_t rpcb_gettime(const char *host, time_t *timep);

Depuis C, cette fonction sera appelée avec les instructions suivantes.

#include <rpc/rpc.h>
bool_t status;
time_t timep;
status = rpcb_gettime( "localhost", &timep );

Si un XSUB est créé pour offrir une traduction directe entre cette fonction et Perl, alors ce XSUB sera utilisé depuis Perl avec le code suivant. Les variables $status et $timep contiendront la sortie de la fonction.

use RPC;
$status = rpcb_gettime( "localhost", $timep );

Le fichier XS suivant montre une sous-routine XS, ou XSUB, qui démontre une interface possible à la fonction rpcb_gettime(). Cet XSUB représente une traduction directe entre C et Perl et préserve ainsi l'interface même depuis Perl. Cet XSUB sera invoqué depuis Perl avec l'utilisation montrée ci-dessus. Notez que les trois premières instructions #include, pour "EXTERN.h", "perl.h", et "XSUB.h", seront toujours présentes au début d'un fichier XS. Cette approche et d'autres seront développées plus tard dans ce document. Un #define pour "PERL_NO_GET_CONTEXT" devrait être présent pour récupérer le contexte de l'interpréteur plus efficacement, voir perlguts pour plus de détails.

#define PERL_NO_GET_CONTEXT
#include "EXTERN.h"
#include "perl.h"
#include "XSUB.h"
#include <rpc/rpc.h>
MODULE = RPC  PACKAGE = RPC
bool_t
rpcb_gettime(host,timep)
     char *host
     time_t &timep
   OUTPUT:
     timep

Toute extension à Perl, y compris celles contenant des XSUBs, devrait avoir un module Perl pour servir de bootstrap qui intègre l'extension à Perl. Ce module exportera les fonctions et variables de l'extension au programme Perl et provoquera la liaison des XSUBs de l'extension à Perl. Le module suivant sera utilisé pour la plupart des exemples de ce document et devrait être utilisé depuis Perl avec la commande "use" comme indiqué précédemment. Les modules Perl sont expliqués plus en détail plus loin dans ce document.

package RPC;
require Exporter;
require DynaLoader;
@ISA = qw(Exporter DynaLoader);
@EXPORT = qw( rpcb_gettime );
bootstrap RPC;
1;

Tout au long de ce document, une variété d'interfaces à l'XSUB rpcb_gettime() seront explorées. Les XSUBs prendront leurs paramètres dans des ordres différents ou prendront un nombre différent de paramètres. Dans chaque cas, l'XSUB est une abstraction entre Perl et la vraie fonction C rpcb_gettime(), et l'XSUB doit toujours s'assurer que la vraie fonction rpcb_gettime() est appelée avec les bons paramètres. Cette abstraction permettra au programmeur de créer une interface plus "Perl-like" à la fonction C.

L'anatomie d'un XSUB

Les XSUBs les plus simples se composent de 3 parties : une description de la valeur de retour, le nom de la routine XSUB et les noms de ses arguments, et une description des types ou formats des arguments.

Les XSUBs plus compliqués peuvent contenir de nombreuses autres sections. Chaque section d'un XSUB commence par le mot-clé correspondant, comme INIT: ou CLEANUP:. Cependant, les deux premières lignes d'un XSUB contiennent toujours les mêmes données : descriptions du type de retour et des noms de la fonction et de ses paramètres. Tout ce qui suit immédiatement est considéré comme une section INPUT: à moins qu'il ne soit explicitement marqué avec un autre mot-clé. (Voir "Le mot-clé INPUT:".)

Une section XSUB continue jusqu'à ce qu'un autre mot-clé de début de section soit trouvé.

La Pile d'arguments

La pile d'arguments Perl est utilisée pour stocker les valeurs qui sont envoyées comme paramètres au XSUB et pour stocker le(s) valeur(s) de retour du XSUB. En réalité, toutes les fonctions Perl (y compris celles qui ne sont pas des XSUBs) conservent leurs valeurs sur cette pile en permanence, chacune étant limitée à sa propre plage de positions sur la pile. Dans ce document, la première position sur cette pile qui appartient à la fonction active sera appelée position 0 pour cette fonction.

Les XSUBs font référence à leurs arguments de pile avec la macro ST(x), où x fait référence à une position dans la partie XSUB de la pile. La position 0 pour cette fonction serait connue du XSUB sous le nom de ST(0). Les paramètres entrants et les valeurs de retour sortantes du XSUB commencent toujours à ST(0). Pour de nombreux cas simples, le compilateur xsubpp générera le code nécessaire pour gérer la pile d'arguments en intégrant des fragments de code trouvés dans les typemaps. Dans les cas plus complexes, le programmeur doit fournir le code.

La Variable RETVAL

La variable RETVAL est une variable C spéciale qui est déclarée automatiquement pour vous. Le type C de RETVAL correspond au type de retour de la fonction de bibliothèque C. Le compilateur xsubpp déclarera cette variable dans chaque XSUB avec un type de retour non-"void". Par défaut, la fonction C générée utilisera RETVAL pour contenir la valeur de retour de la fonction de bibliothèque C appelée. Dans les cas simples, la valeur de RETVAL sera placée dans ST(0) de la pile d'arguments où elle pourra être reçue par Perl en tant que valeur de retour du XSUB.

Si le XSUB a un type de retour "void", le compilateur ne déclarera pas de variable RETVAL pour cette fonction. Lors de l'utilisation d'une section PPCODE: aucune manipulation de la variable RETVAL n'est requise, la section peut utiliser une manipulation directe de la pile pour placer les valeurs de sortie sur la pile.

Si la directive PPCODE: n'est pas utilisée, une valeur de retour "void" ne doit être utilisée que pour les sous-routines qui ne retournent aucune valeur, même si la directive CODE: est utilisée, ce qui définit explicitement ST(0).

Les anciennes versions de ce document recommandaient d'utiliser une valeur de retour "void" dans de tels cas. Il a été découvert que cela pouvait entraîner des segfaults dans les cas où le XSUB était vraiment "void". Cette pratique est maintenant dépréciée et pourrait ne pas être prise en charge dans une future version. Utilisez la valeur de retour "SV *" dans de tels cas. (Actuellement, "xsubpp" contient un code heuristique qui tente de distinguer les fonctions "vraiment-void" des fonctions "ancienne pratique déclarées comme void". Votre code est donc à la merci de cette heuristique, sauf si vous utilisez "SV *" comme valeur de retour.)

Retourner des SVs, des AVs et des HVs via RETVAL

Lorsque vous utilisez RETVAL pour retourner un "SV *", une magie s'opère en coulisses qui doit être mentionnée. Lorsque vous manipulez la pile d'arguments en utilisant la macro ST(x), par exemple, vous devez généralement porter une attention particulière aux décomptes de références. (Pour en savoir plus sur les décomptes de références, voir perlguts.) Pour vous faciliter la vie, le fichier typemap rend automatiquement "RETVAL" mortel lorsque vous retournez un "SV *". Ainsi, les deux XSUBs suivants sont plus ou moins équivalents :

void
alpha()
    PPCODE:
        ST(0) = newSVpv("Hello World",0);
        sv_2mortal(ST(0));
        XSRETURN(1);
SV *
beta()
    CODE:
        RETVAL = newSVpv("Hello World",0);
    OUTPUT:
        RETVAL

C'est très utile car cela améliore généralement la lisibilité. Bien que cela fonctionne bien pour un "SV *", il n'est malheureusement pas aussi facile d'avoir un "AV *" ou un "HV *" comme valeur de retour. Vous devriez pouvoir écrire :

AV *
array()
    CODE:
        RETVAL = newAV();
        /* faire quelque chose avec RETVAL */
    OUTPUT:
        RETVAL

Mais en raison d'un bug irréparable (sa correction casserait de nombreux modules CPAN existants) dans le fichier typemap, le décompte de références de l'"AV *" n'est pas correctement décrémenté. Ainsi, le XSUB ci-dessus fuirait de la mémoire chaque fois qu'il est appelé. Le même problème existe pour "HV *", "CV *", et "SVREF" (qui indique une référence scalaire, pas un "SV *" général). Dans le code XS des perls à partir de la version 5.16, vous pouvez remplacer les typemaps pour l'un de ces types par une version qui gère correctement les décomptes de références. Dans votre section "TYPEMAP", faites :

AV*   T_AVREF_REFCOUNT_FIXED

pour obtenir la variante réparée. Pour la compatibilité ascendante avec les anciennes versions de perl, vous pouvez plutôt décrémenter manuellement le décompte de références lorsque vous retournez l'un des types susmentionnés en utilisant "sv_2mortal" :

AV *
array()
    CODE:
        RETVAL = newAV();
        sv_2mortal((SV*)RETVAL);
        /* faire quelque chose avec RETVAL */
    OUTPUT:
        RETVAL

N'oubliez pas que vous n'avez pas à faire cela pour un "SV *". La documentation de référence de tous les typemaps de base se trouve dans perlxstypemap.

Le Mot-clé MODULE

Le mot-clé MODULE est utilisé pour démarrer le code XS et pour spécifier le package des fonctions qui sont définies. Tout texte précédant le premier mot-clé MODULE est considéré comme du code C et est transmis à la sortie avec le POD supprimé, mais sinon intact. Chaque module XS aura une fonction de bootstrap utilisée pour accrocher les XSUBs à Perl. Le nom du package de cette fonction de bootstrap correspondra à la valeur de la dernière instruction MODULE dans les fichiers source XS. La valeur de MODULE doit toujours rester constante au sein du même fichier XS, bien que cela ne soit pas requis.

L'exemple suivant démarrera le code XS et placera toutes les fonctions dans un package nommé RPC.

MODULE = RPC

Le Mot-clé PACKAGE

Lorsque les fonctions au sein d'un fichier source XS doivent être séparées en packages, le mot-clé PACKAGE doit être utilisé. Ce mot-clé est utilisé avec le mot-clé MODULE et doit le suivre immédiatement lorsqu'il est utilisé.

MODULE = RPC  PACKAGE = RPC
[ Code XS dans le package RPC ]
MODULE = RPC  PACKAGE = RPCB
[ Code XS dans le package RPCB ]
MODULE = RPC  PACKAGE = RPC
[ Code XS dans le package RPC ]

Le même nom de package peut être utilisé plusieurs fois, permettant un code non contigu. Ceci est utile si vous avez un principe d'ordonnancement plus fort que les noms de package.

Bien que ce mot-clé soit facultatif et fournisse dans certains cas des informations redondantes, il doit toujours être utilisé. Ce mot-clé garantira que les XSUBs apparaissent dans le package souhaité.

Le Mot-clé PREFIX

Le mot-clé PREFIX désigne les préfixes qui doivent être supprimés des noms de fonctions Perl. Si la fonction C est rpcb_gettime() et que la valeur de PREFIX est "rpcb_", alors Perl verra cette fonction comme gettime().

Ce mot-clé doit suivre le mot-clé PACKAGE lorsqu'il est utilisé. Si PACKAGE n'est pas utilisé, alors PREFIX doit suivre le mot-clé MODULE.

MODULE = RPC  PREFIX = rpc_
MODULE = RPC  PACKAGE = RPCB  PREFIX = rpcb_

Pour les fonctions simples qui n'ont pas de section CODE: ou PPCODE:, comme la fonction sin() ci-dessus, la variable RETVAL est automatiquement désignée comme valeur de sortie. Dans de tels cas, pour forcer une variable supplémentaire à être déclarée en même temps que les déclarations d'autres variables, placez la déclaration dans une section PREINIT:. Le mot-clé PREINIT: peut être utilisé une ou plusieurs fois dans un XSUB.

Les exemples suivants sont équivalents, mais si le code utilise des typemaps complexes, le premier exemple est plus sûr.

bool_t
rpcb_gettime(timep)
     time_t timep = NO_INIT
   PREINIT:
     char *host = "localhost";
   CODE:
     RETVAL = rpcb_gettime( host, &timep );
   OUTPUT:
     timep
     RETVAL

Pour ce cas particulier, un mot-clé INIT: générerait le même code C que le mot-clé PREINIT:. Un autre exemple correct, mais sujet aux erreurs :

bool_t
rpcb_gettime(timep)
     time_t timep = NO_INIT
   CODE:
     char *host = "localhost";
     RETVAL = rpcb_gettime( host, &timep );
   OUTPUT:
     timep
     RETVAL

Une autre façon de déclarer "host" est d'utiliser un bloc C dans la section CODE: :

bool_t
rpcb_gettime(timep)
     time_t timep = NO_INIT
   CODE:
     {
       char *host = "localhost";
       RETVAL = rpcb_gettime( host, &timep );
     }
   OUTPUT:
     timep
     RETVAL

La capacité de placer des déclarations supplémentaires avant que les entrées typemap ne soient traitées est très utile dans les cas où les conversions typemap manipulent un état global :

MyObject
mutate(o)
    PREINIT:
        MyState st = global_state;
    INPUT:
        MyObject o;
    CLEANUP:
        reset_to(global_state, st);

Ici, nous supposons que la conversion vers "MyObject" dans la section INPUT: et depuis MyObject lors du traitement de RETVAL modifiera une variable globale "global_state". Une fois ces conversions effectuées, nous restaurons l'ancienne valeur de "global_state" (pour éviter les fuites de mémoire, par exemple).

Il existe une autre façon d'échanger clarté contre compacité : les sections INPUT: permettent la déclaration de variables C qui n'apparaissent pas dans la liste des paramètres d'une sous-routine. Ainsi, le code ci-dessus pour mutate() peut être réécrit comme suit :

MyObject
mutate(o)
      MyState st = global_state;
      MyObject o;
    CLEANUP:
      reset_to(global_state, st);

et le code pour rpcb_gettime() peut être réécrit comme suit :

bool_t
rpcb_gettime(timep)
     time_t timep = NO_INIT
     char *host = "localhost";
   C_ARGS:
     host, &timep
   OUTPUT:
     timep
     RETVAL

Le mot-clé SCOPE:

Le mot-clé SCOPE: permet d'activer la portée pour un XSUB particulier. Si activé, le XSUB invoquera ENTER et LEAVE automatiquement.

Pour supporter des mappages de types potentiellement complexes, si une entrée typemap utilisée par un XSUB contient un commentaire comme "/*scope*/", alors la portée sera automatiquement activée pour ce XSUB.

Pour activer la portée :

SCOPE: ENABLE

Pour désactiver la portée :

SCOPE: DISABLE

Le mot-clé INPUT:

Les paramètres du XSUB sont généralement évalués immédiatement après l'entrée dans le XSUB. Le mot-clé INPUT: peut être utilisé pour forcer l'évaluation de ces paramètres un peu plus tard. Le mot-clé INPUT: peut être utilisé plusieurs fois dans un XSUB et peut être utilisé pour lister une ou plusieurs variables d'entrée. Ce mot-clé est utilisé avec le mot-clé PREINIT:.

L'exemple suivant montre comment le paramètre d'entrée "timep" peut être évalué tardivement, après un PREINIT.

bool_t
rpcb_gettime(host,timep)
      char *host
    PREINIT:
      time_t tt;
    INPUT:
      time_t timep
    CODE:
           RETVAL = rpcb_gettime( host, &tt );
           timep = tt;
    OUTPUT:
      timep
      RETVAL

L'exemple suivant montre chaque paramètre d'entrée évalué tardivement.

bool_t
rpcb_gettime(host,timep)
    PREINIT:
      time_t tt;
    INPUT:
      char *host
    PREINIT:
      char *h;
    INPUT:
      time_t timep
    CODE:
           h = host;
           RETVAL = rpcb_gettime( h, &tt );
           timep = tt;
    OUTPUT:
      timep
      RETVAL

Étant donné que les sections INPUT permettent la déclaration de variables C qui n'apparaissent pas dans la liste des paramètres d'une sous-routine, cela peut être raccourci à :

bool_t
rpcb_gettime(host,timep)
      time_t tt;
      char *host;
      char *h = host;
      time_t timep;
    CODE:
      RETVAL = rpcb_gettime( h, &tt );
      timep = tt;
    OUTPUT:
      timep
      RETVAL

(Nous avons utilisé notre connaissance que la conversion d'entrée pour "char *" est "simple", donc "host" est initialisé sur la ligne de déclaration, et notre affectation "h = host" n'est pas effectuée trop tôt. Sinon, il faudrait avoir l'affectation "h = host" dans une section CODE: ou INIT:.)

Les mots-clés IN/OUTLIST/IN_OUTLIST/OUT/IN_OUT

Dans la liste des paramètres d'un XSUB, on peut précéder les noms de paramètres par les mots-clés "IN"/"OUTLIST"/"IN_OUTLIST"/"OUT"/"IN_OUT". Le mot-clé "IN" est par défaut, les autres mots-clés indiquent comment l'interface Perl doit différer de l'interface C.

Les paramètres précédés des mots-clés "OUTLIST"/"IN_OUTLIST"/"OUT"/"IN_OUT" sont considérés comme étant utilisés par la sous-routine C *via* des *pointeurs*. Les mots-clés "OUTLIST"/"OUT" indiquent que la sous-routine C n'inspecte pas la mémoire pointée par ce paramètre, mais écrira à travers ce pointeur pour fournir des valeurs de retour supplémentaires.

Les paramètres précédés du mot-clé "OUTLIST" n'apparaissent pas dans la signature d'utilisation de la fonction Perl générée.

Les paramètres précédés des mots-clés "IN_OUTLIST"/"IN_OUT"/"OUT" apparaissent *bien* en tant que paramètres de la fonction Perl. À l'exception des paramètres "OUT", ces paramètres sont convertis vers le type C correspondant, puis des pointeurs vers ces données sont donnés en arguments à la fonction C. Il est attendu que la fonction C écrive à travers ces pointeurs.

La liste de retour de la fonction Perl générée se compose de la valeur de retour C de la fonction (sauf si le XSUB est de type retour "void" ou si "Le mot-clé NO_OUTPUT" a été utilisé) suivie de tous les paramètres "OUTLIST" et "IN_OUTLIST" (dans l'ordre d'apparition). Au retour du XSUB, le paramètre Perl "IN_OUT"/"OUT" sera modifié pour avoir les valeurs écrites par la fonction C.

Par exemple, un XSUB

void
day_month(OUTLIST day, IN unix_time, OUTLIST month)
  int day
  int unix_time
  int month

doit être utilisé depuis Perl comme

my ($day, $month) = day_month(time);

La signature C de la fonction correspondante devrait être

void day_month(int *day, int unix_time, int *month);

Les mots-clés "IN"/"OUTLIST"/"IN_OUTLIST"/"IN_OUT"/"OUT" peuvent être mélangés avec des déclarations de style ANSI, comme dans

void
day_month(OUTLIST int day, int unix_time, OUTLIST int month)

(ici le mot-clé optionnel "IN" est omis).

Les paramètres "IN_OUT" sont identiques aux paramètres introduits par "L'opérateur unaire &" et placés dans la section "OUTPUT:" (voir "Le mot-clé OUTPUT:"). Les paramètres "IN_OUTLIST" sont très similaires, la seule différence étant que la valeur que la fonction C écrit à travers le pointeur ne modifierait pas le paramètre Perl, mais serait placée dans la liste de sortie.

Les paramètres "OUTLIST"/"OUT" diffèrent des paramètres "IN_OUTLIST"/"IN_OUT" uniquement par la valeur initiale du paramètre Perl qui n'est pas lue (et n'est pas transmise à la fonction C, qui reçoit des déchets à la place). Par exemple, la même fonction C peut être interfacée comme suit :

void day_month(OUT int day, int unix_time, OUT int month);

ou

void
day_month(day, unix_time, month)
    int &day = NO_INIT
    int  unix_time
    int &month = NO_INIT
  OUTPUT:
    day
    month

Cependant, la fonction Perl générée est appelée dans un style très C :

my ($day, $month);
day_month($day, time, $month);

Le mot-clé length(NAME)

Si l'un des arguments d'entrée de la fonction C est la longueur d'un argument chaîne "NAME", on peut substituer le nom de l'argument de longueur par length(NAME) dans la déclaration XSUB. Cet argument doit être omis lors de l'appel de la fonction Perl générée. Par exemple :

void
dump_chars(char *s, short l)
{
  short n = 0;
  while (n < l) {
      printf("s[%d] = \"\\%#03o\"\n", n, (int)s[n]);
      n++;
  }
}
MODULE = x            PACKAGE = x
void dump_chars(char *s, short length(s))

doit être appelé comme dump_chars($string).

Cette directive est supportée avec les déclarations de fonction de type ANSI uniquement.

Listes de paramètres de longueur variable

Les XSUB peuvent avoir des listes de paramètres de longueur variable en spécifiant des points de suspension "(...)" dans la liste des paramètres. Cette utilisation des points de suspension est similaire à celle trouvée dans ANSI C. Le programmeur peut déterminer le nombre d'arguments passés à l'XSUB en examinant la variable "items" que le compilateur xsubpp fournit pour tous les XSUB. En utilisant ce mécanisme, on peut créer un XSUB qui accepte une liste de paramètres de longueur inconnue.

Le paramètre host pour l'XSUB rpcb_gettime() peut être facultatif, de sorte que les points de suspension peuvent être utilisés pour indiquer que l'XSUB prendra un nombre variable de paramètres. Perl devrait pouvoir appeler cet XSUB avec l'une des instructions suivantes.

 $status = rpcb_gettime( $timep, $host );
 $status = rpcb_gettime( $timep );

Le code XS, avec les points de suspension, suit.

bool_t
 rpcb_gettime(timep, ...)
      time_t timep = NO_INIT
    PREINIT:
      char *host = "localhost";
    CODE:
      if( items > 1 )
           host = (char *)SvPVbyte_nolen(ST(1));
      RETVAL = rpcb_gettime( host, &timep );
    OUTPUT:
      timep
      RETVAL

Le mot-clé C_ARGS:

Le mot-clé C_ARGS: permet de créer des XSUB qui ont une séquence d'appel différente de Perl par rapport à C, sans avoir besoin d'écrire une section CODE: ou PPCODE:. Le contenu du paragraphe C_ARGS: est placé comme argument de la fonction C appelée sans aucune modification.

Par exemple, supposons qu'une fonction C soit déclarée comme

symbolic nth_derivative(int n, symbolic function, int flags);

et que les drapeaux par défaut soient conservés dans une variable C globale "default_flags". Supposons que vous souhaitiez créer une interface appelée comme

 $second_deriv = $function->nth_derivative(2);

Pour ce faire, déclarez l'XSUB comme suit :

symbolic
 nth_derivative(function, n)
     symbolic        function
     int             n
   C_ARGS:
     n, function, default_flags

Le mot-clé PPCODE:

Le mot-clé PPCODE: est une forme alternative du mot-clé CODE: et est utilisé pour indiquer au compilateur xsubpp que le programmeur fournit le code pour contrôler la pile d'arguments pour les valeurs de retour des XSUB. Parfois, on souhaite qu'un XSUB retourne une liste de valeurs plutôt qu'une seule valeur. Dans ces cas, il faut utiliser PPCODE: puis explicitement empiler la liste des valeurs sur la pile. Les mots-clés PPCODE: et CODE: ne doivent pas être utilisés ensemble dans le même XSUB.

La différence réelle entre les sections PPCODE: et CODE: réside dans l'initialisation de la macro "SP" (qui représente le pointeur de pile Perl actuel) et dans la gestion des données sur la pile lors du retour d'un XSUB. Dans les sections CODE:, SP conserve la valeur qui était présente à l'entrée de l'XSUB : SP se trouve sur le pointeur de fonction (qui suit le dernier paramètre). Dans les sections PPCODE:, SP est déplacé vers le début de la liste des paramètres, ce qui permet aux macros "PUSH*()" de placer les valeurs de sortie à l'endroit où Perl s'attend à les trouver lorsque l'XSUB retourne à Perl.

La bande-annonce générée pour une section CODE: garantit que le nombre de valeurs de retour que Perl verra est de 0 ou 1 (en fonction de la valeur "void" du retour de la fonction C et des heuristiques mentionnées dans "La variable RETVAL"). La bande-annonce générée pour une section PPCODE: est basée sur le nombre de valeurs de retour et sur le nombre de fois où "SP" a été mis à jour par les macros "[X]PUSH*()".

Notez que les macros ST(i), "XST_m*()" et "XSRETURN*()" fonctionnent de la même manière dans les sections CODE: et PPCODE:.

Le XSUB suivant appellera la fonction C rpcb_gettime() et retournera ses deux valeurs de sortie, timep et status, à Perl sous forme d'une seule liste.

void
 rpcb_gettime(host)
      char *host
    PREINIT:
      time_t  timep;
      bool_t  status;
    PPCODE:
      status = rpcb_gettime( host, &timep );
      EXTEND(SP, 2);
      PUSHs(sv_2mortal(newSViv(status)));
      PUSHs(sv_2mortal(newSViv(timep)));

Notez que le programmeur doit fournir le code C nécessaire pour que la vraie fonction rpcb_gettime() soit appelée et que les valeurs de retour soient correctement placées sur la pile d'arguments.

Le type de retour "void" pour cette fonction indique au compilateur xsubpp que la variable RETVAL n'est pas nécessaire ou utilisée et qu'elle ne doit pas être créée. Dans la plupart des cas, le type de retour void doit être utilisé avec la directive PPCODE:.

La macro EXTEND() est utilisée pour faire de la place sur la pile d'arguments pour 2 valeurs de retour. La directive PPCODE: fait que le compilateur xsubpp crée un pointeur de pile disponible sous le nom "SP", et c'est ce pointeur qui est utilisé dans la macro EXTEND(). Les valeurs sont ensuite empilées sur la pile avec la macro PUSHs().

Maintenant, la fonction rpcb_gettime() peut être utilisée depuis Perl avec l'instruction suivante.

 ($status, $timep) = rpcb_gettime("localhost");

Lors du traitement des paramètres de sortie avec une section PPCODE, assurez-vous de gérer correctement la magie de 'set'. Voir perlguts pour plus de détails sur la magie de 'set'.

Retourner undef et des listes vides

Parfois, le programmeur voudra simplement retourner "undef" ou une liste vide en cas d'échec de la fonction, plutôt qu'une valeur de statut séparée. La fonction rpcb_gettime() offre justement cette situation. Si la fonction réussit, nous aimerions qu'elle retourne l'heure et si elle échoue, nous aimerions qu'elle retourne undef. Dans le code Perl suivant, la valeur de $timep sera soit undef, soit une heure valide.

 $timep = rpcb_gettime( "localhost" );

Le XSUB suivant utilise le type de retour "SV *" comme simple aide-mémoire, et utilise un bloc CODE: pour indiquer au compilateur que le programmeur a fourni tout le code nécessaire. L'appel sv_newmortal() initialisera la valeur de retour à undef, en faisant la valeur de retour par défaut.

SV *
 rpcb_gettime(host)
      char *  host
    PREINIT:
      time_t  timep;
      bool_t x;
    CODE:
      ST(0) = sv_newmortal();
      if( rpcb_gettime( host, &timep ) )
           sv_setnv( ST(0), (double)timep);

L'exemple suivant montre comment placer un undef explicite dans la valeur de retour, si le besoin s'en fait sentir.

SV *
 rpcb_gettime(host)
      char *  host
    PREINIT:
      time_t  timep;
      bool_t x;
    CODE:
      if( rpcb_gettime( host, &timep ) ){
           ST(0) = sv_newmortal();
           sv_setnv( ST(0), (double)timep);
      }
      else{
           ST(0) = &PL_sv_undef;
      }

Pour retourner une liste vide, il faut utiliser un bloc PPCODE: et ensuite ne pas empiler de valeurs de retour sur la pile.

void
 rpcb_gettime(host)
      char *host
    PREINIT:
      time_t  timep;
    PPCODE:
      if( rpcb_gettime( host, &timep ) )
           PUSHs(sv_2mortal(newSViv(timep)));
      else{
          /* Rien n'est empilé sur la pile, donc une liste
           * vide est implicitement retournée. */
      }

Certains pourraient être tentés d'inclure un "return" explicite dans le XSUB ci-dessus, plutôt que de laisser le contrôle tomber à la fin. Dans ces situations, il faut utiliser "XSRETURN_EMPTY" à la place. Cela garantira que la pile de l'XSUB est correctement ajustée. Consultez perlapi pour d'autres macros "XSRETURN".

Étant donné que les macros "XSRETURN_*" peuvent également être utilisées avec des blocs CODE, on peut réécrire cet exemple comme suit :

int
 rpcb_gettime(host)
      char *host
    PREINIT:
      time_t  timep;
    CODE:
      RETVAL = rpcb_gettime( host, &timep );
      if (RETVAL == 0)
            XSRETURN_UNDEF;
    OUTPUT:
      RETVAL

En fait, on peut également placer cette vérification dans une section POSTCALL:. Associé aux simplifications de PREINIT:, cela donne :

int
 rpcb_gettime(host)
      char *host
      time_t  timep;
    POSTCALL:
      if (RETVAL == 0)
            XSRETURN_UNDEF;

Le mot-clé REQUIRE:

Le mot-clé REQUIRE: est utilisé pour indiquer la version minimale du compilateur xsubpp nécessaire pour compiler le module XS. Un module XS contenant l'instruction suivante compilera uniquement avec xsubpp version 1.922 ou supérieure :

REQUIRE: 1.922

Le mot-clé CLEANUP:

Ce mot-clé peut être utilisé lorsqu'un XSUB nécessite des procédures de nettoyage spéciales avant de se terminer. Lorsque le mot-clé CLEANUP: est utilisé, il doit suivre tout bloc CODE: ou OUTPUT: présent dans l'XSUB. Le code spécifié pour le bloc de nettoyage sera ajouté comme dernières instructions de l'XSUB.

Le mot-clé POSTCALL:

Ce mot-clé peut être utilisé lorsqu'un XSUB nécessite des procédures spéciales exécutées après l'appel de la sous-routine C. Lorsque le mot-clé POSTCALL: est utilisé, il doit précéder les blocs OUTPUT: et CLEANUP: présents dans l'XSUB.

Voir les exemples dans "Le mot-clé NO_OUTPUT" et "Retourner undef et des listes vides".

Le bloc POSTCALL: n'a pas beaucoup de sens lorsque l'appel de sous-routine C est fourni par l'utilisateur en fournissant une section CODE: ou PPCODE:.

Le mot-clé BOOT:

Le mot-clé BOOT: est utilisé pour ajouter du code à la fonction de bootstrap de l'extension. La fonction de bootstrap est générée par le compilateur xsubpp et contient normalement les instructions nécessaires pour enregistrer les XSUB auprès de Perl. Avec le mot-clé BOOT:, le programmeur peut indiquer au compilateur d'ajouter des instructions supplémentaires à la fonction de bootstrap.

Ce mot-clé peut être utilisé à tout moment après le premier mot-clé MODULE et doit apparaître sur sa propre ligne. La première ligne vide après le mot-clé terminera le bloc de code.

BOOT:
# Le message suivant sera imprimé lorsque la
# fonction de bootstrap s'exécutera.
printf("Hello from the bootstrap!\n");

Le mot-clé NO_OUTPUT

Ce mot-clé est utilisé pour indiquer que l'XSUB ne retourne aucune valeur. Dans ce cas, les sections OUTPUT: et RETVAL sont ignorées.

Le mot-clé NO_ kesan

Ce mot-clé est une alternative au mot-clé NO_OUTPUT et indique que le XSUB ne retourne aucune valeur et ne génère pas de valeur de retour pour le code C.

Le mot-clé WARN:

Le mot-clé WARN: est utilisé pour ajouter du code à la fonction de rappel de Perl après la fin de l'exécution de l'XSUB. Cela peut être utilisé pour effectuer des vérifications ou des actions supplémentaires après le retour de l'XSUB.

Voici un exemple d'utilisation de WARN:

void
my_xsub(arg)
    char *arg
  PREINIT:
    char *result;
  CODE:
    result = do_something(arg);
    RETVAL = strlen(result);
  WARN:
    printf("The length of the result is %d\n", RETVAL);
  OUTPUT:
    RETVAL

Le mot-clé PERL

Le mot-clé PERL est utilisé pour insérer du code Perl directement dans un fichier XS. Ce code Perl sera exécuté lors de la compilation du module.

MODULE test
    VERSION 1.0

    # Ceci est du code Perl qui sera exécuté lors de la compilation.
    use strict;
    use warnings;

    sub helper_function {
        print "Helper function called!\n";
    }

Le mot-clé USE

Le mot-clé USE est utilisé pour inclure des fichiers d'en-tête C dans le code généré. Cela est utile lorsque votre XSUB s'appuie sur des fonctions ou des structures définies dans des fichiers d'en-tête externes.

USE: stdio.h
USE: math.h

int
my_math_func(x)
    int x
  CODE:
    RETVAL = sqrt(x);
  OUTPUT:
    RETVAL

Le mot-clé TYPEMAP

Le mot-clé TYPEMAP est utilisé pour spécifier des règles de conversion de types personnalisées entre Perl et C. Cela vous permet de gérer des types de données complexes ou spécifiques qui ne sont pas pris en charge par défaut par xsubpp.

Vous pouvez définir un fichier typemap séparé et y faire référence dans votre fichier XS.

TYPEMAP: typemap.file

Ou vous pouvez définir des règles de typemap directement dans le fichier XS.

TYPEMAP:
    'char *' TO 'SV*' \
        "$b = sv_2pv_nolen($a); $a = $b;"
    'SV*' TO 'char *' \
        "$b = sv_2pv_nolen($a); $a = $b;"

Le mot-clé CAST

Le mot-clé CAST est utilisé pour spécifier des conversions de type explicites lors de l'appel de fonctions C depuis un XSUB. Cela est utile lorsque le compilateur ne peut pas déduire le type correct ou lorsque vous avez besoin d'un transtypage spécifique.

int
my_func(ptr)
    void *ptr
  CODE:
    RETVAL = func_that_takes_int_ptr((int *)ptr);
  OUTPUT:
    RETVAL

Vous pouvez également utiliser le mot-clé CAST pour spécifier le type de retour d'une fonction C.

double
my_double_func(x)
    int x
  CODE:
    RETVAL = (double)sqrt(x);
  OUTPUT:
    RETVAL

Le mot-clé CONST

Le mot-clé CONST est utilisé pour définir des constantes C qui seront accessibles depuis Perl. Ces constantes seront traduites en variables Perl lors de la compilation.

CONST:
    my_constant = 10
    another_constant = "hello"

int
my_xsub()
  CODE:
    RETVAL = my_constant;
  OUTPUT:
    RETVAL

Vous pouvez également spécifier le type de la constante.

CONST:
    my_int_constant = 10:int
    my_string_constant = "hello":char*

Le mot-clé PROTOTYPE

Le mot-clé PROTOTYPE est utilisé pour spécifier le prototype d'une fonction C. Cela aide le compilateur xsubpp à générer le code d'appel correct et à effectuer les conversions de types appropriées.

PROTOTYPE:
    int func(int, char*)

Si un prototype est spécifié, le compilateur vérifiera que les arguments passés depuis Perl correspondent au prototype. Si ce n'est pas le cas, une erreur de compilation sera générée.

Le mot-clé INLINE

Le mot-clé INLINE est utilisé pour spécifier que le code C doit être intégré directement dans la fonction XSUB générée. Cela peut améliorer les performances en évitant les appels de fonctions supplémentaires.

int
my_inline_func(x)
    int x
  INLINE:
    return x * 2;
  OUTPUT:
    x

Notez que lorsque vous utilisez le mot-clé INLINE, vous ne devez pas utiliser les mots-clés CODE:, PPCODE:, OUTPUT:, ni PREINIT:. Le bloc INLINE remplace entièrement ces sections.

Le mot-clé PACKAGE

Le mot-clé PACKAGE est utilisé pour spécifier le nom du package Perl auquel appartient le module XS. Cela est généralement fait au début du fichier XS avec le mot-clé MODULE.

PACKAGE: My::Module

Si vous utilisez le mot-clé MODULE, le mot-clé PACKAGE n'est pas nécessaire.

Le mot-clé MODULE

Le mot-clé MODULE est utilisé pour spécifier le nom du module Perl et sa version. Il doit être la première ligne du fichier XS.

MODULE: My::Module 1.0

Le mot-clé VERSION

Le mot-clé VERSION est utilisé pour spécifier la version du module Perl. Il est généralement utilisé avec le mot-clé MODULE.

MODULE: My::Module

La variable RETVAL

La variable RETVAL est une variable spéciale utilisée par xsubpp pour stocker la valeur de retour de la fonction C appelée. Elle est automatiquement créée et gérée par le compilateur, sauf si vous utilisez la directive NO_OUTPUT ou si la fonction C a un type de retour void.

Dans la section OUTPUT:, vous pouvez spécifier quelles variables doivent être retournées à Perl. Si RETVAL est l'une de ces variables, sa valeur sera retournée.

int
my_function(x)
    int x
  CODE:
    RETVAL = x * 2;
  OUTPUT:
    RETVAL

Si la fonction C retourne une valeur et que vous n'utilisez pas la section OUTPUT:, la valeur de RETVAL sera automatiquement retournée à Perl.

Si la fonction C a un type de retour void, RETVAL ne sera pas créé. Dans ce cas, vous devez utiliser une section PPCODE: pour retourner explicitement les valeurs à Perl.

La macro ST

La macro ST(i) est utilisée pour accéder aux arguments passés depuis Perl à l'XSUB. ST(0) fait référence au premier argument, ST(1) au deuxième, et ainsi de suite. ST(items) fait référence à la fin de la liste des arguments.

Vous pouvez utiliser des fonctions telles que SvPV_nolen(), SvIV(), SvNV() pour convertir les valeurs Perl en types C appropriés.

void
my_xsub(arg1, arg2)
    char *arg1
    int arg2
  CODE:
    printf("Arg1: %s, Arg2: %d\n", arg1, arg2);
    ST(0) = sv_newmortal(); /* Initialise la valeur de retour */
    sv_setiv(ST(0), arg2); /* Définit la valeur de retour */

La macro SP

La macro SP (Stack Pointer) est utilisée dans les sections PPCODE: pour gérer la pile d'arguments de Perl. Elle pointe vers l'emplacement actuel sur la pile où les valeurs de retour doivent être placées.

Les macros PUSH*() utilisent SP pour empiler les valeurs de retour. La macro EXTEND(SP, n) est utilisée pour réserver de l'espace sur la pile avant d'empiler plusieurs valeurs.

PPCODE:
    EXTEND(SP, 2);
    PUSHs(sv_2mortal(newSViv(10)));
    PUSHs(sv_2mortal(newSVpv("hello", 0)));

Les macros Sv*_*

Il existe plusieurs autres macros Sv*_* pour accéder aux différentes représentations des valeurs Perl (SV), telles que SvUlonlong() pour les entiers non signés longs, SvBool() pour les booléens, etc. Ces macros sont essentielles pour l'interopérabilité entre Perl et C.

Les macros newSV*_*

Les macros newSViv(), newSVnv(), newSVpv(), etc., sont utilisées pour créer de nouvelles valeurs Perl (SV) à partir de types C. Ces nouvelles valeurs peuvent ensuite être empilées sur la pile Perl ou retournées à Perl.

PPCODE:
    EXTEND(SP, 2);

    PUSHs(sv_2mortal(newSVpv("hello", 0))); /* Crée et empile un SV chaîne */

La macro sv_2mortal

La macro sv_2mortal() marque une valeur Perl (SV) comme "mortelle", ce qui signifie qu'elle sera automatiquement libérée par le garbage collector de Perl lorsqu'elle ne sera plus référencée. C'est une pratique courante lors de la création de nouvelles valeurs Perl à retourner à Perl.

PUSHs(sv_2mortal(newSViv(10)));

Les fonctions sv_set*_*

Les fonctions sv_setiv(), sv_setnv(), sv_setpv(), etc., sont utilisées pour modifier une valeur Perl (SV) existante. Elles sont utiles lorsque vous souhaitez modifier une valeur Perl qui a déjà été créée ou lorsque vous manipulez directement la pile Perl.

CODE:
    SV *my_sv = sv_newmortal();
    sv_setiv(my_sv, 10); /* Définit la valeur entière du SV */
    ST(0) = my_sv; /* Affecte le SV à la première position de retour */

La fonction sv_newmortal

La fonction sv_newmortal() crée une nouvelle valeur Perl (SV) et la marque comme "mortelle". Elle est souvent utilisée pour initialiser la valeur de retour d'une fonction XS lorsque vous ne retournez qu'une seule valeur.

CODE:
    ST(0) = sv_newmortal(); /* Crée une SV mortelle pour la valeur de retour */
    sv_setiv(ST(0), 10);

La variable PL_sv_undef

La variable globale PL_sv_undef est un pointeur vers une valeur Perl SV prédéfinie qui représente undef. Vous pouvez l'affecter directement à ST(0) ou l'utiliser avec d'autres fonctions pour retourner undef depuis votre XSUB.

CODE:
    ST(0) = &PL_sv_undef; /* Retourne undef */

La macro dXSARGS est utilisée dans les fonctions XS pour déclarer les arguments nécessaires à l'exécution du code XS, tels que items (nombre d'arguments) et ax (taille du tableau d'arguments). Elle est généralement placée au début de la fonction XS.

Le pointeur de pile des interpréteurs Perl

Le pointeur de pile des interpréteurs Perl, souvent représenté par la macro SP, est un élément crucial de la gestion de la mémoire et des données dans Perl. Il indique l'emplacement actuel sur la pile où les nouvelles valeurs peuvent être ajoutées ou où les valeurs existantes sont stockées.

Dans le contexte des XSUBs, la compréhension et l'utilisation correcte du pointeur de pile sont essentielles, en particulier lors de l'utilisation de la directive PPCODE:. La macro SP est directement manipulée par des fonctions comme PUSH*() et EXTEND() pour gérer les valeurs retournées par l'XSUB vers Perl.

La macro du pointeur de pile Perl SP

La macro SP fait référence au pointeur de pile de Perl. Dans les sections PPCODE: des fichiers XS, SP est initialisé au début de la liste des paramètres Perl. Cela permet aux macros PUSH*() d'ajouter des valeurs de retour à l'emplacement attendu par Perl.

Par exemple, EXTEND(SP, 2) fait avancer SP pour réserver de l'espace pour deux nouveaux éléments sur la pile, et PUSHs(sv_2mortal(newSViv(10))) place une valeur entière sur la pile à l'emplacement indiqué par SP, puis incrémente SP.

La pile d'arguments Perl

La pile d'arguments Perl est l'espace mémoire utilisé par Perl pour passer des arguments aux fonctions et pour stocker les valeurs de retour. Dans le contexte des XSUBs, cette pile est particulièrement importante car c'est le mécanisme par lequel les données circulent entre le code Perl et le code C de l'XSUB.

Lorsque vous appelez un XSUB depuis Perl, les arguments sont placés sur la pile d'arguments. L'XSUB accède à ces arguments en utilisant des macros comme ST(i). Lorsque l'XSUB retourne des valeurs, il doit les placer sur cette même pile d'arguments, généralement en utilisant des macros comme PUSH*() dans une section PPCODE:. Le compilateur xsubpp génère du code pour gérer correctement cette pile lors du retour à Perl.

Le pointeur de pile C

Il est important de ne pas confondre le pointeur de pile Perl (SP) avec le pointeur de pile C standard. Le pointeur de pile C est géré par le processeur et le système d'exploitation pour les appels de fonctions C. L'XSUB s'exécute dans le contexte de la pile C, mais il manipule la pile d'arguments Perl pour communiquer avec l'interpréteur Perl.

Lorsqu'une fonction C est appelée depuis un XSUB (par exemple, dans une section CODE:), le compilateur C gère la pile C pour cet appel. L'XSUB lui-même, cependant, interagit avec la pile Perl pour l'entrée et la sortie des données.

Variables globales et macros Perl

Perl expose un certain nombre de variables globales et de macros qui sont essentielles pour écrire des extensions C. Les plus courantes sont :

  • items : Le nombre d'arguments passés à l'XSUB.
  • ST(i) : Accès aux arguments individuels sur la pile Perl.
  • SP : Le pointeur de pile Perl actuel.
  • PL_sv_undef : Un pointeur vers la valeur undef de Perl.
  • Macros SvIV(), SvNV(), SvPV(), etc. : Pour convertir les valeurs Perl en types C.
  • Macros newSViv(), newSVnv(), newSVpv(), etc. : Pour créer de nouvelles valeurs Perl à partir de types C.
  • Macro sv_2mortal() : Pour marquer les valeurs Perl comme étant gérées par le garbage collector.
  • Fonctions sv_setiv(), sv_setnv(), sv_setpv(), etc. : Pour modifier des valeurs Perl existantes.
  • Macro dXSARGS : Pour déclarer les variables nécessaires à l'environnement XS.
  • Fonction croak() : Pour lever une exception Perl.
  • Fonction warn() : Pour générer un avertissement Perl.

Une compréhension approfondie de ces éléments est cruciale pour interagir efficacement entre Perl et C.

Le compilateur XSUB xsubpp

Le compilateur xsubpp est l'outil principal utilisé pour générer le code C nécessaire à la création d'extensions Perl. Il analyse les fichiers XS et traduit les déclarations et les instructions en code C qui peut être compilé et lié avec l'interpréteur Perl.

xsubpp gère un large éventail de fonctionnalités, y compris la gestion des listes de paramètres de longueur variable, les conversions de types entre Perl et C, la gestion de la pile d'arguments Perl et la génération de code boilerplate pour l'initialisation et le nettoyage.

Les directives comme CODE:, OUTPUT:, PPCODE:, et d'autres, sont des instructions pour xsubpp sur la manière de générer le code C.

Le processus de compilation du module XS

La compilation d'un module XS implique généralement les étapes suivantes :

  1. xsubpp traite le fichier .xs pour générer un fichier .c (ou .cpp).
  2. Un compilateur C (par exemple, GCC, Clang) compile le fichier .c généré, ainsi que tout autre fichier source C que vous fournissez.
  3. Le compilateur crée un fichier objet (.o).
  4. Un éditeur de liens lie le fichier objet avec la bibliothèque Perl pour créer une bibliothèque partagée (par exemple, .so sur Linux, .dll sur Windows) qui peut être chargée par l'interpréteur Perl.

Les outils comme ExtUtils::MakeMaker ou Module::Build automatisent généralement ce processus, en créant un `Makefile` qui gère toutes les étapes de compilation et de liaison.

L'API Perl pour les extensions C

L'API Perl pour les extensions C est un ensemble de fonctions et de macros C qui permettent au code C d'interagir avec l'interpréteur Perl. Elle fournit les outils nécessaires pour créer et manipuler des objets Perl (SV), gérer la pile d'arguments, lever des exceptions et exécuter du code Perl depuis C.

xsubpp génère essentiellement du code qui utilise cette API Perl pour faciliter la communication entre Perl et votre code C.

Les documents de référence tels que perlapi fournissent des détails complets sur l'API Perl.

Intégrer Perl dans C

Bien que cet article se concentre sur la création d'extensions C pour Perl, il est également possible d'intégrer l'interpréteur Perl dans une application C. L'API Perl fournit des fonctions pour initialiser l'interpréteur, exécuter des scripts Perl, passer des données entre C et Perl, et gérer les erreurs.

Cela permet à une application C d'utiliser la puissance et la flexibilité de Perl pour des tâches de scripting ou de traitement de données.

Bonnes pratiques pour l'écriture de code XS

  • **Gérez la mémoire avec soin** : Utilisez sv_2mortal() pour les valeurs Perl qui ne doivent pas persister au-delà de l'appel de fonction. Faites attention aux fuites de mémoire dans votre code C.
  • **Validez les arguments** : Vérifiez toujours le nombre et le type des arguments passés depuis Perl pour éviter les plantages et les comportements inattendus. Utilisez croak() pour signaler les erreurs.
  • **Utilisez les bons types** : Assurez-vous que les conversions de types entre Perl et C sont correctes. Utilisez les macros Sv*_* et newSV*_* appropriées.
  • **Documentez votre code** : Utilisez les commentaires dans vos fichiers XS et générez une documentation POD pour votre module.
  • **Testez rigoureusement** : Écrivez des tests Perl pour vérifier que votre module XS fonctionne comme prévu dans divers scénarios.
  • **Comprenez la pile Perl** : Une bonne compréhension de la pile d'arguments Perl est essentielle pour gérer correctement les entrées et les sorties.
  • **Préférez PPCODE: pour les retours multiples** : Utilisez PPCODE: lorsque vous devez retourner plusieurs valeurs ou des structures de données complexes.
  • **Utilisez PREINIT: pour l'initialisation** : Déclarez et initialisez les variables C nécessaires dans la section PREINIT:.

Pièges courants et conseils de débogage

  • **Fuites de mémoire** : Oublier de libérer la mémoire allouée en C ou de marquer les SV Perl comme mortels peut entraîner des fuites de mémoire. Utilisez des outils comme Valgrind pour détecter ces problèmes.
  • **Accès hors limites de la pile** : Accéder à ST(i) avec un index i invalide (trop grand ou trop petit) entraînera un plantage.
  • **Mauvaises conversions de types** : Passer une chaîne Perl à une fonction C qui attend un entier, par exemple, sans conversion appropriée entraînera des résultats incorrects ou des plantages.
  • **Problèmes de compilation** : Assurez-vous que vos fichiers d'en-tête C sont correctement inclus (avec USE:) et que les types sont déclarés correctement.
  • **Débogage** : Utilisez printf ou warn dans votre code XS pour imprimer des valeurs et suivre le flux d'exécution. Pour un débogage plus avancé, utilisez un débogueur C (comme GDB) en attachant au processus Perl. Compilez votre module avec des informations de débogage (`-g`) pour faciliter cela.
  • **Erreurs de segmentation** : Souvent causées par des accès invalides à la mémoire, des pointeurs nuls ou des conversions de types incorrectes.

Conclusion

La création d'extensions C pour Perl (modules XS) est un moyen puissant d'améliorer les performances et d'intégrer du code existant écrit dans d'autres langages. Le compilateur xsubpp et l'API Perl fournissent les outils nécessaires pour rendre ce processus gérable, bien qu'il nécessite une compréhension approfondie des deux langages et de leur interaction. En suivant les bonnes pratiques et en comprenant les pièges courants, les développeurs peuvent créer des extensions XS robustes et efficaces.

Le mot-clé ALIAS:

Le mot-clé ALIAS : permet à un XSUB d'avoir deux noms Perl ou plus uniques et de savoir lequel de ces noms a été utilisé lors de son invocation. Les noms Perl peuvent être entièrement qualifiés avec des noms de paquetages. Chaque alias se voit attribuer un index. Le compilateur mettra en place une variable appelée "ix" qui contient l'index de l'alias utilisé. Lorsque le XSUB est appelé avec son nom déclaré, "ix" sera 0.

L'exemple suivant créera les alias FOO::gettime() et BAR::getit() pour cette fonction.

bool_t
rpcb_gettime(host,timep)
      char *host
      time_t &timep
    ALIAS:
        FOO::gettime = 1
        BAR::getit = 2
    INIT:
      printf("# ix = %d\n", ix );
    OUTPUT:
      timep

Un avertissement sera produit lorsque vous créerez plus d'un alias pour la même valeur. Cela peut être contourné d'une manière rétrocompatible en créant plusieurs définitions qui se résolvent à la même valeur, ou avec une version moderne de ExtUtils::ParseXS vous pouvez utiliser un alias symbolique, qui est désigné par un "=>" au lieu d'un "=". Par exemple, vous pourriez modifier ce qui précède de sorte que la section alias ressemble à ceci :

ALIAS:
    FOO::gettime = 1
    BAR::getit = 2
    BAZ::gettime => FOO::gettime

cela aurait le même effet que ceci :

ALIAS:
    FOO::gettime = 1
    BAR::getit = 2
    BAZ::gettime = 1

sauf que ce dernier produira des avertissements pendant le processus de construction. Un mécanisme qui fonctionnerait d'une manière rétrocompatible avec les versions plus anciennes de notre chaîne d'outils serait de faire ceci :

#define FOO_GETTIME 1
#define BAR_GETIT 2
#define BAZ_GETTIME 1
bool_t
rpcb_gettime(host,timep)
      char *host
      time_t &timep
    ALIAS:
        FOO::gettime = FOO_GETTIME
        BAR::getit = BAR_GETIT
        BAZ::gettime = BAZ_GETTIME
    INIT:
      printf("# ix = %d\n", ix );
    OUTPUT:

Le mot-clé OVERLOAD:

Au lieu d'écrire une interface surchargée en pur Perl, vous pouvez également utiliser le mot-clé OVERLOAD pour définir des noms Perl supplémentaires pour vos fonctions (comme le mot-clé ALIAS : ci-dessus). Cependant, les fonctions surchargées doivent être définies de manière à accepter le nombre de paramètres fournis par le système de surcharge de Perl. Pour la plupart des méthodes de surcharge, il y aura trois paramètres ; pour la fonction "nomethod", il y en aura quatre. Cependant, les opérateurs bit à bit "&", "|", "^", et "~" peuvent être appelés avec trois ou cinq arguments (voir overload).

Si une fonction a le mot-clé OVERLOAD :, plusieurs lignes supplémentaires seront définies dans le fichier C généré par xsubpp afin de s'enregistrer auprès de la magie de surcharge.

Comme les objets bénis sont réellement stockés sous forme de RV, il est utile d'utiliser les fonctionnalités de typemap pour prétraiter les paramètres et extraire le SV réel stocké dans le RV béni. Voir l'exemple pour T_PTROBJ_SPECIAL dans perlxstypemap.

Pour utiliser le mot-clé OVERLOAD :, créez une fonction XS qui prend trois paramètres d'entrée (ou utilisez la définition de style C '...') comme ceci :

SV *
cmp (lobj, robj, swap)
My_Module_obj    lobj
My_Module_obj    robj
IV               swap
OVERLOAD: cmp <=>
{ /* la fonction est définie ici */}

Dans ce cas, la fonction surchargera les deux opérateurs de comparaison à trois voies. Pour toutes les opérations de surcharge utilisant des caractères non alphabétiques, vous devez taper le paramètre sans guillemets, en séparant les surcharges multiples par des espaces. Notez que « » (la surcharge de stringify) doit être entrée comme \"\" (c'est-à-dire échappée).

Comme mentionné ci-dessus, les opérateurs bit à bit peuvent prendre des arguments supplémentaires, vous pourriez vouloir utiliser quelque chose comme "(lobj, robj, swap, ...)" (avec un "..." littéral) comme liste de paramètres.

Le mot-clé FALLBACK:

En plus du mot-clé OVERLOAD, si vous avez besoin de contrôler la façon dont Perl génère automatiquement les opérateurs surchargés manquants, vous pouvez définir le mot-clé FALLBACK dans la section d'en-tête du module, comme suit :

MODULE = RPC  PACKAGE = RPC
FALLBACK: TRUE
...

où FALLBACK peut prendre l'une des trois valeurs TRUE, FALSE ou UNDEF. Si vous ne définissez aucune valeur FALLBACK lors de l'utilisation de OVERLOAD, elle est par défaut à UNDEF. FALLBACK n'est pas utilisé sauf lorsqu'une ou plusieurs fonctions utilisant OVERLOAD ont été définies. Voir « fallback » dans overload pour plus de détails.

Le mot-clé INTERFACE:

Ce mot-clé déclare le XSUB actuel comme gardien de la signature d'appel donnée. Si du texte suit ce mot-clé, il est considéré comme une liste de fonctions qui ont cette signature et doit être attaché au XSUB actuel.

Par exemple, si vous avez 4 fonctions C multiply(), divide(), add(), subtract() ayant toutes la signature :

symbolic f(symbolic, symbolic);

vous pouvez les faire toutes utiliser le même XSUB en utilisant ceci :

symbolic
interface_s_ss(arg1, arg2)
    symbolic        arg1
    symbolic        arg2
INTERFACE:
    multiply divide
    add subtract

(C'est le code XSUB complet pour 4 fonctions Perl !) Quatre fonctions Perl générées partagent les noms des fonctions C correspondantes.

L'avantage de cette approche par rapport au mot-clé ALIAS : est qu'il n'est pas nécessaire de coder une instruction de commutation, chaque fonction Perl (qui partage le même XSUB) sait quelle fonction C elle doit appeler. De plus, on peut attacher une fonction supplémentaire remainder() à l'exécution en utilisant

CV *mycv = newXSproto("Symbolic::remainder",
                      XS_Symbolic_interface_s_ss, __FILE__, "$$");
XSINTERFACE_FUNC_SET(mycv, remainder);

disons, depuis un autre XSUB. (Cet exemple suppose qu'il n'y avait pas de section INTERFACE_MACRO :, sinon il faut utiliser autre chose que "XSINTERFACE_FUNC_SET", voir la section suivante.)

Le mot-clé INTERFACE_MACRO:

Ce mot-clé permet de définir une INTERFACE en utilisant une manière différente d'extraire un pointeur de fonction d'un XSUB. Le texte qui suit ce mot-clé doit donner le nom des macros qui extrairaient/définiraient un pointeur de fonction. La macro extracteur reçoit le type de retour, "CV*", et "XSANY.any_dptr" pour ce "CV*". La macro définisseur reçoit cv et le pointeur de fonction.

La valeur par défaut est "XSINTERFACE_FUNC" et "XSINTERFACE_FUNC_SET". Un mot-clé INTERFACE avec une liste de fonctions vide peut être omis si le mot-clé INTERFACE_MACRO est utilisé.

Supposons que dans l'exemple précédent, les pointeurs de fonction pour multiply(), divide(), add(), subtract() sont stockés dans un tableau C global "fp[]" avec les décalages étant "multiply_off", "divide_off", "add_off", "subtract_off". Alors on peut utiliser

#define XSINTERFACE_FUNC_BYOFFSET(ret,cv,f) \
    ((XSINTERFACE_CVT_ANON(ret))fp[CvXSUBANY(cv).any_i32])
#define XSINTERFACE_FUNC_BYOFFSET_set(cv,f) \
    CvXSUBANY(cv).any_i32 = CAT2( f, _off )

dans la section C,

symbolic
interface_s_ss(arg1, arg2)
    symbolic        arg1
    sym
bolic arg2 INTERFACE_MACRO: XSINTERFACE_FUNC_BYOFFSET XSINTERFACE_FUNC_BYOFFSET_set INTERFACE: multiply divide add subtract

dans la section XSUB.

Le mot clé INCLUDE:

Ce mot clé peut être utilisé pour inclure d'autres fichiers dans le module XS. Les autres fichiers peuvent contenir du code XS. INCLUDE: peut également être utilisé pour exécuter une commande afin de générer le code XS à inclure dans le module.

Le fichier Rpcb1.xsh contient notre fonction rpcb_gettime() :

bool_t
rpcb_gettime(host,timep)
      char *host
      time_t &timep
    OUTPUT:
      timep

Le module XS peut utiliser INCLUDE: pour inclure ce fichier.

INCLUDE: Rpcb1.xsh

Si les paramètres du mot clé INCLUDE: sont suivis d'un pipe ("|"), le compilateur interprétera les paramètres comme une commande. Cette fonctionnalité est légèrement dépréciée au profit de la directive "INCLUDE_COMMAND:", comme décrit ci-dessous.

INCLUDE: cat Rpcb1.xsh |

N'utilisez pas cela pour exécuter perl : "INCLUDE: perl |" exécutera le perl qui se trouve être le premier dans votre PATH et non nécessairement le même perl qui est utilisé pour exécuter "xsubpp". Voir "Le mot clé INCLUDE_COMMAND:".

Le mot clé INCLUDE_COMMAND:

Exécute la commande fournie et inclut sa sortie dans le document XS actuel. "INCLUDE_COMMAND" attribue une signification spéciale au jeton $^X en ce sens qu'il exécute le même interpréteur Perl qui exécute "xsubpp" :

INCLUDE_COMMAND: cat Rpcb1.xsh
INCLUDE_COMMAND: $^X -e ...

Le mot clé CASE:

Le mot clé CASE: permet à un XSUB d'avoir plusieurs parties distinctes, chaque partie agissant comme un XSUB virtuel. CASE: est gourmand et s'il est utilisé, tous les autres mots clés XS doivent être contenus dans un CASE:. Cela signifie que rien ne peut précéder le premier CASE: dans le XSUB et tout ce qui suit le dernier CASE: est inclus dans ce cas.

Un CASE: peut basculer via un paramètre du XSUB, via la variable d'ALIAS "ix" (voir "Le mot clé ALIAS:"), ou peut-être via la variable "items" (voir "Listes de paramètres de longueur variable"). Le dernier CASE: devient le cas par défaut s'il n'est pas associé à une condition. L'exemple suivant montre un basculement CASE via "ix" avec une fonction rpcb_gettime() ayant un alias x_gettime(). Lorsque la fonction est appelée comme rpcb_gettime() ses paramètres sont les habituels "(char *host, time_t *timep)", mais lorsque la fonction est appelée comme x_gettime() ses paramètres sont inversés, "(time_t *timep, char *host)".

long
rpcb_gettime(a,b)
  CASE: ix == 1
    ALIAS:
      x_gettime = 1
    INPUT:
      # 'a' est timep, 'b' est host
      char *b
      time_t a = NO_INIT
    CODE:
           RETVAL = rpcb_gettime( b, &a );
    OUTPUT:
      a
      RETVAL
  CASE:
      # 'a' est host, 'b' est timep
      char *a
      time_t &b = NO_INIT
    OUTPUT:
      b
      RETVAL

Cette fonction peut être appelée avec l'une des instructions suivantes. Notez les différentes listes d'arguments.

$status = rpcb_gettime( $host, $timep );
$status = x_gettime( $timep, $host );

Le mot clé EXPORT_XSUB_SYMBOLS:

Le mot clé EXPORT_XSUB_SYMBOLS: est probablement quelque chose dont vous n'aurez jamais besoin. Dans les versions de Perl antérieures à 5.16.0, ce mot clé ne fait rien. À partir de la version 5.16, les symboles XSUB ne sont plus exportés par défaut. C'est-à-dire qu'ils sont des fonctions "static". Si vous incluez

EXPORT_XSUB_SYMBOLS: ENABLE

dans votre code XS, les XSUBs qui suivent cette ligne ne seront pas déclarés "static". Vous pouvez désactiver cela plus tard avec

EXPORT_XSUB_SYMBOLS: DISABLE

ce qui, encore une fois, est le comportement par défaut que vous ne devriez probablement jamais modifier. Vous ne pouvez pas utiliser ce mot clé sur les versions de Perl antérieures à 5.16 pour rendre les XSUBs "static".

L'opérateur unaire &

L'opérateur unaire "&" dans la section INPUT: est utilisé pour indiquer à xsubpp qu'il doit convertir une valeur Perl en/depuis C en utilisant le type C à gauche de "&", mais fournir un pointeur vers cette valeur lorsque la fonction C est appelée.

Ceci est utile pour éviter un bloc CODE: pour une fonction C qui prend un paramètre par référence. Généralement, le paramètre ne doit pas être un type pointeur (un "int" ou "long" mais pas un "int*" ou "long*").

Le XSUB suivant générera un code C incorrect. Le compilateur xsubpp le transformera en code qui appelle rpcb_gettime() avec les paramètres "(char *host, time_t timep)", mais le vrai rpcb_gettime() attend que le paramètre "timep" soit de type "time_t*" plutôt que "time_t".

bool_t
rpcb_gettime(host,timep)
      char *host
      time_t timep
    OUTPUT:
      timep

Ce problème est corrigé en utilisant l'opérateur "&". Le compilateur xsubpp le transformera maintenant en code qui appelle rpcb_gettime() correctement avec les paramètres "(char *host, time_t *timep)". Il le fait en conservant le "&", de sorte que l'appel de fonction ressemble à "rpcb_gettime(host, &timep)".

bool_t
rpcb_gettime(host,timep)
      char *host
      time_t &timep
    OUTPUT:
      timep

Insertion de POD, de commentaires et de directives du préprocesseur C

Les directives du préprocesseur C sont autorisées dans les blocs BOOT:, PREINIT:, INIT:, CODE:, PPCODE:, POSTCALL:, et CLEANUP:, ainsi qu'en dehors des fonctions. Les commentaires sont autorisés n'importe où après le mot clé MODULE. Le compilateur transmettra les directives du préprocesseur intactes et supprimera les lignes commentées. La documentation POD est autorisée à tout moment, dans les sections de langage C et XS. POD doit être terminé par une commande "=cut" ; "xsubpp" se terminera avec une erreur s'il ne le trouve pas. Il est très peu probable que du code C généré par un humain soit confondu avec du POD, car la plupart des styles d'indentation aboutissent à des espaces devant toute ligne commençant par "=". Les fichiers XS générés par machine peuvent tomber dans ce piège, à moins que des précautions ne soient prises pour garantir qu'un espace brise la séquence "\n=".

Des commentaires peuvent être ajoutés aux XSUBs en plaçant un "#" comme premier caractère non blanc d'une ligne. Des précautions doivent être prises pour éviter que le commentaire ne ressemble à une directive de préprocesseur C, de peur qu'il ne soit interprété comme tel. La manière la plus simple d'éviter cela est de placer un espace devant le "#".

Si vous utilisez des directives de préprocesseur pour choisir entre deux versions d'une fonction, utilisez

#if ... version1
#else /* ... version2  */
#endif

et non

#if ... version1
#endif
#if ... version2
#endif

car sinon xsubpp croira que vous avez fait une définition dupliquée de la fonction. De plus, laissez une ligne vide avant le #else/#endif afin qu'il ne soit pas considéré comme faisant partie du corps de la fonction.

Utilisation de XS avec C++

Si un nom de XSUB contient "::", il est considéré comme une méthode C++. La fonction Perl générée supposera que son premier argument est un pointeur d'objet. Le pointeur d'objet sera stocké dans une variable appelée THIS. L'objet doit avoir été créé par C++ avec la fonction new() et doit être "blessed" par Perl avec la macro sv_setref_pv(). Le "blessing" de l'objet par Perl peut être géré par une typemap. Un exemple de typemap est montré à la fin de cette section.

Si le type de retour du XSUB inclut "static", la méthode est considérée comme une méthode statique. Elle appellera la fonction C++ en utilisant la syntaxe class::method(). Si la méthode n'est pas statique, la fonction sera appelée en utilisant la syntaxe THIS->method().

Les exemples suivants utiliseront la classe C++ suivante.

class color {
     public:
     color();
     ~color();
     int blue();
     void set_blue( int );
     private:
     int c_blue;
};

Les XSUBs pour les méthodes blue() et set_blue() sont définis avec le nom de la classe mais le paramètre pour l'objet (THIS, ou "self") est implicite et n'est pas listé.

int
color::blue()
void
color::set_blue( val )
     int val

Les deux fonctions Perl attendront un objet comme premier paramètre. Dans le code C++ généré, l'objet est appelé "THIS", et l'appel de méthode sera effectué sur cet objet. Ainsi, dans le code C++, les méthodes blue() et set_blue() seront appelées comme suit :

RETVAL = THIS->blue();
THIS->set_blue( val );

Vous pourriez également écrire une méthode get/set unique en utilisant un argument optionnel :

int
color::blue( val = NO_INIT )
    int val
    PROTOTYPE $;$
    CODE:
        if (items > 1)
            THIS->set_blue( val );
        RETVAL = THIS->blue();
    OUTPUT:
        RETVAL

Si le nom de la fonction est DESTROY, la fonction C++ "delete" sera appelée et "THIS" sera passé comme paramètre. Le code C++ généré pour

void
color::DESTROY()

ressemblera à ceci :

color *THIS = ...;  // Initialisé comme dans la typemap
delete THIS;

Si le nom de la fonction est new, alors la fonction C++ "new" sera appelée pour créer un objet C++ dynamique. Le XSUB attendra que le nom de la classe, qui sera conservé dans une variable appelée "CLASS", soit fourni comme premier argument.

color *
color::new()

Le code C++ généré appellera "new".

RETVAL = new color();

Stratégie d'interface

Lors de la conception d'une interface entre Perl et une bibliothèque C, une traduction directe de C vers XS (telle que créée par "h2xs -x") est souvent suffisante. Cependant, parfois, l'interface ressemblera beaucoup à du C et sera occasionnellement peu intuitive, surtout lorsque la fonction C modifie l'un de ses paramètres, ou retourne un échec dans la bande (comme dans "les valeurs de retour négatives signifient échec"). Dans les cas où le programmeur souhaite créer une interface plus proche de Perl, la stratégie suivante peut aider à identifier les parties les plus critiques de l'interface.

Identifiez les fonctions C avec des paramètres d'entrée/sortie ou de sortie. Les XSUB pour ces fonctions peuvent être capables de retourner des listes à Perl.

Identifiez les fonctions C qui utilisent des informations dans la bande comme indication d'échec. Elles peuvent être des candidats pour retourner undef ou une liste vide en cas d'échec. Si l'échec peut être détecté sans appel à la fonction C, vous pourriez vouloir utiliser une section INIT : pour signaler l'échec. Pour les échecs détectables après le retour de la fonction C, vous pourriez vouloir utiliser une section POSTCALL : pour traiter l'échec. Dans des cas plus compliqués, utilisez des sections CODE : ou PPCODE :.

Si de nombreuses fonctions utilisent la même indication d'échec basée sur la valeur de retour, vous pourriez vouloir créer un typedef spécial pour gérer cette situation. Mettez

typedef int negative_is_failure;

près du début du fichier XS, et créez une entrée de typemap OUTPUT pour "negative_is_failure" qui convertit les valeurs négatives en "undef", ou peut-être croak()s. Après cela, la valeur de retour de type "negative_is_failure" créera une interface plus proche de Perl.

Identifiez quelles valeurs sont utilisées uniquement par les fonctions C et XSUB elles-mêmes, par exemple, lorsqu'un paramètre d'une fonction doit être le contenu d'une variable globale. Si Perl n'a pas besoin d'accéder au contenu de la valeur, il peut ne pas être nécessaire de fournir une traduction pour cette valeur de C vers Perl.

Identifiez les pointeurs dans les listes de paramètres et les valeurs de retour des fonctions C. Certains pointeurs peuvent être utilisés pour implémenter des paramètres d'entrée/sortie ou de sortie, ils peuvent être gérés en XS avec l'opérateur unaire "&", et, éventuellement, en utilisant le mot-clé NO_INIT. D'autres nécessiteront la gestion de types comme "int *", et il faut décider de ce que fera une traduction Perl utile dans un tel cas. Lorsque le sémantique est claire, il est conseillé de placer la traduction dans un fichier de typemap.

Identifiez les structures utilisées par les fonctions C. Dans de nombreux cas, il peut être utile d'utiliser le typemap T_PTROBJ pour ces structures afin qu'elles puissent être manipulées par Perl comme des objets bénis. (Ceci est géré automatiquement par "h2xs -x".)

Si le même type C est utilisé dans plusieurs contextes différents qui nécessitent des traductions différentes, "typedef" plusieurs nouveaux types mappés à ce type C, et créez des entrées de *typemap* distinctes pour ces nouveaux types. Utilisez ces types dans les déclarations de type de retour et de paramètres pour les XSUBs.

Objets Perl et Structures C

Lorsqu'on traite des structures C, il faut choisir soit T_PTROBJ, soit T_PTRREF pour le type XS. Les deux types sont conçus pour gérer des pointeurs vers des objets complexes. Le type T_PTRREF permettra à l'objet Perl d'être désacralisé, tandis que le type T_PTROBJ exigera que l'objet soit béni. En utilisant T_PTROBJ, on peut obtenir une forme de vérification de type car le XSUB tentera de vérifier que l'objet Perl est du type attendu.

Le code XS suivant montre la fonction getnetconfigent() qui est utilisée avec ONC+ TIRPC. La fonction getnetconfigent() retournera un pointeur vers une structure C et a le prototype C montré ci-dessous. L'exemple démontrera comment le pointeur C deviendra une référence Perl. Perl considérera cette référence comme un pointeur vers un objet béni et tentera d'appeler un destructeur pour l'objet. Un destructeur sera fourni dans la source XS pour libérer la mémoire utilisée par getnetconfigent(). Les destructeurs en XS peuvent être créés en spécifiant une fonction XSUB dont le nom se termine par le mot DESTROY. Les destructeurs XS peuvent être utilisés pour libérer la mémoire qui a pu être allouée par un autre XSUB.

struct netconfig *getnetconfigent(const char *netid);

Un "typedef" sera créé pour "struct netconfig". L'objet Perl sera béni dans une classe correspondant au nom du type C, avec le suffixe "Ptr" ajouté, et le nom ne devrait pas avoir d'espaces incorporés s'il doit s'agir d'un nom de package Perl. Le destructeur sera placé dans une classe correspondant à la classe de l'objet et le mot-clé PREFIX sera utilisé pour tronquer le nom au mot DESTROY, comme Perl s'y attendra.

typedef struct netconfig Netconfig;
MODULE = RPC  PACKAGE = RPC
Netconfig *
getnetconfigent(netid)
     char *netid
MODULE = RPC  PACKAGE = NetconfigPtr  PREFIX = rpcb_
void
rpcb_DESTROY(netconf)
     Netconfig *netconf
   CODE:
     printf("Now in NetconfigPtr::DESTROY\n");
     free( netconf );

Cet exemple nécessite l'entrée de typemap suivante. Consultez perlxstypemap pour plus d'informations sur l'ajout de nouveaux typemaps pour une extension.

TYPEMAP
Netconfig *  T_PTROBJ

Cet exemple sera utilisé avec les instructions Perl suivantes.

use RPC;
$netconf = getnetconfigent("udp");

Lorsque Perl détruira l'objet référencé par $netconf, il enverra l'objet à la fonction DESTROY XSUB fournie. Perl ne peut pas déterminer, et ne se soucie pas, que cet objet est une structure C et non un objet Perl. En ce sens, il n'y a aucune différence entre l'objet créé par le XSUB getnetconfigent() et un objet créé par une sous-routine Perl normale.

Stockage sécurisé de données statiques en XS

À partir de Perl 5.8, un cadre de macros a été défini pour permettre de stocker des données statiques en toute sécurité dans les modules XS qui seront accessibles à partir d'un Perl multi-threadé.

Bien que principalement conçu pour être utilisé avec Perl multi-threadé, les macros ont été conçues de manière à fonctionner également avec Perl non-threadé.

Il est donc fortement recommandé que ces macros soient utilisées par tous les modules XS qui utilisent des données statiques.

La manière la plus simple d'obtenir un modèle de macros à utiliser est de spécifier l'option "-g" ("--global") avec h2xs (voir h2xs).

Ci-dessous un exemple de module qui utilise les macros.

#define PERL_NO_GET_CONTEXT
#include "EXTERN.h"
#include "perl.h"
#include "XSUB.h"
/* Global Data */
#define MY_CXT_KEY "BlindMice::_guts" XS_VERSION
typedef struct {
    int count;
    char name[3][100];
} my_cxt_t;
START_MY_CXT
MODULE = BlindMice           PACKAGE = BlindMice
BOOT:
{
    MY_CXT_INIT;
    MY_CXT.count = 0;
    strcpy(MY_CXT.name[0], "None");
    strcpy(MY_CXT.name[1], "None");
    strcpy(MY_CXT.name[2], "None");
}
int
newMouse(char * name)
    PREINIT:
      dMY_CXT;
    CODE:
      if (MY_CXT.count >= 3) {
          warn("Already have 3 blind mice");
          RETVAL = 0;
      }
      else {
          RETVAL = ++ MY_CXT.count;
          strcpy(MY_CXT.name[MY_CXT.count - 1], name);
      }
    OUTPUT:
      RETVAL
char *
get_mouse_name(index)
      int index
    PREINIT:
      dMY_CXT;
    CODE:
      if (index > MY_CXT.count)
        croak("There are only 3 blind mice.");
      else
        RETVAL = MY_CXT.name[index - 1];
    OUTPUT:
      RETVAL
void
CLONE(...)
    CODE:
      MY_CXT_CLONE;

MY_CXT_KEY
Cette macro est utilisée pour définir une clé unique pour référencer les données statiques d'un module XS. Le schéma de nommage suggéré, tel qu'utilisé par h2xs, est d'utiliser une chaîne qui se compose du nom du module, de la chaîne "::_guts" et du numéro de version du module. 
#define MY_CXT_KEY "MyModule::_guts" XS_VERSION
typedef my_cxt_t
Ce typedef de structure doit *toujours* s'appeler "my_cxt_t". Les autres macros "CXT*" supposent l'existence du typedef "my_cxt_t".

Déclarez un typedef nommé "my_cxt_t" qui est une structure contenant toutes les données qui doivent être locales à l'interpréteur.

typedef struct {
    int some_value;

START_MY_CXT
Placez toujours la macro START_MY_CXT directement après la déclaration de "my_cxt_t".
MY_CXT_INIT
La macro MY_CXT_INIT initialise le stockage pour la structure "my_cxt_t".

Elle *doit* être appelée exactement une fois, typiquement dans une section BOOT:. Si vous maintenez plusieurs interpréteurs, elle doit être appelée une fois dans chaque instance d'interpréteur, à l'exception des interpréteurs clonés à partir d'interprèteurs existants. (Mais voir "MY_CXT_CLONE" ci-dessous.)

dMY_CXT
Utilisez la macro dMY_CXT (une déclaration) dans toutes les fonctions qui accèdent à MY_CXT.
MY_CXT
_CXT">MY_CXT
Utilisez la macro MY_CXT pour accéder aux membres de la structure "my_cxt_t". Par exemple, si "my_cxt_t" est 
typedef struct {
    int index;
} my_cxt_t;

alors utilisez ceci pour accéder au membre "index"

dMY_CXT;
MY_CXT.index = 2;
aMY_CXT/pMY_CXT
"dMY_CXT" peut être assez coûteux à calculer, et pour éviter le surcoût de son invocation dans chaque fonction, il est possible de passer la déclaration à d'autres fonctions en utilisant les macros "aMY_CXT"/"pMY_CXT", par exemple 
void sub1() {
    dMY_CXT;
    MY_CXT.index = 1;
    sub2(aMY_CXT);
}
void sub2(pMY_CXT) {
    MY_CXT.index = 2;
}

Par analogie avec "pTHX", il existe des formes équivalentes pour lorsque la macro est la première ou la dernière d'entre plusieurs arguments, où un underscore représente une virgule, c'est-à-dire "_aMY_CXT", "aMY_CXT_", "_pMY_CXT" et "pMY_CXT_".

MY_CXT_CLONE
Par défaut, lorsqu'un nouvel interpréteur est créé comme copie d'un existant (par exemple via "threads->create()"), les deux interpréteurs partagent la même structure physique my_cxt_t. Appeler "MY_CXT_CLONE" (généralement via la fonction CLONE() du package), provoque une copie octet par octet de la structure, et tout dMY_CXT ultérieur provoquera l'accès à la copie à la place.
MY_CXT_INIT_INTERP(my_perl)
dMY_CXT_INTERP(my_perl)
Ce sont des versions des macros qui prennent un interpréteur explicite comme argument.

Notez que ces macros ne fonctionneront ensemble que dans le même fichier source ; c'est-à-dire qu'un dMY_CTX dans un fichier source accédera à une structure différente d'un dMY_CTX dans un autre fichier source.

Boucles d'événements et flux de contrôle

Certains modules ont une boucle d'événements, attendant l'entrée utilisateur. Il est très improbable que deux modules de ce type fonctionnent adéquatement ensemble dans une seule application Perl.

En général, l'interpréteur perl se considère comme le centre de l'univers pour ce qui concerne le programme Perl. Le code XS est considéré comme une aide, pour accomplir des choses que Perl ne fait pas, ou pas assez vite, mais toujours subordonné à Perl. Plus le code XS adhère à ce modèle, moins les conflits sont susceptibles de se produire.
