NOM

perl5120delta - nouveautés de la version Perl v5.12.0

DESCRIPTION

Ce document décrit les différences entre la sortie 5.10.0 et la sortie 5.12.0.

Bon nombre des corrections de bugs dans 5.12.0 sont déjà incluses dans la version de maintenance 5.10.1.

Vous pouvez consulter la liste de ces changements dans les notes de la version 5.10.1 (perl5101delta).

Améliorations du cœur

Nouvelle syntaxe "package NOM VERSION"

Cette nouvelle syntaxe permet à un auteur de module de définir la $VERSION d'un espace de noms lors de la déclaration de l'espace de noms avec 'package'. Elle élimine la nécessité d'utiliser "our $VERSION = ..." et des constructions similaires. Par exemple :

package Foo::Bar 1.23;
# $Foo::Bar::VERSION == 1.23

Il y a plusieurs avantages à cela :

  • $VERSION est analysé exactement de la même manière que "use NOM VERSION"
  • $VERSION est défini au moment de la compilation
  • $VERSION est un objet version qui fournit un surcharge correcte des opérateurs de comparaison, de sorte que la comparaison de $VERSION avec des nombres de version décimaux (1.23) ou décimaux en pointillé (v1.2.3) fonctionne correctement.
  • Élimine l'encombrement de "$VERSION = ..." et "eval $VERSION"
  • Comme il exige que VERSION soit une valeur littérale numérique ou une valeur littérale v-string, elle peut être analysée statiquement par les modules de la chaîne d'outils sans "eval", comme le fait MM->parse_version pour "$VERSION = ..."

Cela ne casse pas le vieux code avec seulement "package NOM", mais le code qui utilise "package NOM VERSION" devra être restreint à Perl 5.12.0 ou plus récent. Ceci est analogue au changement de "open" de deux arguments à trois arguments. Les utilisateurs qui ont besoin de la dernière version de Perl en bénéficieront, et peut-être qu'après plusieurs années, cela deviendra une pratique standard.

Cependant, "package NOM VERSION" nécessite un nouveau format de numéro de version, « strict ». Voir "Formats de numéros de version" pour les détails.

L'opérateur "..."

Un nouvel opérateur, "...", surnommé l'opérateur Yada Yada, a été ajouté. Il est destiné à marquer du code plaque tournante qui n'est pas encore implémenté. Voir "Yada Yada Operator" dans perlop.

Strictures implicites

Utiliser la syntaxe "use VERSION" avec un numéro de version supérieur ou égal à 5.11.0 activera lexicalement les strictures, tout comme le ferait "use strict" (en plus d'activer des fonctionnalités.) Le code suivant :

use 5.12.0;

signifie :

use strict;
use feature ':5.12';

Unicode améliorations

Perl 5.12 est livré avec Unicode 5.2, la dernière version disponible au moment de sa sortie. Cette version d'Unicode a été publiée en octobre 2009. Voir http://www.unicode.org/versions/Unicode5.2.0 pour plus de détails sur les changements dans cette version de la norme. Voir perlunicode pour des instructions sur l'installation et l'utilisation d'autres versions d'Unicode.

De plus, les développeurs de Perl ont considérablement amélioré l'implémentation Unicode de Perl. Pour tous les détails, voir "Rénovation Unicode" ci-dessous.

Conformité Y2038

Les fonctions principales de Perl liées au temps sont maintenant conformes à Y2038. (Cela ne vous signifie peut-être pas grand-chose, mais vos enfants vont adorer !)

qr surcharge

Il est maintenant possible de surcharger l'opérateur "qr//", c'est-à-dire la conversion en regexp, comme il était déjà possible de surcharger la conversion en booléen, chaîne ou nombre d'objets. Elle est invoquée lorsqu'un objet apparaît du côté droit de l'opérateur "=~" ou lorsqu'il est interpolé dans une regexp. Voir overload.

Mots-clés enfichables

Les modules d'extension peuvent maintenant s'accrocher proprement au parseur Perl pour définir de nouveaux types d'expressions sous forme de mot-clé et d'instructions composées. La syntaxe suivant le mot-clé est définie entièrement par l'extension. Cela permet de parser une sous-langue complètement non-Perl en ligne, avec la génération d'ops corrects.

Voir "PL_keyword_plugin" dans perlapi pour le mécanisme. La distribution source de Perl inclut également un nouveau module XS::APItest::KeywordRPN, qui implémente l'arithmétique en notation polonaise inverse via des mots-clés enfichables. Ce module est principalement utilisé à des fins de test, et n'est normalement pas installé, mais sert également d'exemple sur la façon d'utiliser le nouveau mécanisme.

Les développeurs de Perl considèrent cette fonctionnalité comme expérimentale. Nous pourrions la supprimer ou la modifier d'une manière incompatible avec les versions antérieures dans Perl 5.14.

APIs pour plus d'internes

Les couches les plus basses du lexer et certaines parties du système de pad disposent désormais d'API C disponibles pour les extensions XS. Celles-ci sont nécessaires pour supporter l'utilisation correcte des mots-clés enfichables, mais ont également d'autres usages. Les nouvelles API sont expérimentales et ne couvrent qu'une petite partie de ce qui serait nécessaire pour tirer pleinement parti des installations internes dans ces domaines. Il est prévu que le cycle de développement de Perl 5.13 verra l'ajout d'une gamme complète d'interfaces propres et supportées.

Les développeurs de Perl considèrent cette fonctionnalité comme expérimentale. Nous pourrions la supprimer ou la modifier d'une manière incompatible avec les versions antérieures dans Perl 5.14.

Recherche de fonctions surchargeable

Lorsque qu'un module d'extension accroche la création d'ops rv2cv pour modifier le processus de recherche de sous-routines, cela fonctionne maintenant correctement pour les appels de sous-routines en bareword. Cela signifie que les prototypes des sous-routines référencées de cette manière seront traités correctement. (Auparavant, les noms de sous-routines en bareword étaient initialement recherchés, à des fins d'analyse syntaxique, par un mécanisme non accrochable, de sorte que les extensions ne pouvaient influencer correctement que les noms de sous-routines qui apparaissaient avec un sigil "&".)

Une interface propre pour les Ordres de Résolution de Méthodes enfichables

Depuis Perl 5.12.0, il existe une nouvelle interface pour enficher et utiliser des ordres de résolution de méthodes autres que la recherche par défaut en profondeur linéaire. L'ordre de résolution de méthodes C3 ajouté dans 5.10.0 a été réimplémenté comme un plugin, sans modifier son interface dans l'espace Perl. Voir perlmroapi pour plus d'informations.

"\\N" échappement d'expression régulière expérimental

Perl supporte maintenant "\N", un nouvel échappement regex que vous pouvez considérer comme l'inverse de "\n". Il correspondra à tout caractère qui n'est pas un saut de ligne, indépendamment de la présence ou de l'absence du modificateur de correspondance sur une seule ligne "/s". Il n'est pas utilisable dans une classe de caractères. "\N{3}" signifie faire correspondre 3 non-sauts de ligne ; "\N{5,}" signifie faire correspondre au moins 5. "\N{NOM}" signifie toujours le caractère ou la séquence nommée "NOM", mais "NOM" ne peut plus être des choses comme 3, ou "5,".

New Features

"\N{...}" syntax

When used in a regular expression, "\N{...}" now matches a sequence of characters whose Unicode name is given by the contents of the braces.

This will break a custom charnames translator which allows numbers for character names, as "\N{3}" will now mean to match 3 non-newline characters, and not the character whose name is 3. (No name defined by the Unicode standard is a number, so only custom translators might be affected.)

Perl's developers are somewhat concerned about possible user confusion with the existing "\N{...}" construct which matches characters by their Unicode name. Consequently, this feature is experimental. We may remove it or change it in a backwards-incompatible way in Perl 5.14.

DTrace support

Perl now has some support for DTrace. See "DTrace support" in INSTALL.

Support for "configure_requires" in CPAN module metadata

Both "CPAN" and "CPANPLUS" now support the "configure_requires" keyword in the META.yml metadata file included in most recent CPAN distributions. This allows distribution authors to specify configuration prerequisites that must be installed before running Makefile.PL or Build.PL.

See the documentation for "ExtUtils::MakeMaker" or "Module::Build" for more on how to specify "configure_requires" when creating a distribution for CPAN.

"each", "keys", "values" are now more flexible

The "each", "keys", "values" function can now operate on arrays.

"when" as a statement modifier

"when" is now allowed to be used as a statement modifier.

$, flexibility

The variable $, may now be tied.

// in when clauses

// now behaves like || in when clauses

Enabling warnings from your shell environment

You can now set "-W" from the "PERL5OPT" environment variable

"delete local"

"delete local" now allows you to locally delete a hash entry.

New support for Abstract namespace sockets

Abstract namespace sockets are Linux-specific socket type that live in AF_UNIX family, slightly abusing it to be able to use arbitrary character arrays as addresses: They start with nul byte and are not terminated by nul byte, but with the length passed to the socket() system call.

32-bit limit on substr arguments removed

The 32-bit limit on "substr" arguments has now been removed. The full range of the system's signed and unsigned integers is now available for the "pos" and "len" arguments.

Potentially Incompatible Changes

Deprecations warn by default

Over the years, Perl's developers have deprecated a number of language features for a variety of reasons. Perl now defaults to issuing a warning if a deprecated language feature is used. Many of the deprecations Perl now warns you about have been deprecated for many years. You can find a list of what was deprecated in a given release of Perl in the "perl5xxdelta.pod" file for that release.

To disable this feature in a given lexical scope, you should use "no warnings 'deprecated';" For information about which language features are deprecated and explanations of various deprecation warnings, please see perldiag. See "Deprecations" below for the list of features and modules Perl's developers have deprecated as part of this release.

Version number formats

Acceptable version number formats have been formalized into "strict" and "lax" rules. "package NAME VERSION" takes a strict version number. "UNIVERSAL::VERSION" and the version object constructors take lax version numbers. Providing an invalid version will result in a fatal error. The version argument in "use NAME VERSION" is first parsed as a numeric literal or v-string and then passed to "UNIVERSAL::VERSION" (and must then pass the "lax" format test).

These formats are documented fully in the version module. To a first approximation, a "strict" version number is a positive decimal number (integer or decimal-fraction) without exponentiation or else a dotted-decimal v-string with a leading 'v' character and at least three components. A "lax" version number allows v-strings with fewer than three components or without a leading 'v'. Under "lax" rules, both decimal and dotted-decimal versions may have a trailing "alpha" component separated by an underscore character after a fractional or dotted-decimal component.

The version module adds "version::is_strict" and "version::is_lax" functions to check a scalar against these rules.

@INC reorganization

In @INC, "ARCHLIB" and "PRIVLIB" now occur after the current version's "site_perl" and "vendor_perl". Modules installed into "site_perl" and "vendor_perl" will now be loaded in preference to those installed in "ARCHLIB" and "PRIVLIB".

REGEXPs are now first class

Internally, Perl now treats compiled regular expressions (such as those created with "qr//") as first class entities. Perl modules which serialize, deserialize or otherwise have deep interaction with Perl's internal data structures need to be updated for this change. Most affected CPAN modules have already been updated as of this writing.

Switch statement changes

The "given"/"when" switch statement handles complex statements better than Perl 5.10.0 did (These enhancements are also available in 5.10.1 and subsequent 5.10 releases.) There are two new cases where "when" now interprets its argument as a boolean, instead of an expression to be used in a smart match:

flip-flop operators
The ".." and "..." flip-flop operators are now evaluated in boolean context, following their usual semantics; see "Range Operators" in perlop.

Note that, as in perl 5.10.0, "when (1..10)" will not work to test whether a given value is an integer between 1 and 10; you should use "when ([1..10])" instead (note the array reference).

However, contrary to 5.10.0, evaluating the flip-flop operators in boolean context ensures it can now be useful in a when(), notably for implementing bistable conditions, like in:

when (/^=begin/ .. /^=end/) {
  # do something
}
defined-or operator
A compound expression involving the defined-or operator, as in "when (expr1 // expr2)", will be treated as boolean if the first expression is boolean. (This just extends the existing rule that applies to the regular or operator, as in "when (expr1 || expr2)".)

Smart match changes

Since Perl 5.10.0, Perl's developers have made a number of changes to the smart match operator. These, of course, also alter the behaviour of the switch statements where smart matching is implicitly used. These changes were also made for the 5.10.1 release, and will remain in subsequent 5.10 releases.

Changes to type-based dispatch

The smart match operator "~~" is

n'est plus commutative. Le comportement d'une correspondance intelligente dépend désormais principalement du type de son argument droit. De plus, sa sémantique a été ajustée pour une plus grande cohérence ou utilité dans plusieurs cas. Bien que la compatibilité descendante générale soit maintenue, plusieurs changements doivent être notés :

  • Les références de code avec un prototype vide ne sont plus traitées spécialement. Elles reçoivent un argument comme les autres références de code (même si elles choisissent de l'ignorer).
  • « %hash ~~ sub {} » et « @array ~~ sub {} » testent maintenant que le sous-programme renvoie une valeur vraie pour chaque clé du hachage (ou élément du tableau), au lieu de passer l'intégralité du hachage ou du tableau en référence au sous-programme.
  • En raison de la rupture de commutativité, les références de code ne sont plus traitées spécialement lorsqu'elles apparaissent à gauche de l'opérateur « ~~ », mais comme n'importe quel scalaire vulgaire.
  • « undef ~~ %hash » est toujours faux (puisque « undef » ne peut pas être une clé dans un hachage). Aucune conversion implicite en « » n'est effectuée (comme c'était le cas dans perl 5.10.0).
  • « $scalar ~~ @array » distribue maintenant toujours la correspondance intelligente sur les éléments du tableau. Elle est vraie si un élément de @array vérifie « $scalar ~~ $element ». Ceci est une généralisation du comportement précédent qui testait si le tableau contenait le scalaire.

Le tableau de dispatch complet pour l'opérateur de correspondance intelligente est donné dans « Smart matching in detail » dans perlsyn.

Correspondance intelligente et surcharge

Selon la règle de dispatch basée sur le type de l'argument le plus à droite, lorsqu'un objet surchargeant « ~~ » apparaît à droite de l'opérateur, la routine de surcharge sera toujours appelée (avec un troisième argument défini à une valeur vraie, voir overload.) Cependant, lorsque l'objet apparaîtra à gauche, la routine de surcharge ne sera appelée que lorsque l'argument le plus à droite est un scalaire simple. De cette façon, la distributivité de la correspondance intelligente sur les tableaux n'est pas rompue, ainsi que les autres comportements avec les types complexes (coderefs, hachages, regex). Ainsi, les auteurs de routines de surcharge pour la correspondance intelligente n'ont principalement besoin de se soucier que de la comparaison avec un scalaire, et éventuellement de la surcharge de la stringification ; les autres cas courants seront automatiquement gérés de manière cohérente.

« ~~ » refusera maintenant de fonctionner sur des objets qui ne le surchargent pas (afin d'éviter de dépendre de la structure sous-jacente de l'objet). (Cependant, si l'objet surcharge les opérateurs de stringification ou de numification, et si la substitution de surcharge est active, elle sera utilisée à la place, comme d'habitude.)

Autres changements potentiellement incompatibles

  • Les définitions d'un certain nombre de propriétés Unicode ont changé pour correspondre à celles de la norme Unicode actuelle. Celles-ci sont listées ci-dessus sous « Unicode overhaul ». Ce changement peut casser le code qui attendait les anciennes définitions.
  • L'op boolkeys a été déplacé dans le groupe des ops de hachage. Ceci casse la compatibilité binaire.
  • Les descripteurs de fichiers sont maintenant toujours bénis dans « IO::File ».

    Le comportement précédent consistait à bénir les descripteurs de fichiers dans FileHandle (une classe proxy vide) s'il était chargé en mémoire et sinon à les bénir dans « IO::Handle ».

  • La sémantique de « use feature :5.10* » a légèrement changé. Voir « Modules et Pragmata » pour plus d'informations.
  • Les développeurs de Perl utilisent maintenant git, plutôt que Perforce. Ceci ne devrait être qu'un changement interne pertinent pour les personnes travaillant activement sur le cœur. Cependant, vous pourriez observer des différences mineures dans perl à la suite de ce changement. Par exemple, dans certains détails de la sortie de « perl -V ». Voir perlrepository pour plus d'informations.
  • Dans le cadre de la mise à niveau de « Test::Harness » de 2.x à 3.x, le module expérimental « Test::Harness::Straps » a été supprimé. Voir « Modules et Pragmata » pour plus de détails.
  • Dans le cadre de la mise à niveau de « ExtUtils::MakeMaker », les modules « ExtUtils::MakeMaker::bytes » et « ExtUtils::MakeMaker::vmsish » ont été supprimés de cette distribution.
  • « Module::CoreList » ne contient plus le hachage %:patchlevel.
  • « length undef » renvoie maintenant undef.
  • Les fonctions privées de l'API C non prises en charge sont maintenant déclarées « static » pour empêcher toute fuite vers l'API publique de Perl.
  • Pour prendre en charge le processus d'amorçage, miniperl ne compile plus avec la prise en charge UTF-8 dans le moteur d'expressions rationnelles.

    Cela permet une compilation complète avec PERL_UNICODE défini et un locale UTF-8. Sans cela, il y a un problème d'amorçage, car miniperl ne peut pas charger les composants UTF-8 du moteur d'expressions rationnelles, car ils ne sont pas encore construits.

  • Le @INC de miniperl est maintenant limité à seulement « -I... », la division de $ENV{PERL5LIB}, et " ».« "
  • Un espace ou un saut de ligne est maintenant requis après une directive « #line XXX ».
  • Les descripteurs de fichiers liés ont maintenant une méthode supplémentaire EOF qui fournit le type EOF.
  • Pour mieux correspondre à toutes les autres instructions de contrôle de flux, « foreach » ne peut plus être utilisé comme attribut.
  • Le commutateur de ligne de commande de Perl « -P », qui était déprécié dans la version 5.10.0, a maintenant été supprimé. Le module CPAN « Filter::cpp » peut être utilisé comme alternative.

Dépréciations

De temps en temps, les développeurs de Perl jugent nécessaire de déprécier des fonctionnalités ou des modules que nous avons précédemment expédiés dans le cadre de la distribution principale. Nous sommes bien conscients de la douleur et de la frustration qu'un changement de Perl incompatible avec les versions précédentes peut causer aux développeurs qui créent ou maintiennent des logiciels en Perl. Vous pouvez être sûr que lorsque nous déprécions une fonctionnalité ou une syntaxe, ce n'est pas un choix que nous faisons à la légère. Parfois, nous choisissons de déprécier une fonctionnalité ou une syntaxe parce qu'elle s'est avérée mal conçue ou implémentée. Parfois, cela est dû au fait qu'elles freinent d'autres fonctionnalités ou causent des problèmes de performance. Parfois, les raisons sont plus complexes. Dans la mesure du possible, nous essayons de garder les fonctionnalités dépréciées disponibles pour les développeurs sous leur forme précédente pendant au moins une version majeure. Tant qu'une fonctionnalité dépréciée ne perturbe pas activement notre capacité à maintenir et à étendre Perl, nous essaierons de la laisser en place aussi longtemps que possible.

Les éléments suivants sont maintenant dépréciés :

suidperl
« suidperl » ne fait plus partie de Perl. Il fournissait auparavant un mécanisme pour émuler les bits de permission setuid sur les systèmes qui ne le prenaient pas en charge correctement.
Utilisation de « := » pour signifier une liste d'attributs vide
Un accident du parseur de Perl signifiait que ces constructions étaient toutes équivalentes : 
my $pi := 4;
my $pi : = 4;
my $pi :  = 4;

avec le « : » étant traité comme le début d'une liste d'attributs, qui se termine avant le « = ». Comme les espaces blancs ne sont pas significatifs ici, tous sont analysés comme une liste d'attributs vide, donc tous les éléments ci-dessus sont équivalents à, et mieux écrits comme

my $pi = 4;

car aucun traitement d'attribut n'est effectué pour une liste vide.

En l'état, cela signifiait que « := » ne pouvait pas être utilisé comme un nouveau token, sans changer silencieusement le sens du code existant. Par conséquent, cette forme particulière est maintenant dépréciée et deviendra une erreur de syntaxe. S'il est absolument nécessaire d'avoir des listes d'attributs vides (par exemple, à cause d'un générateur de code) alors évitez l'avertissement en ajoutant un espace avant le « = ».

"UNIVERSAL->import()"
La méthode « UNIVERSAL->import() » est maintenant dépréciée. Tenter de passer des arguments d'importation à une instruction « use UNIVERSAL » entraînera un avertissement de dépréciation.
Utilisation de « goto » pour sauter dans une construction
Utiliser « goto » pour sauter d'une portée externe vers une portée interne est maintenant déprécié. Ce cas d'utilisation rare posait des problèmes dans l'implémentation des scopes.
Noms de caractères personnalisés dans \N{name} qui ne ressemblent pas à des noms
Dans « \N{name} », name peut être à peu près n'importe quoi. Les noms Unicode standard ont un domaine très limité, mais un traducteur de noms personnalisé pourrait créer des noms qui sont, par exemple, entièrement composés de symboles de ponctuation. Il est maintenant déprécié de créer des noms qui ne commencent pas par un caractère alphabétique, et qui ne sont pas alphanumériques ou ne contiennent pas d'autres caractères que quelques-uns, à savoir les espaces, tirets, parenthèses et deux-points. En raison du sens ajouté de « \N » (Voir « \N » échappement regex expérimental »), les noms qui ressemblent à des quantificateurs entre accolades ne fonctionneront pas. Par exemple, « \N{3,4} » signifie maintenant faire correspondre 3 à 4 non-sauts de ligne ; avant, un nom personnalisé « 3,4 » aurait pu être créé.

Révision Unicode

Les développeurs de Perl ont fait un effort concerté pour mettre à jour Perl afin qu'il soit synchronisé avec la dernière norme Unicode. Les changements incluent:

Perl peut désormais gérer toutes les propriétés de caractères Unicode. La nouvelle documentation, perluniprops, liste toutes les propriétés de caractères non-Unihan disponibles. Par défaut, perl n'expose pas les propriétés Unihan, obsolètes ou internes à Unicode. Voir ci-dessous pour plus de détails à leur sujet ; il y a aussi une section dans le pod qui les énumère, et explique pourquoi elles ne sont pas exposées.

Perl prend désormais en charge intégralement le style composé Unicode d'utilisation de "=" et ":" dans l'écriture des expressions régulières : "\p{property=value}" et "\p{property:value}" (les deux signifiant la même chose).

Perl prend désormais entièrement en charge les règles de correspondance légère Unicode pour le texte entre les accolades dans les constructions "\p{...}". De plus, Perl autorise les tirets bas entre les chiffres des nombres.

Perl accepte désormais tous les synonymes définis par Unicode pour les propriétés et les valeurs de propriétés.

"qr/\X/", qui correspond à un caractère logique Unicode, a été étendu pour mieux fonctionner avec diverses langues asiatiques. Il est maintenant défini comme un cluster de graphemes étendus. (Voir http://www.unicode.org/reports/tr29/). Tout ce qui était correspondant précédemment et qui avait du sens continuera d'être accepté. De plus :

  • "\X" ne séparera pas une séquence "CR LF".
  • "\X" correspondra maintenant à une séquence qui inclut les caractères "ZWJ" et "ZWNJ".
  • "\X" correspondra maintenant toujours à au moins un caractère, y compris une marque initiale. Les marques viennent généralement après un caractère de base, mais il est possible en Unicode de les avoir isolées, et "\X" gérera maintenant ce cas, par exemple au début d'une ligne, ou après un "ZWSP". Et c'est là que "\X" ne correspond pas aux choses qu'il faisait auparavant et qui n'ont pas de sens. Auparavant, par exemple, vous podiez avoir le cas dénué de sens d'un LF accentué.
  • "\X" correspondra maintenant à une séquence de syllabes (coréennes) Hangul, ainsi qu'aux cas d'exception thaï et lao.

Sinon, ce changement devrait être transparent pour les langues non affectées.

Les correspondances "\p{...}" utilisant la propriété Canonical_Combining_Class étaient complètement défectueuses dans les versions précédentes de Perl. Elles devraient maintenant fonctionner correctement.

Avant Perl 5.12, la propriété Unicode "Decomposition_Type=Compat" et une extension Perl portaient le même nom, ce qui faisait qu'aucune ne correspondait à toutes les valeurs correctes (avec plus de 100 erreurs dans l'une, et plusieurs milliers dans l'autre). L'extension Perl a maintenant été renommée pour être "Decomposition_Type=Noncanonical" (abrégé : "dt=noncanon"). Elle a la même signification que celle initialement prévue, à savoir l'union de tous les types de décomposition non canoniques, "Compat" étant juste l'un d'entre eux.

"\p{Decomposition_Type=Canonical}" inclut désormais les syllabes Hangul.

"\p{Uppercase}" et "\p{Lowercase}" fonctionnent désormais comme le dit la norme Unicode. Cela signifie qu'elles correspondent chacune à quelques caractères supplémentaires par rapport à avant.

"\p{Cntrl}" correspond désormais aux mêmes caractères que "\p{Control}". Cela signifie qu'il ne correspondra plus aux points de code d'usage privé (gc=co), de substitution (gc=cs), ni de format (gc=cf). Les points de code de format représentent le problème le plus important. Sur ces 36, les plus utilisés sont probablement le trait d'union conditionnel (U+00AD), et le BOM, ZWSP, ZWNJ, WJ, et caractères similaires, ainsi que les contrôles bidirectionnels.

"\p{Alpha}" correspond désormais aux mêmes caractères que "\p{Alphabetic}". Avant 5.12, la définition de Perl incluait un certain nombre de choses qui ne sont pas vraiment alphabétiques (toutes les marques) tout en omettant beaucoup de celles qui l'étaient. Les définitions de "\p{Alnum}" et "\p{Word}" dépendent de la définition de Alpha et ont été modifiées en conséquence.

"\p{Word}" ne correspond plus incorrectement à des caractères non-mot tels que les fractions.

"\p{Print}" ne correspond plus aux caractères de contrôle de ligne : Tab, LF, CR, FF, VT, et NEL. Cela le met en conformité avec les normes et la documentation.

"\p{XDigit}" correspond désormais aux mêmes caractères que "\p{Hex_Digit}". Cela signifie qu'en plus des caractères qu'il correspond actuellement, "[A-Fa-f0-9]", il correspondra également aux 22 équivalents pleine chasse, par exemple U+FF10 : CHIFFRE ZÉRO PLEINE CHASSE.

La propriété de type Numérique a été étendue pour inclure les caractères Unihan.

Il existe une nouvelle extension Perl, la propriété 'Present_In', ou simplement 'In'. Il s'agit d'une extension de la propriété Unicode Age, mais "\p{In=5.0}" correspond à tout point de code dont l'utilisation a été déterminée à partir de la version 5.0 d'Unicode. "\p{Age=5.0}" ne correspond qu'aux points de code ajoutés précisément dans la version 5.0.

Un certain nombre de propriétés ont maintenant les valeurs correctes pour les points de code non assignés. Les propriétés concernées sont Bidi_Class, East_Asian_Width, Joining_Type, Decomposition_Type, Hangul_Syllable_Type, Numeric_Type, et Line_Break.

Les propriétés Default_Ignorable_Code_Point, ID_Continue, et ID_Start sont maintenant à jour avec les définitions Unicode actuelles.

Les versions antérieures de Perl exposaient par erreur certaines propriétés qui sont censées être internes à Unicode. Leur utilisation dans les expressions régulières générera désormais, si elles sont activées, un message d'avertissement de dépréciation. Les propriétés sont : Other_Alphabetic, Other_Default_Ignorable_Code_Point, Other_Grapheme_Extend, Other_ID_Continue, Other_ID_Start, Other_Lowercase, Other_Math, et Other_Uppercase.

Il est maintenant possible de modifier les propriétés Unicode que Perl comprend sur une base par installation. Comme mentionné ci-dessus, certaines propriétés sont désactivées par défaut. Celles-ci incluent toutes les propriétés Unihan (qui devraient être accessibles via le module CPAN Unicode::Unihan) et toute propriété obsolète ou interne à Unicode que Perl n'a jamais exposée.

Les fichiers générés dans le répertoire "lib/unicore/To" sont maintenant plus clairement marqués comme étant stables, directement utilisables par les applications. Les nouvelles entrées de hachage

es s'y trouvent, donnent le format des entrées normales, ce qui permet un parsing plus facile par machine. Perl peut générer des fichiers dans ce répertoire pour toute propriété, bien que la plupart soient supprimées. Vous trouverez des instructions pour changer celles qui sont écrites dans perluniprops.

Améliorations des performances sélectionnées

  • Un nouveau cache interne signifie que isa() sera souvent plus rapide.
  • L'implémentation de l'Ordre de Résolution de Méthodes "C3" a été optimisée - la linéarisation pour les classes à héritage simple est 40% plus rapide. Les performances pour l'héritage multiple sont inchangées.
  • Sous "use locale", les informations relatives à la locale sont maintenant mises en cache sur les valeurs en lecture seule, comme la liste retournée par "keys %hash". Cela rend les opérations telles que "sort keys %hash" dans la portée de "use locale" beaucoup plus rapides.
  • Les méthodes "DESTROY" vides ne sont plus appelées.
  • Perl_sv_utf8_upgrade() est maintenant plus rapide.
  • "keys" sur une table de hachage vide est maintenant plus rapide.
  • "if (%foo)" a été optimisé pour être plus rapide que "if (keys %foo)".
  • L'opérateur de répétition de chaîne ("$str x $num") est maintenant plusieurs fois plus rapide lorsque $str a une longueur de un ou lorsque $num est grand.
  • Inverser un tableau sur lui-même (comme dans "@a = reverse @a") en contexte vide se fait maintenant en place et est plusieurs ordres de grandeur plus rapide qu'auparavant. Il préservera également les éléments inexistants chaque fois que possible, c'est-à-dire pour les tableaux non magiques ou les tableaux liés avec des méthodes "EXISTS" et "DELETE".

    Chaque version de Perl voit de nombreux changements internes qui ne devraient pas affecter l'utilisation quotidienne mais peuvent néanmoins être notables pour les développeurs travaillant avec le code source de Perl.

    • Les citations de J.R.R. Tolkien en tête des fichiers source C ont été vérifiées et des citations appropriées ont été ajoutées, grâce à un patch de Tom Christiansen.
    • La structure interne des modules à double durée de vie traditionnellement trouvés dans les répertoires lib/ et ext/ du code source de perl a changé de manière significative. Dans la mesure du possible, les modules à double durée de vie ont été extraits de lib/ et ext/.

      Les modules à double durée de vie maintenus par les développeurs de Perl dans le cadre du cœur de Perl résident désormais dans dist/. Les modules à double durée de vie maintenus principalement sur CPAN résident désormais dans cpan/. Lors du signalement d'un bug dans un module situé sous cpan/, veuillez envoyer votre rapport de bug directement au tracker de bugs ou à l'auteur du module, plutôt qu'au tracker de bugs de Perl.

    • "\N{...}" se compile mieux désormais, forçant toujours la représentation interne UTF-8

      Les développeurs de Perl ont corrigé plusieurs problèmes de reconnaissance des constructions "\N{...}". Dans ce cadre, perl stockera tout scalaire ou regex contenant "\N{nom}" ou "\N{U+point de code}" dans sa définition au format UTF-8. (C'était déjà vrai pour toutes les occurrences de "\N{nom}" qui n'utilisaient pas de traducteur personnalisé, mais c'est maintenant toujours le cas.)

    • Perl_magic_setmglob connaît désormais les globs, corrigeant RT #71254.
    • "SVt_RV" n'existe plus. Les RV sont désormais stockés dans des IV.
    • Perl_vcroak() accepte désormais un premier argument nul. De plus, un audit complet des annotations de compilation "not NULL" a été effectué, et celles de plusieurs autres fonctions internes ont été corrigées.
    • De nouvelles macros "dSAVEDERRNO", "dSAVE_ERRNO", "SAVE_ERRNO", "RESTORE_ERRNO" ont été ajoutées pour formaliser la sauvegarde temporaire de la variable "errno".
    • La fonction "Perl_sv_insert_flags" a été ajoutée pour compléter "Perl_sv_insert".
    • La fonction Perl_newSV_type(type) a été ajoutée, équivalente à Perl_newSV() suivie de Perl_sv_upgrade(type).
    • La fonction Perl_newSVpvn_flags() a été ajoutée, équivalente à Perl_newSVpvn() suivie de l'action pertinente pour le drapeau.

      Deux bits de drapeau sont actuellement pris en charge.

    • "SVf_UTF8" appellera SvUTF8_on() pour vous. (Notez que cela ne convertit pas une séquence de caractères ISO 8859-1 en UTF-8). Un wrapper, newSVpvn_utf8(), est disponible pour cela.

    Il existe également un wrapper qui prend des chaînes constantes, newSVpvs_flags().

    • La fonction "Perl_croak_xs_usage" a été ajoutée en tant que wrapper pour "Perl_croak".
    • Perl exporte désormais les fonctions "PerlIO_find_layer" et "PerlIO_list_alloc".
    • "PL_na" a été supprimé du code central, remplacé par des variables temporaires STRLEN locales ou des appels *_nolen(). Chaque approche est plus rapide que "PL_na", qui est une déréférenciation de pointeur dans la structure de l'interpréteur sous ithreads, et une variable globale sinon.
    • Perl_mg_free() laissait auparavant la mémoire libérée accessible via SvMAGIC() sur le scalaire. Il met désormais à jour la liste chaînée pour supprimer chaque élément magique lorsqu'il est libéré.
    • Sous ithreads, la regex dans "PL_reg_curpm" est désormais comptée par référence. Cela élimine de nombreuses solutions de contournement pour gérer le fait qu'elle n'était pas comptée par référence.

    • Les drapeaux IV et NV publics ne sont plus définis si la valeur chaîne a un "garbage" final. Ce comportement est cohérent avec le fait de ne pas définir les drapeaux IV ou NV publics si la valeur est hors de la plage pour le type.
    • Les utilisations de "Nullav", "Nullcv", "Nullhv", "Nullop", "Nullsv" etc ont été remplacées par "NULL" dans le code central, et les modules non à double durée de vie, car "NULL" est plus clair pour ceux qui ne sont pas familiers avec le code central.
    • Une macro MUTABLE_PTR(p) a été ajoutée, qui sur gcc (non-pédantique) ne supprime pas "const", retournant un "void *".     • Les macros mPUSHs() et mXPUSHs() ont été ajoutées, pour pousser des SV sur la pile et les rendre mortels.
    • L'utilisation de la structure privée "mro_meta" a légèrement changé. Rien en dehors du code central ne devrait y accéder directement de toute façon.
    • Un nouvel outil, Porting/expand-macro.pl, a été ajouté, qui vous permet de voir comment une macro du préprocesseur C serait développée lors de la compilation. Ceci est utile lorsque vous essayez de décoder l'enfer des macros qui constituent les entrailles de perl.

    Tests

    Améliorations des tests

    Tests parallèles
    La distribution principale peut désormais exécuter ses tests de régression en parallèle sur les plateformes de type Unix. Au lieu d'exécuter "make test", définissez "TEST_JOBS" dans votre environnement avec le nombre de tests à exécuter en parallèle, et exécutez "make test_harness". Sur un shell de type Bourne, cela peut être fait comme suit : 
    TEST_JOBS=3 make test_harness  # Exécute 3 tests en parallèle

    Une variable d'environnement est utilisée, plutôt que make parallèle lui-même, car TAP::Harness doit pouvoir planifier lui-même des scripts de test individuels non conflictuels, et il n'existe pas d'interface standard pour les utilitaires "make" afin d'interagir avec leurs planificateurs de jobs.

    Notez que certains scripts de test peuvent actuellement échouer lorsqu'ils sont exécutés en parallèle (notamment "ext/IO/t/io_dir.t"). Si nécessaire, exécutez à nouveau uniquement les scripts défaillants séquentiellement et voyez si les échecs disparaissent.

    Flexibilité du banc d'essai
    Il est désormais possible de remplacer "PERL5OPT" et ses similaires dans t/TEST.
    Chronomètre de tests
    Plusieurs tests qui risquent de planter indéfiniment en cas d'échec intègrent désormais une fonctionnalité de "chronomètre" qui les tuera après un délai d'expiration, ce qui contribue à garantir que "make test" et "make test_harness" s'exécutent automatiquement jusqu'à la fin.

    Nouveaux tests

    New or Changed Diagnostics

    New Diagnostics

    • SV allocation tracing has been added to the diagnostics enabled by -Dm. The tracing can alternatively output via the PERL_MEM_LOG mechanism, if that was enabled when the perl binary was compiled.
    • Smartmatch resolution tracing has been added as a new diagnostic. Use -DM to enable it.
    • A new debugging flag -DB now dumps subroutine definitions, leaving -Dx for its original purpose of dumping syntax trees.
    • Perl 5.12 provides a number of new diagnostic messages to help you write better code. See perldiag for details of these new messages.
    • Bad plugin affecting keyword '%s'
    • gmtime(%.0f) too large
    • Lexing code attempted to stuff non-Latin-1 character into Latin-1 input
    • Lexing code internal error (%s)
    • localtime(%.0f) too large
    • Overloaded dereference did not return a reference
    • Overloaded qr did not return a REGEXP
    • Perl_pmflag() is deprecated, and will be removed from the XS API
    • lvalue attribute ignored after the subroutine has been defined

      This new warning is issued when one attempts to mark a subroutine as lvalue after it has been defined.

    • Perl now warns you if ++ or -- are unable to change the value because it's beyond the limit of representation.

      This uses a new warnings category: "imprecision".

    • lc, uc, lcfirst, and ucfirst warn when passed undef.
    • Show constant in "Useless use of a constant in void context"
    • Prototype after '%s'
    • panic: sv_chop %s

      This new fatal error occurs when the C routine Perl_sv_chop() was passed a position that is not within the scalar's string buffer. This could be caused by buggy XS code, and at this point recovery is not possible.

    • The fatal error Malformed UTF-8 returned by \N is now produced if the charnames handler returns malformed UTF-8.
    • If an unresolved named character or sequence was encountered when compiling a regex pattern then the fatal error \N{NAME} must be resolved by the lexer is now produced. This can happen, for example, when using a single-quotish context like "$re = '\N{SPACE}'; /$re/;". See perldiag for more examples of how the lexer can get bypassed.
    • Invalid hexadecimal number in \N{U+...} is a new fatal error triggered when the character constant represented by ... is not a valid hexadecimal number.
    • The new meaning of \N as [^\n] is not valid in a bracketed character class, just like . in a character class loses its special meaning, and will cause the fatal error \N in a character class must be a named character: \N{...}.
    • The rules on what is legal for the ... in \N{...} have been tightened up so that unless the ... begins with an alphabetic character and continues with a combination of alphanumerics, dashes, spaces, parentheses or colons then the warning Deprecated character(s) in \N{...} starting at '%s' is now issued.
    • The warning Using just the first characters returned by \N{} will be issued if the charnames handler returns a sequence of characters which exceeds the limit of the number of characters that can be used. The message will indicate which characters were used and which were discarded.

    Changed Diagnostics

    A number of existing diagnostic messages have been improved or corrected:

    •
    A new warning category illegalproto allows finer-grained control of warnings around function prototypes.

    The two warnings:

    "Illegal character in prototype for %s : %s"
    "Prototype after '%c' for %s : %s"

    have been moved from the syntax top-level warnings category into a new first-level category, illegalproto. These two warnings are currently the only ones emitted during parsing of an invalid/illegal prototype, so one can now use

    no warnings 'illegalproto';

    to suppress only those, but not other syntax-related warnings. Warnings where prototypes are changed, ignored, or not met are still in the prototype category as before.

    • Deep recursion on subroutine "%s"

      It is now possible to change the depth threshold for this warning from the default of 100, by recompiling the perl binary, setting the C pre-processor macro PERL_SUB_DEPTH_WARN to the desired value.

    • Illegal character in prototype warning is now more precise when reporting illegal characters after _
    • mro merging error messages are now very similar to those produced by Algorithm::C3.
    • Amelioration of the error message "Unrecognized character %s in column %d"

      Changes the error message to "Unrecognized character %s; marked by <-- HERE after %s<-- HERE near column %d". This should make it a little simpler to spot and correct the suspicious character.

    • Perl now explicitly points to $. when it causes an uninitialized warning for ranges in scalar context.

    Reporting Bugs

    If you find what you think is a bug, you might check the articles recently posted to the comp.lang.perl.misc newsgroup and the perl bug database at http://rt.perl.org/perlbug/. There may also be information at http://www.perl.org/, the Perl Home Page.

    If you believe you have an unreported bug, please run the perlbug program included with your release. Be sure to trim your bug down to a tiny but sufficient test case. Your bug report, along with the output of "perl -V", will be sent off to perlbug@perl.org to be analyzed by the Perl porting team.

    If the bug you are reporting has security implications, which make it inappropriate to send to a publicly archived mailing list, then please send it to perl5-security-report@perl.org. This points to a closed subscription unarchived mailing list, which includes all the core committers, who will be able to help assess the impact of issues, figure out a resolution, and help co-ordinate the release of patches to mitigate or fix the problem across all platforms on which Perl is supported. Please only use this address for security issues in the Perl core, not for modules independently distributed on CPAN.
