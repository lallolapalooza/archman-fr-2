PERL56DELTA(1perl) Guide du programmeur Perl PERL56DELTA(1perl)

NOM

perl56delta - nouveautés de la version Perl v5.6.0

DESCRIPTION

Ce document décrit les différences entre la version 5.005 et la version 5.6.0.

Améliorations du cœur du langage

Clonage d'interpréteur, threads, et concurrence

Perl 5.6.0 introduit les bases pour l'exécution simultanée de plusieurs interpréteurs dans différents threads. En conjonction avec l'appel API perl_clone(), qui peut être utilisé pour dupliquer sélectivement l'état de n'importe quel interpréteur donné, il est possible de compiler un morceau de code une fois dans un interpréteur, de cloner cet interpréteur une ou plusieurs fois, et d'exécuter tous les interpréteurs résultants dans des threads distincts.

Sur la plateforme Windows, cette fonctionnalité est utilisée pour émuler fork() au niveau de l'interpréteur. Voir perlfork pour plus de détails.

Cette fonctionnalité est encore en cours d'évolution. Elle est destinée à terme à être utilisée pour cloner sélectivement une sous-routine et les données accessibles depuis cette sous-routine dans un interpréteur séparé et exécuter la sous-routine clonée dans un thread séparé. Comme il n'y a pas de données partagées entre les interpréteurs, peu ou pas de verrouillage sera nécessaire (sauf si des parties de la table des symboles sont explicitement partagées). Ceci est manifestement destiné à être un remplacement facile à utiliser du support des threads existant.

Le support du clonage d'interpréteurs et de la concurrence des interpréteurs peut être activé en utilisant l'option de configuration -Dusethreads (voir win32/Makefile comment l'activer sous Windows). L'exécutable perl résultant sera fonctionnellement identique à celui qui a été compilé avec -Dmultiplicity, mais l'appel API perl_clone() ne sera disponible que dans le premier.

-Dusethreads active par défaut le macro cpp USE_ITHREADS, qui à son tour active les changements du code source Perl qui fournissent une séparation claire entre l'arbre des opérations (op tree) et les données sur lesquelles il opère. Le premier est immuable, et peut donc être partagé entre un interpréteur et tous ses clones, tandis que le second est considéré comme local à chaque interpréteur, et est donc copié pour chaque clone.

Notez que compiler Perl avec l'option de configuration -Dusemultiplicity est suffisant si vous souhaitez exécuter plusieurs interpréteurs indépendants simultanément dans différents threads. -Dusethreads ne fournit que la fonctionnalité supplémentaire de l'appel API perl_clone() et d'autres supports pour exécuter des interpréteurs clonés simultanément.

NOTE : Ceci est une fonctionnalité expérimentale. Les détails
d'implémentation sont sujets à modification.

Catégories d'avertissements à portée lexicale

Vous pouvez maintenant contrôler la granularité des avertissements émis par Perl à un niveau plus fin en utilisant le pragma "use warnings". warnings et perllexwarn contiennent une documentation abondante sur cette fonctionnalité.

Support de Unicode et UTF-8

Perl utilise maintenant UTF-8 comme sa représentation interne pour les chaînes de caractères. Les pragmas "utf8" et "bytes" sont utilisés pour contrôler ce support dans la portée lexicale actuelle. Voir perlunicode, utf8 et bytes pour plus d'informations.

Cette fonctionnalité devrait évoluer rapidement pour supporter une forme de disciplines d'E/S qui peuvent être utilisées pour spécifier le type de données d'entrée et de sortie (octets ou caractères). Jusqu'à ce que cela se produise, des modules supplémentaires de CPAN seront nécessaires pour compléter la boîte à outils pour le traitement de Unicode.

NOTE : Ceci devrait être considéré comme une fonctionnalité expérimentale.
Les détails d'implémentation sont sujets à modification.

Support de l'interpolation de caractères nommés

La nouvelle échappatoire "\N" interpole des caractères nommés dans les chaînes. Par exemple, "Salut ! \N{VISAGE SOURIANT BLANC}" est évalué à une chaîne avec un smiley Unicode à la fin.

Déclarations "our"

Une déclaration "our" introduit une valeur qui peut être mieux comprise comme un alias symbolique de portée lexicale vers une variable globale dans le paquet qui était courant lorsque la variable a été déclarée. Ceci est principalement utile comme alternative au pragma "vars", mais offre également la possibilité d'introduire le typage et d'autres attributs pour de telles variables. Voir "our" dans perlfunc.

Support des chaînes représentées comme un vecteur d'ordinal

Les littéraux de la forme "v1.2.3.4" sont maintenant analysés comme une chaîne composée de caractères avec les ordinals spécifiés. C'est une manière alternative et plus lisible de construire des chaînes (potentiellement Unicode) au lieu d'interpoler des caractères, comme dans "\x{1}\x{2}\x{3}\x{4}". Le "v" initial peut être omis s'il y a plus de deux ordinals, donc 1.2.3 est analysé de la même manière que "v1.2.3".

Les chaînes écrites dans cette forme sont également utiles pour représenter des versions de "nombres". Il est facile de comparer de telles versions de "nombres" (qui sont en réalité de simples chaînes) en utilisant n'importe lequel des opérateurs de comparaison de chaînes habituels "eq", "ne", "lt", "gt", etc., ou d'effectuer des opérations binaires sur elles en utilisant "|", "&", etc.

En conjonction avec la nouvelle variable magique $^V (qui contient la version de Perl sous forme de chaîne), de tels littéraux peuvent être utilisés comme un moyen lisible de vérifier si vous exécutez une version particulière de Perl :

# cela sera également analysé dans les versions plus anciennes de Perl
if ($^V and $^V gt v5.6.0) {
    # nouvelles fonctionnalités supportées
}

"require" et "use" ont également une magie spéciale pour supporter de tels littéraux, mais cette utilisation particulière devrait être évitée car elle conduit à des messages d'erreur trompeurs sous les versions de Perl qui ne supportent pas les chaînes vectorielles. L'utilisation d'un vrai numéro de version garantira un comportement correct dans toutes les versions de Perl :

require 5.006;    # vérification à l'exécution pour v5.6
use 5.006_001;    # vérification à la compilation pour v5.6.1

De plus, "sprintf" et "printf" supportent le flag de format spécifique à Perl %v pour afficher les ordinals des caractères dans des chaînes arbitraires :

printf "v%vd", $^V;         # affiche la version actuelle, comme "v5.5.650"
printf "%*vX", ":", $addr;  # formate une adresse IPv6
printf "%*vb", " ", $bits;  # affiche une chaîne de bits

Voir "Constructeurs de valeurs scalaires" dans perldata pour plus d'informations.

Système de numérotation de version Perl amélioré

À partir de la version Perl 5.6.0, la convention de numéro de version a été modifiée pour un schéma de "nombre entier pointé" plus couramment trouvé dans les projets open source.

Les versions de maintenance de v5.6.0 seront publiées sous les noms v5.6.1, v5.6.2 etc. La prochaine série de développement suivant v5.6.0 sera numérotée v5.7.x, commençant par v5.7.0, et la prochaine version de production majeure suivant v5.6.0 sera v5.8.0.

Le module English définit maintenant $PERL_VERSION par $^V (une valeur de chaîne) plutôt que par $] (une valeur numérique). (Ceci est une incompatibilité potentielle. Envoyez-nous un rapport via perlbug si vous êtes affecté par cela.)

La syntaxe v1.2.3 est maintenant également légale en Perl. Voir "Support des chaînes représentées comme un vecteur d'ordinal" pour plus d'informations.

Pour s'adapter à l'utilisation par le nouveau système de versionnement d'au moins trois chiffres significatifs pour chaque composant de version, la méthode utilisée pour incrémenter le numéro de sous-version a également légèrement changé.

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

Nous supposons que les versions antérieures à v5.6.0 ont incrémenté le composant de sous-version par multiples de 10. Les versions postérieures à v5.6.0 les incrémenteront de 1. Ainsi, en utilisant la nouvelle notation, 5.005_03 est le « même » que v5.5.30, et la première version de maintenance suivant v5.6.0 sera v5.6.1 (qui doit être interprétée comme étant équivalente à une valeur à virgule flottante de 5.006_001 dans l'ancien format, stockée dans $]).

Nouvelle syntaxe pour déclarer les attributs de sous-routine

Auparavant, si vous vouliez marquer une sous-routine comme étant un appel de méthode ou comme nécessitant un lock() automatique lors de son entrée, vous deviez le déclarer avec un pragma "use attrs" dans le corps de la sous-routine. Cela peut maintenant être accompli avec la syntaxe de déclaration, comme suit :

sub mymethod : locked method;
...
sub mymethod : locked method {
    ...
}
sub othermethod :locked :method;
...
sub othermethod :locked :method {
    ...
}

(Notez que seul le premier ":" est obligatoire, et les espaces entourant le ":" sont facultatifs.)

AutoSplit.pm et SelfLoader.pm ont été mis à jour pour conserver les attributs avec les stubs qu'ils fournissent. Voir attributes.

Les descripteurs de fichiers et de répertoires peuvent être autovivifiés

Similaire à la manière dont des constructions telles que "$x->[0]" autovivifient une référence, les constructeurs de descripteurs ( open(), opendir(), pipe(), socketpair(), sysopen(), socket(), et accept()) autovivifient maintenant un descripteur de fichier ou de répertoire si le descripteur qui leur est passé est une variable scalaire non initialisée. Cela permet d'utiliser des constructions telles que "open(my $fh, ...)" et "open(local $fh,...)" pour créer des descripteurs de fichiers qui seront automatiquement fermés à la fin de la portée, à condition qu'il n'y ait pas d'autres références à eux. Cela élimine en grande partie le besoin de typeglobs lors de l'ouverture de descripteurs de fichiers qui doivent être transmis, comme dans l'exemple suivant :

sub myopen {
    open my $fh, "@_"
         or die "Can't open '@_': $!";
    return $fh;
}
{
    my $f = myopen("</etc/motd");
    print <$f>;
    # $f implicitement fermé ici
}

open() avec plus de deux arguments

Si open() reçoit trois arguments au lieu de deux, le deuxième argument est utilisé comme mode et le troisième argument est considéré comme le nom du fichier. Ceci est principalement utile pour se protéger contre les comportements magiques involontaires de la forme traditionnelle à deux arguments. Voir « open » dans perlfunc.

Support 64 bits

Toute plateforme qui possède des entiers 64 bits soit

(1) nativement sous forme de longs ou d'entiers
(2) via des indicateurs de compilation spéciaux
(3) en utilisant long long ou int64_t

est capable d'utiliser des « quads » (entiers 64 bits) comme suit :

  • constantes (décimales, hexadécimales, octales, binaires) dans le code
  • arguments de oct() et hex()
  • arguments de print(), printf() et sprintf() (préfixes de drapeau ll, L, q)
  • affichés comme tels
  • formats « q » et « Q » de pack() et unpack()
  • dans les calculs arithmétiques de base : + - * / % (NOTE : opérer près des limites des valeurs entières peut produire des résultats surprenants)
  • dans les calculs binaires : & | ^ ~ << >> (NOTE : ceux-ci étaient forcés à une largeur de 32 bits mais opèrent maintenant sur la largeur native complète.)
  • vec()

Notez que sauf si vous avez le cas (a), vous devrez configurer et compiler Perl en utilisant l'indicateur Configure -Duse64bitint.

NOTE : Les indicateurs Configure -Duselonglong et -Duse64bits ont été
dépréciés. Utilisez -Duse64bitint à la place.

Il existe en fait deux modes de fonctionnement 64 bits : le premier est obtenu en utilisant Configure -Duse64bitint et le second en utilisant Configure -Duse64bitall. La différence est que le premier est minimal et le second maximal. Le premier fonctionne dans plus d'endroits que le second.

Le "use64bitint" ne fait que ce qui est nécessaire pour obtenir des entiers 64 bits dans Perl (cela peut signifier, par exemple, l'utilisation de « long longs ») tandis que votre mémoire peut toujours être limitée à 2 gigaoctets (car vos pointeurs pourraient toujours être 32 bits). Notez que le nom "64bitint" n'implique pas que votre compilateur C utilisera des "int"s 64 bits (il pourrait le faire, mais il n'est pas obligé) : le "use64bitint" signifie que vous pourrez avoir des valeurs scalaires de 64 bits de large.

Le "use64bitall" va jusqu'au bout en essayant de passer également les entiers (si possible), les longs (et les pointeurs) à 64 bits. Cela peut créer un Perl encore plus incompatible en termes de binaire que -Duse64bitint : l'exécutable résultant peut ne pas fonctionner du tout sur une machine 32 bits, ou vous devrez peut-être redémarrer/reconfigurer/reconstruire votre système d'exploitation pour qu'il soit conscient du 64 bits.

Les systèmes nativement 64 bits comme Alpha et Cray n'ont besoin ni de -Duse64bitint ni de -Duse64bitall.

Enfin et surtout : notez qu'en raison de l'habitude de Perl d'utiliser toujours des nombres à virgule flottante, les quads ne sont toujours pas de vrais entiers. Lorsque les quads dépassent leurs limites (0...18_446_744_073_709_551_615 sans signe, -9_223_372_036_854_775_808...9_223_372_036_854_775_807 signés), ils sont silencieusement promus en nombres à virgule flottante, après quoi ils commenceront à perdre de la précision (dans leurs chiffres les moins significatifs).

NOTE : Le support 64 bits est encore expérimental sur la plupart des plateformes.
Le support existant ne couvre que le modèle de données LP64. En particulier, le
modèle de données LLP64 n'est pas encore supporté. Les bibliothèques 64 bits et les
API système sur de nombreuses plateformes ne sont pas stabilisées - votre expérience peut varier.

Support des grands fichiers

Si vous avez des systèmes de fichiers qui prennent en charge les « grands fichiers » (fichiers de plus de 2 gigaoctets), vous pouvez maintenant également les créer et y accéder depuis Perl.

NOTE : L'action par défaut est d'activer le support des grands fichiers, si
disponible sur la plateforme.

Si le support des grands fichiers est activé, et que vous avez une constante Fcntl O_LARGEFILE, O_LARGEFILE est automatiquement ajouté aux indicateurs de sysopen().

Attention, sauf si votre système de fichiers prend également en charge les « fichiers épars », chercher jusqu'à des pétaoctets peut être déconseillé.

Notez qu'en plus de nécessiter un système de fichiers approprié pour gérer les grands fichiers, vous devrez peut-être également ajuster vos limites maximales de taille de fichier par processus (ou par système, ou par groupe de processus, ou par utilisateur) avant d'exécuter des scripts Perl qui tentent de gérer de grands fichiers, surtout si vous avez l'intention d'écrire de tels fichiers.

Enfin, en plus de vos limites de taille de fichier par processus/groupe de processus, vous pourriez avoir des quotas sur vos systèmes de fichiers qui vous empêchent (votre ID utilisateur ou votre ID de groupe d'utilisateurs) d'utiliser de grands fichiers.

L'ajustement de vos limites de processus/utilisateur/groupe/système de fichiers/système d'exploitation dépasse le cadre du langage Perl. Pour les limites de processus, vous pouvez essayer d'augmenter les limites en utilisant la commande limits/limit/ulimit de votre shell avant d'exécuter Perl. L'extension BSD::Resource (non incluse dans la distribution Perl standard) peut également être utile, elle offre l'interface getrlimit/setrlimit qui peut être utilisée pour ajuster les limites d'utilisation des ressources des processus, y compris la limite maximale de taille de fichier.

Long doubles

Sur certains systèmes, vous pourrez peut-être utiliser des « long doubles » pour améliorer la plage et la précision de vos nombres à virgule flottante de double précision (c'est-à-dire les nombres de Perl). Utilisez Configure -Duselongdouble pour activer ce support (s'il est disponible).

« plus de bits »

Vous pouvez utiliser « Configure -Dusemorebits » pour activer à la fois le support 64 bits et le support long double.

Support amélioré pour les sous-routines de sort()

Les sous-routines Perl avec un prototype de "($$)", et les XSUBs en général, peuvent maintenant être utilisées comme sous-routines de tri. Dans les deux cas, les deux éléments à comparer sont passés comme paramètres normaux dans @_. Voir « sort » dans perlfunc.

Pour les sous-routines de tri non prototypées, le comportement historique consistant à passer les éléments à comparer comme variables globales $a et $b reste inchangé.

« sort $coderef @foo » autorisé

sort() n'acceptait pas de référence de sous-routine comme fonction de comparaison dans les versions précédentes. Ceci est maintenant autorisé.

La glob de fichiers est implémentée en interne

Perl utilise maintenant automatiquement l'implémentation File::Glob de l'opérateur glob(). Cela évite d'utiliser un processus csh externe et les problèmes qui y sont associés.

NOTE : Il s'agit actuellement d'une fonctionnalité expérimentale. Les interfaces et
l'implémentation sont susceptibles d'être modifiées.

Support des blocs CHECK

En plus de "BEGIN", "INIT", "END", "DESTROY" et "AUTOLOAD", les sous-routines nommées "CHECK" sont maintenant spéciales. Celles-ci sont mises en file d'attente pendant la compilation et se comportent de manière similaire aux blocs END, sauf qu'elles sont appelées à la fin de la compilation plutôt qu'à la fin de l'exécution. Elles ne peuvent pas être appelées directement.

Syntaxe de classe de caractères POSIX [: :] supportée

Par exemple, pour faire correspondre des caractères alphabétiques, utilisez /[[:alpha:]]/. Voir perlre pour plus de détails.

Meilleur générateur de nombres pseudo-aléatoires

Dans les versions 5.005_0x et antérieures, la fonction rand() de Perl utilisait la fonction rand(3) de la bibliothèque C. À partir de la version 5.005_52, Configure teste drand48(), random() et rand() (dans cet ordre) et sélectionne la première qu'il trouve.

Ces changements devraient résulter en de meilleurs nombres aléatoires de la part de rand().

Opérateur « qw// » amélioré

L'opérateur "qw//" est maintenant évalué au moment de la compilation en une liste réelle au lieu d'être remplacé par un appel à split() à l'exécution. Cela supprime le comportement erroné déroutant de "qw//" en contexte scalaire, qui avait hérité ce comportement de split().

Ainsi :

$foo = ($bar) = qw(a b c); print "$foo|$bar\n";

affiche maintenant correctement « 3|a » au lieu de « 2|a ».

Meilleur comportement en cas extrême des hashs

De petites modifications dans l'algorithme de hachage ont été implémentées afin d'améliorer la distribution des bits de poids faible dans la valeur hachée. Ceci devrait permettre d'obtenir de meilleures performances sur les clés qui sont des séquences répétées.

Format 'Z' de pack() pris en charge

Le nouveau type de format 'Z' est utile pour empaqueter et dépaqueter des chaînes de caractères terminées par un caractère nul. Voir « pack » dans perlfunc.

Modificateur de format '!' de pack() pris en charge

Le nouveau modificateur de type de format '!' est utile pour empaqueter et dépaqueter des entiers courts, entiers et longs natifs. Voir « pack » dans perlfunc.

pack() et unpack() prennent en charge les chaînes de caractères comptées

Le caractère de modèle '/' peut être utilisé pour spécifier un type de chaîne de caractères comptée à empaqueter ou dépaqueter. Voir « pack » dans perlfunc.

Commentaires dans les modèles de pack()

Le caractère '#' dans un modèle introduit un commentaire jusqu'à la fin de la ligne. Ceci facilite la documentation des modèles de pack().

Références faibles

Dans les versions précédentes de Perl, il était impossible de mettre en cache des objets de manière à permettre leur suppression si la dernière référence externe à la cache était supprimée. La référence dans la cache maintenait un compte de références sur l'objet, et les objets n'étaient jamais détruits.

Un autre problème familier est celui des références circulaires. Lorsqu'un objet se référence lui-même, son compte de références ne descendait jamais à zéro, et il n'était pas détruit avant que le programme ne soit sur le point de se terminer.

Les références faibles résolvent cela en permettant de « affaiblir » n'importe quelle référence, c'est-à-dire de la faire ne pas compter dans le compte de références. Lorsque la dernière référence non faible à un objet est supprimée, l'objet est détruit et toutes les références faibles à cet objet sont automatiquement définies à undef.

Pour utiliser cette fonctionnalité, vous avez besoin du module Devel::WeakRef de CPAN, qui contient une documentation supplémentaire.

NOTE : Ceci est une fonctionnalité expérimentale. Les détails sont susceptibles de changer.

Nombres binaires pris en charge

Les nombres binaires sont maintenant pris en charge en tant que littéraux, dans les formats s?printf, et oct() :

$answer = 0b101010;
printf "The answer is: %b\n", oct("0b101010");

Sous-routines lvalue

Les sous-routines peuvent maintenant retourner des lvalues modifiables. Voir « Sous-routines lvalue » dans perlsub.

NOTE : Ceci est une fonctionnalité expérimentale. Les détails sont susceptibles de changer.

Certaines flèches peuvent être omises dans les appels via des références

Perl autorise maintenant l'omission de la flèche dans de nombreuses constructions impliquant des appels de sous-routines via des références. Par exemple, "$foo[10]->('foo')" peut maintenant s'écrire "$foo[10]('foo')". Ceci est très similaire à la manière dont la flèche peut être omise de "$foo[10]->{'foo'}". Notez cependant que la flèche est toujours requise pour "foo(10)->('bar')".

Les opérateurs d'affectation booléenne sont des lvalues légales

Des constructions telles que "($a ||= 2) += 1" sont maintenant autorisées.

exists() est pris en charge sur les noms de sous-routines

La fonction intégrée exists() fonctionne maintenant sur les noms de sous-routines. Une sous-routine est considérée comme existante si elle a été déclarée (même implicitement). Voir « exists » dans perlfunc pour des exemples.

exists() et delete() sont pris en charge sur les éléments de tableaux

Les fonctions intégrées exists() et delete() fonctionnent maintenant aussi sur les tableaux simples. Le comportement est similaire à celui sur les éléments de hash.

exists() peut être utilisé pour vérifier si un élément de tableau a été initialisé. Cela évite l'auto-vivification des éléments de tableau qui n'existent pas. Si le tableau est lié, la méthode EXISTS() dans le package lié correspondant sera appelée.

delete() peut être utilisé pour supprimer un élément du tableau et le retourner. L'élément du tableau à cette position revient à son état non initialisé, de sorte que tester le même élément avec exists() retournera faux. Si l'élément se trouve être le dernier, la taille du tableau diminue également jusqu'au plus haut élément qui renvoie vrai pour exists(), ou 0 si aucun tel élément n'est trouvé. Si le tableau est lié, la méthode DELETE() dans le package lié correspondant sera appelée.

Voir « exists » dans perlfunc et « delete » dans perlfunc pour des exemples.

Les pseudo-hashs fonctionnent mieux

Le déréférencement de certains types de valeurs de référence dans un pseudo-hash, tel que "$ph->{foo}[1]", était accidentellement interdit. Ceci a été corrigé.

Lorsqu'elle est appliquée à un élément de pseudo-hash, exists() indique maintenant si la valeur spécifiée existe, et pas seulement si la clé est valide.

delete() fonctionne maintenant sur les pseudo-hashs. Lorsqu'il est donné un élément ou une tranche de pseudo-hash, il supprime les valeurs correspondant aux clés (mais pas les clés elles-mêmes). Voir « Pseudo-hashes : Utiliser un tableau comme hash » dans perlref.

Les tranches de pseudo-hash avec des clés constantes sont maintenant optimisées en recherches dans des tableaux au moment de la compilation.

Les affectations de listes aux tranches de pseudo-hash sont maintenant prises en charge.

Le pragma "fields" fournit maintenant des moyens de créer des pseudo-hashs, via fields::new() et fields::phash(). Voir fields.

NOTE : Le type de données pseudo-hash reste expérimental.
Se limiter aux éléments d'interface fournis par le pragma fields
vous protégera des futures modifications.

Vidange automatique des tampons de sortie

fork(), exec(), system(), qx//, et les open() de pipe vident maintenant les tampons de tous les fichiers ouverts en écriture lorsque l'opération a été tentée. Cela élimine la plupart des problèmes de mise en mémoire tampon déroutants rencontrés par les utilisateurs ne connaissant pas la gestion interne des E/S par Perl.

Cela n'est pas pris en charge sur certaines plateformes comme Solaris où une implémentation suffisamment correcte de fflush(NULL) n'est pas disponible.

Meilleures diagnostics sur les opérations de filehandle insensées

Les constructions telles que open(<FH>) et close(<FH>) sont des erreurs de compilation. Tenter de lire à partir de filehandles ouverts uniquement en écriture produira maintenant des avertissements (tout comme écrire sur des filehandles en lecture seule).

Lorsque possible, les données tamponnées sont éliminées du filehandle d'entrée dupliqué

"open(NEW, "<&OLD")" tente maintenant d'éliminer toutes les données qui avaient été précédemment lues et mises en tampon dans "OLD" avant de dupliquer le handle. Sur les plateformes où cela est autorisé, la prochaine opération de lecture sur "NEW" retournera les mêmes données que l'opération correspondante sur "OLD". Auparavant, elle aurait retourné les données du début du bloc disque suivant à la place.

eof() a la même magie ancienne que <0xC2><0xA0><>

eof() retournait vrai si aucune tentative de lecture sur "<>" n'avait encore été faite. eof() a été modifié pour avoir un peu de sa propre magie, il ouvre maintenant les fichiers "<>".

binmode() peut être utilisé pour définir les modes :crlf et :raw

binmode() accepte maintenant un deuxième argument qui spécifie une discipline pour le handle en question. Les deux pseudo-disciplines « :raw » et « :crlf » sont actuellement prises en charge sur les plateformes dérivées de DOS. Voir « binmode » dans perlfunc et open.

Le fichiertest « -T » reconnaît les fichiers encodés en UTF-8 comme « texte »

L'algorithme utilisé pour le fichiertest "-T" a été amélioré pour identifier correctement le contenu UTF-8 comme « texte ».

system(), backticks et pipe ouvrent maintenant pour refléter l'échec de exec()

Sur Unix et les plateformes similaires, system(), qx() et open(FOO, "cmd |") etc., sont implémentés via fork() et exec(). Lorsque l' exec() sous-jacent échoue, les versions antérieures ne signalaient pas correctement l'erreur, car l' exec() se produisait dans un processus différent.

Le processus enfant communique maintenant avec le parent concernant l'erreur dans le lancement de la commande externe, ce qui permet à ces constructions de retourner avec leur valeur d'erreur habituelle et de définir $!.

Diagnostics améliorés

Les numéros de ligne ne sont plus supprimés (dans les circonstances les plus probables) pendant la phase de destruction globale.

Les diagnostics émis par le code exécuté dans des threads autres que le thread principal sont maintenant accompagnés de l'identifiant du thread.

Les caractères nuls intégrés dans les diagnostics apparaissent maintenant. Ils avaient l'habitude de tronquer le message dans les versions précédentes.

$foo::a et $foo::b sont maintenant exemptés des avertissements de "typo possible" uniquement si sort() est rencontré dans le paquetage "foo".

Les séquences d'échappement alphabétiques non reconnues rencontrées lors de l'analyse des constructions de guillemets génèrent maintenant un avertissement, car elles peuvent acquérir de nouvelles sémantiques dans les versions ultérieures de Perl.

De nombreux diagnostics rapportent maintenant l'opération interne à laquelle l'avertissement a été provoqué, comme suit :

Utilisation de valeur non initialisée dans la concaténation (.) à (eval 1) ligne 1.
Utilisation de valeur non initialisée dans print à (eval 1) ligne 1.

Les diagnostics qui se produisent dans un eval peuvent également rapporter le fichier et le numéro de ligne où se trouve l'eval, en plus du numéro de séquence de l'eval et du numéro de ligne dans le texte évalué lui-même. Par exemple :

Pas assez d'arguments pour scalaire à (eval 4)[newlib/perl5db.pl:1411] ligne 2, à la fin du fichier

Les diagnostics suivent STDERR

La sortie de diagnostic va maintenant vers le fichier où le handle "STDERR" pointe, au lieu d'aller toujours vers le "stderr" de la bibliothèque d'exécution C sous-jacente.

Comportement plus cohérent de close-on-exec

Sur les systèmes qui prennent en charge un drapeau close-on-exec sur les descripteurs de fichier, le drapeau est maintenant défini pour tous les descripteurs créés par pipe(), socketpair(), socket() et accept(), si cela est justifié par la valeur de $^F qui peut être en vigueur. Les versions précédentes négligeaient de définir le drapeau pour les descripteurs créés avec ces opérateurs. Voir "pipe" dans perlfunc, "socketpair" dans perlfunc, "socket" dans perlfunc, "accept" dans perlfunc, et "$^F" dans perlvar.

Facilité d'utilisation de syswrite()

L'argument de longueur de syswrite() est devenu facultatif.

Meilleures vérifications de syntaxe des opérateurs unaires entre parenthèses

Des expressions telles que :

print defined(&foo,&bar,&baz);
print uc("foo","bar","baz");
undef($foo,&bar);

étaient autorisées par inadvertance dans les versions précédentes, et produisaient un comportement imprévisible. Certaines produisaient des avertissements accessoires lorsqu'elles étaient utilisées de cette manière ; d'autres faisaient silencieusement la mauvaise chose.

Les formes entre parenthèses de la plupart des opérateurs unaires qui attendent un seul argument garantissent maintenant qu'ils ne sont pas appelés avec plus d'un argument, faisant des cas montrés ci-dessus des erreurs de syntaxe. Le comportement habituel de :

print defined &foo, &bar, &baz;
print uc "foo", "bar", "baz";
undef $foo, &bar;

reste inchangé. Voir perlop.

Les opérateurs bitwise prennent en charge la largeur complète des entiers natifs

Les opérateurs bitwise (& | ^ ~ << >>) opèrent maintenant sur la largeur intégrale native complète (dont la taille exacte est disponible dans $Config{ivsize}). Par exemple, si votre plateforme est nativement 64 bits ou si Perl a été configuré pour utiliser des entiers 64 bits, ces opérations s'appliquent à 8 octets (par opposition à 4 octets sur les plateformes 32 bits). Pour la portabilité, assurez-vous de masquer les bits excédentaires dans le résultat de "~" unaire, par exemple, "~$x & 0xffffffff".

Fonctionnalités de sécurité améliorées

Plus d'opérations potentiellement dangereuses entachent leurs résultats pour une sécurité améliorée.

Les champs "passwd" et "shell" renvoyés par getpwent(), getpwnam() et getpwuid() sont maintenant entachés, car l'utilisateur peut affecter son propre mot de passe crypté et son shell de connexion.

La variable modifiée par shmread(), et les messages renvoyés par msgrcv() (et son interface orientée objet IPC::SysV::Msg::rcv) sont également entachés, car d'autres processus non fiables peuvent modifier les messages et les segments de mémoire partagée à leurs propres fins néfastes.

Prototype de bareword plus fonctionnel (*)

Les prototypes de bareword ont été rationalisés pour leur permettre d'être utilisés pour remplacer les fonctions intégrées qui acceptent des barewords et les interprètent d'une manière spéciale, telles que "require" ou "do".

Les arguments prototypés comme "*" seront maintenant visibles dans la sous-routine soit comme un scalaire simple, soit comme une référence à un typeglob. Voir "Prototypes" dans perlsub.

"require" et "do" peuvent être remplacés

"require" et les opérations "do 'file'" peuvent être remplacées localement en important des sous-routines du même nom dans le paquetage courant (ou globalement en les important dans l'espace de noms CORE::GLOBAL::). Remplacer "require" affectera également "use", à condition que le remplacement soit visible au moment de la compilation. Voir "Overriding Built-in Functions" dans perlsub.

$^X les variables peuvent maintenant avoir des noms plus longs qu'un caractère

Auparavant, $^X était synonyme de ${"\cX"}, mais $^XY était une erreur de syntaxe. Maintenant, les noms de variables qui commencent par un caractère de contrôle peuvent être arbitrairement longs. Cependant, pour des raisons de compatibilité, ces variables *doivent* être écrites avec des accolades explicites, comme "${^XY}" par exemple. "${^XYZ}" est synonyme de ${"\cXYZ"}. Les noms de variables avec plus d'un caractère de contrôle, tels que "${^XY^Z}", sont illégaux.

La syntaxe ancienne n'a pas changé. Comme auparavant, `^X' peut être soit un caractère de contrôle X littéral, soit la séquence de deux caractères `caret' plus `X'. Lorsque les accolades sont omises, le nom de la variable s'arrête après le caractère de contrôle. Ainsi "$^XYZ" continue d'être synonyme de "$^X . "YZ"" comme auparavant.

Comme auparavant, les variables lexicales ne peuvent pas avoir de noms commençant par des caractères de contrôle. Comme auparavant, les variables dont les noms commencent par un caractère de contrôle sont toujours forcées d'être dans le paquetage `main'. Toutes ces variables sont réservées pour des extensions futures, à l'exception de celles qui commencent par "^_", qui peuvent être utilisées par des programmes utilisateurs et dont on garantit qu'elles n'acquerront pas de signification spéciale dans une version future de Perl.

Nouvelle variable $^C reflète le commutateur "-c"

$^C a une valeur booléenne qui reflète si perl est exécuté en mode de seule compilation (c'est-à-dire via le commutateur "-c"). Comme les blocs BEGIN sont exécutés dans de telles conditions, cette variable permet au code perl de déterminer si les actions qui n'ont de sens que pendant l'exécution normale sont justifiées. Voir perlvar.

Nouvelle variable $^V contient la version de Perl sous forme de chaîne

$^V contient le numéro de version de Perl sous forme de chaîne composée de caractères dont les ordinals correspondent aux numéros de version, c'est-à-dire v5.6.0. Ceci peut être utilisé dans des comparaisons de chaînes.

Voir "Support for strings represented as a vector of ordinals" pour un exemple.

Avertissements optionnels sur l'an 2000

Si Perl est construit avec le macro cpp "PERL_Y2KWARN" défini, il émet des avertissements optionnels lors de la concaténation du nombre 19 avec un autre nombre.

Ce comportement doit être spécifiquement activé lors de l'exécution de Configure. Voir INSTALL et README.Y2K.

Les tableaux s'interpolent maintenant toujours dans les chaînes à guillemets doubles

Dans les chaînes à guillemets doubles, les tableaux s'interpolent maintenant, quoi qu'il arrive. Le comportement dans les versions antérieures de perl 5 était que les tableaux s'interpolaient dans les chaînes si le tableau avait été mentionné avant que la chaîne ne soit compilée, et sinon Perl levait une erreur fatale de compilation. Dans les versions 5.000 à 5.003, l'erreur était

Le @exemple littéral nécessite maintenant une barre oblique inverse

Dans les versions 5.004_01 à 5.6.0, l'erreur était

> 
Dans une chaîne, @exemple doit maintenant s'écrire \@exemple

L'idée était d'habituer les gens à écrire "fred\@example.com" lorsqu'ils voulaient un symbole "@" littéral, tout comme ils ont toujours écrit "Donne-moi mon \$5" lorsqu'ils voulaient un symbole "$" littéral.

À partir de la version 5.6.1, lorsque Perl rencontre un symbole "@" dans une chaîne entre guillemets doubles, il tente *toujours* d'interpoler un tableau, qu'il ait été utilisé ou déclaré auparavant ou non. L'erreur fatale a été rétrogradée en un avertissement facultatif :

Interpolation non intentionnelle possible de @exemple dans la chaîne

Cela vous avertit que "fred@example.com" sera transformé en "fred.com" si vous n'échappez pas le "@". Voir http://perl.plover.com/at-error.html pour plus de détails sur l'historique de ce changement.

@- et @+ fournissent les décalages de début/fin des correspondances regex

Les nouvelles variables magiques @- et @+ fournissent respectivement les décalages de début et de fin de $&, $1, $2, etc. Voir perlvar pour les détails.

Significant bug fixes

<HANDLE> on empty files

With $/ set to "undef", "slurping" an empty file returns a string of zero length (instead of "undef", as it used to) the first time the HANDLE is read after $/ is set to "undef". Further reads yield "undef".

This means that the following will append "foo" to an empty file (it used to do nothing):

perl -0777 -pi -e 's/^/foo/' empty_file

The behaviour of:

perl -pi -e 's/^/foo/' empty_file

is unchanged (it continues to leave the file empty).

"eval '...'" improvements

Line numbers (as reflected by caller() and most diagnostics) within "eval '...'" were often incorrect where here documents were involved. This has been corrected.

Corrections

We were searching in the wrong place for lexical variables. The lexical search now correctly ends at the boundary of the subroutine's block.

L'utilisation de "return" dans "eval {...}" empêchait $@ d'être réinitialisé correctement lorsqu'aucune exception ne se produisait dans l'eval. Ceci est corrigé.

L'analyse des here documents était erronée lorsqu'ils apparaissaient comme expression de remplacement dans "eval 's/.../.../e'". Ceci est corrigé.

Toutes les erreurs de compilation sont de vraies erreurs

Certaines "erreurs" rencontrées au moment de la compilation étaient, par nécessité, générées comme avertissements suivis de la terminaison éventuelle du programme. Cela permettait de signaler davantage d'erreurs en une seule exécution, plutôt que de provoquer un arrêt brutal à la première erreur rencontrée.

Le mécanisme de signalement de ces erreurs a été réimplémenté pour mettre en file d'attente les erreurs de compilation et les signaler à la fin de la compilation comme de vraies erreurs plutôt que comme des avertissements. Cela corrige les cas où des messages d'erreur fuyaient sous forme d'avertissements lors de la compilation de code à l'exécution à l'aide de "eval STRING", et permet également de piéger de manière fiable ces erreurs à l'aide de "eval "..."".

Les filehandles fermés implicitement sont plus sûrs

Parfois, les filehandles fermés implicitement (comme lorsqu'ils sont localisés, et que Perl les ferme automatiquement en sortant de la portée) pouvaient involontairement définir $? ou $!. Ceci a été corrigé.

Le comportement des tranches de liste est plus cohérent

Lors de la prise d'une tranche d'une liste littérale (par opposition à une tranche d'un tableau ou d'une table associative), Perl renvoyait auparavant une liste vide si le résultat était composé de toutes des valeurs undef.

Le nouveau comportement consiste à produire une liste vide si (et seulement si) la liste d'origine était vide. Considérons l'exemple suivant :

@a = (1,undef,undef,2)[2,1,2];

Le comportement précédent aurait eu pour résultat que @a n'ait aucun élément. Le nouveau comportement garantit qu'il a trois éléments indéfinis.

Notez en particulier que le comportement des tranches des cas suivants reste inchangé :

@a = ()[1,2];
@a = (getpwent)[7,0];
@a = (anything_returning_empty_list())[2,1,2];
@a = @b[2,1,2];
@a = @c{'a','b','c'};

Voir perldata.

Une référence scalaire de prototype permet désormais correctement un élément de table associative ou de tableau dans cette position.

"goto &sub" et AUTOLOAD

Changements incompatibles

Incompatibilités de source Perl

Attention, toute nouvelle mise en garde ajoutée ou toute ancienne mise en garde améliorée ne sont pas considérées comme des changements incompatibles.

Étant donné que toutes les nouvelles mises en garde doivent être explicitement demandées via le commutateur "-w" ou le pragma "warnings", il incombe en fin de compte au programmeur de s'assurer que les mises en garde sont activées judicieusement.

CHECK est un nouveau mot-clé
Toutes les définitions de sous-routines nommées CHECK sont maintenant spéciales. Voir "/"Support for CHECK blocks"" pour plus d'informations.
Le traitement des tranches de liste d'undef a changé
Il existe une incompatibilité potentielle dans le comportement des tranches de liste qui consistent entièrement en valeurs indéfinies. Voir "Le comportement des tranches de liste est plus cohérent".
Le format de $English::PERL_VERSION est différent
Le module English définit maintenant $PERL_VERSION à $^V (une valeur de chaîne) plutôt qu'à $] (une valeur numérique). Ceci est une incompatibilité potentielle. Envoyez-nous un rapport via perlbug si vous êtes affecté par cela.

Voir "Amélioration du système de numérotation des versions de Perl" pour les raisons de ce changement.

Les littéraux de la forme 1.2.3 sont analysés différemment
Auparavant, les littéraux numériques avec plus d'un point étaient interprétés comme un nombre à virgule flottante concaténé avec un ou plusieurs nombres. Ces "nombres" sont maintenant analysés comme des chaînes composées des ordonnées spécifiées.

Par exemple, "print 97.98.99" affichait auparavant 97.9899 dans les versions précédentes, mais affiche maintenant "abc".

Voir "Prise en charge des chaînes représentées par un vecteur d'ordonnées".

Générateur de nombres pseudo-aléatoires potentiellement modifié
Les programmes Perl qui dépendent de la reproduction d'un ensemble spécifique de nombres pseudo-aléatoires peuvent maintenant produire des résultats différents en raison des améliorations apportées à la fonction intégrée rand(). Vous pouvez utiliser "sh Configure -Drandfunc=rand" pour obtenir le comportement précédent.

Voir "Meilleur générateur de nombres pseudo-aléatoires".

La fonction de hachage pour les clés de hachage a changé
Même si les hachages Perl ne sont pas ordonnés, l'ordre apparemment aléatoire rencontré lors de l'itération sur le contenu d'un hachage est en fait déterminé par l'algorithme de hachage utilisé. Les améliorations apportées à l'algorithme peuvent produire un ordre aléatoire qui est différent de celui des versions précédentes, en particulier lors de l'itération sur des hachages.

Voir "Meilleur comportement dans le pire des cas pour les hachages" pour des informations supplémentaires.

"undef" échoue sur les valeurs en lecture seule
L'utilisation de l'opérateur "undef" sur une valeur en lecture seule (telle que $1) a le même effet que l'affectation de "undef" à la valeur en lecture seule : elle déclenche une exception.
Le bit close-on-exec peut être défini sur les descripteurs de tuyaux et de sockets
Les descripteurs de tuyaux et de sockets sont maintenant également soumis au comportement close-on-exec déterminé par la variable spéciale $^F.

Voir "Comportement close-on-exec plus cohérent".

L'écriture de "$$1" pour signifier "${$}1" n'est pas prise en charge
Perl 5.004 a déprécié l'interprétation de $$1 et similaires dans les chaînes interpolées pour signifier "$$ . "1"", mais l'a toujours autorisée.

Dans Perl 5.6.0 et versions ultérieures, "$$1" signifie toujours "${$1}".

delete(), each(), values() et "\(%h)"
opèrent sur des alias de valeurs, pas des copies

delete(), each(), values() et les hachages (par exemple "\(%h)") dans un contexte de liste renvoient les valeurs réelles du hachage, au lieu de copies (comme ils avaient l'habitude...

sed aux dans les versions antérieures). Les idiomes typiques pour utiliser ces constructions copient les valeurs renvoyées, mais cela peut faire une différence significative lors de la création de références aux valeurs renvoyées. Les clés des hachages sont toujours renvoyées sous forme de copies lors de l'itération sur un hachage.

Voir également « delete(), each(), values() et l'itération sur les hachages sont plus rapides ».

vec(EXPR,OFFSET,BITS) impose des puissances de deux pour BITS
vec() génère une erreur d'exécution si l'argument BITS n'est pas un entier de puissance de deux valide.
Le texte de certaines sorties de diagnostic a changé
La plupart des références aux opérations internes de Perl dans les diagnostics ont été modifiées pour être plus descriptives. Cela peut poser problème aux programmes qui s'appuient incorrectement sur le texte exact des diagnostics pour leur bon fonctionnement.
"%@" a été supprimé
La variable spéciale non documentée "%@" qui accumulait auparavant les erreurs « d'arrière-plan » (telles que celles qui se produisent dans DESTROY()) a été supprimée, car elle pouvait potentiellement entraîner des fuites de mémoire.
not() entre parenthèses se comporte comme un opérateur de liste
L'opérateur "not" relève désormais de la règle « s'il ressemble à une fonction, il se comporte comme une fonction ».

Par conséquent, la forme entre parenthèses peut être utilisée avec "grep" et "map". La construction suivante était auparavant une erreur de syntaxe, mais elle fonctionne maintenant comme prévu :

grep not($_), @things;

En revanche, utiliser "not" avec une tranche de liste littérale peut ne pas fonctionner. La construction précédemment autorisée suivante :

print not (1,2,3)[0];

doit maintenant être écrite avec des parenthèses supplémentaires :

print not((1,2,3)[0]);

Le comportement reste inchangé lorsque "not" n'est pas suivi de parenthèses.

La sémantique du prototype de mot nu "(*)" a changé
La sémantique du prototype de mot nu "*" a changé. Perl 5.005 coercissait toujours les arguments scalaires simples en typeglob, ce qui n'était pas utile dans les situations où la sous-routine devait distinguer un scalaire simple d'un typeglob. Le nouveau comportement consiste à ne pas coercer les arguments de mots nus en typeglob. La valeur sera toujours visible soit comme un scalaire simple, soit comme une référence à un typeglob.

Voir « Prototype de mot nu plus fonctionnel (*) ».

La sémantique des opérateurs binaires a pu changer sur les plates-formes 64 bits
Si votre plate-forme est nativement 64 bits ou si Perl a été configuré pour utiliser des entiers 64 bits, c'est-à-dire si $Config{ivsize} est 8, il peut y avoir une incompatibilité potentielle dans le comportement des opérateurs binaires numériques (& | ^ ~ << >>). Ces opérateurs opéraient auparavant strictement sur les 32 bits inférieurs des entiers dans les versions précédentes, mais opèrent désormais sur toute la largeur entière native. Notez en particulier que l'opérateur unaire "~" produira des résultats différents sur les plates-formes ayant un $Config{ivsize} différent. Pour la portabilité, assurez-vous de masquer les bits excédentaires dans le résultat de l'opérateur unaire "~", par exemple "~$x & 0xffffffff".

Voir « Les opérateurs binaires prennent en charge la largeur entière native complète ».

Plus de fonctions intégrées marquent leurs résultats comme "tainted"
Comme décrit dans « Améliorations de la sécurité », il peut y avoir plus de sources de « taint » dans un programme Perl.

Pour éviter ces nouveaux comportements de « taint », vous pouvez compiler Perl avec l'option Configure "-Accflags=-DINCOMPLETE_TAINTS". Attention, le binaire Perl résultant pourrait être non sécurisé.

Incompatibilités de source C

"PERL_POLLUTE"
La version 5.005 a octroyé des droits d'aïeul aux anciens noms de symboles globaux en fournissant des macros de préprocesseur pour la compatibilité source des extensions. Depuis la version 5.6.0, ces définitions de préprocesseur ne sont pas disponibles par défaut. Vous devez explicitement compiler Perl avec "-DPERL_POLLUTE" pour obtenir ces définitions. Pour les extensions utilisant toujours les anciens symboles, cette option peut être spécifiée via MakeMaker : 
perl Makefile.PL POLLUTE=1
"PERL_IMPLICIT_CONTEXT"
Cette nouvelle option de compilation fournit un ensemble de macros pour toutes les fonctions de l'API, de sorte qu'un argument de contexte d'interpréteur/thread implicite est passé à chaque fonction de l'API. En conséquence, quelque chose comme "sv_setsv(foo,bar)" équivaut à un appel de macro qui se traduit en fait par quelque chose comme "Perl_sv_setsv(my_perl,foo,bar)". Bien que l'on s'attende généralement à ce que cela n'ait pas d'impact significatif sur la compatibilité source, la différence entre une macro et un appel de fonction réel devra être prise en compte.

Cela signifie qu'il **y a** un problème de compatibilité source en raison de cela si vos extensions tentent d'utiliser des pointeurs vers l'une des fonctions de l'API Perl.

Notez que le problème ci-dessus n'est pas pertinent pour la compilation par défaut de Perl, dont les interfaces continuent de correspondre à celles des versions précédentes (mais sous réserve des autres options décrites ici).

Voir « Contexte et PERL_IMPLICIT_CONTEXT » dans perlguts pour des informations détaillées sur les ramifications de la compilation de Perl avec cette option.

NOTE : PERL_IMPLICIT_CONTEXT est automatiquement activé chaque fois que Perl est compilé
avec l'une des options -Dusethreads, -Dusemultiplicity, ou les deux. Il n'est
pas destiné à être activé par les utilisateurs à l'heure actuelle.
"PERL_POLLUTE_MALLOC"
L'activation du malloc de Perl dans la version 5.005 et antérieures provoquait l'empiétement de l'espace de noms des fonctions malloc du système par les versions Perl, car par défaut elles utilisaient les mêmes noms. En plus de causer des problèmes sur les plates-formes qui n'autorisent pas le remplacement propre de ces fonctions, cela signifiait également que les versions système ne pouvaient pas être appelées dans les programmes qui utilisaient le malloc de Perl. Les versions précédentes de Perl permettaient de supprimer ce comportement avec les définitions de préprocesseur HIDEMYMALLOC et EMBEDMYMALLOC.

Depuis la version 5.6.0, les fonctions malloc de Perl ont des noms par défaut distincts de ceux des versions système. Vous devez explicitement compiler Perl avec "-DPERL_POLLUTE_MALLOC" pour obtenir le comportement précédent. HIDEMYMALLOC et EMBEDMYMALLOC n'ont aucun effet, car le comportement qu'ils permettaient est maintenant le comportement par défaut.

Notez que ces fonctions ne constituent **pas** l'API d'allocation mémoire de Perl. Voir « Allocation de mémoire » dans perlguts pour plus d'informations à ce sujet.

Changements compatibles de l'API source C

"PATCHLEVEL" est maintenant "PERL_VERSION"
Les macros cpp "PERL_REVISION", "PERL_VERSION" et "PERL_SUBVERSION" sont maintenant disponibles par défaut à partir de perl.h, et reflètent la révision de base, le niveau de correctif et la sous-version respectivement. "PERL_REVISION" n'avait pas d'équivalent préalable, tandis que "PERL_VERSION" et "PERL_SUBVERSION" étaient précédemment disponibles sous les noms "PATCHLEVEL" et "SUBVERSION".

Les nouveaux noms polluent moins l'espace de noms cpp et reflètent ce que les nombres sont venus représenter dans la pratique courante. Pour la compatibilité, les anciens noms sont toujours pris en charge lorsque patchlevel.h est explicitement inclus (comme requis auparavant), il n'y a donc aucune incompatibilité source due au changement.

Incompatibilités binaires

En général, la compilation par défaut de cette version devrait être compatible au niveau binaire pour les extensions compilées avec la version 5.005 ou ses versions de maintenance. Cependant, des plates-formes spécifiques peuvent avoir rompu la compatibilité binaire en raison de changements dans les valeurs par défaut utilisées dans les fichiers d'indices (hints). Par conséquent, assurez-vous de toujours vérifier les fichiers README spécifiques à la plate-forme pour toute note contraire.

Les compilations usethreads ou usemultiplicity ne sont **pas** compatibles au niveau binaire avec les compilations correspondantes de 5.005.

Sur les plates-formes qui nécessitent une liste explicite d'exportations (AIX, OS/2 et Windows, entre autres), les symboles purement internes tels que les fonctions d'analyse syntaxique et les opcodes d'exécution ne sont pas exportés par défaut. Perl 5.005 exportait toutes les fonctions, qu'elles soient considérées comme faisant partie de l'API publique ou non.

Pour la liste complète des fonctions de l'API publique, voir perlapi.

Problèmes connus

Échecs de tests de threads

Les sous-tests 19 et 20 de lib/thr5005.t sont connus pour échouer en raison de problèmes fondamentaux dans l'implémentation du threading de 5.005. Ce ne sont pas de nouveaux échecs : Perl 5.005_0x a les mêmes bugs, mais n'avait pas ces tests.

Les plates-formes EBCDIC ne sont pas supportées

Dans les versions antérieures de Perl, les environnements EBCDIC comme OS390 (également connu sous le nom d'Open Edition MVS) et VM-ESA étaient pris en charge. En raison des changements requis par le support de UTF-8 (Unicode), les plates-formes EBCDIC ne sont pas prises en charge dans Perl 5.6.0.

Sur HP-UX 64 bits, le test lib/io_multihomed peut se bloquer

Le test lib/io_multihomed peut se bloquer sur HP-UX si Perl a été configuré pour être 64 bits. Comme d'autres plates-formes 64 bits ne se bloquent pas dans ce test, HP-UX est suspect. Tous les autres tests réussissent en 64 bits.

-bit HP-UX. Le test tente de créer et de se connecter à des sockets « multihomés » (sockets qui ont plusieurs adresses IP).

NEXTSTEP 3.3 Échec du test POSIX

Dans NEXTSTEP 3.3p2, l'implémentation de strftime(3) dans les bibliothèques du système d'exploitation est boguée : le format %j numérote les jours d'un mois à partir de zéro, ce qui, bien que logique pour les programmeurs, entraînera l'échec des sous-tests 19 à 27 du test lib/posix.

Tru64 (alias Digital UNIX, alias DEC OSF/1) Échec du test lib/sdbm avec gcc

S'il est compilé avec gcc 2.95, le test lib/sdbm échouera (dump du cœur). La solution est d'utiliser le compilateur fourni par le fournisseur, il est livré avec le système d'exploitation et produit du bon code.

UNICOS/mk Échecs de CC lors de l'exécution de Configure

Dans UNICOS/mk, les erreurs suivantes peuvent apparaître lors de l'exécution de Configure :

Le coupable est l'awk défectueux d'UNICOS/mk. L'effet est heureusement plutôt léger : Perl lui-même n'est pas affecté négativement par l'erreur, seul l'utilitaire h2ph qui accompagne Perl l'est, et celui-ci est rarement nécessaire de nos jours.

Opérateur flèche et tableaux

Lorsque l'argument gauche de l'opérateur flèche "->" est un tableau, ou l'opérateur "scalar" opérant sur un tableau, le résultat de l'opération doit être considéré comme erroné. Par exemple :

@x->[2]
scalar(@x)->[2]

Ces expressions provoqueront des erreurs d'exécution dans une future version de Perl.

Diagnostics obsolètes

Syntaxe de classe de caractères [: :] réservée pour extensions futures
(W) Dans les classes de caractères d'expressions régulières ([]) la syntaxe commençant par « [: » et se terminant par « :] » est réservée aux extensions futures. Si vous devez représenter ces séquences de caractères à l'intérieur d'une classe de caractères d'expression régulière, il suffit d'échapper les crochets avec une barre oblique inverse : « \[: » et « :\] ».
Nom logique mal formé |%s| dans prime_env_iter
(W) Un avertissement propre à VMS. Un nom logique a été rencontré lors de la préparation d'une itération sur %ENV qui viole les règles syntaxiques régissant les noms logiques. Comme il ne peut pas être traduit normalement, il est ignoré et n'apparaîtra pas dans %ENV. Cela peut être un événement bénin, car certains progiciels peuvent modifier directement les tables de noms logiques et introduire des noms non standard, ou cela peut indiquer qu'une table de noms logiques a été corrompue.
Dans la chaîne, @%s doit maintenant être écrit comme \@%s
La description de cette erreur disait autrefois : 
(Un jour, il supposera simplement qu'un @ non échappé
 interpole un tableau.)

Ce jour est arrivé, et cette erreur fatale a été supprimée. Elle a été remplacée par un avertissement non fatal. Voir « Les tableaux interpolent maintenant toujours dans les chaînes à double guillemets » pour plus de détails.

Problème de précédence probable sur %s
(W) Le compilateur a trouvé un bareword là où il attendait une condition, ce qui indique souvent qu'un || ou && a été analysé comme faisant partie du dernier argument du construct précédent, par exemple : 
open FOO || die ;
expression régulière trop grande
(F) L'implémentation actuelle des expressions régulières utilise des `shorts` comme décalages d'adresse dans une chaîne. Malheureusement, cela signifie que si l'expression régulière compile à plus de 32767, elle explosera. Habituellement, lorsque vous voulez une expression régulière aussi grande, il existe une meilleure façon de le faire avec plusieurs instructions. Voir perlre.
L'utilisation de « $$<digit> » pour signifier « ${$}<digit> » est obsolète
(D) Les versions de Perl antérieures à 5.004 interprétaient mal tout marqueur de type suivi de « $& » et d'un chiffre. Par exemple, « $$0 » était incorrectement interprété comme « ${$}0 » au lieu de « ${$0} ». Ce bug est (principalement) corrigé dans Perl 5.004.

Cependant, les développeurs de Perl 5.004 n'ont pas pu corriger entièrement ce bug, car au moins deux modules largement utilisés dépendent de l'ancienne signification de « $$0 » dans une chaîne. Ainsi, Perl 5.004 interprète toujours « $$<digit> » de l'ancienne manière (défectueuse) à l'intérieur des chaînes ; mais il génère ce message comme avertissement. Et dans Perl 5.005, ce traitement spécial cessera.
