NOM

perlfilter - Filtres source

DESCRIPTION

Cet article traite d'une fonctionnalité peu connue de Perl appelée filtres source. Les filtres source modifient le texte du programme d'un module avant que Perl ne le voie, un peu comme un préprocesseur C modifie le texte source d'un programme C avant que le compilateur ne le voie. Cet article vous en dit plus sur ce que sont les filtres source, comment ils fonctionnent, et comment écrire les vôtres.

L'objectif initial des filtres source était de permettre le chiffrement du code source de votre programme pour en empêcher la lecture fortuite. Ce n'est pas leur seule utilité, comme vous ne tarderez pas à le découvrir. Mais d'abord, les bases.

CONCEPTS

Avant que l'interpréteur Perl ne puisse exécuter un script Perl, il doit d'abord le lire depuis un fichier pour le charger en mémoire afin de l'analyser et de le compiler. Si ce script inclut lui-même d'autres scripts avec une instruction "use" ou "require", alors chacun de ces scripts devra également être lu à partir de leurs fichiers respectifs.

Considérez maintenant chaque connexion logique entre l'analyseur Perl et un fichier individuel comme un flux source. Un flux source est créé lorsque l'analyseur Perl ouvre un fichier, il continue d'exister pendant que le code source est chargé en mémoire, et il est détruit lorsque Perl a terminé l'analyse du fichier. Si l'analyseur rencontre une instruction "require" ou "use" dans un flux source, un nouveau flux distinct est créé spécifiquement pour ce fichier.

Le diagramme ci-dessous représente un seul flux source, avec le flux du code source depuis un fichier de script Perl à gauche vers l'analyseur Perl à droite. C'est ainsi que Perl fonctionne normalement.

fichier -------> analyseur

Il y a deux points importants à retenir :

1.
Bien qu'il puisse y avoir un nombre quelconque de flux source en existence à un moment donné, un seul sera actif.
2.
Chaque flux source est associé à un seul fichier.

Un filtre source est un type spécial de module Perl qui intercepte et modifie un flux source avant qu'il n'atteigne l'analyseur. Un filtre source modifie notre diagramme comme suit :

fichier ----> filtre ----> analyseur

Si cela n'a pas beaucoup de sens, considérez l'analogie d'un pipeline de commandes. Supposons que vous ayez un script shell stocké dans le fichier compressé trial.gz. La simple commande pipeline ci-dessous exécute le script sans avoir besoin de créer un fichier temporaire pour conserver le fichier décompressé.

gunzip -c trial.gz | sh

Dans ce cas, le flux de données du pipeline peut être représenté comme suit :

trial.gz ----> gunzip ----> sh

Avec les filtres source, vous pouvez stocker le texte de votre script compressé et utiliser un filtre source pour le décompresser pour l'analyseur Perl :

 programme Perl
 compressé   ----> filtre source ----> analyseur

UTILISATION DES FILTRES

Alors, comment utilisez-vous un filtre source dans un script Perl ? Ci-dessus, j'ai dit qu'un filtre source n'est qu'un type spécial de module. Comme tous les modules Perl, un filtre source est appelé avec une instruction use.

Disons que vous voulez passer votre source Perl à travers le préprocesseur C avant l'exécution. Il se trouve que la distribution des filtres source est livrée avec un module de filtre de préprocesseur C appelé Filter::cpp.

Voici un exemple de programme, "cpp_test", qui utilise ce filtre. Les numéros de ligne ont été ajoutés pour permettre de référencer facilement des lignes spécifiques.

1: use Filter::cpp;
2: #define TRUE 1
3: $a = TRUE;
4: print "a = $a\n";

Lorsque vous exécutez ce script, Perl crée un flux source pour le fichier. Avant que l'analyseur ne traite aucune des lignes du fichier, le flux source ressemble à ceci :

cpp_test ---------> analyseur

La ligne 1, "use Filter::cpp", inclut et installe le module filtre "cpp". Tous les filtres source fonctionnent de cette manière. L'instruction use est compilée et exécutée au moment de la compilation, avant que le reste du fichier ne soit lu, et elle attache le filtre cpp au flux source en arrière-plan. Maintenant, le flux de données ressemble à ceci :

cpp_test ----> filtre cpp ----> analyseur

Lorsque l'analyseur lit la deuxième ligne et les lignes suivantes à partir du flux source, il les fait passer par le filtre source "cpp" avant de les traiter. Le filtre "cpp" fait simplement passer chaque ligne par le véritable préprocesseur C. La sortie du préprocesseur C est ensuite réinsérée dans le flux source par le filtre.

               .-> cpp --.
               |         |
               |         |
               |       <-'
cpp_test ----> filtre cpp ----> analyseur

L'analyseur voit alors le code suivant :

use Filter::cpp;
$a = 1;
print "a = $a\n";

Considérons ce qui se passe lorsque le code filtré inclut un autre module avec use :

1: use Filter::cpp;
2: #define TRUE 1
3: use Fred;
4: $a = TRUE;
5: print "a = $a\n";

Le filtre "cpp" ne s'applique pas au texte du module Fred, mais uniquement au texte du fichier qui l'a utilisé ("cpp_test"). Bien que l'instruction use à la ligne 3 passe par le filtre cpp, le module qui est inclus ("Fred") ne l'est pas. Les flux source ressemblent à ceci après que la ligne 3 a été analysée et avant que la ligne 4 ne soit analysée :

cpp_test ---> filtre cpp ---> analyseur (INACTIF)
Fred.pm ----> analyseur

Comme vous pouvez le voir, un nouveau flux a été créé pour lire la source de "Fred.pm". Ce flux restera actif jusqu'à ce que tout "Fred.pm" ait été analysé. Le flux source pour "cpp_test" existera toujours, mais il sera inactif. Une fois que l'analyseur aura fini de lire Fred.pm, le flux source qui lui est associé sera détruit. Le flux source pour "cpp_test" redevient alors actif et l'analyseur lit la ligne 4 et les lignes suivantes à partir de "cpp_test".

Vous pouvez utiliser plus d'un filtre source sur un seul fichier. De même, vous pouvez réutiliser le même filtre dans autant de fichiers que vous le souhaitez.

Par exemple, si vous avez un fichier source encodé en uuencode et compressé, il est possible d'empiler un filtre de décodage uuencode et un filtre de décompression comme ceci :

use Filter::uudecode; use Filter::uncompress;
M'XL(".H<US4''V9I;F%L')Q;>7/;1I;_>_I3=&E=%:F*I"T?22Q/
M6]9*<IQCO*XFT"0[PL%%'Y+IG?WN^ZYN-$'J.[.JE$,20/?K=_[>
...

Une fois la première ligne traitée, le flux ressemblera à ceci :

fichier ---> décodage uu ---> décompression ---> analyseur
            filtre            filtre

Les données circulent à travers les filtres dans le même ordre qu'elles apparaissent dans le fichier source. Le filtre de décodage uuencode est apparu avant le filtre de décompression, donc le fichier source sera d'abord décodé en uuencode, puis décompressé.

ECRIRE UN FILTRE SOURCE

Il y a trois façons d'écrire votre propre filtre source. Vous pouvez l'écrire en C, utiliser un programme externe comme filtre, ou écrire le filtre en Perl. Je ne vais pas les couvrir en détail, je vais donc m'en débarrasser d'abord. Écrire le filtre en Perl est le plus pratique, je consacrerai donc le plus d'espace à cela.

ECRIRE UN FILTRE SOURCE EN C

La première des trois techniques disponibles consiste à écrire le filtre entièrement en C. Le module externe que vous créez s'interface directement avec les points d'accroche des filtres source fournis par Perl.

L'avantage de cette technique est que vous avez un contrôle total sur l'implémentation de votre filtre. Le gros inconvénient est la complexité accrue nécessaire pour écrire le filtre - non seulement vous devez comprendre les points d'accroche des filtres source, mais vous avez également besoin d'une connaissance raisonnable des entrailles de Perl. L'une des rares fois où cela vaut la peine de faire cet effort est lors de l'écriture d'un brouilleur de source. Le filtre "decrypt" (qui déchiffre la source avant que Perl ne l'analyse) inclus avec la distribution des filtres source est un exemple de filtre source C (voir Filtres de déchiffrement, ci-dessous).

Filtres de déchiffrement
Tous les filtres de déchiffrement fonctionnent sur le

en principe de la « sécurité par l'obscurité ». Quelle que soit la qualité de votre filtre de déchiffrement et la robustesse de votre algorithme de chiffrement, toute personne suffisamment déterminée pourra récupérer le code source original. La raison en est assez simple : pour exécuter votre programme, Perl doit analyser son code source. Cela signifie que Perl doit disposer de toutes les informations nécessaires pour déchiffrer votre programme, et cela signifie que ces informations sont également disponibles pour quiconque peut exécuter le programme.

Cela étant dit, un certain nombre de mesures peuvent être prises pour compliquer la vie du lecteur potentiel. La plus importante : écrivez votre filtre de déchiffrement en C et liez statiquement le module de déchiffrement à l'exécutable Perl. Pour d'autres conseils visant à compliquer la vie du lecteur potentiel, consultez le fichier decrypt.pm dans la distribution des filtres source.

CRÉER UN FILTRE SOURCE EN TANT QU’ÉXÉCUTABLE SÉPARÉ

Une alternative à l'écriture du filtre en C consiste à créer un exécutable séparé dans le langage de votre choix. L'exécutable séparé lit depuis l'entrée standard, effectue le traitement nécessaire et écrit les données filtrées vers la sortie standard. "Filter::cpp" est un exemple de filtre source implémenté sous forme d'exécutable séparé - l'exécutable est le préprocesseur C fourni avec votre compilateur C.

La distribution des filtres source inclut deux modules qui simplifient cette tâche : "Filter::exec" et "Filter::sh". Tous deux vous permettent d'exécuter n'importe quel exécutable externe. Tous deux utilisent un coprocesseur pour contrôler le flux de données vers et depuis l'exécutable externe. (Pour plus de détails sur les coprocesseurs, voir Stephens, W.R., "Advanced Programming in the UNIX Environment." Addison-Wesley, ISBN 0-210-56317-7, pages 441-445.) La différence entre les deux est que "Filter::exec" démarre directement la commande externe, tandis que "Filter::sh" démarre un shell pour exécuter la commande externe. (Unix utilise le shell Bourne ; NT utilise le shell cmd.) Le démarrage d'un shell vous permet d'utiliser les métacaractères et les facilités de redirection du shell.

Voici un exemple de script qui utilise "Filter::sh" :

use Filter::sh 'tr XYZ PQR';
$a = 1;
print "XYZ a = $a\n";

La sortie que vous obtiendrez lorsque le script sera exécuté :

PQR a = 1

Écrire un filtre source sous forme d'exécutable séparé fonctionne bien, mais cela entraîne une légère pénalité de performance. Par exemple, si vous exécutez le petit exemple ci-dessus, un sous-processus séparé sera créé pour exécuter la commande Unix "tr". Chaque utilisation du filtre nécessite son propre sous-processus. Si la création de sous-processus est coûteuse sur votre système, vous pourriez envisager l'une des autres options pour créer des filtres source.

ÉCRIRE UN FILTRE SOURCE EN PERL

L'option la plus simple et la plus portable pour créer votre propre filtre source est de l'écrire entièrement en Perl. Pour le distinguer des deux techniques précédentes, je l'appellerai filtre source Perl.

Pour comprendre comment écrire un filtre source Perl, nous avons besoin d'un exemple à étudier. Voici un filtre source complet qui effectue le déchiffrement rot13. (Rot13 est un schéma de chiffrement très simple utilisé dans les publications Usenet pour masquer le contenu des messages offensants. Il décale chaque lettre de treize positions, de sorte que A devienne N, B devienne O, et Z devienne M.)

package Rot13;
use Filter::Util::Call;
sub import {
   my ($type) = @_;
   my ($ref) = [];
   filter_add(bless $ref);
}
sub filter {
   my ($self) = @_;
   my ($status);
   tr/n-za-mN-ZA-M/a-zA-Z/
      if ($status = filter_read()) > 0;
   $status;
}
1;

Tous les filtres source Perl sont implémentés en tant que classes Perl et ont la même structure de base que l'exemple ci-dessus.

Tout d'abord, nous incluons le module "Filter::Util::Call", qui exporte un certain nombre de fonctions dans l'espace de noms de votre filtre. Le filtre montré ci-dessus utilise deux de ces fonctions, filter_add() et filter_read().

Ensuite, nous créons l'objet filtre et l'associons au flux source en définissant la fonction "import". Si vous connaissez suffisamment bien Perl, vous savez que "import" est appelé automatiquement chaque fois qu'un module est inclus avec une instruction use. Cela fait de "import" l'endroit idéal pour créer et installer un objet filtre.

Dans l'exemple de filtre, l'objet ($ref) est béni (blessed) comme n'importe quel autre objet Perl. Notre exemple utilise un tableau anonyme, mais ce n'est pas une exigence. Étant donné que cet exemple n'a pas besoin de stocker d'informations de contexte, nous aurions tout aussi bien pu utiliser une référence scalaire ou de hachage. La section suivante démontre les données de contexte.

L'association entre l'objet filtre et le flux source est établie avec la fonction filter_add(). Celle-ci prend un objet filtre comme paramètre ($ref dans ce cas) et l'installe dans le flux source.

Enfin, il y a le code qui effectue réellement le filtrage. Pour ce type de filtre source Perl, tout le filtrage est effectué dans une méthode appelée filter(). (Il est également possible d'écrire un filtre source Perl à l'aide d'une fermeture (closure). Voir la page man "Filter::Util::Call" pour plus de détails.) Elle est appelée chaque fois que l'analyseur Perl a besoin d'une autre ligne source à traiter. La méthode filter(), à son tour, lit les lignes du flux source à l'aide de la fonction filter_read().

Si une ligne était disponible à partir du flux source, filter_read() renvoie une valeur de statut supérieure à zéro et ajoute la ligne à $_. Une valeur de statut de zéro indique la fin du fichier, moins de zéro signifie une erreur. La fonction filtre elle-même est censée retourner son statut de la même manière, et placer la ligne filtrée qu'elle souhaite écrire dans le flux source dans $_. L'utilisation de $_ explique la concision de la plupart des filtres source Perl.

Afin d'utiliser le filtre rot13, nous avons besoin d'un moyen d'encoder le fichier source au format rot13. Le script ci-dessous, "mkrot13", fait exactement cela.

die "usage mkrot13 filename\n" unless @ARGV;
my $in = $ARGV[0];
my $out = "$in.tmp";
open(IN, "<$in") or die "Cannot open file $in: $!\n";
open(OUT, ">$out") or die "Cannot open file $out: $!\n";
print OUT "use Rot13;\n";
while (<IN>) {
   tr/a-zA-Z/n-za-mN-ZA-M/;
   print OUT;
}
close IN;
close OUT;
unlink $in;
rename $out, $in;

Si nous chiffrons ceci avec "mkrot13" :

print " hello fred \n";

le résultat sera le suivant :

use Rot13;
cevag "uryyb serq\a";

L'exécution produit la sortie suivante :

hello fred

UTILISER LE CONTRÔLE : LE FILTRE DE DÉBOGAGE

L'exemple rot13 était un exemple trivial. Voici une autre démonstration qui présente quelques fonctionnalités supplémentaires.

Disons que vous souhaitiez inclure beaucoup de code de débogage dans votre script Perl pendant le développement, mais que vous ne souhaitiez pas qu'il soit disponible dans le produit final. Les filtres source offrent une solution. Afin de simplifier l'exemple, supposons que vous souhaitiez que la sortie de débogage soit contrôlée par une variable d'environnement, "DEBUG". Le code de débogage est activé si la variable existe, sinon il est désactivé.

Deux lignes marqueurs spéciales encadreront le code de débogage, comme suit :

## DEBUG_BEGIN
if ($year > 1999) {
   warn "Debug: millennium bug in year $year\n";
}
## DEBUG_END

Le filtre garantit que Perl analyse le code entre les marqueurs <DEBUG_BEGIN> et "DEBUG_END" uniquement lorsque la variable d'environnement "DEBUG" existe. Cela signifie que lorsque "DEBUG" existe, le code ci-dessus doit être transmis sans modification par le filtre. Les lignes marqueurs peuvent également être transmises telles quelles, car l'analyseur Perl les verra comme des lignes de commentaire. Lorsque "DEBUG" n'est pas défini, nous devons trouver un moyen de désactiver le code de débogage. Une façon simple d'y parvenir est de convertir les lignes entre les deux marqueurs en commentaires :

## DEBUG_BEGIN
#if ($year > 1999) {
#     warn "Debug: millennium bug in year $year\n";
#}
## DEBUG_END

Voici le filtre Debug complet :

package Debug;
use v5.36;
use Filter::Util::Call;
use constant TRUE => 1;
use constant FALSE => 0;
sub import {
   my ($type) = @_;
   my (%context) = (
     Enabled => defined $ENV{DEBUG},
     InTraceBlock => FALSE,
     Filename => (caller)[1],
     LineNo => 0,
     LastBegin => 0,
   );
   filter_add(bless \%context);
}
sub Die {
   my ($self) = shift;
   my ($message) = shift;
   my ($line_no) = shift || $self->{LastBegin};
   die "$message at $self->{Filename} line $line_no.\n"
}
sub filter {
   my ($self) = @_;
   my ($status);
   $status = filter_read();
   ++ $self->{LineNo};
   # deal with EOF/error first
   if ($status <= 0) {
       $self->Die("DEBUG_BEGIN has no DEBUG_END")
           if $self->{InTraceBlock};
       return $status;
   }
   if ($self->{InTraceBlock}) {
      if (/^\s*##\s*DEBUG_BEGIN/ ) {
          $self->Die("Nested DEBUG_BEGIN", $self->{LineNo})
      } elsif (/^\s*##\s*DEBUG_END/) {
          $self->{InTraceBlock} = FALSE;
      }
      # comment out the debug lines when the filter is disabled
      s/^/#/ if ! $self->{Enabled};
   } elsif ( /^\s*##\s*DEBUG_BEGIN/ ) {
      $self->{InTraceBlock} = TRUE;
      $self->{LastBegin} = $self->{LineNo};
   } elsif ( /^\s*##\s*DEBUG_END/ ) {
      $self->Die("DEBUG_END has no DEBUG_BEGIN", $self->{LineNo});
   }
   return $status;
}
1;

La grande différence entre ce filtre et l'exemple précédent est l'utilisation de données de contexte dans l'objet filtre. L'objet filtre est basé sur une référence de hachage (hash reference) et est utilisé pour conserver diverses informations de contexte entre les appels à la fonction filtre. Tous les champs du hachage, sauf deux, sont utilisés pour le rapport d'erreurs. Le premier de ces deux champs, Enabled, est utilisé par le filtre pour déterminer si le code de débogage doit être transmis à l'analyseur Perl. Le second, InTraceBlock, est vrai lorsque le filtre a rencontré un "DEBUG_BEGIN " ligne, mais n'a pas encore rencontré la ligne suivante "DEBUG_END".

Si vous ignorez toute la vérification des erreurs que la plupart du code effectue, l'essence du filtre est la suivante :

sub filter {
   my ($self) = @_;
   my ($status);
   $status = filter_read();
   # traite EOF/erreur d'abord
   return $status if $status <= 0;
   if ($self->{InTraceBlock}) {
      if (/^\s*##\s*DEBUG_END/) {
         $self->{InTraceBlock} = FALSE
      }
      # commente les lignes de débogage lorsque le filtre est désactivé
      s/^/#/ if ! $self->{Enabled};
   } elsif ( /^\s*##\s*DEBUG_BEGIN/ ) {
      $self->{InTraceBlock} = TRUE;
   }
   return $status;
}

Attention : tout comme le préprocesseur C ne connaît pas le C, le filtre Debug ne connaît pas Perl. Il peut être facilement trompé :

print <<EOM;
##DEBUG_BEGIN
EOM

Mis à part ces détails, vous pouvez constater qu'on peut accomplir beaucoup de choses avec une quantité modeste de code.

CONCLUSION

Vous avez maintenant une meilleure compréhension de ce qu'est un filtre source, et vous pourriez même avoir une utilité pour eux. Si vous avez envie de jouer avec les filtres source mais que vous avez besoin d'un peu d'inspiration, voici quelques fonctionnalités supplémentaires que vous pourriez ajouter au filtre Debug.

Tout d'abord, une chose facile. Plutôt que d'avoir du code de débogage qui est tout ou rien, il serait beaucoup plus utile de pouvoir contrôler quels blocs spécifiques de code de débogage sont inclus. Essayez d'étendre la syntaxe des blocs de débogage pour permettre l'identification de chacun. Le contenu de la variable d'environnement "DEBUG" peut alors être utilisé pour contrôler quels blocs sont inclus.

Une fois que vous pouvez identifier des blocs individuels, essayez de permettre leur imbrication. Ce n'est pas difficile non plus.

Voici une idée intéressante qui n'implique pas le filtre Debug. Actuellement, les sous-routines Perl ont un support assez limité pour les listes de paramètres formels. Vous pouvez spécifier le nombre de paramètres et leur type, mais vous devez toujours les extraire manuellement du tableau @_ vous-même. Écrivez un filtre source qui vous permet d'avoir une liste de paramètres nommés. Un tel filtre transformerait ceci :

sub MySub ($first, $second, @rest) { ... }

en ceci :

sub MySub($$@) {
   my ($first) = shift;
   my ($second) = shift;
   my (@rest) = @_;
   ...
}

Enfin, si vous vous sentez prêt pour un vrai défi, essayez d'écrire un préprocesseur de macros Perl complet en tant que filtre source. Empruntez les fonctionnalités utiles du préprocesseur C et de tout autre processeur de macros que vous connaissez. La partie délicate sera de choisir quelle quantité de connaissance de la syntaxe de Perl vous voulez que votre filtre ait.

LIMITATIONS

Les filtres source ne fonctionnent qu'au niveau des chaînes de caractères, ils sont donc très limités dans leur capacité à modifier le code source à la volée. Ils ne peuvent pas détecter les commentaires, les chaînes de caractères entre guillemets, les here-docs, ils ne remplacent pas un vrai analyseur. La seule utilisation stable pour les filtres source est le chiffrement, la compression, ou le byteloader, pour traduire le code binaire en code source.

Voir par exemple les limitations dans Switch, qui utilise des filtres source, et donc ne fonctionne pas à l'intérieur d'un eval de chaîne, la présence de regex avec des sauts de ligne intégrés spécifiés avec des délimiteurs bruts "/.../" et qui n'ont pas de modificateur "//x" sont indiscernables des blocs de code commençant par l'opérateur de division "/". Comme solution de contournement, vous devez utiliser "m/.../" ou "m?...?" pour de tels motifs. De plus, la présence d'expressions régulières spécifiées avec des délimiteurs bruts "?...?" peut provoquer des erreurs mystérieuses. La solution de contournement est d'utiliser "m?...?" à la place. Voir https://metacpan.org/pod/Switch#LIMITATIONS.

Actuellement, le contenu du bloc "__DATA__" n'est pas filtré.

Actuellement, les longueurs des tampons internes sont limitées à 32 bits uniquement.

CHOSES À SURVEILLER

Certains Filtres Altèrent la Poignée "DATA"
Certains filtres source utilisent la poignée "DATA" pour lire le programme appelant. Lors de l'utilisation de ces filtres source, vous ne pouvez pas vous fier à cette poignée, ni attendre un comportement particulier lors de son utilisation. Les filtres basés sur Filter::Util::Call (et donc Filter::Simple) ne modifient pas le fichier "DATA", mais d'un autre côté ignorent totalement le texte après "__DATA__".

EXIGENCES

La distribution Source Filters est disponible sur CPAN, dans

CPAN/modules/by-module/Filter

À partir de Perl 5.8, Filter::Util::Call (la partie centrale de la distribution Source Filters) fait partie de la distribution Perl standard. Est également inclus une interface plus conviviale appelée Filter::Simple, par Damian Conway.
