PERLVMS(1perl) Guide de référence pour programmeurs Perl PERLVMS(1perl)

NOM

perlvms - Documentation spécifique à VMS pour Perl

DESCRIPTION

Vous trouverez ci-dessous des notes décrivant les détails du comportement de Perl 5 sous VMS. Elles complètent la documentation régulière de Perl 5, nous nous sommes donc concentrés sur les différences de fonctionnement de Perl 5 sous VMS par rapport à Unix, et sur les interactions entre Perl et le reste du système d'exploitation. Nous n'avons pas tenté de reproduire des descriptions complètes des fonctionnalités de Perl issues de la documentation principale de Perl, qui se trouve dans le sous-répertoire [.pod] de la distribution Perl.

Nous espérons que ces notes vous éviteront confusion et nuits blanches lors de l'écriture de scripts Perl sur VMS. Si vous constatez que nous avons omis quelque chose qui, selon vous, devrait figurer ici, n'hésitez pas à envoyer un message à vmsperl@perl.org.

Installation

Les instructions pour compiler et installer Perl 5 se trouvent dans le fichier README.vms dans le répertoire source principal de la distribution Perl.

Organisation des images Perl

Images de base

Au cours du processus de compilation, trois images Perl sont produites. Miniperl.Exe est une image exécutable qui contient toutes les fonctionnalités de base de Perl, mais ne peut pas tirer parti des extensions Perl XS et a une liste codée en dur des emplacements de bibliothèque pour le chargement des modules pure-Perl. Elle est largement utilisée pour construire et tester Perl et diverses extensions, mais n'est pas installée.

La majeure partie de Perl complet réside dans l'image partageable PerlShr.Exe, qui fournit un cœur auquel l'image exécutable Perl et toutes les extensions Perl sont liées. Elle est généralement localisée via le nom logique PERLSHR. Bien qu'il soit possible de placer l'image dans SYS$SHARE pour la rendre chargeable, cela n'est pas recommandé. Et bien que vous puissiez vouloir INSTALLER l'image pour des raisons de performance, vous ne devriez pas l'installer avec des privilèges ; si vous le faites, le résultat ne sera pas celui attendu car les privilèges de l'image sont désactivés au démarrage de Perl.

Enfin, Perl.Exe est une image exécutable contenant le point d'entrée principal de Perl, ainsi qu'un certain code d'initialisation. Elle doit être placée dans un répertoire public et rendue exécutable par tous. Afin d'exécuter Perl avec des arguments en ligne de commande, vous devriez définir une commande étrangère pour invoquer cette image.

Extensions Perl

Les extensions Perl sont des paquets qui fournissent à la fois du code XS et du code Perl pour ajouter de nouvelles fonctionnalités à perl. (XS est un méta-langage qui simplifie l'écriture de code C qui interagit avec Perl, voir perlxs pour plus de détails.) Le code Perl d'une extension est traité comme tout autre module de bibliothèque - il est rendu disponible dans votre script via l'instruction "use" ou "require" appropriée, et définit généralement un paquet Perl contenant l'extension.

La partie de l'extension fournie par le code XS peut être connectée au reste de Perl de l'une des deux manières suivantes. Dans la configuration statique, le code objet de l'extension est lié directement dans PerlShr.Exe, et est initialisé chaque fois que Perl est invoqué. Dans la configuration dynamique, le code machine de l'extension est placé dans une image partageable séparée, qui est mappée par le DynaLoader de Perl lorsque l'extension est "use" ou "require" dans votre script. Cela vous permet de maintenir l'extension en tant qu'entité distincte, au prix de la gestion de l'image partageable supplémentaire. La plupart des extensions peuvent être configurées comme statiques ou dynamiques.

Le code source d'une extension réside généralement dans son propre répertoire. Au moins trois fichiers sont généralement fournis : Extshortname.xs (où Extshortname est la partie du nom de l'extension suivant le dernier "::"), contenant le code XS, Extshortname.pm, le module de bibliothèque Perl pour l'extension, et Makefile.PL, un script Perl qui utilise les modules de la bibliothèque "MakeMaker" fournis avec Perl pour générer un fichier Descrip.MMS pour l'extension.

Installation des extensions statiques

Étant donné que les extensions statiques sont incorporées directement dans PerlShr.Exe, vous devrez reconstruire Perl pour incorporer une nouvelle extension. Vous devriez éditer le Descrip.MMS principal ou le Makefile que vous utilisez pour construire Perl, en ajoutant le nom de l'extension à la macro "ext", et le fichier objet de l'extension à la macro "extobj". Vous devrez également construire le fichier objet de l'extension, soit en ajoutant des dépendances au Descrip.MMS principal, soit en utilisant un Descrip.MMS séparé pour l'extension. Ensuite, reconstruisez PerlShr.Exe pour incorporer le nouveau code.

Enfin, vous devrez copier le module de bibliothèque Perl de l'extension dans le sous-répertoire [.Extname] sous l'un des répertoires de @INC, où Extname est le nom de l'extension, avec tous les "::" remplacés par "." (par exemple, le module de bibliothèque pour l'extension Foo::Bar serait copié dans un sous-répertoire [.Foo.Bar]).

Installation des extensions dynamiques

En général, le kit distribué pour une extension Perl comprend un fichier nommé Makefile.PL, qui est un programme Perl utilisé pour créer un fichier Descrip.MMS qui peut être utilisé pour construire et installer les fichiers requis par l'extension. Le kit doit être décompressé dans une arborescence de répertoires non sous le répertoire source principal de Perl, et la procédure de construction de l'extension est simplement

$ perl Makefile.PL  ! Crée Descrip.MMS
$ mmk               ! Construit les fichiers nécessaires
$ mmk test          ! Exécute le code de test, s'il est fourni
$ mmk install       ! Installe dans l'arbre Perl public

La prise en charge VMS pour ce processus dans la version actuelle de Perl est suffisante pour gérer la plupart des extensions. (Voir la documentation de MakeMaker pour plus de détails sur les options d'installation des extensions.)

  • le sous-répertoire [.Lib.Auto.Arch$PVersExtname] de l'un des répertoires de @INC (où PVers est la version de Perl que vous utilisez, telle que fournie dans $], avec '.' converti en '_'), ou
  • l'un des répertoires de @INC, ou
  • un répertoire que le module de bibliothèque Perl de l'extension passe au DynaLoader lorsqu'il lui demande de mapper l'image partageable, ou
  • Sys$Share ou Sys$Library.

Si l'image partageable ne se trouve dans aucun de ces endroits, vous devrez définir un nom logique Extshortname, où Extshortname est la partie du nom de l'extension après le dernier "::", qui se traduit par la spécification complète du fichier de l'image partageable.

Spécifications de fichiers

Syntaxe

Nous avons essayé de rendre Perl conscient des spécifications de fichiers de style VMS et de style Unix autant que possible. Vous pouvez utiliser l'un ou l'autre style, ou les deux, sur la ligne de commande et dans les scripts, mais vous ne pouvez pas combiner les deux styles au sein d'une seule spécification de fichier. Perl VMS interprète les noms de chemin Unix de la même manière que le CRTL (par exemple, le premier composant d'un chemin absolu est lu comme le nom de périphérique pour la spécification de fichier VMS). Il existe un ensemble de fonctions fournies dans le paquet "VMS::Filespec" pour la conversion explicite entre la syntaxe VMS et Unix ; sa documentation fournit plus de détails.

Nous avons essayé de minimiser la dépendance des modules de bibliothèque Perl à la syntaxe Unix, mais vous pourriez constater que certains d'entre eux, ainsi que certains scripts écrits pour les systèmes Unix, nécessiteront que vous utilisiez la syntaxe Unix, car ils supposeront que '/' est le séparateur de répertoire, etc. Si vous trouvez des exemples de cela dans la distribution Perl elle-même, veuillez nous en informer, afin que nous puissions essayer de les contourner.

  • CONVERSIONS DE NOM DE FICHIER

    Lorsque vous traitez des noms de fichiers dans un système d'exploitation spécifique, vous devez soit vérifier la fonctionnalité logique DECC$ appropriée, soit appeler une routine de conversion pour la forcer à ce format.

    Le nom logique de fonctionnalité DECC$FILENAME_UNIX_REPORT modifie le comportement traditionnel de Perl dans la conversion des spécifications de fichiers du format Unix au format VMS afin de suivre les règles étendues de gestion des caractères attendues par le CRTL. Spécifiquement, lorsque cette fonctionnalité est activée, le "./.../" dans un chemin Unix est maintenant traduit en "[.^.^.^.]" au lieu du "[...]" VMS traditionnel. Pour être compatible avec ce qu'attend MakeMaker, si un chemin VMS ne peut pas être traduit en un chemin Unix, il est transmis tel quel, de sorte que unixify("[...]") retournera "[...]".

    Il existe plusieurs cas ambigus où une routine de conversion ne peut pas déterminer si un nom de fichier d'entrée est au format Unix ou au format VMS, car maintenant les spécifications de fichiers VMS et Unix peuvent contenir des caractères qui pourraient être confondus avec des délimiteurs de syntaxe de l'autre type. Ainsi, certains noms de chemins ne peuvent tout simplement pas être utilisés dans un mode qui permet la présence de l'un ou l'autre type de nom de chemin. Perl aura tendance à supposer qu'un nom de fichier ambigu est au format Unix.

    Permettre au "." d'être un délimiteur de version est simplement incompatible avec la détermination si un nom de chemin est au format VMS ou au format Unix avec une syntaxe de fichier étendue. Il n'y a aucun moyen de savoir si "perl-5.8.6" est un "perl-5.8.6" Unix ou un "perl-5.8;6" VMS lorsqu'il est passé à unixify() ou vmsify().

    Le nom logique DECC$FILENAME_UNIX_REPORT contrôle la façon dont Perl interprète les noms de fichiers dans la mesure où Perl utilise le CRTL en interne à de nombreuses fins et tente de suivre les conventions du CRTL pour le rapport des noms de fichiers. La fonctionnalité DECC$FILENAME_UNIX_ONLY diffère en ce qu'elle attend que tous les noms de fichiers passés à la bibliothèque d'exécution C soient déjà au format Unix. Cette fonctionnalité n'est pas encore prise en charge dans Perl car Perl utilise les spécifications de fichiers OpenVMS traditionnelles en interne et dans le banc d'essai, et il n'est pas encore clair si ce mode sera utile ou utilisable. Le nom logique de fonctionnalité DECC$POSIX_COMPLIANT_PATHNAMES est nouveau avec le SDK de liens symboliques RMS et inclus avec OpenVMS v8.3, mais n'est pas encore pris en charge dans Perl.

    Casse des noms de fichier

    Perl active DECC$EFS_CASE_PRESERVE et DECC$ARGV_PARSE_STYLE par défaut. Notez que cette dernière ne prend effet que lorsque l'analyse étendue est définie dans le processus dans lequel Perl s'exécute. Lorsque ces fonctionnalités sont explicitement désactivées dans l'environnement ou que le CRTL ne les prend pas en charge, Perl suit le comportement traditionnel du CRTL de mise en minuscules des arguments de la ligne de commande et de retour des spécifications de fichiers uniquement en minuscules.

    N. B. Il est très facile de se faire piéger en utilisant un mélange d'autres programmes, d'utilitaires externes et de scripts Perl qui sont dans des états variables de capacité à gérer la préservation de la casse. Par exemple, un fichier créé par une ancienne version d'un utilitaire d'archivage ou d'un utilitaire de construction tel que MMK ou MMS peut générer un nom de fichier en majuscules même sur un volume ODS-5. Si ce nom de fichier est ultérieurement récupéré par un script ou un module Perl dans un environnement préservant la casse, ce nom en majuscules peut ne pas correspondre aux attentes en casse mixte ou en minuscules du code Perl. Votre meilleure option est de suivre une approche tout ou rien pour la préservation de la casse : soit ne pas l'utiliser du tout, soit vous assurer que toute votre chaîne d'outils et votre environnement d'application la prennent en charge et l'utilisent.

    OpenVMS Alpha v7.3-1 et versions ultérieures et toutes les versions d'OpenVMS I64 prennent en charge la sensibilité à la casse en tant que paramètre de processus (voir "SET PROCESS /CASE_LOOKUP=SENSITIVE"). Perl ne prend actuellement pas en charge la sensibilité à la casse sur VMS, mais il pourrait le faire à l'avenir, de sorte que les programmes Perl doivent utiliser la méthode "File::Spec->case_tolerant" pour déterminer l'état, et non la variable $^O.

    Liens symboliques

    Lorsqu'il est construit sur un volume ODS-5 avec les liens symboliques activés, Perl prend en charge par défaut les liens symboliques lorsque le support requis est disponible dans le système de fichiers et le CRTL (généralement OpenVMS 64 bits v8.3 et versions ultérieures). Il y a un certain nombre de limitations et de mises en garde à connaître lorsque vous travaillez avec des liens symboliques sur VMS. Notamment, la cible d'un lien symbolique valide doit être exprimée sous forme de chemin de style Unix et elle doit exister sur un volume visible depuis votre racine POSIX (voir la commande "SHOW ROOT" dans l'aide DCL). Pour plus de détails sur les capacités et les exigences des liens symboliques, consultez le chapitre 12 du manuel CRTL qui accompagne OpenVMS v8.3 ou ultérieur.

    Expansion des caractères génériques

    Les spécifications de fichiers contenant des caractères génériques sont autorisées à la fois sur la ligne de commande et dans les globs Perl (par exemple "<*.c>"). Si la spécification de caractères génériques utilise la syntaxe VMS, les spécifications résultantes suivront la syntaxe VMS ; si une spécification de fichier de style Unix est passée, des spécifications de fichier de style Unix seront retournées. Similaire au comportement de l'expansion de caractères génériques pour un shell Unix, on peut échapper les caractères génériques de la ligne de commande avec des guillemets doubles """ autour d'un argument de ligne de commande de programme Perl. Cependant, en raison de la suppression des caractères """ effectuée par le traitement C d'argv, vous devrez échapper une construction comme celle-ci (dans un répertoire contenant les fichiers PERL.C, PERL.EXE, PERL.H et PERL.OBJ) :

    $ perl -e "print join(' ',@ARGV)" perl.*
perl.c perl.exe perl.h perl.obj

    de la manière triple guillemets suivante :

    $ perl -e "print join(' ',@ARGV)" """perl.*"""
perl.*

    Dans le cas des arguments de ligne de commande non mis entre guillemets ou dans les appels à glob(), l'expansion des caractères génériques VMS est effectuée. (L'expansion des caractères génériques de style csh est disponible si vous utilisez "File::Glob::glob".) Si la spécification de caractères génériques contient un spécificateur de périphérique ou de répertoire, les spécifications résultantes contiendront également un périphérique et un répertoire ; sinon, les informations de périphérique et de répertoire sont supprimées. Les spécifications résultantes de style VMS conteniront un périphérique et un répertoire complets, tandis que les spécifications résultantes de style Unix ne contiendront qu'une partie du chemin du répertoire qui était présente dans la spécification d'entrée. Par exemple, si votre répertoire par défaut est Perl_Root:[000000], l'expansion de "[.t]*.*" produira des spécifications de fichiers comme "perl_root:[t]base.dir", tandis que l'expansion de "t/*/*" produira des spécifications de fichiers comme "t/base.dir". (Ceci est fait pour correspondre au comportement de l'expansion des caractères génériques effectuée par les shells Unix.)

    De même, la spécification de fichier résultante contiendra la version du fichier uniquement si elle était présente dans la spécification d'entrée.

    Tubes

    Les tubes d'entrée et de sortie vers les descripteurs de fichiers Perl sont pris en charge ; le "nom de fichier" est passé à lib$spawn() pour une exécution asynchrone. Vous devez faire attention à fermer tous les tubes que vous avez ouverts dans un script Perl, de peur de laisser des sous-processus "orphelins" lorsque Perl se termine.

    Vous pouvez également utiliser les backticks pour invoquer un sous-processus DCL, dont la sortie est utilisée comme valeur de retour de l'expression. La chaîne entre les backticks est traitée comme si elle était l'argument de l'opérateur "system" (voir ci-dessous). Dans ce cas, Perl attendra que le sous-processus se termine avant de continuer.

    La boîte aux lettres (MBX) que Perl peut créer pour communiquer avec un tube a une taille de tampon par défaut de 8192 sur les systèmes 64 bits, 512 sur VAX. La taille de tampon par défaut est réglable via le nom logique PERL_MBX_SIZE à condition que la valeur soit comprise entre 128 et le paramètre SYSGEN MAXBUF inclus. Par exemple, pour définir la taille de la boîte aux lettres à 32767, utilisez "$ENV{'PERL_MBX_SIZE'} = 32767;", puis ouvrez et utilisez les constructions de tubes. Une alternative serait d'émettre la commande :

    $ Define PERL_MBX_SIZE 32767

    avant d'exécuter votre programme de tube à enregistrement large. Une valeur plus grande peut améliorer les performances au détriment du quota UAF BYTLM.

    Les éléments d'environnement PERL5LIB et PERLLIB fonctionnent comme documenté dans perl, à l'exception du fait que le séparateur d'éléments est, par défaut, '|' au lieu de ':'. Les spécifications de répertoire peuvent utiliser la syntaxe VMS ou Unix.

    Le débogueur forké de Perl

    Le débogueur forké de Perl place les commandes et la sortie du débogueur dans une fenêtre de terminal X-11 distincte afin que les commandes et la sortie de plusieurs processus ne soient pas mélangées.

    Perl sur VMS prend en charge une émulation du débogueur forké lorsque Perl s'exécute sur un système VMS disposant du support X11 installé.

    Pour utiliser le débogueur forké, vous devez avoir l'affichage par défaut défini sur un serveur X-11 et certaines variables d'environnement définies que Unix attend.

    Le débogueur forké nécessite que la variable d'environnement "TERM" soit "xterm", et que la variable d'environnement "DISPLAY" existe. "xterm" doit être en minuscules.

    $define TERM "xterm"
$define DISPLAY "hostname:0.0"

    Actuellement, la valeur de "DISPLAY" est ignorée. Il est recommandé de la définir sur le nom d'hôte de l'affichage, du serveur et de l'écran en notation Unix. À l'avenir, la valeur de DISPLAY pourrait être prise en compte par Perl au lieu d'utiliser l'affichage par défaut.

    Il peut être utile d'utiliser toujours le débogueur forké afin que les E/S du script soient séparées des E/S du débogueur. Vous pouvez forcer le débogueur à être forké en assignant une valeur au nom logique <PERLDB_PIDS> qui n'est pas un numéro d'identification de processus.

    $define PERLDB_PIDS XXXX

    Redirection et arriérisation des E/S

    Perl pour VMS prend en charge la redirection de l'entrée et de la sortie sur la ligne de commande, en utilisant un sous-ensemble de la syntaxe du shell Bourne :

    • "<fichier" lit stdin depuis "fichier",
    • ">fichier" écrit stdout dans "fichier",
    • ">>fichier" ajoute stdout à "fichier",
    • "2>fichier" écrit stderr dans "fichier",
    • "2>>fichier" ajoute stderr à "fichier", et
    • "2>&1" redirige stderr vers stdout.

    De plus, la sortie peut être dirigée vers un sous-processus, en utilisant le caractère '|'. Tout ce qui suit ce caractère sur la ligne de commande est passé à un sous-processus pour exécution ; le sous-processus prend la sortie de Perl comme son entrée.

    Enfin, si la ligne de commande se termine par '&', la commande entière est exécutée en arrière-plan en tant que sous-processus asynchrone.

    Les tests "-b", "-B", "-c", "-C", "-d", "-e", "-f", "-o", "-M", "-s", "-S", "-t", "-T", et "-z" fonctionnent comme annoncé.     system, times, waitpid, unlink, utime

    system LIST
    When "system" is called without arguments, it provides a convenient interface to the VMS DCL command interpreter.

    If LIST consists of a single scalar argument, it is passed to DCL as a command string. For example:

    system "SHOW MEMORY /FULL"

    If LIST consists of multiple arguments, they are passed to DCL as a command procedure, similar to the standard Unix convention. For example:

    system "PRINT", $file, " /NOTIFY"

    If the token has no file type, and matches a file with null type, then an attempt is made to determine whether the file is an executable image which should be invoked using "MCR" or a text file which should be passed to DCL as a command procedure.

    If LIST consists of the empty string, "system" spawns an interactive DCL subprocess, in the same fashion as typing SPAWN at the DCL prompt.

    Perl waits for the subprocess to complete before continuing execution in the current process. As described in perlfunc, the return value of "system" is a fake "status" which follows POSIX semantics unless the pragma "use vmsish 'status'" is in effect; see the description of $? in this document for more detail.

    time
    The value returned by "time" is the offset in seconds from 01-JAN-1970 00:00:00 (just like the CRTL's times() routine), in order to make life easier for code coming in from the POSIX/Unix world.
    times
    The array returned by the "times" operator is divided up according to the same rules the CRTL times() routine. Therefore, the "system time" elements will always be 0, since there is no difference between "user time" and "system" time under VMS, and the time accumulated by a subprocess may or may not appear separately in the "child time" field, depending on whether times() keeps track of subprocesses separately. Note especially that the VAXCRTL (at least) keeps track only of subprocesses spawned using fork() and exec(); it will not accumulate the times of subprocesses spawned via pipes, system(), or backticks.
    unlink LIST
    "unlink" will delete the highest version of a file only; in order to delete all versions, you need to say 
    1 while unlink LIST;

    You may need to make this change to scripts written for a Unix system which expect that after a call to "unlink", no files with the names passed to "unlink" will exist. (Note: This can be changed at compile time; if you "use Config" and $Config{'d_unlink_all_versions'} is "define", then "unlink" will delete all versions of a file on the first call.)

    "unlink" will delete a file if at all possible, even if it requires changing file protection (though it won't try to change the protection of the parent directory). You can tell whether you've got explicit delete access to a file by using the "VMS::Filespec::candelete" operator. For instance, in order to delete only files to which you have delete access, you could say something like

    sub safe_unlink {
    my($file,$num);
    foreach $file (@_) {
        next unless VMS::Filespec::candelete($file);
        $num += unlink $file;
    }
    $num;
}

    (or you could just use "VMS::Stdio::remove", if you've installed the VMS::Stdio extension distributed with Perl). If "unlink" has to change the file protection to delete the file, and you interrupt it in midstream, the file may be left intact, but with a changed ACL allowing you delete access.

    This behavior of "unlink" is to be compatible with POSIX behavior and not traditional VMS behavior.

    utime LIST
    This operator changes only the modification time of the file (VMS revision date) on ODS-2 volumes and ODS-5 volumes without access dates enabled. On ODS-5 volumes with access dates enabled, the true access time is modified.
    waitpid PID,FLAGS
    If PID is a subprocess started by a piped open() (see open), "waitpid" will wait for that subprocess, and return its final status value in $?. If PID is a subprocess created in some other way (e.g. SPAWNed before Perl was invoked), "waitpid" will simply check once per second whether the process has completed, and return when it has. (If PID specifies a process that isn't a subprocess of the current process, and you invoked Perl with the "-w" switch, a warning will be issued.)

    Returns PID on success, -1 on error. The FLAGS argument is ignored in all cases.

    Variables Perl

    The following VMS-specific information applies to the indicated "special" Perl variables, in addition to the general information in perlvar. Where there is a conflict, this information takes precedence.

    %ENV
    The operation of the %ENV array depends on the translation of the logical name PERL_ENV_TABLES. If defined, it should be a search list, each element of which specifies a location for %ENV elements. If you tell Perl to read or set the element "$ENV{"name"}", then Perl uses the translations of PERL_ENV_TABLES as follows:
    CRTL_ENV
    This string tells Perl to consult the CRTL's internal "environ" array of key-value pairs, using name as the key. In most cases, this contains only a few keys, but if Perl was invoked via the C "exec[lv]e()" function, as is the case for some embedded Perl applications or when running under a shell such as GNV bash, the "environ" array may have been populated by the calling program.
    CLISYM_[LOCAL]
    A string beginning with "CLISYM_"tells Perl to consult the CLI's symbol tables, using name as the name of the symbol. When reading an element of %ENV, the local symbol table is scanned first, followed by the global symbol table.. The characters following "CLISYM_" are significant when an element of %ENV is set or deleted: if the complete string is "CLISYM_LOCAL", the change is made in the local symbol table; otherwise the global symbol table is changed.
    Any other string
    If an element of PERL_ENV_TABLES translates to any other string, that string is used as the name of a logical name table, which is consulted using name as the logical name. The normal search order of access modes is used.

    PERL_ENV_TABLES is translated once when Perl starts up; any changes you make while Perl is running do not affect the behavior of %ENV. If PERL_ENV_TABLES is not defined, then Perl defaults to consulting first the logical name tables specified by LNM$FILE_DEV, and then the CRTL "environ" array. This default order is reversed when the logical name GNV$UNIX_SHELL is defined, such as when running under GNV bash.

    For operations on %ENV entries based on logical names or DCL symbols, the key string is treated as if it were entirely uppercase, regardless of the case actually specified in the Perl expression. Entries in %ENV based on the CRTL's environ array preserve the case of the key string when stored, and lookups are case sensitive.

    When an element of %ENV is read, the locations to which PERL_ENV_TABLES points are checked in order, and the value obtained from the first successful lookup is returned. If the name of the %ENV element contains a semi-colon, it and any characters after it are removed. These are ignored when the CRTL "environ" array or a CLI symbol table is consulted. However, the name is looked up in a logical name table, the suffix after the semi-colon is treated as the translation index to be used for the lookup. This lets you look up successive values for search list logical names. For instance, if you say

    $  Define STORY  once,upon,a,time,there,was
$  perl -e "for ($i = 0; $i <= 6; $i++) " -
_$ -e "{ print $ENV{'story;'.$i},' '}"

    Perl will print "ONCE UPON A TIME THERE WAS", assuming, of course, that PERL_ENV_TABLES is set up so that the logical name "story" is found, rather than a CLI symbol or CRTL "environ" element with the same name.

    When an element of %ENV is set to a defined string, the corresponding definition is made in the location to which the first translation of PERL_ENV_TABLES points. If this causes a logical name to be created, it is defined in supervisor mode. (The same is done if an existing logical name was defined in executive or kernel mode; an existing user or supervisor mode logical name is reset to the new value.) If the value is an empty string, the logical name's translation is defined as a single "NUL" (ASCII "\0") character, since a logical name cannot translate to a zero-length string. (This restriction does not apply to CLI symbols or CRTL "environ" values; they are set to the empty string.)

    When an element of %ENV is set to "undef", the element is looked up as if it were being read, and if it is found, it is deleted. (An item "deleted" from the CRTL "environ" array is set to the empty string.) Using "delete" to remove an element from %ENV has

    un effet similaire, mais après la suppression de l'élément, une nouvelle tentative est faite pour rechercher l'élément, donc un nom logique en mode interne ou un nom dans un autre emplacement remplacera le nom logique qui vient d'être supprimé. Dans les deux cas, seule la première valeur trouvée en recherchant PERL_ENV_TABLES est modifiée. Il n'est pas possible pour le moment de définir un nom logique de liste de recherche via %ENV.

    L'élément $ENV{DEFAULT} est spécial : lorsqu'il est lu, il renvoie le périphérique et le répertoire par défaut actuels de Perl, et lorsqu'il est défini, il les réinitialise, quelle que soit la définition de PERL_ENV_TABLES. Il ne peut être effacé ni supprimé ; les tentatives pour le faire sont ignorées silencieusement.

    Notez que si vous souhaitez transmettre des éléments du tableau d'environnement C-local à un sous-processus qui n'est pas démarré par fork/exec, ou qui n'exécute pas un programme C, vous pouvez les « promouvoir » en noms logiques dans le processus actuel, qui seront alors hérités par tous les sous-processus, en disant :

    foreach my $key (qw[clés locales C que vous souhaitez promouvoir]) {
    my $temp = $ENV{$key}; # lire du tableau local C
    $ENV{$key} = $temp;    # et définir comme nom logique
}

    (Vous ne pouvez pas simplement dire "$ENV{$key} = $ENV{$key}", car l'optimiseur Perl est assez intelligent pour élider l'expression.)

    N'essayez pas d'effacer %ENV en disant "%ENV = ();", cela générera une erreur fatale. Ceci est équivalent à faire ce qui suit depuis DCL :

    DELETE/LOGICAL *

    Vous pouvez imaginer à quel point les choses seraient graves si, par exemple, les noms logiques SYS$MANAGER ou SYS$SYSTEM étaient supprimés.

    Actuellement, la première fois que vous itérez sur %ENV en utilisant "keys", ou "values", vous subirez une pénalité de temps car tous les noms logiques sont lus, afin de remplir complètement %ENV. Les itérations ultérieures ne reliront pas les noms logiques, elles ne seront donc pas aussi lentes, mais elles ne refléteront pas non plus les modifications apportées aux tables de noms logiques par d'autres programmes.

    Vous devez être prudent avec les noms logiques représentant des fichiers permanents de processus, tels que "SYS$INPUT" et "SYS$OUTPUT". Les traductions de ces noms logiques sont préfixées par une valeur binaire de deux octets (0x1B 0x00) qui doit être retirée si vous souhaitez l'utiliser. (Dans les versions précédentes de Perl, il n'était pas possible d'obtenir les valeurs de ces noms logiques, car l'octet nul agissait comme un terminateur de chaîne)

$!
La valeur chaîne de $! est celle renvoyée par la fonction strerror() du CRTL, elle inclura donc le message VMS pour les erreurs spécifiques à VMS. La valeur numérique de $! est la valeur de "errno", sauf si errno est EVMSERR, auquel cas $! contient la valeur de vaxc$errno. La définition de $! définit toujours errno à la valeur spécifiée. Si cette valeur est EVMSERR, elle définit également vaxc$errno à 4 (NONAME-F-NOMSG), de sorte que la valeur chaîne de $! ne reflétera pas le message d'erreur VMS d'avant la définition de $!.
$^E
Cette variable donne un accès direct aux valeurs d'état VMS dans vaxc$errno, qui sont souvent plus spécifiques que les messages d'erreur génériques de style Unix dans $!. Sa valeur numérique est la valeur de vaxc$errno, et sa valeur chaîne est la chaîne de message VMS correspondante, telle qu'obtenue par sys$getmsg(). La définition de $^E définit vaxc$errno à la valeur spécifiée.

Bien que Perl tente de maintenir la valeur de vaxc$errno à jour, si errno n'est pas EVMSERR, elle peut ne pas provenir de l'opération actuelle.

$?
La « valeur d'état » renvoyée dans $? est synthétisée à partir de l'état de sortie réel du sous-processus d'une manière qui approche la sémantique de wait(5) POSIX, afin de permettre aux programmes Perl de tester de manière portable la réussite des sous-processus. Les 8 bits de poids faible de $? sont toujours 0 sous VMS, car l'état de terminaison d'un processus peut ou non avoir été généré par une exception.

Les 8 bits suivants contiennent l'état de terminaison du programme.

Si le processus enfant suit la convention des programmes C compilés avec la macro _POSIX_EXIT définie, la valeur d'état contiendra la valeur réelle de 0 à 255 renvoyée par ce programme lors d'une sortie normale.

Avec la macro _POSIX_EXIT définie, la valeur de sortie Unix zéro est représentée par un état natif VMS de 1, et les valeurs Unix de 2 à 255 sont encodées par l'équation :

VMS_status = 0x35a000 + (unix_value * 8) + 1.

Et dans le cas spécial de la valeur Unix 1, l'encodage est :

VMS_status = 0x35a000 + 8 + 2 + 0x10000000.

Pour d'autres états de terminaison, la partie sévérité de l'état de sortie du sous-processus est utilisée : si la sévérité était succès ou information, ces bits sont tous 0 ; si la sévérité était avertissement, ils contiennent une valeur de 1 ; si la sévérité était erreur ou erreur fatale, ils contiennent les bits de sévérité réels, ce qui se traduit par une valeur de 2 pour erreur et 4 pour erreur sévère. Fatal est un autre terme pour l'état d'erreur sévère.

Par conséquent, $? sera toujours zéro si l'état de sortie du sous-processus indiquait une terminaison réussie, et non nul si un avertissement ou une erreur s'est produit ou si un programme conforme à l'encodage des valeurs _POSIX_EXIT a été exécuté et a défini un état.

Comment faire la différence entre un état non nul qui résulte d'un état d'erreur natif VMS ou d'un état Unix encodé ? Vous ne pouvez pas, à moins de regarder la valeur ${^CHILD_ERROR_NATIVE}. La valeur ${^CHILD_ERROR_NATIVE} renvoie la valeur d'état VMS réelle et vérifie les bits de sévérité. Si les bits de sévérité sont égaux à 1, alors si la valeur numérique de $? est comprise entre 2 et 255 ou 0, alors $? reflète avec précision une valeur renvoyée par une application Unix. Si $? est 1, et que les bits de sévérité indiquent une erreur VMS (2), alors $? provient d'une valeur de sortie d'application Unix.

En pratique, les scripts Perl qui appellent des programmes renvoyant des valeurs d'état de type _POSIX_EXIT s'attendront à ces valeurs, et les programmes qui appellent des programmes VMS traditionnels s'attendront soit au comportement précédent, soit vérifieront simplement un état non nul.

Et le succès est toujours la valeur 0 dans tous les comportements.

Lorsque l'état de terminaison VMS réel de l'enfant est une erreur, en interne, la valeur $! sera définie sur la valeur errno Unix la plus proche de cette erreur afin que les scripts Perl qui testent les messages d'erreur voient le message d'erreur de style Unix attendu au lieu d'un message VMS.

Inversement, lors de la définition de $? dans un bloc END, une tentative est faite pour convertir la valeur POSIX en un état natif compréhensible par le système d'exploitation lors de la sortie de Perl. Ce que cela signifie, c'est que définir $? à zéro entraîne la valeur de succès générique SS$_NORMAL, et définir $? à une valeur non nulle entraîne l'état d'échec générique SS$_ABORT. Voir aussi « exit » dans perlport.

Avec le nom logique "PERL_VMS_POSIX_EXIT" défini sur "ENABLE", la définition de $? entraînera l'encodage de la nouvelle valeur dans $^E afin que les valeurs d'état de sortie du parent ou de l'enfant d'origine
0 à 255 puissent être automatiquement récupérées par les programmes C attendant le comportement _POSIX_EXIT. Si une valeur de sortie de parent et d'enfant est non nulle, alors on supposera qu'il s'agit en fait d'une valeur d'état native VMS à transmettre. La valeur spéciale 0xFFFF est presque un NOOP car elle fera que l'état natif VMS actuel dans la bibliothèque C devienne l'état VMS natif Perl actuel, et est gérée de cette manière car elle n'est pas une valeur d'état native VMS valide. Il est recommandé de n'utiliser que des valeurs dans la plage des numéros d'état natifs VMS Unix normaux, de 0 à 255.

Le pragma "use vmsish 'status'" fait que $? reflète l'état de sortie VMS réel au lieu de l'émulation par défaut de l'état POSIX décrite ci-dessus. Ce pragma désactive également la conversion des valeurs non nulles en SS$_ABORT lors de la définition de $? dans un bloc END (mais zéro sera toujours converti en SS$_NORMAL).

N'utilisez pas le pragma "use vmsish 'status'" avec "PERL_VMS_POSIX_EXIT" activé, car ils demandent parfois des actions contradictoires et les conséquences de l'ignorance de ce conseil seront indéfinies pour permettre de futures améliorations dans la gestion des sorties POSIX.

En général, avec "PERL_VMS_POSIX_EXIT" activé, des informations plus détaillées seront disponibles dans l'état de sortie pour les scripts DCL ou d'autres outils VMS natifs, et fourniront les informations attendues pour les programmes Posix. Il n'a pas été rendu par défaut afin de préserver la compatibilité ascendante.

N.B. La définition de "DECC$FILENAME_UNIX_REPORT" active implicitement "PERL_VMS_POSIX_EXIT".

$|
La définition de $| pour un flux d'E/S provoque la mise en mémoire tampon de vidage des données jusqu'au disque à chaque écriture (c'est-à-dire pas seulement dans les tampons RMS sous-jacents pour un fichier). En d'autres termes, c'est équivalent à appeler fflush() et fsync() depuis C.

Modules standard avec différences spécifiques à VMS

SDBM_File

SDBM_File fonctionne correctement sous VMS. Il présente cependant une légère différence. Le fichier répertoire de base de données créé a une extension .sdbm_dir plutôt qu'une extension .dir. Les fichiers .dir sont des fichiers répertoires du système de fichiers VMS, et leur utilisation à d'autres fins pourrait causer des problèmes inacceptables.
