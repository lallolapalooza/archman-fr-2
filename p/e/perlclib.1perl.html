NOM

perlclib - Interaction avec les fonctions de la bibliothèque C standard

DESCRIPTION

L'interpréteur Perl est écrit en C ; le code XS se développe également en C. Inévitablement, ce code appellera certaines fonctions de la bibliothèque C, "libc". Ce document donne quelques indications sur l'interface avec cette bibliothèque.

Une chose à noter pour les porteurs de Perl est que perl n'utilise pas beaucoup la bibliothèque C standard en interne ; vous verrez très peu d'utilisation, par exemple, des fonctions de ctype.h. C'est parce que Perl a tendance à réimplémenter ou à abstraire les fonctions de la bibliothèque standard, afin que nous sachions exactement comment elles vont fonctionner.

fonctions libc à éviter

Il existe de nombreuses fonctions libc. La plupart d'entre elles peuvent être utilisées, mais certaines ne le peuvent pas. Voici quelques raisons possibles :

  • Elles risquent d'interférer avec le fonctionnement de l'interpréteur Perl, comme sa comptabilité, sa gestion des signaux, son allocation mémoire, ou toute autre chose de nuisible.
  • Elles ne sont pas implémentées sur toutes les plateformes, mais il existe une alternative qui l'est.

    Ou elles peuvent être buggées ou dépréciées sur certaines ou toutes les plateformes.

  • Elles ne conviennent pas aux opérations multithread, mais il existe une alternative qui l'est et qui est tout aussi facile à utiliser.

    Vous ne vous attendez peut-être jamais à ce que votre code soit utilisé sous les threads, mais le code a tendance à être adapté au-delà de nos attentes initiales. S'il est tout aussi facile d'utiliser quelque chose qui peut être utilisé sous les threads, il est préférable de l'utiliser maintenant, juste au cas où.

  • Dans les fonctions qui traitent des chaînes, des complications peuvent survenir car la chaîne peut être encodée de différentes manières, par exemple en UTF-8. Pour celles-ci, il est probablement préférable de placer la chaîne dans un SV et d'utiliser les fonctions de gestion de chaînes SV de Perl qui contiennent une logique étendue pour traiter ce problème.
  • Dans les fonctions qui traitent des nombres, des complications peuvent survenir car les nombres deviennent trop grands ou trop petits, et les limites dépendent de la plateforme actuelle. Encore une fois, les types de données numériques SV de Perl ont une logique étendue pour gérer ce genre de problèmes.
  • Elles sont conscientes de la locale, et votre appelant peut ne pas le vouloir.

Le commentaire et les tableaux suivants donnent quelques fonctions dans la première colonne qui ne devraient pas être utilisées dans le code C ou XS, avec l'alternative préférée (le cas échéant) dans la seconde colonne.

Gestion de la mémoire et manipulation de chaînes

Au lieu de :                    Utiliser :
t* p = malloc(n)               Newx(p, n, t)
t* p = calloc(n, s)            Newxz(p, n, t)
p = realloc(p, n)              Renew(p, n, t)

Il n'est pas portable d'essayer d'allouer 0 octet ; allouer 1 ou plus est portable. Ne mélangez jamais les pointeurs entre "Newx", "Renew", "Safefree" et les équivalents libc "malloc", "realloc", "free". Ils ne proviennent pas du même pool de mémoire ou du même allocateur. Soit un SEGV instantané ou retardé surviendra, soit des fuites de mémoire subtiles ou une corruption subtile du tas se produiront.

memcpy(dst, src, n)            Copy(src, dst, n, t)
memmove(dst, src, n)           Move(src, dst, n, t)
memcpy(dst, src, sizeof(t))    StructCopy(src, dst, t)

Notez l'ordre différent des arguments pour "Copy" et "Move" par rapport à ceux utilisés dans "memcpy" et "memmove".

memset(dst, 0, n * sizeof(t))  Zero(dst, n, t)
memzero(dst, 0)                Zero(dst, n, char)
free(p)                        Safefree(p)
strdup(p)                      savepv(p)
strndup(p, n)                  savepvn(p, n) (Hé, strndup n'existe pas !)

Parfois, au lieu de zérotiser le tas alloué en utilisant Newxz(), vous devriez envisager de "empoisonner" les données. Cela signifie écrire un schéma de bits dedans qui devrait être illégal en tant que pointeurs (et nombres à virgule flottante), et aussi suffisamment surprenant en tant qu'entiers, afin que tout code tentant d'utiliser les données sans réflexion tombe en panne plus tôt que tard. L'empoisonnement peut être effectué à l'aide des macros Poison(), qui ont des arguments similaires à Zero() :

PoisonWith(dst, n, t, b)    scribe la mémoire avec l'octet b
PoisonNew(dst, n, t)        équivalent à PoisonWith(dst, n, t, 0xAB)
PoisonFree(dst, n, t)       équivalent à PoisonWith(dst, n, t, 0xEF)
Poison(dst, n, t)           équivalent à PoisonFree(dst, n, t)
strstr(big, little)            instr(big, little)
memmem(big, blen, little, len) ninstr(big, bigend, little, little_end)
strcmp(s1, s2)                 strLE(s1, s2) / strEQ(s1, s2)
                                             / strGT(s1,s2)
strncmp(s1, s2, n)             strnNE(s1, s2, n) / strnEQ(s1, s2, n)
memcmp(p1, p2, n)              memNE(p1, p2, n)
!memcmp(p1, p2, n)             memEQ(p1, p2, n)

La plupart du temps, cependant, vous voudrez traiter avec des SV en interne au lieu de chaînes "char *" brutes :

strlen(s)                   sv_len(sv)
strcpy(dt, src)             sv_setpv(sv, s)
strncpy(dt, src, n)         sv_setpvn(sv, s, n)
strcat(dt, src)             sv_catpv(sv, s)
strncat(dt, src)            sv_catpvn(sv, s)

Si vous avez besoin de chaînes brutes, utilisez plutôt celles-ci :

my_strnlen(s, maxlen)
my_strlcpy(dt, src, sizeof(dt)

) my_strlcat(dt, src, sizeof(dt))

Similairement, vous pouvez utiliser les SV pour créer des chaînes à partir de formats

sprintf(s, fmt, ...)         sv_setpvf(sv, fmt, ...)
vsprintf(str, fmt, va_list)  sv_vsetpvf(sv, fmt, va_list)

Ou pour les chaînes brutes,

my_snprintf(dt, len, fmt, ...)
my_vsnprintf(dt, len, fmt, va_list)
vsprintf(str, fmt, va_list)  sv_vsnprintf(sv, fmt, va_list)

Notez également l'existence de "sv_catpvf" et "sv_vcatpvfn", combinant la concaténation avec le formatage ; et "Perl_form"() pour une autre forme de population formatée.

Notez que les fonctions printf(), sprintf(), etc. de glibc sont boguées avant la version 2.17 de glibc. Elles ne permettront pas un format "%.s" avec une précision pour créer une chaîne qui n'est pas du UTF-8 valide si la locale sous-jacente actuelle du programme est UTF-8. Ce qui se passe, c'est que le %s et son opérande sont simplement ignorés sans aucun avertissement. https://sourceware.org/bugzilla/show_bug.cgi?id=6530.

Tests de classes de caractères

Il existe plusieurs types de tests de classes de caractères que Perl implémente. Tous sont décrits plus en détail dans "Classification des caractères" de perlapi et "Changement de casse des caractères" de perlapi.

Les routines de la bibliothèque C listées dans le tableau ci-dessous renvoient des valeurs basées sur la locale actuelle. Utilisez les entrées de la dernière colonne pour cette fonctionnalité. Les deux autres colonnes supposent toujours une locale POSIX (ou C). Les entrées de la colonne ASCII ne sont significatives que pour les entrées ASCII, renvoyant FALSE pour tout le reste. Utilisez-les uniquement lorsque vous savez que c'est ce que vous voulez. Les entrées de la colonne Latin1 supposent que les caractères 8 bits non ASCII sont tels que Unicode les définit, identiques à ISO-8859-1, souvent appelés Latin 1.

Pour les fonctions correspondantes comme iswupper(), etc., utilisez isUPPER_uvchr() pour le non-locale ; ou isUPPER_LC_uvchr() pour la locale. Et utilisez toLOWER_uvchr() au lieu de towlower(), etc. Il n'y a pas d'équivalents directs pour la locale ; il est préférable de placer la chaîne dans un SV.

N'utilisez aucune des fonctions comme isalnum_l(). Elles ne sont pas portables et interfèrent avec la gestion interne de Perl.

Pour souligner que vous opérez uniquement sur des caractères ASCII, vous pouvez ajouter "_A" à chacune des macros de la colonne ASCII : "isALPHA_A", "isDIGIT_A", et ainsi de suite.

(Il n'y a pas d'entrée dans la colonne Latin1 pour "isascii" même s'il existe un "isASCII_L1", qui est identique à "isASCII" ; le nom de ce dernier est plus clair. Il n'y a pas d'entrée dans la colonne Latin1 pour "toupper" car le résultat peut être non-Latin1. Vous devez utiliser "toUPPER_uvchr", comme décrit dans "Changement de casse des caractères" de perlapi.)

Notez que les comparaisons insensibles à la casse de libc sont limitées ; Unicode fournit un ensemble plus riche, utilisant le concept de repliage. Si vous avez besoin de plus qu'une égalité/inégalité, il est probablement préférable de stocker vos chaînes dans un SV et d'utiliser les fonctions SV pour effectuer la comparaison. De même pour la collation.

L'utilisation typique est de faire des vérifications de plage sur "uv" avant le transtypage :

int i; UV uv;
char* end_ptr = input_end;
if (grok_atoUV(input, &uv, &end_ptr)
    && uv <= INT_MAX)
  i = (int)uv;
  ... /* continuer l'analyse à partir de end_ptr */
} else {
  ... /* erreur d'analyse : pas un entier décimal dans la plage 0 .. MAX_IV */
}

Notez également les fonctions "grok_bin", "grok_hex" et "grok_oct" dans numeric.c pour convertir des chaînes représentant des nombres dans les bases respectives en "NV"s. Notez que grok_atoUV() ne gère pas les entrées négatives, ni les espaces blancs en tête (en étant délibérément strict).

    depuis votre code, vous êtes affecté par la locale actuelle.


La première chose à savoir sur cette liste est qu'il existe de
    meilleures alternatives à de nombreuses fonctions, que vous devriez très
    probablement utiliser à la place. Voir "fonctions libc à éviter"
    ci-dessus. Cela inclut l'utilisation de l'E/S Perl perlapio.


La deuxième chose à savoir est que Perl est documenté pour ne pas
    faire attention à la locale actuelle, sauf pour le code exécuté dans la portée
    d'une instruction "use locale". Si vous
    enfreignez cela, vous pourriez créer des bugs, selon l'application.


La chose suivante à savoir est que de nombreuses fonctions dépendent
    uniquement de la locale en ce qui concerne les valeurs numériques. Votre code a
    probablement été écrit en supposant que le point décimal (virgule) est un point
    (U+002E : POINT FINAL), et que les chaînes de nombres entiers ne sont pas
    séparées en groupes (1 000 000 dans une locale américaine signifie un
    million ; votre code ne s'attend probablement pas aux virgules). La bonne
    nouvelle est qu'en temps normal (à partir de Perl v5.22), votre code sera appelé
    avec la locale définie de manière à ce que ces attentes soient satisfaites. Une
    action explicite doit être entreprise pour changer cela (décrit un peu plus
    bas). Ceci est accompli par le fait que Perl ne bascule pas réellement dans une
    locale qui n'est pas conforme à ces attentes, sauf lorsqu'il est explicitement
    invité à le façonner. Les routines d'entrée/sortie et de formatage de Perl
    effectuent ce changement pour vous automatiquement, si nécessaire, puis reviennent
    en arrière. Si, pour une raison quelconque, vous devez le faire vous-même, le moyen le
    plus simple à partir de C et de code XS est d'utiliser la macro
    ""WITH_LC_NUMERIC_SET_TO_NEEDED""
    dans perlapi. Vous pouvez encapsuler cette macro autour d'un bloc de code
    entier que vous souhaitez exécuter dans l'environnement correct. En fin de compte,
    votre code fonctionnera probablement comme prévu à cet égard sans que vous ayez
    à prendre de mesures.


Cela laisse les fonctions restantes. Votre code sera appelé avec toutes
    les portions de la locale, à l'exception des parties numériques, définies sur la
    locale sous-jacente. Souvent, la locale n'a pas beaucoup d'importance pour votre
    code, et vous n'aurez pas non plus à prendre de mesures ; les choses se
    dérouleront simplement. Mais vous devriez examiner les pages man des fonctions que
    vous utilisez pour le vérifier. Souvent, Perl a de meilleures façons de faire la
    même fonctionnalité. Envisagez d'utiliser des SV et leurs routines d'accès plutôt que
    d'appeler les fonctions de bas niveau qui, par exemple, déterminent combien
    d'octets se trouvent dans un caractère encodé en UTF-8.


Vous pouvez déterminer si vous avez été appelé depuis la portée d'un
    "use locale" en utilisant la macro booléenne
    ""IN_LOCALE"" dans
    perlapi.


Si vous ne souhaitez pas être dans la locale sous-jacente, vous pouvez
    appeler ""Perl_setlocale"" dans
    perlapi pour la changer temporairement à celle dont vous avez besoin (probablement
    la locale "C"), puis la changer à nouveau avant de revenir. Cela peut
    être **très** problématique sur les perls multithreadés sur certaines
    plateformes. Voir "Gestion des perls embarqués et des threads".


Un problème avec le changement de la locale d'une seule catégorie est que le
    mojibake peut survenir sur certaines plateformes si la catégorie
    "LC_CTYPE" et celle changée ne sont pas les
    mêmes. Sur les plateformes où ce n'est pas un problème, la directive du préprocesseur
    "LIBC_HANDLES_MISMATCHED_CTYPE" sera définie.
    Sinon, vous devrez peut-être changer plus d'une catégorie pour accomplir votre tâche
    correctement. Et, il y aura de nombreuses combinaisons de locales où le mojibake ne se
    produira probablement pas, de sorte que vous ne serez pas confronté à cela tant que le code
    ne sera pas exécuté sur le terrain par quelqu'un qui ne parle pas très bien votre
    langue.


Plus tôt, nous avons mentionné qu'une action explicite est requise pour que votre
    code soit appelé avec les portions numériques de la locale ne satisfaisant pas les attentes
    typiques d'avoir un point pour le caractère radix et aucune ponctuation séparant les groupes
    de chiffres. Cette action consiste à appeler la fonction ""switch_to_global_locale""
    dans perlapi.


switch_to_global_locale() a été écrite
    initialement pour faire face à la bibliothèque "Tk",
    mais est suffisamment générale pour d'autres situations similaires.
    "Tk" change la locale globale pour correspondre
    à ses attentes (les versions ultérieures de celle-ci permettent de désactiver cela).
    Cela crée un conflit avec Perl qui pense qu'il contrôle également la locale. Appeler
    cette fonction indique à Perl de céder le contrôle. Appeler
    ""sync_locale"" dans perlapi indique
    à Perl de reprendre le contrôle, acceptant quelle que soit la locale qui a été changée
    entre-temps. Si votre code est appelé pendant cet intervalle, toutes les portions de la
    locale seront les valeurs brutes sous-jacentes. Si vous avez besoin de manipuler des
    nombres, vous êtes seul en ce qui concerne le caractère radix et le regroupement. Si vous vous
    trouvez dans cette situation, il est généralement préférable de rendre l'intervalle entre les
    appels à ces deux fonctions aussi court que possible, et d'éviter les calculs jusqu'à ce que Perl
    reprenne le contrôle.


Il est important que Perl connaisse toutes les catégories de locale possibles
    sur la plateforme, même si elles ne sont apparemment pas utilisées dans votre programme.
    Perl connaît toutes celles de Linux. Si votre plateforme en a d'autres, vous pouvez soumettre
    un problème à https://github.com/Perl/perl5/issues pour son inclusion dans la prochaine version. En attendant, il est possible d'éditer la source de Perl pour lui enseigner la catégorie, puis de la recompiler. Recherchez des occurrences de, par exemple, "LC_PAPER" dans la source, et utilisez-la comme modèle pour ajouter celle qui manque.


Il y a d'autres complications dans le fonctionnement multithreadé. Continuez
    à lire.

Il est possible d'embarquer un interpréteur Perl dans un programme plus

    Problèmes   généraux liés à la thread-safety
    

    Certaines fonctions libc utilisent et/ou modifient un état global, tel qu'une base de données. Les fonctions libc supposent qu'une seule instance à la fois opère sur cette base de données. Des résultats imprévisibles se produisent si plusieurs instances le font, même si la base de données n'est pas modifiée. Par exemple, il existe généralement un itérateur global pour une telle base de données et cet itérateur est maintenu par libc, de sorte que chaque nouvelle lecture de n'importe quelle instance le fait avancer, ce qui signifie qu'aucune instance ne verra toutes les entrées. La seule façon de rendre ces fonctions thread-safe est d'avoir un verrou exclusif sur un mutex depuis l'appel open jusqu'à l'appel close. Il est conseillé de ne pas utiliser de telles bases de données par plus d'une instance à la fois.
    

    D'autres exemples de fonctions qui utilisent un état global comprennent les générateurs de nombres pseudo-aléatoires. Certaines implémentations libc de BAqrand()', par exemple, peuvent partager les données entre les threads ; d'autres peuvent avoir des données par thread. Les partagées auront des résultats non reproductibles, car les threads varieront dans leurs timings et leurs interactions. C'est peut-être ce que vous voulez ; ou peut-être pas. (Cette fonction particulière est candidate à être retirée de la norme POSIX en raison de ces problèmes.)
    

    Les fonctions qui écrivent dans un flux sont également considérées comme non thread-safe lorsque le verrouillage n'est pas effectué. Mais les conséquences habituelles sont simplement que les données sont écrites dans un ordre imprévisible ; ce résultat peut vous être tout à fait acceptable.
    

    Étant donné que le répertoire de travail courant est global à un processus, toutes les instances en dépendent. Une instance effectuant un chdir(2) affecte toutes les autres instances. Dans un environnement multi-thread, tout appel libc qui s'attend à ce que le répertoire ne change pas pendant son exécution aura des résultats indéfinis si un autre thread l'interrompt au mauvais moment et change le répertoire. Les pages man ne listent qu'un seul appel de ce type, nftw(). Mais il peut y avoir d'autres problèmes cachés.
    

    

    

    Fonctions   équivalentes réentrantes
    

    Certaines fonctions qui posent problème en matière de MULTIPLICITÉ ont des versions réentrantes (sur certaines ou toutes les plateformes) qui sont mieux adaptées, avec moins (peut-être aucune) de courses lors de l'exécution sous des threads.
    

    Certaines de ces fonctions réentrantes qui sont disponibles sur toutes les plateformes devraient de toute façon toujours être utilisées ; elles figurent dans les listes directement sous "fonctions libc à éviter".
    

    D'autres peuvent ne pas être disponibles sur certaines plateformes, ou présenter des problèmes qui les rendent indésirables à utiliser même lorsqu'elles sont disponibles. Ou il peut être simplement plus compliqué et fastidieux d'utiliser la version réentrante. Pour celles-ci, perl dispose d'un mécanisme pour substituer automatiquement la version réentrante lorsqu'elle est disponible et souhaitable, tout en cachant les complications de votre code. Cette fonctionnalité est activée par défaut pour le code du cœur de Perl et ses extensions. Pour l'activer dans d'autres modules XS,

    Il est plus simple pour vous d'utiliser la version non préférée dans votre code, et de vous fier à cette fonctionnalité pour faire le mieux, en partie parce qu'aucune substitution n'est effectuée si l'alternative n'est pas disponible ou souhaitable sur la plateforme, ni si les threads ne sont pas activés. Vous écrivez simplement comme s'il n'y avait pas de threads, et vous obtenez le meilleur comportement sans avoir à y penser.
    

    Sur certaines plateformes, les fonctions de bibliothèque plus sûres peuvent échouer si le tampon de résultat est trop petit (par exemple, les bases de données des groupes d'utilisateurs peuvent être assez volumineuses, et les fonctions réentrantes peuvent devoir conserver une copie complète de ces bases de données).     nombre maximum d'octets que vous autoriserez.

    NAME
    

    perlclib - Standard C library functions used by Perl
    

    

    

    DESCRIPTION
    

    This document lists C library (libc) functions that are of interest
    to Perl programmers, especially those writing extensions (modules in C). It
    covers functions that are problematic in multithreaded environments, functions
    that are locale-dependent, and functions that might be called by embedded
    Perl interpreters.
    

    

    libc functions to avoid
    

    Some libc functions use static internal storage or other global
    state. This makes them unsafe to call from more than one thread simultaneously.
    If a thread calls one of these functions, and another thread calls it or a
    related function that modifies the same state, the first thread's results
    can be incorrect or unpredictable. This is called a data race condition.
    

    The standard solution is to use the reentrant or thread-safe
    variants of these functions (often suffixed with _r or named
    gethostbyname_r, etc.), or to protect access to them with mutexes. However,
    not all such variants are available on all platforms, and even when they are,
    they may be implemented in a way that provides little or no concurrency
    benefit (e.g., by serializing access via a global mutex).
