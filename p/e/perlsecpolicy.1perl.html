PERLSECPOLICY(1perl) Guide du programmeur Perl PERLSECPOLICY(1perl)

NOM

perlsecpolicy - Politique de gestion des rapports de sécurité Perl

DESCRIPTION

Le projet Perl prend les problèmes de sécurité au sérieux.

La responsabilité de gérer les rapports de sécurité de manière rapide et efficace a été déléguée à une équipe de sécurité composée d'un sous-ensemble des développeurs principaux de Perl.

Ce document décrit le fonctionnement de l'équipe de sécurité Perl et la manière dont l'équipe évalue les nouveaux rapports de sécurité.

SIGNALEMENT DES PROBLÈMES DE SÉCURITÉ DANS PERL

Si vous pensez avoir découvert une vulnérabilité de sécurité dans l'interpréteur Perl ou dans les modules maintenus dans la base de code principale de Perl, envoyez les détails par e-mail à perl-security@perl.org <mailto:perl-security@perl.org>. Cette adresse est une liste de diffusion à adhésion fermée surveillée par l'équipe de sécurité Perl.

Vous devriez recevoir une réponse initiale à votre rapport dans les 72 heures. Si vous ne recevez pas de réponse dans ce délai, veuillez contacter le Conseil de direction de Perl <mailto:steering-council@perl.org>.

Lorsque les membres de l'équipe de sécurité répondent à vos messages, ils incluent généralement l'adresse perl-security@perl.org dans les champs « À » ou « Cc » de la réponse. Cela permet à toute l'équipe de sécurité de suivre la discussion et d'intervenir si nécessaire. Utilisez la fonctionnalité « Répondre à tous » de votre client de messagerie lorsque vous envoyez des réponses ultérieures afin que toute l'équipe de sécurité reçoive le message.

L'équipe de sécurité évaluera votre rapport et déterminera initialement s'il correspond probablement à la portée des problèmes traités par l'équipe. Des lignes directrices générales sur la manière dont cela est déterminé sont détaillées dans la section « QU'EST-CE QU'UN PROBLÈME DE SÉCURITÉ ».

Si votre rapport satisfait aux critères de l'équipe, vous recevrez l'identifiant CVE du problème. Les identifiants de problème sont de la forme CVE-AAAA-NNNNN, où AAAA est l'année de signalement du CVE et NNNNN est un numéro unique. Incluez cet identifiant dans tous les messages ultérieurs que vous envoyez.

L'équipe de sécurité vous enverra des mises à jour périodiques sur le statut de votre problème et vous guidera à travers toute action supplémentaire requise pour terminer le processus de correction de la vulnérabilité. Les étapes que les vulnérabilités traversent généralement sont expliquées dans la section « COMMENT NOUS GÉRONS LES PROBLÈMES DE SÉCURITÉ ».

QU'EST-CE QU'UN PROBLÈME DE SÉCURITÉ

Une vulnérabilité est un comportement d'un système logiciel qui compromet les protections attendues de confidentialité, d'intégrité ou de disponibilité du système.

Un problème de sécurité est un bug dans un ou plusieurs composants spécifiques d'un système logiciel qui crée une vulnérabilité.

Les logiciels écrits dans le langage de programmation Perl sont généralement composés de nombreuses couches logicielles écrites par différents groupes. Il peut être très compliqué de déterminer quelle couche spécifique d'une application complexe du monde réel était responsable de la prévention d'un comportement vulnérable, mais c'est une partie essentielle de la correction de la vulnérabilité.

Logiciels couverts par l'équipe de sécurité Perl

L'équipe de sécurité Perl traite les problèmes de sécurité dans :

  • L'interpréteur Perl
  • Les modules Perl expédiés avec l'interpréteur qui sont développés dans le dépôt principal de Perl
  • Les outils en ligne de commande expédiés avec l'interpréteur qui sont développés dans le dépôt principal de Perl

Les fichiers sous le répertoire cpan/ dans le dépôt Perl et les archives de distribution sont développés et maintenus indépendamment. L'équipe de sécurité Perl ne gère pas directement les problèmes de sécurité pour ces modules, mais comme ce code est inclus avec Perl, nous aiderons à transmettre le problème au(x) mainteneur(s) concerné(s) et vous pouvez toujours nous signaler ces problèmes en secret.

Bugs pouvant être qualifiés de problèmes de sécurité dans Perl

Perl est conçu pour être un langage de programmation généraliste rapide et flexible. L'interpréteur Perl et les modules Perl facilitent l'écriture d'applications sûres et sécurisées, mais ils ont des limites.

En règle générale, un bug dans Perl doit satisfaire à tous les critères suivants pour être considéré comme un problème de sécurité :

  • Le comportement vulnérable n'est pas mentionné dans la documentation de Perl ou le traqueur de bogues public.
  • Le comportement vulnérable n'est pas implicite par un comportement attendu.
  • Le comportement vulnérable n'est pas une limitation généralement acceptée de l'implémentation.
  • Le comportement vulnérable est susceptible d'être exposé à une attaque dans des applications Perl autrement sécurisées.
  • Le comportement vulnérable procure un avantage tangible spécifique à un attaquant qui déclenche le comportement.

Bugs ne se qualifiant pas comme problèmes de sécurité dans Perl

Il existe certaines catégories de bugs qui sont fréquemment signalées à l'équipe de sécurité et qui ne répondent pas aux critères énumérés ci-dessus.

Voici une liste de bugs couramment signalés qui ne sont pas traités comme des problèmes de sécurité.

Alimentation de code non fiable à l'interpréteur

L'analyseur Perl n'est pas conçu pour évaluer du code non fiable. Si votre application nécessite l'évaluation de code non fiable, elle doit s'appuyer sur un bac à sable au niveau du système d'exploitation pour sa sécurité.

Dépassements de pile dus à une récursion excessive

La récursion excessive est souvent causée par du code qui n'impose pas de limites aux entrées. L'interpréteur Perl suppose que les limites de récursion seront imposées par l'application.

Erreurs de manque de mémoire

Les constructions Perl courantes telles que "pack", l'opérateur "x" et les expressions régulières acceptent des quantificateurs numériques qui contrôlent la quantité de mémoire allouée pour stocker les valeurs intermédiaires ou les résultats. Si vous permettez à un attaquant de fournir ces quantificateurs et de consommer toute la mémoire disponible, l'interpréteur Perl ne l'empêchera pas.

Évasion d'un compartiment sécurisé

Les restrictions d'opcode et les compartiments sécurisés ne sont pas pris en charge comme mécanismes de sécurité. L'analyseur Perl n'est pas conçu pour évaluer du code non fiable.

Utilisation des modèles pack "p" et "P"

Ces modèles sont dangereux par conception.

Problèmes de pile non référencée

Ces bugs se présentent généralement sous forme d'erreurs d'utilisation après libération (use-after-free) ou d'échecs d'assertion sur le type d'un "SV". Les plantages de pile non référencée se produisent généralement parce que le code modifie une référence ou un glob tout en utilisant les valeurs référencées par ce glob ou cette référence.

Ce type de bug est un problème de longue date avec l'interpréteur Perl qui survient rarement dans le code normal. Les exemples de ce type de bug supposent généralement que le code fourni par l'attaquant sera évalué par l'interpréteur Perl.

Désérialisation de données fournies par l'attaquant avec Storable

Storable est conçu pour être un format de sérialisation très rapide. Il n'est pas conçu pour être sûr lors de la désérialisation d'entrées non fiables.

Utilisation de bases de données SDBM_File fournies par l'attaquant

Le module SDBM_File n'est pas destiné à être utilisé avec des bases de données SDBM non fiables.

Scalaires marqués comme UTF-8 mal encodés

Ce type de bug se produit lorsque la couche PerlIO ":utf8" est utilisée pour lire des données mal encodées, ou lorsque d'autres mécanismes sont utilisés pour manipuler directement le drapeau UTF-8 sur un SV.

Un SV marqué UTF-8 mal encodé n'est pas un SV valide. Le code qui crée des SV de cette manière corrompt l'état interne de Perl.

Problèmes n'existant que dans blead, ou dans un candidat à la release

La branche blead et les candidats à la release Perl ne bénéficient pas d'un support de sécurité. Les défauts de sécurité présents uniquement dans les versions préliminaires de Perl sont traités via le processus normal de signalement et de résolution des bugs.

Modules CPAN ou autres ressources du projet Perl

L'équipe de sécurité Perl se concentre sur l'interpréteur Perl et les modules maintenus dans la base de code principale de Perl. L'équipe n'a pas d'accès spécial pour corriger les modules CPAN.

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

DOCUMENTATION DE SÉCURITÉ PERL

Ce document décrit la façon dont l'équipe de sécurité Perl gère les problèmes de sécurité, et comment vous pouvez nous aider.

CE QUE NOUS CONSIDÉRONS COMME DES PROBLÈMES DE SÉCURITÉ

Les problèmes de sécurité Perl sont divisés en deux catégories principales.

Bugs qui ne sont pas des problèmes de sécurité en eux-mêmes

La plupart des bugs Perl ne sont pas des problèmes de sécurité en eux-mêmes. La plupart des bugs qui entraînent un plantage du programme Perl, ou qui causent un mauvais comportement peuvent être évités en faisant attention à ne pas utiliser de données non fiables en entrée. Ces bugs sont considérés comme étant de la responsabilité de l'utilisateur final d'éviter, plutôt que d'être un bug de sécurité pour lequel Perl doit être corrigé.

Les bugs qui dégradent les performances de Perl sont également exclus de cette catégorie. Les bugs qui entraînent un accès non autorisé aux données sont également exclus de cette catégorie, sauf s'ils peuvent être exploités pour la dégradation des performances ou le déni de service. Les bugs qui entraînent un plantage de Perl sont considérés comme des problèmes de sécurité.

Comportements POSIX émulés sur les systèmes Windows

L'interpréteur Perl tente d'émuler les comportements POSIX tels que "fork", "system", "exec" et autres sur les systèmes Windows. Cette émulation présente de nombreuses particularités qui sont documentées en détail dans le traqueur de problèmes public de Perl. Modifier ces comportements provoquerait des perturbations importantes pour les utilisateurs existants sous Windows.

Bugs qui nécessitent une catégorisation spéciale

Certains bugs dans l'interpréteur Perl surviennent dans des zones du code qui sont sensibles à la sécurité et sujettes à des défaillances lors d'une utilisation normale.

Expressions régulières

Les expressions régulières non fiables sont généralement sûres à compiler et à faire correspondre avec plusieurs mises en garde. Les comportements suivants du moteur d'expressions régulières de Perl sont sous la responsabilité du développeur de les contraindre.

L'évaluation d'expressions régulières non fiables lorsque "use re 'eval';" est active n'est jamais sûre.

La compilation ou l'évaluation des expressions régulières ne sont garanties dans aucun délai fini spécifique.

Les expressions régulières peuvent consommer toute la mémoire système disponible lorsqu'elles sont compilées ou évaluées.

Les expressions régulières peuvent provoquer une récursion excessive qui arrête l'interpréteur Perl.

En règle générale, ne vous attendez pas à ce que le moteur d'expressions régulières de Perl résiste aux attaques par déni de service.

Bases de données DB_File, ODBM_File ou GDBM_File

Ces modules reposent sur des bibliothèques externes pour interagir avec les fichiers de base de données.

Les bugs causés par la lecture et l'écriture de ces formats de fichiers sont généralement causés par l'implémentation de la bibliothèque sous-jacente et ne constituent pas des problèmes de sécurité dans Perl.

Les bugs où Perl gère mal les valeurs de retour valides inattendues des bibliothèques sous-jacentes peuvent être considérés comme des problèmes de sécurité dans Perl.

Attaques par complexité algorithmique

L'interpréteur Perl est raisonnablement robuste aux attaques par complexité algorithmique. Il n'en est pas immunisé.

Les bugs de complexité algorithmique qui dépendent de l'interpréteur traitant des quantités extrêmement importantes de données fournies par un attaquant ne sont généralement pas traités comme des problèmes de sécurité.

Voir "Algorithmic Complexity Attacks" dans perlsec pour plus d'informations.

COMMENT NOUS TRAITONS LES PROBLÈMES DE SÉCURITÉ

L'équipe de sécurité Perl suit les pratiques de divulgation responsable. Les problèmes de sécurité sont gardés secrets jusqu'à ce qu'une correction soit facilement disponible pour la plupart des utilisateurs. Cela minimise les risques inhérents auxquels les utilisateurs sont confrontés en raison des vulnérabilités dans Perl.

Cacher temporairement les problèmes aux utilisateurs est un compromis nécessaire pour assurer leur sécurité. Cacher définitivement les problèmes aux utilisateurs n'est pas le but.

Lorsque vous signalez un problème de sécurité en privé à l'adresse de contact perl-security@perl.org <mailto:perl-security@perl.org>, nous attendons normalement que vous suiviez les pratiques de divulgation responsable dans la gestion du rapport. Si vous êtes incapable ou peu disposé à garder le problème secret jusqu'à ce qu'une correction soit disponible pour les utilisateurs, vous devez l'indiquer clairement dans le rapport initial.

Le flux de travail de remédiation des vulnérabilités de l'équipe de sécurité vise à être aussi ouvert et transparent que possible quant à l'état de votre rapport de sécurité.

Flux de travail de remédiation des vulnérabilités de Perl

Contact initial

Les nouveaux rapports de vulnérabilité recevront une réponse initiale dans les 72 heures suivant leur arrivée sur la liste de diffusion de l'équipe de sécurité. Si vous ne recevez aucune réponse dans ce délai, contactez le Conseil de Direction de Perl <mailto:steering-council@perl.org>.

La réponse initiale envoyée par l'équipe de sécurité confirmera la réception de votre message et fournira un délai estimé pour l'analyse de triage de l'équipe de sécurité.

Triage initial

L'équipe de sécurité évaluera le rapport et déterminera s'il est susceptible de répondre aux critères pour être traité comme un problème de sécurité.

L'équipe de sécurité vise à terminer le triage initial du rapport dans un délai de deux semaines. Les problèmes complexes nécessitant des discussions ou des recherches importantes peuvent prendre plus de temps.

Si le rapport de sécurité ne peut pas être reproduit ou ne répond pas aux critères de l'équipe pour être traité comme un problème de sécurité, vous serez informé par e-mail et vous aurez la possibilité de répondre.

Attribution CVE

Les rapports de sécurité qui réussissent l'analyse de triage initiale sont transformés en CVE. Lorsqu'un rapport progresse à ce stade, un ou plusieurs CVE sont réservés par l'équipe de sécurité. Les identifiants de problème ont la forme CVE-AAAA-NNNNN, où AAAA est l'année où le CVE a été signalé, et NNNNN est un numéro unique. Le CVE sera utilisé dans toute communication ultérieure sur le problème.

L'attribution de ces identifiants ne confirme pas qu'un rapport de sécurité représente une vulnérabilité dans Perl. De nombreux rapports nécessitent une analyse plus approfondie pour parvenir à cette détermination. La vulnérabilité ne doit pas être discutée publiquement à ce stade.

Un ticket interne sera également ouvert. Ces identifiants ont le format perl-security#NNN ou Perl/perl-security#NNN.

Les problèmes dans le traqueur privé de l'équipe de sécurité sont utilisés pour collecter des détails sur le problème et suivre les progrès vers une résolution. Ces notes et autres détails ne sont pas rendus publics une fois le problème résolu. Garder les notes du problème privées permet à l'équipe de sécurité de discuter librement des méthodes d'attaque, des outils d'attaque et d'autres problèmes privés connexes.

Développement de correctifs

Les membres de l'équipe de sécurité inspecteront le rapport et le code associé en détail pour produire des correctifs pour les versions prises en charge de Perl.

Si l'équipe découvre que le problème signalé ne répond pas aux critères de l'équipe à ce stade, vous serez informé par e-mail et vous aurez la possibilité de répondre avant que le problème ne soit clos.

L'équipe peut discuter des correctifs potentiels avec vous ou vous fournir des correctifs à des fins de test pendant cette période.

Le CVE est rédigé

Une fois qu'un problème est entièrement confirmé et qu'un correctif potentiel a été trouvé, l'équipe de sécurité communiquera avec le CNA de sécurité CPAN https://security.metacpan.org/.

Des détails tels que la gamme des versions de Perl vulnérables et l'identité des personnes qui ont découvert la faille doivent être collectés.

L'équipe de sécurité peut vous demander de clarifier le nom exact que nous devrions utiliser pour créditer la découverte du problème. La section "Crédit pour la vulnérabilité et primes" de ce document explique notre format préféré pour ce crédit.

Notifications avant publication

Lorsque l'équipe de sécurité est satisfaite que le correctif pour un problème de sécurité est prêt à être publié publiquement, une annonce de notification pré-publication est envoyée à la liste de diffusion des distributions Openwall https://oss-security.openwall.org/wiki/mailing-lists/distros. D'autres ré-emballeurs sont notifiés.

NOTE : Toutes les informations sous embargo envoyées à la liste de diffusion des distributions Openwall expirent dans les 2 semaines suivant leur divulgation à cet endroit.

Cette annonce pré-publication comprend une liste des versions de Perl affectées par la faille, une analyse des risques pour les utilisateurs, les correctifs produits par l'équipe de sécurité, et toute information sur les mesures d'atténuation ou le rétroportage des correctifs vers des versions antérieures de Perl que l'équipe de sécurité a à disposition.

L'annonce pré-publication comprendra une date cible spécifique pour l'annonce publique du problème. Le délai entre l'annonce pré-publication et la date de publication permet aux redistributeurs de préparer et de tester leurs propres mises à jour et annonces. Pendant cette période, les détails de la vulnérabilité et les correctifs sont sous embargo (voir "Période d'embargo") et ne doivent pas être partagés publiquement. Cette "Période d'embargo" peut être prolongée si des problèmes sont découverts pendant les tests.

Vous recevrez les parties des annonces pré-publication qui sont pertinentes pour le problème spécifique que vous avez signalé. Cet e-mail contera la date de publication cible. Des mises à jour supplémentaires seront envoyées si la date de publication cible change.

Tests pré-publication

L'équipe de sécurité Perl ne produit pas directement de versions officielles de Perl. L'équipe publie des correctifs de sécurité en plaçant des commits dans le dépôt git public de Perl et en envoyant des annonces.

De nombreux utilisateurs et redistributeurs préfèrent utiliser les versions officielles de Perl plutôt que d'appliquer des correctifs à une version antérieure. L'équipe de sécurité travaille avec les responsables de publication de Perl pour rendre cela possible.

De nouvelles versions officielles de Perl sont généralement produites et testées sur des systèmes privés pendant la "Période d'embargo" de pré-publication.

Publication des correctifs et annonces

La "Période d'embargo" se termine lorsque les correctifs de sécurité sont validés dans le dépôt git public de Perl. Des annonces seront envoyées aux listes de diffusion perl5-porters https://lists.perl.org/list/perl5-porters.html et oss-security https://oss-security.openwall.org/wiki/mailing-lists/oss-security.

Si les versions officielles de Perl sont prêtes, elles seront publiées à ce moment-là et annoncées sur la liste de diffusion perl5-porters https://lists.perl.org/list/perl5-porters.html.

L'équipe de sécurité enverra une notification de suivi à toutes les personnes qui ont participé à la "Période d'embargo" de pré-publication une fois le processus de publication terminé. Les rapporteurs de vulnérabilités et les redistributeurs de Perl ne doivent pas publier leurs propres annonces ou correctifs tant que le processus de publication de l'équipe de sécurité de Perl n'est pas terminé.

perlsecpolicy - Perl security policy

NAME

perlsecpolicy - Perl security policy

DESCRIPTION

This document details the security policy of the Perl programming language.

The Perl security team is responsible for addressing security vulnerabilities reported in Perl. This policy outlines the procedures and guidelines followed by the team when handling such reports.

Reporting Security Issues in Perl

To report a security issue in Perl, please send an email to perl-security@perl.org. This address is monitored by the Perl security team.

When reporting an issue, please include as much detail as possible, including:

  • A clear and concise description of the vulnerability.
  • Steps to reproduce the vulnerability, including any necessary code or configuration.
  • The potential impact of the vulnerability.
  • The affected Perl version(s).
  • Any relevant environment information (operating system, etc.).

The security team will acknowledge receipt of your report within 72 hours. We will then investigate the issue and keep you informed of our progress.

What Are Security Issues

A security issue is defined as a flaw in Perl that can be exploited by a malicious actor to compromise the security of a system. This includes, but is not limited to, the following types of vulnerabilities:

  • Buffer overflows: Vulnerabilities that allow writing beyond the allocated buffer, potentially leading to code execution.
  • Integer overflows: Vulnerabilities related to arithmetic operations on integers, which can lead to unexpected behavior or security flaws.
  • Format string bugs: Vulnerabilities arising from the improper handling of format strings in functions like `printf`.
  • Denial of service (DoS): Vulnerabilities that allow an attacker to disrupt the normal operation of a Perl program or the Perl interpreter itself, rendering it unavailable to legitimate users.
  • Information disclosure: Vulnerabilities that allow an attacker to access sensitive information that should not be publicly accessible.
  • Insecure defaults or behavior: Default configurations or operational characteristics that pose a security risk.
  • Vulnerabilities in core modules: Security flaws within modules that are shipped as part of the Perl core distribution.

Issues that are purely theoretical, rely on outdated or unsupported configurations, or have negligible impact may not be treated as security issues.

How We Deal With Security Issues

The Perl security team follows a coordinated disclosure process to ensure that vulnerabilities are fixed and distributed to users in a timely and secure manner. The goal is to minimize the window of opportunity for attackers.

Disclosure policy

Perl adheres to a policy of coordinated vulnerability disclosure. When a security issue is reported, the team works to develop and release a fix before publicly disclosing details about the vulnerability. This allows users to update their systems before the vulnerability becomes widely known and potentially exploited.

Communication channels

Security reports should be sent to perl-security@perl.org. Communications regarding the status of a vulnerability, fixes, and announcements will be made through official channels, including the Perl website and relevant mailing lists.

Remediation workflow

1. Report Received: A security issue is reported to perl-security@perl.org.

2. Acknowledgement and Triage: The security team acknowledges the report and begins an initial assessment to confirm the validity and severity of the issue. This may involve reproducing the vulnerability.

3. Mitigation and Fix Development: If the issue is confirmed, the team works on developing a fix. In some cases, temporary mitigations may be provided if a full fix is not immediately available.

4. Coordination and Testing: The fix is tested internally. Depending on the nature of the vulnerability, trusted third parties (such as distributors) may be involved in testing under an embargo.

5. Public Disclosure and Release: Once a fix is ready and has been tested, details of the vulnerability and the fix are made publicly available. This typically involves releasing a new version of Perl or providing patch instructions.

6. Post-Release Follow-up: The security team monitors for any further issues or exploitation attempts related to the disclosed vulnerability.

Public disclosure considerations

The decision on when and how to disclose a security vulnerability publicly involves careful consideration. The primary goal is to protect users. In some cases, premature disclosure of an unresolved vulnerability could increase the risk of exploitation. Therefore, the security team may choose to withhold public disclosure until a fix is available or a coordinated disclosure plan is in place. In other cases, calling attention to an unresolved security issue will make it more likely to be misused.

Zero-day security issues

If an unresolved critical security issue in Perl is being actively abused to attack systems the security team will send out announcements as rapidly as possible with any mitigations the team has available.

Perl's public defect tracker will be used to handle the issue so that additional information, fixes, and CVE IDs are visible to affected users as rapidly as possible.

Other leaks of security issue information

Depending on the prominence of the information revealed about a security issue and the issue's risk of becoming a zero-day attack, the security team may skip all or part of its normal remediation workflow.

If the security team learns of a significant security issue after it has been identified and resolved in Perl's public issue tracker, the team will request a CVE ID and send an announcement to inform users.

Vulnerability credit and bounties

The Perl project appreciates the effort security researchers invest in making Perl safe and secure.

Since much of this work is hidden from the public, crediting researchers publicly is an important part of the vulnerability remediation process.

Credits in vulnerability announcements

When security issues are fixed we will attempt to credit the specific researcher(s) that discovered the flaw in our announcements.

Credits are announced using the researcher's preferred full name.

If the researcher's contributions were funded by a specific company or part of an organized vulnerability research project, we will include a short name for this group at the researcher's request.

Perl's announcements are written in the English language using the 7bit ASCII character set to be reproducible in a variety of formats. We do not include hyperlinks, domain names or marketing material with these acknowledgments.

In the event that proper credit for vulnerability discovery cannot be established or there is a disagreement between the Perl security team and the researcher about how the credit should be given, it will be omitted from announcements.

Bounties for Perl vulnerabilities

The Perl project is a non-profit volunteer effort. We do not provide any monetary rewards for reporting security issues in Perl.

Embargo Period

In the context of Perl's coordinated vulnerability disclosure process, an "embargo" refers to the period of time during which information about a reported vulnerability is kept confidential. This embargo begins when a security issue is reported to the Perl security team and lasts until a fix has been developed and a fix is provided in a public location.

The purpose of the embargo is to allow the security team to work on a fix and prepare a coordinated release without the risk of the vulnerability being exploited or disclosed prematurely. This helps ensure that users of Perl and its modules are protected from potential attacks while the security issue is being addressed.

Embargo lengths can vary depending on the complexity of the issue and the time required to develop a fix. The security team will communicate the expected duration of the embargo to the reporter and any other parties involved in the process.

As a goal, the security team aims to keep the total embargo period to less than 60 days. This may be extended due to the following factors:

  • The complexity of the issue
  • The time required to develop a fix
  • The need for additional testing or validation
  • The availability of resources to address the issue
  • Public holidays which might affect the ability of end users to apply the fix.

During this period:

  • Details of the vulnerability are shared only with a restricted group of trusted contributors (such as core maintainers, toolchain maintainers, and packagers), solely for the purpose of preparing and testing a fix.
  • Reporters are asked not to disclose the issue publicly or share details with third parties until the embargo is lifted.
  • The duration of the embargo may vary depending on the severity and complexity of the issue, but typically lasts until the relevant security patch is released and announced.
  • Breaking the embargo — by prematurely disclosing details — undermines the coordinated disclosure process and can hinder the coordinated effort to protect users effectively.

The Perl security team strives to resolve vulnerabilities promptly and encourages all parties to respect the embargo period to help protect users and downstream distributions.

Example Release Process

This section provides an example of how a security issue reported by a third party might be handled by the Perl security team, from the initial report to the final release.

Step 1: Reporting the Vulnerability

A security researcher discovers a vulnerability in the Perl interpreter that allows an attacker to cause a denial of service under specific conditions. The researcher emails the details of the issue to perl-security@perl.org <mailto:perl-security@perl.org>, including a proof-of-concept script and a description of the impact.

Step 2: Initial Response

Within 72 hours, the security team acknowledges receipt of the report and confirms that the issue is under investigation. The researcher is informed of the expected timeline for triage.

Step 3: Initial Triage

The security team reproduces the issue using the provided proof-of-concept and determines that it meets the criteria for handling as a security issue. One or more CVEs are reserved in coordination with the CPAN Security Group CNA https://security.metacpan.org/2025/02/25/cpansec-is-cna-for-perl-and-cpan.html. The team notifies the researcher referencing the CVE IDs.

Step 4: Development of a Fix

The security team analyzes the affected code and develops a patch to address the vulnerability. The patch is tested against various scenarios to ensure it resolves the issue without introducing regressions. The researcher is invited to test the patch privately and provide feedback.

Step 5: Pre-Release Notification

The security team prepares a pre-release notification, including details of the vulnerability, the affected Perl versions, and the patch. This notification is sent to major redistributors of Perl under embargo, giving them time to prepare their own updates.

Step 6: Pre-Release Testing

During the remaining embargo period, pre-notified redistributors prepare packages for release and test the patch to ensure compatibility with their systems.

Step 7: Public Release

On the scheduled release date, the patch is committed to Perl's public git repository. An official announcement is sent to the perl5-porters https://lists.perl.org/list/perl5-porters.html and oss-security https://oss-security.openwall.org/wiki/mailing-lists/oss-security mailing lists. If applicable, a new Perl release containing the fix is published.

The security team will notify CPAN Security Group CNA to publish the CVE.

Step 8: Vendor and Third-Party Updates

Vendors and third-party maintainers incorporate the patch or updated Perl release into their distributions. The security team follows up with all parties involved to ensure the issue is resolved and users are protected.
