PEG(1) Manuel des commandes générales PEG(1)

NOM

peg, leg - générateurs d'analyseurs syntaxiques

SYNTAXE

peg [-hvV -osortie] [fichier ...]

leg [-hvV -osortie] [fichier ...]

DESCRIPTION

peg et leg sont des outils pour générer des analyseurs syntaxiques récursifs descendants : des programmes qui effectuent une correspondance de motifs sur du texte. Ils traitent une Grammaire d'Expressions d'Analyse (PEG) [Ford 2004] pour produire un programme qui reconnaît les phrases légales de cette grammaire. peg traite les PEGs écrites dans la syntaxe originale décrite par Ford ; leg traite les PEGs écrites dans une syntaxe et des conventions légèrement différentes qui sont destinées à en faire un remplaçant attrayant pour les analyseurs construits avec lex(1) et yacc(1). Contrairement à lex et yacc, peg et leg supportent le retour arrière illimité, fournissent le choix ordonné comme moyen de désambiguïsation, et peuvent combiner la lecture (analyse lexicale) et l'analyse syntaxique en une seule activité.

peg lit les fichiers spécifiés, ou l'entrée standard si aucun fichier n'est donné, pour une grammaire décrivant l'analyseur à générer. peg génère ensuite un fichier source C qui définit une fonction yyparse(). Ce fichier source C peut être inclus dans, ou compilé puis lié avec, un programme client. Chaque fois que le programme client appelle yyparse(), l'analyseur consomme du texte d'entrée selon les règles d'analyse, en commençant par la première règle de la grammaire. yyparse() renvoie une valeur non nulle si l'entrée a pu être analysée conformément à la grammaire ; il renvoie zéro si l'entrée n'a pas pu être analysée.

Le préfixe 'yy' ou 'YY' est ajouté à tous les symboles visiblement externement dans l'analyseur généré. Ceci est destiné à réduire le risque de pollution de l'espace de noms dans les programmes clients. (Le choix de 'yy' est historique ; voir lex(1) et yacc(1), par exemple.)

OPTIONS

peg et leg fournissent les options suivantes :

-h
affiche un résumé des options disponibles puis quitte.
-osortie
écrit l'analyseur généré dans le fichier sortie au lieu de la sortie standard.
-P
supprime les directives #line dans la sortie.
-v
écrit des informations détaillées sur la sortie d'erreur pendant le travail.
-V
écrit les informations de version sur la sortie d'erreur puis quitte.

UN EXEMPLE SIMPLE

L'entrée peg suivante spécifie une grammaire avec une seule règle (appelée 'start') qui est satisfaite lorsque l'entrée contient la chaîne "username".

    start <- "username"

(Les guillemets ne font pas partie du texte correspondant ; ils servent à indiquer une chaîne littérale à faire correspondre.) En d'autres termes, yyparse() dans le fichier source C généré renverra une valeur non nulle uniquement si les huit caractères suivants lus de l'entrée épellent le mot "username". Si l'entrée contient autre chose, yyparse() renverra zéro et aucun texte n'aura été consommé. (Les appels ultérieurs à yyparse() renverront également zéro, car l'analyseur est effectivement bloqué à la recherche de la chaîne "username".) Pour assurer la progression, nous pouvons ajouter une clause alternative à la règle 'start' qui correspondra à n'importe quel caractère unique si "username" n'est pas trouvé.

    start <- "username"
           / .

yyparse() renvoie maintenant toujours une valeur non nulle (sauf à la toute fin de l'entrée). Pour faire quelque chose d'utile, nous pouvons ajouter des actions aux règles. Ces actions sont exécutées après qu'une correspondance complète est trouvée (en commençant par la première règle) et sont choisies en fonction du 'chemin' emprunté à travers la grammaire pour faire correspondre l'entrée. (Les linguistes appelleraient ce chemin un 'marqueur de phrase'.)

    start <- "username"    { printf("%s\n", getlogin()); }
           / < . >         { putchar(yytext[0]); }

La première ligne demande à l'analyseur d'imprimer le nom de connexion de l'utilisateur chaque fois qu'il voit "username" dans l'entrée. Si cette correspondance échoue, la seconde ligne demande à l'analyseur d'afficher le caractère suivant dans l'entrée sur la sortie standard. Notre analyseur effectue maintenant un travail utile : il copiera l'entrée vers la sortie, remplaçant toutes les occurrences de "username" par le nom de compte de l'utilisateur.

Notez les chevrons ('<' et '>') qui ont été ajoutés à la deuxième alternative. Ceux-ci n'ont aucun effet sur la signification de la règle, mais servent à délimiter le texte rendu disponible pour l'action suivante dans la variable yytext.

Si la grammaire ci-dessus est placée dans le fichier username.peg, l'exécution de la commande

    peg -o username.c username.peg
sauvegardera l'analyseur correspondant dans le fichier username.c. Pour créer un programme complet, cet analyseur pourrait être inclus par un programme C comme suit. 
    #include <stdio.h>      /* printf(), putchar() */
    #include <unistd.h>     /* getlogin() */
    #include "username.c"   /* yyparse() */
    int main()
    {
      while (yyparse())     /* répéter jusqu'à la fin du fichier */
        ;
      return 0;
    }

GRAMMAIRES PEG

Une grammaire se compose d'un ensemble de règles nommées.

    nom <- motif

Le motif contient un ou plusieurs des éléments suivants.

nom
L'élément représente le motif entier dans la règle avec le nom donné.
"caractères"
Un caractère ou une chaîne de caractères entourée de guillemets doubles est mise en correspondance littéralement. Les séquences d'échappement ANSI C sont reconnues dans les caractères.
'caractères'
Un caractère ou une chaîne de caractères entourée de guillemets simples est mise en correspondance littéralement, comme ci-dessus.
[caractères]
Un ensemble de caractères entouré de crochets correspond à n'importe quel caractère unique de l'ensemble, avec des caractères d'échappement reconnus comme ci-dessus. Si l'ensemble commence par un accent circonflexe (^) alors l'ensemble est nié (l'élément correspond à n'importe quel caractère non présent dans l'ensemble). Toute paire de caractères séparée par un tiret (-) représente la plage de caractères allant du premier au second, inclus. Un seul caractère alphabétique ou un tiret bas est mis en correspondance par l'ensemble suivant. 
    [a-zA-Z_]
De même, ce qui suit correspond à n'importe quel caractère non-chiffre unique. 
    [^0-9]
.
Un point correspond à n'importe quel caractère. Notez que la seule fois où cela échoue, c'est à la fin du fichier, où il n'y a pas de caractère à faire correspondre.
( motif )
Les parenthèses sont utilisées pour le regroupement (modifiant la priorité des opérateurs décrits ci-dessous).
{ action }
Les accolades entourent les actions. L'action est du code source C arbitraire à exécuter à la fin de la correspondance. Toutes les accolades dans l'action doivent être correctement imbriquées. Tout texte d'entrée qui a été mis en correspondance avant l'action et délimité par des chevrons (voir ci-dessous) est rendu disponible dans l'action sous forme de contenu du tableau de caractères yytext. La longueur de (nombre de caractères dans) yytext est disponible dans la variable yyleng. (Ces noms de variables sont historiques ; voir lex(1).)
<
Un chevron ouvrant correspond toujours (ne consommant aucune entrée) et fait en sorte que l'analyseur commence à accumuler le texte correspondant. Ce texte sera rendu disponible pour les actions dans la variable yytext.
>
Un chevron fermant correspond toujours (ne consommant aucune entrée) et fait en sorte que l'analyseur arrête d'accumuler du texte pour yytext.

Les éléments ci-dessus peuvent être rendus optionnels et/ou répétables avec les suffixes suivants :

élément ?
L'élément est optionnel. S'il est présent dans l'entrée, il est consommé et la correspondance réussit. S'il n'est pas présent dans l'entrée, aucun texte n'est consommé et la correspondance réussit de toute façon.
élément +
L'élément est répétable. S'il est présent dans l'entrée, une ou plusieurs occurrences de l'élément sont consommées et la correspondance réussit. Si aucune occurrence de l'élément n'est présente dans l'entrée, la correspondance échoue.
élément *

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

dd>L'élément est facultatif et répétable. S'il est présent dans l'entrée, une ou plusieurs occurrences de élément sont consommées et la correspondance réussit. Si aucune occurrence de élément n'est présente dans l'entrée, la correspondance réussit quand même.

Les éléments et suffixes ci-dessus peuvent être convertis en prédicats (qui correspondent à un texte d'entrée arbitraire et réussissent ou échouent ensuite sans consommer cette entrée) avec les préfixes suivants :

& element
Le prédicat réussit uniquement si element peut correspondre. Le texte d'entrée parcouru lors de la mise en correspondance de element n'est pas consommé de l'entrée et reste disponible pour les correspondances ultérieures.
! element
Le prédicat réussit uniquement si element ne peut pas correspondre. Le texte d'entrée parcouru lors de la mise en correspondance de element n'est pas consommé de l'entrée et reste disponible pour les correspondances ultérieures. Un idiome courant est 
    !.
qui correspond à la fin du fichier, après que le dernier caractère de l'entrée a déjà été consommé.

Une forme spéciale du prédicat '&' est fournie :

&{ expression }
Dans ce prédicat, la simple expression C (pas une instruction) est évaluée immédiatement lorsque l'analyseur atteint le prédicat. Si l' expression renvoie une valeur non nulle (vrai), la 'correspondance' réussit et l'analyseur continue avec l'élément suivant dans le modèle. Si l' expression renvoie zéro (faux), la 'correspondance' échoue et l'analyseur revient en arrière pour rechercher une analyse alternative de l'entrée.

Plusieurs éléments (avec ou sans préfixes et suffixes) peuvent être combinés en une séquence en les écrivant les uns après les autres. La séquence entière ne correspond que si chaque élément individuel qu'elle contient correspond, de gauche à droite.

Les séquences peuvent être séparées en alternatives disjointes par l'opérateur d'alternance '/'.

séquence-1 / séquence-2 / ... / séquence-N
Chaque séquence est essayée tour à tour jusqu'à ce que l'une d'elles corresponde, moment auquel la correspondance pour le modèle global réussit. Si aucune des séquences ne correspond, la correspondance du modèle global échoue.

Enfin, le signe dièse (#) introduit un commentaire (ignoré) qui se poursuit jusqu'à la fin de la ligne.

Pour résumer ce qui précède, l'analyseur essaie de faire correspondre le texte d'entrée à un modèle contenant des littéraux, des noms (représentant d'autres règles) et divers opérateurs (écrits sous forme de préfixes, de suffixes, de juxtaposition pour la séquençage et d'opérateur d'alternance infixe) qui modifient la façon dont les éléments du modèle sont mis en correspondance. Les correspondances sont établies de gauche à droite, en 'descendant' dans les sous-règles nommées au fur et à mesure qu'elles sont rencontrées. Si le processus de correspondance échoue, l'analyseur 'revient en arrière' ('rembobinant' l'entrée de manière appropriée dans le processus) pour trouver le chemin 'alternatif' le plus proche à travers la grammaire. En d'autres termes, l'analyseur effectue une recherche en profondeur d'abord, de gauche à droite, du premier chemin de correspondance réussie à travers les règles. S'il est trouvé, les actions le long du chemin réussi sont exécutées (dans l'ordre où elles ont été rencontrées).

Notez que les prédicats sont évalués immédiatement pendant la recherche d'une correspondance réussie, car ils contribuent au succès ou à l'échec de la recherche. Les actions, cependant, ne sont évaluées qu'après qu'une correspondance réussie a été trouvée.

GRAMMAIRE PEG POUR LES GRAMMAIRES PEG

La grammaire des grammaires peg est illustrée ci-dessous. Cela illustrera et formalisera la description ci-dessus.

    Grammaire         <- Espacement Définition+ FinDeFichier
    Définition      <- Identificateur FLECHEEgauche Expression
    Expression      <- Séquence ( BARRE Séquence )*
    Séquence        <- Préfixe*
    Préfixe          <- ET Action
                     / ( ET | NON )? Suffixe
    Suffixe          <- Primaire ( POINTINTERROGATION / ETOILE / PLUS )?
    Primaire        <- Identificateur !FLECHEEgauche
                     / OUVERT Expression FERMÉ
                     / Littéral
                     / Classe
                     / POINT
                     / Action
                     / DÉBUT
                     / FIN
    Identificateur      <- < DébutIdent SuiteIdent* > Espacement
    DébutIdent       <- [a-zA-Z_]
    SuiteIdent       <- DébutIdent / [0-9]
    Littéral         <- ['] < ( !['] Caractère  )* > ['] Espacement
                     / ["] < ( !["] Caractère  )* > ["] Espacement
    Classe           <- '[' < ( !']' Plage )* > ']' Espacement
    Plage           <- Caractère '-' Caractère / Caractère
    Caractère        <- '\\' [abefnrtv'"\[\]\\]
                     / '\\' [0-3][0-7][0-7]
                     / '\\' [0-7][0-7]?
                     / '\\' '-'
                     / !'\\' .
    FLECHEEgauche       <- '<-' Espacement
    BARRE           <- '/' Espacement
    ET              <- '&' Espacement
    NON             <- '!' Espacement
    POINTINTERROGATION       <- '?' Espacement
    ETOILE           <- '*' Espacement
    PLUS            <- '+' Espacement
    OUVERT            <- '(' Espacement
    FERMÉ           <- ')' Espacement
    POINT             <- '.' Espacement
    Espacement         <- ( Espace / Commentaire )*
    Commentaire         <- '#' ( !FinDeLigne . )* FinDeLigne
    Espace           <- ' ' / '\t' / FinDeLigne
    FinDeLigne       <- '\r\n' / '\n' / '\r'
    FinDeFichier       <- !.
    Action          <- '{' < [^}]* > '}' Espacement
    DÉBUT           <- '<' Espacement
    FIN             <- '>' Espacement

GRAMMAIRES LEG

leg est une variante de peg qui ajoute certaines fonctionnalités de lex(1) et yacc(1). Il diffère de peg des manières suivantes.

%{ texte... %}
Une section de déclaration peut apparaître partout où une définition de règle est attendue. Le texte entre les délimiteurs '%{' et '%}' est copié tel quel dans le code d'analyseur C généré avant le code qui implémente l'analyseur lui-même.
nom = modèle
L'opérateur 'affectation' remplace l'opérateur flèche gauche '<-'.
nom-règle
Les traits d'union peuvent apparaître comme lettres dans les noms de règles. Chaque trait d'union est converti en un tiret bas dans le code source C généré. Un seul trait d'union '-' est un nom de règle légal. 
    -       = [ \t\n\r]*
    nombre  = [0-9]+                 -
    nom     = [a-zA-Z_][a-zA_Z_0-9]* -
    parenthèse-g        = '('                    -
    parenthèse-d        = ')'                    -
Cet exemple montre comment les espaces blancs ignorés peuvent être évidents à la lecture de la grammaire et pourtant discrets lorsqu'ils sont placés abondamment à la fin de chaque règle associée à un élément lexical.
seq-1 | seq-2
L'opérateur d'alternance est une barre verticale '|' au lieu d'une barre oblique '/'. La règle peg 
    nom <- séquence-1
          / séquence-2
          / séquence-3
est donc écrite 
    nom = séquence-1
         | séquence-2
         | séquence-3
         ;
en leg (le point-virgule final étant facultatif, comme décrit ci-après).
exp ~ { action }
Un opérateur postfixé ~{ action } peut être placé après n'importe quelle expression et se comportera comme une action normale (code C arbitraire) sauf qu'il est invoqué uniquement lorsque exp échoue. Il se lie moins fortement que tout autre opérateur, sauf l'alternance et le séquençage, et est destiné à faciliter l'écriture du code de gestion des erreurs et de récupération. Notez que yytext et yyleng ne sont pas disponibles dans ces actions, mais le pointeur yy est disponible pour donner au code l'accès à tous les membres définis par l'utilisateur de l'état de l'analyseur (voir "PERSONNALISATION DE L'ANALYSEUR" ci-dessous). Notez également que exp est toujours une seule expression ; pour invoquer une action d'erreur pour tout échec au sein d'une séquence, des parenthèses doivent être utilisées pour regrouper la séquence en une seule expression. 
    règle = e1 e2 e3 ~{ erreur("e[12] ok; e3 a échoué"); }
         | ...
    règle = (e1 e2 e3) ~{ erreur("l'un de e[123] a échoué"); }
         | ...
modèle ;
Un point-virgule ponctuant peut facultativement terminer un modèle.
%% texte...
Un double pourcent '%%' termine la section des règles (et des déclarations) de la grammaire. Tout texte suivant '%%' est copié tel quel dans le code d'analyseur C généré après le code d'implémentation de l'analyseur.
$$ = valeur
Une sous-règle peut retourner une valeur sémantique à partir d'une action en l'affectant à la pseudo-variable '$$'. Toutes les valeurs sémantiques doivent avoir le même type (qui est par défaut 'int'). Ce type peut être modifié en définissant YYSTYPE dans une section de déclaration.
identificateur:nom
La valeur sémantique retournée (en l'affectant à '$$') par la sous-règle nom est associée à l'identificateur et peut être référencée dans les actions ultérieures.

L'exemple de calculatrice de bureau illustre l'utilisation de '$$' et ':'.

EXEMPLE LEG: UNE CALCULATRICE DE BUREAU

Les extensions de leg décrites ci-dessus permettent de conserver des analyseurs et des évaluateurs utiles (y compris des déclarations, des règles de grammaire et des fonctions C de support comme 'main') dans un seul fichier source. Pour l'illustrer, nous présentons une calculatrice de bureau simple prenant en charge les quatre opérateurs arithmétiques courants et les variables nommées. Les résultats intermédiaires de l'évaluation arithmétique seront accumulés sur une pile implicite en les retournant comme valeurs sémantiques des sous-règles.

    %{
    #include <stdio.h>     /* printf() */
    #include <stdlib.h>    /* atoi() */
    int vars[26];
    %}
    Stmt    = - e:Expr EOL                  { printf("%d\n", e); }
            | ( !EOL . )* EOL               { printf("error\n"); }
    Expr    = i:ID ASSIGN s:Sum
{ $$ = vars[i] = s; } | s:Som { $$ = s; } Som = l:Produit ( PLUS r:Produit { l += r; } | MOINS r:Produit { l -= r; } )* { $$ = l; } Produit = l:Valeur ( FOIS r:Valeur { l *= r; } | DIVISE r:Valeur { l /= r; } )* { $$ = l; } Valeur = i:NOMBRE { $$ = atoi(yytext); } | i:ID !ASSIGN { $$ = vars[i]; } | OUVERT i:Expr FERMANT { $$ = i; } NOMBRE = < [0-9]+ > - { $$ = atoi(yytext); } ID = < [a-z] > - { $$ = yytext[0] - 'a'; } ASSIGN = '=' - PLUS = '+' - MINUS = '-' - TIMES = '*' - DIVIDE = '/' - OPEN = '(' - CLOSE = ')' - - = [ \t]* EOL = '\n' | '\r\n' | '\r' | ';' %% int main() { while (yyparse()) ; return 0; }

GRAMMAIRE LEG POUR GRAMMAIRES LEG

La grammaire pour les grammaires leg est présentée ci-dessous. Cela illustrera et formalisera la description ci-dessus.

    grammar =       -
                    ( declaration | definition )+
                    trailer? end-of-file
    declaration =   '%{' < ( !'%}' . )* > RPERCENT
    trailer =       '%%' < .* >
    definition =    identifier EQUAL expression SEMICOLON?
    expression =    sequence ( BAR sequence )*
    sequence =      error+
    error =         prefix ( TILDE action )?
    prefix =        AND action
    |               ( AND | NOT )? suffix
    suffix =        primary ( QUERY | STAR | PLUS )?
    primary =       identifier COLON identifier !EQUAL
    |               identifier !EQUAL
    |               OPEN expression CLOSE
    |               literal
    |               class
    |               DOT
    |               action
    |               BEGIN
    |               END
    identifier =    < [-a-zA-Z_][-a-zA-Z_0-9]* > -
    literal =       ['] < ( !['] char )* > ['] -
    |               ["] < ( !["] char )* > ["] -
    class =         '[' < ( !']' range )* > ']' -
    range =         char '-' char | char
    char =          '\\' [abefnrtv'"\[\]\\]
    |               '\\' [0-3][0-7][0-7]
    |               '\\' [0-7][0-7]?
    |               !'\\' .
    action =        '{' < braces* > '}' -
    braces =        '{' braces* '}'
    |               !'}' .
    EQUAL =         '=' -
    COLON =         ':' -
    SEMICOLON =     ';' -
    BAR =           '|' -
    AND =           '&' -
    NOT =           '!' -
    QUERY =         '?' -
    STAR =          '*' -
    PLUS =          '+' -
    OPEN =          '(' -
    CLOSE =         ')' -
    DOT =           '.' -
    BEGIN =         '<' -
    END =           '>' -
    TILDE =         '~' -
    RPERCENT =      '%}' -
    - =             ( space | comment )*
    space =         ' ' | '\t' | end-of-line
    comment =       '#' ( !end-of-line . )* end-of-line
    end-of-line =   '\r\n' | '\n' | '\r'
    end-of-file =   !.

PERSONNALISATION DU PARSEUR

Les symboles suivants peuvent être redéfinis dans les sections de déclaration pour modifier le code du parseur généré.

YYSTYPE
Le type de la valeur sémantique. La pseudo-variable '$$' et les identifiants 'liés' aux résultats de règles avec l'opérateur deux-points ':' doivent tous être considérés comme étant déclarés de ce type. La valeur par défaut est 'int'.
YYPARSE
Le nom du point d'entrée principal du parseur. La valeur par défaut est 'yyparse'.
YYPARSEFROM
Le nom d'un point d'entrée alternatif du parseur. Cette fonction attend un argument : la fonction correspondant à la règle à partir de laquelle la recherche d'une correspondance doit commencer. La valeur par défaut est 'yyparsefrom'. Notez que yyparse() est défini comme suit : 
    int yyparse() { return yyparsefrom(yy_foo); }
où 'foo' est le nom de la première règle de la grammaire.
YY_INPUT(buf, result, max_size)
Cette macro est appelée par le parseur pour obtenir plus de texte d'entrée. buf pointe vers une zone mémoire pouvant contenir au maximum max_size caractères. La macro doit copier le texte d'entrée dans buf, puis attribuer la variable entière result pour indiquer le nombre de caractères copiés. S'il n'y a plus d'entrée disponible, la macro doit attribuer 0 à result. Par défaut, la macro YY_INPUT est définie comme suit : 
    #define YY_INPUT(buf, result, max_size)        \
    {                                              \
      int yyc= getchar();                          \
      result= (EOF == yyc) ? 0 : (*(buf)= yyc, 1); \
    }
Notez que si YY_CTX_LOCAL est défini (voir ci-dessous), un premier argument supplémentaire, contenant le contexte du parseur, est passé à YY_INPUT.
YY_DEBUG
Si ce symbole est défini, du code supplémentaire sera inclus dans le parseur, imprimant de grandes quantités d'informations archaïques sur la sortie d'erreur standard pendant l'exécution du parseur.
YY_BEGIN
Cette macro est appelée pour marquer le début du texte d'entrée qui sera disponible dans les actions sous le nom 'yytext'. Cela correspond aux occurrences de '<' dans la grammaire. Elles sont converties en prédicats qui sont censés réussir. La définition par défaut 
    #define YY_BEGIN (yybegin= yypos, 1)
sauvegarde donc la position d'entrée actuelle et renvoie 1 ('vrai') comme résultat du prédicat.
YY_END
Cette macro correspond à '>' dans la grammaire. Encore une fois, c'est un prédicat, donc la définition par défaut sauvegarde la position d'entrée avant de 'réussir'. 
    #define YY_END (yyend= yypos, 1)
YY_PARSE(T)
Cette macro déclare les points d'entrée du parseur (yyparse et yyparsefrom) comme étant de type T. La définition par défaut 
    #define YY_PARSE(T) T
laisse yyparse() et yyparsefrom() avec une visibilité globale. S'ils ne doivent pas être visibles extérieurement dans d'autres fichiers source, cette macro peut être redéfinie pour les déclarer 'static'. 
    #define YY_PARSE(T) static T
YY_CTX_LOCAL
Si ce symbole est défini lors de la compilation d'un parseur généré, l'état global du parseur sera conservé dans une structure de type 'yycontext' qui peut être déclarée comme une variable locale. Cela permet à plusieurs instances de parseurs de coexister et d'être thread-safe. La fonction de parsing yyparse() sera déclarée comme attendant un premier argument de type 'yycontext *', une instance de la structure contenant l'état global du parseur. Cette instance doit être allouée et initialisée à zéro par le client. Un exemple trivial mais complet est le suivant : 
    #include <stdio.h>
    #define YY_CTX_LOCAL
    #include "the-generated-parser.peg.c"
    int main()
    {
      yycontext ctx;
      memset(&ctx, 0, sizeof(yycontext));
      while (yyparse(&ctx));
      return 0;
    }
Notez que si ce symbole est indéfini, le parseur compilé allouera statiquement son état global et ne sera ni réentrant ni thread-safe. Notez également que la structure de contexte du parseur yycontext est initialisée automatiquement lors du premier appel à yyparse() ; cette structure **doit** donc être correctement initialisée à zéro avant le premier appel à yyparse().
YY_CTX_MEMBERS
Si YY_CTX_LOCAL est défini (voir ci-dessus), la macro YY_CTX_MEMBERS peut être définie pour s'étendre à toute déclaration de membre supplémentaire que le client souhaite inclure dans la déclaration du type de structure 'yycontext'. Ces membres supplémentaires sont par ailleurs ignorés par le parseur généré. L'instance de 'yycontext' associée au parseur actuellement actif est disponible dans les actions sous le nom de variable pointeur yy.
YY_BUFFER_SIZE
La taille initiale du tampon de texte, en octets. La valeur par défaut est 1024 et la taille du tampon est doublée chaque fois que nécessaire pour répondre à la demande pendant l'analyse. Une application qui analyse typiquement des chaînes beaucoup plus longues peut augmenter cette valeur pour éviter des réallocations de tampon inutiles.
YY_STACK_SIZE
La taille initiale des piles de variables et d'actions. La valeur par défaut est 128, qui est doublée chaque fois que nécessaire pour répondre à la demande pendant l'analyse. Les applications qui ont des piles d'appels profondes avec de nombreuses variables locales, ou qui effectuent de nombreuses actions après une seule correspondance réussie, pourraient augmenter cette valeur pour éviter des réallocations de tampon inutiles.
YY_MALLOC(YY, SIZE)
L'allocateur de mémoire pour tout le stockage lié au parseur. Les paramètres sont la structure yycontext actuelle et le nombre d'octets à allouer. La définition par défaut est : malloc(SIZE)
YY_REALLOC(YY, PTR, SIZE)
Le réallocateur de mémoire pour le stockage qui grandit dynamiquement (comme les tampons de texte et les piles de variables). Les paramètres sont la structure yycontext actuelle, le stockage précédemment alloué et le nombre d'octets auxquels ce stockage doit être agrandi. La définition par défaut est : realloc(PTR, SIZE)
YY_FREE(YY, PTR)
Le désallocateur de mémoire. Les paramètres sont la structure yycontext actuelle et le stockage à désallouer. La définition par défaut est : free(PTR)
YYRELEASE
Le nom de la fonction qui libère toutes les ressources détenues par une structure yycontext. La valeur par défaut est 'yyrelease'.

char *yybuf

Nom

leg, peg — analyseur syntaxique basé sur une grammaire d'expression d'analyse

SYNOPSIS

leg [-bcdfgKklmNnqsvwz] [-Cfile] [-Dfile] [-efile] [-Idir] [-Ofile] [-ttemplate] [-Vversion] [-Wwarn] [-xfile] [-?] [infile [outfile]]

peg [-bcdfgKklmNnqsvwz] [-Cfile] [-Dfile] [-efile] [-Idir] [-Ofile] [-ttemplate] [-Vversion] [-Wwarn] [-xfile] [-?] [infile [outfile]]

DESCRIPTION

leg et peg sont des générateurs d'analyseurs syntaxiques basés sur les grammaires d'expressions d'analyse (PEG). Les PEG sont une classe de grammaires formelles introduites par Bryan Ford en 2004, qui permettent une analyse syntaxique efficace sans retour arrière. Les PEG sont capables d'exprimer toutes les grammaires qui peuvent être exprimées par des grammaires contextuelles, mais d'une manière qui correspond plus étroitement aux constructions naturelles du langage.

leg est un générateur d'analyseurs syntaxiques basé sur une grammaire d'expression d'analyse (PEG) dont la syntaxe est similaire à celle de lex(1). Il est utilisé pour générer des analyseurs syntaxiques C/C++ à partir de grammaires de style PEG.

peg est un générateur d'analyseurs syntaxiques basé sur une grammaire d'expression d'analyse (PEG) dont la syntaxe est basée sur le document original de Bryan Ford. Il est utilisé pour générer des analyseurs syntaxiques C/C++ à partir de grammaires de style PEG.

Les deux programmes lisent une description de grammaire à partir du fichier d'entrée (ou de l'entrée standard si aucun fichier d'entrée n'est spécifié) et produisent un fichier source C (ou C++ si l'option -c est utilisée) en sortie (ou de la sortie standard si aucun fichier de sortie n'est spécifié) qui contient le code d'un analyseur syntaxique pour cette grammaire. Le code généré inclut également un certain nombre de variables et de fonctions globales qui peuvent être utilisées par le programme appelant pour interagir avec l'analyseur syntaxique.

Syntaxe PEG

La syntaxe des grammaires d'expressions d'analyse est la suivante :

expr
Une expression d'analyse peut être l'une des suivantes :
'string'
Correspond à la chaîne littérale donnée.
.
Correspond à n'importe quel caractère.
[abc]
Correspond à n'importe lequel des caractères entre crochets.
[^abc]
Correspond à n'importe quel caractère sauf ceux entre crochets.
a b
Analyse séquentielle. Correspond à a suivi de b.
a / b
Analyse alternative. Correspond à a ou à b.
a*
Correspond à zéro ou plusieurs occurrences de a.
a+
Correspond à une ou plusieurs occurrences de a.
a?
Correspond à zéro ou une occurrence de a.
a*?
Correspond à zéro ou plusieurs occurrences de a, de manière non gourmande.
a+?
Correspond à une ou plusieurs occurrences de a, de manière non gourmande.
a??
Correspond à zéro ou une occurrence de a, de manière non gourmande.
&(a)
Assertion positive. Correspond si a correspond à la position actuelle, mais ne consomme aucune entrée.
!(a)
Assertion négative. Correspond si a ne correspond pas à la position actuelle, mais ne consomme aucune entrée.
(a)
Regroupement. Correspond à a.
{ action }
Action C. Exécute le code C donné lorsque l'expression correspond.
rule = expr
Définit une règle d'analyse syntaxique nommée rule.
rule <- expr
Définit une règle d'analyse syntaxique nommée rule avec une action C associée.

Syntaxe LEG

La syntaxe des grammaires leg est similaire à celle de lex(1). Elle utilise des expressions régulières pour définir les jetons, qui sont ensuite utilisés pour construire un analyseur syntaxique.

pattern { action }
Définit un jeton avec le motif donné et l'action C associée à exécuter lorsque le jeton est trouvé.
%option value
Définit une option pour l'analyseur syntaxique.
%%
Sépare la section des définitions de la section des règles.

Variables Globales

Les analyseurs syntaxiques générés par leg et peg exposent les variables globales suivantes pour interagir avec l'analyseur syntaxique :

char *yytext
Le texte correspondant le plus récent délimité par '<' et '>' est stocké dans cette variable.
int yyleng
Cette variable indique le nombre de caractères dans yytext.
yycontext *yy
Cette variable pointe vers l'instance de yycontext associée à l'analyseur syntaxique actuellement actif.

Les programmes qui souhaitent libérer toutes les ressources associées à un analyseur syntaxique peuvent utiliser la fonction suivante.

yyrelease(yycontext*yy)
Retourne au système tout le stockage alloué par l'analyseur syntaxique associé à yy. Le stockage sera réalloué lors du prochain appel à yyparse().

Notez que le stockage pour la structure yycontext elle-même n'est jamais alloué ou récupéré implicitement. L'application doit allouer ces structures dans le stockage automatique, ou utiliser calloc() et free() pour les gérer explicitement. L'exemple de la section suivante démontre une approche de gestion des ressources.

LEG EXEMPLE : EXTENSION DU CONTEXTE DE L'ANALYSEUR SYNTAXIQUE

La variable yy passée aux actions contient l'état de l'analyseur syntaxique plus tous les champs supplémentaires définis par YY_CTX_MEMBERS. Ces champs peuvent être utilisés pour stocker des informations spécifiques à l'application qui sont globales à un appel particulier de yyparse(). Un exemple trivial mais complet de leg suit, dans lequel la structure yycontext est étendue avec un count du nombre de caractères de nouvelle ligne rencontrés dans l'entrée jusqu'à présent (la grammaire consomme et ignore par ailleurs l'intégralité de l'entrée). L'appelant de yyparse() utilise count pour imprimer le nombre de lignes d'entrée qui ont été lues.

    %{
    #define YY_CTX_LOCAL 1
    #define YY_CTX_MEMBERS \
      int count;
    %}
    Char    = ('\n' | '\r\n' | '\r')        { yy->count++ }
            | .
    %%
    #include <stdio.h>
    #include <string.h>
    int main()
    {
        /* créer un contexte d'analyseur syntaxique local en stockage automatique */
        yycontext yy;
        /* le contexte *doit* être initialisé à zéro avant la première utilisation */
        memset(&yy, 0, sizeof(yy));
        while (yyparse(&yy))
            ;
        printf("%d nouvelles lignes\n", yy.count);
        /* libérer toutes les ressources associées au contexte */
        yyrelease(&yy);
        return 0;
    }

DIAGNOSTICS

peg et leg avertissent des conditions suivantes lors de la conversion d'une grammaire en analyseur syntaxique.

erreur de syntaxe
La grammaire d'entrée était mal formée d'une manière ou d'une autre. Le message d'erreur inclura le texte sur le point d'être reconnu (souvent beaucoup en retrait par rapport à l'emplacement réel de l'erreur) et le numéro de ligne du caractère le plus récemment considéré (qui est souvent l'emplacement réel du problème).
règle 'foo' utilisée mais non définie
La grammaire faisait référence à une règle nommée 'foo' mais aucune définition n'a été fournie. Tenter d'utiliser l'analyseur syntaxique généré entraînera probablement des erreurs de l'éditeur de liens en raison de symboles indéfinis associés à la règle manquante.
règle 'foo' définie mais non utilisée
La grammaire a défini une règle nommée 'foo' puis l'a ignorée. Le code associé à la règle est inclus dans l'analyseur syntaxique généré qui sera par ailleurs sain.
possible récursion gauche infinie dans la règle 'foo'
Il existe au moins un chemin à travers la grammaire qui mène de la règle 'foo' à (une invocation récursive de) la même règle sans consommer d'entrée.

La récursion gauche, en particulier celle trouvée dans les documents standard, est souvent 'directe' et implique une répétition triviale.

    # (6.7.6)
    direct-abstract-declarator =
        LPAREN abstract-declarator RPAREN
    |   direct-abstract-declarator? LBRACKET assign-expr? RBRACKET
    |   direct-abstract-declarator? LBRACKET STAR RBRACKET
    |   direct-abstract-declarator? LPAREN param-type-list? RPAREN
La récursion peut facilement être éliminée en convertissant les parties du motif suivant la récursion en un suffixe répétable. 
    # (6.7.6)
    direct-abstract-declarator =
        direct-abstract-declarator-head?
        direct-abstract-declarator-tail*
    direct-abstract-declarator-head =
        LPAREN abstract-declarator RPAREN
    direct-abstract-declarator-tail =
        LBRACKET assign-expr? RBRACKET
    |   LBRACKET STAR RBRACKET
    |   LPAREN param-type-list? RPAREN

CAVEATS

Un analyseur syntaxique qui accepte une entrée vide réussira *toujours*. Considérons l'exemple suivant, typique d'une première tentative d'écriture d'un analyseur syntaxique basé sur PEG :

    Program = Expression*
    Expression = "whatever"
    %%
    int main() {
      while (yyparse())
        puts("success!");
      return 0;
    }

Ce programme boucle indéfiniment, quelle que soit l'entrée (ou absence d'entrée) fournie sur stdin. De nombreuses corrections sont possibles, la plus simple étant d'insister pour que l'analyseur syntaxique consomme toujours une entrée non vide. Changer la première ligne en

    Program = Expression+

accompli cela. Si l'analyseur syntaxique doit consommer l'intégralité de l'entrée, il est également fortement recommandé d'exiger explicitement la fin du fichier :

    Program = Expression+ !.

Cela fonctionne car l'analyseur syntaxique ne parviendra pas à faire correspondre ("!" prédicat) n'importe quel caractère ("." expression) lorsqu'il tentera de lire au-delà de la fin de l'entrée.

BUGS

Vous devez taper 'man peg' pour lire la page de manuel de leg(1).

Les préfixes 'yy' et 'YY' ne peuvent pas être changés.

La récursion gauche est détectée dans la grammaire d'entrée mais n'est pas gérée correctement dans l'analyseur syntaxique généré.

Les diagnostics pour les erreurs dans la grammaire d'entrée sont obscurs et pas particulièrement utiles.

Les opérateurs ! et ~ devraient vraiment être nommés l'un l'autre.

Plusieurs fonctionnalités couramment utilisées de lex(1) (yywrap(), yyin, etc.) sont complètement absentes.

L'analyseur syntaxique généré ne contient pas de directives '#line' pour rediriger les erreurs du compilateur C vers la description de la grammaire le cas échéant.
