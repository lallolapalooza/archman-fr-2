PERLXSTYPEMAP(1perl) Guide de référence du programmeur Perl PERLXSTYPEMAP(1perl)

NOM

perlxstypemap - Mappage des types C/Perl pour Perl XS

DESCRIPTION

Plus vous réfléchissez à l'interface entre deux langages, plus vous réalisez que la majorité de l'effort du programmeur doit être consacrée à la conversion entre les structures de données natives à l'un ou l'autre des langages impliqués. Cela prime sur d'autres considérations telles que les conventions d'appel différentes, car l'espace des problèmes est beaucoup plus vaste. Il y a tout simplement plus de façons de manipuler des données en mémoire qu'il n'y a de façons d'implémenter un appel de fonction.

La tentative de solution de Perl XS à ce problème est le concept de typemaps. À un niveau abstrait, un typemap Perl XS n'est rien d'autre qu'une recette pour convertir une certaine structure de données Perl en une certaine structure de données C et vice versa. Étant donné qu'il peut exister des types C suffisamment similaires pour justifier une conversion avec la même logique, les typemaps XS sont représentés par un identifiant unique, appelé ci-après un type XS dans ce document. Vous pouvez alors indiquer au compilateur XS que plusieurs types C doivent être mappés avec le même typemap XS.

Dans votre code XS, lorsque vous définissez un argument avec un type C ou lorsque vous utilisez ensemble une section "CODE:" et une section "OUTPUT:" avec un type de retour C de votre XSUB, c'est le mécanisme de typemapping qui rend cela facile.

Anatomie d'un typemap

De manière plus pratique, le typemap est une collection de fragments de code utilisés par le compilateur xsubpp pour mapper les paramètres et les valeurs des fonctions C aux valeurs Perl. Le fichier typemap peut se composer de trois sections intitulées "TYPEMAP", "INPUT" et "OUTPUT". Une section initiale sans étiquette est supposée être une section "TYPEMAP". La section INPUT indique au compilateur comment traduire les valeurs Perl en variables de certains types C. La section OUTPUT indique au compilateur comment traduire les valeurs de certains types C en valeurs que Perl peut comprendre. La section TYPEMAP indique au compilateur quels fragments de code INPUT et OUTPUT doivent être utilisés pour mapper un type C donné à une valeur Perl. Les étiquettes de section "TYPEMAP", "INPUT" ou "OUTPUT" doivent commencer dans la première colonne, sur une ligne à part, et doivent être en majuscules.

Chaque type de section peut apparaître un nombre arbitraire de fois et n'a pas besoin d'apparaître du tout. Par exemple, un typemap peut couramment manquer des sections "INPUT" et "OUTPUT" si tout ce qu'il doit faire est d'associer des types C supplémentaires à des types XS de base comme T_PTROBJ. Les lignes commençant par un dièse "#" sont considérées comme des commentaires et ignorées dans la section "TYPEMAP", mais sont considérées comme significatives dans les sections "INPUT" et "OUTPUT". Les lignes vides sont généralement ignorées.

Traditionnellement, les typemaps devaient être écrits dans un fichier séparé, conventionnellement appelé "typemap" dans une distribution CPAN. Avec ExtUtils::ParseXS (le compilateur XS) version 3.12 ou supérieure, qui est fourni avec perl 5.16, les typemaps peuvent également être intégrés directement dans le code XS en utilisant une syntaxe similaire aux HERE-docs :

TYPEMAP: <<HERE
...
HERE

où "HERE" peut être remplacé par d'autres identifiants comme avec les HERE-docs Perl normaux. Tous les détails ci-dessous concernant le format textuel du typemap restent valides.

La section "TYPEMAP" doit contenir une paire de type C et de type XS par ligne, comme suit. Un exemple tiré du fichier typemap principal :

TYPEMAP
# toutes les variantes de char* sont gérées par le typemap T_PV
char *          T_PV
const char *    T_PV
unsigned char * T_PV
...

Les sections "INPUT" et "OUTPUT" ont des formats identiques, c'est-à-dire que chaque ligne non indentée commence une nouvelle carte d'entrée ou de sortie respectivement. Une nouvelle carte d'entrée ou de sortie doit commencer par le nom du type XS à mapper sur une ligne à part, suivi du code qui l'implémente, indiqué sur les lignes suivantes. Exemple :

INPUT
T_PV
  $var = ($type)SvPV_nolen($arg)
T_PTR
  $var = INT2PTR($type,SvIV($arg))

Nous aborderons bientôt la signification de ces variables d'apparence Perlish.

Enfin, voici un exemple de fichier typemap complet pour mapper les chaînes C de type "char *" aux scalaires/chaînes Perl :

TYPEMAP
char *  T_PV
INPUT
T_PV
  $var = ($type)SvPV_nolen($arg)
OUTPUT
T_PV
  sv_setpv((SV*)$arg, $var);

Voici un exemple plus complexe : supposons que vous vouliez que "struct netconfig" soit béni dans la classe "Net::Config". Une façon de le faire est d'utiliser des underscores (_) pour séparer les noms de packages, comme suit :

typedef struct netconfig * Net_Config;

Et ensuite fournir une entrée typemap "T_PTROBJ_SPECIAL" qui remplace les underscores par des doubles deux-points (::), et déclarer "Net_Config" comme étant de ce type :

TYPEMAP
Net_Config      T_PTROBJ_SPECIAL
INPUT
T_PTROBJ_SPECIAL
  if (sv_derived_from($arg, \"${(my $ntt=$ntype)=~s/_/::/g;\$ntt}\")){
    IV tmp = SvIV((SV*)SvRV($arg));
    $var = INT2PTR($type, tmp);
  }
  else
    croak(\"$var is not of type ${(my $ntt=$ntype)=~s/_/::/g;\$ntt}\")
OUTPUT
T_PTROBJ_SPECIAL
  sv_setref_pv($arg, \"${(my $ntt=$ntype)=~s/_/::/g;\$ntt}\",
               (void*)$var);

Les sections INPUT et OUTPUT remplacent les underscores par des doubles deux-points à la volée, produisant l'effet désiré. Cet exemple démontre une partie de la puissance et de la polyvalence de la fonctionnalité de typemap.

La macro "INT2PTR" (définie dans perl.h) convertit un entier en un pointeur d'un type donné, en tenant compte des différences possibles de taille entre les entiers et les pointeurs. Il existe également les macros "PTR2IV", "PTR2UV", "PTR2NV", pour mapper dans l'autre sens, qui peuvent être utiles dans les sections OUTPUT.

Le rôle du fichier typemap dans votre distribution

Le typemap par défaut dans le répertoire lib/ExtUtils de la source de Perl contient de nombreux types utiles qui peuvent être utilisés par les extensions Perl. Certaines extensions définissent des typemaps supplémentaires qu'elles conservent dans leur propre répertoire. Ces typemaps supplémentaires peuvent référencer des maps INPUT et OUTPUT dans le typemap principal. Le compilateur xsubpp permettra au typemap de l'extension d'outrepasser toutes les associations présentes dans le typemap par défaut. Au lieu d'utiliser un fichier typemap supplémentaire, les typemaps peuvent être intégrés verbatim dans XS avec une syntaxe de type héredoc. Voir la documentation sur le mot-clé XS "TYPEMAP:".

Pour les distributions CPAN, vous pouvez supposer que les types XS définis par le cœur de Perl sont déjà disponibles. De plus, le typemap de base a des types XS par défaut pour un grand nombre de types C. Par exemple, si vous retournez simplement un "char *" de votre XSUB, le typemap de base associera ce type C au type XS T_PV. Cela signifie que votre chaîne C sera copiée dans le slot PV (valeur du pointeur) d'un nouveau scalaire qui sera retourné de votre XSUB à Perl.

Si vous développez une distribution CPAN en utilisant XS, vous pouvez ajouter votre propre fichier nommé typemap à la distribution. Ce fichier peut contenir des typemaps qui mappent soit des types spécifiques à votre code, soit qui outrepassent les associations du fichier typemap de base pour les types C courants.

Partage des typemaps entre les distributions CPAN

À partir de la version 3.13_01 d'ExtUtils::ParseXS (fournie avec perl 5.16 et versions ultérieures), il est assez facile de partager du code de typemap entre plusieurs distributions CPAN. L'idée générale est de le partager sous forme de module qui offre une certaine API, et de faire déclarer aux modules dépendants cette exigence en temps de construction et d'importer le typemap dans le XS. Un exemple d'un tel module de partage de typemap sur CPAN est "ExtUtils::Typemaps::Basic". Deux étapes pour rendre les typemaps de ce module disponibles dans votre code :

  • Déclarez "ExtUtils::Typemaps::Ba
sic" en tant que dépendance de construction dans "Makefile.PL" (utilisez "BUILD_REQUIRES"), ou dans votre "Build.PL" (utilisez "build_requires").
  • Incluez la ligne suivante dans la section XS de votre fichier XS : (ne pas casser la ligne) 
    INCLUDE_COMMAND: $^X -MExtUtils::Typemaps::Cmd
                 -e "print embeddable_typemap(q{Basic})"

    • Écrire des entrées typemap

    Chaque entrée de typemap INPUT ou OUTPUT est une chaîne Perl entre guillemets doubles qui sera évaluée en présence de certaines variables pour obtenir le code C final pour le mappage d'un type C donné.

    Cela signifie que vous pouvez intégrer du code Perl dans votre code typemap (C) en utilisant des constructions telles que "${ code Perl qui s'évalue en référence scalaire ici }". Un cas d'utilisation courant est de générer des messages d'erreur qui font référence au nom de fonction réel, même lors de l'utilisation de la fonctionnalité ALIAS XS :

    ${ $ALIAS ? \q[GvNAME(CvGV(cv))] : \qq[\"$pname\"] }

    Pour de nombreux exemples de typemap, référez-vous au fichier typemap principal qui se trouve dans l'arborescence source de Perl à l'adresse lib/ExtUtils/typemap.

    Les variables Perl disponibles pour l'interpolation dans les typemaps sont les suivantes :

    • $var - le nom de la variable d'entrée ou de sortie, par exemple RETVAL pour les valeurs de retour.
    • $type - le type C brut du paramètre, tout ":" remplacé par "_". par exemple, pour un type de "Foo::Bar", $type est "Foo__Bar"
    • $ntype - le type fourni avec "*" remplacé par "Ptr". par exemple, pour un type de "Foo*", $ntype est "FooPtr"
    • $arg - l'entrée de la pile, à partir de laquelle le paramètre est entré ou vers laquelle il est sorti, par exemple ST(0)
    • $argoff - le décalage de la pile d'arguments de l'argument. c'est-à-dire 0 pour le premier argument, etc.
    • $pname - le nom complet du XSUB, incluant le nom du "PACKAGE", avec tout "PREFIX" supprimé. C'est le nom non-ALIAS.
    • $Package - le package spécifié par le mot-clé "PACKAGE" le plus récent.
    • $ALIAS - non nul si le XSUB actuel a des alias déclarés avec "ALIAS".

    Liste complète des typemaps principaux

    Chaque type C est représenté par une entrée dans le fichier typemap qui est responsable de la conversion des variables Perl (SV, AV, HV, CV, etc.) vers et depuis ce type. Les sections suivantes listent tous les types XS livrés avec Perl par défaut.

    T_SV
    Ceci passe simplement la représentation C de la variable Perl (un SV*) dans et hors de la couche XS. Ceci peut être utilisé si le code C souhaite traiter directement la variable Perl.
    T_SVREF
    Utilisé pour passer et retourner une référence vers un SV.

    Notez que ce typemap ne décrémente pas le compteur de références lors du retour de la référence vers un SV*. Voir aussi : T_SVREF_REFCOUNT_FIXED

    T_SVREF_FIXED
    Utilisé pour passer et retourner une référence vers un SV. Il s'agit d'une variante fixe de T_SVREF qui décrémente correctement le compteur de références lors du retour d'une référence vers un SV*. Introduit dans perl 5.15.4.
    T_AVREF
    Du niveau Perl, c'est une référence vers un tableau Perl. Du niveau C, c'est un pointeur vers un AV.

    Notez que ce typemap ne décrémente pas le compteur de références lors du retour d'un AV*. Voir aussi : T_AVREF_REFCOUNT_FIXED

    T_AVREF_REFCOUNT_FIXED
    Du niveau Perl, c'est une référence vers un tableau Perl. Du niveau C, c'est un pointeur vers un AV. Il s'agit d'une variante fixe de T_AVREF qui décrémente correctement le compteur de références lors du retour d'un AV*. Introduit dans perl 5.15.4.
    T_HVREF
    Du niveau Perl, c'est une référence vers une table de hachage Perl. Du niveau C, c'est un pointeur vers une HV.

    Notez que ce typemap ne décrémente pas le compteur de références lors du retour d'une HV*. Voir aussi : T_HVREF_REFCOUNT_FIXED

    T_HVREF_REFCOUNT_FIXED
    Du niveau Perl, c'est une référence vers une table de hachage Perl. Du niveau C, c'est un pointeur vers une HV. Il s'agit d'une variante fixe de T_HVREF qui décrémente correctement le compteur de références lors du retour d'une HV*. Introduit dans perl 5.15.4.
    T_CVREF
    Du niveau Perl, c'est une référence vers une sous-routine Perl (par exemple, $sub = sub { 1 };). Du niveau C, c'est un pointeur vers une CV.

    Notez que ce typemap ne décrémente pas le compteur de références lors du retour d'une HV*. Voir aussi : T_HVREF_REFCOUNT_FIXED

    T_CVREF_REFCOUNT_FIXED
    Du niveau Perl, c'est une référence vers une sous-routine Perl (par exemple, $sub = sub { 1 };). Du niveau C, c'est un pointeur vers une CV.

    Il s'agit d'une variante fixe de T_HVREF qui décrémente correctement le compteur de références lors du retour d'une HV*. Introduit dans perl 5.15.4.

    T_SYSRET
    Le typemap T_SYSRET est utilisé pour traiter les valeurs de retour des appels système. Il n'est significatif que lors du passage de valeurs de C à Perl (il n'y a pas de concept de passage d'un retour système de Perl à C).

    Les appels système retournent -1 en cas d'erreur (en définissant ERRNO avec la raison) et (généralement) 0 en cas de succès. Si la valeur de retour est -1, ce typemap retourne "undef". Si la valeur de retour n'est pas -1, ce typemap traduit un 0 (faux Perl) en "0 mais vrai" (qui est vrai Perl) ou retourne la valeur elle-même, pour indiquer que la commande a réussi.

    Le module POSIX utilise intensivement ce type.

    T_UV
    Un entier non signé.
    T_IV
    Un entier signé. Celui-ci est converti en type entier requis lors du passage à C et converti en IV lors du retour à Perl.
    T_INT
    Un entier signé. Ce typemap convertit la valeur Perl en un type entier natif (le type "int" sur la plateforme actuelle). Lors du retour de la valeur à Perl, elle est traitée de la même manière que pour T_IV.

    Son comportement est identique à celui de l'utilisation d'un type "int" dans XS avec T_IV.

    T_ENUM
    Une valeur d'énumération. Utilisé pour transférer un composant d'énumération depuis C. Il n'y a aucune raison de passer une valeur d'énumération à C car elle est stockée sous forme d'IV dans Perl.
    T_BOOL
    Un type booléen. Ceci peut être utilisé pour passer des valeurs vraies et fausses vers et depuis C.
    T_U_INT
    Ceci est pour les entiers non signés. Il est équivalent à utiliser T_UV mais convertit explicitement la variable en type "unsigned int". Le type par défaut pour "unsigned int" est T_UV.
    T_SHORT
    Entiers courts. Ceci est équivalent à T_IV mais convertit explicitement le retour en type "short". Le typemap par défaut pour "short" est T_IV.
    T_U_SHORT
    Entiers courts non signés. Ceci est équivalent à T_UV mais convertit explicitement le retour en type "unsigned short". Le typemap par défaut pour "unsigned short" est T_UV.

    T_U_SHORT est utilisé pour le type "U16" dans le typemap standard.

    T_LONG
    Entiers longs. Ceci est équivalent à T_IV mais convertit explicitement le retour en type "long". Le typemap par défaut pour "long" est T_IV.
    T_U_LONG
    Entiers longs non signés. Ceci est équivalent à T_UV mais convertit explicitement le retour en type "unsigned long". Le typemap par défaut pour "unsigned long" est T_UV.

    T_U_LONG est utilisé pour le type "U32" dans le typemap standard.

    T_CHAR
    Caractères simples de 8 bits.
    T_U_CHAR
    Un octet non signé.
    T_FLOAT
    Un nombre à virgule flottante. Ce typemap garantit de retourner une variable convertie en "float".
    T_NV
    Un nombre à virgule flottante Perl. Similaire à T_IV et T_UV dans le sens où le type de retour est converti vers le type numérique demandé plutôt que vers un type spécifique.
    T_DOUBLE
    Un nombre à virgule flottante de double précision. Ce typemap garantit de retourner une variable convertie en "double".
    T_PV
    Une chaîne (char *).
    T_PTR
    Une adresse mémoire (pointeur). Typiquement associé à un type "void *".
    T_PT
    T_REFREF
    Similaire à T_PTRREF, sauf que le pointeur stocké dans le scalaire référencé est déréférencé et copié dans la variable de sortie. Cela signifie que T_REFREF est à T_PTRREF ce que T_OPAQUE est à T_OPAQUEPTR. Tout est clair ?

    Seule la partie ENTRÉE de cela est implémentée (Perl vers XSUB) et il n'y a pas d'utilisateurs connus dans le noyau ou sur CPAN.

    T_REFOBJ
    Comme T_REFREF, sauf qu'il effectue une vérification stricte des types (l'héritage n'est pas pris en charge).

    Pour les XSUB de type "DESTROY" uniquement, un T_REFOBJ est optimisé en T_REFREF. Cela signifie que la vérification de classe est ignorée.

    T_OPAQUEPTR
    Cela peut être utilisé pour stocker des octets dans le composant chaîne du SV. Ici, la représentation des données est sans importance pour perl et les octets eux-mêmes sont simplement stockés dans le SV. On suppose que la variable C est un pointeur (les octets sont copiés à partir de cet emplacement mémoire). Si le pointeur pointe vers quelque chose représenté par 8 octets, alors ces 8 octets sont stockés dans le SV (et length() rapportera une valeur de 8). Cette entrée est similaire à T_OPAQUE.

    En principe, la commande unpack() peut être utilisée pour reconvertir les octets en un nombre (si le type sous-jacent est connu pour être un nombre).

    Cette entrée peut être utilisée pour stocker une structure C (le nombre d'octets à copier est calculé à l'aide de la fonction C "sizeof") et peut être utilisée comme alternative à T_PTRREF sans avoir à se soucier d'une fuite de mémoire (puisque Perl nettoiera le SV).

    T_OPAQUE
    Cela peut être utilisé pour stocker des données de types non pointeurs dans la partie chaîne d'un SV. C'est similaire à T_OPAQUEPTR, sauf que le typemap récupère le pointeur directement plutôt que de supposer qu'il est fourni. Par exemple, si un entier est importé dans Perl en utilisant T_OPAQUE plutôt que T_IV, les octets sous-jacents représentant l'entier seront stockés dans le SV mais la valeur entière réelle ne sera pas disponible. C'est-à-dire que les données sont opaques pour perl.

    Les données peuvent être récupérées à l'aide de la fonction "unpack" si le type sous-jacent du flux d'octets est connu.

    T_OPAQUE prend en charge l'entrée et la sortie de types simples. T_OPAQUEPTR peut être utilisé pour renvoyer ces octets à C si un pointeur est acceptable.

    Tableau implicite
    xsubpp prend en charge une syntaxe spéciale pour renvoyer des tableaux C "packed" à perl. Si le type de retour XS est donné comme 
    array(type, nelem)

    xsubpp copiera le contenu de "nelem * sizeof(type)" octets de RETVAL vers un SV et le poussera sur la pile. Ceci n'est vraiment utile que si le nombre d'éléments à retourner est connu au moment de la compilation et que vous n'avez pas d'objection à avoir une chaîne d'octets dans votre SV. Utilisez T_ARRAY pour pousser un nombre variable d'arguments sur la pile de retour (ils ne seront cependant pas "packed" en une seule chaîne).

    Ceci est similaire à l'utilisation de T_OPAQUEPTR mais peut être utilisé pour traiter plus d'un élément.

    T_PACKED
    Appelle des fonctions fournies par l'utilisateur pour la conversion. Pour "OUTPUT" (XSUB vers Perl), une fonction nommée "XS_pack_$ntype" est appelée avec le scalaire Perl de sortie et la variable C à convertir. $ntype est le type C normalisé qui doit être mappé à Perl. Normalisé signifie que tous les "*" sont remplacés par la chaîne "Ptr". La valeur de retour de la fonction est ignorée.

    Inversement, pour le mappage "INPUT" (Perl vers XSUB), la fonction nommée "XS_unpack_$ntype" est appelée avec le scalaire Perl d'entrée comme argument, et la valeur de retour est transtypée vers le type C mappé et assignée à la variable C de sortie.

    Une fonction de conversion d'exemple pour une structure typemappée "foo_t *" pourrait être :

    static void
XS_pack_foo_tPtr(SV *out, foo_t *in)
{
  dTHX; /* hélas, la signature n'inclut pas pTHX_ */
  HV* hash = newHV();
  hv_stores(hash, "int_member", newSViv(in->int_member));
  hv_stores(hash, "float_member", newSVnv(in->float_member));
  /* ... */
  /* mortaliser car ta pile n'est pas comptée en références */
  sv_setsv(out, sv_2mortal(newRV_noinc((SV*)hash)));
}

    La conversion de Perl vers C est laissée en exercice au lecteur, mais le prototype serait :

    static foo_t *
XS_unpack_foo_tPtr(SV *in);

    Au lieu d'une véritable fonction C qui doit récupérer le contexte du thread en utilisant "dTHX", vous pouvez définir des macros du même nom et éviter la surcharge. Gardez également à l'esprit de libérer éventuellement la mémoire allouée par "XS_unpack_foo_tPtr".

    T_PACKEDARRAY
    T_PACKEDARRAY est similaire à T_PACKED. En fait, le typemap "INPUT" (Perl vers XSUB) est identique, mais le typemap "OUTPUT" passe un argument supplémentaire à la fonction "XS_pack_$ntype". Ce troisième paramètre indique le nombre d'éléments dans la sortie afin que la fonction puisse gérer les tableaux C de manière cohérente. La variable doit être déclarée par l'utilisateur et doit porter le nom "count_$ntype" où $ntype est le nom du type C normalisé comme expliqué ci-dessus. La signature de la fonction serait pour l'exemple ci-dessus et "foo_t **" : 
    static void
XS_pack_foo_tPtrPtr(SV *out, foo_t *in, UV count_foo_tPtrPtr);

    Le type du troisième paramètre est arbitraire en ce qui concerne le typemap. Il doit simplement être en accord avec la variable déclarée.

    Bien sûr, à moins que vous ne connaissiez le nombre d'éléments dans le tableau C "sometype **", il sera difficile de déchiffrer la valeur de retour de "foo_t ** XS_unpack_foo_tPtrPtr(...)" au sein de votre XSUB. Étant donné que les détails dépendent entièrement de l'auteur XS (l'utilisateur du typemap), il existe plusieurs solutions, dont aucune n'est particulièrement élégante. La solution la plus couramment rencontrée a été d'allouer de la mémoire pour N+1 pointeurs et d'assigner "NULL" au (N+1)ème pour faciliter l'itération.

    Alternativement, utiliser un typemap personnalisé pour vos besoins dès le départ est probablement préférable.

    T_ARRAY
    Ceci est utilisé pour convertir la liste d'arguments perl en un tableau C et pour pousser le contenu d'un tableau C sur la pile d'arguments perl.

    La signature d'appel habituelle est

    @out = array_func( @in );

    N'importe quel nombre d'arguments peut figurer dans la liste avant le tableau, mais les tableaux d'entrée et de sortie doivent être les derniers éléments de la liste.

    Lorsqu'il est utilisé pour passer une liste perl à C, l'auteur XS doit fournir une fonction (nommée d'après le type de tableau mais avec 'Ptr' substitué à '*') pour allouer la mémoire nécessaire pour contenir la liste. Un pointeur doit être retourné. Il incombe à l'auteur XS de libérer la mémoire à la sortie de la fonction. La variable "ix_$var" est définie sur le nombre d'éléments dans le nouveau tableau.

    Lors du retour d'un tableau C à Perl, l'auteur XS doit fournir une variable entière appelée "size_$var" contenant le nombre d'éléments dans le tableau. Ceci est utilisé pour déterminer combien d'éléments doivent être poussés sur la pile d'arguments de retour. Ceci n'est pas requis en entrée car Perl sait combien d'arguments se trouvent sur la pile lorsque la routine est appelée. Ordinairement, cette variable serait appelée "size_RETVAL".

    De plus, le type de chaque élément est déterminé à partir du type du tableau. Si le tableau utilise le type "intArray *", xsubpp déduira automatiquement qu'il contient des variables de type "int" et utilisera cette entrée de typemap pour effectuer la copie de chaque élément. Tous les pointeurs '*' et les balises 'Array' sont supprimés du nom pour déterminer le sous-type.

    T_STDIO
    Ceci est utilisé pour passer des descripteurs de fichiers perl vers et depuis C en utilisant
    "FILE *" structures. 
    T_INOUT
    Ceci est utilisé pour passer des descripteurs de fichiers perl à et depuis C en utilisant des structures "PerlIO *". Le descripteur de fichier peut être utilisé pour la lecture et l'écriture. Ceci correspond au mode "+<", voir également T_IN et T_OUT.

    Voir perliol pour plus d'informations sur la couche d'abstraction Perl IO. Perl doit avoir été compilé avec "-Duseperlio".

    Il n'y a pas de vérification pour s'assurer que le descripteur de fichier passé de Perl à C a été créé avec le bon mode open().

    Astuce : Le tutoriel perlxstut couvre bien les types XS T_INOUT, T_IN et T_OUT.

    T_IN
    Identique à T_INOUT, mais le descripteur de fichier qui est retourné de C à Perl ne peut être utilisé que pour la lecture (mode "<").
    T_OUT
    Identique à T_INOUT, mais le descripteur de fichier qui est retourné de C à Perl est configuré pour utiliser le mode d'ouverture "+>".
