PERLSUB(1perl) Guide du programmeur Perl PERLSUB(1perl)

NOM

perlsub - Sous-programmes Perl (fonctions définies par l'utilisateur)

SYNTAXE

Pour déclarer des sous-programmes :

sub NOM;                       # Une déclaration "anticipée".
sub NOM(PROTO);                #  idem, mais avec prototypes
sub NOM : ATTRIBUTS;           #  avec attributs
sub NOM(PROTO) : ATTRIBUTS;    #  avec attributs et prototypes
sub NOM BLOC                  # Une déclaration et une définition.
sub NOM(PROTO) BLOC           #  idem, mais avec prototypes
sub NOM : ATTRIBUTS BLOC      #  avec attributs
sub NOM(PROTO) : ATTRIBUTS BLOC   #  avec prototypes et attributs
use feature 'signatures';
sub NOM(SIG) BLOC                     # avec signature
sub NOM :ATTRIBUTS (SIG) BLOC         # avec signature, attributs
sub NOM :prototype(PROTO) (SIG) BLOC  # avec signature, prototype

Pour définir un sous-programme anonyme à l'exécution :

$ref_sub = sub BLOC;                    # pas de proto
$ref_sub = sub (PROTO) BLOC;            # avec proto
$ref_sub = sub : ATTRIBUTS BLOC;            # avec attributs
$ref_sub = sub (PROTO) : ATTRIBUTS BLOC;    # avec proto et attributs
use feature 'signatures';
$ref_sub = sub (SIG) BLOC;          # avec signature
$ref_sub = sub : ATTRIBUTS(SIG) BLOC;   # avec signature, attributs

Pour importer des sous-programmes :

use MODULE qw(NOM1 NOM2 NOM3);

Pour appeler des sous-programmes :

NOM(LISTE);     # Appel de sous-programme régulier.
NOM LISTE;      # Parenthèses optionnelles si prédéclaré/importé.
&NOM(LISTE);    # Contourne les prototypes.
&NOM;          # Rend @_ courant visible au sous-programme appelé.

DESCRIPTION

Comme beaucoup de langages, Perl permet des sous-programmes définis par l'utilisateur. Ceux-ci peuvent être situés n'importe où dans le programme principal, être chargés depuis d'autres fichiers via les mots-clés "do", "require" ou "use", ou être générés à la volée en utilisant "eval" ou des sous-programmes anonymes. Vous pouvez même appeler une fonction indirectement en utilisant une variable contenant son nom ou une référence de type CODE.

Le modèle de Perl pour l'appel de fonctions et les valeurs de retour est simple : toutes les fonctions sont passées comme paramètres dans une seule liste plate de scalaires, et toutes les fonctions retournent de même à leur appelant une seule liste plate de scalaires. Les tableaux ou les hashes dans ces listes d'appel et de retour s'aplatiront, perdant leur identité - mais vous pouvez toujours utiliser la passe par référence à la place pour éviter cela. Les listes d'appel et de retour peuvent contenir autant ou aussi peu d'éléments scalaires que vous le souhaitez. (Souvent une fonction sans instruction de retour explicite est appelée une sous-routine, mais il n'y a vraiment aucune différence du point de vue de Perl.)

Dans un sous-programme qui utilise des signatures (voir "Signatures" ci-dessous), les arguments sont assignés à des variables lexicales introduites par la signature. Dans l'implémentation actuelle de Perl, ils sont également accessibles dans le tableau @_ de la même manière que pour les sous-programmes sans signature, mais y accéder de cette manière est maintenant déconseillé à l'intérieur d'un tel sous-programme utilisant des signatures.

Dans un sous-programme qui n'utilise pas de signatures, les arguments passés apparaissent dans le tableau @_. Par conséquent, si vous appeliez une fonction avec deux arguments, ceux-ci seraient stockés dans $_[0] et $_[1]. Le tableau @_ est un tableau local, mais ses éléments sont des alias pour les paramètres scalaires réels. En particulier, si un élément $_[0] est mis à jour, le paramètre correspondant est mis à jour (ou une erreur survient s'il n'est pas modifiable). Si un argument est un élément de tableau ou de hash qui n'existait pas lors de l'appel de la fonction, cet élément est créé uniquement lorsque (et si) il est modifié ou qu'une référence vers lui est prise. (Certaines versions antérieures de Perl créaient l'élément que l'élément soit assigné ou non.) L'assignation au tableau entier @_ supprime cet alias et ne met pas à jour les arguments.

Lorsque vous n'utilisez pas de signatures, Perl ne fournit pas d'autre moyen de créer des paramètres formels nommés. En pratique, tout ce que vous faites est d'assigner à une liste my() de ceux-ci. Les variables qui ne sont pas déclarées comme privées sont des variables globales. Pour des détails approfondis sur la création de variables privées, voir "Variables privées via my()" et "Valeurs temporaires via local()". Pour créer des environnements protégés pour un ensemble de fonctions dans un package séparé (et probablement un fichier séparé), voir "Packages" dans perlmod.

Une instruction "return" peut être utilisée pour sortir d'un sous-programme, en spécifiant éventuellement la valeur retournée, qui sera évaluée dans le contexte approprié (liste, scalaire ou vide) en fonction du contexte de l'appel du sous-programme. Si vous ne spécifiez pas de valeur de retour, le sous-programme retourne une liste vide en contexte de liste, la valeur indéfinie en contexte scalaire, ou rien en contexte vide. Si vous retournez un ou plusieurs agrégats (tableaux et hashes), ceux-ci seront aplatis ensemble en une grande liste indistincte.

Si aucun "return" n'est trouvé et si la dernière instruction est une expression, sa valeur est retournée. Si la dernière instruction est une structure de contrôle de boucle comme un "foreach" ou un "while", la valeur retournée est indéterminée. Le sous-programme vide retourne la liste vide.

Exemple :

sub max {
    my $max = shift(@_);
    foreach $foo (@_) {
        $max = $foo if $max < $foo;
    }
    return $max;
}
$meilleurjour = max($lun,$mar,$mer,$jeu,$ven);

Exemple :

# qui commencent par un espace blanc

Assigner à une liste de variables privées pour nommer vos arguments :

sub peut_definir {
    my($cle, $valeur) = @_;
    $Foo{$cle} = $valeur unless $Foo{$cle};
}

Comme l'affectation copie les valeurs, cela a également pour effet de transformer le passage par référence en passage par valeur. Sinon, une fonction est libre de modifier @_ sur place et de changer les valeurs de son appelant.

maj_interne($v1, $v2);  # cela change $v1 et $v2
sub maj_interne {
    for (@_) { tr/a-z/A-Z/ }
}

Vous n'êtes bien sûr pas autorisé à modifier des constantes de cette manière. Si un argument était littéral et que vous essayiez de le changer, vous prendriez une exception (probablement fatale). Par exemple, ceci ne fonctionnera pas :

maj_interne("frédéric");

Il serait beaucoup plus sûr que la fonction maj_interne() soit écrite pour retourner une copie de ses paramètres au lieu de les modifier sur place :

($v3, $v4) = maj($v1, $v2);  # cela ne change pas $v1 et $v2
sub maj {
    return unless defined wantarray;  # contexte vide, ne rien faire
    my @parametres = @_;
    for (@parametres) { tr/a-z/A-Z/ }
    return wantarray ? @parametres : $parametres[0];
}

Remarquez comment cette fonction (non prototypée) ne se soucie pas de savoir si elle a reçu des scalaires réels ou des tableaux. Perl voit tous les arguments comme une seule grande liste de paramètres, longue et plate, dans @_. C'est un domaine où le style simple de passage d'arguments de Perl brille. La fonction maj() fonctionnerait parfaitement sans changer la définition de maj() même si nous lui fournissions des choses comme celles-ci :

@nouvelle_liste   = maj(@liste1, @liste2);
@nouvelle_liste   = maj( split /:/, $var );

Ne soyez cependant pas tenté de faire ceci :

(@x, @y)   = maj(@liste1, @liste2);

Comme la liste de paramètres entrante aplatie, la liste de retour est également aplatie lors du retour. Donc, tout ce que vous avez réussi à faire ici est de tout stocker dans @x et de rendre @y vide. Voir "Passe par Référence" pour des alternatives.

Un sous-programme peut être appelé en utilisant un préfixe "&" explicite. Le "&" est optionnel dans Perl moderne, tout comme les parenthèses si le sous-programme a été prédéclaré. Le "&" n'est *pas* optionnel lors de la simple nomination du sous-programme, comme lorsqu'il est utilisé comme argument pour defined() ou undef(). Il n'est pas non plus optionnel lorsque vous souhaitez effectuer un appel de sous-programme indirect avec un nom de sous-programme ou une référence en utilisant les constructs &$ref_sub() ou "&{$ref_sub}()", bien que la notation $ref_sub->() résolve ce problème. Les sous-programmes peuvent être appelés récursivement. Si un sous-programme est appelé en utilisant la forme "&", la liste d'arguments est facultative, et si elle est omise, aucun tableau @_ n'est configuré pour le sous-programme : le tableau @_ au moment de l'appel est visible par le sous-programme à la place. Il s'agit d'un mécanisme d'efficacité que les nouveaux utilisateurs voudront peut-être éviter.

&foo(1,2,3);        # passe trois arguments
foo(1,2,3);         # identique
foo();              # passe une liste d'arguments vide
&foo();             # identique
&foo;               # foo() reçoit les arguments courants, comme foo(@_) !
use strict 'subs';
foo;                # comme foo() si sub foo est prédéclaré, sinon
                    # une erreur de compilation
no strict 'subs';
foo;                # comme foo() si sub foo est prédéclaré, sinon
                    # une chaîne littérale "foo"

Non seulement la forme "&" rend la liste d'arguments facultative, mais elle désactive également toute vérification de prototype sur les arguments que vous fournissez. C'est en partie pour des raisons historiques, et en partie pour avoir un moyen pratique de tricher si vous savez ce que vous faites. Voir "Prototypes" ci-dessous.

Depuis Perl 5.16.0, le jeton "__SUB__" est disponible sous use feature 'current_sub' et "use v5.16". Il sera évalué comme une référence au sous-programme en cours d'exécution, ce qui permet des appels récursifs sans connaître le nom de votre sous-programme.

use v5.16;
my $factorial = sub {
    my ($x) = @_;
    return 1 if $x == 1;
    return($x * __SUB__->( $x - 1 ) );
};

Le comportement de "__SUB__" dans un bloc de code regex (tel que "/(?{...})/") est sujet à changement.

Les sous-programmes dont les noms sont entièrement en majuscules sont réservés au cœur de Perl, tout comme les modules dont les noms sont entièrement en minuscules. Un sous-programme en majuscules est une convention peu stricte signifiant qu'il sera appelé indirectement par le système d'exécution lui-même, généralement en raison d'un événement déclenché. Signatures

Perl dispose d'une fonctionnalité pour permettre aux paramètres formels d'un sous-programme d'être déclarés par une syntaxe spéciale, distincte du code procédural du corps du sous-programme. La liste des paramètres formels est connue sous le nom de signature.

Cette fonctionnalité doit être activée avant de pouvoir être utilisée. Elle est activée automatiquement par une déclaration "use v5.36" (ou supérieure), ou plus directement par "use feature 'signatures'", dans la portée actuelle.

La signature fait partie du corps d'un sous-programme. Normalement, le corps d'un sous-programme est simplement un bloc de code entre accolades, mais lorsque vous utilisez une signature, la signature est une liste entre parenthèses qui précède immédiatement le bloc, après le nom ou les attributs éventuels.

Par exemple,

sub foo :lvalue ($x, $y = 1, @z) { .... }

La signature déclare des variables lexicales qui sont dans la portée du bloc. Lorsque le sous-programme est appelé, la signature prend le contrôle en premier. Elle remplit les variables de la signature à partir de la liste d'arguments qui ont été passés. Si la liste d'arguments ne répond pas aux exigences de la signature, une exception sera levée. Lorsque le traitement de la signature est terminé, le contrôle passe au bloc.

Les paramètres positionnels sont gérés en nommant simplement des variables scalaires dans la signature. Par exemple,

sub foo ($left, $right) {
    return $left + $right;
}

prend deux paramètres positionnels, qui doivent être remplis à l'exécution par deux arguments. Par défaut, les paramètres sont obligatoires, et il n'est pas permis de passer plus d'arguments que prévu. Le code ci-dessus est donc équivalent à

sub foo {
    die "Trop d'arguments pour le sous-programme" unless @_ <= 2;
    die "Trop peu d'arguments pour le sous-programme" unless @_ >= 2;
    my $left = $_[0];
    my $right = $_[1];
    return $left + $right;
}

Un argument peut être ignoré en omettant la partie principale du nom d'une déclaration de paramètre, ne laissant qu'un sigil nu "$". Par exemple,

sub foo ($first, $, $third) {
    return "first=$first, third=$third";
}

Bien que l'argument ignoré n'aille dans aucune variable, il est toujours obligatoire pour l'appelant de le passer.

Un paramètre positionnel est rendu facultatif en lui donnant une valeur par défaut, séparée du nom du paramètre par "=":

sub foo ($left, $right = 0) {
    return $left + $right;
}

Le sous-programme ci-dessus peut être appelé avec un ou deux arguments. L'expression de la valeur par défaut est évaluée lors de l'appel du sous-programme, de sorte qu'elle peut fournir différentes valeurs par défaut pour différents appels. Elle n'est évaluée que si l'argument a été réellement omis de l'appel. Par exemple,

my $auto_id = 0;
sub foo ($thing, $id = $auto_id++) {
    print "$thing has ID $id";
}

attribue automatiquement des identifiants séquentiels distincts aux éléments pour lesquels aucun identifiant n'a été fourni par l'appelant. Une expression de valeur par défaut peut également faire référence à des paramètres antérieurs dans la signature, de sorte que la valeur par défaut d'un paramètre varie en fonction des paramètres précédents. Par exemple,

sub foo ($first_name, $surname, $nickname = $first_name) {
    print "$first_name $surname is known as \"$nickname\"";
}

Depuis Perl 5.38, une expression de valeur par défaut peut également être écrite en utilisant l'opérateur "//=", où elle sera évaluée et utilisée si l'appelant a omis une valeur ou si la valeur fournie était "undef".

sub foo ($name //= "world") {
    print "Hello, $name";
}
foo(undef);  # affichera "Hello, world"

De même, depuis Perl 5.38, l'opérateur "||=" peut être utilisé pour fournir une expression par défaut à utiliser chaque fois que l'appelant a fourni une valeur fausse (et rappelez-vous qu'une valeur manquante ou "undef" sont également fausses).

sub foo ($x ||= 10) {
    return 5 + $x;
}

Un paramètre facultatif

ter peut être sans nom, tout comme un paramètre obligatoire. Par exemple,

sub foo ($thing, $ = 1) {
    print $thing;
}

La valeur par défaut du paramètre sera toujours évaluée si l'argument correspondant n'est pas fourni, même si la valeur ne sera stockée nulle part. C'est au cas où son évaluation aurait des effets secondaires importants. Cependant, elle sera évaluée dans un contexte vide, donc si elle n'a pas d'effets secondaires et n'est pas triviale, elle générera un avertissement si la catégorie d'avertissement « void » est activée. Si la valeur par défaut d'un paramètre optionnel sans nom n'est pas importante, elle peut être omise, tout comme le nom du paramètre l'a été :

sub foo ($thing, $=) {
    print $thing;
}

Les paramètres positionnels optionnels doivent venir après tous les paramètres positionnels obligatoires. (S'il n'y a pas de paramètres positionnels obligatoires, les paramètres positionnels optionnels peuvent être la première chose dans la signature.) S'il y a plusieurs paramètres positionnels optionnels et que suffisamment d'arguments ne sont pas fournis pour tous les remplir, ils seront remplis de gauche à droite.

Après les paramètres positionnels, des arguments supplémentaires peuvent être capturés dans un paramètre « slurpy ». La forme la plus simple est juste une variable tableau :

sub foo ($filter, @inputs) {
    print $filter->($_) foreach @inputs;
}

Avec un paramètre « slurpy » dans la signature, il n'y a pas de limite supérieure au nombre d'arguments qui peuvent être passés. Un paramètre tableau « slurpy » peut être sans nom, tout comme un paramètre positionnel, auquel cas son seul effet est de désactiver la limite d'arguments qui s'appliquerait autrement :

sub foo ($thing, @) {
    print $thing;
}

Un paramètre « slurpy » peut au lieu de cela être une table de hachage, auquel cas les arguments qui lui sont disponibles sont interprétés comme des clés et des valeurs alternées. Il doit y avoir autant de clés que de valeurs : s'il y a un argument impair, une exception sera levée. Les clés seront stringifiées, et s'il y a des doublons, l'instance ultérieure prendra la priorité sur la précédente, comme avec la construction normale de table de hachage.

sub foo ($filter, %inputs) {
    print $filter->($_, $inputs{$_}) foreach sort keys %inputs;
}

Un paramètre table de hachage « slurpy » peut être sans nom, tout comme d'autres types de paramètres. Il insiste toujours pour que le nombre d'arguments qui lui sont disponibles soit pair, même s'ils ne sont pas placés dans une variable.

sub foo ($thing, %) {
    print $thing;
}

Un paramètre « slurpy », qu'il soit tableau ou table de hachage, doit être la dernière chose dans la signature. Il peut suivre des paramètres positionnels obligatoires et optionnels ; il peut également être la seule chose dans la signature. Les paramètres « slurpy » ne peuvent pas avoir de valeurs par défaut : si aucun argument ne leur est fourni, vous obtenez un tableau vide ou une table de hachage vide.

Une signature peut être entièrement vide, auquel cas tout ce qu'elle fait est de vérifier que l'appelant n'a passé aucun argument :

sub foo () {
    return 123;
}

Avant Perl 5.36, celles-ci étaient considérées comme expérimentales et émettaient un avertissement dans la catégorie "experimental::signatures". À partir de Perl 5.36, cela ne se produit plus, bien que la catégorie d'avertissement existe toujours pour la compatibilité arrière avec le code qui tente de la désactiver avec une instruction telle que :

no warnings 'experimental::signatures';

Dans l'implémentation Perl actuelle, lors de l'utilisation d'une signature, les arguments sont toujours également disponibles dans la variable tableau spéciale @_. Cependant, y accéder via ce tableau est maintenant déconseillé, et ne doit pas être utilisé dans du nouveau code car cette capacité peut changer dans une version future. Le code qui tente d'accéder au tableau @_ produira des avertissements dans la catégorie "experimental::args_array_with_signatures" lors de la compilation :

sub f ($x) {
    # Cette ligne émet l'avertissement vu ci-dessous
    print "Arguments are @_";
}
Use of @_ in join or string with signatured subroutine is
experimental at ...

Il y a une différence entre les deux façons d'accéder aux arguments : @_ *alias* les arguments, mais les variables de signature obtiennent des *copies* des arguments. Donc écrire dans une variable de signature ne change que cette variable et n'a aucun effet sur les variables de l'appelant, mais écrire dans un élément de @_ modifie ce que l'appelant a utilisé pour fournir cet argument.

Il y a une ambiguïté syntaxique potentielle entre les signatures et les prototypes (voir « Prototypes »), car les deux commencent par une parenthèse ouvrante et les deux peuvent apparaître dans certains des mêmes endroits, comme juste après le nom dans une déclaration de sous-routine. Pour des raisons historiques, lorsque les signatures ne sont pas activées, toute parenthèse ouvrante dans un tel contexte déclenchera une analyse de prototype très indulgente. La plupart des signatures seront interprétées comme des prototypes dans ces circonstances, mais ne seront pas des prototypes valides. (Un prototype valide ne peut pas contenir de caractère alphabétique.) Cela conduira à des messages d'erreur quelque peu déroutants.

Pour éviter toute ambiguïté, lorsque les signatures sont activées, la syntaxe spéciale pour les prototypes est désactivée. Aucune tentative n'est faite pour deviner si un groupe entre parenthèses était destiné à être un prototype ou une signature. Pour donner un prototype à une sous-routine dans ces circonstances, utilisez un attribut de prototype. Par exemple,

sub foo :prototype($) { $_[0] }

Il est tout à fait possible pour une sous-routine d'avoir à la fois un prototype et une signature. Ils remplissent des fonctions différentes : le prototype affecte la compilation des appels à la sous-routine, et la signature place les valeurs des arguments dans des variables lexicales au moment de l'exécution. Vous pouvez donc écrire

sub foo :prototype($$) ($left, $right) {
    return $left + $right;
}

L'attribut de prototype, et tout autre attribut, doit précéder la signature. La signature précède toujours immédiatement le bloc du corps de la sous-routine.

Variables privées via my()

Synopsis :

my $foo;            # déclare $foo local à la portée lexicale
my (@wid, %get);    # déclare une liste de variables locales
my $foo = "flurp";  # déclare $foo lexical et l'initialise
my @oof = @bar;     # déclare @oof lexical et l'initialise
my $x : Foo = $y;   # similaire, avec un attribut appliqué

AVERTISSEMENT : L'utilisation de listes d'attributs sur les déclarations "my" est encore en évolution. Les sémantiques et l'interface actuelles sont susceptibles de changer. Voir attributes et Attribute::Handlers.

L'opérateur "my" déclare que les variables listées sont lexicalement confinées au bloc englobant, à la conditionnelle ("if"/"unless"/"elsif"/"else"), à la boucle ("for"/"foreach"/"while"/"until"/"continue"), à la sous-routine, à l'"eval", ou au fichier "do"/"require"/"use"'d. Si plus d'une valeur est listée, la liste doit être placée entre parenthèses. Tous les éléments listés doivent être des lvalues légales. Seuls les identifiants alphanumériques peuvent être mis en portée lexicale ; les « magical built-ins » comme $/ doivent actuellement être "local"isés avec "local" au lieu de cela pour limiter leur portée dynamiquement.

Contrairement aux variables globales ou de paquetées localisées par l'opérateur "local", les variables lexicales déclarées avec "my" sont totalement cachées du monde extérieur, y compris de toute sous-routine appelée. Ceci est vrai qu'il s'agisse de la même sous-routine appelée depuis elle-même ou ailleurs ; chaque appel obtient sa propre copie.

Cela ne signifie pas qu'une variable "my" déclarée dans une portée lexicale statiquement englobante serait invisible. Seules les portées dynamiques sont coupées. Par exemple, la fonction bumpx() ci-dessous a accès à la variable lexicale $x car le "my" et le "sub" se sont produits dans la même portée, présumablement la portée du fichier.

my $x = 10;
sub bumpx { $x++ }

Un eval(), cependant, peut voir les variables lexicales de la portée dans laquelle il est évalué, tant que les noms ne sont pas masqués par des déclarations dans le eval() lui-même. Voir perlref.

La liste de paramètres de my() peut être assignée si désiré, ce qui permet d'initialiser vos variables. (Si aucun initialiseur n'est donné pour une variable particulière, elle est créée avec la valeur indéfinie.) Couramment, cela est utilisé pour nommer les paramètres d'entrée d'une sous-routine. Exemples :

$arg = "fred";          # variable "globale"
$n = cube_root(27);
print "$arg pense que la racine est $n\n";
# sorties : fred pense que la racine est 3
sub cube_root {
    my $arg = shift;  # le nom n'a pas d'importance
    $arg **= 1/3;
    return $arg;
}

Le "my" est simplement un modificateur sur quelque chose auquel vous pourriez assigner. Donc, lorsque vous assignez des variables dans sa liste d'arguments, "my" ne change pas si ces variables sont vues comme un scalaire ou un tableau. Donc

my ($foo) = <STDIN>;                # INCORRECT ?
my @FOO = <STDIN>;

fournissent tous deux un contexte de liste à la partie droite, tandis que

my $foo = <STDIN>;

fournit un contexte scalaire. Mais ce qui suit déclare une seule variable :

my $foo, $bar = 1;                  # INCORRECT

Cela a le même effet que

my $foo;
$bar = 1;

La variable déclarée n'est pas introduite (n'est pas visible) avant l'instruction actuelle. Ainsi,

my $x = $x;

peut être utilisé pour initialiser un nouveau $x avec la valeur de l'ancien $x, et l'expression

my $x = 123 and $x == 123

est fausse à moins que l'ancien $x n'ait eu la valeur 123.

Les portées lexicales des structures de contrôle ne sont pas précisément délimitées par les accolades qui délimitent leurs blocs contrôlés ; les expressions de contrôle font également partie de cette portée. Ainsi, dans la boucle

while (my $line = <>) {
    $line = lc $line;
} continue {
    print $line;
}

la portée de $line s'étend de sa déclaration à travers le reste de la structure de boucle (y compris la clause "continue"), mais pas au-delà. De même, dans la conditionnelle

if ((my $answer = <STDIN>) =~ /^yes$/i) {
    user_agrees();
} elsif ($answer =~ /^no$/i) {
    user_disagrees();
} else {
    chomp $answer;
    die "'$answer' is neither 'yes' nor 'no'";
}

la portée de $answer s'étend de sa déclaration à la fin de cette condition, y compris toutes les clauses "elsif" et "else", mais pas au-delà. Voir "Simple Statements" dans perlsyn pour des informations sur la portée des variables dans les instructions avec modificateurs.

La boucle "foreach" par défaut définit la portée de sa variable d'index dynamiquement de la manière de "local". Cependant, si la variable d'index est précédée du mot-clé "my", ou s'il existe déjà une portée lexicale portant ce nom, une nouvelle portée lexicale est créée à la place. Ainsi, dans la boucle

for my $i (1, 2, 3) {
    some_function();
}

la portée de $i s'étend jusqu'à la fin de la boucle, mais pas au-delà, rendant la valeur de $i inaccessible dans some_function().

Certains utilisateurs souhaitent peut-être encourager l'utilisation de variables à portée lexicale. Pour aider à détecter les utilisations implicites de variables de paquetage, qui sont toujours globales, si vous écrivez

use strict 'vars';

alors toute variable mentionnée à partir de là jusqu'à la fin du bloc englobant doit soit faire référence à une variable lexicale, soit être prédichée via "our" ou "use vars", soit être entièrement qualifiée avec le nom du paquetage. Sinon, une erreur de compilation se produit. Un bloc interne peut annuler cela avec "no strict 'vars'".

Un "my" a à la fois un effet d'exécution et de compilation. Au moment de la compilation, le compilateur en prend note. L'utilité principale est de supprimer les avertissements de "use strict 'vars'", mais c'est aussi essentiel pour la génération de fermetures comme détaillé dans perlref. L'initialisation réelle est cependant retardée jusqu'à l'exécution, de sorte qu'elle est exécutée au moment approprié, par exemple à chaque passage dans une boucle.

Les variables déclarées avec "my" ne font partie d'aucun paquetage et ne sont donc jamais entièrement qualifiées par le nom du paquetage. En particulier, vous n'êtes pas autorisé à essayer de rendre une variable de paquetage (ou autre globale) lexicale :

my $pack::var;      # ERREUR ! Syntaxe illégale

En fait, une variable de paquetage ou globale est toujours accessible en utilisant la notation "::" entièrement qualifiée, même lorsqu'une variable lexicale du même nom est également visible :

package main;
our $x = 10;
my  $x = 20;
print "$x et $::x\n";

Cela imprimera 20 et 10.

Vous pouvez déclarer des variables "my" au niveau de portée le plus externe d'un fichier pour masquer ces identifiants du monde extérieur à ce fichier. Ceci est similaire dans l'esprit aux variables statiques de C lorsqu'elles sont utilisées au niveau du fichier. Pour ce faire avec une sous-routine, il faut utiliser une fermeture (une fonction anonyme qui accède aux variables lexicales englobantes). Si vous voulez créer une sous-routine privée qui ne peut pas être appelée depuis l'extérieur de ce bloc, elle peut déclarer une variable lexicale contenant une référence à une procédure anonyme :

my $secret_version = '1.001-beta';
my $secret_sub = sub { print $secret_version };
$secret_sub->();

Tant que la référence n'est jamais retournée par une fonction du module, aucun module externe ne peut voir la sous-routine, car son nom ne figure pas dans la table des symboles d'un paquetage. N'oubliez pas qu'elle n'est pas *VRAIMENT* appelée $some_pack::secret_version ou quoi que ce soit ; elle est juste $secret_version, non qualifiée et non qualifiable.

Cependant, cela ne fonctionne pas avec les méthodes d'objets ; toutes les méthodes d'objets doivent être dans la table des symboles d'un paquetage pour être trouvées. Voir "Function Templates" dans perlref pour une solution de contournement.

Variables Privées Persistantes

Il existe deux façons de construire des variables privées persistantes en Perl 5.10. Premièrement, vous pouvez simplement utiliser la fonctionnalité "state". Deuxièmement, vous pouvez utiliser des fermetures, si vous souhaitez rester compatible avec les versions antérieures à 5.10.

Variables persistantes via state()

À partir de Perl 5.10.0, vous pouvez déclarer des variables avec le mot-clé "state" à la place de "my". Pour que cela fonctionne, cependant, vous devez avoir activé cette fonctionnalité au préalable, soit en utilisant le pragmatique "feature", soit en utilisant "-E" sur les one-liners (voir feature). À partir de Perl 5.16, la forme "CORE::state" ne nécessite pas le pragmatique "feature".

Le mot-clé "state" crée une variable lexicale (suivant les mêmes règles de portée que "my") qui persiste d'un appel de sous-routine à l'autre. Si une variable d'état réside à l'intérieur d'une sous-routine anonyme, alors chaque copie de la sous-routine a sa propre copie de la variable d'état. Cependant, la valeur de la variable d'état persistera entre les appels à la même copie de la sous-routine anonyme. (N'oubliez pas que "sub { ... }" crée une nouvelle sous-routine chaque fois qu'elle est exécutée.)

Par exemple, le code suivant maintient un compteur privé, incrémenté chaque fois que la fonction gimme_another() est appelée :

use feature 'state';
sub gimme_another { state $x; return ++$x }

Et cet exemple utilise des sous-routines anonymes pour créer des compteurs séparés :

use feature 'state';
sub create_counter {
    return sub { state $x; return ++$x }
}

De plus, comme $x est lexical, il ne peut pas être atteint ou modifié par du code Perl extérieur.

Lorsqu'il est combiné avec la déclaration de variables, une simple affectation aux variables "state" (comme dans "state $x = 42") n'est exécutée que la première fois. Lorsque de telles instructions sont évaluées lors d'évaluations ultérieures, l'affectation est ignorée. Le comportement d'affectation aux déclarations "state" où le côté gauche de l'affectation implique des parenthèses est actuellement indéfini.

Variables persistantes avec fermetures

Ce n'est pas parce qu'une variable lexicale a une portée lexicale (également appelée statique) sur son bloc englobant, "eval", ou "do" FILE, qu'elle fonctionne comme un static C à l'intérieur d'une fonction. Elle fonctionne normalement davantage comme un auto C, mais avec une gestion automatique de la mémoire.

Contrairement aux variables locales en C ou C++, les variables lexicales de Perl ne sont pas nécessairement recyclées simplement parce que leur portée est terminée. Si quelque chose de plus permanent est toujours conscient de la variable lexicale, elle persistera. Tant que quelque chose d'autre fait référence à une variable lexicale, cette variable lexicale ne sera pas libérée – comme il se doit. Vous ne voudriez pas que la mémoire soit libérée tant que vous ne l'avez pas utilisée, ou qu'elle soit conservée une fois que vous avez terminé. La gestion automatique de la mémoire s'en charge pour vous.

Cela signifie que vous pouvez renvoyer ou sauvegarder des références à des variables lexicales, alors qu'il est une grave erreur de retourner un pointeur vers un auto C. Cela nous donne également un moyen de simuler les statics de fonction C. Voici un mécanisme pour donner à une fonction des variables privées avec une portée lexicale et une durée de vie statique. Si vous voulez créer quelque chose comme les variables statiques C, il suffit d'englober toute la fonction dans un bloc supplémentaire, et de placer la variable statique en dehors de la fonction mais dans le bloc.

{
    my $secret_val = 0;
    sub gimme_another {
        return ++$secret_val;
    }
}
# $secret_val devient alors inaccessible au monde extérieur,
# mais conserve sa valeur entre les appels à gimme_another

Si cette fonction est sourcée à partir d'un fichier distinct via "require" ou "use", alors c'est probablement très bien. Si elle est entièrement dans le programme principal, vous devrez faire en sorte que le "my" soit exécuté tôt, soit en plaçant tout le bloc au-dessus de votre programme principal, soit, plus probablement, en y plaçant simplement un bloc de code "BEGIN" autour pour vous assurer qu'il est exécuté avant que votre programme ne commence à s'exécuter :

BEGIN {
    my $secret_val = 0;
    sub gimme_another {
        return ++$secret_val;
    }
}

Voir "BEGIN, UNITCHECK, CHECK, INIT and END" dans perlmod concernant les blocs de code déclenchés spéciaux, "BEGIN", "UNITCHECK", "CHECK", "INIT" et "END".

Si elles sont déclarées à la portée la plus externe (la portée du fichier), alors les variables lexicales fonctionnent un peu comme les statiques de fichier C. Elles sont disponibles pour toutes les fonctions de ce même fichier déclarées en dessous, mais sont inaccessibles de l'extérieur de ce fichier. Cette stratégie est parfois utilisée dans les modules pour créer des variables privées que l'ensemble du module peut voir.

Valeurs Temporaires via local()

ATTENTION : En général, vous devriez utiliser "my" au lieu de "local", car c'est plus rapide et plus sûr. Les exceptions incluent les variables de ponctuation globales, les descripteurs de fichiers et les formats globaux, ainsi que la manipulation directe de la table des symboles de Perl elle-même. "local" est principalement utilisé lorsque la valeur actuelle d'une variable doit être visible par les sous-routines appelées.

Synopsis :

# localisation des valeurs
local $foo;                # rend $foo dynamiquement local
local (@wid, %get);        # rend la liste de variables locale
local $foo = "flurp";      # rend $foo dynamique, et l'initialise
local @oof = @bar;         # rend @oof dynamique, et l'initialise
local $hash{key} = "val";  # définit une valeur locale pour cette entrée de hash
delete local $hash{key};   # supprime cette entrée pour le bloc actuel
local ($cond ? $v1 : $v2); # plusieurs types de lvalues supportent
                           # la localisation
# localisation des symboles
local *FH;                 # localise $FH, @FH, %FH, &FH  ...
local *merlyn = *randal;   # maintenant $merlyn est vraiment $randal, plus
                           #     @merlyn est vraiment @randal, etc
local *merlyn = 'randal';  # MÊME CHOSE : promeut 'randal' en *randal
local *merlyn = \$randal;  # aliase juste $merlyn, pas @merlyn etc

Un "local" modifie ses variables listées pour qu'elles soient "locales" au bloc englobant, "eval", ou "do FILE" – et à *toute sous-routine* *appelée

MODIFICATION LVALUE

Dans le contexte de Perl, une « lvalue » est une expression qui peut apparaître du côté gauche d'une affectation, ou une expression qui peut être la cible d'une opération qui modifie sa valeur. Par exemple, dans 

 $foo = 1;
$foo est une lvalue, mais 1 ne l'est pas.

Les lvalues peuvent être des variables scalaires, des tableaux, des hashs, des éléments de tableaux ou de hashs, des éléments de slices, des références, des appelants de sous-routines qui retournent des lvalues, et certaines valeurs spéciales comme $_.

Il est possible de localiser des lvalues comme des variables normales. Cependant, il y a une différence subtile entre la localisation d'une variable et la localisation d'un membre d'une lvalue.

Quand vous localisez une variable (par exemple, local $foo), Perl sauvegarde la valeur de la variable globale $foo et crée une nouvelle variable locale qui n'est visible qu'à l'intérieur du bloc courant. Quand le bloc se termine, la valeur sauvegardée est restaurée.

Quand vous localisez un membre d'une lvalue (par exemple, local $array[0] ou local $hash{key}), Perl sauvegarde la valeur de ce membre spécifique et fait en sorte que toute référence ultérieure à ce membre dans le bloc courant fasse référence à une nouvelle valeur, sans affecter la variable globale originale. Quand le bloc se termine, la valeur sauvegardée est restaurée.

Cette distinction est importante car elle affecte le comportement des opérations comme delete. Si vous localisez une variable scalaire qui contient une référence à une lvalue, la localisation ne s'appliquera qu'à la référence elle-même, pas à l'lvalue qu'elle désigne.

local

L'opérateur "local" est utilisé pour créer des variables à portée dynamique. Quand vous déclarez une variable avec "local" à l'intérieur d'un bloc, la valeur originale de cette variable (si elle existe) est sauvegardée, et la variable prend une nouvelle valeur locale pour la durée de ce bloc. Quand le bloc se termine, la valeur originale est restaurée.

Il est important de comprendre que "local" ne crée pas de nouvelle variable au sens lexical. Il affecte la valeur d'une variable existante (généralement une variable globale ou de package) uniquement pour la durée du bloc où "local" est utilisé. C'est ce qu'on appelle la portée dynamique.

La portée lexicale, qui crée de véritables variables locales qui n'existent que dans le bloc, est obtenue avec "my", qui fonctionne de manière similaire aux déclarations `auto` en C.

Certains types de lvalues peuvent également être localisés : les éléments de hashs et de tableaux, ainsi que leurs slices, les conditionnelles (à condition que leur résultat soit toujours localisable), et les références symboliques. Comme pour les variables simples, cela crée de nouvelles valeurs à portée dynamique.

Si plusieurs variables ou expressions sont fournies à "local", elles doivent être placées entre parenthèses. Cet opérateur fonctionne en sauvegardant les valeurs actuelles des variables listées dans sa liste d'arguments sur une pile cachée et en les restaurrant à la sortie du bloc, de la sous-routine ou de l'éval. Cela signifie que les sous-routines appelées peuvent également référencer la variable locale, mais pas la variable globale. La liste d'arguments peut être assignée si désiré, ce qui permet d'initialiser vos variables locales. (Si aucun initialiseur n'est donné pour une variable particulière, elle est créée avec une valeur indéfinie.)

Comme "local" est un opérateur d'exécution, il est exécuté à chaque passage dans une boucle. Par conséquent, il est plus efficace de localiser vos variables en dehors de la boucle.

Note grammaticale sur local()

Un "local" est simplement un modificateur sur une expression lvalue. Lorsque vous assignez à une variable "local"isée, le "local" ne change pas la façon dont sa liste est vue, que ce soit comme un scalaire ou un tableau. Ainsi

local($foo) = <STDIN>;
local @FOO = <STDIN>;

fournissent tous deux un contexte de liste à la partie droite, tandis que

local $foo = <STDIN>;

fournit un contexte scalaire.

Localisation des variables spéciales

Si vous localisez une variable spéciale, vous lui donnerez une nouvelle valeur, mais sa magie ne disparaîtra pas. Cela signifie que tous les effets secondaires liés à cette magie continueront de fonctionner avec la valeur localisée.

Cette fonctionnalité permet au code comme celui-ci de fonctionner :

# Lire tout le contenu de FILE dans $slurp
{ local $/ = undef; $slurp = <FILE>; }

Notez cependant que cela restreint la localisation de certaines valeurs ; par exemple, l'instruction suivante échoue, depuis Perl 5.10.0, avec une erreur Modification d'une valeur en lecture seule tentée, car la variable $1 est magique et en lecture seule :

local $1 = 2;

Une exception est la variable scalaire par défaut : à partir de Perl 5.14, local($_) retirera toujours toute magie de $_, afin de permettre une réutilisation sûre de $_ dans une sous-routine.

ATTENTION : La localisation des tableaux et hashs liés ne fonctionne actuellement pas comme décrit. Cela sera corrigé dans une future version de Perl ; en attendant, évitez le code qui repose sur un comportement particulier de localisation de tableaux ou hashs liés (la localisation des éléments individuels est toujours acceptable). Voir « Localising Tied Arrays and Hashes Is Broken » dans perl58delta pour plus de détails.

Localisation des globs

La construction

local *name;

crée une nouvelle entrée de table de symboles pour le glob "name" dans le package courant. Cela signifie que toutes les variables dans son slot de glob ( $name, @name, %name, &name, et le handle de fichier "name") sont dynamiquement réinitialisées.

Cela implique, entre autres, que toute magie éventuellement portée par ces variables est localement perdue. En d'autres termes, dire "local */" n'aura aucun effet sur la valeur interne du séparateur d'enregistrements d'entrée.

Localisation des éléments de types composites

Il vaut également la peine de prendre un moment pour expliquer ce qui se passe lorsque vous "local"isez un membre d'un type composite (c'est-à-dire un élément de tableau ou de hash). Dans ce cas, l'élément est "local"isé *par nom*. Cela signifie que lorsque la portée du local() se termine, la valeur sauvegardée sera restaurée dans l'élément de hash dont la clé a été nommée dans le local(), ou l'élément de tableau dont l'index a été nommé dans le local(). Si cet élément a été supprimé pendant que le local() était en vigueur (par exemple, par un delete() d'un hash ou un shift() d'un tableau), il réapparaîtra, étendant éventuellement un tableau et remplissant les éléments sautés avec "undef". Par exemple, si vous dites

%hash = ( 'This' => 'is', 'a' => 'test' );
@ary  = ( 0..5 );
{
    local($ary[5]) = 6;
    local($hash{'a'}) = 'drill';
    while (my $e = pop(@ary)) {
        print "$e . . .\n";
        last unless $e > 3;
    }
    if (@ary) {
        $hash{'only a'} = 'test';
        delete $hash{'a'};
    }
}
print join(' ', map { "$_ $hash{$_}" } sort keys %hash),".\n";
print "The array has ",scalar(@ary)," elements: ",
    join(', ', map { defined $_ ? $_ : 'undef' } @ary),"\n";

Perl affichera

6 . . .
4 . . .
3 . . .
This is a test only a test.
The array has 6 elements: 0, 1, 2, undef, undef, 5

Le comportement de local() sur les membres inexistants de types composites est sujet à modification dans le futur. Le comportement de local() sur les éléments de tableaux spécifiés à l'aide d'index négatifs est particulièrement surprenant, et susceptible de changer.

Suppression localisée des éléments de types composites

Vous pouvez utiliser les constructions "delete local $array[$idx]" et "delete local $hash{key}" pour supprimer une entrée de type composite pour le bloc courant et la restaurer à sa fin. Elles retournent la valeur du tableau/hash avant la localisation, ce qui signifie qu'elles sont respectivement équivalentes à

do {
    my $val = $array[$idx];
    local  $array[$idx];
    delete $array[$idx];
    $val
}

et

do {
    my $val = $hash{key};
    local  $hash{key};
    delete $hash{key};
    $val
}

sauf que pour celles-ci, le "local" est limité au bloc "do". Les slices sont également acceptées.

my %hash = (
    a => [ 7, 8, 9 ],
    b => 1,
)
{
    my $x = delete local $hash{a};
    # $x est [ 7, 8, 9 ]
    # %hash est (b => 1)
    {
        my @nums = delete local @$x[0, 2]
        # @nums est (7, 9)
        # $x est [ undef, 8 ]
        $x[0] = 999; # sera effacé quand la portée se terminera
    }
    # $x est de retour à [ 7, 8, 9 ]
}
# %hash est de retour à son état d'origine

Cette construction est prise en charge depuis Perl v5.12.

Sous-routines Lvalue

Il est possible de retourner une valeur modifiable d'une sous-routine. Pour ce faire, vous devez déclarer que la sous-routine retourne une lvalue.

my $val;
sub canmod : lvalue {
    $val;  # ou :  return $val;
}
sub nomod {
    $val;
}
canmod() = 5;   # assigne à $val
nomod()  = 5;   # ERREUR

Le contexte scalaire/liste pour la sous-routine et pour la partie droite de l'affectation est déterminé comme si l'appel de sous-routine était remplacé par un scalaire. Par exemple, considérons :

data(2,3) = get_data(3,4);

Les deux sous-routines ici sont appelées dans un contexte scalaire, tandis que dans :

(data(2,3)) = get_data(3,4);

et dans :

(data(2),data(3)) = get_data(3,4);

toutes les sous-routines sont appelées dans un contexte de liste.

Les sous-routines lvalue sont pratiques, mais vous devez garder à l'esprit que, lorsqu'elles sont utilisées avec des objets, elles peuvent violer l'encapsulation. Un mutateur normal peut vérifier l'argument fourni avant de définir l'attribut qu'il protège, une sous-routine lvalue ne le peut pas. Si vous avez besoin d'un traitement spécial lors de la récupération et de la définition des valeurs, envisagez d'utiliser le module CPAN Sentinel ou quelque chose de similaire.

Sous-routines Lexicales

Depuis Perl 5.18, vous pouvez déclarer une sous-routine privée avec "my" ou "state". Comme pour les variables d'état, le mot-clé "state" n'est disponible que sous "use feature 'state'" ou "use v5.10" ou supérieur.

Avant Perl 5.26, les sous-routines lexicales étaient considérées comme expérimentales et n'étaient disponibles que sous le pragma "use feature 'lexical_subs'". Elles produisaient également un avertissement sauf si la catégorie d'avertissement "experimental::lexical_subs" était désactivée.

Ces sous-routines ne sont visibles qu'à l'intérieur du bloc dans lequel elles sont déclarées, et seulement après cette déclaration :

# Inclure ces deux lignes si votre code est destiné à être exécuté sous des versions de Perl
# antérieures à 5.26.
no warnings "experimental::lexical_subs";
use feature 'lexical_subs';
foo();              # appelle la sous-routine de package/globale
state sub foo {
    foo();          # appelle aussi la sous-routine de package
}
foo();              # appelle la sous-routine "state"
my $ref = \&foo;    # prend une référence à la sous-routine "state"
my sub bar { ... }
bar();              # appelle la sous-routine "my"

Vous ne pouvez pas (directement) écrire une sous-routine lexicale récursive :

# INCORRECT
my sub baz {
    baz();
}

Cet exemple échoue car baz() fait référence à la sous-routine de package/globale "baz", et non à la sous-routine lexicale en cours de définition.

La solution est d'utiliser "__SUB__" :

my sub baz {
    __SUB__->();    # s'appelle elle-même
}

Il est possible de prédéclarer une sous-routine lexicale. La syntaxe de définition de sous-routine "sub foo {...}" respecte toute déclaration précédente "my sub;" ou "state sub;". Utiliser ceci pour définir des sous-routines récursives est cependant une mauvaise idée :

my sub baz;         # prédéclaration
sub baz {           # définit la sous-routine "my"
    baz();          # INCORRECT : s'appelle elle-même, mais fuit de la mémoire
}

Tout comme "my $f; $f = sub { $f->() }", cet exemple fuit de la mémoire. Le nom "baz" est une référence à la sous-routine, et la sous-routine utilise le nom "baz" ; elles se maintiennent mutuellement en vie (voir « Circular References » dans perlref).

"state sub" vs

« mon sub »

Quelle est la différence entre les sous-programmes « state » et les sous-programmes « my » ? Chaque fois que l'exécution entre dans un bloc lorsque les sous-programmes « my » sont déclarés, une nouvelle copie de chaque sous-programme est créée. Les sous-programmes « state » persistent d'une exécution du bloc conteneur à la suivante.

Donc, en général, les sous-programmes « state » sont plus rapides. Mais les sous-programmes « my » sont nécessaires si vous voulez créer des fermetures :

sub whatever {
    my $x = shift;
    my sub inner {
        ... faire quelque chose avec $x ...
    }
    inner();
}

Dans cet exemple, un nouveau $x est créé lorsque "whatever" est appelé, ainsi qu'un nouveau "inner", qui peut voir le nouveau $x. Un sous-programme « state » ne verra que le $x du premier appel à "whatever".

« our » sous-programmes

Comme "our $variable", "our sub" crée un alias lexical du sous-programme du package du même nom.

Les deux utilisations principales sont de revenir à l'utilisation du sous-programme du package à l'intérieur d'une portée interne :

sub foo { ... }
sub bar {
    my sub foo { ... }
    {
        # besoin d'utiliser le foo externe ici
        our sub foo;
        foo();
    }
}

et de rendre un sous-programme visible aux autres packages dans la même portée :

package MySneakyModule;
our sub do_something { ... }
sub do_something_with_caller {
    package DB;
    () = caller 1;          # définit @DB::args
    do_something(@args);    # utilise MySneakyModule::do_something
}

Passation des entrées de table des symboles (typeglobs)

AVERTISSEMENT : Le mécanisme décrit dans cette section était initialement le seul moyen de simuler le passage par référence dans les anciennes versions de Perl. Bien qu'il fonctionne toujours bien dans les versions modernes, le nouveau mécanisme de référence est généralement plus facile à utiliser. Voir ci-dessous.

Parfois, vous ne voulez pas passer la valeur d'un tableau à un sous-programme, mais plutôt son nom, afin que le sous-programme puisse modifier la copie globale de celui-ci plutôt que de travailler avec une copie locale. En Perl, vous pouvez faire référence à tous les objets d'un nom particulier en faisant précéder le nom d'une étoile : *foo. Ceci est souvent connu sous le nom de « typeglob », car l'étoile au début peut être considérée comme une correspondance générique pour tous les caractères préfixes étranges des variables, sous-programmes, etc.

Lors de son évaluation, le typeglob produit une valeur scalaire qui représente tous les objets de ce nom, y compris tout descripteur de fichier, format ou sous-programme. Lors de l'affectation, il fait en sorte que le nom mentionné fasse référence à la valeur « * » qui lui a été attribuée. Exemple :

sub doubleary {
    local(*someary) = @_;
    foreach $elem (@someary) {
        $elem *= 2;
    }
}
doubleary(*foo);
doubleary(*bar);

Les scalaires sont déjà passés par référence, vous pouvez donc modifier les arguments scalaires sans utiliser ce mécanisme en faisant référence explicitement à $_[0] etc. Vous pouvez modifier tous les éléments d'un tableau en passant tous les éléments comme scalaires, mais vous devez utiliser le mécanisme « * » (ou le mécanisme de référence équivalent) pour « push », « pop », ou changer la taille d'un tableau. Il sera certainement plus rapide de passer le typeglob (ou la référence).

Même si vous ne voulez pas modifier un tableau, ce mécanisme est utile pour passer plusieurs tableaux dans une seule LISTE, car normalement le mécanisme LIST fusionne toutes les valeurs de tableau de sorte que vous ne pouvez pas extraire les tableaux individuels. Pour en savoir plus sur les typeglobs, voir « Typeglobs and Filehandles » dans perldata.

Quand utiliser encore local()

Malgré l'existence de « my », il existe encore trois situations où l'opérateur « local » brille toujours. En fait, dans ces trois situations, vous *devez* utiliser « local » au lieu de « my ».

1.
Vous devez donner une valeur temporaire à une variable globale, en particulier $_.

Les variables globales, comme @ARGV ou les variables de ponctuation, doivent être « local »isées avec local(). Ce bloc lit /etc/motd, et le divise en morceaux séparés par des lignes d'égal, qui sont placés dans @Fields.

{
    local @ARGV = ("/etc/motd");
    local $/ = undef;
    local $_ = <>;
    @Fields = split /^\s*=+\s*$/;
}

En particulier, il est important de « local »iser $_ dans toute routine qui lui affecte une valeur. Faites attention aux affectations implicites dans les conditions « while ».

2.
Vous devez créer un descripteur de fichier ou de répertoire local ou une fonction locale.

Une fonction qui a besoin de son propre descripteur de fichier doit utiliser local() sur un typeglob complet. Ceci peut être utilisé pour créer de nouvelles entrées de table des symboles :

sub ioqueue {
    local  (*READER, *WRITER);    # pas my !
    pipe    (READER,  WRITER)     or die "pipe: $!";
    return (*READER, *WRITER);
}
($head, $tail) = ioqueue();

Voir le module Symbol pour une façon de créer des entrées de table des symboles anonymes.

Comme l'affectation d'une référence à un typeglob crée un alias, cela peut être utilisé pour créer ce qui est effectivement une fonction locale, ou du moins, un alias local.

{
    local *grow = \&shrink; # seulement jusqu'à la sortie de ce bloc
    grow();                # appelle réellement shrink()
    move();                # si move() grow(), il shrink() aussi
}
grow();                    # récupère à nouveau le vrai grow()

Voir « Function Templates » dans perlref pour en savoir plus sur la manipulation des fonctions par nom de cette manière.

3.
Vous voulez changer temporairement un seul élément d'un tableau ou d'une hash.

Vous pouvez « local »iser juste un élément d'un agrégat. Habituellement, cela se fait sur les dynamiques :

{
    local $SIG{INT} = 'IGNORE';
    funct();                            # ininterrompible
}
# l'interruptibilité est automatiquement restaurée ici

Mais cela fonctionne également sur les agrégats déclarés lexicalement.

Passage par Référence

Si vous voulez passer plusieurs tableaux ou hashes à une fonction - ou en retourner - et qu'ils conservent leur intégrité, alors vous allez devoir utiliser un passage par référence explicite. Avant de faire cela, vous devez comprendre les références comme détaillé dans perlref. Cette section pourrait ne pas avoir beaucoup de sens pour vous autrement.

Voici quelques exemples simples. D'abord, passons plusieurs tableaux à une fonction et faisons-la « pop » tous, retournant une nouvelle liste de tous leurs anciens derniers éléments :

@tailings = popmany ( \@w, \@x, \@y, \@z );
sub popmany {
    my $aref;
    my @retlist;
    foreach $aref ( @_ ) {
        push @retlist, pop @$aref;
    }
    return @retlist;
}

Voici comment vous pourriez écrire une fonction qui retourne une liste de clés qui se produisent dans tous les hashes qui lui sont passés :

@common = inter( \%foo, \%bar, \%joe );
sub inter {
    my ($k, $href, %seen); # locals
    foreach $href (@_) {
        while ( $k = each %$href ) {
            $seen{$k}++;
        }
    }
    return grep { $seen{$_} == @_ } keys %seen;
}

Jusqu'à présent, nous utilisons uniquement le mécanisme de retour de liste normal. Que se passe-t-il si vous voulez passer ou retourner un hash ? Eh bien, si vous n'en utilisez qu'un, ou si vous ne vous souciez pas de leur concaténation, alors la convention d'appel normale est acceptable, bien qu'un peu coûteuse.

Là où les gens ont des problèmes, c'est ici :

    (@w, @x) = func(@y, @z);
ou
    (%w, %x) = func(%y, %z);

Cette syntaxe ne fonctionnera tout simplement pas. Elle ne définit que @w ou %w et efface @x ou %x. De plus, la fonction n'a pas reçu deux tableaux ou hashes séparés : elle a reçu une longue liste dans @_, comme toujours.

Si vous pouvez organiser pour que tout le monde gère cela via des références, le code est plus propre, bien que moins agréable à regarder. Voici une fonction qui prend deux références de tableau comme arguments, renvoyant les deux éléments de tableau dans l'ordre de leur nombre d'éléments : 

($wref, $xref) = func(\@y, \@z);
print "@$wref a plus que @$xref\n";
sub func {
    my ($yref, $zref) = @_;
    if (@$yref > @$zref) {
        return ($yref, $zref);
    } else {
        return ($zref, $yref);
    }
}

Il s'avère que vous pouvez réellement faire cela aussi :

(*w, *x) = func(\@y, \@z);
print "@w a plus que @x\n";
sub func {
    local (*y, *z) = @_;
    if (@y > @z) {
        return (\@y, \@z);
    } else {
        return (\@z, \@y);
    }
}

Ici, nous utilisons les typeglobs pour faire de l'aliasing de table des symboles. C'est un peu subtil, et cela ne fonctionnera pas non plus si vous utilisez des variables « my », car seules les variables globales (même déguisées en « local ») sont dans la table des symboles.

Si vous transmettez des descripteurs de fichier, vous pourriez généralement utiliser simplement le typeglob nu, comme *STDOUT, mais les références de typeglob fonctionnent également. Par exemple :

splutter(\*STDOUT);
sub splutter {
    my $fh = shift;
    print $fh "her um well a hmmm\n";
}
$rec = get_rec(\*STDIN);
sub get_rec {
    my $fh = shift;
    return scalar <$fh>;
}

Si vous prévoyez de générer de nouveaux descripteurs de fichier, vous pourriez faire ceci. Notez qu'il faut renvoyer le typeglob nu *FH, pas sa référence.

sub openit {
    my $path = shift;
    local *FH;
    return open (FH, $path) ? *FH : undef;
}

Prototypes

Perl prend en charge un type très limité de vérification d'arguments au moment de la compilation en utilisant les prototypes de fonction. Cela peut être déclaré dans la section PROTO ou avec un attribut prototype. Si vous déclarez l'un des deux :

sub mypush (\@@)
sub mypush :prototype(\@@)

alors mypush() prend des arguments exactement comme le fait push().

Si la signature du sous-programme

s sont activées (voir "Signatures"), alors la syntaxe PROTO plus courte n'est pas disponible, car elle entrerait en conflit avec les signatures. Dans ce cas, un prototype ne peut être déclaré que sous la forme d'un attribut.

La déclaration de fonction doit être visible au moment de la compilation. Le prototype affecte uniquement l'interprétation des appels réguliers à la fonction, où régulier est défini comme n'utilisant pas le sigil &. En d'autres termes, si vous l'appelez comme une fonction intégrée, alors elle se comporte comme une fonction intégrée. Si vous l'appelez comme une sous-routine à l'ancienne (perl4), alors elle se comporte comme une sous-routine à l'ancienne. Il découle naturellement de cette règle que les prototypes n'ont aucune influence sur les références de sous-routines comme &foo ou sur les appels de sous-routines indirects comme &{$subref}() ou $subref->().

Les appels de méthode ne sont pas non plus influencés par les prototypes, car la fonction à appeler est indéterminée au moment de la compilation, le code exact appelé dépendant de l'héritage.

L'objectif de cette fonctionnalité étant principalement de vous permettre de définir des sous-routines qui fonctionnent comme des fonctions intégrées, voici des prototypes pour d'autres fonctions qui s'analysent presque exactement comme les fonctions intégrées correspondantes.

Chaque caractère de prototype précédé d'une barre oblique inverse représente un argument réel qui doit commencer par ce caractère (éventuellement précédé de "my", "our" ou "local"), à l'exception de "$", qui acceptera toute expression lvalue scalaire, telle que "$foo = 7" ou "my_function()->[0]". La valeur passée dans @_ sera une référence à l'argument réel donné dans l'appel de sous-routine, obtenue en appliquant "\" à cet argument.

Vous pouvez utiliser la notation de groupe de barres obliques inverses "\[]" pour spécifier plus d'un type d'argument autorisé. Par exemple :

sub myref (\[$@%&*])

permettra d'appeler myref() comme suit :

myref $var
myref @array
myref %hash
myref &sub
myref *glob

et le premier argument de myref() sera une référence à un scalaire, un tableau, une table de hachage, une sous-routine ou un glob.

Les caractères de prototype non précédés d'une barre oblique inverse ont des significations spéciales. Tout "@" ou "%" non précédé d'une barre oblique inverse consomme tous les arguments restants et force le contexte de liste. Un argument représenté par "$" force le contexte scalaire. Un "&" exige une sous-routine anonyme qui, si elle est passée comme premier argument, peut ressembler à un bloc nu : elle ne nécessite pas le mot-clé "sub" ni une virgule suivante.

Un "*" permet à la sous-routine d'accepter un bareword, une constante, une expression scalaire, un typeglob, ou une référence à un typeglob dans cet emplacement. La valeur sera disponible pour la sous-routine soit comme un simple scalaire, soit (dans les deux derniers cas) comme une référence au typeglob. Si vous souhaitez toujours convertir ces arguments en une référence de typeglob, utilisez Symbol::qualify_to_ref() comme suit :

use Symbol 'qualify_to_ref';
sub foo (*) {
    my $fh = qualify_to_ref(shift, caller);
    ...
}

Le prototype "+" est une alternative spéciale à "$" qui agira comme "\[@%]" lorsqu'elle recevra une variable de tableau ou de table de hachage littérale, mais forcera par ailleurs le contexte scalaire sur l'argument. Ceci est utile pour les fonctions qui devraient accepter soit un tableau littéral, soit une référence de tableau comme argument :

sub mypush (+@) {
    my $aref = shift;
    die "Pas un tableau ou une référence de tableau" unless ref $aref eq 'ARRAY';
    push @$aref, @_;
}

Lors de l'utilisation du prototype "+", votre fonction doit vérifier que l'argument est d'un type acceptable.

Un point-virgule (";") sépare les arguments obligatoires des arguments optionnels. Il est redondant avant "@" ou "%", qui consomment tout le reste.

Comme dernier caractère d'un prototype, ou juste avant un point-virgule, un "@" ou un "%", vous pouvez utiliser "_" à la place de "$" : si cet argument n'est pas fourni, $_ sera utilisé à la place.

L'objectif principal du mécanisme actuel est de permettre aux auteurs de modules de fournir de meilleurs diagnostics aux utilisateurs de modules. L'avertissement pourra être mis à niveau vers une erreur fatale dans une future version de Perl une fois que la majorité du code fautif sera corrigée.

Il est probablement préférable de prototyper les nouvelles fonctions, et non de rétro-équiper les anciennes. En effet, vous devez être particulièrement attentif aux impositions silencieuses de contextes de liste et scalaire différents. Par exemple, si vous décidez qu'une fonction ne doit accepter qu'un seul paramètre, comme ceci :

Inlining Subroutines

Inlining is the process of substituting a subroutine call with the body of the subroutine itself. Perl does this automatically for subroutines that meet certain criteria, primarily subroutines that have a "()" prototype and whose bodies consist of a single expression. The primary advantage of inlining is speed, as it eliminates the overhead of a subroutine call.

However, inlining can sometimes have side effects that you might not expect. For example, inlining a subroutine that returns a lexically-scoped variable can cause that variable to be captured by the inlined code, and subsequent modifications to the variable might not be reflected when the subroutine is called. This is because the inlined code is essentially a copy of the subroutine body at compile time, and it might capture the value of the variable at that specific moment.

To illustrate, consider the following code:

sub baz_val () {
    if (OPT_BAZ) {
        return 23;
    }
    else {
        return 42;
    }
}
sub bonk_val () { return 12345 }

In this example, both baz_val and bonk_val have "()" prototypes and consist of single expressions. Therefore, they are candidates for inlining. If OPT_BAZ is true, baz_val will effectively be replaced with return 23;. If OPT_BAZ is false, it will be replaced with return 42;.

You can prevent a subroutine from being inlined by using an explicit "return" statement, even if the subroutine body is otherwise eligible for inlining. This is because the explicit "return" changes the structure of the subroutine's body in a way that prevents automatic inlining.

As alluded to earlier you can also declare inlined subs dynamically at BEGIN time if their body consists of a lexically-scoped scalar which has no other references. Only the first example here will be inlined:

BEGIN {
    my $var = 1;
    no strict 'refs';
    *INLINED = sub () { $var };
}
BEGIN {
    my $var = 1;
    my $ref = \$var;
    no strict 'refs';
    *NOT_INLINED = sub () { $var };
}

A not so obvious caveat with this (see [RT #79908]) is what happens if the variable is potentially modifiable. For example:

BEGIN {
    my $x = 10;
    *FOO = sub () { $x };
    $x++;
}
print FOO(); # printed 10 prior to 5.32.0

From Perl 5.22 onwards this gave a deprecation warning, and from Perl 5.32 onwards it became a run-time error. Previously the variable was immediately inlined, and stopped behaving like a normal lexical variable; so it printed 10, not 11.

If you still want such a subroutine to be inlined (with no warning), make sure the variable is not used in a context where it could be modified aside from where it is declared.

# Fine, no warning
BEGIN {
    my $x = 54321;
    *INLINED = sub () { $x };
}
# Error
BEGIN {
    my $x;
    $x = 54321;
    *ALSO_INLINED = sub () { $x };
}

Perl 5.22 also introduced the "const" attribute as an alternative. It was initially experimental, but made stable in Perl 5.40. When applied to an anonymous subroutine, it forces the sub to be called when the "sub" expression is evaluated. The return value is captured and turned into a constant subroutine:

my $x = 54321;
*INLINED = sub : const { $x };
$x++;

The return value of "INLINED" in this example will always be 54321, regardless of later modifications to $x. You can also put any arbitrary code inside the sub, at it will be executed immediately and its return value captured the same way.

If you really want a subroutine with a "()" prototype that returns a lexical variable you can easily force it to not be inlined by adding an explicit "return":

BEGIN {
    my $x = 10;
    *FOO = sub () { return $x };
    $x++;
}
print FOO(); # prints 11

The easiest way to tell if a subroutine was inlined is by using B::Deparse. Consider this example of two subroutines returning 1, one with a "()" prototype causing it to be inlined, and one without (with deparse output truncated for clarity):

$ perl -MO=Deparse -e 'sub ONE { 1 } if (ONE) { print ONE if ONE }'
sub ONE {
    1;
}
if (ONE ) {
    print ONE() if ONE ;
}
$ perl -MO=Deparse -e 'sub ONE () { 1 } if (ONE) { print ONE if ONE }'
sub ONE () { 1 }
do {
    print 1
};

If you redefine a subroutine that was eligible for inlining, you'll get a warning by default. You can use this warning to tell whether or not a particular subroutine is considered inlinable, since it's different than the warning for overriding non-inlined subroutines:

$ perl -e 'sub one () {1} sub one () {2}'
Constant subroutine one redefined at -e line 1.
$ perl -we 'sub one {1} sub one {2}'
Subroutine one redefined at -e line 1.

The warning is considered severe enough not to be affected by the -w switch (or its absence) because previously compiled invocations of the function will still be using the old value of the function. If you need to be able to redefine the subroutine, you need to ensure that it isn't inlined, either by dropping the "()" prototype (which changes calling semantics, so beware) or by thwarting the inlining mechanism in some other way, e.g. by adding an explicit "return", as mentioned above:

sub not_inlined () { return 23 }

Overriding Built-in Functions

Many built-in functions may be overridden, though this should be tried only occasionally and for good reason. Typically this might be done by a package attempting to emulate missing built-in functionality on a non-Unix system.

Overriding may be done only by importing the name from a module at compile time--ordinary predeclaration isn't good enough. However, the "use subs" pragma lets you, in effect, predeclare subs via the import syntax, and these names may then override built-in ones:

use subs 'chdir', 'chroot', 'chmod', 'chown';
chdir $somewhere;
sub chdir { ... }

To unambiguously refer to the built-in form, precede the built-in name with the special package qualifier "CORE::". For example, saying CORE::open() always refers to the built-in open(), even if the current package has imported some other subroutine called &open() from elsewhere. Even though it looks like a regular function call, it isn't: the "CORE::" prefix in that case is part of Perl's syntax, and works for any keyword, regardless of what is in the "CORE" package. Taking a reference to it, that is, "\&CORE::open", only works for some keywords. See CORE.

Library modules should not in general export built-in names like "open" or "chdir" as part of their default @EXPORT list, because these may sneak into someone else's namespace and change the semantics unexpectedly. Instead, if the module adds that name to @EXPORT_OK, then it's possible for a user to import the name explicitly, but not implicitly. That is, they could say

use Module 'open';

and it would import the "open" override. But if they said

use Module;

they would get the default imports without overrides.

The foregoing mechanism for overriding built-in is restricted, quite deliberately, to the package that requests the import. There is a second method that is sometimes applicable when you wish to override a built-in everywhere, without regard to namespace boundaries. This is achieved by importing a sub into the special namespace "CORE::GLOBAL::". Here is an example that quite brazenly replaces the "glob" operator with something that understands regular expressions.

package REGlob;
require Exporter;
@ISA = 'Exporter';
@EXPORT_OK = 'glob';
sub import {
    my $pkg = shift;
    return unless @_;
    my $sym = shift;
    my $where = ($sym =~ s/^GLOBAL_// ? 'CORE::GLOBAL' : caller(0));
    $pkg->export($where, $sym, @_);
}
sub glob {
    my $pat = shift;
    my @got;
    if (opendir my $d, '.') {
        @got = grep /$pat/, readdir $d;
        closedir $d;
    }
    return @got;
}
1;

And here's how it could be (ab)used:

#use REGlob 'GLOBAL_glob';      # override glob() in ALL namespaces
package Foo;
use REGlob 'glob';              # override glob() in Foo:: only
print for <^[a-z_]+\.pm\$>;     # show all pragmatic modules

The initial comment shows a contrived, even dangerous example. By overriding "glob" globally, you would be forcing the new (and subversive) behavior for the "glob" operator for every namespace, without the complete cognizance or cooperation of the modules that own those namespaces. Naturally, this should be done with extreme caution--if it must be done at all.

The "REGlob" example above does not implement all the support needed to cleanly override Perl's "glob" operator. The built-in "glob" has different behaviors depending on whether it appears in a scalar or list context, but our "REGlob" doesn't. Indeed, many Perl built-ins have such context sensitive behaviors, and these must be adequately supported by a properly written override. For a fully functional example of overriding "glob", study the implementation of "File::DosGlob" in the standard library.

When you override a built-in, your replacement should be consistent (if possible) with the built-in native syntax. You can achieve this by using a suitable prototype. To get the prototype of an overridable built-in, use the "prototype" function with an argument of "CORE::builtin_name" (see "prototype" in perlfunc).

Note however that some built-ins can't have their syntax expressed by a prototype (such as "system" or "chomp"). If you override them you won't be able to fully mimic their original syntax.

The built-ins "do", "require" and "glob" can also be overridden, but due to special magic, their original syntax is preserved, and you don't have to define a prototype for their replacements. (You can't override the "do BLOCK" syntax, though).

"require" has special additional dark magic: if you invoke your "require" replacement as "require Foo::Bar", it will actually receive the argument "Foo/Bar.pm" in @_. See "require" in perlfunc.

And, as you'll have noticed from the previous example, if you override "glob", the "<*>" glob operator is overridden as well.

In a similar fashion, overriding the "readline" function also overrides the equivalent I/O operator "<FILEHANDLE>". Also, overriding "readpipe" also overrides the operators `` and "qx//".

Finally, some built-ins (e.g. "exists" or "grep") can't be overridden.

DESCRIPTION

Lorsque vous appelez une sous-routine qui n'est pas définie, vous obtenez normalement une erreur immédiate et fatale indiquant que la sous-routine n'existe pas. (Il en va de même pour les sous-programmes utilisés comme méthodes, lorsque la méthode n'existe dans aucune classe de base du package de la classe.) Cependant, si une sous-routine "AUTOLOAD" est définie dans le package ou les packages utilisés pour localiser la sous-routine d'origine, alors cette sous-routine "AUTOLOAD" est appelée avec les arguments qui auraient été passés à la sous-routine d'origine. Le nom qualifié complet de la sous-routine d'origine apparaît magiquement dans la variable globale $AUTOLOAD du même package que la routine "AUTOLOAD". Le nom n'est pas passé comme argument ordinaire car, euh, eh bien, juste parce que, c'est pourquoi. (À titre d'exception, un appel de méthode à une méthode "import" ou "unimport" inexistante est simplement ignoré à la place. De plus, si la sous-routine AUTOLOAD est une XSUB, il existe d'autres moyens de récupérer le nom de la sous-routine. Voir "Autoloading with XSUBs" dans perlguts pour plus de détails.)

De nombreuses routines "AUTOLOAD" chargent une définition pour la sous-routine demandée à l'aide de eval(), puis exécutent cette sous-routine à l'aide d'une forme spéciale de goto() qui efface le cadre de pile de la routine "AUTOLOAD" sans laisser de trace. (Voir la source du module standard documenté dans AutoLoader, par exemple.) Mais une routine "AUTOLOAD" peut également simplement émuler la routine et ne jamais la définir. Par exemple, faisons semblant qu'une fonction qui n'a pas été définie devrait simplement invoquer "system" avec ces arguments. Tout ce que vous feriez est ceci :

sub AUTOLOAD {
    our $AUTOLOAD;              # keep 'use strict' happy
    my $program = $AUTOLOAD;
    $program =~ s/.*:://;
    system($program, @_);
}

En fait, si vous prédéclarez les fonctions que vous souhaitez appeler de cette manière, vous n'avez même pas besoin de parenthèses :

use subs qw(date who ls);
date;
who;
ls '-l';

Un exemple plus complet de ceci est le module Shell sur CPAN, qui peut traiter les appels de sous-programmes indéfinis comme des appels à des programmes externes.

Des mécanismes sont disponibles pour aider les auteurs de modules à diviser leurs modules en fichiers chargeables automatiquement. Voir le module standard AutoLoader décrit dans AutoLoader et dans AutoSplit, les modules standard SelfLoader dans SelfLoader, et le document sur l'ajout de fonctions C au code Perl dans perlxs.

Attributs de sous-programme

Une déclaration ou une définition de sous-routine peut avoir une liste d'attributs qui lui sont associés. Si une telle liste d'attributs est présente, elle est décomposée aux limites d'espaces ou de deux-points et traitée comme si un "use attributes" avait été vu. Voir attributes pour les détails sur les attributs actuellement pris en charge. Contrairement à la limitation avec l'obsolète "use attrs", la syntaxe "sub : ATTRLIST" fonctionne pour associer les attributs à une pré-déclaration, et pas seulement à une définition de sous-routine.

Les attributs doivent être valides en tant que noms d'identificateurs simples (sans aucune ponctuation autre que le caractère '\_'). Ils peuvent avoir une liste de paramètres ajoutée, dont seule la bonne imbrication des parenthèses ('()') est vérifiée.

Exemples de syntaxe valide (même si les attributs sont inconnus) :

sub fnord (&\%) : switch(10,foo(7,3))  :  expensive;
sub plugh () : Ugly('\(") :Bad;
sub xyzzy : _5x5 { ... }

Exemples de syntaxe invalide :

sub fnord : switch(10,foo();    # la chaîne () n'est pas équilibrée
sub snoid : Ugly('(');          # la chaîne () n'est pas équilibrée
sub xyzzy : 5x5;                # "5x5" n'est pas un identificateur valide
sub plugh : Y2::north;          # "Y2::north" n'est pas un identificateur simple
sub snurt : foo + bar;          # "+" n'est pas un deux-points ou un espace

La liste d'attributs est passée sous forme de liste de chaînes constantes au code qui les associe à la sous-routine. En particulier, le deuxième exemple de syntaxe valide ci-dessus ressemble actuellement à ceci en termes de parsing et d'invocation :

use attributes __PACKAGE__, \&plugh, q[Ugly('\(")], 'Bad';

Pour plus de détails sur les listes d'attributs et leur manipulation, voir attributes et Attribute::Handlers.
