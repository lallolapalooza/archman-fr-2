NOM

perl581delta - nouveautés de la version perl v5.8.1

DESCRIPTION

Ce document décrit les différences entre la version 5.8.0 et la version 5.8.1.

Si vous mettez à jour depuis une version antérieure comme la 5.6.1, lisez d'abord perl58delta, qui décrit les différences entre 5.6.0 et 5.8.0.

Au cas où vous vous poseriez la question concernant la 5.6.1, elle était plutôt identique en termes de correction de bugs à la version de développement 5.7.1. Confus ? Cette chronologie espérons-vous aidera un peu : elle liste les nouvelles versions majeures, leurs versions de maintenance et les versions de développement.

Changements Incompatibles

Randomisation des Hashes

Principalement pour des raisons de sécurité, l'« ordre aléatoire » des hashes a été rendu encore plus aléatoire. Auparavant, bien que l'ordre des éléments de hash de keys(), values() et each() soit essentiellement aléatoire, il était toujours reproductible. Désormais, cependant, l'ordre varie entre les différentes exécutions de Perl.

Perl n'a jamais garanti aucun ordre des clés de hash, et l'ordre a déjà changé plusieurs fois au cours de la vie de Perl 5. De plus, l'ordre des clés de hash a toujours été, et continue d'être, affecté par l'ordre d'insertion.

Le caractère aléatoire ajouté peut affecter les applications.

Un scénario possible est lorsque la sortie d'une application incluait des données de hash. Par exemple, si vous avez utilisé le module Data::Dumper pour sauvegarder des données dans différents fichiers, puis comparé les fichiers pour voir si les données avaient changé, vous aurez maintenant de faux positifs car l'ordre dans lequel les hashes sont sauvegardés variera. En général, la solution est de trier les clés (ou les valeurs) ; en particulier pour Data::Dumper, utilisez l'option "Sortkeys". Si un ordre particulier est vraiment important, utilisez des hashes liés : par exemple le module Tie::IxHash qui par défaut préserve l'ordre dans lequel les éléments de hash ont été ajoutés.

Un problème plus subtil est la dépendance à l'ordre de la « destruction globale ». C'est ce qui se passe à la fin de l'exécution : Perl détruit toutes les structures de données, y compris les données utilisateur. Si vos destructeurs (les sous-routines DESTROY) ont supposé un ordre particulier pour la destruction globale, il pourrait y avoir des problèmes à venir. Par exemple, dans le destructeur d'un objet, vous ne pouvez pas supposer que les objets de toute autre classe sont toujours disponibles, à moins que vous n'y conserviez une référence. Si la variable d'environnement PERL_DESTRUCT_LEVEL est définie à une valeur non nulle, ou si Perl sort d'un thread lancé, il détruira également les références ordinaires et les tables de symboles qui ne sont plus utilisées. Vous ne pouvez pas appeler une méthode de classe ou une fonction ordinaire sur une classe qui a été collectée de cette manière.

La randomisation des hashes est certaine de révéler des hypothèses cachées sur un ordre particulier des éléments de hash, et des bugs manifestes : elle a révélé quelques bugs dans le noyau Perl et les modules du noyau.

Pour désactiver la randomisation des hashes à l'exécution, définissez la variable d'environnement PERL_HASH_SEED à 0 (zéro) avant d'exécuter Perl (pour plus d'informations, voir "PERL_HASH_SEED" dans perlrun), ou pour désactiver complètement la fonctionnalité à la compilation, compilez avec "-DNO_HASH_SEED" (voir INSTALL).

Voir "Algorithmic Complexity Attacks" dans perlsec pour la raison initiale de ce changement.

UTF-8 sur les filehandles n'est plus activé par locale

Dans Perl 5.8.0, tous les filehandles, y compris les filehandles standard, étaient implicitement définis en UTF-8 si les paramètres de locale indiquaient l'utilisation de UTF-8. Cette fonctionnalité a causé trop de problèmes, elle a donc été désactivée et repensée : voir "Améliorations du Noyau".

Les chaînes v à nombre unique ne sont plus des chaînes v avant « => »

La fonctionnalité des chaînes de version ou chaînes v (voir "Version Strings" dans perldata) introduite dans Perl 5.6.0 a été une source de confusion - surtout lorsque l'utilisateur ne voulait pas l'utiliser, mais Perl pensait savoir mieux. Particulièrement problématique a été la fonctionnalité selon laquelle avant un « => » une chaîne de version (un « v » suivi de chiffres) était interprétée comme une chaîne v au lieu d'une chaîne littérale. En d'autres termes :

%h = ( v65 => 42 );

signifiait depuis Perl 5.6.0

%h = ( 'A' => 42 );

(du moins sur les plateformes descendant de l'ASCII) Perl 5.8.1 rétablit l'interprétation plus naturelle

%h = ( 'v65' => 42 );

Les chaînes v à nombres multiples comme v65.66 et 65.66.67 continuent toujours d'être des chaînes v dans Perl 5.8.

(Win32) Le Switch -C a été réattribué

Le switch -C a été modifié d'une manière incompatible. Les anciennes sémantiques de ce switch n'avaient de sens que sous Win32 et uniquement dans l'univers « use utf8 » des versions 5.6.x, et n'ont pas de sens pour l'implémentation Unicode dans la version 5.8.0. Étant donné que ce switch n'aurait pu être utilisé par personne, il a été réattribué. Le comportement que ce switch permettait dans les versions 5.6.x pourrait être pris en charge de manière transparente et dépendante des données dans une future version.

Pour la nouvelle vie de ce switch, voir "UTF-8 n'est plus par défaut sous les locales UTF-8", et "-C" dans perlrun.

(Win32) Le Switch /d de cmd.exe

Perl 5.8.1 utilise le switch /d lors de l'exécution interne du shell cmd.exe pour system(), les backticks, et lors de l'ouverture de pipes vers des programmes externes. Le switch supplémentaire désactive l'exécution des commandes AutoRun du registre, ce qui est généralement considéré comme indésirable lors de l'exécution de programmes externes. Si vous souhaitez conserver la compatibilité avec le comportement précédent, définissez PERL5SHELL dans votre environnement sur "cmd /x/c".

Améliorations du Noyau

UTF-8 n'est plus par défaut sous les locales UTF-8

Dans Perl 5.8.0, de nombreuses fonctionnalités Unicode ont été introduites. L'une d'elles s'est avérée plus gênante qu'utile : la « UTF-8-ification » automatique (et silencieuse) des filehandles, y compris les filehandles standards, si les paramètres de locale de l'utilisateur indiquaient l'utilisation de UTF-8.

Par exemple, si vous aviez "en_US.UTF-8" comme locale, votre STDIN et STDOUT étaient automatiquement « UTF-8 », en d'autres termes un binmode(..., ":utf8") implicite était appliqué. Cela signifiait qu'essayer d'imprimer, par exemple, chr(0xff), résultait à imprimer les octets 0xc3 0xbf. Difficilement ce que vous aviez en tête sauf si vous étiez au courant de cette fonctionnalité de Perl 5.8.0. Le problème est que la grande majorité des gens ne l'étaient pas : par exemple, dans les versions 8 et 9 de RedHat, le paramètre de locale par défaut est UTF-8, donc tous les utilisateurs de RedHat ont obtenu des filehandles UTF-8, qu'ils le veuillent ou non. La douleur a été intensifiée par l'implémentation Unicode de Perl 5.8.0 (qui avait encore) de vilains bugs, notamment liés à l'utilisation de s/// et tr///. (Bugs qui ont été corrigés dans la 5.8.1)

Par conséquent, une décision a été prise de revenir sur cette fonctionnalité et de la faire passer d'un défaut silencieux implicite à une option explicite et consciente. La nouvelle option de ligne de commande de Perl "-C" et sa contrepartie la variable d'environnement PERL_UNICODE peuvent maintenant être utilisées pour contrôler comment Perl et Unicode interagissent aux interfaces comme l'E/S et par exemple les arguments de ligne de commande. Voir "-C" dans perlrun et "PERL_UNICODE" dans perlrun pour plus d'informations.

Signaux non sécurisés à nouveau disponibles

Dans Perl 5.8.0, les soi-disant « signaux sécurisés » ont été introduits. Cela signifie que Perl ne gère plus les signaux

als immédiatement mais plutôt « entre les opcodes », lorsque cela est sans danger. La gestion immédiate précédente pouvait facilement corrompre l'état interne de Perl, entraînant des plantages mystérieux.

Cependant, le nouveau modèle plus sûr a aussi ses problèmes. Parce que maintenant un opcode, une unité de base de l'exécution de Perl, n'est jamais interrompu mais au lieu de cela, on le laisse s'exécuter jusqu'à la fin, certaines opérations qui peuvent prendre du temps prennent maintenant réellement du temps. Par exemple, certaines opérations réseau ont leurs propres mécanismes de blocage et de timeout, et pouvoir les interrompre immédiatement serait souhaitable.

Par conséquent, perl 5.8.1 introduit une « porte dérobée » pour restaurer le comportement de signalisation d'avant 5.8.0 (en fait, d'avant 5.7.3). Définissez simplement la variable d'environnement PERL_SIGNALS à « unsafe », et l'ancien comportement de gestion des signaux immédiat (et dangereux) sera de retour. Voir « PERL_SIGNALS » dans perlrun et « Deferred Signals (Safe Signals) » dans perlipc.

Dans des nouvelles complètement sans rapport, vous pouvez maintenant utiliser les signaux sûrs avec POSIX::SigAction. Voir « POSIX::SigAction » dans POSIX.

Tableaux liés avec des indices de tableau négatifs

Auparavant, les indices passés aux méthodes « FETCH », « STORE », « EXISTS » et « DELETE » dans les classes de tableaux liés étaient toujours non négatifs. Si l'argument réel était négatif, Perl appelait implicitement FETCHSIZE et ajoutait le résultat à l'indice avant de passer le résultat à la méthode du tableau lié. Ce comportement est maintenant facultatif. Si la classe de tableau lié contient une variable de paquet nommée $NEGATIVE_INDICES qui est définie à une valeur vraie, les valeurs négatives seront passées à « FETCH », « STORE », « EXISTS » et « DELETE » inchangées.

local ${$x}

Les syntaxes

local ${$x}
local @{$x}
local %{$x}

localisent maintenant des variables, étant donné que $x est un nom de variable valide.

Base de données de caractères Unicode 4.0.0

La copie de la base de données de caractères Unicode incluse dans Perl 5.8 a été mise à jour de 3.2.0 à 4.0.0. Cela signifie, par exemple, que les propriétés des caractères Unicode sont celles de Unicode 4.0.0.

Avertissements de dépréciation

Il y a une nouvelle dépréciation de fonctionnalité. Perl 5.8.0 a oublié d'ajouter quelques avertissements de dépréciation, ces avertissements ont maintenant été ajoutés. Enfin, un rappel d'une suppression imminente de fonctionnalité.

(Rappel) Les pseudo-hashes sont obsolètes (vraiment)

Les pseudo-hashes ont été dépréciés dans Perl 5.8.0 et seront supprimés dans Perl 5.10.0, voir perl58delta pour les détails. Chaque tentative d'accès aux pseudo-hashes déclenchera l'avertissement « Pseudo-hashes are deprecated ». Si vous souhaitez vraiment continuer à utiliser les pseudo-hashes mais ne pas voir les avertissements de dépréciation, utilisez :

no warnings 'deprecated';

Ou vous pouvez continuer à utiliser le pragma fields, mais n'espérez pas que les structures de données soient encore des pseudo-hashes.

(Rappel) Les threads style 5.005 sont obsolètes (vraiment)

Les threads style 5.005 (activés par « use Thread; ») ont été dépréciés dans Perl 5.8.0 et seront supprimés après Perl 5.8, voir perl58delta pour les détails. Chaque création de thread style 5.005 déclenchera l'avertissement « 5.005 threads are deprecated ». Si vous souhaitez vraiment continuer à utiliser les threads style 5.005 mais ne pas voir les avertissements de dépréciation, utilisez :

no warnings 'deprecated';

(Rappel) La variable $* est obsolète (vraiment)

La variable $* contrôlant la correspondance multi-lignes a été dépréciée et sera supprimée après 5.8. La variable est dépréciée depuis longtemps, et un avertissement de dépréciation « Use of $* is deprecated » est émis, maintenant la variable sera finalement supprimée. La fonctionnalité a été remplacée par les modificateurs « /s » et « /m » sur la correspondance de motifs. Si vous souhaitez vraiment continuer à utiliser la variable $* mais ne pas voir les avertissements de dépréciation, utilisez :

no warnings 'deprecated';

Améliorations diverses

« map » en contexte vide n'est plus coûteux. « map » est maintenant conscient du contexte, et ne construira pas une liste s'il est appelé en contexte vide.

Si une socket est fermée par le serveur lors de l'écriture dessus, le client reçoit maintenant un SIGPIPE. Bien que cette nouvelle fonctionnalité n'ait pas été prévue, elle découle naturellement des changements apportés à PerlIO, et doit être considérée comme une fonctionnalité accidentelle.

PerlIO::get_layers(FH) renvoie les noms des couches PerlIO actives sur un descripteur de fichier.

Les couches PerlIO::via peuvent maintenant avoir une méthode UTF8 facultative pour indiquer si la couche souhaite « auto-:utf8 » le flux.

utf8::is_utf8() a été ajouté comme moyen rapide de tester si un scalaire est encodé en interne en UTF-8 (Unicode).

Améliorations d'Installation et de Configuration

L'emplacement standard Perl sous Unix, /usr/bin/perl, n'est plus écrasé par défaut s'il existe. Ce changement était très prudent car de nombreux fournisseurs Unix fournissent déjà un /usr/bin/perl, mais simultanément de nombreux utilitaires système peuvent dépendre de cette version exacte de Perl, il est donc préférable de ne pas l'écraser.

On peut maintenant spécifier les répertoires d'installation pour les pages man et HTML de site et de vendeur, et les scripts de site et de vendeur. Voir INSTALL.

On peut maintenant spécifier un répertoire de destination pour l'installation de Perl en spécifiant la variable DESTDIR pour "make install". (Cette fonctionnalité est légèrement différente de la précédente "Configure -Dinstallprefix=...".) Voir INSTALL.

Les versions 3.x de gcc ont introduit un nouvel avertissement qui a causé beaucoup de bruit lors de la compilation de Perl : "gcc -Ialreadyknowndirectory (warning: changing search order)". Cet avertissement a maintenant été évité par Configure qui élimine de tels répertoires avant la compilation.

On peut maintenant construire des sous-ensembles de modules Perl de base en utilisant les drapeaux de configuration "-Dnoextensions=..." et "-Donlyextensions=...", voir INSTALL.

Améliorations spécifiques à la plateforme

Dans Cygwin, Perl peut maintenant être construit avec des threads ("Configure -Duseithreads"). Cela fonctionne avec Cygwin 1.3.22 et Cygwin 1.5.3.

Dans les versions plus récentes de FreeBSD, la compilation de Perl 5.8.0 échouait à cause de la tentative d'utilisation de malloc.h, qui dans FreeBSD n'est qu'un fichier factice, et qui génère une erreur fatale même en essayant de l'utiliser. Maintenant, malloc.h n'est plus utilisé.

Perl est maintenant connu pour construire également sous Hitachi HI-UXMPP.

Perl est maintenant connu pour construire à nouveau sous LynxOS.

Mac OS X s'installe maintenant avec le numéro de version de Perl intégré dans les noms de répertoires d'installation pour faciliter la mise à niveau de Perl compilé par l'utilisateur, et les répertoires d'installation en général sont plus standards. En d'autres termes, l'installation par défaut ne casse plus le Perl fourni par Apple. D'autre part, avec "Configure -Dprefix=/usr" vous pouvez maintenant vraiment remplacer le Perl fourni par Apple (veuillez faire attention).

Mac OS X construit maintenant Perl statiquement par défaut. Ce changement a été effectué principalement pour des temps de démarrage plus rapides. Le Perl fourni par Apple est toujours lié dynamiquement et partagé, et vous pouvez activer le partage pour vos propres compilations Perl avec "Configure -Duseshrplib".

Perl a été porté sur l'environnement PASE d'IBM OS/400. La meilleure façon de construire un Perl pour PASE est d'utiliser un hôte AIX comme environnement de compilation croisée. Voir README.os400.

Encore une option de compilation croisée a été ajoutée : maintenant Perl se construit sur OpenZaurus, une distribution Linux basée sur Mandrake + Embedix pour le PDA Sharp Zaurus. Voir le fichier Cross/README.

Tru64 lors de l'utilisation de gcc 3 réduit l'optimisation pour toke.c à "-O2" en raison de l'utilisation gigantesque de mémoire avec le "-O3" par défaut.

Tru64 peut maintenant construire Perl avec les nouvelles bases de données Berkeley.

La construction de Perl sous WinCE a été grandement améliorée, voir README.ce et README.perlce.

Corrections de Bugs Sélectionnées

Closures, eval et lexiscales

Il y a eu de nombreuses corrections dans le domaine des sous-programmes anonymes, des lexiscales et des closures. Bien que cela signifie que Perl est maintenant plus « correct », il est possible que du code existant qui dépendait du comportement fautif se casse. En pratique, cela est peu probable à moins que votre code ne contienne un imbrication très complexe de sous-programmes anonymes, d'evals et de lexiscales.

Corrections génériques

Si un handle de fichier d'entrée est marqué ":utf8" et que Perl rencontre du UTF-8 illégal en entrée lors de l'opération "<FH>", si les avertissements sont activés, un avertissement est immédiatement donné - au lieu de rester silencieux et que Perl soit mécontent des données corrompues plus tard. (La couche :encoding(utf8) fonctionne également de la même manière.)

binmode(SOCKET, ":utf8") ne fonctionnait que côté entrée, pas côté sortie du socket. Maintenant, cela fonctionne dans les deux sens.

Pour les Perl multithreadés, certaines fonctions de base de données système comme getpwent() et getgrent() augmentent maintenant dynamiquement leur tampon de résultat, au lieu d'échouer. Cela signifie que sur les sites avec beaucoup d'utilisateurs et de groupes, les fonctions n'échouent plus en retournant seulement des résultats partiels.

Perl 5.8.0 avait accidentellement cassé la capacité des utilisateurs à définir leurs propres mappings Unicode majuscules<->minuscules (comme annoncé par le Camel). Cette fonctionnalité a été corrigée et est également mieux documentée.

En 5.8.0, ceci

$some_unicode .= <FH>;

ne fonctionnait pas correctement mais corrompait les données. Ceci a maintenant été corrigé.

Les méthodes liées comme FETCH etc. peuvent maintenant accéder en toute sécurité aux valeurs liées, c'est-à-dire que cela entraîne un appel récursif à FETCH etc. N'oubliez pas de casser la récursion, cependant.

Au démarrage, Perl bloque le signal SIGFPE car Perl ne peut pas faire grand-chose à ce sujet. Auparavant, ce blocage était également en vigueur pour les programmes exécutés depuis Perl. Maintenant, Perl restaure la routine de gestion SIGFPE d'origine, quelle qu'elle soit, avant d'exécuter des programmes externes.

Les numéros de ligne dans les scripts Perl peuvent maintenant être supérieurs à 65536, soit 2^16. (Les scripts Perl ont toujours pu être plus grands que cela, c'est juste que le numéro de ligne pour les erreurs et les avertissements signalés « bouclait ».) Bien que les scripts aussi grands indiquent généralement un besoin de revoir un peu votre code, de tels scripts Perl existent, par exemple comme résultats de code généré. Maintenant, les numéros de ligne peuvent aller jusqu'à 4294967296, soit 2^32.

Corrections et changements

Les changements suivants ont été effectués dans Perl 5.8.1.

VMS

  • La configuration teste désormais la présence de poll(), et IO::Poll utilise la fonction fournie par le fournisseur si elle est détectée.
  • Une rare violation d'accès au démarrage de Perl pouvait survenir si l'image Perl était installée avec des privilèges ou s'il y avait un identifiant avec l'attribut sous-système défini dans la liste des droits du processus. L'une ou l'autre de ces circonstances déclenchait un code de mise en garde (tainting) contenant un bug de pointeur. L'arithmétique des pointeurs défectueuse a été corrigée.
  • La limite de longueur des valeurs (pas des clés) dans la table de hachage %ENV a été augmentée de 255 octets à 32640 octets (sauf lorsque le paramètre PERL_ENV_TABLES remplace l'utilisation par défaut des noms logiques pour %ENV). S'il est nécessaire d'accéder à ces valeurs longues depuis l'extérieur de Perl, sachez qu'elles sont implémentées à l'aide de noms logiques de liste de recherche qui stockent la valeur par morceaux, chaque morceau de 255 octets (jusqu'à 128 d'entre eux) étant un élément de la liste de recherche. Lors d'une recherche dans %ENV depuis Perl, les éléments sont combinés en une seule valeur. La capacité spécifique à VMS d'accéder aux éléments individuels d'un nom logique de liste de recherche via la syntaxe $ENV{'foo;N'} (où N est l'indice de la liste de recherche) n'est pas affectée.
  • L'implémentation du piping utilise désormais des symboles DCL locaux plutôt que globaux pour la communication inter-processus.
  • File::Find pouvait se tromper lors de la navigation vers un répertoire relatif dont le nom entrait en collision avec un nom logique. Ce problème a été corrigé en ajoutant la syntaxe de répertoire aux noms de chemins relatifs, empêchant ainsi la traduction des noms logiques.

Win32

  • Une fuite de mémoire dans l'émulation fork() a été corrigée.
  • La valeur de retour de la fonction intégrée ioctl() a été accidentellement cassée en 5.8.0. Ceci a été corrigé.
  • La boucle de messages interne exécutée par perl lors d'opérations bloquantes interférait parfois avec des messages externes à Perl. Cela entraînait souvent l'interruption prématurée des opérations bloquantes ou le retour de résultats incorrects, lorsque Perl s'exécutait dans des environnements susceptibles de générer des messages Windows. Ceci a été corrigé.
  • Les pipes et les sockets sont désormais en mode binaire par défaut.
  • La forme à quatre arguments de select() ne préservait pas correctement $! (errno) en cas d'erreurs dans l'appel sous-jacent. Ceci est maintenant corrigé.
  • Le problème du "CR CR LF" a été résolu, binmode(FH, ":crlf") est désormais effectivement une opération nulle.

Diagnostics nouveaux ou modifiés

Tous les avertissements liés à pack() et unpack() ont été rendus plus informatifs et cohérents.

Modification de "A thread exited while %d threads were running"

L'ancienne version

A thread exited while %d other threads were still running

était trompeuse car le "autre" incluait également le thread qui générait l'avertissement.

Suppression de "Attempt to clear a restricted hash"

Il n'est pas illégal de vider une table de hachage restreinte, donc l'avertissement a été supprimé.

Nouveau "Illegal declaration of anonymous subroutine"

Vous devez spécifier le bloc de code pour "sub".

Modification de "Invalid range "%s" in transliteration operator"

L'ancienne version

Invalid [] range "%s" in transliteration operator

était simplement fausse car il n'y a pas de "plages []" dans tr///.

Nouveau "Missing control char name in \c"

Auto-explicatif.

Nouveau "Newline in left-justified string for %s"

Les espaces de remplissage apparaîtraient après le saut de ligne, ce qui n'est probablement pas ce que vous aviez en tête.

Nouveau "Possible precedence problem on bitwise %c operator"

Si vous pensez que ceci

$x & $y == 0

teste si le ET bit à bit de $x et $y est zéro, vous aimerez cet avertissement.

Nouveau "Pseudo-hashes are deprecated"

Cet avertissement aurait déjà dû être présent en 5.8.0, car ils le sont.

Nouveau "read() on %s filehandle %s"

Vous ne pouvez pas utiliser read() (ou sysread()) sur un descripteur de fichier fermé ou non ouvert.

Nouveau "5.005 threads are deprecated"

Cet avertissement aurait déjà dû être présent en 5.8.0, car ils le sont.

Nouveau "Tied variable freed while still in use"

Quelque chose a débranché une variable liée vivante, Perl joue la sécurité en abandonnant.

Nouveau "To%s: illegal mapping '%s'"

Une mise en correspondance de casse Unicode illégale définie par l'utilisateur a été spécifiée.

Nouveau "Use of freed value in iteration"

Quelque chose a modifié les valeurs en cours d'itération. Ce n'est pas une bonne chose.

Internes modifiés

Ces nouvelles ne vous concernent que si vous écrivez du code XS ou aimez connaître ou pirater les internes de Perl (l'utilisation de Devel::Peek ou l'un des modules "B::" compte), ou si vous aimez exécuter Perl avec l'option "-D".

Les exemples d'intégration de perlembed ont été revus pour être à jour et cohérents : par exemple, l'utilisation correcte de PERL_SYS_INIT3() et PERL_SYS_TERM().

Des travaux approfondis sur le code du pad (le code responsable des variables lexicales) ont été réalisés par Dave Mitchell.

Des travaux importants sur les chaînes v par John Peacock.

Cache de longueur et de position UTF-8 : pour accélérer le traitement des scalaires Unicode (UTF-8), un cache a été introduit. Des problèmes potentiels existent si une extension contourne les API officielles et modifie directement le PV d'un SV : le cache UTF-8 n'est pas effacé comme il le devrait.

Les API obsolètes dans Perl 5.8.0, comme sv_2pv, sv_catpvn, sv_catsv, sv_setsv, sont à nouveau disponibles.

Certaines API C principales de Perl comme cxinc et regatom ne sont plus du tout disponibles pour le code externe au cœur de Perl et à ses extensions. Ceci est intentionnel. Elles n'auraient jamais dû être disponibles sous des noms plus courts, et si votre application dépend d'elles, vous devriez (avoir honte et) contacter les perl5-porters pour discuter des API appropriées.

Certaines API C principales de Perl comme "Perl_list" ne sont plus disponibles sans leur préfixe "Perl_". Si votre module XS cesse de fonctionner car certaines fonctions ne sont pas trouvées, dans de nombreux cas, une simple correction consiste à ajouter le préfixe "Perl_" à la fonction et le contexte de thread "aTHX_" comme premier argument de l'appel de fonction. C'est aussi ainsi que cela aurait toujours dû être fait : laisser les formes sans Perl fuir du cœur était un accident. Pour une intégration plus propre, vous pouvez également forcer cela pour toutes les API en définissant au moment de la compilation la macro cpp PERL_NO_SHORT_NAMES.

Perl_save_bool() a été ajouté.

Les objets regexp (ceux créés avec "qr") ont maintenant du S-magic plutôt que du R-magic. Cela a corrigé les regexp de la forme /...(??{...;$x})/ pour qu'elles n'ignorent plus les modifications apportées à $x. Le S-magic évite de laisser tomber l'optimisation de mise en cache et de rendre les constructions (??{...}) obscénément lentes (et par conséquent inutiles). Voir également "Magic Variables" dans perlguts. Regexp::Copy a été affecté par ce changement.

Les macros de débogage internes de Perl DEBUG() et DEB() ont été renommées en PERL_DEBUG() et PERL_DEB() pour éviter les conflits de noms.

"-DL" supprimé (le test de fuite était cassé et non pris en charge depuis des années, utilisez des mallocs de débogage alternatifs ou des outils comme valgrind et Purify).

Le modificateur verbeux "v" a été ajouté pour "-DXv" et "-Dsv", voir perlrun.

Problèmes connus

La randomisation des hachages mentionnée dans "Changements incompatibles" est définitivement problématique : elle réveillera des bugs dormants et fera apparaître de mauvaises hypothèses.

Si vous souhaitez utiliser mod_perl 2.x avec Perl 5.8.1, vous aurez besoin de mod_perl-1.99_10 ou d'une version supérieure. Les versions antérieures de mod_perl 2.x ne fonctionnent pas avec les hachages randomisés. (mod_perl 1.x fonctionne bien.) Vous aurez également besoin d'Apache::Test 1.04 ou d'une version supérieure.

De nombreuses plateformes plus rares qui fonctionnaient à 100 % ou presque avec perl 5.8.0 ont été un peu délaissées car leurs mainteneurs étaient occupés ailleurs récemment, et par conséquent, il y aura plus d'échecs sur ces plateformes. Ces plateformes incluent Mac OS Classic, IBM z/OS (et d'autres plateformes EBCDIC), et NetWare. Les plateformes Perl les plus courantes (Unix et Unix-like, plateformes Microsoft et VMS) ont une population de tests et d'experts suffisamment importante pour bien fonctionner.

Hachages liés en contexte scalaire

Les hachages liés ne retournent actuellement rien d'utile en contexte scalaire, par exemple lorsqu'ils sont utilisés comme tests booléens :

if (%tied_hash) { ... }

Le comportement absurde actuel est de toujours retourner faux, indépendamment du fait que le hachage soit vide ou contienne des éléments.

La cause profonde est qu'il n'existe pas d'interface permettant aux implémenteurs de hachages liés d'implémenter le comportement d'un hachage en contexte scalaire.

Net::Ping 450_service et 510_ping_udp échecs

Les sous-tests 9 et 18 de lib/Net/Ping/t/450_service.t, et le sous-test 2 de lib/Net/Ping/t/510_ping_udp.t peuvent échouer si vous avez une configuration réseau inhabituelle. Par exemple, dans ce dernier cas, le test essaie d'envoyer un ping UDP à l'adresse IP 127.0.0.1.

B::C

Le backend de compilateur générant du C, B::C (le frontend étant "perlcc -c") est encore plus cassé qu'auparavant en raison des changements étendus des variables lexicales. (La bonne nouvelle est que B::Bytecode et ByteLoader sont meilleurs qu'avant.)

Problèmes spécifiques à la plateforme

Plateformes EBCDIC

IBM z/OS et d'autres plateformes EBCDIC continuent de poser problème en matière de support Unicode. De nombreux tests Unicode sont ignorés alors qu'ils devraient être corrigés.

Problèmes Cygwin 1.5

Dans Cygwin 1.5, les tests io/tell et op/sysio échouent pour une raison encore inconnue. Dans la version 1.5.5, les tests de threads stress_cv, stress_re et stress_string échouent à moins que la variable d'environnement PERLIO ne soit définie à "perlio" (ce qui résout également l'échec de io/tell).

Perl 5.8.1 se compile et fonctionne bien avec Cygwin 1.3 : avec (uname -a) "CYGWIN_NT-5.0 ... 1.3.22(0.78/3/2) 2003-03-18 09:20 i686 ...", un "make test" à 100 % a été obtenu avec "Configure -des -Duseithreads".

HP-UX : Avertissements HP cc concernant sendfile et sendpath

Avec certaines versions du compilateur C de HP (par exemple B.11.11.02), vous obtiendrez de nombreux avertissements comme celui-ci (lignes renvoyées pour une lecture plus facile) :

cc: "/usr/include/sys/socket.h", ligne 504 : avertissement 562 :
  Redéclaration de "sendfile" avec un spécificateur de classe de stockage différent :
    "sendfile" aura une liaison interne.
cc: "/usr/include/sys/socket.h", ligne 505 : avertissement 562 :
  Redéclaration de "sendpath" avec un spécificateur de classe de stockage différent :
    "sendpath" aura une liaison interne.

Les avertissements apparaissent lors de la compilation de Perl et lors de certains tests lib/ExtUtils qui invoquent le compilateur C. L'avertissement n'est cependant pas grave et peut être ignoré.

IRIX : t/uni/tr_7jis.t échoue faussement

Le test t/uni/tr_7jis.t est connu pour signaler un échec lors de 'make test' ou du harnais de test avec certaines versions d'IRIX (au moins IRIX 6.5 et MIPSpro Compilers Version 7.3.1.1m), mais s'il est exécuté manuellement, le test passe complètement.

Mac OS X : pas de usemymalloc

Le malloc de Perl ("-Dusemymalloc") ne fonctionne pas du tout sous Mac OS X. Ce n'est cependant pas très grave, car le malloc natif fonctionne très bien.

Tru64 : Pas de compilations threadées avec GNU cc (gcc)

Dans les dernières versions de Tru64 (par exemple v5.1B ou ultérieures), gcc ne peut pas être utilisé pour compiler un Perl threadé (-Duseithreads) car le fichier système "<pthread.h>" ne connaît pas gcc.

Win32 : sysopen, sysread, syswrite

Depuis la version 5.8.0, sysopen()/sysread()/syswrite() ne se comportent plus comme auparavant en 5.6.1 et versions antérieures en ce qui concerne le mode "texte". Ces fonctions intégrées fonctionnent désormais toujours en mode "binaire" (même si sysopen() a reçu le drapeau O_TEXT, ou si binmode() a été utilisé sur le handle de fichier). Notez que ce problème ne devrait faire une différence que pour les fichiers disque, car les sockets et les pipes ont toujours été en mode "binaire" dans le port Windows. Comme ce comportement est actuellement considéré comme un bug, un comportement compatible pourrait être réintroduit dans une future version. En attendant, l'utilisation de sysopen(), sysread() et syswrite() n'est pas prise en charge pour les opérations en mode "texte".

Directions futures

Les choses suivantes pourraient arriver à l'avenir. Les premières versions publiquement disponibles ayant ces caractéristiques seront les versions de développement Perl 5.9.x, culminant avec la version Perl 5.10.0. Ce sont nos meilleures estimations pour le moment : nous nous réservons le droit de changer d'avis.

  • PerlIO deviendra le défaut. Actuellement (dans Perl 5.8.x), la bibliothèque stdio est toujours utilisée si Perl pense pouvoir utiliser certaines astuces pour rendre stdio vraiment rapide. Pour les futures versions, notre objectif est de rendre PerlIO encore plus rapide.
  • Une nouvelle fonctionnalité appelée assertions sera disponible. Cela signifie que l'on pourra avoir du code appelé assertions disséminé dans le code : généralement, elles sont optimisées et supprimées, mais elles peuvent être activées avec l'option "-A".
  • Un nouvel opérateur "//" (défini-ou) sera disponible. Cela signifie que l'on pourra écrire 
    $a // $b

    au lieu de

    defined $a ? $a : $b

    et

    $c //= $d;

    au lieu de

    $c = $d unless defined $c;

    L'opérateur aura la même précédence et associativité que "||". Un patch du code source contre les sources de Perl 5.8.1 sera disponible sur CPAN sous la forme de authors/id/H/HM/HMBRAND/dor-5.8.1.diff.

  • unpack() désassemblera par défaut le $_.
  • Diverses techniques de Copie Sur Écriture seront étudiées dans l'espoir d'accélérer Perl.
  • CPANPLUS, Inline et Module::Build deviendront des modules de base.
  • La possibilité d'écrire de véritables pragmas à portée lexicale sera introduite.
  • Les travaux sur le bytecode et le chargeur de bytecode se poursuivront.
  • Les chaînes v (v-strings) telles qu'elles existent actuellement sont prévues pour être dépréciées. La forme sans v (1.2.3) deviendra un "objet version" lorsqu'elle sera utilisée avec "use", "require" et $VERSION. $^V sera également un "objet version" afin que la construction printf("%vd",...) ne soit plus nécessaire. La version avec v (v1.2.3) deviendra obsolète. L'équivalence des chaînes et des chaînes v (par exemple, que 5.8.0 est actuellement égal à "\5\8\0") disparaîtra. Il se peut qu'il n'y ait pas d'avertissement de dépréciation pour les chaînes v : il est assez difficile de détecter quand les chaînes v sont utilisées en toute sécurité et quand elles ne le sont pas.
  • Les Threads 5.005 seront supprimés
  • La variable $* sera supprimée (elle a été dépréciée il y a longtemps)
  • Les pseudohachages seront supprimés

Signalement des bugs

Si vous trouvez ce qui vous semble être un bug, vous pourriez consulter les articles récemment postés dans le groupe de discussion comp.lang.perl.misc et la base de données des bugs de Perl à l'adresse http://bugs.perl.org/ . Il peut également y avoir des informations sur http://www.perl.com/ , la page d'accueil de Perl.

Si vous pensez avoir un bug non signalé, veuillez exécuter le programme perlbug inclus dans votre version. Assurez-vous de réduire votre bug à un cas de test minimal mais suffisant. Votre rapport de bug, ainsi que la sortie de "perl -V", seront envoyés à perlbug@perl.org pour être analysés par l'équipe de portage de Perl. Vous pouvez parcourir et rechercher les bugs de Perl 5 à l'adresse http://bugs.perl.org/
