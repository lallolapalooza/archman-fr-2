PERLNEWMOD(1perl) Guide du programmeur Perl PERLNEWMOD(1perl)

NOM

perlnewmod - préparation d'un nouveau module pour la distribution

DESCRIPTION

Ce document vous donne quelques suggestions sur la manière d'écrire des modules Perl, de les préparer pour la distribution et de les rendre disponibles via CPAN.

L'une des choses qui rend Perl vraiment puissant est le fait que les hackers Perl ont tendance à vouloir partager les solutions aux problèmes qu'ils ont rencontrés, afin que vous et moi n'ayons pas à nous battre avec le même problème à nouveau.

La principale façon dont ils le font est d'abstraire la solution dans un module Perl. Si vous ne savez pas ce qu'est l'un de ceux-ci, le reste de ce document ne vous sera pas très utile. Vous manquez également beaucoup de code utile ; envisagez de jeter un œil à perlmod, perlmodlib et perlmodinstall avant de revenir ici.

Lorsque vous avez constaté qu'aucun module n'est disponible pour ce que vous essayez de faire, et que vous avez dû écrire le code vous-même, envisagez d'empaqueter la solution dans un module et de la téléverser sur CPAN afin que d'autres puissent en bénéficier.

Vous devriez également jeter un œil à perlmodstyle pour connaître les meilleures pratiques pour créer un module.

Attention

Nous allons principalement nous concentrer ici sur les modules exclusivement en Perl, plutôt que sur les modules XS. Les modules XS servent un objectif assez différent, et vous devriez considérer des choses différentes avant de les distribuer - la popularité de la bibliothèque que vous reliez, la portabilité vers d'autres systèmes d'exploitation, etc. Cependant, les notes sur la préparation de la partie Perl du module, son empaquetage et sa distribution s'appliqueront aussi bien à un module XS qu'à un module pur Perl.

Que dois-je transformer en module ?

Vous devriez transformer en module tout code que vous pensez être utile à d'autres. Tout ce qui est susceptible de combler un manque dans la bibliothèque commune et que quelqu'un d'autre peut insérer directement dans son programme. Toute partie de votre code que vous pouvez isoler, extraire et greffer ailleurs est un candidat probable.

Prenons un exemple. Supposons que vous lisiez des données à partir d'un format local dans une structure de hachage imbriquée en Perl, que vous la transformiez en arbre, que vous parcouriez l'arbre et que vous redirigiez ensuite chaque nœud vers un serveur Acme Transmogrifier.

Maintenant, pas mal de gens ont le serveur Acme Transmogrifier, et vous avez dû écrire quelque chose pour gérer le protocole à partir de zéro - vous voudriez presque certainement en faire un module. Le niveau auquel vous le proposez dépend de vous : vous pourriez vouloir des modules au niveau du protocole analogues à Net::SMTP qui parlent ensuite à des modules de plus haut niveau analogues à Mail::Send. Le choix vous appartient, mais vous voulez absolument sortir un module pour ce protocole serveur.

Personne d'autre sur la planète ne parlera votre format de données local, nous pouvons donc l'ignorer. Mais qu'en est-il de la chose au milieu ? Construire des structures arborescentes à partir de variables Perl et les parcourir est un problème agréable et général, et si personne n'a déjà écrit de module qui fait cela, vous pourriez vouloir modulariser ce code aussi.

Donc, j'espère que vous avez maintenant quelques idées sur ce qu'il est bon de modulariser. Voyons maintenant comment cela se fait.

Pas à pas : Préparer le terrain

Avant même de commencer à gratter le code, il y a quelques choses que nous voudrons faire à l'avance.

Regardez autour
Plongez dans un tas de modules pour voir comment ils sont écrits. Je suggérerais de commencer par Text::Tabs, car il fait partie de la bibliothèque standard et est agréable et simple, puis de regarder quelque chose d'un peu plus complexe comme File::Copy. Pour le code orienté objet, WWW::Mechanize ou les modules "Email::*" fournissent de bons exemples.

Ceux-ci devraient vous donner une idée générale de la manière dont les modules sont organisés et écrits.

Vérifiez que c'est nouveau
Il y a beaucoup de modules sur CPAN, et il est facile d'en manquer un qui est similaire à ce que vous prévoyez de contribuer. Faites un bon passage sur https://metacpan.org et assurez-vous que vous n'êtes pas celui qui réinvente la roue !
Discutez du besoin
Vous pourriez l'adorer. Vous pourriez sentir que tout le monde en a besoin. Mais il n'y a peut-être pas de demande réelle pour cela. Si vous n'êtes pas sûr de la demande que votre module aura, envisagez de demander à la liste de diffusion "module-authors@perl.org" (envoyez un e-mail à "module-authors-subscribe@perl.org" pour vous abonner ; voir https://lists.perl.org/list/module-authors.html pour plus d'informations et un lien vers les archives).
Choisissez un nom
Les modules Perl inclus sur CPAN ont une hiérarchie de noms à laquelle vous devriez essayer de vous conformer. Voir perlmodlib pour plus de détails sur le fonctionnement, et parcourez CPAN et la liste des modules pour avoir une idée. Au minimum, rappelez-vous ceci : les modules doivent être capitalisés en titre (Ceci::Chose), s'intégrer dans une catégorie et expliquer leur objectif succinctement.
Vérifiez encore
Pendant que vous faites cela, assurez-vous vraiment que vous n'avez pas manqué un module similaire à celui que vous êtes sur le point d'écrire.

Une fois que vous avez défini votre nom et que vous êtes sûr que votre module est souhaité et non disponible actuellement, il est temps de commencer à coder.

Pas à pas : Création du module

Commencez avec module-starter ou h2xs
L'utilitaire module-starter est distribué dans le cadre du paquet CPAN Module::Starter. Il crée un répertoire avec des modèles de tous les fichiers nécessaires pour démarrer un nouveau module, conformément aux "meilleures pratiques" récentes pour le développement de modules, et s'invoque depuis la ligne de commande, ainsi : 
module-starter --module=Foo::Bar \
   --author="Votre Nom" --email=votrenom@cpan.org

Si vous ne souhaitez pas installer le paquet Module::Starter de CPAN, h2xs est un outil plus ancien, initialement destiné au développement de modules XS, qui est inclus dans la distribution Perl.

Une invocation typique de h2xs pour un module pur Perl est :

h2xs -AX --skip-exporter --use-new-tests -n Foo::Bar

Le "-A" omet le code Autoloader, le "-X" omet les éléments XS, "--skip-exporter" omet le code Exporter, "--use-new-tests" met en place un environnement de test moderne, et "-n" spécifie le nom du module.

Utilisez strict et warnings
Le code d'un module doit être propre en termes de warnings et de strict, car vous ne pouvez pas garantir les conditions dans lesquelles il sera utilisé. De plus, vous ne voudriez pas distribuer de code qui ne serait pas propre en termes de warnings ou de strict, n'est-ce pas ?
Utilisez Carp
Le module Carp vous permet de présenter vos messages d'erreur du point de vue de l'appelant ; cela vous donne un moyen de signaler un problème avec l'appelant et non avec votre module. Par exemple, si vous dites ceci : 
warn "Aucun nom d'hôte donné";

l'utilisateur verra quelque chose comme ceci :

Aucun nom d'hôte donné à
/usr/local/lib/perl5/site_perl/5.6.0/Net/Acme.pm ligne 123.

ce qui donne l'impression que votre module fait quelque chose de mal. Au lieu de cela, vous voulez blâmer l'utilisateur et dire ceci :

Aucun nom d'hôte donné à mauvais_code, ligne 10.

Vous faites cela en utilisant Carp et en remplaçant vos "warn" par des "carp". Si vous avez besoin de "die", dites "croak" à la place. Cependant, conservez "warn" et "die" pour vos vérifications de cohérence - là où c'est vraiment votre module qui est en faute.

Utilisez Exporter - judicieusement !
Exporter vous donne un moyen standard d'exporter des symboles et des sous-routines depuis votre module dans l'espace de noms de l'appelant. Par exemple, dire "use Net::Acme qw(&frob)" importerait la sous-routine "frob"<

La variable de package @EXPORT déterminera quels symboles seront exportés lorsque l'appelant dit simplement "use Net::Acme" - vous ne voudrez presque jamais rien y mettre. @EXPORT_OK, en revanche, spécifie quels symboles vous êtes prêt à exporter. Si vous souhaitez exporter un ensemble de symboles, utilisez le %EXPORT_TAGS et définissez un ensemble d'exportation standard - regardez Exporter pour plus de détails.

Utiliser la vieille documentation
Le travail n'est pas terminé tant que la paperasse n'est pas faite, et vous devrez consacrer du temps à rédiger de la documentation pour votre module. "module-starter" ou "h2xs" vous fourniront un squelette à compléter ; si vous n'êtes pas sûr du format, regardez perlpod pour une introduction. Fournissez un bon résumé de la façon dont votre module est utilisé dans le code, une description, puis des notes sur la syntaxe et la fonction des sous-programmes ou méthodes individuels. Utilisez des commentaires Perl pour les notes du développeur et POD pour les notes de l'utilisateur final.
Écrire des tests
Vous êtes encouragé à créer des auto-tests pour votre module afin de vous assurer qu'il fonctionne comme prévu sur la myriade de plateformes que Perl prend en charge ; si vous téléchargez votre module sur CPAN, une foule de testeurs construiront votre module et vous enverront les résultats des tests. Encore une fois, "module-starter" et "h2xs" fournissent un cadre de test que vous pouvez étendre - vous devriez faire plus que de simplement vérifier que votre module compile. Test::Simple et Test::More sont de bons points de démarrage lors de l'écriture d'une suite de tests.
Écrire le README
Si vous téléchargez sur CPAN, les lutins automatisés extrairont le fichier README et le placeront dans votre répertoire CPAN. Il apparaîtra également dans les répertoires principaux par module et par catégorie si vous êtes sur la liste des modules. Il est bon de mettre ici ce que le module fait en détail.
Écrire les Changes
Ajoutez toutes les modifications visibles par l'utilisateur depuis la dernière version à votre fichier Changes.

Pas à pas : Distribution de votre module

Obtenir un identifiant utilisateur CPAN
Chaque développeur publiant des modules sur CPAN a besoin d'un identifiant CPAN. Visitez "https://pause.perl.org/", sélectionnez "Request PAUSE Account" et attendez que votre demande soit approuvée par les administrateurs PAUSE.
Créer la tarball
Encore une fois, "module-starter" ou "h2xs" a fait tout le travail pour vous. Ils produisent le standard "Makefile.PL" que vous voyez lorsque vous téléchargez et installez des modules, et ceci produit un Makefile avec une cible "dist". 
perl Makefile.PL && make test && make distcheck && make dist

Une fois que vous vous êtes assuré que votre module passe ses propres tests - c'est toujours une bonne chose à vérifier - vous pouvez faire "make distcheck" pour vous assurer que tout semble correct, suivi de "make dist", et le Makefile produira idéalement une jolie tarball de votre module, prête à être téléchargée.

Télécharger la tarball
L'e-mail que vous avez reçu lors de la réception de votre identifiant CPAN vous expliquera comment vous connecter à PAUSE, le Perl Authors Upload SErver. Depuis les menus, vous pouvez télécharger votre module sur CPAN.

Alternativement, vous pouvez utiliser le script cpan-upload, faisant partie de la distribution CPAN::Uploader sur CPAN.

Corriger les bugs !
Une fois que vous commencez à avoir des utilisateurs, ils vous enverront des rapports de bugs. Si vous avez de la chance, ils vous enverront même des correctifs. Bienvenue dans les joies de la maintenance d'un projet logiciel...
