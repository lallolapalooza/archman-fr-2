PERLINTERP(1perl) Guide de référence du programmeur Perl PERLINTERP(1perl)

NOM

perlinterp - Aperçu de l'interpréteur Perl

DESCRIPTION

Ce document fournit un aperçu du fonctionnement de l'interpréteur Perl au niveau du code C, ainsi que des pointeurs vers les fichiers source C pertinents.

ÉLÉMENTS DE L'INTERPRÉTEUR

Le travail de l'interpréteur comporte deux étapes principales : la compilation du code en représentation interne, ou bytecode, et son exécution. Le document "Compiled code" dans perlguts explique exactement comment se déroule l'étape de compilation.

Voici un bref résumé du fonctionnement de Perl :

Démarrage

L'action commence dans perlmain.c. (ou miniperlmain.c pour miniperl) C'est un code de très haut niveau, suffisant pour tenir sur un seul écran, et il ressemble au code trouvé dans perlembed ; la majeure partie de l'action réelle a lieu dans perl.c

perlmain.c est généré par "ExtUtils::Miniperl" à partir de miniperlmain.c lors de la compilation, vous devriez donc compiler Perl pour suivre cela.

Tout d'abord, perlmain.c alloue de la mémoire et construit un interpréteur Perl, en gros comme suit :

1 PERL_SYS_INIT3(&argc,&argv,&env);
2
3 if (!PL_do_undump) {
4     my_perl = perl_alloc();
5     if (!my_perl)
6         exit(1);
7     perl_construct(my_perl);
8     PL_perl_destruct_level = 0;
9 }

La ligne 1 est une macro, et sa définition dépend de votre système d'exploitation. La ligne 3 fait référence à "PL_do_undump", une variable globale - toutes les variables globales dans Perl commencent par "PL_". Cela vous indique si le programme en cours d'exécution a été créé avec le flag "-u" pour perl puis undump, ce qui signifie qu'il sera faux dans tout contexte sain.

La ligne 4 appelle une fonction dans perl.c pour allouer de la mémoire pour un interpréteur Perl. C'est une fonction assez simple, dont le contenu ressemble à ceci :

my_perl = (PerlInterpreter*)PerlMem_malloc(sizeof(PerlInterpreter));

Ici, vous voyez un exemple de l'abstraction système de Perl, que nous verrons plus tard : "PerlMem_malloc" est soit le "malloc" de votre système, soit le "malloc" de Perl lui-même tel que défini dans malloc.c si vous avez sélectionné cette option lors de la configuration.

Ensuite, à la ligne 7, nous construisons l'interpréteur en utilisant perl_construct, également dans perl.c ; cela configure toutes les variables spéciales dont Perl a besoin, les piles, etc.

Maintenant, nous passons les options de ligne de commande à Perl, et nous lui disons de commencer :

if (!perl_parse(my_perl, xs_init, argc, argv, (char **)NULL))
    perl_run(my_perl);
exitstatus = perl_destruct(my_perl);
perl_free(my_perl);

"perl_parse" est en fait un wrapper autour de "S_parse_body", tel que défini dans perl.c, qui traite les options de la ligne de commande, configure les modules XS liés statiquement, ouvre le programme et appelle "yyparse" pour le parser.

Analyse (Parsing)

L'objectif de cette étape est de transformer le code source Perl en un arbre d'opérations (op tree). Nous verrons à quoi il ressemble plus tard. Strictement parlant, trois choses se déroulent ici.

"yyparse", le parseur, se trouve dans perly.c, bien qu'il soit préférable de lire l'entrée YACC d'origine dans perly.y. (Oui, Virginia, il existe bien une grammaire YACC pour Perl !) Le travail du parseur est de comprendre votre code, de le diviser en phrases, de décider quels opérandes vont avec quels opérateurs, etc.

Le parseur est noblement assisté par le lexer, qui découpe votre entrée en jetons (tokens) et détermine le type de chaque jeton : un nom de variable, un opérateur, un bareword, une sous-routine, une fonction intégrée, etc. Le point d'entrée principal du lexer est "yylex", et celui-ci ainsi que ses routines associées se trouvent dans toke.c. Perl n'est pas très différent des autres langages informatiques ; il est parfois très sensible au contexte, il peut être difficile de déterminer le type d'un jeton, ou où se termine un jeton. Par conséquent, il y a beaucoup d'interactions entre le tokeniseur et le parseur, ce qui peut être assez effrayant si vous n'y êtes pas habitué.

Au fur et à mesure que le parseur comprend un programme Perl, il construit un arbre d'opérations que l'interpréteur doit effectuer lors de l'exécution. Les routines qui construisent et relient les diverses opérations se trouvent dans op.c, et seront examinées plus tard.

Optimisation

L'étape d'analyse est maintenant terminée, et l'arbre fini représente les opérations que l'interpréteur Perl doit effectuer pour exécuter notre programme. Ensuite, Perl fait un essai sur l'arbre à la recherche d'optimisations : les expressions constantes telles que "3 + 4" seront calculées maintenant, et l'optimiseur verra également si des opérations multiples peuvent être remplacées par une seule. Par exemple, pour récupérer la variable $foo, au lieu de saisir le glob *foo et de regarder le composant scalaire, l'optimiseur modifie l'arbre d'opérations pour utiliser une fonction qui recherche directement le scalaire en question. L'optimiseur principal est "peep" dans op.c, et de nombreux ops ont leurs propres fonctions d'optimisation.

Exécution

Nous sommes enfin prêts à partir : nous avons compilé le bytecode Perl, et il ne reste plus qu'à l'exécuter. L'exécution réelle est effectuée par la fonction "runops_standard" dans run.c ; plus précisément, elle est effectuée par ces trois lignes d'apparence innocente :

while ((PL_op = PL_op->op_ppaddr(aTHX))) {
    PERL_ASYNC_CHECK();
}

Vous serez peut-être plus à l'aise avec la version Perl de ceci :

PERL_ASYNC_CHECK() while $Perl::op = &{$Perl::op->{function}};

Bon, peut-être pas. Quoi qu'il en soit, chaque op contient un pointeur de fonction, qui spécifie la fonction qui effectuera réellement l'opération. Cette fonction renverra le prochain op de la séquence - cela permet des choses comme "if" qui choisissent dynamiquement le prochain op au moment de l'exécution. Le "PERL_ASYNC_CHECK" garantit que les choses comme les signaux interrompent l'exécution si nécessaire.

Les fonctions réellement appelées sont connues sous le nom de code PP, et elles sont réparties entre quatre fichiers : pp_hot.c contient le code "chaud", qui est le plus souvent utilisé et hautement optimisé, pp_sys.c contient toutes les fonctions spécifiques au système, pp_ctl.c contient les fonctions qui implémentent les structures de contrôle ("if", "while" et similaires) et pp.c contient tout le reste. Ce sont, si vous voulez, le code C des fonctions et opérateurs intégrés de Perl.

Notez que chaque fonction "pp_" est censée renvoyer un pointeur vers l'op suivant. Les appels aux sous-routines Perl (et aux blocs eval) sont gérés dans la même boucle runops, et ne consomment pas d'espace supplémentaire sur la pile C. Par exemple, "pp_entersub" et "pp_entertry" poussent simplement une structure de bloc "CXt_SUB" ou "CXt_EVAL" sur la pile de contexte, qui contient l'adresse de l'op suivant l'appel de sous-routine ou l'eval. Ils renvoient ensuite le premier op de cette sous-routine ou de ce bloc d'eval, et l'exécution continue ainsi de cette sous-routine ou de ce bloc. Plus tard, un op "pp_leavesub" ou "pp_leavetry" dépile le "CXt_SUB" ou "CXt_EVAL", récupère l'op de retour de celui-ci et le renvoie.

Gestion des exceptions

La gestion des exceptions de Perl (c'est-à-dire "die" etc.) est construite au-dessus des fonctions C de bas niveau setjmp()/longjmp(). Celles-ci fournissent essentiellement un moyen de capturer les registres PC et SP actuels du CPU et de les restaurer plus tard : c'est-à-dire qu'un longjmp() continue au point du code où un précédent setjmp()

était fait, avec tout ce qui était plus haut dans la pile C étant perdu. (C'est pourquoi le code devrait toujours sauvegarder les valeurs en utilisant "SAVE_FOO" plutôt que dans des variables automatiques.)

Le cœur de Perl encapsule setjmp() et longjmp() dans les macros "JMPENV_PUSH" et "JMPENV_JUMP". L'opération push, ainsi que l'établissement d'un setjump(), stocke un état temporaire dans une structure locale à la fonction courante (allouée par "dJMPENV"). En particulier, elle stocke un pointeur vers la structure "JMPENV" précédente, et met à jour "PL_top_env" pour qu'il pointe vers la plus récente, formant une chaîne d'états "JMPENV". Le push et le jump peuvent produire des informations de débogage sous "perl -Dl".

Une règle de base des internes de Perl est que toutes les sorties de l'interpréteur sont réalisées via un JMPENV_JUMP(). En particulier :

  • niveau 2 : exit() au niveau Perl et my_exit() aux internes

    Ceux-ci déroulent toutes les piles, puis effectuent un JMPENV_JUMP(2).

  • niveau 3 : die() au niveau Perl et croak() aux internes

    Si l'on se trouve actuellement dans une évaluation (eval), ceux-ci retirent la pile de contexte jusqu'au cadre "CXt_EVAL" le plus proche, établissent $@ de manière appropriée, établissent "PL_restartop" sur l'op qui suit l'évaluation associée à ce cadre, puis effectuent un JMPENV_JUMP(3).

    Sinon, le message d'erreur est affiché sur "STDERR", puis il est traité comme une sortie : dérouler toutes les piles et effectuer un JMPENV_JUMP(2).

  • niveau 1 : non utilisé

    JMPENV_JUMP(1) n'est actuellement pas utilisé sauf dans perl_run().

  • niveau 0 : retour normal.

    La valeur zéro est pour un retour normal de JMPENV_PUSH()

Ainsi, l'interpréteur Perl s'attend à ce que, à tout moment, un "JMPENV_PUSH" approprié soit configuré (et à un emplacement approprié dans la pile d'appels CPU) qui puisse capturer et traiter un saut à 2 ou 3 valeurs ; et dans le cas d'un 3, démarrer une nouvelle boucle runops pour exécuter "PL_restartop" et tous les ops restants (comme expliqué sous peu).

Les points d'entrée de l'interpréteur Perl fournissent tous un tel mécanisme. Par exemple, perl_parse(), perl_run() et "call_sv(cv, G_EVAL)" contiennent tous quelque chose de similaire dans les grandes lignes à :

{
    dJMPENV;
    JMPENV_PUSH(ret);
    switch (ret) {
    case 0:                     /* retour normal de JMPENV_PUSH() */
      redo_body:
        CALLRUNOPS(aTHX);
        break;
    case 2:                     /* longjmp(2) capturé - sortie / die */
        break;
    case 3:                     /* longjmp(3) capturé - eval { die } */
        PL_op = PL_restartop;
        goto redo_body;
    }
    JMPENV_POP;
}

Une boucle runops telle que Perl_runops_standard() (telle que configurée par CALLRUNOPS()) est, dans son cœur, juste un simple :

while ((PL_op = PL_op->op_ppaddr(aTHX))) { 1; }

qui appelle la fonction pp() associée à chaque op, comptant sur elle pour retourner un pointeur vers l'op suivant à exécuter.

En plus d'établir des attrapeurs aux points d'entrée de l'interpréteur Perl, on pourrait s'attendre à ce que Perl effectue également un JMPENV_PUSH() dans des endroits comme pp_entertry(), juste avant que certains ops trappables ne soient exécutés. En fait, Perl ne fait pas normalement cela. L'inconvénient est qu'avec du code imbriqué ou récursif comme :

sub foo { my ($i) = @_; return if $i < 0; eval { foo(--$i) } }

Alors la pile C déborderait rapidement avec des paires d'entrées comme

...
#N+3 Perl_runops()
#N+2 Perl_pp_entertry()
#N+1 Perl_runops()
#N   Perl_pp_entertry()
...

Au lieu de cela, Perl place ses gardes aux *appelants* des boucles runops. Ensuite, autant d'appels de sous-routines et d'évaluations imbriqués peuvent être appelés que vous le souhaitez, le tout au sein d'une seule boucle runops. Si une exception se produit, le contrôle revient à l'appelant de la boucle, qui redémarre simplement immédiatement une nouvelle boucle avec "PL_restartop" comme prochain op à appeler.

Ainsi, en fonctionnement normal où il y a plusieurs évaluations imbriquées, il y aura plusieurs entrées de pile de contexte "CXt_EVAL", mais une seule boucle runops, protégée par un seul "JMPENV_PUSH". Chaque évaluation capturée retirera la prochaine "CXt_EVAL" de la pile, établira "PL_restartop", puis fera un longjmp() vers perl_run() et continuera.

Cependant, des ops sont parfois exécutés dans une boucle runops interne, comme dans un tie, un sort, ou un code de surcharge (overload). Dans ce cas, quelque chose comme

sub FETCH { eval { die }; .... }

provoquerait, sauf traitement spécial, un longjmp() directement vers la garde dans perl_run(), retirant *les deux* boucles runops - ce qui est clairement incorrect. Une façon d'éviter cela est que le code de tie effectue un "JMPENV_PUSH" avant d'exécuter "FETCH" dans la boucle runops interne, mais pour des raisons d'efficacité, Perl établit en fait simplement temporairement un drapeau en utilisant CATCH_SET(TRUE). Ce drapeau avertit toute opération "require", "entereval" ou "entertry" subséquente que l'appelant ne promet plus de capturer les exceptions levées en leur nom.

Ces ops vérifient ce drapeau, et s'il est vrai, ils (via docatch()) effectuent un "JMPENV_PUSH" et démarrent une nouvelle boucle runops pour exécuter le code, plutôt que de le faire avec la boucle actuelle.

Par conséquent, à la sortie du bloc d'évaluation dans le "FETCH" ci-dessus, l'exécution du code qui suit le bloc se poursuit dans la boucle interne (c'est-à-dire celle établie par pp_entertry()). Pour éviter la confusion, si une autre exception est alors levée, docatch() compare le niveau "JMPENV" de "CXt_EVAL" avec "PL_top_env" et, s'ils diffèrent, relance simplement l'exception. De cette façon, toutes les boucles internes sont retirées, et l'exception sera traitée correctement par le niveau qui l'attend.

Voici un exemple.

1: eval { tie @a, 'A' };
2: sub A::TIEARRAY {
3:     eval { die };
4:     die;
5: }

Pour exécuter ce code, perl_run() est appelé, ce qui fait un JMPENV_PUSH(), puis entre dans une boucle runops. Cette boucle exécute les ops "entereval" et "tie" à la ligne 1, l' "entereval" empilant un "CXt_EVAL" sur la pile de contexte.

Le pp_tie() effectue un CATCH_SET(TRUE), puis démarre une deuxième boucle runops pour exécuter le corps de TIEARRAY(). Lorsque la boucle exécute l'op "entertry" à la ligne 3, CATCH_GET() est vrai, donc pp_entertry() appelle docatch() qui fait un "JMPENV_PUSH" et démarre une troisième boucle runops, qui redémarre le pp_entertry(), puis exécute l'op "die". À ce stade, la pile d'appels C ressemble à ceci :

#10 Perl_pp_die()
#9  Perl_runops()      # boucle runops 3
#8  S_docatch()        # niveau JMPENV 2
#7  Perl_pp_entertry()
#6  Perl_runops()      # boucle runops 2
#5  Perl_call_sv()
#4  Perl_pp_tie()
#3  Perl_runops()      # boucle runops 1
#2  S_run_body()
#1  perl_run()         # niveau JMPENV 1
#0  main()

et les piles de contexte et de données, telles qu'affichées par "perl -Dstv", ressemblent à :

STACK 0: MAIN
  CX 0: BLOCK  =>
  CX 1: EVAL   => AV()  PV("A"\0)
  retop=leave
STACK 1: MAGIC
  CX 0: SUB    =>
  retop=(null)
  CX 1: EVAL   => *
retop=nextstate

Le die() retire la première "CXt_EVAL" de la pile de contexte, établit "PL_restartop" à partir de celle-ci, fait un JMPENV_JUMP(3), et le contrôle retourne au niveau "JMPENV" établi dans docatch(). Ceci démarre alors une autre boucle runops de troisième niveau, qui exécute les ops "nextstate", "pushmark" et "die" de la ligne 4. Au moment où le second pp_die() est appelé, la pile d'appels C ressemble exactement à celle ci-dessus, même si nous ne sommes plus dans une évaluation interne. Cependant, la pile de contexte ressemble maintenant à ceci, c'est-à-dire avec le CXt_EVAL supérieur retiré :

STACK 0: MAIN
  CX 0: BLOCK  =>
  CX 1: EVAL   => AV()  PV("A"\0)
  retop=leave
STACK 1: MAGIC
  CX 0: SUB    =>
  retop=(null)

Le die() à la ligne 4 retire la pile de contexte jusqu'au "CXt_EVAL", la laissant comme :

STACK 0: MAIN
  CX 0: BLOCK  =>

Comme d'habitude, "PL_restartop" est extrait du "CXt_EVAL", et un JMPENV_JUMP(3) est effectué, ce qui retire la pile C jusqu'à docatch() :

#8  S_docatch()        # niveau JMPENV 2
#7  Perl_pp_entertry()
#6  Perl_runops()      # boucle runops 2
#5  Perl_call_sv()
#4  Perl_pp_tie()
#3  Perl_runops()      # boucle runops 1
#2  S_run_body()
#1  perl_run()         # niveau JMPENV 1
#0  main()

Dans ce cas, parce que le niveau "JMPENV" enregistré dans le "CXt_EVAL" diffère du courant, docatch() effectue simplement un JMPENV_JUMP(3) pour relancer l'exception, et la pile C est déroulée jusqu'à :

#1  perl_run()         # niveau JMPENV 1
#0  main()

Parce que "PL_restartop" n'est pas nul, run_body() démarre une nouvelle boucle runops, et l'exécution continue.

TYPES DE VARIABLES INTERNES

Vous devriez avoir jeté un œil à perlguts à ce stade, qui vous parle des types de variables internes de Perl : SVs, HVs, AVs et le reste. Sinon, faites-le maintenant.

Ces variables sont utilisées non seulement pour représenter les variables de l'espace Perl, mais aussi toutes les constantes dans le code, ainsi que certaines structures complètement internes à Perl. Le

STRUCTURES DE DONNÉES INTERNES DE PERL

La table des symboles, par exemple, est une table de hachage Perl ordinaire. Votre code est représenté par un SV lorsqu'il est lu par l'analyseur ; tous les fichiers de programme que vous appelez sont ouverts via des descripteurs de fichiers Perl ordinaires, et ainsi de suite.

Le module principal Devel::Peek nous permet d'examiner les SV à partir d'un programme Perl. Voyons, par exemple, comment Perl traite la constante "hello".

  % perl -MDevel::Peek -e 'Dump("hello")'
1 SV = PV(0xa041450) at 0xa04ecbc
2   REFCNT = 1
3   FLAGS = (POK,READONLY,pPOK)
4   PV = 0xa0484e0 "hello"\0
5   CUR = 5
6   LEN = 6

La lecture de la sortie de "Devel::Peek" demande un peu de pratique, alors parcourons-la ligne par ligne.

La ligne 1 nous indique que nous regardons un SV qui se trouve à l'adresse 0xa04ecbc en mémoire. Les SV eux-mêmes sont des structures très simples, mais elles contiennent un pointeur vers une structure plus complexe. Dans ce cas, il s'agit d'un PV, une structure qui contient une valeur de chaîne, à l'emplacement 0xa041450. La ligne 2 est le compteur de références ; il n'y a pas d'autres références à ces données, donc il est de 1.

La ligne 3 contient les indicateurs de ce SV : il est acceptable de l'utiliser comme PV, c'est un SV en lecture seule (car c'est une constante) et les données sont un PV en interne. Ensuite, nous avons le contenu de la chaîne, à partir de l'emplacement 0xa0484e0.

La ligne 5 nous donne la longueur actuelle de la chaîne ; notez que cela n'inclut **pas** le terminateur nul. La ligne 6 n'est pas la longueur de la chaîne, mais la longueur du tampon actuellement alloué ; à mesure que la chaîne grandit, Perl étend automatiquement l'espace disponible via une routine appelée "SvGROW".

Vous pouvez accéder à n'importe laquelle de ces quantités depuis C très facilement ; ajoutez simplement "Sv" au nom du champ indiqué dans l'extrait, et vous obtenez une macro qui renvoie la valeur : SvCUR(sv) renvoie la longueur actuelle de la chaîne, SvREFCOUNT(sv) renvoie le compteur de références, "SvPV(sv, len)" renvoie la chaîne elle-même avec sa longueur, et ainsi de suite. D'autres macros pour manipuler ces propriétés se trouvent dans perlguts.

Prenons un exemple de manipulation d'un PV, à partir de "sv_catpvn", dans sv.c

 1  void
 2  Perl_sv_catpvn(pTHX_ SV *sv, const char *ptr, STRLEN len)
 3  {
 4      STRLEN tlen;
 5      char *junk;
 6      junk = SvPV_force(sv, tlen);
 7      SvGROW(sv, tlen + len + 1);
 8      if (ptr == junk)
 9          ptr = SvPVX(sv);
10      Move(ptr,SvPVX(sv)+tlen,len,char);
11      SvCUR(sv) += len;
12      *SvEND(sv) = '\0';
13      (void)SvPOK_only_UTF8(sv);          /* validate pointer */
14      SvTAINT(sv);
15  }

Ceci est une fonction qui ajoute une chaîne, "ptr", de longueur "len" à la fin du PV stocké dans "sv". La première chose que nous faisons à la ligne 6 est de nous assurer que le SV **a** un PV valide, en appelant la macro "SvPV_force" pour forcer un PV. Comme effet secondaire, "tlen" est défini à la valeur actuelle du PV, et le PV lui-même est renvoyé à "junk".

À la ligne 7, nous nous assurons que le SV aura suffisamment de place pour accueillir l'ancienne chaîne, la nouvelle chaîne et le terminateur nul. Si "LEN" n'est pas assez grand, "SvGROW" réallouera de l'espace pour nous.

Maintenant, si "junk" est identique à la chaîne que nous essayons d'ajouter, nous pouvons récupérer la chaîne directement à partir du SV ; "SvPVX" est l'adresse du PV dans le SV.

La ligne 10 effectue la concaténation réelle : la macro "Move" déplace un bloc de mémoire : nous déplaçons la chaîne "ptr" à la fin du PV, c'est-à-dire au début du PV plus sa longueur actuelle. Nous déplaçons "len" octets de type "char". Après cela, nous devons informer Perl que nous avons étendu la chaîne, en modifiant "CUR" pour refléter la nouvelle longueur. "SvEND" est une macro qui nous donne la fin de la chaîne, elle doit donc être un "\0".

La ligne 13 manipule les indicateurs ; puisque nous avons changé le PV, toutes les valeurs IV ou NV ne seront plus valides : si nous avons "$x=10; $x.="6";" nous ne voulons pas utiliser l'ancien IV de 10. "SvPOK_only_utf8" est une version spéciale sensible à UTF-8 de "SvPOK_only", une macro qui désactive les indicateurs IOK et NOK et active POK. Le dernier "SvTAINT" est une macro qui nettoie les données "tainted" si le mode "taint" est activé.

Les AV et HV sont plus compliqués, mais les SV sont de loin le type de variable le plus couramment utilisé. Après avoir vu un peu comment nous les manipulons, passons à la façon dont l'arbre des ops est construit.

ARBRES D'OPS

Tout d'abord, qu'est-ce qu'un arbre d'ops, de toute façon ? L'arbre d'ops est la représentation analysée de votre programme, comme nous l'avons vu dans notre section sur l'analyse, et c'est la séquence d'opérations que Perl effectue pour exécuter votre programme, comme nous l'avons vu dans "Exécution".

Un op est une opération fondamentale que Perl peut effectuer : toutes les fonctions intégrées et les opérateurs sont des ops, et il existe une série d'ops qui traitent des concepts dont l'interpréteur a besoin en interne : entrer et sortir d'un bloc, terminer une instruction, récupérer une variable, etc.

L'arbre d'ops est connecté de deux manières : vous pouvez imaginer qu'il y a deux "routes" à travers lui, deux ordres dans lesquels vous pouvez parcourir l'arbre. Premièrement, l'ordre d'analyse reflète la façon dont l'analyseur a compris le code, et deuxièmement, l'ordre d'exécution indique à Perl l'ordre dans lequel effectuer les opérations.

La façon la plus simple d'examiner l'arbre d'ops est d'arrêter Perl après qu'il ait fini l'analyse, et de lui demander de vider l'arbre. C'est exactement ce que font les backends de compilateur B::Terse, B::Concise et le module CPAN <B::Debug.

Regardons comment Perl voit "$x = $y + $z" :

 % perl -MO=Terse -e '$x=$y+$z'
 1  LISTOP (0x8179888) leave
 2      OP (0x81798b0) enter
 3      COP (0x8179850) nextstate
 4      BINOP (0x8179828) sassign
 5          BINOP (0x8179800) add [1]
 6              UNOP (0x81796e0) null [15]
 7                  SVOP (0x80fafe0) gvsv  GV (0x80fa4cc) *y
 8              UNOP (0x81797e0) null [15]
 9                  SVOP (0x8179700) gvsv  GV (0x80efeb0) *z
10          UNOP (0x816b4f0) null [15]
11              SVOP (0x816dcf0) gvsv  GV (0x80fa460) *x

Commençons au milieu, à la ligne 4. C'est un BINOP, un opérateur binaire, qui se trouve à l'adresse 0x8179828. L'opérateur spécifique en question est "sassign" - assignation scalaire - et vous pouvez trouver le code qui l'implémente dans la fonction "pp_sassign" dans pp_hot.c. En tant qu'opérateur binaire, il a deux enfants : l'opérateur d'addition, fournissant le résultat de "$y+$z", est tout en haut à la ligne 5, et le côté gauche est à la ligne 10.

La ligne 10 est l'op nul : il ne fait absolument rien. Qu'est-ce qu'il fait là ? Si vous voyez l'op nul, c'est un signe que quelque chose a été optimisé après l'analyse. Comme nous l'avons mentionné dans "Optimisation", l'étape d'optimisation convertit parfois deux opérations en une seule, par exemple lors de la récupération d'une variable scalaire. Lorsque cela se produit, au lieu de réécrire l'arbre d'ops et de nettoyer les pointeurs orphelins, il est plus facile de remplacer l'opération redondante par l'op nul. Initialement, l'arbre aurait ressemblé à ceci :

10          SVOP (0x816b4f0) rv2sv [15]
11              SVOP (0x816dcf0) gv  GV (0x80fa460) *x

C'est-à-dire, récupérer l'entrée "a" de la table des symboles principale, puis examiner le composant scalaire de celle-ci : "gvsv" ("pp_gvsv" dans pp_hot.c) fait justement ces deux choses.

Le côté droit, à partir de la ligne 5, est similaire à ce que nous venons de voir : nous avons l'op "add" ("pp_add", également dans pp_hot.c) qui additionne deux "gvsv".

Maintenant, qu'en est-il de ceci ?

1  LISTOP (0x8179888) leave
2      OP (0x81798b0) enter
3      COP (0x8179850) nextstate

"enter" et "leave" sont des ops de portée (scoping ops), et leur travail est d'effectuer les tâches de maintenance chaque fois que vous entrez et sortez d'un bloc : les variables lexicales sont rangées, les variables non référencées sont détruites, et ainsi de suite. Chaque programme aura ces trois premières lignes : "leave" est une liste, et ses enfants sont toutes les instructions du bloc. Les instructions sont délimitées par "nextstate", donc un bloc est une collection d'ops "nextstate", les ops à effectuer pour chaque instruction étant les enfants de "nextstate". "enter" est un op unique qui fonctionne comme un marqueur.

Voilà comment Perl a analysé le programme, de haut en bas :

 Programme
    |
Instruction
    |
    =
   / \
  /   \
 $x   +
     / \
   $y   $z

Cependant, il est impossible **d'effectuer** les opérations dans cet ordre : il faut trouver les valeurs de $y et $z avant de les additionner, par exemple. Ainsi, l'autre fil qui traverse l'arbre d'ops est l'ordre d'exécution : chaque op a un champ "op_next" qui pointe vers l'op suivant à exécuter, donc suivre ces pointeurs nous indique comment Perl exécute le code. Nous pouvons parcourir l'arbre dans cet ordre en utilisant l'option "exec" de "B::Terse" :

% perl -MO=Terse,exec -e '$x=$y+$z'
1  OP (0x8179928) enter
2  COP (0x81798c8) nextstate
3  SVOP (0x81796c8) gvsv  GV (0x80fa4d4) *y
4  SVOP (0x8179798) gvsv  GV (0x80efeb0) *z
5  BINOP (0x8179878) add [1]
6  SVOP (0x816dd38) gvsv  GV (0x80fa468) *x
7  BINOP (0x81798a0) sassign
8  LISTOP (0x8179900) leave

Ceci a probablement plus de sens pour un humain : entrer dans un bloc, commencer une instruction. Obtenir les valeurs de $y et $z, et les additionner. Trouver $x, et assigner l'un à l'autre. Puis quitter.

La manière dont Perl construit ces arbres d'ops lors du processus d'analyse peut être démêlée en examinant toke.c, le lexer, et perly.y, la grammaire YACC. Regardons le code qui construit le t

ree pour $x = $y + $z.

Premièrement, nous allons examiner la fonction "Perl_yylex" dans le lexer. Nous voulons chercher "case 'x'", où x est le premier caractère de l'opérateur. (Accessoirement, lorsque vous recherchez le code qui gère un mot-clé, vous voudrez rechercher "KEY_foo" où "foo" est le mot-clé.) Voici le code qui gère l'affectation (il y a pas mal d'opérateurs commençant par "=", donc la plupart est omis pour des raisons de brièveté) :

1    case '=':
2        s++;
         ... code qui gère == => etc. et pod ...
3        pl_yylval.ival = 0;
4        OPERATOR(ASSIGNOP);

Nous pouvons voir à la ligne 4 que notre type de jeton est "ASSIGNOP" ("OPERATOR" est une macro, définie dans toke.c, qui renvoie le type de jeton, entre autres choses). Et "+" :

1     case '+':
2         {
3             const char tmp = *s++;
              ... code pour ++ ...
4             if (PL_expect == XOPERATOR) {
                  ...
5                 Aop(OP_ADD);
6             }
              ...
7         }

La ligne 4 vérifie quel type de jeton nous attendons. "Aop" renvoie un jeton. Si vous recherchez "Aop" ailleurs dans toke.c, vous verrez qu'il renvoie un jeton "ADDOP".

Maintenant que nous connaissons les deux types de jetons que nous voulons rechercher dans l'analyseur syntaxique, prenons le morceau de perly.y dont nous avons besoin pour construire l'arbre pour "$x = $y + $z"

1 term    :   term ASSIGNOP term
2                { $$ = newASSIGNOP(OPf_STACKED, $1, $2, $3); }
3         |   term ADDOP term
4                { $$ = newBINOP($2, 0, scalar($1), scalar($3)); }

Si vous n'êtes pas habitué à lire des grammaires BNF, voici comment cela fonctionne : Vous recevez certains éléments du tokeniseur, qui finissent généralement en majuscules. "ADDOP" et "ASSIGNOP" sont des exemples de "symboles terminaux", car vous ne pouvez pas obtenir plus simple qu'eux.

La grammaire, lignes un et trois de l'extrait ci-dessus, vous indique comment construire des formes plus complexes. Ces formes complexes, "symboles non terminaux" sont généralement placées en minuscules. "term" est ici un symbole non terminal, représentant une expression unique.

La grammaire vous donne la règle suivante : vous pouvez créer la chose à gauche des deux-points si vous voyez toutes les choses à droite en séquence. Ceci s'appelle une "réduction", et le but de l'analyse syntaxique est de réduire complètement l'entrée. Il existe plusieurs façons différentes d'effectuer une réduction, séparées par des barres verticales : ainsi, "term" suivi de "=" suivi de "term" fait un "term", et "term" suivi de "+" suivi de "term" peut aussi faire un "term".

Donc, si vous voyez deux termes avec un "=" ou "+" entre eux, vous pouvez les transformer en une seule expression. Lorsque vous le faites, vous exécutez le code dans le bloc de la ligne suivante : si vous voyez "=", vous exécuterez le code à la ligne 2. Si vous voyez "+", vous exécuterez le code à la ligne 4. C'est ce code qui contribue à l'arbre d'opérations.

|   term ADDOP term
{ $$ = newBINOP($2, 0, scalar($1), scalar($3)); }

Ce que cela fait, c'est créer une nouvelle opération binaire et lui fournir un certain nombre de variables. Les variables font référence aux jetons : $1 est le premier jeton de l'entrée, $2 le second, et ainsi de suite - pensez aux références arrière des expressions régulières. $$ est l'opération renvoyée par cette réduction. Ainsi, nous appelons "newBINOP" pour créer un nouvel opérateur binaire. Le premier paramètre de "newBINOP", une fonction dans op.c, est le type d'opération. C'est un opérateur d'addition, donc nous voulons que le type soit "ADDOP". Nous pourrions le spécifier directement, mais il est juste là comme deuxième jeton de l'entrée, donc nous utilisons $2. Le deuxième paramètre est les drapeaux de l'opération : 0 signifie "rien de spécial". Ensuite, les éléments à ajouter : le côté gauche et le côté droit de notre expression, dans un contexte scalaire.

Les fonctions qui créent des opérations, qui ont des noms comme "newUNOP" et "newBINOP", appellent une fonction "de vérification" associée à chaque type d'opération, avant de renvoyer l'opération. Les fonctions de vérification peuvent manipuler l'opération comme elles le souhaitent, et même la remplacer par une toute nouvelle. Ces fonctions sont définies dans op.c et ont un préfixe "Perl_ck_". Vous pouvez découvrir quelle fonction de vérification est utilisée pour un type d'opération particulier en regardant dans regen/opcodes. Prenez "OP_ADD", par exemple. ("OP_ADD" est la valeur du jeton de Aop(OP_ADD) dans toke.c que l'analyseur syntaxique transmet à "newBINOP" comme premier argument.) Voici la ligne pertinente :

add             addition (+)            ck_null         IfsT2   S S

La fonction de vérification dans ce cas est "Perl_ck_null", qui ne fait rien. Regardons un cas plus intéressant :

readline        <HANDLE>                ck_readline     t%      F?

Et voici la fonction de op.c :

 1 OP *
 2 Perl_ck_readline(pTHX_ OP *o)
 3 {
 4     PERL_ARGS_ASSERT_CK_READLINE;

 7          OP *kid = cLISTOPo->op_first;
 8          if (kid->op_type == OP_RV2GV)
 9              kid->op_private |= OPpALLOW_FAKE;
10     }
11     else {
12         OP * const newop
13             = newUNOP(OP_READLINE, 0, newGVOP(OP_GV, 0,

Un aspect particulièrement intéressant est que si l'opération n'a pas d'enfants (c'est-à-dire, readline() ou "<>"), l'opération est libérée et remplacée par une toute nouvelle qui référence *ARGV (lignes 12-16).

PILAGES

Lorsque Perl exécute quelque chose comme "addop", comment transmet-il ses résultats à l'opération suivante ? La réponse est, grâce à l'utilisation de pilages. Perl a un certain nombre de pilages pour stocker les choses sur lesquelles il travaille actuellement, et nous examinerons les trois plus importants ici.

Pilage d'arguments

Les arguments sont passés au code PP et renvoyés depuis le code PP en utilisant le pilage d'arguments, "ST". La manière typique de gérer les arguments est de les dépiler, de les traiter comme vous le souhaitez, puis de remettre le résultat sur le pilage. C'est ainsi, par exemple, que fonctionne l'opérateur cosinus :

NV value;
value = POPn;
value = Perl_cos(value);
XPUSHn(value);

Nous verrons un exemple plus délicat de ceci lorsque nous considérerons les macros de Perl ci-dessous. "POPn" vous donne la valeur NV (valeur en virgule flottante) du SV supérieur sur le pilage : le $x dans cos($x). Ensuite, nous calculons le cosinus et remettons le résultat sous forme de NV. Le "X" dans "XPUSHn" signifie que le pilage doit être étendu si nécessaire - cela ne peut pas être nécessaire ici, car nous savons qu'il y a de la place pour un élément de plus sur le pilage, puisque nous venons d'en retirer un ! Les macros "XPUSH*" garantissent au moins la sécurité.

Alternativement, vous pouvez manipuler le pilage directement : "SP" vous donne le premier élément de votre portion de pilage, et "TOP*" vous donne le SV/IV/NV/etc. supérieur sur le pilage. Ainsi, par exemple, pour faire une négation unaire d'un entier :

SETi(-TOPi);

Définissez simplement la valeur entière du sommet du pilage à sa négation.

La manipulation du pilage d'arguments dans le noyau est exactement la même qu'en XSUBs - voir perlxstut, perlxs et perlguts pour une description plus longue des macros utilisées dans la manipulation des pilages.

Pilage de marqueurs

Je dis "votre portion de pilage" ci-dessus car le code PP n'a pas nécessairement toute la portée du pilage pour lui-même : si votre fonction appelle une autre fonction, vous ne voudrez exposer que les arguments destinés à la fonction appelée, et pas nécessairement lui permettre d'accéder à vos propres données. La façon dont nous faisons cela est d'avoir un fond de pilage "virtuel", exposé à chaque fonction. Le pilage de marqueurs conserve des marque-pages aux emplacements du pilage d'arguments utilisables par chaque fonction. Par exemple, lors du traitement d'une variable liée, (interne, quelque chose avec la magie "P") Perl doit appeler des méthodes pour les accès aux variables liées. Cependant, nous devons séparer les arguments exposés à la méthode des arguments exposés à la fonction d'origine - le stockage ou la récupération ou quoi que ce soit d'autre. Voici à peu près comment le "push" lié est implémenté ; voir "av_push" dans av.c :

1  PUSHMARK(SP);
2  EXTEND(SP,2);
3  PUSHs(SvTIED_obj((SV*)av, mg));
4  PUSHs(val);
5  PUTBACK;
6  ENTER;
7  call_method("PUSH", G_SCALAR|G_DISCARD);
8  LEAVE;

Examinons l'implémentation complète, pour s'entraîner :

1  PUSHMARK(SP);

Pousse l'état actuel du pointeur de pilage sur le pilage de marqueurs. Ceci afin que, lorsque nous aurons fini d'ajouter des éléments au pilage d'arguments, Perl sache combien de choses nous avons ajoutées récemment.

2  EXTEND(SP,2);
3  PUSHs(SvTIED_obj((SV*)av, mg));
4  PUSHs(val);

Nous allons ajouter deux éléments supplémentaires au pilage d'arguments : lorsque vous avez un tableau lié, la sous-routine "PUSH" reçoit l'objet et la valeur à empiler, et c'est exactement ce que nous avons ici - l'objet lié, récupéré avec "SvTIED_obj", et la valeur, le SV "val".

5  PUTBACK;

Ensuite, nous disons à Perl de mettre à jour le pointeur de pilage global à partir de notre variable interne : "dSP" ne nous a donné qu'une copie locale, pas une référence au global.

6  ENTER;
7  call_method("PUSH
", G_SCALAR|G_DISCARD); 8 LEAVE;

"ENTER" et "LEAVE" localisent un bloc de code - ils s'assurent que toutes les variables sont rangées, que tout ce qui a été localisé retrouve sa valeur précédente, etc. Pensez-y comme aux "{" et "}" d'un bloc Perl.

Pour effectuer réellement l'appel de méthode magique, nous devons appeler une sous-routine dans l'espace Perl : "call_method" s'en charge, et elle est décrite dans perlcall. Nous appelons la méthode "PUSH" dans un contexte scalaire, et nous allons ignorer sa valeur de retour. La fonction call_method() retire le dernier élément de la pile des marques, il n'y a donc rien à nettoyer pour l'appelant.

Pile de sauvegarde

C n'a pas de concept de portée locale, donc Perl en fournit une. Nous avons vu que "ENTER" et "LEAVE" sont utilisés comme des accolades de portée ; la pile de sauvegarde implémente l'équivalent C de, par exemple :

{
    local $foo = 42;
    ...
}

Voir "Localizing changes" dans perlguts pour savoir comment utiliser la pile de sauvegarde.

MILLIONS DE MACROS

Une chose que vous remarquerez dans le code source de Perl est qu'il est plein de macros. Certains ont appelé l'utilisation omniprésente des macros la chose la plus difficile à comprendre, d'autres trouvent qu'elle ajoute à la clarté. Prenons un exemple, une version simplifiée du code qui implémente l'opérateur d'addition :

 1  PP(pp_add)
 2  {
 3      dSP; dATARGET;
 4      tryAMAGICbin_MG(add_amg, AMGf_assign|AMGf_numeric);
 5      {
 6        dPOPTOPnnrl_ul;
 7        SETn( left + right );
 8        RETURN;
 9      }
10  }

Chaque ligne ici (à part les accolades, bien sûr) contient une macro. La première ligne configure la déclaration de la fonction comme Perl l'attend pour le code PP ; la ligne 3 configure les déclarations de variables pour la pile d'arguments et la cible, la valeur de retour de l'opération. La ligne 4 essaie de voir si l'opération d'addition est surchargée ; si c'est le cas, la sous-routine appropriée est appelée.

La ligne 6 est une autre déclaration de variable - toutes les déclarations de variables commencent par "d" - qui dépile du sommet de la pile d'arguments deux NV (d'où "nn") et les place dans les variables "right" et "left", d'où le "rl". Ce sont les deux opérandes de l'opérateur d'addition. Ensuite, nous appelons "SETn" pour définir le NV de la valeur de retour au résultat de l'addition des deux valeurs. Ceci fait, nous retournons - la macro "RETURN" s'assure que notre valeur de retour est correctement gérée, et nous passons l'opérateur suivant à exécuter à la boucle d'exécution principale.

La plupart de ces macros sont expliquées dans perlapi, et certaines des plus importantes sont également expliquées dans perlxs. Portez une attention particulière à "Background and MULTIPLICITY" dans perlguts pour des informations sur les macros "[pad]THX_?".
