PERF-REPORT(1) Manuel perf PERF-REPORT(1)

NOM

perf-report - Lire perf.data (créé par perf record) et afficher le profil

SYNTAXE

perf report [-i <fichier> | --input=fichier]

DESCRIPTION

Cette commande affiche les informations de profil des compteurs de performance enregistrées via perf record.

OPTIONS

-i, --input=

Nom du fichier d'entrée. (par défaut : perf.data sauf si stdin est un tube nommé)

-v, --verbose

Être plus verbeux. (afficher l'adresse du symbole, etc.)

-q, --quiet

Ne pas afficher les avertissements ou messages. (Supprime -v)

-n, --show-nr-samples

Afficher le nombre d'échantillons pour chaque symbole

--show-cpu-utilization

Afficher le pourcentage d'échantillons pour différents modes de CPU.

-T, --threads

Afficher les compteurs d'événements par thread. Le fichier de données d'entrée doit être enregistré avec l'option -s.

-c, --comms=

Ne considérer que les symboles de ces communications. CSV qui comprend les entrées file://nom_de_fichier. Cette option affectera le pourcentage des colonnes de surcharge et de latence. Voir --percentage pour plus d'informations.

--pid=

Afficher uniquement les événements pour l'ID de processus donné (liste séparée par des virgules).

--tid=

Afficher uniquement les événements pour l'ID de thread donné (liste séparée par des virgules).

-d, --dsos=

Ne considérer que les symboles de ces DSO (Dynamic Shared Objects). CSV qui comprend les entrées file://nom_de_fichier. Cette option affectera le pourcentage des colonnes de surcharge et de latence. Voir --percentage pour plus d'informations.

-S, --symbols=

Ne considérer que ces symboles. CSV qui comprend les entrées file://nom_de_fichier. Cette option affectera le pourcentage des colonnes de surcharge et de latence. Voir --percentage pour plus d'informations.

--symbol-filter=

Afficher uniquement les symboles qui correspondent (partiellement) à ce filtre.

-U, --hide-unresolved

Afficher uniquement les entrées résolues en un symbole.

--parallelism

Ne considérer que ces niveaux de parallélisme. Le niveau de parallélisme est le nombre de threads activement exécutés sur les CPU au moment de l'échantillon. L'indicateur accepte un nombre unique, une liste séparée par des virgules et des plages (par exemple : "1", "7,8", "1,64-128"). Ceci est utile pour comprendre ce que fait un programme pendant les phases séquentielles/faiblement parallèles par rapport aux phases fortement parallèles. Cette option affectera le pourcentage des colonnes de surcharge et de latence. Voir --percentage pour plus d'informations. Voir également la section ‘Surcharges CPU et latence’ pour plus de détails.

--latency

Afficher un profil centré sur la latence plutôt que le profil par défaut centré sur la consommation CPU (nécessite l'indicateur perf record --latency).

-s, --sort=

Trier les entrées de l'histogramme par clé(s) donnée(s) - plusieurs clés peuvent être spécifiées au format CSV. Les clés de tri suivantes sont disponibles : pid, comm, dso, symbol, parent, cpu, socket, srcline, weight, local_weight, cgroup_id, addr. 
Chaque clé a la signification suivante :
•comm : commande (nom) de la tâche lisible via /proc/<pid>/comm
•pid : commande et tid de la tâche
•tgid : commande et tgid de la tâche
•dso : nom de la bibliothèque ou du module exécuté au moment de l'échantillon
•dso_size : taille de la bibliothèque ou du module exécuté au moment de l'échantillon
•symbol : nom de la fonction exécutée au moment de l'échantillon
•symbol_size : taille de la fonction exécutée au moment de l'échantillon
•parent : nom de la fonction correspondant au filtre regex parent. Les entrées non correspondantes sont affichées comme "[autre]".
•cpu : numéro du CPU sur lequel la tâche s'exécutait au moment de l'échantillon
•socket : numéro du socket processeur sur lequel la tâche s'exécutait au moment de l'échantillon
•parallelism : nombre de threads actifs au moment de l'échantillon
•srcline : nom de fichier et numéro de ligne exécutés au moment de l'échantillon. Les informations de débogage DWARF doivent être fournies.
•srcfile : nom du fichier source des échantillons. Nécessite des informations de débogage DWARF.
•weight : poids spécifique à l'événement, par exemple latence mémoire ou coût d'abandon de transaction. C'est le poids global.
•local_weight : version locale du poids ci-dessus.
•cgroup_id : ID dérivé de l'appareil de l'espace de noms cgroup et des numéros d'inode.
•cgroup : chemin d'accès cgroup dans le système de fichiers cgroup.
•transaction : indicateurs d'abandon de transaction.
•overhead : pourcentage de surcharge CPU de l'échantillon.
•latency : pourcentage de surcharge de latence (temps réel) de l'échantillon. Voir la section ‘Surcharges CPU et latence’ pour plus de détails.
•overhead_sys : pourcentage de surcharge CPU de l'échantillon s'exécutant en mode système
•overhead_us : pourcentage de surcharge CPU de l'échantillon s'exécutant en mode utilisateur
•overhead_guest_sys : pourcentage de surcharge CPU de l'échantillon s'exécutant en mode système sur une machine virtuelle
•overhead_guest_us : pourcentage de surcharge CPU de l'échantillon s'exécutant en mode utilisateur sur une machine virtuelle
•sample : nombre d'échantillons
•period : nombre brut de comptages d'événements de l'échantillon
•time : sépare les échantillons par horodatage avec la résolution spécifiée par --time-quantum (par défaut 100 ms). Spécifier avec la surcharge et avant celle-ci.
•code_page_size : la taille de page de code de l'adresse de code échantillonnée (ip)
•ins_lat : latence d'instruction en cycles de cœur. C'est la latence globale d'instruction
•local_ins_lat : version locale de la latence d'instruction
•p_stage_cyc : Sur powerpc, cela représente le nombre de cycles passés dans une étape de pipeline. Et actuellement pris en charge uniquement sur powerpc.
•addr : adresse virtuelle (complète) de l'instruction échantillonnée
•retire_lat : Sur x86, cela rapporte le blocage de pipeline de cette instruction par rapport à l'instruction précédente en cycles. Et actuellement pris en charge uniquement sur x86
•simd : indicateurs décrivant une opération SIMD. "e" pour le prédicat vide d'Arm SVE. "p" pour le prédicat partiel d'Arm SVE
•type : type de données de l'accès mémoire échantillonné.
•typeoff : décalage dans le type de données de l'accès mémoire échantillonné.
•symoff : décalage dans le symbole.
•weight1 : valeur moyenne du poids spécifique à l'événement (1er champ de weight_struct).
•weight2 : valeur moyenne du poids spécifique à l'événement (2ème champ de weight_struct).
•weight3 : valeur moyenne du poids spécifique à l'événement (3ème champ de weight_struct). 
Par défaut, les clés overhead, comm, dso et symbol sont utilisées.
(c'est-à-dire --sort overhead,comm,dso,symbol).
Si l'option --branch-stack est utilisée, les clés de tri suivantes sont également
disponibles :
•dso_from : nom de la bibliothèque ou du module d'où provient le saut
•dso_to : nom de la bibliothèque ou du module vers lequel le saut a été effectué
•symbol_from : nom de la fonction d'où provient le saut
•symbol_to : nom de la fonction vers laquelle le saut a été effectué
•srcline_from : fichier source et ligne d'où provient le saut
•srcline_to : fichier source et ligne vers lesquels le saut a été effectué
•mispredict : "N" pour branche prédite, "Y" pour branche mal prédite
•in_tx : branche dans une transaction TSX
•abort : abandon de transaction TSX.
•cycles : cycles dans le bloc de base 
Et les clés de tri par défaut sont modifiées en comm, dso_from, symbol_from, dso_to
et symbol_to, voir '--branch-stack'.
Lorsque la clé de tri symbol est spécifiée, les colonnes "IPC" et "IPC Coverage"
sont activées automatiquement. La colonne "IPC" affiche l'IPC moyen par fonction
et la colonne "IPC coverage" affiche le pourcentage
de instructions avec IPC échantillonné dans cette fonction. IPC signifie Instructions Par Cycle. S'il est bas, cela indique qu'il peut y avoir un goulot d'étranglement de performance lors de l'exécution de la fonction, tel qu'un goulot d'étranglement d'accès mémoire. Si une fonction a une surcharge élevée et un IPC faible, il est utile de l'analyser davantage pour optimiser ses performances. 
Si l'option --mem-mode est utilisée, les clés de tri suivantes sont également disponibles
(incompatibles avec --branch-stack) :
symbol_daddr, dso_daddr, locked, tlb, mem, snoop, dcacheline, blocked.
•symbol_daddr : nom du symbole de données sur lequel l'exécution est en cours au moment de l'échantillon
•dso_daddr : nom de la bibliothèque ou du module contenant les données sur lesquelles l'exécution est en cours au moment de l'échantillon
•locked : si le bus était verrouillé au moment de l'échantillon
•tlb : type d'accès TLB pour les données au moment de l'échantillon
•mem : type d'accès mémoire pour les données au moment de l'échantillon
•snoop : type de snoop (le cas échéant) pour les données au moment de l'échantillon
•dcacheline : la ligne de cache sur laquelle se trouve l'adresse des données au moment de l'échantillon
•phys_daddr : adresse physique des données sur lesquelles l'exécution est en cours au moment de l'échantillon
•data_page_size : la taille de page des données sur lesquelles l'exécution est en cours au moment de l'échantillon
•blocked : raison du blocage de l'accès de lecture pour les données au moment de l'échantillon 
Et les clés de tri par défaut sont modifiées en local_weight, mem, sym, dso,
symbol_daddr, dso_daddr, snoop, tlb, locked, blocked, local_ins_lat,
voir '--mem-mode'.
Si le fichier de données contient des événements de tracepoint, les clés de tri (dynamiques) suivantes
sont également disponibles :
trace, trace_fields, [<event>.]<field>[/raw]
•trace : sortie de trace formatée joliment en une seule colonne
•trace_fields : champs dans les tracepoints dans des colonnes séparées
•<nom_du_champ> : événement optionnel et nom du champ pour un champ spécifique 
La dernière forme se compose des noms d'événement et de champ. Si le nom de l'événement est
omis, il recherche dans tous les événements le nom de champ correspondant. Le champ
correspondant ne sera affiché que pour l'événement qui possède ce champ. Le nom de l'événement
prend en charge la correspondance de sous-chaînes afin que l'utilisateur n'ait pas besoin de spécifier
le nom complet du sous-système et de l'événement à chaque fois. Par exemple, l'événement 'sched:sched_switch' peut
être abrégé en 'switch' tant qu'il n'est pas ambigu. L'événement peut également
être spécifié par son index (à partir de 1) précédé de '%'.
Ainsi, '%1' est le premier événement, '%2' est le second, et ainsi de suite.
Le nom du champ peut avoir un suffixe '/raw' qui désactive le formatage et affiche la valeur brute du champ,
comme des nombres hexadécimaux. L'option --raw-trace a le même effet pour toutes les clés de tri dynamiques.
Les clés de tri par défaut sont modifiées en 'trace' si tous les événements du fichier de données sont des tracepoints.

-F, --fields=

Spécifiez les champs de sortie - plusieurs clés peuvent être spécifiées au format CSV. Les champs suivants sont disponibles : overhead, latency, overhead_sys, overhead_us, overhead_children, sample, period, weight1, weight2, weight3, ins_lat, p_stage_cyc et retire_lat. Les trois derniers noms sont des alias pour les poids correspondants. Lorsque les champs de poids sont utilisés, ils affichent la valeur moyenne du poids. 
Il peut également contenir des clés de tri.
Par défaut, toutes les clés de tri non spécifiées dans -F seront ajoutées
automatiquement.
Si les clés commencent par un préfixe '+', elles ajouteront les champs spécifiés
à l'ordre par défaut des champs. Par exemple : perf report -F +period,sample.

-p, --parent=<regex>

Un filtre regex pour identifier le parent. Le parent est un appelant de cette fonction et est recherché dans la chaîne d'appels, nécessitant donc l'enregistrement des informations de chaîne d'appels. Le modèle est au format regex étendu et vaut par défaut "^sys_|^do_page_fault", voir --sort parent.

-x, --exclude-other

N'affichez que les entrées correspondant au parent.

-w, --column-widths=<largeur[,largeur...]>

Forcez la largeur de chaque colonne à la liste fournie, pour une meilleure lisibilité sur les grands terminaux. 0 signifie aucune limite (comportement par défaut).

-t, --field-separator=

Utilisez un caractère séparateur spécial et ne complétez pas avec des espaces, en remplaçant toutes les occurrences de ce séparateur dans les noms de symboles (et autres sorties) par un caractère ., qui est ainsi le seul séparateur non valide.

-D, --dump-raw-trace

Affiche la trace brute en ASCII.

--disable-order

Désactive l'ordonnancement de la trace brute.

-g, --call-graph=<print_type,threshold[,print_limit],order,sort_key[,branch],value>

Affiche les chaînes d'appels en utilisant le type, le seuil de pourcentage minimum, la limite d'impression, l'ordre d'appel, la clé de tri, la branche optionnelle et la valeur. Notez que l'ordre n'est pas fixe, donc n'importe quel paramètre peut être donné dans un ordre arbitraire. Une exception est la limite d'impression, qui doit être précédée du seuil. 
print_type peut être :
- flat : exposition linéaire des chaînes d'appels sur une seule colonne.
- graph : utilise un arbre graphique, affichant les taux de surcharge absolus. (par défaut)
- fractal : comme graph, mais affiche les taux relatifs. Chaque branche de
         l'arbre est considérée comme un nouvel objet profilé.
- folded : les chaînes d'appels sont affichées en ligne, séparées par des points-virgules.
- none : désactive l'affichage des chaînes d'appels.
threshold est une valeur en pourcentage qui spécifie un pourcentage minimum pour être inclus dans le graphe d'appels de sortie. La valeur par défaut est de 0,5 (%).
print_limit s'applique uniquement lorsque l'interface stdio est utilisée. Il sert à limiter le nombre d'entrées de graphe d'appels dans une seule entrée hist. Notez qu'il doit être donné après le seuil (mais pas nécessairement consécutivement).
Par défaut : 0 (illimité).
order peut être :
- callee : graphe d'appels basé sur les appelés.
- caller : graphe d'appels inversé basé sur les appelants.
Par défaut : 'caller' lorsque --children est utilisé, sinon 'callee'.
sort_key peut être :
- function : comparaison sur les fonctions (par défaut)
- address : comparaison sur les adresses de code individuelles
- srcline : comparaison sur le nom du fichier source et le numéro de ligne
branch peut être :
- branch : inclure les informations de la dernière branche dans le graphe d'appels si disponibles.
          Il est généralement plus pratique d'utiliser --branch-history pour cela.
value peut être :
- percent : affiche le pourcentage de surcharge (par défaut)
- period : affiche la période de l'événement
- count : affiche le nombre d'événements

--children

Accumule la chaîne d'appels des enfants sur l'entrée parente afin qu'ils puissent apparaître dans la sortie. La sortie aura une nouvelle colonne "Children" et sera triée sur ces données. Nécessite l'enregistrement des chaînes d'appels. Voir la section ‘Calcul de la surcharge’ pour plus de détails. Activé par défaut, désactivé avec --no-children.

--max-stack

Définit la limite de profondeur de la pile lors de l'analyse de la chaîne d'appels, tout ce qui dépasse la profondeur spécifiée sera ignoré. Il s'agit d'un compromis entre la perte d'informations et un traitement plus rapide, en particulier pour les charges de travail qui peuvent avoir une très longue pile d'appels. Notez qu'en utilisant l'option --itrace, la taille de la chaîne d'appels synthétisée remplacera cette valeur si la taille de la chaîne d'appels synthétisée est plus grande. 
Par défaut : 127

-G, --inverted

Alias pour le graphe d'appels inversé basé sur l'appelant.

--ignore-callees=<regex>

Ignore les appelés de la ou des fonctions correspondant à l'expression régulière donnée. Cela a pour effet de collecter les appelants de chaque fonction correspondante en un seul endroit dans l'arbre du graphe d'appels.

--pretty=<key>

Style de formatage. clé : normal, raw

--stdio

Utilise l'interface stdio.

--stdio-color

always, never ou auto, permettant de configurer la sortie couleur via la ligne de commande, en plus de via "color.ui" .perfconfig. Utilisez --stdio-color always pour générer de la couleur même lors de la redirection vers un pipe ou un fichier. Utiliser simplement --stdio-color équivaut à utiliser always.

--tui

Utilise l'interface TUI, qui est intégrée à l'annotation et permet de zoomer dans les DSO ou les threads, entre autres fonctionnalités. L'utilisation de --tui nécessite un tty, si aucun n'est présent, comme lors du piping vers d'autres commandes, l'interface stdio est utilisée.

--gtk

Utilise l'interface GTK2.

-k, --vmlinux=<fichier>

chemin du vmlinux

--ignore-vmlinux

Ignore les fichiers vmlinux.

--kallsyms=<fichier>

chemin des kallsyms

-m, --modules

Charge les symboles des modules. ATTENTION : Ceci ne doit être utilisé qu'avec -k et un noyau LIVE.

-f, --force

Ne pas effectuer la validation de propriété.

--symfs=<répertoire>

Recherche les fichiers avec des symboles relatifs à ce répertoire.

-C, --cpu

Ne rapportez que les échantillons pour la liste des CPUs fournis. Plusieurs CPUs peuvent être fournis sous forme de liste séparée par des virgules sans espace : 0,1. Les plages de CPUs sont spécifiées avec - : 0-2. Par défaut, les échantillons sont rapportés sur tous les CPUs.

-M, --disassembler-style=

Définit le style du désassembleur pour objdump.

--source

Entrelace le code source avec le code assembleur. Activé par défaut, désactivé avec --no-source.

--asm-raw

Affiche le codage d'instruction brut des instructions assembleur.

--show-total-period

Affiche une colonne avec la somme des périodes.

-I, --show-info

Affiche des informations étendues sur le fichier perf.data. Cela ajoute des informations qui peuvent être très volumineuses et donc encombrer l'affichage. Il comprend actuellement : la topologie CPU et NUMA du système hôte.

-b, --branch-stack

Utilise les adresses des branches échantillonnées prises au lieu de l'adresse de l'instruction pour construire les histogrammes. Pour générer une sortie significative, le fichier perf.data doit avoir été obtenu à l'aide de perf record -b ou de perf record --branch-filter xxx où xxx est une option de filtre de branche. perf report est capable de détecter automatiquement si un fichier perf.data contient des piles de branches et passera automatiquement en mode d'affichage des branches, sauf si --no-branch-stack est utilisé.

--branch-history

Ajoute les adresses des branches échantillonnées prises à la pile d'appels. Cela permet d'examiner le chemin emprunté par le programme pour chaque échantillon. La collecte de données doit avoir utilisé -b
(ou -j) et -g. 
Afficher également avec des indicateurs de branche qui peuvent être :
- Prédites : afficher le pourcentage moyen de branches prédites.
             (nombre prédit / nombre total)
- Abandon : afficher le nombre de branches tsx abandonnées.
- Cycles : cycles dans le bloc de base.
•itérations : afficher le nombre moyen d'itérations dans la liste de la chaîne d'appels.

--addr2line=<chemin>

Chemin vers le binaire addr2line.

--objdump=<chemin>

Chemin vers le binaire objdump.

--prefix=PREFIX, --prefix-strip=N

Supprimer les N premières entrées des noms de fichiers source dans les exécutables et ajouter PREFIX. Cela permet d'afficher le code source compilé sur des systèmes avec une disposition de système de fichiers différente.

--group

Afficher les informations de groupe d'événements ensemble. Force la sortie de groupe même s'il n'y a pas de groupes définis dans le fichier de données.

--group-sort-idx

Trier la sortie par l'événement à l'index n dans le groupe. Si n est invalide, trier par le premier événement. Il peut prendre en charge plusieurs groupes avec une quantité d'événements différente. ATTENTION : Ceci doit être utilisé sur des événements groupés.

--demangle

Démêler les noms de symboles pour les rendre lisibles par l'homme. C'est activé par défaut, désactiver avec --no-demangle.

--demangle-kernel

Démêler les noms de symboles du noyau pour les rendre lisibles par l'homme (pour les noyaux C++).

--mem-mode

Utiliser les adresses de données des échantillons en plus des adresses d'instructions pour construire les histogrammes. Pour générer une sortie significative, le fichier perf.data doit avoir été obtenu en utilisant perf record -d -W et un événement spécial -e cpu/mem-loads/p ou -e cpu/mem-stores/p. Voir perf mem pour un accès plus simple.

--percent-limit

Ne pas afficher les entrées dont la surcharge est inférieure à ce pourcentage. (Par défaut : 0). Notez que cette option définit également la limite de pourcentage (seuil) des chaînes d'appels. Cependant, la valeur par défaut du seuil de chaîne d'appels est différente de la valeur par défaut des entrées d'histogramme. Veuillez consulter l'option --call-graph pour plus de détails.

--percentage

Déterminer comment afficher le pourcentage de surcharge CPU et de latence des entrées filtrées. Des filtres peuvent être appliqués par les options --comms, --dsos, --symbols et/ou --parallelism, ainsi que par des opérations de zoom sur le TUI (thread, dso, etc.). 
"relative" signifie que c'est relatif aux entrées filtrées uniquement, de sorte que la somme des entrées affichées sera toujours de 100 %. "absolute" signifie qu'elle conserve la valeur d'origine avant et après l'application du filtre.

--header

Afficher les informations d'en-tête dans le fichier perf.data. Cela inclut diverses informations comme le nom d'hôte, le système d'exploitation et la version de perf, les informations CPU/mémoire, la ligne de commande de perf, la liste des événements, etc. Actuellement, seule la sortie --stdio prend en charge cette fonctionnalité.

--header-only

Afficher uniquement l'en-tête perf.data (force --stdio).

--time

Analyser uniquement les échantillons dans une fenêtre de temps donnée : <début>,<fin>. Les temps ont le format secondes.nanosecondes. Si start n'est pas donné (c'est-à-dire que la chaîne de temps est ,x.y), l'analyse commence au début du fichier. Si le temps d'arrêt n'est pas donné (c'est-à-dire que la chaîne de temps est x.y,), l'analyse va jusqu'à la fin du fichier. Plusieurs plages peuvent être séparées par des espaces, ce qui nécessite que l'argument soit entre guillemets, par exemple --time "1234.567,1234.789 1235," 
Prend également en charge les pourcentages de temps avec plusieurs plages de temps. La chaîne de temps est 'a%/n,b%/m,...' ou 'a%-b%,c%-%d,...'.
Par exemple :
Sélectionner la deuxième tranche de temps de 10 % :
perf report --time 10%/2
Sélectionner de 0 % à 10 % de tranche de temps :
perf report --time 0%-10%
Sélectionner les première et deuxième tranches de temps de 10 % :
perf report --time 10%/1,10%/2
Sélectionner les tranches de 0 % à 10 % et de 30 % à 40 % :
perf report --time 0%-10%,30%-40%

--switch-on EVENT_NAME

Ne considérer les événements qu'après la découverte de cet événement. 
Cela peut être intéressant pour mesurer une charge de travail uniquement après la fin d'une phase d'initialisation, c'est-à-dire insérer une sonde perf à ce point, puis utiliser cette option avec cette sonde.

--switch-off EVENT_NAME

Arrêter de considérer les événements après la découverte de cet événement.

--show-on-off-events

Afficher également les événements --switch-on/off. Cela n'a aucun effet dans perf report actuellement, mais nous ferons probablement en sorte que la valeur par défaut n'affiche pas les événements de basculement on/off en mode --group et s'il n'y a qu'un seul événement autre que ceux de basculement on/off, passez directement au navigateur d'histogrammes, tout comme perf report sans événements explicitement spécifiés le fait.

--itrace

Options pour décoder les données de traçage d'instructions. Les options sont : 
i       synthétiser les événements d'instructions
y       synthétiser les événements de cycles
b       synthétiser les événements de branches
c       synthétiser les événements de branches (appels uniquement)
r       synthétiser les événements de branches (retours uniquement)
x       synthétiser les événements de transactions
w       synthétiser les événements ptwrite
p       synthétiser les événements de puissance (y compris les événements PSB pour Intel PT)

Par défaut, tous les événements sont activés, c'est-à-dire la même chose que --itrace=iybxwpe,
sauf pour perf script où c'est --itrace=ce
De plus, la période (par défaut 100000, sauf pour perf script où c'est 1)

La taille de la chaîne d'appels (par défaut 16, max 1024) pour les événements d'instructions ou de transactions peut également être spécifiée.

ignore le premier million d'instructions.

SURCHARGES CPU ET LATENCE

Il existe deux notions de temps : le temps réel (wall-clock time) et le temps CPU. Pour un programme mono-threadé, ou un programme s'exécutant sur une machine mono-cœur, ces notions sont identiques. Cependant, pour un programme multi-threadé/multi-processus s'exécutant sur une machine multi-cœur, ces notions sont significativement différentes. Chaque seconde de temps réel, nous avons un nombre de cœurs secondes de temps CPU. Perf peut mesurer les surcharges pour ces deux types de temps (affichées dans les colonnes overhead et latency pour le temps CPU et le temps réel respectivement).

Optimiser la surcharge CPU est utile pour améliorer le débit, tandis qu'optimiser la surcharge de latence est utile pour améliorer la latence. Il est important de comprendre lequel est utile dans une situation concrète. Par exemple, le premier peut être utile pour améliorer le débit maximal d'un serveur de build CI qui fonctionne à 100% d'utilisation CPU, tandis que le second peut être utile pour améliorer la latence perçue par l'utilisateur d'une compilation de programme interactif unique. Ces surcharges peuvent être significativement différentes dans certains cas. Par exemple, considérez un programme qui exécute la fonction foo pendant 9 secondes avec 1 thread, puis exécute la fonction bar pendant 1 seconde avec 128 threads (consomme 128 secondes de temps CPU). La surcharge CPU est : foo - 6,6%, bar - 93,4%. Tandis que la surcharge de latence est : foo - 90%, bar - 10%. Si nous essayons d'optimiser le temps d'exécution du programme en regardant la (mauvaise dans ce cas) surcharge CPU, nous nous concentrerions sur la fonction bar, mais cela ne pourrait produire qu'une amélioration de 10% du temps d'exécution au mieux.

Par défaut, perf affiche uniquement la surcharge CPU. Pour afficher la surcharge de latence, utilisez perf record --latency et perf report :

.ft C
Overhead  Latency  Command
  93.88%   25.79%  cc1
   1.90%   39.87%  gzip
   0.99%   10.16%  dpkg-deb
   0.57%    1.00%  as
   0.40%    0.46%  sh
.ft

Pour trier par surcharge de latence, utilisez perf report --latency :

.ft C
Latency  Overhead  Command
 39.87%     1.90%  gzip
 25.79%    93.88%  cc1
 10.16%     0.99%  dpkg-deb
  4.17%     0.29%  git
  2.81%     0.11%  objtool
.ft

Pour avoir un aperçu de la différence entre les surcharges, vous pouvez vérifier l'histogramme de parallélisation avec les options --sort=latency,parallelism,comm,symbol --hierarchy. Il montre la fraction du temps (temps réel) que la charge de travail utilise différents nombres de cœurs (colonne Parallelism). Par exemple, dans le cas suivant, la charge de travail n'utilise qu'un seul cœur la plupart du temps, mais a également des phases hautement parallèles, ce qui explique la différence significative entre les surcharges CPU et temps réel :

.ft C
  Latency  Overhead     Parallelism / Command / Symbol
+  56.98%     2.29%     1
+  16.94%     1.36%     2
+   4.00%    20.13%     125
+   3.66%    18.25%     124
+   3.48%    17.66%     126
+   3.26%     0.39%     3
+   2.61%    12.93%     123
.ft

En développant les lignes correspondantes, vous pouvez voir quelles commandes/fonctions s'exécutent au niveau de parallélisme donné :

.ft C
  Latency  Overhead     Parallelism / Command / Symbol
-  56.98%     2.29%     1
      32.80%     1.32%     gzip
       4.46%     0.18%     cc1
       2.81%     0.11%     objtool
       2.43%     0.10%     dpkg-source
       2.22%     0.09%     ld
       2.10%     0.08%     dpkg-genchanges
.ft

Pour voir le profil de fonction normal pour des niveaux de parallélisme particuliers (nombre de threads activement en cours d'exécution sur les CPU), vous pouvez utiliser le filtre --parallelism. Par exemple, pour voir le profil uniquement pour les phases de faible parallélisme d'une charge de travail, utilisez les options --latency --parallelism=1-2.

CALCUL DE LA SURCHARGE

La surcharge CPU peut être affichée dans deux colonnes comme Children et Self lorsque perf collecte les chaînes d'appels (et les colonnes Wall correspondantes pour la surcharge temps réel). La surcharge self est simplement calculée en additionnant toutes les valeurs de période de l'entrée - généralement une fonction (symbole). C'est la valeur que perf affiche traditionnellement et la somme de toutes les valeurs de surcharge self devrait être de 100%.

La surcharge children est calculée en additionnant toutes les valeurs de période des fonctions enfants afin qu'elle puisse montrer la surcharge totale des fonctions de niveau supérieur, même si elles n'exécutent pas beaucoup directement. Children signifie ici les fonctions qui sont appelées à partir d'une autre fonction (parente).

Il peut être déroutant que la somme de toutes les valeurs de surcharge children dépasse 100%, car chacune d'entre elles est déjà une accumulation de la surcharge self de ses fonctions enfants. Mais avec cela activé, les utilisateurs peuvent trouver quelle fonction a le plus de surcharge même si les échantillons sont répartis sur les enfants.

Considérez l'exemple suivant ; il y a trois fonctions comme ci-dessous.

.ft C
void foo(void) {
    /* do something */
}
void bar(void) {
    /* do something */
    foo();
}
int main(void) {
    bar()
    return 0;
}
.ft

Dans ce cas, foo est une enfant de bar, et bar est une enfant immédiate de main, donc foo est également une enfant de main. En d'autres termes, main est une parente de foo et bar, et bar est une parente de foo.

Supposons que tous les échantillons soient enregistrés uniquement dans foo et bar. Lorsqu'ils sont enregistrés avec des chaînes d'appels, la sortie affichera quelque chose comme ceci dans la sortie habituelle de perf report (qui ne montre que la surcharge self) :

.ft C
Overhead  Symbol
........  .....................
  60.00%  foo
          |
          --- foo
              bar
              main
              __libc_start_main
  40.00%  bar
          |
          --- bar
              main
              __libc_start_main
.ft

Lorsque l'option --children est activée, les valeurs de surcharge self des fonctions enfants (c'est-à-dire foo et bar) sont ajoutées aux parents pour calculer la surcharge children. Dans ce cas, le rapport pourrait être affiché comme suit :

.ft C
Children      Self  Symbol
........  ........  ....................
 100.00%     0.00%  __libc_start_main
          |
          --- __libc_start_main
 100.00%     0.00%  main
          |
          --- main
              __libc_start_main
 100.00%    40.00%  bar
          |
          --- bar
              main
              __libc_start_main
  60.00%    60.00%  foo
          |
          --- foo
              bar
              main
              __libc_start_main
.ft

Dans la sortie ci-dessus, la surcharge self de foo (60%) a été ajoutée à la surcharge children de bar, main et __libc_start_main. De même, la surcharge self de bar (40%) a été ajoutée à la surcharge children de main et \_\_libc_start_main.

Ainsi, \_\_libc_start_main et main sont affichés en premier car ils ont la même surcharge children (100%) (même s'ils ont une surcharge self nulle) et ce sont les parents de foo et bar.

Depuis la v3.16, la surcharge children est affichée par défaut et la sortie est triée selon ses valeurs. La surcharge children est désactivée en spécifiant l'option --no-children sur la ligne de commande ou en ajoutant report.children = false ou top.children = false dans le fichier de configuration perf.

perf-report(1)

NOM

perf-report - Interpréteur de rapports perf

SYNOPSIS

perf report [-i<fichier_de_données>] [options]

DESCRIPTION

perf report est un utilitaire qui permet d'interpréter les fichiers de données générés par l'outil perf. Il affiche un résumé des statistiques de performance sous forme de tableau interactif, permettant d'identifier les goulots d'étranglement dans le code.

OPTIONS

-i <fichier_de_données>
Spécifie le fichier de données d'entrée à interpréter. Par défaut, perf report utilise le fichier perf.data dans le répertoire courant.
--percent-limit <pourcentage>
N'affiche que les entrées dont la contribution est supérieure au pourcentage spécifié. Utile pour filtrer les données moins significatives.
--sort <champ>
Trie les résultats selon le champ spécifié (par exemple, comm, dso, symbol, cpu, ip).
-g, --call-graph
Affiche les graphes d'appels pour chaque entrée.
--symbol-filter <motif>
Filtre les symboles qui correspondent au motif spécifié.
--dso-filter <motif>
Filtre les bibliothèques partagées (DSO) qui correspondent au motif spécifié.
--tty <fichier_tty>
Utilise le fichier TTY spécifié pour l'affichage interactif.

SURCHARGES CPU ET LATENCE

perf report peut également afficher des informations sur les surcharges CPU et les latences introduites par le système de profilage lui-même. Ces informations sont utiles pour évaluer l'impact de perf sur les performances mesurées.

CALCUL DES SURCHARGES

Pour estimer les surcharges, il faut exécuter le même code avec et sans le profilage perf, puis comparer les résultats. La différence peut donner une indication de la surcharge.
