PERF-LIST(1) Manuel perf PERF-LIST(1)

NOM

perf-list - Lister tous les types d'événements symboliques

SYNTAXE

perf list [<options>]
            [hw|sw|cache|tracepoint|pmu|sdt|metric|metricgroup|event_glob]

DESCRIPTION

Cette commande affiche les types d'événements symboliques qui peuvent être sélectionnés dans les différentes commandes perf avec l'option -e.

OPTIONS

-d, --desc

Afficher des descriptions d'événements supplémentaires. (par défaut)

--no-desc

Ne pas afficher les descriptions.

-v, --long-desc

Afficher des descriptions d'événements plus longues et tous les PMU similaires avec des suffixes alphanumériques.

--debug

Activer la sortie de débogage.

--details

Afficher comment les événements nommés sont résolus en interne en événements perf, ainsi que toute expression supplémentaire calculée par perf stat.

--deprecated

Afficher les événements obsolètes. Par défaut, les événements obsolètes sont masqués.

--unit

Afficher les événements et métriques PMU limités au nom de PMU spécifique. (ex: --unit cpu, --unit msr, --unit cpu_core, --unit cpu_atom)

-j, --json

Sortie au format JSON.

-o, --output=

Nom du fichier de sortie. Par défaut, la sortie est écrite sur stdout.

MODIFICATEURS D'ÉVÉNEMENTS

Les événements peuvent éventuellement avoir un modificateur en ajoutant un deux-points et un ou plusieurs modificateurs. Les modificateurs permettent à l'utilisateur de restreindre les événements à compter. Les modificateurs suivants existent :

u - comptage en espace utilisateur
k - comptage noyau
h - comptage hyperviseur
I - comptage non inactif
G - comptage invité (dans les invités KVM)
H - comptage hôte (pas dans les invités KVM)
p - niveau de précision
P - utiliser le niveau de précision maximum détecté
S - lire la valeur d'échantillon (PERF_SAMPLE_READ)
D - épingler l'événement sur le PMU
W - le groupe est faible et se rabattra sur le non-groupe s'il n'est pas planifiable,
e - le groupe ou l'événement est exclusif et ne partage pas le PMU
b - utiliser l'agrégation BPF (voir perf stat --bpf-counters)
R - valeur de latence de retrait de l'événement

Le modificateur p peut être utilisé pour spécifier la précision de l'adresse d'instruction. Le modificateur p peut être spécifié plusieurs fois :

0 - SAMPLE_IP peut avoir un décalage arbitraire
1 - SAMPLE_IP doit avoir un décalage constant
2 - SAMPLE_IP demandé d'avoir un décalage de 0
3 - SAMPLE_IP doit avoir un décalage de 0, ou utilise la randomisation pour éviter
    les effets d'ombre d'échantillons.

Pour les systèmes Intel, l'échantillonnage précis des événements est implémenté avec PEBS, qui prend en charge jusqu'au niveau de précision 2, et le niveau de précision 3 pour certains cas spéciaux.

Sur les systèmes AMD, il est implémenté en utilisant IBS OP (jusqu'au niveau de précision 2). Contrairement à PEBS d'Intel qui offre des niveaux de précision, le PMU du cœur AMD est intrinsèquement imprécis et IBS est intrinsèquement précis. (c'est-à-dire que ibs_op//, ibs_op//p, ibs_op//pp et ibs_op//ppp sont tous identiques). Le modificateur précis fonctionne avec les types d'événements 0x76 (cycles cpu, horloges CPU non arrêtées) et 0xC1 (micro-opérations retirées). Les deux événements correspondent à l'échantillonnage d'exécution IBS (IBS op) avec le bit IBS Op Counter Control (IbsOpCntCtl) défini respectivement (voir la section "Core Complex (CCX) → Processor x86 Core → Instruction Based Sampling (IBS)" du [AMD Processor Programming Reference (PPR)] pertinent pour la famille, le modèle et l'étape du processeur utilisé).

Manuel Volume 2 : Programmation Système, 13.3 Échantillonnage Basé sur les Instructions). Exemples d'utilisation d'IBS :

perf record -a -e cpu-cycles:p ...    # utiliser ibs op comptant les cycles
perf record -a -e r076:p ...          # identique à -e cpu-cycles:p
perf record -a -e r0C1:p ...          # utiliser ibs op comptant les micro-opérations

DESCRIPTEUR D'ÉVÉNEMENT MATÉRIEL BRUT

Même lorsqu'un événement n'est pas disponible sous forme symbolique dans perf actuellement, il peut être encodé d'une manière spécifique au processeur.

Par exemple, sur les processeurs x86, N est une valeur hexadécimale qui représente l'encodage brut du registre avec la disposition des MSR IA32_PERFEVTSELx (voir le Manuel du développeur logiciel des architectures Intel® 64 et IA-32, Volume 3B : Guide de programmation système, Figure 30-1 Disposition des MSR IA32_PERFEVTSELx) ou les MSR PERF_CTL d'AMD (voir la section "Core Complex (CCX) → Processor x86 Core → MSR Registers" du [AMD Processor Programming Reference (PPR)] pertinent pour la famille, le modèle et l'étape du processeur utilisé).

Note : Seuls les champs de bits suivants peuvent être définis dans les registres de compteur x86 : event, umask, edge, inv, cmask. Notamment, les indicateurs de mode invité/hôte et OS/utilisateur doivent être configurés en utilisant les MODIFICATEURS D'ÉVÉNEMENTS.

Exemple :

Si la documentation Intel pour un QM720 Core i7 décrit un événement comme :

Num.   Valeur Umask  Mnémonique    Description                        Comment
A8H      01H  LSD.UOPS    Compte le nombre de micro-opérations     Utiliser cmask=1 et
                          fournies par le détecteur de flux de boucles  inverser pour compter
                                                             les cycles

l'encodage brut 0x1A8 peut être utilisé :

perf stat -e r1a8 -a sleep 1
perf record -e r1a8 ...

Il est également possible d'utiliser la syntaxe pmu :

perf record -e r1a8 -a sleep 1
perf record -e cpu/r1a8/ ...
perf record -e cpu/r0x1a8/ ...

Certains processeurs, comme ceux d'AMD, prennent en charge des codes d'événements et des masques d'unités plus grands qu'un octet. Dans de tels cas, les bits correspondant aux paramètres de configuration des événements peuvent être vus avec :

cat /sys/bus/event_source/devices/<pmu>/format/<config>

Exemple :

Si la documentation AMD pour un processeur EPYC 7713 décrit un événement comme :

Num.   Valeur Umask  Mnémonique                        Description
28FH     03H  op_cache_hit_miss.op_cache_hit  Compte les événements de succès
                                              du cache d'opérations.

l'encodage brut 0x0328F ne peut pas être utilisé car le nibble supérieur des bits EventSelect doit être spécifié via les bits 32-35, comme on peut le voir avec :

cat /sys/bus/event_source/devices/cpu/format/event

l'encodage brut 0x20000038F devrait plutôt être utilisé :

perf stat -e r20000038f -a sleep 1
perf record -e r20000038f ...

Il est également possible d'utiliser la syntaxe pmu :

perf record -e r20000038f -a sleep 1
perf record -e cpu/r20000038f/ ...
perf record -e cpu/r0x20000038f/ ...

Vous devriez consulter la documentation spécifique au processeur pour obtenir ces détails. Certains d'entre eux sont référencés dans la section VOIR AUSSI ci-dessous.

PMU ARBITRAIRES

perf prend également en charge une syntaxe étendue pour spécifier des paramètres bruts aux PMU. L'utilisation de cette fonction nécessite généralement de rechercher l'événement spécifique dans la documentation spécifique au vendeur du CPU.

Les PMU disponibles et leurs paramètres bruts peuvent être listés avec

ls /sys/bus/event_source/devices/*/format

Par exemple, l'événement brut "LSD.UOPS" du cœur pmu ci-dessus pourrait être spécifié comme

perf stat -e cpu/event=0xa8,umask=0x1,name=LSD.UOPS_CYCLES,cmask=0x1/ ...
ou en utilisant la syntaxe de nom étendue
perf stat -e cpu/event=0xa8,umask=0x1,cmask=0x1,name=\'LSD.UOPS_CYCLES:cmask=0x1\'/ ...

PMU PAR SOCKET

Certains PMU ne sont pas associés à un cœur, mais à un socket CPU entier. Les événements sur ces PMU ne peuvent généralement pas être échantillonnés, mais seulement comptés globalement avec perf stat -a. Ils peuvent être liés à un CPU logique, mais mesureront tous les cœurs du même socket.

Cet exemple mesure la bande passante mémoire chaque seconde sur le premier contrôleur mémoire du socket 0 d'un système Intel Xeon

perf stat -C 0 -a uncore_imc_0/cas_count_read/,uncore_imc_0/cas_count_write/ -I 1000 ...

Chaque contrôleur mémoire a son propre PMU. La mesure de la bande passante de l'ensemble du système nécessiterait de spécifier tous les PMU imc (voir la sortie de perf list), et d'additionner les valeurs to

ether. Pour simplifier la création de plusieurs événements, la correspondance de préfixes et d'expressions régulières est prise en charge dans le nom PMU, et le préfixe uncore_ est également ignoré lors de la correspondance. Ainsi, la commande ci-dessus peut être étendue à tous les contrôleurs mémoire en utilisant les syntaxes :

perf stat -C 0 -a imc/cas_count_read/,imc/cas_count_write/ -I 1000 ...
perf stat -C 0 -a *imc*/cas_count_read/,*imc*/cas_count_write/ -I 1000 ...

Cet exemple mesure la puissance combinée des cœurs chaque seconde

perf stat -I 1000 -e power/energy-cores/  -a

RESTRICTIONS D'ACCES

Pour les utilisateurs non root, seuls les événements PMU commutés par contexte sont généralement disponibles. Il s'agit normalement uniquement des événements du PMU CPU, des événements prédéfinis comme cycles et instructions, et de certains événements logiciels.

Les autres PMU et les mesures globales sont normalement réservés aux root. Certains qualificateurs d'événements, tels que « any », sont également réservés aux root.

Ceci peut être outrepassé en définissant le sysctl kernel.perf_event_paranoid sur -1, ce qui permet aux utilisateurs non root d'utiliser ces événements.

Pour accéder aux événements de tracepoint, perf a besoin d'un accès en lecture à /sys/kernel/tracing, même lorsque perf_event_paranoid est dans un réglage détendu.

ÉVÉNEMENTS OUTILS/HWMON

Certains événements n'ont pas de PMU associé, au lieu de cela, ils lisent des valeurs disponibles pour le logiciel sans perf_event_open. Comme ces événements ne prennent pas en charge l'échantillonnage, ils ne peuvent être lus que par des outils comme perf stat.

Les événements d'outils fournissent des temps et certains paramètres système. Les exemples incluent duration_time, user_time, system_time et num_cpus_online.

Les événements Hwmon fournissent un accès facile aux données sysfs hwmon, typiquement dans /sys/class/hwmon. Ces informations incluent les températures, les vitesses des ventilateurs et la consommation d'énergie.

TRACAGE

Certains PMU contrôlent des capacités de traçage matériel avancées, telles que Intel PT, qui permet un traçage d'exécution à faible surcharge. Celles-ci sont décrites dans un document séparé intel-pt.txt.

ÉVÉNEMENTS PARAMÉTRÉS

Certains événements pmu listés par perf-list seront affichés avec ? dedans. Par exemple :

hv_gpci/dtbp_ptitc,phys_processor_idx=?/

Cela signifie que lorsqu'il est fourni comme événement, une valeur pour ? doit également être fournie. Par exemple :

perf stat -C 0 -e 'hv_gpci/dtbp_ptitc,phys_processor_idx=0x2/' ...

QUALIFICATEURS D'ÉVÉNEMENT

Il est également possible d'ajouter des qualificateurs supplémentaires à un événement :

par cœur :

Additionne les comptes d'événements pour tous les threads matériels d'un cœur, par exemple :
  perf stat -e cpu/event=0,umask=0x3,percore=1/

cpu :

Spécifie un CPU ou une plage de CPU sur lesquels ouvrir l'événement. Il peut également référencer un PMU pour copier le masque CPU. La valeur peut être répétée pour spécifier l'ouverture de l'événement sur plusieurs CPU.
Exemple 1 : pour ouvrir l'événement instructions sur les CPU 0 et 2, l'événement cycles sur les CPU 1 et 2 :
  perf stat -e instructions/cpu=0,cpu=2/,cycles/cpu=1-2/ -a sleep 1
Exemple 2 : pour ouvrir l'événement uncore data_read sur le CPU 0 et l'événement uncore data_write sur le CPU 1 :
  perf stat -e data_read/cpu=0/,data_write/cpu=1/ -a sleep 1
Exemple 3 : pour ouvrir l'événement software msr/tsc/ uniquement sur les CPU correspondant à ceux du PMU cpu_core :
  perf stat -e msr/tsc,cpu=cpu_core/ -a sleep 1

GROUPES D'ÉVÉNEMENTS

Perf prend en charge le multiplexage d'événements basé sur le temps, lorsque le nombre d'événements actifs dépasse le nombre de compteurs de performance matériels. Le multiplexage peut entraîner des erreurs de mesure lorsque la charge de travail modifie son profil d'exécution.

Lorsque les métriques sont calculées à l'aide de formules à partir des comptes d'événements, il est utile de s'assurer que certains événements sont toujours mesurés ensemble en groupe pour minimiser les erreurs de multiplexage. Les groupes d'événements peuvent être spécifiés à l'aide de { }.

perf stat -e '{instructions,cycles}' ...

Le nombre de compteurs de performance disponibles dépend du CPU. Un groupe ne peut pas contenir plus d'événements que de compteurs disponibles. Par exemple, les CPU Intel Core disposent généralement de quatre compteurs de performance génériques pour le cœur, plus trois compteurs fixes pour les instructions, les cycles et les ref-cycles. Certains événements spéciaux ont des restrictions quant au compteur sur lequel ils peuvent être planifiés, et peuvent ne pas prendre en charge plusieurs instances dans un seul groupe. Lorsque trop d'événements sont spécifiés dans le groupe, certains d'entre eux ne seront pas mesurés.

Les événements épinglés globalement peuvent limiter le nombre de compteurs disponibles pour d'autres groupes. Sur les systèmes x86, le chien de garde NMI épingle un compteur par défaut. Le chien de garde NMI peut être désactivé en tant que root avec

echo 0 > /proc/sys/kernel/nmi_watchdog

Les événements de différents PMU ne peuvent pas être mélangés dans un groupe, à quelques exceptions près pour les événements logiciels.

ÉCHANTILLONNAGE DE LEADER

Perf prend également en charge l'échantillonnage de groupe leader en utilisant le spécificateur :S.

perf record -e '{cycles,instructions}:S' ...
perf report --group

Normalement, tous les événements d'un groupe d'événements échantillonnent, mais avec :S seul le premier événement (le leader) échantillonne, et il ne lit que les valeurs des autres événements du groupe.

Cependant, dans le cas des événements de zone AUX (par exemple, Intel PT ou CoreSight), l'événement de zone AUX doit être le leader, donc le deuxième événement échantillonne, pas le premier.

OPTIONS

Sans options, tous les événements connus seront listés.

Pour limiter la liste, utilisez :

1.hw ou hardware pour lister les événements matériels tels que les défauts de cache, etc.
2.sw ou software pour lister les événements logiciels tels que les commutations de contexte, etc.
3.cache ou hwcache pour lister les événements de cache matériels tels que L1-dcache-loads, etc.
4.tracepoint pour lister tous les événements de tracepoint, alternativement utilisez subsys_glob:event_glob pour filtrer par sous-systèmes de tracepoint tels que sched, block, etc.
5.pmu pour afficher les événements PMU fournis par le noyau.
6.sdt pour lister tous les événements de tracepoint définis statiquement.
7.metric pour lister les métriques
8.metricgroup pour lister les groupes de métriques avec des métriques.
9.Si aucun des éléments ci-dessus n'est trouvé, il appliquera l'expression régulière fournie à tous les événements, affichant ceux qui correspondent.
10.En dernier recours, il effectuera une recherche de sous-chaîne dans tous les noms d'événements.

Un ou plusieurs types peuvent être utilisés en même temps, listant les événements pour les types spécifiés.

Support du format brut :

1.--raw-dump, affiche la vidange brute de tous les événements.
2.--raw-dump [hw|sw|cache|tracepoint|pmu|event_glob], affiche la vidange brute d'un certain type d'événements.
