PERLOBJ(1perl) Guide de référence du programmeur Perl PERLOBJ(1perl)

NOM

perlobj - Référence des objets Perl

DESCRIPTION

Ce document fournit une référence pour les fonctionnalités d'orientation objet de Perl. Si vous cherchez une introduction à la programmation orientée objet en Perl, veuillez consulter perlootut.

Pour comprendre les objets Perl, vous devez d'abord comprendre les références en Perl. Voir perlreftut pour plus de détails.

Ce document décrit toutes les fonctionnalités d'orientation objet (OO) de Perl à partir de zéro. Si vous cherchez simplement à écrire votre propre code orienté objet, il est probablement préférable d'utiliser l'un des systèmes d'objets de CPAN décrits dans perlootut.

Si vous cherchez à écrire votre propre système d'objets, ou si vous devez maintenir du code qui implémente des objets à partir de zéro, ce document vous aidera à comprendre exactement comment Perl gère l'orientation objet.

Il y a quelques principes de base qui définissent l'objet orienté Perl :

1.
Un objet est simplement une structure de données qui sait à quelle classe il appartient.
2.
Une classe est simplement un paquetage. Une classe fournit des méthodes qui s'attendent à opérer sur des objets.
3.
Une méthode est simplement une sous-routine qui attend une référence à un objet (ou un nom de paquetage, pour les méthodes de classe) comme premier argument.

Examinons chacun de ces principes en profondeur.

Un Objet est Simplement une Structure de Données

Contrairement à de nombreux autres langages qui supportent l'orientation objet, Perl ne fournit aucune syntaxe spéciale pour construire un objet. Les objets sont simplement des structures de données Perl (hashes, tableaux, scalaires, descripteurs de fichiers, etc.) qui ont été explicitement associées à une classe particulière.

Cette association explicite est créée par la fonction intégrée "bless", qui est généralement utilisée dans la sous-routine de *constructeur* de la classe.

Voici un constructeur simple :

package File;
sub new {
    my $class = shift;
    return bless {}, $class;
}

Le nom "new" n'est pas spécial. Nous pourrions nommer notre constructeur autrement :

package File;
sub load {
    my $class = shift;
    return bless {}, $class;
}

La convention moderne pour les modules OO est d'utiliser toujours "new" comme nom pour le constructeur, mais il n'y a aucune obligation de le faire. Toute sous-routine qui bénit une structure de données dans une classe est un constructeur valide en Perl.

Dans les exemples précédents, le code "{}" crée une référence à un hash anonyme vide. La fonction "bless" prend ensuite cette référence et associe le hash à la classe dans $class. Dans le cas le plus simple, la variable $class finira par contenir la chaîne de caractères "File".

Nous pouvons également utiliser une variable pour stocker une référence à la structure de données qui est bénie comme notre objet :

sub new {
    my $class = shift;
    my $self = {};
    bless $self, $class;
    return $self;
}

Une fois que nous avons béni le hash référencé par $self, nous pouvons commencer à appeler des méthodes dessus. Ceci est utile si vous voulez mettre l'initialisation de l'objet dans sa propre méthode séparée :

sub new {
    my $class = shift;
    my $self = {};
    bless $self, $class;
    $self->_initialize();
    return $self;
}

Comme l'objet est aussi un hash, vous pouvez le traiter comme tel, en l'utilisant pour stocker des données associées à l'objet. Typiquement, le code à l'intérieur de la classe peut traiter le hash comme une structure de données accessible, tandis que le code à l'extérieur de la classe devrait toujours traiter l'objet comme opaque. C'est ce qu'on appelle l'encapsulation. L'encapsulation signifie que l'utilisateur d'un objet n'a pas à savoir comment il est implémenté. L'utilisateur appelle simplement des méthodes documentées sur l'objet.

Notez, cependant, que (contrairement à la plupart des autres langages OO) Perl n'assure ni ne fait respecter l'encapsulation d'aucune manière. Si vous voulez que les objets soient réellement *opaques*, vous devez vous en arranger vous-même. Cela peut être fait de diverses manières, y compris en utilisant des "objets Inside-Out" ou des modules de CPAN.

Les Objets Sont Bénis ; Les Variables Ne le Sont Pas

Lorsque nous bénissons quelque chose, nous ne bénissons pas la variable qui contient une référence à cette chose, ni la référence que la variable stocke ; nous bénissons la chose à laquelle la variable fait référence (parfois appelée le *référent*). Ceci est mieux démontré avec ce code :

use Scalar::Util 'blessed';
my $foo = {};
my $bar = $foo;
bless $foo, 'Class';
print blessed( $bar ) // 'non béni';    # affiche "Class"
$bar = "une autre valeur";
print blessed( $bar ) // 'non béni';    # affiche "non béni"

Lorsque nous appelons "bless" sur une variable, nous bénissons en réalité la structure de données sous-jacente à laquelle la variable fait référence. Nous ne bénissons pas la référence elle-même, ni la variable qui contient cette référence. C'est pourquoi le deuxième appel à blessed( $bar ) renvoie faux. À ce moment-là, $bar ne stocke plus une référence à un objet.

Vous verrez parfois d'anciens livres ou documentations mentionner "bénir une référence" ou décrire un objet comme une "référence bénie", mais c'est incorrect. Ce n'est pas la référence qui est bénie en tant qu'objet ; c'est la chose à laquelle la référence fait référence (c'est-à-dire, le référent).

Une Classe est Simplement un Paquetage

Perl ne fournit aucune syntaxe spéciale pour les définitions de classe. Un paquetage est simplement un espace de noms contenant des variables et des sous-routines. La seule différence est que dans une classe, les sous-routines peuvent attendre une référence à un objet ou le nom d'une classe comme premier argument. C'est purement une question de convention, donc une classe peut contenir à la fois des méthodes et des sous-routines qui *n'opèrent pas* sur un objet ou une classe.

Chaque paquetage contient un tableau spécial appelé @ISA. Le tableau @ISA contient une liste des classes parentes de cette classe, s'il y en a. Ce tableau est examiné lorsque Perl effectue la résolution de méthode, ce que nous aborderons plus tard.

Appeler des méthodes à partir d'un paquetage signifie qu'il doit être chargé, bien sûr, vous voudrez donc souvent charger un module et l'ajouter à @ISA en même temps. Vous pouvez le faire en une seule étape en utilisant le pragma parent. (Dans le code plus ancien, vous pourriez rencontrer le pragma base, qui est aujourd'hui déconseillé sauf si vous devez travailler avec le pragma equally déconseillé fields.)

Cependant, les classes parentes sont définies, la variable @ISA du paquetage contiendra une liste de ces parents. Il s'agit simplement d'une liste de scalaires, chacun étant une chaîne de caractères correspondant à un nom de paquetage.

Toutes les classes héritent implicitement de la classe UNIVERSAL. La classe UNIVERSAL est implémentée par le noyau Perl et fournit plusieurs méthodes par défaut, telles que isa(), can() et VERSION(). La classe "UNIVERSAL" n'apparaîtra *jamais* dans la variable @ISA d'un paquetage.

Perl fournit *uniquement* l'héritage de méthodes comme fonctionnalité intégrée. L'héritage d'attributs est laissé à la classe pour être implémenté. Voir la section "Écriture d'accesseurs" pour plus de détails.

Une Méthode est Simplement une Sous-routine

Perl ne fournit aucune syntaxe spéciale pour définir une méthode. Une méthode est simplement une sous-routine ordinaire, et est déclarée avec "sub". Ce qui rend une méthode spéciale, c'est qu'elle s'attend à recevoir soit un objet, soit un nom de classe comme premier argument.

Perl *fournit* une syntaxe spéciale pour l'invocation de méthode, l'opérateur "->". Nous aborderons cela plus en détail plus tard.

La plupart des méthodes que vous écrivez s'attendront à opérer sur des objets :

sub save {
    my $self = shift;
    open my $fh, '>', $self->path() or die $!;
    print {$fh} $self->data()       or die $!;
    close $fh                       or die $!;
}

Invocation de Méthode

Appeler une méthode sur un objet s'écrit "$object->method".

L'opérateur flèche

L'opérateur flèche "->" est la manière dont Perl fait la différence entre l'appel d'une méthode et le déréférencement d'une référence. Voici la syntaxe de base pour l'appel de méthode :

    $objet->methode( @arguments );
    $classe->methode( @arguments );

Sur la gauche de la flèche se trouve soit un objet (ou plus précisément, une référence à un objet), soit le nom d'une classe (un paquet en fait). Sur la droite se trouve le nom de la méthode à appeler.

Dans le cas où la gauche est un nom de paquet, il s'agit d'un appel de méthode de classe. Dans le cas où la gauche est un objet, il s'agit d'un appel de méthode d'instance.

my $pod = File->new( 'perlobj.pod', $data );
$pod->save();

La syntaxe "->" est également utilisée lors du déréférencement d'une référence. Cela ressemble au même opérateur, mais il s'agit de deux opérations distinctes.

Lorsque vous appelez une méthode, ce qui se trouve à gauche de la flèche est passé comme premier argument à la méthode. Cela signifie que lorsque nous appelons "Critter->new()", la méthode new() reçoit la chaîne "Critter" comme premier argument. Lorsque nous appelons "$fred->speak()", la variable $fred est passée comme premier argument à speak().

Comme pour toute sous-routine Perl, tous les arguments passés dans @_ sont des alias des arguments d'origine. Cela inclut l'objet lui-même. Si vous assignez directement à $_[0], vous modifierez le contenu de la variable qui contient la référence à l'objet. Nous vous recommandons de ne pas le faire à moins de savoir exactement ce que vous faites.

Perl sait dans quel paquet se trouve la méthode en examinant le côté gauche de la flèche. Si le côté gauche est un nom de paquet, il recherche la méthode dans ce paquet. Si le côté gauche est un objet, Perl recherche la méthode dans le paquet dans lequel l'objet a été béni.

Si le côté gauche n'est ni un nom de paquet ni un objet, l'appel de méthode provoquera une erreur, mais voir la section sur les "Variations d'appel de méthode" pour plus de nuances.

Héritage

Nous avons déjà parlé du tableau spécial @ISA et du pragma parent.

Lorsqu'une classe hérite d'une autre classe, toutes les méthodes définies dans la classe parente sont disponibles pour la classe enfant. Si vous tentez d'appeler une méthode sur un objet qui n'est pas défini dans sa propre classe, Perl recherchera également cette méthode dans les classes parentes qu'elle pourrait avoir.

package File::MP3;
use parent 'File';    # définit @File::MP3::ISA = ('File');
my $mp3 = File::MP3->new( 'Andvari.mp3', $data );
$mp3->save();

Comme nous n'avons pas défini de méthode save() dans la classe "File::MP3", Perl recherchera dans les classes parentes de "File::MP3" pour trouver la méthode save(). Si Perl ne parvient pas à trouver de méthode save() n'importe où dans la hiérarchie d'héritage, il mourra.

Dans ce cas, il trouve une méthode save() dans la classe "File". Notez que l'objet passé à save() dans ce cas est toujours un objet "File::MP3", même si la méthode est trouvée dans la classe "File".

Nous pouvons surcharger une méthode parente dans une classe enfant. Lorsque nous le faisons, nous pouvons toujours appeler la méthode de la classe parente avec la pseudo-classe "SUPER".

sub save {
    my $self = shift;
    say 'Prepare to rock';
    $self->SUPER::save();
}

Le modificateur "SUPER" peut *uniquement* être utilisé pour les appels de méthode. Vous ne pouvez pas l'utiliser pour les appels de sous-routine réguliers ou les méthodes de classe :

SUPER::save($thing);     # ÉCHEC : recherche la sous-routine save() dans le paquet SUPER
SUPER->save($thing);     # ÉCHEC : recherche la méthode save() dans la classe
                         #       SUPER
$thing->SUPER::save();   # OK : recherche la méthode save() dans les classes
                         #       parentes

Résolution de SUPER

La pseudo-classe "SUPER" est résolue à partir du paquet où l'appel est effectué. Elle n'est *pas* résolue en fonction de la classe de l'objet. Ceci est important, car cela permet aux méthodes à différents niveaux d'une hiérarchie d'héritage profonde d'appeler correctement leurs méthodes parentes respectives.

package A;
sub new {
    return bless {}, shift;
}
sub speak {
    my $self = shift;
    say 'A';
}
package B;
use parent -norequire, 'A';
sub speak {
    my $self = shift;
    $self->SUPER::speak();
    say 'B';
}
package C;
use parent -norequire, 'B';
sub speak {
    my $self = shift;
    $self->SUPER::speak();
    say 'C';
}
my $c = C->new();
$c->speak();

Dans cet exemple, nous obtiendrons la sortie suivante :

A
B
C

Cela démontre comment "SUPER" est résolu. Même si l'objet est béni dans la classe "C", la méthode speak() dans la classe "B" peut toujours appeler SUPER::speak() et s'attendre à ce qu'elle recherche correctement dans la classe parente de "B" (c'est-à-dire le paquet où se trouve l'appel de méthode), et non dans la classe parente de "C" (c'est-à-dire la classe à laquelle appartient l'objet).

Il existe des cas rares où cette résolution basée sur le paquet peut poser problème. Si vous copiez une sous-routine d'un paquet à un autre, la résolution "SUPER" sera effectuée sur la base du paquet d'origine.

Héritage Multiple

L'héritage multiple indique souvent un problème de conception, mais Perl vous donne toujours assez de corde pour vous pendre si vous le demandez.

Pour déclarer plusieurs parents, il suffit de passer plusieurs noms de classe à "use parent" :

package MultiChild;
use parent 'Parent1', 'Parent2';

Ordre de Résolution des Méthodes

L'ordre de résolution des méthodes n'a d'importance qu'en cas d'héritage multiple. Dans le cas d'un héritage simple, Perl remonte simplement la chaîne d'héritage pour trouver une méthode :

Grandparent
  |
Parent
  |
Child

Si nous appelons une méthode sur un objet "Child" et que cette méthode n'est pas définie dans la classe "Child", Perl la recherchera dans la classe "Parent" puis, si nécessaire, dans la classe "Grandparent".

Si Perl ne parvient pas à trouver la méthode dans l'une de ces classes, il mourra avec un message d'erreur.

Lorsqu'une classe a plusieurs parents, l'ordre de recherche des méthodes devient plus complexe.

Par défaut, Perl effectue une recherche en profondeur de gauche à droite pour une méthode. Cela signifie qu'il commence par le premier parent dans le tableau @ISA, puis recherche tous ses parents, grands-parents, etc. S'il ne parvient pas à trouver la méthode, il passe au parent suivant dans le tableau @ISA de la classe d'origine et recherche à partir de là.

          SharedGreatGrandParent
          /                    \
PaternalGrandparent       MaternalGrandparent
          \                    /
           Father        Mother
                 \      /
                  Child

Ainsi, étant donné le schéma ci-dessus, Perl recherchera dans "Child", "Father", "PaternalGrandparent", "SharedGreatGrandParent", "Mother", et enfin "MaternalGrandparent". Cela peut poser un problème car nous regardons maintenant dans "SharedGreatGrandParent" *avant* d'avoir vérifié toutes ses classes dérivées (c'est-à-dire avant d'essayer "Mother" et "MaternalGrandparent").

Il est possible de demander un ordre de résolution des méthodes différent avec le pragma mro.

package Child;
use mro 'c3';
use parent 'Father', 'Mother';

Ce pragma vous permet de passer à l'ordre de résolution "C3". En termes simples, l'ordre "C3" garantit que les classes parentes partagées ne sont jamais recherchées avant les classes enfants, Perl recherchera donc maintenant : "Child", "Father", "PaternalGrandparent", "Mother", "MaternalGrandparent", et enfin "SharedGreatGrandParent". Notez cependant qu'il ne s'agit pas d'une recherche "en largeur" : tous les ancêtres de "Father" (sauf l'ancêtre commun) sont recherchés avant que l'un des ancêtres de "Mother" ne soit pris en compte.

L'ordre C3 vous permet également d'appeler des méthodes dans des classes sœurs avec la pseudo-classe "next". Voir la documentation de mro pour plus de détails sur cette fonctionnalité.

Mise en Cache de Résolution des Méthodes

Lorsque Perl recherche une méthode, il met en cache la recherche afin que les appels futurs à la méthode n'aient pas besoin de la rechercher à nouveau. La modification de la classe parente d'une classe ou l'ajout de sous-routines à une classe invalidera le cache pour cette classe.

Le pragma mro fournit des fonctions pour manipuler directement le cache des méthodes.

Écrire des constructeurs

Comme nous l'avons mentionné précédemment, Perl ne fournit aucune syntaxe spéciale de constructeur. Cela signifie qu'une classe doit implémenter son propre constructeur. Un constructeur est simplement une méthode de classe qui renvoie une référence à un nouvel objet.

Le constructeur peut également accepter des paramètres supplémentaires qui définissent l'objet. Écrivons un véritable constructeur pour la classe "File" que nous avons utilisée précédemment :

package File;
sub new {
    my $class = shift;
    my ( $path, $data ) = @_;
    my $self = bless {
        path => $path,
        data => $data,
    }, $class;
    return $self;
}

Comme vous pouvez le voir, nous avons stocké le chemin et les données du fichier dans l'objet lui-même. Rappelez-vous, sous le capot, cet objet n'est qu'une table de hachage. Plus tard, nous écrirons des accesseurs pour manipuler ces données.

Pour notre classe "File::MP3", nous pouvons vérifier que le chemin que nous recevons se termine par ".mp3" :

package File::MP3;
sub new {
    my $class = shift;
    my ( $path, $data ) = @_;
    die "You cannot create a File::MP3 without an mp3 extension\n"
        unless $path =~ /\.mp3\z/;
    return $class->SUPER::new(@_);
}

Ce constructeur laisse sa classe parente effectuer la construction réelle de l'objet.

Attributs

Un attribut est une donnée appartenant à un objet particulier. Contrairement à la plupart des langages orientés objet, Perl ne fournit aucune syntaxe ou support spécial pour déclarer et manipuler des attributs.

Les attributs dans les objets

Les attributs sont souvent stockés dans l'objet lui-même. Par exemple, si l'objet est une table de hachage anonyme, nous pouvons stocker les valeurs des attributs dans la table de hachage en utilisant le nom de l'attribut comme clé.

Bien qu'il soit possible de faire directement référence à ces clés de table de hachage en dehors de la classe, il est considéré comme une bonne pratique d'encapsuler tout accès à l'attribut avec des méthodes d'accesseur.

Cela présente plusieurs avantages. Les accesseurs facilitent la modification ultérieure de l'implémentation d'un objet tout en préservant l'API d'origine.

Un accesseur vous permet d'ajouter du code supplémentaire autour de l'accès à l'attribut. Par exemple, vous pourriez appliquer une valeur par défaut à un attribut qui n'a pas été défini dans le constructeur, ou vous pourriez valider qu'une nouvelle valeur pour l'attribut est acceptable.

Enfin, l'utilisation d'accesseurs rend l'héritage beaucoup plus simple. Les sous-classes peuvent utiliser les accesseurs plutôt que d'avoir à savoir comment une classe parente est implémentée en interne.

Écrire des accesseurs

Comme pour les constructeurs, Perl ne fournit pas de syntaxe spéciale de déclaration d'accesseur, les classes doivent donc fournir des méthodes d'accesseur explicitement écrites. Il existe deux types courants d'accesseurs, en lecture seule et en lecture-écriture.

Un simple accesseur en lecture seule récupère la valeur d'un seul attribut :

sub path {
    my $self = shift;
    return $self->{path};
}

Un accesseur en lecture-écriture permettra à l'appelant de définir la valeur ainsi que de la récupérer :

sub path {
    my $self = shift;
    if (@_) {
        $self->{path} = shift;
    }
    return $self->{path};
}

Une parenthèse sur le code plus intelligent et plus sûr

Notre constructeur et nos accesseurs ne sont pas très intelligents. Ils ne vérifient pas que $path est défini, ni qu'il s'agit d'un chemin de système de fichiers valide.

Effectuer ces vérifications manuellement peut rapidement devenir fastidieux. Écrire une multitude d'accesseurs à la main est également incroyablement fastidieux. Il existe de nombreux modules sur CPAN qui peuvent vous aider à écrire du code plus sûr et plus concis, y compris les modules que nous recommandons dans perlootut.

Variations d'appels de méthodes

Perl prend en charge plusieurs autres façons d'appeler des méthodes, en plus de l'utilisation "$object->method()" que nous avons vue jusqu'à présent.

Noms de méthodes avec un nom entièrement qualifié

Perl vous permet d'appeler des méthodes en utilisant leur nom entièrement qualifié (le nom du paquet et de la méthode) :

my $mp3 = File::MP3->new( 'Regin.mp3', $data );
$mp3->File::save();

Lorsque vous appelez un nom de méthode entièrement qualifié comme "File::save", la recherche de résolution de méthode pour la méthode "save" commence dans la classe "File", ignorant toute méthode "save" que la classe "File::MP3" aurait pu définir. Elle recherche toujours les parents de la classe "File" si nécessaire.

Bien que cette fonctionnalité soit le plus souvent utilisée pour appeler explicitement des méthodes héritées d'une classe parente, il n'y a aucune restriction technique qui l'impose :

my $obj = Tree->new();
$obj->Dog::bark();

Ceci appelle la méthode "bark" de la classe "Dog" sur un objet de la classe "Tree", même si les deux classes ne sont pas liées du tout. Utilisez ceci avec une grande prudence.

La pseudo-classe "SUPER" décrite précédemment n'est *pas* la même chose qu'appeler une méthode avec un nom entièrement qualifié. Voir la section précédente sur l'héritage pour plus de détails.

Noms de méthodes sous forme de chaînes

Perl vous permet d'utiliser une variable scalaire contenant une chaîne comme nom de méthode :

my $file = File->new( $path, $data );
my $method = 'save';
$file->$method();

Cela fonctionne exactement comme l'appel de "$file->save()". Cela peut être très utile pour écrire du code dynamique. Par exemple, cela vous permet de passer un nom de méthode à appeler comme paramètre à une autre méthode.

Noms de classes sous forme de chaînes

Perl vous permet également d'utiliser un scalaire contenant une chaîne comme nom de classe :

my $class = 'File';
my $file = $class->new( $path, $data );

Encore une fois, cela permet un code très dynamique.

Références de sous-routines comme méthodes

Vous pouvez également utiliser une référence de sous-routine comme méthode :

my $sub = sub {
    my $self = shift;
    $self->save();
};
$file->$sub();

Ceci est exactement équivalent à écrire $sub->($file). Vous pourriez voir cet idiome dans la nature combiné avec un appel à "can" :

if ( my $meth = $object->can('foo') ) {
    $object->$meth();
}

Déréférencement d'appel de méthode

Perl vous permet également d'utiliser une référence scalaire déréférencée dans un appel de méthode. C'est un peu technique, alors regardons du code :

$file->${ \'save' };
$file->${ returns_scalar_ref() };
$file->${ \( returns_scalar() ) };
$file->${ returns_ref_to_sub_ref() };

Cela fonctionne si le déréférencement produit une chaîne *ou* une référence de sous-routine.

Appels de méthodes sur des descripteurs de fichiers

En interne, les descripteurs de fichiers Perl sont des instances de la classe "IO::Handle" ou "IO::File". Une fois que vous avez un descripteur de fichier ouvert, vous pouvez appeler des méthodes dessus. De plus, vous pouvez appeler des méthodes sur les descripteurs de fichiers "STDIN", "STDOUT" et "STDERR".

open my $fh, '>', 'path/to/file';
$fh->autoflush();
$fh->print('content');
STDOUT->autoflush();

Invocation des méthodes de classe

Étant donné que Perl vous permet d'utiliser des mots vides (barewords) pour les noms de paquets et de sous-programmes, il interprète parfois incorrectement la signification d'un mot vide. Par exemple, la construction "Class->new()" peut être interprétée comme "'Class'->new()" ou "Class()->new()". En français, la deuxième interprétation se lit comme « appeler un sous-programme nommé Class(), puis appeler new() comme méthode sur la valeur de retour de Class() ». S'il existe un sous-programme nommé Class() dans l'espace de noms actuel, Perl interprétera toujours "Class->new()" comme la deuxième alternative : un appel à new() sur l'objet retourné par un appel à Class().

Vous pouvez forcer Perl à utiliser la première interprétation (c'est-à-dire comme un appel de méthode sur la classe nommée « Class ») de deux manières. Premièrement, vous pouvez ajouter un "::" au nom de la classe :

Class::->new()

Perl interprétera toujours cela comme un appel de méthode.

Alternativement, vous pouvez mettre le nom de la classe entre guillemets :

'Class'->new()

Bien sûr, si le nom de la classe est dans un scalaire, Perl fera la bonne chose également :

my $class = 'Class';
$class->new();

Syntaxe d'objet indirect

En dehors du cas du descripteur de fichier, l'utilisation de cette syntaxe est déconseillée car elle peut confondre l'interpréteur Perl. Voir ci-dessous pour plus de détails.

Perl prend en charge une autre syntaxe d'invocation de méthode appelée notation « objet indirect ». Cette syntaxe est appelée « indirecte » car la méthode précède l'objet sur lequel elle est appelée.

Cette syntaxe peut être utilisée avec n'importe quelle méthode de classe ou d'objet :

my $file = new File $path, $data;
save $file;

Nous vous recommandons d'éviter cette syntaxe, pour plusieurs raisons.

Premièrement, elle peut être déroutante à lire. Dans l'exemple ci-dessus, il n'est pas clair si "save" est une méthode fournie par la classe "File" ou simplement un sous-programme qui attend un objet fichier comme premier argument.

Lorsqu'elle est utilisée avec des méthodes de classe, le problème est encore pire. Parce que Perl autorise les noms de sous-programmes à être écrits comme des mots vides, Perl doit deviner si le mot vide après la méthode est un nom de classe ou un nom de sous-programme. En d'autres termes, Perl peut résoudre la syntaxe comme "File->new( $path, $data )" *ou* "new( File( $path, $data ) )".

Pour analyser ce code, Perl utilise une heuristique basée sur les noms de paquets qu'il a vus, les sous-programmes existant dans le paquet actuel, les mots vides qu'il a précédemment vus, et d'autres entrées. Il va sans dire que les heuristiques peuvent produire des résultats très surprenants !

La documentation plus ancienne (et certains modules CPAN) encourageait cette syntaxe, en particulier pour les constructeurs, vous pourriez donc encore la rencontrer. Cependant, nous vous encourageons à éviter de l'utiliser dans du nouveau code.

Vous pouvez forcer Perl à interpréter le mot vide comme un nom de classe en ajoutant "::", comme nous l'avons vu précédemment :

my $file = new File:: $path, $data;

La syntaxe d'objet indirect n'est disponible que lorsque la fonctionnalité nommée "indirect" est activée. Elle est activée par défaut, mais peut être désactivée sur demande. Cette fonctionnalité est présente dans les anciens lots de fonctionnalités, mais a été supprimée du lot ":5.36" ; ainsi, une déclaration "use VERSION" de "v5.36" ou supérieure désactivera également la fonctionnalité.

use v5.36;
# la syntaxe d'objet indirect n'est plus disponible

"bless", "blessed", et "ref"

Comme nous l'avons vu précédemment, un objet est simplement une structure de données qui a été bénie dans une classe via la fonction "bless". La fonction "bless" peut prendre un ou deux arguments :

my $object = bless {}, $class;
my $object = bless {};

Dans la première forme, la table de hachage anonyme est bénie dans la classe dans $class. Dans la seconde forme, la table de hachage anonyme est bénie dans le paquet actuel.

La seconde forme est fortement déconseillée, car elle empêche une sous-classe de réutiliser le constructeur parent, mais vous pourriez encore la rencontrer dans du code existant.

Perl Object-Oriented Programming

This document provides an introduction to object-oriented programming in Perl.

Checking if a Scalar is an Object

To determine if a particular scalar refers to an object, you can use the "blessed" function exported by Scalar::Util, which is shipped with the Perl core.

use Scalar::Util 'blessed';
if ( defined blessed($thing) ) { ... }

If $thing refers to an object, then this function returns the name of the package the object has been blessed into. If $thing doesn't contain a reference to a blessed object, the "blessed" function returns "undef".

Note that blessed($thing) will also return false if $thing has been blessed into a class named "0". This is possible, but quite pathological. Don't create a class named "0" unless you know what you're doing.

Similarly, Perl's built-in "ref" function treats a reference to a blessed object specially. If you call ref($thing) and $thing holds a reference to an object, it will return the name of the class that the object has been blessed into.

If you simply want to check that a variable contains an object reference, we recommend that you use "defined blessed($object)", since "ref" returns true values for all references, not just objects.

The UNIVERSAL Class

All classes automatically inherit from the UNIVERSAL class, which is built-in to the Perl core. This class provides a number of methods, all of which can be called on either a class or an object. You can also choose to override some of these methods in your class. If you do so, we recommend that you follow the built-in semantics described below.

isa($class)
The "isa" method returns true if the object is a member of the class in $class, or a member of a subclass of $class.

If you override this method, it should never throw an exception.

DOES($role)
The "DOES" method returns true if its object claims to perform the role $role. By default, this is equivalent to "isa". This method is provided for use by object system extensions that implement roles, like "Moose" and "Role::Tiny".

You can also override "DOES" directly in your own classes. If you override this method, it should never throw an exception.

can($method)
The "can" method checks to see if the class or object it was called on has a method named $method. This checks for the method in the class and all of its parents. If the method exists, then a reference to the subroutine is returned. If it does not then "undef" is returned.

If your class responds to method calls via "AUTOLOAD", you may want to overload "can" to return a subroutine reference for methods which your "AUTOLOAD" method handles.

If you override this method, it should never throw an exception.

VERSION($need)
The "VERSION" method returns the version number of the class (package).

If the $need argument is given then it will check that the current version (as defined by the $VERSION variable in the package) is greater than or equal to $need; it will die if this is not the case. This method is called automatically by the "VERSION" form of "use".

use Package 1.2 qw(some imported subs);
# implies:
Package->VERSION(1.2);

We recommend that you use this method to access another package's version, rather than looking directly at $Package::VERSION. The package you are looking at could have overridden the "VERSION" method.

We also recommend using this method to check whether a module has a sufficient version. The internal implementation uses the version module to make sure that different types of version numbers are compared correctly.

AUTOLOAD

If you call a method that doesn't exist in a class, Perl will throw an error. However, if that class or any of its parent classes defines an "AUTOLOAD" method, that "AUTOLOAD" method is called instead.

"AUTOLOAD" is called as a regular method, and the caller will not know the difference. Whatever value your "AUTOLOAD" method returns is returned to the caller.

The fully qualified method name that was called is available in the $AUTOLOAD package global for your class. Since this is a global, if you want to refer to it without a package name prefix under strict 'vars', you need to declare it.

# XXX - this is a terrible way to implement accessors, but it makes
# for a simple example.
our $AUTOLOAD;
sub AUTOLOAD {
    my $self = shift;
    # Remove qualifier from original method name...
    my $called =  $AUTOLOAD =~ s/.*:://r;
    # Is there an attribute of that name?
    die "No such attribute: $called"
        unless exists $self->{$called};
    # If so, return it...
    return $self->{$called};
}
sub DESTROY { } # see below

Without the "our $AUTOLOAD" declaration, this code will not compile under the strict pragma.

As the comment says, this is not a good way to implement accessors. It's slow and too clever by far. However, you may see this as a way to provide accessors in older Perl code. See perlootut for recommendations on OO coding in Perl.

If your class does have an "AUTOLOAD" method, we strongly recommend that you override "can" in your class as well. Your overridden "can" method should return a subroutine reference for any method that your "AUTOLOAD" responds to.

Destructors

When the last reference to an object goes away, the object is destroyed. If you only have one reference to an object stored in a lexical scalar, the object is destroyed when that scalar goes out of scope. If you store the object in a package global, that object may not go out of scope until the program exits.

If you want to do something when the object is destroyed, you can define a "DESTROY" method in your class. This method will always be called by Perl at the appropriate time, unless the method is empty.

This is called just like any other method, with the object as the first argument. It does not receive any additional arguments. However, the $_[0] variable will be read-only in the destructor, so you cannot assign a value to it.

If your "DESTROY" method throws an exception, this will not cause any control transfer beyond exiting the method. The exception will be reported to "STDERR" as a warning, marked "(in cleanup)", and Perl will continue with whatever it was doing before.

Because "DESTROY" methods can be called at any time, you should localize any global status variables that might be set by anything you do in your "DESTROY" method. If you are in doubt about a particular status variable, it doesn't hurt to localize it. There are five global status variables, and the safest way is to localize all five of them:

sub DESTROY {
    local($., $@, $!, $^E, $?);
    my $self = shift;
    ...;
}

If you define an "AUTOLOAD" in your class, then Perl will call your "AUTOLOAD" to handle the "DESTROY" method. You can prevent this by defining an empty "DESTROY", like we did in the autoloading example. You can also check the value of $AUTOLOAD and return without doing anything when called to handle "DESTROY".

Global Destruction

The order in which objects are destroyed during the global destruction before the program exits is unpredictable. This means that any objects contained by your object may already have been destroyed. You should check that a contained object is defined before calling a method on it:

sub DESTROY {
    my $self = shift;
    $self->{handle}->close() if $self->{handle};
}

You can use the "${^GLOBAL_PHASE}" variable to detect if you are currently in the global destruction phase:

sub DESTROY {
    my $self = shift;
    return if ${^GLOBAL_PHASE} eq 'DESTRUCT';
    $self->{handle}->close();
}

Note that this variable was added in Perl 5.14.0. If you want to detect the global destruction phase on older versions of Perl, you can use the "Devel::GlobalDestruction" module on CPAN.

If your "DESTROY" method issues a warning during global destruction, the Perl interpreter will append the string " during global destruction" to the warning.

During global destruction, Perl will always garbage collect objects before unblessed references. See "PERL_DESTRUCT_LEVEL" in perlhacktips for more information about global destruction.

Non-Hash Objects

All the examples so far have shown objects based on a blessed hash. However, it's

possible de bénir tout type de structure de données ou de référent, y compris les scalaires, les globales et les sous-routines. Vous pouvez voir ce genre de chose en regardant du code dans la nature.

Voici un exemple de module comme scalaire béni :

package Time;
use v5.36;
sub new {
    my $class = shift;
    my $time = time;
    return bless \$time, $class;
}
sub epoch {
    my $self = shift;
    return $$self;
}
my $time = Time->new();
print $time->epoch();

Objets Inside-Out

Par le passé, la communauté Perl a expérimenté une technique appelée « objets inside-out ». Un objet inside-out stocke ses données à l'extérieur de la référence de l'objet, indexées sur une propriété unique de l'objet, telle que son adresse mémoire, plutôt que dans l'objet lui-même. Cela a l'avantage de forcer l'encapsulation des attributs de l'objet, car leurs données ne sont pas stockées dans l'objet lui-même.

Cette technique a été populaire pendant un certain temps (et a été recommandée dans Perl Best Practices de Damian Conway), mais n'a jamais atteint une adoption universelle. Le module Object::InsideOut sur CPAN fournit une implémentation complète de cette technique, et vous pourriez la voir, ou d'autres modules inside-out, dans la nature.

Voici un exemple simple de la technique, utilisant le module core Hash::Util::FieldHash. Ce module a été ajouté au cœur pour supporter les implémentations d'objets inside-out.

package Time;
use v5.36;
use Hash::Util::FieldHash 'fieldhash';
fieldhash my %time_for;
sub new {
    my $class = shift;
    my $self = bless \( my $object ), $class;
    $time_for{$self} = time;
    return $self;
}
sub epoch {
    my $self = shift;
    return $time_for{$self};
}
my $time = Time->new;
print $time->epoch;

Pseudo-hashes

La fonctionnalité des pseudo-hashes était une fonctionnalité expérimentale introduite dans les versions antérieures de Perl et supprimée en 5.10.0. Un pseudo-hash est une référence de tableau qui peut être accédée en utilisant des clés nommées comme un hash. Vous pourriez rencontrer du code dans la nature qui l'utilise. Voir le pragma fields pour plus d'informations.
