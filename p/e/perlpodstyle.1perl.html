PERLPODSTYLE(1perl) Guide de référence des programmeurs Perl PERLPODSTYLE(1perl)

NOM

perlpodstyle - Guide de style de la documentation POD de Perl

DESCRIPTION

Ce sont des directives générales sur la manière de rédiger la documentation POD pour les scripts et modules Perl, basées sur les directives générales pour la rédaction de bonnes pages de manuel UNIX. Toutes ces directives sont, bien entendu, facultatives, mais leur respect rendra votre documentation plus cohérente avec les autres documentations du système.

Le nom du programme documenté est conventionnellement écrit en gras (en utilisant B<>) partout où il apparaît, tout comme les options du programme. Les arguments doivent être écrits en italique (I<>). Les noms de fonctions sont traditionnellement écrits en italique ; si vous écrivez une fonction comme fonction(), Pod::Man s'en chargera pour vous. Le code littéral ou les commandes doivent être en C<>. Les références à d'autres pages de manuel doivent être sous la forme manpage(section) ou "L<manpage(section)>", et Pod::Man les formatera automatiquement de manière appropriée. La deuxième forme, avec L<>, est utilisée pour demander à un formateur POD de créer un lien vers la page de manuel si possible. Par exception, on omet normalement la section lors de la référence à la documentation d'un module car il n'est pas clair dans quelle section la documentation du module se trouvera ; utilisez "L<Module::Nom>" pour les références de modules à la place.

Les références à d'autres programmes ou fonctions sont normalement sous forme de références de pages de manuel afin que les outils de référence croisée puissent fournir des liens à l'utilisateur, etc. Il est possible d'en abuser, alors faites attention à ne pas surcharger votre documentation avec trop de balisage. Les références à d'autres programmes qui ne sont pas données comme références de pages de manuel doivent être entourées de B<>>.

Les en-têtes majeurs doivent être définis à l'aide d'une directive "=head1", et sont historiquement écrits dans le format assez frappant TOUT EN MAJUSCULES ; ce n'est pas obligatoire, mais c'est fortement recommandé afin que les sections aient une dénomination cohérente à travers différents paquets logiciels. Les en-têtes mineurs peuvent être inclus en utilisant "=head2", et sont typiquement en casse mixte.

Les sections standard d'une page de manuel sont :

NOM
Section obligatoire ; doit être une liste de programmes ou de fonctions séparés par des virgules, documentés par cette page POD, telle que : 
foo, bar - programmes pour faire quelque chose

Les indexeurs de pages de manuel sont souvent extrêmement pointilleux sur le format de cette section, donc n'y mettez rien d'autre que cette ligne. Chaque programme ou fonction documenté par cette page POD doit être listé, séparé par une virgule et un espace. Pour un module Perl, donnez simplement le nom du module. Un seul tiret, et un seul tiret, doit séparer la liste des programmes ou fonctions de la description. N'utilisez aucune balise telle que C<> ou B<> nulle part sur cette ligne. Les fonctions ne doivent pas être qualifiées avec "()" ou similaire. La description doit idéalement tenir sur une seule ligne, même si un programme de manuel remplace le tiret par quelques tabulations.

SYNOPSIS
Un bref résumé d'utilisation pour les programmes et fonctions. Cette section est obligatoire pour les pages de section 3. Pour la documentation de modules Perl, il est généralement pratique d'avoir le contenu de cette section comme un bloc verbatim montrant quelques exemples (brefs) de la manière typique d'utiliser le module.
DESCRIPTION
Description et discussion étendues du programme ou des fonctions, ou le corps de la documentation pour les pages de manuel qui documentent autre chose. Si particulièrement long, il est bon de le diviser en sous-sections avec des directives "=head2" comme : 
=head2 Utilisation Normale
=head2 Fonctionnalités Avancées
=head2 Écriture de Fichiers de Configuration

ou tout ce qui est approprié pour votre documentation.

Pour un module, c'est généralement là que va la documentation des interfaces fournies par le module, généralement sous forme de liste avec un "=item" pour chaque interface. Selon le nombre d'interfaces, vous pourriez vouloir placer cette documentation dans des sections séparées MÉTHODES, FONCTIONS, MÉTHODES DE CLASSE ou MÉTHODES D'INSTANCE à la place et réserver la section DESCRIPTION pour un aperçu.

OPTIONS
Description détaillée de chacune des options en ligne de commande prises par le programme. Ceci doit être séparé de la description pour l'utilisation par des analyseurs comme Pod::Usage. Ceci est normalement présenté sous forme de liste, chaque option étant un "=item" séparé. La chaîne d'option spécifique doit être entourée de B<>>. Les valeurs que l'option prend doivent être entourées de I<>>. Par exemple, la section pour l'option --section=manext serait introduite par : 
=item B<--section>=I<manext>

Les options synonymes (comme les formes courte et longue) sont séparées par une virgule et un espace sur la même ligne "=item", ou optionnellement listées comme leur propre élément avec une référence au nom canonique. Par exemple, puisque --section peut aussi s'écrire -s, ce qui précède serait :

=item B<-s> I<manext>, B<--section>=I<manext>

Il est recommandé d'écrire d'abord l'option courte car elle est plus facile à lire. L'option longue est suffisamment longue pour attirer l'œil de toute façon et l'option courte peut autrement se perdre dans le bruit visuel.

VALEUR DE RETOUR
Ce que le programme ou la fonction retourne, en cas de succès. Cette section peut être omise pour les programmes dont les codes de sortie précis ne sont pas importants, à condition qu'ils retournent 0 en cas de succès et non nul en cas d'échec, comme il est standard. Elle doit toujours être présente pour les fonctions. Pour les modules, il peut être utile de résumer ici les valeurs de retour de l'interface du module, ou il peut être plus utile de discuter des valeurs de retour séparément dans la documentation de chaque fonction ou méthode que le module fournit.
ERREURS
Exceptions, codes de retour d'erreur, statuts de sortie et paramètres errno. Typiquement utilisé pour la documentation de fonctions ou de modules ; la documentation de programmes utilise DIAGNOSTICS à la place. La règle générale est que les erreurs imprimées sur "STDOUT" ou "STDERR" et destinées à l'utilisateur final sont documentées dans DIAGNOSTICS tandis que les erreurs passées en interne au programme appelant et destinées à d'autres programmeurs sont documentées dans ERREURS. Lors de la documentation d'une fonction qui définit errno, une liste complète des valeurs errno possibles devrait être donnée ici.
DIAGNOSTICS
Tous les messages possibles que le programme peut afficher et leur signification. Vous pourriez vouloir suivre le même style de documentation que la documentation Perl ; voir perldiag(1) pour plus de détails (et regardez aussi la source POD).

Si applicable, veuillez inclure des détails sur ce que l'utilisateur doit faire pour corriger l'erreur ; documenter une erreur comme indiquant "le tampon d'entrée est trop petit" sans indiquer à l'utilisateur comment augmenter la taille du tampon d'entrée (ou du moins lui dire que ce n'est pas possible) n'est pas très utile.

EXEMPLES
Donnez quelques exemples d'utilisation du programme ou de la fonction. Ne lésinez pas ; les utilisateurs trouvent souvent cette partie la plus utile de la documentation. Les exemples sont généralement donnés comme paragraphes verbatim.

Ne présentez pas simplement un exemple sans expliquer ce qu'il fait. Ajouter un court paragraphe expliquant ce que l'exemple fera peut augmenter considérablement la valeur de l'exemple.

ENVIRONNEMENT
Variables d'environnement auxquelles le programme prête attention, normalement présentées comme une liste utilisant "=over", "=item" et "=back". Par exemple : 
=over 6
=item HOME
Utilisé pour déterminer le répertoire personnel de l'utilisateur. F<.foorc> dans ce
répertoire est lu pour les détails de configuration, s'il existe.
=back

Comme les variables d'environnement sont normalement tout en majuscules, aucun formatage spécial supplémentaire n'est généralement nécessaire ; elles sont assez criardes en soi.

perlpodstyle - Style conventions for POD documentation

NAME

perlpodstyle - Style conventions for POD documentation

DESCRIPTION

This document describes the conventions used in the Perl POD (Plain Old Documentation) documentation system. Adhering to these conventions makes the documentation more readable and understandable.

NAME
The name of the command or module being documented. It should be followed by a short description.
SYNOPSIS
A brief overview of how to use the command or module. For commands, this usually shows the command line usage. For modules, it shows a typical usage example.
DESCRIPTION
A more detailed explanation of what the command or module does.
OPTIONS
A description of all command-line options available. For modules, this section might describe configuration options or parameters.
RETURN VALUE
What the command or function returns. For commands, this might describe exit codes. For functions, it describes the value returned upon success or failure.
DIAGNOSTICS
Information about potential error messages or error conditions and how to handle them.
EXPORTS
For modules, this section describes what symbols (variables, subroutines) are exported by default or optionally.
FILES
Lists important files that the command or module interacts with. File names should be enclosed in F<>. It's particularly important to document files that will be potentially modified.
CAVEATS
Things to take special care with, sometimes called WARNINGS.
BUGS
Things that are broken or just don't work quite right.
RESTRICTIONS
Bugs you don't plan to fix. :-)
NOTES
Miscellaneous commentary.
AUTHOR
Who wrote it (use AUTHORS for multiple people). It's a good idea to include your current e-mail address (or some e-mail address to which bug reports should be sent) or some other contact information so that users have a way of contacting you. Remember that program documentation tends to roam the wild for far longer than you expect and pick a contact method that's likely to last.
HISTORY
Programs derived from other sources sometimes have this. Some people keep a modification log here, but that usually gets long and is normally better maintained in a separate file.
COPYRIGHT AND LICENSE
For copyright 
Copyright YEAR(s) YOUR NAME(s)
(No, (C) is not needed. No, "all rights reserved" is not needed.) For licensing the easiest way is to use the same licensing as Perl itself: 
This library is free software; you may redistribute it and/or
modify it under the same terms as Perl itself.
This makes it easy for people to use your module with Perl. Note that this licensing example is neither an endorsement nor a requirement, you are of course free to choose any licensing.
SEE ALSO
Other man pages to check out, like man(1), man(7), makewhatis(8), or catman(8). Normally a simple list of man pages separated by commas, or a paragraph giving the name of a reference work. Man page references, if they use the standard name(section) form, don't have to be enclosed in L<> (although it's recommended), but other things in this section probably should be when appropriate. If the package has a mailing list, include a URL or subscription instructions here. If the package has a web site, include a URL here.

Documentation of object-oriented libraries or modules may want to use CONSTRUCTORS and METHODS sections, or CLASS METHODS and INSTANCE METHODS sections, for detailed documentation of the parts of the library and save the DESCRIPTION section for an overview. Large modules with a function interface may want to use FUNCTIONS for similar reasons. Some people use OVERVIEW to summarize the description if it's quite long.

Section ordering varies, although NAME must always be the first section (you'll break some man page systems otherwise), and NAME, SYNOPSIS, DESCRIPTION, and OPTIONS generally always occur first and in that order if present. In general, SEE ALSO, AUTHOR, and similar material should be left for last. Some systems also move WARNINGS and NOTES to last. The order given above should be reasonable for most purposes.

Some systems use CONFORMING TO to note conformance to relevant standards and MT-LEVEL to note safeness for use in threaded programs or signal handlers. These headings are primarily useful when documenting parts of a C library.

Finally, as a general note, try not to use an excessive amount of markup. As documented here and in Pod::Man, you can safely leave Perl variables, function names, man page references, and the like unadorned by markup and the POD translators will figure it out for you. This makes it much easier to later edit the documentation. Note that many existing translators will do the wrong thing with e-mail addresses when wrapped in L<>, so don't do that.
