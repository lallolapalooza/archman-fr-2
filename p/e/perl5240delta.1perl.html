PERL5240DELTA(1perl) Guide de référence du programmeur Perl PERL5240DELTA(1perl)

NOM

perl5240delta - nouveautés pour la version perl v5.24.0

DESCRIPTION

Ce document décrit les différences entre la version 5.22.0 et la version 5.24.0.

Améliorations du cœur

Le déréférencement postfixe n'est plus expérimental

L'utilisation des fonctionnalités "postderef" et "postderef_qq" n'émet plus d'avertissement. Le code existant qui désactivait la catégorie d'avertissement "experimental::postderef" qu'ils utilisaient auparavant continuera de fonctionner. La fonctionnalité "postderef" n'a aucun effet ; tout code Perl peut utiliser le déréférencement postfixe, quelles que soient les déclarations de fonctionnalités en cours. Le paquet de fonctionnalités 5.24 inclut désormais la fonctionnalité "postderef_qq".

Unicode 8.0 est maintenant pris en charge

Pour plus de détails sur cette version, consultez http://www.unicode.org/versions/Unicode8.0.0/.

Perl va maintenant planter lorsque la fermeture d'un fichier de sortie en place échoue

Jusqu'à présent, l'échec de la fermeture du fichier de sortie pour une édition en place n'était pas détecté, ce qui signifiait que le fichier source pouvait être écrasé sans que l'édition ne soit terminée avec succès. Désormais, lorsque le fichier de sortie ne peut pas être fermé correctement, une exception est levée.

Nouvelle "\lb" limite dans les expressions régulières

"lb" signifie Line Break (Saut de Ligne). Il s'agit d'une propriété Unicode qui détermine où une ligne de texte est appropriée pour une coupure (généralement afin qu'elle puisse être affichée sans dépasser l'espace horizontal disponible). Cette capacité était fournie depuis longtemps par le module Unicode::LineBreak, mais maintenant une version légère et non personnalisable, adaptée à de nombreux usages, fait partie du cœur de Perl.

qr/(?[_])/ maintenant fonctionne dans les locales UTF-8

Les classes de caractères étendues entre crochets se compileront maintenant avec succès lorsque "use locale" est actif. Le modèle compilé utilisera les règles Unicode standard. Si la locale d'exécution n'est pas une locale UTF-8, un avertissement est émis et les règles Unicode standard sont utilisées de toute façon. Aucune salissure n'est effectuée car le résultat ne dépend pas réellement de la locale.

Le décalage d'entiers ("<<" et ">>") est maintenant défini de manière plus explicite

Les décalages négatifs sont des décalages inverses : le décalage vers la gauche devient un décalage vers la droite, et le décalage vers la droite devient un décalage vers la gauche.

Le décalage par le nombre de bits dans un entier natif (ou plus) est zéro, sauf lorsque le "sur-décalage" décale vers la droite une valeur négative sous "use integer", auquel cas le résultat est -1 (décalage arithmétique).

Jusqu'à présent, les décalages négatifs et les sur-décalages étaient non définis car ils dépendaient du comportement de l'implémentation C. Par exemple, pour le sur-décalage, un comportement C courant est le "décalage modulo" :

1 >> 64 == 1 >> (64 % 64) == 1 >> 0 == 1  # Comportement C courant.
# Et de même pour <<, alors que Perl produit maintenant 0 pour les deux.

Maintenant, ces comportements sont bien définis sous Perl, indépendamment de ce que fait l'implémentation C sous-jacente. Notez cependant que vous êtes toujours limité par la largeur native de l'entier : vous devez savoir jusqu'où vous pouvez décaler vers la gauche. Vous pouvez utiliser par exemple :

use Config;
my $wordbits = $Config{uvsize} * 8;  # Ou $Config{uvsize} << 3.

Si vous avez besoin de plus de bits pour le décalage vers la gauche, vous pouvez utiliser par exemple le pragma "bigint", ou le module "Bit::Vector" de CPAN.

printf et sprintf autorisent maintenant les arguments de précision réordonnés

C'est-à-dire que "sprintf '|%.*2$d|', 2, 3" renvoie maintenant "|002|". Cela étend le mécanisme de réordonnancement existant (qui permet de réordonner les arguments utilisés comme champs de format, largeurs et séparateurs de vecteurs).

Plus de champs fournis à la fonction de rappel "sigaction" avec "SA_SIGINFO"

Lorsqu'on passe le drapeau "SA_SIGINFO" à sigaction, les champs "errno", "status", "uid", "pid", "addr" et "band" sont désormais inclus dans le hash passé au gestionnaire, si la plateforme le prend en charge.

Redirection de hashbang vers Perl 6

Auparavant, perl redirigeait vers un autre interpréteur s'il trouvait un chemin de hashbang à moins que le chemin ne contienne "perl" (voir perlrun). Pour améliorer la compatibilité avec Perl 6, ce comportement a été étendu pour rediriger également si "perl" est suivi de "6".

Sécurité

Définir le bon umask avant d'appeler mkstemp(3)

En 5.22, perl commençait par définir umask à 0600 avant d'appeler mkstemp(3) et le restaurait ensuite. Cela indique à tort à open(2) de supprimer les bits de lecture et d'écriture du propriétaire du mode donné avant de l'appliquer, plutôt que l'intention de ne laisser que ces bits en place.

Les systèmes qui utilisent le mode 0666 dans mkstemp(3) (comme les anciennes versions de glibc) créent un fichier avec les permissions 0066, laissant des permissions de lecture et d'écriture pour tout le monde, indépendamment de l'umask actuel.

Cela a été corrigé en utilisant umask 0177 à la place. [perl #127322]

Corriger l'accès hors limites dans la gestion des chemins Win32

Ceci est CVE-2015-8608. Pour plus d'informations, voir [GH #15067] https://github.com/Perl/perl5/issues/15067

Corriger la perte de taint dans canonpath

Ceci est CVE-2015-8607. Pour plus d'informations, voir [GH #15084] https://github.com/Perl/perl5/issues/15084

Éviter l'accès à une mémoire non initialisée dans win32 crypt()

Ajout d'une validation qui détectera à la fois un sel court et des caractères invalides dans le sel. [GH #15091] https://github.com/Perl/perl5/issues/15091

Supprimer les variables d'environnement en double de "environ"

Pour éviter une vulnérabilité de sécurité, lorsqu'un programme est exécuté avec l'option -T (taint mode), perl va maintenant supprimer les doublons de variables d'environnement que le système d'exploitation peut avoir inclus.

Divers

La valeur de retour de Autoloader "AUTOLOAD" est maintenant plus cohérente

Le code à l'intérieur de la méthode AUTOLOAD est maintenant exécuté dans le package de l'appelant, plutôt que dans le package où le sous-programme manquant est défini. Cela permet à AUTOLOAD de mieux se comporter par défaut lors de l'appel d'une méthode ou d'un sous-programme

La gestion des erreurs de compilation est améliorée

L'erreur de compilation "Too many dots" s'est produite dans le cas de "use Foo::Bar::Baz::" (avec une barre oblique finale). Cela s'est produit car le compilateur ne pouvait pas trouver le nom du paquet de remplacement. Le compilateur recherche désormais le nom du paquet de remplacement à la place, et s'il ne le trouve pas, il génère une erreur plus informative.

Supprimer les variables d'environnement doublons de "environ"

Auparavant, si une variable d'environnement apparaissait plus d'une fois dans "environ[]", %ENV contenait la dernière entrée pour ce nom, tandis qu'un getenv() typique retournait la première entrée. Nous nous assurons maintenant que %ENV contient la même chose que ce que retourne "getenv".

Deuxièmement, nous supprimons les doublons de "environ[]", donc si un réglage portant ce nom est défini dans %ENV, nous ne passerons pas une valeur non sécurisée à un processus enfant.

[CVE-2016-2381]

Changements incompatibles

La fonctionnalité "autoderef" a été supprimée

La fonctionnalité expérimentale "autoderef" (qui permettait d'appeler "push", "pop", "shift", "unshift", "splice", "keys", "values" et "each" sur un argument scalaire) a été jugée infructueuse. Elle a maintenant été supprimée ; toute tentative d'utilisation de cette fonctionnalité (ou de désactivation de l'avertissement "experimental::autoderef" qu'elle déclenchait auparavant) génère désormais une exception.

Le "$_" lexical a été supprimé

"my $_" a été introduit dans Perl 5.10, et a ensuite causé beaucoup de confusion sans solution évidente. Dans Perl 5.18.0, il a été rendu expérimental dans l'idée qu'il serait soit supprimé, soit redessiné d'une manière moins confuse (mais rétroactivement incompatible). Au cours des années suivantes, aucune alternative n'a été proposée. La fonctionnalité a maintenant été supprimée et échouera à la compilation.

"qr/\b{wb}/" est maintenant adapté aux attentes de Perl

Il est maintenant plus approprié comme remplacement direct pour "\b", mais donne de meilleurs résultats pour l'analyse du langage naturel. Auparavant, il suivait strictement les règles Unicode actuelles, ce qui le faisait correspondre entre chaque caractère d'espacement. Maintenant, il ne correspond généralement pas aux étendues d'espacement, se comportant comme "\b". Voir "\b{wb}" dans perlrebackslash.

Erreurs de compilation d'expressions régulières

Certains motifs d'expressions régulières qui causaient des erreurs d'exécution ne se compilent maintenant plus du tout.

Presque toutes les propriétés Unicode utilisant les constructions de motifs d'expressions régulières "\p{}" et "\P{}" sont maintenant vérifiées pour leur validité lors de la compilation du motif, et les motifs invalides feront échouer la compilation du programme. Dans les versions précédentes, cette vérification était souvent reportée à l'exécution. Chaque fois qu'une vérification d'erreur est déplacée de l'exécution à la compilation, le code erroné est détecté 100% du temps, alors qu'auparavant, il n'était détecté que si et quand la partie fautive était effectivement exécutée, ce qui pour du code inaccessible pouvait ne jamais arriver.

"qr/\N{}/" est maintenant interdit sous "use re "strict""

Un "\N{}" vide n'a pas de sens, mais pour des raisons de compatibilité ascendante, il est accepté comme ne faisant rien, bien qu'un avertissement de dépréciation soit émis par défaut. Mais maintenant, c'est une erreur fatale sous la fonctionnalité expérimentale "mode 'strict'" dans re.

Les déclarations imbriquées sont maintenant interdites

Une déclaration "my", "our" ou "state" n'est plus autorisée à l'intérieur d'une autre déclaration "my", "our" ou "state".

Par exemple, ceci est maintenant fatal :

my ($x, my($y));
our (my $x);

[GH #14799] https://github.com/Perl/perl5/issues/14799

[GH #13548] https://github.com/Perl/perl5/issues/13548

La classe de caractères "/\C/" a été supprimée

Cette classe de caractères d'expression régulière a été dépréciée dans la v5.20.0 et a produit un avertissement de dépréciation depuis la v5.22.0. C'est maintenant une erreur de compilation. Si vous avez besoin d'examiner les octets individuels qui composent un caractère encodé en UTF8, utilisez d'abord utf8::encode() sur la chaîne (ou une copie).

chdir('') ne chdirera plus vers le dossier personnel

L'utilisation de chdir('') ou chdir(undef) pour changer vers le dossier personnel est dépréciée depuis perl v5.8, et échouera maintenant. Utilisez chdir() à la place.

Les caractères ASCII dans les noms de variables doivent maintenant être entièrement visibles

Il était légal jusqu'à présent sur les plateformes ASCII pour les noms de variables de contenir des caractères de contrôle ASCII non graphiques (ordinaux 0 à 31, et 127, qui sont les contrôles C0 et "DELETE"). Cette utilisation est dépréciée depuis la v5.20, et provoque maintenant une erreur de syntaxe. Les variables auxquelles ces noms faisaient référence sont spéciales, réservées par Perl pour tout usage qu'il pourrait choisir, maintenant ou dans le futur. Chaque variable de ce type a une manière alternative de l'épeler. Au lieu du seul caractère de contrôle non graphique, une séquence de deux caractères commençant par un accent circonflexe est utilisée, comme $^] et "${^GLOBAL_PHASE}". Les détails se trouvent dans perlvar. Il reste légal, bien que déconseillé et déprécié (provoquant un avertissement de dépréciation), d'utiliser certains caractères non graphiques non-ASCII dans les noms de variables lorsque "use utf8" n'est pas actif. Aucun code ne devrait faire cela, car toutes ces variables sont réservées par Perl, et Perl n'en définit actuellement aucune (mais pourrait le faire à tout moment, sans préavis).

Un problème d'un décalage dans $Carp::MaxArgNums a été corrigé

$Carp::MaxArgNums est censé être le nombre d'arguments à afficher. Avant cette version, il affichait au lieu de cela $Carp::MaxArgNums + 1 arguments, contrairement à la documentation.

Seuls les espaces et les tabulations sont maintenant autorisés dans "[...]" dans "(?[...])"

Les classes de caractères entre crochets étendues expérimentales peuvent contenir des classes de caractères entre crochets régulières. Celles-ci diffèrent des classes régulières en ce que les espaces blancs sont généralement ignorés, sauf s'ils sont échappés par un antislash précédent. L'espace blanc ignoré est maintenant limité aux tabulations "\t" et aux caractères ESPACE. Auparavant, il s'agissait de tout espace blanc. Voir "Extended Bracketed Character Classes" dans perlrecharclass.

Dépréciations

L'utilisation de points de code supérieurs au "IV_MAX" de la plateforme est maintenant dépréciée

Unicode définit les points de code dans la plage "0..0x10FFFF". Certaines normes à une époque les définissaient jusqu'à 2**31 - 1, mais Perl a permis qu'ils soient aussi élevés que tout ce qui peut tenir dans un mot sur la plateforme utilisée. Cependant, l'utilisation de ceux supérieurs au "IV_MAX" de la plateforme est problématique dans certaines constructions, notamment "tr///", les motifs d'expressions régulières impliquant des quantificateurs, et dans certaines opérations arithmétiques et de comparaison, comme être la limite supérieure d'une boucle. Maintenant, l'utilisation de tels points de code déclenche un avertissement de dépréciation, à moins que cette catégorie d'avertissement ne soit désactivée. "IV_MAX" est généralement 2**31 -1 sur les plateformes 32 bits, et 2**63-1 sur les plateformes 64 bits.

Effectuer des opérations binaires sur des chaînes contenant des points de code supérieurs à 0xFF est déprécié

Les opérateurs binaires sur chaînes traitent leurs opérandes comme des chaînes d'octets, et les valeurs au-delà de 0xFF sont absurdes dans ce contexte. Pour opérer sur des octets encodés, encodez d'abord les chaînes. Pour opérer sur les valeurs numériques des points de code, utilisez "split" et "map ord". À l'avenir, cet avertissement sera remplacé par une exception.

sysread(), syswrite(), recv() et send() sont dépréciés sur les handles :utf8

Les opérateurs sysread(), recv(), syswrite() et send() sont dépréciés sur les handles qui ont la couche ":utf8", soit par

explicitement, ou implicitement, par ex., avec la couche :encoding(UTF-16LE).

Les deux sysread() et recv() utilisent actuellement uniquement le drapeau ":utf8" pour le flux, ignorant les couches réelles. Comme sysread() et recv() ne font aucune validation UTF-8, ils peuvent finir par créer des scalaires encodés de manière invalide.

De même, syswrite() et send() utilisent uniquement le drapeau ":utf8", ignorant autrement toutes les couches. Si le drapeau est défini, les deux écrivent la valeur encodée en UTF-8, même si la couche est un encodage différent, tel que l'exemple ci-dessus.

Idéalement, tous ces opérateurs ignoreraient complètement l'état ":utf8", travaillant uniquement avec des octets, mais cela entraînerait la rupture silencieuse du code existant. Pour éviter cela, une future version de perl lèvera une exception lorsque l'un des sysread(), recv(), syswrite() ou send() sera appelé sur un handle avec la couche ":utf8".

Améliorations des Performances

  • Le surcoût de l'entrée et de la sortie de portée a été considérablement réduit, de sorte que, par exemple, les appels de sous-routines, les boucles et les blocs de base sont maintenant plus rapides. Cet appel de fonction vide prend maintenant environ un tiers de temps en moins pour s'exécuter : 
    sub f{} f();
  • De nombreuses langues, comme le chinois, ne font pas de distinction entre majuscules et minuscules. Perl connaît maintenant la plupart d'entre elles et évite une grande partie du travail lorsqu'un programme tente de changer la casse dans celles-ci (comme ucfirst()) ou de faire des correspondances sans distinction de casse ("qr//i"). Cela accélérera un programme, comme un serveur web, qui peut fonctionner sur plusieurs langues tout en fonctionnant sur une langue sans distinction de casse.
  • "/sous-chaîne-fixe/" a été rendu beaucoup plus rapide.

    Sur les plates-formes disposant d'une implémentation libc memchr() qui utilise bien le support matériel sous-jacent, les motifs qui incluent des sous-chaînes fixes seront maintenant souvent beaucoup plus rapides ; par exemple avec glibc sur un CPU x86_64 récent, ceci :

    $s = "a" x 1000 . "wxyz";
$s =~ /wxyz/ for 1..30000

    est maintenant environ 7 fois plus rapide. Sur les systèmes disposant d'un memchr() lent, par exemple un Raspberry Pi ARM 32 bits, il y aura une légère amélioration de la vitesse. Inversement, certains cas pathologiques, comme ""ab" x 1000 =~ /aa/" seront plus lents maintenant ; jusqu'à 3 fois plus lents sur le rPi, 1,5 fois plus lents sur x86_64.

  • Addition, soustraction et multiplication plus rapides.

    Depuis 5.8.0, l'arithmétique est devenue plus lente en raison de la nécessité de supporter les entiers de 64 bits. Pour traiter les entiers de 64 bits, il faut vérifier beaucoup plus de cas limites, ce qui prend du temps. Nous détectons maintenant les cas courants où il n'est pas nécessaire de vérifier ces cas limites et nous les traitons spécifiquement.

  • Les préincrémentations, prédécrémentations, postincrémentations et postdécrémentations ont été rendues plus rapides en divisant en interne les fonctions qui géraient plusieurs cas en différentes fonctions.
  • La création de structures de données de débogueur Perl (voir "Debugger Internals" dans perldebguts) pour les XSUBs et les sous-programmes constants a été supprimée. Cela a supprimé un combo glob/scalaire pour chaque fichier ".c" unique d'où provenaient les XSUBs et les sous-programmes constants. Au démarrage ("perl -e"0""), une demi-douzaine de combos de débogueur glob/scalaire ont été créés. Le chargement de modules XS a créé plus de combos glob/scalaire. Ces éléments étaient créés, que le débogueur perl soit utilisé ou non, et malgré le fait qu'il ne puisse pas déboguer le code C de toute façon.
  • Sur Win32, le fait de faire un "stat" ou un "-X" sur un chemin, si le fichier ou le répertoire n'existe pas, est maintenant 3,5 fois plus rapide qu'auparavant.
  • Les arguments uniques dans l'affectation de liste sont maintenant légèrement plus rapides : 
    ($x) = (...);
(...) = ($x);
  • Moins de mémoire de pointe est maintenant utilisée lors de la compilation des motifs d'expressions régulières.

EBCDIC
UTF-EBCDIC étendu
UTF-EBCDIC est similaire à UTF-8, mais pour les plateformes EBCDIC. Il a été étendu pour pouvoir représenter des points de code jusqu'à 2 ** 64 - 1 sur les plateformes disposant de mots de 64 bits. Cela le met à parité avec UTF-8. Cette amélioration nécessite un changement incompatible dans la représentation des points de code dans la plage 2 ** 30 à 2 ** 31 -1 (cette dernière étant le point de code maximal précédemment représentable). Cela signifie qu'un fichier contenant l'un de ces points de code, écrit avec des versions précédentes de perl, ne peut pas être lu, sans conversion, par une perl contenant cette modification. Nous ne pensons pas que de tels fichiers existent, mais si vous en avez un, soumettez un ticket à perlbug@perl.org <mailto:perlbug@perl.org>, et nous écrirons un script de conversion pour vous.
EBCDIC cmp() et sort() corrigés pour les chaînes UTF-EBCDIC
La comparaison de deux chaînes encodées en UTF-8 (ou plus précisément, UTF-EBCDIC) ne fonctionnait pas correctement jusqu'à présent. Comme sort() utilise cmp(), cela corrige également cela.
EBCDIC "tr///" et "y///" corrigés pour "\N{}" et les plages "use utf8"
Perl v5.22 a introduit le concept de plages portables dans les motifs d'expressions régulières. Une plage portable correspond au même ensemble de caractères, quelle que soit la plateforme sur laquelle le programme s'exécute. Ce concept est maintenant étendu à "tr///". Voir "tr///".

Notez qu'aucun changement significatif n'a été apporté aux API externes, mais le code XS qui repose sur ces détails internes pourrait nécessiter des corrections. Les principaux changements sont :
    • Les macros PUSHBLOCK(), POPSUB() etc. ont été remplacées par des fonctions inline statiques telles que cx_pushblock(), cx_popsub() etc. Celles-ci utilisent des arguments de fonction plutôt que de s'appuyer implicitement sur des variables locales telles que "gimme" et "newsp" disponibles. De plus, leur fonctionnalité a changé : en particulier, cx_popblock() ne décrémente plus "cxstack_ix". L'ordre des étapes dans les fonctions "pp_leave*" impliquant cx_popblock(), cx_popsub() etc. a changé. Voir la nouvelle documentation, "Dynamic Scope and the Context Stack" dans perlguts, pour les détails sur leur utilisation.
    • Diverses macros, qui ont désormais un préfixe CX_ cohérent, ont été ajoutées : 
      CX_CUR(), CX_LEAVE_SCOPE(), CX_POP()

      ou renommées :

      CX_POP_SAVEARRAY(), CX_DEBUG(), CX_PUSHSUBST(), CX_POPSUBST()
    • cx_pushblock() sauvegarde désormais "PL_savestack_ix" et "PL_tmps_floor", de sorte que "pp_enter*" et "pp_leave*" ne font plus 
      ENTER; SAVETMPS; ....; LEAVE
    • cx_popblock() restaure désormais également "PL_curpm".
    • Dans dounwind() pour chaque type de contexte, la trame savestack courante est désormais traitée avant que chaque contexte ne soit dépilé ; auparavant, cela n'était fait que pour les cadres de contexte similaires à des sous-routines. Cette action a été supprimée de cx_popsub() et placée dans sa propre macro, CX_LEAVE_SCOPE(cx), qui doit être appelée avant cx_popsub() etc.

      dounwind() effectue désormais également un cx_popblock() sur le dernier cadre dépilé (auparavant, il n'effectuait que les actions cx_popsub() etc. sur chaque cadre).

    • La pile des temporaires est désormais libérée à la sortie de la portée ; auparavant, les temporaires créés lors de la dernière instruction d'un bloc ne seraient libérés qu'au prochain "nextstate" suivant le bloc (à l'exception d'un hack existant qui faisait cela pour les sous-routines récursives dans un contexte scalaire) ; et dans quelque chose comme "f(g())", les temporaires créés par la dernière instruction dans g() ne seraient auparavant pas libérés avant l'instruction suivant le retour de f().
    • La plupart des valeurs qui étaient sauvegardées sur la savestack lors de l'entrée dans une portée sont désormais sauvegardées dans de nouveaux champs appropriés dans la structure de contexte, et sauvegardées et restaurées directement par cx_pushfoo() et cx_popfoo(), ce qui est beaucoup plus rapide.
    • Divers champs de la structure de contexte ont été ajoutés, supprimés ou modifiés.
    • La gestion de @_ dans cx_pushsub() et cx_popsub() a été considérablement simplifiée, notamment en supprimant le champ "argarray" de la structure de contexte, et en extrayant une partie du code commun (mais rarement utilisé) dans une fonction séparée, clear_defarray(). De plus, des sous-ensembles utiles de cx_popsub() qui avaient été déroulés à des endroits comme "pp_goto" ont été regroupés dans les nouvelles fonctions cx_popsub_args() et cx_popsub_common().
    • "pp_leavesub" et "pp_leavesublv" utilisent désormais la même fonction que le reste des "pp_leave*" pour traiter les arguments de retour.
    • Les indicateurs "CXp_FOR_PAD" et "CXp_FOR_GV" ont été ajoutés, et "CXt_LOOP_FOR" a été divisé en "CXt_LOOP_LIST", "CXt_LOOP_ARY".
    • Certaines variables anciennement déclarées par "dMULTICALL" (mais non documentées) ont été supprimées.
    • La variable obscure "PL_timesbuf", effectivement un vestige de Perl 1, a été supprimée. Elle était documentée comme étant dépréciée dans Perl 5.20, avec une mention indiquant qu'elle serait supprimée au début de la série 5.21.x ; cela est maintenant finalement arrivé. [GH #13632] https://github.com/Perl/perl5/issues/13632
    • Une assertion injustifiée dans Perl_newATTRSUB_x() a été supprimée. Si une définition de sous-routine "stub" avec un prototype a été rencontrée, alors toute "stub" (ou définition) subséquente de la même sous-routine avec un attribut provoquait un échec d'assertion en raison d'un pointeur nul. [GH #15081] https://github.com/Perl/perl5/issues/15081
    • "::" a été remplacé par "__" dans "ExtUtils::ParseXS", comme cela est fait pour les paramètres/valeurs de retour. C'est plus cohérent et simplifie l'écriture de code XS encapsulant des classes C++ dans un espace de noms Perl imbriqué (cela ne nécessite qu'un typedef pour "Foo__Bar" au lieu de deux, un pour "Foo_Bar" et l'autre pour "Foo::Bar").
    • La fonction to_utf8_case() est désormais dépréciée. Utilisez plutôt "toUPPER_utf8", "toTITLE_utf8", "toLOWER_utf8", et "toFOLD_utf8". (Voir http://nntp.perl.org/group/perl.perl5.porters/233287.)
    • Le code principal de Perl et l'extension threads ont été annotés de sorte que, si Perl est configuré pour utiliser des threads, alors lors de la compilation, clang (3.6 ou ultérieur) avertira des utilisations suspectes de mutex. Voir http://clang.llvm.org/docs/ThreadSafetyAnalysis.html pour plus d'informations.
    • L'émulation de signbit() a été améliorée. Cela aidera les plateformes ou configurations plus anciennes et/ou plus exotiques.
    • La plupart du code spécifique EBCDIC dans le cœur a été unifié avec le code non-EBCDIC, afin d'éviter les répétitions et de faciliter la maintenance.
    • Le code MSWin32 pour $^X a été déplacé du répertoire win32 vers caretx.c, où d'autres systèmes d'exploitation définissent cette variable.
    • sv_ref() fait désormais partie de l'API.
    • "sv_backoff" dans perlapi a vu son type de retour modifié de "int" à "void". Il retournait auparavant toujours 0 depuis Perl 5.000 stable, mais cela n'était pas documenté. Bien que "sv_backoff" soit marqué comme API publique, le code XS n'est pas censé être impacté car l'appel API approprié se ferait via l'API publique "sv_setsv(sv, &PL_sv_undef)", ou l'API quasi-publique "SvOOK_off", ou les appels non-publics "SvOK_off", et la valeur de retour de "sv_backoff" était auparavant une constante dénuée de sens qui peut être réécrite comme "(sv_backoff(sv),0)".
    • Les macros "EXTEND" et "MEXTEND" ont été améliorées pour éviter divers problèmes de troncature et de dépassement d'entiers. En particulier, certains transtypages utilisés précédemment dans les macros ont été supprimés. Cela signifie par exemple que passer un argument non signé "nitems" risque désormais de provoquer un avertissement du compilateur (il a toujours été documenté comme nécessitant une valeur signée ; anciennement int, récemment SSize_t).

      TO Perl 5.24.0 NEWS

      This document outlines the changes made to the Perl interpreter and core modules between the release of Perl 5.22.0 and Perl 5.24.0. The following list is a summary of the most significant changes. For a comprehensive list, please see the Changes file in the Perl source distribution.

      • A crash with "qr/(?[...])" constructs within regular expression patterns could cause a segfault instead of a proper error message. [GH #14933] https://github.com/Perl/perl5/issues/14933 [GH #14996] https://github.com/Perl/perl5/issues/14996
      • Another problem with "(?[...])" constructs has been fixed wherein things like "\c]" could cause panics. [GH #14934] https://github.com/Perl/perl5/issues/14934
      • Some problems with attempting to extend the perl stack to around 2G or 4G entries have been fixed. This was particularly an issue on 32-bit perls built to use 64-bit integers, and was easily noticeable with the list repetition operator, e.g. 
        @a = (1) x $big_number

        Formerly perl may have crashed, depending on the exact value of $big_number; now it will typically raise an exception. [GH #14880] https://github.com/Perl/perl5/issues/14880

      • In a regex conditional expression "(?(condition)yes-pattern|no-pattern)", if the condition is "(?!)" then perl failed the match outright instead of matching the no-pattern. This has been fixed. [GH #14947] https://github.com/Perl/perl5/issues/14947
      • The special backtracking control verbs "(*VERB:ARG)" now all allow an optional argument and set "REGERROR"/"REGMARK" appropriately as well. [GH #14937] https://github.com/Perl/perl5/issues/14937
      • Several bugs, including a segmentation fault, have been fixed with the boundary checking constructs (introduced in Perl 5.22) "\b{gcb}", "\b{sb}", "\b{wb}", "\B{gcb}", "\B{sb}", and "\B{wb}". All the "\B{}" ones now match an empty string; none of the "\b{}" ones do. [GH #14976] https://github.com/Perl/perl5/issues/14976
      • Duplicating a closed file handle for write no longer creates a filename of the form GLOB(0xXXXXXXXX). [perl #125115]
      • Warning fatality is now ignored when rewinding the stack. This prevents infinite recursion when the now fatal error also causes rewinding of the stack. [perl #123398]
      • In perl v5.22.0, the logic changed when parsing a numeric parameter to the -C option, such that the successfully parsed number was not saved as the option value if it parsed to the end of the argument. [perl #125381]
      • The PadlistNAMES macro is an lvalue again.
      • Zero -DPERL_TRACE_OPS memory for sub-threads.

        perl_clone_using() was missing Zero init of PL_op_exec_cnt[]. This caused sub-threads in threaded -DPERL_TRACE_OPS builds to spew exceedingly large op-counts at destruct. These counts would print %x as "ABABABAB", clearly a mem-poison value.

      • A leak in the XS typemap caused one scalar to be leaked each time a "FILE *" or a "PerlIO *" was "OUTPUT:"ed or imported to Perl, since perl 5.000. These particular typemap entries are thought to be extremely rarely used by XS modules. [perl #124181]
      • alarm() and sleep() will now warn if the argument is a negative number and return undef. Previously they would pass the negative value to the underlying C function which may have set up a timer with a surprising value.
      • Perl can again be compiled with any Unicode version. This used to (mostly) work, but was lost in v5.18 through v5.20. The property "Name_Alias" did not exist prior to Unicode 5.0. Unicode::UCD incorrectly said it did. This has been fixed.
      • Very large code-points (beyond Unicode) in regular expressions no longer cause a buffer overflow in some cases when converted to UTF-8. [GH #14858] https://github.com/Perl/perl5/issues/14858
      • The integer overflow check for the range operator (...) in list context now correctly handles the case where the size of the range is larger than the address space. This could happen on 32-bits with -Duse64bitint. [GH #14843] https://github.com/Perl/perl5/issues/14843
      • A crash with "%::=(); J->${\"::"}" has been fixed. [GH #14790] https://github.com/Perl/perl5/issues/14790
      • "qr/(?[ () ])/" no longer segfaults, giving a syntax error message instead. [perl #125805]
      • Regular expression possessive quantifier v5.20 regression now fixed. "qr/"PAT"{"min,max"}+""/" is supposed to behave identically to "qr/(?>"PAT"{"min,max"})/". Since v5.20, this didn't work if min and max were equal. [perl #125825]
      • "BEGIN <>" no longer segfaults and properly produces an error message. [perl #125341]
      • In "tr///" an illegal backwards range like "tr/\x{101}-\x{100}//" was not always detected, giving incorrect results. This is now fixed.
