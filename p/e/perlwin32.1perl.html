PERLWIN32(1perl) Guide de référence du programmeur Perl PERLWIN32(1perl)

NOM

perlwin32 - Perl sous Windows

SYNTAXE

Ce sont des instructions pour compiler Perl sous Windows 7 et plus récent.

DESCRIPTION

Avant de commencer, vous devriez parcourir le fichier README situé dans le répertoire de niveau supérieur dans lequel la distribution Perl a été extraite. Assurez-vous de lire et de comprendre les conditions sous lesquelles ce logiciel est distribué.

Assurez-vous également de lire la section « BUGS ET LIMITATIONS » ci-dessous pour connaître les limitations connues de ce portage.

Le fichier INSTALL dans le répertoire racine de Perl contient de nombreuses informations qui ne sont pertinentes que pour les personnes compilant Perl sur des systèmes de type Unix. En particulier, vous pouvez ignorer en toute sécurité toute information parlant de "Configure".

Vous pourriez également vouloir examiner une autre option pour compiler un Perl qui fonctionnera sous Windows : le fichier README.cygwin, qui donne un ensemble différent de règles pour compiler un Perl pour Windows. Cette méthode vous permettra probablement de compiler un Perl plus compatible avec Unix, mais vous devrez également télécharger et utiliser divers autres logiciels de support au moment de la compilation et à l'exécution décrits dans ce fichier.

Cet ensemble d'instructions est destiné à décrire un portage dit « natif » de Perl vers la plateforme Windows. Cela inclut les systèmes d'exploitation Windows 32 bits et 64 bits. Le Perl résultant ne nécessite aucun logiciel supplémentaire pour fonctionner (autre que celui fourni avec votre système d'exploitation). Actuellement, ce port est capable d'utiliser l'un des compilateurs suivants sur les architectures Intel x86 et x86_64 :

Microsoft Visual C++    Visual C++ 2015 (version 14.0) ou plus récent
Intel C++ Compiler      (expérimental)
Gcc by mingw.org        gcc version 3.4.5-5.3.0
Gcc by mingw-w64.org    gcc version 4.4.3 ou plus récent

Notez que les deux derniers sont en fait des projets concurrents qui fournissent tous deux une chaîne d'outils gcc complète pour MS Windows :

https://osdn.net/projects/mingw/
Fournit une chaîne d'outils gcc compilant des exécutables 32 bits (qui peuvent être utilisés sur les plateformes Windows 32 bits et 64 bits).
https://mingw-w64.org
Fournit une chaîne d'outils gcc ciblant les plateformes Windows 64 bits et 32 bits (malgré le nom du projet « mingw-w64 », ils ne sont pas uniquement orientés 64 bits). Ils fournissent les compilateurs gcc natifs et les compilateurs croisés qui sont également pris en charge par le Makefile de Perl.

Les compilateurs Microsoft Visual C++ sont également distribués gratuitement. Ils sont disponibles sous forme de "Visual C++ 2015-2022 Community Edition" et sont les mêmes compilateurs que ceux fournis avec "Visual C++ 2015-2022 Professional".

Le compilateur MinGW64 est disponible sur https://mingw-w64.org. Ce dernier est en fait un compilateur croisé ciblant Win64. Il existe également un compilateur allégé (sans java, ni gfortran) adapté à la compilation de Perl, disponible sur : https://strawberryperl.com/package/kmx/64_gcctoolchain/

NOTE : Si vous utilisez un compilateur 32 bits pour compiler Perl sur un système d'exploitation Windows 64 bits, vous devez définir la variable d'environnement WIN64 sur "undef". De plus, le compilateur allégé ne passe les tests que lorsque USE_ITHREADS est défini (par opposition à undef) et lorsque la ligne CFG *= Debug est commentée.

Ce portage prend entièrement en charge MakeMaker (l'ensemble des modules utilisés pour construire des extensions à Perl). Par conséquent, vous devriez être capable de compiler et d'installer la plupart des extensions trouvées sur les sites CPAN. Voir « Astuces d'utilisation pour Perl sous Windows » ci-dessous pour des conseils généraux à ce sujet.

Configuration de Perl sous Windows

Make
Vous avez besoin d'un programme "make" pour compiler les sources. Si vous utilisez Visual C++, vous pouvez utiliser nmake fourni avec Visual C++. Vous pouvez également utiliser gmake au lieu de nmake. Les compilations utilisant gcc nécessitent gmake. nmake n'est pas pris en charge pour les compilations gcc. La compilation parallèle n'est prise en charge qu'avec gmake, pas avec nmake.
Shell de Commande
Utilisez le shell "cmd" par défaut fourni avec Windows. Certaines versions du populaire shell 4DOS/NT ont des incompatibilités qui peuvent vous causer des problèmes. Si la compilation échoue sous ce shell, essayez de la relancer avec le shell cmd.

Assurez-vous que le chemin du répertoire de compilation ne contient pas d'espaces. La compilation fonctionne généralement dans ce cas, mais certains tests échoueront.

Microsoft Visual C++
Le nmake fourni avec Visual C++ suffira pour la compilation. Visual C++ nécessite que certaines choses soient configurées dans la console avant que Visual C++ ne puisse s'exécuter correctement. Pour qu'une boîte de console puisse exécuter le compilateur C, vous devrez au préalable exécuter "vcvarsall.bat x86" pour compiler pour x86-32 et pour x86-64 "vcvarsall.bat amd64". Lors d'une installation typique d'un produit de compilateur Microsoft C++, ces fichiers batch seront déjà dans votre variable d'environnement "PATH", vous pourrez donc les taper sans chemin absolu dans votre console. Si vous avez besoin de trouver le chemin absolu du fichier batch, il se trouve généralement quelque part comme C:\Program Files (x86)\Microsoft Visual Studio 14.0\VC. Avec certains produits C Microsoft plus récents (sortis après ~2004), l'installateur placera un raccourci dans le menu Démarrer pour lancer une nouvelle fenêtre de console avec la console déjà configurée pour votre architecture cible (x86-32 ou x86-64 ou IA64). Avec les compilateurs plus récents, vous pouvez également utiliser les anciens fichiers batch si vous le souhaitez.
Microsoft Visual C++ 2015-2022 Community Edition
Ces versions gratuites de Visual C++ 2015-2022 Professional contiennent les mêmes compilateurs et linkers que ceux fournis avec les versions complètes, et contiennent également tout le nécessaire pour compiler Perl.

Ces paquets peuvent être téléchargés sur https://visualstudio.microsoft.com/.

Installez Visual C++ 2015-2022 Community, puis configurez votre environnement en utilisant, par exemple,

C:\Program Files\Microsoft Visual Studio 14.0\Common7\Tools\vsvars32.bat

(en supposant que l'emplacement d'installation par défaut ait été choisi).

Perl devrait maintenant se compiler en utilisant win32/Makefile. Vous devrez éditer ce fichier pour définir "CCTYPE" sur l'une des valeurs "MSVC140" à "MSVC143".

Outils de build Microsoft C++
Il existe également une version autonome (sans IDE) des outils de build mentionnés ci-dessus, contenant le compilateur MSVC, disponible en téléchargement sur https://visualstudio.microsoft.com/visual-cpp-build-tools/.

Ceci est également appelé Build Tools for Visual Studio.

GCC
Perl peut être compilé avec gcc de MinGW (version 3.4.5 ou plus récente) ou de MinGW64 (version 4.4.3 ou plus récente). Il peut être téléchargé ici :

https://osdn.net/projects/mingw/ https://www.mingw-w64.org/

Vous avez également besoin de gmake. Habituellement, il est fourni avec MinGW, mais son exécutable peut avoir un nom différent, tel que mingw32-make.exe.

Notez que la compilation MinGW échoue actuellement avec la version 6.3.0 ou plus récente.

Notez également que la compilation en mode C++ échoue actuellement avec MinGW 3.4.5 et 4.7.2 ou plus récent, et avec MinGW64 64 bits 6.3.0 ou plus récent.

Intel C++ Compiler
Un support expérimental pour l'utilisation de l'Intel C++ Compiler a été ajouté. Modifiez win32/Makefile et choisissez le "CCTYPE" correct pour le Visual C dans lequel Intel C a été installé. Décommentez également "__ICC" pour activer Intel C sur le support Visual C. Pour configurer l'environnement de build, depuis le menu Démarrer, exécutez le mode Visual Studio 20__ IA-32 ou le mode Visual Studio 20__ Intel 64 selon le cas. Ensuite, exécutez "nmake" comme d'habitude dans cette fenêtre de prompt.

Seul l'Intel C++ Compiler v12.1 a été testé. D'autres versions fonctionneront probablement. Utiliser l'Intel C++ Compiler au lieu de Visual C présente l'avantage de C9

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

9 compatibilité qui est nécessaire à certains modules CPAN XS, tout en maintenant la compatibilité avec le code objet Visual C et l'infrastructure de débogage Visual C, contrairement à GCC.

Compilation

  • Assurez-vous de vous trouver dans le sous-répertoire win32 du répertoire racine de Perl. Ce répertoire contient un Makefile qui fonctionnera avec les versions de "nmake" livrées avec Visual C++, et un GNUmakefile GNU make qui fonctionnera pour tous les compilateurs pris en charge. Les valeurs par défaut du fichier GNUmakefile de "gmake" sont configurées pour compiler avec MinGW/gcc.
  • Modifiez le GNUmakefile (ou le Makefile, si vous utilisez nmake) et modifiez les valeurs de INST_DRV et "INST_TOP". Vous pouvez également activer divers indicateurs de compilation. Ceux-ci sont expliqués dans les Makefiles.

    Notez qu'il n'est généralement pas conseillé d'essayer de compiler un "perl" avec "INST_DRV" et "INST_TOP" définis sur un chemin qui existe déjà à partir d'une compilation précédente. Cela peut notamment causer des problèmes avec le test lib/ExtUtils/t/Embed.t, qui tente de compiler un programme de test et peut finir par compiler contre le répertoire lib/CORE de Perl installé plutôt que celui testé.

    Vous devrez vous assurer que "CCTYPE" est correctement défini et que "CCHOME" pointe vers l'endroit où vous avez installé votre compilateur. Pour GCC, il doit s'agir du répertoire contenant les sous-répertoires bin, include et lib.

    Si vous compilez avec le compilateur croisé fourni par mingw-w64.org, vous devrez décommenter la ligne qui définit "GCCCROSS" dans le GNUmakefile. Ne le faites que s'il s'agit du compilateur croisé, c'est-à-dire seulement si le dossier bin ne contient pas de fichier gcc.exe. (Le compilateur croisé ne fournit pas de fichier gcc.exe, g++.exe, ar.exe, etc. Au lieu de cela, tous ces exécutables sont préfixés par "x86_64-w64-mingw32-".)

    La valeur par défaut de "CCHOME" dans les Makefiles pour Visual C++ peut ne pas être correcte pour certaines versions. Assurez-vous que la valeur par défaut existe et est valide.

    Si vous souhaitez intégrer statiquement certaines extensions de base dans la DLL de "perl", spécifiez-les dans la macro "STATIC_EXT".

    Lisez attentivement les instructions situées en haut des Makefiles.

  • Tapez "gmake" (ou "nmake" si vous utilisez cette version de "make").

    Cela devrait tout compiler. Plus précisément, cela créera perl.exe, perl542.dll au niveau du répertoire racine de Perl, et diverses autres DLL d'extension dans le répertoire lib\auto. Si la compilation échoue pour une raison quelconque, assurez-vous d'avoir correctement effectué les étapes précédentes.

    Pour essayer le mode parallèle de "gmake", tapez "gmake -j2" où 2 est le nombre maximal de tâches parallèles que vous souhaitez exécuter. Un certain nombre d'éléments du processus de compilation s'exécuteront en parallèle, mais il y aura des points de sérialisation où vous ne verrez qu'un seul CPU utilisé au maximum. C'est normal.

    Si vous êtes suffisamment expérimenté dans la compilation de code C, voici une suggestion pour accélérer la compilation de "perl", et plus tard de "make test". Essayez de conserver votre variable d'environnement "PATH" avec le moins de dossiers possible (n'oubliez pas de conserver les dossiers de votre compilateur C). C:\WINDOWS\system32 ou C:\WINNT\system32 selon la version de votre système d'exploitation devrait être le premier dossier dans "PATH", car "cmd.exe" est le programme le plus couramment lancé pendant la compilation et les tests ultérieurs.

Tests de Perl sous Windows

Tapez "gmake test" (ou "nmake test"). Cela exécutera la plupart des tests de la suite de tests (de nombreux tests seront ignorés).

Il ne devrait y avoir aucun échec de test.

Si vous compilez avec Visual C++ 2015 ou une version ultérieure, ext/XS-APItest/t/locale.t peut planter (après que tous ses tests aient réussi). Cela est dû à une régression dans le Universal CRT introduite dans la mise à jour d'avril 2018 de Windows 10, et sera corrigé dans la mise à jour de mai 2019, comme expliqué ici : https://developercommunity.visualstudio.com/content/problem/519486/setlocalelc-numeric-iso-latin-16-fails-then-succee.html.

Si vous compilez avec certaines versions (par exemple, 4.8.1) de gcc de mingw, ext/POSIX/t/time.t peut échouer au test 17 en raison d'un bug connu dans ces compilations gcc : voir https://sourceforge.net/p/mingw/bugs/2152/.

Certains échecs de tests peuvent survenir si vous utilisez un shell de commande autre que le "cmd.exe" natif, ou si vous compilez à partir d'un chemin contenant des espaces. Ne faites donc pas cela.

Si vous exécutez les tests à partir d'une fenêtre de shell emacs, vous pourriez voir des échecs dans op/stat.t. Exécutez "gmake test-notty" dans ce cas.

De plus, vous devez vous assurer que lors de "make test", vous n'avez aucun paquet d'outils GNU dans votre chemin : certains kits d'outils comme Unixutils incluent certains outils ("type" par exemple) qui remplacent les outils Windows et font échouer les tests. Supprimez-les de votre chemin pendant les tests pour éviter ces erreurs.

Pour voir la sortie des tests spécifiques qui échouent, exécutez le harnais depuis le répertoire t :

# en supposant que vous partez du répertoire win32
cd ..\win32
.\perl harness <liste des tests>

Veuillez signaler tout autre échec comme décrit dans la section "BUGS ET LIMITATIONS".

Installation de Perl sous Windows

Tapez "gmake install" ("nmake install"). Cela placera le Perl nouvellement compilé et les bibliothèques sous le chemin défini par "INST_TOP" dans le Makefile. Il installera également la documentation pod sous "$INST_TOP\$INST_VER\lib\pod" et les versions HTML de celle-ci sous "$INST_TOP\$INST_VER\lib\pod\html".

Pour utiliser le Perl que vous venez d'installer, vous devrez ajouter une nouvelle entrée à votre variable d'environnement PATH : "$INST_TOP\bin", par exemple :

set PATH=c:\perl\bin;%PATH%

Si vous avez choisi de décommenter "INST_VER" et "INST_ARCH" dans le Makefile, la structure d'installation est un peu plus compliquée et vous devrez ajouter deux nouveaux composants PATH : "$INST_TOP\$INST_VER\bin" et "$INST_TOP\$INST_VER\bin\$ARCHNAME", par exemple :

set PATH=c:\perl\5.6.0\bin;c:\perl\5.6.0\bin\MSWin32-x86;%PATH%

Astuces d'utilisation de Perl sous Windows

Variables d'environnement
Les chemins d'installation que vous avez définis lors de la compilation sont intégrés dans Perl, vous n'avez donc rien d'autre à faire pour commencer à utiliser ce Perl (sauf ajouter son emplacement à votre variable PATH).

Si vous placez des extensions dans des endroits inhabituels, vous pouvez définir PERL5LIB sur une liste de chemins séparés par des points-virgules où vous souhaitez que Perl recherche les bibliothèques. Recherchez des descriptions d'autres variables d'environnement que vous pouvez définir dans perlrun.

Vous pouvez également contrôler le shell que Perl utilise pour exécuter les commandes system() et les commandes entre guillemets via PERL5SHELL. Voir perlrun.

Perl ne dépend pas du registre, mais il peut rechercher certaines valeurs par défaut si vous choisissez de les y placer, à moins que cela ne soit désactivé au moment de la compilation avec USE_NO_REGISTRY. Au démarrage du processus Perl, Perl vérifie si "HKEY_CURRENT_USER\Software\Perl" et "HKEY_LOCAL_MACHINE\Software\Perl" existent. Si les clés existent, elles seront vérifiées pour le reste de la durée de vie du processus Perl pour certaines entrées. Les entrées dans "HKEY_CURRENT_USER\Software\Perl" remplacent les entrées dans "HKEY_LOCAL_MACHINE\Software\Perl". Une ou plusieurs des entrées suivantes (de type REG_SZ ou REG_EXPAND_SZ) peuvent être définies dans les clés :

lib-$]        chemin de la bibliothèque standard spécifique à la version à ajouter à @INC
lib           chemin de la bibliothèque standard à ajouter à @INC
sitelib-$]    chemin de la bibliothèque de site spécifique à la version à ajouter à @INC
sitelib       chemin de la bibliothèque de site à ajouter à @INC
vendorlib-$]  chemin de la bibliothèque fournisseur spécifique à la version à ajouter à @INC
vendorlib     chemin de la bibliothèque fournisseur à ajouter à @INC
PERL*         solution de secours pour toutes les recherches %ENV qui commencent par "PERL"

Notez que le $] dans ce qui précède n'est pas littéral. Remplacez la version de Perl pour laquelle vous souhaitez honorer cette entrée, par exemple 5.6.0. Les chemins doivent être séparés par des points-virgules, comme d'habitude sous Windows.

Globbing de fichiers
Par défaut, Perl gère le globbing de fichiers en utilisant l'extension File::Glob, qui fournit un globbing portable.

Si vous souhaitez que Perl utilise un globbing qui émule les particularités des conventions de nom de fichier DOS, vous pourriez envisager d'utiliser File::DosGlob pour remplacer l'implémentation interne de glob(). Voir File::DosGlob pour plus de détails.

Utilisation de Perl en ligne de commande
Si vous êtes habitué à utiliser Perl à partir de divers shells de ligne de commande que l'on trouve dans les environnements UNIX, vous serez moins que satisfait de ce que Windows offre en matière de shell de commande.

La chose cruciale à comprendre à propos de l'environnement Windows est que la ligne de commande que vous tapez est traitée deux fois avant d'être vue par Perl. D'abord, votre shell de commande (généralement CMD.EXE) pré-traite la ligne de commande, pour gérer la redirection

ion, expansion des variables d'environnement et emplacement de l'exécutable à exécuter. Ensuite, l'exécutable perl divise le reste de la ligne de commande en arguments individuels, en utilisant la bibliothèque d'exécution C sur laquelle Perl a été construit.

Il est particulièrement important de noter que ni le shell ni l'exécution C n'effectuent d'expansions de caractères génériques sur les arguments de la ligne de commande (donc les caractères génériques n'ont pas besoin d'être mis entre guillemets). De plus, les comportements de mise entre guillemets du shell et de l'exécution C sont au mieux rudimentaires (et peuvent, si vous utilisez un shell non standard, être incohérents). Le seul caractère de guillemet (utile) est le guillemet double ("). Il peut être utilisé pour protéger les espaces et autres caractères spéciaux dans les arguments.

La documentation Windows décrit les règles d'analyse du shell ici : https://docs.microsoft.com/en-us/windows-server/administration/windows-commands/cmd et les règles d'analyse de l'exécution C ici : https://msdn.microsoft.com/en-us/library/17w5ykft%28v=VS.100%29.aspx.

Voici quelques observations supplémentaires basées sur des expériences : l'exécution C divise les arguments aux espaces et les passe aux programmes dans argc/argv. Les guillemets doubles peuvent être utilisés pour empêcher les arguments contenant des espaces d'être séparés. Vous pouvez insérer un guillemet double dans un argument en l'échappant avec une barre oblique inverse et en enfermant l'argument entier entre guillemets doubles. La barre oblique inverse et la paire de guillemets doubles entourant l'argument seront supprimées par l'exécution C.

Les caractères de redirection de fichier "<" ">", et "|" peuvent être mis entre guillemets doubles (bien qu'il y ait des suggestions que ce ne soit pas toujours vrai). Les guillemets simples ne sont pas traités comme des guillemets par le shell ou l'exécution C, ils ne sont pas supprimés par le shell (juste pour rendre ce type de mise entre guillemets complètement inutile). Le caret "^" a également été observé comme se comportant comme un caractère de mise entre guillemets, mais cela semble être une fonctionnalité du shell, et le caret n'est pas supprimé de la ligne de commande, donc Perl le voit toujours (et l'exécution C ne traite pas le caret comme un caractère de guillemet).

Voici quelques exemples d'utilisation du shell "cmd" :

Ceci imprime deux guillemets doubles :

perl -e "print '\"\"' "

Ceci fait la même chose :

perl -e "print \"\\\"\\\"\" "

Ceci imprime "bar" et écrit "foo" dans le fichier "blurch" :

perl -e "print 'foo'; print STDERR 'bar'" > blurch

Ceci imprime "foo" ("bar" disparaît dans les limbes) :

perl -e "print 'foo'; print STDERR 'bar'" 2> nul

Ceci imprime "bar" et écrit "foo" dans le fichier "blurch" :

perl -e "print 'foo'; print STDERR 'bar'" 1> blurch

Ceci redirige "foo" vers le pager "less" et imprime "bar" sur la console :

perl -e "print 'foo'; print STDERR 'bar'" | less

Ceci redirige "foo\nbar\n" vers le pager less :

perl -le "print 'foo'; print STDERR 'bar'" 2>&1 | less

Ceci redirige "foo" vers le pager et écrit "bar" dans le fichier "blurch" :

perl -e "print 'foo'; print STDERR 'bar'" 2> blurch | less

Découvrir l'utilité du shell "command.com" sous Windows 9x est laissé en exercice au lecteur :)

Un problème particulièrement pernicieux avec le shell de commandes 4NT pour Windows est qu'il traite (presque) toujours un caractère % comme indiquant que l'expansion des variables d'environnement est nécessaire. Sous ce shell, il est donc important de toujours doubler les caractères % que vous voulez que Perl voie (par exemple, pour les variables de hachage), même lorsqu'ils sont mis entre guillemets.

Compilation d'extensions
Le Comprehensive Perl Archive Network (CPAN) propose une multitude d'extensions, dont certaines nécessitent un compilateur C pour être compilées. Consultez https://www.cpan.org/ pour plus d'informations sur CPAN.

Notez que toutes les extensions disponibles sur CPAN ne peuvent pas fonctionner dans l'environnement Windows ; vous devriez vérifier les informations sur https://www.cpantesters.org/ avant d'investir trop d'efforts dans le portage de modules qui ne se compilent pas facilement.

La plupart des extensions (qu'elles nécessitent un compilateur C ou non) peuvent être compilées, testées et installées avec le mantra standard :

perl Makefile.PL
$MAKE
$MAKE test
$MAKE install

où $MAKE est le programme 'make' que vous avez configuré pour utiliser perl. Utilisez "perl -V:make" pour savoir lequel. Certaines extensions peuvent ne pas fournir de suite de tests (donc "$MAKE test" peut ne rien faire ou échouer), mais la plupart des extensions sérieuses le font.

Il est important que vous utilisiez un programme 'make' pris en charge, et que Config.pm en soit informé.

Notez que MakeMaker génère des makefiles avec une syntaxe différente selon le 'make' qu'il pense que vous utilisez. Par conséquent, il est important que l'une des valeurs suivantes apparaisse dans Config.pm :

make='nmake'        # MakeMaker génère la syntaxe nmake
toute autre valeur     # MakeMaker génère la syntaxe make générique
                    #   (par exemple, GNU make, ou Perl make)

Si la valeur ne correspond pas au programme 'make' que vous souhaitez utiliser, modifiez Config.pm pour corriger cela.

Si un module implémente des XSUBs, vous aurez besoin d'un des compilateurs C pris en charge. Vous devez vous assurer que l'environnement du compilateur est configuré pour la compilation en ligne de commande avant d'exécuter "perl Makefile.PL" ou toute invocation de make.

Si un module ne compile pas pour une raison quelconque, recherchez attentivement la raison de l'échec et signalez les problèmes à l'auteur du module. S'il semble que le support de compilation d'extension est défectueux, signalez-le avec tous les détails sur la manière dont la compilation a échoué en utilisant le traqueur de problèmes GitHub à l'adresse https://github.com/Perl/perl5/issues.

Expansion des caractères génériques en ligne de commande
Les shells de commandes par défaut sur les systèmes descendants de DOS (tels qu'ils sont) n'étendent généralement pas les arguments génériques fournis aux programmes. Ils considèrent qu'il appartient à l'application de gérer cela. Ceci est généralement réalisé en liant l'application (dans notre cas, perl) avec du code de démarrage que les bibliothèques d'exécution C fournissent habituellement. Cependant, cela entraîne des versions incompatibles de perl (car le comportement du code d'expansion argv diffère selon le compilateur, et il est même bogué sur certains compilateurs). De plus, cela peut être une source de frustration si vous utilisez un tel binaire perl avec un shell alternatif qui *étend* les caractères génériques.

Au lieu de cela, la solution suivante fonctionne plutôt bien. Les avantages sont : 1) vous pouvez commencer à l'utiliser immédiatement ; 2) elle est plus puissante, car elle fera la bonne chose avec un motif comme */*/*.c ; 3) vous pouvez décider si vous voulez l'utiliser ou non ; et 4) vous pouvez étendre la méthode pour ajouter des personnalisations (ou même des types d'expansion de caractères génériques entièrement différents).

C:\> copy con c:\perl\lib\Wild.pm
# Wild.pm - émule l'expansion @ARGV du shell sur les shells qui ne le font pas
use File::DosGlob;
@ARGV = map {
             my @g = File::DosGlob::glob($_) if /[*?]/;
             @g ? @g : $_;
           } @ARGV;
1;
^Z
C:\> set PERL5OPT=-MWild
C:\> perl -le "for (@ARGV) { print }" */*/perl*.c
p4view/perl/perl.c
p4view/perl/perlio.c
p4view/perl/perly.c
perl5.005/win32/perlglob.c
perl5.005/win32/perllib.c
perl5.005/win32/perlglob.c
perl5.005/win32/perllib.c
perl5.005/win32/perlglob.c
perl5.005/win32/perllib.c

Notez qu'il y a deux étapes distinctes ici : 1) Vous devrez créer Wild.pm et le placer dans votre répertoire lib de perl. 2) Vous devrez définir la variable d'environnement PERL5OPT. Si vous voulez que l'expansion argv soit par défaut, définissez simplement PERL5OPT dans votre environnement de démarrage par défaut.

Si vous utilisez le compilateur Visual C, vous pouvez obtenir l'expansion des caractères génériques de la ligne de commande du runtime C intégrée dans le binaire perl. Le binaire résultant étendra toujours les lignes de commande non mises entre guillemets, ce qui peut ne pas être ce que vous voulez si vous utilisez un shell qui le fait pour vous. L'expansion effectuée est également quelque peu moins puissante que l'approche suggérée ci-dessus.

Notes sur Windows 64 bits
Windows .NET Server prend en charge le modèle de données LLP64 sur l'architecture Intel Itanium.

Le modèle de données LLP64 est différent du modèle de données LP64 qui est la norme sur les plateformes Unix 64 bits. Dans le premier, "int" et "long" sont tous deux des types de données 32 bits, tandis que les pointeurs sont de 64 bits de large. De plus, il existe un type intégral séparé de 64 bits de large, "__int64". En revanche, le modèle de données LP64 omniprésent sur les plateformes Unix fournit "int" comme type 32 bits, tandis que les types "long" et les pointeurs sont de précision 64 bits. Notez que les deux modèles permettent une adressabilité de 64 bits.

Windows 64 bits fonctionnant sur Itanium est capable d'exécuter des binaires x86 32 bits de manière transparente. Cela signifie que vous pourriez utiliser une version compilée en 32 bits de Perl sur un système 64 bits. Cela étant dit, pourquoi voudrait-on compiler une version 64 bits de Perl ? Voici quelques raisons pour lesquelles vous pourriez vous en soucier :

  • Une application native 64 bits s'exécutera beaucoup plus efficacement sur le matériel Itanium.
  • Il n'y a pas de limite de 2 Go pour la taille des processus.
  • Perl offre automatiquement la prise en charge des fichiers volumineux lorsqu'il est compilé sous Windows 64 bits.
  • Intégration de Perl à l'intérieur d'une application 64 bits.

Exécution des Scripts Perl

Les scripts Perl sous UNIX utilisent la ligne "#!" (également appelée "shebang") pour indiquer au système d'exploitation qu'il doit exécuter le fichier en utilisant perl. Windows n'a aucun moyen comparable d'indiquer que des fichiers arbitraires sont exécutables.

Au lieu de cela, toutes les méthodes disponibles pour exécuter des fichiers texte brut sous Windows reposent sur "l'extension" du fichier. Il existe trois méthodes pour utiliser cela pour exécuter des scripts perl :

1.
Il existe une fonctionnalité appelée "associations d'extensions de fichiers". Cela peut être manipulé
via les deux commandes "assoc" et "ftype" qui sont standard sous Windows. Tapez "ftype /?" pour un exemple complet sur la façon de configurer cela pour les scripts perl (Quoi ? Vous pensiez que Windows n'était pas prêt pour Perl ? :).
2.
Comme les associations de fichiers ne fonctionnent pas partout, et qu'il y a apparemment des bugs avec les associations de fichiers là où elles fonctionnent, l'ancienne méthode consistant à encapsuler le script perl pour qu'il ressemble à un fichier batch normal pour le système d'exploitation peut être utilisée. Le processus d'installation met à disposition le script "pl2bat.bat" qui peut être utilisé pour encapsuler les scripts perl dans des fichiers batch. Par exemple : 
pl2bat foo.pl

créera le fichier "FOO.BAT". Notez que "pl2bat" supprime tout suffixe .pl et ajoute un suffixe .bat au fichier généré.

Si vous utilisez le shell de commande 4DOS/NT ou similaire, notez que "pl2bat" utilise la variable "%*" dans le fichier batch généré pour faire référence à tous les arguments de la ligne de commande, vous devrez donc peut-être vous assurer que cette construction fonctionne dans les fichiers batch. À l'heure actuelle, les utilisateurs de 4DOS/NT auront besoin d'une instruction "ParameterChar = *" dans leur fichier 4NT.INI ou devront exécuter "setdos /p*" dans le fichier de démarrage 4DOS/NT pour activer cela.

3.
L'utilisation de "pl2bat" pose quelques problèmes : le nom du fichier est modifié, de sorte que les scripts qui dépendent de $0 pour trouver ce qu'ils doivent faire peuvent ne pas s'exécuter correctement ; l'exécution de "pl2bat" reproduit le contenu du script d'origine, et donc ce processus peut être intensif en maintenance si les originaux sont mis à jour souvent. Une approche différente qui évite ces deux problèmes est possible.

Un script appelé "runperl.bat" est disponible et peut être copié sous n'importe quel nom de fichier (avec le suffixe .bat). Par exemple, si vous l'appelez "foo.bat", il exécutera le fichier "foo" lorsqu'il sera exécuté. Comme vous pouvez exécuter des fichiers batch sur les plateformes Windows simplement en tapant le nom (sans l'extension), cela exécute effectivement le fichier "foo" lorsque vous tapez soit "foo", soit "foo.bat". Avec cette méthode, "foo.bat" peut même être situé à un endroit différent du fichier "foo", tant que "foo" est disponible quelque part dans le PATH. Si vos scripts se trouvent sur un système de fichiers qui autorise les liens symboliques, vous pouvez même éviter de copier "runperl.bat".

Divers choses

Un ensemble complet de documentation HTML est installé, vous devriez donc pouvoir l'utiliser si vous avez un navigateur web installé sur votre système.

"perldoc" est également un outil utile pour parcourir les informations contenues dans la documentation, en particulier en conjonction avec un pager comme "less" (dont les versions récentes ont un support Windows). Vous devrez peut-être définir la variable d'environnement PAGER pour utiliser un pager spécifique. "perldoc -f foo" affichera des informations sur l'opérateur perl "foo".

Une erreur courante lors de l'utilisation de ce port avec une bibliothèque graphique comme "Tk" est de supposer que le comportement normal de Perl d'ouvrir une fenêtre de ligne de commande disparaîtra. Ce n'est pas le cas. Si vous souhaitez démarrer une copie de "perl" sans ouvrir de fenêtre de ligne de commande, utilisez l'exécutable "wperl" créé lors du processus d'installation. L'utilisation est exactement la même que pour "perl" normal sous Windows, sauf que des options comme "-h" ne fonctionnent pas (car elles nécessitent une fenêtre de ligne de commande pour s'afficher).

Si vous trouvez des bugs dans perl, vous pouvez les signaler à https://github.com/Perl/perl5/issues.

BOGUES ET AVERTISSEMENTS

Norton AntiVirus interfère avec le processus de construction, en particulier s'il est configuré sur "AutoProtect, All Files, when Opened". Contrairement aux grandes applications, le processus de construction de perl ouvre et modifie un grand nombre de fichiers. Le fait que l'antivirus scanne chacun d'eux ralentit considérablement le processus de construction. Pire encore, avec PERLIO=stdio, le processus de construction échoue avec des messages étranges car le vérificateur de virus interagit mal avec miniperl.exe qui écrit des fichiers de configuration (il semble soit attraper une partie de fichier écrite et la traiter comme suspecte, soit le vérificateur de virus peut la "verrouiller" d'une manière qui empêche miniperl de la mettre à jour). La construction s'achève avec

set PERLIO=perlio

mais c'est peut-être juste de la chance. D'autres logiciels antivirus peuvent avoir des problèmes similaires.

Une extension d'interface graphique pour Git sous Windows telle que TortoiseGit ralentira considérablement la construction et plus tard l'exécution de "make test" car chaque fichier est vérifié pour son statut git dès qu'il est créé et/ou modifié. TortoiseGit ne cause aucun échec de test ni aucun problème de construction contrairement au logiciel antivirus décrit ci-dessus, mais il provoque une lenteur similaire. Il est suggéré d'utiliser le Gestionnaire des tâches pour rechercher les processus en arrière-plan qui utilisent une quantité élevée de CPU pendant le processus de construction.

Certaines des fonctions intégrées n'agissent pas exactement comme documenté dans perlfunc, et quelques-unes ne sont pas implémentées du tout. Pour éviter les surprises, en particulier si vous avez déjà utilisé Perl dans d'autres environnements d'exploitation ou si vous avez l'intention d'écrire du code portable vers d'autres environnements, consultez perlport pour une liste raisonnablement définitive de ces différences.

Toutes les extensions disponibles sur CPAN ne peuvent pas être construites ou fonctionner correctement dans l'environnement Windows. Voir "Building Extensions".

La plupart des appels liés aux sockets () sont pris en charge, mais ils peuvent ne pas se comporter comme sur les plateformes Unix. Voir perlport pour la liste complète.

La gestion des signaux peut ne pas se comporter comme sur les plateformes Unix (où elle ne "se comporte" pas exactement non plus :). Par exemple, l'appel de die () ou exit () à partir des gestionnaires de signaux provoquera une exception, car la plupart des implémentations de signal () sous Windows sont sévèrement handicapées. Ainsi, les signaux peuvent ne fonctionner que pour des choses simples comme la définition d'une variable drapeau dans le gestionnaire. L'utilisation des signaux sous ce port doit actuellement être considérée comme non prise en charge.

Veuillez décrire en détail tout problème et solution que vous pourriez trouver à <https://github.com/Perl/perl5/issues>, ainsi que la sortie produite par "perl -V".
