PERLGIT(1perl) Guide de référence du programmeur Perl PERLGIT(1perl)

NOM

perlgit - Informations détaillées sur git et le dépôt Perl

DESCRIPTION

Ce document fournit des détails sur l'utilisation de git pour développer Perl. Si vous êtes seulement intéressé par la création d'un correctif rapide, consultez d'abord perlhack. Ce document est destiné aux personnes qui contribuent régulièrement à Perl, y compris celles qui ont un accès en écriture au dépôt git.

CLONAGE DU RÉPÖSITOIRE

Tout le code source de Perl est conservé centralement dans un dépôt Git sur github.com.

Vous pouvez faire un clone en lecture seule du dépôt en exécutant :

% git clone git@github.com:Perl/perl5.git perl

Si vous ne pouvez pas utiliser ceci pour des raisons de pare-feu, vous pouvez également cloner via http :

% git clone https://github.com/Perl/perl5.git perl

TRAVAILLER AVEC LE RÉPÖSITOIRE

Une fois que vous êtes entré dans le répertoire du dépôt, vous pouvez l'inspecter. Après un clone, le dépôt contiendra une seule branche locale, qui sera également la branche actuelle, comme indiqué par l'astérisque.

% git branch
* blead

L'utilisation de l'option -a à la commande "branch" affichera également les branches de suivi distantes dans le dépôt :

% git branch -a
* blead
  origin/HEAD
  origin/blead
...

Les branches qui commencent par "origin" correspondent au "git remote" que vous avez cloné (nommé "origin"). Chaque branche distante sera exactement suivie par ces branches. Vous ne devez JAMAIS travailler sur ces branches de suivi distantes. Vous travaillez toujours dans une branche locale. Les branches locales peuvent être configurées pour fusionner automatiquement (lors du pull) à partir d'une branche de suivi distante désignée. C'est le cas de la branche par défaut "blead" qui sera configurée pour fusionner à partir de la branche de suivi distante "origin/blead".

Vous pouvez voir les commits récents :

% git log

Et récupérer les nouveaux changements du dépôt, et mettre à jour votre dépôt local (doit être propre au préalable)

% git pull

En supposant que nous sommes sur la branche "blead" immédiatement après un pull, cette commande serait plus ou moins équivalente à :

% git fetch
% git merge origin/blead

En fait, si vous voulez mettre à jour votre dépôt local sans toucher à votre répertoire de travail, faites :

% git fetch

Et si vous voulez mettre à jour vos branches de suivi distantes pour toutes les branches distantes définies simultanément, vous pouvez faire :

% git remote update

Aucune de ces deux dernières commandes ne mettra à jour votre répertoire de travail, cependant toutes deux mettront à jour les branches de suivi distantes dans votre dépôt.

Pour créer une branche locale à partir d'une branche distante :

% git checkout -b maint-5.10 origin/maint-5.10

Pour revenir à blead :

% git checkout blead

Connaître votre statut

La commande git la plus couramment utilisée sera probablement

% git status

Cette commande produira une description de l'état actuel du dépôt, y compris les fichiers modifiés et les fichiers non suivis non ignorés, et en plus elle montrera par exemple quels fichiers ont été préparés pour le prochain commit, et généralement des informations utiles sur la façon de modifier les choses. Par exemple, ceci :

% git status
On branch blead
Your branch is ahead of 'origin/blead' by 1 commit.
Changes to be committed:
  (use "git reset HEAD <file>..." to unstage)
      modified:   pod/perlgit.pod
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git checkout -- <file>..." to discard changes in working
                                                             directory)
      modified:   pod/perlgit.pod
Untracked files:
  (use "git add <file>..." to include in what will be committed)
      deliberate.untracked

Cela montre qu'il y a eu des modifications apportées à ce document, préparées pour le commit, et qu'il y a eu d'autres modifications dans le répertoire de travail non encore préparées. Cela montre également qu'il y avait un fichier non suivi dans le répertoire de travail, et comme vous pouvez le voir, cela montre comment modifier tout cela. Cela montre également qu'il y a un commit sur la branche de travail "blead" qui n'a pas encore été poussé vers la branche distante "origin". **NOTE** : Cette sortie est également ce que vous voyez comme modèle si vous ne fournissez pas de message à "git commit".

Flux de travail des correctifs

Tout d'abord, veuillez lire perlhack pour connaître les détails sur la modification du cœur de Perl. Ce document couvre de nombreux détails sur la façon de créer un bon correctif.

Si vous avez déjà un dépôt Perl, vous devriez vous assurer que vous êtes sur la branche blead et que votre dépôt est à jour :

% git checkout blead
% git pull

Il est préférable de patcher contre la dernière version de blead, car c'est là que se déroulent les nouveaux développements pour toutes les modifications autres que les corrections de bugs critiques. Les correctifs de bugs critiques doivent être appliqués aux branches de maintenance pertinentes, ou être soumis avec une note indiquant toutes les branches où le correctif doit être appliqué.

Maintenant que nous avons tout à jour, nous devons créer une nouvelle branche temporaire pour ces modifications et y basculer :

% git checkout -b orange

qui est la forme courte de

% git branch orange
% git checkout orange

La création d'une branche thématique facilite le rebasage ou la fusion par les mainteneurs dans la branche principale blead pour un historique plus linéaire. Si vous ne travaillez pas sur une branche thématique, le mainteneur doit sélectionner manuellement vos modifications sur blead avant qu'elles ne puissent être appliquées.

Cela vous fera gronder sur perl5-porters, alors ne le faites pas. Soyez génial.

Ensuite, effectuez vos modifications. Par exemple, si Leon Brocard change son nom en Orange Brocard, nous devrions changer son nom dans le fichier AUTHORS :

% perl -pi -e 's{Leon Brocard}{Orange Brocard}' AUTHORS

Vous pouvez voir les fichiers modifiés :

% git status
On branch orange
Changes to be committed:
  (use "git reset HEAD <file>..." to unstage)
   modified:   AUTHORS

Et vous pouvez voir les modifications :

% git diff
diff --git a/AUTHORS b/AUTHORS
index 293dd70..722c93e 100644
--- a/AUTHORS
+++ b/AUTHORS
@@ -541,7 +541,7 @@    Lars Hecking              <lhecking@nmrc.ucc.ie>
 Laszlo Molnar                  <laszlo.molnar@eth.ericsson.se>
 Leif Huhn                      <leif@hale.dkstat.com>
 Len Johnson                    <lenjay@ibm.net>
-Leon Brocard                   <acme@astray.com>
+Orange Brocard                 <acme@astray.com>
 Les Peters                     <lpeters@aol.net>
 Lesley Binks                   <lesley.binks@gmail.com>
 Lincoln D. Stein               <lstein@cshl.org>

Maintenant, committez votre modification localement :

% git commit -a -m 'Renommer Leon Brocard en Orange Brocard'
Created commit 6196c1d: Rename Leon Brocard to Orange Brocard
 1 files changed, 1 insertions(+), 1 deletions(-)

L'option "-a" est utilisée pour inclure tous les fichiers que git suit et que vous avez modifiés. Si à ce moment, vous ne voulez commiter que certains des fichiers sur lesquels vous avez travaillé, vous pouvez omettre "-a" et utiliser la commande "git add FICHIER ..." avant de faire le commit. "git add --interactive" permet même de ne commiter que des portions de fichiers au lieu de toutes les modifications qu'ils contiennent.

L'option "-m" est utilisée pour spécifier le message de commit. Si vous l'omettez, git ouvrira un éditeur de texte pour que vous composiez le message interactivement. C'est utile lorsque les modifications sont plus complexes que l'exemple donné ici, et, selon l'éditeur, pour savoir que la première ligne du message de commit ne dépasse pas la limite légale de 50 caractères. Voir "Message de commit" dans perlhack pour plus d'informations sur ce qui fait un bon message de commit.

Une fois que vous avez fini d'écrire votre message de commit et quitté votre éditeur, git écrira votre modification sur disque et vous dira quelque chose comme ceci :

Created commit daf8e63: explain git status and stuff about remotes
 1 files changed, 83 insertions(+), 3 deletions(-)

A Note On Submitting Patches

When in doubt, before you do anything else, check your status and read it carefully, many questions are answered directly by the git status output.

% git status
On branch orange
Untracked files:
  (use "git add <file>..." to include in what will be committed)
      deliberate.untracked
nothing added to commit but untracked files present (use "git add" to
                                                                 track)

You can examine your last commit with:

% git show HEAD

and if you are not happy with either the description or the patch itself you can fix it up by editing the files once more and then issue:

% git commit -a --amend

Now, create a fork on GitHub to push your branch to, and add it as a remote if you haven't already, as described in the GitHub documentation at https://help.github.com/en/articles/working-with-forks:

% git remote add fork git@github.com:MyUser/perl5.git

And push the branch to your fork:

% git push -u fork orange

You should now submit a Pull Request (PR) on GitHub from the new branch to blead. For more information, see the GitHub documentation at https://help.github.com/en/articles/creating-a-pull-request-from-a-fork.

You can also send patch files to perl5-porters@perl.org <mailto:perl5-porters@perl.org> directly if the patch is not ready to be applied, but intended for discussion.

To create a patch file for all your local changes:

% git format-patch -M blead..
0001-Rename-Leon-Brocard-to-Orange-Brocard.patch

Or for a lot of changes, e.g. from a topic branch:

% git format-patch --stdout -M blead.. > topic-branch-changes.patch

If you want to delete your temporary branch, you may do so with:

% git checkout blead
% git branch -d orange
error: The branch 'orange' is not an ancestor of your current HEAD.
If you are sure you want to delete it, run 'git branch -D orange'.
% git branch -D orange
Deleted branch orange.

A note on derived files

Be aware that many files in the distribution are derivative--avoid patching them, because git won't see the changes to them, and the build process will overwrite them. Patch the originals instead. Most utilities (like perldoc) are in this category, i.e. patch utils/perldoc.PL rather than utils/perldoc. Similarly, don't create patches for files under $src_root/ext from their copies found in $install_root/lib. If you are unsure about the proper location of a file that may have gotten copied while building the source distribution, consult the MANIFEST.

Cleaning a working directory

The command "git clean" can with varying arguments be used as a replacement for "make clean".

To reset your working directory to a pristine condition you can do:

% git clean -dxf

However, be aware this will delete ALL untracked content. You can use

% git clean -Xf

to remove all ignored untracked files, such as build and test byproduct, but leave any manually created files alone.

If you only want to cancel some uncommitted edits, you can use "git checkout" and give it a list of files to be reverted, or "git checkout -f" to revert them all.

If you want to cancel one or several commits, you can use "git reset".

Bisecting

"git" provides a built-in way to determine which commit should be blamed for introducing a given bug. "git bisect" performs a binary search of history to locate the first failing commit. It is fast, powerful and flexible, but requires some setup and to automate the process an auxiliary shell script is needed.

The core provides a wrapper program, Porting/bisect.pl, which attempts to simplify as much as possible, making bisecting as simple as running a Perl one-liner. For example, if you want to know when this became an error:

perl -e 'my $x := 2'

you simply run this:

.../Porting/bisect.pl -e 'my $x := 2;'

Using Porting/bisect.pl, with one command (and no other files) it's easy to find out

  • Which commit caused this example code to break?
  • Which commit caused this example code to start working?
  • Which commit added the first file to match this regex?
  • Which commit removed the last file to match this regex?

usually without needing to know which versions of perl to use as start and end revisions, as Porting/bisect.pl automatically searches to find the earliest stable version for which the test case passes. Run "Porting/bisect.pl --help" for the full documentation, including how to set the "Configure" and build time options.

If you require more flexibility than Porting/bisect.pl has to offer, you'll need to run "git bisect" yourself. It's most useful to use "git bisect run" to automate the building and testing of perl revisions. For this you'll need a shell script for "git" to call to test a particular revision. An example script is Porting/bisect-example.sh, which you should copy outside of the repository, as the bisect process will reset the state to a clean checkout as it runs. The instructions below assume that you copied it as ~/run and then edited it as appropriate.

You first enter in bisect mode with:

% git bisect start

For example, if the bug is present on "HEAD" but wasn't in 5.10.0, "git" will learn about this when you enter:

% git bisect bad
% git bisect good perl-5.10.0
Bisecting: 853 revisions left to test after this

This results in checking out the median commit between "HEAD" and "perl-5.10.0". You can then run the bisecting process with:

% git bisect run ~/run

When the first bad commit is isolated, "git bisect" will tell you so:

ca4cfd28534303b82a216cfe83a1c80cbc3b9dc5 is first bad commit
commit ca4cfd28534303b82a216cfe83a1c80cbc3b9dc5
Author: Dave Mitchell <davem@fdisolutions.com>
Date:   Sat Feb 9 14:56:23 2008 +0000
    [perl #49472] Attributes + Unknown Error
    ...
bisect run success

You can peek into the bisecting process with "git bisect log" and "git bisect visualize". "git bisect reset" will get you out of bisect mode.

Please note that the first "good" state must be an ancestor of the first "bad" state. If you want to search for the commit that solved some bug, you have to negate your test case (i.e. exit with 1 if OK and 0 if not) and still mark the lower bound as "good" and the upper as "bad". The "first bad commit" has then to be understood as the "first commit where the bug is solved".

"git help bisect" has much more information on how you can tweak your binary searches.

Following bisection you may wish to configure, build and test perl at commits identified by the bisection process. Sometimes, particularly with older perls, "make" may fail during this process. In this case you may be able to patch the source code at the older commit point. To do so, please follow the suggestions provided in "Building perl at older commits" in perlhack.

Topic branches and rewriting history

Individual committers should create topic branches under yourname/some_descriptive_name:

% branch="$yourname/$some_descriptive_name"
% git checkout -b $branch
... do local edits, commits etc ...
% git push origin -u $branch

Should you be stuck with an ancient version of git (prior to 1.7), then "git push" will not have the "-u" switch, and you have to replace the last step with the following sequence:

% git push origin $branch:refs/heads/$branch
% git config branch.$branch.remote origin
% git config branch.$branch.merge refs/heads/$branch

If you want to make changes to someone else's topic branch, you should check with its creator before making any change to it.

You might sometimes find that the original author has edited the branch's history. There are lots of good reasons for this. Sometimes, an author might simply be rebasing the branch onto a newer source point. Sometimes, an author might have found an error in an early commit which they wanted to fix before merging the branch to blead.

Currently the master repository is configured to forbid non-fast-forward merges. This means that the branches within can not be rebased and pushed as a single step.

The only way you will ever be allowed to rebase or modify the history of a pushed branch is to delete it and push it as a new branch under the same name. Please think carefully about doing this. It may be better to sequentially rename your branches so that it is easier for others working with you to cherry-pick their local changes onto the new version. (XXX: needs explanation).

If you want to rebase a personal topic branch, you will have to delete your existing topic branch and push as a new version of it. You can do this via the following formula (see the explanation about "refspec"'s in the git push documentation for details) after you have rebased your branch:

# first rebase
% git checkout $user/$topic
% git fetch
% git rebase origin/blead
# the
n « supprimer-et-pousser » % git push origin :$user/$topic % git push origin $user/$topic

NOTE: il est interdit au niveau du dépôt de supprimer l'une des branches « primaires ». Il s'agit de toute branche correspondant à « m!^(blead|maint|perl)! ». Toute tentative de le faire entraînera une erreur git telle que :

% git push origin :blead
*** Il est interdit de supprimer les branches blead/maint dans ce dépôt
error: hooks/update exited with error code 1
error: hook declined to update refs/heads/blead
To ssh://perl5.git.perl.org/perl
 ! [remote rejected] blead (hook declined)
 error: failed to push some refs to 'ssh://perl5.git.perl.org/perl'

Par politique, nous ne modifions pas l'historique des branches blead et maint-*. Si une faute de frappe (ou pire) s'est glissée dans un commit sur blead ou maint-*, nous la corrigerons dans un autre commit. Les seuls types de mises à jour autorisées sur ces branches sont les « fast-forwards », où tout l'historique est préservé.

Les tags annotés dans le dépôt canonique perl.git ne seront jamais supprimés ou modifiés. Réfléchissez bien avant de pousser un tag local vers perl.git. (La poussée de tags simples n'est pas autorisée.)

Greffons

L'historique de perl contient une erreur qui n'a pas été détectée lors de la conversion : une fusion a été enregistrée dans l'historique entre blead et maint-5.10 alors qu'aucune fusion n'a réellement eu lieu. En raison de la nature de git, il est désormais impossible de corriger cela dans le dépôt public. Vous pouvez supprimer cette mauvaise fusion localement en ajoutant la ligne suivante à votre fichier «.git/info/grafts» :

296f12bbbbaa06de9be9d09d3dcf8f4528898a49 434946e0cb7a32589ed92d18008aaa1d88515930

Il est particulièrement important d'avoir cette ligne de greffon si une opération de bisecting est effectuée dans la zone de la « fusion » en question.

ACCÈS EN ÉCRITURE AU DÉPÔT GIT

Une fois que vous avez l'accès en écriture, vous devrez modifier l'URL de la télécommande d'origine pour permettre la poussée. Modifiez .git/config avec la commande git-config(1) :

% git config remote.origin.url git@github.com:Perl/perl5.git

Vous pouvez également définir votre nom d'utilisateur et votre adresse e-mail. La plupart des gens le font une seule fois globalement dans leur ~/.gitconfig en faisant quelque chose comme :

% git config --global user.name "Ævar Arnfjörð Bjarmason"
% git config --global user.email avarab@gmail.com

Cependant, si vous souhaitez remplacer cela uniquement pour perl, exécutez quelque chose comme ce qui suit dans perl :

% git config user.email avar@cpan.org

Il est également possible de conserver « origin » comme télécommande git et d'en ajouter une nouvelle pour l'accès ssh :

% git remote add camel git@github.com:Perl/perl5.git

Cela vous permet de mettre à jour votre dépôt local en tirant de « origin », ce qui est plus rapide et ne nécessite pas d'authentification, et de repousser vos modifications avec la télécommande « camel » :

% git fetch camel
% git push camel

La commande « fetch » met uniquement à jour les références « camel », car les objets eux-mêmes devraient avoir été récupérés lors du tirage de « origin ».

Travailler avec les demandes de tirage GitHub

Les demandes de tirage proviennent généralement de l'extérieur du dépôt « Perl/perl.git », donc si vous souhaitez les tester ou travailler avec localement, un simple « git fetch » du dépôt « Perl/perl5.git » ne les récupérera pas.

Cependant, GitHub fournit un mécanisme pour récupérer une demande de tirage vers une branche locale. Elles sont disponibles sur les télécommandes GitHub sous « pull/ », vous pouvez donc utiliser « git fetch pull/PRID/head:nomlocal« » pour créer une copie locale. Par exemple, pour récupérer la demande de tirage 9999 vers la branche locale « nom-branche-locale », exécutez :

git fetch origin pull/9999/head:nom-branche-locale

et ensuite :

git checkout nom-branche-locale

Note : cette branche n'est pas rebasée sur « blead », donc au lieu du checkout ci-dessus, vous pourriez vouloir :

git rebase origin/blead nom-branche-locale

ce qui rebase « nom-branche-locale » sur « blead » et la sélectionne.

Alternativement, vous pouvez configurer la télécommande pour récupérer toutes les demandes de tirage en tant que branches de suivi à distance. Pour ce faire, modifiez la télécommande dans .git/config, par exemple si votre télécommande GitHub est « origin », vous aurez :

[remote "origin"]
        url = git@github.com:/Perl/perl5.git
        fetch = +refs/heads/*:refs/remotes/origin/*

Ajoutez une ligne pour mapper les branches de demande de tirage distantes aux branches de suivi à distance :

[remote "origin"]
        url = git@github.com:/Perl/perl5.git
        fetch = +refs/heads/*:refs/remotes/origin/*
        fetch = +refs/pull/*/head:refs/remotes/origin/pull/*

et ensuite effectuez un fetch comme d'habitude :

git fetch origin

Cela créera une branche de suivi à distance pour chaque demande de tirage, y compris les demandes fermées.

Pour supprimer ces branches de suivi à distance, supprimez la ligne ajoutée ci-dessus et élaguez :

git fetch -p origin # ou git remote prune origin

Accepter un patch

Si vous avez reçu un fichier patch généré à l'aide de la section ci-dessus, vous devriez essayer le patch.

D'abord, nous devons créer une nouvelle branche temporaire pour ces modifications et y basculer :

% git checkout -b experimental

Les patches formatés par « git format-patch » sont appliqués avec « git am » :

% git am 0001-Rename-Leon-Brocard-to-Orange-Brocard.patch
Applying Rename Leon Brocard to Orange Brocard

Notez que certains systèmes de messagerie UNIX peuvent interférer avec les pièces jointes texte contenant « From ». Ceci les corrigera :

% perl -pi -e's/^>From /From /' \
                       0001-Rename-Leon-Brocard-to-Orange-Brocard.patch

Si un diff brut est fourni, il est également possible d'utiliser ce processus en deux étapes :

% git apply bugfix.diff
% git commit -a -m "Quelque correction" \
                           --author="Ce Mec <ce.mec@internets.com>"

Maintenant, nous pouvons inspecter le changement :

% git show HEAD

Si vous êtes un committer pour Perl et que vous pensez que le patch est bon, vous pouvez alors le fusionner dans blead puis le pousser vers le dépôt principal :

% git checkout blead
% git merge experimental
% git push origin blead

Si vous souhaitez supprimer votre branche temporaire, vous pouvez le faire avec :

% git checkout blead
% git branch -d experimental
error: The branch 'experimental' is not an ancestor of your current
HEAD.  If you are sure you want to delete it, run 'git branch -D
experimental'.
% git branch -D experimental
Deleted branch experimental.

Commiter sur blead

La branche « blead » deviendra la prochaine version de production de Perl.

Avant de pousser quelque modification locale vers blead, il est incroyablement important de faire quelques choses, de peur que d'autres committeurs ne viennent après vous avec des torches et des fourches :

  • Assurez-vous d'avoir un bon message de commit. Voir « Message de commit » dans perlhack pour plus de détails.
  • Exécutez la suite de tests. Vous pourriez ne pas penser qu'une seule correction de faute de frappe casserait un fichier de test. Vous auriez tort. Voici un exemple où ne pas exécuter la suite a causé des problèmes. Un patch a été soumis qui ajoutait quelques tests à un .t existant. Il ne pouvait affecter quoi que ce soit d'autre, donc pas besoin de tester au-delà du seul .t affecté, n'est-ce pas ? Mais, l'adresse e-mail du soumetteur avait changé depuis la dernière de ses soumissions, et cela a provoqué l'échec d'autres tests. L'exécution de la cible de test donnée dans le point suivant aurait capturé ce problème.
  • Si vous n'exécutez pas la suite de tests complète, exécutez au moins « make test_porting ». Cela effectuera des vérifications de base. Pour voir quelles vérifications de base, jetez un œil dans t/porting.
  • Si vous apportez des modifications qui affectent miniperl ou les routines de base qui ont des chemins de code différents pour miniperl, assurez-vous d'exécuter « make minitest ». Cela capturera des problèmes que même la suite de tests complète ne capturera pas car elle exécute un sous-ensemble de tests sous miniperl plutôt que sous perl.

Concernant la fusion et le rebasage

Les commits simples, uniques poussés vers la branche 'blead' devraient être des commits simples qui s'appliquent proprement. En d'autres termes, vous devriez vous assurer que votre travail est commité par rapport à la position actuelle de blead, de sorte que vous puissiez repousser vers le dépôt maître sans fusion.

Parfois, blead avancera pendant que vous construisez ou testez vos modifications. Lorsque cela se produit, votre poussée sera rejetée avec un message comme celui-ci :

To ssh://perl5.git.perl.org/perl.git
 ! [rejected]        blead -> blead (non-fast-forward)
error: failed to push some refs to 'ssh://perl5.git.perl.org/perl.git'
To prevent you from losing history, non-fast-forward updates were

Lorsque cela se produit, vous pouvez simplement rebaser à nouveau votre travail

st la nouvelle position de blead, comme ceci (en supposant que votre dépôt distant pour le dépôt maître est "p5p") :

% git fetch p5p
% git rebase p5p/blead

Vous verrez vos commits être réappliqués, et vous pourrez alors pousser en toute sécurité. Plus d'informations sur le rebasage peuvent être trouvées dans la documentation de la commande git-rebase(1).

Pour des ensembles de commits plus importants qui n'ont de sens que collectivement, ou qui bénéficieraient d'un résumé de l'objectif de l'ensemble, vous devriez utiliser un commit de fusion. Vous devriez effectuer votre travail sur une branche de sujet, que vous devriez régulièrement rebaser contre blead pour vous assurer que votre code n'est pas cassé par les changements de blead. Lorsque vous avez terminé votre travail, veuillez effectuer un rebasage final et tester. L'historique linéaire est quelque chose qui se perd à chaque commit sur blead, mais un rebasage final rend l'historique à nouveau linéaire, ce qui permet aux futurs mainteneurs de voir plus facilement ce qui s'est passé. Rebasez comme suit (en supposant que votre travail était sur la branche "committer/somework") :

% git checkout committer/somework
% git rebase blead

Ensuite, vous pouvez le fusionner dans master comme ceci :

% git checkout blead
% git merge --no-ff --no-commit committer/somework
% git commit -a

Les options ci-dessus méritent une explication. "--no-ff" indique que même si tout votre travail peut être appliqué linéairement contre blead, un commit de fusion doit toujours être préparé. Cela garantit que tout votre travail sera présenté comme une branche latérale, avec tous ses commits fusionnés dans le courant principal de blead par le commit de fusion.

"--no-commit" signifie que le commit de fusion sera *préparé* mais pas *commité*. Le commit est ensuite réellement effectué lorsque vous exécutez la commande suivante, qui ouvrira votre éditeur pour décrire le commit. Sans "--no-commit", le commit serait créé avec presque aucun message utile, ce qui diminuerait considérablement la valeur du commit de fusion en tant qu'espace réservé pour la description du travail.

Lors de la description du commit de fusion, expliquez l'objectif de la branche, et gardez à l'esprit que cette description sera probablement utilisée par l'ingénieur de publication éventuel lors de la révision du prochain document perldelta.

Si le *push* subséquent échoue, vous devez être prudent quant à la manière dont vous *rebasez*. Si vous utilisez

% git rebase p5p/blead

ou

% git pull --rebase

alors votre commit de fusion soigneusement créé sera perdu ! Pour éviter cela, vous pouvez utiliser :

% git fetch p5p
% git rebase --rebase-merges p5p/blead

Cela recréera votre commit de fusion.

(Si vous êtes bloqué avec une ancienne version de git (antérieure à 2.18), alors "git rebase" n'aura pas l'option "--rebase-merges", à la place vous devrez utiliser l'option "--preserve-merges".)

Commits aux versions de maintenance

Les versions de maintenance ne doivent être modifiées que pour ajouter des corrections de bugs critiques, voir perlpolicy.

Pour commiter une version de maintenance de perl, vous devez créer une branche de suivi locale :

% git checkout --track -b maint-5.005 origin/maint-5.005

Cela crée une branche locale nommée "maint-5.005", qui suit la branche distante "origin/maint-5.005". Ensuite, vous pouvez tirer, commiter, fusionner et pousser comme auparavant.

Vous pouvez également sélectionner des commits de blead et d'une autre branche, en utilisant la commande "git cherry-pick". Il est recommandé d'utiliser l'option -x de "git cherry-pick" afin d'enregistrer le SHA1 du commit d'origine dans le nouveau message de commit.

Avant de pousser une modification vers une version de maintenance, assurez-vous d'avoir satisfait les étapes décrites dans "Committing to blead" ci-dessus.

Utilisation d'une branche smoke-me pour tester les modifications

Parfois, une modification affecte des chemins de code que vous ne pouvez pas tester sur les systèmes d'exploitation qui vous sont directement disponibles et il serait judicieux de faire tester la modification par des utilisateurs sur d'autres systèmes d'exploitation avant de la commiter dans blead.

Heureusement, il existe un moyen de faire tester votre modification sur différents systèmes d'exploitation : poussez-la vers une branche "smoke-me" et attendez que certains testeurs automatiques rapportent les résultats de leurs systèmes d'exploitation. Une branche "smoke-me" est identifiée par le nom de la branche : spécifiquement, comme vu sur github.com, il doit s'agir d'une branche locale dont le premier composant du nom est précisément "smoke-me".

La procédure pour ce faire est approximativement la suivante (en utilisant l'exemple de la branche smoke-me de tonyc appelée win32stat) :

Tout d'abord, créez une branche locale et basculez dessus :

% git checkout -b win32stat

Effectuez quelques modifications, compilez perl et testez vos modifications, puis commitez-les sur votre branche locale. Ensuite, poussez votre branche locale vers une branche smoke-me distante :

% git push origin win32stat:smoke-me/tonyc/win32stat

Maintenant, vous pouvez revenir à blead localement :

% git checkout blead

et continuer à travailler sur d'autres choses pendant que vous attendez un jour ou deux, en gardant un œil sur les résultats rapportés pour votre branche "smoke-me" à l'adresse https://perl.develop-help.com/?b=smoke-me/tonyc/win32state.

Si tout va bien, mettez à jour votre branche blead :

% git pull

puis retournez sur votre branche smoke-me et rebasez-la sur blead :

% git rebase blead win32stat

Revenez ensuite sur blead et fusionnez votre branche smoke-me dedans :

% git checkout blead
% git merge win32stat

Comme décrit précédemment, s'il y a de nombreuses modifications dans votre branche smoke-me, vous devriez préparer un commit de fusion pour donner un aperçu de ces modifications en utilisant la commande suivante au lieu de la dernière commande ci-dessus :

% git merge win32stat --no-ff --no-commit

Vous devriez maintenant compiler perl et tester vos modifications (fusionnées) une dernière fois (idéalement, exécutez toute la suite de tests, mais à défaut, exécutez au moins les tests *t/porting/*.t*) avant de pousser vos modifications comme d'habitude :

% git push origin blead

Enfin, vous devriez ensuite supprimer la branche smoke-me distante :

% git push origin :smoke-me/tonyc/win32stat

(ce qui risque de produire un avertissement comme celui-ci, qui peut être ignoré :

remote: fatal: ambiguous argument
                                 'refs/heads/smoke-me/tonyc/win32stat':
unknown revision or path not in the working tree.
remote: Use '--' to separate paths from revisions

) et ensuite supprimer votre branche locale :

% git branch -d win32stat
