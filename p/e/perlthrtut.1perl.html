PERLTHRTUT(1perl) Guide de référence des programmeurs Perl PERLTHRTUT(1perl)

NOM

perlthrtut - Tutoriel sur les threads en Perl

DESCRIPTION

Ce tutoriel décrit l'utilisation des threads de l'interpréteur Perl (parfois appelés ithreads). Dans ce modèle, chaque thread s'exécute dans son propre interpréteur Perl, et tout partage de données entre les threads doit être explicite. L'interface utilisateur pour les ithreads utilise la classe threads.

NOTE : Il existait une ancienne variante de threading Perl appelée modèle 5.005 qui utilisait la classe Thread. Ce vieux modèle était connu pour avoir des problèmes, a été déprécié et a été supprimé dans la version 5.10. Il est fortement recommandé de migrer tout code existant basé sur les threads 5.005 vers le nouveau modèle dès que possible.

Vous pouvez voir quel modèle de threading (ou aucun) est présent en exécutant "perl -V" et en regardant la section "Platform". Si vous avez "useithreads=define", vous avez les ithreads ; si vous avez "use5005threads=define", vous avez les threads 5.005. Si vous n'avez aucun des deux, vous n'avez pas de support de threading intégré. Si vous avez les deux, vous avez un problème.

Plus récemment, les termes "ithreads" et "threads" sont synonymes et utilisés de manière interchangeable. La meilleure pratique est d'utiliser "useithreads" si votre code dépend de quelque chose de spécifique à cette implémentation, et d'utiliser "usethreads" si ce n'est pas le cas. De cette façon, dans le cas très improbable où un nouveau modèle de threading apparaîtrait, votre code serait plus protégé contre les modifications nécessaires. (Les symboles correspondants au niveau du langage C sont "USE_ITHREADS" et "USE_THREADS" ; ils sont actuellement totalement synonymes, mais rien ne garantit absolument qu'ils le resteront.)

Les modules threads et threads::shared sont inclus dans la distribution Perl principale. De plus, ils sont maintenus en tant que modules distincts sur CPAN, vous pouvez donc vérifier là-bas pour toute mise à jour.

Qu'est-ce qu'un thread en fait?

Un thread est un flux de contrôle à travers un programme, avec un point d'exécution unique.

Cela ressemble beaucoup à un processus, n'est-ce pas? Eh bien, ça devrait. Les threads sont l'une des composantes d'un processus. Chaque processus a au moins un thread et, jusqu'à présent, chaque processus exécutant Perl n'avait qu'un seul thread. Avec la version 5.8, cependant, vous pouvez créer des threads supplémentaires. Nous allons vous montrer comment, quand et pourquoi.

Modèles de programmes threadés

Il existe trois modèles principaux pour structurer un programme threadé. Le modèle que vous choisissez dépend de ce que vous voulez que votre programme fasse. Pour de nombreux programmes threadés non triviaux, vous devrez choisir différents modèles pour différentes parties de votre programme.

Boss/Worker

Le modèle boss/worker a généralement un thread boss et un ou plusieurs threads worker. Le thread boss collecte ou génère les tâches qui doivent être effectuées, puis distribue ces tâches au thread worker approprié.

Ce modèle est courant dans les programmes d'interface graphique et les serveurs, où un thread principal attend un événement, puis transmet cet événement aux threads workers appropriés pour traitement. Une fois l'événement transmis, le thread boss retourne à l'attente d'un nouvel événement.

Le thread boss effectue relativement peu de travail. Bien que les tâches ne soient pas nécessairement effectuées plus rapidement qu'avec toute autre méthode, ce modèle tend à offrir les meilleurs temps de réponse pour l'utilisateur.

Équipe de travail

Dans le modèle de l'équipe de travail, plusieurs threads sont créés qui effectuent essentiellement la même chose sur différentes données. Il reflète étroitement le traitement parallèle classique et les processeurs vectoriels, où un grand nombre de processeurs effectuent exactement la même chose sur de nombreuses données.

Ce modèle est particulièrement utile si le système exécutant le programme distribue plusieurs threads sur différents processeurs. Il peut également être utile dans les moteurs de lancer de rayons ou de rendu, où les threads individuels peuvent transmettre des résultats intermédiaires pour donner un retour visuel à l'utilisateur.

Pipeline

Le modèle pipeline divise une tâche en une série d'étapes et transmet les résultats d'une étape au thread traitant l'étape suivante. Chaque thread effectue une opération sur chaque élément de données et transmet les résultats au thread suivant dans la chaîne.

Ce modèle est le plus pertinent si vous disposez de plusieurs processeurs, afin que deux threads ou plus s'exécutent en parallèle, bien qu'il puisse souvent avoir du sens dans d'autres contextes également. Il tend à garder les tâches individuelles petites et simples, et permet à certaines parties du pipeline de bloquer (sur des I/O ou des appels système, par exemple) pendant que d'autres parties continuent. Si vous exécutez différentes parties du pipeline sur différents processeurs, vous pouvez également tirer parti des caches de chaque processeur.

Ce modèle est également utile pour une forme de programmation récursive où, au lieu d'avoir une sous-routine qui s'appelle elle-même, elle crée plutôt un autre thread. Les générateurs de nombres premiers et de Fibonacci correspondent bien à cette forme de modèle pipeline. (Une version d'un générateur de nombres premiers est présentée plus loin.)

Quel genre de threads sont les threads Perl?

Si vous avez de l'expérience avec d'autres implémentations de threads, vous pourriez trouver que les choses ne sont pas tout à fait ce que vous attendez. Il est très important de se rappeler lorsque l'on traite des threads Perl que les threads Perl ne sont pas des threads X pour toutes les valeurs de X. Ce ne sont pas des threads POSIX, ni des DecThreads, ni des threads Green de Java, ni des threads Win32. Il y a des similitudes, et les concepts généraux sont les mêmes, mais si vous commencez à chercher des détails d'implémentation, vous serez soit déçu, soit confus. Probablement les deux.

Cela ne veut pas dire que les threads Perl sont complètement différents de tout ce qui a existé auparavant. Ils ne le sont pas. Le modèle de threading de Perl doit beaucoup à d'autres modèles de threads, en particulier POSIX. Tout comme Perl n'est pas du C, les threads Perl ne sont pas des threads POSIX. Donc, si vous vous retrouvez à chercher des mutex, ou des priorités de thread, il est temps de prendre du recul et de réfléchir à ce que vous voulez faire et comment Perl peut le faire.

Cependant, il est important de se rappeler que les threads Perl ne peuvent pas faire des choses par magie à moins que les threads de votre système d'exploitation ne le permettent. Donc, si votre système bloque l'ensemble du processus sur sleep(), Perl le fera généralement aussi.

Les threads Perl sont différents.

Modules thread-safe

L'ajout de threads a considérablement modifié les internes de Perl. Il y a des implications pour les personnes qui écrivent des modules avec du code XS ou des bibliothèques externes. Cependant, comme les données Perl ne sont pas partagées entre les threads par défaut, les modules Perl ont une forte probabilité d'être thread-safe ou peuvent être rendus thread-safe facilement. Les modules qui ne sont pas marqués comme thread-safe doivent être testés ou leur code revu avant d'être utilisés dans du code de production.

Tous les modules que vous pourriez utiliser ne sont pas thread-safe, et vous devriez toujours supposer qu'un module est dangereux à moins que sa documentation n'indique le contraire. Cela inclut les modules distribués dans le cadre du noyau. Les threads sont une fonctionnalité relativement nouvelle, et même certains modules standard ne sont pas thread-safe.

Même si un module est thread-safe, cela ne signifie pas que le module est optimisé pour fonctionner correctement avec les threads. Un module pourrait potentiellement être réécrit pour utiliser les nouvelles fonctionnalités de Perl threadé afin d'augmenter les performances dans un environnement threadé.

Si vous utilisez un module qui n'est pas thread-safe pour une raison quelconque, vous pouvez vous protéger en l'utilisant à partir d'un seul thread, et un seul à la fois. Si vous avez besoin que plusieurs threads accèdent à un tel module, vous pouvez utiliser des sémaphores et beaucoup de discipline de programmation pour contrôler l'accès à celui-ci. Les sémaphores sont abordés dans "Sémaphores de base".

Voir aussi "Thread-Safety des bibliothèques système".

Bases des threads

Le module threads fournit les fonctions de base dont vous avez besoin pour écrire des programmes threadés. Dans les sections suivantes, nous aborderons les bases,

montrant ce qu'il faut faire pour créer un programme multithreadé. Ensuite, nous examinerons certaines des fonctionnalités du module threads qui facilitent la programmation multithreadée.

Support de base des threads

Le support des threads est une option de compilation de Perl. C'est quelque chose qui est activé ou désactivé lors de la compilation de Perl sur votre site, plutôt que lors de la compilation de vos programmes. Si votre Perl n'a pas été compilé avec le support des threads activé, toute tentative d'utilisation de threads échouera.

Vos programmes peuvent utiliser le module Config pour vérifier si les threads sont activés. Si votre programme ne peut pas s'exécuter sans eux, vous pouvez écrire quelque chose comme ceci :

use Config;
$Config{useithreads} or
    die('Recompilez Perl avec le support des threads pour exécuter ce programme.');

Un programme potentiellement multithreadé utilisant un module potentiellement multithreadé pourrait contenir du code comme celui-ci :

use Config;
use MyMod;
BEGIN {
    if ($Config{useithreads}) {
        # Nous avons des threads
        require MyMod_threaded;
        MyMod_threaded->import();
    } else {
        require MyMod_unthreaded;
        MyMod_unthreaded->import();
    }
}

Comme le code qui s'exécute avec et sans threads est généralement assez désordonné, il est préférable d'isoler le code spécifique aux threads dans son propre module. Dans notre exemple ci-dessus, c'est ce que fait "MyMod_threaded", et il n'est importé que si nous exécutons sur un Perl multithreadé.

Une note sur les exemples

Dans une situation réelle, il faut veiller à ce que tous les threads aient fini leur exécution avant que le programme ne se termine. Ce soin n'a pas été pris dans ces exemples dans un souci de simplicité. L'exécution de ces exemples *tels quels* produira des messages d'erreur, généralement causés par le fait qu'il reste des threads en cours d'exécution lorsque le programme se termine. Vous ne devriez pas être alarmé par cela.

Création de threads

Le module threads fournit les outils dont vous avez besoin pour créer de nouveaux threads. Comme pour tout autre module, vous devez indiquer à Perl que vous souhaitez l'utiliser ; "use threads;" importe toutes les pièces dont vous avez besoin pour créer des threads de base.

La manière la plus simple et la plus directe de créer un thread est d'utiliser create() :

use threads;
my $thr = threads->create(\&sub1);
sub sub1 {
    print("Dans le thread\n");
}

La méthode create() prend une référence à une sous-routine et crée un nouveau thread qui commence à s'exécuter dans la sous-routine référencée. Le contrôle passe ensuite à la fois à la sous-routine et à l'appelant.

Si nécessaire, votre programme peut passer des paramètres à la sous-routine lors du démarrage du thread. Il suffit d'inclure la liste des paramètres dans l'appel "threads->create()", comme ceci :

use threads;
my $Param3 = 'foo';
my $thr1 = threads->create(\&sub1, 'Param 1', 'Param 2', $Param3);
my @ParamList = (42, 'Hello', 3.14);
my $thr2 = threads->create(\&sub1, @ParamList);
my $thr3 = threads->create(\&sub1, qw(Param1 Param2 Param3));
sub sub1 {
    my @InboundParameters = @_;
    print("Dans le thread\n");
    print('Paramètres reçus >', join('<>',@InboundParameters), "<\n");
}

Le dernier exemple illustre une autre caractéristique des threads. Vous pouvez lancer plusieurs threads en utilisant la même sous-routine. Chaque thread exécute la même sous-routine, mais dans un thread séparé avec un environnement séparé et potentiellement des arguments séparés.

new() est un synonyme de create().

Attendre la fin d'un thread

Puisque les threads sont aussi des sous-routines, ils peuvent retourner des valeurs. Pour attendre qu'un thread se termine et récupérer les valeurs qu'il pourrait retourner, vous pouvez utiliser la méthode join() :

use threads;
my ($thr) = threads->create(\&sub1);
my @ReturnData = $thr->join();
print('Le thread a retourné ', join(', ', @ReturnData), "\n");
sub sub1 { return ('Cinquante-six', 'foo', 2); }

Dans l'exemple ci-dessus, la méthode join() retourne dès que le thread se termine. En plus d'attendre qu'un thread se termine et de rassembler les valeurs que le thread pourrait avoir retournées, join() effectue également tout nettoyage du système d'exploitation nécessaire pour le thread. Ce nettoyage peut être important, en particulier pour les programmes de longue durée qui lancent de nombreux threads. Si vous ne voulez pas des valeurs de retour et que vous ne voulez pas attendre la fin du thread, vous devriez appeler la méthode detach() à la place, comme décrit ci-dessous.

NOTE : Dans l'exemple ci-dessus, le thread retourne une liste, ce qui nécessite que l'appel de création de thread soit fait dans un contexte de liste (c'est-à-dire "my ($thr)"). Voir "$thr->join()" dans threads et "CONTEXTE DES THREADS" dans threads pour plus de détails sur le contexte des threads et les valeurs de retour.

Ignorer un thread

join() fait trois choses : il attend qu'un thread se termine, le nettoie et retourne les données que le thread a pu produire. Mais que se passe-t-il si vous ne vous intéressez pas aux valeurs de retour du thread et que vous ne vous souciez pas vraiment de savoir quand le thread se termine ? Tout ce que vous voulez, c'est que le thread soit nettoyé une fois qu'il est terminé.

Dans ce cas, vous utilisez la méthode detach(). Une fois qu'un thread est détaché, il s'exécute jusqu'à ce qu'il soit terminé ; ensuite, Perl le nettoie automatiquement.

use threads;
my $thr = threads->create(\&sub1);   # Lance le thread
$thr->detach();   # Désormais, nous ne nous en soucions plus officiellement
sleep(15);        # Laisse le thread s'exécuter pendant un certain temps
sub sub1 {
    my $count = 0;
    while (1) {
        $count++;
        print("\$count est $count\n");
        sleep(1);
    }
}

Une fois qu'un thread est détaché, il ne peut pas être joint, et toutes les données de retour qu'il aurait pu produire (s'il était terminé et en attente d'un join) sont perdues.

detach() peut également être appelé en tant que méthode de classe pour permettre à un thread de se détacher lui-même :

use threads;
my $thr = threads->create(\&sub1);
sub sub1 {
    threads->detach();
    # Faire plus de travail
}

Terminaison de processus et de threads

Avec les threads, il faut veiller à leur donner une chance de s'exécuter jusqu'à leur complétion, en supposant que c'est ce que vous voulez.

Une action qui termine un processus terminera *tous* les threads en cours d'exécution. die() et exit() ont cette propriété, et Perl effectue une sortie lorsque le thread principal se termine, peut-être implicitement en sortant du code, même si ce n'est pas ce que vous voulez.

À titre d'exemple de ce cas, ce code affiche le message "Perl s'est terminé avec des threads actifs : 2 en cours d'exécution et non joints" :

use threads;
my $thr1 = threads->new(\&thrsub, "test1");
my $thr2 = threads->new(\&thrsub, "test2");
sub thrsub {
   my ($message) = @_;
   sleep 1;
   print "thread $message\n";
}

Mais lorsque les lignes suivantes sont ajoutées à la fin :

$thr1->join();
$thr2->join();

il affiche deux lignes de sortie, un résultat peut-être plus utile.

Threads et données

Maintenant que nous avons couvert les bases des threads, passons à notre prochain sujet : les données. Le multithreading introduit quelques complications dans l'accès aux données que les programmes non multithreadés n'ont jamais à considérer.

Données partagées et non partagées

La plus grande différence entre les *ithreads* de Perl et le vieux threading style 5.005, ou pour autant, pour la plupart des autres systèmes de threading existants, est qu'en règle générale, aucune donnée n'est partagée. Lorsqu'un nouveau thread Perl est créé, toutes les données associées au thread actuel sont copiées dans le nouveau thread, et sont ensuite privées à ce nouveau thread ! C'est similaire à ce qui se passe lorsqu'un processus Unix effectue un fork, sauf que dans ce cas, les données sont simplement copiées dans une partie différente de la mémoire au sein du même processus plutôt qu'un véritable fork.

Pour utiliser le multithreading, cependant, on souhaite généralement que les threads partagent au moins certaines données entre eux. Ceci est fait avec le module threads::shared et l'attribut ":shared" :

use threads;
use threads::shared;
my $foo :shared = 1;
my $bar = 1;
threads->create(sub { $foo++; $bar++; })->join();
print("$foo\n");  # Affiche 2 car $foo est partagé
print("$bar\n");  # Affiche 1 car $bar n'est pas partagé

Dans le cas d'un tableau partagé, tous les éléments du tableau sont partagés, et pour une hash partagée, toutes les clés et valeurs sont partagées. Cela impose des restrictions sur ce qui peut être assigné aux éléments de tableaux et de hash partagés : seules des valeurs simples ou des références à des variables partagées sont autorisées - ceci afin qu'une variable privée ne devienne pas accidentellement partagée. Une mauvaise assignation fera mourir le thread. Par exemple :

use threads;
use threads::shared;
my $var          = 1;
my $svar :shared = 2;
my %hash :shared;
... créer quelques threads ...
$hash{a} = 1;       # Tous les threads voient exists($hash{a})
                    # et $hash{a} == 1
$hash{a} = $var;    # ok - copie par valeur : même effet que précédemment
$hash{a} = $svar;   # ok - copie par valeur : même effet que précédemment
$hash{a} = \$svar;  # ok - une référence à une variable partagée
$hash{a} = \$var;   # Cela échouera
delete($hash{a});   # ok - tous les threads verront !exists($hash{a})

Notez qu'une variable partagée garantit que si deux threads ou plus essaient de la modifier en même temps, l'état interne de la variable ne sera pas corrompu. Cependant, il n'y a aucune garantie au-delà de cela, comme expliqué dans la section suivante.

Pièges des threads : les courses de condition

Si les threads apportent un nouvel ensemble d'outils utiles, ils apportent également un certain nombre de pièges. Un piège est la condition de concurrence (race condition) :

use threads;
use threads::shared;
my $x :shared = 1;
my $thr1 = threads->create(\&sub1);
my $thr2 = threads->create(\&sub2);
$thr1->join();
$thr2->join();
print("$x\n");
sub sub1 { my $foo = $x; $x = $foo + 1; }
sub sub2 { my $bar = $x; $x = $bar + 1; }

Que pensez-vous que sera $x ? La réponse, malheureusement, est *ça*

>dépend. Les deux sub1() et sub2() accèdent à la variable globale $x, une fois pour lire et une fois pour écrire. Selon des facteurs allant de l'algorithme de planification de votre implémentation de threads à la phase de la lune, $x peut être 2 ou 3.

Les conditions de concurrence sont causées par un accès non synchronisé à des données partagées. Sans synchronisation explicite, il n'y a aucun moyen d'être sûr que rien n'est arrivé aux données partagées entre le moment où vous y accédez et le moment où vous les mettez à jour. Même ce simple fragment de code a une possibilité d'erreur :

use threads;
my $x :shared = 2;
my $y :shared;
my $z :shared;
my $thr1 = threads->create(sub { $y = $x; $x = $y + 1; });
my $thr2 = threads->create(sub { $z = $x; $x = $z + 1; });
$thr1->join();
$thr2->join();

Deux threads accèdent tous deux à $x. Chaque thread peut potentiellement être interrompu à tout moment, ou être exécuté dans n'importe quel ordre. À la fin, $x pourrait être 3 ou 4, et $y et $z pourraient être 2 ou 3.

Même "$x += 5" ou "$x++" ne sont pas garantis d'être atomiques.

Chaque fois que votre programme accède à des données ou à des ressources qui peuvent être accessibles par d'autres threads, vous devez prendre des mesures pour coordonner l'accès ou risquer une incohérence des données et des conditions de concurrence. Notez que Perl protégera ses internes de vos conditions de concurrence, mais il ne vous protégera pas de vous-même.

Synchronisation et contrôle

Perl fournit un certain nombre de mécanismes pour coordonner les interactions entre les threads et leurs données, afin d'éviter les conditions de concurrence et autres problèmes similaires. Certains sont conçus pour ressembler aux techniques courantes utilisées dans les bibliothèques de threads telles que "pthreads" ; d'autres sont spécifiques à Perl. Souvent, les techniques standard sont maladroites et difficiles à mettre en œuvre correctement (comme les attentes sur condition). Dans la mesure du possible, il est généralement plus facile d'utiliser des techniques à la Perl comme les files d'attente, qui éliminent une partie du travail difficile.

Contrôle d'accès : lock()

La fonction lock() prend une variable partagée et y place un verrou. Aucun autre thread ne peut verrouiller la variable tant que la variable n'est pas déverrouillée par le thread qui détient le verrou. Le déverrouillage se produit automatiquement lorsque le thread de verrouillage quitte le bloc qui contient l'appel à la fonction lock(). L'utilisation de lock() est simple : cet exemple comporte plusieurs threads effectuant des calculs en parallèle et mettant à jour occasionnellement un total courant :

use threads;
use threads::shared;
my $total :shared = 0;
sub calc {
    while (1) {
        my $result;
        # (... faire des calculs et définir $result ...)
        {
            lock($total);  # Bloquer jusqu'à l'obtention du verrou
            $total += $result;
        } # Le verrou est implicitement libéré à la fin de la portée
        last if $result == 0;
    }
}
my $thr1 = threads->create(\&calc);
my $thr2 = threads->create(\&calc);
my $thr3 = threads->create(\&calc);
$thr1->join();
$thr2->join();
$thr3->join();
print("total=$total\n");

lock() bloque le thread jusqu'à ce que la variable verrouillée soit disponible. Lorsque lock() revient, votre thread peut être sûr qu'aucun autre thread ne peut verrouiller cette variable tant que le bloc contenant le verrou ne sort pas de portée.

Il est important de noter que les verrous n'empêchent pas l'accès à la variable en question, seulement les tentatives de verrouillage. Ceci est conforme à la longue tradition de programmation courtoise de Perl, et au verrouillage de fichier advisory que flock() vous fournit.

Vous pouvez verrouiller des tableaux et des hachages ainsi que des scalaires. Cependant, le verrouillage d'un tableau n'empêchera pas les verrous ultérieurs sur les éléments du tableau, seulement les tentatives de verrouillage sur le tableau lui-même.

Les verrous sont récursifs, ce qui signifie qu'il est possible pour un thread de verrouiller une variable plus d'une fois. Le verrou durera jusqu'à ce que le lock() le plus externe sur la variable sorte de portée. Par exemple :

my $x :shared;
doit();
sub doit {
    {
        {
            lock($x); # Attendre le verrou
            lock($x); # NOOP - nous avons déjà le verrou
            {
                lock($x); # NOOP
                {
                    lock($x); # NOOP
                    lockit_some_more();
                }
            }
        } # *** Déverrouillage implicite ici ***
    }
}
sub lockit_some_more {
    lock($x); # NOOP
} # Rien ne se passe ici

Notez qu'il n'y a pas de fonction unlock() - la seule façon de déverrouiller une variable est de la laisser sortir de portée.

Un verrou peut soit être utilisé pour protéger les données contenues dans la variable verrouillée, soit pour protéger autre chose, comme une section de code. Dans ce dernier cas, la variable en question ne contient aucune donnée utile, et n'existe que dans le but d'être verrouillée. À cet égard, la variable se comporte comme les mutex et les sémaphores de base des bibliothèques de threads traditionnelles.

Un Piège des Threads : Les Interblocages

Les verrous sont un outil pratique pour synchroniser l'accès aux données, et leur utilisation correcte est la clé pour des données partagées sûres. Malheureusement, les verrous ne sont pas sans danger, surtout lorsqu'il s'agit de plusieurs verrous. Considérez le code suivant :

use threads;
use threads::shared;
my $x :shared = 4;
my $y :shared = 'foo';
my $thr1 = threads->create(sub {
    lock($x);
    sleep(20);
    lock($y);
});
my $thr2 = threads->create(sub {
    lock($y);
    sleep(20);
    lock($x);
});
$thr1->join();
$thr2->join();

Ce programme va probablement se bloquer jusqu'à ce que vous l'arrêtiez. La seule façon pour qu'il ne se bloque pas est si l'un des deux threads acquiert les deux verrous en premier. Une version garantissant le blocage est plus compliquée, mais le principe est le même.

Le premier thread acquiert un verrou sur $x, puis, après une pause pendant laquelle le second thread a probablement eu le temps de faire quelques travaux, essaie d'acquérir un verrou sur $y. Pendant ce temps, le second thread acquiert un verrou sur $y, puis plus tard essaie d'acquérir un verrou sur $x. La deuxième tentative de verrouillage pour les deux threads va bloquer, chacun attendant que l'autre libère son verrou.

Cette condition est appelée un interblocage, et elle se produit chaque fois que deux threads ou plus tentent d'obtenir des verrous sur des ressources que les autres possèdent. Chaque thread va bloquer, attendant que l'autre libère un verrou sur une ressource. Cela n'arrive jamais, cependant, puisque le thread qui détient la ressource attend lui-même qu'un verrou soit libéré.

Il existe un certain nombre de façons de gérer ce type de problème. La meilleure façon est de toujours faire en sorte que tous les threads acquièrent les verrous dans le même ordre exact. Si, par exemple, vous verrouillez les variables $x, $y, et $z, verrouillez toujours $x avant $y, et $y avant $z. Il est également préférable de conserver les verrous pendant la période la plus courte possible afin de minimiser les risques d'interblocage.

Les autres primitives de synchronisation décrites ci-dessous peuvent souffrir de problèmes similaires.

Files d'attente : Passer des Données

Une file d'attente est un objet spécial thread-safe qui vous permet de mettre des données à une extrémité et de les retirer de l'autre sans avoir à vous soucier des problèmes de synchronisation. Elles sont assez simples et se présentent comme suit :

use threads;
use Thread::Queue;
my $DataQueue = Thread::Queue->new();
my $thr = threads->create(sub {
    while (my $DataElement = $DataQueue->dequeue()) {
        print("Popped $DataElement off the queue\n");
    }
});
$DataQueue->enqueue(12);
$DataQueue->enqueue("A", "B", "C");
sleep(10);
$DataQueue->enqueue(undef);
$thr->join();

Vous créez la file d'attente avec "Thread::Queue->new()". Ensuite, vous pouvez ajouter des listes de scalaires à la fin avec enqueue(), et retirer des scalaires du début avec dequeue(). Une file d'attente n'a pas de taille fixe et peut croître selon les besoins pour contenir tout ce qui y est ajouté.

Si une file d'attente est vide, dequeue() se bloque jusqu'à ce qu'un autre thread y ajoute quelque chose. Cela rend les files d'attente idéales pour les boucles d'événements et autres communications entre threads.

Sémaphores : Synchronisation d'Accès aux Données

Les sémaphores sont une sorte de mécanisme de verrouillage générique. Dans leur forme la plus basique, ils se comportent de manière très similaire aux scalaires verrouillables, à la seule différence qu'ils ne peuvent pas contenir de données et qu'ils doivent être explicitement déverrouillés. Dans leur forme avancée, ils agissent comme une sorte de compteur, et peuvent permettre à plusieurs threads d'avoir le *verrou* à un moment donné.

Sémaphores de base

Les sémaphores ont deux méthodes, down() et up() : down() décrémente le compteur de ressources, tandis que up() l'incrémente. Les appels à down() se bloqueront si le compte actuel du sémaphore devient négatif lors de la décrémentation. Ce programme donne une démonstration rapide :

use threads;
use Thread::Semaphore;
my $semaphore = Thread::Semaphore->new();
my $GlobalVariable :shared = 0;
$thr1 = threads->create(\&sample_sub, 1);
$thr2 = threads->create(\&sample_sub, 2);
$thr3 = threads->create(\&sample_sub, 3);
sub sample_sub {
    my $SubNumber = shift(@_);
    my $TryCount = 10;
    my $LocalCopy;
    sleep(1);
    while ($TryCount--) {
        $semaphore->down();
        $LocalCopy = $GlobalVariable;
        print("$TryCount tries left for sub $SubNumber "
             ."(\$GlobalVariable is $GlobalVariable)\n");
        sleep(2);
        $LocalCopy++;
        $GlobalVariable = $LocalCopy;
        $semaphore->up();
    }
}
$thr1->join();
$thr2->join();
$thr3->join();

Les trois invocations de la sous-routine fonctionnent de manière synchronisée. Le sémaphore, cependant, s'assure qu'un seul thread accède à la variable globale à la fois.

Sémaphores avancés

Par défaut, les sémaphores se comportent comme des verrous, ne permettant à un seul thread de les down() à la fois. Ho

Semaphores avancés

Cependant, il existe d'autres utilisations pour les sémaphores.

Chaque sémaphore a un compteur attaché. Par défaut, les sémaphores sont créés avec le compteur défini à un, down() décrémente le compteur de un, et up() l'incrémente de un. Cependant, nous pouvons outrepasser l'un ou l'ensemble de ces valeurs par défaut en passant simplement des valeurs différentes :

use threads;
use Thread::Semaphore;
my $semaphore = Thread::Semaphore->new(5);
                # Crée un sémaphore avec le compteur défini à cinq
my $thr1 = threads->create(\&sub1);
my $thr2 = threads->create(\&sub1);
sub sub1 {
    $semaphore->down(5); # Décrémente le compteur de cinq
    # Faire des choses ici
    $semaphore->up(5); # Incrémente le compteur de cinq
}
$thr1->detach();
$thr2->detach();

Si down() tente de décrémenter le compteur en dessous de zéro, il se bloque jusqu'à ce que le compteur soit suffisamment grand. Notez que bien qu'un sémaphore puisse être créé avec un compte initial de zéro, tout up() ou down() change toujours le compteur d'au moins un, et donc "$semaphore->down(0)" est identique à "$semaphore->down(1)".

La question, bien sûr, est de savoir pourquoi feriez-vous quelque chose comme ça ? Pourquoi créer un sémaphore avec un compte initial qui n'est pas un, ou pourquoi le décrémenter ou l'incrémenter de plus d'un ? La réponse est la disponibilité des ressources. De nombreuses ressources dont vous voulez gérer l'accès peuvent être utilisées en toute sécurité par plusieurs threads à la fois.

Par exemple, prenons un programme piloté par une interface graphique. Il a un sémaphore qu'il utilise pour synchroniser l'accès à l'affichage, de sorte qu'un seul thread dessine à la fois. Pratique, mais bien sûr, vous ne voulez pas qu'un thread commence à dessiner avant que les choses ne soient correctement configurées. Dans ce cas, vous pouvez créer un sémaphore avec un compteur défini à zéro, et l'incrémenter lorsque les choses sont prêtes pour le dessin.

Les sémaphores avec des compteurs supérieurs à un sont également utiles pour établir des quotas. Disons, par exemple, que vous avez un certain nombre de threads qui peuvent effectuer des opérations d'E/S simultanément. Vous ne voulez pas que tous les threads lisent ou écrivent en même temps, car cela peut potentiellement surcharger vos canaux d'E/S, ou épuiser le quota de descripteurs de fichiers de votre processus. Vous pouvez utiliser un sémaphore initialisé au nombre de requêtes d'E/S concurrentes (ou de fichiers ouverts) que vous souhaitez à tout moment, et laisser vos threads se bloquer et se débloquer tranquillement.

Les incrémentations ou décrémentations plus importantes sont utiles dans les cas où un thread doit retirer ou restituer plusieurs ressources à la fois.

Attente d'une condition

Les fonctions cond_wait() et cond_signal() peuvent être utilisées conjointement avec des verrous pour notifier des threads coopératifs qu'une ressource est devenue disponible. Elles sont très similaires dans leur utilisation aux fonctions trouvées dans "pthreads". Cependant, pour la plupart des usages, les files d'attente sont plus simples à utiliser et plus intuitives. Voir threads::shared pour plus de détails.

Abandon du contrôle

Il y aura des moments où vous trouverez utile qu'un thread abandonne explicitement le CPU à un autre thread. Vous pourriez faire quelque chose d'intensif en processeur et vouloir vous assurer que le thread de l'interface utilisateur est appelé fréquemment. Quoi qu'il en soit, il y aura des moments où vous voudrez qu'un thread cède le processeur.

Le package de threading de Perl fournit la fonction yield() qui fait cela. yield() est assez simple et fonctionne comme suit :

use threads;
sub loop {
    my $thread = shift;
    my $foo = 50;
    while($foo--) { print("Dans le thread $thread\n"); }
    threads->yield();
    $foo = 50;
    while($foo--) { print("Dans le thread $thread\n"); }
}
my $thr1 = threads->create(\&loop, 'premier');
my $thr2 = threads->create(\&loop, 'deuxième');
my $thr3 = threads->create(\&loop, 'troisième');

Il est important de se rappeler que yield() n'est qu'un indice pour céder le CPU, cela dépend de votre matériel, de votre système d'exploitation et de vos bibliothèques de threading de ce qui se passe réellement. **Sur de nombreux systèmes d'exploitation, yield() est une opération nulle.** Il est donc important de noter qu'il ne faut pas construire la planification des threads autour des appels à yield(). Cela pourrait fonctionner sur votre plateforme, mais cela ne fonctionnera pas sur une autre.

Routines utilitaires générales des threads

Nous avons couvert les éléments essentiels du package de threading de Perl, et avec ces outils, vous devriez être bien avancé dans l'écriture de code et de packages multi-threads. Il y a quelques petites pièces utiles qui ne rentraient pas vraiment ailleurs.

Dans quel thread suis-je ?

La méthode de classe "threads->self()" fournit à votre programme un moyen d'obtenir un objet représentant le thread dans lequel il se trouve actuellement. Vous pouvez utiliser cet objet de la même manière que ceux retournés par la création de thread.

Identifiants de thread

tid() est une méthode d'objet thread qui retourne l'identifiant du thread que représente l'objet. Les identifiants de thread sont des entiers, le thread principal d'un programme étant 0. Actuellement, Perl attribue un TID unique à chaque thread jamais créé dans votre programme, attribuant au premier thread créé un TID de 1, et augmentant le TID de 1 pour chaque nouveau thread créé. Lorsqu'il est utilisé comme méthode de classe, "threads->tid()" peut être utilisé par un thread pour obtenir son propre TID.

Ces threads sont-ils les mêmes ?

La méthode equal() prend deux objets thread et retourne vrai si les objets représentent le même thread, et faux s'ils ne le font pas.

Les objets thread ont également une comparaison "==" surchargée afin que vous puissiez effectuer des comparaisons sur eux comme vous le feriez avec des objets normaux.

Quels threads sont en cours d'exécution ?

"threads->list()" retourne une liste d'objets thread, un pour chaque thread en cours d'exécution et non détaché. Pratique pour un certain nombre de choses, y compris le nettoyage à la fin de votre programme (depuis le thread Perl principal, bien sûr) :

# Boucler à travers tous les threads
foreach my $thr (threads->list()) {
    $thr->join();
}

Si certains threads n'ont pas fini de s'exécuter lorsque le thread Perl principal se termine, Perl vous avertira et mourra, car il est impossible pour Perl de se nettoyer pendant que d'autres threads s'exécutent.

NOTE : Le thread Perl principal (thread 0) est en état détaché, et n'apparaît donc pas dans la liste retournée par "threads->list()".

Un exemple complet

Confus encore ? Il est temps d'un exemple de programme pour montrer certaines des choses que nous avons couvertes. Ce programme trouve des nombres premiers en utilisant des threads.

 1 #!/usr/bin/perl
 2 # prime-pthread, avec l'aimable autorisation de Tom Christiansen
 3
 4 use v5.36;
 5
 6 use threads;
 7 use Thread::Queue;
 8
 9 sub check_num ($upstream, $cur_prime) {
10     my $kid;
11     my $downstream = Thread::Queue->new();
12     while (my $num = $upstream->dequeue()) {
13         next unless ($num % $cur_prime);
14         if ($kid) {
15             $downstream->enqueue($num);
16         } else {
17             print("Trouvé premier : $num\n");
18             $kid = threads->create(\&check_num, $downstream, $num);
19             if (! $kid) {
20                 warn("Désolé. Manque de threads.\n");
21                 last;
22             }
23         }
24     }
25     if ($kid) {
26         $downstream->enqueue(undef);
27         $kid->join();
28     }
29 }
30
31 my $stream = Thread::Queue->new(3..1000, undef);
32 check_num($stream, 2);

Ce programme utilise le modèle de pipeline pour générer des nombres premiers. Chaque thread du pipeline a une file d'attente d'entrée qui alimente les nombres à vérifier, un nombre premier dont il est responsable, et une file d'attente de sortie dans laquelle il dirige les nombres qui ont échoué à la vérification. Si le thread a un nombre qui a échoué à sa vérification et qu'il n'y a pas de thread enfant, alors le thread doit avoir trouvé un nouveau nombre premier. Dans ce cas, un nouveau thread enfant est créé pour ce premier et ajouté à la fin du pipeline.

Cela semble probablement un peu plus déroutant que cela ne l'est en réalité, alors examinons ce programme morceau par morceau et voyons ce qu'il fait. (Pour ceux d'entre vous qui pourraient essayer de se souvenir exactement de ce qu'est un nombre premier, c'est un nombre qui n'est divisible que par lui-même et par 1.)

La majeure partie du travail est effectuée par la sous-routine check_num(), qui prend une référence à sa file d'attente d'entrée et un nombre premier dont elle est responsable. Nous créons une nouvelle file d'attente (ligne 11) et réservons un scalaire pour le thread que nous allons probablement créer plus tard (ligne 10).

La boucle while des lignes 12 à 24 récupère un scalaire de la file d'attente d'entrée et vérifie par rapport au premier dont ce thread est responsable. La ligne 13 vérifie s'il y a un reste lorsque nous divisons le nombre à vérifier par notre premier. S'il y en a un, le nombre ne doit pas être divisible par notre premier, nous devons donc soit le passer au thread suivant si nous en avons créé un (ligne 15), soit créer un nouveau thread si nous n'en avons pas.

La création d'un nouveau thread se fait à la ligne 18. Nous lui passons une référence à la file d'attente que nous avons créée et le nombre premier que nous avons trouvé. Aux lignes 19 à 22, nous vérifions si notre nouveau thread a été créé, et sinon, nous arrêtons de vérifier les nombres restants dans la file d'attente.

Enfin, une fois que la boucle se termine (parce que nous avons obtenu un 0 ou "undef" dans la file d'attente, ce qui sert de signal pour terminer), nous transmettons l'avis à notre enfant et attendons qu'il se termine si nous en avons créé un (lignes 25 et 28).

Pendant ce temps, dans le thread principal, nous créons d'abord une file d'attente (ligne 31) et mettons en file d'attente tous les nombres de 3 à 1000 pour vérification, plus une notification de fin. Ensuite, tout ce que nous avons à faire pour lancer le processus est de passer la file d'attente et le premier premier à la sous-routine check_num() (ligne 32).

Voilà comment ça marche. C'est assez simple ; comme pour de nombreux programmes Perl, l'explication est beaucoup plus longue que le programme.

Lecture supplémentaire

Différentes implémentations de threads

Quelques informations sur les implémentations de threads du point de vue du système d'exploitation. Il existe trois catégories principales de threads : les threads en mode utilisateur, les threads noyau et les threads noyau multiprocesseurs.

Les threads en mode utilisateur sont des threads qui résident entièrement dans un programme et ses bibliothèques. Dans ce modèle, le SE ne sait rien des threads. Pour lui, votre processus est juste un processus.

C'est la manière la plus simple d'implémenter les threads, et celle par laquelle la plupart des SE commencent. Le principal inconvénient est que, puisque le SE ne sait rien des threads, si un thread se bloque, ils se bloquent tous. Les activités de blocage typiques incluent la plupart des appels système, la plupart des E/S, et des choses comme sleep().

Les threads noyau sont l'étape suivante dans l'évolution des threads. Le SE connaît les threads noyau et en tient compte. La principale différence entre un thread noyau et un thread en mode utilisateur est le blocage. Avec les threads noyau, les choses qui bloquent un seul thread ne bloquent pas les autres threads. Ce n'est pas le cas des threads en mode utilisateur, où le noyau bloque au niveau du processus et non au niveau du thread.

C'est un grand pas en avant, et cela peut donner un coup de pouce de performance considérable à un programme multithread par rapport aux programmes non multithread. Les threads qui se bloquent lors des E/S, par exemple, ne bloqueront pas les threads qui font d'autres choses. Chaque processus n'a toujours qu'un seul thread en cours d'exécution à la fois, cependant, quel que soit le nombre de CPU qu'un système peut avoir.

Étant donné que le threading noyau peut interrompre un thread à tout moment, il révélera certaines des hypothèses de verrouillage implicites que vous pourriez faire dans votre programme. Par exemple, quelque chose d'aussi simple que "$x = $x + 2" peut se comporter de manière imprévisible avec les threads noyau si $x est visible par d'autres threads, car un autre thread peut avoir modifié $x entre le moment où il a été récupéré du côté droit et le moment où la nouvelle valeur est stockée.

Les threads noyau multiprocesseurs sont l'étape finale du support des threads. Avec les threads noyau multiprocesseurs sur une machine avec plusieurs CPU, le SE peut planifier l'exécution de deux threads ou plus simultanément sur différents CPU.

Cela peut donner un sérieux coup de pouce de performance à votre programme multithread, car plus d'un thread sera en cours d'exécution en même temps. En contrepartie, cependant, tous ces problèmes de synchronisation gênants qui n'auraient peut-être pas été révélés avec les threads noyau de base apparaîtront avec une vengeance.

En plus des différents niveaux d'implication du SE dans les threads, différents SE (et différentes implémentations de threads pour un SE particulier) allouent les cycles CPU aux threads de différentes manières.

Les systèmes multitâche coopératifs font en sorte que les threads en cours cèdent le contrôle si l'une des deux conditions suivantes se produit. Si un thread appelle une fonction de céder le contrôle, il cède le contrôle. Il cède également le contrôle si le thread fait quelque chose qui le bloquerait, comme effectuer des E/S. Dans une implémentation multitâche coopérative, un thread peut affamer tous les autres de temps CPU s'il le choisit.

Les systèmes multitâche préemptifs interrompent les threads à intervalles réguliers pendant que le système décide quel thread doit s'exécuter ensuite. Dans un système multitâche préemptif, un thread ne monopolisera généralement pas le CPU.

Sur certains systèmes, des threads coopératifs et préemptifs peuvent s'exécuter simultanément. (Par exemple, les threads s'exécutant avec des priorités temps réel se comportent souvent de manière coopérative, tandis que les threads s'exécutant à des priorités normales se comportent de manière préemptive.)

La plupart des systèmes d'exploitation modernes prennent en charge le multitâche préemptif de nos jours.

Considérations de performance

La chose principale à garder à l'esprit lors de la comparaison des ithreads de Perl avec d'autres modèles de threading est le fait que pour chaque nouveau thread créé, une copie complète de toutes les variables et données du thread parent doit être effectuée. Ainsi, la création de threads peut être assez coûteuse, tant en termes d'utilisation de la mémoire que de temps passé à la création. La manière idéale de réduire ces coûts est d'avoir un nombre relativement faible de threads à longue durée de vie, tous créés assez tôt (avant que le thread de base n'ait accumulé trop de données). Bien sûr, cela n'est pas toujours possible, il faut donc faire des compromis. Cependant, une fois qu'un thread a été créé, ses performances et son utilisation supplémentaire de la mémoire devraient être peu différentes de celles d'un code ordinaire.

Notez également que dans l'implémentation actuelle, les variables partagées utilisent un peu plus de mémoire et sont un peu plus lentes que les variables ordinaires.

Changements de portée de processus

Notez que si les threads eux-mêmes sont des threads d'exécution distincts et que les données Perl sont privées au thread sauf si elles sont explicitement partagées, les threads peuvent affecter l'état de portée du processus, affectant tous les threads.

L'exemple le plus courant est de changer le répertoire de travail actuel à l'aide de chdir(). Un thread appelle chdir(), et le répertoire de travail de tous les threads change.

Un exemple encore plus drastique de changement de portée de processus est chroot() : le répertoire racine de tous les threads change, et aucun thread ne peut l'annuler (contrairement à chdir()).

D'autres exemples de changements de portée de processus incluent umask() et le changement des UID et GID.

Vous pensez mélanger fork() et threads ? Veuillez vous allonger et attendre que la sensation passe. Sachez que la sémantique de fork() varie selon les plateformes. Par exemple, certains systèmes Unix copient tous les threads actuels dans le processus enfant, tandis que d'autres ne copient que le thread qui a appelé fork(). Vous avez été prévenu !

De même, mélanger signaux et threads peut être problématique. Les implémentations dépendent de la plateforme, et même la sémantique POSIX peut ne pas être celle que vous attendez (et Perl ne vous donne même pas l'API POSIX complète). Par exemple, il n'y a aucun moyen de garantir qu'un signal envoyé à une application Perl multithread sera intercepté par un thread particulier. (Cependant, une fonctionnalité récemment ajoutée fournit la capacité d'envoyer des signaux entre threads. Voir "THREAD SIGNALLING" dans threads pour plus de détails.)

Sécurité des threads des bibliothèques système

La sécurité des threads des appels de bibliothèque C est hors du contrôle de Perl. Un comportement indéfini se produira si des appels non sécurisés sont utilisés pendant le fonctionnement multithread. Voir "Dealing with embedded perls and threads" dans perlclib.

Conclusion

Un tutoriel complet sur les threads pourrait remplir un livre (et l'a fait, plusieurs fois), mais avec ce que nous avons couvert dans cette introduction, vous devriez être sur la bonne voie pour devenir un expert en threading Perl.
