PERL5260DELTA(1perl) Guide de référence du programmeur Perl PERL5260DELTA(1perl)

NOM

perl5260delta - ce qui est nouveau pour la version perl v5.26.0

DESCRIPTION

Ce document décrit les différences entre la version 5.24.0 et la version 5.26.0.

Remarque

Cette version inclut trois mises à jour aux effets généralisés :

  • "." n'est plus dans @INC

    Pour des raisons de sécurité, le répertoire courant (".") n'est plus inclus par défaut à la fin du chemin de recherche des modules (@INC). Cela peut avoir des implications généralisées pour la construction, le test et l'installation de modules, ainsi que pour l'exécution de scripts. Voir la section "Suppression du répertoire courant (".") de @INC" pour tous les détails.

  • "do" peut maintenant avertir

    "do" émet maintenant un avertissement de dépréciation lorsqu'il ne parvient pas à charger un fichier qu'il aurait chargé si "." était dans @INC.

  • Dans les motifs d'expressions régulières, une accolade littérale "{" doit être échappée

    Voir "Les caractères d'accolade littérale "{" non échappée dans les motifs d'expressions régulières ne sont plus autorisés".

Améliorations du cœur

Les sous-routines lexicales ne sont plus expérimentales

L'utilisation de la fonctionnalité "lexical_subs" introduite dans la v5.18 n'émet plus d'avertissement. Le code existant qui désactive la catégorie d'avertissement "experimental::lexical_subs", que la fonctionnalité utilisait précédemment, continuera de fonctionner. La fonctionnalité "lexical_subs" n'a aucun effet ; tout code Perl peut utiliser des sous-routines lexicales, quelles que soient les déclarations de fonctionnalités en portée.

Here-documents indentés

Ajoute un nouveau modificateur "~" aux here-docs qui indique à l'analyseur de rechercher "/^\s*$DELIM\n/" comme délimiteur de fermeture.

Ces syntaxes sont toutes supportées :

<<~EOF;
<<~\EOF;
<<~'EOF';
<<~"EOF";
<<~`EOF`;
<<~ 'EOF';
<<~ "EOF";
<<~ `EOF`;

Le modificateur "~" supprimera, de chaque ligne du here-doc, les mêmes espaces blancs qui apparaissent avant le délimiteur.

Les sauts de ligne seront copiés tels quels, et les lignes ne contenant pas les espaces blancs appropriés provoqueront un plantage de Perl.

Par exemple :

if (1) {
  print <<~EOF;
    Bonjour
    EOF
}

imprime "Bonjour\n" sans espace blanc initial.

Nouveau modificateur d'expression régulière "/xx"

Spécifier deux caractères "x" pour modifier un motif d'expression régulière fait tout ce qu'un seul fait, mais ignore en plus les caractères TAB et ESPACE à l'intérieur d'une classe de caractères entre crochets et peut être ajouté pour améliorer la lisibilité, comme "/[ ^ A-Z d-f p-x ]/xx". Les détails se trouvent dans "/x et /xx" dans perlre.

"@{^CAPTURE}", "%{^CAPTURE}", et "%{^CAPTURE_ALL}"

"@{^CAPTURE}" expose les tampons de capture de la dernière correspondance sous forme de tableau. Ainsi, $1 est "${^CAPTURE}[0]". C'est un équivalent plus efficace d'un code comme "substr($matched_string,$-[0],$+[0]-$-[0])", et vous n'avez pas non plus à suivre $matched_string. Cette variable n'a pas d'équivalent en un seul caractère. Notez que, comme les autres variables magiques de regex, le contenu de cette variable est dynamique ; si vous souhaitez la stocker au-delà de la durée de vie de la correspondance, vous devez la copier dans un autre tableau.

"%{^CAPTURE}" est équivalent à "%+" (c'est-à-dire les captures nommées). Hormis le fait d'être plus auto-documenté, il n'y a pas de différence entre les deux formes.

"%{^CAPTURE_ALL}" est équivalent à "%-" (c'est-à-dire toutes les captures nommées). Hormis le fait d'être plus auto-documenté, il n'y a pas de différence entre les deux formes.

Déclaration d'une référence à une variable

En tant que fonctionnalité expérimentale, Perl permet désormais à l'opérateur de référencement de venir après my(), state(), our(), ou local(). Cette syntaxe doit être activée avec "use feature 'declared_refs'". Elle est expérimentale et produira un avertissement par défaut à moins que "no warnings 'experimental::refaliasing'" ne soit actif. Elle est principalement destinée à être utilisée dans les affectations à des références. Par exemple :

use experimental 'refaliasing', 'declared_refs';
my \$a = \$b;

Voir "Affectation aux références" dans perlref pour plus de détails.

Unicode 9.0 est maintenant supporté

Une liste des changements est disponible à http://www.unicode.org/versions/Unicode9.0.0/. Les modules distribués avec le cœur de Perl mais non maintenus par p5p ne supportent pas nécessairement Unicode 9.0. Unicode::Normalize fonctionne avec la version 9.0.

L'utilisation de "\p{script}" utilise la propriété améliorée Script_Extensions

Unicode 6.0 a introduit une forme améliorée de la propriété Script ("sc"), appelée Script_Extensions ("scx"). Perl utilise maintenant cette version améliorée lorsqu'une propriété est spécifiée simplement comme "\p{script}". Cela devrait rendre les programmes plus précis lors de la détermination si un caractère est utilisé dans un script donné, mais il y a une légère possibilité de rupture pour les programmes qui nécessitaient très spécifiquement l'ancien comportement. La signification des formes composées, comme "\p{sc=script}" reste inchangée. Voir "Scripts" dans perlunicode.

Perl peut maintenant effectuer une collation par défaut dans les locales UTF-8 sur les plateformes qui le supportent

Certaines plateformes effectuent nativement un travail raisonnable de collation et de tri dans les locales UTF-8. Perl fonctionne maintenant avec celles-ci. Pour la portabilité et un contrôle total, Unicode::Collate est toujours recommandé, mais vous n'aurez peut-être plus besoin de faire quoi que ce soit de spécial pour obtenir des résultats suffisamment bons, selon votre application. Voir "Catégorie "LC_COLLATE" : Collation : Comparaisons de texte et tri" dans perllocale.

Meilleure collation locale des chaînes contenant des caractères "NUL" intégrés

La fonctionnalité de collation des chaînes intégrées avec des caractères NUL.

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

Contenant des caractères « NUL » intégrés

Dans les locales qui ont des poids de caractères à plusieurs niveaux, les « NUL » sont désormais ignorés aux priorités les plus élevées. Il subsiste néanmoins quelques pièges dans certaines chaînes de caractères. Voir « Collation of strings containing embedded « NUL » characters » dans perllocale.

Sous-routines « CORE » pour les fonctions de hachage et de tableau appelables via une référence

Les fonctions de hachage et de tableau de l'espace de noms « CORE » ( « keys », « each », « values », « push », « pop », « shift », « unshift » et « splice ») peuvent désormais être appelées avec la syntaxe ampersand ( « &CORE::keys(\%hash ») et via une référence ( « my $k = \&CORE::keys; $k->(\%hash) »). Auparavant, elles ne pouvaient être utilisées que lorsqu'elles étaient intégrées.

Nouvelle fonction de hachage pour les compilations 64 bits

Nous sommes passés à une fonction de hachage hybride pour mieux équilibrer les performances pour les clés courtes et longues.

Pour les clés courtes, de 16 octets ou moins, nous utilisons une variante optimisée de « One At A Time Hard », et pour les clés plus longues, nous utilisons Siphash 1-3. Pour les clés très longues, c'est une amélioration majeure des performances. Pour les clés plus courtes, l'amélioration est modeste.

Sécurité

Suppression du répertoire courant (« . ») de @INC

Le binaire Perl inclut un ensemble par défaut de chemins dans @INC. Historiquement, il incluait également le répertoire courant ( « . ») comme dernière entrée, sauf lorsqu'il était exécuté en mode « taint » ( « perl -T »). Bien que pratique, cela avait des implications en matière de sécurité : par exemple, lorsqu'un script tente de charger un module optionnel alors que son répertoire courant n'est pas fiable (par exemple, /tmp), il pourrait charger et exécuter du code à partir de ce répertoire.

À partir de la v5.26, « . » est toujours supprimé par défaut, pas seulement sous « taint ». Cela a des implications majeures pour l'installation de modules et l'exécution de scripts.

Les nouvelles fonctionnalités suivantes ont été ajoutées pour aider à atténuer ces problèmes.

  • Configure -Udefault_inc_excludes_dot

    Il existe une nouvelle option « Configure », « default_inc_excludes_dot » (activée par défaut) qui crée un exécutable Perl sans « . » ; désactiver cette option avec « -U » rétablit le comportement précédent de Perl. Cela peut résoudre vos problèmes de chemin, mais réintroduira toutes les préoccupations de sécurité, ne compilez donc pas un exécutable Perl de cette manière à moins d'être *vraiment* sûr que de tels problèmes ne sont pas une préoccupation dans votre environnement.

  • « PERL_USE_UNSAFE_INC »

    Il existe une nouvelle variable d'environnement reconnue par l'interpréteur Perl. Si cette variable a la valeur 1 au démarrage de l'interpréteur Perl, alors « . » sera automatiquement ajouté à @INC (sauf sous « taint »).

    Cela vous permet de rétablir l'ancien comportement de l'interpréteur Perl au cas par cas. Mais notez que cela est destiné à être une béquille temporaire, et cette fonctionnalité sera probablement supprimée dans une future version de Perl. Elle est actuellement définie par l'utilitaire « cpan » et « Test::Harness » pour faciliter l'installation de modules CPAN qui n'ont pas été mis à jour pour gérer l'absence de point. Encore une fois, n'utilisez pas cela à moins d'être sûr que cela ne réintroduira aucune préoccupation de sécurité.

  • Un nouvel avertissement de dépréciation émis par « do ».

    Bien qu'il soit bien connu que « use » et « require » utilisent @INC pour rechercher le fichier à charger, beaucoup de gens ne réalisent pas que « do « file » » recherche également dans @INC si le fichier est un chemin relatif. Avec la suppression de « . », un simple « do « file.pl » » échouera à lire et exécuter « file.pl » du répertoire courant. Comme il s'agit d'un comportement généralement attendu, un nouvel avertissement de dépréciation est maintenant émis chaque fois que « do » ne parvient pas à charger un fichier qu'il aurait autrement trouvé si un point avait été dans @INC.

Voici quelques éléments que les auteurs de scripts et de modules pourraient avoir besoin de faire pour que leurs logiciels fonctionnent dans le nouveau régime.

  • Auteurs de scripts

    Si le problème se situe dans votre propre code (plutôt que dans les modules inclus), vous avez deux options principales. Premièrement, si vous êtes confiant que votre script ne sera exécuté que dans un répertoire de confiance (sous lequel vous vous attendez à trouver des fichiers et des modules de confiance), alors réinsérez « . » dans le chemin ; par exemple :

    BEGIN {
    my $dir = "/some/trusted/directory";
    chdir $dir or die "Can't chdir to $dir: $!\n";
    # sûr maintenant
    push @INC, '.';
}
use "Foo::Bar"; # peut charger /some/trusted/directory/Foo/Bar.pm
do "config.pl"; # peut charger /some/trusted/directory/config.pl

    D'autre part, si votre script est destiné à être exécuté depuis des répertoires non fiables (tels que /tmp), alors le fait que votre script échoue soudainement à charger des fichiers peut indiquer un problème de sécurité. Vous voudrez très probablement remplacer tous les chemins relatifs par des chemins complets ; par exemple,

    do "foo_config.pl"

    pourrait devenir

    do "$ENV{HOME}/foo_config.pl"

    Si vous êtes absolument certain que vous voulez que votre script charge et exécute un fichier du répertoire courant, utilisez un préfixe « ./ » ; par exemple :

    do "./foo_config.pl"
  • Installation et utilisation de modules CPAN

    Si vous installez un module CPAN à l'aide d'un outil automatique comme « cpan », cet outil définira lui-même la variable d'environnement « PERL_USE_UNSAFE_INC » lors de la compilation et du test du module, ce qui peut suffire à installer une distribution qui n'a pas été mise à jour pour être consciente des points. Si vous souhaitez installer un tel module manuellement, vous devrez remplacer l'invocation traditionnelle :

    perl Makefile.PL && make && make test && make install

    par quelque chose comme

    (export PERL_USE_UNSAFE_INC=1; \
 perl Makefile.PL && make && make test && make install)

    Notez que cela n'aide qu'à compiler et installer un module non corrigé. Il est possible que les tests réussissent (car ils ont été exécutés sous « PERL_USE_UNSAFE_INC=1 »), mais que le module lui-même ne fonctionne pas correctement en production. Dans ce cas, vous pourrez avoir à modifier temporairement votre script jusqu'à ce qu'une version corrigée du module soit publiée. Par exemple :

    use Foo::Bar;
{
    local @INC = (@INC, '.');
    # en supposant que read_config() a besoin de '.' dans @INC
    $config = Foo::Bar->read_config();
}

    On s'attend à ce que cela ne soit nécessaire que rarement. Là encore, si vous faites cela, évaluez d'abord les risques résultants.

  • Auteurs de modules

    Si vous maintenez une distribution CPAN, elle pourrait avoir besoin d'une mise à jour pour s'exécuter dans un environnement sans point. Bien que « cpan » et d'autres outils similaires définissent actuellement la variable d'environnement « PERL_USE_UNSAFE_INC » pendant la compilation du module, il s'agit d'une solution temporaire pour l'ensemble des modules qui dépendent de « . » dans @INC pour l'installation et les tests, et cela peut masquer des problèmes plus profonds. Cela pourrait entraîner un module qui réussit les tests et s'installe, mais qui échoue à l'exécution.

    Pendant la compilation, les tests et l'installation, il sera normalement le cas que tout processus Perl s'exécute directement dans le répertoire racine de la distribution décompressée, ou dans un sous-répertoire connu de celle-ci, tel que t/. Il est fort possible que Makefile.PL ou t/foo.t tente d'inclure des modules locaux et des fichiers de configuration en utilisant leurs noms de fichiers relatifs directs, ce qui échouera désormais.

    Cependant, comme décrit ci-dessus, les outils automatiques tels que cpan définiront (pour l'instant) la variable d'environnement « PERL_USE_UNSAFE_INC », qui introduit le point pendant une compilation.

    Il est donc probable que votre code de compilation et de test existant fonctionnera, mais cela pourrait masquer des problèmes dans votre code qui ne se manifestent qu'après l'installation. Il est prudent d'essayer d'exécuter votre processus de compilation avec cette variable explicitement désactivée :

    (export PERL_USE_UNSAFE_INC=0; \
 perl Makefile.PL && make && make test && make install)

    Cela est plus susceptible de révéler d'éventuels problèmes avec le processus de compilation de votre module, voire avec le module lui-même. La résolution de tels problèmes garantira que votre module peut à nouveau être installé manuellement et qu'il continuera à être compilé une fois la béquille « PERL_USE_UNSAFE_INC » disparue.

    Lors de la correction de problèmes dans les tests dus à la suppression du point de @INC, la réinsertion du point dans @INC doit être effectuée avec prudence, car cela pourrait également masquer des erreurs réelles dans votre code d'exécution. Il est conseillé, dans la mesure du possible, d'appliquer les approches mentionnées ci-dessus avec des chemins absolus/relatifs explicites, ou de déplacer vos fichiers nécessaires dans un sous-répertoire et d'insérer ce sous-répertoire dans @INC à la place.

    <

    Si votre code d'exécution rencontre des problèmes sous le @INC sans point, les commentaires ci-dessus sur la façon de corriger pour les auteurs de scripts s'appliqueront en grande partie ici aussi. Gardez à l'esprit cependant qu'il est considéré comme une mauvaise pratique pour un module d'ajouter globalement un point à @INC, car cela introduit à la fois un risque de sécurité et masque les problèmes d'inclusion accidentelle de points dans @INC, comme expliqué ci-dessus.

Colonnes échappées et chemins relatifs dans PATH

Sur les systèmes Unix, Perl traite les chemins relatifs dans la variable d'environnement "PATH" comme étant taintés lors du démarrage d'un nouveau processus. Auparavant, il permettait à une barre oblique inverse d'échapper à un deux-points (contrairement au système d'exploitation), permettant ainsi de considérer les chemins relatifs comme sûrs si le PATH était défini sur quelque chose comme "/\:.". La vérification a été corrigée pour traiter "." comme étant tainté dans cet exemple.

Le nouveau commutateur "-Di" est maintenant requis pour la sortie de débogage PerlIO

Ceci est utilisé pour le débogage du code dans PerlIO afin d'éviter les appels récursifs. Auparavant, cette sortie était envoyée au fichier spécifié par la variable d'environnement "PERLIO_DEBUG" si Perl ne fonctionnait pas setuid et que les commutateurs "-T" ou "-t" n'avaient pas encore été analysés.

Si Perl produisait une sortie à un moment où il n'avait pas encore analysé ses commutateurs, cela pouvait entraîner la création ou l'écrasement par Perl du fichier nommé par "PERLIO_DEBUG" même lorsque le commutateur "-T" avait été fourni.

Perl nécessite maintenant que le commutateur "-Di" soit présent avant de produire une sortie de débogage PerlIO. Par défaut, elle est écrite sur "stderr", mais peut être redirigée en option vers un fichier en définissant la variable d'environnement "PERLIO_DEBUG".

Si Perl s'exécute en setuid ou si le commutateur "-T" a été fourni, "PERLIO_DEBUG" est ignoré et la sortie de débogage est envoyée à "stderr" comme pour tout autre commutateur "-D".

Changements incompatibles

Les caractères apostrophe littéraux non échappés dans les motifs d'expression régulière ne sont plus autorisés

Vous devez maintenant dire quelque chose comme "\{" ou "[{]" pour spécifier la correspondance d'une ACCOLADE OUVRANTE ; sinon, c'est une erreur de compilation de motif fatale. Ce changement permettra de futures extensions du langage.

Ces éléments étaient dépréciés depuis la v5.16, avec un message de dépréciation soulevé pour certaines utilisations à partir de la v5.22. Malheureusement, le code ajouté pour soulever le message était bogué et ne parvenait pas à avertir dans certains cas où il aurait dû le faire. Par conséquent, l'application de cette interdiction pour ces cas est reportée jusqu'à Perl 5.30, mais le code a été corrigé pour soulever un message de dépréciation par défaut pour eux entre-temps.

Certaines utilisations d'apostrophes littéraux "{" se produisent dans des contextes où nous ne prévoyons pas que le sens soit autre que littéral, comme le tout premier caractère du motif, ou après un "|" signifiant alternance. Ainsi

qr/{fee|{fie/

correspond soit à l'une des chaînes "{fee" soit à "{fie". Pour éviter de forcer des changements de code inutiles, ces utilisations n'ont pas besoin d'être échappées, et aucun avertissement n'est émis à leur sujet, et il n'y a actuellement aucun plan pour changer cela.

Mais il est toujours correct d'échapper "{", et la règle simple à retenir est de le faire toujours.

Voir Unescaped left brace in regex is illegal here.

la signature de retour de scalar(%hash) a changé

La valeur retournée pour scalar(%hash) n'affichera plus d'informations sur les buckets alloués dans le hash. Elle retournera simplement le nombre de clés utilisées. Elle est donc équivalente à "0+keys(%hash)".

Une forme de compatibilité ascendante est fournie via Hash::Util::bucket_ratio() qui fournit le même comportement que scalar(%hash) fourni dans Perl 5.24 et versions antérieures.

"keys" retourné par une subroutine lvalue

"keys" retourné par une subroutine lvalue ne peut plus être assigné dans un contexte de liste.

sub foo : lvalue { keys(%INC) }
(foo) = 3; # erreur
sub bar : lvalue { keys(@_) }
(bar) = 3; # aussi une erreur

Cela rend le cas de la sub lvalue cohérent avec "(keys %hash) = ..." et "(keys @_) = ...", qui sont également des erreurs. [GH #15339] https://github.com/Perl/perl5/issues/15339

La fonctionnalité "${^ENCODING}" a été supprimée

Le comportement spécial associé à l'affectation d'une valeur à cette variable a été supprimé. Par conséquent, le mode par défaut du pragma `encoding` n'est plus pris en charge. Si vous avez toujours besoin d'écrire votre code source dans des encodages autres que UTF-8, utilisez un filtre source tel que Filter::Encoding sur CPAN ou l'option "Filter" d'encoding.

POSIX::tmpnam() a été supprimé

L'interface fondamentalement non sécurisée tmpnam() a été dépréciée dans Perl 5.22 et a maintenant été supprimée. À sa place, vous pouvez utiliser, par exemple, les interfaces de File::Temp.

require ::Foo::Bar est maintenant illégal

Auparavant, "require ::Foo::Bar" essayait de lire /Foo/Bar.pm. Désormais, toute require de mot-clé nu commençant par deux points provoque une erreur.

Les noms de variables de caractères de contrôle littéraux ne sont plus autorisés

Un nom de variable ne peut plus contenir de caractère de contrôle littéral en aucune circonstancces. Ceux-ci étaient précédemment autorisés dans les noms d'un seul caractère sur les plateformes ASCII, mais y étaient dépréciés depuis Perl 5.20. Cela affecte des choses comme "$\cT", où \cT est un caractère de contrôle littéral (tel qu'un caractère "NAK" ou "NEGATIVE ACKNOWLEDGE") dans le code source.

"NBSP" n'est plus autorisé dans "\N{...}"

Le nom d'un caractère ne peut plus contenir d'espaces insécables. Il était déprécié de le faire depuis Perl 5.22.

Dépréciations

Les délimiteurs de chaînes qui ne sont pas des graphes autonomes sont maintenant dépréciés

Pour permettre à Perl d'autoriser éventuellement les délimiteurs de chaînes à être des clusters de graphes Unicode (qui ressemblent à un seul caractère, mais peuvent être une séquence de plusieurs), nous devons cesser d'autoriser un délimiteur à un seul caractère qui n'est pas un graphe en soi. Ceux-ci sont peu susceptibles d'exister dans le code réel, car ils s'afficheraient généralement attachés au caractère qui les précède.

"\cX" qui se mappe vers un caractère imprimable n'est plus déprécié

Cela signifie que nous n'avons pas l'intention de supprimer cette fonctionnalité. Elle déclenche toujours un avertissement, mais uniquement si les avertissements de syntaxe sont activés. La fonctionnalité était initialement destinée à être un moyen d'exprimer des caractères non imprimables qui n'ont pas de mnémonique ("\t" et "\n" sont des mnémoniques pour deux caractères non imprimables, mais la plupart des non-imprimables n'ont pas de mnémonique.) Mais la fonctionnalité peut être utilisée pour spécifier quelques caractères imprimables, bien que ceux-ci soient plus clairement exprimés comme le caractère imprimable lui-même. Voir http://www.nntp.perl.org/group/perl.perl5.porters/2017/02/msg242944.html.

Améliorations des performances

  • Un hash dans un contexte booléen est maintenant parfois plus rapide, par ex. 
    if (!%h) { ... }

    Cela était déjà traité spécialement, mais certains cas ont été manqués (comme "grep %$_, @AoH"), et même ceux qui ne l'étaient pas ont été améliorés.

  • Nouvelle fonction de hachage plus rapide sur les builds 64 bits

    Nous utilisons une fonction de hachage différente pour les clés courtes et longues. Cela devrait améliorer

prove performance and security, especially for long keys.

  • readline est plus rapide

    Lire à partir d'un fichier ligne par ligne avec readline() ou "<>" devrait maintenant être généralement plus rapide grâce à une meilleure implémentation du code qui recherche le prochain caractère de nouvelle ligne.

  • L'assignation d'une référence à une autre, *par exemple* "$ref1 = $ref2" a été optimisée dans certains cas.
  • Suppression de certaines exceptions à la création de chaînes Copy-on-Write. L'algorithme de croissance du tampon de chaîne a été légèrement modifié de sorte que vous êtes moins susceptible de rencontrer une chaîne qui ne peut pas être COWed.
  • Meilleure optimisation de l'assignation de tableaux et de hachages : là où un tableau ou un hachage apparaît dans le membre gauche d'une assignation de liste, comme "(..., @a) = (...);", il est susceptible d'être considérablement plus rapide, surtout s'il implique de vider le tableau/hachage. Par exemple, ce code s'exécute environ un tiers plus vite par rapport à Perl 5.24.0 : 
    my @a;
for my $i (1..10_000_000) {
    @a = (1,2,3);
    @a = ();
}
  • La conversion d'une chaîne à un chiffre en un nombre est maintenant substantiellement plus rapide.
  • La fonction intégrée "split" est maintenant légèrement plus rapide dans de nombreux cas : en particulier pour les deux formes spécialement traitées 
    my    @a = split ...;
local @a = split ...;
  • L'implémentation plutôt lente de la fonctionnalité expérimentale des signatures de sous-rotines a été rendue beaucoup plus rapide ; elle est maintenant comparable en vitesse à la méthode traditionnelle "my ($a, $b, @c) = @_".
  • Les chaînes de littéraux non qualifiés sont maintenant autorisées à participer au pliage de constantes. Elles étaient initialement exemptées du pliage de constantes en août 1999, lors du développement de Perl 5.6, pour garantir que "use strict "subs"" s'appliquerait toujours aux constantes de littéraux non qualifiés. Cela a maintenant été accompli d'une autre manière, de sorte que les littéraux non qualifiés, comme les autres constantes, bénéficient maintenant des avantages en termes de performance du pliage de constantes.

    Cela signifie également que les avertissements de contexte vide sur les expressions constantes de littéraux non qualifiés signalent maintenant l'opérande constant replié, plutôt que l'opération ; cela correspond au comportement des constantes non littérales.

    Changements internes

    • Several new UTF-8 validation functions have been added, all extensions of the "is_utf8_string_*()" fonctions, qui appliquent diverses restrictions à l'UTF-8 reconnu comme valide :

      "is_strict_utf8_string", "is_strict_utf8_string_loc", "is_strict_utf8_string_loclen",

      "is_c9strict_utf8_string", "is_c9strict_utf8_string_loc", "is_c9strict_utf8_string_loclen",

      "is_utf8_string_flags", "is_utf8_string_loc_flags", "is_utf8_string_loclen_flags",

      "is_utf8_fixed_width_buf_flags", "is_utf8_fixed_width_buf_loc_flags", "is_utf8_fixed_width_buf_loclen_flags".

      "is_utf8_invariant_string". "is_utf8_valid_partial_char". "is_utf8_valid_partial_char_flags".

    • Les fonctions "utf8n_to_uvchr" et ses dérivées ont subi plusieurs changements de comportement.

      Les appeler, en passant une longueur de chaîne de 0 est maintenant vérifié dans les builds DE DÉBOGAGE, et sinon, retourne le CARACTÈRE DE REMPLACEMENT Unicode. Si vous n'avez rien à décoder, vous ne devriez pas appeler la fonction de décodage.

      Elles retournent maintenant le CARACTÈRE DE REMPLACEMENT Unicode si elles sont appelées avec un UTF-8 qui présente la malformation de sur-codage et que cette malformation est autorisée par les paramètres d'entrée. Cette malformation se produit lorsque l'UTF-8 semble syntaxiquement valide, mais qu'il existe une séquence plus courte qui produit le même point de code. Ceci est interdit depuis la version 3.1 de Unicode.

      Elles acceptent maintenant un indicateur d'entrée pour autoriser la malformation de dépassement. Cette malformation se produit lorsque l'UTF-8 peut être syntaxiquement valide, mais que le point de code qu'il représente ne peut pas être représenté dans la longueur de mot de la plateforme. Ce que signifie "autorisé" dans ce cas, c'est que la fonction ne retourne pas d'erreur, et elle avance le pointeur d'analyse au-delà de l'UTF-8 en question, mais elle retourne le CARACTÈRE DE REMPLACEMENT Unicode comme valeur du point de code (puisque la valeur réelle n'est pas représentable).

      Elles n'abandonnent plus la recherche d'autres malformations lorsque la première est rencontrée. Un appel à l'une de ces fonctions peut ainsi générer plusieurs diagnostics, au lieu d'un seul.

    • valid_utf8_to_uvchr() a été ajouté à l'API (bien qu'il était présent dans le cœur auparavant). Comme utf8_to_uvchr_buf(), mais suppose que le caractère suivant est bien formé. À utiliser avec prudence.
    • Une nouvelle fonction, "utf8n_to_uvchr_error", a été ajoutée pour être utilisée par les modules qui ont besoin de connaître les détails des malformations UTF-8 au-delà de succès/échec. Auparavant, les seuls moyens de savoir pourquoi une séquence était mal formée étaient de capturer et d'analyser les diagnostics générés ou de faire votre propre analyse.
    • Il existe maintenant une version plus sûre de utf8_hop(), appelée utf8_hop_safe(). Contrairement à utf8_hop(), utf8_hop_safe() ne naviguera pas avant le début ou après la fin du tampon fourni.
    • Deux nouvelles fonctions, utf8_hop_forward() et utf8_hop_back(), sont similaires à utf8_hop_safe() mais sont destinées à lorsque vous savez dans quelle direction vous souhaitez vous déplacer.
    • Deux nouvelles macros qui retournent des séquences d'octets utf8 utiles :

      "BOM_UTF8"

      "REPLACEMENT_CHARACTER_UTF8"

    • Perl est maintenant compilé avec la définition du compilateur "PERL_OP_PARENT" activée par défaut. Pour la désactiver, utilisez la définition du compilateur "PERL_NO_OP_PARENT". Ce drapeau modifie la façon dont le champ "op_sibling" est utilisé dans les structures "OP", et est disponible en option depuis perl 5.22.

      Voir "Internal Changes" dans perl5220delta pour plus de détails sur ce que fait cette option de compilation.

    • Trois nouveaux ops, "OP_ARGELEM", "OP_ARGDEFELEM", et "OP_ARGCHECK" ont été ajoutés. Ils sont principalement destinés à implémenter les éléments individuels d'une signature de sous-routine, ainsi que toute vérification globale requise.
    • L'op "OP_PUSHRE" a été éliminé et l'op "OP_SPLIT" a été changé de la classe "LISTOP" à "PMOP".

      Auparavant, le premier enfant d'un split était un "pushre", qui avait l'expression régulière du "split" attaché. Maintenant, l'expression régulière est attachée directement à l'op "split", et le "pushre" a été éliminé.

    • La fonction API op_class() a été ajoutée. Elle est similaire à la macro existante OP_CLASS(), mais peut déterminer plus précisément à quelle structure un op a été alloué. Par exemple, OP_CLASS() pourrait retourner "OA_BASEOP_OR_UNOP" indiquant que les ops de ce type sont généralement alloués en tant que "OP" ou "UNOP" ; tandis que op_class() retournera "OPclass_BASEOP" ou "OPclass_UNOP" selon le cas.
    • Toutes les parties internes s'accordent maintenant sur le fait que l'op "sassign" est un "BINOP" ; auparavant, il était listé comme un "BASEOP" dans regen/opcodes, ce qui signifiait que plusieurs parties des internes devaient être spécialement traitées pour l'accommoder. La motivation originale de cette bizarrerie était de gérer du code comme "$x ||= 1" ; cela est maintenant géré de manière plus simple.
    • Le format de sortie de la fonction op_dump() (telle qu'utilisée par "perl -Dx") a changé : elle affiche maintenant une structure arborescente en "ASCII art", et montre plus de détails de bas niveau sur chaque op, tels que son adresse et sa classe.
    • Le type "PADOFFSET" est passé d'unsigned à signed, et plusieurs variables liées aux pads comme "PL_padix" sont passées du type "I32" au type "PADOFFSET".
    • La sortie en mode "DEBUGGING" pour la compilation et l'exécution des expressions régulières a été améliorée.
    • Plusieurs indicateurs SV obscurs ont été éliminés, parfois avec les macros qui les manipulent : "SVpbm_VALID", "SVpbm_TAIL", "SvTAIL_on", "SvTAIL_off", "SVrepl_EVAL", "SvEVALED".
    • Un indicateur "op_private" de l'OP "OPpRUNTIME" a été éliminé. Il était souvent défini sur les "PMOP" ops, mais était devenu dénué de sens au fil du temps.
