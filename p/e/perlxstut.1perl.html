PERLXSTUT(1perl) Guide de référence pour programmeurs Perl PERLXSTUT(1perl)

NOM

perlxstut - Tutoriel pour écrire des XSUBs

DESCRIPTION

Ce tutoriel a pour but d'éduquer le lecteur sur les étapes impliquées dans la création d'une extension Perl. Le lecteur est supposé avoir accès à perlguts, perlclib, perlapi et perlxs.

Ce tutoriel commence par des exemples très simples et devient plus complexe, chaque nouvel exemple ajoutant de nouvelles fonctionnalités. Certains concepts peuvent ne pas être entièrement expliqués avant la fin du tutoriel afin d'initier progressivement le lecteur à la création d'extensions.

Ce tutoriel a été écrit d'un point de vue Unix. Lorsque je connais des différences pour d'autres plateformes (par exemple, Win32), je les listerai. Si vous trouvez quelque chose qui a été omis, merci de me le faire savoir.

NOTES SPÉCIALES

make

Ce tutoriel suppose que le programme "make" utilisé par Perl est appelé "make". Au lieu d'exécuter "make" dans les exemples suivants, vous devrez peut-être substituer le programme "make" pour lequel Perl a été configuré. L'exécution de perl -V:make devrait vous indiquer lequel c'est.

Avertissement de version

Lorsque vous écrivez une extension Perl destinée à être utilisée par le grand public, vous devez vous attendre à ce que l'extension soit utilisée avec des versions de Perl différentes de celle disponible sur votre machine. Puisque vous lisez ce document, la version de Perl sur votre machine est probablement 5.005 ou ultérieure, mais les utilisateurs de votre extension peuvent avoir des versions plus anciennes.

Pour comprendre quels types d'incompatibilités vous pouvez rencontrer, et dans le cas rare où la version de Perl sur votre machine est antérieure à ce document, consultez la section sur le "Dépannage de ces exemples" pour plus d'informations.

Si votre extension utilise des fonctionnalités de Perl qui ne sont pas disponibles sur les anciennes versions de Perl, vos utilisateurs apprécieront un avertissement significatif et précoce. Vous pourriez probablement mettre cette information dans le fichier README, mais de nos jours, l'installation des extensions peut être effectuée automatiquement, guidée par le module CPAN.pm ou d'autres outils.

Dans les installations basées sur MakeMaker, Makefile.PL offre la première opportunité d'effectuer des vérifications de version. On peut y mettre quelque chose comme ceci à cette fin :

eval { require 5.007 }
    or die <<EOD;
############
### Ce module utilise le framework de frobnication qui n'est pas disponible
### avant la version 5.007 de Perl. Mettez à jour votre Perl avant
### d'installer Kara::Mba.
############
EOD

Chargement dynamique vs Chargement statique

Il est couramment pensé que si un système n'a pas la capacité de charger une bibliothèque dynamiquement, vous ne pouvez pas construire de XSUBs. Ceci est incorrect. Vous *pouvez* les construire, mais vous devez lier les sous-routines XSUB avec le reste de Perl, créant ainsi un nouvel exécutable. Cette situation est similaire à celle de Perl 4.

Ce tutoriel peut toujours être utilisé sur un tel système. Le mécanisme de construction des XSUBs vérifiera le système et construira une bibliothèque dynamiquement chargeable si possible, ou sinon une bibliothèque statique et ensuite, optionnellement, un nouvel exécutable lié statiquement avec cette bibliothèque statique.

Si vous souhaitez construire un exécutable lié statiquement sur un système capable de charger des bibliothèques dynamiquement, vous pouvez, dans tous les exemples suivants, là où la commande ""make"" sans arguments est exécutée, exécuter plutôt la commande ""make perl"".

Si vous avez généré un tel exécutable lié statiquement par choix, alors au lieu de dire ""make test"", vous devriez dire ""make test_static"". Sur les systèmes qui ne peuvent pas construire de bibliothèques dynamiquement chargeables, dire simplement ""make test"" est suffisant.

Threads et PERL_NO_GET_CONTEXT

Pour les constructions multi-threads, perl nécessite le pointeur de contexte pour le thread actuel, sans "PERL_NO_GET_CONTEXT", perl appellera une fonction pour récupérer le contexte.

Pour des performances améliorées, incluez :

#define PERL_NO_GET_CONTEXT

comme montré ci-dessous.

Pour plus de détails, voir perlguts.

EXEMPLE 1

Notre première extension sera très simple. Lorsque nous appellerons la routine de l'extension, elle affichera un message bien connu et retournera.

Exécutez ""h2xs -A -n Mytest"". Cela crée un répertoire nommé Mytest, éventuellement sous ext/ si ce répertoire existe dans le répertoire de travail actuel. Plusieurs fichiers seront créés sous le répertoire Mytest, y compris MANIFEST, Makefile.PL, lib/Mytest.pm, Mytest.xs, t/Mytest.t et Changes.

Le fichier MANIFEST contient les noms de tous les fichiers qui viennent d'être créés dans le répertoire Mytest.

Le fichier Makefile.PL devrait ressembler à ceci :

use ExtUtils::MakeMaker;
# See lib/ExtUtils::MakeMaker.pm for details of how to influence
# the contents of the Makefile that is written.
WriteMakefile(
    NAME         => 'Mytest',
    VERSION_FROM => 'Mytest.pm', # finds $VERSION
    LIBS         => [''],        # e.g., '-lm'
    DEFINE       => '',          # e.g., '-DHAVE_SOMETHING'
    INC          => '-I',        # e.g., '-I. -I/usr/include/other'
);

Le fichier Mytest.pm devrait commencer par quelque chose comme ceci :

package Mytest;
use 5.008008;
use strict;
use warnings;
require Exporter;
our @ISA = qw(Exporter);
our %EXPORT_TAGS = ( 'all' => [ qw(
) ] );
our @EXPORT_OK = ( @{ $EXPORT_TAGS{'all'} } );
our @EXPORT = qw(
);
our $VERSION = '0.01';
require XSLoader;
XSLoader::load('Mytest', $VERSION);
# Preloaded methods go here.
1;
__END__
# Below is the stub of documentation for your module. You better
# edit it!

Le reste du fichier .pm contient un exemple de code pour fournir la documentation de l'extension.

Enfin, le fichier Mytest.xs devrait ressembler à ceci :

#define PERL_NO_GET_CONTEXT
#include "EXTERN.h"
#include "perl.h"
#include "XSUB.h"
#include "ppport.h"
MODULE = Mytest             PACKAGE = Mytest

Modifions le fichier .xs en ajoutant ceci à la fin du fichier :

void
hello()
    CODE:
        printf("Hello, world!\n");

Il est acceptable que les lignes commençant par la ligne "CODE:" ne soient pas indentées. Cependant, pour des raisons de lisibilité, il est suggéré d'indenter CODE: d'un niveau et les lignes suivantes d'un niveau supplémentaire.

Maintenant, nous exécuterons ""perl Makefile.PL"". Cela créera un vrai Makefile, dont make a besoin. Son résultat ressemble à ceci :

% perl Makefile.PL
Checking if your kit is complete...
Looks good
Writing Makefile for Mytest
%

Maintenant, exécuter make produira une sortie qui ressemblera à ceci (certaines longues lignes ont été raccourcies pour plus de clarté et certaines lignes superflues ont été supprimées) :

% make
cp lib/Mytest.pm blib/lib/Mytest.pm
perl xsubpp  -typemap typemap  Mytest.xs > Mytest.xsc && \
mv Mytest.xsc Mytest.c

cc -c     Mytest.c

chmod 644 Mytest.bs
rm -f blib/arch/auto/Mytest/Mytest.so
cc -shared -L/usr/local/lib Mytest.o -o blib/arch/auto/Mytest/Mytest.so
chmod 755 blib/arch/auto/Mytest/Mytest.so
cp Mytest.bs blib/arch/auto/Mytest/Mytest.bs
chmod 644 blib/arch/auto/Mytest/Mytest.bs
Manifying blib/man3/Mytest.3pm
%

Vous pouvez ignorer sans risque la ligne concernant le "comportement de prototypage" - elle est expliquée dans "The PROTOTYPES: Keyword" dans perlxs.

Perl a sa propre manière spéciale d'écrire facilement des scripts de test, mais pour cet exemple uniquement, nous allons créer notre propre script de test. Créez un fichier nommé hello qui ressemble à ceci :

#! /opt/perl5/bin/perl
use ExtUtils::testlib;
use Mytest;
Mytest::hello();

Maintenant, nous rendons le script exécutable ("chmod +x hello"), nous exécutons le script et nous devrions voir la sortie suivante :

% ./hello
Hello, world!
%

Dans cet exemple, nous allons créer une fonction qui prend un argument, le double, et renvoie le résultat. Nous allons utiliser un seul argument à la fois.

Vous pouvez ajouter le code suivant à la fin du fichier Mytest.xs :

int
double(x)
    int x
    CODE:
        return x * 2;

La ligne "int x" indique que nous attendons un entier comme premier argument, et que nous allons le référencer avec le nom "x". La ligne "return x * 2;" est le code C réel qui sera exécuté.

Modifions le fichier lib/Mytest.pm. Nous devons ajouter "double" à la liste d'exportation et à la liste d'exportation par défaut.

our @EXPORT = qw(

);

Exécutez maintenant ""make"" et ""make test"". Ensuite, créez un nouveau fichier de test appelé "doubletest" et exécutez-le.

#! /opt/perl5/bin/perl
use ExtUtils::testlib;

Maintenant, nous allons créer une fonction qui prend une chaîne de caractères comme argument, la convertit en majuscules, et renvoie la chaîne convertie.

Ajoutez le code suivant à la fin de "Mytest.xs" :

char *
str_to_upper(s)
    char *s
    CODE:
        char *ptr = Perl_str_toupper(aTHX_ s);

Notez que nous utilisons "char *" pour indiquer que nous prenons une chaîne de caractères en entrée et que nous renvoyons une chaîne de caractères. EXEMPLE 2

Ajoutons maintenant à notre extension une sous-routine qui prendra un unique argument numérique en entrée et retournera 1 si le nombre est pair ou 0 s'il est impair.

Ajoutez ce qui suit à la fin de Mytest.xs :

int
is_even(input)
        int input
    CODE:
        RETVAL = (input % 2 == 0);
    OUTPUT:
        RETVAL

Il n'est pas nécessaire qu'il y ait d'espace blanc au début de la ligne ""int input"", mais c'est utile pour améliorer la lisibilité. Placer un point-virgule à la fin de cette ligne est également facultatif. N'importe quelle quantité et type d'espace blanc peut être placé entre ""int"" et ""input"".

Réexécutez maintenant make pour reconstruire notre nouvelle bibliothèque partagée.

Effectuez maintenant les mêmes étapes qu'auparavant, en générant un Makefile à partir du fichier Makefile.PL et en exécutant make.

Afin de tester le bon fonctionnement de notre extension, nous devons maintenant examiner le fichier Mytest.t. Ce fichier est configuré pour imiter le même type de structure de test que Perl lui-même. Dans le script de test, vous effectuez un certain nombre de tests pour confirmer le comportement de l'extension, en affichant "ok" lorsque le test est correct, "not ok" lorsqu'il ne l'est pas.

use Test::More tests => 4;
BEGIN { use_ok('Mytest') };
#########################
# Insérez votre code de test ci-dessous, le module Test::More est use()d ici
# lisez donc sa page de manuel ( perldoc Test::More ) pour obtenir de l'aide sur l'écriture de ce
# script de test.
is( Mytest::is_even(0), 1 );
is( Mytest::is_even(1), 0 );
is( Mytest::is_even(2), 1 );

Nous appellerons le script de test via la commande ""make test"". Vous devriez voir une sortie ressemblant à ceci :

Ce qui s'est passé ?

Le programme h2xs est le point de départ de la création d'extensions. Dans les exemples ultérieurs, nous verrons comment nous pouvons utiliser h2xs pour lire des fichiers d'en-tête et générer des modèles pour se connecter à des routines C.

h2xs crée un certain nombre de fichiers dans le répertoire de l'extension. Le fichier Makefile.PL est un script perl qui générera un véritable Makefile pour construire l'extension. Nous y regarderons de plus près plus tard.

Les fichiers .pm et .xs contiennent la substance de l'extension. Le fichier .xs contient les routines C qui composent l'extension. Le fichier .pm contient des routines qui indiquent à Perl comment charger votre extension.

La génération du Makefile et l'exécution de "make" ont créé un répertoire appelé blib (qui signifie "build library") dans le répertoire de travail actuel. Ce répertoire contiendra la bibliothèque partagée que nous allons construire. Une fois que nous l'aurons testée, nous pourrons l'installer à son emplacement final.

L'invocation du script de test via ""make test"" a fait quelque chose de très important. Elle a invoqué perl avec tous ces arguments "-I" afin qu'il puisse trouver les différents fichiers qui font partie de l'extension. Il est *très* important que, tant que vous testez des extensions, vous utilisiez ""make test"". Si vous essayez d'exécuter le script de test tout seul, vous obtiendrez une erreur fatale. Une autre raison pour laquelle il est important d'utiliser ""make test"" pour exécuter votre script de test est que si vous testez une mise à niveau d'une version déjà existante, l'utilisation de ""make test"" garantit que vous testerez votre nouvelle extension, et non la version déjà existante.

Lorsque Perl voit un "use extension;", il recherche un fichier portant le même nom que l'extension "use"d et qui a le suffixe .pm. Si ce fichier ne peut pas être trouvé, Perl meurt avec une erreur fatale. Le chemin de recherche par défaut est contenu dans le tableau @INC.

Dans notre cas, Mytest.pm indique à perl qu'il aura besoin des extensions Exporter et Dynamic Loader. Il définit ensuite les tableaux @ISA et @EXPORT ainsi que le scalaire $VERSION ; enfin, il indique à perl d'amorcer le module. Perl appellera sa routine de chargement dynamique (s'il y en a une) et chargera la bibliothèque partagée.

Les deux tableaux @ISA et @EXPORT sont très importants. Le tableau @ISA contient une liste d'autres paquets dans lesquels rechercher des méthodes (ou des sous-routines) qui n'existent pas dans le paquet actuel. Ceci est généralement important uniquement pour les extensions orientées objet (dont nous parlerons beaucoup plus tard), et donc n'a généralement pas besoin d'être modifié.

Le tableau @EXPORT indique à Perl quelles variables et sous-routines de l'extension doivent être placées dans l'espace de noms du paquet appelant. Comme vous ne savez pas si l'utilisateur a déjà utilisé vos noms de variables et de sous-routines, il est d'une importance vitale de sélectionner soigneusement ce qu'il faut exporter. N'exportez *pas* les noms de méthodes ou de variables *par défaut* sans une bonne raison.

En règle générale, si le module essaie d'être orienté objet, n'exportez rien. S'il s'agit simplement d'une collection de fonctions et de variables, vous pouvez les exporter via un autre tableau, appelé @EXPORT_OK. Ce tableau ne place pas automatiquement ses noms de sous-routines et de variables dans l'espace de noms, sauf si l'utilisateur demande spécifiquement que cela soit fait.

Voir perlmod pour plus d'informations.

La variable $VERSION est utilisée pour s'assurer que le fichier .pm et la bibliothèque partagée sont "synchronisés" l'un avec l'autre. Chaque fois que vous apportez des modifications aux fichiers .pm ou .xs, vous devez incrémenter la valeur de cette variable.

Écrire de bons scripts de test

L'importance d'écrire de bons scripts de test ne peut être suffisamment soulignée. Vous devriez suivre de près le style "ok/not ok" que Perl utilise lui-même, afin qu'il soit très facile et sans ambiguïté de déterminer le résultat de chaque cas de test. Lorsque vous trouvez et corrigez un bug, assurez-vous d'y ajouter un cas de test.

En exécutant ""make test"", vous vous assurez que votre script Mytest.t s'exécute et utilise la bonne version de votre extension. Si vous avez de nombreux cas de test, enregistrez vos fichiers de test dans le répertoire "t" et utilisez le suffixe ".t". Lorsque vous exécutez ""make test"", tous ces fichiers de test seront exécutés.

EXEMPLE 3

Notre troisième extension prendra un argument comme entrée, arrondira cette valeur et définira l'*argument* à la valeur arrondie.

Ajoutez ce qui suit à la fin de Mytest.xs :

void
round(arg)
        double  arg
    CODE:
        if (arg > 0.0) {
                arg = floor(arg + 0.5);
        } else if (arg < 0.0) {
                arg = ceil(arg - 0.5);
        } else {
                arg = 0.0;
        }
    OUTPUT:
        arg

Modifiez le fichier Makefile.PL afin que la ligne correspondante ressemble à ceci :

LIBS      => ['-lm'],   # par exemple, '-lm'

Générez le Makefile et exécutez make. Changez le numéro de test dans Mytest.t en "9" et ajoutez les tests suivants :

my $i;
$i = -1.5;
Mytest::round($i);
is( $i, -2.0, 'Arrondir -1.5 à -2.0' );
$i = -1.1;
Mytest::round($i);
is( $i, -1.0, 'Arrondir -1.1 à -1.0' );
$i = 0.0;
Mytest::round($i);
is( $i, 0.0, 'Arrondir 0.0 à 0.0' );
$i = 0.5;
Mytest::round($i);
is( $i, 1.0, 'Arrondir 0.5 à 1.0' );
$i = 1.2;
Mytest::round($i);
is( $i, 1.0, 'Arrondir 1.2 à 1.0' );

L'exécution de ""make test"" devrait maintenant afficher que les neuf tests sont ok.

Notez que dans ces nouveaux cas de test, l'argument passé à round était une variable scalaire. Vous vous demandez peut-être si vous pouvez arrondir une constante ou une valeur littérale. Pour voir ce qui se passe, ajoutez temporairement la ligne suivante à Mytest.t :

Mytest::round(3);

Exécutez ""make test"" et notez que Perl meurt avec une erreur fatale. Perl ne vous laissera pas modifier la valeur des constantes !

Quoi de neuf ici ?

  • Nous avons apporté quelques modifications à Makefile.PL. Dans ce cas, nous avons spécifié une bibliothèque supplémentaire à lier à la bibliothèque partagée de l'extension, la bibliothèque mathématique libm dans ce cas. Nous parlerons plus tard de la façon d'écrire des XSUBs qui peuvent appeler toutes les routines d'une bibliothèque.
  • La valeur de la fonction n'est pas renvoyée comme valeur de retour de la fonction, mais en modifiant la valeur de la variable qui a été passée à la fonction. Vous auriez pu le deviner en voyant que la valeur de retour de round est de type "void".

Paramètres d'entrée et de sortie

Vous spécifiez les paramètres qui seront passés à l'XSUB sur la ou les lignes suivant la déclaration de la valeur de retour et du nom de la fonction. Chaque ligne de paramètre d'entrée commence par un espace blanc facultatif et peut avoir un point-virgule final facultatif.

La liste des paramètres de sortie se trouve à la toute fin de la fonction, juste après la directive OUTPUT:. L'utilisation de RETVAL indique à Perl que vous souhaitez renvoyer cette valeur comme valeur de retour de la fonction XSUB. Dans l'exemple 3, nous voulions que la "valeur de retour" soit placée dans la variable d'origine que nous avons passée, nous l'avons donc listée (et non RETVAL) dans la section OUTPUT:.

Le programme XSUBPP

Le programme xsubpp prend le code XS du fichier .xs et le traduit en code C, le plaçant dans un fichier dont le suffixe est .c. Le code C généré utilise intensivement les fonctions C de Perl.

Le fichier TYPEMAP

Le programme xsubpp utilise des règles pour convertir les types de données de Perl (scalaire, tableau, etc.) en types de données C (int, char, etc.). Ces règles sont stockées dans le fichier typemap ($PERLLIB/ExtUtils/typemap). Il y a une brève discussion ci-dessous, mais tous les détails techniques peuvent être trouvés dans perlxstypemap. Si vous avez une version suffisamment récente de perl (5.16 et supérieur) ou un XS mis à jour

compiler ("ExtUtils::ParseXS" 3.13_01 ou mieux), vous pouvez intégrer des typemaps dans votre XS au lieu d'écrire des fichiers séparés. Dans tous les cas, cette chose de typemap est divisée en trois parties :

La première section mappe divers types de données C à un nom, qui correspond quelque peu aux divers types Perl. La deuxième section contient du code C que xsubpp utilise pour gérer les paramètres d'entrée. La troisième section contient du code C que xsubpp utilise pour gérer les paramètres de sortie.

Jetons un coup d'œil à une partie du fichier .c créé pour notre extension. Le nom du fichier est Mytest.c :

XS(XS_Mytest_round)
{
    dXSARGS;
    if (items != 1)
        Perl_croak(aTHX_ "Usage: Mytest::round(arg)");
    PERL_UNUSED_VAR(cv); /* -W */
    {
        double  arg = (double)SvNV(ST(0));      /* XXXXX */
        if (arg > 0.0) {
                arg = floor(arg + 0.5);
        } else if (arg < 0.0) {
                arg = ceil(arg - 0.5);
        } else {
                arg = 0.0;
        }
        sv_setnv(ST(0), (double)arg);   /* XXXXX */
        SvSETMAGIC(ST(0));
    }
    XSRETURN_EMPTY;
}

Notez les deux lignes commentées avec "XXXXX". Si vous vérifiez la première partie du fichier typemap (ou section), vous verrez que les doubles sont de type T_DOUBLE. Dans la partie INPUT du typemap, un argument qui est T_DOUBLE est assigné à la variable arg en appelant la routine SvNV sur quelque chose, puis en le castant en double, puis assigné à la variable arg. De même, dans la section OUTPUT, une fois que arg a sa valeur finale, elle est passée à la fonction sv_setnv pour être renvoyée à la sous-routine appelante. Ces deux fonctions sont expliquées dans perlguts ; nous parlerons plus tard de ce que signifie "ST(0)" dans la section sur la pile d'arguments.

Avertissement concernant les arguments de sortie

En général, ce n'est pas une bonne idée d'écrire des extensions qui modifient leurs paramètres d'entrée, comme dans l'Exemple 3. Au lieu de cela, vous devriez probablement retourner plusieurs valeurs dans un tableau et laisser l'appelant les gérer (nous le ferons dans un exemple ultérieur). Cependant, afin de mieux s'adapter à l'appel de routines C préexistantes, qui modifient souvent leurs paramètres d'entrée, ce comportement est toléré.

EXEMPLE 4

Dans cet exemple, nous allons commencer à écrire des XSUB qui interagiront avec des bibliothèques C prédéfinies. Pour commencer, nous allons créer une petite bibliothèque de notre propre création, puis laisser h2xs écrire nos fichiers .pm et .xs pour nous.

Créez un nouveau répertoire appelé Mytest2 au même niveau que le répertoire Mytest. Dans le répertoire Mytest2, créez un autre répertoire appelé mylib, et déplacez-vous dans ce répertoire.

Ici, nous allons créer des fichiers qui généreront une bibliothèque de test. Ceux-ci incluront un fichier source C et un fichier d'en-tête. Nous créerons également un Makefile.PL dans ce répertoire. Ensuite, nous nous assurerons que l'exécution de make au niveau Mytest2 exécutera automatiquement ce fichier Makefile.PL et le Makefile résultant.

Dans le répertoire mylib, créez un fichier mylib.h qui ressemble à ceci :

#define TESTVAL 4
extern double   foo(int, long, const char*);

Créez également un fichier mylib.c qui ressemble à ceci :

#include <stdlib.h>
#include "mylib.h"
double
foo(int a, long b, const char *c)
{
        return (a + b + atof(c) + TESTVAL);
}

Et enfin, créez un fichier Makefile.PL qui ressemble à ceci :

use ExtUtils::MakeMaker;
$Verbose = 1;
WriteMakefile(
    NAME  => 'Mytest2::mylib',
    SKIP  => [qw(all static static_lib dynamic dynamic_lib)],
    clean => {'FILES' => 'libmylib$(LIB_EXT)'},
);
sub MY::top_targets {
        '
all :: static
pure_all :: static
static ::       libmylib$(LIB_EXT)
libmylib$(LIB_EXT): $(O_FILES)
        $(AR) cr libmylib$(LIB_EXT) $(O_FILES)
        $(RANLIB) libmylib$(LIB_EXT)
';
}

Assurez-vous d'utiliser une tabulation et non des espaces sur les lignes commençant par "$(AR)" et "$(RANLIB)". Make ne fonctionnera pas correctement si vous utilisez des espaces. Il a également été rapporté que l'argument "cr" pour $(AR) est inutile sur les systèmes Win32.

Nous allons maintenant créer les fichiers principaux de Mytest2. Changez de répertoire pour vous placer au-dessus de Mytest2 et exécutez la commande suivante :

% h2xs -O -n Mytest2 Mytest2/mylib/mylib.h

Cela affichera un avertissement concernant l'écrasement de Mytest2, mais ce n'est pas grave. Nos fichiers sont stockés dans Mytest2/mylib et ne seront pas touchés.

Le Makefile.PL normal généré par h2xs ne connaît pas le répertoire mylib. Nous devons lui indiquer qu'il existe un sous-répertoire et que nous allons y générer une bibliothèque. Ajoutons l'argument MYEXTLIB à l'appel de WriteMakefile pour qu'il ressemble à ceci :

WriteMakefile(
    NAME         => 'Mytest2',
    VERSION_FROM => 'Mytest2.pm', # trouve $VERSION
    LIBS         => [''],   # par exemple, '-lm'
    DEFINE       => '',     # par exemple, '-DHAVE_SOMETHING'
    INC          => '',     # par exemple, '-I/usr/include/other'
    MYEXTLIB     => 'mylib/libmylib$(LIB_EXT)',
);

et puis à la fin, ajoutez une sous-routine (qui remplacera la sous-routine préexistante). N'oubliez pas d'utiliser un caractère de tabulation pour indenter la ligne commençant par "cd" !

sub MY::postamble {
'
$(MYEXTLIB): mylib/Makefile
        cd mylib && $(MAKE) $(PASSTHRU)
';
}

Corrigeons également le fichier MANIFEST en ajoutant les trois lignes suivantes :

mylib/Makefile.PL
mylib/mylib.c
mylib/mylib.h

Afin de garder notre espace de noms propre et non pollué, éditez le fichier .pm et changez la variable @EXPORT en @EXPORT_OK. Enfin, dans le fichier .xs, éditez la ligne #include pour qu'elle dise :

#include "mylib/mylib.h"

Et ajoutez également la définition de fonction suivante à la fin du fichier .xs :

double
foo(a,b,c)
        int             a
        long            b
        const char *    c
    OUTPUT:
        RETVAL

Nous devons maintenant également créer un typemap car le Perl par défaut ne prend pas encore en charge le type "const char *". Incluez une nouvelle section TYPEMAP dans votre code XS avant la fonction ci-dessus :

TYPEMAP: <<END
const char *    T_PV
END

Exécutez maintenant perl sur le Makefile.PL de niveau supérieur. Notez qu'il a également créé un Makefile dans le répertoire mylib. Exécutez make et observez qu'il se déplace dans le répertoire mylib et exécute make là-bas également.

Modifiez maintenant le script Mytest2.t et changez le nombre de tests à "5", et ajoutez les lignes suivantes à la fin du script :

is( Mytest2::foo( 1, 2, "Hello, world!" ), 7 );
is( Mytest2::foo( 1, 2, "0.0" ),           7 );
ok( abs( Mytest2::foo( 0, 0, "-3.4" ) - 0.6 ) <= 0.01 );

(Lors de la comparaison de nombres à virgule flottante, il est préférable de ne pas vérifier l'égalité, mais plutôt que la différence entre le résultat attendu et le résultat réel est inférieure à un certain montant (appelé epsilon) qui est de 0.01 dans ce cas)

Exécutez ""make test"" et tout devrait bien se passer. Il y a quelques avertissements sur les tests manquants pour l'extension Mytest2::mylib, mais vous pouvez les ignorer.

Qu'est-ce qui s'est passé ici ?

Contrairement aux exemples précédents, nous avons maintenant exécuté h2xs sur un vrai fichier d'inclusion. Cela a provoqué l'apparition de quelques extras dans les fichiers .pm et .xs.

  • Dans le fichier .xs, il y a maintenant une directive #include avec le chemin absolu du fichier d'en-tête mylib.h. Nous l'avons changé en chemin relatif afin de pouvoir déplacer le répertoire d'extension si nous le souhaitions.
  • Il y a maintenant du nouveau code C ajouté au fichier .xs. Le but de la routine "constant" est de rendre les valeurs qui sont #define'd dans le fichier d'en-tête accessibles par le script Perl (en appelant soit "TESTVAL", soit &Mytest2::TESTVAL). Il y a aussi du code XS pour permettre des appels à la routine "constant".
  • Le fichier .pm exportait à l'origine le nom "TESTVAL" dans le tableau @EXPORT. Cela pourrait entraîner des conflits de noms. Une règle générale est que si le #define doit seulement être utilisé par les routines C elles-mêmes, et non par l'utilisateur, il doit être retiré du tableau @EXPORT. Alternativement, si vous ne voyez pas d'inconvénient à utiliser le "nom qualifié complet" d'une variable, vous pourriez déplacer la plupart ou la totalité des éléments du tableau @EXPORT dans le tableau @EXPORT_OK.
  • Si notre fichier d'inclusion avait contenu des directives #include, celles-ci n'auraient pas été traitées par h2xs. Il n'y a pas de bonne solution pour cela pour le moment.
  • Nous avons également informé Perl de la bibliothèque que nous avons créée dans le sous-répertoire mylib. Cela a nécessité uniquement l'ajout de la variable "MYEXTLIB" à l'appel de WriteMakefile et le remplacement de la sous-routine postamble pour se déplacer dans le sous-répertoire et exécuter make. Le Makefile.PL pour la bibliothèque est un peu plus compliqué, mais pas excessivement. Encore une fois, nous avons remplacé la sous-routine postamble pour insérer notre propre code. Ce code spécifiait simplement que la bibliothèque à créer ici était une bibliothèque d'archives statique (par opposition à une bibliothèque chargeable dynamiquement) et fournissait les commandes pour la construire.

Anatomie d'un fichier .xs

Le fichier .xs de "EXEMPLE 4" contenait de nouveaux éléments. Pour comprendre la signification de ces éléments, prêtez attention à la ligne qui dit

MODULE = Mytest2                PACKAGE = Mytest2

Tout ce qui précède cette ligne est du code C brut qui décrit quels en-têtes inclure, et définit des fonctions pratiques. Aucune traduction n'est effectuée sur cette partie, à part le fait que la documentation POD intégrée est ignorée (voir perlpod) ; elle va dans le fichier C généré tel quel.

Tout ce qui suit cette ligne est la description des fonctions XSUB. Ces descriptions sont traduites par xsubpp en code C qui implémente ces fonctions en utilisant les conventions d'appel Perl, et qui rend ces fonctions visibles depuis l'interpréteur Perl.

Portez une attention particulière à la fonction "constant". Ce nom apparaît deux fois dans le fichier .xs généré : une fois dans la première partie, en tant que fonction C statique, puis une autre fois dans la seconde partie, lorsqu'une interface XSUB à cette fonction C statique est définie.

C'est assez typique pour les fichiers .xs : généralement, le fichier .xs fournit une interface à une fonction C existante. Ensuite, cette fonction C est définie quelque part (soit dans une bibliothèque externe, soit dans la première partie du fichier .xs

ile), et une interface Perl pour cette fonction (c'est-à-dire, « colle Perl ») est décrite dans la seconde partie du fichier .xs. La situation dans « EXEMPLE 1 », « EXEMPLE 2 », et « EXEMPLE 3 », où tout le travail est effectué dans la « colle Perl », est plutôt une exception qu'une règle.

Sortir le gras des XSUBs

Dans « EXEMPLE 4 », la seconde partie du fichier .xs contenait la description suivante d'un XSUB :

double
foo(a,b,c)
        int             a
        long            b
        const char *    c
    OUTPUT:
        RETVAL

Notez que, contrairement aux « EXEMPLE 1 », « EXEMPLE 2 » et « EXEMPLE 3 », cette description ne contient pas le *code* réel de ce qui est fait lors d'un appel à la fonction Perl foo(). Pour comprendre ce qui se passe ici, on peut ajouter une section CODE à ce XSUB :

double
foo(a,b,c)
        int             a
        long            b
        const char *    c
    CODE:
        RETVAL = foo(a,b,c);
    OUTPUT:
        RETVAL

Cependant, ces deux XSUBs fournissent un code C généré quasi identique : le compilateur xsubpp est assez intelligent pour déduire la section "CODE:" des deux premières lignes de la description du XSUB. Qu'en est-il de la section "OUTPUT:" ? En fait, c'est absolument la même chose ! La section "OUTPUT:" peut également être supprimée, *tant que* la section "CODE:" ou la section "PPCODE:" n'est pas spécifiée : xsubpp peut voir qu'il doit générer une section d'appel de fonction et générera également la section OUTPUT automatiquement. Ainsi, on peut raccourcir le XSUB pour qu'il devienne :

double
foo(a,b,c)
        int             a
        long            b
        const char *    c

Peut-on faire de même avec un XSUB

int
is_even(input)
        int     input
    CODE:
        RETVAL = (input % 2 == 0);
    OUTPUT:
        RETVAL

de l'« EXEMPLE 2 » ? Pour ce faire, il faut définir une fonction C "int is_even(int input)". Comme nous l'avons vu dans « Anatomie d'un fichier .xs », l'endroit approprié pour cette définition est la première partie du fichier .xs. En fait, une fonction C

int
is_even(int arg)
{
        return (arg % 2 == 0);
}

est probablement exagérée pour cela. Quelque chose d'aussi simple qu'un "#define" fera également l'affaire :

#define is_even(arg)    ((arg) % 2 == 0)

Après avoir ajouté ceci à la première partie du fichier .xs, la partie « colle Perl » devient aussi simple que

int
is_even(input)
        int     input

Cette technique de séparation de la partie colle de la partie exécutrice a des compromis évidents : si vous voulez changer une interface Perl, vous devez changer deux endroits dans votre code. Cependant, elle supprime beaucoup d'encombrement et rend la partie exécutrice indépendante des idiosyncrasies de la convention d'appel Perl. (En fait, il n'y a rien de spécifique à Perl dans la description ci-dessus, une version différente de xsubpp aurait pu la traduire en colle TCL ou en colle Python.)

En savoir plus sur les arguments XSUB

Avec la finalisation de l'Exemple 4, nous avons maintenant un moyen facile de simuler certaines bibliothèques réelles dont les interfaces peuvent ne pas être les plus propres au monde. Nous allons maintenant continuer avec une discussion sur les arguments passés au compilateur xsubpp.

Lorsque vous spécifiez des arguments aux routines dans le fichier .xs, vous passez en réalité trois informations pour chaque argument listé. La première information est l'ordre de cet argument par rapport aux autres (premier, deuxième, etc.). La seconde est le type de l'argument, et consiste en la déclaration du type de l'argument (par exemple, int, char*, etc.). La troisième information est la convention d'appel pour l'argument dans l'appel à la fonction de la bibliothèque.

Alors que Perl passe les arguments aux fonctions par référence, C passe les arguments par valeur ; pour implémenter une fonction C qui modifie des données de l'un des « arguments », l'argument réel de cette fonction C serait un pointeur vers les données. Ainsi, deux fonctions C avec les déclarations

int string_length(char *s);
int upper_case_char(char *cp);

peuvent avoir des sémantiques complètement différentes : la première peut inspecter un tableau de caractères pointé par s, et la seconde peut directement déréférencer "cp" et manipuler seulement *cp (en utilisant la valeur de retour comme indicateur de succès, par exemple). Depuis Perl, on utiliserait ces fonctions de manière complètement différente.

On transmet cette information à xsubpp en remplaçant "*" avant l'argument par "&". "&" signifie que l'argument doit être passé à une fonction de bibliothèque par son adresse. Les deux fonctions ci-dessus peuvent être transformées en XSUB comme suit :

int
string_length(s)
        char *  s
int
upper_case_char(cp)
        char    &cp

Par exemple, considérons :

int
foo(a,b)
        char    &a
        char *  b

Le premier argument Perl à cette fonction serait traité comme un char et assigné à la variable a, et son adresse serait passée à la fonction foo. Le second argument Perl serait traité comme un pointeur de chaîne et assigné à la variable b. La *valeur* de b serait passée à la fonction foo. L'appel réel à la fonction foo que xsubpp génère ressemblerait à ceci :

foo(&a, b);

xsubpp analysera les listes d'arguments de fonction suivantes de manière identique :

char    &a
char&a
char    & a

Cependant, pour faciliter la compréhension, il est suggéré de placer un « & » à côté du nom de la variable et loin du type de la variable), et de placer un « * » près du type de la variable, mais loin du nom de la variable (comme dans l'appel à foo ci-dessus). Ce faisant, il est facile de comprendre exactement ce qui sera passé à la fonction C ; ce sera tout ce qui se trouve dans la « dernière colonne ».

Vous devriez faire de grands efforts pour essayer de passer à la fonction le type de variable qu'elle attend, lorsque cela est possible. Cela vous évitera beaucoup de tracas à long terme.

La Pile des Arguments

Si nous examinons n'importe lequel des codes C générés par l'un des exemples, à l'exception de l'exemple 1, vous remarquerez un certain nombre de références à ST(n), où n est généralement 0. « ST » est en fait une macro qui pointe vers le n-ième argument sur la pile des arguments. ST(0) est donc le premier argument sur la pile et par conséquent le premier argument passé au XSUB, ST(1) est le deuxième argument, et ainsi de suite.

Lorsque vous listez les arguments du XSUB dans le fichier .xs, cela indique à xsubpp quel argument correspond à quel élément de la pile d'arguments (c'est-à-dire, le premier listé est le premier argument, et ainsi de suite). Vous invitez le désastre si vous ne les listez pas dans le même ordre que la fonction les attend.

Les valeurs réelles sur la pile des arguments sont des pointeurs vers les valeurs passées. Lorsqu'un argument est listé comme valeur OUTPUT, sa valeur correspondante sur la pile (c'est-à-dire ST(0) s'il était le premier argument) est modifiée. Vous pouvez le vérifier en examinant le code C généré pour l'Exemple 3. Le code de la routine XSUB round() contient des lignes qui ressemblent à ceci :

double  arg = (double)SvNV(ST(0));
/* Round the contents of the variable arg */
sv_setnv(ST(0), (double)arg);

La variable arg est initialement définie en prenant la valeur de ST(0), puis est stockée à nouveau dans ST(0) à la fin de la routine.

Les XSUBs sont également autorisés à retourner des listes, pas seulement des scalaires. Cela doit être fait en manipulant les valeurs de la pile ST(0), ST(1), etc., d'une manière subtilement différente. Voir perlxs pour plus de détails.

Les XSUBs sont également autorisés à éviter la conversion automatique des arguments de fonction Perl en arguments de fonction C. Voir perlxs pour plus de détails. Certaines personnes préfèrent la conversion manuelle en inspectant ST(i) même dans les cas où la conversion automatique fonctionnerait, soutenant que cela rend la logique d'un appel XSUB plus claire. Comparez avec « Sortir le gras des XSUBs » pour un compromis similaire de séparation complète des parties « colle Perl » et « exécutrice » d'un XSUB.

Alors que les experts peuvent débattre de ces idiomes, un novice en « entrailles Perl » peut préférer une manière qui est aussi peu spécifique aux « entrailles Perl » que possible, ce qui signifie conversion automatique et génération d'appel automatique, comme dans « Sortir le gras des XSUBs ». Cette approche a l'avantage supplémentaire de protéger l'écrivain de XSUB contre les changements futurs de l'API Perl.

Étendre votre Extension

Parfois, vous voudrez peut-être fournir des méthodes ou des sous-routines supplémentaires pour aider à rendre l'interface entre Perl et votre extension plus simple ou plus facile à comprendre. Ces routines devraient se trouver dans le fichier .pm. Que leur chargement soit automatique lorsque l'extension elle-même est chargée ou seulement lorsqu'elles sont appelées dépend de l'endroit où la définition de la sous-routine est placée dans le fichier .pm. Vous pouvez également consulter AutoLoader pour une autre façon de stocker et de charger vos sous-routines supplémentaires.

Documenter votre Extension

Il n'y a absolument aucune excuse pour ne pas documenter votre extension. La documentation appartient au fichier .pm. Ce fichier sera transmis à pod2man, et la documentation intégrée sera convertie au format manpage, puis placée dans le répertoire blib. Elle sera copiée dans le répertoire des manpages de Perl lors de l'installation de l'extension.

Vous pouvez intercaler de la documentation et du code Perl dans le fichier .pm. En fait, si vous voulez utiliser l'autoloading de méthodes, vous devez le faire, comme l'explique le commentaire à l'intérieur du fichier .pm.

Voir perlpod pour plus d'informations sur le format pod.

Installer votre Extension

Une fois votre extension terminée et ayant passé tous ses tests, son installation est très simple : vous exécutez simplement « make install ». Vous devrez soit avoir les permissions d'écriture dans les répertoires où Perl est installé, soit demander à votre administrateur système d'exécuter le make pour vous.

Alternativement, vous pouvez spécifier le répertoire exact où placer le e

xtension's files en plaçant un "PREFIX=/destination/directory" après make install (ou entre make et install si vous avez une version de make dépassée). Ceci peut être très utile si vous construisez une extension qui sera distribuée sur plusieurs systèmes. Vous pourrez alors simplement archiver les fichiers dans le répertoire de destination et les distribuer à vos systèmes de destination.

EXEMPLE 5

Dans cet exemple, nous allons travailler davantage avec la pile d'arguments. Les exemples précédents n'ont retourné qu'une seule valeur. Nous allons maintenant créer une extension qui retourne un tableau.

Cette extension est très orientée Unix (struct statfs et l'appel système statfs). Si vous n'êtes pas sous un système Unix, vous pouvez remplacer statfs par toute autre fonction qui retourne plusieurs valeurs, vous pouvez coder en dur des valeurs à retourner à l'appelant (bien que cela soit un peu plus difficile pour tester le cas d'erreur), ou vous pouvez simplement ne pas faire cet exemple. Si vous modifiez le XSUB, assurez-vous de corriger les cas de test pour qu'ils correspondent aux modifications.

Retournez dans le répertoire Mytest et ajoutez le code suivant à la fin de Mytest.xs :

void
statfs(path)
        char *  path
    INIT:
        int i;
        struct statfs buf;
    PPCODE:
        i = statfs(path, &buf);
        if (i == 0) {
                XPUSHs(sv_2mortal(newSVnv(buf.f_bavail)));
                XPUSHs(sv_2mortal(newSVnv(buf.f_bfree)));
                XPUSHs(sv_2mortal(newSVnv(buf.f_blocks)));
                XPUSHs(sv_2mortal(newSVnv(buf.f_bsize)));
                XPUSHs(sv_2mortal(newSVnv(buf.f_ffree)));
                XPUSHs(sv_2mortal(newSVnv(buf.f_files)));
                XPUSHs(sv_2mortal(newSVnv(buf.f_type)));
        } else {
                XPUSHs(sv_2mortal(newSVnv(errno)));
        }

Vous devrez également ajouter le code suivant en haut du fichier .xs, juste après l'inclusion de "XSUB.h" :

#include <sys/vfs.h>

Ajoutez également le segment de code suivant à Mytest.t tout en incrémentant les tests "9" à "11" :

my @a;
    @a = Mytest::statfs("/blech");
    ok( scalar(@a) == 1 && $a[0] == 2 );
    @a = Mytest::statfs("/");
    is( scalar(@a), 7 );

Nouveautés de cet exemple

Cet exemple a ajouté plusieurs nouveaux concepts. Nous allons les aborder un par un.

  • La directive INIT: contient du code qui sera placé immédiatement après le décodage de la pile d'arguments. C ne permet pas les déclarations de variables à des emplacements arbitraires à l'intérieur d'une fonction, c'est donc généralement la meilleure façon de déclarer les variables locales nécessaires au XSUB. (Alternativement, on pourrait mettre toute la section "PPCODE:" entre accolades, et placer ces déclarations en haut.)
  • Cette routine retourne également un nombre différent d'arguments en fonction du succès ou de l'échec de l'appel à statfs. En cas d'erreur, le numéro d'erreur est retourné sous forme de tableau à un seul élément. Si l'appel réussit, un tableau de 7 éléments est retourné. Comme un seul argument est passé à cette fonction, nous avons besoin de place sur la pile pour contenir les 7 valeurs qui peuvent être retournées.

    Nous faisons cela en utilisant la directive PPCODE:, plutôt que la directive CODE:. Cela indique à xsubpp que nous allons gérer nous-mêmes les valeurs de retour qui seront placées sur la pile d'arguments.

  • Lorsque nous voulons placer des valeurs à retourner à l'appelant sur la pile, nous utilisons la série de macros commençant par "XPUSH". Il existe cinq versions différentes, pour placer des entiers, des entiers non signés, des doubles, des chaînes de caractères et des scalaires Perl sur la pile. Dans notre exemple, nous avons placé un scalaire Perl sur la pile. (En fait, c'est la seule macro qui peut être utilisée pour retourner plusieurs valeurs.)

    Les macros XPUSH* étendront automatiquement la pile de retour pour éviter qu'elle ne soit dépassée. Vous poussez les valeurs sur la pile dans l'ordre dans lequel vous souhaitez qu'elles soient vues par le programme appelant.

  • Les valeurs poussées sur la pile de retour du XSUB sont en fait des SV mortels. Ils sont rendus mortels afin qu'une fois que les valeurs sont copiées par le programme appelant, les SV qui contenaient les valeurs retournées puissent être désalloués. S'ils n'étaient pas mortels, ils continueraient d'exister après le retour de la routine XSUB, mais ne seraient pas accessibles. Ceci est une fuite de mémoire.
  • Si nous étions intéressés par la performance, et non par la compacité du code, dans la branche succès, nous n'utiliserions pas les macros "XPUSHs", mais les macros "PUSHs", et nous étendrions la pile avant de pousser les valeurs de retour : 
    EXTEND(SP, 7);

    Le compromis est qu'il faut calculer le nombre de valeurs de retour à l'avance (bien que dépasser la pile ne nuise généralement qu'à la consommation de mémoire).

    De même, dans la branche échec, nous pourrions utiliser "PUSHs" *sans* étendre la pile : la référence de la fonction Perl arrive sur la pile d'un XSUB, donc la pile est *toujours* assez grande pour prendre une valeur de retour.

EXEMPLE 6

Dans cet exemple, nous allons accepter une référence à un tableau comme paramètre d'entrée, et retourner une référence à un tableau de hachages. Ceci démontrera la manipulation de types de données Perl complexes à partir d'un XSUB.

Cette extension est quelque peu artificielle. Elle est basée sur le code de l'exemple précédent. Elle appelle la fonction statfs plusieurs fois, acceptant une référence à un tableau de noms de fichiers comme entrée, et retournant une référence à un tableau de hachages contenant les données pour chacun des systèmes de fichiers.

Retournez dans le répertoire Mytest et ajoutez le code suivant à la fin de Mytest.xs :

SV *
multi_statfs(paths)
        SV * paths
    INIT:
        AV * results;
        SSize_t numpaths = 0, n;
        int i;
        struct statfs buf;
        SvGETMAGIC(paths);
        if ((!SvROK(paths))
            || (SvTYPE(SvRV(paths)) != SVt_PVAV)
            || ((numpaths = av_top_index((AV *)SvRV(paths))) < 0))
        {
            XSRETURN_UNDEF;
        }
        results = (AV *)sv_2mortal((SV *)newAV());
    CODE:
        for (n = 0; n <= numpaths; n++) {
            HV * rh;
            STRLEN l;
            SV * path = *av_fetch((AV *)SvRV(paths), n, 0);
            char * fn = SvPVbyte(path, l);
            i = statfs(fn, &buf);
            if (i != 0) {
                av_push(results, newSVnv(errno));
                continue;
            }
            rh = (HV *)sv_2mortal((SV *)newHV());
            hv_store(rh, "f_bavail", 8, newSVnv(buf.f_bavail), 0);
            hv_store(rh, "f_bfree",  7, newSVnv(buf.f_bfree),  0);
            hv_store(rh, "f_blocks", 8, newSVnv(buf.f_blocks), 0);
            hv_store(rh, "f_bsize",  7, newSVnv(buf.f_bsize),  0);
            hv_store(rh, "f_ffree",  7, newSVnv(buf.f_ffree),  0);
            hv_store(rh, "f_files",  7, newSVnv(buf.f_files),  0);
            hv_store(rh, "f_type",   6, newSVnv(buf.f_type),   0);
            av_push(results, newRV_inc((SV *)rh));
        }
        RETVAL = newRV_inc((SV *)results);
    OUTPUT:
        RETVAL

Et ajoutez le code suivant à Mytest.t tout en incrémentant les tests "11" à "13" :

my $results = Mytest::multi_statfs([ '/', '/blech' ]);
ok( ref $results->[0] );
ok( ! ref $results->[1] );

Nouveautés de cet exemple

Un certain nombre de nouveaux concepts sont introduits ici, décrits ci-dessous :

  • Cette fonction n'utilise pas de typemap. Au lieu de cela, nous la déclarons comme acceptant un paramètre SV* (scalaire), et retournant une valeur SV*, et nous nous chargeons de remplir ces scalaires dans le code. Comme nous ne retournons qu'une seule valeur, nous n'avons pas besoin d'une directive "PPCODE:" - à la place, nous utilisons les directives "CODE:" et "OUTPUT:".
  • Lorsqu'il s'agit de références, il est important de les manipuler avec prudence. Le bloc "INIT:" appelle d'abord SvGETMAGIC(paths), au cas où paths serait une variable liée. Il vérifie ensuite que "SvROK" retourne vrai, ce qui indique que paths est une référence valide. (Simplement vérifier "SvROK" ne déclencherait pas FETCH sur une variable liée.) Il vérifie ensuite que l'objet référencé par paths est un tableau, en utilisant "SvRV" pour déréférencer paths, et "SvTYPE" pour découvrir son type. En guise de test supplémentaire, il vérifie que le tableau référencé par paths n'est pas vide, en utilisant la fonction "av_top_index" (qui retourne -1 si le tableau est vide). La macro XSRETURN_UNDEF est utilisée pour abandonner le XSUB et retourner la valeur indéfinie lorsque ces trois conditions ne sont pas remplies.
  • Nous manipulons plusieurs tableaux dans ce XSUB. Notez qu'un tableau est représenté en interne par un pointeur AV*. Les fonctions et macros pour manipuler les tableaux sont similaires aux fonctions de Perl : "av_top_index" retourne l'indice le plus élevé dans un AV*, tout comme $#tableau ; "av_fetch" récupère une seule valeur scalaire d'un tableau, étant donné son indice ; "av_push" pousse une valeur scalaire à la fin du tableau, l'étendant automatiquement si nécessaire.

    Spécifiquement, nous lisons les noms de chemins un par un depuis le tableau d'entrée, et stockons les résultats dans un tableau de sortie (results) dans le même ordre. Si statfs échoue, l'élément poussé dans le tableau de retour est la valeur de errno après l'échec. Si statfs réussit, la valeur poussée dans le tableau de retour est une référence à un hachage contenant certaines des informations de la structure statfs.

    Comme pour la pile de retour, il serait possible (et un petit gain de performance) d'étendre le tableau de retour avant d'y pousser des données, car nous savons combien d'éléments nous allons retourner :

    av_extend(results, numpaths);
  • Nous effectuons une seule opération de hachage dans cette fonction, qui consiste à stocker un nouveau scalaire sous une clé en utilisant "hv_store". Un hachage est représenté par un pointeur HV*. Comme les tableaux, les fonctions de manipulation des hachages à partir d'un XSUB reflètent les fonctionnalités disponibles depuis Perl. Voir perlguts et perlapi pour les détails.
  • Pour créer une référence, nous utilisons la fonction "newRV_inc". Notez que vous pouvez caster un AV* ou un HV* en type SV* dans ce cas (et dans de nombreux autres). Cela vous permet de prendre des références à des tableaux, des hachages et des scalaires avec la même fonction. Inversement, la fonction "SvRV" retourne toujours un SV*, qui peut devoir être casté dans le type approprié si

EXAMPLE 9 Passing open files to XSes

You would think passing files to an XS is difficult, with all the typeglobs and stuff. Well, it isn't.

Suppose that for some strange reason we need a wrapper around the standard C library function fputs(). This is all we need:

#define PERLIO_NOT_STDIO 0  /* For co-existence with stdio only */
#define PERL_NO_GET_CONTEXT /* This is more efficient */
#include "EXTERN.h"
#include "perl.h"
#include "XSUB.h"
#include <stdio.h>
int
fputs(s, stream)
  char *          s
  FILE *          stream

The real work is done in the standard typemap.

For more details, see "Co-existence with stdio" in perlapio.

But you lose all the fine stuff done by the perlio layers. This calls the stdio function fputs(), which knows nothing about them.

The standard typemap offers three variants of PerlIO *: "InputStream" (T_IN), "InOutStream" (T_INOUT) and "OutputStream" (T_OUT). A bare "PerlIO *" is considered a T_INOUT. If it matters in your code (see below for why it might) #define or typedef one of the specific names and use that as the argument or result type in your XS file.

The standard typemap does not contain PerlIO * before perl 5.7, but it has the three stream variants. Using a PerlIO * directly is not backwards compatible unless you provide your own typemap.

For streams coming from perl the main difference is that "OutputStream" will get the output PerlIO * - which may make a difference on a socket. Like in our example...

For streams being handed to perl a new file handle is created (i.e. a reference to a new glob) and associated with the PerlIO * provided. If the read/write state of the PerlIO * is not correct then you may get errors or warnings from when the file handle is used. So if you opened the PerlIO * as "w" it should really be an "OutputStream" if open as "r" it should be an "InputStream".

Now, suppose you want to use perlio layers in your XS. We'll use the perlio PerlIO_puts() function as an example.

In the C part of the XS file (above the first MODULE line) you have

    #define OutputStream    PerlIO *
or
    typedef PerlIO *        OutputStream;

And this is the XS code:

int
perlioputs(s, stream)
        char *          s
        OutputStream    stream
CODE:
        RETVAL = PerlIO_puts(stream, s);
OUTPUT:
        RETVAL

We have to use a "CODE" section because PerlIO_puts() has the arguments reversed compared to fputs(), and we want to keep the arguments the same.

Wanting to explore this thoroughly, we want to use the stdio fputs() on a PerlIO *. This means we have to ask the perlio system for a stdio "FILE *":

int
perliofputs(s, stream)
        char *          s
        OutputStream    stream
PREINIT:
        FILE *fp = PerlIO_findFILE(stream);
CODE:
        if (fp != (FILE*) 0) {
                RETVAL = fputs(s, fp);
        } else {
                RETVAL = -1;
        }
OUTPUT:
        RETVAL

Note: PerlIO_findFILE() will search the layers for a stdio layer. If it can't find one, it will call PerlIO_exportFILE() to generate a new stdio "FILE". Please only call PerlIO_exportFILE() if you want a new "FILE". It will generate one on each call and push a new stdio layer. So don't call it repeatedly on the same file. PerlIO_findFILE() will retrieve the stdio layer once it has been generated by PerlIO_exportFILE().

This applies to the perlio system only. For versions before 5.7, PerlIO_exportFILE() is equivalent to PerlIO_findFILE().

EXEMPLE 9 Passer des fichiers ouverts à des XS

On pourrait penser que passer des fichiers à un XS est difficile, avec tous les typeglobs et autres. Eh bien, ce n'est pas le cas.

Supposons que pour une raison étrange, nous ayons besoin d'un wrapper autour de la fonction standard de la bibliothèque C fputs(). C'est tout ce dont nous avons besoin :

#define PERLIO_NOT_STDIO 0  /* Pour la coexistence avec stdio uniquement */
#define PERL_NO_GET_CONTEXT /* C'est plus efficace */
#include "EXTERN.h"
#include "perl.h"
#include "XSUB.h"
#include <stdio.h>
int
fputs(s, stream)
  char *          s
  FILE *          stream

Le vrai travail est effectué dans la typemap standard.

Pour plus de détails, voir "Co-existence avec stdio" dans perlapio.

Mais vous perdez toutes les fonctionnalités fines assurées par les couches perlio. Ceci appelle la fonction stdio fputs(), qui n'en sait rien.

La typemap standard offre trois variantes de PerlIO *: "InputStream" (T_IN), "InOutStream" (T_INOUT) et "OutputStream" (T_OUT). Un "PerlIO *" nu est considéré comme un T_INOUT. Si cela importe dans votre code (voir ci-dessous pourquoi cela pourrait être le cas) #define ou typedef l'un des noms spécifiques et utilisez-le comme argument ou type de résultat dans votre fichier XS.

La typemap standard ne contient pas PerlIO * avant perl 5.7, mais elle a les trois variantes de flux. Utiliser un PerlIO * directement n'est pas rétrocompatible à moins que vous ne fournissiez votre propre typemap.

Pour les flux venant de perl, la principale différence est que "OutputStream" obtiendra le PerlIO * de sortie - ce qui peut faire une différence sur une socket. Comme dans notre exemple...

Pour les flux transmis à perl, un nouveau descripteur de fichier est créé (c'est-à-dire une référence à un nouveau glob) et associé au PerlIO * fourni. Si l'état de lecture/écriture du PerlIO * n'est pas correct, vous pourriez obtenir des erreurs ou des avertissements lors de l'utilisation du descripteur de fichier. Donc, si vous avez ouvert le PerlIO * en tant que "w", il devrait vraiment être un "OutputStream", s'il est ouvert en tant que "r", il devrait être un "InputStream".

Maintenant, supposons que vous souhaitiez utiliser les couches perlio dans votre XS. Nous utiliserons la fonction perlio PerlIO_puts() comme exemple.

Dans la partie C du fichier XS (au-dessus de la première ligne MODULE), vous avez

    #define OutputStream    PerlIO *
ou
    typedef PerlIO *        OutputStream;

Et voici le code XS :

int
perlioputs(s, stream)
        char *          s
        OutputStream    stream
CODE:
        RETVAL = PerlIO_puts(stream, s);
OUTPUT:
        RETVAL

Nous devons utiliser une section "CODE" car PerlIO_puts() a les arguments inversés par rapport à fputs(), et nous voulons garder les arguments les mêmes.

Voulant explorer cela en profondeur, nous voulons utiliser le stdio fputs() sur un PerlIO *. Cela signifie que nous devons demander au système perlio un "FILE *" stdio :

int
perliofputs(s, stream)
        char *          s
        OutputStream    stream
PREINIT:
        FILE *fp = PerlIO_findFILE(stream);
CODE:
        if (fp != (FILE*) 0) {
                RETVAL = fputs(s, fp);
        } else {
                RETVAL = -1;
        }
OUTPUT:
        RETVAL

Note : PerlIO_findFILE() recherchera dans les couches une couche stdio. S'il n'en trouve pas, il appellera PerlIO_exportFILE() pour générer un nouveau "FILE" stdio. N'appelez PerlIO_exportFILE() que si vous voulez un *nouveau* "FILE". Il en générera un à chaque appel et ajoutera une nouvelle couche stdio. Donc, ne l'appelez pas plusieurs fois sur le même fichier. PerlIO_findFILE() récupérera la couche stdio une fois qu'elle aura été générée par PerlIO_exportFILE().

Ceci s'applique uniquement au système perlio. Pour les versions antérieures à 5.7, PerlIO_exportFILE() est équivalent à PerlIO_findFILE().

  • Dans les versions de 5.002 antérieures à la version gamma, le script de test de l'exemple 1 ne fonctionnera pas correctement. Vous devez modifier la ligne "use lib" pour lire : 
    use lib './blib';
  • Dans les versions de 5.002 antérieures à la version 5.002b1h, le fichier test.pl n'était pas automatiquement créé par h2xs. Cela signifie que vous ne pouvez pas dire "make test" pour exécuter le script de test. Vous devrez ajouter la ligne suivante avant l'instruction "use extension" : 
    use lib './blib';
  • Dans les versions 5.000 et 5.001, au lieu d'utiliser la ligne ci-dessus, vous devrez utiliser la ligne suivante : 
    BEGIN { unshift(@INC, "./blib") }
  • Ce document suppose que l'exécutable nommé "perl" est Perl version 5. Certains systèmes peuvent avoir installé Perl version 5 sous le nom "perl5".
