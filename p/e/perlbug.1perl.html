NOM

perlbug - comment soumettre des rapports de bogues sur Perl

SYNOPIS

perlbug

DESCRIPTION

Ce programme est conçu pour vous aider à générer des rapports de bogues (et des notes de remerciement) concernant perl5 et les modules qui l'accompagnent.

Dans la plupart des cas, vous pouvez simplement l'exécuter interactivement depuis une ligne de commande sans arguments spéciaux et suivre les instructions.

Si vous avez trouvé un bogue dans un port non standard (un qui ne fait pas partie de la distribution standard), une distribution binaire, ou un module non essentiel (tel que Tk, DBI, etc.), veuillez consulter la documentation fournie avec cette distribution pour déterminer l'endroit correct pour signaler les bogues.

Les rapports de bogues doivent être soumis au traqueur de problèmes GitHub à l'adresse https://github.com/Perl/perl5/issues. L'adresse perlbug@perl.org n'ouvre plus automatiquement de tickets. Vous pouvez utiliser cet outil pour composer votre rapport et l'enregistrer dans un fichier que vous pourrez ensuite soumettre au traqueur de problèmes.

Dans des cas extrêmes, perlbug peut ne pas fonctionner suffisamment bien sur votre système pour vous guider dans la composition d'un rapport de bogue. Dans ces cas, vous pouvez essayer d'utiliser perlbug -d ou perl -V pour obtenir des informations de configuration système à inclure dans votre rapport de problème.

Lors du signalement d'un bogue, veuillez passer en revue cette liste de contrôle :

Quelle version de Perl utilisez-vous ?
Tapez "perl -v" dans la ligne de commande pour le savoir.
Utilisez-vous la dernière version publiée de Perl ?
Consultez http://www.perl.org/ pour le savoir. Si vous n'utilisez pas la dernière version publiée, veuillez essayer de reproduire votre bogue sur la dernière version stable.

Notez que les rapports concernant des bogues dans d'anciennes versions de Perl, en particulier ceux qui indiquent que vous n'avez pas également testé la version stable actuelle de Perl, recevront probablement moins d'attention de la part des bénévoles qui construisent et maintiennent Perl que les rapports concernant des bogues dans la version actuelle.

Êtes-vous sûr de ce que vous avez est un bogue ?
Un nombre significatif des rapports de bogues que nous recevons s'avèrent être des fonctionnalités documentées dans Perl. Assurez-vous que le problème que vous avez rencontré n'est pas intentionnel en parcourant la documentation qui accompagne la distribution Perl.

Étant donné le volume de documentation Perl, ce n'est pas une tâche triviale, mais si vous pouvez indiquer une documentation suggérant que le comportement que vous observez est erroné, votre problème recevra probablement plus d'attention. Vous voudrez peut-être commencer par perldoc perltrap pour obtenir des indications sur les pièges courants dans lesquels les programmeurs Perl, nouveaux (et expérimentés), tombent.

Si vous n'êtes pas sûr de la signification d'un message d'erreur que vous avez rencontré, consultez perldoc perldiag pour une explication. Si le message n'est pas dans perldiag, il n'est probablement pas généré par Perl. Vous pourriez avoir de la chance en consultant la documentation de votre système d'exploitation à la place.

Si vous êtes sur une plateforme non-UNIX, consultez perldoc perlport, car certaines fonctionnalités peuvent ne pas être implémentées ou fonctionner différemment.

Vous pourriez être en mesure de déterminer ce qui ne va pas en utilisant le débogueur Perl. Pour des informations sur la façon d'utiliser le débogueur, consultez perldoc perldebug.

Avez-vous un cas de test approprié ?
Plus il est facile de reproduire votre bogue, plus il est probable qu'il soit corrigé -- si personne ne peut reproduire votre problème, il ne sera probablement pas résolu.

Un bon cas de test possède la plupart des attributs suivants : code court et simple ; peu de dépendances vis-à-vis de commandes, modules ou bibliothèques externes ; aucun code dépendant de la plateforme (sauf s'il s'agit d'un bogue spécifique à une plateforme) ; documentation claire et simple.

Un bon cas de test est presque toujours un bon candidat pour être inclus dans la suite de tests de Perl. Si vous avez le temps, envisagez de rédiger votre cas de test de manière à ce qu'il puisse être facilement intégré dans la suite de tests standard.

Avez-vous inclus toutes les informations pertinentes ?
Assurez-vous d'inclure les messages d'erreur exacts, le cas échéant. "Perl a donné une erreur" n'est pas un message d'erreur exact.

Si vous obtenez un vidage du noyau (ou équivalent), vous pouvez utiliser un débogueur (dbx, gdb, etc.) pour produire une trace de la pile à inclure dans le rapport de bogue.

NOTE : sauf si votre Perl a été compilé avec des informations de débogage (souvent -g), la trace de la pile sera probablement assez difficile à utiliser car elle ne contiendra très probablement que les noms des fonctions et non leurs arguments. Si possible, recompilez votre Perl avec des informations de débogage et reproduisez le crash et la trace de la pile.

Pouvez-vous décrire le bogue en langage clair ?
Plus un bogue reproductible est facile à comprendre, plus il est probable qu'il soit corrigé. Toute perspicacité que vous pouvez fournir sur le problème aidera grandement. En d'autres termes, essayez d'analyser le problème (dans la mesure de vos capacités) et rapportez vos découvertes.
Pouvez-vous corriger le bogue vous-même ?
Si oui, c'est une excellente nouvelle ; les rapports de bogues avec des correctifs recevront probablement beaucoup plus d'attention et d'intérêt que ceux sans correctifs. Veuillez soumettre votre correctif via le flux de travail de Pull Request de GitHub tel que décrit dans perldoc perlhack. Vous pouvez également envoyer des correctifs à perl5-porters@perl.org. Lors de l'envoi d'un correctif, créez-le en utilisant "git format-patch" si possible, bien qu'un diff unifié créé avec "diff -pu" fera presque aussi bien.

Votre correctif peut être retourné avec des demandes de changements, ou des demandes d'explications plus détaillées sur votre correction.

Voici quelques conseils pour créer des correctifs de haute qualité :

Assurez-vous que le correctif n'est pas inversé (le premier argument de diff est généralement le fichier original, le second argument votre fichier modifié). Assurez-vous de tester votre correctif en l'appliquant avec "git am" ou le programme "patch" avant de l'envoyer. Essayez de suivre le même style que le code que vous essayez de corriger. Assurez-vous que votre correctif fonctionne réellement ("make test", si ce que vous corrigez est couvert par la suite de tests de Perl).

Pouvez-vous utiliser "perlbug" pour soumettre une note de remerciement ?
Oui, vous pouvez le faire en utilisant l'option "-T", ou en invoquant le programme en tant que "perlthanks". Les notes de remerciement sont une bonne chose. Elles font sourire les gens.

Veuillez rendre le titre de votre problème informatif. "un bogue" n'est pas informatif. Pas plus que "perl plante" ni "AIDE !!!". Ces titres n'aident pas. Une description concise de ce qui ne va pas convient.

Une fois que vous avez fait votre part, veuillez être prêt à attendre, à vous faire dire que le bogue est dans votre code, ou éventuellement à ne recevoir aucune réponse. Les bénévoles qui maintiennent Perl sont des gens occupés, donc si votre problème est un bogue évident dans votre propre code, difficile à comprendre ou un doublon d'un rapport existant, vous pourriez ne pas recevoir de réponse personnelle.

S'il est important pour vous que votre bogue soit corrigé, surveillez le traqueur de problèmes (vous serez abonné aux notifications pour les problèmes que vous soumettez ou auxquels vous commentez) et les journaux de commits des versions de développement de Perl, et encouragez les mainteneurs avec des mots gentils ou des offres de boissons fraîches. perlbug(1) — Perl Bug Reporting Utility

NAME

perlbug — report bugs in Perl

SYNOPSIS

perlbug [-option] [-option ...]

DESCRIPTION

This program helps you report bugs in Perl. It gathers information about your system and the bug you are experiencing, and then either saves the report to a file, or e-mails it to the Perlporters.

When run without options, it will try to guess your return address, ask you for a subject, and then prompt you to enter the body of the bug report. It will also ask you to confirm the report before sending it.

It is recommended that you run perlbug with the Perl interpreter you suspect the bug to be in. For example:

    ~/perl/bin/perl bug/script.pl
    ~/perl/bin/perlbug -v

The latter command will ask you for a subject and the body of the bug report, but will automatically prepend the output of perl -V (and other useful configuration data) to the report.

It is generally a good idea to check the Perlporters' FAQ at https://perl.apache.org/qa/perlbugfaq.html before filing a bug report. Many common problems are explained there.

If you are reporting a bug in a module that ships with Perl, check the module documentation first. There may be specific instructions for reporting bugs in that module.

If you are reporting a bug in a third-party module (one not distributed with Perl), you should report the bug to the module's author, not the Perlporters. See the module's documentation for the correct procedure. Usually, this involves e-mailing the author, or filing a bug report on the module's CPAN page.

If you suspect a bug in Perl itself, please try to create a small, self-contained test case that demonstrates the bug. This makes it much easier for the developers to diagnose and fix the problem. It is also a good idea to check if the bug is still present in the latest development version of Perl. You can download development versions from http://dev.perl.org/.

If your bug is still present in a newer version of Perl, please consider reporting it on the Perl bug tracking system at https://github.com/Perl/perl5/issues. Please do not report bugs that have already been fixed. Note that a bug report is not necessarily a bug; it may be a feature request, or a misunderstanding of how Perl works. In such cases, the Perl mailing lists or IRC channels are a better place to ask for help.

If you are submitting a bug report for a crash or other serious problem, please include as much detail as possible. This includes the full error message, the stack trace (if available), and any relevant system information.

Note that running perlbug with certain options may cause it to send mail automatically. This might not be what you want, and could (unlikely, but possible) have the opposite effect of the one you want.)

Feel free to update the ticket about your bug on https://github.com/Perl/perl5/issues if a new version of Perl is released and your bug is still present.

OPTIONS

-a
Adresse à laquelle envoyer le rapport au lieu de l'enregistrer dans un fichier.
-b
Corps du rapport. S'il n'est pas inclus dans la ligne de commande, ou dans un fichier avec -f, vous aurez la possibilité d'éditer le rapport.
-C
N'envoyer pas de copie à l'administrateur lors de l'envoi du rapport par courrier.
-c
Adresse à laquelle envoyer une copie du rapport lors de l'envoi du rapport par courrier. Par défaut, c'est l'adresse de l'administrateur local de Perl (enregistrée lors de la construction de Perl).
-d
Mode données (par défaut si vous redirigez ou transmettez la sortie). Ceci affiche vos données de configuration, sans rien enregistrer ni envoyer par courrier. Vous pouvez l'utiliser avec -v pour obtenir des données plus complètes.
-e
Éditeur à utiliser.
-f
Fichier contenant le corps du rapport. Utilisez ceci pour envoyer rapidement un rapport préparé.
-F
Fichier où écrire les résultats. Par défaut, c'est perlbug.rep.
-h
Affiche un bref résumé des options.
-ok
Signaler une construction réussie sur ce système aux Perlporters. Force -S et -C. Force et fournit des valeurs pour -s et -b. Ne demande une adresse de retour que s'il ne peut pas la deviner (pour une utilisation avec make). Respecte l'adresse de retour spécifiée avec -r. Vous pouvez utiliser ceci avec -v pour obtenir des données plus complètes. Ne crée un rapport que si ce système a moins de 60 jours.
-okay
Comme -ok, sauf qu'il signalera les systèmes plus anciens.
-nok
Signaler une construction non réussie sur ce système. Force -C. Force et fournit une valeur pour -s, puis vous demande d'éditer le rapport et d'expliquer ce qui s'est mal passé. Alternativement, un rapport préparé peut être fourni en utilisant -f. Ne demande une adresse de retour que s'il ne peut pas la deviner (pour une utilisation avec make). Respecte l'adresse de retour spécifiée avec -r. Vous pouvez utiliser ceci avec -v pour obtenir des données plus complètes. Ne crée un rapport que si ce système a moins de 60 jours.
-nokay
Comme -nok, sauf qu'il signalera les systèmes plus anciens.
-p
Les noms d'un ou plusieurs fichiers de correctifs (patchs) ou d'autres pièces jointes texte à inclure dans le rapport. Les fichiers multiples doivent être séparés par des virgules.
-r
Votre adresse de retour. Le programme vous demandera de confirmer sa valeur par défaut si vous n'utilisez pas cette option.
-S
Enregistrer ou envoyer le rapport sans demander de confirmation.
-s
Sujet à inclure dans le rapport. Il vous sera demandé si vous n'en fournissez pas dans la ligne de commande.
-t
Mode test. Permet de commander perlbug à partir d'un tuyau (pipe) ou d'un fichier, à des fins de test.
-T
Envoyer une note de remerciement au lieu d'un rapport de bug.
-v
Inclure des données de configuration détaillées dans le rapport.
