PERLPERF(1perl) Guide de référence du programmeur Perl PERLPERF(1perl)

NOM

perlperf - Techniques de performance et d'optimisation Perl

DESCRIPTION

Ceci est une introduction à l'utilisation de techniques de performance et d'optimisation qui peuvent être utilisées avec une référence particulière aux programmes Perl. Bien que de nombreux développeurs Perl viennent d'autres langages et puissent utiliser leurs connaissances antérieures lorsque cela est approprié, il y a beaucoup d'autres personnes qui pourraient bénéficier de quelques conseils spécifiques à Perl. Si vous voulez la version condensée, le meilleur conseil vient peut-être du célèbre Samouraï japonais, Miyamoto Musashi, qui a dit :

"Ne vous engagez pas dans une activité inutile"

en 1645.

APERÇU

L'erreur la plus courante que font les programmeurs est probablement de tenter d'optimiser leur code avant qu'un programme ne fasse réellement quelque chose d'utile - c'est une mauvaise idée. Il est inutile d'avoir un programme extrêmement rapide qui ne fonctionne pas. Le premier travail consiste à faire en sorte qu'un programme fasse *correctement* quelque chose d'*utile* (sans oublier de s'assurer que la suite de tests est entièrement fonctionnelle), et seulement ensuite à envisager de l'optimiser. Ayant décidé d'optimiser du code existant qui fonctionne, plusieurs étapes simples mais essentielles doivent être prises en considération, qui sont intrinsèques à tout processus d'optimisation.

UN PAS DE CÔTÉ

Premièrement, vous devez établir un temps de référence pour le code existant, temps qui doit être fiable et reproductible. Vous voudrez probablement utiliser les modules "Benchmark" ou "Devel::NYTProf", ou quelque chose de similaire, pour cette étape, ou peut-être l'utilitaire système Unix "time", selon ce qui est approprié. Voir la base de ce document pour une liste plus longue de modules de benchmarking et de profilage, et pour des lectures recommandées.

UN PAS EN AVANT

Ensuite, après avoir examiné le programme pour trouver les *points chauds* (endroits où le code semble s'exécuter lentement), modifiez le code avec l'intention de le rendre plus rapide. L'utilisation d'un logiciel de contrôle de version, comme "subversion", garantira que les modifications ne sont pas irréversibles. Il est trop facile de trifouiller ici et là - ne changez pas trop de choses à la fois, sinon vous pourriez ne pas découvrir quelle partie du code était *vraiment* le point lent.

UN AUTRE PAS DE CÔTÉ

Il ne suffit pas de dire : "ça le rendra plus rapide", il faut le vérifier. Réexécutez le code sous le contrôle des modules de benchmarking ou de profilage, à partir de la première étape ci-dessus, et vérifiez que le nouveau code a exécuté *la même tâche* en *moins de temps*. Sauvegardez votre travail et répétez...

DIRECTIVES GÉNÉRALES

La chose critique à retenir lors de la prise en compte de la performance est qu'il n'existe pas de *balle d'argent*, c'est pourquoi il n'y a pas de règles, seulement des directives.

Il est clair que le code en ligne sera plus rapide que les appels de sous-routines ou de méthodes, car il y a moins de surcharge, mais cette approche a l'inconvénient d'être moins maintenable et coûte plus cher en mémoire - il n'y a pas de repas gratuit. Si vous recherchez un élément dans une liste, il peut être plus efficace de stocker les données dans une structure de hash, et ensuite de simplement vérifier si la clé est définie, plutôt que de parcourir l'intégralité du tableau en utilisant *grep()* par exemple. *substr()* peut être (beaucoup) plus rapide que *grep()* mais pas aussi flexible, vous avez donc un autre compromis à faire. Votre code peut contenir une ligne qui prend 0,01 seconde à exécuter, et si vous l'appelez 1 000 fois, très probablement dans un programme qui analyse même des fichiers de taille moyenne par exemple, vous avez déjà un délai de 10 secondes, à un seul endroit du code, et si vous appelez cette ligne 100 000 fois, votre programme entier ralentira jusqu'à un crawl insupportable.

Utiliser une sous-routine dans le cadre de votre tri est un moyen puissant d'obtenir exactement ce que vous voulez, mais sera généralement plus lent que les opérateurs de tri intégrés *alphabétiques* "cmp" et *numériques* "<=>". Il est possible de faire plusieurs passages sur vos données, en construisant des index pour rendre le tri à venir plus efficace, et d'utiliser ce qui est connu sous le nom de *"OM"* (Orcish Maneuver) pour mettre en cache les clés de tri à l'avance. La recherche dans le cache, bien que bonne idée, peut elle-même être une source de ralentissement en imposant un double passage sur les données - une fois pour configurer le cache, et une fois pour trier les données. L'utilisation de *pack()* pour extraire la clé de tri requise dans une chaîne cohérente peut être un moyen efficace de construire une seule chaîne à comparer, au lieu d'utiliser plusieurs clés de tri, ce qui rend possible l'utilisation de la fonction *sort()* de Perl standard, écrite en *c* et rapide, sur la sortie, et constitue la base de la *"GRT"* (Guttman Rossler Transform). Certaines combinaisons de chaînes peuvent ralentir la *"GRT"*, en étant simplement trop simplement complexes pour son propre bien.

Pour les applications utilisant des bases de données, l'espace de nom standard *"DBIx"* a tenté d'aider à maintenir les choses rapides, non seulement parce qu'il essaie de *ne pas* interroger la base de données avant le dernier moment possible, mais lisez toujours la documentation qui accompagne votre choix de bibliothèques. Parmi les nombreuses questions qui se posent aux développeurs traitant de bases de données, il faut rester conscient d'utiliser toujours les placeholders *"SQL"* et d'envisager la pré-extraction des ensembles de données lorsque cela peut s'avérer avantageux. Diviser un gros fichier en assignant plusieurs processus à l'analyse d'un seul fichier, en utilisant par exemple *"POE"*, *"threads"* ou *"fork"* peut également être un moyen utile d'optimiser votre utilisation des ressources *"CPU"* disponibles, bien que cette technique soit semée d'embûches de concurrence et exige une grande attention aux détails.

Chaque cas a une application spécifique et une ou plusieurs exceptions, et il n'y a pas de substitut à l'exécution de quelques tests et à la découverte de la méthode qui fonctionne le mieux pour votre environnement particulier, c'est pourquoi l'écriture de code optimal n'est pas une science exacte, et pourquoi nous aimons tant utiliser Perl - TMTOWTDI.

BENCHMARKS

Voici quelques exemples pour démontrer l'utilisation des outils de benchmarking de Perl.

Assignation et Déréférencement de Variables

Je suis sûr que la plupart d'entre nous ont vu du code qui ressemble à, (ou pire que), ceci :

if ( $obj->{_ref}->{_myscore} >= $obj->{_ref}->{_yourscore} ) {
    ...

Ce type de code peut être une vraie plaie à lire, ainsi qu'être très sensible aux fautes de frappe, et il est beaucoup plus clair de déréférencer la variable explicitement. Nous évitons ici la question de travailler avec des techniques de programmation orientée objet pour encapsuler l'accès aux variables via des méthodes, accessibles uniquement via un objet. Nous discutons ici simplement du choix de l'implémentation technique, et si cela a un effet sur la performance. Nous pouvons voir si cette opération de déréférencement a une surcharge en plaçant du code comparatif dans un fichier et en exécutant un test *"Benchmark"*.

# déréférencement

#!/usr/bin/perl
use v5.36;
use Benchmark;
my $ref = {
        'ref'   => {
            _myscore    => '100 + 1',
            _yourscore  => '102 - 1',
        },
};
timethese(1000000, {
        'direct'       => sub {
          my $x = $ref->{ref}->{_myscore} . $ref->{ref}->{_yourscore} ;
        },
        'dereference'  => sub {
            my $ref  = $ref->{ref};
            my $myscore = $ref->{_myscore};
            my $yourscore = $ref->{_yourscore};
            my $x = $myscore . $yourscore;
        },
});

Il est essentiel d'exécuter toute mesure de temps un nombre suffisant de fois afin que les nombres se stabilisent sur une moyenne numérique, sinon chaque exécution fluctuera naturellement en raison de variations dans l'environnement, pour réduire l'effet de la contention pour les ressources *"CPU"* et la bande passante réseau par exemple. Malheureusement, car il existe de nombreux exemples de code écrits en utilisant l'accès direct aux variables en plusieurs couches, et c'est généralement horrible. C'est cependant minusculement plus rapide. La question demeure si le gain minime vaut réellement la peine de se fatiguer les yeux, ou la perte de maintenabilité.

Recherche et remplacement ou tr

Si nous avons une chaîne qui doit être modifiée, alors qu'une regex sera presque toujours beaucoup plus flexible, "tr", un outil souvent sous-utilisé, peut toujours être utile. Un scénario pourrait être de remplacer toutes les voyelles par un autre caractère. La solution regex pourrait ressembler à ceci :

$str =~ s/[aeiou]/x/g

L'alternative "tr" pourrait ressembler à ceci :

$str =~ tr/aeiou/xxxxx/

Nous pouvons intégrer cela dans un fichier de test que nous pouvons exécuter pour vérifier quelle approche est la plus rapide, en utilisant une variable globale $STR pour affecter la variable "my $str" afin d'éviter que perl n'essaie d'optimiser le travail en remarquant qu'il n'est affecté qu'une seule fois.

# regex-transliterate

#!/usr/bin/perl
use v5.36;
use Benchmark;
my $STR = "$$-this and that";
timethese(1000000, {
'sr'  => sub { my $str = $STR; $str =~ s/[aeiou]/x/g; return $str; },
'tr'  => sub { my $str = $STR; $str =~ tr/aeiou/xxxxx/; return $str; },
});

L'exécution du code nous donne nos résultats :

$> perl regex-transliterate
Benchmark: timing 1000000 iterations of sr, tr...
        sr:  2 wallclock secs ( 1.19 usr +  0.00 sys =  1.19 CPU) @ 840336.13/s (n=1000000)
        tr:  0 wallclock secs ( 0.49 usr +  0.00 sys =  0.49 CPU) @ 2040816.33/s (n=1000000)

La version "tr" est un vainqueur clair. Une solution est flexible, l'autre est rapide - et c'est appropriément le choix du programmeur de l'utiliser.

Consultez la documentation de "Benchmark" pour d'autres techniques utiles.

OUTILS DE PROFILAGE

Un morceau de code légèrement plus grand fournira quelque chose sur quoi un profileur peut produire des statistiques de rapport plus complètes. Cet exemple utilise le simpliste programme "wordmatch" qui analyse un fichier d'entrée donné et produit un court rapport sur son contenu.

# wordmatch

#!/usr/bin/perl
use v5.36;
=head1 NAME
filewords - analyse de mots d'un fichier d'entrée
=head1 SYNOPSIS
    filewords -f nomfichierentree [-d]
=head1 DESCRIPTION
Ce programme analyse le nom de fichier donné, spécifié avec C<-f>, et
affiche une analyse simple des mots qui s'y trouvent. Utilisez le commutateur
C<-d> pour activer les messages de débogage.
=cut
use FileHandle;
use Getopt::Long;
my $debug   =  0;
my $file    = '';
my $result = GetOptions (
    'debug'         => \$debug,
    'file=s'        => \$file,
);
die("arguments invalides") unless $result;
unless ( -f $file ) {
    die("Usage: $0 -f nomfichier [-d]");
}
my $FH = FileHandle->new("< $file")
                              or die("impossible d'ouvrir le fichier($file): $!");
my $i_LINES = 0;
my $i_WORDS = 0;
my %count   = ();
my @lines = <$FH>;
foreach my $line ( @lines ) {
    $i_LINES++;
    $line =~ s/\n//;
    my @words = split(/ +/, $line);
    my $i_words = scalar(@words);
    $i_WORDS = $i_WORDS + $i_words;
    debug("ligne: $i_LINES fournissant $i_words mots: @words");
    my $i_word = 0;
    foreach my $word ( @words ) {
        $i_word++;
        $count{$i_LINES}{spec} += matches($i_word, $word,
                                          '[^a-zA-Z0-9]');
        $count{$i_LINES}{only} += matches($i_word, $word,
                                          '^[^a-zA-Z0-9]+$');
        $count{$i_LINES}{cons} += matches($i_word, $word,
                                    '^[(?i:bcdfghjklmnpqrstvwxyz)]+$');
        $count{$i_LINES}{vows} += matches($i_word, $word,
                                          '^[(?i:aeiou)]+$');
        $count{$i_LINES}{caps} += matches($i_word, $word,
                                          '^[(A-Z)]+$');
    }
}
print report( %count );
sub matches {
    my $i_wd  = shift;
    my $word  = shift;
    my $regex = shift;
    my $has = 0;
    if ( $word =~ /($regex)/ ) {
        $has++ if $1;
    }
    debug( "mot: $i_wd "
          . ($has ? 'correspond' : 'ne correspond pas')
          . " caracteres: /$regex/");
    return $has;
}
sub report {
    my %report = @_;
    my %rep;
    foreach my $line ( keys %report ) {
        foreach my $key ( keys $report{$line}->%* ) {
            $rep{$key} += $report{$line}{$key};
        }
    }
    my $report = qq|
$0 rapport pour $file:
lignes dans le fichier: $i_LINES
mots dans le fichier: $i_WORDS
mots avec caracteres speciaux (non-mot): $i_spec
mots avec seulement caracteres speciaux (non-mot): $i_only
mots avec seulement consonnes: $i_cons
mots avec seulement lettres capitales: $i_caps
mots avec seulement voyelles: $i_vows
|;
    return $report;
}
sub debug {
    my $message = shift;
    if ( $debug ) {
        print STDERR "DBG: $message\n";
    }
}
exit 0;

Devel::DProf

Ce module vénérable a été la norme de facto pour le profilage de code Perl pendant plus d'une décennie, mais il a été remplacé par un certain nombre d'autres modules qui nous ont ramenés au 21e siècle. Bien qu'il vous soit recommandé d'évaluer votre outil parmi plusieurs mentionnés ici et dans la liste CPAN à la base de ce document (et actuellement Devel::NYTProf semble être l'arme de choix - voir ci-dessous), nous allons jeter un coup d'œil rapide à la sortie de Devel::DProf d'abord, pour établir une base de référence pour les outils de profilage Perl. Exécutez le programme ci-dessus sous le contrôle de "Devel::DProf" en utilisant le commutateur "-d" sur la ligne de commande.

Devel::SmallProf

Le profileur "Devel::SmallProf" examine le temps d'exécution de votre programme Perl et produit une liste ligne par ligne pour montrer combien de fois chaque ligne a été appelée, et combien de temps chaque ligne a pris pour s'exécuter. Il est appelé en fournissant le drapeau familier "-d" à Perl au moment de l'exécution.

$> perl -d:SmallProf wordmatch -f perl5db.pl

Devel::FastProf

"Devel::FastProf" est un autre profileur de lignes Perl. Il a été écrit dans le but d'obtenir un profileur de lignes plus rapide que ce qui est possible avec, par exemple, "Devel::SmallProf", car il est écrit en "C". Pour utiliser "Devel::FastProf", fournissez l'argument "-d" à Perl :

$> perl -d:FastProf wordmatch -f perl5db.pl
<...plusieurs lignes tronquées...>
rapport wordmatch pour perl5db.pl :
lignes dans le fichier : 9428
mots dans le fichier : 50243
mots avec des caractères spéciaux (non-mot) : 20480
mots avec seulement des caractères spéciaux (non-mot) : 7790
mots avec seulement des consonnes : 4801
mots avec seulement des majuscules : 1316
mots avec seulement des voyelles : 1701

"Devel::FastProf" écrit les statistiques dans le fichier fastprof.out dans le répertoire courant. Le fichier de sortie, qui peut être spécifié, peut être interprété en utilisant le programme en ligne de commande "fprofpp".

$> fprofpp | head -n20
# format de sortie fprofpp est :
# nom_fichier:ligne temps nombre: source
wordmatch:75 3.93338 251215: if ( $word =~ /($regex)/ ) {
wordmatch:79 1.77774 251215: debug("word: $i_wd ".($has ? 'matches' : 'does not match')." chars: /$regex/");
wordmatch:81 1.47604 251215: return $has;
wordmatch:126 1.43441 260643: my $message = shift;
wordmatch:128 1.42156 260643: if ( $debug ) {
wordmatch:70 1.36824 251215: my $i_wd  = shift;
wordmatch:71 1.36739 251215: my $word  = shift;
wordmatch:72 1.35939 251215: my $regex = shift;

Immédiatement, nous pouvons voir que le nombre de fois que chaque ligne a été appelée est identique à la sortie de "Devel::SmallProf", et la séquence n'est que très légèrement différente en fonction de l'ordre du temps que chaque ligne a pris pour s'exécuter, "if ( $debug ) { " et "my $message = shift;", par exemple. Les différences dans les temps réels enregistrés pourraient être dues à l'algorithme utilisé en interne, ou elles pourraient être dues à des limitations ou à une contention des ressources système.

Voir aussi DBIx::Profile qui profilera les requêtes de base de données exécutées sous le namespace "DBIx::*".

Devel::NYTProf

"Devel::NYTProf" est le profileur de code Perl de **prochaine génération**, corrigeant de nombreuses lacunes des autres outils et implémentant de nombreuses fonctionnalités intéressantes. Tout d'abord, il peut être utilisé comme profileur de *lignes*, de *blocs* ou de *sous-routines*, tout à la fois. Il peut également utiliser une résolution sub-microseconde (100 ns) sur les systèmes qui fournissent clock_gettime(). Il peut être démarré et arrêté même par le programme en cours de profilage. C'est une entrée en une seule ligne pour profiler les applications "mod_perl". Il est écrit en "c" et est probablement le profileur le plus rapide disponible pour Perl. La liste des fonctionnalités cool ne fait que s'allonger. Assez parlé, voyons comment il fonctionne - utilisez simplement le commutateur familier "-d" pour le connecter et exécuter le code.

$> perl -d:NYTProf wordmatch -f perl5db.pl
rapport wordmatch pour perl5db.pl :
lignes dans le fichier : 9427
mots dans le fichier : 50243
mots avec des caractères spéciaux (non-mot) : 20480
mots avec seulement des caractères spéciaux (non-mot) : 7790
mots avec seulement des consonnes : 4801
