PERF-STAT(1) Manuel perf PERF-STAT(1)

NOM

perf-stat - Exécuter une commande et collecter des statistiques de compteurs de performance

SYNTAXE

perf stat [-e <ÉVÉNEMENT> | --event=ÉVÉNEMENT] [-a] <commande>
perf stat [-e <ÉVÉNEMENT> | --event=ÉVÉNEMENT] [-a] -- <commande> [<options>]
perf stat [-e <ÉVÉNEMENT> | --event=ÉVÉNEMENT] [-a] record [-o fichier] -- <commande> [<options>]
perf stat report [-i fichier]

DESCRIPTION

Cette commande exécute une commande et collecte des statistiques de compteurs de performance à partir de celle-ci.

OPTIONS

<commande>...

Toute commande que vous pouvez spécifier dans un shell.

record

Voir STAT RECORD.

report

Voir STAT REPORT.

-e, --event=

Sélectionne l'événement PMU. La sélection peut être :
•un nom d'événement symbolique (utilisez perf list pour lister tous les événements)
•un événement PMU brut sous la forme rN où N est une valeur hexadécimale représentant l'encodage brut du registre avec la disposition des registres de contrôle d'événements telle que décrite par les entrées de /sys/bus/event_source/devices/cpu/format/*.
•un événement PMU symbolique ou brut suivi facultativement d'un deux-points et d'une liste de modificateurs d'événement, par exemple, cpu-cycles:p. Voir la page de manuel perf-list(1) pour plus de détails sur les modificateurs d'événement.
•un événement formé symboliquement comme pmu/param1=0x3,param2/ où param1 et param2 sont définis comme formats pour le PMU dans /sys/bus/event_source/devices/<pmu>/format/* 
'percore' est un qualificateur d'événement qui somme les comptes d'événements pour les deux threads matériels d'un cœur. Par exemple :
perf stat -A -a -e cpu/event,percore=1/,otherevent ...
•un événement formé symboliquement comme pmu/config=M,config1=N,config2=K/ où M, N, K sont des nombres (en format décimal, hexadécimal, octal). Les valeurs acceptables pour chacun des paramètres config, config1 et config2 sont définies par les entrées correspondantes dans /sys/bus/event_source/devices/<pmu>/format/* 
Notez que les deux dernières syntaxes prennent en charge la correspondance de préfixes et de glob sur le nom du PMU pour simplifier la création d'événements sur plusieurs instances du même type de PMU dans les systèmes volumineux (par exemple, les PMU du contrôleur mémoire).
Plusieurs instances de PMU sont typiques pour les PMU "uncore", donc le préfixe
'uncore_' est également ignoré lors de cette correspondance.

-i, --no-inherit

les tâches enfants n'héritent pas des compteurs

-p, --pid=<pid>

statistiques d'événements sur l'identifiant de processus existant (liste séparée par des virgules)

-t, --tid=<tid>

statistiques d'événements sur l'identifiant de thread existant (liste séparée par des virgules)

-b, --bpf-prog

statistiques d'événements sur l'identifiant du programme bpf existant (liste séparée par des virgules), nécessitant les droits root. bpftool-prog peut être utilisé pour trouver l'identifiant du programme de tous les programmes bpf du système. Par exemple : 
# bpftool prog | head -n 1
17247: tracepoint  name sys_enter  tag 192d548b9d754067  gpl
# perf stat -e cycles,instructions --bpf-prog 17247 --timeout 1000
Statistiques de compteurs de performance pour 'programme(s) BPF 17247' :
85 967      cycles
28 982      instructions              #    0.34  insn par cycle
1.102235068 secondes de temps écoulé

--bpf-counters

Utilise des programmes BPF pour agréger les lectures de perf_events. Cela permet à plusieurs sessions perf-stat qui comptent la même métrique (cycles, instructions, etc.) de partager des compteurs matériels. Pour utiliser des programmes BPF sur des événements courants par défaut, utilisez "perf config stat.bpf-counter-events=<liste_des_événements>".

--bpf-attr-map

Avec l'option "--bpf-counters", différentes sessions perf-stat partagent des informations sur les programmes et les maps BPF partagés via une hashmap épinglée. Utilisez "--bpf-attr-map" pour spécifier le chemin de cette hashmap épinglée. Le chemin par défaut est /sys/fs/bpf/perf_attr_map.

--pfm-events événements

Sélectionne un événement PMU en utilisant la syntaxe libpfm4 (voir http://perfmon2.sf.net) incluant la prise en charge des filtres d'événements. Par exemple --pfm-events inst_retired:any_p:u:c=1:i. Plus d'un événement peut être passé à l'option en utilisant le séparateur virgule. Les événements matériels et les événements matériels génériques ne peuvent pas être mélangés. Ces derniers doivent être utilisés avec l'option -e. L'option -e et celle-ci peuvent être mélangées. Les événements peuvent être regroupés en utilisant la notation {}.

-a, --all-cpus

collecte à l'échelle du système à partir de tous les CPU (par défaut si aucune cible n'est spécifiée)

--no-scale

Ne pas mettre à l'échelle/normaliser les valeurs des compteurs

-d, --detailed

affiche des statistiques plus détaillées, peut être spécifié jusqu'à 3 fois 
      -d:          événements détaillés, cache de données L1 et LLC
   -d -d:     événements plus détaillés, événements dTLB et iTLB
-d -d -d:     événements très détaillés, ajout d'événements de pré-extraction

-r, --repeat=<n>

répète la commande et affiche la moyenne + l'écart-type (max : 100). 0 signifie à l'infini.

-B, --big-num

affiche les grands nombres avec des séparateurs de milliers conformément à la locale. Activé par défaut. Utilisez "--no-big-num" pour désactiver. Le réglage par défaut peut être modifié avec "perf config stat.big-num=false".

-C, --cpu=

Compte uniquement sur la liste des CPU fournis. Plusieurs CPU peuvent être fournis sous forme de liste séparée par des virgules sans espace : 0,1. Les plages de CPU sont spécifiées avec - : 0-2. En mode par thread, cette option est ignorée. L'option -a est toujours nécessaire pour activer la surveillance à l'échelle du système. Par défaut, le comptage se fait sur tous les CPU.

-A, --no-aggr

Ne pas agréger les comptes sur tous les CPU surveillés.

-n, --null

exécution nulle - Ne démarre aucun compteur.

Ceci peut être utile pour mesurer uniquement le temps d'horloge écoulé - ou pour évaluer la surcharge brute de perf stat lui-même, sans exécuter aucun compteur.

-v, --verbose

soyez plus verbeux (affichez les erreurs d'ouverture de compteur, etc.)

-x SEP, --field-separator SEP

affiche les comptes en utilisant une sortie de style CSV pour faciliter l'importation directe dans des feuilles de calcul. Les colonnes sont séparées par la chaîne spécifiée dans SEP.

--table

Affiche le temps pour chaque exécution (option -r), sous forme de tableau, par exemple : 
$ perf stat --null -r 5 --table perf bench sched pipe
Statistiques de compteurs de performance pour 'perf bench sched pipe' (5 exécutions) :
# Tableau des mesures individuelles :
5.189 (-0.293) #
5.189 (-0.294) #
5.186 (-0.296) #
5.663 (+0.181) ##
6.186 (+0.703) ####
# Résultat final :
5.483 +- 0.198 secondes de temps écoulé  ( +-  3.62% )

-G name, --cgroup name

surveiller uniquement dans le conteneur (cgroup) nommé "name". Cette option n'est disponible qu'en mode par CPU. Le système de fichiers cgroup doit être monté. Tous les threads appartenant au conteneur "name" sont surveillés lorsqu'ils s'exécutent sur les CPU surveillés. Plusieurs cgroups peuvent être fournies. Chaque cgroup est appliquée à l'événement correspondant, c'est-à-dire le premier cgroup au premier événement, le deuxième cgroup au deuxième événement, et ainsi de suite. Il est possible de fournir un cgroup vide (surveiller tout le temps) en utilisant, par exemple, -G foo,,bar. Les cgroups doivent avoir des événements correspondants, c'est-à-dire qu'ils se réfèrent toujours à des événements définis précédemment dans la ligne de commande. Si l'utilisateur souhaite suivre plusieurs événements pour un cgroup spécifique, l'utilisateur peut utiliser -e e1 -e e2 -G foo,foo ou simplement utiliser -e e1 -e e2 -G foo.

Si vous souhaitez surveiller, par exemple, cycles pour un cgroup et également pour l'ensemble du système, la ligne de commande suivante peut être utilisée : perf stat -e cycles -G nom_cgroup -a -e cycles.

--for-each-cgroup name

Développe la liste des événements pour chaque cgroup dans "name" (autorise plusieurs cgroups séparés par une virgule). Il prend également en charge les modèles regex pour faire correspondre plusieurs groupes. Cela a le même effet que de répéter les options -e et -G pour chaque événement x nom. Cette option ne peut pas être utilisée avec l'option -G/--cgroup.

-o fichier, --output fichier

Imprime la sortie dans le fichier désigné.

--append

Ajoute au fichier de sortie désigné avec l'option -o. Ignoré si -o n'est pas spécifié.--log-fd

Enregistre la sortie dans un descripteur de fichier (fd), au lieu de la sortie d'erreur standard. Complémentaire à --output, et mutuellement exclusif avec celui-ci. --append peut être utilisé ici. Exemples : 3>results perf stat --log-fd 3 -- $cmd 3>>results perf stat --log-fd 3 --append -- $cmd

--control=fifo:ctl-fifo[,ack-fifo], --control=fd:ctl-fd[,ack-fd]

Les descripteurs de fichier ctl-fifo / ack-fifo sont ouverts et utilisés comme ctl-fd / ack-fd comme suit. Écoute sur le descripteur ctl-fd pour les commandes permettant de contrôler la mesure (enable : activer les événements, disable : désactiver les événements). Les mesures peuvent être démarrées avec les événements désactivés en utilisant l'option --delay=-1. Facultativement, envoyez l'accusé de réception de la commande de contrôle (ack\n) au descripteur ack-fd pour synchroniser avec le processus de contrôle. Exemple de script shell bash pour activer et désactiver les événements pendant les mesures : 
#!/bin/bash
ctl_dir=/tmp/
ctl_fifo=${ctl_dir}perf_ctl.fifo
test -p ${ctl_fifo} && unlink ${ctl_fifo}
mkfifo ${ctl_fifo}
exec {ctl_fd}<>${ctl_fifo}
ctl_ack_fifo=${ctl_dir}perf_ctl_ack.fifo
test -p ${ctl_ack_fifo} && unlink ${ctl_ack_fifo}
mkfifo ${ctl_ack_fifo}
exec {ctl_fd_ack}<>${ctl_ack_fifo}
perf stat -D -1 -e cpu-cycles -a -I 1000       \
          --control fd:${ctl_fd},${ctl_fd_ack} \
          \-- sleep 30 &
perf_pid=$!
sleep 5  && echo 'enable' >&${ctl_fd} && read -u ${ctl_fd_ack} e1 && echo "enabled(${e1})"
sleep 10 && echo 'disable' >&${ctl_fd} && read -u ${ctl_fd_ack} d1 && echo "disabled(${d1})"
exec {ctl_fd_ack}>&-
unlink ${ctl_ack_fifo}
exec {ctl_fd}>&-
unlink ${ctl_fifo}
wait -n ${perf_pid}
exit $?

--pre, --post

Crochets de pré et post-mesure, par exemple :

perf stat --repeat 10 --null --sync --pre make -s O=defconfig-build/clean -- make -s -j64 O=defconfig-build/ bzImage

-I msecs, --interval-print msecs

Affiche les deltas de comptage toutes les N millisecondes (minimum : 1 ms). Le pourcentage de surcharge peut être élevé dans certains cas, par exemple avec des intervalles courts, inférieurs à 100 ms. À utiliser avec prudence. Exemple : perf stat -I 1000 -e cycles -a sleep 5

Si la métrique existe, elle est calculée à partir des comptages générés pendant cet intervalle et la métrique est affichée après un #.

--interval-count times

Affiche les deltas de comptage pour un nombre fixe de fois. Cette option doit être utilisée conjointement avec l'option "-I". Exemple : perf stat -I 1000 --interval-count 2 -e cycles -a

--interval-clear

Efface l'écran avant le prochain intervalle.

--timeout msecs

Arrête la session perf stat et affiche les deltas de comptage après N millisecondes (minimum : 10 ms). Cette option n'est pas prise en charge avec l'option "-I". Exemple : perf stat --time 2000 -e cycles -a

--metric-only

Affiche uniquement les métriques calculées. Les affiche sur une seule ligne. Ne montre aucune valeur brute. Non pris en charge avec --per-thread.

--per-socket

Agrège les comptages par socket processeur pour les mesures en mode système. C'est un mode utile pour détecter les déséquilibres entre les sockets. Pour activer ce mode, utilisez --per-socket en plus de -a. (en mode système). La sortie inclut le numéro du socket et le nombre de processeurs en ligne sur ce socket. C'est utile pour évaluer le niveau d'agrégation.

--per-die

Agrège les comptages par die processeur pour les mesures en mode système. C'est un mode utile pour détecter les déséquilibres entre les dies. Pour activer ce mode, utilisez --per-die en plus de -a. (en mode système). La sortie inclut le numéro du die et le nombre de processeurs en ligne sur ce die. C'est utile pour évaluer le niveau d'agrégation.

--per-cluster

Agrège les comptages par cluster processeur pour les mesures en mode système. C'est un mode utile pour détecter les déséquilibres entre les clusters. Pour activer ce mode, utilisez --per-cluster en plus de -a. (en mode système). La sortie inclut le numéro du cluster et le nombre de processeurs en ligne sur ce cluster. C'est utile pour évaluer le niveau d'agrégation. Les informations sur l'ID du cluster et les CPU associés peuvent être obtenues à partir de /sys/devices/system/cpu/cpuX/topology/cluster_{id, cpus}.

--per-cache

Agrège les comptages par instance de cache pour les mesures en mode système. Par défaut, l'agrégation se fait pour le niveau de cache ayant l'indice le plus élevé dans le système. Pour spécifier un niveau particulier, mentionnez le niveau de cache à côté de l'option sous la forme [Ll][1-9][0-9]*. Par exemple : Utiliser l'option "--per-cache=l3" ou "--per-cache=L3" agrègera les informations à la limite du cache de niveau 3 dans le système.

--per-core

Agrège les comptages par processeur physique pour les mesures en mode système. C'est un mode utile pour détecter les déséquilibres entre les cœurs physiques. Pour activer ce mode, utilisez --per-core en plus de -a. (en mode système). La sortie inclut le numéro du cœur et le nombre de processeurs logiques en ligne sur ce processeur physique.

--per-thread

Agrège les comptages par threads surveillés, lors de la surveillance de threads (-t option) ou de processus (-p option).

--per-node

Agrège les comptages par nœuds NUMA pour les mesures en mode système. C'est un mode utile pour détecter les déséquilibres entre les nœuds NUMA. Pour activer ce mode, utilisez --per-node en plus de -a. (en mode système).

-D msecs, --delay msecs

Après avoir démarré le programme, attend msecs avant de mesurer (-1 : démarrage avec les événements désactivés). Ceci est utile pour filtrer la phase de démarrage du programme, qui est souvent très différente.

-T, --transaction

Affiche les statistiques d'exécution transactionnelle si pris en charge.

--metric-no-group

Par défaut, les événements pour calculer une métrique sont placés dans des groupes faibles. Le groupe tente d'ordonnancer tous les événements ou aucun. L'option --metric-no-group place les événements en dehors des groupes et peut augmenter la probabilité que l'événement soit ordonnancé, conduisant à une plus grande précision. Cependant, comme les événements peuvent ne pas être ordonnancés ensemble, la précision des métriques comme les cycles par instruction peut être plus faible, car les deux métriques peuvent ne plus être mesurées en même temps.

--metric-no-merge

Par défaut, les événements de métrique dans différents groupes faibles peuvent être partagés si un groupe contient tous les événements nécessaires à un autre. Dans de tels cas, un groupe sera éliminé, réduisant le multiplexage des événements et faisant en sorte que certains groupes de métriques somment à 100 %. Un inconvénient du partage d'un groupe est que celui-ci peut nécessiter un multiplexage et donc réduire la précision d'un petit groupe qui n'en aurait pas besoin. Cette option interdit la logique de fusion d'événements de partager des événements entre les groupes et peut être utilisée pour augmenter la précision dans ce cas.

--metric-no-threshold

Les seuils de métrique peuvent augmenter le nombre d'événements nécessaires pour calculer si une métrique a dépassé son expression de seuil. Cela peut ne pas être souhaitable, par exemple, car les événements peuvent introduire un multiplexage. Cette option désactive l'ajout d'événements d'expression de seuil pour une métrique. Cependant, s'il y a suffisamment d'événements pour calculer le seuil, le seuil est toujours calculé et utilisé pour colorer la valeur calculée de la métrique.

--quiet

Ne pas afficher la sortie, les avertissements ou les messages. C'est utile avec perf stat record ci-dessous pour n'écrire que les données dans le fichier perf.data.

-M, --metrics

Affiche les métriques ou les groupes de métriques spécifiés dans une liste séparée par des virgules. Pour un groupe, toutes les métriques du groupe sont ajoutées. Les événements des métriques sont mesurés automatiquement. Consultez la sortie de perf list pour connaître les métriques et groupes de métriques possibles. 
Lorsque des informations de seuil sont disponibles pour une métrique, la
couleur rouge est utilisée pour indiquer qu'une métrique a dépassé un seuil,
tandis que le vert indique qu'elle ne l'a pas fait. La couleur par défaut
signifie qu'aucune information de seuil n'était disponible ou que le seuil
n'a pas pu être calculé.

-A, --no-aggr, --no-merge

N'agrège/fusionne pas les comptages sur les CPU ou les PMU surveillés.

Lorsque plusieurs événements sont créés à partir d'une seule spécification d'événement, stat agrège par défaut les comptages d'événements et affiche le résultat sur une seule ligne. Cette option désactive ce comportement et affiche les événements et les comptages individuels.

Plusieurs événements sont créés à partir d'une seule spécification d'événement lorsque :

1.La surveillance de PID n'est pas demandée et le système a plus d'un CPU. Par exemple, un système avec 8 threads SMT aura un événement ouvert sur chaque thread et l'agrégation sera effectuée entre eux.
2.Un préfixe ou un joker est utilisé pour le nom du PMU. Par exemple, plusieurs PMU de contrôleurs mémoire peuvent exister, généralement avec un suffixe _0, _1, etc. Par défaut, les comptages d'événements seront tous combinés si le PMU est spécifié sans le suffixe, comme uncore_imc plutôt que uncore_imc_0.
3.Des alias, qui sont listés immédiatement après les événements PMU du noyau par perf list, sont utilisés.

OPTIONS

--group

Print event counts as groups of PMUs. For instance, on an Intel hybrid system, this option aggregates counts from both the core PMU and the atom PMU. By default, each core PMU will report its count separately. This option forces core PMU counts to be combined to give a behavior closer to having a single CPU type in the system.

--topdown

Print top-down metrics supported by the CPU. This allows to determine bottle necks in the CPU pipeline for CPU bound workloads, by breaking the cycles consumed down into frontend bound, backend bound, bad speculation and retiring.

Frontend bound means that the CPU cannot fetch and decode instructions fast enough. Backend bound means that computation or memory access is the bottle neck. Bad Speculation means that the CPU wasted cycles due to branch mispredictions and similar issues. Retiring means that the CPU computed without an apparently bottleneck. The bottleneck is only the real bottleneck if the workload is actually bound by the CPU and not by something else.

For best results it is usually a good idea to use it with interval mode like -I 1000, as the bottleneck of workloads can change often.

This enables --metric-only, unless overridden with --no-metric-only.

The following restrictions only apply to older Intel CPUs and Atom, on newer CPUs (IceLake and later) TopDown can be collected for any thread:

The top down metrics are collected per core instead of per CPU thread. Per core mode is automatically enabled and -a (global monitoring) is needed, requiring root rights or perf.perf_event_paranoid=-1.

Topdown uses the full Performance Monitoring Unit, and needs disabling of the NMI watchdog (as root): echo 0 > /proc/sys/kernel/nmi_watchdog for best results. Otherwise the bottlenecks may be inconsistent on workload with changing phases.

To interpret the results it is usually needed to know on which CPUs the workload runs on. If needed the CPUs can be forced using taskset.

--record-tpebs

Enable automatic sampling on Intel TPEBS retire_latency events (event with :R modifier). Without this option, perf would not capture dynamic retire_latency at runtime. Currently, a zero value is assigned to the retire_latency event when this option is not set. The TPEBS hardware feature starts from Intel Granite Rapids microarchitecture. This option only exists in X86_64 and is meaningful on Intel platforms with TPEBS feature.

--tpebs-mode=[mean|min|max|last]

Set how retirement latency events have their sample times combined. The default "mean" gives the average of retirement latency. "min" or "max" give the smallest or largest retirment latency times respectively. "last" uses the last retirment latency sample’s time.

--td-level

Print the top-down statistics that equal the input level. It allows users to print the interested top-down metrics level instead of the level 1 top-down metrics.

As the higher levels gather more metrics and use more counters they will be less accurate. By convention a metric can be examined by appending _group to it and this will increase accuracy compared to gathering all metrics for a level. For example, level 1 analysis may highlight tma_frontend_bound. This metric may be drilled into with tma_frontend_bound_group with perf stat -M tma_frontend_bound_group....

Error out if the input is higher than the supported max level.

--smi-cost

Measure SMI cost if msr/aperf/ and msr/smi/ events are supported.

During the measurement, the /sys/device/cpu/freeze_on_smi will be set to freeze core counters on SMI. The aperf counter will not be effected by the setting. The cost of SMI can be measured by (aperf - unhalted core cycles).

In practice, the percentages of SMI cycles is very useful for performance oriented analysis. --metric_only will be applied by default. The output is SMI cycles%, equals to (aperf - unhalted core cycles) / aperf

Users who wants to get the actual value can apply --no-metric-only.

--all-kernel

Configure all used events to run in kernel space.

--all-user

Configure all used events to run in user space.

--percore-show-thread

The event modifier "percore" has supported to sum up the event counts for all hardware threads in a core and show the counts per core.

This option with event modifier "percore" enabled also sums up the event counts for all hardware threads in a core but show the sum counts per hardware thread. This is essentially a replacement for the any bit and convenient for post processing.

--summary

Print summary for interval mode (-I).

--no-csv-summary

Don’t print summary at the first column for CVS summary output. This option must be used with -x and --summary.

This option can be enabled in perf config by setting the variable stat.no-csv-summary.

$ perf config stat.no-csv-summary=true

--cputype

Only enable events on applying cpu with this type for hybrid platform (e.g. core or atom)"

83.409183620 secondes de temps écoulé

Pour les sessions de charge de travail, nous affichons également le temps passé par les charges de travail dans les espaces utilisateur/système :

74.684747000 secondes utilisateur
 8.739217000 secondes système

Ces temps sont identiques à ceux affichés par l'outil time.

FORMAT CSV

Avec -x, perf stat est capable de sortir un format de sortie pas tout à fait CSV. Les virgules dans la sortie ne sont pas mises entre guillemets. Pour faciliter l'analyse, il est recommandé d'utiliser un caractère différent comme -x \;

Les champs sont dans cet ordre :

•horodatage optionnel en microsecondes en fractions de seconde (avec -I xxx)
•identifiant optionnel de CPU, de cœur ou de socket
•nombre optionnel de CPUs logiques agrégés
•valeur du compteur
•unité de la valeur du compteur ou vide
•nom de l'événement
•temps d'exécution du compteur
•pourcentage du temps de mesure pendant lequel le compteur était en cours d'exécution
•variance optionnelle si plusieurs valeurs sont collectées avec -r
•valeur métrique optionnelle
•unité métrique optionnelle

Des métriques supplémentaires peuvent être affichées avec tous les champs précédents vides.

SUPPORT INTEL HYBRIDE

Support pour les événements hybrides Intel dans les outils perf.

Pour certaines plateformes Intel, comme AlderLake, qui est une plateforme hybride et qui se compose de CPUs atom et de CPUs core. Chaque CPU a une liste d'événements dédiée. Une partie des événements est disponible sur les CPUs core, une partie des événements est disponible sur les CPUs atom et même une partie des événements est disponible sur les deux.

Le noyau exporte deux nouveaux pmu de CPU via sysfs : /sys/bus/event_source/devices/cpu_core /sys/bus/event_source/devices/cpu_atom

Les fichiers cpus sont créés dans les répertoires. Par exemple,

cat /sys/bus/event_source/devices/cpu_core/cpus 0-15

cat /sys/bus/event_source/devices/cpu_atom/cpus 16-23

Cela indique que les CPUs 0-15 sont des CPUs core et que les CPUs 16-23 sont des CPUs atom.

Comme auparavant, utilisez perf-list pour lister l'événement symbolique.

perf list

inst_retired.any [Fixed Counter: Compte le nombre d'instructions retirées. Unité : cpu_atom] inst_retired.any [Nombre d'instructions retirées. Compteur fixe - événement architectural. Unité : cpu_core]

L'indication Unité : xxx est ajoutée à la brève description pour indiquer à quel pmu l'événement appartient. Le même nom d'événement mais avec un pmu différent peut être supporté.

Activer l'événement hybride avec un pmu spécifique

Pour activer un événement uniquement pour le core ou uniquement pour l'atom, la syntaxe suivante est prise en charge :

        cpu_core/<nom_événement>/
ou
        cpu_atom/<nom_événement>/

Par exemple, pour compter l'événement cycles sur les CPUs core.

perf stat -e cpu_core/cycles/

Créer automatiquement deux événements pour un événement matériel

Lors de la création d'un événement et que cet événement est disponible à la fois sur l'atom et sur le core, deux événements sont créés automatiquement. L'un est pour l'atom, l'autre pour le core. La plupart des événements matériels et des événements de cache sont disponibles sur cpu_core et cpu_atom.

Pour les événements matériels, ils ont des configurations prédéfinies (par exemple, 0 pour cycles). Mais sur une plateforme hybride, le noyau doit savoir d'où vient l'événement (de l'atom ou du core). Le type d'événement perf d'origine PERF_TYPE_HARDWARE ne peut pas transporter d'informations sur le pmu. Il est donc maintenant étendu pour être un type conscient du PMU. L'ID du type PMU est stocké dans attr.config[63:32].

L'ID du type PMU est récupéré à partir de sysfs. /sys/bus/event_source/devices/cpu_atom/type /sys/bus/event_source/devices/cpu_core/type

La nouvelle disposition de attr.config pour PERF_TYPE_HARDWARE :

PERF_TYPE_HARDWARE: 0xEEEEEEEE000000AA AA : ID de l'événement matériel EEEEEEEE : ID du type PMU

L'événement de cache est similaire. Le type PERF_TYPE_HW_CACHE est étendu pour être un type conscient du PMU. L'ID du type PMU est stocké dans attr.config[63:32].

La nouvelle disposition de attr.config pour PERF_TYPE_HW_CACHE :

PERF_TYPE_HW_CACHE: 0xEEEEEEEE00DDCCBB BB : ID du cache matériel CC : ID de l'opération du cache matériel DD : ID du résultat de l'opération du cache matériel EEEEEEEE : ID du type PMU

perf-stat(1) - Page de manuel en français

NOM

perf-stat - Collecter et analyser les compteurs de performance du système

SYNOPSIS

perf stat [perf options] [--command[Args]]

DESCRIPTION

perf-stat est un outil utilitaire pour collecter et analyser les compteurs de performance du système. Il peut être utilisé pour collecter des événements pour l'ensemble du système, des processus spécifiques ou des threads.

OPTIONS

Vous pouvez spécifier les options suivantes :

-e event
Spécifie les événements de performance à collecter. Peut être un nom d'événement (par exemple, « cycles », « instructions »), un nom d'événement avec un nom de PMU (par exemple, « cpu_core/cycles/ »), un ID d'événement ou un qualificateur.
-a, --all-cpu
Collecter les événements pour l'ensemble du système.
-p pid
Collecter les événements pour le processus spécifié.
-t tid
Collecter les événements pour le thread spécifié.
-I [interval in ms]
Afficher la sortie en mode intervalle.
-r [nr_runs]
Répéter les mesures plusieurs fois et afficher la variance.
-v, --verbose
Afficher plus d'informations sur les événements et les compteurs.
-j, --json
Afficher la sortie au format JSON.
-h, --help
Afficher le message d'aide.

STAT RECORD

Lorsque vous utilisez perf record, si aucun événement n'est spécifié sur une plateforme hybride, deux événements cycles par défaut sont créés et ajoutés à la liste des événements. L'un est pour le cœur (core) et l'autre pour l'atome (atom).

STAT REPORT

Lorsque vous utilisez perf stat, si aucun événement n'est spécifié sur une plateforme hybride, en plus des événements logiciels, les événements suivants sont créés et ajoutés à la liste des événements dans l'ordre :

cpu_core/cycles/, cpu_atom/cycles/, cpu_core/instructions/, cpu_atom/instructions/, cpu_core/branches/, cpu_atom/branches/, cpu_core/branch-misses/, cpu_atom/branch-misses/

EXAMPLES

Activer un événement matériel sans PMU spécifié, par exemple, perf stat -e cycles -a (utilisation du système entier dans cet exemple), deux événements sont créés automatiquement.

------------------------------------------------------------
perf_event_attr:
  size                             120
  config                           0x400000000
  sample_type                      IDENTIFIER
  read_format                      TOTAL_TIME_ENABLED|TOTAL_TIME_RUNNING
  disabled                         1
  inherit                          1
  exclude_guest                    1
------------------------------------------------------------

et

------------------------------------------------------------
perf_event_attr:
  size                             120
  config                           0x800000000
  sample_type                      IDENTIFIER
  read_format                      TOTAL_TIME_ENABLED|TOTAL_TIME_RUNNING
  disabled                         1
  inherit                          1
  exclude_guest                    1
------------------------------------------------------------

Le type 0 est PERF_TYPE_HARDWARE. 0x4 dans 0x400000000 indique que c'est le PMU cpu_core. 0x8 dans 0x800000000 indique que c'est le PMU cpu_atom (l'ID du type de PMU atom est aléatoire).

Le noyau crée cycles (0x400000000) sur les CPU0-CPU15 (cœurs de CPU), et crée cycles (0x800000000) sur les CPU16-CPU23 (CPU atom).

Pour le résultat perf-stat, il affiche deux événements :

Performance counter stats for 'system wide':
6,744,979      cpu_core/cycles/
1,965,552      cpu_atom/cycles/

Le premier cycles est l'événement du cœur, le second cycles est l'événement de l'atome.

Exemple en mode thread :

perf-stat affiche les comptes mis à l'échelle pour les événements hybrides et avec un pourcentage affiché. Le pourcentage est le temps d'exécution/temps d'activation de l'événement.

Un exemple, triad_loop s'exécute sur le CPU16 (cœur atom), tandis que nous pouvons voir la valeur mise à l'échelle pour les cycles du cœur est de 160 444 092 et le pourcentage est de 0,47 %.

perf stat -e cycles -- taskset -c 16 ./triad_loop

  disabled                         1
  inherit                          1
  enable_on_exec                   1
  exclude_guest                    1
.ft

et

.ft C
perf_event_attr:

perf-record :

S'il n'y a pas de -e spécifié dans perf record, sur une plateforme hybride, il crée deux cycles par défaut et les ajoute à la liste des événements. L'un est pour le cœur, l'autre pour l'atome.

perf-stat :

S'il n'y a pas de -e spécifié dans perf stat, sur une plateforme hybride, en plus des événements logiciels, les événements suivants sont créés et ajoutés à la liste des événements dans l'ordre.

cpu_core/cycles/, cpu_atom/cycles/, cpu_core/instructions/, cpu_atom/instructions/, cpu_core/branches/, cpu_atom/branches/, cpu_core/branch-misses/, cpu_atom/branch-misses/

Bien sûr, perf-stat et perf-record prennent tous deux en charge l'activation d'événements hybrides avec un PMU spécifique.

par exemple, perf stat -e cpu_core/cycles/ perf stat -e cpu_atom/cycles/ perf stat -e cpu_core/r1a/ perf stat -e cpu_atom/L1-icache-loads/ perf stat -e cpu_core/cycles/,cpu_atom/instructions/ perf stat -e {cpu_core/cycles/,cpu_core/instructions/}

Mais {cpu_core/cycles/,cpu_atom/instructions/} retournera un avertissement et désactivera le regroupement, car les PMU dans le groupe ne correspondent pas (cpu_core vs. cpu_atom).

TIMINGS

Voici les informations relatives aux timings :

•TOTAL_TIME_ENABLED : temps total pendant lequel l'événement a été activé.
•TOTAL_TIME_RUNNING : temps total pendant lequel l'événement était en cours d'exécution.

Ces valeurs sont utilisées pour calculer le pourcentage de temps pendant lequel l'événement était actif par rapport au temps total.

CSV FORMAT

Avec -c, perf stat peut afficher la sortie au format CSV (valeurs séparées par des virgules).

•Période : période optionnelle en fractions de seconde (avec -I)
•Options d'agrégation optionnelles :
•cœur : identifiant du cœur (avec --per-core)
•die : identifiant du die (avec --per-die)
•socket : identifiant du socket (avec --per-socket)
•node : identifiant du nœud (avec --per-node)
•thread : identifiant du thread (avec --per-thread)
•compteurs : nombre de compteurs PMU agrégés
•valeur_compteur : valeur du compteur
•unité : unité de la valeur du compteur ou vide
•événement : nom de l'événement
•variance : variance optionnelle si plusieurs valeurs sont collectées (avec -r)
•temps_exécution_événement : temps d'exécution de l'événement
•pourcentage_exécution : pourcentage du temps pendant lequel l'événement était en cours d'exécution
•valeur_métrique : valeur métrique optionnelle
•unité_métrique : unité métrique optionnelle
