PERLCLASSGUTS(1perl) Guide du programmeur Perl PERLCLASSGUTS(1perl)

NOM

perlclassguts - Internes de la façon dont "feature 'class'" et la syntaxe des classes fonctionnent

DESCRIPTION

Ce document fournit des informations approfondies sur la manière dont l'interpréteur Perl implémente la syntaxe "feature 'class'" et son comportement général. Il n'est pas destiné à être un guide pour l'utilisateur final sur la façon d'utiliser cette fonctionnalité. Pour cela, voir perlclass.

Le lecteur est censé être généralement familier avec les internes de l'interpréteur Perl en général. Pour un aperçu plus général de ces détails, voir également perlguts.

STOCKAGE DES DONNÉES

Classes

Une classe est fondamentalement un package et existe dans la table des symboles en tant que HV avec une structure auxiliaire, exactement de la même manière qu'un package non-classe. Elle est distinguée d'un package non-classe par le fait que la macro HvSTASH_IS_CLASS() renvoie vrai pour elle.

Des informations supplémentaires la concernant en tant que classe sont stockées dans la structure "struct xpvhv_aux" attachée au stash, dans les champs suivants :

HV          *xhv_class_superclass;
CV          *xhv_class_initfields_cv;
AV          *xhv_class_adjust_blocks;
PADNAMELIST *xhv_class_fields;
PADOFFSET    xhv_class_next_fieldix;
HV          *xhv_class_param_map;
  • "xhv_class_superclass" sera "NULL" pour une classe sans superclasse. Il pointera directement vers le stash de la classe parente si une a été définie avec l'attribut de classe :isa().
  • "xhv_class_initfields_cv" contiendra un "CV *" pointant vers une fonction à appeler dans le cadre du constructeur de cette classe ou de toute sous-classe de celle-ci. Ce CV est responsable de l'initialisation de tous les champs définis par cette classe pour une nouvelle instance. Ce CV sera une fonction réelle anonyme - c'est-à-dire que bien qu'il n'ait pas de nom ni de GV, ce n'est *pas* un protosub et il peut être invoqué directement.
  • "xhv_class_adjust_blocks" peut pointer vers un AV contenant des pointeurs de CV vers chacun des blocs "ADJUST" définis sur la classe. Si la classe a une superclasse, ce tableau contiendra également des pointeurs dupliqués des CV de sa classe parente. L'AV est créé paresseusement lors de la première poussée d'un élément ; il est valide qu'il n'y en ait pas, et ce pointeur sera "NULL" dans ce cas.

    Les CV sont stockés directement, pas via des RV. Chaque CV sera une fonction réelle anonyme.

  • "xhv_class_fields" pointera vers une "PADNAMELIST" contenant des "PADNAME"s, chacun étant un champ défini de la classe. Ils sont stockés dans l'ordre de déclaration. Notez cependant que l'index dans ce tableau ne sera pas nécessairement égal au "fieldix" de chaque champ, car dans le cas d'une sous-classe, le tableau commencera à zéro mais l'index du premier champ qu'il contient sera non nul si sa classe parente contient des champs.

    Pour plus d'informations sur la façon dont les champs individuels sont représentés, voir "Champs".

  • "xhv_class_next_fieldix" donne l'index de champ qui sera assigné au prochain champ à ajouter à la classe. Il n'est utile qu'à la compilation.
  • "xhv_class_param_map" peut pointer vers un HV qui mappe les noms d'attributs de champ ":param" à l'index de champ du champ portant ce nom. Cette mappage est copié des classes parentes ; chaque classe contiendra le total de ses parents en plus des siens.

Champs

Un champ est toujours fondamentalement une variable lexicale déclarée dans une portée, et existe dans la "PADNAMELIST" de son CV correspondant. Les méthodes et autres CV de type méthode peuvent toujours les capturer exactement comme elles le peuvent avec des lexicals régulières. Un champ est distingué des autres types d'entrées de PAD par le fait que la macro PadnameIsFIELD() renvoie vrai pour lui.

Des informations supplémentaires le concernant en tant que champ sont stockées dans une structure supplémentaire accessible via la macro PadnameFIELDINFO() sur le padname. Cette structure a les champs suivants :

PADOFFSET  fieldix;
HV        *fieldstash;
OP        *defop;
SV        *paramname;
bool       def_if_undef;
bool       def_if_false;
  • "fieldix" stocke l'"index de champ" du champ ; c'est-à-dire, l'index dans le tableau de champs de l'instance où la valeur de ce champ sera stockée. Notez que le premier index du tableau n'est pas spécialement réservé. Le premier champ d'une classe commencera à l'index de champ 0.
  • "fieldstash" stocke un pointeur vers le stash de la classe qui a défini ce champ. Ceci est nécessaire au cas où il y aurait plusieurs classes définies dans la même portée ; il est utilisé pour désambiguïser les champs de chacune. 
    {
    class C1; field $x;
    class C2; field $x;
}
  • "defop" peut stocker un pointeur vers un arbre d'opérations d'expression par défaut pour ce champ. Les expressions par défaut sont optionnelles ; ce champ peut être "NULL".
  • "paramname" peut pointer vers un SV de chaîne régulier contenant l'attribut ":param" donné au champ. S'il n'y en a pas, il sera "NULL".
  • L'un de "def_if_undef" et "def_if_false" sera vrai si l'expression par défaut a été définie en utilisant respectivement les opérateurs "//=" ou "||=".

Méthodes

Une méthode est toujours fondamentalement un CV, et a la même représentation de base qu'un CV. Elle a un optree et un pad, et est stockée via un GV dans le stash de son package contenant. Elle est distinguée d'un CV non-méthode par le fait que la macro CvIsMETHOD() renvoie vrai pour elle.

(Note : Cette macro ne doit pas être confondue avec celle qui était précédemment appelée CvMETHOD(). Celle-ci n'est pas liée au système de classes, et a été renommée en CvNOWARN_AMBIGUOUS() pour éviter cette confusion.)

Il n'y a actuellement aucune information supplémentaire à stocker sur un CV de méthode, donc la structure n'ajoute aucun nouveau champ.

Instances

Les instances d'objets sont représentées par un tout nouveau type de SV, dont le type de base est "SVt_PVOBJ". Il doit toujours être béni dans le stash de sa classe et enveloppé dans un RV de la manière habituelle pour les objets classiques.

Comme il s'agit de leur propre type de conteneur unique, distinct des hashes ou des arrays, la fonction principale "builtin::reftype" renvoie une nouvelle valeur lorsqu'on l'interroge sur ces objets. Cette valeur est "OBJECT".

En interne, un tel objet est un tableau de pointeurs SV dont la taille est fixée à la création (car le nombre de champs d'une classe est connu après la compilation). Une instance d'objet stocke l'index de champ maximum à l'intérieur (pour une vérification d'erreur de base lors de l'accès), et un tableau de taille fixe de pointeurs SV stockant les valeurs des champs individuels.

Les champs de type tableau et hash stockent directement des pointeurs AV ou HV dans le tableau ; ils ne sont pas stockés via un RV intermédiaire.

API

Les structures de données décrites ci-dessus sont supportées par les fonctions API suivantes.

Manipulation des classes

class_setup_stash

void class_setup_stash(HV *stash);

Appelé par l'analyseur lors de la rencontre du mot-clé "class". Il met à niveau le stash pour en faire une classe et le prépare à recevoir des éléments spécifiques aux classes tels que les méthodes et les champs.

class_seal_stash

vo
id class_seal_stash(HV *stash);

Appelé par l'analyseur à la fin d'un bloc "class", ou pour les classes unitaires, son portée parente. Cette fonction effectue diverses activités de finalisation qui sont nécessaires avant que des instances de la classe puissent être construites, mais qui n'auraient pas pu être effectuées tant que toutes les informations sur les membres de la classe n'étaient pas connues.

Toutes les additions ou modifications de la classe en cours de compilation doivent être effectuées entre ces deux appels de fonction. Les classes ne peuvent pas être modifiées une fois qu'elles ont été scellées.

class_add_field

void class_add_field(HV *stash, PADNAME *pn);

Appelé par pad.c dans le cadre de la définition d'un nouveau nom de champ dans le pad actuel. Notez que cette fonction ne crée pas le nom de pad ; cela doit déjà être fait par pad.c. Cette fonction API informe simplement la classe que le nouveau nom de champ a été créé et est maintenant disponible pour elle.

class_add_ADJUST

void class_add_ADJUST(HV *stash, CV *cv);

Appelé par l'analyseur une fois qu'il a analysé et construit un CV pour un nouveau bloc "ADJUST". Ceci est ajouté à la liste stockée par la classe.

Manipulation des champs

class_prepare_initfield_parse

void class_prepare_initfield_parse();

Appelé par l'analyseur juste avant d'analyser une expression d'initialisation pour une variable de champ. Ceci utilise un compcv suspendu pour combiner toutes les expressions d'initialisation de champ dans le même CV.

class_set_field_defop

void class_set_field_defop(PADNAME *pn, OPCODE defmode, OP *defop);

Appelé par l'analyseur après qu'il a analysé une expression d'initialisation pour le champ. Définit l'expression et le mode d'application par défaut. "defmode" doit être soit zéro, soit l'un de "OP_ORASSIGN" ou "OP_DORASSIGN" selon le mode de défaut.

padadd_FIELD

#define padadd_FIELD

Cette constante de drapeau indique à la famille de fonctions "pad_add_name_*" que le nouveau nom doit être ajouté comme champ. Il n'est pas nécessaire d'appeler class_add_field() ; cela sera fait automatiquement.

Manipulation des méthodes

class_prepare_method_parse

void class_prepare_method_parse(CV *cv);

Appelé par l'analyseur après start_subparse() mais immédiatement avant de faire quoi que ce soit d'autre. Ceci prépare le "PL_compcv" pour l'analyse d'une méthode ; organisant pour que le test "CvIsMETHOD" soit vrai, ajoutant le lexique $self, et toute autre activité qui pourrait être nécessaire.

class_wrap_method_body

OP *class_wrap_method_body(OP *o);

Appelé par l'analyseur à la fin de l'analyse du corps d'une méthode dans un arbre d'opérations mais juste avant de l'envelopper dans le CV final. Cette fonction insère des ops supplémentaires dans l'arbre d'opérations pour que la méthode fonctionne correctement.

Instances d'objets

SVt_PVOBJ

#define SVt_PVOBJ

Une constante de type SV utilisée pour la comparaison avec la macro SvTYPE().

ObjectMAXFIELD

SSize_t ObjectMAXFIELD(sv);

Une macro de type fonction qui obtient l'indice de champ maximal valide qui peut être accédé à partir du tableau "ObjectFIELDS".

ObjectFIELDS

SV **ObjectFIELDS(sv);

Une macro de type fonction qui obtient directement le tableau de champs à partir d'une instance d'objet. Les champs peuvent être accédés par leur indice de champ, de 0 jusqu'à l'indice maximal valide donné par "ObjectMAXFIELD".

OPCODES

OP_METHSTART

newUNOP_AUX(OP_METHSTART, ...);

Un "OP_METHSTART" est un "UNOP_AUX" qui doit être présent au début d'un CV de méthode pour qu'il fonctionne correctement. Ceci est inséré par class_wrap_method_body(), et apparaît même avant tout fragment d'arbre d'opérations associé à la vérification ou à l'extraction des arguments de la signature.

Cet op est responsable du décalage de la valeur de $self hors de la liste des arguments et de la liaison de tous les champs que la méthode nécessite d'accéder dans le pad. Le vecteur AUX contiendra des détails sur les associations champ/indice de pad requises.

Cet op effectue également une vérification de cohérence sur la valeur invocante. Il vérifie qu'il s'agit bien d'une référence d'objet d'un type de classe compatible. Sinon, une exception est levée.

Si le champ "op_private" inclut le drapeau "OPpINITFIELDS", cela indique que l'op commence le CV spécial "xhv_class_initfields_cv". Dans ce cas, il doit en plus prendre la deuxième valeur de la liste des arguments, qui doit être un pointeur HV simple ( *directement*, pas via RV), et le lier au deuxième emplacement du pad, où l'arbre d'opérations généré s'attendra à le trouver.

OP_INITFIELD

Un "OP_INITFIELD" n'est invoqué que dans le cadre du CV "xhv_class_initfields_cv" pendant la phase de construction d'une instance. C'est à ce moment que les SV individuels qui composent les champs mutables de l'instance (y compris les AV et les HV) sont réellement assignés dans le tableau "ObjectFIELDS". Les drapeaux privés "OPpINITFIELD_AV" et "OPpINITFIELD_HV" indiquent s'il crée un AV ou un HV ; si aucun n'est défini, un SV est créé.

Si l'op a le drapeau "OPf_STACKED", il s'attend à trouver une valeur d'initialisation sur la pile. Pour les SV, c'est le SV le plus haut sur la pile de données. Pour les AV et les HV, il attend une liste marquée.

COMPORTEMENT À LA COMPILATION

Phasers "ADJUST"

Lors de la compilation, l'analyse d'un phaser "ADJUST" est gérée d'une manière fondamentalement différente des phasers perl existants ("BEGIN", etc...)

Au lieu de suivre la voie habituelle, le tokenizer reconnaît que le mot-clé "ADJUST" introduit un bloc phaser. L'analyseur analyse ensuite le corps de ce bloc de manière similaire à la façon dont il analyserait un corps de méthode (anonyme), créant un CV sans nom GV. Celui-ci est ensuite inséré directement dans les informations de la classe en appelant "class_add_ADJUST", contournant complètement la table des symboles.

Attributs

Pendant la compilation, les attributs des classes et des champs sont gérés d'une manière différente des attributs perl existants sur les sous-routines et les variables lexicales.

L'analyseur forme toujours un arbre d'opérations "OP_LIST" de nœuds "OP_CONST", mais ceux-ci sont passés aux fonctions "class_apply_attributes" ou "class_apply_field_attributes". Plutôt que d'utiliser une recherche de classe pour une méthode dans la classe en cours d'analyse, une liste interne fixe d'attributs connus est utilisée pour trouver les fonctions d'application de l'attribut à la classe ou au champ. À l'avenir, cela pourra supporter des extensions d'attributs fournies par l'utilisateur, bien qu'actuellement, il ne reconnaisse que ceux définis par le cœur lui-même.

Expressions d'initialisation de champ

Pendant la compilation, l'analyseur utilise un compcv suspendu lors de l'analyse de l'expression de défaut pour un champ. Toutes les expressions de tous les champs de la classe partagent le même compcv suspendu, qui est ensuite compilé dans le même CV interne appelé par le constructeur pour initialiser tous les champs fournis par cette classe.

COMPORTEMENT À L'EXÉCUTION

Constructeur

Le constructeur généré pour une classe est lui-même un XSUB qui effectue trois tâches dans l'ordre : il crée le SV d'instance lui-même, invoque les initialisateurs de champ, puis invoque les CV de bloc ADJUST. Le constructeur de toute classe a toujours la même forme de base, que la classe ait ou non une superclasse.

Les initialisateurs de champ sont collectés dans un CV généré basé sur un arbre d'opérations, appelé le CV d'initialiseur de champ. C'est le CV qui contient tous les fragments d'arbre d'opérations pour les expressions d'initialisation de champ. Lorsqu'il est invoqué, le CV d'initialiseur de champ peut effectuer un appel chaîné à l'initialiseur de la superclasse s'il en existe un, avant d'invoquer toutes les opérations d'initialisation de champ individuelles. Le CV d'initialiseur de champ est invoqué avec deux éléments sur la pile ; étant le SV d'instance et un HV direct contenant les paramètres du constructeur. Notez bien : ce HV est passé *directement*, pas via une référence RV. Ceci est permis car l'appelant et l'appelé sont du code généré directement et non des sous-routines perl pures arbitraires.

Les CV de bloc ADJUST sont tous collectés dans une seule liste plate, fusionnant également tous ceux définis par la superclasse. Ils sont tous invoqués dans l'ordre, après le CV d'initialiseur de champ.

Accès à $self pendant les méthodes

Lorsque class_prepare_method_parse() est appelé, il s'arrange pour que le pad du corps du nouveau CV commence par un lexique appelé $self. Comme le pad doit être fraîchement créé à ce moment-là, il aura l'indice de pad de 1. La fonction vérifie cela et avorte si ce n'est pas le cas.

NOM

perlclassguts - internes de la gestion des classes Perl

DESCRIPTION

Ce document décrit la manière dont les classes sont implémentées en Perl, en se concentrant sur les structures de données internes et les opérations utilisées lors de la compilation et de l'exécution.

STOCKAGE DES DONNÉES

La gestion des classes en Perl repose sur un ensemble de structures de données internes, notamment les structures de données utilisées pour représenter les objets, les classes et les méthodes.

API

Il existe une API interne qui permet aux différentes parties de l'interpréteur Perl d'interagir avec ces structures de données. Cette API n'est pas destinée à être utilisée directement par les programmeurs Perl.

OPCODES

Plusieurs opcodes de bas niveau sont utilisés pour manipuler les objets et les classes. Parmi eux, on trouve OP_INITFIELD, utilisé pour initialiser les champs d'un objet lors de sa création.

COMPORTEMENT À LA COMPILATION

Lors de la compilation, Perl analyse la définition des classes et prépare les structures de données nécessaires. Par exemple, lors de la création d'un objet, les informations sur les champs sont stockées et accessibles via des indices de remplissage (pad index).

COMPORTEMENT À L'EXÉCUTION

À l'exécution, Perl utilise ces structures pour effectuer des opérations telles que l'appel de méthodes, l'accès aux champs et la gestion de l'héritage. Le remplissage de l'index 1 est utilisé pour obtenir une référence à l'invocant dans le corps d'une méthode ou d'une structure similaire. L'opcode "OP_INITFIELD" s'appuie sur ce fait.

De manière similaire, lors de "xhv_class_initfields_cv", la zone de remplissage suivante est utilisée pour stocker les paramètres du constructeur HV, à l'index de remplissage 2.
