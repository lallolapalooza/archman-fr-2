PERLPACKTUT(1perl) Guide de référence pour programmeurs Perl PERLPACKTUT(1perl)

NOM

perlpacktut - tutoriel sur "pack" et "unpack"

DESCRIPTION

"pack" et "unpack" sont deux fonctions pour transformer des données selon un modèle défini par l'utilisateur, entre la manière dont Perl stocke les valeurs et une représentation bien définie telle qu'elle pourrait être requise dans l'environnement d'un programme Perl. Malheureusement, ce sont aussi deux des fonctions les plus mal comprises et les plus souvent négligées que Perl propose. Ce tutoriel va vous les démystifier.

Le Principe de Base

La plupart des langages de programmation ne protègent pas la mémoire où sont stockées les variables. En C, par exemple, vous pouvez obtenir l'adresse d'une variable, et l'opérateur "sizeof" vous indique combien d'octets sont alloués à la variable. En utilisant l'adresse et la taille, vous pouvez accéder au stockage à votre guise.

En Perl, vous ne pouvez pas simplement accéder à la mémoire de manière aléatoire, mais la conversion structurelle et de représentation fournie par "pack" et "unpack" est une excellente alternative. La fonction "pack" convertit des valeurs en une séquence d'octets contenant des représentations selon une spécification donnée, le soi-disant argument "template". "unpack" est le processus inverse, dérivant certaines valeurs à partir du contenu d'une chaîne d'octets. (Attention, cependant, tout ce qui a été empaqueté ne peut pas être soigneusement désempaqueté - une expérience très courante, comme les voyageurs expérimentés peuvent probablement le confirmer.)

Pourquoi, demanderez-vous, auriez-vous besoin d'un bloc de mémoire contenant des valeurs en représentation binaire ? Une bonne raison est l'accès en entrée/sortie à un fichier, un appareil, ou une connexion réseau, où cette représentation binaire vous est soit imposée, soit vous donnera un avantage dans le traitement. Une autre cause est le passage de données à un appel système qui n'est pas disponible en tant que fonction Perl : "syscall" exige que vous fournissiez des paramètres stockés de la même manière qu'en C. Même le traitement de texte (comme montré dans la section suivante) peut être simplifié par une utilisation judicieuse de ces deux fonctions.

Pour voir comment fonctionne (dé)sempaquetage, nous commencerons par un code de modèle simple où la conversion est au ralenti : entre le contenu d'une séquence d'octets et une chaîne de chiffres hexadécimaux. Utilisons "unpack", car cela vous rappellera probablement un programme de vidage mémoire, ou un dernier message désespéré que les programmes malheureux ont tendance à vous lancer avant d'expirer dans le grand bleu. En supposant que la variable $mem contient une séquence d'octets que nous aimerions inspecter sans rien supposer de sa signification, nous pouvons écrire :

my( $hex ) = unpack( 'H*', $mem );
print "$hex\n";

sur quoi nous pourrions voir quelque chose comme ceci, chaque paire de chiffres hexadécimaux correspondant à un octet :

41204d414e204120504c414e20412043414e414c2050414e414d41

Qu'y avait-il dans ce bloc de mémoire ? Des nombres, des caractères, ou un mélange des deux ? En supposant que nous sommes sur un ordinateur où le codage ASCII (ou similaire) est utilisé : les valeurs hexadécimales dans la plage 0x40 - 0x5A indiquent une lettre majuscule, et 0x20 code un espace. Nous pourrions donc supposer qu'il s'agit d'un morceau de texte, que certains peuvent lire comme un tabloïd ; mais d'autres devront se procurer une table ASCII et revivre ce sentiment de première année. Sans trop nous soucier de la manière de lire ceci, nous notons que "unpack" avec le code de modèle "H" convertit le contenu d'une séquence d'octets en la notation hexadécimale habituelle. Comme "une séquence de" est une indication assez vague de quantité, "H" a été défini pour convertir un seul chiffre hexadécimal, sauf s'il est suivi d'un compte de répétition. Un astérisque pour le compte de répétition signifie utiliser tout ce qui reste.

L'opération inverse - empaqueter le contenu des octets à partir d'une chaîne de chiffres hexadécimaux - est tout aussi facile à écrire. Par exemple :

my $s = pack( 'H2' x 10, 30..39 );
print "$s\n";

Puisque nous fournissons une liste de dix chaînes hexadécimales à 2 chiffres à "pack", le modèle d'empaquetage doit contenir dix codes d'empaquetage. Si cela est exécuté sur un ordinateur avec un codage de caractères ASCII, cela imprimera 0123456789.

Empaqueter du texte

Supposons que vous deviez lire un fichier de données comme celui-ci :

Date      |Description                | Income|Expenditure
01/24/2001 Zed's Camel Emporium                    1147.99
01/28/2001 Flea spray                                24.99
01/29/2001 Camel rides to tourists      235.00

Comment faire ? Vous pourriez penser d'abord à utiliser "split" ; cependant, comme "split" réduit les champs vides, vous ne saurez jamais si un enregistrement était un revenu ou une dépense. Oups. Eh bien, vous pourriez toujours utiliser "substr" :

while (<>) { 
    my $date   = substr($_,  0, 11);
    my $desc   = substr($_, 12, 27);
    my $income = substr($_, 40,  7);
    my $expend = substr($_, 52,  7);
    ...
}

Ce n'est pas vraiment une partie de plaisir, n'est-ce pas ? En fait, c'est pire qu'il n'y paraît ; les yeux perçants remarqueront que le premier champ ne devrait faire que 10 caractères de large, et l'erreur s'est propagée à travers les autres nombres - que nous avons dû compter à la main. C'est donc source d'erreurs et horriblement peu convivial.

Ou peut-être pourrions-nous utiliser des expressions régulières :

while (<>) { 
    my($date, $desc, $income, $expend) = 
        m|(\d\d/\d\d/\d{4}) (.{27}) (.{7})(.*)|;
    ...
}

Beurk. Bon, c'est un peu mieux, mais - bon, voudriez-vous maintenir ça ?

Hé, n'est-ce pas censé être facile en Perl, ce genre de chose ? Eh bien, ça l'est, si vous utilisez les bons outils. "pack" et "unpack" sont conçus pour vous aider lorsque vous traitez des données de largeur fixe comme celles ci-dessus. Jetons un coup d'œil à une solution avec "unpack" :

while (<>) { 
    my($date, $desc, $income, $expend) = unpack("A10xA27xA7A*", $_);
    ...
}

C'est un peu plus joli ; mais il faut décortiquer ce modèle étrange. D'où est-ce que je l'ai sorti ?

OK, regardons à nouveau certaines de nos données ; en fait, nous inclurons les en-têtes, et une règle pratique pour nous aider à suivre notre position.

         1         2         3         4         5        
1234567890123456789012345678901234567890123456789012345678
Date      |Description                | Income|Expenditure
01/28/2001 Flea spray                                24.99
01/29/2001 Camel rides to tourists      235.00

D'après cela, nous pouvons voir que la colonne de date s'étend de la colonne 1 à la colonne 10 - dix caractères de large. Le "pack"-ese" pour "caractère" est "A", et dix d'entre eux sont "A10". Donc, si nous voulions simplement extraire les dates, nous pourrions dire ceci :

my($date) = unpack("A10", $_);

OK, quoi d'autre ? Entre la date et la description se trouve une colonne vide ; nous voulons la sauter. Le modèle "x" signifie "avancer", donc nous en voulons une. Ensuite, nous avons un autre lot de caractères, de 12 à 38. Cela fait 27 caractères supplémentaires, donc "A27". (Ne faites pas l'erreur du poteau indicateur - il y a 27 caractères entre 12 et 38, pas 26. Comptez-les !)

Maintenant, nous sautons un autre caractère et prenons les 7 caractères suivants :

my($date,$description,$income) = unpack("A10xA27xA7", $_);

Maintenant vient la partie astucieuse. Les lignes de notre livre de comptes qui ne sont que des revenus et non des dépenses peuvent se terminer à la colonne 46. Par conséquent, nous ne voulons pas dire à notre modèle "unpack" que nous devons absolument trouver 12 caractères supplémentaires ; nous dirons simplement "s'il reste quelque chose, prenez-le". Comme vous pourriez le deviner d'après les expressions régulières, c'est ce que signifie l'"*" : "utilisez tout ce qui reste".

•
Attention cependant, contrairement aux expressions régulières, si le modèle "unpack" ne correspond pas aux données entrantes, Perl criera et mourra.

Donc, en combinant le tout :

my ($date, $

description, $revenu, $depense) = unpack("A10xA27xA7xA*", $_);

Maintenant, nos données sont analysées. Je suppose que ce que nous pourrions vouloir faire maintenant est de totaliser nos revenus et dépenses, et d'ajouter une autre ligne à la fin de notre grand livre - dans le même format - indiquant combien nous avons rapporté et combien nous avons dépensé :

while (<>) {
    my ($date, $desc, $revenu, $depense) =
        unpack("A10xA27xA7xA*", $_);
    $tot_revenu += $revenu;
    $tot_depense += $depense;
}
$tot_revenu = sprintf("%.2f", $tot_revenu); # Les mettre en
$tot_depense = sprintf("%.2f", $tot_depense); # format "financier"
$date = POSIX::strftime("%m/%d/%Y", localtime);
# OK, allons-y :
print pack("A10xA27xA7xA*", $date, "Totaux",
    $tot_revenu, $tot_depense);

Oh, hmm. Cela n'a pas tout à fait fonctionné. Voyons ce qui s'est passé :

01/24/2001 Zed's Camel Emporium                     1147.99
01/28/2001 Flea spray                                 24.99
01/29/2001 Camel rides to tourists     1235.00
03/23/2001Totals                     1235.001172.98

OK, c'est un début, mais qu'en est-il des espaces ? Nous avons mis "x", n'est-ce pas ? Ne devrait-il pas sauter vers l'avant ? Regardons ce que dit "pack" dans perlfunc :

x   Un octet nul.

Argh. Pas étonnant. Il y a une grande différence entre "un octet nul", le caractère zéro, et "un espace", le caractère 32. Perl a mis quelque chose entre la date et la description - mais malheureusement, nous ne pouvons pas le voir !

Ce que nous devons réellement faire, c'est étendre la largeur des champs. Le format "A" remplit les caractères inexistants avec des espaces, nous pouvons donc utiliser les espaces supplémentaires pour aligner nos champs, comme ceci :

print pack("A11 A28 A8 A*", $date, "Totaux",
    $tot_revenu, $tot_depense);

(Notez que vous pouvez mettre des espaces dans le modèle pour le rendre plus lisible, mais ils ne se traduisent pas par des espaces dans la sortie.) Voici ce que nous avons obtenu cette fois :

01/24/2001 Zed's Camel Emporium                     1147.99
01/28/2001 Flea spray                                 24.99
01/29/2001 Camel rides to tourists     1235.00
03/23/2001 Totals                      1235.00 1172.98

C'est un peu mieux, mais nous avons toujours cette dernière colonne qui doit être déplacée plus loin. Il y a un moyen simple de résoudre ce problème : malheureusement, nous ne pouvons pas faire en sorte que "pack" justifie nos champs à droite, mais nous pouvons faire en sorte que "sprintf" le fasse :

$tot_revenu = sprintf("%.2f", $tot_revenu);
$tot_depense = sprintf("%12.2f", $tot_depense);
$date = POSIX::strftime("%m/%d/%Y", localtime);
print pack("A11 A28 A8 A*", $date, "Totaux",
    $tot_revenu, $tot_depense);

Cette fois, nous obtenons le bon résultat :

01/28/2001 Flea spray                                 24.99
01/29/2001 Camel rides to tourists     1235.00
03/23/2001 Totals                      1235.00      1172.98

Voilà donc comment nous consommons et produisons des données de largeur fixe. Récapitulons ce que nous avons vu de "pack" et "unpack" jusqu'à présent :

  • Utilisez "pack" pour passer de plusieurs éléments de données à une version de largeur fixe ; utilisez "unpack" pour transformer une chaîne de format de largeur fixe en plusieurs éléments de données.
  • Le format de pack "A" signifie "tout caractère" ; si vous "pack"ez et qu'il ne reste plus rien à packager, "pack" remplira le reste avec des espaces.
  • "x" signifie "sauter un octet" lors de l'"unpack"age ; lors du "pack"age, cela signifie "introduire un octet nul" - ce n'est probablement pas ce que vous voulez dire si vous manipulez du texte brut.
  • Vous pouvez suivre les formats avec des nombres pour indiquer combien de caractères doivent être affectés par ce format : "A12" signifie "prendre 12 caractères" ; "x6" signifie "sauter 6 octets" ou "caractère 0, 6 fois".
  • Au lieu d'un nombre, vous pouvez utiliser "*" pour signifier "consommer tout le reste".

    Avertissement : lors du pack multiple de données, "*" signifie seulement "consommer toutes les données actuelles". C'est-à-dire

    pack("A*A*", $un, $deux)

    pack tout $un dans le premier "A*" puis tout $deux dans le second. C'est un principe général : chaque caractère de format correspond à une donnée à "pack"er.

Emballage des nombres

Ainsi soit fait pour les données textuelles. Passons aux choses sérieuses que "pack" et "unpack" font le mieux : la manipulation des formats binaires pour les nombres. Il n'y a, bien sûr, pas qu'un seul format binaire - la vie serait trop simple - mais Perl fera tout le travail minutieux pour vous.

Entiers

Emballer et déballer des nombres implique la conversion vers et depuis une représentation binaire *spécifique*. En laissant de côté les nombres à virgule flottante pour le moment, les propriétés saillantes de toute représentation de ce type sont :

  • le nombre d'octets utilisés pour stocker l'entier,
  • si le contenu est interprété comme un nombre signé ou non signé,
  • l'ordre des octets : si le premier octet est l'octet le moins significatif ou le plus significatif (ou : little-endian ou big-endian, respectivement).

Ainsi, par exemple, pour emballer 20302 dans un entier signé de 16 bits dans la représentation de votre ordinateur, vous écrivez

my $ps = pack( 's', 20302 );

Encore une fois, le résultat est une chaîne, contenant maintenant 2 octets. Si vous imprimez cette chaîne (ce qui, en général, n'est pas recommandé), vous pourriez voir "ON" ou "NO" (selon l'ordre des octets de votre système) - ou quelque chose de complètement différent si votre ordinateur n'utilise pas le codage de caractères ASCII. Le déballage de $ps avec le même modèle renvoie la valeur entière d'origine :

my( $s ) = unpack( 's', $ps );

C'est vrai pour tous les codes de modèle numériques. Mais ne vous attendez pas à des miracles : si la valeur emballée dépasse la capacité d'octets allouée, les bits de poids fort sont silencieusement supprimés, et unpack ne pourra certainement pas les récupérer d'un chapeau magique. Et, lorsque vous emballez en utilisant un code de modèle signé comme "s", une valeur excessive peut entraîner le réglage du bit de signe, et son déballage renverra intelligemment une valeur négative.

16 bits ne vous mèneront pas très loin avec les entiers, mais il y a "l" et "L" pour les entiers signés et non signés de 32 bits. Et si cela ne suffit pas et que votre système prend en charge les entiers de 64 bits, vous pouvez rapprocher les limites de l'infini avec les codes d'emballage "q" et "Q". Une exception notable est fournie par les codes d'emballage "i" et "I" pour les entiers signés et non signés de "variété personnalisée locale" : un tel entier prendra autant d'octets qu'un compilateur C local renvoie pour sizeof(int), mais il utilisera *au moins* 32 bits.

Chacun des codes d'emballage d'entiers "sSlLqQ" produit un nombre fixe d'octets, peu importe où vous exécutez votre programme. Cela peut être utile pour certaines applications, mais cela ne fournit pas un moyen portable de transmettre des structures de données entre Perl et des programmes C (ce qui peut arriver lorsque vous appelez des extensions XS ou la fonction Perl "syscall"), ou lorsque vous lisez ou écrivez des fichiers binaires. Ce dont vous aurez besoin dans ce cas, ce sont des codes de modèle qui dépendent de ce que votre compilateur C local compile lorsque vous codez "short" ou "unsigned long", par exemple. Ces codes et leurs longueurs d'octets correspondantes sont présentés dans le tableau ci-dessous. Comme la norme C laisse beaucoup de latitude quant aux tailles relatives de ces types de données, les valeurs réelles peuvent varier, et c'est pourquoi les valeurs sont données comme des expressions en C et en Perl. (Si vous souhaitez utiliser les valeurs de %Config dans votre programme, vous devez l'importer avec "use Config".)

signé non signé  longueur en octets en C   longueur en octets en Perl
  s!     S!      sizeof(short)      $Config{shortsize}
  i!     I!      sizeof(int)        $Config{intsize}
  l!     L!      sizeof(long)       $Config{longsize}
  q!     Q!      sizeof(long long)  $Config{longlongsize}

Les codes "i!" et "I!" ne sont pas différents de "i" et "I" ; ils sont tolérés pour des raisons de complétude.

Déballage d'une pile d'appels

Demander un ordre d'octets particulier peut être nécessaire lorsque vous travaillez avec des données binaires provenant d'une architecture spécifique, alors que votre programme pourrait s'exécuter sur un système totalement différent. Par exemple, supposez que vous avez 24 octets contenant une pile d'appels telle qu'elle se présente sur un CPU Intel 8086 :

     +---------+        +----+----+               +---------+
TOS: |   IP    |  TOS+4:| FL | FH | FLAGS  TOS+14:|   SI    |
     +---------+        +----+----+               +---------+
     |   CS    |        | AL | AH | AX            |   DI    |
     +---------+        +----+----+               +---------+
                        | BL | BH | BX            |   BP    |
                        +----+----+               +---------+
                        | CL | CH | CX            |   DS    |
                        +----+----+               +---------+
                        | DL | DH | DX            |   ES    |
                        +----+----+               +---------+

Premièrement, nous notons que ce CPU 16 bits vieillissant utilise l'ordre little-endian, et c'est pourquoi l'octet de poids faible est stocké à l'adresse la plus basse. Pour déballer un tel short (non signé), nous devrons utiliser le code "v". Un compte de répétition déballe les 12 shorts :

my( $ip, $cs, $flags, $ax, $bx, $cx, $dx, $si, $di, $bp, $ds, $es ) =
  unpack( 'v12', $frame );

Alternativement, nous aurions pu utiliser "C" pour déballer les registres d'octets individuellement accessibles FL, FH, AL, AH, etc. :

my( $fl, $f
h, $al, $ah, $bl, $bh, $cl, $ch, $dl, $dh ) = unpack( 'C10', substr( $frame, 4, 10 ) );

Il serait agréable de pouvoir faire cela en un seul coup : décompresser un short, reculer un peu, puis décompresser 2 octets. Puisque Perl *est* agréable, il propose le code de modèle "X" pour reculer d'un octet. En combinant tout cela, nous pouvons maintenant écrire :

my( $ip, $cs,
    $flags,$fl,$fh,
    $ax,$al,$ah, $bx,$bl,$bh, $cx,$cl,$ch, $dx,$dl,$dh,
    $si, $di, $bp, $ds, $es ) =
unpack( 'v2' . ('vXXCC' x 5) . 'v5', $frame );

(La construction maladroite du modèle peut être évitée - continuez à lire !)

Nous avons pris soin de construire le modèle pour qu'il corresponde au contenu de notre tampon d'images. Sinon, nous obtiendrions des valeurs indéfinies, ou "unpack" ne pourrait pas tout décompresser. Si "pack" manque d'éléments, il fournira des chaînes nulles (qui sont converties en zéros chaque fois que le code de paquet l'indique).

Comment manger un œuf sur un réseau

Le code de paquet pour l'endianisme de gros (octet de poids fort à l'adresse la plus basse) est "n" pour les entiers de 16 bits et "N" pour les entiers de 32 bits. Vous utilisez ces codes si vous savez que vos données proviennent d'une architecture conforme, mais, étonnamment, vous devriez également utiliser ces codes de paquet si vous échangez des données binaires, sur le réseau, avec un système que vous connaissez très peu. La raison simple est que cet ordre a été choisi comme *ordre réseau*, et tous les programmes respectant les normes devraient suivre cette convention. (Ceci est, bien sûr, un soutien ferme à l'une des parties Lilliputiennes et pourrait bien influencer le développement politique là-bas.) Ainsi, si le protocole vous demande d'envoyer un message en envoyant d'abord la longueur, suivie d'autant d'octets, vous pourriez écrire :

my $buf = pack( 'N', length( $msg ) ) . $msg;

ou même :

my $buf = pack( 'NA*', length( $msg ), $msg );

et passer $buf à votre routine d'envoi. Certains protocoles exigent que le nombre inclue la longueur du nombre lui-même : ajoutez alors simplement 4 à la longueur des données. (Mais assurez-vous de lire "Tailles et Largeurs" avant de vraiment coder cela !)

Modificateurs d'ordre des octets

Dans les sections précédentes, nous avons appris à utiliser "n", "N", "v" et "V" pour empaqueter et décompresser des entiers avec un ordre d'octets gros ou petit-boutiste. Bien que ce soit bien, c'est encore assez limité car cela exclut toutes sortes d'entiers signés ainsi que les entiers de 64 bits. Par exemple, si vous vouliez décompresser une séquence d'entiers signés de 16 bits en gros boutiste de manière indépendante de la plateforme, vous devriez écrire :

my @data = unpack 's*', pack 'S*', unpack 'n*', $buf;

C'est moche. Depuis Perl 5.9.2, il existe un moyen beaucoup plus agréable d'exprimer votre désir d'un certain ordre d'octets : les modificateurs ">" et "<". ">" est le modificateur gros boutiste, tandis que "<" est le modificateur petit boutiste. En les utilisant, nous pourrions réécrire le code ci-dessus comme suit :

my @data = unpack 's>*', $buf;

Comme vous pouvez le voir, le "gros bout" de la flèche touche le "s", ce qui est un bon moyen de se souvenir que ">" est le modificateur gros boutiste. La même chose fonctionne évidemment pour "<", où le "petit bout" touche le code.

Vous trouverez probablement ces modificateurs encore plus utiles si vous devez traiter des structures C gros boutistes ou petit boutistes. Assurez-vous de lire "Empaquetage et décompression de structures C" pour en savoir plus à ce sujet.

Nombres à virgule flottante

Pour empaqueter des nombres à virgule flottante, vous avez le choix entre les codes de paquet "f", "d", "F" et "D". "f" et "d" empaquètent dans (ou décompressent à partir de) la représentation de précision simple ou double telle qu'elle est fournie par votre système. Si votre système le prend en charge, "D" peut être utilisé pour empaqueter et décompresser des valeurs ("long double"), qui peuvent offrir encore plus de résolution que "f" ou "d". **Notez qu'il existe différents formats de long double.**

"F" empaquette un "NV", qui est le type à virgule flottante utilisé par Perl en interne.

Il n'existe pas de représentation réseau pour les réels, donc si vous souhaitez envoyer vos nombres réels à travers les frontières informatiques, vous feriez mieux de vous en tenir à la représentation textuelle, en utilisant éventuellement le format hexadécimal flottant (en évitant la perte de conversion décimale), sauf si vous êtes absolument sûr de ce qui se trouve à l'autre bout de la ligne. Pour les plus aventureux, vous pouvez également utiliser les modificateurs d'ordre des octets de la section précédente sur les codes à virgule flottante.

Modèles exotiques

Chaînes de bits

Les bits sont les atomes dans le monde de la mémoire. L'accès aux bits individuels peut être nécessaire soit en dernier recours, soit parce que c'est le moyen le plus pratique de gérer vos données. L'empaquetage et la décompression de chaînes de bits convertissent des chaînes contenant une série de caractères 0 et 1 en une séquence d'octets, chacun contenant un groupe de 8 bits. C'est presque aussi simple que cela en a l'air, sauf qu'il existe deux façons d'écrire le contenu d'un octet sous forme de chaîne de bits. Regardons un octet annoté :

  7 6 5 4 3 2 1 0
+-----------------+
| 1 0 0 0 1 1 0 0 |
+-----------------+
 MSB           LSB

C'est encore manger des œufs : certains pensent que sous forme de chaîne de bits, cela devrait s'écrire "10001100", c'est-à-dire en commençant par le bit le plus significatif, d'autres insistent pour "00110001". Eh bien, Perl n'est pas biaisé, c'est pourquoi nous avons deux codes de chaîne de bits :

$byte = pack( 'B8', '10001100' ); # commence par MSB
$byte = pack( 'b8', '00110001' ); # commence par LSB

Il n'est pas possible d'empaqueter ou de décompresser des champs de bits - juste des octets entiers. "pack" commence toujours à la prochaine frontière d'octet et "arrondit" au multiple de 8 suivant en ajoutant des bits zéro si nécessaire. (Si vous voulez des champs de bits, il y a "vec" dans perlfunc. Ou vous pourriez implémenter la gestion des champs de bits au niveau des chaînes de caractères, en utilisant split, substr et la concaténation sur des chaînes de bits décompressées.)

Pour illustrer la décompression de chaînes de bits, nous allons décomposer un simple registre d'état (un "-" représente un bit "réservé") :

+-----------------+-----------------+
| S Z - A - P - C | - - - - O D I T |
+-----------------+-----------------+
 MSB           LSB MSB           LSB

La conversion de ces deux octets en une chaîne peut être effectuée avec le modèle de décompression 'b16'. Pour obtenir les valeurs de bits individuelles à partir de la chaîne de bits, nous utilisons "split" avec le séparateur "vide" qui décompose en caractères individuels. Les valeurs de bits des positions "réservées" sont simplement affectées à "undef", une notation pratique pour "peu importe où cela va".

($carry, undef, $parity, undef, $auxcarry, undef, $zero, $sign,
 $trace, $interrupt, $direction, $overflow) =
   split( //, unpack( 'b16', $status ) );

Nous aurions tout aussi bien pu utiliser un modèle de décompression 'b12', car les 4 derniers bits peuvent être ignorés de toute façon.

Encodage Uu

Un autre élément hors norme dans l'alphabet des modèles est "u", qui empaquette une "chaîne encodée uu". ("uu" est l'abréviation de Unix-to-Unix.) Il y a de fortes chances que vous n'ayez jamais besoin de cette technique d'encodage qui a été inventée pour surmonter les lacunes des anciens supports de transmission qui ne supportent que des données ASCII simples. La recette essentielle est simple : prenez trois octets, soit 24 bits. Divisez-les en 4 groupes de six, en ajoutant un espace (0x20) à chacun. Répétez jusqu'à ce que toutes les données soient mélangées. Pliez les groupes de 4 octets en lignes ne dépassant pas 60 et garnissez-les devant du nombre d'octets d'origine (augmenté de 0x20) et d'un "\n" à la fin. - Le chef "pack" préparera cela pour vous, à la minute, lorsque vous sélectionnerez le code de paquet "u" au menu :

my $uubuf = pack( 'u', $bindat );

Un compteur de répétition après "u" définit le nombre d'octets à mettre dans une ligne encodée uu, qui est au maximum de 45 par défaut, mais pourrait être défini sur un multiple (plus petit) de trois. "unpack" ignore simplement le compteur de répétition.

Faire des sommes

Un code de modèle encore plus étrange est "%"<nombre>. Premièrement, parce qu'il est utilisé comme préfixe d'un autre code de modèle. Deuxièmement, parce qu'il ne peut pas du tout être utilisé dans "pack", et troisièmement, dans "unpack", ne renvoie pas les données telles que définies par le code de modèle qu'il précède. Au lieu de cela, il vous donnera un entier de nombre bits calculé à partir de la valeur des données en faisant des sommes. Pour les codes de décompression numériques, peu d'exploit est réalisé :

my $buf = pack( 'iii', 100, 20, 3 );
print unpack( '%32i3', $buf ), "\n";  # affiche 123

Pour les valeurs de chaîne, "%" renvoie la somme des valeurs d'octets, vous épargnant la peine d'une boucle de somme avec "substr" et "ord" :

print unpack( '%32A*', "\x01\x10" ), "\n";  # affiche 17

Bien que le code "%" soit documenté comme renvoyant une "somme de contrôle" : ne vous fiez pas à de telles valeurs ! Même lorsqu'elles sont appliquées à un petit nombre d'octets, elles ne garantiront pas une distance de Hamming notable.

En relation avec "b"

ou "B", "%" ajoutent simplement des bits, et cela peut être bien utilisé pour compter efficacement les bits définis :

my $bitcount = unpack( '%32b*', $mask );

Et un bit de parité pair peut être déterminé comme suit :

my $evenparity = unpack( '%1b*', $mask );

Unicode

Unicode est un jeu de caractères qui peut représenter la plupart des caractères dans la plupart des langues du monde, offrant de la place pour plus d'un million de caractères différents. Unicode 3.1 spécifie 94 140 caractères : Les caractères de base latins sont assignés aux nombres 0 - 127. Le complément latin-1 avec les caractères utilisés dans plusieurs langues européennes se trouve dans la plage suivante, jusqu'à 255. Après quelques extensions latines supplémentaires, nous trouvons les jeux de caractères des langues utilisant des alphabets non romains, entremêlés d'une variété de jeux de symboles tels que les symboles de devise, Zapf Dingbats ou Braille. (Vous pourriez vouloir visiter https://www.unicode.org/ pour voir certains d'entre eux - mes préférés personnels sont le Telugu et le Kannada.)

Les jeux de caractères Unicode associent des caractères à des entiers. L'encodage de ces nombres dans un nombre égal d'octets doublerait plus que les exigences de stockage de textes écrits en alphabets latins. L'encodage UTF-8 évite cela en stockant les caractères les plus courants (d'un point de vue occidental) en un seul octet tout en encodant les plus rares en trois octets ou plus.

Perl utilise UTF-8, en interne, pour la plupart des chaînes Unicode.

Alors, qu'est-ce que cela a à voir avec "pack" ? Eh bien, si vous voulez composer une chaîne Unicode (qui est encodée en interne en UTF-8), vous pouvez le faire en utilisant le code de modèle "U". Par exemple, produisons le symbole de la monnaie Euro (numéro de code 0x20AC) :

$UTF8{Euro} = pack( 'U', 0x20AC );
# Équivalent à : $UTF8{Euro} = "\x{20ac}";

L'inspection de $UTF8{Euro} montre qu'il contient 3 octets : "\xe2\x82\xac". Cependant, il ne contient qu'1 caractère, le numéro 0x20AC. L'aller-retour peut être effectué avec "unpack" :

$Unicode{Euro} = unpack( 'U', $UTF8{Euro} );

Le déballage à l'aide du code de modèle "U" fonctionne également sur les chaînes d'octets encodées en UTF-8.

Généralement, vous voudrez empaqueter ou déballer des chaînes UTF-8 :

# empaqueter et déballer l'alphabet hébreu
my $alefbet = pack( 'U*', 0x05d0..0x05ea );
my @hebrew = unpack( 'U*', $utf );

Veuillez noter : dans le cas général, il est préférable d'utiliser "Encode::decode('UTF-8', $utf)" pour décoder une chaîne d'octets encodée en UTF-8 en une chaîne Unicode Perl, et "Encode::encode('UTF-8', $str)" pour encoder une chaîne Unicode Perl en octets UTF-8. Ces fonctions permettent de gérer les séquences d'octets invalides et ont généralement une interface plus conviviale.

Un Autre Encodage Binaire Portable

Le code d'empaquetage "w" a été ajouté pour supporter un schéma d'encodage de données binaires portable qui va bien au-delà des simples entiers. (Les détails peuvent être trouvés à https://github.com/mworks-project/mw_scarab/blob/master/Scarab-0.1.00d19/doc/binary-serialization.txt, le projet Scarab.) Un entier non signé compressé BER (Binary Encoded Representation) stocke des chiffres en base 128, chiffre le plus significatif en premier, avec le moins de chiffres possible. Le bit huit (le bit de poids fort) est défini sur chaque octet sauf le dernier. Il n'y a pas de limite de taille à l'encodage BER, mais Perl n'ira pas à l'extrême.

my $berbuf = pack( 'w*', 1, 128, 128+1, 128*128+127 );

Une vidange hexadécimale de $berbuf, avec des espaces insérés aux bons endroits, montre 01 8100 8101 81807F. Comme le dernier octet est toujours inférieur à 128, "unpack" sait où s'arrêter.

Groupement de Modèles

Avant Perl 5.8, les répétitions de modèles devaient être faites par multiplication par "x" des chaînes de modèles. Il existe maintenant une meilleure façon car nous pouvons utiliser les codes d'empaquetage "(" et ")" combinés avec un compteur de répétition. Le modèle "unpack" de l'exemple de pile d'appels peut simplement être écrit comme suit :

unpack( 'v2 (vXXCC)5 v5', $frame )

Explorons un peu plus cette fonctionnalité. Nous commencerons par l'équivalent de

join( '', map( substr( $_, 0, 1 ), @str ) )

qui renvoie une chaîne composée du premier caractère de chaque chaîne. En utilisant pack, nous pouvons écrire

pack( '(A)'.@str, @str )

ou, parce qu'un compteur de répétition "*" signifie "répéter autant de fois que nécessaire", simplement

pack( '(A)*', @str )

(Notez que le modèle "A*" n'aurait empaqueté $str[0] qu'en pleine longueur.)

Pour empaqueter des dates stockées sous forme de triplets (jour, mois, année) dans un tableau @dates en une séquence d'octet, octet, entier court, nous pouvons écrire

$pd = pack( '(CCS)*', map( @$_, @dates ) );

Pour échanger des paires de caractères dans une chaîne (de longueur paire), on pourrait utiliser plusieurs techniques. Premièrement, utilisons "x" et "X" pour avancer et reculer :

$s = pack( '(A)*', unpack( '(xAXXAx)*', $s ) );

Nous pouvons également utiliser "@" pour sauter à un décalage, 0 étant la position où nous étions lorsque le dernier "(" a été rencontré :

$s = pack( '(A)*', unpack( '(@1A @0A @2)*', $s ) );

Enfin, il existe également une approche entièrement différente en déballant des shorts big-endian et en les empaquetant dans l'ordre des octets inversé :

$s = pack( '(v)*', unpack( '(n)*', $s );

Longueurs et Largeurs

Longueurs de Chaînes

Dans la section précédente, nous avons vu un message réseau construit en préfixant la longueur binaire du message au message réel. Vous constaterez que l'empaquetage d'une longueur suivie de tant d'octets de données est une recette fréquemment utilisée, car l'ajout d'un octet nul ne fonctionne pas si un octet nul peut faire partie des données. Voici un exemple où les deux techniques sont utilisées : après deux chaînes terminées par un octet nul avec l'adresse source et destination, un Short Message (vers un téléphone mobile) est envoyé après un octet de longueur :

my $msg = pack( 'Z*Z*CA*', $src, $dst, length( $sm ), $sm );

Le déballage de ce message peut être effectué avec le même modèle :

( $src, $dst, $len, $sm ) = unpack( 'Z*Z*CA*', $msg );

Il y a un piège subtil qui se profile : ajouter un autre champ après le Short Message (dans la variable $sm) est tout à fait normal lors de l'empaquetage, mais cela ne peut pas être déballé naïvement :

# empaqueter un message
my $msg = pack( 'Z*Z*CA*C', $src, $dst, length( $sm ), $sm, $prio );
# le déballage échoue - $prio reste indéfini !
( $src, $dst, $len, $sm, $prio ) = unpack( 'Z*Z*CA*C', $msg );

Le code d'empaquetage "A*" consomme tous les octets restants, et $prio reste indéfini ! Avant que nous ne laissions la déception assombrir le moral : Perl a l'atout pour réussir ce tour aussi, juste un peu plus loin dans la manche. Regardez ceci :

# empaqueter un message : ASCIIZ, ASCIIZ, longueur/chaîne, octet
my $msg = pack( 'Z* Z* C/A* C', $src, $dst, $sm, $prio );
# déballer
( $src, $dst, $sm, $prio ) = unpack( 'Z* Z* C/A* C', $msg );

La combinaison de deux codes d'empaquetage avec une barre oblique ("/") les associe à une seule valeur de la liste d'arguments. Dans "pack", la longueur de l'argument est prise et empaquetée selon le premier code tandis que l'argument lui-même est ajouté après avoir été converti avec le code de modèle après la barre oblique. Cela nous évite le problème d'insérer l'appel "length", mais c'est dans "unpack" que nous marquons vraiment des points : la valeur de l'octet de longueur marque la fin de la chaîne à prendre dans le tampon. Puisque cette combinaison n'a de sens que lorsque le second code d'empaquetage n'est pas "a*", "A*" ou "Z*", Perl ne vous le permettra pas.

Le code d'empaquetage précédant "/" peut être n'importe quoi qui convient pour représenter un nombre : tous les codes numériques d'empaquetage binaire, et même les codes textuels tels que "A4" ou "Z*" :

# empaqueter/déballer une chaîne précédée de sa longueur en ASCII
my $buf = pack( 'A4/A*', "Humpty-Dumpty" );
# déballer $buf : '13  Humpty-Dumpty'
my $txt = unpack( 'A4/A*', $buf );

"/" n'est pas implémenté dans les Perls avant 5.6, donc si votre code doit fonctionner sur des Perls anciens, vous devrez "unpack( 'Z* Z* C')" pour obtenir la longueur, puis l'utiliser pour créer une nouvelle chaîne de déballage. Par exemple

# empaqueter un message : ASCIIZ, ASCIIZ, longueur, chaîne, octet
# (compatible 5.005)
my $msg = pack( 'Z* Z* C A* C', $src, $dst, length $sm, $sm, $prio );
# déballer
( undef, undef, $len) = unpack( 'Z* Z* C', $msg );
($src, $dst, $sm, $prio) = unpack ( "Z* Z* x A$len C", $msg );

Mais ce second "unpack" va trop vite. Il n'utilise pas une simple chaîne littérale pour le modèle. Alors peut-être devrions-nous introduire...

Modèles Dynamiques

Jusqu'à présent, nous avons vu des littéraux utilisés comme modèles. Si la liste des éléments d'empaquetage n'a pas de longueur fixe, une expression construisant le modèle est requise (chaque fois que, pour une raison quelconque, "()*" ne peut pas être utilisée). Voici un exemple : Pour stocker des valeurs de chaînes nommées d'une manière qui puisse être facilement analysée par un programme C, nous créons une séquence de noms et de chaînes ASCII terminées par un octet nul, avec "=" entre le nom et la valeur, suivi d'un octet nul délimiteur supplémentaire. Voici comment :

my $env = pack( '(A*A*Z*)' . keys( %Env ) . 'C',
                map( { ( $_, '=', $Env{$_} ) } keys( %Env ) ), 0 );

Examinons les rouages de ce moulin à octets, un par un. Il y a l'appel "map", créant les éléments que nous avons l'intention de mettre dans le tampon $env : pour chaque

ch clé (dans $_) il ajoute le sépareur "=" et la valeur de l'entrée de hachage. Chaque triplet est empaqueté avec la séquence de code de modèle "A*A*Z*" qui est répétée selon le nombre de clés. (Oui, c'est ce que la fonction "keys" retourne dans le contexte scalaire.) Pour obtenir le tout dernier octet nul, nous ajoutons un 0 à la fin de la liste "pack", pour être empaqueté avec "C". (Les lecteurs attentifs auront peut-être remarqué que nous aurions pu omettre le 0.)

Pour l'opération inverse, nous devrons déterminer le nombre d'éléments dans le tampon avant de pouvoir laisser "unpack" le décomposer :

my $n = $env =~ tr/\0// - 1;
my %env = map( split( /=/, $_ ), unpack( "(Z*)$n", $env ) );

Le "tr" compte les octets nuls. L'appel "unpack" retourne une liste de paires nom-valeur dont chacune est décomposée dans le bloc "map".

Comptage des Répétitions

Au lieu de stocker un sentinelle à la fin d'un élément de données (ou une liste d'éléments), nous pourrions précéder les données d'un compte. Encore une fois, nous empaquetons les clés et les valeurs d'un hachage, en précédant chacune d'un compteur de longueur court non signé, et en tête, nous stockons le nombre de paires :

my $env = pack( 'S(S/A* S/A*)*', scalar keys( %Env ), %Env );

Cela simplifie l'opération inverse car le nombre de répétitions peut être désempaqueté avec le code "/" :

my %env = unpack( 'S/(S/A* S/A*)', $env );

Notez que c'est l'un des rares cas où vous ne pouvez pas utiliser le même modèle pour "pack" et "unpack" car "pack" ne peut pas déterminer un nombre de répétitions pour un groupe "()".

Intel HEX

Intel HEX est un format de fichier pour représenter des données binaires, principalement pour la programmation de diverses puces, sous forme de fichier texte. (Voir https://en.wikipedia.org/wiki/.hex pour une description détaillée, et <https://en.wikipedia.org/wiki/SREC_(file_format)> pour le format S-record de Motorola, qui peut être analysé en utilisant la même technique.) Chaque ligne commence par un deux-points (':') et est suivie d'une séquence de caractères hexadécimaux, spécifiant un nombre d'octets n (8 bits), une adresse (16 bits, big endian), un type d'enregistrement (8 bits), n octets de données et une somme de contrôle (8 bits) calculée comme l'octet le moins significatif de la somme en complément à deux des octets précédents. Exemple : ":0300300002337A1E".

La première étape du traitement d'une telle ligne est la conversion, en binaire, des données hexadécimales, pour obtenir les quatre champs, tout en vérifiant la somme de contrôle. Pas de surprise ici : nous commencerons par un simple appel "pack" pour tout convertir en binaire :

my $binrec = pack( 'H*', substr( $hexrec, 1 ) );

La séquence d'octets résultante est très pratique pour vérifier la somme de contrôle. Ne ralentissez pas votre programme avec une boucle for ajoutant les valeurs "ord" des octets de cette chaîne - le code "unpack" "%" est ce qu'il faut utiliser pour calculer la somme de 8 bits de tous les octets, qui doit être égale à zéro :

die unless unpack( "%8C*", $binrec ) == 0;

Enfin, obtenons ces quatre champs. À ce stade, vous ne devriez plus avoir de problèmes avec les trois premiers champs - mais comment utiliser le nombre d'octets des données dans le premier champ comme longueur pour le champ de données ? Ici, les codes "x" et "X" viennent à la rescousse, car ils permettent de revenir en arrière et d'avancer dans la chaîne pour désempaqueter.

my( $addr, $type, $data ) = unpack( "x n C X4 C x3 /a", $bin );

Le code "x" saute un octet, car nous n'avons pas encore besoin du compte. Le code "n" prend en charge l'adresse entière big-endian de 16 bits, et "C" désempaquette le type d'enregistrement. En étant à l'offset 4, où commencent les données, nous avons besoin du compte. "X4" nous ramène à la case départ, qui est l'octet à l'offset 0. Maintenant, nous récupérons le compte et avançons rapidement à l'offset 4, où nous sommes maintenant entièrement équipés pour extraire le nombre exact d'octets de données, en laissant de côté l'octet de somme de contrôle final.

Empaquetage et Dsempaquetage de Structures C

Dans les sections précédentes, nous avons vu comment empaqueter des nombres et des chaînes de caractères. S'il n'y avait pas quelques accrocs, nous pourrions conclure cette section immédiatement avec la remarque concise que les structures C ne contiennent rien d'autre, et donc vous savez déjà tout ce qu'il y a à savoir. Désolé, non : lisez la suite, s'il vous plaît.

Si vous devez traiter beaucoup de structures C, et que vous ne voulez pas hacker manuellement toutes vos chaînes de modèles, vous voudrez probablement jeter un œil au module CPAN "Convert::Binary::C". Non seulement il peut analyser votre source C directement, mais il a également un support intégré pour tous les petits extras décrits plus loin dans cette section.

Le Piège de l'Alignement

Dans la considération de la vitesse par rapport aux exigences de mémoire, l'équilibre a été penché en faveur d'une exécution plus rapide. Cela a influencé la façon dont les compilateurs C allouent la mémoire pour les structures : Sur les architectures où un opérande de 16 ou 32 bits peut être déplacé plus rapidement entre des endroits en mémoire, ou vers ou depuis un registre CPU, s'il est aligné à une adresse paire, multiple de quatre, ou même multiple de huit, un compilateur C vous donnera cet avantage de vitesse en insérant des octets supplémentaires dans les structures. Si vous ne franchissez pas la frontière C, cela ne vous causera probablement pas de problèmes (bien que vous devriez y faire attention lorsque vous concevez de grandes structures de données, ou que vous voulez que votre code soit portable entre les architectures (vous le voulez, n'est-ce pas ?)).

Pour voir comment cela affecte "pack" et "unpack", nous comparerons ces deux structures C :

typedef struct {
  char     c1;
  short    s;
  char     c2;
  long     l;
} gappy_t;
typedef struct {
  long     l;
  short    s;
  char     c1;
  char     c2;
} dense_t;

Typiquement, un compilateur C alloue 12 octets à une variable "gappy_t", mais ne nécessite que 8 octets pour une "dense_t". Après avoir étudié cela plus en détail, nous pouvons dessiner des cartes mémoire, montrant où sont cachés les 4 octets supplémentaires :

0           +4          +8          +12
+--+--+--+--+--+--+--+--+--+--+--+--+
|c1|xx|  s  |c2|xx|xx|xx|     l     |    xx = octet de remplissage
+--+--+--+--+--+--+--+--+--+--+--+--+
gappy_t
0           +4          +8
+--+--+--+--+--+--+--+--+
|     l     |  h  |c1|c2|
+--+--+--+--+--+--+--+--+
dense_t

Et c'est là que le premier hic frappe : les modèles "pack" et "unpack" doivent être remplis de codes "x" pour obtenir ces octets de remplissage supplémentaires.

La question naturelle : "Pourquoi Perl ne peut-il pas compenser les écarts ?" mérite une réponse. Une bonne raison est que les compilateurs C peuvent fournir des extensions (non-ANSI) permettant toutes sortes de contrôles sophistiqués sur la façon dont les structures sont alignées, même au niveau d'un champ de structure individuel. Et, si cela ne suffisait pas, il y a une chose insidieuse appelée "union" où la quantité d'octets de remplissage ne peut pas être dérivée uniquement de l'alignement de l'élément suivant.

OK, alors mordons la balle. Voici une façon d'obtenir l'alignement correct en insérant les codes de modèle "x", qui ne prennent pas d'élément correspondant dans la liste :

my $gappy = pack( 'cxs cxxx l!', $c1, $s, $c2, $l );

Notez le "!" après "l" : Nous voulons nous assurer que nous empaquetons un entier long tel qu'il est compilé par notre compilateur C. Et même maintenant, cela ne fonctionnera que pour les plateformes où le compilateur aligne les choses comme ci-dessus. Et quelqu'un quelque part a une plateforme où ce n'est pas le cas. [Probablement un Cray, où "short", "int" et "long" sont tous de 8 octets. :-)]

Compter les octets et surveiller les alignements dans de longues structures est forcément fastidieux. N'y a-t-il pas un moyen de créer le modèle avec un simple programme ? Voici un programme C qui fait l'affaire :

#include <stdio.h>
#include <stddef.h>
typedef struct {
  char     fc1;
  short    fs;
  char     fc2;
  long     fl;
} gappy_t;
#define Pt(struct,field,tchar) \
  printf( "@%d%s ", offsetof(struct,field), # tchar );
int main() {
  Pt( gappy_t, fc1, c  );
  Pt( gappy_t, fs,  s! );
  Pt( gappy_t, fc2, c  );
  Pt( gappy_t, fl,  l! );
  printf( "\n" );
}

La ligne de sortie peut être utilisée comme modèle dans un appel "pack" ou "unpack" :

my $gappy = pack( '@0c @2s! @4c @8l!', $c1, $s, $c2, $l );

Génial, encore un code de modèle - comme si nous n'en avions pas assez. Mais "@" nous sauve en nous permettant de spécifier le décalage par rapport au début du tampon d'empaquetage jusqu'au prochain élément : c'est juste la valeur que la macro "offsetof" (définie dans "<stddef.h>") retourne lorsqu'on lui donne un type "struct" et l'un de ses noms de champ ("désignateur de membre" dans le langage standard C).

Ni l'utilisation de décalages ni l'ajout de "x" pour combler les écarts ne sont satisfaisants. (Imaginez juste ce qui se passe si la structure change.) Ce dont nous avons vraiment besoin, c'est un moyen de dire "saute autant d'octets que nécessaire jusqu'au prochain multiple de N". Dans les modèles fluides, vous dites cela avec "x!N" où N est remplacé par la valeur appropriée. Voici la prochaine version de notre empaquetage de struct :

my $gappy = pack( 'c x!2 s c x!4 l!', $c1, $s, $c2, $l );

C'est certainement mieux, mais nous devons toujours savoir quelle est la longueur de tous les entiers, et la portabilité est loin. Plutôt que 2, par exemple, nous voulons dire "quelle que soit la longueur d'un short". Mais cela peut être fait en entourant le code d'empaquetage approprié entre crochets : "[s]". Donc,

pack

Permet de remplir un tampon avec des données sous une forme spécifiée par un modèle.

pack(TEMPLATE, EXPR, ...)

Retourne une chaîne de caractères contenant les valeurs de EXPR, ..., empaquetées selon le TEMPLATE donné. Le TEMPLATE est une chaîne de caractères qui décrit le format des données à générer.

Les codes de modèle courants incluent :

A
Chaîne de caractères ASCII remplie d'espaces. Si la chaîne est plus longue que le champ, elle est tronquée. Si elle est plus courte, elle est complétée par des espaces.
a
Chaîne de caractères ASCII sans remplissage. Si la chaîne est plus longue que le champ, elle est tronquée. Si elle est plus courte, elle est complétée par des octets nuls.
b
Chaîne de bits (octets représentés par '0' et '1'). Le bit de poids fort est traité en premier.
B
Chaîne de bits (octets représentés par '0' et '1'). Le bit de poids faible est traité en premier.
c
Caractère signé (valeur de 8 bits).
C
Caractère non signé (valeur de 8 bits).
d
Nombre à virgule flottante double précision (selon la convention du système).
f
Nombre à virgule flottante simple précision (selon la convention du système).
h
Chiffre hexadécimal (quatre bits). Le chiffre de poids fort est traité en premier.
H
Chiffre hexadécimal (quatre bits). Le chiffre de poids faible est traité en premier.
i
Entier signé (taille native).
I
Entier non signé (taille native).
l
Entier long signé (taille native, généralement 32 bits).
L
Entier long non signé (taille native, généralement 32 bits).
n
Entier court non signé (16 bits), big-endian.

Entier long non signé (32 bits), big-endian.

Pointeur vers une chaîne de caractères terminée par un octet nul. L'adresse est packée sous forme d'entier non signé.

Pointeur vers une chaîne de caractères de longueur fixe. L'adresse est packée sous forme d'entier non signé.
q

Entier court signé (taille native, généralement 16 bits).

Définit la position courante dans le tampon de sortie.

Les caractères suivants peuvent être ajoutés à la fin d'un code de modèle pour spécifier l'ordre des octets :

!
Utilise l'ordre des octets natif du système.
<
Utilise l'ordre des octets little-endian.
>
Utilise l'ordre des octets big-endian.

Un nombre avant un code de modèle spécifie le nombre de fois que ce code doit être répété. Par défaut, la répétition est de 1. Un '*' répète le code autant de fois que possible en utilisant les arguments restants.

Le code x! est un cas particulier qui insère un nombre spécifié d'octets nuls sans avancer dans le modèle. C'est utile pour l'alignement.

Gestion de l'endianness

Maintenant, imaginez que nous voulons empaqueter les données pour une machine avec un ordre d'octets différent. Tout d'abord, nous devons déterminer la taille réelle des types de données sur la machine cible. Supposons que les longs font 32 bits et les shorts 16 bits. Vous pouvez alors réécrire le modèle comme suit :

my $gappy = pack( 'c x![s] s c x![l] l', $c1, $s, $c2, $l );

Si la machine cible est little-endian, nous pouvons écrire :

my $gappy = pack( 'c x![s] s< c x![l] l<', $c1, $s, $c2, $l );

Cela force les membres short et long à être little-endian, et convient si vous n'avez pas trop de membres dans la structure. Mais nous pouvons également utiliser le modificateur d'ordre des octets sur un groupe et écrire ce qui suit :

my $gappy = pack( '( c x![s] s c x![l] l )<', $c1, $s, $c2, $l );

Ce n'est pas aussi court qu'avant, mais cela rend plus évident que nous avons l'intention d'avoir un ordre d'octets little-endian pour un groupe entier, pas seulement pour les codes de modèle individuels. Cela peut également être plus lisible et plus facile à maintenir.

Alignement, Reprise 2

Je crains que nous n'ayons pas encore tout à fait terminé avec le piège de l'alignement. L'hydre soulève une autre tête laide lorsque vous empaquetez des tableaux de structures :

typedef struct {
  short    count;
  char     glyph;
} cell_t;
typedef cell_t buffer_t[BUFLEN];

Où est le problème ? Le remplissage n'est requis ni avant le premier champ "count", ni entre celui-ci et le champ suivant "glyph", alors pourquoi ne pouvons-nous pas simplement empaqueter comme ceci :

# quelque chose tourne mal ici :
pack( 's!a' x @buffer,
      map{ ( $_->{count}, $_->{glyph} ) } @buffer );

Cela empaquette "3*@buffer" octets, mais il s'avère que la taille de "buffer_t" est quatre fois "BUFLEN" ! La morale de l'histoire est que l'alignement requis d'une structure ou d'un tableau est propagé au niveau supérieur suivant où nous devons également tenir compte du remplissage *à la fin* de chaque composant. Ainsi, le modèle correct est :

pack( 's!ax' x @buffer,
      map{ ( $_->{count}, $_->{glyph} ) } @buffer );

Alignement, Reprise 3

Et même si vous tenez compte de tout ce qui précède, ANSI permet ceci :

typedef struct {
  char     foo[2];
} foo_t;

varie en taille. La contrainte d'alignement de la structure peut être supérieure à celle de l'un de ses éléments. [Et si vous pensez que cela n'affecte rien de courant, démembrez le prochain téléphone portable que vous verrez. Beaucoup ont des cœurs ARM, et les règles de structure ARM font que "sizeof (foo_t)" == 4]

Pointeurs pour savoir comment les utiliser

Le titre de cette section indique le deuxième problème que vous pourriez rencontrer tôt ou tard lorsque vous empaquetez des structures C. Si la fonction que vous avez l'intention d'appeler attend, disons, une valeur "void *", vous ne pouvez *pas* simplement prendre une référence à une variable Perl. (Bien que cette valeur soit certainement une adresse mémoire, ce n'est pas l'adresse où le contenu de la variable est stocké.)

Le code de modèle "P" promet d'empaqueter un « pointeur vers une chaîne de longueur fixe ». N'est-ce pas ce que nous voulons ? Essayons :

# allouer un espace mémoire et y empaqueter un pointeur
my $memory = "\x00" x $size;
my $memptr = pack( 'P', $memory );

Mais attendez : "pack" ne retourne-t-il pas simplement une séquence d'octets ? Comment pouvons-nous passer cette chaîne d'octets à du code C qui attend un pointeur qui, après tout, n'est rien d'autre qu'un nombre ? La réponse est simple : nous devons obtenir l'adresse numérique à partir des octets retournés par "pack".

my $ptr = unpack( 'L!', $memptr );

Évidemment, cela suppose qu'il est possible de caster un pointeur en unsigned long et vice versa, ce qui fonctionne souvent mais ne doit pas être considéré comme une loi universelle. - Maintenant que nous avons ce pointeur, la prochaine question est : comment l'utiliser à bon escient ? Nous avons besoin d'un appel à une fonction C où un pointeur est attendu. L'appel système read(2) vient à l'esprit :

ssize_t read(int fd, void *buf, size_t count);

Après avoir lu perlfunc expliquant comment utiliser "syscall", nous pouvons écrire cette fonction Perl copiant un fichier vers la sortie standard :

require 'syscall.ph'; # exécuter h2ph pour générer ce fichier
sub cat($){
    my $path = shift();
    my $size = -s $path;
    my $memory = "\x00" x $size;  # allouer de la mémoire
    my $ptr = unpack( 'L', pack( 'P', $memory ) );
    open( F, $path ) || die( "$path: impossible d'ouvrir ($!)\n" );
    my $fd = fileno(F);
    my $res = syscall( &SYS_read, fileno(F), $ptr, $size );
    print $memory;
    close( F );
}

Ce n'est ni un spécimen de simplicité ni un modèle de portabilité, mais cela illustre le propos : nous sommes capables de nous faufiler en coulisses et d'accéder à la mémoire de Perl autrement bien gardée ! (Note importante : "syscall" de Perl ne vous oblige pas à construire des pointeurs de cette manière détournée. Vous passez simplement une variable de chaîne, et Perl transmet l'adresse.)

Comment fonctionne "unpack" avec "P" ? Imaginez un pointeur dans le tampon sur le point d'être décompressé : s'il n'est pas le pointeur nul (qui produira intelligemment la valeur "undef"), nous avons une adresse de départ - mais ensuite quoi ? Perl n'a aucun moyen de savoir quelle est la longueur de cette « chaîne de longueur fixe », c'est donc à vous de spécifier la taille réelle comme longueur explicite après "P".

my $mem = "abcdefghijklmn";
print unpack( 'P5', pack( 'P', $mem ) ); # imprime "abcde"

Par conséquent, "pack" ignore tout nombre ou "*" après "P".

Maintenant que nous avons vu "P" à l'œuvre, nous pourrions aussi bien essayer "p". Pourquoi avons-nous besoin d'un deuxième code de modèle pour empaqueter les pointeurs ? La réponse réside dans le simple fait qu'un "unpack" avec "p" promet une chaîne terminée par un octet nul commençant à l'adresse prise dans le tampon, et cela implique une longueur pour l'élément de données à retourner :

my $buf = pack( 'p', "abc\x00efhijklmn" );
print unpack( 'p', $buf );    # imprime "abc"

Bien que cela puisse prêter à confusion : par conséquent, la longueur étant implicite par la longueur de la chaîne, un nombre après le code d'empaquetage "p" est un compteur de répétition, pas une longueur comme après "P".

Utiliser "pack(..., $x)" avec "P" ou "p" pour obtenir l'adresse où $x est réellement stocké doit être utilisé avec circonspection. La machinerie interne de Perl considère la relation entre une variable et cette adresse comme sa propre affaire privée et ne se soucie pas vraiment que nous ayons obtenu une copie. Par conséquent :

  • N'utilisez pas "pack" avec "p" ou "P" pour obtenir l'adresse d'une variable qui est sur le point de sortir de portée (et par conséquent de libérer sa mémoire) avant que vous ayez fini d'utiliser la mémoire à cette adresse.
  • Soyez très prudent avec les opérations Perl qui modifient la valeur de la variable. Ajouter quelque chose à la variable, par exemple, peut nécessiter une réallocation de son stockage, vous laissant avec un pointeur dans le no man's land.
  • Ne pensez pas que vous pouvez obtenir l'adresse d'une variable Perl lorsqu'elle est stockée sous forme de nombre entier ou double ! "pack('P', $x)" forcera la représentation interne de la variable en chaîne, comme si vous aviez écrit quelque chose comme "$x .= ''".

Il est cependant sûr de P- ou p-empaqueter une chaîne littérale, car Perl alloue simplement une variable anonyme.

Recettes Pack

Voici une collection de recettes (éventuellement) utiles pour "pack" et "unpack" :

# Convertir une adresse IP pour les fonctions socket
pack( "C4", split /\./, "123.4.5.6" );
# Compter les bits dans un bloc de mémoire (par exemple, un vecteur de sélection)
unpack( '%32b*', $mask );
# Déterminer l'endianness de votre système
$is_little_endian = unpack( 'c', pack( 's', 1 ) );
$is_big_endian = unpack( 'xc', pack( 's', 1 ) );
# Déterminer le nombre de bits dans un entier natif
$bits = unpack( '%32I!', ~0 );
# Préparer l'argument pour l'appel système nanosleep
my $timespec = pack( 'L!L!', $secs, $nanosecs );

Pour un vidage mémoire simple, nous décompressons quelques octets en autant de paires de chiffres hexadécimaux, et utilisons "map" pour gérer l'espacement traditionnel - 16 octets par ligne :

my $i;
print map( ++$i % 16 ? "$_ " : "$_\n",
           unpack( 'H2' x length( $mem ), $mem ) ),
      length( $mem ) % 16 ? "\n" : '';
