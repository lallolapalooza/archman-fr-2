NOM

perf-script-python - Traiter les données de trace avec un script Python

SYNOPSIS

perf script [-s [Python]:script[.py] ]

DESCRIPTION

Cette option de script perf est utilisée pour traiter les données de script perf à l'aide de l'interpréteur Python intégré de perf. Elle lit et traite le fichier d'entrée et affiche les résultats de l'analyse de trace implémentée dans le script Python donné, le cas échéant.

UN EXEMPLE RAPIDE

Cette section montre le processus, du début à la fin, de création d'un script Python fonctionnel qui agrège et extrait des informations utiles d'un flux de script perf brut. Vous pouvez éviter de lire le reste de ce document si un exemple vous suffit ; le reste du document fournit plus de détails sur chaque étape et liste les fonctions de bibliothèque disponibles pour les auteurs de scripts.

Cet exemple détaille en fait les étapes qui ont été utilisées pour créer le script syscall-counts que vous voyez lorsque vous listez les scripts de script perf disponibles via perf script -l. En tant que tel, ce script montre également comment intégrer votre script dans la liste des scripts perf script généraux listés par cette commande.

Le script syscall-counts est un script simple, mais il démontre toutes les idées de base nécessaires pour créer un script utile. Voici un exemple de sa sortie (les noms de syscall ne sont pas encore pris en charge, ils apparaîtront sous forme de nombres) :

Fondamentalement, notre tâche consiste à conserver un décompte par syscall qui est mis à jour chaque fois qu'un appel système se produit dans le système. Notre script fera cela, mais nous devons d'abord enregistrer les données qui seront traitées par ce script. Théoriquement, il existe plusieurs façons de le faire :

• nous pouvons activer tous les événements dans le répertoire tracing/events/syscalls, mais cela représente plus de 600 syscalls, bien au-delà du nombre autorisé par perf. Ces événements syscall individuels seront cependant utiles si nous voulons plus tard utiliser les conseils obtenus à partir des scripts généraux pour approfondir et obtenir plus de détails sur les syscalls individuels intéressants.
• nous pouvons activer les syscalls sys_enter et/ou sys_exit trouvées sous tracing/events/raw_syscalls. Ceux-ci sont appelés pour toutes les syscalls ; le champ id peut être utilisé pour distinguer les numéros de syscall individuels.

Pour ce script, nous avons seulement besoin de savoir qu'une syscall a été entrée ; nous ne nous soucions pas de la façon dont elle est sortie, nous utiliserons donc perf record pour n'enregistrer que les événements sys_enter :

.ft C
# perf record -a -e raw_syscalls:sys_enter
^C[ perf record: Woken up 1 times to write data ]
[ perf record: Captured and wrote 56.545 MB perf.data (~2470503 samples) ]
.ft

Les options disent essentiellement de collecter des données pour chaque événement syscall dans tout le système et de multiplexer la sortie par cœur CPU en un seul flux. Ce flux unique sera enregistré dans un fichier dans le répertoire courant appelé perf.data.

Une fois que nous avons un fichier perf.data contenant nos données, nous pouvons utiliser l'option -g de perf script pour générer un script Python qui contiendra une fonction de rappel pour chaque type d'événement trouvé dans le flux de trace perf.data (pour plus de détails, voir la section SCRIPTS DE DÉMARRAGE).

En haut se trouve un bloc de commentaires suivi de quelques instructions d'importation et d'une ajout de chemin que tous les scripts perf devraient inclure.

Après cela, il y a quelques fonctions générées, trace_begin() et trace_end(), qui sont appelées au début et à la fin du script respectivement (pour plus de détails, voir la section STRUCTURE_DU_SCRIPT ci-dessous).

Après celles-ci se trouvent les fonctions de gestionnaire d'événements générées pour chaque événement dans la sortie de perf record. Les fonctions de gestionnaire prennent la forme subsystem__event_name, et contiennent des paramètres nommés, un pour chaque champ de l'événement ; dans ce cas, il n'y a qu'un seul événement, raw_syscalls__sys_enter(). (voir la section GESTIONNAIRES D'ÉVÉNEMENTS ci-dessous pour plus d'informations sur les gestionnaires d'événements).

Les deux dernières fonctions sont, comme les fonctions begin et end, générées pour chaque script. La première, trace_unhandled(), est appelée chaque fois que le script trouve un événement dans le fichier perf.data qui ne correspond à aucun gestionnaire d'événements dans le script. Cela pourrait signifier soit que l'étape d'enregistrement a enregistré des types d'événements qui ne l'intéressaient pas vraiment, soit que le script a été exécuté sur un fichier de trace qui ne correspond pas au script.

Le script généré par l'option -g imprime simplement une ligne pour chaque événement trouvé dans le flux de trace, c'est-à-dire qu'il affiche essentiellement l'événement et ses valeurs de paramètres sur la sortie standard. La fonction print_header() est simplement une fonction utilitaire utilisée à cette fin. Renommons le script et exécutons-le pour voir la sortie par défaut :

Bien sûr, pour ce script, nous ne sommes pas intéressés par l'impression de chaque événement de trace, mais plutôt par son agrégation d'une manière utile. Nous allons donc nous débarrasser de tout ce qui concerne l'impression ainsi que des fonctions trace_begin() et trace_unhandled(), que nous n'utiliserons pas. Cela nous laisse avec ce squelette minimaliste :

.ft C
import os
import sys
sys.path.append(os.environ['PERF_EXEC_PATH'] + \
        '/scripts/python/Perf-Trace-Util/lib/Perf/Trace')
from perf_trace_context import *
from Core import *
def trace_end():
        print "dans trace_end"
def raw_syscalls__sys_enter(event_name, context, common_cpu,
        common_secs, common_nsecs, common_pid, common_comm,
        id, args):
.ft

Dans trace_end(), nous allons simplement afficher les résultats, mais avant cela, nous devons générer quelques résultats à afficher. Pour ce faire, nous devons faire en sorte que notre gestionnaire sys_enter() effectue le comptage nécessaire jusqu'à ce que tous les événements aient été comptés. Une table de hachage indexée par l'ID de l'appel système est un bon moyen de stocker ces informations ; chaque fois que le gestionnaire sys_enter() est appelé, nous incrémentons simplement un compteur associé à cette entrée de hachage indexée par cet ID d'appel système :

.ft C
  syscalls = autodict()
  try:
    syscalls[id] += 1
  except TypeError:
    syscalls[id] = 1
.ft

L'objet autodict des appels système est un type spécial de dictionnaire Python (implémenté dans Core.py) qui implémente les hachages autovivifiants de Perl en Python, c'est-à-dire qu'avec les hachages autovivifiants, vous pouvez affecter des valeurs de hachage imbriquées sans avoir à créer les niveaux intermédiaires s'ils n'existent pas, par exemple syscalls[comm][pid][id] = 1 créera les niveaux de hachage intermédiaires et affectera finalement la valeur 1 à l'entrée de hachage pour id (car la valeur affectée n'est pas un objet de hachage en soi, la valeur initiale est affectée dans l'exception TypeError. Eh bien, il existe peut-être une meilleure façon de faire cela en Python, mais c'est ce qui fonctionne pour l'instant).

En intégrant ce code dans le gestionnaire raw_syscalls__sys_enter(), nous obtenons effectivement un dictionnaire à un seul niveau indexé par l'ID de l'appel système et dont les valeurs sont les compteurs que nous avons totalisés.

La fonction print_syscall_totals() itère sur les entrées du dictionnaire et affiche une ligne pour chaque entrée contenant le nom de l'appel système (les clés du dictionnaire contiennent les ID des appels système, qui sont passés à la fonction Util syscall_name(), qui traduit les numéros bruts des appels système en chaînes de noms d'appels système correspondants). La sortie est affichée après que tous les événements du trace aient été traités, en appelant la fonction print_syscall_totals() depuis le gestionnaire trace_end() appelé à la fin du traitement du script.

Le script final produisant la sortie montrée ci-dessus est présenté en entier ci-dessous (la fonction d'aide syscall_name() n'est pas encore disponible, vous ne pouvez manipuler que les ID pour le moment) :

.ft C
import os
import sys
sys.path.append(os.environ['PERF_EXEC_PATH'] + \
        '/scripts/python/Perf-Trace-Util/lib/Perf/Trace')
from perf_trace_context import *
from Core import *
from Util import *
syscalls = autodict()
def trace_end():
        print_syscall_totals()
def raw_syscalls__sys_enter(event_name, context, common_cpu,
        common_secs, common_nsecs, common_pid, common_comm,
        id, args):
        try:
                syscalls[id] += 1
        except TypeError:
                syscalls[id] = 1
def print_syscall_totals():
    if for_comm is not None:
            print "\nsyscall events for %s:\n\n" % (for_comm),
    else:
            print "\nsyscall events:\n\n",
    print "%-40s  %10s\n" % ("event", "count"),
    print "%-40s  %10s\n" % ("----------------------------------------", \
                                 "-----------"),
    for id, val in sorted(syscalls.iteritems(), key = lambda(k, v): (v, k), \
                                  reverse = True):
            print "%-40s  %10d\n" % (syscall_name(id), val),

Le script peut être exécuté comme auparavant :

# perf script -s syscall-counts.py

Ce sont donc les étapes essentielles pour écrire et exécuter un script. Le processus peut être généralisé à n'importe quel point de trace ou ensemble de points de trace qui vous intéressent - trouvez essentiellement le point de trace (les points de trace) qui vous intéressent en consultant la liste des événements disponibles montrée par perf list et/ou en consultant /sys/kernel/tracing/events/ pour des informations détaillées sur les événements et les champs, enregistrez les données de trace correspondantes en utilisant perf record, en lui passant la liste des événements intéressants, générez un script squelette en utilisant perf script -g python et modifiez le code pour agréger et afficher les données pour vos besoins particuliers.

Après avoir fait cela, vous pourriez vous retrouver avec un script généraliste que vous souhaitez conserver et avoir à disposition pour une utilisation future. En écrivant quelques scripts shell très simples et en les plaçant au bon endroit, vous pouvez faire apparaître votre script aux côtés des autres scripts listés par la commande perf script -l, par exemple :

.ft C
# perf script -l
List of available trace scripts:
  wakeup-latency                       system-wide min/max/avg wakeup latency
  rw-by-file <comm>                    r/w activity for a program, by file
  rw-by-pid                            system-wide r/w activity
.ft

Un effet secondaire agréable de cela est que vous capturez également la commande perf record, probablement longue, nécessaire pour enregistrer les événements pour le script.

Pour que le script apparaisse comme un script intégré, vous écrivez deux scripts simples, un pour l'enregistrement et un pour le rapport.

Le script record est un script shell portant le même nom de base que votre script, mais avec -record ajouté. Le script shell doit être placé dans le répertoire perf/scripts/python/bin de l'arborescence source du noyau. Dans ce script, vous écrivez la ligne de commande perf record nécessaire pour votre script :

.ft C
# cat kernel-source/tools/perf/scripts/python/bin/syscall-counts-record
#!/bin/bash
perf record -a -e raw_syscalls:sys_enter
.ft

Le script report est également un script shell portant le même nom de base que votre script, mais avec -report ajouté. Il doit également être situé dans le répertoire perf/scripts/python/bin. Dans ce script, vous écrivez la ligne de commande perf script -s nécessaire pour exécuter votre script :

.ft C
# cat kernel-source/tools/perf/scripts/python/bin/syscall-counts-report
#!/bin/bash
# description: system-wide syscall counts
perf script -s ~/libexec/perf-core/scripts/python/syscall-counts.py
.ft

Notez que l'emplacement du script Python indiqué dans le script shell se trouve dans le répertoire libexec/perf-core/scripts/python - c'est là que le script sera copié par make install lorsque vous installerez perf. Pour que l'installation copie votre script là-bas, votre script doit être situé dans le répertoire perf/scripts/python de l'arborescence source du noyau :

.ft C

Une fois que vous avez fait cela (n'oubliez pas de refaire un make install, sinon votre script n'apparaîtra pas à l'exécution), perf script -l devrait afficher une nouvelle entrée pour votre script :

.ft C
# perf script -l
List of available trace scripts:
  wakeup-latency                       system-wide min/max/avg wakeup latency
  rw-by-file <comm>                    r/w activity for a program, by file
  rw-by-pid                            system-wide r/w activity
  syscall-counts                       system-wide syscall counts

Vous pouvez maintenant effectuer l'étape d'enregistrement via perf script record :

# perf script record syscall-counts

et afficher la sortie en utilisant perf script report :

# perf script report syscall-counts

SCRIPTS DÉMARREURS

Vous pouvez rapidement commencer à écrire un script pour un ensemble particulier de données de trace en générant un script squelette à l'aide de perf script -g python dans le même répertoire qu'un fichier de trace perf.data existant. Cela générera un script de démarrage contenant un gestionnaire pour chaque type d'événement dans le fichier de trace ; il affiche simplement tous les champs disponibles pour chaque événement du fichier de trace.

Vous pouvez également consulter les scripts existants dans ~/libexec/perf-core/scripts/python pour des exemples typiques montrant comment effectuer des opérations de base comme agréger des données d'événements, afficher des résultats, etc. De plus, le script check-perf-script.py, bien qu'il ne soit pas intéressant pour ses résultats, tente d'exercer toutes les fonctionnalités principales de scripting.

GESTIONNAIRES D'ÉVÉNEMENTS

Lorsque perf script est appelé en utilisant un script de trace, une fonction de gestionnaire définie par l'utilisateur est appelée pour chaque événement dans la trace. S'il n'y a pas de fonction de gestionnaire définie pour un type d'événement donné, l'événement est ignoré (ou passé à une fonction trace_unhandled, voir ci-dessous) et l'événement suivant est traité.

La plupart des valeurs de champs des événements sont passées comme arguments à la fonction de gestionnaire ; certains des moins courants ne le sont pas - ceux-ci sont disponibles via des appels vers l'exécutable perf (voir ci-dessous).

Par exemple, la commande perf record suivante peut être utilisée pour enregistrer tous les événements sched_wakeup du système :

# perf record -a -e sched:sched_wakeup

Les traces destinées à être traitées à l'aide d'un script doivent être enregistrées avec l'option ci-dessus : -a pour activer la collecte à l'échelle du système.

Le fichier de format pour l'événement sched_wakeup définit les champs suivants (voir /sys/kernel/tracing/events/sched/sched_wakeup/format) :

.ft C
 format:
        field:unsigned short common_type;
        field:unsigned char common_flags;
        field:unsigned char common_preempt_count;
        field:int common_pid;
        field:char comm[TASK_COMM_LEN];
        field:pid_t pid;
        field:int prio;
        field:int success;
        field:int target_cpu;
.ft

La fonction de gestionnaire pour cet événement serait définie comme :

.ft C
def sched__sched_wakeup(event_name, context, common_cpu, common_secs,
       common_nsecs, common_pid, common_comm,
       comm, pid, prio, success, target_cpu):
       pass
.ft

Le gestionnaire prend la forme sous-système__nom_événement.

Les arguments common_* dans la liste des arguments du gestionnaire sont l'ensemble des arguments passés à tous les gestionnaires d'événements ; certains des champs correspondent aux champs common_* dans le fichier de format, mais certains sont synthétisés, et certains des champs common_* ne sont pas assez communs pour être passés à chaque événement comme arguments mais sont disponibles en tant que fonctions de bibliothèque.

Voici une brève description de chacun des arguments d'événement invariants :

event_name
le nom de l'événement sous forme de texte contexte un 'cookie' opaque utilisé dans les rappels vers perf common_cpu le cpu sur lequel l'événement s'est produit common_secs la partie secondes de l'horodatage de l'événement common_nsecs la partie nanosecondes de l'horodatage de l'événement common_pid le pid de la tâche courante common_comm le nom du processus courant

Tous les champs restants dans le fichier de format de l'événement ont des homologues en tant qu'arguments de fonction de gestionnaire du même nom, comme on peut le voir dans l'exemple ci-dessus.

Ce qui précède fournit les bases nécessaires pour accéder directement à chaque champ de chaque événement dans un trace, ce qui couvre 90 % de ce que vous devez savoir pour écrire un script de trace utile. Les sections ci-dessous couvrent le reste.

MISE EN PAGE DU SCRIPT

Chaque script Python de script perf doit commencer par configurer un chemin de recherche de modules Python et importer quelques modules de support (voir les descriptions des modules ci-dessous) :

.ft C
 import os
 import sys
 sys.path.append(os.environ['PERF_EXEC_PATH'] + \
              '/scripts/python/Perf-Trace-Util/lib/Perf/Trace')
 from perf_trace_context import *
 from Core import *
.ft

Le reste du script peut contenir des fonctions de gestionnaire et des fonctions de support dans n'importe quel ordre.

Outre les fonctions de gestionnaire d'événements discutées ci-dessus, chaque script peut implémenter un ensemble de fonctions facultatives :

trace_begin, si défini, est appelé avant le traitement de tout événement et donne aux scripts une chance d'effectuer des tâches de configuration :

.ft C
def trace_begin():
    pass
.ft

trace_end, si défini, est appelé après le traitement de tous les événements et donne aux scripts une chance d'effectuer des tâches de fin de script, telles que l'affichage des résultats :

.ft C
def trace_end():
    pass
.ft

trace_unhandled, si défini, est appelé pour tout événement pour lequel aucun gestionnaire n'est explicitement défini. L'ensemble standard d'arguments courants lui est passé :

.ft C
def trace_unhandled(event_name, context, event_fields_dict):
    pass
.ft

process_event, si défini, est appelé pour tout événement autre qu'un point de trace

.ft C
def process_event(param_dict):
    pass
.ft

context_switch, si défini, est appelé pour chaque changement de contexte

.ft C
def context_switch(ts, cpu, pid, tid, np_pid, np_tid, machine_pid, out, out_preempt, *x):
    pass
.ft

auxtrace_error, si défini, est appelé pour toute erreur de trace de zone AUX

.ft C
def auxtrace_error(typ, code, cpu, pid, tid, ip, ts, msg, cpumode, *x):
    pass
.ft

Les sections suivantes décrivent chacun des modules Python de scripts perf intégrés disponibles et leurs fonctions associées.

MODULES ET FONCTIONS DISPONIBLES

Les sections suivantes décrivent les fonctions et variables disponibles via les différents modules Python de script perf. Pour utiliser les fonctions et variables du module donné, ajoutez la ligne from XXXX import correspondante à votre script de script perf.

Module Core.py

Ces fonctions fournissent quelques fonctions essentielles aux scripts utilisateur.

Les fonctions flag_str et symbol_str fournissent des chaînes de caractères lisibles par l'homme pour les champs de drapeau et symboliques. Celles-ci correspondent aux chaînes et valeurs analysées à partir des champs print fmt des fichiers de format d'événement :

flag_str(event_name, field_name, field_value) - retourne la représentation textuelle correspondant à field_value pour le champ de drapeau field_name de l'événement event_name
symbol_str(event_name, field_name, field_value) - retourne la représentation textuelle correspondant à field_value pour le champ symbolique field_name de l'événement event_name

La fonction autodict renvoie un type spécial de dictionnaire Python qui implémente les hachages autovivifiants de Perl en Python, c'est-à-dire qu'avec les hachages autovivifiants, vous pouvez attribuer des valeurs de hachage imbriquées sans avoir à vous soucier de créer des niveaux intermédiaires s'ils n'existent pas.

autodict() - retourne une instance de dictionnaire autovivifiant

Module perf_trace_context

Certains des champs communs du fichier de format d'événement ne sont pas si communs, mais doivent néanmoins être rendus accessibles aux scripts utilisateur.

perf_trace_context définit un ensemble de fonctions qui peuvent être utilisées pour accéder à ces données dans le contexte de l'événement courant. Chacune de ces fonctions attend une variable de contexte, qui est la même que la variable de contexte passée à chaque gestionnaire d'événement tracepoint comme deuxième argument. Pour les événements non-tracepoint, la variable de contexte est également présente sous le nom perf_trace_context.perf_script_context.

common_pc(context) - retourne le nombre de préemptions communes pour l'événement courant
common_flags(context) - retourne les drapeaux communs pour l'événement courant
common_lock_depth(context) - retourne la profondeur de verrouillage commune pour l'événement courant
perf_sample_insn(context) - retourne l'instruction de code machine
perf_set_itrace_options(context, itrace_options) - définit les options --itrace si elles n'ont pas déjà été définies
perf_sample_srcline(context) - retourne le nom du fichier source, le numéro de ligne
perf_sample_srccode(context) - retourne le nom du fichier source, le numéro de ligne, la ligne source
perf_config_get(config_name) - retourne la valeur de l'élément de configuration nommé, ou None s'il n'est pas défini

Module Util.py

Diverses fonctions utilitaires à utiliser avec perf script :

nsecs(secs, nsecs) - retourne le nombre total de nanosecondes étant donné une paire secondes/nanosecondes
nsecs_secs(nsecs) - retourne la partie entière des secondes étant donné des nanosecondes
nsecs_nsecs(nsecs) - retourne le reste des nanosecondes étant donné des nanosecondes
nsecs_str(nsecs) - retourne une chaîne imprimable sous la forme secondes.nanosecondes
avg(total, n) - retourne la moyenne étant donné une somme et un nombre total de valeurs

CHAMPS SUPPORTÉS

Champs actuellement supportés :

ev_name, comm, id, stream_id, pid, tid, cpu, ip, time, period, phys_addr, addr, symbol, symoff, dso, time_enabled, time_running, values, callchain, brstack, brstacksym, datasrc, datasrc_decode, iregs, uregs, weight, transaction, raw_buf, attr, cpumode.

Champs qui peuvent également être présents :

flags - drapeaux d'échantillon
flags_disp - affichage des drapeaux d'échantillon
insn_cnt - nombre d'instructions pour déterminer les instructions par cycle (IPC)
cyc_cnt - nombre de cycles pour déterminer l'IPC
addr_correlates_sym - addr peut être corrélé à un symbole
addr_dso - addr dso
addr_symbol - addr symbole
addr_symoff - addr décalage de symbole

Certains champs ont des sous-éléments :

brstack: from, to, from_dsoname, to_dsoname, mispred, predicted, in_tx, abort, cycles.

brstacksym: items: from, to, pred, in_tx, abort (converti en chaîne)

Par exemple, nous pouvons utiliser ce code pour imprimer les champs "from", "to", "cycles" de brstack.

if brstack in dict: for entry in dict[brstack]: print "from %s, to %s, cycles %s" % (entry["from"], entry["to"], entry["cycles"])
