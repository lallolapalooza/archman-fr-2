NOM

perlsec — Sécurité Perl

DESCRIPTION

Perl est conçu pour faciliter la programmation sécurisée, même lors de l'exécution avec des privilèges supplémentaires, tels que des programmes setuid ou setgid. Contrairement à la plupart des shells de ligne de commande, qui sont basés sur plusieurs passes de substitution sur chaque ligne du script, Perl utilise un schéma d'évaluation plus conventionnel avec moins de pièges cachés. De plus, comme le langage dispose de plus de fonctionnalités intégrées, il peut moins dépendre de programmes externes (et potentiellement non fiables) pour accomplir ses objectifs.

INFORMATIONS DE CONTACT POUR LES VULNÉRABILITÉS DE SÉCURITÉ

Si vous pensez avoir trouvé une vulnérabilité de sécurité dans l'interpréteur Perl ou dans des modules maintenus dans la base du code de Perl, envoyez les détails par courriel à perl-security@perl.org <mailto:perl-security@perl.org>. Cette adresse est une liste de diffusion à adhésion fermée surveillée par l'équipe de sécurité de Perl.

Voir perlsecpolicy pour plus d'informations.

MÉCANISMES ET PRÉOCCUPATIONS DE SÉCURITÉ

Mode taint (contamination)

Par défaut, Perl active automatiquement un ensemble de vérifications de sécurité spéciales, appelées mode taint (mode de contamination), lorsqu'il détecte que son programme s'exécute avec des identifiants d'utilisateur ou de groupe réels et effectifs différents. Le bit setuid dans les permissions Unix est le mode 04000, le bit setgid est le mode 02000 ; l'un ou l'autre ou les deux peuvent être définis. Vous pouvez également activer explicitement le mode taint en utilisant le drapeau de commande -T. Ce drapeau est fortement suggéré pour les programmes serveur et tout programme exécuté au nom de quelqu'un d'autre, tel qu'un script CGI. Une fois le mode taint activé, il reste activé pour le reste de votre script.

Dans ce mode, Perl prend des précautions spéciales appelées vérifications taint pour éviter les pièges évidents et subtils. Certaines de ces vérifications sont raisonnablement simples, comme la vérification que les répertoires de chemin ne sont pas écrivables par d'autres ; les programmeurs prudents ont toujours utilisé de telles vérifications. D'autres vérifications, cependant, sont mieux prises en charge par le langage lui-même, et ce sont surtout ces vérifications qui contribuent à rendre un programme Perl set-id plus sûr qu'un programme C correspondant.

Le support des vérifications taint ajoute une surcharge à tous les programmes Perl, que vous utilisiez ou non les fonctionnalités taint. Perl 5.18 a introduit des symboles du préprocesseur C qui peuvent être utilisés pour désactiver les fonctionnalités taint lors de la construction de Perl.

Lorsque taint est activé, vous ne pouvez pas utiliser de données dérivées de l'extérieur de votre programme pour affecter autre chose à l'extérieur de votre programme - du moins, pas par accident. Tous les arguments de la ligne de commande, les variables d'environnement, les informations de locale (voir perllocale), les résultats de certains appels système (readdir(), readlink(), la variable de shmread(), les messages retournés par msgrcv(), les champs password, gcos et shell retournés par les appels getpwxxx()), et toute entrée de fichier sont marqués comme « tainted » (contaminés). Les données taint ne peuvent pas être utilisées directement ou indirectement dans aucune commande qui invoque un sous-shell, ni dans aucune commande qui modifie des fichiers, des répertoires ou des processus, à l'exception des suivantes:

  • Les arguments de "print" et "syswrite" ne sont pas vérifiés pour la contamination.
  • Les méthodes symboliques 
    $obj->$method(@args);

    et les références de sous-programmes symboliques

    &{$foo}(@args);
$foo->(@args);

    ne sont pas vérifiées pour la contamination. Cela nécessite une prudence supplémentaire à moins que vous ne vouliez que des données externes affectent votre flux de contrôle. À moins que vous ne limitiez soigneusement ce que sont ces valeurs symboliques, les gens sont capables d'appeler des fonctions en dehors de votre code Perl, telles que POSIX::system, auquel cas ils sont capables d'exécuter du code externe arbitraire.

  • Les clés de hachage ne sont jamais contaminées.

Pour des raisons d'efficacité, Perl adopte une vision conservatrice quant à savoir si les données sont contaminées. Si une expression contient des données contaminées, toute sous-expression peut être considérée comme contaminée, même si la valeur de la sous-expression n'est pas elle-même affectée par les données contaminées.

Étant donné que la contamination est associée à chaque valeur scalaire, certains éléments d'un tableau ou d'une table de hachage peuvent être contaminés et d'autres non. Les clés d'une table de hachage ne sont jamais contaminées.

Par exemple:

$arg = shift;               # $arg est contaminé
$hid = $arg . 'bar';        # $hid est aussi contaminé
$line = <>;                 # Contaminé
$line = <STDIN>;            # Aussi contaminé
open FOO, "/home/me/bar" or die $!;
$line = <FOO>;              # Toujours contaminé
$path = $ENV{'PATH'};       # Contaminé, mais voir ci-dessous
$data = 'abc';              # Non contaminé
system "echo $arg";         # Non sécurisé
system "/bin/echo", $arg;   # Considéré non sécurisé
                            # (Perl ne connaît pas /bin/echo)
system "echo $hid";         # Non sécurisé
system "echo $data";        # Non sécurisé jusqu'à ce que PATH soit défini
$path = $ENV{'PATH'};       # $path maintenant contaminé
$ENV{'PATH'} = '/bin:/usr/bin';
delete @ENV{'IFS', 'CDPATH', 'ENV', 'BASH_ENV'};
$path = $ENV{'PATH'};       # $path maintenant NON contaminé
system "echo $data";        # Est sécurisé maintenant !
open(FOO, "< $arg");        # OK - fichier en lecture seule
open(FOO, "> $arg");        # Pas OK - tentative d'écriture
open(FOO,"echo $arg|");     # Pas OK
open(FOO,"-|")
    or exec 'echo', $arg;   # Pas OK non plus
$shout = `echo $arg`;       # Non sécurisé, $shout maintenant contaminé
unlink $data, $arg;         # Non sécurisé
umask $arg;                 # Non sécurisé
exec "echo $arg";           # Non sécurisé
exec "echo", $arg;          # Non sécurisé
exec "sh", '-c', $arg;      # Très non sécurisé !
@files = <*.c>;             # non sécurisé (utilise readdir() ou similaire)
@files = glob('*.c');       # non sécurisé (utilise readdir() ou similaire)
# Dans les deux cas, les résultats de glob sont contaminés, puisque la liste des
# noms de fichiers provient de l'extérieur du programme.
$bad = ($arg, 23);          # $bad sera contaminé
$arg, `true`;               # Non sécurisé (bien que ce ne soit pas vraiment le cas)

Si vous essayez de faire quelque chose de non sécurisé, vous obtiendrez une erreur fatale disant quelque chose comme « Insecure dependency » ou « Insecure $ENV{PATH} ».

L'exception au principe selon lequel « une valeur contaminée en-têtes toute l'expression » est l'opérateur conditionnel ternaire "?:". Étant donné que le code avec un conditionnel ternaire

$result = $tainted_value ? "Untainted" : "Also untainted";

est effectivement

if ( $tainted_value ) {
    $result = "Untainted";
} else {
    $result = "Also untainted";
}

il n'est pas logique que $result soit contaminé.

Nettoyage et détection des données contaminées

Pour tester si une variable contient des données contaminées, et dont l'utilisation déclencherait ainsi un message « Insecure dependency », vous pouvez utiliser la fonction tainted() du module Scalar::Util, disponible sur votre miroir CPAN le plus proche, et incluse dans Perl à partir de la version 5.8.0. Ou vous pourrez peut-être utiliser la fonction is_tainted() suivante.

sub is_tainted {
    local $@;   # Ne pas polluer la valeur de l'appelant.
    return ! eval { eval("#" . substr(join("", @_), 0, 0)); 1 };
}

Cette fonction utilise le fait que la présence de données contaminées n'importe où dans une expression rend l'expression entière contaminée. Il serait inefficace pour chaque opérateur de tester chaque argument pour la contamination. Au lieu de cela, l'approche légèrement plus efficace et conservatrice est utilisée : si une valeur contaminée a été accédée dans la même expression, toute l'expression est considérée comme contaminée.

Mais tester la contamination ne vous mène que jusqu'à un certain point. Parfois, il suffit de nettoyer la contamination de vos données. Les valeurs peuvent être nettoyées en les utilisant comme clés dans une table de hachage ; sinon, le seul moyen de contourner le mécanisme de contamination est de référencer des sous-modèles à partir d'une correspondance d'expression régulière. Perl présume que si vous référencez une sous-chaîne en utilisant $1, $2, etc. dans un modèle non contaminé, vous saviez ce que vous faisiez lorsque vous avez écrit ce modèle. Cela signifie qu'il faut réfléchir un peu - ne pas simplement nettoyer aveuglément quoi que ce soit, sinon vous perdez tout le mécanisme. Nettoyage des données

Il est beaucoup plus sûr de vérifier les données qui ont été approuvées (par exemple, les valeurs autorisées de "bon") plutôt que de vérifier la présence de caractères indésirables. En effet, il est beaucoup trop facile d'oublier des caractères indésirables auxquels on n'avait pas pensé.

Voici un test pour s'assurer que les données ne contiennent que des caractères de "mot" (alphabétiques, numériques et tiret bas), un tiret, un symbole arobase ou un point.

if ($data =~ /^([-\@\w.]+)$/) {
    $data = $1;                     # $data maintenant non entaché
} else {
    die "Données invalides dans '$data'";      # enregistrer ceci quelque part
}

C'est relativement sûr car "/\w+/" ne correspond normalement pas aux métacaractères du shell, et le point, le tiret ou l'arobase n'auront pas de signification particulière pour le shell. L'utilisation de "/.+/" serait théoriquement dangereuse car elle laisserait passer n'importe quoi, mais Perl ne le vérifie pas. La leçon est que lors du nettoyage, il faut être extrêmement prudent avec ses motifs. Le nettoyage des données à l'aide d'expressions régulières est le *seul* mécanisme pour nettoyer des données entachées, sauf si vous utilisez la stratégie détaillée ci-dessous pour créer un processus enfant avec des privilèges réduits.

L'exemple n'enlève pas l'entachement de $data si "use locale" est actif, car les caractères correspondant à "\w" sont déterminés par la locale. Perl considère que les définitions de locale ne sont pas fiables car elles contiennent des données provenant de l'extérieur du programme. Si vous écrivez un programme sensible à la locale et que vous souhaitez nettoyer des données avec une expression régulière contenant "\w", mettez "no locale" avant l'expression dans le même bloc. Voir "SECURITY" dans perllocale pour plus de détails et d'exemples.

Commutateurs Sur la ligne "#!"

Lorsque vous rendez un script exécutable, afin de l'utiliser comme une commande, le système passera des commutateurs à perl depuis la ligne #! du script. Perl vérifie que tous les commutateurs de ligne de commande donnés à un script setuid (ou setgid) correspondent réellement à ceux définis sur la ligne #!. Certains environnements Unix et Unix-like imposent une limite d'un commutateur sur la ligne #!, vous pourriez donc avoir besoin d'utiliser quelque chose comme "-wU" au lieu de "-w -U" sur de tels systèmes. (Ce problème ne devrait se présenter que dans les environnements Unix ou Unix-like qui prennent en charge les scripts #! et setuid ou setgid.)

Mode entaché et @INC

Lorsque le mode entaché ("-T") est actif, les variables d'environnement "PERL5LIB", "PERLLIB", et "PERL_USE_UNSAFE_INC" sont ignorées par Perl. Vous pouvez toujours ajuster @INC depuis l'extérieur du programme en utilisant l'option de ligne de commande "-I" comme expliqué dans perlrun. Les deux variables d'environnement sont ignorées car elles sont cachées, et un utilisateur exécutant un programme pourrait ne pas savoir qu'elles sont définies, alors que l'option "-I" est clairement visible et donc autorisée.

Une autre façon de modifier @INC sans modifier le programme est d'utiliser le pragma "lib", par exemple :

perl -Mlib=/foo programme

L'avantage d'utiliser "-Mlib=/foo" par rapport à "-I/foo" est que le premier supprimera automatiquement les répertoires dupliqués, tandis que le second ne le fera pas.

Notez que si une chaîne entachée est ajoutée à @INC, le problème suivant sera signalé :

Dépendance non sécurisée dans require lors de l'exécution avec le commutateur -T

Dans les versions de Perl antérieures à 5.26, l'activation du mode entaché supprimait également le répertoire courant (".") de la valeur par défaut de @INC. Depuis la version 5.26, le répertoire courant n'est pas inclus dans @INC par défaut.

Nettoyage de votre Path

Pour les messages "Insecure $ENV{PATH}", vous devez définir $ENV{'PATH'} à une valeur connue, et chaque répertoire dans le chemin doit être absolu et non inscriptible par d'autres que son propriétaire et son groupe. Notez qu'au moins dans les environnements de type Unix, un composant vide du PATH peut être interprété comme "." (le répertoire local), ce qui déclenchera également ce message. Vous pourriez être surpris d'obtenir ce message même si le nom de chemin de votre exécutable est entièrement qualifié. Ceci n'est *pas* généré parce que vous n'avez pas fourni un chemin complet vers le programme ; au lieu de cela, il est généré parce que vous n'avez jamais défini votre variable d'environnement PATH, ou vous ne l'avez pas définie à quelque chose de sûr. Parce que Perl ne peut pas garantir que l'exécutable en question ne va pas lui-même exécuter un autre programme qui dépend de votre PATH, il s'assure que vous définissez le PATH.

PATH n'est pas la seule variable d'environnement qui peut causer des problèmes. Parce que certains shells peuvent utiliser les variables IFS, CDPATH, ENV et BASH_ENV, Perl vérifie que celles-ci sont vides ou non entachées lors du lancement de sous-processus. Vous pourriez vouloir ajouter quelque chose comme ceci à vos scripts setid et vérifiant l'entachement.

delete @ENV{qw(IFS CDPATH ENV BASH_ENV)};   # Rendre %ENV plus sûr

Il est également possible d'avoir des problèmes avec d'autres opérations qui ne se soucient pas d'utiliser des valeurs entachées. Faites une utilisation judicieuse des tests de fichiers pour traiter les noms de fichiers fournis par l'utilisateur. Lorsque cela est possible, faites les ouvertures et autres opérations *après* avoir correctement abandonné tout privilège spécial d'utilisateur (ou de groupe !). Perl ne vous empêche pas d'ouvrir des noms de fichiers entachés en lecture, alors faites attention à ce que vous affichez. Le mécanisme d'entachement est destiné à prévenir les erreurs stupides, pas à supprimer le besoin de réflexion.

Perl n'appelle pas le shell pour développer les jokers lorsque vous passez à "system" et "exec" des listes de paramètres explicites au lieu de chaînes contenant potentiellement des jokers de shell. Malheureusement, les fonctions "open", "glob", et les backticks ne fournissent aucune convention d'appel alternative, donc davantage de subterfuges seront nécessaires.

Perl fournit un moyen raisonnablement sûr d'ouvrir un fichier ou un tube à partir d'un programme setuid ou setgid : créez simplement un processus enfant avec des privilèges réduits qui effectue le sale travail pour vous. D'abord, créez un enfant en utilisant la syntaxe spéciale "open" qui relie le parent et l'enfant par un tube. Maintenant, l'enfant réinitialise son ensemble d'identifiants et tout autre attribut par processus, comme les variables d'environnement, les umasks, les répertoires de travail actuels, aux valeurs d'origine ou connues sûres. Ensuite, le processus enfant, qui n'a plus de permissions spéciales, effectue l'"open" ou un autre appel système. Enfin, l'enfant transmet les données qu'il a réussi à accéder au parent. Parce que le fichier ou le tube a été ouvert dans l'enfant tout en fonctionnant avec des privilèges inférieurs à ceux du parent, il est peu probable qu'il soit trompé pour faire quelque chose qu'il ne devrait pas.

Voici une façon de faire des backticks raisonnablement sûrement. Notez comment l'"exec" n'est pas appelé avec une chaîne que le shell pourrait développer. C'est de loin la meilleure façon d'appeler quelque chose qui pourrait être soumis à des échappements de shell : ne jamais appeler le shell du tout.

use English;
die "Impossible de forker : $!" unless defined($pid = open(KID, "-|"));
if ($pid) {           # parent
    while (<KID>) {
        # faire quelque chose
    }
    close KID;
} else {
    my @temp     = ($EUID, $EGID);
    my $orig_uid = $UID;
    my $orig_gid = $GID;
    $EUID = $UID;
    $EGID = $GID;
    # Abandonner les privilèges
    $UID  = $orig_uid;
    $GID  = $orig_gid;
    # S'assurer que les privilèges sont vraiment partis
    ($EUID, $EGID) = @temp;
    die "Impossible d'abandonner les privilèges"
        unless $UID == $EUID  && $GID eq $EGID;
    $ENV{PATH} = "/bin:/usr/bin"; # PATH minimal.
    # Envisager de nettoyer davantage l'environnement.
    exec 'myprog', 'arg1', 'arg2'
        or die "impossible d'exécuter myprog : $!";
}

Une stratégie similaire fonctionnerait pour l'expansion des jokers via "glob", bien que vous puissiez utiliser "readdir" à la place.

La vérification de l'entachement est plus utile lorsque, bien que vous vous fissiez confiance pour ne pas avoir écrit de programme qui vous donne tout, vous ne faites pas nécessairement confiance à ceux qui finissent par l'utiliser pour essayer de le tromper pour qu'il fasse quelque chose de mal. C'est le genre de vérification de sécurité qui est utile pour les programmes set-id et les programmes lancés pour le compte de quelqu'un d'autre, comme les programmes CGI.

Ceci est cependant très différent de ne même pas faire confiance à l'auteur du code pour ne pas essayer de faire quelque chose de malicieux. C'est le genre de confiance nécessaire lorsque quelqu'un vous tend un programme que vous n'avez jamais vu auparavant et dit : "Tiens, exécute ça." Pour ce genre de sécurité, vous pourriez vouloir jeter un œil au module Safe, inclus standard dans la distribution Perl. Ce module permet au programmeur de configurer des compartiments spéciaux dans lesquels toutes les opérations système sont interceptées et l'accès aux espaces de noms est soigneusement contrôlé. Safe ne doit cependant pas être considéré comme inviolable : il n'empêchera pas le code étranger de créer des boucles infinies, d'allouer des gigaoctets de mémoire, ni même d'exploiter des bugs de perl pour faire planter l'interpréteur hôte ou se comporter de manière imprévisible. Dans tous les cas, il faut l'éviter complètement si vous êtes vraiment préoccupé par la sécurité.

Condition de course shebang

Au-delà des problèmes évidents qui découlent de l'octroi de privilèges spéciaux à des systèmes aussi flexibles que les scripts, sur de nombreuses versions d'Unix, les scripts set-id sont intrinsèquement dangereux dès le départ. Le problème est une condition de course dans le noyau. Entre le moment où le noyau ouvre le fichier pour voir quel interpréteur exécuter et le moment où l'interpréteur (maintenant set-id) rouvre le fichier pour l'interpréter, le fichier en question peut avoir changé, surtout si vous avez des liens symboliques sur votre système.

Certains Unix, en particulier les plus récents, sont exempts de ce bug de sécurité inhérent. Sur de tels systèmes, lorsque le noyau transmet le nom du script set-id à ouvrir à l'interpréteur, au lieu d'utiliser un chemin sujet à la manipulation, il transmet plutôt /dev/fd/3. C'est un fichier spécial déjà ouvert sur le script, de sorte qu'il ne peut y avoir de condition de course à exploiter pour des scripts malicieux. Sur ces systèmes, Perl devrait être compilé avec "-DSETUID_SCRIPTS_ARE_SECURE_NOW". Le programme Configure qui construit Perl essaie de déterminer cela par lui-même, vous ne devriez donc jamais

doit vous-même. La plupart des versions modernes de SysVr4 et BSD 4.4 utilisent cette approche pour éviter la condition de concurrence du noyau.

Si vous ne disposez pas de la version sécurisée des scripts set-id, tout n'est pas perdu. Parfois, cette « fonctionnalité » du noyau peut être désactivée, de sorte que le noyau n'exécute pas les scripts set-id avec le bit set-id ou ne les exécute pas du tout. L'une ou l'autre solution évite l'exploitabilité de la condition de concurrence, mais n'aide pas à exécuter réellement les scripts set-id.

Si la fonctionnalité de script set-id du noyau n'est pas désactivée, alors tout script set-id constitue une vulnérabilité exploitable. Perl ne peut pas éviter d'être exploitable, mais signalera les scripts vulnérables lorsque cela est possible. Si Perl détecte qu'il est appliqué à un script set-id, il se plaindra bruyamment que votre script set-id n'est pas sécurisé et ne l'exécutera pas. Lorsque Perl se plaint, vous devez supprimer le bit set-id du script pour éliminer la vulnérabilité. Refuser d'exécuter le script ne ferme pas la vulnérabilité en soi ; c'est juste la manière dont Perl vous encourage à le faire.

Pour exécuter réellement un script set-id, si vous ne disposez pas de la version sécurisée des scripts set-id, vous devrez placer un wrapper C autour du script. Un wrapper C n'est qu'un programme compilé qui ne fait rien d'autre qu'appeler votre programme Perl. Les programmes compilés ne sont pas soumis au bug du noyau qui affecte les scripts set-id. Voici un wrapper simple, écrit en C :

#include <unistd.h>
#include <stdio.h>
#include <string.h>
#include <errno.h>
#define REAL_PATH "/chemin/vers/script"
int main(int argc, char **argv)
{
    execv(REAL_PATH, argv);
    fprintf(stderr, "%s: %s: %s\n",
                    argv[0], REAL_PATH, strerror(errno));
    return 127;
}

Compilez ce wrapper en un exécutable binaire, puis définissez le bit setuid ou setgid sur celui-ci plutôt que sur votre script. Notez que ce wrapper n'effectue aucune opération pour assainir l'environnement d'exécution, autre que de garantir qu'un chemin sécurisé vers le script est utilisé. Il ne fait qu'éviter la condition de concurrence shebang. Il s'appuie sur les propres fonctionnalités de Perl et sur le script lui-même pour être suffisamment prudent, afin de le rendre sécurisé pour exécuter le script set-id.

Protection de vos programmes

Il existe un certain nombre de façons de masquer la source de vos programmes Perl, avec des niveaux variables de « sécurité ».

Tout d'abord, cependant, vous ne pouvez pas supprimer la permission de lecture, car le code source doit être lisible pour être compilé et interprété. (Cela ne signifie pas que la source d'un script CGI est lisible par les personnes sur le Web, cependant.) Vous devez donc laisser les permissions au niveau socialement convivial de 0755. Cela permet aux personnes sur votre système local de ne voir que votre source.

Certaines personnes considèrent à tort cela comme un problème de sécurité. Si votre programme fait des choses non sécurisées et repose sur le fait que les gens ne savent pas comment exploiter ces insécurités, il n'est pas sécurisé. Il est souvent possible pour quelqu'un de déterminer les choses non sécurisées et de les exploiter sans consulter la source. La sécurité par obscurité, le nom donné au fait de masquer vos bugs au lieu de les corriger, est une sécurité bien maigre.

Vous pouvez essayer d'utiliser le chiffrement via des filtres source (Filter::* de CPAN, ou Filter::Util::Call et Filter::Simple depuis Perl 5.8). Mais les crackers pourraient être capables de le déchiffrer. Vous pouvez essayer d'utiliser le compilateur et l'interpréteur de bytecode décrits ci-dessous, mais les crackers pourraient être capables de le décompiler. Vous pouvez essayer d'utiliser le compilateur de code natif décrit ci-dessous, mais les crackers pourraient être capables de le désassembler. Ceux-ci posent des degrés de difficulté variables aux personnes qui veulent accéder à votre code, mais aucun ne peut le dissimuler définitivement (cela est vrai de tous les langages, pas seulement de Perl).

Si vous vous souciez que les gens profitent de votre code, alors en fin de compte, rien d'autre qu'une licence restrictive ne vous donnera une sécurité juridique. Licencez votre logiciel et parsemez-le de déclarations menaçantes comme « Ceci est un logiciel propriétaire non publié de XYZ Corp. Votre accès à celui-ci ne vous donne pas la permission de l'utiliser, bla bla bla. » Vous devriez consulter un avocat pour vous assurer que la formulation de votre licence sera valable devant un tribunal.

Unicode

Unicode est une technologie nouvelle et complexe et l'on peut facilement négliger certains pièges de sécurité. Voir perluniintro pour un aperçu et perlunicode pour les détails, et « Security Implications of Unicode » dans perlunicode pour les implications de sécurité en particulier.

Attaques par complexité algorithmique

Certains algorithmes internes utilisés dans l'implémentation de Perl peuvent être attaqués en choisissant l'entrée soigneusement pour consommer de grandes quantités de temps ou d'espace, ou les deux. Cela peut conduire à des attaques dites de déni de service (DoS).

•
Algorithme de hachage - Les algorithmes de hachage comme celui utilisé dans Perl sont bien connus pour être vulnérables aux attaques par collision sur leur fonction de hachage. De telles attaques impliquent la construction d'un ensemble de clés qui entrent en collision dans le même compartiment, produisant un comportement inefficace. De telles attaques dépendent souvent de la découverte de la graine de la fonction de hachage utilisée pour mapper les clés aux compartiments. Cette graine est ensuite utilisée pour forcer brutalement un ensemble de clés qui peut être utilisé pour monter une attaque par déni de service. Dans Perl 5.8.1, des modifications ont été introduites pour durcir Perl contre de telles attaques, puis plus tard dans Perl 5.18.0, ces fonctionnalités ont été améliorées et des protections supplémentaires ajoutées.

Au moment de la rédaction, Perl 5.18.0 est considéré comme bien protégé contre les attaques par complexité algorithmique sur son implémentation de hachage. Ceci est largement dû aux mesures suivantes qui atténuent les attaques :

Randomisation de la graine de hachage
Afin de rendre impossible de savoir quelle graine générer un ensemble de clés d'attaque, cette graine est initialisée aléatoirement au démarrage du processus. Cela peut être remplacé en utilisant la variable d'environnement PERL_HASH_SEED, voir « PERL_HASH_SEED » dans perlrun. Cette variable d'environnement contrôle la façon dont les éléments sont réellement stockés, et non la façon dont ils sont présentés via "keys", "values" et "each".
Randomisation du parcours du hachage
Indépendamment de la graine utilisée dans la fonction de hachage, "keys", "values" et "each" renvoient les éléments dans un ordre aléatoire par hachage. La modification d'un hachage par insertion changera l'ordre d'itération de ce hachage. Ce comportement peut être outrepassé en utilisant hash_traversal_mask() de Hash::Util ou en utilisant la variable d'environnement PERL_PERTURB_KEYS, voir « PERL_PERTURB_KEYS » dans perlrun. Notez que cette fonctionnalité contrôle l'ordre « visible » des clés, et non l'ordre réel dans lequel elles sont stockées.
Perturbation de l'ordre des compartiments
Lorsque des éléments entrent en collision dans un compartiment de hachage donné, l'ordre dans lequel ils sont stockés dans la chaîne n'est plus prévisible dans Perl 5.18. Ceci vise à rendre plus difficile l'observation d'une collision. Ce comportement peut être outrepassé en utilisant la variable d'environnement PERL_PERTURB_KEYS, voir « PERL_PERTURB_KEYS » dans perlrun.
Nouvelle fonction de hachage par défaut
La fonction de hachage par défaut a été modifiée dans le but de rendre plus difficile l'inférence de la graine de hachage.
Fonctions de hachage alternatives
Le code source inclut plusieurs algorithmes de hachage parmi lesquels choisir. Bien que nous pensions que le hachage Perl par défaut est robuste aux attaques, nous avons inclus la fonction de hachage Siphash comme option de secours. Au moment de la sortie de Perl 5.18.0, Siphash est considéré comme étant de force cryptographique. Ce n'est pas la valeur par défaut car il est beaucoup plus lent que le hachage par défaut.

Sans compiler un Perl spécial, il n'y a aucun moyen d'obtenir exactement le même comportement que les versions antérieures à Perl 5.18.0. Le plus proche que l'on puisse obtenir est en définissant PERL_PERTURB_KEYS à 0 et en définissant PERL_HASH_SEED à une valeur connue. Nous ne recommandons pas ces paramètres pour une utilisation en production en raison des considérations de sécurité ci-dessus.

Perl n'a jamais garanti d'ordre pour les clés de hachage, et l'ordre a déjà changé plusieurs fois au cours de la durée de vie de Perl 5. De plus, l'ordre des clés de hachage a toujours été, et continue d'être, affecté par l'ordre d'insertion et l'historique des modifications apportées au hachage au cours de sa durée de vie.

Notez également que si l'ordre des éléments de hachage peut être aléatoire, cet « ordre pseudo-aléatoire » ne doit pas être utilisé pour des applications telles que le mélange aléatoire d'une liste (utilisez List::Util::shuffle() pour cela, voir List::Util, un module standard inclus depuis Perl 5.8.0 ; ou le module CPAN "Algorithm::Numerical::Shuffle"), ou pour la génération de permutations (utilisez par exemple les modules CPAN "Algorithm::Permute" ou "Algorithm::FastPermute"), ou pour toute application cryptographique.

Les hachages liés peuvent avoir leur propre ordre et leurs propres attaques par complexité algorithmique.

  • Expressions régulières - Le moteur d'expressions régulières de Perl est le soi-disant NFA (Automate Fini Non déterministe), ce qui, entre autres, signifie qu'il peut assez facilement consommer de grandes quantités de temps et d'espace si l'expression régulière peut correspondre de plusieurs manières. Une élaboration soignée des expressions régulières peut aider, mais très souvent, il n'y a pas grand-chose que l'on puisse faire (le livre « Mastering Regular Expressions » est une lecture obligatoire, voir perlfaq2). Manquer d'espace se manifeste par le fait que Perl manque de mémoire.
  • Tri - l'algorithme quicksort utilisé dans les versions de Perl antérieures à 5.8.0 pour implémenter la fonction sort() était très facile à tromper pour qu'il se comporte mal afin qu'il consomme beaucoup de temps. À partir de Perl 5.8.0, un algorithme de tri différent, le tri fusion, est utilisé par défaut. Le tri fusion ne peut pas mal se comporter sur une entrée donnée.

Voir https://www.usenix.org/legacy/events/sec03/tech/full_papers/crosby/crosby.pdf pour plus d'informations, et tout manuel d'informatique sur la complexité algorithmique.

Utilisation de Sudo

L'outil populaire "sudo" fournit un moyen contrôlé pour les utilisateurs d'exécuter des programmes en tant qu'autres utilisateurs. Il assainit dans une certaine mesure l'environnement d'exécution, et

évitera la condition de concurrence des shebangs. Si vous n'avez pas la version sûre des scripts set-id, alors "sudo" peut être un moyen plus pratique d'exécuter un script en tant qu'un autre utilisateur que d'écrire un wrapper C. Cependant, "sudo" définit l'identifiant réel de l'utilisateur ou du groupe sur celui de l'identité cible, et pas seulement l'identifiant effectif comme le font les bits set-id. En conséquence, Perl ne peut pas détecter qu'il s'exécute sous "sudo", et ne prend donc pas automatiquement ses propres précautions de sécurité, comme l'activation du mode taint. Lorsque la configuration de "sudo" dicte exactement quelle commande peut être exécutée, la commande approuvée peut inclure une option "-T" pour perl afin d'activer le mode taint. En général, il est nécessaire d'évaluer l'aptitude d'un script à s'exécuter sous "sudo" spécifiquement en tenant compte de ce type d'environnement d'exécution. Il n'est ni nécessaire ni suffisant que le même script soit adapté à une configuration set-id traditionnelle, bien que de nombreux problèmes se recoupent.
