PERLSTYLE(1perl) Guide de référence du programmeur Perl PERLSTYLE(1perl)

NOM

perlstyle - Guide de style Perl

DESCRIPTION

Chaque programmeur aura, bien sûr, ses propres préférences en matière de formatage, mais il existe quelques directives générales qui rendront vos programmes plus faciles à lire, à comprendre et à maintenir.

La chose la plus importante est d'utiliser strict et warnings dans tout votre code ou de savoir pourquoi ne pas le faire. Vous pouvez les désactiver explicitement pour des portions particulières du code via "no warnings" ou "no strict", et cela peut être limité aux avertissements spécifiques ou aux fonctionnalités strictes que vous souhaitez désactiver. Le drapeau -w et la variable $^W ne doivent pas être utilisés à cette fin car ils peuvent affecter le code que vous utilisez mais n'avez pas écrit, comme les modules du noyau ou de CPAN.

Une façon concise d'organiser cela est d'utiliser la syntaxe "use VERSION", en demandant une version 5.36 ou supérieure, ce qui activera les pragmas "strict" et "warnings" (ainsi que plusieurs autres fonctionnalités nommées utiles).

use v5.36;

Concernant l'esthétique de la mise en page du code, la seule chose à laquelle Larry tient fortement est que la parenthèse fermante d'un BLOC multi-lignes doit s'aligner avec le mot-clé qui a démarré la construction. Au delà de cela, il a d'autres préférences qui ne sont pas si fortes :

  • Indentation de 4 colonnes.
  • Parenthèse ouvrante sur la même ligne que le mot-clé, si possible, sinon alignée.
  • Espace avant la parenthèse ouvrante d'un BLOC multi-lignes.
  • Un BLOC d'une seule ligne peut être mis sur une seule ligne, y compris les parenthèses.
  • Pas d'espace avant le point-virgule.
  • Point-virgule omis dans un BLOC d'une seule ligne "court".
  • Espace autour de la plupart des opérateurs.
  • Espace autour d'un indice "complexe" (à l'intérieur des crochets).
  • Lignes vides entre les blocs qui font des choses différentes.
  • Elses non collés.
  • Pas d'espace entre le nom de la fonction et sa parenthèse ouvrante.
  • Espace après chaque virgule.
  • Lignes longues coupées après un opérateur (sauf "and" et "or").
  • Espace après la dernière parenthèse correspondante sur la ligne actuelle.
  • Aligner verticalement les éléments correspondants.
  • Omettre la ponctuation redondante tant que la clarté n'en souffre pas.

Larry a ses raisons pour chacune de ces choses, mais il ne prétend pas que l'esprit de tout le monde fonctionne de la même manière que le sien.

Voici d'autres problèmes de style plus substantiels à considérer :

  • Ce n'est pas parce que vous POUVEZ faire quelque chose d'une certaine manière que vous DEVRIEZ le faire ainsi. Perl est conçu pour vous donner plusieurs façons de faire n'importe quoi, alors envisagez de choisir la plus lisible. Par exemple 
    open(my $fh, '<', $foo) || die "Impossible d'ouvrir $foo : $!";

    est mieux que

    die "Impossible d'ouvrir $foo : $!" unless open(my $fh, '<', $foo);

    car la deuxième façon masque le point principal de l'instruction dans un modificateur. D'un autre côté

    print "Démarrage de l'analyse\n" if $verbose;

    est mieux que

    $verbose && print "Démarrage de l'analyse\n";

    car le point principal n'est pas de savoir si l'utilisateur a tapé -v ou non.

    De même, ce n'est pas parce qu'un opérateur vous permet d'assumer des arguments par défaut que vous devez utiliser ces défauts. Les défauts sont là pour les programmeurs système paresseux écrivant des programmes jetables. Si vous voulez que votre programme soit lisible, envisagez de fournir l'argument.

    Dans le même ordre d'idées, ce n'est pas parce que vous POUVEZ omettre les parenthèses dans de nombreux endroits que vous devriez le faire :

    return print reverse sort num values %array;
return print(reverse(sort num (values(%array))));

    En cas de doute, mettez des parenthèses. Au moins, cela permettra à un pauvre type de sauter sur la touche % dans vi.

    Même si vous n'avez pas de doute, considérez le bien-être mental de la personne qui devra maintenir le code après vous, et qui mettra probablement les parenthèses au mauvais endroit.

  • N'ayez pas peur d'utiliser des contorsions stupides pour sortir d'une boucle par le haut ou par le bas, lorsque Perl fournit l'opérateur "last" pour que vous puissiez sortir au milieu. Il suffit de le "désindenter" un peu pour le rendre plus visible : 
    LINE:
    for (;;) {
        statements;
      last LINE if $foo;
        next LINE if /^#/;
        statements;
    }
  • N'ayez pas peur d'utiliser des étiquettes de boucle - elles sont là pour améliorer la lisibilité ainsi que pour permettre des interruptions de boucle à plusieurs niveaux. Voir l'exemple précédent.
  • Évitez d'utiliser grep() (ou map()) ou des `backticks` dans un contexte nul, c'est-à-dire lorsque vous rejetez simplement leurs valeurs de retour. Ces fonctions ont toutes des valeurs de retour, alors utilisez-les. Sinon, utilisez une boucle foreach() ou la fonction system() à la place.
  • Pour la portabilité, lors de l'utilisation de fonctionnalités qui peuvent ne pas être implémentées sur toutes les machines, testez la construction dans un eval pour voir si elle échoue. Si vous savez à quelle version ou quel niveau de patch une fonctionnalité particulière a été implémentée, vous pouvez tester $] ($PERL_VERSION dans "English") pour voir si elle sera là. Le module "Config" vous permettra également d'interroger les valeurs déterminées par le programme Configure lors de l'installation de Perl.
  • Choisissez des identifiants mnémoniques. Si vous ne vous souvenez pas de ce que signifie mnémonique, vous avez un problème.
  • Bien que de courts identifiants comme $gotit soient probablement corrects, utilisez des traits d'union pour séparer les mots dans des identifiants plus longs. Il est généralement plus facile de lire $var_names_like_this que $VarNamesLikeThis, surtout pour les non-natifs de l'anglais. C'est aussi une règle simple qui fonctionne de manière cohérente avec "VAR_NAMES_LIKE_THIS".

    Les noms de paquets sont parfois une exception à cette règle. Perl réserve informellement les noms de modules en minuscules pour les modules "pragma" comme "integer" et "strict". Les autres modules doivent commencer par une majuscule et utiliser la casse mixte, mais probablement sans traits d'union en raison des limitations des systèmes de fichiers primitifs dans la représentation des noms de modules sous forme de fichiers qui doivent tenir dans quelques octets épars.

  • Vous trouverez peut-être utile d'utiliser la casse des lettres pour indiquer la portée ou la nature d'une variable. Par exemple : 
    $ALL_CAPS_HERE   constantes uniquement (attention aux conflits avec les variables perl !)
$Some_Caps_Here  global/statique pour tout le package
$no_caps_here    variables my() ou local() de portée de fonction

    Les noms de fonctions et de méthodes semblent mieux fonctionner en minuscules. Par exemple, "$obj->as_string()".

    Vous pouvez utiliser un trait d'union initial pour indiquer qu'une variable ou une fonction ne doit pas être utilisée en dehors du package qui l'a définie.

  • Si vous avez une expression régulière vraiment compliquée, utilisez les modificateurs "/x" ou "/xx" et ajoutez des espaces pour qu'elle ressemble un peu moins à du bruit de ligne. N'utilisez pas le slash comme délimiteur lorsque votre regexp contient des slashes ou des backslashes.
  • Utilisez les opérateurs "and" et "or" pour éviter d'avoir à mettre autant de parenthèses autour des opérateurs de liste, et pour réduire l'incidence des opérateurs de ponctuation comme "&&" et "||". Appelez vos sous-routines comme si c'étaient des fonctions ou des opérateurs de liste pour éviter les ampersands et les parenthèses excessifs.
  • Utilisez des here documents au lieu de multiples instructions print().
  • Alignez verticalement les éléments correspondants, surtout s'ils sont trop longs pour tenir sur une seule ligne de toute façon. 
    $IDX = $ST_MTIME;
$IDX = $ST_ATIME       if $opt_u;
$IDX = $ST_CTIME       if $opt_c;
$IDX = $ST_SIZE        if $opt_s;
mkdir $tmpdir, 0700 or die "impossible de mkdir $tmpdir : $!";
chdir($tmpdir)      or die "impossible de chdir $tmpdir : $!";
mkdir 'tmp',   0777 or die "impossible de mkdir $tmpdir/tmp : $!";
  • Vérifiez toujours les codes de retour des appels système. Les bons messages d'erreur doivent aller sur "STDERR", inclure quel programme a causé le problème, quels étaient l'appel système et les arguments échoués, et (TRÈS IMPORTANT) doivent contenir le message d'erreur système standard pour ce qui s'est mal passé. Voici un exemple simple mais suffisant : 
opendir(my $dh, $dir)        or die "can't opendir $dir: $!";
  • Alignez vos translittérations lorsque cela a du sens : 
    tr [abc]
   [xyz];
  • Pensez à la réutilisabilité. Pourquoi gaspiller de l'énergie cérébrale pour une action unique alors que vous pourriez vouloir faire quelque chose de similaire à nouveau ? Envisagez de généraliser votre code. Envisagez d'écrire un module ou une classe d'objet. Envisagez de faire fonctionner votre code proprement avec "use strict" et "use warnings" activés. Envisagez de donner votre code. Envisagez de changer toute votre vision du monde. Envisagez... oh, peu importe.
  • Essayez de documenter votre code et utilisez le format Pod de manière cohérente. Voici les conventions couramment attendues :
    • Utilisez "C<>" pour les noms de fonctions, de variables et de modules (et plus généralement tout ce qui peut être considéré comme faisant partie du code, comme les descripteurs de fichiers ou les valeurs spécifiques). Notez que les noms de fonctions sont considérés comme plus lisibles avec des parenthèses après leur nom, c'est-à-dire function().
    • Utilisez "B<>" pour les noms de commandes comme cat ou grep.
    • Utilisez "F<>" ou "C<>" pour les noms de fichiers. "F<>" devrait être le seul code Pod pour les noms de fichiers, mais comme la plupart des formateurs Pod le rendent en italique, les chemins Unix et Windows avec leurs barres obliques et leurs barres obliques inverses peuvent être moins lisibles, et mieux rendus avec "C<>".
    • Soyez cohérent.
    • Soyez gentil.
