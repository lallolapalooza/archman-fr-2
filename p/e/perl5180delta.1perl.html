PERL5180DELTA(1perl) Guide du programmeur Perl PERL5180DELTA(1perl)

NOM

perl5180delta - ce qu'il y a de nouveau pour la version v5.18.0 de Perl

DESCRIPTION

Ce document décrit les différences entre la version v5.16.0 et la version v5.18.0.

Si vous effectuez une mise à niveau à partir d'une version antérieure, telle que la v5.14.0, lisez d'abord perl5160delta, qui décrit les différences entre les versions v5.14.0 et v5.16.0.

Améliorations du cœur

Nouveau mécanisme pour les fonctionnalités expérimentales

Les fonctionnalités expérimentales nouvellement ajoutées nécessiteront désormais cette incantation :

no warnings "experimental::nom_fonctionnalité";
use feature "nom_fonctionnalité";  # émettra un avertissement sans la ligne précédente

Il existe une nouvelle catégorie d'avertissements, appelée "experimental", contenant les avertissements que le pragma feature émet lors de l'activation de fonctionnalités expérimentales.

Les fonctionnalités expérimentales nouvellement ajoutées recevront également des identifiants d'avertissement spéciaux, qui consistent en "experimental::" suivi du nom de la fonctionnalité. (Le plan est d'étendre éventuellement ce mécanisme à tous les avertissements, pour permettre leur activation ou désactivation individuelle, et pas seulement par catégorie.)

En disant

no warnings "experimental::nom_fonctionnalité";

vous assumez la responsabilité de toute interruption que des changements futurs ou la suppression de la fonctionnalité pourraient causer.

Étant donné que certaines fonctionnalités (comme "~~" ou "my $_") émettent désormais des avertissements expérimentaux, et que vous pourriez vouloir les désactiver dans un code qui est également exécuté sur des versions de Perl qui ne reconnaissent pas ces catégories d'avertissement, envisagez d'utiliser le pragma "if" comme ceci :

no if $] >= 5.018, warnings => "experimental::nom_fonctionnalité";

Les fonctionnalités expérimentales existantes peuvent également commencer à émettre ces avertissements. Veuillez consulter perlexperiment pour savoir quelles fonctionnalités sont considérées comme expérimentales.

Révision des hashes

Les changements apportés à l'implémentation des hashes dans Perl v5.18.0 seront parmi les changements les plus visibles dans le comportement du code existant.

Par défaut, deux variables de hachage distinctes avec des clés et des valeurs identiques peuvent désormais fournir leur contenu dans un ordre différent là où il était auparavant identique.

Face à ces changements, la clé pour s'en défaire est d'accepter que les hashes sont des collections non ordonnées et d'agir en conséquence.

Randomisation des hashes

La graine utilisée par la fonction de hachage de Perl est désormais aléatoire. Cela signifie que l'ordre dans lequel les clés/valeurs seront renvoyés par des fonctions comme keys(), values() et each() différera d'une exécution à l'autre.

Ce changement a été introduit pour rendre les hashes de Perl plus résistants aux attaques par complexité algorithmique, et aussi parce que nous avons découvert qu'il expose les bugs de dépendance à l'ordre des hashes et les rend plus faciles à traquer.

Les mainteneurs de chaînes d'outils pourraient vouloir investir dans une infrastructure supplémentaire pour tester ce genre de choses. Exécuter les tests plusieurs fois de suite, puis comparer les résultats, facilitera la détection des dépendances à l'ordre des hashes dans le code. Les auteurs sont fortement encouragés à ne pas exposer l'ordre des clés des hashes de Perl à des audiences non sécurisées.

De plus, chaque hash a son propre ordre d'itération, ce qui devrait rendre beaucoup plus difficile de déterminer quelle est la graine de hash actuelle.

Nouvelles fonctions de hachage

Perl v5.18 inclut la prise en charge de plusieurs fonctions de hachage et a modifié la valeur par défaut (pour passer à ONE_AT_A_TIME_HARD). Vous pouvez choisir un algorithme différent en définissant un symbole au moment de la compilation. Pour une liste actuelle, consultez le document INSTALL. Notez qu'à partir de Perl v5.18, nous ne pouvons que recommander l'utilisation de la valeur par défaut ou de SIPHASH. Tous les autres sont connus pour avoir des problèmes de sécurité et sont uniquement à des fins de recherche.

La variable d'environnement PERL_HASH_SEED accepte désormais une valeur hexadécimale

"PERL_HASH_SEED" n'accepte plus un entier comme paramètre ; la valeur attendue est désormais une valeur binaire codée sous forme de chaîne hexadécimale, telle que "0xf5867c55039dc724". Ceci afin de permettre à l'infrastructure de prendre en charge des graines de hash de longueurs arbitraires, qui peuvent dépasser celle d'un entier. (SipHash utilise une graine de 16 octets.)

La variable d'environnement PERL_PERTURB_KEYS a été ajoutée

La variable d'environnement "PERL_PERTURB_KEYS" permet de contrôler le niveau de randomisation appliqué aux fonctions "keys" et similaires.

Lorsque "PERL_PERTURB_KEYS" est défini sur 0, Perl ne randomisera pas du tout l'ordre des clés. La probabilité que "keys" change en raison d'une insertion sera la même que dans les versions précédentes de Perl, essentiellement uniquement lorsque la taille du compartiment est modifiée.

Lorsque "PERL_PERTURB_KEYS" est défini sur 1, Perl randomisera les clés de manière non reproductible. La probabilité que "keys" change en raison d'une insertion sera très élevée. C'est le mode le plus sécurisé et le mode par défaut.

Lorsque "PERL_PERTURB_KEYS" est défini sur 2, Perl randomisera les clés de manière reproductible. Les exécutions répétées du même programme devraient produire le même résultat à chaque fois.

"PERL_HASH_SEED" implique un paramètre "PERL_PERTURB_KEYS" non défini par défaut. Définir "PERL_HASH_SEED=0" (un seul 0) implique "PERL_PERTURB_KEYS=0" (randomisation des clés de hash désactivée) ; définir "PERL_HASH_SEED" sur toute autre valeur implique "PERL_PERTURB_KEYS=2" (randomisation déterministe et reproductible des clés de hash). La spécification explicite de "PERL_PERTURB_KEYS" à un niveau différent annule ce comportement.

Hash::Util::hash_seed() renvoie maintenant une chaîne

Hash::Util::hash_seed() renvoie maintenant une chaîne au lieu d'un entier. Ceci est fait pour permettre à l'infrastructure de prendre en charge des graines de hachage de longueurs arbitraires qui pourraient dépasser celle d'un entier. (SipHash utilise une graine de 16 octets.)

La sortie de PERL_HASH_SEED_DEBUG a été modifiée

La variable d'environnement PERL_HASH_SEED_DEBUG fait maintenant afficher à Perl à la fois la fonction de hachage avec laquelle Perl a été compilé *et* la graine, en hexadécimal, utilisée pour ce processus. Le code qui analyserait cette sortie, s'il en existe, doit être modifié pour s'adapter au nouveau format. Exemple du nouveau format :

$ PERL_HASH_SEED_DEBUG=1 ./perl -e1
HASH_FUNCTION = MURMUR3 HASH_SEED = 0x1476bb9f

Mise à niveau vers Unicode 6.2

Perl prend désormais en charge Unicode 6.2. Une liste des changements par rapport à Unicode 6.1 est disponible sur http://www.unicode.org/versions/Unicode6.2.0.

Les alias de nom de caractère peuvent désormais inclure des caractères hors de la plage Latin1

Il est possible de définir vos propres noms pour les caractères à utiliser dans "\N{...}", charnames::vianame(), etc. Ces noms peuvent désormais contenir des caractères de toute la plage Unicode. Cela permet aux noms d'être dans votre langue maternelle, et pas seulement en anglais. Certaines restrictions s'appliquent aux caractères qui peuvent être utilisés (vous ne pouvez pas définir un nom qui contient de la ponctuation, par exemple). Voir "CUSTOM ALIASES" dans charnames.

Nouvelles sondes DTrace

Les nouvelles sondes DTrace suivantes ont été ajoutées :

  • "op-entry"
  • "loading-file"
  • "loaded-file"

"${^LAST_FH}"

Cette nouvelle variable donne accès au descripteur de fichier qui a été lu en dernier. C'est le descripteur utilisé par $. et par "tell" et "eof" sans arguments.

Opérations sur les ensembles d'expressions régulières

Ceci est une fonctionnalité expérimentale pour permettre la correspondance avec l'union, l'intersection, etc., d'ensembles de points de code, similaire à Unicode::Regex::Set. Elle peut également être utilisée pour étendre le traitement de "/x" aux classes de caractères [entre crochets], et comme remplacement des propriétés définies par l'utilisateur, permettant des expressions plus complexes. Voir "Classes de caractères entre crochets étendues" dans perlrecharclass.

Sous-routines lexicales

Cette nouvelle fonctionnalité est toujours considérée comme expérimentale. Pour l'activer :

use 5.018;
no warnings "experimental::lexical_subs";
use feature "lexical_subs";

Vous pouvez maintenant déclarer des sous-routines avec "state sub foo", "my sub foo", et "our sub foo". ("state sub" nécessite que la fonctionnalité "state" soit activée, sauf si vous l'écrivez comme "CORE::state sub foo".)

"state sub" crée une sous-routine visible dans la portée lexicale dans laquelle elle est déclarée. La sous-routine est partagée entre les appels à la sous-routine externe.

"my sub" déclare une sous-routine lexicale qui est créée à chaque entrée dans le bloc englobant. "state sub" est généralement légèrement plus rapide que "my sub".

"our sub" déclare un alias lexical à la sous-routine du package du même nom.

Pour plus d'informations, voir "Sous-routines lexicales" dans perlsub.

Étiquettes calculées

Les commandes de boucle "next", "last" et "redo", ainsi que l'opérateur spécial "dump", permettent désormais d'utiliser des expressions arbitraires pour calculer des étiquettes à l'exécution. Auparavant, tout argument qui n'était pas une constante était traité comme une chaîne vide.

Plus de sous-routines CORE::

Plusieurs autres fonctions intégrées ont été ajoutées en tant que sous-routines dans l'espace de noms CORE:: - à savoir, les mots-clés non redéfinissables qui peuvent être implémentés sans analyseurs personnalisés : "defined", "delete", "exists", "glob", "pos", "prototype", "scalar", "split", "study", et "undef".

Comme certaines de celles-ci ont des prototypes, prototype('CORE::...') a été modifié pour ne pas faire de distinction entre les mots-clés redéfinissables et non redéfinissables. Ceci afin de rendre prototype('CORE::pos') cohérent avec prototype(&CORE::pos).

"kill" avec des noms de signaux négatifs

"kill" a toujours permis un numéro de signal négatif, qui tue le groupe de processus au lieu d'un seul processus. Il a également permis les noms de signaux. Mais il ne se comportait pas de manière cohérente, car les noms de signaux négatifs étaient traités comme 0. Désormais, les noms de signaux négatifs comme "-INT" sont pris en charge et traités de la même manière que -2 [perl #112990].

Sécurité

Voir aussi : refonte des hachages

Certains des changements apportés à la refonte des hachages ont été faits pour améliorer la sécurité. Veuillez lire cette section.

Avertissement de sécurité "Storable" dans la documentation

La documentation pour "Storable" comprend maintenant une section qui avertit les lecteurs du danger d'accepter des documents Storable provenant de sources non fiables. En bref, la désérialisation de certains types de données peut entraîner le chargement de modules et d'autres exécutions de code. C'est un comportement documenté et souhaité, mais cela ouvre une voie d'attaque pour des entités malveillantes.

"Locale::Maketext" permettait l'injection de code via un template malveillant

Si les utilisateurs pouvaient fournir une chaîne de traduction à Locale::Maketext, cela pouvait être utilisé pour invoquer des sous-routines Perl arbitraires disponibles dans le processus courant.

Cela a été corrigé, mais il est toujours possible d'invoquer n'importe quelle méthode fournie par "Locale::Maketext" lui-même ou une sous-classe que vous utilisez. L'une de ces méthodes invoquera à son tour la sous-routine "sprintf" du cœur de Perl.

En résumé, permettre aux utilisateurs de fournir des chaînes de traduction sans les vérifier est une mauvaise idée.

Cette vulnérabilité est documentée dans CVE-2012-6329.

Éviter d'appeler memset avec un compteur négatif

Un code Perl mal écrit qui permet à un attaquant de spécifier le compteur à l'opérateur de répétition de chaîne "x" de Perl peut déjà causer une attaque par déni de service par épuisement de mémoire. Un défaut dans les versions de perl avant v5.15.5 peut transformer cela en un débordement de tampon sur le tas ; couplé aux versions de glibc avant 2.16, cela permet potentiellement l'exécution de code arbitraire.

La faille corrigée par ce commit a reçu l'identifiant CVE-2012-5195 et a été étudiée par Tim Brown.

Changements incompatibles

Voir aussi : refonte des hachages

Certains des changements apportés à la refonte des hachages ne sont pas entièrement compatibles avec les versions précédentes de perl. Veuillez lire cette section.

Un nom de caractère inconnu dans "\N{...}" est maintenant une erreur de syntaxe

Auparavant, cela générait un avertissement et le CARACTÈRE DE REMPLACEMENT Unicode était substitué. Unicode recommande maintenant que cette situation soit une erreur de syntaxe. De plus, le comportement précédent entraînait des avertissements et des comportements confus, et comme le CARACTÈRE DE REMPLACEMENT n'a aucune utilité autre que celle d'un substitut pour un caractère inconnu, tout code ayant ce problème est bogué.

Les alias de noms de caractères précédemment dépréciés dans "\N{}" sont maintenant des erreurs

Depuis la v5.12.0, il était déprécié d'utiliser certains caractères dans les noms de caractères "\N{...}" définis par l'utilisateur. Ceux-ci provoquent maintenant une erreur de syntaxe. Par exemple, il est maintenant une erreur de commencer un nom par un chiffre, comme dans

my $undraftable = "\N{4F}";    # Erreur de syntaxe !

ou d'avoir des virgules n'importe où dans le nom. Voir "ALIAS PERSONNALISÉS" dans charnames.

"\N{BELL}" fait maintenant référence à U+1F514 au lieu de U+0007

Unicode 6.0 a réutilisé le nom "BELL" pour un point de code différent de ce qu'il signifiait traditionnellement. Depuis Perl v5.14, l'utilisation de ce nom faisait toujours référence à U+0007, mais générait un avertissement de dépréciation. Maintenant, "BELL" fait référence à U+1F514, et le nom pour U+0007 est "ALERT". Toutes les fonctions dans charnames ont été mises à jour en conséquence.

Nouvelles restrictions sur la correspondance insensible à la casse multi-caractères dans les classes de caractères entre crochets des expressions régulières

Unicode a retiré sa recommandation précédente pour que les expressions régulières gèrent automatiquement les cas où un seul caractère peut correspondre à plusieurs caractères insensible à la casse, par exemple, la lettre LATIN SMALL LETTER SHARP S et la séquence "ss". Cela est dû au fait qu'il s'est avéré impraticable de le faire correctement dans toutes les circonstances. Comme Perl a essayé de le faire au mieux, il continuera à le faire. (Nous envisageons une option pour le désactiver.) Cependant, une nouvelle restriction est ajoutée à ces correspondances lorsqu'elles se produisent dans des classes de caractères [entre crochets]. Les gens spécifiaient des choses comme "/[\0-\xff]/i", et étaient surpris que cela corresponde à la séquence de deux caractères "ss" (puisque LATIN SMALL LETTER SHARP S apparaît dans cette plage). Ce comportement est également incohérent avec l'utilisation d'une propriété au lieu d'une plage : "\p{Block=Latin1}" inclut également LATIN SMALL LETTER SHARP S, mais "/[\p{Block=Latin1}]/i" ne correspond pas à "ss". La nouvelle règle est que pour qu'une correspondance insensible à la casse multi-caractères se produise dans une classe de caractères entre crochets, le caractère doit être explicitement listé, et non pas comme point de terminaison d'une plage. Cela obéit plus étroitement au Principe de Moindre Surprise. Voir "Classes de caractères entre crochets" dans perlrecharclass. Notez qu'un bogue [perl #89774], maintenant corrigé dans le cadre de ce changement, empêchait le comportement précédent de fonctionner pleinement.

Règles explicites pour les noms de variables et les identificateurs

En raison d'un oubli, les noms de variables à un seul caractère dans v5.16 étaient complètement illimités. Cela a ouvert la porte à plusieurs types de folie. Depuis la v5.18, ceux-ci suivent désormais les règles des autres identificateurs, en plus d'accepter les caractères qui correspondent à la propriété "\p{POSIX_Punct}".

Il n'y a plus de différence dans l'analyse des identificateurs spécifiés en utilisant des accolades par rapport à ceux sans accolades. Par exemple, Perl autorisait auparavant "${foo:bar}" (avec un seul deux-points), mais pas $foo:bar. Maintenant que les deux sont gérés par un seul chemin de code, ils sont traités de la même manière : les deux sont interdits. Notez que ce changement concerne la plage des identificateurs littéraux autorisés, pas d'autres expressions.

Les tabulations verticales sont maintenant des espaces blancs

Personne ne pouvait se rappeler pourquoi "\s" ne correspondait pas à "\cK", la tabulation verticale. Maintenant, c'est le cas. Compte tenu de la rareté extrême de ce caractère, très peu de problèmes sont attendus. Cela dit, voici ce que cela signifie :

"\s" dans une expression régulière correspond maintenant à une tabulation verticale dans toutes les circonstances.

Les tabulations verticales littérales dans un littéral d'expression régulière sont ignorées lorsque le modificateur "/x" est utilisé.

Les tabulations verticales de tête, seules ou mélangées à d'autres espaces blancs, sont désormais ignorées lors de l'interprétation d'une chaîne de caractères comme un nombre. Par exemple :

$dec = " \cK \t 123";
$hex = " \cK \t 0xF";
say 0 + $dec;   # était 0 avec avertissement, maintenant 123
say int $dec;   # était 0, maintenant 123
say oct $hex;   # était 0, maintenant 15

"/(?{})/" et "/(??{})/" ont été considérablement retravaillés

L'implémentation de cette fonctionnalité a été presque entièrement réécrite. Bien que son objectif principal soit de corriger des bugs, certains comportements, notamment en ce qui concerne la portée des variables lexicales, auront changé. Ceci est décrit plus en détail dans la section « Corrections de bugs sélectionnées ».

Analyse plus stricte du remplacement de substitution

Il n'est plus possible d'abuser de la façon dont l'analyseur analyse "s///e" comme ceci :

%_=(_,"Just another ");
$_="Perl hacker,\n";
s//_}->{_/e;print

"given" alias maintenant le global $_

Au lieu d'affecter un lexical implicite $_, "given" fait maintenant de $_ global un alias pour son argument, tout comme "foreach". Cependant, il utilise toujours le lexical $_ s'il y a un lexical $_ dans la portée (encore une fois, tout comme "foreach") [perl #114020].

La famille de fonctionnalités smartmatch est maintenant expérimentale

Smart match, ajouté dans la v5.10.0 et révisé de manière significative dans la v5.10.1, a été un point de plainte régulier. Bien qu'il y ait un certain nombre de façons dont il est utile, il s'est également avéré problématique et déroutant pour les utilisateurs et les implémenteurs de Perl. Il y a eu un certain nombre de propositions sur la meilleure façon de résoudre le problème. Il est clair que smartmatch va presque certainement changer ou disparaître à l'avenir. L'utilisation de son comportement actuel n'est pas recommandée.

Des avertissements seront désormais émis lorsque l'analyseur rencontrera "~~", "given" ou "when". Pour désactiver ces avertissements, vous pouvez ajouter cette ligne dans la portée appropriée :

no if $] >= 5.018, warnings => "experimental::smartmatch";

Considérez, cependant, le remplacement de l'utilisation de ces fonctionnalités, car leur comportement pourrait à nouveau changer avant de devenir stable.

Le $_ lexical est maintenant expérimental

Depuis son introduction dans Perl v5.10, il a causé beaucoup de confusion sans solution évidente :

  • Divers modules (par exemple, List::Util) attendent que les routines de rappel utilisent le $_ global. "use List::Util 'first'; my $_; first { $_ == 1 } @list" ne fonctionne pas comme on pourrait s'y attendre.
  • Une déclaration "my $_" plus tôt dans le même fichier peut provoquer des avertissements de fermeture déroutants.
  • Le caractère de prototype de sous-routine « _ » permet aux sous-routines appelées d'accéder à votre $_ lexical, il n'est donc pas vraiment privé après tout.
  • Néanmoins, les sous-routines avec un prototype « (@) » et les méthodes ne peuvent pas accéder au $_ lexical de l'appelant, sauf si elles sont écrites en XS.
  • Mais même les routines XS ne peuvent pas accéder à un $_ lexical déclaré, non pas dans la sous-routine appelante, mais dans une portée extérieure, si cette sous-routine n'a pas mentionné $_ ou n'a pas utilisé d'opérateurs qui par défaut sur $_.

Nous espérons que le $_ lexical pourra être réhabilité, mais cela pourrait entraîner des changements dans son comportement. Veuillez l'utiliser avec prudence jusqu'à ce qu'il devienne stable.

readline() avec « $/ = \N » lit maintenant N caractères, pas N octets

Auparavant, lors de la lecture à partir d'un flux avec des couches d'E/S telles que "encoding", la fonction readline(), également connue sous le nom d'opérateur "<>", lisait *N* octets à partir de la couche supérieure. [perl #79960]

Maintenant, *N* caractères sont lus à la place.

Il n'y a aucun changement de comportement lors de la lecture à partir de flux sans couches supplémentaires, car les octets correspondent exactement aux caractères.

Le « glob » surchargé reçoit maintenant un argument

Les surcharges de "glob" recevaient auparavant un deuxième argument magique non documenté qui identifiait l'appelant. Rien sur CPAN n'utilisait cela, et cela entravait la correction d'un bug, il a donc été supprimé. Si vous avez vraiment besoin d'identifier l'appelant, consultez Devel::Callsite sur CPAN.

Analyse des here docs

Le corps d'un here document à l'intérieur d'un opérateur de type quote commence désormais toujours sur la ligne suivant le marqueur « <<foo ». Auparavant, il était documenté comme commençant sur la ligne suivant l'opérateur de type quote contenant, mais ce n'était que parfois le cas [perl #114040].

Les opérateurs alphanumériques doivent maintenant être séparés du délimiteur de fermeture des expressions régulières

Vous ne pouvez plus écrire quelque chose comme :

m/a/and 1

Vous devez maintenant écrire

m/a/ and 1

avec un espace séparant l'opérateur du délimiteur de fermeture de l'expression régulière. L'absence d'espace entraînait un avertissement de dépréciation depuis la version Perl v5.14.0.

qw(...) ne peut plus être utilisé comme parenthèses

Les listes « qw » trompaient auparavant l'analyseur en lui faisant croire qu'elles étaient toujours entourées de parenthèses. Cela permettait des constructions surprenantes telles que "foreach $x qw(a b c) {...}", qui devrait plutôt s'écrire "foreach $x (qw(a b c)) {...}". Celles-ci pouvaient parfois mettre le lexer dans le mauvais état, donc elles ne fonctionnaient pas complètement, et le similaire "foreach qw(a b c) {...}" que l'on pourrait s'attendre à autoriser n'a jamais fonctionné du tout.

Cet effet secondaire de "qw" a maintenant été aboli. Il est déprécié depuis Perl v5.13.11. Il est désormais nécessaire d'utiliser de vraies parenthèses partout où la grammaire l'exige.

Interaction des avertissements lexicaux et par défaut

L'activation de tout avertissement lexical désactivait auparavant tous les avertissements par défaut si les avertissements lexicaux n'étaient pas déjà activés :

$*; # avertissement de dépréciation
use warnings "void";
$#; # avertissement void; pas d'avertissement de dépréciation

Maintenant, les catégories d'avertissement "debugging", "deprecated", "glob", "inplace" et "malloc" restent activées lors de l'activation des avertissements lexicaux (sauf si elles sont désactivées par "no warnings", bien sûr).

Cela peut entraîner l'apparition d'avertissements de dépréciation dans du code qui était auparavant exempt d'avertissements.

Ce sont les seules catégories ne contenant que des avertissements par défaut. Les avertissements par défaut dans d'autres catégories sont toujours désactivés par "use warnings "category"", car nous n'avons pas encore l'infrastructure pour contrôler les avertissements individuels.

"state sub" et "our sub"

En raison d'un accident historique, "state sub"

n> et "notre sub" étaient équivalents à un simple "sub", on pouvait même créer une sub anonyme avec "notre sub { ... }". Celles-ci sont maintenant interdites en dehors de la fonctionnalité "lexical_subs". Sous la fonctionnalité "lexical_subs", elles ont de nouveaux sens décrits dans "Lexical Subroutines" dans perlsub.

Les valeurs définies stockées dans l'environnement sont forcées en chaînes d'octets

Une valeur stockée dans une variable d'environnement était toujours transformée en chaîne lors de son héritage par les processus enfants.

Dans cette version, lors de l'assignation à %ENV, les valeurs sont immédiatement transformées en chaîne, et converties pour n'être qu'une chaîne d'octets.

Premièrement, elle est forcée d'être seulement une chaîne. Ensuite, si la chaîne est utf8 et que l'équivalent de utf8::downgrade() fonctionne, ce résultat est utilisé ; sinon, l'équivalent de utf8::encode() est utilisé, et un avertissement est émis concernant les caractères larges ("Diagnostics").

"require" échoue pour les fichiers illisibles

Lorsque "require" rencontre un fichier illisible, il échoue maintenant. Auparavant, il ignorait le fichier et continuait à chercher dans les répertoires de @INC [perl #113422].

"gv_fetchmeth_*" et SUPER

Les diverses fonctions XS "gv_fetchmeth_*" traitaient autrefois un paquet dont le nom se terminait par "::SUPER" de manière spéciale. Une recherche de méthode sur le paquet "Foo::SUPER" était traitée comme une recherche de méthode "SUPER" sur le paquet "Foo". Ce n'est plus le cas. Pour effectuer une recherche "SUPER", passez le stash de "Foo" et le drapeau "GV_SUPER".

Le premier argument de "split" est interprété de manière plus cohérente

Après certains changements plus tôt dans la v5.17, le comportement de "split" a été simplifié : si l'argument PATTERN s'évalue en une chaîne contenant un seul espace, il est traité comme l'était une chaîne *littérale* contenant un seul espace.

Certaines rares utilisations des antislashs dans les expressions régulières sont désormais dépréciées

Il existe trois paires de caractères que Perl reconnaît comme des méta-caractères dans les motifs d'expressions régulières : "{}", "[]", et "()". Ceux-ci peuvent être utilisés pour délimiter des motifs, comme dans :

m{foo}
s(foo)(bar)

Comme ce sont des méta-caractères, ils ont une signification spéciale pour les motifs d'expressions régulières, et il s'avère que vous ne pouvez pas désactiver cette signification spéciale par les moyens normaux qui consistent à les faire précéder d'un antislash, si vous les utilisez, par paire, dans un motif délimité par eux. Par exemple, dans

m{foo\{1,3\}}

les antislashs ne changent pas le comportement, et cela correspond à "f o" suivi d'une à trois autres occurrences de "o".

Les utilisations comme celle-ci, où ils sont interprétés comme des méta-caractères, sont extrêmement rares ; nous pensons qu'il n'en existe aucune, par exemple, dans tout CPAN. Par conséquent, cette dépréciation ne devrait affecter que très peu de code. Elle donne cependant un avertissement, indiquant que tout code de ce type doit être modifié, ce qui nous permettra en retour de changer le comportement dans les futures versions de Perl afin que les antislashs aient un effet, et sans craindre de casser silencieusement du code existant.

Séparation des tokens "(?" et "(*" dans les expressions régulières

Un avertissement de dépréciation est désormais émis si le "(" et le "?" sont séparés par un espace blanc ou des commentaires dans les constructions d'expressions régulières "(?...)". De même, si le "(" et le "*" sont séparés dans les constructions "(*VERB...)".

Implémentations IO pré-PerlIO

En théorie, vous pouvez actuellement construire perl sans PerlIO. Au lieu de cela, vous utiliseriez un wrapper autour de stdio ou sfio. En pratique, ce n'est pas très utile. Ce n'est pas bien testé, et sans aucun support pour les couches IO ou (donc) Unicode, ce n'est pas vraiment un perl. La construction sans PerlIO sera très probablement supprimée dans la prochaine version de perl.

PerlIO prend en charge une couche "stdio" si l'utilisation de stdio est souhaitée. De même, une couche sfio pourrait être produite à l'avenir, si nécessaire.

  • Échange de $< et $>

    Perl a pris en charge l'idiome d'échange de $< et $> (et de même $( et $)) pour abandonner temporairement les permissions depuis la version 5.0, comme ceci :

    ($<, $>) = ($>, $<);

    Cependant, cet idiome modifie l'identifiant utilisateur/groupe réel, ce qui peut avoir des effets secondaires indésirables, n'est plus utile sur aucune plateforme supportée par perl et complique la mise en œuvre de ces variables et l'affectation de listes en général.

    En alternative, l'affectation uniquement à $> est recommandée :

    local $> = $<;

    Voir aussi : Setuid Demystified http://www.cs.berkeley.edu/~daw/papers/setuid-usenix02.pdf.

  • Rénovation de la sémantique de "\Q" dans les chaînes entre guillemets doubles lorsqu'elles sont combinées avec d'autres échappements.

    Il existe plusieurs bugs et incohérences impliquant des combinaisons de "\Q" et d'échappements tels que "\x", "\L", etc., dans une paire "\Q...\E". Ceux-ci doivent être corrigés, et le faire changera nécessairement le comportement actuel. Les changements n'ont pas encore été finalisés.

  • L'utilisation de $x, où "x" représente n'importe quel caractère de contrôle C0 réel (non imprimable) sera interdite dans une future version de Perl. Utilisez plutôt "${x}" (où à nouveau "x" représente un caractère de contrôle), ou mieux, $^A , où "^" est un accent circonflexe, et "A" représente l'un des caractères listés à la fin de "OPERATOR DIFFERENCES" dans perlebcdic.

Améliorations des performances

  • Les listes de déclarations de variables lexicales ("my($x, $y)") sont maintenant optimisées en un seul op et sont donc plus rapides qu'auparavant.
  • Une nouvelle définition du préprocesseur C "NO_TAINT_SUPPORT" a été ajoutée. Si elle est définie, elle désactive complètement le support de la taint de Perl. L'utilisation des drapeaux de commande -T ou -t provoquera une erreur fatale. Attention, les tests de base ainsi que de nombreuses distributions CPAN échoueront avec ce changement. En contrepartie, il offre un léger gain de performance dû à une réduction des embranchements.

    N'activez cela que si vous savez exactement ce que vous faites.

  • "pack" avec des arguments constants est maintenant plié en constante dans la plupart des cas [perl #113470].
  • Accélération de la correspondance des expressions régulières avec les propriétés Unicode. Le gain le plus important concerne "\X", le « cluster de graphèmes étendu  » Unicode. Le gain pour celui-ci est d'environ 35 % à 40 %. Les classes de caractères entre crochets, par exemple "[0-9\x{100}]" contenant des points de code supérieurs à 255 sont également plus rapides maintenant.
  • Sur les plateformes qui le supportent, plusieurs anciennes macros sont maintenant implémentées comme des fonctions inline statiques. Cela devrait accélérer légèrement les choses sur les plateformes non-GCC.
  • L'optimisation des tables de hachage en contexte booléen a été étendue pour affecter scalar(%hash), "%hash ? ... : ...", et "sub { %hash || ... }".
  • Les opérateurs de test de fichier gèrent la pile de manière légèrement plus efficace.
  • Les jokers utilisés dans un contexte numérique sont maintenant numérisés directement dans la plupart des cas, au lieu d'être numérisés via la transformation en chaîne de caractères.
  • L'opérateur de répétition "x" est maintenant plié en une seule constante au moment de la compilation s'il est appelé dans un contexte scalaire avec des opérandes constants et sans parenthèses autour de l'opérande gauche.

    Nouveaux avertissements

    • 'Les chaînes avec des points de code supérieurs à 0xFF peuvent ne pas être mappées dans les handles de fichiers en mémoire'
    • '%s' résolu en '\o{%s}%d'
    • 'Les espaces blancs de fin dans une définition d'alias charnames sont dépréciés'
    • 'Une séquence d'espaces multiples dans une définition d'alias charnames est dépréciée'
    • 'Passer du UTF-8 mal formé à " %s " est déprécié'
    • La sous-routine "&%s" n'est pas disponible

      (W closure) Lors de la compilation, une sous-routine nommée interne ou un eval tente de capturer une sous-routine lexicale externe qui n'est pas actuellement disponible. Cela peut se produire pour l'une des deux raisons suivantes. Premièrement, la sous-routine lexicale peut être déclarée dans une sous-routine anonyme externe qui n'a pas encore été créée. (Rappelez-vous que les sous-routines nommées sont créées au moment de la compilation, tandis que les sous-routines anonymes sont créées au moment de l'exécution.) Par exemple,

      sub { my sub a {...} sub f { \&a } }

      Au moment où f est créé, il ne peut pas capturer le courant sous-routine "a", car la sous-routine anonyme n'a pas encore été créée. Inversement, ce qui suit ne générera pas d'avertissement car la sous-routine anonyme a maintenant été créée et est active :

      sub { my sub a {...} eval 'sub f { \&a }' }->();

      La deuxième situation est causée par un eval accédant à une variable qui est sortie de portée, par exemple,

      sub f {
    my sub a {...}
    sub { eval '\&a' }
}
f()->();

      Ici, lorsque '\&a' dans l'eval est en cours de compilation, f() n'est pas actuellement exécuté, donc son &a n'est pas disponible pour la capture.

    • La sous-routine "%s" &%s masque la déclaration précédente dans le même %s

      (W misc) Une sous-routine "my" ou "state" a été redéclarée dans la portée ou l'instruction actuelle, éliminant effectivement tout accès à l'instance précédente. C'est presque toujours une erreur typographique. Notez que la sous-routine précédente existera toujours jusqu'à la fin de la portée ou jusqu'à ce que toutes les références de fermeture à celle-ci soient détruites.

    • La fonctionnalité %s est expérimentale

      (S experimental) Cet avertissement est émis si vous activez une fonctionnalité expérimentale via "use feature". Supprimez simplement l'avertissement si vous souhaitez utiliser la fonctionnalité, mais sachez qu'en le faisant, vous prenez le risque d'utiliser une fonctionnalité expérimentale qui pourrait changer ou être supprimée dans une future version de Perl :

      no warnings "experimental::lexical_subs";
use feature "lexical_subs";
    • sleep(%u) trop grand

      (W overflow) Vous avez appelé "sleep" avec un nombre supérieur à ce qu'il peut gérer de manière fiable et "sleep" a probablement dormi moins longtemps que demandé.

    • Caractère large dans setenv

      Les tentatives d'insertion de caractères larges dans les variables d'environnement via %ENV provoquent maintenant cet avertissement.

    • "Nombre négatif invalide (%s) dans chr"

      chr() émet maintenant un avertissement lorsqu'il reçoit une valeur négative [perl #83048].

    • "Dépassement d'entier dans srand"

      srand() émet maintenant un avertissement lorsqu'il reçoit une valeur qui ne rentre pas dans un "UV" (car la valeur sera tronquée plutôt que de déborder) [perl #40605].

    • "-i utilisé sans noms de fichiers sur la ligne de commande, lecture depuis STDIN"

      L'exécution de perl avec le drapeau "-i" émet maintenant un avertissement si aucun fichier d'entrée n'est fourni sur la ligne de commande [perl #113410].

Au lieu de cela, elle place les fichiers spécifiques à l'architecture dans " $install_base/lib/perl5/$archname". Cela rend difficile l'utilisation d'un chemin de bibliothèque commun "INSTALL_BASE" avec plusieurs versions de perl.

      En définissant "-Duseversionedarchname", le $archname sera distinct pour l'architecture et la version de l'API, permettant une utilisation mixte de "INSTALL_BASE".

    • Ajout d'une option "PERL_NO_INLINE_FUNCTIONS"

      Si "PERL_NO_INLINE_FUNCTIONS" est définie, n'incluez pas "inline.h"

      Cela permet au code de test d'inclure les en-têtes perl pour les définitions sans créer de dépendance de liaison avec la bibliothèque perl (qui peut ne pas encore exister).

    • Configure honorera la variable d'environnement externe "MAILDOMAIN", si elle est définie.
    • "installman" ignore désormais l'option silencieuse.
    • Les fichiers "META.yml" et "META.json" sont désormais inclus dans la distribution.
    • Configure détectera désormais correctement isblank() lors de la compilation avec un compilateur C++.
    • La détection du paginator dans Configure a été améliorée pour permettre des réponses qui spécifient des options après le nom du programme, par exemple /usr/bin/less -R, si l'utilisateur accepte la valeur par défaut. Cela aide perldoc lors du traitement des échappements ANSI [perl #72156].

    BeOS était un système d'exploitation pour ordinateurs personnels développé par Be Inc, initialement pour son matériel BeBox. Le système d'exploitation Haiku a été écrit comme un remplacement/une continuation open source de BeOS, et son portage Perl est actuel et activement maintenu.

    Le support de MPE/IX a été supprimé.
    EPOC
    Le code de support relatif à EPOC a été supprimé. EPOC était une famille de systèmes d'exploitation développés par Psion pour les appareils mobiles. C'était le prédécesseur de Symbian. Le portage a été mis à jour pour la dernière fois en avril 2002.
    Rhapsody
    Le support de Rhapsody a été supprimé.

    Changements internes

    • Des synonymes pour la fonction mal nommée av_len() ont été créés : av_top_index() et "av_tindex". Ces trois fonctions retournent l'indice le plus élevé dans le tableau, pas le nombre d'éléments qu'il contient.
    • SvUPGRADE() n'est plus une expression. Initialement, cette macro (et sa fonction sous-jacente, sv_upgrade()) était documentée comme booléenne, bien qu'en réalité elle échouait toujours en cas d'erreur et ne retournait jamais faux. En 2005, la documentation a été mise à jour pour spécifier une valeur de retour vide, mais SvUPGRADE() a continué de retourner 1 pour des raisons de compatibilité ascendante. Cela a maintenant été supprimé, et SvUPGRADE() est maintenant une instruction sans valeur de retour.

      Ceci est donc maintenant une erreur de syntaxe :

      if (!SvUPGRADE(sv)) { croak(...); }

      Si vous avez du code comme celui-ci, remplacez-le simplement par

      SvUPGRADE(sv);

      ou pour éviter les avertissements du compilateur avec les anciennes versions de Perl, éventuellement

      (void)SvUPGRADE(sv);
    • Perl dispose d'un nouveau mécanisme de copie sur écriture qui permet à tout scalaire SvPOK d'être mis à niveau vers un scalaire en copie sur écriture. Un compte de références sur le tampon de chaîne est stocké dans le tampon de chaîne lui-même. Cette fonctionnalité n'est **pas activée par défaut**.

      Elle peut être activée dans une compilation de Perl en exécutant Configure avec -Accflags=-DPERL_NEW_COPY_ON_WRITE, et nous encourageons les auteurs XS à tester leur code avec un Perl ainsi activé, et à fournir des commentaires. Malheureusement, il n'y a pas encore de bon guide pour mettre à jour le code XS afin de gérer le COW. Tant qu'un tel document ne sera pas disponible, consultez la liste de diffusion perl5-porters.

      Cela casse quelques modules XS en permettant aux scalaires en copie sur écriture de passer par des chemins de code qu'ils n'avaient jamais rencontrés auparavant.

    • La copie sur écriture n'utilise plus les indicateurs SvFAKE et SvREADONLY. Par conséquent, SvREADONLY indique un SV réellement en lecture seule.

      Utilisez la macro SvIsCOW (comme auparavant) pour identifier un scalaire en copie sur écriture.

    • "PL_glob_index" a été supprimé.
    • La fonction privée Perl_croak_no_modify a vu son paramètre de contexte supprimé. Elle a maintenant un prototype vide. Les utilisateurs de l'API publique croak_no_modify ne sont pas affectés.
    • Les scalaires en copie sur écriture (clé de hachage partagée) ne sont plus marqués comme lecture seule. "SvREADONLY" retourne faux sur un tel SV, mais "SvIsCOW" retourne toujours vrai.
    • Un nouveau type d'op, "OP_PADRANGE", a été introduit. L'optimiseur peephole de Perl substituera, lorsque cela est possible, un seul op padrange à un pushmark suivi d'un ou plusieurs ops pad, et éventuellement aussi en sautant les ops de liste et de nextstate. De plus, l'op peut accomplir les tâches associées à la partie droite d'une affectation "my(...) = @_", de sorte que ces ops peuvent également être optimisés.
    • La correspondance insensible à la casse à l'intérieur d'une classe de caractères [entre crochets] avec un pliage multi-caractères n'exclut plus une des possibilités dans les circonstances où elle le faisait auparavant. [perl #89774].
    • "PL_formfeed" a été supprimé.
    • Le moteur d'expressions régulières ne lit plus un octet au-delà de la fin de la chaîne cible. Bien que pour tous les scalaires internes bien formés, cela n'ait jamais dû poser de problème, ce changement facilite les astuces intelligentes avec les tampons de chaîne dans les modules CPAN. [perl #73542]
    • À l'intérieur d'un bloc BEGIN, "PL_compcv" pointe maintenant vers la sous-routine en cours de compilation, plutôt que vers le bloc BEGIN lui-même.
    • "mg_length" a été déprécié.
    • "sv_len" retourne maintenant toujours un compte d'octets et "sv_len_utf8" un compte de caractères. Auparavant, "sv_len" et "sv_len_utf8" étaient tous deux bogués et pouvaient parfois retourner des octets et parfois des caractères. "sv_len_utf8" ne suppose plus que son argument est en UTF-8. Ni l'un ni l'autre ne crée désormais de caches UTF-8 pour les valeurs liées ou surchargées, ni pour les non-PV.
    • "sv_mortalcopy" copie maintenant les tampons de chaînes des scalaires de clés de hachage partagées lorsqu'ils sont appelés depuis des modules XS [perl #79824].
    • Le nouvel indicateur "RXf_MODIFIES_VARS" peut être défini par les moteurs d'expressions régulières personnalisés pour indiquer que l'exécution de l'expression régulière peut entraîner la modification des variables. Cela permet à "s///" de sauter certaines optimisations. Le propre moteur d'expressions régulières de Perl définit cet indicateur pour les verbes de backtracking spéciaux qui définissent $REGMARK et $REGERROR.
    • Les API d'accès aux pads lexicaux ont considérablement changé.

      "PADLIST"s ne sont plus des "AV"s, mais leur propre type à la place. Les "PADLIST"s contiennent maintenant un "PAD" et une "PADNAMELIST" de "PADNAME"s, plutôt que des "AV"s pour le pad et la liste des noms de pad. Les "PAD"s, "PADNAMELIST"s et "PADNAME"s doivent être accédés en tant que tels via la nouvelle API de pad ajoutée au lieu des API simples "AV" et "SV". Voir perlapi pour plus de détails.

    • Dans l'API regex, les rappels de capture numérotée reçoivent un index indiquant quelle variable de correspondance est accédée. Il existe des valeurs d'index spéciales pour les variables "$`, $&, $&". Auparavant, les trois mêmes valeurs étaient utilisées pour récupérer également "${^PREMATCH}, ${^MATCH}, ${^POSTMATCH}", mais celles-ci ont maintenant reçu trois valeurs distinctes. Voir "Numbered capture callbacks" dans perlreapi.
    • "PL_sawampersand" était auparavant un booléen indiquant que l'une des variables "$`, $&, $&" avait été vue ; il contient maintenant trois indicateurs d'un bit indiquant la présence de chacune des variables individuellement.
    • L'entrée typemap "CV *" prend maintenant en charge le surcharge "&{}" et les typeglobs, tout comme "&{...}" [perl #96872].
    • L'indicateur "SVf_AMAGIC" pour indiquer le surcharge est maintenant sur le stash, pas sur l'objet. Il est maintenant défini automatiquement chaque fois qu'une méthode ou @ISA change, donc sa signification a également changé. Il signifie maintenant "potentiellement surchargé". Lorsque la table de surcharge est calculée, l'indicateur est automatiquement désactivé s'il n'y a pas de surcharge, donc il ne devrait y avoir aucun ralentissement notable.

      La fraîcheur des tables de surcharge est maintenant vérifiée lorsque les méthodes de surcharge sont invoquées, plutôt que pendant "bless".

      "A" magic a disparu. Les changements apportés à la gestion de l'indicateur "SVf_AMAGIC" éliminent le besoin.

      "PL_amagic_generation" a été supprimé car il n'est plus nécessaire. Pour les modules XS, il s'agit maintenant d'un alias macro pour "PL_na".

      Le paramètre de surcharge de secours est maintenant stocké dans une entrée de stash distincte de la surcharge elle-même.

    • Le code de traitement des caractères a été nettoyé par endroits. Les changements devraient être invisibles en termes de fonctionnement.
    • La fonction "study" a été transformée en no-op dans la v5.16. Elle était simplement désactivée via une instruction "return" ; le code était laissé en place. Maintenant, le code qui prend en charge ce que "study"
    • La partie "cop->stashpv" qui était auparavant utilisée pour allouer dynamiquement un PV pour chaque COP afin de stocker son nom de paquet a été supprimée.
    • Sous les perls multithreadés, il n'y a plus de PV distinct alloué pour chaque COP afin de stocker son nom de paquet ("cop->stashpv"). À la place, il y a un décalage ("cop->stashoff") dans le nouveau tableau "PL_stashpad", qui contient des pointeurs de stash.
    • Dans l'API des expressions régulières enfichables, la structure "regexp_engine" a acquis un nouveau champ "op_comp", qui est actuellement réservé à l'usage interne de perl et doit être initialisé à NULL par les autres modules de plugin d'expressions régulières.
    • Une nouvelle fonction "alloccopstash" a été ajoutée à l'API, mais elle est considérée comme expérimentale. Voir perlapi.
    • Perl implémentait auparavant l'interception magique d'une manière qui pouvait parfois masquer des bugs dans le code qui pouvait appeler mg_get() trop de fois sur des valeurs magiques. Cette dissimulation d'erreurs ne se produit plus, de sorte que des bugs de longue date peuvent maintenant apparaître. Si vous rencontrez des erreurs liées à la magie dans du code XS, assurez-vous qu'il appelle mg_get() une seule fois sur les valeurs SvGMAGICAL(), ainsi que les fonctions de l'API Perl qu'il utilise.
    • L'allocation des OP pour les CV utilise maintenant un allocateur par blocs (slab allocator). Cela simplifie la gestion de la mémoire pour les OP alloués à un CV, rendant le nettoyage après une erreur de compilation plus simple et plus sûr [perl #111462][perl #112312].
    • "PERL_DEBUG_READONLY_OPS" a été réécrit pour fonctionner avec le nouvel allocateur par blocs, lui permettant de détecter davantage de violations qu'auparavant.
    • L'ancien allocateur par blocs pour les ops, qui n'était activé que pour "PERL_IMPLICIT_SYS" et "PERL_DEBUG_READONLY_OPS", a été retiré.

    Corrections de bogues sélectionnées

    • Les terminateurs de here-document ne nécessitent plus de caractère de fin de nouvelle ligne lorsqu'ils se trouvent à la fin d'un fichier. C'était déjà le cas à la fin d'une évaluation de chaîne [perl #65838].
    • Les compilations avec "-DPERL_GLOBAL_STRUCT" libèrent maintenant la structure globale après avoir fini de l'utiliser.
    • Un '/' final sur un chemin dans @INC n'aura plus un '/' supplémentaire ajouté.
    • La couche ":crlf" fonctionne maintenant lorsque les données non lues ne rentrent pas dans son propre tampon. [perl #112244].
    • ungetc() gère maintenant les données encodées en UTF-8. [perl #116322].
    • Un bug dans la typemap principale empêchait que les types C qui se mappent à l'entrée de typemap T_BOOL ne soient définis, mis à jour ou modifiés lorsque la variable T_BOOL était utilisée dans une section OUTPUT : avec une exception pour RETVAL. T_BOOL dans une section INPUT : n'était pas affecté. L'utilisation d'un type de retour T_BOOL pour un XSUB (RETVAL) n'était pas affectée. Un effet secondaire de la correction de ce bug est que, si un T_BOOL est spécifié dans la section OUTPUT : (qui ne faisait rien à l'SV auparavant), et qu'un SV en lecture seule (littéral) est passé à l'XSUB, des croaks comme "Modification d'une valeur en lecture seule tentée" se produiront. [perl #115796]
    • Sur de nombreuses plateformes, fournir un nom de répertoire comme nom de script faisait que perl ne faisait rien et rapportait un succès. Il devrait maintenant signaler universellement une erreur et se terminer avec un code non nul. [perl #61362]
    • "sort {undef} ..." sous des avertissements fatals ne plante plus. Cela avait commencé à planter dans Perl v5.16.
    • Les stashes imbriqués les uns dans les autres ("bless \%Foo::, 'Bar'; bless \%Bar::, 'Foo'") ne provoquent plus de doubles libérations. Ce bug a commencé à se produire dans Perl v5.16.
    • De nombreuses fuites de mémoire ont été corrigées, impliquant principalement des avertissements fatals et des erreurs de syntaxe.
    • Certains correspondances d'expressions régulières échouées telles que "'f' =~ /../g" ne réinitialisaient pas "pos". De plus, les motifs "une seule correspondance" ("m?...?g") ne le réinitialisaient pas non plus lorsqu'ils étaient invoqués une deuxième fois [perl #23180].
    • Plusieurs bugs impliquant "local *ISA" et "local *Foo::" provoquant des caches MRO obsolètes ont été corrigés.
    • Définir une sous-routine lorsque son glob de type a été aliasé ne résulte plus en des caches de méthodes obsolètes. Ce bug a été introduit dans Perl v5.10.
    • Localiser un glob de type contenant une sous-routine lorsque le paquet du glob de type a été supprimé de son stash parent ne produit plus d'erreur. Ce bug a été introduit dans Perl v5.14.
    • Dans certaines circonstances, "local *method=..." échouait à réinitialiser les caches de méthodes à la sortie de portée.
    • "/[.foo.]/" n'est plus une erreur, mais produit un avertissement (comme auparavant) et est traité comme "/[.fo]/" [perl #115818].
    • "goto $tied_var" appelle maintenant FETCH avant de décider du type de goto (sous-routine ou étiquette).
    • Renommer des paquets via une affectation de glob ("*Foo:: = *Bar::; *Bar:: = *Baz::") en combinaison avec "m?...?" et "reset" ne fait plus planter les builds multithreadés.
    • Un certain nombre de bugs liés à l'affectation d'une liste à un hash ont été corrigés. Beaucoup d'entre eux impliquent des listes avec des clés répétées comme "(1, 1, 1, 1)".
    • L'expression "scalar(%h = (1, 1, 1, 1))" renvoie maintenant 4, et non 2.
    • La valeur de retour de "%h = (1, 1, 1)" en contexte de liste était incorrecte. Auparavant, cela renvoyait "(1, undef, 1)", maintenant cela renvoie "(1, undef)".
    • Perl émet maintenant le même avertissement pour "($s, %h) = (1, {})" que pour "(%h) = ({})", "Référence trouvée où une liste de taille paire était attendue".
    • Un certain nombre de cas limites supplémentaires dans l'affectation de liste aux hachages ont été corrigés. Pour plus de détails, voir le commit 23b7025ebc.
    • Les attributs appliqués aux variables lexicales ne fuient plus de mémoire. [perl #114764]
    • "dump", "goto", "last", "next", "redo" ou "require" suivis d'un bareword (ou d'une version) puis d'un opérateur infixé ne sont plus une erreur de syntaxe. C'était le cas pour ces opérateurs infixés (comme "+") qui ont une signification différente là où un terme est attendu. [perl #105924]
    • "require a::b . 1" et "require a::b + 1" ne produisent plus d'avertissements d'ambiguïté erronés. [perl #107002]
    • Les appels de méthodes de classe sont maintenant autorisés sur toute chaîne, et pas seulement sur des chaînes commençant par un caractère alphanumérique. [perl #105922]
    • Un motif vide créé avec "qr//" utilisé dans "m///" ne déclenche plus le comportement "le motif vide réutilise le dernier motif". [perl #96230]
    • L'association (tying) d'un hash lors de l'itération ne résulte plus en une fuite de mémoire.
    • La libération d'un hash associé lors de l'itération ne résulte plus en une fuite de mémoire.
    • L'affectation de liste à un tableau ou un hash associé qui meurt sur STORE ne résulte plus en une fuite de mémoire.
    • Si le hash d'indices ("%^H") est associé, l'entrée de portée de compilation (qui copie le hash d'indices) ne fuit plus de mémoire si FETCH meurt. [perl #107000]
    • La pliage de constantes ne déclenche plus de manière inappropriée le comportement spécial "split ' '". [perl #94490]
    • "defined scalar(@array)", "defined do { &foo }", et des constructions similaires traitent maintenant l'argument de "defined" comme un scalaire simple. [perl #97466]
    • L'exécution d'un débogueur personnalisé qui ne définit aucun glob *DB::DB ou ne fournit pas de stub de sous-routine pour &DB::DB ne résulte plus en un crash, mais en une erreur. [perl #114990]
    • "reset ''" correspond maintenant à sa documentation. "reset" ne réinitialise que les motifs "m?...?" lorsqu'il est appelé sans argument. Une chaîne vide comme argument ne fait maintenant rien. (Elle était auparavant traitée comme sans argument.) [perl #97958]
    • "printf" avec un argument renvoyant une liste vide ne lit plus au-delà de la fin de la pile, ce qui entraînait un comportement erratique. [perl #77094]

    for my $i (0..2) {

  • Les déclarations "my ()" avec une liste de variables vide sont désormais autorisées [perl #113554].
  • Lors de l'analyse syntaxique, les sous-routines déclarées après des erreurs ne laissent plus de stubs [perl #113712].
  • Les fermetures ne contenant aucune évaluation de chaîne ne conservent plus leurs sous-routines englobantes, ce qui permet aux variables fermées par des sous-routines externes d'être libérées lorsque la sous-routine externe est libérée, même si la sous-routine interne existe toujours [perl #89544].
  • La duplication des descripteurs de fichiers en mémoire en les ouvrant avec un mode "<&=" ou ">&=" a cessé de fonctionner correctement en v5.16.0. Cela faisait que le nouveau descripteur référençait une variable scalaire différente. Ceci a été corrigé [perl #113764].
  • Les expressions "qr//" ne plantent plus avec des moteurs d'expressions régulières personnalisés qui ne définissent pas "offs" au moment de la compilation de l'expression régulière [perl #112962].
  • "delete local" ne plante plus avec certains tableaux et hachages magiques [perl #112966].
  • "local" sur les éléments de certains tableaux et hachages magiques n'organisait pas la suppression de l'élément à la sortie de portée, même si l'élément n'existait pas avant "local".
  • scalar(write) ne renvoie plus plusieurs éléments [perl #73690].
  • Les conversions de chaînes en virgule flottante ne paraphrasent plus mal certaines chaînes sous "use locale" [perl #109318].
  • Les filtres @INC qui meurent ne fuient plus de mémoire [perl #92252].
  • Les implémentations des opérations surchargées sont désormais appelées dans le contexte correct. Cela permet, entre autres, de remplacer correctement "<>" [perl #47119].
  • La spécification de la clé "fallback" uniquement lors de l'appel à "use overload" se comporte désormais correctement [perl #113010].
  • "sub foo { my $a = 0; while ($a) { ... } }" et "sub foo { while (0) { ... } }" renvoient désormais la même chose [perl #73618].
  • La négation de chaîne se comporte désormais de la même manière sous "use integer;" que sans [perl #113012].
  • "chr" renvoie désormais le caractère de remplacement Unicode (U+FFFD) pour -1, quelle que soit la représentation interne. -1 utilisait auparavant un wrapping si l'argument était lié ou une chaîne en interne.
  • L'utilisation d'un "format" après la libération de sa sous-routine englobante pouvait planter depuis perl v5.12.0, si le format référençait des variables lexicales de la sous-routine externe.
  • L'utilisation d'un "format" après la non-définition de sa sous-routine englobante pouvait planter depuis perl v5.10.0, si le format référençait des variables lexicales de la sous-routine externe.
  • L'utilisation d'un "format" défini à l'intérieur d'une fermeture, qui référence des variables lexicales de l'extérieur, n'a jamais vraiment fonctionné sauf si l'appel "write" était directement à l'intérieur de la fermeture. En v5.10.0, cela commençait même à planter. Désormais, la copie de cette fermeture la plus proche du sommet de la pile d'appels est utilisée pour trouver ces variables.
  • Les formats qui ferment sur des variables dans des blocs spéciaux ne plantent plus si une stub porte le même nom que le bloc spécial avant la compilation du bloc spécial.
  • L'analyseur syntaxique ne se perd plus, traitant "eval foo ()" comme une erreur de syntaxe si elle est précédée par "print;" [perl #16249].
  • La valeur de retour de "syscall" n'est plus tronquée sur les plateformes 64 bits [perl #113980].
  • La pliage de constantes n'entraîne plus "print 1 ? FOO : BAR" à écrire sur le descripteur FOO [perl #78064].
  • "do subname" appelle désormais la sous-routine nommée et utilise le nom de fichier qu'elle renvoie, au lieu d'ouvrir un fichier nommé "subname".
  • Les sous-routines recherchées par les crochets de vérification rv2cv (enregistrés par des modules XS) sont désormais prises en compte pour déterminer si "foo bar" doit être l'appel de sous-routine foo(bar) ou l'appel de méthode ""bar"->foo".
  • "CORE::foo::bar" n'est plus traité spécialement, permettant que les remplacements globaux soient appelés directement via CORE::GLOBAL::uc(...) [perl #113016].
  • L'appel d'une sous-routine indéfinie dont le typeglob a été indéfini produit désormais l'erreur habituelle "Undefined subroutine called", au lieu de "Not a CODE reference".
  • Deux bogues impliquant @ISA ont été corrigés. "*ISA = *glob_sans_tableau" et "undef *ISA; @{*ISA}" empêchaient les futures modifications de @ISA de mettre à jour les caches internes utilisés pour rechercher des méthodes. Le cas *glob_sans_tableau était une régression de Perl v5.12.
  • Les optimisations d'expressions régulières causaient parfois que "$" avec "/m" produise des correspondances échouées ou incorrectes [perl #114068].
  • "__SUB__" fonctionne désormais dans un bloc "sort" lorsque la sous-routine englobante est prédéclarée avec la syntaxe "sub foo;" [perl #113710].
  • Les propriétés Unicode ne s'appliquent qu'aux points de code Unicode, ce qui entraîne quelques subtilités lorsque les expressions régulières sont mises en correspondance avec des points de code supérieurs à Unicode. Un avertissement est généré pour attirer votre attention sur ce point. Cependant, cet avertissement était généré de manière inappropriée dans certains cas, par exemple lors de l'analyse d'un programme. Les correspondances non Unicode telles que "\w" et "[:word:]" ne devraient pas générer l'avertissement, car leurs définitions ne les limitent pas à s'appliquer uniquement aux points de code Unicode. Maintenant, le message n'est généré que lors de la mise en correspondance avec "\p{}" et "\P{}". Il subsiste un bogue, [perl #114148], pour les très rares propriétés Unicode qui correspondent à un seul point de code. L'avertissement n'est pas généré s'ils sont mis en correspondance avec un point de code supérieur à Unicode.
  • Les avertissements sur les éléments non initialisés concernant les éléments de hachage ne mentionnaient que le nom de l'élément s'il n'était pas dans le premier compartiment du hachage, en raison d'une erreur d'un cran.
  • Un bogue de l'optimiseur d'expressions régulières pouvait faire en sorte que le caractère "^" en mode multiligne se comporte incorrectement en présence de sauts de ligne, de sorte que ""/\n\n" =~ m#\A(?:^/$)#im" ne correspondait pas [perl #115242].
  • Les "fork" échoués en contexte de liste ne corrompent plus la pile. "@a = (1, 2, fork, 3)" avait l'habitude d'engloutir le 2 et d'assigner

    • Selected Bug Fixes

    • An attempt to call "undef" as a subroutine no longer crashes Perl.
    • Passing an undefined value to substr() no longer crashes Perl, and is now documented to return an empty string.
    • Accessing "${a[0]}" on an array reference that has been previously typed into a string, such as by doing "print $aref;", no longer corrupts the array reference.
    • A regular expression match against an empty string no longer produces false positives in certain obscure cases.
    • The /aa, /a, /c, and /u regex modifiers no longer interfere with each other.
    • A regression in Perl_re_match_util() that could cause crashes when sv_use_svlog() was used is fixed.
    • A regression where goto &sub would not correctly clear @_ if @_ had been explicitly set is fixed.
    • Forking child processes when running under use ithreads; is no longer liable to produce corrupted data.
    • Packers that return undef no longer cause Perl to exit with a status of (1, undef, 3) if the "fork" call failed.
    • Numerous memory leaks have been fixed, mostly involving tied variables that die, regular expression character classes and code blocks, and syntax errors.
    • Assigning a regular expression ("${qr//}") to a variable that happens to hold a floating point number no longer causes assertion failures on debugging builds.
    • Assigning a regular expression to a scalar containing a number no longer causes subsequent numification to produce random numbers.
    • Assigning a regular expression to a magic variable no longer wipes away the magic. This was a regression from v5.10.
    • Assigning a regular expression to a blessed scalar no longer results in crashes. This was also a regression from v5.10.
    • Regular expression can now be assigned to tied hash and array elements with flattening into strings.
    • Numifying a regular expression no longer results in an uninitialized warning.
    • Negative array indices no longer cause EXISTS methods of tied variables to be ignored. This was a regression from v5.12.
    • Negative array indices no longer result in crashes on arrays tied to non-objects.
    • "$byte_overload .= $utf8" no longer results in doubly-encoded UTF-8 if the left-hand scalar happened to have produced a UTF-8 string the last time overloading was invoked.
    • "goto &sub" now uses the current value of @_, instead of using the array the subroutine was originally called with. This means "local @_ = (...); goto &sub" now works [perl #43077].
    • If a debugger is invoked recursively, it no longer stomps on its own lexical variables. Formerly under recursion all calls would share the same set of lexical variables [perl #115742].
    • *_{ARRAY} returned from a subroutine no longer spontaneously becomes empty.
    • When using "say" to print to a tied filehandle, the value of "$\" is correctly localized, even if it was previously undef. [perl #119927]

    UTF8-flagged strings in %ENV on HP-UX 11.00 are buggy

    Reporting Bugs

    If you find what you think is a bug, you might check the articles recently posted to the comp.lang.perl.misc newsgroup and the perl bug database at http://rt.perl.org/perlbug/ . There may also be information at http://www.perl.org/ , the Perl Home Page.

    If you believe you have an unreported bug, please run the perlbug program included with your release. Be sure to trim your bug down to a tiny but sufficient test case. Your bug report, along with the output of "perl -V", will be sent off to perlbug@perl.org to be analysed by the Perl porting team.

    If the bug you are reporting has security implications, which make it inappropriate to send to a publicly archived mailing list, then please send it to perl5-security-report@perl.org. This points to a closed subscription unarchived mailing list, which includes all the core committers, who will be able to help assess the impact of issues, figure out a resolution, and help co-ordinate the release of patches to mitigate or fix the problem across all platforms on which Perl is supported. Please only use this address for security issues in the Perl core, not for modules independently distributed on CPAN.
