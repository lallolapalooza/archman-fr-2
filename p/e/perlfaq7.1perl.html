DESCRIPTION

Cette section traite des questions générales sur le langage Perl qui ne rentrent pas clairement dans les autres sections.

Peut-on obtenir une BNF/yacc/RE pour le langage Perl ?

Il n'y a pas de BNF, mais vous pouvez vous frayer un chemin dans la grammaire yacc de perly.y dans la distribution source si vous êtes particulièrement courageux. La grammaire repose sur un code de tokenisation très intelligent, alors préparez-vous à vous aventurer également dans toke.c.

Selon les mots de Chaim Frenkel : « La grammaire de Perl ne peut pas être réduite à une BNF. Le travail d'analyse syntaxique de Perl est réparti entre yacc, le lexer, la fumée et les miroirs. »

Que sont tous ces signes de ponctuation $`%&*_, et comment savoir quand les utiliser ?

Ce sont des spécificateurs de type, comme détaillé dans perldata :

$ pour les valeurs scalaires (nombre, chaîne ou référence)
@ pour les tableaux
% pour les hachages (tableaux associatifs)
& pour les sous-routines (également appelées fonctions, procédures, méthodes)
* pour tous les types de ce nom de symbole. Dans la version 4, vous les utilisiez
  comme des pointeurs, mais dans les Perl plus récents, vous pouvez simplement
  utiliser des références.

Il y a quelques autres symboles que vous êtes susceptible de rencontrer et qui ne sont pas réellement des spécificateurs de type :

<> sont utilisés pour lire un enregistrement à partir d'un handle de fichier.
\  prend une référence vers quelque chose.

Notez que <FILE> n'est ni le spécificateur de type pour les fichiers ni le nom du handle. C'est l'opérateur "<>" appliqué au handle FILE. Il lit une ligne (enfin, un enregistrement — voir « $/ » dans perlvar) à partir du handle FILE en contexte scalaire, ou toutes les lignes en contexte liste. Lors de l'ouverture, de la fermeture ou de toute autre opération autre que "<>" sur les fichiers, ou même lors de la référence au handle, n'utilisez pas les crochets. Voici ce qui est correct : eof(FH), "seek(FH, 0, 2)" et « copier depuis STDIN vers FILE ».

Dois-je toujours/ne jamais mettre entre guillemets mes chaînes ou utiliser des points-virgules et des virgules ?

Normalement, un bareword n'a pas besoin d'être mis entre guillemets, mais dans la plupart des cas, il devrait probablement l'être (et doit l'être sous "use strict"). Mais une clé de hachage constituée d'un simple mot et l'opérande gauche de l'opérateur "=>" sont traités comme s'ils étaient mis entre guillemets :

Ceci                    est comme ceci
------------            ---------------
$foo{line}              $foo{'line'}
bar => stuff            'bar' => stuff

Le point-virgule final dans un bloc est facultatif, tout comme la virgule finale dans une liste. Un bon style (voir perlstyle) dit de les mettre sauf pour les one-liners :

if ($whoops) { exit 1 }
my @nums = (1, 2, 3);
if ($whoops) {
    exit 1;
}
my @lines = (
    "There Beren came from mountains cold",
    "And lost he wandered under leaves",
);

How do I skip some return values?

Une façon est de traiter les valeurs de retour comme une liste et d'y accéder par index :

$dir = (getpwnam($user))[7];

Une autre façon est d'utiliser undef comme élément du côté gauche :

($dev, $ino, undef, undef, $uid, $gid) = stat($file);

Vous pouvez également utiliser une tranche de liste pour ne sélectionner que les éléments dont vous avez besoin :

($dev, $ino, $uid, $gid) = ( stat($file) )[0,1,4,5];

How do I temporarily block warnings?

Si vous utilisez Perl 5.6.0 ou une version ultérieure, le pragma "use warnings" permet un contrôle précis des avertissements produits. Voir perllexwarn pour plus de détails.

{
    no warnings;          # désactiver temporairement les avertissements
    $x = $y + $z;         # je sais que ceux-ci pourraient être undef
}

De plus, vous pouvez activer et désactiver des catégories d'avertissements. Vous désactivez les catégories que vous souhaitez ignorer et vous pouvez toujours recevoir d'autres catégories d'avertissements. Voir perllexwarn pour les détails complets, y compris les noms des catégories et leur hiérarchie.

{
    no warnings 'uninitialized';
    $x = $y + $z;
}

Si vous avez une version plus ancienne de Perl, la variable $^W (documentée dans perlvar) contrôle les avertissements d'exécution pour un bloc :

{
    local $^W = 0;        # désactiver temporairement les avertissements
    $x = $y + $z;         # je sais que ceux-ci pourraient être undef
}

Notez que, comme toutes les variables de ponctuation, vous ne pouvez pas actuellement utiliser my() sur $^W, seulement local().

Qu'est-ce qu'une extension ?

Une extension est un moyen d'appeler du code C compilé depuis Perl. Lire perlxstut est un bon endroit pour en apprendre davantage sur les extensions.

Why do Perl operators have different precedence than C operators?

En fait, ce n'est pas le cas. Tous les opérateurs C que Perl copie ont la même priorité dans Perl que dans C. Le problème concerne les opérateurs que C n'a pas, en particulier les fonctions qui donnent un contexte de liste à tout ce qui se trouve à leur droite, par exemple print, chmod, exec, etc. Ces fonctions sont appelées « opérateurs de liste » et apparaissent comme tels dans le tableau de priorité de perlop.

Une erreur courante est d'écrire :

unlink $file || die "snafu";

Cela est interprété comme :

unlink ($file || die "snafu");

Pour éviter ce problème, ajoutez des parenthèses supplémentaires ou utilisez l'opérateur « or » à très basse priorité :

(unlink $file) || die "snafu";
unlink $file or die "snafu";

Les opérateurs « English » ("and", "or", "xor" et "not") ont délibérément une priorité inférieure à celle des opérateurs de liste pour des situations comme celle ci-dessus.

Un autre opérateur avec une priorité surprenante est l'exponentiation. Il se lie plus étroitement que le moins unaire, produisant ainsi "-2**2" quatre négatif et non quatre positif. Il est également associatif à droite, ce qui signifie que "2**3**2" est deux élevé à la puissance neuf, et non huit au carré.

Bien qu'il ait la même priorité qu'en C, l'opérateur "?:" de Perl produit une lvalue. Ceci assigne $x soit à $if_true soit à $if_false, selon la véracité de $maybe :

($maybe ? $if_true : $if_false) = $x;

How do I declare/create a structure?

En général, vous ne « déclarez » pas une structure. Utilisez simplement une référence de hachage (probablement anonyme). Voir perlref et perldsc pour les détails. Voici un exemple :

$person = {};                   # nouveau hachage anonyme
$person->{AGE}  = 24;           # définir le champ AGE à 24
$person->{NAME} = "Nat";        # définir le champ NAME à "Nat"

Si vous recherchez quelque chose d'un peu plus rigoureux, essayez perlootut.

Comment créer une classe ?

(contribué par brian d foy)

En Perl, une classe n'est qu'un package, et les méthodes ne sont que des sous-routines. Perl ne va pas plus loin et vous laisse configurer le package comme vous le souhaitez (c'est-à-dire qu'il ne fait rien pour vous).

Vous pouvez utiliser la fonction tainted() du module Scalar::Util, disponible sur CPAN (ou inclus avec Perl depuis la version 5.8.0). Voir aussi « Blanchiment et détection des données taintées » dans perlsec.

Qu'est-ce qu'une closure ?

Les closures sont documentées dans perlref.

Closure est un terme de l'informatique ayant une signification précise mais difficile à expliquer. Généralement, les closures sont implémentées en Perl sous forme de sous-routines anonymes avec des références durables à des variables lexicales en dehors de leurs propres portées. Ces variables lexicales font magiquement référence aux variables qui étaient présentes lorsque la sous-routine a été définie (liaison profonde).

Les closures sont le plus souvent utilisées dans les langages de programmation où le résultat d'une fonction peut être une autre fonction, comme en Perl. Notez que certains langages fournissent des fonctions anonymes mais ne sont pas capables de fournir de vraies closures : par exemple Python 2. Pour plus d'informations sur les closures, consultez n'importe quel manuel de programmation fonctionnelle. Scheme est un langage qui non seulement prend en charge mais encourage les closures.

Voici une fonction classique de génération de fonction qui n'est pas une closure :

sub add_function_generator {
    return sub { shift() + shift() };
}
my $add_sub = add_function_generator();
my $sum = $add_sub->(4,5);                # $sum vaut 9 maintenant.

La sous-routine anonyme renvoyée par add_function_generator() n'est techniquement pas une closure car elle ne fait référence à aucune variable lexicale en dehors de sa propre portée. Utiliser une closure vous donne un *modèle de fonction* avec quelques emplacements de personnalisation laissés vides à remplir plus tard.

Comparez cela avec la fonction make_adder() suivante, dans laquelle la fonction anonyme renvoyée contient une référence à une variable lexicale en dehors de la portée de cette fonction elle-même. Une telle référence nécessite que Perl renvoie une vraie closure, bloquant ainsi pour toujours la valeur que la variable lexicale avait lorsque la fonction a été créée.

sub make_adder {
    my $addpiece = shift;
    return sub { shift() + $addpiece };
}
my $f1 = make_adder(20);
my $f2 = make_adder(555);

Maintenant, $f1->($n) vaut toujours 20 plus la valeur de $n que vous passez, tandis que $f2->($n) vaut toujours 555 plus la valeur de $n que vous passez. Le $addpiece dans la closure reste.

Les closures sont souvent utilisées à des fins moins ésotériques. Par exemple, lorsque vous souhaitez passer un bout de code dans une fonction :

my $line;
timeout( 30, sub { $line = <STDIN> } );

Si le code à exécuter avait été passé sous forme de chaîne, '$line = <STDIN>', il n'y aurait eu aucun moyen pour la fonction hypothétique timeout() d'accéder à la variable lexicale $line dans la portée de son appelant.

Une autre utilisation d'une closure est de rendre une variable *privée* pour une sous-routine nommée, par exemple un compteur qui est initialisé au moment de la création de la sous-routine et qui ne peut être modifié qu'à l'intérieur de la sous-routine. Ceci est parfois utilisé avec un bloc BEGIN dans les fichiers de package pour s'assurer qu'une variable ne sera pas manipulée pendant la durée de vie du package :

BEGIN {
    my $id = 0;
    sub next_id { ++$id }
}

Ceci est discuté plus en détail dans perlsub ; voir l'entrée sur les *Variables Privées Persistantes*.

Qu'est-ce que le suicide de variable et comment puis-je l'éviter ?

Ce problème a été corrigé dans perl 5.004_05, donc l'éviter signifie mettre à jour votre version de perl. ;)

Le suicide de variable se produit lorsque vous perdez (temporairement ou définitivement) la valeur d'une variable. Il est causé par la portée à travers my() et local() interagissant avec soit des closures, soit des variables itératrices foreach() et des arguments de sous-routine aliasés. Il était autrefois facile de perdre involontairement la valeur d'une variable de cette manière, mais c'est maintenant beaucoup plus difficile. Prenez ce code :

my $f = 'foo';
sub T {
    while ($i++ < 3) { my $f = $f; $f .= "bar"; print $f, "\n" }
}
T;
print "Enfin $f\n";

Si vous rencontrez un suicide de variable, ce "my $f" dans la sous-routine ne prend pas une nouvelle copie du $f dont la valeur est 'foo'. La sortie montre qu'à l'intérieur de la sous-routine, la valeur de $f transparaît alors qu'elle ne devrait pas, comme dans cette sortie :

foobar
foobarbar
foobarbarbar
Enfin foo

Le $f auquel "bar" est ajouté trois fois devrait être un nouveau $f. "my $f" devrait créer une nouvelle variable lexicale à chaque passage dans la boucle. La sortie attendue est :

foobar
foobar
foobar
Enfin foo

Comment puis-je passer/retourner une {Fonction, Descripteur de fichier, Tableau, Hash, Méthode, Regex} ?

Vous devez passer des références à ces objets. Voir « Passage par référence » dans perlsub pour cette question particulière, et perlref pour des informations sur les références.

Passage de variables et de fonctions
Les variables et fonctions régulières sont assez faciles à passer : il suffit de passer une référence à une variable ou une fonction existante ou anonyme : 
func( \$some_scalar );
func( \@some_array  );
func( [ 1 .. 10 ]   );
func( \%some_hash   );
func( { this => 10, that => 20 }   );
func( \&some_func   );
func( sub { $_[0] ** $_[1] }   );
Passage de descripteurs de fichiers
À partir de Perl 5.6, vous pouvez représenter les descripteurs de fichiers par des variables scalaires que vous traitez comme n'importe quel autre scalaire. 
open my $fh, $filename or die "Impossible d'ouvrir $filename ! $!";
func( $fh );
sub func {
    my $passed_fh = shift;
    my $line = <$passed_fh>;
}

Avant Perl 5.6, vous deviez utiliser les notations *FH ou "\*FH". Ce sont des "typeglobs" - voir « Typeglobs et descripteurs de fichiers » dans perldata et surtout « Passage par référence » dans perlsub pour plus d'informations.

Passage de regex
Voici un exemple de la manière de passer une chaîne de caractères et une expression régulière pour la faire correspondre. Vous construisez le motif avec l'opérateur "qr//" : 
sub compare {
    my ($val1, $regex) = @_;
    my $retval = $val1 =~ /$regex/;
    return $retval;
}
$match = compare("vieux McDonald", qr/d.*D/i);
Passage de méthodes
Pour passer une méthode d'objet dans une sous-routine, vous pouvez faire ceci : 
call_a_lot(10, $some_obj, "methname")
sub call_a_lot {
    my ($count, $widget, $trick) = @_;
    for (my $i = 0; $i < $count; $i++) {
        $widget->$trick();
    }
}

Ou, vous pouvez utiliser une closure pour regrouper l'objet, l'appel de sa méthode et les arguments :

my $whatnot = sub { $some_obj->obfuscate(@args) };
func($whatnot);
sub func {
    my $code = shift;
    &$code();
}

Vous pourriez également explorer la méthode can() de la classe UNIVERSAL (partie de la distribution standard de perl).

Comment créer une variable statique ?

(contribué par brian d foy)

En Perl 5.10, déclarez la variable avec "state". La déclaration "state" crée la variable lexicale qui persiste entre les appels à la sous-routine :

sub counter { state $count = 1; $count++ }

Vous pouvez simuler une variable statique en utilisant une variable lexicale qui sort de sa portée. Dans cet exemple, vous définissez la sous-routine "counter", et elle utilise la variable lexicale $count. Comme vous encapsulez cela dans un bloc BEGIN, $count est défini au moment de la compilation, mais sort également de sa portée à la fin du bloc BEGIN. Le bloc BEGIN garantit également que la sous-routine et la valeur qu'elle utilise sont définies au moment de la compilation, de sorte que la sous-routine est prête à être utilisée comme toute autre sous-routine, et vous pouvez placer ce code au même endroit que d'autres sous-routines dans le texte du programme (c'est-à-dire à la fin du code, généralement). La sous-routine "counter" a toujours une référence aux données, et est la seule façon dont vous pouvez accéder à la valeur (et chaque fois que vous le faites,

Comment la portée est-elle gérée par défaut ?

Les variables déclarées avec my sont dites à portée lexicale. Elles ne sont accessibles que dans le bloc dans lequel elles sont déclarées et dans les blocs imbriqués. Les variables déclarées avec our sont en fait des variables de paquetage (globales) qui sont visibles depuis n'importe quel endroit de votre code. Les variables de paquetage sont également visibles par les sous-routines appelées depuis d'autres sous-routines. Vous incrémentez la valeur). Les données dans le bloc de mémoire défini par $count sont privées à "counter".

BEGIN {
    my $count = 1;
    sub counter { $count++ }
}
my $start = counter();
.... # code qui appelle counter();
my $end = counter();

Dans l'exemple précédent, vous avez créé une variable privée à la fonction car une seule fonction se souvenait de sa référence. Vous pouvez définir plusieurs fonctions tant que la variable est dans la portée, et chaque fonction peut partager la variable "privée". Ce n'est pas vraiment "statique" car vous pouvez y accéder en dehors de la fonction tant que la variable lexicale est dans la portée, et même créer des références vers elle. Dans cet exemple, "increment_count" et "return_count" partagent la variable. Une fonction ajoute à la valeur et l'autre renvoie simplement la valeur. Elles peuvent toutes deux accéder à $count, et comme il est sorti de la portée, il n'y a aucun autre moyen d'y accéder.

BEGIN {
    my $count = 1;
    sub increment_count { $count++ }
    sub return_count    { $count }
}

Pour déclarer une variable privée au fichier, vous utilisez toujours une variable lexicale. Un fichier est aussi une portée, donc une variable lexicale définie dans le fichier ne peut pas être vue depuis un autre fichier.

Voir "Persistent Private Variables" dans perlsub pour plus d'informations. La discussion sur les fermetures dans perlref peut vous aider même si nous n'avons pas utilisé de sous-routines anonymes dans cette réponse. Voir "Persistent Private Variables" dans perlsub pour les détails.

Quelle est la différence entre la portée dynamique et lexicale (statique) ? Entre local() et my() ?

local($x) sauvegarde l'ancienne valeur de la variable globale $x et assigne une nouvelle valeur pour la durée de la sous-routine *qui est visible dans d'autres fonctions appelées depuis cette sous-routine*. Ceci est fait à l'exécution, donc on appelle cela la portée dynamique. local() affecte toujours les variables globales, également appelées variables de paquetage ou variables dynamiques.

my($x) crée une nouvelle variable qui n'est visible que dans la sous-routine actuelle. Ceci est fait à la compilation, donc on appelle cela la portée lexicale ou statique. my() affecte toujours les variables privées, également appelées variables lexicales ou (incorrectement) variables à portée (statique).

Par exemple :

sub visible {
    print "var a la valeur $var\n";
}
sub dynamic {
    local $var = 'local';    # nouvelle valeur temporaire pour la variable
    visible();              #   toujours globale appelée $var
}
sub lexical {
    my $var = 'private';    # nouvelle variable privée, $var
    visible();              # (invisible en dehors de la portée de la sub)
}
$var = 'global';
visible();              # affiche global
dynamic();              # affiche local
lexical();              # affiche global

Remarquez comment à aucun moment la valeur "private" n'est affichée. C'est parce que $var n'a cette valeur qu'à l'intérieur du bloc de la fonction lexical(), et qu'elle est cachée de la sous-routine appelée.

En résumé, local() ne crée pas ce que vous considérez comme des variables privées et locales. Il donne à une variable globale une valeur temporaire. my() est ce que vous recherchez si vous voulez des variables privées.

Voir "Private Variables via my()" dans perlsub et "Temporary Values via local()" dans perlsub pour des détails exquis.

Comment puis-je accéder à une variable dynamique alors qu'une variable lexicale de même nom est dans la portée ?

Si vous connaissez votre paquetage, vous pouvez le mentionner explicitement, comme dans $Some_Pack::var. Notez que la notation $::var n'est pas le $var dynamique du paquetage actuel, mais plutôt celui du paquetage "main", comme si vous aviez écrit $main::var.

use vars '$var';
local $var = "global";
my    $var = "lexical";
print "lexical est $var\n";
print "global  est $main::var\n";

Alternativement, vous pouvez utiliser la directive de compilation our() pour amener une variable dynamique dans la portée lexicale actuelle.

require 5.006; # our() n'existait pas avant 5.6
use vars '$var';
local $var = "global";
my $var    = "lexical";
print "lexical est $var\n";
{
    our $var;
    print "global  est $var\n";
}

Quelle est la différence entre la liaison profonde et la liaison superficielle ?

En liaison profonde, les variables lexicales mentionnées dans les sous-routines anonymes sont les mêmes que celles qui étaient dans la portée lorsque la sous-routine a été créée. En liaison superficielle, ce sont les variables avec les mêmes noms qui se trouvent dans la portée lorsque la sous-routine est appelée. Perl utilise toujours la liaison profonde des variables lexicales (c'est-à-dire celles créées avec my()). Cependant, les variables dynamiques (alias globales, locales ou de paquetage) sont effectivement liées superficiellement. Considérez ceci comme une raison de plus de ne pas les utiliser. Voir la réponse à "Qu'est-ce qu'une fermeture ?".

Pourquoi "my($foo) = <$fh>;" ne fonctionne-t-il pas correctement ?

my() et local() donnent un contexte de liste à la partie droite de "=". L'opération de lecture <$fh>, comme tant d'autres fonctions et opérateurs de Perl, peut déterminer dans quel contexte elle a été appelée et se comporter de manière appropriée. En général, la fonction scalar() peut aider. Cette fonction ne fait rien aux données elles-mêmes (contrairement à la croyance populaire) mais demande plutôt à son argument de se comporter selon sa manière scalaire. Si cette fonction n'a pas de comportement scalaire défini, cela ne vous aide bien sûr pas (comme avec sort()).

Pour forcer le contexte scalaire dans ce cas particulier, vous n'avez qu'à omettre les parenthèses :

local($foo) = <$fh>;        # FAUX
local($foo) = scalar(<$fh>);   # ok
local $foo  = <$fh>;        # correct

Vous devriez probablement utiliser des variables lexicales de toute façon, bien que le problème soit le même ici :

my($foo) = <$fh>;    # FAUX
my $foo  = <$fh>;    # correct

Comment puis-je redéfinir une fonction, un opérateur, ou une méthode intégrée ?

Pourquoi voulez-vous faire ça ? :-)

Si vous voulez remplacer une fonction prédéfinie, comme open(), alors vous devrez importer la nouvelle définition depuis un module différent. Voir "Overriding Built-in Functions" dans perlsub.

Si vous voulez surcharger un opérateur Perl, comme "+" ou "**", alors vous voudrez utiliser le pragma "use overload", documenté dans overload.

Si vous parlez d'obscurcir les appels de méthodes des classes parentes, voir "Overriding methods and method resolution" dans perlootut.

Quelle est la différence entre appeler une fonction comme &foo et foo() ?

(contribué par brian d foy)

Appeler une sous-routine comme &foo sans parenthèses finales ignore le prototype de "foo" et lui passe la valeur actuelle de la liste d'arguments, @_. Voici un exemple ; la sous-routine "bar" appelle &foo, qui affiche sa liste d'arguments :

sub foo { print "Args in foo are: @_\n"; }
sub bar { &foo; }
bar( "a", "b", "c" );

Lorsque vous appelez "bar" avec des arguments, vous voyez que "foo" a reçu le même @_ :

Args in foo are: a b c

Appeler la sous-routine avec des parenthèses finales, avec ou sans arguments, n'utilise pas le @_ actuel. Changer l'exemple pour mettre des parenthèses après l'appel à "foo" modifie le programme :

sub foo { print "Args in foo are: @_\n"; }
sub bar { &foo(); }
bar( "a", "b", "c" );

Maintenant, la sortie montre que "foo" ne reçoit pas le @_ de son appelant.

Args in foo are:

Cependant, utiliser "&" dans l'appel remplace toujours le prototype de "foo" s'il est présent :

sub foo ($$$) { print "Args in foo are: @_\n"; }
sub bar_1 { &foo; }
sub bar_2 { &foo(); }
sub bar_3 { foo( $_[0], $_[1], $_[2] ); }
# sub bar_4 { foo(); }
# bar_4 ne compile pas : "Not enough arguments for main::foo at ..."
bar_1( "a", "b", "c" );
# Args in foo are: a b c
bar_2( "a", "b", "c" );
# Args in foo are:
bar_3( "a", "b", "c" );
# Args in foo are: a b c

L'utilisation principale de la fonctionnalité de passage de @_ est d'écrire des sous-routines dont le but principal est d'appeler d'autres sous-routines pour vous. Pour plus de détails, voir perlsub.

Comment puis-je créer une instruction switch ou case ?

Il existe une instruction given/when en Perl, mais elle est expérimentale et sera supprimée dans Perl 5.42. Voir perlsyn pour plus de détails.

La réponse générale est d'utiliser un module CPAN tel que Switch::Plain :

use Switch::Plain;
sswitch($variable_contenant_une_chaîne) {
    case 'premier': { }
    case 'deuxième': { }
    default: { }
}

ou pour des comparaisons plus complexes, "if-elsif-else" :

for ($variable_à_tester) {
    if    (/pat1/)  { }     # faire quelque chose
    elsif (/pat2/)  { }     # faire autre chose
    elsif (/pat3/)  { }     # faire autre chose
    else            { }     # par défaut
}

Voici un exemple simple de switch basé sur la correspondance de modèles, aligné de manière à ressembler davantage à une instruction switch. Nous allons faire une condition multiple basée sur le type de référence stocké dans $whatchamacallit :

SWITCH: for (ref $whatchamacallit) {
    /^$/           && die "pas une référence";
    /SCALAR/       && do {
                    print_scalar($$ref);
dernier SWITCH; }; /ARRAY/ && do { print_array(@$ref); dernier SWITCH; }; /HASH/ && do { print_hash(%$ref); dernier SWITCH; }; /CODE/ && do { warn "impossible d'imprimer la référence de fonction"; dernier SWITCH; }; # DÉFAUT warn "Type défini par l'utilisateur ignoré"; }

Voir perlsyn pour d'autres exemples dans ce style.

Parfois, il faut changer la position de la constante et de la variable. Par exemple, disons que vous vouliez tester parmi plusieurs réponses possibles, mais de manière insensible à la casse et autorisant les abréviations. Vous pouvez utiliser la technique suivante si toutes les chaînes commencent par des caractères différents ou si vous voulez organiser les correspondances de manière à ce que l'une ait la priorité sur une autre, comme "SEND" a la priorité sur "STOP" ici :

chomp($reponse = <>);
if    ("SEND"  =~ /^\Q$reponse/i) { print "L'action est envoyer\n"  }
elsif ("STOP"  =~ /^\Q$reponse/i) { print "L'action est arrêter\n"  }
elsif ("ABORT" =~ /^\Q$reponse/i) { print "L'action est annuler\n" }
elsif ("LIST"  =~ /^\Q$reponse/i) { print "L'action est lister\n"  }
elsif ("EDIT"  =~ /^\Q$reponse/i) { print "L'action est modifier\n"  }

Une approche totalement différente consiste à créer une table de références de fonctions.

my %commandes = (
    "heureux" => \&joie,
    "triste"   => \&maussade,
    "fini"  => sub { die "À plus !" },
    "en colère"   => \&colère,
);
print "Comment allez-vous ? ";
chomp($chaine = <STDIN>);
if ($commandes{$chaine}) {
    $commandes{$chaine}->();
} else {
    print "Commande inconnue : $chaine\n";
}

À partir de Perl 5.8, un module de filtre source, "Switch", peut également être utilisé pour obtenir switch et case. Son utilisation est maintenant déconseillée, car il n'est pas entièrement compatible avec le switch natif de Perl 5.10, et parce que, étant implémenté comme un filtre source, il ne fonctionne pas toujours comme prévu lorsque la syntaxe est complexe.

Comment puis-je intercepter les accès à des variables, fonctions ou méthodes indéfinies ?

La méthode AUTOLOAD, discutée dans "Autoloading" dans perlsub, vous permet de capturer les appels à des fonctions et méthodes indéfinies.

En ce qui concerne les variables indéfinies qui déclencheraient un avertissement sous "use warnings", vous pouvez promouvoir l'avertissement en erreur.

use warnings FATAL => qw(uninitialized);

Pourquoi une méthode incluse dans ce même fichier ne peut-elle pas être trouvée ?

Quelques raisons possibles : votre héritage est confus, vous avez fait une faute de frappe dans le nom de la méthode, ou l'objet est du mauvais type. Consultez perlootut pour plus de détails sur l'un des cas ci-dessus. Vous pouvez également utiliser "print ref($objet)" pour savoir dans quelle classe $objet a été béni.

Une autre raison possible de problèmes est que vous avez utilisé la syntaxe d'objet indirect (par exemple, "trouver Guru "Samy"") sur un nom de classe avant que Perl n'ait vu qu'un tel paquet existe. Il est plus sage de s'assurer que tous vos paquets sont définis avant de commencer à les utiliser, ce qui sera géré si vous utilisez l'instruction "use" au lieu de "require". Sinon, assurez-vous d'utiliser la notation fléchée (par exemple, "Guru->find("Samy")") à la place. La notation d'objet est expliquée dans perlobj.

Assurez-vous de lire sur la création de modules dans perlmod et les dangers des objets indirects dans "Method Invocation" dans perlobj.

Comment puis-je connaître mon package actuel ou celui qui m'appelle ?

(contribué par brian d foy)

Pour connaître le package dans lequel vous vous trouvez actuellement, utilisez la littérale spéciale "__PACKAGE__", comme documenté dans perldata. Vous ne pouvez utiliser les littérales spéciales qu'en tant que jetons distincts, vous ne pouvez donc pas les interpoler dans des chaînes comme vous pouvez le faire avec des variables :

my $package_actuel = __PACKAGE__;
print "Je suis dans le package $package_actuel\n";

Si vous voulez connaître le package qui appelle votre code, peut-être pour fournir de meilleurs diagnostics comme le fait Carp, utilisez la fonction intégrée "caller" :

sub foo {
    my @args = ...;
    my( $package, $filename, $line ) = caller;
    print "J'ai été appelé depuis le package $package\n";
};

Par défaut, votre programme démarre dans le package "main", vous serez donc toujours dans un package.

Ceci est différent de la recherche du package dans lequel un objet est béni, qui peut ne pas être le package actuel. Pour cela, utilisez "blessed" de Scalar::Util, qui fait partie de la bibliothèque standard depuis Perl 5.8 :

use Scalar::Util qw(blessed);
my $package_objet = blessed( $objet );

La plupart du temps, vous ne devriez pas vous soucier du package dans lequel un objet est béni, cependant, tant qu'il prétend hériter de cette classe :

my $est_bon_type = eval { $objet->isa( $package ) }; # vrai ou faux

Et, avec Perl 5.10 et plus, vous n'avez pas à vérifier l'héritage pour voir si l'objet peut gérer un rôle. Pour cela, vous pouvez utiliser "DOES", qui vient de "UNIVERSAL" :

my $type_le_fait = eval { $objet->DOES( $role ) }; # vrai ou faux

Vous pouvez remplacer en toute sécurité "isa" par "DOES" (bien que l'inverse ne soit pas vrai).

Comment puis-je commenter un grand bloc de code Perl ?

(contribué par brian d foy)

La méthode rapide et sale pour commenter plus d'une ligne de Perl est de les entourer de directives Pod. Vous devez placer ces directives au début de la ligne et à un endroit où Perl attend une nouvelle instruction (donc pas au milieu d'instructions comme les commentaires "#"). Vous terminez le commentaire avec "=cut", terminant la section Pod :

=pod
my $objet = PasPossible->new();
fonction_ignoree();
$pas_assigne = 37;
=cut

La méthode rapide et sale ne fonctionne bien que lorsque vous n'avez pas l'intention de laisser le code commenté dans la source. Si un analyseur Pod arrive, votre commentaire multiligne apparaîtra dans la traduction Pod. Une meilleure méthode le masque également aux analyseurs Pod.

La directive "=begin" peut marquer une section à des fins particulières. Si l'analyseur Pod ne veut pas la gérer, il l'ignore simplement. Étiquetez les commentaires avec "comment". Terminez le commentaire en utilisant "=end" avec la même étiquette. Vous avez toujours besoin de "=cut" pour revenir au code Perl depuis le commentaire Pod :

=begin comment
my $objet = PasPossible->new();
fonction_ignoree();
$pas_assigne = 37;
=end comment
=cut

Pour plus d'informations sur Pod, consultez perlpod et perlpodspec.

Comment puis-je vider un package ?

Utilisez ce code, fourni par Mark-Jason Dominus :

sub vider_package {
    no strict 'refs';
    my $pack = shift;
    die "Ne devrait pas supprimer le package principal"
        if $pack eq "" || $pack eq "main";
    my $stash = *{$pack . '::'}{HASH};
    my $nom;
    foreach $nom (keys %$stash) {
        my $nom_complet = $pack . '::' . $nom;
        # Supprimer tout ce qui porte ce nom.
        undef $$nom_complet;
        undef @$nom_complet;
        undef %$nom_complet;
        undef &$nom_complet;
        undef *$nom_complet;
    }
}

Ou, si vous utilisez une version récente de Perl, vous pouvez simplement utiliser la fonction Symbol::delete_package() à la place.

Comment puis-je utiliser une variable comme nom de variable ?

Les débutants pensent souvent qu'ils veulent qu'une variable contienne le nom d'une variable.

$fred    = 23;
$nomvar = "fred";
++$$nomvar;         # $fred vaut maintenant 24

Cela fonctionne *parfois*, mais c'est une très mauvaise idée pour deux raisons.

La première raison est que cette technique ne fonctionne *que sur les variables globales*. Cela signifie que si $fred est une variable lexicale créée avec my() dans l'exemple ci-dessus, le code ne fonctionnerait pas du tout : vous accéderiez accidentellement au global et ignoreriez complètement le lexical privé. Les variables globales sont mauvaises car elles peuvent facilement entrer en collision accidentellement et, en général, rendre le code non évolutif et confus.

Les références symboliques sont interdites sous le pragma "use strict". Ce ne sont pas de vraies références et par conséquent elles ne sont pas comptées de références ni collectées automatiquement.

L'autre raison pour laquelle utiliser une variable pour contenir le nom d'une autre variable est une mauvaise idée est que la question découle souvent d'un manque de compréhension des structures de données de Perl, en particulier des tables de hachage. En utilisant des références symboliques, vous utilisez simplement la table des symboles du paquet (comme %main::) au lieu d'une table de hachage définie par l'utilisateur. La solution est d'utiliser votre propre table de hachage ou une vraie référence à la place.

$VAR_UTILISATEUR{"fred"} = 23;
my $nomvar = "fred";
$VAR_UTILISATEUR{$nomvar}++;  # pas $$nomvar++

Là, nous utilisons la table de hachage %VAR_UTILISATEUR au lieu de références symboliques. Parfois, cela se produit lors de la lecture de chaînes auprès de l'utilisateur avec des références de variables et que l'on veut les développer aux valeurs des variables de votre programme Perl. C'est également une mauvaise idée car cela mélange l'espace de noms adressable par le programme et celui adressable par l'utilisateur. Au lieu de lire une chaîne et de l'étendre au contenu réel des variables de votre propre programme :

$str = 'ceci contient un $fred et un $barney';
$str =~ s/(\$\w+)/$1/eeg;          # double eval nécessaire

Pourquoi les références symboliques sont-elles mauvaises?

Les références symboliques sont un vestige de l'ère des premiers langages de script où les structures de données n'étaient pas aussi sophistiquées qu'aujourd'hui. L'utilisation de références symboliques dans Perl peut être source de confusion et peut entraîner des erreurs difficiles à diagnostiquer.

Par exemple, supposons que vous ayez une table de hachage %USER_VARS qui contient les valeurs pour des variables nommées. Vous pourriez être tenté d'utiliser une expression régulière pour remplacer les variables de chaîne par leurs valeurs.

$str = 'this has a $fred and a $barney in it';
$str =~ s/\$(\w+)/$USER_VARS{$1}/e;   # DEPRECATED AND DANGEROUS

La raison pour laquelle cela est dangereux est que l'expression régulière peut remplacer des chaînes qui ne sont pas censées être interprétées comme des noms de variables. De plus, cela utilise l'indicateur /e qui évalue le côté droit de la substitution en tant que code Perl, ce qui peut introduire des failles de sécurité si la chaîne provient d'une entrée utilisateur.

Une approche bien meilleure consiste à utiliser l'expression régulière pour extraire les noms des variables, puis à utiliser ces noms pour accéder aux valeurs dans votre table de hachage %USER_VARS:

$str =~ s/\$(\w+)/$USER_VARS{$1}/g;   # pas de /e ici du tout

C'est plus rapide, plus propre et plus sûr que l'approche précédente. Bien sûr, vous n'avez pas besoin d'utiliser le signe dollar. Vous pourriez utiliser votre propre schéma pour rendre cela moins déroutant, comme des symboles pour cent entre crochets, etc.

$str = 'this has a %fred% and %barney% in it';
$str =~ s/%(\w+)%/$USER_VARS{$1}/g;   # pas de /e ici du tout

Une autre raison pour laquelle les gens pensent parfois vouloir qu'une variable contienne le nom d'une autre variable est qu'ils ne savent pas comment construire des structures de données appropriées à l'aide de tables de hachage. Par exemple, supposons qu'ils veuillent deux tables de hachage dans leur programme : %fred et %barney, et qu'ils veuillent utiliser une autre variable scalaire pour y faire référence par nom.

$name = "fred";
$$name{WIFE} = "wilma";     # définit %fred
$name = "barney";
$$name{WIFE} = "betty";    # définit %barney

Ceci est toujours une référence symbolique, et est toujours plombée par les problèmes énumérés ci-dessus. Il serait bien meilleur d'écrire :

$folks{"fred"}{WIFE}   = "wilma";
$folks{"barney"}{WIFE} = "betty";

Et d'utiliser simplement une table de hachage à plusieurs niveaux dès le départ.

Les seuls moments où vous devez absolument utiliser des références symboliques sont lorsque vous devez réellement faire référence à la table des symboles. Cela peut être parce que c'est quelque chose auquel on ne peut pas faire une vraie référence, comme un nom de format. Le faire peut également être important pour les appels de méthodes, car ceux-ci passent toujours par la table des symboles pour la résolution.

Dans ces cas, vous désactiveriez "strict 'refs'" temporairement afin de pouvoir jouer avec la table des symboles. Par exemple :

@colors = qw(red blue green yellow orange purple violet);
for my $name (@colors) {
    no strict 'refs';  # renonce pour le bloc
    *$name = sub { "<FONT COLOR='$name'>@_</FONT>" };
}

Toutes ces fonctions (red(), blue(), green(), etc.) semblent être distinctes, mais le vrai code dans la fermeture a en fait été compilé une seule fois.

Donc, parfois, vous pourriez vouloir utiliser des références symboliques pour manipuler directement la table des symboles. Cela n'a pas d'importance pour les formats, les descripteurs et les sous-routines, car ils sont toujours globaux - vous ne pouvez pas utiliser my() dessus. Pour les scalaires, les tableaux et les tables de hachage, cependant - et généralement pour les sous-routines - vous ne voudrez probablement utiliser que des références fortes.

Qu'est-ce que "mauvais interpréteur" signifie?

(contribué par brian d foy)

Le message "mauvais interpréteur" vient du shell, pas de perl. Le message réel peut varier en fonction de votre plateforme, de votre shell et des paramètres régionaux.

Si vous voyez "mauvais interpréteur - fichier ou répertoire inexistant", la première ligne de votre script perl (la ligne "shebang") ne contient pas le bon chemin vers perl (ou tout autre programme capable d'exécuter des scripts). Parfois, cela se produit lorsque vous déplacez le script d'une machine à une autre et que chaque machine a un chemin différent vers perl - /usr/bin/perl versus /usr/local/bin/perl, par exemple. Cela peut également indiquer que la machine source a des terminateurs de ligne CRLF et que la machine de destination n'a que LF : le shell essaie de trouver /usr/bin/perl<CR>, mais ne le trouve pas.

Si vous voyez "mauvais interpréteur : Permission refusée", vous devez rendre votre script exécutable.

Dans les deux cas, vous devriez toujours pouvoir exécuter les scripts en spécifiant explicitement perl :

% perl script.pl

Si vous obtenez un message comme "perl : commande introuvable", perl n'est pas dans votre PATH, ce qui pourrait également signifier que l'emplacement de perl n'est pas celui que vous attendez, vous devez donc ajuster votre ligne shebang.

Dois-je recompiler les modules XS lorsqu'il y a un changement dans la bibliothèque C?

(contribué par Alex Beamish)

Si la nouvelle version de la bibliothèque C est compatible ABI (c'est-à-dire compatible avec l'Interface Binaire d'Application) avec la version dont vous faites la mise à niveau, et si la version de la bibliothèque partagée n'a pas changé, aucune recompilation ne devrait être nécessaire.
