PERLOS2(1perl) Guide de référence du programmeur Perl PERLOS2(1perl)

NOM

perlos2 - Perl sous OS/2, DOS, Win0.3*, Win0.95 et WinNT.

SYNOPIS

On peut lire ce document dans les formats suivants :

man perlos2
view perl perlos2
explorer perlos2.html
info perlos2

pour n'en citer que quelques-uns (tous peuvent ne pas être disponibles simultanément), ou il peut être lu tel quel : soit comme README.os2, soit comme pod/perlos2.pod.

Pour lire la version .INF de la documentation (très recommandée) en dehors d'OS/2, il faut un lecteur d'IBM (peut-être disponible sur les sites ftp d'IBM (?) (URL quelqu'un ?)) ou fourni avec PC DOS 7.0 et IBM Visual Age C++ 3.5.

Une copie d'un visualiseur Win* est contenue dans le paquet "Just add OS/2 Warp"

ftp://ftp.software.ibm.com/ps/products/os2/tools/jaow/jaow.zip

dans ?:\JUST_ADD\view.exe. Cela donne également accès aux documents .INF d'EMX (la forme texte est disponible dans /emx/doc dans la distribution d'EMX). Il existe aussi un autre visualiseur nommé xview.

Notez que si vous avez lynx.exe ou netscape.exe installés, vous pouvez suivre les liens WWW de ce document au format .INF. Si vous avez les documents EMX installés correctement, vous pouvez suivre les liens de bibliothèque (vous devez avoir "view emxbook" qui fonctionne en configurant la variable d'environnement "EMXBOOK" comme décrit dans la documentation EMX).

DESCRIPTION

Cible

L'objectif est de faire d'OS/2 l'une des plateformes les mieux supportées pour utiliser/construire/développer Perl et des applications Perl, ainsi que de faire de Perl le meilleur langage à utiliser sous OS/2. L'objectif secondaire est d'essayer de faire fonctionner cela aussi sous DOS et Win* (mais pas trop difficilement).

L'état actuel est assez proche de cet objectif. Limitations connues :

  • Certains programmes *nix utilisent beaucoup fork() ; avec les saveurs de perl les plus utiles pour OS/2 (plusieurs sont construites simultanément), cela est supporté ; mais certaines saveurs ne le supportent pas (par exemple, lorsque Perl est appelé depuis REXX). L'utilisation de fork() après use d'extensions chargeables dynamiquement ne fonctionnera pas avec les versions très anciennes d'EMX.
  • Vous avez besoin d'un exécutable perl séparé perl__.exe (voir "perl__.exe") si vous souhaitez utiliser du code PM dans votre application (comme le font les modules Perl/Tk ou OpenGL Perl) sans avoir de fenêtre en mode texte présente.

    Bien qu'il soit également possible d'utiliser le perl.exe standard depuis une fenêtre en mode texte, j'ai vu des cas où cela dégrade la stabilité du système. L'utilisation de perl__.exe évite une telle dégradation.

  • Il n'y a pas de moyen simple d'accéder aux objets WPS. La seule façon que je connaisse est via les extensions "OS2::REXX" et "SOM" (voir OS2::REXX, SOM). Cependant, nous n'avons pas accès aux méthodes pratiques d'Object-REXX. (Est-ce possible du tout ? Je ne connais aucune API Object-REXX.) L'extension "SOM" (actuellement en alpha-text) pourrait éventuellement supprimer cette lacune ; cependant, du fait que DII n'est pas supporté par le module "SOM", l'utilisation de "SOM" n'est pas aussi pratique qu'on le souhaiterait.

Veuillez garder cette liste à jour en m'informant d'autres éléments.

Autres OS

Étant donné que le portage Perl pour OS/2 utilise un environnement EMX remarquable, il peut s'exécuter (et construire des extensions, et - possiblement - être construit lui-même) sous tout environnement capable d'exécuter EMX. La liste actuelle est DOS, DOS-dans-OS/2, Win0.3*, Win0.95 et WinNT. Parmi les nombreuses saveurs de perl, une seule fonctionne, voir "perl_.exe".

Notez que toutes les fonctionnalités de Perl ne sont pas disponibles sous ces environnements. Cela dépend des fonctionnalités que l'*extender* - très probablement RSX - a décidé d'implémenter.

Cf. "Prérequis".

Prérequis

EMX
L'environnement d'exécution EMX est requis (peut être substitué par RSX). Notez qu'il est possible de faire fonctionner perl_.exe sous DOS sans aucun support externe en liant emx.exe/rsx.exe à celui-ci, voir emxbind(1). Notez que sous DOS, pour de meilleurs résultats, il faut utiliser l'environnement d'exécution RSX, qui a beaucoup plus de fonctions qui fonctionnent (comme "fork", "popen", etc.). En fait, RSX est requis s'il n'y a pas de VCPI présent. Notez que RSX nécessite DPMI. De nombreuses implémentations de DPMI sont connues pour être très boguées, attention !

Seul le dernier environnement d'exécution est supporté, actuellement "0.9d fix 03". Perl peut fonctionner sous des versions antérieures d'EMX, mais cela n'a pas été testé.

On peut obtenir différentes parties d'EMX, par exemple

ftp://crydee.sai.msu.ru/pub/comp/os/os2/leo/gnu/emx+gcc/
http://hobbes.nmsu.edu/h-browse.php?dir=/pub/os2/dev/emx/v0.9d/

Le composant d'exécution devrait s'appeler emxrt.zip.

NOTE. Lors de l'utilisation d'emx.exe/rsx.exe, il suffit de les avoir dans votre chemin. Il n'est pas nécessaire de les spécifier explicitement (bien que

emx perl_.exe -de 0

fonctionnera aussi.)

RSX
Pour exécuter Perl sur des plateformes DPMI, il faut l'environnement d'exécution RSX. Ceci est nécessaire sous DOS-dans-OS/2, Win0.3*, Win0.95 et WinNT (voir "Autres OSes"). RSX ne fonctionnera pas uniquement avec VCPI, comme le ferait EMX, il nécessite DMPI.

En ayant RSX et le dernier sh.exe, on obtient un environnement *nix-like entièrement fonctionnel sous DOS, par exemple, "fork", `` et le pipe "open" fonctionnent. En fait, MakeMaker fonctionne (pour la construction statique), donc on peut avoir un environnement de développement Perl sous DOS.

On peut obtenir RSX, par exemple

http://cd.textfiles.com/hobbesos29804/disk1/EMX09C/
ftp://crydee.sai.msu.ru/pub/comp/os/os2/leo/gnu/emx+gcc/contrib/

Contactez l'auteur à l'adresse "rainer@mathematik.uni-bielefeld.de".

Le dernier sh.exe avec des hooks DOS est disponible dans

http://www.ilyaz.org/software/os2/

sous le nom de sh_dos.zip ou sous des noms similaires commençant par "sh", "pdksh", etc.

HPFS
Perl ne se soucie pas des systèmes de fichiers, mais la bibliothèque perl contient de nombreux fichiers avec de longs noms, donc pour l'installer intact, il faut un système de fichiers qui supporte les longs noms de fichiers.

Notez que si vous ne prévoyez pas de construire Perl lui-même, il peut être possible de tromper EMX pour qu'il tronque les noms de fichiers. Ce n'est pas supporté, lisez la documentation EMX pour savoir comment faire.

pdksh
Pour démarrer des programmes externes avec des lignes de commande compliquées (comme avec des pipes entre eux, et/ou des guillemets pour les arguments), Perl utilise un shell externe. Avec le portage EMX, un tel shell devrait s'appeler sh.exe, et être situé soit dans des emplacements codés en dur lors de la compilation (généralement F:/bin), soit dans un emplacement configurable (voir ""PERL_SH_DIR"").

Pour de meilleurs résultats, utilisez pdksh d'EMX. Le binaire standard (5.2.14 ou plus récent) s'exécute également sous DOS (avec "RSX"), voir

http://www.ilyaz.org/software/os2/

Démarrage des programmes Perl sous OS/2 (et DOS et...)

Démarrez votre programme Perl foo.pl avec les arguments "arg1 arg2 arg3" de la même manière que sur toute autre plateforme, en utilisant

perl foo.pl arg1 arg2 arg3

Si vous souhaitez spécifier des options Perl "-mes_opts" pour Perl lui-même (par opposition à votre programme), utilisez

perl -mes_opts foo.pl arg1 arg2 arg3

Alternativement, si vous utilisez un shell de type OS/2, comme CMD ou 4os2, placez ce qui suit au début de votre script Perl :

extproc perl -S -mes_opts

renommez votre programme en foo.

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

cmd, et démarrez-le en tapant

foo arg1 arg2 arg3

Notez qu'en raison de limitations stupides d'OS/2, le chemin complet du script perl n'est pas disponible lorsque vous utilisez "extproc". Par conséquent, vous êtes obligé d'utiliser le commutateur perl "-S", et votre script doit être sur le "PATH". Comme avantage, si vous connaissez le chemin complet de votre script, vous pouvez toujours le démarrer avec

perl ../../blah/foo.cmd arg1 arg2 arg3

(notez que l'argument "-my_opts" est géré par la ligne "extproc" dans votre script, voir "extproc" sur la première ligne).

Pour comprendre ce que fait cette magie, lisez la documentation perl sur le commutateur "-S" - voir perlrun, et cmdref sur "extproc":

view perl perlrun
man perlrun
view cmdref extproc
help extproc

ou toute autre méthode que vous préférez.

Il existe également des possibilités infinies d'utiliser les extensions exécutables de 4os2, les associations de WPS, et ainsi de suite... Cependant, si vous utilisez un shell *nixish (comme sh.exe fourni dans la distribution binaire), vous devez suivre la syntaxe spécifiée dans "Command Switches" de perlrun.

Notez que le commutateur -S prend également en charge les scripts avec des extensions supplémentaires .cmd, .btm, .bat, .pl.

Démarrage des programmes OS/2 (et DOS) sous Perl

C'est à cela que servent system() (voir "system" dans perlfunc), `` (voir "I/O Operators" dans perlop), et pipe ouverte (voir "open" dans perlfunc). (Évitez exec() (voir "exec" dans perlfunc) à moins que vous ne sachiez ce que vous faites).

Notez cependant que pour utiliser certains de ces opérateurs, vous devez avoir installé un shell de syntaxe sh (voir "Pdksh", "Frequently asked questions"), et perl doit pouvoir le trouver (voir ""PERL_SH_DIR"").

Les cas où le shell est utilisé sont les suivants :

1.
system() à un argument (voir "system" dans perlfunc), exec() (voir "exec" dans perlfunc) avec redirection ou caractères spéciaux du shell ;
2.
Pipe ouverte (voir "open" dans perlfunc) avec une commande qui contient une redirection ou des caractères spéciaux du shell ;
3.
Accolades inversées `` (voir "I/O Operators" dans perlop) avec une commande qui contient une redirection ou des caractères spéciaux du shell ;
4.
Si l'exécutable appelé par system()/exec()/pipe-open()/`` est un script avec la ligne "magique" "#!" ou la ligne "extproc" qui spécifie un shell ;
5.
Si l'exécutable appelé par system()/exec()/pipe-open()/`` est un script sans ligne "magique", et que $ENV{EXECSHELL} est défini sur un shell ;
6.
Si l'exécutable appelé par system()/exec()/pipe-open()/`` n'est pas trouvé (cette remarque est-elle obsolète ?) ;
7.
Pour le globbing (voir "glob" dans perlfunc, "I/O Operators" dans perlop) (obsolète ? Perl utilise maintenant le globbing intégré...).

Pour des raisons de rapidité dans le cas courant, dans les algorithmes ci-dessus, les antislashs dans le nom de commande ne sont pas considérés comme des caractères spéciaux du shell.

Perl démarre directement les scripts qui commencent par les "cookies" "extproc" ou "#!", sans intervention du shell. Perl utilise le même algorithme pour trouver l'exécutable que pdksh : si le chemin sur la ligne "#!" ne fonctionne pas et contient "/", alors la partie répertoire de l'exécutable est ignorée, et l'exécutable est recherché dans . et sur "PATH". Pour trouver les arguments de ces scripts, Perl utilise un algorithme différent de celui de pdksh : jusqu'à 3 arguments sont reconnus, et les espaces blancs finaux sont supprimés.

Si un script ne contient pas un tel cookie, alors pour éviter d'appeler sh.exe, Perl utilise le même algorithme que pdksh : si $ENV{EXECSHELL} est défini, le script est donné comme premier argument à cette commande, sinon "$ENV{COMSPEC} /c" est utilisé (ou une supposition codée en dur si $ENV{COMSPEC} n'est pas défini).

Lors du démarrage direct des scripts, Perl utilise exactement le même algorithme que pour la recherche de scripts donnée par l'option de ligne de commande -S : il cherchera dans le répertoire courant, puis dans les composants de $ENV{PATH} en utilisant l'ordre suivant des extensions ajoutées : aucune extension, .cmd, .btm, .bat, .pl.

Notez que Perl ne commencera à chercher les scripts que si OS/2 ne peut pas démarrer l'application spécifiée, donc "system 'blah'" ne cherchera pas de script s'il existe un fichier exécutable blah.exe quelque part sur "PATH". En d'autres termes, "PATH" est essentiellement recherché deux fois : une fois par le système d'exploitation pour un exécutable, puis par Perl pour les scripts.

Notez également que les fichiers exécutables sur OS/2 peuvent avoir une extension arbitraire, mais .exe sera automatiquement ajouté s'il n'y a pas de point dans le nom. La solution de contournement est aussi simple que cela : puisque blah. et blah désignent le même fichier (du moins sur les systèmes de fichiers FAT et HPFS), pour démarrer un exécutable résidant dans le fichier n:/bin/blah (sans extension), donnez l'argument "n:/bin/blah." (point ajouté) à system().

Perl lancera les programmes PM depuis un processus Perl en mode texte (VIO) dans une session PM séparée ; l'inverse n'est pas vrai : lorsque vous lancez un programme non-PM depuis un processus Perl PM, Perl ne le lancerait pas dans une session séparée. Si une session séparée est souhaitée, assurez-vous que le shell sera utilisé, comme dans "system 'cmd /c myprog'", ou lancez-le en utilisant les arguments optionnels de system() documentés dans le module "OS2::Process". Ceci est considéré comme une fonctionnalité.

Foire aux questions

"Ça ne marche pas"

Les distributions binaires de Perl sont livrées avec un script testperl.cmd qui tente de détecter les problèmes courants d'installations mal configurées. Il y a de fortes chances qu'il découvre quelle étape de l'installation vous avez réussi à rater. ";-)"

Je ne peux pas exécuter de programmes externes

  • Avez-vous exécuté vos programmes avec le commutateur "-w" ? Voir "Démarrage des programmes OS/2 (et DOS) sous Perl".
  • Essayez-vous d'exécuter des commandes internes du shell, comme `copy a b` (interne à cmd.exe), ou `glob a*b` (interne à ksh) ? Vous devez spécifier votre shell explicitement, comme `cmd /c copy a b`, car Perl ne peut pas déduire quelles commandes sont internes à votre shell.

Je ne peux pas intégrer perl dans mon programme, ou utiliser perl.dll depuis mon programme.

Votre programme est-il compilé avec EMX en utilisant "-Zmt -Zcrtdll" ?
Eh bien, de nos jours, Perl DLL devrait également être utilisable depuis un programme compilé différemment... Si vous pouvez exécuter du code Perl depuis des scripts REXX (voir OS2::REXX), alors il y a d'autres aspects de l'interaction qui sont négligés par le code actuel, qui est un peu une "bidouille", pour supporter les programmes principaux compilés différemment.

Si tout le reste échoue, vous devez construire une DLL autonome pour perl. Contactez-moi, je l'ai fait une fois. Les sockets ne fonctionneraient pas, comme beaucoup d'autres choses.

Avez-vous utilisé ExtUtils::Embed ?
Il y a quelque temps, j'ai eu des rapports indiquant que cela ne fonctionnait pas. De nos jours, il est vérifié dans la suite de tests Perl, alors cherchez dans le sous-répertoire ./t de l'arbre de build (ainsi que dans les fichiers *.t du sous-répertoire ./lib) pour trouver comment cela devrait être fait "correctement".

`` et pipe-"open" ne fonctionnent pas sous DOS

Cela peut être une variante de "Je ne peux pas exécuter de programmes externes", ou un problème plus profond. Essentiellement : vous avez besoin de RSX (voir "Prerequisites") pour que ces commandes fonctionnent, et vous pourriez avoir besoin d'un port de sh.exe qui comprend les arguments de commande. L'un de ces ports est listé dans "Prerequisites" sous RSX. N'oubliez pas de définir également la variable ""PERL_SH_DIR"".

DPMI est requis pour RSX.

Impossible de démarrer "find.exe "pattern" file"

L'idée entière de la "API C standard pour lancer des applications" est que les formes "foo" et "foo" des arguments de programme sont complètement interchangeables. find viole ce paradigme ;

find "pattern" file
find pattern file

ne sont pas équivalents ; find ne peut pas être démarré directement en utilisant l'API ci-dessus. Il faut un moyen d'entourer les guillemets doubles dans une autre construction de guillemets, ayant nécessairement un shell supplémentaire non-Unixish entre les deux.

Utilisez l'une de ces options :

system 'cmd', '/c', 'find "pattern" file';
`cmd /c 'find "pattern" file'`

Ceci lancerait find.exe via cmd.exe via "sh.exe" via "perl.exe", mais c'est le prix à payer si vous voulez utiliser un programme non conforme.

INSTALLATION

Installation binaire automatique

La manière la plus pratique d'installer une distribution binaire de perl est d'utiliser l'installateur perl, install.exe. Suivez simplement les instructions, et 99% des problèmes d'installation disparaîtront.

Notez cependant que vous devez avoir unzip.exe dans votre PATH, et l'environnement EMX en cours d'exécution. Ce dernier point signifie que si vous venez d'installer EMX et d'apporter toutes les modifications nécessaires à Config.sys, vous devrez peut-être redémarrer entre-temps. Vérifiez l'exécution d'EMX en tapant

emxrev

L'installateur binaire crée également un dossier sur votre bureau avec quelques objets utiles. Si vous avez besoin de modifier certains aspects du fonctionnement de l'installateur binaire, n'hésitez pas à modifier le fichier Perl.pkg. Cela peut être utile, par exemple, si vous avez besoin d'exécuter l'installateur plusieurs fois et que vous ne souhaitez pas faire de nombreux changements interactifs dans l'interface graphique.

Ce qui n'est pas pris en charge par l'installation binaire automatique :

"PERL_BADLANG"
peut être nécessaire si vous changez votre codepage après l'installation de perl, et que la nouvelle valeur n'est pas prise en charge par EMX. Voir ""PERL_BADLANG"".
"PERL_BADFREE"
voir ""PERL_BADFREE"".
Config.pm
Ce fichier se trouve quelque part en profondeur dans l'emplacement où vous avez installé votre bibliothèque perl, trouvez-le en tapant 
perl -MConfig -le "print $INC{'Config.pm'}"

Bien que la plupart des valeurs importantes de ce fichier soient mises à jour par l'installateur binaire, certaines d'entre elles peuvent nécessiter une édition manuelle. Je ne connais aucune donnée de ce type, veuillez me tenir informé si vous en trouvez une. De plus, les modifications manuelles de la version installée peuvent nécessiter un accompagnement par une modification de ce fichier.

NOTE. En raison d'une faute de frappe, l'installateur binaire de 5.00305 installerait une variable "PERL_SHPATH" dans Config.sys. Veuillez supprimer cette variable et la remplacer par "PERL_SH_DIR".

Installation binaire manuelle

À partir de la version 5.00305, la distribution binaire Perl pour OS/2 est divisée en 11 composants. Malheureusement, pour permettre une installation binaire configurable, les chemins de fichiers dans les archives zip ne sont pas absolus, mais relatifs à un répertoire.

Notez que l'extraction avec les chemins stockés est toujours nécessaire (par défaut avec unzip, spécifiez "-d" à pkunzip). Cependant, vous devez savoir où extraire les fichiers. Vous devez également modifier manuellement les entrées dans Config.sys pour refléter où vous avez placé les fichiers. Notez que si vous avez un décompresseur primitif (comme "pkunzip"), vous pourriez obtenir de nombreux avertissements/erreurs lors de la décompression. Mettez à jour vers "(w)unzip".

Ci-dessous se trouve un exemple de ce qu'il faut faire pour reproduire la configuration sur ma machine. Dans VIEW.EXE, vous pouvez appuyer sur "Ctrl-Insert" maintenant, et couper-coller depuis le fichier résultant - créé dans le répertoire où vous avez démarré VIEW.EXE.

Pour chaque composant, nous mentionnons les variables d'environnement liées à chaque répertoire d'installation. Soit choisissez des répertoires pour correspondre à vos valeurs des variables, soit créez/ajoutez des variables pour prendre en compte les répertoires.

Exécutables Perl VIO et PM (liés dynamiquement)
unzip perl_exc.zip *.exe *.ico -d f:/emx.add/bin
unzip perl_exc.zip *.dll -d f:/emx.add/dll

(avoir les répertoires avec "*.exe" sur PATH, et "*.dll" sur LIBPATH) ;

Exécutable Perl VIO (lié statiquement)
unzip perl_aou.zip -d f:/emx.add/bin

(avoir le répertoire sur PATH) ;

Exécutables pour les utilitaires Perl
unzip perl_utl.zip -d f:/emx.add/bin

(avoir le répertoire sur PATH) ;

Bibliothèque Perl principale
unzip perl_mlb.zip -d f:/perllib/lib

Si ce répertoire est exactement le même que le préfixe qui a été compilé dans perl.exe, vous n'avez rien à changer. Cependant, pour que Perl trouve la bibliothèque si vous utilisez un chemin différent, vous devez définir "PERLLIB_PREFIX" dans Config.sys, voir ""PERLLIB_PREFIX"".

Modules Perl supplémentaires
unzip perl_ste.zip -d f:/perllib/lib/site_perl/5.42.0/

Même remarque que ci-dessus. De plus, si ce répertoire ne fait pas partie des répertoires de @INC (et que @INC est influencé par "PERLLIB_PREFIX"), vous devez placer ce répertoire et le sous-répertoire ./os2 dans la variable "PERLLIB" ou "PERL5LIB". N'utilisez pas "PERL5LIB" à moins qu'elle ne soit déjà définie. Voir "ENVIRONNEMENT" dans perl.

[Vérifiez si ce répertoire d'extraction est toujours pertinent avec la nouvelle structure de répertoire !]

Outils pour compiler les modules Perl
unzip perl_blb.zip -d f:/perllib/lib

Même remarque que pour perl_ste.zip.

Manpages pour Perl et les utilitaires
unzip perl_man.zip -d f:/perllib/man

Ce répertoire devrait idéalement être sur "MANPATH". Vous devez avoir un man fonctionnel pour accéder à ces fichiers.

Manpages pour les modules Perl
unzip perl_mam.zip -d f:/perllib/man

Ce répertoire devrait idéalement être sur "MANPATH". Vous devez avoir un man fonctionnel pour accéder à ces fichiers.

Source de la documentation Perl
unzip perl_pod.zip -d f:/perllib/lib

Ceci est utilisé par le programme "perldoc" (voir perldoc), et peut être utilisé pour générer de la documentation HTML utilisable par les navigateurs WWW, et de la documentation dans des milliards d'autres formats : "info", "LaTeX", "Acrobat", "FrameMaker" et ainsi de suite. [Utilisez des programmes comme pod2latex etc.]

Manuel Perl au format .INF
unzip perl_inf.zip -d d:/os2/book

Ce répertoire devrait idéalement être sur "BOOKSHELF".

Pdksh
unzip perl_sh.zip -d f:/bin

Ceci est utilisé par perl pour exécuter des commandes externes qui nécessitent explicitement un shell, comme les commandes utilisant la redirection et les méta-caractères du shell. Il est également utilisé à la place de /bin/sh explicite.

Définissez "PERL_SH_DIR" (voir ""PERL_SH_DIR"") si vous déplacez sh.exe de l'emplacement ci-dessus.

Note. Il peut être possible d'utiliser un autre shell compatible sh (non testé).

Après avoir installé les composants dont vous aviez besoin et mis à jour Config.sys en conséquence, vous devez modifier manuellement Config.pm. Ce fichier se trouve quelque part en profondeur dans l'emplacement où vous avez installé votre bibliothèque perl, trouvez-le en tapant

perl -MConfig -le "print $INC{'Config.pm'}"

Vous devez corriger toutes les entrées qui ressemblent à des chemins de fichiers (elles commencent actuellement par "f:/").

Avertissement

L'installation automatique et manuelle de Perl laisse des chemins précompilés à l'intérieur des exécutables Perl. Bien que ces chemins soient remplaçables (voir ""PERLLIB_PREFIX"", ""PERL_SH_DIR""), certaines personnes peuvent préférer éditer les chemins binaires à l'intérieur des exécutables/DLL.

Accéder à la documentation

Selon la manière dont vous avez construit/installé Perl, vous pouvez avoir (sinon identique) la documentation Perl dans les formats suivants :

Fichier .INF OS/2

Probablement la forme la plus pratique. Sous OS/2, affichez-la comme suit :

view perl
view perl perlfunc
view perl less
view perl ExtUtils::MakeMaker

(actuellement, les deux derniers peuvent pointer vers un mauvais emplacement, mais cela pourrait s'améliorer bientôt). Sous Win*, voir "SYNOPSIS".

Si vous souhaitez construire vous-même les documents et que vous avez la boîte à outils OS/2, exécutez

pod2ipf > perl.ipf

dans le répertoire /perllib/lib/pod, puis

ipfc /inf perl.ipf

(Attendez-vous à de nombreuses erreurs lors des deux étapes.) Déplacez-le ensuite sur votre chemin BOOKSHELF.

Texte brut

Si vous avez la documentation Perl sous forme source, les utilitaires Perl installés et GNU groff installé, vous pouvez utiliser

perldoc perlfunc
perldoc less
perldoc ExtUtils::MakeMaker

pour accéder à la documentation Perl sous forme de texte (notez que vous pourriez obtenir de meilleurs résultats en utilisant les manpages Perl).

BUILD

Ici, nous discutons de la manière de construire Perl sous OS/2.

L'histoire courte

Supposons que vous êtes un porteur expérimenté, donc que vous êtes sûr que tous les outils nécessaires sont déjà présents sur votre système et que vous savez comment obtenir la distribution source de Perl. Décompressez-la, déplacez-vous dans le répertoire d'extraction et faites :

gnupatch -p0 < os2\diff.configure
sh Configure -des -D prefix=f:/perllib
make
make test
make install
make aout_test
make aout_install

Cela place les exécutables dans f:/perllib/bin. Déplacez manuellement les DLL perl* construites vers "LIBPATH" (ici, pour les DLL Perl, * est une somme de contrôle hexadécimale peu significative), et exécutez :

make installcmd INSTALLCMDDIR=d:/ir/on/path

En supposant que les fichiers "man" ont été placés à un endroit approprié, cela complète l'installation du système Perl minimal. (La distribution binaire contient également de nombreux modules supplémentaires, et la documentation au format INF.)

Ce qui suit est un guide détaillé de ces étapes.

Prérequis

Vous devez avoir le dernier environnement de développement EMX, la suite complète d'outils GNU (gawk renommé en awk, et find.exe GNU avant celui d'OS/2 dans le PATH, idem pour sort.exe, pour vérifier utilisez :

find --version
sort --version

). Vous devez avoir la dernière version de pdksh installée comme sh.exe.

Vérifiez que vous avez les bibliothèques et les en-têtes BSD installés, et - facultativement - les en-têtes et bibliothèques Berkeley DB, et crypt.

Emplacements possibles pour obtenir les fichiers :

ftp://ftp.uni-heidelberg.de/pub/os2/unix/
http://hobbes.nmsu.edu/h-browse.php?dir=/pub/os2
http://cd.textfiles.com/hobbesos29804/disk1/DEV32/
http://cd.textfiles.com/hobbesos29804/disk1/EMX09C/

Il est rapporté que les archives suivantes contiennent suffisamment d'utilitaires pour construire Perl : gnufutil.zip, gnusutil.zip, gnututil.zip, gnused.zip, gnupatch.zip, gnuawk.zip, gnumake.zip, gnugrep.zip, bsddev.zip et ksh527rt.zip (ou une version ultérieure). Notez que tous ces utilitaires sont disponibles auprès de LEO :

ftp://crydee.sai.msu.ru/pub/comp/os/os2/leo/gnu/

Notez également que les fichiers db.lib et db.a de la distribution EMX ne conviennent pas à une compilation multithread (même la version monothread de Perl utilise la RTL C multithread, pour la compatibilité avec XFree86-OS/2). Obtenez une version corrigée depuis :

http://www.ilyaz.org/software/os2/db_mt.zip

Si vous avez exactement la même version de Perl installée, assurez-vous qu'aucune copie de Perl n'est actuellement en cours d'exécution. Les étapes ultérieures de la construction pourraient échouer car une ancienne version de perl.dll chargée en mémoire pourrait être trouvée. L'exécution de "make test" deviendrait sans signification, car les tests vérifieraient une version précédente de Perl construite (cette situation est détectée et signalée par le test os2/os2_base.t). N'oubliez pas de désactiver "PERL_EMXLOAD_SEC" dans l'environnement.

Assurez-vous également d'avoir un répertoire /tmp sur le lecteur actuel et le répertoire . dans votre "LIBPATH". On peut essayer de corriger cette dernière condition en :

set BEGINLIBPATH .\.

si vous utilisez quelque chose comme CMD.EXE ou les dernières versions de 4os2.exe. (La définition de BEGINLIBPATH à seulement "." est ignorée par le noyau OS/2.)

Assurez-vous que votre gcc est compatible avec le lien "-Zomf" : exécutez le script "omflibs" dans le répertoire /emx/lib.

Vérifiez que vous avez link386 installé. Il est fourni en standard avec OS/2, mais peut ne pas être installé en raison d'une personnalisation. Si taper

link386

vous indique que vous ne l'avez pas, faites Installation sélective et choisissez "Lien des modules objets" dans Utilitaires système facultatifs/Plus. Si vous entrez dans les invites de link386, appuyez sur "Ctrl-C" pour quitter.

Obtenir la source de Perl

Vous devez télécharger la dernière source de Perl (y compris les versions développeurs). Avec une certaine probabilité, elle se trouve dans :

http://www.cpan.org/src/
http://www.cpan.org/src/unsupported

Sinon, vous devrez peut-être fouiller dans les index pour la trouver dans le répertoire du mainteneur actuel.

Un cycle rapide des versions développeurs peut casser la construction OS/2 de temps en temps. Consulter

http://www.cpan.org/ports/os2/

peut indiquer la dernière version publiquement publiée par le mainteneur. Notez que la version peut inclure des correctifs supplémentaires à appliquer à la source actuelle de Perl.

Extrayez-la comme suit :

tar vzxf perl5.00409.tar.gz

Vous pourriez voir un message d'erreur lors de l'extraction de Configure. Cela est dû à un conflit avec un fichier nommé de manière similaire, configure.

Déplacez-vous dans le répertoire d'extraction.

Application des correctifs

Vous devez appliquer les correctifs dans ./os2/diff.* comme suit :

gnupatch -p0 < os2\diff.configure

Vous devrez peut-être également appliquer les correctifs fournis avec la distribution binaire de Perl. Il est également judicieux de consulter la liste de diffusion perl5-porters pour les derniers correctifs liés à OS/2 (voir http://www.xray.mpe.mpg.de/mailing-lists/perl5-porters/). De tels correctifs contiennent généralement les chaînes "/os2/" et "patch", il est donc logique de rechercher ces chaînes.

Modification manuelle

Vous pouvez consulter le fichier ./hints/os2.sh et corriger tout ce que vous y trouvez de mal. Je ne m'attends pas à ce que ce soit nécessaire.

Compilation

sh Configure -des -D prefix=f:/perllib

"prefix" signifie : où installer la bibliothèque Perl résultante. En donnant le bon préfixe, vous pouvez éviter d'avoir à spécifier "PERLLIB_PREFIX", voir ""PERLLIB_PREFIX"".

Ignorez le message concernant l'absence de "ln", et concernant l'option "-c" pour tr. Ce dernier est très probablement déjà corrigé. Si vous le voyez et pouvez tracer d'où vient cet avertissement parasite, veuillez m'en informer.

Maintenant :

make

À un moment donné, la compilation peut échouer, signalant une incompatibilité de version ou impossible d'exécuter perl. Cela signifie que vous n'avez pas . dans votre LIBPATH, donc perl.exe ne peut pas trouver le perl67B2.dll nécessaire (considérez ces chiffres hexadécimaux comme du bruit blanc). Une fois cela corrigé, la compilation devrait se terminer sans trop de problèmes.

Tests

Maintenant, exécutez :

make test

Tous les tests devraient réussir (certains étant ignorés). Si vous avez la même version de Perl installée, il est crucial que vous ayez . tôt dans votre LIBPATH (ou dans BEGINLIBPATH), sinon vos tests testeront très probablement la mauvaise version de Perl.

Certains tests peuvent générer des messages supplémentaires similaires à :

Beaucoup de "bad free"
dans les tests de base de données liés à Berkeley DB. Cela devrait déjà être corrigé. Si cela persiste, vous pouvez désactiver ces avertissements, voir ""PERL_BADFREE"".

C'est un message standard émis par les applications OS/2. Les applications *nix meurent silencieusement. C'est considéré comme une fonctionnalité. On peut facilement le désactiver avec des gestionnaires de signaux appropriés.

Cependant, le moteur de test diffuse ces messages à l'écran à des moments inattendus. Deux messages de ce type devraient être présents pendant les tests.

Installation du perl compilé

If you haven't yet moved "perl*.dll" onto LIBPATH, do it now.

Run

make install

It would put the generated files into needed locations. Manually put perl.exe, perl__.exe and perl___.exe to a location on your PATH, perl.dll to a location on your LIBPATH.

Run

make installcmd INSTALLCMDDIR=d:/ir/on/path

to convert perl utilities to .cmd files and put them on PATH. You need to put .EXE-utilities on path manually. They are installed in "$prefix/bin", here $prefix is what you gave to Configure, see "Making".

If you use "man", either move the installed */man/ directories to your "MANPATH", or modify "MANPATH" to match the location. (One could have avoided this by providing a correct "manpath" option to ./Configure, or editing ./config.sh between configuring and making steps.)

Compilation de style "a.out"

Proceed as above, but make perl_.exe (see "perl_.exe") by

make perl_

test and install by

make aout_test
make aout_install

Manually put perl_.exe to a location on your PATH.

Note. The build process for "perl_" does not know about all the dependencies, so you should make sure that anything is up-to-date, say, by doing

make perl_dll

first.

Construction d'une distribution binaire

[This section provides a short overview only...]

Building should proceed differently depending on whether the version of perl you install is already present and used on your system, or is a new version not yet used. The description below assumes that the version is new, so installing its DLLs and .pm files will not disrupt the operation of your system even if some intermediate steps are not yet fully working.

The other cases require a little bit more convoluted procedures. Below I suppose that the current version of Perl is 5.8.2, so the executables are named accordingly.

1.
Fully build and test the Perl distribution. Make sure that no tests are failing with "test" and "aout_test" targets; fix the bugs in Perl and the Perl test suite detected by these tests. Make sure that "all_test" make target runs as clean as possible. Check that os2/perlrexx.cmd runs fine.
2.
Fully install Perl, including "installcmd" target. Copy the generated DLLs to "LIBPATH"; copy the numbered Perl executables (as in perl5.8.2.exe) to "PATH"; copy "perl_.exe" to "PATH" as "perl_5.8.2.exe". Think whether you need backward-compatibility DLLs. In most cases you do not need to install them yet; but sometime this may simplify the following steps.
3.
Make sure that "CPAN.pm" can download files from CPAN. If not, you may need to manually install "Net::FTP".
4.
Install the bundle "Bundle::OS2_default" 
perl5.8.2 -MCPAN -e "install Bundle::OS2_default" < nul |& tee 00cpan_i_1

This may take a couple of hours on 1GHz processor (when run the first time). And this should not be necessarily a smooth procedure. Some modules may not specify required dependencies, so one may need to repeat this procedure several times until the results stabilize.

perl5.8.2 -MCPAN -e "install Bundle::OS2_default" < nul |& tee 00cpan_i_2
perl5.8.2 -MCPAN -e "install Bundle::OS2_default" < nul |& tee 00cpan_i_3

Even after they stabilize, some tests may fail.

Fix as many discovered bugs as possible. Document all the bugs which are not fixed, and all the failures with unknown reasons. Inspect the produced logs 00cpan_i_1 to find suspiciously skipped tests, and other fishy events.

Keep in mind that installation of some modules may fail too: for example, the DLLs to update may be already loaded by CPAN.pm. Inspect the "install" logs (in the example above 00cpan_i_1 etc) for errors, and install things manually, as in

cd $CPANHOME/.cpan/build/Digest-MD5-2.31
make install

Some distributions may fail some tests, but you may want to install them anyway (as above, or via "force install" command of "CPAN.pm" shell-mode).

Since this procedure may take quite a long time to complete, it makes sense to "freeze" your CPAN configuration by disabling periodic updates of the local copy of CPAN index: set "index_expire" to some big value (I use 365), then save the settings

CPAN> o conf index_expire 365
CPAN> o conf commit

Reset back to the default value 1 when you are finished.

5.
When satisfied with the results, rerun the "installcmd" target. Now you can copy "perl5.8.2.exe" to "perl.exe", and install the other OMF-build executables: "perl__.exe" etc. They are ready to be used.
6.
Change to the "./pod" directory of the build tree, download the Perl logo CamelGrayBig.BMP, and run 
( perl2ipf > perl.ipf ) |& tee 00ipf
ipfc /INF perl.ipf |& tee 00inf

This produces the Perl docs online book "perl.INF". Install in on "BOOKSHELF" path.

7.
Now is the time to build statically linked executable perl_.exe which includes newly-installed via "Bundle::OS2_default" modules. Doing testing via "CPAN.pm" is going to be painfully slow, since it statically links a new executable per XS extension.

Here is a possible workaround: create a toplevel Makefile.PL in $CPANHOME/.cpan/build/ with contents being (compare with "Making executables with a custom collection of statically loaded extensions")

use ExtUtils::MakeMaker;
WriteMakefile NAME => 'dummy';

execute this as

perl_5.8.2.exe Makefile.PL <nul |& tee 00aout_c1
make -k all test <nul |& 00aout_t1

Again, this procedure should not be absolutely smooth. Some "Makefile.PL"'s in subdirectories may be buggy, and would not run as "child" scripts. The interdependency of modules can strike you; however, since non-XS modules are already installed, the prerequisites of most modules have a very good chance to be present.

If you discover some glitches, move directories of problematic modules to a different location; if these modules are non-XS modules, you may just ignore them - they are already installed; the remaining, XS, modules you need to install manually one by one.

After each such removal you need to rerun the "Makefile.PL"/"make" process; usually this procedure converges soon. (But be sure to convert all the necessary external C libraries from .lib format to .a format: run one of

emxaout foo.lib
emximp -o foo.a foo.lib

whichever is appropriate.) Also, make sure that the DLLs for external libraries are usable with executables compiled without "-Zmtd" options.

When you are sure that only a few subdirectories lead to failures, you may want to add "-j4" option to "make" to speed up skipping subdirectories with already finished build.

When you are satisfied with the results of tests, install the build C libraries for extensions:

make install |& tee 00aout_i

Now you can rename the file ./perl.exe generated during the last phase to perl_5.8.2.exe; place it on "PATH"; if there is an inter-dependency between some XS modules, you may need to repeat the "test"/"install" loop with this new executable and some excl

modules utilisés - jusqu'à ce que la procédure converge.

Vous avez maintenant toutes les bibliothèques .a nécessaires pour ces modules Perl aux endroits où le constructeur Perl peut les trouver. Utilisez le constructeur Perl : déplacez-vous dans un répertoire vide, créez à nouveau un Makefile.PL "factice", et exécutez

perl_5.8.2.exe Makefile.PL |& tee 00c
make perl                  |& tee 00p

Cela devrait créer un exécutable ./perl.exe avec toutes les extensions statiquement chargées intégrées. Comparez les fichiers perlmain.c générés pour vous assurer que pendant les itérations, le nombre d'extensions chargées n'augmente que. Renommez ./perl.exe en perl_5.8.2.exe sur "PATH".

Lorsque cela converge, vous obtenez une variante fonctionnelle de perl_5.8.2.exe ; copiez-la dans "perl_.exe". Vous avez terminé la génération de l'installation Perl locale.

8.
Assurez-vous que les modules installés sont effectivement installés à l'emplacement du nouveau Perl, et ne sont pas hérités des entrées de @INC données pour l'héritage des anciennes versions de Perl : définissez "PERLLIB_582_PREFIX" pour rediriger la nouvelle version de Perl vers un nouvel emplacement, et copiez les fichiers installés dans ce nouvel emplacement. Répétez les tests pour vous assurer que les versions des modules héritées des anciennes versions de Perl ne sont pas nécessaires.

En fait, la sortie du journal de pod2ipf(1) lors de l'étape 6 donne des informations très détaillées sur les modules qui sont chargés et d'où ; vous pouvez donc l'utiliser comme outil de vérification supplémentaire.

Vérifiez que certains fichiers temporaires ne se sont pas retrouvés dans l'arborescence d'installation de perl. Exécutez quelque chose comme ceci

pfind . -f "!(/\.(pm|pl|ix|al|h|a|lib|txt|pod|imp|bs|dll|ld|bs|inc|xbm|yml|cgi|uu|e2x|skip|packlist|eg|cfg|html|pub|enc|all|ini|po|pot)$/i or /^\w+$/") | less

dans l'arborescence d'installation (la principale et celle de sitelib).

Compressez toutes les DLL avec lxlite. Le minuscule .exe peut être compressé avec "/c:max" (le bug n'apparaît que lorsqu'il y a un correctif dans les 6 derniers octets d'une page (?); puisque les exécutables minuscules sont beaucoup plus petits qu'une page, le bug ne se produira pas). Ne compressez pas "perl_.exe" - cela ne fonctionnerait pas sous DOS.

9.
Vous pouvez maintenant générer la distribution binaire. Cela se fait en exécutant le test de la distribution CPAN "OS2::SoftInstaller". Adaptez le fichier test.pl à la disposition de la version actuelle de Perl d'abord. N'oubliez pas d'empaqueter les DLL externes nécessaires en conséquence. Incluez la description des bugs et des échecs de la suite de tests que vous n'avez pas pu corriger. Incluez les versions avec une pile petite des exécutables Perl du répertoire de construction de Perl.

Incluez perl5.def afin que les gens puissent relier la DLL Perl en préservant la compatibilité binaire, ou créer des DLL de compatibilité. Incluez les fichiers diff ("diff -pu old new") des corrections que vous avez apportées afin que les gens puissent reconstruire votre version. Incluez perl5.map afin que l'on puisse utiliser le débogage à distance.

10.
Partagez ce que vous avez fait avec les autres. Détendez-vous. Profitez des fruits de votre travail.
11.
Préparez-vous aux remerciements, rapports de bugs, courriels de haine et spam résultant de l'étape précédente. Aucune bonne action ne devrait rester impunie !

Construction de fichiers .EXE personnalisés

Les exécutables Perl peuvent être reconstruits à tout moment. De plus, on peut utiliser l'interface d'intégration (voir perlembed) pour créer des exécutables très personnalisés.

Création d'exécutables avec une collection personnalisée d'extensions chargées statiquement

C'est un peu plus facile à faire en diminuant la liste des extensions chargées statiquement. Nous n'examinons ce cas qu'ici.

1.
Déplacez-vous dans un répertoire vide et créez un fichier placeholder <Makefile.PL> : 
use ExtUtils::MakeMaker;
WriteMakefile NAME => 'dummy';
2.
Exécutez-le avec la saveur de Perl (perl.exe ou perl_.exe) que vous voulez reconstruire. 
perl_ Makefile.PL
3.
Demandez-lui de créer un nouvel exécutable Perl : 
make perl

(vous devrez peut-être ajouter manuellement "PERLTYPE=-DPERL_CORE" à cette ligne de commande sur certaines versions de Perl ; le symptôme est que la boucle de la ligne de commande ne fonctionne pas depuis les shells OS/2 avec l'exécutable nouvellement compilé ; vérifiez avec

.\perl.exe -wle "print for @ARGV" *

).

4.
L'étape précédente a créé perlmain.c qui contient une liste d'appels newXS() vers la fin. En supprimant les appels inutiles et en réexécutant 
make perl

, un exécutable personnalisé sera produit.

Création d'exécutables avec des chemins de recherche personnalisés

L'exécutable Perl par défaut est suffisamment flexible pour prendre en charge la plupart des utilisations. Cependant, on peut souhaiter quelque chose d'encore plus flexible ; par exemple, on peut vouloir trouver la DLL Perl par rapport à l'emplacement du fichier EXE ; ou on peut vouloir ignorer l'environnement lors de la définition du chemin de recherche de la bibliothèque Perl, etc.

Si vous êtes à l'aise avec l'interface d'intégration (voir perlembed), ces choses sont faciles à faire en répétant les étapes décrites dans "Création d'exécutables avec une collection personnalisée d'extensions chargées statiquement", et en effectuant des modifications plus complètes à main() de perlmain.c. Les personnes qui ont peu envie de comprendre Perl peuvent simplement renommer main() et effectuer les modifications nécessaires dans un main() personnalisé qui appelle la fonction renommée au moment opportun.

Cependant, il existe une troisième voie : la DLL Perl exporte la fonction main() et plusieurs rappels pour personnaliser le chemin de recherche. Ci-dessous un exemple complet d'un "chargeur Perl" qui

1.
Recherche la DLL Perl dans le répertoire "$exedir/../dll" ;
2.
Prépends le répertoire ci-dessus à "BEGINLIBPATH" ;
3.
Échoue si la DLL Perl trouvée via "BEGINLIBPATH" est différente de celle qui a été chargée à l'étape 1 ; par exemple, un autre processus pourrait l'avoir chargée depuis "LIBPATH" ou depuis une valeur différente de "BEGINLIBPATH". Dans ces cas, il faut modifier le réglage du système de sorte que cet autre processus ne s'exécute pas, ou charge la DLL depuis "BEGINLIBPATH" avec "LIBPATHSTRICT=T" (disponible avec les noyaux après septembre 2000).
4.
Charge la bibliothèque Perl depuis "$exedir/../dll/lib/".
5.
Utilise le shell Bourne depuis "$exedir/../dll/sh/ksh.exe".

Pour de meilleurs résultats, compilez le fichier C ci-dessous avec les mêmes options que la DLL Perl. Cependant, une grande partie de la fonctionnalité fonctionnera même si l'exécutable n'est pas une application EMX, par exemple, s'il est compilé avec

gcc -Wall -DDOSISH -DOS2=1 -O2 -s -Zomf -Zsys perl-starter.c \
  -DPERL_DLL_BASENAME=\"perl312F\" -Zstack 8192 -Zlinker /PM:VIO

Fonctionnalités (maladresses) spécifiques du port OS/2

"setpriority", "getpriority"

Notez que ces fonctions sont compatibles avec *nix, pas avec les anciens ports de '94 - 95. Les priorités sont absolues, allant de 32 à -95, plus bas est plus rapide. 0 est la priorité par défaut.

AVERTISSEMENT. Appeler "getpriority" sur un processus inexistant pouvait bloquer le système avant Warp3 fixpak22. À partir de Warp3, Perl utilisera une solution de contournement : il abandonnera getpriority() si le processus n'est pas présent. Ce n'est pas possible sur les versions plus anciennes "2.*", et il y a de toute façon une condition de concurrence.

system()

La forme multi-arguments de system() permet un argument numérique supplémentaire. La signification de cet argument est décrite dans OS2::Process.

Lors de la recherche d'un programme à exécuter, Perl demande d'abord au système d'exploitation de rechercher les exécutables dans "PATH" (OS/2 ajoute l'extension .exe si aucune extension n'est présente). Si introuvable, il recherche un script avec les extensions possibles ajoutées dans cet ordre : aucune extension, .cmd, .btm, .bat, .pl. Si trouvé, Perl vérifie le début du fichier pour les chaînes magiques "#!" et "extproc ". Si trouvé, Perl utilise le reste de la première ligne comme début de la ligne de commande pour exécuter ce script. La seule modification apportée à la première ligne est l'extraction des arguments (actuellement jusqu'à 3), et l'ignorance de la partie chemin du nom de « l'interpréteur » s'il ne peut être trouvé en utilisant le chemin complet.

Par exemple, "system 'foo', 'bar', 'baz'" peut amener Perl à trouver C:/emx/bin/foo.cmd avec la première ligne étant

extproc /bin/bash    -x   -c

Si /bin/bash.exe est introuvable, Perl recherche alors un exécutable bash.exe dans "PATH". S'il est trouvé dans C:/emx.add/bin/bash.exe, alors le system() ci-dessus est traduit par

system qw(C:/emx.add/bin/bash.exe -x -c C:/emx/bin/foo.cmd bar baz)

Une traduction supplémentaire est effectuée : au lieu de /bin/sh, Perl utilise le shell codé en dur ou personnalisé (voir ""PERL_SH_DIR"").

La recherche susmentionnée de « l'interpréteur » est récursive : si l'exécutable bash est introuvable, mais que bash.btm est trouvé, Perl en examinera la première ligne, etc. La seule limite codée en dur sur la profondeur de récursion est implicite : il y a une limite de 4 sur le nombre d'arguments supplémentaires insérés avant les arguments réels donnés à system(). En particulier, si aucun argument supplémentaire n'est spécifié sur les premières lignes « magiques », la limite de profondeur est de 4.

Si Perl découvre que l'exécutable trouvé est de type PM alors que la session actuelle ne l'est pas, il démarrera le nouveau processus dans une session séparée du type nécessaire. Appel via "OS2::Process" pour désactiver cette magie.

AVERTISSEMENT. En raison de la logique décrite, vous devez explicitement spécifier l'extension .com si nécessaire. De plus, si l'exécutable perl5.6.1 est demandé, Perl ne recherchera pas perl5.6.1.exe. [Cela peut changer à l'avenir.]

"extproc" sur la première ligne

Si les premiers caractères d'un script Perl sont "extproc ", cette ligne est traitée comme une ligne "#!", donc tous les commutateurs de cette ligne sont traités (deux fois si le script a été lancé via cmd.exe). Voir "DESCRIPTION" dans perlrun.

Gestion centralisée des ressources

Étant donné que pour appeler certaines API OS/2 il faut avoir un sous-système "Win" correctement initialisé, les extensions spécifiques à OS/2 peuvent nécessiter l'obtention de "HAB" et de "HMQ". Si une extension le faisait elle-même, une autre extension pourrait ne pas pouvoir s'initialiser.

Perl fournit une gestion centralisée de ces ressources :

"HAB"
Pour obtenir le HAB, l'extension doit appeler "hab = perl_hab_GET()" en C. Après cet appel, "hab" est accessible sous le nom "Perl_hab". Il n'est pas nécessaire de libérer le HAB après utilisation.

Si, pour une raison quelconque, perl.h ne peut pas être inclus, utilisez

extern int Perl_hab_GET(void);

à la place.

"HMQ"
Il existe deux cas :
  • l'extension a besoin d'un "HMQ" uniquement parce que certaines API ne fonctionneront pas autrement. Utilisez "serve = 0" ci-dessous.
  • l'extension a besoin d'un "HMQ" car elle veut s'engager dans une boucle d'événements PM. Utilisez "serve = 1" ci-dessous.

Pour obtenir un "HMQ", l'extension doit appeler "hmq = perl_hmq_GET(serve)" en C. Après cet appel, "hmq" est accessible sous le nom "Perl_hmq".

Pour signaler à Perl que le HMQ n'est plus nécessaire, appelez perl_hmq_UNSET(serve). Le processus Perl se morphera/démorphera automatiquement en/depuis un processus PM si le HMQ est requis/non requis. Perl activera/désactivera automatiquement le message "WM_QUIT" lors de l'arrêt si la file d'attente de messages est servie/non servie.

NOTE. Si lors d'un arrêt, il existe une file d'attente de messages qui n'a pas désactivé WM_QUIT, et qui n'a pas traité le message WM_QUIT reçu, l'arrêt sera automatiquement annulé. N'appelez pas perl_hmq_GET(1) à moins que vous n'ayez l'intention de traiter les messages de manière ordonnée.

Traitement des erreurs signalées par l'API OS/2
Il existe deux conventions principales (il est utile de les appeler "Dos*" et "Win*" - bien que cette partie de la signature de la fonction ne soit pas toujours déterminée par le nom de l'API) pour signaler les conditions d'erreur de l'API OS/2. La plupart des API "Dos*" signalent le code d'erreur comme résultat de l'appel (donc 0 signifie succès, et il existe de nombreux types d'erreurs). La plupart des API "Win*" signalent le succès/échec via le résultat étant "TRUE"/"FALSE" ; pour trouver la raison de l'échec, il faut appeler l'API WinGetLastError().

Certains points d'entrée "Win*" surchargent également une valeur de retour "significative" avec l'indicateur d'erreur ; une valeur de retour de 0 indique une erreur. D'autres points d'entrée "Win*" surchargent encore plus les choses, et une valeur de retour de 0 peut signifier un appel réussi retournant une valeur valide 0, ainsi qu'une condition d'erreur ; dans le cas d'une valeur de retour de 0, il faut appeler l'API WinGetLastError() pour distinguer un appel réussi d'un appel raté.

Par convention, tous les appels à l'API OS/2 devraient signaler leurs échecs en réinitialisant $^E. Toutes les fonctions accessibles depuis Perl qui appellent l'API OS/2 peuvent être divisées en deux classes : certaines font un die() lorsqu'une erreur d'API est rencontrée, les autres signalent l'erreur via une valeur de retour fausse (bien sûr, cela ne concerne pas les fonctions accessibles depuis Perl qui s'attendent à un échec de l'appel API OS/2, ayant mis en place des solutions de contournement).

Évidemment, dans la situation du dernier type de signature d'une API OS/2, il est beaucoup plus pratique pour les utilisateurs que l'échec soit indiqué par un die() : on n'a pas besoin de vérifier $^E pour savoir que quelque chose s'est mal passé. Si, cependant, cette solution n'est pas souhaitable pour une raison quelconque, le code en question doit réinitialiser $^E à 0 avant de faire cet appel API OS/2, afin que l'appelant de cette fonction accessible depuis Perl ait une chance de distinguer un succès-mais-retour-0 d'un échec. (On peut retourner undef comme moyen alternatif de signaler une erreur.)

Les macros pour simplifier ce type de propagation d'erreurs sont

CheckOSError(expr)
Retourne vrai en cas d'erreur, définit $^E. Attend que expr() soit un appel à une API de style "Dos*".
CheckWinError(expr)
Retourne vrai en cas d'erreur, définit $^E. Attend que expr() soit un appel à une API de style "Win*".
SaveWinError(expr)
Retourne "expr", définit $^E à partir de WinGetLastError() si "expr" est faux.
"SaveCroakWinError(expr,die,name1,name2)"
Retourne "expr", définit $^E à partir de WinGetLastError() si "expr" est faux, et fait un die() si "die" et $^E sont vrais. Le message du die est la concaténation des chaînes "name1" et "name2", séparées par ": " du contenu de $^E.
"WinError_2_Perl_rc"
Définit "Perl_rc" à la valeur de retour de WinGetLastError().
"FillWinError"
Définit "Perl_rc" à la valeur de retour de WinGetLastError(), et définit $^E à la valeur correspondante.
FillOSError(rc)
Définit "Perl_rc" à "rc", et définit $^E à la valeur correspondante.
Chargement des DLLs et des ordinaux dans les DLLs
Certaines DLL ne sont présentes que dans certaines versions d'OS/2, ou dans certaines configurations d'OS/2. Certains points d'entrée exportés ne sont présents que dans les DLL livrées avec certaines versions d'OS/2. Si ces DLL et points d'entrée étaient liés directement pour un exécutable/DLL Perl ou à partir d'extensions Perl, cet exécutable ne fonctionnerait qu'avec les versions/configurations spécifiées. Saveurs de Perl

En raison des idiosyncrasies d'OS/2, on ne peut pas mettre tous ses œufs dans le même panier (bien que l'environnement EMX fasse de grands efforts pour surmonter ces limitations, la situation pourrait donc s'améliorer). Il existe 4 exécutables pour Perl fournis par la distribution :

perl.exe

Le cheval de bataille principal. C'est un exécutable chimérique : il est compilé comme un exécutable de style "a.out", mais est lié à la bibliothèque dynamique de style "omf" perl.dll, et à la DLL CRT dynamique. Cet exécutable est une application VIO.

Il peut charger des extensions dynamiques Perl, et il peut faire fork().

Note. Gardez à l'esprit que fork() est nécessaire pour ouvrir un pipe vers soi-même.

perl_.exe

C'est un exécutable de style "a.out" statiquement lié. Il ne peut pas charger d'extensions Perl dynamiques. L'exécutable fourni dans les distributions binaires a de nombreuses extensions pré-compilées, donc la restriction ci-dessus n'est importante que si vous utilisez des extensions compilées sur mesure. Cet exécutable est une application VIO.

C'est le seul exécutable qui ne nécessite pas OS/2. Les amis bloqués dans le monde "M$" apprécieraient le fait que cet exécutable fonctionne sous DOS, Win0.3*, Win0.95 et WinNT avec un extender approprié. Voir "Autres OS".

perl__.exe

C'est le même exécutable que perl___.exe, mais c'est une application PM.

Note. Habituellement (sauf redirection explicite lors du démarrage) STDIN, STDERR et STDOUT d'une application PM sont redirigés vers nul. Cependant, il est possible de les voir si vous démarrez "perl__.exe" à partir d'un programme PM qui émule une fenêtre de console, comme le mode Shell d'Emacs ou EPM. Ainsi, il est possible d'utiliser le débogueur Perl (voir perldebug) pour déboguer votre application PM (mais attention à la m

boucles de messagerie bloquées - cela ne fonctionnera pas si vous avez une file d'attente de messages à servir, à moins que vous n'intégreriez le service dans la fonction getc() du débogueur).

Une autre façon de voir la sortie d'un programme PM est de l'exécuter comme suit :

pm_prog args 2>&1 | cat -

avec un shell différent de cmd.exe, de sorte qu'il ne crée pas de lien entre une session VIO et la session de "pm_porg". (Un tel lien ferme la fenêtre VIO.) Par exemple, cela fonctionne avec sh.exe - ou avec Perl !

open P, 'pm_prog args 2>&1 |' or die;
print while <P>;

Le programme perl__.exe est requis si vous souhaitez lancer votre programme sans fenêtre VIO présente, mais pas "detach"é (exécutez "help detach" pour plus d'informations). Très utile pour les extensions qui utilisent PM, telles que "Perl/Tk" ou "OpenGL".

Notez également que les différences entre les exécutables PM et VIO ne concernent que le comportement par défaut. On peut lancer n'importe quel exécutable dans n'importe quel type de session en utilisant les arguments "/fs", "/pm" ou "/win" de la commande "start" (de CMD.EXE ou un shell similaire). Alternativement, on peut utiliser le premier argument numérique de la fonction Perl "system" (voir OS2::Process).

perl___.exe

C'est un exécutable de style "omf" qui est lié dynamiquement à perl.dll et aux DLL CRT. Je ne connais aucun avantage de cet exécutable par rapport à "perl.exe", mais il ne peut pas fork() du tout. Eh bien, un avantage est que le processus de construction n'est pas aussi compliqué qu'avec "perl.exe".

C'est une application VIO.

Pourquoi des noms bizarres ?

Puisque Perl traite la ligne "#!" (cf. "DESCRIPTION" dans perlrun, "Command Switches" dans perlrun, "No Perl script found in input" dans perldiag), il doit savoir quand un programme est un Perl. Il existe une convention de nommage qui permet à Perl de distinguer les lignes correctes des lignes incorrectes. Les noms ci-dessus sont presque les seuls noms autorisés par cette convention qui ne contiennent pas de chiffres (qui ont une sémantique absolument différente).

Pourquoi liaison dynamique ?

Eh bien, avoir plusieurs exécutables liés dynamiquement à la même grosse bibliothèque présente des avantages, mais cela ne justifierait pas le travail supplémentaire pour la compiler. La raison est la liaison dynamique « difficile » utilisée par OS/2, compliquée pour les développeurs mais très rapide et pratique pour les utilisateurs.

Il y a deux caractéristiques distinctives du modèle de liaison dynamique d'OS/2 : premièrement, toutes les références aux fonctions externes sont résolues au moment de la compilation ; deuxièmement, il n'y a pas de correction au moment de l'exécution des DLL une fois qu'elles sont chargées en mémoire. La première caractéristique est un avantage énorme par rapport aux autres modèles : elle évite les conflits lorsque plusieurs DLL utilisées par une application exportent des entrées portant le même nom. Dans de tels cas, les « autres » modèles de liaison dynamique choisissent simplement entre ces deux points d'entrée en utilisant un critère aléatoire - avec des catastrophes prévisibles comme résultat. Mais c'est la deuxième caractéristique qui nécessite la construction de perl.dll.

Les tables d'adresses des DLL ne sont corrigées qu'une seule fois, lors de leur chargement. Les adresses des points d'entrée dans les DLL sont garanties d'être les mêmes pour tous les programmes qui utilisent la même DLL. Cela élimine la correction au moment de l'exécution - une fois qu'une DLL est chargée, son code est en lecture seule.

Bien que cela permette certains avantages de performance (significatifs ?), cela rend la vie beaucoup plus difficile pour les développeurs, car le schéma ci-dessus rend impossible pour une DLL d'être « liée » à un symbole dans le fichier .EXE. En effet, cela nécessiterait qu'une DLL ait des tables de relocalisation différentes pour les exécutables (différents) qui utilisent cette DLL.

Cependant, une extension Perl chargée dynamiquement est obligée d'utiliser certains symboles de l'exécutable Perl, par exemple pour savoir comment trouver les arguments des fonctions : les arguments résident sur la pile d'évaluation interne de Perl. La solution consiste à placer le code principal de l'interpréteur dans une DLL, et à faire de l'exécutable .EXE qui charge simplement cette DLL en mémoire et fournit les arguments de la commande. L'extension DLL ne peut pas se lier aux symboles de .EXE, mais elle n'a aucun problème à se lier aux symboles de .DLL.

Cela augmente considérablement le temps de chargement de l'application (ainsi que la complexité de la compilation). Puisque l'interpréteur est dans une DLL, la RTL C est essentiellement obligée de résider également dans une DLL (sinon les extensions ne pourraient pas utiliser la CRT). Il y a des avantages si vous utilisez différentes saveurs de Perl, comme l'exécution simultanée de perl.exe et perl__.exe : elles partagent la mémoire de perl.dll.

NOTE. Il y a un effet supplémentaire qui rend les DLL plus coûteuses en ressources : les DLL sont chargées dans la région de mémoire partagée, qui est une ressource rare étant donné la barrière de 512 Mo de la mémoire virtuelle « standard » d'OS/2. Le code des fichiers .EXE est également partagé par tous les processus qui utilisent le fichier .EXE particulier, mais ils sont « partagés dans l'espace d'adressage privé du processus » ; cela est possible car l'adresse à laquelle les différentes sections du fichier .EXE sont chargées est décidée au moment de la compilation, donc tous les processus ont ces sections chargées aux mêmes adresses, et aucune correction des liens internes dans le .EXE n'est nécessaire.

Puisque les DLL peuvent être chargées au moment de l'exécution, pour avoir le même mécanisme pour les DLL, il faut que la plage d'adresses de n'importe quelle DLL chargée dans le système soit disponible dans tous les processus qui n'ont pas encore chargé une DLL particulière. C'est pourquoi les DLL sont mappées dans la région de mémoire partagée.

Pourquoi une construction chimérique ?

L'environnement EMX actuel ne permet pas aux DLL compilées à l'aide du format Unix "a.out" d'exporter des symboles pour des données (ou du moins certains types de données). Cela force la compilation de style "omf" pour perl.dll.

L'environnement EMX actuel ne permet pas aux fichiers .EXE compilés au format "omf" de fork(). fork() est nécessaire pour exactement trois opérations Perl :

  • fork() explicite dans le script,
  • "open FH, "|-""
  • "open FH, "-|"", en d'autres termes, ouvrir des pipes vers lui-même.

Bien que ces opérations ne soient pas vitales, elles sont nécessaires pour de nombreux scripts utiles. Cela force la compilation de style "a.out" pour perl.exe.

ENVIRONNEMENT

Ici, nous listons les variables d'environnement qui sont spécifiques à OS/2, DOS et Win*, ou qui sont plus importantes sous OS/2 que sous d'autres systèmes d'exploitation.

"PERLLIB_PREFIX"

Spécifique au port EMX. Doit avoir la forme

chemin1;chemin2

ou

chemin1 chemin2

Si le début d'un chemin précompilé correspond à chemin1, il est substitué par chemin2.

Doit être utilisé si la bibliothèque Perl est déplacée de son emplacement par défaut de préférence à "PERL(5)LIB", car cela ne laisserait pas de fausses entrées dans @INC. Par exemple, si la version compilée de Perl recherche @INC dans f:/perllib/lib, et que vous souhaitez installer la bibliothèque dans h:/opt/gnu, faites :

f:/perllib/lib/5.00553/os2
f:/perllib/lib/5.00553
f:/perllib/lib/site_perl/5.00553/os2
f:/perllib/lib/site_perl/5.00553
.

à savoir :

h:/opt/gnu/5.00553/os2
h:/opt/gnu/5.00553
h:/opt/gnu/site_perl/5.00553/os2
h:/opt/gnu/site_perl/5.00553
.

"PERL_BADLANG"

Si 0, Perl ignore l'échec de setlocale(). Peut être utile avec des locales étranges.

"PERL_BADFREE"

Si 0, Perl ne signalera pas en cas de free() non justifié. Avec les versions plus anciennes de Perl, cela pourrait être utile en conjonction avec le module DB_File, qui était bogué lorsqu'il était lié dynamiquement et construit en OMF.

Ne doit pas être défini avec les versions plus récentes de Perl, car cela pourrait masquer des problèmes réels.

Spécifique au port EMX. Indique la partie répertoire de l'emplacement de sh.exe.

"USE_PERL_FLOCK"

Spécifique au port EMX. Puisque flock(3) est présent dans EMX, mais n'est pas fonctionnel, il est émulated par Perl. Pour désactiver les émulations, définissez la variable d'environnement "USE_PERL_FLOCK=0".

"TMP" ou "TEMP"

Spécifique au port EMX. Utilisé comme emplacement de stockage pour les fichiers temporaires.

Évolution

Ici, nous listons les changements majeurs qui pourraient vous surprendre.

Descripteurs de fichiers en mode texte

À partir de la version 5.8, Perl utilise une couche de traduction intégrée pour les fichiers en mode texte. Cela remplace la couche EMX efficace et bien testée par un code qui devrait être mieux caractérisé comme un « hack rapide ».

En plus des bugs possibles et d'un ina

bilité de suivre les changements dans la politique de traduction avec des interrupteurs marche/arrêt pour la traduction TERMIO, cela introduit un changement incompatible grave : avant, sysread() sur les descripteurs de fichiers en mode texte passait par la couche de traduction, maintenant ce n'est plus le cas.

Priorités

"setpriority" et "getpriority" ne sont pas compatibles avec les ports antérieurs d'Andreas Kaiser. Voir "setpriority, getpriority".

Désignation des noms de DLL : avant 5.6.2

Avec la version 5.003_01, les bibliothèques chargeables dynamiquement doivent être reconstruites lorsqu'une version différente de Perl est compilée. En particulier, les DLL (y compris perl.dll) sont maintenant créées avec des noms contenant une somme de contrôle, permettant ainsi de contourner le schéma d'OS/2 de mise en cache des DLL.

Il peut être possible de coder une solution de contournement simple qui permettrait de

  • trouver les anciennes DLL en parcourant l'ancien @INC ;
  • désigner les noms conformément au schéma de la nouvelle Perl et copier les DLL sous ces noms ;
  • modifier les tables internes "LX" des DLL pour refléter le changement de nom (probablement pas nécessaire pour les DLL d'extension Perl, car les noms codés en interne ne sont pas utilisés pour les DLL "spécifiques", ils sont seulement utilisés pour les DLL "globales").
  • modifier les tables internes "IMPORT" et changer le nom de perl????.dll "ancien" en perl????.dll "nouveau".

Désignation des noms de DLL : 5.6.2 et au-delà

En fait, la désignation des DLL d'extension était due à une mauvaise compréhension du modèle de chargement dynamique d'OS/2. OS/2 maintient (effectivement) deux tables différentes de DLL chargées :

DLL globales
celles chargées par le nom de base depuis "LIBPATH" ; y compris celles associées au moment de l'édition des liens ;
DLL spécifiques
chargées par leur nom complet.

Lors de la résolution d'une requête pour une DLL globale, la table des DLL spécifiques déjà chargées est (effectivement) ignorée ; de plus, les DLL spécifiques sont *toujours* chargées depuis le chemin spécifié.

Il y a/avait une petite subtilité qui rend ce schéma fragile : que faire des DLL chargées depuis

"BEGINLIBPATH" et "ENDLIBPATH"
(qui dépendent du processus)
. depuis "LIBPATH"
qui dépend effectivement du processus (bien que "LIBPATH" soit le même pour tous les processus).

À moins que "LIBPATHSTRICT" ne soit défini sur "T" (et que le noyau soit postérieur au 2000/09/01), de telles DLL sont considérées comme globales. Lors du chargement d'une DLL globale, elle est d'abord recherchée dans la table des DLL globales déjà chargées. Par conséquent, le fait qu'un exécutable ait chargé une DLL depuis "BEGINLIBPATH" et "ENDLIBPATH", ou . depuis "LIBPATH" peut affecter *quelle* DLL est chargée lorsqu'un *autre* exécutable demande une DLL du même nom. C'est la raison de la désignation des noms des DLL Perl spécifique à la version.

Étant donné que les DLL d'extension Perl sont toujours chargées avec le chemin complet, il n'est pas nécessaire de désigner leurs noms de manière spécifique à la version : leur répertoire reflète déjà la version correspondante de Perl, et @INC prend en compte la compatibilité binaire avec les versions antérieures. À partir de 5.6.2, le schéma de désignation des noms est corrigé pour être le même que celui de Perl 5.005_53 (identique à une version binaire populaire). Ainsi, les nouvelles versions de Perl pourront *résoudre les noms* des anciennes DLL d'extension si @INC permet de trouver leurs répertoires.

Cependant, cela ne garantit toujours pas que ces DLL puissent être chargées. La raison en est la désignation du nom de la DLL *Perl*. Et comme les DLL d'extension se lient à la DLL Perl, les DLL d'extension pour les anciennes versions chargeraient une ancienne DLL Perl et échoueraient très probablement (car les données de cette DLL ne sont pas correctement initialisées).

Il existe une solution de contournement partielle (qui peut être rendue complète avec des noyaux OS/2 plus récents) : créer une DLL de redirection avec le même nom que la DLL de l'ancienne version de Perl, qui redirige les points d'entrée vers la DLL de la nouvelle version de Perl. Rendre cette DLL accessible sur (par exemple) "BEGINLIBPATH" du nouvel exécutable Perl. Lorsque le nouvel exécutable accède aux DLL d'extension de l'ancienne version de Perl, elles demanderaient la DLL de l'ancienne version de Perl par nom, obtiendraient la DLL de redirection à la place, et se lieraient ainsi effectivement à la DLL Perl actuellement en cours d'exécution (la nouvelle).

Cela peut échouer de deux manières :

  • L'ancien exécutable Perl est lancé lorsqu'un nouvel exécutable est en cours d'exécution a chargé une extension compilée pour l'ancien exécutable (oups !). Dans ce cas, l'ancien exécutable obtiendra une DLL de redirection au lieu de l'ancienne DLL Perl, et se liera donc à la nouvelle DLL Perl. Bien que pas directement fatal, cela se comportera de la même manière que le nouvel exécutable. Cela va à l'encontre de l'objectif principal de lancer explicitement un ancien exécutable.
  • Un nouvel exécutable charge une extension compilée pour l'ancien exécutable lorsqu'un ancien exécutable Perl est en cours d'exécution. Dans ce cas, l'extension ne récupérera pas la DLL de redirection, avec des conséquences fatales.

Avec le support de "LIBPATHSTRICT", cela peut être évité - à moins que l'une des DLL ne soit lancée depuis . depuis "LIBPATH" (je ne sais pas si "LIBPATHSTRICT" affecte ce cas).

REMARQUE. À moins que les noyaux plus récents n'autorisent . dans "BEGINLIBPATH" (les anciens ne le font pas), ce désordre ne peut pas être complètement nettoyé. (Il s'avère qu'au début de 2002, . n'est pas autorisé, mais .\. l'est - et cela a le même effet.)

REMARQUE. "LIBPATHSTRICT", "BEGINLIBPATH" et "ENDLIBPATH" ne sont pas des variables d'environnement, bien que cmd.exe les émule sur les lignes "SET ...". Depuis Perl, ils peuvent être accédés par Cwd::extLibpath et Cwd::extLibpath_set.

Génération de DLL de redirection

Supposons que l'ancienne DLL soit nommée perlE0AC.dll (comme celle de 5.005_53), et que la nouvelle version soit 5.6.1. Créez un fichier perl5shim.def-leader avec

DESCRIPTION '@#perl5-porters@perl.org:5.006001#@ Perl module for 5.00553 -> Perl 5.6.1 forwarder'
CODE LOADONCALL
DATA LOADONCALL NONSHARED MULTIPLE
EXPORTS

en modifiant les versions/noms selon les besoins. Exécutez

perl -wnle "next if 0../EXPORTS/; print qq(  \"$1\")

dans le répertoire de construction de Perl (pour réduire la taille de la DLL, remplacez perl5.def par le fichier de définition de l'ancienne version de Perl, s'il existe).

gcc -Zomf -Zdll -o perlE0AC.dll perl5shim.def -s -llibperl

(ignorez les multiples "warning L4085").

Multithreading

Depuis la version 5.003_01, Perl est lié à la DLL RTL C multithread. Si Perl lui-même n'est pas compilé avec le support multithread, le malloc() de Perl ne le sera pas non plus. Cependant, les extensions peuvent utiliser plusieurs threads à leurs risques et périls.

Cela était nécessaire pour compiler "Perl/Tk" pour XFree86-OS/2 immédiatement, et pour lier avec des DLL d'autres bibliothèques utiles, qui sont généralement compilées avec "-Zmt -Zcrtdll".

Appels à des programmes externes

À la demande générale, l'appel de programmes externes par Perl a été modifié par rapport au port d'Andreas Kaiser. *Si* Perl doit appeler un programme externe *via le shell*, f:/bin/sh.exe sera appelé, ou quel que soit le remplacement, voir ""PERL_SH_DIR"".

Cela signifie que vous devez également vous procurer une copie de sh.exe (j'utilise celle de pdksh). Le chemin F:/bin ci-dessus est défini automatiquement lors de la construction pour une valeur correcte sur la machine de construction, mais il est remplaçable à l'exécution.

La compilation de Perl par lui-même serait impossible avec cmd.exe comme shell, j'ai donc choisi "sh.exe". Cela assure une compatibilité quasi à 100% avec les scripts provenant de *nix. Comme avantage supplémentaire, cela fonctionne également sous DOS si vous utilisez un port DOS de pdksh (voir "Prérequis").

Frequently asked questions

Q: How do I start an OS/2 program?

A: Use the system() function. For example:

    system('cmd.exe', '/c', 'dir');
    system('program.exe', 'arg1', 'arg2');

Note that "system()" passes arguments to "cmd.exe /c", which is the default shell.

Q: How do I start a DOS program?

A: Same way as an OS/2 program. The OS/2 system automatically runs DOS programs.

Q: How do I start a program from a different directory?

A: Use the "cd" command within the "system()" call:

    system('cmd.exe', '/c', 'cd C:\\my\\programs && myprog.exe');

Q: How do I use pipes?

A: Use the "|&" operator from "ExtUtils::MakeMaker" or define your own pipe function using the "os2pipe" function.

Q: How do I start a program in a different window?

A: Use the "start" command:

    system('cmd.exe', '/c', 'start /win myprog.exe');

Q: How do I use OS/2 specific features, like named pipes or mutexes?

A: You can use the "Win32::API" module from CPAN, which allows calling Win32 API functions (and many OS/2 API functions).

INSTALLATION

To install Perl under OS/2, follow the general instructions in the Perl installation guide.

The OS/2 port uses the standard Perl distribution. You can compile it from source or use a pre-compiled binary.

The documentation is installed in the same way as on other platforms. You can access it using the "perldoc" command.

    perldoc OS2::Process

The OS/2 port can be built using the standard Perl build process. You will need a C compiler that is compatible with OS/2, such as EMX or Microsoft C/C++.

    perl Configure -de -Dtargetarch=os2-glibc

Follow the instructions provided by the "Configure" script.

Perl scripts can be compiled into standalone OS/2 executables using the "perlapp" tool. This tool is part of the Perl distribution and can be found in the "utils" directory.

To use "perlapp", run it from the command line with the path to your Perl script as an argument:

    perlapp your_script.pl

This will create an executable file named "your_script.exe" in the current directory.

Specific (mis)features of OS/2 port

The OS/2 port of Perl has some specific behaviors and limitations that you should be aware of.

Perl flavors

There are two main flavors of Perl available for OS/2:

This is the standard Perl interpreter linked against the OS/2 DLLs. It provides the most features and is generally recommended.
Static Perl
This is a statically linked version of Perl that does not depend on any external DLLs. It is useful for creating standalone executables or when you need to minimize dependencies.

The choice between DLL Perl and Static Perl depends on your specific needs and environment.

Evolution

The OS/2 port of Perl has evolved significantly over time. Early versions were based on the EMX environment, while later versions are more closely integrated with the native OS/2 API.

The current version of the OS/2 port is based on the standard Perl source code and includes OS/2-specific adaptations. It is actively developed and maintained.

One notable change is the way external programs are invoked. In earlier versions, "system()" directly called "cmd.exe /c". This behavior has been modified to allow more flexibility in how external programs are executed.

If you have some working code for "OS2::Cmd", please send it to me, I will include it into distribution. I have no need for such a module, so cannot test it.

For the details of the current situation with calling external programs, see "Starting OS/2 (and DOS) programs under Perl". Set us mention a couple of features:

  • External scripts may be called by their basename. Perl will try the same extensions as when processing -S command-line switch.
  • External scripts starting with "#! " or "extproc " will be executed directly, without calling the shell, by calling the program specified on the rest of the first line.

Memory allocation

Perl uses its own malloc() under OS/2 - interpreters are usually malloc-bound for speed, but perl is not, since its malloc is lightning-fast. Perl-memory-usage-tuned benchmarks show that Perl's malloc is 5 times quicker than EMX one. I do not have convincing data about memory footprint, but a (pretty random) benchmark showed that Perl's one is 5% better.

Combination of perl's malloc() and rigid DLL name resolution creates a special problem with library functions which expect their return value to be free()d by system's free(). To facilitate extensions which need to call such functions, system memory-allocation functions are still available with the prefix "emx_" added. (Currently only DLL perl has this, it should propagate to perl_.exe shortly.)

Threads

One can build perl with thread support enabled by providing "-D usethreads" option to Configure. Currently OS/2 support of threads is very preliminary.

Most notable problems:

"COND_WAIT"
may have a race condition (but probably does not due to edge-triggered nature of OS/2 Event semaphores). (Needs a reimplementation (in terms of chaining waiting threads, with the linked list stored in per-thread structure?)?)
os2.c
has a couple of static variables used in OS/2-specific functions. (Need to be moved to per-thread structure, or serialized?)

Note that these problems should not discourage experimenting, since they have a low probability of affecting small programs.
