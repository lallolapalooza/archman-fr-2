PERLIPC(1perl) Guide du programmeur Perl PERLIPC(1perl)

NOM

perlipc - communication inter-processus Perl (signaux, tubes nommés, tubes, processus fils sûrs, sockets et sémaphores)

DESCRIPTION

Les installations de communication inter-processus de base de Perl sont construites à partir des bonnes vieilles routines Unix de signaux, de tubes nommés, d'ouvertures de tubes, des routines de socket Berkeley et des appels IPC SysV. Chacun est utilisé dans des situations légèrement différentes.

Signaux

Perl utilise un modèle simple de gestion des signaux : le tableau associatif %SIG contient les noms ou les références des gestionnaires de signaux installés par l'utilisateur. Ces gestionnaires seront appelés avec un argument qui est le nom du signal qui les a déclenchés. Un signal peut être généré intentionnellement à partir d'une séquence de touches particulière comme Ctrl-C ou Ctrl-Z, vous être envoyé par un autre processus, ou déclenché automatiquement par le noyau lorsque des événements spéciaux se produisent, comme la sortie d'un processus fils, votre propre processus manquant d'espace de pile, ou atteignant une limite de taille de fichier de processus.

Par exemple, pour intercepter un signal d'interruption, configurez un gestionnaire comme suit :

our $shucks;
sub catch_zap {
    my $signame = shift;
    $shucks++;
    die "Quelqu'un m'a envoyé un SIG$signame";
}
$SIG{INT} = __PACKAGE__ . "::catch_zap";
$SIG{INT} = \&catch_zap;  # meilleure stratégie

Avant Perl 5.8.0, il était nécessaire de faire le moins de choses possible dans votre gestionnaire ; remarquez que tout ce que nous faisons est de définir une variable globale puis de lever une exception. C'est parce que sur la plupart des systèmes, les bibliothèques ne sont pas réentrantes ; en particulier, les routines d'allocation de mémoire et d'E/S ne le sont pas. Cela signifiait que faire presque *n'importe quoi* dans votre gestionnaire pouvait en théorie déclencher une erreur de mémoire et un dump de mémoire subséquent - voir "Signaux différés (Signaux sûrs)" ci-dessous.

Les noms des signaux sont ceux listés par "kill -l" sur votre système, ou vous pouvez les récupérer en utilisant le module CPAN IPC::Signal.

Vous pouvez également choisir d'assigner les chaînes "IGNORE" ou "DEFAULT" comme gestionnaire, auquel cas Perl essaiera de rejeter le signal ou de faire l'action par défaut.

Sur la plupart des plateformes Unix, le signal "CHLD" (parfois aussi connu sous le nom de "CLD") a un comportement spécial par rapport à la valeur "IGNORE". Définir $SIG{CHLD} à "IGNORE" sur une telle plateforme a pour effet de ne pas créer de processus zombies lorsque le processus parent ne parvient pas à wait() sur ses processus fils (c'est-à-dire que les processus fils sont automatiquement récupérés). Appeler wait() avec $SIG{CHLD} défini à "IGNORE" renvoie généralement -1 sur de telles plateformes.

Certains signaux ne peuvent être ni interceptés ni ignorés, tels que les signaux KILL et STOP (mais pas TSTP). Notez qu'ignorer les signaux les fait disparaître. Si vous voulez seulement les bloquer temporairement sans qu'ils soient perdus, vous devrez utiliser le module POSIX' "POSIX" sigprocmask.

Envoyer un signal à un identifiant de processus négatif signifie que vous envoyez le signal à tout le groupe de processus Unix. Ce code envoie un signal de suspension à tous les processus du groupe de processus courant, et définit également $SIG{HUP} à "IGNORE" pour qu'il ne se tue pas lui-même :

# portée de bloc pour local
{
    local $SIG{HUP} = "IGNORE";
    kill HUP => -getpgrp();
    # écriture stylée de : kill("HUP", -getpgrp())
}

Un autre signal intéressant à envoyer est le signal numéro zéro. Cela n'affecte pas réellement un processus fils, mais vérifie plutôt s'il est en vie ou s'il a changé ses UID.

unless (kill 0 => $kid_pid) {
    warn "quelque chose de mal est arrivé à $kid_pid";
}

Le signal numéro zéro peut échouer parce que vous n'avez pas la permission d'envoyer le signal lorsqu'il est dirigé vers un processus dont l'UID réel ou sauvegardé n'est pas identique à l'UID réel ou effectif du processus émetteur, même si le processus est en vie. Vous pourriez être capable de déterminer la cause de l'échec en utilisant $! ou "%!".

unless (kill(0 => $pid) || $!{EPERM}) {
    warn "$pid semble mort";
}

Vous pourriez également vouloir utiliser des fonctions anonymes pour des gestionnaires de signaux simples :

$SIG{INT} = sub { die "\nDehors !\n" };

Les gestionnaires de SIGCHLD nécessitent des précautions particulières. Si un deuxième fils meurt pendant que le gestionnaire de signaux causé par la première mort est en cours d'exécution, nous ne recevrons pas d'autre signal. Il faut donc boucler ici sinon nous laisserons le fils non récupéré comme un zombie. Et la prochaine fois que deux fils meurent, nous obtenons un autre zombie. Et ainsi de suite.

use POSIX ":sys_wait_h";
$SIG{CHLD} = sub {
    while ((my $child = waitpid(-1, WNOHANG)) > 0) {
        $Kid_Status{$child} = $?;
    }
};
# faire quelque chose qui fork...

Soyez prudent : qx(), system(), et certains modules pour appeler des commandes externes font un fork(), puis wait() pour le résultat. Ainsi, votre gestionnaire de signaux sera appelé. Parce que wait() a déjà été appelé par system() ou qx(), le wait() dans le gestionnaire de signaux ne verra plus de zombies et bloquera donc.

La meilleure façon d'éviter ce problème est d'utiliser waitpid(), comme dans l'exemple suivant :

use POSIX ":sys_wait_h"; # pour la lecture non bloquante
my %children;
$SIG{CHLD} = sub {
    # ne pas changer $! et $? en dehors du gestionnaire
    local ($!, $?);
    while ( (my $pid = waitpid(-1, WNOHANG)) > 0 ) {
        delete $children{$pid};
        cleanup_child($pid, $?);
    }
};
while (1) {
    my $pid = fork();
    die "impossible de forker" unless defined $pid;
    if ($pid == 0) {
        # ...
        exit 0;
    } else {
        $children{$pid}=1;
        # ...
        system($command);
        # ...
   }
}

La gestion des signaux est également utilisée pour les délais d'attente sous Unix. Tout en étant prudemment protégé dans un bloc "eval{}", vous définissez un gestionnaire de signaux pour intercepter les signaux d'alarme, puis vous planifiez la livraison d'un signal à vous-même dans un certain nombre de secondes. Ensuite, vous essayez votre opération bloquante, effaçant l'alarme une fois qu'elle est terminée mais pas avant d'avoir quitté votre bloc "eval{}". Si elle se déclenche, vous utiliserez die() pour sortir du bloc.

Voici un exemple :

my $ALARM_EXCEPTION = "redémarrage de l'horloge d'alarme";
eval {
    local $SIG{ALRM} = sub { die $ALARM_EXCEPTION };
    alarm 10;
    flock($fh, 2)    # verrouillage d'écriture bloquant
                    || die "impossible de verrouiller: $!";
    alarm 0;
};
if ($@ && $@ !~ quotemeta($ALARM_EXCEPTION)) { die }

Si l'opération qui expire est system() ou qx(), cette technique risque de générer des zombies. Si cela vous pose problème, vous devrez faire votre propre fork() et exec(), et tuer le processus fils fautif.

Pour une gestion de signaux plus complexe, vous pourriez consulter le module POSIX standard. Malheureusement, il est presque entièrement non documenté, mais le fichier ext/POSIX/t/sigaction.t de la distribution source de Perl contient quelques exemples.

Gestion du signal SIGHUP dans les daemons

Un processus qui démarre généralement lorsque le système démarre et s'arrête lorsque le système est arrêté est appelé un daemon (Disk And Execution MONitor). Si un processus daemon possède un fichier de configuration qui est modifié après le démarrage du processus, il devrait y avoir un moyen de dire à ce processus de relire son fichier de configuration sans arrêter le processus. De nombreux daemons fournissent ce mécanisme en utilisant un gestionnaire de signaux "SIGHUP". Lorsque vous voulez dire au daemon de relire le fichier, envoyez-lui simplement le signal "SIGHUP".

Appels de fonction avec exécution (plutôt que retour)

Avant Perl 5.8.0, l'installation de code Perl pour gérer les signaux vous exposait à deux dangers. Premièrement, peu de fonctions de la bibliothèque système sont réentrantes. Si le signal interrompt Perl alors qu'il exécute une fonction (comme malloc(3) ou printf(3)), et que votre gestionnaire de signaux appelle ensuite la même fonction, vous pourriez obtenir un comportement imprévisible, souvent un vidage de mémoire (core dump). Deuxièmement, Perl lui-même n'est pas réentrant aux niveaux les plus bas. Si le signal interrompt Perl alors que Perl modifie ses propres structures de données internes, un comportement de manière similaire imprévisible peut en résulter.

Il y avait deux choses que vous pouviez faire, en sachant cela : être paranoïaque ou être pragmatique. L'approche paranoïaque consistait à faire le moins possible dans votre gestionnaire de signaux. Définissez une variable entière existante qui a déjà une valeur, et retournez. Cela ne vous aide pas si vous êtes dans un appel système lent, qui va simplement redémarrer. Cela signifie que vous devez "mourir" pour sortir du gestionnaire par longjmp(3). Même cela est un peu désinvolte pour le vrai paranoïaque, qui évite "mourir" dans un gestionnaire car le système *est* contre vous. L'approche pragmatique était de dire "Je connais les risques, mais je préfère la commodité", et de faire tout ce que vous vouliez dans votre gestionnaire de signaux, en étant prêt à nettoyer les vidages de mémoire de temps en temps.

Perl 5.8.0 et versions ultérieures évitent ces problèmes en "reportant" les signaux. C'est-à-dire que lorsque le signal est délivré au processus par le système (au code C qui implémente Perl), un drapeau est défini et le gestionnaire retourne immédiatement. Ensuite, à des points "sûrs" stratégiques de l'interpréteur Perl (par exemple, lorsqu'il est sur le point d'exécuter un nouvel opcode), les drapeaux sont vérifiés et le gestionnaire de niveau Perl de %SIG est exécuté. Le schéma de "report" permet beaucoup plus de flexibilité dans le codage des gestionnaires de signaux, car nous savons que l'interpréteur Perl est dans un état sûr, et que nous ne sommes pas dans une fonction de bibliothèque système lorsque le gestionnaire est appelé. Cependant, l'implémentation diffère des Perls précédents de la manière suivante :

Opcodes longs
Comme l'interpréteur Perl ne vérifie les drapeaux de signaux que lorsqu'il est sur le point d'exécuter un nouvel opcode, un signal qui arrive pendant un opcode long (par exemple, une opération d'expression régulière sur une très grande chaîne) ne sera pas vu tant que l'opcode courant ne sera pas terminé.

Si un signal d'un type donné se déclenche plusieurs fois pendant un opcode (par exemple, à partir d'une minuterie à grains fins), le gestionnaire pour ce signal ne sera appelé qu'une seule fois, après la fin de l'opcode ; toutes les autres instances seront discardées. De plus, si la file d'attente des signaux de votre système est tellement inondée qu'il y a des signaux qui ont été levés mais pas encore capturés (et donc non reportés) au moment où un opcode se termine, ces signaux pourraient bien être capturés et reportés lors des opcodes suivants, avec des résultats parfois surprenants. Par exemple, vous pourriez voir des alarmes livrées même après avoir appelé alarm(0), car cette dernière arrête la levée des alarmes mais n'annule pas la livraison des alarmes levées mais pas encore capturées. Ne dépendez pas des comportements décrits dans ce paragraphe, car ce sont des effets secondaires de l'implémentation actuelle et pourraient changer dans les futures versions de Perl.

Interruption des E/S
Lorsqu'un signal est délivré (par exemple, SIGINT à partir d'un contrôle-C), le système d'exploitation interrompt les opérations d'E/S comme read(2), qui est utilisé pour implémenter la fonction readline() de Perl, l'opérateur "<>". Sur les anciens Perls, le gestionnaire était appelé immédiatement (et comme "read" n'est pas "dangereux", cela fonctionnait bien). Avec le schéma "reporté", le gestionnaire n'est *pas* appelé immédiatement, et si Perl utilise la bibliothèque standard "stdio" du système, cette bibliothèque peut redémarrer "read" sans retourner à Perl pour lui donner une chance d'appeler le gestionnaire %SIG. Si cela se produit sur votre système, la solution est d'utiliser la couche ":perlio" pour effectuer les E/S, du moins sur les descripteurs de fichiers que vous souhaitez pouvoir interrompre avec des signaux. (La couche ":perlio" vérifie les drapeaux de signaux et appelle les gestionnaires %SIG avant de reprendre l'opération d'E/S.)

Par défaut dans Perl 5.8.0 et versions ultérieures, la couche ":perlio" est utilisée automatiquement.

Notez qu'il n'est pas conseillé d'accéder à un descripteur de fichier dans un gestionnaire de signaux où ce signal a interrompu une opération d'E/S sur ce même descripteur. Bien que Perl essaie au moins de ne pas planter, il n'y a aucune garantie d'intégrité des données ; par exemple, certaines données pourraient être perdues ou écrites deux fois.

Certaines fonctions de bibliothèque réseau comme gethostbyname() sont connues pour avoir leurs propres implémentations de délais qui peuvent entrer en conflit avec vos délais. Si vous rencontrez des problèmes avec de telles fonctions, essayez d'utiliser la fonction sigaction() de POSIX, qui contourne les signaux sûrs de Perl. Soyez averti que cela vous expose à une possible corruption de mémoire, comme décrit ci-dessus.

Au lieu de définir $SIG{ALRM} :

local $SIG{ALRM} = sub { die "alarm" };

essayez quelque chose comme ceci :

use POSIX qw(SIGALRM);
POSIX::sigaction(SIGALRM,
                 POSIX::SigAction->new(sub { die "alarm" }))
         || die "Error setting SIGALRM handler: $!\n";

Une autre façon de désactiver localement le comportement de signalisation sûr est d'utiliser le module "Perl::Unsafe::Signals" de CPAN, qui affecte tous les signaux.

Appels système redémarrables
Sur les systèmes qui le supportaient, les anciennes versions de Perl utilisaient le drapeau SA_RESTART lors de l'installation des gestionnaires %SIG. Cela signifiait que les appels système redémarrables continuaient plutôt que de retourner lorsqu'un signal arrivait. Afin de délivrer rapidement les signaux reportés, Perl 5.8.0 et versions ultérieures *n'*utilisent *pas* SA_RESTART. Par conséquent, les appels système redémarrables peuvent échouer (avec $! défini à "EINTR") à des endroits où ils auraient précédemment réussi.

La couche par défaut ":perlio" réessaie "read", "write" et "close" comme décrit ci-dessus ; les appels "wait" et "waitpid" interrompus seront toujours réessayés.

Signaux comme "défauts"
Certains signaux comme SEGV, ILL, BUS et FPE sont générés par des erreurs d'adressage de mémoire virtuelle et des "défauts" similaires. Ceux-ci sont normalement fatals : il y a peu qu'un gestionnaire de niveau Perl puisse faire avec eux. Ainsi, Perl les délivre immédiatement plutôt que de tenter de les reporter.

Il est possible de les intercepter avec un gestionnaire %SIG (voir perlvar), mais en plus des problèmes habituels de signaux "dangereux", le signal sera probablement relancé immédiatement au retour du gestionnaire de signaux, donc un tel gestionnaire devrait "mourir" ou "sortir" à la place.

Signaux déclenchés par l'état du système d'exploitation
Sur certains systèmes d'exploitation, certains gestionnaires de signaux sont censés "faire quelque chose" avant de retourner. Un exemple peut être CHLD ou CLD, qui indique qu'un processus fils s'est terminé. Sur certains systèmes d'exploitation, le gestionnaire de signaux est censé "attendre" le processus fils terminé. Sur de tels systèmes, le schéma de signalisation reportée ne fonctionnera pas pour ces signaux : il ne fait pas l'"attente". Encore une fois, l'échec ressemblera à une boucle car le système d'exploitation réémettra le signal car il y a des processus fils terminés qui n'ont pas encore été attendus.

Si vous souhaitez retrouver l'ancien comportement des signaux malgré une possible corruption de mémoire, définissez la variable d'environnement "PERL_SIGNALS" à "unsafe". Cette fonctionnalité est apparue pour la première fois dans Perl 5.8.1.

Tubes Nommés

Un tube nommé (souvent appelé FIFO) est un ancien mécanisme de communication inter-processus Unix pour les processus communiquant sur la même machine. Il fonctionne comme les tubes anonymes classiques, sauf que les processus se rencontrent en utilisant un nom de fichier et n'ont pas besoin d'être apparentés.

Pour créer un tube nommé, utilisez la fonction POSIX::mkfifo().

use POSIX qw(mkfifo);
mkfifo($path, 0700)     ||  die "mkfifo $path failed: $!";

Vous pouvez également utiliser la commande Unix mknod(1), ou sur certains systèmes, mkfifo(1). Celles-ci peuvent ne pas être dans votre chemin normal, cependant.

# La valeur de retour du système est inversée, donc && et non ||
#
$ENV{PATH} .= ":/etc:/usr/etc";
if  (      system("mknod",  $path, "p")
        && system("mkfifo", $path) )
{
    die "mk{nod,fifo} $path failed";
}

Un fifo est pratique lorsque vous souhaitez connecter un processus à un processus non apparenté. Lorsque vous ouvrez un fifo, le programme se bloquera jusqu'à ce qu'il y ait quelque chose de l'autre côté.

Par exemple, disons que vous aimeriez que votre fichier .signature soit un tube nommé qui a un programme Perl de l'autre côté. Maintenant, chaque fois qu'un programme (comme un programme de messagerie, un lecteur de nouvelles, un programme finger, etc.) essaie de lire dans ce fichier, le programme lecteur lira la nouvelle signature de votre programme. Nous utiliserons l'opérateur de test de fichier vérifiant les tubes, -p, pour savoir si quelqu'un (ou quelque chose) a accidentellement supprimé notre fifo.

chdir();    # aller à la maison
my $FIFO = ".signature";
while (1) {
    unless (-p $FIFO) {
        unlink $FIFO;   # ignorer tout échec, sera rattrapé plus tard
        require POSIX;  # chargement différé du module lourd
        POSIX::mkfifo($FIFO, 0700)
                              || die "can't mkfi
fo $FIFO: $!"; } # la ligne suivante bloque jusqu'à ce qu'il y ait un lecteur open (my $fh, ">", $FIFO) || die "impossible d'ouvrir $FIFO: $!"; print $fh "John Smith (smith\@host.org)\n", `fortune -s`; close($fh) || die "impossible de fermer $FIFO: $!"; sleep 2; # pour éviter les signaux en double }

Utilisation de open() pour l'IPC

L'instruction de base open() de Perl peut également être utilisée pour la communication inter-processus unidirectionnelle en spécifiant le mode d'ouverture comme "|-" ou "-|". Voici comment démarrer quelque chose dans un processus enfant auquel vous avez l'intention d'écrire :

open(my $spooler, "|-", "cat -v | lpr -h 2>/dev/null")
                    || die "impossible de forker: $!";
local $SIG{PIPE} = sub { die "le tuyau du spooler est cassé" };
print $spooler "du contenu\n";
close $spooler      || die "spool incorrect: $! $?";

Et voici comment démarrer un processus enfant dont vous avez l'intention de lire :

open(my $status, "-|", "netstat -an 2>&1")
                    || die "impossible de forker: $!";
while (<$status>) {
    next if /^(tcp|udp)/;
    print;
}
close $status       || die "netstat incorrect: $! $?";

Soyez conscient que ces opérations sont des forks Unix complets, ce qui signifie qu'ils peuvent ne pas être correctement implémentés sur tous les systèmes étrangers. Voir "open" dans perlport pour les détails de portabilité.

Dans la forme à deux arguments de open(), une ouverture de tuyau peut être réalisée en ajoutant ou en préfixant un symbole de tuyau au deuxième argument :

open(my $spooler, "| cat -v | lpr -h 2>/dev/null")
                    || die "impossible de forker: $!";
open(my $status, "netstat -an 2>&1 |")
                    || die "impossible de forker: $!";

Cela peut être utilisé même sur les systèmes qui ne prennent pas en charge le fork, mais cela permet potentiellement à du code destiné à lire des fichiers d'exécuter de manière inattendue des programmes. Si l'on peut être sûr qu'un programme particulier est un script Perl attendant des noms de fichiers dans @ARGV en utilisant la forme à deux arguments de open() ou l'opérateur "<>", le programmeur avisé peut écrire quelque chose comme ceci :

% program f1 "cmd1|" - f2 "cmd2|" f3 < tmpfile

et peu importe le type de shell à partir duquel il est appelé, le programme Perl lira à partir du fichier f1, du processus cmd1, de l'entrée standard (tmpfile dans ce cas), du fichier f2, de la commande cmd2, et enfin du fichier f3. Plutôt astucieux, hein ?

Vous pourriez remarquer que vous pourriez utiliser des backticks pour un effet similaire à l'ouverture d'un tuyau pour la lecture :

print grep { !/^(tcp|udp)/ } `netstat -an 2>&1`;
die "mauvais statut netstat ($?)" if $?;

Bien que cela soit vrai en apparence, il est beaucoup plus efficace de traiter le fichier ligne par ligne ou enregistrement par enregistrement, car vous n'avez pas à lire l'intégralité en mémoire à la fois. Cela vous donne également un contrôle plus fin sur l'ensemble du processus, vous permettant de tuer le processus enfant plus tôt si vous le souhaitez.

Faites attention à vérifier les valeurs de retour de open() et close(). Si vous écrivez dans un tuyau, vous devriez également capturer SIGPIPE. Sinon, pensez à ce qui se passe lorsque vous démarrez un tuyau vers une commande qui n'existe pas : open() réussira probablement (il ne reflète que le succès de fork()), mais votre sortie échouera--spectaculairement. Perl ne peut pas savoir si la commande a fonctionné, car votre commande s'exécute en fait dans un processus séparé dont l'exec() a pu échouer. Par conséquent, tandis que les lecteurs de commandes bidons retournent juste un EOF rapide, les écrivains vers des commandes bidons recevront un signal, qu'ils feraient mieux d'être prêts à gérer. Considérez :

open(my $fh, "|-", "bogus") || die "impossible de forker: $!";
print $fh "bang\n";         #  ni nécessaire ni suffisant
                            #  pour vérifier la valeur de retour de print !
close($fh)                  || die "impossible de fermer: $!";

La raison pour laquelle la valeur de retour de print() n'est pas vérifiée est due à la mise en mémoire tampon du tuyau ; les écritures physiques sont retardées. Cela n'échouera pas avant la fermeture, et cela échouera avec un SIGPIPE. Pour le capturer, vous pourriez utiliser ceci :

$SIG{PIPE} = "IGNORE";
open(my $fh, "|-", "bogus") || die "impossible de forker: $!";
print $fh "bang\n";
close($fh)                  || die "impossible de fermer: status=$?";

Descripteurs de fichiers

Le processus principal et tout processus enfant qu'il crée partagent les mêmes descripteurs de fichiers STDIN, STDOUT et STDERR. Si les deux processus essaient d'y accéder en même temps, des choses étranges peuvent se produire. Vous pourriez également vouloir fermer ou rouvrir les descripteurs de fichiers pour l'enfant. Vous pouvez contourner cela en ouvrant votre tuyau avec open(), mais sur certains systèmes, cela signifie que le processus enfant ne peut pas survivre au parent.

Processus en Arrière-plan

Vous pouvez exécuter une commande en arrière-plan avec :

system("cmd &");

La sortie standard et l'erreur standard (et potentiellement l'entrée standard, selon votre shell) de la commande seront les mêmes que celles du parent. Vous n'aurez pas besoin de capturer SIGCHLD en raison du double fork qui se produit ; voir ci-dessous pour les détails.

Dissociation Complète de l'Enfant du Parent

Dans certains cas (démarrage de processus serveur, par exemple) vous voulez dissocier complètement le processus enfant du parent. Ceci est souvent appelé daemonisation. Un démon bien élevé va également chdir() vers le répertoire racine afin de ne pas empêcher le démontage du système de fichiers contenant le répertoire à partir duquel il a été lancé, et rediriger ses descripteurs de fichiers standards depuis et vers /dev/null afin que les sorties aléatoires ne se retrouvent pas sur le terminal de l'utilisateur.

use POSIX "setsid";
sub daemonize {
    chdir("/")                     || die "impossible de faire chdir vers /: $!";
    open(STDIN,  "<", "/dev/null") || die "impossible de lire /dev/null: $!";
    open(STDOUT, ">", "/dev/null") || die "impossible d'écrire sur /dev/null: $!";
    defined(my $pid = fork())      || die "impossible de forker: $!";
    exit if $pid;              # non-zéro maintenant signifie que je suis le parent
    (setsid() != -1)           || die "Impossible de démarrer une nouvelle session: $!";
    open(STDERR, ">&", STDOUT) || die "impossible de dupliquer stdout: $!";
}

Le fork() doit venir avant le setsid() pour s'assurer que vous n'êtes pas un leader de groupe de processus ; setsid() échouera si c'est le cas. Si votre système n'a pas la fonction setsid(), ouvrez /dev/tty et utilisez "TIOCNOTTY" ioctl() dessus à la place. Voir tty(4) pour les détails.

Les utilisateurs non Unix devraient vérifier leur module "Votre_OS::Process" pour d'autres solutions possibles.

Ouvertures de Tuyaux Sûres

Une autre approche intéressante de l'IPC est de faire passer votre programme unique à plusieurs processus et de communiquer entre eux, voire parmi eux. La forme à deux arguments de la fonction open() acceptera un argument de fichier de "-|" ou "|-" pour faire quelque chose de très intéressant : elle crée un fork enfant connecté au descripteur de fichier que vous avez ouvert. L'enfant exécute le même programme que le parent. Ceci est utile pour ouvrir en toute sécurité un fichier lors de l'exécution sous un UID ou GID assumé, par exemple. Si vous ouvrez un tuyau vers moins, vous pouvez écrire dans le descripteur de fichier que vous avez ouvert et votre enfant le trouvera dans sa STDIN. Si vous ouvrez un tuyau depuis moins, vous pouvez lire depuis le descripteur de fichier que vous avez ouvert tout ce que votre enfant écrit sur sa STDOUT.

my $PRECIOUS = "/chemin/vers/un/fichier/sûr";
my $sleep_count;
my $pid;
my $kid_to_write;
do {
    $pid = open($kid_to_write, "|-");
    unless (defined $pid) {
        warn "impossible de forker: $!";
        die "abandon" if $sleep_count++ > 6;
        sleep 10;
    }
} until defined $pid;
if ($pid) {                 # je suis le parent
    print $kid_to_write @some_data;
    close($kid_to_write)    || warn "l'enfant s'est terminé avec $?";
} else {                    # je suis l'enfant
    # baisser les permissions dans les programmes setuid et/ou setgid :
    ($>, $)) = ($<, $();
    open (my $outfile, ">", $PRECIOUS)
                            || die "impossible d'ouvrir $PRECIOUS: $!";
    while (<STDIN>) {
        print $outfile;     # STDIN de l'enfant est $kid_to_write du parent
    }
    close($outfile)         || die "impossible de fermer $PRECIOUS: $!";
    exit(0);                # n'oubliez pas ceci !!
}

Une autre utilisation courante de cette construction est lorsque vous devez exécuter quelque chose sans l'interférence du shell. Avec system(), c'est simple, mais vous ne pouvez pas utiliser un tuyau ouvert ou des backticks en toute sécurité. C'est parce qu'il n'y a aucun moyen d'empêcher le shell de mettre la main sur vos arguments. Utilisez plutôt un contrôle de plus bas niveau pour appeler exec() directement.

Voici une ouverture de tuyau ou des backticks sûrs pour la lecture :

my $pid = open(my $kid_to_read, "-|");
defined($pid)            || die "impossible de forker: $!";
if ($pid) {             # parent
    while (<$kid_to_read>) {
                        # faire quelque chose d'intéressant
    }
    close($kid_to_read)  || warn "l'enfant s'est terminé avec $?";
} else {                # enfant
    ($>, $)) = ($<, $(); # suid seulement
    exec($program, @options, @args)
                         || die "impossible d'exécuter le programme: $!";
    # NON ATTEINT
}

Et voici une ouverture de tuyau sûre pour l'écriture :

my $pid = open(my $kid_to_write, "|-");
defined($pid)            || die "impossible de forker: $!";
$SIG{PIPE} = sub { die "oops, le tuyau de $program est cassé" };
if ($pid) {             # parent
    print $kid_to_write @data;
    close($kid_to_write) || warn "l'enfant s'est terminé avec $?";
} else {                # enfant
    ($>, $)) = ($<, $();
    exec($program, @options, @args)
                         || die "impossible d'exécuter le programme: $!";
    # NON ATTEINT
}

Il est très facile de provoquer un blocage d'un processus en utilisant cette forme de open(), ou effectivement avec toute utilisation de pipe() avec plusieurs sous-processus. L'exemple ci-dessus est "sûr" car il est simple et appelle exec(). Voir "Éviter les blocages de tuyaux" pour les principes généraux de sécurité, mais il y a des pièges supplémentaires avec les ouvertures de tuyaux sûres.

En particulier, si vous avez ouvert le tuyau en utilisant "open $fh, "|-"", alors vous ne pouvez pas simplement utiliser close() dans le processus parent pour fermer un écrivain non désiré. Considérez ce code :

my $pid = open(my $writer, "|-");        # fork open a kid
defined($pid)               || die "first fork failed: $!";
if ($pid) {
    if (my $sub_pid = fork()) {
        defined($sub_pid)   || die "second fork failed: $!";
        close($writer)      || die "couldn't close writer: $!";
        # now do something else...
    }
    else {
        # first write to $writer
        # ...
        # then when finished
        close($writer)      || die "couldn't close writer: $!";
        exit(0);
    }
}
else {
    # first do something with STDIN, then
    exit(0);
}

Dans l'exemple ci-dessus, le véritable parent ne souhaite pas écrire dans le descripteur de fichier $writer, il le ferme donc. Cependant, parce que $writer a été ouvert en utilisant "open $fh, "|-"", il a un comportement spécial : le fermer appelle waitpid() (voir "waitpid" dans perlfunc), qui attend que le sous-processus se termine. Si le processus enfant finit par attendre quelque chose qui se passe dans la section marquée "do something else", vous avez un interblocage.

Cela peut également être un problème avec des sous-processus intermédiaires dans un code plus complexe, qui appelleront waitpid() sur tous les descripteurs de fichiers ouverts lors de la destruction globale - sans ordre prévisible.

Pour résoudre ce problème, vous devez utiliser manuellement pipe(), fork() et la forme de open() qui associe un descripteur de fichier à un autre, comme indiqué ci-dessous :

pipe(my $reader, my $writer)   || die "pipe failed: $!";
my $pid = fork();
defined($pid)                  || die "first fork failed: $!";
if ($pid) {
    close $reader;
    if (my $sub_pid = fork()) {
        defined($sub_pid)      || die "first fork failed: $!";
        close($writer)         || die "can't close writer: $!";
    }
    else {
        # write to $writer...
        # ...
        # then  when finished
        close($writer)         || die "can't close writer: $!";
        exit(0);
    }
    # write to $writer...
}
else {
    open(STDIN, "<&", $reader) || die "can't reopen STDIN: $!";
    close($writer)             || die "can't close writer: $!";
    # do something...
    exit(0);
}

Depuis Perl 5.8.0, vous pouvez également utiliser la forme de liste de "open" pour les pipes. C'est préférable si vous souhaitez éviter que le shell n'interprète les métacaractères qui pourraient se trouver dans votre chaîne de commande.

Donc, par exemple, au lieu d'utiliser :

open(my $ps_pipe, "-|", "ps aux") || die "can't open ps pipe: $!";

On utiliserait l'une ou l'autre de ces :

open(my $ps_pipe, "-|", "ps", "aux")
                                  || die "can't open ps pipe: $!";
my @ps_args = qw[ ps aux ];
open(my $ps_pipe, "-|", @ps_args)
                                  || die "can't open @ps_args|: $!";

Parce qu'il y a plus de trois arguments pour open(), il effectue un fork de la commande ps(1) *sans* lancer de shell, et lit sa sortie standard via le descripteur de fichier $ps_pipe. La syntaxe correspondante pour *écrire* dans des pipes de commande consiste à utiliser "|-" à la place de "-|".

C'était, il faut l'avouer, un exemple plutôt stupide, car vous utilisez des littéraux de chaîne dont le contenu est parfaitement sûr. Il n'y a donc aucune raison de recourir à la forme multi-arguments de pipe open(), plus difficile à lire. Cependant, chaque fois que vous ne pouvez pas être assuré que les arguments du programme sont exempts de métacaractères de shell, la forme plus élaborée de open() doit être utilisée. Par exemple :

my @grep_args = ("egrep", "-i", $some_pattern, @many_files);
open(my $grep_pipe, "-|", @grep_args)
                    || die "can't open @grep_args|: $!";

Ici, la forme multi-arguments de pipe open() est préférable car le motif et même les noms de fichiers peuvent contenir des métacaractères.

Éviter les interblocages de pipes

Chaque fois que vous avez plus d'un sous-processus, vous devez veiller à ce que chacun ferme la moitié des pipes créés pour la communication interprocessus qu'il n'utilise pas. En effet, tout processus enfant lisant à partir du pipe et s'attendant à un EOF ne le recevra jamais, et donc n'en sortira jamais. La fermeture d'un pipe par un seul processus n'est pas suffisante ; le dernier processus ayant le pipe ouvert doit le fermer pour qu'il lise EOF.

Certaines fonctionnalités intégrées d'Unix aident à prévenir cela la plupart du temps. Par exemple, les descripteurs de fichiers ont un indicateur "close on exec", qui est défini *en masse* sous le contrôle de la variable $^F. Cela permet de s'assurer que tous les descripteurs de fichiers que vous n'avez pas explicitement acheminés vers STDIN, STDOUT ou STDERR d'un programme enfant seront automatiquement fermés.

Appelez toujours explicitement et immédiatement close() sur l'extrémité d'écriture de tout pipe, à moins que ce processus n'écrive réellement dedans. Même si vous n'appelez pas explicitement close(), Perl fermera toujours tous les descripteurs de fichiers lors de la destruction globale. Comme discuté précédemment, si ces descripteurs de fichiers ont été ouverts avec Safe Pipe Open, cela entraînera l'appel de waitpid(), ce qui peut à nouveau provoquer un interblocage.

Communication bidirectionnelle avec un autre processus

Bien que cela fonctionne raisonnablement bien pour la communication unidirectionnelle, qu'en est-il de la communication bidirectionnelle ? L'approche la plus évidente ne fonctionne pas :

# CECI NE FONCTIONNE PAS !!
open(my $prog_for_reading_and_writing, "| some program |")

Si vous oubliez de "use warnings", vous manquerez complètement le message de diagnostic utile :

Can't do bidirectional pipe at -e line 1.

Si vous le souhaitez vraiment, vous pouvez utiliser la fonction standard open2() du module IPC::Open2 pour capturer les deux extrémités. Il existe également une fonction open3() dans IPC::Open3 pour les E/S tridirectionnelles afin que vous puissiez également capturer STDERR de votre enfant, mais cela nécessiterait une boucle select() maladroite et ne vous permettrait pas d'utiliser les opérations d'entrée Perl normales.

Si vous regardez sa source, vous verrez que open2() utilise des primitives de bas niveau comme les appels système pipe() et exec() pour créer toutes les connexions. Bien qu'il aurait pu être plus efficace en utilisant socketpair(), cela aurait été encore moins portable qu'il ne l'est déjà. Les fonctions open2() et open3() ne fonctionneront probablement nulle part sauf sur un système Unix, ou du moins sur un système qui prétend être conforme à POSIX.

Voici un exemple d'utilisation de open2() :

use IPC::Open2;
my $pid = open2(my $reader, my $writer, "cat -un");
print $writer "stuff\n";
my $got = <$reader>;
waitpid $pid, 0;

Le problème ici est que la mise en mémoire tampon va vraiment vous gâcher la journée. Même si votre descripteur de fichier $writer est automatiquement vidé pour que le processus de l'autre côté reçoive vos données en temps voulu, vous ne pouvez généralement rien faire pour forcer ce processus à vous donner ses données de manière similaire. Dans ce cas spécial, nous aurions pu le faire, car nous avons donné à *cat* un indicateur -u pour le rendre non mis en mémoire tampon. Mais très peu de commandes sont conçues pour fonctionner sur des pipes, donc cela fonctionne rarement à moins que vous n'ayez écrit vous-même le programme de l'autre côté du pipe double.

Une solution à cela consiste à utiliser une bibliothèque qui utilise des pseudo-terminaux pour que votre programme se comporte plus raisonnablement. De cette façon, vous n'avez pas besoin de contrôler le code source du programme que vous utilisez. Le module "Expect" de CPAN aborde également ce genre de chose. Ce module nécessite deux autres modules de CPAN, "IO::Pty" et "IO::Stty". Il configure un pseudo-terminal pour interagir avec les programmes qui insistent pour parler au pilote de périphérique du terminal. Si votre système est pris en charge, cela pourrait être votre meilleure solution.

Communication bidirectionnelle avec soi-même

Si vous le souhaitez, vous pouvez effectuer des appels système pipe() et fork() de bas niveau pour assembler cela à la main. Cet exemple ne communique qu'avec lui-même, mais vous pourriez réaffecter les descripteurs appropriés à STDIN et STDOUT et appeler d'autres processus. (L'exemple suivant manque de vérification d'erreurs appropriée.)

#!/usr/bin/perl
# pipe1 - communication bidirectionnelle utilisant deux paires de pipes
#         conçu pour les systèmes sans socketpair
use v5.36;
use IO::Handle;  # active la méthode autoflush avant Perl 5.14
pipe(my $parent_rdr, my $child_wtr);  # XXX: vérifier l'échec ?
pipe(my $child_rdr,  my $parent_wtr); # XXX: vérifier l'échec ?
$child_wtr->autoflush(1);
$parent_wtr->autoflush(1);
if ($pid = fork()) {
    close $parent_rdr;
    close $parent_wtr;
    print $child_wtr "Parent Pid $$ is sending this\n";
    chomp(my $line = <$child_rdr>);
    print "Parent Pid $$ just read this: '$line'\n";
    close $child_rdr; close $child_wtr;
    waitpid($pid, 0);
} else {
    die "cannot fork: $!" unless defined $pid;
    close $child_rdr;
    close $child_wtr;
    chomp(my $line = <$parent_rdr>);
    print "Child Pid $$ just read this: '$line'\n";
    print $parent_wtr "Child Pid $$ is sending this\n";
    close $parent_rdr;
    close $parent_wtr;
    exit(0);
}

Mais vous n'avez pas réellement à faire deux appels de pipe. Si vous avez l'appel système socketpair(), il fera tout cela pour vous.

#!/usr/bin/perl
# pipe2 - communication bidirectionnelle utilisant socketpair
#   "les meilleurs vont toujours dans les deux sens"
use v5.36;
use Socket;
use IO::Handle;  # active la méthode autoflush avant Perl 5.14
# Nous disons AF_UNIX car bien que *_LOCAL soit la
# forme POSIX 1003.1g de la constante, beaucoup de machines
# ne l'ont toujours pas.
socketpair(my $child, my $parent, AF_UNIX, SOCK_STREAM, PF_UNSPEC)
                            ||  die "socketpair: $!";
$child->autoflush(1);
$parent->autoflush(1);
if ($pid = fork()) {
    close $parent;
    print $child "Parent Pid $$ is sending this\n";
    chomp(my $line = <$child>);
    print "Parent Pid $$ just read this: '$line'\n";
    close $child;
    waitpid($pid, 0);
} else {
    die "cannot fork: $!" unless defined $pid;
    close $child;
    chomp(my $line = <$parent>);
    print "Child Pid $$ just read this: '$line'\n";
    print $parent "Child Pid $$ is sending this\n";
    close $parent;
    exit(0);
}

Sockets : Communication client/serveur

Sockets : Communication Client/Serveur

Bien que pas entièrement limitées aux systèmes d'exploitation dérivés d'Unix (par exemple, WinSock sur les PC fournit un support de socket, tout comme certaines bibliothèques VMS), vous n'avez peut-être pas de sockets sur votre système, auquel cas cette section ne vous sera probablement d'aucune utilité. Avec les sockets, vous pouvez réaliser à la fois des circuits virtuels comme les flux TCP et des datagrammes comme les paquets UDP. Vous pourrez peut-être faire encore plus selon votre système.

Les fonctions Perl pour traiter les sockets portent les mêmes noms que les appels système correspondants en C, mais leurs arguments ont tendance à différer pour deux raisons. Premièrement, les filehandles Perl fonctionnent différemment des descripteurs de fichiers C. Deuxièmement, Perl connaît déjà la longueur de ses chaînes de caractères, vous n'avez donc pas besoin de fournir cette information.

L'un des problèmes majeurs du code de socket ancien, d'avant le millénaire, en Perl était qu'il utilisait des valeurs codées en dur pour certaines constantes, ce qui nuisait gravement à la portabilité. Si vous voyez du code qui fait quelque chose comme définir explicitement "$AF_INET = 2", vous savez que vous allez avoir de gros problèmes. Une approche infiniment supérieure consiste à utiliser le module Socket, qui accorde de manière plus fiable l'accès aux diverses constantes et fonctions dont vous aurez besoin.

Si vous n'écrivez pas un client/serveur pour un protocole existant comme NNTP ou SMTP, vous devriez réfléchir à la manière dont votre serveur saura quand le client a fini de parler, et vice versa. La plupart des protocoles sont basés sur des messages et des réponses d'une ligne (donc une partie sait que l'autre a terminé lorsqu'un "\n" est reçu) ou des messages et réponses multilignes se terminant par un point sur une ligne vide ("\n.\n" termine un message/une réponse).

Terminaisons de lignes Internet

La terminaison de ligne Internet est "\015\012". Sous les variantes ASCII d'Unix, cela pouvait généralement s'écrire "\r\n", mais sous d'autres systèmes, "\r\n" pouvait parfois être "\015\015\012", "\012\012\015", ou quelque chose de complètement différent. Les normes spécifient l'écriture de "\015\012" pour être conforme (soyez strict dans ce que vous fournissez), mais elles recommandent également d'accepter un "\012" isolé en entrée (soyez indulgent dans ce que vous exigez). Nous n'avons pas toujours été très bons à ce sujet dans le code de ce manpage, mais à moins que vous ne soyez sur un Mac de son âge sombre pré-Unix, vous vous en sortirez probablement.

Clients et serveurs TCP Internet

Utilisez des sockets de domaine Internet lorsque vous souhaitez effectuer une communication client-serveur qui pourrait s'étendre à des machines en dehors de votre propre système.

Voici un exemple de client TCP utilisant des sockets de domaine Internet :

#!/usr/bin/perl
use v5.36;
use Socket;
my $remote  = shift || "localhost";
my $port    = shift || 2345;  # port aléatoire
if ($port =~ /\D/) { $port = getservbyname($port, "tcp") }
die "Pas de port" unless $port;
my $iaddr   = inet_aton($remote)       || die "pas d'hôte : $remote";
my $paddr   = sockaddr_in($port, $iaddr);
my $proto   = getprotobyname("tcp");
socket(my $sock, PF_INET, SOCK_STREAM, $proto)  || die "socket : $!";
connect($sock, $paddr)              || die "connect : $!";
while (my $line = <$sock>) {
    print $line;
}
close ($sock)                        || die "close : $!";
exit(0);

Et voici un serveur correspondant pour l'accompagner. Nous laisserons l'adresse comme "INADDR_ANY" afin que le noyau puisse choisir l'interface appropriée sur les hôtes multihébergés. Si vous souhaitez vous attacher à une interface particulière (comme le côté externe d'une passerelle ou d'une machine pare-feu), remplissez ceci avec votre véritable adresse à la place.

#!/usr/bin/perl -T
use v5.36;
BEGIN { $ENV{PATH} = "/usr/bin:/bin" }
use Socket;
use Carp;
my $EOL = "\015\012";
sub logmsg { print "$0 $$: @_ à ", scalar localtime(), "\n" }
my $port  = shift || 2345;
die "port invalide" unless $port =~ /^ \d+ $/x;
my $proto = getprotobyname("tcp");
socket(my $server, PF_INET, SOCK_STREAM, $proto) || die "socket : $!";
setsockopt($server, SOL_SOCKET, SO_REUSEADDR, pack("l", 1))
                                              || die "setsockopt : $!";
bind($server, sockaddr_in($port, INADDR_ANY)) || die "bind : $!";
listen($server, SOMAXCONN)                    || die "listen : $!";
logmsg "serveur démarré sur le port $port";
for (my $paddr; $paddr = accept(my $client, $server); close $client) {
    my($port, $iaddr) = sockaddr_in($paddr);
    my $name = gethostbyaddr($iaddr, AF_INET);
    logmsg "connexion depuis $name [",
            inet_ntoa($iaddr), "]
            au port $port";
    print $client "Bonjour, $name, il est maintenant ",
                    scalar localtime(), $EOL;
}

Et voici une version multitâche. Elle est multitâche dans le sens où, comme la plupart des serveurs typiques, elle crée (fait un fork()) un serveur enfant pour traiter la requête du client afin que le serveur principal puisse rapidement revenir au service d'un nouveau client.

#!/usr/bin/perl -T
use v5.36;
BEGIN { $ENV{PATH} = "/usr/bin:/bin" }
use Socket;
use Carp;
my $EOL = "\015\012";
sub spawn;  # déclaration anticipée
sub logmsg { print "$0 $$: @_ à ", scalar localtime(), "\n" }
my $port  = shift || 2345;
die "port invalide" unless $port =~ /^ \d+ $/x;
my $proto = getprotobyname("tcp");
socket(my $server, PF_INET, SOCK_STREAM, $proto) || die "socket : $!";
setsockopt($server, SOL_SOCKET, SO_REUSEADDR, pack("l", 1))
                                              || die "setsockopt : $!";
bind($server, sockaddr_in($port, INADDR_ANY)) || die "bind : $!";
listen($server, SOMAXCONN)                    || die "listen : $!";
logmsg "serveur démarré sur le port $port";
my $waitedpid = 0;
use POSIX ":sys_wait_h";
use Errno;
sub REAPER {
    local $!;   # ne pas laisser waitpid() écraser l'erreur actuelle
    while ((my $pid = waitpid(-1, WNOHANG)) > 0 && WIFEXITED($?)) {
        logmsg "récupéré $waitedpid" . ($? ? " avec sortie $?" : "");
    }
    $SIG{CHLD} = \&REAPER;  # exécrable SysV
}
$SIG{CHLD} = \&REAPER;
while (1) {
    my $paddr = accept(my $client, $server) || do {
        # réessayer si accept() a renvoyé parce qu'il a reçu un signal
        next if $!{EINTR};
        die "accept : $!";
    };
    my ($port, $iaddr) = sockaddr_in($paddr);
    my $name = gethostbyaddr($iaddr, AF_INET);
    logmsg "connexion depuis $name [",
           inet_ntoa($iaddr),
           "] au port $port";
    spawn $client, sub {
        $| = 1;
        print "Bonjour, $name, il est maintenant ",
              scalar localtime(),
              $EOL;
        exec "/usr/games/fortune"       # XXX : pourquoi pas des terminaisons de ligne « correctes »
            or confess "impossible d'exécuter fortune : $!";
    };
    close $client;
}
sub spawn {
    my $client = shift;
    my $coderef = shift;
    unless (@_ == 0 && $coderef && ref($coderef) eq "CODE") {
        confess "usage : spawn CLIENT CODEREF";
    }
    my $pid;
    unless (defined($pid = fork())) {
        logmsg "impossible de forker : $!";
        return;
    }
    elsif ($pid) {
        logmsg "créé $pid";
        return; # Je suis le parent
    }
    # sinon je suis l'enfant -- aller créer
    open(STDIN,  "<&", $client)   || die "impossible de dupliquer le client vers stdin";
    open(STDOUT, ">&", $client)   || die "impossible de dupliquer le client vers stdout";
    ## open(STDERR, ">&", STDOUT) || die "impossible de dupliquer stdout vers stderr";
    exit($coderef->());
}

Ce serveur prend la peine de cloner une version enfant via fork() pour chaque requête entrante. De cette façon, il peut gérer plusieurs requêtes à la fois, ce qui n'est pas toujours souhaitable. Même si vous ne faites pas de fork(), listen() autorisera ce nombre de connexions en attente. Les serveurs qui utilisent fork() doivent être particulièrement attentifs au nettoyage de leurs enfants morts (appelés "zombies" dans le jargon Unix), car sinon vous remplirez rapidement votre table de processus. La sous-routine REAPER est utilisée ici pour appeler waitpid() pour tous les processus enfants qui ont terminé, garantissant ainsi qu'ils se terminent proprement et ne rejoignent pas les rangs des morts-vivants.

Dans la boucle while, nous appelons accept() et vérifions s'il renvoie une valeur fausse. Cela indiquerait normalement une erreur système à signaler. Cependant, l'introduction des signaux sûrs (voir "Signaux différés (Signaux sûrs)" ci-dessus) dans Perl 5.8.0 signifie que accept() peut également être interrompu lorsque le processus reçoit un signal. Cela se produit généralement lorsqu'un des sous-processus fork()és se termine et notifie le processus parent avec un signal CHLD.

Si accept() est interrompu par un signal, $! sera défini sur EINTR. Si cela se produit, nous pouvons continuer en toute sécurité vers l'itération suivante de la boucle et un autre appel à accept(). Il est important que votre code de gestion des signaux ne modifie pas la valeur de $!, sinon ce test échouera probablement. Dans la sous-routine REAPER, nous créons une version locale de $! avant d'appeler waitpid(). Lorsque waitpid() définit $! sur ECHILD comme il le fait inévitablement lorsqu'il n'y a plus d'enfants en attente, il met à jour la copie locale et laisse l'original inchangé.

Vous devriez utiliser l'indicateur -T pour activer la vérification de la contamination (voir perlsec) même si nous ne nous exécutons pas en setuid ou setgid. C'est toujours une bonne idée pour les serveurs ou tout programme exécuté pour le compte de quelqu'un d'autre (comme les scripts CGI), car cela réduit les chances que des personnes extérieures puissent compromettre votre système. Notez que perl peut être compilé sans support de contamination. Il existe deux modes différents : dans l'un, -T ne fait silencieusement rien. Dans l'autre mode, -T entraîne une erreur fatale.

Examinons un autre client TCP. Celui-ci se connecte au service TCP "time" sur un certain nombre de machines différentes et montre à quel point leurs horloges diffèrent de celles du système sur lequel il est exécuté :

#!/usr/bin/perl
use v5.36;
use Socket;
my $SECS_OF_70_YEARS = 2208988800;

my $iaddr = gethostbyname("localhost");
my $proto = getprotobyname("tcp");
my $port = getservbyname("time", "tcp");
my $paddr = sockaddr_in(0, $iaddr);
$| = 1;
printf "%-24s %8s %s\n", "localhost", 0, ctime();
foreach my $host (@ARGV) {
    printf "%-24s ", $host;
    my $hisiaddr = inet_aton($host)     || die "hôte inconnu";
    my $hispaddr = sockaddr_in($port, $hisiaddr);
    socket(my $socket, PF_INET, SOCK_STREAM, $proto)
                                        || die "socket : $!";
    connect($socket, $hispaddr)         || die "connect : $!";
    my $rtime = pack("C4", ());
    read($socket, $rtime, 4);
    close($socket);
    my $histime = unpack("N", $rtime) - $SECS_OF_70_YEARS;

}

Clients et Serveurs TCP de Domaine Unix

C'est bien pour les clients et serveurs de domaine Internet, mais qu'en est-il des communications locales ? Bien que vous puissiez utiliser la même configuration, parfois vous ne le souhaitez pas. Les sockets de domaine Unix sont locaux à l'hôte actuel et sont souvent utilisés en interne pour implémenter des pipes. Contrairement aux sockets de domaine Internet, les sockets de domaine Unix peuvent apparaître dans le système de fichiers avec un listage ls(1).

% ls -l /dev/log
srw-rw-rw-  1 root            0 Oct 31 07:23 /dev/log

Vous pouvez tester cela avec le test de fichier -S de Perl :

unless (-S "/dev/log") {
    die "quelque chose ne va pas avec le système de log";
}

Voici un exemple de client de domaine Unix :

#!/usr/bin/perl
use v5.36;
use Socket;
my $rendezvous = shift || "catsock";
socket(my $sock, PF_UNIX, SOCK_STREAM, 0) || die "socket: $!";
connect($sock, sockaddr_un($rendezvous))  || die "connect: $!";
while (defined(my $line = <$sock>)) {
    print $line;
}
exit(0);

Et voici un serveur correspondant. Vous n'avez pas à vous soucier des terminaisons réseau stupides ici car les sockets de domaine Unix sont garantis d'être sur le localhost, et donc tout fonctionne correctement.

use Socket;
use Carp;
BEGIN { $ENV{PATH} = "/usr/bin:/bin" }

unlink($NAME);
bind  ($server, $uaddr)                     || die "bind: $!";
listen($server, SOMAXCONN)                  || die "listen: $!";
logmsg "serveur démarré sur $NAME";
my $waitedpid;
use POSIX ":sys_wait_h";
sub REAPER {
    my $child;
    while (($waitedpid = waitpid(-1, WNOHANG)) > 0) {
        logmsg "récupéré $waitedpid" . ($? ? " avec sortie $?" : "");
    }
    $SIG{CHLD} = \&REAPER;  # déteste SysV
}
$SIG{CHLD} = \&REAPER;
for ( $waitedpid = 0;
      accept(my $client, $server) || $waitedpid;
      $waitedpid = 0, close $client)
{
    next if $waitedpid;
    logmsg "connexion sur $NAME";
    spawn $client, sub {
        print "Bonjour, il est maintenant ", scalar localtime(), "\n";
        exec("/usr/games/fortune")  || die "impossible d'exécuter fortune: $!";
    };
}
sub spawn {
    my $client = shift();
    my $coderef = shift();
    unless (@_ == 0 && $coderef && ref($coderef) eq "CODE") {
        confess "usage: spawn CLIENT CODEREF";
    }
    my $pid;
    unless (defined($pid = fork())) {
        logmsg "impossible de forker: $!";
        return;
    }
    elsif ($pid) {
        logmsg "engendré $pid";
        return; # Je suis le parent
    }
    else {
        # Je suis l'enfant -- va générer
    }
    open(STDIN,  "<&", $client)
        || die "impossible de dupliquer le client vers stdin";
    open(STDOUT, ">&", $client)
        || die "impossible de dupliquer le client vers stdout";
    ## open(STDERR, ">&", STDOUT)
    ##  || die "impossible de dupliquer stdout vers stderr";
    exit($coderef->());
}

Comme vous pouvez le voir, c'est remarquablement similaire au serveur TCP de domaine Internet, à tel point, en fait, que nous avons omis plusieurs fonctions dupliquées--spawn(), logmsg(), ctime(), et REAPER()--qui sont les mêmes que dans l'autre serveur.

Alors, pourquoi voudriez-vous utiliser un socket de domaine Unix au lieu d'un pipe nommé plus simple ? Parce qu'un pipe nommé ne vous donne pas de sessions. Vous ne pouvez pas distinguer les données d'un processus de celles d'un autre. Avec la programmation de sockets, vous obtenez une session séparée pour chaque client ; c'est pourquoi accept() prend deux arguments.

Par exemple, disons que vous avez un démon serveur de base de données qui tourne depuis longtemps et auquel vous voulez que les gens puissent accéder depuis le Web, mais seulement s'ils passent par une interface CGI. Vous auriez un petit programme CGI simple qui effectue les vérifications et la journalisation que vous souhaitez, puis agit comme un client de domaine Unix et se connecte à votre serveur privé.

Un Client Simple

Voici un client qui crée une connexion TCP au service "daytime" sur le port 13 de l'hôte nommé "localhost" et imprime tout ce que le serveur là-bas se soucie de fournir.

#!/usr/bin/perl
use v5.36;
use IO::Socket;
my $remote = IO::Socket::INET->new(
                    Proto    => "tcp",
                    PeerAddr => "localhost",
                    PeerPort => "daytime(13)",
                )
             || die "impossible de se connecter au service daytime sur localhost";

Lorsque vous exécutez ce programme, vous devriez obtenir quelque chose qui ressemble à ceci :

Mer 14 Mai 08:40:46 MDT 1997

Voici ce que signifient ces paramètres du constructeur new() :

"Proto"
C'est le protocole à utiliser. Dans ce cas, le handle de socket retourné sera connecté à un socket TCP, car nous voulons une connexion orientée flux, c'est-à-dire une connexion qui se comporte à peu près comme un simple fichier. Tous les sockets ne sont pas de ce type. Par exemple, le protocole UDP peut être utilisé pour créer un socket de datagramme, utilisé pour la transmission de messages.
"PeerAddr"
C'est le nom ou l'adresse Internet de l'hôte distant sur lequel le serveur s'exécute. Nous aurions pu spécifier un nom plus long comme "www.perl.com", ou une adresse comme "207.171.7.72". À des fins de démonstration, nous avons utilisé le nom d'hôte spécial "localhost", qui devrait toujours signifier la machine actuelle sur laquelle vous vous exécutez. L'adresse Internet correspondante pour localhost est "127.0.0.1", si vous préférez l'utiliser.
"PeerPort"
C'est le nom du service ou le numéro de port auquel nous aimerions nous connecter. Nous aurions pu nous en sortir en utilisant simplement "daytime" sur des systèmes avec un fichier de services système bien configuré,[FOOTNOTE: Le fichier de services système se trouve dans /etc/services sur les systèmes de type Unix.] mais ici nous avons spécifié le numéro de port (13) entre parenthèses. L'utilisation du simple numéro aurait également fonctionné, mais les littéraux numériques rendent les programmeurs prudents nerveux.

Un Client Webget

Voici un client simple qui prend un hôte distant pour récupérer un document, puis une liste de fichiers à obtenir de cet hôte. C'est un client plus intéressant que le précédent car il envoie d'abord quelque chose au serveur avant de récupérer la réponse du serveur.

#!/usr/bin/perl
use v5.36;
use IO::Socket;
unless (@ARGV > 1) { die "usage: $0 host url ..." }
my $host = shift(@ARGV);
my $EOL = "\015\012";
my $BLANK = $EOL x 2;
for my $document (@ARGV) {
    my $remote = IO::Socket::INET->new( Proto     => "tcp",
                                        PeerAddr  => $host,
                                        PeerPort  => "http(80)",
              )     || die "impossible de se connecter à httpd sur $host";
    $remote->autoflush(1);
    print $remote "GET $document HTTP/1.0" . $BLANK;
    while ( <$remote> ) { print }
    close $remote;
}

Le serveur Web gérant le service HTTP est supposé être sur son port standard, le numéro 80. Si le serveur auquel vous essayez de vous connecter est sur un port différent, comme 1080 ou 8080, vous devriez le spécifier comme la paire nom-valeur "PeerPort => 8080". La méthode "autoflush" est utilisée sur le socket car sinon le système mettrait en mémoire tampon la sortie que nous lui envoyons. (Si vous êtes sur un Mac préhistorique, vous devrez également changer chaque "\n" dans votre code qui envoie des données sur le réseau pour qu'il soit un "\015\012" à la place.)

Se connecter au serveur n'est que la première partie du processus : une fois que vous avez la connexion, vous devez utiliser le langage du serveur. Chaque serveur sur le réseau a son propre petit langage de commande qu'il attend en entrée. La chaîne que nous envoyons au serveur commençant par "GET" est en syntaxe HTTP. Dans ce cas, nous demandons simplement chaque document spécifié. Oui, nous établissons réellement une nouvelle connexion pour chaque document, même si c'est le même hôte. C'est ainsi qu'il fallait toujours parler HTTP. Les versions récentes des navigateurs Web peuvent demander au serveur distant de laisser la connexion ouverte un peu, mais le serveur n'est pas obligé d'honorer une telle demande.

Clients TCP avec IO::Socket

Le programme a une tâche très simple : le processus parent copie tout ce qui provient du socket vers la sortie standard, tandis que le processus enfant copie simultanément tout ce qui provient de l'entrée standard vers le socket. Accomplir la même chose en utilisant un seul processus serait beaucoup plus difficile, car il est plus facile de coder deux processus pour faire une chose que de coder un processus pour faire deux choses. (Ce principe de simplicité est une pierre angulaire de la philosophie Unix, et une bonne ingénierie logicielle également, c'est probablement pourquoi il s'est étendu à d'autres systèmes.)

Voici le code :

#!/usr/bin/perl
use v5.36;
use IO::Socket;
unless (@ARGV == 2) { die "usage: $0 host port" }
my ($host, $port) = @ARGV;
# créer une connexion tcp vers l'hôte et le port spécifiés
my $handle = IO::Socket::INET->new(Proto     => "tcp",
                                   PeerAddr  => $host,
                                   PeerPort  => $port)
           || die "can't connect to port $port on $host: $!";
$handle->autoflush(1);       # pour que la sortie arrive immédiatement
print STDERR "[Connected to $host:$port]\n";
# diviser le programme en deux processus, des jumeaux identiques
die "can't fork: $!" unless defined(my $kidpid = fork());
# le bloc if{} s'exécute uniquement dans le processus parent
if ($kidpid) {
    # copier le socket vers la sortie standard
    while (defined (my $line = <$handle>)) {
        print STDOUT $line;
    }
    kill("TERM", $kidpid);   # envoyer SIGTERM à l'enfant
}
# le bloc else{} s'exécute uniquement dans le processus enfant
else {
    # copier l'entrée standard vers le socket
    while (defined (my $line = <STDIN>)) {
        print $handle $line;
    }
    exit(0);                # juste au cas où
}

La fonction "kill" dans le bloc "if" du parent est là pour envoyer un signal à notre processus enfant, qui s'exécute actuellement dans le bloc "else", dès que le serveur distant a fermé sa partie de la connexion.

Si le serveur distant envoie des données octet par octet, et que vous avez besoin de ces données immédiatement sans attendre un retour à la ligne (qui pourrait ne jamais arriver), vous pourriez souhaiter remplacer la boucle "while" dans le parent par ce qui suit :

my $byte;
while (sysread($handle, $byte, 1) == 1) {
    print STDOUT $byte;
}

Effectuer un appel système pour chaque octet que vous souhaitez lire n'est pas très efficace (pour le dire poliment), mais c'est le plus simple à expliquer et cela fonctionne raisonnablement bien.

Serveurs TCP avec IO::Socket

Comme toujours, la mise en place d'un serveur est un peu plus complexe que l'exécution d'un client. Le modèle est que le serveur crée un type spécial de socket qui ne fait rien d'autre qu'écouter sur un port particulier pour les connexions entrantes. Il le fait en appelant la méthode "IO::Socket::INET->new()" avec des arguments légèrement différents de ceux du client.

Proto
C'est le protocole à utiliser. Comme pour nos clients, nous spécifierons toujours "tcp" ici.
LocalPort
Nous spécifions un port local dans l'argument "LocalPort", ce que nous n'avons pas fait pour le client. C'est le nom du service ou le numéro de port pour lequel vous voulez être le serveur. (Sous Unix, les ports inférieurs à 1024 sont réservés au superutilisateur.) Dans notre exemple, nous utiliserons le port 9000, mais vous pouvez utiliser n'importe quel port qui n'est pas actuellement utilisé sur votre système. Si vous essayez d'en utiliser un déjà utilisé, vous obtiendrez un message "Address already in use". Sous Unix, la commande "netstat -a" affichera quels services ont actuellement des serveurs.
Listen
Le paramètre "Listen" est défini sur le nombre maximum de connexions en attente que nous pouvons accepter avant de refuser les clients entrants. Pensez-y comme à une file d'attente pour votre téléphone. Le module Socket de bas niveau a un symbole spécial pour le maximum système, qui est SOMAXCONN.
Reuse
Le paramètre "Reuse" est nécessaire pour que nous puissions redémarrer notre serveur manuellement sans attendre quelques minutes pour permettre aux tampons système de se vider.

Une fois le socket serveur générique créé à l'aide des paramètres énumérés ci-dessus, le serveur attend qu'un nouveau client s'y connecte. Le serveur se bloque dans la méthode "accept", qui accepte finalement une connexion bidirectionnelle du client distant. (Assurez-vous de lancer ce handle pour contourner la mise en tampon.)

Pour améliorer la convivialité, notre serveur invite l'utilisateur à entrer des commandes. La plupart des serveurs ne font pas cela. En raison de l'invite sans retour à la ligne, vous devrez utiliser la variante "sysread" du client interactif ci-dessus.

Ce serveur accepte une de cinq commandes différentes, renvoyant la sortie au client. Contrairement à la plupart des serveurs réseau, celui-ci ne gère qu'un seul client entrant à la fois. Les serveurs multitâches sont couverts au chapitre 16 du Camel.

Voici le code.

#!/usr/bin/perl
use v5.36;
use IO::Socket;
use Net::hostent;      # pour la version OOish de gethostbyaddr
my $PORT = 9000;       # choisir quelque chose qui n'est pas utilisé
my $server = IO::Socket::INET->new( Proto     => "tcp",
                                    LocalPort => $PORT,
                                    Listen    => SOMAXCONN,
                                    Reuse     => 1);
die "can't setup server" unless $server;
print "[Server $0 accepting clients]\n";
while (my $client = $server->accept()) {
  $client->autoflush(1);
  print $client "Welcome to $0; type help for command list.\n";
  my $hostinfo = gethostbyaddr($client->peeraddr);
  printf "[Connect from %s]\n",
         $hostinfo ? $hostinfo->name : $client->peerhost;
  print $client "Command? ";
  while ( <$client>) {
    next unless /\S/;     # ligne vide
    if    (/quit|exit/i)  { last                                      }
    elsif (/date|time/i)  { printf $client "%s\n", scalar localtime() }
    elsif (/who/i )       { print  $client `who 2>&1`                 }
    elsif (/cookie/i )    { print  $client `/usr/games/fortune 2>&1`  }
    elsif (/motd/i )      { print  $client `cat /etc/motd 2>&1`       }
    else {
      print $client "Commands: quit date who cookie motd\n";
    }
  } continue {
     print $client "Command? ";
  }
  close $client;
}

UDP : Transmission de messages

Un autre type de configuration client-serveur utilise des messages plutôt que des connexions. Les communications UDP ont une surcharge beaucoup plus faible mais offrent également moins de fiabilité, car rien ne garantit que les messages arriveront, encore moins dans l'ordre et sans corruption. Néanmoins, l'UDP offre certains avantages par rapport au TCP, notamment la possibilité de "diffuser" ou de "multidiffuser" vers un grand nombre d'hôtes de destination en même temps (généralement sur votre sous-réseau local). Si vous vous souciez excessivement de la fiabilité et que vous commencez à intégrer des vérifications dans votre système de messagerie, alors vous devriez probablement commencer par utiliser simplement le TCP.

Les datagrammes UDP ne sont pas un flux d'octets et ne doivent pas être traités comme tels. Cela rend l'utilisation de mécanismes d'E/S avec mise en tampon interne comme stdio (c'est-à-dire print() et fonctions similaires) particulièrement fastidieuse. Utilisez syswrite(), ou mieux encore send(), comme dans l'exemple ci-dessous.

Voici un programme UDP similaire au client Internet TCP exemple donné précédemment. Cependant, au lieu de vérifier un hôte à la fois, la version UDP en vérifiera plusieurs de manière asynchrone en simulant un multidiffusion, puis en utilisant select() pour attendre les E/S avec délai d'attente. Pour faire quelque chose de similaire avec TCP, vous devriez utiliser un descripteur de socket différent pour chaque hôte.

#!/usr/bin/perl
use v5.36;
use Socket;
use Sys::Hostname;
my $SECS_OF_70_YEARS = 2_208_988_800;
my $iaddr = gethostbyname(hostname());
my $proto = getprotobyname("udp");
my $port = getservbyname("time", "udp");
my $paddr = sockaddr_in(0, $iaddr); # 0 signifie laisser le noyau choisir
socket(my $socket, PF_INET, SOCK_DGRAM, $proto) || die "socket: $!";
bind($socket, $paddr)                           || die "bind: $!";
$| = 1;
printf "%-12s %8s %s\n",  "localhost", 0, scalar localtime();
my $count = 0;
for my $host (@ARGV) {
    $count++;
    my $hisiaddr = inet_aton($host)         || die "unknown host";
    my $hispaddr = sockaddr_in($port, $hisiaddr);
    defined(send($socket, 0, 0, $hispaddr)) || die "send $host: $!";
}
my $rout = my $rin = "";
vec($rin, fileno($socket), 1) = 1;
# délai d'attente après 10.0 secondes
while ($count && select($rout = $rin, undef, undef, 10.0)) {
    my $rtime = "";
    my $hispaddr = recv($socket, $rtime, 4, 0) || die "recv: $!";
    my ($port, $hisiaddr) = sockaddr_in($hispaddr);
    my $host = gethostbyaddr($hisiaddr, AF_INET);
    my $histime = unpack("N", $rtime) - $SECS_OF_70_YEARS;
    printf "%-12s ", $host;
    printf "%8d %s\n", $histime - time(), scalar localtime($histime);
    $count--;
}

Cet exemple n'inclut aucune nouvelle tentative et peut donc échouer à contacter un hôte accessible. La raison la plus évidente en est la congestion des files d'attente sur l'hôte d'envoi si le nombre d'hôtes à contacter est suffisamment important.

SysV IPC

Bien que l'IPC System V ne soit pas aussi largement utilisé que les sockets, il a toujours des utilisations intéressantes. Cependant, vous ne pouvez pas utiliser l'IPC SysV ou le mmap() de Berkeley pour partager une variable entre plusieurs processus. C'est parce que Perl réallouerait votre chaîne de caractères alors que vous ne le souhaiteriez pas. Vous pourriez vous pencher sur les modules "IPC::Shareable" ou "threads::shared" pour cela.

Voici un petit exemple montrant l'utilisation de la mémoire partagée.

use IPC::SysV qw(IPC_PRIVATE IPC_RMID S_IRUSR S_IWUSR);
my $size = 2000;
my $id = shmget(IPC_PRIVATE, $size, S_IRUSR | S_IWUSR);
defined($id)                    || die "shmget: $!";
print "shm key $id\n";
my $message = "Message #1";
shmwrite($id, $message, 0, 60)  || die "shmwrite: $!";
print "wrote: '$message'\n";
shmread($id, my $buff, 0, 60)      || die "shmread: $!";
print "read : '$buff'\n";
# le tampon de shmread est terminé par des caractères nuls.
substr($buff, index($buff, "\0")) = "";
print "un" unless $buff eq $message;
print "swell\n";

Perl Cookbook - Interprocess Communication

NOM

perlipc - Guide de cuisine Perl - Communication Inter-Processus

DESCRIPTION

Ce document fournit des exemples et des explications sur la façon d'implémenter la communication inter-processus (IPC) en utilisant Perl. Il couvre diverses méthodes, notamment les signaux, les tubes nommés, l'utilisation de open() pour l'IPC, les sockets et SysV IPC.

Signaux

Les signaux peuvent être utilisés pour la communication simple entre processus. Les signaux peuvent être envoyés à l'aide de la fonction kill().

# Sender process
my $pid = fork();
if ($pid == 0) {
    # Child process
    print "Child PID: $$\n";
    my $sig = <>; # Read signal number from stdin
    kill $sig, $pid; # Send signal to parent
    exit;
} else {
    # Parent process
    print "Parent PID: $$\n";
    $SIG{USR1} = sub { print "Received USR1 signal!\n" };
    wait;
}

Tubes nommés

Les tubes nommés (FIFO) permettent la communication entre des processus non apparentés. Ils peuvent être créés à l'aide de la fonction mkfifo().

use IPC::Open3;

# Create a named pipe
my $pipe = "/tmp/my_pipe";
mkfifo($pipe) unless -e $pipe;

my $pid = fork();

if ($pid == 0) {
    # Writer process
    open my $fh, '>', $pipe or die "Cannot open pipe for writing: $!";
    print $fh "Hello from writer!\n";
    close $fh;
} else {
    # Reader process
    open my $fh, '<', $pipe or die "Cannot open pipe for reading: $!";
    my $line = <$fh>;
    print "Reader received: $line";
    close $fh;
    unlink $pipe; # Clean up the pipe
}

Utilisation de open() pour l'IPC

La fonction open() peut être utilisée pour communiquer avec des commandes externes, ce qui permet une forme d'IPC.

open my $pipe, '-|', 'ls -l' or die "Cannot run ls: $!";
while (my $line = <$pipe>) {
    print $line;
}
close $pipe;

Sockets : Communication client/serveur

Les sockets sont la méthode standard pour la communication réseau et IPC entre processus sur différents systèmes ou sur le même système.

Clients TCP avec IO::Socket

use IO::Socket;

my $host = 'localhost';
my $port = 12345;

my $sock = IO::Socket::INET->new(
    Proto    => 'tcp',
    PeerAddr => $host,
    PeerPort => $port,
) or die "Cannot connect to $host:$port: $@";

print $sock "Hello, server!\n";
my $reply = <$sock>;
print "Server replied: $reply";
close $sock;

Serveurs TCP avec IO::Socket

use IO::Socket;

my $port = 12345;
my $server = IO::Socket::INET->new(
    Listen    => 5,
    LocalPort => $port,
    Proto     => 'tcp',
) or die "Cannot create server on port $port: $@";

print "Server listening on port $port...\n";

while (my $client = $server->accept()) {
    print "Accepted connection from ", $client->peerhost(), ":", $client->peerport(), "\n";
    my $request = <$client>;
    print "Received: $request";
    print $client "Hello, client!\n";
    close $client;
}
close $server;

UDP : Passage de messages

UDP est un protocole sans connexion souvent utilisé pour envoyer de petits messages ou des datagrammes.

# Sender
use IO::Socket;

my $sock = IO::Socket::INET->new(
    Proto     => 'udp',
) or die "Cannot create socket: $@";

my $host = 'localhost';
my $port = 12346;

$sock->send("Hello, UDP server!");

# Receiver
use IO::Socket;

my $sock = IO::Socket::INET->new(
    Proto     => 'udp',
    LocalPort => 12346,
) or die "Cannot create socket: $@";

my $data;
my $sender_addr;
$sock->recv($data, 1024, $sender_addr);
print "Received '$data' from $sender_addr\n";
close $sock;

SysV IPC

Perl fournit une interface aux primitives IPC de style System V, y compris les sémaphores, les files de messages et la mémoire partagée.

Un exemple simple utilisant les sémaphores SysV pour la synchronisation :

# This code should be placed in a separate file, e.g., 'init_sem.pl'
# It initializes a semaphore.
my $IPC_KEY = 1234;
my $semid = semget($IPC_KEY, 1, 0666 | IPC_CREAT);
die "semget: $!" unless defined $semid;
print "Semaphore ID: $semid\n";
semctl($semid, 0, SETVAL, 1); # Initialize semaphore to 1

Placez ce code dans un fichier séparé pour qu'il soit exécuté par plus d'un processus. Appelez le fichier take :

# create a semaphore
my $IPC_KEY = 1234;
my $id = semget($IPC_KEY, 0, 0);
defined($id)                    || die "semget: $!";
my $semnum  = 0;
my $semflag = 0;
# "take" semaphore
# wait for semaphore to be zero
my $semop = 0;
my $opstring1 = pack("s!s!s!", $semnum, $semop, $semflag);
# Increment the semaphore count
$semop = 1;
my $opstring2 = pack("s!s!s!", $semnum, $semop,  $semflag);
my $opstring  = $opstring1 . $opstring2;
semop($id, $opstring)   || die "semop: $!";

Placez ce code dans un fichier séparé pour qu'il soit exécuté par plus d'un processus. Appelez ce fichier give :

# "give" the semaphore
# run this in the original process and you will see
# that the second process continues
my $IPC_KEY = 1234;
my $id = semget($IPC_KEY, 0, 0);
die unless defined($id);
my $semnum  = 0;
my $semflag = 0;
# Decrement the semaphore count
my $semop = -1;
my $opstring = pack("s!s!s!", $semnum, $semop, $semflag);
semop($id, $opstring)   || die "semop: $!";

Le code IPC SysV ci-dessus a été écrit il y a longtemps, et il semble définitivement peu soigné. Pour une apparence plus moderne, consultez le module IPC::SysV.

Un petit exemple démontrant les files de messages SysV :

use IPC::SysV qw(IPC_PRIVATE IPC_RMID IPC_CREAT S_IRUSR S_IWUSR);
my $id = msgget(IPC_PRIVATE, IPC_CREAT | S_IRUSR | S_IWUSR);
defined($id)                || die "msgget failed: $!";
my $sent      = "message";
my $type_sent = 1234;
msgsnd($id, pack("l! a*", $type_sent, $sent), 0)
                            || die "msgsnd failed: $!";
msgrcv($id, my $rcvd_buf, 60, 0, 0)
                            || die "msgrcv failed: $!";
my($type_rcvd, $rcvd) = unpack("l! a*", $rcvd_buf);
if ($rcvd eq $sent) {
    print "okay\n";
} else {
    print "not okay\n";
}
msgctl($id, IPC_RMID, 0)    || die "msgctl failed: $!\n";

NOTES

La plupart de ces routines renvoient silencieusement mais poliment "undef" lorsqu'elles échouent au lieu de faire planter votre programme sur-le-champ en raison d'une exception non interceptée. (En fait, certaines des nouvelles fonctions de conversion de Socket font croak() sur de mauvais arguments.) Il est donc essentiel de vérifier les valeurs de retour de ces fonctions. Commencez toujours vos programmes de sockets de cette manière pour un succès optimal, et n'oubliez pas d'ajouter le drapeau de vérification d'altération -T à la ligne "#!" pour les serveurs :

#!/usr/bin/perl -T

BOGUES

Ces routines créent toutes des problèmes de portabilité spécifiques au système. Comme indiqué ailleurs, Perl est à la merci de vos bibliothèques C pour une grande partie de son comportement système. Il est probablement plus sûr de supposer des sémantiques SysV défaillantes pour les signaux et de s'en tenir à des opérations de sockets TCP et UDP simples ; par exemple, n'essayez pas de transmettre des descripteurs de fichiers ouverts sur un socket de datagramme UDP local si vous voulez que votre code ait une chance d'être portable.
