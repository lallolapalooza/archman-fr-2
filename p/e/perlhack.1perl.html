PERLHACK(1perl) Guide du programmeur Perl PERLHACK(1perl)

NOM

perlhack - Comment contribuer au développement de Perl

DESCRIPTION

Ce document explique comment fonctionne le développement de Perl. Il inclut des détails sur la liste de diffusion Perl 5 Porters, le dépôt de Perl, le système de suivi des bogues de Perl, les directives pour les correctifs et des commentaires sur la philosophie du développement de Perl.

GUIDE SUPER RAPIDE DES CORRECTIFS

Si vous souhaitez simplement soumettre un petit correctif, comme une correction de pod, un test pour un bogue, des corrections de commentaires, etc., c'est facile ! Voici comment faire :

  • Récupérez le dépôt source

    La source de Perl se trouve dans un dépôt git. Vous pouvez cloner le dépôt avec la commande suivante :

    % git clone https://github.com/Perl/perl5.git perl
  • Assurez-vous de suivre les derniers conseils

    Au cas où les conseils de ce guide auraient été mis à jour récemment, lisez la dernière version directement depuis la source de Perl :

    % perldoc pod/perlhack.pod
  • Créez une branche pour votre modification

    Créez une branche basée sur `blead` pour y commiter votre modification, qui sera utilisée plus tard pour l'envoyer au système de suivi des problèmes de Perl.

    % git checkout -b mychange
  • Apportez votre modification

    Hacker, hacker, hacker. Gardez à l'esprit que Perl fonctionne sur de nombreuses plateformes différentes, avec des systèmes d'exploitation différents qui ont des capacités différentes, des organisations de système de fichiers différentes, et même des jeux de caractères différents. perlhacktips donne des conseils à ce sujet.

  • Testez votre modification

    Vous pouvez exécuter tous les tests avec les commandes suivantes :

    % ./Configure -des -Dusedevel
% make test

    Continuez à hacker jusqu'à ce que les tests passent.

  • Commitez votre modification

    Commiter votre travail sauvegardera la modification *sur votre système local* :

    % git commit -a -m 'Le message de commit va ici'

    Assurez-vous que le message de commit décrit votre modification en une seule phrase. Par exemple, "Correction d'erreurs d'orthographe dans perlhack.pod".

  • Envoyez votre modification au système de suivi des problèmes de Perl

    L'étape suivante consiste à soumettre votre correctif au système de suivi des tickets du noyau de Perl.

    Créez une fork GitHub du dépôt perl5 et ajoutez-la comme distant, si vous ne l'avez pas déjà fait, comme décrit dans la documentation GitHub à https://help.github.com/en/articles/working-with-forks.

    % git remote add fork git@github.com:MonUtilisateur/perl5.git

    Pour plus d'informations, consultez "Se connecter à GitHub avec SSH" https://docs.github.com/en/free-pro-team@latest/github/authenticating-to-github/connecting-to-github-with-ssh.

    Si vous préférez utiliser une URL HTTPS pour votre "git push", consultez "Cloner avec des URL HTTPS" https://docs.github.com/en/free-pro-team@latest/github/using-git/which-remote-url-should-i-use#cloning-with-https-urls.

    % git remote add fork https://github.com/MonUtilisateur/perl5.git

    Ensuite, poussez votre nouvelle branche vers votre fork.

    % git push -u fork mychange

    Enfin, créez une demande d'extraction (Pull Request) sur GitHub depuis votre branche vers `blead` comme décrit dans la documentation GitHub à https://help.github.com/en/articles/creating-a-pull-request-from-a-fork.

  • Merci

    Les mainteneurs apprécient le temps que vous avez consacré à améliorer Perl. Merci !

  • Remerciements

    Tous les contributeurs sont crédités (par leur nom et adresse e-mail) dans le fichier AUTHORS, qui fait partie de la distribution Perl, ainsi que dans l'historique des commits Git.

    Si vous ne souhaitez pas être inclus dans le fichier AUTHORS, faites-le nous savoir. Sinon, nous considérerons votre soumission de correctif comme une permission de vous créditer dans le fichier AUTHORS.

  • La prochaine fois

    La prochaine fois que vous souhaiterez apporter un correctif, vous devrez repartir de la dernière version de Perl dans un état propre. Vérifiez que vous n'avez aucune modification locale ou fichier ajouté dans votre copie de Perl que vous souhaitez conserver, puis exécutez ces commandes :

    % git checkout blead
% git pull
% git reset --hard origin/blead
% git clean -dxf

SIGNALEMENT DE BOGUES

Si vous souhaitez signaler un bogue dans Perl, ou parcourir les bogues et les correctifs Perl existants, utilisez le système de suivi des problèmes GitHub à https://github.com/perl/perl5/issues.

Veuillez consulter les archives de la liste perl5-porters (voir ci-dessous) et/ou le système de suivi des bogues avant de soumettre un rapport de bogue. Souvent, vous constaterez que le bogue a déjà été signalé.

Vous pouvez vous connecter au système de suivi des bogues et commenter les rapports de bogues existants. Si vous avez des informations supplémentaires concernant un bogue existant, veuillez les ajouter. Cela aidera les mainteneurs à corriger le bogue.

PERL 5 PORTERS

La liste de diffusion perl5-porters (p5p) est l'endroit où la distribution standard de Perl est maintenue et développée. Les personnes qui maintennent Perl sont également appelées les "Perl 5 Porters", "p5p" ou simplement les "porters".

Une archive consultable de la liste est disponible à https://markmail.org/search/?q=perl5-porters. Il existe également une archive à https://archive.develooper.com/perl5-porters@perl.org/.

liste de diffusion perl-changes

La liste de diffusion perl5-changes reçoit une copie de chaque correctif qui est soumis aux branches de maintenance et de développement du dépôt Perl. Voir https://lists.perl.org/list/perl5-changes.html pour des informations sur l'abonnement et les archives.

#p5p sur IRC

De nombreux mainteneurs sont également actifs sur le canal <irc://irc.perl.org/#p5p>. N'hésitez pas à rejoindre le canal et à poser des questions sur le développement du noyau de Perl.

OBTENIR LA SOURCE DE PERL

Tout le code source de Perl est conservé centralement dans un dépôt Git sur github.com. Le dépôt contient de nombreuses révisions de Perl depuis Perl 1 et toutes les révisions de Perforce, le système de contrôle de version précédent.

Pour beaucoup plus de détails sur l'utilisation de git avec le dépôt Perl, veuillez consulter perlgit.

Accès en lecture via Git

Vous aurez besoin d'une copie de Git pour votre ordinateur. Vous pouvez télécharger une copie du dépôt en utilisant le protocole git :

% git clone git@github.com:Perl/perl5.git perl

Ceci clone le dépôt et crée une copie locale dans le répertoire perl.

Si vous ne pouvez pas utiliser le protocole git pour des raisons de pare-feu, vous pouvez également cloner via http :

% git clone https://github.com/Perl/perl5.git perl

Accès en lecture via le web

Vous pouvez accéder au dépôt via le web. Cela vous permet de parcourir l'arborescence, de voir les commits récents, de vous abonner aux notifications du dépôt, de rechercher des commits particuliers et plus encore. Vous pouvez y accéder à https://github.com/Perl/perl5.

Accès en écriture via git

Si vous avez un bit de commit, veuillez consulter perlgit pour plus de détails sur l'utilisation de git.

APPLIQUER DES CORRECTIFS À PERL

Si vous prévoyez de faire un travail plus important qu'une seule petite correction, nous vous encourageons à lire la documentation ci-dessous. Cela vous aidera à concentrer votre travail et à rendre vos correctifs plus faciles à intégrer dans le noyau de Perl.

source.

Soumettre des patchs

Si vous avez un petit patch à soumettre, veuillez l'envoyer via le flux de travail des Pull Requests de GitHub. Vous pouvez également envoyer des patchs à la liste p5p.

Les patchs sont examinés et discutés sur GitHub ou sur la liste p5p. Les patchs simples et non controversés sont généralement appliqués sans discussion. Lorsque le patch est appliqué, le ticket sera mis à jour et vous recevrez un e-mail.

Dans d'autres cas, le patch nécessitera plus de travail ou de discussion. Vous êtes encouragé à participer à la discussion et à défendre votre patch. Parfois, votre patch peut se perdre dans la mêlée. Il est approprié d'envoyer un e-mail de rappel à p5p si aucune action n'a été entreprise pendant un mois. N'oubliez pas que les développeurs de Perl 5 sont tous des volontaires, et soyez poli.

Les changements sont toujours appliqués directement à la branche principale de développement, appelée « blead ». Certains patchs peuvent être rétroportés vers une branche de maintenance. Si vous pensez que votre patch est approprié pour la branche de maintenance (voir « BRANCHES DE MAINTENANCE » dans perlpolicy), veuillez l'expliquer lors de sa soumission.

Faire accepter votre patch

Si vous soumettez un patch de code, vous pouvez faire plusieurs choses pour aider les Porters de Perl 5 à accepter votre patch.

Style de patch

En utilisant le flux de travail des Pull Requests de GitHub, votre patch sera automatiquement disponible dans un format approprié. Si vous souhaitez soumettre un patch à la liste p5p pour examen, assurez-vous de le créer de manière appropriée.

Si vous avez utilisé git pour extraire la source de Perl, alors utiliser "git format-patch" produira un patch dans un style adapté à Perl. La commande "format-patch" produit un fichier de patch pour chaque commit que vous avez effectué. Si vous préférez envoyer un seul patch pour tous les commits, vous pouvez utiliser "git diff".

% git checkout blead
% git pull
% git diff blead mon-nom-de-branche

Ceci produit un patch basé sur la différence entre blead et votre branche actuelle. Il est important de s'assurer que blead est à jour avant de produire le diff, c'est pourquoi nous appelons "git pull" en premier.

Nous vous recommandons fortement d'utiliser git si possible. Cela vous facilitera la vie, ainsi qu'à nous.

Cependant, si vous n'utilisez pas git, vous pouvez toujours produire un patch approprié. Vous aurez besoin d'une copie vierge de la source de Perl pour faire la différence. Les porters préfèrent les diffs unifiés. En utilisant le diff GNU, vous pouvez produire un diff comme celui-ci :

% diff -Npurd perl.vierge perl.mien

Assurez-vous de faire "make realclean" dans votre copie de Perl pour supprimer tous les artefacts de construction, sinon vous pourriez obtenir un résultat déroutant.

Message de commit

Lorsque vous créez chaque patch que vous avez l'intention de soumettre au cœur de Perl, il est important d'écrire un bon message de commit. Ceci est particulièrement important si votre soumission consiste en une série de commits.

La première ligne du message de commit doit être une courte description sans point final. Elle ne doit pas dépasser la ligne d'objet d'un e-mail, 50 caractères étant une bonne règle générale.

Beaucoup d'outils Git (Gitweb, GitHub, git log --pretty=oneline, ...) n'afficheront que la première ligne (tronquée à 50 caractères) lors de la présentation des résumés de commit.

Le message de commit doit inclure une description du problème que le patch corrige ou de la nouvelle fonctionnalité que le patch ajoute.

En règle générale, votre message de commit doit aider un programmeur qui connaît le cœur de Perl à comprendre rapidement ce que vous essayiez de faire, comment vous essayiez de le faire, et pourquoi le changement est important pour Perl.

  • Pourquoi

    Votre message de commit doit décrire pourquoi le changement que vous apportez est important. Lorsque quelqu'un examinera votre changement dans six mois ou six ans, votre intention doit être claire.

    Si vous dépréciez une fonctionnalité dans l'intention de simplifier plus tard une autre partie du code, dites-le. Si vous corrigez un problème de performance ou ajoutez une nouvelle fonctionnalité pour prendre en charge une autre partie du cœur, mentionnez-le.

  • Quoi

    Votre message de commit doit décrire quelle partie du cœur de Perl vous modifiez et ce que vous attendez de votre patch.

  • Comment

    Bien que ce ne soit pas nécessaire pour les changements de documentation, les nouveaux tests ou les patchs triviaux, il est souvent utile d'expliquer comment fonctionne votre changement. Même si c'est clair pour vous aujourd'hui, cela pourrait ne pas l'être pour un porteur le mois prochain ou l'année prochaine.

Un message de commit n'est pas destiné à remplacer les commentaires dans votre code. Les messages de commit doivent décrire le changement que vous avez apporté, tandis que les commentaires de code doivent décrire l'état actuel du code.

Si vous venez d'implémenter une nouvelle fonctionnalité, avec la documentation, les tests et un code bien commenté, un court message de commit suffira souvent. Si, cependant, vous venez de modifier un seul caractère au plus profond de l'analyseur ou du lexer, vous pourriez avoir besoin d'écrire un petit roman pour vous assurer que les lecteurs futurs comprennent ce que vous avez fait et pourquoi vous l'avez fait.

Commentaires, commentaires, commentaires

Assurez-vous de commenter adéquatement votre code. Bien que commenter chaque ligne soit inutile, tout ce qui tire parti des effets secondaires des opérateurs, qui crée des changements qui seront ressentis en dehors de la fonction modifiée, ou que d'autres pourraient trouver déroutant doit être documenté. Si vous devez faire une erreur, il vaut mieux faire une erreur en ajoutant trop de commentaires que pas assez.

Les meilleurs commentaires expliquent *pourquoi* le code fait ce qu'il fait, pas *ce qu'il fait*.

Style

En général, veuillez suivre le style particulier du code que vous modifiez.

En particulier, suivez ces directives générales pour patcher les sources de Perl :

  • Indentation de 4 espaces pour le code, 2 espaces pour les #define CPP imbriqués, avec des tabulations de 8 espaces.
  • Utilisez des espaces pour l'indentation, pas des caractères de tabulation.

    La base de code mélange des tabulations et des espaces pour l'indentation, et nous passons à des espaces uniquement. La conversion des lignes que vous modifiez des tabulations de 8 espaces en espaces aidera cette migration.

  • Essayez de ne pas dépasser 79 colonnes

    En général, nous visons des lignes de 80 colonnes. Lorsque le respect des 80 colonnes entraînerait un code tortueux ou un remaniement, il est acceptable de dépasser. Essayez de minimiser votre dépassement au-delà de 80.

  • Prototypes C ANSI
  • Accolades non regroupées (uncuddled elses) et style « K&R » pour l'indentation des constructions de contrôle
  • Pas de commentaires style C++ (//)
  • Marquez les endroits qui nécessitent une révision avec XXX (et revoyez souvent !)
  • L'accolade d'ouverture s'aligne avec « if » lorsque la condition s'étend sur plusieurs lignes ; sinon, elle doit être en fin de ligne
  • Dans les définitions de fonction, le nom commence dans la colonne 0 (le type de valeur de retour est sur la ligne précédente)
  • Espace unique après les mots-clés suivis de parenthèses, pas d'espace entre le nom de la fonction et la parenthèse suivante
  • Évitez les affectations dans les conditions, mais si elles sont inévitables, utilisez des parenthèses supplémentaires, par exemple « if (a && (b = c)) ... »
  • « return foo; » plutôt que « return(foo); »
  • « if (!foo) ... » plutôt que « if (foo == FALSE) ... », etc.
  • Ne déclarez pas de variables en utilisant « register ». Cela peut être contre-productif avec les compilateurs modernes et est déprécié en C++, sous lequel les sources de Perl sont régulièrement compilées.
  • Les fonctions en ligne dans les en-têtes accessibles au code XS doivent pouvoir compiler sans avertissements avec des indicateurs de compilation supplémentaires couramment utilisés, tels que l'indicateur de gcc "-Wswitch-default", qui avertit chaque fois qu'une instruction switch n'a pas de cas « default ». L'utilisation de ces indicateurs supplémentaires vise à détecter les problèmes potentiels dans du code C légal, et est souvent utilisée par les agrégateurs Perl, tels que les distributeurs Linux.

Suite de tests

Si votre patch modifie du code (plutôt que de simplement modifier la documentation), vous devriez également inclure un ou plusieurs cas de test qui illustrent le bug que vous corrigez ou valident la nouvelle fonctionnalité que vous ajoutez. En général, vous devriez mettre à jour un fichier de test existant plutôt que d'en créer un nouveau.

Vos ajouts à la suite de tests devraient généralement suivre ces directives (par la courtoisie de Gurusamy Sarathy <gsar@activestate.com>) :

  • Sachez ce que vous testez. Lisez la documentation et le code source.
  • Tendez à échouer, pas à réussir.
  • Interprétez les résultats strictement.
  • Utilisez des fonctionnalités non liées (cela révélera des interactions bizarres).
  • Utilisez des idiomes non standard (sinon, vous ne testez pas TIMTOWTDI).
  • Évitez d'utiliser des numéros de test codés en dur autant que possible (le système EXPECTED/GOT trouvé dans t/op/tie.t est beaucoup plus maintenable et donne de meilleurs rapports d'échec).
  • Donnez des messages d'erreur significatifs en cas d'échec d'un test.
  • Évitez d'utiliser qx// et system() sauf si vous les testez. Si vous les utilisez, assurez-vous de couvrir *toutes* les plateformes Perl.
  • Supprimez les fichiers temporaires que vous créez.
  • Transformez les avertissements imprévus en erreurs avec $SIG{__WARN__}.
  • Assurez-vous d'utiliser les bibliothèques et les modules fournis avec la version testée, pas ceux qui étaient déjà installés.
  • Ajoutez des commentaires au code expliquant ce que vous testez.
  • Rendez la mise à jour de la chaîne '1..42' inutile. Ou assurez-vous de la mettre à jour.
  • Testez *tous* les comportements d'un opérateur, d'une bibliothèque ou d'une fonction donnée.

    Testez tous les arguments optionnels.

    Testez les valeurs de retour dans divers contextes (booléen, scalaire, liste, lvalue).

    Utilisez des variables globales et lexicales.

    N'oubliez pas les cas exceptionnels et pathologiques.

Patch d'un module cœur

Cela fonctionne comme pour patcher n'importe quoi d'autre, avec une considération supplémentaire.

Les modules du répertoire cpan/ de l'arborescence source sont maintenus en dehors du cœur de Perl. Lorsque l'auteur met à jour le module, les mises à jour sont simplement copiées dans le cœur. Consultez la documentation de ce module ou sa liste sur https://metacpan.org/ pour plus d'informations sur le signalement de bugs et la soumission de patchs.

Dans la plupart des cas, les patchs pour les modules dans cpan/ doivent être envoyés en amont (upstream) et ne doivent pas être appliqués individuellement au cœur de Perl. Si un patch pour un fichier dans cpan/ ne peut absolument pas attendre que la correction soit effectuée en amont, publiée sur CPAN et copiée dans blead, vous devez ajouter (ou mettre à jour) un fichier "C

"PERSONNALISÉ" dans l'entrée du fichier Porting/Maintainers.pl pour signaler qu'une modification locale a été apportée. Voir Porting/Maintainers.pl pour plus de détails.

En revanche, les modules du répertoire dist/ sont gérés dans le noyau.

Mise à jour de perldelta

Pour les changements suffisamment importants pour justifier une entrée dans pod/perldelta.pod, les porteurs apprécieront grandement si vous soumettez une entrée de delta avec votre modification réelle. Les changements significatifs incluent, sans s'y limiter :

  • Ajout, dépréciation ou suppression de fonctionnalités de base
  • Ajout, dépréciation, suppression ou mise à niveau de modules de base ou à double durée de vie
  • Ajout de nouveaux tests de base
  • Correction de problèmes de sécurité et de bugs visibles par l'utilisateur dans le noyau
  • Changements susceptibles de casser du code existant, au niveau de Perl ou de C
  • Améliorations significatives des performances
  • Ajout, suppression ou modification significative de la documentation dans le répertoire pod/
  • Changements importants spécifiques à la plateforme

Assurez-vous d'ajouter l'entrée perldelta à la bonne section de pod/perldelta.pod. Plus d'informations sur la manière de rédiger de bonnes entrées perldelta sont disponibles dans la section "Style" de Porting/how_to_write_a_perldelta.pod.

Qu'est-ce qui fait un bon patch ?

Les nouvelles fonctionnalités et extensions du langage peuvent être sujettes à controverse. Il n'existe pas d'ensemble spécifique de critères qui déterminent les fonctionnalités à ajouter, mais voici quelques questions à considérer lors du développement d'un patch :

Le concept correspond-il aux objectifs généraux de Perl ?

Nos objectifs incluent, sans s'y limiter :

1.
Garder la rapidité, la simplicité et l'utilité.
2.
Garder les fonctionnalités/concepts aussi orthogonaux que possible.
3.
Pas de limites arbitraires (plateformes, tailles de données, cultures).
4.
Garder Perl ouvert et passionnant à utiliser/patcher/promouvoir partout.
5.
Assimiler les nouvelles technologies ou construire des ponts vers elles.

Où est l'implémentation ?

Toutes les discussions du monde sont inutiles sans implémentation. Dans presque tous les cas, la personne ou les personnes qui plaident pour une nouvelle fonctionnalité devront l'implémenter. Les porteurs capables de coder de nouvelles fonctionnalités ont leurs propres agendas et ne sont pas disponibles pour implémenter votre idée (peut-être bonne).

Compatibilité ascendante

Casser les programmes Perl existants est un péché capital. Les nouveaux avertissements peuvent être controversés - certains disent qu'un programme qui émet des avertissements n'est pas cassé, tandis que d'autres disent qu'il l'est. L'ajout de mots-clés a le potentiel de casser des programmes, modifier le sens de séquences de jetons ou de fonctions existantes pourrait casser des programmes.

Le noyau de Perl 5 comprend des mécanismes pour aider les porteurs à rendre les changements incompatibles avec les versions antérieures plus compatibles, tels que les modules feature et deprecate. Veuillez les utiliser quand cela est approprié.

Cela pourrait-il être un module à la place ?

Perl 5 dispose de mécanismes d'extension, les modules et XS, spécifiquement pour éviter d'avoir à modifier constamment l'interpréteur Perl. Vous pouvez écrire des modules qui exportent des fonctions, vous pouvez donner à ces fonctions des prototypes afin qu'elles puissent être appelées comme des fonctions intégrées, vous pouvez même écrire du code XS pour manipuler les structures de données d'exécution de l'interpréteur Perl si vous voulez implémenter des choses vraiment compliquées.

Chaque fois que possible, les nouvelles fonctionnalités doivent être prototypées dans un module CPAN avant d'être prises en compte pour le noyau.

La fonctionnalité est-elle suffisamment générique ?

Est-ce quelque chose que seul le soumissionnaire souhaite ajouter au langage, ou est-ce largement utile ? Parfois, au lieu d'ajouter une fonctionnalité avec un objectif précis, les porteurs pourraient décider d'attendre que quelqu'un implémente la fonctionnalité plus généralisée.

Cela introduit-il potentiellement de nouveaux bugs ?

Les réécritures radicales de grandes parties de l'interpréteur Perl ont le potentiel d'introduire de nouveaux bugs.

Quelle est sa taille ?

Plus le changement est petit et localisé, mieux c'est. De même, une série de petits patches est grandement préférée à un seul gros patch.

Cela exclut-il d'autres fonctionnalités souhaitables ?

Un patch sera probablement rejeté s'il ferme des avenues de développement futures. Par exemple, un patch qui donnerait une interprétation vraie et définitive des prototypes serait probablement rejeté car il existe encore des options pour l'avenir des prototypes qui n'ont pas été abordées.

L'implémentation est-elle robuste ?

Les bons patches (code concis, complet, correct) ont plus de chances d'être intégrés. Les patches bâclés ou incorrects pourraient être mis de côté jusqu'à ce que des corrections puissent être apportées, ou ils pourraient être rejetés complètement sans préavis.

L'implémentation est-elle suffisamment générique pour être portable ?

Les pires patches utilisent des fonctionnalités spécifiques au système. Il est très peu probable que des ajouts non portables au langage Perl soient acceptés.

L'implémentation est-elle testée ?

Les patches qui modifient le comportement (correction de bugs ou introduction de nouvelles fonctionnalités) doivent inclure des tests de régression pour vérifier que tout fonctionne comme prévu.

Sans tests fournis par l'auteur original, comment quelqu'un d'autre modifiant Perl à l'avenir peut-il être sûr de ne pas avoir involontairement cassé le comportement que le patch implémente ? Et sans tests, comment l'auteur du patch peut-il être confiant que son travail acharné investi dans le patch ne sera pas accidentellement perdu par quelqu'un à l'avenir ?

Y a-t-il suffisamment de documentation ?

Les patches sans documentation sont probablement mal conçus ou incomplets. Aucune fonctionnalité ne peut être ajoutée ou modifiée sans documentation, il est donc important de soumettre un patch pour la documentation pod appropriée ainsi que pour le code source.

Y a-t-il une autre façon de faire ?

Larry a dit : « Bien que le slogan de Perl soit *Il y a plus d'une façon de* *le faire*, j'hésite à proposer 10 façons de faire quelque chose ». C'est cependant une heuristique délicate à naviguer - l'ajout essentiel pour l'un est un encombrement inutile pour l'autre.

Cela crée-t-il trop de travail ?

Du travail pour les commiteurs, du travail pour les programmeurs Perl, du travail pour les auteurs de modules, ... Perl est censé être facile.

Les patches parlent plus fort que les mots

Le code fonctionnel est toujours préférable aux idées chimériques. Un patch pour ajouter une fonctionnalité a une bien plus grande chance d'être intégré au langage qu'une demande de fonctionnalité aléatoire, aussi ardemment argumentée soit-elle. Ceci est lié à la question « Sera-t-il utile ? », car le fait que quelqu'un ait pris le temps de créer le patch démontre un fort désir pour la fonctionnalité.

TESTING

Le noyau utilise le même style de test que le reste de Perl, un simple "ok/not ok" exécuté via Test::Harness, mais il y a quelques considérations spéciales.

Il existe trois façons d'écrire un test dans le noyau : Test::More, t/test.pl et des tests ad hoc "print $test ? "ok 42\n" : "not ok 42\n"". Le choix de la méthode dépend de la partie de la suite de tests sur laquelle vous travaillez. C'est une mesure pour éviter qu'une défaillance de haut niveau (comme une panne de Config.pm) ne fasse échouer les tests de fonctionnalités de base.

La bibliothèque t/test.pl fournit certaines des fonctionnalités de Test::More, mais évite de charger la plupart des modules et utilise autant que possible les fonctionnalités de base.

Si vous écrivez votre propre test, utilisez le protocole Test Anything https://testanything.org.

  • t/base, t/comp et t/opbasic

    Comme nous ne savons pas si "require" fonctionne, ni même les sous-routines, utilisez des tests ad hoc pour ces trois-là. Procédez avec précaution pour éviter d'utiliser la fonctionnalité testée. Les tests dans t/opbasic, par exemple, y ont été placés plutôt que dans t/op car ils testent des fonctionnalités que t/test.pl suppose déjà avoir fait ses preuves.

  • Tous les autres sous-répertoires de t/

    Maintenant que les sous-routines et require() de base sont testés, vous pouvez utiliser la bibliothèque t/test.pl.

    Vous pouvez également utiliser certaines bibliothèques comme Config conditionnellement, mais assurez-vous de sauter le test gracieusement s'il n'est pas présent.

  • Fichiers de test non trouvés sous t/

    Cette catégorie comprend les fichiers .t sous des répertoires tels que dist, ext et lib. Étant donné que le noyau de Perl a maintenant été testé, Test::More peut et doit maintenant être utilisé. Vous pouvez également utiliser la suite complète de modules de base dans les tests. (Comme indiqué dans "Patching a core module" ci-dessus, les modifications des fichiers .t trouvés sous cpan/ doivent être soumises aux mainteneurs en amont de ces modules.)

Lorsque vous dites "make test", Perl utilise le programme t/TEST pour exécuter la suite de tests (sauf sous Win32 où il utilise t/harness à la place). Tous les tests sont exécutés à partir du répertoire t/, pas du répertoire qui contient le test. Cela pose des problèmes avec les tests dans lib/, il y a donc une opportunité de patching.

Vous devez être triplement conscient des préoccupations multiplateformes. Cela se résume généralement à utiliser File::Spec, éviter les choses comme fork() et system() sauf si absolument nécessaire, et ne pas supposer qu'un caractère donné a une valeur ordinale (point de code) particulière ou que sa représentation UTF-8 est composée d'octets particuliers.

Plusieurs fonctions sont disponibles pour spécifier les caractères et les points de code de manière portable dans les tests. Les fonctions toujours préchargées utf8::unicode_to_native() et son inverse utf8::native_to_unicode() prennent des points de code et traduisent de manière appropriée. Le fichier t/charset_tools.pl contient plusieurs fonctions utiles. Il a des versions des deux fonctions précédentes qui prennent des chaînes de caractères comme entrées - pas des points de code numériques uniques : uni_to_native() et native_to_uni(). Si vous devez examiner les octets individuels composant une chaîne encodée en UTF-8, byte_utf8a_to_utf8n() prend en entrée une chaîne de ces octets encodée pour une plateforme ASCII, et retourne la chaîne équivalente sur la plateforme native. Par exemple, byte_utf8a_to_utf8n("\xC2\xA0") retourne la séquence d'octets sur la plateforme actuelle qui forme l'UTF-8 de "U+00A0", puisque "\xC2\xA0" sont les octets UTF-8 sur une plateforme ASCII pour ce point de code. Cette fonction retourne "\xC2\xA0" sur une plateforme ASCII, et "\x80\x41" sur une plateforme EBCDIC 1047.

Mais le plus simple est, si le caractère est spécifiable comme une littérale, comme "A" ou "%", de l'utiliser ; sinon, vous pouvez utiliser "\N{}" , si les effets secondaires ne sont pas gênants. Spécifiez simplement tous vos caractères en hexadécimal, en utilisant "\N{U+ZZ}" au lieu de "\xZZ". "\N{}" est le nom Unicode, et il vous donne donc toujours le caractère Unicode. "\N{U+41}" est le caractère dont le point de code Unicode est 0x41, donc c'est 'A' sur toutes les plateformes. Les effets secondaires sont :

  • Ces options sélectionnent les règles Unicode. Cela signifie que dans les chaînes entre guillemets doubles, la chaîne est toujours convertie en UTF-8 pour forcer une interprétation Unicode (vous pouvez utf8::downgrade() ensuite pour reconvertir en non-UTF8, si possible). Dans les motifs d'expressions régulières, la conversion n'est pas effectuée, mais si le modificateur de jeu de caractères était autrement "/d", il est changé en "/u".
  • Si vous utilisez la forme "\N{nom du caractère}", le module charnames est automatiquement chargé. Cela peut ne pas convenir au niveau de test que vous effectuez.

Si vous testez des locales (voir perllocale), il existe des fonctions d'aide dans t/loc_tools.pl pour vous permettre de voir quelles locales existent sur la plateforme actuelle.

Cibles "make test" spéciales

Il existe diverses cibles make spéciales qui peuvent être utilisées pour tester Perl différemment de la cible standard "test". Toutes ne sont pas censées donner un taux de succès de 100 %. Beaucoup d'entre elles ont plusieurs alias, et beaucoup ne sont pas disponibles sur certains systèmes d'exploitation.

  • test_porting

    Exécute certains tests de sanity de base sur l'arbre source et aide à attraper les erreurs de base avant de soumettre un correctif.

  • minitest

    Exécute miniperl sur les tests t/base, t/comp, t/cmd, t/run, t/io, t/op, t/uni et t/mro.

    miniperl est un perl minimaliste conçu pour amorcer la construction d'extensions, d'utilitaires, de documentation, etc. Il ne prend pas en charge le chargement dynamique et, selon le point du processus de construction, n'aura accès qu'à un ensemble limité de modules principaux. miniperl n'est pas destiné à une utilisation quotidienne.

  • test.valgrind check.valgrind

    (Uniquement sous Linux) Exécute tous les tests en utilisant l'outil de détection de fuites de mémoire et d'accès mémoire non autorisés "valgrind". Les fichiers journaux seront nommés testname.valgrind.

  • test_harness

    Exécute la suite de tests avec le programme de contrôle t/harness, au lieu de t/TEST. t/harness est plus sophistiqué et utilise le module Test::Harness, donc l'utilisation de cette cible de test suppose que perl fonctionne globalement. L'avantage principal pour nos objectifs est qu'il imprime un résumé détaillé des tests échoués à la fin. De plus, contrairement à t/TEST, il ne redirige pas stderr vers stdout.

    Notez que sous Win32, t/harness est toujours utilisé à la place de t/TEST, donc il n'y a pas de cible spéciale "test_harness".

    Sous le processus de construction Unix, vous pouvez utiliser les paramètres TEST_ARGS et TEST_FILES pour passer des arguments à l'outil de gestion sous-jacent. Cela signifie que, par exemple, vous pourriez faire

    make test_harness TEST_ARGS="-v -re pat"

    ce qui compilerait, puis exécuterait l'outil de gestion de tests en mode verbeux sur les fichiers contenant "pat". Ou vous pourriez faire

    make test_harness TEST_ARGS="-torture" TEST_FILES="op/*.t"

    et exécuter les tests de torture sur les fichiers correspondant au glob "op/*.t".

    Sous Win32, la cible "test" vous permet d'utiliser les variables d'environnement TEST_SWITCHES et TEST_FILES pour contrôler le comportement de t/harness. Cela signifie que vous pouvez dire

    nmake test TEST_FILES="op/*.t"
nmake test TEST_SWITCHES="-torture" TEST_FILES="op/*.t"

    Notez que pour la compatibilité avec le processus de construction Unix, TEST_ARGS peut également être utilisé à la place de l'argument traditionnel TEST_SWITCHES.

  • test-notty test_notty

    Définit PERL_SKIP_TTY_TEST à vrai avant d'exécuter le test normal.

Tests parallèles

La distribution principale peut désormais exécuter ses tests de régression en parallèle sur les plateformes de type Unix et Windows. Sous Unix, au lieu d'exécuter "make test", définissez "TEST_JOBS" dans votre environnement au nombre de tests à exécuter en parallèle, et exécutez "make test_harness". Sur un shell de type Bourne, cela peut être fait comme suit :

TEST_JOBS=3 make test_harness  # Exécute 3 tests en parallèle

Une variable d'environnement est utilisée, plutôt que make parallèle lui-même, car TAP::Harness doit pouvoir planifier les scripts de test individuels non conflictuels lui-même, et il n'y a pas d'interface standard aux utilitaires "make" pour interagir avec leurs planificateurs de tâches.

Les tests sont normalement exécutés dans un ordre logique, avec les tests de sanity d'abord, puis les tests principaux de la fonctionnalité principale de Perl, puis les tests pour les modules non principaux. Sur les systèmes multi-cœurs, cela peut ne pas utiliser le matériel de manière aussi efficace que possible. En spécifiant également

TEST_JOBS=19 PERL_TEST_HARNESS_ASAP=1 make -j19 test_harness

vous indiquez que vous souhaitez que les tests se terminent le plus rapidement possible en temps réel. Une fois les tests de sanity terminés, cela permet d'empaqueter les tests restants dans les cœurs disponibles de la manière la plus serrée possible. Cela a le plus grand effet sur les systèmes multi-cœurs plus lents. Le débit a été accéléré de 20 % sur un système obsolète à 24 cœurs ; moins sur des systèmes plus récents et plus rapides avec moins de cœurs.

Notez que la commande ci-dessus a ajouté un paramètre "-j" à make, afin de provoquer la compilation parallèle. Cela peut ou peut ne pas fonctionner sur votre plateforme.

Normalement, les données sur la durée des tests sont stockées dans t/test_state, cependant, vous pouvez changer cela pour utiliser un nom de fichier différent en définissant la variable d'environnement "PERL_TEST_STATE_FILE" sur quelque chose de différent, ou sur une valeur fausse (0 ou une chaîne vide) pour désactiver complètement l'utilisation du mécanisme d'état. Il n'y a pas de protection contre la modification du format du fichier d'état au fil du temps, donc si vous avez des problèmes liés à ce fichier, il vous appartient de supprimer manuellement le fichier et de laisser l'outil de gestion le recréer, bien que le format du fichier ne change pas fréquemment, donc cela ne devrait pas être nécessaire très souvent.

Exécution des tests manuellement

Vous pouvez exécuter une partie de la suite de tests manuellement en utilisant l'une des commandes suivantes depuis le répertoire t/ :

./perl -I../lib TEST liste-de-fichiers-.t

ou

./perl -I../lib harness liste-de-fichiers-.t

(Si vous ne spécifiez pas de scripts de test, toute la suite de tests sera exécutée.)

Utilisation de t/harness pour les tests

Si vous utilisez "harness" pour les tests, vous disposez de plusieurs options en ligne de commande. Les arguments sont les suivants, et sont dans l'ordre dans lequel ils doivent apparaître s'ils sont utilisés ensemble.

harness -v -torture -re=pattern LISTE DE FICHIERS A TESTER
harness -v -torture -re LISTE DE MOTIFS A CORRESPONDRE

Si "LISTE DE FICHIERS A TESTER" est omis, la liste des fichiers est obtenue à partir du manifeste. La liste des fichiers peut inclure des caractères génériques de shell qui seront développés.

  • -v

    Exécute les tests en mode verbeux afin que vous puissiez voir quels tests ont été exécutés et les sorties de débogage.

  • -torture

    Exécute les tests de torture ainsi que l'ensemble normal.

  • -re=PATTERN

    Filtre la liste des fichiers de sorte que tous les fichiers de test exécutés correspondent au MOTIF. Notez que cette forme est distincte de la forme -re LISTE DE MOTIFS ci-dessous en ce qu'elle permet également de fournir la liste des fichiers.

  • -re LISTE DE MOTIFS

    Filtre la liste des fichiers de sorte que tous les fichiers de test exécutés correspondent à /(LISTE|DE|MOTIFS)/. Notez qu'avec cette forme, les motifs sont joints par '|' et vous ne pouvez pas fournir une liste de fichiers ; au lieu de cela, les fichiers de test sont obtenus à partir du MANIFESTE.

Vous pouvez exécuter un test individuel avec une commande similaire à

./perl -I../lib path/to/foo.t

sauf que les outils de gestion configurent certaines variables d'environnement qui peuvent affecter l'exécution du test :

  • PERL_CORE=1

    indique que nous exécutons ce test dans le cadre de la suite de tests principale de perl. C'est utile pour les modules qui ont une double vie sur CPAN.

  • PERL_DESTRUCT_LEVEL=2

    est défini à 2 s'il n'est pas déjà défini (voir "PERL_DESTRUCT_LEVEL" dans perlhacktips).

  • PERL

    (utilisé uniquement par t/TEST) s'il est défini, remplace le chemin d'accès à l'exécutable perl qui doit être utilisé pour exécuter les tests (par défaut ./perl).

  • PERL_SKIP_TTY_TEST

    s'il est défini, indique de sauter les tests qui nécessitent un terminal. Il est en fait défini automatiquement par le Makefile, mais peut également être forcé artificiellement en exécutant 'make test_notty'.

Autres variables d'environnement pouvant influencer les tests

  • PERL_TEST_Net_Ping

    Définir cette variable exécute tous les tests des modules Net::Ping, sinon certains tests qui interagissent avec le monde extérieur sont ignorés. Voir perl58delta.

  • PERL_TEST_NOVREXX

    Définir cette variable ignore les tests vrexx.t pour OS2::REXX.

  • PERL_TEST_NUMCONVERTS

    Définit une variable dans op/numconvert.t.

  • PERL_TEST_MEMORY

    Définir cette variable inclut le test

ts dans t/bigmem/. Ceci doit être défini au nombre de gigaoctets de mémoire disponibles pour les tests, par exemple "PERL_TEST_MEMORY=4" indique que les tests nécessitant 4Gio de mémoire disponible peuvent être exécutés en toute sécurité.

Voir aussi la documentation des modules Test et Test::Harness, pour d'autres variables d'environnement qui affectent les tests.

Tests de performance

Le fichier t/perf/benchmarks contient des extraits de code perl qui sont destinés à être benchmarkés sur une gamme de perls par l'outil Porting/bench.pl. Si vous corrigez ou améliorez un problème de performance, vous pourriez vouloir ajouter un exemple de code représentatif au fichier, puis exécuter bench.pl sur les perls précédents et actuels pour voir la différence qu'il a faite, et si autre chose a ralenti en conséquence.

Le fichier t/perf/opcount.t est conçu pour tester si un extrait de code particulier a été compilé en un optree contenant les nombres spécifiés de types d'op spécifiques. C'est bien pour tester si les optimisations qui modifient les ops, comme la conversion d'un op "aelem" en un op "aelemfast", font réellement cela.

Les fichiers t/perf/speed.t et t/re/speed.t sont conçus pour tester des choses qui s'exécutent des milliers de fois plus lentement si une optimisation particulière est cassée (par exemple, le cache de longueur utf8 sur de longues chaînes utf8). Ajoutez un test qui prendrait une fraction de seconde normalement, et des minutes autrement, provoquant le dépassement du délai d'attente du fichier de test en cas d'échec.

Compilation de perl sur d'anciens commits

Dans le cadre du piratage de la distribution principale de Perl, vous pourriez avoir besoin de configurer, compiler et tester Perl sur un ancien commit. Parfois "make" échouera pendant ce processus. Si cela se produit, vous pourrez peut-être sauver la situation en utilisant la bibliothèque Devel::PatchPerl de CPAN (non incluse dans le cœur) pour amener le code source à ce commit dans un état compilable.

Voici un exemple réel, tiré des travaux effectués pour résoudre le problème perl #10118 https://github.com/Perl/perl5/issues/10118. L'utilisation de Porting/bisect.pl avait identifié le commit "ba77e4cc9d1ceebf472c9c5c18b2377ee47062e6" comme étant le commit dans lequel un bug a été corrigé. Pour confirmer, un développeur P5P a voulu configurer et compiler Perl au commit "ba77e4c^" (probablement "mauvais") puis au commit "ba77e4c" (probablement "bon"). La configuration et la compilation normales ont été tentées :

$ sh ./Configure -des -Dusedevel
$ make test_prep

"make", cependant, a échoué avec une sortie (extraite) comme celle-ci :

cc -fstack-protector -L/usr/local/lib -o miniperl \
  gv.o toke.o perly.o pad.o regcomp.o dump.o util.o \
  mg.o reentr.o mro.o hv.o av.o run.o pp_hot.o sv.o \
  pp.o scope.o pp_ctl.o pp_sys.o doop.o doio.o regexec.o \
  utf8.o taint.o deb.o universal.o globals.o perlio.o \
  numeric.o mathoms.o locale.o pp_pack.o pp_sort.o  \
  miniperlmain.o opmini.o perlmini.o
pp.o: In function `Perl_pp_pow':
pp.c:(.text+0x2db9): undefined reference to `pow'
...
collect2: error: ld returned 1 exit status
makefile:348: recipe for target 'miniperl' failed
make: *** [miniperl] Error 1

Un autre contributeur P5P a recommandé l'installation et l'utilisation de Devel::PatchPerl pour cette situation, d'abord pour déterminer la version de Perl au commit en question, puis pour patcher le code source à ce stade afin de faciliter la compilation.

$ perl -MDevel::PatchPerl -e \
    'print Devel::PatchPerl->determine_version("/path/to/sourcecode"),
           "\n";'
5.11.1
$ perl -MDevel::PatchPerl -e \
    'Devel::PatchPerl->patch_source("5.11.1", "/path/to/sourcecode");'

Une fois le code source patché, "./Configure" et "make test_prep" ont été appelés et se sont terminés avec succès, permettant la confirmation des conclusions dans RT #72414.

    SUPER QUICK PATCH GUIDE

    If you're new to patching Perl, or just want to get a patch submitted quickly, try this:

    • Fix the bug.
    • Run make test. You should still pass.
    • Run make test_portability. You should still pass.
    • Get the latest version of Perl source from https://perl.org/ftp/pub/perl/ports/.
    • Check the code into your own repository using cvs diff or equivalent.
    • Send a patch to the perl5-porters@perl.org mailing list. Include a clear explanation of the bug, how to reproduce it, and how your patch fixes it. Explain why it's a bug, and why your fix is correct.

    If you want to be absolutely sure, run make snap, and compare your patched source tree to the results of make snap run on the pristine source tree. They should be identical.

    BUG REPORTING

    The best way to report a bug is to send a clear, concise, and reproducible bug report to the perl5-porters@perl.org mailing list. Include all the information you can. If you can provide a patch, all the better.

    We're particularly interested in bug reports for regression bugs, i.e., bugs that break code that used to work in previous releases of Perl.

    PERL 5 PORTERS

    The perl5-porters mailing list is the primary forum for discussion of Perl development. For more information, see the file PORTING in the Perl source distribution.

    GETTING THE PERL SOURCE

    The canonical place to get the latest Perl source is https://perl.org/ftp/pub/perl/ports/. You can also check out the source from the Git repository at https://github.com/Perl/perl5.

    PATCHING PERL

    Most patches are submitted in the form of unified diffs. You can generate these using the diff command:

    diff -uprN old_dir new_dir > patchfile

    Or, if you are using Git, you can generate a patch like this:

    git format-patch -u HEAD^

    The patch should include a clear explanation of what it does, why it does it, and what bug it fixes. It should also include the date and your name.

    The primary source for patches is the perl5-porters mailing list. Patches should be sent there for review.

    Please make sure that your patch doesn't break existing tests. Run make test and make test_portability before submitting.

    If you're adding a new feature, please also add corresponding tests. The tests live in the t/ directory.

    If you're adding new documentation, please add it to the pod/ directory and follow the existing style. Run make POD2HTML to see how it looks.

    When submitting a patch, please also add a line to the Changes file in the root directory detailing your patch.

    The preferred source for quotes is J.R.R. Tolkien's "The Hobbit". If you can't find anything suitable there, then you can use other Tolkien works, such as "The Lord of the Rings".

    TESTING

    After you make changes, you should always run the tests to make sure you haven't broken anything. The tests are located in the t/ directory.

    The primary test suite is run with make test. This will run all the tests in the t/ directory.

    There is also a portability test suite, run with make test_portability. This suite checks that Perl behaves correctly on a variety of platforms and compilers.

    If you're submitting a patch, you should also run make snap. This creates a tarball of the current source tree. You can compare this to a tarball created from the pristine source tree. They should be identical except for the files you have changed.

GUIDE ULTRA-RAPIDE DE PATCH

Si vous débutez avec le patching de Perl, ou si vous voulez simplement soumettre un patch rapidement, essayez ceci :

  • Corrigez le bug.
  • Lancez make test. Vous devriez toujours passer.
  • Lancez make test_portability. Vous devriez toujours passer.
  • Obtenez la dernière version de la source de Perl à l'adresse https://perl.org/ftp/pub/perl/ports/.
  • Intégrez le code dans votre propre dépôt en utilisant cvs diff ou un équivalent.
  • Envoyez un patch à la liste de diffusion perl5-porters@perl.org. Incluez une explication claire du bug, comment le reproduire, et comment votre patch le corrige. Expliquez pourquoi c'est un bug, et pourquoi votre correction est correcte.

Si vous voulez être absolument sûr, lancez make snap, et comparez votre arborescence de sources patchée avec le résultat de make snap exécuté sur l'arborescence de sources vierge. Ils devraient être identiques.

SIGNALEMENT DE BOGUES

La meilleure façon de signaler un bug est d'envoyer un rapport de bug clair, concis et reproductible à la liste de diffusion perl5-porters@perl.org. Incluez toutes les informations possibles. Si vous pouvez fournir un patch, c'est encore mieux.

Nous sommes particulièrement intéressés par les rapports de bugs de régression, c'est-à-dire les bugs qui cassent du code qui fonctionnait dans les versions précédentes de Perl.

PERL 5 PORTERS

La liste de diffusion perl5-porters est le forum principal pour la discussion du développement de Perl. Pour plus d'informations, voir le fichier PORTING dans la distribution source de Perl.

OBTENIR LES SOURCES DE PERL

L'endroit canonique pour obtenir la dernière source de Perl est https://perl.org/ftp/pub/perl/ports/. Vous pouvez également récupérer les sources du dépôt Git à l'adresse https://github.com/Perl/perl5.

PATCHER PERL

La plupart des patchs sont soumis sous forme de diffs unifiés. Vous pouvez les générer en utilisant la commande diff :

diff -uprN old_dir new_dir > patchfile

Ou, si vous utilisez Git, vous pouvez générer un patch comme ceci :

git format-patch -u HEAD^

Le patch doit inclure une explication claire de ce qu'il fait, pourquoi il le fait, et quel bug il corrige. Il doit également inclure la date et votre nom.

La source principale pour les patchs est la liste de diffusion perl5-porters. Les patchs doivent y être envoyés pour révision.

Veuillez vous assurer que votre patch ne casse pas les tests existants. Lancez make test et make test_portability avant de soumettre.

Si vous ajoutez une nouvelle fonctionnalité, veuillez également ajouter les tests correspondants. Les tests se trouvent dans le répertoire t/.

Si vous ajoutez une nouvelle documentation, veuillez l'ajouter au répertoire pod/ et suivre le style existant. Lancez make POD2HTML pour voir à quoi cela ressemble.

Lors de la soumission d'un patch, veuillez également ajouter une ligne au fichier Changes dans le répertoire racine détaillant votre patch.

La source préférée pour les citations est "Le Hobbit" de J.R.R. Tolkien. Si vous ne trouvez rien de convenable, vous pouvez utiliser d'autres œuvres de Tolkien, telles que "Le Seigneur des Anneaux".

  • The Hobbit, Allen & Unwin; pas de numéros de page modifiés pour l'édition omnibus spéciale en 3 volumes de 2002 ou pour les diverses éditions en livre de poche, toutes désormais chez Harper Collins ou Houghton Mifflin.

D'autres livres de JRRT valables pour des citations incluraient donc Les Aventures de Tom Bombadil, Le Silmarillion, Contes Inachevés, et Le Conte des Enfants de Húrin, tous assemblés posthumement par CJRT à l'exception du premier. Mais Le Seigneur des Anneaux lui-même est tout à fait acceptable et probablement préférable pour citer, à condition que vous y trouviez une citation appropriée.

Ainsi, si vous deviez fournir un nouveau fichier source complet de haut niveau à ajouter à Perl, vous devriez vous conformer à cette pratique particulière en sélectionnant vous-même une citation appropriée de Tolkien, en conservant l'orthographe et la ponctuation d'origine et en utilisant le même format que celui des autres citations.
