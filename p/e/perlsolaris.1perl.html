PERLSOLARIS(1perl) Guide de référence du programmeur Perl PERLSOLARIS(1perl)

NOM

perlsolaris - Version Perl 5 sur les systèmes Solaris

DESCRIPTION

Ce document décrit diverses caractéristiques du système d'exploitation Solaris de Sun qui affecteront la façon dont Perl version 5 (ci-après appelé perl) sera compilé et/ou s'exécutera. Certains problèmes liés à l'ancien SunOS 4.x sont également abordés, bien qu'ils puissent être obsolètes.

Dans la plupart des cas, tout devrait fonctionner.

À partir de Solaris 8, perl5.00503 (ou une version ultérieure) est fourni avec le système d'exploitation, vous n'aurez donc peut-être même pas besoin de compiler une nouvelle version de perl. La version fournie par Sun est installée dans /usr/perl5 avec /usr/bin/perl pointant vers /usr/perl5/bin/perl. Ne touchez pas à cette installation à moins de savoir vraiment ce que vous faites. Si vous supprimez le perl fourni avec l'OS, vous rendrez certains éléments de votre système inopérants. Si vous souhaitez installer une nouvelle version de perl, installez-la sous un préfixe différent de /usr/perl5. Les préfixes courants à utiliser sont /usr/local et /opt/perl.

Vous pourriez vouloir ajouter votre version de perl au PATH de tous les utilisateurs en modifiant le lien /usr/bin/perl. C'est probablement acceptable, car la plupart des scripts perl livrés avec Solaris utilisent un chemin explicite. (Il y a quelques exceptions, telles que /usr/bin/rpm2cpio et /etc/rcm/scripts/README, mais elles sont aussi suffisamment génériques pour que la version réelle de perl n'ait probablement pas beaucoup d'importance.)

Solaris fournit une gamme de modules spécifiques à Solaris. Si vous choisissez d'installer votre propre version de perl, vous trouverez la source de bon nombre de ces modules disponible sur CPAN sous le namespace Sun::Solaris::.

Solaris peut inclure deux versions de perl, par exemple Solaris 9 inclut à la fois 5.005_03 et 5.6.1. Ceci est fait pour assurer la stabilité entre les versions de Solaris, dans les cas où une version perl ultérieure a des incompatibilités avec la version incluse dans la version Solaris précédente. Le perl par défaut sera toujours le plus récent, et en général l'ancienne version ne sera conservée que pour une seule version de Solaris. Notez également que le perl par défaut NE sera PAS configuré pour rechercher des modules dans l'ancienne version, à nouveau pour des raisons de compatibilité/stabilité. Par conséquent, si vous mettez à niveau Solaris, vous devrez recompiler/réinstaller tous les modules CPAN supplémentaires que vous aviez installés pour la version Solaris précédente. Voir la page man de CPAN sous 'autobundle' pour une méthode rapide pour ce faire.

À titre de mesure temporaire, vous pouvez soit modifier la ligne #!/ de vos scripts pour faire référence spécifiquement à l'ancienne version de perl, par exemple sur Solaris 9 utilisez #!/usr/perl5/5.00503/bin/perl pour utiliser la version de perl qui était par défaut pour Solaris 8, ou si vous avez un grand nombre de scripts, il peut être plus pratique de faire de l'ancienne version de perl la version par défaut sur votre système. Vous pouvez le faire en modifiant les liens symboliques appropriés sous /usr/perl5 comme suit (exemple pour Solaris 9) :

# cd /usr/perl5
# rm bin man pod
# ln -s ./5.00503/bin
# ln -s ./5.00503/man
# ln -s ./5.00503/lib/pod
# rm /usr/bin/perl
# ln -s ../perl5/5.00503/bin/perl /usr/bin/perl

Dans les deux cas, cela ne devrait être considéré que comme une mesure temporaire - vous devriez passer à la version perl ultérieure dès que possible.

Notez également que les utilitaires en ligne de commande de perl (par exemple, perldoc) et ceux qui sont ajoutés par les modules que vous installez se trouveront sous /usr/perl5/bin, donc ce répertoire devrait être ajouté à votre PATH.

MISE EN PLACE

Problèmes d'extraction de fichiers sur Solaris

Assurez-vous d'utiliser un programme tar compilé sous Solaris (pas SunOS 4.x) pour extraire le fichier perl-5.x.x.tar.gz. N'utilisez pas GNU tar compilé pour SunOS4 sur Solaris. (GNU tar compilé pour Solaris devrait être correct.) Lorsque vous exécutez des binaires SunOS4 sur Solaris, le système d'exécution modifie magiquement les noms de chemin correspondant à m#lib/locale# de sorte que lorsque tar essaie de créer lib/locale.pm, un fichier nommé lib/oldlocale.pm est créé à la place. Si vous avez trouvé ce conseil trop tard et avez utilisé un tar compilé pour SunOS4 de toute façon, vous devez trouver le fichier renommé incorrectement et le déplacer à nouveau vers lib/locale.pm.

Compilateur et outils associés sur Solaris

Vous devez utiliser un compilateur C ANSI pour compiler perl. Perl peut être compilé soit avec le compilateur C additionnel de Sun, soit avec gcc. Le compilateur C fourni avec SunOS4 ne suffira pas.

Inclure /usr/ccs/bin/ dans votre PATH

Plusieurs outils nécessaires pour compiler perl se trouvent dans /usr/ccs/bin/ : ar, as, ld et make. Assurez-vous que /usr/ccs/bin/ est dans votre PATH.

Sur toutes les versions publiées de Solaris (8, 9 et 10), vous devez vous assurer que les paquets suivants sont installés (ces informations sont extraites de la FAQ Solaris) :

pour les outils (sccs, lex, yacc, make, nm, truss, ld, as) : SUNWbtool, SUNWsprot, SUNWtoo

pour les bibliothèques et en-têtes : SUNWhea, SUNWarc, SUNWlibm, SUNWlibms, SUNWdfbh, SUNWcg6h, SUNWxwinc

De plus, sur Solaris 8 et 9, vous avez également besoin de :

pour le développement 64 bits : SUNWarcx, SUNWbtoox, SUNWdplx, SUNWscpux, SUNWsprox, SUNWtoox, SUNWlmsx, SUNWlmx, SUNWlibCx

Et uniquement sur Solaris 8, vous avez également besoin de :

pour les bibliothèques et en-têtes : SUNWolinc

En cas de doute sur le paquet contenant un fichier manquant, essayez de trouver une installation qui contient ce fichier. Ensuite, faites un

$ grep /mon/fichier/manquant /var/sadm/install/contents

Cela affichera une ligne comme celle-ci :

/usr/include/sys/errno.h f none 0644 root bin 7471 37605 956241356 SUNWhea

Le dernier élément listé (SUNWhea dans cet exemple) est le paquet dont vous avez besoin.

Évitez /usr/ucb/cc

Vous n'avez pas besoin d'avoir /usr/ucb/ dans votre PATH pour compiler perl. Si vous voulez quand même /usr/ucb/ dans votre PATH, assurez-vous que /usr/ucb/ N'EST PAS dans votre PATH avant le répertoire contenant le bon compilateur C.

Compilateur C de Sun

Si vous utilisez le compilateur C de Sun, assurez-vous que le bon répertoire (généralement /opt/SUNWspro/bin/) est dans votre PATH (avant /usr/ucb/).

GCC

Si vous utilisez gcc, assurez-vous que votre installation est récente et complète. Les versions de perl depuis 5.6.0 compilent bien avec gcc > 2.8.1 sur Solaris >= 2.6.

Vous devez configurer perl avec

$ sh Configure -Dcc=gcc

Sinon, vous pourriez rencontrer des erreurs de compilation étranges.

Si vous avez mis à jour votre version de Solaris, vous devrez peut-être également mettre à jour votre gcc. Par exemple, si vous exécutez Solaris 2.6 et que votre gcc est installé dans /usr/local, vérifiez dans /usr/local/lib/gcc-lib et assurez-vous que vous avez le répertoire approprié, sparc-sun-so

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

laris2.6/ ou i386-pc-solaris2.6/. Si le répertoire de gcc est destiné à une version différente de Solaris que celle que vous utilisez, vous devrez reconstruire gcc pour votre nouvelle version de Solaris.

Vous pouvez obtenir une version précompilée de gcc sur http://www.sunfreeware.com/ ou http://www.blastwave.org/. Assurez-vous de télécharger le paquet pour votre version de Solaris.

Si vous souhaitez utiliser gcc pour compiler des modules complémentaires à utiliser avec le perl fourni avec Solaris, vous devriez utiliser le module Solaris::PerlGcc qui est disponible sur CPAN. Le perl fourni avec Solaris est configuré et compilé avec les compilateurs Sun, et les informations de configuration du compilateur stockées dans Config.pm ne sont donc pertinentes que pour les compilateurs Sun. Le module Solaris::PerlGcc contient un remplacement de Config.pm qui est correct pour gcc - voir le module pour plus de détails.

GNU as et GNU ld

Les informations suivantes s'appliquent à gcc version 2. Des bénévoles pour le mettre à jour de manière appropriée pour gcc version 3 seraient appréciés.

Les versions de as et ld fournies avec Solaris fonctionnent parfaitement pour compiler perl. Il n'est normalement pas nécessaire d'installer les versions GNU pour compiler perl.

Si vous décidez d'ignorer ces conseils et d'utiliser les versions GNU de toute façon, assurez-vous qu'elles sont relativement récentes. Les versions plus récentes que 2.7 sont apparemment suffisantes. Les versions plus anciennes peuvent avoir des problèmes avec le chargement dynamique.

Si vous souhaitez utiliser GNU ld, vous devez lui passer le drapeau -Wl,-E. Le fichier hints/solaris_2.sh essaie de faire cela automatiquement en définissant les variables Configure suivantes :

ccdlflags="$ccdlflags -Wl,-E"
lddlflags="$lddlflags -Wl,-E -G"

Cependant, au fil des ans, des changements dans gcc, GNU ld et Solaris ld ont rendu difficile la détection automatique de quel ld est finalement appelé. Vous devrez peut-être éditer manuellement config.sh et ajouter les drapeaux -Wl,-E vous-même, ou exécuter Configure interactivement et ajouter les drapeaux aux invites appropriées.

Si votre gcc est configuré pour utiliser GNU as et ld mais que vous voulez utiliser ceux de Solaris à la place pour compiler perl, alors vous devrez ajouter -B/usr/ccs/bin/ à la ligne de commande de gcc. Une façon pratique de le faire est avec

$ sh Configure -Dcc='gcc -B/usr/ccs/bin/'

Notez que la barre oblique finale est requise. Cela entraînera des avertissements inoffensifs lors de l'exécution de Configure :

gcc: file path prefix `/usr/ccs/bin/' never used

Ces messages peuvent être ignorés en toute sécurité. (Notez que pour un système SunOS4, vous devez utiliser -B/bin/ à la place.)

Alternativement, vous pouvez utiliser la variable d'environnement GCC_EXEC_PREFIX pour garantir que les as et ld de Sun sont utilisés. Consultez la documentation de votre gcc pour plus d'informations sur l'option -B et la variable GCC_EXEC_PREFIX.

Sun et GNU make

Le make sous /usr/ccs/bin fonctionne parfaitement pour compiler perl. Si vous avez les compilateurs C de Sun, vous aurez également une version parallèle de make (dmake). Cela fonctionne bien pour compiler perl, mais peut parfois causer des problèmes lors de l'exécution de 'make test' en raison de dépendances non spécifiées entre les différents fichiers du banc d'essai. Le même problème peut également affecter la compilation de certains modules complémentaires, donc dans ces cas, spécifiez '-m serial' sur la ligne de commande de dmake, ou utilisez /usr/ccs/bin/make à la place. Si vous souhaitez utiliser GNU make, assurez-vous que le bit set-group-id n'est pas défini. S'il l'est, configurez votre PATH de manière à ce que /usr/ccs/bin/make soit avant GNU make, ou demandez à l'administrateur système de désactiver le bit set-group-id sur GNU make.

Évitez libucb

Solaris fournit certaines fonctions de compatibilité BSD dans /usr/ucblib/libucb.a. Perl ne se compilera ni ne fonctionnera correctement s'il est lié contre -lucb car il contient des routines incompatibles avec libc standard de Solaris. Normalement, ce n'est pas un problème car le fichier hints/solaris_sh empêche Configure de rechercher des bibliothèques dans /usr/ucblib, et omet également explicitement -lucb.

Environnement pour compiler perl sur Solaris

PATH

Assurez-vous que votre PATH inclut le compilateur (/opt/SUNWspro/bin/ si vous utilisez le compilateur Sun) ainsi que /usr/ccs/bin/ pour récupérer les autres outils de développement (tels que make, ar, as et ld). Assurez-vous que votre PATH n'inclut pas /usr/ucb ou qu'il l'inclut après le compilateur et les outils de compilation et d'autres répertoires Solaris standard. Vous ne voulez absolument pas /usr/ucb/cc.

LD_LIBRARY_PATH

Si la variable d'environnement LD_LIBRARY_PATH est définie, assurez-vous qu'elle n'inclut PAS /lib ou /usr/lib. Si vous allez compiler des extensions qui appellent des bibliothèques partagées tierces (par exemple, Berkeley DB), assurez-vous que votre variable d'environnement LD_LIBRARY_PATH inclut le répertoire avec cette bibliothèque (par exemple, /usr/local/lib).

Si vous obtenez un message d'erreur

dlopen: stub interception failed

c'est probablement parce que votre variable d'environnement LD_LIBRARY_PATH inclut un répertoire qui est un lien symbolique vers /usr/lib (tel que /lib). La raison pour laquelle cela pose un problème est assez subtile. Le fichier libdl.so.1.0 contient *uniquement* des fonctions qui génèrent des erreurs de 'stub interception failed' ! Le linker d'exécution intercepte les liens vers "/usr/lib/libdl.so.1.0" et inclut des implémentations internes de ces fonctions à la place. [Merci à Tim Bunce pour cette explication.]

EXECUTER CONFIGURE

Voir le fichier INSTALL pour des informations générales concernant Configure. Seuls les problèmes spécifiques à Solaris sont abordés ici. Normalement, les valeurs par défaut devraient convenir.

perl 64 bits sur Solaris

Voir le fichier INSTALL pour des informations générales concernant les compilations 64 bits. En général, les valeurs par défaut devraient convenir à la plupart des gens.

Par défaut, perl-5.6.0 (ou plus récent) est compilé en tant qu'application 32 bits avec prise en charge de largefile et long-long.

Problèmes généraux 32 bits vs 64 bits

Solaris 7 et versions ultérieures s'exécutent en mode 32 bits ou 64 bits sur les processeurs SPARC, via un redémarrage. Vous pouvez compiler des applications 64 bits tout en exécutant en mode 32 bits et vice-versa. Les applications 32 bits s'exécuteront sous Solaris fonctionnant en mode 32 ou 64 bits. Les applications 64 bits nécessitent que Solaris fonctionne en mode 64 bits.

Les applications 32 bits existantes sont correctement appelées LP32, c'est-à-dire que les Longs et les Pointers sont de 32 bits. Les applications 64 bits sont plus correctement appelées LP64. La caractéristique distinctive d'une application 64 bits LP64 est sa capacité à utiliser un espace d'adressage de 64 bits. Il est parfaitement possible d'avoir une application 32 bits LP qui prend en charge à la fois les entiers 64 bits (long long) et les largefiles (> 2 Go), et c'est la valeur par défaut pour perl-5.6.0.

Pour une explication plus complète des problèmes 64 bits, consultez le "Solaris 64-bit Developer's Guide" sur http://docs.sun.com/

Vous pouvez détecter le mode du système d'exploitation en utilisant "isainfo -v", par exemple.

$ isainfo -v   # Ultra 30 en mode 64 bits
64-bit sparcv9 applications
32-bit sparc applications

Par défaut, perl sera compilé en tant qu'application 32 bits. À moins que vous ne souhaitiez allouer plus de ~ 4 Go de mémoire à l'intérieur de perl, ou à moins que vous n'ayez besoin de plus de 255 descripteurs de fichiers ouverts, vous n'avez probablement pas besoin que perl soit une application 64 bits.

Support des grands fichiers

Pour Solaris 2.6 et versions ultérieures, il existe deux façons différentes pour les applications 32 bits de manipuler les grands fichiers (fichiers dont la taille est > 2 Go). (Une application 64 bits dispose automatiquement du support largefile intégré par défaut.)

La première est l'"environnement de compilation transitoire", décrit dans lfcompile64(5). Selon le manuel, 

L'environnement de compilation transitoire exporte toutes les
fonctions et types explicites 64 bits (xxx64()) ainsi que toutes les
fonctions (xxx()) et types réguliers. Les fonctions xxx() et xxx64()
sont disponibles pour la source du programme. Une application 32 bits
doit utiliser les fonctions xxx64() pour accéder aux grands fichiers.
Voir la page de manuel lf64(5) pour une liste complète des interfaces
transitoires 64 bits.

L'environnement de compilation transitoire est obtenu avec les indicateurs de compilation et de liaison suivants :

getconf LFS64_CFLAGS        -D_LARGEFILE64_SOURCE
getconf LFS64_LDFLAG        # rien de spécial nécessaire
getconf LFS64_LIBS          # rien de spécial nécessaire

La seconde est l'"environnement de compilation large file", décrit dans lfcompile(5). Selon le manuel, 

Chaque interface nommée xxx() qui doit accéder à des entités 64 bits
pour accéder aux grands fichiers est mappée à un appel xxx64() dans le
binaire résultant. Tous les types de données pertinents sont définis pour
être de la bonne taille (par exemple, off_t a une définition typedef pour
une entité 64 bits).
Une application compilée dans cet environnement peut utiliser les
interfaces source xxx() pour accéder aux fichiers grands et petits,
plutôt que d'avoir à utiliser explicitement les appels d'interface
transitoire xxx64() pour accéder aux grands fichiers.

Deux exceptions sont fseek() et ftell(). Les applications 32 bits doivent utiliser fseeko(3C) et ftello(3C). Celles-ci seront automatiquement mappées à fseeko64() et ftello64().

L'environnement de compilation large file est obtenu avec

getconf LFS_CFLAGS      -D_LARGEFILE_SOURCE -D_FILE_OFFSET_BITS=64
getconf LFS_LDFLAGS     # rien de spécial nécessaire
getconf LFS_LIBS        # rien de spécial nécessaire

Par défaut, perl utilise l'environnement de compilation large file et s'appuie sur Solaris pour effectuer le mappage sous-jacent des interfaces.

Compiler un perl LP64

Pour compiler une application 64 bits sur un UltraSparc avec un compilateur Sun récent, vous devez utiliser le drapeau "-xarch=v9". getconf(1) vous le dira, par exemple.

$ getconf -a | grep v9
XBS5_LP64_OFF64_CFLAGS:         -xarch=v9
XBS5_LP64_OFF64_LDFLAGS:        -xarch=v9
XBS5_LP64_OFF64_LINTFLAGS:      -xarch=v9
XBS5_LPBIG_OFFBIG_CFLAGS:       -xarch=v9
XBS5_LPBIG_OFFBIG_LDFLAGS:      -xarch=v9
XBS5_LPBIG_OFFBIG_LINTFLAGS:    -xarch=v9
_XBS5_LP64_OFF64_CFLAGS:        -xarch=v9
_XBS5_LP64_OFF64_LDFLAGS:       -xarch=v9
_XBS5_LP64_OFF64_LINTFLAGS:     -xarch=v9
_XBS5_LPBIG_OFFBIG_CFLAGS:      -xarch=v9
_XBS5_LPBIG_OFFBIG_LDFLAGS:     -xarch=v9
_XBS5_LPBIG_OFFBIG_LINTFLAGS:   -xarch=v9

Ce drapeau est pris en charge dans les Sun WorkShop Compilers 5.0 et versions ultérieures (maintenant commercialisés sous le nom de Forte) lorsqu'ils sont utilisés sur Solaris 7 ou versions ultérieures sur les systèmes UltraSparc.

Si vous utilisez gcc, vous devrez utiliser -mcpu=v9 -m64 à la place. Cette option n'est pas encore prise en charge dans gcc 2.95.2 ; à partir de install/SPECIFIC dans cette version :

GCC version 2.95 is not able to compile code correctly for sparc64
targets. Users of the Linux kernel, at least, can use the sparc32
program to start up a new shell invocation with an environment that
causes configure
pour reconnaître (via uname -a) le système comme sparc-*-* plutôt.

Tout cela devrait être géré automatiquement par le fichier hints, si demandé.

Doubles longs

Depuis la version 5.8.1, les doubles longs fonctionnent si vous utilisez les compilateurs Sun (nécessaires pour des routines mathématiques supplémentaires non incluses dans libm).

Threads dans perl sous Solaris

Il est possible de construire une version threadée de perl sous Solaris. L'implémentation complète des threads de perl est toujours expérimentale, cependant, donc soyez prudent.

Problèmes de malloc avec perl sous Solaris

À partir de perl 5.7.1, perl utilise le malloc de Solaris, car le malloc de perl se casse lorsqu'il traite plus de 2 Go de mémoire, et le malloc de Solaris semble également être plus rapide.

Si pour une raison quelconque (telle que la compatibilité binaire descendante) vous avez vraiment besoin d'utiliser le malloc de perl, vous pouvez reconstruire perl à partir des sources et configurer la compilation avec

$ sh Configure -Dusemymalloc

Vous ne devriez pas utiliser le malloc de perl si vous compilez avec gcc. Il y a des rapports de plantages, en particulier dans le module PDL. Le problème semble disparaître avec -DDEBUGGING, il a donc été difficile à identifier. Le compilateur de Sun semble fonctionner correctement avec ou sans le malloc de perl. PROBLÈMES DE MAKE

Problèmes de chargement dynamique avec GNU as et GNU ld
Si vous rencontrez des problèmes avec le chargement dynamique en utilisant gcc sur SunOS ou Solaris, et que vous utilisez GNU as et GNU ld, consultez la section "GNU as et GNU ld" ci-dessus.
ld.so.1: ./perl: fatal: relocation error:
Si vous obtenez ce message sur SunOS ou Solaris, et que vous utilisez gcc, il s'agit probablement du problème GNU as ou GNU ld mentionné dans l'élément précédent "GNU as et GNU ld".
dlopen: stub interception failed
La cause principale du message "dlopen: stub interception failed" est que la variable d'environnement LD_LIBRARY_PATH inclut un répertoire qui est un lien symbolique vers /usr/lib (tel que /lib). Voir "LD_LIBRARY_PATH" ci-dessus.
#error "No DATAMODEL_NATIVE specified"
C'est une erreur courante lors de la tentative de compilation de perl sous Solaris 2.6 avec une installation gcc de Solaris 2.5 ou 2.5.1. Les fichiers d'en-tête de Solaris ont changé, vous devez donc mettre à jour votre installation gcc. Vous pouvez soit réexécuter le script fixincludes de gcc, soit profiter de l'occasion pour mettre à jour votre installation gcc.
sh: ar: not found
C'est un message de votre shell vous indiquant que la commande 'ar' est introuvable. Vous devez vérifier votre variable d'environnement PATH pour vous assurer qu'elle inclut le répertoire contenant la commande 'ar'. C'est un problème courant sur Solaris, où 'ar' se trouve dans le répertoire /usr/ccs/bin/.

MAKE TEST

op/stat.t test 4 sous Solaris

Le test 4 de op/stat.t peut échouer si vous êtes sur un tmpfs d'une sorte. La compilation dans /tmp montre parfois ce comportement. La suite de tests détecte si vous compilez dans /tmp, mais elle peut ne pas être en mesure de détecter toutes les situations tmpfs.

nss_delete core dump de op/pwent ou op/grent

Voir "nss_delete core dump from op/pwent or op/grent" dans perlhpux.

COMPILATION CROISÉE

Rien de trop inhabituel ici. Vous pouvez facilement le faire si vous disposez d'un compilateur croisé disponible ; une invocation typique de Configure lors de la cible Solaris x86 ressemble à ceci :

sh ./Configure -des -Dusecrosscompile \
    -Dcc=i386-pc-solaris2.11-gcc      \
    -Dsysroot=$SYSROOT                \
    -Alddlflags=" -Wl,-z,notext"      \
    -Dtargethost=... # Les options de compilation croisée habituelles

L'ajout à lddlflags est le seul élément anormal.

PROBLÈMES D'EXÉCUTION POUR PERL SOUS SOLARIS

Limites sur le nombre de fichiers ouverts sous Solaris

La page de manuel stdio(3C) note que pour les applications LP32, seuls 255 fichiers peuvent être ouverts à l'aide de fopen(), et seuls les descripteurs de fichiers 0 à 255 peuvent être utilisés dans un flux. Comme perl appelle open() puis fdopen(3C) avec le descripteur de fichier résultant, perl est limité à 255 fichiers ouverts simultanément, même si sysopen() est utilisé. Si cela s'avère être un problème insurmontable, vous pouvez compiler perl en tant qu'application LP64, voir "Building an LP64 perl" pour plus de détails. Notez également que la limite de ressources par défaut pour les descripteurs de fichiers ouverts sous Solaris est de 255, vous devrez donc modifier votre ulimit ou rctl (Solaris 9 et versions ultérieures) en conséquence.

Voir les modules sous les espaces de noms Solaris:: et Sun::Solaris sur CPAN, voir http://www.cpan.org/modules/by-module/Solaris/ et http://www.cpan.org/modules/by-module/Sun/.

PROBLÈMES SPÉCIFIQUES À SOLARIS AVEC LES MODULES

Proc::ProcessTable sous Solaris

Proc::ProcessTable ne compile pas sous Solaris avec perl5.6.0 et supérieur si LARGEFILES est défini. Étant donné que le support des gros fichiers est activé par défaut dans les versions 5.6.0 et ultérieures, vous devez prendre des mesures spéciales pour utiliser ce module.

Le problème est que diverses structures visibles via procfs utilisent off_t, et si vous compilez avec le support des gros fichiers, celles-ci passent de 32 bits à 64 bits. Ainsi, ce que vous obtenez de procfs ne correspond pas aux structures dans perl, résultant en des données incorrectes. Voir proc(4) pour une discussion plus approfondie.

Une solution pour Proc::ProcessTable consiste à éditer Makefile pour supprimer explicitement les indicateurs de gros fichiers de ceux que MakeMaker récupère de Config.pm. Cela entraînera la compilation de Proc::ProcessTable dans l'environnement approprié. Tout devrait alors fonctionner tant que Proc::ProcessTable n'essaie pas de partager des off_t avec le reste de perl, ou si c'est le cas, ils devraient être explicitement spécifiés comme off64_t.

BSD::Resource sous Solaris

Les versions de BSD::Resource antérieures à 1.09 ne compilent pas sous Solaris avec perl 5.6.0 et supérieur, pour les mêmes raisons que Proc::ProcessTable. Les versions de BSD::Resource à partir de 1.09 incluent une solution de contournement pour le problème.

Net::SSLeay sous Solaris

Net::SSLeay nécessite la présence d'un /dev/urandom. Ce périphérique est disponible à partir de Solaris 9 et versions ultérieures. Pour les versions antérieures de Solaris, vous pouvez soit obtenir le package SUNWski (empaqueté avec plusieurs produits logiciels Sun, par exemple le Sun WebServer, qui fait partie de Solaris Server Intranet Extension, ou le Sun Directory Services, faisant partie de Solaris pour les FAI), soit télécharger le package ANDIrand depuis http://www.cosy.sbg.ac.at/~andi/. Si vous utilisez SUNWski, créez un lien symbolique /dev/urandom pointant vers /dev/random. Pour plus de détails, consultez le document ID27606 intitulé "Differing /dev/random support requirements within Solaris[TM] Operating Environments", disponible sur http://sunsolve.sun.com .

Il est possible d'utiliser l'Entropy Gathering Daemon (écrit en Perl !), disponible sur http://www.lothar.com/tech/crypto/.

SunOS 4.x

Sous SunOS 4.x, vous voudrez très probablement utiliser le ld de SunOS, /usr/bin/ld, car les versions plus récentes de GNU ld (comme 2.13) ne semblent plus fonctionner pour la compilation de Perl. Lors de la liaison des extensions, GNU ld devient très mécontent et produit de nombreuses erreurs comme celle-ci

... relocation truncated to fit: BASE13 ...

et meurt. Par conséquent, le fichier hints de SunOS 4.1 définit explicitement le ld comme étant /usr/bin/ld.

Depuis Perl 5.8.1, le chargement dynamique des bibliothèques (DynaLoader, XSLoader) semble également être devenu défectueux sous SunOS 4.x. Par conséquent, la valeur par défaut est de compiler Perl statiquement.

L'exécution de la suite de tests sous SunOS 4.1 est un peu délicate car le test dist/Tie-File/t/09_gen_rs.t se bloque (sous-test #51, FWIW) pour une raison inconnue. Arrêtez simplement le test et tuez ce processus Perl particulier.

Il existe divers autres échecs, qui sous SunOS 4.1.4 et gcc 3.2.2 ressemblent beaucoup à des bugs de gcc. De nombreux échecs se produisent dans les tests Encode, où, par exemple, lorsque le test attend "0", vous obtenez "&#48;", ce qui, après un peu d'observation attentive, devrait sembler très étrange. Un autre exemple se situe plus tôt dans t/run/fresh_perl où chr(0xff) est attendu mais le test échoue car le résultat est chr(0xff). Exactement.
