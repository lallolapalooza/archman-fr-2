NOM

perlfaq8 - Interaction avec le système

VERSION

version 5.20250619

DESCRIPTION

Cette section de la FAQ Perl couvre les questions relatives à l'interaction avec le système d'exploitation. Les sujets incluent la communication inter-processus (IPC), le contrôle de l'interface utilisateur (clavier, écran et périphériques de pointage), et la plupart des autres éléments non liés à la manipulation de données.

Lisez les FAQs et la documentation spécifiques au portage de perl sur votre système d'exploitation (par exemple, perlvms, perlplan9, ...). Celles-ci devraient contenir des informations plus détaillées sur les particularités de votre perl.

Comment savoir quel système d'exploitation j'utilise ?

La variable $^O ($OSNAME si vous utilisez "English") contient une indication du nom du système d'exploitation (pas son numéro de version) pour lequel votre binaire perl a été compilé.

Pourquoi exec() ne revient-il pas ?

(contribué par brian d foy)

Le travail de la fonction "exec" est de transformer votre processus en une autre commande et de ne jamais revenir. Si ce n'est pas ce que vous voulez faire, n'utilisez pas "exec". :)

Si vous voulez exécuter une commande externe et laisser votre processus Perl continuer, regardez du côté de "open" avec tube, "fork", ou "system".

Comment imprimer quelque chose en couleur ?

En général, vous ne le faites pas, car vous ne savez pas si le destinataire a un appareil d'affichage compatible couleur. Si vous savez qu'il dispose d'un terminal ANSI qui comprend la couleur, vous pouvez utiliser le module Term::ANSIColor de CPAN :

use Term::ANSIColor;
print color("red"), "Stop !\n", color("reset");
print color("green"), "Allez !\n", color("reset");

Ou comme ceci :

use Term::ANSIColor qw(:constants);
print RED, "Stop !\n", RESET;
print GREEN, "Allez !\n", RESET;

Comment lire une seule touche sans attendre la touche Entrée ?

Le contrôle de la mise en mémoire tampon de l'entrée est une question remarquablement dépendante du système. Sur de nombreux systèmes, vous pouvez simplement utiliser la commande stty comme montré dans "getc" dans perlfunc, mais comme vous le voyez, cela vous amène déjà à des problèmes de portabilité.

open(TTY, "+</dev/tty") or die "pas de tty : $!";
system "stty  cbreak </dev/tty >/dev/tty 2>&1";
$key = getc(TTY);        # peut-être que cela fonctionne
# OU ALORS
sysread(TTY, $key, 1);    # probablement que cela fonctionne
system "stty -cbreak </dev/tty >/dev/tty 2>&1";

Le module Term::ReadKey de CPAN offre une interface facile à utiliser qui devrait être plus efficace que de lancer stty pour chaque touche. Il inclut même un support limité pour Windows.

use Term::ReadKey;
ReadMode('cbreak');
$key = ReadKey(0);
ReadMode('normal');

Cependant, l'utilisation du code nécessite que vous ayez un compilateur C fonctionnel et que vous puissiez l'utiliser pour construire et installer un module CPAN. Voici une solution utilisant le module POSIX standard, qui est déjà sur votre système (en supposant que votre système prend en charge POSIX).

use HotKey;
$key = readkey();

Et voici le module "HotKey", qui masque les appels quelque peu mystifiants pour manipuler les structures termios POSIX.

# HotKey.pm
package HotKey;
use strict;
use warnings;
use parent 'Exporter';
our @EXPORT = qw(cbreak cooked readkey);
use POSIX qw(:termios_h);
my ($term, $oterm, $echo, $noecho, $fd_stdin);
$fd_stdin = fileno(STDIN);
$term     = POSIX::Termios->new();
$term->getattr($fd_stdin);
$oterm     = $term->getlflag();
$echo     = ECHO | ECHOK | ICANON;
$noecho   = $oterm & ~$echo;
sub cbreak {
    $term->setlflag($noecho);  # ok, donc je ne veux pas d'écho non plus
    $term->setcc(VTIME, 1);
    $term->setattr($fd_stdin, TCSANOW);
}
sub cooked {
    $term->setlflag($oterm);
    $term->setcc(VTIME, 0);
    $term->setattr($fd_stdin, TCSANOW);
}
sub readkey {
    my $key = '';
    cbreak();
    sysread(STDIN, $key, 1);
    cooked();
    return $key;
}
END { cooked() }
1;

Comment vérifier si une entrée est prête sur le clavier ?

La manière la plus simple de le faire est de lire une touche en mode non bloquant avec le module Term::ReadKey de CPAN, en lui passant l'argument -1 pour indiquer de ne pas bloquer :

use Term::ReadKey;
ReadMode('cbreak');
if (defined (my $char = ReadKey(-1)) ) {
    # une entrée était en attente et c'était $char
} else {
    # aucune entrée n'était en attente
}
ReadMode('normal');                  # restaurer les paramètres normaux du terminal

Comment effacer l'écran ?

(contribué par brian d foy)

Pour effacer l'écran, il suffit d'imprimer la séquence spéciale qui indique au terminal d'effacer l'écran. Une fois que vous avez cette séquence, affichez-la lorsque vous souhaitez effacer l'écran.

Vous pouvez utiliser le module Term::ANSIScreen pour obtenir la séquence spéciale. Importez la fonction "cls" (ou la balise ":screen") :

use Term::ANSIScreen qw(cls);
my $clear_screen = cls();
print $clear_screen;

Le module Term::Cap peut également obtenir la séquence spéciale si vous souhaitez traiter les détails de bas niveau du contrôle du terminal. La méthode "Tputs" renvoie la chaîne pour la capacité donnée :

use Term::Cap;
my $terminal = Term::Cap->Tgetent( { OSPEED => 9600 } );
my $clear_screen = $terminal->Tputs('cl');
print $clear_screen;

Sous Windows, vous pouvez utiliser le module Win32::Console. Après avoir créé un objet pour le descripteur de fichier de sortie que vous souhaitez affecter, appelez la méthode "Cls" :

Win32::Console;
my $OUT = Win32::Console->new(STD_OUTPUT_HANDLE);
$OUT->Cls;

Si vous avez un programme en ligne de commande qui fait le travail, vous pouvez l'appeler entre backticks pour capturer tout ce qu'il produit afin de pouvoir l'utiliser plus tard :

my $clear_string = `clear`;
print $clear_string;

Comment obtenir la taille de l'écran ?

Si vous avez le module Term::ReadKey installé depuis CPAN, vous pouvez l'utiliser pour récupérer la largeur et la hauteur en caractères et en pixels :

use Term::ReadKey;
my ($wchar, $hchar, $wpixels, $hpixels) = GetTerminalSize();

C'est plus portable que l'appel brut "ioctl", mais moins illustratif :

require './sys/ioctl.ph';
die "pas de TIOCGWINSZ " unless defined &TIOCGWINSZ;
open(my $tty_fh, "+</dev/tty")

Comment demander un mot de passe à l'utilisateur ?

(Cette question n'a rien à voir avec le web. Voir une autre FAQ pour cela.)

Il y a un exemple de cela dans "crypt" dans perlfunc. Premièrement, vous mettez le terminal en mode "pas d'écho", puis vous lisez simplement le mot de passe normalement. Vous pouvez faire cela avec une fonction ioctl() style ancien, le contrôle de terminal POSIX (voir POSIX ou sa documentation dans le Camel Book), ou un appel au programme stty, avec des degrés de portabilité variables.

Vous pouvez également faire cela pour la plupart des systèmes en utilisant le module Term::ReadKey de CPAN, qui est plus facile à utiliser et en théorie plus portable.

use Term::ReadKey;
ReadMode('noecho');
my $password = ReadLine(0);

Comment lire et écrire sur le port série ?

Cela dépend du système d'exploitation sur lequel votre programme s'exécute. Dans le cas d'Unix, les ports série seront accessibles via des fichiers dans "/dev"; sur d'autres systèmes, les noms de périphériques différeront sans aucun doute. Plusieurs problèmes communs à toute interaction avec un périphérique sont les suivants :

fichiers-verrouillés
Votre système peut utiliser des fichiers de verrouillage pour contrôler les accès multiples. Assurez-vous de suivre le protocole correct. Des comportements imprévisibles peuvent résulter de multiples processus lisant sur un périphérique.
mode d'ouverture
Si vous prévoyez d'utiliser à la fois des opérations de lecture et d'écriture sur le périphérique, vous devrez l'ouvrir en mise à jour (voir "open" dans perlfunc pour plus de détails). Vous pourriez vouloir l'ouvrir sans risquer de blocage en utilisant sysopen() et "O_RDWR|O_NDELAY|O_NOCTTY" du module Fcntl (qui fait partie de la distribution perl standard). Voir "sysopen" dans perlfunc pour en savoir plus sur cette approche.
fin de ligne
Certains périphériques attendront un à la fin de chaque ligne plutôt qu'un . Dans certains ports de perl, et sont différents de leurs valeurs ASCII usuelles (Unix) de et . Vous devrez peut-être donner directement les valeurs numériques souhaitées, en utilisant l'octal ("\015"), l'hexadécimal ("0x0D"), ou comme spécification de caractère de contrôle ("\cM"). 
print DEV "atv1\012";    # faux, pour certains périphériques
print DEV "atv1\015";    # correct, pour certains périphériques

Même si avec les fichiers texte normaux un fait l'affaire, il n'y a toujours pas de schéma unifié pour terminer une ligne qui soit portable entre Unix, DOS/Win et Macintosh, sauf de terminer TOUTES les fins de ligne avec , et de supprimer ce dont vous n'avez pas besoin de la sortie. Ceci s'applique particulièrement à l'E/S des sockets et au vidage automatique, discutés ensuite.

vidage de la sortie
Si vous vous attendez à ce que les caractères arrivent à votre périphérique quand vous les print(), vous voudrez vider automatiquement ce descripteur de fichier. Vous pouvez utiliser select() et la variable $| pour contrôler le vidage automatique (voir "$|" dans perlvar et "select" dans perlfunc, ou perlfaq5, "Comment puis-je vider/débufferiser un descripteur de fichier de sortie ? Pourquoi dois-je faire cela ?") : 
my $old_handle = select($dev_fh);
$| = 1;
select($old_handle);

Vous verrez aussi du code qui fait cela sans variable temporaire, comme dans

select((select($deb_handle), $| = 1)[0]);

Ou si vous ne craignez pas d'importer quelques milliers de lignes de code juste parce que vous avez peur d'une petite variable $| :

use IO::Handle;
$dev_fh->autoflush(1);

Comme mentionné dans l'élément précédent, cela ne fonctionne toujours pas lors de l'utilisation d'E/S de sockets entre Unix et Macintosh. Vous devrez coder en dur vos terminateurs de ligne dans ce cas.

entrée non bloquante
Si vous effectuez une lecture bloquante read() ou sysread(), vous devrez prévoir un gestionnaire d'alarme pour fournir un délai d'attente (voir "alarm" dans perlfunc). Si vous avez une ouverture non bloquante, vous aurez probablement une lecture non bloquante, ce qui signifie que vous pourriez avoir à utiliser un select() à 4 arguments pour déterminer si les E/S sont prêtes sur ce périphérique (voir "select" dans perlfunc.

En essayant de lire depuis sa boîte d'identification d'appelant, le célèbre Jamie Zawinski "<jwz@netscape.com>", après beaucoup de grincements de dents et de luttes avec "sysread", "sysopen", les affaires "tcgetattr" de POSIX, et diverses autres fonctions qui font des bruits étranges la nuit, a finalement trouvé ceci :

sub open_modem {
    use IPC::Open2;
    my $stty = `/bin/stty -g`;
    open2( \*MODEM_IN, \*MODEM_OUT, "cu -l$modem_device -s2400 2>&1");
    # démarrer cu corrompt les paramètres stty de /dev/tty, même quand il a
    # été ouvert sur un tuyau...
    system("/bin/stty $stty");
    $_ = ;
    chomp;
    if ( !m/^Connected/ ) {
        print STDERR "$0: cu a affiché '$_' au lieu de 'Connected'\n";
    }
}

Comment décoder les fichiers de mots de passe cryptés ?

Vous dépensez beaucoup, beaucoup d'argent en matériel dédié, mais cela ne manquera pas de vous faire parler.

Sérieusement, vous ne pouvez pas si ce sont des fichiers de mots de passe Unix - le système de mots de passe Unix utilise un cryptage unidirectionnel. C'est plus comme un hachage qu'un cryptage. Le mieux que vous puissiez faire est de vérifier si autre chose correspond à la même chaîne. Vous ne pouvez pas transformer un hash en chaîne d'origine. Des programmes comme Crack peuvent essayer de deviner les mots de passe par la force (et intelligemment), mais ne garantissent pas (ne peuvent pas garantir) un succès rapide.

Si vous vous inquiétez des utilisateurs qui choisissent de mauvais mots de passe, vous devriez vérifier proactivement lorsqu'ils essaient de changer leur mot de passe (en modifiant passwd(1), par exemple).

Comment lancer un processus en arrière-plan ?

(contribué par brian d foy)

Il n'y a pas une seule façon d'exécuter du code en arrière-plan pour ne pas avoir à attendre qu'il se termine avant que votre programme ne passe à d'autres tâches. La gestion des processus dépend de votre système d'exploitation particulier, et bon nombre de ces techniques sont couvertes dans perlipc.

Plusieurs modules CPAN peuvent être en mesure d'aider, y compris IPC::Open2 ou IPC::Open3, IPC::Run, Parallel::Jobs, Parallel::ForkManager, POE, Proc::Background, et Win32::Process. Il existe de nombreux autres modules que vous pourriez utiliser, alors vérifiez ces espaces de noms pour d'autres options également.

Si vous êtes sur un système de type Unix, vous pourriez vous en sortir avec un appel système où vous mettez un "&" à la fin de la commande :

system("cmd &")

Vous pouvez également essayer d'utiliser "fork", comme décrit dans perlfunc (bien que ce soit la même chose que ce que feront bon nombre des modules pour vous).

STDIN, STDOUT et STDERR sont partagés
Le processus principal et le processus en arrière-plan (le processus "enfant") partagent les mêmes descripteurs de fichiers STDIN, STDOUT et STDERR. Si les deux essaient d'y accéder en même temps, des choses étranges peuvent arriver. Vous pourriez vouloir fermer ou rouvrir ces derniers pour l'enfant. Vous pouvez contourner cela en ouvrant un tube (voir "open" dans perlfunc) mais sur certains systèmes, cela signifie que le processus enfant ne peut pas survivre au parent.
Signaux
Vous devrez intercepter le signal SIGCHLD, et peut-être aussi SIGPIPE. SIGCHLD est envoyé lorsque le processus en arrière-plan se termine. SIGPIPE est envoyé lorsque vous écrivez sur un descripteur de fichier dont le processus enfant s'est fermé (un SIGPIPE non intercepté peut faire mourir votre programme silencieusement). Ce n'est pas un problème avec system("cmd&").
Zombies
Vous devez être prêt à "récupérer" le processus enfant lorsqu'il se termine. 
$SIG{CHLD} = sub { wait };
$SIG{CHLD} = 'IGNORE';

Vous pouvez également utiliser un double fork. Vous attendez immédiatement votre premier enfant, et le démon init attendra votre petit-enfant une fois qu'il sera terminé.

unless ($pid = fork) {
    unless (fork) {
        exec "ce que vous voulez vraiment faire";
        die "exec a échoué !";
    }
    exit 0;
}
waitpid($pid, 0);

Voir "Signals" dans perlipc pour d'autres exemples de code pour faire cela. Les zombies ne sont pas un problème avec "system("prog &")".

Comment intercepter les caractères de contrôle / signaux ?

Vous n'interceptez pas réellement un caractère de contrôle. Au lieu de cela, ce caractère génère un signal qui est envoyé au groupe de processus actuellement au premier plan de votre terminal, que vous interceptez alors dans votre processus. Les signaux sont documentés dans "Signals" dans perlipc et dans la section sur les "Signals" dans le Camel.

Vous pouvez définir les valeurs de la table de hachage %SIG pour qu'elles soient les fonctions que vous voulez gérer le signal. Après que perl attrape le signal, il recherche dans %SIG une clé portant le même nom que le signal, puis appelle la sous-routine associée à cette clé.

# comme une sous-routine anonyme
$SIG{INT} = sub { syswrite(STDERR, "aïe\n", 5 ) };
# ou une référence à une fonction
$SIG{INT} = \&ouch;
# ou le nom de la fonction sous forme de chaîne
$SIG{INT} = "ouch";

Les versions de Perl antérieures à la 5.8 avaient dans leur code source C des gestionnaires de signaux qui interceptaient le signal et pouvaient exécuter un Perl

function que vous aviez définie dans %SIG. Cela violait les règles de gestion des signaux à ce niveau, provoquant l'arrêt brutal de perl. Depuis la version 5.8.0, perl examine %SIG **après** que le signal ait été intercepté, plutôt qu'au moment où il est intercepté. Les versions précédentes de cette réponse étaient incorrectes.

Comment modifier le fichier de mots de passe shadow sur un système Unix ?

Si perl a été correctement installé et que votre bibliothèque shadow a été correctement écrite, les fonctions "getpw*()" décrites dans perlfunc devraient en théorie fournir un accès (en lecture seule) aux entrées du fichier de mots de passe shadow. Pour modifier le fichier, créez un nouveau fichier de mots de passe shadow (le format varie d'un système à l'autre, consultez passwd(1) pour plus de détails) et utilisez pwd_mkdb(8) pour l'installer (consultez pwd_mkdb(8) pour plus d'informations).

Comment régler l'heure et la date ?

En supposant que vous ayez les permissions suffisantes, vous devriez pouvoir régler la date et l'heure du système en exécutant le programme date(1). (Il n'y a aucun moyen de régler l'heure et la date par processus.) Ce mécanisme fonctionnera pour Unix, MS-DOS, Windows et NT ; l'équivalent VMS est "set time".

Cependant, si tout ce que vous voulez faire est de changer votre fuseau horaire, vous pouvez probablement vous en sortir en définissant une variable d'environnement :

$ENV{TZ} = "MST7MDT";           # Style Unix
$ENV{'SYS$TIMEZONE_DIFFERENTIAL'}="-5" # vms
system('trn', 'comp.lang.perl.misc');

Comment puis-je mettre en pause sleep() ou envoyer une alarme alarm() pendant moins d'une seconde ?

Si vous souhaitez une granularité plus fine que la seconde fournie par la fonction sleep(), le moyen le plus simple est d'utiliser la fonction select() telle que documentée dans "select" dans perlfunc. Essayez les modules Time::HiRes et BSD::Itimer (disponibles sur CPAN, et à partir de Perl 5.8, Time::HiRes fait partie de la distribution standard).

Comment puis-je mesurer le temps en dessous d'une seconde ?

(contribué par brian d foy)

Le module Time::HiRes (faisant partie de la distribution standard depuis Perl 5.8) mesure le temps avec l'appel système gettimeofday(), qui renvoie le temps en microsecondes depuis l'époque. Si vous ne pouvez pas installer Time::HiRes pour les anciennes versions de Perl et que vous êtes sur un système de type Unix, vous pourrez peut-être appeler gettimeofday(2) directement. Voir "syscall" dans perlfunc.

Comment puis-je faire un atexit() ou un setjmp()/longjmp() ? (Gestion des exceptions)

Vous pouvez utiliser le bloc "END" pour simuler atexit(). Le bloc "END" de chaque paquet est appelé lorsque le programme ou le thread se termine. Voir la page man perlmod pour plus de détails sur les blocs "END".

Par exemple, vous pouvez l'utiliser pour vous assurer que votre programme filtre a réussi à terminer sa sortie sans remplir le disque :

END {
    close(STDOUT) || die "La fermeture de stdout a échoué : $!";
}

Le bloc "END" n'est cependant pas appelé lorsque des signaux non interceptés tuent le programme. Ainsi, si vous utilisez des blocs "END", vous devriez également utiliser

use sigtrap qw(die normal-signals);

Le mécanisme de gestion des exceptions de Perl est son opérateur eval(). Vous pouvez utiliser eval() comme "setjmp" et die() comme "longjmp". Pour plus de détails à ce sujet, voir la section sur les signaux, en particulier le gestionnaire de délai d'attente pour un flock() bloquant dans "Signals" dans perlipc ou la section "Signals" dans Programming Perl.

Si la gestion des exceptions est tout ce qui vous intéresse, utilisez l'un des nombreux modules CPAN qui gèrent les exceptions, tels que Try::Tiny.

Si vous souhaitez la syntaxe atexit() (et aussi un rmexit()), essayez le module "AtExit" disponible sur CPAN.

Pourquoi mon programme de sockets ne fonctionne-t-il pas sous System V (Solaris) ? Que signifie le message d'erreur "Protocol not supported" ?

Certains systèmes basés sur Sys-V, notamment Solaris 2.X, ont redéfini certaines des constantes de socket standard. Comme celles-ci étaient constantes sur toutes les architectures, elles étaient souvent codées en dur dans le code perl. La bonne façon de traiter cela est d'"use Socket" pour obtenir les bonnes valeurs.

Notez que même si SunOS et Solaris sont binaires compatibles, ces valeurs sont différentes. Cherchez à comprendre.

Comment puis-je appeler les fonctions C uniques de mon système depuis Perl ?

Dans la plupart des cas, vous écrivez un module externe pour le faire - voir la réponse à "Où puis-je en apprendre davantage sur la liaison de C avec Perl ? [h2xs, xsubpp]". Cependant, si la fonction est un appel système et que votre système prend en charge syscall(), vous pouvez utiliser la fonction "syscall" (documentée dans perlfunc).

N'oubliez pas de vérifier les modules qui sont livrés avec votre distribution, ainsi que CPAN - quelqu'un a peut-être déjà écrit un module pour le faire. Sous Windows, essayez Win32::API. Sur Mac, essayez Mac::Carbon. Si aucun module n'a d'interface avec la fonction C, vous pouvez intégrer un peu de C dans votre source Perl avec Inline::C.

Où puis-je obtenir les fichiers d'inclusion pour faire un ioctl() ou un syscall() ?

Historiquement, ceux-ci étaient générés par l'outil h2ph, faisant partie de la distribution standard de perl. Ce programme convertit les directives cpp(1) dans les fichiers d'en-tête C en fichiers contenant des définitions de sous-routines, comme SYS_getitimer(), que vous pouvez utiliser comme arguments pour vos fonctions. Il ne fonctionne pas parfaitement, mais il accomplit généralement la majeure partie du travail. Les fichiers simples comme errno.h, syscall.h et socket.h convenaient, mais les fichiers difficiles comme ioctl.h nécessitent presque toujours une édition manuelle. Voici comment installer les fichiers *.ph :

1. Devenez le super-utilisateur
2. cd /usr/include
3. h2ph *.h */*.h

Si votre système prend en charge le chargement dynamique, pour des raisons de portabilité et de sanité, vous devriez probablement utiliser h2xs (également partie de la distribution standard de perl). Cet outil convertit les fichiers d'en-tête C en extensions Perl. Voir perlxstut pour savoir comment commencer avec h2xs.

Si votre système ne prend pas en charge le chargement dynamique, vous devriez toujours utiliser h2xs. Voir perlxstut et ExtUtils::MakeMaker pour plus d'informations (en bref, utilisez simplement make perl au lieu d'un simple make pour reconstruire perl avec une nouvelle extension statique).

Pourquoi les scripts perl setuid se plaignent-ils de problèmes du noyau ?

Certains systèmes d'exploitation ont des bogues dans le noyau qui rendent les scripts setuid intrinsèquement peu sûrs. Perl vous offre un certain nombre d'options (décrites dans perlsec) pour contourner de tels systèmes.

Comment puis-je ouvrir un tube à la fois vers et depuis une commande ?

Le module IPC::Open2 (faisant partie de la distribution standard de perl) est une approche facile à utiliser qui utilise en interne pipe(), fork() et exec() pour accomplir la tâche. Assurez-vous cependant de lire les avertissements de blocage dans sa documentation (voir IPC::Open2). Voir "Bidirectional Communication with Another Process" dans perlipc et "Bidirectional Communication with Yourself" dans perlipc

Vous pouvez également utiliser le module IPC::Open3 (faisant partie de la distribution standard de perl), mais attention, il a un ordre d'arguments différent de IPC::Open2 (voir IPC::Open3).

Pourquoi ne puis-je pas obtenir la sortie d'une commande avec system() ?

Vous confondez le but de system() et des backticks (``). system() exécute une commande et renvoie des informations sur le statut de sortie (sous forme de valeur de 16 bits : les 7 bits inférieurs représentent le signal à l'origine du décès du processus, le cas échéant, et les 8 bits supérieurs représentent la valeur de sortie réelle). Les backticks (``) exécutent une commande et renvoient ce qu'elle a envoyé à STDOUT.

my $exit_status   = system("mail-users");
my $output_string = `ls`;

Comment puis-je capturer STDERR d'une commande externe ?

Il existe trois méthodes de base pour exécuter des commandes externes :

system $cmd;        # en utilisant system()
my $output = `$cmd`;        # en utilisant les backticks (``)
open (my $pipe_fh, "$cmd |");    # en utilisant open()

Avec system(), STDOUT et STDERR iront au même endroit que le STDOUT et STDERR du script, sauf si la commande system() les redirige. Les backticks et open() ne lisent que le STDOUT de votre commande.

Vous pouvez également utiliser la fonction open3() d'IPC::Open3. Benjamin Goldberg fournit un exemple de code :

Pour capturer la sortie standard d'un programme, mais ignorer sa sortie d'erreur standard :

use IPC::Open3;
use File::Spec;
my $in = '';
open(NULL, ">", File::Spec->devnull);
my $pid = open3($in, \*PH, ">&NULL",
"cmd"); while( <PH> ) { } waitpid($pid, 0);

Pour capturer la sortie d'erreur standard (STDERR) d'un programme, mais ignorer sa sortie standard (STDOUT) :

use IPC::Open3;
use File::Spec;
my $in = '';
open(NULL, ">", File::Spec->devnull);
my $pid = open3($in, ">&NULL", \*PH, "cmd");
while( <PH> ) { }
waitpid($pid, 0);

Pour capturer la sortie d'erreur standard (STDERR) d'un programme, et laisser sa sortie standard (STDOUT) aller vers notre propre sortie d'erreur standard :

use IPC::Open3;
my $in = '';
my $pid = open3($in, ">&STDERR", \*PH, "cmd");
while( <PH> ) { }
waitpid($pid, 0);

Pour lire séparément la sortie standard (STDOUT) et la sortie d'erreur standard (STDERR) d'une commande, vous pouvez les rediriger vers des fichiers temporaires, laisser la commande s'exécuter, puis lire les fichiers temporaires :

use IPC::Open3;
use IO::File;
my $in = '';
local *CATCHOUT = IO::File->new_tmpfile;
local *CATCHERR = IO::File->new_tmpfile;
my $pid = open3($in, ">&CATCHOUT", ">&CATCHERR", "cmd");
waitpid($pid, 0);
seek $_, 0, 0 for \*CATCHOUT, \*CATCHERR;
while( <CATCHOUT> ) {}
while( <CATCHERR> ) {}

Mais il n'y a pas vraiment besoin que les deux soient des fichiers temporaires... ce qui suit devrait fonctionner tout aussi bien, sans interblocage :

use IPC::Open3;
my $in = '';
use IO::File;
local *CATCHERR = IO::File->new_tmpfile;
my $pid = open3($in, \*CATCHOUT, ">&CATCHERR", "cmd");
while( <CATCHOUT> ) {}
waitpid($pid, 0);
seek CATCHERR, 0, 0;
while( <CATCHERR> ) {}

Et ce sera aussi plus rapide, puisque nous pouvons commencer à traiter la sortie standard du programme immédiatement, au lieu d'attendre que le programme se termine.

Avec l'une de ces méthodes, vous pouvez changer les descripteurs de fichiers avant l'appel :

open(STDOUT, ">logfile");
system("ls");

ou vous pouvez utiliser la redirection de descripteurs de fichiers du shell Bourne :

$output = `$cmd 2>some_file`;
open (PIPE, "cmd 2>some_file |");

Vous pouvez également utiliser la redirection de descripteurs de fichiers pour faire de STDERR un duplicata de STDOUT :

$output = `$cmd 2>&1`;
open (PIPE, "cmd 2>&1 |");

Notez que vous ne pouvez *pas* simplement ouvrir STDERR pour qu'il soit un duplicata de STDOUT dans votre programme Perl et éviter d'appeler le shell pour effectuer la redirection. Cela ne fonctionne pas :

open(STDERR, ">&STDOUT");
$alloutput = `cmd args`;  # stderr s'échappe toujours

Cela échoue parce que open() fait pointer STDERR vers l'endroit où STDOUT pointait au moment de l'open(). Les backticks font ensuite pointer STDOUT vers une chaîne, mais ne modifient pas STDERR (qui pointe toujours vers l'ancien STDOUT).

Notez que vous *devez* utiliser la syntaxe de redirection du shell Bourne (sh(1)) dans les backticks, pas celle de csh(1) ! Les détails expliquant pourquoi system() et les ouvreurs de pipe et de backticks de Perl utilisent tous le shell Bourne se trouvent dans l'article versus/csh.whynot de la collection "Far More Than You Ever Wanted To Know" sur http://www.cpan.org/misc/olddoc/FMTEYEWTK.tgz. Pour capturer la sortie d'erreur standard (STDERR) et la sortie standard (STDOUT) d'une commande ensemble :

$output = `cmd 2>&1`;                       # soit avec des backticks
$pid = open(PH, "cmd 2>&1 |");              # soit avec un pipe ouvert
while (<PH>) { }                            #    plus une lecture

Pour capturer la sortie standard (STDOUT) d'une commande mais ignorer sa sortie d'erreur standard (STDERR) :

$output = `cmd 2>/dev/null`;                # soit avec des backticks
$pid = open(PH, "cmd 2>/dev/null |");       # soit avec un pipe ouvert
while (<PH>) { }                            #    plus une lecture

Pour capturer la sortie d'erreur standard (STDERR) d'une commande mais ignorer sa sortie standard (STDOUT) :

$output = `cmd 2>&1 1>/dev/null`;           # soit avec des backticks
$pid = open(PH, "cmd 2>&1 1>/dev/null |");  # soit avec un pipe ouvert
while (<PH>) { }                            #    plus une lecture

Pour échanger la sortie standard (STDOUT) et la sortie d'erreur standard (STDERR) d'une commande afin de capturer la sortie d'erreur standard (STDERR) tout en laissant sa sortie standard (STDOUT) sortir vers notre ancienne sortie d'erreur standard :

$output = `cmd 3>&1 1>&2 2>&3 3>&-`;        # soit avec des backticks
$pid = open(PH, "cmd 3>&1 1>&2 2>&3 3>&-|");# soit avec un pipe ouvert
while (<PH>) { }                            #    plus une lecture

Pour lire séparément la sortie standard (STDOUT) et la sortie d'erreur standard (STDERR) d'une commande, le plus simple est de les rediriger séparément vers des fichiers, puis de lire à partir de ces fichiers une fois le programme terminé :

system("program args 1>program.stdout 2>program.stderr");

L'ordre est important dans tous ces exemples. En effet, le shell traite les redirections de descripteurs de fichiers dans l'ordre strictement de gauche à droite.

system("prog args 1>tmpfile 2>&1");
system("prog args 2>&1 1>tmpfile");

La première commande envoie la sortie standard et la sortie d'erreur standard vers le fichier temporaire. La seconde commande n'y envoie que l'ancienne sortie standard, et l'ancienne sortie d'erreur standard apparaît sur l'ancienne sortie standard.

Pourquoi open() ne renvoie-t-il pas d'erreur lorsqu'un pipe ouvert échoue ?

Si le deuxième argument d'un open() de pipe contient des métacaractères du shell, perl fait un fork(), puis un exec() d'un shell pour décoder les métacaractères et finalement exécuter le programme désiré. Si le programme n'a pas pu être exécuté, c'est le shell qui reçoit le message, pas Perl. Tout ce que votre programme Perl peut savoir, c'est si le shell lui-même a pu être démarré avec succès. Vous pouvez toujours capturer la sortie d'erreur standard (STDERR) du shell et la vérifier pour des messages d'erreur. Voir "Comment puis-je capturer la sortie d'erreur standard (STDERR) d'une commande externe ?" ailleurs dans ce document, ou utiliser le module IPC::Open3.

S'il n'y a pas de métacaractères du shell dans l'argument de open(), Perl exécute la commande directement, sans utiliser le shell, et peut signaler correctement si la commande a été démarrée.

Qu'est-ce qui ne va pas avec l'utilisation des backticks dans un contexte vide ?

Strictement parlant, rien. Stylistiquement parlant, ce n'est pas une bonne façon d'écrire du code maintenable. Perl a plusieurs opérateurs pour exécuter des commandes externes. Les backticks en sont un ; ils collectent la sortie de la commande pour l'utiliser dans votre programme. La fonction "system" en est une autre ; elle ne fait pas cela.

Écrire des backticks dans votre programme envoie un message clair aux lecteurs de votre code que vous vouliez collecter la sortie de la commande. Pourquoi envoyer un message clair qui n'est pas vrai ?

Considérez cette ligne :

`cat /etc/termcap`;

Vous avez oublié de vérifier $? pour voir si le programme a même été exécuté correctement. Même si vous écriviez

print `cat /etc/termcap`;

ce code pourrait et devrait probablement être écrit comme :

system("cat /etc/termcap") == 0
or die "cat program failed!";

qui affichera la sortie de la commande cat au fur et à mesure de sa génération, au lieu d'attendre que le programme soit terminé pour l'imprimer. Il vérifie également la valeur de retour.

"system" fournit également un contrôle direct sur la possibilité que le traitement des jokers du shell ait lieu, alors que les backticks ne le font pas.

Comment puis-je appeler des backticks sans traitement par le shell ?

C'est un peu délicat. Vous ne pouvez pas simplement écrire la commande comme ceci :

@ok = `grep @opts '$search_string' @filenames`;

Depuis Perl 5.8.0, vous pouvez utiliser open() avec plusieurs arguments. Tout comme les formes de liste de system() et exec(), aucune échappatoire du shell ne se produit.

open( GREP, "-|", 'grep', @opts, $search_string, @filenames );
chomp(@ok = <GREP>);
close GREP;

Vous pouvez également :

my @ok = ();
if (open(GREP, "-|")) {
    while (<GREP>) {
        chomp;
        push(@ok, $_);
    }
    close GREP;
} else {
    exec 'grep', @opts, $search_string, @filenames;
}

Tout comme avec system(), aucune échappatoire du shell ne se produit lorsque vous exec() une liste. D'autres exemples de ceci se trouvent dans "Safe Pipe Opens" dans perlipc.

Notez que si vous utilisez Windows, aucune solution à ce problème agaçant n'est possible. Même si Perl émule fork(), vous serez toujours bloqué, car Windows n'a pas d'API de type argc/argv.

Pourquoi mon script ne peut-il pas lire depuis STDIN après que je lui ai donné EOF (^D sur Unix, ^Z sur MS-DOS) ?

Cela ne se produit que si votre perl est compilé pour utiliser stdio au lieu de perlio, ce qui est le défaut. Certains (peut-être tous ?) stdio définissent des indicateurs d'erreur et d'eof que vous devrez peut-être effacer. Le module POSIX définit clearerr() que vous pouvez utiliser. C'est la manière techniquement correcte de le faire. Voici quelques solutions de contournement moins fiables :

1.
Essayez de conserver le pointeur de recherche et d'y aller, comme ceci : 
my $where = tell($log_fh);
seek($log_fh, $where, 0);
2.
Si cela ne fonctionne pas, essayez de vous déplacer vers une partie différente du fichier, puis de revenir.
3.
Si cela ne fonctionne pas, essayez de vous déplacer vers une partie différente du fichier, de lire quelque chose, puis de revenir.
4.
Si cela ne fonctionne pas, abandonnez votre package stdio et utilisez sysread.

Comment puis-je convertir mon script shell en perl ?

Apprenez Perl et réécrivez-le. Sérieusement, il n'y a pas de convertisseur simple. Les choses qui sont difficiles à faire dans le shell sont faciles à faire en Perl, et cette difficulté même rendrait un convertisseur shell vers perl quasiment impossible à écrire. En le réécrivant, vous réfléchirez à ce que vous essayez vraiment de faire, et vous échapperez idéalement au paradigme du flux de données en pipeline du shell, qui, bien que pratique pour certaines choses, cause de nombreuses inefficacités.

Puis-je utiliser perl pour exécuter une session telnet ou ftp ?

Essayez les modules Net::FTP et Net::Telnet (disponibles sur CPAN). http://www.cpan.org/scripts/netstuff/telnet.emul.shar vous aidera également pour émuler le protocole telnet, mais Net::Telnet est probablement beaucoup plus facile à utiliser.

Si tout ce que vous voulez faire est de prétendre être telnet mais que vous n'avez pas besoin de la négociation initiale telnet, alors l'approche standard à double processus suffira :

use IO::Socket;             # nouveau en 5.004
my $handle = IO::Socket::INET->new('www.perl.com:80')
    or die "can't connect to port 80 on www.perl.com $!";
$handle->autoflush(
1); if (fork()) { # XXX: undef signifie échec select($handle); print while ; # tout de stdin vers le socket } else { print while <$handle>; # tout du socket vers stdout } close $handle; exit;

Comment puis-je écrire expect en Perl ?

Il fut un temps où il existait une bibliothèque appelée chat2.pl (qui faisait partie de la distribution standard de Perl), qui n'a jamais vraiment été terminée. Si vous la trouvez quelque part, ne l'utilisez pas. De nos jours, votre meilleure option est de consulter le module Expect disponible sur CPAN, qui nécessite également deux autres modules de CPAN, IO::Pty et IO::Stty.

Existe-t-il un moyen de cacher la ligne de commande de Perl aux programmes comme "ps" ?

Tout d'abord, notez que si vous faites cela pour des raisons de sécurité (pour éviter que des personnes ne voient des mots de passe, par exemple), vous devriez réécrire votre programme de manière à ce que les informations critiques ne soient jamais fournies en argument. Cacher les arguments ne rendra pas votre programme complètement sécurisé.

Pour modifier réellement la ligne de commande visible, vous pouvez assigner à la variable $0 comme documenté dans perlvar. Cela ne fonctionnera cependant pas sur tous les systèmes d'exploitation. Les programmes démons comme sendmail y placent leur état, comme ceci :

$0 = "orcus [en attente de connexions]";

J'ai {changé de répertoire, modifié mon environnement} dans un script Perl. Comment se fait-il que le changement ait disparu quand j'ai quitté le script ? Comment puis-je faire en sorte que mes changements soient visibles ?

Unix
Au sens le plus strict, cela ne peut pas être fait - le script s'exécute en tant que processus différent de celui du shell à partir duquel il a été lancé. Les modifications apportées à un processus ne sont pas reflétées dans son parent - seulement dans les enfants créés après la modification. Il existe des astuces de shell qui peuvent vous permettre de le simuler en faisant un eval() de la sortie du script dans votre shell ; consultez le FAQ de comp.unix.questions pour plus de détails.

Comment puis-je fermer le descripteur de fichier d'un processus sans attendre sa fin ?

En supposant que votre système prend en charge de telles choses, envoyez simplement un signal approprié au processus (voir "kill" dans perlfunc). Il est courant d'envoyer d'abord un signal TERM, d'attendre un peu, puis d'envoyer un signal KILL pour le terminer.

Comment puis-je créer un processus démon ?

Si par processus démon vous entendez un processus détaché (dissocié de son tty), alors le processus suivant est rapporté comme fonctionnant sur la plupart des systèmes de type Unix. Les utilisateurs non-Unix devraient consulter leur module Your_OS::Process pour d'autres solutions.

  • Ouvrez /dev/tty et utilisez l'ioctl TIOCNOTTY dessus. Voir tty(4) pour les détails. Ou mieux encore, vous pouvez simplement utiliser la fonction POSIX::setsid(), afin de ne pas avoir à vous soucier des groupes de processus.
  • Changez de répertoire pour /
  • Rouvrez STDIN, STDOUT et STDERR afin qu'ils ne soient pas connectés à l'ancien tty.
  • Mettez-vous en arrière-plan comme ceci : 
    fork && exit;

Le module Proc::Daemon, disponible sur CPAN, fournit une fonction pour effectuer ces actions pour vous.

Comment puis-je savoir si je suis en cours d'exécution en mode interactif ou non ?

(contribué par brian d foy)

C'est une question difficile à répondre, et la meilleure réponse n'est qu'une supposition.

Que voulez-vous vraiment savoir ? Si vous voulez simplement savoir si l'un de vos descripteurs de fichier est connecté à un terminal, vous pouvez essayer le test de fichier "-t" :

if( -t STDOUT ) {
    print "Je suis connecté à un terminal !\n";
}

Cependant, vous risquez d'être déçu si vous vous attendez à ce que cela signifie qu'il y a une vraie personne de l'autre côté. Avec le module Expect, un autre programme peut prétendre être une personne. Le programme pourrait même s'approcher de passer le test de Turing.

Le module IO::Interactive fait de son mieux pour vous donner une réponse. Sa fonction "is_interactive" renvoie un descripteur de fichier de sortie ; ce descripteur de fichier pointe vers la sortie standard si le module pense que la session est interactive. Sinon, le descripteur de fichier est un descripteur de fichier nul qui rejette simplement la sortie :

use IO::Interactive;
print { is_interactive } "Je pourrais aller à la sortie standard !\n";

Cela ne garantit toujours pas qu'une vraie personne répond à vos invites ou lit votre sortie.

Si vous voulez savoir comment gérer les tests automatisés pour votre distribution, vous pouvez vérifier l'environnement. Les CPAN Testers, par exemple, définissent la valeur de "AUTOMATED_TESTING" :

unless( $ENV{AUTOMATED_TESTING} ) {
    print "Bonjour testeur interactif !\n";
}

Comment puis-je délai une événement lent ?

Utilisez la fonction alarm(), probablement en conjonction avec un gestionnaire de signaux, comme documenté dans "Signals" dans perlipc et la section sur "Signals" dans le Camel. Vous pouvez également utiliser le module Sys::AlarmCall, plus flexible, disponible sur CPAN.

alarm() n'est pas implémentée sur toutes les versions de Windows. Consultez la documentation de votre version spécifique de Perl.

Comment puis-je définir des limites de CPU ?

(contribué par Xho)

Utilisez le module BSD::Resource de CPAN. Par exemple :

use BSD::Resource;
setrlimit(RLIMIT_CPU,10,20) or die $!;

Cela définit les limites douces et dures respectivement à 10 et 20 secondes. Après 10 secondes de temps CPU passé en exécution (pas en temps "mur"), le processus recevra un signal (XCPU sur certains systèmes) qui, s'il n'est pas intercepté, provoquera la terminaison du processus. Si ce signal est intercepté, alors après 10 secondes supplémentaires (20 secondes au total), le processus sera tué avec un signal non interceptable.

Consultez BSD::Resource et la documentation de votre système pour les détails sordides.

Comment puis-je éviter les zombies sur un système Unix ?

Utilisez le code de récupération de "Signals" dans perlipc pour appeler wait() lorsqu'un SIGCHLD est reçu, ou utilisez la technique du double fork décrite dans "Comment démarrer un processus en arrière-plan ?" dans perlfaq8.

Comment puis-je utiliser une base de données SQL ?

Le module DBI fournit une interface abstraite à la plupart des serveurs et types de bases de données, y compris Oracle, DB2, Sybase, mysql, Postgresql, ODBC, et les fichiers plats. Le module DBI accède à chaque type de base de données via un pilote de base de données, ou DBD. Vous pouvez voir une liste complète des pilotes disponibles sur CPAN : http://www.cpan.org/modules/by-module/DBD/ . Vous pouvez en lire plus sur DBI sur http://dbi.perl.org/ .

D'autres modules fournissent un accès plus spécifique : Win32::ODBC, Alzabo, "iodbc", et d'autres trouvés sur CPAN Search : https://metacpan.org/ .

Comment puis-je faire en sorte qu'un appel system() se termine en cas de contrôle-C ?

Vous ne pouvez pas. Vous devez imiter l'appel system() (voir perlipc pour des exemples de code) et ensuite avoir un gestionnaire de signaux pour le signal INT qui transmet le signal au sous-processus. Ou vous pouvez vérifier :

$rc = system($cmd);
if ($rc & 127) { die "mort par signal" }

Comment puis-je ouvrir un fichier sans bloquer ?

Si vous avez la chance d'utiliser un système qui prend en charge les lectures non bloquantes (la plupart des systèmes de type Unix le font), vous devez seulement utiliser le drapeau "O_NDELAY" ou "O_NONBLOCK" du module "Fcntl" en conjonction avec sysopen() :

use Fcntl;
sysopen(my $fh, "/foo/somefile", O_WRONLY|O_NDELAY|O_CREAT, 0644)
    or die "impossible d'ouvrir /foo/somefile : $!";

Comment puis-je faire la différence entre les erreurs du shell et de Perl ?

(réponse contribuée par brian d foy)

Lorsque vous exécutez un script Perl, quelque chose d'autre exécute le script pour vous, et cette chose peut afficher des messages d'erreur. Le script peut émettre ses propres avertissements et messages d'erreur. La plupart du temps, vous ne pouvez pas dire qui a dit quoi.

Vous ne pourrez probablement pas corriger la chose qui exécute perl, mais vous pouvez modifier la façon dont perl affiche ses avertissements en définissant des fonctions personnalisées d'avertissement et de mort.

Considérez ce script, qui contient une erreur que vous pourriez ne pas remarquer immédiatement.

#!/usr/locl/bin/perl
print "Bonjour le monde\n";

J'obtiens une erreur lorsque j'exécute ceci depuis mon shell (qui se trouve être bash). Cela peut ressembler à perl qui a oublié qu'il a une fonction print(), mais ma ligne shebang n'est pas le chemin vers perl, donc le shell exécute le script, et j'obtiens l'erreur.

$ ./test
./test : ligne 3 : print : commande introuvable

Une méthode rapide et sale

fix implique un peu de code, mais cela peut être tout ce dont vous avez besoin pour comprendre le problème.

#!/usr/bin/perl -w
BEGIN {
    $SIG{__WARN__} = sub{ print STDERR "Perl: ", @_; };
    $SIG{__DIE__}  = sub{ print STDERR "Perl: ", @_; exit 1};
}
$a = 1 + undef;
$x / 0;
__END__

Le message perl apparaît avec "Perl" en préfixe. Le bloc "BEGIN" fonctionne au moment de la compilation, donc toutes les erreurs et avertissements de compilation reçoivent aussi le préfixe "Perl:".

Perl: Useless use of division (/) in void context at ./test line 9.
Perl: Name "main::a" used only once: possible typo at ./test line 8.
Perl: Name "main::x" used only once: possible typo at ./test line 9.
Perl: Use of uninitialized value in addition (+) at ./test line 8.
Perl: Use of uninitialized value in division (/) at ./test line 9.
Perl: Illegal division by zero at ./test line 9.
Perl: Illegal division by zero at -e line 3.

Si je ne vois pas ce "Perl:", ce n'est pas de perl.

Vous pourriez aussi simplement connaître tous les messages d'erreur de perl, et bien qu'il y ait des personnes qui les connaissent tous, vous probablement pas. Cependant, ils devraient tous se trouver dans la page de manuel perldiag. Si vous ne trouvez pas l'erreur là-dedans, ce n'est probablement pas une erreur de perl.

Chercher chaque message n'est pas la méthode la plus facile, alors laissez perl le faire pour vous. Utilisez le pragma diagnostics qui transforme les messages normaux de perl en discussions plus longues sur le sujet.

use diagnostics;

Si vous n'obtenez pas un paragraphe ou deux de discussion étendue, il pourrait s'agir d'un message qui n'est pas de perl.

Comment puis-je installer un module depuis CPAN ?

(contribué par brian d foy)

Le moyen le plus simple est d'avoir un module également nommé CPAN pour le faire en utilisant la commande "cpan" qui est fournie avec Perl. Vous pouvez lui donner une liste de modules à installer :

$ cpan IO::Interactive Getopt::Whatever

Si vous préférez "CPANPLUS", c'est tout aussi simple :

$ cpanp i IO::Interactive Getopt::Whatever

Si vous voulez installer une distribution depuis le répertoire courant, vous pouvez dire à "CPAN.pm" d'installer "." (le point).

$ cpan .

Consultez la documentation de l'une de ces commandes pour voir ce que vous pouvez faire d'autre.

Si vous voulez essayer d'installer une distribution par vous-même, en résolvant toutes les dépendances vous-même, vous suivez l'un des deux chemins de construction possibles.

Pour les distributions qui utilisent Makefile.PL :

$ perl Makefile.PL
$ make test install

Pour les distributions qui utilisent Build.PL :

$ perl Build.PL
$ ./Build test
$ ./Build install

Certaines distributions peuvent avoir besoin de se lier à des bibliothèques ou à d'autres codes tiers, et leurs séquences de construction et d'installation peuvent être plus compliquées. Vérifiez tous les fichiers README ou INSTALL que vous pourriez trouver.

Quelle est la différence entre require et use ?

(contribué par brian d foy)

Perl exécute l'instruction "require" au moment de l'exécution. Une fois que Perl a chargé, compilé et exécuté le fichier, il ne fait rien d'autre. L'instruction "use" est identique à un "require" exécuté au moment de la compilation, mais Perl appelle également la méthode "import" pour le package chargé. Ces deux instructions sont identiques :

use MODULE qw(import list);
BEGIN {
    require MODULE;
    MODULE->import(import list);
}

Cependant, vous pouvez supprimer l'"import" en utilisant une liste d'importation explicite et vide. Les deux actions se déroulent toujours au moment de la compilation :

use MODULE ();
BEGIN {
    require MODULE;
}

Étant donné que "use" appelle également la méthode "import", la valeur réelle pour "MODULE" doit être un mot nu. C'est-à-dire que "use" ne peut pas charger de fichiers par nom, bien que "require" le puisse :

require "$ENV{HOME}/lib/Foo.pm"; # pas de recherche @INC !

Voir l'entrée pour "use" dans perlfunc pour plus de détails.

Comment puis-je conserver mon propre répertoire de modules/bibliothèques ?

Lorsque vous construisez des modules, indiquez à Perl où installer les modules.

Si vous souhaitez installer des modules pour votre propre usage, le moyen le plus simple pourrait être local::lib, que vous pouvez télécharger depuis CPAN. Il configure divers paramètres d'installation pour vous et utilise ces mêmes paramètres dans vos programmes.

Si vous souhaitez plus de flexibilité, vous devez configurer votre client CPAN pour votre situation particulière.

Pour les distributions basées sur "Makefile.PL", utilisez l'option INSTALL_BASE lors de la génération des Makefiles :

perl Makefile.PL INSTALL_BASE=/mydir/perl

Vous pouvez le définir dans votre configuration "CPAN.pm" afin que les modules s'installent automatiquement dans votre répertoire de bibliothèques privé lorsque vous utilisez le shell CPAN.pm :

% cpan
cpan> o conf makepl_arg INSTALL_BASE=/mydir/perl
cpan> o conf commit

Pour les distributions basées sur "Build.PL", utilisez l'option --install_base :

perl Build.PL --install_base /mydir/perl

Vous pouvez également configurer "CPAN.pm" pour qu'il utilise automatiquement cette option :

% cpan
cpan> o conf mbuild_arg "--install_base /mydir/perl"
cpan> o conf commit

INSTALL_BASE indique à ces outils de placer vos modules dans /mydir/perl/lib/perl5. Voir "Comment ajouter un répertoire à mon chemin d'inclusion (@INC) au moment de l'exécution ?" pour des détails sur la façon d'exécuter vos modules nouvellement installés.

Il y a une mise en garde avec INSTALL_BASE, car il agit différemment des paramètres PREFIX et LIB que les versions antérieures d'ExtUtils::MakeMaker recommandaient. INSTALL_BASE ne prend pas en charge l'installation de modules pour plusieurs versions de Perl ou différentes architectures sous le même répertoire. Vous devriez considérer si vous le voulez vraiment et, si c'est le cas, utiliser les anciens paramètres PREFIX et LIB. Voir la documentation d'ExtUtils::MakeMaker pour plus de détails.

Comment puis-je ajouter le répertoire où se trouve mon programme au chemin de recherche des modules/bibliothèques ?

(contribué par brian d foy)

Si vous connaissez déjà le répertoire, vous pouvez l'ajouter à @INC comme vous le feriez pour tout autre répertoire. Vous pourriez utiliser "use lib" si vous connaissez le répertoire au moment de la compilation :

use lib $directory;

L'astuce dans cette tâche consiste à trouver le répertoire. Avant que votre script ne fasse quoi que ce soit (comme un "chdir"), vous pouvez obtenir le répertoire de travail courant avec le module "Cwd", qui est fourni avec Perl :

BEGIN {
    use Cwd;
    our $directory = cwd;
}
use lib $directory;

Vous pouvez faire quelque chose de similaire avec la valeur de $0, qui contient le nom du script. Cela pourrait contenir un chemin relatif, mais "rel2abs" peut le transformer en chemin absolu. Une fois que vous avez le

BEGIN {
    use File::Spec::Functions qw(rel2abs);
    use File::Basename qw(dirname);
    my $path   = rel2abs( $0 );
    our $directory = dirname( $path );
}
use lib $directory;

Le module FindBin, qui est fourni avec Perl, pourrait fonctionner. Il trouve le répertoire du script en cours d'exécution et le place dans $Bin, que vous pouvez ensuite utiliser pour construire le bon chemin de bibliothèques :

use FindBin qw($Bin);

Vous pouvez également utiliser local::lib pour faire une grande partie de la même chose. Installez des modules en utilisant les paramètres de local::lib puis utilisez le module dans votre programme :

use local::lib; # configure une bibliothèque locale dans ~/perl5

Voir la documentation de local::lib pour plus de détails.

Comment puis-je ajouter un répertoire à mon chemin d'inclusion (@INC) au moment de l'exécution ?

Voici les méthodes suggérées pour modifier votre chemin d'inclusion, y compris les variables d'environnement, les options d'exécution et les instructions dans le code :

la variable d'environnement "PERLLIB"
$ export PERLLIB=/path/to/my/dir
$ perl program.pl
la variable d'environnement "PERL5LIB"
$ export PERL5LIB=/path/to/my/dir
$ perl program.pl
le drapeau de ligne de commande "perl -Idir"
$ perl -I/path/to/my/dir program.pl
le pragma "lib" :
use lib "$ENV{HOME}/myown_perllib";
le module local::lib :
use local::lib;
use local::lib "~/myown_perllib";

Où les modules sont-ils installés ?

Les modules sont installés au cas par cas (comme décrit dans les méthodes de la section précédente) et dans le système d'exploitation. Tous ces chemins sont stockés dans @INC, que vous pouvez afficher avec l'outil en ligne unique

perl -e 'print join("\n",@INC,"")'

Les mêmes informations sont affichées à la fin de la sortie de la commande

perl -V

Pour savoir où se trouve le code source d'un module, utilisez

perldoc -l Encode

pour afficher le chemin du module. Dans certains cas (par exemple, le module "AutoLoader"), cette commande affichera le chemin vers un fichier "pod" séparé ; le module lui-même devrait se trouver dans le même répertoire, avec une extension de fichier 'pm'.

Qu'est-ce que socket.ph et où puis-je le trouver ?

C'est un fichier de style Perl 4 définissant les valeurs des constantes réseau du système. Parfois, il

est intégré à l'aide de h2ph lors de l'installation de Perl, mais d'autres fois, ce n'est pas le cas. Les programmes modernes devraient utiliser "use Socket;" à la place.
