perf_event_open(2) Manuel des appels système perf_event_open(2)

NOM

perf_event_open - configurer la surveillance des performances

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <linux/perf_event.h>    /* Définition des constantes PERF_* */
#include <linux/hw_breakpoint.h> /* Définition des constantes HW_* */
#include <sys/syscall.h>         /* Définition des constantes SYS_* */
#include <unistd.h>
int syscall(SYS_perf_event_open, struct perf_event_attr *attr,
            pid_t pid, int cpu, int group_fd, unsigned long flags);

Note : glibc ne fournit pas d'enrobage pour perf_event_open(), rendant nécessaire l'utilisation de syscall(2).

DESCRIPTION

Étant donné une liste de paramètres, perf_event_open() retourne un descripteur de fichier, à utiliser dans des appels système ultérieurs (read(2), mmap(2), prctl(2), fcntl(2), etc.).

Un appel à perf_event_open() crée un descripteur de fichier qui permet de mesurer des informations de performance. Chaque descripteur de fichier correspond à un événement mesuré ; ceux-ci peuvent être groupés pour mesurer plusieurs événements simultanément.

Les événements peuvent être activés et désactivés de deux manières : via ioctl(2) et via prctl(2). Quand un événement est désactivé, il ne compte pas et ne génère pas d'overflows mais continue d'exister et de maintenir sa valeur de compteur.

Les événements sont de deux types : de comptage et échantillonnés. Un événement de comptage est utilisé pour compter le nombre agrégé d'événements qui se produisent. En général, les résultats des événements de comptage sont collectés avec un appel read(2). Un événement d'échantillonnage écrit périodiquement des mesures dans un tampon qui peut ensuite être accédé via mmap(2).

Arguments

Les arguments pid et cpu permettent de spécifier quel processus et quel CPU surveiller :

pid == 0 et cpu == -1
Cela mesure le processus/thread appelant sur n'importe quel CPU.
pid == 0 et cpu >= 0
Cela mesure le processus/thread appelant uniquement lorsqu'il s'exécute sur le CPU spécifié.
pid > 0 et cpu == -1
Cela mesure le processus/thread spécifié sur n'importe quel CPU.
pid > 0 et cpu >= 0
Cela mesure le processus/thread spécifié uniquement lorsqu'il s'exécute sur le CPU spécifié.
pid == -1 et cpu >= 0
Cela mesure tous les processus/threads sur le CPU spécifié. Cela nécessite la capacité CAP_PERFMON (depuis Linux 5.8) ou CAP_SYS_ADMIN ou une valeur de /proc/sys/kernel/perf_event_paranoid inférieure à 1.
pid == -1 et cpu == -1
Ce réglage est invalide et retournera une erreur.

Lorsque pid est supérieur à zéro, la permission d'effectuer cet appel système est régie par CAP_PERFMON (depuis Linux 5.9) et une vérification du mode d'accès ptrace PTRACE_MODE_READ_REALCREDS sur les anciennes versions de Linux ; voir ptrace(2).

L'argument group_fd permet de créer des groupes d'événements. Un groupe d'événements a un événement qui est le leader du groupe. Le leader est créé en premier, avec group_fd = -1. Les autres membres du groupe sont créés avec des appels ultérieurs à perf_event_open() avec group_fd défini sur le descripteur de fichier du leader du groupe. (Un seul événement est créé avec group_fd = -1 et est considéré comme un groupe de 1 seul membre.) Un groupe d'événements est planifié sur le CPU en tant qu'unité : il ne sera mis sur le CPU que si tous les événements du groupe peuvent être mis sur le CPU. Cela signifie que les valeurs des événements membres peuvent être significativement comparées – additionnées, divisées (pour obtenir des ratios), et ainsi de suite – les unes aux autres, car elles ont compté des événements pour le même ensemble d'instructions exécutées.

L'argument flags est formé en combinant par OR zéro ou plus des valeurs suivantes :

PERF_FLAG_FD_CLOEXEC (depuis Linux 3.14)
Ce drapeau active le drapeau close-on-exec pour le descripteur de fichier d'événement créé, de sorte que le descripteur de fichier soit automatiquement fermé lors d'un execve(2). La définition des drapeaux close-on-exec au moment de la création, plutôt qu'ultérieurement avec fcntl(2), évite les conditions de concurrence potentielles où le thread appelant invoque perf_event_open() et fcntl(2) en même temps qu'un autre thread appelle fork(2) puis execve(2).
PERF_FLAG_FD_NO_GROUP
Ce drapeau indique à l'événement d'ignorer le paramètre group_fd, sauf dans le but de configurer la redirection de sortie à l'aide du drapeau PERF_FLAG_FD_OUTPUT.
PERF_FLAG_FD_OUTPUT (cassé depuis Linux 2.6.35)
Ce drapeau redirige la sortie échantillonnée de l'événement pour qu'elle soit incluse dans le tampon mmap de l'événement spécifié par group_fd.
PERF_FLAG_PID_CGROUP (depuis Linux 2.6.39)
Ce drapeau active la surveillance globale par conteneur (cgroup). Un conteneur est une abstraction qui isole un ensemble de ressources pour un contrôle plus fin (CPU, mémoire, etc.). Dans ce mode, l'événement n'est mesuré que si le thread s'exécutant sur le CPU surveillé appartient au conteneur (cgroup) désigné. Le cgroup est identifié en passant un descripteur de fichier ouvert sur son répertoire dans le système de fichiers cgroupfs. Par exemple, si le cgroup à surveiller s'appelle test, alors un descripteur de fichier ouvert sur /dev/cgroup/test (en supposant que cgroupfs est monté sur /dev/cgroup) doit être passé comme paramètre pid. La surveillance des cgroups n'est disponible que pour les événements système et peut donc nécessiter des permissions supplémentaires.

Les champs de la structure perf_event_attr sont décrits plus en détail ci-dessous :

type
Ce champ spécifie le type global d'événement. Il prend l'une des valeurs suivantes :
PERF_TYPE_HARDWARE
Indique l'un des événements matériels "généralisés" fournis par le noyau. Voir la définition du champ config pour plus de détails.
PERF_TYPE_SOFTWARE
Indique l'un des événements logiciels définis fournis par le noyau (même si aucun support matériel n'est disponible).
PERF_TYPE_TRACEPOINT
Indique un point de trace fourni par l'infrastructure de points de trace du noyau.
PERF_TYPE_HW_CACHE
Indique un événement de cache matériel. Ceci a un encodage spécial, décrit dans la définition du champ config.
PERF_TYPE_RAW
Indique un événement spécifique à l'implémentation "brut" dans le champ config.
PERF_TYPE_BREAKPOINT (depuis Linux 2.6.33)
Indique un point d'arrêt matériel tel que fourni par le CPU. Les points d'arrêt peuvent être des accès en lecture/écriture à une adresse ainsi que l'exécution d'une adresse d'instruction.
PMU dynamique
Depuis Linux 2.6.38, perf_event_open() peut supporter plusieurs PMU. Pour activer cela, une valeur exportée par le noyau peut être utilisée dans le champ type pour indiquer quelle PMU utiliser. La valeur à utiliser se trouve dans le système de fichiers sysfs : il y a un sous-répertoire par instance de PMU sous /sys/bus/event_source/devices. Dans chaque sous-répertoire, il y a un fichier type dont le contenu est un entier qui peut être utilisé dans le champ type. Par exemple, /sys/bus/event_source/devices/cpu/type contient la valeur pour la PMU du CPU principal, qui est généralement 4.
kprobe
uprobe (tous deux depuis Linux 4.17)
Ces deux PMU dynamiques créent un kprobe/uprobe et l'attachent au descripteur de fichier généré par perf_event_open. Le kprobe/uprobe sera détruit lors de la destruction du descripteur de fichier. Voir les champs kprobe_func, uprobe_path, kprobe_addr et probe_offset pour plus de détails.
size
La taille de la structure perf_event_attr pour la compatibilité avant/arrière. Définissez ceci en utilisant sizeof(struct perf_event_attr) pour permettre au noyau de connaître la taille de la structure au moment de la compilation.
La définition associée PERF_ATTR_SIZE_VER0 est définie à 64 ; c'était la taille de la première structure publiée. PERF_ATTR_SIZE_VER1 est 72, correspondant à l'ajout des points d'arrêt dans Linux 2.6.33. PERF_ATTR_SIZE_VER2 est 80 correspondant à l'ajout de l'échantillonnage de branche dans Linux 3.4. PERF_ATTR_SIZE_VER3 est 96 correspondant à l'ajout de sample_regs_user et sample_stack_user dans Linux 3.7. PERF_ATTR_SIZE_VER4 est 104 correspondant à l'ajout de sample_regs_intr dans Linux 3.19. PERF_ATTR_SIZE_VER5 est 112 correspondant à l'ajout de aux_watermark dans Linux 4.1.
config
Ceci spécifie quel événement vous souhaitez, en conjonction avec le champ type. Les champs config1 et config2 sont également pris en compte dans les cas où 64 bits ne suffisent pas pour spécifier entièrement l'événement. L'encodage de ces champs dépend de l'événement.
Il existe diverses façons de définir le champ config qui dépendent de la valeur du champ type décrit précédemment. Ce qui suit sont diverses paramètres possibles pour config séparés par type.
Si type est PERF_TYPE_HARDWARE, nous mesurons l'un des événements CPU matériels généralisés. Tous ne sont pas disponibles sur toutes les plateformes. Définissez config sur l'une des valeurs suivantes :
PERF_COUNT_HW_CPU_CYCLES
Cycles totaux. Soyez prudent quant à ce qui se passe lors de la mise à l'échelle de la fréquence du CPU.
PERF_COUNT_HW_INSTRUCTIONS
Instructions traitées. Attention, celles-ci peuvent être affectées par divers problèmes, notamment les comptes d'interruptions matérielles.
PERF_COUNT_HW_CACHE_REFERENCES
Accès au cache. Généralement, cela indique les accès au cache de dernier niveau, mais cela peut varier en fonction de votre CPU. Cela peut inclure les prédictions et les messages de cohérence ; encore une fois, cela dépend de la conception de votre CPU.
PERF_COUNT_HW_CACHE_MISSES
Manques de cache. Généralement, cela indique les manques au cache de dernier niveau ; ceci est destiné à être utilisé en conjonction avec l'événement PERF_COUNT_HW_CACHE_REFERENCES pour calculer les taux de manques de cache.
PERF_COUNT_HW_BRANCH_INSTRUCTIONS
Instructions de branchement traitées. Avant Linux 2.6.35, cela utilisait le mauvais événement sur les processeurs AMD.
PERF_COUNT_HW_BRANCH_MISSES
Instructions de branchement mal prédites.
PERF_COUNT_HW_BUS_CYCLES
Cycles de bus, qui peuvent être différents des cycles totaux.
PERF_COUNT_HW_STALLED_CYCLES_FRONTEND (depuis Linux 3.0)
Cycles bloqués lors de l'émission.
PERF_COUNT_HW_STALLED_CYCLES_BACKEND (depuis Linux 3.0)
Cycles bloqués lors du retrait.
PERF_COUNT_HW_REF_CPU_CYCLES (depuis Linux 3.3)
Cycles totaux ; non affectés par la mise à l'échelle de la fréquence du CPU.
Si type est PERF_TYPE_SOFTWARE, nous mesurons des événements logiciels fournis par le noyau. Définissez config sur l'une des valeurs suivantes :
PERF_COUNT_SW_CPU_CLOCK
Ceci rapporte l'horloge du CPU, une minuterie par CPU à haute résolution.
PERF_COUNT_SW_TASK_CLOCK
Ceci rapporte un compte d'horloge spécifique à la tâche en cours d'exécution.
PERF_COUNT_SW_PAGE_FAULTS
Ceci rapporte le nombre de défauts de page.
PERF_COUNT_SW_CONTEXT_SWITCHES
Ceci compte les commutations de contexte. Jusqu'à Linux 2.6.34, celles-ci étaient toutes rapportées comme des événements utilisateur, après quoi elles sont rapportées comme se produisant dans le noyau.
PERF_COUNT_SW_CPU_MIGRATIONS
Ceci rapporte le nombre de fois où le processus a migré vers un nouveau CPU.
PERF_COUNT_SW_PAGE_FAULTS_MIN
Ceci compte le nombre de défauts de page mineurs. Ceux-ci n'ont pas nécessité d'E/S disque pour être traités.
PERF_COUNT_SW_PAGE_FAULTS_MAJ
Ceci compte le nombre de défauts de page majeurs. Ceux-ci ont nécessité des E/S disque pour être traités.
PERF_COUNT_SW_ALIGNMENT_FAULTS (depuis Linux 2.6.33)
Ceci compte le nombre de fautes d'alignement. Celles-ci se produisent lorsque des accès mémoire non alignés ont lieu ; le noyau peut les gérer mais cela réduit les performances. Ceci ne se produit que sur certaines architectures (jamais sur x86).
PERF_COUNT_SW_EMULATION_FAULTS (depuis Linux 2.6.33)
Ceci compte le nombre de fautes d'émulation. Le noyau intercepte parfois des instructions non implémentées et les émule pour l'espace utilisateur. Cela peut avoir un impact négatif sur les performances.
PERF_COUNT_SW_DUMMY (depuis Linux 3.12)
Ceci est un événement factice qui ne compte rien. Les types d'enregistrements d'échantillons informationnels tels que mmap ou comm doivent être associés à un événement actif. Cet événement factice permet de collecter de tels enregistrements sans nécessiter d'événement de comptage.
PERF_COUNT_SW_BPF_OUTPUT (depuis Linux 4.4)
Ceci est utilisé pour générer des données d'échantillon brutes à partir de BPF. Les programmes BPF peuvent écrire dans cet événement à l'aide de l'aide bpf_perf_event_output.
PERF_COUNT_SW_CGROUP_SWITCHES (depuis Linux 5.13)
Ceci compte les changements de contexte vers une tâche dans un cgroup différent. En d'autres termes, si la tâche suivante est dans le même cgroup, le changement ne sera pas compté.
Si type est PERF_TYPE_TRACEPOINT, alors nous mesurons des tracepoints du noyau. La valeur à utiliser dans config peut être obtenue sous debugfs tracing/events/*/*/id si ftrace est activé dans le noyau.
Si type est PERF_TYPE_HW_CACHE, alors nous mesurons un événement de cache CPU matériel. Pour calculer la valeur config appropriée, utilisez l'équation suivante : 


config = (perf_hw_cache_id) |
         (perf_hw_cache_op_id << 8) |
         (perf_hw_cache_op_result_id << 16);

où perf_hw_cache_id est l'un des éléments suivants :

PERF_COUNT_HW_CACHE_L1D
pour mesurer le cache de données de niveau 1
PERF_COUNT_HW_CACHE_L1I
pour mesurer le cache d'instructions de niveau 1
PERF_COUNT_HW_CACHE_LL
pour mesurer le cache de dernier niveau
PERF_COUNT_HW_CACHE_DTLB
pour mesurer le TLB de données
PERF_COUNT_HW_CACHE_ITLB
pour mesurer le TLB d'instructions
PERF_COUNT_HW_CACHE_BPU
pour mesurer l'unité de prédiction de branchement
PERF_COUNT_HW_CACHE_NODE (depuis Linux 3.1)
pour mesurer les accès mémoire locaux

et perf_hw_cache_op_id est l'un des éléments suivants :

PERF_COUNT_HW_CACHE_OP_READ
pour les accès en lecture
PERF_COUNT_HW_CACHE_OP_WRITE
pour les accès en écriture
PERF_COUNT_HW_CACHE_OP_PREFETCH
pour les accès de préchargement

et perf_hw_cache_op_result_id est l'un des éléments suivants :

PERF_COUNT_HW_CACHE_RESULT_ACCESS
pour mesurer les accès
PERF_COUNT_HW_CACHE_RESULT_MISS
pour mesurer les manques

Si type est PERF_TYPE_RAW, alors une valeur config "brute" personnalisée est nécessaire. La plupart des CPU prennent en charge des événements qui ne sont pas couverts par les événements "généralisés". Ceux-ci sont définis par l'implémentation ; consultez le manuel de votre CPU (par exemple, la documentation Intel Volume 3B, ou le guide du développeur BIOS et du noyau AMD). La bibliothèque libpfm4 peut être utilisée pour traduire le nom des manuels architecturaux en la valeur hexadécimale brute attendue par perf_event_open() dans ce champ.

Si type est PERF_TYPE_BREAKPOINT, laissez config défini à zéro. Ses paramètres sont définis ailleurs.

Si type est kprobe ou uprobe, définissez retprobe (bit 0 de config, voir /sys/bus/event_source/devices/[k,u]probe/format/retprobe) pour kretprobe/uretprobe. Voir les champs kprobe_func, uprobe_path, kprobe_addr et probe_offset pour plus de détails.

kprobe_func
uprobe_path
kprobe_addr
probe_offset
Ces champs décrivent le kprobe/uprobe pour les PMU dynamiques kprobe et uprobe. Pour kprobe : utilisez kprobe_func et probe_offset, ou utilisez kprobe_addr et laissez kprobe_func défini à NULL. Pour uprobe : utilisez uprobe_path et probe_offset.
sample_period
sample_freq
Un événement "d'échantillonnage" est celui qui génère une notification de débordement tous les N événements, où N est donné par sample_period. Un événement d'échantillonnage a sample_period > 0. Lorsqu'un débordement se produit, les données demandées sont enregistrées dans le tampon mmap. Le champ sample_type contrôle quelles données sont enregistrées lors de chaque débordement.
sample_freq peut être utilisé si vous souhaitez utiliser la fréquence plutôt que la période. Dans ce cas, vous définissez le drapeau freq. Le noyau ajustera la période d'échantillonnage pour tenter d'atteindre le taux souhaité. Le taux d'ajustement est un tick de timer.
sample_type
Les différents bits de ce champ spécifient quelles valeurs inclure dans l'échantillon. Elles seront enregistrées dans un tampon circulaire, accessible à l'espace utilisateur via mmap(2). L'ordre dans lequel les valeurs sont sauvegardées dans l'échantillon est documenté dans la sous-section Disposition MMAP ci-dessous ; ce n'est pas l'ordre de enum perf_event_sample_format.
PERF_SAMPLE_IP
Enregistre le pointeur d'instruction.
PERF_SAMPLE_TID
Enregistre les identifiants de processus et de thread.
PERF_SAMPLE_TIME
Enregistre un horodatage.
PERF_SAMPLE_ADDR
Enregistre une adresse, si applicable.
PERF_SAMPLE_READ
Enregistre les valeurs de compteur pour tous les événements d'un groupe, pas seulement pour le chef de groupe.
PERF_SAMPLE_CALLCHAIN
Enregistre la chaîne d'appels (trace de pile).
PERF_SAMPLE_ID
Enregistre un identifiant unique pour le chef de groupe de l'événement ouvert.
PERF_SAMPLE_CPU
Enregistre le numéro du CPU.
PERF_SAMPLE_PERIOD
Enregistre la période d'échantillonnage actuelle.
PERF_SAMPLE_STREAM_ID
Enregistre un identifiant unique pour l'événement ouvert. Contrairement à PERF_SAMPLE_ID, l'ID réel est retourné, pas le chef de groupe. Cet ID est le même que celui retourné par PERF_FORMAT_ID.
PERF_SAMPLE_RAW
Enregistre des données supplémentaires, si applicable. Généralement retourné par les événements de tracepoint.
PERF_SAMPLE_BRANCH_STACK (depuis Linux 3.4)
Ceci fournit un enregistrement des branches récentes, tel que fourni par le matériel d'échantillonnage de branches du CPU (tel que le Last Branch Record d'Intel). Tout le matériel ne prend pas en charge cette fonctionnalité.
Voir le champ branch_sample_type pour savoir comment filtrer les branches signalées.
PERF_SAMPLE_REGS_USER (depuis Linux 3.7)
Enregistre l'état actuel des registres CPU au niveau utilisateur (les valeurs dans le processus avant que le noyau ne soit appelé).
PERF_SAMPLE_STACK_USER (depuis Linux 3.7)
Enregistre la pile au niveau utilisateur, permettant le déroulement de la pile.
PERF_SAMPLE_WEIGHT (depuis Linux 3.10)
Enregistre une valeur de poids fournie par le matériel qui exprime le coût de l'événement échantillonné. Cela permet au matériel de mettre en évidence les événements coûteux dans un profil.
PERF_SAMPLE_DATA_SRC (depuis Linux 3.10)
Enregistre la source de données : d'où dans la hiérarchie mémoire provenaient les données associées à l'instruction échantillonnée. Ceci n'est disponible que si le matériel sous-jacent prend en charge cette fonctionnalité.
PERF_SAMPLE_IDENTIFIER (depuis Linux 3.12)
Place la valeur SAMPLE_ID dans une position fixe dans l'enregistrement, soit au début (pour les événements d'échantillon), soit à la fin (s'il s'agit d'un événement non-échantillon).
Ceci était nécessaire car un flux d'échantillons peut contenir des enregistrements provenant de divers événements
sources avec des paramètres sample_type différents. Il n'a pas été possible d'analyser correctement le flux d'événements car le format de l'enregistrement était nécessaire pour trouver SAMPLE_ID, mais le format n'a pas pu être trouvé sans savoir à quel événement l'échantillon appartenait (ce qui entraînait une dépendance circulaire).
Le paramètre PERF_SAMPLE_IDENTIFIER rend le flux d'événements toujours analysable en plaçant SAMPLE_ID dans un emplacement fixe, même si cela implique d'avoir des valeurs SAMPLE_ID en double dans les enregistrements.
PERF_SAMPLE_TRANSACTION (depuis Linux 3.13)
Enregistre les raisons des événements d'abandon de mémoire transactionnelle (par exemple, du support de mémoire transactionnelle Intel TSX).
Le paramètre precise_ip doit être supérieur à 0 et un événement d'abandon de mémoire transactionnelle doit être mesuré, sinon aucune valeur ne sera enregistrée. Notez également que certaines mesures perf_event, telles que le comptage de cycles échantillonnés, peuvent provoquer des abandons parasites (en provoquant une interruption pendant une transaction).
PERF_SAMPLE_REGS_INTR (depuis Linux 3.19)
Enregistre un sous-ensemble de l'état actuel des registres du processeur tel que spécifié par sample_regs_intr. Contrairement à PERF_SAMPLE_REGS_USER, les valeurs des registres retourneront l'état des registres du noyau si le dépassement s'est produit pendant l'exécution du code du noyau. Si le processeur prend en charge l'échantillonnage matériel de l'état des registres (par exemple, PEBS sur Intel x86) et que precise_ip est défini à une valeur supérieure à zéro, les valeurs de registres retournées sont celles capturées par le matériel au moment de la retraite de l'instruction échantillonnée.
PERF_SAMPLE_PHYS_ADDR (depuis Linux 4.13)
Enregistre l'adresse physique des données comme dans PERF_SAMPLE_ADDR.
PERF_SAMPLE_CGROUP (depuis Linux 5.7)
Enregistre l'ID du cgroup (perf_event) du processus. Ceci correspond au champ id de l'événement PERF_RECORD_CGROUP.
PERF_SAMPLE_DATA_PAGE_SIZE (depuis Linux 5.11)
Enregistre la taille de page des données comme dans PERF_SAMPLE_ADDR.
PERF_SAMPLE_CODE_PAGE_SIZE (depuis Linux 5.11)
Enregistre la taille de page de l'IP comme dans PERF_SAMPLE_IP.
PERF_SAMPLE_WEIGHT_STRUCT (depuis Linux 5.12)
Enregistre les valeurs de poids fournies par le matériel comme dans PERF_SAMPLE_WEIGHT, mais il peut représenter plusieurs valeurs dans une structure. Il partage le même espace que PERF_SAMPLE_WEIGHT, les utilisateurs peuvent donc en appliquer l'un ou l'autre, mais pas les deux. Il a le format suivant et la signification de chaque champ dépend de l'implémentation matérielle.


union perf_sample_weight {
    u64  full;           /* PERF_SAMPLE_WEIGHT */
    struct {             /* PERF_SAMPLE_WEIGHT_STRUCT */
        u32  var1_dw;
        u16  var2_w;
        u16  var3_w;
    };
};
read_format
Ce champ spécifie le format des données renvoyées par read(2) sur un descripteur de fichier perf_event_open().
PERF_FORMAT_TOTAL_TIME_ENABLED
Ajoute le champ time_enabled de 64 bits. Ceci peut être utilisé pour calculer des totaux estimés si le PMU est sur-engagé et que le multiplexage se produit.
PERF_FORMAT_TOTAL_TIME_RUNNING
Ajoute le champ time_running de 64 bits. Ceci peut être utilisé pour calculer des totaux estimés si le PMU est sur-engagé et que le multiplexage se produit.
PERF_FORMAT_ID
Ajoute une valeur unique de 64 bits qui correspond au groupe d'événements.
PERF_FORMAT_GROUP
Permet de lire toutes les valeurs de compteurs d'un groupe d'événements avec une seule lecture.
PERF_FORMAT_LOST (depuis Linux 6.0)
Ajoute une valeur de 64 bits représentant le nombre d'échantillons perdus pour cet événement. Ceci n'aurait de sens que si sample_period ou sample_freq est défini.
disabled
Le bit disabled spécifie si le compteur démarre désactivé ou activé. S'il est désactivé, l'événement peut être activé ultérieurement par ioctl(2), prctl(2), ou enable_on_exec.
Lors de la création d'un groupe d'événements, le chef de groupe est généralement initialisé avec le bit disabled défini à 1 et les événements enfants sont initialisés avec le bit disabled défini à 0. Malgré le fait que disabled soit à 0, les événements enfants ne démarreront pas tant que le chef de groupe n'est pas activé.
inherit
Le bit inherit spécifie que ce compteur doit compter les événements des tâches enfants ainsi que ceux de la tâche spécifiée. Cela s'applique uniquement aux nouveaux enfants, et non aux enfants existants au moment de la création du compteur (ni aux nouveaux enfants des enfants existants).
L'héritage ne fonctionne pas pour certaines combinaisons de valeurs de read_format, telles que PERF_FORMAT_GROUP. De plus, son utilisation avec cpu == -1 empêche la création du tampon circulaire mmap utilisé pour l'enregistrement asynchrone des événements en mode échantillonné.
pinned
Le bit pinned spécifie que le compteur doit toujours être sur le processeur si possible. Il s'applique uniquement aux compteurs matériels et uniquement aux chefs de groupe. Si un compteur épinglé ne peut pas être placé sur le processeur (par exemple, parce qu'il n'y a pas assez de compteurs matériels ou à cause d'un conflit avec un autre événement), le compteur entre dans un état « erreur », où les lectures renvoient la fin de fichier (c'est-à-dire que read(2) renvoie 0) jusqu'à ce que le compteur soit ultérieurement activé ou désactivé.
exclusive
Le bit exclusive spécifie que lorsque le groupe de ce compteur est sur le processeur, il doit être le seul groupe à utiliser les compteurs du processeur. À l'avenir, cela pourrait permettre aux programmes de surveillance de prendre en charge des fonctionnalités de PMU qui doivent s'exécuter seuls afin de ne pas perturber d'autres compteurs matériels.
Notez que de nombreuses situations inattendues peuvent empêcher l'exécution des événements dont le bit exclusive est défini. Cela inclut tout utilisateur exécutant une mesure à l'échelle du système ainsi que toute utilisation du noyau des compteurs de performance (y compris l'interface NMI Watchdog Timer couramment activée).
exclude_user
Si ce bit est défini, le décompte exclut les événements qui se produisent dans l'espace utilisateur.
exclude_kernel
Si ce bit est défini, le décompte exclut les événements qui se produisent dans l'espace noyau.
exclude_hv
Si ce bit est défini, le décompte exclut les événements qui se produisent dans l'hyperviseur. Ceci est principalement destiné aux PMU qui ont un support intégré pour gérer cela (comme POWER). Un support supplémentaire est nécessaire pour gérer les mesures de l'hyperviseur sur la plupart des machines.
exclude_idle
Si défini, ne pas compter lorsque le processeur exécute la tâche idle. Bien que vous puissiez actuellement activer cela pour tout type d'événement, il est ignoré pour tous les événements sauf les événements logiciels.
mmap
Le bit mmap active la génération d'échantillons PERF_RECORD_MMAP pour chaque appel à mmap(2) qui a PROT_EXEC défini. Cela permet aux outils de remarquer le nouveau code exécutable étant mappé dans un programme (bibliothèques partagées dynamiques par exemple) afin que les adresses puissent être mappées au code original.
comm
Le bit comm active le suivi du nom de commande du processus tel que modifié par les appels système execve(2) et prctl(PR_SET_NAME) ainsi que par l'écriture dans /proc/self/comm. Si le drapeau comm_exec est également défini avec succès (possible depuis Linux 3.16), alors le drapeau divers PERF_RECORD_MISC_COMM_EXEC peut être utilisé pour différencier le cas execve(2) des autres.
freq
Si ce bit est défini, alors sample_frequency et non sample_period est utilisé lors de la configuration de l'intervalle d'échantillonnage.
inherit_stat
Ce bit active l'enregistrement des comptes d'événements lors des changements de contexte pour les tâches héritées. Ceci n'est significatif que si le champ inherit est défini.
enable_on_exec
Si ce bit est défini, un compteur est automatiquement activé après un appel à execve(2).
task
Si ce bit est défini, alors les notifications de fork/exit sont incluses dans le tampon circulaire.
watermark
Si défini, une notification de dépassement se produit lorsque l'on franchit le seuil wakeup_watermark. Sinon, les notifications de dépassement se produisent après wakeup_events échantillons.
precise_ip (depuis Linux 2.6.35)
Ceci contrôle le niveau de décalage (skid). Le décalage est le nombre d'instructions exécutées entre la survenue d'un événement d'intérêt et la capacité du noyau à s'arrêter et à enregistrer l'événement. Un décalage plus petit est préférable et permet un rapport plus précis des événements correspondant aux instructions, mais le matériel est souvent limité quant à la valeur minimale possible.
Les valeurs possibles de ce champ sont les suivantes :
0
SAMPLE_IP peut avoir un décalage arbitraire.
1
SAMPLE_IP
must have constant skid.
2
SAMPLE_IP requested to have 0 skid.
3
SAMPLE_IP must have 0 skid. See also the description of PERF_RECORD_MISC_EXACT_IP.
mmap_data (depuis Linux 2.6.36)
C'est l'homologue du champ mmap. Cela permet la génération de échantillons PERF_RECORD_MMAP pour les appels mmap(2) qui n'ont pas l'indicateur PROT_EXEC défini (par exemple, mémoire partagée de données et SysV).
sample_id_all (depuis Linux 2.6.38)
Si défini, alors TID, TIME, ID, STREAM_ID et CPU peuvent également être inclus dans les enregistrements autres que PERF_RECORD_SAMPLE si le sample_type correspondant est sélectionné.
Si PERF_SAMPLE_IDENTIFIER est spécifié, alors une valeur d'ID supplémentaire est incluse comme dernière valeur pour faciliter l'analyse du flux d'enregistrements. Cela peut entraîner l'apparition du valeur id deux fois.
La disposition est décrite par cette pseudo-structure :

struct sample_id {
    { u32 pid, tid; }   /* if PERF_SAMPLE_TID set */
    { u64 time;     }   /* if PERF_SAMPLE_TIME set */
    { u64 id;       }   /* if PERF_SAMPLE_ID set */
    { u64 stream_id;}   /* if PERF_SAMPLE_STREAM_ID set  */
    { u32 cpu, res; }   /* if PERF_SAMPLE_CPU set */
    { u64 id;       }   /* if PERF_SAMPLE_IDENTIFIER set */
};

exclude_host (depuis Linux 3.2)
Lors de la réalisation de mesures incluant des processus exécutant des instances VM (c'est-à-dire, ayant exécuté un ioctl(2) KVM_RUN), ne mesurer que les événements se produisant à l'intérieur d'une instance invitée. Ceci n'est significatif qu'à l'extérieur des invités ; ce réglage ne modifie pas les comptages collectés à l'intérieur d'un invité. Actuellement, cette fonctionnalité est uniquement x86.
exclude_guest (depuis Linux 3.2)
Lors de la réalisation de mesures incluant des processus exécutant des instances VM (c'est-à-dire, ayant exécuté un ioctl(2) KVM_RUN), ne pas mesurer les événements se produisant à l'intérieur des instances invitées. Ceci n'est significatif qu'à l'extérieur des invités ; ce réglage ne modifie pas les comptages collectés à l'intérieur d'un invité. Actuellement, cette fonctionnalité est uniquement x86.
exclude_callchain_kernel (depuis Linux 3.7)
Ne pas inclure les chaînes d'appels du noyau.
exclude_callchain_user (depuis Linux 3.7)
Ne pas inclure les chaînes d'appels utilisateur.
mmap2 (depuis Linux 3.16)
Génère un enregistrement mmap exécutable étendu qui contient suffisamment d'informations supplémentaires pour identifier de manière unique les mappings partagés. L'indicateur mmap doit également être défini pour que cela fonctionne.
comm_exec (depuis Linux 3.16)
Ceci est purement un indicateur de détection de fonctionnalités, il ne modifie pas le comportement du noyau. Si cet indicateur peut être défini avec succès, alors, lorsque comm est activé, l'indicateur PERF_RECORD_MISC_COMM_EXEC sera défini dans le champ misc de l'en-tête d'un enregistrement comm si l'événement de renommage signalé était causé par un appel à execve(2). Cela permet aux outils de distinguer les différents types de renommage de processus.
use_clockid (depuis Linux 4.1)
Cela permet de sélectionner l'horloge Linux interne à utiliser lors de la génération d'horodatages via le champ clockid. Cela peut faciliter la corrélation des temps d'échantillonnage perf avec les horodatages générés par d'autres outils.
context_switch (depuis Linux 4.3)
Cela active la génération d'enregistrements PERF_RECORD_SWITCH lors d'un changement de contexte. Cela active également la génération d'enregistrements PERF_RECORD_SWITCH_CPU_WIDE lors de l'échantillonnage en mode CPU complet. Cette fonctionnalité s'ajoute aux événements tracepoint et logiciels existants pour mesurer les changements de contexte. L'avantage de cette méthode est qu'elle fournira des informations complètes même avec des paramètres perf_event_paranoid stricts.
write_backward (depuis Linux 4.6)
Cela fait que le tampon circulaire est écrit de la fin vers le début. Ceci est destiné à supporter la lecture depuis un tampon circulaire pouvant être écrasé.
namespaces (depuis Linux 4.11)
Cela active la génération d'enregistrements PERF_RECORD_NAMESPACES lorsqu'une tâche entre dans un nouveau namespace. Chaque namespace a une combinaison de numéros de périphérique et d'inœuds.
ksymbol (depuis Linux 5.0)
Cela active la génération d'enregistrements PERF_RECORD_KSYMBOL lorsque de nouveaux symboles du noyau sont enregistrés ou désenregistrés. Ceci est pour l'analyse des fonctions dynamiques du noyau comme eBPF.
bpf_event (depuis Linux 5.0)
Cela active la génération d'enregistrements PERF_RECORD_BPF_EVENT lorsqu'un programme eBPF est chargé ou déchargé.
aux_output (depuis Linux 5.4)
Cela permet aux événements normaux (non-AUX) de générer des données pour les événements AUX si le matériel le prend en charge.
cgroup (depuis Linux 5.7)
Cela active la génération d'enregistrements PERF_RECORD_CGROUP lorsqu'un nouveau cgroup est créé (et activé).
text_poke (depuis Linux 5.8)

build_id (depuis Linux 5.12)
Cela modifie le contenu de PERF_RECORD_MMAP2 pour contenir un identifiant de construction (build-id) au lieu des numéros de périphérique et d'inœuds.
inherit_thread (depuis Linux 5.13)
Cela désactive l'héritage de l'événement à un processus enfant. Seules les nouvelles threads du même processus (clonées avec CLONE_THREAD) hériteront de l'événement.
remove_on_exec (depuis Linux 5.13)
Cela ferme l'événement lorsqu'il démarre une nouvelle image de processus via execve(2).
sigtrap (depuis Linux 5.13)
Cela active la livraison synchrone du signal SIGTRAP en cas de débordement d'événement.
wakeup_events
wakeup_watermark
Cet union définit combien d'échantillons (wakeup_events) ou d'octets (wakeup_watermark) se produisent avant qu'une notification de débordement ne survienne. Lequel est utilisé est sélectionné par l'indicateur de bit watermark.

Ceci choisit le type de point d'arrêt. C'est l'une des options suivantes :

HW_BREAKPOINT_W

C'est l'adresse du point d'arrêt. Pour les points d'arrêt d'exécution, il s'agit de l'adresse mémoire de l'instruction d'intérêt ; pour les points d'arrêt de lecture et d'écriture, il s'agit de l'adresse mémoire de l'emplacement mémoire d'intérêt.
config1 (depuis Linux 2.6.39)

Lecture des résultats

Une fois qu'un descripteur de fichier perf_event_open() a été ouvert, les valeurs des événements peuvent être lues à partir du descripteur de fichier. Les valeurs qui s'y trouvent sont spécifiées par le champ read_format dans la structure attr lors de l'ouverture.

Si vous tentez de lire dans un tampon qui n'est pas assez grand pour contenir les données, l'erreur ENOSPC se produit.

Voici la disposition des données renvoyées par une lecture :

•
Si PERF_FORMAT_GROUP a été spécifié pour permettre la lecture de tous les événements d'un groupe à la fois :

struct read_format {
    u64 nr;            /* Le nombre d'événements */
    u64 time_enabled;  /* si PERF_FORMAT_TOTAL_TIME_ENABLED */
    u64 time_running;  /* si PERF_FORMAT_TOTAL_TIME_RUNNING */
    struct {
        u64 value;     /* La valeur de l'événement */
        u64 id;        /* si PERF_FORMAT_ID */
        u64 lost;      /* si PERF_FORMAT_LOST */
    } values[nr];
};

•
Si PERF_FORMAT_GROUP n'a *pas* été spécifié :

struct read_format {
    u64 value;         /* La valeur de l'événement */
    u64 time_enabled;  /* si PERF_FORMAT_TOTAL_TIME_ENABLED */
    u64 time_running;  /* si PERF_FORMAT_TOTAL_TIME_RUNNING */
    u64 id;            /* si PERF_FORMAT_ID */
    u64 lost;          /* si PERF_FORMAT_LOST */
};

Les valeurs lues sont les suivantes :

nr
Le nombre d'événements dans ce descripteur de fichier. Disponible uniquement si PERF_FORMAT_GROUP a été spécifié.
time_enabled
time_running
Temps total pendant lequel l'événement était activé et en cours d'exécution. Normalement, ces valeurs sont identiques. Le multiplexage se produit si le nombre d'événements est supérieur au nombre d'emplacements de compteur PMU disponibles. Dans ce cas, les événements ne s'exécutent qu'une partie du temps et les valeurs time_enabled et time running peuvent être utilisées pour ajuster une valeur estimée pour le décompte.
value
Une valeur de 64 bits non signée contenant le résultat du compteur.
id
Une valeur unique globalement pour cet événement particulier ; présent uniquement si PERF_FORMAT_ID a été spécifié dans read_format.
lost
Le nombre d'échantillons perdus de cet événement ; présent uniquement si PERF_FORMAT_LOST a été spécifié dans read_format.

Disposition MMAP

Lorsque vous utilisez perf_event_open() en mode échantillonné, les événements asynchrones (comme le débordement du compteur ou le suivi mmap(2) PROT_EXEC) sont enregistrés dans un tampon circulaire. Ce tampon circulaire est créé et accédé via mmap(2).

La taille du mmap doit être de 1 + 2^n pages, où la première page est une page de métadonnées (struct perf_event_mmap_page) qui contient diverses informations telles que la position de la tête du tampon circulaire.

Avant Linux 2.6.39, un bug faisait que vous deviez allouer un tampon circulaire mmap lors de l'échantillonnage, même si vous n'aviez pas l'intention d'y accéder.

La structure de la première page mmap de métadonnées est la suivante :


struct perf_event_mmap_page {
    __u32 version;        /* numéro de version de cette structure */
    __u32 compat_version; /* version la plus basse avec laquelle c'est compatible */
    __u32 lock;           /* seqlock pour la synchronisation */
    __u32 index;          /* identifiant du compteur matériel */
    __s64 offset;         /* ajouter à la valeur du compteur matériel */
    __u64 time_enabled;   /* temps pendant lequel l'événement est actif */
    __u64 time_running;   /* temps pendant lequel l'événement est sur le CPU */
    union {
        __u64   capabilities;
        struct {
            __u64   cap_usr_time / cap_usr_rdpmc / cap_bit0 : 1,
                  cap_bit0_is_deprecated : 1,
                  cap_user_rdpmc         : 1,

cap_usr_time / cap_usr_rdpmc / cap_bit0 (depuis Linux 3.4)
Il y avait un bug dans la définition de cap_usr_time et cap_usr_rdpmc de Linux 3.4 à Linux 3.11. Les deux bits étaient définis pour pointer au même endroit, il était donc impossible de savoir si cap_usr_time ou cap_usr_rdpmc étaient effectivement définis.
À partir de Linux 3.12, ils sont renommés en cap_bit0 et vous devriez utiliser les champs cap_user_time et cap_user_rdpmc à la place.
c
ap_bit0_is_deprecated (depuis Linux 3.12)
S'il est défini, ce bit indique que le noyau prend en charge les bits cap_user_time et cap_user_rdpmc correctement séparés.
S'il n'est pas défini, il indique un ancien noyau où cap_usr_time et cap_usr_rdpmc correspondent au même bit et donc les deux fonctionnalités doivent être utilisées avec prudence.
cap_user_rdpmc (depuis Linux 3.12)
Si le matériel prend en charge la lecture par l'espace utilisateur des compteurs de performance sans appel système (il s'agit de l'instruction "rdpmc" sur x86), alors le code suivant peut être utilisé pour effectuer une lecture :

u32 seq, time_mult, time_shift, idx, width;
u64 count, enabled, running;
u64 cyc, time_offset;
do {
    seq = pc->lock;
    barrier();
    enabled = pc->time_enabled;
    running = pc->time_running;
    if (pc->cap_usr_time && enabled != running) {
        cyc = rdtsc();
        time_offset = pc->time_offset;
        time_mult   = pc->time_mult;
        time_shift  = pc->time_shift;
    }
    idx = pc->index;
    count = pc->offset;
    if (pc->cap_usr_rdpmc && idx) {
        width = pc->pmc_width;
        count += rdpmc(idx - 1);
    }
    barrier();
} while (pc->lock != seq);

cap_user_time (depuis Linux 3.12)
Ce bit indique que le matériel dispose d'un compteur d'horodatage constant et non interrompu (TSC sur x86).
cap_user_time_zero (depuis Linux 3.12)
Indique la présence de time_zero qui permet de mapper les valeurs d'horodatage à l'horloge matérielle.
pmc_width
Si cap_usr_rdpmc est défini, ce champ fournit la largeur en bits de la valeur lue à l'aide de l'instruction rdpmc ou équivalente. Cela peut être utilisé pour signer l'extension du résultat comme suit :

pmc <<= 64 - pmc_width;
pmc >>= 64 - pmc_width;  // décalage signé à droite
count += pmc;

time_shift
time_mult
time_offset
Si cap_usr_time est défini, ces champs peuvent être utilisés pour calculer la différence de temps depuis time_enabled (en nanosecondes) en utilisant rdtsc ou similaire.

u64 quot, rem;
u64 delta;
quot  = cyc >> time_shift;
rem   = cyc & (((u64)1 << time_shift) - 1);
delta = time_offset + quot * time_mult +
        ((rem * time_mult) >> time_shift);

Où time_offset, time_mult, time_shift et cyc sont lus dans la boucle seqcount décrite ci-dessus. Cette différence peut alors être ajoutée à enabled et possiblement running (si idx), améliorant la mise à l'échelle :

enabled += delta;
if (idx)
    running += delta;
quot  = count / running;
rem   = count % running;
count = quot * enabled + (rem * enabled) / running;

time_zero (depuis Linux 3.12)
Si cap_usr_time_zero est défini, alors l'horloge matérielle (le compteur d'horodatage TSC sur x86) peut être calculée à partir des valeurs time_zero, time_mult et time_shift :

time = timestamp - time_zero;
quot = time / time_mult;
rem  = time % time_mult;
cyc  = (quot << time_shift) + (rem << time_shift) / time_mult;

Et vice versa :

quot = cyc >> time_shift;
rem  = cyc & (((u64)1 << time_shift) - 1);
timestamp = time_zero + quot * time_mult +
            ((rem * time_mult) >> time_shift);

data_head
Ceci pointe vers la tête de la section de données. La valeur augmente continuellement, elle ne boucle pas. La valeur doit être manuellement bouclée par la taille du tampon mmap avant d'accéder aux échantillons.
Sur les plates-formes compatibles SMP, après avoir lu la valeur data_head, l'espace utilisateur doit émettre un rmb().
data_tail
Lorsque le mappage est PROT_WRITE, la valeur data_tail doit être écrite par l'espace utilisateur pour refléter les dernières données lues. Dans ce cas, le noyau ne remplacera pas les données non lues.
data_offset (depuis Linux 4.1)
Contient le décalage de l'emplacement dans le tampon mmap où commencent les données d'échantillon perf.
data_size (depuis Linux 4.1)
Contient la taille de la région d'échantillon perf dans le tampon mmap.
aux_head
aux_tail
aux_offset
aux_size (depuis Linux 4.1)
La région AUX permet le mappage mmap(2) d'un tampon d'échantillons séparé pour les flux de données à large bande passante (séparé du tampon d'échantillons perf principal). Un exemple de flux à large bande passante est la prise en charge du traçage d'instructions, telle que trouvée dans les processeurs Intel plus récents.
Pour configurer une zone AUX, aux_offset doit d'abord être défini avec un décalage supérieur à data_offset+data_size et aux_size doit être défini sur la taille de tampon souhaitée. Le décalage et la taille souhaités doivent être alignés sur page, et la taille doit être une puissance de deux. Ces valeurs sont ensuite transmises à mmap afin de mapper le tampon AUX. Les pages du tampon AUX sont incluses dans la limite de ressources RLIMIT_MEMLOCK (voir setrlimit(2)), ainsi que dans l'allocation perf_event_mlock_kb.
Par défaut, le tampon AUX sera tronqué s'il ne rentre pas dans l'espace disponible dans le tampon circulaire. Si le tampon AUX est mappé en lecture seule, il fonctionnera en mode tampon circulaire où les anciennes données seront écrasées par les nouvelles. En mode d'écrasement, il peut ne pas être possible de déduire où les nouvelles données ont commencé, et il incombe au consommateur de désactiver la mesure pendant la lecture pour éviter les possibles conditions de concurrence sur les données.
Les pointeurs de tampon circulaire aux_head et aux_tail ont le même comportement et les mêmes règles d'ordonnancement que les data_head et data_tail décrits précédemment.

Gestion des dépassements

Les événements peuvent être configurés pour notifier lorsqu'un seuil est franchi, indiquant un dépassement. Les conditions de dépassement peuvent être capturées en surveillant le descripteur de fichier de l'événement avec poll(2), select(2), ou epoll(7). Alternativement, les événements de dépassement peuvent être capturés via un gestionnaire de signaux, en activant la signalisation d'E/S sur le descripteur de fichier ; voir la discussion des opérations F_SETOWN et F_SETSIG dans fcntl(2).

Les dépassements ne sont générés que par les événements d'échantillonnage (sample_period doit avoir une valeur non nulle).

Il existe deux façons de générer des notifications de dépassement.

La première consiste à définir une valeur wakeup_events ou wakeup_watermark qui se déclenchera si un certain nombre d'échantillons ou d'octets ont été écrits dans le tampon circulaire mmap. Dans ce cas, POLL_IN est indiqué.

L'autre méthode utilise l'appel ioctl PERF_EVENT_IOC_REFRESH. Cet ioctl ajoute à un compteur qui se décrémente à chaque fois que l'événement dépasse. Lorsqu'il est non nul, POLL_IN est indiqué, mais une fois que le compteur atteint 0, POLL_HUP est indiqué et l'événement sous-jacent est désactivé.

Actualiser un leader de groupe d'événements actualise tous les frères et sœurs, et actualiser avec un paramètre de 0 permet actuellement des actualisations infinies ; ces comportements ne sont pas pris en charge et ne doivent pas être utilisés.

À partir de Linux 3.18, POLL_HUP est indiqué si l'événement surveillé est attaché à un processus différent et que ce processus se termine.

Instruction rdpmc

À partir de Linux 3.4 sur x86, vous pouvez utiliser l'instruction rdpmc pour obtenir des lectures à faible latence sans avoir à entrer dans le noyau. Notez que l'utilisation de rdpmc n'est pas nécessairement plus rapide que d'autres méthodes pour lire les valeurs d'événements.

Le support pour cela peut être détecté avec le champ cap_usr_rdpmc dans la page mmap ; la documentation sur la manière de calculer les valeurs d'événements se trouve dans cette section.

À l'origine, lorsque le support rdpmc était activé, tout processus (pas seulement ceux ayant un événement perf actif) pouvait utiliser l'instruction rdpmc pour accéder aux compteurs. À partir de Linux 4.0, le support rdpmc n'est autorisé que si un événement est actuellement activé dans le contexte d'un processus. Pour restaurer l'ancien comportement, écrivez la valeur 2 dans /sys/devices/cpu/rdpmc.

Appels ioctl perf_event

Divers ioctls agissent sur les descripteurs de fichiers perf_event_open() :

PERF_EVENT_IOC_ENABLE
Cela active l'événement individuel ou le groupe d'événements spécifié par l'argument descripteur de fichier.
Si le bit PERF_IOC_FLAG_GROUP est défini dans l'argument ioctl, alors tous les événements d'un groupe sont activés, même si l'événement spécifié n'est pas le leader du groupe (mais voir BUGS).
PERF_EVENT_IOC_DISABLE
Cela désactive le compteur individuel ou le groupe d'événements spécifié par l'argument descripteur de fichier.
L'activation ou la désactivation du leader d'un groupe active ou désactive l'ensemble du groupe ; c'est-à-dire que tant que le leader du groupe est désactivé, aucun des compteurs du groupe ne comptera. L'activation ou la désactivation d'un membre d'un groupe autre que le leader n'affecte que ce compteur ; la désactivation d'un non-leader arrête ce compteur de compter mais n'affecte aucun autre compteur.
Si le bit PERF_IOC_FLAG_GROUP est défini dans l'argument ioctl, alors tous les événements d'un groupe sont désactivés, même si l'événement spécifié n'est pas le leader du groupe (mais voir BUGS).
PERF_EVENT_IOC_REFRESH
Les compteurs de dépassement non hérités peuvent utiliser cela pour activer un compteur pour un nombre de dépassements spécifié par l'argument, après quoi il est désactivé. Les appels ultérieurs de cet ioctl ajoutent la valeur de l'argument au compte courant. Une notification de dépassement avec POLL_IN défini se produira à chaque dépassement jusqu'à ce que le compte atteigne 0 ; lorsque cela se produit, une notification avec POLL_HUP défini est envoyée et l'événement est désactivé. L'utilisation d'un argument de 0 est considérée comme un comportement indéfini.
PERF_EVENT_IOC_RESET
Réinitialise le compte de l'événement spécifié par l'argument descripteur de fichier à zéro. Cela ne réinitialise que les comptes ; il n'y a aucun moyen de réinitialiser les valeurs de multiplexage time_enabled ou time_running.
Si le bit PERF_IOC_FLAG_GROUP est défini dans l'argument ioctl, alors tous les événements d'un groupe sont réinitialisés, même si l'événement spécifié n'est pas le leader du groupe (mais voir BUGS).
PERF_EVENT_IOC_PERIOD
Cela met à jour la période de dépassement pour l'événement.
Depuis Linux 3.7 (sur ARM) et Linux 3.14 (toutes les autres architectures), la nouvelle période prend effet immédiatement. Sur les anciens noyaux, la nouvelle période ne prenait effet qu'après le prochain dépassement.
L'argument est un pointeur vers une valeur 64 bits contenant la nouvelle période souhaitée.
Avant Linux 2.6.36, cet ioctl échouait toujours en raison d'un bug dans le noyau.
PERF_EVENT_IOC_SET_OUTPUT
Définit le descripteur de fichier d'E/S pour les événements de ce groupe. Les événements de groupe qui ne sont pas le leader ne devraient pas avoir ce descripteur de fichier défini.
PERF_EVENT_IOC_SET_FILTER
Définit un filtre BPF pour l'événement. La chaîne d'argument est un filtre BPF compilé.
PERF_EVENT_IOC_PROBE
Active le sondage (probing) pour un événement donné.
PERF_EVENT_IOC_TELEMETRY
Demande des données de télémétrie pour un événement donné.
PERF_EVENT_IOC_SET_BRANCH_SAMPLE_TYPE
Définit le type d'échantillonnage des branchements pour l'événement.
PERF_EVENT_IOC_UNPROBE
Désactive le sondage pour un événement donné.
/b>
Indique au noyau de signaler les notifications d'événements au descripteur de fichier spécifié plutôt qu'à celui par défaut. Les descripteurs de fichier doivent tous être sur le même CPU.
L'argument spécifie le descripteur de fichier souhaité, ou -1 si la sortie doit être ignorée.
PERF_EVENT_IOC_SET_FILTER (depuis Linux 2.6.33)
Ajoute un filtre ftrace à cet événement.
L'argument est un pointeur vers le filtre ftrace souhaité.
PERF_EVENT_IOC_ID (depuis Linux 3.12)
Renvoie la valeur de l'ID de l'événement pour le descripteur de fichier d'événement donné.
L'argument est un pointeur vers un entier non signé de 64 bits pour contenir le résultat.
PERF_EVENT_IOC_SET_BPF (depuis Linux 4.1)
Permet d'attacher un programme Berkeley Packet Filter (BPF) à un événement de trace kprobe existant. Vous avez besoin des privilèges CAP_PERFMON (depuis Linux 5.8) ou CAP_SYS_ADMIN pour utiliser cet ioctl.
L'argument est un descripteur de fichier de programme BPF créé par un appel système bpf(2) précédent.
PERF_EVENT_IOC_PAUSE_OUTPUT (depuis Linux 4.7)
Permet de mettre en pause et de reprendre le tampon circulaire de l'événement. Un tampon circulaire en pause n'empêche pas la génération d'échantillons, mais les ignore simplement. Les échantillons ignorés sont considérés comme perdus et provoquent la génération d'un échantillon PERF_RECORD_LOST lorsque cela est possible. Un signal de dépassement de capacité peut toujours être déclenché par l'échantillon ignoré même si le tampon circulaire reste vide.
L'argument est un entier non signé de 32 bits. Une valeur non nulle met en pause le tampon circulaire, tandis qu'une valeur nulle le reprend.
PERF_EVENT_MODIFY_ATTRIBUTES (depuis Linux 4.17)
Permet de modifier un événement existant sans avoir à le fermer et à en rouvrir un nouveau. Actuellement, cela n'est pris en charge que pour les événements de point d'arrêt.
L'argument est un pointeur vers une structure perf_event_attr contenant les paramètres mis à jour de l'événement.
PERF_EVENT_IOC_QUERY_BPF (depuis Linux 4.16)
Permet de demander quels programmes Berkeley Packet Filter (BPF) sont attachés à un événement de trace kprobe existant. Vous ne pouvez attacher qu'un seul programme BPF par événement, mais vous pouvez avoir plusieurs événements attachés à un point de trace. La demande de cette valeur sur un événement de trace renvoie l'ID de tous les programmes BPF dans tous les événements attachés au point de trace. Vous avez besoin des privilèges CAP_PERFMON (depuis Linux 5.8) ou CAP_SYS_ADMIN pour utiliser cet ioctl.
L'argument est un pointeur vers une structure 
struct perf_event_query_bpf {
    __u32    ids_len;
    __u32    prog_cnt;
    __u32    ids[0];
};

Le champ ids_len indique le nombre d'IDs qui peuvent tenir dans le tableau ids fourni. La valeur prog_cnt est remplie par le noyau avec le nombre de programmes BPF attachés. Le tableau ids est rempli avec l'ID de chaque programme BPF attaché. S'il y a plus de programmes que ce qui peut tenir dans le tableau, le noyau renverra ENOSPC et ids_len indiquera le nombre d'IDs de programme qui ont été copiés avec succès.

Utilisation de prctl(2)

Un processus peut activer ou désactiver tous les groupes d'événements actuellement ouverts en utilisant les opérations PR_TASK_PERF_EVENTS_ENABLE et PR_TASK_PERF_EVENTS_DISABLE de prctl(2). Cela ne s'applique qu'aux événements créés localement par le processus appelant. Cela ne s'applique pas aux événements créés par d'autres processus attachés au processus appelant ou aux événements hérités d'un processus parent. Seuls les chefs de groupe sont activés et désactivés, pas les autres membres des groupes.

Fichiers de configuration liés à perf_event

Fichiers dans /proc/sys/kernel/

/proc/sys/kernel/perf_event_paranoid
Le fichier perf_event_paranoid peut être défini pour restreindre l'accès aux compteurs de performance.
2
autorise uniquement les mesures en espace utilisateur (par défaut depuis Linux 4.6).
1
autorise les mesures en noyau et en espace utilisateur (par défaut avant Linux 4.6).
0
autorise l'accès aux données spécifiques au CPU mais pas aux échantillons de trace bruts.
-1
aucune restriction.
L'existence du fichier perf_event_paranoid est la méthode officielle pour déterminer si un noyau prend en charge perf_event_open().
/proc/sys/kernel/perf_event_max_sample_rate
Définit le taux d'échantillonnage maximum. Le régler trop haut peut permettre aux utilisateurs d'échantillonner à un taux qui affecte les performances globales de la machine et potentiellement la bloquer. La valeur par défaut est 100000 (échantillons par seconde).
/proc/sys/kernel/perf_event_max_stack
Ce fichier définit la profondeur maximale des entrées de la pile signalées lors de la génération d'une trace d'appels.
/proc/sys/kernel/perf_event_mlock_kb
Nombre maximum de pages qu'un utilisateur non privilégié peut mlock(2). La valeur par défaut est 516 (Ko).

Fichiers dans /sys/bus/event_source/devices/

Depuis Linux 2.6.34, le noyau prend en charge plusieurs PMU disponibles pour la surveillance. Les informations sur la façon de programmer ces PMU se trouvent dans /sys/bus/event_source/devices/. Chaque sous-répertoire correspond à un PMU différent.
/sys/bus/event_source/devices/*/type (depuis Linux 2.6.38)
Contient un entier qui peut être utilisé dans le champ type de perf_event_attr pour indiquer que vous souhaitez utiliser ce PMU.
/sys/bus/event_source/devices/cpu/rdpmc (depuis Linux 3.4)
Si ce fichier est 1, alors l'accès direct en espace utilisateur aux registres des compteurs de performance est autorisé via l'instruction rdpmc. Cela peut être désactivé en écrivant 0 dans le fichier.
Depuis Linux 4.0, le comportement a changé, de sorte que 1 signifie maintenant autoriser l'accès uniquement aux processus ayant des événements perf actifs, et 2 indique l'ancien comportement d'autoriser l'accès à n'importe qui.
/sys/bus/event_source/devices/*/format/ (depuis Linux 3.4)
Ce sous-répertoire contient des informations sur les sous-champs spécifiques à l'architecture disponibles pour programmer les divers champs config de la structure perf_event_attr.
Le contenu de chaque fichier est le nom du champ config, suivi d'un deux-points, suivi d'une série d'intervalles de bits entiers séparés par des virgules. Par exemple, le fichier event peut contenir la valeur config1:1,6-10,44, ce qui indique que event est un attribut qui occupe les bits 1, 6-10 et 44 de perf_event_attr::config1.
/sys/bus/event_source/devices/*/events/ (depuis Linux 3.4)
Ce sous-répertoire contient des fichiers avec des événements prédéfinis. Les contenus sont des chaînes de caractères décrivant les paramètres de l'événement exprimés en termes des champs trouvés dans le répertoire ./format/ mentionné précédemment. Il ne s'agit pas nécessairement de listes complètes de tous les événements pris en charge par un PMU, mais généralement d'un sous-ensemble d'événements jugés utiles ou intéressants.
Le contenu de chaque fichier est une liste de noms d'attributs séparés par des virgules. Chaque entrée a une valeur optionnelle (hexadécimale ou décimale). Si aucune valeur n'est spécifiée, il est supposé être un champ à bit unique avec une valeur de 1. Une entrée d'exemple peut ressembler à ceci : event=0x2,inv,ldlat=3.
/sys/bus/event_source/devices/*/uevent
Ce fichier est l'interface standard du périphérique du noyau pour injecter des événements de branchement à chaud.
/sys/bus/event_source/devices/*/cpumask (depuis Linux 3.7)
Le fichier cpumask contient une liste d'entiers séparés par des virgules qui indiquent un numéro de CPU représentatif pour chaque socket (package) sur la carte mère. Ceci est nécessaire lors de la configuration des événements uncore ou northbridge, car ces PMU présentent des événements à l'échelle du socket.

En cas de succès, perf_event_open() renvoie le nouveau descripteur de fichier. En cas d'erreur, -1 est renvoyé et errno est défini pour indiquer l'erreur.

HISTORIQUE

perf_event_open() a été introduit dans Linux 2.6.31 mais s'appelait perf_counter_open(). Il a été renommé dans Linux 2.6.32.

NOTES

La manière officielle de savoir si le support de perf_event_open() est activé est de vérifier l'existence du fichier /proc/sys/kernel/perf_event_paranoid.

La capacité CAP_PERFMON (depuis Linux 5.8) fournit une approche sécurisée pour les opérations de surveillance des performances et d'observabilité dans un système, conformément au principe du moindre privilège (POSIX IEEE 1003.1e). L'accès aux opérations de surveillance des performances et d'observabilité du système en utilisant CAP_PERFMON plutôt que CAP_SYS_ADMIN, beaucoup plus puissant, exclut les chances de mauvaise utilisation des identifiants et rend les opérations plus sûres. L'utilisation de CAP_SYS_ADMIN pour la surveillance des performances et l'observabilité sécurisées du système est découragée au profit de la capacité CAP_PERFMON.

BOGUES

L'option F_SETOWN_EX de fcntl(2) est nécessaire pour recevoir correctement les signaux de dépassement dans les threads. Elle a été introduite dans Linux 2.6.32.

Avant Linux 2.6.33 (au moins pour x86), le noyau ne vérifiait pas si les événements pouvaient être planifiés ensemble avant l'heure de lecture. Il en va de même sur tous les noyaux connus si le watchdog NMI est activé. Cela signifie que pour savoir si un ensemble donné d'événements fonctionne, vous devez appeler perf_event_open(), démarrer, puis lire avant de savoir avec certitude que vous pouvez obtenir des mesures valides.

Avant Linux 2.6.34, les contraintes d'événements n'étaient pas imposées par le noyau. Dans ce cas, certains événements retournaient silencieusement "0" si le noyau les planifiait dans une fente de compteur impropre.

Avant Linux 2.6.34, il y avait un bogue lors du multiplexage où des résultats incorrects pouvaient être retournés.

Les noyaux de Linux 2.6.35 à Linux 2.6.39 peuvent rapidement faire planter le noyau si "inherit" est activé et que de nombreux threads sont démarrés.

Avant Linux 2.6.35, PERF_FORMAT_GROUP ne fonctionnait pas avec les processus attachés.

Il y a un bogue dans le code du noyau entre Linux 2.6.36 et Linux 3.0 qui ignore le champ "watermark" et agit comme si un wakeup_event était choisi si l'union a une valeur non nulle.

De Linux 2.6.31 à Linux 3.4, l'argument ioctl PERF_IOC_FLAG_GROUP était défectueux et opérait répétitivement sur l'événement spécifié au lieu d'itérer sur tous les événements frères d'un groupe.

De Linux 3.4 à Linux 3.11, les bits mmap cap_usr_rdpmc et cap_usr_time étaient mappés au même emplacement. Le code devrait migrer vers les nouveaux champs cap_user_rdpmc et cap_user_time à la place.

Vérifiez toujours vos résultats ! Divers événements généralisés ont eu des valeurs incorrectes. Par exemple, les branches retirées mesuraient la mauvaise chose sur les machines AMD jusqu'à Linux 2.6.35.

EXEMPLES

L'exemple suivant mesure le nombre total d'instructions d'un appel à printf(3).

#include <err.h>
#include <linux/perf_event.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/ioctl.h>
#include <sys/syscall.h>
#include <sys/types.h>
#include <unistd.h>
static long
perf_event_open(struct perf_event_attr *hw_event, pid_t pid,
                int cpu, int group_fd, unsigned long flags)
{
    int ret;
    ret = syscall(SYS_perf_event_open, hw_event, pid, cpu,
                  group_fd, flags);
    return ret;
}
int
main(void)
{
    int                     fd;
    long long               count;
    struct perf_event_attr  pe;
    memset(&pe, 0, sizeof(pe));
    pe.type = PERF_TYPE_HARDWARE;
    pe.size = sizeof(pe);
    pe.config = PERF_COUNT_HW_INSTRUCTIONS;
    pe.disabled = 1;
    pe.exclude_kernel = 1;
    pe.exclude_hv = 1;
    fd = perf_event_open(&pe, 0, -1, -1, 0);
    if (fd == -1)
        err(EXIT_FAILURE, "Error opening leader %llx\n", pe.config);
    if (ioctl(fd, PERF_EVENT_IOC_RESET, 0) == -1)
        err(EXIT_FAILURE, "PERF_EVENT_IOC_RESET");
    if (ioctl(fd, PERF_EVENT_IOC_ENABLE, 0) == -1)
        err(EXIT_FAILURE, "PERF_EVENT_IOC_ENABLE");
    printf("Measuring instruction count for this printf\n");
    if (ioctl(fd, PERF_EVENT_IOC_DISABLE, 0) == -1)
        err(EXIT_FAILURE, "PERF_EVENT_IOC_DISABLE");
    if (read(fd, &count, sizeof(count)) != sizeof(count))
        err(EXIT_FAILURE, "read");
    printf("Used %lld instructions\n", count);
    if (close(fd) == -1)
        err(EXIT_FAILURE, "close");
}
