Comment utiliser Perl de manière interactive ?

L'approche typique utilise le débogueur Perl, décrit dans la page de manuel perldebug(1), sur un programme "vide", comme ceci :

perl -de 42

Maintenant, tapez simplement tout code Perl légal, et il sera immédiatement évalué. Vous pouvez également examiner la table des symboles, obtenir des traces de pile, vérifier les valeurs des variables, définir des points d'arrêt et d'autres opérations typiques des débogueurs symboliques.

Vous pouvez également utiliser Devel::REPL, qui est un shell interactif pour Perl, communément appelé REPL - Read, Evaluate, Print, Loop (Lire, Évaluer, Imprimer, Boucler). Il offre diverses fonctionnalités pratiques.

Comment trouver quels modules sont installés sur mon système ?

Depuis la ligne de commande, vous pouvez utiliser le commutateur "-l" de la commande "cpan" :

$ cpan -l

Vous pouvez également utiliser le commutateur "-a" de "cpan" pour créer un fichier d'autobundle que "CPAN.pm" comprend et peut utiliser pour réinstaller chaque module :

$ cpan -a

Dans un programme Perl, vous pouvez utiliser le module ExtUtils::Installed pour afficher toutes les distributions installées, bien que cela puisse prendre un certain temps pour faire sa magie. La bibliothèque standard fournie avec Perl apparaît simplement comme "Perl" (bien que vous puissiez les obtenir avec Module::CoreList).

use ExtUtils::Installed;
my $inst    = ExtUtils::Installed->new();
my @modules = $inst->modules();

Si vous souhaitez une liste de tous les noms de fichiers de modules Perl, vous pouvez utiliser File::Find::Rule :

use File::Find::Rule;
my @files = File::Find::Rule->
    extras({follow => 1})->
    file()->
    name( '*.pm' )->
    in( @INC )
    ;

Si vous n'avez pas ce module, vous pouvez faire la même chose avec File::Find, qui fait partie de la bibliothèque standard :

use File::Find;
my @files;
find(
    {
    wanted => sub {
        push @files, $File::Find::fullname
        if -f $File::Find::fullname && /\.pm$/
    },
    follow => 1,
    follow_skip => 2,
    },
    @INC
);
print join "\n", @files;

Si vous avez simplement besoin de vérifier rapidement si un module est disponible, vous pouvez vérifier sa documentation. Si vous pouvez lire la documentation, le module est très probablement installé. Si vous ne pouvez pas lire la documentation, le module n'en a peut-être pas (dans de rares cas) :

$ perldoc Module::Name

Vous pouvez également essayer d'inclure le module dans un script en une seule ligne pour voir si Perl le trouve :

$ perl -MModule::Name -e1

(Si vous ne recevez pas de message d'erreur "Can't locate ... in @INC", alors Perl a trouvé le nom du module que vous avez demandé.)

Comment déboguer mes programmes Perl ?

Le débogueur Perl est décrit dans la page de manuel perldebug(1). C'est un débogueur symbolique avec des fonctionnalités que l'on trouve typiquement dans les débogueurs C ou Pascal.

Si vous déboguez des programmes complexes, des scripts qui prennent du temps à s'exécuter, ou des programmes qui ne semblent pas fonctionner correctement, vous pouvez utiliser le débogueur Perl. Pour l'utiliser, vous devriez généralement écrire votre programme, puis exécuter le débogueur comme ceci :

perl -d my_script.pl

Alternativement, vous pouvez intégrer le débogueur dans votre code à l'aide d'un point d'arrêt :

use Devel::ebug; # ou use Devel::NYTProf

Le module `Devel::ebug` permet de définir des points d'arrêt dans votre code. Le module `Devel::NYTProf` est un profiler de code, qui peut également être utilisé pour le débogage.

Il existe également d'autres modules utiles pour le débogage, tels que `Devel::Trace` (qui trace l'exécution du code) et `Devel::DProf` (un profiler de code plus ancien).

Pour une approche plus interactive, vous pouvez utiliser la commande `perl -de 1` (comme mentionné précédemment) pour entrer dans le débogueur directement avec un code arbitraire.

Certaines personnes préfèrent utiliser des instructions `print` pour déboguer leurs programmes. Bien que cette méthode puisse être simple pour les problèmes mineurs, elle peut rapidement devenir encombrante pour les programmes plus complexes. Le débogueur Perl est généralement plus efficace pour identifier et résoudre des bogues.

(contribué par brian d foy)

Avant de faire quoi que ce soit d'autre, vous pouvez vous aider en vous assurant que Perl vous informe des zones problématiques de votre code. En activant les avertissements et les strictures, vous pouvez résoudre de nombreux problèmes avant qu'ils ne deviennent trop importants. Vous en saurez plus sur ces sujets dans strict et warnings.

#!/usr/bin/perl
use strict;
use warnings;

Au-delà de cela, le débogueur le plus simple est la fonction "print". Utilisez-la pour examiner les valeurs pendant l'exécution de votre programme :

print STDERR "La valeur est [$value]\n";

Le module Data::Dumper peut afficher joliment les structures de données Perl :

use Data::Dumper qw( Dumper );
print STDERR "Le hash est " . Dumper( \%hash ) . "\n";

Perl est livré avec un débogueur interactif, que vous pouvez lancer avec le commutateur "-d". Il est entièrement expliqué dans perldebug.

Si vous souhaitez une interface graphique et que vous disposez de Tk, vous pouvez utiliser "ptkdb". Il est sur CPAN et disponible gratuitement.

Si vous avez besoin de quelque chose de beaucoup plus sophistiqué et contrôlable, Devel::ebug de Leon Brocard (que vous pouvez appeler avec le commutateur "-D" comme "-Debug") vous fournit les points d'accès programmables à tout ce dont vous avez besoin pour écrire votre propre code (sans trop de douleur et de souffrance).

Vous pouvez également utiliser un débogueur commercial tel qu'Affrus (Mac OS X), Komodo d'Activestate (Windows et Mac OS X) ou EPIC (la plupart des plateformes).

Comment puis-je profiler mes programmes Perl ?

(contribué par brian d foy, mis à jour le ven. 25 juil. 2008, 12:22:26 PDT)

L'espace de noms "Devel" contient plusieurs modules que vous pouvez utiliser pour profiler vos programmes Perl.

Devel::NYTProf (New York Times Profiler) effectue un profilage à la fois par instruction et par sous-routine. Il est disponible sur CPAN et vous l'invoquez également avec le commutateur "-d" :

perl -d:NYTProf some_perl.pl

Il crée une base de données d'informations de profil que vous pouvez transformer en rapports. La commande "nytprofhtml" transforme les données en un rapport HTML similaire au rapport Devel::Cover :

nytprofhtml

Vous pourriez également être intéressé par l'utilisation de Benchmark pour mesurer et comparer des extraits de code.

Vous pouvez en lire plus sur le profilage dans *Programming Perl*, chapitre 20, ou *Mastering Perl*, chapitre 5.

perldebguts documente la création d'un débogueur personnalisé si vous avez besoin de créer un type spécial de profileur. brian d foy décrit le processus dans *The Perl Journal*, "Creating a Perl Debugger", https://drdobbs.com/creating-a-perl-debugger/184404522 , et "Profiling in Perl" https://drdobbs.com/profiling-in-perl/184404580 .

Perl.com propose deux articles intéressants sur le profilage : "Profiling Perl", par Simon Cozens, https://www.perl.com/pub/2004/06/25/profiling.html/ et "Debugging and Profiling mod_perl Applications", par Frank Wiles, http://www.perl.com/pub/a/2006/02/09/debug_mod_perl.html .

Randal L. Schwartz écrit sur le profilage dans "Speeding up Your Perl Programs" pour *Unix Review*, http://www.stonehenge.com/merlyn/UnixReview/col49.html , et "Profiling in Template Toolkit via Overriding" pour *Linux Magazine*, http://www.stonehenge.com/merlyn/LinuxMag/col75.html .

Comment puis-je faire la référence croisée de mes programmes Perl ?

Le module B::Xref peut être utilisé pour générer des rapports de référence croisée pour les programmes Perl.

perl -MO=Xref[,OPTIONS] scriptname.plx

Existe-t-il un jolie-imprimeur (formateur) pour Perl ?

Perl::Tidy est livré avec un script perl perltidy qui indente et reformatte les scripts Perl pour les rendre plus faciles à lire en essayant de suivre les règles de perlstyle. Si vous écrivez du Perl, ou passez beaucoup de temps à lire du Perl, vous le trouverez probablement utile.

Bien sûr, si vous suivez simplement les directives de perlstyle, vous ne devriez pas avoir besoin de reformater. L'habitude de formater votre code au fur et à mesure que vous l'écrivez aidera à prévenir les bugs. Votre éditeur peut et doit vous aider dans ce domaine. Le mode perl ou le mode cperl plus récent pour emacs peuvent fournir une aide remarquable sur la plupart du code (mais pas tout), et même les éditeurs moins programmables peuvent apporter une assistance significative. Tom Christiansen et de nombreux autres utilisateurs de VI jurent par les paramètres suivants dans vi et ses clones :

set ai sw=4
map! ^O {^M}^[O^T

Placez cela dans votre fichier .exrc (en remplaçant les caractères caret par des caractères de contrôle) et c'est parti. En mode insertion, ^T sert à indenter, ^D à désindenter, et ^O à désindenter par bloc - pour ainsi dire. Un exemple plus complet, avec des commentaires, peut être trouvé à l'adresse http://www.cpan.org/authors/id/T/TO/TOMC/scripts/toms.exrc.gz

Où puis-je trouver perl-mode ou cperl-mode pour emacs ?

Depuis la version 19 de Emacs, niveau de correctif 22 environ, il existe à la fois perl-mode.el et un support pour le débogueur Perl intégré. Ceux-ci devraient être inclus dans la distribution standard d'Emacs 19.

Notez que le mode perl d'emacs aura des difficultés avec "main'foo" (apostrophe), et perturbera l'indentation et la coloration syntaxique. Vous utilisez probablement "main::foo" dans le nouveau code Perl de toute façon, donc cela ne devrait pas poser de problème.

Pour CPerlMode, voir https://www.emacswiki.org/emacs/CPerlMode

Comment puis-je écrire une GUI (X, Tk, Gtk, etc.) en Perl ?

(contribué par Ben Morrow)

Il existe un certain nombre de modules qui vous permettent d'écrire des interfaces graphiques en Perl. La plupart des boîtes à outils graphiques ont une interface Perl : une liste incomplète suit.

Tk
Cela fonctionne sous Unix et Windows, et la version actuelle n'est pas si laide sous Windows qu'elle l'était. Certains des éléments graphiques ne semblent toujours pas tout à fait corrects. L'interface est très naturelle et "perlesque", ce qui la rend facile à utiliser dans de petits scripts qui n'ont besoin que d'une interface graphique simple. Elle n'a pas été mise à jour depuis un certain temps.
Wx
Il s'agit d'une liaison Perl pour la boîte à outils multiplateforme wxWidgets ( http://www.wxwidgets.org ). Elle fonctionne sous Unix, Win32 et Mac OS X, en utilisant des widgets natifs (Gtk sous Unix). L'interface suit de près l'interface C++, mais la documentation est un peu sparse pour quelqu'un qui ne connaît pas la bibliothèque, se référant principalement à la documentation C++.
Gtk et Gtk2
Ce sont des liaisons Perl pour la boîte à outils Gtk ( http://www.gtk.org ). L'interface a considérablement changé entre les versions 1 et 2, elles ont donc des modules Perl distincts. Elle fonctionne sous Unix, Win32 et Mac OS X (actuellement, elle nécessite un serveur X sur Mac OS, mais un port "natif" est en cours), et les widgets ont le même aspect sur toutes les plateformes : c'est-à-dire qu'ils ne correspondent pas aux widgets natifs. Comme avec Wx, les liaisons Perl suivent de près l'API C, et la documentation vous oblige à lire la documentation C pour la comprendre.
Win32::GUI
Cela donne accès à la plupart des widgets GUI Win32 depuis Perl. Évidemment, cela ne fonctionne que sous Win32 et utilise des widgets natifs. L'interface Perl ne suit pas vraiment l'interface C : elle a été rendue plus "perlesque", et la documentation est assez bonne. Des choses plus avancées peuvent nécessiter une familiarité avec les API Win32 C, ou une référence à MSDN.
CamelBones
CamelBones ( http://camelbones.sourceforge.net ) est une interface Perl vers la boîte à outils GUI Cocoa de Mac OS X, et en tant que telle, peut être utilisée pour produire des interfaces graphiques natives sur Mac OS X. Elle n'est pas sur CPAN, car elle nécessite des frameworks que CPAN.pm ne sait pas installer, mais l'installation se fait via l'installeur de paquets standard OSX. L'API Perl est, là encore, très proche de l'API ObjC qu'elle enveloppe, et la documentation vous dit simplement comment traduire de l'une à l'autre.
Qt
Il existe une interface Perl pour la boîte à outils Qt de TrollTech, mais elle ne semble pas être maintenue.
Athena
Sx est une interface pour l'ensemble de widgets Athena qui est livré avec X, mais là encore, il semble qu'elle ne soit plus beaucoup utilisée de nos jours.

Comment puis-je accélérer mon programme Perl ?

La meilleure façon de le faire est de trouver un meilleur algorithme. Cela peut souvent faire une différence spectaculaire. Le livre de Jon Bentley, Programming Pearls (ce n'est pas une faute d'orthographe !) contient également quelques bons conseils sur l'optimisation. Les conseils sur le benchmarking se résument à : faire du benchmarking et du profilage pour s'assurer que vous optimisez la bonne partie, rechercher de meilleurs algorithmes au lieu de micro-optimiser votre code, et quand tout le reste échoue, envisager simplement d'acheter du matériel plus rapide. Vous voudrez probablement lire la réponse à la question précédente "Comment puis-je profiler mes programmes Perl ?" si vous ne l'avez pas déjà fait.

Une approche différente consiste à charger à la demande le code Perl rarement utilisé. Voir les modules AutoSplit et AutoLoader dans la distribution standard pour cela. Ou vous pourriez localiser le goulot d'étranglement et envisager d'écrire juste cette partie en C, de la manière dont nous avions l'habitude de prendre des goulots d'étranglement dans du code C et de les écrire en assembleur. Similaire à la réécriture en C, les modules qui ont des sections critiques peuvent être écrits en C (par exemple, le module PDL de CPAN).

Si vous liez actuellement votre exécutable Perl à une libc.so partagée, vous pouvez souvent gagner un avantage de performance de 10 à 25 % en le reconstruisant pour le lier avec une libc.a statique à la place. Cela rendra l'exécutable Perl plus grand, mais vos programmes (et vos programmeurs) Perl pourraient vous en remercier. Voir le fichier INSTALL dans la distribution source pour plus d'informations.

Le programme undump était une ancienne tentative d'accélérer les programmes Perl en stockant la forme déjà compilée sur disque. Ce n'est plus une option viable, car cela ne fonctionnait que sur quelques architectures et n'était de toute façon pas une bonne solution.

Comment puis-je faire en sorte que mon programme Perl consomme moins de mémoire ?

En ce qui concerne les compromis temps-espace, Perl préfère presque toujours consacrer de la mémoire à un problème. Les scalaires en Perl utilisent plus de mémoire que les chaînes en C, les tableaux en prennent plus, et les hachages en utilisent encore plus. Bien qu'il y ait encore beaucoup à faire, les versions récentes ont abordé ces problèmes. Par exemple, à partir de la version 5.004, les clés de hachage dupliquées sont partagées entre tous les hachages qui les utilisent, ne nécessitant donc aucune réallocation.

RÉSUMÉ EXÉCUTIF

Les programmes Perl peuvent être transformés en exécutables indépendants pour les plates-formes Windows, Mac OS, OS/2, DOS, Amiga, Atari, BeOS, et divers systèmes Unix. Les exemples incluent Perl Dev Kit d'ActiveState et Perl2Exe.

COMMENT PUIS-JE FAIRE FONCTIONNER « #!/usr/bin/perl » SUR [MS-DOS, NT, ...] ?

Pour OS/2, utilisez simplement

extproc perl -S -vos_options

comme première ligne dans un fichier "*.cmd" ("-S" à cause d'un bug dans la gestion de « extproc » par cmd.exe). Pour DOS, il faut d'abord inventer un fichier batch correspondant et le coder dans "ALTERNATE_SHEBANG" (voir le fichier dosish.h dans la distribution source pour plus d'informations).

L'installation sous Win95/NT, lors de l'utilisation du port ActiveState de Perl, modifiera le Registre pour associer l'extension ".pl" à l'interpréteur Perl. Si vous installez un autre port, voire que vous compilez votre propre Perl Win95/NT à partir des sources standard en utilisant un port Windows de gcc (par exemple, avec cygwin ou mingw32), vous devrez modifier le Registre vous-même. En plus d'associer ".pl" à l'interpréteur, les utilisateurs de NT peuvent utiliser : "SET PATHEXT=%PATHEXT%;.PL" pour leur permettre d'exécuter le programme "install-linux.pl" simplement en tapant "install-linux".

Sous MacOS « Classique », un programme Perl aura le Créateur et le Type appropriés, de sorte que le double-clic dessus appellera l'application MacPerl. Sous Mac OS X, des applications cliquables peuvent être créées à partir de n'importe quel script "#!" à l'aide de l'utilitaire DropScript de Wil Sanchez : http://www.wsanchez.net/software/.

IMPORTANT ! : Quoi que vous fassiez, NE vous frustrez pas et ne jetez pas l'interpréteur Perl dans votre répertoire cgi-bin pour faire fonctionner vos programmes sur un serveur Web. C'est un risque de sécurité EXTRÊMEMENT important. Prenez le temps de comprendre comment le faire correctement.

PUIS-JE ÉCRIRE DES PROGRAMMES PERL UTILES EN LIGNE DE COMMANDE ?

Oui. Lisez perlrun pour plus d'informations. Quelques exemples suivent. (Ceux-ci supposent les règles de guillemets standard du shell Unix.)

# somme des premier et dernier champs
perl -lane 'print $F[0] + $F[-1]' *
# identifier les fichiers texte
perl -le 'for(@ARGV) {print if -f && -T _}' *
# supprimer (la plupart) des commentaires d'un programme C
perl -0777 -pe 's{/\*.*?\*/}{}gs' foo.c
# rendre un fichier un mois plus jeune qu'aujourd'hui, déjouant les démons de nettoyage
perl -e '$X=24*60*60; utime(time(),time() + 30 * $X,@ARGV)' *
# trouver le premier uid inutilisé
perl -le '$i++ while getpwuid($i); print $i'
# afficher un manpath raisonnable
echo $PATH | perl -nl -072 -e '
s![^/+]*$!man!&&-d&&!$s{$_}++&&push@m,$_;END{print"@m"}'

OK, le dernier était en fait une entrée du Concours Perl Obfusqué. :-)

POURQUOI LES INSTRUCTIONS PERL EN UNE LIGNE NE FONCTIONNENT-ELLES PAS SUR MON SYSTÈME DOS/MAC/VMS ?

Le problème est généralement que les interpréteurs de commandes de ces systèmes ont des idées assez différentes sur les guillemets par rapport aux shells Unix sous lesquels les instructions en une ligne ont été créées. Sur certains systèmes, vous devrez peut-être changer les guillemets simples en guillemets doubles, ce que vous ne devez PAS faire sur les systèmes Unix ou Plan9. Vous pourriez également devoir changer un % simple en %%.

Par exemple :

# Unix (y compris Mac OS X)
perl -e 'print "Hello world\n"'
# DOS, etc.
perl -e "print \"Hello world\n\""
# Mac Classic
print "Hello world\n"
 (puis Exécuter "Myscript" ou Maj-Commande-R)
# MPW
perl -e 'print "Hello world\n"'
# VMS
perl -e "print ""Hello world\n"""

Le problème est qu'aucun de ces exemples n'est fiable : ils dépendent de l'interpréteur de commandes. Sous Unix, les deux premiers fonctionnent souvent. Sous DOS, il est tout à fait possible qu'aucun des deux ne fonctionne. Si 4DOS était le shell de commande, vous auriez probablement plus de succès comme ceci :

perl -e "print <Ctrl-x>"Hello world\n<Ctrl-x>""

Sous Mac, cela dépend de l'environnement que vous utilisez. Le shell MacPerl, ou MPW, ressemble beaucoup aux shells Unix dans son support de plusieurs variantes de guillemets, sauf qu'il utilise librement les caractères non ASCII de Mac comme caractères de contrôle.

Utiliser qq(), q(), et qx(), au lieu de « guillemets doubles », 'guillemets simples', et `backticks`, peut rendre les instructions en une ligne plus faciles à écrire.

Il n'y a pas de solution générale à tout cela. C'est un gâchis.

OÙ PUIS-JE APPRENDRE LA PROGRAMMATION CGI OU WEB EN PERL ?

Pour les modules, obtenez les modules CGI ou LWP de CPAN. Pour les livres, consultez les deux ouvrages spécialement dédiés aux sujets Web dans la question sur les livres. Pour les problèmes et questions liés au Web, comme « Pourquoi ai-je des erreurs 500 » ou « Pourquoi mon script ne fonctionne-t-il pas depuis le navigateur alors qu'il fonctionne bien en ligne de commande », consultez les guides de dépannage et les références dans perlfaq9 ou dans le CGI MetaFAQ :

L<http://www.perl.org/CGI_MetaFAQ.html>

Il est fortement recommandé de jeter un coup d'œil à https://plackperl.org et aux frameworks Web Perl modernes ; la programmation Web en Perl a beaucoup évolué depuis les vieux jours des simples scripts CGI.

OÙ PUIS-JE APPRENDRE LA PROGRAMMATION ORIENTÉE OBJET EN PERL ?

Un bon endroit pour commencer est perlootut, et vous pouvez utiliser perlobj comme référence.

Un bon livre sur la POO en Perl est « Object-Oriented Perl » par Damian Conway chez Manning Publications, ou « Intermediate Perl » par Randal Schwartz, brian d foy et Tom Phoenix chez O'Reilly Media.

OÙ PUIS-JE APPRENDRE À LIER C AVEC PERL ?

Si vous souhaitez appeler C depuis Perl, commencez par perlxstut, puis passez à perlxs, xsubpp et perlguts. Si vous souhaitez appeler Perl depuis C, lisez perlembed, perlcall et perlguts. N'oubliez pas que vous pouvez beaucoup apprendre en examinant comment les auteurs des modules d'extension existants ont écrit leur code et résolu leurs problèmes.

Vous n'aurez peut-être pas besoin de toute la puissance de XS. Le module Inline::C vous permet de placer du code C directement dans votre source Perl. Il gère toute la magie pour que cela fonctionne. Vous devrez toujours apprendre au moins une partie de l'API Perl, mais vous n'aurez pas à gérer la complexité des fichiers de support XS.

J'AI LU PERLEMBED, PERLGUTS, ETC., MAIS JE N'ARRIVE PAS À INTÉGRER PERL DANS MON PROGRAMME C ; QU'EST-CE QUE JE FAIS DE MAL ?

Téléchargez le kit ExtUtils::Embed depuis CPAN et exécutez `make test'. Si les tests passent, relisez les pods encore et encore. S'ils échouent, soumettez un rapport de bug à https://github.com/Perl/perl5/issues avec la sortie de "make test TEST_VERBOSE=1" ainsi que "perl -V".

QUAND J'AI ESSAYÉ D'EXÉCUTER MON SCRIPT, J'AI REÇU CE MESSAGE. QU'EST-CE QUE CELA SIGNIFIE ?

Une liste complète des messages d'erreur et d'avertissement de Perl avec des explications se trouve dans perldiag. Vous pouvez également utiliser le programme splain (distribué avec Perl) pour expliquer les messages d'erreur :

perl programme 2>diag.out
splain [-v] [-p] diag.out

ou modifiez votre programme pour qu'il explique lui-même les messages :

use diagnostics;

ou

use diagnostics -verbose;

QU'EST-CE QUE MAKEMAKER ?

(contribué par brian d foy)

Le module ExtUtils::MakeMaker, plus connu simplement sous le nom de « MakeMaker », transforme un script Perl, typiquement appelé "Makefile.PL", en un Makefile. L'outil Unix "make" utilise ce fichier pour gérer les dépendances et les actions afin de traiter et d'installer une distribution Perl.
