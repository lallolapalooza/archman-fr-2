NOM

pelican - documentation de pelican

  • Écrivez votre contenu directement avec l'éditeur de votre choix dans les formats reStructuredText ou Markdown
  • Inclut un outil CLI simple pour (re)générer votre site
  • Facile à intégrer avec des systèmes de contrôle de version distribués et des webhooks
  • Un contenu de sortie entièrement statique est facile à héberger n'importe où

Prêt à commencer ? Consultez le guide Démarrage rapide.

CARACTÉRISTIQUES

Les principales caractéristiques de Pelican incluent :

  • Articles (par exemple, articles de blog) et pages (par exemple, "À propos", "Projets", "Contact")
  • Intégration avec des services externes
  • Thèmes de site (créés à l'aide de modèles Jinja2)
  • Publication d'articles en plusieurs langues
  • Génération de flux Atom et RSS
  • Mise en évidence de la syntaxe du code
  • Importation de contenu existant depuis WordPress, Dotclear ou des flux RSS
  • Temps de reconstruction rapides grâce à la mise en cache du contenu et à l'écriture sélective de la sortie
  • Extensible via un riche écosystème de plugins : Plugins Pelican

"Pelican" est un anagramme de calepin, ce qui signifie "carnet" en français. ;)

Démarrage rapide

La lecture de toute la documentation est fortement recommandée, mais pour les plus impatients, voici quelques étapes rapides pour commencer.

Installation

Installez Pelican (et optionnellement Markdown si vous avez l'intention de l'utiliser) sur Python >=3.9 en exécutant la commande suivante dans votre terminal préféré, en préfixant avec sudo si les permissions le justifient :

python -m pip install "pelican[markdown]"

Créer un projet

Tout d'abord, choisissez un nom pour votre projet, créez un répertoire approprié pour votre site et déplacez-vous dans ce répertoire :

mkdir -p ~/projets/votresite
cd ~/projets/votresite

Créez un projet squelette via la commande pelican-quickstart, qui commence par poser quelques questions sur votre site :

pelican-quickstart

Pour les questions qui ont des valeurs par défaut indiquées entre crochets, n'hésitez pas à utiliser la touche Retour pour accepter ces valeurs par défaut [1]. Lorsque vous êtes invité à entrer votre préfixe d'URL, entrez votre nom de domaine comme indiqué (par exemple, https://example.com).

Créer un article

Vous ne pouvez pas exécuter Pelican tant que vous n'avez pas créé de contenu. Utilisez votre éditeur de texte préféré pour créer votre premier article avec le contenu suivant :

Titre : Ma première critique
Date : 2010-12-03 10:20
Catégorie : Critique
Voici une critique de mon clavier mécanique préféré.

Étant donné que cet article d'exemple est au format Markdown, enregistrez-le sous le nom ~/projets/votresite/content/keyboard-review.md.

Générer votre site

Depuis le répertoire racine de votre projet, exécutez la commande pelican pour générer votre site :

pelican content

Votre site a maintenant été généré dans le répertoire output/. (Vous pourriez voir un avertissement concernant les flux, mais c'est normal lorsque vous développez localement et pouvez être ignoré pour l'instant.)

Installation de Pelican

Pelican fonctionne actuellement mieux sur >=3.9 ; les versions antérieures de Python ne sont pas prises en charge.

python -m pip install pelican

Ou, si vous prévoyez d'utiliser Markdown :

(Gardez à l'esprit que certains systèmes d'exploitation vous demanderont de préfixer la commande ci-dessus avec sudo afin d'installer Pelican système dans son ensemble.)

virtualenv ~/virtualenvs/pelican
cd ~/virtualenvs/pelican
source bin/activate

Une fois l'environnement virtuel créé et activé, Pelican peut être installé via python -m pip install pelican comme indiqué ci-dessus. Alternativement, si vous avez le code source du projet, vous pouvez installer Pelican en utilisant la méthode distutils :

cd chemin-vers-source-Pelican
python setup.py install

Si vous avez Git installé et préférez installer la dernière version de pointe de Pelican plutôt qu'une version stable, utilisez la commande suivante :

python -m pip install -e "git+https://github.com/getpelican/pelican.git#egg=pelican"

Une fois Pelican installé, vous pouvez exécuter pelican --help pour voir les options d'utilisation de base. Pour plus de détails, référez-vous à la section Publier.

Démarrer votre site

Une fois Pelican installé, vous pouvez créer un projet squelette via la commande pelican-quickstart, qui commence par vous poser quelques questions sur votre site :

pelican-quickstart

Si elle est exécutée dans un environnement virtuel activé, pelican-quickstart recherchera un chemin de projet associé dans $VIRTUAL_ENV/.project. Si ce fichier existe et contient un chemin de répertoire valide, le nouveau projet Pelican sera enregistré à cet emplacement. Sinon, le répertoire de travail actuel est utilisé par défaut. Pour définir le nouveau chemin de projet lors de l'invocation initiale, utilisez : pelican-quickstart --path /votre/repertoire/desire

Une fois que vous aurez répondu à toutes les questions, votre projet sera constitué de la hiérarchie suivante (à l'exception de pages — indiqué entre parenthèses ci-dessous — que vous pouvez éventuellement ajouter vous-même si vous prévoyez de créer du contenu non chronologique) :

votresite/
├── content
│   └── (pages)
├── output
├── tasks.py
├── Makefile
├── pelicanconf.py       # Fichier de configuration principal
└── publishconf.py       # Paramètres à utiliser lorsque vous êtes prêt à publier

L'étape suivante consiste à commencer à ajouter du contenu dans le dossier content qui a été créé pour vous.

Écriture de contenu

Articles et pages

Pelican considère les "articles" comme du contenu chronologique, tel que des publications de blog, et donc associés à une date.

L'idée derrière les "pages" est qu'elles ne sont généralement pas temporelles et sont utilisées pour du contenu qui ne change pas très souvent (par exemple, les pages "À propos" ou "Contact").

Vous pouvez trouver des exemples de contenu dans le dépôt à l'adresse samples/content/.

Métadonnées de fichier

Pelican essaie d'être assez intelligent pour obtenir les informations dont il a besoin du système de fichiers (par exemple, sur la catégorie de vos articles), mais certaines informations doivent être fournies sous forme de métadonnées à l'intérieur de vos fichiers.

Si vous écrivez votre contenu au format reStructuredText, vous pouvez fournir ces métadonnées dans des fichiers texte en utilisant la syntaxe suivante (donnez à votre fichier l'extension .rst) :

Mon super titre
##############
:date: 2010-10-03 10:20
:modified: 2010-10-04 18:40
:tags: c, est, génial
:category: ouais
:slug: mon-super-post
:authors: Alexis Metaireau, Conan Doyle
:summary: Version courte pour les index et les flux

Les listes d'auteurs et d'étiquettes peuvent également être séparées par des points-virgules, ce qui vous permet d'écrire des auteurs et des étiquettes contenant des virgules :

:tags: pelican, outil-de-publication; pelican, oiseau
:authors: Metaireau, Alexis; Doyle, Conan

Pelican implémente une extension à reStructuredText pour activer la prise en charge de la balise HTML abbr. Pour l'utiliser, écrivez quelque chose comme ceci dans votre article :

La syntaxe des métadonnées pour les articles Markdown doit suivre ce modèle :

Titre: Mon super titre
Date: 2010-12-03 10:20
Modifié: 2010-12-05 19:30
Catégorie: Python
Tags: pelican, publication
Slug: mon-super-post
Auteurs: Alexis Metaireau, Conan Doyle
Résumé: Version courte pour les index et les flux
Ceci est le contenu de mon super article de blog.

Vous pouvez également avoir vos propres clés de métadonnées (tant qu'elles ne rentrent pas en conflit avec les mots-clés réservés aux métadonnées) à utiliser dans vos modèles. Le tableau suivant contient une liste des mots-clés réservés pour les métadonnées :

Métadonnée Description
title Titre de l'article ou de la page
date Date de publication (par exemple, AAAA-MM-JJ HH:MM)
modified Date de modification (par exemple, AAAA-MM-JJ HH:MM)
tags Étiquettes du contenu, séparées par des virgules
keywords Mots-clés du contenu, séparés par des virgules (contenu HTML uniquement)
category Catégorie du contenu (une seule — pas plusieurs)
slug Identifiant utilisé dans les URL et les traductions
author Auteur du contenu, lorsqu'il n'y en a qu'un
authors Auteurs du contenu, lorsqu'il y en a plusieurs
summary Brève description du contenu pour les pages d'index
lang Identifiant de la langue du contenu (en, fr, etc.)
translation Si le contenu est une traduction d'un autre (true ou false)
status Statut du contenu : draft, hidden, skip, ou published
template Nom du modèle à utiliser pour générer le contenu (sans extension)
save_as Enregistrer le contenu à ce chemin de fichier relatif
url URL à utiliser pour cet article/page

Pelican peut également traiter des fichiers HTML se terminant par .html et .htm. Pelican interprète le HTML de manière très simple, lisant les métadonnées à partir des balises meta, le titre à partir de la balise title et le corps à partir de la balise body :

<html>
    <head>
        <title>Mon super titre</title>
        <meta name="tags" content="c, est, génial" />
        <meta name="date" content="2012-07-09 22:28" />
        <meta name="modified" content="2012-07
<!DOCTYPE html> <html> <head> <meta charset="utf-8" /> <title>This is my title</title> <meta name="author" content="Alexis Métaireau" /> <meta name="date" content="2012-12-12 10:14" /> <meta name="category" content="yeah" /> <meta name="authors" content="Alexis Métaireau, Conan Doyle" /> <meta name="summary" content="Version courte pour l'index et les flux" /> </head> <body> Ceci est le contenu de mon super article de blog. </body> </html> ```

Avec HTML, il existe une seule exception simple aux métadonnées standard : les balises peuvent être spécifiées soit via les métadonnées tags, comme c'est la norme dans Pelican, soit via les métadonnées keywords, comme c'est la norme en HTML. Les deux peuvent être utilisés indifféremment.

Le titre est donc la seule métadonnée requise. Si cela vous gêne, ne vous inquiétez pas. Au lieu de spécifier manuellement un titre dans vos métadonnées à chaque fois, vous pouvez utiliser le nom du fichier source comme titre. Par exemple, un fichier source Markdown nommé Publishing via Pelican.md se verrait automatiquement attribuer le titre *Publishing via Pelican*. Si vous préférez ce comportement, ajoutez la ligne suivante à votre fichier de configuration :

FILENAME_METADATA = '(?P<title>.*)'

NOTE :

Lors de l'expérimentation avec différents paramètres (en particulier ceux des métadonnées), la mise en cache peut interférer et les modifications peuvent ne pas être visibles. Dans de tels cas, désactivez la mise en cache avec LOAD_CONTENT_CACHE = False ou utilisez l'option de ligne de commande --ignore-cache.

modified doit être la dernière fois que vous avez mis à jour l'article, et par défaut date s'il n'est pas spécifié. De plus, vous pouvez afficher modified dans les modèles, les entrées de flux dans les lecteurs de flux seront automatiquement mises à jour lorsque vous définirez modified à la date actuelle après avoir modifié votre article.

authors est une liste d'auteurs d'articles séparés par des virgules. S'il n'y a qu'un seul auteur, vous pouvez utiliser le champ author.

Si vous ne spécifiez pas explicitement de métadonnées de résumé pour un article donné, le paramètre SUMMARY_MAX_LENGTH peut être utilisé pour spécifier combien de mots du début d'un article sont utilisés comme résumé. Vous pouvez également utiliser les N premiers paragraphes d'un article comme résumé en utilisant le paramètre SUMMARY_MAX_PARAGRAPHS. Si les deux paramètres sont utilisés, le nombre spécifié de paragraphes sera utilisé mais pourra être tronqué pour respecter la longueur maximale spécifiée.

Vous pouvez également extraire des métadonnées du nom de fichier via une expression régulière à définir dans le paramètre FILENAME_METADATA. Tous les groupes nommés qui correspondent seront définis dans l'objet métadonnées. La valeur par défaut du paramètre FILENAME_METADATA n'extraira que la date du nom de fichier. Par exemple, si vous souhaitez extraire la date et le slug, vous pourriez définir quelque chose comme : '(?P<date>\d{4}-\d{2}-\d{2})_(?P<slug>.*)'

Veuillez noter que les métadonnées disponibles dans vos fichiers ont la priorité sur les métadonnées extraites du nom de fichier.

Pages

Si vous créez un dossier nommé pages à l'intérieur du dossier de contenu, tous les fichiers qu'il contient seront utilisés pour générer des pages statiques, telles que les pages À propos ou Contact. (Voir l'exemple de disposition du système de fichiers ci-dessous.)

Vous pouvez utiliser le paramètre DISPLAY_PAGES_ON_MENU pour contrôler si toutes ces pages sont affichées dans le menu de navigation principal. (Par défaut, c'est True.)

Si vous souhaitez exclure certaines pages d'être liées ou listées dans le menu, ajoutez un attribut status: hidden à leurs métadonnées. Ceci est utile pour des choses comme la création de pages d'erreur qui correspondent au thème généré de votre site.

Contenu statique

Les fichiers statiques sont des fichiers autres que des articles et des pages qui sont copiés dans le dossier de sortie tels quels, sans traitement. Vous pouvez contrôler quels fichiers statiques sont copiés avec le paramètre STATIC_PATHS du fichier pelicanconf.py du projet. La configuration par défaut de Pelican inclut le répertoire images pour cela, mais d'autres doivent être ajoutés manuellement. De plus, les fichiers statiques auxquels il est explicitement fait référence sont inclus (voir ci-dessous).

NOTE :

Dans la configuration par défaut, tous les fichiers avec une extension de fichier de contenu valide (.html, .rst, .md, ...) sont traités par les générateurs d'articles et de pages *avant* le générateur statique. Ceci est évité en modifiant appropriément les paramètres *_EXCLUDE.

Contenu mixte dans le même répertoire

À partir de Pelican 3.5, les fichiers statiques peuvent partager en toute sécurité un répertoire source avec les fichiers source des pages, sans exposer les sources des pages sur le site généré. De tels répertoires doivent être ajoutés à la fois à STATIC_PATHS et à PAGE_PATHS (ou à STATIC_PATHS et ARTICLE_PATHS). Pelican identifiera et traitera les fichiers source des pages normalement, et copiera les fichiers restants comme s'ils se trouvaient dans un répertoire séparé réservé aux fichiers statiques.

Remarque : Placer des fichiers statiques et des fichiers source de contenu ensemble dans le même répertoire source ne garantit pas qu'ils se retrouveront au même endroit dans le site généré. Le moyen le plus simple de le faire est d'utiliser la syntaxe de lien {attach} (décrite ci-dessous). Alternativement, les paramètres STATIC_SAVE_AS, PAGE_SAVE_AS et ARTICLE_SAVE_AS (et les paramètres correspondants *_URL) peuvent être configurés pour placer des fichiers de différents types ensemble, tout comme ils pouvaient l'être dans les versions antérieures de Pelican.

Liaison vers le contenu interne

À partir de Pelican 3.1, il est désormais possible de spécifier des liens intra-site vers des fichiers de la hiérarchie du *contenu source* au lieu de fichiers de la hiérarchie *générée*. Cela facilite la liaison depuis l'article actuel vers d'autres contenus qui pourraient se trouver aux côtés de cet article (au lieu d'avoir à déterminer où l'autre contenu sera placé après la génération du site).

Pour créer un lien vers du contenu interne (fichiers dans le répertoire content), utilisez la syntaxe suivante pour la cible du lien : {filename}path/to/file. Remarque : les barres obliques, /, sont le séparateur de chemin requis dans la directive {filename} sur tous les systèmes d'exploitation, y compris Windows.

Par exemple, un projet Pelican pourrait être structuré comme suit :

website/
├── content
│   ├── category/
│   │   └── article1.rst
│   ├── article2.md
│   └── pages
│       └── about.md
└── pelican.conf.py

Dans cet exemple, article1.rst pourrait ressembler à ceci :

The first article
#################
:date: 2012-12-01 10:02
See below intra-site link examples in reStructuredText format.
`a link relative to the current file <{filename}../article2.md>`_
`a link relative to the content root <{filename}/article2.md>`_

et article2.md :

Title: The second article
Date: 2012-12-01 10:02
See below intra-site link examples in Markdown format.
[a link relative to the current file]({filename}category/article1.rst)
[a link relative to the content root]({filename}/category/article1.rst)

Liaison vers les fichiers statiques

Vous pouvez créer un lien vers du contenu statique en utilisant {static}path/to/file. Les fichiers auxquels il est fait référence avec cette syntaxe seront automatiquement copiés dans le répertoire de sortie, même si les répertoires sources qui les contiennent ne sont pas inclus dans le paramètre STATIC_PATHS du fichier pelicanconf.py du projet.

Par exemple, le répertoire de contenu d'un projet pourrait être structuré comme suit :

content
├── images
│   └── han.jpg
├── pdfs
│   └── menu.pdf
└── pages
    └── test.md

test.md inclurait :

![Alt Text]({static}/images/han.jpg)
[Our Menu]({static}/pdfs/menu.pdf)

La génération du site copierait alors han.jpg vers output/images/han.jpg, menu.pdf vers output/pdfs/menu.pdf, et écrirait les liens appropriés dans test.md.

Si vous utilisez {static} pour créer un lien vers un article ou une page, cela sera transformé en un lien vers son code source.

Attachement de fichiers statiques

À partir de Pelican 3.5, les fichiers statiques peuvent être "attachés" à une page ou un article en utilisant cette syntaxe pour la cible du lien : {attach}path/to/file. Cela fonctionne comme la syntaxe {static}, mais déplace également le fichier statique dans le répertoire de sortie du document liant. Si le fichier statique provient d'un sous-répertoire sous le document liant, cette relation sera préservée à la sortie. Sinon, il deviendra un frère du document liant.

Cela ne fonctionne que pour la création de liens vers des fichiers statiques.

Par exemple, le répertoire de contenu d'un projet pourrait être structuré comme suit :

content
├── blog
│   ├── icons
│   │   └── icon.png
│   ├── photo.jpg
│   └── testpost.md
└── telechargements
    └── archive.zip

pelicanconf.py inclurait :

PATH = 'content'
ARTICLE_PATHS = ['blog']
ARTICLE_SAVE_AS = '{date:%Y}/{slug}.html'
ARTICLE_URL = '{date:%Y}/{slug}.html'

testpost.md inclurait :

Title: Test Post
Category: test
Date: 2014-10-31
![Icon]({attach}icons/icon.png)
![Photo]({attach}photo.jpg)
[Fichier téléchargeable]({attach}/downloads/archive.zip)

La génération du site produirait alors une structure de répertoire de sortie comme suit :

output
└── 2014
    ├── archive.zip
    ├── icons
    │   └── icon.png
    ├── photo.jpg
    └── test-post.html

Notez que tous les fichiers liés à l'aide de {attach} se retrouvent dans ou sous le répertoire de sortie de l'article.

Si un fichier statique est lié plusieurs fois, la fonction de relocalisation de {attach} ne fonctionnera que pour le premier de ces liens à être traité. Après le premier lien, Pelican traitera {attach} comme {static}. Cela évite de casser les liens déjà traités.

Soyez prudent lorsque vous créez des liens vers un fichier depuis plusieurs documents : Étant donné que le premier lien vers un fichier finalise son emplacement et que Pelican ne définit pas l'ordre de traitement des documents, l'utilisation de {attach} sur un fichier lié par plusieurs documents peut entraîner la modification de son emplacement d'une construction de site à l'autre. (Que cela se produise en pratique dépendra du système d'exploitation, du système de fichiers, de la version de Pelican et des documents ajoutés, modifiés ou supprimés du projet.) Les sites externes qui lient vers l'ancien emplacement du fichier pourraient alors voir leurs liens brisés. Il est donc conseillé d'utiliser {attach} uniquement si vous l'utilisez dans tous les liens vers un fichier, et uniquement si les documents liant partagent un seul répertoire. Dans ces conditions, l'emplacement de sortie du fichier ne changera pas lors des futures constructions. Dans les cas où ces précautions ne sont pas possibles, envisagez d'utiliser des liens {static} au lieu de {attach}, et de laisser l'emplacement du fichier être déterminé par les paramètres STATIC_SAVE_AS et STATIC_URL du projet. (Les remplacements save_as et url par fichier peuvent toujours être définis dans EXTRA_PATH_METADATA.)

NOTE :

Lors de l'utilisation de {attach}, tout répertoire parent dans les paramètres *_URL / *_SAVE_AS doit correspondre. Voir aussi : Paramètres d'URL

Lier aux auteurs, catégories, index et tags

Vous pouvez lier aux auteurs, catégories, index et tags en utilisant la syntaxe {author}nom, {category}foobar, {index} et {tag}tagname.

Syntaxe de lien interne dépréciée

Pour rester compatible avec les versions antérieures, Pelican prend toujours en charge les barres verticales (||) en plus des accolades ({}) pour les liens internes. Par exemple : |filename|an_article.rst, |tag|tagname, |category|foobar. La syntaxe a été modifiée de || à {} pour éviter les collisions avec les extensions Markdown ou les directives reST. De même, Pelican prend toujours en charge la liaison au contenu statique avec {filename}. La syntaxe a été modifiée en {static} pour permettre de lier à la fois les articles et pages générés et leurs sources statiques.

La prise en charge de l'ancienne syntaxe pourra être supprimée ultérieurement.

Inclure d'autres fichiers

Les syntaxes Markdown et reStructuredText offrent toutes deux des mécanismes pour cela.

.. include:: file.rst

Inclure un fragment d'un fichier délimité par deux identifiants, mis en évidence comme C++ (le découpage basé sur les numéros de ligne est également possible) :

.. include:: main.cpp
    :code: c++
    :start-after: // begin
    :end-before: // end

Inclure un fichier HTML brut (ou un SVG en ligne) et le placer directement dans la sortie sans aucun traitement :

```html
{! template.html !}
```

Traductions

Il est possible de traduire des articles. Pour ce faire, vous devez ajouter un attribut méta lang à vos articles/pages et définir un paramètre DEFAULT_LANG (qui est l'anglais [en] par défaut). Avec ces paramètres en place, seuls les articles dans la langue par défaut seront listés, et chaque article sera accompagné d'une liste des traductions disponibles pour cet article.

NOTE :

Cette fonctionnalité de base de Pelican ne crée pas de sous-sites (par exemple, example.com/de) avec des templates traduits pour chaque langue. Pour des fonctionnalités plus avancées de ce type, le plugin i18n_subsites peut être utilisé.

Par défaut, Pelican utilise le "slug" de l'URL de l'article pour déterminer si deux articles ou plus sont des traductions l'un de l'autre. (Cela peut être modifié avec le paramètre ARTICLE_TRANSLATION_ID.) Le slug peut être défini manuellement dans les métadonnées du fichier ; s'il n'est pas défini explicitement, Pelican générera automatiquement le slug à partir du titre de l'article.

Voici un exemple de deux articles, l'un en anglais et l'autre en français.

L'article en anglais :

Foobar is not dead
##################
:slug: foobar-is-not-dead
:lang: en
That's true, foobar is still alive!

Et la version française :

Foobar n'est pas mort !

Publication des brouillons

Si vous souhaitez publier un article ou une page en tant que brouillon (pour que des amis le révisent avant publication, par exemple), vous pouvez ajouter un attribut Status: draft à ses métadonnées. Cet article sera alors généré dans le dossier drafts et ne sera pas listé sur la page d'accueil ni sur aucune page de catégorie ou de tag.

Si vos articles doivent être automatiquement publiés en tant que brouillon (pour ne pas publier accidentellement un article avant qu'il ne soit terminé), incluez le statut dans DEFAULT_METADATA :

DEFAULT_METADATA = {
    'status': 'draft',
}

Pour publier un article lorsque le statut par défaut est draft, mettez à jour les métadonnées de l'article pour inclure Status: published.

Articles masqués

Comme les pages, les articles peuvent également être marqués comme hidden (masqués) avec l'attribut Status: hidden. Les articles masqués seront générés vers ARTICLE_SAVE_AS comme prévu, mais ne seront pas inclus par défaut dans les index de tags, de catégories et d'auteurs, ni dans le flux principal d'articles. Cela a pour effet de créer un article "non répertorié".

Ignorer les articles

Les articles marqués avec le statut skip sont ignorés entièrement. Ils ne sont ni traités ni générés vers le chemin ARTICLE_SAVE_AS. Ces articles ne seront de même pas inclus dans les index ou les flux.

Paramètres

Pelican est configurable grâce à un fichier de paramètres que vous pouvez passer en ligne de commande :

pelican content -s path/to/your/pelicanconf.py

Si vous avez utilisé la commande pelican-quickstart, votre fichier de paramètres principal sera nommé pelicanconf.py par défaut.

Vous pouvez également spécifier des paramètres via les options -e / --extra-settings. Cela remplacera les paramètres par défaut ainsi que ceux définis dans le fichier de paramètres. Notez que les valeurs doivent suivre la notation JSON :

pelican content -e SITENAME='"Un site"' READERS='{"html": null}' CACHE_CONTENT=true

Les variables d'environnement peuvent également être utilisées ici, mais doivent être correctement échappées :

pelican content -e API_KEY=''\"$API_KEY\"''

Lorsque vous expérimentez avec différents paramètres (en particulier ceux des métadonnées), la mise en cache peut interférer et les changements peuvent ne pas être visibles. Paramètres d'URL

La première chose à comprendre est qu'il existe actuellement deux méthodes prises en charge pour la formation des URL : relatives et absolues. Les URL relatives sont utiles pour les tests locaux, et les URL absolues sont fiables et les plus utiles pour la publication. Une méthode pour prendre en charge les deux est d'avoir un fichier de configuration Pelican pour le développement local et un autre pour la publication. Pour voir un exemple de ce type de configuration, utilisez le script pelican-quickstart comme décrit dans la section Installation, qui produira deux fichiers de configuration distincts pour le développement local et la publication, respectivement.

Vous pouvez personnaliser les URL et les emplacements où les fichiers seront enregistrés. Les variables *_URL et *_SAVE_AS utilisent les chaînes de format Python. Ces variables vous permettent de placer vos articles dans un emplacement tel que {slug}/index.html et d'y faire référence comme {slug} pour des URL propres (voir exemple ci-dessous). Ces paramètres vous donnent la flexibilité de placer vos articles et pages où vous le souhaitez.

  • date
  • lang
  • author

Pagination

Le comportement par défaut de Pelican est de lister tous les titres d'articles avec une courte description sur la page d'accueil. Bien que cela fonctionne bien pour les sites de petite à moyenne taille, les sites avec une grande quantité d'articles bénéficieront probablement de la pagination de cette liste.

Vous pouvez utiliser les paramètres suivants pour configurer la pagination.

DEFAULT_ORPHANS = 0
Le nombre minimum d'articles autorisés sur la dernière page. Utilisez ceci si vous ne voulez pas que la dernière page ne contienne qu'une poignée d'articles.
DEFAULT_PAGINATION = False
Le nombre maximum d'articles à inclure sur une page, sans compter les orphelins. False pour désactiver la pagination.
PAGINATED_TEMPLATES = {'index': None, 'tag': None, 'category': None, 'author': None}
Les modèles à utiliser avec la pagination, et le nombre d'articles à inclure sur une page. Si cette valeur est None, elle prend par défaut la valeur de DEFAULT_PAGINATION.
PAGINATION_PATTERNS = (
(1, '{name}{extension}', '{name}{extension}'),
(2, '{name}{number}{extension}', '{name}{number}{extension}'),
)
Un ensemble de motifs utilisés pour déterminer la sortie avancée de la pagination.

Utilisation des motifs de pagination

Par défaut, les pages qui suivent .../foo.html sont créées comme .../foo2.html, etc. Le paramètre PAGINATION_PATTERNS peut être utilisé pour modifier cela. Il prend une séquence de triples, où chaque triple est constitué de :

(minimum_page, page_url, page_save_as,)

Pour page_url et page_save_as, vous pouvez utiliser un certain nombre de variables. {url} et {save_as} correspondent respectivement aux valeurs *_URL et *_SAVE_AS du type de page correspondant (par exemple, ARTICLE_SAVE_AS). Si {save_as} == foo/bar.html, alors {name} == foo/bar et {extension} == .html. {base_name} est égal à {name} sauf qu'il supprime le /index final s'il est présent. {number} est le numéro de page.

Par exemple, si vous souhaitez laisser la première page inchangée, mais placer les pages suivantes à .../page/2/ etc, vous pouvez définir PAGINATION_PATTERNS comme suit :

PAGINATION_PATTERNS = (
    (1, '{url}', '{save_as}'),
    (2, '{base_name}/page/{number}/', '{base_name}/page/{number}/index.html'),
)

Si vous souhaitez qu'un motif s'applique à la dernière page de la liste, utilisez -1 comme valeur de minimum_page :

(-1, '{base_name}/last/', '{base_name}/last/index.html'),

Journalisation

Parfois, une longue liste d'avertissements peut apparaître lors de la génération du site. Trouver le message d'erreur significatif au milieu d'une tonne de sorties de log agaçantes peut être assez difficile. Afin de filtrer les messages de log redondants, Pelican fournit le paramètre LOG_FILTER.

LOG_FILTER doit être une liste de tuples (level, msg), chacun composé du niveau de journalisation (jusqu'à warning) et du message à ignorer. Il suffit de remplir la liste avec les messages de log que vous souhaitez masquer, et ils seront filtrés.

Par exemple :

import logging
LOG_FILTER = [(logging.WARN, 'TAG_SAVE_AS is set to False')]

Il est possible de filtrer les messages par modèle. Consultez le code source pour obtenir un modèle.

Par exemple :

import logging
LOG_FILTER = [(logging.WARN, 'Empty alt attribute for image %s in %s')]

ATTENTION :

Le silence des messages par modèle est une fonctionnalité dangereuse. Il est possible de filtrer involontairement plusieurs types de messages avec le même modèle (y compris des messages des futures versions de Pelican). Procédez avec prudence.

NOTE :

Cette option ne fait rien si --debug est passé.

Lecture uniquement du contenu modifié

Pour accélérer le processus de construction, Pelican peut éventuellement lire uniquement les articles et les pages dont le contenu a été modifié.

Lorsque Pelican s'apprête à lire un fichier source de contenu :

1.
Les informations de hachage ou de temps de modification du fichier d'une construction précédente sont chargées à partir d'un fichier cache si LOAD_CONTENT_CACHE est défini sur True. Ces fichiers sont stockés dans le répertoire CACHE_PATH. Si le fichier n'a pas d'enregistrement dans le fichier cache, il est lu comme d'habitude.
2.
Le fichier est vérifié selon CHECK_MODIFIED_METHOD :
  • Si défini sur 'mtime', le temps de modification du fichier est vérifié.
  • Si défini sur le nom d'une fonction fournie par le module hashlib, par exemple 'md5', le hachage du fichier est vérifié.
  • Si défini sur autre chose ou si les informations nécessaires sur le fichier ne peuvent pas être trouvées dans le fichier cache, le contenu est lu comme d'habitude.
3.
Si le fichier est considéré comme inchangé, les données de contenu sauvegardées lors d'une construction précédente correspondant au fichier sont chargées depuis le cache, et le fichier n'est pas lu.
4.
Si le fichier est considéré comme modifié, le fichier est lu et les nouvelles informations de modification ainsi que les données de contenu sont sauvegardées dans le cache si CACHE_CONTENT est défini sur True.

Si CONTENT_CACHING_LAYER est défini sur 'reader' (par défaut), le contenu brut et les métadonnées renvoyés par un lecteur sont mis en cache. Si ce paramètre est défini sur 'generator', l'objet de contenu traité est mis en cache. La mise en cache de l'objet de contenu traité m

ay conflict avec les plugins (car certains signaux liés à la lecture peuvent être ignorés) et la fonctionnalité WITH_FUTURE_DATES (car le statut brouillon des objets de contenu mis en cache ne changerait pas automatiquement avec le temps).

La vérification des heures de modification est plus rapide que la comparaison des hachages de fichiers, mais elle n'est pas aussi fiable car les informations mtime peuvent être perdues, par exemple lors de la copie de fichiers sources de contenu à l'aide des commandes cp ou rsync sans le mode de préservation mtime (qui pour rsync peut être appelé en passant le drapeau --archive).

Les fichiers de cache sont des "pickles" Python, ils peuvent donc ne pas être lisibles par différentes versions de Python car le format pickle change souvent. Si une telle erreur est rencontrée, elle est interceptée et le fichier de cache est reconstruit automatiquement dans le nouveau format. Les fichiers de cache seront également reconstruits après la modification du paramètre GZIP_CACHE.

L'option de ligne de commande --ignore-cache est utile lorsque l'ensemble du cache doit être régénéré, par exemple lors de modifications du fichier de configuration qui affecteront le contenu mis en cache, ou simplement à des fins de débogage. Lorsque Pelican s'exécute en mode de rechargement automatique, la modification du fichier de configuration le fera ignorer le cache automatiquement si AUTORELOAD_IGNORE_CACHE est True.

Notez que même en utilisant du contenu mis en cache, toutes les sorties sont toujours générées, donc les heures de modification des fichiers *.html générés changeront toujours. Par conséquent, le téléchargement basé sur rsync peut bénéficier de l'option --checksum.

Plugins

À partir de la version 3.0, Pelican prend en charge les plugins. Les plugins sont un moyen d'ajouter des fonctionnalités à Pelican sans avoir à modifier directement le cœur de Pelican.

Comment utiliser les plugins

pelican-plugins

Si vous laissez le paramètre PLUGINS par défaut (None), Pelican découvrira automatiquement les plugins de namespace et les enregistrera. Si, en revanche, vous spécifiez un paramètre PLUGINS sous forme de liste de plugins, cette auto-découverte sera désactivée. À ce stade, seuls les plugins que vous spécifiez seront enregistrés, et vous devrez explicitement lister tous les plugins de namespace.

Si vous utilisez le paramètre PLUGINS, vous pouvez spécifier des plugins de deux manières. La première méthode spécifie les plugins sous forme de liste de chaînes de caractères. Les plugins de namespace peuvent être spécifiés soit par leurs noms complets (pelican.plugins.myplugin) soit par leurs noms courts (myplugin) :

PLUGINS = ['package.myplugin',
           'namespace_plugin1',
           'pelican.plugins.namespace_plugin2']

Alternativement, vous pouvez les importer dans votre fichier de configuration et passer les modules :

from package import myplugin
from pelican.plugins import namespace_plugin1, namespace_plugin2
PLUGINS = [myplugin, namespace_plugin1, namespace_plugin2]

NOTE :

Lors de l'expérimentation avec différents plugins (en particulier ceux qui traitent des métadonnées et du contenu), la mise en cache peut interférer et les modifications peuvent ne pas être visibles. Dans de tels cas, désactivez la mise en cache avec LOAD_CONTENT_CACHE = False ou utilisez l'option de ligne de commande --ignore-cache.

Si vos plugins ne se trouvent pas dans un chemin importable, vous pouvez spécifier une liste de chemins via le paramètre PLUGIN_PATHS. Comme le montre l'exemple suivant, les chemins dans la liste PLUGIN_PATHS peuvent être absolus ou relatifs au fichier de configuration :

Comment créer des plugins

Les plugins sont basés sur le concept de signaux. Pelican émet des signaux et les plugins s'y abonnent. La liste des signaux disponibles est documentée dans une section ultérieure.

La seule règle à suivre pour les plugins est de définir une fonction appelable register, dans laquelle vous mappez les signaux à la logique de votre plugin. Prenons un exemple simple :

import logging
from pelican import signals
log = logging.getLogger(__name__)
def test(sender):
    log.debug("%s initialisé !!", sender)
def register():
    signals.initialized.connect(test)

NOTE :

Les récepteurs de signaux sont faiblement référencés et ne doivent donc pas être définis dans votre fonction appelable register, sinon ils seront récupérés par le garbage collector avant que le signal ne soit émis.

Si plusieurs plugins se connectent au même signal, les plugins seront invoqués dans l'ordre où ils sont enregistrés. Lorsque le paramètre PLUGINS est défini, l'ordre d'invocation des plugins sera l'ordre dans lequel les plugins sont listés dans le paramètre PLUGINS. Si vous vous fiez aux plugins de namespace auto-découverts et qu'aucun paramètre PLUGINS n'est défini, les plugins seront invoqués dans le même ordre qu'ils sont découverts (le même ordre que celui listé dans la sortie de la commande pelican-plugins). Si vous souhaitez spécifier l'ordre explicitement, désactivez l'auto-découverte en définissant PLUGINS dans l'ordre souhaité.

Structure des plugins de namespace

Les plugins de namespace doivent adhérer à une certaine structure pour fonctionner correctement. Ils doivent être installables (c'est-à-dire contenir setup.py ou équivalent) et avoir une structure de dossiers comme suit :

myplugin
├── pelican
│   └── plugins
│       └── myplugin
│           ├── __init__.py
│           └── ...
├── ...
└── setup.py

Il est crucial que le dossier pelican ou pelican/plugins ne contienne pas de fichier __init__.py. En fait, il est préférable que ces dossiers soient vides à l'exception des dossiers listés dans la structure ci-dessus et que vous gardiez vos fichiers liés aux plugins contenus uniquement dans le dossier pelican/plugins/myplugin pour éviter tout problème.

Comment créer un nouveau lecteur

Une chose que vous pourriez vouloir est d'ajouter la prise en charge de votre propre format d'entrée. Bien que cela puisse avoir du sens d'ajouter cette fonctionnalité au cœur de Pelican, nous avons sagement choisi d'éviter cette situation et avons plutôt fait définir les différents lecteurs via des plugins.

La raison derrière ce choix est principalement que les plugins sont vraiment faciles à écrire et ne ralentissent pas Pelican lui-même lorsqu'ils ne sont pas actifs.

Assez parlé — voici un exemple :

from pelican import signals
from pelican.readers import BaseReader
# Créer une nouvelle classe de lecteur, héritant de pelican.reader.BaseReader
class NewReader(BaseReader):
    enabled = True  # Ouais, vous voudrez probablement ça :-)
    # La liste des extensions de fichiers que ce lecteur doit correspondre.
    # Si plusieurs lecteurs utilisaient la même extension, le dernier l'emportera
    # (donc celui que vous définissez ici, très probablement).
    file_extensions = ['yeah']
    # Vous devez avoir une méthode read, qui prend un nom de fichier et retourne
    # un contenu et les métadonnées associées.
    def read(self, filename):
        metadata = {'title': 'Oh yeah',
                    'category': 'Foo',
                    'date': '2012-12-01'}
        parsed = {}
        for key, value in metadata.items():
            parsed[key] = self.process_metadata(key, value)
        return "Some content", parsed
def add_reader(readers):
    readers.reader_classes['yeah'] = NewReader
# C'est comme ça que fonctionne pelican.
def register():
    signals.readers_init.connect(add_reader)

Lister et lier les archives par période

La variable period_archives peut être utilisée pour générer une liste de liens vers l'ensemble des archives par période que Pelican génère. En tant que variable commune, elle est disponible pour être utilisée dans n'importe quel template, vous pouvez donc implémenter un tel index dans un template direct personnalisé, ou dans une barre latérale visible sur différentes pages du site.

period_archives est un dictionnaire qui peut contenir les clés year, month et/ou day, selon les paramètres *_ARCHIVE_SAVE_AS activés. La valeur correspondante est une liste de dictionnaires, où chaque dictionnaire représente une période (ordonnée selon le paramètre NEWEST_FIRST_ARCHIVES) avec les clés et valeurs suivantes :

Clé Valeur
period Le même tuple que celui décrit dans period_archives.html, par exemple (2023, 'Juin', 18).
period_num Le même tuple que celui décrit dans period_archives.html, par exemple (2023, 6, 18).
url L'URL de la page d'archive par période, par exemple posts/2023/06/18/. Ceci est contrôlé par le paramètre correspondant *_ARCHIVE_URL.
save_as L'emplacement pour sauvegarder le fichier de la page d'archive par période, par exemple posts/2023/06/18/index.html. Ceci est utilisé en interne par Pelican et n'est généralement pas pertinent pour les thèmes.
articles Une liste d'objets Article qui correspondent à la période.
dates Même liste que articles, mais triée selon le paramètre NEWEST_FIRST_ARCHIVES.

Voici un exemple de la façon dont period_archives peut être utilisé dans un template :

<ul>
{% for archive in period_archives.month %}
    <li>
        <a href="{{ SITEURL }}/{{ archive.url }}">
            {{ archive.period | reverse | join(' ') }} ({{ archive.articles|count }})
        </a>
    </li>
{% endfor %}
</ul>

Vous pouvez changer period_archives.month dans l'instruction for par period_archives.year ou period_archives.day selon ce qui convient, en fonction de la granularité de période souhaitée.

Inheritance

Since version 3.0, Pelican supports inheritance from the simple theme, so you can reuse the simple theme templates in your own themes.

If one of the mandatory files in the templates/ directory of your theme is missing, it will be replaced by the matching template from the simple theme. So if the HTML structure of a template in the simple theme is right for you, you don't have to write a new template from scratch.

You can also extend templates from the simple theme in your own themes by using the {% extends %} directive as in the following example:

{% extends "!simple/index.html" %}   <!-- extends the ``index.html`` template from the ``simple`` theme -->
{% extends "index.html" %}   <!-- "regular" extending -->

Example

With this system, it is possible to create a theme with just two files.

base.html

The first file is the templates/base.html template:

{% extends "!simple/base.html" %}
{% block head %}
{{ super() }}
   <link rel="stylesheet" type="text/css" href="{{ SITEURL }}/theme/css/style.css" />
{% endblock %}
1.
On the first line, we extend the base.html template from the simple theme, so we don't have to rewrite the entire file.
2.
On the third line, we open the head block which has already been defined in the simple theme.
3.
On the fourth line, the function super() keeps the content previously inserted in the head block.
4.
On the fifth line, we append a stylesheet to the page.
5.
On the last line, we close the head block.

This file will be extended by all the other templates, so the stylesheet will be linked from all pages.

style.css

The second file is the static/css/style.css CSS stylesheet:

body {
    font-family : monospace ;
    font-size : 100% ;
    background-color : white ;

}

Listing the installed themes

With pelican-themes, you can see the available themes by using the -l or --list option:

$ pelican-themes -l
notmyidea
two-column@
simple
$ pelican-themes --list
notmyidea
two-column@
simple

In this example, we can see there are three themes available: notmyidea, simple, and two-column.

two-column is followed by an @ because this theme is not copied to the Pelican theme path, but is instead just linked to it (see Creating symbolic links for details about creating symbolic links).

Note that you can combine the --list option with the -v or --verbose option to get more verbose output, like this:

$ pelican-themes -v -l
/usr/local/lib/python2.6/dist-packages/pelican-2.6.0-py2.6.egg/pelican/themes/notmyidea
/usr/local/lib/python2.6/dist-packages/pelican-2.6.0-py2.6.egg/pelican/themes/two-column (symbolic link to `/home/skami/Dev/Python/pelican-themes/two-column')
/usr/local/lib/python2.6/dist-packages/pelican-2.6.0-py2.6.egg/pelican/themes/simple

Installing themes

You can install one or more themes using the -i or --install option. This option takes as argument the path(s) of the theme(s) you want to install, and can be combined with the --verbose option:

# pelican-themes --install ~/Dev/Python/pelican-themes/notmyidea-cms --verbose
# pelican-themes -
-installer ~/Dev/Python/pelican-themes/notmyidea-cms\ ~/Dev/Python/pelican-themes/martyalchin \ --verbeux 
# pelican-themes -vi ~/Dev/Python/pelican-themes/two-column

La commande pelican-themes peut également supprimer des thèmes du chemin des thèmes de Pelican. L'option -r ou --remove prend comme argument le nom du ou des thèmes que vous souhaitez supprimer, et peut être combinée avec l'option --verbose.

# pelican-themes --remove two-column
# pelican-themes -r martyachin notmyidea-cmd -v

Création de liens symboliques

pelican-themes peut également installer des thèmes en créant des liens symboliques au lieu de copier l'intégralité des thèmes dans le chemin des thèmes de Pelican.

Pour lier symboliquement un thème, vous pouvez utiliser l'option -s ou --symlink, qui fonctionne exactement comme l'option --install :

# pelican-themes --symlink ~/Dev/Python/pelican-themes/two-column

Dans cet exemple, le thème two-column est maintenant lié symboliquement au chemin des thèmes de Pelican, nous pouvons donc l'utiliser, mais nous pouvons aussi le modifier sans avoir à le réinstaller après chaque modification.

Ceci est utile pour le développement de thèmes :

$ sudo pelican-themes -s ~/Dev/Python/pelican-themes/two-column
$ pelican ~/Blog/content -o /tmp/out -t two-column
$ firefox /tmp/out/index.html
$ vim ~/Dev/Pelican/pelican-themes/two-column/static/css/main.css
$ pelican ~/Blog/content -o /tmp/out -t two-column
$ cp /tmp/bg.png ~/Dev/Pelican/pelican-themes/two-column/static/img/bg.png
$ pelican ~/Blog/content -o /tmp/out -t two-column
$ vim ~/Dev/Pelican/pelican-themes/two-column/templates/index.html
$ pelican ~/Blog/content -o /tmp/out -t two-column

Faire plusieurs choses à la fois

Les options --install, --remove et --symlink ne sont pas mutuellement exclusives, vous pouvez donc les combiner dans la même ligne de commande pour effectuer plus d'une opération à la fois, comme ceci :

# pelican-themes --remove notmyidea-cms two-column \
                 --install ~/Dev/Python/pelican-themes/notmyidea-cms-fr \
                 --symlink ~/Dev/Python/pelican-themes/two-column \
                 --verbose

Dans cet exemple, le thème notmyidea-cms est remplacé par le thème notmyidea-cms-fr

Lors de l'expérimentation avec différents paramètres (en particulier ceux des métadonnées), la mise en cache peut interférer et les modifications peuvent ne pas être visibles. Dans de tels cas, assurez-vous que la mise en cache est désactivée via LOAD_CONTENT_CACHE = False ou utilisez le commutateur de ligne de commande --ignore-cache.

Je crée mon propre thème. Comment utiliser Pygments pour la coloration syntaxique ?

Comment créer mon propre thème ?

Veuillez vous référer à Thèmes.

Puis-je remplacer des modèles individuels sans forker tout le thème ?

Oui, vous pouvez remplacer les modèles existants du thème que vous utilisez, ou ajouter de nouveaux modèles, via la variable THEME_TEMPLATES_OVERRIDES. Par exemple, pour remplacer le modèle de page, vous pouvez définir l'emplacement de vos modèles comme ceci :

THEME_TEMPLATES_OVERRIDES = ["templates"]

Vous pouvez ensuite définir un modèle personnalisé dans templates/page.html. Voir Thèmes pour plus de détails.

Je veux utiliser Markdown, mais j'ai reçu une erreur.

Si vous essayez de générer du contenu Markdown sans avoir d'abord installé la bibliothèque Markdown, vous pourriez voir un message indiquant Aucun fichier valide trouvé dans le contenu. Markdown n'est pas une dépendance forte pour Pelican, donc si vous avez du contenu au format Markdown, vous devrez explicitement installer la bibliothèque Markdown. Vous pouvez le faire en tapant la commande suivante, en ajoutant sudo si les autorisations le nécessitent :

python -m pip install markdown

Puis-je utiliser des métadonnées arbitraires dans mes modèles ?

Oui. Par exemple, pour inclure une date de modification dans un article Markdown, on pourrait inclure ceci en haut de l'article :

Modifié : 2012-08-08

Pour reStructuredText, ces métadonnées devraient bien sûr être préfixées par un deux-points :

:Modifié : 2012-08-08

Ces métadonnées peuvent ensuite être accessibles dans les modèles comme article.html via :

{% if article.modified %}
Dernière modification : {{ article.modified }}
{% endif %}

Si vous souhaitez inclure des métadonnées dans des modèles en dehors du contexte de l'article (par exemple, base.html), l'instruction if devrait plutôt être :

{% if article and article.modified %}

Essayez ces paramètres :

USE_FOLDER_AS_CATEGORY = False

Comment attribuer des modèles personnalisés à chaque page ?

C'est aussi simple que d'ajouter une ligne de métadonnées supplémentaire à n'importe quelle page ou article que vous souhaitez personnaliser. Par exemple, voici comment cela serait géré pour du contenu au format reST :

:template: nom_du_template

Pour du contenu au format Markdown :

Template: nom_du_template

Assurez-vous ensuite que votre thème contient le fichier de modèle pertinent (par exemple, nom_du_template.html). Si vous souhaitez simplement ajouter un nouveau modèle personnalisé à un thème existant, vous pouvez également le fournir dans un répertoire spécifié par THEME_TEMPLATES_OVERRIDES (voir Thèmes).

Comment puis-je remplacer l'URL générée d'une page ou d'un article spécifique ?

Incluez les métadonnées url et save_as dans toutes les pages ou articles dont vous souhaitez remplacer l'URL générée. Voici un exemple de page au format reST :

Page d'URL/save_as de remplacement
#########################
:url: remplacement/url/
:save_as: remplacement/url/index.html

Avec ces métadonnées, la page sera écrite dans remplacement/url/index.html et Pelican utilisera l'URL remplacement/url/ pour lier à cette page.

Comment puis-je utiliser une page statique comme page d'accueil ?

La fonctionnalité de remplacement mentionnée ci-dessus peut être utilisée pour spécifier une page statique comme page d'accueil. L'exemple Markdown suivant pourrait être stocké dans content/pages/home.md :

Titre : Bienvenue sur mon site
URL :
save_as : index.html
Merci de votre visite. Bienvenue !

Si l'index original du blog est toujours souhaité, il peut alors être enregistré dans un emplacement différent en définissant INDEX_SAVE_AS = 'blog_index.html' pour le modèle direct 'index'.

Et si je veux désactiver la génération de flux ?

Pour désactiver la génération de flux, tous les paramètres de flux doivent être définis sur None. Tous les paramètres de flux sauf trois sont déjà définis sur None par défaut, donc si vous voulez désactiver toute génération de flux, vous n'avez qu'à spécifier les paramètres suivants :

FEED_ALL_ATOM = None
CATEGORY_FEED_ATOM = None
TRANSLATION_FEED_ATOM = None
AUTHOR_FEED_ATOM = None
AUTHOR_FEED_RSS = None

Le mot None ne doit pas être entouré de guillemets. Veuillez noter que None et '' ne sont pas la même chose.

Questions fréquentes

SITEURL n'est pas défini

Afin de générer correctement les liens dans Pelican, vous devez définir SITEURL sur le chemin complet de votre site.

Les flux sont toujours générés lorsque cet avertissement est affiché, mais les liens internes peuvent être mal formés et donc le flux peut ne pas être validé.

Puis-je forcer les flux Atom à n'afficher que des résumés au lieu du contenu des articles ?

Au lieu d'avoir à ouvrir une fenêtre de navigateur séparée pour lire les articles, la grande majorité des utilisateurs de lecteurs de flux préfèrent lire le contenu dans le lecteur de flux lui-même. C'est principalement pour cette raison que Pelican ne prend pas en charge la restriction des flux Atom pour ne contenir que des résumés. Contrairement aux flux Atom, la spécification du flux RSS ne comprend pas de champ content séparé, de sorte que par défaut Pelican publie des flux RSS qui ne contiennent que des résumés (mais peuvent éventuellement être configurés pour publier des flux RSS de contenu complet). Le comportement par défaut de génération de flux offre donc aux utilisateurs un choix : s'abonner aux flux Atom pour le contenu complet ou aux flux RSS pour les résumés uniquement.

Pelican convient-il uniquement aux blogs ?

Non. Pelican peut être facilement configuré pour créer et maintenir tout type de site statique. Cela peut nécessiter une légère personnalisation de votre thème et de votre configuration Pelican. Par exemple, si vous créez un site de lancement pour votre produit et que vous n'avez pas besoin de tags sur votre site, vous pourriez supprimer le code HTML pertinent de votre thème. Vous pouvez également désactiver la génération de pages liées aux tags via :

TAGS_SAVE_AS = ''
TAG_SAVE_AS = ''

Pourquoi Pelican écrit-il toujours tous les fichiers HTML même avec la mise en cache du contenu activée ?

Afin de déterminer de manière fiable si la sortie HTML est différente avant de l'écrire, une grande partie de l'environnement de génération, y compris les contextes de modèles, les plugins importés, etc., devrait être sauvegardée et comparée, au moins sous la forme d'un hachage (ce qui nécessiterait une gestion spéciale des types non hachables), en raison de toutes les combinaisons possibles de plugins, de pagination, etc. qui peuvent changer de nombreuses manières différentes. Cela nécessiterait beaucoup plus de temps de traitement, de mémoire et d'espace de stockage. L'écriture des fichiers à chaque fois est beaucoup plus rapide et beaucoup plus fiable.

Cependant, cela signifie que l'heure de modification des fichiers change à chaque fois, de sorte qu'un transfert basé sur rsync les transférera même si leur contenu n'a pas changé. Une solution simple consiste à faire en sorte que rsync utilise l'option --checksum, ce qui lui permettra de comparer les sommes de contrôle des fichiers de manière beaucoup plus rapide que Pelican.

Comment traiter uniquement un sous-ensemble de tous les articles ?

Il est souvent utile de traiter seulement, par exemple, 10 articles à des fins de débogage. Cela peut être réalisé en spécifiant explicitement uniquement les noms de fichiers de ces articles dans ARTICLE_PATHS. Une liste de tels noms de fichiers pourrait être trouvée en utilisant une commande similaire à cd content; find -name '*.md' | head -n 10.

Mon nuage de tags a disparu/est cassé depuis que j'ai mis à niveau Pelican

Depuis que j'ai mis à niveau Pelican, mes pages ne sont plus rendues

Les pages étaient disponibles pour les thèmes sous forme de pages en minuscules et de PAGES en majuscules. Pour aligner cela avec la section Templates and Variables, PAGES a été supprimé. Ceci est rapidement résolu en mettant à jour votre thème pour itérer sur pages au lieu de PAGES. Remplacez simplement :

{% for pg in PAGES %}

par quelque chose comme :

{% for pg in pages %}

Comment empêcher Pelican d'essayer d'analyser mes fichiers statiques comme du contenu ?

Les générateurs d'articles et de pages de Pelican s'exécutent avant son générateur de fichiers statiques. Cela signifie que si vous utilisez une configuration similaire à la configuration par défaut, où un répertoire source statique est défini dans un paramètre *_PATHS, tous les fichiers ayant une extension de fichier de contenu valide (.html, .rst, .md, ...) seront traités comme des articles ou des pages avant d'être traités comme des fichiers statiques.

Pour contourner ce problème, utilisez le paramètre *_EXCLUDES approprié ou désactivez le lecteur concerné via READERS si vous n'en avez pas besoin.

Pages personnalisées 404

Lorsqu'un navigateur demande une ressource que le serveur web ne trouve pas, le serveur web affiche généralement une page d'erreur générique "Fichier non trouvé" (404) qui peut être austère et inesthétique. Title: Non trouvé
Status: hidden
Save_as: 404.html
L'élément demandé n'a pas pu être trouvé. Peut-être souhaitez-vous consulter les [Archives](/archives.html) ?

La prochaine étape consiste à configurer votre serveur web pour afficher cette page personnalisée au lieu de sa page 404 par défaut. Pour Nginx, ajoutez ce qui suit au bloc location de votre fichier de configuration :

error_page 404 /404.html;

Pour Apache :

ErrorDocument 404 /404.html

Là encore, vous pouvez profiter de ghp-import:

$ pelican content -o output -s pelicanconf.py
$ ghp-import output -b gh-pages

name: Build and Deploy Site

La section on du workflow définit les événements qui déclencheront le workflow. Dans cet exemple, le workflow s'exécutera lors des pushes vers la branche principale, des pull requests vers la branche principale et des exécutions manuelles du workflow.

Conseils de journalisation

Essayez d'utiliser la journalisation avec des niveaux appropriés.

Pour les messages de journalisation qui ne sont pas répétés, utilisez la méthode Python habituelle:

# en haut du fichier
import logging
logger = logging.getLogger(__name__)
# quand nécessaire
logger.warning("Un avertissement avec formatage %s", arg_a_formater)

Ne formatez pas vous-même les messages de journal. Utilisez le formatage %s dans les messages et passez des arguments au logger. Ceci est important, car le logger Pelican prétraitera certains arguments, tels que les exceptions.

Limitation des messages de journal superflus

Si le message de journal peut survenir plusieurs fois, vous voudrez peut-être limiter le journal pour éviter de le saturer. Pour ce faire, utilisez l'argument de mot-clé extra pour le message de journalisation dans le format suivant:

logger.warning("Un avertissement avec formatage %s", arg_a_formater,
    extra={'limit_msg': 'Un message générique pour trop d\'avertissements'})

Optionnellement, vous pouvez également définir 'limit_args' comme un tuple d'arguments dans le dictionnaire extra si votre message générique nécessite un formatage.

La limite est fixée à 5, c'est-à-dire que les quatre premiers logs avec le même 'limit_msg' sont affichés normalement, mais le cinquième sera journalisé en utilisant 'limit_msg' (et 'limit_args' si présent). Après le cinquième, les messages de journal correspondants seront ignorés.

Par exemple, si vous souhaitez journaliser les ressources manquantes, utilisez le code suivant:

for resource in resources:
    if resource.is_missing:
        logger.warning(
            'La ressource %s est manquante', resource.name,
            extra={'limit_msg': 'D\'autres ressources étaient manquantes'})

Les messages de journal seront affichés comme suit:

WARNING : La ressource prettiest_cat.jpg est manquante
WARNING : La ressource best_cat_ever.jpg est manquante
WARNING : La ressource cutest_cat.jpg est manquante
WARNING : La ressource lolcat.jpg est manquante
WARNING : D'autres ressources étaient manquantes

Sortie de traceback dans les journaux

Si vous journalisez dans un bloc except, vous voudrez peut-être fournir également les informations de traceback. Vous pouvez le faire en définissant l'argument de mot-clé exc_info sur True lors de la journalisation. Cependant, le faire par défaut peut être indésirable car les tracebacks sont longs et peuvent être déroutants pour les utilisateurs ordinaires. Essayez de les limiter au mode --debug comme suit:

try:
    some_action()
except Exception as e:
    logger.error('Une exception s\'est produite : %s', e,
        exc_info=settings.get('DEBUG', False))

Internes de Pelican

Cette section décrit le fonctionnement interne de Pelican. Comme vous le verrez, c'est assez simple, mais un peu de documentation ne fait pas de mal. :)

Vous pouvez également trouver dans la section Un peu d'histoire sur Pelican un extrait d'un rapport que l'auteur original a écrit avec des informations sur la conception du logiciel.

Structure globale

Ce que fait Pelican, c'est prendre une liste de fichiers et les traiter en une sorte de sortie. Habituellement, les fichiers d'entrée sont des fichiers reStructuredText et Markdown, et la sortie est un blog, mais l'entrée et la sortie peuvent être tout ce que vous voulez.

La logique est séparée en différentes classes et concepts:

  • Les Writers sont responsables de l'écriture des fichiers: fichiers .html, flux RSS, etc. Comme ces opérations sont couramment utilisées, l'objet est créé une fois, puis passé aux générateurs.
  • Les Readers sont utilisés pour lire à partir de divers formats (HTML, Markdown et reStructuredText pour le moment, mais le système est extensible). Étant donné un fichier, ils renvoient des métadonnées (auteur, tags, catégorie, etc.) et du contenu (formaté en HTML).
  • Les Generators génèrent les différentes sorties. Par exemple, Pelican est livré avec ArticlesGenerator et PageGenerator. Étant donné une configuration, ils peuvent faire ce qu'ils veulent. La plupart du temps, il s'agit de générer des fichiers à partir d'entrées.
  • Pelican utilise également des modèles, il est donc facile d'écrire votre propre thème. La syntaxe est Jinja2 et est très facile à apprendre, n'hésitez donc pas à vous lancer et à créer votre propre thème.

Comment implémenter un nouveau lecteur ?

Existe-t-il un langage de balisage génial que vous souhaitez ajouter à Pelican ? Eh bien, la seule chose que vous ayez à faire est de créer une classe avec une méthode read qui renvoie le contenu HTML et certaines métadonnées.

Regardez le lecteur Markdown:

from pelican.readers import BaseReader
from pelican.utils import pelican_open
from markdown import Markdown
class MarkdownReader(BaseReader):
    enabled = True
    def read(self, source_path):
        """Parse content and metadata of markdown files"""
        with pelican_open(source_path) as text:
            md_extensions = {'markdown.extensions.meta': {},
                             'markdown.extensions.codehilite': {}}
            md = Markdown(extensions=md_extensions.keys(),
                          extension_configs=md_extensions)
            content = md.convert(text)
        metadata = {}
        for name, value in md.Meta.items():
            name = name.lower()
            meta = self.process_metadata(name, value[0])
            metadata[name] = meta
        return content, metadata

Simple, n'est-ce pas ?

Si votre nouveau lecteur nécessite des dépendances Python supplémentaires, vous devez encapsuler leurs instructions d'importation dans un bloc try...except. Ensuite, à l'intérieur de la classe du lecteur, définissez l'attribut de classe enabled pour marquer le succès ou l'échec de l'importation. Cela permet aux utilisateurs de continuer à utiliser leur méthode de balisage préférée sans avoir à installer des modules pour les formats qu'ils n'utilisent pas.

Comment implémenter un nouveau générateur ?

Les générateurs ont deux méthodes importantes. Vous n'êtes pas obligé de créer les deux ; seuls les générateurs existants seront appelés.

  • generate_context, qui est appelée en premier, pour tous les générateurs. Faites ce que vous avez à faire et mettez à jour le contexte global si nécessaire. Ce contexte est partagé entre tous les générateurs et sera passé aux modèles. Par exemple, la méthode generate_context de PageGenerator trouve toutes les pages, les transforme en objets et les ajoute au contexte. Faites attention à ne rien produire en utilisant ce contexte à ce stade, car il l est
likely to change by the effect of other generators.
  • generate_output is then called. And guess what is it made for? Oh, generating the output. :) It's here that you may want to look at the context and call the methods of the writer object that is passed as the first argument of this function. In the PageGenerator example, this method will look at all the pages recorded in the global context and output a file on the disk (using the writer method write_file) for each page encountered.

    Pelican est un générateur de blog statique simple. Il analyse des fichiers en balisage (Markdown ou reStructuredText pour le moment) et génère un dossier HTML avec tous les fichiers dedans. J'ai choisi d'utiliser Python pour implémenter Pelican car cela me semblait simple et adapté à mes besoins. Je ne voulais pas définir une classe pour chaque chose, tout en gardant mes éléments faiblement couplés. Il s'avère que c'était exactement ce que je voulais. De temps en temps, grâce aux retours de certains utilisateurs, il m'a fallu très peu de temps pour y apporter des corrections. Jusqu'à présent, j'ai refactorisé le code de Pelican deux fois ; chaque fois cela a pris moins de 30 minutes.

    Cas d'utilisation

    J'utilisais auparavant WordPress, une solution que vous pouvez héberger sur un serveur web pour gérer votre blog. La plupart du temps, je préfère utiliser des langages de balisage comme Markdown ou reStructuredText pour taper mes articles. Pour ce faire, j'utilise vim. Je pense qu'il est important de laisser les gens choisir l'outil qu'ils veulent pour écrire leurs articles. À mon avis, un gestionnaire de blog devrait simplement vous permettre de prendre n'importe quel type d'entrée et de le transformer en un weblog. C'est ce que fait Pelican. Vous pouvez écrire vos articles en utilisant l'outil que vous voulez, et le langage de balisage que vous voulez, puis générer un weblog statique en HTML. [image]

    Pour être suffisamment flexible, Pelican prend en charge les modèles, vous pouvez donc facilement écrire vos propres thèmes si vous le souhaitez.

    Processus de conception

    Pelican est né d'un besoin que j'avais. J'ai commencé par créer une application en un seul fichier, et je l'ai fait évoluer pour supporter ce qu'elle fait maintenant. Pour commencer, j'ai écrit une partie de la documentation sur ce que je voulais faire. Ensuite, j'ai créé le contenu que je voulais analyser (les fichiers reStructuredText) et j'ai commencé à expérimenter avec le code. Pelican faisait 200 lignes et contenait près de dix fonctions et une classe lorsqu'il était utilisable pour la première fois.

    J'ai rencontré différents problèmes au fil du temps et j'ai voulu ajouter des fonctionnalités à Pelican tout en l'utilisant. Le premier changement que j'ai effectué a été d'ajouter la prise en charge d'un fichier de configuration. Il est possible de passer les options en ligne de commande, mais cela peut être fastidieux s'il y en a beaucoup. De même, j'ai ajouté la prise en charge de différentes choses au fil du temps : flux Atom, thèmes multiples, prise en charge de plusieurs langages de balisage, etc. À un moment donné, il est apparu que le mantra "un seul fichier" n'était plus suffisant pour Pelican, j'ai donc décidé de retravailler un peu tout cela, et de le diviser en plusieurs fichiers distincts.

    J'ai séparé la logique en différentes classes et concepts :

    • Les writers sont responsables de tout le processus d'écriture des fichiers. Ils sont responsables de l'écriture des fichiers .html, des flux RSS, etc. Comme ces opérations sont couramment utilisées, l'objet est créé une seule fois, puis passé aux générateurs.
    • Les readers sont utilisés pour lire à partir de divers formats (Markdown et reStructuredText pour le moment, mais le système est extensible). Étant donné un fichier, ils renvoient des métadonnées (auteur, tags, catégorie, etc.) et du contenu (formaté en HTML).
    • Les generators génèrent les différentes sorties. Par exemple, Pelican est livré avec un ArticlesGenerator et un PagesGenerator, entre autres. Étant donné une configuration, ils peuvent faire tout ce que vous voulez. Le plus souvent, il s'agit de générer des fichiers à partir d'entrées (entrées utilisateur et fichiers).

    Je traite également des objets de contenu. Ils peuvent être des Articles, des Pages, des Citations, ou tout ce que vous voulez. Ils sont définis dans le module contents.py et représentent un contenu à utiliser par le programme.

    Plus en détail

    Voici un aperçu des classes impliquées dans Pelican. [image]

    L'interface n'existe pas vraiment, et je ne l'ai ajoutée que pour clarifier l'ensemble. J'utilise le "duck typing" et non les interfaces.

    En interne, le processus suivant est suivi :

    • Tout d'abord, la ligne de commande est analysée, et le contenu de l'utilisateur est utilisé pour initialiser les différents objets générateurs.
    • Un contexte est créé. Il contient les paramètres de la ligne de commande et d'un fichier de configuration s'il est fourni.
    • La méthode generate_context de chaque générateur est appelée, mettant à jour le contexte.
    • Le writer est créé et donné à la méthode generate_output de chaque générateur.

    Je fais deux appels car il est important que lorsque la sortie est générée par les générateurs, le contexte ne change pas. Autrement dit, la première méthode generate_context doit modifier le contexte, tandis que la seconde méthode generate_output ne doit pas le faire.

    Ensuite, il appartient aux générateurs de faire ce qu'ils veulent, dans les méthodes generate_context et generate_content. Prendre la classe ArticlesGenerator aidera à comprendre certains autres concepts. Voici ce qui se passe lors de l'appel de la méthode generate_context :

    • Lire le dossier « path », à la recherche de fichiers restructured text, les charger un par un, et construire un objet de contenu (Article) avec lui. Pour ce faire, utiliser des objets Reader.
    • Mettre à jour le contexte avec tous ces articles.

    Ensuite, la méthode generate_content utilise le contexte et le writer pour générer la sortie souhaitée.

    Synopsis

    pelican [OPTIONS] INPUTDIR OUTPUTDIR

    -h, --help
    Afficher un message d'aide et quitter.
    -v, --version
    Afficher la version du programme et quitter.
    -p, --portable-output
    Crée des chemins de sortie portables (relatifs à `OUTPUTDIR`). C'est le comportement par défaut.
    -f, --dont-feed-output
    Désactive la génération de flux de syndication (Atom, RSS).
    -s, --dont-static
    Désactive la copie des fichiers statiques depuis `INPUTDIR` vers `OUTPUTDIR`.
    -t, --theme THEME
    Utilise le thème spécifié. Par défaut, il essaie de trouver un thème nommé `pelican-theme` dans le répertoire `OUTPUTDIR`.
    --advanced-warnings

    -e, --extra-path CHEMIN
    Ajoute un chemin supplémentaire pour la recherche de thèmes.

    DESCRIPTION

    Pelican est un générateur de site statique simple, rapide et extensible. Il prend du contenu écrit en Markdown ou reStructuredText, le traite et génère un site web statique complet prêt à être servi par n'importe quel serveur web.

    Le processus de construction est le suivant :

    • Pelican recherche des fichiers de contenu dans le répertoire d'entrée spécifié (`INPUTDIR`).
    • Il traite ces fichiers, en convertissant le contenu en HTML.
    • Il applique un thème pour générer les pages HTML finales, les flux de syndication et les fichiers nécessaires.
    • Tous les fichiers sont placés dans le répertoire de sortie spécifié (`OUTPUTDIR`).

    EXEMPLES

    Pour construire un site avec le contenu dans `~/MonSite/content` et le sortir dans `~/MonSite/output` :

    pelican ~/MonSite/content ~/MonSite/output

    Pour utiliser un thème spécifique nommé `mon_theme` situé dans le répertoire `~/MonSite/themes` :

    pelican -t mon_theme ~/MonSite/content ~/MonSite/output

    Pour utiliser un fichier de configuration personnalisé :

    pelican -c pelicanconf.py ~/MonSite/content ~/MonSite/output
