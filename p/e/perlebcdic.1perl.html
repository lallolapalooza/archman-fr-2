PERLEBCDIC(1perl) Guide de référence du programmeur Perl PERLEBCDIC(1perl)

NOM

perlebcdic - Considérations pour l'exécution de Perl sur des plateformes EBCDIC

DESCRIPTION

Une exploration de certains des problèmes rencontrés par les programmeurs Perl sur des ordinateurs basés sur EBCDIC.

Les parties de ce document qui sont encore incomplètes sont marquées par XXX.

Les premières versions de Perl fonctionnaient sur certaines machines EBCDIC, mais la dernière version connue qui fonctionnait sur EBCDIC était la v5.8.7, jusqu'à la v5.22, où le cœur de Perl fonctionne à nouveau sur z/OS. Théoriquement, cela pourrait fonctionner sur OS/400 ou BS2000 de Siemens (ou leurs successeurs), mais cela n'a pas été testé. Dans les versions v5.22 et v5.24, tous les modules trouvés sur CPAN mais distribués avec le cœur de Perl ne fonctionnent pas sur z/OS.

Si vous souhaitez utiliser Perl sur une machine EBCDIC non-z/OS, veuillez nous en informer sur https://github.com/Perl/perl5/issues.

Écrire du code Perl sur une plateforme EBCDIC n'est vraiment pas différent que d'écrire sur une plateforme "ASCII", mais avec des nombres sous-jacents différents, comme nous le verrons bientôt. Vous devrez en savoir un peu sur ces plateformes "ASCII" car la documentation est biaisée et utilisera fréquemment des exemples de nombres qui ne s'appliquent pas à EBCDIC. Il existe également très peu de modules CPAN qui sont écrits pour EBCDIC et qui ne fonctionnent pas sur ASCII ; au lieu de cela, la grande majorité des modules CPAN sont écrits pour ASCII, et certains peuvent fonctionner sur EBCDIC, tandis que quelques-uns ont été conçus pour fonctionner de manière portable sur les deux.

Si votre code utilise uniquement les 52 lettres A-Z et a-z, plus l'ESPACE, les chiffres 0-9, et les caractères de ponctuation utilisés par Perl, ainsi que quelques contrôles désignés par des séquences d'échappement comme "\n" et "\t", alors il n'y a rien de spécial à utiliser Perl, et votre code pourrait très bien fonctionner sur une machine ASCII sans modification.

Mais si vous écrivez du code qui utilise "\005" pour désigner une TAB ou "\xC1" pour désigner un "A", ou "\xDF" pour désigner un "ÿ" (petit "y" avec un tréma), alors votre code peut très bien fonctionner sur votre plateforme EBCDIC, mais pas sur une plateforme ASCII. C'est une bonne chose à faire si personne ne souhaite jamais exécuter votre code sur une plateforme ASCII ; mais le biais de ce document sera en faveur de l'écriture de code portable entre les systèmes EBCDIC et ASCII. Encore une fois, si chaque caractère qui vous importe est facilement saisissable depuis votre clavier, vous n'avez pas besoin de connaître l'ASCII, mais de nombreux claviers ne vous permettent pas facilement de saisir directement, par exemple, le caractère "\xDF", vous devez donc le spécifier indirectement, par exemple en utilisant la séquence d'échappement "\xDF". Dans ces cas, il est plus facile de connaître les jeux de caractères ASCII/Unicode. Si vous savez que le petit "ÿ" est "U+00FF", vous pouvez alors le spécifier comme "\N{U+FF}" et laisser l'ordinateur le traduire automatiquement en "\xDF" sur votre plateforme, et le laisser comme "\xFF" sur les plateformes ASCII. Ou vous pourriez le spécifier par son nom, "\N{LATIN SMALL LETTER Y WITH DIAERESIS" et ne pas avoir à connaître les nombres. Les deux méthodes fonctionnent, mais les deux nécessitent une familiarité avec Unicode.

ENSEMBLES DE CODES DE CARACTÈRES COMMUNES

ASCII

L'American Standard Code for Information Interchange (ASCII ou US-ASCII) est un ensemble d'entiers allant de 0 à 127 (décimal) qui ont des interprétations standardisées par les ordinateurs qui utilisent ASCII. Par exemple, 65 signifie la lettre "A". La plage 0..127 peut être couverte en réglant divers bits dans un chiffre binaire de 7 bits, d'où le nom de "ASCII 7 bits". ASCII a été décrit par le document ANSI X3.4-1986 de l'American National Standards Institute. Il a également été décrit par ISO 646:1991 (avec localisation pour les symboles de devise). L'ensemble ASCII complet est donné dans le tableau ci-dessous comme les 128 premiers éléments. Les langues qui peuvent être écrites adéquatement avec les caractères ASCII incluent l'anglais, le hawaïen, l'indonésien, le swahili et certaines langues amérindiennes.

La plupart des jeux de caractères non-EBCDIC sont des sur-ensembles d'ASCII. C'est-à-dire que les entiers 0-127 signifient ce que ASCII dit qu'ils signifient. Mais les entiers 128 et supérieurs sont spécifiques au jeu de caractères.

Beaucoup de ceux-ci tiennent entièrement en 8 bits, utilisant ASCII comme 0-127, tout en spécifiant ce que signifient 128-255, et n'utilisant rien au-dessus de 255. Ainsi, ce sont des jeux de caractères à un seul octet. Un important (puisque Unicode est un sur-ensemble de celui-ci) est le jeu de caractères ISO 8859-1.

ISO 8859

Les ISO 8859-$n sont une collection de jeux de codes de caractères de l'Organisation Internationale de Normalisation (ISO), chacun ajoutant des caractères à l'ensemble ASCII qui se trouvent généralement dans diverses langues, dont beaucoup sont basées sur l'alphabet romain ou latin. La plupart sont pour les langues européennes, mais il y en a aussi pour l'arabe, le grec, l'hébreu et le thaï. Il existe de bonnes références sur le web concernant tous ces jeux.

Latin 1 (ISO 8859-1)

Une extension particulière de 8 bits à ASCII qui inclut les caractères latins accentués grave et aigu. Les langues qui peuvent utiliser ISO 8859-1 incluent toutes les langues couvertes par ASCII ainsi que l'afrikaans, l'albanais, le basque, le catalan, le danois, le féroïen, le finnois, le norvégien, le portugais, l'espagnol et le suédois. Le néerlandais est couvert, bien qu'sans la ligature ij. Le français est également couvert, mais sans la ligature oe. L'allemand peut utiliser ISO 8859-1 mais doit le faire sans les guillemets allemands. Cet ensemble est basé sur les extensions de l'Europe occidentale à ASCII et est couramment rencontré dans le travail sur le World Wide Web. Dans la terminologie IBM d'identification des jeux de codes de caractères, ISO 8859-1 est également connu sous le nom de CCSID 819 (ou parfois 0819 ou même 00819).

EBCDIC

L'Extended Binary Coded Decimal Interchange Code fait référence à une grande collection de jeux de codes de caractères à un ou plusieurs octets qui sont très différents d'ASCII et d'ISO 8859-1, et qui sont tous légèrement différents les uns des autres ; ils s'exécutent généralement sur des ordinateurs centraux. Les codages EBCDIC dérivent des extensions d'octets de 8 bits des codages de cartes perforées Hollerith, qui sont bien antérieures à ASCII. La disposition sur les cartes était telle que les bits supérieurs étaient activés pour les caractères alphabétiques latins "[a-z]" et "[A-Z]", mais il y avait des lacunes dans chaque plage alphabétique latine, visibles dans le tableau ci-dessous. Ces lacunes peuvent causer des complications.

Certains jeux de codes de caractères EBCDIC d'IBM peuvent être connus sous des numéros d'identification de jeux de codes de caractères (numéros CCSID) ou des numéros de page de codes.

Perl peut être compilé sur des plateformes qui exécutent l'un des trois jeux de codes de caractères EBCDIC couramment utilisés, listés ci-dessous.

Les 13 caractères variables

Parmi les jeux de codes de caractères EBCDIC d'IBM, il y a 13 caractères qui sont souvent mappés à des valeurs entières différentes. Ces caractères sont connus sous le nom de 13 caractères "variables" et sont :

\ [ ] { } ^ ~ ! # | $ @ `

Lorsque Perl est compilé pour une plateforme, il examine tous ces caractères pour deviner quel jeu de caractères EBCDIC la plateforme utilise, et s'adapte en conséquence à cette plateforme. Si la plateforme utilise un jeu de caractères qui n'est pas l'un des trois que Perl connaît, Perl échouera à la compilation ou en choisira incorrectement et silencieusement un des trois.

Le caractère de saut de ligne (LF) est en fait un 14ème caractère variable, et Perl le vérifie également.

Jeux de codes EBCDIC reconnus par Perl

0037
Le jeu de codes de caractères 0037 est un mappage des caractères ASCII plus Latin-1 (c'est-à-dire ISO 8859-1) vers un ensemble EBCDIC. 0037 est utilisé dans les locales anglais nord-américaines sur le système d'exploitation OS/400 qui s'exécute sur les ordinateurs AS/400. CCSID 0037 diffère de ISO 8859-1 dans 236 endroits ; en d'autres termes, ils ne concordent que sur 20 valeurs de points de code.
1047
Le jeu de codes de caractères 1047 est également un mappage des caractères ASCII plus Latin-1 (c'est-à-dire ISO 8859-1) vers un ensemble EBCDIC. 1047 est utilisé sous Unix System Services pour OS/390 ou z/OS, et OpenEdition pour VM/ESA. CCSID 1047 diffère de CCSID 0037 dans huit endroits, et de ISO 8859-1 dans 236.
POSIX-BC
Ce jeu de codes de caractères est le plus proche des chaînes de caractères ASCII, mais il a encore des différences significatives. Ce jeu de codes de caractères est utilisé pour la compatibilité POSIX sur z/OS. CCSID 1114 diffère de CCSID 0037 en deux endroits, et de ISO 8859-1 en 238.

Points de code Unicode versus points de code EBCDIC

En terminologie Unicode, un point de code est le numéro attribué à un caractère : par exemple, en EBCDIC, le caractère « A » se voit généralement attribuer le numéro 193. En Unicode, le caractère « A » se voit attribuer le numéro 65. Tous les points de code en ASCII et Latin-1 (ISO 8859-1) ont la même signification en Unicode. Les trois ensembles de codes EBCDIC reconnus ont 256 points de code, et dans chaque ensemble de codes, les 256 points de code sont mappés à des points de code Latin1 équivalents. Évidemment, « A » sera mappé à « A », « B » => « B », « % » => « % », etc., pour tous les caractères imprimables en Latin1 et ces pages de code.

Il s'avère également qu'EBCDIC possède des équivalents presque précis pour les contrôles C0 ASCII/Latin1 et le contrôle DELETE. (Les contrôles C0 sont ceux dont les points de code ASCII sont 0..0x1F ; des choses comme TAB, ACK, BEL, etc.) Un mappage est établi entre ces contrôles ASCII/EBCDIC. Il n'existe pas de mappage aussi précis entre les contrôles C1 sur les plateformes ASCII et les contrôles EBCDIC restants. Ce qui a été fait, c'est de mapper ces contrôles, la plupart du temps arbitrairement, à certains caractères autrement non attribués dans l'autre jeu de caractères. La plupart d'entre eux sont d'ailleurs très rarement utilisés de nos jours en EBCDIC, et leurs noms ont été supprimés, sans grande plainte. Par exemple, le contrôle EBCDIC EO (Eight Ones) (composé de huit bits à un = 0xFF) est mappé au contrôle C1 APC (0x9F), et vous ne pouvez pas utiliser le nom « EO ».

Les contrôles EBCDIC fournissent trois caractères terminateurs de ligne possibles : CR (0x0D), LF (0x25), et NL (0x15). Sur les plateformes ASCII, les symboles « NL » et « LF » font référence au même caractère, mais en terminologie EBCDIC stricte, ce sont des caractères différents. Le NL EBCDIC est mappé au contrôle C1 appelé « NEL » (« Next Line » ; voici un cas où le mappage a beaucoup de sens, et n'est donc pas juste arbitraire). Sur certaines plateformes EBCDIC, ce NL ou NEL est le terminateur de ligne typique. C'est le cas de z/OS et BS2000. Sur ces plateformes, les compilateurs C échangent les points de code LF et NEL, de sorte que "\n" vaut 0x15, et fait référence à NL. Perl fait aussi cela ; vous pouvez le voir dans le tableau de code ci-dessous. Cela permet généralement aux choses de « fonctionner » sans même que vous ayez à savoir qu'il y a un échange.

Unicode et UTF

UTF signifie « Unicode Transformation Format ». UTF-8 est un encodage d'Unicode en une séquence de blocs d'octets de 8 bits, basé sur ASCII et Latin-1. La longueur d'une séquence requise pour représenter un point de code Unicode dépend du numéro ordinal de ce point de code, les nombres plus grands nécessitant plus d'octets. UTF-EBCDIC est similaire à UTF-8, mais basé sur EBCDIC. Ils sont suffisamment similaires que souvent, une utilisation informelle confondra les deux termes et utilisera « UTF-8 » pour désigner à la fois UTF-8 trouvé sur les plateformes ASCII et UTF-EBCDIC trouvé sur celles EBCDIC.

Vous pouvez rencontrer le terme de caractère ou point de code « invariant ». Cela signifie simplement que le caractère a la même valeur numérique et la même représentation lorsqu'il est encodé en UTF-8 (ou UTF-EBCDIC) que lorsqu'il ne l'est pas. (Notez qu'il s'agit d'un concept très différent de « Les 13 caractères variants » mentionnés ci-dessus. Une prose soignée utilisera le terme « invariant UTF-8 » plutôt que juste « invariant », mais le plus souvent vous verrez juste « invariant ».) Par exemple, la valeur ordinale de « A » est de 193 dans la plupart des pages de code EBCDIC, et est également de 193 lorsqu'elle est encodée en UTF-EBCDIC. Tous les points de code variants UTF-8 (ou UTF-EBCDIC) occupent au moins deux octets lorsqu'ils sont encodés en UTF-8 (ou UTF-EBCDIC) ; par définition, les points de code invariants UTF-8 (ou UTF-EBCDIC) ne prennent qu'un octet, qu'ils soient encodés en UTF-8 (ou UTF-EBCDIC) ou non. (Vous comprenez maintenant pourquoi les gens disent généralement « UTF-8 » lorsqu'ils veulent aussi dire « UTF-EBCDIC ». Pour le reste de ce document, nous serons également assez informels à ce sujet.) En UTF-8 ASCII, les points de code correspondant aux 128 plus petits numéros ordinaux (0 - 127 : les caractères ASCII) sont invariants. En UTF-EBCDIC, il y a 160 caractères invariants. (Si cela vous intéresse, les invariants EBCDIC sont les caractères qui ont des équivalents ASCII, plus ceux qui correspondent aux contrôles C1 (128 - 159 sur les plateformes ASCII).)

Une chaîne encodée en UTF-EBCDIC peut être plus longue (très rarement plus courte) qu'une chaîne encodée en UTF-8. Perl étend à la fois UTF-8 et UTF-EBCDIC de manière à pouvoir encoder des points de code supérieurs au maximum Unicode de U+10FFFF. Les deux extensions sont construites pour permettre l'encodage de tout point de code qui tient dans un mot de 64 bits.

UTF-EBCDIC est défini par le rapport technique Unicode n° 16 https://www.unicode.org/reports/tr16 (souvent appelé simplement TR16). Il est défini sur la base du CCSID 1047, sans tenir compte des différences avec d'autres pages de code. Cela permet un échange facile de texte entre ordinateurs exécutant différentes pages de code, mais le rend inutilisable, sans adaptation, pour Perl sur ces autres pages de code.

La raison de cette inutilisabilité est qu'une hypothèse fondamentale de Perl est que les caractères qui l'intéressent pour l'analyse syntaxique et l'analyse lexicale sont les mêmes que le texte soit encodé en UTF-8 ou non. Par exemple, Perl s'attend à ce que le caractère « [ » ait la même représentation, qu'il soit dans une chaîne (ou un code de programme) encodée en UTF-8 ou non. Pour garantir cela, Perl adapte UTF-EBCDIC à la page de code particulière afin que tous les caractères qu'il s'attend à être invariants UTF-8 soient en fait invariants UTF-8. Cela signifie que le texte généré sur un ordinateur exécutant une version d'UTF-EBCDIC de Perl doit être traduit pour être intelligible à un ordinateur exécutant une autre version.

TR16 implique une méthode pour étendre UTF-EBCDIC afin d'encoder des points jusqu'à "2 ** 31 - 1". Perl utilise cette méthode pour les points de code jusqu'à "2 ** 30 - 1", mais utilise une méthode incompatible pour les points plus grands, afin de pouvoir gérer des points de code beaucoup plus grands qu'auparavant.

Utilisation de Encode

À partir de Perl 5.8, vous pouvez utiliser le module standard Encode pour traduire des points de code EBCDIC en Latin-1. Encode connaît plus de jeux de caractères EBCDIC que Perl ne peut actuellement être compilé pour les exécuter.

use Encode 'from_to';
my %ebcdic = ( 176 => 'cp37', 95 => 'cp1047', 106 => 'posix-bc' );
# $x est en points de code EBCDIC
from_to($x, $ebcdic{ord '^'}, 'latin1');
# $x est en points de code ISO 8859-1

et des points de code Latin-1 vers des points de code EBCDIC

use Encode 'from_to';
my %ebcdic = ( 176 => 'cp37', 95 => 'cp1047', 106 => 'posix-bc' );
# $x est en points de code ISO 8859-1
from_to($x, 'latin1', $ebcdic{ord '^'});
# $x est en points de code EBCDIC

Pour les opérations d'E/S, il est suggéré d'utiliser les fonctionnalités d'auto-traduction de PerlIO, voir perluniintro.

Depuis la version 5.8, Perl utilise la bibliothèque d'E/S PerlIO. Cela vous permet d'utiliser différents encodages par canal d'E/S. Par exemple, vous pouvez utiliser

use Encode;
open($f, ">:encoding(ascii)", "test.ascii");
print $f "Hello World!\n";
open($f, ">:encoding(cp37)", "test.ebcdic");
print $f "Hello World!\n";
open($f, ">:encoding(latin1)", "test.latin1");
print $f "Hello World!\n";
open($f, ">:encoding(utf8)", "test.utf8");
print $f "Hello World!\n";

pour obtenir quatre fichiers contenant « Hello World!\n » en ASCII, CP 0037 EBCDIC, ISO 8859-1 (Latin-1) (dans cet exemple, identique à ASCII car seuls des caractères ASCII ont été imprimés), et UTF-EBCDIC (dans cet exemple, identique à EBCDIC normal car seuls des caractères qui ne diffèrent pas entre EBCDIC et UTF-EBCDIC ont été imprimés). Voir la documentation de Encode::PerlIO pour plus de détails.

Comme la couche PerlIO utilise des E/S brutes (octets) en interne, tout cela ignore complètement des choses comme le type de votre système de fichiers (ASCII ou EBCDIC).

IDENTIFIER LES JEUX DE CODES DE CARACTERES

Il est possible de déterminer dans quel jeu de caractères vous opérez. Mais il faut d'abord être vraiment, vraiment sûr que vous avez besoin de le faire. Votre code sera plus simple et probablement tout aussi portable si vous n'avez pas à tester le jeu de caractères et à faire des choses différentes, selon le cas. Il n'y a en fait que très peu de circonstances où il n'est pas facile d'écrire un code en ligne droite portable vers tous les jeux de caractères. Voir "Unicode et EBCDIC" dans perluniintro pour savoir comment spécifier les caractères de manière portable.

Mais il y a certains cas où vous pourriez vouloir savoir sous quel jeu de caractères vous fonctionnez. Un exemple possible est le tri dans des boucles internes où les performances sont critiques.

Pour déterminer si vous fonctionnez sous ASCII ou EBCDIC, vous pouvez utiliser la valeur de retour de ord() ou chr() pour tester une ou plusieurs valeurs de caractères. Par exemple :

$est_ascii  = "A" eq chr(65);
$est_ebcdic = "A" eq chr(193);
$est_ascii  = ord("A") == 65;
$est_ebcdic = ord("A") == 193;

Il y a encore moins besoin de distinguer entre les pages de codes EBCDIC, mais pour le faire, essayez de regarder un ou plusieurs des caractères qui diffèrent entre eux.

$est_ascii           = ord('[') == 91;
$est_ebcdic_37       = ord('[') == 186;
$est_ebcdic_1047     = ord('[') == 173;
$est_ebcdic_POSIX_BC = ord('[') == 187;

Cependant, il serait imprudent d'écrire des tests tels que :

$est_ascii = "\r" ne chr(13);  #  FAUX
$est_ascii = "\n" ne chr(10);  #  DECONSEILLE

Évidemment, le premier de ces tests ne parviendra pas à distinguer la plupart des plateformes ASCII d'une plateforme EBCDIC CCSID 0037, 1047 ou POSIX-BC, car ""\r" eq chr(13)" sous tous ces jeux de caractères codés. Mais notez aussi que parce que "\n" est chr(13) et "\r" est chr(10) sur les anciens Macintosh (qui sont des plateformes ASCII), le second test $est_ascii y entraînera des problèmes.

Pour déterminer si perl a été construit sous une page de codes EBCDIC ou non, vous pouvez utiliser le module Config comme suit :

use Config;
$est_ebcdic = $Config{'ebcdic'} eq 'define';

DIFFERENCES OPERATEUR

L'opérateur de plage ".." traite certaines plages de caractères avec soin sur les plateformes EBCDIC. Par exemple, le tableau suivant aura vingt-six éléments sur une plateforme EBCDIC ou sur une plateforme ASCII :

@alphabet = ('A'..'Z');   #  $#alphabet == 25

Les opérateurs bit à bit tels que & ^ | peuvent renvoyer des résultats différents lorsqu'ils opèrent sur des données de chaîne ou de caractère dans un programme Perl s'exécutant sur une plateforme EBCDIC par rapport à une plateforme ASCII. Voici un exemple adapté de celui de perlop :

# Exemples basés sur EBCDIC
print "j p \n" ^ " a h";                      # imprime "JAPH\n"
print "JA" | "  ph\n";                        # imprime "japh\n"
print "JAPH\nJunk" & "\277\277\277\277\277";  # imprime "japh\n";
print 'p N$' ^ " E<H\n";                      # imprime "Perl\n";

DIFFERENCES DE FONCTION

chr()
chr() doit recevoir un argument numérique de code EBCDIC pour renvoyer un caractère désiré sur une plateforme EBCDIC. Par exemple : 
$LETTRE_CAPITALE_A = chr(193);
ord()
ord() renverra des valeurs numériques de code EBCDIC sur une plateforme EBCDIC. Par exemple : 
$LE_NOMBRE_193 = ord("A");
pack()
Les gabarits "c" et "C" pour pack() dépendent de l'encodage du jeu de caractères. Exemples d'utilisation sur EBCDIC : 
$foo = pack("CCCC",193,194,195,196);
# $foo eq "ABCD"
$foo = pack("C4",193,194,195,196);
# même chose
$foo = pack("ccxxcc",193,194,195,196);
# $foo eq "AB\0\0CD"

Le gabarit "U" a été porté pour signifier "Unicode" sur toutes les plateformes afin que

pack("U", 65) eq 'A'

soit vrai sur toutes les plateformes. Si vous voulez les points de code natifs pour les 256 premiers octets, utilisez le gabarit "W". Cela signifie que les équivalences

pack("W", ord($caractere)) eq $caractere
unpack("W", $caractere) == ord $caractere

seront respectées.

print()
Il faut faire attention aux scalaires et aux chaînes passées à print qui contiennent des encodages ASCII. Un endroit courant où cela se produit est la sortie de l'en-tête de type MIME pour l'écriture de scripts CGI. Par exemple, de nombreux guides de programmation Perl recommandent quelque chose de similaire à : 
print "Content-type:\ttext/html\015\012\015\012";
# cela peut être faux sur EBCDIC

Vous pouvez écrire à la place :

print "Content-type:\ttext/html\r\n\r\n"; # OK pour DGW et al.

et que cela fonctionne de manière portable.

C'est parce que la traduction d'EBCDIC en ASCII est effectuée par le serveur Web dans ce cas. Consultez la documentation de votre serveur Web pour plus de détails.

printf()
Les formats qui peuvent convertir des caractères en nombres et vice versa différeront de leurs homologues ASCII lorsqu'ils seront exécutés sur une plateforme EBCDIC. Exemples : 
printf("%c%c%c",193,194,195);  # imprime ABC
sort()
Les résultats de tri EBCDIC peuvent différer des résultats de tri ASCII, en particulier pour les chaînes de caractères mixtes. Ceci est discuté plus en détail ci-dessous.
sprintf()
Voir la discussion sur "printf()" ci-dessus. Un exemple d'utilisation de sprintf serait : 
$LETTRE_CAPITALE_A = sprintf("%c",193);
unpack()
Voir la discussion sur "pack()" ci-dessus.

Notez qu'il est possible d'écrire du code portable pour ceux-ci en spécifiant des choses en nombres Unicode, et en utilisant une fonction de conversion :

printf("%c",utf8::unicode_to_native(65));  # imprime A sur toutes les
                                           # plateformes
print utf8::native_to_unicode(ord("A"));   # De même, imprime 65

Voir "Unicode et EBCDIC" dans perluniintro et "CONVERSIONS" pour d'autres options.

DIFFERENCES D'EXPRESSION REGULIERE

Vous pouvez écrire vos expressions régulières comme quelqu'un sur une plateforme ASCII le ferait. Mais gardez à l'esprit que l'utilisation de la notation octale ou hexadécimale pour spécifier un point de code particulier vous donnera le caractère auquel la page de code EBCDIC le mappe nativement. (Ceci est également vrai pour toutes les chaînes entre guillemets doubles.) Si vous voulez écrire de manière portable, utilisez simplement la notation "\N{U+...}" partout où vous auriez utilisé "\x{...}", et n'utilisez pas du tout la notation octale.

À partir de Perl v5.22, cela s'applique aux plages dans les classes de caractères entre crochets. Si vous dites, par exemple, "qr/[\N{U+20}-\N{U+7F}]/", cela signifie les caractères "\N{U+20}", "\N{U+21}", ..., "\N{U+7F}". Cette plage contient tous les caractères imprimables que le jeu de caractères ASCII contient.

Avant la version 5.22, vous ne pouviez pas spécifier de plages de manière portable, sauf (à partir de Perl v5.5.3) tous les sous-ensembles des plages "[A-Z]" et "[a-z]" sont spécialement codés pour ne pas capturer de caractères d'espacement. Par exemple, des caractères comme "ô" ("o AVEC CIRCONFLEXE") qui se situent entre "I" et "J" ne seraient pas correspondus par la plage d'expression régulière "/[H-K]/". Mais si l'un des points finaux de la plage est explicitement numérique (et aucun n'est spécifié par "\N{U+...}"), les caractères d'espacement sont capturés :

/[\x89-\x91]/

correspondra à "\x8e", même si "\x89" est "i" et "\x91 " est "j", et "\x8e" est un caractère d'espacement, du point de vue alphabétique.

Une autre construction à surveiller est l'utilisation inappropriée des constantes hexadécimales (sauf si vous utilisez "\N{U+...}") ou octales dans les expressions régulières. Considérez l'ensemble de subs suivant :

sub is_c0 {
    my $char = substr(shift,0,1);
    $char =~ /[\000-\037]/;
}
sub is_print_ascii {
    my $char = substr(shift,0,1);
    $char =~ /[\040-\176]/;
}
sub is_delete {
    my $char = substr(shift,0,1);
    $char eq "\177";
}
sub is_c1 {
    my $char = substr(shift,0,1);
    $char =~ /[\200-\237]/;
}
sub is_latin_1 {    # Mais pas ASCII ; pas C1
    my $char = substr(shift,0,1);
    $char =~ /[\240-\377]/;
}

Ceux-ci ne sont valides que sur les plateformes ASCII. À partir de Perl v5.22, le simple fait de changer les constantes octales en valeurs équivalentes "\N{U+...}" les rend portables :

sub is_c0 {
    my $char = substr(shift,0,1);
    $char =~ /[\N{U+00}-\N{U+1F}]/;
}
sub is_print_ascii {
    my $char = substr(shift,0,1);
    $char =~ /[\N{U+20}-\N{U+7E}]/;
}
sub is_delete {
    my $char = substr(shift,0,1);
    $char eq "\N{U+7F}";
}
sub is_c1 {
    my $char = substr(shift,0,1);
    $char =~ /[\N{U+80}-\N{U+9F}]/;
}
sub is_latin_1 {    # Mais pas ASCII ; pas C1
    my $char = substr(shift,0,1);
    $char =~ /[\N{U+A0}-\N{U+FF}]/;
}

Et voici quelques autres façons portables de les écrire :

SOCKETS

La plupart des programmations de sockets supposent des encodages de caractères ASCII en ordre d'octets réseau. Les exceptions peuvent inclure l'écriture de scripts CGI sous un serveur Web hôte où le serveur peut prendre en charge la traduction pour vous. La plupart des serveurs Web hôtes convertissent les données EBCDIC en ISO-8859-1 ou Unicode à la sortie.

TRI

Une grande différence entre les jeux de caractères basés sur ASCII et ceux basés sur EBCDIC réside dans les positions relatives des caractères lors du tri dans l'ordre natif. Les plus préoccupants sont les lettres majuscules et minuscules, les chiffres et le trait de soulignement ("_"). Sur les plateformes ASCII, l'ordre de tri natif place les chiffres avant les lettres majuscules, qui viennent avant le trait de soulignement, qui vient avant les lettres minuscules. Sur EBCDIC, le trait de soulignement vient en premier, puis les lettres minuscules, puis les majuscules, et les chiffres en dernier. S'il est trié sur une plateforme basée sur ASCII, l'abréviation de deux lettres pour un médecin vient avant l'abréviation de deux lettres pour conduire ; c'est-à-dire :

@sorted = sort(qw(Dr. dr.));  # @sorted contient ('Dr.','dr.') sur ASCII,
                                 # mais ('dr.','Dr.') sur EBCDIC

La propriété des lettres minuscules avant les majuscules en EBCDIC se retrouve même dans les pages EBCDIC Latin 1 telles que 0037 et 1047. Un exemple serait que « Ë » ("E AVEC DIACRITIQUE", 203) vient avant « ë » ("e AVEC DIACRITIQUE", 235) sur une plateforme ASCII, mais ce dernier (83) vient avant le premier (115) sur une plateforme EBCDIC. (Les lecteurs avertis noteront que la version majuscule de « ß » "LETTRE MINUSCULE ESPRIT S" est simplement « SS » et que les versions majuscules de « ÿ » (petit "y AVEC DIACRITIQUE") et « µ » ("SIGNE MICRO") ne sont pas dans la plage 0..255 mais sont dans Unicode, dans un Perl activé pour Unicode).

L'ordre de tri provoquera des différences entre les résultats obtenus sur les plateformes ASCII et les plateformes EBCDIC. Voici quelques suggestions sur la manière de traiter ces différences.

Ignorer les différences de tri ASCII vs. EBCDIC

C'est la stratégie la moins coûteuse en termes de calcul. Elle peut nécessiter une certaine éducation des utilisateurs.

Utiliser une fonction d'aide au tri

C'est la stratégie la plus générale, mais aussi la plus coûteuse en calcul. Choisissez l'un ou l'autre jeu de caractères et transformez vers celui-ci pour chaque comparaison de tri. Voici un exemple complet qui transforme vers l'ordre de tri ASCII :

sub native_to_uni($) {
   my $string = shift;
   # Gagne du temps sur une plateforme ASCII
   return $string if ord 'A' ==  65;
   my $output = "";
   for my $i (0 .. length($string) - 1) {
       $output
          .= chr(utf8::native_to_unicode(ord(substr($string, $i, 1))));
   }
   # Préserve le caractère utf8 de l'entrée sur la sortie, même si elle n'avait pas
   # besoin d'être en utf8
   utf8::upgrade($output) if utf8::is_utf8($string);
   return $output;
}
sub ascii_order {   # Aide au tri
   return native_to_uni($a) cmp native_to_uni($b);
}
sort ascii_order @list;

METTRE EN CASSE UNIQUE puis trier les données (pour les non-chiffres, non-underscore)

Si vous ne vous souciez pas de la position des chiffres et du trait de soulignement dans le tri, vous pouvez faire quelque chose comme ceci

sub case_insensitive_order {   # Aide au tri
   return lc($a) cmp lc($b)
}
sort case_insensitive_order @list;

Si les performances sont un problème, et que vous ne vous souciez pas de savoir si la sortie est dans la même casse que l'entrée, utilisez "tr///" pour transformer dans la casse la plus employée dans les données. Si les données sont principalement en MAJUSCULES non Latin1, appliquez alors "tr/[a-z]/[A-Z]/", puis sort(). Si les données sont principalement en minuscules non Latin1, appliquez alors "tr/[A-Z]/[a-z]/" avant de trier. Si les données sont principalement en MAJUSCULES et incluent des caractères Latin-1, alors appliquez :

tr/[a-z]/[A-Z]/;
tr/[àáâãäåæçèéêëìíîïðñòóôõöøùúûüýþ]/[ÀÁÂÃÄÅÆÇÈÉÊËÌÍÎÏÐÑÒÓÔÕÖØÙÚÛÜÝÞ/;
s/ß/SS/g;

puis sort(). Si vous avez le choix, il est préférable de mettre en minuscules pour éviter les problèmes des deux caractères Latin-1 dont la casse majuscule est en dehors de Latin-1 : « ÿ » (petit "y AVEC DIACRITIQUE") et « µ » ("SIGNE MICRO"). Si vous devez mettre en majuscules, vous pouvez le faire ; avec un Perl activé pour Unicode, faites :

tr/ÿ/\x{178}/;
tr/µ/\x{39C}/;

Effectuer le tri sur un seul type de plateforme

Cette stratégie peut employer une connexion réseau. En tant que telle, elle serait coûteuse en calcul.

FORMATS DE TRANSFORMATION

Il existe une variété de façons de transformer des données avec un mappage intra-jeu de caractères qui servent à diverses fins. Le tri a été discuté dans la section précédente et quelques-unes des autres techniques de mappage les plus populaires sont discutées ensuite.

Décodage et encodage d'URL

Notez que certaines URL contiennent des points de code hexadécimaux ASCII pour tenter de surmonter les problèmes de caractères ou de limitations de protocole. Par exemple, le caractère tilde ne se trouve pas sur tous les claviers, d'où une URL de la forme :

http://www.pvhp.com/~pvhp/

peut également être exprimée par l'une des formes suivantes :

http://www.pvhp.com/%7Epvhp/
http://www.pvhp.com/%7epvhp/

où 7E est le point de code ASCII hexadécimal pour « ~ ». Voici un exemple de décodage d'une telle URL dans n'importe quelle page de code EBCDIC :

$url = 'http://www.pvhp.com/%7Epvhp/';
$url =~ s/%([0-9a-fA-F]{2})/
          pack("c",utf8::unicode_to_native(hex($1)))/xge;

Inversement, voici une solution partielle pour la tâche d'encodage d'une telle URL dans n'importe quelle page de code EBCDIC :

$url = 'http://www.pvhp.com/~pvhp/';
# L'expression régulière suivante n'aborde pas les
# mappages pour : ('.' => '%2E', '/' => '%2F', ':' => '%3A')
$url =~ s/([\t "#%&\(\),;<=>\?\@\[\\\]^`{|}~])/
           sprintf("%%%02X",utf8::native_to_unicode(ord($1)))/xge;

où une solution plus complète diviserait l'URL en composants et appliquerait une substitution complète s/// uniquement aux parties appropriées.

Encodage et décodage Quoted-Printable

Sur les plateformes encodées en ASCII, il est possible de supprimer les caractères en dehors de l'ensemble imprimable en utilisant :

# Cet encodeur QP fonctionne sur ASCII uniquement
$qp_string =~ s/([=\x00-\x1F\x80-\xFF])/
                sprintf("=%02X",ord($1))/xge;

À partir de la version Perl v5.22, cela peut être facilement modifié pour fonctionner de manière portable sur les plateformes ASCII et EBCDIC.

# Cet encodeur QP fonctionne sur ASCII et EBCDIC
$qp_string =~ s/([=\N{U+00}-\N{U+1F}\N{U+80}-\N{U+FF}])/
                sprintf("=%02X",ord($1))/xge;

Pour les versions antérieures de Perl, un encodeur QP qui fonctionne sur les plateformes ASCII et EBCDIC ressemblerait à ceci :

$delete = utf8::unicode_to_native(ord("\x7F"));
$q
p_string =~ s/([^[:print:]$delete])/ sprintf("=%02X",utf8::native_to_unicode(ord($1)))/xage;

(bien que dans le code de production, les substitutions puissent être effectuées dans la branche EBCDIC avec l'appel de fonction et séparément dans la branche ASCII sans le coût de la carte d'identité ; dans Perl v5.22, la carte d'identité est optimisée, donc il n'y a pas de coût, mais l'alternative ci-dessus est plus simple et est également disponible en v5.22).

De telles chaînes QP peuvent être décodées avec :

# Ce décodeur QP est limité à l'ASCII uniquement
$string =~ s/=([[:xdigit:][[:xdigit:])/chr hex $1/ge;
$string =~ s/=[\n\r]+$//;

Alors qu'un décodeur QP qui fonctionne sur les plateformes ASCII et EBCDIC ressemblerait à ceci :

$string =~ s/=([[:xdigit:][:xdigit:]])/
                            chr utf8::native_to_unicode(hex $1)/xge;
$string =~ s/=[\n\r]+$//;

Chiffres de César

La pratique de décaler un alphabet d'un ou plusieurs caractères pour l'encipherment remonte à des milliers d'années et a été explicitement détaillée par Gaius Julius Caesar dans son texte sur la Guerre des Gaules. Un seul décalage d'alphabet est parfois appelé une rotation et le montant du décalage est donné par un nombre $n après la chaîne 'rot' ou "rot$n". Rot0 et rot26 désigneraient des cartes d'identité sur la version anglaise à 26 lettres de l'alphabet latin. Rot13 a la propriété intéressante que les invocations séquentielles alternées sont des cartes d'identité (ainsi rot13 est son propre inverse non trivial dans le groupe des 26 rotations d'alphabet). Par conséquent, ce qui suit est un encodeur et décodeur rot13 qui fonctionnera sur les plateformes ASCII et EBCDIC :

#!/usr/local/bin/perl
while(<>){
    tr/n-za-mN-ZA-M/a-zA-Z/;
    print;
}

Sous forme de ligne unique :

perl -ne 'tr/n-za-mN-ZA-M/a-zA-Z/;print'

perl

DESCRIPTION

perl est l'interpréteur du langage Perl. Le script d'initialisation perl est exécuté à chaque fois que Perl est lancé. Ce script d'initialisation lit et exécute le code contenu dans le fichier $Config{PERLINIT}, si ce fichier existe. Le nom de ce fichier par défaut est perl.init.

$Config{PERLINIT}

$Config{ENCODE_LIB}
Répertoire contenant la bibliothèque Encode.

Pour exécuter un script Perl en utilisant la locale EBCDIC, lancez simplement l'interpréteur perl : 

perl mon_script.pl

Le script mon_script.pl sera exécuté dans un environnement EBCDIC.

VOIR AUSSI

perlrun(1), perlvar(1), Encode(3pm), Encode::EBCDIC(3pm).

REFERENCES

Aucune.

HISTORIQUE

Ce script a été créé pour faciliter l'utilisation de Perl dans des environnements où EBCDIC est la locale par défaut.
