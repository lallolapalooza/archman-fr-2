LA BIBLIOTHEQUE DE MODULES PERL

De nombreux modules sont inclus dans la distribution Perl. Ceux-ci sont décrits ci-dessous, et tous se terminent par .pm. Vous pourriez découvrir des fichiers de bibliothèque compilés (se terminant généralement par .so) ou de petits morceaux de modules à charger automatiquement (se terminant par .al) ; ceux-ci ont été générés automatiquement par le processus d'installation. Vous pourriez également découvrir des fichiers dans le répertoire de la bibliothèque qui se terminent par .pl ou .ph. Ce sont d'anciennes bibliothèques fournies pour que les anciens programmes qui les utilisent continuent de fonctionner. Les fichiers .pl seront tous éventuellement convertis en modules standards, et les fichiers .ph créés par h2ph deviendront probablement des modules d'extension créés par h2xs. (Certaines valeurs .ph peuvent déjà être disponibles via les modules POSIX, Errno ou Fcntl.) Le fichier pl2pm de la distribution peut aider à votre conversion, mais ce n'est qu'un processus mécanique et donc loin d'être infaillible.

Modules pragmatiques

Ils fonctionnent un peu comme des directives de compilation (pragmata) dans le sens où ils ont tendance à affecter la compilation de votre programme, et donc ne fonctionneront généralement bien que lorsqu'ils sont utilisés dans un "use" ou un "no". La plupart d'entre eux sont limités à la portée lexicale, de sorte qu'un BLOC interne peut les contrecarrer en disant :

no integer;
no strict 'refs';
no warnings;

ce qui dure jusqu'à la fin de ce BLOC.

Certains pragmas sont à portée lexicale - généralement ceux qui affectent la variable d'indices $^H. D'autres affectent plutôt le paquet courant, comme "use vars" et "use subs", qui vous permettent de prédéclarer une variable ou une sous-routine dans un fichier particulier plutôt que juste dans un bloc. De telles déclarations sont effectives pour l'ensemble du fichier pour lequel elles ont été déclarées. Vous ne pouvez pas les annuler avec "no vars" ou "no subs".

(Le -T est ici pour empêcher @INC d'être rempli par "PERL5LIB", "PERLLIB", et "PERL_USE_UNSAFE_INC".) Ils devraient tous avoir leur propre documentation installée et accessible via votre commande man(1) système. Si vous n'avez pas de programme find, vous pouvez utiliser le programme Perl find2perl à la place, qui génère du code Perl en sortie que vous pouvez exécuter avec perl. Si vous avez un programme man mais qu'il ne trouve pas vos modules, vous devrez corriger votre manpath. Voir perl pour les détails. Si vous n'avez pas de commande man système, vous pourriez essayer le programme perldoc.

Notez également que la commande "perldoc perllocal" vous donne une liste (éventuellement incomplète) des modules qui ont été supplémentaires installés sur votre système. (Le fichier perllocal.pod est mis à jour par le processus d'installation standard de MakeMaker.)

Modules d'extension

Les modules d'extension sont écrits en C (ou un mélange de Perl et de C). Ils sont généralement chargés dynamiquement dans Perl si et quand vous en avez besoin, mais peuvent également être liés statiquement. Les modules d'extension pris en charge incluent Socket, Fcntl et POSIX.

De nombreux modules d'extension C populaires ne sont pas livrés groupés (du moins, pas complètement) en raison de leur taille, de leur volatilité, ou simplement du manque de temps pour des tests et une configuration adéquats sur la multitude de plateformes pour lesquelles Perl a été testé en version bêta. Nous vous encourageons à les rechercher sur CPAN (décrit ci-dessous), ou en utilisant des moteurs de recherche comme Google ou DuckDuckGo.

CPAN

CPAN signifie Comprehensive Perl Archive Network ; c'est un dépôt mondialement répliqué de matériel Perl, y compris la documentation, des guides de style, des astuces et des pièges, des ports alternatifs vers des systèmes non Unix et des distributions binaires occasionnelles pour ceux-ci. Des moteurs de recherche pour CPAN sont disponibles sur https://www.cpan.org/

Le plus important est que CPAN comprend environ un millier de modules non groupés, dont certains nécessitent un compilateur C pour être compilés. Les principales catégories de modules sont :

  • Interfaces de bases de données
  • Interfaces utilisateur
  • Interfaces vers / Émulations d'autres langages de programmation
  • Noms de fichiers, systèmes de fichiers et verrouillage de fichiers (voir aussi Fichiershandles)
  • Traitement de chaînes, traitement de texte linguistique, analyse et recherche
  • Traitement des options, arguments, paramètres et fichiers de configuration
  • Internationalisation et localisation

Modules : Création, Utilisation, et Abus

(La section suivante est empruntée directement au fichier de modules de Tim Bunce, disponible sur votre site CPAN le plus proche.)

Perl implémente une classe à l'aide d'un package, mais la présence d'un package n'implique pas la présence d'une classe. Un package est juste un espace de noms. Une classe est un package qui fournit des sous-programmes qui peuvent être utilisés comme méthodes. Une méthode est juste un sous-programme qui attend, comme premier argument, soit le nom d'un package (pour "statique"

quot; méthodes), ou une référence à quelque chose (pour les méthodes "virtuelles").

Un module est un fichier qui (par convention) fournit une classe du même nom (sans le .pm), plus une méthode d'importation dans cette classe qui peut être appelée pour récupérer les symboles exportés. Ce module peut implémenter certaines de ses méthodes en chargeant des objets dynamiques C ou C++, mais cela devrait être totalement transparent pour l'utilisateur du module. De même, le module pourrait configurer une fonction AUTOLOAD pour charger les définitions de sous-routines à la demande, mais c'est aussi transparent. Seul le fichier .pm doit exister. Voir perlsub, perlobj, et AutoLoader pour les détails sur le mécanisme AUTOLOAD.

Directives pour la création de modules

  • Des modules similaires existent-ils déjà sous une forme ou une autre ?

    Si oui, veuillez essayer de réutiliser les modules existants, soit en totalité, soit en héritant de fonctionnalités utiles dans une nouvelle classe. Si cela n'est pas pratique, essayez de vous réunir avec les auteurs des modules pour travailler à l'extension ou à l'amélioration des fonctionnalités des modules existants. Un exemple parfait est la pléthore de packages perl4 pour traiter les options de ligne de commande.

    Si vous écrivez un module pour étendre un ensemble de modules déjà existant, veuillez coordonner avec l'auteur du package. Il est utile de suivre le même schéma de nommage et le même schéma d'interaction de module que l'auteur d'origine.

  • Essayez de concevoir le nouveau module pour qu'il soit facile à étendre et à réutiliser.

    Essayez de faire "use warnings;" (ou "use warnings qw(...);"). N'oubliez pas que vous pouvez ajouter "no warnings qw(...);" à des blocs de code individuels qui nécessitent moins d'avertissements.

    Utilisez des références bénies. Utilisez la forme à deux arguments de bless pour bénir dans le nom de classe donné comme premier paramètre du constructeur, par exemple :

    sub new {
    my $class = shift;
    return bless {}, $class;
}

    ou même ceci si vous souhaitez qu'il soit utilisé comme méthode statique ou virtuelle.

    sub new {
    my $self  = shift;
    my $class = ref($self) || $self;
    return bless {}, $class;
}

    Passez des tableaux sous forme de références afin que des paramètres supplémentaires puissent être ajoutés ultérieurement (c'est aussi plus rapide). Convertissez les fonctions en méthodes le cas échéant. Divisez les méthodes volumineuses en méthodes plus petites et plus flexibles. Héritez des méthodes d'autres modules si cela est approprié.

    Évitez les tests de nom de classe tels que : "die "Invalid" unless ref $ref eq 'FOO'". En général, vous pouvez supprimer la partie "eq 'FOO'" sans aucun problème. Laissez les objets s'en charger ! En général, évitez autant que possible les noms de classe codés en dur.

    Évitez "$r->Class::func()" lorsque l'utilisation de "@ISA=qw(... Class ...)" et "$r->func()" fonctionnerait.

    Utilisez autosplit afin que les fonctions peu utilisées ou nouvellement ajoutées ne soient pas un fardeau pour les programmes qui ne les utilisent pas. Ajoutez des fonctions de test au module après __END__ soit en utilisant AutoSplit, soit en disant :

    eval join('',<main::DATA>) || die $@ unless caller();

    Votre module passe-t-il le test de la 'sous-classe vide' ? Si vous dites "@SUBCLASS::ISA = qw(YOURCLASS);", vos applications devraient pouvoir utiliser SUBCLASS de la même manière que YOURCLASS. Par exemple, votre application fonctionne-t-elle toujours si vous modifiez : "$obj = YOURCLASS->new();" en : "$obj = SUBCLASS->new();" ?

    Évitez de conserver toute information d'état dans vos packages. Cela rend difficile l'utilisation de votre package par plusieurs autres packages. Conservez les informations d'état dans les objets.

    Utilisez toujours -w.

    Essayez de faire "use strict;" (ou "use strict qw(...);"). N'oubliez pas que vous pouvez ajouter "no strict qw(...);" à des blocs de code individuels qui nécessitent moins de rigueur.

    Utilisez toujours -w.

    Suivez les directives de perlstyle.

    Utilisez toujours -w.

  • Quelques directives de style simples

    Le manuel perlstyle fourni avec Perl contient de nombreux points utiles.

    Le style de codage est une question de goût personnel. Beaucoup de personnes font évoluer leur style sur plusieurs années à mesure qu'elles apprennent ce qui les aide à écrire et à maintenir un bon code. Voici un ensemble de suggestions diverses qui semblent être largement utilisées par les développeurs expérimentés :

    Utilisez des traits d'union pour séparer les mots. Il est généralement plus facile de lire $var_names_like_this que $VarNamesLikeThis, en particulier pour les non-natifs de l'anglais. C'est aussi une règle simple qui fonctionne cohéremment avec VAR_NAMES_LIKE_THIS.

    Les noms de package/module sont une exception à cette règle. Perl réserve informellement les noms de module en minuscules pour les modules de type 'pragma' comme integer et strict. Les autres modules commencent normalement par une majuscule et utilisent des casse mixtes sans traits d'union (doivent être courts et portables).

    Vous pourriez trouver utile d'utiliser la casse pour indiquer la portée ou la nature d'une variable. Par exemple :

    $ALL_CAPS_HERE    constantes uniquement (attention aux conflits avec les variables Perl)
$Some_Caps_Here  global/statique à l'échelle du package
$no_caps_here    variables my() ou local() de portée fonctionnelle

    Les noms de fonctions et de méthodes semblent fonctionner au mieux en minuscules. Par exemple, "$obj->as_string()".

    Vous pouvez utiliser un trait d'union initial pour indiquer qu'une variable ou une fonction ne doit pas être utilisée en dehors du package qui l'a définie.

  • Sélectionnez ce qu'il faut exporter.

    N'exportez PAS les noms de méthodes !

    N'exportez RIEN d'autre par défaut sans une bonne raison !

    Les exportations polluent l'espace de noms de l'utilisateur du module. Si vous devez exporter, essayez d'utiliser @EXPORT_OK de préférence à @EXPORT et évitez les noms courts ou communs pour réduire le risque de conflits de noms.

    En général, tout ce qui n'est pas exporté reste accessible depuis l'extérieur du module en utilisant la syntaxe ModuleName::nom_item (ou "$blessed_ref->method"). Par convention, vous pouvez utiliser un trait d'union initial sur les noms pour indiquer informellement qu'ils sont 'internes' et non destinés à un usage public.

    (Il est en fait possible d'obtenir des fonctions privées en disant : "my $subref = sub { ... }; &$subref;". Mais il n'y a aucun moyen de l'appeler directement comme une méthode, car une méthode doit avoir un nom dans la table des symboles.)

    En règle générale, si le module essaie d'être orienté objet, n'exportez rien. S'il s'agit simplement d'une collection de fonctions, alors exportez tout avec @EXPORT_OK mais utilisez @EXPORT avec prudence.

  • Sélectionnez un nom pour le module.

    Ce nom doit être aussi descriptif, précis et complet que possible. Évitez tout risque d'ambiguïté. Essayez toujours d'utiliser deux mots ou plus entiers. En général, le nom doit refléter ce qui est spécial dans ce que fait le module plutôt que comment il le fait. Veuillez utiliser des noms de module imbriqués pour regrouper informellement ou catégoriser un module. Il devrait y avoir une très bonne raison pour qu'un module n'ait pas de nom imbriqué. Les noms de module doivent commencer par une majuscule.

    Avoir 57 modules appelés Sort ne facilitera la vie de personne (bien qu'avoir 23 appelés Sort::Quick ne soit que marginalement mieux :-). Imaginez quelqu'un essayant d'installer votre module aux côtés de beaucoup d'autres.

    Si vous développez une suite de modules/classes apparentés, il est bon de pratiquer l'utilisation de classes imbriquées avec un préfixe commun, car cela évitera les conflits d'espaces de noms. Par exemple : Xyz::Control, Xyz::View, Xyz::Model, etc. Utilisez les modules de cette liste comme guide de nommage.

    Si vous ajoutez un nouveau module à un ensemble, suivez les normes de l'auteur d'origine pour nommer les modules et l'interface des méthodes dans ces modules.

    Si vous développez des modules pour un usage interne privé ou spécifique à un projet, qui ne seront jamais rendus publics, alors vous devez vous assurer que leurs noms n'entreront pas en conflit avec un futur module public. Vous pouvez le faire soit en utilisant la catégorie réservée Local::*, soit en utilisant un nom de catégorie qui comprend un trait d'union comme Foo_Corp::*.

    Pour être portable, chaque composant d'un nom de module doit être limité à 11 caractères. S'il peut être utilisé sur MS-DOS, essayez de vous assurer que chaque composant est unique dans les 8 premiers caractères. Les modules imbriqués facilitent cela.

    Pour des conseils supplémentaires sur le nommage des modules, veuillez consulter :

    https://pause.perl.org/pause/query?ACTION=pause_namingmodules

    ou envoyez un courriel à la liste de diffusion <module-authors@perl.org>.

  • Avez-vous bien fait ?

    Comment savez-vous que vous avez pris les bonnes décisions ? Avez-vous choisi une conception d'interface qui causera des problèmes plus tard ? Avez-vous choisi le nom le plus approprié ? Avez-vous des questions ?

    La meilleure façon de le savoir avec certitude, et de recueillir de nombreuses suggestions utiles, est de demander à quelqu'un qui sait. La liste de diffusion <module-authors@perl.org> est utile à cet effet ; elle est également accessible via l'interface news sous le nom perl.module-authors à l'adresse nntp.perl.org.

    Il vous suffit de publier un bref résumé du module, de son objectif et de ses interfaces. Quelques lignes sur chacune des méthodes principales sont probablement suffisantes. (Si vous publiez l'intégralité du module, il pourrait être ignoré par des personnes occupées - généralement celles que vous souhaitez le plus lire !)

    Ne vous inquiétez pas de publier si vous ne pouvez pas dire quand le module sera prêt - dites-le simplement dans le message. Il pourrait être utile d'inviter d'autres personnes à vous aider, elles pourraient être en mesure de le terminer pour vous !

  • README et autres fichiers supplémentaires.

    Il est bien connu que les développeurs de logiciels documentent généralement entièrement les logiciels qu'ils écrivent. Si, cependant, le monde a un besoin urgent de votre logiciel et qu'il n'y a pas assez de temps pour écrire la documentation complète, veuillez au moins fournir un fichier README contenant :

  • Une description du module/package/extension, etc.
  • Un avis de droit d'auteur - voir ci-dessous.
  • Prérequis - ce dont vous pourriez avoir besoin en plus.
  • Comment le construire - modifications possibles de Makefile.PL, etc.
  • Comment l'installer.
  • Changements récents dans cette version
, en particulier les incompatibilités
  • Changements / améliorations que vous prévoyez d'apporter à l'avenir.

    • Si le fichier README semble devenir trop volumineux, vous pourriez souhaiter diviser certaines sections dans des fichiers séparés : INSTALL, Copying, ToDo, etc.

    • Ajout d'un avis de copyright.

      La manière dont vous choisissez de licencier votre travail est une décision personnelle. Le mécanisme général consiste à affirmer votre copyright, puis à déclarer comment les autres peuvent copier/utiliser/modifier votre travail.

      Perl, par exemple, est fourni avec deux types de licences : la GNU GPL et la licence artistique (voir les fichiers README, Copying et Artistic, ou perlgpl et perlartistic). Larry a de bonnes raisons de NE PAS utiliser uniquement la GNU GPL.

      Ma recommandation personnelle, par respect pour Larry, Perl et la communauté Perl en général, est de déclarer quelque chose de simple comme :

      Copyright (c) 1995 Your Name. Tous droits réservés.
Ce programme est un logiciel libre ; vous pouvez le redistribuer et/ou
le modifier sous les mêmes conditions que Perl lui-même.

      Cette déclaration devrait au moins apparaître dans le fichier README. Vous pourriez également souhaiter l'inclure dans un fichier Copying et vos fichiers sources. N'oubliez pas d'inclure les autres mots en plus du Copyright.

    • Donnez un numéro de version/d'édition/de publication au module.

      Pour être entièrement compatible avec les modules Exporter et MakeMaker, vous devez stocker le numéro de version de votre module dans une variable de package non-my appelée $VERSION. Il doit s'agir d'un nombre flottant positif avec au moins deux chiffres après la virgule (c'est-à-dire les centièmes, par exemple, "$VERSION = "0.01""). N'utilisez pas un style de version « 1.3.2 ». Voir Exporter pour plus de détails.

      Il peut être utile d'ajouter une fonction ou une méthode pour récupérer le numéro. Utilisez le numéro dans les annonces et les noms de fichiers d'archive lors de la publication du module (ModuleName-1.02.tar.Z). Voir perldoc ExtUtils::MakeMaker.pm pour plus de détails.

    • Comment publier et distribuer un module.

      Si possible, enregistrez le module auprès de CPAN. Suivez les instructions et les liens sur :

      https://www.cpan.org/modules/04pause.html

      et téléversez sur :

      https://pause.perl.org/

      et informez <modules@perl.org>. Cela permettra à quiconque d'installer votre module en utilisant l'outil "cpan" distribué avec Perl.

      En utilisant l'interface WWW, vous pouvez demander au serveur de téléversement de mettre en miroir vos modules depuis votre site ftp ou WWW dans votre propre répertoire sur CPAN !

    • Soyez prudent lorsque vous modifiez un module publié.

      Efforcez-vous toujours de rester compatible avec les versions publiées précédemment. Sinon, essayez d'ajouter un mécanisme pour revenir à l'ancien comportement si les gens s'y fient. Documentez les changements incompatibles.

    Lignes directrices pour la conversion de scripts de bibliothèque Perl 4 en modules

    • Il n'est pas nécessaire de tout convertir.

      Si ça ne casse pas, ne le réparez pas ! Les scripts de bibliothèque Perl 4 devraient continuer à fonctionner sans problème. Vous pourrez avoir besoin de faire quelques modifications mineures (comme échapper les @ non-tableaux dans les chaînes entre guillemets doubles) mais il n'est pas nécessaire de convertir un fichier .pl en module juste pour cela.

    • Considérez les implications.

      Toutes les applications Perl qui utilisent le script devront être modifiées (légèrement) si le script est converti en module. Est-ce que cela en vaut la peine, à moins que vous ne prévoyiez de faire d'autres changements en même temps ?

    • Profitez de l'opportunité.

      Si vous allez convertir le script en module, vous pouvez profiter de l'occasion pour redessiner l'interface. Les directives de création de modules ci-dessus incluent bon nombre des problèmes que vous devriez considérer.

    • L'utilitaire pl2pm vous aidera à démarrer.

      Cet utilitaire lit les fichiers *.pl (fournis en paramètres) et écrit les fichiers *.pm correspondants. Les utilitaires pl2pm font ce qui suit :

    • Ajoute les lignes standard du prologue de module
    • Convertit les spécificateurs de package de ' en ::
    • Convertit die(...) en croak(...)
    • Plusieurs autres modifications mineures

    Étant un processus mécanique, pl2pm n'est pas infaillible. Le code converti nécessitera une vérification minutieuse, en particulier les instructions de package. Ne supprimez pas le fichier .pl d'origine tant que le nouveau fichier .pm ne fonctionne pas !

    Lignes directrices pour la réutilisation de code d'application

    • Les applications complètes appartiennent rarement à la bibliothèque de modules Perl.
    • De nombreuses applications contiennent du code Perl qui pourrait être réutilisé.

      Aidez à sauver le monde ! Partagez votre code sous une forme qui facilite sa réutilisation.

    • Extrayez le code réutilisable dans un ou plusieurs fichiers de module séparés.
    • Profitez de l'occasion pour reconsidérer et redessiner les interfaces.
    • Dans certains cas, l''application' peut alors être réduite à un petit

      fragment de code construit sur les modules réutilisables. Dans ces cas, l'application pourrait être invoquée comme suit :

           % perl -e 'use Module::Name; method(@ARGV)' ...
ou
     % perl -mModule::Name ...    (dans perl5.002 ou supérieur)

    NOTE

    Perl n'impose pas de parties privées et publiques à ses modules comme vous avez pu en avoir l'habitude dans d'autres langages comme C++, Ada ou Modula-17. Perl n'a pas d'engouement pour la vie privée imposée. Il préférerait que vous restiez en dehors de son salon parce que vous n'avez pas été invité, pas parce qu'il a un fusil.

    Le module et son utilisateur ont un contrat, dont une partie est la coutume, et une partie est « écrite ». Une partie de la coutume est qu'un module ne pollue pas un espace de noms pour lequel il n'a pas été sollicité. Le contrat écrit pour le module (alias documentation) peut faire d'autres dispositions. Mais alors vous savez lorsque vous "use RedefineTheWorld" que vous redéfinissez le monde et que vous acceptez les conséquences.
