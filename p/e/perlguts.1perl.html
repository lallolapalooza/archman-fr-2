NOM

perlguts - Introduction à l'API Perl

DESCRIPTION

Ce document tente de décrire comment utiliser l'API Perl, ainsi que de fournir quelques informations sur le fonctionnement de base du noyau Perl. Il est loin d'être complet et contient probablement de nombreuses erreurs. Veuillez adresser toute question ou commentaire à l'auteur ci-dessous.

Variables

Types de données

Perl possède trois typedefs qui gèrent les trois types de données principaux de Perl :

SV  Valeur Scalaire
AV  Valeur de Tableau
HV  Valeur de Table de Hachage

Chaque typedef possède des routines spécifiques qui manipulent les différents types de données.

Qu'est-ce qu'un "IV" ?

Perl utilise un typedef spécial IV qui est un simple type entier signé garanti pour être suffisamment grand pour contenir un pointeur, mais peut être plus grand, en fonction de la configuration de Perl. De plus, il y a UV, qui est simplement un IV non signé.

Perl utilise également plusieurs typedefs spéciaux pour déclarer des variables afin de contenir des entiers d'une taille donnée (au moins). Utilisez I8, I16, I32 et I64 pour déclarer une variable entière signée ayant au moins autant de bits que le nombre indiqué dans son nom. Ceux-ci s'évaluent tous au type C natif qui est le plus proche du nombre de bits donné, mais pas plus petit que ce nombre. Par exemple, sur de nombreuses plateformes, un "short" a 16 bits de long, et si c'est le cas, I16 s'évaluera en un "short". Mais sur les plateformes où un "short" n'a pas exactement 16 bits, Perl utilisera le plus petit type contenant 16 bits ou plus.

U8, U16, U32 et U64 servent à déclarer les types entiers non signés correspondants.

Si la plateforme ne prend pas en charge les entiers 64 bits, I64 et U64 seront indéfinis. Utilisez IV et UV pour déclarer le plus grand type possible, et "WIDEST_UTYPE" dans perlapi pour le type non signé absolu maximal, mais qui peut ne pas être utilisable dans toutes les circonstances.

Une constante numérique peut être spécifiée avec ""INT16_C"" dans perlapi, ""UINTMAX_C"" dans perlapi, et similaires.

Travailler avec les SVs

Un SV peut être créé et chargé avec une seule commande. Il existe cinq types de valeurs qui peuvent être chargées : une valeur entière (IV), une valeur entière non signée (UV), un double (NV), une chaîne (PV), et un autre scalaire (SV). ("PV" signifie "Pointer Value" - Valeur Pointeur. Vous pourriez penser que le nom est mal choisi car il est décrit comme pointant uniquement vers des chaînes. Cependant, il est possible de le faire pointer vers d'autres choses. Par exemple, il pourrait pointer vers un tableau d'UV. Mais, l'utiliser pour des non-chaînes nécessite de la prudence, car l'hypothèse sous-jacente de bon nombre des éléments internes est que les PV sont uniquement pour les chaînes. Souvent, par exemple, un NUL final est ajouté automatiquement. L'utilisation non-chaîne est uniquement documentée dans ce paragraphe.)

Il existe plusieurs routines qui créent et initialisent des SV, avec de nouvelles routines ajoutées occasionnellement. Celles-ci sont toutes documentées dans "SV Handling" dans perlapi ; le nom de chacune commence par "newSV". Voici les plus basiques :

SV*  newSVbool(boolean_value);
SV*  newSViv(IV);
SV*  newSVuv(UV);
SV*  newSVnv(double);
SV*  newSVpv(const char*, STRLEN);
SV*  newSVpvf_nocontext(const char * const pat, ...)
SV*  newSVpvn(const char*, STRLEN);
SV*  newSVpvs("literal string")
SV*  newSVpvz(STRLEN)
SV*  newSVsv(SV*);

"STRLEN" est un type entier ("Size_t", généralement défini comme "size_t" dans config.h) garanti pour être suffisamment grand pour représenter la taille de toute chaîne que Perl peut gérer.

"literal string" est une chaîne entourée de guillemets doubles, et le SV créé est de type chaîne (un PV), initialisé pour contenir une copie de la chaîne littérale fournie. newSVpvs("") crée un SV contenant une chaîne vide (de longueur zéro) et retourne un pointeur vers celui-ci.

"newSVpvz" est similaire à newSVpvs(""), mais il réserve le nombre d'octets spécifié par son paramètre pour une croissance future, sans avoir à réallouer de mémoire. Il est utile dans les situations où vous ne connaissez pas la taille finale de la chaîne, mais vous avez une assez bonne idée de sa taille minimale éventuelle.

Dans le cas où un SV nécessite une initialisation plus complexe, vous pouvez créer un SV vide avec newSV(len). Si "len" est 0, un SV de type NULL est retourné, sinon un SV de type PV est retourné avec len + 1 (pour le NUL) octets de stockage alloués, accessibles via SvPVX. Dans les deux cas, le SV a la valeur undef.

SV *sv = newSV(0);   /* aucun stockage alloué  */
SV *sv = newSV(10);  /* 10 (+1) octets de stockage non initialisé
                      * alloués */

Pour modifier la valeur d'un SV *déjà existant*, voici les routines de base (avec d'autres spécifiées dans "SV Handling" dans perlapi) :

void  sv_setbool(SV*, bool);
void  sv_setiv(SV*, IV);
void  sv_setuv(SV*, UV);
void  sv_setnv(SV*, double);
void  sv_setpv(SV*, const char*);
void  sv_setpvn(SV*, const char*, STRLEN)
void  sv_setpvf(SV*, const char*, ...);
void  sv_vsetpvfn(SV*, const char*, STRLEN, va_list *,
                                    SV **, Size_t, bool *);
void  sv_setsv(SV*, SV*);

Notez que vous pouvez choisir de spécifier la longueur de la chaîne à assigner en utilisant "sv_setpvn", "newSVpvn", ou "newSVpv", ou vous pouvez laisser Perl calculer la longueur en utilisant "sv_setpv" ou en spécifiant 0 comme deuxième argument à "newSVpv". Attention cependant, Perl déterminera la longueur de la chaîne en utilisant "strlen", qui dépend de la chaîne se terminant par un caractère "NUL", et ne contenant pas d'autres NUL.

Les arguments de "sv_setpvf" sont traités comme "sprintf", et la sortie formatée devient la valeur.

"sv_vsetpvfn" est un analogue de "vsprintf", mais il vous permet de spécifier soit un pointeur vers une liste d'arguments variables, soit l'adresse et la longueur d'un tableau de SV. Le dernier argument pointe vers un booléen ; au retour, si ce booléen est vrai, des informations spécifiques à la locale ont été utilisées pour formater la chaîne, et le contenu de la chaîne n'est donc pas fiable (voir perlsec). Ce pointeur peut être NULL si ces informations ne sont pas importantes. Notez que cette fonction nécessite de spécifier la longueur du format.

Les fonctions "sv_set*()" ne sont pas assez génériques pour opérer sur des valeurs ayant du "magic". Voir "Magic Virtual Tables" plus loin dans ce document.

Tous les SV contenant des chaînes doivent se terminer par un caractère "NUL". S'il n'est pas terminé par un "NUL", il y a un risque de plantages du cœur (core dumps) et de corruptions de la part du code qui passe la chaîne à des fonctions C ou à des appels système qui attendent une chaîne terminée par un "NUL". Les fonctions propres à Perl ajoutent généralement un "NUL" final pour cette raison. Néanmoins, vous devez être très prudent lorsque vous passez une chaîne stockée dans un SV à une fonction C ou à un appel système.

Pour accéder à la valeur réelle vers laquelle pointe un SV, l'API de Perl expose plusieurs macros qui convertissent le type scalaire réel en IV, UV, double, ou chaîne :

  • SvIV(SV*) ("IV") et SvUV(SV*) ("UV")
  • SvNV(SV*) ("double")
  • Les chaînes sont un peu compliquées :
  • Chaîne d'octets : "SvPVbyte(SV*, STRLEN len)" ou SvPVbyte_nolen(SV*)

    Si la chaîne Perl est "\xff\xff", alors cela retourne une chaîne de 2 octets

    Ceci convient aux chaînes Perl qui représentent des octets.

  • Chaîne UTF-8 : "SvPVutf8(SV*, STRLEN len)" ou SvPVutf8_nolen(SV*)

    Si la chaîne Perl est "\xff\xff", alors ceci retourne un "char*" de 4 octets.

    Ceci convient aux chaînes Perl qui représentent des caractères.

    ATTENTION : Ce "char*" sera encodé via la variante interne de Perl pour UTF-8, ce qui signifie que si le SV contient des points de code non-Unicode (par exemple, 0x110000), le résultat peut contenir des extensions au-delà d'un UTF-8 valide. Voir "is_strict_utf8_string" dans perlapi pour des méthodes que Perl met à votre disposition pour vérifier la validité UTF-8 des retours de ces macros.

  • Vous pouvez également utiliser "SvPV(SV*, STRLEN len)" ou SvPV_nolen(SV*) pour récupérer le tampon interne brut du SV. C'est délicat, cependant ; si votre chaîne Perl est "\xff\xff", alors en fonction de l'encodage interne du SV, vous pourriez obtenir un "char*" de 2 octets **OU** de 4 octets. De plus, s'il s'agit de la chaîne de 4 octets, cela pourrait provenir soit de "\xff\xff" stocké en UTF-8, soit de "\xc3\xbf\xc3\xbf" stocké en octets bruts. Pour différencier ces cas, vous **DEVEZ** vérifier le bit UTF8 du SV (cf. "SvUTF8") pour savoir si la chaîne Perl source est de 2 caractères ("SvUTF8" serait activé) ou de 4 caractères ("SvUTF8" serait désactivé).

    IMPORTANT : L'utilisation de "SvPV", "SvPV_nolen", ou de macros de noms similaires *sans* vérifier le bit UTF8 du SV est presque certainement un bug si une entrée non-ASCII est autorisée.

    Lorsque le bit UTF8 est activé, la même **ATTENTION** concernant la validité UTF-8 s'applique ici que pour "SvPVutf8".

(Voir "How do I pass a Perl string to a C library?" pour plus de détails.)

Dans "SvPVbyte", "SvPVutf8", et "SvPV", la longueur du "char*" retourné est placée dans la variable "len" (ce sont des macros, donc vous n'utilisez *pas* &len). Si vous ne vous souciez pas de la longueur des données, utilisez plutôt "SvPVbyte_nolen", "SvPVutf8_nolen", ou "SvPV_nolen". La variable globale "PL_na" peut également être donnée à "SvPVbyte"/"SvPVutf8"/"SvPV" dans ce cas. Mais cela peut être assez inefficace car "PL_na" doit être accédé dans le stockage local des threads dans un Perl threadé. Quoi qu'il en soit, rappelez-vous que Perl autorise des chaînes de données arbitraires qui peuvent contenir des NULs et qui pourraient ne pas être terminées par un "NUL".

Rappelez-vous également que C ne vous permet pas de dire en toute sécurité "foo(SvPVbyte(s, len), len);". Cela pourrait fonctionner avec votre compilateur, mais cela ne fonctionnera pas pour tout le monde. Décomposez ce type d'instruction en affectations séparées :

SV *s;
STRLEN len;
char *ptr;
ptr = SvPVbyte(s, len);
foo(ptr, len);

Si vous voulez savoir si la valeur scalaire est VRAIE, vous pouvez utiliser :

SvTRUE(SV*)

Bien que Perl augmente automatiquement les chaînes pour vous, si vous avez besoin de forcer Perl à allouer plus de mémoire pour votre SV, vous pouvez utiliser la macro

SvGROW(SV*, STRLEN newlen)

qui déterminera si plus de mémoire doit être allouée. Si c'est le cas, elle appellera la fonction "sv_grow". Notez que "SvGROW" ne peut qu'augmenter, pas diminuer, la mémoire allouée d'un SV et qu'elle n'ajoute pas automatiquement d'espace pour l'octet "NUL" final (les fonctions propres à Perl font généralement "SvGROW(sv, len + 1)").

Si vous voulez écrire dans le tampon d'un SV existant et définir sa valeur à une chaîne, utilisez **SvPVbyte_force()** ou l'une de ses variantes pour forcer le SV à être un PV. Cela supprimera les divers types de non-chaînes du SV tout en préservant le contenu du SV dans le PV. Cela peut être utilisé, par exemple, pour ajouter des données d'une fonction API à un tampon sans copie supplémentaire :

(void)SvPVbyte_force(sv, len);
s = SvGROW(sv, len + needlen + 1);
/* quelque chose qui modifie jusqu'à needlen octets à s+len, mais
   modifie newlen octets
     par ex. newlen = read(fd, s + len, needlen);
   en ignorant les erreurs pour ces exemples
 */
s[len + newlen] = '\0';
SvCUR_set(sv, len + newlen);
SvUTF8_off(sv);
SvSETMAGIC(sv);

Si vous avez déjà les données en mémoire ou si vous voulez garder votre code simple, vous pouvez utiliser l'une des variantes sv_cat*(), comme **sv_catpvn()**. Si vous voulez insérer n'importe où dans la chaîne, vous pouvez utiliser **sv_insert()** ou **sv_insert_flags()**.

Si vous n'avez pas besoin du contenu existant du SV, vous pouvez éviter certaines copies avec :

SvPVCLEAR(sv);
s = SvGROW(sv, needlen + 1);
/* quelque chose qui modifie jusqu'à needlen octets à s, mais modifie
   newlen octets
     par ex. newlen = read(fd, s, needlen);
 */
s[newlen] = '\0';
SvCUR_set(sv, newlen);
SvPOK_only(sv); /* efface également SVf_UTF8 */
SvSETMAGIC(sv);

Encore une fois, si vous avez déjà les données en mémoire ou si vous voulez éviter la complexité de ce qui précède, vous pouvez utiliser **sv_setpvn()**.

Si vous avez un tampon alloué avec **Newx()** et que vous voulez le définir comme valeur du SV, vous pouvez utiliser **sv_usepvn_flags()**. Cela a quelques exigences si vous voulez éviter que Perl ne réalloue le tampon pour qu'il contienne le NUL final :

Newx(buf, somesize+1, char);
/* ... remplir buf ... */
buf[somesize] = '\0';
sv_usepvn_flags(sv, buf, somesize, SV_SMAGIC | SV_HAS_TRAILING_NUL);
/* buf appartient maintenant à perl, ne le libérez pas */

Si vous avez un SV et que vous voulez savoir quel type de données Perl pense qu'il est stocké, vous pouvez utiliser les macros suivantes pour vérifier le type de SV que vous avez.

SvIOK(SV*)
SvNOK(SV*)
SvPOK(SV*)

Soyez conscient que la récupération de la valeur numérique d'un SV peut activer IOK ou NOK sur ce SV, même lorsque le SV a commencé comme une chaîne. Avant Perl 5.36.0, la récupération de la valeur de chaîne d'un entier pouvait activer POK, mais cela ne peut plus se produire. À partir de 5.36.0, cela peut être utilisé pour distinguer la représentation d'origine d'un SV et est conçu pour simplifier la vie des sérialiseurs :

/* références gérées ailleurs */
if (SvIsBOOL(sv)) {
    /* booléen d'origine */
    ...
}
else if (SvPOK(sv)) {
    /* chaîne d'origine */
    ...
}
else if (SvNIOK(sv)) {
    /* numérique d'origine */
    ...
}
else {
    /* quelque chose de spécial ou undef */
}

Vous pouvez obtenir et définir la longueur actuelle de la chaîne stockée dans un SV avec les macros suivantes :

SvCUR(SV*)
SvCUR_set(SV*, I32 val)

Vous pouvez également obtenir un pointeur vers la fin de la chaîne stockée dans le SV avec la macro :

SvEND(SV*)

Mais notez que ces trois dernières macros ne sont valides que si SvPOK() est vrai.

Si vous voulez ajouter quelque chose à la fin de la chaîne stockée dans un "SV*", vous pouvez utiliser les fonctions suivantes :

void  sv_catpv(SV*, const char*);
void  sv_catpvn(SV*, const char*, STRLEN);
void  sv_catpvf(SV*, const char*, ...);
void  sv_vcatpvfn(SV*, const char*, STRLEN, va_list *, SV **,
                                                         I32, bool);
void  sv_catsv(SV*, SV*);

La première fonction calcule la longueur de la chaîne à ajouter en utilisant "strlen". Dans la seconde, vous spécifiez vous-même la longueur de la chaîne. La troisième fonction traite ses arguments comme "sprintf" et ajoute la sortie formatée. La quatrième fonction fonctionne comme "vsprintf". Vous pouvez spécifier l'adresse et la longueur d'un tableau de SV au lieu de l'argument va_list. La cinquième fonction étend la chaîne stockée dans le premier SV avec la chaîne stockée dans le second SV. Elle force également le second SV à être interprété comme une chaîne.

Les fonctions "sv_cat*()" ne sont pas assez génériques pour opérer sur des valeurs qui ont du "magic". Voir "Magic Virtual Tables" plus loin dans ce document.

Si vous connaissez le nom d'une variable scalaire, vous pouvez obtenir un pointeur vers son SV en utilisant ce qui suit :

SV*  get_sv("package::varname", 0);

Ceci retourne NULL si la variable n'existe pas.

Si vous voulez savoir si cette variable (ou tout autre SV) est effectivement "définie", vous pouvez appeler :

SvOK(SV*)

La valeur scalaire "undef" est stockée dans une instance de SV appelée "PL_sv_undef".

Son adresse peut être utilisée chaque fois qu'un "SV*" est nécessaire. Assurez-vous de ne pas essayer de comparer un sv aléatoire avec &PL_sv_undef. Par exemple, lors de l'interfaçage avec du code Perl, cela fonctionnera correctement pour :

foo(undef);

Mais cela ne fonctionnera pas lorsque appelé comme suit :

$x = undef;
foo($x);

Donc, pour répéter, utilisez toujours **SvOK()** pour vérifier si un sv est défini.

Vous devez également faire attention lorsque vous utilisez &PL_sv_undef comme valeur dans les AVs ou les HVs (voir "AVs, HVs et valeurs indéfinies").

Il existe également les deux valeurs "PL_sv_yes" et "PL_sv_no", qui contiennent respectivement les valeurs booléennes VRAI et FAUX. Comme "PL_sv_undef", leurs adresses peuvent être utilisées chaque fois qu'un "SV*" est nécessaire.

Ne vous laissez pas tromper en pensant que "(SV *) 0" est la même chose que &PL_sv_undef. Prenez ce code :

SV* sv = (SV*) 0;
if (I-am-to-return-a-real-value) {
        sv = sv_2mortal(newSViv(42));
}
sv_setsv(ST(0), sv);

Ce code essaie de retourner un nouveau SV (qui contient la valeur 42) s'il doit retourner une vraie valeur, ou undef sinon. Au lieu de cela, il a retourné un pointeur NULL qui, quelque part en aval, provoquera une violation de segmentation, une erreur de bus, ou simplement des résultats étranges. Remplacez le zéro par &PL_sv_undef dans la première ligne et tout ira bien.

Pour libérer un SV que vous avez créé,

appel SvREFCNT_dec(SV*). Normalement, cet appel n'est pas nécessaire (voir "Comptes de références et mortalité").

Décalages

Perl fournit la fonction "sv_chop" pour supprimer efficacement des caractères du début d'une chaîne ; vous lui donnez un SV et un pointeur vers un endroit à l'intérieur du PV, et elle ignore tout ce qui précède le pointeur. L'efficacité provient d'une petite astuce : au lieu de réellement supprimer les caractères, "sv_chop" définit le drapeau "OOK" (offset OK) pour signaler à d'autres fonctions que l'astuce de décalage est en vigueur, et elle déplace le pointeur PV (appelé "SvPVX") vers l'avant du nombre d'octets coupés, et ajuste "SvCUR" et "SvLEN" en conséquence. (Une partie de l'espace entre les anciens et les nouveaux pointeurs PV est utilisée pour stocker le nombre d'octets coupés.)

Par conséquent, à ce stade, le début du tampon que nous avons alloué se trouve à "SvPVX(sv) - SvIV(sv)" en mémoire et le pointeur PV pointe au milieu de ce stockage alloué.

Ceci est mieux démontré par un exemple. Normalement, la copie sur écriture empêchera la substitution de l'opérateur d'utiliser cette astuce, mais si vous pouvez construire une chaîne pour laquelle la copie sur écriture n'est pas possible, vous pouvez la voir en action. Dans l'implémentation actuelle, le dernier octet d'un tampon de chaîne est utilisé comme compteur de références de copie sur écriture. Si le tampon n'est pas assez grand, la copie sur écriture est ignorée. Regardons d'abord une chaîne vide :

% ./perl -Ilib -MDevel::Peek -le '$a=""; $a .= ""; Dump $a'
SV = PV(0x7ffb7c008a70) at 0x7ffb7c030390
  REFCNT = 1
  FLAGS = (POK,pPOK)
  PV = 0x7ffb7bc05b50 ""\0
  CUR = 0
  LEN = 10

Remarquez ici que LEN est de 10. (Cela peut différer sur votre plateforme.) Étendez la longueur de la chaîne à un de moins que 10, et faites une substitution :

% ./perl -Ilib -MDevel::Peek -le '$a=""; $a.="123456789"; $a=~s/.//; \
                                                           Dump($a)'
SV = PV(0x7ffa04008a70) at 0x7ffa04030390
  REFCNT = 1
  FLAGS = (POK,OOK,pPOK)
  OFFSET = 1
  PV = 0x7ffa03c05b61 ( "\1" . ) "23456789"\0
  CUR = 8
  LEN = 9

Ici, le nombre d'octets coupés (1) est indiqué ensuite comme OFFSET. La partie de la chaîne entre le "vrai" et le "faux" début est indiquée entre parenthèses, et les valeurs de "SvCUR" et "SvLEN" reflètent le faux début, pas le vrai. (Le premier caractère du tampon de chaîne a été changé en "\1" ici, pas en "1", car l'implémentation actuelle stocke le nombre de décalages dans le tampon de chaîne. Ceci est susceptible d'être modifié.)

Quelque chose de similaire à l'astuce de décalage est effectué sur les AV pour permettre un décalage et un épissage efficaces depuis le début du tableau ; tandis que "AvARRAY" pointe vers le premier élément du tableau visible depuis Perl, "AvALLOC" pointe vers le début réel du tableau C. Ce sont généralement les mêmes, mais une opération de "shift" peut être effectuée en augmentant "AvARRAY" d'un et en diminuant "AvFILL" et "AvMAX". Encore une fois, l'emplacement du début réel du tableau C n'intervient que lors de la libération du tableau. Voir "av_shift" dans av.c.

Qu'est-ce qui est vraiment stocké dans un SV ?

Rappelez-vous que la méthode habituelle pour déterminer le type de scalaire que vous avez est d'utiliser les macros "Sv*OK". Parce qu'un scalaire peut être à la fois un nombre et une chaîne, ces macros renvoient généralement toujours TRUE et l'appel des macros "Sv*V" effectuera la conversion appropriée de chaîne en entier/double ou d'entier/double en chaîne.

Si vous avez *vraiment* besoin de savoir si vous avez un entier, un double ou un pointeur de chaîne dans un SV, vous pouvez utiliser les trois macros suivantes à la place :

SvIOKp(SV*)
SvNOKp(SV*)
SvPOKp(SV*)

Celles-ci vous indiqueront si vous avez réellement un entier, un double ou un pointeur de chaîne stocké dans votre SV. Le "p" signifie privé.

Il existe diverses façons dont les drapeaux privés et publics peuvent différer. Par exemple, dans perl 5.16 et antérieur, un SV lié peut avoir une valeur sous-jacente valide dans l'emplacement IV (donc SvIOKp est vrai), mais les données doivent être accessibles via la routine FETCH plutôt que directement, donc SvIOK est faux. (Dans perl 5.18 et versions ultérieures, les scalaires liés utilisent les drapeaux de la même manière que les scalaires non liés.) Une autre situation est lorsque la conversion numérique a eu lieu et que la précision a été perdue : seul le drapeau privé est défini sur les valeurs "perte". Ainsi, lorsqu'un NV est converti en IV avec perte, SvIOKp, SvNOKp et SvNOK seront définis, tandis que SvIOK ne le sera pas.

En général, cependant, il est préférable d'utiliser les macros "Sv*V".

Valeurs en lecture seule

Dans Perl 5.16 et versions antérieures, la copie sur écriture (voir la section suivante) partageait un bit de drapeau avec les scalaires en lecture seule. Ainsi, la seule façon de tester si "sv_setsv", etc., lèvera une erreur "Modification d'une valeur en lecture seule" dans ces versions est :

SvREADONLY(sv) && !SvIsCOW(sv)

Sous Perl 5.18 et versions ultérieures, SvREADONLY s'applique uniquement aux variables en lecture seule, et, sous 5.20, les scalaires en copie sur écriture peuvent également être en lecture seule, donc la vérification ci-dessus est incorrecte. Vous voulez juste :

SvREADONLY(sv)

Si vous avez besoin d'effectuer cette vérification souvent, définissez votre propre macro comme suit :

#if PERL_VERSION >= 18
# define SvTRULYREADONLY(sv) SvREADONLY(sv)
#else
# define SvTRULYREADONLY(sv) (SvREADONLY(sv) && !SvIsCOW(sv))
#endif

Ou mieux encore, lisez les macros THINKFIRST ci-dessous.

Copie sur écriture

Perl implémente un mécanisme de copie sur écriture (COW) pour les scalaires, dans lequel les copies de chaînes ne sont pas immédiatement effectuées lorsqu'elles sont demandées, mais sont différées jusqu'à ce qu'elles soient rendues nécessaires par la modification de l'un ou l'autre scalaire. Ceci est en grande partie transparent, mais il faut veiller à ne pas modifier les tampons de chaînes qui sont partagés par plusieurs SV.

Vous pouvez tester si un SV utilise la copie sur écriture avec SvIsCOW(sv).

Vous pouvez forcer un SV à faire sa propre copie de son tampon de chaîne en appelant sv_force_normal(sv) ou SvPV_force_nolen(sv).

Si vous voulez que le SV abandonne son tampon de chaîne, utilisez "sv_force_normal_flags(sv, SV_COW_DROP_PV)" ou simplement "sv_setsv(sv, NULL)".

Toutes ces fonctions échoueront sur les scalaires en lecture seule (voir la section précédente pour plus d'informations à leur sujet).

Pour tester que votre code se comporte correctement et ne modifie pas les tampons COW, sur les systèmes qui prennent en charge mmap(2) (par exemple, Unix, Linux, BSD, macOS) vous pouvez configurer perl avec "-Accflags=-DPERL_DEBUG_READONLY_COW" et cela transformera les violations de tampon en crashs. Vous le trouverez merveilleusement lent, vous pourriez donc vouloir ignorer les propres tests de perl.

PENSER AVANT d'écrire dans un tampon de chaîne

Vous êtes plus susceptible de voir (et devriez généralement le faire) la macro SvTHINKFIRST(sv) utilisée pour vérifier si un SV est prêt à être écrit, car il s'agit d'une vérification unique combinée pour voir si le SV :

  • Pointe vers un tampon COW
  • Est en lecture seule
  • Contient une référence
  • A une magie pertinente assignée

Deux macros liées peuvent être utilisées pour effectuer ces vérifications et, si nécessaire, effectuer également une action :

  • SV_CHECK_THINKFIRST(sv) appelle sv_force_normal(sv) pour copier le tampon de chaîne, le transformant en une chaîne mutable.
  • SV_CHECK_THINKFIRST_COW_DROP(sv) appelle "sv_force_normal_flags(sv, SV_COW_DROP_PV)" qui abandonne tout tampon de chaîne pointé par "sv". Ceci est généralement utilisé pour éviter de copier une chaîne COW vers un nouveau tampon, avant d'écrire une chaîne complètement nouvelle à "sv".

Travailler avec les AVs

Il existe deux principales méthodes de longue date pour créer et charger un AV. La première méthode crée un AV vide :

AV*  newAV();

La seconde méthode crée l'AV et le remplit initialement avec des SV :

AV*  av_make(SSize_t num, SV **ptr);

Le second argument pointe vers un tableau contenant "num" "SV*". Une fois l'AV créé, les SV peuvent être détruits, si désiré.

Perl v5.36 a ajouté deux nouvelles façons de créer un AV et d'allouer un tableau SV** sans le remplir. Celles-ci sont plus efficaces qu'un newAV() suivi d'un av_extend().

/* Crée mais n'initialise pas (zéro) le tableau SV** */
AV *av = newAV_alloc_x(1);
/* Crée et initialise (zéro) le tableau SV** */
AV *av = newAV_alloc_xz(1);

L'argument numérique fait référence au nombre d'éléments de tableau à allouer, pas à un indice de tableau, et doit être supérieur à 0. La première forme ne doit jamais être utilisée que lorsque tous les éléments seront initialisés avant toute lecture. La lecture d'un SV* non initialisé - c'est-à-dire traiter une adresse mémoire aléatoire comme un SV* - est un bug grave.

Une fois l'AV créé, les opérations suivantes sont possibles :

void  av_push(AV*, SV*);
SV*   av_pop(AV*);
SV*   av_shift(AV*);
void  av_unshift(AV*, SSize_t num);

Ces opérations devraient être familières, à l'exception de "av_unshift". Cette routine ajoute "num" éléments au début du tableau avec la valeur "undef". Vous devez ensuite utiliser "av_store" (décrit ci-dessous) pour assigner des valeurs à ces nouveaux éléments.

Voici quelques autres fonctions :

Size_t  av_count(AV*);
SSize_t av_top_index(AV*);
SV**    av_fetch(AV*, SSize_t key, I32 lval);
SV**    av_store(AV*, SSize_t key, SV* val);

"av_count" retourne le nombre d’éléments dans le tableau (y compris les emplacements vides (non définis) qui sont mélangés avec ceux remplis). La fonction "av_top_index" retourne l'indice le plus élevé dans un tableau (similaire à $#tableau en Perl). Si le tableau est vide, -1 est retourné. C'est toujours égal à "av_count() - 1". La fonction "av_fetch" retourne la valeur à l'indice "key", mais si "lval" est non nul, alors "av_fetch" stockera une valeur indéfinie à cet indice. La fonction "av_store" stocke la valeur "val" à l'indice "key", et n'incrémente pas le compte de référence de "val". Ainsi, l'appelant est responsable de s'en occuper, et si "av_store" retourne NULL, l'appelant devra décrémenter le compte de référence pour éviter une fuite de mémoire. Notez que "av_fetch" et "av_store" retournent tous deux des "SV**", pas des "SV*" comme valeur de retour.

Quelques fonctions supplémentaires :

void  av_clear(AV*);
void  av_undef(AV*);
void  av_extend(AV*, SSize_t key);

La fonction "av_clear" supprime tous les éléments du tableau AV*, mais ne supprime pas le tableau lui-même. La fonction "av_undef" supprime tous les éléments du tableau ainsi que le tableau lui-même. La fonction "av_extend" étend le tableau afin qu'il contienne au moins "key+1" éléments. Si "key+1" est inférieur à la longueur actuellement allouée du tableau, rien ne se passe.

Si vous connaissez le nom d'une variable tableau, vous pouvez obtenir un pointeur vers son AV en utilisant la commande suivante :

AV*  get_av("package::varname", 0);

Ceci retourne NULL si la variable n'existe pas.

Voir "Understanding the Magic of Tied Hashes and Arrays" pour plus d'informations sur la façon d'utiliser les fonctions d'accès aux tableaux sur des tableaux liés.

Travail plus efficace avec les AV nouveaux ou standards

Perl v5.36 et v5.38 ont introduit des versions rationalisées et en ligne de certaines fonctions :

  • "av_store_simple"
  • "av_fetch_simple"
  • "av_push_simple"

Ce sont des remplacements directs, mais ils ne peuvent être utilisés que sur des AV directs qui répondent aux critères suivants :

  • ne sont pas magiques
  • ne sont pas en lecture seule
  • sont des "vrais" AV (voir la section suivante)
  • ont une valeur av_top_index > -2

Les AV créés à l'aide de newAV(), "av_make", "newAV_alloc_x", et "newAV_alloc_xz" sont tous compatibles au moment de la création. C'est seulement s'ils sont déclarés en lecture seule ou non réels, ont de la magie attachée, ou sont autrement configurés de manière inhabituelle qu'ils cesseront d'être compatibles.

Notez que certaines fonctions de l'interpréteur peuvent attacher de la magie à un AV dans le cadre d'opérations normales. Il est donc plus sûr, à moins que vous ne soyez sûr du cycle de vie d'un AV, de n'utiliser ces nouvelles fonctions qu'à proximité du point de création de l'AV.

Vrais AV - et ceux qui ne le sont pas

L'AV standard ou typique est parfois appelé un AV "réel", un état qui peut être vérifié avec la macro "AvREAL". Cet état signifie essentiellement que :

  • Chaque élément accessible du tableau est soit initialisé mais vide, soit contient un pointeur vers un SV vivant.
  • Lorsqu'un SV* est assigné à un élément du tableau, le nombre de références sur le SV est incrémenté. Inversement, lorsque l'élément est désassigné ou qu'un autre SV* lui est assigné, le nombre de références du SV expulsé est décrémenté.

Les AV "faux" sont destinés à des cas d'utilisation spécifiques et limités uniquement. Leur utilisation en dehors du noyau de Perl est fortement déconseillée.

Par exemple, la pile d'arguments de l'interpréteur est implémentée comme un AV, mais elle n'est pas "AvREAL". Ses éléments n'étaient historiquement pas comptés en référence, ce qui donne naissance à la catégorie de bugs "stack-not-refcounted" lorsque les SV sont libérés pendant l'exécution d'une instruction mais sont encore nécessaires plus tard dans cette instruction. Des efforts sont actuellement en cours pour passer à une pile comptée en référence afin de corriger cette catégorie de bugs : voir la section "Reference-counted argument stack" dans ce document.

Un AV "faux" peut être converti en un AV "réel" par "av_reify". La conversion doit avoir lieu si l'AV a le drapeau "SVpav_REIFY" défini, ce qui peut être vérifié à l'aide de la macro AvREIFY(). Essayer de stocker un SV* dans un AV, ou de le supprimer, implique généralement une vérification AvREIFY() et une conversion si nécessaire.

Voir les commentaires dans av.h et les fonctions dans av.c si vous voulez vraiment en savoir plus.

Travail avec les HV

Pour créer un HV, vous utilisez la routine suivante :

HV*  newHV();

Une fois que le HV a été créé, les opérations suivantes sont possibles sur celui-ci :

SV**  hv_store(HV*, const char* key, U32 klen, SV* val, U32 hash);
SV**  hv_fetch(HV*, const char* key, U32 klen, I32 lval);

Le paramètre "klen" est la longueur de la clé passée (Notez que vous ne pouvez pas passer 0 comme valeur de "klen" pour indiquer à Perl de mesurer la longueur de la clé). L'argument "val" contient le pointeur SV du scalaire stocké, et "hash" est la valeur de hachage pré-calculée (zéro si vous voulez que "hv_store" la calcule pour vous). Le paramètre "lval" indique si ce fetch fait réellement partie d'une opération de stockage, auquel cas une nouvelle valeur indéfinie sera ajoutée au HV avec la clé fournie et "hv_fetch" retournera comme si la valeur avait déjà existé.

N'oubliez pas que "hv_store" et "hv_fetch" retournent des "SV**" et pas seulement des "SV*". Pour accéder à la valeur scalaire, vous devez d'abord déréférencer la valeur de retour. Cependant, vous devez vérifier que la valeur de retour n'est pas NULL avant de la déréférencer.

Le premier de ces deux fonctions vérifie si une entrée de table de hachage existe, et le second la supprime.

bool  hv_exists(HV*, const char* key, U32 klen);
SV*   hv_delete(HV*, const char* key, U32 klen, I32 flags);

Si "flags" n'inclut pas le drapeau "G_DISCARD", alors "hv_delete" créera et retournera une copie mortelle de la valeur supprimée.

Et d'autres fonctions diverses :

void   hv_clear(HV*);
void   hv_undef(HV*);

Comme leurs homologues AV, "hv_clear" supprime toutes les entrées de la table de hachage mais ne supprime pas la table de hachage elle-même. "hv_undef" supprime à la fois les entrées et la table de hachage elle-même.

Perl conserve les données réelles dans une liste chaînée de structures avec un typedef HE. Celles-ci contiennent les pointeurs de clé et de valeur réels (plus une surcharge administrative supplémentaire). La clé est un pointeur de chaîne ; la valeur est un "SV*". Cependant, une fois que vous avez un "HE*", pour obtenir la clé et la valeur réelles, utilisez les routines spécifiées ci-dessous.

I32    hv_iterinit(HV*);
        /* Prépare le point de départ pour parcourir la table de hachage */
HE*    hv_iternext(HV*);
        /* Obtient l'entrée suivante et retourne un pointeur vers une
           structure contenant à la fois la clé et la valeur */
char*  hv_iterkey(HE* entry, I32* retlen);
        /* Obtient la clé à partir d'une structure HE et retourne
           également la longueur de la chaîne de clé */
SV*    hv_iterval(HV*, HE* entry);
        /* Retourne un pointeur SV vers la valeur de la structure HE */
SV*    hv_iternextsv(HV*, char** key, I32* retlen);
        /* Cette routine de commodité combine hv_iternext,
           hv_iterkey et hv_iterval. Les arguments key et retlen
           sont les valeurs de retour pour la clé et sa longueur.
           La valeur est retournée dans l'argument SV* */

Si vous connaissez le nom d'une variable de hachage, vous pouvez obtenir un pointeur vers son HV en utilisant la commande suivante :

HV*  get_hv("package::varname", 0);

Ceci retourne NULL si la variable n'existe pas.

L'algorithme de hachage est défini dans la macro "PERL_HASH" :

PERL_HASH(hash, key, klen)

L'implémentation exacte de cette macro varie selon l'architecture et la version de perl, et la valeur de retour peut changer à chaque invocation, de sorte que la valeur n'est valide que pour la durée d'un seul processus perl.

Voir "Understanding the Magic of Tied Hashes and Arrays" pour plus d'informations sur la façon d'utiliser les fonctions d'accès aux hachages sur des hachages liés.

Extensions de l'API de hachage

À partir de la version 5.004, les fonctions suivantes sont également prises en charge :

HE*     hv_fetch_ent  (HV* tb, SV* key, I32 lval, U32 hash);
HE*     hv_store_ent  (HV* tb, SV* key, SV* val, U32 hash);
bool    hv_exists_ent (HV* tb, SV* key, U32 hash);
SV*     hv_delete_ent (HV* tb, SV* key, I32 flags, U32 hash);
SV*     hv_iterkeysv  (HE* entry);

Notez que ces fonctions prennent des clés "SV*", ce qui simplifie l'écriture de code d'extension qui traite des structures de hachage. Ces fonctions permettent également de passer des clés "SV*" aux fonctions "tie" sans vous obliger à convertir les clés en chaînes (contrairement à l'ensemble précédent de fonctions).

Elles retournent et acceptent également des entrées de hachage complètes ("HE*"), ce qui rend leur utilisation plus efficace (car le numéro de hachage pour une chaîne particulière n'a pas besoin d'être recalculé à chaque fois). Voir perlapi pour des descriptions détaillées.

Les macros suivantes doivent toujours être utilisées pour accéder au contenu des entrées de hachage. Notez que les arguments de ces macros doivent être de simples variables, car ils peuvent être évalués plus d'une fois. Voir perlap

HeVAL(HE* he)

Notez que les deux fonctions "hv_store" et "hv_store_ent" n'incrémentent pas le compteur de références de la "val" stockée, ce qui est la responsabilité de l'appelant. Si ces fonctions retournent une valeur NULL, l'appelant devra généralement décrémenter le compteur de références de "val" pour éviter une fuite de mémoire.

AVs, HVs et valeurs indéfinies

Parfois, vous devez stocker des valeurs indéfinies dans des AV ou des HV. Bien que cela puisse être un cas rare, cela peut être délicat. C'est parce que vous êtes habitué à utiliser &PL_sv_undef si vous avez besoin d'un SV indéfini.

Par exemple, l'intuition vous dit que ce code XS :

AV *av = newAV();
av_store( av, 0, &PL_sv_undef );

est équivalent à ce code Perl :

my @av;
$av[0] = undef;

Malheureusement, ce n'est pas vrai. Dans perl 5.18 et les versions antérieures, les AV utilisent &PL_sv_undef comme marqueur pour indiquer qu'un élément de tableau n'a pas encore été initialisé. Ainsi, "exists $av[0]" serait vrai pour le code Perl ci-dessus, mais faux pour le tableau généré par le code XS. Dans perl 5.20, le stockage de &PL_sv_undef créera un élément en lecture seule, car le scalaire &PL_sv_undef lui-même est stocké, pas une copie.

Des problèmes similaires peuvent survenir lors du stockage de &PL_sv_undef dans des HV :

hv_store( hv, "key", 3, &PL_sv_undef, 0 );

Cela rendra effectivement la valeur "undef", mais si vous essayez de modifier la valeur de "key", vous obtiendrez l'erreur suivante :

Modification of non-creatable hash value attempted

Dans perl 5.8.0, &PL_sv_undef était également utilisé pour marquer des espaces réservés dans les hachages restreints. Cela faisait que ces entrées de hachage n'apparaissaient pas lors de l'itération sur le hachage ou lors de la vérification des clés avec la fonction "hv_exists".

Vous pouvez rencontrer des problèmes similaires lorsque vous stockez &PL_sv_yes ou &PL_sv_no dans des AV ou des HV. Essayer de modifier de tels éléments vous donnera l'erreur suivante :

Modification of a read-only value attempted

Pour faire court, vous pouvez utiliser les variables spéciales &PL_sv_undef, &PL_sv_yes et &PL_sv_no avec les AV et les HV, mais vous devez vous assurer de savoir ce que vous faites.

En général, si vous souhaitez stocker une valeur indéfinie dans un AV ou un HV, vous ne devez pas utiliser &PL_sv_undef, mais plutôt créer une nouvelle valeur indéfinie en utilisant la fonction "newSV", par exemple :

av_store( av, 42, newSV(0) );
hv_store( hv, "foo", 3, newSV(0), 0 );

Références

Les références sont un type spécial de scalaire qui pointe vers d'autres types de données (y compris d'autres références).

Pour créer une référence, utilisez l'une des fonctions suivantes :

SV* newRV_inc((SV*) thing);
SV* newRV_noinc((SV*) thing);

L'argument "thing" peut être n'importe lequel parmi un "SV*", un "AV*", ou un "HV*". Les fonctions sont identiques sauf que "newRV_inc" incrémente le compteur de références de "thing", tandis que "newRV_noinc" ne le fait pas. Pour des raisons historiques, "newRV" est un synonyme de "newRV_inc".

Une fois que vous avez une référence, vous pouvez utiliser la macro suivante pour déréférencer la référence :

SvRV(SV*)

puis appeler les routines appropriées, en convertissant le "SV*" retourné en "AV*" ou "HV*", si nécessaire.

Pour déterminer si un SV est une référence, vous pouvez utiliser la macro suivante :

SvROK(SV*)

Pour découvrir à quel type de valeur la référence pointe, utilisez la macro suivante et vérifiez ensuite la valeur de retour.

SvTYPE(SvRV(SV*))

Les types les plus utiles qui seront retournés sont :

SVt_PVAV    Array
SVt_PVHV    Hash
SVt_PVCV    Code
SVt_PVGV    Glob (possiblement un descripteur de fichier)

Toute valeur numérique retournée inférieure à SVt_PVAV sera un scalaire d'une certaine forme.

Voir "svtype" dans perlapi pour plus de détails.

Références bénies et objets de classe

Les références sont également utilisées pour prendre en charge la programmation orientée objet. Dans le lexique OO de Perl, un objet est simplement une référence qui a été bénie dans un paquet (ou une classe). Une fois bénie, le programmeur peut désormais utiliser la référence pour accéder aux différentes méthodes de la classe.

Une référence peut être bénie dans un paquet avec la fonction suivante :

SV* sv_bless(SV* sv, HV* stash);

L'argument "sv" doit être une valeur de référence. L'argument "stash" spécifie à quelle classe la référence appartiendra. Voir "Stashes et Globs" pour des informations sur la conversion des noms de classes en stashes.

/* Encore en construction */

La fonction suivante met à niveau rv vers une référence s'il n'en est pas déjà une. Crée un nouveau SV auquel rv pourra pointer. Si "classname" n'est pas nul, le SV est béni dans la classe spécifiée. SV est retourné.

SV* newSVrv(SV* rv, const char* classname);

Les trois fonctions suivantes copient un entier, un entier non signé ou un double dans un SV dont la référence est "rv". SV est béni si "classname" n'est pas nul.

SV* sv_setref_iv(SV* rv, const char* classname, IV iv);
SV* sv_setref_uv(SV* rv, const char* classname, UV uv);
SV* sv_setref_nv(SV* rv, const char* classname, NV iv);

La fonction suivante copie la valeur du pointeur (le *}$, l'adresse, pas la* chaîne !) dans un SV dont la référence est rv. SV est béni si "classname" n'est pas nul.

SV* sv_setref_pv(SV* rv, const char* classname, void* pv);

La fonction suivante copie une chaîne dans un SV dont la référence est "rv". Définissez la longueur sur 0 pour laisser Perl calculer la longueur de la chaîne. SV est béni si "classname" n'est pas nul.

SV* sv_setref_pvn(SV* rv, const char* classname, char* pv,
                                                     STRLEN length);

La fonction suivante teste si le SV est béni dans la classe spécifiée. Elle ne vérifie pas les relations d'héritage.

int  sv_isa(SV* sv, const char* name);

La fonction suivante teste si le SV est une référence vers un objet béni.

int  sv_isobject(SV* sv);

La fonction suivante teste si le SV est dérivé de la classe spécifiée. SV peut être soit une référence à un objet béni, soit une chaîne contenant un nom de classe. C'est la fonction qui implémente la fonctionnalité "UNIVERSAL::isa".

bool sv_derived_from(SV* sv, const char* name);

Pour vérifier si vous avez un objet dérivé d'une classe spécifique, vous devez écrire :

if (sv_isobject(sv) && sv_derived_from(sv, class)) { ... }

Création de nouvelles variables

Pour créer une nouvelle variable Perl avec une valeur indéfinie qui peut être accessible depuis votre script Perl, utilisez les routines suivantes, en fonction du type de variable.

SV*  get_sv("package::varname", GV_ADD);
AV*  get_av("package::varname", GV_ADD);
HV*  get_hv("package::varname", GV_ADD);

Remarquez l'utilisation de GV_ADD comme second paramètre. La nouvelle variable peut maintenant être définie, en utilisant les routines appropriées au type de données.

Il existe des macros supplémentaires dont les valeurs peuvent être combinées par OR bit à bit avec l'argument "GV_ADD" pour activer certaines fonctionnalités supplémentaires. Ces bits sont :

GV_ADDMULTI
Marque la variable comme étant définie plusieurs fois, empêchant ainsi :

avertissement.

GV_ADDWARN
Émet l'avertissement :

si la variable n'existait pas avant l'appel de la fonction.

Si vous ne spécifiez pas de nom de paquet, la variable est créée dans le paquet courant.

Compteurs de références et mortalité

Perl utilise un mécanisme de ramasse-miettes piloté par des compteurs de références. Les SV, AV ou HV (xV pour faire court dans ce qui suit) commencent leur vie avec un compteur de références de 1. Si le compteur de références d'un xV atteint 0, il sera détruit et sa mémoire sera rendue disponible pour réutilisation. Au niveau interne le plus basique, les compteurs de références peuvent être manipulés avec les macros suivantes :

int SvREFCNT(SV* sv);
SV* SvREFCNT_inc(SV* sv);
void SvREFCNT_dec(SV* sv);

(Il existe également des versions suffixées des macros d'incrémentation et de décrémentation, pour les situations où la pleine généralité de ces macros de base peut être échangée contre des performances.)

Cependant, la façon dont un programmeur devrait penser aux références n'est pas tant en termes de compteur de références brut, mais en termes de *propriété* des références. Une référence à un xV peut être détenue par n'importe laquelle d'une variété d'entités : un autre xV, l'interpréteur Perl, une structure de données XS, un morceau de code en cours d'exécution ou une portée dynamique. Un xV ne sait généralement pas quelles entités détiennent les références qui lui sont associées ; il sait seulement combien de références il y a, ce qui correspond au compteur de références.

Référencement

Le code XS manipule des données complexes, et le programmeur doit toujours savoir d'où provient une référence et qui la possède. Il doit être conscient de toute création ou destruction de références, ainsi que de tout transfert de propriété. Comme la propriété n'est pas explicitement représentée dans les structures de données xV, seul le compteur de références doit être réellement maintenu par le code, ce qui signifie que cette compréhension de la propriété n'est pas réellement évidente dans le code. Par exemple, le transfert de la propriété d'une référence d'un propriétaire à un autre ne modifie pas du tout le compteur de références, et peut donc être réalisé sans aucun code réel. (Le code de transfert ne touche pas à l'objet référencé, mais doit s'assurer que l'ancien propriétaire sait qu'il ne possède plus la référence, et que le nouveau propriétaire sait qu'il la possède désormais.)

Un xV visible au niveau Perl ne doit pas devenir non référencé et donc être détruit. Normalement, un objet ne devient non référencé que lorsqu'il n'est plus visible, souvent par les mêmes moyens qui le rendent invisible. Par exemple, une valeur de référence Perl (RV) possède une référence à son référent. Si le RV est écrasé, cette référence est détruite, et le référent, qui n'est plus accessible, peut être détruit en conséquence.

De nombreuses fonctions ont une forme de manipulation de références dans le cadre de leur objectif. Parfois, cela est documenté en termes de propriété des références, et parfois (moins utilement) en termes de modifications des compteurs de références. Par exemple, la fonction newRV_inc() est documentée pour créer un nouveau RV (avec un compteur de références de 1) et pour incrémenter le compteur de références du référent fourni par l'appelant. Il est préférable de comprendre cela comme la création d'une nouvelle référence au référent, qui est possédée par le RV créé, et le retour à l'appelant de la propriété de la seule référence au RV. La fonction newRV_noinc(), quant à elle, n'incrémente pas le compteur de références du référent, mais le RV finit néanmoins par posséder une référence au référent. Il est donc sous-entendu que l'appelant de newRV_noinc() renonce à une référence au référent, ce qui rend cette opération conceptuellement plus complexe, même si elle affecte moins les structures de données.

Par exemple, imaginez que vous souhaitiez retourner une référence depuis une fonction XSUB. À l'intérieur de la routine XSUB, vous créez un SV qui, initialement, n'a qu'une seule référence, détenue par la routine XSUB. Cette référence doit être éliminée avant que la routine ne se termine, sinon elle fuira, empêchant le SV d'être jamais détruit. Pour créer un RV faisant référence au SV, il est plus pratique de passer le SV à newRV_noinc(), qui consomme cette référence. La routine XSUB ne possède alors plus de référence au SV, mais possède une référence au RV, qui à son tour possède une référence au SV. La propriété de la référence au RV est ensuite transférée par le processus de retour du RV depuis l'XSUB.

Il existe des fonctions utilitaires qui peuvent aider à la destruction des xVs. Ces fonctions introduisent le concept de « "mortalité" ». Une grande partie de la documentation parle d'un xV lui-même étant mortel, mais c'est trompeur. C'est en réalité *une référence vers* un xV qui est mortelle, et il est possible qu'il y ait plus d'une référence mortelle vers un seul xV. Être mortel pour une référence signifie qu'elle est détenue par la pile temporaire, l'une des nombreuses piles internes de Perl, qui détruira cette référence « peu de temps après ». Généralement, « peu de temps après » correspond à la fin de l'instruction Perl actuelle. Cependant, cela devient plus complexe autour des portées dynamiques : il peut y avoir plusieurs ensembles de références mortelles en même temps, avec des dates de fin différentes. En interne, le déterminant réel de la destruction des références xV mortelles dépend de deux macros, SAVETMPS et FREETMPS. Voir perlcall et perlxs et « Pile des temporaires » ci-dessous pour plus de détails sur ces macros.

Les références mortelles sont principalement utilisées pour les xVs qui sont placés sur la pile principale de Perl. La pile pose problème pour le suivi des références, car elle contient de nombreuses références xV, mais ne détient pas ces références : elles ne sont pas comptées. Actuellement, de nombreux bugs résultent de la destruction de xVs alors qu'ils sont référencés par la pile, car les références non comptées de la pile ne suffisent pas à maintenir les xVs en vie. Ainsi, lorsque vous placez une référence (non comptée) sur la pile, il est d'une importance vitale de s'assurer qu'il y aura une référence comptée vers le même xV qui durera au moins aussi longtemps que la référence non comptée. Mais il est également important que cette référence comptée soit nettoyée au moment approprié, et ne prolonge pas indûment la durée de vie du xV. Avoir une référence mortelle est souvent le meilleur moyen de satisfaire cette exigence, surtout si le xV a été créé spécifiquement pour être placé sur la pile et serait autrement non référencé.

Pour créer une référence mortelle, utilisez les fonctions :

SV*  sv_newmortal()
SV*  sv_mortalcopy(SV*)
SV*  sv_2mortal(SV*)

sv_newmortal() crée un SV (avec la valeur indéfinie) dont la seule référence est mortelle. sv_mortalcopy() crée un xV dont la valeur est une copie d'un xV fourni et dont la seule référence est mortelle. sv_2mortal() rend mortelle une référence xV existante : elle transfère la propriété d'une référence de l'appelant à la pile des temporaires. Comme "sv_newmortal" ne donne aucune valeur au nouveau SV, il faut normalement lui en donner une via "sv_setpv", "sv_setiv", etc. :

SV *tmp = sv_newmortal();
sv_setiv(tmp, an_integer);

Comme il s'agit de plusieurs instructions C, il est très courant de voir plutôt cet idiome :

SV *tmp = sv_2mortal(newSViv(an_integer));

Les routines mortelles ne sont pas réservées aux SVs ; les AVs et les HVs peuvent être rendus mortels en passant leur adresse (castée en "SV*") aux routines "sv_2mortal" ou "sv_mortalcopy".

Stashes et Globs

Un stash est une table de hachage qui contient toutes les variables définies dans un paquet. Chaque clé du stash est un nom de symbole (partagé par tous les différents types d'objets portant le même nom), et chaque valeur dans la table de hachage est un GV (Glob Value). Ce GV contient à son tour des références aux différents objets de ce nom, y compris (mais sans s'y limiter) les éléments suivants :

Valeur scalaire
Valeur de tableau
Valeur de hachage
Descripteur d'E/S
Format
Sous-routine

Il existe un seul stash appelé "PL_defstash" qui contient les éléments qui existent dans le paquet "main". Pour accéder aux éléments des autres paquets, ajoutez la chaîne « :: » au nom du paquet. Les éléments du paquet "Foo" se trouvent dans le stash "Foo::" dans PL_defstash. Les éléments du paquet "Bar::Baz" se trouvent dans le stash "Baz::" dans le stash de "Bar::".

Pour obtenir le pointeur du stash pour un paquet particulier, utilisez la fonction :

HV*  gv_stashpv(const char* name, I32 flags)
HV*  gv_stashsv(SV*, I32 flags)

La première fonction prend une chaîne littérale, la seconde utilise la chaîne stockée dans le SV. N'oubliez pas qu'un stash n'est qu'une table de hachage, vous récupérez donc un "HV*". Le flag "flags" créera un nouveau paquet s'il est défini sur GV_ADD.

Le nom que "gv_stash*v" attend est le nom du paquet dont vous voulez la table de symboles. Le paquet par défaut s'appelle "main". Si vous avez des paquets multiples imbriqués, passez leurs noms à "gv_stash*v", séparés par "::" comme dans le langage Perl lui-même.

Alternativement, si vous avez un SV qui est une référence bénie, vous pouvez trouver le pointeur du stash en utilisant :

HV*  SvSTASH(SvRV(SV*));

puis utilisez ce qui suit pour obtenir le nom du paquet lui-même :

char*  HvNAME(HV* stash);

Si vous avez besoin de bénir ou de re-bénir un objet, vous pouvez utiliser la fonction suivante :

SV*  sv_bless(SV*, HV* stash)

où le premier argument, un "SV*", doit être une référence, et le second argument est un stash. Le "SV*" retourné peut maintenant être utilisé de la même manière que n'importe quel autre SV.

Pour plus d'informations sur les références et les bénédictions, consultez perlref.

Descripteurs d'E/S

Comme les AVs et les HVs, les objets IO sont un autre type de SV non scalaire qui peut contenir des objets PerlIO d'entrée et de sortie ou un "DIR *" de opendir().

Vous pouvez créer un nouvel objet IO :

IO*  newIO();

Contrairement aux autres SVs, un nouvel objet IO est automatiquement béni dans la classe IO::File.

L'objet IO contient un descripteur PerlIO d'entrée et de sortie :

PerlIO *IoIFP(IO *io);
PerlIO *IoOFP(IO *io);

Généralement, si l'objet IO a été ouvert sur un fichier, le descripteur d'entrée est toujours présent, mais le descripteur de sortie n'est présent que si le fichier est ouvert en écriture. Pour un fichier, si les deux sont présents, ils seront le même objet PerlIO.

Des objets PerlIO distincts d'entrée et de sortie sont créés pour les sockets et les périphériques de caractères.

L'objet IO contient également d'autres données associées aux descripteurs d'E/S Perl :

IV IoLINES(io);                /* $. */
IV IoPAGE(io);                 /* $% */
IV IoPAGE_LEN(io);             /* $= */
IV IoLINES_LEFT(io);           /* $- */
char *IoTOP_NAME(io);          /* $^ */
GV *IoTOP_GV(io);              /* $^ */
char *IoFMT_NAME(io);          /* $~ */
GV *IoFMT_GV(io);              /* $~ */
char IoTYPE(io);
U8 IoFLAGS(io);

La plupart de ceux-ci sont impliqués dans les formats.

IoFLAGs() peut contenir une combinaison de drapeaux, dont les plus intéressants sont "IOf_FLUSH" ($|) pour la vidange automatique et "IOf_UNTAINT", qui peut être défini avec la méthode untaint() de IO::Handle.

L'objet IO peut également contenir un descripteur de répertoire :

DIR *IoDIRP(io);

adapté à une utilisation avec PerlDir_read(), etc.

Toutes ces macros d'accès sont des lvalues, il n'y a pas de macros _set() distinctes pour modifier les membres de l'objet IO.

SVs à double type

Les variables scalaires ne contiennent normalement qu'un seul type de valeur : un entier, un double, un pointeur ou une référence. Perl convertira automatiquement les données scalaires réelles du type stocké dans

Variables Magiques

Certaines variables scalaires contiennent plus d'un type de données scalaires. Par exemple, la variable $! contient soit la valeur numérique de "errno", soit son équivalent en chaîne à partir de "strerror" ou de "sys_errlist[]".

Pour forcer plusieurs valeurs de données dans un SV, vous devez faire deux choses : utiliser les routines "sv_set*v" pour ajouter le type scalaire supplémentaire, puis définir un indicateur afin que Perl croie qu'il contient plus d'un type de données. Les quatre macros pour définir les indicateurs sont :

SvIOK_on
SvNOK_on
SvPOK_on
SvROK_on

La macro particulière que vous devez utiliser dépend de la routine "sv_set*v" que vous avez appelée en premier. En effet, chaque routine "sv_set*v" active uniquement le bit correspondant au type de données en cours de définition, et désactive tous les autres.

Par exemple, pour créer une nouvelle variable Perl appelée "dberror" qui contient à la fois les valeurs numériques et descriptives de l'erreur, vous pouvez utiliser le code suivant :

extern int  dberror;
extern char *dberror_list;
SV* sv = get_sv("dberror", GV_ADD);
sv_setiv(sv, (IV) dberror);
sv_setpv(sv, dberror_list[dberror]);
SvIOK_on(sv);

Si l'ordre de "sv_setiv" et "sv_setpv" avait été inversé, alors la macro "SvPOK_on" aurait dû être appelée à la place de "SvIOK_on".

Variables Magiques

Tout SV peut être magique, c'est-à-dire qu'il possède des fonctionnalités spéciales qu'un SV normal n'a pas. Ces fonctionnalités sont stockées dans la structure SV dans une liste chaînée de "struct magic", typée en "MAGIC".

struct magic {
    MAGIC*      mg_moremagic;
    MGVTBL*     mg_virtual;
    U16         mg_private;
    char        mg_type;
    U8          mg_flags;
    I32         mg_len;
    SV*         mg_obj;
    char*       mg_ptr;
};

Notez que ceci est à jour à partir du niveau de correctif 0 et pourrait changer à tout moment.

Attribution de la Magie

Perl ajoute de la magie à un SV en utilisant la fonction sv_magic :

void sv_magic(SV* sv, SV* obj, int how, const char* name, I32 namlen);

L'argument "sv" est un pointeur vers le SV qui doit acquérir une nouvelle fonctionnalité magique.

Si "sv" n'est pas déjà magique, Perl utilise la macro "SvUPGRADE" pour convertir "sv" au type "SVt_PVMG". Perl continue ensuite en ajoutant une nouvelle magie au début de la liste chaînée des fonctionnalités magiques. Toute entrée précédente du même type de magie est supprimée. Notez que cela peut être outrepassé, et que plusieurs instances du même type de magie peuvent être associées à un SV.

Les arguments "name" et "namlen" sont utilisés pour associer une chaîne à la magie, typiquement le nom d'une variable. "namlen" est stocké dans le champ "mg_len" et si "name" n'est pas nul, alors soit une copie "savepvn" de "name", soit "name" lui-même est stocké dans le champ "mg_ptr", selon que "namlen" est supérieur à zéro ou égal à zéro respectivement. À titre de cas spécial, si "(name && namlen == HEf_SVKEY)" alors "name" est supposé contenir un "SV*" et est stocké tel quel avec son REFCNT incrémenté.

La fonction sv_magic utilise "how" pour déterminer quelle table virtuelle de magie prédéfinie, le cas échéant, doit être assignée au champ "mg_virtual". Voir la section "Tables Virtuelles Magiques" ci-dessous. L'argument "how" est également stocké dans le champ "mg_type". La valeur de "how" doit être choisie parmi l'ensemble des macros "PERL_MAGIC_foo" trouvées dans perl.h. Notez qu'avant l'ajout de ces macros, les internes de Perl utilisaient directement des littéraux de caractères, vous pourriez donc rencontrer du code ou de la documentation anciens faisant référence à la magie 'U' plutôt qu'à "PERL_MAGIC_uvar" par exemple.

L'argument "obj" est stocké dans le champ "mg_obj" de la structure "MAGIC". S'il n'est pas identique à l'argument "sv", le compteur de références de l'objet "obj" est incrémenté. S'il est identique, ou si l'argument "how" est "PERL_MAGIC_arylen", "PERL_MAGIC_regdatum", "PERL_MAGIC_regdata", ou s'il s'agit d'un pointeur NULL, alors "obj" est simplement stocké, sans que le compteur de références ne soit incrémenté.

Voir également "sv_magicext" dans perlapi pour une manière plus flexible d'ajouter de la magie à un SV.

Il existe également une fonction pour ajouter de la magie à un "HV" :

void hv_magic(HV *hv, GV *gv, int how);

Celle-ci appelle simplement "sv_magic" et convertit l'argument "gv" en un "SV".

Pour supprimer la magie d'un SV, appelez la fonction sv_unmagic :

int sv_unmagic(SV *sv, int type);

L'argument "type" doit être égal à la valeur "how" lors de la magie initiale du "SV".

Cependant, notez que "sv_unmagic" supprime toute magie d'un certain "type" du "SV". Si vous souhaitez supprimer uniquement une certaine magie d'un "type" basée sur la table virtuelle magique, utilisez "sv_unmagicext" à la place :

int sv_unmagicext(SV *sv, int type, MGVTBL *vtbl);

Tables Virtuelles Magiques

Le champ "mg_virtual" dans la structure "MAGIC" est un pointeur vers une "MGVTBL", qui est une structure de pointeurs de fonctions et signifie "Table Virtuelle Magique" pour gérer les diverses opérations qui pourraient être appliquées à cette variable.

La "MGVTBL" comporte cinq (ou parfois huit) pointeurs vers les types de routines suivants :

int  (*svt_get)  (pTHX_ SV* sv, MAGIC* mg);
int  (*svt_set)  (pTHX_ SV* sv, MAGIC* mg);
U32  (*svt_len)  (pTHX_ SV* sv, MAGIC* mg);
int  (*svt_clear)(pTHX_ SV* sv, MAGIC* mg);
int  (*svt_free) (pTHX_ SV* sv, MAGIC* mg);
int  (*svt_copy) (pTHX_ SV *sv, MAGIC* mg, SV *nsv,
                                      const char *name, I32 namlen);
int  (*svt_dup)  (pTHX_ MAGIC *mg, CLONE_PARAMS *param);
int  (*svt_local)(pTHX_ SV *nsv, MAGIC *mg);

Cette structure MGVTBL est définie au moment de la compilation dans perl.h et il existe actuellement 32 types. Ces différentes structures contiennent des pointeurs vers diverses routines qui effectuent des actions supplémentaires en fonction de la fonction appelée.

Pointeur de fonction    Action effectuée
--------------------    ----------------
svt_get                 Faire quelque chose avant que la valeur du SV ne soit
                        récupérée.
svt_set                 Faire quelque chose après que le SV se soit vu attribuer
                        une valeur.
svt_len                 Rapporter la longueur du SV.
svt_clear               Effacer quelque chose que le SV représente.
svt_free                Libérer tout stockage supplémentaire associé au SV.
svt_copy                copier la magie des variables liées dans un élément lié
svt_dup                 dupliquer une structure magique lors du clonage de thread
svt_local               copier la magie dans une valeur locale lors de 'local'

Par exemple, la structure MGVTBL appelée "vtbl_sv" (qui correspond à un "mg_type" de "PERL_MAGIC_sv") contient :

{ magic_get, magic_set, magic_len, 0, 0 }

Ainsi, lorsqu'un SV est déterminé comme étant magique et de type "PERL_MAGIC_sv", si une opération de récupération (get) est effectuée, la routine "magic_get" est appelée. Toutes les diverses routines pour les divers types magiques commencent par "magic_". REMARQUE : les routines magiques ne sont pas considérées comme faisant partie de l'API Perl et peuvent ne pas être exportées par la bibliothèque Perl.

Les trois dernières emplacements sont un ajout récent, et pour des raisons de compatibilité du code source, ils ne sont vérifiés que si l'un des trois indicateurs "MGf_COPY", "MGf_DUP", ou "MGf_LOCAL" est défini dans mg_flags. Cela signifie que la plupart du code peut continuer à déclarer une vtable comme une valeur à 5 éléments. Ces trois derniers sont actuellement utilisés exclusivement par le code de gestion des threads et sont susceptibles de changer.

De même, la magie "PERL_MAGIC_uvar" peut être utilisée un peu comme tie() pour appeler une fonction C chaque fois que la valeur d'un scalaire est utilisée ou modifiée. Le champ "mg_ptr" de "MAGIC" pointe vers une structure "ufuncs":

struct ufuncs {
    I32 (*uf_val)(pTHX_ IV, SV*);
    I32 (*uf_set)(pTHX_ IV, SV*);
    IV uf_index;
};

Lorsque le SV est lu ou écrit, la fonction "uf_val" ou "uf_set" sera appelée avec "uf_index" comme premier argument et un pointeur vers le SV comme second. Un exemple simple de la façon d'ajouter la magie "PERL_MAGIC_uvar" est montré ci-dessous. Notez que la structure ufuncs est copiée par sv_magic, vous pouvez donc l'allouer en toute sécurité sur la pile.

void
Umagic(sv)
    SV *sv;
PREINIT:
    struct ufuncs uf;
CODE:
    uf.uf_val   = &my_get_fn;
    uf.uf_set   = &my_set_fn;
    uf.uf_index = 0;
    sv_magic(sv, 0, PERL_MAGIC_uvar, (char*)&uf, sizeof(uf));

L'attachement de "PERL_MAGIC_uvar" aux tableaux est autorisé mais n'a aucun effet.

Pour les hashes, il existe un crochet spécialisé qui donne le contrôle sur les clés de hash (mais pas sur les valeurs). Ce crochet appelle la magie 'get' de "PERL_MAGIC_uvar" si la fonction "set" de la structure "ufuncs" est NULL. Le crochet est activé chaque fois que le hash est accédé avec une clé spécifiée comme "SV" via les fonctions "hv_store_ent", "hv_fetch_ent", "hv_delete_ent" et "hv_exists_ent". L'accès à la clé sous forme de chaîne via les fonctions sans le suffixe "..._ent" contourne le crochet. Voir "GUTS" dans Hash::Util::FieldHash pour une description détaillée.

Notez que comme plusieurs extensions peuvent utiliser la magie "PERL_MAGIC_ext" ou "PERL_MAGIC_uvar", il est important que les extensions fassent des efforts supplémentaires pour éviter les conflits. Généralement, utiliser la magie uniquement sur les objets bénis dans la même classe que l'extension est suffisant. Pour la magie "PERL_MAGIC_ext", il est généralement bon de définir une "MGVTBL", même si tous ses champs seront 0, afin que des pointeurs "MAGIC" individuels puissent être identifiés comme un type de magie particulier en utilisant leur table virtuelle magique. "mg_findext" offre un moyen facile de le faire :

STATIC MGVTBL my_vtbl = { 0, 0, 0, 0, 0, 0, 0, 0 };
MAGIC *mg;
if ((mg = mg_findext(sv, PERL_MAGIC_ext, &my_vtbl))) {
    /* ceci est vraiment le nôtre, pas un PERL_MAGIC_ext d'un autre module */
    my_priv_data_t *priv = (my_priv_data_t *)mg->mg_ptr;
    ...
}

Notez également que les fonctions "sv_set*()" et "sv_cat*()" décrites précédemment n'invoquent PAS la magie 'set' sur leurs cibles. Cela doit être fait par l'utilisateur, soit en appelant la macro SvSETMAGIC() après avoir appelé ces fonctions, soit en utilisant l'une des fonctions "sv_set*_mg()" ou "sv_cat*_mg()". De même, le code C générique doit appeler la macro SvGETMAGIC() pour invoquer toute magie 'get' s'il utilise un SV obtenu à partir de sources externes dans des fonctions qui ne gèrent pas la magie. Voir perlapi pour une description de ces fonctions. Par exemple, les appels aux fonctions "sv_cat*()" doivent généralement être suivis de SvSETMAGIC(), mais ils n'ont pas besoin d'un SvGETMAGIC() préalable car leur implémentation gère la magie 'get'.

Localisation des changements

Perl possède une construction très pratique

{
  local $var = 2;
  ...
}

Cette construction est *approximativement* équivalente à

{
  my $oldvar = $var;
  $var = 2;
  ...
  $var = $oldvar;
}

La principale différence est que la première construction rétablirait la valeur initiale de $var, quelle que soit la manière dont le contrôle quitte le bloc : "goto", "return", "die"/ "eval", etc. Elle est également un peu plus efficace.

Il existe un moyen d'accomplir une tâche similaire en C via l'API Perl : créer un *pseudo-bloc*, et faire en sorte que certains changements soient automatiquement annulés à sa fin, soit explicitement, soit via une sortie non locale (via die()). Une construction de type *bloc* est créée par une paire de macros "ENTER"/ "LEAVE" (voir "Returning a Scalar" in perlcall). Une telle construction peut être créée spécialement pour une tâche localisée importante, ou une construction existante (comme les limites d'une sous-routine/bloc Perl englobant, ou une paire existante pour libérer des TMP) peut être utilisée. (Dans le second cas, la surcharge d'une localisation supplémentaire doit être presque négligeable.) Notez que toute XSUB est automatiquement encapsulée dans une paire "ENTER"/ "LEAVE".

À l'intérieur d'un tel *pseudo-bloc*, le service suivant est disponible :

"SAVEINT(int i)"
"SAVEIV(IV i)"
"SAVEI32(I32 i)"
"SAVEI8(I8 i)"
"SAVEI16(I16 i)"
"SAVEBOOL(int i)"
"SAVESTRLEN(STRLEN i)"
Ces macros organisent la restauration de la valeur de la variable entière "i" à la fin du *pseudo-bloc* englobant.
SAVESPTR(s)
SAVEPPTR(p)
Ces macros organisent la restauration de la valeur des pointeurs "s" et "p". "s" doit être un pointeur d'un type qui survit à la conversion en "SV*" et retour, "p" doit pouvoir survivre à la conversion en "char*" et retour.
"SAVERCPV(char **ppv)"
Cette macro organise la restauration de la valeur d'une variable "char *" qui a été allouée avec un appel à rcpv_new() à son état précédent lorsque le pseudo-bloc courant est terminé. Le pointeur stocké dans *ppv au moment de l'appel sera incrémenté de son compteur de références et stocké dans la pile de sauvegarde. Plus tard, lorsque le *pseudo-bloc* courant sera terminé, la valeur stockée dans *ppv sera décrémentée de son compteur de références, et la valeur précédente sera restaurée à partir de la pile de sauvegarde, qui sera également décrémentée de son compteur de références.

C'est l'équivalent "RCPV" de SAVEGENERICSV().

"SAVEGENERICSV(SV **psv)"
Cette macro organise la restauration de la valeur d'une variable "SV *" à son état précédent lorsque le pseudo-bloc courant est terminé. Le pointeur stocké dans *psv au moment de l'appel sera incrémenté de son compteur de références et stocké dans la pile de sauvegarde. Plus tard, lorsque le *pseudo-bloc* courant sera terminé, la valeur stockée dans *ppv sera décrémentée de son compteur de références, et la valeur précédente sera restaurée à partir de la pile de sauvegarde, qui sera également décrémentée de son compteur de références. Ceci est l'équivalent C de "local $sv".
"SAVEFREESV(SV *sv)"
Le compteur de références de "sv" sera décrémenté à la fin du *pseudo-bloc*. Ceci est similaire à "sv_2mortal" en ce sens que c'est aussi un mécanisme pour effectuer un "SvREFCNT_dec" retardé. Cependant, alors que "sv_2mortal" étend la durée de vie de "sv" jusqu'au début de l'instruction suivante, "SAVEFREESV" l'étend jusqu'à la fin de la portée englobante. Ces durées de vie peuvent être radicalement différentes.

Comparer également avec "SAVEMORTALIZESV".

"SAVEMORTALIZESV(SV *sv)"
Comme "SAVEFREESV", mais rend "sv" mortel à la fin de la portée actuelle au lieu de décrémenter son compteur de références. Cela a généralement pour effet de maintenir "sv" en vie jusqu'à ce que l'instruction qui a appelé la portée actuellement vivante ait fini de s'exécuter.
"SAVEFREEOP(OP *op)"
L'objet "OP *" est libéré avec op_free() à la fin du *pseudo-bloc*.
SAVEFREEPV(p)
Le bloc de mémoire pointé par "p" est libéré avec Safefree() à la fin du *pseudo-bloc* courant.
"SAVEFREERCPV(char *pv)"
Assure qu'un "char *" qui a été créé par un appel à rcpv_new() est libéré avec rcpv_free() à la fin du *pseudo-bloc* courant.

C'est l'équivalent RCPV de SAVEFREESV().

"SAVECLEARSV(SV *sv)"
Efface un emplacement dans le tampon de travail courant qui correspond à "sv" à la fin du *pseudo-bloc*.
"SAVEDELETE(HV *hv, char *key, I32 length)"

À la fin du *pseudo-bloc*, la fonction "f" est appelée avec le seul argument "p" qui peut être NULL.
"SAVEDESTRUCTOR_X(DESTRUCTORFUNC_t f, void *p)"
À la fin du *pseudo-bloc*, la fonction "f" est appelée avec l'argument de contexte implicite (le cas échéant), et "p" qui peut être NULL.

Notez que la *fin du pseudo-bloc courant* peut survenir beaucoup plus tard que la *fin de l'instruction courante*. Vous pourriez vouloir regarder la macro MORTALSVFUNC_X() à la place.

Soyez conscient que l'argument paramètre de la fonction destructeur diffère de celui de SAVEDESTRUCTOR_X() apparenté en ce sens qu'il DOIT être soit NULL soit un "SV*".

Notez que la *fin de l'instruction actuelle* peut survenir bien avant la *fin du pseudo-bloc actuel*. Vous pourriez souhaiter regarder à la place la macro SAVEDESTRUCTOR_X().

"MORTALDESTRUCTOR_SV(SV *coderef, SV *args)"
À la fin de *l'instruction actuelle*, la fonction Perl contenue dans "coderef" est appelée avec les arguments fournis (s'il y en a) dans "args". Voir la documentation de mortal_destructor_sv() pour les détails sur la façon dont le paramètre "args" est géré.

Notez que la *fin de l'instruction actuelle* peut survenir bien avant la *fin du pseudo-bloc actuel*. Si vous souhaitez appeler une fonction perl à la fin du pseudo-bloc actuel, vous devriez utiliser l'API SAVEDESTRUCTOR_X() à la place, ce qui nécessitera la création d'un wrapper C pour appeler la fonction Perl.

Sous-programmes

XSUBs et la pile d'arguments

Le mécanisme XSUB est un moyen simple pour les programmes Perl d'accéder aux sous-programmes C. Une routine XSUB aura une pile qui contient les arguments du programme Perl, et un moyen de mapper les structures de données Perl à un équivalent C.

Les arguments de la pile sont accessibles via la macro ST(n), qui retourne le *n*-ième argument de la pile. L'argument 0 est le premier argument passé dans l'appel de sous-programme Perl. Ces arguments sont des "SV*", et peuvent être utilisés partout où un "SV*" est utilisé.

La plupart du temps, la sortie de la routine C peut être gérée grâce à l'utilisation des directives RETVAL et OUTPUT. Cependant, il y a certains cas où la pile d'arguments n'est pas assez longue pour gérer toutes les valeurs de retour. Un exemple est l'appel POSIX tzname(), qui ne prend aucun argument, mais en retourne deux, les abréviations des fuseaux horaires standard et d'été.

Pour gérer cette situation, la directive PPCODE est utilisée et la pile est étendue en utilisant la macro :

EXTEND(SP, num);

où "SP" est la macro qui représente la copie locale du pointeur de pile, et "num" est le nombre d'éléments par lesquels la pile doit être étendue.

Maintenant qu'il y a de la place sur la pile, les valeurs peuvent y être ajoutées en utilisant la macro "PUSHs". Les valeurs ajoutées devront souvent être « mortelles » (Voir « Références et Mortalié ») :

PUSHs(sv_2mortal(newSViv(an_integer)))
PUSHs(sv_2mortal(newSVuv(an_unsigned_integer)))
PUSHs(sv_2mortal(newSVnv(a_double)))
PUSHs(sv_2mortal(newSVpv("Some String",0)))
/* Bien que le dernier exemple soit mieux écrit comme suit, plus
 * efficace : */
PUSHs(newSVpvs_flags("Some String", SVs_TEMP))

Et maintenant, le programme Perl appelant "tzname", les deux valeurs seront assignées comme suit :

($standard_abbrev, $summer_abbrev) = POSIX::tzname;

Une méthode alternative (et peut-être plus simple) pour ajouter des valeurs à la pile est d'utiliser la macro :

XPUSHs(SV*)

Cette macro ajuste automatiquement la pile pour vous, si nécessaire. Ainsi, vous n'avez pas besoin d'appeler "EXTEND" pour étendre la pile.

Malgré leurs suggestions dans les versions antérieures de ce document, les macros "(X)PUSH[iunp]" ne conviennent *pas* aux XSUBs qui retournent plusieurs résultats. Pour cela, soit s'en tenir aux macros "(X)PUSHs" montrées ci-dessus, soit utiliser les nouvelles macros "m(X)PUSH[iunp]" ; voir « Placer une valeur C sur la pile Perl ».

Pour plus d'informations, consultez perlxs et perlxstut.

Chargement automatique avec les XSUBs

Si une routine AUTOLOAD est une XSUB, comme avec les sous-programmes Perl, Perl place le nom entièrement qualifié du sous-programme chargé automatiquement dans la variable $AUTOLOAD du package de la XSUB.

Mais il place également les mêmes informations dans certains champs de la XSUB elle-même :

HV *stash           = CvSTASH(cv);
const char *subname = SvPVX(cv);
STRLEN name_length  = SvCUR(cv); /* en octets */
U32 is_utf8         = SvUTF8(cv);

SvPVX(cv) contient uniquement le nom du sous-programme lui-même, sans inclure le package. Pour une routine AUTOLOAD dans UNIVERSAL ou l'une de ses superclasses, CvSTASH(cv) retourne NULL lors d'un appel de méthode sur un package inexistant.

Note : La définition de $AUTOLOAD a cessé de fonctionner en 5.6.1, qui ne prenait pas du tout en charge les sous-programmes AUTOLOAD XS. Perl 5.8.0 a introduit l'utilisation des champs dans la XSUB elle-même. Perl 5.16.0 a restauré la définition de $AUTOLOAD. Si vous devez prendre en charge 5.8-5.14, utilisez les champs de la XSUB.

Placer une valeur C sur la pile Perl

Beaucoup d'opcodes (c'est une opération élémentaire dans la machine à pile interne de Perl) placent un SV* sur la pile. Cependant, par optimisation, le SV correspondant n'est (généralement) pas recréé à chaque fois. Les opcodes réutilisent des SV* spécialement assignés (*cibles*) qui ne sont (par conséquent) pas constamment libérés/créés.

Chacune des cibles est créée une seule fois (mais voir « Zones temporaires et récursion » ci-dessous), et lorsqu'un opcode doit placer un entier, un double ou une chaîne sur la pile, il se contente de définir les parties correspondantes de sa *cible* et de placer la *cible* sur la pile.

La macro pour placer cette cible sur la pile est "PUSHTARG", et elle est directement utilisée dans certains opcodes, ainsi qu'indirectement dans des myriades d'autres, qui l'utilisent via "(X)PUSH[iunp]".

Comme la cible est réutilisée, vous devez faire attention lorsque vous placez plusieurs valeurs sur la pile. Le code suivant ne fera pas ce que vous pensez :

XPUSHi(10);
XPUSHi(20);

Pile d'arguments

Les XSUBs et les codes Perl compilés utilisent une pile d'arguments pour passer des valeurs aux fonctions et aux opérations. Il existe plusieurs macros pour manipuler cette pile, y compris pour ajouter des valeurs à la pile.

Les macros "(X)PUSH[iunp]" sont utilisées pour pousser une valeur sur la pile d'arguments. Les suffixes "i", "u", "n" et "p" indiquent le type de la valeur (entier, non signé, nombre, chaîne de caractères). Par exemple, "XPUSHi(10)" pousse la valeur entière 10 sur la pile.

Si vous avez besoin de pousser plusieurs valeurs différentes, vous devriez soit utiliser les macros "(X)PUSHs", soit utiliser les nouvelles macros "m(X)PUSH[iunp]", dont aucune n'utilise "TARG". Les macros "(X)PUSHs" poussent simplement un SV* sur la pile, qui, comme noté dans "XSUBs et la pile d'arguments", devra souvent être "mortel". Les nouvelles macros "m(X)PUSH[iunp]" facilitent un peu cela en créant une nouvelle valeur mortelle pour vous (via "(X)PUSHmortal"), en la poussant sur la pile (en l'étendant si nécessaire dans le cas des macros "mXPUSH[iunp]"), puis en définissant sa valeur. Ainsi, au lieu d'écrire ceci pour "corriger" l'exemple ci-dessus :

XPUSHs(sv_2mortal(newSViv(10)))
XPUSHs(sv_2mortal(newSViv(20)))

vous pouvez simplement écrire :

mXPUSHi(10)
mXPUSHi(20)

Dans un ordre d'idées similaire, si vous utilisez "(X)PUSH[iunp]", vous aurez besoin d'un "dTARG" dans vos déclarations de variables pour que les macros "*PUSH*" puissent utiliser la variable locale "TARG". Voir aussi "dTARGET" et "dXSTARG".

Soyez prudent avec TARG : chaque appel non récursif de votre OP, ou XSUB pour dXSTARG, utilisera le même SV pour TARG à chaque appel, vous ne pouvez donc pas supposer que le SV est vierge car les résultats de l'appel précédent de votre OP ou XSUB peuvent toujours être dans TARG.

D'autres états tels qu'une version numérique mise en cache d'un PV ou la longueur UTF-8 mise en cache peuvent également être définis. Vous pouvez éviter les problèmes en utilisant les API sv_set*() normales au lieu d'essayer d'optimiser en manipulant directement le SV.

Pour les OPs qui implémentent l'optimisation "OA_TARGLEX", TARG peut être spécial d'autres manières, il peut y avoir des références à celui-ci, il pourrait être béni, lié, ou magique d'autres manières.

Vous ne devez pas utiliser TARG pour retourner une référence, car cette référence sera active jusqu'à la prochaine fois que l'OP ou XSUB s'exécutera non récursivement, ou jusqu'à la sortie de Perl.

Blocs-mémoire

La question demeure : quand les SVs qui sont des *cibles* pour les opcodes sont-ils créés ? La réponse est qu'ils sont créés lorsque l'unité actuelle - une sous-routine ou un fichier (pour les opcodes des instructions en dehors des sous-routines) - est compilée. Pendant ce temps, un tableau Perl anonyme spécial est créé, appelé bloc-mémoire pour l'unité courante.

Un bloc-mémoire conserve les SVs qui sont des variables lexicales pour l'unité courante et qui sont des cibles pour les opcodes. Une version précédente de ce document indiquait que l'on pouvait déduire qu'un SV réside dans un bloc-mémoire en regardant ses drapeaux : les variables lexicales ont "SVs_PADMY" défini, et les *cibles* ont "SVs_PADTMP" défini. Mais cela n'a jamais été entièrement vrai. "SVs_PADMY" pouvait être défini sur une variable qui ne résidait plus dans aucun bloc. Tandis que les *cibles* ont bien "SVs_PADTMP" défini, il peut aussi être défini sur des variables qui n'ont jamais résidé dans un bloc, mais qui agissent néanmoins comme des *cibles*. Depuis Perl 5.21.5, l'indicateur "SVs_PADMY" n'est plus utilisé et est défini à 0. SvPADMY() renvoie maintenant vrai pour tout ce qui n'a pas "SVs_PADTMP".

La correspondance entre les OPs et les *cibles* n'est pas du 1 pour 1. Différents OPs dans l'arbre de compilation de l'unité peuvent utiliser la même cible, si cela ne conflitait pas avec la durée de vie attendue du temporaire.

Blocs-mémoire et récursivité

En fait, il n'est pas vrai à 100% qu'une unité compilée contienne un pointeur vers le tableau AV du bloc-mémoire. En fait, elle contient un pointeur vers un AV d'un élément (initialement un), et cet élément est le tableau AV du bloc-mémoire. Pourquoi avons-nous besoin d'un niveau d'indirection supplémentaire ?

La réponse est la **récursivité**, et peut-être les **threads**. Ces deux éléments peuvent créer plusieurs pointeurs d'exécution pointant vers la même sous-routine. Pour que le fils de la sous-routine n'écrase pas les temporaires du parent de la sous-routine (dont la durée de vie couvre l'appel du fils), le parent et le fils devraient avoir des blocs-mémoire différents. (Et les variables lexicales devraient de toute façon être séparées !)

Ainsi, chaque sous-routine naît avec un tableau de blocs-mémoire (de longueur 1). À chaque entrée dans la sous-routine, on vérifie que la profondeur actuelle de la récursivité n'est pas supérieure à la longueur de ce tableau, et si c'est le cas, un nouveau bloc-mémoire est créé et poussé dans le tableau.

Les *cibles* sur ce bloc-mémoire sont des "undef", mais elles sont déjà marquées avec les bons indicateurs.

Allocation mémoire

Allocation

Toute mémoire destinée à être utilisée avec les fonctions de l'API Perl doit être manipulée à l'aide des macros décrites dans cette section. Les macros fournissent la transparence nécessaire entre les différences dans l'implémentation malloc réelle utilisée dans Perl. Ne mélangez jamais de pointeurs entre "Newx", "Renew", "Safefree" et les équivalents de *libc* "malloc", "realloc", "free". Ils ne proviennent pas du même pool mémoire ou allocateur. Soit une *SEGV* immédiate ou retardée se produira, soit des fuites de mémoire subtiles ou une corruption subtile du tas se produiront.

Les trois macros suivantes sont utilisées pour allouer initialement de la mémoire :

Newx(pointer, number, type);
Newxc(pointer, number, type, cast);
Newxz(pointer, number, type);

Le premier argument "pointer" doit être le nom d'une variable qui pointera vers la mémoire nouvellement allouée.

Les deuxième et troisième arguments "number" et "type" spécifient combien d'instances du type de structure de données spécifié doivent être allouées. L'argument "type" est passé à "sizeof". Le dernier argument de "Newxc", "cast", doit être utilisé si l'argument "pointer" est différent de l'argument "type".

Contrairement aux macros "Newx" et "Newxc", la macro "Newxz" appelle "memzero" pour remettre à zéro toute la mémoire nouvellement allouée.

Réallocation

Renew(pointer, number, type);
Renewc(pointer, number, type, cast);
Safefree(pointer)

Ces trois macros sont utilisées pour changer la taille d'un tampon mémoire ou pour libérer un bloc mémoire qui n'est plus nécessaire. Les arguments de "Renew" et "Renewc" correspondent à ceux de "New" et "Newc", à l'exception de l'absence de l'argument "magic cookie".

Déplacement

Move(source, dest, number, type);
Copy(source, dest, number, type);
Zero(dest, number, type);

Ces trois macros sont utilisées pour déplacer, copier ou mettre à zéro une mémoire préalablement allouée. Les arguments "source" et "dest" pointent vers les points de départ de la source et de la destination. Perl déplacera, copiera ou mettra à zéro "number" instances de la taille du type de structure de données "type" (en utilisant la fonction "sizeof").

PerlIO

Les versions de développement les plus récentes de Perl ont expérimenté la suppression de la dépendance de Perl vis-à-vis de la suite d'E/S standard "normale" et ont permis l'utilisation d'autres implémentations stdio. Cela implique la création d'une nouvelle couche d'abstraction qui appelle ensuite l'implémentation stdio avec laquelle Perl a été compilé. Tous les XSUBs devraient désormais utiliser les fonctions de la couche d'abstraction PerlIO et ne faire aucune supposition quant au type de stdio utilisé.

Pour une description complète de l'abstraction PerlIO, consultez perlapio.

Code compilé

Arbre de code

Ici, nous décrivons la forme interne à laquelle votre code est converti par Perl. Commençons par un exemple simple :

$a = $b + $c;

Ceci est converti en un arbre similaire à celui-ci :

       assign-to
     /           \
    +             $a
  /   \
$b     $c

(mais légèrement plus compliqué). Cet arbre reflète la manière dont Perl a analysé votre code, mais n'a rien à voir avec l'ordre d'exécution. Il y a un "fil" supplémentaire traversant les nœuds de l'arbre qui indique l'ordre d'exécution des nœuds. Dans notre exemple simplifié ci-dessus, il ressemble à ceci :

$b ---> $c ---> + ---> $a ---> assign-to

Mais avec l'arbre de compilation réel pour "$a = $b + $c", c'est différent : certains nœuds sont *optimisés et supprimés*. Par conséquent, bien que l'arbre réel contienne plus de nœuds que notre exemple simplifié, l'ordre d'exécution est le même que dans notre exemple.

Examen de l'arbre

Si votre Perl a été compilé pour le débogage (généralement fait avec "-DDEBUGGING" sur la ligne de commande "Configure"), vous pouvez examiner l'arbre compilé en spécifiant "-Dx" sur la ligne de commande Perl. La sortie prend plusieurs lignes par nœud, et pour "$b+$c", elle ressemble à ceci :

5           TYPE = add  ===> 6
            TARG = 1
            FLAGS = (SCALAR,KIDS)
            {
                TYPE = null  ===> (4)
                  (was rv2sv)
                FLAGS = (SCALAR,KID
S) { 3 TYPE = gvsv ===> 4 FLAGS = (SCALAR) GV = main::b } } { TYPE = null ===> (5) (était rv2sv) FLAGS = (SCALAR,KIDS) { 4 TYPE = gvsv ===> 5 FLAGS = (SCALAR) GV = main::c } }

Cet arbre contient 5 nœuds (un par spécificateur "TYPE"), dont seulement 3 n'ont pas été optimisés (un par nombre dans la colonne de gauche). Les enfants immédiats du nœud donné correspondent aux paires "{}" au même niveau d'indentation, donc cette liste correspond à l'arbre :

    add
  /     \
null    null
 |       |
gvsv    gvsv

L'ordre d'exécution est indiqué par les marques "===>", donc il est "3 4 5 6" (le nœud 6 n'est pas inclus dans la liste ci-dessus), c'est-à-dire "gvsv gvsv add whatever".

Chacun de ces nœuds représente un op, une opération fondamentale au sein du cœur de Perl. Le code qui implémente chaque opération se trouve dans les fichiers pp*.c ; la fonction qui implémente l'op de type "gvsv" est "pp_gvsv", et ainsi de suite. Comme le montre l'arbre ci-dessus, différents ops ont un nombre différent d'enfants : "add" est un opérateur binaire, comme on peut s'y attendre, et a donc deux enfants. Pour accueillir les différents nombres d'enfants, il existe différents types de structures de données d'op, et elles se lient de différentes manières.

Le type de structure d'op le plus simple est "OP" : il n'a pas d'enfants. Les opérateurs unaires, les "UNOP"s, ont un enfant, et celui-ci est pointé par le champ "op_first". Les opérateurs binaires ("BINOP"s) ont non seulement un champ "op_first" mais aussi un champ "op_last". Le type d'op le plus complexe est un "LISTOP", qui a un nombre quelconque d'enfants. Dans ce cas, le premier enfant est pointé par "op_first" et le dernier enfant par "op_last". Les enfants intermédiaires peuvent être trouvés en suivant itérativement le pointeur "OpSIBLING" du premier enfant au dernier (mais voir ci-dessous).

Il existe également d'autres types d'op : un "PMOP" contient une expression régulière et n'a pas d'enfants, et une "LOOP" peut ou non avoir des enfants. Si le champ "op_children" est non nul, elle se comporte comme un "LISTOP". Pour compliquer les choses, si un "UNOP" est en fait un op "null" après optimisation (voir "Passe de compilation 2 : propagation du contexte"), il aura toujours des enfants conformément à son type précédent.

Enfin, il existe un "LOGOP", ou op logique. Comme un "LISTOP", il a un ou plusieurs enfants, mais il n'a pas de champ "op_last" : vous devez donc suivre "op_first" puis la chaîne "OpSIBLING" elle-même pour trouver le dernier enfant. À la place, il a un champ "op_other", qui est comparable au champ "op_next" décrit ci-dessous, et représente un chemin d'exécution alternatif. Les opérateurs comme "and", "or" et "?" sont des "LOGOP"s. Notez qu'en général, "op_other" peut ne pas pointer vers l'un des enfants directs du "LOGOP".

À partir de la version 5.21.2, les perls compilés avec la définition expérimentale "-DPERL_OP_PARENT" ajoutent un drapeau booléen supplémentaire pour chaque op, "op_moresib". Lorsqu'il n'est pas défini, cela indique qu'il s'agit du dernier op dans une chaîne "OpSIBLING". Cela libère le champ "op_sibling" du dernier frère pour pointer vers l'op parent. Dans cette compilation, ce champ est également renommé "op_sibparent" pour refléter son rôle conjoint. La macro OpSIBLING(o) encapsule ce comportement spécial, et retourne toujours NULL sur le dernier frère. Avec cette compilation, la fonction op_parent(o) peut être utilisée pour trouver le parent de n'importe quel op. Ainsi, pour une compatibilité ascendante, vous devriez toujours utiliser la macro OpSIBLING(o) plutôt que d'accéder directement à "op_sibling".

Une autre façon d'examiner l'arbre est d'utiliser un module de backend de compilateur, tel que B::Concise.

Passe de compilation 1 : routines de vérification

L'arbre est créé par le compilateur pendant que le code yacc lui fournit les constructions qu'il reconnaît. Étant donné que yacc fonctionne de bas en haut, il en va de même pour la première passe de la compilation de Perl.

Ce qui rend cette passe intéressante pour les développeurs Perl, c'est que certaines optimisations peuvent être effectuées lors de cette passe. Il s'agit d'optimisations par les soi-disant "routines de vérification". La correspondance entre les noms des nœuds et les routines de vérification correspondantes est décrite dans opcode.pl (n'oubliez pas d'exécuter "make regen_headers" si vous modifiez ce fichier).

Une routine de vérification est appelée lorsque le nœud est entièrement construit, à l'exception du fil d'exécution de l'ordre d'exécution. Comme il n'y a pas de liens de retour vers le nœud en cours de construction à ce moment-là, on peut effectuer la plupart des opérations sur le nœud de niveau supérieur, y compris sa libération et/ou la création de nouveaux nœuds au-dessus/en dessous.

La routine de vérification renvoie le nœud qui doit être inséré dans l'arbre (si le nœud de niveau supérieur n'a pas été modifié, la routine de vérification renvoie son argument).

Par convention, les routines de vérification ont des noms "ck_*". Elles sont généralement appelées depuis les sous-routines "new*OP" (ou "convert") (qui sont à leur tour appelées depuis perly.y).

Passe de compilation 1a : repliement des constantes

Immédiatement après l'appel de la routine de vérification, le nœud renvoyé est vérifié pour être exécutable au moment de la compilation. S'il l'est (la valeur est jugée constante), il est immédiatement exécuté, et un nœud constant avec la "valeur de retour" du sous-arbre correspondant est substitué à la place. Le sous-arbre est supprimé.

Si le repliement des constantes n'a pas été effectué, le fil d'exécution de l'ordre d'exécution est créé.

Passe de compilation 2 : propagation du contexte

Lorsqu'un contexte pour une partie de l'arbre de compilation est connu, il est propagé vers le bas dans l'arbre. À ce moment, le contexte peut avoir 5 valeurs (au lieu de 2 pour le contexte d'exécution) : vide, booléen, scalaire, liste et lvalue. Contrairement à la passe 1, cette passe est traitée de haut en bas : le contexte d'un nœud détermine le contexte de ses enfants.

Des optimisations supplémentaires dépendant du contexte sont effectuées à ce moment-là. Comme l'arbre de compilation contient des références inverses (via les pointeurs de "fil d'exécution") à ce stade, les nœuds ne peuvent pas être free()d maintenant. Pour permettre aux nœuds d'être optimisés à ce stade, de tels nœuds sont null()ifiés au lieu d'être free()s (c'est-à-dire que leur type est changé en OP_NULL).

Passe de compilation 3 : optimisation en gros plan (peephole)

Une fois l'arbre de compilation d'une sous-routine (ou d'un "eval" ou d'un fichier) créé, une passe supplémentaire est effectuée sur le code. Cette passe n'est ni de haut en bas, ni de bas en haut, mais dans l'ordre d'exécution (avec des complications supplémentaires pour les conditions). Les optimisations effectuées à ce stade sont soumises aux mêmes restrictions que dans la passe 2.

Les optimisations en gros plan sont effectuées en appelant la fonction pointée par la variable globale "PL_peepp". Par défaut, "PL_peepp" appelle simplement la fonction pointée par la variable globale "PL_rpeepp". Par défaut, celle-ci effectue des réparations et des optimisations d'op de base le long de la chaîne d'op de l'ordre d'exécution, et appelle récursivement "PL_rpeepp" pour chaque chaîne latérale d'ops (résultant de conditions). Les extensions peuvent fournir des optimisations ou des réparations supplémentaires, en se greffant sur la phase par sous-routine ou la phase récursive, comme suit :

static peep_t prev_peepp;
static void my_peep(pTHX_ OP *o)
{
    /* optimisation personnalisée par sous-routine va ici */
    prev_peepp(aTHX_ o);
    /* optimisation personnalisée par sous-routine peut aussi aller ici */
}
BOOT:
    prev_peepp = PL_peepp;
    PL_peepp = my_peep;
static peep_t prev_rpeepp;
static void my_rpeep(pTHX_ OP *first)
{
    OP *o = first, *t = first;
    for(; o = o->op_next, t = t->op_next) {
        /* optimisation personnalisée par op va ici */
        o = o->op_next;
        if (!o || o == t) break;
        /* optimisation personnalisée par op va aussi ici */
    }
    prev_rpeepp(aTHX_ orig_o);
}
BOOT:
    prev_rpeepp = PL_rpeepp;
    PL_rpeepp = my_rpeep;

runops enfichables

L'arbre de compilation est exécuté dans une fonction runops. Il existe deux fonctions runops, dans run.c et dans dump.c. "Perl_runops_debug" est utilisée avec DEBUGGING et "Perl_runops_standard" est utilisée sinon. Pour un contrôle fin de l'exécution de l'arbre de compilation, il est possible de fournir votre propre fonction runops.

Il est probablement préférable de copier l'une des fonctions runops existantes et de la modifier selon vos besoins. Ensuite, dans la section BOOT de votre fichier XS, ajoutez la ligne :

PL_runops = my_runops;

Cette fonction doit être aussi efficace que possible pour que vos programmes s'exécutent le plus rapidement possible.

Hooks de portée au moment de la compilation

À partir de Perl 5.14, il est possible de

Accrocher au mécanisme de portée lexicale au moment de la compilation

Utilisez "Perl_blockhook_register". Cela s'utilise comme suit :

STATIC void my_start_hook(pTHX_ int full);
STATIC BHK my_hooks;
BOOT:
    BhkENTRY_set(&my_hooks, bhk_start, my_start_hook);
    Perl_blockhook_register(aTHX_ &my_hooks);

Ceci organisera l'appel de "my_start_hook" au début de la compilation de chaque portée lexicale. Les crochets disponibles sont :

"void bhk_start(pTHX_ int full)"
Ceci est appelé juste après le début d'une nouvelle portée lexicale. Notez que le code Perl comme 
if ($x) { ... }

crée deux portées : la première commence à la "(" et a "full == 1", la seconde commence à la "{" et a "full == 0". Les deux se terminent à la "}", donc les appels à "start" et "pre"/"post_end" correspondra. Tout ce qui est poussé sur la pile de sauvegarde par ce crochet sera dépilé juste avant la fin de la portée (entre les crochets "pre_" et "post_end", en fait).

"void bhk_pre_end(pTHX_ OP **o)"
Ceci est appelé à la fin d'une portée lexicale, juste avant de dérouler la pile. o est la racine de l'arbre d'opérations représentant la portée ; c'est un double pointeur afin que vous puissiez remplacer l'OP si nécessaire.
"void bhk_post_end(pTHX_ OP **o)"
Ceci est appelé à la fin d'une portée lexicale, juste après avoir déroulé la pile. o est comme ci-dessus. Notez qu'il est possible que les appels à "pre_" et "post_end" s'imbriquent, s'il y a quelque chose sur la pile de sauvegarde qui appelle l'évaluation de chaînes.
"void bhk_eval(pTHX_ OP *const o)"
Ceci est appelé juste avant de commencer à compiler un "eval STRING", "do FILE", "require" ou "use", après que l'évaluation a été configurée. o est l'OP qui a demandé l'évaluation, et sera normalement un "OP_ENTEREVAL", "OP_DOFILE" ou "OP_REQUIRE".

Une fois que vous avez vos fonctions de crochet, vous avez besoin d'une structure "BHK" pour y placer vos fonctions. Il est préférable de l'allouer statiquement, car il n'y a aucun moyen de la libérer une fois enregistrée. Les pointeurs de fonction doivent être insérés dans cette structure à l'aide de la macro "BhkENTRY_set", qui définira également les drapeaux indiquant quelles entrées sont valides. Si vous devez allouer votre "BHK" dynamiquement pour une raison quelconque, assurez-vous de le mettre à zéro avant de commencer.

Une fois enregistrés, il n'existe aucun mécanisme pour désactiver ces crochets, donc si cela est nécessaire, vous devrez le faire vous-même. Une entrée dans "%^H" est probablement la meilleure façon, afin que l'effet soit borné à la portée lexicale ; cependant, il est également possible d'utiliser les macros "BhkDISABLE" et "BhkENABLE" pour activer et désactiver temporairement les entrées. Vous devez également être conscient qu'en général au moins une portée sera ouverte avant que votre extension ne soit chargée, vous verrez donc certaines paires "pre"/"post_end" qui n'avaient pas de "start" correspondant.

Examiner les structures de données internes avec les fonctions "dump"

Pour faciliter le débogage, le fichier source dump.c contient un certain nombre de fonctions qui produisent une sortie formatée des structures de données internes.

La plus couramment utilisée de ces fonctions est "Perl_sv_dump" ; elle est utilisée pour vider les SV, AV, HV et CV. Le module "Devel::Peek" appelle "sv_dump" pour produire une sortie de débogage à partir de l'espace Perl, donc les utilisateurs de ce module devraient déjà être familiers avec son format.

"Perl_op_dump" peut être utilisé pour vider une structure "OP" ou l'une de ses dérivées, et produit une sortie similaire à "perl -Dx" ; en fait, "Perl_dump_eval" videra la racine principale du code en cours d'évaluation, exactement comme "-Dx".

D'autres fonctions utiles sont "Perl_dump_sub", qui transforme un "GV" en un arbre d'opérations, "Perl_dump_packsubs" qui appelle "Perl_dump_sub" sur toutes les sous-routines d'un paquet comme ceci : (Heureusement, ce sont toutes des xsubs, donc il n'y a pas d'arbre d'opérations)

SUB UNIVERSAL::can = (xsub 0x811f50c 0)
SUB UNIVERSAL::isa = (xsub 0x811f304 0)

et "Perl_dump_all", qui vide toutes les sous-routines du stash et l'arbre d'opérations de la racine principale.

Comment les multiples interpréteurs et la concurrence sont pris en charge

Contexte et MULTIPLICITY

L'interpréteur Perl peut être considéré comme une boîte fermée : il possède une API pour lui fournir du code ou pour le faire agir, mais il a aussi des fonctions pour son propre usage. Cela ressemble beaucoup à un objet, et il existe un moyen de construire Perl de manière à pouvoir avoir plusieurs interpréteurs, avec un interpréteur représenté soit par une structure C, soit à l'intérieur d'une structure spécifique au thread. Ces structures contiennent tout le contexte, l'état de cet interpréteur.

La macro qui contrôle la saveur majeure de la construction de Perl est MULTIPLICITY. La construction MULTIPLICITY possède une structure C qui regroupe tout l'état de l'interpréteur, qui est passé à diverses fonctions Perl comme premier argument « caché ». MULTIPLICITY rend possibles les interpréteurs Perl multi-threads (avec le modèle de threading ithreads, lié à la macro USE_ITHREADS.)

PERL_IMPLICIT_CONTEXT est un synonyme hérité pour MULTIPLICITY.

Pour voir si vous avez des données non constantes, vous pouvez utiliser un "nm" compatible BSD (ou GNU) :

nm libperl.a | grep -v ' [TURtr] '

Si cela affiche des symboles "D" ou "d" (ou éventuellement "C" ou "c"), vous avez des données non constantes. Les symboles que le "grep" a supprimés sont les suivants : "Tt" sont le texte, ou code, les "Rr" sont des données en lecture seule (constantes), et le "U" est <non défini>, symboles externes référencés.

Le test t/porting/libperl.t effectue ce type de vérification de cohérence de symboles sur "libperl.a".

Tout cela nécessite évidemment un moyen pour les fonctions internes de Perl d'être soit des sous-routines prenant une sorte de structure comme premier argument, soit des sous-routines ne prenant rien comme premier argument. Pour permettre ces deux manières très différentes de construire l'interpréteur, le code source de Perl (comme il le fait dans tant d'autres situations) utilise intensivement des macros et des conventions de nommage de sous-routines.

Premier problème : décider quelles fonctions seront des fonctions d'API publiques et quelles seront privées. Toutes les fonctions dont le nom commence par "S_" sont privées (pensez « S » pour « secret » ou « statique »). Toutes les autres fonctions commencent par « Perl_ », mais ce n'est pas parce qu'une fonction commence par « Perl_ » qu'elle fait partie de l'API. (Voir « Fonctions internes ».) Le moyen le plus simple d'être sûr qu'une fonction fait partie de l'API est de trouver son entrée dans perlapi. Si elle existe dans perlapi, elle fait partie de l'API. Si elle n'existe pas, et que vous pensez qu'elle devrait (c'est-à-dire que vous en avez besoin pour votre extension), soumettez un problème sur https://github.com/Perl/perl5/issues en expliquant pourquoi vous pensez qu'elle devrait l'être.

Deuxième problème : il doit y avoir une syntaxe permettant aux mêmes déclarations et appels de sous-routines de passer une structure comme premier argument, ou de ne rien passer. Pour résoudre cela, les sous-routines sont nommées et déclarées d'une manière particulière. Voici un début typique d'une fonction statique utilisée dans les entrailles de Perl :

STATIC void
S_incline(pTHX_ char *s)

STATIC devient « static » en C, et pourrait être #define'd à rien dans certaines configurations à l'avenir.

Une fonction publique (c'est-à-dire faisant partie de l'API interne, mais pas nécessairement approuvée pour une utilisation dans les extensions) commence comme ceci :

void
Perl_sv_setiv(pTHX_ SV* dsv, IV num)

"pTHX_" est l'une d'un certain nombre de macros (dans perl.h) qui cachent les détails du contexte de l'interpréteur. THX signifie « thread », « this », ou « thingy », selon le cas. (Et non, George Lucas n'est pas impliqué. :-) Le premier caractère pourrait être 'p' pour un prototype, 'a' pour un argument, ou 'd' pour une déclaration, donc nous avons "pTHX", "aTHX" et "dTHX", et leurs variantes.

Lorsque Perl est construit sans options qui définissent MULTIPLICITY, il n'y a pas de premier argument contenant le contexte de l'interpréteur. Le trait de soulignement final dans la macro pTHX_ indique que l'expansion de la macro nécessite une virgule après l'argument de contexte car d'autres arguments la suivent. Si MULTIPLICITY n'est pas défini, pTHX_ est ignoré, et la sous-routine n'est pas prototypée pour prendre l'argument supplémentaire. La forme de la macro sans le trait de soulignement final est utilisée lorsqu'il n'y a pas d'arguments explicites supplémentaires.

Lorsqu'une fonction du cœur appelle une autre fonction, elle doit passer le contexte. Ceci est normalement caché via des macros. Considérons "sv_setiv". Elle se développe en quelque chose comme ceci :

#ifdef MULTIPLICITY
  #define sv_setiv(a,
b) Perl_sv_setiv(aTHX_ a, b) /* ne peut pas faire cela pour les fonctions vararg, voir ci-dessous */ #else #define sv_setiv Perl_sv_setiv #endif

Cela fonctionne bien, et signifie que les auteurs XS peuvent joyeusement écrire :

sv_setiv(foo, bar);

et cela fonctionnera toujours sous tous les modes dans lesquels Perl a pu être compilé.

Cela ne fonctionne pas aussi proprement pour les fonctions varargs, cependant, car les macros impliquent que le nombre d'arguments est connu à l'avance. Au lieu de cela, nous devons soit les épeler entièrement, en passant "aTHX_" comme premier argument (le cœur de Perl a tendance à faire cela avec des fonctions comme Perl_warner), soit utiliser une version sans contexte.

La version sans contexte de Perl_warner s'appelle Perl_warner_nocontext, et ne prend pas d'argument supplémentaire. Au lieu de cela, elle fait "dTHX;" pour obtenir le contexte à partir du stockage local au thread. Nous avons défini "#define warner Perl_warner_nocontext" afin que les extensions bénéficient de la compatibilité source au détriment des performances. (Passer un argument est moins coûteux que de le récupérer depuis le stockage local au thread.)

Vous pouvez ignorer [pad]THXx lors de la consultation des en-têtes/sources de Perl. Ceux-ci sont strictement destinés à être utilisés dans le cœur du programme. Les extensions et les embarqueurs n'ont besoin de connaître que [pad]THX.

Alors, qu'est-il arrivé à dTHR ?

"dTHR" a été introduit dans perl 5.005 pour prendre en charge l'ancien modèle de thread. L'ancien modèle de thread utilise maintenant le mécanisme "THX" pour passer les pointeurs de contexte, donc "dTHR" n'est plus utile. Perl 5.6.0 et versions ultérieures le conservent pour la compatibilité source ascendante, mais il est défini comme une opération nulle.

Comment utiliser tout cela dans les extensions ?

Voir également "Dealing with embedded perls and threads" dans perlclib.

Lorsque Perl est construit avec MULTIPLICITY, les extensions qui appellent des fonctions de l'API Perl devront passer l'argument de contexte initial d'une manière ou d'une autre. La difficulté est que vous devrez l'écrire de telle sorte que l'extension compile toujours lorsque Perl n'a pas été construit avec MULTIPLICITY activé.

Il y a trois façons de faire cela. Premièrement, la manière facile mais inefficace, qui est aussi la manière par défaut, afin de maintenir la compatibilité source avec les extensions : chaque fois que XSUB.h est inclus (#included), il redéfinit les macros aTHX et aTHX_ pour appeler une fonction qui retournera le contexte. Ainsi, quelque chose comme :

sv_setiv(sv, num);

dans votre extension se traduira par ceci lorsque MULTIPLICITY est effectif :

Perl_sv_setiv(Perl_get_context(), sv, num);

ou par ceci sinon :

Perl_sv_setiv(sv, num);

Vous n'avez rien de nouveau à faire dans votre extension pour obtenir cela ; comme la bibliothèque Perl fournit Perl_get_context(), tout fonctionnera.

La deuxième manière, plus efficace, est d'utiliser le modèle suivant pour votre Foo.xs :

#define PERL_NO_GET_CONTEXT     /* nous voulons de l'efficacité */
#include "EXTERN.h"
#include "perl.h"
#include "XSUB.h"
STATIC void my_private_function(int arg1, int arg2);
STATIC void
my_private_function(int arg1, int arg2)
{
    dTHX;       /* récupérer le contexte */
    ... appeler de nombreuses fonctions de l'API Perl ...
}

Notez que les deux seules modifications par rapport à la manière normale d'écrire une extension sont l'ajout d'un "#define PERL_NO_GET_CONTEXT" avant d'inclure les en-têtes Perl, suivi d'une déclaration "dTHX;" au début de chaque fonction qui appellera l'API Perl. (Vous saurez quelles fonctions en ont besoin, car le compilateur C se plaindra qu'il y a un identifiant non déclaré dans ces fonctions.) Aucune modification n'est nécessaire pour les XSUB eux-mêmes, car la macro XS() est correctement définie pour passer le contexte implicite si nécessaire.

La troisième manière, encore plus efficace, est d'imiter la façon dont c'est fait à l'intérieur des entrailles de Perl :

#define PERL_NO_GET_CONTEXT     /* nous voulons de l'efficacité */
#include "EXTERN.h"
#include "perl.h"
#include "XSUB.h"
/* pTHX_ n'est nécessaire que pour les fonctions qui appellent l'API Perl */
STATIC void my_private_function(pTHX_ int arg1, int arg2);
STATIC void
my_private_function(pTHX_ int arg1, int arg2)
{
    /* dTHX; n'est pas nécessaire ici, car THX est un argument */
    ... appeler les fonctions de l'API Perl ...
}

Cette implémentation n'a jamais besoin de récupérer le contexte via un appel de fonction, car il est toujours passé comme argument supplémentaire. Selon vos besoins de simplicité ou d'efficacité, vous pouvez mélanger librement les deux approches précédentes.

N'ajoutez jamais de virgule après "pTHX" vous-même - utilisez toujours la forme de la macro avec le trait de soulignement pour les fonctions qui prennent des arguments explicites, ou la forme sans argument pour les fonctions sans arguments explicites.

Dois-je faire quelque chose de spécial si j'appelle Perl depuis plusieurs threads ?

Si vous créez des interpréteurs dans un thread, puis que vous les appelez dans un autre, vous devez vous assurer que la propre slot de stockage local aux threads (TLS) de Perl est correctement initialisée dans chacun de ces threads.

Les fonctions d'API "perl_alloc" et "perl_clone" définiront automatiquement la slot TLS à l'interpréteur qu'elles ont créé, de sorte qu'il n'est pas nécessaire de faire quoi que ce soit de spécial si l'interpréteur est toujours accédé dans le même thread qui l'a créé, et que ce thread n'a créé ni appelé d'autres interpréteurs par la suite. Si ce n'est pas le cas, vous devez définir la slot TLS du thread avant d'appeler des fonctions de l'API Perl sur cet interpréteur particulier. Cela se fait en appelant la macro "PERL_SET_CONTEXT" dans ce thread comme première chose que vous faites :

/* faire ceci avant toute autre chose avec some_perl */
PERL_SET_CONTEXT(some_perl);
... d'autres appels à l'API Perl sur some_perl vont ici ...

(Vous pouvez toujours obtenir le contexte actuel via "PERL_GET_CONTEXT".)

Plans futurs et PERL_IMPLICIT_SYS

Tout comme MULTIPLICITY fournit un moyen de regrouper tout ce que l'interpréteur sait sur lui-même et de le transmettre, il est également prévu de permettre à l'interpréteur de regrouper tout ce qu'il sait sur l'environnement dans lequel il s'exécute. Ceci est activé avec la macro PERL_IMPLICIT_SYS. Actuellement, cela ne fonctionne qu'avec USE_ITHREADS sous Windows.

Cela permet de fournir un pointeur supplémentaire (appelé environnement "hôte") pour tous les appels système. Cela permet à tout le matériel système de maintenir son propre état, divisé en sept structures C. Ce sont de minces wrappers autour des appels système habituels (voir win32/perllib.c) pour l'exécutable Perl par défaut, mais pour un hôte plus ambitieux (comme celui qui ferait l'émulation de fork()) tout le travail supplémentaire nécessaire pour prétendre que différents interpréteurs sont en fait différents "processus", serait fait ici.

Le moteur/interpréteur Perl et l'hôte sont des entités orthogonales. Il pourrait y avoir un ou plusieurs interpréteurs dans un processus, et un ou plusieurs "hôtes", avec une association libre entre eux.

Fonctions internes

Toutes les fonctions internes de Perl qui seront exposées au monde extérieur sont préfixées par "Perl_" afin qu'elles n'entrent pas en conflit avec les fonctions XS ou les fonctions utilisées dans un programme dans lequel Perl est embarqué. De même, toutes les variables globales commencent par "PL_". (Par convention, les fonctions statiques commencent par "S_".)

À l'intérieur du cœur de Perl ("PERL_CORE" défini), vous pouvez accéder aux fonctions soit avec, soit sans le préfixe "Perl_", grâce à un tas de defines qui se trouvent dans embed.h. Notez que le code d'extension ne doit *pas* définir "PERL_CORE" ; cela expose les détails internes complets de Perl, et est susceptible de provoquer des erreurs dans les XS à chaque nouvelle version de Perl.

Le fichier embed.h est généré automatiquement à partir de embed.pl et embed.fnc. embed.pl crée également les fichiers d'en-tête de prototypage pour les fonctions internes, génère la documentation et de nombreuses autres petites choses. Il est important que lorsque vous ajoutez une nouvelle fonction au cœur ou que vous modifiez une fonction existante, vous modifiez également les données dans la table de embed.fnc. Voici un exemple d'entrée de cette table :

Apd |SV**   |av_fetch   |AV* ar|I32 key|I32 lval

La première colonne est un ensemble d'indicateurs, la seconde colonne le type de retour, la troisième colonne le nom. Les colonnes suivantes sont les arguments. Les indicateurs sont documentés en haut de embed.fnc.

Si vous modifiez embed.pl ou embed.fnc, vous devrez exécuter "make regen_headers" pour forcer une reconstruction de embed.h et d'autres fichiers auto-générés.

Le contenu des SV peut être imprimé en utilisant le format "SVf", comme suit :

Perl_croak(aTHX_ "This croaked because: %" SVf "\n", SVfARG(err_msg))

Gestion des exceptions

Il existe quelques macros pour effectuer une gestion très basique des exceptions dans les modules XS. Vous devez définir "NO_XSLOCKS" avant d'inclure XSUB.h pour pouvoir utiliser ces macros :

#define NO_XSLOCKS
#include "XSUB.h"

Vous pouvez utiliser ces macros si vous appelez du code qui peut "croak" (lever une exception), mais vous devez effectuer un nettoyage avant de rendre le contrôle à Perl. Par exemple :

dXCPT;    /* met en place les variables nécessaires */
XCPT_TRY_START {
  code_that_may_croak();
} XCPT_TRY_END
XCPT_CATCH
{
  /* faire le nettoyage ici */
  XCPT_RETHROW;
}

Notez que vous devez toujours relancer une exception qui a été capturée. En utilisant ces macros, il n'est pas possible de simplement capturer l'exception et de l'ignorer. Si vous devez ignorer l'exception, vous devez utiliser la fonction "call_*".

L'avantage d'utiliser les macros ci-dessus est que vous n'avez pas à mettre en place une fonction supplémentaire pour "call_*", et que l'utilisation de ces macros est plus rapide que l'utilisation de "call_*".

Support Unicode

Perl 5.6.0 a introduit le support Unicode. Il est important pour les porteurs et les auteurs XS de comprendre ce support et de s'assurer que le code qu'ils écrivent ne corrompt pas les données Unicode.

Qu'est-ce que l'Unicode, au fait ?

Dans les temps anciens, moins éclairés, nous utilisions tous l'ASCII. La plupart d'entre nous, en tout cas. Le gros problème avec l'ASCII est qu'il est américain. Eh bien, non, ce n'est pas vraiment le problème ; le problème est qu'il n'est pas particulièrement utile pour les personnes qui n'utilisent pas l'alphabet romain. Ce qui se passait autrefois, c'est que des langues particulières plaçaient leur propre alphabet dans la plage supérieure de la séquence, entre 128 et 255. Bien sûr, nous nous sommes alors retrouvés avec beaucoup de variantes qui n'étaient pas tout à fait ASCII, et le but même d'en faire un standard était perdu.

Pire encore, si vous avez une langue comme le chinois ou le japonais qui a des centaines ou des milliers de caractères, alors vous ne pouvez vraiment pas les faire rentrer dans seulement 256, donc ils ont dû oublier l'ASCII complètement, et construire leurs propres systèmes utilisant

ng paires de nombres pour faire référence à un seul caractère.

Pour résoudre ce problème, certaines personnes ont formé Unicode, Inc. et ont produit un nouvel ensemble de caractères contenant tous les caractères auxquels vous pouvez penser et plus encore. Il existe plusieurs façons de représenter ces caractères, et celle que Perl utilise s'appelle UTF-8. UTF-8 utilise un nombre variable d'octets pour représenter un caractère. Vous pouvez en apprendre davantage sur Unicode et le modèle Unicode de Perl dans perlunicode.

(Sur les plateformes EBCDIC, Perl utilise à la place UTF-EBCDIC, qui est une forme d'UTF-8 adaptée aux plateformes EBCDIC. Ci-dessous, nous parlons simplement d'UTF-8. UTF-EBCDIC est comme UTF-8, mais les détails sont différents. Les macros vous cachent les différences, rappelez-vous simplement que les nombres et les modèles de bits spécifiques présentés ci-dessous différeront en UTF-EBCDIC.)

Comment puis-je reconnaître une chaîne UTF-8 ?

Vous ne pouvez pas. C'est parce que les données UTF-8 sont stockées en octets, tout comme les données non-UTF-8. Le caractère Unicode 200, (0xC8 pour les amateurs d'hexadécimal) E majuscule avec accent grave, est représenté par les deux octets "v196.172". Malheureusement, la chaîne non-Unicode "chr(196).chr(172)" a également cette séquence d'octets. Vous ne pouvez donc pas le dire juste en regardant -- c'est ce qui fait de l'entrée Unicode un problème intéressant.

En général, vous devez soit savoir à quoi vous avez affaire, soit deviner. La fonction API "is_utf8_string" peut aider ; elle vous dira si une chaîne ne contient que des caractères UTF-8 valides, et les chances qu'une chaîne non-UTF-8 ressemble à du UTF-8 valide deviennent très faibles très rapidement avec l'augmentation de la longueur de la chaîne. Caractère par caractère, "isUTF8_CHAR" vous dira si le caractère actuel d'une chaîne est du UTF-8 valide.

Comment l'UTF-8 représente-t-il les caractères Unicode ?

Comme mentionné ci-dessus, UTF-8 utilise un nombre variable d'octets pour stocker un caractère. Les caractères de valeurs 0...127 sont stockés en un seul octet, tout comme le bon vieil ASCII. Le caractère 128 est stocké sous forme de "v194.128" ; cela continue jusqu'au caractère 191, qui est "v194.191". Maintenant, nous avons épuisé les bits (191 est binaire 10111111), nous passons donc à la suite ; le caractère 192 est "v195.128". Et ainsi de suite, passant à trois octets à partir du caractère 2048. "Unicode Encodings" dans perlunicode contient des illustrations de la façon dont cela fonctionne.

En supposant que vous sachiez que vous avez affaire à une chaîne UTF-8, vous pouvez découvrir la longueur du premier caractère avec la macro "UTF8SKIP" :

char *utf = "\305\233\340\240\201";
I32 len;
len = UTF8SKIP(utf); /* len vaut 2 ici */
utf += len;
len = UTF8SKIP(utf); /* len vaut 3 ici */

Une autre façon de sauter des caractères dans une chaîne UTF-8 est d'utiliser "utf8_hop", qui prend une chaîne et un nombre de caractères à sauter. Cependant, vous êtes seul responsable de la vérification des limites, alors ne l'utilisez pas à la légère.

Tous les octets d'un caractère UTF-8 multi-octets auront le bit de poids fort défini, vous pouvez donc tester si vous devez faire quelque chose de spécial avec ce caractère comme ceci (le UTF8_IS_INVARIANT() est une macro qui teste si l'octet est encodé comme un seul octet même en UTF-8) :

U8 *utf;     /* Initialisez ceci pour pointer vers le début de la
                séquence à convertir */
U8 *utf_end; /* Initialisez ceci à 1 au-delà de la fin de la séquence
                pointée par 'utf' */
UV uv;       /* Point de code retourné ; note : un UV, pas un U8, pas un
                char */
STRLEN len; /* Longueur du caractère retournée en octets */
if (!UTF8_IS_INVARIANT(*utf))
    /* Doit être traité comme UTF-8 */
    uv = utf8_to_uvchr_buf(utf, utf_end, &len);
else
    /* OK pour traiter ce caractère comme un octet */
    uv = *utf;

Vous pouvez également voir dans cet exemple que nous utilisons "utf8_to_uvchr_buf" pour obtenir la valeur du caractère ; la fonction inverse "uvchr_to_utf8" est disponible pour convertir un UV en UTF-8 :

if (!UVCHR_IS_INVARIANT(uv))
    /* Doit être traité comme UTF8 */
    utf8 = uvchr_to_utf8(utf8, uv);
else
    /* OK pour traiter ce caractère comme un octet */
    *utf8++ = uv;

Vous **devez** convertir les caractères en UV en utilisant les fonctions ci-dessus si vous vous trouvez dans une situation où vous devez faire correspondre des caractères UTF-8 et non-UTF-8. Vous ne pouvez pas sauter les caractères UTF-8 dans ce cas. Si vous le faites, vous perdrez la capacité de faire correspondre des caractères non-UTF-8 à bit élevé ; par exemple, si votre chaîne UTF-8 contient "v196.172", et que vous sautez ce caractère, vous ne pourrez jamais faire correspondre un chr(200) dans une chaîne non-UTF-8. Alors ne faites pas cela !

(Notez que nous n'avons pas à tester les caractères invariants dans les exemples ci-dessus. Les fonctions fonctionnent sur n'importe quelle entrée UTF-8 bien formée. C'est juste que c'est plus rapide d'éviter les frais généraux de fonction quand ce n'est pas nécessaire.)

Comment Perl stocke-t-il les chaînes UTF-8 ?

Actuellement, Perl traite les chaînes UTF-8 et les chaînes non-UTF-8 légèrement différemment. Un drapeau dans le SV, "SVf_UTF8", indique que la chaîne est encodée en interne en UTF-8. Sans lui, la valeur octet est le numéro de point de code et vice versa. Ce drapeau n'est significatif que si le SV est "SvPOK" ou immédiatement après la stringification via "SvPV" ou une macro similaire. Vous pouvez vérifier et manipuler ce drapeau avec les macros suivantes :

SvUTF8(sv)
SvUTF8_on(sv)
SvUTF8_off(sv)

Ce drapeau a un effet important sur le traitement des chaînes par Perl : si les données UTF-8 ne sont pas correctement distinguées, les expressions régulières, "length", "substr" et d'autres opérations sur les chaînes auront des résultats indésirables (incorrects).

Le problème survient lorsque vous avez, par exemple, une chaîne qui n'est pas marquée comme UTF-8 et qui contient une séquence d'octets qui pourrait être de l'UTF-8 -- surtout lors de la combinaison de chaînes non-UTF-8 et UTF-8.

N'oubliez jamais que le drapeau "SVf_UTF8" est distinct de la valeur PV ; vous devez vous assurer de ne pas le désactiver accidentellement lorsque vous manipulez des SV. Plus précisément, vous ne pouvez pas vous attendre à faire ceci :

SV *sv;
SV *nsv;
STRLEN len;
char *p;
p = SvPV(sv, len);
frobnicate(p);
nsv = newSVpvn(p, len);

La chaîne "char*" ne raconte pas toute l'histoire, et vous ne pouvez pas copier ou reconstruire un SV simplement en copiant la valeur de la chaîne. Vérifiez si l'ancien SV a le drapeau UTF8 défini (après l'appel "SvPV"), et agissez en conséquence :

p = SvPV(sv, len);
is_utf8 = SvUTF8(sv);
frobnicate(p, is_utf8);
nsv = newSVpvn(p, len);
if (is_utf8)
    SvUTF8_on(nsv);

Dans ce qui précède, votre fonction "frobnicate" a été modifiée pour être informée si elle traite ou non des données UTF-8, afin qu'elle puisse gérer la chaîne de manière appropriée.

Étant donné que le simple passage d'un SV à une fonction XS et la copie des données du SV ne suffisent pas à copier les drapeaux UTF8, il est encore moins correct de simplement passer un "char *" à une fonction XS.

Pour une généralité complète, utilisez la macro "DO_UTF8" pour voir si la chaîne d'un SV doit être *traitée* comme UTF-8. Cela tient compte du fait que l'appel à la fonction XS est fait dans le cadre de "use bytes". Si c'est le cas, les octets sous-jacents qui composent la chaîne UTF-8 doivent être exposés, plutôt que le caractère qu'ils représentent. Mais ce pragma ne devrait vraiment être utilisé que pour le débogage et peut-être des tests de bas niveau au niveau des octets. Par conséquent, la plupart du code XS n'a pas besoin de s'en préoccuper, mais diverses parties du noyau Perl doivent le prendre en charge.

Et ce n'est pas tout. À partir de la version Perl v5.12, les chaînes qui ne sont pas encodées en UTF-8 peuvent également être traitées comme Unicode dans diverses conditions (voir "ASCII Rules versus Unicode Rules" dans perlunicode). C'est surtout un problème pour les caractères dont les ordonnaux sont compris entre 128 et 255, et leur comportement varie sous les règles ASCII par rapport aux règles Unicode d'une manière qui intéresse votre code (voir "The "Unicode Bug"" dans perlunicode). Il n'y a pas d'API publiée pour gérer cela, car elle est sujette à modification, mais vous pouvez consulter le code de "pp_lc" dans pp.c pour un exemple de la façon dont c'est fait actuellement.

Comment puis-je passer une chaîne Perl à une bibliothèque C ?

Une chaîne Perl, conceptuellement, est une séquence opaque de points de code. De nombreuses bibliothèques C attendent que leurs entrées soient des chaînes C « classiques », qui sont des tableaux d'octets 1-255, terminés par un octet NUL. Votre travail lorsque vous écrivez une interface entre Perl et une bibliothèque C est de définir le mappage entre Perl et cette bibliothèque.

D'une manière générale, "SvPVbyte" et les macros associées conviennent bien à cette tâche. Celles-ci supposent que votre chaîne Perl est une « chaîne d'octets », c'est-à-dire soit une entrée brute et non décodée dans Perl, soit pré-encodée, par exemple, en UTF-8.

Alternativement, si votre bibliothèque C attend du texte UTF-8, vous pouvez utiliser "SvPVutf8" et les macros associées. Cela a le même effet que l'encodage en UTF-8, puis l'appel de la macro correspondante liée à "SvPVbyte".

Certaines bibliothèques C peuvent attendre d'autres encodages (par exemple, UTF-16LE). Pour passer des chaînes Perl à de telles bibliothèques, vous devez soit effectuer cet encodage en Perl, puis utiliser "SvPVbyte", soit utiliser une bibliothèque C intermédiaire pour convertir à partir de la manière dont Perl stocke la chaîne vers l'encodage souhaité.

Faites également attention à ce que les NUL dans votre chaîne Perl ne confondent pas la bibliothèque C. Si possible, donnez la longueur de la chaîne à la bibliothèque C ; si ce n'est pas possible, envisagez de rejeter les chaînes contenant des octets NUL.

Qu'en est-il de "SvPV", "SvPV_nolen", etc. ?

Considérez une chaîne Perl de 3 caractères "$foo = "\x64\x78\x8c"". Perl peut stocker ces 3 caractères de deux manières :

  • octets : 0x64 0x78 0x8c
  • UTF-8 : 0x64 0x78 0xc2 0x8c

Maintenant, disons que vous convertissez $foo en C chaîne de caractères comme ceci :

STRLEN strlen;
char *str = SvPV(foo_sv, strlen);

À ce stade, "str" pourrait pointer vers une chaîne C de 3 octets ou une chaîne de 4 octets.

D'une manière générale, nous voulons que "str" soit le même, quelle que soit la façon dont Perl stocke $foo, donc l'ambiguïté ici est indésirable. "SvPVbyte" et "SvPVutf8" résolvent cela en donnant des résultats prévisibles : utilisez "SvPVbyte" si votre bibliothèque C attend des chaînes d'octets, ou "SvPVutf8" si elle attend de l'UTF-8.

Si votre bibliothèque C prend en charge les deux encodages, alors "SvPV" -- toujours en conjonction avec des appels à "SvUTF8" -- peut être sûr et (légèrement) plus efficace.

ASTUCE DE TEST : Utilisez les fonctions "upgrade" et "downgrade" de utf8 dans vos tests pour assurer une gestion cohérente, quelle que soit l'encodage interne de Perl.

Comment convertir une chaîne en UTF-8 ?

Si vous mélangez des chaînes UTF-8 et non-UTF-8, il est nécessaire de mettre à niveau les chaînes non-UTF-8 vers UTF-8. Si vous avez un SV, le moyen le plus simple de le faire est :

sv_utf8_upgrade(sv);

Cependant, vous ne devez pas faire ceci, par exemple :

if (!SvUTF8(left))
    sv_utf8_upgrade(left);

Si vous faites cela dans un opérateur binaire, vous modifierez en fait l'une des chaînes qui sont entrées dans l'opérateur et, bien que cela ne devrait pas être perceptible par l'utilisateur final, cela peut causer des problèmes dans un code défaillant.

Au lieu de cela, "bytes_to_utf8" vous donnera une copie de sa chaîne d'argument, encodée en UTF-8. Ceci est utile pour avoir les données disponibles pour les comparaisons, etc., sans endommager le SV d'origine. Il y a aussi "utf8_to_bytes" pour faire le contraire, mais naturellement, cela échouera si la chaîne contient des caractères supérieurs à 255 qui ne peuvent pas être représentés en un seul octet.

Comment comparer des chaînes ?

"sv_cmp" dans perlapi et "sv_cmp_flags" dans perlapi effectuent une comparaison lexicographique de deux SV et gèrent correctement l'état UTF-8. Notez, cependant, que Unicode spécifie un mécanisme beaucoup plus sophistiqué pour la collation, disponible via le module Unicode::Collate.

Pour simplement comparer deux chaînes pour égalité/non-égalité, vous pouvez utiliser memEQ() et memNE() comme d'habitude, à condition que les chaînes soient toutes deux encodées en UTF-8 ou non.

Pour comparer deux chaînes de manière insensible à la casse, utilisez foldEQ_utf8() (les chaînes n'ont pas besoin d'avoir la même propriété UTF-8).

Y a-t-il autre chose que je dois savoir ?

Pas vraiment. Retenez simplement ces choses :

  • Il n'y a aucun moyen de savoir si une chaîne "char *" ou "U8 *" est en UTF-8 ou non. Mais vous pouvez savoir si un SV doit être traité comme UTF-8 en appelant "DO_UTF8" dessus, après l'avoir converti en chaîne avec "SvPV" ou une macro similaire. Et vous pouvez savoir si un SV est réellement en UTF-8 (même s'il ne doit pas être traité comme tel) en regardant son drapeau "SvUTF8" (encore après l'avoir converti en chaîne). N'oubliez pas de définir le drapeau si quelque chose devrait être en UTF-8. Traitez le drapeau comme faisant partie du PV, même s'il ne l'est pas -- si vous passez le PV à quelqu'un, passez aussi le drapeau.
  • Si une chaîne est en UTF-8, utilisez toujours "utf8_to_uvchr_buf" pour accéder à la valeur, sauf si UTF8_IS_INVARIANT(*s), auquel cas vous pouvez utiliser *s.
  • Lorsque vous écrivez un caractère UV dans une chaîne UTF-8, utilisez toujours "uvchr_to_utf8", sauf si "UVCHR_IS_INVARIANT(uv))", auquel cas vous pouvez utiliser "*s = uv".
  • Mélanger des chaînes UTF-8 et non-UTF-8 est délicat. Utilisez "bytes_to_utf8" pour obtenir une nouvelle chaîne encodée en UTF-8, puis combinez-les.

Opérateurs personnalisés

Le support des opérateurs personnalisés est une fonctionnalité expérimentale qui vous permet de définir vos propres opérations (ops). Ceci est principalement destiné à permettre la création d'interpréteurs pour d'autres langages au sein du noyau Perl, mais permet également des optimisations par la création de "macro-ops" (opérations qui effectuent les fonctions de plusieurs opérations généralement exécutées ensemble, comme "gvsv, gvsv, add".)

Cette fonctionnalité est implémentée comme un nouveau type d'op, "OP_CUSTOM". Le noyau Perl ne "sait" rien de spécial à propos de ce type d'op, et donc il ne sera impliqué dans aucune optimisation. Cela signifie également que vous pouvez définir vos opérations personnalisées comme toute structure d'op -- unaire, binaire, liste, etc. -- que vous souhaitez.

Il est important de savoir ce que les opérateurs personnalisés ne feront pas pour vous. Ils ne vous permettront pas d'ajouter directement une nouvelle syntaxe à Perl. Ils ne vous permettront même pas d'ajouter directement de nouveaux mots-clés. En fait, ils ne changeront pas la façon dont Perl compile un programme. Vous devez effectuer ces changements vous-même, après que Perl ait compilé le programme. Vous le faites soit en manipulant l'arbre d'opérations à l'aide d'un bloc "CHECK" et du module "B::Generate", soit en ajoutant un optimiseur "peephole" personnalisé avec le module "optimize".

Lorsque vous faites cela, vous remplacez les opérations Perl ordinaires par des opérations personnalisées en créant des opérations avec le type "OP_CUSTOM" et l'adresse PP de votre propre fonction PP (`op_ppaddr`). Ceci doit être défini dans du code XS et ressembler aux ops PP dans "pp_*.c". Vous êtes responsable de vous assurer que votre op prend le nombre approprié de valeurs de la pile, et vous êtes responsable d'ajouter des marques de pile si nécessaire.

Vous devriez également "enregistrer" votre op auprès de l'interpréteur Perl afin qu'il puisse produire des messages d'erreur et d'avertissement sensés. Puisqu'il est possible d'avoir plusieurs ops personnalisés au sein du même type d'op "logique" "OP_CUSTOM", Perl utilise la valeur de "o->op_ppaddr" pour déterminer quel op personnalisé il traite. Vous devriez créer une structure "XOP" pour chaque ppaddr que vous utilisez, définir les propriétés de l'op personnalisé avec "XopENTRY_set", et enregistrer la structure contre le ppaddr à l'aide de "Perl_custom_op_register". Un exemple trivial pourrait ressembler à ceci :

static XOP my_xop;
static OP *my_pp(pTHX);
BOOT:
    XopENTRY_set(&my_xop, xop_name, "myxop");
    XopENTRY_set(&my_xop, xop_desc, "Useless custom op");
    Perl_custom_op_register(aTHX_ my_pp, &my_xop);

Les champs disponibles dans la structure sont :

xop_name
Un nom court pour votre op. Il sera inclus dans certains messages d'erreur, et sera également renvoyé comme "$op->name" par le module B, il apparaîtra donc dans la sortie de modules comme B::Concise.
xop_desc
Une courte description de la fonction de l'op.
xop_class
Laquelle des diverses structures *OP cet op utilise. Ce devrait être l'une des constantes "OA_*" de op.h, à savoir
OA_BASEOP
OA_UNOP
OA_BINOP
OA_LOGOP
OA_LISTOP
OA_PMOP
OA_SVOP
OA_PADOP
OA_PVOP_OR_SVOP
Ceci devrait être interprété comme '"PVOP"' seulement. Le "_OR_SVOP" est dû au fait que le seul "PVOP" du noyau, "OP_TRANS", peut parfois être un "SVOP" à la place.
OA_LOOP
OA_COP

Les autres constantes "OA_*" ne doivent pas être utilisées.

xop_peep
Ce membre est de type "Perl_cpeep_t", qui s'étend à "void (*Perl_cpeep_t)(aTHX_ OP *o, OP *oldop)". S'il est défini, cette fonction sera appelée par "Perl_rpeep" lorsque des ops de ce type sont rencontrés par l'optimiseur "peephole". o est l'op qui doit être optimisé ; oldop est l'op précédent optimisé, dont "op_next" pointe vers o.
xop_dump
Ce membre est un pointeur vers une fonction de type "void (pTHX_ OP *, struct OpDumpContext *)". Si elle est définie, cette fonction est appelée par op_dump() lors de l'affichage d'un opérateur personnalisé de ce type, après l'impression des champs de base de l'op. Cette fonction peut utiliser opdump_printf() pour émettre une sortie supplémentaire qui peut être utile pour le débogage.

Le pointeur de structure opaque passé comme argument final doit être passé directement à opdump_printf().

"B::Genera

te" prend directement en charge la création d'opérations personnalisées par leur nom.

Piles

Les descriptions ci-dessus font parfois référence à « la pile », mais il existe en fait de nombreuses structures de données de type pile dans l'interpréteur perl. Lorsqu'elle n'est pas qualifiée, « la pile » fait généralement référence à la pile de valeurs.

Les différentes piles ont des objectifs variés et fonctionnent de manières légèrement différentes. Leurs différences sont notées ci-dessous.

Pile des valeurs

Cette pile stocke les valeurs sur lesquelles le code perl régulier opère, généralement des valeurs intermédiaires d'expressions au sein d'une instruction. La pile elle-même est formée d'un tableau de pointeurs SV.

La base de cette pile est pointée par la variable de l'interpréteur "PL_stack_base", de type "SV **".

La tête de la pile est "PL_stack_sp", et pointe vers l'élément le plus récemment empilé.

Les éléments sont empilés à l'aide de la macro PUSHs() ou de ses variantes décrites ci-dessus ; XPUSHs(), mPUSHs(), mXPUSHs() et les versions typées. Notez bien que les versions sans « X » de ces macros ne vérifient pas la taille de la pile et supposent qu'elle est suffisamment grande. Celles-ci doivent être associées à une vérification appropriée de la taille de la pile, telle que la macro "EXTEND" pour s'assurer qu'elle est suffisamment grande. Par exemple :

EXTEND(SP, 4);
mPUSHi(10);
mPUSHi(20);
mPUSHi(30);
mPUSHi(40);

C'est légèrement plus performant que de faire quatre vérifications séparées dans quatre appels mXPUSHi() distincts.

Pour une optimisation des performances supplémentaire, les diverses macros "PUSH" opèrent toutes à l'aide d'une variable locale "SP", plutôt que de la variable globale de l'interpréteur "PL_stack_sp". Cette variable est déclarée par la macro "dSP" - bien qu'elle soit normalement impliquée par les XSUBs et similaires, il est donc rare que vous ayez à vous en soucier directement. Une fois déclarée, les macros "PUSH" opéreront uniquement sur cette variable locale, donc avant d'invoquer toute autre fonction du noyau perl, vous devez utiliser la macro "PUTBACK" pour renvoyer la valeur de la variable locale "SP" à la variable de l'interpréteur. De même, après avoir appelé une fonction du noyau perl qui aurait pu avoir une raison de déplacer la pile ou d'y empiler/d'en dépiler des valeurs, vous devez utiliser la macro "SPAGAIN" qui rafraîchit la valeur locale "SP" à partir de celle de l'interpréteur.

Les éléments sont dépilés à l'aide de la macro "POPs" ou de ses versions typées. Il existe également une macro "TOPs" qui inspecte l'élément le plus haut sans le supprimer.

Notez spécifiquement que les pointeurs SV sur la pile de valeurs ne contribuent pas au compte de références global des xV référencés. Si des xV nouvellement créés sont empilés, vous devez prévoir leur destruction à un moment opportun ; généralement en utilisant l'une des macros "mPUSH*" ou sv_2mortal() pour rendre le xV mortel.

Pile des marques

La pile de valeurs stocke des valeurs scalaires perl individuelles en tant que temporaires entre les expressions. Certaines expressions perl opèrent sur des listes entières ; à cette fin, nous devons savoir où commence chaque liste sur la pile. C'est le but de la pile des marques.

La pile des marques stocke des entiers sous forme de valeurs I32, qui représentent la hauteur de la pile de valeurs au moment précédant le début de la liste ; ainsi, la marque elle-même pointe en fait vers l'entrée de la pile de valeurs précédant la liste. La liste elle-même commence à "mark + 1".

La base de cette pile est pointée par la variable de l'interpréteur "PL_markstack", de type "I32 *".

La tête de la pile est "PL_markstack_ptr", et pointe vers l'élément le plus récemment empilé.

Les éléments sont empilés à l'aide de la macro PUSHMARK(). Même si la pile elle-même stocke des indices de pile (de valeur) sous forme d'entiers, la macro "PUSHMARK" doit recevoir directement un pointeur de pile ; elle calculera le décalage d'indice en comparant avec la variable "PL_stack_sp". Ainsi, le code pour effectuer cela est presque toujours :

PUSHMARK(SP);

Les éléments sont dépilés par la macro "POPMARK". Il existe également une macro "TOPMARK" qui inspecte l'élément le plus haut sans le supprimer. Ces macros renvoient directement des valeurs d'indice I32. Il existe également la macro "dMARK" qui déclare une nouvelle variable double pointeur SV, appelée "mark", qui pointe vers l'emplacement marqué de la pile ; c'est la macro la plus couramment utilisée par le code C lorsqu'il opère sur des listes fournies sur la pile.

Comme noté ci-dessus, la variable "mark" pointera vers la valeur la plus récemment empilée sur la pile de valeurs avant le début de la liste, et donc la liste elle-même commence à "mark + 1". Les valeurs de la liste peuvent être parcourues par un code tel que :

for(SV **svp = mark + 1; svp <= PL_stack_sp; svp++) {
  SV *item = *svp;
  ...
}

Notez spécifiquement dans le cas où la liste est déjà vide, "mark" sera égal à "PL_stack_sp".

Étant donné que la variable "mark" est convertie en pointeur sur la pile de valeurs, une attention particulière doit être portée si "EXTEND" ou l'une des macros "XPUSH" est appelée dans la fonction, car la pile peut devoir être déplacée pour l'étendre et donc le pointeur existant deviendra invalide. Si cela peut poser problème, une solution possible est de suivre le décalage de la marque comme un entier et de suivre la marque elle-même plus tard, une fois que la pile a été déplacée.

I32 markoff = POPMARK;
...
SP **mark = PL_stack_base + markoff;

Pile des temporaires

Comme noté ci-dessus, les références SV sur la pile de valeurs principale ne contribuent pas au compte de références d'un SV, et donc un autre mécanisme est utilisé pour suivre quand les valeurs temporaires qui résident sur la pile doivent être libérées. C'est le rôle de la pile des temporaires.

La pile des temporaires stocke des pointeurs vers des SV dont le compte de références sera décrémenté bientôt.

La base de cette pile est pointée par la variable de l'interpréteur "PL_tmps_stack", de type "SV **".

La tête de la pile est indexée par "PL_tmps_ix", un entier qui stocke l'indice dans le tableau de l'élément le plus récemment empilé.

Il n'y a pas d'API publique pour empiler directement des éléments sur la pile des temporaires. Au lieu de cela, la fonction d'API sv_2mortal() est utilisée pour rendre un SV mortel, en ajoutant son adresse à la pile des temporaires.

De même, il n'y a pas d'API publique pour lire des valeurs depuis la pile des temporaires. Au lieu de cela, les macros "SAVETMPS" et "FREETMPS" sont utilisées. La macro "SAVETMPS" établit les niveaux de base de la pile des temporaires, en capturant la valeur actuelle de "PL_tmps_ix" dans "PL_tmps_floor" et en sauvegardant la valeur précédente dans la pile de sauvegarde. Par la suite, chaque fois que "FREETMPS" est invoqué, tous les temporaires qui ont été empilés depuis ce niveau sont récupérés.

Bien qu'il soit courant de voir ces deux macros par paires dans une paire "ENTER"/ "LEAVE", il n'est pas nécessaire de les faire correspondre. Il est permis d'invoquer "FREETMPS" plusieurs fois depuis le dernier "SAVETMPS" ; par exemple dans une boucle itérant sur les éléments d'une liste. Bien que vous puissiez invoquer "SAVETMPS" plusieurs fois dans une paire de portées, il est peu probable que cela soit utile. Les invocations ultérieures déplaceront le plancher des temporaires plus haut, piégeant ainsi efficacement les temporaires existants pour qu'ils ne soient libérés qu'à la fin de la portée.

Pile de sauvegarde

La pile de sauvegarde est utilisée par perl pour implémenter le mot-clé "local" et d'autres comportements similaires ; toutes les opérations de nettoyage qui doivent être effectuées lors de la sortie de la portée actuelle. Les éléments empilés sur cette pile capturent généralement la valeur actuelle d'une variable ou d'un état interne, qui sera restaurée lorsque la portée sera déroulée en raison d'une sortie, d'un "return", d'un "die", d'un "goto" ou d'autres raisons.

Alors que d'autres piles internes de perl stockent des éléments individuels de même type (généralement des pointeurs SV ou des entiers), les éléments empilés sur la pile de sauvegarde sont formés de nombreux types différents, ayant plusieurs champs. Par exemple, le type "SAVEt_INT" doit stocker à la fois l'adresse de la variable "int" à restaurer, et la valeur à restaurer. Ces informations auraient pu être stockées à l'aide des champs d'une "struct", mais auraient dû être assez grandes pour stocker trois pointeurs dans le cas le plus large, ce qui aurait gaspillé beaucoup d'espace dans la plupart des cas plus petits.

Au lieu de cela, la pile stocke des informations dans un encodage de longueur variable de structures "ANY". La valeur finale empilée est stockée dans le champ "UV" qui encode le type d'élément détenu par les éléments précédents ; le nombre et les types desquels dépendront du type d'élément stocké. Le champ de type est empilé en dernier car ce sera le premier champ à être dépilé lors du déroulement des éléments de la pile.

La base de cette pile est pointée par la variable de l'interpréteur "PL_savestack", de type "ANY *".

La tête de la pile est indexée par

"PL_savestack_ix", un entier qui stocke l'indice dans le tableau où le prochain élément doit être inséré. (Notez que c'est différent de la plupart des autres piles, qui font référence à l'élément le plus récemment inséré).

Les éléments sont insérés dans la pile de sauvegarde en utilisant les diverses macros "SAVE...()". Beaucoup de ces macros prennent une variable et stockent à la fois son adresse et sa valeur actuelle dans la pile de sauvegarde, assurant que la valeur soit restaurée à la sortie de la portée.

SAVEI8(i8)
SAVEI16(i16)
SAVEI32(i32)
SAVEINT(i)
...

Il existe également une variété d'autres macros spéciales pour sauvegarder des types ou des valeurs particuliers. "SAVETMPS" a déjà été mentionné ci-dessus. D'autres incluent "SAVEFREEPV" qui organise la libération d'un PV (c'est-à-dire un tampon de chaîne), ou "SAVEDESTRUCTOR" qui organise l'appel d'un pointeur de fonction donné à la sortie de la portée. Une liste complète de ces macros se trouve dans scope.h.

Il n'y a pas d'API publique pour dépiler des valeurs individuelles ou des éléments de la pile de sauvegarde. Au lieu de cela, via la pile de portée, la paire "ENTER" et "LEAVE" forme un moyen de démarrer et d'arrêter des portées imbriquées. Quitter une portée imbriquée via "LEAVE" restaurera toutes les valeurs sauvegardées qui avaient été insérées depuis le plus récent "ENTER".

Pile de portée

Comme pour la pile de marques (mark stack) par rapport à la pile de valeurs (value stack), la pile de portée forme une paire avec la pile de sauvegarde. La pile de portée stocke la hauteur de la pile de sauvegarde au début des portées imbriquées, et permet de dérouler la pile de sauvegarde jusqu'à ce point lorsqu'on quitte la portée.

Lorsque Perl est compilé avec le débogage activé, il y a une seconde partie à cette pile qui stocke des noms de chaînes lisibles par l'homme décrivant le type de contexte de la pile. Chaque opération d'insertion sauvegarde le nom ainsi que la hauteur de la pile de sauvegarde, et chaque opération de dépilage vérifie le nom du sommet avec ce qui est attendu, provoquant un échec d'assertion si le nom ne correspond pas.

La base de cette pile est pointée par la variable interpréteur "PL_scopestack", de type "I32 *". Si activée, les noms de la pile de portée sont stockés dans un tableau séparé pointé par "PL_scopestack_name", de type "const char **".

La tête de la pile est indexée par "PL_scopestack_ix", un entier qui stocke l'indice du ou des tableaux où le prochain élément doit être inséré. (Notez que c'est différent de la plupart des autres piles, qui font référence à l'élément le plus récemment inséré).

Les valeurs sont insérées dans la pile de portée en utilisant la macro "ENTER", qui démarre une nouvelle portée imbriquée. Tous les éléments insérés dans la pile de sauvegarde sont ensuite restaurés lors de la prochaine invocation imbriquée de la macro "LEAVE".

Portée dynamique et pile de contexte

Note : cette section décrit une API interne non publique susceptible d'être modifiée sans préavis.

Introduction à la pile de contexte

En Perl, la portée dynamique fait référence à l'imbrication à l'exécution de choses comme les appels de sous-routines, les eval, etc., ainsi qu'à l'entrée et à la sortie des portées de blocs. Par exemple, la restauration d'une variable "local"isée est déterminée par la portée dynamique.

Perl suit la portée dynamique par une structure de données appelée la pile de contexte, qui est un tableau de structures "PERL_CONTEXT", et qui est elle-même une grande union pour tous les types de contexte. Chaque fois qu'une nouvelle portée est entrée (comme un bloc, une boucle "for", ou un appel de sous-routine), une nouvelle entrée de contexte est insérée dans la pile. De même, lors de la sortie d'un bloc ou du retour d'un appel de sous-routine, etc., un contexte est dépilé. Comme la pile de contexte représente la portée dynamique actuelle, elle peut être recherchée. Par exemple, "next LABEL" recherche dans la pile pour trouver un contexte de boucle qui correspond à l'étiquette ; "return" dépile les contextes jusqu'à ce qu'il trouve un contexte de sous-routine ou d'eval ou similaire ; "caller" examine les contextes de sous-routines sur la pile.

Chaque entrée de contexte est étiquetée avec un type de contexte, "cx_type". Les types de contexte typiques sont "CXt_SUB", "CXt_EVAL", etc., ainsi que "CXt_BLOCK" et "CXt_NULL" qui représentent une portée de base (comme insérée par "pp_enter") et un bloc de tri. Le type détermine quelle partie de l'union de contexte est valide.

La division principale dans la structure de contexte se situe entre une portée de substitution ("CXt_SUBST") et les portées de bloc, qui sont tout le reste. La première est juste utilisée lors de l'exécution de "s///e", et ne sera pas discutée plus loin ici.

Tous les types de portées de bloc partagent une base commune, qui correspond à "CXt_BLOCK". Celle-ci stocke les anciennes valeurs de diverses variables liées à la portée comme "PL_curpm", ainsi que des informations sur la portée actuelle, comme "gimme". À la sortie de la portée, les anciennes variables sont restaurées.

Les types de portées de bloc particuliers stockent des informations supplémentaires spécifiques au type. Par exemple, "CXt_SUB" stocke le CV en cours d'exécution, tandis que les divers types de boucles for peuvent détenir la variable de boucle d'origine SV. À la sortie de la portée, les données spécifiques au type sont traitées ; par exemple, le CV voit son compteur de références décrémenté, et la variable de boucle d'origine est restaurée.

La macro "cxstack" renvoie la base de la pile de contexte actuelle, tandis que "cxstack_ix" est l'indice du cadre actuel dans cette pile.

En fait, la pile de contexte fait partie d'un système de pile de piles ; chaque fois que quelque chose d'inhabituel est fait, comme l'appel d'un gestionnaire "DESTROY" ou tie, une nouvelle pile est insérée, puis dépilée à la fin.

Notez que l'API décrite ici a considérablement changé dans perl 5.24 ; avant cela, de grandes macros comme "PUSHBLOCK" et "POPSUB" étaient utilisées ; en 5.24, elles ont été remplacées par les fonctions statiques en ligne décrites ci-dessous. De plus, l'ordre et les détails du fonctionnement de ces macros/fonctions ont changé de nombreuses manières, souvent subtiles. En particulier, elles ne géraient pas la sauvegarde des positions des piles savestack et temps, et nécessitaient des appels supplémentaires à "ENTER", "SAVETMPS" et "LEAVE" par rapport aux nouvelles fonctions. Les macros de l'ancienne manière ne seront pas décrites plus loin.

Insertion des contextes

Pour insérer un nouveau contexte, les deux fonctions de base sont "cx = cx_pushblock()", qui insère un nouveau bloc de contexte de base et renvoie son adresse, et une famille de fonctions similaires nommées comme cx_pushsub(cx) qui peuplent les champs supplémentaires dépendants du type dans la structure "cx". Notez que "CXt_NULL" et "CXt_BLOCK" n'ont pas leurs propres fonctions d'insertion, car ils ne stockent aucune donnée au-delà de celle insérée par "cx_pushblock".

Les champs de la structure de contexte et les arguments des fonctions "cx_*" sont sujets à modification entre les versions de Perl, représentant ce qui est pratique ou efficace pour cette version.

Une insertion typique de la pile de contexte se trouve dans "pp_entersub" ; ce qui suit montre un exemple simplifié et épuré d'un appel non-XS, avec des commentaires montrant grossièrement ce que fait chaque fonction.

dMARK;
U8 gimme      = GIMME_V;
bool hasargs  = cBOOL(PL_op->op_flags & OPf_STACKED);
OP *retop     = PL_op->op_next;
I32 old_ss_ix = PL_savestack_ix;
CV *cv        = ....;
/* ... créer des copies mortelles des arguments de pile qui sont des PADTMP ici ... */
/* ... effectuer des insertions supplémentaires dans savestack ici ... */
/* Maintenant, insérer une nouvelle entrée de contexte de type 'CXt_SUB'; initialement,
 * on effectue uniquement les actions communes à tous les types de blocs : */
cx = cx_pushblock(CXt_SUB, gimme, MARK, old_ss_ix);
    /* cela fait (approximativement) :
        CXINC;              /* cxstack_ix++ (agrandir si nécessaire) */
        cx = CX_CUR();      /* et obtenir l'adresse du nouveau cadre */
        cx->cx_type        = CXt_SUB;
        cx->blk_gimme      = gimme;
        cx->blk_oldsp      = MARK - PL_stack_base;
        cx->blk_oldsaveix  = old_ss_ix;
        cx->blk_oldcop     = PL_curcop;
        cx->blk_oldmarksp  = PL_markstack_ptr - PL_markstack;
        cx->blk_oldscopesp = PL_scopestack_ix;
        cx->blk_oldpm      = PL_curpm;
        cx->blk_old_tmpsfloor = PL_tmps_floor;
        PL_tmps_floor        = PL_tmps_ix;
    */
/* puis mettre à jour le nouveau cadre de contexte avec des informations spécifiques à la sous-routine,
 * comme le CV sur le point d'être exécuté : */
cx_pushsub(cx, cv, retop, hasargs);
    /* cela fait (approximativement) :
        cx->blk_sub.cv          = cv;
        cx->blk_sub.olddepth    = CvDEPTH(cv);
        cx->blk_sub.prevcomppad = PL_comppad;
        cx->cx_type            |= (hasargs) ? CXp_HASARGS : 0;
        cx->blk_sub.retop       = retop;
        SvREFCNT_inc_simple_void_NN(cv);
    */

Notez que cx_pushblock() définit deux nouveaux planchers : pour la pile d'arguments (à "MARK") et pour la pile des temporaires (à "PL_tmps_ix"). Pendant l'exécution à ce niveau de portée, chaque "nextstate" (entre autres) réinitialisera les niveaux des piles d'arguments et de temporaires à ces planchers. Notez que puisque "cx_pushblock" utilise la valeur actuelle de "PL_tmps_ix" plutôt que de la passer comme argument, cela dicte à quel moment "cx_pushblock" doit être appelé. En particulier, tout nouveau mortel qui doit être libéré uniquement à la sortie de la portée (plutôt qu'au prochain "nextstate") doit être créé en premier.

La plupart des appelants de "cx_pushblock" définit simplement le nouveau niveau de pile d'arguments au sommet du cadre de pile précédent, mais pour "CXt_LOOP_LIST", il stocke les éléments sur lesquels on itère sur la pile, et définit donc "blk_oldsp" au sommet de ces éléments à la place. Notez que, contrairement à son nom, "blk_oldsp" ne représente pas toujours la valeur à laquelle "PL_stack_sp" doit être restaurée à la sortie de la portée.

Notez la capture précoce de "PL_savestack_ix" dans "old_ss_ix", qui est ensuite passée comme argument à "cx_pushblock". Dans le cas de "pp_entersub", c'est parce que, bien que la plupart des valeurs devant être sauvegardées soient stockées dans des champs de la structure de contexte, une valeur supplémentaire ne doit être sauvegardée que lorsque le débogueur est en cours d'exécution, et il n'est pas logique d'enfler la structure pour ce cas rare. Elle est donc sauvegardée sur la pile de sauvegarde. Comme cette valeur est calculée et sauvegardée avant que le contexte ne soit empilé, il est nécessaire de passer l'ancienne valeur de "PL_savestack_ix" à "cx_pushblock", afin de garantir que la valeur sauvegardée soit libérée lors de la sortie de portée. Pour la plupart des utilisateurs de "cx_pushblock", où rien ne doit être empilé sur la pile de sauvegarde, "PL_savestack_ix" est simplement passé directement comme argument à "cx_pushblock".

Notez que lorsque cela est possible, les valeurs doivent être sauvegardées dans la structure de contexte plutôt que sur la pile de sauvegarde ; c'est beaucoup plus rapide ainsi.

Normalement, "cx_pushblock" doit être immédiatement suivi de la fonction appropriée "cx_pushfoo", sans rien entre les deux ; ceci est parce que si le code entre les deux pouvait mourir (par exemple, un avertissement mis à niveau en fatale), le code de déroulement de la pile de contexte dans "dounwind" verrait (dans l'exemple ci-dessus) un cadre de contexte "CXt_SUB", mais sans tous les champs spécifiques à la sous-routine définis, et des plantages s'ensuivraient bientôt.

Lorsque les deux doivent être séparés, initialisez d'abord le type à "CXt_NULL" ou "CXt_BLOCK", et changez-le plus tard en "CXt_foo" lors de l'appel à "cx_pushfoo". C'est exactement ce que fait "pp_enteriter", une fois qu'il a déterminé le type de boucle qu'il empile.

Désémpilage des contextes

Les contextes sont désémpilés en utilisant cx_popsub() etc. et cx_popblock(). Notez cependant que, contrairement à "cx_pushblock", aucune de ces fonctions ne décrémente réellement l'index de la pile de contexte actuelle ; cela est fait séparément en utilisant CX_POP().

Il y a deux principales façons dont les contextes sont désémpilés. Pendant l'exécution normale, lorsque les portées sont quittées, des fonctions comme "pp_leave", "pp_leaveloop" et "pp_leavesub" traitent et désémpilent un seul contexte en utilisant "cx_popfoo" et "cx_popblock". D'autre part, des éléments comme "pp_return" et "next" peuvent devoir remonter plusieurs portées jusqu'à trouver un contexte de sous-routine ou de boucle, et les exceptions (comme "die") nécessitent de remonter des contextes jusqu'à trouver un contexte d'évaluation. Les deux sont accomplis par dounwind(), qui est capable de traiter et de désémpiler tous les contextes au-dessus de celui cible.

Voici un exemple typique de désémpilage de contexte, tel que trouvé dans "pp_leavesub" (légèrement simplifié) :

U8 gimme;
PERL_CONTEXT *cx;
SV **oldsp;
OP *retop;
cx = CX_CUR();
gimme = cx->blk_gimme;
oldsp = PL_stack_base + cx->blk_oldsp; /* dernier argument du cadre précédent */
if (gimme == G_VOID)
    PL_stack_sp = oldsp;
else
    leave_adjust_stacks(oldsp, oldsp, gimme, 0);
CX_LEAVE_SCOPE(cx);
cx_popsub(cx);
cx_popblock(cx);
retop = cx->blk_sub.retop;
CX_POP(cx);
return retop;

Les étapes ci-dessus sont dans un ordre très spécifique, conçu pour être l'ordre inverse de celui où le contexte a été empilé. La première chose à faire est de copier et/ou de protéger les arguments de retour et de libérer les temporaires dans la portée actuelle. Les sorties de portée comme une sous-routine rvalue retournent normalement une copie mortelle de leurs arguments de retour (par opposition aux sous-routines lvalue). Il est important de faire cette copie avant que la pile de sauvegarde ne soit désémpilée ou que les variables ne soient restaurées, sinon des problèmes comme les suivants peuvent survenir :

sub f { my $x =...; $x }  # $x libéré avant que nous ne le copiions
sub f { /(...)/;    $1 }  # PL_curpm restauré avant que $1 ne soit copié

Bien que nous souhaitions libérer tous les temporaires en même temps, nous devons faire attention à ne pas libérer les temporaires qui maintiennent les arguments de retour en vie ; ni à libérer les temporaires que nous venons de créer lors de la copie mortelle des arguments de retour. Heureusement, leave_adjust_stacks() est capable de faire des copies mortelles des arguments de retour, de décaler les arguments vers le bas de la pile, et de ne traiter que les entrées de la pile des temporaires qui peuvent être traitées en toute sécurité.

Dans un contexte vide, aucun argument n'est retourné, il est donc plus efficace de sauter l'appel à leave_adjust_stacks(). De plus, dans un contexte vide, un op "nextstate" est susceptible d'être appelé prochainement, ce qui effectuera un "FREETMPS", il n'est donc pas nécessaire de le faire non plus.

L'étape suivante consiste à désémpiler les entrées de la pile de sauvegarde : CX_LEAVE_SCOPE(cx) est simplement défini comme LEAVE_SCOPE(cx->blk_oldsaveix). Notez que pendant le désémpilage, il est possible que perl appelle des destructeurs, appelle "STORE" pour annuler les localisations des variables liées, etc. N'importe laquelle de ces opérations peut mourir ou appeler exit(). Dans ce cas, dounwind() sera appelée, et le cadre de contexte actuel sera retraité. Il est donc vital que toutes les étapes de désémpilage d'un contexte soient effectuées de manière à supporter la réentrance. L'autre alternative, qui consiste à décrémenter "cxstack_ix" *avant* de traiter le cadre, entraînerait des fuites et autres problèmes si quelque chose mourait à mi-chemin, ou l'écrasement du cadre actuel.

"CX_LEAVE_SCOPE" est lui-même sans risque réentrant : si seulement la moitié des éléments de la pile de sauvegarde ont été désémpilés avant de mourir et d'être capturés par eval, alors les appels à "CX_LEAVE_SCOPE" dans "dounwind" ou "pp_leaveeval" reprendront là où le premier s'est arrêté.

L'étape suivante est le traitement spécifique au type de contexte ; dans ce cas, "cx_popsub". En partie, cela ressemble à ceci :

cv = cx->blk_sub.cv;
CvDEPTH(cv) = cx->blk_sub.olddepth;
cx->blk_sub.cv = NULL;
SvREFCNT_dec(cv);

où il traite le CV qui vient d'être exécuté. Notez qu'avant de décrémenter le compteur de références du CV, il met à NULL le champ "blk_sub.cv". Cela signifie que s'il y a réentrée, le CV ne sera pas libéré deux fois. Cela signifie également que vous ne pouvez pas vous fier à de tels champs spécifiques au type pour avoir des valeurs utiles après le retour de "cx_popfoo".

Ensuite, "cx_popblock" restaure toutes les variables d'interpréteur à leurs valeurs précédentes ou à leurs marques hautes précédentes ; il s'étend à :

PL_markstack_ptr = PL_markstack + cx->blk_oldmarksp;
PL_scopestack_ix = cx->blk_oldscopesp;
PL_curpm         = cx->blk_oldpm;
PL_curcop        = cx->blk_oldcop;
PL_tmps_floor    = cx->blk_old_tmpsfloor;

Notez qu'il ne restaure *pas* "PL_stack_sp" ; comme mentionné précédemment, la valeur à laquelle il doit être restauré dépend du type de contexte (spécifiquement "for (list) {}"), et des arguments (le cas échéant) qu'il retourne ; et cela aura déjà été trié plus tôt par leave_adjust_stacks().

Enfin, le pointeur de la pile de contexte est réellement décrémenté par CX_POP(cx). Après ce point, il est possible que le cadre de contexte actuel soit écrasé par d'autres contextes en cours d'empilement. Bien que les éléments comme les liens (ties) et "DESTROY" soient censés fonctionner dans un nouveau contexte de pile, il est préférable de ne pas l'assumer. En fait, dans les builds de débogage, CX_POP(cx) met délibérément "cx" à null pour détecter le code qui s'appuie encore sur les valeurs des champs de ce cadre de contexte. Notez dans l'exemple de pp_leavesub() ci-dessus, nous récupérons "blk_sub.retop" *avant* d'appeler "CX_POP".

Réinitialisation des contextes

Enfin, il y a cx_topblock(cx), qui agit comme un super- "nextstate" en ce qui concerne la réinitialisation de diverses variables à leurs valeurs de base. Il est utilisé dans des endroits comme "pp_next", "pp_redo" et "pp_goto" où, au lieu de quitter une portée, nous voulons la réinitialiser. En plus de réinitialiser "PL_stack_sp" comme "nextstate", il réinitialise également "PL_markstack_ptr", "PL_scopestack_ix" et "PL_curpm". Notez qu'il n'effectue pas de "FREETMPS".

Pile d'arguments à comptage de références

Introduction

Depuis perl 5.40, il existe une option de compilation, "PERL_RC_STACK", non activée par défaut, qui exige que les éléments empilés ou dépilés de la pile d'arguments aient leur compteur de références ajusté. Il est prévu que cela devienne à terme le moyen par défaut (et finalement le seul) de configurer perl.

Les macros qui manipulent la pile telles que PUSHs() et POPs() n'ajustent pas le compteur de références du SV. La plupart du temps, cela convient, car quelque chose d'autre maintient le SV en vie pendant qu'il est sur la pile d'arguments, comme un pointeur de la pile TEMPs, ou du pad (par exemple, une variable lexicale ou un "PADTMP"). Parfois

ally cela peut mal tourner. Par exemple, ce code : 
mon @a = (1,2,3);
sous f { @a = (); imprimer "(@_)\n" };
f(@a, 4);

peut imprimer des valeurs non définies ou libérées aléatoirement, étant donné que certains des éléments de @_, qui ont été aliasés aux éléments de @a, ont été libérés. "PERL_RC_STACK" est destiné à résoudre ce problème en faisant en sorte que chaque pointeur SV sur la pile d'arguments incrémente le compteur de références (RC) du SV d'une unité.

Dans ce nouvel environnement, les fonctions PP et XS existantes non modifiées, qui ont été écrites en supposant une pile sans comptage de références (non-RC pour faire court), sont appelées via des fonctions enveloppes spéciales qui ajustent la pile avant et après. À l'heure actuelle, il n'y a pas d'API pour écrire une fonction XS RC, donc tout code XS continuera à être appelé via un enveloppe (ce qui les rend légèrement plus lents), mais cela signifie qu'en général, les distributions CPAN contenant du code XS continuent de fonctionner sans modification.

Cependant, les fonctions PP, soit dans le cœur de Perl, soit celles des fonctions XS utilisées pour implémenter des opérations personnalisées ou pour remplacer les fonctions PP des opérations intégrées, nécessitent un traitement spécial. Pour ces dernières, elles peuvent simplement être enveloppées ; cela demande le moins de travail, mais a un impact sur les performances. À plus long terme, et pour les fonctions PP du cœur, elles doivent être déballées et réécrites à l'aide d'une nouvelle API. Avec cela, les anciennes macros telles que PUSHs() ont été remplacées par un nouvel ensemble de fonctions (majoritairement en ligne) avec un préfixe commun, tel que rpp_push_1(). « RPP » signifie « référence-counted push and pop functions ». Les nouvelles fonctions modifient le compteur de références sur les constructions "PERL_RC_STACK", tout en les laissant non ajustées autrement. Ainsi, dans le cœur, elles fonctionnent généralement dans les deux cas, tandis que dans le code XS, elles sont portables vers les anciennes versions de Perl via "PPPort" (XXX en supposant qu'elles soient ajoutées à "PPPort").

Le reste de cette section concerne principalement la manière de convertir les fonctions PP existantes et d'écrire de nouvelles fonctions PP pour utiliser la nouvelle API "rpp_".

Un Perl avec comptage de références peut être construit en utilisant la définition PERL_RC_STACK. À des fins de développement et de débogage, il est préférable d'activer également le débogage des fuites de scalaires, car cela affiche des informations supplémentaires sur les scalaires qui ont fui ou ont été libérés prématurément.

Configure -DDEBUGGING \
  -Accflags='-DPERL_RC_STACK -DDEBUG_LEAKING_SCALARS'

États de la pile avec comptage de références

Dans le nouveau régime, la pile d'arguments actuelle peut être dans l'un des trois états, qui peuvent être déterminés par l'expression montrée.

  • pas de comptage de références 
    !AvREAL(PL_curstack)

    Dans ce cas, Perl supposera lors de la vidange de la pile (par exemple, lors d'un croak()) que les éléments présents n'ont pas besoin d'être libérés. C'est le comportement traditionnel de Perl. Sur les constructions "PERL_RC_STACK", de telles piles seront rarement rencontrées.

  • comptage de références complet 
    AvREAL(PL_curstack) && !PL_curstackinfo->si_stack_nonrc_base

    Tous les éléments de la pile ont un comptage de références, et seront libérés par des fonctions comme rpp_popfree_1() ou si Perl croak(). C'est l'état normal de la pile dans les constructions "PERL_RC_STACK".

  • comptage de références partiel (divisé) 
    AvREAL(PL_curstack) && PL_curstackinfo->si_stack_nonrc_base > 0

    Dans ce cas, les éléments de la pile à partir de l'index "si_stack_nonrc_base" et au-dessus sont sans RC ; ceux en dessous ont un RC. Cet état se produit lorsqu'une fonction PP ou XS a été enveloppée. Dans ce cas, la fonction enveloppe pousse une copie non-RC des pointeurs d'arguments au-dessus de la coupure, puis appelle la fonction réelle. Lorsque celle-ci revient, la fonction enveloppe augmente le RC de tous les arguments retournés. Voir ci-dessous pour plus de détails.

Notez que Perl utilise une pile de piles, et les états AvREAL() et "si_stack_nonrc_base" sont par pile. Lorsque Perl démarre, la pile principale est RC, mais par défaut, les nouvelles piles poussées dans le code XS via PUSHSTACKi() sont non-RC, il est donc tout à fait possible d'obtenir un mélange. Le cœur de Perl utilise lui-même la nouvelle fonction push_stackinfo() qui remplace PUSHSTACKi() et vous permet de spécifier que la nouvelle pile doit être RC par défaut. (XXX le cœur n'a en fait pas encore été majoritairement mis à jour pour utiliser push_stackinfo())

La plupart des endroits dans le cœur supposent un environnement RC particulier. Notamment, il est supposé qu'à l'intérieur d'une boucle runops, toutes les fonctions PP sont conscientes de la gestion RC, soit parce qu'elles ont été (re)écrites pour l'être, soit parce qu'elles ont été enveloppées. Chaque fois qu'une boucle runops est entrée via CALLRUNOPS(), elle vérifiera l'état actuel de la pile et, si elle n'est pas entièrement RC, mettra temporairement à jour son contenu pour qu'il soit entièrement RC avant d'entrer dans la boucle runops principale. Ensuite, si nécessaire, elle restaurera la pile à son ancien état au retour. Cela signifie que des fonctions comme call_sv(), qui peuvent être appelées depuis n'importe quel environnement (par exemple, un cœur RC ou un code XS enveloppé et temporairement non-RC) feront toujours la bonne chose lors de l'invocation de la boucle runops, quel que soit l'état actuel de la pile.

De même, les croaks et autres (qui peuvent survenir n'importe où) doivent pouvoir gérer les deux types de piles. Il y a donc quelques endroits dans le cœur - call_sv(), eval_sv() etc, Perl_die_unwind() et S_my_exit_jump() - qui ont été spécialement conçus pour gérer les deux cas ; tout le reste peut supposer un environnement fixe.

Enveloppement

Normalement, une fonction PP du cœur est déclarée comme suit :

PP(pp_foo)
{
    ...
}

Cela se développe en quelque chose comme :

OP* Perl_pp_foo(pTHX)
{
    ...
}

Lorsque une telle fonction doit être enveloppée, elle est plutôt déclarée comme ceci :

PP_wrapped(pp_foo, nargs, nlists)
{
    ...
}

ce qui, sur les constructions non-RC, se développe de la même manière que PP() (les arguments supplémentaires sont ignorés). Sur les constructions RC, cela se développe en quelque chose comme

OP* Perl_pp_foo(pTHX)
{
    return Perl_pp_wrap(aTHX_ S_Perl_pp_foo_norc, nargs, nlists);
}
STATIC OP* S_Perl_pp_foo_norc(pTHX)
{
    ...
}

Ici, la fonction PP visible extérieurement appelle pp_wrap(), qui ajuste le contenu de la pile, puis appelle le corps réel caché de la fonction PP, puis, au retour, réajuste la pile.

Il existe une macro d'API, XSPP_wrapped(), destinée à être utilisée sur les fonctions PP déclarées dans le code XS. Elle est identique à PP_wrapped(), à l'exception qu'elle n'ajoute pas de préfixe "Perl_" au nom de la fonction.

Les paramètres "nargs" et "nlists" de la macro sont des constantes numériques ou des expressions simples qui spécifient le nombre d'arguments que la fonction PP attend, ou le nombre de listes qu'elle attend. Par exemple,

PP_wrapped(pp_add, 2, 0);     /* consomme deux arguments de la pile */
PP_wrapped(pp_readline,       /* consomme un ou deux arguments */
        ((PL_op->op_flags & OPf_STACKED) ? 2 : 1), 0);
PP_wrapped(pp_push, 0, 1);    /* consomme une liste */
PP_wrapped(pp_aassign, 0, 2); /* consomme deux listes */

Pour comprendre ce que fait pp_wrap(), considérez l'appel de Perl_pp_foo() qui attend trois arguments. À l'entrée, la pile peut ressembler à ceci :

... A+ B+ C+

(où le "+" indique que les pointeurs vers A, B et C sont chacun référencés). La fonction enveloppe pp_wrap() marque une coupure à la position actuelle de la pile à l'aide de "si_stack_nonrc_base", puis, en fonction de la valeur de "nargs", pousse une copie de ces trois pointeurs au-dessus de la coupure :

... A+ B+ C+ | A0 B0 C0

(où le 0 indique que les pointeurs ne sont pas RC), puis appelle la vraie fonction PP, S_Perl_pp_foo_norc(). Cette fonction traite A, B et C, les retire de la pile et pousse quelques SV de résultat. Aucune de ces manipulations n'ajuste les RC. Au retour vers pp_wrap(), la pile peut ressembler à ceci :

... A+ B+ C+ | X0 Y0

La fonction enveloppe augmente les RC de X et Y, décrémente A B C, déplace les résultats vers le bas et définit "si_stack_nonrc_base" à zéro, laissant la pile comme ceci :

... X+ Y+

Dans des endroits comme pp_entersub(), un enveloppement similaire (via les fonctions rpp_invoke_xs() puis xs_wrap()) est effectué lors de l'appel de sous-programmes XS.

Lorsque "nlists" est positif, une action similaire a lieu, sauf que la pile des marques est examinée (et ajustée) afin de déterminer le nombre d'arguments à copier.

Un environnement d'appel complexe peut avoir plusieurs piles imbriquées avec des états RC différents. Perl démarre avec une pile RC. Ensuite, par exemple, pp_entersub() est appelée, ce qui (via xs_wrap()) divise la pile et exécute la fonction XS dans un environnement non-RC. Cette fonction peut appeler PUSHSTACKi(), qui crée une nouvelle pile non-RC, puis appelle call_sv(), qui exécute CALLRUNOPS(), ce qui fait que la nouvelle pile devient temporairement RC. Ensuite, une méthode liée est appelée, qui pousse une nouvelle pile RC, et ainsi de suite. (XXX actuellement, les méthodes liées poussent en fait une pile non-RC. Sera corrigé bientôt).

(Re)écriture d'une fonction PP utilisant l'API rpp_()

L'enveloppement d'une fonction PP a une surcharge de performance, et existe principalement comme béquille temporaire. Finalement, les fonctions PP devraient être mises à jour pour utiliser les fonctions rpp_(), et toute nouvelle fonction PP devrait être écrite de cette manière à partir de zéro et donc ne jamais avoir besoin d'être enveloppée.

Quelques exemples de fonctions PP du cœur converties peuvent être vus dans les commits "v5.39.1-304-g205fcd8410" et "v5.39.1-303-g2fe263a83a", qui démontrent la conversion d'une opération unaire et binaire (pp_not() et pp_and()).

L'API traditionnelle de la pile PP consistait en une déclaration "dSP", plus un certain nombre de macros pour pousser, dépiler et étendre la pile. Une fonction pp_add() *très simplifiée* pourrait ressembler à ceci :

PP(pp_add)
{
    dSP;
    dTARGET;
    IV right = SvIV(POPs);
    IV left  = SvIV(POPs);
    TARGi(left + right, 1);
    PUSHs(TARG);
    PUTBACK;
    return NORMAL;
}

ce qui se développe en quelque chose comme :

{
    SV **sp = PL_stack_sp;
    SV *targ =
PAD_SV(PL_op->op_targ); IV right = SvIV(*sp--); IV left = SvIV(*sp--); sv_setiv(targ, left + right); *++sp = targ; PL_stack_sp = sp; return PL_op->op_next; }

Le concept de "dSP" remonte aux jours précédant les compilateurs d'optimisation décents. C'était toujours source d'erreurs, par exemple si vous oubliiez un "PUTBACK" ou "SPAGAIN". La nouvelle API accède toujours directement à "PL_stack_sp". En fait, la première étape de mise à jour d'une fonction PP consiste toujours à supprimer la déclaration "dSP". Cela a l'effet secondaire heureux que les anciennes macros qui utilisent implicitement "sp" deviendront des erreurs de compilation. La présence d'un "dSP" quelque part dans le noyau est un bon signe que cette fonction a encore besoin d'être mise à jour.

Une question évidente est : pourquoi ne pas simplement modifier les définitions des macros PUSHs() etc. pour modifier les comptes de référence sur les builds RC ? Le problème fondamental est qu'un SV peut maintenant être maintenu en vie uniquement par un seul compte de référence de la pile (auparavant, ils avaient tendance à être également sur la pile TEMPs). Donc, dans un code comme :

SV *sv = POPs;
IV i = SvIV(sv);

l'inclusion d'un SvREFCNT_dec() dans la définition de la macro "POPs" entraînerait la libération immédiate de "sv", avant que sa valeur entière ne puisse être lue.

Un problème potentiel avec le nouveau régime est que perl peut planter à pratiquement n'importe quel point de l'exécution (par exemple, le SvIV() ci-dessus pourrait appeler FETCH() sur une variable liée qui plante alors). Ainsi, à tout moment, le RC de chaque SV doit être correctement comptabilisé. Dans l'exemple ci-dessus, une approche naïve pour éviter une libération prématurée de "sv" pourrait être :

SV *sv = *PL_stack_sp--;
IV i = SvIV(sv);
SvREFCNT_dec(sv); // avons i, donc c'est bon de libérer sv maintenant

mais cela signifie que "sv" fuit si SvIV() déclenche un plantage.

Pour éviter cela, le nouveau régime a pour principe général que les arguments restent sur la pile *jusqu'à ce qu'ils soient terminés*, puis sont supprimés et leur compte de référence ajusté à ce moment-là. Avec la nouvelle API, la fonction pp_add() ressemble à ceci :

{
    dTARGET;
    IV right = SvIV(PL_stack_sp[ 0]); // NB : arguments laissés sur la pile
    IV left  = SvIV(PL_stack_sp[-1]);
    TARGi(left + right, 1);
    rpp_replace_2_1(targ);
    return NORMAL;
}

La fonction rpp_replace_2_1() retire deux valeurs de la pile et en ajoute une nouvelle, tout en ajustant les comptes de référence de manière appropriée (selon qu'elle soit construite avec "PERL_RC_STACK" ou non).

Les fonctions rpp_() de la nouvelle API seront décrites en détail ci-dessous, mais en résumé :

Il existe également des variantes "_NN" qui supposent que tous les éléments retirés de la pile sont non NULL, et sont donc légèrement plus efficaces :

rpp_popfree_1_NN()
rpp_popfree_2_NN()

rpp_replace_1_1_NN(sv)
rpp_replace_2_1_NN(sv)

Il existe également quelques variantes "_IMM", qui attendent que la valeur unique poussée ou de remplacement soit immortelle, comme &PL_sv_undef - cela évite d'incrémenter le compte de référence du SV immortel. Peu importe si le compte de référence du SV atteint prématurément zéro, car sv_free2() le ressuscitera. Toutes les variantes ne sont pas fournies ; si une variante appropriée n'existe pas, il suffit d'utiliser une version standard "_1", bien qu'elle soit légèrement plus lente.

rpp_push_IMM(&PL_sv_undef)
rpp_xpush_IMM(&PL_sv_zero)
rpp_replace_1_IMM_NN(&PL_sv_yes)
rpp_replace_2_IMM_NN(&PL_sv_no)

Certaines de ces nouvelles fonctions sont triviales, mais doivent être utilisées de préférence à l'écriture de code direct car elles fonctionneront sur les builds RC et non-RC, et peuvent effectuer des vérifications et des assertions supplémentaires sur les builds "DEBUGGING".

Notez que rpp_popfree_1() etc. ne sont pas des remplacements directs pour "POPs". Les variantes rpp_() ne retournent pas de valeur et sont destinées à être appelées lorsque le SV est terminé. Donc

SV *sv = POPs;
... faire des choses avec sv ...

devient

SV *sv = *PL_stack_sp;
... faire des choses avec sv ...
rpp_popfree_1(); /* fait SvREFCNT_dec(*PL_stack_sp--) */

Les fonctions rpp_replace_M_N() sont des raccourcis pour retirer et libérer "M" éléments, puis ajouter et incrémenter les RC de "N" éléments. Notez qu'elles gèrent les cas limites tels qu'un ancien et un nouveau SV étant identiques.

rpp_replace_at(sp, sv) est similaire à rpp_replace_1_1(), sauf qu'elle remplace un SV à une adresse dans la pile plutôt qu'au sommet.

rpp_replace_at_norc(sp, sv) est similaire à rpp_replace_at(), sauf qu'elle suppose que "sv" a déjà un compte de référence incrémenté. Donc, un peu comme rpp_push_1_norc() (voir ci-dessous), elle ne prend pas la peine d'augmenter le compte de référence de "sv", ou sur les builds non-RC, elle le rend mortel à la place.

rpp_popfree_to(svp) est conçue pour remplacer un code comme

PL_stack_sp = PL_stack_base + cx->blk_oldsp;

qui apparaît généralement dans les ops de liste ou les sorties de portée lorsque les arguments sont terminés. Laissé inchangé, tous les SVs au-dessus de "oldsp" fuiraient. La nouvelle approche est

rpp_popfree_to(PL_stack_base + cx->blk_oldsp);

Il existe une variante rarement utilisée, rpp_obliterate_stack_to(), qui retire la pile jusqu'à l'index spécifié, quel que soit l'état RC actuel de la pile. Par exemple, si la pile est divisée, elle n'ajustera que les RC de tous les SVs qui se trouvent sous le point de division, tandis que rpp_popfree_to() libérerait aveuglément *tous* les SVs (sur les builds RC de toute façon). Pour les fonctions PP normales, vous ne devriez jamais utiliser que rpp_popfree_to(), qui est plus rapide.

Il n'y a pas de nouveaux équivalents pour toutes les macros pratiques comme POPi() et (frémissement) dPOPPOPiirl(). Celles-ci doivent être remplacées par les fonctions rpp_() ci-dessus et par les conversions et déclarations de variables rendues explicites, par exemple dPOPPOPiirl() devient :

IV right = SvIV(PL_stack_sp[ 0]);
IV left  = SvIV(PL_stack_sp[-1]);
rpp_popfree_2();

Quelques-unes des fonctions rpp_() avec "norc" dans leur nom n'ajustent pas le compte de référence sur les builds RC (mais, inversement, le font sur les builds non-RC).

rpp_push_1_norc(sv) effectue une simple "*++PL_stack_sp = sv" sur les builds RC. Elle est typiquement utilisée pour "enraciner" un SV nouvellement créé, qui a déjà un RC de 1. Sur les builds non-RC, elle rend le SV mortel à la place. Ainsi, par exemple, le code qui ressemblait auparavant à

mPUSHs(newSViv(i));

et qui se développait en l'équivalent de :

PUSHs(sv_2mortal(newSViv(i));

devrait être réécrit comme :

rpp_push_1_norc(newSViv(i));

Ceci parce que newSViv() et similaires créent un nouveau SV avec un compte de référence trop élevé (1 au lieu de 0). Ce compte est ensuite "donné" à la pile en le poussant. Inversement sur les builds non-RC, le compte est donné à la pile TEMPs.

De même, sur les builds RC, "sv = rpp_pop_1_norc()" effectue une simple "sv = *PL_stack_sv--" sans ajuster le compte de référence, tandis que sur les builds non-RC, elle incrémente réellement le compte de référence du SV. Elle est prévue pour les cas où vous souhaitez immédiatement incrémenter à nouveau le compte de référence après avoir retiré, par exemple lorsque le SV doit être immédiatement intégré quelque part. Par exemple, ce code :

SV *sv = PL_stack_sp[0];
SvREFCNT_inc(sv);
av_store(av, i, sv); /* en réalité, il faut vérifier la valeur de retour */
rpp_popfree_1();

peut être écrit plus efficacement comme

av_store(av, i, rpp_pop_1_norc());

En utilisant cette fonction, le code fonctionne correctement sur les builds RC et non-RC.

Une opération courante sur les ops de liste est d'imposer un contexte void, scalaire ou liste sur les arguments de retour, en éliminant éventuellement tout, ou tout sauf un, d'entre eux. rpp_context(mark, gimme, extra) fait cela. Comme première étape (pour la commodité et l'efficacité), il retire notionnellement "extra" arguments de la pile. Ensuite, pour le contexte de liste, il laisse les choses telles quelles. Pour le contexte void, le pointeur de pile est réinitialisé à mark, et tout ce qui est au-dessus est retiré. Pour le scalaire, l'argument supérieur (ou &PL_sv_undef) est déplacé du sommet vers mark+1 et tout ce qui est au-dessus est éliminé.

Les macros qui apparaissent au début de nombreuses fonctions PP pour vérifier le surcharge de l'op unaire ou binaire (entre autres choses) ont été remplacées par des fonctions inline rpp_try_AMAGIC_1() et _2(), qui s'appuient maintenant sur la fonction PP appelante pour choisir de retourner immédiatement plutôt que le retour ne soit caché dans la macro.

La fonction rpp_invoke_xs() appelle la fonction XS associée au CV, mais peut le faire via une fonction wrapper pour ajuster la pile si nécessaire.

perlapi - Perl API and internals documentation

DESCRIPTION

This document describes the internal API of Perl, which is subject to change between versions. It is intended for module authors and others who need to interact with Perl's internals, not for general programmers.

The primary source of information about Perl's internals is the source code itself, especially the files in the op/, pp/, and regcomp/ directories. This document aims to provide a higher-level overview of some of the key internal structures and functions.

Stack manipulation

The Perl stack is implemented as a C array of SV* pointers. The stack pointer PL_stack_sp points to the current top of the stack. The stack grows downwards, so pushing an element involves incrementing PL_stack_sp and assigning the element to the new location.

Several macros and functions are provided for manipulating the stack:

PP_add()
A helper function for adding items to the stack. It takes a format string similar to sprintf, where specifiers indicate how to interpret the following arguments. For example, PP_add("i") would push an integer onto the stack.
pp_add()
A low-level function that adds a single SV* to the stack. It's primarily used internally by other stack manipulation functions.
rpp_add()
Similar to pp_add(), but operates on the return stack rather than the argument stack.
rpp_xpush_1()
Pushes a single SV* onto the return stack. Deprecated in favor of rpp_push_1().
rpp_extend()
Extends the stack by a specified number of elements. Useful when you know you'll be pushing multiple items.
rpp_push_1()
Pushes a single SV* onto the return stack. This is the preferred way to push a single item onto the return stack.
push_stackinfo()
A newer function for pushing a new stack frame. It takes a type and a boolean indicating whether the new argument stack should be reference-counted. The older PUSHSTACKi(type) macro is defined as push_stackinfo(type, 0) for backward compatibility.
rpp_is_lone()
Checks if a given SV* is only referenced by the argument or temporary stacks. This can be used for optimizations, such as skipping unnecessary copying of return values.
rpp_stack_is_rc()
Indicates whether the current stack is reference-counted. This is important for functions like call_sv() which can be called from different contexts (e.g., standard PP functions vs. wrapped PP or XS functions).

The macros for pushing new stackinfos have been replaced with inline functions which don't rely on dSP being in scope, and which have less ambiguous names: they make it clear that a new stackinfo is being pushed, rather than just some sort of stack. push_stackinfo() also has a boolean argument indicating whether the new argument stack should be reference-counted or not. For backwards compatibility, PUSHSTACKi(type) is defined to be push_stackinfo(type, 0).

Some test scripts check for things like leaks by testing that the reference count of a particular variable has an expected value. If this is different on a perl built with PERL_RC_STACK, then the perl function Internals::stack_refcounted() can be used. This returns an integer, the lowest bit of which indicates that perl was built with PERL_RC_STACK. Other bits are reserved for future use and should be masked out.

Slab-based operator allocation

Note: this section describes a non-public internal API that is subject to change without notice.

Perl's internal error-handling mechanisms implement die (and its internal equivalents) using longjmp. If this occurs during lexing, parsing or compilation, we must ensure that any ops allocated as part of the compilation process are freed. (Older Perl versions did not adequately handle this situation: when failing a parse, they would leak ops that were stored in C auto variables and not linked anywhere else.)

To handle this situation, Perl uses op slabs that are attached to the currently-compiling CV. A slab is a chunk of allocated memory. New ops are allocated as regions of the slab. If the slab fills up, a new one is created (and linked from the previous one). When an error occurs and the CV is freed, any ops remaining are freed.

Each op is preceded by two pointers: one points to the next op in the slab, and the other points to the slab that owns it. The next-op pointer is needed so that Perl can iterate over a slab and free all its ops. (Op structures are of different sizes, so the slab's ops can't merely be treated as a dense array.) The slab pointer is needed for accessing a reference count on the slab: when the last op on a slab is freed, the slab itself is freed.

The slab allocator puts the ops at the end of the slab first. This will tend to allocate the leaves of the op tree first, and the layout will therefore hopefully be cache-friendly. In addition, this means that there's no need to store the size of the slab (see below on why slabs vary in size), because Perl can follow pointers to find the last op.

It might seem possible to eliminate slab reference counts altogether, by having all ops implicitly attached to PL_compcv when allocated and freed when the CV is freed. That would also allow op_free to skip FreeOp altogether, and thus free ops faster. But that doesn't work in those cases where ops need to survive beyond their CVs, such as re-evals.

The CV also has to have a reference count on the slab. Sometimes the first op created is immediately freed. If the reference count of the slab reaches 0, then it will be freed with the CV still pointing to it.

CVs use the CVf_SLABBED flag to indicate that the CV has a reference count on the slab. When this flag is set, the slab is accessible via CvSTART when CvROOT is not set, or by subtracting two pointers (2*sizeof(I32 *)) from CvROOT when it is set. The alternative to this approach of sneaking the slab into CvSTART during compilation would be to enlarge the xpvcv struct by another pointer. But that would make all CVs larger, even though slab-based op freeing is typically of benefit only for programs that make significant use of string eval.

When the CVf_SLABBED flag is set, the CV takes responsibility for freeing the slab. If CvROOT is not set when the CV is freed or undeffed, it is assumed that a compilation error has occurred, so the op slab is traversed and all the ops are freed.

Under normal circumstances, the CV forgets about its slab (decrementing the reference count) when the root is attached. So the slab reference counting that happens when ops are freed takes care of freeing the slab. In some cases, the CV is told to forget about the slab (cv_forget_slab) precisely so that the ops can survive after the CV is done away with.

Forgetting the slab when the root is attached is not strictly necessary, but avoids potential problems with CvROOT being written over. There is code all over the place, both in core and on CPAN, that does things with CvROOT, so forgetting the slab makes things more robust and avoids potential problems.

Since the CV takes ownership of its slab when flagged, that flag is never copied when a CV is cloned, as one CV could free a slab that another CV still points to, since forced freeing of ops ignores the reference count (but asserts that it looks right).

To avoid slab fragmentation, freed ops are marked as freed and attached to the slab's freed chain (an idea stolen from DBM::Deep). Those freed ops are reused when possible. Not reusing freed ops would be simpler, but it would result in significantly higher memory usage for programs with large if (DEBUG) {...} blocks.

SAVEFREEOP is slightly problematic under this scheme. Sometimes it can cause an op to be freed after its CV. If the CV has forcibly freed the ops on its slab and the slab itself, then we will be fiddling with a freed slab. Making SAVEFREEOP a no-op doesn't help, as sometimes an op can be savefreed when there is no compilation error, so the op would never be freed. It holds a reference count on the slab, so the whole slab would leak. So SAVEFREEOP now sets a special flag on the op (->op_savefree). The forced freeing of ops after a compilation error won't free any ops thus marked.

Since many pieces of code create tiny subroutines consisting of only a few ops, and since a huge slab would be quite a bit of baggage for those to carry around, the first slab is always very small. To avoid allocating too many slabs for a single CV, each subsequent slab is twice the size of the previous.

Smartmatch expects to be able to allocate an op at run time, run it, and then throw it away. For that to work the op is simply malloced when PL_compcv hasn't been set up. So all slab-allocated ops are marked as such (->op_slabbed), to distinguish them from malloced ops.
