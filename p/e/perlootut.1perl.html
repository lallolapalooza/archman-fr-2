PERLOOTUT(1perl) Guide de référence du programmeur Perl PERLOOTUT(1perl)

NOM

perlootut - Tutoriel sur la programmation orientée objet en Perl

DATE

Ce document a été créé en février 2011, et la dernière révision majeure date de février 2013.

Si vous lisez ceci dans le futur, il est possible que l'état de l'art ait changé. Nous vous recommandons de commencer par lire le document perlootut dans la dernière version stable de Perl, plutôt que cette version.

DESCRIPTION

Ce document fournit une introduction à la programmation orientée objet en Perl. Il commence par un bref aperçu des concepts derrière la conception orientée objet. Ensuite, il présente plusieurs systèmes OO différents de CPAN https://www.cpan.org qui s'appuient sur ce que Perl fournit.

Par défaut, le système OO intégré de Perl est très minimaliste, vous laissant faire la majeure partie du travail. Ce minimalisme avait beaucoup de sens en 1994, mais depuis Perl 5.0, un certain nombre de modèles courants ont émergé en Perl OO. Heureusement, la flexibilité de Perl a permis à un riche écosystème de systèmes Perl OO de prospérer.

Si vous voulez savoir comment fonctionne Perl OO en interne, le document perlobj explique les détails techniques.

Ce document suppose que vous comprenez déjà les bases de la syntaxe Perl, des types de variables, des opérateurs et des appels de sous-programmes. Si vous ne comprenez pas encore ces concepts, veuillez lire perlintro en premier. Vous devriez également lire les documents perlsyn, perlop et perlsub.

FONDEMENTS DE LA PROGRAMMATION ORIENTÉE OBJET

La plupart des systèmes orientés objet partagent un certain nombre de concepts communs. Vous avez probablement déjà entendu des termes comme « classe », « objet », « méthode » et « attribut ». Comprendre ces concepts facilitera grandement la lecture et l'écriture de code orienté objet. Si vous êtes déjà familier avec ces termes, vous devriez néanmoins parcourir cette section, car elle explique chaque concept en termes d'implémentation OO de Perl.

Le système OO de Perl est basé sur les classes. La POO basée sur les classes est assez courante. Elle est utilisée par Java, C++, C#, Python, Ruby et de nombreux autres langages. Il existe également d'autres paradigmes d'orientation objet. JavaScript est le langage le plus populaire pour utiliser un autre paradigme. Le système OO de JavaScript est basé sur des prototypes.

Objet

Un objet est une structure de données qui regroupe des données et des sous-programmes qui opèrent sur ces données. Les données d'un objet sont appelées attributs, et ses sous-programmes sont appelés méthodes. Un objet peut être considéré comme un nom (une personne, un service web, un ordinateur).

Un objet représente une seule chose discrète. Par exemple, un objet pourrait représenter un fichier. Les attributs d'un objet fichier pourraient inclure son chemin, son contenu et la dernière date de modification. Si nous créions un objet pour représenter /etc/hostname sur une machine nommée « foo.example.com », le chemin de cet objet serait « /etc/hostname », son contenu serait « foo\n », et sa dernière date de modification serait 1304974868 secondes depuis le début de l'époque.

Les méthodes associées à un fichier pourraient inclure rename() et write().

En Perl, la plupart des objets sont des hachages, mais les systèmes OO que nous recommandons vous évitent de vous en soucier. En pratique, il est préférable de considérer la structure de données interne d'un objet comme opaque.

Classe

Une classe définit le comportement d'une catégorie d'objets. Une classe est un nom pour une catégorie (comme « Fichier »), et une classe définit également le comportement des objets de cette catégorie.

Tous les objets appartiennent à une classe spécifique. Par exemple, notre objet /etc/hostname appartient à la classe "Fichier". Lorsque nous voulons créer un objet spécifique, nous commençons par sa classe, et nous construisons ou instancions un objet. Un objet spécifique est souvent appelé une instance d'une classe.

En Perl, n'importe quel paquet peut être une classe. La différence entre un paquet qui est une classe et un qui ne l'est pas est basée sur la façon dont le paquet est utilisé. Voici notre « déclaration de classe » pour la classe "Fichier" :

package File;

En Perl, il n'y a pas de mot-clé spécial pour construire un objet. Cependant, la plupart des modules OO sur CPAN utilisent une méthode nommée new() pour construire un nouvel objet :

my $hostname = File->new(
    path          => '/etc/hostname',
    content       => "foo\n",
    last_mod_time => 1304974868,
);

(Ne vous inquiétez pas de cet opérateur "->", il sera expliqué plus tard.)

Bénédiction

Comme nous l'avons dit précédemment, la plupart des objets Perl sont des hachages, mais un objet peut être une instance de n'importe quel type de données Perl (scalaire, tableau, etc.). Transformer une structure de données brute en objet se fait en bénissant cette structure de données à l'aide de la fonction "bless" de Perl.

Bien que nous vous suggérions fortement de ne pas construire vos objets à partir de zéro, vous devriez connaître le terme bless. Une structure de données bénie (également appelée « référent ») est un objet. Nous disons parfois qu'un objet a été « béni dans une classe ».

Une fois qu'un référent a été béni, la fonction "blessed" du module principal Scalar::Util peut nous indiquer son nom de classe. Cette sous-routine retourne la classe d'un objet lorsqu'on lui passe un objet, et faux sinon.

use Scalar::Util 'blessed';
print blessed($hash);      # undef
print blessed($hostname);  # File

Constructeur

Un constructeur crée un nouvel objet. En Perl, le constructeur d'une classe n'est qu'une autre méthode, contrairement à certains autres langages qui fournissent une syntaxe pour les constructeurs. La plupart des classes Perl utilisent "new" comme nom pour leur constructeur :

my $file = File->new(...);

Méthodes

Vous avez déjà appris qu'une méthode est un sous-programme qui opère sur un objet. Vous pouvez considérer une méthode comme les choses qu'un objet peut faire. Si un objet est un nom, alors les méthodes sont ses verbes (sauvegarder, imprimer, ouvrir).

En Perl, les méthodes sont simplement des sous-programmes qui vivent dans le paquet de la classe. Les méthodes sont toujours écrites pour recevoir l'objet comme premier argument :

sub print_info {
    my $self = shift;
    print "Ce fichier est à ", $self->path, "\n";
}
$file->print_info;
# Ce fichier est à /etc/hostname

Ce qui rend une méthode spéciale, c'est la façon dont elle est appelée. L'opérateur flèche ("->") indique à Perl que nous appelons une méthode.

Lorsque nous effectuons un appel de méthode, Perl s'arrange pour que l'invoquant de la méthode soit passé comme premier argument. Invoquant est un nom fantaisiste pour la chose à gauche de la flèche. L'invoquant peut être soit un nom de classe, soit un objet. Nous pouvons également passer des arguments supplémentaires à la méthode :

sub print_info {
    my $self   = shift;
    my $prefix = shift // "Ce fichier est à ";
    print $prefix, ", ", $self->path, "\n";
}
$file->print_info("Le fichier est situé à ");
# Le fichier est situé à /etc/hostname

Attributs

Chaque classe peut définir ses attributs. Lorsque nous instancions un objet, nous attribuons des valeurs à ces attributs. Par exemple, chaque objet "Fichier" a un chemin. Les attributs sont parfois appelés propriétés.

Perl n'a pas de syntaxe spéciale pour les attributs. Sous le capot, les attributs sont souvent stockés comme des clés dans le hachage sous-jacent de l'objet, mais ne vous en souciez pas.

Nous vous recommandons de n'accéder aux attributs que via des méthodes accesseurs. Ce sont des méthodes qui peuvent obtenir ou définir la valeur de chaque attribut. Nous l'avons vu plus tôt dans l'exemple print_info(), qui appelle "$self->path".

Vous pourriez également voir les termes getter et setter. Ce sont deux types d'accesseurs. Un getter récupère la valeur de l'attribut, tandis qu'un setter la définit. Un autre terme pour un setter est mutateur.

Les attributs sont généralement définis comme en lecture seule ou en lecture-écriture. Les attributs en lecture seule ne peuvent être définis que lors de la création initiale de l'objet, tandis que les attributs en lecture-écriture peuvent être modifiés à tout moment.

s="Pp">La valeur d'un attribut peut elle-même être un autre objet. Par exemple, au lieu de retourner son heure de dernière modification sous forme de nombre, la classe "File" pourrait retourner un objet DateTime représentant cette valeur.

Il est possible d'avoir une classe qui n'expose aucun attribut publiquement modifiable. Toutes les classes n'ont pas d'attributs et de méthodes.

Polymorphisme

Polymorphisme est une façon sophistiquée de dire que des objets de deux classes différentes partagent une API. Par exemple, nous pourrions avoir les classes "File" et "WebPage" qui ont toutes deux une méthode print_content(). Cette méthode pourrait produire une sortie différente pour chaque classe, mais elles partagent une interface commune.

Alors que les deux classes peuvent différer de bien des manières, en ce qui concerne la méthode print_content(), elles sont identiques. Cela signifie que nous pouvons essayer d'appeler la méthode print_content() sur un objet de l'une ou l'autre classe, et nous n'avons pas besoin de savoir à quelle classe appartient l'objet !

Le polymorphisme est l'un des concepts clés de la conception orientée objet.

Héritage

L'héritage vous permet de créer une version spécialisée d'une classe existante. L'héritage permet à la nouvelle classe de réutiliser les méthodes et les attributs d'une autre classe.

Par exemple, nous pourrions créer une classe "File::MP3" qui hérite de "File". Un "File::MP3" est un type plus spécifique de "File". Tous les fichiers mp3 sont des fichiers, mais tous les fichiers ne sont pas des fichiers mp3.

Nous faisons souvent référence aux relations d'héritage comme étant des relations parent-enfant ou "superclasse"/"sous-classe". Parfois, nous disons que l'enfant a une relation est-un avec sa classe parente.

"File" est une superclasse de "File::MP3", et "File::MP3" est une sous-classe de "File".

package File::MP3;
use parent 'File';

Le module parent est l'une des plusieurs façons dont Perl vous permet de définir des relations d'héritage.

Perl autorise l'héritage multiple, ce qui signifie qu'une classe peut hériter de plusieurs parents. Bien que cela soit possible, nous le déconseillons fortement. En général, vous pouvez utiliser des rôles pour faire tout ce que vous pouvez faire avec l'héritage multiple, mais d'une manière plus propre.

Notez qu'il n'y a rien de mal à définir plusieurs sous-classes d'une classe donnée. C'est à la fois courant et sûr. Par exemple, nous pourrions définir les classes "File::MP3::FixedBitrate" et "File::MP3::VariableBitrate" pour distinguer différents types de fichiers mp3.

Surcharge de méthodes et résolution de méthodes

L'héritage permet à deux classes de partager du code. Par défaut, chaque méthode de la classe parente est également disponible dans la classe enfant. L'enfant peut explicitement surcharger une méthode parente pour fournir sa propre implémentation. Par exemple, si nous avons un objet "File::MP3", il possède la méthode print_info() de "File":

my $cage = File::MP3->new(
    path          => 'mp3s/My-Body-Is-a-Cage.mp3',
    content       => $mp3_data,
    last_mod_time => 1304974868,
    title         => 'My Body Is a Cage',
);
$cage->print_info;
# Le fichier est à mp3s/My-Body-Is-a-Cage.mp3

Si nous voulions inclure le titre du mp3 dans le message, nous pourrions surcharger la méthode :

package File::MP3;
use parent 'File';
sub print_info {
    my $self = shift;
    print "Ce fichier est à ", $self->path, "\n";
    print "Son titre est ", $self->title, "\n";
}
$cage->print_info;
# Le fichier est à mp3s/My-Body-Is-a-Cage.mp3
# Son titre est My Body Is a Cage

Le processus de détermination de la méthode à utiliser est appelé résolution de méthodes. Ce que Perl fait, c'est regarder d'abord la classe de l'objet ("File::MP3" dans ce cas). Si cette classe définit la méthode, alors la version de la méthode de cette classe est appelée. Sinon, Perl examine chaque classe parente à tour de rôle. Pour "File::MP3", son unique parent est "File". Si "File::MP3" ne définit pas la méthode, mais "File" le fait, alors Perl appelle la méthode dans "File".

Si "File" héritait de "DataSource", qui héritait de "Thing", alors Perl continuerait à chercher "vers le haut de la chaîne" si nécessaire.

Il est possible d'appeler explicitement une méthode parente depuis une classe enfant :

package File::MP3;
use parent 'File';
sub print_info {
    my $self = shift;
    $self->SUPER::print_info();
    print "Son titre est ", $self->title, "\n";
}

La partie "SUPER::" indique à Perl de rechercher la méthode print_info() dans la chaîne d'héritage de la classe "File::MP3". Lorsqu'elle trouve la classe parente qui implémente cette méthode, la méthode est appelée.

Nous avons mentionné l'héritage multiple plus tôt. Le principal problème de l'héritage multiple est qu'il complique grandement la résolution de méthodes. Voir perlobj pour plus de détails.

Encapsulation

L'encapsulation est l'idée qu'un objet est opaque. Lorsqu'un autre développeur utilise votre classe, il n'a pas besoin de savoir comment elle est implémentée, il a juste besoin de savoir ce qu'elle fait.

L'encapsulation est importante pour plusieurs raisons. Premièrement, elle vous permet de séparer l'API publique de l'implémentation privée. Cela signifie que vous pouvez modifier cette implémentation sans casser l'API.

Deuxièmement, lorsque les classes sont bien encapsulées, elles deviennent plus faciles à spécialiser. Idéalement, une sous-classe utilise les mêmes API pour accéder aux données de l'objet que celles utilisées par sa classe parente. En réalité, la spécialisation implique parfois de violer l'encapsulation, mais une bonne API peut minimiser la nécessité de le faire.

Nous avons mentionné plus tôt que la plupart des objets Perl sont implémentés comme des hachages en interne. Le principe d'encapsulation nous dit que nous ne devrions pas nous fier à cela. Au lieu de cela, nous devrions utiliser des méthodes d'accès pour accéder aux données de ce hachage. Les systèmes d'objets que nous recommandons ci-dessous automatisent tous la génération de méthodes d'accès. Si vous en utilisez un, vous ne devriez jamais avoir à accéder directement à l'objet en tant que hachage.

Composition

Dans le code orienté objet, nous constatons souvent qu'un objet référence un autre objet. Cela s'appelle la composition, ou une relation a-un.

Plus tôt, nous avons mentionné que l'accesseur "last_mod_time" de la classe "File" pourrait retourner un objet DateTime. C'est un exemple parfait de composition. Nous pourrions aller encore plus loin et faire en sorte que les accesseurs "path" et "content" retournent également des objets. La classe "File" serait alors composée de plusieurs autres objets.

Rôles

Les rôles sont quelque chose qu'une classe *fait*, plutôt que quelque chose qu'elle *est*. Les rôles sont relativement nouveaux en Perl, mais sont devenus assez populaires. Les rôles sont appliqués aux classes. Parfois, nous disons que les classes consomment des rôles.

Les rôles sont une alternative à l'héritage pour fournir du polymorphisme. Supposons que nous ayons deux classes, "Radio" et "Computer". Ces deux objets ont des interrupteurs marche/arrêt. Nous voulons modéliser cela dans nos définitions de classe.

Nous pourrions faire hériter les deux classes d'une classe parente commune, comme "Machine", mais toutes les machines n'ont pas d'interrupteurs marche/arrêt. Nous pourrions créer une classe parente appelée "HasOnOffSwitch", mais c'est très artificiel. Les radios et les ordinateurs ne sont pas des spécialisations de ce parent. Ce parent est vraiment une création plutôt ridicule.

C'est là qu'interviennent les rôles. Il est très logique de créer un rôle "HasOnOffSwitch" et de l'appliquer aux deux classes. Ce rôle définirait une API connue, comme la fourniture des méthodes turn_on() et turn_off().

Perl n'a pas de moyen intégré pour exprimer les rôles. Par le passé, les gens prenaient leur mal en patience et utilisaient l'héritage multiple. Aujourd'hui, il existe plusieurs bons choix sur CPAN pour utiliser les rôles.

Quand utiliser la POO

L'orientation objet n'est pas la meilleure solution à tous les problèmes. Dans Perl Best Practices (copyright 2004, publié par O'Reilly Media, Inc.), Damian Conway fournit une liste de critères à utiliser pour décider si la POO est adaptée à votre problème :

  • Le système en cours de conception est vaste, ou susceptible de le devenir.
  • Les données peuvent être agrégées en structures évidentes, surtout s'il y a une grande quantité de données dans chaque agrégat.
  • Les différents types d'agrégats de données forment une hiérarchie naturelle qui facilite l'utilisation de l'héritage et du polymorphisme.
  • Vous avez un élément de donnée sur lequel de nombreuses opérations différentes sont appliquées.
  • Vous devez effectuer les mêmes opérations générales sur des types de données apparentés, mais avec de légères variations en fonction du type de données spécifiques sur lesquelles les opérations sont appliquées.
  • Il est probable que vous devrez ajouter de nouveaux types de données plus tard.
  • Les interactions typiques entre les éléments de données sont mieux représentées par des opérateurs.
  • L'implémentation des composants individuels du système est susceptible de changer avec le temps.
  • La conception du système est déjà orientée objet.
  • Un grand nombre d'autres programmeurs utiliseront vos modules de code.

SYSTÈMES DE POO EN PERL

Comme nous l'avons mentionné précédemment, le système POO intégré de Perl est très minimaliste, mais aussi très flexible. Au fil des années, de nombreuses personnes ont développé des systèmes wqui s'appuient sur le système intégré de Perl pour offrir plus de fonctionnalités et de commodité.

Nous vous recommandons vivement d'utiliser l'un de ces systèmes. Même le plus minimal d'entre eux élimine beaucoup de répétitions et de code boilerplate. Il n'y a vraiment aucune bonne raison d'écrire vos classes à partir de zéro en Perl.

Si vous êtes intéressé par les mécanismes internes de ces systèmes, consultez perlobj.

Moose

Moose se présente comme un « système objet postmoderne pour Perl 5 ». Ne vous laissez pas effrayer, l'étiquette « postmoderne » est un clin d'œil à la description de Perl par Larry comme « le premier langage informatique postmoderne ».

"Moose" fournit un système OO complet et moderne. Son influence principale est le Common Lisp Object System, mais il emprunte également des idées à Smalltalk et à plusieurs autres langages. "Moose" a été créé par Stevan Little et s'inspire largement de son travail sur la conception OO de Raku.

Voici notre classe "File" utilisant "Moose" :

package File;
use Moose;
has path          => ( is => 'ro' );
has content       => ( is => 'ro' );
has last_mod_time => ( is => 'ro' );
sub print_info {
    my $self = shift;
    print "This file is at ", $self->path, "\n";
}

"Moose" offre un certain nombre de fonctionnalités :

  • Sucre déclaratif

    "Moose" fournit une couche de « sucre » déclaratif pour définir des classes. Ce sucre est simplement un ensemble de fonctions exportées qui rendent la déclaration du fonctionnement de votre classe plus simple et plus agréable. Cela vous permet de décrire *ce qu'est* votre classe, plutôt que de devoir dire à Perl *comment* implémenter votre classe.

    La sous-routine has() déclare un attribut, et "Moose" crée automatiquement des accesseurs pour ces attributs. Elle s'occupe également de créer une méthode new() pour vous. Ce constructeur connaît les attributs que vous avez déclarés, vous pouvez donc les définir lors de la création d'un nouveau "File".

  • Rôles intégrés

    "Moose" vous permet de définir des rôles de la même manière que vous définissez des classes :

    package HasOnOffSwitch;
use Moose::Role;
has is_on => (
    is  => 'rw',
    isa => 'Bool',
);
sub turn_on {
    my $self = shift;
    $self->is_on(1);
}
sub turn_off {
    my $self = shift;
    $self->is_on(0);
}
  • Un système de types miniature

    Dans l'exemple ci-dessus, vous pouvez voir que nous avons passé "isa => 'Bool'" à has() lors de la création de notre attribut "is_on". Cela indique à "Moose" que cet attribut doit être une valeur booléenne. Si nous essayons de le définir à une valeur invalide, notre code générera une erreur.

  • Introspection et manipulation complètes

    Les fonctionnalités d'introspection intégrées de Perl sont assez minimales. "Moose" s'appuie sur elles et crée une couche d'introspection complète pour vos classes. Cela vous permet de poser des questions comme « quelles méthodes la classe File implémente-t-elle ? ». Cela vous permet également de modifier vos classes par programmation.

  • Auto-hébergé et extensible

    "Moose" se décrit à l'aide de sa propre API d'introspection. En plus d'être un tour de passe-passe sympa, cela signifie que vous pouvez étendre "Moose" en utilisant "Moose" lui-même.

  • Riche écosystème

    Il existe un riche écosystème d'extensions "Moose" sur CPAN sous le nom d'espace MooseX. De plus, de nombreux modules sur CPAN utilisent déjà "Moose", vous fournissant de nombreux exemples pour apprendre.

  • Beaucoup plus de fonctionnalités

    "Moose" est un outil très puissant, et nous ne pouvons pas couvrir toutes ses fonctionnalités ici. Nous vous encourageons à en apprendre davantage en lisant la documentation "Moose", en commençant par Moose::Manual https://metacpan.org/pod/Moose::Manual.

Bien sûr, "Moose" n'est pas parfait.

"Moose" peut ralentir le chargement de votre code. "Moose" lui-même n'est pas petit, et il effectue *beaucoup* de génération de code lorsque vous définissez votre classe. Cette génération de code signifie que votre code d'exécution est aussi rapide que possible, mais vous le payez lors du premier chargement de vos modules.

Ce temps de chargement peut poser problème lorsque la vitesse de démarrage est importante, comme avec un script en ligne de commande ou un script CGI « tout simple » qui doit être chargé à chaque exécution.

Avant de paniquer, sachez que beaucoup de gens utilisent "Moose" pour des outils en ligne de commande et d'autres codes sensibles au démarrage. Nous vous encourageons à essayer "Moose" d'abord avant de vous soucier de la vitesse de démarrage.

"Moose" a également plusieurs dépendances sur d'autres modules. La plupart d'entre eux sont de petits modules autonomes, dont un certain nombre ont été issus de "Moose". "Moose" lui-même, et certaines de ses dépendances, nécessitent un compilateur. Si vous devez installer votre logiciel sur un système sans compilateur, ou si avoir *des* dépendances est un problème, alors "Moose" n'est peut-être pas fait pour vous.

Moo

Si vous essayez "Moose" et constatez que l'un de ces problèmes vous empêche d'utiliser "Moose", nous vous encourageons à considérer Moo ensuite. "Moo" implémente un sous-ensemble des fonctionnalités de "Moose" dans un package plus simple. Pour la plupart des fonctionnalités qu'il implémente, l'API utilisateur final est *identique* à celle de "Moose", ce qui signifie que vous pouvez passer de "Moo" à "Moose" assez facilement.

"Moo" n'implémente pas la majeure partie de l'API d'introspection de "Moose", il est donc souvent plus rapide lors du chargement de vos modules. De plus, aucune de ses dépendances ne nécessite XS, il peut donc être installé sur des machines sans compilateur.

L'une des fonctionnalités les plus intéressantes de "Moo" est son interopérabilité avec "Moose". Lorsque quelqu'un essaie d'utiliser l'API d'introspection de "Moose" sur une classe ou un rôle "Moo", il est transparentement gonflé en une classe ou un rôle "Moose". Cela facilite l'intégration du code utilisant "Moo" dans une base de code "Moose" et vice versa.

Par exemple, une classe "Moose" peut hériter d'une classe "Moo" en utilisant "extends" ou consommer un rôle "Moo" en utilisant "with".

Les auteurs de "Moose" espèrent qu'un jour "Moo" pourra être rendu obsolète en améliorant suffisamment "Moose", mais pour l'instant, il offre une alternative intéressante à "Moose".

Class::Accessor

Class::Accessor est le polaire opposé de "Moose". Il offre très peu de fonctionnalités, et n'est pas auto-hébergé.

Il est cependant très simple, pur Perl, et il n'a aucune dépendance non-core. Il offre également une API « semblable à Moose » sur demande pour les fonctionnalités qu'il prend en charge.

Même s'il ne fait pas grand-chose, il est toujours préférable d'écrire vos propres classes à partir de zéro.

Voici notre classe "File" avec "Class::Accessor" :

package File;
use Class::Accessor 'antlers';
has path          => ( is => 'ro' );
has content       => ( is => 'ro' );
has last_mod_time => ( is => 'ro' );
sub print_info {
    my $self = shift;
    print "This file is at ", $self->path, "\n";
}

Le drapeau d'importation "antlers" indique à "Class::Accessor" que vous souhaitez définir vos attributs en utilisant une syntaxe similaire à "Moose". Le seul paramètre que vous pouvez passer à "has" est "is". Nous vous recommandons d'utiliser cette syntaxe semblable à Moose si vous choisissez "Class::Accessor" car cela signifie que vous aurez une voie de mise à niveau plus douce si vous décidez plus tard de passer à "Moose".

Comme "Moose", "Class::Accessor" génère des méthodes accesseurs et un constructeur pour votre classe.

Class::Tiny

Enfin, nous avons Class::Tiny. Ce module porte vraiment bien son nom. Il a une API incroyablement minimale et aucune dépendance sur les versions récentes de Perl. Néanmoins, nous pensons qu'il est beaucoup plus facile à utiliser que d'écrire votre propre code OO à partir de zéro.

Voici notre classe "File" encore une fois :

package File;
use Class::Tiny qw( path content last_mod_time );
sub print_info {
    my $self = shift;
    print "This file is at ", $self->path, "\n";
}

C'est tout !

Avec "Class::Tiny", tous les accesseurs sont en lecture-écriture. Il génère un constructeur pour vous, ainsi que les accesseurs que vous définissez.

Vous pouvez également utiliser Class::Tiny::Antlers pour une syntaxe semblable à "Moose".

Role::Tiny

Comme nous l'avons mentionné précédemment, les rôles offrent une alternative à l'héritage, mais Perl n'a aucun support de rôle intégré. Si vous choisissez d'utiliser Moose, il est livré avec une implémentation complète des rôles. Comment

DESCRIPTION

Bienvenue dans le tutoriel sur l'orientation objet en Perl ! Ce tutoriel a été écrit il y a un certain temps, et l'écosystème Perl a considérablement évolué. Nous nous concentrerons ici sur les systèmes d'objets les plus courants en Perl. Vous pourrez aussi les trouver utiles lorsque vous commencerez à écrire des programmes pour des systèmes embarqués.

Les Perlistes s'intéressent depuis longtemps à la programmation orientée objet. Le système de base de Perl est suffisamment flexible pour implémenter une variété de systèmes OO, et c'est ce qui a conduit à une profusion de systèmes OO différents sur CPAN. Heureusement, vous n'avez pas à choisir entre tous, car beaucoup d'entre eux ont des points communs.

A Note on Role::Tiny

Si vous utilisez déjà l'un de nos autres modules OO recommandés, vous pouvez toujours utiliser les rôles avec "Role::Tiny".

"Role::Tiny" fournit certaines des mêmes fonctionnalités que le système de rôles de Moose, mais dans un package beaucoup plus petit. Notamment, il ne prend pas en charge les déclarations d'attributs, vous devez donc les faire manuellement. Néanmoins, il est utile et fonctionne bien avec "Class::Accessor" et "Class::Tiny".

OO System Summary

Voici un bref résumé des options que nous avons couvertes :

  • Moose

    "Moose" est l'option maximale. Elle possède de nombreuses fonctionnalités, un grand écosystème et une base d'utilisateurs florissante. Nous avons également brièvement couvert Moo. "Moo" est la version allégée de "Moose", et une alternative raisonnable lorsque Moose ne convient pas à votre application.

  • Class::Accessor

    "Class::Accessor" fait beaucoup moins que "Moose", et constitue une bonne alternative si vous trouvez "Moose" écrasant. Il existe depuis longtemps et est bien éprouvé. Il dispose également d'un mode de compatibilité "Moose" minimal qui facilite la migration de "Class::Accessor" vers "Moose".

  • Class::Tiny

    "Class::Tiny" est l'option absolument minimale. Il n'a aucune dépendance, et presque aucune syntaxe à apprendre. C'est une bonne option pour un environnement super minimaliste et pour assembler rapidement quelque chose sans avoir à se soucier des détails.

  • Role::Tiny

    Utilisez "Role::Tiny" avec "Class::Accessor" ou "Class::Tiny" si vous envisagez l'héritage multiple. Si vous optez pour "Moose", il est livré avec sa propre implémentation de rôles.

Other OO Systems

Il existe littéralement des dizaines d'autres modules liés à l'OO sur CPAN en dehors de ceux couverts ici, et vous risquez d'en rencontrer un ou plusieurs si vous travaillez avec le code d'autres personnes.

De plus, de nombreux codes en production effectuent toute leur OO « à la main », en utilisant uniquement les fonctionnalités OO intégrées de Perl. Si vous devez maintenir un tel code, vous devriez lire perlobj pour comprendre exactement comment fonctionne l'OO intégrée de Perl.

CONCLUSION

Comme nous l'avons dit précédemment, le système OO minimaliste de Perl a conduit à une profusion de systèmes OO sur CPAN. Bien que vous puissiez toujours revenir à la base et écrire vos classes manuellement, il n'y a vraiment aucune raison de le faire avec Perl moderne.

Pour les petits systèmes, "Class::Tiny" et "Class::Accessor" fournissent tous deux des systèmes d'objets minimaux qui s'occupent du boilerplate de base pour vous.

Pour les projets plus importants, Moose fournit un riche ensemble de fonctionnalités qui vous permettront de vous concentrer sur l'implémentation de votre logique métier. Moo offre une alternative intéressante à Moose lorsque vous souhaitez de nombreuses fonctionnalités mais avez besoin d'un temps de compilation plus rapide ou d'éviter XS.

Nous vous encourageons à expérimenter et à évaluer Moose, Moo, Class::Accessor et Class::Tiny pour voir quel système OO vous convient le mieux.
