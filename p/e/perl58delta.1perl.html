PERL58DELTA(1perl) Guide de référence du programmeur Perl PERL58DELTA(1perl)

NOM

perl58delta - nouveautés de la version perl v5.8.0

DESCRIPTION

Ce document décrit les différences entre la version 5.6.0 et la version 5.8.0.

Beaucoup des corrections de bugs dans 5.8.0 ont déjà été vues dans la version de maintenance 5.6.1, car les deux versions ont été maintenues en étroite coordination (alors que 5.8.0 était encore appelée 5.7.quelque chose).

Les changements qui ont été intégrés dans la version 5.6.1 sont marqués "[561]". Beaucoup de ces changements ont été développés davantage depuis la sortie de 5.6.1, ceux-ci sont marqués "[561+]".

Vous pouvez voir la liste des changements de la version 5.6.1 (tant ceux de la version 5.005_03 que ceux de la version 5.6.0) en lisant perl561delta.

Points forts de la version 5.8.0

  • Meilleur support Unicode
  • Nouvelle implémentation IO
  • Nouvelle implémentation de threads
  • Meilleure précision numérique
  • Signaux sûrs
  • Nombreux nouveaux modules
  • Tests de régression plus poussés

Changements incompatibles

Incompatibilité binaire

Perl 5.8 n'est pas binaire compatible avec les versions antérieures de Perl.

Vous devez recompiler vos modules XS.

(Les modules pure Perl devraient continuer à fonctionner.)

La raison principale de cette discontinuité est la nouvelle architecture IO appelée PerlIO. PerlIO est la configuration par défaut car sans elle, de nombreuses nouvelles fonctionnalités de Perl 5.8 ne peuvent pas être utilisées. En d'autres termes : vous devez simplement recompiler vos modules contenant du code XS, désolé pour cela.

Dans les futures versions de Perl, les modules XS non compatibles avec PerlIO pourraient ne plus être supportés du tout. Cela ne devrait pas être trop difficile pour les auteurs de modules cependant : PerlIO a été conçu comme un remplacement direct (au niveau du code source) de l'interface stdio.

Selon votre plateforme, il y a aussi d'autres raisons pour lesquelles nous avons décidé de casser la compatibilité binaire, veuillez lire la suite.

Plateformes 64 bits et malloc

Si vos pointeurs font 64 bits de large, le malloc de Perl n'est plus utilisé car il ne fonctionne pas bien avec les pointeurs de 8 octets. De plus, généralement, les malloc système sur de telles plateformes sont bien mieux optimisés pour de tels modèles mémoire larges que le malloc de Perl. Certaines applications Perl gourmandes en mémoire comme PDL ne fonctionnent pas bien avec le malloc de Perl. Enfin, d'autres applications que Perl (comme mod_perl) préfèrent le malloc système. Ces plateformes incluent Alpha et HPPA 64 bits, MIPS, PPC et Sparc.

Dynaload AIX

Le dynaload AIX utilise maintenant, dans les versions 4.3 et plus récentes d'AIX, l'interface native dlopen d'AIX au lieu de l'ancienne interface émulée. Ce changement cassera probablement la compatibilité arrière avec les modules compilés. Ce changement a été fait pour rendre Perl plus conforme avec d'autres applications comme mod_perl qui utilisent l'interface native AIX.

Les attributs pour les variables "my" sont maintenant gérés à l'exécution

La syntaxe "my EXPR : ATTRS" applique maintenant les attributs de variable à l'exécution. (Les variables de sous-routine et "our" reçoivent toujours les attributs à la compilation.) Voir attributes pour des détails supplémentaires. En particulier, cela permet cependant aux attributs de variable d'être utiles pour les interfaces "tie", ce qui était une lacune des versions antérieures. Notez que la nouvelle sémantique ne fonctionne pas avec le module Attribute::Handlers (depuis la version 0.76).

Extension Socket dynamique sous VMS

L'extension Socket est maintenant chargée dynamiquement au lieu d'être intégrée statiquement. Cela peut ou peut ne pas être un problème avec d'anciennes piles TCP/IP de VMS : nous ne savons pas car nous n'avons pas pu tester Perl dans de telles configurations.

Point flottant au format IEEE par défaut sur OpenVMS Alpha

Perl utilise maintenant le format IEEE (T_FLOAT) comme format de point flottant interne par défaut sur OpenVMS Alpha, rompant potentiellement la compatibilité binaire avec les bibliothèques externes ou les données existantes. G_FLOAT est toujours disponible en tant qu'option de configuration. Le défaut sur VAX (D_FLOAT) n'a pas changé.

Nouvelle sémantique Unicode (plus de "use utf8", presque)

Précédemment, dans Perl 5.6, pour utiliser Unicode, on disait "use utf8", puis les opérations (comme la concaténation de chaînes) étaient conscientes d'Unicode dans cette portée lexicale.

Cette interface s'est avérée peu pratique, et dans Perl 5.8, le modèle Unicode a complètement changé : maintenant, l'"unicité" est liée aux données elles-mêmes, et la plupart du temps "use utf8" n'est pas nécessaire du tout. Le seul usage restant de "use utf8" est lorsque le script Perl lui-même a été écrit dans l'encodage UTF-8 d'Unicode. (UTF-8 n'a pas été rendu par défaut car il existe de nombreux scripts Perl qui utilisent divers jeux de caractères nationaux sur huit bits, ce qui serait illégal en UTF-8.)

Voir perluniintro pour l'explication du modèle actuel, et utf8 pour l'usage actuel du pragma utf8.

Nouvelles propriétés Unicode

Les *scripts* Unicode sont maintenant supportés. Les scripts sont similaires (et supérieurs) aux *blocs* Unicode. La différence entre les scripts et les blocs est que les scripts sont les glyphes utilisés par une langue ou un groupe de langues, tandis que les blocs sont des regroupements plus artificiels de (principalement) 256 caractères basés sur la numérotation Unicode.

En général, les scripts sont plus inclusifs, mais pas universellement ainsi. Par exemple, alors que le script "Latin" inclut tous les caractères latins et leurs diverses versions ornées de diacritiques, il n'inclut pas la ponctuation ou les chiffres divers (car ils ne sont pas uniquement "Latins").

Un certain nombre d'autres propriétés sont maintenant supportées, y compris "\p{L}", "\p{Any}" "\p{Assigned}", "\p{Unassigned}", "\p{Blank}" [561] et "\p{SpacePerl}" [561] (avec leurs versions "\P{...}", bien sûr). Voir perlunicode pour les détails, et d'autres ajouts.

Le préfixe "In" ou "Is" aux noms utilisés avec "\p{...}" et "\P{...}" est maintenant presque toujours facultatif. La seule exception est qu'un préfixe "In" est requis pour signifier un bloc Unicode lorsqu'un nom de bloc entre en conflit avec un nom de script. Par exemple, "\p{Tibetan}" fait référence au script, tandis que "\p{InTibetan}" fait référence au bloc. Lorsqu'il n'y a pas de conflit de nom, vous pouvez omettre le "In" du nom du bloc (par ex. "\p{BraillePatterns}"), mais par sécurité, il est probablement préférable d'utiliser toujours le "In").

REF(...) à la place de SCALAR(...)

Une référence à une référence se chaîne maintenant comme "REF(0x81485ec)" au lieu de "SCALAR(0x81485ec)" afin d'être plus cohérent avec la valeur de retour de ref().

pack/unpack D/F recyclés

Les formats "D" et "F" dans pack et unpack ont été rendus recyclables. Auparavant, ils se basaient sur des valeurs flottantes littérales qui étaient fixées lors de la compilation. Cela pouvait poser problème sur les machines où les flottants sont codés différemment, par exemple, VAX.

Les formats "d" et "f" (en minuscules) continuent de se comporter comme ils le faisaient auparavant, c'est-à-dire qu'ils utilisent le format interne de Perl pour les flottants.

Support explicite pour les caractères d'espace Unicode

En plus de l'espace ASCII habituel, la classe de caractères "\s" correspond maintenant à tous les caractères Unicode qui sont considérés comme des espaces. Le nouveau caractère "\h" correspond aux caractères qui sont des espaces horizontaux, et "\v" correspond aux espaces verticaux. Ceci est similaire à la façon dont Perl 5.6 gérait les classes d'espaces.

Voir perlrecharclass pour plus de détails.

L'opérateur tr// ne fonctionne plus avec les chemins spéciaux

Les chemins spéciaux comme :: ne fonctionnent plus avec l'opérateur tr///. L'intention est que tr/// ne soit utilisé qu'avec des noms de package simples.

Le pragma feature en préversion

Le pragma use feature a été introduit, bien qu'il soit encore en préversion. Il permet de spécifier certaines fonctionnalités qui pourraient être ajoutées dans les futures versions de Perl, afin de permettre aux gens d'essayer les nouvelles fonctionnalités et de donner un retour d'information.

Pour l'instant, il est principalement utilisé pour activer le nouveau modèle Unicode décrit ci-dessus. Voir feature pour plus de détails.

La fonction ynnn a une nouvelle valeur de retour par défaut

La fonction ynnn renvoie maintenant undef au lieu de 0 lorsqu'elle ne trouve pas de correspondance. Cela est plus cohérent avec la façon dont d'autres fonctions de recherche de chaînes se comportent.

Les entrées de tableau corrompues ne sont plus automatiquement réparées

Dans les versions antérieures, si vous accédiez à un index de tableau qui n'existait pas, Perl allouait automatiquement une nouvelle entrée et l'initialisait à undef. Si vous accediez à un index qui existait mais qui était corrompu, Perl tentait de réparer la corruption. Maintenant, Perl n'initialise plus automatiquement de nouvelles entrées de tableau lorsque vous y accédez, et il ne tentera plus de réparer les corruptions. Cela permet de détecter les bogues plus tôt.

La gestion des erreurs d'une chaîne vide a été modifiée

L'accès à une chaîne vide sans indice (par exemple, $string[0]) causait auparavant une erreur de segmentation. Ce n'est plus le cas.

Les listes ne sont plus automatiquement tronquées quand elles sont utilisées comme scalaires

Lorsqu'une liste était utilisée dans un contexte scalaire, elle renvoyait automatiquement le dernier élément de la liste. C'est-à-dire que my ($a, $b) = (1, 2); my $c = ($a, $b); faisait que $c valait 2. Ceci est maintenant obsolète. Si vous voulez la dernière valeur d'une liste, vous devez explicitement l'indiquer en utilisant pop() ou en accédant au dernier élément de la liste (ce qui est maintenant possible grâce à la nouvelle syntaxe pop @list ou en utilisant une notation d'indexation).

Le contrôle des références a été amélioré

Perl est maintenant plus strict quant à la manière dont les références sont manipulées. Par exemple, essayer de déréférencer une valeur qui n'est pas une référence (par exemple, un entier) provoquera une erreur d'exécution au lieu d'une erreur subtile.

La fonction eval ne garde plus de trace des caractères d'espacement dans les chaînes

L'utilisation de la fonction eval sur une chaîne qui contient des caractères d'espacement avant la chaîne est maintenant gérée différemment. Auparavant, ces espaces étaient ignorés. Maintenant, ils sont considérés comme des erreurs, sauf si l'option use strict 'eval' est activée.

Les caractères de contrôle dans les expressions régulières

Les caractères de contrôle (comme \n, \t, etc.) ne sont plus interprétés de manière spéciale dans les listes de caractères (par exemple, [abc\n]). Ils sont traités littéralement. Si vous voulez inclure un caractère de contrôle dans une liste de caractères, vous devez maintenant utiliser sa forme octale ou hexadécimale (par exemple, [abc\012] pour un saut de ligne).

La fonction printf accepte maintenant des arguments spéciaux pour le formatage

La fonction printf accepte maintenant certains arguments spéciaux pour le formatage. Par exemple, vous pouvez utiliser %s pour formater une chaîne, %d pour un entier, et %f pour un flottant. Cela rend la fonction printf plus flexible et plus facile à utiliser.

Le pragma use filetest est obsolète

Le pragma use filetest, qui contrôlait le comportement des opérateurs de test de fichiers comme -e, -f, et -d, est maintenant obsolète. Son comportement est maintenant déterminé par les paramètres système et les fonctions POSIX.

La fonction chr() ne fonctionne plus avec les nombres négatifs

La fonction chr() ne fonctionne plus avec les nombres négatifs. Elle ne fonctionne maintenant qu'avec des entiers non négatifs. Si vous avez besoin de convertir un nombre négatif en caractère, vous devrez d'abord le convertir en un nombre positif correspondant.

Les champs de temps dans les heuristiques de compilation des expressions régulières ont été supprimés

Les champs de temps qui étaient utilisés pour optimiser la compilation des expressions régulières ont été supprimés. Cela devrait rendre la compilation des expressions régulières plus prévisible et moins sujette aux bogues.

Le compilateur Perl ne conserve plus les symboles inutiles

Le compilateur Perl ne conserve plus les symboles inutiles (par exemple, les variables non utilisées, les fonctions non appelées) dans le code compilé. Cela devrait réduire la taille des exécutables Perl et améliorer les performances.

La fonction splice() ne fonctionne plus avec les caractères nuls

La fonction splice() ne fonctionne plus avec les caractères nuls dans les chaînes. Si vous avez besoin d'utiliser des caractères nuls dans les chaînes, vous devrez utiliser une autre méthode pour manipuler les chaînes, comme la manipulation de tableaux de chaînes.

Les opérateurs de chaîne et numériques ne sont plus interchangeables

Dans les versions précédentes de Perl, les opérateurs de chaîne (comme . pour la concaténation) et les opérateurs numériques (comme + pour l'addition) étaient souvent interchangeables. Cela pouvait entraîner des erreurs subtiles. Maintenant, ils ne sont plus interchangeables. Vous devez utiliser l'opérateur approprié pour le type de données que vous manipulez.

La fonction tie() ne gère plus les objets qui ne sont pas des références

La fonction tie() ne fonctionne plus avec les objets qui ne sont pas des références. Vous devez maintenant toujours passer une référence à tie(). Cela rend le comportement de tie() plus prévisible.

La fonction substr() ne fonctionne plus avec les indices négatifs en dehors des limites

La fonction substr() ne fonctionne plus avec les indices négatifs qui sont en dehors des limites de la chaîne. Par exemple, substr($str, -100, 1) où $str est une chaîne courte provoquera maintenant une erreur. Vous devez vous assurer que vos indices sont dans les limites de la chaîne.

La variable spéciale $! est maintenant une référence vers un tableau

La variable spéciale $!, qui contient le dernier code d'erreur système, est maintenant une référence vers un tableau. Le premier élément du tableau est le numéro d'erreur (code d'erreur), et le deuxième élément est la chaîne de message d'erreur. Cela rend l'accès aux informations d'erreur plus cohérent et plus facile.

Les opérateurs de comparaison ont été modifiés pour être plus cohérents avec les conversions de types

Les opérateurs de comparaison (par exemple, ==, !=, <, >) ont été modifiés pour être plus cohérents avec les conversions de types de Perl. Cela signifie que le comportement des comparaisons peut être différent de celui des versions précédentes de Perl, en particulier lorsque vous comparez des chaînes et des nombres.

La fonction join() a été optimisée

La fonction join() a été optimisée pour améliorer les performances, en particulier lors de la jonction de grandes listes de chaînes.

Le mode strict a été renforcé

Le mode strict a été renforcé pour détecter plus d'erreurs potentielles dans votre code. Par exemple, l'utilisation de variables non déclarées provoquera maintenant une erreur d'exécution même si elles sont utilisées dans un contexte qui n'exigerait normalement pas de déclaration (par exemple, dans une affectation).

Les messages d'erreur sont maintenant plus informatifs

Les messages d'erreur générés par Perl sont maintenant plus informatifs et fournissent plus de détails sur la cause de l'erreur. Cela devrait faciliter le débogage de votre code.

Le mode de débogage de Perl a été amélioré

Le mode de débogage de Perl (activé avec l'option -d) a été amélioré pour fournir plus de fonctionnalités et une meilleure interface utilisateur. Cela devrait faciliter le débogage de votre code.

Le nouvel interpréteur de bytecode

Perl 5.8 inclut un nouvel interpréteur de bytecode qui est plus rapide et plus efficace que l'ancien interpréteur. Cela devrait améliorer les performances de vos programmes Perl.

Le nouvel algorithme de collecte des déchets

Perl 5.8 utilise un nouvel algorithme de collecte des déchets qui est plus efficace et consomme moins de mémoire. Cela devrait améliorer les performances et la stabilité de vos programmes Perl.

Le support de l'Unicode ameliore

Comme mentionné ci-dessus, le support de l'Unicode a été considérablement amélioré dans Perl 5.8. Cela inclut un meilleur support pour les caractères Unicode, les propriétés Unicode et les différentes normes d'encodage Unicode.

La nouvelle implementation de l'IO

La nouvelle architecture d'entrée/sortie (IO) de Perl, appelée PerlIO, est maintenant activée par défaut. PerlIO offre une meilleure gestion des flux d'entrée/sortie, un meilleur support des différents encodages de caractères et une interface plus cohérente pour la manipulation des fichiers.

La nouvelle implementation des threads

Perl 5.8 inclut une nouvelle implémentation des threads qui est plus stable et plus performante que l'ancienne. Les threads permettent d'exécuter plusieurs parties de votre programme simultanément, ce qui peut améliorer les performances des applications gourmandes en calcul.

Notez que l'utilisation des threads dans Perl peut être complexe et doit être abordée avec prudence. Consultez la documentation sur les threads pour plus d'informations.

La meilleure precision numerique

Perl 5.8 offre une meilleure précision numérique pour les calculs en point flottant. Cela est dû à l'utilisation de bibliothèques mathématiques plus avancées et à une gestion plus rigoureuse des erreurs de représentation.

Les signaux surs

Perl 5.8 introduit le concept de "signaux sûrs". Les signaux sûrs sont des signaux qui peuvent être traités de manière sûre sans risque de corrompre l'état du programme. Cela améliore la robustesse de vos programmes Perl lorsqu'ils doivent gérer des signaux.

Plusieurs nouveaux modules

Perl 5.8 est livré avec un certain nombre de nouveaux modules qui étendent les fonctionnalités de Perl. Ces modules couvrent une large gamme de domaines, tels que le réseau, la manipulation de données, les interfaces de base de données, etc.

Tests de regression plus extensifs

La suite de tests de régression incluse avec Perl 5.8 est plus complète que jamais. Cela garantit que Perl est plus stable et fiable, et que les bogues sont détectés et corrigés plus rapidement.

Nouvelles fonctionnalités

pack/unpack D/F recyclés

Les lettres de modèle non documentées pack/unpack D/F ont été recyclées pour une meilleure utilisation : elles représentent maintenant le double long (si supporté par la plateforme) et le type interne à virgule flottante NV (Perl). (Elles étaient auparavant des alias pour d/f, mais vous ne le saviez pas.)

glob() retourne maintenant les noms de fichiers par ordre alphabétique

La liste des noms de fichiers de glob() (ou <...>) est maintenant triée par défaut par ordre alphabétique pour être conforme à csh (ce qui se passait auparavant sur la plupart des plateformes Unix). (bsd_glob() trie toujours nativement selon la plateforme, ASCII ou EBCDIC, sauf si GLOB_ALPHASORT est spécifié.) [561]

Dépréciations

  • La sémantique de bless(REF, REF) était peu claire et tant que quelqu'un ne prouvera pas qu'elle a un sens, elle est interdite.
  • L'obsolète bibliothèque chat2, qui n'aurait jamais dû quitter le laboratoire, a été mise hors service.
  • Utiliser chdir("") ou chdir(undef) au lieu de chdir() explicite est douteux. Un échec (pensez à chdir(some_function())) peut entraîner un chdir() non intentionnel vers le répertoire personnel, par conséquent ce comportement est déprécié.
  • La fonction intégrée dump() a probablement dépassé la plupart de son utilité. La fonctionnalité de vidage de noyau restera disponible à l'avenir sous la forme d'un appel explicite à CORE::dump(), mais dans les futures versions, le comportement d'un appel non qualifié à dump() pourrait changer.
  • Les exemples très poussiéreux dans le répertoire eg/ ont été supprimés. Des suggestions pour de nouveaux exemples brillants sont les bienvenues, mais le principal problème est que les exemples doivent être documentés, testés et (surtout) maintenus.
  • Les séquences d'échappement (bogues) \8 et \9 génèrent maintenant un avertissement optionnel ("Unrecognized escape passed through"). Il n'est pas nécessaire d'échapper "\w".
  • Le *glob{FILEHANDLE} est déprécié, utilisez *glob{IO} à la place.
  • La syntaxe "package;" ("package" sans argument) a été dépréciée. Sa sémantique n'a jamais été très claire et son implémentation encore moins. Si vous avez utilisé cette fonctionnalité pour interdire toutes les variables sauf celles entièrement qualifiées, utilisez "use strict;" à la place.
  • Les fonctionnalités d'expressions régulières POSIX non implémentées [[.cc.]] et [[=c=]] sont toujours reconnues mais provoquent maintenant des erreurs fatales. Le comportement précédent de les ignorer par défaut et d'émettre un avertissement si demandé était inacceptable car cela promettait, en quelque sorte, faussement que les fonctionnalités pouvaient être utilisées.
  • Dans les futures versions, les modules XS non compatibles avec PerlIO pourraient ne plus être supportés du tout. PerlIO étant un remplacement transparent pour stdio au niveau du code source, cela ne devrait pas être un changement aussi drastique.
  • Les versions précédentes de perl et certaines lectures de sections de Camel III impliquaient que la "discipline" :raw était l'inverse de :crlf. Désactiver la "clrfness" ne suffisait plus à rendre un flux réellement binaire. Ainsi, la couche PerlIO :raw (ou "discipline", pour utiliser l'ancienne terminologie du livre de Camel) est maintenant définie formellement comme étant équivalente à binmode(FH) - qui est à son tour définie comme faisant tout le nécessaire pour passer chaque octet tel quel sans aucune traduction. En particulier, binmode(FH) - et donc :raw - désactivera maintenant la traduction CRLF et UTF-8 et supprimera d'autres couches (par exemple :encoding()) qui modifieraient le flux d'octets.
  • L'implémentation actuelle visible par l'utilisateur des pseudo-hashes (l'utilisation étrange du premier élément de tableau) est dépréciée à partir de Perl 5.8.0 et sera supprimée dans Perl 5.10.0, et la fonctionnalité sera implémentée différemment. Non seulement l'interface actuelle est plutôt laide, mais l'implémentation actuelle ralentit l'utilisation normale des tableaux et des hachages de manière assez notable. L'interface du pragma "fields" restera disponible. L'interface des *hashes restreints* devrait être l'interface de remplacement (voir Hash::Util). Si vos programmes existants dépendent de l'implémentation sous-jacente, envisagez d'utiliser Class::PseudoHash de CPAN.
  • Les syntaxes "@a->[...]" et "%h->{...}" sont maintenant dépréciées.
  • Après des années d'efforts, suidperl est considéré comme trop complexe pour être considéré comme véritablement sécurisé. La fonctionnalité suidperl sera probablement supprimée dans une future version.
  • Le modèle de threads 5.005 (module "Thread") est déprécié et devrait être supprimé dans Perl 5.10. Le code multithreadé doit être migré vers le nouveau modèle ithreads (voir threads, threads::shared et perlthrtut).
  • Les alias en majuscules, longtemps dépréciés, pour les opérateurs de comparaison de chaînes (EQ, NE, LT, LE, GE, GT) ont maintenant été supprimés.
  • Les fonctionnalités tr///C et tr///U ont été supprimées et ne reviendront pas ; l'interface était une erreur. Désolé. Pour une fonctionnalité similaire, voir pack('U0', ...) et pack('C0', ...). [561]
  • Les versions antérieures de perl et certaines lectures de sections de Camel III impliquaient que "sub foo (@bar)" était équivalent à "sub foo (@)". Les prototypes sont maintenant mieux vérifiés à la compilation pour la syntaxe invalide. Un avertissement optionnel est généré ("Illegal character in prototype...") mais cela pourrait être mis à niveau vers une erreur fatale dans une future version.
  • Les opérations "exec LIST" et "system LIST" produisent maintenant des avertissements sur les données souillées et dans une future version, elles produiront des erreurs fatales.
  • Le comportement existant lors de la localisation de tableaux et de hachages liés est incorrect et sera modifié dans une future version, ne vous fiez donc pas au comportement existant. Voir "Localising Tied Arrays and Hashes Is Broken".

Améliorations du noyau

Révision Unicode

Unicode en général devrait maintenant être beaucoup plus utilisable qu'en Perl 5.6.0 (ou même qu'en 5.6.1). Unicode peut être utilisé dans les clés de hachage, Unicode dans les expressions régulières devrait maintenant fonctionner, Unicode dans tr/// devrait maintenant fonctionner, Unicode dans les I/O devrait maintenant fonctionner. Voir perluniintro pour une introduction et perlunicode pour les détails.

  • La base de données de caractères Unicode livrée avec Perl a été mise à jour vers Unicode 3.2.0. Pour plus d'informations, voir http://www.unicode.org/ . [561+] (5.6.1 a UCD 3.0.1.)
  • Pour les développeurs intéressés par l'amélioration des capacités Unicode de Perl : presque tous les fichiers UCD sont inclus avec la distribution Perl dans le sous-répertoire lib/unicore. L'omission la plus notable, pour des raisons d'espace, est la base de données Unihan.
  • Les propriétés \p{Blank} et \p{SpacePerl} ont été ajoutées. "Blank" est comme C isblank(), c'est-à-dire qu'il ne contient que les "espaces horizontaux" (le caractère espace est inclus, le saut de ligne ne l'est pas), et "SpacePerl" est l'équivalent Unicode de "\s" (\p{Space} ne l'est pas, car il inclut le caractère tabulation verticale, alors que "\s" ne l'inclut pas.)

    Voir "New Unicode Properties" plus haut dans ce document pour des informations supplémentaires sur les changements des propriétés Unicode.

PerlIO est maintenant par défaut

  • Les I/O sont maintenant effectuées par défaut via PerlIO plutôt que via le "stdio" du système. PerlIO permet de "pousser" des "couches" sur un descripteur de fichier pour modifier le comportement du descripteur. Les couches peuvent être spécifiées à l'ouverture via la forme à 3 arguments de open : 
    open($fh,'>:crlf :utf8', $path) || ...

    ou sur des descripteurs déjà ouverts via "binmode" étendu :

    binmode($fh,':encoding(iso-8859-7)');

    Les couches intégrées sont : unix (lecture/écriture de bas niveau), stdio (comme dans les Perls précédents), perlio (réimplémentation de la mise en tampon stdio de manière portable), crlf (effectue la traduction CRLF <=> "\n" comme sous Win32, mais disponible sur n'importe quelle plateforme). Une couche mmap peut être disponible si la plateforme la supporte (principalement les Unix).

    Les couches à appliquer par défaut peuvent être spécifiées via le pragma 'open'.

    Voir "Installation and Configuration Improvements" pour les effets de PerlIO sur le nom de votre architecture.

  • Si votre plateforme supporte fork(), vous pouvez utiliser la forme en liste de "open" pour les tuyaux. Par exemple : 
    open KID_PS, "-|", "ps", "aux" or die $!;

    fork la commande ps(1) (sans lancer de shell, car il y a plus de trois arguments à open()), et lit sa sortie standard via le descripteur de fichier "KID_PS". Voir perlipc.

  • Les descripteurs de fichiers peuvent être marqués comme acceptant l'encodage interne de Perl pour Unicode (UTF-8 ou UTF-EBCDIC selon la plateforme) par une pseudo-couche ":utf8" : 
    open($fh,">:utf8","Uni.txt");

    Note pour les utilisateurs EBCDIC : la pseudo-couche ":utf8" est mal nommée pour vous car ce n'est pas UTF-8 que vous obtiendrez, mais plutôt UTF-EBCDIC. Voir perlunicode, utf8, et http://www.unicode.org/reports/tr16/ pour plus d'informations. Dans les futures versions, cette dénomination pourrait changer. Voir perluniintro pour plus d'informations sur UTF-8.

  • Si vos variables d'environnement (LC_ALL, LC_CTYPE, LANG) indiquent que vous voulez utiliser UTF-8 (toutes les variables correspondent à "/utf-?8/i"), vos descripteurs STDIN, STDOUT, STDERR et la couche d'ouverture par défaut (voir open) sont marqués comme UTF-8. (Cette fonctionnalité, comme d'autres nouvelles fonctionnalités qui combinent Unicode et I/O, ne fonctionne que si vous utilisez PerlIO, mais c'est le défaut.)

    Notez qu'après cela, Perl suppose réellement que tout est UTF-8 : par exemple, si un descripteur d'entrée ne l'est pas, Perl se plaindra probablement très bientôt des données d'entrée comme ceci "Malformed UTF-8 ...", car toute vieille donnée à huit bits n'est pas une UTF-8 légale.

    Note pour les auteurs de code : si vous voulez permettre à vos utilisateurs d'utiliser UTF-8 comme encodage par défaut, mais conserver dans votre code des flux d'E/S à huit bits (tels que des images ou des fichiers zip), vous devez explicitement open() ou binmode() avec ":bytes" (voir &qu

ot;open" dans perlfunc et "binmode" dans perlfunc), ou vous pouvez simplement utiliser binmode(FH) (pratique pour la compatibilité ascendante avant la version 5.8.0).

  • Les descripteurs de fichiers peuvent traduire les encodages de caractères depuis/vers la forme Unicode interne de Perl lors de la lecture/écriture via la couche ":encoding()".
  • Les descripteurs de fichiers peuvent être ouverts sur des fichiers "en mémoire" détenus dans des scalaires Perl via : 
    open($fh,'>', \$variable) || ...
  • Des fichiers temporaires anonymes sont disponibles sans avoir besoin d'utiliser 'use FileHandle' ou un autre module via 
    open($fh,"+>", undef) || ...

    Il s'agit d'un undef littéral, pas d'une valeur indéfinie.

    • ithreads

    La nouvelle implémentation des threads d'interpréteur ("ithreads" en abrégé) de multithreading, par Arthur Bergman, remplace l'ancienne implémentation "threads 5.005". Dans le modèle ithreads, tout partage de données entre les threads doit être explicite, par opposition au modèle où le partage de données était implicite. Voir threads et threads::shared, et perlthrtut.

    Dans le cadre de l'implémentation ithreads, Perl utilisera également toutes les interfaces libc réentrantes nécessaires et détectables.

    Hashes restreints

    Un hash restreint est limité à un certain ensemble de clés, aucune clé en dehors de cet ensemble ne peut être ajoutée. De plus, des clés individuelles peuvent être restreintes de sorte que la clé ne puisse pas être supprimée et que la valeur ne puisse pas être modifiée. Aucune nouvelle syntaxe n'est impliquée : le module Hash::Util est l'interface.

    Signaux sûrs

    Perl était auparavant fragile car les signaux arrivant à des moments inopportuns pouvaient corrompre l'état interne de Perl. Désormais, Perl reporte la gestion des signaux jusqu'à ce qu'il soit sûr (entre les opcodes).

    Ce changement peut avoir des effets secondaires surprenants car les signaux n'interrompent plus Perl instantanément. Perl terminera maintenant d'abord tout ce qu'il faisait, comme terminer une opération interne (comme sort()) ou une opération externe (comme une opération d'E/S), puis examinera les signaux arrivés (et avant de commencer l'opération suivante). Plus d'état interne corrompu car l'opération en cours est toujours terminée d'abord, mais le signal peut prendre plus de temps à être entendu. Notez que sortir d'opérations potentiellement bloquantes devrait toujours fonctionner, cependant.

    Compréhension des nombres

    En général, beaucoup de corrections ont été apportées dans le domaine de la compréhension des nombres par Perl, tant entiers que flottants. Comme dans de nombreux systèmes, les fonctions standard d'analyse de nombres comme strtoul() et atof() semblent avoir des bugs, Perl essaie de contourner leurs lacunes. Cela se traduit, espérons-le, par des nombres plus précis.

    Perl essaie maintenant en interne d'utiliser des valeurs entières dans les conversions numériques et l'arithmétique de base (+ - * /) si les arguments sont des entiers, et essaie également de conserver les résultats stockés en interne sous forme d'entiers. Ce changement conduit à une arithmétique souvent légèrement plus rapide et toujours moins sujette à perte. (Précédemment, Perl préférait toujours les nombres à virgule flottante dans ses calculs.)

    Les tableaux s'interpolent désormais toujours dans les chaînes entre guillemets doubles [561]

    Dans les chaînes entre guillemets doubles, les tableaux s'interpolent désormais, quoi qu'il arrive. Le comportement dans les versions antérieures de Perl 5 était que les tableaux s'interpolaient dans les chaînes si le tableau avait été mentionné avant la compilation de la chaîne, sinon Perl générait une erreur fatale lors de la compilation. Dans les versions 5.000 à 5.003, l'erreur était

    Literal @example now requires backslash

    Dans les versions 5.004_01 à 5.6.0, l'erreur était

    In string, @example now must be written as \@example

    L'idée était d'habituer les gens à écrire "fred\@example.com" lorsqu'ils voulaient un signe "@" littéral, tout comme ils ont toujours écrit "Donne-moi mes \$5" quand ils voulaient un signe "$" littéral.

    À partir de la version 5.6.1, lorsque Perl voit maintenant un signe "@" dans une chaîne entre guillemets doubles, il tente *toujours* d'interpoler un tableau, qu'il s'agisse ou non du tableau a déjà été utilisé ou déclaré. L'erreur fatale a été déclassée en avertissement optionnel :

    Possible unintended interpolation of @example in string

    Cela vous avertit que "fred@example.com" deviendra "fred.com" si vous n'échappez pas le "@". Voir http://perl.plover.com/at-error.html pour plus de détails sur l'historique ici.

    Changements divers

    • AUTOLOAD est désormais lvaluable, ce qui signifie que vous pouvez ajouter l'attribut :lvalue aux sous-routines AUTOLOAD et vous pouvez affecter la valeur de retour d'AUTOLOAD.
    • Le champ $Config{byteorder} (et le BYTEORDER correspondant dans config.h) était auparavant incorrect sur les plateformes si sizeof(long) était de 4 mais sizeof(IV) était de 8. L'octet était seulement de la longueur de sizeof(long) (1234 ou 4321), mais il est maintenant correctement de la longueur de sizeof(IV) (12345678 ou 87654321). (Ce problème n'affectait pas les plateformes Windows.)

      De plus, $Config{byteorder} est désormais calculé dynamiquement, ce qui est plus robuste avec les "binaires gras" où une image exécutable contient des binaires pour plus d'une plateforme binaire, et lors de la compilation croisée.

    • "perl -d:Module=arg,arg,arg" fonctionne désormais (auparavant, on ne pouvait pas passer plusieurs arguments).
    • "do" suivi d'un bareword garantit désormais que ce bareword n'est pas un mot-clé (pour éviter un bug où "do q(foo.pl)" essayait d'appeler une sous-routine nommée "q"). Cela signifie par exemple qu'au lieu de "do format()" vous devez écrire "do &format()".
    • Le builtin dump() donne désormais un avertissement optionnel "dump() better written as CORE::dump()", ce qui signifie que par défaut dump(...) est résolu comme le builtin dump() qui vide le cœur et avorte, et non comme une sous-routine potentiellement définie par l'utilisateur "sub dump". Pour appeler cette dernière, qualifiez l'appel comme &dump(...). (Toute la fonctionnalité dump() est considérée comme obsolète et pourrait être supprimée/modifiée dans les futures versions.)
    • chomp() et chop() sont désormais remplaçables. Notez cependant que leur prototype (tel que donné par prototype("CORE::chomp") est indéfini, car il ne peut pas être exprimé et par conséquent, on ne peut pas vraiment écrire de remplacements pour remplacer ces builtins.
    • Les blocs END sont maintenant exécutés même si vous quittez/mourrez dans un bloc BEGIN. Internement, l'exécution des blocs END est maintenant contrôlée par PL_exit_flags & PERL_EXIT_DESTRUCT_END. Cela active le nouveau comportement pour les intégrateurs Perl. Cela sera par défaut en 5.10. Voir perlembed.
    • Les formats supportent désormais les champs décimaux complétés par des zéros.
    • Bien qu'il soit dit "vous ne devriez pas faire cela", il était possible d'écrire du code qui dépend de l'ordre des clés hachées de Perl (Data::Dumper fait cela). Le nouvel algorithme "One-at-a-Time" produit un ordre de clés hachées différent. Plus de détails dans "Améliorations des performances".
    • lstat(FILEHANDLE) génère désormais un avertissement car l'opération n'a pas de sens. Dans les futures versions, cela pourrait devenir une erreur fatale.
    • Des erreurs de syntaxe parasites générées dans certaines situations, lorsque glob() provoquait le chargement de File::Glob pour la première fois, ont été corrigées. [561]
    • Les sous-routines Lvalue peuvent désormais retourner "undef" en contexte de liste. Cependant, la fonctionnalité de sous-routine lvalue reste expérimentale. [561+]
    • Un avertissement perdu "Can't declare ... dereference in my" a été restauré (Perl l'avait plus tôt mais il s'est perdu dans les versions ultérieures).
    • Une nouvelle variable spéciale d'expression régulière a été introduite : $^N, qui contient le sous-match du groupe le plus récemment fermé.
    • "no Module;" ne produit pas d'erreur même si Module n'a pas de méthode unimport(). Cela fait écho au comportement de "use" par rapport à "import". [561]
    • Les opérateurs de comparaison numérique retournent "undef" si l'un des opérandes est un NaN. Auparavant, le comportement était non spécifié.
    • "our" peut désormais avoir un attribut optionnel expérimental "unique" qui affecte la manière dont les variables globales sont partagées entre plusieurs interpréteurs, voir "our" dans perlfunc.
    • Les fonctions builtins suivantes sont désormais remplaçables : each(), keys(), pop(), push(), shift(), splice(), unshift(). [561]
    • "pack() / unpack()" peut désormais grouper des lettres de modèle avec "()" puis appliquer des modificateurs de répétition/compte sur les groupes.
    • "pack() / unpack()" peut désormais traiter les types numériques internes de Perl : IV, UV, NV -- et aussi les doubles longs, si supportés par la plateforme. Les lettres de modèle sont "j", "J", "F", et "D".
    • "pack('U0a*', ...)" peut désormais être utilisé pour forcer une chaîne en UTF-8.
    • my __PACKAGE__ $obj fonctionne désormais. [561]
    • POSIX::sleep() retourne désormais le nombre de secondes *non dormies* (comme le spécifie la norme POSIX), par opposition à CORE::sleep() qui retourne le nombre de secondes dormies.
    • printf() et sprintf() supportent désormais la réorganisation des paramètres en utilisant les syntaxes "%\d+\$" et "*\d+\$". Par exemple 
      printf "%2\$s %1\$s\n", "foo", "bar";

      affichera "bar foo\n". Cette fonctionnalité aide à écrire des logiciels internationalisés, un

    d en général lorsque l'ordre des paramètres peut varier.

  • Le prototype de (\&) fonctionne désormais correctement. [561]
  • prototype(\[$@%&]) est maintenant disponible pour créer implicitement des références (utile par exemple si vous souhaitez émuler l'interface tie()).
  • Une nouvelle option de ligne de commande, "-t" est disponible. C'est le petit frère de "-T" : au lieu de s'arrêter en cas de violation de taint, des avertissements lexicaux sont émis. Ceci n'est destiné qu'à titre d'aide temporaire de débogage lors de la sécurisation du code d'anciennes applications héritées. Ceci ne remplace pas -T.
  • Autre nouvelle concernant le taint, les formes "exec LIST" et "system LIST" sont désormais considérées comme trop risquées (pensez à "exec @ARGV" : cela peut lancer n'importe quel programme avec n'importe quels arguments), et ces formes déclenchent maintenant un avertissement dans le cadre des avertissements lexicaux. Vous devez soigneusement nettoyer les arguments pour garantir leur validité. Dans les futures versions de Perl, ces formes deviendront des erreurs fatales, alors envisagez de commencer le nettoyage dès maintenant.
  • Les interfaces de hachage liées exigent désormais les méthodes EXISTS et DELETE (qu'elles soient propres ou héritées).
  • Si tr/// ne fait que compter des caractères, il ne tente pas de modifier sa cible.
  • untie() appellera désormais un hook UNTIE() s'il existe. Voir perltie pour plus de détails. [561]
  • "utime" dans perlfunc prend désormais en charge "utime undef, undef, @files" pour changer les horodatages des fichiers à l'heure actuelle.
  • Les règles d'autorisation des tirets (underscores) dans les constantes numériques ont été assouplies et simplifiées : vous pouvez maintenant avoir un tiret simplement entre des chiffres.
  • Plutôt que de s'appuyer sur argv[0] de C (qui peut ne pas contenir un chemin d'accès complet) lorsque cela est possible, $^X est maintenant défini en demandant au système d'exploitation. (par exemple, en lisant /proc/self/exe sous Linux, /proc/curproc/file sous FreeBSD)
  • Une nouvelle variable, "${^TAINT}", indique si le mode taint est activé.
  • Vous pouvez maintenant surcharger la fonction intégrée readline(), et cela surcharge également l'opérateur d'angle <<FILEHANDLE>.
  • Les options de ligne de commande -s et -F sont maintenant reconnues sur la ligne shebang (#!).
  • L'utilisation du modificateur de correspondance "/c" sans modificateur "/g" correspondant déclenche un nouvel avertissement : "Use of /c modifier is meaningless without /g".

    L'utilisation de "/c" dans les substitutions, même avec "/g", déclenche "Use of /c modifier is meaningless in s///".

    L'utilisation de "/g" avec "split" déclenche "Use of /g modifier is meaningless in split".

  • La prise en charge de la sous-routine spéciale "CLONE" a été ajoutée. Avec ithreads, lorsqu'un nouveau thread est créé, toutes les données Perl sont clonées, mais les données non-Perl ne peuvent pas être clonées automatiquement. Dans "CLONE", vous pouvez faire tout ce que vous avez à faire, comme par exemple gérer le clonage de données non-Perl, si nécessaire. "CLONE" sera exécuté une fois pour chaque package qui l'a défini ou hérité. Il sera appelé dans le contexte du nouveau thread, de sorte que toutes les modifications sont effectuées dans la nouvelle zone.

    Améliorations des performances

    • map() pouvait devenir pathologiquement lent lorsque la liste de résultats qu'il générait était plus grande que la liste source. Les performances ont été améliorées pour les scénarios courants. [561]
    • sort() est également entièrement réentrant, dans le sens où la fonction de tri peut elle-même appeler sort(). Cela ne fonctionnait pas de manière fiable dans les versions précédentes. [561]
    • sort() a été modifié pour utiliser principalement le tri fusion (mergesort) en interne, par opposition au tri rapide (quicksort) précédent. Pour des listes très petites, cela peut entraîner des temps de tri légèrement plus lents, mais en général, l'accélération devrait être d'au moins 20 %. Les avantages supplémentaires sont que le comportement du pire cas de sort() est désormais meilleur (en termes informatiques, il s'exécute désormais en temps O(N log N), par opposition au comportement du pire cas de quicksort en temps Thêta(N**2)), et que sort() est désormais stable (ce qui signifie que les éléments ayant des clés identiques resteront ordonnés comme ils l'étaient avant le tri). Voir le pragma "sort" pour plus d'informations.

      L'histoire plus en détail : supposons que vous vouliez vous servir une petite tranche de Pi.

      @digits = ( 3,1,4,1,5,9 );

      Un tri numérique des chiffres donnera (1,1,3,4,5,9), comme prévu. Lequel des 1 vient en premier est difficile à savoir, car un 1 ressemble beaucoup à un autre. Vous pouvez considérer cela comme totalement trivial, ou quelque peu profond. Cependant, si vous voulez simplement trier les chiffres pairs

    gits en avant des impairs, alors que donnera

    sort { ($a % 2) <=> ($b % 2) } @digits;

    Le seul chiffre pair, 4, viendra en premier. Mais qu'en est-il des nombres impairs, qui se comparent tous de manière égale ? Avec l'algorithme quicksort utilisé pour implémenter Perl 5.6 et versions antérieures, l'ordre des égalités est laissé à la discrétion du tri. Ainsi, à mesure que vous ajoutez de plus en plus de chiffres de Pi, l'ordre dans lequel les chiffres pairs et impairs triés apparaissent changera. Et, pour des tranches de Pi suffisamment grandes, l'algorithme quicksort de Perl 5.8 ne renverra pas les mêmes résultats même s'il est réinvoqué avec la même entrée. La justification repose sur le comportement dans le pire des cas de quicksort. Si vous exécutez

    sort { $a <=> $b } ( 1 .. $N , 1 .. $N );

    (quelque chose que vous pourriez approximer si vous vouliez fusionner deux tableaux triés à l'aide de sort), doubler $N ne double pas seulement le temps de quicksort, il le quadruple. Quicksort a un temps d'exécution dans le pire des cas qui peut croître comme N**2, un comportement dit quadratique, et cela peut se produire sur des motifs qui peuvent bien survenir dans une utilisation normale. Vous ne le remarquerez pas pour les petits tableaux, mais vous le remarquerez avec les grands tableaux, et vous pourriez ne pas vivre assez longtemps pour que le tri soit terminé sur des tableaux d'un million d'éléments. Ainsi, le quicksort de la version 5.8 brouille les grands tableaux avant de les trier, comme une défense statistique contre le comportement quadratique. Mais cela signifie que si vous triez le même grand tableau deux fois, les égalités peuvent être résolues de différentes manières.

    En raison de l'imprévisibilité de l'ordre de résolution des égalités, et du comportement quadratique dans le pire des cas, quicksort a été presque complètement remplacé par un mergesort stable. Stable signifie que les égalités sont résolues pour préserver l'ordre d'apparition original dans le tableau d'entrée. Ainsi

    sort { ($a % 2) <=> ($b % 2) } (3,1,4,1,5,9);

    donnera (4,3,1,1,5,9), garanti. Les nombres pairs et impairs apparaissent dans la sortie dans le même ordre qu'ils sont apparus dans l'entrée. Mergesort a un comportement O(N log N) dans le pire des cas, la meilleure valeur possible. Et, ironiquement, ce mergesort réussit particulièrement bien là où quicksort devient quadratique : mergesort trie (1..$N, 1..$N) en temps O(N). Mais quicksort a été sauvé à la dernière minute car il est plus rapide que mergesort sur certaines entrées et plateformes. Par exemple, si vous ne vous souciez vraiment pas de l'ordre des chiffres pairs et impairs, quicksort s'exécutera en temps O(N) ; il est très bon pour trier de nombreuses répétitions d'un petit nombre d'éléments distincts. La stratégie de division et de conquête de Quicksort fonctionne bien sur les plateformes dotées de caches relativement petits et très rapides. Finalement, le problème est réduit à quelque chose qui tient dans le cache, à partir duquel il bénéficie de la vitesse accrue de la mémoire.

    Quicksort a été sauvé en implémentant un pragma sort pour contrôler les aspects du tri. Le sous-pragma stable force un comportement stable, quel que soit l'algorithme. Les sous-pragmas _quicksort et _mergesort sont des moyens rudimentaires de sélectionner l'implémentation sous-jacente. Le "_" initial est un rappel que ces sous-pragmas pourraient ne pas survivre au-delà de la version 5.8. Des mécanismes plus appropriés pour sélectionner l'implémentation existent, mais ils ne seraient pas arrivés à temps pour sauver quicksort.

  • Les hachages utilisent désormais l'algorithme de hachage de clé "One-at-a-Time" de Bob Jenkins ( http://burtleburtle.net/bob/hash/doobs.html ). Cet algorithme est raisonnablement rapide tout en produisant une bien meilleure répartition des valeurs que l'ancien algorithme de hachage (initialement par Chris Torek, ensuite ajusté par Ilya Zakharevich). Les valeurs de hachage générées par l'algorithme sur un hachage de toutes les clés ASCII imprimables de 3 caractères se rapprochent beaucoup plus de la réussite aux tests de génération de nombres aléatoires DIEHARD. Selon perlbench, ce changement n'a pas affecté la vitesse globale de Perl.
  • unshift() devrait maintenant être sensiblement plus rapide.

Si cela semble être le cas et que 'cc' ne semble pas être le compilateur C GNU 'gcc', une tentative automatique est faite pour trouver et utiliser 'gcc' à la place.

Si Configure constate que gcc a été compilé pour une version du système d'exploitation différente de celle en cours d'exécution, il affiche maintenant un avertissement clairement visible indiquant qu'il pourrait y avoir des problèmes.

    • Le support de Configure pour les modèles de mémoire de style pdp11 a été supprimé en raison de l'obsolescence. [561]
    • configure.gnu fonctionne maintenant avec des options contenant des espaces.

    • Parce que PerlIO est maintenant la valeur par défaut sur la plupart des plateformes, "-perlio" n'est plus ajouté à $Config{archname} (également connu sous le nom de $^O).     • Si vous avez un accès CPAN (réseau ou copie locale comme un CD-ROM), vous pouvez spécifier des modules supplémentaires à compiler et installer avec Perl pendant Configure en utilisant l'option -Dextras=... Voir INSTALL pour plus de détails.

Ce fichier est destiné à être utilisé par les auteurs de fichiers d'indices pour des changements à l'échelle de l'architecture (par opposition à config.over qui est pour des changements à l'échelle du site).

cd perl/build/directory

      et Perl sera compilé et testé, le tout dans perl/build/directory. [561]

    • Si vous êtes sur des plateformes IRIX ou Tru64, de nouvelles options de profilage/débogage ont été ajoutées ; voir perlhack pour plus d'informations sur pixie et Third Degree.
    • Des directives sur la manière de construire des installations Perl minimales ont été ajoutées à INSTALL.
    • L'extension Thread n'est maintenant plus compilée du tout sous ithreads ("Configure -Duseithreads") car elle ne fonctionnerait de toute façon pas (l'extension Thread nécessite d'être configurée avec "-Duse5005threads").

    Vulnérabilité de Sécurité Corrigée [561]

    (Ce changement a déjà été effectué dans 5.7.0 mais mérite d'être répété ici.) (5.7.0 est sorti avant 5.6.1 : la branche de développement 5.7 est sortie plus tôt que la branche de maintenance 5.6)

    Une vulnérabilité de sécurité potentielle dans le composant optionnel suidperl de Perl a été identifiée en août 2000. suidperl n'est ni construit ni installé par défaut. Depuis novembre 2001, la seule plateforme connue vulnérable est Linux, très probablement toutes les distributions Linux. CERT et divers fournisseurs et distributeurs ont été alertés de la vulnérabilité. Voir http://www.cpan.org/src/5.0/sperl-2000-08-05/sperl-2000-08-05.txt pour plus d'informations.

    Le problème était causé par Perl essayant de signaler une tentative d'exploit de sécurité suspectée à l'aide d'un programme externe, /bin/mail. Sur les plateformes Linux, le programme /bin/mail avait une fonctionnalité non documentée qui, lorsqu'elle était combinée avec suidperl, donnait accès à un shell root, entraînant un compromis grave au lieu de signaler la tentative d'exploit. Si vous n'avez pas /bin/mail, ou si vous avez des 'safe setuid scripts', ou si suidperl n'est pas installé, vous êtes en sécurité.

    La fonctionnalité de signalement des tentatives d'exploit a été complètement supprimée de Perl 5.8.0 (et de la version de maintenance 5.6.1, et elle a également été supprimée de toutes les versions 5.7 de Perl), donc cette vulnérabilité particulière n'existe plus. Cependant, d'autres vulnérabilités de sécurité sont, malheureusement, toujours possibles. La fonctionnalité suidperl sera très probablement supprimée dans Perl 5.10. Dans tous les cas, suidperl ne doit être utilisé que par des experts en sécurité qui savent exactement ce qu'ils font et pourquoi ils utilisent suidperl au lieu d'une autre solution comme sudo (voir http://www.courtesan.com/sudo/ ).

    Plusieurs nouveaux tests ont été ajoutés, en particulier pour les sections lib et ext. Il y a maintenant environ 69 000 tests individuels (répartis sur environ 700 scripts de test), dans la suite de régression (5.6.1 a environ 11 700 tests, dans 258 scripts de test). Les chiffres exacts dépendent de la plateforme et de la configuration de Perl utilisée. Beaucoup de nouveaux tests sont bien sûr introduits par les nouveaux modules, mais en général Perl est maintenant testé plus rigoureusement.

    En raison du grand nombre de tests, l'exécution de la suite de régression prendra considérablement plus de temps que

    il avait l'habitude : attendez-vous à ce que la suite prenne jusqu'à 4 à 5 fois plus de temps à s'exécuter qu'en Perl 5.6. Sur une machine très rapide, vous pouvez espérer terminer la suite en environ 6 à 8 minutes (temps réel).

    Les tests sont maintenant rapportés dans un ordre différent de celui des Perls précédents. (Cela se produit parce que les scripts de test sous t/lib ont été déplacés pour être plus proches de la bibliothèque/extension qu'ils testent.)

    Problèmes Connus

    La Suite Du Compilateur Est Toujours Très Expérimentale

    La suite du compilateur s'améliore lentement mais reste très expérimentale. Son utilisation dans des environnements de production est déconseillée.

    La Localisation Des Tableaux Et Hashes Liés Est Cassée

    local %tied_array;

    ne fonctionne pas comme prévu : l'ancienne valeur est restaurée incorrectement. Cela sera modifié dans une future version, mais nous ne savons pas encore quelles seront exactement les nouvelles sémantiques. En tout cas, la modification cassera le code existant qui repose sur les sémantiques actuelles (mal définies), alors évitez simplement de le faire en général.

    La Compilation Des Extensions Peut Échouer À Cause Des Gros Fichiers

    Certaines extensions comme mod_perl sont connues pour avoir des problèmes avec `largefiles', un changement apporté par Perl 5.6.0 dans lequel les décalages de fichiers sont par défaut de 64 bits, là où c'est supporté. Les modules peuvent ne pas compiler du tout, ou peuvent compiler et fonctionner incorrectement. Actuellement, il n'y a pas de bonne solution au problème, mais Configure fournit maintenant des ccflags, ldflags, libswanted et libs appropriés sans `largefiles' dans le hash %Config (par exemple, $Config{ccflags_nolargefiles}) de sorte que les extensions qui rencontrent des problèmes peuvent essayer de se configurer sans le support des gros fichiers. Ce n'est pas une solution idéale, et la solution peut même ne pas fonctionner du tout. Une défaillance potentielle est de savoir si l'on peut (ou, si l'on peut, si c'est une bonne idée) lier ensemble des binaires avec des idées différentes sur les décalages de fichiers ; tout cela dépend de la plateforme.

    Modification De $_ Dans Une Boucle For(..)

    for (1..5) { $_++ }

    fonctionne sans complaintes. Elle ne devrait pas. (Vous ne devriez pouvoir modifier que les éléments lvalues à l'intérieur des boucles.) Vous pouvez voir le comportement correct en remplaçant 1..5 par 1, 2, 3, 4, 5.

    Utilisez mod_perl 1.27 ou une version supérieure.

    lib/ftmp-security tests affichent 'system possibly insecure'

    Ne paniquez pas. Lisez plutôt la section 'make test' de INSTALL.

    libwww-perl (LWP) échoue à base/date #51

    Utilisez libwww-perl 5.65 ou une version ultérieure.

    PDL échoue à certains tests

    Utilisez PDL 2.3.4 ou une version ultérieure.

    Perl_get_sv

    Vous pouvez obtenir des erreurs comme 'Undefined symbol "Perl_get_sv"' ou "can't resolve symbol 'Perl_get_sv'", ou le symbole peut être "Perl_sv_2pv". Cela signifie probablement que vous essayez d'utiliser une ancienne bibliothèque Perl partagée (ou des extensions liées avec une telle) avec un exécutable Perl 5.8.0. Perl avait l'habitude d'avoir une telle sous-routine, mais ce n'est plus le cas. Vérifiez votre chemin de bibliothèques partagées, et toutes les bibliothèques Perl partagées dans ces répertoires.

    Parfois, ce problème peut également indiquer une installation partielle de Perl 5.8.0, voir "Mac OS X dyld undefined symbols" pour un exemple et comment le résoudre.

    Problèmes d'auto-liaison de variables

    L'auto-liaison des tableaux et des hashes est cassée de manière profonde et difficile à corriger. Par mesure de sécurité pour éviter que les gens ne soient frustrés par des résultats mystérieux (plantages, le plus souvent), c'est interdit pour l'instant (vous obtiendrez une erreur fatale même pour une tentative).

    Une modification de l'auto-liaison des globs a provoqué leur référence récursive (voir : "Two-Phased Garbage Collection" dans perlobj). Vous aurez maintenant besoin d'un `untie' explicite pour détruire un glob auto-lié. Ce comportement pourrait être corrigé ultérieurement.

    L'auto-liaison des scalaires et des objets IO fonctionne.

    ext/threads/t/libc

    Si ce test échoue, cela indique que votre libc (bibliothèque C) n'est pas thread-safe. Ce test particulier soumet la fonction localtime() à rude épreuve pour déterminer si elle est thread-safe. Voir perlthrtut pour plus d'informations.

    L'une des raisons de cette inachèvement est son caractère (actuellement) inhéremment non portable : puisque les noms de packages et les noms de sous-routines peuvent devoir être mappés à des noms de fichiers et de répertoires, la capacité Unicode du système de fichiers devient importante -- et malheureusement, il n'y a pas de réponses portables.

    C'est inoffensif ; cela est causé par le fait que getnetbyaddr() et getnetbyaddr_r() ont des types légèrement différents pour leur premier argument.

(RedHat Linux/alpha avec gcc 3.1 n'a signalé aucun problème, tout comme Linux 2.4.18 avec gcc 2.95.4.) (Sous Tru64, il est préférable d'utiliser le compilateur C intégré.)

    FreeBSD compilé avec ithreads plante en lisant de grands répertoires

    C'est un bogue connu dans readdir_r() de FreeBSD 4.5, il a été corrigé dans FreeBSD 4.6 (voir perlfreebsd (README.freebsd)).

    FreeBSD le test locale 117 échoue pour les locales ISO 8859-15

    Les locales ISO 8859-15 peuvent échouer au test locale 117 sous FreeBSD. Ceci est causé par les caractères \xFF (y tréma) et \xBE (Y tréma) qui ne se comportent pas correctement lorsqu'ils sont comparés sans tenir compte de la casse. Apparemment, ce problème a été corrigé dans les dernières versions de FreeBSD. ( http://www.freebsd.org/cgi/query-pr.cgi?pr=34308 )

Cela semble être une erreur de compilation car si compilé avec gcc, il n'y a pas de crash, et aucun échec n'a été observé sur le test mentionné sur aucune autre plateforme.

    De même, la compilation de l'extension Digest::MD5 est connue pour échouer avec ""*** Termination code 139 (bu21)"".

    La solution est de baisser le niveau d'optimisation (Configure -Doptimize=-O2).

    Les tests suivants sont connus pour échouer sous Mac OS X 10.1.5 en raison d'implémentations boguées (anciennes) de Berkeley DB incluses dans Mac OS X :

    Mac OS X symboles non définis de dyld

    Si après avoir installé Perl 5.8.0 vous recevez des avertissements concernant des symboles manquants, par exemple

    dyld: perl Undefined symbols
_perl_sv_2pv
_perl_get_sv

    vous avez probablement une ancienne installation de pré-Perl-5.8.0 (ou des parties de celle-ci) dans /Library/Perl (les symboles non définis existaient dans les versions de Perl antérieures à 5.8.0). Il semble que pour une raison quelconque, "make install" ne remplace pas toujours complètement les fichiers dans /Library/Perl. Vous pouvez déplacer l'ancienne bibliothèque partagée Perl hors du chemin comme ceci :

    cd /Library/Perl/darwin/CORE
mv libperl.dylib libperlold.dylib

    et ensuite relancer "make install". Notez que ce qui précède est bien sûr extrêmement perturbateur pour tout ce qui utilise /usr/local/bin/perl. Si cela ne fonctionne pas, vous devrez peut-être essayer de supprimer tous les fichiers .bundle sous /Library/Perl, et relancer "make install".

    Support Unicode sur EBCDIC encore inégal

    Bien que largement fonctionnel, le support Unicode présente encore des points problématiques sur les plateformes EBCDIC. L'un de ces points connus concerne les constructions d'expressions régulières "\p{}" et "\P{}" pour les points de code inférieurs à 256 : le "pP" teste les points de code Unicode, sans connaître EBCDIC.

    Vu dans Perl 5.7 mais disparu maintenant

    "Time::Piece" (anciennement connu sous le nom de "Time::Object") a été supprimé car on estimait qu'il n'avait pas assez de valeur pour être un module de base. C'est cependant toujours un module utile, et il est disponible sur CPAN.

    Perl 5.8 ne se compile malheureusement plus sur AmigaOS ; cela s'est cassé accidentellement à un moment donné. Comme il n'y a pas beaucoup de développeurs Amiga disponibles, nous n'avons pas pu résoudre et tester cela à temps pour 5.8.0. Perl 5.6.1 fonctionne toujours pour AmigaOS (tout comme la version de développement 5.7.2).

    Les modules "PerlIO::Scalar" et "PerlIO::Via" (avec majuscules) ont été renommés en "PerlIO::scalar" et "PerlIO::via" (tout en minuscules) juste avant 5.8.0. La raison principale était d'avoir tous les couches PerlIO de base avec des noms entièrement en minuscules. Les "plugins" sont nommés comme d'habitude, par exemple "PerlIO::via::QuotedPrint".

    Les modules "threads::shared::queue" et "threads::shared::semaphore" ont été renommés en "Thread::Queue" et "Thread::Semaphore" juste avant 5.8.0. La raison principale était d'avoir les modules de threads qui respectent la nomenclature normale, "Thread::" (les modules "threads" et "threads::shared" eux-mêmes sont plus de type pragma, ils affectent le temps de compilation, donc ils restent en minuscules).

    Si vous trouvez ce qui vous semble être un bug, vous pourriez consulter les articles récemment postés dans le groupe de discussion comp.lang.perl.misc et la base de données des bugs Perl à l'adresse http://bugs.perl.org/ . Il peut également y avoir des informations sur http://www.perl.com/ , la page d'accueil de Perl.

    Si vous pensez avoir un bug non signalé, veuillez exécuter le programme perlbug inclus dans votre version. Assurez-vous de réduire votre bug à un cas de test minuscule mais suffisant. Votre rapport de bug, ainsi que la sortie de "perl -V", seront envoyés à perlbug@perl.org pour être analysés par l'équipe de portage de Perl.
