NOM

perlhacktips - Conseils pour le piratage du code C principal de Perl

DESCRIPTION

Ce document vous aidera à apprendre la meilleure façon de pirater le code C principal de Perl. Il couvre les problèmes courants, le débogage, le profilage, et plus encore.

Si vous n'avez pas encore lu perlhack et perlhacktut, vous voudrez peut-être le faire d'abord.

PROBLÈMES COURANTS

La source Perl autorise désormais certaines fonctionnalités spécifiques de C99 dont nous savons qu'elles sont prises en charge par toutes les plateformes, mais elle suit principalement les règles d'ANSI C89. Vous ne vous souciez pas qu'une plateforme particulière ait une version défectueuse de Perl ? J'entends dire qu'il y a toujours une forte demande de programmeurs J2EE.

Problèmes d'environnement Perl

  • Ne pas compiler avec le multithreading

    Compiler avec le multithreading (-Duseithreads) réécrit complètement les prototypes de fonction de Perl. Il est préférable d'essayer vos modifications avec cela. Lié à cela est la différence entre les API "Perl_-less" et "Perl_-ly", par exemple :

    Perl_sv_setiv(aTHX_ ...);
sv_setiv(...);

    La première passe explicitement le contexte, ce qui est nécessaire pour par exemple les builds multithreadés. La seconde le fait implicitement ; ne les mélangez pas. Si vous ne passez pas un aTHX_, vous devrez faire un dTHX comme première chose dans la fonction.

    Voir "Comment plusieurs interpréteurs et la concurrence sont pris en charge" dans perlguts pour une discussion plus approfondie sur le contexte.

  • Ne pas compiler avec -DDEBUGGING

    La définition DEBUGGING expose plus de code au compilateur, donc plus de façons pour que les choses tournent mal. Vous devriez l'essayer.

  • Introduction de variables globales (non en lecture seule)

    N'introduisez aucune variable globale modifiable, vraiment globale ou statique de fichier. Elles sont de mauvais goût et compliquent le multithreading et d'autres formes de concurrence. La bonne façon est de les introduire comme de nouvelles variables d'interpréteur, voir intrpvar.h (tout à la fin pour la compatibilité binaire).

    L'introduction de variables globales en lecture seule (const) est acceptable, tant que vous vérifiez avec par exemple "nm libperl.a|egrep -v ' [TURtr] " (si votre "nm" a une sortie de style BSD) que les données que vous avez ajoutées sont réellement en lecture seule. (Si c'est le cas, elles ne devraient pas apparaître dans la sortie de cette commande.)

    Si vous voulez avoir des chaînes statiques, rendez-les constantes :

    static const char etc[] = "...";

    Si vous voulez avoir des tableaux de chaînes constantes, notez soigneusement la bonne combinaison de "const" :

    static const char * const yippee[] =
    {"hi", "ho", "silver"};
  • Ne pas exporter votre nouvelle fonction

    Certaines plateformes (Win32, AIX, VMS, OS/2, pour n'en nommer que quelques-unes) exigent que toute fonction faisant partie de l'API publique (la bibliothèque Perl partagée) soit explicitement marquée comme exportée. Voir la discussion sur embed.pl dans perlguts.

  • Exporter votre nouvelle fonction

    Le nouveau résultat brillant soit d'une nouvelle fonctionnalité authentique, soit de votre arduous refactoring est maintenant prêt et correctement exporté. Alors, que pourrait-il bien se passer ?

    Peut-être simplement que votre fonction n'avait pas besoin d'être exportée en premier lieu. Perl a une longue et pas si glorieuse histoire d'exportation de fonctions qu'il n'aurait pas dû.

    Si la fonction est utilisée uniquement à l'intérieur d'un fichier source, faites-en une fonction statique. Voir la discussion sur embed.pl dans perlguts.

    Si la fonction est utilisée dans plusieurs fichiers, mais destinée uniquement à l'usage interne de Perl (et cela devrait être le cas courant), ne l'exportez pas vers l'API publique. Voir la discussion sur embed.pl dans perlguts.

C99

À partir de la version 5.35.5, nous autorisons désormais certaines fonctionnalités de C99 dans le code source C principal. Cependant, le code des extensions à double durée de vie doit toujours être uniquement C89, car il doit compiler contre des versions antérieures de Perl s'exécutant sur des plateformes plus anciennes. Notez également que nos en-têtes doivent également être valides en tant que C++, car les extensions XS écrites en C++ doivent les inclure, par conséquent les initialiseurs de membres de structure ne peuvent pas être utilisés dans les en-têtes.

La prise en charge de C99 est encore loin d'être complète sur toutes les plateformes que nous prenons actuellement en charge. Comme base, nous ne pouvons supposer que des sémantiques C89 avec les fonctionnalités C99 spécifiques décrites ci-dessous, dont nous avons vérifié qu'elles fonctionnent partout. Il est acceptable de sonder des fonctionnalités C99 supplémentaires et de les utiliser là où elles sont disponibles, à condition qu'il existe également un mécanisme de repli pour les compilateurs qui ne prennent pas en charge la fonctionnalité. Par exemple, nous utilisons le stockage local de thread C11 lorsqu'il est disponible, mais nous nous rabattons sur les API spécifiques aux threads POSIX sinon.

Le code peut utiliser (et dépendre) des fonctionnalités C99 suivantes :

  • déclarations mixtes et code
  • types d'entiers 64 bits

    Pour la cohérence avec le code source existant, utilisez les typedefs "I64" et "U64", au lieu d'utiliser directement "long long" et "unsigned long long".

  • macros variadiques 
    void greet(char *file, unsigned int line, char *format, ...);
#define logged_greet(...) greet(__FILE__, __LINE__, __VA_ARGS__);

    Notez que "__VA_OPT__" est standardisé depuis C23 et C++20. Avant cela, c'était une extension gcc.

  • déclarations dans les boucles for 
    for (const char *p = message; *p; ++p) {
    putchar(*p);
}
  • initialiseurs de membres de structure

    Mais pas dans les en-têtes, car la prise en charge n'a été ajoutée au C++ que relativement récemment.

    Par conséquent, c'est acceptable dans le code C et XS, mais pas dans les en-têtes :

    struct message {
    char *action;
    char *target;
};
struct message mcguffin = {
    .target = "initialiseurs de membres de structure",
    .action = "Construit"
 };

    Vous ne pouvez pas utiliser la syntaxe similaire pour les littéraux composites, car nous compilons également Perl à l'aide de compilateurs C++ :

    /* c'est acceptable */
struct message m = {
    .target = "une cible",
    .action = "une action"
};
/* ce n'est pas valide en C++ */
m = (struct message){
    .target = "une cible",
    .action = "une action"
};

    Bien que les descripteurs de structure soient utilisables, les descripteurs de tableau associés ne le sont pas, car ils ne sont pas du tout pris en charge par C++.

  • membres de tableau flexibles

    Ceci est conforme aux normes :

    struct greeting {
    unsigned int len;
    char message[];
};

    Cependant, le code source utilise déjà le hack "chumminess non garantie avec le compilateur" dans de nombreux endroits :

    struct greeting {
    unsigned int len;
    char message[1];
};

    Strictement, c'est un comportement indéfini d'accéder au-delà de "message[0]", mais il s'agit d'un hack couramment utilisé depuis l'époque de K&R, et son utilisation n'a pas posé de problème pratique nulle part (dans le code source de Perl ou tout autre code C courant). Par conséquent, on ne sait pas ce que nous gagnerions en passant activement à l'approche C99.

  • commentaires "//"

    Tous les compilateurs que nous avons testés en prennent en charge l'utilisation. Tous les humains que nous avons testés n'en prennent pas en charge l'utilisation.

  • booléens

    Vous pouvez utiliser "bool", "true", et "false" tels que fournis par "<stdbool.h>" (ou nativement en C++).

Le code ne doit explicitement pas utiliser d'autres fonctionnalités C99. Par exemple :

  • tableaux de longueur variable

    Non pris en charge par aucun MSVC, et cela ne changera pas.

    Même les tableaux de longueur "variable" où la variable est une expression constante sont des erreurs de syntaxe sous MSVC.

  • types C99 dans "<stdint.h>"

    Utilisez "PERL_INT_FAST8_T" etc. tels que définis dans handy.h

  • chaînes de format C99 dans "<inttypes.h>"

    "snprintf" dans la libc VMS n'a ajouté la prise en charge de "PRIdN" etc. que très récemment, ce qui signifie que des binaires vivants

(Le "sv_catpvf" etc de Perl utilise le code d'analyse dans sv.c, qui prend en charge le modificateur "z", ainsi que des formats spécifiques à Perl tels que "SVf".)

Si vous souhaitez utiliser une fonctionnalité C99 non répertoriée ci-dessus, vous devez faire l'une des choses suivantes :

  • Sondez-la dans Configure, définissez une variable dans config.sh et ajoutez une logique de secours dans les en-têtes pour les plateformes qui ne la possèdent pas.
  • Écrivez du code de test et vérifiez qu'il fonctionne sur les plateformes que nous devons prendre en charge, avant de vous y fier inconditionnellement.

Il est probable que vous souhaitiez répéter le même plan que celui utilisé pour obtenir l'ensemble actuel de fonctionnalités C99. Voir le message à https://markmail.org/thread/odr4fjrn72u2fkpz pour les sondes C99 que nous avons utilisées auparavant. Notez que les deux compilateurs les plus "difficiles" semblent être MSVC et le compilateur du vendeur sur VMS. À ce jour, tous les compilateurs *nix ont été beaucoup plus flexibles dans ce qu'ils prennent en charge.

Sur les plateformes *nix, Configure tente de définir les indicateurs du compilateur de manière appropriée. Tous les compilateurs du vendeur que nous avons testés prenaient en charge C99 (ou C11) par défaut. Cependant, les anciennes versions de gcc utilisent par défaut C89, ou autorisent la plupart des fonctionnalités C99 (avec des avertissements), mais interdisent les déclarations dans les boucles for à moins que "-std=gnu99" ne soit ajouté. L'alternative "-std=c99" pourrait sembler meilleure, mais son utilisation sur certaines plateformes peut empêcher "<unistd.h>" de déclarer certains prototypes, ce qui casse la compilation. L'indicateur "-ansi" de gcc implique "-std=c89", nous ne pouvons donc plus le définir, d'où l'option Configure "-gccansipedantic" qui n'ajoute désormais que "-pedantic".

Les fichiers source du cœur de Perl (ceux situés au niveau supérieur de la distribution source) sont automatiquement compilés avec autant que possible des indicateurs "-std=gnu99", "-pedantic", et une sélection d'indicateurs "-W" (voir cflags.SH). Les fichiers dans ext/, dist/, cpan/, etc. sont compilés avec les mêmes indicateurs que ceux que Perl installé utiliserait pour compiler les extensions XS.

Fondamentalement, il est sûr de supposer que Configure et cflags.SH ont choisi la meilleure combinaison d'indicateurs pour la version de gcc sur la plateforme, et toute tentative d'ajouter d'autres indicateurs liés à l'application d'un dialecte C entraînera des problèmes soit localement, soit sur d'autres systèmes vers lesquels le code est expédié.

Nous pensons que le support C99 dans gcc 3.1 est suffisant pour nous, mais nous n'avons pas de gcc vieux de 19 ans sous la main pour le vérifier :-) Si vous avez des compilateurs anciens du vendeur qui ne prennent pas C99 par défaut, les indicateurs que vous pourriez vouloir essayer sont

"-qlanglvl=stdc99"
HP/UX
"-AC99"
Solaris
"-xc99"

Noms de symboles et pollution de namespace

Choisir des noms de symboles légaux

C réserve à son implémentation tout symbole dont le nom commence par un trait de soulignement suivi immédiatement soit d'une lettre majuscule "[A-Z]", soit d'un autre trait de soulignement. C++ réserve en outre tout symbole contenant deux traits de soulignement consécutifs, et réserve de plus dans l'espace de noms global tout symbole commençant par un trait de soulignement, pas seulement ceux suivis d'une majuscule. Nous nous intéressons à C++ car les fichiers d'en-tête (*.h) doivent pouvoir être compilés par lui, et certaines personnes développent entièrement avec un compilateur C++.

Les conséquences de l'échec de cette démarche sont probablement nulles. À moins que vous ne tombiez sur un nom que l'implémentation utilise, les choses fonctionneront. En fait, le cœur de Perl présente plus de quelques cas d'utilisation de symboles réservés par l'implémentation. (Ceux-ci sont progressivement modifiés.) Mais votre code pourrait cesser de fonctionner à tout moment où l'implémentation déciderait d'utiliser un nom que vous aviez déjà choisi, potentiellement des années auparavant.

Il est donc préférable de :

Ne pas commencer un nom de symbole au niveau du fichier par un trait de soulignement ; (par exemple, n'utilisez pas : "_FOOBAR")
Il est acceptable d'avoir un symbole dans une fonction ou un bloc tel que "_ref", commençant par un trait de soulignement suivi d'une lettre minuscule.
Ne pas utiliser deux traits de soulignement consécutifs dans un nom de symbole ; (par exemple, n'utilisez pas "FOO__BAR")

POSIX réserve également de nombreux symboles. Voir la section 2.2.2 dans https://pubs.opengroup.org/onlinepubs/9699919799/functions/V2_chap02.html. Perl entre également en conflit avec cela.

Perl se réserve pour son utilisation tout symbole commençant par "Perl", "perl", ou "PL_". Chaque fois que vous introduisez une macro dans un fichier d'en-tête qui ne respecte pas cette convention, vous créez la possibilité d'un conflit de nom avec un module XS existant, à moins que vous ne la limitiez, par exemple,

#ifdef PERL_CORE
#  define my_symbol
#endif

Il existe de nombreux symboles dans les fichiers d'en-tête qui ne sont pas de cette forme, et qui sont accessibles depuis l'espace de noms XS, intentionnellement ou non, à peu près tout dans config.h, par exemple.

Devoir utiliser l'un de ces préfixes nuit à la lisibilité du code, et n'a pas posé de problème réel pour les noms non triviaux. Des choses comme Perl définissant sa propre macro "MAX" ont été problématiques, mais elles ont été rapidement découvertes, et une garde "#ifdef PERL_CORE" a été ajoutée.

Il n'y a donc pas de règle imposée concernant l'utilisation de tels symboles, soyez simplement conscient des problèmes.

Choisir de bons noms de symboles

Idéalement, un nom de symbole doit décrire correctement et précisément son objectif. Mais il y a une tension entre cela et obtenir des noms qui sont trop longs et donc maladroits à taper et à lire. Les métaphores pourraient être utiles (un nom poétique), mais celles-ci ont tendance à être culturellement spécifiques et peuvent ne pas être comprises par quelqu'un dont la langue maternelle n'est pas l'anglais, ou même qui provient d'un milieu culturel différent. De plus, le talent d'écrire de la poésie semble rare chez les programmeurs.

Certains noms de symboles ne reflètent pas leur objectif, mais sont néanmoins utilisables en raison de conventions de longue date. Ceux-ci sont souvent originaires du domaine des mathématiques, où "i" et "j" sont fréquemment utilisés comme indices, et "n" comme compte de population. Depuis au moins les années 1950, les programmes informatiques utilisent "i", etc. comme variables de boucle.

Notre recommandation est de choisir un nom qui décrit raisonnablement le but, et de commenter sa déclaration plus précisément.

On ne devrait certainement pas utiliser de noms trompeurs ou ambigus. "last_foo" pourrait signifier soit le dernier "foo", soit le précédent "foo", et pourrait donc être déroutant pour le lecteur, ou même pour l'auteur qui revient au code après quelques mois de travail sur autre chose. Parfois, le programmeur a une ligne de pensée particulière à l'esprit, et ne réalise pas que l'ambiguïté est présente.

Il y a probablement encore de nombreux bugs d'off-by-one à cause du fait que le nom ""av_len"" dans perlapi ne correspond pas à ce que signifient d'autres constructions "-len", comme ""sv_len"" dans perlapi. Des synonymes maladroits (et controversés) ont été créés à utiliser à la place pour transmettre son vrai sens (""av_top_index"" dans perlapi). Finalement, cependant, quelqu'un a eu la meilleure idée de créer un nouveau nom pour signifier ce que la plupart des gens pensent que "-len" signifie. Ainsi, ""av_count"" dans perlapi est né. Et nous souhaitons que cela ait été pensé beaucoup plus tôt.

Écrire des macros plus sûres

Les macros sont largement utilisées dans le cœur de Perl pour des choses comme masquer les détails internes à l'appelant, de sorte qu'il n'ait pas à s'en préoccuper. Par exemple, la plupart des lignes de code n'ont pas besoin de savoir si elles s'exécutent sur une perl threadée ou non threadée. Ce détail est automatiquement largement masqué.

Il est souvent préférable d'utiliser une fonction en ligne au lieu d'une macro. Elles sont immunisées contre les collisions de noms avec l'appelant, et ne magnifient pas les problèmes lorsqu'elles sont appelées avec des paramètres qui sont des expressions avec des effets secondaires. Il fut un temps où l'on pouvait choisir une macro plutôt qu'une fonction en ligne car le support des compilateurs pour les fonctions en ligne était assez limité. Certains n'inlineraient réellement que les deux ou trois premières rencontrées dans une compilation. Mais ces jours sont révolus depuis longtemps, et les fonctions en ligne sont entièrement prises en charge dans les compilateurs modernes.

Néanmoins, il existe des situations où une fonction ne suffit pas et où une macro est requise. Un exemple est lorsqu'un paramètre peut être de plusieurs types. Une fonction doit être déclarée avec un seul type de paramètre explicite, une macro peut donc être appelée.

Ou peut-être que le code impliqué est si trivial qu'une fonction serait simplement une complication excessive, comme lorsque la macro crée simplement un nom mnémotechnique pour une valeur constante.

Si vous choisissez d'utiliser une macro non triviale, soyez conscient qu'il existe plusieurs pièges évitables qui peuvent survenir. Gardez à l'esprit qu'une macro est développée dans le contexte lexical de chaque endroit de la source où elle est appelée. Si vous avez un jeton "foo" dans la macro et que la source possède également "foo", la signification du "foo" de la macro deviendra celle de l'appelant. Parfois, c'est exactement le comportement souhaité, mais soyez conscient que cela a tendance à être confus plus tard. Cela transforme effectivement "foo" en un mot réservé pour tout code qui appelle la macro, et ce fait n'est généralement pas documenté ni pris en compte. Il est plus sûr de passer "foo" en tant que paramètre, de sorte que " ;foo" reste librement disponible pour l'appelant et l'interface de la macro est explicitement spécifiée.

Pire encore lorsque l'équivalence entre les deux "foo" est fortuite. Supposons par exemple que la macro déclare une variable

int foo

Cela fonctionne bien tant que l'appelant ne définit pas la chaîne "foo" d'une manière ou d'une autre. Et cela pourrait ne pas être avant des années que quelqu'un ne rencontre un cas où "foo" est utilisé. Par exemple, un futur appelant pourrait faire ceci :

#define foo  bar

Alors cette déclaration de "foo" dans la macro devient soudainement

int bar

Cela pourrait signifier que quelque chose de complètement différent se produit que prévu. C'est difficile à déboguer ; la macro et l'appel peuvent même ne pas être dans le même fichier, il faudrait donc creuser et grincer des dents pour le découvrir.

Par conséquent, si une macro utilise des variables, leurs noms devraient être tels qu'il est très peu probable qu'ils entrent en collision avec un appelant, maintenant ou jamais. Une façon de faire cela, maintenant utilisée dans la source de Perl, est d'inclure le nom de la macro elle-même dans le nom de chaque variable de la macro. Supposons que la macro s'appelle "SvPV". Nous pourrions alors avoir

int foo_svpv_ = 0;

C'est plus difficile à lire que le simple "foo", mais il est à peu près garanti qu'un appelant n'utilisera jamais naïvement "foo_svpv_" (et rencontrera des problèmes). (La mise en minuscules le rend plus clair qu'il s'agit d'une variable, mais suppose qu'il n'y aura pas deux éléments dont les noms diffèrent uniquement par la casse de leurs lettres.) Le trait de soulignement final rend encore plus improbable un conflit, car ceux-ci, par convention, signifient un nom de variable privé. (Voir "Choix des noms de symboles légaux" pour les restrictions sur les noms que vous pouvez utiliser.)

Ce type de collision de noms ne se produit pas avec les paramètres formels de la macro, ils n'ont donc pas besoin d'avoir des noms compliqués. Mais il existe des pièges lorsqu'un paramètre est une expression, ou a une magie Perl attachée. Lors de l'appel d'une fonction, C évaluera le paramètre une fois et passera le résultat à la fonction. Mais lors de l'appel d'une macro, le paramètre est copié tel quel par le préprocesseur C à chaque instance à l'intérieur de la macro. Cela signifie que lors de l'évaluation d'un paramètre ayant des effets secondaires, les résultats de la fonction et de la macro diffèrent. C'est particulièrement risqué lorsqu'un paramètre a une magie de surcharge, disons que c'est une variable liée qui lit la ligne suivante d'un fichier à chaque évaluation. La faire lire plusieurs lignes par appel n'est probablement pas ce que l'appelant avait l'intention. Si une macro fait référence à un paramètre potentiellement surchargé plus d'une fois, elle devrait d'abord en faire une copie, puis utiliser cette copie pour le reste du temps. Il existe des macros dans le noyau de Perl qui violent cela, mais elles sont progressivement converties, généralement en utilisant des fonctions en ligne à la place.

Ci-dessus, nous avons dit "faire d'abord une copie". Dans une macro, c'est plus facile à dire qu'à faire, car les macros sont normalement des expressions, et les déclarations ne sont pas autorisées dans les expressions. Mais la construction "STMT_START" .. "STMT_END", décrite dans perlapi, vous permet d'avoir des déclarations dans la plupart des contextes, tant que vous n'avez pas besoin d'une valeur de retour. Si vous avez besoin d'une valeur de retour, vous pouvez rendre l'interface telle qu'un pointeur soit passé à la construction, qui y stocke alors son résultat. (Ou vous pouvez utiliser des groupes d'accolades GCC. Mais ceux-ci nécessitent une solution de repli si le code doit un jour être exécuté sur une plateforme qui ne dispose pas de cette extension non standard de C. Et cette solution de repli serait un autre chemin de code, qui peut se désynchroniser avec celui des accolades, donc faire cela n'est pas conseillé.) Dans les situations où il n'y a pas d'autre moyen, Perl fournit ""PL_Sv"" dans perlintern et ""PL_na"" dans perlapi à utiliser (avec une légère pénalité de performance) pour certains de ces cas courants. Mais attention, une chaîne d'appels impliquant plusieurs macros qui les utilisent annulera l'utilisation des autres. Il a été très difficile de déboguer.

Pour un exemple concret de ces pièges en action, voir https://perlmonks.org/?node_id=11144355.

Problèmes de portabilité

Les causes courantes de défaillances de compilation et/ou d'exécution, non spécifiques à Perl en tant que tel, sont les suivantes. Le FAQ C est une bonne lecture pour s'endormir. Veuillez tester vos modifications avec autant de compilateurs C et de plateformes que possible ; nous le ferons de toute façon, et il est agréable de s'éviter une gêne publique.

Étudiez également attentivement perlport pour éviter toute mauvaise hypothèse concernant le système d'exploitation, les systèmes de fichiers, le jeu de caractères, etc.

Ne présumez pas qu'un système d'exploitation indique un compilateur particulier.

  • Conversion de pointeurs en entiers ou d'entiers en pointeurs 
    void castaway(U8* p)
{
  IV i = p;

    ou

    void castaway(U8* p)
{
  IV i = (IV)p;

    Les deux sont mauvais, défectueux et non portables. Utilisez la macro PTR2IV() qui fait cela correctement. (De même, il existe PTR2UV(), PTR2NV(), INT2PTR() et NUM2PTR().)

  • Conversion entre pointeurs de fonction et pointeurs de données

    Techniquement, la conversion entre pointeurs de fonction et pointeurs de données n'est pas portable et est indéfinie, mais en pratique, cela semble fonctionner, mais vous devriez utiliser les macros FPTR2DPTR() et DPTR2FPTR(). Parfois, vous pouvez également jouer avec des unions.

  • Supposer "sizeof(int) == sizeof(long)"

    Il existe des plateformes où les longs sont de 64 bits, et des plateformes où les entiers sont de 64 bits, et pendant que nous vous choquons, même des plateformes où les courts sont de 64 bits. Tout cela est légal selon la norme C. (En d'autres termes, "long long" n'est pas un moyen portable de spécifier 64 bits, et "long long" n'est même pas garanti d'être plus large que "long".)

    Au lieu de cela, utilisez les définitions "IV", "UV", "IVSIZE", "I32SIZE", et ainsi de suite. Évitez les choses comme "I32" car il n'est pas garanti qu'elles soient *exactement* de 32 bits (elles sont *au moins* de 32 bits), ni qu'elles soient "int" ou "long". Si vous avez explicitement besoin de variables 64 bits, utilisez "I64" et "U64".

  • Supposer que l'on peut déréférencer n'importe quel type de pointeur pour n'importe quel type de données 
    char *p = ...;
long pony = *(long *)p;    /* MAUVAIS */

    Beaucoup de plateformes, tout à fait justement, vous donneront un dump mémoire au lieu d'un poney si p n'est pas correctement aligné.

  • Conversions d'expressions à valeur (lvalue casts) 
    (int)*p = ...;    /* MAUVAIS */

    Simplement pas portable. Obtenez votre valeur à gauche (lvalue) du bon type, ou utilisez peut-être des variables temporaires, ou des astuces sales avec des unions.

  • Supposer quoi que ce soit à propos des structs (en particulier celles que vous ne contrôlez pas, comme celles provenant des en-têtes système)
  • Qu'un certain champ existe dans une struct
  • Qu'aucun autre champ n'existe en dehors de ceux que vous connaissez
  • Qu'un champ a une certaine signation, taille ou type
  • Que les champs sont dans un ordre particulier
•

•

  • Il peut y avoir des octets de remplissage entre les champs pour aligner les champs - les octets peuvent être n'importe quoi
  • Les structs sont requises d'être alignées sur l'alignement maximal requis par les champs - ce qui pour les types natifs est généralement équivalent à sizeof(le_champ).
  • Supposer que le jeu de caractères est similaire à l'ASCII

    Perl peut être compilé et exécuté sous des plateformes EBCDIC. Voir perlebcdic. C'est transparent dans la plupart des cas, mais parce que les jeux de caractères diffèrent, vous ne devriez pas utiliser de constantes numériques (décimales, octales, ni hexadécimales) pour faire référence à des caractères. Vous pouvez dire sans risque 'A', mais pas 0x41. Vous pouvez dire sans risque '\n', mais pas "\012". Cependant, vous pouvez utiliser des macros définies dans utf8.h pour spécifier n'importe quel point de code de manière portable. LATIN1_TO_NATIVE(0xDF) sera le point de code qui signifie LETTRE LATINE PETITE eszett sur la plateforme sur laquelle vous êtes en train de fonctionner (sur les plateformes ASCII, cela compile sans ajouter de code supplémentaire, donc il n'y a aucun impact sur les performances sur celles-ci). Les entrées acceptables pour "LATIN1_TO_NATIVE" vont de 0x00 à 0xFF. Si votre entrée n'est pas garantie dans cette plage, utilisez plutôt "UNICODE_TO_NATIVE". "NATIVE_TO_LATIN1" et "NATIVE_TO_UNICODE" traduisent dans le sens inverse.

    Si vous avez besoin de la représentation sous forme de chaîne d'un caractère qui n'a pas de nom mnémotechnique en C, vous devriez l'ajouter à la liste dans regen/unicode_constants.pl, et laisser Perl créer des "#define" pour vous, en fonction de la plateforme actuelle.

    Notez que les macros "isFOO" et "toFOO" dans handy.h fonctionnent correctement sur les points de code et chaînes natifs.

    De plus, la plage 'A' - 'Z' en ASCII est une séquence continue de 26 caractères alphabétiques majuscules. Ce n'est pas vrai en EBCDIC. Ni pour 'a' à 'z'. Mais '0' - '9' est une plage continue dans les deux systèmes. Ne supposez rien sur d'autres plages. (Notez que la gestion spéciale des plages dans les motifs d'expressions régulières et les translittérations donne l'impression au code Perl que les plages susmentionnées sont toutes continues.)

    Beaucoup de commentaires dans le code existant ignorent la possibilité d'EBCDIC, et

    peut être erroné, même si le code fonctionne. Ceci est en fait un hommage à la réussite de l'insertion transparente permettant de gérer EBCDIC sans avoir à modifier le code préexistant.

    UTF-8 et UTF-EBCDIC sont deux encodages différents utilisés pour représenter des points de code Unicode sous forme de séquences d'octets. Des macros portant les mêmes noms (mais avec des définitions différentes) dans utf8.h et utfebcdic.h sont utilisées pour permettre au code appelant de croire qu'il n'existe qu'un seul encodage. Il est presque toujours fait référence à "utf8", mais cela inclut aussi la version EBCDIC. Encore une fois, les commentaires dans le code peuvent être erronés même si le code lui-même est correct. Par exemple, le concept des caractères "invariants" UTF-8 diffère entre ASCII et EBCDIC. Sur les plateformes ASCII, seuls les caractères qui n'ont pas le bit de poids fort défini (c'est-à-dire dont les ordonnaux sont strictement ASCII, 0 - 127) sont invariants, et la documentation et les commentaires du code peuvent supposer cela, faisant souvent référence à quelque chose comme, par exemple, "hibit". La situation diffère et n'est pas aussi simple sur les machines EBCDIC, mais tant que le code utilise lui-même la macro NATIVE_IS_INVARIANT() de manière appropriée, il fonctionne, même si les commentaires sont erronés.

    Comme indiqué dans "TESTING" dans perlhack, lors de la rédaction de scripts de test, le fichier t/charset_tools.pl contient des fonctions utiles pour écrire des tests valides sur les plateformes ASCII et EBCDIC. Parfois, cependant, un test ne peut pas utiliser une fonction et il est gênant d'avoir différentes versions de test selon la plateforme. Il existe 20 points de code qui sont identiques dans les 4 jeux de caractères actuellement reconnus par Perl (les 3 pages de codes EBCDIC plus ISO 8859-1 (ASCII/Latin1)). Ceux-ci peuvent être utilisés dans de tels tests, bien qu'il y ait une faible possibilité que Perl devienne disponible dans un autre jeu de caractères, ce qui pourrait casser votre test. Tous ces points de code, sauf un, sont des caractères de contrôle C0. Les contrôles les plus significatifs qui sont identiques sont "\0", "\r", et "\N{VT}" (également spécifiable sous forme de "\cK", "\x0B", "\N{U+0B}", ou "\013"). Le seul non-contrôle est U+00B6 PILCROW SIGN. Les contrôles qui sont identiques ont le même motif de bits dans les 4 jeux de caractères, quelle que soit la nature UTF8 de la chaîne qui les contient. Le motif de bits pour U+B6 est le même dans les 4 pour les chaînes non-UTF8, mais diffère dans chacune lorsque la chaîne contenant est encodée en UTF-8. Les seuls autres points de code qui présentent une sorte de similitude à travers les 4 jeux de caractères sont la paire 0xDC et 0xFC. Ensemble, ils représentent la LETTRE LATINE U AVEC DIACRITIQUE majuscule et minuscule, mais laquelle est majuscule et laquelle est minuscule peut être inversée : 0xDC est la majuscule en Latin1 et 0xFC est la minuscule, tandis que 0xFC est la majuscule en EBCDIC et 0xDC est la minuscule. Ce fait peut être exploité pour écrire des tests insensibles à la casse qui sont identiques sur les 4 jeux de caractères.

  • En supposant que le jeu de caractères est uniquement ASCII

    ASCII est un encodage de 7 bits, mais les octets contiennent 8 bits. Les 128 caractères supplémentaires ont des significations différentes selon la locale. En l'absence de locale, ces caractères supplémentaires sont généralement considérés comme non assignés, ce qui a posé certains problèmes. Cela a été modifié à partir de la version 5.12 afin que ces caractères puissent être considérés comme Latin-1 (ISO-8859-1).

    #ifdef SNOSH
...

...
#endif SNOSH    /* MAUVAIS */

    Les directives #endif et #else ne peuvent pas avoir de contenu non-commentaire après elles de manière portable. Si vous souhaitez documenter ce qui se passe (ce qui est une bonne idée surtout si les branches sont longues), utilisez des commentaires (C) :

    #ifdef SNOSH

...

    enum color {
  CERULEAN,
  CHARTREUSE,
  CINNABAR,     /* MAUVAIS */

    n'est pas portable. Laissez la dernière virgule.

    Notez également que la façon dont les enums sont implicitement transformables en entiers varie selon les compilateurs, vous pourriez avoir besoin de (int).

  • Mélange de pointeurs char signés avec des pointeurs unsigned char 
    int foo(char *s) { ... }
...
unsigned char *t = ...; /* Ou U8* t = ... */
foo(t);   /* MAUVAIS */

    Bien que ce soit une pratique légale, elle est certainement douteuse, et carrément fatale sur au moins une plateforme : par exemple, VMS cc considère cela comme une erreur fatale. L'une des raisons pour lesquelles les gens font souvent cette erreur est qu'un "char nu" et donc le déréférencement d'un "pointeur char nu" ont une signification indéfinie : cela dépend du compilateur, des options du compilateur et de la plateforme sous-jacente que le résultat soit signé ou non signé. Pour cette même raison, utiliser un 'char' comme indice de tableau est mauvais.

  • Macros qui contiennent des constantes de chaîne et leurs arguments comme sous-chaînes des constantes de chaîne 
    #define FOO(n) printf("number = %d\n", n)    /* MAUVAIS */
FOO(10);

    La sémantique pré-ANSI pour cela était équivalente à

    printf("10umber = %d\10");

    ce qui n'est probablement pas ce que vous attendiez. Malheureusement, au moins un compilateur C raisonnablement courant et moderne fait une "vraie rétrocompatibilité" ici, sur AIX c'est ce qui se passe encore même si le reste du compilateur AIX est très heureux d'être C89.

  • Utilisation de formats printf pour des types C non basiques 
    IV i = ...;
printf("i = %d\n", i);    /* MAUVAIS */

    Bien que cela puisse fonctionner par accident sur certaines plateformes (où IV est un "int"), en général cela ne peut pas. IV peut être quelque chose de plus grand. La situation est encore pire avec des types plus spécifiques (définis par l'étape de configuration de Perl dans config.h) :

    Uid_t who = ...;
printf("who = %d\n", who);    /* MAUVAIS */

    Le problème ici est que Uid_t peut non seulement ne pas être de la largeur d'un "int", mais il peut aussi être non signé, auquel cas de grands uid seraient affichés comme des valeurs négatives.

    Il n'y a pas de solution simple à cela en raison de l'intelligence limitée de printf(), mais pour de nombreux types, le bon format est disponible avec le suffixe 'f' ou '_f', par exemple :

    IVdf /* IV en décimal */
UVxf /* UV en hexadécimal */
U32of /* Un U32 en octal */
printf("i = %"IVdf"\n", i); /* Le IVdf est une constante de chaîne. */
Uid_t_f /* Uid_t en décimal */
printf("who = %"Uid_t_f"\n", who);

    Ou vous pouvez essayer de caster vers un type "assez large" :

    printf("i = %"IVdf"\n", (IV)quelque_chose_de_très_petit_et_signé);

    Voir "Formatted Printing of Size_t and SSize_t" dans perlguts pour savoir comment les imprimer.

    N'oubliez pas non plus que le format %p requiert réellement un pointeur void :

    U8* p = ...;
printf("p = %p\n", (void*)p);

    L'option gcc "-Wformat" recherche de tels problèmes.

  • Passage aveugle de va_list

    Toutes les plateformes ne prennent pas en charge le passage de va_list à d'autres fonctions varargs (stdarg). La bonne chose à faire est de copier la va_list en utilisant Perl_va_copy() si NEED_VA_COPY est défini.

  • Utilisation d'expressions de déclaration gcc 
    val = ({...;...;...});    /* MAUVAIS */

    Bien que ce soit une extension agréable, elle n'est pas portable. Historiquement, Perl les utilisait dans des macros si disponibles pour gagner en vitesse (essentiellement comme une forme étrange d'inlining), mais nous prenons désormais en charge (ou émules) les fonctions C99 "static inline", utilisez-les donc à la place. Déclarez les fonctions comme "PERL_STATIC_INLINE" pour revenir transparenment à l'émulation si nécessaire.

  • Relier plusieurs instructions dans une macro

    Utilisez les macros "STMT_START" et "STMT_END".

    STMT_START {
   ...
} STMT_END

    Mais des bugs subtils (mais évitables si vous le faites correctement) peuvent être introduits avec ceux-ci ; voir ""STMT_START"" dans perlapi pour les meilleures pratiques d'utilisation.

  • Supposer que le contenu de la mémoire statique pointée par les valeurs de retour des wrappers Perl pour C l library functions doesn't change. Many C library functions return pointers to static storage that can be overwritten by subsequent calls to the same or related functions. If you handle those returns before one of those functions that share the storage gets called, this is fine, but in embedded perls, or when using threads, such a function may get called before you get a chance to handle it.

    "Dealing with embedded perls and threads" in perlclib contains a list of problematic functions with good advice as to how to cope with them.

Problematic System Interfaces

There are lots of issues with using various C library functions, including security ones. You should read perlclib which covers things in detail.

Remember that Perl strings are NOT the same as C strings: They may contain "NUL" characters, whereas a C string is terminated by the first "NUL". That is why Perl API functions that deal with strings generally take a pointer to the first byte and either a length or a pointer to the byte just beyond the final one.

And this is the reason that many of the C library string handling functions should not be used. They don't cope with the full generality of Perl strings. It may be that your test cases don't have embedded "NUL"s, and so the tests pass, whereas there may well eventually arise real-world cases where they fail. A lesson here is to include "NUL"s in your tests. Now it's fairly rare in most real world cases to get "NUL"s, so your code may seem to work, until one day a "NUL" comes along.

Here's an example. It used to be a common paradigm, for decades, in the perl core to use "strchr("list", c)" to see if the character "c" is any of the ones given in "list", a double-quote-enclosed string of the set of characters that we are seeing if "c" is one of. As long as "c" isn't a "NUL", it works. But when "c" is a "NUL", "strchr" returns a pointer to the terminating "NUL" in "list". This likely will result in a segfault or a security issue when the caller uses that end pointer as the starting point to read from.

A solution to this and many similar issues is to use the "mem"-foo C library functions instead. In this case "memchr" can be used to see if "c" is in "list" and works even if "c" is "NUL". These functions need an additional parameter to give the string length. In the case of literal string parameters, perl has defined macros that calculate the length for you. See "String Handling" in perlapi.

DEBUGGING

You can compile a special debugging version of Perl, which allows you to use the "-D" option of Perl to tell more about what Perl is doing. But sometimes there is no alternative than to dive in with a debugger, either to see the stack trace of a core dump (very useful in a bug report), or trying to figure out what went wrong before the core dump happened, or how did we end up having wrong or unexpected results.

Poking at Perl

To really poke around with Perl, you'll probably want to build Perl for debugging, like this:

./Configure -d -DDEBUGGING
make

"-DDEBUGGING" turns on the C compiler's "-g" flag to have it produce debugging information which will allow us to step through a running program, and to see in which C function we are at (without the debugging information we might see only the numerical addresses of the functions, which is not very helpful). It will also turn on the "DEBUGGING" compilation symbol which enables all the internal debugging code in Perl. There are a whole bunch of things you can debug with this: perlrun lists them all, and the best way to find out about them is to play about with them. The most useful options are probably

l  Context (loop) stack processing
s  Stack snapshots (with v, displays all stacks)
t  Trace execution
o  Method and overloading resolution
c  String/numeric conversions

For example

$ perl -Dst -e '$x + 1'
....
(-e:1)      gvsv(main::x)
    =>  UNDEF
(-e:1)      const(IV(1))
    =>  UNDEF  IV(1)
(-e:1)      add
    =>  NV(1)

Some of the functionality of the debugging code can be achieved with a non-debugging perl by using XS modules:

-Dr => use re 'debug'
-Dx => use O 'Debug'

Using a source-level debugger

If the debugging output of "-D" doesn't help you, it's time to step through perl's execution with a source-level debugger.

•
We'll use "gdb" for our examples here; the principles will apply to any debugger (many vendors call their debugger "dbx"), but check the manual of the one you're using.

To fire up the debugger, type

gdb ./perl

Or if you have a core dump:

gdb ./perl core

You'll want to do that in your Perl source tree so the debugger can read the source code. You should see the copyright message, followed by the prompt.

(gdb)

  • run [args]

    Run the program with the given arguments.

  • break function_name
  • break source.c:xxx

    Tells the debugger that we'll want to pause execution when we reach either the named function (but see "Internal Functions" in perlguts!) or the given line in the named source file.

  • step

    Steps through the program a line at a time.

  • next

    Steps through the program a line at a time, without descending into functions.

  • continue

    Run until the next breakpoint.

  • finish

    Run until the end of the current function, then stop again.

  • 'enter'

    Just pressing Enter will do the most recent operation again - it's a blessing when stepping through miles of source code.

  • ptype

    Prints the C definition of the argument given.

    (gdb) ptype PL_op

    OP *op_sibparent;

Recent versions of gdb have fairly good macro support, but in order to use it you'll need to compile perl with macro definitions included in the debugging information. Dumping Perl Data Structures

One way to get around this macro hell is to use the dumping functions in dump.c; these work a little like an internal Devel::Peek, but they also cover OPs and other structures that you can't get at from Perl. Interfaces système problématiques

Il y a beaucoup de problèmes avec l'utilisation de diverses fonctions de la bibliothèque C, y compris celles relatives à la sécurité. Vous devriez lire perlclib qui couvre ces aspects en détail.

Rappelez-vous que les chaînes Perl ne sont PAS identiques aux chaînes C : elles peuvent contenir des caractères "NUL", alors qu'une chaîne C est terminée par le premier caractère "NUL". C'est pourquoi les fonctions de l'API Perl qui traitent des chaînes prennent généralement un pointeur vers le premier octet et soit une longueur, soit un pointeur vers l'octet juste après le dernier.

Et c'est la raison pour laquelle de nombreuses fonctions de manipulation de chaînes de la bibliothèque C ne devraient pas être utilisées. Elles ne gèrent pas toute la généralité des chaînes Perl. Il se peut que vos cas de test n'aient pas de caractères "NUL" intégrés, et donc que les tests réussissent, alors qu'il peut très bien y avoir à terme des cas réels où ils échouent. Une leçon à retenir est d'inclure des caractères "NUL" dans vos tests. Il est assez rare dans la plupart des cas réels d'obtenir des caractères "NUL", donc votre code peut sembler fonctionner, jusqu'au jour où un caractère "NUL" apparaît.

Voici un exemple. C'était autrefois un paradigme courant, pendant des décennies, dans le cœur de Perl d'utiliser "strchr("list", c)" pour voir si le caractère "c" fait partie de ceux donnés dans "list", une chaîne délimitée par des guillemets doubles contenant l'ensemble des caractères que nous vérifions si "c" en fait partie. Tant que "c" n'est pas un caractère "NUL", cela fonctionne. Mais quand "c" est un caractère "NUL", "strchr" renvoie un pointeur vers le caractère "NUL" de terminaison dans "list". Cela entraînera probablement un segfault ou un problème de sécurité lorsque l'appelant utilisera ce pointeur de fin comme point de départ pour lire.

Une solution à ce problème et à de nombreux problèmes similaires est d'utiliser plutôt les fonctions de bibliothèque C de type "mem"-foo. Dans ce cas, "memchr" peut être utilisé pour vérifier si "c" se trouve dans "list" et fonctionne même si "c" est un caractère "NUL". Ces fonctions nécessitent un paramètre supplémentaire pour spécifier la longueur de la chaîne. Dans le cas de paramètres de chaînes littérales, Perl a défini des macros qui calculent la longueur pour vous. Voir "String Handling" dans perlapi.

DÉBOGAGE

Vous pouvez compiler une version spéciale de débogage de Perl, qui vous permet d'utiliser l'option "-D" de Perl pour en savoir plus sur ce que Perl fait. Mais parfois, il n'y a pas d'autre alternative que de plonger dans un débogueur, soit pour voir la trace de la pile d'un core dump (très utile dans un rapport de bug), soit pour essayer de comprendre ce qui s'est mal passé avant que le core dump ne se produise, ou comment nous avons fini par obtenir des résultats erronés ou inattendus.

Explorer Perl

./Configure -d -DDEBUGGING

Il activera également le symbole de compilation "DEBUGGING" qui active tout le code de débogage interne de Perl. Il y a un tas de choses que vous pouvez déboguer avec cela : perlrun les liste toutes, et la meilleure façon de les connaître est de jouer avec elles. Les options les plus utiles sont probablement

l  Traitement de la pile de contexte (boucle)
s  Instantanés de la pile (avec v, affiche toutes les piles)
t  Trace d'exécution
o  Résolution de méthodes et de surcharge
c  Conversions chaîne/numérique

Par exemple

    =>  UNDEF
(-e:1)      const(IV(1))
    =>  UNDEF  IV(1)

    Indique au débogueur que nous voulons arrêter l'exécution lorsque nous atteignons soit la fonction nommée (mais voir "Internal Functions" dans perlguts !), soit la ligne donnée dans le fichier source nommé.

  • step

    Parcourt le programme ligne par ligne.

  • next

    Parcourt le programme ligne par ligne, sans descendre dans les fonctions.

  • continue

    Exécute jusqu'au prochain point d'arrêt.

  • finish

    Exécute jusqu'à la fin de la fonction actuelle, puis s'arrête à nouveau.

  • 'enter'

    Appuyer simplement sur Entrée répétera la dernière opération effectuée - c'est une bénédiction lorsqu'on parcourt des kilomètres de code source.

  • ptype

    Affiche la définition C de l'argument donné.

    (gdb) ptype PL_op
type = struct op {
    OP *op_next;
    OP *op_sibparent;
    OP *(*op_ppaddr)(void);
    PADOFFSET op_targ;
    unsigned int op_type : 9;
    unsigned int op_opt : 1;
    unsigned int op_slabbed : 1;
    unsigned int op_savefree : 1;
    unsigned int op_static : 1;
    unsigned int op_folded : 1;
    unsigned int op_spare : 2;

    U8 op_private;
} *
  • print

    Exécute le code C donné et imprime ses résultats. ATTENTION : Perl utilise beaucoup de macros, et gdb ne prend pas nécessairement en charge les macros (voir plus loin "gdb macro support"). Vous devrez les substituer vous-même, ou invoquer cpp sur les fichiers de code source (voir "The .i Targets"). Ainsi, par exemple, vous ne pouvez pas dire

    print SvPV_nolen(sv)

    mais vous devez dire

    print Perl_sv_2pv_nolen(sv)

Il peut être utile d'avoir un "dictionnaire de macros", que vous pouvez produire en tapant "cpp -dM perl.c | sort". Même dans ce cas, cpp n'appliquera pas récursivement ces macros pour vous.

Support des macros gdb

Les versions récentes de gdb ont un support assez bon des macros, mais pour l'utiliser, vous devrez compiler Perl avec les définitions de macros incluses dans les informations de débogage. En utilisant gcc version 3.1, cela signifie configurer avec "-Doptimize=-g3". D'autres compilateurs pourraient utiliser un commutateur différent (s'ils prennent en charge les macros de débogage du tout).

Exportation des structures de données Perl

Une façon de contourner cet enfer de macros est d'utiliser les fonctions d'exportation dans dump.c ; elles fonctionnent un peu comme un Devel::Peek interne, mais elles couvrent également les OPs et d'autres structures auxquelles vous ne pouvez pas accéder depuis Perl. Prenons un exemple. Nous utiliserons le code "$x = $y + $z" que nous avons utilisé précédemment, mais nous lui donnerons un peu de contexte : "$y = "6XXXX"; $z = 2.3;". Où est un bon endroit pour s'arrêter et examiner ?

Que diriez-vous de "pp_add", la fonction que nous avons examinée précédemment pour implémenter l'opérateur "+" :

(gdb) break Perl_pp_add

Notez que nous utilisons "Perl_pp_add" et pas "pp_add" - voir "Internal Functions" dans perlguts. Avec le point d'arrêt en place, nous pouvons exécuter notre programme :

(gdb) run -e '$y = "6XXXX"; $z = 2.3; $x = $y + $z'

Beaucoup d'informations passeront pendant que gdb lit les fichiers source et les bibliothèques pertinents, puis :

Breakpoint 1, Perl_pp_add () at pp_hot.c:309
1396    dSP; dATARGET; bool useleft; SV *svl, *svr;
(gdb) step

(gdb)

Nous avons examiné ce bout de code précédemment, et nous avons dit que "dPOPTOPnnrl_ul" arrange pour que deux caractères "NV" soient placés dans "left" et "right" - élargissons-le légèrement :

#define dPOPTOPnnrl_ul  NV right = POPn; \
                        SV *leftsv = TOPs; \
                        NV left = USE_LEFT(leftsv) ? SvNV(leftsv) : 0.0

"POPn" prend le SV du sommet de la pile et obtient son NV soit directement (si "SvNOK" est défini) soit en appelant la fonction "sv_2nv". "TOPs" prend le prochain SV du sommet de la pile - oui, "POPn" utilise "TOPs" - mais ne le retire pas. Nous utilisons ensuite "SvNV" pour obtenir le NV de "leftsv" de la même manière qu'auparavant - oui, "POPn" utilise "SvNV".

Comme nous n'avons pas de NV pour $y, nous devons utiliser "sv_2nv" pour le convertir. Si nous continuons l'exécution pas à pas, nous nous retrouverons là :

(gdb) step

1669        if (!sv)

0x462669 in Perl_pp_add () at pp_hot.c:311
311           dPOPTOPnnrl_ul;

Nous pouvons également examiner cet op : l'op actuel est toujours stocké dans "PL_op", et nous pouvons l'examiner avec "Perl_op_dump". Cela nous donnera un résultat similaire au module CPAN B::Debug.

Utilisation de gdb pour examiner des parties spécifiques d'un programme

Avec l'exemple ci-dessus, vous saviez chercher "Perl_pp_add", mais s'il y avait plusieurs appels à celui-ci partout, ou si vous ne saviez pas quel op vous cherchiez ?

Une façon de faire cela est d'injecter un appel rare quelque part près de ce que vous cherchez. Par exemple, vous pourriez ajouter "study" avant votre méthode :

study;

Et dans gdb, faire :

(gdb) break Perl_pp_study

Puis continuer pas à pas jusqu'à ce que vous trouviez ce que vous cherchez. Cela fonctionne bien dans une boucle si vous ne voulez vous arrêter qu'à certaines itérations :

for my $i (1..100) {
    study if $i == 50;
}

Utilisation de gdb pour examiner ce que font le parseur/lexeur

Si vous voulez voir ce que fait perl lors de l'analyse syntaxique/lexicale de votre code, vous pouvez utiliser "BEGIN {}" :

print "Avant\n";
BEGIN { study; }
print "Après\n";

Et dans gdb :

(gdb) break Perl_pp_study

Si vous voulez voir ce que le parseur/lexeur fait à l'intérieur des blocs "if" et autres, vous devez être un peu plus astucieux :

if ($x && $y && do { BEGIN { study } 1 } && $z) { ... }

ANALYSE STATIQUE DU CODE SOURCE

Divers outils existent pour analyser le code source C **statiquement**, par opposition à **dynamiquement**, c'est-à-dire sans exécuter le code. Il est possible de détecter les fuites de ressources, les comportements indéfinis, les incompatibilités de types, les problèmes de portabilité, les chemins de code qui causeraient des accès mémoire illégaux, et d'autres problèmes similaires en analysant simplement le code C et en examinant le graphe résultant, ce qu'il dit sur l'exécution et les flux de données. En fait, c'est ainsi que les compilateurs C savent donner des avertissements sur du code douteux.

lint

Le bon vieil inspecteur de qualité du code C, "lint", est disponible sur plusieurs plateformes, mais veuillez noter qu'il existe plusieurs implémentations différentes par différents fournisseurs, ce qui signifie que les options ne sont pas identiques d'une plateforme à l'autre.

Il y a une cible "lint" dans le Makefile, mais vous devrez peut-être ajuster les options (voir ci-dessus).

Coverity

Coverity (https://www.coverity.com/) est un produit similaire à lint et, comme banc d'essai pour leur produit, ils vérifient périodiquement plusieurs projets open source, et ils accordent des comptes aux développeurs open source pour accéder aux bases de données de défauts.

Il existe une configuration Coverity pour le projet perl5 : https://scan.coverity.com/projects/perl5

HP-UX cadvise (Code Advisor)

HP a un produit d'analyse statique C/C++ pour HP-UX appelé Code Advisor. (Lien non donné ici car l'URL est horriblement longue et semble horriblement instable ; utilisez votre moteur de recherche préféré pour le trouver.) L'utilisation de la recette "cadvise_cc" avec "Configure ... -Dcc=./cadvise_cc" (voir le guide de l'utilisateur de cadvise) est recommandée ; tout comme l'utilisation de "+wall".

cpd (détecteur de copier-coller)

L'outil cpd détecte le code copié-collé. Si une instance du code copié-collé change, tous les autres endroits devraient probablement être modifiés aussi. Par conséquent, un tel code devrait probablement être transformé en sous-routine ou en macro.

cpd (https://docs.pmd-code.org/latest/pmd_userdocs_cpd.html) fait partie du projet pmd (https://pmd.github.io/). pmd a été écrit à l'origine pour l'analyse statique du code Java, mais plus tard, la partie cpd a été étendue pour analyser également le C et le C++.

Téléchargez le fichier pmd-bin-X.Y.zip () depuis le site SourceForge, extrayez le fichier pmd-X.Y.jar, puis exécutez-le sur le code source ainsi :

java -cp pmd-X.Y.jar net.sourceforge.pmd.cpd.CPD \
 --minimum-tokens 100 --files /some/where/src --language c > cpd.txt

Vous pourriez rencontrer des limites de mémoire, auquel cas vous devriez utiliser l'option -Xmx :

java -Xmx512M ...

avertissements gcc

Bien que l'on puisse beaucoup écrire sur l'incohérence et les problèmes de couverture des avertissements gcc (comme "-Wall" ne signifiant pas "tous les avertissements", ou certains problèmes de portabilité courants n'étant pas couverts par "-Wall", ou "-ansi" et "-pedantic" étant tous deux une collection mal définie d'avertissements, etc.), gcc reste un outil utile pour garder notre code propre.

L'option "-Wall" est activée par défaut.

Il serait souhaitable que "-pedantic" soit toujours activé, mais malheureusement, il n'est pas sûr sur toutes les plateformes - par exemple, il entre en conflit fatal avec les en-têtes système (Solaris en étant un exemple primordial). Si Configure est exécuté avec "-Dgccansipedantic", le frontend "cflags" sélectionne "-pedantic" pour les plateformes où il est connu pour être sûr.

Les options supplémentaires suivantes sont ajoutées :

  • "-Wendif-labels"
  • "-Wextra"
  • "-Wc++-compat"
  • "-Wwrite-strings"
  • "-Werror=pointer-arith"
  • "-Werror=vla"

Les options suivantes seraient souhaitables mais nécessiteraient d'abord leur propre Augean stablemaster :

  • "-Wshadow"
  • "-Wstrict-prototypes"

L'option "-Wtraditional" est un autre exemple de la tendance agaçante de gcc à regrouper de nombreux avertissements sous un seul commutateur (il serait impossible de le déployer en pratique car il se plaindrait beaucoup) mais elle contient certains avertissements qui seraient bénéfiques d'avoir disponibles séparément, tels que l'avertissement concernant les constantes de chaîne à l'intérieur des macros contenant les arguments de la macro : cela se comportait différemment avant l'ANSI de ce qu'il fait en ANSI, et certains compilateurs C sont encore en transition, AIX en étant un exemple.

Avertissements d'autres compilateurs C

D'autres compilateurs C (oui, il **existe** d'autres compilateurs C que gcc) ont souvent leurs modes "strict ANSI" ou "strict ANSI avec quelques extensions de portabilité" activés, comme par exemple le Sun Workshop qui a son mode "-Xa" activé (bien qu'implicitement), ou DEC (aujourd'hui HP...) qui a son mode "-std1" activé.

DÉBOGAGEURS DE MÉMOIRE

**NOTE 1** : L'exécution sous d'anciens débogueurs de mémoire tels que Purify, valgrind ou Third Degree ralentit considérablement l'exécution : les secondes deviennent des minutes, les minutes deviennent des heures. Par exemple, à partir de Perl 5.8.1, le test ext/Encode/t/Unicode.t prend extraordinairement longtemps à s'exécuter sous par exemple Purify, Third Degree et valgrind. Sous valgrind, cela prend plus de six heures, même sur un ordinateur performant. Ce test doit faire quelque chose qui est assez peu vriend envers les débogueurs de mémoire. Si vous n'avez pas envie d'attendre, vous pouvez simplement tuer le processus perl. Valgrind ralentit l'exécution d'un facteur 10 environ, AddressSanitizer d'un facteur 2.

**NOTE 2** : Pour minimiser le nombre de fausses alarmes de fuite de mémoire (voir "PERL_DESTRUCT_LEVEL" pour plus d'informations), vous devez définir la variable d'environnement "PERL_DESTRUCT_LEVEL"

" pour 2. Par exemple, comme ceci :

env PERL_DESTRUCT_LEVEL=2 valgrind ./perl -Ilib ...

NOTE 3 : Il y a des fuites de mémoire connues lorsqu'il y a des erreurs de compilation dans "eval" ou "require" ; voir "S_doeval" dans la pile d'appels est un bon indicateur de ces problèmes. Corriger ces fuites n'est malheureusement pas trivial, mais elles devront être corrigées un jour.

NOTE 4 : DynaLoader ne fera pas un nettoyage complet après lui-même à moins que Perl ne soit compilé avec l'option Configure "-Accflags=-DDL_UNLOAD_ALL_AT_EXIT".

valgrind

L'outil valgrind peut être utilisé pour identifier les fuites de mémoire et les accès illégaux à la mémoire du tas. Depuis la version 3.3.0, Valgrind ne prend en charge que Linux sur x86, x86-64 et PowerPC, ainsi que Darwin (OS X) sur x86 et x86-64. La cible spéciale "test.valgrind" peut être utilisée pour exécuter les tests sous valgrind. Les erreurs trouvées et les fuites de mémoire sont enregistrées dans des fichiers nommés testfile.valgrind et, par défaut, la sortie est affichée en ligne.

Exemple d'utilisation :

make test.valgrind

Comme valgrind ajoute une surcharge significative, les tests prendront beaucoup plus de temps à s'exécuter. Les tests valgrind prennent en charge l'exécution en parallèle pour aider à cela :

TEST_JOBS=9 make test.valgrind

Notez que les deux invocations ci-dessus seront très verbeuses car la mémoire accessible et la vérification des fuites sont activées par défaut. Si vous souhaitez uniquement voir les erreurs pures, essayez :

VG_OPTS='-q --leak-check=no --show-reachable=no' TEST_JOBS=9 \
    make test.valgrind

Valgrind fournit également un outil cachegrind, invoqué sur perl comme suit :

VG_OPTS=--tool=cachegrind make test.valgrind

Étant donné que les bibliothèques système (notamment glibc) déclenchent également des erreurs, valgrind permet de supprimer ces erreurs à l'aide de fichiers de suppression. Le fichier de suppression par défaut qui accompagne valgrind en attrape déjà un grand nombre. Certaines suppressions supplémentaires sont définies dans t/perl.supp.

Pour obtenir valgrind et plus d'informations, voir https://valgrind.org/.

AddressSanitizer

AddressSanitizer ("ASan") se compose d'un module d'instrumentation de compilateur et d'une bibliothèque d'exécution "malloc". ASan est disponible pour une variété d'architectures, de systèmes d'exploitation et de compilateurs (voir le lien du projet ci-dessous). Il vérifie l'utilisation non sécurisée de la mémoire, telle que l'utilisation après libération et les dépassements de tampon, et est assez rapide pour que vous puissiez facilement compiler votre perl de débogage ou optimisé avec lui. Les versions modernes d'ASan vérifient les fuites de mémoire par défaut sur la plupart des plateformes, sinon (par exemple, x86_64 OS X), cette fonctionnalité peut être activée via "ASAN_OPTIONS=detect_leaks=1".

Pour compiler perl avec AddressSanitizer, votre invocation Configure devrait ressembler à ceci :

sh Configure -des -Dcc=clang \
   -Accflags=-fsanitize=address -Aldflags=-fsanitize=address \
   -Alddlflags=-shared\ -fsanitize=address \
   -fsanitize-blacklist=`pwd`/asan_ignore

où ces arguments signifient :

  • -Dcc=clang

    Ceci doit être remplacé par le chemin complet vers votre exécutable clang s'il n'est pas dans votre chemin.

  • -Accflags=-fsanitize=address

    Compiler les sources de perl et des extensions avec AddressSanitizer.

  • -Aldflags=-fsanitize=address

    Lier l'exécutable perl avec AddressSanitizer.

  • -Alddlflags=-shared\ -fsanitize=address

    Lier les extensions dynamiques avec AddressSanitizer. Vous devez spécifier manuellement "-shared" car l'utilisation de "-Alddlflags=-shared" empêchera Configure de définir une valeur par défaut pour "lddlflags", qui contient généralement "-shared" (au moins sous Linux).

  • -fsanitize-blacklist=`pwd`/asan_ignore

    AddressSanitizer ignorera les fonctions listées dans le fichier "asan_ignore". (Ce fichier devrait contenir une brève explication de la raison pour laquelle chaque fonction est listée.)

Voir aussi https://github.com/google/sanitizers/wiki/AddressSanitizer.

Dr Memory

Dr. Memory est un outil similaire à valgrind qui est utilisable sous Windows et Linux.

Il prend en charge la vérification du tas comme "memcheck" de valgrind. Il existe également d'autres outils inclus.

Voir https://drmemory.org/.

PROFILAGE

Selon votre plateforme, il existe diverses façons de profiler Perl.

Il existe deux techniques couramment utilisées pour profiler les exécutables : l'échantillonnage temporel statistique et le comptage de blocs de base.

La première méthode prend périodiquement des échantillons du compteur de programme du CPU, et comme le compteur de programme peut être corrélé avec le code généré pour les fonctions, nous obtenons une vue statistique des fonctions dans lesquelles le programme passe son temps. Les mises en garde sont que les fonctions très petites/rapides ont une probabilité plus faible d'apparaître dans le profil, et que l'interruption périodique du programme (cela est généralement fait assez fréquemment, à l'échelle de la milliseconde) impose une surcharge supplémentaire qui peut fausser les résultats. Le premier problème peut être atténué en exécutant le code plus longtemps (en général, c'est une bonne idée pour le profilage), le second problème est généralement contrôlé par les outils de profilage eux-mêmes.

La seconde méthode divise le code généré en blocs de base. Les blocs de base sont des sections de code qui ne sont entrées qu'au début et ne sont sorties qu'à la fin. Par exemple, un saut conditionnel commence un bloc de base. Le profilage de blocs de base fonctionne généralement en instrumentant le code en ajoutant du code de comptabilité entrer bloc de base #nnnn au code généré. Pendant l'exécution du code, les compteurs de blocs de base sont alors mis à jour de manière appropriée. La mise en garde est que le code supplémentaire ajouté peut fausser les résultats : là encore, les outils de profilage essaient généralement de supprimer leurs propres effets des résultats.

Profilage avec Gprof

gprof est un outil de profilage disponible sur de nombreuses plateformes Unix qui utilise l'échantillonnage temporel statistique. Vous pouvez créer une version profilée de perl en compilant avec gcc et l'indicateur "-pg". Modifiez config.sh ou réexécutez Configure. L'exécution de la version profilée de Perl créera un fichier de sortie appelé gmon.out qui contient les données de profilage collectées pendant l'exécution.

Indice rapide :

$ sh Configure -des -Dusedevel -Accflags='-pg' \
    -Aldflags='-pg' -Alddlflags='-pg -shared' \
    && make perl
$ ./perl ... # crée gmon.out dans le répertoire courant
$ gprof ./perl > out
$ less out

(vous devrez probablement ajouter "-shared" à la ligne <-Alddlflags> jusqu'à ce que RT #118199 soit résolu)

L'outil gprof peut ensuite afficher les données collectées de diverses manières. Généralement, gprof comprend les options suivantes :

  • -a

    Supprimer les fonctions définies statiquement du profil.

  • -b

    Supprimer les descriptions détaillées du profil.

  • -e routine

    Exclure la routine donnée et ses descendants du profil.

  • -f routine

    Afficher uniquement la routine donnée et ses descendants dans le profil.

  • -s

    Générer un fichier récapitulatif appelé gmon.sum qui peut ensuite être donné à des exécutions gprof ultérieures pour accumuler des données sur plusieurs exécutions.

  • -z

    Afficher les routines qui n'ont pas été utilisées.

Pour une explication plus détaillée des commandes disponibles et des formats de sortie, consultez votre propre documentation locale de gprof.

Profilage avec GCC gcov

Le profilage de blocs de base est officiellement disponible dans gcc 3.0 et versions ultérieures. Vous pouvez créer une version profilée de perl en compilant avec gcc et les indicateurs "-fprofile-arcs -ftest-coverage". Modifiez config.sh ou réexécutez Configure.

Indice rapide :

$ sh Configure -des -Dusedevel -Doptimize='-g' \
    -Accflags='-fprofile-arcs -ftest-coverage' \
    -Aldflags='-fprofile-arcs -ftest-coverage' \
    -Alddlflags='-fprofile-arcs -ftest-coverage -shared' \
    && make perl
$ rm -f regexec.c.gcov regexec.gcda
$ ./perl ...
$ gcov regexec.c
$ less regexec.c.gcov

(vous devrez probablement ajouter "-shared" à la ligne <-Alddlflags> jusqu'à ce que RT #118199 soit résolu)

L'exécution de la version profilée de Perl générera une sortie de profil. Pour chaque fichier source, un fichier .gcda correspondant sera créé.

Pour afficher les résultats, vous utilisez l'utilitaire gcov (qui devrait être installé si vous avez gcc 3.0 ou plus récent installé). gcov est exécuté sur des fichiers de code source, comme ceci :

gcov sv.c

ce qui créera sv.c.gcov. Les fichiers .gcov contiennent le code source annoté avec des fréquences d'exécution relatives indiquées par des marqueurs "#". Si vous souhaitez générer des fichiers .gcov pour tous les fichiers objet profilés, vous pouvez exécuter quelque chose comme ceci :

for file in `find . -name \*.gcno`
do sh -c "cd `dirname $file` && gcov `basename $file .gcno`"
done

Les options utiles de gcov incluent "-b" qui résumera la couverture des blocs de base, des branchements et des appels de fonction, et "-c" qui utilisera les décomptes réels au lieu des fréquences relatives. Pour plus d'informations sur l'utilisation de gcov et le profilage de blocs de base avec gcc, consultez le dernier manuel de GNU CC. À partir de gcc 4.8, il se trouve à https://gcc.gnu.org/onlinedocs/gcc/Gcov-Intro.html#Gcov-Intro.

Profilage avec callgrind

callgrind est un outil valgrind pour le profilage du code source. Associé à kcachegrind (une interface utilisateur basée sur Qt), il vous donne un aperçu des endroits où le code prend du temps, ainsi que la possibilité d'examiner les appelants, l'arbre des appels

s, et plus. L'un de ses avantages est que vous pouvez l'utiliser sur des modules perl et XS qui n'ont pas été compilés avec des symboles de débogage.

Si perl est compilé avec des symboles de débogage ("-g"), vous pouvez afficher le code source annoté et naviguer, un peu comme la sortie HTML de Devel::NYTProf.

Pour une utilisation de base :

valgrind --tool=callgrind ./perl ...

Par défaut, il écrira la sortie dans callgrind.out.PID, mais vous pouvez la modifier avec "--callgrind-out-file=..."

Pour afficher les données, faites :

kcachegrind callgrind.out.PID

Si vous préférez afficher les données dans un terminal, vous pouvez utiliser callgrind_annotate. Dans sa forme de base :

callgrind_annotate callgrind.out.PID | less

Quelques options utiles :

  • --threshold

    Pourcentage de décomptes (de l'événement de tri principal) qui nous intéressent. La valeur par défaut est 99%. 100% peut afficher des éléments qui semblent manquants.

  • --auto

    Annoter tous les fichiers source contenant des fonctions qui ont contribué à atteindre le seuil de décompte de l'événement.

Profilage « profiler » (Cygwin)

Cygwin permet le profilage "gprof" et les tests de couverture "gcov", mais cela ne profile que l'exécutable principal.

Vous pouvez utiliser l'outil "profiler" pour effectuer un profilage basé sur des échantillons. Il ne nécessite aucune préparation spéciale des exécutables au-delà des symboles de débogage.

Cela produit des données d'échantillonnage qui peuvent être traitées avec "gprof".

Il y a une documentation limitée https://www.cygwin.com/cygwin-ug-net/profiler.html sur le site Web de Cygwin.

Profilage Visual Studio

Vous pouvez utiliser le profiler Visual Studio pour profiler perl si vous avez compilé perl avec MSVC, même si nous compilons perl en ligne de commande. Vous devrez compiler perl avec "CFG=Debug" ou "CFG=DebugSymbols".

Le profiler Visual Studio est un profiler d'échantillonnage.

Consultez la documentation de Visual Studio https://github.com/MicrosoftDocs/visualstudio-docs/blob/main/docs/profiling/beginners-guide-to-performance-profiling.md pour commencer.

ASTUCES DIVERSES

PERL_DESTRUCT_LEVEL

Si vous souhaitez exécuter vous-même certains des tests manuellement en utilisant, par exemple, valgrind, veuillez noter que par défaut, perl ne nettoie **pas** explicitement toute la mémoire qu'il a allouée (telles que les arènes de mémoire globales) mais laisse plutôt le exit() du programme entier « s'occuper » de ces allocations, également connu sous le nom de « destruction globale des objets ».

Il existe un moyen de dire à perl d'effectuer un nettoyage complet : définissez la variable d'environnement "PERL_DESTRUCT_LEVEL" à une valeur non nulle. Le wrapper t/TEST la définit à 2, et c'est ce que vous devez faire aussi, si vous ne voulez pas voir les « fuites globales » : Par exemple, pour exécuter sous valgrind

env PERL_DESTRUCT_LEVEL=2 valgrind ./perl -Ilib t/foo/bar.t

(Note : le module mod_perl Apache utilise cette variable d'environnement à ses propres fins et étend sa sémantique. Référez-vous à la documentation mod_perl https://perl.apache.org/docs/ pour plus d'informations. De plus, les threads lancés effectuent l'équivalent de la définition de cette variable à la valeur 1.)

Si, à la fin d'une exécution, vous obtenez le message N scalaires ont fui, vous pouvez recompiler avec "-DDEBUG_LEAKING_SCALARS" ("Configure -Accflags=-DDEBUG_LEAKING_SCALARS"), ce qui fera afficher les adresses de tous ces SV qui ont fui ainsi que des détails sur l'endroit où chaque SV a été alloué à l'origine. Ces informations sont également affichées par Devel::Peek. Notez que les détails supplémentaires enregistrés avec chaque SV augmentent l'utilisation de la mémoire, il ne faut donc pas l'utiliser dans les environnements de production. Cela convertit également new_SV() d'une macro en une vraie fonction, vous pouvez donc utiliser votre débogueur préféré pour découvrir où ces SV récalcitrants ont été alloués.

Si vous constatez des fuites de mémoire pendant l'exécution, mais que ni valgrind ni "-DDEBUG_LEAKING_SCALARS" ne trouvent quoi que ce soit, vous fuyez probablement des SV qui sont toujours accessibles et qui seront correctement nettoyés lors de la destruction de l'interpréteur. Dans de tels cas, l'utilisation du commutateur "-Dm" peut vous indiquer la source de la fuite. Si l'exécutable a été compilé avec "-DDEBUG_LEAKING_SCALARS", "-Dm" affichera les allocations de SV en plus des allocations de mémoire. Chaque allocation de SV a un numéro de série distinct qui sera écrit lors de la création et de la destruction du SV. Donc, si vous exécutez le code qui fuit dans une boucle, vous devez rechercher les SV qui sont créés mais jamais détruits entre chaque cycle. Si un tel SV est trouvé, définissez un point d'arrêt conditionnel dans new_SV() et faites-le s'arrêter uniquement lorsque "PL_sv_serial" est égal au numéro de série du SV qui fuit. Vous attraperez alors l'interpréteur dans l'état exact où le SV qui fuit est alloué, ce qui est suffisant dans de nombreux cas pour trouver la source de la fuite.

Comme "-Dm" utilise la couche PerlIO pour la sortie, il allouera lui-même un grand nombre de SV, qui sont cachés pour éviter la récursion. Vous pouvez contourner la couche PerlIO si vous utilisez plutôt la journalisation des SV fournie par "-DPERL_MEM_LOG".

Repérage des SV qui ont fui : sv_mark_arenas() et sv_sweep_arenas()

Ces fonctions n'existent que dans les compilations "DEBUGGING". La première marque tous les SV actifs qui peuvent être trouvés dans les arènes de SV avec le drapeau "SVf_BREAK". La seconde liste tous les SV qui n'ont pas le drapeau défini, et réinitialise le drapeau sur les autres. Elles sont destinées à identifier les SV qui sont créés mais pas libérés entre deux points du code. Elles peuvent être utilisées soit en ajoutant temporairement des appels dans les endroits pertinents du code, soit en les appelant directement à partir d'un débogueur.

Par exemple, supposons que le code suivant ait été trouvé comme fuyant :

while (1) { eval '\(1..3)' }

Une session gdb sur un perl threadé pourrait ressembler à ceci :

$ gdb ./perl
(gdb) break Perl_pp_entereval
(gdb) run -e'while (1) { eval q{\(1..3)} }'
...
Breakpoint 1, Perl_pp_entereval ....
(gdb) call Perl_sv_mark_arenas(my_perl)
(gdb) continue
...
Breakpoint 1, Perl_pp_entereval ....`
(gdb) call Perl_sv_sweep_arenas(my_perl)
Unmarked SV: 0xaf23a8: AV()
Unmarked SV: 0xaf2408: IV(1)
Unmarked SV: 0xaf2468: IV(2)
Unmarked SV: 0xaf24c8: IV(3)
Unmarked SV: 0xace6c8: PV("AV()"\0)
Unmarked SV: 0xace848: PV("IV(1)"\0)
(gdb)

Ici, au début du premier appel à pp_entereval(), tous les SV existants sont marqués. Ensuite, au début du second appel, nous listons tous les SV qui ont été créés entre-temps mais pas encore libérés. Il est rapidement clair qu'un tableau et ses trois éléments ne sont probablement pas libérés, peut-être en raison d'un bug lors du repliement des constantes. Les deux derniers SV ne sont que des temporaires créés lors de la sortie de débogage et peuvent être ignorés.

Cette astuce repose sur le fait que le drapeau "SVf_BREAK" n'est pas utilisé autrement. Ce drapeau est généralement utilisé uniquement lors de la destruction globale, mais aussi parfois pour une opération de marquage et de balayage lors de la recherche d'éléments communs des deux côtés d'une affectation de liste. La présence du drapeau peut également modifier le comportement de certaines actions spécifiques du noyau, comme choisir de copier ou d'utiliser le COW (copy-on-write) pour un SV de chaîne. L'activer peut donc occasionnellement modifier légèrement le comportement du code.

PERL_MEM_LOG

Si compilé avec "-DPERL_MEM_LOG" ("-Accflags=-DPERL_MEM_LOG"), les allocations de mémoire et de SV passent par des fonctions de journalisation, ce qui est pratique pour définir des points d'arrêt.

Sauf si "-DPERL_MEM_LOG_NOIMPL" ("-Accflags=-DPERL_MEM_LOG_NOIMPL") est également compilé, les fonctions de journalisation lisent $ENV{PERL_MEM_LOG} pour déterminer si elles doivent journaliser l'événement, et si oui, comment :

$ENV{PERL_MEM_LOG} =~ /m/           Journaliser toutes les opérations mémoire
$ENV{PERL_MEM_LOG} =~ /s/           Journaliser toutes les opérations SV
$ENV{PERL_MEM_LOG} =~ /c/           Journaliser en plus la trace C pour
                                    les événements new_SV
$ENV{PERL_MEM_LOG} =~ /t/           Inclure un horodatage dans le journal
$ENV{PERL_MEM_LOG} =~ /^(\d+)/      Écrire sur le descripteur de fichier donné (par défaut 2)

La journalisation de la mémoire est quelque peu similaire à "-Dm" mais est indépendante de "-DDEBUGGING", et à un niveau supérieur ; toutes les utilisations de Newx(), Renew(), et Safefree() sont journalisées avec le fichier source et le numéro de ligne de l'appelant (et le nom de la fonction C, si supporté par le compilateur C). En revanche, "-Dm" est directement au point de malloc(). La journalisation des SV est similaire.

Étant donné que la journalisation n'utilise pas PerlIO, toutes les allocations de SV sont journalisées et aucune allocation de SV supplémentaire n'est introduite en activant la journalisation. Si compilé avec "-DDEBUG_LEAKING_SCALARS", le numéro de série de chaque allocation de SV est également journalisé.

L'option "c" utilise la facilité "Perl_c_backtrace", et nécessite donc en plus le drapeau de compilation Configure "-Dusecbacktrace" pour y accéder.

DDD sur gdb

Ceux qui déboguent Perl avec le frontend DDD sur gdb pourraient trouver ce qui suit utile :

Vous pouvez étendre le menu des raccourcis de conversion de données, de sorte que, par exemple, vous puissiez afficher la valeur IV d'un SV d'un simple clic, sans avoir à taper quoi que ce soit. Pour ce faire, modifiez simplement le fichier ~/.ddd/init et ajoutez après :

! Display shortcuts.
Ddd*gdbDisplayShortcuts: \
/t ()   // Convert to Bin\n\
/d ()   // Convert to Dec\n\
/x ()   // Convert to Hex\n\
/o ()   // Convert to Oct(\n\

les deux lignes suivantes :

((XPV*) (())->sv_any )->xpv_pv  // 2pvx\n\
((XPVIV*) (())->sv_any )->xiv_iv // 2ivx

ainsi, vous pouvez maintenant effectuer des recherches ivx et pvx, ou vous pouvez y insérer la conversion « sv_peek » :

Perl_sv_peek(my_perl, (SV*)()) // sv_peek

(Le my_perl est pour les compilations multi-thread.) N'oubliez pas que chaque ligne, sauf la dernière, doit se terminer par \n\

Alternativement, modifiez le fichier init de manière interactive via : bouton de la souris 3e -> Nouveau affichage -> Modifier le menu

Note : vous pouvez définir jusqu'à 20 raccourcis de conversion dans la section gdb.

C backtrace

Sur certaines plateformes, Perl prend en charge la récupération de la traçabilité de pile de niveau C (similaire à ce que font les débogueurs symboliques comme gdb).

La traçabilité de pile retourne la trace de la pile des cadres d'appel C, avec les noms symboliques (noms de fonctions), les noms d'objets (comme « perl »), et si possible, également les emplacements du code source (fichier:ligne).

Les plateformes prises en charge sont Linux et OS X (certains *BSD pourraient fonctionner au moins partiellement, mais ils n'ont pas encore été testés).

Cette fonctionnalité n'a pas été testée avec plusieurs threads, mais elle n'affichera que la traçabilité de pile du thread qui effectue la traçabilité.

La fonctionnalité doit être activée avec "Configure -Dusecbacktrace".

Le "-Dusecbacktrace" active également la conservation des informations de débogage lors de la compilation/édition des liens (souvent : "-g"). De nombreux compilateurs/éditeurs de liens prennent en charge à la fois l'optimisation et la conservation des informations de débogage. Les informations de débogage sont nécessaires pour les noms symboliques et les emplacements des sources.

Les fonctions statiques pourraient ne pas être visibles pour la traçabilité de pile.

Les emplacements du code source, même s'ils sont disponibles, peuvent souvent manquer ou être trompeurs si le compilateur a, par exemple, intégré du code. L'optimiseur peut rendre la mise en correspondance du code source et du code objet assez difficile.

Linux
Vous devez avoir la bibliothèque BFD (-lbfd) installée, sinon "perl" échouera à lier. BFD est généralement distribué dans le cadre des binutils GNU.

Résumé : "Configure ... -Dusecbacktrace" et vous avez besoin de "-lbfd".

OS X
Les emplacements du code source sont pris en charge uniquement si vous avez installé les Outils de Développement. (BFD n'est pas nécessaire.)

Résumé : "Configure ... -Dusecbacktrace" et l'installation des Outils de Développement serait une bonne chose.

Facultativement, pour essayer la fonctionnalité, vous pourriez vouloir activer le vidage automatique de la traçabilité de pile juste avant qu'un message d'avertissement ou de croak (die) ne soit émis, en ajoutant "-Accflags=-DUSE_C_BACKTRACE_ON_ERROR" pour Configure.

Sauf si la fonctionnalité supplémentaire ci-dessus est activée, rien concernant la fonctionnalité de traçabilité de pile n'est visible, à part au niveau Perl/XS.

De plus, même si vous avez activé cette fonctionnalité pour être compilée, vous devez l'activer à l'exécution avec une variable d'environnement : "PERL_C_BACKTRACE_ON_ERROR=10". Elle doit être un entier supérieur à zéro, indiquant le nombre d'images souhaité.

La récupération de la traçabilité de pile depuis le niveau Perl (en utilisant par exemple une extension XS) serait beaucoup moins excitante que ce que l'on pourrait espérer : normalement, vous verriez "runops", "entersub", et pas grand-chose d'autre. Cette API est destinée à être appelée depuis l'intérieur de l'implémentation de Perl, pas depuis l'exécution au niveau Perl.

L'API C pour la traçabilité de pile est la suivante :

get_c_backtrace
free_c_backtrace
get_c_backtrace_dump
dump_c_backtrace

Poison

Si vous voyez dans un débogueur une zone mémoire mystérieusement remplie de 0xABABABAB ou 0xEFEFEFEF, vous pourriez voir l'effet des macros Poison(), voir perlclib.

Read-only optrees

Sous ithreads, l'arbre d'options (optree) est en lecture seule. Si vous souhaitez appliquer cela, pour vérifier les écritures provenant de code défectueux, compilez avec "-Accflags=-DPERL_DEBUG_READONLY_OPS" pour activer le code qui alloue la mémoire des ops via "mmap", et la définit en lecture seule lorsqu'elle est attachée à une sous-routine. Toute écriture sur une op entraînera un "SIGBUS" et un arrêt.

Ce code est destiné au développement uniquement, et peut ne pas être portable même sur toutes les variantes Unix. De plus, c'est une solution à 80%, en ce sens qu'elle n'est pas capable de rendre toutes les ops en lecture seule. Plus spécifiquement, elle ne s'applique pas aux blocs d'ops appartenant aux blocs "BEGIN".

Cependant, en tant que solution à 80%, elle est toujours efficace, car elle a détecté des bogues par le passé.

When is a bool not a bool?

Il n'y avait pas nécessairement de type "bool" standard sur les compilateurs avant C99, et donc certaines solutions de contournement ont été créées. Les macros "TRUE" et "FALSE" sont toujours disponibles comme alternatives à "true" et "false". Et la macro "cBOOL" a été créée pour caster correctement vers une valeur vraie/fausse dans toutes les circonstances, mais elle ne devrait plus être nécessaire. L'utilisation de "(bool)" expr devrait maintenant toujours fonctionner.

Il n'est pas prévu de supprimer "TRUE", "FALSE", ni "cBOOL".

Finding unsafe truncations

Vous pourriez souhaiter exécuter "Configure" avec quelque chose comme

-Accflags='-Wconversion -Wno-sign-conversion -Wno-shorten-64-to-32'

ou l'équivalent de votre compilateur pour faciliter la détection de toute troncature non sécurisée qui apparaîtrait.

The .i Targets

Vous pouvez développer les macros dans un fichier foo.c en disant

make foo.i

ce qui développera les macros en utilisant cpp. Ne vous laissez pas effrayer par les résultats.
