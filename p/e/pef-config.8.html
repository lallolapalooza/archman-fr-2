IPMI-CONFIG(8) Commandes système IPMI-CONFIG(8)

NOM

ipmi-config - configurer les valeurs IPMI

SYNOPSIS

ipmi-config [OPTION...]

DESCRIPTION

ipmi-config est utilisé pour obtenir et définir les paramètres de configuration dans IPMI. Il peut être utilisé pour configurer les noms d'utilisateur, les mots de passe, les informations réseau, la sécurité, le Serial-over-LAN (SOL), le Platform Event Filtering (PEF), les périphériques de démarrage, la politique de restauration de l'alimentation, les seuils de capteurs, les événements de capteurs, et de nombreuses autres options de configuration. Une certaine configuration est généralement requise avant que la plupart des outils IPMI puissent être utilisés pour accéder à une machine à distance. Par défaut, ipmi-config vous permet de --checkout ou --commit uniquement les valeurs IPMI de base nécessaires à la configuration IPMI. Pour des champs de configuration avancés supplémentaires liés à la configuration du châssis (y compris les options de démarrage), au Platform Event Filtering (PEF), ou aux capteurs, voir l'option --category ci-dessous. Pour plus de détails sur la configuration IPMI de base, voir ipmi-config.conf(5). La majorité des opérations de configuration nécessitent le privilège ADMIN lors de l'utilisation de ipmi-config hors bande. Bien que la connexion via un utilisateur avec des privilèges ADMIN ne soit pas requise pour une utilisation hors bande, la grande majorité des options de configuration ne seront pas récupérées ou définies.

Sont listés ci-dessous les options générales IPMI, les options spécifiques à l'outil, les informations de dépannage, les informations de contournement, les exemples et les problèmes connus. Pour une introduction générale à FreeIPMI, veuillez consulter freeipmi(7). Voir UTILISATION GÉNÉRALE ci-dessous pour une description de l'utilisation de base de ipmi-config.

OPTIONS GÉNÉRALES

Les options suivantes sont des options générales pour configurer la communication IPMI et exécuter des commandes générales de l'outil.

-D PILOTEIPMI, --driver-type=PILOTEIPMI
Spécifier le type de pilote à utiliser au lieu de faire une sélection automatique. Les pilotes hors bande actuellement disponibles sont LAN et LAN_2_0, qui réalisent respectivement IPMI 1.5 et IPMI 2.0. Les pilotes en bande actuellement disponibles sont KCS, SSIF, OPENIPMI, SUNBMC et INTELDCMI.
--disable-auto-probe
Ne pas sonder les périphériques IPMI en bande pour les paramètres par défaut.
--driver-address=ADRESSEPILOTE
Spécifier l'adresse du pilote en bande à utiliser au lieu de la valeur sondée. ADRESSEPILOTE doit être préfixée par "0x" pour une valeur hexadécimale et '0' pour une valeur octale.
--driver-device=PÉRIPH
Spécifier le chemin du périphérique pilote en bande à utiliser au lieu du chemin sondé.
--register-spacing=ESPACEMENTREGISTRE
Spécifier l'espacement des registres du pilote en bande au lieu de la valeur sondée. L'argument est en octets (c'est-à-dire, espacement des registres 32 bits = 4)
--target-channel-number=NUMÉROCANAL
Spécifier le numéro de canal cible du pilote en bande pour envoyer les requêtes IPMI.
--target-slave-address=ADRESSESCLAVE
Spécifier le numéro d'esclave cible du pilote en bande pour envoyer les requêtes IPMI.
-h HÔTEIPMI1,HÔTEIPMI2,..., --hostname=HÔTEIPMI1[:PORT],HÔTEIPMI2[:PORT],...
Spécifier le(s) hôte(s) distant(s) avec lequel/lesquels communiquer. Plusieurs noms d'hôtes peuvent être séparés par une virgule ou spécifiés dans un format de plage ; voir SUPPORT DE PLAGE D'HÔTES ci-dessous. Un port optionnel peut être spécifié avec chaque hôte, ce qui peut être utile dans des situations de redirection de port ou similaires. Si vous spécifiez une adresse IPv6 et un port, utilisez le format [ADRESSE]:PORT.
-u NOMUTILISATEUR, --username=NOMUTILISATEUR
Spécifier le nom d'utilisateur à utiliser lors de l'authentification avec l'hôte distant. S'il n'est pas spécifié, un nom d'utilisateur nul (c'est-à-dire anonyme) est supposé. L'utilisateur doit avoir au moins les privilèges ADMIN pour que cet outil fonctionne pleinement.
-p MOTDEPASSE, --password=MOTDEPASSE
Spécifier le mot de passe à utiliser lors de l'authentification avec l'hôte distant. S'il n'est pas spécifié, un mot de passe nul est supposé. La longueur maximale du mot de passe est de 16 pour IPMI 1.5 et de 20 pour IPMI 2.0.
-P, --password-prompt
Demander le mot de passe pour éviter la possibilité de le lister dans les listes de processus.
-k CLÉK_G, --k-g=CLÉK_G
Spécifier la clé K_g BMC à utiliser lors de l'authentification avec l'hôte distant pour IPMI 2.0. S'il n'est pas spécifié, une clé nulle est supposée. Pour saisir la clé sous forme hexadécimale, préfixez la chaîne par '0x'. Par exemple, la clé 'abc' peut être entrée avec soit la chaîne 'abc' soit la chaîne '0x616263'.
-K, --k-g-prompt
Demander la clé k-g pour éviter la possibilité de la lister dans les listes de processus.
--session-timeout=MILLISECONDES
Spécifier le délai d'expiration de la session en millisecondes. Par défaut, 20000 millisecondes (20 secondes) si non spécifié.
--retransmission-timeout=MILLISECONDES
Spécifier le délai de retransmission des paquets en millisecondes. Par défaut, 1000 millisecondes (1 seconde) si non spécifié. Le délai de retransmission ne peut pas être supérieur au délai d'expiration de la session.
-a TYPETAUTH, --authentication-type=TYPETAUTH
Spécifier le type d'authentification IPMI 1.5 à utiliser. Les types d'authentification actuellement disponibles sont NONE, STRAIGHT_PASSWORD_KEY, MD2 et MD5. Par défaut, MD5 est utilisé si non spécifié.
-I IDSUITECHIFFREMENT, --cipher-suite-id=IDSUITECHIFFREMENT
Spécifier l'identifiant de la suite de chiffrement IPMI 2.0 à utiliser. L'identifiant de la suite de chiffrement identifie un ensemble d'algorithmes d'authentification, d'intégrité et de confidentialité à utiliser pour la communication IPMI 2.0. L'algorithme d'authentification identifie l'algorithme à utiliser pour la configuration de la session, l'algorithme d'intégrité identifie l'algorithme à utiliser pour les signatures de paquets de session, et l'algorithme de confidentialité identifie l'algorithme à utiliser pour le chiffrement de la charge utile. Par défaut, l'identifiant de la suite de chiffrement 3 est utilisé si non spécifié. Les identifiants de suites de chiffrement suivants sont actuellement pris en charge :

0 - Algorithme d'authentification = Aucun ; Algorithme d'intégrité = Aucun ; Algorithme de confidentialité = Aucun

1 - Algorithme d'authentification = HMAC-SHA1 ; Algorithme d'intégrité = Aucun ; Algorithme de confidentialité = Aucun

2 - Algorithme d'authentification = HMAC-SHA1 ; Algorithme d'intégrité = HMAC-SHA1-96 ; Algorithme de confidentialité = Aucun

3 - Algorithme d'authentification = HMAC-SHA1 ; Algorithme d'intégrité = HMAC-SHA1-96 ; Algorithme de confidentialité = AES-CBC-128

6 - Algorithme d'authentification = HMAC-MD5 ; Algorithme d'intégrité = Aucun ; Algorithme de confidentialité = Aucun

7 - Algorithme d'authentification = HMAC-MD5 ; Algorithme d'intégrité = HMAC-MD5-128 ; Algorithme de confidentialité = Aucun

8 - Algorithme d'authentification = HMAC-MD5 ; Algorithme d'intégrité = HMAC-MD5-128 ; Algorithme de confidentialité = AES-CBC-128

11 - Algorithme d'authentification = HMAC-MD5 ; Algorithme d'intégrité = MD5-128 ; Algorithme de confidentialité = Aucun

12 - Algorithme d'authentification = HMAC-MD5 ; Algorithme d'intégrité = MD5-128 ; Algorithme de confidentialité = AES-CBC-128

15 - Algorithme d'authentification = HMAC-SHA256 ; Algorithme d'intégrité = Aucun ; Algorithme de confidentialité = Aucun

16 - Algorithme d'authentification = HMAC-SHA256 ; Algorithme d'intégrité = HMAC_SHA256_128 ; Algorithme de confidentialité = Aucun

17 - Algorithme d'authentification = HMAC-SHA256 ; Algorithme d'intégrité = HMAC_SHA256_128 ; Algorithme de confidentialité = AES-CBC-128

-l NIVEAUPRIVILÈGE, --privilege-level=NIVEAUPRIVILÈGE
Spécifier le niveau de privilège à utiliser. Les niveaux de privilège actuellement disponibles sont USER, OPERATOR et ADMIN. Par défaut, ADMIN est utilisé si non spécifié.
--config-file=FICHIER
Spécifier un fichier de configuration alternatif.

OPTIONS IPMI-CONFIG

Les options suivantes sont utilisées pour lire, écrire et trouver les différences dans les valeurs de configuration.

-g CATEGORY, --category=CATEGORY
Spécifiez la catégorie ou les catégories de données de configuration à configurer. Choix actuellement disponibles : core, chassis, sensors, pef, dcmi. Plusieurs catégories peuvent être séparées par une virgule. core inclut toute la configuration IPMI majeure nécessaire au bon fonctionnement de l'IPMI sur un système, telle que la configuration des utilisateurs, des mots de passe, de l'authentification, du réseau et du port série sur LAN (SOL). chassis inclut toute la configuration pertinente du châssis, y compris les options de démarrage, les boutons du panneau avant et le comportement d'alimentation. dcmi inclut les fonctions spécialisées fournies par l'interface de gestion du centre de données (DCMI). Par défaut, c'est core si non spécifié.
-o, --checkout
Récupérez les informations de configuration.
-c, --commit
Mettez à jour les informations de configuration à partir d'un fichier de configuration ou de paires clé-valeur.
-d, --diff
Affichez les différences entre les informations stockées et un fichier de configuration ou des paires clé-valeur.
-n FILENAME, --filename=FILENAME
Spécifiez un fichier de configuration pour le checkout/commit/diff. S'il est spécifié avec checkout, il ne peut pas être utilisé avec plusieurs hôtes ou avec --always-prefix.
-e "KEY=VALUE", --key-pair="KEY=VALUE"
Spécifiez des paires CLÉ=VALEUR pour le checkout/commit/diff. Spécifiez la CLÉ par NomDeSection:NomDeChamp. Cette option peut être utilisée plusieurs fois. Lors d'un commit, toutes les paires CLÉ=VALEUR écraseront toutes les paires spécifiées dans un fichier avec --filename.
-S SECTION, --section=SECTION
Spécifiez une SECTION pour le checkout. Cette option peut être utilisée plusieurs fois. La SECTION que vous spécifiez doit se trouver dans la ou les catégories spécifiées avec --category.
-L, --listsections
Listez les sections disponibles pour le checkout par rapport à la ou aux catégories sous --category. Certaines sections de la liste peuvent ne pas être récupérées par défaut et peuvent nécessiter une augmentation de la verbosité.
-v, --verbose
Affichez des informations détaillées. Lorsque utilisé avec --checkout, des sections et/ou champs supplémentaires et peu courants seront affichés. Dans la catégorie core, cela inclut la récupération des paramètres de configuration série, des paramètres VLAN, des paramètres d'en-tête IPv4, du port RMCP, de toutes les adresses configurables IPv6 (si plus d'une est prise en charge) et des sections pour chaque canal d'un système (s'il existe plusieurs canaux). Dans la catégorie pef, cela inclut la récupération des sections pour chaque canal d'un système (s'il existe plusieurs canaux).
-vv
Affichez des informations très détaillées. Affichez des informations détaillées supplémentaires sur les champs qui peuvent et ne peuvent pas être récupérés, et parfois la raison pour laquelle. Affiche parfois des champs qui sont identifiés comme non pris en charge sur la carte mère.
--lan-channel-number=NUMBER
Utilisez un numéro de canal spécifique pour la configuration LAN. Particulièrement utile si la carte mère contient plusieurs canaux LAN et qu'un utilisateur souhaite en utiliser un spécifique.
--serial-channel-number=NUMBER
Utilisez un numéro de canal spécifique pour la configuration série. Particulièrement utile si la carte mère contient plusieurs canaux série et qu'un utilisateur souhaite en utiliser un spécifique.
--sol-channel-number=NUMBER
Utilisez un numéro de canal spécifique pour la configuration SOL. Particulièrement utile si la carte mère contient plusieurs canaux SOL et qu'un utilisateur souhaite en utiliser un spécifique.

OPTIONS DE CACHE SDR

Cet outil nécessite l'accès au cache du dépôt de données de capteur (SDR) pour un fonctionnement général. Par défaut, les données SDR seront téléchargées et mises en cache sur la machine locale. Les options suivantes s'appliquent au cache SDR.

--flush-cache
Videz une version mise en cache du cache du dépôt de données de capteur (SDR). Le SDR est généralement mis en cache pour un accès ultérieur plus rapide. Cependant, il peut être nécessaire de le vider et de le régénérer si le SDR a été mis à jour sur un système.
--quiet-cache
Ne pas afficher d'informations sur la création/suppression du cache. Peut être utile dans les scripts.
--sdr-cache-recreate
Si le cache SDR est obsolète ou invalide, recréez automatiquement le cache du dépôt de données de capteur (SDR). Cette option peut être utile à des fins de script.
--sdr-cache-file=FILE
Spécifiez un fichier de cache de dépôt de données de capteur (SDR) spécifique à stocker ou à lire. Si cette option est utilisée lorsque plusieurs hôtes sont spécifiés, le même fichier de cache SDR sera utilisé pour tous les hôtes.
--sdr-cache-directory=DIRECTORY
Spécifiez un répertoire alternatif pour les caches du dépôt de données de capteur (SDR) à stocker ou à lire. Par défaut, le répertoire personnel est utilisé s'il n'est pas spécifié.

OPTIONS HOSTRANGED

Les options suivantes manipulent la sortie hostranged. Voir HOSTRANGED SUPPORT ci-dessous pour des informations supplémentaires sur les hostranges.

-B, --buffer-output
Mettez en mémoire tampon la sortie de hostranged. Pour chaque nœud, mettez en mémoire tampon la sortie standard jusqu'à ce que le nœud ait terminé son opération IPMI. Lorsque vous spécifiez cette option, les données peuvent apparaître plus lentement à l'utilisateur car l'opération IPMI complète doit se terminer avant que toute donnée puisse être affichée. Voir HOSTRANGED SUPPORT ci-dessous pour des informations supplémentaires.
-C, --consolidate-output
Consolidez la sortie de hostranged. La sortie standard complète de chaque nœud spécifié sera consolidée de sorte que les nœuds avec une sortie identique ne soient pas affichés deux fois. Un en-tête listera les nœuds avec la sortie consolidée. Lorsque cette option est spécifiée, aucune sortie ne peut être vue tant que les opérations IPMI sur tous les nœuds ne sont pas terminées. Si l'utilisateur interrompt le programme prématurément, toute la sortie consolidée sera vidée. Voir HOSTRANGED SUPPORT ci-dessous pour des informations supplémentaires.
-F NUM, --fanout=NUM
Spécifiez le fanout de plusieurs hôtes. Un algorithme de "fenêtre glissante" (ou fanout) est utilisé pour la communication IPMI parallèle afin que les nœuds lents ou les nœuds ayant expiré n'entravent pas la communication parallèle. Le nombre maximum de threads disponibles simultanément est limité par le fanout. La valeur par défaut est 64.
-E, --eliminate
Éliminez les hôtes déterminés comme non détectés par ipmidetect. Cela tente de résoudre le problème courant de temporisation de l'exécution de hostranged en raison de plusieurs nœuds retirés du service dans un grand cluster. Le démon ipmidetectd doit être en cours d'exécution sur le nœud exécutant la commande.
--always-prefix
Toujours préfixer la sortie, même si un seul hôte est spécifié ou communique en bande. Cette option est principalement utile pour les scripts. L'option sera ignorée si elle est spécifiée avec l'option -C.

UTILISATION GÉNÉRALE

La plupart des utilisateurs voudront :

A) Exécuter avec --checkout pour obtenir une copie de la configuration actuelle et la stocker dans un fichier. La sortie standard peut être redirigée vers un fichier ou un fichier peut être spécifié avec l'option --filename.

B) Modifier le fichier de configuration avec un éditeur.

C) Valider la configuration en utilisant l'option --commit et en spécifiant le fichier de configuration avec l'option --filename. La configuration peut être validée sur plusieurs hôtes en parallèle via le support hostrange.

Bien que ce ne soit généralement pas nécessaire, certaines cartes mères ne stockent pas les valeurs de configuration dans la mémoire non volatile. Par conséquent, après les redémarrages du système, certaines valeurs de configuration peuvent avoir changé. L'utilisateur peut souhaiter exécuter les outils de configuration à chaque démarrage pour s'assurer que les valeurs de configuration restent.

Des commentaires seront parfois listés dans les fichiers récupérés avec des informations sur la façon de configurer les champs. La page de manuel ipmi-config.conf(5) fournit également des informations supplémentaires sur la signification des différents champs.

Pour les utilisateurs avec de grands clusters ou ensembles de nœuds, vous pourriez souhaiter utiliser le même fichier de configuration pour tous les nœuds. Le seul problème est que l'adresse IP et l'adresse MAC seront différentes sur chaque nœud de votre cluster et ne peuvent donc pas être configurées via le même fichier de configuration. L'adresse IP et l'adresse MAC de votre fichier de configuration peuvent être écrasées sur la ligne de commande en utilisant l'option --key-pair. L'exemple suivant pourrait être utilisé dans un script pour configurer chaque nœud d'un cluster avec le même fichier de configuration BMC. Le script n'a qu'à déterminer l'adresse IP et l'adresse MAC correctes à utiliser.

# ipmi-config --commit -k Lan_Conf:Ip_Address=$MY_IP -k Lan_Conf:Mac_Address=$MY_MAC --filename=my_bmc.conf

INFORMATION SUR LES CAS PARTICULIERS DE CONFIGURATION DU NOYAU

Les champs UserN:Password (où N est un numéro) ne peuvent pas être extraits sur certains systèmes, par conséquent la valeur extraite sera toujours vide.

Le champ UserN:Enable_User (où N est un numéro) ne peut pas être extrait sur les anciens systèmes IPMI, par conséquent la valeur extraite sera parfois vide.

Les champs UserN:Lan_Session_Limit et UserN:Serial_Session_Limit (où N est un numéro) ne peuvent pas être extraits sur certains systèmes, par conséquent la valeur extraite sera toujours vide. S'il n'est pas spécifié dans des commits ultérieurs de configurations, le champ peut être réinitialisé à 0 en raison d'une exigence selon laquelle d'autres champs (configurés avec la limite de session) nécessiteront une valeur d'entrée pour la limite de session. Dans la plupart des cas, il n'est pas nécessaire de définir ce champ et la plupart des utilisateurs peuvent choisir de l'ignorer. Ce champ est considéré comme facultatif selon les normes IPMI, et peut entraîner des erreurs lorsqu'on tente de le configurer à une valeur non nulle. Si des erreurs se produisent, la remise de la valeur à 0 devrait résoudre les problèmes.

Les champs Lan_Conf:IP_Address et Lan_Conf:MAC_Address ne peuvent pas être validés en parallèle via le support hostrange. Chaque machine doit être configurée avec un tuple unique d'adresse IP et d'adresse MAC, par conséquent nous interdisons cette configuration dans ipmi-config.

Sur certaines cartes mères, Lan_Conf:MAC_Address peut être en lecture seule et l'adresse MAC est configurée automatiquement.

Sur certaines cartes mères, Lan_Conf:MAC_Address peut être en lecture seule et l'adresse MAC est configurée via une commande OEM. Voir ipmi-oem(8) pour savoir si la configuration OEM pour votre carte mère est prise en charge.

Sur certaines cartes mères, un certain nombre de champs de configuration utilisateur ne peuvent pas être lus ou configurés avant qu'un nom d'utilisateur non nul ou un mot de passe non nul ne soit configuré. Dans certains de ces cas, une sortie appropriée dans le fichier de configuration indiquera cette situation. Cependant, tous les cas particuliers des cartes mères ne peuvent pas être détectés. Les utilisateurs peuvent souhaiter jouer avec l'ordre des champs pour contourner ces problèmes.

Sur certaines cartes mères, l'authentification OEM dans Lan_Conf_Auth ne peut pas être activée. Cependant, les paramètres par défaut de la carte mère ont ces champs activés. Il est conseillé aux utilisateurs de désactiver toute authentification OEM dans cette section.

Sur certaines cartes mères, plusieurs canaux peuvent exister pour la communication IPMI LAN ou série. Si plusieurs canaux existent, la configuration des deux canaux peut être consultée et finalement configurée en exécutant --checkout en mode verbeux. Chaque section ou nom de clé sera suffixé appropriément avec le mot Channel et le numéro de canal. Par exemple, vous pourriez voir un Lan_Conf_Channel_1 et un Lan_Conf_Channel_3, où vous pouvez configurer la configuration LAN sur les canaux 1 et 3 respectivement.

Sur certaines cartes mères, les modifications de configuration ne seront pas "absorbées" par le système avant que la carte mère ne soit réinitialisée de manière matérielle. Cela peut être accompli en éteignant et en rallumant physiquement le système (par exemple, en appuyant sur un bouton), ou cela peut être accompli via une réinitialisation à froid. Une réinitialisation à froid peut être exécutée via bmc-device.

INFORMATION SUR LES CAS PARTICULIERS DE CONFIGURATION DU CHASSIS

Les champs Chassis_Front_Panel_Buttons:Enable_Standby_Button_For_Entering_Standby, Chassis_Front_Panel_Buttons:Enable_Diagnostic_Interrupt_Button Chassis_Front_Panel_Buttons:Enable_Reset_Button, et Chassis_Front_Panel_Buttons:Enable_Power_Off_Button_For_Power_Off_Only peuvent ne pas être extractibles sur certains systèmes IPMI, par conséquent la valeur extraite peut être vide. Certains de ces champs peuvent être désactivables, tandis que d'autres ne le sont pas. Le champ Chassis_Power_Conf:Power_Control_Interval ne peut pas être extrait. Par conséquent, la valeur extraite sera toujours vide.

INFORMATION SUR LES CAS PARTICULIERS PEF

Sur certaines cartes mères, plusieurs canaux peuvent exister pour la communication IPMI LAN. Si plusieurs canaux existent, la configuration des deux canaux peut être consultée et finalement configurée en exécutant --checkout en mode verbeux. Chaque nom de section sera suffixé appropriément avec le mot Channel et le numéro de canal. Par exemple, vous pourriez voir un Community_String_Channel_1 et un Community_String_Channel_3, où vous pouvez configurer la chaîne de communauté sur les canaux 1 et 3 respectivement. Les options suivantes sont appropriées pour l'entrée de Sensor_Type dans la configuration PEF.

Options de Sensor_Type

INFORMATION SUR LES CAS PARTICULIERS DES CAPTEURS

Étant donné que de nombreux champs configurables impliquent des nombres décimaux, des inexactitudes de précision/virgule flottante peuvent survenir lors de la configuration de nouveaux seuils. Les inexactitudes peuvent ne pas être apparentes immédiatement. Il est recommandé aux utilisateurs de vérifier leurs modifications après avoir configuré de nouveaux seuils.

SUPPORT HOSTRANGE

Plusieurs hôtes peuvent être saisis soit sous forme de listes explicites d'hôtes séparées par des virgules, soit d'une plage de noms d'hôtes sous la forme générale : préfixe[n-m,l-k,...], où n < m et l < k, etc. La forme ultérieure ne doit pas être confondue avec les classes de caractères d'expressions régulières (également désignées par []). Par exemple, foo[19] ne représente pas foo1 ou foo9, mais plutôt une plage dégénérée : foo19.

Cette syntaxe de plage est destinée uniquement à la commodité sur les clusters avec une convention de dénomination préfixeNN et la spécification de plages ne doit pas être considérée comme nécessaire -- la liste foo1,foo9 peut être spécifiée comme telle, ou par la plage foo[1,9].

Quelques exemples d'utilisation de plages suivent :

    foo[01-05] au lieu de foo01,foo02,foo03,foo04,foo05
    foo[7,9-10] au lieu de foo7,foo9,foo10
    foo[0-3] au lieu de foo0,foo1,foo2,foo3

Pour rappel au lecteur, certains shells interpréteront les crochets ( [ et ] ) pour la mise en correspondance de motifs. Selon votre shell, il peut être nécessaire d'encadrer les listes de plages entre guillemets.

Lorsque plusieurs hôtes sont spécifiés par l'utilisateur, un thread sera exécuté pour chaque hôte en parallèle jusqu'à la diffusion configurée (qui peut être ajustée via l'option -F). Cela permettra de communiquer avec un grand nombre de nœuds beaucoup plus rapidement que s'ils étaient traités en série.

Par défaut, la sortie standard de chaque nœud spécifié sera affichée avec le nom d'hôte précédant chaque ligne. Bien que cette sortie soit lisible dans de nombreuses situations, elle peut être difficile à lire dans d'autres situations. Par exemple, la sortie de plusieurs nœuds peut être mélangée. Les options -B et -C peuvent être utilisées pour modifier ce comportement par défaut.

La communication IPMI en bande sera utilisée lorsque l'hôte "localhost" est spécifié. Cela permet à l'utilisateur d'ajouter le localhost dans la sortie hostranged.

DÉPANNAGE GÉNÉRAL

Le plus souvent, les problèmes IPMI sont dus à des problèmes de configuration.

Les problèmes IPMI sur LAN impliquent une mauvaise configuration du BMC de la machine distante. Vérifiez attentivement que les éléments suivants sont correctement configurés dans le BMC de la machine distante : adresse IP, adresse MAC, masque de sous-réseau, nom d'utilisateur, activation de l'utilisateur, privilège utilisateur, mot de passe, privilège LAN, activation LAN et type(s) d'authentification autorisés. Pour les connexions IPMI 2.0, vérifiez attentivement que le(s) privilège(s) de suite de chiffrement et la clé K_g sont correctement configurés. L'outil ipmi-config(8) peut être utilisé pour vérifier et/ou modifier ces paramètres de configuration.

Les problèmes IPMI en bande sont généralement causés par des pilotes mal configurés ou des BMC non standard.

En plus des conseils de dépannnage ci-dessous, veuillez également consulter les SOLUTIONS DE CONTOURNEMENT ci-dessous s'il existe des bogues spécifiques au fournisseur qui ont été découverts et contournés.

Vous trouverez ci-dessous une liste des problèmes courants pour les messages d'erreur. Pour une assistance supplémentaire, veuillez envoyer un e-mail à la liste de diffusion <freeipmi-users@gnu.org>.

"username invalid" - Le nom d'utilisateur saisi (ou un nom d'utilisateur NULL s'il n'y en a pas eu) n'est pas disponible sur la machine distante. Il est également possible que la configuration du nom d'utilisateur du BMC distant soit incorrecte.

"password invalid" - Le mot de passe saisi (ou un mot de passe NULL s'il n'y en a pas eu) est incorrect. Il est également possible que le mot de passe de l'utilisateur ne soit pas correctement configuré sur le BMC distant.

"password verification timeout" - La vérification du mot de passe a expiré. Une erreur "password invalid" (décrite ci-dessus) ou une erreur générique "session timeout" (décrite ci-dessous) s'est produite. À ce stade du protocole, il ne peut pas être différencié laquelle s'est produite.

"k_g invalid" - La clé K_g saisie (ou une clé K_g NULL s'il n'y en a pas eu) est incorrecte. Il est également possible que la clé K_g ne soit pas correctement configurée sur le BMC distant.

"privilege level insufficient" - Une commande IPMI nécessite un privilège utilisateur plus élevé que celui avec lequel vous vous êtes authentifié. Veuillez essayer de vous authentifier avec un privilège plus élevé. Cela peut nécessiter de s'authentifier auprès d'un autre utilisateur qui a un privilège maximum plus élevé.

"privilege level cannot be obtained for this user" - Le niveau de privilège avec lequel vous essayez de vous authentifier est supérieur au maximum autorisé pour cet utilisateur. Veuillez réessayer avec un privilège inférieur. Il est également possible que le niveau de privilège maximum autorisé pour un utilisateur ne soit pas correctement configuré sur le BMC distant.

"authentication type unavailable for attempted privilege level" - Le type d'authentification avec lequel vous souhaitez vous authentifier n'est pas disponible

ERREURS

"authentication type unavailable for attempted privilege level" - Le type d'authentification que vous souhaitez utiliser n'est pas disponible pour ce niveau de privilège. Veuillez réessayer avec un type d'authentification alternatif ou un niveau de privilège alternatif. Il est également possible que les types d'authentification disponibles avec lesquels vous pouvez vous authentifier ne soient pas correctement configurés sur le BMC distant.

"cipher suite id unavailable" - L'ID de la suite de chiffrement avec lequel vous souhaitez vous authentifier n'est pas disponible sur le BMC distant. Veuillez réessayer avec un ID de suite de chiffrement alternatif. Il est également possible que les ID de suite de chiffrement disponibles ne soient pas correctement configurés sur le BMC distant.

"ipmi 2.0 unavailable" - IPMI 2.0 n'a pas été découvert sur la machine distante. Veuillez essayer d'utiliser IPMI 1.5 à la place.

"connection timeout" - La communication IPMI initiale a échoué. Un certain nombre d'erreurs potentielles sont possibles, y compris un nom d'hôte invalide spécifié, une adresse IP IPMI qui ne peut pas être résolue, IPMI qui n'est pas activé sur le serveur distant, une mauvaise connexion réseau, etc. Veuillez vérifier la configuration et la connectivité.

"session timeout" - La session IPMI a expiré. Veuillez vous reconnecter. Si cette erreur se produit souvent, vous pourriez souhaiter augmenter le délai d'expiration de la retransmission. Certains BMC distants sont considérablement plus lents que d'autres.

"device not found" - Le périphérique spécifié n'a pas pu être trouvé. Veuillez vérifier la configuration ou les entrées et réessayer.

"driver timeout" - La communication avec le pilote ou le périphérique a expiré. Veuillez réessayer.

"message timeout" - La communication avec le pilote ou le périphérique a expiré. Veuillez réessayer.

"BMC busy" - Le BMC est actuellement occupé. Il peut être en train de traiter des informations ou avoir trop de sessions simultanées à gérer. Veuillez patienter et réessayer.

"could not find inband device" - Un périphérique en bande n'a pas pu être trouvé. Veuillez vérifier la configuration ou spécifier un périphérique ou un pilote spécifique sur la ligne de commande.

"driver timeout" - Le pilote en bande a expiré lors de la communication avec le BMC local ou le processeur de service. Le BMC ou le processeur de service peut être occupé ou (dans le pire des cas) potentiellement défectueux.

CONTOURNEMENTS

Avec autant de fournisseurs différents implémentant leurs propres solutions IPMI, différents fournisseurs peuvent implémenter leurs protocoles IPMI de manière incorrecte. Ce qui suit décrit un certain nombre de contournements actuellement disponibles pour gérer les problèmes de conformité découverts. Lorsque cela est possible, les contournements ont été implémentés de manière à être transparents pour l'utilisateur. Cependant, certains exigeront que l'utilisateur spécifie qu'un contournement doit être utilisé via l'option -W.

Le matériel listé ci-dessous peut seulement indiquer le matériel sur lequel un problème a été découvert. Des versions plus récentes du matériel peuvent corriger les problèmes indiqués ci-dessous. Des machines similaires de différents fournisseurs peuvent ou non présenter les mêmes problèmes. Différents fournisseurs peuvent licencier leur firmware auprès du même développeur de firmware IPMI, il peut donc être utile d'essayer les contournements listés ci-dessous même si votre carte mère n'est pas répertoriée.

Si vous pensez que votre matériel présente un problème de conformité supplémentaire nécessitant l'implémentation d'un contournement, veuillez contacter les mainteneurs de FreeIPMI sur <freeipmi-users@gnu.org> ou <freeipmi-devel@gnu.org>.

assumeio - Ce drapeau de contournement supposera que les interfaces en bande communiquent avec l'I/O système plutôt que d'être mappées en mémoire. Cela permettra de contourner les systèmes qui rapportent des adresses de base invalides. Ceux qui rencontrent ce problème peuvent voir des erreurs telles que "device not supported" ou "could not find inband device". Problème observé sur HP ProLiant DL145 G1.

spinpoll - Ce drapeau de contournement indiquera à certains pilotes en bande (notamment le pilote KCS) de tourner en boucle lors du sondage plutôt que de mettre le processus en veille. Cela peut améliorer significativement le temps d'exécution des outils, car la granularité d'un ordonnanceur de système d'exploitation peut être beaucoup plus grande que le temps nécessaire pour effectuer une seule transaction de message IPMI. Cependant, en tournant en boucle, votre système peut effectuer moins de travail utile en ne transférant pas le contexte de l'outil vers une tâche plus utile.

authcap - Ce drapeau de contournement ignorera les vérifications précoces des capacités de nom d'utilisateur, des capacités d'authentification et du support K_g, et permettra à l'authentification IPMI de réussir. Il contourne plusieurs problèmes où le système distant ne rapporte pas correctement les capacités de nom d'utilisateur, les capacités d'authentification ou l'état K_g. Ceux qui rencontrent ce problème peuvent voir des erreurs telles que "username invalid", "authentication type unavailable for attempted privilege level" ou "k_g invalid". Problème observé sur Asus P5M2/P5MT-R/RS162-E4/RX4, Intel SR1520ML/X38ML et Sun Fire 2200/4150/4450 avec ELOM.

nochecksumcheck - Ce drapeau de contournement indiquera à FreeIPMI de ne pas vérifier les sommes de contrôle retournées par les réponses des commandes IPMI. Il contourne les systèmes qui renvoient des sommes de contrôle invalides en raison d'erreurs d'implémentation, mais le paquet est par ailleurs valide. Les utilisateurs sont avertis de l'utilisation de cette option, car elle supprime la validation de l'intégrité du paquet dans un certain nombre de circonstances. Cependant, il est peu probable que cela pose un problème dans la plupart des situations. Ceux qui rencontrent ce problème peuvent voir des erreurs telles que "connection timeout", "session timeout" ou "password verification timeout". Sur les connexions IPMI 1.5, le contournement "noauthcodecheck" peut également être nécessaire. Problème observé sur Supermicro X9SCM-iiF, Supermicro X9DRi-F et Supermicro X9DRFR.

idzero - Ce drapeau de contournement permettra l'acceptation des ID de session vides par le client. Il contourne les sessions IPMI qui rapportent des ID de session vides au client. Ceux qui rencontrent ce problème peuvent voir des erreurs de "session timeout". Problème observé sur Tyan S2882 avec BMC M3289.

unexpectedauth - Ce drapeau de contournement permettra la vérification des codes d'authentification inattendus non nuls comme s'ils étaient attendus. Il contourne un problème où les paquets contiennent des données d'authentification non nulles alors qu'elles devraient être nulles en raison de la désactivation de l'authentification par message. Ceux qui rencontrent ce problème peuvent voir des erreurs de "session timeout". Problème observé sur Dell PowerEdge 2850, SC1425. Corrigé sur des firmwares plus récents.

forcepermsg - Ce drapeau de contournement forcera l'utilisation de l'authentification par message, peu importe ce qui est annoncé par le système distant. Il contourne un problème où l'authentification par message est annoncée comme désactivée sur le système distant, mais elle est en fait requise pour le protocole. Ceux qui rencontrent ce problème peuvent voir des erreurs de "session timeout". Problème observé sur IBM eServer 325.

endianseq - Ce drapeau de contournement inversera l'endianness des numéros de séquence de session pour permettre à la session de continuer correctement. Il contourne les numéros de séquence IPMI 1.5 dont l'endianness est incorrecte. Ceux qui rencontrent ce problème peuvent voir des erreurs de "session timeout". Problème observé sur certains Sun ILOM 1.0/2.0 (dépend de l'endianness du processeur de service).

noauthcodecheck - Ce drapeau de contournement indiquera à FreeIPMI de ne pas vérifier les codes d'authentification retournés par les réponses des commandes IPMI 1.5. Il contourne les systèmes qui renvoient des codes d'authentification invalides en raison d'erreurs de hachage ou d'implémentation. Les utilisateurs sont avertis de l'utilisation de cette option, car elle supprime une vérification d'authentification validant l'intégrité d'un paquet. Cependant, dans la plupart des organisations, cela ne pose probablement pas de problème de sécurité. Ceux qui rencontrent ce problème peuvent voir des erreurs telles que "connection timeout", "session timeout" ou "password verification timeout". Problème observé sur Xyratex FB-H8-SRAY, Intel Windmill, Quanta Winterfell et Wiwynn Windmill.

intel20 - Ce drapeau de contournement permettra de résoudre plusieurs problèmes d'authentification IPMI 2.0 d'Intel. Les problèmes traités incluent le remplissage des noms d'utilisateur et la troncature des mots de passe si l'algorithme d'authentification est HMAC-MD5-128. Ceux qui rencontrent ce problème peuvent voir des erreurs telles que "username invalid", "password invalid" ou "k_g invalid". Problème observé sur Intel SE7520AF2 avec Intel Server Management Module (Professional Edition).

supermicro20 - Ce drapeau de contournement permettra de résoudre plusieurs problèmes d'authentification IPMI 2.0 de Supermicro sur les cartes mères avec firmware IPMI Peppercon. Les problèmes traités incluent la gestion des codes d'authentification de longueur invalide. Ceux qui rencontrent ce problème peuvent voir des erreurs de "password invalid". Problème observé sur Supermicro H8QME avec carte fille SIMSO. Corrigé sur des firmwares plus récents.

sun20 - Ce drapeau de contournement permettra de résoudre plusieurs problèmes d'authentification IPMI 2.0 de Sun. Les problèmes traités incluent les clés de hachage de longueur invalide, les clés mal hachées et les enregistrements de suite de chiffrement invalides. Ceux qui rencontrent ce problème peuvent voir des erreurs de "password invalid" ou "bmc error". Problème observé sur Sun Fire 4100/4200/4500 avec ILOM. Ce contournement inclut automatiquement le contournement "opensesspriv".

opensesspriv - Ce drapeau de contournement modifiera légèrement le protocole de connexion IPMI 2.0 de FreeIPMI pour contourner un algorithme de hachage invalide utilisé par le système distant. Le niveau de privilège envoyé lors de l'étape Open Session d'une connexion IPMI 2.0 est utilisé pour le hachage des clés au lieu du niveau de privilège envoyé lors de l'étape de connexion RAKP1. Ceux qui rencontrent ce problème peuvent voir des erreurs telles que "password invalid", "k_g invalid", "bad rmcpplus status code" ou "privilege level cannot be obtained for this user". Problème observé sur Sun Fire 4100/4200/4500 avec ILOM, Inventec 5441/Dell Xanadu II, Supermicro X8DTH, Supermicro X8DTG, Intel S5500WBV/Penguin Relion 700, Intel S2600JF/Appro 512X, Quanta QSSC-S4R/Appro GB812X-CN, Dell C5220 et le BMC logiciel OpenIPMI. Ce contournement est automatiquement déclenché avec le contournement "sun20".

integritycheckvalue - Ce drapeau de contournement permettra de résoudre une valeur de contrôle d'intégrité invalide lors de l'établissement d'une session IPMI 2.0 en utilisant l'ID de suite de chiffrement 0. La valeur de contrôle d'intégrité devrait être de longueur 0, cependant la carte mère distante répond avec un champ non vide. Ceux qui rencontrent ce problème peuvent voir des erreurs de "k_g invalid". Problème observé sur Supermicro X8DTG, Supermicro X8DTU et Intel S5500WBV/Penguin Relion 700, et Intel S2600JF/Appro 512X.

Pas de support IPMI 1.5 - Certaines cartes mères prenant en charge IPMI 2.0 se sont avérées ne pas prendre en charge IPMI 1.5. Ceux qui rencontrent ce problème peuvent voir des erreurs telles que "ipmi 2.0 unavailable" ou "connection timeout". Ce problème peut être résolu en utilisant IPMI 2.0 au lieu d'IPMI 1.5 en spécifiant --driver-type=LAN_2_0. Problème observé sur un certain nombre de cartes mères HP et Supermicro.

slowcommit - Ce contournement ralentira les validations vers le BMC en dormant une seconde entre la validation des sections. Il permet de contourner les cartes mères dont les BMC peuvent être submergés par les validations. Ceux qui rencontrent ce problème peuvent voir des erreurs de validation ou des validations qui ne sont pas écrites sur le BMC. Problème observé sur Supermicro H8QME.

WORKAROUNDS

The following workarounds are available:

batchcommit - This workaround will force ipmi-config to commit only one key at a time. It works around motherboards that have BMCs that can be overwhelmed by commits. Those hitting this issue may see commit errors or commits not being written to the BMC. Issue observed on Quanta S99Q/Dell FS12-TY and Dell PowerEdge T320.

solchannelassumelanchannel - This workaround will force ipmi-config to assume that the channel used SOL is identical to the channel used for LAN. On some motherboards, the SOL channel is reported incorrectly, leading to incorrect configuration. Most notably, this problem has come up when attempting to configure multiple channels. Issue observed on Intel S5500WBV/Penguin Relion 700.

EXEMPLES

# ipmi-config --checkout

Sort toutes les informations de configuration de base sur la console. # ipmi-config --checkout --category=pef

Sort toutes les informations de configuration PEF sur la console. # ipmi-config --checkout --category=pef,chassis

Sort toutes les informations de configuration PEF et châssis sur la console.

# ipmi-config --checkout --filename=bmc-data1.conf

Stocke toutes les informations de configuration de base dans bmc-data1.conf.

# ipmi-config --diff --filename=bmc-data2.conf

Affiche toutes les différences entre la configuration actuelle et le fichier bmc-data2.conf.

# ipmi-config --diff --key-pair="lan_conf_misc:gratuitous_arp_interval=8"

Affiche la différence entre la configuration actuelle et la valeur '8' de 'lan_conf_misc:gratuitous_arp_interval'.

# ipmi-config --commit --filename=bmc-data1.conf

Valide toutes les valeurs de configuration du fichier bmc-data1.conf.

# ipmi-config --commit --key-pair="lan_conf_misc:gratuitous_arp_interval=4"

Valide la clé 'lan_conf_misc:gratuitous_arp_interval' avec la valeur '4'.

# ipmi-config --commit --filename=bmc-data-updt.conf --key-pair="lan_conf_misc:gratuitous_arp_interval=4"

Valide toutes les valeurs de configuration du fichier bmc-data-updt.conf et la clé 'lan_conf_misc:gratuitous_arp_interval' avec la valeur '4'.

DIAGNOSTICS

Lors d'une exécution réussie, le code de sortie est 0. En cas d'erreur non fatale, le code de sortie est 1. En cas d'erreur fatale, le code de sortie est 2.

Si plusieurs hôtes sont spécifiés pour la communication, le code de sortie est 0 si et seulement si toutes les cibles s'exécutent avec succès. Si une erreur non fatale se produit, le code de sortie est 1. Si une erreur fatale se produit, le code de sortie est 2.

PROBLÈMES CONNUS

Sur les systèmes d'exploitation plus anciens, si vous saisissez votre nom d'utilisateur, mot de passe et d'autres informations potentiellement sensibles sur la ligne de commande, ces informations peuvent être découvertes par d'autres utilisateurs lors de l'utilisation d'outils tels que la commande ps(1) ou en consultant le système de fichiers /proc. Il est généralement plus sûr de saisir les informations de mot de passe avec des options telles que -P ou -K. La configuration des informations sensibles dans le fichier de configuration FreeIPMI serait également une manière appropriée de masquer ces informations.

Afin d'empêcher les attaques par force brute, certains BMC se bloquent temporairement après un certain nombre d'erreurs d'authentification à distance. Vous pourriez avoir à attendre un certain temps pour que ce blocage temporaire passe avant de pouvoir vous authentifier à nouveau.
