NOM

perf-record - Exécute une commande et enregistre son profil dans perf.data

SYNTAXE

perf record [-e <EVENT> | --event=EVENT] [-a] <commande>
perf record [-e <EVENT> | --event=EVENT] [-a] -- <commande> [<options>]

DESCRIPTION

Cette commande exécute une commande et recueille un profil de compteur de performance à partir de celle-ci, dans perf.data - sans rien afficher.

Ce fichier peut ensuite être inspecté ultérieurement, en utilisant perf report.

OPTIONS

<commande>...

Toute commande que vous pouvez spécifier dans un shell.

-e, --event=

Sélectionne l'événement PMU. La sélection peut être :
•un nom d'événement symbolique (utilisez perf list pour lister tous les événements)
•un événement PMU brut sous la forme rN où N est une valeur hexadécimale représentant le codage du registre brut avec la disposition des registres de contrôle d'événement telle que décrite par les entrées de /sys/bus/event_source/devices/cpu/format/*.
•un événement PMU symbolique ou brut suivi d'un deux-points optionnel et d'une liste de modificateurs d'événement, par exemple, cpu-cycles:p. Voir la page de manuel perf-list(1) pour plus de détails sur les modificateurs d'événement.
•un événement PMU formé symboliquement comme pmu/param1=0x3,param2/ où param1, param2, etc. sont définis comme des formats pour le PMU dans /sys/bus/event_source/devices/<pmu>/format/*.
•un événement formé symboliquement comme pmu/config=M,config1=N,config3=K/ 
où M, N, K sont des nombres (en format décimal, hexadécimal, octal). Les valeurs acceptables pour chaque 'config', 'config1' et 'config2' sont définies par les entrées correspondantes dans /sys/bus/event_source/devices/<pmu>/format/*
param1 et param2 sont définis comme des formats pour le PMU dans :
/sys/bus/event_source/devices/<pmu>/format/*
Il existe également certains paramètres qui ne sont pas définis dans .../<pmu>/format/*.
Ces paramètres peuvent être utilisés pour surcharger les valeurs de configuration par défaut par événement.
Voici quelques paramètres courants :
- 'period' : Définit la période d'échantillonnage de l'événement
- 'freq' : Définit la fréquence d'échantillonnage de l'événement
- 'time' : Désactive/active l'horodatage. Les valeurs acceptables sont 1 pour
          activer l'horodatage. 0 pour désactiver l'horodatage.
          La valeur par défaut est 1.
- 'call-graph' : Désactive/active le graphe d'appels. Les chaînes acceptables sont « fp » pour
               le mode FP, « dwarf » pour le mode DWARF, « lbr » pour le mode LBR et
               « no » pour désactiver le graphe d'appels.
- 'stack-size' : taille de la pile utilisateur pour le mode nain
- 'name' : Nom d'événement défini par l'utilisateur. Des apostrophes (') peuvent être utilisées pour
          échapper les symboles dans le nom du parsing par le shell et l'outil
          comme ceci : name=\'CPU_CLK_UNHALTED.THREAD:cmask=0x1\'.
- 'aux-output' : Génère des enregistrements AUX au lieu d'événements. Ceci nécessite
                qu'un événement de zone AUX soit également fourni.
- 'aux-action' : « pause » ou « resume » pour mettre en pause ou reprendre une zone AUX
                (le chef de groupe) lorsque cet événement se produit.
                « start-paused » sur un événement de zone AUX lui-même, démarrera
                en état de pause.
- 'aux-sample-size' : Définit la taille de l'échantillon pour l'échantillonnage de la zone AUX. Si
'--aux-sample' a été utilisé, définir aux-sample-size=0 pour désactiver
l'échantillonnage de zone AUX pour l'événement.
Voir la page de manuel linkperf:perf-list[1] pour plus de paramètres.
Remarque : Si l'utilisateur définit explicitement des options qui entrent en conflit avec les paramètres,
la valeur définie par les paramètres sera remplacée.
Sont également non définis dans .../<pmu>/format/* des paramètres de configuration spécifiques au pilote PMU.
Tout paramètre de configuration précédé de la lettre '@' n'est pas interprété dans l'espace utilisateur et est envoyé directement
au pilote PMU. Par exemple :
perf record -e some_event/@cfg1,@cfg2=config/ ...
verra 'cfg1' et 'cfg2=config' poussés vers le pilote PMU associé
à l'événement pour un traitement ultérieur. Il n'y a aucune restriction sur
les paramètres de configuration, tant que leur sémantique est comprise
et supportée par le pilote PMU.
•un événement de point d'arrêt matériel sous la forme \mem:addr[/len][:access] où addr est l'adresse mémoire sur laquelle vous voulez vous arrêter. Access est le type d'accès mémoire (lecture, écriture, exécution) ; il peut être passé comme suit : \mem:addr[:[r][w][x]]. len est la plage, le nombre d'octets à partir de l'addr spécifiée, que le point d'arrêt couvrira. Si vous voulez profiler les accès en lecture-écriture à 0x1000, définissez simplement mem:0x1000:rw. Si vous voulez profiler les accès en écriture dans [0x1000~1008), définissez simplement mem:0x1000/8:w.
•un groupe d'événements entouré d'une paire d'accolades ("{event1,event2,...}"). Chaque événement est séparé par des virgules et le groupe doit être mis entre guillemets pour éviter l'interprétation par le shell. Vous devez également utiliser --group sur « perf report » pour voir les événements de groupe ensemble.

--filter=<filtre>

Filtre d'événement. Cette option doit suivre un sélecteur d'événement (-e). Si l'événement est un point de trace, la chaîne de filtre sera analysée par le noyau. Si l'événement est un PMU de trace matériel (par exemple, Intel PT ou CoreSight), il sera traité comme un filtre d'adresse. Sinon, il signifie un filtre général utilisant BPF qui peut être appliqué à tout type d'événement.

L'utilisateur doit également demander la collecte de ces informations (avec
l'option -d dans le cas ci-dessus). Sinon, le message suivant sera affiché.
$ sudo perf record -e cycles --filter 'mem_op == load'

Essentiellement, l'expression du filtre BPF est :
<terme> <opérateur> <valeur> (("," | "||") <terme> <opérateur> <valeur>)*
Le <terme> peut être l'un des éléments suivants :
  ip, id, tid, pid, cpu, time, addr, period, txn, weight, phys_addr,
  code_pgsz, data_pgsz, weight1, weight2, weight3, ins_lat, retire_lat,
  p_stage_cyc, mem_op, mem_lvl, mem_snoop, mem_remote, mem_lock,
  mem_dtlb, mem_blk, mem_hops, uid, gid
L'<opérateur> peut être l'un des éléments suivants :
  ==, !=, >, >=, <, <=, &
La <valeur> peut être l'un des éléments suivants :
  <nombre> (pour n'importe quel terme)
  na, load, store, pfetch, exec (pour mem_op)
  l1, l2, l3, l4, cxl, io, any_cache, lfb, ram, pmem (pour mem_lvl)
  na, none, hit, miss, hitm, fwd, peer (pour mem_snoop)
  remote (pour mem_remote)
  na, locked (pour mem_locked)
  na, l1_hit, l1_miss, l2_hit, l2_miss, any_hit, any_miss, walk, fault (pour mem_dtlb)
  na, by_data, by_addr (pour mem_blk)
  hops0, hops1, hops2, hops3 (pour mem_hops)

--exclude-perf

N'enregistre pas les événements émis par perf lui-même. Cette option doit suivre un sélecteur d'événement (-e) qui sélectionne un ou plusieurs événements de trace. Elle ajoute une expression de filtre common_pid != $PERFPID aux filtres. S'il existe d'autres filtres --filter, le nouveau filtre sera combiné avec eux par &&.

--latency

Active la collecte de données pour le profilage de latence. Utilisez perf report --latency pour un profil centré sur la latence.

-a, --all-cpus

Collecte au niveau du système sur tous les cœurs CPU (par défaut si aucune cible n'est spécifiée).

-p, --pid=

Enregistre les événements sur un identifiant de processus existant (liste séparée par des virgules).

-t, --tid=

Enregistre les événements sur un identifiant de thread existant (liste séparée par des virgules). Cette option désactive également l'héritage par défaut. Activez-le en ajoutant --inherit.

-u, --uid=

Enregistre les événements dans les threads appartenant à l'uid. Nom ou numéro.

-r, --realtime=

Collecte les données avec cette priorité RT SCHED_FIFO.

--no-buffering

Collecte les données sans mise en mémoire tampon.

-c, --count=

Période d'échantillonnage de l'événement.

-o, --output=

Nom du fichier de sortie.

-i, --no-inherit

Les processus enfants n'héritent pas des compteurs.

-F, --freq=

Profile à cette fréquence. Utilisez max pour utiliser la fréquence maximale actuellement autorisée, c'est-à-dire la valeur du noyau sysctl kernel.perf_event_max_sample_rate. Réduira la fréquence à la valeur maximale autorisée actuellement. Voir --strict-freq.

--strict-freq

Échoue si la fréquence spécifiée ne peut pas être utilisée.

-m, --mmap-pages=

Nombre de pages de données mmap (doit être une puissance de deux) ou spécification de taille en octets avec un caractère d'unité ajouté - B/K/M/G. La taille est arrondie à la puissance de deux pages supérieure. En ajoutant une virgule, un paramètre supplémentaire avec la même sémantique que pour les zones mmap normales peut être spécifié pour la zone de traçage AUX.

-g

Active l'enregistrement des graphes d'appels (chaîne de pile/trace) pour l'espace noyau et l'espace utilisateur.

--call-graph

Configure et active l'enregistrement des graphes d'appels (chaîne de pile/trace), implique -g. Par défaut, c'est "fp" (pour l'espace utilisateur). 
La méthode de déroulement utilisée pour l'espace noyau dépend du
dérouleur utilisé par la configuration active du noyau, c'est-à-dire
CONFIG_UNWINDER_FRAME_POINTER (fp) ou CONFIG_UNWINDER_ORC (orc)
Toute option spécifiée ici contrôle la méthode utilisée pour l'espace
utilisateur.
Les options valides sont "fp" (pointeur de frame), "dwarf" (CFI de DWARF -
Informations sur le cadre d'appel) ou "lbr" (installation matérielle Last Branch
Record).
Dans certains systèmes, où les binaires sont compilés avec gcc
--fomit-frame-pointer, l'utilisation de la méthode "fp" produira de faux
graphes d'appels. L'utilisation de "dwarf", si disponible (outils perf liés
à la bibliothèque libunwind ou libdw), devrait être utilisée à la place.
L'utilisation de la méthode "lbr" ne nécessite aucune option de compilateur.
Elle produira des graphes d'appels à partir des registres LBR matériels. La
principale limitation est qu'elle n'est disponible que sur les nouvelles
plateformes Intel, telles que Haswell. Elle ne peut obtenir que la chaîne
d'appels utilisateur. Elle ne fonctionne pas avec l'échantillonnage de la
pile de branches en même temps.
Lorsque l'enregistrement "dwarf" est utilisé, perf enregistre également
(utilisateur) des dumps de pile lorsque ceux-ci sont échantillonnés. La taille
par défaut du dump de pile est de 8192 (octets). L'utilisateur peut changer la
taille en passant la taille après une virgule, comme
"--call-graph dwarf,4096".
Lorsque l'enregistrement "fp" est utilisé, perf essaie de sauvegarder des
entrées de pile jusqu'au nombre spécifié dans sysctl.kernel.perf_event_max_stack
par défaut. L'utilisateur peut changer le nombre en le passant après une
virgule, comme "--call-graph fp,32".

-q, --quiet

N'affiche aucun avertissement ou message, utile pour les scripts.

-v, --verbose

Soyez plus verbeux (affichez les erreurs d'ouverture de compteur, etc.).

-s, --stat

Enregistre les décomptes d'événements par thread. Utilisez-le avec perf report -T pour voir les valeurs.

-d, --data

Enregistre les adresses virtuelles d'échantillon. Implique --sample-mem-info.

--phys-data

Enregistre les adresses physiques d'échantillon.

--data-page-size

Enregistre la taille de la page de données de l'adresse de données échantillonnée.

--code-page-size

Enregistre la taille de page de l'adresse de code (ip) échantillonnée.

-T, --timestamp

Enregistre les horodatages d'échantillon. Utilisez-le avec perf report -D pour voir les horodatages, par exemple.

-P, --period

Enregistre la période d'échantillon.

--sample-cpu

Enregistre le CPU d'échantillon.

--sample-identifier

Enregistre l'identifiant d'échantillon, c'est-à-dire le bit PERF_SAMPLE_IDENTIFIER défini dans le membre sample_type de l'argument struct perf_event_attr pour l'appel système perf_event_open.

--sample-mem-info

Enregistre les informations sur la source de données d'échantillon pour les opérations mémoire. Nécessite le support matériel et peut ne fonctionner que sur des événements spécifiques. Envisagez d'utiliser perf mem record à la place si vous n'êtes pas sûr.

-n, --no-samples

Ne pas échantillonner.

-R, --raw-samples

Collecte les enregistrements d'échantillons bruts de tous les compteurs ouverts (par défaut pour les compteurs de tracepoints).

-C, --cpu

Collecte les échantillons uniquement sur la liste des CPUs fournie. Plusieurs CPUs peuvent être fournis sous forme de liste séparée par des virgules sans espace : 0,1. Les plages de CPUs sont spécifiées avec - : 0-2. En mode par thread avec le mode héritage activé (par défaut), les échantillons sont capturés uniquement lorsque le thread s'exécute sur les CPUs désignés. Par défaut, tous les CPUs sont surveillés.

Les processus de l'espace utilisateur peuvent migrer entre les CPUs, donc lors du traçage de CPUs sélectionnés, un événement factice est créé pour suivre la bande latérale pour tous les CPUs.

-B, --no-buildid

Ne pas enregistrer les identifiants de construction des binaires dans les fichiers perf.data. Cela permet d'éviter le post-traitement après l'enregistrement, ce qui rend parfois la dernière étape du processus d'enregistrement longue, car elle doit traiter tous les événements à la recherche d'enregistrements mmap. Le revers est que cela peut mal résoudre les symboles si les binaires de la charge de travail utilisés lors de l'enregistrement sont recompilés ou mis à niveau localement, car la seule clé disponible dans ce cas est le nom du chemin. Vous pouvez également définir la variable de configuration "record.build-id" sur "skip" pour avoir ce comportement en permanence.

-N, --no-buildid-cache

Ne pas mettre à jour le cache des identifiants de construction. Cela permet d'économiser une certaine surcharge dans les situations où les informations du fichier perf.data (qui incluent les identifiants de construction) sont suffisantes. Vous pouvez également définir la variable de configuration "record.build-id" sur no-cache pour obtenir le même effet.

-G name,..., --cgroup name,...

Surveille uniquement dans le conteneur (cgroup) appelé "name". Cette option n'est disponible qu'en mode par cœur CPU. Le système de fichiers cgroup doit être monté. Tous les threads appartenant au conteneur "name" sont surveillés lorsqu'ils s'exécutent sur les cœurs CPU surveillés. Plusieurs cgroups peuvent être fournis. Chaque cgroup s'applique à l'événement correspondant, c'est-à-dire le premier cgroup au premier événement, le second cgroup au second événement, et ainsi de suite. Il est possible de fournir un cgroup vide (surveillance permanente) en utilisant, par exemple, -G foo,,bar. Les cgroups doivent avoir des événements correspondants, c'est-à-dire qu'ils se réfèrent toujours aux événements définis précédemment sur la ligne de commande. Si l'utilisateur souhaite suivre plusieurs événements pour un cgroup spécifique, il peut utiliser -e e1 -e e2 -G foo,foo ou simplement -e e1 -e e2 -G foo.

Si vous souhaitez surveiller, par exemple, cycles pour un cgroup et aussi pour l'ensemble du système, cette ligne de commande peut être utilisée : perf stat -e cycles -G cgroup_name -a -e cycles.

-b, --branch-any

Active l'échantillonnage des piles de branches prises. Tout type de branche prise peut être échantillonné. C'est un raccourci pour --branch-filter any. Voir --branch-filter pour plus d'informations.

-j, --branch-filter

Active l'échantillonnage des piles de branches prises. Chaque échantillon capture une série de branches prises consécutives. Le nombre de branches capturées avec chaque échantillon dépend du matériel sous-jacent, du type de branches d'intérêt et du code exécuté. Il est possible de sélectionner les types de branches capturées en activant des filtres. Les filtres suivants sont définis :
•any: tout type de branche
•any_call: tout appel de fonction ou appel système
•any_ret: tout retour de fonction ou retour d'appel système
•ind_call: tout branchement indirect
•ind_jmp: tout saut indirect
•call: appels directs, y compris les appels lointains (vers/depuis le noyau)
•u: uniquement lorsque la cible du branchement est au niveau utilisateur
•k: uniquement lorsque la cible du branchement est dans le noyau
•hv: uniquement lorsque la cible est au niveau de l'hyperviseur
•in_tx : uniquement lorsque la cible est dans une transaction matérielle
•no_tx : uniquement lorsque la cible n’est pas dans une transaction matérielle
•abort_tx : uniquement lorsque la cible est une interruption de transaction matérielle
•cond : branches conditionnelles
•call_stack : enregistrer la pile d’appels
•no_flags : ne pas enregistrer les indicateurs de branchement (par exemple, prédiction, mauvaise prédiction, etc.)
•no_cycles : ne pas enregistrer les cycles de branchement
•hw_index : enregistrer l’index matériel du branchement
•save_type : enregistrer le type de branchement lors de l’échantillonnage si le binaire n’est pas disponible ultérieurement. Pour les plates-formes prenant en charge la pile LBR d’Intel Arch (génération 12+ client ou serveur Xeon 4ème génération+), le type de branchement enregistré est activé sans condition lorsque l’échantillonnage de la pile de branchements pris est activé.
•priv : enregistrer l’état de privilège lors de l’échantillonnage si le binaire n’est pas disponible ultérieurement
•counter : enregistrer le nombre d’occurrences de l’événement depuis la dernière entrée de branchement. Actuellement, cette fonctionnalité n’est prise en charge que par un CPU plus récent, par exemple, les plates-formes Intel Sierra Forest et ultérieures. Une erreur est attendue si elle est utilisée sur un noyau ou des CPU non pris en charge.

L’option nécessite au moins un type de branchement parmi any, any_call, any_ret, ind_call, cond. Les niveaux de privilège peuvent être omis, auquel cas les niveaux de privilège de l’événement associé sont appliqués au filtre de branchement. Les niveaux de privilège du noyau (k) et de l’hyperviseur (hv) sont soumis aux autorisations. Lors de l’échantillonnage sur plusieurs événements, l’échantillonnage de la pile de branchements est activé pour tous les événements d’échantillonnage. Le type de branchement échantillonné est le même pour tous les événements. Les différents filtres doivent être spécifiés sous forme de liste séparée par des virgules : --branch-filter any_ret,u,k. Notez que cette fonctionnalité peut ne pas être disponible sur tous les processeurs.

-W, --weight

Active l’échantillonnage pondéré. Un poids supplémentaire est enregistré par échantillon et peut être affiché avec les clés de tri weight et local_weight. Cela fonctionne actuellement pour les événements d’interruption TSX et certains événements mémoire en mode précis sur les CPU Intel modernes.

--namespaces

Enregistre les événements de type PERF_RECORD_NAMESPACES. Cela active la clé de tri cgroup_id.

--all-cgroups

Enregistre les événements de type PERF_RECORD_CGROUP. Cela active la clé de tri cgroup.

--transaction

Enregistre les indicateurs de transaction pour les événements liés aux transactions.

--per-thread

Utilise les mmaps par thread. Par défaut, des mmaps par cœur sont créés. Cette option remplace ce comportement et utilise des mmaps par thread. Un effet secondaire est que l’héritage est automatiquement désactivé. --per-thread est ignoré avec un avertissement s’il est combiné avec les options -a ou -C.

-D, --delay=

Après avoir démarré le programme, attendez msec avant de mesurer (-1 : démarrage avec les événements désactivés), ou activez les événements uniquement pour des plages de msec spécifiées (par exemple, -D 10-20,30-40 signifie attendre 10 msec, activer pendant 10 msec, attendre 10 msec, activer pendant 10 msec, puis arrêter). Notez que le retardement de l’activation des événements est utile pour filtrer la phase de démarrage du programme, qui est souvent très différente.

-I, --intr-regs

Capture l’état de la machine (registres) à l’interruption, c’est-à-dire lors des débordements de compteur pour chaque échantillon. La liste des registres capturés dépend de l’architecture. Cette option est désactivée par défaut. Il est possible de sélectionner les registres à échantillonner en utilisant leurs noms symboliques, par exemple sur x86, ax, si. Pour lister les registres disponibles, utilisez --intr-regs=\?. Pour nommer les registres, passez une liste séparée par des virgules telle que --intr-regs=ax,bx. La liste des registres dépend de l’architecture.

--user-regs

Similaire à -I, mais capture les registres utilisateur au moment de l’échantillon. Pour lister les registres utilisateur disponibles, utilisez --user-regs=\?.

--running-time

Enregistre le temps d’exécution et le temps activé pour les événements de lecture (:S)

-k, --clockid

Définit l’ID de l’horloge à utiliser pour les différents champs temporels dans les enregistrements de type perf_event_type. Voir clock_gettime(). En particulier, CLOCK_MONOTONIC et CLOCK_MONOTONIC_RAW sont pris en charge, certains événements peuvent également autoriser CLOCK_BOOTTIME, CLOCK_REALTIME et CLOCK_TAI.

-S, --snapshot

Sélectionne le mode instantané de traçage de la zone AUX. Cette option n’est valide qu’avec un événement de traçage de zone AUX. Facultativement, certains paramètres de capture d’instantané peuvent être spécifiés dans une chaîne qui suit cette option :
• e : prendre un dernier instantané à la sortie ; garantit qu’il y a au moins un instantané dans le fichier de sortie ;
•<size> : si le PMU prend en charge cela, spécifiez la taille d’instantané souhaitée.

En mode instantané, les données de traçage ne sont capturées que lorsqu’un signal SIGUSR2 est reçu et à la sortie si l’option e ci-dessus est donnée.

--aux-sample[=OPTIONS]

Sélectionne l’échantillonnage de la zone AUX. Au moins un des événements sélectionnés par l’option -e doit être un événement de zone AUX. Des échantillons sur d’autres événements seront créés contenant des données de la zone AUX. La taille de l’échantillon peut éventuellement être spécifiée, sinon elle est par défaut à 4 Kio.

--proc-map-timeout

Lors du traitement des threads préexistants /proc/XXX/mmap, cela peut prendre beaucoup de temps, car le fichier peut être énorme. Un délai d’attente est nécessaire dans de tels cas. Cette option définit la limite de délai d’attente. La valeur par défaut est de 500 ms.

--switch-events

Enregistre les événements de commutation de contexte, c’est-à-dire les événements de type PERF_RECORD_SWITCH ou PERF_RECORD_SWITCH_CPU_WIDE. Dans certains cas (par exemple, Intel PT, CoreSight ou Arm SPE), les événements de commutation seront activés automatiquement, ce qui peut être supprimé par l’option --no-switch-events.

--vmlinux=PATH

Spécifie le chemin vmlinux qui a les informations de débogage. (activé lorsque le prologue BPF est activé)

--buildid-all

Enregistre l’ID de construction de tous les DSOs, qu’il soit effectivement atteint ou non.

--buildid-mmap

Ancienne option d’enregistrement de l’ID de construction dans les événements de carte, qui est maintenant la valeur par défaut. Se comporte de manière identique à --no-buildid. Désactivez avec --no-buildid-mmap.

--aio[=n]

Utilise <n> blocs de contrôle en mode d’écriture de traçage asynchrone (Posix AIO) (par défaut : 1, max : 4). Le mode asynchrone n’est pris en charge que lors de la liaison de l’outil Perf avec la bibliothèque libc fournissant une implémentation de l’API Posix AIO.

--affinity=mode

Définit le masque d’affinité du thread de lecture de traçage selon la politique définie par la valeur mode :
•node - le masque CPU du nœud NUMA du tampon mmap traité est défini pour l’affinité du thread
•cpu - le masque CPU du tampon mmap traité est défini pour l’affinité du thread

--mmap-flush=number

Spécifie le nombre minimal d’octets extraits des pages de données mmap et traités pour la sortie. On peut spécifier le nombre en utilisant les suffixes B/K/M/G.

La valeur maximale autorisée est d’un quart de la taille des pages de données mmapées.

La valeur par défaut de l’option est de 1 octet, ce qui signifie que chaque fois que le thread d’écriture de sortie trouve de nouvelles données dans le tampon mmapé, les données sont extraites, éventuellement compressées (-z) et écrites dans la sortie, perf.data ou le pipe.

Les gros morceaux de données sont compressés plus efficacement que les petits morceaux, de sorte que l’extraction de gros morceaux des pages de données mmapées est préférable du point de vue de la réduction de la taille de sortie.

De plus, dans certains cas, l’exécution de moins d’appels système d’écriture de sortie avec une taille de données plus importante peut prendre moins de temps que l’exécution de plus d’appels système d’écriture de sortie avec une taille de données plus petite, réduisant ainsi la surcharge de profilage d’exécution.

-z, --compression-level[=n]

Produit une traçage compressé en utilisant le niveau spécifié n (par défaut : 1 - compression la plus rapide, 22 - traçage le plus petit)

--all-kernel

Configure tous les événements utilisés pour s’exécuter dans l’espace noyau.

--all-user

Configure tous les événements utilisés pour s’exécuter dans l’espace utilisateur.

--kernel-callchains

Collecte les chaînes d’appels uniquement à partir de l’espace noyau. C’est-à-dire que cette option définit perf_event_attr.exclude_callchain_user à 1.

--user-callchains

Collecte les chaînes d’appels uniquement à partir de l’espace utilisateur. C’est-à-dire que cette option définit perf_event_attr.exclude_callchain_kernel à 1.

N’utilisez pas simultanément --kernel-callchains et --user-callchains, sinon aucune chaîne d’appels ne sera collectée.

--timestamp-filename Ajoute un horodatage au nom du fichier de sortie.

--timestamp-boundary

Enregistre la limite d’horodatage (heure des premiers/derniers échantillons).

--switch-output[=mode]

Génère plusieurs fichiers perf.data, préfixés par un horodatage, en passant à un nouveau fichier en fonction de la valeur mode :
•« signal » - lors de la réception d’un SIGUSR2 (valeur par défaut) ou
•<size> - lors de l’atteinte du seuil de taille, la taille est attendue comme un nombre avec un caractère d’unité ajouté - B/K/M/G
•<time> - lors de l’atteinte du seuil de temps, la taille est attendue comme un nombre avec un caractère d’unité ajouté - s/m/h/d 
Note : la précision du seuil de taille dépend énormément de votre configuration - le nombre et la taille de vos tampons circulaires (-m). Elle est généralement plus précise pour les tailles plus élevées (comme >5M), pour les valeurs plus basses, attendez-vous à des tailles différentes.

Un cas d’utilisation possible est de, lors d’un événement externe, découper le fichier perf.data qui est ensuite traité, éventuellement via un script perf, pour décider si ce cliché perf.data particulier doit être conservé ou non.

Implique --timestamp-filename, --no-buildid et --no-buildid-cache. La raison de ces deux derniers est de réduire la surcharge de commutation de fichier de données. Vous pouvez toujours les activer avec :

--switch-output --no-no-buildid  --no-no-buildid-cache

--switch-output-event

Événements qui entraîneront la commutation du fichier perf.data, sélectionnant automatiquement --switch-output=signal. Les résultats sont similaires car en interne le thread de bande latérale enverra également un SIGUSR2 au thread principal.

Utilise la même syntaxe que --event, il ne sera tout simplement pas enregistré, servant uniquement à basculer le fichier perf.data dès que l’événement --switch-output est traité par un thread de bande latérale séparé.

Ce thread de bande latérale est également utilisé à d’autres fins, comme le traitement des enregistrements PERF_RECORD_BPF_EVENT au fur et à mesure qu’ils se produisent, demandant au noyau des informations BPF supplémentaires, etc.

--switch-max-files=N

Lors de la rotation de perf.data avec --switch-output, ne conservez que N fichiers.

--dry-run

Analyse les options puis quitte. --dry-run peut être utilisé pour détecter des erreurs dans les options de la ligne de commande.

perf record --dry-run -e peut agir comme un compilateur de script BPF si llvm.dump-obj dans

le fichier de configuration est défini sur true.

--synth=TYPE

Collecte et synthétise le type d'événements donné (séparé par des virgules). Notez que cette option contrôle la synthèse à partir du système de fichiers /proc, qui représente l'état des tâches pour les threads préexistants.

Les événements du noyau (et certains autres) sont enregistrés indépendamment du choix de cette option. Par exemple, --synth=no aurait des événements MMAP pour le noyau et les modules.

Les types disponibles sont :

•task - synthétise les événements FORK et COMM pour chaque tâche
•mmap - synthétise les événements MMAP pour chaque processus (implique task)
•cgroup - synthétise les événements CGROUP pour chaque cgroup
•all - synthétise tous les événements (par défaut)
•no - ne synthétise aucun des événements ci-dessus.

--tail-synthesize

Au lieu de collecter les événements non échantillonnés (par exemple, fork, comm, mmap) au début de l'enregistrement, collecte-les lors de la finalisation d'un fichier de sortie. Les événements non échantillonnés collectés reflètent l'état du système lorsque l'enregistrement est terminé.

--overwrite

Fait en sorte que tous les événements utilisent un tampon circulaire écrasable. Un tampon circulaire écrasable fonctionne comme un enregistreur de vol : lorsqu'il est plein, le noyau écrase les enregistrements les plus anciens, qui n'atteindront donc jamais le fichier perf.data.

Lorsque --overwrite et --switch-output sont utilisés, perf enregistre et ignore les événements jusqu'à ce qu'il reçoive un signal, indiquant que quelque chose d'inhabituel a été détecté et justifie la prise d'un instantané des événements les plus récents, ceux qui tiennent dans le tampon circulaire à ce moment-là.

L'attribut overwrite peut également être défini ou annulé pour un événement à l'aide de termes de configuration. Par exemple : cycles/overwrite/ et instructions/no-overwrite/.

Implique --tail-synthesize.

--kcore

Crée une copie de /proc/kcore et la place dans un répertoire avec le fichier de données perf.

--max-size=<size>

Limite la taille maximale des données d'échantillon, <size> est attendu comme un nombre avec un caractère d'unité ajouté - B/K/M/G

--num-thread-synthesize

Le nombre de threads à exécuter lors de la synthèse des événements pour les processus existants. Par défaut, le nombre de threads est égal à 1.

--pfm-events events

Sélectionne un événement PMU en utilisant la syntaxe libpfm4 (voir http://perfmon2.sf.net) y compris la prise en charge des filtres d'événements. Par exemple --pfm-events inst_retired:any_p:u:c=1:i. Plusieurs événements peuvent être passés à l'option en utilisant le séparateur virgule. Les événements matériels et les événements matériels génériques ne peuvent pas être mélangés. Ces derniers doivent être utilisés avec l'option -e. L'option -e et celle-ci peuvent être combinées. Les événements peuvent être regroupés à l'aide de la notation {}.

--control=fifo:ctl-fifo[,ack-fifo], --control=fd:ctl-fd[,ack-fd]

ctl-fifo / ack-fifo sont ouverts et utilisés comme ctl-fd / ack-fd comme suit. Écoute sur le descripteur ctl-fd pour les commandes de contrôle de la mesure.

Commandes disponibles :

•enable : activer les événements
•disable : désactiver les événements
•enable name : activer l'événement name
•disable name : désactiver l'événement name
•snapshot : instantané de traçage de la zone AUX).
•stop : arrêter l'enregistrement perf
•ping : ping
•'evlist [-v|-g|-F] : afficher tous les événements 
-F  Affiche uniquement la fréquence d'échantillonnage utilisée pour chaque événement.
-v  Affiche tous les champs.
-g  Affiche les informations de groupe d'événements.

Les mesures peuvent être démarrées avec des événements désactivés en utilisant l'option --delay=-1. Optionnellement, envoyez une confirmation de commande de contrôle (ack\n) au descripteur ack-fd pour synchroniser avec le processus de contrôle. Exemple de script shell bash pour activer et désactiver les événements pendant les mesures :

#!/bin/bash
ctl_dir=/tmp/
ctl_fifo=${ctl_dir}perf_ctl.fifo
test -p ${ctl_fifo} && unlink ${ctl_fifo}
mkfifo ${ctl_fifo}
exec {ctl_fd}<>${ctl_fifo}
ctl_ack_fifo=${ctl_dir}perf_ctl_ack.fifo
test -p ${ctl_ack_fifo} && unlink ${ctl_ack_fifo}
mkfifo ${ctl_ack_fifo}
exec {ctl_fd_ack}<>${ctl_ack_fifo}
perf record -D -1 -e cpu-cycles -a \
            --control fd:${ctl_fd},${ctl_fd_ack} \
            -- sleep 30 &
perf_pid=$!
sleep 5  && echo 'enable' >&${ctl_fd} && read -u ${ctl_fd_ack} e1 && echo "enabled(${e1})"
sleep 10 && echo 'disable' >&${ctl_fd} && read -u ${ctl_fd_ack} d1 && echo "disabled(${d1})"
exec {ctl_fd_ack}>&-
unlink ${ctl_ack_fifo}
exec {ctl_fd}>&-
unlink ${ctl_fifo}
wait -n ${perf_pid}
exit $?

--threads=<spec>

Écrit les données de trace collectées dans plusieurs fichiers de données à l'aide de threads parallèles. La valeur <spec> peut être une liste définie par l'utilisateur de masques. Les masques séparés par des deux-points définissent les cœurs à surveiller par un thread et le masque d'affinité de ce thread est séparé par une barre oblique : 
<masque de cœurs 1>/<masque d'affinité 1>:<masque de cœurs 2>/<masque d'affinité 2>:...

Les masques de cœurs ou d'affinité ne doivent pas chevaucher d'autres masques correspondants. Les cœurs invalides sont ignorés, mais les masques ne contenant que des cœurs invalides ne sont pas autorisés.

Par exemple, une spécification utilisateur comme suit :

0,2-4/2-4:1,5-7/5-7

spécifie une disposition de threads parallèles composée de deux threads, le premier thread surveille les cœurs 0 et 2-4 avec le masque d'affinité 2-4, le second surveille les cœurs 1 et 5-7 avec le masque d'affinité 5-7.

<spec> La valeur peut également être une chaîne signifiant une disposition de threads parallèles prédéfinie :

•cpu - crée un nouveau thread de flux de données pour chaque CPU surveillé
•core - crée un nouveau thread pour surveiller les CPU groupés par un cœur
•package - crée un nouveau thread pour surveiller les CPU groupés par un package
•numa - crée un nouveau thread pour surveiller les CPU groupés par un domaine NUMA

Les dispositions prédéfinies peuvent être utilisées sur des systèmes avec un grand nombre de CPU afin de ne pas lancer plusieurs threads de flux par CPU, mais d'éviter tout de même les événements PERDUS dans les fichiers du répertoire de données. L'option spécifiée avec une valeur nulle ou vide utilise par défaut la disposition CPU. Les masques définis ou fournis par la valeur de l'option sont filtrés par le masque fourni par l'option -C.

--debuginfod[=URLs]

Spécifie l'URL debuginfod à utiliser lors de la mise en cache des binaires perf.data, il suit la même syntaxe que la variable DEBUGINFOD_URLS, comme :
http://192.168.122.174:8002 
Si les URLs ne sont pas spécifiées, la valeur de la variable d'environnement système DEBUGINFOD_URLS est utilisée.

--off-cpu

Active le profilage hors CPU avec BPF. Le programme BPF collectera les informations de planification des tâches avec (la pile d'appels utilisateur) et les enregistrera comme données d'échantillon d'un événement logiciel nommé "offcpu-time". La période d'échantillon aura le temps pendant lequel la tâche a dormi en nanosecondes. 
Notez que BPF ne peut collecter des traces de pile qu'en utilisant le pointeur de trame ("fp") pour le moment. Les applications compilées sans le pointeur de trame peuvent donc afficher des adresses erronées.
Le profilage hors CPU se compose de deux types d'échantillons : les échantillons directs, qui partagent le même comportement que les échantillons réguliers, et les échantillons accumulés, stockés dans la carte des piles BPF, présentés après tous les échantillons réguliers.

--off-cpu-thresh

Une fois que le temps hors CPU d'une tâche atteint ce seuil (en millisecondes), il génère un échantillon hors CPU direct. La valeur par défaut est 500 ms.

--setup-filter=<action>

Prépare un filtre BPF à être utilisé par les utilisateurs réguliers. L'action doit être soit "pin", soit "unpin". Le filtre peut être utilisé après avoir été épinglé.

SUPPORT DES HYBRIDES INTEL

Support des événements hybrides Intel dans les outils perf.

Pour certaines plateformes Intel, comme AlderLake, qui est une plateforme hybride et se compose de CPU atom et de CPU core. Chaque CPU a une liste d'événements dédiée. Une partie des événements est disponible sur le CPU core, une partie est disponible sur le CPU atom et même une partie est disponible sur les deux.

Le noyau exporte deux nouveaux PMU CPU via sysfs : /sys/bus/event_source/devices/cpu_core /sys/bus/event_source/devices/cpu_atom

Les fichiers cpus sont créés dans les répertoires. Par exemple,

cat /sys/bus/event_source/devices/cpu_core/cpus 0-15

cat /sys/bus/event_source/devices/cpu_atom/cpus 16-23

Cela indique que les CPU 0-15 sont des CPU core et les CPU 16-23 sont des CPU atom.

Comme auparavant, utilisez perf-list pour lister l'événement symbolique.

perf list

inst_retired.any [Fixed Counter: Compte le nombre d'instructions exécutées. Unité : cpu_atom] inst_retired.any [Nombre d'instructions exécutées. Compteur fixe - événement architectural. Unité : cpu_core]

La mention Unité : xxx est ajoutée à la brève description pour indiquer à quel PMU appartient l'événement. Le même nom d'événement mais avec un PMU différent peut être pris en charge.

Activer l'événement hybride avec un PMU spécifique

Pour activer un événement uniquement pour le core ou uniquement pour l'atom, la syntaxe suivante est prise en charge :

        cpu_core/<nom de l'événement>/
ou
        cpu_atom/<nom de l'événement>/

Par exemple, compter l'événement cycles sur les CPU core.

perf stat -e cpu_core/cycles/

Créer automatiquement deux événements pour un événement matériel

Lors de la création d'un événement et que celui-ci est disponible à la fois sur atom et sur core, deux événements sont créés automatiquement. L'un est pour atom, l'autre est pour core. La plupart des événements matériels et des événements de cache sont disponibles sur cpu_core et cpu_atom.

Pour les événements matériels, ils ont des configurations prédéfinies (par exemple, 0 pour cycles). Mais sur une plateforme hybride, le noyau doit savoir d'où provient l'événement (de l'atom ou du core). Le type d'événement d'origine PERF_TYPE_HARDWARE ne peut pas transporter d'informations PMU. Ce type est donc maintenant étendu pour être un type conscient du PMU. L'ID du type PMU est stocké dans attr.config[63:32].

perf-record(1) — Arch Linux

NAME

perf-record

record:

SYNOPSIS

perf record

[-e event[,event]...] [--] [record options] [-- program [program options]]

DESCRIPTION

This command records and analyzes dynamic program behavior, like the call graph, CPU cache misses, branch mispredictions, and total load/store operations.

The perf tool provides simple and unified access to advanced performance monitoring hardware capabilities of modern processors.

This man page is the documentation for the perf-record command.

OPTIONS

The recording options are detailed in perf-record(1).

INTEL HYBRID SUPPORT

The MU type ID is retrieved from sysfs. /sys/bus/event_source/devices/cpu_atom/type /sys/bus/event_source/devices/cpu_core/type

The new attr.config layout for PERF_TYPE_HARDWARE:

PERF_TYPE_HARDWARE: 0xEEEEEEEE000000AA AA: hardware event ID EEEEEEEE: PMU type ID

Cache event is similar. The type PERF_TYPE_HW_CACHE is extended to be PMU aware type. The PMU type ID is stored at attr.config[63:32].

The new attr.config layout for PERF_TYPE_HW_CACHE:

PERF_TYPE_HW_CACHE: 0xEEEEEEEE00DDCCBB BB: hardware cache ID CC: hardware cache op ID DD: hardware cache op result ID EEEEEEEE: PMU type ID

When enabling a hardware event without specified pmu, such as, perf stat -e cycles -a (use system-wide in this example), two events are created automatically.

------------------------------------------------------------
perf_event_attr:
  size                             120
  config                           0x400000000
  sample_type                      IDENTIFIER
  read_format                      TOTAL_TIME_ENABLED|TOTAL_TIME_RUNNING
  disabled                         1
  inherit                          1
  exclude_guest                    1
------------------------------------------------------------

and

------------------------------------------------------------
perf_event_attr:
  size                             120
  config                           0x800000000
  sample_type                      IDENTIFIER
  read_format                      TOTAL_TIME_ENABLED|TOTAL_TIME_RUNNING
  disabled                         1
  inherit                          1
  exclude_guest                    1
------------------------------------------------------------

type 0 is PERF_TYPE_HARDWARE. 0x4 in 0x400000000 indicates it’s cpu_core pmu. 0x8 in 0x800000000 indicates it’s cpu_atom pmu (atom pmu type id is random).

The kernel creates cycles (0x400000000) on cpu0-cpu15 (core cpus), and create cycles (0x800000000) on cpu16-cpu23 (atom cpus).

For perf-stat result, it displays two events:

Performance counter stats for 'system wide':
6,744,979      cpu_core/cycles/
1,965,552      cpu_atom/cycles/

The first cycles is core event, the second cycles is atom event.

Thread mode example:

perf-stat reports the scaled counts for hybrid event and with a percentage displayed. The percentage is the event’s running time/enabling time.

One example, triad_loop runs on cpu16 (atom core), while we can see the scaled value for core cycles is 160,444,092 and the percentage is 0.47%.

perf stat -e cycles -- taskset -c 16 ./triad_loop

As previous, two events are created.

.ft C
perf_event_attr:
  size                             120
  config                           0x400000000
  sample_type                      IDENTIFIER
  read_format                      TOTAL_TIME_ENABLED|TOTAL_TIME_RUNNING
  disabled                         1
  inherit                          1
  enable_on_exec                   1
  exclude_guest                    1
.ft

and

.ft C
perf_event_attr:
  size                             120
  config                           0x800000000
  sample_type                      IDENTIFIER
  read_format                      TOTAL_TIME_ENABLED|TOTAL_TIME_RUNNING
  disabled                         1
  inherit                          1
  enable_on_exec                   1
  exclude_guest                    1
.ft
Performance counter stats for 'taskset -c 16 ./triad_loop':
233,066,666      cpu_core/cycles/                                              (0.43%)
604,097,080      cpu_atom/cycles/                                              (99.57%)

perf-record:

If there is no -e specified in perf record, on hybrid platform, it creates two default cycles and adds them to event list. One is for core, the other is for atom.

perf-stat:

If there is no -e specified in perf stat, on hybrid platform, besides of software events, following events are created and added to event list in order.

cpu_core/cycles/, cpu_atom/cycles/, cpu_core/instructions/, cpu_atom/instructions/, cpu_core/branches/, cpu_atom/branches/, cpu_core/branch-misses/, cpu_atom/branch-misses/

Of course, both perf-stat and perf-record support to enable hybrid event with a specific pmu.

e.g. perf stat -e cpu_core/cycles/ perf stat -e cpu_atom/cycles/ perf stat -e cpu_core/r1a/ perf stat -e cpu_atom/L1-icache-loads/ perf stat -e cpu_core/cycles/,cpu_atom/instructions/ perf stat -e {cpu_core/cycles/,cpu_core/instructions/}

But {cpu_core/cycles/,cpu_atom/instructions/} will return warning and disable grouping, because the pmus in group are not matched (cpu_core vs. cpu_atom).
