PERLPORT(1perl) Guide du programmeur Perl PERLPORT(1perl)

NOM

perlport - Écrire du Perl portable

DESCRIPTION

Perl fonctionne sur de nombreux systèmes d'exploitation. Bien que la plupart d'entre eux partagent beaucoup de points communs, ils ont aussi leurs propres caractéristiques uniques.

Ce document est destiné à vous aider à découvrir ce qui constitue un code Perl portable. De cette façon, une fois que vous décidez d'écrire de manière portable, vous saurez où se situent les limites, et vous pourrez les respecter.

Il y a un compromis entre tirer pleinement parti d'un type particulier d'ordinateur et tirer parti d'une gamme complète d'entre eux. Naturellement, à mesure que vous élargissez votre gamme et devenez plus diversifié, les facteurs communs diminuent, et vous vous retrouvez avec une zone de terrain commun de plus en plus petite dans laquelle vous pouvez opérer pour accomplir une tâche particulière. Ainsi, lorsque vous commencez à aborder un problème, il est important de considérer sous quelle partie de la courbe de compromis vous souhaitez opérer. Spécifiquement, vous devez décider s'il est important que la tâche que vous codez ait la pleine généralité d'être portable, ou si elle doit simplement accomplir le travail tout de suite. C'est le choix le plus difficile à faire. Le reste est facile, car Perl offre de nombreux choix, quelle que soit la manière dont vous souhaitez aborder votre problème.

Vu autrement, écrire du code portable consiste généralement à limiter volontairement vos choix disponibles. Naturellement, cela demande de la discipline et des sacrifices. Le produit de la portabilité et de la commodité peut être une constante. Vous avez été prévenu.

Soyez conscient de deux points importants :

Pas tous les programmes Perl doivent être portables
Il n'y a aucune raison pour laquelle vous ne devriez pas utiliser Perl comme langage pour relier des outils Unix, ou pour prototyper une application Macintosh, ou pour gérer le registre Windows. S'il n'y a pas lieu de viser la portabilité pour une raison ou une autre dans un programme donné, alors ne vous en souciez pas.
Presque tout Perl est *déjà* portable
Ne vous laissez pas tromper en pensant qu'il est difficile de créer du code Perl portable. Ça ne l'est pas. Perl fait de son mieux pour combler les lacunes entre ce qui est disponible sur différentes plateformes, et tous les moyens disponibles pour utiliser ces fonctionnalités. Ainsi, presque tout le code Perl s'exécute sur n'importe quelle machine sans modification. Mais il y a quelques problèmes importants dans l'écriture de code portable, et ce document concerne entièrement ces problèmes.

Voici la règle générale : lorsque vous abordez une tâche couramment effectuée sur une gamme complète de plateformes, pensez à écrire du code portable. De cette façon, vous ne sacrifiez pas grand-chose en termes de choix d'implémentation dont vous pouvez disposer, et en même temps, vous pouvez offrir à vos utilisateurs un grand choix de plateformes. D'autre part, lorsque vous devez tirer parti d'une fonctionnalité unique d'une plateforme particulière, comme c'est souvent le cas en programmation système (que ce soit pour Unix, Windows, VMS, etc.), envisagez d'écrire du code spécifique à la plateforme.

Lorsque le code ne s'exécutera que sur deux ou trois systèmes d'exploitation, vous devrez peut-être ne considérer que les différences entre ces systèmes particuliers. L'important est de décider où le code s'exécutera et d'être délibéré dans votre décision.

Le matériel ci-dessous est divisé en trois sections principales : les problèmes majeurs de portabilité ("ISSUES"), les problèmes spécifiques à la plateforme ("PLATFORMS"), et les fonctions Perl intégrées qui se comportent différemment sur divers ports ("FUNCTION IMPLEMENTATIONS").

Ces informations ne doivent pas être considérées comme complètes ; elles incluent des informations potentiellement temporaires sur les idiosyncrasies de certains ports, dont la quasi-totalité sont en constante évolution. Par conséquent, ce matériel doit être considéré comme un travail en cours perpétuel ("<IMG SRC="yellow_sign.gif" ALT="En construction">").

PROBLÈMES

Nouvelles lignes

Dans la plupart des systèmes d'exploitation, les lignes dans les fichiers sont terminées par des nouvelles lignes. Ce qui est utilisé comme nouvelle ligne peut varier d'un système d'exploitation à l'autre. Unix utilise traditionnellement "\012", un type d'E/S de type DOS utilise "\015\012", Mac OS utilise "\015", et z/OS utilise "\025".

Perl utilise "\n" pour représenter la nouvelle ligne "logique", où ce qui est logique peut dépendre de la plateforme utilisée. Dans MacPerl, "\n" signifie toujours "\015". Sur les plateformes EBCDIC, "\n" pourrait être "\025" ou "\045". Dans les perls de type DOS, "\n" signifie généralement "\012", mais lors de l'accès à un fichier en mode "texte", perl utilise la couche ":crlf" qui le traduit vers (ou depuis) "\015\012", selon que vous lisez ou écrivez. Unix fait de même sur les terminaux en mode canonique. "\015\012" est couramment appelé CRLF.

Pour supprimer les nouvelles lignes de fin de texte, utilisez "chomp". Avec les paramètres par défaut, cette fonction recherche un caractère "\n" final et supprime ainsi de manière portable.

Lors du traitement de fichiers binaires (ou de fichiers texte en mode binaire), assurez-vous de définir explicitement $/ sur la valeur appropriée pour votre format de fichier avant d'utiliser "chomp".

En raison de la traduction en mode "texte", les perls de type DOS ont des limitations dans l'utilisation de "seek" et "tell" sur un fichier accédé en mode "texte". Restez-en à "seek"er vers des emplacements obtenus de "tell" (et aucun autre), et vous êtes généralement libre d'utiliser "seek" et "tell" même en mode "texte". L'utilisation de "seek", "tell" ou d'autres opérations de fichier peut ne pas être portable. Si vous utilisez "binmode" sur un fichier, cependant, vous pouvez généralement "seek" et "tell" avec des valeurs arbitraires en toute sécurité.

Une idée fausse courante en programmation de sockets est que "\n" est égal à "\012" partout. Lors de l'utilisation de protocoles tels que les protocoles Internet courants, "\012" et "\015" sont spécifiquement requis, et les valeurs des nouvelles lignes logiques "\n" et "\r" (retour chariot) ne sont pas fiables.

print $socket "Salut client !\r\n";      # FAUX
print $socket "Salut client !\015\012";  # VRAI

Cependant, l'utilisation de "\015\012" (ou "\cM\cJ", ou "\x0D\x0A") peut être fastidieuse et peu esthétique, ainsi que déroutante pour ceux qui maintiennent le code. Ainsi, le module "Socket" fournit la bonne chose pour ceux qui le souhaitent.

use Socket qw(:DEFAULT :crlf);
print $socket "Salut client !$CRLF"      # VRAI

Lors de la lecture depuis un socket, rappelez-vous que le séparateur d'enregistrement d'entrée par défaut $/ est "\n", mais un code de socket robuste reconnaîtra à la fois "\012" et "\015\012" comme fin de ligne :

while (<$socket>) {  # PAS RECOMMANDÉ !
    # ...
}

Comme CRLF et LF se terminent par LF, le séparateur d'enregistrement d'entrée peut être défini sur LF et tout CR supprimé plus tard. Mieux vaut écrire :

use Socket qw(:DEFAULT :crlf);
local($/) = LF;      # pas nécessaire si $/ est déjà \012
while (<$socket>) {
    s/$CR?$LF/\n/;   # pas sûr si le socket utilise LF ou CRLF, OK
#   s/\015?\012/\n/; # même chose
}

Cet exemple est préférable à l'exemple précédent - même pour les plateformes Unix - car maintenant tous les "\015" ("\cM") sont supprimés (et il y eut beaucoup de réjouissances).

De même, les fonctions qui renvoient des données textuelles - comme une fonction qui récupère une page Web - devraient parfois traduire les nouvelles lignes avant de renvoyer les données, si elles n'ont pas encore été traduites dans la représentation locale des nouvelles lignes. Une seule ligne de code suffit souvent :

$data =~ s/\015?\012/\n/g;

Perl Differences

This section describes some common differences between Perl implementations, and offers advice on how to write portable code.

ASCII CR and LF

rn $data;

Some of this may be confusing. Here's a handy reference to the ASCII CR and LF characters. You can print it out and stick it in your wallet.

LF  eq  \012  eq  \x0A  eq  \cJ  eq  chr(10)  eq  ASCII 10
CR  eq  \015  eq  \x0D  eq  \cM  eq  chr(13)  eq  ASCII 13
         | Unix | DOS  | Mac  |
    ---------------------------
    \n   |  LF  |  LF  |  CR  |
    \r   |  CR  |  CR  |  LF  |
    \n * |  LF  | CRLF |  CR  |
    \r * |  CR  |  CR  |  LF  |
    ---------------------------
    * text-mode STDIO

The Unix column assumes that you are not accessing a serial line (like a tty) in canonical mode. If you are, then CR on input becomes "\n", and "\n" on output becomes CRLF.

These are just the most common definitions of "\n" and "\r" in Perl. There may well be others. For example, on an EBCDIC implementation such as z/OS (OS/390) or OS/400 (using the ILE, the PASE is ASCII-based) the above material is similar to "Unix" but the code numbers change:

LF  eq  \025  eq  \x15  eq  \cU  eq  chr(21)  eq  CP-1047 21
LF  eq  \045  eq  \x25  eq           chr(37)  eq  CP-0037 37
CR  eq  \015  eq  \x0D  eq  \cM  eq  chr(13)  eq  CP-1047 13
CR  eq  \015  eq  \x0D  eq  \cM  eq  chr(13)  eq  CP-0037 13
         | z/OS | OS/400 |
    ----------------------
    \n   |  LF  |  LF    |
    \r   |  CR  |  CR    |
    \n * |  LF  |  LF    |
    \r * |  CR  |  CR    |
    ----------------------
    * text-mode STDIO

Numbers endianness and Width

Different CPUs store integers and floating point numbers in different orders (called endianness) and widths (32-bit and 64-bit being the most common today). This affects your programs when they attempt to transfer numbers in binary format from one CPU architecture to another, usually either "live" via network connection, or by storing the numbers to secondary storage such as a disk file or tape.

Conflicting storage orders make an utter mess out of the numbers. If a little-endian host (Intel, VAX) stores 0x12345678 (305419896 in decimal), a big-endian host (Motorola, Sparc, PA) reads it as 0x78563412 (2018915346 in decimal). Alpha and MIPS can be either: Digital/Compaq used/uses them in little-endian mode; SGI/Cray uses them in big-endian mode. To avoid this problem in network (socket) connections use the "pack" and "unpack" formats "n" and "N", the "network" orders. These are guaranteed to be portable.

As of Perl 5.10.0, you can also use the ">" and "<" modifiers to force big- or little-endian byte-order. This is useful if you want to store signed integers or 64-bit integers, for example.

You can explore the endianness of your platform by unpacking a data structure packed in native format such as:

print unpack("h*", pack("s2", 1, 2)), "\n";
# '10002000' on e.g. Intel x86 or Alpha 21064 in little-endian mode
# '00100020' on e.g. Motorola 68040

If you need to distinguish between endian architectures you could use either of the variables set like so:

$is_big_endian   = unpack("h*", pack("s", 1)) =~ /01/;
$is_little_endian = unpack("h*", pack("s", 1)) =~ /^1/;

Differing widths can cause truncation even between platforms of equal endianness. The platform of shorter width loses the upper parts of the number. There is no good solution for this problem except to avoid transferring or storing raw binary numbers.

One can circumnavigate both these problems in two ways. Either transfer and store numbers always in text format, instead of raw binary, or else consider using modules like "Data::Dumper" and "Storable" (included as of Perl 5.8). Keeping all data as text significantly simplifies matters.

Files and Filesystems

Most platforms these days structure files in a hierarchical fashion. So, it is reasonably safe to assume that all platforms support the notion of a "path" to uniquely identify a file on the system. How that path is really written, though, differs considerably.

Although similar, file path specifications differ between Unix, Windows, Mac OS, OS/2, VMS, VOS, RISC OS, and probably others. Unix, for example, is one of the few OSes that has the elegant idea of a single root directory.

DOS, OS/2, VMS, VOS, and Windows can work similarly to Unix with "/" as path separator, or in their own idiosyncratic ways (such as having several root directories and various "unrooted" device files such NIL: and LPT:).

Mac OS 9 and earlier used ":" as a path separator instead of "/".

The filesystem may support neither hard links ("link") nor symbolic links ("symlink", "readlink", "lstat").

The filesystem may support neither access timestamp nor change timestamp (meaning that about the only portable timestamp is the modification timestamp), or one second granularity of any timestamps (e.g. the FAT filesystem limits the time granularity to two seconds).

The "inode change timestamp" (the "-C" filetest) may really be the "creation timestamp" (which it is not in Unix).

VOS perl can emulate Unix filenames with "/" as path separator. The native pathname characters greater-than, less-than, number-sign, and percent-sign are always accepted.

RISC OS perl can emulate Unix filenames with "/" as path separator, or go native and use "." for path separator and ":" to signal filesystems and disk names.

Don't assume Unix filesystem access semantics: that read, write, and execute are all the permissions there are, and even if they exist, that their semantics (for example what do "r", "w", and "x" mean on a directory) are the Unix ones. The various Unix/POSIX compatibility layers usually try to make interfaces like "chmod" work, but sometimes there simply is no good mapping.

The "File::Spec" modules provide methods to manipulate path specifications and return the results in native format for each platform. This is often unnecessary as Unix-style paths are understood by Perl on every supported platform, but if you need to produce native paths for a native utility that does not understand Unix syntax, or if you are operating on paths or path components in unknown (and thus possibly native) syntax, "File::Spec" is your friend. Here are two brief examples:

use File::Spec::Functions;
chdir(updir());        # go up one directory
# Concatenate a path from its components
my $file = catfile(updir(), 'temp', 'file.txt');
# on Unix:    '../temp/file.txt'
# on Win32:   '..\temp\file.txt'
# on VMS:     '[-.temp]file.txt'

In general, production code should not have file paths hardcoded. Making them user-supplied or read from a configuration file is better, keeping in mind that file path syntax varies on different machines.

This is especially noticeable in scripts like Makefiles and test suites, which often assume "/" as a path separator for subdirectories.

Also of use is "File::Basename" from the standard distribution, which splits a pathname into pieces (base filename, full path to directory, and file suffix).

Even when on a single platform (if you can call Unix a single platform), remember not to count on the existence or the contents of particular system-specific files or directories, like /etc/passwd, /etc/sendmail.conf, /etc/resolv.conf, or even /tmp/. For example, /etc/passwd may exist but not contain the encrypted passwords, because the system is using some form of enhanced security. Or it may not contain all the accounts, because the system is using NIS. If code does need to rely on such a file, include a description of the file and its format in the code's documentation, then make it easy for the user to override the default location of the file.

Don't assume a text file will end with a newline. They should, but people forget.

Do not have two files or directories of the same name with different case, like test.pl and Test.pl, as many platforms have case-insensitive (or at least case-forgiving) filenames. Also, try not to have non-word characters (except for ".") in the names, and keep them to the 8.3 convention, for maximum portability, onerous a burden though this may appear.

Likewise, when using the "AutoSplit" module, try to keep your functions to 8.3 naming and case-insensitive conventions; or, at the least, make it so the resulting files have a unique (case-insensitively) first 8 characters.

Whitespace in filenames is tolerated on most systems, but not all, and even on systems where it might be tolerated, some utilities might become confused by such whitespace.

Many systems (DOS, VMS ODS-2) cannot have more than one "." in their filenames.

Don't assume ">" won't be the first character of a filename. Always use the three-arg version of "open":

open my $fh, '<', $existing_file) or die $!;

Two-arg "open" is magic and can translate characters like ">", "<", and "|" in filenames, which is usually the wrong thing to do. "sysopen" and three-arg "open" don't have this problem.

Portability

The following sections are guidelines for writing portable Perl code.

Mail

The "MailTools" distribution are commonly used, and provide several mailing methods, including "mail", "sendmail", and direct SMTP (via "Net::SMTP") if a mail transfer agent is not available. "Mail::Sendmail" is a standalone module that provides simple, platform-independent mailing.

The Unix System V IPC ("msg*(), sem*(), shm*()") is not available even on all Unix platforms.

Do not use either the bare result of "pack("N", 10, 20, 30, 40)" or bare v-strings (such as "v10.20.30.40") to represent IPv4 addresses: both forms just pack the four bytes into network order. That this would be equal to the C language "in_addr" struct (which is what the socket code internally uses) is not guaranteed. To be portable use the routines of the "Socket" module, such as "inet_aton", "inet_ntoa", and "sockaddr_in".

The rule of thumb for portable code is: Do it all in portable Perl, or use a module (that may internally implement it with platform-specific code, but exposes a common interface).

External Subroutines (XS)

XS code can usually be made to work with any platform, but dependent libraries, header files, etc., might not be readily available or portable, or the XS code itself might be platform-specific, just as Perl code might be. If the libraries and headers are portable, then it is normally reasonable to make sure the XS code is portable, too.

A different type of portability issue arises when writing XS code: availability of a C compiler on the end-user's system. C brings with it its own portability issues, and writing XS code will expose you to some of those. Writing purely in Perl is an easier way to achieve portability.

Standard Modules

In general, the standard modules work across platforms. Notable exceptions are the "CPAN" module (which currently makes connections to external programs that may not be available), platform-specific modules (like "ExtUtils::MM_VMS"), and DBM modules.

There is no one DBM module available on all platforms. "SDBM_File" and the others are generally available on all Unix and DOSish ports, but not in MacPerl, where only "NDBM_File" and "DB_File" are available.

The good news is that at least some DBM module should be available, and "AnyDBM_File" will use whichever module it can find. Of course, then the code needs to be fairly strict, dropping to the greatest common factor (e.g., not exceeding 1K for each record), so that it will work with any DBM module. See AnyDBM_File for more details.

Time and Date

The system's notion of time of day and calendar date is controlled in widely different ways. Don't assume the timezone is stored in $ENV{TZ}, and even if it is, don't assume that you can control the timezone through that variable. Don't assume anything about the three-letter timezone abbreviations (for example that MST would be the Mountain Standard Time, it's been known to stand for Moscow Standard Time). If you need to use timezones, express them in some unambiguous format like the exact number of minutes offset from UTC, or the POSIX timezone format.

Don't assume that the epoch starts at 00:00:00, January 1, 1970, because that is OS- and implementation-specific. It is better to store a date in an unambiguous representation. The ISO 8601 standard defines YYYY-MM-DD as the date format, or YYYY-MM-DDTHH:MM:SS (that's a literal "T" separating the date from the time). Please do use the ISO 8601 instead of making us guess what date 02/03/04 might be. ISO 8601 even sorts nicely as-is. A text representation (like "1987-12-18") can be easily converted into an OS-specific value using a module like "Time::Piece" (see "Date Parsing" in Time::Piece) or "Date::Parse". An array of values, such as those returned by "localtime", can be converted to an OS-specific representation using "Time::Local".

When calculating specific times, such as for tests in time or date modules, it may be appropriate to calculate an offset for the epoch.

use Time::Local qw(timegm);
my $offset = timegm(0, 0, 0, 1, 0, 1970);

The value for $offset in Unix will be 0, but in Mac OS Classic will be some large number. $offset can then be added to a Unix time value to get what should be the proper value on any system.

Character sets and character encoding

Assume very little about character sets.

Assume nothing about numerical values ("ord", "chr") of characters. Do not use explicit code point ranges (like "\xHH-\xHH)". However, starting in Perl v5.22, regular expression pattern bracketed character class ranges specified like "qr/[\N{U+HH}-\N{U+HH}]/" are portable, and starting in Perl v5.24, the same ranges are portable in "tr///". You can portably use symbolic character classes like "[:print:]".

Do not assume that the alphabetic characters are encoded contiguously (in the numeric sense). There may be gaps. Special coding in Perl, however, guarantees that all subsets of "qr/[A-Z]/", "qr/[a-z]/", and "qr/[0-9]/" behave as expected. "tr///" behaves the same for these ranges. In patterns, any ranges specified with end points using the "\N{...}" notations ensures character set portability, but it is a bug in Perl v5.22 that this isn't true of "tr///", fixed in v5.24.

Do not assume anything about the ordering of the characters. The lowercase letters may come before or after the uppercase letters; the lowercase and uppercase may be interlaced so that both "a" and "A" come before "b"; the accented and other international characters may be interlaced so that ä comes before "b". Unicode::Collate can be used to sort this all out.

Internationalisation

If you may assume POSIX (a rather large assumption), you may read more about the POSIX locale system from perllocale. The locale system at least attempts to make things a little bit more portable, or at least more convenient and native-friendly for non-English users. The system affects character sets and encoding, and date and time formatting--amongst other things.

If you really want to be international, you should consider Unicode. See perluniintro and perlunicode for more information.

By default Perl assumes your source code is written in an 8-bit ASCII superset. To embed Unicode characters in your strings and regexes, you can use the "\x{HH}" or (more portably) "\N{U+HH}" notations. You can also use the "utf8" pragma and write your code in UTF-8, which lets you use Unicode characters directly (not just in quoted constructs but also in identifiers).

System Resources

If your code is destined for systems with severely constrained (or missing!) virtual memory systems then you want to be especially mindful of avoiding wasteful constructs such as:

my @lines = <$very_large_file>;            # bad
while (<$fh>) {$file .= $_}                # sometimes bad
my $file = join('', <$fh>);                # better

The last two constructs may appear unintuitive to most people. The first repeatedly grows a string, whereas the second allocates a large chunk of memory in one go. On some systems, the second is more efficient than the first.

Security

Most multi-user platforms provide basic levels of security, usually implemented at the filesystem level. Some, however, unfortunately do not. Thus the notion of user id, or "home" directory, or even the state of being logged-in, may be unrecognizable on many platforms. If you write programs that are security-conscious, it is usually best to know what type of system you will be running under so that you can write code explicitly for that platform (or class of platforms).

Don't assume the Unix filesystem access semantics: the operating system or the filesystem may be using some ACL systems, which are richer languages than the usual "rwx". Even if the "rwx" exist, their semantics might be different.

(From the security viewpoint, testing for permissions before attempting to do something is silly anyway: if one tries this, there is potential for race conditions. Someone or something might change the permissions between the permissions check and the actual operation. Just try the operation.)

Don't assume the Unix user and group semantics: especially, don't expect $< and $> (or $( and $)) to work for switching identities (or memberships).

Don't assume set-uid and set-gid semantics. (And even if you do, think twice: set-uid and set-gid are a known can of security worms.)

Style

For those times when it is necessary to have platform-specific code, consider keeping the platform-specific code in one place, making

portant plus facilement sur d'autres plateformes. Utilisez le module "Config" et la variable spéciale $^O pour différencier les plateformes, comme décrit dans "PLATFORMS".

Méfiez-vous du "syndrome du else" :

if ($^O eq 'MSWin32') {
  # code qui suppose Windows
} else {
  # code qui suppose Linux
}

La branche "else" devrait être utilisée pour le dernier recours ultime, pas pour du code spécifique à une plateforme.

Soyez prudent dans les tests que vous fournissez avec votre module ou vos programmes. Le code du module peut être entièrement portable, mais ses tests pourraient ne pas l'être. Cela arrive souvent lorsque les tests lancent d'autres processus ou appellent des programmes externes pour aider aux tests, ou lorsque (comme noté ci-dessus) les tests supposent certaines choses sur le système de fichiers et les chemins. Faites attention à ne pas dépendre d'un style de sortie d'erreur spécifique, comme lors de la vérification de $! après un appel système échoué. L'utilisation de $! pour autre chose que son affichage est douteuse (bien que voir le module "Errno" pour tester raisonnablement de manière portable la valeur d'erreur). Certaines plateformes attendent un certain format de sortie, et Perl sur ces plateformes peut avoir été ajusté en conséquence. Plus spécifiquement, n'ancrez pas une expression régulière lors du test d'une valeur d'erreur.

DOS et dérivés

Perl a longtemps été porté sur les micro-ordinateurs de style Intel tournant sous des systèmes comme PC-DOS, MS-DOS, OS/2, et la plupart des plateformes Windows que vous pouvez mentionner (à l'exception de Windows CE, si vous en comptez une). Les utilisateurs familiers avec les shells de style COMMAND.COM ou CMD.EXE doivent être conscients que chacune de ces spécifications de fichiers peut avoir des différences subtiles :

my $filespec0 = "c:/foo/bar/file.txt";
my $filespec1 = "c:\\foo\\bar\\file.txt";
my $filespec2 = 'c:\foo\bar\file.txt';
my $filespec3 = 'c:\\foo\\bar\\file.txt';

Les appels système acceptent soit "/" soit "\" comme séparateur de chemin. Cependant, de nombreux utilitaires en ligne de commande d'époque DOS traitent "/" comme le préfixe d'option, ils peuvent donc être confus par des noms de fichiers contenant "/". En dehors de l'appel à des programmes externes, "/" fonctionnera très bien, et probablement mieux, car il est plus cohérent avec l'usage populaire et évite le problème de se souvenir de ce qu'il faut mettre en antislash et de ce qu'il ne faut pas.

Le système de fichiers FAT de DOS ne peut accueillir que des noms de fichiers de style "8.3". Sous les systèmes de fichiers HPFS (OS/2) et NTFS (NT) "insensibles à la casse, mais préservant la casse", vous devrez peut-être faire attention à la casse renvoyée par des fonctions comme "readdir" ou utilisée avec des fonctions comme "open" ou "opendir".

DOS traite également plusieurs noms de fichiers comme spéciaux, tels que AUX, PRN, NUL, CON, COM1, LPT1, LPT2, etc. Malheureusement, parfois ces noms de fichiers ne fonctionneront même pas si vous incluez un préfixe de répertoire explicite. Il est préférable d'éviter de tels noms de fichiers si vous voulez que votre code soit portable vers DOS et ses dérivés. Il est difficile de savoir ce que sont tous ces noms, malheureusement.

Les utilisateurs de ces systèmes d'exploitation peuvent également souhaiter utiliser des scripts tels que pl2bat.bat pour créer des enveloppes autour de vos scripts.

Les sauts de ligne ("\n") sont traduits en "\015\012" par le système d'E/S lors de la lecture et de l'écriture dans des fichiers (voir "Newlines"). binmode($filehandle) conservera "\n" traduit en "\012" pour ce handle de fichier. "binmode" doit toujours être utilisé pour le code qui traite des données binaires. C'est en supposant que vous réalisez à l'avance que vos données sont binaires. Les programmes à usage général devraient souvent ne rien supposer de leurs données.

VMS

Perl sur VMS est discuté dans perlvms dans la distribution Perl.

Le nom officiel de VMS à l'heure actuelle est OpenVMS.

L'interaction avec Perl depuis le shell Digital Command Language (DCL) nécessite souvent un ensemble différent de guillemets par rapport aux shells Unix. Par exemple :

$ perl -e "print ""Hello, world.\n"""
Hello, world.

Il existe plusieurs façons d'encapsuler vos scripts Perl dans des fichiers .COM DCL, si vous le souhaitez. Par exemple :

$ write sys$output "Hello from DCL!"
$ if p1 .eqs. ""
$ then perl -x 'f$environment("PROCEDURE")
$ else perl -x - 'p1 'p2 'p3 'p4 'p5 'p6 'p7 'p8
$ deck/dollars="__END__"
#!/usr/bin/perl
print "Hello from Perl!\n";
__END__
$ endif

Faites attention avec "$ ASSIGN/nolog/user SYS$COMMAND: SYS$INPUT" si votre script Perl dans DCL s'attend à faire des choses comme "$read = <STDIN>;".

Le système d'exploitation VMS possède deux systèmes de fichiers, désignés par leur structure sur disque (ODS) : ODS-2 et son successeur ODS-5. Le portage initial de Perl vers VMS précède ODS-5, mais tous les tests et développements actuels supposent ODS-5 et ses capacités, y compris la préservation de la casse, les caractères étendus dans les spécifications de fichiers et les noms pouvant atteindre 8192 octets.

Perl sur VMS peut accepter des spécifications de fichiers de style VMS ou Unix, comme dans l'un des exemples suivants :

$ perl -ne "print if /perl_setup/i" SYS$LOGIN:LOGIN.COM
$ perl -ne "print if /perl_setup/i" /sys$login/login.com

mais pas un mélange des deux comme dans :

$ perl -ne "print if /perl_setup/i" sys$login:/login.com
Can't open sys$login:/login.com: file specification syntax error

En général, le chemin le plus simple vers la portabilité consiste toujours à spécifier les noms de fichiers au format Unix, sauf s'ils doivent être traités par des commandes ou des utilitaires natifs. En raison de cette dernière considération, le module File::Spec renvoie par défaut des spécifications au format natif, quel que soit le format d'entrée. Ce défaut peut être inversé afin que les noms de fichiers soient toujours signalés au format Unix en spécifiant la fonctionnalité logique "DECC$FILENAME_UNIX_REPORT" dans l'environnement.

Le type de fichier, ou extension, est toujours présent dans une spécification de fichier au format VMS, même s'il est de longueur nulle. Cela signifie que, par défaut, "readdir" renverra un point final sur un fichier sans extension, donc là où vous verriez "a" sur Unix, vous verrez "a." sur VMS. Cependant, le point final peut être supprimé en activant la fonctionnalité "DECC$READDIR_DROPDOTNOTYPE" dans l'environnement (voir la documentation CRTL sur les noms logiques de fonctionnalités).

Ce que "\n" représente dépend du type de fichier ouvert. Il représente généralement "\012", mais il pourrait aussi être "\015", "\012", "\015\012", "\000", "\040", ou rien, selon l'organisation du fichier et le format d'enregistrement. Le module "VMS::Stdio" fournit l'accès aux exigences spéciales de fopen() pour les fichiers ayant des attributs inhabituels sur VMS.

La valeur de $^O sur OpenVMS est "VMS". Pour déterminer l'architecture sur laquelle vous vous exécutez, consultez $Config{archname}.

Sur VMS, perl détermine le décalage UTC à partir du nom logique "SYS$TIMEZONE_DIFFERENTIAL". Bien que l'époque VMS ait commencé le 17-NOV-1858 00:00:00.00, les appels à "localtime" sont ajustés pour compter les décalages à partir du 01-JAN-1970 00:00:00.00, tout comme Unix.

VOS

Perl sur VOS (également connu sous le nom d'OpenVOS) est discuté dans README.vos dans la distribution Perl (installé sous le nom perlvos). Perl sur VOS peut accepter des spécifications de fichiers de style VOS ou Unix, comme dans l'un des exemples suivants :

$ perl -ne "print if /perl_setup/i" >system>notices
$ perl -ne "print if /perl_setup/i" /system/notices

ou même un mélange des deux comme dans :

$ perl -ne "print if /perl_setup/i" >system/notices

Même si VOS autorise le caractère slash à apparaître dans les noms d'objets, parce que le port VOS de Perl l'interprète comme un délimiteur de chemin, les fichiers, répertoires ou liens VOS dont les noms contiennent un caractère slash ne peuvent pas être traités. Ces fichiers doivent être renommés avant de pouvoir être traités par Perl.

Les versions plus anciennes de VOS (avant OpenVOS Release 17.0) limitent les noms de fichiers à 32 caractères ou moins, interdisent aux noms de fichiers de commencer par un caractère "-", et interdisent aux noms de fichiers de contenir " " (espace) ou tout caractère de l'ensemble "!#%&'()*;<=>?".

Les versions plus récentes de VOS (OpenVOS Release 17.0 ou ultérieure) prennent en charge une fonctionnalité connue sous le nom de noms étendus. Sur ces versions, les noms de fichiers peuvent contenir jusqu'à 255 caractères, sont interdits de commencer par un caractère "-", et l'ensemble des caractères interdits est réduit à "#%*<>?". Il existe des restrictions concernant les espaces et les apostrophes : ces caractères ne doivent pas commencer ou terminer un nom, ni précéder ou suivre immédiatement un point. De plus, un espace ne doit pas précéder immédiatement un autre espace ou un trait d'union. Plus précisément, les combinaisons de caractères suivantes sont interdites : espace-espace, espace-trait d'union, point-espace, espace-point, point-apostrophe, apostrophe-point, espace en début ou fin, et apostrophe en début ou fin. Bien qu'un nom de fichier étendu soit limité à 255 caractères, un nom de chemin est toujours limité à 256 caractères.

La valeur de $^O sur VOS est "vos". Pour déterminer l'architecture sur laquelle vous vous exécutez, consultez $Config{archname}.

Acorn RISC OS

Comme Acorns utilise ASCII avec des sauts de ligne ("\n") dans les fichiers texte comme "\012" comme Unix, et parce que l'émulation des noms de fichiers Unix est activée par défaut, la plupart des scripts simples fonctionneront probablement "dès la sortie de la boîte". Le système de fichiers natif est modulaire, et les systèmes de fichiers individuels sont libres d'être sensibles ou insensibles à la casse, et respectent généralement la casse. Certains systèmes de fichiers natifs ont des limites de longueur de nom, auxquelles les noms de fichiers et de répertoires sont silencieusement tronqués pour s'adapter. Les scripts doivent être conscients que le système de fichiers standard a actuellement une limite de longueur de nom de 10 caractères, avec jusqu'à 77 éléments dans un répertoire, mais d'autres systèmes de fichiers peuvent ne pas imposer de telles limitations.

Les noms de fichiers natifs sont de la forme

Filesystem#Special_Field::DiskName.$.Directory.Directory.File

où

Special_Field n'est généralement pas présent, mais peut contenir . et $ .
Filesystem =~ m|[A-Za-z0-9_]|
DsicName   =~ m|[A-Za-z0-9_/]|
$ représente le répertoire racine
. est le séparateur de chemin
@ est le répertoire courant (par système de fichiers mais global à la machine)
^ est le répertoire parent
Directory et File =~ m|[^\0- "\.\$\%\&:\@\\^\|\177]+|

La traduction par défaut des noms de fichiers est à peu près "tr|/.|./|", échangeant les points et les slashs.

Notez que ""ADFS::HardDisk.$.File" ne 'ADFS::HardDisk.$.File'" et que la deuxième étape de l'interpolation "$" dans les expressions régulières tombera sur la variable $. si les scripts ne font pas attention.

Les chemins logiques spécifiés par des variables système contenant des listes de recherche séparées par des virgules sont également autorisés ; ainsi "System:Modules" est un nom de fichier valide, et le système de fichiers ajoutera en préfixe à "Modules" chaque section de "System$Path" jusqu'à ce qu'un nom soit créé qui pointe vers un objet sur disque. L'écriture dans un nouveau fichier "System:Modules" ne serait autorisée que si "System$Path" contenait une liste d'un seul élément. Le système de fichiers développera également des variables système dans les noms de fichiers s'ils sont entourés d'accolades, donc "<System$Dir>.Modules" chercherait le fichier "$ENV{'System$Dir'} . 'Modules'". L'implication évidente est que les noms de fichiers entièrement qualifiés peuvent commencer par "<>" et que la forme à trois arguments de "open" doit toujours être utilisée.

Parce que "." était utilisé comme séparateur de répertoire et que les noms de fichiers ne pouvaient pas être supposés être uniques après 10 caractères, Acorn a implémenté le compilateur C pour supprimer les suffixes de fin ".c" ".h" ".s" et ".o" des noms de fichiers spécifiés dans le code source et stocker les fichiers respectifs dans des sous-répertoires nommés d'après le suffixe. Par conséquent, les fichiers sont traduits :

foo.h           h.foo
C:foo.h         C:h.foo        (variable de chemin logique)
sys/os.h        sys.h.os       (le compilateur C comprend le langage Unix)
10charname.c    c.10charname
10charname.o    o.10charname
11charname_.c   c.11charname   (en supposant que le système de fichiers tronque à 10)

La traduction des noms de fichiers en natif par la bibliothèque d'émulation Unix suppose que ce type de traduction est nécessaire, et elle permet une liste de suffixes connus définie par l'utilisateur qu'elle transpose de cette manière. Cela peut sembler transparent, mais considérez qu'avec ces règles, foo/bar/baz.h et foo/bar/h/baz correspondent tous deux à foo.bar.h.baz, et que "readdir" et "glob" ne peuvent pas et n'essaient pas d'émuler le mappage inverse. D'autres "." dans les noms de fichiers sont traduits en "/".

Comme implicite ci-dessus, l'environnement accédé via %ENV est global, et la convention est que les variables d'environnement spécifiques au programme sont de la forme "Program$Name". Chaque système de fichiers maintient un répertoire courant, et le répertoire courant du système de fichiers courant est le répertoire courant global. Par conséquent, les programmes sociables ne changent pas le répertoire courant mais s'appuient sur des noms de chemins complets, et les programmes (et les Makefiles) ne peuvent pas supposer qu'ils peuvent lancer un processus enfant qui peut changer le répertoire courant sans affecter son parent (et tous les autres d'ailleurs).

Parce que les descripteurs de fichiers du système d'exploitation natif sont globaux et sont actuellement alloués à partir de 255, 0 étant une valeur réservée, la bibliothèque d'émulation Unix émule les descripteurs de fichiers Unix. Par conséquent, vous ne pouvez pas compter sur le passage de "STDIN", "STDOUT", ou "STDERR" à vos enfants.

Le désir des utilisateurs d'exprimer des noms de fichiers de la forme "<Foo$Dir>.Bar" sur la ligne de commande sans guillemets pose également des problèmes : la capture de sortie de commande `` doit effectuer un jeu de devinettes. Elle suppose qu'une chaîne "<[^<>]+\$[^<>]>" est une référence à une variable d'environnement, tandis que tout autre chose impliquant "<" ou ">" est une redirection, et parvient généralement à être correcte dans 99% des cas. Bien sûr, le problème demeure que les scripts ne peuvent pas compter sur la disponibilité d'outils Unix, ni sur le fait que les outils trouvés aient des arguments de ligne de commande de type Unix.

Les extensions et les XS sont, en théorie, constructibles par quiconque utilisant des outils gratuits. En pratique, beaucoup ne le font pas, car les utilisateurs de la plateforme Acorn sont habitués aux distributions binaires. MakeMaker fonctionne, mais aucun make disponible ne gère actuellement les makefiles de MakeMaker ; même si cela devrait être corrigé, le manque d'un shell de type Unix causera des problèmes avec les règles de makefile, en particulier les lignes de la forme "cd sdbm && make all", et tout ce qui utilise des guillemets.

"RISC OS" est le nom propre du système d'exploitation, mais la valeur dans $^O est "riscos" (parce que nous n'aimons pas crier).

(VMS) Implémenté sur VMS 64 bits 8.3. VMS nécessite que le lien symbolique soit en syntaxe Unix s'il est destiné à résoudre un chemin valide.

system
(Win32) Par optimisation, il est possible que le shell de commande spécifié dans $ENV{PERL5SHELL} ne soit pas appelé. "system(1, @args)" lance un processus externe et renvoie immédiatement son descripteur de processus, sans attendre sa terminaison. La valeur de retour peut être utilisée ultérieurement dans "wait" ou "waitpid". L'échec du lancement d'un sous-processus (spawn()) est indiqué par l'affectation de $? à "255 << 8". $? est défini de manière compatible avec Unix (c'est-à-dire que le statut de sortie du sous-processus est obtenu par "$? >> 8", comme décrit dans la documentation).

Notez que la forme liste de system() est émulée car l'API Win32 CreateProcess() accepte une chaîne simple plutôt qu'un tableau d'arguments de ligne de commande. Cela peut avoir des implications de sécurité pour votre code.

(RISC OS) Il n'y a pas de shell pour traiter les métacaractères, et la norme native consiste à passer une ligne de commande terminée par "\n", "\r" ou "\0" au programme lancé. La redirection, telle que "> foo", est effectuée (si elle l'est) par la bibliothèque d'exécution du programme lancé. "system LIST" appellera l'exec émulation de la bibliothèque d'émulation Unix, qui tente de fournir une émulation des entrées/sorties standard (stdin, stdout, stderr) actives dans le parent, à condition que le programme enfant utilise une version compatible de la bibliothèque d'émulation. "system SCALAR" appellera directement la ligne de commande native et aucune émulation de programme Unix enfant ne se produira. L'expérience **variera**.

(Win32) "system LIST" sans l'utilisation de la syntaxe d'objet indirect ("system PROGRAM LIST") peut se rabattre sur l'essai du shell si le premier spawn() échoue.

(SunOS, Solaris, HP-UX) Ne vide pas automatiquement les descripteurs de sortie sur certaines plateformes.

(VMS) Comme avec Win32, "system(1, @args)" lance un processus externe et renvoie immédiatement son descripteur de processus sans attendre la fin du processus. Dans ce cas, la valeur de retour peut être utilisée ultérieurement dans "wait" ou "waitpid". Sinon, la valeur de retour est de type POSIX (décalée de 8 bits), ce qui ne laisse de place que pour une valeur fabriquée dérivée des bits de gravité du code de condition natif de 32 bits (sauf si elle est remplacée par "use vmsish 'status'"). Si le code de condition natif est celui qui contient une valeur POSIX encodée, la valeur POSIX sera décodée pour extraire la valeur de sortie attendue. Pour plus de détails, voir "$?" dans perlvms.
