NOM

path_resolution - comment un nom de chemin est résolu en un fichier

DESCRIPTION

Certains appels système UNIX/Linux ont comme paramètre un ou plusieurs noms de fichiers. Un nom de fichier (ou nom de chemin) est résolu comme suit.

Étape 1 : début du processus de résolution

Si le nom de chemin commence par le caractère « / », le répertoire de recherche de départ est le répertoire racine du processus appelant. Un processus hérite de son répertoire racine de son parent. Habituellement, il s'agit du répertoire racine de la hiérarchie des fichiers. Un processus peut obtenir un répertoire racine différent en utilisant l'appel système chroot(2), ou peut utiliser temporairement un répertoire racine différent en utilisant openat2(2) avec le drapeau RESOLVE_IN_ROOT activé.

Un processus peut obtenir un espace de noms de montage entièrement privé si lui—ou l'un de ses ancêtres—a été lancé par une invocation de l'appel système clone(2) qui avait le drapeau CLONE_NEWNS activé. Ceci gère la partie « / » du nom de chemin.

Si le nom de chemin ne commence pas par le caractère « / », le répertoire de recherche de départ du processus de résolution est le répertoire de travail courant du processus — ou dans le cas des appels système de type openat(2), l'argument dfd (ou le répertoire de travail courant si AT_FDCWD est passé comme argument dfd). Le répertoire de travail courant est hérité du parent et peut être modifié en utilisant l'appel système chdir(2).

Les noms de chemin commençant par un caractère « / » sont appelés noms de chemin absolus. Les noms de chemin ne commençant pas par « / » sont appelés noms de chemin relatifs.

Étape 2 : parcourir le chemin

Définir le répertoire de recherche courant au répertoire de recherche de départ. Maintenant, pour chaque composant non final du nom de chemin, où un composant est une sous-chaîne délimitée par des caractères « / », ce composant est recherché dans le répertoire de recherche courant.

Si le processus n'a pas la permission de recherche sur le répertoire de recherche courant, une erreur EACCES est retournée (« Permission refusée »).

Si le composant n'est pas trouvé, une erreur ENOENT est retournée (« Aucun fichier ou répertoire de ce type »).

Si le composant est trouvé, mais n'est ni un répertoire ni un lien symbolique, une erreur ENOTDIR est retournée (« Pas un répertoire »).

Si le composant est trouvé et est un répertoire, nous définissons le répertoire de recherche courant à ce répertoire, et passons au composant suivant.

Si le composant est trouvé et est un lien symbolique, nous résolvons d'abord ce lien symbolique (avec le répertoire de recherche courant comme répertoire de recherche de départ). En cas d'erreur, cette erreur est retournée. Si le résultat n'est pas un répertoire, une erreur ENOTDIR est retournée. Si la résolution du lien symbolique réussit et renvoie un répertoire, nous définissons le répertoire de recherche courant à ce répertoire, et passons au composant suivant. Notez que le processus de résolution peut impliquer une récursion si le préfixe (« dirname ») d'un nom de chemin contient un nom de fichier qui est un lien symbolique se résolvant en un répertoire (où le composant préfixe de ce répertoire peut contenir un lien symbolique, et ainsi de suite). Afin de protéger le noyau contre les débordements de pile, et aussi pour protéger contre le déni de service, il existe des limites sur la profondeur de récursion maximale, et sur le nombre maximal de liens symboliques suivis. Une erreur ELOOP est retournée lorsque le maximum est dépassé (« Trop de niveaux de liens symboliques »).

Tel qu'implémenté actuellement sous Linux, le nombre maximal de liens symboliques qui seront suivis lors de la résolution d'un nom de chemin est de 40. Avant Linux 2.6.18, la limite de profondeur de récursion était de 5. À partir de Linux 2.6.18, cette limite a été portée à 8. Dans Linux 4.2, le code de résolution de noms de chemin du noyau a été retravaillé pour éliminer l'utilisation de la récursion, de sorte que la seule limite restante est le maximum de 40 résolutions pour l'ensemble du nom de chemin.

La résolution des liens symboliques pendant cette étape peut être bloquée en utilisant openat2(2), avec le drapeau RESOLVE_NO_SYMLINKS activé.

Étape 3 : trouver la dernière entrée

La recherche du dernier composant du nom de chemin se fait exactement comme pour tous les autres composants, comme décrit dans l'étape précédente, avec deux différences : (i) le dernier composant ne doit pas nécessairement être un répertoire (du moins en ce qui concerne le processus de résolution de chemin — il devra peut-être être un répertoire, ou un non-répertoire, en raison des exigences de l'appel système spécifique), et (ii) ce n'est pas nécessairement une erreur si le composant n'est pas trouvé — peut-être que nous le créons simplement. Les détails sur le traitement de la dernière entrée sont décrits dans les pages de manuel des appels système spécifiques.

. et ..

Par convention, chaque répertoire possède les entrées « . » et « .. », qui font référence respectivement au répertoire lui-même et à son répertoire parent.

Le processus de résolution de chemin supposera que ces entrées ont leurs significations conventionnelles, indépendamment de leur présence physique dans le système de fichiers.

On ne peut pas remonter au-delà de la racine : « /.. » est identique à « / ».

Points de montage

Après une commande mount dev path, le nom de chemin « path » fait référence à la racine de la hiérarchie des systèmes de fichiers sur le périphérique « dev », et ne fait plus référence à ce à quoi il faisait référence précédemment.

On peut sortir d'un système de fichiers monté : « path/.. » fait référence au répertoire parent de « path », en dehors de la hiérarchie des systèmes de fichiers sur « dev ».

La traversée des points de montage peut être bloquée en utilisant openat2(2), avec le drapeau RESOLVE_NO_XDEV activé (bien qu'il note que cela restreint également la traversée des montages bind).

Barres obliques finales

Si un nom de chemin se termine par une barre oblique « / », cela force la résolution du composant précédent comme à l'étape 2 : le composant précédant la barre oblique existe et se résout en un répertoire ou il nomme un répertoire qui doit être créé immédiatement après la résolution du nom de chemin. Sinon, une barre oblique finale « / » est ignorée.

Lien symbolique final

Si le dernier composant d'un nom de chemin est un lien symbolique, alors cela dépend de l'appel système pour savoir si le fichier référencé sera le lien symbolique ou le résultat de la résolution du chemin sur son contenu. Par exemple, l'appel système lstat(2) agira sur le lien symbolique, tandis que stat(2) agira sur le fichier pointé par le lien symbolique.

Limite de longueur

Il existe une longueur maximale pour les noms de chemin. Si le nom de chemin (ou un nom de chemin intermédiaire obtenu lors de la résolution de liens symboliques) est trop long, une erreur ENAMETOOLONG est retournée (« Nom de fichier trop long »).

Nom de chemin vide

Dans le UNIX original, le nom de chemin vide faisait référence au répertoire courant. Aujourd'hui, POSIX décrète qu'un nom de chemin vide ne doit pas être résolu avec succès. Linux retourne ENOENT dans ce cas.

Permissions

Les bits de permissions d'un fichier se composent de trois groupes de trois bits ; voir chmod(1) et stat(2). Le premier groupe de trois est utilisé lorsque l'ID utilisateur effectif du processus appelant est égal à l'ID du propriétaire du fichier. Le second groupe de trois est utilisé lorsque l'ID de groupe du fichier est égal à l'ID de groupe effectif du processus appelant, ou est

one of the supplementary group IDs of the calling process (as set by setgroups(2)). When neither holds, the third group is used.

Of the three bits used, the first bit determines read permission, the second write permission, and the last execute permission in case of ordinary files, or search permission in case of directories.

Linux uses the fsuid instead of the effective user ID in permission checks. Ordinarily the fsuid will equal the effective user ID, but the fsuid can be changed by the system call setfsuid(2).

(Here "fsuid" stands for something like "filesystem user ID". The concept was required for the implementation of a user space NFS server at a time when processes could send a signal to a process with the same effective user ID. It is obsolete now. Nobody should use setfsuid(2).)

Similarly, Linux uses the fsgid ("filesystem group ID") instead of the effective group ID. See setfsgid(2).

Contournement des vérifications des permissions : superutilisateur et capacités

On a traditional UNIX system, the superuser (root, user ID 0) is all-powerful, and bypasses all permissions restrictions when accessing files.

On Linux, superuser privileges are divided into capabilities (see capabilities(7)). Two capabilities are relevant for file permissions checks: CAP_DAC_OVERRIDE and CAP_DAC_READ_SEARCH. (A process has these capabilities if its fsuid is 0.)

The CAP_DAC_OVERRIDE capability overrides all permission checking, but grants execute permission only when at least one of the file's three execute permission bits is set.

The CAP_DAC_READ_SEARCH capability grants read and search permission on directories, and read permission on ordinary files.
