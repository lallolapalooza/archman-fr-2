PATHCHK(1P) Manuel du programmeur POSIX PATHCHK(1P)

PROLOGUE

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consultez la page de manuel Linux correspondante pour les détails du comportement sous Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

pathchk — vérifier les noms de chemin

SYNOPSIS

pathchk [-p] [-P] nom_chemin...

DESCRIPTION

L'utilitaire pathchk vérifie si un ou plusieurs noms de chemin sont valides (c'est-à-dire qu'ils pourraient être utilisés pour accéder ou créer un fichier sans provoquer d'erreurs de syntaxe) et portables (c'est-à-dire qu'aucune troncature de nom de fichier n'en résulte). Des vérifications de portabilité plus poussées sont fournies par les options -p et -P.

Par défaut, l'utilitaire pathchk vérifie chaque composant de chaque opérande nom_chemin en fonction du système de fichiers sous-jacent. Un message de diagnostic est écrit pour chaque opérande nom_chemin qui :

*
Est plus long que {PATH_MAX} octets (voir Valeurs de variables de noms de chemin dans le volume Définitions de base de POSIX.1‐2017, <limits.h>)
*
Contient un composant plus long que {NAME_MAX} octets dans son répertoire parent
*
Contient un composant dans un répertoire qui n'est pas accessible en lecture
*
Contient une séquence d'octets qui n'est pas valide dans son répertoire parent

Le format du message de diagnostic n'est pas spécifié, mais doit indiquer l'erreur détectée et l'opérande nom_chemin correspondant.

Il ne sera pas considéré comme une erreur si un ou plusieurs composants d'un opérande nom_chemin n'existent pas, tant qu'un fichier correspondant au nom de chemin spécifié par les composants manquants pourrait être créé sans violer aucune des vérifications spécifiées ci-dessus.

OPTIONS

L'utilitaire pathchk est conforme au volume Définitions de base de POSIX.1‐2017, Section 12.2, Directives de syntaxe des utilitaires.

L'option suivante est prise en charge :

-p
Au lieu d'effectuer des vérifications basées sur le système de fichiers sous-jacent, écrire un message de diagnostic pour chaque opérande nom_chemin qui :
*
Est plus long que {_POSIX_PATH_MAX} octets (voir Valeurs minimales dans le volume Définitions de base de POSIX.1‐2017, <limits.h>)
*
Contient un composant plus long que {_POSIX_NAME_MAX} octets
*
Contient un caractère dans un composant qui ne fait pas partie de l'ensemble de caractères de nom de fichier portable
-P
Écrire un message de diagnostic pour chaque opérande nom_chemin qui :
*
Contient un composant dont le premier caractère est le caractère <tiret-moins>
*
Est vide

OPÉRANDES

L'opérande suivant est pris en charge :

nom_chemin
Un nom de chemin à vérifier.

Détermine la localisation qui doit être utilisée pour affecter le format et le contenu des messages de diagnostic écrits sur la sortie standard.

Détermine l'emplacement des catalogues de messages pour le traitement de LC_MESSAGES.

UTILISATION PAR L'APPLICATION

L'utilitaire test peut être utilisé pour déterminer si un nom de chemin donné désigne un fichier existant ; il n'indique cependant pas si un composant du nom de chemin a été tronqué dans un répertoire où la fonctionnalité _POSIX_NO_TRUNC n'est pas active. L'utilitaire pathchk ne vérifie pas l'existence de fichiers ; il effectue des vérifications pour déterminer si un nom de chemin existe ou pourrait être créé sans troncature de composant du nom de chemin.

L'option noclobber du shell (voir la commande interne set) peut être utilisée pour créer un fichier de manière atomique. Comme pour toutes les sémantiques de création de fichiers dans le volume Interfaces système de POSIX.1‐2017, elle garantit la création atomique, mais repose toujours sur les applications pour convenir de conventions et coopérer sur l'utilisation des fichiers après leur création.

Pour vérifier qu'un nom de chemin répond aux exigences de portabilité des noms de fichiers, les applications doivent utiliser les options -p et -P ensemble.

EXEMPLES

Pour vérifier que tous les noms de chemin dans une archive de transfert de données importée sont légitimes et sans ambiguïté sur le système actuel :

# Cet exemple suppose qu'aucun nom de chemin dans l'archive
# ne contient de caractères <nouvelle ligne>.
pax -f archive | sed -e 's/[^[:alnum:]]/\\&/g' | xargs pathchk --
if [ $? -eq 0 ]
then
    pax -r -f archive
else
    echo Enquêter sur les problèmes avant d'importer des fichiers.
    exit 1
fi

Pour vérifier que tous les fichiers de la hiérarchie de répertoires actuelle pourraient être déplacés vers n'importe quel système conforme au volume Interfaces système de POSIX.1‐2017 qui prend également en charge l'utilitaire pax :

find . -exec pathchk -p -P {} +
if [ $? -eq 0 ]
then
    pax -w -f ../archive .
else
    echo Impossible de créer une archive portable.
    exit 1
fi

Les hypothèses suivantes sont faites dans cet exemple :

1.
PROCESSING représente le code utilisé par l'application pour utiliser $path une fois qu'il est vérifié que $path.out fonctionne comme prévu.
2.
L'état de l'option noclobber est inconnu lorsque ce code est appelé et doit être défini à la sortie dans l'état où il était lorsque ce code a été appelé. (La variable reset est utilisée dans cet exemple pour restaurer l'état initial.)
3.
Notez l'utilisation de :
rm "$path.out" > "$path.out"
a.
La commande pathchk a déjà vérifié, à ce stade, que $path.out n'est pas tronqué.
b.
Avec l'option noclobber définie, le shell vérifie que $path.out n'existe pas déjà avant d'appeler rm.
c.
Si le shell a réussi à créer $path.out, rm le supprime afin que l'application puisse recréer le fichier dans l'étape PROCESSING.
d.
Si l'étape PROCESSING souhaite que le fichier existe déjà lorsqu'elle est appelée, la :
rm "$path.out" > "$path.out"

doit être remplacée par :

> "$path.out"

qui vérifie que le fichier n'existait pas déjà, mais laisse $path.out en place pour être utilisé par PROCESSING.

RATIONALE

L'utilitaire pathchk était nouveau pour la norme ISO POSIX‐2:1993. Il, ainsi que l'option set -C(noclobber) ajoutée au shell, remplace les utilitaires mktemp, validfnam et create qui sont apparus dans les premières propositions. Tous ces utilitaires étaient des tentatives pour résoudre plusieurs problèmes courants :

*
Vérifier la validité (pour plusieurs définitions de ``valide'') d'un nom de chemin fourni par un utilisateur, généré par une application ou importé d'une source externe.
*
Créer un fichier de manière atomique.
*
Effectuer diverses fonctions de manipulation de chaînes pour générer un nom de fichier temporaire.

L'utilitaire create, inclus dans une proposition précoce, assurait la vérification et la création atomique en une seule invocation de l'utilitaire ; ces problèmes sont orthogonaux et n'ont pas besoin d'être regroupés en un seul utilitaire. Notez que l'option noclobber fournit également un moyen de créer un verrou pour la synchronisation des processus ; comme elle fournit une création atomique, il n'y a pas de compétition entre un test d'existence et la création suivante s'il n'existait pas.

Avoir une fonction comme tmpnam() dans la norme ISO C est important dans de nombreux langages de haut niveau. Le langage de programmation shell, cependant, possède des installations de manipulation de chaînes intégrées, ce qui rend très facile la construction de noms de fichiers temporaires. Les noms nécessaires dépendent évidemment de l'application, mais sont fréquemment de la forme :

$TMPDIR/abréviation_application$$.suffixe

Dans les cas où il est probable qu'il y ait une concurrence pour un suffixe donné, une simple boucle for ou while du shell peut être utilisée avec l'option noclobber du shell pour créer un fichier sans risque de collisions, tant que les applications essayant d'utiliser le même espace de noms de noms de fichiers coopèrent sur l'utilisation des fichiers une fois qu'ils ont été créés.

À des fins historiques, -p ne vérifie pas l'utilisation du caractère <trait d'union> comme premier caractère d'un composant du nom de chemin, ni un opérande pathname vide.
