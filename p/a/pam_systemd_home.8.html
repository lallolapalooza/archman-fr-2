NOM

pam_systemd_home - Authentifier les utilisateurs et monter les répertoires personnels via systemd-homed.service

SYNTAXE

pam_systemd_home.so

DESCRIPTION

pam_systemd_home assure que les répertoires personnels gérés par systemd-homed.service(8) sont automatiquement activés (montés) lors de la connexion de l'utilisateur, et sont désactivés (démontés) lorsque la dernière session de l'utilisateur se termine. Pour ces utilisateurs, il assure également l'authentification (lorsque le chiffrement de disque par utilisateur est utilisé, la clé de chiffrement du disque est dérivée de l'identifiant d'authentification fourni lors de la connexion), la gestion des comptes (l'enregistrement JSON de l'utilisateur[1] intégré dans le magasin personnel contient les détails du compte) et met à jour le mot de passe de chiffrement (qui est également utilisé pour l'authentification de l'utilisateur).

OPTIONS

Les options suivantes sont comprises :

suspend=

Prend un argument booléen. Si vrai, le répertoire personnel de l'utilisateur sera automatiquement suspendu lors de la mise en veille du système ; si faux, il restera actif. La suspension automatique du répertoire personnel améliore considérablement la sécurité car les clés secrètes sont automatiquement supprimées de la mémoire avant que le système ne soit mis en veille et doivent être réacquises (par nouvelle authentification de l'utilisateur) lors du retour de veille. Il est recommandé de définir ce paramètre pour toutes les applications PAM qui prennent en charge la nouvelle authentification automatique via PAM lors de la reprise du système. Si plusieurs sessions du même utilisateur sont ouvertes en parallèle, le répertoire personnel de l'utilisateur restera non suspendu lors de la mise en veille du système tant qu'au moins une des sessions ne définit pas ce paramètre sur activé. Par défaut, désactivé.

Notez que les connexions TTY ne prennent généralement pas en charge la nouvelle authentification lors de la reprise du système. La nouvelle authentification à la reprise du système est principalement un concept implémentable dans les environnements graphiques, sous la forme d'écrans de verrouillage qui apparaissent automatiquement lorsque le système se met en veille. Cela signifie que si un utilisateur utilise simultanément des sessions de connexion graphiques qui implémentent le mécanisme de nouvelle authentification requis et des connexions console qui ne le font pas, le répertoire personnel n'est pas verrouillé pendant la mise en veille, en raison de la logique expliquée ci-dessus. Cela dit, il est possible de définir ce champ pour les connexions TTY également, ignorant le fait que les connexions TTY ne prennent pas en charge le mécanisme de nouvelle authentification. Dans ce cas, les sessions TTY sembleront figées jusqu'à ce que l'utilisateur se connecte sur un autre terminal virtuel (que ce soit via une autre session TTY ou graphiquement) ce qui reprendra le répertoire personnel et débloquera la session TTY d'origine. (Notez que l'absence de verrouillage d'écran sur les sessions TTY signifie que même si la session TTY semble figée, les frappes peuvent toujours être mises en file d'attente, et le contenu de l'écran existant peut être lu sans nouvelle authentification ; cette limitation n'est pas liée à la gestion du répertoire personnel que pam_systemd_home et systemd-homed.service implémentent.)

L'activation de cette option par défaut est fortement recommandée pour toutes les sessions, mais uniquement si le service gérant ces sessions implémente correctement la nouvelle authentification mentionnée ci-dessus. Notez que la nouvelle authentification doit avoir lieu à partir d'un composant s'exécutant en dehors du contexte de l'utilisateur, de sorte qu'elle ne nécessite pas d'accès au répertoire personnel de l'utilisateur pour fonctionner. Traditionnellement, la plupart des environnements de bureau n'implémentent pas le verrouillage d'écran de cette manière et doivent être mis à jour en conséquence.

Ce paramètre peut également être contrôlé via la variable d'environnement $SYSTEMD_HOME_SUSPEND (voir ci-dessous), que pam_systemd_home lit lors de l'initialisation et définit pour les sessions. Si la variable d'environnement est définie et que le paramètre du module est spécifié, ce dernier a la priorité.

Ajouté dans la version 245.

debug[=]

Prend un argument booléen optionnel. Si oui ou sans l'argument, le module enregistrera des informations de débogage lors de son exécution.

Ajouté dans la version 245.

SUPPORT ZONE PERSONNELLE

Les répertoires personnels gérés par systemd-homed.service(8) prennent en charge plusieurs "zones" personnelles, qui sont des répertoires personnels secondaires supplémentaires de l'utilisateur dans le répertoire personnel principal. Par exemple : lors de la connexion, si un utilisateur "lennart" avec un répertoire personnel de /home/lennart spécifie "lennart%versuch1" comme nom de compte lors de la connexion, alors pam_systemd_home exécutera une connexion en tant que "lennart" mais s'assurera que la variable $HOME est définie sur /home/lennart/Areas/versuch1 au lieu du /home/lennart habituel.

Ceci est particulièrement utile lors du partage du même répertoire personnel entre plusieurs systèmes (par exemple, entre un hôte et une VM), avec le désir de partager le répertoire personnel dans une large mesure, mais en gardant une configuration de session séparée en place.

Notez que la zone par défaut à laquelle se connecter peut également être encodée dans l'enregistrement de l'utilisateur, et elle peut être spécifiée parmi les paramètres de configuration de pam_systemd(8). Cependant, une zone explicite spécifiée lors de la connexion (via le "%" décrit ci-dessus) remplace toute valeur par défaut. Notez également que le simple suffixage d'un compte avec "%" lors de la connexion (c'est-à-dire, spécifier un nom de zone vide) a pour effet d'assurer une connexion au répertoire personnel principal, remplaçant toute configuration de zone par défaut via l'enregistrement de l'utilisateur ou PAM.

Notez que tous les mécanismes de connexion ne sont pas compatibles avec la syntaxe "%" lors de la connexion. ssh(8) en particulier ne l'est pas.

Notez que le répertoire de zone à utiliser pour la connexion doit exister pour que la spécification de zone soit respectée. Si une zone est spécifiée lors de la connexion via la logique "%" (ou les autres mécanismes mentionnés) et qu'elle n'existe pas réellement, la requête sera ignorée et l'utilisateur se connectera au répertoire personnel principal à la place.

Typiquement, pour utiliser ce mécanisme, configurez d'abord une zone, comme ceci :

lennart@zeta$ mkdir -p ~/Areas
lennart@zeta$ cp -av /etc/skel ~/Areas/versuch1

Cela devrait suffire pour se connecter à la zone nouvellement créée, soit via un terminal classique (en utilisant "lennart%versuch1" lorsqu'on vous demande le nom d'utilisateur), soit via run0(1) :

lennart@zeta$ run0 --area=versuch1

TYPES DE MODULES FOURNIS

Le module implémente les quatre opérations PAM : auth (pour autoriser l'authentification à l'aide des données chiffrées), account (car les utilisateurs avec des comptes d'utilisateur systemd-homed.service sont décrits dans un enregistrement JSON de l'utilisateur[1] et peuvent être configurés plus en détail que dans la base de données des utilisateurs traditionnelle de Linux), session (car les sessions d'utilisateur doivent être suivies pour implémenter la libération automatique lorsque la dernière session de l'utilisateur a disparu), password (pour changer le mot de passe de chiffrement — également utilisé pour l'authentification de l'utilisateur — via PAM).

ENVIRONNEMENT

Les variables d'environnement suivantes sont initialisées par le module et disponibles pour les processus de la session de l'utilisateur :

$SYSTEMD_HOME=1

Indique que le répertoire personnel de l'utilisateur est géré par systemd-homed.service.

Ajouté dans la version 245.

$SYSTEMD_HOME_SUSPEND=

Indique si la session a été enregistrée avec le mécanisme de suspension activé ou désactivé (voir ci-dessus). La valeur de la variable est soit "0", soit "1". Notez que le module lit la variable lors de son initialisation et la définit pour les sessions.

Ajouté dans la version 246.

EXEMPLE

Voici un exemple de fragment de configuration PAM qui permet aux utilisateurs gérés par systemd-homed.service de se connecter :

#%PAM-1.0
    -auth     [success=done authtok_err=bad perm_denied=bad maxtries=bad default=ignore] pam_systemd_home.so
auth      sufficient pam_unix.so
auth      required   pam_deny.so
account   required   pam_nologin.so
-account  [success=done authtok_expired=bad new_authtok_reqd=bad maxtries=bad acct_expired=bad default=ignore] pam_systemd_home.so
account   required   pam_unix.so
-password sufficient pam_systemd_home.so
password  sufficient pam_unix.so sha512 shadow try_first_pass
password  required   pam_deny.so
-sess

pam_systemd_home.8.en - Arch Linux

NAME

pam_systemd_home - PAM module to manage systemd user session homes

SYNOPSIS

pam_systemd_home.so

DESCRIPTION

The pam_systemd_home.so module integrates with systemd user sessions. It is primarily used to manage user home directories, especially in the context of dynamic user creation and home directory encryption as managed by systemd-homed.service(8).

This module is typically configured in the PAM stack for services that involve user logins, such as login.pam, sshd.pam, or systemd-user.pam.

When a user session starts, the module checks for the presence of a home directory managed by systemd-homed.service(8). If found, it may mount the user's home directory and set up the necessary environment variables.

During session termination, it may unmount the home directory if it was mounted by the module.

OPTIONS

The pam_systemd_home.so module does not support any options.

HOME AREA SUPPORT

pam_systemd_home.so is intended to work alongside systemd-homed.service(8) and homectl(1) to provide robust home directory management. This includes:

  • Automounting of user home directories when a session starts.
  • Support for encrypted home directories, including prompt for passphrase if necessary.
  • Unmounting home directories when a session ends.
  • Integration with user record management (e.g., from files, LDAP, or systemd-cryptouuid).

MODULE TYPES PROVIDED

The following PAM module types are provided:

session
This module type is used to manage the setup and teardown of user sessions, including mounting and unmounting home directories.

ENVIRONMENT

This module may set or use the following environment variables:

HOME
Set to the user's home directory path.
XDG_HOME_DIR
Set to the user's home directory path, if applicable.

EXAMPLE

A typical configuration in /etc/pam.d/systemd-user might look like this:

#%PAM-1.0
auth       required     pam_unix.so
auth       optional     pam_keyinit.so revoke
-session   optional     pam_loginuid.so
-session   optional     pam_systemd_home.so
-session   optional     pam_systemd.so
session    required     pam_unix.so
