NOM

pam_krb5 - Module PAM pour Kerberos

SYNTAXE

auth            sufficient      pam_krb5.so minimum_uid=1000
session         required        pam_krb5.so minimum_uid=1000
account         required        pam_krb5.so minimum_uid=1000
password        sufficient      pam_krb5.so minimum_uid=1000

DESCRIPTION

Le module de service Kerberos pour PAM, typiquement installé à /lib/security/pam_krb5.so, fournit des fonctionnalités pour les quatre opérations PAM : authentification, gestion de compte, gestion de session et gestion de mot de passe. pam_krb5.so est un objet partagé qui est chargé dynamiquement par le sous-système PAM selon les besoins, basé sur la configuration PAM du système. PAM est un système permettant de greffer des modules externes d'authentification et de gestion de session afin que chaque application n'ait pas besoin de connaître la meilleure façon de vérifier l'authentification d'un utilisateur ou de créer une session utilisateur sur ce système. Pour plus de détails sur la configuration de PAM sur votre système, consultez la page man de PAM, souvent pam(7).

Voici les actions de ce module lorsqu'il est appelé depuis chaque groupe :

auth
Fournit les implémentations de pam_authenticate() et pam_setcred(). La première récupère le nom d'utilisateur à partir de la session PAM, demande le mot de passe de l'utilisateur (sauf si configuré pour utiliser un mot de passe déjà saisi) et effectue ensuite une authentification initiale Kerberos, stockant les informations d'identification obtenues (en cas de succès) dans un cache de tickets temporaire. La seconde, en fonction des drapeaux avec lesquels elle est appelée, prend soit le contenu du cache de tickets temporaire et l'écrit dans un cache de tickets persistant appartenant à l'utilisateur, soit utilise le cache de tickets temporaire pour rafraîchir un cache de tickets utilisateur existant.

Les mots de passe aussi longs ou plus longs que PAM_MAX_RESP_SIZE octets (normalement 512 octets) seront rejetés, car des mots de passe excessivement longs peuvent être utilisés comme attaque par déni de service.

Après avoir effectué l'authentification initiale, le module PAM Kerberos tentera d'obtenir des tickets pour une clé dans la keytab du système local, puis vérifiera ces tickets. À moins que cette étape ne soit effectuée, l'authentification est vulnérable à l'usurpation de KDC, mais elle nécessite que le système ait une clé locale et que le module PAM s'exécute en tant qu'utilisateur pouvant lire le fichier keytab (normalement /etc/krb5.keytab. Vous pouvez pointer le module PAM Kerberos vers un autre keytab avec l'option keytab. Si ce keytab ne peut être lu ou si aucune clé n'y est trouvée, le comportement par défaut (potentiellement non sécurisé) est de sauter cette vérification. Si vous voulez plutôt échouer l'authentification si les tickets obtenus ne peuvent être vérifiés, définissez "verify_ap_req_nofail" sur true dans la section [libdefaults] de /etc/krb5.conf. Notez que cela affectera les applications autres que ce module PAM.

Par défaut, chaque fois que l'utilisateur est authentifié, une vérification d'autorisation de base sera également effectuée à l'aide de krb5_kuserok(). Le comportement par défaut de cette fonction est de vérifier le compte de l'utilisateur pour un fichier .k5login et, si celui-ci est présent, de s'assurer que le principal de l'utilisateur est listé dans ce fichier. Si .k5login n'est pas présent, la vérification par défaut consiste à s'assurer que le principal de l'utilisateur se trouve dans le domaine local par défaut et que la partie utilisateur du principal correspond au nom du compte (cela peut être modifié en configurant une correspondance personnalisée aname vers localname dans krb5.conf ; voir la documentation Kerberos pour les détails). Ceci peut être personnalisé avec plusieurs options de configuration ; voir ci-dessous.

Si le nom d'utilisateur fourni à PAM contient un "@" et que Kerberos peut, en traitant le nom d'utilisateur comme un principal, le mapper à un nom de compte local, pam_authenticate() changera l'utilisateur PAM vers ce nom de compte local. Cela permet aux utilisateurs de se connecter avec leur principal Kerberos et de laisser Kerberos s'occuper du mappage vers un compte. Ceci peut être désactivé avec l'option no_update_user. Soyez conscient, cependant, que cette fonctionnalité ne peut pas être utilisée avec OpenSSH. OpenSSH rejettera les noms d'utilisateur qui ne correspondent pas aux comptes locaux avant que ce remappage puisse être effectué et passera un mot de passe invalide au module PAM. Soyez également conscient que plusieurs autres modules PAM courants, tels que pam_securetty, s'attendent à pouvoir rechercher l'utilisateur avec getpwnam() et ne peuvent pas être appelés avant pam_krb5 lors de l'utilisation de cette fonctionnalité.

Lorsque pam_setcred() est appelé pour initialiser un nouveau cache de tickets, la variable d'environnement KRB5CCNAME est définie sur le chemin de ce cache de tickets. Par défaut, le cache sera nommé /tmp/krb5cc_UID_RANDOM où UID est l'UID de l'utilisateur et RANDOM est composé de six lettres choisies aléatoirement. Ceci peut être configuré avec les options ccache et ccache_dir.

pam-krb5 n'utilise pas l'emplacement de cache de tickets par défaut ni default_cc_name dans la section "[libdefaults]" de krb5.conf. L'emplacement de cache par défaut partagerait un cache pour toutes les sessions du même utilisateur, ce qui provoque un comportement confus lorsque l'utilisateur se déconnecte d'une de ses multiples sessions.

Si pam_setcred() initialise un nouveau cache de tickets, il configurera également ce cache de tickets pour qu'il soit supprimé à la fermeture de la session PAM. Normalement, le programme appelant (login, sshd, etc.) exécutera le shell de l'utilisateur comme sous-processus, attendera sa sortie, puis fermera la session PAM, nettoyant ainsi la session de l'utilisateur.

session
Fournit les implémentations de pam_open_session(), qui équivaut à appeler pam_setcred() avec le drapeau PAM_ESTABLISH_CRED, et pam_close_session(), qui détruit le cache de tickets créé par pam_setcred().
account
Fournit une implémentation de pam_acct_mgmt(). Tout ce qu'elle fait est d'effectuer la même vérification d'autorisation que celle effectuée par l'implémentation pam_authenticate() décrite ci-dessus.
password
Fournit une implémentation de pam_chauthtok(), qui gère les changements de mot de passe. L'utilisateur est invité à saisir son mot de passe actuel (sauf si configuré pour utiliser un mot de passe déjà saisi) et le module PAM obtient alors les informations d'identification pour le principal Kerberos spécial "kadmin/changepw". Il invite ensuite l'utilisateur à saisir un nouveau mot de passe, deux fois pour s'assurer que l'utilisateur l'a correctement saisi (là encore, sauf si configuré pour utiliser un mot de passe déjà saisi), puis effectue un changement de mot de passe Kerberos.

Les mots de passe aussi longs ou plus longs que PAM_MAX_RESP_SIZE octets (normalement 512 octets) seront rejetés, car des mots de passe excessivement longs peuvent être utilisés comme attaque par déni de service.

Contrairement au module de mot de passe Unix normal, ce module permettra à n'importe quel utilisateur de changer le mot de passe de tout autre utilisateur s'il connaît l'ancien mot de passe. De plus, contrairement au module de mot de passe Unix normal, root sera toujours invité à saisir l'ancien mot de passe, car root n'a pas de statut spécial dans Kerberos. (Pour changer les mots de passe dans Kerberos sans connaître l'ancien mot de passe, utilisez plutôt kadmin(8).)

Les appels de gestion de compte et de session du module PAM Kerberos retourneront PAM_IGNORE s'ils sont appelés dans le contexte d'une session PAM pour un utilisateur qui ne s'est pas authentifié avec Kerberos (un code de retour "ignore" dans le langage de configuration PAM Linux).

Notez que ce module suppose que le réseau est disponible pour effectuer une authentification Kerberos. Si le réseau n'est pas disponible, certaines bibliothèques Kerberos ont des délais d'attente plus longs que le délai imposé par le processus de connexion. Cela signifie qu'utiliser ce module sans précaution peut rendre impossible la connexion en console en tant que root. Pour cette raison, vous devriez toujours utiliser les options ignore_root ou minimum_uid, lister un module d'authentification local tel que pam_unix en premier avec un champ de contrôle "sufficient" afin que le module PAM Kerberos soit ignoré si l'authentification par mot de passe local a réussi.

Ce n'est pas le même module PAM que le module PAM Kerberos disponible sur Sourceforge, ni celui inclus dans les systèmes Red Hat. Il prend en charge beaucoup des mêmes options, possède quelques options supplémentaires et ne prend pas en charge certaines des options que ces modules font.

CONFIGURATION

Le module PAM Kerberos prend de nombreuses options, dont toutes ne sont pas pertinentes pour ev

groupe PAM; les options qui ne sont pas pertinentes seront silencieusement ignorées. Chacune de ces options peut être configurée dans la configuration PAM comme arguments listés après "pam_krb5.so". Certaines des options peuvent également être configurées dans le fichier système krb5.conf ; si cela est possible, cela sera noté ci-dessous dans la description de l'option.

Pour définir une option booléenne dans le fichier de configuration PAM, donnez simplement le nom de l'option dans les arguments. Pour définir une option qui prend un argument, suivez le nom de l'option par un signe égal (=) et la valeur, sans espace séparateur. Les espaces dans les arguments d'option ne sont pas pris en charge dans la configuration PAM.

Pour définir une option pour le module PAM dans le fichier système krb5.conf, placez cette option dans la section "[appdefaults]". Toutes les options doivent être suivies d'un signe égal (=) et d'une valeur, donc pour les options booléennes, ajoutez "= true". Le module PAM Kerberos recherchera les options soit au niveau supérieur de la section "[appdefaults]", soit dans une sous-section nommée "pam", à l'intérieur ou à l'extérieur d'une section pour le royaume. Par exemple, le fragment suivant d'un fichier krb5.conf définirait forwardable à true, minimum_uid à 1000, et définirait ignore_k5login uniquement si le royaume est EXAMPLE.COM.

[appdefaults]
    forwardable = true
    pam = {
        minimum_uid = 1000
        EXAMPLE.COM = {
            ignore_k5login = true
        }
    }

Pour plus d'informations sur la syntaxe de krb5.conf, consultez krb5.conf(5). Notez que les options qui dépendent du royaume seront définies uniquement sur la base du royaume par défaut, tel que configuré dans krb5.conf(5) ou tel que défini par l'option realm décrite ci-dessous. Si l'utilisateur s'authentifie auprès d'un compte qualifié avec un royaume, ce royaume ne sera pas utilisé pour déterminer quelles options s'appliqueront.

Il n'y a aucune différence pour le module PAM que les options soient spécifiées au niveau supérieur ou dans une section "pam" ; la section "pam" est prise en charge au cas où il y aurait des options qui devraient être définies pour le module PAM mais pas pour d'autres applications.

Si la même option est définie dans krb5.conf et dans la configuration PAM, cette dernière a priorité. Notez cependant qu'en raison de la syntaxe de configuration, il n'y a aucun moyen de désactiver une option booléenne dans la configuration PAM qui a été activée dans krb5.conf.

Le début de chaque description d'option est annoté avec la version de pam-krb5 dans laquelle cette option a été ajoutée avec sa signification actuelle.

Autorisation

alt_auth_map=<format>
[3.12] Ceci fonctionne de manière similaire à l'option search_k5login. L'argument <format> est utilisé comme principal Kerberos d'authentification, avec tout %s dans <format> remplacé par le nom d'utilisateur. Si le nom d'utilisateur contient un "@", seule la partie du nom d'utilisateur avant le royaume est utilisée pour remplacer %s. Si <format> contient un royaume, il sera utilisé ; sinon, le royaume du nom d'utilisateur (le cas échéant) sera ajouté au résultat. Il n'y a pas de suppression de guillemets.

Si cette option est présente, le comportement par défaut est d'essayer d'abord ce principal alternatif, puis de revenir au comportement standard en cas d'échec. L'utilisation principale est de permettre l'utilisation de principaux alternatifs pour l'authentification dans des programmes comme sudo. La plupart des exemples ressembleront à :

alt_auth_map=%s/root

ce qui tente d'abord l'authentification en tant qu'instance root du nom d'utilisateur, puis revient au nom d'utilisateur régulier (mais voir force_alt_auth et only_alt_auth).

Cette option permet également un moyen simple de tenter d'abord l'authentification dans un royaume alternatif, puis de revenir au royaume principal. Un réglage comme :

alt_auth_map=%s@EXAMPLE.COM

tentera d'abord l'authentification dans le royaume EXAMPLE.COM, puis reviendra au royaume par défaut local. C'est plus pratique que d'exécuter le module plusieurs fois avec plusieurs royaumes par défaut définis avec realm, mais c'est très limité : seuls deux royaumes peuvent être essayés, et le royaume alternatif est toujours essayé en premier.

Cette option peut être configurée dans "[appdefaults]" dans krb5.conf, bien que normalement cela n'ait pas de sens de le faire ; normalement, elle est utilisée dans les options PAM de la configuration pour des programmes spécifiques. Elle n'est applicable qu'aux groupes d'authentification et de compte. Si cette option est définie pour le groupe d'authentification, assurez-vous de la définir également pour le groupe de compte, sinon l'autorisation de compte pourrait échouer.

force_alt_auth
[3.12] Cette option est utilisée avec alt_auth_map et force l'authentification en tant que principal mappé si ce principal existe dans le KDC. Ce n'est que si le KDC retourne « principal inconnu » que le module PAM Kerberos revient à l'authentification normale. Ceci peut être utilisé pour forcer l'authentification avec une instance alternative. Si alt_auth_map n'est pas défini, elle n'a aucun effet.

Cette option peut être configurée dans "[appdefaults]" dans krb5.conf et n'est applicable qu'au groupe d'authentification.

ignore_k5login
[2.0] Ne jamais rechercher de fichier .k5login dans le répertoire personnel de l'utilisateur. Au lieu de cela, vérifiez uniquement que le principal Kerberos correspond au nom du compte local. La vérification par défaut consiste à s'assurer que le royaume correspond au royaume local et que la partie utilisateur du principal correspond au nom du compte local, mais cela peut être personnalisé en configurant un mappage aname vers localname dans krb5.conf.

Cette option peut être configurée dans "[appdefaults]" dans krb5.conf et n'est applicable qu'aux groupes d'authentification et de compte.

ignore_root
[1.1] Ne rien faire si le nom d'utilisateur est "root". Les appels d'authentification et de mot de passe échoueront silencieusement (permettant d'ignorer ce statut via un contrôle "optional" ou "sufficient"), et les appels de compte et de session (y compris pam_setcred) retourneront PAM_IGNORE, indiquant à la bibliothèque PAM de procéder comme s'ils n'avaient pas été mentionnés dans la configuration PAM. Cette option est prise en charge et le restera, mais normalement, vous voudrez utiliser minimum_uid à la place.

Cette option peut être configurée dans "[appdefaults]" dans krb5.conf.

minimum_uid=<uid>
[2.0] Ne rien faire si le nom du compte authentifié correspond à un compte local et que ce compte local a un UID inférieur à <uid>. Si ces deux conditions sont vraies, les appels d'authentification et de mot de passe échoueront silencieusement (permettant d'ignorer ce statut via un contrôle "optional" ou "sufficient"), et les appels de compte et de session (y compris pam_setcred) retourneront PAM_IGNORE, indiquant à la bibliothèque PAM de procéder comme s'ils n'avaient pas été mentionnés dans la configuration PAM.

L'utilisation de cette option est fortement recommandée si vous n'avez pas besoin d'utiliser Kerberos pour authentifier les connexions par mot de passe au compte root (ce qui n'est pas recommandé car Kerberos nécessite une connexion réseau). Elle fournit une certaine sécurité supplémentaire contre les principaux utilisateurs qui correspondent accidentellement à un compte système et s'authentifient incorrectement en tant que ce compte système.

Cette option peut être configurée dans "[appdefaults]" dans krb5.conf.

only_alt_auth
[3.12] Cette option est utilisée avec alt_auth_map et force l'utilisation du principal mappé pour l'authentification. Elle désactive le retour à l'authentification normale dans tous les cas et remplace search_k5login et force_alt_auth. Si alt_auth_map n'est pas défini, elle n'a aucun effet et le comportement d'authentification standard est utilisé.

Cette option peut être configurée dans "[appdefaults]" dans krb5.conf et n'est applicable qu'au groupe d'authentification.

search_k5login
[2.0] Normalement, l'implémentation Kerberos de pam_authenticate tente d'obtenir des tickets pour le nom d'utilisateur d'authentification dans le royaume local. Si cette option est définie et que l'utilisateur local possède un fichier .k5login dans son répertoire personnel, le module ouvrira et lira ce fichier .k5login, tentant d'utiliser le mot de passe fourni pour s'authentifier en tant que chaque principal répertorié là-bas à tour de rôle. Si l'une de ces authentifications réussit, l'utilisateur sera authentifié avec succès ; sinon, l'authentification échouera. Cette option est utile pour permettre l'authentification par mot de passe (via la console ou sshd sans support GSS-API) pour des comptes partagés. S'il n'y a pas de fichier .k5login, le comportement est le même que la normale. L'utilisation de cette option nécessite que le fichier .k5login de l'utilisateur soit lisible au moment de l'authentification.

Cette option peut être configurée dans "[appdefaults]" dans krb5.conf et n'est applicable qu'au groupe d'authentification.

Comportement Kerberos

anon_fast
[4.6] Tenter d'utiliser Flexible Authentication Secure Tunneling (FAST) en s'authentifiant d'abord en tant qu'utilisateur anonyme (WELLKNOWN/ANONYMOUS) et en utilisant ses informations d'identification comme armure FAST. Cela nécessite que PKINIT anonyme soit activé pour le royaume local, que PKINIT soit configuré sur le système local, et que la bibliothèque Kerberos prenne en charge FAST et PKINIT anonyme.

FAST est un mécanisme pour protéger Kerberos contre les attaques par devinettes de mot de passe et fournir d'autres améliorations de sécurité. Pour fonctionner, FAST nécessite qu'un ticket soit obtenu avec une clé forte pour protéger les échanges avec des mots de passe utilisateur potentiellement plus faibles. Cette option utilise l'authentification anonyme pour obtenir cette clé, puis l'utilise pour protéger l'authentification ultérieure.

Si PKINIT anonyme n'est pas disponible ou échoue, FAST ne sera pas utilisé et l'authentification se déroulera normalement.

Pour utiliser à la place une

ticket cache pour le FAST identifiants, utilisez fast_ccache au lieu de cette option. Si fast_ccache et anon_fast sont tous deux définis, le cache de tickets nommé par fast_ccache sera essayé en premier, et le module PAM Kerberos tentera ensuite l'authentification PKINIT anonyme si ce cache n'a pas pu être utilisé.

Cette option peut être définie dans "[appdefaults]" dans krb5.conf et n'est applicable qu'aux groupes auth et password.

L'opération est la même que lors de l'utilisation de l'option fast_ccache, mais le cache est créé et détruit automatiquement. Si les options fast_ccache et anon_fast sont utilisées, fast_ccache a la priorité et aucune authentification anonyme n'est effectuée.

fast_ccache=<ccache_name>
[4.3] Identique à anon_fast, mais utilise un cache de tickets Kerberos existant au lieu de PKINIT anonyme. Cela permet d'utiliser FAST avec un royaume qui ne prend pas en charge PKINIT ou l'authentification anonyme.

<ccache_name> doit être un cache d'identifiants contenant un ticket obtenu à l'aide d'une clé forte, telle que la clé aléatoire du principal de l'hôte du système local. Si <ccache_name> nomme un cache de tickets lisible par le processus d'authentification et contenant des tickets, FAST sera tenté. La manière la plus simple d'utiliser cette option est d'utiliser un programme comme k5start pour maintenir un cache de tickets à l'aide du keytab de l'hôte. Ce cache de tickets ne devrait normalement être lisible que par root, donc cette option ne pourra pas protéger les authentifications effectuées par des utilisateurs non-root (tels que les économiseurs d'écran).

Si aucun identifiant n'est présent dans le cache de tickets, ou si le cache de tickets n'existe pas ou n'est pas lisible, FAST ne sera pas utilisé et l'authentification se poursuivra normalement. Cependant, si les identifiants de ce cache de tickets sont expirés, l'authentification échouera si le KDC prend en charge FAST.

Pour utiliser PKINIT anonyme afin de protéger l'échange FAST, utilisez plutôt l'option anon_fast. anon_fast est plus facile à configurer, car aucun cache de tickets existant n'est requis, mais nécessite que PKINIT soit disponible et configuré, et que le royaume local prenne en charge l'authentification anonyme. Si fast_ccache et anon_fast sont tous deux définis, le cache de tickets nommé par fast_ccache sera essayé en premier, et le module PAM Kerberos tentera ensuite l'authentification PKINIT anonyme si ce cache n'a pas pu être utilisé.

Cette option peut être définie dans "[appdefaults]" dans krb5.conf et n'est applicable qu'aux groupes auth et password.

forwardable
[1.0] Obtenir des tickets transférables. S'il est défini (vrai ou faux, bien qu'il ne puisse être défini sur faux que dans krb5.conf), cela remplace la valeur par défaut de la bibliothèque Kerberos définie dans la section [libdefaults] de krb5.conf.

Cette option peut être définie dans "[appdefaults]" dans krb5.conf et n'est applicable qu'au groupe auth.

keytab=<path>
[3.0] Spécifie le keytab à utiliser lors de la validation des identifiants de l'utilisateur. La valeur par défaut est le keytab système par défaut (normalement /etc/krb5.keytab), qui n'est généralement lisible que par root. Les applications qui ne s'exécutent pas en tant que root et qui utilisent ce module PAM pour l'authentification peuvent souhaiter pointer vers un autre keytab que l'application peut lire. Le premier principal trouvé dans le keytab sera utilisé comme principal pour la vérification des identifiants.

Cette option peut être définie dans "[appdefaults]" dans krb5.conf et n'est applicable qu'au groupe auth.

realm=<realm>
[2.2] Définit le royaume Kerberos par défaut et obtient les identifiants dans ce royaume, plutôt que dans le royaume par défaut normal de ce système. Si cette option est utilisée, elle doit être définie pour tous les groupes utilisés pour des résultats cohérents. Ce réglage affectera les décisions d'autorisation car il modifie le royaume par défaut. Ce réglage modifiera également le principal de service utilisé pour vérifier les identifiants obtenus afin qu'il soit dans le royaume spécifié.

Si vous souhaitez uniquement définir le royaume supposé pour les principaux utilisateurs sans modifier le royaume pour les décisions d'autorisation ou le principal de service utilisé pour vérifier les identifiants, consultez l'option user_realm.

renew_lifetime=<lifetime>
[2.0] Obtenir des tickets renouvelables avec une durée de vie maximale de renouvellement de <lifetime>. <lifetime> doit être une chaîne de durée de vie Kerberos telle que "2d4h10m" ou une durée en minutes. S'il est défini, cela remplace la valeur par défaut de la bibliothèque Kerberos définie dans la section [libdefaults] de krb5.conf.

Cette option peut être définie dans "[appdefaults]" dans krb5.conf et n'est applicable qu'au groupe auth.

ticket_lifetime=<lifetime>
[3.0] Obtenir des tickets avec une durée de vie maximale de <lifetime>. <lifetime> doit être une chaîne de durée de vie Kerberos telle que "2d4h10m" ou une durée en minutes. S'il est défini, cela remplace la valeur par défaut de la bibliothèque Kerberos définie dans la section [libdefaults] de krb5.conf.

Cette option peut être définie dans "[appdefaults]" dans krb5.conf et n'est applicable qu'au groupe auth.

user_realm
[4.6] Obtenir les identifiants dans le royaume spécifié plutôt que dans le royaume par défaut de ce système. Si cette option est utilisée, elle doit être définie pour tous les groupes utilisés pour des résultats cohérents (bien que le groupe de comptes ne se soucie actuellement pas du royaume). Cela ne modifiera pas les décisions d'autorisation. Si les identifiants obtenus sont censés permettre l'accès à un compte shell, l'utilisateur aura besoin d'une entrée appropriée dans son fichier .k5login ou le système devra avoir une correspondance personnalisée aname_to_localname.

Comportement PAM

clear_on_fail
[3.9] Lors du changement de mot de passe, PAM effectue d'abord une vérification préliminaire via la pile complète des mots de passe, puis appelle à nouveau chaque module pour effectuer le changement de mot de passe. Après cette vérification préliminaire, l'ordre d'invocation des modules est fixe. Cela signifie que même si le changement de mot de passe Kerberos échoue (ou si l'un des autres changements de mot de passe dans la pile échoue), d'autres modules PAM de mot de passe dans la pile seront toujours appelés même si le module défaillant est marqué comme requis ou obligatoire. Lors de l'utilisation de plusieurs modules PAM de mot de passe pour synchroniser les mots de passe entre plusieurs systèmes lors de leur changement, ce comportement peut entraîner des différences indésirables entre les environnements.

La définition de cette option fournit un moyen de contourner ce comportement. Si cette option est définie et qu'une tentative de changement de mot de passe Kerberos échoue (en raison d'erreurs réseau ou de la vérification de la force du mot de passe sur le KDC, par exemple), ce module effacera le mot de passe stocké dans la pile PAM. Cela obligera les modules ultérieurs qui ont use_authtok défini à échouer afin que ces environnements ne se désynchronisent pas avec le mot de passe dans Kerberos. Le module PAM Kerberos ne modifiera pas le mot de passe stocké s'il ignore l'utilisateur en raison d'une configuration telle que minimum_uid.

Malheureusement, la définition de cette option interfère avec d'autres configurations PAM souhaitables, telles que tenter de changer le mot de passe dans Kerberos en premier lieu et de se rabattre sur la base de données de mots de passe Unix locale en cas d'échec. Elle n'est donc pas la valeur par défaut. Activez-la (et listez pam_krb5 en premier après pam_cracklib s'il est utilisé) lors de la synchronisation des mots de passe entre plusieurs environnements.

Cette option peut être définie dans "[appdefaults]" dans krb5.conf et n'est applicable qu'au groupe password.

debug
[1.0] Enregistrez des informations de traçage et de débogage plus verbeuses dans syslog avec la priorité LOG_DEBUG, y compris l'entrée et la sortie de chacune des interfaces PAM externes (sauf pam_close_session).

Cette option peut être définie dans "[appdefaults]" dans krb5.conf.

defer_pwchange
[3.11] Par défaut, pam-krb5 laisse la bibliothèque Kerberos gérer la demande de changement de mot de passe si le mot de passe d'un compte est expiré pendant le groupe auth. Si cela échoue, pam_authenticate() renvoie une erreur.

Conformément à la norme PAM, ce n'est pas la bonne façon de gérer les mots de passe expirés. Au lieu de cela, pam_authenticate() devrait renvoyer un succès sans tenter de changement de mot de passe, puis pam_acct_mgmt() devrait renvoyer PAM_NEW_AUTHTOK_REQD, auquel cas l'application appelante est responsable soit de rejeter l'authentification, soit d'appeler pam_chauthtok(). Cependant, suivre la norme exige que toutes les applications appellent pam_acct_mgmt() et vérifient son statut de retour ; sinon, les comptes expirés pourraient réussir à s'authentifier. De nombreuses applications ne le font pas.

Si cette option est définie, pam-krb5 utilise le mécanisme PAM entièrement correct pour gérer les comptes expirés au lieu d'échouer dans pam_authenticate(). En raison du risque de sécurité des applications défectueuses généralisées, soyez très prudent lorsque vous activez cette option. Elle ne devrait normalement être activée que pour résoudre un problème spécifique (tel que l'utilisation de bibliothèques Kerberos Solaris qui ne prennent pas en charge la demande de changement de mot de passe pendant l'authentification), et uniquement pour des applications spécifiques connues pour appeler pam_acct_mgmt() et vérifier correctement son statut de retour.

Cette option n'est prise en charge que lorsque pam-krb5 est compilé avec MIT Kerberos. Si compilé avec Heimdal, cette option ne fait rien et la gestion normale des mots de passe expirés se produit toujours. (Heimdal manque de l'API nécessaire pour implémenter cette option, du moins à partir de la version 1.6.)

Cette option peut être définie dans "[appdefaults]" dans krb5.conf et n'est applicable qu'au groupe auth.

fail_pwchange
[4.2] Par défaut, pam-krb5 laisse la bibliothèque Kerberos gérer la demande de changement de mot de passe si le mot de passe d'un compte est expiré pendant le groupe auth.
Si cette option est définie, les mots de passe expirés sont plutôt traités comme un échec d'authentification identique à un mot de passe incorrect. Voir également defer_pwchange et force_pwchange.

Cette option peut être définie dans "[appdefaults]" dans krb5.conf et n'est applicable qu'au groupe d'authentification.

force_pwchange
[3.11] Si cette option est définie et que l'authentification échoue avec une erreur Kerberos indiquant que le mot de passe de l'utilisateur a expiré, tentez de changer immédiatement son mot de passe pendant l'étape d'authentification. Dans des circonstances normales, ceci est inutile. La plupart des bibliothèques Kerberos le font pour vous, et la définition de cette option incitera l'utilisateur à changer son mot de passe deux fois si la première tentative (effectuée par la bibliothèque Kerberos) échoue. Cependant, certaines bibliothèques Kerberos système (comme celle de Solaris) ont l'invite de changement de mot de passe désactivée dans la bibliothèque Kerberos ; sur ces systèmes, vous pouvez définir cette option pour simuler le comportement normal de la bibliothèque.

Cette option peut être définie dans "[appdefaults]" dans krb5.conf et n'est applicable qu'au groupe d'authentification.

no_update_user
[4.7] Normalement, si pam-krb5 est capable de canoniser le principal en un nom local en utilisant krb5_aname_to_localname() ou des appels similaires, il modifie la variable PAM_USER pour cette session PAM au nom local canonisé. La définition de cette option désactive ce comportement et laisse PAM_USER défini sur l'identité d'authentification initiale.

Cette option peut être définie dans "[appdefaults]" dans krb5.conf et n'est applicable qu'au groupe d'authentification.

silent
[1.0] Ne pas afficher les messages et les erreurs de Kerberos, tels que les avertissements d'expiration de mot de passe, à l'utilisateur via le prompteur. Ceci est équivalent au comportement lorsque l'application passe PAM_SILENT, mais peut être défini dans la configuration PAM.

Cette option n'est applicable qu'aux groupes d'authentification et de mot de passe.

trace=<journal>
[4.6] Active la journalisation des traces de la bibliothèque Kerberos dans le fichier journal spécifié si elle est prise en charge par la bibliothèque Kerberos. Ceci est destiné au débogage temporaire. Le fichier spécifié sera ajouté sans vérification de sécurité supplémentaire, ne spécifiez donc pas de fichier dans un répertoire accessible en écriture publique comme /tmp.

PKINIT

pkinit_anchors=<ancres>
[3.0] Lors de l'authentification PKINIT, utilisez <ancres> comme ancres de confiance client. Il s'agit normalement d'une référence à un fichier contenant les autorités de certification de confiance. Cette option n'est utilisée que si try_pkinit ou use_pkinit sont définis.

Cette option peut être définie dans "[appdefaults]" dans krb5.conf et n'est applicable qu'aux groupes d'authentification et de mot de passe.

pkinit_prompt
[3.0] Avant de tenter l'authentification PKINIT, invitez l'utilisateur à insérer une carte à puce. Vous pourriez vouloir définir cette option pour des programmes tels que gnome-screensaver qui appellent PAM dès que la souris est touchée et ne donnent pas à l'utilisateur la possibilité d'entrer d'abord la carte à puce. Toute information entrée lors de la première invite est ignorée. Si try_pkinit est défini, un utilisateur qui souhaite utiliser un mot de passe à la place peut simplement appuyer sur Entrée puis entrer son mot de passe normalement. Cette option n'est utilisée que si try_pkinit ou use_pkinit sont définis.

Cette option peut être définie dans "[appdefaults]" dans krb5.conf et n'est applicable qu'aux groupes d'authentification et de mot de passe.

pkinit_user=<identifiant_utilisateur>
[3.0] Lors de l'authentification PKINIT, utilisez <identifiant_utilisateur> comme identifiant utilisateur. La valeur de cette chaîne dépend fortement du type d'implémentation PKINIT que vous utilisez, mais sera généralement quelque chose comme : 
PKCS11:/usr/lib/pkcs11/lib/soft-pkcs11.so

pour spécifier le module à utiliser avec une carte à puce. Il peut également pointer vers un certificat utilisateur ou vers d'autres types d'identifiants utilisateur. Voir la documentation de la bibliothèque Kerberos pour plus de détails. Cette option n'est utilisée que si try_pkinit ou use_pkinit sont définis.

Cette option peut être définie dans "[appdefaults]" dans krb5.conf et n'est applicable qu'aux groupes d'authentification et de mot de passe.

preauth_opt=<option>
[3.3] Définit une option de pré-authentification (actuellement applicable uniquement lorsque compilé avec MIT Kerberos). <option> est soit une paire clé/valeur avec la clé séparée de la valeur par "=", soit une option booléenne (auquel cas elle est activée). Dans krb5.conf, plusieurs options doivent être séparées par des espaces. Dans la configuration PAM, cette option peut être donnée plusieurs fois pour définir plusieurs options. Dans les deux cas, <option> ne peut pas contenir d'espace.

L'utilisation principale de cette option, du moins dans un avenir proche, sera de définir les options pour le support PKINIT de MIT Kerberos. Pour la liste complète des options possibles, voir la documentation du plugin PKINIT. Au moment de la rédaction, "X509_user_identity" est équivalent à pkinit_user et "X509_anchors" est équivalent à pkinit_anchors. "flag_DSA_PROTOCOL" ne peut être défini que via cette option.

Tous les paramètres définis avec cette option sont appliqués après les options pkinit_anchors et pkinit_user, donc si un paramètre équivalent est défini via preauth_opt, il remplacera probablement l'autre paramètre.

Cette option peut être définie dans "[appdefaults]" dans krb5.conf et n'est applicable qu'aux groupes d'authentification et de mot de passe. Notez qu'il n'existe aucun moyen de supprimer un paramètre défini dans krb5.conf en utilisant la configuration PAM, mais les options définies dans la configuration PAM sont appliquées après les options définies dans krb5.conf et peuvent donc remplacer les paramètres antérieurs.

try_pkinit
[3.0] Tente l'authentification PKINIT avant d'essayer un mot de passe régulier. Vous devrez probablement également définir l'option de configuration pkinit_user. Si PKINIT échoue, le module PAM se rabattra sur l'authentification par mot de passe régulier. Cette option n'est actuellement prise en charge que si pam-krb5 a été compilé contre Heimdal 0.8rc1 ou une version ultérieure, ou MIT Kerberos 1.6.3 ou une version ultérieure.

Si cette option est définie et que pam-krb5 est compilé contre MIT Kerberos, et que PKINIT échoue et que le module se rabat sur l'authentification par mot de passe, le mot de passe de l'utilisateur ne sera pas stocké dans la pile PAM pour les modules suivants. Il s'agit d'un bogue dans l'interaction entre le module et MIT Kerberos qui nécessite une refonte de la méthode d'authentification PKINIT pour être corrigé.

Cette option peut être définie dans "[appdefaults]" dans krb5.conf et n'est applicable qu'aux groupes d'authentification et de mot de passe.

use_pkinit
[3.0, 4.9 pour MIT Kerberos] Requiert l'authentification PKINIT. Vous devrez probablement également définir l'option de configuration pkinit_user. Si PKINIT échoue, l'authentification échouera. Cette option n'est prise en charge que si pam-krb5 a été compilé contre Heimdal 0.8rc1 ou une version ultérieure, ou MIT Kerberos 1.12 ou une version ultérieure.

Soyez conscient que, avec MIT Kerberos, cette option est implémentée en utilisant un répondeur sans prompteur, et donc tous les messages informatifs des bibliothèques Kerberos ou du KDC pendant l'authentification ne seront pas affichés.

Cette option peut être définie dans "[appdefaults]" dans krb5.conf et n'est applicable qu'aux groupes d'authentification et de mot de passe.

Invites

banner=<bannière>
[3.0] Par défaut, les invites lors d'un changement de mot de passe sont : 
Mot de passe Kerberos actuel :
Entrez le nouveau mot de passe Kerberos :
Retypez le nouveau mot de passe Kerberos :

La chaîne « Kerberos » est insérée pour que les utilisateurs ne soient pas confus quant au mot de passe qu'ils changent. Définir cette option remplace le mot « Kerberos » par ce que cette option est définie. Définir cette option sur une chaîne vide supprime complètement le mot avant « mot de passe : ».

Si elle est définie dans la configuration PAM, <bannière> ne peut pas contenir d'espace. Si vous souhaitez une valeur contenant des espaces, définissez-la dans krb5.conf.

Cette option peut être définie dans "[appdefaults]" dans krb5.conf et n'est applicable qu'au groupe de mots de passe.

expose_account
[3.0] Par défaut, l'invite de mot de passe du module PAM Kerberos est simplement « Mot de passe : ». Cela évite de divulguer des informations sur le royaume système ou les conversions de compte en principal. Si cette option est définie, la chaîne « pour <principal> » est ajoutée avant le côlon, où <principal> est le principal de l'utilisateur. Cette chaîne est également ajoutée avant le côlon sur les invites lors du changement de mot de passe de l'utilisateur.

L'activation de cette option avec ChallengeResponseAuthentication activé dans OpenSSH peut causer des problèmes pour certains clients ssh qui ne reconnaissent que « Mot de passe : » comme invite. Cette option est automatiquement désactivée si search_k5login est activé, car le principal affiché serait inexact.

Cette option peut être définie dans "[appdefaults]" dans krb5.conf et n'est applicable qu'aux groupes d'authentification et de mot de passe.

force_first_pass
[4.0] Utilise le mot de passe obtenu par un module d'authentification ou de mot de passe précédent pour authentifier l'utilisateur sans demander à nouveau à l'utilisateur. Si aucun module précédent n'a obtenu le mot de passe de l'utilisateur, échoue sans demander à l'utilisateur. Voir également try_first_pass et use_first_pass pour des versions plus faibles de cette option.

Cette option n'est applicable qu'aux groupes d'authentification et de mot de passe. Pour le groupe de mots de passe, elle s'applique uniquement à l'ancien

OPTIONS

The pam_krb5 module supports the following options:

expose_account
[4.0] Do not hide the fact that Kerberos authentication is being used. Normally, pam_krb5 tries to hide this fact by making the prompts look like standard password prompts. This option will cause the module to reveal that it is performing Kerberos authentication. This is useful when using Kerberos authentication in conjunction with the challenge authentication mechanism of OpenSSH, as clients may have trouble with prompts other than "Password:".
force_first_pass
[3.0] Similar to use_first_pass, but fail without prompting if the previous module did not obtain the user's password. This option has no effect if the authentication module is first in the stack or if no previous module obtained the user's password. Also see try_first_pass for a weaker version of this option.
hide_restricted_principals
[3.4] Hide the fact that Kerberos authentication is being used if the principal is restricted. If this option is set, the module will behave as if the expose_account option is not set. This is the default behavior.
k5login_path
[4.1] Specify the path to the user's .k5login file. The default is ~/.k5login. This option may be specified multiple times to allow for multiple .k5login files. The default path is always searched first, before any specified paths.
map_})^{principals
[3.5] Allow mapping of principals to local user accounts. This option allows the user to specify a mapping from Kerberos principals to local user accounts. The mapping is specified in the form principal=user, where principal is the Kerberos principal name and user is the local user name. This option may be specified multiple times. The default is to not map any principals.
no_prompt
[4.6] Never prompt for the current password. Instead, pass in a NULL password to the Kerberos library and let the Kerberos library do the prompting. This may be needed if, for example, the Kerberos library is configured to use other authentication mechanisms than passwords and needs full control over the prompting process.

The major disadvantage of this option is that it means the PAM module will never see the user's password and therefore cannot save it in the PAM module data for any subsequent modules. In other words, this option cannot be used if another module is in the stack behind the Kerberos PAM module and wants to use use_first_pass. The Kerberos library also usually includes the principal in the prompt, and therefore this option implies behavior similar to expose_account. Similar to expose_account, this can cause problems with OpenSSH if ChallengeResponseAuthentication is enabled, since clients may not recognize password prompts other than "Password:".

Using this option with search_k5login would result in a password prompt for every principal listed in the user's .k5login file. This is probably not desired behavior, although it's not prohibited by the module.

This option is only applicable to the auth and password groups. For the password group, it applies only to the authentication process; the user will still be prompted for a new password.

prompt_principal
[3.6] Before prompting for the user's password (or using the previously entered password, if try_first_pass, use_first_pass, or force_first_pass are set), prompt the user for the Kerberos principal to use for authentication. This allows the user to authenticate with a different principal than the one corresponding to the local username, provided that either a .k5login file or local Kerberos principal to account mapping authorize that principal to access the local account.

Be cautious when using this configuration option and don't use it with OpenSSH PasswordAuthentication, only ChallengeResponseAuthentication. Some PAM-enabled applications expect PAM modules to only prompt for passwords and may even blindly give the password to the first prompt, no matter what it is. Such applications, in combination with this option, may expose the user's password in log messages and Kerberos requests.

search_k5login
[3.1] Search the user's k5login_path file for a principal that matches the one provided by the user. If a match is found, use that principal for authentication. This option can be used to allow users to authenticate with a different principal than their local username.

This option is only applicable to the auth group.

try_first_pass
[1.0] If the authentication module isn't the first on the stack, and a previous module obtained the user's password, use that password to authenticate the user without prompting them again. If that authentication fails, fall back on prompting the user for their password. This option has no effect if the authentication module is first in the stack or if no previous module obtained the user's password. Also see use_first_pass and force_first_pass for stronger versions of this option.

This option is only applicable to the auth and password groups. For the password group, it applies only to the old password.

use_authtok
[4.0] Use the new password obtained by a previous password module when changing passwords rather than prompting for the new password. If the new password isn't available, fail. This can be used to require passwords be checked by another, prior module, such as pam_cracklib.

This option is only applicable to the password group.

use_first_pass
[1.0] Use the password obtained by a previous authentication module to authenticate the user without prompting the user again. If no previous module obtained the user's password for either an authentication or password change, fall back on prompting the user. If a previous module did obtain the user's password but authentication with that password fails, fail without further prompting the user. Also see try_first_pass and force_first_pass for other versions of this option.

This option is only applicable to the auth and password groups. For the password group, it applies only to the old password. See use_authtok for a similar setting for the new password.

Ticket Caches

ccache=<pattern>
[2.0] Use <pattern> as the pattern for creating credential cache names. <pattern> must be in the form <type>:<residual> where <type> and the following colon are optional if a file cache should be used. The special token %u, anywhere in <pattern>, is replaced with the user's numeric UID. The special token %p, anywhere in <pattern>, is replaced with the current process ID.

If <pattern> ends in the literal string "XXXXXX" (six X's), that string will be replaced by randomly generated characters and the ticket cache will be created using mkstemp(3). This is strongly recommended if <pattern> points to a world-writable directory.

This option can be set in "[appdefaults]" in krb5.conf and is only applicable to the auth and session groups.

ccache_dir=<directory>
[1.2] Store both the temporary ticket cache used during authentication and user ticket caches in <directory> instead of in /tmp. The algorithm for generating the ticket cache name is otherwise unchanged. <directory> may be prefixed with "FILE:" to make the cache type unambiguous (and this may be required on systems that use a cache type other than file as the default).

Be aware that pam_krb5 creates and stores a temporary ticket cache file owned by root during the login process. If you set ccache above to avoid using the system /tmp directory for user ticket caches, you may also want to set ccache_dir to move those temporary caches to some other location. This will allow pam_krb5 to continue working even if the system /tmp directory is full.

This option can be set in "[appdefaults]" in krb5.conf and is only applicable to the auth and session groups.

no_ccache
[1.0] Do not create a ticket cache after authentication. This option shouldn't be set in general, but is useful as part of the PAM configuration for a particular service that uses PAM for authentication but isn't creating user sessions and doesn't want the overhead of ever writing the user credentials to disk. When using this option, the application should only call pam_authenticate(); other functions like pam_setcred(), pam_start_session(), and pam_acct_mgmt() don't make sense with this option. Don't use this option if the application needs PAM account and session management calls.

This option is only applicable to the auth group.

retain_after_close
[2.3] Normally, the user's ticket cache is destroyed when either pam_end() or pam_close_session() is called by the authenticating application so that ticket caches aren't left behind after the user logs out. In some cases, however, this isn't desirable. (On Solaris 8, for instance, the default behavior means login will destroy the ticket cache before running the user's shell.) If this option is set, the PAM module will never destroy the user's ticket cache. If you set this, you may want to call kdestroy in the shell's logout configuration or run a temporary file removal program to avoid accumulating hundreds of ticket caches in /tmp.

This option can be set in "[appdefaults]" in krb5.conf and is only applicable to the auth and session groups.

ENVIRONMENT

KRB5CCNAME
Set by pam_setcred() with the PAM_ESTABLISH_CRED option, and therefore also by pam_open_session(), to point to the new credential cache for the user. See the ccache and ccache_dir options. By default, the cache name will be prefixed with "FILE:" to make the cache type unambiguous.
PAM_KRB5CCNAME
Set by pam_authenticate() to point to the temporary ticket cache used for authentication (unless the no_ccache option was given). pam_setcred() then uses that environment variable to locate the temporary cache even if it was not called in the same PAM session as pam_authenticate() (a problem with sshd running in some modes). This environment variable is only used internal to the PAM module.

FILES

/tmp/krb5cc_UID_RANDOM
The default credential cache name. UID is the decimal UID of the local user and RANDOM is a random six-character string. The pattern may be changed with the ccache option and the directory with the ccache_dir option.
/tmp/krb5cc_pam_RANDOM
The credential cache name used for the temporary credential cache created by pam_authenticate(). This cache is removed again when the PAM session is ended or when pam_setcred() is called and will normally not be user-visible. RANDOM is a random six-character string.
~/.k5login
File containing Kerberos principals that are allowed access to that account.

BUGS

If try_pkinit is set and pam-krb5 is built with MIT Kerberos, the user's password is not saved in the PAM data if PKINIT fails and the module falls back to password authentication.

IMPORTANTES PRÉCISIONS

Assurez-vous de lister ce module dans le groupe de session ainsi que dans le groupe d'authentification lors de son utilisation pour les connexions interactives. Sinon, certaines applications (comme OpenSSH) ne configureront pas correctement le cache de tickets de l'utilisateur.

La bibliothèque Kerberos, via pam-krb5, demandera à l'utilisateur de changer son mot de passe si celui-ci est expiré, mais lors de l'utilisation d'OpenSSH, cela ne fonctionnera que si ChallengeResponseAuthentication est activé. Sauf si cette option est activée, OpenSSH ne transmet pas les messages PAM à l'utilisateur et ne peut répondre qu'à une simple invite de mot de passe.

Si vous utilisez MIT Kerberos, sachez que les utilisateurs dont les mots de passe sont expirés ne seront pas invités à les changer, sauf si la configuration KDC pour votre domaine dans [realms] de krb5.conf contient un paramètre master_kdc ou, si vous utilisez des enregistrements DNS SRV, vous avez une entrée DNS pour _kerberos-master ainsi que pour _kerberos.

pam_authenticate() renvoie une erreur lorsqu'il est appelé pour un compte ignoré, obligeant l'administrateur système à utiliser "optional" ou "sufficient" pour ignorer le module et passer au module suivant. Il est sans doute plus correct de renvoyer PAM_IGNORE, ce qui provoque l'ignorance du module comme s'il n'était pas dans la configuration, mais cela augmente le risque de failles de sécurité involontaires lors de l'inscription de pam-krb5 comme seul module d'authentification.

Ce module traite le mot de passe vide comme un échec d'authentification plutôt que de tenter de l'utiliser, afin d'éviter un comportement de sollicitation indésirable dans les bibliothèques Kerberos. Si vous avez un principal Kerberos qui a intentionnellement un mot de passe vide, il ne fonctionnera pas avec ce module.

Ce module ne rafraîchira pas un cache de tickets existant s'il est appelé avec un UID ou un GID effectif différent de l'UID ou du GID réel, car le rafraîchissement d'un cache de tickets existant nécessite de faire confiance à la variable d'environnement KRB5CCNAME et l'environnement ne doit pas être considéré comme digne de confiance dans un contexte setuid.

Les anciennes versions d'OpenSSH sont connues pour appeler pam_authenticate suivi de pam_setcred(PAM_REINITIALIZE_CRED) sans appeler au préalable pam_open_session, demandant ainsi la rénovation d'un cache de tickets existant (similaire à ce que voudrait un économiseur d'écran) plutôt que la création d'un nouveau cache de tickets. Comme ce comportement est indiscernable au niveau PAM d'un économiseur d'écran, pam-krb5 lorsqu'il est utilisé avec ces anciennes versions d'OpenSSH, rafraîchira le cache de tickets du démon OpenSSH au lieu de configurer un nouveau cache de tickets pour l'utilisateur. Le cache de tickets résultant aura les bonnes permissions, mais ne sera pas nommé correctement ni référencé dans l'environnement de l'utilisateur et sera écrasé par la prochaine connexion utilisateur. La meilleure solution à ce problème est de mettre à niveau OpenSSH. Je ne suis pas certain exactement quand ce problème a été corrigé, mais au minimum les versions d'OpenSSH 4.3 et ultérieures ne le présentent pas.
