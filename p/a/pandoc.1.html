pandoc(1) Guide de l'utilisateur Pandoc pandoc(1)

NOM

pandoc - convertisseur général de balisage

SYNTAXE

pandoc [options] [fichier-entrée]...

DESCRIPTION

Pandoc est une bibliothèque Haskell pour convertir un format de balisage en un autre, et un outil en ligne de commande qui utilise cette bibliothèque.

Pandoc peut convertir entre de nombreux formats de balisage et de traitement de texte, y compris, mais sans s'y limiter, diverses saveurs de Markdown, HTML, LaTeX et Word docx. Pour les listes complètes des formats d'entrée et de sortie, voir les options --from et --to ci-dessous. Pandoc peut également produire une sortie PDF : voir création d'un PDF, ci-dessous.

La version améliorée de Markdown de Pandoc inclut une syntaxe pour les tableaux, les listes de définition, les blocs de métadonnées, les notes de bas de page, les citations, les mathématiques, et bien plus encore. Voir ci-dessous sous Markdown de Pandoc.

Pandoc a une conception modulaire : il se compose d'un ensemble de lecteurs, qui analysent le texte dans un format donné et produisent une représentation native du document (un arbre syntaxique abstrait ou AST), et d'un ensemble de rédacteurs, qui convertissent cette représentation native en un format cible. Ainsi, ajouter un format d'entrée ou de sortie nécessite seulement d'ajouter un lecteur ou un rédacteur. Les utilisateurs peuvent également exécuter des filtres pandoc personnalisés pour modifier l'AST intermédiaire.

Étant donné que la représentation intermédiaire d'un document par pandoc est moins expressive que celle de nombreux formats entre lesquels il convertit, on ne doit pas s'attendre à des conversions parfaites entre chaque format et tous les autres. Pandoc tente de préserver les éléments structurels d'un document, mais pas les détails de mise en forme tels que la taille des marges. Et certains éléments de document, tels que les tableaux complexes, peuvent ne pas correspondre au modèle de document simple de pandoc. Bien que les conversions du Markdown de pandoc vers tous les formats visent la perfection, les conversions à partir de formats plus expressifs que le Markdown de pandoc peuvent être attendues comme étant avec pertes.

Utilisation de pandoc

Si aucun fichier-entrée n'est spécifié, l'entrée est lue depuis stdin. La sortie va vers stdout par défaut. Pour une sortie vers un fichier, utilisez l'option -o :

pandoc -o sortie.html entree.txt

Par défaut, pandoc produit un fragment de document. Pour produire un document autonome (par exemple, un fichier HTML valide incluant <head> et <body>), utilisez l'indicateur -s ou --standalone :

pandoc -s -o sortie.html entree.txt

Pour plus d'informations sur la manière dont les documents autonomes sont produits, voir Modèles ci-dessous.

Si plusieurs fichiers d'entrée sont donnés, pandoc les concaténera tous (avec des lignes vierges entre eux) avant l'analyse. (Utilisez --file-scope pour analyser les fichiers individuellement.)

Spécification des formats

Le format de l'entrée et de la sortie peut être spécifié explicitement à l'aide des options de ligne de commande. Le format d'entrée peut être spécifié en utilisant l'option -f/--from, le format de sortie en utilisant l'option -t/--to. Ainsi, pour convertir bonjour.txt de Markdown en LaTeX, vous pouvez taper :

pandoc -f markdown -t latex bonjour.txt

Pour convertir bonjour.html de HTML en Markdown :

pandoc -f html -t markdown bonjour.html

Les formats d'entrée et de sortie pris en charge sont listés ci-dessous sous Options (voir -f pour les formats d'entrée et -t pour les formats de sortie). Vous pouvez également utiliser pandoc --list-input-formats et pandoc --list-output-formats pour imprimer des listes des formats pris en charge.

Si le format d'entrée ou de sortie n'est pas spécifié explicitement, pandoc tentera de le deviner à partir des extensions des noms de fichiers. Ainsi, par exemple,

pandoc -o bonjour.tex bonjour.txt

convertira bonjour.txt de Markdown en LaTeX. Si aucun fichier de sortie n'est spécifié (donc la sortie va vers stdout), ou si l'extension du fichier de sortie est inconnue, le format de sortie sera par défaut HTML. Si aucun fichier d'entrée n'est spécifié (donc l'entrée vient de stdin), ou si les extensions des fichiers d'entrée sont inconnues, le format d'entrée sera supposé être Markdown.

Encodage des caractères

Pandoc utilise l'encodage de caractères UTF-8 pour l'entrée et la sortie. Si votre encodage de caractères local n'est pas UTF-8, vous devriez utiliser des pipes avec iconv pour l'entrée et la sortie :

iconv -t utf-8 entree.txt | pandoc | iconv -f utf-8

Notez que dans certains formats de sortie (tels que HTML, LaTeX, ConTeXt, RTF, OPML, DocBook et Texinfo), des informations sur l'encodage des caractères sont incluses dans l'en-tête du document, ce qui ne sera inclus que si vous utilisez l'option -s/--standalone.

Création d'un PDF

Pour produire un PDF, spécifiez un fichier de sortie avec une extension .pdf :

pandoc test.txt -o test.pdf

Par défaut, pandoc utilisera LaTeX pour créer le PDF, ce qui nécessite qu'un moteur LaTeX soit installé (voir --pdf-engine ci-dessous). Alternativement, pandoc peut utiliser ConTeXt, roff ms, ou HTML comme format intermédiaire. Pour ce faire, spécifiez un fichier de sortie avec une extension .pdf, comme précédemment, mais ajoutez l'option --pdf-engine ou -t context, -t html, ou -t ms à la ligne de commande. L'outil utilisé pour générer le PDF à partir du format intermédiaire peut être spécifié à l'aide de --pdf-engine.

Vous pouvez contrôler le style du PDF à l'aide de variables, en fonction du format intermédiaire utilisé : voir variables pour LaTeX, variables pour ConTeXt, variables pour wkhtmltopdf, variables pour ms. Lorsque HTML est utilisé comme format intermédiaire, la sortie peut être stylisée à l'aide de --css.

Pour déboguer la création du PDF, il peut être utile de regarder la représentation intermédiaire : au lieu de -o test.pdf, utilisez par exemple -s -o test.tex pour sortir le LaTeX généré. Vous pouvez ensuite le tester avec pdflatex test.tex.

Lors de l'utilisation de LaTeX, les paquets suivants doivent être disponibles (ils sont inclus dans toutes les versions récentes de TeX Live) : amsfonts, amsmath, lm, unicode-math, iftex, listings (si l'option --listings est utilisée), fancyvrb, longtable, booktabs, graphicx (si le document contient des images), hyperref, xcolor, soul, geometry (avec la variable geometry définie), setspace (avec linestretch), et babel (avec lang). Si CJKmainfont est définie, xeCJK est nécessaire. L'utilisation de xelatex ou lualatex comme moteur PDF nécessite fontspec. lualatex utilise selnolig. xelatex utilise bidi (avec la variable dir définie). Si la variable mathspec est définie, xelatex utilisera mathspec au lieu de unicode-math. TEXT FORMATS

Pandoc has built-in support for a large number of text formats. The most important are Markdown and reStructuredText, but Pandoc can also read and write LaTeX, HTML, and many other formats.

When reading a document, Pandoc determines the format from the file extension, if possible. If the input is from standard input, or if the file extension is not recognized, then the format must be specified using the -f option (or --from). Likewise, the output format is determined from the file extension when writing, unless specified with the -t option (or --to).

For each format, Pandoc supports a set of extensions that can be individually enabled or disabled by appending +EXTENSION or -EXTENSION to the format name. For example, to specify Markdown with the tex_math_dollars extension enabled, but the auto_identifiers extension disabled, you would use -f markdown+tex_math_dollars-auto_identifiers. See Extensions below for a list of extensions and their names.

The following standard LaTeX packages are used when writing LaTeX or PDF output:

  • booktabs (for nicer tables)

  • amsmath and amssymb (for math)

  • hyperref (for links, including citations)

  • natbib (for citations, if --natbib is used)

  • bibtex, and biber packages can optionally be used for citation rendering. The following packages will be used to improve output quality if present, but pandoc does not require them to be present: upquote (for straight quotes in verbatim environments), microtype (for better spacing adjustments), parskip (for better inter-paragraph spaces), xurl (for better line breaks in URLs), bookmark (for better PDF bookmarks), and footnotehyper or footnote (to allow footnotes in tables).

Reading from the Web

Instead of an input file, an absolute URI may be given. In this case pandoc will fetch the content using HTTP:

pandoc -f html -t markdown https://www.fsf.org

It is possible to supply a custom User-Agent string or other header when requesting a document from a URL:

pandoc -f html -t markdown --request-header User-Agent:"Mozilla/5.0" \
  https://www.fsf.org

-o FICHIER, --output=FICHIER
Écrit la sortie dans FICHIER au lieu de stdout. Si FICHIER est -, la sortie ira à stdout, même si un format non textuel (docx, odt, epub2, epub3) est spécifié. Si le format de sortie est chunkedhtml et que FICHIER n'a pas d'extension, alors au lieu de produire un fichier .zip, pandoc créera un répertoire FICHIER et y décompressera l'archive zip (sauf si FICHIER existe déjà, auquel cas une erreur sera générée).
--data-dir=RÉPERTOIRE
Spécifie le répertoire de données utilisateur où chercher les fichiers de données pandoc. Si cette option n'est pas spécifiée, le répertoire de données utilisateur par défaut sera utilisé. Vous pouvez trouver le répertoire de données utilisateur par défaut sur votre système en consultant la sortie de pandoc --version. Les fichiers de données placés dans ce répertoire (par exemple, reference.odt, reference.docx, epub.css, templates) remplaceront les valeurs par défaut normales de pandoc. (Notez que le répertoire de données utilisateur n'est pas créé par pandoc, vous devrez donc le créer vous-même si vous souhaitez l'utiliser.)

Options du lecteur

--shift-heading-level-by=NOMBRE
Décale les niveaux de titre par un entier positif ou négatif. Par exemple, avec --shift-heading-level-by=-1, les titres de niveau 2 deviennent des titres de niveau 1, et les titres de niveau 3 deviennent des titres de niveau 2. Les titres ne peuvent pas avoir un niveau inférieur à 1, donc un titre qui serait décalé en dessous du niveau 1 devient un paragraphe ordinaire. Exception : avec un décalage de -N, un titre de niveau N au début du document remplace le titre des métadonnées. --shift-heading-level-by=-1 est un bon choix lors de la conversion de documents HTML ou Markdown qui utilisent un titre de niveau 1 initial pour le titre du document et des titres de niveau 2 et supérieurs pour les sections. --shift-heading-level-by=1 peut être un bon choix pour convertir des documents Markdown qui utilisent des titres de niveau 1 pour les sections en HTML, car pandoc utilise un titre de niveau 1 pour rendre le titre du document.
--base-header-level=NOMBRE
Obsolète. Utilisez --shift-heading-level-by=X à la place, où X = NOMBRE - 1. Spécifie le niveau de base pour les titres (par défaut à 1).
--indented-code-classes=CLASSES
Spécifie les classes à utiliser pour les blocs de code indentés — par exemple, perl,numberLines ou haskell. Plusieurs classes peuvent être séparées par des espaces ou des virgules.
--default-image-extension=EXTENSION
Spécifie une extension par défaut à utiliser lorsque les chemins/URL d'images n'ont pas d'extension. Cela vous permet d'utiliser la même source pour des formats qui nécessitent différents types d'images. Actuellement, cette option n'affecte que les lecteurs Markdown et LaTeX.
--file-scope[=true|false]
Traite chaque fichier individuellement avant de combiner pour les documents multifichiers. Cela permettra aux notes de bas de page dans différents fichiers avec les mêmes identifiants de fonctionner comme prévu. Si cette option est définie, les notes de bas de page et les liens ne fonctionneront pas entre les fichiers. La lecture de fichiers binaires (docx, odt, epub) implique --file-scope.

Si deux fichiers ou plus sont traités à l'aide de --file-scope, des préfixes basés sur les noms de fichiers seront ajoutés aux identifiants afin de les désambiguïser, et les liens internes seront ajustés en conséquence. Par exemple, un en-tête avec l'identifiant foo dans subdir/file1.txt verra son identifiant modifié en subdir__file1.txt__foo.

De plus, un Div avec un identifiant basé sur le nom du fichier sera ajouté autour du contenu du fichier, de sorte que les liens internes vers le nom du fichier pointeront vers l'identifiant de ce Div.

-F PROGRAMME, --filter=PROGRAMME
Spécifie un exécutable à utiliser comme filtre transformant l'AST de pandoc après l'analyse de l'entrée et avant l'écriture de la sortie. L'exécutable doit lire du JSON depuis stdin et écrire du JSON sur stdout. Le JSON doit être formaté comme l'entrée et la sortie JSON de pandoc. Le nom du format de sortie sera passé au filtre comme premier argument. Ainsi,
pandoc --filter ./caps.py -t latex

est équivalent à

pandoc -t json | ./caps.py latex | pandoc -f json -t latex

La dernière forme peut être utile pour déboguer des filtres.

Les filtres peuvent être écrits dans n'importe quel langage. Text.Pandoc.JSON exporte toJSONFilter pour faciliter l'écriture de filtres en Haskell. Ceux qui préféreraient écrire des filtres en Python peuvent utiliser le module pandocfilters, installable depuis PyPI. Il existe également des bibliothèques de filtres pandoc en PHP, Perl et JavaScript/node.js.

Par ordre de préférence, pandoc recherchera les filtres dans

1.
un chemin complet ou relatif spécifié (exécutable ou non exécutable),
2.
$DATADIR/filters (exécutable ou (non exécutable) où $DATADIR est le répertoire des données utilisateur (voir --data-dir, ci-dessus),
3.
$PATH (exécutable uniquement).

Les filtres, les filtres Lua et le traitement citeproc sont appliqués dans l'ordre spécifié sur la ligne de commande.

-L SCRIPT, --lua-filter=SCRIPT
Transforme le document d'une manière similaire aux filtres JSON (voir --filter), mais utilise le système de filtrage Lua intégré de pandoc. Le script Lua donné doit retourner une liste de filtres Lua qui seront appliqués dans l'ordre. Chaque filtre Lua doit contenir des fonctions transformant les éléments, indexées par le nom de l'élément AST sur lequel la fonction de filtre doit être appliquée.

Le module Lua pandoc fournit des fonctions d'aide pour la création d'éléments. Il est toujours chargé dans l'environnement Lua du script.

Voir la documentation des filtres Lua pour plus de détails.

Dans l'ordre de préférence, pandoc recherchera les filtres Lua dans

1.
un chemin complet ou relatif spécifié,
2.
$DATADIR/filters où $DATADIR est le répertoire des données utilisateur (voir --data-dir, ci-dessus).

Les filtres, les filtres Lua et le traitement citeproc sont appliqués dans l'ordre spécifié sur la ligne de commande.

-M CLÉ[=VALEUR], --metadata=CLÉ[:VALEUR]
Définit le champ de métadonnées CLÉ à la valeur VALEUR. Une valeur spécifiée sur la ligne de commande remplace une valeur spécifiée dans le document à l'aide de blocs de métadonnées YAML. Les valeurs seront analysées comme des valeurs booléennes ou chaînes YAML. Si aucune valeur n'est spécifiée, la valeur sera traitée comme un booléen vrai. Comme --variable, --metadata définit des variables de modèle. Mais contrairement à --variable, --metadata affecte les métadonnées du document sous-jacent (qui sont accessibles depuis les filtres et peuvent être imprimées dans certains formats de sortie) et les valeurs de métadonnées seront échappées lors de leur insertion dans le modèle.
--metadata-file=FICHIER
Lit les métadonnées à partir du fichier YAML (ou JSON) fourni. Cette option peut être utilisée avec tous les formats d'entrée, mais les scalaires de chaîne dans le fichier de métadonnées seront toujours analysés comme du Markdown. (Si le format d'entrée est Markdown ou une variante de Markdown, alors la même variante sera utilisée pour analyser le fichier de métadonnées ; s'il s'agit d'un format non-Markdown, les extensions Markdown par défaut de pandoc seront utilisées.) Cette option peut être utilisée de manière répétée pour inclure plusieurs fichiers de métadonnées ; les valeurs dans les fichiers spécifiés plus tard sur la ligne de commande auront la préférence sur celles spécifiées dans les fichiers précédents. Les valeurs de métadonnées spécifiées à l'intérieur du document, ou en utilisant -M, remplacent les valeurs spécifiées avec cette option. Le fichier sera recherché d'abord dans le répertoire de travail, puis dans le sous-répertoire metadata du répertoire des données utilisateur (voir --data-dir).
-p, --preserve-tabs[=true|false]
Préserve les tabulations au lieu de les convertir en espaces. (Par défaut, pandoc convertit les tabulations en espaces avant d'analyser son entrée.) Notez que cela n'affectera que les tabulations dans les spans de code littéral et les blocs de code. Les tabulations dans le texte normal sont toujours traitées comme des espaces.
--tab-stop=NOMBRE
Spécifie le nombre d'espaces par tabulation (par défaut 4).
--track-changes=accept|reject|all
Spécifie quoi faire des insertions, suppressions et commentaires produits par la fonctionnalité « Suivi des modifications » de MS Word. accept (par défaut) traite toutes les insertions et suppressions. reject les ignore. Les deux accept et reject ignorent les commentaires. all inclut toutes les insertions, suppressions et commentaires, enveloppés dans des spans avec les classes insertion, deletion, comment-start, et comment-end, respectivement. L'auteur et l'heure de la modification sont inclus. all est utile pour le scripting : n'accepter que les modifications d'un certain réviseur, par exemple, ou avant une certaine date. Si un paragraphe est inséré ou supprimé, track-changes=all produit un span avec la classe paragraph-insertion/paragraph-deletion avant la rupture de paragraphe affectée. Cette option n'affecte que le lecteur docx.
--extract-media=DIR
Extrait les images et autres médias contenus ou référencés dans le document source vers le chemin DIR, en le créant si nécessaire, et ajuste les références des images dans le document pour qu'elles pointent vers les fichiers extraits. Les médias sont téléchargés, lus à partir du système de fichiers, ou extraits d'un conteneur binaire (par exemple, docx), selon les besoins. Les chemins de fichiers d'origine sont utilisés s'il s'agit de chemins relatifs ne contenant pas ... Sinon, les noms de fichiers sont construits à partir du hachage SHA1 du contenu.
--abbreviations=FICHIER
Spécifie un fichier personnalisé d'abréviations, avec une abréviation par ligne. Si cette option n'est pas spécifiée, pandoc lira le fichier de données abbreviations du répertoire des données utilisateur ou se rabattra sur une valeur par défaut du système. Pour voir la valeur par défaut du système, utilisez pandoc --print-default-data-file=abbreviations. La seule utilisation que pandoc fait de cette liste est dans le lecteur Markdown. Les chaînes trouvées dans cette liste seront suivies d'un espace insécable, et le point ne produira pas d'espace de fin de phrase dans les formats comme LaTeX. Les chaînes ne peuvent pas contenir d'espaces.
--trace[=true|false]
Imprime des informations de diagnostic retraçant la progression de l'analyseur vers stderr. Cette option est destinée aux développeurs pour diagnostiquer les problèmes de performance.

Options générales d'écriture

-s, --standalone
Produit une sortie avec un en-tête et un pied de page appropriés (par exemple, un fichier HTML, LaTeX, TEI ou RTF autonome, pas un fragment). Cette option est définie automatiquement pour les sorties pdf, epub, epub3, fb2, docx, et odt. Pour la sortie native, cette option inclut les métadonnées ; sinon, les métadonnées sont supprimées.
--template=FICHIER|URL
Utilise le fichier spécifié comme modèle personnalisé pour le document généré. Implique --standalone. Voir Modèles, ci-dessous, pour une description de la syntaxe des modèles. Si aucune extension n'est spécifiée, une extension correspondant à l'écrivain sera ajoutée, de sorte que --template=special recherche special.html pour la sortie HTML. Si le modèle n'est pas trouvé, pandoc le recherchera dans le sous-répertoire templates du répertoire des données utilisateur (voir --data-dir). Si cette option n'est pas utilisée, un modèle par défaut approprié pour le format de sortie sera utilisé (voir -D/--print-default-template).
-V CLÉ[=VALEUR], --variable=CLÉ[:VALEUR]
Définit la variable de modèle CLÉ à la valeur VALEUR lors du rendu du document en mode autonome. Si aucune VALEUR n'est spécifiée, la clé recevra la valeur true.
--sandbox[=true|false]
Exécute pandoc en mode sandbox, limitant les opérations d'E/S dans les lecteurs et rédacteurs à la lecture des fichiers spécifiés sur la ligne de commande. Notez que cette option ne limite pas les opérations d'E/S des filtres ou dans la production de documents PDF. Mais elle offre une sécurité contre, par exemple, la divulgation de fichiers par l'utilisation de directives include. Toute personne utilisant pandoc sur une entrée utilisateur non fiable devrait utiliser cette option.

Note : certains lecteurs et rédacteurs (par exemple, docx) ont besoin d'accéder à des fichiers de données. S'ils sont stockés sur le système de fichiers, pandoc ne pourra pas les trouver lorsqu'il est exécuté en mode --sandbox et lèvera une erreur. Pour ces applications, nous recommandons d'utiliser un binaire pandoc compilé avec l'option embed_data_files, qui permet d'intégrer les fichiers de données dans le binaire au lieu de les stocker sur le système de fichiers.

-D FORMAT, --print-default-template=FORMAT
Imprime le modèle système par défaut pour un FORMAT de sortie. (Voir -t pour une liste de FORMATs possibles.) Les modèles dans le répertoire des données utilisateur sont ignorés. Cette option peut être utilisée avec -o/--output pour rediriger la sortie vers un fichier, mais -o/--output doit précéder --print-default-template sur la ligne de commande.

Notez que certains des modèles par défaut utilisent des parties, par exemple styles.html. Pour imprimer les parties, utilisez --print-default-data-file : par exemple, --print-default-data-file=templates/styles.html.

--print-default-data-file=FICHIER
Imprime un fichier de données système par défaut. Les fichiers dans les données utilisateur
directory sont ignorés. Cette option peut être utilisée avec -o/--output pour rediriger la sortie vers un fichier, mais -o/--output doit précéder --print-default-data-file sur la ligne de commande.
--eol=crlf|lf|native
Spécifiez manuellement les fins de ligne : crlf (Windows), lf (macOS/Linux/UNIX), ou native (fins de ligne appropriées au système d'exploitation sur lequel pandoc est exécuté). La valeur par défaut est native.
--dpi=NOMBRE
Spécifiez la valeur par défaut de dpi (points par pouce) pour la conversion de pixels en pouces/centimètres et vice versa. (Techniquement, le terme correct serait ppp : pixels par pouce.) La valeur par défaut est 96 ppp. Lorsque les images contiennent des informations sur les ppp en interne, la valeur encodée est utilisée à la place de la valeur par défaut spécifiée par cette option.
--wrap=auto|none|preserve
Déterminez comment le texte est mis en forme dans la sortie (le code source, pas la version rendue). Avec auto (la valeur par défaut), pandoc tentera de mettre en forme les lignes selon la largeur de colonne spécifiée par --columns (par défaut 72). Avec none, pandoc ne mettra pas en forme les lignes du tout. Avec preserve, pandoc tentera de préserver la mise en forme du document source (c'est-à-dire que là où il y a des sauts de ligne non sémantiques dans la source, il y aura également des sauts de ligne non sémantiques dans la sortie). Dans la sortie ipynb, cette option affecte la mise en forme du contenu des cellules markdown.
--columns=NOMBRE
Spécifiez la longueur des lignes en caractères. Ceci affecte la mise en forme du texte dans le code source généré (voir --wrap). Cela affecte également le calcul des largeurs de colonnes pour les tableaux en texte brut (voir Tableaux ci-dessous).
--toc[=true|false], --table-of-contents[=true|false]
Incluez une table des matières générée automatiquement (ou, dans le cas de latex, context, docx, odt, opendocument, rst, ou ms, une instruction pour en créer une) dans le document de sortie. Cette option n'a aucun effet sauf si -s/--standalone est utilisé, et elle n'a aucun effet sur la sortie man, docbook4, docbook5, ou jats.

Notez que si vous produisez un PDF via ms, la table des matières apparaîtra au début du document, avant le titre. Si vous préférez qu'elle soit à la fin du document, utilisez l'option --pdf-engine-opt=--no-toc-relocation.

--toc-depth=NOMBRE
Spécifiez le nombre de niveaux de sections à inclure dans la table des matières. La valeur par défaut est 3 (ce qui signifie que les titres de niveau 1, 2 et 3 seront listés dans le sommaire).
--strip-comments[=true|false]
Supprimez les commentaires HTML du source Markdown ou Textile, au lieu de les transmettre à la sortie Markdown, Textile ou HTML en tant que HTML brut. Ceci ne s'applique pas aux commentaires HTML à l'intérieur des blocs HTML bruts lorsque l'extension markdown_in_html_blocks n'est pas définie.
--no-highlight
Désactive la coloration syntaxique pour les blocs de code et les inline, même lorsqu'un attribut de langage est donné.
--highlight-style=STYLE|FICHIER
Spécifie le style de coloration à utiliser dans le code source mis en évidence. Les options sont pygments (la valeur par défaut), kate, monochrome, breezeDark, espresso, zenburn, haddock, et tango. Pour plus d'informations sur la coloration syntaxique dans pandoc, voir Coloration syntaxique, ci-dessous. Voir aussi --list-highlight-styles.

Au lieu d'un nom de STYLE, un fichier JSON avec l'extension .theme peut être fourni. Celui-ci sera analysé comme un thème de coloration syntaxique KDE et (s'il est valide) utilisé comme style de coloration.

Pour générer la version JSON d'un style existant, utilisez --print-highlight-style.

--print-highlight-style=STYLE|FICHIER
Affiche une version JSON d'un style de coloration, qui peut être modifiée, enregistrée avec une extension .theme, et utilisée avec --highlight-style. Cette option peut être utilisée avec -o/--output pour rediriger la sortie vers un fichier, mais -o/--output doit précéder --print-highlight-style sur la ligne de commande.
--syntax-definition=FICHIER
Demande à pandoc de charger un fichier de définition de syntaxe XML KDE, qui sera utilisé pour la coloration syntaxique des blocs de code marqués de manière appropriée. Ceci peut être utilisé pour ajouter la prise en charge de nouveaux langages ou pour utiliser des définitions de syntaxe modifiées pour les langages existants. Cette option peut être répétée pour ajouter plusieurs définitions de syntaxe.
-H FICHIER, --include-in-header=FICHIER|URL
Inclut le contenu de FICHIER, tel quel, à la fin de l'en-tête. Ceci peut être utilisé, par exemple, pour inclure du CSS ou du JavaScript spécial dans les documents HTML. Cette option peut être utilisée de manière répétée pour inclure plusieurs fichiers dans l'en-tête. Ils seront inclus dans l'ordre spécifié. Implique --standalone.
-B FICHIER, --include-before-body=FICHIER|URL
Inclut le contenu de FICHIER, tel quel, au début du corps du document (par exemple, après la balise <body> en HTML, ou la commande \begin{document} en LaTeX). Ceci peut être utilisé pour inclure des barres de navigation ou des bannières dans les documents HTML. Cette option peut être utilisée de manière répétée pour inclure plusieurs fichiers. Ils seront inclus dans l'ordre spécifié. Implique --standalone.
-A FICHIER, --include-after-body=FICHIER|URL
Inclut le contenu de FICHIER, tel quel, à la fin du corps du document (avant la balise </body> en HTML, ou la commande \end{document} en LaTeX). Cette option peut être utilisée de manière répétée pour inclure plusieurs fichiers. Ils seront inclus dans l'ordre spécifié. Implique --standalone.
--resource-path=CHEMIN DE RECHERCHE
Liste des chemins à rechercher pour les images et autres ressources. Les chemins doivent être séparés par : sur les systèmes Linux, UNIX et macOS, et par ; sur Windows. Si --resource-path n'est pas spécifié, le chemin de ressource par défaut est le répertoire de travail. Notez que, si --resource-path est spécifié, le répertoire de travail doit être explicitement listé ou il ne sera pas recherché. Par exemple : --resource-path=.:test recherchera le répertoire de travail et le sous-répertoire test, dans cet ordre. Cette option peut être utilisée de manière répétée. Les composants du chemin de recherche qui viennent plus tard dans la ligne de commande seront recherchés avant ceux qui viennent plus tôt, donc --resource-path foo:bar --resource-path baz:bim est équivalent à --resource-path baz:bim:foo:bar.
--request-header=NOM:VALEUR
Définit l'en-tête de requête NOM à la valeur VALEUR lors des requêtes HTTP (par exemple, lorsqu'une URL est donnée sur la ligne de commande, ou lorsque des ressources utilisées dans un document doivent être téléchargées). Si vous êtes derrière un proxy, vous devez également définir la variable d'environnement http_proxy à http://....
--no-check-certificate[=true|false]
Désactive la vérification du certificat pour autoriser l'accès aux ressources HTTP non sécurisées (par exemple, lorsque le certificat n'est plus valide ou est auto-signé).

Le fichier résultant devrait être "autonome", dans le sens où il n'a pas besoin de fichiers externes ni d'accès réseau pour être affiché correctement par un navigateur. --html-q-tags[=true|false]
Utiliser des balises <q> pour les citations en HTML. (Cette option n'a d'effet que si l'extension smart est activée pour le format d'entrée utilisé.)
--ascii[=true|false]
Utiliser uniquement des caractères ASCII dans la sortie. Actuellement pris en charge pour les formats XML et HTML (qui utilisent des entités au lieu de UTF-8 lorsque cette option est sélectionnée), CommonMark, gfm et Markdown (qui utilisent des entités), roff man et ms (qui utilisent des échappements hexadécimaux), et dans une mesure limitée LaTeX (qui utilise des commandes standard pour les caractères accentués lorsque possible).
--reference-links[=true|false]
Utiliser des liens de style référence, plutôt que des liens en ligne, lors de l'écriture de Markdown ou de reStructuredText. Par défaut, les liens en ligne sont utilisés. Le placement des références de liens est affecté par l'option --reference-location.
--reference-location=block|section|document
Spécifier où les notes de bas de page (et les références, si reference-links est défini) sont placées : à la fin du bloc (de niveau supérieur) actuel, de la section actuelle ou du document. La valeur par défaut est document. Actuellement, cette option n'affecte que les générateurs markdown, muse, html, epub, slidy, s5, slideous, dzslides, et revealjs. Dans les formats de diaporama, spécifier --reference-location=section entraînera le rendu des notes en bas d'une diapositive.
--markdown-headings=setext|atx
Spécifier s'il faut utiliser le style ATX (précédé de #) ou le style Setext (souligné) pour les titres de niveau 1 et 2 en sortie Markdown. (La valeur par défaut est atx.) Les titres de style ATX sont toujours utilisés pour les niveaux 3 et supérieurs. Cette option affecte également les cellules Markdown en sortie ipynb.
--list-tables[=true|false]
Rendre les tableaux sous forme de tableaux listés en sortie RST.
--top-level-division=default|section|chapter|part
Traiter les titres de niveau supérieur comme le type de division donné en sortie LaTeX, ConTeXt, DocBook et TEI. L'ordre hiérarchique est partie, chapitre, puis section ; tous les titres sont décalés de sorte que le titre de niveau supérieur devienne le type spécifié. Le comportement par défaut est de déterminer le meilleur type de division par heuristiques : sauf si d'autres conditions s'appliquent, section est choisi. Lorsque la variable documentclass est définie sur report, book, ou memoir (sauf si l'option article est spécifiée), chapter est implicitement défini pour cette option. Si beamer est le format de sortie, spécifier chapter ou part fera que les titres de niveau supérieur deviendront \part{..}, tandis que les titres de second niveau conserveront leur type par défaut.
-N, --number-sections
Numéroter les titres de section en sortie LaTeX, ConTeXt, HTML, Docx, ms ou EPUB. Par défaut, les sections ne sont pas numérotées. Les sections avec la classe unnumbered ne seront jamais numérotées, même si --number-sections est spécifié.
--number-offset=NOMBRE[, NOMBRE,...]
Décalage pour les titres de section en sortie HTML (ignoré dans les autres formats de sortie). Le premier nombre est ajouté au numéro de section pour les titres de niveau supérieur, le second pour les titres de niveau deux, et ainsi de suite. Ainsi, par exemple, si vous voulez que le premier titre de niveau supérieur de votre document soit numéroté « 6 », spécifiez --number-offset=5. Si votre document commence par un titre de niveau 2 que vous souhaitez numéroter « 1.5 », spécifiez --number-offset=1,4. Les décalages sont de 0 par défaut. Implique --number-sections.
--listings[=true|false]
Utiliser le package listings pour les blocs de code LaTeX. Le package ne prend pas en charge l'encodage multi-octets pour le code source. Pour gérer UTF-8, vous auriez besoin d'un modèle personnalisé. Ce problème est entièrement documenté ici : Problème d'encodage avec le package listings.
-i, --incremental[=true|false]
Faire en sorte que les éléments de liste dans les diaporamas s'affichent progressivement (un par un). Par défaut, les listes sont affichées toutes à la fois.
--slide-level=NOMBRE
Spécifie que les titres avec le niveau spécifié créent des diapositives (pour beamer, s5, slidy, slideous, dzslides). Les titres au-dessus de ce niveau dans la hiérarchie sont utilisés pour diviser le diaporama en sections ; les titres en dessous de ce niveau créent des sous-titres dans une diapositive. Les valeurs valides sont 0-6. Si un niveau de diapositive de 0 est spécifié, les diapositives ne seront pas divisées automatiquement sur les titres, et des lignes horizontales devront être utilisées pour indiquer les limites des diapositives. Si un niveau de diapositive n'est pas explicitement spécifié, le niveau de diapositive sera automatiquement défini en fonction du contenu du document ; voir Structuration du diaporama.
--section-divs[=true|false]
Encapsuler les sections dans des balises <section> (ou <div> pour html4), et attacher des identifiants aux <section> (ou <div>) englobants plutôt qu'au titre lui-même (voir Identifiants de titre, ci-dessous). Cette option n'affecte que la sortie HTML (et n'affecte pas les formats de diaporama HTML).
--email-obfuscation=none|javascript|references
Spécifier une méthode pour masquer les liens mailto: dans les documents HTML. none laisse les liens mailto: tels quels. javascript les masque à l'aide de JavaScript. references les masque en imprimant leurs lettres sous forme de références de caractères décimales ou hexadécimales. --id-prefix=CHAINE
Spécifier une chaîne à ajouter à tous les identifiants et liens internes en sortie HTML et DocBook, et aux numéros de notes de bas de page en sortie Markdown et Haddock. Ceci est utile pour éviter les doublons d'identifiants lors de la génération de fragments à inclure dans d'autres pages.
-T CHAINE, --title-prefix=CHAINE
Spécifier CHAINE comme préfixe au début du titre qui apparaît dans l'en-tête HTML (mais pas dans le titre tel qu'il apparaît au début du corps HTML). Implique --standalone.
-c URL, --css=URL
Lier à une feuille de style CSS. Cette option peut être utilisée de manière répétée pour inclure plusieurs fichiers. Ils seront inclus dans l'ordre spécifié. --split-level=NOMBRE
Spécifie le niveau de titre auquel diviser un document EPUB ou HTML fragmenté en fichiers distincts. Par défaut, la division se fait en chapitres aux titres de niveau 1. Dans le cas des EPUB, cette option n'affecte que la composition interne de l'EPUB, pas la manière dont les chapitres et les sections sont affichés aux utilisateurs. Certains lecteurs peuvent être lents si les fichiers de chapitre sont trop volumineux, donc pour les documents volumineux avec peu de titres de niveau 1, on peut utiliser un niveau de chapitre de 2 ou 3. Pour le HTML fragmenté, cette option détermine la quantité de contenu allant dans chaque « fragment ».
--chunk-template=CHEMINMODÈLE
Spécifie un modèle pour les noms de fichiers dans un document chunkedhtml. Dans le modèle, %n sera remplacé par le numéro de fragment (rempli de zéros en tête pour atteindre 3 chiffres), %s par le numéro de section du fragment, %h par le texte du titre (sans formatage), %i par l'identifiant de la section. Par exemple, %section-%s-%i.html pourrait être résolu en section-1.1-introduction.html. Les caractères / et \ ne sont pas autorisés dans les modèles de fragments et seront ignorés. Le modèle par défaut est %s-%i.html.
--epub-chapter-level=NOMBRE
Synonyme obsolète de --split-level.
--epub-cover-image=FICHIER
Utilise l'image spécifiée comme couverture de l'EPUB. Il est recommandé que l'image ait moins de 1000 pixels en largeur et en hauteur. Notez que dans un document source Markdown, vous pouvez également spécifier cover-image dans un bloc de métadonnées YAML (voir Métadonnées EPUB, ci-dessous).
--epub-title-page=true|false
Détermine si la page de titre est incluse dans l'EPUB (la valeur par défaut est true).
--epub-metadata=FICHIER
Recherche dans le fichier XML spécifié les métadonnées pour l'EPUB. Le fichier doit contenir une série d'éléments Dublin Core. Par exemple :
 <dc:rights>Creative Commons</dc:rights>
 <dc:language>es-AR</dc:language>

Par défaut, pandoc inclura les éléments de métadonnées suivants : <dc:title> (provenant du titre du document), <dc:creator> (provenant des auteurs du document), <dc:date> (provenant de la date du document, qui doit être au format ISO 8601), <dc:language> (provenant de la variable lang, ou, si elle n'est pas définie, de la locale), et <dc:identifier id="BookId"> (un UUID généré aléatoirement). Chacun de ces éléments peut être remplacé par des éléments du fichier de métadonnées.

Remarque : si le document source est Markdown, un bloc de métadonnées YAML dans le document peut être utilisé à la place. Voir ci-dessous sous Métadonnées EPUB.

--epub-embed-font=FICHIER

Spécifie le sous-répertoire dans le conteneur OCF qui doit contenir le contenu spécifique à l'EPUB. La valeur par défaut est EPUB. Pour placer le contenu EPUB au niveau supérieur, utilisez une chaîne vide.
--ipynb-output=all|none|best
Détermine comment les cellules de sortie ipynb sont traitées. all signifie que tous les formats de données inclus dans l'original sont conservés. none signifie que le contenu des cellules de données est omis. best fait en sorte que pandoc essaie de choisir le bloc de données le plus riche dans chaque cellule de sortie compatible avec le format de sortie. --pdf-engine=PROGRAMME
Utilise le moteur spécifié lors de la production de sortie PDF. •

•
-t context : context
•
-t html : wkhtmltopdf (autres options : prince, weasyprint, pagedjs-cli ; voir print-css.rocks pour une bonne introduction à la génération de PDF à partir de HTML/CSS)
•

•
-t typst : typst

Rendu des citations

-C, --citeproc
Traiter les citations dans le fichier, en les remplaçant par des citations rendues et en ajoutant une bibliographie. Le traitement des citations n'aura pas lieu à moins que des données bibliographiques ne soient fournies, soit par le biais d'un fichier externe spécifié à l'aide de l'option --bibliography ou du champ bibliography dans les métadonnées, soit via une section references dans les métadonnées contenant une liste de citations au format CSL YAML avec formatage Markdown. Le style est contrôlé par une feuille de style CSL spécifiée à l'aide de l'option --csl ou du champ csl dans les métadonnées. (Si aucune feuille de style n'est spécifiée, le style chicago-author-date sera utilisé par défaut.) La transformation de traitement des citations peut être appliquée avant ou après les filtres ou les filtres Lua (voir --filter, --lua-filter) : ces transformations sont appliquées dans l'ordre où elles apparaissent sur la ligne de commande. Pour plus d'informations, voir la section sur les Citations.
--bibliography=FICHIER
Définir le champ bibliography dans les métadonnées du document sur FICHIER, en remplaçant toute valeur définie dans les métadonnées. Si vous fournissez cet argument plusieurs fois, chaque FICHIER sera ajouté à la bibliographie. Si FICHIER est une URL, il sera récupéré via HTTP. Si FICHIER n'est pas trouvé par rapport au répertoire de travail, il sera recherché dans le chemin des ressources (voir --resource-path).
--csl=FICHIER
Définir le champ csl dans les métadonnées du document sur FICHIER, en remplaçant toute valeur définie dans les métadonnées. (Ceci est équivalent à --metadata csl=FICHIER.) Si FICHIER est une URL, il sera récupéré via HTTP. Si FICHIER n'est pas trouvé par rapport au répertoire de travail, il sera recherché dans le chemin des ressources (voir --resource-path) et enfin dans le sous-répertoire csl du répertoire de données utilisateur pandoc.
--citation-abbreviations=FICHIER
Définir le champ citation-abbreviations dans les métadonnées du document sur FICHIER, en remplaçant toute valeur définie dans les métadonnées. (Ceci est équivalent à --metadata citation-abbreviations=FICHIER.) Si FICHIER est une URL, il sera récupéré via HTTP. Si FICHIER n'est pas trouvé par rapport au répertoire de travail, il sera recherché dans le chemin des ressources (voir --resource-path) et enfin dans le sous-répertoire csl du répertoire de données utilisateur pandoc.
--natbib
Utiliser natbib pour les citations en sortie LaTeX. Cette option ne doit pas être utilisée avec l'option --citeproc ou avec une sortie PDF. Elle est destinée à la production d'un fichier LaTeX qui peut être traité avec bibtex.
--biblatex
Utiliser biblatex pour les citations en sortie LaTeX. Cette option ne doit pas être utilisée avec l'option --citeproc ou avec une sortie PDF. Elle est destinée à la production d'un fichier LaTeX qui peut être traité avec bibtex ou biber.

Rendu des mathématiques en HTML

La valeur par défaut consiste à rendre les mathématiques TeX autant que possible en utilisant des caractères Unicode. Les formules sont placées à l'intérieur d'un span avec class="math", de sorte qu'elles puissent être stylisées différemment du texte environnant si nécessaire. Cependant, cela donne des résultats acceptables uniquement pour les mathématiques de base ; vous voudrez généralement utiliser --mathjax ou l'une des options suivantes.

--mathjax[=URL]
Utiliser MathJax pour afficher les mathématiques TeX intégrées dans la sortie HTML. Les mathématiques TeX seront placées entre \(...\) (pour les mathématiques en ligne) ou \[...\] (pour les mathématiques affichées) et enveloppées dans des balises <span> avec la classe math. Ensuite, le JavaScript MathJax les rendra. L'URL doit pointer vers le script de chargement MathJax.js. Si aucune URL n'est fournie, un lien vers le CDN Cloudflare sera inséré.
--mathml
Convertir les mathématiques TeX en MathML (en epub3, docbook4, docbook5, jats, html4 et html5). C'est la valeur par défaut en sortie odt. MathML est pris en charge nativement par les principaux navigateurs Web et certains lecteurs d'e-books.
--webtex[=URL]
Convertir les formules TeX en balises <img> qui pointent vers un script externe convertissant les formules en images. La formule sera encodée en URL et concaténée avec l'URL fournie. Pour les images SVG, vous pouvez par exemple utiliser --webtex https://latex.codecogs.com/svg.latex?. Si aucune URL n'est spécifiée, l'URL CodeCogs générant des PNG sera utilisée (https://latex.codecogs.com/png.latex?). Remarque : l'option --webtex affectera également la sortie Markdown ainsi que le HTML, ce qui est utile si vous ciblez une version de Markdown sans prise en charge native des mathématiques.
--katex[=URL]
Utiliser KaTeX pour afficher les mathématiques TeX intégrées dans la sortie HTML. L'URL est l'URL de base de la bibliothèque KaTeX. Ce répertoire doit contenir un fichier katex.min.js et un fichier katex.min.css. Si aucune URL n'est fournie, un lien vers le CDN KaTeX sera inséré.
--gladtex
Envelopper les mathématiques TeX dans des balises <eq> dans la sortie HTML. Le HTML résultant peut ensuite être traité par GladTeX pour produire des images SVG des formules mises en page et un fichier HTML avec ces images intégrées.
pandoc -s --gladtex input.md -o myfile.htex
gladtex -d image_dir myfile.htex
# produit myfile.html et des images dans image_dir

Options pour les scripts d'encapsulation

--dump-args[=true|false]
Afficher des informations sur les arguments de la ligne de commande sur stdout, puis quitter. Cette option est principalement destinée à être utilisée dans des scripts d'encapsulation. La première ligne de sortie contient le nom du fichier de sortie spécifié avec l'option -o, ou - (pour stdout) si aucun fichier de sortie n'a été spécifié. Les lignes restantes contiennent les arguments de la ligne de commande, un par ligne, dans l'ordre où ils apparaissent. Ceux-ci n'incluent pas les options pandoc régulières et leurs arguments, mais incluent toutes les options apparaissant après un séparateur -- à la fin de la ligne.
--ignore-args[=true|false]
Ignorer les arguments de la ligne de commande (pour une utilisation dans les scripts d'encapsulation). Les options pandoc régulières ne sont pas ignorées. Ainsi, par exemple,
pandoc --ignore-args -o foo.html -s foo.txt -- -e latin1

est équivalent à

pandoc -o foo.html -s

FICHIERS DEFAULTS

L'option --defaults peut être utilisée pour spécifier un ensemble d'options, sous la forme d'un fichier YAML.

Les champs omis auront leurs valeurs par défaut habituelles. Ainsi, un fichier de defaults peut être aussi simple qu'une seule ligne :

verbosity: INFO

Dans les champs qui attendent un chemin de fichier (ou une liste de chemins de fichiers), la syntaxe suivante peut être utilisée pour interpoler des variables d'environnement :

csl:  ${HOME}/mycsldir/special.csl

${USERDATA} peut également être utilisé ; cela sera toujours résolu en tant que répertoire de données utilisateur actuel lors de l'analyse du fichier de defaults, quelle que soit la valeur de la variable d'environnement USERDATA.

${.} sera résolu en tant que répertoire contenant le fichier de defaults lui-même. Cela vous permet de faire référence à des ressources contenues dans ce répertoire :

epub-cover-image: ${.}/cover.jpg
epub-metadata: ${.}/meta.xml
resource-path:
- .             # le répertoire de travail à partir duquel pandoc est exécuté
- ${.}/images   # le sous-répertoire des images du répertoire
                # contenant ce fichier de defaults

Cette syntaxe d'interpolation de variables d'environnement ne fonctionne *que* dans les champs qui attendent des chemins de fichiers.

Les fichiers de defaults peuvent être placés dans le sous-répertoire defaults du répertoire de données utilisateur et être utilisés depuis n'importe quel répertoire. Par exemple, on pourrait créer un fichier spécifiant les defaults pour l'écriture de lettres, le sauvegarder sous letter.yaml dans le sous-répertoire defaults du répertoire de données utilisateur, et ensuite invoquer ces defaults depuis n'importe quel répertoire en utilisant pandoc --defaults letter ou pandoc -dletter.

Lorsque plusieurs defaults sont utilisés, leur contenu sera combiné.

Notez que, là où les arguments de ligne de commande peuvent être répétés (--metadata-file, --css, --include-in-header, --include-before-body, --include-after-body, --variable, --metadata, --syntax-definition), les valeurs spécifiées sur la ligne de commande seront combinées avec les valeurs spécifiées dans le fichier de defaults, plutôt que de les remplacer.

Les tableaux suivants montrent la correspondance entre la ligne de commande et les entrées du fichier de defaults.

 ligne de commande                   fichier de defaults                     
 --------------------------------- ----------------------------------

                                     - foo.md                    
                                     - bar.md

La valeur de input-files peut être laissée vide pour indiquer une entrée depuis stdin, et il peut s'agir d'une séquence vide [] pour aucune entrée.

MODÈLES

Lorsque l'option -s/--standalone est utilisée, pandoc utilise un modèle pour ajouter l'en-tête et le pied de page nécessaires à un document autonome. Pour voir le modèle par défaut utilisé, tapez simplement

pandoc -D *FORMAT*

où FORMAT est le nom du format de sortie. Un modèle personnalisé peut être spécifié en utilisant l'option --template. Vous pouvez également remplacer les modèles système par défaut pour un format de sortie donné FORMAT en plaçant un fichier templates/default.*FORMAT* dans le répertoire de données utilisateur (voir --data-dir, ci-dessus). Exceptions :

•
Pour la sortie odt, personnalisez le modèle default.opendocument.
•
Pour la sortie pdf, personnalisez le modèle default.latex (ou le modèle default.context, si vous utilisez -t context, ou le modèle default.ms, si vous utilisez -t ms, ou le modèle default.html, si vous utilisez -t html).
•
docx et pptx n'ont pas de modèle (cependant, vous pouvez utiliser --reference-doc pour personnaliser la sortie).

Les modèles contiennent des variables, qui permettent d'inclure des informations arbitraires à n'importe quel point du fichier. Elles peuvent être définies en ligne de commande en utilisant l'option -V/--variable. Si une variable n'est pas définie, pandoc recherchera la clé dans les métadonnées du document, qui peuvent être définies en utilisant soit des blocs de métadonnées YAML, soit avec l'option -M/--metadata. De plus, certaines variables reçoivent des valeurs par défaut de la part de pandoc. Voir Variables ci-dessous pour une liste des variables utilisées dans les modèles par défaut de pandoc.

Si vous utilisez des modèles personnalisés, vous devrez peut-être les réviser à mesure que pandoc évolue. Nous recommandons de suivre les modifications dans les modèles par défaut et de modifier vos modèles personnalisés en conséquence. Un moyen simple de le faire est de "fork" le dépôt pandoc-templates et de fusionner les modifications après chaque version de pandoc.

Syntaxe des modèles

Commentaires

Tout ce qui se trouve entre la séquence $-- et la fin de la ligne sera traité comme un commentaire et omis de la sortie.

Délimiteurs

Pour marquer les variables et les structures de contrôle dans le modèle, soit $...$, soit ${...} peut être utilisé comme délimiteur. Les styles peuvent également être mélangés dans le même modèle, mais le délimiteur d'ouverture et de fermeture doivent correspondre dans chaque cas. Le délimiteur d'ouverture peut être suivi d'un ou plusieurs espaces ou tabulations, qui seront ignorés. Le délimiteur de fermeture peut être précédé d'un ou plusieurs espaces ou tabulations, qui seront ignorés.

Pour inclure un $ littéral dans le document, utilisez $$.

Variables interpolées

Un emplacement pour une variable interpolée est un nom de variable entouré de délimiteurs correspondants. Les noms de variables doivent commencer par une lettre et peuvent contenir des lettres, des chiffres, _, -, et .. Les mots-clés it, if, else, endif, for, sep, et endfor ne peuvent pas être utilisés comme noms de variables. Exemples :

$foo$
$foo.bar.baz$
$foo_bar.baz-bim$
$ foo $
${foo}
${foo.bar.baz}
${foo_bar.baz-bim}
${ foo }

Les noms de variables avec des points sont utilisés pour accéder aux valeurs de variables structurées. Ainsi, par exemple, employee.salary renverra la valeur du champ salary de l'objet qui est la valeur du champ employee.

•
Si la valeur de la variable est une valeur simple, elle sera rendue brutalement. (Notez qu'aucun échappement n'est effectué ; on suppose que le programme appelant échappera les chaînes de manière appropriée pour le format de sortie.)
•
Si la valeur est une liste, les valeurs seront concaténées.
•
Si la valeur est une carte (map), la chaîne true sera rendue.
•
Toute autre valeur sera rendue comme une chaîne vide.

Conditionnels

Un conditionnel commence par if(variable) (entouré de délimiteurs correspondants) et se termine par endif (entouré de délimiteurs correspondants). Il peut optionnellement contenir un else (entouré de délimiteurs correspondants). La section if est utilisée si variable a une valeur non vide, sinon la section else est utilisée (si présente). Exemples :

$if(foo)$bar$endif$
$if(foo)$
  $foo$
$endif$
$if(foo)$
partie un
$else$
partie deux
$endif$
${if(foo)}bar${endif}
${if(foo)}
  ${foo}
${endif}
${if(foo)}
${ foo.bar }
${else}
pas de foo!
${endif}

Le mot-clé elseif peut être utilisé pour simplifier les conditionnels imbriqués complexes :

$if(foo)$
XXX
$elseif(bar)$
YYY
$else$
ZZZ
$endif$

Boucles For

Une boucle for commence par for(variable) (entouré de délimiteurs correspondants) et se termine par endfor (entouré de délimiteurs correspondants).

•
Si variable est un tableau (array), le matériel à l'intérieur de la boucle sera évalué à plusieurs reprises, avec variable étant définie à chaque valeur du tableau tour à tour, et concaténé.
•
Si variable est une carte (map), le matériel à l'intérieur sera défini à la carte.
•
Si la valeur de la variable associée n'est ni un tableau ni une carte, une seule itération sera effectuée sur sa valeur.

Exemples :

class="Bl-tag"> 
$for(foo)$$foo$$sep$, $endfor$
$for(foo)$
  - $foo.last$, $foo.first$
$endfor$
${ for(foo.bar) }
  - ${ foo.bar.last }, ${ foo.bar.first }
${ endfor }
$for(mymap)$
$it.name$: $it.office$
$endfor$

Vous pouvez éventuellement spécifier un séparateur entre les valeurs consécutives en utilisant sep (entre délimiteurs correspondants). Le contenu entre sep et endfor est le séparateur.

${ for(foo) }${ foo }${ sep }, ${ endfor }

Au lieu d'utiliser variable dans la boucle, le mot-clé anaphorique spécial it peut être utilisé.

${ for(foo.bar) }
  - ${ it.last }, ${ it.first }
${ endfor }

Partiels

Les partiels (sous-modèles stockés dans différents fichiers) peuvent être inclus en utilisant le nom du partiel, suivi de (), par exemple :

${ styles() }

Les partiels seront recherchés dans le répertoire contenant le modèle principal. Le nom du fichier sera supposé avoir la même extension que le modèle principal s'il n'a pas d'extension. Lors de l'appel du partiel, le nom complet incluant l'extension du fichier peut également être utilisé :

${ styles.html() }

(Si un partiel n'est pas trouvé dans le répertoire du modèle et que le chemin du modèle est donné en chemin relatif, il sera également recherché dans le sous-répertoire templates du répertoire de données utilisateur.)

Les partiels peuvent éventuellement être appliqués à des variables en utilisant deux-points :

${ date:fancy() }
${ articles:bibentry() }

Si articles est un tableau, cela itérera sur ses valeurs, appliquant le partiel bibentry() à chacune d'elles. Ainsi, le second exemple ci-dessus est équivalent à :

${ for(articles) }
${ it:bibentry() }
${ endfor }

Notez que le mot-clé anaphorique it doit être utilisé lors de l'itération sur des partiels. Dans les exemples ci-dessus, le partiel bibentry devrait contenir it.title (et ainsi de suite) au lieu de articles.title.

Les sauts de ligne finaux sont omis des partiels inclus.

Les partiels peuvent inclure d'autres partiels.

Un séparateur entre les valeurs d'un tableau peut être spécifié entre crochets, immédiatement après le nom de la variable ou le partiel :

${months[, ]}$
${articles:bibentry()[; ]$

Le séparateur dans ce cas est littéral et (contrairement à sep dans une boucle for explicite) ne peut pas contenir de variables interpolées ou d'autres directives de modèle.

Nidification

Pour s'assurer que le contenu est « imbriqué », c'est-à-dire que les lignes suivantes sont indentées, utilisez la directive ^ :

$item.number$  $^$$item.description$ ($item.price$)

Dans cet exemple, si item.description a plusieurs lignes, elles seront toutes indentées pour s'aligner sur la première ligne :

00123  Une belle bouteille de 18 ans d'âge
       Oban whiskey. ($148)

Pour imbriquer plusieurs lignes au même niveau, alignez-les avec la directive ^ dans le modèle. Par exemple :

$item.number$  $^$$item.description$ ($item.price$)
               (Disponible jusqu'au $item.sellby$.)

produira

00123  Une belle bouteille de 18 ans d'âge
       Oban whiskey. ($148)
       (Disponible jusqu'au 30 mars 2020.)

Si une variable apparaît seule sur une ligne, précédée d'un espace blanc et sans texte ou directives supplémentaires sur la même ligne, et que la valeur de la variable contient plusieurs lignes, elle sera imbriquée automatiquement.

Espaces insécables

Normalement, les espaces dans le modèle lui-même (par opposition aux valeurs des variables interpolées) ne sont pas insécables, mais ils peuvent être rendus insécables dans une partie du modèle en utilisant le mot-clé ~ (terminé par un autre ~).

$~$Cette longue ligne peut être coupée si le document est rendu
avec une longueur de ligne courte.$~$

Pipes

Un pipe transforme la valeur d'une variable ou d'un partiel. Les pipes sont spécifiés à l'aide d'une barre oblique (/) entre le nom de la variable (ou du partiel) et le nom du pipe. Exemple :

$for(name)$
$name/uppercase$
$endfor$
$for(metadata/pairs)$
- $it.key$: $it.value$
$endfor$
$employee:name()/uppercase$

Les pipes peuvent être chaînés :

$for(employees/pairs)$
$it.key/alpha/uppercase$. $it.name$
$endfor$

Certains pipes prennent des paramètres :

|----------------------|------------|
$for(employee)$
$it.name.first/uppercase/left 20 "| "$$it.name.salary/right 10 " | " " |"$
$endfor$
|----------------------|------------|

Actuellement, les pipes suivants sont prédéfinis :

•
pairs : Convertit une map ou un tableau en un tableau de maps, chacune avec les champs key et value. Si la valeur d'origine était un tableau, la key sera l'indice du tableau, en commençant par 1.
•
uppercase : Convertit le texte en majuscules.
•
lowercase : Convertit le texte en minuscules.
•
length : Retourne la longueur de la valeur : nombre de caractères pour une valeur textuelle, nombre d'éléments pour une map ou un tableau.
•
reverse : Inverse une valeur textuelle ou un tableau, et n'a aucun effet sur les autres valeurs.
•
first : Retourne la première valeur d'un tableau, si appliqué à un tableau non vide ; sinon, retourne la valeur d'origine.
•
last : Retourne la dernière valeur d'un tableau, si appliqué à un tableau non vide ; sinon, retourne la valeur d'origine.
•
rest : Retourne toutes les valeurs sauf la première d'un tableau, si appliqué à un tableau non vide ; sinon, retourne la valeur d'origine.
•
allbutlast : Retourne toutes les valeurs sauf la dernière d'un tableau, si appliqué à un tableau non vide ; sinon, retourne la valeur d'origine.
•
chomp : Supprime les sauts de ligne finaux (et les espaces insécables).
•
nowrap : Désactive le retour à la ligne sur les espaces insécables.
•
alpha : Convertit les valeurs textuelles qui peuvent être lues comme un entier en caractères alphabétiques minuscules a..z (mod 26). Ceci peut être utilisé pour obtenir une énumération par lettres à partir des indices de tableau. Pour obtenir des lettres majuscules, chaînez avec uppercase.
•
roman : Convertit les valeurs textuelles qui peuvent être lues comme un entier en chiffres romains minuscules. Ceci peut être utilisé pour obtenir une énumération par lettres à partir des indices de tableau. Pour obtenir des chiffres romains majuscules, chaînez avec uppercase.
•
left n "leftborder" "rightborder" : Rend une valeur textuelle dans un bloc de largeur n, alignée à gauche, avec une bordure gauche et droite optionnelle. N'a aucun effet sur les autres valeurs. Peut être utilisé pour aligner du matériel dans des tableaux. Les largeurs sont des entiers positifs indiquant le nombre de caractères. Les bordures sont des chaînes de caractères entre guillemets doubles ; les caractères littéraux " et \ doivent être échappés avec une barre oblique inverse.
•
right n "leftborder" "rightborder" : Rend une valeur textuelle dans un bloc de largeur n, alignée à droite, et n'a aucun effet sur les autres valeurs.
•
center n "leftborder" "rightborder" : Rend une valeur textuelle dans un bloc de largeur n, alignée au centre, et n'a aucun effet sur les autres valeurs.

EXTENSIONS

Le comportement de certains lecteurs et rédacteurs peut être ajusté en activant ou en désactivant diverses extensions.

Une extension peut être activée en ajoutant +EXTENSION au nom du format et désactivée en ajoutant -EXTENSION. Par exemple, --from markdown_strict+footnotes est du Markdown strict avec les notes de bas de page activées, tandis que --from markdown-footnotes-pipe_tables est le Markdown de pandoc sans notes de bas de page ni tableaux à tuyaux.

Le lecteur et le rédacteur Markdown font de loin le plus usage des extensions. Les extensions utilisées uniquement par eux sont donc couvertes dans la section Markdown de Pandoc ci-dessous (voir Variantes Markdown pour commonmark et gfm). Dans ce qui suit, les extensions qui fonctionnent également pour d'autres formats sont couvertes.

Notez que les extensions Markdown ajoutées au format ipynb affectent les cellules Markdown dans les notebooks Jupyter (tout comme les options de ligne de commande comme --markdown-headings).

Typographie

Extension : smart

Interprète les guillemets droits comme des guillemets courbes, --- comme des tirets cadratins, -- comme des tirets demi-cadratins, et ... comme des points de suspension. Des espaces insécables sont insérés après certaines abréviations, comme « M. »

Cette extension peut être activée/désactivée pour les formats suivants :

formats d'entrée
markdown, commonmark, latex, mediawiki, org, rst, twiki, html
formats de sortie
markdown, latex, context, rst
activé par défaut dans
markdown, latex, context (entrée et sortie)

Note : Si vous *écrivez* du Markdown, l'extension smart a l'effet inverse : ce qui aurait dû être des guillemets courbes sortira droit.

En LaTeX, smart signifie utiliser les ligatures TeX standard pour les guillemets (« `` » et « '' » pour les guillemets doubles, « ` » et « ' » pour les guillemets simples) et les tirets (« -- » pour le tiret demi-cadratin et « --- » pour le tiret cadratin). Si smart est désactivé, alors en lisant du LaTeX, pandoc analysera ces caractères littéralement. En écrivant du LaTeX, l'activation de smart indique à pandoc d'utiliser les ligatures lorsque c'est possible ; si smart est désactivé, pandoc utilisera des caractères de guillemets et de tirets unicode.

Titres et sections

Extension : auto_identifiers

Un titre sans identifiant explicitement spécifié se verra attribuer automatiquement un identifiant unique basé sur le texte du titre.

Cette extension peut être activée/désactivée pour les formats suivants :

formats d'entrée
markdown, latex, rst, mediawiki, textile
formats de sortie
markdown, muse
activé par défaut dans
markdown, muse

L'algorithme par défaut utilisé pour dériver l'identifiant du texte du titre est :

•
Supprimer toute mise en forme, liens, etc.
•
Supprimer toutes les notes de bas de page.
•
Supprimer tous les caractères non alphanumériques, à l'exception des tirets bas, des tirets et des points.
•
Remplacer tous les espaces et sauts de ligne par des tirets.
•
Convertir tous les caractères alphabétiques en minuscules.
•
Supprimer tout ce qui précède la première lettre (les identifiants ne peuvent pas commencer par un chiffre ou un signe de ponctuation).
•
S'il ne reste rien après cela, utiliser l'identifiant section.

Ainsi, par exemple,

  Titre                       Identifiant
  ----------------------------- -----------------------------
  Titres de section en HTML   titres-de-section-en-html
  Maître d'hôtel                maître-dhôtel
  *Chiens*?--dans *ma* maison?       chiens--dans-ma-maison
  [HTML], [S5], ou [RTF]?       html-s5-ou-rtf
  3. Applications               applications
  33                            section

Ces règles devraient, dans la plupart des cas, permettre de déterminer l'identifiant à partir du texte du titre. L'exception se produit lorsque plusieurs titres ont le même texte ; dans ce cas, le premier obtiendra un identifiant comme décrit ci-dessus ; le deuxième obtiendra le même identifiant avec -1 ajouté ; le troisième avec -2 ; et ainsi de suite.

(Cependant, un algorithme différent est utilisé si gfm_auto_identifiers est activé ; voir ci-dessous.)

Ces i dentificateurs sont utilisés pour fournir des cibles de lien dans la table des matières générée par l'option --toc|--table-of-contents. Ils facilitent également la création de liens d'une section d'un document à une autre. Un lien vers cette section, par exemple, pourrait ressembler à ceci :

Notez cependant que cette méthode de création de liens vers des sections ne fonctionne qu'en HTML, LaTeX et ConTeXt.

Si l'option --section-divs est spécifiée, chaque section sera enveloppée dans une section (ou un div, si html4 a été spécifié), et l'identificateur sera attaché à la balise <section> (ou <div>) englobante plutôt qu'au titre lui-même. Extension : ascii_identifiers

Force les identificateurs produits par auto_identifiers à être en ASCII pur. Les accents sont supprimés des lettres latines accentuées, et les lettres non latines sont omises.

Modifie l'algorithme utilisé par auto_identifiers pour se conformer à la méthode de GitHub. Les espaces sont convertis en tirets (-), les caractères majuscules en caractères minuscules, et les caractères de ponctuation autres que - et _ sont supprimés. Les emojis sont remplacés par leurs noms.

Prise en charge de Literate Haskell

Extension : literate_haskell

Traite le document comme une source Literate Haskell.

Cette extension peut être activée/désactivée pour les formats suivants :

formats d'entrée
markdown, rst, latex
formats de sortie
markdown, rst, latex, html

Si vous ajoutez +lhs (ou +literate_haskell) à l'un des formats ci-dessus, pandoc traitera le document comme une source Literate Haskell. Cela signifie que

•
En entrée Markdown, les sections en « bird track » seront analysées comme du code Haskell plutôt que comme des citations de bloc. Le texte entre \begin{code} et \end{code} sera également traité comme du code Haskell. Pour les titres de style ATX, le caractère `=' sera utilisé à la place de `#'.
•
En sortie Markdown, les blocs de code avec les classes haskell et literate seront rendus en utilisant des « bird tracks », et les citations de bloc seront indentées d'un espace, de sorte qu'elles ne seront pas traitées comme du code Haskell. De plus, les titres seront rendus en style setext (avec des soulignements) plutôt qu'en style ATX (avec des caractères `#' ). (C'est parce que ghc traite les caractères `#' dans la colonne 1 comme introduisant des numéros de ligne.)
•
En entrée reStructuredText, les sections en « bird track » seront analysées comme du code Haskell.
•
En sortie reStructuredText, les blocs de code avec la classe haskell seront rendus en utilisant des « bird tracks ».
•
En entrée LaTeX, le texte dans les environnements code sera analysé comme du code Haskell.
•
En sortie LaTeX, les blocs de code avec la classe haskell seront rendus à l'intérieur des environnements code.
•
En sortie HTML, les blocs de code avec la classe haskell seront rendus avec la classe literatehaskell et des « bird tracks ».

Exemples :

pandoc -f markdown+lhs -t html

lit du code source Literate Haskell formaté avec des conventions Markdown et écrit du HTML ordinaire (sans « bird tracks »).

pandoc -f markdown+lhs -t html+lhs

écrit du HTML avec le code Haskell dans des « bird tracks », de sorte qu'il puisse être copié et collé comme source Literate Haskell.

Notez que GHC attend les « bird tracks » dans la première colonne, donc les blocs de code littéraires indentés (par exemple, à l'intérieur d'un environnement listé) ne seront pas reconnus par le compilateur Haskell.

MARKDOWN DE PANDOC

Pandoc comprend une version étendue et légèrement révisée de la syntaxe Markdown de John Gruber. Ce document explique la syntaxe, en notant les différences par rapport au Markdown original. Sauf indication contraire, ces différences peuvent être supprimées en utilisant le format markdown_strict au lieu de markdown. Les extensions peuvent être activées ou désactivées pour spécifier le comportement de manière plus granulaire. Elles sont décrites ci-dessous. Voir également Extensions ci-dessus, pour les extensions qui fonctionnent également sur d'autres formats.

Philosophie

Markdown est conçu pour être facile à écrire, et, encore plus important, facile à lire :

Un document formaté en Markdown devrait pouvoir être publié tel quel, comme du texte brut, sans donner l'impression qu'il a été marqué avec des balises ou des instructions de formatage. – John Gruber

Ce principe a guidé les décisions de pandoc dans la recherche de syntaxe pour les tableaux, les notes de bas de page et autres extensions.

Il y a, cependant, un aspect où les objectifs de pandoc diffèrent des objectifs originaux de Markdown. Alors que Markdown a été initialement conçu dans le but de générer du HTML, pandoc est conçu pour de multiples formats de sortie. Ainsi, bien que pandoc permette l'intégration de HTML brut, il le décourage, et fournit d'autres moyens, non-HTML, pour représenter des éléments de document importants comme les listes de définitions, les tableaux, les mathématiques et les notes de bas de page.

Paragraphes

Un paragraphe est une ou plusieurs lignes de texte suivies d'une ou plusieurs lignes vides. Les sauts de ligne sont traités comme des espaces, vous pouvez donc réorganiser vos paragraphes comme vous le souhaitez. Si vous avez besoin d'un saut de ligne forcé, mettez deux espaces ou plus à la fin d'une ligne.

Extension : escaped_line_breaks

Une barre oblique inverse suivie d'un saut de ligne est également un saut de ligne forcé. Note : dans les cellules de tableaux multilignes et de grille, c'est la seule façon de créer un saut de ligne forcé, car les espaces finaux dans les cellules sont ignorés.

Titres

Il existe deux types de titres : Setext et ATX.

Titres de style Setext

Un titre de style Setext est une ligne de texte "soulignée" par une rangée de signes = (pour un titre de niveau un) ou de signes - (pour un titre de niveau deux) :

Un titre de niveau un
===================
Un titre de niveau deux
-------------------

Le texte du titre peut contenir du formatage en ligne, tel que l'emphase (voir Mise en forme en ligne, ci-dessous).

Titres de style ATX

Un titre de style ATX consiste en un à six signes # et une ligne de texte, facultativement suivie d'un nombre quelconque de signes #. Le nombre de signes # au début de la ligne est le niveau du titre :

## Un titre de niveau deux
### Un titre de niveau trois ###

Comme pour les titres de style Setext, le texte du titre peut contenir du formatage :

# Un titre de niveau un avec un [lien](/url) et de l'*emphase*

Extension : blank_before_header

La syntaxe Markdown originale ne nécessite pas de ligne vide avant un titre. Pandoc l'exige (sauf, bien sûr, au début du document). La raison de cette exigence est qu'il est trop facile qu'un # se retrouve au début d'une ligne par accident (peut-être à cause d'un retour à la ligne). Considérons, par exemple :

J'aime plusieurs de leurs parfums de glace :
#22, par exemple, et #5.

Extension : space_in_atx_header

De nombreuses implémentations Markdown n'exigent pas d'espace entre les signes d'ouverture # d'un titre ATX et le texte du titre, de sorte que #5 bolt et #hashtag soient considérés comme des titres. Avec cette extension, pandoc exige l'espace.

Identificateurs de titre

Voir aussi l'extension auto_identifiers ci-dessus.

Extension : header_attributes

Les titres peuvent se voir attribuer des attributs en utilisant cette syntaxe à la fin de la ligne contenant le texte du titre :

{#identificateur .classe .classe cle=valeur cle=valeur}

Ainsi, par exemple, les titres suivants se verront tous attribuer l'identificateur foo :

# Mon titre {#foo}
## Mon titre ##    {#foo}
Mon autre titre   {#foo}
---------------

(Cette syntaxe est compatible avec PHP Markdown Extra.)

Notez que bien que cette syntaxe permette l'attribution de classes et d'attributs clé/valeur, les auteurs n'utilisent généralement pas toutes ces informations. Les identificateurs, les classes et les attributs clé/valeur sont utilisés dans les formats HTML et basés sur HTML comme EPUB et slidy. Les identificateurs sont utilisés pour les étiquettes et les ancres de liens dans les générateurs LaTeX, ConTeXt, Textile, Jira markup et AsciiDoc.

Extension: auto_identifiers


Pandoc recognizes headings of the form:



  

  

    
# Heading 1
## Heading 2
### Heading 3
#### Heading 4
##### Heading 5
###### Heading 6


  




These are converted to HTML h1-h6 tags.


By default, pandoc automatically generates an HTML anchor ID for each heading. It does this by converting the heading text to lowercase, removing punctuation and spaces, and adding hyphens between words. For example, a heading such as "A Brief History of Time" will get the ID "a-brief-history-of-time".


If you want to use your own IDs, or if you want to ensure that headings with identical text get distinct IDs, you can specify the ID explicitly using the explicit link reference definition syntax:



  

  

    
# Heading {#my-custom-id}
## Another Heading {#another-one}
### Yet Another Heading


  




This will generate the following HTML:



  

  

    
<h1 id="my-custom-id">Heading</h1>
<h2 id="another-one">Another Heading</h2>
<h3>Yet Another Heading</h3>


  




The automatic ID generation can be disabled using the
    --normalize flag. This means that headings will not
    have IDs automatically generated, and only explicitly defined IDs will be
    used.


You can also link to headings using the standard Markdown link syntax. If the link text matches the heading text (case-insensitively), and there is no explicit ID for that heading, the heading ID will be automatically generated:



  

  

    
[A Brief History of Time](#a-brief-history-of-time)


  




If there is an explicit ID, the link will point to that ID:



  

  

    
[Heading {#my-custom-id}](#my-custom-id)


  




If the link text does not match the heading text, you can still link to the heading by explicitly specifying the ID, either using the auto-generated ID or a custom ID:



  

  

    
[Click here](#a-brief-history-of-time)
[Go to section 3](#my-custom-id)


  




Alternatively, you can use the explicit link reference definition syntax to define a link to a heading:



  

  

    
[A Brief History of Time]


  




instead of giving the identifier explicitly:



  

  

    
[Heading identifiers in HTML](#heading-identifiers-in-html)


  




If there are multiple headings with identical text, the
    corresponding reference will link to the first one only, and you will need
    to use explicit links to link to the others, as described above.


Like regular reference links, these references are
    case-insensitive.


Explicit link reference definitions always take priority over
    implicit heading references. So, in the following example, the link will
    point to bar, not to
  #foo:



  

  

    
# Foo
[foo]: bar
See [foo]


  








Citations en bloc


Markdown utilise les conventions de courriel pour citer des blocs de texte. Une citation en bloc est constituée d'un ou plusieurs paragraphes ou d'autres éléments de bloc (listes, titres, etc.), chaque ligne étant précédée d'un caractère
    > et éventuellement d'un espace. (Le
    > n'a pas besoin de commencer en marge gauche, mais il ne doit pas être indenté de plus de trois espaces.)



  

  

    
> Ceci est une citation en bloc. Ce
> paragraphe a deux lignes.
>
> 1. Ceci est une liste dans une citation en bloc.
> 2. Deuxième élément.


  




Une forme « paresseuse », qui ne nécessite le caractère
    > que sur la première ligne de chaque bloc,
    est également autorisée :



  

  

    
> Ceci est une citation en bloc. Ce
paragraphe a deux lignes.
> 1. Ceci est une liste dans une citation en bloc.
2. Deuxième élément.


  




Parmi les éléments de bloc qui peuvent être contenus dans une citation en bloc, il y a d'autres citations en bloc. C'est-à-dire que les citations en bloc peuvent être imbriquées :



  

  

    
> Ceci est une citation en bloc.
>
> > Une citation en bloc dans une citation en bloc.


  




Si le caractère > est suivi d'un espace optionnel, cet espace sera considéré comme faisant partie du marqueur de citation en bloc et non de l'indentation du contenu. Ainsi, pour mettre un bloc de code indenté dans une citation en bloc, il faut cinq espaces après le
    > :



  

  

    
>     code


  








Extension : blank_before_blockquote


La syntaxe Markdown d'origine n'exige pas de ligne vide avant une citation en bloc. Pandoc l'exige (sauf, bien sûr, au début du document). La raison de cette exigence est qu'il est très facile qu'un > se retrouve accidentellement en début de ligne (peut-être par retour à la ligne). Ainsi, sauf si le format markdown_strict est utilisé, ce qui suit ne produit pas de citation en bloc imbriquée dans pandoc :



  

  

    
> Ceci est une citation en bloc.
>> Pas imbriqué, car `blank_before_blockquote` est activé par défaut


  








Blocs de texte brut (code)






Blocs de code indentés


Un bloc de texte indenté de quatre espaces (ou une tabulation) est traité comme un texte brut : c'est-à-dire que les caractères spéciaux ne déclenchent pas de formatage spécial, et tous les espaces et sauts de ligne sont préservés. Par exemple,



  

  

    
    if (a > 3) {
      moveShip(5 * gravity, DOWN);
    }


  




L'indentation initiale (quatre espaces ou une tabulation) n'est pas considérée comme faisant partie du texte brut et est supprimée dans la sortie.


Note : les lignes vides dans le texte brut n'ont pas besoin de commencer par quatre espaces.






Blocs de code délimités






Extension : fenced_code_blocks


En plus des blocs de code indentés standard, pandoc prend en charge les blocs de code *délimités*. Ceux-ci commencent par une ligne de trois tildes (~) ou plus et se terminent par une ligne de tildes qui doit être au moins aussi longue que la ligne de départ. Tout ce qui se trouve entre ces lignes est traité comme du code. Aucune indentation n'est nécessaire :



  

  

    
~~~~~~~
if (a > 3) {
  moveShip(5 * gravity, DOWN);
}
~~~~~~~


  




Comme les blocs de code ordinaires, les blocs de code délimités doivent être séparés du texte environnant par des lignes vides.


Si le code lui-même contient une ligne de tildes ou de backticks, utilisez simplement une ligne plus longue de tildes ou de backticks au début et à la fin :



  

  

    
~~~~~~~~~~~~~~~~
~~~~~~~~~~
code incluant des tildes
~~~~~~~~~~
~~~~~~~~~~~~~~~~


  








Extension : backtick_code_blocks


Identique à fenced_code_blocks, mais utilise des backticks (`) au lieu des tildes (~).






Extension : fenced_code_attributes


Optionnellement, vous pouvez joindre des attributs à des blocs de code délimités ou à des backticks en utilisant cette syntaxe :

~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~


  




Ici, mycode est un identifiant,

Une forme raccourcie peut également être utilisée pour spécifier la langue du bloc de code :



  

  

    

Ceci est équivalent à :


Blocs de lignes






Extension : line_blocks


Un bloc de lignes est une séquence de lignes commençant par une barre
    verticale (|) suivie d'un espace. La division en lignes
    sera préservée dans la sortie, ainsi que les espaces de début ; sinon, les
    lignes seront formatées comme du Markdown. Ceci est utile pour les vers et les
  adresses :



  

  

    
| Le limerick contient des rires anatomiques
| Dans un espace très économique.
|    Mais les bons que j'ai vus
|    Si rarement sont propres
| Et les propres si rarement sont comiques
| 200 Main St.
| Berkeley, CA 94718


  




Les lignes peuvent être coupées si nécessaire, mais la ligne de
    continuation doit commencer par un espace.



  

  

    
| Le Très Honorable Très Vénérable et Juste Samuel L.
  Constable, Jr.
| 200 Main St.
| Berkeley, CA 94718


  




Le formatage en ligne (comme l'emphase) est autorisé dans le contenu
    (bien qu'il ne puisse pas traverser les limites des lignes). Le formatage au
    niveau du bloc (comme les citations en bloc ou les listes) n'est pas reconnu.

Listes






Listes à puces


Une liste à puces est une liste d'éléments de liste à puces. Un élément de liste à puces commence par une puce (*,
    + ou -). Voici un exemple simple :



  

  

    
* un
* deux
* trois


  




Cela produira une liste « compacte ». Si vous voulez une liste
    « lâche », dans laquelle chaque élément est formaté comme un paragraphe,
    mettez des espaces entre les éléments :



  

  

    
* un
* deux
* trois


  




Les puces n'ont pas besoin d'être alignées avec la marge gauche ; elles peuvent être indentées de un, deux ou trois espaces. La puce doit être suivie d'un espace blanc.


Les éléments de liste ont meilleur aspect si les lignes suivantes sont alignées sur la première ligne (après la puce) :



  

  

    
* voici mon premier
  élément de liste.
* et mon deuxième.


  




Mais Markdown autorise également un format « paresseux » :



  

  

    
* voici mon premier
élément de liste.
* et mon deuxième.


  








Contenu de bloc dans les éléments de liste




Contenu de bloc dans les éléments de liste


Un élément de liste peut contenir plusieurs paragraphes et d'autres
    contenus de bloc. Cependant, les paragraphes suivants doivent être précédés d'une ligne vide et
    indentés pour s'aligner sur le premier contenu non-espace après le marqueur de liste.



  

  

    
    * Premier paragraphe.
    Suite.
    * Deuxième paragraphe. Avec un bloc de code, qui doit être indenté
    huit espaces :
        { code }


  




Exception : si le marqueur de liste est suivi d'un bloc de code indenté, qui doit commencer 5 espaces après le marqueur de liste, alors les paragraphes suivants doivent commencer deux colonnes après le dernier caractère du marqueur de liste :



  

  

    
*     code
  paragraphe de continuation


  




Les éléments de liste peuvent inclure d'autres listes. Dans ce cas, la ligne vide précédente est facultative. La liste imbriquée doit être indentée pour s'aligner sur le premier caractère non-espace après le marqueur de liste de l'élément de liste parent.



  

  

    
* fruits
  + pommes
    - macintosh
    - red delicious
  + poires
  + pêches
* légumes
  + brocoli
  + bette


  




Comme mentionné ci-dessus, Markdown vous permet d'écrire des éléments de liste
    "paresseusement", au lieu d'indenter les lignes de continuation. Cependant, s'il y a plusieurs paragraphes ou d'autres blocs dans un élément de liste, la première ligne de chacun doit être indentée.



  

  

    
+ Un élément de liste paresseux, paresseux.
item.
+ Un autre; cela semble
mauvais mais est légal.
    Deuxième paragraphe du deuxième
élément de liste.


  








Listes ordonnées


Les listes ordonnées fonctionnent comme les listes à puces, sauf que les éléments
    commencent par des numéroteurs plutôt que des puces.


Dans le Markdown original, les numéroteurs sont des nombres décimaux suivis d'un point et d'un espace. Les nombres eux-mêmes sont ignorés, il n'y a donc aucune différence entre cette liste :



  

  

    
1.  un
2.  deux
3.  trois


  




et celle-ci :



  

  

    
5.  un
7.  deux
1.  trois


  








Extension : fancy_lists


Contrairement au Markdown original, pandoc autorise les éléments de liste ordonnée à être marqués avec des lettres majuscules et minuscules et des chiffres romains, en plus des chiffres arabes. Les marqueurs de liste peuvent être entourés de parenthèses ou suivis d'une seule parenthèse droite ou d'un point. Ils doivent être séparés du texte qui suit par au moins un espace, et, si le marqueur de liste est une lettre majuscule avec un point, par au moins deux espaces.


L'extension fancy_lists autorise également l'utilisation de
    `#' comme marqueur de liste ordonnée à la place d'un chiffre :



  

  

    
#. un
#. deux


  




Note : le marqueur de liste ordonnée `#' ne fonctionne pas avec
    commonmark.






Extension : startnum


Pandoc prête également attention au type de marqueur de liste utilisé, ainsi qu'au numéro de départ, et ces deux éléments sont préservés dans la mesure du possible dans le format de sortie. Ainsi, ce qui suit produit une liste avec des nombres suivis d'une seule parenthèse, commençant par 9, et une sous-liste avec des chiffres romains minuscules :



  

  

    
 9)  Neuvième
10)  Dixième
11)  Onzième
       i. sousun
      ii. sousdeux
     iii. soutrois


  




Pandoc commencera une nouvelle liste chaque fois qu'un type différent de marqueur de liste sera utilisé. Ainsi, ce qui suit créera trois listes :



  

  

    
(2) Deux
(5) Trois
1.  Quatre
*   Cinq


  




Si des marqueurs de liste par défaut sont souhaités, utilisez
    #. :



  

  

    
#.  un
#.  deux
#.  trois


  








Extension : task_lists


Pandoc prend en charge les listes de tâches, en utilisant la syntaxe de GitHub-Flavored Markdown.



  

  

    
- [ ] un élément de liste de tâches non cochée
- [x] élément coché


  








Listes de définition






Extension : definition_lists


Pandoc prend en charge les listes de définition, en utilisant la syntaxe de PHP Markdown Extra avec quelques extensions.



  

  

    
Terme 1
:   Définition 1
Terme 2 avec *balisage en ligne*
:   Définition 2
        { un code, partie de la Définition 2 }
    Troisième paragraphe de la définition 2.


  




Chaque terme doit tenir sur une seule ligne, qui peut éventuellement être suivie d'une ligne vide, et doit être suivie d'une ou plusieurs définitions. Une définition commence par deux-points ou un tilde, qui peut être indenté d'un ou deux espaces.


Un terme peut avoir plusieurs définitions, et chaque définition peut se composer d'un ou plusieurs éléments de bloc (paragraphe, bloc de code, liste, etc.), chacun indenté de quatre espaces ou d'un taquet de tabulation. Le corps de la définition (sans la première ligne) doit être indenté de quatre espaces. Cependant, comme pour les autres listes Markdown, vous pouvez omettre "paresseusement" l'indentation sauf au début d'un paragraphe ou d'un autre élément de bloc :



  

  

    
Terme 1
:   Définition
avec continuation paresseuse.
    Deuxième paragraphe de la définition.


  




Si vous laissez un espace avant la définition (comme dans l'exemple ci-dessus), le texte de la définition sera traité comme un paragraphe. Dans certains formats de sortie, cela entraînera un espacement plus important entre les paires terme/définition. Pour une liste de définition plus compacte, omettez l'espace avant la définition :



  

  

    
Terme 1
  ~ Définition 1
Terme 2
  ~ Définition 2a
  ~ Définition 2b


  




Notez que l'espace entre les éléments d'une liste de définition est requis. (Une variante qui assouplit cette exigence, mais interdit le retour à la ligne "paresseux", peut être activée avec l'extension
    compact_definition_lists.)






Listes d'exemples numérotées






Extension : example_lists


Le marqueur spécial de liste
    @ peut être utilisé pour les exemples numérotés séquentiellement. Le premier élément de liste avec un marqueur
    @ sera numéroté `1', le suivant `2', et ainsi de suite, tout au long du document. Les exemples numérotés n'ont pas besoin d'apparaître dans une seule liste ; chaque nouvelle liste utilisant
    @ reprendra là où la précédente s'est arrêtée. Ainsi, par exemple :



  

  

    
(@)  Mon premier exemple sera numéroté (1).
(@)  Mon deuxième exemple sera numéroté (2).
Explication des exemples.
(@)  Mon troisième exemple sera numéroté (3).


  




Les exemples numérotés peuvent être étiquetés et référencés ailleurs dans le document :



  

  

    
(@bon)  C'est un bon exemple.
Comme l'illustre (@bon), ...


  




L'étiquette peut être n'importe quelle chaîne de caractères alphanumériques, de traits de soulignement ou de tirets.


Note : les paragraphes de continuation dans les listes d'exemples doivent toujours être indentés de quatre espaces, quelle que soit la longueur du marqueur de liste. C'est-à-dire que les listes d'exemples se comportent toujours comme si l'extension
    four_space_rule était définie. Ceci est dû au fait que les étiquettes d'exemple ont tendance à être longues, et indenter le contenu sur le premier caractère non-espace après l'étiquette serait gênant.






Terminer une liste


Et si vous voulez mettre un bloc de code indenté après une liste ?



  

  

    
-   élément un
-   élément deux
    { mon bloc de code }


  




Problème ! Ici, pandoc (comme d'autres implémentations Markdown) traitera
    { mon bloc de code } comme le deuxième paragraphe de l'élément deux, et non comme un bloc de code.


Pour "couper" la liste après l'élément deux, vous pouvez insérer du contenu non indenté, comme un commentaire HTML, qui ne produira pas de sortie visible dans aucun format :



  

  

    
-   élément un
-   élément deux
<!-- fin de la liste -->
    { mon bloc de code }


  




Vous pouvez utiliser le même truc si vous voulez deux listes consécutives au lieu d'une seule grande liste :



  

  

    
1.  un
2.  deux
3.  trois
<!-- -->
1.  uno
2.  dos
3.  tres


  








Règles horizontales


Une ligne contenant une rangée de trois caractères
    *, -, ou
    _ (éventuellement séparés par des espaces)
    produit une règle horizontale :

---------------


  




Nous recommandons fortement que les règles horizontales soient séparées du texte environnant par des lignes vides. Si une règle horizontale n'est pas suivie d'une ligne vide, pandoc peut essayer d'interpréter les lignes suivantes comme un bloc de métadonnées YAML ou un tableau.






Tableaux


Quatre types de tableaux peuvent être utilisés. Les trois premiers types supposent l'utilisation d'une police à chasse fixe, comme Courier. Le quatrième type peut être utilisé avec des polices à espacement proportionnel, car il ne nécessite pas l'alignement des colonnes.

Une légende peut être fournie facultativement avec les 4 types de tableaux (comme illustré dans les exemples ci-dessous). Une légende est un paragraphe commençant par la chaîne

    :), qui sera supprimée. Elle peut apparaître avant ou après le tableau.






Extension : simple_tables


Les tableaux simples ressemblent à ceci :

-------     ------ ----------   -------

    123     123       123          123
      1     1          1             1
Table:  Démonstration de la syntaxe des tableaux simples.


  




L'en-tête et les lignes de tableau doivent chacun tenir sur une seule ligne. Les alignements de colonnes sont déterminés par la position du texte de l'en-tête par rapport à la ligne pointillée en dessous :



  
•

  
Si la ligne pointillée est alignée avec



ith the header text on the right side but
      extends beyond it on the left, the column is right-aligned.
•

•

Extension : multiline_tables

Multiline tables allow header and table rows to span multiple lines of text (but cells that span multiple columns or rows of the table are not supported). Here is an example:

-------------------------------------------------------------

  Header    Aligned         Aligned Aligned
----------- ------- --------------- -------------------------

                                    rows.

These work like simple tables, but with the following differences:

•
They must begin with a row of dashes, before the header text (unless the header row is omitted).
•
They must end with a row of dashes, then a blank line.
•
The rows must be separated by blank lines.

In multiline tables, the table parser pays attention to the widths of the columns, and the writers try to reproduce these relative widths in the output. So, if you find that one of the columns is too narrow in the output, try widening it in the Markdown source.

----------- ------- --------------- -------------------------

                                    spans multiple lines.

                                    the blank line between
                                    rows.

| 1961-1990   | mean  | 14 °C    |
|             +-------+----------+
|             | max   | 56.7 °C  |
+-------------+-------+----------+

A table header may contain more than one row:

+---------------------+-----------------------+
| Location            | Temperature 1961-1990 |
|                     | in degree Celsius     |
|                     +-------+-------+-------+
|                     | min   | mean  | max   |
+=====================+=======+=======+=======+
| Antarctica          | -89.2 | N/A   | 19.8  |
+---------------------+-------+-------+-------+
| Earth               | -89.2 | 14    | 56.7  |
+---------------------+-------+-------+-------+

Alignments can be specified as with pipe tables, by putting colons at the boundaries of the separator line after the header:

+---------------+---------------+--------------------+
| Right         | Left          | Centered           |
+==============:+:==============+:==================:+
| Bananas       | $1.34         | built-in wrapper   |
+---------------+---------------+--------------------+

For headerless tables, the colons go on the top line instead:

+--------------:+:--------------+:------------------:+
| Right         | Left          | Centered           |
+---------------+---------------+--------------------+

A table foot can be defined by enclosing it with separator lines that use = instead of -:

 +---------------+---------------+
 | Fruit         | Price         |
 +===============+===============+
 | Bananas       | $1.34         |
 +---------------+---------------+
 | Oranges       | $2.10         |
 +===============+===============+
 | Sum           | $3.44         |
 +===============+===============+

The foot must always be placed at the very bottom of the table.

Grid tables can be created easily using Emacs’ table-mode (M-x table-insert).

Extension : pipe_tables

Pipe tables look like this:

| Right | Left | Default | Center |
|------:|:-----|---------|:------:|
|   12  |  12  |    12   |    12  |
|  123  |  123 |   123   |   123  |
|    1  |    1 |     1   |     1  |
  : Demonstration of pipe table syntax.

The syntax is identical to PHP Markdown Extra tables. The beginning and ending pipe characters are optional, but pipes are required between all columns. The colons indicate column alignment as shown. The header cannot be omitted. To simulate a headerless table, include a header with blank cells.

Since the pipes indicate column boundaries, columns need not be vertically aligned, as they are in the above example. So, this is a perfectly legal (though ugly) pipe table:

fruit| price
-----|-----:
apple|2.05
pear|1.37
orange|3.09

The cells of pipe tables cannot contain block elements like paragraphs and lists, and cannot span multiple lines. If any line of the markdown source is longer than the column width (see --columns), then the table will take up the full text width and the cell contents will wrap, with the relative cell widths determined by the number of dashes in the line separating the table header from the table body. (For example ---|- would make the first column 3/4 and the second column 1/4 of the full text width.) On the other hand, if no lines are wider than column width, then cell contents will not be wrapped, and the cells will be sized to their contents.

Note: pandoc also recognizes pipe tables of the following form, as can be produced by Emacs’ orgtbl-mode:

| One | Two   |
|-----+-------|
| my  | table |
| is  | nice  |

The difference is that + is used instead of |. Other orgtbl features are not supported. In particular, to get non-default column alignment, you’ll need to add colons as above.

Blocs de métadonnées

Extension : pandoc_title_block

If the file begins with a title block

% title
% author(s) (separated by semicolons)
% date

it will be parsed as bibliographic information, not regular text. (It will be used, for example, in the title of standalone LaTeX or HTML output.) The block may contain just a title, a title and an author, or all three elements. If you want to include an author but no title, or a title and a date but no author, you need a blank line:

%
% Author

% My title
%
% June 15, 2006

The title may occupy multiple lines, but continuation lines must begin with leading space, thus:

% My title
  on multiple lines

If a document has multiple authors, the authors may be put on separate lines with leading space, or separated by semicolons, or both. So, all of the following are equivalent:

% Author One
  Author Two

% Author One; Author Two

% Author One;
  Author Two

The date must fit on one line.

All three metadata fields may contain standard inline formatting (italics, links, footnotes, etc.).

Title blocks will always be parsed, but they will affect the output only when the --standalone (-s) option is chosen. In HTML output, titles will appear twice: once in the document head – this is the title that will appear at the top of the window i

Dans un navigateur — et une fois au début du corps du document. Le titre dans l'en-tête du document peut avoir un préfixe optionnel attaché (option --title-prefix ou -T). Le titre dans le corps apparaît comme un élément H1 avec la classe « title », de sorte qu'il peut être supprimé ou reformaté avec CSS. Si un préfixe de titre est spécifié avec -T et qu'aucun bloc de titre n'apparaît dans le document, le préfixe de titre sera utilisé seul comme titre HTML.

Le rédacteur de manuel extrait un titre, un numéro de section de manuel et d'autres informations d'en-tête et de pied de page de la ligne de titre. Le titre est supposé être le premier mot de la ligne de titre, qui peut éventuellement se terminer par un numéro de section (à un seul chiffre) entre parenthèses. (Il ne devrait y avoir aucun espace entre le titre et les parenthèses.) Tout ce qui suit est supposé être du texte supplémentaire de pied de page et d'en-tête. Un seul caractère pipe (|) doit être utilisé pour séparer le texte du pied de page du texte de l'en-tête. Ainsi,

% PANDOC(1)

donnera une page de manuel avec le titre PANDOC et la section 1.

% PANDOC(1) Pandoc User Manuals

aura également « Pandoc User Manuals » dans le pied de page.

% PANDOC(1) Pandoc User Manuals | Version 4.0

aura également « Version 4.0 » dans l'en-tête.

Extension : yaml_metadata_block

Un bloc de métadonnées YAML est un objet YAML valide, délimité par une ligne de trois tirets (---) en haut et une ligne de trois tirets (---) ou trois points (...) en bas. La ligne initiale --- ne doit pas être suivie d'une ligne vide. Un bloc de métadonnées YAML peut apparaître n'importe où dans le document, mais s'il n'est pas au début, il doit être précédé d'une ligne vide.

Notez que, compte tenu de la manière dont pandoc concatène les fichiers d'entrée lorsque plusieurs sont fournis, vous pouvez également conserver les métadonnées dans un fichier YAML séparé et le passer à pandoc en tant qu'argument, avec vos fichiers Markdown :

pandoc chap1.md chap2.md chap3.md metadata.yaml -s -o book.html

Assurez-vous simplement que le fichier YAML commence par --- et se termine par --- ou .... Alternativement, vous pouvez utiliser l'option --metadata-file. En utilisant cette approche cependant, vous ne pouvez pas référencer de contenu (comme des notes de bas de page) à partir du document d'entrée Markdown principal.

Les métadonnées seront extraites des champs de l'objet YAML et ajoutées aux métadonnées de document existantes. Les métadonnées peuvent contenir des listes et des objets (imbriqués arbitrairement), mais tous les scalaires de chaîne seront interprétés comme Markdown. Les champs dont les noms se terminent par un trait de soulignement seront ignorés par pandoc. (Ils peuvent se voir attribuer un rôle par des processeurs externes.) Les noms de champs ne doivent pas être interprétables comme des nombres ou des valeurs booléennes YAML (donc, par exemple, yes, True, et 15 ne peuvent pas être utilisés comme noms de champs).

Un document peut contenir plusieurs blocs de métadonnées. Si deux blocs de métadonnées tentent de définir le même champ, la valeur du deuxième bloc sera utilisée.

Chaque bloc de métadonnées est traité en interne comme un document YAML indépendant. Cela signifie, par exemple, que toutes les ancres YAML définies dans un bloc ne peuvent pas être référencées dans un autre bloc.

Lorsque pandoc est utilisé avec -t markdown pour créer un document Markdown, un bloc de métadonnées YAML ne sera produit que si l'option -s/--standalone est utilisée. Toutes les métadonnées apparaîtront dans un seul bloc au début du document.

Notez que les règles d'échappement YAML doivent être respectées. Ainsi, par exemple, si un titre contient un deux-points, il doit être mis entre guillemets, et s'il contient une séquence d'échappement avec une barre oblique inverse, il faut s'assurer qu'elle n'est pas traitée comme une séquence d'échappement YAML. Le caractère pipe (|) peut être utilisé pour commencer un bloc indenté qui sera interprété littéralement, sans avoir besoin d'échappement. Cette forme est nécessaire lorsque le champ contient des lignes vides ou une mise en forme au niveau du bloc :

---
title:  'Ceci est le titre : il contient un deux-points'
author:
- Auteur Un
- Auteur Deux
keywords: [rien, néant]
abstract: |
  Ceci est le résumé.
  Il se compose de deux paragraphes.
...

Le bloc littéral après le | doit être indenté par rapport à la ligne contenant le |. Sinon, le YAML sera invalide et pandoc ne l'interprétera pas comme des métadonnées. Pour un aperçu des règles complexes régissant YAML, consultez l'entrée Wikipedia sur la syntaxe YAML.

Les variables de modèle seront automatiquement définies à partir des métadonnées. Ainsi, par exemple, lors de la rédaction HTML, la variable abstract sera définie sur l'équivalent HTML du Markdown dans le champ abstract :

<p>Ceci est le résumé.</p>
<p>Il se compose de deux paragraphes.</p>

Les variables peuvent contenir des structures YAML arbitraires, mais le modèle doit correspondre à cette structure. La variable author dans les modèles par défaut attend une simple liste ou chaîne, mais peut être modifiée pour prendre en charge des structures plus complexes. La combinaison suivante, par exemple, ajouterait une affiliation à l'auteur si elle est fournie :

---
title: Le titre du document
author:
- name: Auteur Un
  affiliation: Université de quelque part
- name: Auteur Deux
  affiliation: Université de nulle part
...

Pour utiliser les auteurs structurés dans l'exemple ci-dessus, vous auriez besoin d'un modèle personnalisé :

$for(author)$
$if(author.name)$
$author.name$$if(author.affiliation)$ ($author.affiliation$)$endif$
$else$
$author$
$endif$
$endfor$

Le contenu brut à inclure dans l'en-tête du document peut être spécifié à l'aide de header-includes ; cependant, il est important de baliser ce contenu comme code brut pour un format de sortie particulier, en utilisant l'extension raw_attribute, sinon il sera interprété comme du markdown. Par exemple :

header-includes:
- |
  ```{=latex}
  \let\oldsection\section
  \renewcommand{\section}[1]{\clearpage\oldsection{#1}}
  ```

Remarque : l'extension yaml_metadata_block fonctionne avec commonmark ainsi qu'avec markdown (et elle est activée par défaut dans gfm et commonmark_x). Cependant, dans ces formats, les restrictions suivantes s'appliquent :

•
Le bloc de métadonnées YAML doit se trouver au début du document (et il ne peut y en avoir qu'un seul). Si plusieurs fichiers sont fournis en arguments à pandoc, seul le premier peut être un bloc de métadonnées YAML.
•
Les nœuds feuilles de la structure YAML sont analysés isolément les uns des autres et du reste du document. Ainsi, par exemple, vous ne pouvez pas utiliser un lien de référence dans ces contextes si la définition du lien se trouve ailleurs dans le document.

Échappements par barre oblique inverse

Extension : all_symbols_escapable

Sauf à l'intérieur d'un bloc de code ou d'un code inline, tout caractère de ponctuation ou d'espace précédé d'une barre oblique inverse sera traité littéralement, même s'il indiquait normalement du formatage. Ainsi, par exemple, si l'on écrit

*\*bonjour\**

on obtiendra

<em>*bonjour*</em>

au lieu de

<strong>bonjour</strong>

Cette règle est plus facile à retenir que la règle du Markdown original, qui n'autorise que les caractères suivants à être échappés par une barre oblique inverse :

\`*_{}[]()>#+-.!

(Cependant, si le format markdown_strict est utilisé, la règle du Markdown original sera utilisée.)

Un espace échappé par une barre oblique inverse est analysé comme un espace insécable. En sortie TeX, il apparaîtra sous forme de ~. En sortie HTML et XML, il apparaîtra sous forme de caractère d'espace insécable Unicode littéral (notez qu'il apparaîtra ainsi « invisible » dans le code source HTML généré ; vous pouvez toujours utiliser l'option de ligne de commande --ascii pour qu'il apparaisse sous forme d'entité explicite).

Une nouvelle ligne échappée par une barre oblique inverse (c'est-à-dire une barre oblique inverse à la fin d'une ligne) est analysée comme un saut de ligne forcé. Elle apparaîtra en sortie TeX sous forme de \\ et en HTML sous forme de <br />. C'est une bonne alternative à la manière « invisible » du Markdown d'indiquer des sauts de ligne forcés en utilisant deux espaces en fin de ligne.

Les échappements par barre oblique inverse ne fonctionnent pas dans les contextes de verbatim.

Formatage en ligne

Emphase

Pour *mettre en emphase* du texte, entourez-le d'astérisques (*) ou de tirets bas (_), comme ceci :

Ce texte est _en emphase avec des tirets bas_, et ceci
est *en emphase avec des astérisques*.

Deux astérisques (**) ou deux tirets bas (__) produisent une emphase forte :

Ceci est **en emphase forte** et __avec des tirets bas__.

Un caractère astérisque (*) ou tiret bas (_) entouré d'espaces, ou échappé par une barre oblique inverse, ne déclenchera pas d'emphase :

Ceci est * pas en emphase *, et \*pas plus ceci\*.

Extension : intraword_underscores

Parce que le _ est parfois utilisé à l'intérieur de mots et d'identifiants, pandoc n'interprète pas un _ entouré de caractères alphanumériques comme marqueur d'emphase. Si vous voulez mettre en emphase seulement une partie d'un mot, utilisez un astérisque (*) :

fais*able*, pas fais*able*.

Biffure

Extension : strikeout

Pour biffer une section de texte avec une ligne horizontale, entourez-la de ~~. Par exemple,

Ceci ~~est du texte supprimé.~~

Exposants et indices

Extension : superscript, subscript

Les exposants peuvent être écrits en entourant le texte à mettre en exposant par des caractères ^ ; les indices peuvent être écrits en entourant le texte à mettre en indice par des caractères ~. Par exemple,

H~2~O est un liquide.  2^10^ est 1024.

Le texte entre ^...^ ou ~...~ ne peut pas contenir d'espaces ou de sauts de ligne. Si le texte en exposant ou indice contient des espaces, ces espaces doivent être échappés avec des antislashs. (Ceci afin d'éviter les mises en exposant et indice accidentelles lors de l'utilisation ordinaire de ~ et ^, ainsi que de mauvaises interactions avec les notes de bas de page.) Ainsi, si vous voulez la lettre P avec `un chat' en indice, utilisez P~un\ chat~, pas P~un chat~.

Verbatim

Pour rendre un court passage de texte en verbatim, mettez-le entre des apostrophes inversées :

Quelle est la différence entre `>>=` et `>>`?

Si le texte en verbatim inclut une apostrophe inversée, utilisez deux apostrophes inversées :

Voici une apostrophe inversée littérale `` ` ``.

(Les espaces après les apostrophes inversées ouvrantes et avant les apostrophes inversées fermantes seront ignorés.)

La règle générale est qu'un segment verbatim commence par une séquence d'apostrophes inversées consécutives (suivies éventuellement d'un espace) et se termine par une séquence du même nombre d'apostrophes inversées (précédées éventuellement d'un espace).

Notez que les échappements par antislash (et autres constructions Markdown) ne fonctionnent pas dans les contextes verbatim :

Ceci est un antislash suivi d'un astérisque : `\*`.

Extension : inline_code_attributes

Des attributs peuvent être attachés à du texte verbatim, tout comme avec les blocs de code délimités :

`<$>`{.haskell}

Soulignement

Pour souligner du texte, utilisez la classe underline :

[Souligné]{.underline}

Ou, sans l'extension bracketed_spans (mais avec native_spans) :

<span class="underline">Souligné</span>

Cela fonctionnera dans tous les formats de sortie qui prennent en charge le soulignement.

Pour écrire en petites capitales, utilisez la classe smallcaps :

[Petites capitales]{.smallcaps}

<span class="smallcaps">Petites capitales</span>

<span style="font-variant:small-caps;">Petites capitales</span>

Cela fonctionnera dans tous les formats de sortie qui prennent en charge les petites capitales.

[Marqué]{.mark}

Cela fonctionnera dans tous les formats de sortie qui prennent en charge la mise en surbrillance.

Mathématiques

Extension : tex_math_dollars

Tout ce qui se trouve entre deux caractères $ sera traité comme des mathématiques TeX. Le $ d'ouverture doit avoir un caractère non-espace immédiatement à sa droite, tandis que le $ de fermeture doit avoir un caractère non-espace immédiatement à sa gauche, et ne doit pas être suivi immédiatement d'un chiffre. Ainsi, $20,000 et $30,000 ne seront pas analysés comme des mathématiques. Si pour une raison quelconque vous avez besoin d'inclure du texte entre des caractères $ littéraux, échappez-les avec un antislash et ils ne seront pas traités comme des délimiteurs mathématiques.

Pour les mathématiques en mode affichage, utilisez des délimiteurs $$. (Dans ce cas, les délimiteurs peuvent être séparés de la formule par des espaces blancs. Cependant, il ne peut y avoir de lignes vides entre les délimiteurs $$ d'ouverture et de fermeture.)

Les mathématiques TeX seront imprimées dans tous les formats de sortie. Leur rendu dépendra du format de sortie :

LaTeX
Elles apparaîtront en verbatim entourées de \(...\) (pour les mathématiques en ligne) ou de \[...\] (pour les mathématiques en mode affichage).
Markdown, mode Emacs Org, ConTeXt, ZimWiki
Elles apparaîtront en verbatim entourées de $...$ (pour les mathématiques en ligne) ou de $$...$$ (pour les mathématiques en mode affichage).
XWiki
Elles apparaîtront en verbatim entourées de {{formula}}..{{/formula}}.
reStructuredText
Elles seront rendues à l'aide d'un rôle de texte interprété :math:.
AsciiDoc
Pour la sortie AsciiDoc, les mathématiques apparaîtront en verbatim entourées de latexmath:[...]. Pour asciidoc_legacy, le contenu entre crochets inclura également des délimiteurs mathématiques en ligne ou en mode affichage.
Texinfo
Elles seront rendues à l'intérieur d'une commande @math.
roff man, balisage Jira
Elles seront rendues en verbatim sans les $.
MediaWiki, DokuWiki
Elles seront rendues à l'intérieur de balises <math>.
Textile
Elles seront rendues à l'intérieur de balises <span class="math">.
RTF, OpenDocument
Elles seront rendues, si possible, à l'aide de caractères Unicode, et apparaîtront sinon en verbatim.
ODT
Elles seront rendues, si possible, à l'aide de MathML.
DocBook
Si l'option --mathml est utilisée, elles seront rendues à l'aide de MathML dans une balise inlineequation ou informalequation. Sinon, elles seront rendues, si possible, à l'aide de caractères Unicode.

Elles seront rendues à l'aide du balisage mathématique OMML.
FictionBook2
Si l'option --webtex est utilisée, les formules sont rendues sous forme d'images à l'aide de CodeCogs ou d'un autre service web compatible, téléchargées et intégrées dans le livre électronique. Sinon, elles apparaîtront en verbatim.

HTML brut

Extension : raw_html

Markdown permet d'insérer du HTML brut (ou DocBook) n'importe où dans un document (sauf dans les contextes verbatim, où <, >, et & sont interprétés littéralement). (Techniquement, ce n'est pas une extension, car le Markdown standard le permet, mais cela a été fait en tant qu'extension afin de pouvoir être désactivé si désiré.)

Le HTML brut est transmis tel quel dans les sorties HTML, S5, Slidy, Slideous, DZSlides, EPUB, Markdown, CommonMark, mode Emacs Org et Textile, et supprimé dans les autres formats.

Pour une manière plus explicite d'inclure du HTML brut dans un document Markdown, voir l'extension raw_attribute.

Dans le format CommonMark, si raw_html est activé, les exposants, les indices, les biffures et les petites capitales seront représentés en HTML. Sinon, des substitutions en texte brut seront utilisées. Notez que même si raw_html est désactivé, les tableaux seront rendus avec une syntaxe HTML s'ils ne peuvent pas utiliser la syntaxe par tuyaux.

Extension : markdown_in_html_blocks

Le Markdown original permet d'inclure des “blocs” HTML : des blocs de HTML entre des balises équilibrées qui sont séparés du texte environnant par des lignes vides, et qui commencent et finissent à la marge gauche. À l'intérieur de ces blocs, tout est interprété comme du HTML, et non comme du Markdown ; ainsi (par exemple), * ne signifie pas de l'emphase.

Pandoc se comporte ainsi lorsque le format markdown_strict est utilisé ; mais par défaut, pandoc interprète le contenu entre les balises de bloc HTML comme du Markdown. Ainsi, par exemple, pandoc transformera

<table>
<tr>
<td>*un*</td>
<td>[un lien](https://google.com)</td>
</tr>
</table>

Raw HTML

By default, pandoc will process Markdown syntax within HTML block elements. For example, consider this Markdown:

<table>
<tr>
<td>*one*</td>
<td>[a link](https://google.com)</td>
</tr>
</table>

into

<table>
<tr>
<td><em>one</em></td>
<td><a href="https://google.com">a link</a></td>
</tr>
</table>

whereas Markdown.pl will preserve it as is.

There is one exception to this rule: text between <script>, <style>, and <textarea> tags is not interpreted as Markdown.

This departure from original Markdown should make it easier to mix Markdown with HTML block elements. For example, one can surround a block of Markdown text with <div> tags without preventing it from being interpreted as Markdown.

Extension: native_divs

Use native pandoc Div blocks for content inside <div> tags. For the most part this should give the same output as markdown_in_html_blocks, but it makes it easier to write pandoc filters to manipulate groups of blocks.

Extension: native_spans

Use native pandoc Span blocks for content inside <span> tags. For the most part this should give the same output as raw_html, but it makes it easier to write pandoc filters to manipulate groups of inlines.

Extension: raw_tex

In addition to raw HTML, pandoc allows raw LaTeX, TeX, and ConTeXt to be included in a document. Inline TeX commands will be preserved and passed unchanged to the LaTeX and ConTeXt writers. Thus, for example, you can use LaTeX to include BibTeX citations:

This result was proved in \cite{jones.1967}.

Note that in LaTeX environments, like

\begin{tabular}{|l|l|}\hline
Age & Frequency \\ \hline
18--25  & 15 \\
26--35  & 33 \\
36--45  & 22 \\ \hline
\end{tabular}

the material between the begin and end tags will be interpreted as raw LaTeX, not as Markdown.

For a more explicit and flexible way of including raw TeX in a Markdown document, see the raw_attribute extension.

Inline LaTeX is ignored in output formats other than Markdown, LaTeX, Emacs Org mode, and ConTeXt.

Generic raw attribute

Extension: raw_attribute

Inline spans and fenced code blocks with a special kind of attribute will be parsed as raw content with the designated format. For example, the following produces a raw roff ms block:

```{=ms}
.MYMACRO
blah blah
```

And the following produces a raw html inline element:

This is `<a>html</a>`{=html}

This can be useful to insert raw xml into docx documents, e.g. a pagebreak:

```{=openxml}
<w:p>
  <w:r>
    <w:br w:type="page"/>
  </w:r>
</w:p>
```

The format name should match the target format name (see -t/--to, above, for a list, or use pandoc --list-output-formats). Use openxml for docx output, opendocument for odt output, html5 for epub3 output, html4 for epub2 output, and latex, beamer, ms, or html5 for pdf output (depending on what you use for --pdf-engine).

This extension presupposes that the relevant kind of inline code or fenced code block is enabled. Thus, for example, to use a raw attribute with a backtick code block, backtick_code_blocks must be enabled.

The raw attribute cannot be combined with regular attributes.

LaTeX macros

Extension: latex_macros

When this extension is enabled, pandoc will parse LaTeX macro definitions and apply the resulting macros to all LaTeX math and raw LaTeX. So, for example, the following will work in all output formats, not just LaTeX:

\newcommand{\tuple}[1]{\langle #1 \rangle}
$\tuple{a, b, c}$

Note that LaTeX macros will not be applied if they occur inside a raw span or block marked with the raw_attribute extension.

When latex_macros is disabled, the raw LaTeX and math will not have macros applied. This is usually a better approach when you are targeting LaTeX or PDF.

Macro definitions in LaTeX will be passed through as raw LaTeX only if latex_macros is not enabled. Macro definitions in Markdown source (or other formats allowing raw_tex) will be passed through regardless of whether latex_macros is enabled.

Links

Markdown allows links to be specified in several ways.

Automatic links

If you enclose a URL or email address in pointy brackets, it will become a link:

<https://google.com>
<sam@green.eggs.ham>

Inline links

An inline link consists of the link text in square brackets, followed by the URL in parentheses. (Optionally, the URL can be followed by a link title, in quotes.)

This is an [inline link](/url), and here's [one with
a title](https://fsf.org "click here for a good time!").

There can be no space between the bracketed part and the parenthesized part. The link text can contain formatting (such as emphasis), but the title cannot.

Email addresses in inline links are not autodetected, so they have to be prefixed with mailto:

[Write me!](mailto:sam@green.eggs.ham)

Reference links

An explicit reference link has two parts, the link itself and the link definition, which may occur elsewhere in the document (either before or after the link).

The link consists of link text in square brackets, followed by a label in square brackets. (There cannot be space between the two unless the spaced_reference_links extension is enabled.) The link definition consists of the bracketed label, followed by a colon and a space, followed by the URL, and optionally (after a space) a link title either in quotes or in parentheses. The label must not be parseable as a citation (assuming the citations extension is enabled): citations take precedence over link labels.

Here are some examples:

[my label 1]: /foo/bar.html  "My title, optional"
[my label 2]: /foo
[my label 3]: https://fsf.org (The Free Software Foundation)
[my label 4]: /bar#special  'A title in single quotes'

The URL may optionally be surrounded by angle brackets:

[my label 5]: <http://foo.bar.baz>

The title may go on the next line:

[my label 3]: https://fsf.org
  "The Free Software Foundation"

Note that link labels are not case sensitive. So, this will work:

Here is [my link][FOO]
[Foo]: /bar/baz

In an implicit reference link, the second pair of brackets is empty:

See [my website][].
[my website]: http://foo.bar.baz

Note: In Markdown.pl and most other Markdown implementations, reference link definitions cannot occur in nested constructions such as list items or block quotes. Pandoc lifts this arbitrary-seeming restriction. So the following is fine in pandoc, though not in most other implementations:

> My block [quote].
>
> [quote]: /foo

Extension: shortcut_reference_links

In a shortcut reference link, the second pair of brackets may be omitted entirely:

See [my website].
[my website]: http://foo.bar.baz

Internal links

To link to another section of the same document, use the automatically generated identifier (see Heading identifiers). For example:

See the [Introduction](#introduction).

or

See the [Introduction].
[Introduction]: #introduction

Internal links are currently supported for HTML formats (including HTML slide shows and EPUB), LaTeX, and ConTeXt.

Images

A link immediately preceded by a ! will be treated as an image. The link text will be used as the image’s alt text:

![la lune](lalune.jpg "Voyage to the moon")
![movie reel]
[movie reel]: movie.gif

Extension: implicit_figures

If this extension is enabled, an image which is not inside a link will be enclosed in a figure.

Footnotes

Footnotes are supported using the following syntax:

Here is some text with a footnote.[^1]

[^1]: This is the footnote.

Footnote references are not automatically numbered. Instead, the label in the brackets is used. This allows you to refer to the same footnote multiple times:

Here is some text with a footnote.[^note]
And here it is again.[^note]

[^note]: This is the footnote.

You can also use labels that are parsable as citations, provided that the citations extension is enabled. In that case, the label will be treated as a citation, not a footnote. This is to avoid conflicts with Pandoc’s citation syntax.

Footnote definitions can appear anywhere in the document, but they are typically placed at the end.

Footnote definitions may also be implicit:

Here is some text with a footnote.[^1]

[^1]: This is the footnote.

If a footnote reference appears without a corresponding definition, pandoc will create an implicit footnote definition.

Extension: explicit_footers

This extension adds explicit footer blocks. These are denoted by lines starting with ===. The content of the footer block is parsed as Markdown.

Here is some text with a footer.
===
This is the footer content.
It can contain multiple paragraphs.
===
This is another footer block.

This extension is mainly useful for presentation formats, where footers may be used for things like slide numbers or presenter notes.

Extension: inline_notes

This extension is similar to explicit_footers, but it uses a different syntax to denote inline notes. Inline notes are denoted by lines starting with ---. The content of the note block is parsed as Markdown.

Here is some text with an inline note.
---
This is the inline note content.
It can contain multiple paragraphs.
---
This is another inline note block.

This extension is also mainly useful for presentation formats, where inline notes may be used for things like presenter notes.

Definition lists

Definition lists are supported using the following syntax:

Term 1
:   Definition 1

Term 2
:   Definition 2a
    Definition 2b

The term line must be followed by a blank line, then the definition line(s), which must start with a colon and a space.

Extension: delimiters_for_definitions

By default, the delimiter for definition lists is a colon. This extension allows you to use other delimiters, such as a plus sign or an equals sign.

Term 1
+   Definition 1

Term 2
=   Definition 2a
    Definition 2b

This extension is useful if you want to use definition lists in a context where colons are already used for other purposes.

Extension: extended_definition_lists

This extension extends the definition list syntax to allow for multiple terms to be associated with a single definition.

Term 1
Term 2
:   Definition 1

Term 3
:   Definition 2a
    Definition 2b

In this example, both "Term 1" and "Term 2" are associated with "Definition 1".

Tables

Pandoc supports tables using the pipe-separated syntax common in other flavors of Markdown:

Right-aligned | Center aligned | Left aligned
----------- |:-----------:|:-----------
Cell 1      | Cell 2      | Cell 3
Cell 4      | Cell 5      | Cell 6

The header row is separated from the data rows by a line containing dashes and optionally colons for alignment. The number of dashes does not matter. You can use pipes anywhere in the cell contents.

For example:

| Header 1 | Header 2 |
|----------|----------|
| Cell 1   | Cell 2   |
| Cell 3   | Cell 4   |

Here’s a table with alignment specified:

| Left-aligned | Center aligned | Right aligned |
|:-----------|:--------------:|------------:|
| Cell 1     | Cell 2        | Cell 3      |
| Cell 4     | Cell 5        | Cell 6      |

Cells may contain formatting, including links, bold, italics, and code. They may also contain block-level elements like lists or block quotes, provided they are preceded by a blank line.

The table syntax can be used for tables in HTML, LaTeX, ConTeXt, and Groff man pages.

Extension: grid_tables

This extension adds support for "grid tables", which are similar to the pipe-separated tables but use a more explicit syntax that allows for more complex table structures, including cells that span multiple rows or columns.

+-----------------+-----------------+
| Header 1        | Header 2        |
+=================+=================+
| Cell 1          | Cell 2          |
+-----------------+-----------------+
| Cell 3          | Cell 4          |
+-----------------+-----------------+

Grid tables are more verbose but offer greater control over table layout and formatting.

Extension: pipe_tables

This extension explicitly enables the pipe-separated table syntax. By default, pandoc supports pipe tables without needing this extension.

Extension: simple_tables

This extension enables the "simple table" syntax, which is a simpler version of pipe tables that does not support alignment or cell spanning.

Header 1
--------
Cell 1

Header 2
--------
Cell 2

Simple tables are easier to write but less flexible than pipe tables.

Extension: table_captions

This extension allows you to specify captions for tables using a syntax similar to that for figures.

# My Table Caption

| Header 1 | Header 2 |
|----------|----------|
| Cell 1   | Cell 2   |
| Cell 3   | Cell 4   |

The caption must immediately precede the table, and must start with a heading (e.g., # or ##).

Block quotes

Block quotes are indicated by a > at the beginning of the line:

> This is a block quote.
> It can span multiple lines.

Nested block quotes are also supported:

> This is the outer block quote.
>
> > This is the inner block quote.
>
> Back to the outer block quote.

Lists

Pandoc supports both ordered and unordered lists.

Unordered lists

Unordered lists are created using asterisks, plus signs, or hyphens:

* Item 1
* Item 2
  * Item 2a
  * Item 2b
* Item 3

Or:

+ Item 1
+ Item 2
  + Item 2a
  + Item 2b
+ Item 3

Or:

- Item 1
- Item 2
  - Item 2a
  - Item 2b
- Item 3

Note that items in a list must have the same marker. If you mix markers, the first marker determines the type of list.

Ordered lists

Ordered lists are created using numbers followed by periods:

1. Item 1
2. Item 2
   1. Item 2a
   2. Item 2b
3. Item 3

The numbers do not have to be in order. Pandoc will automatically number them correctly in the output.

However, if the numbers are not consecutive, pandoc will interpret the list as a set of separate lists, and will not automatically number them.

To ensure that lists are numbered correctly, use consecutive numbers:

1. Item 1
2. Item 2
   1. Item 2a
   2. Item 2b
3. Item 3

Note that the second level list items are indented relative to the first level list items.

You can also use Roman numerals or letters for ordered lists:

A. Item A
B. Item B
C. Item C

i. Item i
ii. Item ii
iii. Item iii

Task lists

Task lists can be created by adding square brackets with a space or an x inside to list items:

* [x] This is a completed task.
* [ ] This is an incomplete task.

Task lists are supported in HTML, Markdown, and Org mode output.

Continuations in lists

If a list item is followed by another list item that is indented more than the first, it will be treated as a continuation of the first list item. This allows you to include block-level elements within list items:

* Item 1
  This is a paragraph within Item 1.

  * Item 2

This rule also applies to nested lists.

Tight lists

By default, pandoc treats lists as "loose", meaning that each list item is treated as a separate paragraph. This results in extra vertical space between items.

If you want "tight" lists, where list items are not separated by extra space, you can use the tight_lists extension.

With tight_lists enabled, the following Markdown:

* Item 1
* Item 2

will be rendered as:

<ul>
<li>Item 1</li>
<li>Item 2</li>
</ul>

Without tight_lists, there would be extra vertical space between the list items.

Code blocks

Code blocks can be created in two ways:

Fenced code blocks

Fenced code blocks are created by lines starting with four or more tildes or dashes:

~~~~
This is a code block.
It can contain multiple lines.
~~~~

You can also specify the language of the code block:

```python
def hello():
  print "Hello, world!"
```

The language identifier will be used for syntax highlighting when rendering to HTML.

Indented code blocks

Indented code blocks are created by indenting the lines by four spaces or one tab:

    This is an indented code block.
    It can contain multiple lines.

Note that indented code blocks are parsed differently from fenced code blocks. In particular, indented code blocks cannot contain blank lines. If you need blank lines within a code block, use fenced code blocks.

Attributes for code blocks

Pandoc extends fenced code blocks to allow attributes, which can be used to specify an ID and/or classes for the code block. This is useful for referencing code blocks or for applying CSS styles.

```python {#my-code-block .python .numberLines}
def hello():
  print "Hello, world!"
```

The ID comes first, preceded by a hash symbol (#). Then come the classes, each preceded by a dot (.). You can specify multiple classes. The language identifier is still supported and should come before the attributes.

Line numbering in code blocks

You can enable line numbering in fenced code blocks by adding the numberLines class to the attributes:

```python {#my-code-block .python .numberLines}
def hello():
  print "Hello, world!"
```

This will cause line numbers to be displayed next to the code.

Highlighting specific lines in code blocks

You can highlight specific lines in fenced code blocks by adding a highlight attribute with a comma-separated list of line numbers or ranges:

```python {#my-code-block .python highlight="1,3-5"}
def hello():  # Line 1
  print "Hello, world!" # Line 2
  another_function() # Line 3
  yet_another()  # Line 4
  final_function() # Line 5
```

This is useful for drawing attention to specific parts of the code in documentation.

Hugging the left edge

By default, pandoc removes leading indentation from code blocks to prevent it from being interpreted as Markdown formatting. However, sometimes you want to preserve that indentation, especially when using fenced code blocks.

If you enable the hugging_the_left_edge extension, pandoc will not remove leading indentation from fenced code blocks. This can be useful when you want to preserve the exact formatting of the code.

Minimal div attributes

This extension allows you to use minimal div attributes in fenced code blocks. For example:

``` {#my-code-block}
code
```

This is equivalent to specifying {#my-code-block} as a regular attribute.

Horizontal rules

Horizontal rules can be created using three or more hyphens, asterisks, or underscores on a line by themselves:

---

Or:

***

Or:

___

Emphasis and strong emphasis

You can emphasize text by surrounding it with asterisks or underscores:

*emphasized text*
_emphasized text_

You can make text strongly emphasized by surrounding it with two asterisks or two underscores:

**strongly emphasized text**
__strongly emphasized text__

You can also combine emphasis and strong emphasis:

***strongly emphasized and emphasized text***
___strongly emphasized and emphasized text___

Note that underscores within words are not treated as emphasis. For example, `_this_` will not be emphasized.

Strikeout

Text can be struck out by surrounding it with two tildes:

~~This text is struck out.~~

Superscripts and subscripts

Superscripts and subscripts are not part of standard Markdown, but pandoc supports them using the following syntax:

x^2^
x_2_
x^2^y_{3a}

This is converted to LaTeX for LaTeX output, and to HTML for HTML output.

Hard line breaks

A line break within a paragraph will be treated as a hard line break (a line break in the output) if and only if the line break is preceded by two or more spaces:

This is the first line.  
This is the second line.

Alternatively, you can use the HTML entity &#10; or the LaTeX command \\ to insert a hard line break.

Soft line breaks

By default, pandoc treats line breaks in the input Markdown as whitespace, effectively joining lines into paragraphs. This is often called a "soft line break".

If you want to preserve line breaks exactly as they appear in the input (i.e., treat them as hard line breaks), you can enable the hard_line_breaks extension.

Ending a paragraph

A paragraph is terminated by a blank line.

Inline markup

The following inline markup elements are supported:

Code spans

Inline code is created by surrounding the text with backticks:

`code`

If the code contains backticks, you must use matching pairs of backticks:

``code with ` backticks` ``

Automatic links

URLs and email addresses enclosed in angle brackets will be automatically converted to links:

<https://www.google.com>
<contact@example.com>

Raw inline HTML

Any text enclosed in <tag>...</tag> will be treated as raw HTML and passed through unchanged to the output. This means that Markdown syntax inside such tags will not be parsed.

This is some text, and here is <b>some HTML</b>.

This behavior can be disabled using the raw_html extension.

Inline Math

Inline math is delimited by $...$ or \(...\).

$y = mx + b$
\(y = mx + b\)

Delimited math is converted to LaTeX math when outputting to LaTeX, and to MathML for HTML output.

Display Math

Display math is delimited by $$...$$ or \[...\].

$$
y = mx + b
$$
\[
y = mx + b
\]

Display math is converted to LaTeX math when outputting to LaTeX, and to MathML for HTML output.

Extension : attributs_liens

Les attributs peuvent être définis sur les liens et les images :

Une image en ligne ![image](foo.jpg){#id .classe largeur=30 hauteur=20px}
et une image de référence ![image][ref] avec attributs.
[ref]: foo.jpg "titre optionnel" {#id .classe cle=val cle2="val 2"}

(Cette syntaxe est compatible avec PHP Markdown Extra lorsque seuls #id et .classe sont utilisés.)

Pour HTML et EPUB, tous les attributs HTML5 connus à l'exception de largeur et hauteur (mais incluant srcset et sizes) sont transmis tels quels. Les attributs inconnus sont transmis comme attributs personnalisés, avec data- préfixé. Les autres générateurs ignorent les attributs qui ne sont pas spécifiquement pris en charge par leur format de sortie.

Les attributs largeur et hauteur sur les images sont traités spécialement. Lorsqu'ils sont utilisés sans unité, l'unité est supposée être des pixels. Cependant, n'importe lequel des identifiants d'unité suivants peut être utilisé : px, cm, mm, in, inch et %. Il ne doit pas y avoir d'espaces entre le nombre et l'unité. Par exemple :

![](file.jpg){ largeur=50% }
•

La conversion entre pixels et mesures physiques est affectée par l'option --dpi (par défaut, 96 dpi sont supposés, sauf si l'image contient elle-même des informations dpi).
•
L'unité % est généralement relative à un espace disponible. Par exemple, l'exemple ci-dessus sera rendu comme suit.
•
HTML : <img href="file.jpg" style="width: 50%;" />
•
LaTeX : \includegraphics[width=0.5\textwidth,height=\textheight]{file.jpg} (Si vous utilisez un modèle personnalisé, vous devez configurer graphicx comme dans le modèle par défaut.)
•
ConTeXt : \externalfigure[file.jpg][width=0.5\textwidth]
•
Certains formats de sortie ont une notion de classe (ConTeXt) ou d'identifiant unique (LaTeX \caption), ou les deux (HTML).
•
Lorsqu'aucun attribut largeur ou hauteur n'est spécifié, le recours consiste à examiner la résolution de l'image et les métadonnées dpi intégrées dans le fichier image.

Divs et Spans

En utilisant les extensions native_divs et native_spans (voir ci-dessus), la syntaxe HTML peut être utilisée dans le markdown pour créer des éléments natifs Div et Span dans l'AST de pandoc (par opposition au HTML brut). Cependant, il existe également une syntaxe plus agréable :

Extension : fenced_divs

Permet une syntaxe spéciale de clôture pour les blocs Div natifs. Un Div commence par une clôture contenant au moins trois deux-points consécutifs plus des attributs. Les attributs peuvent éventuellement être suivis d'une autre chaîne de deux-points consécutifs.

Remarque : le parseur commonmark n'autorise pas les deux-points après les attributs.

La syntaxe des attributs est exactement celle des blocs de code clôturés (voir Extension : fenced_code_attributes). Comme pour les blocs de code clôturés, on peut utiliser soit des attributs entre accolades, soit un seul mot sans accolades, qui sera traité comme un nom de classe. Le Div se termine par une autre ligne contenant une chaîne d'au moins trois deux-points consécutifs. Le Div clôturé doit être séparé par des lignes vides des blocs précédents et suivants.

Exemple :

::::: {#special .sidebar}
Voici un paragraphe.
Et un autre.
:::::

Les divs clôturés peuvent être imbriqués. Les clôtures d'ouverture sont distinguées car elles *doivent* avoir des attributs :

::: Warning ::::::
Ceci est un avertissement.
::: Danger
Ceci est un avertissement dans un avertissement.
:::
::::::::::::::::::

Les clôtures sans attributs sont toujours des clôtures de fermeture. Contrairement aux blocs de code clôturés, le nombre de deux-points dans la clôture de fermeture n'a pas besoin de correspondre au nombre dans la clôture d'ouverture. Cependant, il peut être utile pour la clarté visuelle d'utiliser des clôtures de longueurs différentes pour distinguer les divs imbriqués de leurs parents.

Extension : footnotes

Le Markdown de Pandoc permet les notes de bas de page, en utilisant la syntaxe suivante :

Voici une référence de note de bas de page,[^1] et une autre.[^longnote]
[^1]: Voici la note de bas de page.
[^longnote]: Voici une note avec plusieurs blocs.
    Les paragraphes suivants sont indentés pour montrer qu'ils
appartiennent à la note de bas de page précédente.
        { quelque.code }
    L'ensemble du paragraphe peut être indenté, ou seulement la première
    ligne. De cette façon, les notes de bas de page multiparagraphes fonctionnent comme
    des éléments de liste multiparagraphes.
Ce paragraphe ne fera pas partie de la note, car il
n'est pas indenté.

Les identificateurs dans les références de notes de bas de page ne peuvent pas contenir d'espaces, de tabulations, de sauts de ligne, ni les caractères ^, [ ou ]. Ces identificateurs ne sont utilisés que pour faire correspondre la référence de note de bas de page avec la note elle-même ; dans la sortie, les notes de bas de page seront numérotées séquentiellement.

Les notes de bas de page elles-mêmes n'ont pas besoin d'être placées à la fin du document. Elles peuvent apparaître n'importe où sauf à l'intérieur d'autres éléments de bloc (listes, blocs de citation, tableaux, etc.). Chaque note de bas de page doit être séparée du contenu environnant (y compris les autres notes de bas de page) par des lignes vides.

Extension : notes_en_ligne

Les notes de bas de page en ligne sont également autorisées (bien que, contrairement aux notes régulières, elles ne puissent pas contenir plusieurs paragraphes). La syntaxe est la suivante :

Voici une note en ligne.^[Les notes en ligne sont plus faciles à écrire, car
vous n'avez pas à choisir un identificateur et à descendre pour taper la
note.]

Les notes en ligne et les notes régulières peuvent être mélangées librement.

Syntaxe de citation

Extension : citations

Pour citer un élément bibliographique avec un identifiant foo, utilisez la syntaxe @foo. Les citations normales doivent être incluses entre crochets, avec des points-virgules séparant les éléments distincts :

Blabla bla [@doe99; @smith2000; @smith2004].

La façon dont cela est rendu dépend du style de citation. Dans un style auteur-date, cela pourrait être rendu comme

Blabla bla (Doe 1999, Smith 2000, 2004).

Dans un style de note de bas de page, cela pourrait être rendu comme

Blabla bla.[^1]
[^1]:  John Doe, "Grenouilles", *Journal des Amphibiens* 44 (1999) ;
Susan Smith, "Mouches", *Journal des Insectes* (2000) ;
Susan Smith, "Abeilles", *Journal des Insectes* (2004).

Consultez la documentation utilisateur de CSL pour plus d'informations sur les styles CSL et comment ils affectent le rendu.

À moins qu'une clé de citation ne commence par une lettre, un chiffre ou _, et ne contienne que des caractères alphanumériques et des caractères de ponctuation internes uniques (:.#$%&-+?<>~/), elle doit être entourée d'accolades, qui ne sont pas considérées comme faisant partie de la clé. Dans @Foo_bar.baz., la clé est Foo_bar.baz car le point final n'est pas une ponctuation *interne*, il n'est donc pas inclus dans la clé. Dans @{Foo_bar.baz.}, la clé est Foo_bar.baz., y compris le point final. Dans @Foo_bar--baz, la clé est Foo_bar car les caractères de ponctuation internes répétés terminent la clé. Les accolades sont recommandées si vous utilisez des URL comme clés : [@{https://example.com/bib?name=foobar&date=2000}, p. 33].

Les éléments de citation peuvent éventuellement inclure un préfixe, un localisateur et un suffixe. Dans

Blabla bla [voir @doe99, pp. 33-35 et *passim* ; @smith04, chap. 1].

Syntaxe de citation de Pandoc

Une référence bibliographique peut être insérée dans le texte en utilisant la syntaxe de citation de pandoc, qui commence par @ ou -@, suivie de l'ID d'une entrée dans votre fichier de bibliographie.

@   smith04
-@  smith04

L'ID est généralement un nom d'auteur suivi de l'année (par exemple, smith04), mais cela dépend de la façon dont les références ont été générées. Le - au début supprime la mention de l'auteur dans la citation.

Pour inclure des informations de localisation, ajoutez-les après l'ID de la citation, séparées par une virgule.

[@smith04, pp. 1-5]
[-@smith04, chap. 1]

Pandoc utilise certaines heuristiques pour séparer le localisateur du reste du sujet. Il est sensible aux termes de localisation définis dans les fichiers de locale CSL. Les formes abrégées ou non abrégées sont acceptées. Dans la locale en-US, les termes de localisation peuvent être écrits sous forme singulière ou plurielle, comme book, bk./bks. ; chapter, chap./chaps. ; column, col./cols. ; figure, fig./figs. ; folio, fol./fols. ; number, no./nos. ; line, l./ll. ; note, n./nn. ; opus, op./opp. ; page, p./pp. ; paragraph, para./paras. ; part, pt./pts. ; section, sec./secs. ; sub verbo, s.v./s.vv. ; verse, v./vv. ; volume, vol./vols. ; ¶/¶¶ ; §/§§. Si aucun terme de localisation n'est utilisé, « page » est supposé.

Dans les cas complexes, vous pouvez forcer un élément à être traité comme un localisateur en l'entourant d'accolades ou empêcher l'analyse du suffixe comme localisateur en le précédant d'accolades :

[@smith{ii, A, D-Z}, with a suffix]
[@smith, {pp. iv, vi-xi, (xv)-(xvii)} with suffix here]
[@smith{}, 99 years later]

Un signe moins (-) avant le @ supprimera la mention de l'auteur dans la citation. Cela peut être utile lorsque l'auteur est déjà mentionné dans le texte :

Smith says blah [-@smith04].

Vous pouvez également écrire une citation avec l'auteur dans le texte, en omettant les crochets :

@smith04 says blah.
@smith04 [p. 33] says blah.

Cela entraînera le rendu du nom de l'auteur, suivi des détails bibliographiques. Utilisez cette forme lorsque vous voulez faire de la citation le sujet d'une phrase.

Lorsque vous utilisez un style de notes, il est généralement préférable de laisser citeproc créer les notes de bas de page à partir des citations plutôt que d'écrire une note explicite. Si vous écrivez une note explicite contenant une citation, notez que les citations normales seront placées entre parenthèses, tandis que les citations avec l'auteur dans le texte ne le seront pas. Pour cette raison, il est parfois préférable d'utiliser le style auteur-dans-le-texte à l'intérieur des notes lorsque vous utilisez un style de notes.

Extensions non par défaut

Les extensions Markdown suivantes ne sont pas activées par défaut dans pandoc, mais peuvent l'être en ajoutant +EXTENSION au nom du format, où EXTENSION est le nom de l'extension. Ainsi, par exemple, markdown+hard_line_breaks est du Markdown avec des sauts de ligne forcés.

Extension : rebase_relative_paths

Réécrit les chemins relatifs pour les liens et images Markdown, en fonction du chemin du fichier contenant le lien ou l'image. Pour chaque lien ou image, pandoc calculera le répertoire du fichier contenant, par rapport au répertoire de travail, et préfixera le chemin résultant au chemin du lien ou de l'image.

L'utilisation de cette extension est mieux comprise par un exemple. Supposons que vous ayez un sous-répertoire pour chaque chapitre d'un livre, chap1, chap2, chap3. Chacun contient un fichier text.md et un certain nombre d'images utilisées dans le chapitre. Vous voudriez que ![image](spider.jpg) dans chap1/text.md fasse référence à chap1/spider.jpg et que ![image](spider.jpg) dans chap2/text.md fasse référence à chap2/spider.jpg. Pour ce faire, utilisez

pandoc chap*/*.md -f markdown+rebase_relative_paths

Sans cette extension, vous devriez utiliser ![image](chap1/spider.jpg) dans chap1/text.md et ![image](chap2/spider.jpg) dans chap2/text.md. Les liens avec des chemins relatifs seront réécrits de la même manière que les images.

Les chemins absolus et les URL ne sont pas modifiés. Ni les chemins vides ni les chemins ne consistant entièrement en un fragment, par exemple, #foo.

Notez que les chemins relatifs dans les liens de référence et les images seront réécrits par rapport au fichier contenant la définition de la référence du lien, et non par rapport au fichier contenant le lien de référence ou l'image elle-même, si ceux-ci diffèrent.

Extension : mark

Pour mettre en évidence une section de texte, commencez-la et terminez-la avec ==. Ainsi, par exemple,

This ==is deleted text.==

Extension : attributes

Permet d'attacher des attributs à n'importe quel élément inline ou block lors de l'analyse de commonmark. La syntaxe des attributs est la même que celle utilisée dans header_attributes.

•
Les attributs qui surviennent immédiatement après un élément inline affectent cet élément. S'ils suivent un espace, alors ils appartiennent à l'espace. (Par conséquent, cette option englobe inline_code_attributes et link_attributes.)
•
Les attributs qui surviennent immédiatement avant un élément block, sur une ligne à part, affectent cet élément.
•
Des spécificateurs d'attributs consécutifs peuvent être utilisés, soit pour les blocks, soit pour les inlines. Leurs attributs seront combinés.
•
Les attributs qui surviennent à la fin du texte d'une en-tête Setext ou ATX (séparés par un espace blanc du texte) affectent l'élément d'en-tête. (Par conséquent, cette option englobe header_attributes.)
•
Les attributs qui surviennent après la clôture dans un bloc de code clôturé affectent l'élément de bloc de code. (Par conséquent, cette option englobe fenced_code_attributes.)
•
Les attributs qui surviennent à la fin d'une définition de lien de référence affectent les liens qui font référence à cette définition.

Notez que l'AST de pandoc ne permet pas actuellement d'attacher des attributs à des éléments arbitraires. Par conséquent, un conteneur Span ou Div sera ajouté si nécessaire.

Extension : old_dashes

Sélectionne le comportement de pandoc <= 1.8.2.1 pour l'analyse des tirets intelligents : - avant un chiffre est un tiret demi-cadratin, et -- est un tiret cadratin. Cette option n'a d'effet que si smart est activé. Elle est sélectionnée automatiquement pour l'entrée textile.

Extension : angle_brackets_escapable

Permet à < et > d'être échappés par une barre oblique inverse, comme ils peuvent l'être dans le GitHub flavored Markdown mais pas dans le Markdown original. Ceci est implicite par la valeur par défaut all_symbols_escapable de pandoc.

Extension : lists_without_preceding_blankline

Permet à une liste de survenir juste après un paragraphe, sans espace blanc intermédiaire.

Extension : four_space_rule

Sélectionne le comportement de pandoc <= 2.0 pour l'analyse des listes, de sorte que quatre espaces d'indentation soient nécessaires pour les paragraphes de continuation d'éléments de liste.

Extension : spaced_reference_links

Permet un espace entre les deux composants d'un lien de référence, par exemple,

[foo] [bar].

Extension : hard_line_breaks

Induit que tous les retours à la ligne dans un paragraphe soient interprétés comme des sauts de ligne forcés au lieu d'espaces.

Extension : ignore_line_breaks

Induit que les retours à la ligne dans un paragraphe soient ignorés, au lieu d'être traités comme des espaces ou des sauts de ligne forcés. Cette option est destinée à être utilisée avec les langues d'Asie de l'Est où les espaces ne sont pas utilisés entre les mots, mais le texte est divisé en lignes pour des raisons de lisibilité.

Extension : east_asian_line_breaks

Induit que les retours à la ligne dans un paragraphe soient ignorés, au lieu d'être traités comme des espaces ou des sauts de ligne forcés, lorsqu'ils surviennent entre deux caractères larges d'Asie de l'Est. C'est un meilleur choix que ignore_line_breaks pour les textes qui incluent un mélange de caractères larges d'Asie de l'Est et d'autres caractères.

Extension : emoji

Analyse les emojis textuels comme :smile: en émoticônes Unicode.

Extension : tex_math_gfm

Prend en charge deux formats spécifiques à GitHub pour les mathématiques. Mathématiques en ligne : $`e=mc^2`$.

Mathématiques d'affichage :

``` math

```

Extension : tex_math_single_backslash

Induit que tout ce qui se trouve entre \( et \) soit interprété comme des mathématiques TeX en ligne, et tout ce qui se trouve entre \[ et \] soit interprété

as afficher TeX math. Note: un inconvénient de cette extension est qu'elle empêche l'échappement de ( et [.

Extension : tex_math_double_backslash

Cause que tout ce qui se trouve entre \\( et \\) soit interprété comme des maths TeX en ligne, et que tout ce qui se trouve entre \\[ et \\] soit interprété comme des maths TeX affichées.

Extension : markdown_attribute

Par défaut, pandoc interprète le contenu des balises de niveau bloc comme du Markdown. Cette extension modifie le comportement de sorte que le Markdown ne soit analysé à l'intérieur des balises de niveau bloc que si les balises ont l'attribut markdown=1.

Extension : mmd_title_block

Active un bloc titre de style MultiMarkdown en haut du document, par exemple :

Titre :   Mon titre
Auteur : John Doe
Date :    1er septembre 2008
Commentaire : Ceci est un exemple de bloc titre mmd, avec
         un champ s'étendant sur plusieurs lignes.

Voir la documentation MultiMarkdown pour les détails. Si pandoc_title_block ou yaml_metadata_block est activé, il aura la priorité sur mmd_title_block.

Extension : abbreviations

Analyse les clés d'abréviation PHP Markdown Extra, comme

Notez que le modèle de document pandoc ne prend pas en charge les abréviations, donc si cette extension est activée, les clés d'abréviation sont simplement ignorées (contrairement à leur analyse comme paragraphes).

Extension : autolink_bare_uris

Transforme toutes les URIs absolues en liens, même lorsqu'elles ne sont pas entourées d'accolades <...>.

Extension : mmd_link_attributes

Analyse les attributs clé-valeur de style multimarkdown sur les références de liens et d'images. Cette extension ne doit pas être confondue avec l'extension link_attributes.

Ceci est une référence ![image][ref] avec des attributs multimarkdown.

Extension : mmd_header_identifiers

Analyse les identifiants d'en-tête de style multimarkdown (entre crochets, après l'en-tête mais avant les éventuels # finaux dans un en-tête ATX).

Extension : compact_definition_lists

Active la syntaxe des listes de définition de pandoc 1.12.x et antérieur. Cette syntaxe diffère de celle décrite ci-dessus sous Listes de définitions à plusieurs égards :

•
Aucune ligne vide n'est requise entre les éléments consécutifs de la liste de définition.
•
Pour obtenir une liste "serrée" ou "compacte", omettez l'espace entre les éléments consécutifs ; l'espace entre un terme et sa définition n'affecte rien.
•
Le retour à la ligne automatique des paragraphes n'est pas autorisé : l'ensemble de la définition doit être indenté de quatre espaces.

Extension : gutenberg

Utilise les conventions de Project Gutenberg pour la sortie plain : majuscules pour l'emphase forte, entouré d'underscores pour l'emphase normale, ajoute un espace vide supplémentaire autour des en-têtes.

Extension : sourcepos

Inclut les attributs de position source lors de l'analyse de commonmark. Pour les éléments qui acceptent des attributs, un attribut data-pos est ajouté ; d'autres éléments sont placés dans un élément Div ou Span enveloppant avec un attribut data-pos.

Extension : short_subsuperscripts

Analyse les sous-et superscripts de style multimarkdown, qui commencent par un caractère `~' ou `^', respectivement, et incluent la séquence alphanumérique qui suit. Par exemple :

CITATIONS

Lorsque l'option --citeproc est utilisée, pandoc peut générer automatiquement des citations et une bibliographie dans plusieurs styles. L'utilisation de base est

pandoc --citeproc monentree.txt

Pour utiliser cette fonctionnalité, vous aurez besoin de :

•
un document contenant des citations (voir Syntaxe des citations) ;
•
une source de données bibliographiques : soit un fichier de bibliographie externe, soit une liste de references dans les métadonnées YAML du document ;
•
facultativement, un style de citation CSL.

Spécification des données bibliographiques

Vous pouvez spécifier une bibliographie externe en utilisant le champ de métadonnées bibliography dans une section de métadonnées YAML ou l'argument de ligne de commande --bibliography. Si vous souhaitez utiliser plusieurs fichiers de bibliographie, vous pouvez fournir plusieurs arguments --bibliography ou définir le champ de métadonnées bibliography à un tableau YAML. Une bibliographie peut avoir l'un des formats suivants :

  Format     Extension de fichier
  ---------- ----------------
  BibLaTeX   .bib
  BibTeX     .bibtex
  CSL JSON   .json
  CSL YAML   .yaml
  RIS        .ris

Notez que .bib peut être utilisé avec des fichiers BibTeX et BibLaTeX ; utilisez l'extension .bibtex pour forcer l'interprétation comme BibTeX.

Dans les bases de données BibTeX et BibLaTeX, pandoc analyse le balisage LaTeX à l'intérieur des champs tels que title ; dans les bases de données CSL YAML, le Markdown pandoc ; et dans les bases de données CSL JSON, un balisage de type HTML :

<i>...</i>
italique
<b>...</b>
gras
<span style="font-variant:small-caps;">...</span> ou <sc>...</sc>
petites majuscules
<sub>...</sub>
indice
<sup>...</sup>
exposant
<span class="nocase">...</span>
empêcher une phrase d'être capitalisée en casse de titre

En alternative à la spécification d'un fichier de bibliographie à l'aide de --bibliography ou du champ de métadonnées YAML bibliography, vous pouvez inclure les données de citation directement dans le champ references des métadonnées YAML du document. Le champ doit contenir un tableau de références encodées en YAML, par exemple :

---
references:
- type: article-journal
  id: WatsonCrick1953
  author:
  - family: Watson
    given: J. D.
  - family: Crick
    given: F. H. C.
  issued:
    date-parts:
    - - 1953
      - 4
      - 25
  title: 'Structure moléculaire des acides nucléiques : une structure pour
    l''acide désoxyribonucléique'
  title-short: Structure moléculaire des acides nucléiques
  container-title: Nature
  volume: 171
  issue: 4356
  page: 737-738
  DOI: 10.1038/171737a0
  URL: https://www.nature.com/articles/171737a0
  language: en-GB
...

Si une bibliographie externe et des références inline (métadonnées YAML) sont fournies, les deux seront utilisées. En cas de conflits d'id, les références inline auront la priorité.

Notez que pandoc peut être utilisé pour produire une telle section de métadonnées YAML à partir d'une bibliographie BibTeX, BibLaTeX ou CSL JSON :

pandoc chem.bib -s -f biblatex -t markdown
pandoc chem.json -s -f csljson -t markdown

En effet, pandoc peut convertir entre n'importe lequel de ces formats de cita

tion formats :

pandoc chem.bib -s -f biblatex -t csljson
pandoc chem.yaml -s -f markdown -t biblatex

Lancer pandoc sur un fichier de bibliographie avec l'option --citeproc créera une bibliographie formatée dans le format de votre choix :

pandoc chem.bib -s --citeproc -o chem.html
pandoc chem.bib -s --citeproc -o chem.pdf

Capitalisation dans les titres

Si vous utilisez une bibliographie bibtex ou biblatex, observez les règles suivantes :

•
Les titres anglais doivent être en casse de titre (title case). Les titres non anglais doivent être en casse de phrase (sentence case), et le champ langid dans biblatex doit être défini sur la langue pertinente. (Les valeurs suivantes sont traitées comme anglaises : american, british, canadian, english, australian, newzealand, USenglish, ou UKenglish.)
•
Comme il est d'usage avec bibtex/biblatex, les noms propres doivent être protégés par des accolades afin qu'ils ne soient pas mis en minuscule dans les styles qui nécessitent la casse de phrase. Par exemple :
title = {My Dinner with {Andre}}
•
De plus, les mots qui doivent rester en minuscule (ou en camelCase) doivent être protégés :
title = {Spin Wave Dispersion on the {nm} Scale}

Bien que cela ne soit pas nécessaire dans bibtex/biblatex, c'est nécessaire avec citeproc, qui stocke les titres en interne en casse de phrase et les convertit en casse de titre dans les styles qui l'exigent. Ici, nous protégeons « nm » afin qu'il ne soit pas converti en « Nm » à ce stade.

Si vous utilisez une bibliographie CSL (JSON ou YAML), observez les règles suivantes :

•
Tous les titres doivent être en casse de phrase.
•
Utilisez le champ language pour les titres non anglais afin d'empêcher leur conversion en casse de titre dans les styles qui l'exigent. (La conversion ne se produit que si language commence par en ou est laissé vide.)
•
Protégez les mots qui ne doivent pas être convertis en casse de titre en utilisant cette syntaxe :
Spin wave dispersion on the <span class="nocase">nm</span> scale

Articles de conférence, publiés vs. non publiés

Pour un article de conférence formellement publié, utilisez le type d'entrée biblatex inproceedings (qui sera mappé sur CSL paper-conference).

Pour un manuscrit non publié, utilisez le type d'entrée biblatex unpublished sans champ eventtitle (ce type d'entrée sera mappé sur CSL manuscript).

Pour une présentation orale, un article de conférence non publié, ou une présentation par affiche, utilisez le type d'entrée biblatex unpublished avec un champ eventtitle (ce type d'entrée sera mappé sur CSL speech). Utilisez le champ biblatex type pour indiquer le type, par exemple « Paper » ou « Poster ». venue et eventdate peuvent également être utiles, bien que eventdate ne soit pas rendu par la plupart des styles CSL. Notez que venue concerne le lieu de l'événement, contrairement à location qui décrit l'emplacement de l'éditeur ; n'utilisez pas ce dernier pour un article de conférence non publié.

Spécification d'un style de citation

Les citations et les références peuvent être formatées à l'aide de n'importe quel style pris en charge par le Citation Style Language, listé dans le Zotero Style Repository. Ces fichiers sont spécifiés à l'aide de l'option --csl ou du champ de métadonnées csl (ou citation-style). Par défaut, pandoc utilisera le format auteur-date du Chicago Manual of Style. (Vous pouvez remplacer cette valeur par défaut en copiant un style CSL de votre choix sous le nom default.csl dans votre répertoire de données utilisateur.) Le projet CSL fournit des informations supplémentaires sur la recherche et la modification des styles.

L'option --citation-abbreviations (ou le champ de métadonnées citation-abbreviations) peut être utilisée pour spécifier un fichier JSON contenant des abréviations de journaux qui devraient être utilisées dans les bibliographies formatées lorsque form="short" est spécifié. Le format du fichier peut être illustré par un exemple :

{ "default": {
    "container-title": {
            "Lloyd's Law Reports": "Lloyd's Rep",
            "Estates Gazette": "EG",
            "Scots Law Times": "SLT"
    }
  }
}

Citations dans les styles de notes

Le traitement des citations par pandoc est conçu pour vous permettre de passer des styles auteur-date, numériques et de notes sans modifier la source markdown. Lorsque vous utilisez un style de notes, évitez d'insérer des notes de bas de page manuellement. Insérez plutôt les citations comme vous le feriez dans un style auteur-date — par exemple,

Blah blah [@foo, p. 33].

La note de bas de page sera créée automatiquement. Pandoc se chargera de supprimer l'espace et de déplacer la note avant ou après le point, en fonction du réglage de notes-after-punctuation, comme décrit ci-dessous dans Autres champs de métadonnées pertinents.

Dans certains cas, vous pourriez avoir besoin de placer une citation dans une note de bas de page normale. Les citations normales dans les notes de bas de page (telles que [@foo, p. 33]) seront rendues entre parenthèses. Les citations dans le texte (telles que @foo [p. 33]) seront rendues sans parenthèses. (Une virgule sera ajoutée si nécessaire.) Ainsi :

[^1]:  Some studies [@foo; @bar, p. 33] show that
frubulicious zoosnaps are quantical.  For a survey
of the literature, see @baz [chap. 1].

Emplacement de la bibliographie

Si le style requiert une liste des œuvres citées, elle sera placée dans une div avec l'id refs, si elle existe :

::: {#refs}
:::

Sinon, elle sera placée à la fin du document. La génération de la bibliographie peut être supprimée en définissant suppress-bibliography: true dans les métadonnées YAML.

Si vous souhaitez que la bibliographie ait un titre de section, vous pouvez définir reference-section-title dans les métadonnées, ou placer le titre au début de la div avec l'id refs (si vous l'utilisez) ou à la fin de votre document :

last paragraph...
# References

La bibliographie sera insérée après ce titre. Notez que la classe unnumbered sera ajoutée à ce titre, de sorte que la section ne sera pas numérotée.

Si vous voulez placer la bibliographie dans une variable de votre template, une façon de le faire est de placer la div avec l'id refs dans un champ de métadonnées, par exemple :

---
refs: |
   ::: {#refs}
   :::
...

Vous pouvez ensuite placer la variable $refs$ dans votre template où vous souhaitez que la bibliographie soit placée.

Inclusion d'éléments non cités dans la bibliographie

Si vous souhaitez inclure des éléments dans la bibliographie sans les citer réellement dans le corps du texte, vous pouvez définir un champ de métadonnées factice nocite et y placer les citations :

---
nocite: |
  @item1, @item2
...
@item3

Dans cet exemple, le document ne contiendra une citation que pour item3, mais la bibliographie contiendra des entrées pour item1, item2 et item3.

Il est possible de créer une bibliographie avec toutes les citations, qu'elles apparaissent ou non dans le document, en utilisant un joker :

---
nocite: |
  @*
...

Pour la sortie LaTeX, vous pouvez également utiliser natbib ou biblatex pour rendre la bibliographie. Pour ce faire, spécifiez les fichiers de bibliographie comme indiqué ci-dessus, et ajoutez l'argument --natbib ou --biblatex à l'invocation de pandoc. Gardez à l'esprit que les fichiers de bibliographie doivent être au format BibTeX (pour --natbib) ou BibLaTeX (pour --biblatex).

Autres champs de métadonnées pertinents

Quelques autres champs de métadonnées affectent le formatage de la bibliographie :

link-citations
Si vrai, les citations seront hyperliens vers les entrées de bibliographie correspondantes (uniquement pour les styles auteur-date et numériques). Par défaut, false.
link-bibliography
Si vrai, les DOI, PMCIDs, PMIDs et URL dans les bibliographies seront rendus comme des hyperliens. (Si une entrée contient un DOI, un PMCID, un PMID ou une URL, mais qu'aucun de ces champs n'est rendu par le style, alors le titre, ou dans t
he absence de titre, l'intégralité de l'entrée sera hyperliée.) Par défaut, c'est vrai.
lang
Le champ lang affectera la façon dont le style est localisé, par exemple dans la traduction des étiquettes, l'utilisation des guillemets et la façon dont les éléments sont triés. (Pour des raisons de compatibilité descendante, locale peut être utilisé à la place de lang, mais cette utilisation est obsolète.)

Une balise de langue BCP 47 est attendue : par exemple, en, de, en-US, fr-CA, ug-Cyrl. La syntaxe d'extension Unicode (après -u-) peut être utilisée pour spécifier plus précisément les options de collationnement (tri). Voici quelques exemples :

•
zh-u-co-pinyin – Chinois avec la collation Pinyin.
•
es-u-co-trad – Espagnol avec la collation traditionnelle (avec Ch trié après C).
•
fr-u-kb – Français avec un tri d'accents « à l'envers » (avec coté trié après côte).
•
en-US-u-kf-upper – Anglais avec les lettres majuscules triées avant les minuscules (par défaut, les minuscules sont avant les majuscules).
notes-after-punctuation
Si vrai (par défaut pour les styles de notes), pandoc placera les références de notes de bas de page ou les citations numériques en exposant après la ponctuation suivante. Par exemple, si la source contient blah blah [@jones99]., le résultat ressemblera à blah blah.[^1], la note étant déplacée après le point et l'espace étant réduit. Si faux, l'espace sera toujours réduit, mais la note de bas de page ne sera pas déplacée après la ponctuation. L'option peut également être utilisée dans les styles numériques qui utilisent des exposants pour les numéros de citation (mais pour ces styles, le comportement par défaut n'est pas de déplacer la citation).

DIAPORAMAS

Vous pouvez utiliser pandoc pour produire une présentation de diapositives HTML + JavaScript qui peut être visualisée via un navigateur Web. Il existe cinq façons de le faire, en utilisant S5, DZSlides, Slidy, Slideous ou reveal.js. Vous pouvez également produire un diaporama PDF en utilisant LaTeX beamer, ou des diaporamas au format Microsoft PowerPoint.

Voici la source Markdown d'un simple diaporama, habits.txt :

% Habits
% John Doe
% 22 mars 2005
# Le matin
## Se lever
- Éteindre l'alarme
- Sortir du lit
## Petit-déjeuner
- Manger des œufs
- Boire du café
# Le soir
## Dîner
- Manger des spaghettis
- Boire du vin
------------------
![photo de spaghettis](images/spaghetti.jpg)
## Se coucher
- Aller au lit
- Compter les moutons

Pour produire un diaporama HTML/JavaScript, tapez simplement

pandoc -t FORMAT -s habits.txt -o habits.html

où FORMAT est soit s5, slidy, slideous, dzslides, soit revealjs.

Pour Slidy, Slideous, reveal.js et S5, le fichier produit par pandoc avec l'option -s/--standalone intègre un lien vers des fichiers JavaScript et CSS, qui sont supposés être disponibles au chemin relatif s5/default (pour S5), slideous (pour Slideous), reveal.js (pour reveal.js), ou sur le site de Slidy à w3.org (pour Slidy). (Ces chemins peuvent être modifiés en définissant les variables slidy-url, slideous-url, revealjs-url, ou s5-url ; voir Variables pour les diapositives HTML, ci-dessus.) Pour DZSlides, le JavaScript et le CSS (relativement courts) sont inclus dans le fichier par défaut.

Avec tous les formats de diapositives HTML, l'option --self-contained peut être utilisée pour produire un fichier unique contenant toutes les données nécessaires à l'affichage du diaporama, y compris les scripts, feuilles de style, images et vidéos liés.

Pour produire un diaporama PDF en utilisant beamer, tapez

pandoc -t beamer habits.txt -o habits.pdf

Notez qu'un diaporama reveal.js peut également être converti en PDF en l'imprimant dans un fichier depuis le navigateur.

Pour produire un diaporama PowerPoint, tapez

pandoc habits.txt -o habits.pptx

Structuration du diaporama

Par défaut, le *niveau de diapositive* est le niveau de titre le plus élevé de la hiérarchie qui est suivi immédiatement par du contenu, et non par un autre titre, quelque part dans le document. Dans l'exemple ci-dessus, les titres de niveau 1 sont toujours suivis de titres de niveau 2, qui sont suivis de contenu, donc le niveau de diapositive est 2. Cette valeur par défaut peut être outrepassée en utilisant l'option --slide-level.

Le document est découpé en diapositives selon les règles suivantes :

•
Une ligne horizontale commence toujours une nouvelle diapositive.
•
Un titre au niveau de diapositive commence toujours une nouvelle diapositive.
•
Les titres *en dessous* du niveau de diapositive dans la hiérarchie créent des titres *à l'intérieur* d'une diapositive. (Dans beamer, un « bloc » sera créé. Si le titre a la classe example, un environnement exampleblock sera utilisé ; s'il a la classe alert, un alertblock sera utilisé ; sinon un block régulier sera utilisé.)
•
Les titres *au dessus* du niveau de diapositive dans la hiérarchie créent des « diapositives de titre », qui contiennent uniquement le titre de la section et aident à diviser le diaporama en sections. Le contenu non-diapositive sous ces titres sera inclus dans la diapositive de titre (pour les diaporamas HTML) ou dans une diapositive ultérieure portant le même titre (pour beamer).
•
Une page de titre est construite automatiquement à partir du bloc de titre du document, s'il est présent. (Dans le cas de beamer, cela peut être désactivé en commentant certaines lignes du modèle par défaut.)

Ces règles sont conçues pour prendre en charge de nombreux styles de diaporama différents. Si vous ne vous souciez pas de structurer vos diapositives en sections et sous-sections, vous pouvez simplement utiliser des titres de niveau 1 pour toutes les diapositives (auquel cas, le niveau 1 sera le niveau de diapositive) ou vous pouvez définir --slide-level=0.

Remarque : dans les diaporamas reveal.js, si le niveau de diapositive est 2, une disposition bidimensionnelle sera produite, avec les titres de niveau 1 construisant horizontalement et les titres de niveau 2 construisant verticalement. Il n'est pas recommandé d'utiliser un imbrication plus profonde de niveaux de section avec reveal.js à moins de définir --slide-level=0 (ce qui permet à reveal.js de produire une disposition unidimensionnelle et n'interprète les lignes horizontales que comme des limites de diapositives).

Choix de la disposition PowerPoint

Lors de la création de diapositives, le générateur pptx choisit parmi un certain nombre de dispositions prédéfinies, basées sur le contenu de la diapositive :

Diapositive de titre
Cette disposition est utilisée pour la diapositive initiale, qui est générée et remplie à partir des champs de métadonnées date, author et title, s'ils sont présents.
En-tête de section
Cette disposition est utilisée pour ce que pandoc appelle des « diapositives de titre », c'est-à-dire des diapositives qui commencent par un en-tête qui est au-dessus du niveau de diapositive dans la hiérarchie.
Deux contenus
Cette disposition est utilisée pour les diapositives à deux colonnes, c'est-à-dire les diapositives contenant une div avec la classe columns qui contient au moins deux divs avec la classe column.
Comparaison
Cette disposition est utilisée à la place de « Deux contenus » pour toute diapositive à deux colonnes dans laquelle au moins une colonne contient du texte suivi de non-texte (par exemple, une image ou un tableau).
Contenu avec légende
Cette disposition est utilisée pour toutes les diapositives qui ne sont pas à deux colonnes et qui contiennent du texte suivi de non-texte (par exemple, une image ou un tableau).
Vide
Cette disposition est utilisée pour toutes les diapositives qui ne contiennent que du contenu vide, par exemple une diapositive ne contenant que des notes de l'orateur, ou une diapositive ne contenant qu'une espace insécable.
Titre et contenu
Cette disposition est utilisée pour toutes les diapositives qui ne correspondent pas aux critères d'une autre disposition.

Ces dispositions sont choisies à partir du document de référence pptx par défaut inclus avec pandoc, sauf si un document de référence alternatif est spécifié à l'aide de --reference-doc.

Listes incrémentielles

Par défaut, ces générateurs produisent des listes qui s'affichent « en une seule fois ». Si vous souhaitez que vos listes s'affichent incrémentiellement (un élément à la fois), utilisez l'option -i. Si vous souhaitez qu'une liste particulière déroge à la valeur par défaut, placez-la dans un bloc div avec la classe incremental ou nonincremental. Ainsi, par exemple, en utilisant la syntaxe de div délimité, ce qui suit serait incrémentiel quel que soit le défaut du document :

::: incremental
- Manger des spaghettis
- Boire du vin
:::

ou

::: nonincremental
- Manger des spaghettis
- Boire du vin
:::

Bien que l'utilisation des divs incremental et nonincremental soit la méthode recommandée pour définir les listes incrémentielles au cas par cas, une méthode plus ancienne est également prise en charge : placer les listes dans un bloc quote

e sortira du document par défaut (c'est-à-dire qu'il s'affichera progressivement sans l'option -i et tout à la fois avec l'option -i) :

> - Manger des spaghettis
> - Boire du vin

Les deux méthodes permettent de mélanger listes progressives et non progressives dans un seul document.

Si vous souhaitez inclure une liste en bloc, vous pouvez contourner ce comportement en plaçant la liste à l'intérieur d'un "fenced div", de sorte qu'elle ne soit pas un enfant direct de la citation en bloc :

> ::: wrapper
> - un
> - liste dans une citation
> :::

Insertion de pauses

Vous pouvez ajouter des « pauses » dans une diapositive en incluant un paragraphe contenant trois points, séparés par des espaces :

# Diapositive avec une pause
contenu avant la pause
. . .
contenu après la pause

Note : cette fonctionnalité n'est pas encore implémentée pour la sortie PowerPoint.

Mise en forme des diapositives

Vous pouvez modifier le style des diapositives HTML en plaçant des fichiers CSS personnalisés dans $DATADIR/s5/default (pour S5), $DATADIR/slidy (pour Slidy) ou $DATADIR/slideous (pour Slideous), où $DATADIR est le répertoire de données utilisateur (voir --data-dir, ci-dessus). Les originaux se trouvent dans le répertoire de données système de pandoc (généralement $CABALDIR/pandoc-VERSION/s5/default). Pandoc y cherchera les fichiers qu'il ne trouve pas dans le répertoire de données utilisateur.

Pour dzslides, le CSS est inclus dans le fichier HTML lui-même et peut y être modifié.

Toutes les options de configuration de reveal.js peuvent être définies via des variables. Par exemple, les thèmes peuvent être utilisés en définissant la variable theme :

-V theme=moon

Vous pouvez également spécifier une feuille de style personnalisée à l'aide de l'option --css.

Pour mettre en forme les diapositives beamer, vous pouvez spécifier un theme, un colortheme, un fonttheme, un innertheme et un outertheme, en utilisant l'option -V :

pandoc -t beamer habits.txt -V theme:Warsaw -o habits.pdf

Notez que les attributs de titre se transformeront en attributs de diapositive (sur un <div> ou <section>) dans les formats de diapositives HTML, vous permettant de styliser des diapositives individuelles. Dans beamer, un certain nombre de classes et d'attributs de titre sont reconnus comme options de frame et seront transmis comme options à la frame : voir Attributs de frame dans beamer, ci-dessous.

Notes du présentateur

Les notes du présentateur sont prises en charge dans les sorties reveal.js, PowerPoint (pptx) et beamer. Vous pouvez ajouter des notes à votre document Markdown comme suit :

::: notes
Ceci est ma note.
- Elle peut contenir du Markdown
- comme cette liste
:::

Pour afficher la fenêtre de notes dans reveal.js, appuyez sur s pendant que vous regardez la présentation. Les notes du présentateur dans PowerPoint seront disponibles, comme d'habitude, dans les documents distribués et la vue du présentateur.

Les notes ne sont pas encore prises en charge pour d'autres formats de diapositives, mais les notes n'apparaîtront pas sur les diapositives elles-mêmes.

Colonnes

Pour placer du contenu dans des colonnes côte à côte, vous pouvez utiliser un conteneur div natif avec la classe columns, contenant deux conteneurs div ou plus avec la classe column et un attribut width :

:::::::::::::: {.columns}
::: {.column width="40%"}
contenu...
:::
::: {.column width="60%"}
contenu...
:::
::::::::::::::

Attributs de colonnes supplémentaires dans beamer

Les conteneurs div avec les classes columns et column peuvent éventuellement avoir un attribut align. La classe columns peut éventuellement avoir un attribut totalwidth ou une classe onlytextwidth.

:::::::::::::: {.columns align=center totalwidth=8em}
::: {.column width="40%"}
contenu...
:::
::: {.column width="60%" align=bottom}
contenu...
:::
::::::::::::::

Les attributs align sur columns et column peuvent être utilisés avec les valeurs top, top-baseline, center et bottom pour aligner verticalement les colonnes. Elle est par défaut à top dans columns.

L'attribut totalwidth limite la largeur des colonnes à la valeur donnée.

:::::::::::::: {.columns align=top .onlytextwidth}
::: {.column width="40%" align=center}
contenu...
:::
::: {.column width="60%"}
contenu...
:::
::::::::::::::

La classe onlytextwidth définit le totalwidth à \textwidth.

Voir la section 12.7 du guide de l'utilisateur Beamer pour plus de détails.

Attributs de frame dans beamer

Il est parfois nécessaire d'ajouter l'option LaTeX [fragile] à une frame dans beamer (par exemple, lors de l'utilisation de l'environnement minted). Cela peut être forcé en ajoutant la classe fragile au titre introduisant la diapositive :

# Diapositive fragile {.fragile}

Tous les autres attributs de frame décrits dans la section 8.1 du guide de l'utilisateur Beamer peuvent également être utilisés : allowdisplaybreaks, allowframebreaks, b, c, s, t, environment, label, plain, shrink, standout, noframenumbering, squeeze. allowframebreaks est particulièrement recommandé pour les bibliographies, car il permet de créer plusieurs diapositives si le contenu dépasse la frame :

# Références {.allowframebreaks}

De plus, l'attribut frameoptions peut être utilisé pour passer des options de frame arbitraires à une diapositive beamer :

# Titre {frameoptions="squeeze,shrink,customoption=foobar"}

Arrière-plan dans reveal.js, beamer, et pptx

Des images d'arrière-plan peuvent être ajoutées aux présentations reveal.js, beamer et pptx autonomes.

Sur toutes les diapositives (beamer, reveal.js, pptx)

Avec beamer et reveal.js, l'option de configuration background-image peut être utilisée soit dans le bloc de métadonnées YAML, soit comme variable en ligne de commande pour obtenir la même image sur chaque diapositive.

Notez que pour reveal.js, background-image sera utilisé comme parallaxBackgroundImage (voir ci-dessous).

Pour pptx, vous pouvez utiliser un document de référence dans lequel des images d'arrière-plan ont été définies sur les mises en page pertinentes.

parallaxBackgroundImage (reveal.js)

Pour reveal.js, il existe également l'option native de reveal.js parallaxBackgroundImage, qui produit un arrière-plan à défilement parallaxe. Vous devez également définir parallaxBackgroundSize, et vous pouvez éventuellement définir parallaxBackgroundHorizontal et parallaxBackgroundVertical pour configurer le comportement de défilement. Voir la documentation de reveal.js pour plus de détails sur la signification de ces options.

Dans le mode vue d'ensemble de reveal.js, le parallaxBackgroundImage s'affichera uniquement sur la première diapositive.

Sur les diapositives individuelles (reveal.js, pptx)

Pour définir une image pour une diapositive reveal.js ou pptx particulière, ajoutez {background-image="/chemin/vers/image"} au premier titre de niveau diapositive sur la diapositive (qui peut même être vide).

Comme les générateurs HTML transmettent les attributs inconnus, d'autres paramètres d'arrière-plan de reveal.js fonctionnent également sur les diapositives individuelles, notamment background-size, background-repeat, background-color, transition et transition-speed. (Le préfixe data- sera automatiquement ajouté.)

Note : data-background-image est également pris en charge dans pptx pour la cohérence avec reveal.js – si background-image n'est pas trouvé, data-background-image sera vérifié.

Sur la diapositive titre (reveal.js, pptx)

Pour ajouter une image d'arrière-plan à la diapositive titre générée automatiquement pour reveal.js, utilisez la variable title-slide-attributes dans le bloc de métadonnées YAML. Elle doit contenir une carte des noms et valeurs d'attributs. (Notez que le préfixe data- est requis ici, car il n'est pas ajouté automatiquement.)

Pour pptx, passez un document de référence avec l'image d'arrière-plan définie sur la mise en page « Diapositive de titre ».

Exemple (reveal.js)

---
title: Mon diaporama
parallaxBackgroundImage: /chemin/vers/mon/image_de_fond.png
title-slide-attributes:
    data-background-image: /chemin/vers/l_image_du_titre.png
    data-background-size: contain
---
## Diapositive Une
La diapositive 1 a image_de_fond.png comme arrière-plan.
## {background-image="/chemin/vers/image_speciale.jpg"}
La diapositive 2 a une image spéciale pour son arrière-plan, même si le titre n'a pas de contenu.

EPUBS

Métadonnées EPUB

Les métadonnées EPUB peuvent être spécifiées à l'aide de l'option --epub-metadata, mais si le document source est Markdown, il est préférable d'utiliser un bloc de métadonnées YAML. Voici un exemple :

---
title:
- type: main
  text: Mon livre
- type: subtitle
  text: Une enquête sur les métadonnées
creator:
- role: author
  text: John Smith
- role: editor
  text: Sarah Jones
identifier:
- scheme: DOI
  text: doi:10.234234.234/33
publisher: Ma maison d'édition
rights: © 2007 John Smith, CC BY-NC
ibooks:
  version: 1.3.4
...

Les champs suivants sont reconnus :

identifier
Soit une valeur de chaîne, soit un objet avec les champs text et scheme. Les valeurs valides pour scheme sont ISBN-10, GTIN-13, UPC, ISMN-10, DOI, LCCN, GTIN-14, ISBN-13, Numéro de dépôt légal, URN, OCLC, ISMN-13, ISBN-A, JP, OLCC.
title
Soit une valeur de chaîne, soit un objet avec les champs file-as et type, soit une liste de tels objets. Les valeurs valides pour type sont main, subtitle, short, collection, edition, extended.
creator
Soit une valeur de chaîne, soit un objet avec les champs role, file-as et text, soit une liste de tels objets. Les valeurs valides pour role sont les relations MARC, mais pandoc tentera de traduire les versions lisibles par l'homme (comme « auteur » et « éditeur ») en relations MARC appropriées.
contributor
Même format que creator.
date
Une valeur de chaîne au format AAAA-MM-JJ. (Seule l'année est nécessaire.) Pandoc tentera de convertir d'autres formats de date courants.
lang (ou héritage : language)
Une valeur de chaîne au format BCP 47. Pandoc utilisera par défaut la langue locale si rien n'est spécifié.
subject
Soit une valeur de chaîne, soit un objet avec les champs text, authority et term, soit une liste de tels objets. Les valeurs valides pour authority sont soit une valeur d'autorité réservée (actuellement AAT, BIC, BISAC, CLC, DDC, CLIL, EuroVoc, MEDTOP, LCSH, NDC, Thema, UDC, et WGS) soit un IRI absolu identifiant un schéma personnalisé. Les valeurs valides pour term sont définies par le schéma.
description
Une valeur de chaîne.
type
Une valeur de chaîne.
format
Une valeur de chaîne.
relation
Une valeur de chaîne.
coverage
Une valeur de chaîne.
rights
Une valeur de chaîne.
belongs-to-collection
Une valeur de chaîne. Identifie le nom d'une collection à laquelle la publication EPUB appartient.
group-position
Le champ group-position indique la position numérique à laquelle la publication EPUB appartient par rapport aux autres œuvres appartenant au même champ belongs-to-collection.
cover-image
Une valeur de chaîne (chemin vers l'image de couverture).
css (ou héritage : stylesheet)
Une valeur de chaîne (chemin vers la feuille de style CSS).
page-progression-direction
Soit ltr, soit rtl. Spécifie l'attribut page-progression-direction pour l'élément spine.
ibooks
Métadonnées spécifiques à iBooks, avec les champs suivants :
•
version : (chaîne de caractères)
•
specified-fonts : true|false (par défaut false)
•
ipad-orientation-lock : portrait-only|landscape-only
•
iphone-orientation-lock : portrait-only|landscape-only
•
binding : true|false (par défaut true)
•
scroll-axis : vertical|horizontal|default

L'attribut epub:type

Pour la sortie epub3, vous pouvez marquer le titre qui correspond à un chapitre EPUB en utilisant l'attribut epub:type. Par exemple, pour définir l'attribut sur la valeur prologue, utilisez ce markdown :

# Mon chapitre {epub:type=prologue}

<body epub:type="frontmatter">

  prologue                     frontmatter
  abstract                     frontmatter
  acknowledgments              frontmatter
  copyright-page               frontmatter
  dedication                   frontmatter
  credits                      frontmatter
  keywords                     frontmatter
  imprint                      frontmatter
  contributors                 frontmatter
  other-credits                frontmatter
  errata                       frontmatter
  revision-history             frontmatter
  titlepage                    frontmatter
  halftitlepage                frontmatter

Médias liés

Par défaut, pandoc téléchargera les médias référencés à partir de tout élément <img>, <audio>, <video> ou <source> présent dans l'EPUB généré, et l'inclura dans le conteneur EPUB, produisant un EPUB entièrement autonome. STYLING EPUB

Par défaut, pandoc inclura un style de base contenu dans son fichier de données epub.css. (Pour le voir, utilisez pandoc --print-default-data-file epub.css.) Pour utiliser un fichier CSS différent, utilisez simplement l'option de ligne de commande --css. Quelques styles en ligne sont également définis ; ils sont essentiels pour un formatage correct de la sortie HTML de pandoc.

La variable document-css peut être définie si le style plus direct des modèles HTML par défaut de pandoc est souhaité (et dans ce cas, les variables définies dans Variables pour HTML peuvent être utilisées pour affiner le style).

HTML FRAGMENTÉ

pandoc -t chunkedhtml produira une archive zip de fichiers HTML liés, un pour chaque section du document original. Les liens internes seront automatiquement ajustés pour pointer au bon endroit, les images liées sous le répertoire de travail seront incorporées, et des liens de navigation seront ajoutés. De plus, un fichier JSON sitemap.json sera inclus décrivant la structure hiérarchique des fichiers.

Si un fichier de sortie sans extension est spécifié, il sera interprété comme un répertoire et l'archive zip sera automatiquement décompressée dedans (sauf s'il existe déjà, auquel cas une erreur sera levée). Sinon, un fichier .zip sera produit.

Les liens de navigation peuvent être personnalisés en ajustant le modèle. Par défaut, une table des matières n'est incluse que sur la page principale. Pour l'inclure sur chaque page, définissez manuellement la variable toc.

MISE EN SURBRILLANCE

Pandoc mettra automatiquement en surbrillance la syntaxe dans les blocs de code clôturés marqués avec un nom de langage. La bibliothèque Haskell skylighting est utilisée pour la mise en surbrillance. Actuellement, la mise en surbrillance n'est prise en charge que pour les sorties HTML, EPUB, Docx, Ms et LaTeX/PDF. Pour voir une liste des noms de langages que pandoc reconnaîtra, tapez pandoc --list-highlight-languages.

La palette de couleurs peut être sélectionnée à l'aide de l'option --highlight-style. La palette de couleurs par défaut est pygments, qui imite la palette de couleurs par défaut utilisée par la bibliothèque Python pygments (bien que pygments ne soit pas réellement utilisé pour la mise en surbrillance). Pour voir une liste des styles de mise en surbrillance, tapez pandoc --list-highlight-styles.

Si vous n'êtes pas satisfait des styles prédéfinis, vous pouvez utiliser --print-highlight-style pour générer un fichier .theme JSON qui peut être modifié et utilisé comme argument pour --highlight-style. Pour obtenir une version JSON du style pygments, par exemple :

pandoc --print-highlight-style pygments > my.theme

Modifiez ensuite my.theme et utilisez-le comme ceci :

pandoc --highlight-style my.theme

Si vous n'êtes pas satisfait de la mise en surbrillance intégrée, ou si vous souhaitez mettre en surbrillance un langage non pris en charge, vous pouvez utiliser l'option --syntax-definition pour charger un fichier de définition de syntaxe XML de style KDE. Avant d'écrire le vôtre, consultez le référentiel des définitions de syntaxe de KDE.

Pour désactiver la mise en surbrillance, utilisez l'option --no-highlight.

STYLES PERSONNALISÉS

Des styles personnalisés peuvent être utilisés dans les formats docx et ICML.

Sortie

Par défaut, la sortie docx et ICML de pandoc applique un ensemble prédéfini de styles pour les blocs tels que les paragraphes et les citations, et utilise largement le formatage par défaut (italique, gras) pour les inlines. Cela fonctionnera dans la plupart des cas, en particulier avec un fichier reference.docx. Cependant, si vous avez besoin d'appliquer vos propres styles aux blocs, ou de faire correspondre un ensemble de styles préexistant, pandoc vous permet de définir des styles personnalisés pour les blocs et le texte en utilisant des divs et des spans, respectivement.

Si vous définissez un div ou un span avec l'attribut custom-style, pandoc appliquera votre style spécifié aux éléments contenus (à l'exception des éléments dont la fonction dépend d'un style, comme les titres, les blocs de code, les citations ou les liens). Ainsi, par exemple, en utilisant la syntaxe bracketed_spans,

LECTEURS ET ÉCRIVEURS PERSONNALISÉS

Pandoc peut être étendu avec des lecteurs et écrivains personnalisés écrits en Lua. (Pandoc inclut un interpréteur Lua, donc Lua n'a pas besoin d'être installé séparément.)

Pour utiliser un lecteur ou écrivain personnalisé, spécifiez simplement le chemin d'accès au script Lua à la place du format d'entrée ou de sortie. Par exemple :

pandoc -t data/sample.lua
pandoc -f my_custom_markup_language.lua -t latex -s

Si le script n'est pas trouvé par rapport au répertoire de travail, il sera recherché dans le sous-répertoire custom du répertoire de données utilisateur (voir --data-dir).

Un lecteur personnalisé est un script Lua qui définit une seule fonction, `Reader`, qui prend une chaîne de caractères en entrée et renvoie une AST Pandoc. Consultez la documentation des filtres Lua pour connaître les fonctions disponibles pour créer des éléments d'AST Pandoc. Pour l'analyse, la bibliothèque d'analyse lpg est disponible par défaut. Pour voir un exemple de lecteur personnalisé :

pandoc --print-default-data-file creole.lua

Si vous souhaitez que votre lecteur personnalisé ait accès aux options du lecteur (par exemple, le réglage de la tabulation), vous donnez à votre fonction `Reader` un second paramètre options.

Un écrivain personnalisé est un script Lua qui définit une fonction spécifiant comment rendre chaque élément d'une AST Pandoc. Consultez `djot-writer.lua` pour un exemple complet.

Notez que les écrivains personnalisés n'ont pas de modèle par défaut. Si vous souhaitez utiliser --standalone avec un écrivain personnalisé, vous devrez spécifier manuellement un modèle à l'aide de --template ou ajouter un nouveau modèle par défaut sous le nom `default.NOM_DE_L_ÉCRIVAIN_PERSONNALISÉ.lua` dans le sous-répertoire `templates` de votre répertoire de données utilisateur (voir Modèles).

BUILDS REPRODUCTIBLES

Certains formats de documents ciblés par pandoc (tels que EPUB, docx et ODT) incluent des horodatages de build dans le document généré. Cela signifie que les fichiers générés lors des builds successifs seront différents, même si la source ne change pas. Pour éviter cela, définissez la variable d'environnement SOURCE_DATE_EPOCH, et l'horodatage en sera pris au lieu de l'heure actuelle. SOURCE_DATE_EPOCH doit contenir un horodatage Unix entier (spécifiant le nombre de secondes depuis minuit UTC le 1er janvier 1970).

Certains formats de documents incluent également un identifiant unique. Pour EPUB, cela peut être défini explicitement en définissant le champ de métadonnées identifier (voir Métadonnées EPUB, ci-dessus).

PDFS ACCESSIBLES ET NORMES D'ARCHIVAGE PDF

Le PDF est un format flexible et son utilisation dans certains contextes requiert des conventions supplémentaires. Par exemple, les PDF ne sont pas accessibles par défaut ; ils définissent comment les caractères sont placés sur une page mais ne contiennent pas d'informations sémantiques sur le contenu. Cependant, il est possible de générer des PDF accessibles, qui utilisent le marquage pour ajouter des informations sémantiques au document.

Pandoc utilise LaTeX par défaut pour générer des PDF. La prise en charge du marquage dans LaTeX est en cours de développement et n'est pas facilement disponible, donc les PDF générés de cette manière seront toujours non marqués et non accessibles. Cela signifie que des moteurs alternatifs doivent être utilisés pour générer des PDF accessibles.

Les normes PDF PDF/A et PDF/UA définissent des restrictions supplémentaires visant à optimiser les PDF pour l'archivage et l'accessibilité. Le marquage est couramment utilisé en combinaison avec ces normes pour garantir les meilleurs résultats.

Notez cependant que la conformité aux normes dépend de nombreux facteurs, notamment de l'espace colorimétrique des images intégrées. Pandoc ne peut pas vérifier cela, et des programmes externes doivent être utilisés pour garantir que les PDF générés sont conformes.

ConTeXt

ConTeXt produit toujours des PDF marqués, mais la qualité dépend de l'entrée. Le balisage ConTeXt par défaut généré par pandoc est optimisé pour la lisibilité et la réutilisation, pas pour le marquage. Activez l'extension de format tagging pour forcer un balisage optimisé pour le marquage. Cela peut être combiné avec la variable pdfa pour générer des PDF conformes aux normes. Par exemple :

pandoc --to=context+tagging -V pdfa=3a

Une version récente de context doit être utilisée, car les versions plus anciennes contenaient un bug qui entraînait des métadonnées PDF invalides.

WeasyPrint

Le moteur basé sur HTML WeasyPrint inclut un support expérimental pour PDF/A et PDF/UA depuis la version 57. Des PDF marqués peuvent être créés avec :

pandoc --pdf-engine=weasyprint \
       --pdf-engine-opt=--pdf-variant=pdf/ua-1 ...

La fonctionnalité est expérimentale et la conformité aux normes ne doit pas être présumée.

Prince XML

Le convertisseur HTML-vers-PDF non libre prince a un support étendu pour diverses normes PDF ainsi que pour le marquage. Par exemple :

pandoc --pdf-engine=prince \
       --pdf-engine-opt=--tagged-pdf ...

Consultez la documentation de prince pour plus d'informations.

Traitement de texte

Les traitements de texte comme LibreOffice et MS Word peuvent également être utilisés pour générer des sorties PDF standardisées et marquées. Pandoc ne prend pas en charge les conversions directes via ces outils. Cependant, pandoc peut convertir un document en fichier docx ou odt, qui peut ensuite être ouvert et converti en PDF avec le traitement de texte respectif. Consultez la documentation de Word et LibreOffice.

EXÉCUTION DE PANDOC EN TANT QUE SERVEUR WEB

Si vous renommez (ou créez un lien symbolique vers) l'exécutable pandoc en pandoc-server, ou si vous appelez pandoc avec server comme premier argument, il démarrera un serveur web avec une API JSON. Ce serveur expose la plupart des fonctionnalités de conversion de pandoc. Pour une documentation complète, consultez la page de man pandoc-server.

Si vous renommez (ou créez un lien symbolique vers) l'exécutable pandoc en pandoc-server.cgi, il fonctionnera comme un programme CGI exposant la même API que pandoc-server.

pandoc-server est conçu pour être un maximum sécurisé ; il utilise le système de types de Haskell pour fournir des garanties solides qu'aucune E/S ne sera effectuée sur le serveur pendant les conversions pandoc.

EXÉCUTION DE PANDOC EN TANT QU'INTERPRÉTEUR LUA

Appeler l'exécutable pandoc sous le nom pandoc-lua ou avec lua comme premier argument le fera fonctionner comme un interpréteur Lua autonome. Le comportement est presque identique à celui de l'exécutable autonome lua, version 5.4. Cependant, il n'y a pas encore de REPL, et l'option -i n'a aucun effet. Pour une documentation complète, consultez la page de man pandoc-lua.

UNE NOTE SUR LA SÉCURITÉ

1.
Bien que pandoc lui-même ne créera ni ne modifiera aucun fichier autre que ceux que vous lui demandez explicitement de créer (à l'exception des fichiers temporaires utilisés pour produire des PDF), un filtre ou un écrivain personnalisé pourrait en principe faire n'importe quoi sur votre système de fichiers. Veuillez auditer très attentivement les filtres et les écrivains personnalisés avant de les utiliser.
2.
Plusieurs formats d'entrée (y compris HTML, Org et RST) prennent en charge les directives include qui permettent d'inclure le contenu d'un fichier dans la sortie. Un attaquant non fiable pourrait les utiliser pour visualiser le contenu des fichiers sur le système de fichiers. (L'utilisation de l'option --sandbox peut protéger contre cette menace.)
3.
Plusieurs formats de sortie (y compris RTF, FB2, HTML avec --self-contained, EPUB, Docx et ODT) intégreront des images encodées ou brutes dans le fichier de sortie. Un attaquant non fiable pourrait exploiter cela pour visualiser le contenu de fichiers non image sur le système de fichiers. (L'utilisation de l'option --sandbox peut protéger contre cette menace, mais empêchera également l'inclusion d'images dans ces formats.)
4.
Si votre application utilise pandoc comme bibliothèque Haskell (plutôt que de faire appel à l'exécutable), il est possible de l'utiliser dans un mode qui isole complètement pandoc de votre système de fichiers, en exécutant les opérations pandoc dans le monade PandocPure. Voir le document Utilisation de l'API pandoc pour plus de détails. (Cela correspond à l'utilisation de l'option --sandbox en ligne de commande.)
5.
Les analyseurs de Pandoc peuvent présenter des performances pathologiques sur certains cas limites. Il est sage de placer toute opération pandoc sous timeout, afin d'éviter les attaques par déni de service qui exploitent ces problèmes. Si vous utilisez l'exécutable pandoc, vous pouvez ajouter les options de ligne de commande +RTS -M512M -RTS (par exemple) pour limiter la taille du tas à 512 Mo. Notez que l'analyseur commonmark (y compris commonmark_x et gfm) est beaucoup moins vulnérable aux patholog
ical que le parseur markdown, il constitue donc un meilleur choix pour le traitement d'entrées non fiables.
6.
Le HTML généré par pandoc n'est pas garanti d'être sûr. Si raw_html est activé pour l'entrée Markdown, les utilisateurs peuvent injecter du HTML arbitraire. Même si raw_html est désactivé, les utilisateurs peuvent inclure du contenu dangereux dans les URL et les attributs. Pour être sûr, vous devriez exécuter tout HTML généré à partir d'entrées utilisateur non fiables via un nettoyeur HTML.
