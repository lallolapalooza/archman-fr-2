NOM

pacutils-sysroot - gestion d'un système invité monté

DESCRIPTION

Gestion des invités avec --root

Lorsqu'une installation basée sur libalpm devient tellement dégradée qu'elle ne peut plus être réparée par le gestionnaire de paquets lui-même, il faut la corriger en chargeant un environnement fonctionnel et en montant l'installation nécessitant une réparation en tant qu'invité. Généralement, cela se fait en définissant la racine de l'installation comme invité avec l'option --root. Libalpm utilise uniquement la racine de l'installation pour déterminer où installer et supprimer des fichiers lors des transactions de paquets. Elle est complètement indépendante de toutes les autres options de configuration. Cela rend l'utilisation de --root peu fiable pour gérer un invité monté.

Le premier problème est que lorsque la racine de l'installation est modifiée, la configuration du système hôte est toujours utilisée. Étant donné que la racine de l'installation est une option de configuration ("RootDir"), elle ne peut pas être utilisée pour charger un fichier de configuration alternatif. Même si --config est ajouté pour charger la configuration de l'invité, tous les chemins ("Include") seront toujours résolus par rapport à la racine de l'hôte. La seule façon d'utiliser réellement la configuration de l'invité sans utiliser "chroot" est d'utiliser --config et d'ajouter manuellement le chemin de montage à tous les chemins ("Include").

Maintenant, les fichiers de configuration de l'invité sont utilisés, mais tous les chemins configurés feront toujours référence à des chemins sous la racine de l'hôte, et non à ceux de l'invité. Si une racine d'installation est explicitement fournie, pacman et pacutils définiront des valeurs par défaut pour certains, mais pas tous, les chemins de configuration qui se trouveront sous celle-ci. Cela fonctionne généralement, car ces chemins sont rarement définis explicitement, donc les valeurs par défaut font généralement ce qu'il faut. S'ils ont été définis, cependant, les valeurs configurées seront utilisées sans modification. Afin d'opérer de manière fiable sur l'invité, tous les chemins de configuration doivent être définis par rapport à la racine de l'installation (à l'exception des chemins des fichiers de base de données et de journal qui seront par défaut des chemins à l'intérieur de la racine de l'installation s'ils ne sont pas définis).

Introduction du Sysroot

Cela représente une quantité de travail considérable juste pour pouvoir opérer sur un système monté. Afin de permettre une opération fiable sur un invité monté, pacman et pacutils ont ajouté le concept de "sysroot". Le sysroot est ce qui est communément prévu lors de l'utilisation de l'option --root ; le programme fonctionnera comme si le sysroot était effectivement la racine du système de fichiers. C'est similaire à l'utilisation de "chroot" pour entrer dans le système monté avant d'exécuter le programme, mais cela exécute toujours la copie de l'hôte. Il y a deux façons de faire cela : utiliser "chroot" dans le sysroot peu après le démarrage, avant de lire toute configuration, ou préfixer le sysroot à tous les chemins.

L'utilisation directe de "chroot" peut causer des problèmes avec les bibliothèques qui utilisent le chargement différé des fichiers de configuration ou des objets partagés. Notamment, glibc charge certains objets avec retard jusqu'à ce que leur fonctionnalité soit réellement utilisée. Cela peut provoquer une incohérence entre les composants chargés avant le "chroot" et ceux chargés après. Pour éviter ce problème, libalpm doit généralement être configuré pour utiliser des chemins sous le sysroot sans appeler réellement "chroot".

Pacutils fournit des versions conscientes du sysroot de ses fonctions d'analyse de configuration pour simplifier le processus. Notez que le sysroot est préfixé à tous les chemins lors de la résolution de la configuration. Les programmes utilisant les routines d'analyse de configuration du sysroot ne doivent PAS préfixer le sysroot aux chemins de configuration fournis sur la ligne de commande.

EXEMPLES

#include <alpm.h>
#include <getopt.h>
#include <pacutils.h>
enum {
       FLAG_CONFIG = 1,
       FLAG_SYSROOT,
};
int main(int argc, char *argv[]) {
 const char *config_file = "/etc/pacman.conf";
 const char *sysroot = NULL;
       alpm_handle_t *handle = NULL;
       pu_config_t *config = NULL;
       struct option long_opts[] = {
               { "config"        , required_argument , NULL    , FLAG_CONFIG        } ,
               { "sysroot"       , required_argument , NULL    , FLAG_SYSROOT       } ,
               { 0, 0, 0, 0 },
       };
       while((c = getopt_long(argc, argv, short_opts, long_opts, NULL)) != -1) {
               switch(c) {
                       case FLAG_CONFIG: config_file = optarg; break;
                       case FLAG_SYSROOT: sysroot = optarg; break;
                       case '?': return 1; /* getopt_long a déjà affiché un message d'erreur */
               }
       }
       if((config = pu_ui_config_load_sysroot(NULL, config_file, sysroot)) == NULL)
               { return 1; } /* load_sysroot a déjà affiché un message d'erreur */
       if(!(handle = pu_initialize_handle_from_config(config))) {
               fprintf(stderr, "erreur : impossible d'initialiser alpm.\n");
               return 1;
       }
       puts(alpm_option_get_root(handle));
       pu_config_free(config);
       alpm_release(handle);
       return 0;
}
