PATCH(1) Manuel des commandes générales PATCH(1)

NOM

patch - applique un fichier de diff à un original

SYNTAXE

patch [options] [fichier original [fichier de patch]]

mais généralement juste

patch -pnum <fichier de patch

DESCRIPTION

patch prend un fichier de patch fichier de patch contenant une liste de différences produite par le programme diff et applique ces différences à un ou plusieurs fichiers originaux, produisant des versions corrigées. Normalement, les versions corrigées remplacent les originaux. Des sauvegardes peuvent être créées ; voir l'option -b ou --backup. Les noms des fichiers à corriger sont généralement pris dans le fichier de patch, mais s'il n'y a qu'un seul fichier à corriger, il peut être spécifié sur la ligne de commande comme fichier original.

Au démarrage, patch tente de déterminer le type de la liste de différences, sauf si cela est outrepassé par une option -c (--context), -e (--ed), -n (--normal), ou -u (--unified). Les diffs de contexte (ancien style, nouveau style et unifiés) et les diffs normaux sont appliqués par le programme patch lui-même, tandis que les diffs ed sont simplement transmis à l'éditeur ed(1) via un pipe.

patch essaie de sauter toute partie inutile de début, d'appliquer le diff, puis de sauter toute partie inutile de fin. Ainsi, vous pouvez fournir à patch un message email contenant une liste de différences, et cela devrait fonctionner. Si l'ensemble du diff est indenté d'un montant constant, si les lignes se terminent par CRLF, ou si un diff est encapsulé une ou plusieurs fois en préfixant les lignes commençant par « - » avec « - » comme spécifié par la RFC 934 de l'Internet, cela est pris en compte. Après avoir supprimé l'indentation ou l'encapsulation, les lignes commençant par # sont ignorées, car elles sont considérées comme des commentaires.

Avec les diffs de contexte, et dans une moindre mesure avec les diffs normaux, patch peut détecter lorsque les numéros de ligne mentionnés dans le patch sont incorrects, et tente de trouver le bon endroit pour appliquer chaque bloc (hunk) du patch. Comme première estimation, il prend le numéro de ligne mentionné pour le bloc, plus ou moins le décalage utilisé pour appliquer le bloc précédent. Si ce n'est pas le bon endroit, patch scanne vers l'avant et vers l'arrière à la recherche d'un ensemble de lignes correspondant au contexte donné dans le bloc. D'abord, patch cherche un endroit où toutes les lignes du contexte correspondent. Si aucun endroit n'est trouvé, et qu'il s'agit d'un diff de contexte, et que le facteur de flou (fuzz) maximal est réglé à 1 ou plus, alors un autre scan est effectué en ignorant la première et la dernière ligne du contexte. Si cela échoue, et que le facteur de flou maximal est réglé à 2 ou plus, les deux premières et les deux dernières lignes du contexte sont ignorées, et un autre scan est effectué. (Le facteur de flou maximal par défaut est de 2.)

Les blocs avec moins de contexte préfixe que de contexte suffixe (après application du flou) doivent être appliqués au début du fichier si leur numéro de première ligne est 1. Les blocs avec plus de contexte préfixe que de contexte suffixe (après application du flou) doivent être appliqués à la fin du fichier.

Si patch ne parvient pas à trouver un endroit pour installer ce bloc du patch, il le place dans un fichier de rejet, dont le nom est normalement le nom du fichier de sortie plus le suffixe .rej, ou # si .rej générerait un nom de fichier trop long (si même l'ajout du caractère unique # rend le nom de fichier trop long, alors # remplace le dernier caractère du nom de fichier).

Le bloc rejeté sort au format diff unifié ou de contexte. Si l'entrée était un diff normal, beaucoup des contextes sont simplement nuls. Les numéros de ligne des blocs dans le fichier de rejet peuvent être différents de ceux du fichier de patch : ils reflètent l'emplacement approximatif où patch pense que les blocs échoués devraient se trouver dans le nouveau fichier plutôt que dans l'ancien.

À mesure que chaque bloc est complété, vous êtes informé si le bloc a échoué, et si oui, sur quelle ligne (dans le nouveau fichier) patch pensait que le bloc devait aller. Si le bloc est installé à une ligne différente de celle spécifiée dans le diff, le décalage vous est indiqué. Un unique grand décalage peut indiquer qu'un bloc a été installé au mauvais endroit. Vous êtes également informé si un facteur de flou a été utilisé pour faire correspondre, auquel cas vous devriez également être légèrement suspicieux. Si l'option --verbose est donnée, vous êtes également informé des blocs qui correspondent exactement.

Si aucun fichier original fichier original n'est spécifié sur la ligne de commande, patch essaie de déduire des parties inutiles de début le nom du fichier à éditer, en utilisant les règles suivantes.

Premièrement, patch prend une liste ordonnée de noms de fichiers candidats comme suit :

  • Si l'en-tête est celle d'un diff de contexte, patch prend les anciens et nouveaux noms de fichiers dans l'en-tête. Un nom est ignoré s'il n'a pas suffisamment de barres obliques pour satisfaire l'option -pnum ou --strip=num. Le nom /dev/null est également ignoré.
  • S'il y a une ligne Index: dans les parties inutiles de début et si soit les anciens et nouveaux noms sont absents, soit si patch est conforme à POSIX, patch prend le nom de la ligne Index:.
  • Dans le but des règles suivantes, les noms de fichiers candidats sont considérés dans l'ordre (ancien, nouveau, index), indépendamment de l'ordre dans lequel ils apparaissent dans l'en-tête.

Ensuite, patch sélectionne un nom de fichier dans la liste des candidats comme suit :

  • Si certains des fichiers nommés existent, patch sélectionne le premier nom s'il est conforme à POSIX, et le meilleur nom sinon.
  • Si patch n'ignore pas RCS, ClearCase, Perforce et SCCS (voir l'option -g num ou --get=num), et si aucun fichier nommé n'existe mais qu'un maître RCS, ClearCase, Perforce ou SCCS est trouvé, patch sélectionne le premier fichier nommé avec un maître RCS, ClearCase, Perforce ou SCCS.
  • Si aucun fichier nommé n'existe, aucun maître RCS, ClearCase, Perforce ou SCCS n'a été trouvé, certains noms sont donnés, patch n'est pas conforme à POSIX, et le patch semble créer un fichier, patch sélectionne le meilleur nom nécessitant la création du moins de répertoires.
  • Si aucun nom de fichier ne résulte des heuristiques ci-dessus, il vous est demandé le nom du fichier à corriger, et patch sélectionne ce nom.

Pour déterminer le meilleur d'une liste non vide de noms de fichiers, patch prend d'abord tous les noms avec le moins de composantes de nom de chemin ; parmi ceux-ci, il prend ensuite tous les noms avec le nom de base le plus court ; parmi ceux-ci, il prend ensuite tous les noms les plus courts ; enfin, il prend le premier nom restant.

De plus, si les parties inutiles de début contiennent une ligne Prereq:, patch prend le premier mot de la ligne des prérequis (normalement un numéro de version) et vérifie dans le fichier original si ce mot peut être trouvé. Sinon, patch demande confirmation avant de procéder.

Le résultat de tout cela est que vous devriez être en mesure d'exécuter quelque chose comme la commande shell suivante :

patch -d /usr/src/local/blurfl

et patcher un fichier dans le répertoire blurfl directement à partir d'un patch lu depuis l'entrée standard.

Si le fichier de patch contient plus d'un patch, patch essaie de les appliquer chacun comme s'ils provenaient de fichiers de patch distincts. Cela signifie, entre autres, qu'on suppose que le nom du fichier à corriger doit être déterminé pour chaque liste de différences, et que les parties inutiles avant chaque liste de différences contiennent des éléments intéressants tels que les noms de fichiers et le niveau de révision, comme mentionné précédemment.

OPTIONS

-b ou --backup
Crée des fichiers de sauvegarde. C'est-à-dire, lors de la correction d'un fichier, renomme ou copie l'original au lieu de le supprimer. Voir l'option -V ou --version-control pour les détails sur la manière dont les noms des fichiers de sauvegarde sont déterminés.
--backup-if-mismatch
Sauvegarde un fichier si le patch ne correspond pas exactement au fichier et si les sauvegardes ne sont pas autrement demandées. C'est le comportement par défaut à moins que patch ne soit conforme à POSIX.
--no-backup-if-mismatch
Ne sauvegarde pas un fichier si le patch ne correspond pas exactement au fichier et si les sauvegardes ne sont pas autrement demandées. C'est le comportement par défaut si patch est conforme à POSIX.
-B pref ou --prefix=pref
Utilise la méthode simple pour déterminer les noms des fichiers de sauvegarde (voir l'option -V méthode ou --version-control méthode), et ajoute pref au nom d'un fichier lors de la génération de son nom de fichier de sauvegarde.

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

Par exemple, avec -B /junk/ le nom de fichier de sauvegarde simple pour src/patch/util.c est /junk/src/patch/util.c.
--binary
Écrit tous les fichiers en mode binaire, à l'exception de la sortie standard et de /dev/tty. Lors de la lecture, désactive l'heuristique pour transformer les fins de ligne CRLF en fins de ligne LF. Cette option est nécessaire sur les systèmes POSIX lors de l'application de correctifs générés sur des systèmes non-POSIX à des fichiers non-POSIX. (Sur les systèmes POSIX, les lectures et écritures de fichiers ne transforment jamais les fins de ligne. Sur Windows, les lectures et écritures transforment les fins de ligne par défaut, et les correctifs doivent être générés par diff --binary lorsque les fins de ligne sont importantes.)
-c ou --context
Interprète le fichier de correctifs comme un diff de contexte ordinaire.
-d dir ou --directory=dir
Changez pour le répertoire dir immédiatement, avant de faire quoi que ce soit d'autre.
-D define ou --ifdef=define
Utilise la construction #ifdef ... #endif pour marquer les changements, avec define comme symbole différenciateur.
--dry-run
Imprime les résultats de l'application des correctifs sans modifier réellement de fichiers.
-e ou --ed
Interprète le fichier de correctifs comme un script ed.
-E ou --remove-empty-files
Supprime les fichiers de sortie qui sont vides après l'application des correctifs. Normalement, cette option est inutile, car patch peut examiner les horodatages sur l'en-tête pour déterminer si un fichier doit exister après la correction. Cependant, si l'entrée n'est pas un diff de contexte ou si patch se conforme à POSIX, patch ne supprime pas les fichiers corrigés vides sauf si cette option est donnée. Lorsque patch supprime un fichier, il tente également de supprimer les répertoires parents vides.
-f ou --force
Suppose que l'utilisateur sait exactement ce qu'il fait, et ne pose aucune question. Ignore les correctifs dont les en-têtes n'indiquent pas quel fichier doit être corrigé ; corrige les fichiers même s'ils ont la mauvaise version pour la ligne Prereq: dans le correctif ; et suppose que les correctifs ne sont pas inversés même s'ils en ont l'air. Cette option ne supprime pas les commentaires ; utilisez -s pour cela.
-F num ou --fuzz=num
Définit le facteur de "fuzz" maximal. Cette option ne s'applique qu'aux diffs qui ont du contexte, et amène patch à ignorer jusqu'à autant de lignes de contexte en cherchant des endroits pour installer un "hunk". Notez qu'un facteur de "fuzz" plus élevé augmente les chances d'un correctif défectueux. Le facteur de "fuzz" par défaut est de 2. Un facteur de "fuzz" supérieur ou égal au nombre de lignes de contexte dans le diff de contexte, normalement 3, ignore tout le contexte.
-g num ou --get=num
Cette option contrôle les actions de patch lorsqu'un fichier est sous contrôle RCS ou SCCS, et n'existe pas ou est en lecture seule et correspond à la version par défaut, ou lorsqu'un fichier est sous contrôle ClearCase ou Perforce et n'existe pas. Si num est positif, patch récupère (ou extrait) le fichier du système de gestion des révisions ; si zéro, patch ignore RCS, ClearCase, Perforce et SCCS et ne récupère pas le fichier ; et si négatif, patch demande à l'utilisateur s'il faut récupérer le fichier. La valeur par défaut de cette option est donnée par la valeur de la variable d'environnement PATCH_GET si elle est définie ; sinon, la valeur par défaut est zéro.
--help
Imprime un résumé des options et quitte.
-i patchfile ou --input=patchfile
Lit le correctif depuis patchfile. Si patchfile est -, lit depuis l'entrée standard, ce qui est le comportement par défaut.
-l ou --ignore-whitespace
Fait correspondre les motifs de manière lâche, au cas où des tabulations ou des espaces auraient été modifiés dans vos fichiers. Toute séquence d'un ou plusieurs blancs dans le fichier de correctifs correspond à toute séquence dans le fichier d'origine, et les séquences de blancs en fin de ligne sont ignorées. Les caractères normaux doivent toujours correspondre exactement. Chaque ligne du contexte doit toujours correspondre à une ligne du fichier d'origine.
--merge ou --merge=merge ou --merge=diff3
Fusionne un fichier de correctifs dans les fichiers d'origine, de manière similaire à diff3(1) ou merge(1). Si un conflit est trouvé, patch émet un avertissement et encadre le conflit avec les lignes <<<<<<< et >>>>>>>. Un conflit typique ressemble à ceci :
<<<<<<<
lignes du fichier d'origine
|||||||
lignes d'origine du correctif
=======
nouvelles lignes du correctif
>>>>>>>
L'argument optionnel de --merge détermine le format de sortie pour les conflits : le format diff3 affiche la section ||||||| avec les lignes d'origine du correctif ; dans le format merge, cette section est absente. Le format merge est le comportement par défaut.

Cette option implique --forward et ne prend pas en compte l'option --fuzz=num.

-n ou --normal
Interprète le fichier de correctifs comme un diff normal.
-N ou --forward
Lorsqu'un correctif ne s'applique pas, patch vérifie généralement si le correctif semble avoir déjà été appliqué en essayant d'appliquer de manière inverse le premier "hunk". L'option --forward empêche cela. Voir aussi -R.
-o outfile ou --output=outfile
Envoie la sortie à outfile au lieu de corriger les fichiers sur place. N'utilisez pas cette option si outfile est l'un des fichiers à corriger. Lorsque outfile est -, envoie la sortie à la sortie standard, et envoie tous les messages qui iraient normalement à la sortie standard à la sortie d'erreur.
-pnum ou --strip=num
Supprime le plus petit préfixe contenant num barres obliques initiales de chaque nom de fichier trouvé dans le fichier de correctifs. Une séquence d'une ou plusieurs barres obliques adjacentes est comptée comme une seule barre oblique. Cela contrôle la façon dont les noms de fichiers trouvés dans le fichier de correctifs sont traités, au cas où vous conserveriez vos fichiers dans un répertoire différent de celui de la personne qui a envoyé le correctif. Par exemple, en supposant que le nom de fichier dans le fichier de correctifs était
/u/howard/src/blurfl/blurfl.c

définir -p0 donne le nom de fichier complet non modifié, -p1 donne

u/howard/src/blurfl/blurfl.c

sans la barre oblique initiale, -p4 donne

blurfl/blurfl.c

et ne pas spécifier -p du tout donne simplement blurfl.c. Tout ce que vous obtenez est recherché soit dans le répertoire courant, soit dans le répertoire spécifié par l'option -d.

--posix
Se conformer plus strictement à la norme POSIX, comme suit.
  • Prenez le premier fichier existant de la liste (ancien, nouveau, index) lors de l'intuition des noms de fichiers à partir des en-têtes de diff.
  • Ne supprimez pas les fichiers qui sont vides après la correction.
  • Ne demandez pas s'il faut récupérer des fichiers depuis RCS, ClearCase, Perforce ou SCCS.
  • Exigez que toutes les options précèdent les fichiers dans la ligne de commande.
  • Ne sauvegardez pas les fichiers en cas de non-concordance.
--quoting-style=word
Utilisez le style word pour citer les noms de sortie. Le word doit être l'un des éléments suivants :
literal
Sortir les noms tels quels.
shell
Citer les noms pour le shell s'ils contiennent des métacaractères du shell ou s'ils provoqueraient une sortie ambiguë.
shell-always
Citer les noms pour le shell, même s'ils ne nécessiteraient normalement pas de citation.
c
Citer les noms comme pour une chaîne de caractères en langage C.
escape
Citer comme avec c sauf omettre les caractères de guillemets environnants.

Vous pouvez spécifier la valeur par défaut de l'option --quoting-style avec la variable d'environnement QUOTING_STYLE. Si cette variable d'environnement n'est pas définie, la valeur par défaut est shell.

-r rejectfile ou --reject-file=rejectfile
Place les rejets dans rejectfile au lieu du fichier .rej par défaut. Lorsque rejectfile est -, supprime les rejets.
-R ou --reverse
Suppose que ce correctif a été créé avec les fichiers anciens et nouveaux échangés. (Oui, j'ai bien peur que cela n'arrive de temps en temps, la nature humaine étant ce qu'elle est.) patch tente d'échanger chaque "hunk" avant de l'appliquer. Les rejets sortent dans le format échangé. L'option -R ne fonctionne pas avec les scripts de diff ed car il y a trop peu d'informations pour reconstruire l'opération inverse.

Si le premier "hunk" d'un correctif échoue, patch inverse le "hunk" pour voir s'il peut être appliqué de cette manière. Si c'est le cas, il vous est demandé si vous souhaitez que l'option -R soit définie. Si ce n'est pas le cas, le correctif continue d'être appliqué normalement. (Note : cette méthode ne peut pas détecter un correctif inversé s'il s'agit d'un diff normal et si la première commande est une ajout (c'est-à-dire qu'elle aurait dû être une suppression) car les ajouts réussissent toujours, en raison du fait qu'un contexte nul correspond n'importe où. Heureusement, la plupart des correctifs ajoutent ou modifient des lignes plutôt que de les supprimer, donc la plupart des diffs normaux inversés commencent par une suppression, qui échoue, déclenchant l'heuristique.)

--read-only=behavior
Se comporte comme demandé lors de la tentative de modification d'un fichier en lecture seule : ignore le problème potentiel, warn à son sujet (comportement par défaut), ou fail.
--reject-format=format
Produit des fichiers de rejet dans le format spécifié (soit context soit unified). Sans cette option, les morceaux rejetés sont produits au format de diff unifié si le patch d'entrée était de ce format, sinon au format de diff de contexte ordinaire.
-s ou --silent ou --quiet
Travaille silencieusement, sauf en cas d'erreur.
--follow-symlinks
Lors de la recherche de fichiers d'entrée, suit les liens symboliques. Remplace les liens symboliques, au lieu de modifier les fichiers vers lesquels les liens symboliques pointent. Les patchs de style Git sur les liens symboliques ne s'appliqueront plus. Cette option existe pour la compatibilité ascendante avec les versions précédentes de patch ; son utilisation est déconseillée.
-t ou --batch
Supprime les questions comme -f, mais fait des hypothèses différentes : saute les patchs dont les en-têtes ne contiennent pas de noms de fichiers (comme -f) ; saute les patchs pour lesquels le fichier a la mauvaise version pour la ligne Prereq: dans le patch ; et suppose que les patchs sont inversés s'ils semblent l'être.
-T ou --set-time
Définit les heures de modification et d'accès des fichiers patchés à partir des horodatages donnés dans les en-têtes de diff de contexte. Sauf indication contraire dans les horodatages, suppose que les en-têtes de diff de contexte utilisent l'heure locale.

L'utilisation de cette option avec des horodatages qui n'incluent pas de fuseaux horaires n'est pas recommandée, car les horodatages utilisant l'heure locale ne peuvent pas être facilement utilisés par des personnes dans d'autres fuseaux horaires, et parce que les horodatages locaux sont ambigus lorsque les horloges locales reculent lors des ajustements d'heure d'été.

Assurez-vous que les horodatages incluent les fuseaux horaires, ou générez des patchs avec UTC et utilisez plutôt l'option -Z ou --set-utc.
-u ou --unified
Interprète le fichier de patch comme un diff de contexte unifié.
-v ou --version
Affiche l'en-tête de révision et le niveau de patch de patch, puis quitte.
-V method ou --version-control=method
Utilise la méthode method pour déterminer les noms de fichiers de sauvegarde. La méthode peut également être spécifiée par la variable d'environnement PATCH_VERSION_CONTROL (ou, si celle-ci n'est pas définie, VERSION_CONTROL), qui est remplacée par cette option. La méthode n'affecte pas la création de fichiers de sauvegarde ; elle affecte uniquement les noms des fichiers de sauvegarde qui sont créés.

La valeur de method est similaire à la variable version-control de GNU Emacs ; patch reconnaît également des synonymes plus descriptifs. Les valeurs valides pour method sont (les abréviations uniques sont acceptées) :

existing ou nil
Crée des sauvegardes numérotées pour les fichiers qui en ont déjà, sinon des sauvegardes simples. C'est le comportement par défaut.
numbered ou t
Crée des sauvegardes numérotées. Le nom du fichier de sauvegarde numérotée pour F est F.~N~ où N est le numéro de version.
simple ou never
Crée des sauvegardes simples. Les options -B ou --prefix, -Y ou --basename-prefix, et -z ou --suffix spécifient le nom du fichier de sauvegarde simple. Si aucune de ces options n'est donnée, alors un suffixe de sauvegarde simple est utilisé ; il s'agit de la valeur de la variable d'environnement SIMPLE_BACKUP_SUFFIX si elle est définie, et .orig sinon.

Avec des sauvegardes numérotées ou simples, si le nom du fichier de sauvegarde est trop long, le suffixe de sauvegarde ~ est utilisé à la place ; si même l'ajout de ~ rend le nom trop long, alors ~ remplace le dernier caractère du nom du fichier.

--verbose
Affiche des informations supplémentaires sur le travail en cours.
-x num ou --debug=num
Définit des indicateurs de débogage internes qui n'intéressent que les correcteurs de patch.
-Y pref ou --basename-prefix=pref
Utilise la méthode simple pour déterminer les noms de fichiers de sauvegarde (voir l'option -V method ou --version-control method), et préfixe pref au nom de base d'un nom de fichier lors de la génération de son nom de fichier de sauvegarde. Par exemple, avec -Y .del/ le nom du fichier de sauvegarde simple pour src/patch/util.c est src/patch/.del/util.c.
-z suffix ou --suffix=suffix
Utilise la méthode simple pour déterminer les noms de fichiers de sauvegarde (voir l'option -V method ou --version-control method), et utilise suffix comme suffixe. Par exemple, avec -z - le nom du fichier de sauvegarde pour src/patch/util.c est src/patch/util.c-.
-Z ou --set-utc
Définit les heures de modification et d'accès des fichiers patchés à partir des horodatages donnés dans les en-têtes de diff de contexte. Sauf indication contraire dans les horodatages, suppose que les en-têtes de diff de contexte utilisent le Temps Universel Coordonné (UTC, souvent connu sous le nom de GMT). Voir également l'option -T ou --set-time.

Les options -Z ou --set-utc et -T ou --set-time s'abstiennent normalement de définir l'heure d'un fichier si l'heure d'origine du fichier ne correspond pas à l'heure donnée dans l'en-tête du patch, ou si son contenu ne correspond pas exactement au patch. Cependant, si l'option -f ou --force est donnée, l'heure du fichier est définie quoi qu'il arrive.

En raison des limitations du format de sortie de diff, ces options ne peuvent pas mettre à jour les heures des fichiers dont le contenu n'a pas changé. De plus, si vous utilisez ces options, vous devriez supprimer (par exemple, avec make clean) tous les fichiers qui dépendent des fichiers patchés, afin que les invocations ultérieures de make ne soient pas confuses par les heures des fichiers patchés.

ENVIRONNEMENT

PATCH_GET
Spécifie si patch récupère par défaut les fichiers manquants ou en lecture seule de RCS, ClearCase, Perforce ou SCCS ; voir l'option -g ou --get.
POSIXLY_CORRECT
Si elle est définie, patch se conforme plus strictement à la norme POSIX par défaut : voir l'option --posix.
QUOTING_STYLE
Valeur par défaut de l'option --quoting-style.
SIMPLE_BACKUP_SUFFIX
Extension à utiliser pour les noms de fichiers de sauvegarde simples au lieu de .orig.
TMPDIR, TMP, TEMP
Répertoire où placer les fichiers temporaires ; patch utilise la première variable d'environnement de cette liste qui est définie. Si aucune n'est définie, la valeur par défaut dépend du système ; elle est normalement /tmp sur les hôtes Unix.
VERSION_CONTROL ou PATCH_VERSION_CONTROL
Sélectionne le style de contrôle de version ; voir l'option -v ou --version-control.

FICHIERS

$TMPDIR/p*
fichiers temporaires
/dev/tty
terminal de contrôle ; utilisé pour obtenir les réponses aux questions posées à l'utilisateur

NOTES POUR LES EXPÉDITEURS DE PATCHS

Il y a plusieurs choses à garder à l'esprit si vous allez envoyer des patchs.

Créez votre patch de manière systématique. Lorsque vous utilisez un système de contrôle de version, cela devrait être facile ; par exemple, avec Git, vous pouvez utiliser git diff. Sinon, une bonne méthode est la commande diff -Naur old new où old et new identifient les anciens et nouveaux répertoires. Les noms old et new ne doivent pas contenir de barres obliques.

Si le patch doit communiquer les horodatages des fichiers ainsi que le contenu des fichiers, les en-têtes de ses commandes diff doivent avoir les dates et heures en Temps Universel en utilisant le format Unix traditionnel, afin que les destinataires du patch puissent utiliser l'option -Z ou --set-utc. Voici un exemple de commande pour générer de tels en-têtes, en utilisant la syntaxe du shell Bourne :

LC_ALL=C TZ=UTC0 diff -Naur myprog-2.7 myprog-2.8

Indiquez à vos destinataires comment appliquer le patch en leur disant dans quel répertoire se cd, et quelles options patch utiliser. La chaîne d'options -Np1 est recommandée. Testez votre procédure en prétendant être un destinataire et en appliquant votre patch à une copie des fichiers d'origine.

Vous pouvez épargner beaucoup de soucis aux gens en conservant un fichier patchlevel.h qui est patché pour incrémenter le niveau de patch comme premier diff dans le fichier de patch que vous envoyez. Si vous mettez une ligne Prereq: avec le patch, cela ne leur permettra pas d'appliquer les patchs dans le désordre sans un avertissement.

Vous pouvez créer un fichier en envoyant un diff qui compare /dev/null ou un fichier vide daté de l'Epoch (1970-01-01 00:00:00 UTC) au fichier que vous souhaitez créer. Cela ne fonctionne que si le fichier que vous souhaitez créer n'existe pas déjà dans le répertoire cible. Inversement, vous pouvez supprimer un fichier en envoyant un diff de contexte qui compare le fichier à supprimer avec un fichier vide daté de l'Epoch. Le fichier sera supprimé à moins que patch ne se conforme à POSIX et que l'option -E ou --remove-empty-files ne soit pas donnée. Un moyen facile de générer des patchs qui créent et suppriment des fichiers est d'utiliser l'option -N ou --new-file de GNU diff.

Si le destinataire est censé utiliser l'option -p

N, n'envoyez pas de sortie qui ressemble à ceci :

diff -Naur v2.0.29/prog/README prog/README
--- v2.0.29/prog/README Mon Mar 10 15:13:12 2024
+++ prog/README Mon Mar 17 14:58:22 2024

car les deux noms de fichiers ont un nombre différent de barres obliques et les différentes versions de patch interprètent les noms de fichiers différemment. Pour éviter toute confusion, envoyez plutôt une sortie qui ressemble à ceci :

diff -Naur v2.0.29/prog/README v2.0.30/prog/README
--- v2.0.29/prog/README Mon Mar 10 15:13:12 2024
+++ v2.0.30/prog/README Mon Mar 17 14:58:22 2024

Évitez d'envoyer des correctifs qui comparent les noms de fichiers de sauvegarde comme README.orig, car cela pourrait induire patch en erreur et le faire appliquer le correctif au fichier de sauvegarde au lieu du vrai fichier. Envoyez plutôt des correctifs qui comparent les mêmes noms de fichiers de base dans des répertoires différents, par exemple old/README et new/README.

Veillez à ne pas envoyer de correctifs inversés, car cela amène les gens à se demander s'ils ont déjà appliqué le correctif.

Essayez de ne pas faire modifier vos correctifs de fichiers dérivés (par exemple, le fichier configure lorsqu'il y a une ligne configure: configure.ac dans votre makefile), car le destinataire devrait pouvoir régénérer les fichiers dérivés de toute façon. Si vous devez envoyer des diffs de fichiers dérivés, générez les diffs en utilisant UTC, demandez aux destinataires d'appliquer le correctif avec l'option -Z ou --set-utc, et demandez-leur de supprimer tous les fichiers non corrigés qui dépendent des fichiers corrigés (par exemple avec make clean).

Bien que vous puissiez vous en sortir en mettant 582 listes de diff dans un seul fichier, il peut être plus sage de regrouper les correctifs apparentés dans des fichiers séparés au cas où quelque chose tournerait mal.

DIAGNOSTICS

Les diagnostics indiquent généralement que patch n'a pas pu analyser votre fichier de correctifs.

Si l'option --verbose est donnée, le message Hmm... indique qu'il y a du texte non traité dans le fichier de correctifs et que patch tente d'en déduire s'il y a un correctif dans ce texte et, si c'est le cas, de quel type de correctif il s'agit.

Le code de sortie de patch est 0 si tous les blocs sont appliqués avec succès, 1 si certains blocs ne peuvent pas être appliqués ou s'il y a eu des conflits de fusion, et 2 s'il y a des problèmes plus graves. Lors de l'application d'un ensemble de correctifs en boucle, il est conseillé de vérifier ce code de sortie afin de ne pas appliquer un correctif ultérieur à un fichier partiellement corrigé.

CAVEATS

Les diffs de contexte ne peuvent pas représenter de manière fiable la création ou la suppression de fichiers vides, de répertoires vides ou de fichiers spéciaux tels que les liens symboliques. Ils ne peuvent pas non plus représenter les modifications apportées aux métadonnées de fichiers comme la propriété, les permissions, ou si un fichier est un lien physique vers un autre. Si des modifications comme celles-ci sont également nécessaires, des instructions séparées (par exemple, un script shell) pour les réaliser devraient accompagner le correctif.

patch ne peut pas dire si les numéros de ligne sont incorrects dans un script ed, et ne peut détecter les numéros de ligne incorrects dans un diff normal que lorsqu'il trouve une modification ou une suppression. Un diff de contexte utilisant un facteur de tolérance de 3 peut avoir le même problème. Vous devriez probablement faire un diff de contexte dans ces cas pour voir si les modifications avaient du sens. Bien sûr, compiler sans erreurs est une très bonne indication que le correctif a fonctionné, mais pas toujours.

patch produit généralement des résultats corrects, même lorsqu'il doit faire beaucoup de suppositions. Cependant, les résultats ne sont garantis d'être corrects que lorsque le correctif est appliqué à exactement la même version du fichier que celle à partir de laquelle le correctif a été généré.

COMPATIBILITY ISSUES

La norme POSIX spécifie un comportement différent de celui de GNU patch.

  • Dans POSIX patch, lorsque -b n'est pas utilisé, les sauvegardes ne sont pas créées même en cas d'incompatibilité. Dans GNU patch, ce comportement est activé avec l'option --no-backup-if-mismatch, ou en se conformant à POSIX avec l'option --posix ou en définissant la variable d'environnement POSIXLY_CORRECT.
  • Lorsqu'il déduit le nom du fichier à corriger à partir de l'en-tête du correctif, patch utilise une méthode compliquée qui est éventuellement conforme à POSIX. La méthode est équivalente à POSIX si les noms de fichiers dans l'en-tête du diff de contexte et la ligne Index: sont tous identiques après suppression du préfixe. Votre correctif est normalement compatible si les noms de fichiers de chaque en-tête contiennent tous le même nombre de barres obliques.
  • Limitez-vous aux options suivantes lorsque vous envoyez des instructions destinées à être exécutées par quiconque utilise GNU patch ou un patch conforme à POSIX. Les espaces sont facultatifs dans la liste suivante. 
    -b
-c
-d dir
-D define
-e
-i patchfile
-l
-n
-N
-o outfile
-p num
-R
-r rejectfile
-u

BUGS

Veuillez signaler les bogues par e-mail à <bug-patch@gnu.org>.

Si du code a été dupliqué (par exemple avec #ifdef OLDCODE ... #else ... #endif), patch est incapable de corriger les deux versions et, si cela fonctionne, il corrigera probablement la mauvaise, et vous dira même qu'il a réussi.

Si vous appliquez un correctif que vous avez déjà appliqué, patch pense qu'il s'agit d'un correctif inversé et propose de le désappliquer. Cela pourrait être considéré comme une fonctionnalité.

Calculer comment fusionner un bloc est significativement plus difficile qu'utiliser l'algorithme flou standard. Des blocs plus grands, plus de contexte, un décalage plus important par rapport à l'emplacement d'origine et une moins bonne correspondance ralentissent tous l'algorithme.
