NOM

packet - interface de paquet au niveau du périphérique

SYNOPSIS

#include <sys/socket.h>
#include <linux/if_packet.h>
#include <net/ethernet.h> /* les protocoles L2 */
packet_socket = socket(AF_PACKET, int socket_type, int protocol);

DESCRIPTION

Les sockets de paquet sont utilisés pour recevoir ou envoyer des paquets bruts au niveau du pilote de périphérique (couche 2 OSI). Ils permettent à l'utilisateur d'implémenter des modules de protocole dans l'espace utilisateur au-dessus de la couche physique.

Le socket_type est soit SOCK_RAW pour les paquets bruts incluant l'en-tête de liaison, soit SOCK_DGRAM pour les paquets "cuits" sans l'en-tête de liaison. Les informations d'en-tête de liaison sont disponibles dans un format commun dans une structure sockaddr_ll. protocol est le numéro de protocole IEEE 802.3 en ordre d'octets réseau. Voir le fichier d'inclusion <linux/if_ether.h> pour une liste de protocoles autorisés. Lorsque le protocole est défini sur htons(ETH_P_ALL), tous les protocoles sont reçus. Tous les paquets entrants de ce type de protocole seront transmis au socket de paquet avant d'être transmis aux protocoles implémentés dans le noyau. Si protocol est défini sur zéro, aucun paquet n'est reçu. bind(2) peut éventuellement être appelé avec un sll_protocol non nul pour commencer à recevoir des paquets pour les protocoles spécifiés.

Pour créer un socket de paquet, un processus doit avoir la capacité CAP_NET_RAW dans l'espace de noms utilisateur qui régit son espace de noms réseau.

Les paquets SOCK_RAW sont transmis vers et depuis le pilote de périphérique sans aucune modification des données du paquet. Lors de la réception d'un paquet, l'adresse est toujours analysée et transmise dans une structure d'adresse sockaddr_ll standard. Lors de la transmission d'un paquet, le tampon fourni par l'utilisateur doit contenir l'en-tête de la couche physique. Ce paquet est ensuite mis en file d'attente sans modification vers le pilote réseau de l'interface définie par l'adresse de destination. Certains pilotes de périphérique ajoutent toujours d'autres en-têtes. SOCK_RAW est similaire mais non compatible avec l'obsolète AF_INET/SOCK_PACKET de Linux 2.0.

SOCK_DGRAM fonctionne à un niveau légèrement supérieur. L'en-tête physique est retiré avant que le paquet ne soit transmis à l'utilisateur. Les paquets envoyés via un socket de paquet SOCK_DGRAM reçoivent un en-tête de couche physique approprié basé sur les informations de l'adresse de destination sockaddr_ll avant d'être mis en file d'attente.

Par défaut, tous les paquets du type de protocole spécifié sont transmis à un socket de paquet. Pour obtenir des paquets d'une interface spécifique uniquement, utilisez bind(2) en spécifiant une adresse dans une struct sockaddr_ll pour lier le socket de paquet à une interface. Les champs utilisés pour la liaison sont sll_family (doit être AF_PACKET), sll_protocol et sll_ifindex.

L'opération connect(2) n'est pas prise en charge sur les sockets de paquet.

Lorsque le drapeau MSG_TRUNC est passé à recvmsg(2), recv(2), ou recvfrom(2), la taille réelle du paquet sur le réseau est toujours retournée, même si elle est plus longue que le tampon.

Types d'adresse

La structure sockaddr_ll est une adresse de couche physique indépendante du périphérique.


struct sockaddr_ll {
    unsigned short sll_family;   /* Toujours AF_PACKET */
    unsigned short sll_protocol; /* Protocole de couche physique */
    int            sll_ifindex;  /* Numéro d'interface */
    unsigned short sll_hatype;   /* Type matériel ARP */
    unsigned char  sll_pkttype;  /* Type de paquet */
    unsigned char  sll_halen;    /* Taille de l'adresse */
    unsigned char  sll_addr[8];  /* Adresse de couche physique */
};

Les champs de cette structure sont les suivants :

sll_protocol
est le type de protocole ethernet standard en ordre d'octets réseau tel que défini dans le fichier d'inclusion <linux/if_ether.h>. Il vaut par défaut le protocole du socket.
sll_ifindex
est l'index de l'interface (voir netdevice(7)) ; 0 correspond à n'importe quelle interface (autorisé uniquement pour la liaison). sll_hatype est un type ARP tel que défini dans le fichier d'inclusion <linux/if_arp.h>.
sll_pkttype
contient le type de paquet. Les types valides sont PACKET_HOST pour un paquet adressé à l'hôte local, PACKET_BROADCAST pour un paquet de diffusion physique, PACKET_MULTICAST pour un paquet envoyé à une adresse de multidiffusion physique, PACKET_OTHERHOST pour un paquet destiné à un autre hôte qui a été capturé par un pilote de périphérique en mode promiscueux, et PACKET_OUTGOING pour un paquet originaire de l'hôte local qui est renvoyé vers un socket de paquet. Ces types n'ont de sens que pour la réception.
sll_addr
sll_halen
contiennent l'adresse de couche physique (par exemple, IEEE 802.3) et sa taille. L'interprétation exacte dépend du périphérique.

Lorsque vous envoyez des paquets, il suffit de spécifier sll_family, sll_addr, sll_halen, sll_ifindex et sll_protocol. Les autres champs doivent être à 0. sll_hatype et sll_pkttype sont définis sur les paquets reçus pour votre information.

Options de socket

Les options de socket de paquet sont configurées en appelant setsockopt(2) avec le niveau SOL_PACKET.

PACKET_ADD_MEMBERSHIP
PACKET_DROP_MEMBERSHIP
Les sockets de paquet peuvent être utilisés pour configurer la multidiffusion de couche physique et le mode promiscueux. PACKET_ADD_MEMBERSHIP ajoute une liaison et PACKET_DROP_MEMBERSHIP la supprime. Ils attendent tous deux une structure packet_mreq comme argument :

struct packet_mreq {
    int            mr_ifindex;    /* index d'interface */
    unsigned short mr_type;       /* action */
    unsigned short mr_alen;       /* taille d'adresse */
    unsigned char  mr_address[8]; /* adresse de couche physique */
};

mr_ifindex contient l'index de l'interface dont le statut doit être modifié. Le champ mr_type spécifie l'action à effectuer. PACKET_MR_PROMISC active la réception de tous les paquets sur un support partagé (souvent connu sous le nom de « mode promiscueux »), PACKET_MR_MULTICAST lie le socket au groupe de multidiffusion de couche physique spécifié dans mr_address et mr_alen, et PACKET_MR_ALLMULTI configure le socket pour recevoir tous les paquets de multidiffusion arrivant sur l'interface.
En outre, les ioctls traditionnels SIOCSIFFLAGS, SIOCADDMULTI, SIOCDELMULTI peuvent être utilisés dans le même but.
PACKET_AUXDATA (depuis Linux 2.6.21)
Si cette option binaire est activée, le socket de paquet transmet une structure de métadonnées avec chaque paquet dans le champ de contrôle de recvmsg(2). La structure peut être lue avec cmsg(3). Elle est définie comme

struct tpacket_auxdata {
    __u32 tp_status;
    __u32 tp_len;      /* taille du paquet */
    __u32 tp_snaplen;  /* taille capturée */
    __u16 tp_mac;
    __u16 tp_net;
    __u16 tp_vlan_tci;
    __u16 tp_vlan_tpid; /* Depuis Linux 3.14 ; avant, il s'agissait
                           d'octets de remplissage inutilisés */
};

PACKET_FANOUT (depuis Linux 3.1)
Pour distribuer le traitement entre les threads, les sockets de paquet peuvent former un groupe de distribution (fanout). Dans ce mode, chaque paquet correspondant est mis en file d'attente sur un seul socket du groupe. Un socket rejoint un groupe de distribution en appelant setsockopt(2)

>ensemble de `setsockopt(2) avec le niveau SOL_PACKET et l'option PACKET_FANOUT. Chaque espace de noms réseau peut avoir jusqu'à 65536 groupes indépendants. Une socket sélectionne un groupe en encodant l'ID dans les 16 bits de poids fort de la valeur entière de l'option. La première socket de paquet à rejoindre un groupe le crée implicitement. Pour rejoindre avec succès un groupe existant, les sockets de paquet suivantes doivent avoir le même protocole, les mêmes réglages de périphérique, le même mode fanout et les mêmes drapeaux (voir ci-dessous). Les sockets de paquet ne peuvent quitter un groupe de fanout qu'en fermant la socket. Le groupe est supprimé lorsque la dernière socket est fermée.
Fanout prend en charge plusieurs algorithmes pour répartir le trafic entre les sockets, comme suit :
•
Le mode par défaut, PACKET_FANOUT_HASH, envoie les paquets du même flux vers la même socket pour maintenir l'ordre par flux. Pour chaque paquet, il choisit une socket en prenant le hachage du flux du paquet modulo le nombre de sockets dans le groupe, où un hachage de flux est un hachage sur l'adresse de la couche réseau et les champs optionnels du port de la couche transport.
•
Le mode d'équilibrage de charge PACKET_FANOUT_LB implémente un algorithme de round-robin.
•
PACKET_FANOUT_CPU sélectionne la socket en fonction du CPU sur lequel le paquet est arrivé.
•
PACKET_FANOUT_ROLLOVER traite toutes les données sur une seule socket, en passant à la suivante lorsqu'une devient engorgée.
•
PACKET_FANOUT_RND sélectionne la socket à l'aide d'un générateur de nombres pseudo-aléatoires.
•
PACKET_FANOUT_QM (disponible depuis Linux 3.14) sélectionne la socket en utilisant le `queue_mapping` enregistré du skb reçu.
Les modes fanout peuvent prendre des options supplémentaires. La fragmentation IP provoque l'obtention de paquets du même flux de différents hachages de flux. Le drapeau PACKET_FANOUT_FLAG_DEFRAG, s'il est défini, provoque la défragmentation des paquets avant l'application du fanout, afin de préserver l'ordre même dans ce cas. Le mode fanout et les options sont communiqués dans les 16 bits de poids faible de la valeur entière de l'option. Le drapeau PACKET_FANOUT_FLAG_ROLLOVER active le mécanisme de basculement comme stratégie de secours : si l'algorithme de fanout d'origine sélectionne une socket engorgée, le paquet bascule vers la suivante disponible.
PACKET_LOSS (avec PACKET_TX_RING)
Lorsqu'un paquet malformé est rencontré sur un anneau de transmission, le comportement par défaut est de réinitialiser son `tp_status` à TP_STATUS_WRONG_FORMAT et d'interrompre immédiatement la transmission. Le paquet malformé se bloque lui-même et les paquets ultérieurement mis en file d'attente ne peuvent pas être envoyés. L'erreur de format doit être corrigée, le `tp_status` associé réinitialisé à TP_STATUS_SEND_REQUEST, et le processus de transmission redémarré via send(2). Cependant, si PACKET_LOSS est défini, tout paquet malformé sera ignoré, son `tp_status` réinitialisé à TP_STATUS_AVAILABLE, et le processus de transmission continuera.
PACKET_RESERVE (avec PACKET_RX_RING)
Par défaut, un anneau de réception de paquets écrit les paquets immédiatement après la structure de métadonnées et le rembourrage d'alignement. Cette option entière réserve des en-têtes supplémentaires.
PACKET_RX_RING
Crée un tampon circulaire mappé en mémoire pour la réception asynchrone de paquets. La socket de paquet réserve une région contiguë d'espace d'adressage de l'application, la dispose en un tableau de slots de paquets et copie les paquets (jusqu'à `tp_snaplen`) dans les slots suivants. Chaque paquet est précédé d'une structure de métadonnées similaire à `tpacket_auxdata`. Les champs `protocol` encodent le décalage des données par rapport au début de l'en-tête des métadonnées. `tp_net` stocke le décalage vers la couche réseau. Si la socket de paquet est de type SOCK_DGRAM, alors `tp_mac` est le même. Si elle est de type SOCK_RAW, alors ce champ stocke le décalage vers la trame de la couche lien. La socket de paquet et l'application communiquent la tête et la queue de l'anneau via le champ `tp_status`. La socket de paquet possède tous les slots dont `tp_status` est égal à TP_STATUS_KERNEL. Après avoir rempli un slot, elle change le statut du slot pour transférer la propriété à l'application. Pendant le fonctionnement normal, la nouvelle valeur de `tp_status` a au moins le bit TP_STATUS_USER défini pour signaler qu'un paquet reçu a été stocké. Lorsque l'application a fini de traiter un paquet, elle transfère la propriété du slot à la socket en définissant `tp_status` égal à TP_STATUS_KERNEL.
Les sockets de paquet implémentent plusieurs variantes de l'anneau de paquets. Les détails d'implémentation sont décrits dans Documentation/networking/packet_mmap.rst dans l'arborescence source du noyau Linux.
PACKET_STATISTICS
Récupère les statistiques de la socket de paquet sous la forme d'une structure

struct tpacket_stats {
    unsigned int tp_packets;  /* Nombre total de paquets */
    unsigned int tp_drops;    /* Nombre de paquets abandonnés */
};

La réception des statistiques réinitialise les compteurs internes. La structure des statistiques diffère lors de l'utilisation d'un anneau de variante TPACKET_V3.
PACKET_TIMESTAMP (avec PACKET_RX_RING ; depuis Linux 2.6.36)
L'anneau de réception de paquets stocke toujours un horodatage dans l'en-tête des métadonnées. Par défaut, il s'agit d'un horodatage généré par le logiciel lorsque le paquet est copié dans l'anneau. Cette option entière sélectionne le type d'horodatage. Outre la valeur par défaut, elle prend en charge les deux formats matériels décrits dans Documentation/networking/timestamping.rst dans l'arborescence source du noyau Linux.
PACKET_TX_RING (depuis Linux 2.6.31)
Crée un tampon circulaire mappé en mémoire pour la transmission de paquets. Cette option est similaire à PACKET_RX_RING et prend les mêmes arguments. L'application écrit les paquets dans les slots avec `tp_status` égal à TP_STATUS_AVAILABLE et les planifie pour transmission en modifiant `tp_status` à TP_STATUS_SEND_REQUEST. Lorsque les paquets sont prêts à être transmis, l'application appelle send(2) ou une variante de celle-ci. Les champs `buf` et `len` de cet appel sont ignorés. Si une adresse est passée en utilisant sendto(2) ou sendmsg(2), cela remplace la valeur par défaut de la socket. En cas de transmission réussie, la socket réinitialise `tp_status` à TP_STATUS_AVAILABLE. Elle abandonne immédiatement la transmission en cas d'erreur, sauf si PACKET_LOSS est défini.
PACKET_VERSION (avec PACKET_RX_RING ; depuis Linux 2.6.27)
Par défaut, PACKET_RX_RING crée un anneau de réception de paquets de variante TPACKET_V1. Pour créer une autre variante, configurez la variante souhaitée en définissant cette option entière avant de créer l'anneau.
PACKET_QDISC_BYPASS (depuis Linux 3.14)
Par défaut, les paquets envoyés via les sockets de paquet passent par la couche qdisc (contrôle du trafic) du noyau, ce qui convient à la grande majorité des cas d'utilisation. Pour les appliances génératrices de trafic utilisant des sockets de paquet qui ont l'intention de submerger le réseau par force brute — par exemple, pour tester des périphériques sous charge de manière similaire à pktgen — cette couche peut être contournée en définissant cette option entière à 1. Un effet secondaire est que la mise en tampon des paquets dans la couche qdisc est évitée, ce qui entraînera plus de pertes lorsque les files d'attente de transmission du périphérique réseau sont occupées ; par conséquent, utilisez à vos propres risques.

Ioctls

SIOCGSTAMP peut être utilisé pour recevoir l'horodatage du dernier paquet reçu. L'argument est une variable de type struct timeval.

De plus, toutes les ioctls standard définies dans netdevice(7) et socket(7) sont valides sur les sockets de paquet.

Gestion des erreurs

Les sockets de paquet n'effectuent aucune gestion d'erreurs, à l'exception des erreurs survenant lors du passage du paquet au pilote du périphérique. Elles n'ont pas le concept d'erreur en attente.

ERREURS

EADDRNOTAVAIL
Adresse multicast inconnue passée.
EFAULT
L'utilisateur a passé une adresse mémoire invalide.
EINVAL
Argument invalide.
EMSGSIZE
Le paquet est plus grand que le MTU de l'interface.
ENETDOWN
L'interface n'est pas active.
ENOBUFS
Pas assez de mémoire pour allouer le paquet.
ENODEV
Nom de périphérique inconnu ou index d'interface spécifié dans l'adresse d'interface.
ENOENT
Aucun paquet reçu.
ENOTCONN
Aucune adresse d'interface passée.
ENXIO
L'adresse d'interface contenait un index d'interface invalide.
EPERM
L'utilisateur n'a pas les privilèges suffisants pour effectuer cette opération.

De plus, d'autres erreurs peuvent être générées par le pilote de bas niveau.

VERSIONS

AF_PACKET est une nouvelle fonctionnalité dans Linux 2.2. Les versions antérieures de Linux ne supportaient que SOCK_PACKET.

NOTES

Pour les programmes portables, il est suggéré d'utiliser AF_PACKET via pcap(3) ; bien que cela ne couvre qu'un sous-ensemble des fonctionnalités de AF_PACKET.

Les sockets de paquet SOCK_DGRAM ne tentent pas de créer ou d'analyser l'en-tête LLC IEEE 802.2 pour une trame IEEE 802.3. Lorsque ETH_P_802_3 est spécifié

édité comme protocole pour l'envoi du noyau crée la trame 802.3 et remplit le champ de taille ; l'utilisateur doit fournir l'en-tête LLC pour obtenir un paquet entièrement conforme. Les paquets 802.3 entrants ne sont pas multiplexés sur les champs de protocole DSAP/SSAP ; au lieu de cela, ils sont fournis à l'utilisateur en tant que protocole ETH_P_802_2 avec l'en-tête LLC préfixé. Il est donc impossible de se lier à ETH_P_802_3 ; liez-vous plutôt à ETH_P_802_2 et gérez vous-même le multiplexage de protocole. La valeur par défaut pour l'envoi est l'encapsulation Ethernet DIX standard avec le protocole rempli.

Les sockets de paquets ne sont pas soumis aux chaînes de pare-feu d'entrée ou de sortie.

Compatibilité

Sous Linux 2.0, la seule façon d'obtenir un socket de paquet était avec l'appel :


socket(AF_INET, SOCK_PACKET, protocol)

Ceci est toujours pris en charge, mais déconseillé et fortement déconseillé. La principale différence entre les deux méthodes est que SOCK_PACKET utilise l'ancienne structure struct sockaddr_pkt pour spécifier une interface, qui ne fournit pas d'indépendance de couche physique.


struct sockaddr_pkt {
    unsigned short spkt_family;
    unsigned char  spkt_device[14];
    unsigned short spkt_protocol;
};

spkt_family contient le type de périphérique, spkt_protocol est le type de protocole IEEE 802.3 tel que défini dans <sys/if_ether.h> et spkt_device est le nom de l'interface sous forme de chaîne terminée par un caractère nul, par exemple, eth0.

Cette structure est obsolète et ne doit pas être utilisée dans du nouveau code.

BOGUES

Gestion de l'en-tête LLC

La gestion LLC IEEE 802.2/803.3 pourrait être considérée comme un bogage.

Problèmes MSG_TRUNC

L'extension MSG_TRUNC de recvmsg(2) est un hack maladroit et devrait être remplacé par un message de contrôle. Il n'y a actuellement aucun moyen d'obtenir l'adresse de destination d'origine des paquets via SOCK_DGRAM.

Truncation du nom de périphérique spkt_device

Le champ spkt_device de sockaddr_pkt a une taille de 14 octets, ce qui est inférieur à la constante IFNAMSIZ définie dans <net/if.h> qui est de 16 octets et décrit la limite du système pour un nom d'interface réseau. Cela signifie que les noms d'interfaces réseau plus longs que 14 octets seront tronqués pour tenir dans spkt_device. Toutes ces tailles incluent le caractère nul de terminaison ('\0').

Les problèmes qui en découlent avec le code ancien se manifestent généralement avec des noms d'interfaces très longs utilisés par la fonctionnalité Noms d'interface réseau prévisibles activée par défaut dans de nombreuses distributions Linux modernes.

La solution privilégiée est de réécrire le code pour éviter SOCK_PACKET. Les solutions possibles pour l'utilisateur sont de désactiver les Noms d'interface réseau prévisibles ou de renommer l'interface avec un nom d'au plus 13 octets, par exemple en utilisant l'outil ip(8).

Problèmes de documentation

Les filtres de socket ne sont pas documentés.
