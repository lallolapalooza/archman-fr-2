EXEMPLES GNU PARALLEL

EXEMPLE: Fonctionnement similaire à xargs -n1. Ajout dargument

GNU parallel peut fonctionner de manière similaire à xargs -n1.

Pour compresser tous les fichiers html avec gzip, exécutez :

find . -name '*.html' | parallel gzip --best

Si les noms de fichiers peuvent contenir un saut de ligne, utilisez -0. Remplacez FOO BAR par FUBAR dans tous les fichiers de ce répertoire et de ses sous-répertoires :

find . -type f -print0 | \
  parallel -q0 perl -i -pe 's/FOO BAR/FUBAR/g'

Notez que -q est nécessaire à cause de l'espace dans 'FOO BAR'.

EXEMPLE: Lecture des arguments depuis la ligne de commande

GNU parallel peut prendre les arguments depuis la ligne de commande au lieu de stdin (entrée standard). Pour compresser tous les fichiers html du répertoire courant avec gzip, exécutez :

parallel gzip --best ::: *.html

Pour convertir *.wav en *.mp3 avec LAME en exécutant un processus par CPU, exécutez :

parallel lame {} -o {.}.mp3 ::: *.wav

EXEMPLE: Exécution de commandes complètes en parallèle

S'il n'y a pas de commande donnée à GNU parallel, alors les arguments sont traités comme une ligne de commande.

Pour exécuter gzip foo et bzip2 bar en parallèle, exécutez :

parallel ::: "gzip foo" "bzip2 bar"

ou :

(echo "gzip foo"; echo "bzip2 bar") | parallel

EXEMPLE: Insertion de multiples arguments

Lors du déplacement de nombreux fichiers comme ceci : mv *.log destdir, vous obtiendrez parfois l'erreur :

bash: /bin/mv: Argument list too long

car il y a trop de fichiers. Vous pouvez faire ceci à la place :

ls | grep -E '\.log$' | parallel mv {} destdir

Cela exécutera mv pour chaque fichier. Cela peut être fait plus rapidement si mv reçoit autant d'arguments que possible sur la ligne :

ls | grep -E '\.log$' | parallel -m mv {} destdir

Dans de nombreux shells, vous pouvez également utiliser printf :

printf '%s\0' *.log | parallel -0 -m mv {} destdir

EXEMPLE: Remplacement de contexte

Pour supprimer les fichiers pict0000.jpg .. pict9999.jpg, vous pourriez faire :

seq -w 0 9999 | parallel rm pict{}.jpg

Vous pourriez aussi faire :

seq -w 0 9999 | perl -pe 's/(.*)/pict$1.jpg/' | parallel -m rm

Le premier exécutera rm 10000 fois, tandis que le dernier n'exécutera rm que le nombre de fois nécessaire pour que la longueur de la ligne de commande reste suffisamment courte afin d'éviter Argument list too long (il s'exécute généralement 1 à 2 fois).

Vous pourriez aussi exécuter :

seq -w 0 9999 | parallel -X rm pict{}.jpg

Cela n'exécutera également rm que le nombre de fois nécessaire pour que la longueur de la ligne de commande reste suffisamment courte.

EXEMPLE: Tâches intensives en calcul et substitution

Si ImageMagick est installé, cela générera une miniature d'un fichier jpg :

convert -geometry 120 foo.jpg thumb_foo.jpg

Cela s'exécutera avec un nombre de tâches égal au nombre de CPU en parallèle pour tous les fichiers jpg d'un répertoire :

ls *.jpg | parallel convert -geometry 120 {} thumb_{}

Pour le faire récursivement, utilisez find :

find . -name '*.jpg' | \
  parallel convert -geometry 120 {} {}_thumb.jpg

Remarquez comment l'argument doit commencer par {} car {} inclura le chemin (par exemple, exécuter convert -geometry 120 ./foo/bar.jpg thumb_./foo/bar.jpg serait clairement incorrect). La commande générera des fichiers comme ./foo/bar.jpg_thumb.jpg.

Utilisez {.} pour éviter le .jpg supplémentaire dans le nom du fichier. Cette commande créera des fichiers comme ./foo/bar_thumb.jpg :

find . -name '*.jpg' | \
  parallel convert -geometry 120 {} {.}_thumb.jpg

EXEMPLE: Substitution et redirection

Cela générera une version non compressée des fichiers .gz à côté du fichier .gz :

parallel zcat {} ">"{.} ::: *.gz

La mise entre guillemets de > est nécessaire pour reporter la redirection. Une autre solution consiste à mettre la commande entière entre guillemets :

parallel "zcat {} >{.}" ::: *.gz

D'autres caractères spéciaux du shell (tels que * ; $ > < | >> <<) doivent également être mis entre guillemets, car ils pourraient sinon être interprétés par le shell et non transmis à GNU parallel.

EXEMPLE: Commandes composées

Une tâche peut être composée de plusieurs commandes. Cela affichera le nombre de fichiers dans chaque répertoire :

ls | parallel 'echo -n {}" "; ls {}|wc -l'

Pour placer la sortie dans un fichier nommé <nom>.dir :

ls | parallel '(echo -n {}" "; ls {}|wc -l) >{}.dir'

Même de petits scripts shell peuvent être exécutés par GNU parallel :

find . | parallel 'a={}; name=${a##*/};' \
  'upper=$(echo "$name" | tr "[:lower:]" "[:upper:]");'\
  'echo "$name - $upper"'
ls | parallel 'mv {} "$(echo {} | tr "[:upper:]" "[:lower:]")"'

Étant donné une liste d'URL, listez toutes les URL qui échouent au téléchargement. Affichez le numéro de ligne et l'URL.

cat urlfile | parallel "wget {} 2>/dev/null || grep -n {} urlfile"

Créez un répertoire miroir avec les mêmes noms de fichiers, sauf que tous les fichiers et liens symboliques sont des fichiers vides.

cp -rs /the/source/dir mirror_dir
find mirror_dir -type l | parallel -m rm {} '&&' touch {}

Trouvez dans une liste les fichiers qui n'existent pas

cat file_list | parallel 'if [ ! -e {} ] ; then echo {}; fi'

EXEMPLE: Commande composée avec chaîne de remplacement perl

Vous avez un tas de fichiers. Vous voulez qu'ils soient triés dans des répertoires. Le répertoire de chaque fichier doit être nommé par la première lettre du nom de fichier.

parallel 'mkdir -p {=s/(.).*/$1/=}; mv {} {=s/(.).*/$1/=}' ::: *

En pratique, vous n'utiliseriez probablement pas une chaîne de remplacement perl mais plutôt --match :

parallel --match '(.)' 'mkdir -p {1.1} && mv {} {1.1}' ::: *

EXEMPLE: Commande composée avec multiples sources d'entrées

Vous avez un répertoire avec des fichiers nommés selon des intervalles de 5 minutes sur 24 heures : 00:00, 00:05, 00:10 .. 23:55. Vous voulez trouver les fichiers manquants :

parallel [ -f {1}:{2} ] "||" echo {1}:{2} does not exist \
  ::: {00..23} ::: {00..55..5}

EXEMPLE : Champs de remplacement à partir d'un fichier CSV avec en-têtes

Ceci est un exemple avancé. Vous avez :

Date;Nom;Lieu
3/8/1978;"Beeblebrox; Zaphod";"Betelgeuse V"
10/12/1979;"Dent; Arthur";Earth
1/5/1981;Slartibartfast;Magrathea

Vous voulez :

Z. Beeblebrox: 1978-03-08/BET
A. Dent: 1979-10-12/EAR
Slartibartfast: 1981-01-05/MAG

Exécutez :

parallel --csv --colsep ';' --header : --match "(\d+)/(\d+)/(\d+)" \
  --match "^([^;]+)(; (.))?" --match "(...)"   \
  echo '{=Name.3 s/(.)/$1. /;=}'{Name.1}: \
    {Date.3}-{Date.1:%02d}-{Date.2:%02d}/'{=Location.1 $_=uc =}' \
  :::: people.csv

--csv analyse l'entrée comme un CSV avec --colsep ; comme séparateur - gérant correctement les chaînes entre guillemets. L'entrée est divisée en 3 colonnes. --header : rend les colonnes disponibles sous forme de {nomcolonne}. Chaque colonne a son --match correspondant afin que chaque champ puisse être accédé sous la forme {nomcolonne.#}. s/(.)/$1. / est une expression Perl qui ajoute ". " si le nom a une initiale. :%02d formate les chiffres simples en deux chiffres. uc met en majuscules l'argument.

EXEMPLE : Appel de fonctions Bash

Si la commande composée est plus longue qu'une ligne, elle devient difficile à lire. Dans Bash, vous pouvez utiliser des fonctions. N'oubliez pas d' exporter -f la fonction.

doit() {
  echo Faire pour $1
  sleep 2
  echo Fait avec $1
}
export -f doit
parallel doit ::: 1 2 3
doubleit() {
  echo Faire pour $1 $2
  sleep 2
  echo Fait avec $1 $2
}
export -f doubleit
parallel doubleit ::: 1 2 3 ::: a b

Pour faire cela sur des serveurs distants, vous devez transférer la fonction à l'aide de --env :

parallel --env doit -S serveur doit ::: 1 2 3
parallel --env doubleit -S serveur doubleit ::: 1 2 3 ::: a b

Si votre environnement (alias, variables et fonctions) est petit, vous pouvez copier l'environnement complet sans avoir à exporter -f quoi que ce soit. Voir env_parallel.

EXEMPLE : Testeur de fonctions

Pour tester un programme avec différents paramètres :

tester() {
  if (eval "$@") >&/dev/null; then
    perl -e 'printf "\033[30;102m[ OK ]\033[0m @ARGV\n"' "$@"
  else
    perl -e 'printf "\033[30;101m[FAIL]\033[0m @ARGV\n"' "$@"
  fi
}
export -f tester
parallel tester mon_programme ::: arg1 arg2
parallel tester exit ::: 1 0 2 0

Si mon_programme échoue, un FAIL rouge sera imprimé suivi de la commande échouée ; sinon, un OK vert sera imprimé suivi de la commande.

EXEMPLE : Identifier quelques tâches échouées

--bar fonctionne mieux si les tâches n'ont pas de sortie. Si les tâches échouées ont une sortie, vous pouvez les identifier comme suit :

job-with-few-failures() {
    # Forcer la reproductibilité
    RANDOM=$1
    # Ceci échoue 1% (328 sur 32768)
    if [ $RANDOM -lt 328 ] ; then
      echo Échoué $1
    fi
}
export -f job-with-few-failures
seq 1000 | parallel --bar --tag job-with-few-failures

EXEMPLE : Afficher en continu la dernière ligne de sortie

Il peut être utile de surveiller la sortie des tâches en cours.

Ceci affiche la ligne de sortie la plus récente jusqu'à ce qu'une tâche se termine. Après quoi, la sortie de la tâche est imprimée dans son intégralité :

EXEMPLE : Rotation des journaux

La rotation des journaux renomme un fichier journal avec une extension à nombre plus élevé : log.1 devient log.2, log.2 devient log.3, et ainsi de suite. Le journal le plus ancien est supprimé. Pour éviter d'écraser les fichiers, le processus commence à l'envers, du nombre élevé au nombre bas. Ceci conservera 10 anciennes versions du journal :

seq 9 -1 1 | parallel -j1 mv log.{} log.'{= $_++ =}'
mv log log.1

EXEMPLE : Supprimer l'extension de fichier lors du traitement des fichiers

Lors du traitement des fichiers, supprimer l'extension du fichier à l'aide de {.} est souvent utile.

Créez un répertoire pour chaque fichier zip et décompressez-le dans ce répertoire :

parallel 'mkdir {.}; cd {.}; unzip ../{}' ::: *.zip

Recompressez tous les fichiers .gz dans le répertoire courant à l'aide de bzip2 en exécutant 1 tâche par CPU en parallèle :

parallel "zcat {} | bzip2 >{.}.bz2 && rm {}" ::: *.gz

Convertissez tous les fichiers WAV en MP3 à l'aide de LAME :

find sounddir -type f -name '*.wav' | parallel lame {} -o {.}.mp3

Placez tous les fichiers convertis dans le même répertoire :

find sounddir -type f -name '*.wav' | \
  parallel lame {} -o mydir/{/.}.mp3

EXEMPLE : Remplacer des parties de noms de fichiers

Si vous traitez des lectures par paires, vous aurez des fichiers comme barcode1_R1.fq.gz, barcode1_R2.fq.gz, barcode2_R1.fq.gz, et barcode2_R2.fq.gz.

Vous voulez que barcodeN_R1 soit traité avec barcodeN_R2.

parallel --plus monprocessus {} {/_R1.fq.gz/_R2.fq.gz} ::: *_R1.fq.gz

Si le code-barres ne contient pas '_R1', vous pouvez faire ceci :

parallel --plus monprocessus {} {/_R1/_R2} ::: *_R1.fq.gz

Ou vous pouvez utiliser --match :

parallel --match '(.*)_R1(.*)' monprocessus {} {1.1}_R2{1.2} ::: *_R1.fq.gz

EXEMPLE : Supprimer des chaînes de l'argument

Si vous avez un répertoire avec des fichiers tar.gz et que vous souhaitez les extraire dans le répertoire correspondant (par exemple, foo.tar.gz sera extrait dans le répertoire foo), vous pouvez faire ceci :

parallel --plus 'mkdir {..}; tar -C {..} -xf {}' ::: *.tar.gz

Si vous souhaitez supprimer une terminaison différente, vous pouvez utiliser {%chaîne} :

parallel --plus echo {%_demo} ::: mycode_demo keep_demo_here

Vous pouvez également supprimer une chaîne de début avec {#chaîne}

parallel --plus echo {#demo_} ::: demo_mycode keep_demo_here

Pour supprimer une chaîne n'importe où, vous pouvez utiliser des expressions régulières avec {/regexp/remplacement} et laisser le remplacement vide :

parallel --plus echo {/demo_/} ::: demo_mycode remove_demo_here

Vous pouvez souvent aussi utiliser --match :

parallel --match '(.*)demo_(.*)' echo {1.1}{1.2} ::: demo_mycode remove_demo_here

EXEMPLE : Télécharger 24 images pour chacun des 30 derniers jours

Supposons qu'un site Web stocke des images comme ceci :

https://www.example.com/path/to/YYYYMMDD_##.jpg

où YYYYMMDD est la date et ## est le numéro 01-24. Ceci téléchargera les images des 30 derniers jours :

getit() {
  date=$(date -d "aujourd'hui -$1 jours" +%Y%m%d)
  num=$2
  echo wget https://www.example.com/path/to/${date}_${num}.jpg
}
export -f getit

parallel getit ::: $(seq 30) ::: $(seq -w 24)

$(date -d "aujourd'hui -$1 jours" +%Y%m%d) donnera les dates au format YYYYMMDD avec $1 jours soustraits.

EXEMPLE : Agrégation du contenu des fichiers

Ceci :

parallel --header : echo x{X}y{Y}z{Z} \> x{X}y{Y}z{Z} \
::: X {1..5} ::: Y {01..10} ::: Z {1..5}

générera les fichiers x1y01z1 .. x5y10z5. Si vous voulez agréger la sortie en groupant par x et z vous pouvez faire ceci :

EXEMPLE : Explorateur de répertoires parallèle en largeur d'abord

Pour traiter tous les fichiers dans les répertoires et sous-répertoires vous exécuteriez normalement :

find . -print | parallel do_stuff

Mais parfois vous voulez paralléliser chaque répertoire. Peut-être qu'un scan de répertoire est lent ?

Alors vous pouvez utiliser un scan de répertoire en largeur d'abord.

process() {
    process_file() {
        echo "Do your processing of file here $1"
    }
    queue="$1"
    shift
    if  [ -d "$1" ] ; then
        echo "queueing $1"
        find "$1" -mindepth 1 -maxdepth 1 > "$queue"
        if [ ! -s "$queue" ] ; then
            # Ignore les répertoires vides
            rm "$queue"
        fi
    else
        process_file "$1"
    fi
}
export -f process

# Listes de files d'attente
queue=$(mktemp)
queuenew=$(mktemp -d)

# Répertoire de départ
echo . > "$queue"

while [ -s "$queue" ] ; do
    # Exécute un tour pour chaque niveau de répertoire
    # (Largeur d'abord)
    cat "$queue" |
        parallel process "$queuenew"/{#} {}
    # Chaque tâche peut créer une liste dans "$queuenew"/job_no
    cat "$queuenew"/* > "$queue" 2>/dev/null
    rm -f "$queuenew"/*
done
rmdir "$queuenew"
rm "$queue"

Ce n'est pas un remplacement parfait (par exemple, --halt n'est pas respecté, et $? n'est pas défini correctement).

EXEMPLE : Robot d'exploration/miroir web parallèle en largeur d'abord

Le script ci-dessous va explorer et mettre en miroir une URL en parallèle. Il télécharge d'abord les pages qui sont à 1 clic de distance, puis à 2 clics, puis à 3 ; au lieu de la profondeur d'abord habituelle, où le premier lien de chaque page est récupéré en premier.

Exécutez comme ceci :

PARALLEL=-j100 ./parallel-crawl https://freenet.org/

Supprimez la partie wget si vous voulez seulement un robot d'exploration web.

Il fonctionne en récupérant une page d'une liste d'URL et en recherchant des liens dans cette page qui sont dans le même domaine de départ et qui n'ont pas encore été vus. Ces liens sont ajoutés à une nouvelle file d'attente. Quand toutes les pages de la liste sont traitées, la nouvelle file d'attente est déplacée vers la liste d'URL et le processus est recommencé jusqu'à ce qu'aucun lien non vu ne soit trouvé.

#!/bin/bash
# E.g. https://freenet.org/
url=$1
# Rester dans le répertoire de départ
baseurl=$(echo "$url" | perl -pe 's:#.*::; s:(//.*/)[^/]*:$1:')
urllist=$(mktemp -t urllist.XXXX)
newurllist=$(mktemp -t urllist.XXXX)
seen=$(mktemp -t seen.XXXX)

# Ajouter l'URL de départ à la liste
echo "$url" >"$urllist"
cp "$urllist" "$seen"

process_single_url() {
    # Trouver tous les liens dans l'URL
    lynx -listonly -image_links -dump "$1"
    # Supprimer cette ligne pour obtenir seulement le spider
    wget -qm -l1 -Q1 "$1"
    echo
    echo Spidered: "$1" >&2
}
export -f process_single_url

unique() {
    # Comme `sort -u` mais sans le tri
    perl -ne 's/#.*//; s/\s+\d+.\s(\S+)$/$1/ and do { $seen{$1}++ or print }'
}

while [ -s "$urllist" ] ; do
  cat "$urllist" |
    parallel process_single_url |
    unique |
    # Ignorer les liens hors de $baseurl
    grep -a -F "$baseurl" |
    # Ignorer les liens déjà vus
    grep -a -v -x -F -f "$seen" |
    tee -a "$seen" > "$newurllist"
  mv "$newurllist" "$urllist"
done

rm -f "$newurllist" "$urllist" "$seen"

EXEMPLE : Traiter les fichiers d'un fichier tar lors de la décompression

Si les fichiers à traiter se trouvent dans un fichier tar, décompresser un fichier et le traiter immédiatement peut être plus rapide que de d'abord tout décompresser.

tar xvf foo.tgz | perl -ne 'print $l;$l=$_;END{print $l}' | \

Le one-liner Perl est nécessaire pour s'assurer que le fichier est complet avant de le transmettre à GNU parallel.

EXEMPLE : Réécriture d'une boucle for et d'une boucle while-read

Les boucles for comme ceci :

(for x in `cat list` ; do
  do_something $x
done) | process_output

et les boucles while-read comme ceci :

cat list | (while read x ; do
  do_something $x
done) | process_output

peuvent être écrites comme ceci :

cat list | parallel do_something | process_output

Par exemple : Trouver quel nom d'hôte dans une liste a l'adresse IP 1.2.3 4 :

cat hosts.txt | parallel -P 100 host | grep 1.2.3.4

Si le traitement nécessite plus d'étapes, comme dans la boucle for :

(for x in `cat list` ; do
  no_extension=${x%.*};
  do_step1 $x scale $no_extension.jpg
  do_step2 <$x $no_extension
done) | process_output

et les boucles while comme ceci :

cat list | (while read x ; do
  no_extension=${x%.*};
  do_step1 $x scale $no_extension.jpg
  do_step2 <$x $no_extension
done) | process_output

peuvent être écrites comme ceci :

cat list | parallel "do_step1 {} scale {.}.jpg ; do_step2 <{} {.}" |\
  process_output

Si le corps de la boucle est plus grand, il améliore la lisibilité d'utiliser une fonction :

(for x in `cat list` ; do
  do_something $x
  [... 100 lines that do something with $x ...]
done) | process_output
cat list | (while read x ; do
  do_something $x
  [... 100 lines that do something with $x ...]
done) | process_output

peuvent toutes deux être réécrites comme :

doit() {
  x=$1
  do_something $x
  [... 100 lines that do something with $x ...]
}
export -f doit
cat list | parallel doit

EXEMPLE : Réécriture de boucles for imbriquées

Les boucles for imbriquées comme ceci :

(for x in `cat xlist` ; do
  for y in `cat ylist` ; do
    do_something $x $y
  done
done) | process_output

peuvent être écrites comme ceci :

parallel do_something {1} {2} :::: xlist ylist | process_output

Les boucles for imbriquées comme ceci :

(for colour in red green blue ; do
  for size in S M L XL XXL ; do
    echo $colour $size
  done
done) | sort

peuvent être écrites comme ceci :

parallel echo {1} {2} ::: red green blue ::: S M L XL XXL | sort

diff est bon pour trouver les différences dans les fichiers texte. diff | wc -l donne une indication de la taille de la différence. Pour trouver les différences entre tous les fichiers dans le répertoire courant faites :

EXEMPLE: Toutes les combinaisons dans une liste

GNU parallel crée toutes les combinaisons lorsqu'il reçoit deux listes.

Pour créer toutes les combinaisons dans une seule liste avec des valeurs uniques, vous répétez la liste et utilisez la chaîne de remplacement {choose_k} :

parallel --plus echo {choose_k} ::: A B C D ::: A B C D
parallel --plus echo 2{2choose_k} 1{1choose_k} ::: A B C D ::: A B C D

{choose_k} fonctionne pour n'importe quel nombre de sources d'entrée :

parallel --plus echo {choose_k} ::: A B C D ::: A B C D ::: A B C D

Alors que {choose_k} ne tient pas compte de l'ordre, {uniq} en tient compte. Il ignore simplement les travaux où les valeurs des différentes sources d'entrée sont identiques :

parallel --plus echo {uniq} ::: A B C  ::: A B C  ::: A B C
parallel --plus echo {1uniq}+{2uniq}+{3uniq} \
  ::: A B C  ::: A B C  ::: A B C

Le comportement de {choose_k} est indéfini si les valeurs d'entrée de chaque source sont différentes.

et que vous souhaitiez exécuter des combinaisons comme :

EXEMPLE: Accélérer les travaux rapides

Le démarrage d'un travail sur la machine locale prend environ 3 à 10 ms. Cela peut représenter une surcharge importante si le travail prend très peu de ms à s'exécuter. Souvent, vous pouvez regrouper de petits travaux ensemble en utilisant -X, ce qui rendra la surcharge moins significative. Comparez la vitesse des éléments suivants :

seq -w 0 9999 | parallel touch pict{}.jpg
seq -w 0 9999 | parallel -X touch pict{}.jpg

Si votre programme ne peut pas accepter plusieurs arguments, vous pouvez utiliser GNU parallel pour lancer plusieurs GNU parallel :

seq -w 0 9999999 | \
  parallel -j10 -q -I,, --pipe parallel -j0 touch pict{}.jpg

Si -j0 lance normalement 252 travaux, la commande ci-dessus tentera de lancer 2520 travaux. Sur un système GNU/Linux normal, vous pouvez lancer 32000 travaux en utilisant cette technique sans problème. Pour dépasser la limite de 32000 travaux, augmentez /proc/sys/kernel/pid_max à 4194303.

Si vous n'avez pas besoin que GNU parallel contrôle chaque travail (donc pas besoin de --retries ou --joblog ou similaire), il peut être encore plus rapide si vous pouvez générer les lignes de commande et les rediriger vers un shell. Donc, si vous pouvez faire ceci :

mygenerator | sh

Alors cela peut être parallélisé comme ceci :

mygenerator | parallel --pipe --block 10M sh

Par exemple :

mygenerator() {
  seq 10000000 | perl -pe 'print "echo This is fast job number "';
}
mygenerator | parallel --pipe --block 10M sh

La surcharge est 100000 fois plus petite, soit environ 100 nanosecondes par travail.

EXEMPLE: Utiliser les variables du shell

Lorsque vous utilisez des variables shell, vous devez les citer correctement car elles pourraient sinon être interprétées par le shell.

Remarquez la différence entre :

ARR=("My brother's 12\" records are worth <\$\$\$>"'!' Foo Bar)
parallel echo ::: ${ARR[@]} # Ceci n'est probablement pas ce que vous voulez

et :

ARR=("My brother's 12\" records are worth <\$\$\$>"'!' Foo Bar)
parallel echo ::: "${ARR[@]}"

Lorsque vous utilisez des variables dans la commande réelle contenant des caractères spéciaux (par exemple, espace), vous pouvez les citer en utilisant '"$VAR"' ou en utilisant des guillemets et -q :

VAR="My brother's 12\" records are worth <\$\$\$>"
parallel -q echo "$VAR" ::: '!'
export VAR
parallel echo '"$VAR"' ::: '!'

Si $VAR ne contient pas d'apostrophe, alors "'$VAR'" fonctionnera également (et ne nécessite pas export) :

VAR="My 12\" records are worth <\$\$\$>"
parallel echo "'$VAR'" ::: '!'

Si vous les utilisez dans une fonction, vous citez simplement comme vous le feriez normalement :

VAR="My brother's 12\" records are worth <\$\$\$>"
export VAR
myfunc() { echo "$VAR" "$1"; }
export -f myfunc
parallel myfunc ::: '!'

EXEMPLE: Regrouper les lignes de sortie

Lorsque vous exécutez des travaux qui produisent des données, vous ne voulez souvent pas que la sortie de plusieurs travaux soit mélangée. GNU parallel regroupe par défaut la sortie de chaque travail, de sorte que la sortie est imprimée lorsque le travail est terminé. Si vous souhaitez que les lignes complètes soient imprimées pendant que le travail s'exécute, vous pouvez utiliser --line-buffer. Si vous souhaitez que la sortie soit imprimée dès que possible, vous pouvez utiliser -u.

Comparez la sortie de :

parallel wget --progress=dot --limit-rate=100k \
  https://ftpmirror.gnu.org/parallel/parallel-20{}0822.tar.bz2 \
  ::: {12..16}
parallel --line-buffer wget --progress=dot --limit-rate=100k \
  https://ftpmirror.gnu.org/parallel/parallel-20{}0822.tar.bz2 \
  ::: {12..16}
parallel --latest-line wget --progress=dot --limit-rate=100k \
  https://ftpmirror.gnu.org/parallel/parallel-20{}0822.tar.bz2 \
  ::: {12..16}
parallel -u wget --progress=dot --limit-rate=100k \
  https://ftpmirror.gnu.org/parallel/parallel-20{}0822.tar.bz2 \
  ::: {12..16}

EXEMPLE: Marquer les lignes de sortie

GNU parallel regroupe les lignes de sortie, mais il peut être difficile de voir où commencent les différents travaux. --tag préfixe l'argument pour le rendre plus visible :

parallel --tag wget --limit-rate=100k \
  https://ftpmirror.gnu.org/parallel/parallel-20{}0822.tar.bz2 \
  ::: {12..16}

--tag fonctionne avec --line-buffer mais pas avec -u :

parallel --tag --line-buffer wget --limit-rate=100k \
  https://ftpmirror.gnu.org/parallel/parallel-20{}0822.tar.bz2 \
  ::: {12..16}

Vérifiez le temps de disponibilité des serveurs dans ~/.parallel/sshloginfile :

parallel --tag -S .. --nonall uptime

Donnez une nouvelle couleur à chaque travail. La plupart des terminaux prennent en charge les couleurs ANSI avec le code d'échappement "\033[30;3Xm" où 0 <= X <= 7 :

seq 10 | \
  parallel --tagstring '\033[30;3{=$_=++$::color%8=}m' seq {}
parallel --rpl '{color} $_="\033[30;3".(++$::color%8)."m"' \

... | perl -pe 's/\t//'

EXEMPLE: Conserver l'ordre de sortie identique à l'ordre d'entrée

Normalement, la sortie d'un travail sera imprimée dès qu'il sera terminé. Parfois, vous souhaitez que l'ordre de sortie reste le même que l'ordre d'entrée. Ceci est souvent important si la sortie est utilisée comme entrée pour un autre système. -k garantira que l'ordre de sortie sera le même que l'ordre d'entrée, même si les travaux ultérieurs se terminent avant les travaux précédents.

Ajouter une chaîne à chaque ligne d'un fichier texte :

cat textfile | parallel -k echo {} append_string

Si vous retirez -k, certaines lignes peuvent sortir dans le mauvais ordre.

Un autre exemple est traceroute :

parallel traceroute ::: qubes-os.org debian.org freenetproject.org

affichera traceroute de qubes-os.org, debian.org et freenetproject.org, mais il sera trié en fonction du travail qui s'est terminé en premier.

Pour conserver le même ordre qu'à l'entrée, exécutez :

parallel -k traceroute ::: qubes-os.org debian.org freenetproject.org

Cela garantira que le traceroute vers qubes-os.org sera imprimé en premier.

Un exemple un peu plus complexe est le téléchargement d'un fichier énorme en morceaux en parallèle : Certaines connexions Internet fourniront plus de données si vous téléchargez des fichiers en parallèle. Pour télécharger des fichiers en parallèle, voir : "EXEMPLE: Télécharger 10 images pour chacun des 30 derniers jours". Mais si vous téléchargez un gros fichier, vous pouvez le télécharger en morceaux en parallèle.

Pour télécharger les octets 10000000-19999999, vous pouvez utiliser curl :

curl -r 10000000-19999999 https://example.com/the/big/file >file.part

Pour télécharger un fichier de 1 Go, nous avons besoin de 100 morceaux de 10 Mo téléchargés et combinés dans le bon ordre.

seq 0 99 | parallel -k curl -r \
  {}0000000-{}9999999 https://example.com/the/big/file > file

EXEMPLE: Conserver l'ordre, mais rendre la sortie du travail 1 rapide

Si vous souhaitez que la sortie du travail 1 ne soit pas mise en mémoire tampon, mais que l'ordre soit conservé, vous pouvez faire ceci :

doit() {
  echo "$@" ERR >&2
  echo "$@" out
  sleep 0.$1
  echo "$@" ERR >&2
  echo "$@" out
}
export -f doit
parallel -k -u doit {= 'seq() > 1 and $opt::ungroup = 0' =} ::: 9 1 2 3

Cela affichera le travail 1 avec moins de surcharge.

EXEMPLE: Grep parallèle

grep -r recherche récursivement dans les répertoires. GNU parallel peut souvent accélérer cela.

find . -type f | parallel -k -j150% -n 1000 -m gr
ep -H -n STRING {}

Cela exécutera 1,5 tâche par CPU, et fournira 1000 arguments à grep.

Il existe des situations où ce qui précède sera plus lent que grep -r :

  • Si les données sont déjà en RAM. La surcharge liée au démarrage des tâches et au mise en mémoire tampon de la sortie peut l'emporter sur l'avantage de l'exécution en parallèle.
  • Si les fichiers sont volumineux. Si un fichier ne peut pas être lu en une seule opération de recherche, le disque peut commencer à s'essouffler.

L'accélération est causée par deux facteurs :

  • Sur les disques durs rotatifs, les petits fichiers nécessitent souvent une recherche pour chaque fichier. En recherchant plus de fichiers en parallèle, le bras peut passer sur un autre fichier recherché en cours de route.
  • Les disques NVMe sont souvent plus performants en exécutant plusieurs commandes en parallèle.

EXEMPLE : Grepping n lignes pour m expressions régulières.

La solution la plus simple pour grep un gros fichier pour de nombreux regexp est :

grep -f regexps.txt grosfichier

Ou si les regexp sont des chaînes de caractères fixes :

grep -F -f regexps.txt grosfichier

Il y a 3 facteurs limitants : CPU, RAM et I/O disque.

La RAM est facile à mesurer : Si le processus grep occupe la majeure partie de votre mémoire libre (par exemple, en exécutant top), alors la RAM est un facteur limitant.

Le CPU est également facile à mesurer : Si le grep utilise >90% du CPU dans top, alors le CPU est un facteur limitant, et la parallélisation accélérera cela.

Il est plus difficile de déterminer si les I/O disque sont le facteur limitant, et selon le système de disque, la parallélisation peut être plus ou moins rapide. La seule façon de savoir avec certitude est de tester et de mesurer.

Facteur limitant : RAM

Le grep -f regexps.txt grosfichier normal fonctionne quelle que soit la taille de grosfichier, mais si regexps.txt est si gros qu'il ne peut pas tenir en mémoire, alors vous devez le diviser.

grep -F prend environ 100 octets de RAM et grep prend environ 500 octets de RAM par octet de regexp. Donc, si regexps.txt représente 1% de votre RAM, il est peut-être trop gros.

Si vous pouvez convertir vos regexp en chaînes de caractères fixes, faites-le. Par exemple, si les lignes que vous recherchez dans grosfichier ressemblent toutes à :

ID1 foo bar baz Identifiant1 quux
fubar ID2 foo bar baz Identifiant2

alors votre regexps.txt peut être converti de :

ID1.*Identifiant1
ID2.*Identifiant2

en :

ID1 foo bar baz Identifiant1
ID2 foo bar baz Identifiant2

De cette façon, vous pouvez utiliser grep -F qui utilise environ 80% de mémoire en moins et est beaucoup plus rapide.

Si cela ne tient toujours pas en mémoire, vous pouvez faire ceci :

parallel --pipe-part -a regexps.txt --block 1M grep -F -f - -n grosfichier | \
  sort -un | perl -pe 's/^\d+://'

Le 1M devrait être votre mémoire libre divisée par le nombre de threads CPU et divisée par 200 pour grep -F et par 1000 pour grep normal. Sur GNU/Linux, vous pouvez faire :

free=$(awk '/^((Swap)?Cached|MemFree|Buffers):/ { sum += $2 }
            END { print sum }' /proc/meminfo)
percpu=$((free / 200 / $(parallel --number-of-threads)))k
parallel --pipe-part -a regexps.txt --block $percpu --compress \
  grep -F -f - -n grosfichier | \
  sort -un | perl -pe 's/^\d+://'

Si vous pouvez accepter des lignes dupliquées et un ordre incorrect, il est plus rapide de faire :

parallel --pipe-part -a regexps.txt --block $percpu --compress \
  grep -F -f - grosfichier

Facteur limitant : CPU

Si le CPU est le facteur limitant, la parallélisation doit être faite sur les regexp :

cat regexps.txt | parallel --pipe -L1000 --round-robin --compress \
  grep -f - -n grosfichier | \
  sort -un | perl -pe 's/^\d+://'

La commande démarrera un grep par CPU et lira grosfichier une fois par CPU, mais comme cela est fait en parallèle, toutes les lectures sauf la première seront mises en cache en RAM. En fonction de la taille de regexps.txt, il peut être plus rapide d'utiliser --block 10m au lieu de -L1000.

Certains systèmes de stockage sont plus performants lors de la lecture de plusieurs blocs en parallèle. C'est le cas de certains systèmes RAID et de certains systèmes de fichiers réseau. Pour paralléliser la lecture de grosfichier :

parallel --pipe-part --block 100M -a grosfichier -k --compress \
  grep -f regexps.txt

Cela divisera grosfichier en blocs de 100 Mo et exécutera grep sur chacun de ces blocs. Pour paralléliser à la fois la lecture de grosfichier et de regexps.txt, combinez les deux en utilisant --cat :

parallel --pipe-part --block 100M -a grosfichier --cat cat regexps.txt \
  \| parallel --pipe -L1000 --round-robin grep -f - {}

Si une ligne correspond à plusieurs regexp, la ligne peut être dupliquée.

Problème plus important

Si le problème est trop grand pour être résolu ainsi, vous êtes probablement prêt pour Lucene.

EXEMPLE : Utilisation d'ordinateurs distants

Pour exécuter des commandes sur un ordinateur distant, SSH doit être configuré et vous devez pouvoir vous connecter sans entrer de mot de passe (Les commandes ssh-copy-id, ssh-agent et sshpass peuvent vous aider).

Si vous devez vous connecter à un cluster entier, vous ne voudrez généralement pas accepter la clé d'hôte pour chaque hôte. Vous voulez les accepter la première fois et être averti s'ils sont jamais modifiés. Pour ce faire :

# Ajouter les serveurs au fichier de connexion ssh
(echo servera; echo serverb) > .parallel/my_cluster
# S'assurer que .ssh/config existe
touch .ssh/config
cp .ssh/config .ssh/config.backup
# Désactiver StrictHostKeyChecking temporairement
(echo 'Host *'; echo StrictHostKeyChecking no) >> .ssh/config
parallel --slf my_cluster --nonall true
# Supprimer la désactivation de StrictHostKeyChecking
mv .ssh/config.backup .ssh/config

Les serveurs dans .parallel/my_cluster sont maintenant ajoutés dans .ssh/known_hosts.

Pour exécuter echo sur server.example.com :

seq 10 | parallel --sshlogin server.example.com echo

Pour exécuter des commandes sur plus d'un ordinateur distant, exécutez :

seq 10 | parallel --sshlogin s1.example.com,s2.example.net echo

Ou :

seq 10 | parallel --sshlogin server.example.com \
  --sshlogin server2.example.net echo

Si le nom d'utilisateur de connexion est foo sur server2.example.net, utilisez :

seq 10 | parallel --sshlogin server.example.com \
  --sshlogin foo@server2.example.net echo

Si votre liste d'hôtes est server1-88.example.net avec le login foo :

seq 10 | parallel -Sfoo@server{1..88}.example.net echo

Pour distribuer les commandes à une liste d'ordinateurs, créez un fichier mycomputers avec tous les ordinateurs :

server.example.com
foo@server2.example.com
server3.example.com

Ensuite, exécutez :

seq 10 | parallel --sshloginfile mycomputers echo

Pour inclure l'ordinateur local, ajoutez le sshlogin spécial ':' à la liste :

server.example.com
foo@server2.example.com
server3.example.com
:

GNU parallel essaiera de déterminer le nombre de CPU sur chacun des ordinateurs distants, et exécutera une tâche par CPU - même si les ordinateurs distants n'ont pas le même nombre de CPU.

Si le nombre de CPU sur les ordinateurs distants n'est pas correctement identifié, le nombre de CPU peut être ajouté au début. Ici, l'ordinateur a 8 CPU.

seq 10 | parallel --sshlogin 8/server.example.com echo

EXEMPLE : Transfert de fichiers

Pour recompresser des fichiers gzippés avec bzip2 en utilisant un ordinateur distant, exécutez :

find logs/ -name '*.gz' | \
  parallel --sshlogin server.example.com \
  --transfer "zcat {} | bzip2 -9 >{.}.bz2"

Cela listera les fichiers .gz dans le répertoire logs et tous les répertoires en dessous. Ensuite, il transférera les fichiers vers server.example.com dans le répertoire correspondant de $HOME/logs. Sur server.example.com, le fichier sera recompressé à l'aide de zcat et bzip2, résultant en un fichier correspondant avec .gz remplacé par .bz2.

Si vous souhaitez que le fichier bz2 résultant soit retransféré sur l'ordinateur local, ajoutez --return {.}.bz2 :

find logs/ -name '*.gz' | \
  parallel --sshlogin server.example.com \
  --transfer --return {.}.bz2 "zcat {} | bzip2 -9 >{.}.bz2"

Une fois la recompression terminée, le fichier .bz2 est retransféré vers l'ordinateur local et placé à côté du fichier .gz d'origine.

Si vous souhaitez supprimer les fichiers transférés sur l'ordinateur distant, ajoutez --cleanup. Cela supprimera à la fois le fichier transféré vers l'ordinateur distant et les fichiers transférés depuis l'ordinateur distant :

find logs/ -name '*.gz' | \
  parallel --sshlogin server.example.com \
  --transfer --return {.}.bz2 --cleanup "zcat {} | bzip2 -9 >{.}.bz2"

Si vous souhaitez exécuter sur plusieurs ordinateurs, ajoutez les ordinateurs à --sshlogin soit en utilisant ',' soit plusieurs --sshlogin :

find logs/ -name '*.gz' | \
  parallel --sshlogin server.example.com,server2.example.com \
  --sshlogin server3.example.com \
  --transfer --return {.}.bz2 --cleanup "zcat {} | bzip2 -9 >{.}.bz2"

Vous pouvez ajouter l'ordinateur local en utilisant --sshlogin :. Cela désactivera la suppression et le transfert pour l'ordinateur local uniquement :

find logs/ -name '*.gz' | \
  parallel --sshlogin server.example.com,server2.example.com \
  --sshlogin server3.example.com \
  --sshlogin : \
  --transfer --return {.}.bz2 --cleanup "zcat {} | bzip2 -9 >{.}.bz2"

Souvent, --transfer, --return et --cleanup sont utilisés ensemble. Ils peuvent être abrégés en --trc :

find logs/ -name '*.gz' | \
  parallel --sshlogin server.example.com,server2.example.com \
  --sshlogin server3.example.com \
  --sshlogin : \
  --trc {.}.bz2 "zcat {} | bzip2 -9 >{.}.bz2"

Avec le fichier mycomputers contenant la liste des ordinateurs, cela devient :

find logs/ -name '*.gz' | parallel --sshloginfile mycomputers \
  --trc {.}.bz2 "zcat {} | bzip2 -9 >{.}.bz2"

Si le fichier ~/.parallel/sshloginfile contient la liste des ordinateurs, le raccourci spécial -S .. peut être utilisé :

find logs/ -name '*.gz' | parallel -S .. \
  --trc {.}.bz2 "zcat {} | bzip2 -9 >{.}.bz2"

EXEMPLE : Utilisation d'ordinateurs distants derrière un mur NAT

Si les workers sont derrière un mur NAT, vous aurez besoin de quelques astuces pour y accéder.

Si vous pouvez utiliser ssh vers un jumphost et atteindre les workers à partir de là, alors la solution évidente serait celle-ci, mais cela ne fonctionne pas :

parallel --ssh 'ssh jumphost ssh' -S host1 echo ::: NE FONCTIONNE PAS

Cela ne fonctionne pas car la commande est dé-quotée par ssh deux fois, alors que parallel de GNU ne s'attend qu'à une seule dé-quotation.

Vous pouvez utiliser une fonction bash et faire en sorte que GNU parallel quote la commande :

jumpssh() { ssh -A jumphost ssh $(parallel --shellquote ::: "$@"); }
export -f jumpssh
parallel --ssh jumpssh -S host1 echo ::: cela fonctionne

Ou vous pouvez plutôt mettre ceci dans ~/.ssh/config :

Host host1 host2 host3
  ProxyCommand ssh jumphost.domain nc -w 1 %h 22

Cela nécessite que nc (netcat) soit installé sur le jumphost. Avec cela, vous pouvez simplement :

parallel -S host1,host2,host3 echo ::: Cela fonctionne

Pas de jumphost, mais des redirections de port

S'il n'y a pas de jumphost mais que chaque serveur a le port 22 redirigé depuis le pare-feu (par exemple, le port 22001 du pare-feu = port 22 sur host1, 22002 = host2, 22003 = host3), alors vous pouvez utiliser ~/.ssh/config :

Host host1.v
  Port 22001
Host host2.v
  Port 22002
Host host3.v
  Port 22003
Host *.v
  Hostname firewall

Et ensuite, utilisez host{1..3}.v comme des hôtes normaux :

parallel -S host1.v,host2.v,host3.v echo ::: a b c

Pas de jumphost, pas de redirections de port

Si les ports ne peuvent pas être redirigés, vous avez besoin d'une sorte de VPN pour traverser le mur NAT. TOR est une option pour cela, car il est très facile à faire fonctionner.

Vous devez installer TOR et configurer un service caché. Dans torrc, mettez :

HiddenServiceDir /var/lib/tor/hidden_service/
HiddenServicePort 22 127.0.0.1:22

Ensuite, démarrez TOR : /etc/init.d/tor restart

Le nom d'hôte TOR se trouve maintenant dans /var/lib/tor/hidden_service/hostname et ressemble à izjafdceobowklhz.onion. Maintenant, il vous suffit de préfixer torsocks à ssh :

parallel --ssh 'torsocks ssh' -S izjafdceobowklhz.onion \
  -S zfcdaeiojoklbwhz.onion,auclucjzobowklhi.onion echo ::: a b c

Si tous les hôtes ne sont pas accessibles via TOR :

parallel -S 'torsocks ssh izjafdceobowklhz.onion,host2,host3' \
  echo ::: a b c

Voir plus d'astuces ssh sur https://en.wikibooks.org/wiki/OpenSSH/Cookbook/Proxies_and_Jump_Hosts

EXEMPLE : Parallélisation de rsync

rsync est un excellent outil, mais il ne remplit pas toujours la bande passante disponible. L'exécution de plusieurs rsync en parallèle peut résoudre ce problème.

Ajustez -j10 jusqu'à trouver le nombre optimal.

La commande perl produit 2 lignes pour chaque entrée. GNU parallel prend 2 entrées (en utilisant -N2) et remplace {1} et {2} par les entrées.

EXEMPLE : Sortie vers une base de données

GNU parallel peut sortir vers une table de base de données et un fichier CSV :

dburl=csv:///%2Ftmp%2Fmydir
dbtableurl=$dburl/mytable.csv
parallel --sqlandworker $dbtableurl seq ::: {1..10}

C'est plutôt lent et consomme beaucoup de temps CPU car GNU parallel analyse l'ensemble du fichier CSV pour chaque mise à jour.

Une meilleure approche consiste à utiliser une base SQLite, puis à la convertir en CSV :

dburl=sqlite3:///%2Ftmp%2Fmy.sqlite
dbtableurl=$dburl/mytable
parallel --sqlandworker $dbtableurl seq ::: {1..10}
sql $dburl '.headers on' '.mode csv' 'SELECT * FROM mytable;'

Cela prend environ une seconde par tâche.

Si vous avez accès à un vrai système de gestion de base de données, tel que PostgreSQL, c'est encore plus rapide :

dburl=pg://user:pass@host/mydb
dbtableurl=$dburl/mytable
parallel --sqlandworker $dbtableurl seq ::: {1..10}
sql $dburl \
  "COPY (SELECT * FROM mytable) TO stdout DELIMITER ',' CSV HEADER;"

Ou MySQL :

dburl=mysql://user:pass@host/mydb
dbtableurl=$dburl/mytable
parallel --sqlandworker $dbtableurl seq ::: {1..10}
sql -p -B $dburl "SELECT * FROM mytable;" > mytable.tsv
perl -pe 's/"/""/g; s/\t/","/g; s/^/"/; s/$/"/;
  %s=("\\" => "\\", "t" => "\t", "n" => "\n");
  s/\\([\\tn])/$s{$1}/g;' mytable.tsv

EXEMPLE : Traiter un gros fichier en utilisant plus de CPU

Pour traiter un gros fichier ou une sortie, vous pouvez utiliser --pipe pour diviser les données en blocs et les passer au programme de traitement.

Si le programme est gzip -9, vous pouvez faire :

cat bigfile | parallel --pipe --recend '' -k gzip -9 > bigfile.gz

Cela divisera bigfile en blocs de 1 Mo et les passera en parallèle à gzip -9. Un gzip sera exécuté par CPU. La sortie de gzip -9 sera conservée dans l'ordre et sauvegardée dans bigfile.gz.

gzip fonctionne bien si la sortie est ajoutée, mais certains traitements ne fonctionnent pas ainsi - par exemple le tri. Pour cela, GNU parallel peut placer la sortie de chaque commande dans un fichier. Ceci triera un gros fichier en parallèle :

cat bigfile | parallel --pipe --files sort |\
  parallel -Xj1 sort -m {} ';' rm {} >bigfile.sort

Ici, bigfile est divisé en blocs d'environ 1 Mo, chaque bloc se terminant par '\n' (ce qui est le défaut pour --recend). Chaque bloc est passé à sort et la sortie de sort est sauvegardée dans des fichiers. Ces fichiers sont passés au second parallel qui exécute sort -m sur les fichiers avant de les supprimer. La sortie est sauvegardée dans bigfile.sort.

--pipe de GNU parallel atteint environ 100 Mo/s car chaque octet doit être copié via GNU parallel. Mais si bigfile est un vrai fichier (avec possibilité de seek), GNU parallel peut éviter la copie et envoyer les parties directement au programme :

parallel --pipe-part --block 100m -a bigfile --files sort |\
  parallel -Xj1 sort -m {} ';' rm {} >bigfile.sort

Lors du traitement avec --pipe, vous pouvez avoir des lignes regroupées par une valeur. Voici my.csv :

Transaction Client Article
     1       a       53
     2       b       65
     3       b       82
     4       c       96
     5       c       67
     6       c       13
     7       d       90
     8       d       43
     9       d       91
     10      d       84
     11      e       72
     12      e       102
     13      e       63

     15      e       74

Supposons que vous souhaitiez que GNU parallel traite chaque client. Autrement dit : vous voulez que toutes les transactions d'un seul client soient traitées comme un seul enregistrement.

Pour ce faire, nous pré-traitons les données avec un programme qui insère un séparateur d'enregistrement avant chaque client (colonne 2 = $F[1]). Ici, nous créons d'abord une chaîne aléatoire de 50 caractères, que nous utilisons ensuite comme séparateur :

EXEMPLE : Exécuter plus de 250 tâches solution de contournement

Si vous devez exécuter un nombre massif de tâches en parallèle, vous atteindrez probablement la limite de descripteurs de fichiers, qui est souvent d'environ 250 tâches. Si vous êtes superutilisateur, vous pouvez augmenter la limite dans /etc/security/limits.conf, mais vous pouvez également utiliser cette solution de contournement. La limite de descripteurs de fichiers est par processus. Cela signifie que si vous lancez simplement plusieurs GNU parallel, chacun d'eux peut exécuter 250 tâches. Ceci lancera jusqu'à 2500 tâches :

cat myinput |\
  parallel --pipe -N 50 --round-robin -j50 parallel -j50 votre_prg

Ceci lancera jusqu'à 62500 tâches (à utiliser avec prudence - vous avez besoin de 64 Go de RAM pour cela, et vous devrez peut-être augmenter /proc/sys/kernel/pid_max) :

cat myinput |\
  parallel --pipe -N 250 --round-robin -j250 parallel -j250 votre_prg

EXEMPLE : Fonctionne comme mutex et sémaphore comptant

La commande sem est un alias pour parallel --semaphore.

Un sémaphore comptant autorisera le démarrage d'un nombre donné de tâches en arrière-plan. Lorsque le nombre de tâches s'exécute en arrière-plan, GNU sem attendra qu'une de ces tâches se termine avant d'en démarrer une autre. sem --wait attendra que toutes les tâches soient terminées.

Exécuter 10 tâches simultanément en arrière-plan :

for i in *.log ; do
  echo $i
  sem -j10 gzip $i ";" echo done
done
sem --wait

Un mutex est un sémaphore comptant autorisant l'exécution d'une seule tâche. Ceci modifiera le fichier myfile et ajoutera des lignes avec les numéros de 1 à 3 au début du fichier.

seq 3 | parallel sem sed -i -e '1i{}' myfile

Comme myfile peut être très volumineux, il est important qu'un seul processus modifie le fichier en même temps.

Nommez le sémaphore pour avoir plusieurs sémaphores différents actifs en même temps :

seq 3 | parallel sem --id mymutex sed -i -e '1i{}' myfile

EXEMPLE : GNU Parallel comme système de file d'attente/gestionnaire de batch

GNU parallel peut fonctionner comme un simple système de file d'attente de tâches ou un gestionnaire de batch. L'idée est de mettre les tâches dans un fichier et de laisser GNU parallel lire en continu depuis celui-ci. Comme GNU parallel s'arrêtera à la fin du fichier, nous utilisons tail pour continuer la lecture :

true >jobqueue; tail -n+0 -f jobqueue | parallel

Pour soumettre vos tâches à la file d'attente :

echo my_command my_arg >> jobqueue

Vous pouvez bien sûr utiliser -S pour distribuer les tâches vers des ordinateurs distants :

true >jobqueue; tail -n+0 -f jobqueue | parallel -S ..

La sortie ne sera imprimée que lors de la lecture de la prochaine entrée après qu'une tâche soit terminée : Vous devrez donc soumettre une tâche après que la première soit terminée pour voir la sortie de la première tâche.

Si vous laissez cela tourner pendant longtemps, jobqueue va s'agrandir. Une façon de supprimer les tâches déjà exécutées est de faire en sorte que GNU parallel s'arrête lorsqu'il rencontre une valeur spéciale et de redémarrer ensuite. Pour utiliser --eof afin que GNU parallel se termine, tail doit également être forcé à se terminer :

true >jobqueue;
while true; do
  tail -n+0 -f jobqueue |
    (parallel -E StOpHeRe -S ..; echo GNU Parallel est maintenant terminé;
     perl -e 'while(<>){/StOpHeRe/ and last};print <>' jobqueue > j2;
     (seq 1000 >> jobqueue &);
     echo Fin de l'ajout de données factices forçant tail à se terminer)
  echo tail terminé;
  mv j2 jobqueue
done

Dans certains cas, vous pouvez utiliser plus de CPUs et d'ordinateurs la nuit :

# De jour
echo 50% > jobfile
cp day_server_list ~/.parallel/sshloginfile
# De nuit
echo 100% > jobfile
cp night_server_list ~/.parallel/sshloginfile
tail -n+0 -f jobqueue | parallel --jobs jobfile -S ..

GNU parallel découvre si jobfile ou ~/.parallel/sshloginfile change.

EXEMPLE : GNU Parallel comme processeur de répertoires

Si vous avez un répertoire dans lequel les utilisateurs déposent des fichiers qui doivent être traités, vous pouvez faire ceci sous GNU/Linux (Si vous savez comment inotifywait s'appelle sur d'autres plateformes, veuillez signaler un bug) :

Cela exécutera la commande echo sur chaque fichier placé dans my_dir ou ses sous-répertoires.

EXEMPLE : Localiser le paquet manquant

Si vous avez téléchargé une source et tenté de la compiler, vous avez peut-être vu :

$ ./configure

configure: error: "libsomething not found"

Souvent, il n'est pas évident de savoir quel paquet installer pour obtenir ce fichier. Debian a `apt-file` pour rechercher un fichier. `tracefile` de https://codeberg.org/tange/tangetools peut dire quels fichiers un programme a essayé d'accéder. Dans ce cas, nous sommes intéressés par l'un des derniers fichiers :

$ tracefile -un ./configure | tail | parallel -j0 apt-file search
