NOM

pam_systemd - Enregistre les sessions utilisateur dans le gestionnaire de connexion systemd

SYNTAXE

pam_systemd.so

DESCRIPTION

pam_systemd enregistre les sessions utilisateur auprès du gestionnaire de connexion systemd systemd-logind.service(8), et par conséquent dans la hiérarchie des groupes de contrôle systemd.

Le module applique également diverses gestions de ressources et paramètres d'exécution à la nouvelle session, tels que configurés dans les Enregistrements utilisateur JSON[1], lorsqu'ils sont définis.

Lors de la connexion, ce module — conjointement avec systemd-logind.service — garantit ce qui suit :

1. S'il n'existe pas encore, le répertoire d'exécution utilisateur /run/user/$UID est créé ou monté en tant que nouveau système de fichiers "tmpfs" avec quota appliqué, et son ownership est modifié pour l'utilisateur qui se connecte.
2. La variable d'environnement $XDG_SESSION_ID est initialisée. Si l'audit est disponible et que pam_loginuid.so a été exécuté avant ce module (ce qui est fortement recommandé), la variable est initialisée à partir de l'identifiant de session d'audit (/proc/self/sessionid). Sinon, un compteur de session indépendant est utilisé.
3. Une nouvelle unité de portée systemd est créée pour la session. Si c'est la première session concurrente de l'utilisateur, une unité de tranche implicite par utilisateur sous user.slice est automatiquement créée et la portée y est placée. Une instance du service système user@.service, qui exécute l'instance du gestionnaire utilisateur systemd, est démarrée.
4. Les variables d'environnement "$TZ", "$EMAIL" et "$LANG" sont configurées pour l'utilisateur, sur la base des données respectives de l'enregistrement JSON de l'utilisateur (s'il est défini). De plus, toutes les variables d'environnement explicitement configurées dans l'enregistrement utilisateur sont importées, et l'umask, le niveau de priorité et les limites de ressources sont initialisés.

Lors de la déconnexion, ce module garantit ce qui suit :

1. Si activé dans logind.conf(5) (KillUserProcesses=), tous les processus de la session sont terminés. Si la dernière session concurrente d'un utilisateur se termine, l'instance systemd de l'utilisateur sera également terminée, tout comme l'unité de tranche de l'utilisateur.
2. Si la dernière session concurrente d'un utilisateur se termine, le répertoire d'exécution utilisateur /run/user/$UID et tout son contenu sont également supprimés.

Si le système n'a pas été démarré avec systemd comme système d'initialisation, ce module ne fait rien et renvoie immédiatement PAM_SUCCESS.

OPTIONS

Les options suivantes sont comprises :

class=

Prend un argument de chaîne de caractères qui définit la classe de session. La variable d'environnement XDG_SESSION_CLASS (voir ci-dessous) a la priorité. Voir sd_session_get_class(3) pour une façon de demander la classe d'une session. Les classes de session suivantes sont définies :

Tableau 1. Classes de session

Nom Explication
user Une session utilisateur interactive normale. C'est la classe par défaut pour les sessions pour lesquelles un TTY ou un écran X est connu au moment de l'enregistrement de la session.
user-early Similaire à user, mais les sessions de cette classe ne sont pas ordonnées après systemd-user-sessions.service(8), c'est-à-dire qu'elles peuvent être démarrées avant que les sessions régulières ne soient autorisées à être établies. Cette classe de session est la valeur par défaut pour les sessions de l'utilisateur root qui seraient autrement qualifiées pour la classe user, voir ci-dessus. (Ajouté dans la v256.)
user-light Similaire à user, mais les sessions de cette classe n'entraîneront pas le démarrage du service user@.service(5) de l'utilisateur, et donc pourraient ne pas avoir de gestionnaire de service de l'utilisateur en cours d'exécution. (Ajouté dans la v258.)
user-early-light Similaire à user-early, mais les sessions de cette classe n'entraîneront pas le démarrage du service user@.service(5) de l'utilisateur, et donc pourraient ne pas avoir de gestionnaire de service de l'utilisateur en cours d'exécution. (Ajouté dans la v258.)
user-incomplete Similaire à user, mais pour les sessions qui ne sont pas encore entièrement configurées, c'est-à-dire qui n'ont pas de répertoire personnel monté ou similaire. Ceci est utilisé par systemd-homed.service(8) pour permettre aux utilisateurs de se connecter via ssh(1) avant que leur répertoire personnel ne soit monté, retardant le montage jusqu'à ce que l'utilisateur ait fourni le mot de passe de déverrouillage. Les sessions de cette classe sont mises à niveau vers la classe user régulière une fois le répertoire personnel activé.
greeter Similaire à user, mais pour les sessions qui sont lancées de manière éphémère par un gestionnaire d'affichage et qui invitent l'utilisateur à saisir ses identifiants de connexion.
lock-screen Similaire à user, mais pour les sessions qui sont lancées de manière éphémère par un gestionnaire d'affichage et qui affichent un écran de verrouillage pouvant être utilisé pour déverrouiller des comptes ou des sessions utilisateur verrouillés.
background Utilisé pour les sessions en arrière-plan, comme celles invoquées par cron(8) et des outils similaires. C'est la classe par défaut pour les sessions pour lesquelles aucun TTY ou écran X n'est connu au moment de l'enregistrement de la session.
background-light Similaire à background, mais les sessions de cette classe n'entraîneront pas le démarrage du service user@.service(5) de l'utilisateur, et donc pourraient ne pas avoir de gestionnaire de service de l'utilisateur en cours d'exécution. (Ajouté dans la v256.)
manager Le service user@.service(5) de l'utilisateur est enregistré sous cette classe de session. (Ajouté dans la v256.)
manager-early Similaire à manager, mais pour l'utilisateur root. Comparer avec la situation user vs. user-early. (Ajouté dans la v256.)
none Ignore l'enregistrement de cette session auprès de logind. Aucune unité de portée ne sera créée et le gestionnaire de service utilisateur ne sera pas démarré. (Ajouté dans la v258.)

Ajouté dans la version 197.

type=

Prend un argument de chaîne de caractères qui définit le type de session. La variable d'environnement XDG_SESSION_TYPE (voir ci-dessous) a la priorité. L'un des choix parmi unspecified, tty, x11, wayland, mir, ou web. Voir sd_session_get_type(3) pour plus de détails sur le type de session.

Ajouté dans la version 209.

desktop=

Prend une seule chaîne d'identification courte pour l'environnement de bureau. La variable d'environnement XDG_SESSION_DESKTOP (voir ci-dessous) a la priorité. Ceci peut être utilisé pour indiquer le bureau de session utilisé, lorsque cela s'applique et si cette information est disponible. Par exemple : GNOME, ou KDE. Il est recommandé d'utiliser les mêmes identifiants et capitalisation que pour $XDG_CURRENT_DESKTOP, tels que définis par la Spécification des entrées de bureau[2]. (Cependant, notez que l'option ne prend qu'un seul élément, et non une liste séparée par des deux-points comme $XDG_CURRENT_DESKTOP.) Voir sd_session_get_desktop(3) pour plus de détails.

Ajouté dans la version 240.

area=

Prend un nom de fichier comme paramètre. Si spécifié et que l'utilisateur se connecte à son compte, la variable d'environnement $HOME sera définie sur ~/Areas/ suffixé par la chaîne spécifiée, mais seulement si ce répertoire existe. De plus, la variable $XDG_AREA sera définie sur le paramètre (sans préfixe).

Cette fonctionnalité peut être utilisée pour maintenir plusieurs répertoires personnels secondaires séparés au sein du répertoire personnel principal de l'utilisateur. Typiquement, la zone de connexion est spécifiée lors de la connexion, si le compte le permet (ce que font les comptes fournis par pam_systemd_home(8)), mais ce paramètre peut être utilisé pour définir une valeur par défaut si cela n'est pas fourni.

Notez que cela ajuste seulement $HOME pendant la connexion, cela n'affecte pas le répertoire personnel de l'utilisateur autrement déclaré. Spécifiquement, cela signifie que sshd(8) continuera à rechercher les clés SSH de l'utilisateur uniquement dans le répertoire personnel principal de l'utilisateur, pas dans l'une de ses zones.

default-capability-bounding-set=, default-capability-ambient-set=

Prend une liste de capacités de processus séparées par des virgules (par exemple, CAP_WAKE_ALARM, CAP_BLOCK_SUSPEND, ...) à définir pour les processus de la session invoquée, si l'enregistrement utilisateur n'encode pas directement des ensembles appropriés de capacités. Voir capabilities(7) pour plus de détails sur le concept de capacités. Si non spécifié, l'ensemble borné par défaut est laissé tel quel (c'est-à-dire qu'il contient généralement l'ensemble complet des capacités). L'ensemble ambiant par défaut est défini sur CAP_WAKE_ALARM pour les utilisateurs réguliers si la session PAM est associée à un siège local ou si elle est invoquée pour le service utilisateur systemd user@.service. Sinon, la valeur par défaut est l'ensemble vide.

Ajouté dans la version 254.

debug[=]

Prend un argument booléen optionnel. Si oui ou sans l'argument, le module enregistrera des informations de débogage pendant son fonctionnement.

MODULE TYPES FOURNIS

Seul session est fourni.

ENVIRONNEMENT

Les variables d'environnement suivantes sont initialisées par le module et disponibles pour les processus de la session utilisateur :

$XDG_SESSION_ID

Un identifiant de session court, adapté pour être utilisé dans les noms de fichiers. La chaîne elle-même doit être considérée comme opaque, bien qu'il s'agisse souvent de l'identifiant de session d'audit tel que rapporté par /proc/self/sessionid. Chaque identifiant sera attribué une seule fois pendant la durée de fonctionnement de la machine. Il peut donc être utilisé pour étiqueter de manière unique des fichiers ou d'autres ressources de cette session. Combinez cet identifiant avec l'identifiant de démarrage, tel que retourné par sd_id128_get_boot(3), pour un identifiant globalement unique.

$XDG_RUNTIME_DIR

Chemin d'accès à un répertoire utilisateur privé et inscriptible par l'utilisateur, qui est lié au moment de la connexion de l'utilisateur sur la machine. Il est automatiquement créé lors de la première connexion d'un utilisateur et supprimé lors de sa dernière déconnexion. Si un utilisateur se connecte deux fois simultanément, les deux sessions verront le même $XDG_RUNTIME_DIR et le même contenu. Si un utilisateur se connecte une fois, puis se déconnecte, puis se reconnecte, le contenu du répertoire sera perdu entre-temps, mais les applications ne doivent pas s'appuyer sur ce comportement et doivent être capables de gérer les fichiers obsolètes. Pour stocker des données spécifiques à la session dans ce répertoire, l'utilisateur doit inclure la valeur de $XDG_SESSION_ID dans le nom du fichier. Ce répertoire doit être utilisé pour les objets du système de fichiers d'exécution tels que les sockets AF_UNIX, les FIFO, les fichiers PID et similaires. Il est garanti que ce répertoire est local et offre l'ensemble de fonctionnalités du système de fichiers le plus large possible que le système d'exploitation fournit. Pour plus de détails, voir la XDG Base Directory Specification[3]. $XDG_RUNTIME_DIR n'est pas défini si l'utilisateur actuel n'est pas l'utilisateur d'origine de la session.

$TZ, $EMAIL, $LANG

Si un enregistrement utilisateur JSON est connu pour l'utilisateur qui se connecte, ces variables sont initialisées à partir des données respectives de l'enregistrement.

Ajouté dans la version 245.

$SHELL_PROMPT_PREFIX, $SHELL_PROMPT_SUFFIX, $SHELL_WELCOME

Ces variables d'environnement sont initialisées à partir des identifiants de service « shell.prompt.prefix », « shell.prompt.suffix » et « shell.welcome » s'ils sont définis. Elles sont transmises aux processus de session invoqués, où elles sont importées dans tout invite de commande (spécifiquement $SHELL_PROMPT_PREFIX est ajouté en préfixe à $PS1, et $SHELL_PROMPT_SUFFIX en suffixe) ou imprimées à l'écran lorsque le shell s'initialise pour la première fois.

Ajouté dans la version 257.

Les variables d'environnement suivantes sont lues par le module et peuvent être utilisées par le service PAM pour transmettre des métadonnées au module. Si ces variables ne sont pas définies lorsque le module PAM est invoqué mais peuvent être déterminées autrement, elles sont définies par le module, de sorte que ces variables sont initialisées pour la session et les applications si elles sont connues.

$XDG_SESSION_TYPE

Le type de session. Ceci peut être utilisé à la place de type= sur la ligne de paramètre du module, et est généralement préféré.

Ajouté dans la version 209.

$XDG_SESSION_CLASS

La classe de session. Ceci peut être utilisé à la place de class= sur la ligne de paramètre du module, et est généralement préféré.

Ajouté dans la version 209.

$XDG_SESSION_DESKTOP

L'identifiant du bureau. Ceci peut être utilisé à la place de desktop= sur la ligne de paramètre du module, et est généralement préféré.

Ajouté dans la version 209.

$XDG_SEAT

Le nom du siège auquel la session doit être enregistrée, le cas échéant.

Ajouté dans la version 209.

$XDG_VTNR

Le numéro de VT auquel la session doit être enregistrée, le cas échéant. (Ne s'applique qu'aux sièges disposant d'un VT, tel que « seat0 »)

Ajouté dans la version 209.

$XDG_AREA

Si une zone (répertoires personnels secondaires de l'utilisateur, dans le répertoire personnel primaire) dans laquelle se connecter a été sélectionnée, cette variable est définie sur le nom de la zone (sans aucun préfixe de chemin). Elle est sinon non définie. Pour plus de détails sur les zones, voir ci-dessus.

Ajouté dans la version 258.

Si non défini, pam_systemd initialisera $XDG_SEAT et $XDG_VTNR en fonction de la variable $DISPLAY (si cette dernière est définie).

LIMITES DE SESSION

Les modules PAM antérieurs dans la pile, c'est-à-dire ceux qui précèdent pam_systemd.so, peuvent définir des limites de portée de session à l'aide des objets de contexte PAM. Les données de ces objets sont fournies sous forme de chaînes C terminées par NUL et correspondent directement aux directives de contrôle des ressources unitaires respectives. Notez que ces limites s'appliquent aux sessions individuelles de l'utilisateur, elles ne s'appliquent pas à tous les processus utilisateur dans leur ensemble. En particulier, l'instance d'unité user@.service par utilisateur, qui exécute le processus gestionnaire systemd --user et ses enfants, et est suivie en dehors de toute session, étant partagée par toutes les sessions de l'utilisateur, n'est pas couverte par ces limites.

Voir systemd.resource-control(5) pour plus d'informations sur les ressources. Voir également pam_set_data(3) pour des informations supplémentaires sur la façon de définir les objets de contexte.

systemd.memory_max=

Définit l'unité MemoryMax=.

Ajouté dans la version 239.

systemd.tasks_max=

Définit l'unité TasksMax=.

Ajouté dans la version 239.

systemd.cpu_weight=

Définit l'unité CPUWeight=.

Ajouté dans la version 239.

systemd.io_weight=

Définit l'unité IOWeight=.

Ajouté dans la version 239.

systemd.runtime_max_sec=

Définit l'unité RuntimeMaxSec=.

Ajouté dans la version 244.

Exemple de données pouvant être fournies par un autre module PAM :

pam_set_data(handle, "systemd.memory_max", (void *)"200M", cleanup);
pam_set_data(handle, "systemd.tasks_max",  (void *)"50",   cleanup);
pam_set_data(handle, "systemd.cpu_weight", (void *)"100",  cleanup);
pam_set_data(handle, "systemd.io_weight",  (void *)"340",  cleanup);
pam_set_data(handle, "systemd.runtime_max_sec", (void *)"3600", cleanup);

EXEMPLE

Voici un exemple de fragment de configuration PAM qui permet aux sessions des utilisateurs d'être gérées par systemd-logind.service :

#%PAM-1.0
-auth     [success=done authtok_err=bad perm_denied=bad maxtries=bad default=ignore] pam_systemd_home.so
auth      sufficient pam_unix.so
auth      required   pam_deny.so
account   required   pam_nologin.so
-account  [success=done authtok_expired=bad new_authtok_reqd=bad maxtries=bad acct_expired=bad default=ignore] pam_systemd_home.so
account   required   pam_unix.so
-password sufficient pam_systemd_home.so
password  sufficient pam_unix.so sha512 shadow try_first_pass
password  required   pam_deny.so
-session  optional   pam_keyinit.so revoke
-session  optional   pam_loginuid.so
-session  optional   pam_systemd_home.so
-session  optional   pam_systemd.so
session   required   pam_unix.so
