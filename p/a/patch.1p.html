PATCH(1P) Manuel du programmeur POSIX PATCH(1P)

PROLOGUE

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consulter la page de manuel Linux correspondante pour les détails du comportement sous Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

patch — applique les modifications aux fichiers

SYNOPSIS

patch [-blNR] [-c|-e|-n|-u] [-d rép] [-D définition] [-i fichier_patch]
    [-o fichier_sortie] [-p num] [-r fichier_rejet] [fichier]

DESCRIPTION

L'utilitaire patch lit un fichier source (patch) contenant l'une des quatre formes de listes de différences (diff) produites par l'utilitaire diff (contexte normal, contexte copié, contexte unifié, ou dans le style de ed) et applique ces différences à un fichier. Par défaut, patch lit depuis l'entrée standard.

L'utilitaire patch tente de déterminer le type de la liste diff, à moins qu'il ne soit outrepassé par une option -c, -e, -n ou -u.

Si le fichier de patch contient plus d'un patch, patch tente de les appliquer chacun comme s'ils provenaient de fichiers de patch distincts. (Dans ce cas, l'application doit s'assurer que le nom du fichier de patch est déterminable pour chaque liste diff.)

OPTIONS

L'utilitaire patch est conforme aux Définitions de Base du volume POSIX.1‐2017, Section 12.2, Directives de syntaxe utilitaire.

Les options suivantes sont prises en charge :

-b
Sauvegarde une copie du contenu original de chaque fichier modifié, avant l'application des différences, dans un fichier du même nom avec le suffixe .orig ajouté. Si le fichier existe déjà, il sera écrasé ; si plusieurs patchs sont appliqués au même fichier, le fichier .orig ne sera écrit que pour le premier patch. Lorsque l'option -o fichier_sortie est également spécifiée, fichier.orig ne sera pas créé mais, si fichier_sortie existe déjà, fichier_sortie.orig sera créé.
-c
Interprète le fichier de patch comme une différence de contexte copié (la sortie de l'utilitaire diff lorsque les options -c ou -C sont spécifiées).
-d rép
Change le répertoire courant en rép avant le traitement comme décrit dans la section DESCRIPTION ÉTENDUE.
-D définition
Marque les changements avec l'une des constructions du préprocesseur C suivantes :
#ifdef définition
...
#endif
#ifndef définition
...
#endif

éventuellement combiné avec la construction du préprocesseur C #else. Si le fichier patché est traité avec le préprocesseur C, où la macro définition est définie, la sortie contiendra les changements du fichier de patch ; sinon, la sortie ne contiendra pas les patchs spécifiés dans le fichier de patch.

-e
Interprète le fichier de patch comme un script ed, plutôt qu'un script diff.
-i fichier_patch
Lit les informations de patch depuis le fichier nommé par le chemin fichier_patch, plutôt que depuis l'entrée standard.
-l
(La lettre L.) Cause toute séquence de caractères d'espacement dans le script de différence à correspondre à toute séquence de caractères d'espacement dans le fichier d'entrée. Les autres caractères seront mis en correspondance exactement.
-n
Interprète le script comme une différence normale.
-N
Ignore les patchs où les différences ont déjà été appliquées au fichier ; par défaut, les patchs déjà appliqués seront rejetés.
-o fichier_sortie
Au lieu de modifier directement les fichiers (spécifiés par l'opérande fichier ou les listes de différences), écrit une copie du fichier référencé par chaque patch, avec les différences appropriées appliquées, dans fichier_sortie. Plusieurs patchs pour un seul fichier seront appliqués aux versions intermédiaires du fichier créées par les patchs précédents, et entraîneront l'écriture de versions multiples et concaténées du fichier dans fichier_sortie.
-p num
Pour tous les chemins dans le fichier de patch qui indiquent les noms des fichiers à patcher, supprime num composants de chemin du début de chaque chemin. Si le chemin dans le fichier de patch est absolu, tout caractère <slash> de début est considéré comme le premier composant (c'est-à-dire que -p 1 supprimera les caractères <slash> de début). Spécifier -p 0 provoquera l'utilisation du chemin complet. Si -p n'est pas spécifié, seul le nom de base (le dernier composant du chemin) sera utilisé.
-R
Inverse le sens du script de patch ; c'est-à-dire, suppose que le script de différence a été créé de la nouvelle version vers l'ancienne. L'option -R ne peut pas être utilisée avec les scripts ed. L'utilitaire patch tentera d'inverser chaque partie du script avant de l'appliquer. Les différences rejetées seront sauvegardées au format inversé. Si cette option n'est pas spécifiée, et jusqu'à ce qu'une partie du fichier de patch soit appliquée avec succès, patch tente d'appliquer chaque partie dans son sens inversé ainsi que dans son sens normal. Si la tentative réussit, l'utilisateur sera invité à déterminer si l'option -R doit être définie.
-r fichier_rejet
Remplace le nom du fichier de rejet par défaut. Dans le cas par défaut, le fichier de rejet portera le même nom que le fichier de sortie, avec le suffixe .rej ajouté ; voir Application du Patch.
-u
Interprète le fichier de patch comme une différence de contexte unifié (la sortie de l'utilitaire diff lorsque les options -u ou -U sont spécifiées).

OPÉRANDES

L'opérande suivant est pris en charge :

fichier
Un chemin d'accès à un fichier à patcher.

STDIN

Voir la section FICHIERS D'ENTRÉE.

FICHIERS D'ENTRÉE

Les fichiers d'entrée sont des fichiers texte.

VARIABLES D'ENVIRONNEMENT

Les variables d'environnement suivantes affectent l'exécution de patch :

LANG
Fournit une valeur par défaut pour les variables d'internationalisation qui sont non définies ou vides. (Voir le volume Définitions de Base de POSIX.1‐2017, Section 8.2, Variables d'internationalisation pour la priorité des variables d'internationalisation utilisées pour déterminer les valeurs des catégories de locale.)
LC_ALL
Si définie à une chaîne de caractères non vide, remplace les valeurs de toutes les autres variables d'internationalisation.
LC_COLLATE

Détermine la locale pour le comportement des plages, des classes d'équivalence et des éléments de collation multicaractères utilisés dans l'expression régulière étendue définie pour le mot-clé yesexpr de la catégorie LC_MESSAGES.
LC_CTYPE
Détermine la locale pour l'interprétation des séquences d'octets de données textuelles en caractères (par exemple, caractères mono-octet par opposition aux caractères multi-octets dans les arguments et les fichiers d'entrée), et le comportement des classes de caractères utilisées dans l'expression régulière étendue définie pour le mot-clé yesexpr de la catégorie LC_MESSAGES

ÉVÉNEMENTS ASYNCHRONES

Défaut.

STDOUT

Non utilisé.

STDERR

La sortie d'erreur standard sera utilisée pour les messages de diagnostic et d'information.

FICHIERS DE SORTIE

La sortie de l'utilitaire patch, les fichiers de sauvegarde (suffixes .orig) et les fichiers de rejet (suffixes .rej) seront des fichiers texte.

DESCRIPTION ÉTENDUE

Un fichier de patch peut contenir des instructions de patch pour plusieurs fichiers ; les noms de fichiers seront déterminés comme spécifié dans Détermination du nom de fichier. Lorsque l'option -b est spécifiée, pour chaque fichier patché, l'original sera sauvegardé dans un fichier du même nom avec le suffixe .orig ajouté.

Pour chaque fichier patché, un fichier de rejet peut également être créé comme indiqué dans Application du patch. En l'absence de l'option -r, le nom de ce fichier sera formé en ajoutant le suffixe .rej au nom de fichier original.

Format du fichier de patch

Le fichier de patch contiendra zéro ou plusieurs lignes d'informations d'en-tête suivies d'un ou plusieurs patches. Chaque patch contiendra zéro ou plusieurs lignes d'identification de nom de fichier au format produit par les options -c, -C, -u ou -U de l'utilitaire diff, et un ou plusieurs ensembles de sortie diff, qui sont communément appelés hunks.

L'utilitaire patch reconnaîtra l'expression suivante dans les informations d'en-tête :

Index: chemin

Le fichier à patcher est nommé chemin.

Si toutes les lignes (y compris les en-têtes) d'un patch commencent par la même séquence de caractères d'espacement ( <blank>), l'utilitaire patch supprimera cette séquence avant de continuer. Dans chaque patch, si le type de différence est un contexte commun, l'utilitaire patch reconnaîtra les expressions suivantes :

*** nom_fichier horodatage

Les patches proviennent de nom_fichier.
--- nom_fichier horodatage

Les patches doivent être appliqués à nom_fichier.

Si le type de différence est un contexte unifié, l'utilitaire patch reconnaîtra les expressions suivantes :

--- nom_fichier horodatage

Les patches proviennent de nom_fichier.
+++ nom_fichier horodatage

Les patches doivent être appliqués à nom_fichier.

Chaque hunk dans un patch sera la sortie diff pour modifier une plage de lignes dans le fichier original. Les numéros de ligne pour les hunks successifs dans un patch seront dans un ordre croissant.

Détermination du nom de fichier

Si aucun opérande file n'est spécifié, patch effectuera les étapes suivantes pour déterminer le nom de fichier à utiliser :

1.
Si le type de diff est contextuel, l'utilitaire patch supprimera les composants du chemin (comme spécifié par l'option -p) du nom de fichier sur la ligne commençant par "***" (si contexte copié) ou "---" (si contexte unifié), puis testera l'existence de ce fichier par rapport au répertoire courant (ou au répertoire spécifié avec l'option -d). Si le fichier existe, l'utilitaire patch utilisera ce nom de fichier.
2.
Si le type de diff est contextuel, l'utilitaire patch supprimera les composants du chemin (comme spécifié par l'option -p) du nom de fichier sur la ligne commençant par "---" (si contexte copié) ou "+++" (si contexte unifié), puis testera l'existence de ce fichier par rapport au répertoire courant (ou au répertoire spécifié avec l'option -d). Si le fichier existe, l'utilitaire patch utilisera ce nom de fichier.
3.
Si les informations d'en-tête contiennent une ligne commençant par la chaîne Index:, l'utilitaire patch supprimera les composants du chemin (comme spécifié par l'option -p) de cette ligne, puis testera l'existence de ce fichier par rapport au répertoire courant (ou au répertoire spécifié avec l'option -d). Si le fichier existe, l'utilitaire patch utilisera ce nom de fichier.
4.
Si un répertoire SCCS existe dans le répertoire courant, patch tentera d'exécuter la commande get -e SCCS/s.nom_fichier pour récupérer une version éditable du fichier. Si le fichier existe, l'utilitaire patch utilisera ce nom de fichier.
5.
L'utilitaire patch écrira une invite sur la sortie standard et demandera interactivement un nom de fichier au terminal de contrôle (par exemple, /dev/tty).

Application du patch

Si l'option -c, -e, -n ou -u est présente, l'utilitaire patch interprétera les informations de chaque hunk comme une différence de contexte copié, une différence ed, une différence normale ou une différence de contexte unifié, respectivement. En l'absence de l'une de ces options, l'utilitaire patch déterminera le type de différence en fonction du format des informations contenues dans le hunk.

Pour chaque hunk, l'utilitaire patch commencera à rechercher l'emplacement d'application du patch au numéro de ligne au début du hunk, plus ou moins le décalage utilisé pour appliquer le hunk précédent. Si des lignes correspondant au contexte du hunk ne sont pas trouvées, patch recherchera en avant et en arrière sur au moins 1000 octets un ensemble de lignes correspondant au contexte du hunk.

Si aucun emplacement n'est trouvé et qu'il s'agit d'une différence contextuelle, une autre recherche sera effectuée en ignorant la première et la dernière ligne de contexte. Si cela échoue, les deux premières et les deux dernières lignes de contexte seront ignorées et une autre recherche sera effectuée. Les implémentations peuvent effectuer des recherches plus approfondies pour les emplacements d'installation.

Si aucun emplacement ne peut être trouvé, l'utilitaire patch ajoutera le hunk au fichier de rejet. Un hunk rejeté qui est une différence de contexte copié, une différence ed ou une différence normale sera écrit au format différence de contexte copié, quel que soit le format du fichier de patch. Il est défini par l'implémentation si un hunk rejeté qui est une différence de contexte unifié est écrit au format différence de contexte copié ou au format différence de contexte unifié. Si l'entrée était une différence de style normal ou ed, le fichier de rejet peut contenir des différences avec zéro ligne de contexte. Les numéros de ligne des hunks dans le fichier de rejet peuvent différer des numéros de ligne du fichier de patch car ils refléteront les emplacements approximatifs des hunks échoués dans le nouveau fichier plutôt que dans l'ancien.

Si le type de patch est une différence ed, l'implémentation peut effectuer le patching en invoquant l'utilitaire ed.

STATUT DE SORTIE

Les valeurs de sortie suivantes seront retournées :

 0
Achèvement réussi.
 1
Une ou plusieurs lignes ont été écrites dans un fichier de rejet.
>1
Une erreur s'est produite.

CONSÉQUENCES DES ERREURS

Les patchs qui ne peuvent pas être correctement placés dans le fichier seront écrits dans un fichier de rejet.

Les sections suivantes sont informatives.

UTILISATION PAR L'APPLICATION

L'option -R ne fonctionne pas avec les scripts ed car il y a trop peu d'informations pour reconstruire l'opération inverse.

L'option -p permet de personnaliser un fichier de patch pour les structures de répertoires locales des utilisateurs sans modifier manuellement le fichier de patch. Par exemple, si le nom de fichier dans le fichier de patch était :

/curds/whey/src/blurfl/blurfl.c

Définir -p 0 donne le chemin complet non modifié ; -p 1 donne :

curds/whey/src/blurfl/blurfl.c

sans le slash initial, -p 4 donne :

blurfl/blurfl.c

et ne pas spécifier -p du tout donne :

blurfl.c .

Aucun.

RATIONALE

Certaines fonctionnalités des implémentations historiques de patch n'étaient pas spécifiées. Les éléments suivants documentent les fonctionnalités présentes dans les implémentations historiques qui n'ont pas été spécifiées.

Une fonctionnalité supprimée était la pseudo-option '+' permettant de donner un ensemble supplémentaire d'options et un opérande de fichier de patch. Ceci a été considéré comme pas suffisamment utile pour être standardisé.

Dans les implémentations historiques, si la chaîne "Prereq:" apparaissait dans l'en-tête, l'utilitaire patch recherchait les informations de version correspondantes (la chaîne spécifiée dans l'en-tête, délimitée par des caractères d'espacement ( <blank>) ou le début ou la fin d'une ligne ou du fichier) et

ywhere in the original file. This was deleted as too simplistic and insufficiently trustworthy a mechanism to standardize. For example, if:

Prereq: 1.2

were in the header, the presence of a delimited 1.2 anywhere in the file would satisfy the prerequisite.

The following options were dropped from historical implementations of patch as insufficiently useful to standardize:

-b
The -b option historically provided a method for changing the name extension of the backup file from the default .orig. This option has been modified and retained in this volume of POSIX.1‐2017.
-F
The -F option specified the number of lines of a context diff to ignore when searching for a place to install a patch.
-f
The -f option historically caused patch not to request additional information from the user.
-r
The -r option historically provided a method of overriding the extension of the reject file from the default .rej.
-s
The -s option historically caused patch to work silently unless an error occurred.
-x
The -x option historically set internal debugging flags.

In some file system implementations, the saving of a .orig file may produce unwanted results. In the case of 12, 13, or 14-character filenames (on file systems supporting 14-character maximum filenames), the .orig file overwrites the new file. The reject file may also exceed this filename limit. It was suggested, due to some historical practice, that a <tilde> ('~') suffix be used instead of .orig and some other character instead of the .rej suffix. This was rejected because it is not obvious to the user which file is which. The suffixes .orig and .rej are clearer and more understandable.

The -b option has the opposite sense in some historical implementations—do not save the .orig file. The default case here is not to save the files, making patch behave more consistently with the other standard utilities.

The -w option in early proposals was changed to -l to match historical practice.

The -N option was included because without it, a non-interactive application cannot reject previously applied patches. For example, if a user is piping the output of diff into the patch utility, and the user only wants to patch a file to a newer version non-interactively, the -N option is required.

Changes to the -l option description were proposed to allow matching across <newline> characters in addition to just <blank> characters. Since this is not historical practice, and since some ambiguities could result, it is suggested that future developments in this area utilize another option letter, such as -L.

The -u option of GNU patch has been added, along with support for unified context formats.
