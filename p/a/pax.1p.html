PAX(1P) Manuel du programmeur POSIX PAX(1P)

PROLOG

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation de cette interface sous Linux peut différer (consultez la page de manuel Linux correspondante pour les détails sur le comportement sous Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

pax — échange d'archives portable

SYNTAXE

pax [-dv] [-c|-n] [-H|-L] [-o options] [-f archive] [-s replstr]...
    [motif...]
pax -r[-c|-n] [-dikuv] [-H|-L] [-f archive] [-o options]... [-p chaîne]...
    [-s replstr]... [motif...]
pax -w [-dituvX] [-H|-L] [-b taille_bloc] [[-a] [-f archive]] [-o options]...
    [-s replstr]... [-x format] [fichier...]
pax -r -w [-diklntuvX] [-H|-L] [-o options]... [-p chaîne]...
    [-s replstr]... [fichier...] répertoire

DESCRIPTION

L'utilitaire pax lit, écrit et liste les membres de fichiers d'archives, et copie des hiérarchies de répertoires. Une variété de formats d'archives est prise en charge ; voir l'option -x format.

L'action à entreprendre dépend de la présence des options -r et -w. Les quatre combinaisons de -r et -w sont appelées les quatre modes de fonctionnement : modes liste, lecture, écriture et copie, correspondant respectivement aux quatre formes présentées dans la section SYNTAXE.

liste
En mode liste (lorsque ni -r ni -w ne sont spécifiés), pax écrit les noms des membres du fichier archive lus depuis l'entrée standard, avec les chemins correspondant aux motifs spécifiés, vers la sortie standard. Si un fichier nommé est de type répertoire, la hiérarchie de fichiers racinée à ce fichier est également listée.
lecture
En mode lecture (lorsque -r est spécifié, mais -w ne l'est pas), pax extrait les membres du fichier archive lus depuis l'entrée standard, avec les chemins correspondant aux motifs spécifiés. Si un fichier extrait est de type répertoire, la hiérarchie de fichiers racinée à ce fichier est également extraite. Les fichiers extraits sont créés en résolvant les chemins par rapport au répertoire dans lequel pax a été invoqué comme répertoire de travail courant.

Si une tentative est faite pour extraire un répertoire alors que le répertoire existe déjà, cela n'est pas considéré comme une erreur. Si une tentative est faite pour extraire un FIFO alors que le FIFO existe déjà, cela n'est pas considéré comme une erreur.

La propriété, les temps d'accès et de modification, et le mode de fichier des fichiers restaurés sont discutés sous l'option -p.

écriture
En mode écriture (lorsque -w est spécifié, mais -r ne l'est pas), pax écrit le contenu des opérandes fichier dans la sortie standard dans un format d'archive. Si aucun opérande fichier n'est spécifié, une liste de fichiers à copier, un par ligne, est lue depuis l'entrée standard et chaque entrée de cette liste est traitée comme si elle avait été un opérande fichier sur la ligne de commande. Un fichier de type répertoire inclut tous les fichiers de la hiérarchie de fichiers racinée au fichier.
copie
En mode copie (lorsque -r et -w sont spécifiés), pax copie les opérandes fichier dans le répertoire de destination.

Si aucun opérande fichier n'est spécifié, une liste de fichiers à copier, un par ligne, est lue depuis l'entrée standard. Un fichier de type répertoire inclut tous les fichiers de la hiérarchie de fichiers racinée au fichier.

L'effet de la copie est comme si les fichiers copiés étaient écrits dans un fichier d'archive au format pax puis ultérieurement extraits, sauf que la copie des sockets peut être prise en charge même si leur archivage en mode écriture ne l'est pas, et qu'il peut y avoir des liens matériels entre les fichiers d'origine et les fichiers copiés. Si le répertoire de destination est un sous-répertoire de l'un des fichiers à copier, les résultats sont indéterminés. Si le répertoire de destination est un fichier d'un type non défini par le volume Interfaces système de POSIX.1‐2017, les résultats sont définis par l'implémentation ; sinon, il sera une erreur que le fichier nommé par l'opérande répertoire n'existe pas, ne soit pas inscriptible par l'utilisateur, ou ne soit pas un fichier de type répertoire.

En modes lecture ou copie, si des répertoires intermédiaires sont nécessaires pour extraire un membre d'archive, pax effectue des actions équivalentes à la fonction mkdir() définie dans le volume Interfaces système de POSIX.1‐2017, appelée avec les arguments suivants :

*
Le répertoire intermédiaire utilisé comme argument chemin
*
La valeur du OU logique inclusif de S_IRWXU, S_IRWXG et S_IRWXO comme argument mode

Si un motif ou des opérandes fichier spécifiés ne correspondent à aucun fichier ou membre d'archive, pax écrit un message de diagnostic sur la sortie d'erreur standard pour chacun de ceux qui n'ont pas correspondu et se termine avec un statut de sortie non nul.

Les formats d'archive décrits dans la section DESCRIPTION EXTENDUE sont automatiquement détectés à l'entrée. Le format d'archive de sortie par défaut est indéfini par l'implémentation.

Une seule archive peut s'étendre sur plusieurs fichiers. L'utilitaire pax détermine, d'une manière définie par l'implémentation, quel fichier lire ou écrire comme prochain fichier.

Si le format d'archive sélectionné prend en charge la spécification de fichiers liés, il sera une erreur si ces fichiers ne peuvent pas être liés lors de l'extraction de l'archive. Pour les formats d'archive qui ne stockent pas le contenu des fichiers avec chaque nom qui provoque un lien matériel, si le fichier contenant les données n'est pas extrait pendant cette session pax, soit les données seront restaurées à partir du fichier d'origine, soit un message de diagnostic sera affiché avec le nom d'un fichier pouvant être utilisé pour extraire les données. En parcourant les répertoires, pax détecte les boucles infinies ; c'est-à-dire entrer dans un répertoire précédemment visité qui est un ancêtre du dernier fichier visité. Lorsqu'il détecte une boucle infinie, pax écrit un message de diagnostic sur la sortie d'erreur standard et se termine.

OPTIONS

L'utilitaire pax est conforme aux définitions de base du volume POSIX.1‐2017, Section 12.2, Directives de syntaxe de l'utilitaire, sauf que l'ordre de présentation des options -o, -p et -s est significatif.

Les options suivantes sont prises en charge :

-r
Lit un fichier archive depuis l'entrée standard.
-w
Écrit les fichiers dans la sortie standard dans le format d'archive spécifié.
-a
Ajoute des fichiers à la fin de l'archive. Il est indéfini par l'implémentation quels périphériques du système prennent en charge l'ajout. Des formats de fichiers supplémentaires non spécifiés par ce volume de POSIX.1‐2017 peuvent imposer des restrictions sur l'ajout.
-b taille_bloc
Blocage de la sortie à un nombre décimal positif d'octets par écriture dans le fichier archive. Les périphériques et les formats d'archive peuvent imposer des restrictions sur le blocage. Le blocage est automatiquement déterminé à l'entrée. Les applications conformes ne doivent pas spécifier une valeur taille_bloc supérieure à 32256. Le blocage par défaut lors de la création d'archives dépend du format d'archive. (Voir l'option -x ci-dessous.)
-c
Correspond à tous les fichiers ou membres d'archive, sauf ceux spécifiés par les opérandes motif ou fichier.
-d
Fait en sorte que les fichiers de type répertoire en cours de copie ou d'archivage, ou les membres d'archive de type répertoire en cours d'extraction ou de listage, ne correspondent qu'au fichier ou au membre d'archive lui-même et non à la hiérarchie de fichiers racinée au fichier.
-f
="#f">-f archive
Spécifie le chemin du fichier archive d'entrée ou de sortie, remplaçant l'entrée standard par défaut (dans les modes list ou read) ou la sortie standard (mode write).
-H
Si un lien symbolique référençant un fichier de type répertoire est spécifié sur la ligne de commande, pax doit archiver la hiérarchie de fichiers racinée dans le fichier référencé par le lien, en utilisant le nom du lien comme racine de la hiérarchie de fichiers. Sinon, si un lien symbolique référençant un fichier de tout autre type de fichier que pax peut normalement archiver est spécifié sur la ligne de commande, alors pax doit archiver le fichier référencé par le lien, en utilisant le nom du lien. Le comportement par défaut, lorsque ni -H ni -L ne sont spécifiés, est d'archiver le lien symbolique lui-même.
-i
Renommer interactivement les fichiers ou les membres de l'archive. Pour chaque membre de l'archive correspondant à un opérande pattern ou fichier correspondant à un opérande file, une invite sera écrite sur le fichier /dev/tty. L'invite contiendra le nom du fichier ou du membre de l'archive, mais le format n'est pas spécifié autrement. Une ligne sera alors lue depuis /dev/tty. Si cette ligne est vide, le fichier ou le membre de l'archive sera ignoré. Si cette ligne consiste en un seul point, le fichier ou le membre de l'archive sera traité sans modification de son nom. Sinon, son nom sera remplacé par le contenu de la ligne. L'utilitaire pax quittera immédiatement avec un statut de sortie non nul si la fin de fichier est rencontrée lors de la lecture d'une réponse ou si /dev/tty ne peut pas être ouvert en lecture et écriture.

Les résultats de l'extraction d'un lien physique vers un fichier qui a été renommé pendant l'extraction ne sont pas spécifiés.

-k
Empêcher l'écrasement des fichiers existants.
-l
(La lettre ell.) En mode copy, des liens physiques seront créés entre les hiérarchies de fichiers source et destination lorsque cela est possible. Si spécifié conjointement avec -H ou -L, lorsqu'un lien symbolique est rencontré, le lien physique créé dans la hiérarchie de fichiers de destination sera un lien vers le fichier référencé par le lien symbolique. Si spécifié lorsque ni -H ni -L ne sont spécifiés, lorsqu'un lien symbolique est rencontré, l'implémentation doit créer un lien physique vers le lien symbolique dans la hiérarchie de fichiers source ou copier le lien symbolique vers la destination.
-L
Si un lien symbolique référençant un fichier de type répertoire est spécifié sur la ligne de commande ou rencontré lors du parcours d'une hiérarchie de fichiers, pax doit archiver la hiérarchie de fichiers enracinée dans le fichier référencé par le lien, en utilisant le nom du lien comme racine de la hiérarchie de fichiers. Sinon, si un lien symbolique référençant un fichier de tout autre type de fichier que pax peut normalement archiver est spécifié sur la ligne de commande ou rencontré lors du parcours d'une hiérarchie de fichiers, pax doit archiver le fichier référencé par le lien, en utilisant le nom du lien. Le comportement par défaut, lorsque ni -H ni -L ne sont spécifiés, est d'archiver le lien symbolique lui-même.
-n
Sélectionne le premier membre de l'archive qui correspond à chaque opérande pattern. Pas plus d'un membre d'archive ne doit être trouvé pour chaque modèle (bien que les membres de type répertoire correspondent toujours à la hiérarchie de fichiers enracinée à ce fichier).
-o options
Fournit des informations à l'implémentation pour modifier l'algorithme d'extraction ou d'écriture des fichiers. La valeur de options doit consister en un ou plusieurs mots-clés séparés par une <virgule> de la forme :
mot-clé[[:]=valeur][,mot-clé[[:]=valeur], ...]

Certains mots-clés ne s'appliquent qu'à certains formats de fichiers, comme indiqué pour chaque description. L'utilisation de mots-clés inapplicables au format de fichier traité produit des résultats indéfinis.

Les mots-clés dans l'opérande options doivent être une chaîne qui serait un nom de fichier portable valide tel que décrit dans le volume Base Definitions de POSIX.1‐2017, Section 3.282, Portable Filename Character Set.

Note :
Les mots-clés ne sont pas censés être des noms de fichiers, mais seulement suivre les mêmes règles de composition de caractères que les noms de fichiers portables.

Les mots-clés peuvent être précédés d'un espace blanc. Le champ valeur doit consister en zéro caractère ou plus ; dans valeur, l'application doit précéder toute <virgule> littérale d'une <barre oblique inverse>, qui sera ignorée, mais qui préserve la <virgule> comme faisant partie de valeur. Une <virgule> comme caractère final, ou une <virgule> suivie uniquement d'un espace blanc comme caractères finaux, dans options sera ignorée. Plusieurs options -o peuvent être spécifiées ; si les mots-clés donnés à ces options multiples -o entrent en conflit, les mots-clés et valeurs apparaissant plus tard dans la séquence de ligne de commande auront la priorité et les précédents seront silencieusement ignorés. Les valeurs de mots-clés suivantes de options doivent être supportées pour les formats de fichiers comme indiqué :

delete=motif

(Applicable uniquement au format -x pax.) Lorsqu'il est utilisé en mode write ou copy, pax omettra des enregistrements d'en-tête étendus qu'il produit tous les mots-clés correspondant au motif de chaîne. Lorsqu'il est utilisé en mode read ou list, pax ignorera tous les mots-clés correspondant au motif de chaîne dans les enregistrements d'en-tête étendus. Dans les deux cas, la correspondance sera effectuée en utilisant la notation de correspondance de motif décrite dans la Section 2.13.1, Patterns Matching a Single Character et la Section 2.13.2, Patterns Matching Multiple Characters. Par exemple :
-o delete=security.*

supprimerait les informations relatives à la sécurité. Voir pax Extended Header pour l'utilisation des mots-clés des enregistrements d'en-tête étendus.

Lorsque plusieurs options -odelete=motif sont spécifiées, les motifs sont additifs ; tous les mots-clés correspondant aux motifs de chaîne spécifiés seront omis des enregistrements d'en-tête étendus que pax produit.

exthdr.name=chaîne

(Applicable uniquement au format -x pax.) Ce mot-clé permet à l'utilisateur de contrôler le nom qui est écrit dans les blocs d'en-tête ustar pour l'en-tête étendu produit dans les circonstances décrites dans pax Header Block. Le nom sera le contenu de chaîne, après que les substitutions de caractères suivantes aient été effectuées :
chaîne
Comprend : Remplacé par :
%d Le nom du répertoire du fichier, équivalent au résultat de l'utilitaire dirname sur le chemin traduit.
%f Le nom du fichier, équivalent au résultat de l'utilitaire basename sur le chemin traduit.
%p L'identifiant du processus de pax.
%% Un caractère '%'.

Tout autre caractère '%' dans chaîne produit des résultats indéfinis.

Si aucune option -o exthdr.name=chaîne n'est spécifiée, pax utilisera la valeur par défaut suivante :

%d/PaxHeaders.%p/%f
globexthdr.name=chaîne

(Applicable uniquement au format -x pax.) Lorsqu'il est utilisé en mode write ou copy avec les options appropriées, pax créera des enregistrements d'en-tête globaux étendus avec des blocs d'en-tête ustar qui seront traités comme des fichiers ordinaires par les versions précédentes de pax. Ce mot-clé permet à l'utilisateur de contrôler le nom qui est écrit dans les blocs d'en-tête ustar pour les enregistrements d'en-tête globaux étendus. Le nom sera le contenu de chaîne, après que les substitutions de caractères suivantes aient été effectuées :
chaîne
Comprend : Remplacé par :
%n Un entier qui représente le numéro de séquence de l'enregistrement d'en-tête global étendu dans l'archive, commençant à 1.
%p L'identifiant du processus de pax.
%% Un caractère '%'.

Tout autre caractère '%' dans chaîne produit des résultats indéfinis.

Si aucune option -o globexthdr.name=chaîne n'est spécifiée, pax utilisera la valeur par défaut suivante :

$TMPDIR/GlobalHead.%p.%n

où $TMPDIR représente la valeur de la variable d'environnement TMPDIR. Si TMPDIR n'est pas défini, pax utilisera /tmp.

invalid=action

(Applicable uniquement au format -x pax.) Ce mot-clé permet à l'utilisateur de contrôler l'action que pax entreprend lorsqu'il rencontre des valeurs dans un enregistrement d'en-tête étendu qui, en mode read ou copy, sont invalides dans la hiérarchie de destination ou, en mode list, ne peuvent pas être écrites dans le jeu de codes et la locale actuelle de l'implémentation. Les valeurs invalides suivantes doivent être reconnues par pax :
--
En mode lecture ou copie, un nom de fichier ou de lien contenant des encodages de caractères invalides dans la hiérarchie de destination. (Par exemple, le nom peut contenir des NUL incorporés.)
--
En mode lecture ou copie, un nom de fichier ou de lien plus long que le maximum autorisé dans la hiérarchie de destination (pour un composant de chemin ou le chemin entier).
--
En mode liste, toute valeur de chaîne de caractères (nom de fichier, nom de lien, nom d'utilisateur, etc.) qui ne peut pas être écrite dans le jeu de codes et la locale actuelle de l'implémentation.

Les valeurs mutuellement exclusives suivantes de l'argument action sont prises en charge :

binary
En mode écriture, pax génère un enregistrement d'en-tête étendu hdrcharset=BINARY pour chaque fichier dont le nom de fichier, le nom de lien, le nom de groupe, le nom d'utilisateur ou tout autre champ d'un enregistrement d'en-tête étendu ne peut pas être traduit dans le jeu de codes UTF‐8, permettant à l'archive de contenir les fichiers avec des valeurs d'en-tête étendues non encodées. En mode lecture ou copie, pax utilise les valeurs spécifiées dans l'en-tête sans traduction, quelle que soit la possibilité d'écraser un fichier existant avec un nom valide. En mode liste, pax se comporte de manière identique à l'action bypass.
bypass
En mode lecture ou copie, pax contourne le fichier, ne provoquant aucun changement dans la hiérarchie de destination. En mode liste, pax écrit toutes les valeurs valides demandées pour le fichier, mais sa méthode d'écriture des valeurs invalides n'est pas spécifiée.
rename
En mode lecture ou copie, pax agit comme si l'option -i était activée pour chaque fichier avec des noms de fichiers ou de liens invalides, permettant à l'utilisateur de fournir un nouveau nom de manière interactive. En mode liste, pax se comporte de manière identique à l'action bypass.
UTF‐8
Lorsqu'il est utilisé en mode lecture, copie ou liste et qu'un nom de fichier, un nom de lien, un nom d'utilisateur ou tout autre champ d'un enregistrement d'en-tête étendu ne peut pas être traduit du format du jeu de codes pax UTF‐8 vers le jeu de codes et la locale actuelle de l'implémentation, pax utilise l'encodage UTF‐8 réel pour le nom. Si un enregistrement d'en-tête étendu hdrcharset est actif pour ce fichier, le jeu de caractères spécifié par cet enregistrement est utilisé à la place de UTF‐8. Si un enregistrement d'en-tête étendu hdrcharset=BINARY est actif pour ce fichier, aucune traduction n'est effectuée.
write
En mode lecture ou copie, pax écrit le fichier, en traduisant le nom, quelle que soit la possibilité d'écraser un fichier existant avec un nom valide. En mode liste, pax se comporte de manière identique à l'action bypass.

Si aucune option -o invalid=option n'est spécifiée, pax agit comme si -oinvalid=bypass était spécifié. Tout écrasement de fichiers existants autorisé par les actions -oinvalid= est soumis aux restrictions de permissions (-p) et de temps de modification (-u), et est supprimé si l'option -k est également spécifiée.

linkdata

(Applicable uniquement au format -x pax.) En mode écriture, pax écrit le contenu d'un fichier dans l'archive même lorsque ce fichier n'est qu'un lien physique vers un fichier dont le contenu a déjà été écrit dans l'archive.
listopt=format

Ce mot-clé spécifie le format de sortie de la table des matières produite lorsque l'option -v est spécifiée en mode liste. Voir Spécifications de format pour le mode liste. Pour éviter toute ambiguïté, listopt=format doit être la seule ou la dernière paire mot-clé=valeur dans un argument d'option -o ; tous les caractères du reste de l'argument d'option sont considérés comme faisant partie de la chaîne de format. Lorsque plusieurs options -olistopt=format sont spécifiées, les chaînes de format sont considérées comme une seule chaîne concaténée, évaluée dans l'ordre de la ligne de commande.
times

(Applicable uniquement au format pax -x.) Lors de son utilisation en mode écriture ou copie, pax inclut des enregistrements d'en-tête étendus atime et mtime pour chaque fichier. Voir Horodatages étendus de pax.

En plus de ces mots-clés, si le format pax -x est spécifié, n'importe lequel des mots-clés et valeurs définis dans En-tête étendu de pax, y compris les extensions d'implémentation, peut être utilisé dans les arguments d'option -o, dans l'un des deux modes suivants :

keyword=value

Lorsqu'ils sont utilisés en mode écriture ou copie, ces paires mot-clé/valeur sont incluses au début de l'archive sous forme d'enregistrements d'en-tête étendus globaux de typeflag g. Lors de leur utilisation en mode lecture ou liste, ces paires mot-clé/valeur agissent comme si elles avaient été au début de l'archive sous forme d'enregistrements d'en-tête étendus globaux de typeflag g.
keyword:=value

Lorsqu'ils sont utilisés en mode écriture ou copie, ces paires mot-clé/valeur sont incluses sous forme d'enregistrements au début d'un en-tête étendu de typeflag x pour chaque fichier. (Cela est équivalent à la forme <signe-égal> sauf que cela ne crée pas d'enregistrements d'en-tête étendus globaux typeflag g.) Lors de leur utilisation en mode lecture ou liste, ces paires mot-clé/valeur agissent comme si elles étaient incluses en tant qu'enregistrements à la fin de chaque en-tête étendu ; ainsi, elles remplacent tout mot-clé d'en-tête étendu global ou spécifique au fichier portant le même nom. Par exemple, dans la commande :
pax -r -o "
gname:=mygroup,
" <archive

le nom du groupe sera forcé à une nouvelle valeur pour tous les fichiers lus de l'archive.

La précédence des mots-clés -o sur divers champs de l'archive est décrite dans Précédence des mots-clés d'en-tête étendu de pax. Si les options -o delete=pattern, -o keyword=value, ou -o keyword:=value sont utilisées pour remplacer ou supprimer des données d'en-tête étendues nécessaires à la recherche de fichiers dans une archive (par exemple, -o delete=size pour un fichier dont la taille ne peut pas être représentée dans un en-tête ustar ou -o size=100 pour un fichier dont la taille n'est pas de 100 octets), le comportement est indéfini.

-p string
Spécifie une ou plusieurs options de caractéristiques de fichier (privilèges). L'argument d'option string est une chaîne spécifiant les caractéristiques de fichier à conserver ou à supprimer lors de l'extraction. La chaîne doit être composée des caractères de spécification a, e, m, o et p. D'autres caractères définis par l'implémentation peuvent être inclus. Plusieurs caractéristiques peuvent être concaténées dans la même chaîne et plusieurs options -p peuvent être spécifiées. La signification des caractères de spécification est la suivante :
a
Ne pas préserver les temps d'accès aux fichiers.
e
Préserver l'identifiant utilisateur, l'identifiant de groupe, les bits de mode de fichier (voir le volume Base Definitions de POSIX.1‐2017, Section 3.169, Bits de mode de fichier), le temps d'accès, le temps de modification et toute autre caractéristique de fichier définie par l'implémentation.
m
Ne pas préserver les temps de modification des fichiers.
o
Préserver l'identifiant utilisateur et l'identifiant de groupe.
p
Préserver les bits de mode de fichier. D'autres attributs de mode de fichier définis par l'implémentation peuvent être préservés.

Dans la liste précédente, « préserver » indique qu'un attribut stocké dans l'archive sera appliqué au fichier extrait, sous réserve des permissions du processus appelant. Les temps d'accès et de modification du fichier seront préservés sauf indication contraire avec l'option -p ou s'ils ne sont pas stockés dans l'archive. Tous les attributs qui ne sont pas préservés seront déterminés dans le cadre de l'action normale de création de fichier (voir Section 1.1.1.4, Lecture, écriture et création de fichiers).

Si ni le caractère de spécification e ni le caractère o n'est spécifié, ou si l'identifiant utilisateur et l'identifiant de groupe ne sont pas préservés pour quelque raison que ce soit, pax ne définira pas les bits S_ISUID et S_ISGID du mode de fichier.

Si la préservation de l'un de ces éléments échoue pour quelque raison que ce soit, pax écrira un message de diagnostic sur la sortie d'erreur standard. L'échec de la préservation de ces éléments affectera le statut de sortie final, mais n'entraînera pas la suppression du fichier extrait.

Si des lettres de caractéristiques de fichier dans l'un des arguments d'option string sont dupliquées ou entrent en conflit les unes avec les autres, celles qui sont données en dernier prennent le dessus. Par exemple, si -p eme est spécifié, les temps de modification des fichiers sont préservés.

-s replstr
Modifie les noms de fichiers ou de membres d'archive nommés par les opérandes pattern ou file selon l'expression de substitution replstr, en utilisant la syntaxe de l'utilitaire ed. Les concepts d'"adresse" et de "ligne" n'ont pas de sens dans le contexte de l'utilitaire pax et ne doivent pas être fournis. Le format sera :
-s /ancien/nouveau/[gp]

où, comme dans ed, ancien est une expression régulière de base et nouveau peut contenir un <esperluette>, des références arrière '\n' (où n est un chiffre) ou une correspondance de sous-expression. La chaîne ancien pourra également contenir des caractères <nouvelle ligne>.

Tout caractère non nul peut être utilisé comme délimiteur ('/' indiqué ici). Plusieurs expressions -s peuvent être spécifiées ; les expressions seront appliquées dans l'ordre spécifié, en terminant par la première substitution réussie. Le 'g' final optionnel est tel que défini dans l'utilitaire ed. Le 'p' final optionnel s'appliquera cause les substitutions réussies à être écrites dans la sortie d'erreur standard. Les noms de fichiers ou de membres d'archive qui se substituent à une chaîne vide seront ignorés lors de la lecture et de l'écriture des archives.

-t
Lors de la lecture de fichiers à partir du système de fichiers, et si l'utilisateur dispose des autorisations requises par utime() pour le faire, définit l'heure d'accès de chaque fichier lu à l'heure d'accès qu'il avait avant d'être lu par pax.
-u
Ignore les fichiers qui sont plus anciens (ayant une heure de modification de fichier moins récente) qu'un fichier ou membre d'archive préexistant portant le même nom. En mode lecture, un membre d'archive portant le même nom qu'un fichier dans le système de fichiers sera extrait si le membre d'archive est plus récent que le fichier. En mode écriture, un membre de fichier d'archive portant le même nom qu'un fichier dans le système de fichiers sera remplacé si le fichier est plus récent que le membre d'archive. Si -a est également spécifié, cela est accompli en ajoutant à l'archive; sinon, il n'est pas précisé si cela est accompli par un remplacement réel dans l'archive ou par ajout à l'archive. En mode copie, le fichier dans la hiérarchie de destination sera remplacé par le fichier dans la hiérarchie source ou par un lien vers le fichier dans la hiérarchie source si le fichier dans la hiérarchie source est plus récent.
-v
En mode liste, produit une table des matières détaillée (voir la section STDOUT). Sinon, écrit les noms de chemin des membres d'archive dans la sortie d'erreur standard (voir la section STDERR).
-x format
Spécifie le format de l'archive de sortie. L'utilitaire pax prendra en charge les formats suivants :
cpio
Le format d'échange cpio ; voir la section DESCRIPTION ÉTENDUE. La taille de bloc blocksize par défaut pour ce format pour les fichiers d'archive spéciaux de caractères sera de 5120. Les implémentations prendront en charge toutes les valeurs de blocksize inférieures ou égales à 32256 qui sont des multiples de 512.
pax
Le format d'échange pax ; voir la section DESCRIPTION ÉTENDUE. La taille de bloc blocksize par défaut pour ce format pour les fichiers d'archive spéciaux de caractères sera de 5120. Les implémentations prendront en charge toutes les valeurs de blocksize inférieures ou égales à 32256 qui sont des multiples de 512.
ustar
Le format d'échange tar ; voir la section DESCRIPTION ÉTENDUE. La taille de bloc blocksize par défaut pour ce format pour les fichiers d'archive spéciaux de caractères sera de 10240. Les implémentations prendront en charge toutes les valeurs de blocksize inférieures ou égales à 32256 qui sont des multiples de 512.

Les formats définis par l'implémentation spécifieront une taille de bloc par défaut ainsi que toutes les autres tailles de bloc prises en charge pour les fichiers d'archive spéciaux de caractères.

Toute tentative d'ajout à un fichier d'archive dans un format différent du format d'archive existant provoquera la sortie immédiate de pax avec un statut de sortie non nul.

-X
Lors de la traversée de la hiérarchie de fichiers spécifiée par un nom de chemin, pax ne descendra pas dans les répertoires qui ont un identifiant de périphérique différent (st_dev ; voir le volume Interfaces système de POSIX.1-2017, stat()).

La spécification de plusieurs options mutuellement exclusives -H et -L ne sera pas considérée comme une erreur et la dernière option spécifiée déterminera le comportement de l'utilitaire.

Les options qui opèrent sur les noms de fichiers ou de membres d'archive (-c, -i, -n, -s, -u et -v) interagiront comme suit. En mode lecture, les membres d'archive seront sélectionnés en fonction des opérandes pattern spécifiés par l'utilisateur, tels que modifiés par les options -c, -n et -u. Ensuite, toutes les options -s et -i modifieront, dans cet ordre, les noms des fichiers sélectionnés. L'option -v écrira les noms résultant de ces modifications.

En mode écriture, les fichiers seront sélectionnés en fonction des noms de chemin spécifiés par l'utilisateur, tels que modifiés par les options -n et -u. Ensuite, toutes les options -s et -i modifieront, dans cet ordre, les noms de ces fichiers sélectionnés. L'option -v écrira les noms résultant de ces modifications.

Si les options -u et -n sont toutes deux spécifiées, pax ne considérera pas un fichier comme sélectionné à moins qu'il ne soit plus récent que le fichier auquel il est comparé.

Une archive pax, sur bande ou fichier, produite au format -xpax contiendra une série de blocs. La disposition physique de l'archive sera identique au format ustar décrit dans Format d'échange ustar. Chaque fichier archivé sera représenté par la séquence suivante :

*
Un bloc d'en-tête optionnel avec des enregistrements d'en-tête étendus. Ce bloc d'en-tête est de la forme décrite dans Bloc d'en-tête pax, avec une valeur typeflag de x ou g. Les enregistrements d'en-tête étendus, décrits dans En-tête étendu pax, seront inclus comme données pour ce bloc d'en-tête.

Un bloc d'en-tête qui décrit le fichier. Tous les champs de l'en-tête étendu optionnel précédent remplaceront les champs associés dans ce bloc d'en-tête pour ce fichier.

Zéro ou plusieurs blocs contenant le contenu du fichier.

Un en-tête étendu pax contient des valeurs inappropriées pour le bloc d'en-tête ustar en raison des limitations de ce format : champs nécessitant un encodage de caractères autre que celui décrit dans la norme ISO/IEC 646:1991, champs représentant des attributs de fichier non décrits dans l'en-tête ustar, et champs dont le format ou la longueur ne correspondent pas aux exigences de l'en-tête ustar. Un en-tête étendu doit être composé d'un ou plusieurs enregistrements, chacun construit comme suit :

"%d %s=%s\n", <longueur>, <mot-clé>, <valeur>

Les enregistrements d'en-tête étendu doivent être encodés selon la norme ISO/IEC 10646‐1:2000, encodage UTF‐8. Le champ <longueur>, l'<espace>, le <signe égal> et le <saut de ligne> affichés doivent être limités à l'ensemble de caractères portable, tel qu'encodé en UTF‐8. Les champs <mot-clé> peuvent être n'importe quels caractères UTF‐8. Le champ <longueur> doit être la longueur décimale de l'enregistrement d'en-tête étendu en octets, y compris le <saut de ligne> final. S'il y a un en-tête étendu hdrcharset en vigueur pour un fichier, le champ valeur pour tous les enregistrements d'en-tête étendu gname, linkpath, path et uname doit être encodé en utilisant l'ensemble de caractères spécifié par l'enregistrement d'en-tête étendu hdrcharset ; sinon, le champ valeur doit être encodé en utilisant UTF‐8. Le champ valeur pour tous les autres mots-clés spécifiés par POSIX.1‐2008 doit être encodé en utilisant UTF‐8.

Cette section décrit la priorité selon laquelle les divers enregistrements et champs d'en-tête ainsi que les options de ligne de commande sont sélectionnés pour s'appliquer à un fichier dans l'archive. 1.

2.
Si -omot_clé:= est utilisé, les attributs affectés seront ignorés.
3.
Si -omot_clé:=valeur est utilisé, l'attribut affecté recevra la valeur.

Temps de fichiers des en-têtes étendus pax

L'utilitaire pax écrira un enregistrement mtime pour chaque fichier en mode write (écriture) ou copy (copie) si l'heure de modification du fichier ne peut pas être représentée exactement dans l'enregistrement logique d'en-tête ustar décrit dans le Format d'échange ustar. Cela peut se produire si l'heure est hors de la plage ustar, ou si le système de fichiers de l'implémentation sous-jacente prend en charge des granularités temporelles non entières et que l'heure n'est pas un entier. Tous ces enregistrements temporels seront formatés comme une représentation décimale du temps en secondes depuis l'Epoch. Si un caractère de point décimal <période> ('.') est présent, les chiffres à droite du point représenteront les unités d'une granularité temporelle sous-seconde, où le premier chiffre est les dixièmes de seconde et chaque chiffre suivant est un dixième du chiffre précédent. En mode read (lecture) ou copy (copie), l'utilitaire pax tronquera l'heure d'un fichier à la plus grande valeur qui n'est pas supérieure à l'heure de fichier de l'en-tête d'entrée. En mode write (écriture) ou copy (copie), l'utilitaire pax affichera une heure exactement si elle peut être représentée exactement comme un nombre décimal, et sinon, il générera suffisamment de chiffres pour que la même heure soit récupérée si le fichier est extrait sur un système dont l'implémentation sous-jacente prend en charge la même granularité temporelle.

Format d'échange ustar

Une bande ou un fichier d'archive ustar contiendra une série d'enregistrements logiques. Chaque enregistrement logique sera un enregistrement logique de taille fixe de 512 octets (voir ci-dessous). Bien que ce format puisse être considéré comme étant stocké sur une bande magnétique standard de l'industrie à 9 pistes de 12,7 mm (0,5 pouce), d'autres types de supports transportables ne sont pas exclus. Chaque fichier archivé sera représenté par un enregistrement logique d'en-tête qui décrit le fichier, suivi de zéro ou plusieurs enregistrements logiques qui donnent le contenu du fichier. À la fin du fichier d'archive, il y aura deux enregistrements logiques de 512 octets remplis de zéros binaires, interprétés comme un indicateur de fin d'archive.

Les enregistrements logiques peuvent être groupés pour des opérations d'E/S physiques, comme décrit dans les options -btaille_bloc et -x ustar. Chaque groupe d'enregistrements logiques peut être écrit avec une seule opération équivalente à la fonction write(). Sur une bande magnétique, le résultat de cette écriture sera un seul bloc physique de bande. Le dernier bloc physique sera toujours de taille complète, de sorte que les enregistrements logiques après les deux enregistrements logiques zéro peuvent contenir des données indéfinies.

Tous les caractères de l'enregistrement logique d'en-tête doivent être représentés dans le jeu de caractères codés de la norme ISO/IEC 646:1991. Pour une portabilité maximale entre les implémentations, les noms doivent être sélectionnés parmi les caractères représentés par le jeu de caractères de nom de fichier portable sous forme d'octets avec le bit le plus significatif à zéro. L'utilitaire pax peut choisir d'ignorer ces fichiers tant qu'il produit une erreur indiquant que le fichier est ignoré.

Chaque champ de l'enregistrement logique d'en-tête est contigu; c'est-à-dire qu'il n'y a pas de remplissage utilisé. Chaque caractère sur le support d'archivage doit être stocké de manière contiguë.

Les champs magic, uname et gname sont des chaînes de caractères terminées chacune par un caractère NUL. Les champs name, linkname et prefix sont des chaînes de caractères terminées par NUL, sauf lorsque tous les caractères du tableau contiennent des caractères non-NUL, y compris le dernier caractère. Le champ version est constitué de deux octets contenant les caractères **"00"** (zéro-zéro). Le champ typeflag contient un seul caractère. Tous les autres champs sont des nombres octaux remplis de zéros en tête, utilisant les chiffres de la norme ISO/IEC 646:1991 IRV. Chaque champ numérique est terminé par un ou plusieurs caractères <space> ou NUL.

Les champs name et prefix doivent produire le chemin du fichier. Un nouveau chemin doit être formé, si prefix n'est pas une chaîne vide (son premier caractère n'est pas NUL), en concaténant prefix (jusqu'au premier caractère NUL), un caractère <slash>, et name; sinon, name est utilisé seul. Dans les deux cas, name est terminé au premier caractère NUL. Si prefix commence par un caractère NUL, il est ignoré. De cette manière, des chemins allant jusqu'à 256 caractères peuvent être pris en charge. Si un chemin ne rentre pas dans l'espace prévu, pax doit informer l'utilisateur de l'erreur et ne doit stocker aucune partie du fichier - en-tête ou données - sur le support.

Le champ linkname, décrit ci-dessous, ne doit pas utiliser le prefix pour produire un chemin. Ainsi, un linkname est limité à 100 caractères. Si le nom ne rentre pas dans l'espace prévu, pax doit informer l'utilisateur de l'erreur et ne doit pas tenter de stocker le lien sur le support.

Les champs uid et gid sont les ID utilisateur et groupe du propriétaire et du groupe du fichier, respectivement.

Le champ size est la taille du fichier en octets. Si le champ typeflag est défini pour spécifier un fichier de type 1 (un lien) ou 2 (un lien symbolique), le champ size doit être spécifié comme zéro. Si le champ typeflag est défini pour spécifier un fichier de type 5 (répertoire), le champ size doit être interprété comme décrit dans la définition de ce type d'enregistrement. Aucun enregistrement logique de données n'est stocké pour les types 1, 2 ou 5. Chaque octet de l'en-tête doit être traité comme une valeur non signée. Ces valeurs doivent être ajoutées à un entier non signé, initialisé à zéro, dont la précision n'est pas inférieure à 17 bits. Lors du calcul de la somme de contrôle, le champ chksum est traité comme s'il était composé uniquement de caractères <space>.

Si une conversion en fichier régulier se produit, l'utilitaire pax produira une erreur indiquant que la conversion a eu lieu. Il n'est pas spécifié si les fichiers dont les noms de chemin font référence à la même entrée de répertoire sont archivés comme fichiers liés ou comme fichiers distincts. S'ils sont archivés comme fichiers liés, cela signifie que tenter d'extraire les deux noms de chemin de l'archive résultante provoquera toujours une erreur (sauf si l'option -u est utilisée) car le lien ne peut pas être créé.

Il n'est pas spécifié si les fichiers ayant le même numéro de périphérique et de numéro de série de fichier qui sont ajoutés à une archive sont traités comme des fichiers liés à des membres qui étaient dans l'archive avant l'ajout.

Les tentatives d'archivage d'une socket doivent produire un message de diagnostic lorsque le format d'échange ustar est utilisé, mais peuvent être autorisées lorsque le format d'échange pax est utilisé. La gestion des autres types de fichiers est définie par l'implémentation.

Le champ magic est la spécification que cette archive a été générée dans ce format d'archive. Lorsque le fichier est restauré par une version de l'utilitaire privilégiée et respectant la protection, les bases de données utilisateur et groupe seront recherchées pour ces noms. Si elles sont trouvées, les identifiants utilisateur et groupe contenus dans ces fichiers seront utilisés plutôt que les valeurs contenues dans les champs uid et gid.

Format d'échange cpio

Le format d'archive cpio orienté octet est une série d'entrées, chacune comprenant un en-tête qui décrit le fichier, le nom du fichier, puis le contenu du fichier.

Nom de fichier cpio

Le champ c_name doit contenir le nom du fichier. La longueur de ce champ en octets est la valeur de c_namesize.

Si un nom de fichier est trouvé sur le support qui créerait un nom de fichier invalide, il est défini par l'implémentation si les données du fichier sont stockées dans la hiérarchie de fichiers et sous quel nom elles sont stockées.

Tous les caractères doivent être représentés dans l'IRV de la norme ISO/IEC 646:1991. Pour une portabilité maximale entre les implémentations, les noms doivent être choisis parmi les caractères représentés par l'ensemble de caractères de nom de fichier portable sous forme d'octets dont le bit le plus significatif est zéro. Si une implémentation prend en charge l'utilisation de caractères en dehors de l'ensemble de caractères de nom de fichier portable dans les noms de fichiers, d'utilisateurs et de groupes, un ou plusieurs encodages définis par l'implémentation de ces caractères doivent être fournis à des fins d'échange. Cependant, l'utilitaire pax ne doit jamais créer de noms de fichiers sur le système local qui ne peuvent pas être accessibles via les procédures décrites précédemment dans ce volume de POSIX.1-2017. Si un nom de fichier est trouvé sur le support qui créerait un nom de fichier invalide, il est défini par l'implémentation si les données du fichier sont stockées sur le système de fichiers local et sous quel nom elles sont stockées. L'utilitaire pax peut choisir d'ignorer ces fichiers tant qu'il produit une erreur indiquant que le fichier est ignoré.

Données de fichier cpio

Après c_name, il doit y avoir c_filesize octets de données. L'interprétation de ces données dépend du fichier. Pour les fichiers réguliers, les données doivent constituer le contenu du fichier. Pour les liens symboliques, les données doivent constituer le contenu du lien symbolique. Si c_filesize est zéro, aucune donnée ne doit être contenue dans c_filedata.

Lors de la restauration à partir d'une archive :

*
Si l'utilisateur n'a pas les privilèges appropriés pour créer un fichier du type spécifié, pax doit ignorer l'entrée et écrire un message d'erreur sur la sortie d'erreur standard.
*
Seuls les fichiers réguliers et les liens symboliques ont des données à restaurer. En supposant qu'un fichier régulier satisfasse aux critères de sélection qui pourraient être imposés à l'utilitaire de lecture de format par l'utilisateur, ces données doivent être restaurées.
*
Si un utilisateur n'a pas les privilèges appropriés pour définir un indicateur de mode particulier, l'indicateur doit être ignoré. Certains des indicateurs de mode dans le format d'archive ne sont pas mentionnés ailleurs dans ce volume de POSIX.1-2017. Si l'implémentation ne prend pas en charge ces indicateurs, ils peuvent être ignorés.

Entrées spéciales cpio

Les fichiers spéciaux FIFO, les répertoires et la remorque doivent être enregistrés avec c_filesize égal à zéro. Les liens symboliques doivent être enregistrés avec c_filesize égal à la longueur du contenu du lien symbolique. Pour les autres fichiers spéciaux, c_filesize n'est pas spécifié par ce volume de POSIX.1-2017. L'en-tête de la prochaine entrée de fichier dans l'archive doit être écrit directement après le dernier octet de l'entrée de fichier qui la précède. Un en-tête désignant le nom de fichier TRAILER!!! doit indiquer la fin de l'archive ; le contenu des octets du dernier bloc de l'archive après un tel en-tête est indéfini.

CONSÉQUENCES DES ERREURS

Si pax ne parvient pas à créer un fichier ou un lien lors de la lecture d'une archive ou ne parvient pas à trouver un fichier lors de l'écriture d'une archive, ou ne parvient pas à préserver l'ID utilisateur, l'ID de groupe ou le mode de fichier lorsque l'option -p est spécifiée, un message de diagnostic doit être écrit sur la sortie d'erreur standard et un statut de sortie non nul doit être retourné, mais le traitement doit continuer. Dans le cas où pax ne parvient pas à créer un lien vers un fichier, pax ne doit pas, par défaut, créer une seconde copie du fichier.

Si l'extraction d'un fichier d'une archive est terminée prématurément par un signal ou une erreur, pax peut n'avoir extrait que partiellement le fichier ou (si l'option -n n'a pas été spécifiée) peut avoir extrait un fichier portant le même nom que celui spécifié par l'utilisateur, mais qui n'est pas le fichier souhaité par l'utilisateur. De plus, les modes de fichiers des répertoires extraits peuvent avoir des bits supplémentaires du masque S_IRWXU définis ainsi que des heures de modification et d'accès incorrectes.

UTILISATION APPLICATIVE

La prudence est de mise lors de l'utilisation de l'option -a pour ajouter à une archive au format cpio. Si certains des fichiers ajoutés se voient attribuer les mêmes valeurs c_dev et c_ino qu'un fichier dans la partie existante de l'archive, ils peuvent être traités comme des liens vers ce fichier lors de l'extraction. Ainsi, il est risqué d'utiliser -a avec le format cpio sauf lorsque cela est fait sur le même système que celui où l'archive d'origine a été créée, et avec le même utilitaire pax, et en sachant qu'il y a eu peu ou pas d'activité du système de fichiers depuis la création de l'archive d'origine qui pourrait conduire à ce que certains des fichiers ajoutés se voient attribuer les mêmes valeurs c_dev et c_ino qu'un fichier non lié dans la partie existante de l'archive. De plus, lorsque l'on ajoute (intentionnellement) des liens supplémentaires à un fichier dans la partie existante de l'archive, les valeurs c_nlink dans l'archive modifiée peuvent être inférieures au nombre de liens vers le fichier dans l'archive, ce qui peut signifier que les liens ne sont pas préservés lors de l'extraction.

L'option -p (privilèges) a été inventée pour réconcilier les différences entre les implémentations historiques de tar et cpio. En particulier, les deux utilitaires utilisent -m de manière diamétralement opposée. L'option -p fournit également un moyen cohérent d'étendre les moyens par lesquels les futurs attributs de fichiers peuvent être abordés, par exemple pour les systèmes de sécurité améliorés ou les fichiers haute performance. Bien que cela puisse sembler complexe, il existe en réalité deux modes les plus couramment utilisés :

-p e
« Tout préserver ». Ceci serait utilisé par le superutilisateur historique, quelqu'un ayant tous les privilèges appropriés, pour préserver tous les aspects des fichiers tels qu'ils sont enregistrés dans l'archive. L'indicateur e est la somme de o et p, et d'autres attributs définis par l'implémentation.
-p p
« Préserver » les bits de mode de fichier. Ceci serait utilisé par l'utilisateur avec des privilèges réguliers qui souhaite préserver les aspects du fichier autres que la propriété. Les heures de fichier sont préservées par défaut, mais deux autres indicateurs sont proposés pour désactiver ces derniers et utiliser l'heure d'extraction.

Le format une ligne de chemin par ligne de l'entrée standard exclut les noms de chemin contenant des caractères de . Ce problème est hérité des programmes d'archivage historiques. Le problème peut être évité en listant les arguments de nom de fichier sur la ligne de commande au lieu de l'entrée standard.

Il est presque certain que des privilèges appropriés sont requis pour que pax accomplisse certaines parties de ce volume de POSIX.1-2017. Spécifiquement, la création de fichiers de type bloc spécial ou caractère spécial, la restauration des temps d'accès aux fichiers sauf si les fichiers appartiennent à l'utilisateur (l'option -t), ou la préservation du propriétaire du fichier, du groupe et du mode (l'option -p) nécessitent probablement des privilèges appropriés.

RATIONALE

L'utilitaire pax était nouveau pour la norme ISO POSIX‐2:1993. Il représente un compromis pacifique entre les défenseurs des utilitaires historiques tar et cpio.

Une différence fondamentale entre cpio et tar résidait dans la manière dont les répertoires étaient traités. L'utilitaire cpio ne traitait pas les répertoires différemment des autres fichiers, et pour sélectionner un répertoire et son contenu, il fallait spécifier explicitement chaque fichier de la hiérarchie. Pour tar, un répertoire correspondait à chaque fichier de la hiérarchie de fichiers qu'il enracinait.

L'utilitaire pax offre les deux interfaces ; par défaut, les répertoires sont mappés dans la hiérarchie de fichiers qu'ils enracinent. L'option -d fait en sorte que pax ignore tout fichier non explicitement référencé, comme le faisait historiquement cpio. Le comportement de style tar a été choisi par défaut car on pensait que c'était l'usage le plus courant et parce que tar est l'interface la plus couramment disponible, ayant été historiquement fournie sur les implémentations System V et BSD.

La spécification du format d'échange de données de ce volume de POSIX.1‐2017 exige que les processus disposant des « privilèges appropriés » restaurent toujours la propriété et les permissions des fichiers extraits exactement comme dans l'archive. Si l'on considère l'équivalence historique entre superutilisateur et « privilèges appropriés », il y a deux problèmes avec cette exigence. Premièrement, les utilisateurs exécutant en tant que superutilisateurs peuvent sans le savoir définir des permissions dangereuses sur les fichiers extraits. Deuxièmement, c'est inutilement restrictif, dans la mesure où les superutilisateurs ne peuvent pas extraire de fichiers et les posséder en tant que superutilisateur à moins que l'archive n'ait été créée par le superutilisateur. (Il convient de noter que la restauration des propriétés et des permissions pour le superutilisateur, par défaut, est une pratique historique dans cpio, mais pas dans tar.) Afin d'éviter ces deux problèmes, la spécification pax dispose d'un mécanisme supplémentaire de « privilège », l'option -p. Seule une invocation de pax avec les privilèges nécessaires, et qui a l'option -p définie en utilisant le caractère de spécification e, a les privilèges appropriés pour restaurer les informations complètes de propriété et de permission.

Notez également que ce volume de POSIX.1‐2017 exige que la propriété des fichiers et les permissions d'accès soient définies, lors de l'extraction, de la même manière que la fonction creat() lorsqu'elle reçoit le mode stocké dans l'archive. Cela signifie que le masque de création de fichier de l'utilisateur est appliqué aux permissions du fichier.

Les utilisateurs doivent noter que des répertoires peuvent être créés par pax lors de l'extraction de fichiers avec des permissions différentes de celles qui existaient au moment où l'archive a été créée. Lors de l'extraction d'informations sensibles dans une hiérarchie de répertoires qui n'existe plus, les utilisateurs sont encouragés à définir leur masque de création de fichier de manière appropriée pour protéger ces fichiers pendant l'extraction.

La sortie de la table des matières est écrite sur la sortie standard pour faciliter le traitement par pipeline.

Une première proposition prévoyait l'affichage des liens physiques pour tous les noms de voie d'accès. Cela a été supprimé car cela complique la sortie du cas où -v n'est pas spécifié et ne correspond pas à l'usage historique de cpio. Les informations sur les liens physiques sont disponibles dans l'affichage -v.

La description de l'option -l permet aux implémentations de créer des liens physiques vers des liens symboliques. Les versions antérieures de cette norme ne spécifiaient aucun moyen de créer un lien physique vers un lien symbolique, mais de nombreuses implémentations fournissaient cette capacité en tant qu'extension. S'il existe des liens physiques vers des liens symboliques lors de la création d'une archive, l'implémentation est tenue d'archiver le lien physique dans l'archive (sauf si -H ou -L est spécifié). En mode lecture et en mode copie, les implémentations prenant en charge les liens physiques vers des liens symboliques devraient les utiliser lorsque cela est approprié.

Les formats d'archive hérités de la norme POSIX.1‐1990 ont certaines restrictions qui ont été conservées de l'usage historique. Par exemple, il existe des restrictions sur la longueur des noms de voie d'accès stockés dans l'archive. Lorsque pax est utilisé en mode copie(-rw) (copie de hiérarchies de répertoires), la capacité d'utiliser des extensions du format -xpax surmonte ces restrictions.

La valeur par défaut de blocksize de 5120 octets pour cpio a été choisie car c'est l'une des valeurs de taille de bloc standard pour cpio, définie lorsque l'option -B est spécifiée. (L'autre valeur de taille de bloc par défaut pour cpio est de 512 octets, et cela était considéré comme trop petit.) La valeur de bloc par défaut de 10240 octets pour tar a été choisie car c'est la valeur de taille de bloc standard pour BSD tar. La taille de bloc maximale de 32256 octets (215-512 octets) est le multiple le plus grand de 512 octets qui rentre dans un registre de transfert de contrôleur de bande 16 bits signé. Il existe des limitations connues dans certains systèmes historiques qui empêcheraient l'acceptation de blocs plus grands. Les valeurs historiques ont été choisies pour améliorer la compatibilité avec les scripts historiques utilisant dd ou des utilitaires similaires pour manipuler des archives. De plus, les tailles de bloc par défaut pour tout type de fichier autre qu'un fichier spécial de caractère ont été supprimées de ce volume de POSIX.1‐2017 car sans importance et peu susceptibles d'affecter la structure de l'archive résultante.

Les implémentations sont autorisées à modifier la valeur de la taille de bloc en fonction du format de l'archive ou du périphérique sur lequel l'archive est écrite. Ceci afin de donner aux implémentations la possibilité de tirer parti de types spéciaux de périphériques, et cela ne devrait pas être utilisé sans une grande considération car cela diminue presque certainement la portabilité de l'archive.

L'utilisation prévue de l'option -n était de permettre l'extraction d'un ou plusieurs fichiers de l'archive sans traiter toute l'archive. Ceci était considéré par les développeurs de la norme comme offrant des avantages de performance significatifs par rapport aux implémentations historiques. L'option -n dans les premières propositions avait trois effets ; le premier était de faire en sorte que les caractères spéciaux dans les modèles ne soient pas traités comme spéciaux. Le second était de faire en sorte que seul le premier fichier correspondant à un modèle soit extrait. Le troisième était de faire en sorte que pax écrive un message diagnostique sur la sortie d'erreur standard lorsqu'aucun fichier ne correspondait à un modèle spécifié. Seul le second comportement est conservé par ce volume de POSIX.1‐2017, pour de nombreuses raisons. Premièrement, il n'est généralement pas acceptable qu'une seule option ait plusieurs effets. Deuxièmement, la capacité de faire agir les caractères de mise en correspondance de modèle comme des caractères normaux est utile pour des parties de pax autres que l'extraction de fichiers. Troisièmement, un contrôle plus fin sur les caractères spéciaux est utile car les utilisateurs peuvent souhaiter normaliser un seul caractère spécial dans un seul nom de fichier. Quatrièmement, étant donné un mécanisme d'échappement plus général, le comportement précédent de l'option -n peut être facilement obtenu en utilisant l'option -s ou un script sed. Enfin, écrire un message diagnostique lorsqu'un modèle spécifié par l'utilisateur n'est associé à aucun fichier est un comportement utile dans tous les cas.

Dans cette version, -n a été supprimé de la synopsis du mode copie de pax ; il est inapplicable car aucun opérande de modèle n'est spécifié dans ce mode.

Il existe une autre méthode que pax pour copier des sous-arborescences dans POSIX.1‐2008, décrite dans le cadre de l'utilitaire cp. Les deux méthodes sont des pratiques historiques : cp offre une interface plus simple et plus intuitive, tandis que pax offre une granularité de contrôle plus fine. Chacun fournit des fonctionnalités supplémentaires à l'autre ; en particulier, pax maintient la structure des liens physiques de la hiérarchie tandis que cp ne le fait pas. L'intention des développeurs de la norme est que les résultats soient similaires (en utilisant des combinaisons d'options appropriées dans les deux utilitaires). Les résultats ne sont pas obligatoirement identiques ; il ne semblait pas y avoir un gain suffisant pour les applications pour équilibrer la difficulté pour les implémentations de devoir garantir que les résultats seraient exactement identiques.

Une archive unique peut s'étendre sur plusieurs fichiers. Il est suggéré que les implémentations fournissent des messages informatifs à l'utilisateur sur la sortie d'erreur standard chaque fois que le fichier d'archive est modifié.

L'option -d (ne pas créer de répertoires intermédiaires non listés dans l'archive) trouvée dans les premières propositions a été initialement fournie en complément de l'option historique -d de cpio. Elle a été supprimée.

pax -s " foo bar " ...

La description de -t est formulée de manière à noter que cela peut entraîner l'écrasement de la mise à jour de l'heure d'accès causée par une autre activité (qui se produit pendant la lecture du fichier).

Le comportement par défaut de pax concernant les heures de modification des fichiers est le même que celui des implémentations historiques de tar. Ce n'est pas le comportement historique de cpio.

Étant donné que l'option -i utilise /dev/tty, les utilitaires sans terminal de contrôle ne peuvent pas utiliser cette option.

L'option -y, trouvée dans les premières propositions, a été supprimée car une ligne contenant un seul <point> pour l'option -i a une fonctionnalité équivalente. Les lignes spéciales pour l'option -i (un seul <point> et la ligne vide) sont une pratique historique chez cpio.

Dans les premières ébauches, une option -echarmap a été incluse pour augmenter la portabilité des fichiers entre des systèmes utilisant différents jeux de caractères codés. Cette option a été omise car il est apparu qu'aucun consensus ne pouvait être formé à son sujet. Dans cette version, l'utilisation de UTF‐8 devrait être un substitut adéquat.

Cependant, les exigences des normes ISO POSIX‐2:1993 et ISO POSIX‐1 pour pax ont rendu très difficile la création d'une seule archive contenant des fichiers créés à l'aide de caractères étendus fournis par différentes locales. Cette version ajoute le mot-clé hdrcharset pour permettre l'archivage de fichiers dans ces cas sans perdre de fichiers en raison d'erreurs de traduction.

La traduction des noms de fichiers et d'autres attributs de l'encodage d'une locale vers UTF‐8, puis à nouveau, peut entraîner une perte d'informations, car le nom de fichier résultant peut ne pas être identique octet par octet à l'original. Pour éviter ce problème, les utilisateurs peuvent spécifier l'option -o hdrcharset=binary, qui fera utiliser le format binaire pour tous les noms et attributs dans l'archive résultante. De telles archives ne sont pas portables entre des hôtes utilisant différents encodages natifs (par exemple, EBCDIC vs encodages basés sur ASCII), mais elles permettront l'échange entre la grande majorité des systèmes de fichiers POSIX en usage pratique. De plus, l'option -o hdrcharset=binary fera que pax en mode copy se comportera davantage comme d'autres utilitaires standard tels que cp.

Si les valeurs spécifiées par -o exthdr.name=value, -o globexthdr.name=value, ou par $TMPDIR (si -o globexthdr.name n'est pas spécifié) nécessitent un encodage de caractères autre que celui décrit dans la norme ISO/IEC 646:1991, un enregistrement d'en-tête étendu path devra être créé pour le fichier. Si un enregistrement d'en-tête étendu hdrcharset est actif pour de tels en-têtes, il déterminera le jeu de codes utilisé pour le champ de valeur dans ces enregistrements d'en-tête étendus path. Ces enregistrements d'en-tête étendus path doivent toujours être créés lors de l'écriture d'une archive, même si hdrcharset=binary a été spécifié et contiendrait les mêmes données (binaires) que celles qui apparaissent dans le préfixe de l'enregistrement d'en-tête ustar et les champs name. (En d'autres termes, un enregistrement d'en-tête étendu path est toujours requis s'il est généré si les champs prefix ou name contiennent des caractères non-ASCII, même quand hdrcharset=binary est également en vigueur pour ce fichier.)

L'option -k a été ajoutée pour répondre aux préoccupations internationales concernant les dangers liés aux transformations de jeux de caractères de -e (si le jeu de caractères cible était différent de la source, les noms de fichiers pourraient être transformés en noms correspondant à des fichiers existants) et a également été rendue plus générale pour protéger les fichiers transférés entre des systèmes de fichiers ayant des valeurs {NAME_MAX} différentes (tronquer un nom de fichier sur un système plus petit pourrait également écraser par inadvertance des fichiers existants). Comme indiqué, elle empêche tout écrasement, même si le fichier cible est plus ancien que la source. Cette version ajoute plus de granularité d'options pour résoudre ce problème en introduisant les actions -oinvalid=option — spécifiquement les actions UTF‐8 et binary. (Notez qu'un fichier existant est toujours sujet à l'écrasement dans ce cas. L'option -k ferme cette échappatoire.)

Certaines des caractéristiques de fichiers référencées dans ce volume de POSIX.1‐2017 pourraient ne pas être prises en charge par certains formats d'archive. Par exemple, ni les formats tar ni cpio ne contiennent l'heure d'accès aux fichiers. Pour cette raison, le caractère de spécification e a été fourni, destiné à garantir que toutes les caractéristiques des fichiers spécifiées dans l'archive soient conservées.

Il est requis que les répertoires extraits, par défaut, aient leurs heures d'accès et de modification ainsi que leurs permissions définies aux valeurs spécifiées dans l'archive. Cela pose des problèmes évidents, car les répertoires sont presque certainement modifiés après avoir été extraits et les permissions des répertoires peuvent ne pas autoriser la création de fichiers. Une solution possible est de créer les répertoires avec le mode spécifié dans l'archive, tel que modifié par l' umask de l'utilisateur, avec des permissions suffisantes pour permettre la création de fichiers. Une fois tous les fichiers extraits, pax réinitialiserait alors les heures d'accès et de modification ainsi que les permissions si nécessaire.

La description de la mise en forme en mode liste emprunte beaucoup à celle définie par l'utilitaire printf. Cependant, comme il n'y a pas de liste d'opérandes séparée pour obtenir les arguments de conversion, le format a été étendu pour permettre la spécification du nom de l'argument de conversion dans le cadre de la spécification de conversion.

Le spécificateur de conversion T permet l'affichage des champs temporels dans tous les formats de date. Contrairement à l'utilitaire ls, pax n'ajuste pas le format lorsque la date est antérieure à six mois. Cela rend l'analyse de la sortie plus prévisible.

Le spécificateur de conversion D gère la possibilité d'afficher le majeur/mineur ou la taille du fichier, comme avec ls, en utilisant %-8(size)D.

Le spécificateur de conversion L gère l'affichage ls pour les liens symboliques.

Des spécificateurs de conversion ont été ajoutés pour générer les types connus existants utilisés pour ls.

Format d'échange Pax

Le nouveau format d'échange de données POSIX a été développé principalement pour répondre aux préoccupations internationales selon lesquelles les formats ustar et cpio ne fournissaient pas de noms de fichiers, d'utilisateurs et de groupes encodés dans des caractères en dehors d'un sous-ensemble de la norme ISO/IEC 646:1991. Les développeurs de la norme ont réalisé que ce nouveau format d'échange de données POSIX devrait être très extensible car ils prévoyaient d'autres exigences dans un avenir proche :

*
Prise en charge des encodages de caractères internationaux et des informations de locale
*
Prise en charge des informations de sécurité (ACL, etc.)
*
Prise en charge des futurs types de fichiers, tels que les fichiers temps réel ou contigus
*
Inclusion de zones de données pour l'utilisation par l'implémentation
*
Prise en charge des systèmes avec des mots de plus de 32 bits et des minuteurs avec une granularité sous-seconde

Les éléments suivants n'étaient pas des objectifs pour ce format car ils sont mieux gérés par des utilitaires séparés ou sont inappropriés pour un format portable :

*
Chiffrement
*
Compression
*
Traduction de données entre locales et jeux de codes
*
Stockage des inodes

Le format choisi pour atteindre ces objectifs est une extension du format ustar. Parmi les deux formats précédemment disponibles, seul le format ustar a été sélectionné pour les extensions car :

*
Il était plus facile à étendre de manière rétrocompatible. Il offrait des indicateurs de version et des champs de type de bloc d'en-tête avec de la place pour une standardisation future. Le format cpio, tout en possédant une méthodologie de nommage de fichiers plus flexible, ne pouvait pas être étendu sans enfreindre une implémentation théorique ou utiliser un nom de fichier fictif qui pourrait être un nom de fichier légitime.
*
L'expérience industrielle depuis les « guerres du tar » originelles menées lors du développement de la norme ISO POSIX‐1 a clairement été en faveur du format ustar, qui est généralement le format de sortie par défaut sélectionné pour les implémentations de pax sur les nouveaux systèmes.

Le nouveau format a été conçu avec un objectif supplémentaire : un comportement raisonnable lorsqu'un ancien utilitaire tar ou pax lisait une archive. Étant donné que la norme POSIX.1‐1990 exigeait qu'un « utilitaire de lecture de format » traite les valeurs typeflag non reconnues comme des fichiers ordinaires, cela a permis au format d'inclure toutes les informations étendues dans un pseudo-fichier régulier qui précédait chaque fichier réel. Une option est fournie qui permet au créateur de l'archive de définir des noms raisonnables pour ces fichiers sur les anciens systèmes. De plus, le texte normatif suggère que des valeurs d'accès aux fichiers raisonnables soient utilisées pour ce bloc d'en-tête ustar. Rendre ces fichiers d'en-tête inaccessibles pour une lecture et une suppression faciles ne serait pas raisonnable. Des permissions de fichiers de 600 ou 700 sont suggérées.

Le champ typeflag ustar a été utilisé pour accommoder la fonctionnalité supplémentaire du nouveau format plutôt que des identifiants magiques ou des versions, car la norme POSIX.1‐1990 (et, par référence, la version précédente de pax) imposait le comportement de l'utilitaire de lecture de format lorsqu'il rencontrait un typeflag inconnu, mais restait silencieuse sur les deux autres champs.

Les premières propositions pour la première version de cette norme contenaient un format d'archive proposé qui était basé sur la compatibilité avec la norme des fichiers de bande (ISO 1001, similaire au format utilisé historiquement sur de nombreux mainframes et mini-ordinateurs). Ce format était excessivement complexe et nécessitait une surcharge considérable en termes de volume et d'enregistrements d'en-tête. De plus, les développeurs de la norme ont estimé qu'il ne serait pas acceptable pour la communauté des développeurs POSIX, il a donc été modifié ultérieurement pour être un format plus étroitement lié à la pratique historique sur les systèmes POSIX.

La division préfixe et nom des chemins dans ustar a été remplacée par l'enregistrement d'en-tête étendu unique path pour plus de simplicité.

Le concept d'en-tête étendu global (typeflagg) était controversé. S'il était appliqué à une archive enregistrée sur une bande magnétique, quelques blocs illisibles au début de la bande pourraient poser un problème sérieux ; un utilitaire tentant d'extraire autant de fichiers que possible d'une archive endommagée pourrait perdre un grand pourcentage d'informations d'en-tête de fichier dans ce cas. Cependant, si l'archive était sur un support fiable, tel qu'un CD-ROM, l'en-tête étendu global offre des réductions de taille considérables en éliminant les informations redondantes. Ainsi, le texte met en garde contre l'utilisation de la méthode globale pour les supports peu fiables et fournit une méthode pour implanter des informations globales dans l'en-tête étendu pour chaque fichier, plutôt que dans le typeflag g.

b> enregistrements.

Aucune installation pour la traduction ou le filtrage des données par fichier n'est incluse car les développeurs standard n'ont pas pu inventer une interface qui permettrait cela de manière efficace. Si un filtre, tel que le chiffrement ou la compression, doit être appliqué à tous les fichiers, il est plus efficace d'appliquer le filtre à l'archive entière en un seul fichier. Les développeurs standard ont envisagé des interfaces qui invoqueraient un script shell pour chaque fichier entrant ou sortant de l'archive, mais la charge système de cette approche a été jugée trop élevée.

Une telle approche consisterait à avoir des enregistrements filter= qui donneraient un chemin d'accès à un exécutable. Lorsque le programme est invoqué, le fichier et l'archive seraient ouverts pour l'entrée/sortie standard et tous les champs d'en-tête seraient disponibles sous forme de variables d'environnement ou d'arguments de ligne de commande. Les développeurs standard ont discuté de tels schémas, mais ils ont été omis de POSIX.1‐2008 en raison de préoccupations concernant une surcharge excessive. De plus, le programme lui-même devrait être dans l'archive s'il devait être utilisé de manière portable.

Il n'existe actuellement aucun moyen portable d'identifier le(s) jeu(x) de caractères utilisé(s) pour un fichier dans le système de fichiers. Par conséquent, pax n'a pas reçu de mécanisme pour générer des enregistrements charset automatiquement. Le seul moyen portable de le faire est que l'utilisateur écrive l'archive en utilisant l'option de ligne de commande -ocharset=string. Cela suppose que tous les fichiers de l'archive utilisent le même encodage. Le texte ``défini par l'implémentation'' est inclus pour permettre à un système capable d'identifier les encodages utilisés pour chacun de ses fichiers.

Le tableau des normes qui accompagne la description des enregistrements charset est reconnu comme étant très limité. Seul un nombre limité de normes de jeux de caractères est raisonnable pour un échange maximal. Tout jeu de caractères est, bien sûr, possible par accord préalable. Il a été suggéré d'inclure EBCDIC, mais il a été omis car il n'est pas défini par une norme formelle. Les normes formelles, et alors seulement celles avec un public raisonnablement large, peuvent être incluses ici, simplement par praticité. Les <valeur>s représentent des noms de jeux de caractères officiellement enregistrés dans le format requis par la norme ISO 2375:1985.

Les règles normales de liste séparée par des <virgules> ou des <espaces> ne sont pas suivies dans le cas des options par mot-clé afin de faciliter l'analyse des arguments pour getopts.

Pour plus d'informations sur les encodages de caractères, voir pax Archive Character Set Encoding/Decoding.

Les développeurs standard ont réservé l'espace des noms de mots-clé pour les extensions de fournisseurs. Il est suggéré que le format à utiliser soit :

FOURNISSEUR.mot_clé

où FOURNISSEUR est le nom du fournisseur ou de l'organisation en lettres majuscules. Il est en outre suggéré que le mot-clé suivant le <point> soit nommé différemment de l'un des mots-clé standard afin qu'il puisse être utilisé pour une normalisation future, le cas échéant, en omettant le préfixe FOURNISSEUR.

Le champ <longueur> dans l'enregistrement d'en-tête étendu a été inclus pour simplifier le parcours des enregistrements, même si un enregistrement contient un format inconnu (pour un pax particulier) avec des interactions complexes de caractères spéciaux. Il fournit également un petit contrôle d'intégrité dans les enregistrements pour aider un programme tentant de récupérer des fichiers à partir d'une archive endommagée.

Il n'y a pas de versions d'en-tête étendues pour les champs devmajor et devminor car le champ d'en-tête ustar au format non spécifié devrait être suffisant. S'ils ne le sont pas, des mots-clé étendus spécifiques au fournisseur (tels que FOURNISSEUR.devmajor) devraient être utilisés.

L'étiquetage des fichiers par périphérique et par i-numéro n'a pas été adopté de cpio ; les fichiers sont échangés strictement sur la base du nom symbolique, comme dans ustar.

Tout comme avec les descriptions de format ustar, le nouveau format ne prend pas d'arrangements spéciaux pour les archives multi-volumes. Chacun des types d'archives pax est supposé se trouver à l'intérieur d'un seul fichier POSIX, et la division de ce fichier sur plusieurs volumes (disquettes, cartouches de bande, etc.), le traitement de leurs étiquettes et le montage de chacun dans la séquence appropriée sont considérés comme des détails d'implémentation qui ne peuvent pas être décrits de manière portable.

Le format pax est destiné à l'échange, pas seulement à la sauvegarde sur un (une famille de) système(s). Il n'est pas aussi densément compacté que possible pour la sauvegarde :

*
Il contient des informations sous forme de caractères codés qui pourraient être codés en binaire.
*
Il identifie les enregistrements étendus avec des champs de nom qui pourraient être omis au profit d'une disposition à champs fixes.
*
Il traduit les noms dans un jeu de caractères portable et identifie les informations liées à la locale, ce qui est probablement inutile pour la sauvegarde.

Les exigences de restauration à partir d'une archive sont légèrement différentes de la formulation historique, permettant à des privilèges non monolithiques d'apporter autant que possible. En particulier, des attributs tels que « fichier haute performance » peuvent être accordés largement mais pas universellement, tandis que le SUID ou chown() peuvent être beaucoup plus restreints. Il n'y a aucune implication dans POSIX.1‐2008 que les informations de sécurité doivent être respectées après qu'elles ont été restaurées dans la hiérarchie des fichiers, malgré ce qui pourrait être inféré à tort par le silence sur ce sujet. C'est un sujet pour une autre norme.

Les liens sont enregistrés de la manière décrite ici car un lien peut concerner n'importe quel type de fichier. Il est souhaitable en général de pouvoir restaurer une partie d'une archive sélectivement et de restaurer tous ces fichiers complètement. Si les données ne sont pas associées à chaque lien, il n'est pas possible de le faire. Cependant, les données associées à un fichier peuvent être volumineuses, et lorsque la restauration sélective n'est pas nécessaire, cela peut être une charge importante. L'archive est structurée de telle sorte que les fichiers sans données associées puissent toujours être restaurés par le nom de n'importe quel nom de lien, et l'utilisateur peut choisir si les données sont enregistrées avec chaque instance d'un fichier qui contient des données. Le format permet le mélange des deux types de liens dans une seule archive ; cela peut être fait pour des besoins spéciaux, et pax est censé interpréter de telles archives en entrée correctement, malgré le fait qu'il n'y ait pas d'option pax qui forcerait ce cas mixte en sortie. (Lorsque -o linkdata est utilisé, la sortie doit contenir les données dupliquées, mais l'implémentation est libre de les inclure ou de les omettre lorsque -o linkdata n'est pas utilisé.)

Les valeurs temporelles sont incluses comme enregistrements d'en-tête étendus pour les implémentations nécessitant plus de onze chiffres octaux autorisés par le format ustar. Les horodatages de fichiers portables ne peuvent pas être négatifs. Si pax rencontre un fichier avec un horodatage négatif en mode copy ou write, il peut rejeter le fichier, substituer un horodatage non négatif, ou générer un horodatage non portable avec un '-' préfixé. Même si certaines implémentations peuvent supporter une granularité de temps de fichier plus fine que les secondes, le texte normatif exige le support uniquement pour les secondes depuis l'Époque, car la norme ISO POSIX‐1 les énonce ainsi. Le format ustar n'inclut que mtime ; le nouveau format ajoute atime et ctime pour la symétrie. L'heure d'accès atime restaurée dans le système de fichiers sera affectée par les options -p a et -p e. L'heure de création ctime (en fait, l'heure de modification du nœud ) est décrite avec les privilèges appropriés afin qu'elle puisse être ignorée lors de l'écriture dans le système de fichiers. POSIX ne fournit pas de moyen portable pour modifier l'heure de création d'un fichier. Rien n'est destiné à empêcher une implémentation non portable de pax de restaurer la valeur.

Les enregistrements d'en-tête étendus gid, size et uid ont été inclus pour permettre une extension au-delà des tailles spécifiées dans l'en-tête tar régulier. De nouvelles architectures de systèmes de fichiers émergent qui épuiseront le champ de taille à 12 chiffres. Il n'y a probablement pas beaucoup de systèmes nécessitant plus de 8 chiffres pour les identifiants d'utilisateur et de groupe, mais les valeurs d'en-tête étendues ont été incluses pour plus de complétude, permettant des remplacements pour toutes les valeurs décimales dans l'en-tête tar.

Les développeurs standard avaient l'intention de décrire les résultats effectifs de pax concernant la propriété et les permissions des fichiers ; les implémentations ne sont pas limitées dans le moment ou la séquence de restauration de ceux-ci, à condition que les résultats soient conformes aux spécifications.

Une grande partie du texte décrivant les en-têtes étendus fait référence à une utilisation en modes ``write ou copy''. Les références au mode copy sont dues au texte normatif : « L'effet de la copie doit être comme si les fichiers copiés étaient écrits dans un fichier archive puis ultérieurement extraits... ». Il n'y a certainement aucun moyen de tester si pax génère réellement les en-têtes étendus en mode copy, mais les effets doivent être comme s'il l'avait fait.

pax Encodage/Décodage des Jeux de Caractères d'Archives

Il est nécessaire d'échanger des archives de fichiers entre des systèmes ayant des jeux de codes natifs différents. Les noms de fichiers, les noms de groupes et les noms d'utilisateurs doivent être préservés dans la mesure du possible lorsqu'une archive est lue sur la plateforme réceptrice. La traduction du contenu des fichiers ne relève pas de la portée de l'utilitaire pax.

Il y aura également le besoin de représenter des caractères qui ne sont pas disponibles sur la plateforme réceptrice. Ces caractères non supportés ne peuvent pas être automatiquement convertis vers l'ensemble local de caractères en raison du risque de collisions. Cela pourrait entraîner l'écrasement de fichiers précédemment extraits de l'archive ou de fichiers préexistants sur le système.

Pour ces raisons, le jeu de codes utilisé pour représenter les caractères dans les enregistrements d'en-tête étendus de l'archive pax doit être suffisamment riche pour gérer tous les jeux de caractères couramment utilisés. Les champs nécessitant une traduction incluent, au minimum, les noms de fichiers, les noms d'utilisateurs, les noms de groupes et les noms de liens. Les implémentations peuvent souhaiter avoir des mots-clé étendus localisés qui utilisent des caractères non portables.

Les développeurs standard ont envisagé les options suivantes :

*
Le créateur de l'archive spécifie le nom bien défini du jeu de codes source. Le récepteur doit alors reconnaître le nom du jeu de codes et effectuer les traductions appropriées vers le jeu de codes de destination.
*
Le créateur de l'archive inclut dans l'archive la table de mappage des caractères pour le jeu de codes source utilisé pour encoder les enregistrements d'en-tête étendus. Le récepteur doit alors lire la table de mappage des caractères et effectuer les traductions appropriées vers le jeu de codes de destination.
*
Le créateur de l'archive traduit les enregistrements d'en-tête étendus dans le jeu de codes source vers une forme canonique. Le récepteur doit alors effectuer les traductions appropriées vers le jeu de codes de destination.

DESCRIPTION

L'en-tête pax fournit un moyen de déterminer si un fichier doit être lu ou écrit à l'aide du format d'échange cpio ou d'interchange ustar. Il définit également les types de fichiers et les champs d'en-tête spécifiques à ces formats.

Les spécifications du format d'interchange ustar sont définies dans la section “Format d'interchange” de la norme IEEE P1003.1.

Format d'interchange du fichier

Les informations de fichier sont stockées dans des enregistrements d'en-tête suivie de blocs de données. Les enregistrements d'en-tête sont de taille fixe et sont utilisés pour décrire les informations relatives à un fichier, telles que son nom, sa taille, ses autorisations, son propriétaire et son horodatage.

Les enregistrements d'en-tête sont des enregistrements de 512 octets et sont alignés sur des limites de 512 octets. Les champs de l'en-tête sont décrits à l'aide de la notation de structure C. Tous les champs de caractères sont complétés par des octets NUL.

Les champs définis dans l'en-tête ustar sont les suivants :

char    name[100];        # fichier pathname
char    mode[8];          # specifies given file permissions and type
char    uid[8];           # Specifies the group ID of the file
char    gid[8];           # Specifies the user ID of the file
char    size[12];         # Specifies the size of the file in bytes
char    mtime[12];        # Specifies the last modification time of the file
char    chksum[8];        # Specifies the header Checksum
char    typeflag;         # specifies the file type
char    linkname[100];    # specifies the file name of the target file

Les champs suivants sont également présents dans l'en-tête ustar, mais sont réservés à un usage futur :

char    magic[8];         # Specifies the magic number
char    version[2];       # Specifies the version number

Les champs des enregistrements d'en-tête sont formatés comme suit :

name
Le nom du fichier, y compris son chemin d'accès. Le nom est une chaîne se terminant par un octet NUL. Si le nom dépasse 100 octets, il est tronqué.
mode
Les autorisations du fichier et le type de fichier. Le mode est une chaîne représentant un nombre octal.
uid
L'ID utilisateur du propriétaire du fichier. L'UID est une chaîne représentant un nombre octal.
gid
L'ID groupe du propriétaire du fichier. Le GID est une chaîne représentant un nombre octal.
size
La taille du fichier en octets. La taille est une chaîne représentant un nombre octal.
mtime
L'heure de la dernière modification du fichier. Le mtime est une chaîne représentant un nombre octal.
chksum
La somme de contrôle de l'en-tête. La somme de contrôle est une chaîne représentant un nombre octal.
typeflag
Le type de fichier. Les valeurs possibles pour typeflag sont :
normal file                '0' or '\0'
    link to another file     '1'
    symbolic link to another file '2'
    character special file   '3'
    block special file       '4'
    directory                '5'
    fifo (named pipe)        '6'
    contiguous file          '7'
linkname
Le nom du fichier cible pour les liens symboliques et les liens physiques. Le nom du lien est une chaîne se terminant par un octet NUL.
magic
Le nombre magique, qui doit être "ustar ". (Il y a un espace à la fin.)
version
Le numéro de version, qui doit être "00".

L'objectif de ces changements n'était pas seulement de fournir les améliorations fonctionnelles souhaitées, mais aussi de conserver la compatibilité entre les anciennes et les nouvelles versions. Cette compatibilité a été maintenue. Les archives écrites dans l'ancien format d'archive sont compatibles avec le nouveau format.

Les développeurs doivent savoir que le format de fichier précédent n'incluait pas de mécanisme pour archiver les fichiers de type répertoire. Pour cette raison, la convention d'utiliser un nom de fichier se terminant par un '/' a été adoptée pour spécifier un répertoire dans l'archive.

La taille totale des champs name et prefix a été définie pour répondre aux exigences minimales de {PATH_MAX}. Si un nom de chemin d'accès tient dans le champ name, il est recommandé de le stocker là sans utiliser le champ prefix. Bien que le champ name soit connu pour être trop petit pour contenir {PATH_MAX} caractères, la valeur n'a pas été modifiée dans cette version du format de fichier d'archive afin de conserver la rétrocompatibilité, et le préfixe a été introduit à la place. De plus, en raison de la version précédente du format, il n'y a aucun moyen de supprimer la restriction selon laquelle le champ linkname est limité à la taille du champ name.

Le champ size doit être significatif dans toutes les extensions d'implémentation, bien qu'il puisse être zéro. Ceci est requis afin que les blocs de données puissent toujours être correctement comptés.

Il est suggéré que si des fichiers spéciaux de périphériques qui ne peuvent pas être représentés dans le format standard doivent être représentés, un des types d'extension (A-Z) soit utilisé, et que les informations supplémentaires pour le fichier spécial soient représentées sous forme de données et reflétées dans le champ size.

Tenter de restaurer un type de fichier spécial, où il est converti en données ordinaires et entre en conflit avec un nom de fichier existant, n'a pas besoin d'être spécialement détecté par l'utilitaire. S'il est exécuté en tant qu'utilisateur ordinaire, pax ne devrait pas pouvoir écraser les entrées de, par exemple, /dev, quelle que soit la manière dont le fichier est converti. S'il est exécuté en tant qu'utilisateur privilégié, il devrait pouvoir le faire, et ce serait considéré comme un bogue s'il ne le pouvait pas. Il en va de même pour les fichiers de données ordinaires et les fichiers spéciaux nommés de manière similaire ; il est impossible d'anticiper les besoins de l'utilisateur (qui pourrait réellement avoir l'intention d'écraser le fichier), de sorte que le comportement doit être prévisible (et donc régulier) et s'appuyer sur le système de protection au besoin.

La valeur 7 dans le champ typeflag est destinée à définir comment les fichiers contigus peuvent être stockés dans une archive ustar. POSIX.1-2008 n'exige pas l'extension de fichier contigu, mais définit une manière standard d'archiver de tels fichiers afin que tous les systèmes conformes puissent interpréter ces types de fichiers de manière significative et cohérente. Sur un système qui ne prend pas en charge les types de fichiers étendus, l'utilitaire pax doit faire de son mieux avec le fichier et passer au suivant.

Les modes de protection des fichiers sont ceux utilisés conventionnellement par l'utilitaire ls. Ceci est étendu au-delà de l'utilisation dans la norme ISO POSIX-2 pour prendre en charge le bit "partage de texte" ou "sticky". Il est prévu que le document de conformité ne documente rien au-delà de l'existence et du support d'un tel mode. D'autres extensions sont attendues pour ces bits, notamment avec la surcharge des indicateurs set-user-ID et set-group-ID.

Format d'interchange cpio

La référence aux privilèges appropriés dans le format cpio fait référence à une erreur sur la sortie standard ; le format ustar ne fait pas de déclarations comparables.

Le modèle pour ce format était le format d'interchange de données historique cpio -c de System V. Ce modèle documente la version portable du format cpio et non la version binaire. Il a la flexibilité de transférer des données de tout type décrit dans POSIX.1-2008, tout en étant extensible pour transférer des types de données spécifiques aux extensions au-delà de POSIX.1-2008 (par exemple, les fichiers contigus). Parce qu'il décrit les pratiques existantes, il n'y a pas de question de maintenir la compatibilité ascendante.

En-tête cpio

Il y a eu quelques inquiétudes quant à la petite taille du champ c_ino de l'en-tête pour gérer les systèmes qui ont de très grands numéros d'inode. Cependant, le champ c_ino de l'en-tête est utilisé strictement comme mécanisme de résolution de liens physiques pour les archives. Ce n'est pas nécessairement la même valeur que le numéro d'inode du fichier à l'emplacement d'où le fichier est extrait.

Le nom c_magic est basé sur l'usage historique.

Nom de fichier cpio

Pour la plupart des implémentations historiques de l'utilitaire cpio, {PATH_MAX} octets peuvent être utilisés pour décrire le nom du chemin d'accès sans l'ajout d'autres champs d'en-tête (l'octet NUL serait inclus dans ce décompte). {PATH_MAX} est la valeur minimale pour la taille du nom de chemin, documentée à 256 octets. Cependant, une implémentation peut utiliser c_namesize pour déterminer la longueur exacte du nom du chemin. Avec la description actuelle de l'en-tête <cpio.h>, cette taille de nom de chemin peut être aussi grande qu'un nombre décrit en six chiffres octaux.

Deux valeurs sont documentées sous les valeurs du champ c_mode pour permettre l'extensibilité des types de fichiers connus  :

0110 000
Réservé aux fichiers contigus. L'implémentation peut traiter le reste des informations pour cette archive comme un fichier régulier. Si ce type de fichier n'est pas défini, l'implémentation peut créer le fichier en tant que fichier régulier.

Ceci permet l'extensibilité du format cpio tout en permettant la lecture des anciennes archives. Les fichiers de type inconnu peuvent être lus comme des "fichiers réguliers" sur certaines implémentations. Sur un système qui ne prend pas en charge les types de fichiers étendus, l'utilitaire pax doit faire de son mieux avec le fichier et passer au suivant.

PROLOG

2017

NAME

pax — lire et écrire des archives, et copier des fichiers

SYNOPSIS

pax

pax [options] [input - output]

pax [options] [operand ...]

DESCRIPTION

La commande pax est un utilitaire d'archivage qui peut lire et écrire des archives de fichiers, et copier des fichiers. Elle a été conçue pour être un remplacement de la commande ar et est conforme aux normes POSIX.1-2001 et X/Open Portability Guide (XPG) http://www.opengroup.org/unix/online.html .

La commande pax peut être utilisée de deux manières principales :

  1. En mode copie : pax options input - output

    Dans ce mode, pax copie les fichiers de input vers output. Les options spécifient le type d'archive (par exemple, -f pour un fichier, -t pour un type d'archive spécifique) et d'autres paramètres de copie. La barre oblique inverse (-) indique que l'entrée est une archive et que la sortie doit être un fichier normal.

  2. En mode archive : pax options operand ...

    Dans ce mode, pax crée ou extrait une archive en utilisant les opérandes spécifiés. Les opérandes peuvent être des noms de fichiers ou des options qui spécifient le format de l'archive et les fichiers à inclure ou exclure.

Les options sont précédées d'un tiret (-) et peuvent être combinées. Les options sont décrites ci-dessous.

OPTIONS

Les options suivantes sont disponibles :

-b buffersize
Spécifie la taille du tampon pour les opérations d'entrée/sortie. La valeur doit être un entier positif.
-c
Inverse la correspondance des noms de fichiers. Cela est utile pour exclure des fichiers d'une archive.
-d
Ne pas créer de répertoires. Par défaut, pax crée les répertoires nécessaires.
-f archive
Spécifie le nom du fichier d'archive à utiliser. Si cette option n'est pas fournie, pax utilise l'entrée standard pour la lecture et la sortie standard pour l'écriture.
-H
Suivre les liens symboliques lors de la copie de fichiers, mais pas lors de l'extraction.
-h
Ne pas suivre les liens symboliques lors de la copie de fichiers.
-k
Ne pas écraser les fichiers existants. Si un fichier existe déjà sur la destination, pax ne l'écrira pas.
-L
Suivre les liens symboliques lors de la copie de fichiers et de l'extraction.
-n
Ne sélectionner que le premier fichier correspondant à chaque modèle.
-O
Écrire l'archive sur la sortie standard et lire les entrées de l'entrée standard.
-o
Spécifie des options supplémentaires pour le format de l'archive. Par exemple, -o format=ustar spécifie le format USTAR.
-p
Conserver les attributs des fichiers. Les attributs qui peuvent être conservés incluent les permissions, la propriété et les timestamps.
-r
Lire les fichiers de l'entrée standard et les ajouter à l'archive.
-s chaîne1 chaîne2 options
Remplacer les noms de fichiers. chaîne1 est le motif à rechercher, chaîne2 est la chaîne de remplacement, et options peut inclure des drapeaux comme g pour un remplacement global.
-t type
Spécifie le type de format d'archive à utiliser. Les types courants incluent cpio, tar et ustar.
-u
Ne mettre à jour que les fichiers plus récents. Si un fichier dans l'archive est plus récent qu'un fichier existant sur la destination, le fichier existant sera mis à jour.
-v
Mode verbeux. Affiche les noms des fichiers traités.
-w
Demander une confirmation avant chaque opération. Cela permet de vérifier chaque fichier avant de l'ajouter ou de l'extraire.
-X fichier
Lit les noms de fichiers supplémentaires à partir du fichier spécifié.
-x
Extraire les fichiers de l'archive.

OPERANDS

Les opérandes sont les noms de fichiers ou de répertoires qui doivent être traités par pax. Si aucun opérande n'est spécifié, pax traitera tous les fichiers de l'entrée standard.

STDIN

Si l'option -r est utilisée, pax lit les noms de fichiers de l'entrée standard.

INPUT FILES

Si l'option -f est utilisée, le fichier d'archive spécifié est lu. Sinon, l'entrée standard est utilisée.

ENVIRONMENT VARIABLES

Les variables d'environnement suivantes peuvent affecter le comportement de pax :

BLOCKSIZE
Définit la taille du bloc par défaut pour les opérations d'archivage.
CDPATH
Utilisé pour rechercher les répertoires lors de la résolution des chemins relatifs.
PAGER
Définit le programme à utiliser pour afficher les fichiers longs.

ASYNCHRONOUS EVENTS

Aucune information spécifique.

STDOUT

En mode verbeux (option -v), pax affiche les noms des fichiers traités sur la sortie standard.

STDERR

Les messages d'erreur sont affichés sur la sortie d'erreur standard.

OUTPUT FILES

En mode copie, le fichier de sortie spécifié est créé ou mis à jour.

EXTENDED DESCRIPTION

La commande pax est un outil polyvalent pour la manipulation d'archives de fichiers. Elle prend en charge plusieurs formats d'archive courants, notamment cpio, tar et ustar. La commande peut être utilisée pour créer des archives, extraire des fichiers d'archives, copier des fichiers et comparer des fichiers.

Le comportement de pax peut être ajusté à l'aide d'un large éventail d'options, qui permettent de contrôler la manière dont les fichiers sont traités, le format de l'archive, et la gestion des liens symboliques et des attributs de fichiers.

EXIT STATUS

La commande pax renvoie l'un des codes de sortie suivants :

0
Opération réussie.
1
Erreur s'est produite.
2
L'un des fichiers spécifiés n'a pas pu être accédé ou traité.

CONSEQUENCES OF ERRORS

En cas d'erreur, pax peut abandonner l'opération ou continuer en fonction du type d'erreur et des options spécifiées. Les erreurs peuvent inclure des problèmes d'accès aux fichiers, des erreurs de format d'archive ou des problèmes d'espace disque insuffisant.

APPLICATION USAGE

La commande pax est couramment utilisée dans les scripts shell pour la sauvegarde et la restauration de fichiers, ainsi que pour la gestion des archives logicielles. Son adhésion aux normes POSIX en fait un outil portable et fiable.

EXAMPLES

Créer une archive tar de tous les fichiers du répertoire courant :

pax -w -f archive.tar .

Extraire le contenu d'une archive tar dans le répertoire courant :

pax -r -f archive.tar

Copier les fichiers du répertoire src vers le répertoire dest, en conservant les attributs des fichiers :

pax src/ -rw src/dest/

RATIONALE

La commande pax a été développée pour fournir une interface uniforme pour les opérations d'archivage, en remplaçant les commandes spécifiques à chaque système comme tar et cpio. Son objectif est de simplifier la gestion des archives et d'améliorer la portabilité des scripts.
