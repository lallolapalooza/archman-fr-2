PAM.CONF(5) Manuel Linux-PAM PAM.CONF(5)

NOM

pam.conf, pam.d - Fichiers de configuration PAM

DESCRIPTION

Lorsqu'une application consciente de PAM accordant des privilèges est lancée, elle active sa connexion à l'API PAM. Cette activation effectue un certain nombre de tâches, la plus importante étant la lecture du ou des fichiers de configuration : /etc/pam.conf. Alternativement et de préférence, la configuration peut être définie par des fichiers de configuration individuels situés dans un répertoire pam.d. La présence de ce répertoire fera que Linux-PAM ignorera /etc/pam.conf.

Ces fichiers listent les PAM qui effectueront les tâches d'authentification requises par ce service, ainsi que le comportement approprié de l'API PAM en cas d'échec des PAM individuels.

La syntaxe du fichier de configuration /etc/pam.conf est la suivante. Le fichier est composé d'une liste de règles, chaque règle étant généralement placée sur une seule ligne, mais pouvant être étendue avec un saut de ligne échappé : `\<LF>'. Les commentaires sont précédés de marques `#' et s'étendent jusqu'au prochain saut de ligne.

Le format de chaque règle est une collection de jetons séparés par des espaces, les trois premiers étant insensibles à la casse :

service type contrôle chemin_module arguments_module

La syntaxe des fichiers contenus dans le répertoire /etc/pam.d/, est identique à l'exception de l'absence de tout champ service. Dans ce cas, le service est le nom du fichier dans le répertoire /etc/pam.d/. Ce nom de fichier doit être en minuscules.

Une caractéristique importante de PAM est que plusieurs règles peuvent être empilées pour combiner les services d'un certain nombre de PAM pour une tâche d'authentification donnée.

Le service est généralement le nom familier de l'application correspondante : login et su en sont de bons exemples. Le nom de service, other, est réservé pour donner des règles par défaut. Seules les lignes mentionnant le service actuel (ou en leur absence, les entrées other) seront associées à l'application de service donnée.

Le type est le groupe de gestion auquel la règle correspond. Il est utilisé pour spécifier à quel groupe de gestion le module suivant sera associé. Les entrées valides sont :

account

ce type de module effectue une gestion de compte non basée sur l'authentification. Il est généralement utilisé pour restreindre/permettre l'accès à un service en fonction de l'heure, des ressources système disponibles (nombre maximum d'utilisateurs) ou peut-être de la localisation de l'utilisateur demandeur -- connexion en 'root' uniquement sur la console.

auth

ce type de module offre deux aspects de l'authentification de l'utilisateur. Premièrement, il établit que l'utilisateur est bien celui qu'il prétend être, en demandant à l'application de solliciter un mot de passe ou un autre moyen d'identification. Deuxièmement, le module peut accorder une appartenance à un groupe ou d'autres privilèges grâce à ses propriétés d'octroi de credentials.

password

ce type de module est requis pour mettre à jour le jeton d'authentification associé à l'utilisateur. Généralement, il existe un module pour chaque type d'authentification basé sur un 'défi/réponse' (auth).

session

ce type de module est associé à l'exécution d'actions nécessaires avant/après l'octroi du service à l'utilisateur. Ces actions incluent la journalisation des informations concernant l'ouverture/fermeture d'un échange de données avec un utilisateur, le montage de répertoires, etc.

Si la valeur type de la liste ci-dessus est précédée d'un caractère -, la bibliothèque PAM ne journalisera pas dans le journal système s'il n'est pas possible de charger le module parce qu'il est manquant dans le système. Cela peut être utile, notamment pour les modules qui ne sont pas toujours installés sur le système et qui ne sont pas requis pour une authentification et une autorisation correctes de la session de connexion.

Le troisième champ, contrôle, indique le comportement de l'API PAM en cas d'échec du module dans sa tâche d'authentification. Il existe deux types de syntaxe pour ce champ de contrôle : la syntaxe simple a un mot-clé simple unique ; la plus complexe implique une sélection entre crochets de paires valeur=action.

Pour la syntaxe simple (historique), les valeurs de contrôle valides sont :

required

l'échec d'un tel PAM conduira finalement à un échec de retour de l'API PAM, mais seulement après que les modules empilés restants (pour ce service et ce type) aient été invoqués.

requisite

similaire à required, cependant, en cas d'échec d'un tel module, le contrôle est directement retourné à l'application ou à la pile PAM supérieure. La valeur de retour est celle associée au premier module requis ou requis à échouer. Notez que ce drapeau peut être utilisé pour se protéger contre la possibilité qu'un utilisateur ait l'opportunité d'entrer un mot de passe via un canal non sécurisé. Il est concevable qu'un tel comportement informe un attaquant sur les comptes valides d'un système. Cette possibilité doit être pesée par rapport aux préoccupations non négligeables d'exposer un mot de passe sensible dans un environnement hostile.

sufficient

si un tel module réussit et qu'aucun module requis précédent n'a échoué, le framework PAM retourne un succès à l'application ou à la pile PAM supérieure immédiatement, sans appeler d'autres modules dans la pile. Un échec d'un module sufficient est ignoré et le traitement de la pile de modules PAM continue sans être affecté.

optional

le succès ou l'échec de ce module n'est important que s'il est le seul module de la pile associé à ce service+type.

include

inclure toutes les lignes du type donné du fichier de configuration spécifié comme argument à ce contrôle.

substack

inclure toutes les lignes du type donné du fichier de configuration spécifié comme argument à ce contrôle. Ceci diffère de include en ce que l'évaluation des actions done et die dans un substack ne provoque pas le passage au reste de la pile complète des modules, mais seulement au substack. Les sauts dans un substack ne peuvent pas non plus faire sortir l'évaluation de celui-ci, et l'ensemble du substack est compté comme un module lorsque le saut est effectué dans une pile parente. L'action reset réinitialisera l'état de la pile de modules à l'état qu'il était au début de l'évaluation du substack.

Pour la syntaxe plus complexe, les valeurs de contrôle valides ont la forme suivante :

      [valeur1=action1 valeur2=action2 ...]

Où valeurN correspond au code de retour de la fonction invoquée dans le module pour lequel la ligne est définie. Il est sélectionné parmi : success, open_err, symbol_err, service_err, system_err, buf_err, perm_denied, auth_err, cred_insufficient, authinfo_unavail, user_unknown, maxtries, new_authtok_reqd, acct_expired, session_err, cred_unavail, cred_expired, cred_err, no_module_data, conv_err, authtok_err, authtok_recover_err, authtok_lock_busy, authtok_disable_aging, try_again, ignore, abort, authtok_expired, module_unknown, bad_item, conv_again, incomplete, et default.

Le dernier de ceux-ci, default, implique 'toutes les valeurN' non mentionnées explicitement. Notez que la liste complète des erreurs PAM est disponible dans /usr/include/security/_pam_types.h. L'actionN peut prendre l'une des formes suivantes :

ignore

lorsqu'elle est utilisée avec une pile de modules, le statut de retour du module ne contribuera pas au code de retour que l'application obtient.

bad

cette action indique que le code de retour doit être considéré comme indicatif de l'échec du module. Si ce module est le premier de la pile à échouer, sa valeur de statut sera utilisée pour celle de toute la pile. C'est l'action par défaut pour tous les codes de retour.

die

équivalent à bad avec pour effet secondaire de terminer la pile de modules et le retour immédiat de PAM à l'application.

ok

cela indique à PAM que l'administrateur pense que ce code de retour doit contribuer directement au code de retour de la pile complète des modules. En d'autres termes, si l'état précédent de la pile conduit à un retour de PAM_SUCCESS, le code de retour du module remplacera cette valeur. Notez que si l'état précédent de la pile contient une valeur indicative de l'échec d'un module, cette valeur 'ok' ne sera pas utilisée pour remplacer cette valeur.

done

équivalent à ok avec pour effet secondaire de terminer la pile de modules et le retour immédiat de PAM à l'application, sauf s'il y a eu un échec de module non ignoré auparavant.

pam.conf(5) — Linux-PAM Manual

NAME

pam.conf — PAM configuration file format

DESCRIPTION

The PAM library, libpam, is a framework that allows system administrators to configure authentication, authorization, account management, and session management services independently of the applications that use these services. This is accomplished through the use of PAM configuration files.

There are two ways to configure libpam: using a single configuration file, /etc/pam.conf, or using a directory structure, /etc/pam.d/. The former is the traditional method, while the latter is becoming more common.

The format of the configuration files is similar for both methods. Each line in the configuration file is structured as follows:

    service-name  type  control  module-path  module-arguments

The fields are:

service-name
The name of the service (application) that the PAM module is for. For example, the login service would use login as its service-name. Some modules can apply to all services if the service-name is set to other. The service-name is not present in the files under the /etc/pam.d/ directory.
type
This field specifies the PAM management group to which the module belongs. There are four types: auth, account, password, and session.
control
This field specifies how the return code from the module call is handled. The control flags are:
required
The module must succeed. If it fails, its return code is ignored, but subsequent modules in the stack are still executed. If the module fails, and it is the last module in the stack for this type, the result of the PAM transaction will be failure. However, if any other module in the stack succeeds, the result of the PAM transaction will be success.
requisite
The module must succeed. If it fails, its return code is ignored, and subsequent modules in the stack are not executed. The result of the PAM transaction will be failure. There is one exception: if all modules in the stack have already succeeded, then the transaction result is success.
sufficient
The module must not fail. If it succeeds, and all preceding modules of the same type have already succeeded, the module stack is terminated. The result of the PAM transaction will be success, and subsequent modules of this type are not called. If the module fails, its return code is ignored, and subsequent modules are executed.
optional
The module's return code is always ignored. These modules are typically used for logging purposes.
include
This control flag causes the specified module stack to be included in the current module stack. The module stack defined in the specified file is executed. The return code of the included module stack is the return code of the last module in that stack.
[valueN]
This is a form of the control flag, where N is an unsigned integer. It is used to specify a module that has a specific action associated with a return code. For example, [success=ok new_authtok_reqd=done ignore=ignore default=bad]. The actions are:
ok
Module success.
done
Module success, and the module stack is terminated. The result of the PAM transaction will be success.
no_user
Module success, but the user is not considered authenticated. This is used for modules that perform tasks like checking for root privileges without requiring a user login.
map
Module success, but the user is not considered authenticated. This is used for modules that perform tasks like mapping a user identity without requiring a user login.
access
Module success, but the user is not considered authenticated. This is used for modules that perform tasks like checking access control lists without requiring a user login.
ignore
Module return code is ignored. The module stack continues to the next module.
reset
Module return code is ignored. The module stack is reset, and the PAM transaction starts again from the beginning with the next module.
bad
Module failure. The module stack is terminated. The result of the PAM transaction will be failure.
die
Module failure. The module stack is terminated. The result of the PAM transaction will be failure, and all subsequent modules in the stack are ignored.
పం
Module failure. The module stack is terminated. The result of the PAM transaction will be failure, and all subsequent modules in the stack are ignored. This is equivalent to die.
N (an unsigned integer)
Jump over the next N modules in the stack. Note that N equal to 0 is not allowed, it would be treated as ignore in such case. The side effect depends on the PAM function call: for pam_authenticate, pam_acct_mgmt, pam_chauthtok, and pam_open_session it is ignore; for pam_setcred and pam_close_session it is one of ignore, ok, or bad depending on the module's return value.
reset
Clear all memory of the state of the module stack and start again with the next stacked module.

If a return code's action is not specifically defined via a valueN token, and the default value is not specified, that return code's action defaults to bad.

Each of the four keywords: required; requisite; sufficient; and optional, have an equivalent expression in terms of the [...] syntax. They are as follows:

required

[success=ok new_authtok_reqd=ok ignore=ignore default=bad]

requisite

[success=ok new_authtok_reqd=ok ignore=ignore default=die]

sufficient

[success=done new_authtok_reqd=done default=ignore]

optional

[success=ok new_authtok_reqd=ok default=ignore]
module-path
The path to the PAM module to be loaded. This can be an absolute path (starting with '/') or a relative path. If it's a relative path, it is interpreted relative to the default PAM module directory, which is typically /lib/security/ or /lib64/security/.
module-arguments
A space-separated list of arguments that are passed to the PAM module. These arguments are specific to each module and are used to customize its behavior. If an argument contains spaces, it must be enclosed in square brackets (e.g., [argument with spaces]).

module-path is either the full filename of the PAM to be used by the application (it begins with a '/'), or a relative pathname from the default module location: /lib/security/ or /lib64/security/, depending on the architecture.

module-arguments are a space separated list of tokens that can be used to modify the specific behavior of the given PAM. Such arguments will be documented for each individual module. Note, if you wish to include spaces in an argument, you should surround that argument with square brackets.

    squid auth required pam_mysql.so user=passwd_query passwd=mada \
          db=eminence [query=select user_name from internet_service \
          where user_name='%u' and password=PASSWORD('%p') and \
        service='web_proxy']

When using this convention, you can include `[' characters inside the string, and if you wish to include a `]' character inside the string that will survive the argument parsing, you should use `\]'. In other words:

    [..[..\]..]    -->   ..[..]..

Any line in (one of) the configuration file(s), that is not formatted correctly, will generally tend (erring on the side of caution) to make the authentication process fail. A corresponding error is written to the system log files with a call to syslog(3).

More flexible than the single configuration file is it to configure libpam via the contents of pam.d directories. In this case the directories are filled with files each of which has a filename equal to a service-name (in lower-case): it is the personal configuration file for the named service.

Vendor-supplied PAM configuration files might be installed in the system directory /usr/lib/pam.d/ or a configurable vendor specific directory instead of the machine configuration directory /etc/pam.d/. If no machine configuration file is found, the vendor-supplied file is used. All files in /etc/pam.d/ override files with the same name in other directories.

The syntax of each file in pam.d is similar to that of the /etc/pam.conf file and is made up of lines of the following form:

type  control  module-path  module-arguments

The only difference being that the service-name is not present. The service-name is of course the name of the given configuration file. For example, /etc/pam.d/login contains the configuration for the login service.

FILES

/etc/pam.conf

the configuration file

/etc/pam.d

the Linux-PAM configuration directory. Generally, if this directory is present, the /etc/pam.conf file is ignored.

/usr/lib/pam.d

the Linux-PAM vendor configuration directory. Files in /etc/pam.d override files with the same name in this directory.
