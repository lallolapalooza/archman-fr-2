Conception de GNU Parallel

Ce document décrit les décisions de conception prises lors du développement de GNU parallel et les raisons qui les sous-tendent. Il donnera un aperçu de la raison pour laquelle une partie du code est telle qu'elle est, et aidera les nouveaux mainteneurs à mieux comprendre le code.

Programme en un seul fichier

GNU parallel est un script Perl en un seul fichier. Il est orienté objet, mais contrairement aux scripts Perl normaux, chaque classe n'est pas dans son propre fichier. Ceci est dû à l'expérience utilisateur : l'objectif est qu'en cas de besoin, l'utilisateur puisse faire fonctionner GNU parallel simplement en copiant un seul fichier : pas besoin de se compliquer la vie avec des variables d'environnement comme PERL5LIB.

Choix du langage de programmation

GNU parallel est conçu pour pouvoir fonctionner sur de vieux systèmes. Cela signifie qu'il ne peut pas dépendre de l'installation d'un compilateur - et surtout pas d'un compilateur pour un langage plus jeune que 20 ans.

L'objectif est que vous puissiez utiliser GNU parallel sur n'importe quel système, même si vous n'êtes pas autorisé à installer de logiciels supplémentaires.

Parmi tous les systèmes que j'ai connus, je n'ai jamais vu un système qui avait GCC installé et qui n'avait pas Perl. Il en va de même pour Rust, Go, Haskell et d'autres langages plus jeunes. J'ai cependant vu des systèmes avec Perl sans aucun des compilateurs mentionnés.

La plupart des systèmes modernes ont également Python2 ou Python3 installé, mais vous ne pouvez toujours pas être sûr de la version, et comme Python2 ne peut pas s'exécuter sous Python3, Python n'est pas une option.

Perl a l'avantage supplémentaire de faciliter l'implémentation de la chaîne de remplacement {= perlexpr =}.

Le principal inconvénient est que Perl est lent. Il y a donc une surcharge de 3 à 10 ms par tâche et de 1 ms par Mo de sortie (et encore plus si vous utilisez --tag).

Ancien style Perl

GNU parallel utilise certaines constructions anciennes et obsolètes. Ceci est dû à l'objectif d'être capable de fonctionner sur de vieilles installations. Actuellement, la cible est CentOS 3.9 et Perl 5.8.0.

Évolutivité ascendante et descendante

Le plus petit système sur lequel GNU parallel est testé est un ASUS WL500gP de 32 Mo. Le plus grand est une machine de 2 To à 128 cœurs. Il s'adapte jusqu'à environ 100 machines - en fonction de la durée de chaque tâche.

Rétroaction exponentielle

GNU parallel attend activement (busy waits). C'est parce que la raison pour laquelle une tâche n'est pas lancée peut être due à la charge moyenne (lors de l'utilisation de --load), et il n'est donc pas judicieux de simplement attendre qu'une tâche se termine. Au lieu de cela, la charge moyenne doit être vérifiée régulièrement. La charge moyenne n'est pas la seule raison : --timeout pose un problème similaire.

Pour ne pas consommer trop de CPU, GNU parallel dort de plus en plus longtemps de manière exponentielle si rien ne se passe, plafonnant à 1 seconde.

Compatibilité Shell

L'objectif est que GNU parallel fonctionne de manière égale dans n'importe quel shell. Cependant, en pratique, GNU parallel est développé en bash et les tests dans d'autres shells sont donc limités aux bugs signalés.

Lorsqu'une incompatibilité est trouvée, il n'y a souvent pas de solution facile : corriger le problème dans csh le casse souvent dans bash. Dans ces cas, la solution consiste souvent à utiliser un petit script Perl et à l'appeler.

env_parallel

env_parallel est un script shell factice qui s'exécutera si env_parallel n'est pas un alias ou une fonction et informera l'utilisateur sur la manière d'activer l'alias/la fonction pour les shells pris en charge.

L'alias ou la fonction copiera l'environnement actuel et exécutera la commande avec GNU parallel dans la copie de l'environnement.

Le problème est que vous ne pouvez pas accéder à tout l'environnement actuel dans Perl. Par exemple, les alias, les fonctions et les variables shell non exportées.

L'idée est donc de prendre l'environnement et de le placer dans $PARALLEL_ENV, que GNU parallel préfixe à chaque commande.

La seule façon d'accéder à l'environnement est directement depuis le shell, donc le programme doit être écrit dans un script shell qui sera sourcé et qui devra gérer le dialecte du shell concerné.

env_parallel.*

Ce sont les fichiers qui implémentent l'alias ou la fonction env_parallel pour un shell donné. On pourrait soutenir que ces fichiers devraient être placés dans un endroit obscur sous /usr/lib, mais en les plaçant dans votre PATH, il devient trivial de trouver leur chemin et de les sourcer :

source `which env_parallel.foo`

La beauté est qu'ils peuvent être placés n'importe où dans le PATH sans que l'utilisateur ait besoin de connaître leur emplacement. Ainsi, si le PATH de l'utilisateur inclut /afs/bin/i386_fc5 ou /usr/pkg/parallel/bin ou /usr/local/parallel/20161222/sunos5.6/bin, les fichiers peuvent être placés dans le répertoire qui a le plus de sens pour l'administrateur système.

env_parallel.bash / env_parallel.sh / env_parallel.ash / env_parallel.dash / env_parallel.zsh / env_parallel.ksh / env_parallel.mksh

env_parallel.(bash|sh|ash|dash|ksh|mksh|zsh) définit la fonction env_parallel. Elle utilise alias et typeset pour exporter la configuration (avec quelques exceptions) dans $PARALLEL_ENV avant d'exécuter GNU parallel.

Une fois GNU parallel terminé, $PARALLEL_ENV est supprimé.

env_parallel.csh

env_parallel.csh a deux objectifs : Si env_parallel n'est pas un alias : en faire un alias qui définit $PARALLEL avec des arguments et appelle env_parallel.csh.

Si env_parallel est un alias, alors env_parallel.csh utilise $PARALLEL comme arguments pour GNU parallel.

Il exporte l'environnement en écrivant une définition de variable dans un fichier pour chaque variable. Les définitions des alias sont ajoutées à ce fichier. Enfin, le fichier est placé dans $PARALLEL_ENV.

GNU parallel est alors exécuté et $PARALLEL_ENV est supprimé.

env_parallel.fish

D'abord, toutes les définitions de fonctions sont générées à l'aide d'une boucle et de functions.

Exporter les définitions de variables scalaires est plus difficile.

fish peut représenter des caractères non imprimables de (au moins) 2 manières. Pour éviter les problèmes, tous les scalaires sont convertis en quoting \XX.

Ensuite, des commandes pour générer les définitions sont créées et séparées par NUL.

Ceci est ensuite pipé dans un script Perl qui quote toutes les valeurs. Les éléments de liste seront ajoutés en utilisant deux espaces.

Enfin, \n est converti en \1 car les variables fish ne peuvent pas contenir de \n. GNU parallel convertira plus tard tous les \1 de $PARALLEL_ENV en \n.

Ceci est ensuite sauvegardé dans $PARALLEL_ENV.

GNU parallel est appelé, et $PARALLEL_ENV est supprimé.

parset (supporté en sh, ash, dash, bash, zsh, ksh, mksh)

parset est une fonction shell. C'est la raison pour laquelle parset peut définir des variables : il s'exécute dans le shell qui l'appelle.

C'est aussi la raison pour laquelle parset ne fonctionne pas lorsque des données lui sont envoyées par pipe : ... | parset ... fait démarrer parset dans un sous-shell, et les changements d'environnement ne peuvent donc pas revenir au shell appelant.

Emplacements de tâche

La façon la plus simple d'expliquer ce que fait GNU parallel est de supposer qu'il existe un certain nombre d'emplacements de tâche, et lorsqu'un emplacement devient disponible, une tâche de la file d'attente sera exécutée dans cet emplacement. Mais à l'origine, GNU parallel ne modélisait pas les emplacements de tâche dans le code. Les emplacements de tâche ont été ajoutés pour permettre l'utilisation de {%} comme chaîne de remplacement.

Version du protocole Rsync

rsync 3.1.x utilise le protocole 31 qui n'est pas pris en charge par la version 2.5.7. Cela signifie que vous ne pouvez pas pousser un fichier vers un système distant en utilisant le protocole rsync 31, si le système distant utilise la version 2.5.7. rsync ne rétrograde pas automatiquement vers le protocole 30.

GNU parallel ne nécessite pas le protocole 31, donc si la version de rsync est >= 3.1.0, alors --protocol 30 est ajouté pour forcer les versions plus récentes de rsync à communiquer avec la version 2.5.7.

Options de commodité --nice --basefile --transfer --return --cleanup --tmux --group --compress --cat --fifo --workdir --tag --tagstring

Ce sont toutes des options de commodité qui facilitent l'exécution d'une tâche. Mais plus important encore : elles sont testées pour fonctionner même dans des cas limites. Prenez --nice comme exemple :

nice parallel command ...

fonctionnera très bien. Mais lorsqu'il est exécuté à distance, vous devez déplacer la commande nice de manière à ce qu'elle soit exécutée sur le serveur :

parallel -S serveur nice command ...

Et cela fonctionnera à nouveau très bien, tant que vous exécutez une seule commande. Lorsque vous exécutez une commande composée, vous avez besoin que nice s'applique à l'ensemble de la commande, et cela devient encore plus difficile :

parallel -S serveur -q nice bash -c 'command1 ...; cmd2 | cmd3'

Ce n'est pas impossible, mais en utilisant --nice, GNU parallel fera la bonne chose pour vous. De même en transférant des fichiers : cela devient difficile lorsque les noms de fichiers contiennent des espaces, :, `, *, ou d'autres caractères spéciaux.

Pour exécuter les commandes dans une session tmux, il suffit essentiellement de mettre la commande entre guillemets. Pour les commandes simples, c'est facile, mais lorsque les commandes contiennent des caractères spéciaux, il devient beaucoup plus difficile d'y parvenir.

--compress compresse non seulement la sortie standard (stdout) mais aussi l'erreur standard (stderr) ; et ce, dans des fichiers, qui sont ouverts mais supprimés, de sorte qu'un crash ne laissera pas ces fichiers traîner.

--cat et --fifo sont faciles à faire à la main, jusqu'à ce que vous vouliez nettoyer le fichier temporaire et conserver le code de sortie de la commande.

Le vrai tueur survient lorsque vous essayez de combiner plusieurs de ces options : le faire correctement pour tous les cas limites est presque impossible à faire à la main.

--shard

La manière simple d'implémenter le sharding serait de :

1.
démarrer n tâches,
2.
diviser chaque ligne en colonnes,
3.
sélectionner les données de la colonne pertinente
4.
calculer une valeur de hachage à partir des données
5.
prendre le modulo n de la valeur de hachage
6.
transmettre la ligne complète à la slot de tâche ayant la valeur calculée

Malheureusement, Perl est assez lent pour calculer la valeur de hachage (et un peu lent pour diviser en colonnes).

Une solution consiste à utiliser un langage compilé pour la division et le hachage, mais cela irait à l'encontre des critères de conception de ne pas dépendre d'un compilateur.

Heureusement, ces tâches peuvent être parallélisées. Ainsi, GNU parallel démarre n sharders qui effectuent les étapes 2 à 6, et leur transmet des blocs de 100k de manière cyclique. Pour s'assurer que ces sharders calculent le hachage de la même manière, $PERL_HASH_SEED est défini à la même valeur pour tous les sharders.

L'exécution de n sharders pose un nouveau problème : au lieu d'avoir n sorties (une pour chaque valeur calculée), vous avez maintenant n sorties pour chacune des n valeurs, soit un total de n*n sorties ; et vous devez fusionner ces n*n sorties en n sorties.

Cela peut être fait en exécutant simplement 'parallel -j0 --lb cat ::: outputs_for_one_value', mais c'est assez inefficace, car il lance un processus pour chaque fichier. Au lieu de cela, le code principal de 'parcat' est exécuté, ce qui est également un peu plus rapide.

Tous les sharders et parcats communiquent via des pipes nommés qui sont désolidarisés dès qu'ils sont ouverts.

Shell shock

Le bug shell shock dans bash n'a pas affecté GNU parallel, mais les solutions si. bash a d'abord introduit les fonctions dans des variables nommées : BASH_FUNC_myfunc() et plus tard a changé cela en BASH_FUNC_myfunc%%. Lors du transfert de fonctions, GNU parallel lit la fonction et la transforme en une définition de fonction, qui est copiée sur le système distant et exécutée avant l'exécution de la commande réelle. Par conséquent, GNU parallel doit savoir comment lire la fonction.

À partir de la version 20150122, GNU parallel essaie les deux versions : celle avec () et celle avec %%, et la définition de fonction fonctionne sur les versions de bash avant et après shell shock.

Le wrapper du système distant

Le wrapper du système distant effectue une initialisation avant de démarrer la commande sur le système distant.

Rendre les guillemets inutiles en encodant tout en hexadécimal

Lorsque vous exécutez ssh serveur foo, foo doit être cité une fois :

ssh serveur "echo foo; echo bar"

Si vous exécutez ssh server1 ssh server2 foo, foo doit être cité deux fois :

ssh server1 ssh server2 \'"echo foo; echo bar"\'

GNU parallel évite cela en regroupant tout en valeurs hexadécimales et en exécutant une commande qui ne nécessite pas de guillemets :

perl -X -e GNU_Parallel_worker,eval+pack+q/H10000000/,join+q//,@ARGV

Cette commande lit des valeurs hexadécimales à partir de la ligne de commande et les convertit en octets qui sont ensuite évalués comme une expression Perl.

La chaîne GNU_Parallel_worker n'est pas nécessaire. Elle est simplement là pour faire savoir à l'utilisateur que ce processus est un travailleur GNU parallel.

Ctrl-C et erreur standard (stderr)

Si l'utilisateur appuie sur Ctrl-C, les tâches s'arrêtent comme prévu. Cela fonctionne immédiatement si les tâches sont exécutées localement. Malheureusement, ce n'est pas si simple si les tâches sont exécutées à distance.

Si les tâches distantes sont exécutées dans un tty à l'aide de ssh -tt, Ctrl-C fonctionne, mais toutes les sorties vers l'erreur standard (stderr) sont envoyées à la sortie standard (stdout). Ce n'est pas ce que l'utilisateur attend.

Si les tâches distantes sont exécutées sans tty à l'aide de ssh (sans -tt), la sortie vers l'erreur standard (stderr) reste sur stderr, mais Ctrl-C ne tue pas les tâches distantes. Ce n'est pas ce que l'utilisateur attend.

Il faut donc un moyen d'avoir les deux. Il semble que la raison pour laquelle Ctrl-C ne tue pas les tâches distantes est que le shell ne propage pas le signal de déconnexion de sshd. Mais lorsque sshd meurt, le parent du shell de connexion devient init (processus id 1). Ainsi, en exécutant un wrapper Perl pour surveiller le pid parent et tuer l'enfant si le pid parent devient 1, alors Ctrl-C fonctionne et stderr reste sur stderr.

Ctrl-C tue cependant la connexion ssh, de sorte que toute sortie d'un processus distant mourant est perdue.

Pour pouvoir tuer tous les (petits)*enfants, un nouveau groupe de processus est démarré.

--nice

L'application de nice au processus distant est effectuée par setpriority(0,0,$nice). Quelques vieux systèmes n'implémentent pas cela et --nice n'est pas pris en charge sur ceux-ci.

Définition de $PARALLEL_TMP

$PARALLEL_TMP est utilisé par --fifo et --cat et doit pointer vers un fichier inexistant dans $TMPDIR. Ce nom de fichier est calculé sur le système distant.

Le wrapper

Le wrapper ressemble à ceci :

$shell = $PARALLEL_SHELL || $SHELL;
$tmpdir = $TMPDIR || $PARALLEL_REMOTE_TMPDIR;
$nice = $opt::nice;
$termseq = $opt::termseq;
# Vérifier que $tmpdir est inscriptible
-w $tmpdir ||
    die("$tmpdir n'est pas inscriptible.".
      " Définir PARALLEL_REMOTE_TMPDIR");
# Définir $PARALLEL_TMP sur un nom de fichier inexistant dans $TMPDIR
do {
    $ENV{PARALLEL_TMP} = $tmpdir."/par".
      join"", map { (0..9,"a".."z","A".."Z")[rand(62)] } (1..5);
} while(-e $ENV{PARALLEL_TMP});
# Définir $script sur un nom de fichier inexistant dans $TMPDIR
do {
    $script = $tmpdir."/par".
      join"", map { (0..9,"a".."z","A".."Z")[rand(62)] } (1..5);
} while(-e $script);
# Créer un script à partir du code hexadécimal
# qui se supprime et exécute les commandes
open($fh,">",$script) || die;
# ' nécessaire en raison du shell rc
print($fh("rm \'$script\'\n",$bashfunc.$cmd));
close $fh;
my $parent = getppid;
my $done = 0;
$SIG{CHLD} = sub { $done = 1; };
$pid = fork;
unless($pid) {
    # Créer son propre groupe de processus pour pouvoir le tuer avec HUP plus tard
    eval { setpgrp };
    # Définir la valeur nice
    eval { setpriority(0,0,$nice) };
    # Exécuter le script
    exec($shell,$script);
    die("échec de l'exécution : $!");
}
while((not $done) and (getppid == $parent)) {
    # Le pid parent n'est pas modifié, donc sshd est vivant
    # Somme exponentielle jusqu'à 1 seconde
    $s = $s < 1 ? 0.001 + $s * 1.03 : $s;
    select(undef, undef, undef, $s);
}
if(not $done) {
    # sshd est mort : l'utilisateur a appuyé sur Ctrl-C
    # Tuer selon --termseq
    my @term_seq = split/,/,$termseq;
    if(not @term_seq) {
      @term_seq
= ("TERM",200,"TERM",100,"TERM",50,"KILL",25); } while(@term_seq && kill(0,-$pid)) { kill(shift @term_seq, -$pid); select(undef, undef, undef, (shift @term_seq)/1000); } } wait; exit ($?&127 ? 128+($?&127) : 1+$?>>8)

Transfert des variables et des fonctions

Le transfert des variables et des fonctions spécifiées par --env est effectué en exécutant à distance un script Perl qui appelle la commande réelle. Le script Perl définit $ENV{variable} à la valeur correcte avant d'exécuter un shell qui exécute la définition de la fonction suivie de la commande réelle.

La fonction env_parallel copie l'environnement complet actuel dans la variable d'environnement PARALLEL_ENV. Cette variable est récupérée par GNU parallel et utilisée pour créer le script Perl mentionné ci-dessus.

Bzip2 codé en Base64

csh limite les mots des commandes à 1024 caractères. C'est souvent insuffisant lorsque GNU parallel code les variables d'environnement et encapsule la commande avec différents modèles. Tous ces éléments sont combinés et mis entre guillemets en un seul mot, qui est souvent plus long que 1024 caractères.

Lorsque la ligne à exécuter est > 1000 caractères, GNU parallel code donc la ligne à exécuter. Le codage applique bzip2 à la ligne à exécuter, la convertit en base64, divise la base64 en blocs de 1000 caractères (afin que csh ne génère pas d'erreur) et la préfixe avec ce script Perl qui décode, décompresse et evalue la ligne.

@GNU_Parallel=("use","IPC::Open3;","use","MIME::Base64");
eval "@GNU_Parallel";
$SIG{CHLD}="IGNORE";
# Recherche de bzip2. Non trouvé => utilise le chemin par défaut
my $zip = (grep { -x $_ } "/usr/local/bin/bzip2")[0] || "bzip2";
# $in = stdin sur $zip, $out = stdout de $zip
my($in, $out,$eval);
open3($in,$out,">&STDERR",$zip,"-dc");
if(my $perlpid = fork) {
    close $in;
    $eval = join "", <$out>;
    close $out;
} else {
    close $out;
    # Envoie le base64 décodé dans 'bzip2 -dc'
    print $in (decode_base64(join"",@ARGV));
    close $in;
    exit;
}
wait;
eval $eval;

Perl et bzip2 doivent être installés sur le système distant, mais un petit test a montré que bzip2 est installé par défaut sur toutes les plateformes qui exécutent GNU parallel, ce n'est donc pas un gros problème.

Le bonus supplémentaire est que des environnements beaucoup plus grands peuvent maintenant être transférés car ils seront inférieurs à la limite de 131072 caractères de bash.

Quel shell utiliser

Les différents shells se comportent différemment. Une commande qui fonctionne dans tcsh peut ne pas fonctionner dans bash. Il est donc important que le bon shell soit utilisé lorsque GNU parallel exécute des commandes.

GNU parallel fait de gros efforts pour utiliser le bon shell. Si GNU parallel est appelé depuis tcsh, il utilisera tcsh. S'il est appelé depuis bash, il utilisera bash. Il fait cela en examinant le processus (grand)*parent : si le processus (grand)*parent est un shell, utiliser ce shell ; sinon, examiner le parent de ce (grand)*parent. Si aucun des (grand)*parents n'est un shell, alors $SHELL est utilisé.

Cela fonctionnera correctement si appelé depuis :

  • un shell interactif
  • un script shell
  • un script Perl en `` ou utilisant system si appelé comme une chaîne unique.

Bien que cela couvre la plupart des cas, il existe des situations où cela échouera :

  • Lorsqu'exécuté en utilisant exec.
  • Lorsqu'exécuté comme dernière commande en utilisant -c depuis un autre shell (car certains shells utilisent exec) : 
    zsh% bash -c "parallel 'echo {} is not run in bash; \
     set | grep BASH_VERSION' ::: This"

    Vous pouvez contourner cela en ajoutant '&& true' :

    zsh% bash -c "parallel 'echo {} is run in bash; \
     set | grep BASH_VERSION' ::: This && true"
  • Lorsqu'exécuté dans un script Perl en utilisant system avec parallel comme première chaîne : 
    #!/usr/bin/perl
system("parallel","setenv a {}; echo $a",":::",2);

    Ici, cela dépend du shell utilisé pour appeler le script Perl. Si le script Perl est appelé depuis tcsh, cela fonctionnera parfaitement, mais s'il est appelé depuis bash, cela échouera, car la commande setenv n'est pas connue de bash.

Si GNU parallel se trompe dans ces situations, définissez le shell en utilisant $PARALLEL_SHELL.

Toujours exécuter les commandes dans un shell

Si la commande est une commande simple sans redirection ni définition de variables, la commande *pourrait* être exécutée sans lancer de shell. Par exemple, ce simple grep correspondant soit à 'ls ' soit à ' wc >> c' :

parallel "grep -E 'ls | wc >> c' {}" ::: foo

pourrait être exécuté comme suit :

system("grep","-E","ls | wc >> c","foo");

Cependant, dès que la commande devient un peu plus complexe, un shell *doit* être lancé :

parallel "grep -E 'ls | wc >> c' {} | wc >> c" ::: foo
parallel "LANG=C grep -E 'ls | wc >> c' {}" ::: foo

Il est impossible de savoir comment | wc >> c doit être interprété sans analyser la chaîne (le | est-il un pipe dans le shell ou une alternance dans une expression régulière grep ? LANG=C est-il une commande dans csh ou la définition d'une variable dans bash ? >> est-il une redirection ou fait-il partie d'une expression régulière ?).

En plus de cela, les scripts wrappers nécessiteront souvent qu'un shell soit lancé.

Le désavantage est que vous devez mettre des caractères spéciaux du shell entre guillemets deux fois :

parallel echo '*' ::: Ceci va étendre l'astérisque
parallel echo "'*'" ::: Ceci ne le fera pas
parallel "echo '*'" ::: Ceci ne le fera pas
parallel echo '\*' ::: Ceci ne le fera pas
parallel echo \''*'\' ::: Ceci ne le fera pas
parallel -q echo '*' ::: Ceci ne le fera pas

-q mettra entre guillemets tous les caractères spéciaux, par conséquent la redirection ne fonctionnera pas : ceci affiche '* > out.1' et n'enregistre *pas* '*' dans le fichier out.1 :

parallel -q echo "*" ">" out.{} ::: 1

GNU parallel essaie de respecter le Principe de Moindre Surprise (POLA), et l'exigence d'utiliser -q est difficile à comprendre lorsque l'on ne voit pas l'image complète.

Mise entre guillemets

La mise entre guillemets dépend du shell. Pour la plupart des shells, la mise entre guillemets avec '-' est utilisée pour les chaînes contenant des caractères spéciaux.

Pour tcsh/csh, le saut de ligne est mis entre guillemets sous la forme \ suivi d'un saut de ligne. D'autres caractères spéciaux sont également mis entre guillemets avec \.

Pour rc, tout est mis entre guillemets en utilisant '.

--pipepart vs. --pipe

Bien que --pipe et --pipepart semblent très similaires pour l'utilisateur, ils sont implémentés très différemment.

Avec --pipe, GNU parallel lit les blocs depuis l'entrée standard (stdin), qui est ensuite transmise à la commande sur l'entrée standard (stdin) ; ainsi, chaque bloc est traité par GNU parallel lui-même. C'est la raison pour laquelle --pipe atteint un maximum d'environ 500 Mo/sec.

--pipepart, en revanche, identifie d'abord à quelles positions d'octets commencent les blocs et quelle est leur longueur. Il le fait en cherchant dans le fichier par la taille d'un bloc, puis en lisant jusqu'à ce qu'il rencontre la fin d'un bloc. La recherche explique pourquoi GNU parallel ne connaît pas le numéro de ligne et pourquoi -L/-l et -N ne fonctionnent pas.

Avec une taille de bloc et de fichier raisonnable, cette recherche est plus de 1000 fois plus rapide que la lecture du fichier complet. Les positions d'octets sont ensuite transmises à un petit script qui lit de la position X à Y et envoie la sortie vers la sortie standard (stdout). Ce petit script est préfixé à la commande et la commande complète est exécutée comme si GNU parallel était en mode normal. Le script ressemble à ceci :

< file perl -e 'while(@ARGV) {
   sysseek(STDIN,shift,0) || die;
   $left = shift;
   while($read = sysread(STDIN,$buf,
                         ($left > 131072 ? 131072 : $left))){
     $left -= $read; syswrite(STDOUT,$buf);
   }
}' startbyte length_in_bytes

Il délivre 1 Go/sec par cœur.

Au lieu du script, dd a été essayé, mais de nombreuses versions de dd ne supportent pas la lecture d'un octet à un autre et peuvent causer des données partielles. Voir ceci pour un exemple surprenant : 

yes | dd bs=1024k count=10 | wc

--block-size adjustment

Chaque fois que GNU parallel détecte un enregistrement plus grand que --block-size, il augmente la taille du bloc de 30%. Une petite valeur de --block-size donne de très mauvaises performances ; en augmentant exponentiellement la taille du bloc, les performances ne sont pas affectées.

GNU parallel gaspillera de la puissance CPU si --block-size ne contient pas un enregistrement complet, car il essaie de trouver un enregistrement complet et échouera. La recommandation est donc d'utiliser un --block-size > 2 enregistrements, de sorte que vous obteniez toujours au moins un enregistrement complet lorsque vous lisez un bloc.

Si vous utilisez -N, alors --block-size devrait être assez grand pour contenir N+1 enregistrements.

Calcul automatique de --block-size

Avec --pipepart, GNU parallel peut calculer automatiquement le --block-size. Un --block-size de -1 utilisera une taille de bloc telle que chaque slot de travail recevra approximativement 1 bloc. --block -2 passera 2 blocs à chaque slot de travail et -n passera n blocs à chaque slot de travail.

Cela peut être fait car --pipepart lit à partir de fichiers, et nous pouvons calculer la taille totale de l'entrée.

--jobs et --onall

Lors de l'exécution des mêmes commandes sur de nombreux serveurs, que doit signifier --jobs ? Est-ce le nombre de serveurs sur lesquels exécuter en parallèle ? Est-ce le nombre de travaux exécutés en parallèle sur chaque serveur ?

GNU parallel laisse --jobs représenter le nombre de serveurs sur lesquels exécuter en parallèle. Ceci afin de permettre l'exécution d'une séquence de commandes (qui ne peut pas être parallélisée) sur chaque serveur, mais d'exécuter la même séquence sur plusieurs serveurs.

--shuf

Lorsque vous utilisez --shuf pour mélanger les tâches, toutes les tâches sont lues, puis elles sont mélangées et enfin exécutées. Lors de l'utilisation de SQL, c'est le --sqlmaster qui mélange les tâches. Les --sqlworker exécutent simplement selon le numéro de séquence.

--csv

--pipepart est incompatible avec --csv car vous pouvez avoir des enregistrements comme :

a,b,c
a,"
a,b,c
a,b,c
a,b,c
",c
a,b,c

Ici, le deuxième enregistrement contient un champ multiligne qui ressemble à des enregistrements. Comme --pipepart ne lit pas tout le fichier lors de la recherche des terminaisons d'enregistrement, il peut commencer à lire dans ce champ multiligne, ce qui serait incorrect.

Mise en mémoire tampon sur disque

GNU parallel met en mémoire tampon la sortie, car si la sortie n'est pas mise en mémoire tampon, vous devez être ridiculement prudent quant aux tailles pour éviter le mélange des sorties (voir l'excellent exemple sur https://catern.com/posts/pipes.html).

GNU parallel met en mémoire tampon sur disque dans $TMPDIR à l'aide de fichiers, qui sont supprimés dès leur création, mais qui restent ouverts. Ainsi, même si GNU parallel est arrêté par une panne de courant, il n'y aura aucun fichier à nettoyer par la suite. Un autre avantage est que le système de fichiers sait que ces fichiers seront perdus en cas de crash, il n'a donc pas besoin de les synchroniser sur disque.

Cela crée la situation étrange qu'un disque peut être complètement utilisé, mais qu'il n'y a aucun fichier visible dessus.

Mise en mémoire tampon partielle en mémoire

Lors de l'utilisation des formats de sortie SQL et CSV, GNU Parallel doit lire toute la sortie en mémoire. Lorsqu'il est exécuté normalement, il ne lit que la sortie d'un seul travail. Mais lors de l'utilisation de --linebuffer, chaque ligne imprimée sera également mise en mémoire tampon en mémoire - pour tous les travaux en cours d'exécution.

Si la mémoire est limitée, n'utilisez pas le format de sortie SQL/CSV avec --linebuffer.

Disque plein

GNU parallel met en mémoire tampon sur disque. Si le disque est plein, des données peuvent être perdues. Pour vérifier si le disque est plein, GNU parallel écrit un fichier de 8193 octets chaque seconde. Si ce fichier est écrit avec succès, il est immédiatement supprimé. S'il n'est pas écrit avec succès, le disque est plein. La taille 8193 a été choisie car 8192 donnait un résultat incorrect sur certains systèmes de fichiers, tandis que 8193 fonctionnait correctement sur tous les systèmes de fichiers testés.

Utilisation de la mémoire

Normalement, GNU parallel utilise environ 17 Mo de RAM en permanence - peu importe le nombre de tâches ou la quantité de sortie. Plusieurs éléments peuvent augmenter l'utilisation de la mémoire :

  • Sources d'entrée multiples. GNU parallel ne lit une source d'entrée qu'une seule fois. Ceci est intentionnel, car une source d'entrée peut être un flux (par exemple, FIFO, pipe, entrée standard (stdin)) qui ne peut pas être rembobiné et relu. Lors de la lecture d'une seule source d'entrée, la mémoire est libérée dès que le travail est terminé - maintenant ainsi l'utilisation de la mémoire constante.

    Mais lors de la lecture de plusieurs sources d'entrée, GNU parallel conserve les valeurs déjà lues pour générer toutes les combinaisons avec d'autres sources d'entrée.

  • Calcul du nombre de tâches. --bar, --eta et --halt xx% utilisent total_jobs() pour calculer le nombre total de tâches. Cela se fait en générant les structures de données pour toutes les tâches. Toutes ces structures de données de tâches seront stockées en mémoire et occuperont environ 400 octets par tâche.
  • Mise en mémoire tampon d'une ligne complète. --linebuffer lira une ligne complète par tâche en cours d'exécution. Une ligne de sortie très longue (disons 1 Go sans \n) augmentera temporairement l'utilisation de la RAM : depuis le début de la lecture de la ligne jusqu'à son impression.
  • Mise en mémoire tampon de la sortie complète d'une seule tâche. Cela se produit lors de l'utilisation de --results *.csv/*.tsv ou --sql*. Ici, GNU parallel lira toute la sortie d'une seule tâche et l'enregistrera au format csv/tsv ou SQL.

Séparateurs d'arguments ::: :::: :::+ ::::+

Le séparateur d'arguments ::: a été choisi car je n'ai jamais vu ::: utilisé dans aucune commande. Le choix naturel -- serait une mauvaise idée car il n'est pas improbable que la commande modèle contienne --. J'ai vu :: utilisé dans les langages de programmation pour séparer les classes, et je ne voulais pas que l'utilisateur soit confus quant au fait que le séparateur avait quelque chose à voir avec les classes.

::: crée également une séparation visuelle, ce qui est bien s'il y a plusieurs :::.

Lorsque ::: a été choisi, :::: est venu comme une extension assez naturelle.

Lier les sources d'entrée impliquait de choisir une manière d'indiquer la liaison de ::: et ::::. :::+ et ::::+ ont été choisis, de sorte qu'ils soient similaires à ::: et ::::.

En 2022, j'ai réalisé que /// aurait été un choix encore meilleur, car vous ne pouvez pas avoir un fichier nommé /// alors que vous *pouvez* avoir un fichier nommé :::.

Chaînes de remplacement Perl, {= =}, et --rpl

Les raccourcis pour les chaînes de remplacement rendent une commande plus cryptique. Différents utilisateurs auront besoin de chaînes de remplacement différentes. Au lieu d'inventer plus de raccourcis, vous obtenez des chaînes de remplacement plus flexibles si elles peuvent être programmées par l'utilisateur.

Le langage Perl a été choisi car GNU parallel est écrit en Perl et il était facile et raisonnablement rapide d'exécuter le code fourni par l'utilisateur.

Si un utilisateur a besoin de la même chaîne de remplacement programmée encore et encore, il peut vouloir créer son propre raccourci pour cela. C'est à cela que sert --rpl. Cela fonctionne si bien que même les propres raccourcis de GNU parallel sont implémentés à l'aide de --rpl.

En code Perl, les bigrammes {= et =} existent rarement. Ils ressemblent à une paire correspondante et peuvent être saisis sur tous les claviers. Cela en a fait de bons candidats pour encadrer l'expression Perl dans les chaînes de remplacement. Un autre candidat ,, et ,, a été rejeté car ils ne ressemblent pas à une paire correspondante. --parens a été créé, de sorte que les utilisateurs peuvent toujours utiliser ,, et ,, s'ils le souhaitent : --parens ,,,,

Cependant, en interne, {= et =} sont remplacés par \257< et \257>. Ceci afin de simplifier la création d'expressions régulières. Vous n'avez besoin de regarder qu'un caractère en avance, et jamais de regarder en arrière.

Suite de tests

GNU parallel utilise son propre cadre de test. C'est principalement pour des raisons historiques. Il gère raisonnablement bien les tests qui dépendent de la durée d'exécution d'un test donné (par exemple, plus de 10 secondes est une réussite, mais moins est un échec). Il parallélise la plupart des tests, mais il est facile de forcer un test à s'exécuter comme seul test (ce qui peut être important pour les problèmes de synchronisation). Il gère raisonnablement bien les tests qui échouent de manière intermittente. Il détecte les tests qui ont échoué et les met en premier, de sorte que lors de l'exécution répétée de la suite de tests, les tests qui ont échoué le plus récemment sont exécutés en premier.

Si GNU parallel devait adopter un véritable cadre de test, ces éléments seraient importants.

Étant donné que de nombreux tests dépendent du matériel sur lequel ils sont exécutés, ces tests échouent lorsqu'ils sont exécutés sur un matériel différent de celui pour lequel le test a été écrit.

Lorsque la plupart des bogues sont corrigés, un test est ajouté, afin que ce bogue ne réapparaisse pas. Il est cependant parfois difficile de créer l'environnement dans lequel le bogue se manifeste - surtout si le bogue ne se manifeste que parfois. L'un des problèmes les plus difficiles a été de faire en sorte qu'une machine commence à swapper sans la mettre à genoux.

Temps d'exécution médian

L'utilisation d'un pourcentage pour --timeout amène GNU parallel à calculer le temps d'exécution médian d'une tâche. La médiane est un meilleur indicateur du temps d'exécution attendu que la moyenne, car il y aura souvent des valeurs aberrantes prenant beaucoup plus de temps que le temps d'exécution normal.

Pour éviter de conserver tous les temps d'exécution en mémoire, une implémentation de remedian a été créée (Rousseeuw et al).

Déterminer le nombre de CPU

CPU est un terme ambigu. Il peut signifier le nombre de sockets remplis (c'est-à-dire le nombre de puces physiques). Il peut signifier le nombre de cœurs (c'est-à-dire le nombre de cœurs de calcul physiques). Il peut signifier le nombre de cœurs hyperthreadés (c'est-à-dire le nombre de cœurs virtuels - certains pouvant être hyperthreadés).

Sur ark.intel.com, Intel utilise les termes cores et threads pour le nombre de cœurs physiques et le nombre de cœurs hyperthreadés respectivement.

GNU parallel utilise CPUs comme nombre d'unités de calcul et les termes sockets, cores, et threads pour spécifier comment le nombre d'unités de calcul est calculé.

Calcul de la charge

Contrairement à ce que l'on pourrait penser, --load n'utilise pas la charge moyenne. En effet, la charge moyenne augmente trop lentement. Il utilise plutôt ps pour lister le nombre de threads en cours d'exécution ou bloqués (état D, O ou R). Cela donne une charge instantanée.

Comme le calcul de la charge à distance peut être lent, un processus est lancé pour exécuter ps et placer le résultat dans un fichier, qui est ensuite utilisé la fois suivante.

Tuer les jobs

GNU parallel tue les jobs. Cela peut être dû à --memfree, --halt, ou lorsque GNU parallel rencontre une condition dont il ne peut pas se remettre. Chaque job est lancé en tant que son propre groupe de processus. De cette façon, tous les enfants (ou petits-enfants) seront également tués. Le groupe de processus est tué avec la spécification mentionnée dans --termseq.

Interface SQL

GNU parallel utilise l'URL de la base de données (DBURL) de GNU sql pour fournir le logiciel de base de données, le nom d'utilisateur, le mot de passe, l'hôte, le port, la base de données et la table en une seule chaîne.

La DBURL doit pointer vers un nom de table. La table sera supprimée et créée. La raison de ne pas réutiliser une table existante est que l'utilisateur peut avoir ajouté plus de sources d'entrée, ce qui nécessiterait plus de colonnes dans la table. En ajoutant '+' devant la DBURL, la table ne sera pas supprimée.

Les colonnes de la table sont similaires à celles de joblog, avec l'ajout de V1 à Vn qui sont des valeurs provenant des sources d'entrée, et Stdout et Stderr qui sont les sorties de la sortie standard et de l'erreur standard, respectivement.

La colonne Signal a été renommée en _Signal, car Signal est un mot réservé en MySQL.

Avis de citation

Pour plus de détails: Voir https://git.savannah.gnu.org/cgit/parallel.git/tree/doc/citation-notice-faq.txt

Financer un projet de logiciel libre est difficile. GNU parallel ne fait pas exception. De plus, il semble que moins un projet est visible, plus il est difficile d'obtenir un financement. Et la nature de GNU parallel fait qu'il ne sera jamais vu par "le type avec le chéquier", mais seulement par les personnes qui font le travail réel.

Ce problème a été abordé par d'autres - bien qu'aucune solution n'ait été trouvée: https://www.slideshare.net/NadiaEghbal/consider-the-maintainer https://www.numfocus.org/blog/why-is-numpy-only-now-getting-funded/

Avant de mettre en œuvre l'avis de citation, il a été discuté avec les utilisateurs: https://lists.gnu.org/archive/html/parallel/2013-11/msg00006.html

Passer 10 secondes à exécuter parallel --citation une fois n'est sans doute pas une solution idéale, mais personne n'a encore trouvé de solution idéale - ni pour financer GNU parallel, ni pour d'autres logiciels libres.

Si vous pensez avoir la solution parfaite, vous devriez l'essayer et, si elle fonctionne, la publier sur la liste de diffusion par e-mail. Les idées qui coûteront du travail et qui n'ont pas été testées ne seront probablement pas priorisées.

L'exécution de parallel --citation une seule fois prend moins de 10 secondes et fera taire l'avis de citation pour les exécutions futures. Ceci est comparable aux outils graphiques où vous devez cliquer sur une case à cocher disant "Ne plus afficher". Mais si cela représente trop de tracas pour vous, pourquoi ne pas utiliser l'une des alternatives? Voir une liste dans: man parallel_alternatives.

Comme la demande de citation n'est pas une exigence légale, cela est acceptable en vertu de la GPLv3 et a été approuvé par Richard M. Stallman lui-même. Elle ne relève donc pas de: https://www.gnu.org/licenses/gpl-faq.en.html#RequireCitation

Décisions historiques

Ces décisions étaient pertinentes pour les versions antérieures de GNU parallel, mais pas pour la version actuelle. Elles sont conservées ici comme enregistrement historique.

--tollef

Vous pouvez lire l'histoire de GNU parallel sur https://www.gnu.org/software/parallel/history.html

--tollef a été inclus pour rendre GNU parallel compatible avec le parallel de moreutils (qui est fait par Tollef Fog Heen). Cela a été fait afin que les utilisateurs de ce parallel puissent facilement porter leur utilisation vers GNU parallel: il suffisait de définir PARALLEL="--tollef" et ce serait tout.

Mais plusieurs distributions ont choisi de rendre --tollef global (en le plaçant dans /etc/parallel/config) sans en informer les utilisateurs, et cela a causé beaucoup de confusion lorsque les gens essayaient les exemples de la page de manuel de GNU parallel et que ceux-ci ne fonctionnaient pas. Les utilisateurs étaient frustrés car la distribution ne leur indiquait pas clairement qu'elle avait rendu --tollef global.

Donc, pour réduire la frustration et le support qui en résultait, --tollef a été rendu obsolète le 20130222 et supprimé un an plus tard.
