NOM

pam.conf, pam.d - Fichiers de configuration PAM

DESCRIPTION

Lorsqu'une application reconnaissant PAM accordant des privilèges est démarrée, elle active sa connexion à l'API PAM. Cette activation effectue un certain nombre de tâches, la plus importante étant la lecture du ou des fichiers de configuration : /etc/pam.conf. Alternativement et de préférence, la configuration peut être définie par des fichiers de configuration individuels situés dans un répertoire pam.d. La présence de ce répertoire amènera Linux-PAM à *ignorer* /etc/pam.conf.

Ces fichiers listent les *PAM* qui effectueront les tâches d'authentification requises par ce service, et le comportement approprié de l'API PAM en cas d'échec des PAM individuels.

La syntaxe du fichier de configuration /etc/pam.conf est la suivante. Le fichier est composé d'une liste de règles, chaque règle étant typiquement placée sur une seule ligne, mais peut être étendue avec un caractère d'échappement de fin de ligne : `\<LF>'. Les commentaires sont précédés de marques `#` et s'étendent jusqu'à la fin de la ligne suivante.

Le format de chaque règle est une collection de jetons séparés par des espaces, les trois premiers étant insensibles à la casse :

service type contrôle chemin-module arguments-module

La syntaxe des fichiers contenus dans le répertoire /etc/pam.d/ est identique, à l'exception de l'absence de tout champ *service*. Dans ce cas, le *service* est le nom du fichier dans le répertoire /etc/pam.d/. Ce nom de fichier doit être en minuscules.

Une caractéristique importante de *PAM* est qu'un certain nombre de règles peuvent être *empilées* pour combiner les services d'un certain nombre de PAM pour une tâche d'authentification donnée.

Le *service* est typiquement le nom familier de l'application correspondante : *login* et *su* en sont de bons exemples. Le nom de *service*, *other*, est réservé pour donner des règles *par défaut*. Seules les lignes mentionnant le service actuel (ou en l'absence de telles, les entrées *other*) seront associées à l'application de service donnée.

Le *type* est le groupe de gestion auquel correspond la règle. Il est utilisé pour spécifier à quel groupe de gestion le module suivant doit être associé. Les entrées valides sont :

account

ce type de module effectue la gestion de compte non basée sur l'authentification. Il est typiquement utilisé pour restreindre/permettre l'accès à un service en fonction de l'heure de la journée, des ressources système actuellement disponibles (nombre maximum d'utilisateurs) ou peut-être de l'emplacement de l'utilisateur demandeur -- connexion de `root` uniquement sur la console.

auth

ce type de module offre deux aspects de l'authentification de l'utilisateur. Premièrement, il établit que l'utilisateur est qui il prétend être, en demandant à l'application de solliciter un mot de passe ou d'autres moyens d'identification. Deuxièmement, le module peut accorder une appartenance à un groupe ou d'autres privilèges grâce à ses propriétés d'octroi de crédentials.

password

ce type de module est requis pour la mise à jour du jeton d'authentification associé à l'utilisateur. Typiquement, il y a un module pour chaque type d'authentification basé sur le 'défi/réponse' (auth).

session

ce type de module est associé à l'exécution d'opérations qui doivent être effectuées pour l'utilisateur avant/après qu'il puisse recevoir un service. De telles opérations incluent la journalisation d'informations concernant l'ouverture/la fermeture d'un échange de données avec un utilisateur, le montage de répertoires, etc.

Si la valeur de *type* de la liste ci-dessus est précédée d'un caractère `-`, la bibliothèque PAM ne journalisera pas dans le journal système s'il n'est pas possible de charger le module parce qu'il est manquant dans le système. Ceci peut être utile en particulier pour les modules qui ne sont pas toujours installés sur le système et qui ne sont pas requis pour une authentification et une autorisation correctes de la session de connexion.

Le troisième champ, *contrôle*, indique le comportement de l'API PAM si le module échoue à réussir dans sa tâche d'authentification. Il existe deux types de syntaxe pour ce champ de contrôle : la syntaxe simple a un seul mot-clé simple ; la plus compliquée implique une sélection entre crochets de paires `valeur=action`.

Pour la syntaxe simple (historique), les valeurs de *contrôle* valides sont :

required

l'échec d'un tel PAM conduira finalement l'API PAM à retourner un échec, mais seulement après que les modules *empilés* restants (pour ce *service* et ce *type*) aient été invoqués.

requisite

comme *required*, cependant, dans le cas où un tel module retourne un échec, le contrôle est directement retourné à l'application ou à la pile PAM supérieure. La valeur de retour est celle associée au premier module required ou requisite qui échoue. Notez que ce drapeau peut être utilisé pour se protéger contre la possibilité qu'un utilisateur obtienne l'opportunité de saisir un mot de passe sur un support non sécurisé. Il est concevable qu'un tel comportement puisse informer un attaquant de l'existence de comptes valides sur un système. Cette possibilité doit être pesée par rapport aux préoccupations non négligeables d'exposition d'un mot de passe sensible dans un environnement hostile.

sufficient

si un tel module réussit et qu'aucun module *required* précédent n'a échoué, le framework PAM retourne immédiatement un succès à l'application ou à la pile PAM supérieure sans appeler d'autres modules dans la pile. Un échec d'un module *sufficient* est ignoré et le traitement de la pile de modules PAM continue sans interruption.

optional

le succès ou l'échec de ce module n'est important que s'il est le seul module de la pile associé à ce *service*+*type*.

include

inclure toutes les lignes du type donné du fichier de configuration spécifié comme argument à ce contrôle.

substack

inclure toutes les lignes du type donné du fichier de configuration spécifié comme argument à ce contrôle. Ceci diffère de *include* en ce que l'évaluation des actions *done* et *die* dans un substack ne provoque pas le saut du reste de la pile de modules complète, mais seulement du substack. Les sauts dans un substack ne peuvent pas non plus faire sortir l'évaluation de celui-ci, et l'ensemble du substack est compté comme un module lorsque le saut est effectué dans une pile parente. L'action *reset* réinitialisera l'état d'une pile de modules à l'état qu'elle avait au début de l'évaluation du substack.

Pour la syntaxe plus compliquée, les valeurs de *contrôle* valides ont la forme suivante :

      [valeur1=action1 valeur2=action2 ...]

Où *valeurN* correspond au code de retour de la fonction invoquée dans le module pour lequel la ligne est définie. Il est sélectionné parmi les suivants : *success*, *open_err*, *symbol_err*, *service_err*, *system_err*, *buf_err*, *perm_denied*, *auth_err*, *cred_insufficient*, *authinfo_unavail*, *user_unknown*, *maxtries*, *new_authtok_reqd*, *acct_expired*, *session_err*, *cred_unavail*, *cred_expired*, *cred_err*, *no_module_data*, *conv_err*, *authtok_err*, *authtok_recover_err*, *authtok_lock_busy*, *authtok_disable_aging*, *try_again*, *ignore*, *abort*, *authtok_expired*, *module_unknown*, *bad_item*, *conv_again*, *incomplete*, et *default*.

Ce dernier, *default*, implique 'toutes les valeurs *valeurN*' non mentionnées explicitement. Notez que la liste complète des erreurs PAM est disponible dans /usr/include/security/_pam_types.h. L'*actionN* peut prendre l'une des formes suivantes :

ignore

lorsqu'il est utilisé avec une pile de modules, le statut de retour du module ne contribuera pas au code de retour obtenu par l'application.

bad

cette action indique que le code de retour doit être considéré comme indiquant un échec du module. Si ce module est le premier de la pile à échouer, sa valeur de statut sera utilisée pour l'ensemble de la pile. C'est l'action par défaut pour tous les codes de retour.

die

équivalent à *bad* avec l'effet secondaire de terminer la pile de modules et de retourner immédiatement PAM à l'application.

ok

cela indique à PAM que l'administrateur pense que ce code de retour devrait contribuer directement au code de retour de la pile complète de modules. Autrement dit, si l'état précédent de la pile conduirait à un retour de *PAM_SUCCESS*, le code de retour du module remplacera cette valeur. Notez que si l'état précédent de la pile contient une valeur indiquant un échec de module, cette valeur 'ok' ne sera pas utilisée pour remplacer cette valeur.

done

équivalent à *ok* avec l'effet secondaire de terminer la pile de modules et de retourner immédiatement PAM à l'application, sauf s'il y a eu un échec de module non ignoré auparavant.

NOM

pam.d - configuration files for Linux-PAM

DESCRIPTION

The PAM library, see pam(3), provides a framework for managing authentication, account management, session management, and password management. The framework is designed to be flexible and pluggable, allowing system administrators to configure how these services are provided without having to recompile the applications that use them. The PAM configuration files are used to specify which modules are to be used for each service and how they are to be used.

The PAM configuration file format is described in detail in the pam.conf(5) man page. This man page focuses on the use of the pam.d directory, which is now the preferred way of configuring PAM services.

The pam.d directory contains configuration files for individual services. Each file in the directory is named after the service it configures. For example, the file /etc/pam.d/login contains the PAM configuration for the login service. This approach is generally preferred over the single /etc/pam.conf file because it allows for easier management of PAM configurations, especially in systems with many services.

Each line in a pam.d configuration file specifies a single PAM module to be used for a particular service and control flag. The format of each line is:

type  control  module-path  module-arguments

Where:

type
This specifies the PAM management group to which the module belongs. The possible values are:
auth
Handles authentication tasks, such as verifying user passwords or biometric data.
account
Handles account management tasks, such as checking if an account has expired or if a user is allowed to log in at a particular time.
password
Handles password management tasks, such as changing user passwords.
session
Handles session management tasks, such as setting up and tearing down user environments.
control
This specifies how the return value of the module is to be handled. The possible values are:
required
The module must succeed. If it fails, its return value is ignored, but the overall result of the call will be failure if any subsequent module fails.
requisite
The module must succeed. If it fails, its return value is immediately returned to the application, and no further modules are executed.
sufficient
If the module succeeds, its return value is returned to the application, and no further modules in the same group are executed. If it fails, its return value is ignored.
optional
The module's return value is always ignored. This is useful for modules that perform actions but do not need to contribute to the overall success or failure of the call.
default
This is a special keyword that specifies the default action for any return code not explicitly handled by the module. The default action is bad, meaning that if a return code is not handled, the module is considered to have failed.
module-path
This is the path to the PAM module to be used. It can be an absolute path (starting with '/') or a relative path from the default module location (/lib/security/ or /lib64/security/).
module-arguments
These are space-separated arguments that are passed to the PAM module. These arguments can be used to customize the behavior of the module. If an argument contains spaces, it should be enclosed in square brackets. For example: [user=someuser passwd=somepass query="select ..."].

The following actions can be specified for the control field:

N (an unsigned integer)

jump over the next N modules in the stack. Note that N equal to 0 is not allowed, it would be treated as ignore in such case. The side effect depends on the PAM function call: for pam_authenticate, pam_acct_mgmt, pam_chauthtok, and pam_open_session it is ignore; for pam_setcred and pam_close_session it is one of ignore, ok, or bad depending on the module's return value.

reset

clear all memory of the state of the module stack and start again with the next stacked module.

If a return code's action is not specifically defined via a valueN token, and the default value is not specified, that return code's action defaults to bad.

Each of the four keywords: required; requisite; sufficient; and optional, have an equivalent expression in terms of the [...] syntax. They are as follows:

required

[success=ok new_authtok_reqd=ok ignore=ignore default=bad]

requisite

[success=ok new_authtok_reqd=ok ignore=ignore default=die]

sufficient

[success=done new_authtok_reqd=done default=ignore]

optional

[success=ok new_authtok_reqd=ok default=ignore]

module-path is either the full filename of the PAM to be used by the application (it begins with a '/'), or a relative pathname from the default module location: /lib/security/ or /lib64/security/, depending on the architecture.

module-arguments are a space separated list of tokens that can be used to modify the specific behavior of the given PAM. Such arguments will be documented for each individual module. Note, if you wish to include spaces in an argument, you should surround that argument with square brackets.

    squid auth required pam_mysql.so user=passwd_query passwd=mada \
          db=eminence [query=select user_name from internet_service \
          where user_name='%u' and password=PASSWORD('%p') and \
        service='web_proxy']

When using this convention, you can include `[' characters inside the string, and if you wish to include a `]' character inside the string that will survive the argument parsing, you should use `\]'. In other words:

    [..[..\]..]    -->   ..[..]..

Any line in (one of) the configuration file(s), that is not formatted correctly, will generally tend (erring on the side of caution) to make the authentication process fail. A corresponding error is written to the system log files with a call to syslog(3).

More flexible than the single configuration file is it to configure libpam via the contents of pam.d directories. In this case the directories are filled with files each of which has a filename equal to a service-name (in lower-case): it is the personal configuration file for the named service.

Vendor-supplied PAM configuration files might be installed in the system directory /usr/lib/pam.d/ or a configurable vendor specific directory instead of the machine configuration directory /etc/pam.d/. If no machine configuration file is found, the vendor-supplied file is used. All files in /etc/pam.d/ override files with the same name in other directories.

The syntax of each file in pam.d is similar to that of the /etc/pam.conf file and is made up of lines of the following form:

type  control  module-path  module-arguments

The only difference being that the service-name is not present. The service-name is of course the name of the given configuration file. For example, /etc/pam.d/login contains the configuration for the login service.

FICHIERS

/etc/pam.conf

the configuration file

/etc/pam.d

the Linux-PAM configuration directory. Generally, if this directory is present, the /etc/pam.conf file is ignored.

/usr/lib/pam.d

the Linux-PAM vendor configuration directory. Files in /etc/pam.d override files with the same name in this directory.
