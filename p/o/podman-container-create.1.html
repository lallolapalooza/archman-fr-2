NOM

podman-create - Crée un nouveau conteneur

SYNTAXE

podman create [options] image [commande [arg ...]]

podman container create [options] image [commande [arg ...]]

DESCRIPTION

Crée une couche de conteneur inscriptible par-dessus l'image spécifiée et la prépare pour l'exécution de la commande spécifiée. L'ID du conteneur est ensuite imprimé sur STDOUT. Ceci est similaire à podman run -d sauf que le conteneur n'est jamais démarré. Utilisez la commande podman start conteneur pour démarrer le conteneur à tout moment.

Le statut initial du conteneur créé avec podman create est « created ».

Les paramètres par défaut pour les options sont définis dans containers.conf. La plupart des paramètres pour les connexions à distance utilisent le containers.conf du serveur, sauf indication contraire dans les pages de manuel.

IMAGE

L'image est spécifiée en utilisant le format transport:chemin. Si aucun transport n'est spécifié, le transport docker (registre de conteneurs) est utilisé par défaut. Pour Podman à distance, y compris les machines Mac et Windows (à l'exception de WSL2), docker est le seul transport autorisé.

dir:chemin
Un répertoire local existant chemin stockant le manifest, les archives de couches et les signatures sous forme de fichiers individuels. Ceci est un format non standardisé, principalement utile pour le débogage ou l'inspection non invasive des conteneurs.

$ podman save --format docker-dir fedora -o /tmp/fedora
$ podman create dir:/tmp/fedora echo hello

docker://reference-docker (Par défaut)
Une référence d'image stockée dans un registre d'images de conteneurs distant. Exemple : "quay.io/podman/stable:latest". La référence peut inclure un chemin vers un registre spécifique ; si ce n'est pas le cas, les registres listés dans registries.conf sont interrogés pour trouver une image correspondante. Par défaut, les identifiants de podman login (stockés par défaut dans $XDG_RUNTIME_DIR/containers/auth.json) sont utilisés pour l'authentification ; sinon, il se rabat sur les identifiants dans $HOME/.docker/config.json.

$ podman create registry.fedoraproject.org/fedora:latest echo hello

docker-archive:chemin[:reference-docker] Une image stockée dans le fichier formaté docker save. reference-docker est uniquement utilisée lors de la création d'un tel fichier et ne doit pas contenir de digest.

$ podman save --format docker-archive fedora -o /tmp/fedora
$ podman create docker-archive:/tmp/fedora echo hello

Note : Sur les clients distants, y compris les machines Mac et Windows (à l'exception de WSL2), ce transport n'est pas pris en charge.

docker-daemon:reference-docker
Une image au format reference-docker stockée dans le stockage interne du démon docker. reference-docker peut également être un ID d'image (docker-daemon:algo:digest).

$ sudo docker pull fedora
$ sudo podman create docker-daemon:docker.io/library/fedora echo hello

Note : Sur les clients distants, y compris les machines Mac et Windows (à l'exception de WSL2), ce transport n'est pas pris en charge.

oci-archive:chemin:tag
Une image dans un répertoire conforme à la "Open Container Image Layout Specification" au chemin spécifié et identifiée par un tag.

$ podman save --format oci-archive fedora -o /tmp/fedora
$ podman create oci-archive:/tmp/fedora echo hello

Note : Sur les clients distants, y compris les machines Mac et Windows (à l'exception de WSL2), ce transport n'est pas pris en charge.

OPTIONS

--add-host=nom-hote[;nom-hote[;...]]:ip

Ajoute un mappage personnalisé hôte-IP au fichier /etc/hosts du conteneur.

L'option prend un ou plusieurs noms d'hôtes séparés par des points-virgules à mapper à une seule adresse IPv4 ou IPv6, séparés par un deux-points. Elle peut également être utilisée pour remplacer les adresses IP des noms d'hôtes que Podman ajoute à /etc/hosts par défaut (voir également les options --name et --hostname). Cette option peut être spécifiée plusieurs fois pour ajouter des mappages supplémentaires à /etc/hosts. Elle entre en conflit avec l'option --no-hosts et avec no_hosts=true dans containers.conf.

Au lieu d'une adresse IP, le drapeau spécial host-gateway peut être donné. Ceci résout vers une adresse IP que le conteneur peut utiliser pour se connecter à l'hôte. L'adresse IP choisie dépend de votre configuration réseau, il n'y a donc aucune garantie que Podman puisse déterminer automatiquement l'adresse host-gateway, ce qui provoquera alors une erreur de Podman. Vous pouvez remplacer cette adresse IP en utilisant l'option host_containers_internal_ip dans containers.conf.

L'adresse host-gateway est également utilisée par Podman pour ajouter automatiquement les noms d'hôtes host.containers.internal et host.docker.internal à /etc/hosts. Vous pouvez l'éviter en utilisant l'option --no-hosts ou en définissant host_containers_internal_ip="none" dans containers.conf. Si aucune adresse host-gateway n'a été configurée manuellement et que Podman ne parvient pas à déterminer l'adresse IP automatiquement, Podman ignorera silencieusement l'ajout de ces noms d'hôtes internes à /etc/hosts. Si Podman s'exécute dans une machine virtuelle en utilisant podman machine (cela inclut les hôtes Mac et Windows), Podman ignorera silencieusement l'ajout des noms d'hôtes internes à /etc/hosts, à moins qu'une adresse IP n'ait été configurée manuellement ; les noms d'hôtes internes sont résolus par le résolveur DNS gvproxy à la place.

Podman utilisera par défaut le fichier /etc/hosts de l'hôte comme base, c'est-à-dire que tout nom d'hôte présent dans ce fichier sera également présent dans le fichier /etc/hosts du conteneur. Un fichier de base différent peut être configuré en utilisant la configuration base_hosts_file dans containers.conf.

--annotation=clé=valeur

Ajoute une annotation au conteneur. Cette option peut être définie plusieurs fois.

--arch=ARCH

Remplace l'architecture, par défaut celle de l'hôte, de l'image à télécharger. Par exemple, arm. Sauf remplacement, les recherches ultérieures de la même image dans le stockage local correspondent à cette architecture, indépendamment de l'hôte.

--attach, -a=stdin | stdout | stderr

Attacher à STDIN, STDOUT ou STDERR.

En mode avant-plan (par défaut lorsque -d n'est pas spécifié), podman run peut démarrer le processus dans le conteneur et attacher la console à l'entrée, la sortie et les erreurs standard du processus. Il peut même simuler une TTY (ce que la plupart des exécutables en ligne de commande attendent) et passer les signaux. L'option -a peut être définie pour chacun de stdin, stdout et stderr.

--authfile=chemin

Chemin du fichier d'authentification. Par défaut, c'est ${XDG_RUNTIME_DIR}/containers/auth.json sous Linux, et $HOME/.config/containers/auth.json sous Windows/macOS. Le fichier est créé par podman login. Si l'état d'autorisation n'y est pas trouvé, $HOME/.docker/config.json est vérifié, qui est défini à l'aide de docker login.

Note : Il existe également une option pour remplacer le chemin par défaut du fichier d'authentification en définissant la variable d'environnement REGISTRY_AUTH_FILE. Ceci peut être fait avec export REGISTRY_AUTH_FILE=chemin.

--blkio-weight=poids

Poids relatif de l'entrée/sortie bloc. Le poids est une valeur entre 10 et 1000.

Cette option n'est pas prise en charge sur les systèmes rootless cgroups V1.

--blkio-weight-device=périphérique:poids

Poids relatif de l'entrée/sortie bloc pour un périphérique.

--cap-add=capability

Ajouter des capacités Linux.

Accorder des capacités supplémentaires augmente les privilèges des processus s'exécutant à l'intérieur du conteneur et peut potentiellement lui permettre de s'échapper du confinement. Des capacités telles que CAP_SYS_ADMIN, CAP_SYS_PTRACE, CAP_MKNOD et CAP_SYS_MODULE sont particulièrement dangereuses lorsqu'elles ne sont pas utilisées dans un espace de noms utilisateur. --cap-drop=capability

Supprimer les capacités Linux.

--cert-dir=chemin

Utiliser les certificats dans chemin (*.crt, *.cert, *.key) pour se connecter au registre. (Défaut : /etc/containers/certs.d) Pour plus de détails, voir containers-certs.d(5). (Cette option n'est pas disponible avec le client Podman distant, y compris sur les machines Mac et Windows (hors WSL2))

--cgroup-conf=CLE=VALEUR

Lors de l'exécution sur cgroup v2, spécifiez le fichier cgroup à écrire et sa valeur. Par exemple, --cgroup-conf=memory.high=1073741824 définit la limite de mémoire.high à 1 Go.

--cgroup-parent=chemin

Chemin vers les cgroups sous lequel le cgroup pour le conteneur est créé. Si le chemin n'est pas absolu, il est considéré comme relatif au chemin des cgroups du processus d'initialisation. Les cgroups sont créés s'ils n'existent pas déjà.

--cgroupns=mode

Définir le mode de l'espace de noms cgroup pour le conteneur.

  • host : utiliser l'espace de noms cgroup de l'hôte à l'intérieur du conteneur.
  • container:id : rejoindre l'espace de noms du conteneur spécifié.
  • private : créer un nouvel espace de noms cgroup.
  • ns:chemin : rejoindre l'espace de noms au chemin spécifié.

Si l'hôte utilise cgroups v1, la valeur par défaut est définie sur host. Sur cgroups v2, la valeur par défaut est private.

--cgroups=comment

Détermine si le conteneur crée des cgroups.

La valeur par défaut est enabled.

L'option enabled crée un nouveau cgroup sous le cgroup-parent. L'option disabled force le conteneur à ne pas créer de cgroups, et entre donc en conflit avec les options cgroup (--cgroupns et --cgroup-parent). L'option no-conmon désactive un nouveau cgroup uniquement pour le processus conmon. L'option split divise le cgroup actuel en deux sous-cgroups : un pour conmon et un pour la charge utile du conteneur. Il n'est pas possible de définir --cgroup-parent avec split.

--chrootdirs=chemin

Chemin vers un répertoire à l'intérieur du conteneur qui est traité comme un répertoire chroot. Tout fichier géré par Podman (par exemple, /etc/resolv.conf, /etc/hosts, /etc/hostname) qui est monté dans le répertoire racine est également monté à cet emplacement. Les répertoires multiples sont séparés par une virgule.

--cidfile=fichier

Écrire l'ID du conteneur dans fichier. Le fichier est supprimé avec le conteneur, sauf lorsqu'il est utilisé avec podman --remote run sur des conteneurs détachés.

--conmon-pidfile=fichier

Écrire le PID du processus conmon dans un fichier. Comme conmon s'exécute dans un processus séparé de Podman, cela est nécessaire lors de l'utilisation de systemd pour redémarrer les conteneurs Podman. (Cette option n'est pas disponible avec le client Podman distant, y compris sur les machines Mac et Windows (hors WSL2))

--cpu-period=limite

Définir la période CPU pour le Completely Fair Scheduler (CFS), qui est une durée en microsecondes. Une fois le quota CPU du conteneur épuisé, il ne sera pas planifié avant la fin de la période en cours. La valeur par défaut est de 100 000 microsecondes.

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes sans privilèges cgroups V1.

--cpu-quota=limite

Limiter le quota Completely Fair Scheduler (CFS) du CPU.

Limiter l'utilisation du CPU par le conteneur. Par défaut, les conteneurs s'exécutent avec la totalité des ressources CPU. La limite est un nombre en microsecondes. Si un nombre est fourni, le conteneur est autorisé à utiliser ce temps CPU jusqu'à la fin de la période CPU (contrôlable via --cpu-period).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes sans privilèges cgroups V1.

--cpu-rt-period=microsecondes

Limiter la période temps réel du CPU en microsecondes.

Limiter l'utilisation du CPU en temps réel par le conteneur. Cette option indique au noyau de restreindre l'utilisation du CPU en temps réel du conteneur à la période spécifiée.

Cette option n'est prise en charge que sur les systèmes avec privilèges cgroups V1.

--cpu-rt-runtime=microsecondes

Limiter le temps d'exécution temps réel du CPU en microsecondes.

Limiter l'utilisation du CPU en temps réel des conteneurs. Cette option indique au noyau de limiter la quantité de temps que les tâches en temps réel peuvent consommer dans une période CPU donnée. Par exemple, une période de 1 000 000 us et un temps d'exécution de 950 000 us signifient que ce conteneur peut consommer 95 % du CPU disponible et laisser les 5 % restants aux tâches de priorité normale.

La somme de tous les temps d'exécution entre les conteneurs ne doit pas dépasser la quantité allouée au cgroup parent.

Cette option n'est prise en charge que sur les systèmes avec privilèges cgroups V1.

--cpu-shares, -c=parts

Parts de CPU (poids relatif).

Par défaut, tous les conteneurs reçoivent la même proportion de cycles CPU. Cette proportion peut être modifiée en changeant le poids des parts de CPU du conteneur par rapport au poids combiné de tous les conteneurs en cours d'exécution. Le poids par défaut est de 1024.

La proportion ne s'applique que lorsque des processus gourmands en CPU s'exécutent. Lorsque les tâches d'un conteneur sont inactives, d'autres conteneurs peuvent utiliser le temps CPU restant. La quantité réelle de temps CPU varie en fonction du nombre de conteneurs en cours d'exécution sur le système.

Par exemple, considérons trois conteneurs, l'un a une part de CPU de 1024 et les deux autres ont un réglage de part de CPU de 512. Lorsque les processus des trois conteneurs tentent d'utiliser 100 % du CPU, le premier conteneur reçoit 50 % du temps CPU total. Si un quatrième conteneur est ajouté avec une part de CPU de 1024, le premier conteneur n'obtient que 33 % du CPU. Les conteneurs restants reçoivent respectivement 16,5 %, 16,5 % et 33 % du CPU.

Sur un système multi-cœurs, les parts de temps CPU sont distribuées sur tous les cœurs CPU. Même si un conteneur est limité à moins de 100 % du temps CPU, il peut utiliser 100 % de chaque cœur CPU individuel.

Par exemple, considérez un système avec plus de trois cœurs. Si le conteneur C0 est démarré avec --cpu-shares=512 exécutant un processus, et un autre conteneur C1 avec --cpu-shares=1024 exécutant deux processus, cela peut entraîner la division suivante des parts de CPU :

PID conteneur CPU Part de CPU
100 C0 0 100% du CPU0
101 C1 1 100% du CPU1
102 C1 2 100% du CPU2

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes sans privilèges cgroups V1.

--cpus=nombre

Nombre de CPUs. La valeur par défaut est 0.0, ce qui signifie aucune limite. Ceci est un raccourci pour --cpu-period et --cpu-quota, donc l'option ne peut pas être spécifiée avec --cpu-period ou --cpu-quota.

Sur certains systèmes, la modification des limites CPU peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes sans privilèges cgroups V1.

--cpuset-cpus=nombre

CPUs dans lesquels autoriser l'exécution. Peut être spécifié sous forme de liste séparée par des virgules (par exemple, 0,1), sous forme de plage (par exemple, 0-3), ou toute combinaison de ceux-ci (par exemple, 0-3,7,11-15).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes sans privilèges cgroups V1.

--cpuset-mems=nœuds

Nœuds mémoire (MEMs) dans lesquels autoriser l'exécution (0-3, 0,1). Uniquement efficace sur les systèmes NUMA.

S'il y a quatre nœuds mémoire sur le système (0-3), utilisez --cpuset-mems=0,1, alors les processus dans le conteneur n'utiliseront la mémoire que des deux premiers nœuds mémoire.

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes sans privilèges cgroups V1.

--group-add=groupe | keep-groups

Attribuer des groupes supplémentaires à l'utilisateur principal s'exécutant dans le processus du conteneur.

•
keep-groups est un indicateur spécial qui indique à Podman de conserver l'accès aux groupes supplémentaires.

Permet au conteneur d'utiliser l'accès aux groupes supplémentaires de l'utilisateur. Si les systèmes de fichiers ou les appareils ne sont accessibles que par le groupe de l'utilisateur sans privilèges, cet indicateur indique au runtime OCI de transmettre l'accès au groupe dans le conteneur. --group-entry=ENTRÉE

Personnaliser l'entrée écrite dans le fichier /etc/group du conteneur lorsque --user est utilisé.

Les variables $GROUPNAME, $GID et $USERLIST sont automatiquement remplacées par leur valeur au moment de l'exécution si elles sont présentes.

--health-cmd="commande" | '["commande", arg1 , ...]'

Définir ou modifier une commande de vérification de l'état de santé d'un conteneur. La commande est une commande à exécuter à l'intérieur du conteneur qui détermine l'état de santé du conteneur. La commande est requise pour que les autres options de vérification de l'état de santé soient appliquées. Une valeur de none désactive les vérifications de l'état de santé existantes.

Plusieurs options peuvent être passées sous forme de tableau JSON ; sinon, la commande est interprétée comme un argument de /bin/sh -c.

Remarque : les valeurs par défaut sont utilisées même si la vérification de l'état de santé est configurée dans l'image.

--health-interval=intervalle

Définir un intervalle pour les vérifications de l'état de santé. Un intervalle de disable n'entraîne aucune configuration automatique de minuteur. La valeur par défaut est 30s.

Remarque : ce paramètre remplacera la configuration de vérification de l'état de santé liée à partir de l'image.

--health-log-destination=chemin_répertoire

Définir la destination du journal de vérification de l'état de santé. Chemin du répertoire, local ou events_logger (utilisation locale du fichier d'état du conteneur) (Défaut : local)

  • local : (par défaut) Les journaux de vérification de l'état de santé sont stockés dans les conteneurs de superposition. (Par exemple : $runroot/healthcheck.log)
  • directory : crée un fichier journal nommé <ID_conteneur>-healthcheck.log avec les journaux de vérification de l'état de santé dans le répertoire spécifié.
  • events_logger : le journal sera écrit avec le mécanisme de journalisation défini par events_logger. Il enregistre également le journal dans un répertoire par défaut, pour des performances sur un système comportant un grand nombre de journaux.

--health-max-log-count=nombre de journaux stockés

Définir le nombre maximum de tentatives dans le fichier journal de vérification de l'état de santé ('0' signifie un nombre infini de tentatives dans le fichier journal) (Défaut : 5 tentatives)

--health-max-log-size=taille du journal stocké

Définir la longueur maximale en caractères du journal de vérification de l'état de santé stocké. ("0" signifie une longueur de journal infinie) (Défaut : 500 caractères)

--health-on-failure=action

Action à entreprendre une fois que le conteneur passe à un état de mauvaise santé. La valeur par défaut est none.

  • none : Ne rien faire.
  • kill : Arrêter le conteneur.
  • restart : Redémarrer le conteneur. Ne pas combiner l'action restart avec l'indicateur --restart. Lorsque vous exécutez dans une unité systemd, envisagez d'utiliser plutôt l'action kill ou stop pour profiter de la politique de redémarrage de systemd.
  • stop : Arrêter le conteneur.

--health-retries=tentatives

Le nombre de tentatives autorisées avant qu'une vérification de l'état de santé ne soit considérée comme non saine. La valeur par défaut est 3.

Remarque : ce paramètre peut remplacer la configuration de vérification de l'état de santé de l'image.

--health-start-period=période

Le temps d'initialisation nécessaire au démarrage d'un conteneur. La valeur peut être exprimée dans un format de temps comme 2m3s. La valeur par défaut est 0s.

Remarque : la commande de vérification de l'état de santé est exécutée dès qu'un conteneur est démarré. Si la vérification de l'état de santé réussit, l'état de santé du conteneur sera mis à jour à healthy. Cependant, si la vérification de l'état de santé échoue, l'état de santé restera starting jusqu'à ce que la vérification de l'état de santé réussisse ou jusqu'à ce que la période --health-start-period soit écoulée. Si la commande de vérification de l'état de santé échoue après la fin de la période --health-start-period, l'état de santé sera mis à jour à unhealthy. La commande de vérification de l'état de santé est exécutée périodiquement en fonction de la valeur de --health-interval.

Remarque : ce paramètre remplacera la configuration de vérification de l'état de santé liée à partir de l'image.

--health-startup-cmd="commande" | '["commande", arg1 , ...]'

Définir une commande de vérification de l'état de santé au démarrage pour un conteneur. Cette commande est exécutée à l'intérieur du conteneur et sert à contrôler la vérification régulière de l'état de santé. Lorsque la commande de démarrage réussit, la vérification régulière de l'état de santé commence et la vérification de l'état de santé au démarrage cesse. Facultativement, si la commande échoue un certain nombre de fois, le conteneur est redémarré. Une vérification de l'état de santé au démarrage peut être utilisée pour s'assurer que les conteneurs ayant une période de démarrage prolongée ne sont pas marqués comme non sains tant qu'ils ne sont pas complètement démarrés. Les vérifications de l'état de santé au démarrage ne peuvent être utilisées que lorsqu'une vérification régulière de l'état de santé (provenant de l'image du conteneur ou de l'option --health-cmd) est également définie.

--health-startup-interval=intervalle

Définir un intervalle pour la vérification de l'état de santé au démarrage. Un intervalle de disable n'entraîne aucune configuration automatique de minuteur. La valeur par défaut est 30s.

--health-startup-retries=tentatives

Le nombre de tentatives autorisées avant que la vérification de l'état de santé au démarrage ne redémarre le conteneur. S'il est défini sur 0, le conteneur n'est jamais redémarré. La valeur par défaut est 0.

--health-startup-success=tentatives

Le nombre d'exécutions réussies requis avant que la vérification de l'état de santé au démarrage ne réussisse et que la vérification régulière de l'état de santé ne commence. Une valeur de 0 signifie que toute réussite lance la vérification régulière de l'état de santé. La valeur par défaut est 0.

--health-startup-timeout=délai_d'attente

Le temps maximum dont dispose une commande de vérification de l'état de santé au démarrage pour se terminer avant d'être marquée comme échouée. La valeur peut être exprimée dans un format de temps comme 2m3s. La valeur par défaut est 30s.

--health-timeout=délai_d'attente

Le temps maximum autorisé pour terminer la vérification de l'état de santé avant qu'un intervalle ne soit considéré comme échoué. Comme pour start-period, la valeur peut être exprimée dans un format de temps tel que 1m22s. La valeur par défaut est 30s.

Remarque : un délai d'attente marque la vérification de l'état de santé comme échouée. Si la commande de vérification de l'état de santé elle-même s'exécute plus longtemps que le délai_d'attente spécifié, elle recevra un signal SIGKILL.

Remarque : ce paramètre remplacera la configuration de vérification de l'état de santé liée à partir de l'image.

--mount=type=TYPE,OPTION-SPÉCIFIQUE-TYPE[,...]

Attache un montage de système de fichiers au conteneur.

Les TYPEs de montage actuellement pris en charge sont artifact, bind, devpts, glob, image, ramfs, tmpfs et volume.

Options communes à tous les types de montage :

  • src, source : spécificateur de source de montage pour bind, glob et volume. Obligatoire pour artifact, bind, glob, image et volume.
  • dst, dest, destination, target : spécificateur de destination de montage.

Lorsque les globes sources sont spécifiés sans le répertoire de destination, les fichiers et répertoires sont montés avec leur chemin complet dans le conteneur. Lorsque la destination est spécifiée, les fichiers et répertoires correspondant au globe sur le nom de fichier de base dans le répertoire de destination sont montés. L'option type=glob,src=/foo*,destination=/tmp/bar indique aux moteurs de conteneurs de monter les fichiers hôtes correspondant à /foo* dans le répertoire /tmp/bar/ du conteneur.

Options spécifiques au type=artifact :

  • digest : Si la source de l'artefact contient plusieurs blobs, un digest peut être spécifié pour ne monter que le blob spécifique avec le digest.
  • title : Si la source de l'artefact contient plusieurs blobs, un titre peut être défini et comparé à l'annotation org.opencontainers.image.title.
  • name : Ceci peut être utilisé pour remplacer le nom de fichier que nous utilisons à l'intérieur du conteneur pour le montage. Sur un artefact à blob unique, le nom est utilisé tel quel si dst est un répertoire et sinon ignoré. Avec un artefact à plusieurs blobs, le nom sera utilisé avec un suffixe d'index <nom>-x où x est l'index de la couche dans l'artefact commençant à 0.

L'argument src contient le nom de l'artefact, qui doit déjà exister localement. L'argument dst contient le chemin cible ; si le chemin dans le conteneur est un répertoire, le titre du blob (annotation org.opencontainers.image.title) sera utilisé comme nom de fichier et joint à

le chemin. Si l'annotation n'existe pas, le digest sera utilisé comme nom de fichier à la place. Cela a pour conséquence que tous les blobs de l'artefact sont montés dans le conteneur au chemin donné.

Cependant, si le chemin dst est un fichier existant dans le conteneur, alors le blob sera monté directement dessus. Cela ne fonctionne que lorsque l'artefact contient un seul blob ou lorsque digest ou title sont spécifiés.

Si le chemin dst n'existe pas déjà dans le conteneur, alors si l'artefact contient un seul blob, cela se comporte comme le cas du fichier existant et est monté directement à ce chemin. Si l'artefact contient plus d'un blob, cela fonctionne comme le cas du répertoire existant et monte chaque blob comme un fichier dans le chemin dst.

Options spécifiques au type=volume :

  • ro, readonly : true ou false (par défaut si non spécifié : false).
  • U, chown : true ou false (par défaut si non spécifié : false). Change récursivement le propriétaire et le groupe du volume source en fonction de l'UID et du GID du conteneur.
  • subpath : Monte uniquement un sous-chemin spécifique dans le volume, au lieu du volume entier.
  • idmap : Si spécifié, crée un montage mappé en ID (idmapped mount) vers l'espace de noms utilisateur cible dans le conteneur. L'option idmap n'est prise en charge que par Podman en mode rootful. Le noyau Linux n'autorise pas l'utilisation de systèmes de fichiers mappés en ID pour les utilisateurs non privilégiés. L'option idmap prend en charge un mappage personnalisé qui peut être différent de l'espace de noms utilisateur utilisé par le conteneur. Le mappage peut être spécifié après l'option idmap comme suit : idmap=uids=0-1-10#10-11-10;gids=0-100-10. Pour chaque triplet, la première valeur est le début des ID du système de fichiers source qui sont mappés à la deuxième valeur sur l'hôte. La longueur de ce mappage est donnée par la troisième valeur. Plusieurs plages sont séparées par #. Si le mappage spécifié est préfixé par un '@', le mappage est considéré comme relatif à l'espace de noms utilisateur du conteneur. L'ID hôte du mappage est modifié pour tenir compte de la position relative de l'utilisateur du conteneur dans l'espace de noms utilisateur du conteneur.

Options spécifiques au type=image :

  • rw, readwrite : true ou false (par défaut si non spécifié : false).
  • subpath : Monte uniquement un chemin spécifique dans l'image, au lieu de l'image entière.

Options spécifiques à bind et glob :

  • ro, readonly : true ou false (par défaut si non spécifié : false).
  • bind-propagation : shared, slave, private, unbindable, rshared, rslave, runbindable, ou rprivate (par défaut).[1] ⟨#Footnote1⟩ Voir aussi mount(2).
  • bind-nonrecursive : ne pas configurer de montage bind récursif. Par défaut, il est récursif.
  • relabel : shared, private.
  • idmap : true ou false (par défaut si non spécifié : false). Si vrai, crée un montage mappé en ID (idmapped mount) vers l'espace de noms utilisateur cible dans le conteneur. L'option idmap n'est prise en charge que par Podman en mode rootful.
  • U, chown : true ou false (par défaut si non spécifié : false). Change récursivement le propriétaire et le groupe du volume source en fonction de l'UID et du GID du conteneur.
  • no-dereference : ne pas déréférencer les liens symboliques mais copier la source du lien dans la destination du montage.

Options spécifiques aux types=tmpfs et ramfs :

  • ro, readonly : true ou false (par défaut si non spécifié : false).
  • tmpfs-size : Taille du montage tmpfs/ramfs, en octets. Illimitée par défaut sous Linux.
  • tmpfs-mode : Mode de fichier octal du tmpfs/ramfs (par exemple, 700 ou 0700.).
  • tmpcopyup : Active la copie (copyup) à partir du répertoire de l'image à l'emplacement correspondant vers le tmpfs/ramfs. Utilisé par défaut.
  • noatime : Désactive la mise à jour des heures d'accès aux fichiers lors de leur lecture.
  • notmpcopyup : Désactive la copie des fichiers de l'image vers le tmpfs/ramfs.
  • U, chown : true ou false (par défaut si non spécifié : false). Change récursivement le propriétaire et le groupe du volume source en fonction de l'UID et du GID du conteneur.

Options spécifiques au type=devpts :

  • uid : UID numérique du propriétaire du fichier (par défaut : 0).
  • gid : GID numérique du propriétaire du fichier (par défaut : 0).
  • mode : masque de permissions octal pour le fichier (par défaut : 600).
  • max : nombre maximum de PTY (par défaut : 1048576).

Exemples :

  • type=bind,source=/chemin/sur/hote,destination=/chemin/dans/conteneur
  • type=bind,src=/chemin/sur/hote,dst=/chemin/dans/conteneur,relabel=shared
  • type=bind,src=/chemin/sur/hote,dst=/chemin/dans/conteneur,relabel=shared,U=true
  • type=devpts,destination=/dev/pts
  • type=glob,src=/usr/lib/libfoo*,destination=/usr/lib,ro=true
  • type=image,source=fedora,destination=/fedora-image,rw=true
  • type=ramfs,tmpfs-size=512M,destination=/chemin/dans/conteneur
  • type=tmpfs,tmpfs-size=512M,destination=/chemin/dans/conteneur
  • type=tmpfs,destination=/chemin/dans/conteneur,noswap
  • type=artifact,src=quay.io/libpod/testartifact:20250206-single,dst=/data
  • type=artifact,src=quay.io/libpod/testartifact:20250206-multi,dst=/data,title=test1

--network=mode, --net

Définir le mode réseau pour le conteneur.

Les valeurs valides pour mode sont :

•
bridge[:OPTIONS,...] : Crée une pile réseau sur le pont (bridge) par défaut. C'est le mode par défaut pour les conteneurs rootful. Il est possible de spécifier ces options supplémentaires :
  • alias=nom : Ajoute un alias spécifique à l'étendue du réseau pour le conteneur.
  • ip=IPv4 : Spécifie une adresse IPv4 statique pour ce conteneur.
  • ip6=IPv6 : Spécifie une adresse IPv6 statique pour ce conteneur.
  • mac=MAC : Spécifie une adresse MAC statique pour ce conteneur.
  • interface_name=nom : Spécifie un nom pour l'interface réseau créée à l'intérieur du conteneur.
  • host_interface_name=nom : Spécifie un nom pour l'interface réseau créée à l'extérieur du conteneur.
Toute autre option sera transmise à netavark sans validation. Cela peut être utile pour passer des arguments aux plugins netavark.

Par exemple, pour définir une adresse IPv4 statique et une adresse MAC statique, utilisez --network bridge:ip=10.88.0.10,mac=44:33:22:11:00:99.

  • <nom ou ID de réseau>[:OPTIONS,...] : Connecte à un réseau défini par l'utilisateur ; il s'agit du nom ou de l'ID d'un réseau créé par podman network create. Il est possible de spécifier les mêmes options que celles décrites sous le mode bridge ci-dessus. Utilisez l'option --network plusieurs fois pour spécifier des réseaux supplémentaires.
    Pour des raisons de compatibilité ascendante, il est également possible de spécifier des réseaux séparés par des virgules dans le premier argument --network, mais cela vous empêche d'utiliser les options décrites dans la section bridge ci-dessus.
  • none : Crée un espace de noms réseau pour le conteneur mais ne configure aucune interface réseau pour celui-ci, de sorte que le conteneur n'a aucune connectivité réseau.
  • container:id : Réutilise la pile réseau d'un autre conteneur.
  • host : Utilise l'espace de noms réseau de l'hôte pour le conteneur au lieu d'en créer un isolé. Avertissement : Cela donne au conteneur un accès complet aux sockets Unix abstraits et aux sockets TCP/UDP liés à localhost. Étant donné que ces mécanismes sont souvent utilisés pour empêcher l'accès aux services système sensibles, en les isolant de l'accès par des entités externes, l'utilisation de cette option peut être considérée comme une vulnérabilité de sécurité.
  • ns:chemin : Chemin vers un espace de noms réseau à rejoindre.

    --publish, -p

    Publish container's ports to the host. The format is [ip][:host_port]:container_port[/protocol].

    The container_port is the port exposed by the container. The host_port is the port on the host machine. If the host_port is not specified, it is randomly selected from the range of ports available on the host. The ip is the host IP address to bind to. If not specified, the port is bound to 0.0.0.0 (all IPs).

    When publishing a range of ports, the number of container ports in the range must match the number of host ports in the range.

    If host IP is set to 0.0.0.0 or not set at all, the port is bound on all IPs on the host.

    By default, Podman publishes TCP ports. To publish a UDP port instead, give udp as protocol. To publish both TCP and UDP ports, set --publish twice, with tcp, and udp as protocols respectively. Rootful containers can also publish ports using the sctp protocol.

    Host port does not have to be specified (e.g. podman run -p 127.0.0.1::80). If it is not, the container port is randomly assigned a port on the host.

    Use podman port to see the actual mapping: podman port $CONTAINER $CONTAINERPORT.

    Port publishing is only supported for containers utilizing their own network namespace through bridge networks, or the pasta and slirp4netns network modes.

    Note: If a container runs within a pod, it is not necessary to publish the port for the containers in the pod. The port must only be published by the pod itself. Pod network stacks act like the network stack on the host - when there are a variety of containers in the pod, and programs in the container, all sharing a single interface and IP address, and associated ports. If one container binds to a port, no other container can use that port within the pod while it is in use. Containers in the pod can also communicate over localhost by having one container bind to localhost in the pod, and another connect to that port.

    --publish-all, -P

    Publish all exposed ports to random ports on the host interfaces. The default is false.

    When set to true, publish all exposed ports to the host interfaces. If the operator uses -P (or -p) then Podman makes the exposed port accessible on the host and the ports are available to any client that can reach the host.

    When using this option, Podman binds any exposed port to a random port on the host within an ephemeral port range defined by /proc/sys/net/ipv4/ip_local_port_range. To find the mapping between the host ports and the exposed ports, use podman port.

--secret=secret[,opt=opt ...]

Donne au conteneur l'accès à un secret. Peut être spécifié plusieurs fois.

Un secret est un bloc de données sensibles dont un conteneur a besoin à l'exécution mais qui n'est pas stocké dans l'image ou dans le contrôle de source, tels que des noms d'utilisateur et des mots de passe, des certificats et clés TLS, des clés SSH ou d'autres chaînes génériques importantes ou du contenu binaire (jusqu'à 512 Ko).

Lorsque les secrets sont spécifiés comme type mount, les secrets sont copiés et montés dans le conteneur lors de la création d'un conteneur. Lorsque les secrets sont spécifiés comme type env, le secret est défini comme une variable d'environnement dans le conteneur. Les secrets sont écrits dans le conteneur au moment de la création du conteneur, et la modification du secret à l'aide des commandes podman secret après la création du conteneur affecte le secret à l'intérieur du conteneur.

Les secrets et leur stockage sont gérés à l'aide de la commande podman secret.

Options de secret

  • type=mount|env : Comment le secret est exposé au conteneur.
    mount monte le secret dans le conteneur sous forme de fichier.
    env expose le secret comme une variable d'environnement.
    Par défaut : mount.
  • target=cible : Cible du secret.
    Pour les secrets montés, il s'agit du chemin d'accès au secret à l'intérieur du conteneur.
    Si un chemin d'accès complet est fourni, le secret est monté à cet emplacement.
    Sinon, le secret est monté sur
    /run/secrets/cible pour les conteneurs Linux ou
    /var/run/secrets/cible pour les conteneurs FreeBSD.
    Si la cible n'est pas définie, le secret est monté sur /run/secrets/nomsecret par défaut.
    Pour les secrets env, il s'agit de la clé de variable d'environnement. Par défaut : nomsecret.
  • uid=0 : UID du secret. Par défaut : 0. Type de montage de secret uniquement.
  • gid=0 : GID du secret. Par défaut : 0. Type de montage de secret uniquement.
  • mode=0 : Mode du secret. Par défaut : 0444. Type de montage de secret uniquement.

Exemples

Montage à /my/location/mysecret avec UID 1 :

--secret mysecret,target=/my/location/mysecret,uid=1

Montage à /run/secrets/customtarget avec le mode 0777 :

--secret mysecret,target=customtarget,mode=0777

Créer une variable d'environnement secrète nommée ENVSEC :

--secret mysecret,type=env,target=ENVSEC

Pour plus de détails, voir : https://docs.kernel.org/userspace-api/no_new_privs.html.
  • seccomp=unconfined : Désactive le confinement seccomp pour le conteneur.
  • seccomp=profil.json : Fichier JSON à utiliser comme filtre seccomp. Notez que l'annotation io.podman.annotations.seccomp est définie avec la valeur spécifiée comme indiqué dans podman inspect.
  • proc-opts=OPTIONS : Liste d'options séparées par des virgules à utiliser pour le montage /proc. Plus de détails sur les options de montage possibles sont spécifiés dans la page de manuel proc(5).
  • unmask=TOUT ou /chemin/1:/chemin/2, ou chemins développés par le shell (/proc/*) : Chemins à démasquer séparés par un deux-points. S'il est défini sur TOUT, il démasque tous les chemins qui sont masqués ou rendus en lecture seule par défaut. Les chemins masqués par défaut sont /proc/acpi, /proc/kcore, /proc/keys, /proc/latency_stats, /proc/sched_debug, /proc/scsi, /proc/timer_list, /proc/timer_stats, /sys/firmware, et /sys/fs/selinux, /sys/devices/virtual/powercap. Les chemins par défaut qui sont en lecture seule sont /proc/asound, /proc/bus, /proc/fs, /proc/irq, /proc/sys, /proc/sysrq-trigger, /sys/fs/cgroup.

Note : Le marquage peut être désactivé pour tous les conteneurs en définissant label=false dans le fichier containers.conf(5).

--uidmap=[drapeaux]uid_conteneur:uid_origine[:quantité]

Exécuter le conteneur dans un nouvel espace de noms utilisateur en utilisant le mappage UID fourni. Cette option entre en conflit avec les options --userns et --subuidname. Cette option fournit un moyen de mapper les UIDs de l'hôte aux UIDs du conteneur. Elle peut être passée plusieurs fois pour mapper différentes plages.

Les valeurs possibles des drapeaux optionnels sont discutées plus loin sur cette page. La valeur quantité est optionnelle et supposée être 1 si elle n'est pas fournie.

La valeur uid_origine est basée sur l'utilisateur exécutant la commande, qu'il soit rootful ou rootless.

  • utilisateur rootful : [drapeaux]uid_conteneur:uid_hôte[:quantité]
  • utilisateur rootless : [drapeaux]uid_conteneur:uid_intermédiaire[:quantité]

Mappages rootful

Lorsque podman create est appelé par un utilisateur privilégié, l'option --uidmap fonctionne comme un mappage direct entre les UIDs de l'hôte et les UIDs du conteneur.

UID hôte -> UID conteneur

La quantité spécifie le nombre d'UIDs consécutifs qui sont mappés. Si, par exemple, la quantité est 4, le mappage ressemble à ceci :

UID hôte UID conteneur
uid_origine uid_conteneur
uid_origine + 1 uid_conteneur + 1
uid_origine + 2 uid_conteneur + 2
uid_origine + 3 uid_conteneur + 3

Mappages rootless

Lorsque podman create est appelé par un utilisateur non privilégié (c'est-à-dire exécuté en mode rootless), la valeur uid_origine est interprétée comme un "UID intermédiaire". Dans le cas rootless, les UIDs de l'hôte ne sont pas mappés directement aux UIDs du conteneur. Le mappage s'effectue plutôt en deux étapes :

UID hôte -> UID intermédiaire -> UID conteneur

L'option --uidmap influence uniquement la deuxième étape de mappage.

La première étape de mappage est dérivée par Podman à partir du contenu du fichier /etc/subuid et de l'UID de l'utilisateur appelant Podman.

Première étape de mappage :

UID hôte UID intermédiaire
UID pour l'utilisateur Podman 0
1er UID subordonné 1
2ème UID subordonné 2
3ème UID subordonné 3
nième UID subordonné n

Pour pouvoir utiliser des UIDs intermédiaires supérieurs à zéro, l'utilisateur doit avoir des UIDs subordonnés configurés dans /etc/subuid. Voir subuid(5).

La deuxième étape de mappage est configurée avec --uidmap.

Si, par exemple, la quantité est 5, la deuxième étape de mappage ressemble à ceci :

UID intermédiaire UID conteneur
uid_origine uid_conteneur
uid_origine + 1 uid_conteneur + 1
uid_origine + 2 uid_conteneur + 2
uid_origine + 3 uid_conteneur + 3
uid_origine + 4 uid_conteneur + 4

Lorsqu'il s'exécute en mode rootless, Podman utilise toutes les plages configurées dans le fichier /etc/subuid.

L'ID utilisateur actuel est mappé à UID=0 dans l'espace de noms utilisateur rootless. Chaque plage supplémentaire est ajoutée séquentiellement ensuite :

Hôte Espace de noms utilisateur rootless Longueur
$UID 0 1
1 $PREMIERE_PLAGE_ID $LONGUEUR_PREMIERE_PLAGE
1+$LONGUEUR_PREMIERE_PLAGE $DEUXIEME_PLAGE_ID $LONGUEUR_DEUXIEME_PLAGE

Référencer un ID hôte de l'espace parent

En tant qu'utilisateur rootless, l'ID hôte donné dans --uidmap ou --gidmap est mappé depuis l'espace intermédiaire généré par Podman. Il est parfois souhaitable de se référer directement à l'espace hôte. C'est possible de le faire manuellement, en exécutant podman unshare cat /proc/self/gid_map, en trouvant l'ID hôte désiré dans la deuxième colonne de la sortie, et en récupérant l'ID intermédiaire correspondant de la première colonne.

Podman peut effectuer tout cela en faisant précéder l'ID hôte dans le mappage par le symbole @. Par exemple, en spécifiant --gidmap 100000:@2000:1, podman recherchera l'ID intermédiaire correspondant à l'ID hôte 2000 et mapper la valeur trouvée de l'ID intermédiaire à l'ID de conteneur 100000. L'ID hôte donné doit avoir été subordonné (sinon il ne serait pas mappé dans l'espace intermédiaire en premier lieu).

Si la longueur est supérieure à un, par exemple avec --gidmap 100000:@2000:2, Podman mappera les ID hôtes 2000 et 2001 respectivement à 100000 et 100001, quelle que soit la définition du mappage intermédiaire.

Extension des mappages précédents

Certaines modifications de mappage peuvent être fastidieuses. Par exemple, un utilisateur commence avec un mappage tel que --gidmap="0:0:65000", qui doit être modifié de telle sorte que l'ID parent 1 soit mappé à l'ID de conteneur 100000 au lieu de cela, laissant l'ID de conteneur 1 non assigné. Le --gidmap correspondant devient --gidmap="0:0:1" --gidmap="2:2:65534" --gidmap="100000:1:1".

Cette notation peut être simplifiée en utilisant le drapeau +, qui prend en charge la rupture des mappages précédents en supprimant toute affectation conflictuelle avec le mappage donné. Le drapeau est donné avant l'ID du conteneur comme suit : --gidmap="0:0:65000" --gidmap="+100000:1:1"

Drapeau Exemple Description
+ +100000:1:1 Étendre le mappage précédent

Cette notation entraîne des lacunes dans l'affectation, il peut donc être utile de combler ces lacunes par la suite : --gidmap="0:0:65000" --gidmap="+100000:1:1" --gidmap="1:65001:1"

Un cas d'utilisation spécifique pour ce drapeau est dans le contexte des utilisateurs rootless. Un utilisateur rootless peut spécifier des mappages avec le drapeau + comme dans --gidmap="+100000:1:1". Podman "comblera alors les lacunes" à partir de zéro avec tous les ID intermédiaires restants. Ceci est pratique lorsqu'un utilisateur souhaite mapper un ID intermédiaire spécifique à un ID de conteneur, laissant les autres ID subordonnés être mappés par Podman à volonté.

Passer un seul des --uidmap ou --gidmap

Généralement, les IDs utilisateur et groupe subordonnés sont affectés simultanément, et pour tout utilisateur, les IDs utilisateur subordonnés correspondent aux IDs groupe subordonnés. Pour plus de commodité, si seul l'un des options --uidmap ou --gidmap est donné, podman suppose que le mappage fait référence aux deux UID et GID et applique le mappage donné aux deux. Si seule une des deux valeurs doit être modifiée, les mappages doivent inclure les drapeaux u ou g pour spécifier qu'ils ne s'appliquent qu'aux UID ou GID et ne doivent pas être copiés.

drapeau Exemple Description
u u20000:2000:1 Le mappage s'applique uniquement aux UID
g g10000:1000:1 Le mappage s'applique uniquement aux GID

Par exemple, étant donné la commande

podman create --gidmap "0:0:1000" --gidmap "g2000:2000:1"

Comme aucun --uidmap n'est donné, le --gidmap est copié vers --uidmap, donnant une commande équivalente à

podman create --gidmap "0:0:1000" --gidmap "2000:2000:1" --uidmap "0:0:1000"

Le --gidmap "g2000:2000:1" a utilisé le drapeau g et par conséquent il n'a pas été copié vers --uidmap.

Mappage rootless de GID hôtes supplémentaires

Un utilisateur rootless peut souhaiter mapper un groupe hôte spécifique qui a alr

e déjà été subordonné dans /etc/subgid sans spécifier le reste du mappage.

Cela peut être fait avec --gidmap "+ggid_conteneur:@gid_hote"

Où:

  • Le GID de l'hôte est donné via le symbole @
  • Le mappage de ce GID n'est pas copié vers --usermap grâce au drapeau g.
  • Le reste des GID du conteneur sera mappé à partir de 0 à n, avec tous les GID subordonnés restants, grâce au drapeau +.

Par exemple, si un utilisateur appartient au groupe 2000 et que ce groupe est subordonné à cet utilisateur (avec usermod --add-subgids 2000-2000 $USER), l'utilisateur peut mapper le groupe dans le conteneur avec : --gidmap=+g100000:@2000.

Si ce mappage est combiné avec l'option --group-add=keep-groups, le processus dans le conteneur appartiendra au groupe 100000, et les fichiers appartenant au groupe 2000 sur l'hôte apparaîtront comme appartenant au groupe 100000 à l'intérieur du conteneur.

podman run --group-add=keep-groups --gidmap="+g100000:@2000" ...

Pas d'UID subordonnés

Même si un utilisateur n'a pas d'UID subordonnés dans /etc/subuid, --uidmap peut être utilisé pour mapper l'UID normal de l'utilisateur à un UID de conteneur en exécutant podman create --uidmap $uid_conteneur:0:1 --user $uid_conteneur ....

--ulimit=option

Options Ulimit. Définit les valeurs ulimits à l'intérieur du conteneur.

--ulimit avec une limite douce et une limite dure dans le format =[:]. Par exemple :

$ podman run --ulimit nofile=1024:1024 --rm ubi9 ulimit -n 1024

Définissez -1 pour la limite douce ou dure afin de définir la limite à la limite maximale du processus actuel. En mode rootful, c'est souvent illimité.

Si nofile et nproc ne sont pas définis, une valeur par défaut de 1048576 sera utilisée, sauf si elle est remplacée dans containers.conf(5). Cependant, si la valeur par défaut dépasse la limite dure de l'utilisateur rootless actuel, la limite dure actuelle sera appliquée à la place.

Utilisez host pour copier la configuration actuelle de l'hôte.

N'utilisez pas nproc avec l'indicateur ulimit car Linux utilise nproc pour définir le nombre maximum de processus disponibles pour un utilisateur, et non pour un conteneur.

Utilisez l'option --pids-limit pour modifier le contrôle cgroup afin de limiter le nombre de processus à l'intérieur d'un conteneur.

--umask=umask

Définit l'umask à l'intérieur du conteneur. La valeur par défaut est 0022. Les connexions distantes utilisent le fichier local containers.conf pour les valeurs par défaut.

--unsetenv=env

Supprime les variables d'environnement par défaut pour le conteneur. Les variables d'environnement par défaut incluent les variables fournies nativement par Podman, les variables d'environnement configurées par l'image et les variables d'environnement de containers.conf.

--user, -u=utilisateur[:groupe]

Définit le nom d'utilisateur ou l'UID utilisé et, éventuellement, le nom de groupe ou le GID pour la commande spécifiée. Utilisateur et groupe peuvent être symboliques ou numériques.

Sans cet argument, la commande s'exécute en tant qu'utilisateur spécifié dans l'image du conteneur. Sauf indication contraire par une commande USER dans le Containerfile ou par une valeur passée à cette option, cet utilisateur est généralement défini par défaut sur root.

Lorsqu'un espace de noms utilisateur n'est pas utilisé, l'UID et le GID utilisés à l'intérieur du conteneur et sur l'hôte correspondent. Lorsqu'un espace de noms utilisateur est utilisé, cependant, l'UID et le GID dans le conteneur peuvent correspondre à un autre UID et GID sur l'hôte. Dans les conteneurs sans privilèges (rootless), par exemple, un espace de noms utilisateur est toujours utilisé, et root dans le conteneur correspond par défaut à l'UID et au GID de l'utilisateur qui invoque Podman.

--userns=mode

Définit le mode de l'espace de noms utilisateur pour le conteneur.

Si --userns n'est pas défini, la valeur par défaut est déterminée comme suit. - Si --pod est défini, --userns est ignoré et l'espace de noms utilisateur du pod est utilisé. - Si la variable d'environnement PODMAN_USERNS est définie, sa valeur est utilisée. - Si userns est spécifié dans containers.conf, cette valeur est utilisée. - Sinon, --userns=host est supposé.

--userns="" (c'est-à-dire une chaîne vide) est un alias pour --userns=host.

Cette option est incompatible avec --gidmap, --uidmap, --subuidname et --subgidname.

Mappages des clés --userns pour les utilisateurs sans privilèges :

Clé Utilisateur Hôte Utilisateur Conteneur
auto $UID nil (L'UID de l'utilisateur hôte n'est pas mappé dans le conteneur.)
host $UID 0 (Le compte utilisateur par défaut est mappé à l'utilisateur root dans le conteneur.)
keep-id $UID $UID (Mappe le compte utilisateur au même UID à l'intérieur du conteneur.)
keep-id:uid=200,gid=210 $UID 200:210 (Mappe le compte utilisateur à l'UID et au GID spécifiés à l'intérieur du conteneur.)
nomap $UID nil (L'UID de l'utilisateur hôte n'est pas mappé dans le conteneur.)

Les valeurs valides pour mode sont :

auto[:OPTIONS,...] : crée automatiquement un espace de noms utilisateur unique.

  • mode rootful : l'indicateur --userns=auto nécessite que le nom d'utilisateur containers soit spécifié dans les fichiers /etc/subuid et /etc/subgid, avec une plage inutilisée d'UID d'utilisateurs subordonnés que Podman autorise les conteneurs à allouer. Exemple : containers:2147483647:2147483648.
  • mode sans privilèges (rootless) : la plage d'utilisateurs des fichiers /etc/subuid et /etc/subgid sera utilisée. Notez que l'exécution d'un seul conteneur sans utiliser --userns=auto utilisera toute la plage d'UID et n'autorisera pas de subdivision supplémentaire. Voir subuid(5).

Podman alloue des plages uniques d'UID et de GID à partir des UID subordonnés containers. La taille des plages est basée sur le nombre d'UID requis dans l'image. Le nombre d'UID et de GID peut être remplacé par l'option size.

L'option --userns=keep-id utilise tous les subuids et subgids de l'utilisateur. L'option --userns=nomap utilise tous les subuids et subgids de l'utilisateur à l'exception de l'ID de l'utilisateur lui-même. L'utilisation de --userns=auto lors du démarrage de nouveaux conteneurs ne fonctionne pas tant qu'il existe des conteneurs démarrés avec --userns=nomap ou --userns=keep-id sans limiter la taille de l'espace de noms utilisateur.

Options valides pour auto :

  • gidmapping=CONTAINER_GID:HOST_GID:SIZE : pour forcer un mappage GID à être présent dans l'espace de noms utilisateur.
  • size=TAILLE : pour spécifier une taille explicite pour l'espace de noms utilisateur automatique. Par exemple : --userns=auto:size=8192. Si size n'est pas spécifié, auto estime une taille pour l'espace de noms utilisateur.
  • uidmapping=CONTAINER_UID:HOST_UID:SIZE : pour forcer un mappage UID à être présent dans l'espace de noms utilisateur.

L'UID et le GID de l'hôte dans gidmapping et uidmapping peuvent éventuellement être précédés du symbole @. Dans ce cas, podman recherchera l'ID intermédiaire correspondant à l'ID de l'hôte et mapper l'ID intermédiaire trouvé à l'ID du conteneur. Pour plus de détails, voir --uidmap.

container:id : rejoint l'espace de noms utilisateur du conteneur spécifié.

host ou "" (chaîne vide) : s'exécute dans l'espace de noms utilisateur de l'appelant. Les processus s'exécutant dans le conteneur ont les mêmes privilèges sur l'hôte que tout autre processus lancé par l'utilisateur appelant.

keep-id : crée un espace de noms utilisateur où l'UID:GID de l'utilisateur actuel sont mappés aux mêmes valeurs dans le conteneur. Pour les conteneurs créés par root, le mappage actuel est créé dans un nouvel espace de noms utilisateur.

En outre, le processus init à l'intérieur du conteneur s'exécutera sous l'UID de l'utilisateur actuel. Ce comportement remplace l'instruction USER de l'image à moins que vous ne définissiez explicitement --user.

Options valides pour keep-id :

  • uid=UID : remplace l'UID à l'intérieur du conteneur auquel l'utilisateur actuel est mappé.
  • gid=GID : remplace le GID à l'intérieur du conteneur auquel l'utilisateur actuel est mappé.
  • size=TAILLE : remplace la taille de l'espace de noms utilisateur configuré. Il est utile de ne pas saturer tous les ID disponibles. Non pris en charge lorsqu'il est exécuté en tant que root.

nomap : crée un espace de noms utilisateur où les UID:GID de l'utilisateur rootless actuel ne sont pas mappés dans le conteneur. Cette option n'est pas autorisée pour les conteneurs créés par l'utilisateur root.

ns:namespace : exécute le conteneur dans l'espace de noms utilisateur existant donné.

--uts=mode

Définit le mode de l'espace de noms UTS pour le conteneur. Les valeurs suivantes sont prises en charge :

  • host : utilise l'espace de noms UTS de l'hôte à l'intérieur du conteneur.
  • private : crée un nouvel espace de noms pour le conteneur (par défaut).

Ajoutez l'option :ro ou :rw pour monter un volume en mode lecture seule ou lecture/écriture, respectivement. Par défaut, les volumes sont montés en lecture/écriture. Voir les exemples.

Changement de propriétaire des montages de volumes

Lorsqu'un volume nommé est monté pour la première fois sur un conteneur, Podman ajuste automatiquement la propriété du point de montage du volume lors de l'initialisation du conteneur. Cette opération de changement de propriétaire se produit dans les conditions suivantes :

  • Le volume n'a pas encore été utilisé (NeedsChown est défini sur true)
  • Le volume est vide ou n'a pas encore été copié
  • Le volume n'est pas géré par un pilote de volume externe
  • Le pilote de volume n'est pas "image"

Pour les volumes avec des montages idmapped (utilisant l'option idmap), le changement de propriété prend en compte les mappages de l'espace de noms utilisateur du conteneur, mais le volume idmapped conserve un mappage UID/GID correct. Pour les volumes sans idmapping, le point de montage est modifié pour correspondre à l'utilisateur et au groupe du processus du conteneur, mappé à l'espace de noms utilisateur de l'hôte si le remappage de l'espace de noms utilisateur est activé.

Si un conteneur est créé dans un nouvel espace de noms utilisateur, l'UID et le GID dans le conteneur peuvent correspondre à un autre UID et GID sur l'hôte.

Le suffixe :U indique à Podman d'utiliser l'UID et le GID corrects de l'hôte basés sur l'UID et le GID dans le conteneur, pour changer récursivement le propriétaire et le groupe du volume source. Le changement de propriétaire parcourt le système de fichiers sous le volume et modifie l'UID/GID de chaque fichier. Si le volume contient des milliers d'inodes, ce processus prend beaucoup de temps, retardant le démarrage du conteneur.

Attention : utiliser avec prudence car cela modifie le système de fichiers de l'hôte.

Étiquetage des montages de volumes

Les systèmes d'étiquetage comme SELinux nécessitent que des étiquettes appropriées soient placées sur le contenu du volume monté dans un conteneur. Sans étiquette, le système de sécurité peut empêcher les processus s'exécutant dans le conteneur d'utiliser le contenu. Par défaut, Podman ne modifie pas les étiquettes définies par l'OS.

Pour modifier une étiquette dans le contexte du conteneur, ajoutez l'un des deux suffixes :z ou :Z au montage du volume. Ces suffixes indiquent à Podman de relabéliser les objets de fichier sur les volumes partagés. L'option z indique à Podman que deux conteneurs ou plus partagent le contenu du volume. En conséquence, Podman étiquette le contenu avec une étiquette de contenu partagé. Les étiquettes de volume partagées permettent à tous les conteneurs de lire/écrire le contenu. L'option Z indique à Podman d'étiqueter le contenu avec une étiquette privée non partagée. Seul le conteneur actuel peut utiliser un volume privé.

Note : tous les conteneurs au sein d'un pod partagent la même étiquette SELinux. Cela signifie que tous les conteneurs de ce pod peuvent lire/écrire des volumes partagés dans le conteneur créé avec :Z sur l'un des conteneurs. Le relabélisation parcourt le système de fichiers sous le volume et modifie l'étiquette sur chaque fichier ; si le volume contient des milliers d'inodes, ce processus prend beaucoup de temps, retardant le démarrage du conteneur. Si le volume a été précédemment relabélisé avec l'option z, Podman est optimisé pour ne pas relabéliser une seconde fois. Si des fichiers sont déplacés dans le volume, les étiquettes peuvent être changées manuellement avec la commande chcon -Rt container_file_t PATH.

Note : ne relabélisez pas les fichiers et répertoires système. Relabéliser le contenu système peut entraîner des échecs pour d'autres services confinés sur la machine. Pour ces types de conteneurs, nous recommandons de désactiver la séparation SELinux. L'option --security-opt label=disable désactive la séparation SELinux pour le conteneur. Par exemple, si un utilisateur souhaitait monter son répertoire personnel entier dans un conteneur, il doit désactiver la séparation SELinux.

$ podman create --security-opt label=disable -v $HOME:/home/user fedora touch /home/user/file

Montages de volumes en superposition

Le drapeau :O indique à Podman de monter le répertoire de l'hôte en tant que stockage temporaire en utilisant le système de fichiers en superposition. Les processus du conteneur peuvent modifier le contenu du point de montage, qui est stocké dans le stockage du conteneur dans un répertoire séparé. En termes de superposition, le répertoire source est le niveau inférieur, et le répertoire de stockage du conteneur est le niveau supérieur. Les modifications du point de montage sont détruites lorsque le conteneur a fini de s'exécuter, de manière similaire à un point de montage tmpfs qui est démonté.

Pour les utilisateurs avancés, l'option overlay prend également en charge des upperdir et workdir personnalisés non volatils pour le montage en superposition. Les upperdir et workdir personnalisés peuvent être entièrement gérés par les utilisateurs eux-mêmes, et Podman ne les supprime pas à la fin du cycle de vie. Exemple : :O,upperdir=/some/upper,workdir=/some/work

Les exécutions ultérieures du conteneur voient le contenu du répertoire source d'origine, les modifications des exécutions précédentes du conteneur n'existent plus.

Un cas d'utilisation du montage en superposition est le partage du cache de paquets de l'hôte avec le conteneur pour accélérer les constructions.

Note : le drapeau O entre en conflit avec les autres options listées ci-dessus.

Le contenu monté dans le conteneur est étiqueté avec l'étiquette privée. Sur les systèmes SELinux, les étiquettes dans le répertoire source doivent être lisibles par l'étiquette du conteneur. Habituellement, les conteneurs peuvent lire/exécuter container_share_t et peuvent lire/écrire container_file_t. Si les étiquettes ne peuvent pas être modifiées sur un volume source, la séparation des conteneurs SELinux doit être désactivée pour que le conteneur fonctionne.

Ne modifiez pas le répertoire source monté dans le conteneur avec un montage en superposition, cela pourrait causer des échecs imprévus. Ne modifiez le répertoire qu'après la fin de l'exécution du conteneur.

Propagation des montages

Par défaut, les volumes montés en bind sont privés. Cela signifie que tout montage effectué dans le conteneur n'est pas visible sur l'hôte et vice versa. On peut changer ce comportement en spécifiant une propriété de propagation de montage de volume. Lorsqu'un volume est shared, les montages effectués sous ce volume à l'intérieur du conteneur sont visibles sur l'hôte et vice versa. Faire d'un volume un slave[1] ⟨#Footnote1⟩ permet une propagation des montages unidirectionnelle : les montages effectués sur l'hôte sous ce volume sont visibles à l'intérieur du conteneur mais pas l'inverse.

Pour contrôler la propriété de propagation des montages d'un volume, on peut utiliser le drapeau de propagation [r]shared, [r]slave, [r]private ou [r]unbindable. La propriété de propagation ne peut être spécifiée que pour les volumes montés en bind et non pour les volumes internes ou les volumes nommés. Pour que la propagation des montages fonctionne, le point de montage source (le point de montage où le répertoire source est monté) doit avoir les bonnes propriétés de propagation. Pour les volumes partagés, le point de montage source doit être partagé. Et pour les volumes esclaves, le point de montage source doit être soit partagé, soit esclave. [1] ⟨#Footnote1⟩

Pour monter récursivement un volume et tous ses sous-montages dans un conteneur, utilisez l'option rbind. Par défaut, l'option bind est utilisée, et les sous-montages du répertoire source ne sont pas montés dans le conteneur.

Le montage du volume avec une option copy indique à podman de copier le contenu du répertoire de destination sous-jacent sur les volumes internes nouvellement créés. La copie ne se produit que lors de la création initiale du volume. Le contenu n'est pas copié lors de l'utilisation ultérieure du volume sur différents conteneurs. L'option copy est ignorée sur les montages bind et n'a aucun effet.

Le montage de volumes avec les options nosuid signifie que les exécutables SUID sur le volume ne peuvent pas être utilisés par les applications pour changer leur privilège. Par défaut, les volumes sont montés avec nosuid.

Le montage du volume avec l'option noexec signifie qu'aucun exécutable sur le volume ne peut être exécuté dans le conteneur.

Le montage du volume avec l'option nodev signifie qu'aucun périphérique sur le volume ne peut être utilisé par les processus à l'intérieur du conteneur. Par défaut, les volumes sont montés avec nodev.

Si le HOST-DIR est un point de montage, alors les options dev, suid et exec sont ignorées par le noyau.

Utilisez df HOST-DIR pour déterminer le montage source, puis utilisez findmnt -o TARGET,PROPAGATION source-mount-dir pour déterminer les propriétés de propagation du montage source. Si l'utilitaire findmnt(1) n'est pas disponible, alors on peut regarder l'entrée de montage pour le point de montage source dans /proc/self/mountinfo. Regardez les "champs optionnels" et voyez si des propriétés de propagation y sont spécifiées. Dans ce cas, shared:N signifie que le montage est partagé, master:N signifie que le montage est esclave, et s'il n'y a rien, le montage est privé. [1] ⟨#Footnote1⟩

Pour modifier les propriétés de propagation d'un point de montage, utilisez la commande mount(8). Par exemple, si l'on souhaite monter en bind le répertoire source /foo, on peut faire mount --bind /foo /foo et mount --make-private --make-shared /foo. Cela convertit /foo en un point de montage partagé. Alternativement, on peut modifier directement les propriétés de propagation du montage source. Supposons que / soit le montage source pour /foo, alors utilisez mount --make-shared / pour convertir / en un montage partagé.

Note : si l'utilisateur n'a des droits d'accès que via un groupe, l'accès au volume depuis un conteneur rootless échoue.
