NOM

podman-system-service - Exécute un service API

SYNOPSIS

podman system service [options]

DESCRIPTION

La commande podman system service crée un service d'écoute qui répond aux appels API pour Podman. La commande est disponible sur les systèmes Linux et est généralement exécutée dans des services systemd. La commande n'est pas disponible lorsque la commande Podman est exécutée directement sur un hôte Windows ou macOS, ou dans d'autres situations où la commande Podman accède à un service API Podman distant.

L'API REST fournie par podman system service est divisée en deux parties : une couche de compatibilité offrant un support pour l'API Docker v1.40, et une couche native Podman Libpod. La documentation pour cette dernière est disponible à l'adresse https://docs.podman.io/en/latest/_static/api.html. Les deux API sont versionnées, mais le serveur ne rejette pas les requêtes avec une version non prise en charge.

Exécution de la commande dans un service systemd

La commande podman system service supporte l'activation par socket systemd. Lorsque la commande est exécutée dans un service systemd, le service API peut donc être fourni à la demande. Si le service systemd n'est pas déjà en cours d'exécution, il sera activé dès qu'un client se connectera au socket d'écoute. Systemd exécute alors la commande podman system service. Après un certain temps d'inactivité, tel que défini par l'option --time, la commande se termine. Systemd met l'état du podman.service sur inactif. À ce stade, aucun processus podman system service n'est en cours d'exécution. Aucune ressource de calcul inutile n'est gaspillée. Dès qu'un autre client se connecte, systemd active à nouveau le service systemd.

Les fichiers d'unité systemd qui déclarent le service API Podman pour les utilisateurs sont :

  • /usr/lib/systemd/user/podman.service
  • /usr/lib/systemd/user/podman.socket

Dans le fichier podman.socket, le chemin du socket Unix d'écoute est défini par :

ListenStream=%t/podman/podman.sock

Le chemin contient le spécificateur systemd %t, que systemd développe en la valeur de la variable d'environnement XDG_RUNTIME_DIR (voir les spécificateurs systemd dans la page de manuel systemd.unit(5)).

En plus des services utilisateurs systemd, il existe également un service système systemd, podman.service. Il exécute Podman rootful et est accessible depuis le socket Unix /run/podman/podman.sock. Voir les fichiers d'unité systemd :

  • /usr/lib/systemd/system/podman.service
  • /usr/lib/systemd/system/podman.socket

La commande podman system service ne supporte pas plus d'un socket d'écoute pour le service API.

Note : Les fichiers d'unité systemd par défaut (système et utilisateur) modifient l'option de niveau de journalisation de error à info. Cette modification fournit des informations supplémentaires sur chaque appel API.

Exécution de la commande directement

Pour permettre l'exécution d'un service API sans utiliser de service systemd, la commande accepte également un argument d'endpoint optionnel pour l'API sous forme d'URI. Par exemple, unix:///tmp/foobar.sock ou tcp://localhost:8080. Si aucun endpoint n'est fourni, les valeurs par défaut sont utilisées. L'endpoint par défaut pour un service rootful est unix:///run/podman/podman.sock et pour un service rootless, c'est unix://$XDG_RUNTIME_DIR/podman/podman.sock (par exemple unix:///run/user/1000/podman/podman.sock).

Accès au socket Unix depuis l'intérieur d'un conteneur

Pour accéder au service API depuis l'intérieur d'un conteneur : - montez le socket en tant que volume - exécutez le conteneur avec --security-opt label=disable

Sécurité

Veuillez noter que l'API accorde un accès complet à toutes les fonctionnalités de Podman, et permet donc une exécution de code arbitraire en tant qu'utilisateur exécutant l'API, sans possibilité de limiter ou d'auditer cet accès. Le modèle de sécurité de l'API repose sur l'accès via un socket Unix, avec un accès restreint par les permissions de fichier standard, garantissant que seul l'utilisateur exécutant le service pourra y accéder. TLS peut être utilisé pour sécuriser ce socket en exigeant que les clients présentent un certificat signé par une autorité de certification (« CA ») de confiance, ainsi que pour permettre au client de vérifier l'identité de l'API. Nous déconseillons *fortement* de rendre le socket de l'API disponible via le réseau (c'est-à-dire en liant le service à une URL tcp) sans activer TLS mutuel pour authentifier le client. Même l'accès via localhost comporte des risques - toute personne ayant accès au système pourra accéder à l'API. Si l'accès distant est requis, nous recommandons plutôt de transférer le socket de l'API via SSH et de limiter l'accès sur la machine distante autant que possible. Si une URL tcp doit être utilisée sans TLS, il est recommandé d'utiliser l'option --cors pour améliorer la sécurité.

OPTIONS

--cors

En-têtes CORS à injecter dans la réponse HTTP. La valeur par défaut est une chaîne vide, ce qui désactive les en-têtes CORS.

--help, -h

Affiche le message d'utilisation.

--time, -t

Le temps avant l'expiration de la session en secondes. La valeur par défaut est 5 secondes. Une valeur de 0 signifie pas de délai d'expiration, donc la session n'expire pas.

--tls-cert=chemin

Chemin vers un fichier PEM contenant le certificat TLS à présenter aux clients. --tls-key doit également être fourni.

--tls-client-ca=chemin

Chemin vers un fichier PEM contenant le bundle de certificats TLS pour valider les connexions clients. Les connexions ne présentant aucun certificat ou un certificat non signé par l'un de ces certificats seront rejetées.

--tls-key=chemin

Chemin vers un fichier PEM contenant la clé privée correspondant à --tls-cert. --tls-cert doit également être fourni.

Le délai d'expiration par défaut peut être modifié via le champ service_timeout=VALUE dans containers.conf. Voir containers.conf(5) pour plus d'informations.

EXEMPLES

Démarrez le socket système utilisateur pour un service rootless.

systemctl --user start podman.socket

Configurez la variable d'environnement DOCKER_HOST pour qu'elle pointe vers le socket Podman afin qu'il puisse être utilisé via des outils d'API Docker comme docker-compose.

$ export DOCKER_HOST=unix://$XDG_RUNTIME_DIR/podman/podman.sock
$ docker-compose up

Configurez le socket systemd pour qu'il démarre automatiquement après les redémarrages, et exécutez-le en tant qu'utilisateur spécifié.

systemctl --user enable podman.socket
loginctl enable-linger <UTILISATEUR>

Démarrez le socket systemd pour le service rootful.

sudo systemctl start podman.socket

Configurez le socket pour qu'il démarre automatiquement après les redémarrages.

sudo systemctl enable podman.socket

Il est possible d'exécuter l'API sans utiliser l'activation par socket systemd. Dans ce cas, l'API ne sera pas disponible à la demande car la commande restera terminée une fois le délai d'inactivité écoulé. Exécutez une API avec un délai d'inactivité de 5 secondes sans utiliser l'activation par socket.

podman system service --time 5

Le socket par défaut a été utilisé car aucun argument URI n'a été fourni.

Exécutez un service API avec un chemin de socket personnalisé et aucun délai d'expiration :

podman system service --time 0 unix:///var/run/mypodman.sock

Cela démarre le service API en écoutant sur le socket personnalisé /var/run/mypodman.sock sans délai d'expiration d'inactivité (s'exécute indéfiniment).
