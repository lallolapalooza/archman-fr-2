NOM

po4a - framework pour traduire la documentation et d'autres matériaux

Introduction

po4a (PO for anything) facilite la maintenance des traductions de documentation en utilisant les outils classiques gettext. La principale caractéristique de po4a est qu'elle découple la traduction du contenu de sa structure documentaire.

Ce document sert d'introduction au projet po4a, en se concentrant sur les utilisateurs potentiels envisageant d'utiliser cet outil et sur les curieux qui souhaitent comprendre pourquoi les choses sont ainsi.

Pourquoi po4a ?

La philosophie du Logiciel Libre est de rendre la technologie véritablement accessible à tous. Mais la licence n'est pas la seule considération : un logiciel libre non traduit est inutile pour les non-anglophones. Par conséquent, nous avons encore du travail à faire pour rendre le logiciel accessible à tous.

Cette situation est bien comprise par la plupart des projets et tout le monde est maintenant convaincu de la nécessité de tout traduire. Pourtant, les traductions réelles représentent un énorme effort de nombreux individus, entravé par de petites difficultés techniques.

Heureusement, le logiciel Open Source est très bien traduit à l'aide de la suite d'outils gettext. Ces outils sont utilisés pour extraire les chaînes à traduire d'un programme et présenter les chaînes à traduire dans un format standardisé (appelé fichiers PO, ou catalogues de traduction). Tout un écosystème d'outils a émergé pour aider les traducteurs à traduire ces fichiers PO. Le résultat est ensuite utilisé par gettext au moment de l'exécution pour afficher les messages traduits aux utilisateurs finaux.

Concernant la documentation, cependant, la situation reste quelque peu décevante. Traduire la documentation peut sembler plus facile que de traduire un programme, car il suffirait de copier le fichier source de la documentation et de commencer à traduire le contenu. Cependant, lorsque la documentation originale est modifiée, le suivi des modifications devient rapidement un cauchemar pour les traducteurs. Si cela est fait manuellement, cette tâche est désagréable et sujette aux erreurs.

Les traductions obsolètes sont souvent pires que pas de traduction du tout. Les utilisateurs finaux peuvent être trompés par une documentation décrivant un ancien comportement du programme. De plus, ils ne peuvent pas interagir directement avec les mainteneurs car ils ne parlent pas anglais. De plus, le mainteneur ne peut pas résoudre le problème car il ne connaît pas toutes les langues dans lesquelles sa documentation est traduite. Ces difficultés, souvent causées par des outils médiocres, peuvent saper la motivation des traducteurs bénévoles, aggravant encore le problème.

L'objectif du projet po4a est de faciliter le travail des traducteurs de documentation. En particulier, il rend les traductions de documentation *maintenables*.

L'idée est de réutiliser et d'adapter l'approche gettext dans ce domaine. Comme avec gettext, les textes sont extraits de leurs emplacements originaux et présentés aux traducteurs sous forme de catalogues de traduction PO. Les traducteurs peuvent tirer parti des outils gettext classiques pour suivre le travail à faire, collaborer et s'organiser en équipes. po4a insère ensuite les traductions directement dans la structure de la documentation pour produire des fichiers source traduits qui peuvent être traités et distribués tout comme les fichiers anglais. Tout paragraphe non traduit est laissé en anglais dans le document résultant, garantissant que les utilisateurs finaux ne voient jamais une traduction obsolète dans la documentation.

Cela automatise la majeure partie du travail fastidieux de la maintenance des traductions. Découvrir les paragraphes nécessitant une mise à jour devient très facile, et le processus est entièrement automatisé lorsque les éléments sont réorganisés sans modification supplémentaire. Des vérifications spécifiques peuvent également être utilisées pour réduire les risques d'erreurs de formatage qui entraînement un document cassé.

Veuillez également consulter la FAQ ci-dessous dans ce document pour une liste plus complète des avantages et inconvénients de cette approche.

Formats pris en charge

Actuellement, cette approche a été mise en œuvre avec succès pour plusieurs types de formats de mise en forme de texte :

man (analyseur mature)
Le bon vieux format des pages de manuel, utilisé par tant de programmes. Le support de po4a est très bienvenu ici car ce format est quelque peu difficile à utiliser et pas vraiment convivial pour les débutants.

Le module Locale::Po4a::Man(3pm) prend également en charge le format mdoc, utilisé par les pages man BSD (elles sont également assez courantes sous Linux).

AsciiDoc (analyseur mature)
Ce format est un format de balisage léger destiné à faciliter la création de documentation. Il est par exemple utilisé pour documenter le système git. Ces manpages sont traduites à l'aide de po4a.

Voir Locale::Po4a::AsciiDoc pour plus de détails.

pod (analyseur mature)
C'est le format de documentation en ligne de Perl. Le langage et ses extensions sont eux-mêmes documentés dans ce format en plus de la plupart des scripts Perl existants. Il est facile de maintenir la documentation proche du code réel en les intégrant tous les deux dans le même fichier. Cela facilite la vie des programmeurs, mais malheureusement pas celle des traducteurs, jusqu'à ce que vous utilisiez po4a.

Voir Locale::Po4a::Pod pour plus de détails.

sgml (analyseur mature)
Même s'il est supplanté par XML de nos jours, ce format est encore utilisé pour des documents de plusieurs écrans de long. Il peut même être utilisé pour des livres complets. Les documents de cette longueur peuvent être très difficiles à mettre à jour. diff est souvent inutile lorsque le texte original a été ré-indenter après la mise à jour. Heureusement, po4a peut vous aider après ce processus.

Actuellement, seuls les DTD DebianDoc et DocBook sont pris en charge, mais l'ajout de la prise en charge d'un nouveau est très facile. Il est même possible d'utiliser po4a sur un DTD SGML inconnu sans modifier le code en fournissant les informations nécessaires sur la ligne de commande. Voir Locale::Po4a::Sgml(3pm) pour les détails.

TeX / LaTeX (analyseur mature)
Le format LaTeX est un format de documentation majeur utilisé dans le monde du Logiciel Libre et pour les publications.

Le module Locale::Po4a::LaTeX(3pm) a été testé avec la documentation Python, un livre et quelques présentations.

texte (analyseur mature)
Le format Texte est le format de base de nombreux formats incluant de longs blocs de texte, tels que Markdown, fortunes, section YAML front matter, debian/changelog, et debian/control.

Cela prend en charge le format courant utilisé dans les Générateurs de Sites Statiques, les READMEs, et d'autres systèmes de documentation. Voir Locale::Po4a::Text(3pm) pour plus de détails.

xml et XHMTL (analyseur probablement mature)
Le format XML est un format de base pour de nombreux formats de documentation.

Actuellement, le DTD DocBook (voir Locale::Po4a::Docbook(3pm) pour plus de détails) et XHTML sont pris en charge par po4a.

BibTex (analyseur probablement mature)
Le format BibTex est utilisé conjointement avec LaTex pour formater des listes de références (bibliographies).

Voir Locale::Po4a::BibTex pour plus de détails.

Docbook (analyseur probablement mature)
Un langage de balisage basé sur XML qui utilise des balises sémantiques pour décrire des documents.

Voir Locale::Po4a:Docbook pour plus de détails.

Supported formats

Guide XML (parser probablement mature)
Un format de documentation XML. Ce module a été développé spécifiquement pour aider à la prise en charge et à la maintenance des traductions de la documentation Gentoo Linux jusqu'en mars 2016 au moins (basé sur la Wayback Machine). Gentoo est depuis passé au format XML DevBook.

Voir Locale::Po4a::Guide pour plus de détails.

Wml (parser probablement mature)
Le Web Markup Language, ne pas confondre WML avec le matériel WAP utilisé sur les téléphones portables. Ce module repose sur le module Xhtml, qui repose lui-même sur le module Xml.

Voir Locale::Po4a::Wml pour plus de détails.

Yaml (parser probablement mature)
Un sur-ensemble strict de JSON. YAML est souvent utilisé comme système ou projet de configuration. YAML est au cœur d'Ansible de Red Hat.

Voir Locale::Po4a::Yaml pour plus de détails.

RubyDoc (parser probablement mature)
Le format Ruby Document (RD), à l'origine le format de documentation par défaut pour Ruby et les projets Ruby avant d'être converti en RDoc en 2002. Bien qu'apparemment la version japonaise du manuel de référence Ruby utilise toujours RD.

Voir Locale::Po4a::RubyDoc pour plus de détails.

Halibut (parser probablement expérimental)
Un système de production de documentation, avec des éléments similaires à TeX, debiandoc-sgml, TeXinfo, et d'autres, développé par Simon Tatham, le développeur de PuTTY.

Voir Locale::Po4a::Halibut pour plus de détails.

Ini (parser probablement expérimental)
Format de fichier de configuration popularisé par MS-DOS.

Voir Locale::Po4a::Ini pour plus de détails.

texinfo (parser très très expérimental)
Toute la documentation GNU est écrite dans ce format (c'est même l'une des exigences pour devenir un projet GNU officiel). Le support pour Locale::Po4a::Texinfo(3pm) dans po4a n'en est encore qu'à ses débuts. Veuillez signaler les bugs et les demandes de fonctionnalités.
gemtext (parser très très expérimental)
Le format texte brut natif du protocole Gemini. L'extension ".gmi" est couramment utilisée. Le support de ce module dans po4a est encore à ses débuts. Si vous trouvez quoi que ce soit, veuillez signaler un bug ou une demande de fonctionnalité.
org (parser très très expérimental)
Le format de document utilisé par le mode Org. Le support de ce module dans po4a est encore à ses débuts. Si vous trouvez quoi que ce soit, veuillez signaler un bug ou une demande de fonctionnalité.
vimhelp (parser très très expérimental)
Le format utilisé pour les fichiers d'aide Vim (et la documentation de certains plugins tiers). Le support de ce format dans po4a est encore à ses débuts. Si vous trouvez quoi que ce soit, veuillez signaler un bug ou une demande de fonctionnalité.
simplepod (parser très très expérimental)
Similaire à *pod* mentionné précédemment, celui-ci adopte Pod::Simple comme parser. Étant nouvellement créé, des bugs sont attendus. Si vous remarquez un comportement étrange, veuillez nous en informer. À terme, ce module remplacera *pod*.
Autres formats supportés
Po4a peut également gérer des formats plus rares ou spécialisés, tels que la documentation des options de compilation pour les noyaux Linux 2.4+ (Locale::Po4a::KernelHelp) ou les diagrammes produits par l'outil dia (Locale::Po4a::Dia). L'ajout d'un nouveau format est souvent très facile et la tâche principale consiste à trouver un parseur pour votre format cible. Voir Locale::Po4a::TransTractor(3pm) pour plus d'informations à ce sujet.
Formats non supportés
Malheureusement, po4a manque encore de support pour plusieurs formats de documentation. Beaucoup d'entre eux seraient faciles à supporter dans po4a. Cela inclut les formats non seulement utilisés pour la documentation, tels que les descriptions de paquets (deb et rpm), les scripts d'installation de paquets, les changelogs de paquets, et tous les formats de fichiers spécialisés utilisés par des programmes tels que les scénarios de jeux ou les fichiers de ressources wine.

Utilisation de po4a

La manière la plus simple d'utiliser cet outil dans votre projet est d'écrire un fichier de configuration pour le programme po4a, et de n'interagir qu'avec ce programme. Veuillez vous référer à sa documentation, dans po4a(1). Le reste de cette section fournit plus de détails pour les utilisateurs avancés de po4a souhaitant approfondir leur compréhension.

Schéma détaillé du flux de travail de po4a

Assurez-vous de lire po4a(1) avant cette section trop détaillée pour obtenir un aperçu simplifié du flux de travail de po4a. Revenez ici quand vous voudrez avoir l'image complète et effrayante, avec presque tous les détails.

Dans le schéma suivant, master.doc est un exemple de nom pour la documentation à traduire ; XX.doc est le même document traduit dans la langue XX tandis que doc.XX.po est le catalogue de traduction pour ce document dans la langue XX. Les auteurs de documentation seront principalement concernés par master.doc (qui peut être une page de manuel, un document XML, un fichier AsciiDoc, etc.) ; les traducteurs seront principalement concernés par le fichier PO, tandis que les utilisateurs finaux ne verront que le fichier XX.doc.

Les transitions entre crochets tels que "[po4a met à jour le fichier po]" représentent l'exécution d'un outil po4a, tandis que les transitions entre accolades telles que "{mise à jour de master.doc}" représentent une modification manuelle des fichiers du projet.

Encore une fois, ce schéma est trop compliqué. Consultez po4a(1) pour un aperçu simplifié.

La partie gauche représente comment po4a-gettextize(1) peut être utilisé pour convertir un projet de traduction existant vers l'infrastructure po4a. Ce script prend un document original et sa version traduite, et essaie de construire le fichier PO correspondant. Une telle conversion manuelle est assez fastidieuse (voir la documentation de po4a-gettextize(1) pour plus de détails), mais elle n'est nécessaire qu'une seule fois pour convertir vos traductions existantes. Si vous n'avez aucune traduction à convertir, vous pouvez l'ignorer et vous concentrer sur la partie droite du schéma.

Sur la partie droite supérieure, l'action de l'auteur original est représentée, mettant à jour la documentation. La partie droite du milieu représente les mises à jour automatiques des fichiers de traduction : le nouveau matériel est extrait et comparé à la traduction existante. La traduction précédente est utilisée pour les parties qui n'ont pas changé, tandis que les parties partiellement modifiées sont connectées à la traduction précédente avec un marqueur "flou" indiquant que la traduction doit être mise à jour. Le matériel nouveau ou fortement modifié est laissé non traduit.

Ensuite, le bloc *édition manuelle* représente l'action des traducteurs, qui modifient les fichiers PO pour fournir des traductions à chaque chaîne et paragraphe original. Cela peut être fait en utilisant un éditeur spécifique tel que l'éditeur de traduction GNOME, Lokalize de KDE ou poedit, ou en utilisant une plateforme de localisation en ligne telle que weblate ou pootle. Le résultat de la traduction est un ensemble de fichiers PO, un par langue. Veuillez vous référer à la documentation gettext pour plus de détails.

La partie inférieure de la figure montre comment po4a crée un document source traduit à partir du document original *master.doc* et du catalogue de traduction *doc.XX.po* qui a été mis à jour par les traducteurs. La structure du document est réutilisée, tandis que le contenu original est remplacé par sa contrepartie traduite. Optionnellement, un addendum peut être utilisé pour ajouter du texte supplémentaire à la traduction. Ceci est souvent utilisé pour ajouter le nom du traducteur au document final. Voir ci-dessous pour plus de détails.

Lors de son invocation, po4a met à jour à la fois les fichiers de traduction et les fichiers de documentation traduits automatiquement.

Démarrer un nouveau projet de traduction

class='permalink' href='#Démarrer_un_nouveau_projet_de_traduction'>Démarrer un nouveau projet de traduction

Si vous partez de zéro, il vous suffit d'écrire un fichier de configuration pour po4a, et vous êtes prêt. Les modèles pertinents sont créés pour les fichiers manquants, permettant à vos contributeurs de traduire votre projet dans leur langue. Veuillez vous référer à po4a(1) pour un tutoriel de démarrage rapide et pour tous les détails.

Si vous avez une traduction existante, c'est-à-dire un fichier de documentation qui a été traduit manuellement, vous pouvez intégrer son contenu dans votre flux de travail po4a en utilisant po4a-gettextize. Cette tâche est un peu fastidieuse (comme décrit dans la manpage de l'outil), mais une fois que votre projet est converti au flux de travail po4a, tout sera mis à jour automatiquement.

Mettre à jour les traductions et les documents

Une fois configuré, il suffit d'appeler po4a pour mettre à jour à la fois les fichiers PO de traduction et les documents traduits. Vous pouvez passer l'option "--no-translations" à po4a pour ne pas mettre à jour les traductions (et donc seulement les fichiers PO) ou "--no-update" pour ne pas mettre à jour les fichiers PO (et donc seulement les traductions). Cela correspond approximativement aux scripts individuels po4a-updatepo et po4a-translate qui sont maintenant dépréciés (voir "Pourquoi les scripts individuels sont-ils dépréciés" dans la FAQ ci-dessous).

Utiliser des addenda pour ajouter du texte supplémentaire aux traductions

Ajouter du nouveau texte à la traduction est probablement la seule chose qui est plus facile à long terme lorsque vous traduisez des fichiers manuellement :). Cela se produit lorsque vous souhaitez ajouter une section supplémentaire au document traduit, ne correspondant à aucun contenu du document original. Le cas d'utilisation classique est de créditer l'équipe de traduction et d'indiquer comment signaler les problèmes spécifiques à la traduction.

Avec po4a, vous devez spécifier des fichiers addendum, qui peuvent être conceptuellement considérés comme des patchs appliqués au document localisé après traitement. Chaque addendum doit être fourni sous forme de fichier séparé, dont le format est cependant très différent des patchs classiques. La première ligne est une ligne d'en-tête, définissant le point d'insertion de l'addendum (avec une syntaxe malheureusement cryptique -- voir ci-dessous) tandis que le reste du fichier est ajouté verbatim à la position déterminée.

La ligne d'en-tête doit commencer par la chaîne PO4A-HEADER:, suivie d'une liste de champs clé=valeur séparés par des points-virgules.

Par exemple, l'en-tête suivant déclare un addendum qui doit être placé à la toute fin de la traduction.

PO4A-HEADER: mode=eof

Les choses sont plus complexes lorsque vous souhaitez ajouter votre contenu supplémentaire au milieu du document. L'en-tête suivant déclare un addendum qui doit être placé après la section XML contenant la chaîne "About this document" dans la traduction.

PO4A-HEADER: position=About this document; mode=after; endboundary=</section>

En pratique, lors de l'application d'un addendum, po4a recherche la première ligne correspondant à l'argument "position" (cela peut être une expression régulière). N'oubliez pas que po4a considère ici le document traduit. Cette documentation est en anglais, mais votre ligne devrait probablement se lire comme suit si vous avez l'intention que votre addendum s'applique à la traduction française du document.

PO4A-HEADER: position=À propos de ce document; mode=after; endboundary=</section>

Une fois la "position" trouvée dans le document cible, po4a recherche la ligne suivante après la "position" qui correspond à la "endboundary" fournie. L'addendum est ajouté juste après cette ligne (car nous avons fourni une endboundary, c'est-à-dire une limite terminant la section courante).

Exactement le même effet pourrait être obtenu avec l'en-tête suivant, qui est équivalent :

PO4A-HEADER: position=About this document; mode=after; beginboundary=<section>

Ici, po4a recherche la première ligne correspondant à "<section>" après la ligne correspondant à "About this document" dans la traduction, et ajoute l'addendum avant cette ligne car nous avons fourni une beginboundary, c'est-à-dire une limite marquant le début de la section suivante. Cet en-tête demande donc de placer l'addendum après la section contenant "About this document", et indique à po4a qu'une section commence par une ligne contenant la balise "<section>". Ceci est équivalent à l'exemple précédent car ce que vous voulez vraiment, c'est ajouter cet addendum soit après "</section>" soit avant "<section>".

Vous pouvez également définir le mode d'insertion à la valeur "before", avec une sémantique similaire : combiner "mode=before" avec une "endboundary" placera l'addendum juste après la limite correspondante, qui est la dernière limite potentielle avant la "position". Combiner "mode=before" avec une "beginboundary" placera l'addendum juste avant la limite correspondante, qui est la dernière limite potentielle avant la "position".

 Mode   | Type de limite | Limite utilisée     | Point d'insertion par rapport à la limite
========|===============|=====================|=========================================
'before'| 'endboundary' | dernière avant 'position' | Juste après la limite sélectionnée
'before'|'beginboundary'| dernière avant 'position' | Juste avant la limite sélectionnée
'after' | 'endboundary' | première après 'position' | Juste après la limite sélectionnée
'after' |'beginboundary'| première après 'position' | Juste avant la limite sélectionnée
'eof'   |   (aucun)     |  n/a                | Fin du fichier

Astuces sur les addenda

  • N'oubliez pas qu'il s'agit d'expressions régulières. Par exemple, si vous voulez faire correspondre la fin d'une section nroff se terminant par la ligne ".fi", n'utilisez pas ".fi" comme endboundary, car cela correspondra à "the[ fi]le", ce qui n'est évidemment pas ce que vous attendez. Le bon endboundary dans ce cas est : "^\.fi$".
  • Les espaces blancs SONT importants dans le contenu de la "position" et des limites. Donc les deux lignes suivantes sont différentes. La deuxième ne sera trouvée que s'il y a suffisamment d'espaces à la fin dans le document traduit. 
    PO4A-HEADER: position=About this document; mode=after; beginboundary=<section>
PO4A-HEADER: position=About this document ; mode=after; beginboundary=<section>
  • Bien que cette recherche de contexte puisse être considérée comme opérant sur chaque ligne du document traduit, elle opère en réalité sur la chaîne de données interne du document traduit. Cette chaîne de données interne peut être un texte s'étendant sur un paragraphe contenant plusieurs lignes ou peut être une balise XML seule. Le point d'insertion exact de l'addendum doit être avant ou après la chaîne de données interne et ne peut pas être à l'intérieur de la chaîne de données interne.
  • Passez l'argument "-vv" à po4a pour comprendre comment les addenda sont ajoutés à la traduction. Il peut également être utile d'exécuter po4a en mode débogage pour voir la chaîne de données interne réelle lorsque votre addendum ne s'applique pas.

Exemples d'addenda

  • Si vous voulez ajouter quelque chose après la section nroff suivante : 
    .SH "AUTHORS"

    Vous devriez opter pour une approche en deux étapes en définissant mode=after. Ensuite, vous devriez affiner la recherche à la ligne après AUTHORS avec l'argument position en expression régulière. Ensuite, vous devriez faire correspondre le début de la section suivante (c'est-à-dire, ^\.SH) avec l'argument beginboundary en expression régulière. C'est-à-dire :

    PO4A-HEADER:mode=after;position=AUTHORS;beginboundary=\.SH
  • Si vous voulez ajouter quelque chose juste après une ligne donnée (par exemple, après la ligne "Copyright Big Dude"), utilisez une position qui correspond à cette ligne, mode=after et donnez une beginboundary qui correspond à n'importe quelle ligne. 
    PO4A-HEADER:mode=after;position=Copyright Big Dude, 2004;beginboundary=^
  • Si vous voulez ajouter quelque chose à la fin du document, donnez une position qui correspond à n'importe quelle ligne de votre document (mais une seule ligne. Po4a ne continuera pas si elle n'est pas unique) et donnez une endboundary qui ne correspond à rien. N'utilisez pas de simples chaînes ici comme "EOF", mais préférez celles qui ont moins de chances d'être dans votre document. 
    PO4A-HEADER:mode=after;position=About this document;beginboundary=FakePo4aBoundary

Exemple plus détaillé

Document original (format POD) :

|=head1 NAME
|
|dummy - a dummy program
|
|=head1 AUTHOR
|
|me

Ensuite, l'addendum suivant garantira qu'une section (en français) sur le traducteur est ajoutée à la fin du fichier (en français, "TRADUCTEUR" signifie "TRANSLATOR", et "moi" signifie "me").

|PO4A-HEADER:mode=after;position=AUTEUR;beginboundary=^=head
|
|=head1 TRADUCTEUR
|
|moi
|

Pour placer votre addendum avant l'AUTEUR, utilisez l'en-tête suivant :

PO4A-HEADER:mode=after;position=NOM;beginboundary=^=head1

Cela fonctionne car la ligne suivante correspondant à la beginboundary "/^=head1/" après la section "NAME" (traduite en "NOM" en français), est celle qui déclare les auteurs. Ainsi, l'addendum sera placé entre les deux sections. Notez que si une autre section est ajoutée entre les sections NAME et AUTHOR plus tard, po4a placera à tort les addenda avant la nouvelle section.

Pour éviter cela, vous pouvez accomplir la même chose en utilisant mode=before :

PO4A-HEADER:mode=before;position=^=head1 AUTEUR

Comment cela fonctionne ?

Ce chapitre vous donne un bref aperçu des internes de po4a, afin que vous puissiez vous sentir plus confiant pour nous aider à le maintenir et à l'améliorer. Il peut également vous aider à comprendre pourquoi il ne fait pas ce que vous attendiez, et comment résoudre vos problèmes.

TransTractors et architecture du projet

Au cœur du projet po4a, la classe Locale::Po4a::TransTractor(3pm) est le parent commun de tous les analyseurs po4a. Ce nom étrange vient du fait qu'elle est en charge à la fois de traduire des documents et d'extraire des chaînes de caractères.

Plus formellement, elle prend en entrée un document à traduire ainsi qu'un fichier PO contenant les traductions à utiliser, tout en produisant deux sorties distinctes : un autre fichier PO (résultant de l'extraction des chaînes traduisibles du document d'entrée) et un document traduit (avec la même structure que celui d'entrée, mais avec toutes les chaînes traduisibles remplacées par le contenu du PO d'entrée). Voici une représentation graphique de cela :

Document d'entrée --\                             /---> Document de sortie
                   \      TransTractor::       /       (traduit)
                    +-->--   parse()  --------+
                   /                           \
PO d'entrée --------/                             \---> PO de sortie
                                                    (extrait)

Cet os est au cœur de toute l'architecture de po4a. Si vous fournissez les entrées et ignorez le PO de sortie, vous obtenez po4a-translate. Si vous ignorez le document de sortie, vous obtenez po4a-updatepo. po4a utilise un premier TransTractor pour obtenir un fichier POT de sortie à jour (en ignorant les documents de sortie), appelle msgmerge -U pour mettre à jour les fichiers PO de traduction sur disque, et construit un second TransTractor avec ces fichiers PO mis à jour pour mettre à jour les documents de sortie. En bref, po4a fournit une solution tout-en-un pour mettre à jour ce qui doit l'être, en utilisant un seul fichier de configuration.

po4a-gettextize utilise également deux TransTractors, mais d'une manière différente : il construit un TransTractor par langue, puis construit un nouveau fichier PO en utilisant les msgids du document original comme msgids, et les msgids du document traduit comme msgstrs. Il faut être très prudent pour s'assurer que les chaînes correspondantes de cette manière correspondent réellement, comme décrit dans po4a-gettextize(1).

Analyseurs spécifiques aux formats

Tous les analyseurs de formats po4a sont implémentés au-dessus du TransTractor. Certains d'entre eux sont très simples, tels que ceux pour le texte brut, Markdown et AsciiDoc. Ils chargent les lignes une par une en utilisant TransTractor::shiftline(), accumulent le contenu des paragraphes ou autre. Une fois qu'une chaîne est complètement analysée, l'analyseur utilise TransTractor::translate() pour (1) ajouter cette chaîne au fichier PO de sortie et (2) obtenir la traduction du fichier PO d'entrée. L'analyseur pousse ensuite le résultat vers le fichier de sortie en utilisant TransTractor::pushline().

D'autres analyseurs sont plus complexes car ils s'appuient sur un analyseur externe pour analyser le document d'entrée. Les analyseurs Xml, HTML, SGML et Pod sont construits sur des analyseurs SAX. Ils déclarent des rappels à des événements tels que « J'ai trouvé un nouveau titre dont le contenu est le suivant » pour mettre à jour le document de sortie et les fichiers POT de sortie en fonction du contenu d'entrée en utilisant TransTractor::translate() et TransTractor::pushline(). L'analyseur Yaml est similaire mais différent : il sérialise une structure de données produite par l'analyseur YAML::Tiny. C'est pourquoi le module Yaml de po4a échoue à déclarer les lignes de référence : l'emplacement de chaque chaîne dans le fichier d'entrée n'est pas conservé par l'analyseur, nous ne pouvons donc fournir que « $nom_fichier:1 » comme emplacement de chaîne. Les analyseurs orientés SAX utilisent des variables globales et d'autres astuces pour enregistrer le nom du fichier et les numéros de ligne des références.

Un problème spécifique découle des encodages de fichiers et des marqueurs BOM. Les analyseurs simples peuvent oublier ce problème, qui est géré par TransTractor::read() (utilisé en interne pour obtenir les lignes d'un document d'entrée), mais les modules qui s'appuient sur un analyseur externe doivent s'assurer que tous les fichiers sont lus avec une couche de décodage PerlIO appropriée. Le plus simple est d'ouvrir le fichier soi-même et de fournir un descripteur de fichier ou directement la chaîne complète à votre analyseur externe. Consultez Pod::read() et Pod::parse() pour un exemple. Le contenu lu par le TransTractor est ignoré, mais un descripteur de fichier frais est passé à l'analyseur externe. La partie importante est le mode "<:encoding($charset)" qui est passé à la fonction open() de Perl.

Objets Po

La classe Locale::Po4a::Po(3pm) est responsable du chargement et de l'utilisation des fichiers PO et POT. Essentiellement, vous pouvez lire un fichier, ajouter des entrées, obtenir des traductions avec la méthode gettext(), écrire le PO dans un fichier. Des fonctionnalités plus avancées telles que la fusion d'un fichier PO contre un fichier POT ou la validation d'un fichier sont déléguées respectivement à msgmerge et msgfmt.

FAQ

Comment prononce-t-on po4a ?

Personnellement, je le vocalise comme pouah https://en.wiktionary.org/wiki/pouah, qui est une onomatopée française que nous utilisons à la place de beurk :) J'ai peut-être un sens de l'humour étrange :)

Pourquoi les scripts individuels sont-ils dépréciés ?

En effet, po4a-updatepo et po4a-translate sont dépréciés au profit de po4a. La raison est que si po4a peut être utilisé comme remplacement direct de ces scripts, il y a beaucoup de duplication de code ici. Les scripts individuels font environ 150 lignes de code alors que le programme po4a fait 1200 lignes, ils font donc beaucoup plus en plus des internes communs. La duplication de code entraîne des bugs dans les deux versions qui nécessitent deux corrections. Un exemple de cette duplication sont les bugs #1022216 dans Debian et le problème #442 sur GitHub qui ont eu exactement la même correction, mais une dans po4a et l'autre dans po4a-updatepo.

À long terme, j'aimerais abandonner les scripts individuels et ne maintenir qu'une seule version de ce code. Ce qui est sûr, c'est que les scripts individuels ne seront plus améliorés, donc seul po4a bénéficiera des nouvelles fonctionnalités. Cela dit, il n'y a pas d'urgence de dépréciation. Je prévois de conserver les scripts individuels aussi longtemps que possible, et au moins jusqu'en 2030. Si votre projet utilise encore po4a-updatepo et po4a-translate en 2030, vous pourriez avoir un problème.

Nous pourrions également supprimer la dépréciation de ces scripts à un moment donné, si un refactoring réduit la duplication de code à zéro. Si vous avez une idée (ou mieux : un patch), votre aide est la bienvenue.

Qu'en est-il des autres outils de traduction pour la documentation utilisant gettext ?

Il en existe quelques-uns. Voici une liste potentiellement incomplète, et d'autres outils arrivent à l'horizon.

poxml
C'est l'outil développé par les gens de KDE pour gérer DocBook XML. Autant que je sache, ce fut le premier programme à extraire des chaînes à traduire de la documentation vers des fichiers PO, et à les réinjecter après traduction.

Il ne peut gérer que XML, et seulement un DTD particulier. Je suis assez mécontent de la gestion des listes, qui se terminent en un seul grand msgid. Lorsque la liste devient grande, le bloc devient plus difficile à avaler.

po-debiandoc
Ce programme de Denis Barbier est une sorte de précurseur du module SGML de po4a, qui le déprécie plus ou moins. Comme son nom l'indique, il ne gère que le DTD DebianDoc, qui est plus ou moins un DTD déprécié.
xml2po.py
Utilisé par l'équipe de documentation de GIMP depuis 2004, fonctionne assez bien même si, comme son nom l'indique, uniquement avec des fichiers XML.

NAME

po4a - Documentation translation workflow

Introduction

The po4a project (proof of French automatic translation) aims to simplify the translation of documentation. It uses the standard gettext tools, widely used for translating messages into the native language, but adapted for documentation.

This page describes the general philosophy of po4a and the different tools it offers. You will find below the list of the supported formats, the way po4a works, and a summary of the advantages of this approach.

Why po4a?

For a long time, translators have been working on the translated files directly. This had several drawbacks:

  • The translator had to know the syntax of the file format to translate. This is especially true for formats like man pages, Texinfo, or AsciiDoc, which are not very well-known.
  • It was impossible to get statistics on the translation progress.
  • Translators could modify the documentation structure itself, which is often not desired.
  • It was hard to merge translations, and even harder to detect if a translation was out of date.

The po4a project aims to solve these problems by using gettext, which is the standard for message translation.

Using po4a

po4a is a set of scripts that convert documentation into PO files, which are easily translatable using gettext tools. Once translated, po4a converts the PO files back into the original documentation format.

The general workflow is:

  1. Gettextize: The po4a-gettextize(1) script parses the documentation file and extracts all strings that need to be translated into a POT file (PO Template file).
  2. Translate: Use a PO editor (like Emacs, GEdit, Lokalize, Gtranslator, etc.) to translate the strings in the POT file into a PO file for your language.
  3. Update: The po4a-updatepo(1) script updates the PO file with new strings from the POT file and also removes strings that are no longer present in the original documentation.
  4. Translate: Translate the new strings, and update the existing ones if needed.
  5. Translate back: The po4a-translate(1) script uses the PO file and the original documentation to generate the translated documentation file.

For a more detailed description of how to use po4a, please refer to the specific documentation of each script and to the manual page of the po4a(1) wrapper script.

How does it work?

po4a uses a set of parsers, one for each supported format. These parsers are responsible for extracting the translatable strings and for rebuilding the translated documents.

The general principle is to identify blocks of text that are translatable, and to wrap them in specific markers. These markers are then used by the gettext tools to extract the strings into PO files.

For example, a man page paragraph can be seen as a block of text. The parser will extract the text content of the paragraph and store it in a PO file. Then, when translating back, it will insert the translated text back into the paragraph structure.

The parser must also handle the non-translatable parts of the document, like formatting commands, code snippets, or variable names. This is done by ensuring that these parts are not extracted into the PO file, and are preserved as-is in the translated document.

SUMMARY of the advantages of the gettext based approach

  • The translations are not stored along with the original, which makes it possible to detect if translations become out of date.
  • The translations are stored in separate files from each other, which prevents translators of different languages from interfering, both when submitting their patch and at the file encoding level.
  • It is based internally on gettext (but po4a offers a very simple interface so that you don't need to understand the internals to use it). That way, we don't have to re-implement the wheel, and because of their wide use, we can think that these tools are more or less bug free.
  • Nothing changed for the end-user (beside the fact translations will hopefully be better maintained). The resulting documentation file distributed is exactly the same.
  • No need for translators to learn a new file syntax and their favorite PO file editor (like Emacs' PO mode, Lokalize or Gtranslator) will work just fine.
  • gettext offers a simple way to get statistics about what is done, what should be reviewed and updated, and what is still to do. Some example can be found at those addresses: 
    - https://docs.kde.org/stable5/en/kdesdk/lokalize/project-view.html
- http://www.debian.org/intl/l10n/

But everything isn't green, and this approach also has some disadvantages we have to deal with.

  • Addenda are somewhat strange at the first glance.
  • You can't adapt the translated text to your preferences, like splitting a paragraph here, and joining two other ones there. But in some sense, if there is an issue with the original, it should be reported as a bug anyway.
  • Even with an easy interface, it remains a new tool people have to learn.

    One of my dreams would be to integrate somehow po4a to Gtranslator or Lokalize. When a documentation file is opened, the strings are automatically extracted, and a translated file + po file can be written to disk. If we manage to do an MS Word (TM) module (or at least RTF) professional translators may even use it.
