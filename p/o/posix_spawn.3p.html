PROLOGUE

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consultez la page de manuel Linux correspondante pour les détails du comportement sous Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

posix_spawn, posix_spawnp — créer un processus (TEMPS RÉEL AVANCÉ)

SYNOPIS

#include <spawn.h>
int posix_spawn(pid_t *restrict pid, const char *restrict path,
    const posix_spawn_file_actions_t *file_actions,
    const posix_spawnattr_t *restrict attrp,
    char *const argv[restrict], char *const envp[restrict]);
int posix_spawnp(pid_t *restrict pid, const char *restrict file,
    const posix_spawn_file_actions_t *file_actions,
    const posix_spawnattr_t *restrict attrp,
    char *const argv[restrict], char *const envp[restrict]);

DESCRIPTION

Les fonctions posix_spawn() et posix_spawnp() créent un nouveau processus (processus enfant) à partir de l'image de processus spécifiée. L'image du nouveau processus est construite à partir d'un fichier exécutable régulier appelé fichier image du nouveau processus.

Lorsqu'un programme C est exécuté à la suite de cet appel, il est entré comme un appel de fonction de langage C comme suit :

int main(int argc, char *argv[]);

où argc est le nombre d'arguments et argv est un tableau de pointeurs de caractères vers les arguments eux-mêmes. De plus, la variable suivante :

extern char **environ;

doit être initialisée comme un pointeur vers un tableau de pointeurs de caractères vers les chaînes d'environnement.

L'argument argv est un tableau de pointeurs de caractères vers des chaînes null-terminées. Le dernier membre de ce tableau est un pointeur null et n'est pas compté dans argc. Ces chaînes constituent la liste des arguments disponibles pour l'image du nouveau processus. La valeur dans argv[0] doit pointer vers une chaîne de nom de fichier associée à l'image du processus démarrée par la fonction posix_spawn() ou posix_spawnp().

L'argument envp est un tableau de pointeurs de caractères vers des chaînes null-terminées. Ces chaînes constituent l'environnement de l'image du nouveau processus. Le tableau d'environnement est terminé par un pointeur null.

Le nombre d'octets disponibles pour les listes combinées d'arguments et d'environnement du processus enfant est {ARG_MAX}. L'implémentation doit spécifier dans la documentation système (voir le volume Base Definitions de POSIX.1‐2017, Chapitre 2, Conformité) si des frais généraux de liste, tels que les mots de longueur, les terminateurs null, les pointeurs ou les octets d'alignement, sont inclus dans ce total.

L'argument path pour posix_spawn() est un nom de chemin qui identifie le fichier image du nouveau processus à exécuter.

Le paramètre file pour posix_spawnp() est utilisé pour construire un nom de chemin qui identifie le fichier image du nouveau processus. Si le paramètre file contient un caractère <slash> ( caractères), le paramètre file est utilisé comme nom de chemin pour le fichier image du nouveau processus. Sinon, le préfixe de chemin pour ce fichier est obtenu par une recherche dans les répertoires passés en tant que variable d'environnement PATH (voir le volume Base Definitions de POSIX.1‐2017, Chapitre 8, Variables d'environnement). Si cette variable d'environnement n'est pas définie, les résultats de la recherche sont définis par l'implémentation.

Si file_actions est un pointeur null, alors les descripteurs de fichiers ouverts dans le processus appelant restent ouverts dans le processus enfant, à l'exception de ceux dont le drapeau de fermeture à l'exécution FD_CLOEXEC est défini (voir fcntl()). Pour les descripteurs de fichiers qui restent ouverts, le processus enfant n'hérite d'aucun verrouillage de fichier, mais tous les autres attributs des descriptions de fichiers correspondantes (voir fcntl()) restent inchangés.

Si file_actions n'est pas NULL, alors les descripteurs de fichiers ouverts dans le processus enfant sont ceux ouverts dans le processus appelant, tels que modifiés par l'objet d'actions de fichiers de création pointé par file_actions et le drapeau FD_CLOEXEC de chaque descripteur de fichier ouvert restant après le traitement des actions de fichiers de création. L'ordre effectif de traitement des actions de fichiers de création est le suivant :

1.
L'ensemble des descripteurs de fichiers ouverts pour le processus enfant est initialement le même ensemble que celui ouvert pour le processus appelant. Le processus enfant n'hérite d'aucun verrouillage de fichier, mais tous les autres attributs des descriptions de fichiers correspondantes (voir fcntl()) restent inchangés.
2.
Le masque de signaux, les actions par défaut des signaux et les ID utilisateur et groupe effectifs pour le processus enfant sont modifiés comme spécifié dans l'objet d'attributs référencé par attrp.
3.
Les actions de fichiers spécifiées par l'objet d'actions de fichiers de création sont effectuées dans l'ordre où elles ont été ajoutées à l'objet d'actions de fichiers de création.
4.
Tout descripteur de fichier dont le drapeau FD_CLOEXEC est défini (voir fcntl()) est fermé.

Si le descripteur de fichier 0, 1 ou 2 est autrement fermé dans l'image du nouveau processus créée par posix_spawn() ou posix_spawnp(), les implémentations peuvent ouvrir un fichier non spécifié pour le descripteur de fichier dans l'image du nouveau processus. Si un utilitaire standard ou une application conforme est exécuté avec le descripteur de fichier 0 non ouvert en lecture ou avec le descripteur de fichier 1 ou 2 non ouvert en écriture, l'environnement dans lequel l'utilitaire ou l'application est exécuté est considéré comme non conforme, et par conséquent, l'utilitaire ou l'application peut ne pas se comporter comme décrit dans cette norme.

Le type d'objet d'attributs de création posix_spawnattr_t est défini dans <spawn.h>. Il doit contenir au moins les attributs définis ci-dessous.

Si l'indicateur POSIX_SPAWN_SETPGROUP est défini dans l'attribut spawn-flags de l'objet référencé par attrp, et si l'attribut spawn-pgroup du même objet n'est pas nul, alors le groupe de processus de l'enfant sera celui spécifié dans l'attribut spawn-pgroup de l'objet référencé par attrp.

Dans le cas spécial où l'indicateur POSIX_SPAWN_SETPGROUP est défini dans l'attribut spawn-flags de l'objet référencé par attrp, et si l'attribut spawn-pgroup du même objet est défini à zéro, alors l'enfant sera dans un nouveau groupe de processus avec un ID de groupe de processus égal à son ID de processus.

Si l'indicateur POSIX_SPAWN_SETPGROUP n'est pas défini dans l'attribut spawn-flags de l'objet référencé par attrp, le nouveau processus enfant héritera du groupe de processus du parent.

Si l'indicateur POSIX_SPAWN_SETSCHEDPARAM est défini dans l'attribut spawn-flags de l'objet référencé par attrp, mais que POSIX_SPAWN_SETSCHEDULER n'est pas défini, l'image du nouveau processus aura initialement la politique de planification du processus appelant avec les paramètres de planification spécifiés dans l'attribut spawn-schedparam de l'objet référencé par attrp.

Si l'indicateur POSIX_SPAWN_SETSCHEDULER est défini dans l'attribut spawn-flags de l'objet référencé par attrp (indépendamment du réglage de l'indicateur POSIX_SPAWN_SETSCHEDPARAM), l'image du nouveau processus aura initialement la politique de planification spécifiée dans l'attribut spawn-schedpolicy de l'objet référencé par attrp et les paramètres de planification spécifiés dans l'attribut spawn-schedparam du même objet.

L'indicateur POSIX_SPAWN_RESETIDS dans l'attribut spawn-flags de l'objet référencé par attrp gouverne l'ID utilisateur effectif du processus enfant. Si cet indicateur n'est pas défini, le processus enfant héritera de l'ID utilisateur effectif du processus parent. Si cet indicateur est défini, l'ID utilisateur effectif du processus enfant sera réinitialisé à l'ID utilisateur réel du parent. Dans les deux cas, si le bit de mode set-user-ID du fichier image du nouveau processus est défini, l'ID utilisateur effectif du processus enfant deviendra l'ID du propriétaire du fichier avant que l'image du nouveau processus ne commence son exécution.

L'indicateur POSIX_SPAWN_RESETIDS dans l'attribut spawn-flags de l'objet référencé par attrp gouverne également l'ID groupe effectif du processus enfant. Si cet indicateur n'est pas défini, le processus enfant héritera de l'ID groupe effectif du processus parent. Si cet indicateur est défini, l'ID groupe effectif du processus enfant sera réinitialisé à l'ID groupe réel du parent. DESCRIPTION

The posix_spawn() and posix_spawnp() functions shall create a new process image by, at least conceptually, calling fork() to create a child process and then calling one of the exec family of functions to execute the new process image.

The new process image is that of the file specified by the file argument. The argument list for the new process image is the argument list specified by the argv argument. The environment for the new process image is the environment specified by the envp argument.

The behavior of posix_spawn() and posix_spawnp() is modified by the attrp argument. If the attrp argument is not NULL, it points to an object of type posix_spawnattr_t that contains implementation-defined information used to modify the process creation behavior.

The behavior is also modified by the file_actions argument. If file_actions is not NULL, it points to an object of type posix_spawn_file_actions_t that contains information specifying file descriptor manipulation operations to be performed in the child process image after it is created, but before the new process image is executed.

The posix_spawnp() function is equivalent to posix_spawn() except that the file to be executed is found in the PATH environment variable.

The posix_spawn() and posix_spawnp() functions are not required to be thread-safe. An invocation of posix_spawn() or posix_spawnp() in a multi-threaded process that results in the creation of a child process that is also multi-threaded is subject to additional restrictions. If the child process is multi-threaded, only the calling thread is created in the child process. All other threads are terminated in the child process. If the calling thread is part of a set of threads that have been cancelled, or if it has an outstanding asynchronous cancellation request, the behavior is implementation-defined.

If the POSIX_SPAWN_SETSIGMASK flag is set in the spawn-flags attribute of the object referenced by attrp, the child process shall initially have the signal mask specified in the spawn-sigmask attribute of the object referenced by attrp.

If the POSIX_SPAWN_SETSIGDEF flag is set in the spawn-flags attribute of the object referenced by attrp, the signals specified in the spawn-sigdefault attribute of the same object shall be set to their default actions in the child process. Signals set to the default action in the parent process shall be set to the default action in the child process.

Signals set to be caught by the calling process shall be set to the default action in the child process.

Except for SIGCHLD, signals set to be ignored by the calling process image shall be set to be ignored by the child process, unless otherwise specified by the POSIX_SPAWN_SETSIGDEF flag being set in the spawn-flags attribute of the object referenced by attrp and the signals being indicated in the spawn-sigdefault attribute of the object referenced by attrp.

If the SIGCHLD signal is set to be ignored by the calling process, it is unspecified whether the SIGCHLD signal is set to be ignored or to the default action in the child process, unless otherwise specified by the POSIX_SPAWN_SETSIGDEF flag being set in the spawn_flags attribute of the object referenced by attrp and the SIGCHLD signal being indicated in the spawn_sigdefault attribute of the object referenced by attrp.

If the value of the attrp pointer is NULL, then the default values are used.

All process attributes, other than those influenced by the attributes set in the object referenced by attrp as specified above or by the file descriptor manipulations specified in file_actions, shall appear in the new process image as though fork() had been called to create a child process and then a member of the exec family of functions had been called by the child process to execute the new process image.

It is implementation-defined whether the fork handlers are run when posix_spawn() or posix_spawnp() is called.

VALEUR RENVOYÉE

En cas de succès, posix_spawn() et posix_spawnp() renvoient l'ID du processus enfant au processus parent, dans la variable pointée par un argument pid non NULL, et renvoient zéro comme valeur de retour de la fonction. Sinon, aucun processus enfant n'est créé, la valeur stockée dans la variable pointée par un pid non NULL est indéterminée, et un numéro d'erreur est renvoyé comme valeur de retour de la fonction pour indiquer l'erreur. Si l'argument pid est un pointeur nul, l'ID du processus enfant n'est pas renvoyé à l'appelant.

ERREURS

Ces fonctions peuvent échouer si :

EINVAL
La valeur spécifiée par file_actions ou attrp est invalide.

Si cette erreur se produit après que le processus appelant est retourné avec succès de la fonction posix_spawn() ou posix_spawnp(), le processus enfant peut se terminer avec le statut de sortie 127.

Si posix_spawn() ou posix_spawnp() échoue pour l'une des raisons qui feraient échouer fork() ou l'une des fonctions de la famille exec, une valeur d'erreur sera renvoyée comme décrit par fork() et exec, respectivement (ou, si l'erreur se produit après que le processus appelant est retourné avec succès, le processus enfant se terminera avec le statut de sortie 127).

Si POSIX_SPAWN_SETPGROUP est défini dans l'attribut spawn-flags de l'objet référencé par attrp, et si posix_spawn() ou posix_spawnp() échoue lors de la modification du groupe de processus de l'enfant, une valeur d'erreur sera renvoyée comme décrit par setpgid() (ou, si l'erreur se produit après que le processus appelant est retourné avec succès, le processus enfant se terminera avec le statut de sortie 127).

Si POSIX_SPAWN_SETSCHEDPARAM est défini et POSIX_SPAWN_SETSCHEDULER n'est pas défini dans l'attribut spawn-flags de l'objet référencé par attrp, alors si posix_spawn() ou posix_spawnp() échoue pour l'une des raisons qui feraient échouer sched_setparam(), une valeur d'erreur sera renvoyée comme décrit par sched_setparam() (ou, si l'erreur se produit après que le processus appelant est retourné avec succès, le processus enfant se terminera avec le statut de sortie 127).

Si POSIX_SPAWN_SETSCHEDULER est défini dans l'attribut spawn-flags de l'objet référencé par attrp, et si posix_spawn() ou posix_spawnp() échoue pour l'une des raisons qui feraient échouer sched_setscheduler(), une valeur d'erreur sera renvoyée comme décrit par sched_setscheduler() (ou, si l'erreur se produit après que le processus appelant est retourné avec succès, le processus enfant se terminera avec le statut de sortie 127).

Si l'argument file_actions n'est pas NULL, et spécifie toutes les actions close, dup2, ou open à effectuer, et si posix_spawn() ou posix_spawnp() échoue pour l'une des raisons qui feraient échouer close(), dup2(), ou open(), une valeur d'erreur sera renvoyée comme décrit par close(), dup2(), et open(), respectivement (ou, si l'erreur se produit après que le processus appelant est retourné avec succès, le processus enfant se terminera avec le statut de sortie 127). Une action de fichier ouvert peut, par elle-même, entraîner l'une des erreurs décrites par close() ou dup2(), en plus de celles décrites par open().

UTILISATION PAR L'APPLICATION

Ces fonctions font partie de l'option Spawn et ne sont pas nécessairement fournies sur toutes les implémentations.

Voir également la section UTILISATION PAR L'APPLICATION pour exec.

JUSTIFICATION

La fonction posix_spawn() et sa proche parente posix_spawnp() ont été introduites pour surmonter les difficultés suivantes perçues avec fork() : la fonction fork() est difficile ou impossible à implémenter sans échange (swapping) ou traduction d'adresses dynamique.

*
L'échange est généralement trop lent pour un environnement temps réel.
*
La traduction d'adresses dynamique n'est pas disponible partout où POSIX peut être utile.
*
Les processus sont trop utiles pour être simplement exclus de POSIX chaque fois qu'il doit s'exécuter sans traduction d'adresses ou autres services MMU.

Ainsi, POSIX a besoin de primitives de création de processus et d'exécution de fichiers qui peuvent être implémentées efficacement sans traduction d'adresses ou autres services MMU.

La fonction posix_spawn() est implémentable en tant que routine de bibliothèque, mais posix_spawn() et posix_spawnp() sont conçues comme des opérations noyau. De plus, bien qu'elles puissent être un remplacement efficace pour de nombreuses paires fork()/exec, leur objectif est de fournir des primitives de création de processus utiles pour les systèmes qui ont des difficultés avec fork(), et non de fournir des remplacements directs pour fork()/exec.

Cette vision du rôle de posix_spawn() et posix_spawnp() a influencé la conception de leur API. Elle ne tente pas de fournir la fonctionnalité complète de fork()/exec dans laquelle des opérations arbitraires spécifiées par l'utilisateur de toute sorte sont permises entre la création du processus enfant et l'exécution de la nouvelle image de processus ; toute tentative d'atteindre ce niveau nécessiterait de fournir un langage de programmation comme paramètres. Au lieu de cela, posix_spawn() et posix_spawnp() sont des primitives de création de processus comme le package de liaisons du langage Ada POSIX_Process_Primitives Start_Process et Start_Process_Search, et aussi comme celles de nombreux systèmes d'exploitation qui ne sont pas des systèmes UNIX, mais avec quelques ajouts spécifiques à POSIX.

Pour atteindre ses objectifs de couverture, posix_spawn() et posix_spawnp() contrôlent six types d'héritage : descripteurs de fichiers, ID de groupe de processus, ID utilisateur et groupe, masque de signaux, planification, et si chaque signal ignoré dans le parent restera ignoré dans l'enfant, ou sera réinitialisé à son action par défaut dans l'enfant.

Le contrôle des descripteurs de fichiers est nécessaire pour permettre à une image de processus enfant écrite indépendamment d'accéder aux flux de données ouverts par et même générés ou lus par le processus parent, sans être spécifiquement codée pour savoir quels fichiers et descripteurs de fichiers du parent doivent être utilisés. Le contrôle de l'ID de groupe de processus est nécessaire pour contrôler la relation du contrôle de travail du processus enfant avec celle du parent.

Le contrôle du masque de signaux et des actions par défaut des signaux est suffisant pour supporter l'implémentation de system(). Bien que le support de system() ne soit pas explicitement l'un des objectifs de posix_spawn() et posix_spawnp(), il est couvert par l'objectif de couverture "au moins 50%".

L'intention est que l'héritage normal des descripteurs de fichiers à travers fork(), l'effet ultérieur des actions de fichiers de spawn spécifiées, et l'héritage normal des descripteurs de fichiers à travers l'une des fonctions de la famille exec spécifient entièrement l'héritage des fichiers ouverts. L'implémentation n'a pas besoin de prendre de décisions concernant l'ensemble des descripteurs de fichiers ouverts lorsque l'image du processus enfant commence son exécution, ces décisions ayant déjà été prises par l'appelant et exprimées comme l'ensemble des descripteurs de fichiers ouverts et leurs drapeaux FD_CLOEXEC au moment de l'appel et les actions de fichiers de spawn spécifiées dans l'appel. On nous a assuré que dans les cas où les primitives Ada POSIX Start_Process ont été implémentées dans une bibliothèque, cette méthode de contrôle de l'héritage des descripteurs de fichiers peut être implémentée très facilement.

Nous pouvons identifier plusieurs problèmes avec posix_spawn() et posix_spawnp(), mais il ne semble pas y avoir de solution qui introduise moins de problèmes. La modification de l'environnement pour les attributs du processus enfant non spécifiables via les arguments attrp ou file_actions doit être effectuée dans le processus parent, et comme le parent veut généralement sauvegarder son contexte, c'est plus coûteux que des fonctionnalités similaires avec fork()/exec. Il est également compliqué de modifier l'environnement d'un processus multi-threadé temporairement, car tous les threads doivent s'accorder sur le moment où il est sûr de modifier l'environnement. Cependant, ce coût n'est supporté que par les invocations de posix_spawnposix_spawnp() qui utilisent la fonctionnalité supplémentaire. Comme les modifications étendues ne sont pas le cas habituel, et sont particulièrement improbables dans du code critique en temps, garder une grande partie du contrôle de l'environnement hors de posix_spawn() et posix_spawnp() est une conception appropriée.

Les fonctions posix_spawn() et posix_spawnp() n'ont pas toute la puissance de fork()/exec. C'est attendu. La fonction fork() est une opération merveilleusement puissante. Nous ne nous attendons pas à dupliquer sa fonctionnalité dans une fonction simple et rapide sans exigences matérielles spéciales. Il est à noter que posix_spawn() et posix_spawnp() sont très similaires aux opérations de création de processus sur de nombreux systèmes d'exploitation qui ne sont pas des systèmes UNIX.

Exigences

Les exigences pour posix_spawn() et posix_spawnp() sont :

*
Elles doivent être implémentables sans MMU ni matériel inhabituel.
*
Elles doivent être compatibles avec les normes POSIX existantes.

Les objectifs supplémentaires sont :

*
Elles devraient être implémentables efficacement.
*
Elles devraient pouvoir remplacer au moins 50 % des exécutions typiques de fork().
*
Un système avec posix_spawn() et posix_spawnp() et sans fork() devrait être utile, au moins pour les applications temps réel.
*
Un système avec fork() et la famille exec devrait pouvoir implémenter posix_spawn() et posix_spawnp() en tant que routines de bibliothèque.

Deux Syntaxes

L'appel exec de POSIX a plusieurs séquences d'appel avec environ la même fonctionnalité. Celles-ci semblent nécessaires pour la compatibilité avec la pratique existante. Étant donné que la pratique existante pour les fonctions posix_spawn*() est autrement substantiellement différente de POSIX, nous estimons que la simplicité l'emporte sur la compatibilité. Il n'y a donc que deux noms pour les fonctions posix_spawn*().

La liste des paramètres ne diffère pas entre posix_spawn() et posix_spawnp(); posix_spawnp() interprète le deuxième paramètre de manière plus élaborée que posix_spawn().

Compatibilité avec POSIX.5 (Ada)

Les procédures Start_Process et Start_Process_Search du package POSIX_Process_Primitives de la liaison du langage Ada à POSIX.1 encapsulent la fonctionnalité fork() et exec d'une manière similaire à celle de posix_spawn() et posix_spawnp(). Initialement, dans un souci de simplicité, les développeurs de la norme avaient limité les capacités de posix_spawn() et posix_spawnp() à un sous-ensemble des capacités de Start_Process et Start_Process_Search ; certaines capacités non par défaut n'étaient pas prises en charge. Cependant, sur la base des suggestions du groupe de vote pour améliorer le mappage des descripteurs de fichiers ou le supprimer, et sur les conseils d'un membre du groupe de travail des liaisons du langage Ada, les développeurs de la norme ont décidé que posix_spawn() et posix_spawnp() devraient être suffisamment puissants pour implémenter Start_Process et Start_Process_Search. La raison est que si la liaison du langage Ada à une primitive de ce type a déjà été approuvée comme norme IEEE, il y a peu de justification pour ne pas approuver les parties fonctionnellement équivalentes d'une liaison C. Les trois seules capacités fournies par posix_spawn() et posix_spawnp() qui ne sont pas fournies par Start_Process et Start_Process_Search sont la spécification facultative de l'ID du groupe de processus de l'enfant, l'ensemble des signaux à réinitialiser au traitement de signal par défaut dans le processus enfant, et la politique et les paramètres de planification de l'enfant.

Pour que la liaison du langage Ada pour Start_Process soit implémentée avec posix_spawn(), cette liaison devrait explicitement passer un masque de signaux vide et l'environnement du parent à posix_spawn() chaque fois que l'appelant de Start_Process laissait ces arguments par défaut, car posix_spawn() ne fournit pas de tels défauts. La capacité de Start_Process à masquer les signaux spécifiés par l'utilisateur pendant son exécution est fonctionnellement unique à la liaison du langage Ada et doit être traitée dans la liaison séparément de l'appel à posix_spawn().

Groupe de processus

Le champ d'héritage du groupe de processus peut être utilisé pour joindre le processus enfant à un groupe de processus existant. En attribuant la valeur zéro à l'attribut spawn-pgroup de l'objet référencé par attrp, le mécanisme setpgid() placera le processus enfant dans un nouveau groupe de processus.

Threads

Sans les fonctions posix_spawn() et posix_spawnp(), les systèmes sans traduction d'adresses peuvent toujours utiliser des threads pour fournir une abstraction de concurrence. Dans de nombreux cas, la création de threads suffit, mais ce n'est pas toujours un bon substitut. Les fonctions posix_spawn() et posix_spawnp() sont considérablement « plus lourdes » que la création de threads. Les processus ont plusieurs attributs importants que les threads n'ont pas. Même sans traduction d'adresses, un processus peut avoir une protection mémoire de base et de limites. Chaque processus a un environnement de processus incluant des attributs de sécurité et des capacités de fichiers, et de puissants attributs de planification. Les processus abstraient mieux le comportement des multiprocesseurs à architecture mémoire non uniforme que les threads, et ils sont plus pratiques à utiliser pour des activités qui ne sont pas étroitement liées.

Les fonctions posix_spawn() et posix_spawnp() peuvent ne pas apporter le support de plusieurs processus à toutes les configurations. La création de processus n'est pas la seule pièce de support du système d'exploitation requise pour prendre en charge plusieurs processus. Le coût total du support de plusieurs processus peut être assez élevé dans certaines circonstances. La pratique existante montre que le support de plusieurs processus est rare et que les threads sont courants parmi les « petits noyaux ». Il devrait donc probablement continuer d'y avoir des AEP pour les systèmes d'exploitation avec un seul processus.

Notification asynchrone d'erreur

Une implémentation de bibliothèque de posix_spawn() ou posix_spawnp() peut ne pas être en mesure de détecter toutes les erreurs possibles avant de créer le processus enfant. POSIX.1-2008 prévoit une indication d'erreur renvoyée par un processus enfant qui n'a pas pu terminer correctement l'opération de lancement via un statut de sortie spécial qui peut être détecté à l'aide de la valeur de statut renvoyée par wait(), waitid(), et waitpid().

L'interface stat_val et les macros utilisées pour l'interpréter ne sont pas bien adaptées à la fonction de renvoi d'erreurs d'API, mais elles sont la seule voie disponible pour une implémentation de bibliothèque. Ainsi, une implémentation peut faire sortir le processus enfant avec le statut de sortie 127 pour toute erreur détectée pendant le processus de lancement après que la fonction posix_spawn() ou posix_spawnp() soit revenue avec succès.

Les développeurs de la norme avaient proposé d'utiliser deux macros supplémentaires pour interpréter stat_val. La première, WIFSPAWNFAIL, aurait détecté un statut indiquant que l'enfant est sorti en raison d'une erreur détectée pendant les opérations posix_spawn() ou posix_spawnp() plutôt que pendant l'exécution réelle de l'image du processus enfant ; la seconde, WSPAWNERRNO, aurait extrait la valeur d'erreur si WIFSPAWNFAIL indiquait un échec. Malheureusement, le groupe de vote s'y est fortement opposé car cela rendrait une implémentation de bibliothèque de posix_spawn() ou posix_spawnp() dépendante de modifications du noyau de waitpid() pour pouvoir intégrer des informations spéciales dans stat_val afin d'indiquer un échec de lancement.

Les 8 bits du statut de sortie du processus enfant qui sont garantis par POSIX.1-2008 pour être accessibles au processus parent en attente sont insuffisants pour distinguer une erreur de lancement de tout autre type d'erreur qui peut être renvoyée par une image de processus arbitraire. Aucun autre bit du statut de sortie n'est requis pour être visible dans stat_val, de sorte que ces macros ne pouvaient pas être strictement implémentées au niveau de la bibliothèque. La réservation d'un statut de sortie de 127 pour de telles erreurs de lancement est cohérente avec l'utilisation de cette valeur par system() et popen() pour signaler les échecs de ces opérations qui se produisent après le retour de la fonction mais avant qu'un shell ne soit capable de s'exécuter. Le statut de sortie de 127 n'identifie pas de manière unique cette classe d'erreur, ni ne fournit d'informations détaillées sur la nature de l'échec. Notez qu'une implémentation noyau de posix_spawn() ou posix_spawnp() est autorisée (et encouragée) à renvoyer toute erreur possible en tant que valeur de fonction, fournissant ainsi des informations d'échec plus détaillées au processus parent.

Par conséquent, aucune macro spéciale n'est disponible pour isoler les erreurs asynchrones de posix_spawn() ou posix_spawnp(). Au lieu de cela, les erreurs détectées par les opérations posix_spawn() ou posix_spawnp() dans le contexte du processus enfant avant l'exécution de la nouvelle image de processus sont signalées en définissant le statut de sortie de l'enfant sur 127. Le processus appelant peut utiliser les macros WIFEXITED et WEXITSTATUS sur la stat_val stockée par les fonctions wait() ou waitpid() pour détecter les échecs de lancement dans la mesure où d'autres valeurs de statut avec lesquelles l'image du processus enfant peut sortir (avant que le parent ne puisse déterminer de manière concluante que l'image du processus enfant a commencé son exécution) sont distinctes du statut de sortie 127.
