POSIX_TRACE_GETNEXT_EVENT(3P) Manuel du programmeur POSIX POSIX_TRACE_GETNEXT_EVENT(3P)

PROLOG

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consultez la page de manuel Linux correspondante pour les détails du comportement sous Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

posix_trace_getnext_event, posix_trace_timedgetnext_event, posix_trace_trygetnext_event — récupérer un événement de trace (TRACING)

SYNTAXE

#include <sys/types.h>
#include <trace.h>
int posix_trace_getnext_event(trace_id_t trid,
    struct posix_trace_event_info *restrict event,
    void *restrict data, size_t num_bytes,
    size_t *restrict data_len, int *restrict unavailable);
int posix_trace_timedgetnext_event(trace_id_t trid,
    struct posix_trace_event_info *restrict event,
    void *restrict data, size_t num_bytes,
    size_t *restrict data_len, int *restrict unavailable,
    const struct timespec *restrict abstime);
int posix_trace_trygetnext_event(trace_id_t trid,
    struct posix_trace_event_info *restrict event,
    void *restrict data, size_t num_bytes,
    size_t *restrict data_len, int *restrict unavailable);

DESCRIPTION

La fonction posix_trace_getnext_event() doit rapporter un événement de trace enregistré soit à partir d'un flux de trace actif sans journal, soit d'un flux de trace pré-enregistré identifié par l'argument trid. La fonction posix_trace_trygetnext_event() doit rapporter un événement de trace enregistré à partir d'un flux de trace actif sans journal identifié par l'argument trid.

Les informations de l'événement de trace associées à l'événement de trace enregistré doivent être copiées par la fonction dans la structure pointée par l'argument event et les données associées à l'événement de trace doivent être copiées dans le tampon pointé par l'argument data.

La fonction posix_trace_getnext_event() doit bloquer si l'argument trid identifie un flux de trace actif et qu'aucun événement de trace n'est actuellement prêt à être récupéré. Lors du retour, si un événement de trace enregistré a été rapporté, la variable pointée par l'argument unavailable doit être mise à zéro. Sinon, la variable pointée par l'argument unavailable doit être mise à une valeur différente de zéro.

La fonction posix_trace_timedgetnext_event() doit tenter d'obtenir un autre événement de trace à partir d'un flux de trace actif sans journal, comme dans la fonction posix_trace_getnext_event(). Cependant, si aucun événement de trace n'est disponible dans le flux de trace, l'attente implicite doit être terminée lorsque le délai spécifié par l'argument abstime expire, et la fonction doit retourner l'erreur [ETIMEDOUT].

Le délai d'attente doit expirer lorsque l'heure absolue spécifiée par abstime est passée, telle que mesurée par l'horloge sur laquelle les délais d'attente sont basés (c'est-à-dire lorsque la valeur de cette horloge est égale ou supérieure à abstime), ou si l'heure absolue spécifiée par abstime est déjà passée au moment de l'appel.

Le délai d'attente doit être basé sur l'horloge CLOCK_REALTIME. La résolution du délai d'attente doit être la résolution de l'horloge sur laquelle elle est basée. Le type de données timespec est défini dans l'en-tête <time.h>.

En aucun cas la fonction ne doit échouer avec un délai d'attente si un événement de trace est immédiatement disponible à partir du flux de trace. La validité de l'argument abstime ne doit pas être vérifiée si un événement de trace est immédiatement disponible à partir du flux de trace.

Le comportement de cette fonction pour un flux de trace pré-enregistré n'est pas spécifié.

La fonction posix_trace_trygetnext_event() ne doit pas bloquer. Cette fonction doit retourner une erreur si l'argument trid identifie un flux de trace pré-enregistré. Si un événement de trace enregistré a été rapporté, la variable pointée par l'argument unavailable doit être mise à zéro. Sinon, si aucun événement de trace n'a été rapporté, la variable pointée par l'argument unavailable doit être mise à une valeur différente de zéro.

L'argument num_bytes doit être la taille du tampon pointé par l'argument data. L'argument data_len rapporte à l'application la longueur en octets de l'enregistrement de données qui vient d'être transféré. Si num_bytes est supérieur ou égal à la taille des données associées à l'événement de trace pointé par l'argument event, toutes les données enregistrées doivent être transférées. Dans ce cas, le membre truncation-status de la structure de l'événement de trace doit être soit POSIX_TRACE_NOT_TRUNCATED, si les données de l'événement de trace ont été enregistrées sans troncature pendant le traçage, soit POSIX_TRACE_TRUNCATED_RECORD, si les données de l'événement de trace ont été tronquées lors de leur enregistrement. Si l'argument num_bytes est inférieur à la longueur des données de l'événement de trace enregistrées, les données transférées doivent être tronquées à une longueur de num_bytes, la valeur stockée dans la variable pointée par data_len doit être égale à num_bytes, et le membre truncation-status de l'argument de structure event doit être mis à POSIX_TRACE_TRUNCATED_READ (voir la structure posix_trace_event_info définie dans <trace.h>).

Le rapport d'un événement de trace doit être séquentiel en commençant par le plus ancien événement de trace enregistré. Les événements de trace doivent être rapportés dans l'ordre où ils ont été générés, jusqu'à une résolution temporelle définie par l'implémentation qui rend l'ordre des événements de trace survenant très proches les uns des autres inconnu. Une fois rapporté, un événement de trace ne peut pas être rapporté à nouveau à partir d'un flux de trace actif. Une fois qu'un événement de trace est rapporté à partir d'un flux de trace actif sans journal, le flux de trace doit rendre les ressources associées à cet événement de trace disponibles pour enregistrer les futurs événements de trace générés.

VALEUR RENVOYÉE

En cas de succès, ces fonctions doivent retourner une valeur de zéro. Sinon, elles doivent retourner le numéro d'erreur correspondant.

En cas de succès, ces fonctions stockent :

*
L'événement de trace enregistré dans l'objet pointé par event
*
Les informations de l'événement de trace associées à l'événement de trace enregistré dans l'objet pointé par data
*
La longueur de ces informations d'événement de trace dans l'objet pointé par data_len
*
La valeur zéro dans l'objet pointé par unavailable

ERREURS

Ces fonctions doivent échouer si :

EINVAL
L'argument identifiant le flux de trace trid est invalide.

Les fonctions posix_trace_getnext_event() et posix_trace_timedgetnext_event() doivent échouer si :

EINTR
L'opération a été interrompue par un signal, et donc l'appel n'a eu aucun effet.

La fonction posix_trace_trygetnext_event() doit échouer si :

EINVAL
L'argument identifiant le flux de trace trid ne correspond pas à un flux de trace actif.

La fonction posix_trace_timedgetnext_event() doit échouer si :

EINVAL
Aucun événement de trace n'est immédiatement disponible dans le flux de trace, et l'argument timeout est invalide.
ETIMEDOUT
Aucun événement de trace n'était disponible dans le flux de trace avant que le délai spécifié timeout n'expire.
