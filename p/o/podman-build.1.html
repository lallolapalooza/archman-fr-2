NOM

podman-build - Construire une image de conteneur à l'aide d'un Containerfile

SYNTAXE

podman build [options] [contexte]

podman image build [options] [contexte]

DESCRIPTION

podman build Construit une image en utilisant les instructions d'un ou plusieurs Containerfiles ou Dockerfiles et un répertoire de contexte de construction spécifié. Un Containerfile utilise syntaxiquement le même langage qu'un Dockerfile en interne. Pour ce document, un fichier désigné comme Containerfile peut être nommé soit 'Containerfile' soit 'Dockerfile' exclusivement. Tout fichier comportant une extension supplémentaire ne sera pas reconnu par podman build . à moins qu'un drapeau -f ne soit utilisé pour spécifier le fichier.

Le répertoire de contexte de construction peut être spécifié comme l'URL http(s) d'une archive, d'un dépôt git ou d'un Containerfile.

Lorsqu'il est appelé avec -f et un chemin vers un Containerfile, sans répertoire CONTEXT explicite, Podman utilise le répertoire parent du Containerfile comme son contexte de construction.

Les Containerfiles se terminant par un suffixe « .in » sont prétraités via CPP(1). Cela peut être utile pour décomposer les Containerfiles en plusieurs parties réutilisables qui peuvent être utilisées via la directive #include de CPP. Les Containerfiles se terminant par .in sont restreints aux lignes sans commentaire, sauf s'il s'agit de commandes CPP. Notez qu'un fichier Containerfile.in peut toujours être utilisé par d'autres outils lors de leur prétraitement manuel via cpp -E.

Lorsque l'URL est une archive, le contenu de l'URL est téléchargé dans un emplacement temporaire et extrait avant l'exécution.

Lorsque l'URL est un Containerfile, le Containerfile est téléchargé dans un emplacement temporaire.

Lorsqu'un dépôt Git est défini comme URL, le dépôt est cloné localement puis défini comme contexte. Une URL est traitée comme un dépôt Git si elle a un préfixe git:// ou une terminaison .git.

NOTE : podman build utilise du code provenant du projet Buildah pour construire des images de conteneur. Ce code Buildah crée des conteneurs Buildah pour les options RUN dans le stockage des conteneurs. Dans certaines situations, lorsque podman build plante ou que les utilisateurs tuent le processus podman build, ces conteneurs externes peuvent être laissés dans le stockage des conteneurs. Utilisez la commande podman ps --all --external pour voir ces conteneurs.

La commande podman buildx build est un alias de podman build. Toutes les fonctionnalités de buildx build ne sont pas disponibles dans Podman. L'option buildx build est fournie pour la compatibilité des scripts.

OPTIONS

--add-host=nom-hote[;nom-hote[;...]]:ip

Ajoute une correspondance hôte-IP personnalisée au fichier /etc/hosts du conteneur.

L'option prend un ou plusieurs noms d'hôte séparés par des points-virgules à mapper sur une seule adresse IPv4 ou IPv6, séparés par un deux-points. Elle peut également être utilisée pour écraser les adresses IP des noms d'hôte que Podman ajoute à /etc/hosts par défaut (voir également les options --name et --hostname). Cette option peut être spécifiée plusieurs fois pour ajouter des correspondances supplémentaires à /etc/hosts. Elle entre en conflit avec l'option --no-hosts et avec no_hosts=true dans containers.conf.

Au lieu d'une adresse IP, le drapeau spécial host-gateway peut être donné. Cela se résout en une adresse IP que le conteneur peut utiliser pour se connecter à l'hôte. L'adresse IP choisie dépend de votre configuration réseau, il n'y a donc aucune garantie que Podman puisse déterminer l'adresse host-gateway automatiquement, ce qui amènera Podman à échouer avec un message d'erreur. Vous pouvez écraser cette adresse IP en utilisant l'option host_containers_internal_ip dans containers.conf.

L'adresse host-gateway est également utilisée par Podman pour ajouter automatiquement les noms d'hôte host.containers.internal et host.docker.internal à /etc/hosts. Vous pouvez l'empêcher en donnant l'option --no-hosts ou en définissant host_containers_internal_ip="none" dans containers.conf. Si aucune adresse host-gateway n'a été configurée manuellement et que Podman ne parvient pas à déterminer l'adresse IP automatiquement, Podman omettra silencieusement d'ajouter ces noms d'hôtes internes à /etc/hosts. Si Podman s'exécute dans une machine virtuelle en utilisant podman machine (cela inclut les hôtes Mac et Windows), Podman omettra silencieusement d'ajouter les noms d'hôtes internes à /etc/hosts, sauf si une adresse IP a été configurée manuellement ; les noms d'hôtes internes sont résolus par le résolveur DNS gvproxy à la place.

Podman utilisera le fichier /etc/hosts de l'hôte comme base par défaut, c'est-à-dire que tout nom d'hôte présent dans ce fichier sera également présent dans le fichier /etc/hosts du conteneur. Un fichier de base différent peut être configuré en utilisant la configuration base_hosts_file dans containers.conf.

--all-platforms

Au lieu de construire pour un ensemble de plateformes spécifié à l'aide de l'option --platform, inspecter les images de base de la construction, et construire pour toutes les plateformes pour lesquelles elles sont toutes disponibles. Les étapes qui utilisent scratch comme point de départ ne peuvent pas être inspectées, donc au moins une étape non-scratch doit être présente pour que la détection fonctionne utilement.

--annotation=annotation=valeur

Ajoute une annotation d'image (par exemple, annotation=valeur) aux métadonnées de l'image. Peut être utilisé plusieurs fois.

Note : ces informations ne sont pas présentes dans les formats d'image Docker, elles sont donc ignorées lors de l'écriture d'images dans des formats Docker.

--arch=arch

Définit l'architecture de l'image à construire, ainsi que celle de l'image de base à tirer, si la construction en utilise une, à la valeur fournie au lieu d'utiliser l'architecture de l'hôte de construction. Sauf indication contraire, les recherches ultérieures de la même image dans le stockage local correspondent à cette architecture, indépendamment de l'hôte. (Exemples : arm, arm64, 386, amd64, ppc64le, s390x)

--authfile=chemin

Chemin du fichier d'authentification. Le défaut est ${XDG_RUNTIME_DIR}/containers/auth.json sous Linux, et $HOME/.config/containers/auth.json sous Windows/macOS. Le fichier est créé par podman login. Si l'état d'autorisation n'y est pas trouvé, $HOME/.docker/config.json est vérifié, ce qui est défini à l'aide de docker login.

Note : Il existe également une option pour écraser le chemin par défaut du fichier d'authentification en définissant la variable d'environnement REGISTRY_AUTH_FILE. Cela peut être fait avec export REGISTRY_AUTH_FILE=chemin.

--build-arg=arg=valeur

Spécifie un argument de construction et sa valeur, qui est interpolé dans les instructions lues à partir des Containerfiles de la même manière que les variables d'environnement, mais qui ne sont pas ajoutés à la liste des variables d'environnement dans la configuration de l'image résultante.

--build-arg-file=chemin

Spécifie un fichier contenant des lignes d'arguments de construction de la forme arg=valeur. Le nom de fichier suggéré est argfile.conf.

Les lignes de commentaire commençant par # sont ignorées, ainsi que les lignes vides. Toutes les autres doivent être au format arg=valeur passé à --build-arg.

Si plusieurs arguments sont fournis via les options --build-arg-file et --build-arg, les arguments de construction sont fusionnés sur tous les fichiers fournis et les arguments de la ligne de commande.

Tout fichier fourni dans une option --build-arg-file est lu avant les arguments fournis via l'option --build-arg.

Lorsqu'un nom d'argument donné est spécifié plusieurs fois, la dernière instance est celle qui est transmise aux constructions résultantes. Cela signifie que les valeurs de --build-arg remplacent toujours celles d'un --build-arg-file.

--build-context=nom=valeur

Spécifie un contexte de construction supplémentaire en utilisant son nom court et son emplacement. Les contextes de construction supplémentaires peuvent être référencés de la même manière que nous accédons à différentes étapes dans l'instruction COPY.

Les valeurs valides sont :

  • Répertoire local – par exemple --build-context project2=../chemin/vers/project2/src
  • URL HTTP vers une archive tar – par exemple --build-context src=<a href='https://example.org/releases/src.tar'>https://example.org/releases/src.tar'
  • Image de conteneur – spécifiée avec un préfixe container-image://, par exemple --build-context alpine=container-image://al

Du côté de Containerfile, référez-vous au contexte de build sur toutes les commandes qui acceptent le paramètre “from”. Voici à quoi cela pourrait ressembler :

FROM [nom]
COPY --from=[nom] ...
RUN --mount=from=[nom] …

La valeur de [nom] est mise en correspondance selon l'ordre de priorité suivant :

  • Contexte de build nommé défini avec --build-context [nom]=..
  • Étape définie avec AS [nom] dans Containerfile
  • Image [nom], locale ou dans un registre distant

--cache-from=image

Dépôt à utiliser comme source de cache potentielle. Lorsqu'il est spécifié, Buildah tente de rechercher des images de cache dans le dépôt spécifié et tente de tirer des images de cache au lieu d'exécuter réellement les étapes de build localement. Buildah tente uniquement de tirer des images précédemment mises en cache si elles sont considérées comme des succès de cache valides.

Utilisez l'option --cache-to pour peupler un dépôt distant avec du contenu de cache.

Exemple

# peupler un cache et aussi le consulter
buildah build -t test --layers --cache-to registry/myrepo/cache --cache-from registry/myrepo/cache .

Note : l'option --cache-from est ignorée à moins que --layers ne soit spécifié.

--cache-to=image

Définissez ce drapeau pour spécifier un dépôt distant qui est utilisé pour stocker des images de cache. Buildah tente de pousser une image de cache nouvellement construite vers le dépôt distant.

Note : utilisez l'option --cache-from afin d'utiliser le contenu du cache dans un dépôt distant.

Exemple

# peupler un cache et aussi le consulter
buildah build -t test --layers --cache-to registry/myrepo/cache --cache-from registry/myrepo/cache .

Note : l'option --cache-to est ignorée à moins que --layers ne soit spécifié.

--cache-ttl

Limite l'utilisation des images mises en cache pour ne considérer que les images dont les horodatages de création sont inférieurs à durée. Par exemple, si --cache-ttl=1h est spécifié, Buildah considère les images de cache intermédiaires qui sont créées moins d'une heure auparavant, et les images de cache intermédiaires en dehors de cette durée sont ignorées.

Note : définir --cache-ttl=0 manuellement équivaut à utiliser --no-cache dans l'implémentation car cela signifie que l'utilisateur ne souhaite pas utiliser de cache du tout.

--cap-add=CAP_xxx

Lors de l'exécution des instructions RUN, exécutez la commande spécifiée dans l'instruction avec la capacité spécifiée ajoutée à son ensemble de capacités. Certaines capacités sont accordées par défaut ; cette option peut être utilisée pour en ajouter davantage.

--cap-drop=CAP_xxx

Lors de l'exécution des instructions RUN, exécutez la commande spécifiée dans l'instruction avec la capacité spécifiée retirée de son ensemble de capacités. Les capacités CAP_CHOWN, CAP_DAC_OVERRIDE, CAP_FOWNER, CAP_FSETID, CAP_KILL, CAP_NET_BIND_SERVICE, CAP_SETFCAP, CAP_SETGID, CAP_SETPCAP et CAP_SETUID sont accordées par défaut ; cette option peut être utilisée pour les retirer.

Si une capacité est spécifiée pour les options --cap-add et --cap-drop, elle est supprimée, quel que soit l'ordre dans lequel les options ont été données.

--cert-dir=chemin

Utilisez les certificats situés dans chemin (*.crt, *.cert, *.key) pour vous connecter au registre. (Par défaut : /etc/containers/certs.d) Pour plus de détails, voir containers-certs.d(5). (Cette option n'est pas disponible avec le client Podman distant, y compris sur les machines Mac et Windows (hors WSL2))

--cgroup-parent=chemin

Chemin vers les cgroups sous lequel le cgroup pour le conteneur est créé. Si le chemin n'est pas absolu, le chemin est considéré comme relatif au chemin des cgroups du processus init. Les cgroups sont créés s'ils n'existent pas déjà.

--cgroupns=comment

Définit la configuration des espaces de noms cgroup lors du traitement des instructions RUN. La valeur configurée peut être "" (la chaîne vide) ou "private" pour indiquer qu'un nouvel espace de noms cgroup est créé, ou elle peut être "host" pour indiquer que l'espace de noms cgroup dans lequel buildah lui-même est exécuté est réutilisé.

--compat-volumes

Traitez les répertoires marqués à l'aide de l'instruction VOLUME (à la fois dans cette build et ceux hérités des images de base) de telle sorte que leur contenu ne puisse être modifié que par les instructions ADD et COPY. Toute modification apportée dans ces emplacements par les instructions RUN sera annulée. Avant l'introduction de cette option, ce comportement était par défaut, mais il est maintenant désactivé par défaut.

--compress

Cette option est ajoutée pour être alignée avec d'autres CLIs de conteneurs. Podman ne communique pas avec un démon ou un serveur distant. Ainsi, la compression des données avant leur envoi est sans importance pour Podman. (Cette option n'est pas disponible avec le client Podman distant, y compris sur les machines Mac et Windows (hors WSL2))

--cpp-flag=flags

Définissez des indicateurs supplémentaires à passer au préprocesseur C cpp(1). Les Containerfiles se terminant par le suffixe ".in" sont prétraités via cpp(1). Cette option peut être utilisée pour passer des indicateurs supplémentaires à cpp. Note : Vous pouvez également définir des CPPFLAGS par défaut en définissant la variable d'environnement BUILDAH_CPPFLAGS (par exemple, export BUILDAH_CPPFLAGS="-DDEBUG").

--cpu-period=limite

Définissez la période CPU pour le Completely Fair Scheduler (CFS), qui est une durée en microsecondes. Une fois le quota CPU du conteneur épuisé, il ne sera pas planifié pour s'exécuter avant la fin de la période en cours. La valeur par défaut est 100000 microsecondes.

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes rootless cgroups V1.

--cpu-quota=limite

Limite le quota CFS (Completely Fair Scheduler) du CPU.

Limite l'utilisation du CPU du conteneur. Par défaut, les conteneurs s'exécutent avec la totalité des ressources CPU. La limite est un nombre en microsecondes. Si un nombre est fourni, le conteneur est autorisé à utiliser ce temps CPU jusqu'à la fin de la période CPU (contrôlable via --cpu-period).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes rootless cgroups V1.

--cpu-shares, -c=parts

Parts CPU (poids relatif).

Par défaut, tous les conteneurs reçoivent la même proportion de cycles CPU. Cette proportion peut être modifiée en changeant le poids de part CPU du conteneur par rapport au poids combiné de tous les conteneurs en cours d'exécution. Le poids par défaut est 1024.

La proportion ne s'applique que lorsque des processus gourmands en CPU s'exécutent. Lorsque les tâches d'un conteneur sont inactives, d'autres conteneurs peuvent utiliser le temps CPU restant. La quantité réelle de temps CPU varie en fonction du nombre de conteneurs en cours d'exécution sur le système.

Par exemple, considérons trois conteneurs, l'un a une part de cpu de 1024 et les deux autres ont un réglage de part de cpu de 512. Lorsque les processus des trois conteneurs tentent d'utiliser 100 % du CPU, le premier conteneur reçoit 50 % du temps CPU total. Si un quatrième conteneur est ajouté avec une part de cpu de 1024, le premier conteneur n'obtient que 33 % du CPU. Les conteneurs restants reçoivent 16,5 %, 16,5 % et 33 % du CPU.

Sur un système multi-cœurs, les parts de temps CPU sont distribuées sur tous les cœurs CPU. Même si un conteneur est limité à moins de 100 % du temps CPU, il peut utiliser 100 % de chaque cœur CPU individuel.

Par exemple, considérons un système avec plus de trois cœurs. Si le conteneur C0 est démarré avec --cpu-shares=512 exécutant un processus, et un autre conteneur C1 avec --cpu-shares=1024 exécutant deux processus, cela peut entraîner la division suivante des parts CPU :

PID conteneur CPU Part CPU
100 C0 0 100% de CPU0
101 C1 1 100% de CPU1
102 C1 2 100% de CPU2

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes rootless cgroups V1.

--cpuset-cpus=nombre

CPU dans lesquels autoriser l'exécution. Peut être spécifié sous forme de liste séparée par des virgules (par exemple, 0,1), sous forme de plage (par exemple, 0-3), ou toute combinaison de ceux-ci (par exemple, 0-3,7,11-15).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes rootless cgroups V1.

--cpuset-mems=nœuds

Nœuds mémoire (MEMs) dans lesquels autoriser l'exécution (0-3, 0,1). Seulement effectif sur les systèmes NUMA.

--network=mode, --net

Définit la configuration des espaces de noms réseau lors du traitement des instructions RUN.

Les valeurs valides pour mode sont :

  • none : pas de réseau.
  • host : utilise la pile réseau de l'hôte Podman. Remarque : le mode host donne au conteneur un accès complet aux services système locaux tels que D-Bus et est donc considéré comme non sécurisé.
  • ns:chemin : chemin vers un espace de noms réseau à rejoindre.
  • private : crée un nouvel espace de noms pour le conteneur (par défaut)
  • <nom_réseau|ID> : rejoint le réseau avec le nom ou l'ID donné, par exemple, utilisez --network mynet pour rejoindre le réseau avec le nom mynet. Uniquement pris en charge pour les utilisateurs privilégiés.

  • mtu=MTU : spécifie l'MTU à utiliser pour ce réseau. (La valeur par défaut est 65520).
  • cidr=CIDR : spécifie la plage IP à utiliser pour ce réseau. (La valeur par défaut est 10.0.2.0/24).
  • enable_ipv6=true|false : active l'IPv6. La valeur par défaut est true. (Requis pour outbound_addr6).
  • outbound_addr=INTERFACE : spécifie l'interface sortante sur laquelle slirp se lie (trafic ipv4 uniquement).
  • outbound_addr=IPv4 : spécifie l'adresse ipv4 sortante sur laquelle slirp se lie.
  • outbound_addr6=INTERFACE : spécifie l'interface sortante sur laquelle slirp se lie
  • outbound_addr6=IPv6: Spécifiez l'adresse ipv6 sortante à laquelle slirp se lie.
•
pasta[:OPTIONS,...]: utilisez pasta(1) pour créer une pile réseau en mode utilisateur.
C'est le comportement par défaut pour les conteneurs sans root et uniquement supporté en mode sans root.
Par défaut, les adresses et routes IPv4 et IPv6, ainsi que le nom de l'interface de pod, sont copiés depuis l'hôte. Si le transfert de port n'est pas configuré, les ports sont transférés dynamiquement à mesure que les services sont liés de chaque côté (espace de noms d'initialisation ou espace de noms de conteneur). Le transfert de port préserve l'adresse IP source d'origine. Les options décrites dans pasta(1) peuvent être spécifiées comme arguments séparés par des virgules.
En termes d'options de pasta(1), --config-net est donné par défaut, afin de configurer le réseau lors du démarrage du conteneur, et --no-map-gw est également supposé par défaut, pour éviter l'accès direct du conteneur à l'hôte en utilisant l'adresse de passerelle. Ce dernier peut être remplacé en passant --map-gw dans les options spécifiques à pasta (malgré le fait que ce ne soit pas une option réelle de pasta(1)).
De plus, -t none et -u none sont passés pour désactiver le transfert de port automatique basé sur les ports liés. De même, -T none et -U none sont donnés pour désactiver la même fonctionnalité du conteneur vers l'hôte.
Quelques exemples :
  • pasta:--map-gw: Permet au conteneur d'atteindre directement l'hôte en utilisant l'adresse de passerelle.
  • pasta:--mtu,1500: Spécifiez une MTU de 1500 octets pour l'interface tap dans le conteneur.
  • pasta:--ipv4-only,-a,10.0.2.0,-n,24,-g,10.0.2.2,--dns-forward,10.0.2.3,-m,1500,--no-ndp,--no-dhcpv6,--no-dhcp, équivalent aux options par défaut de slirp4netns(1) : désactive l'IPv6, attribue 10.0.2.0/24 à l'interface tap0 dans le conteneur, avec la passerelle 10.0.2.2, active le réacheminement DNS joignable à 10.0.2.3, définit la MTU à 1500 octets, désactive NDP, DHCPv6 et DHCP.
  • pasta:-I,tap0,--ipv4-only,-a,10.0.2.0,-n,24,-g,10.0.2.2,--dns-forward,10.0.2.3,--no-ndp,--no-dhcpv6,--no-dhcp, équivalent aux options par défaut de slirp4netns(1) avec les substitutions de Podman : identique à ci-dessus, mais laisse la MTU à 65520 octets
  • pasta:-t,auto,-u,auto,-T,auto,-U,auto: active le transfert de port automatique basé sur les ports liés observés des deux côtés (hôte et conteneur)
  • pasta:-T,5201: active le transfert du port TCP 5201 du conteneur vers l'hôte, en utilisant l'interface de boucle locale au lieu de l'interface tap pour de meilleures performances

--output, -o=output-opts

Destination de sortie (format: type=local,dest=path)

L'option --output (ou -o) étend le comportement par défaut de construction d'une image de conteneur en permettant aux utilisateurs d'exporter le contenu de l'image sous forme de fichiers sur le système de fichiers local, ce qui peut être utile pour générer des binaires locaux, la génération de code, etc. (Cette option n'est pas disponible avec le client Podman distant, y compris les machines Mac et Windows (à l'exception de WSL2)).

La valeur de --output est une séquence de paires clé=valeur séparées par des virgules, définissant le type et les options de sortie.

Les clés supportées sont : - dest : chemin de destination pour la sortie exportée. La valeur valide est un chemin absolu ou relatif, - signifie la sortie standard. - type : définit le type de sortie à utiliser. Les valeurs valides sont documentées ci-dessous.

Les valeurs type valides sont : - local : écrire les fichiers de construction résultants dans un répertoire côté client. - tar : écrire les fichiers résultants sous forme d'une seule archive tar (.tar).

Si aucun type n'est spécifié, la valeur prend par défaut local. Alternativement, au lieu d'une séquence séparée par des virgules, la valeur de --output peut être simplement une destination (au format dest) (par exemple, --output some-path, --output -) où --output some-path est traité comme si type=local et --output - est traité comme si type=tar.

Définissez le os/arch de l'image construite (et de son image de base, lorsqu'elle est utilisée) à la valeur fournie au lieu d'utiliser le système d'exploitation et l'architecture actuels de l'hôte (par exemple linux/arm). Sauf substitution, les recherches ultérieures de la même image dans le stockage local correspondent à cette plateforme, quel que soit l'hôte.

Si --platform est défini, alors les valeurs des options --arch, --os et --variant sont remplacées.

L'option --platform peut être spécifiée plus d'une fois, ou un liste de valeurs séparées par des virgules lui être fournie comme argument. Lorsque plus d'une plateforme est spécifiée, l'option --manifest est utilisée à la place de l'option --tag.

Les paires Os/arch sont celles utilisées par le langage de programmation Go. Dans plusieurs cas, la valeur arch pour une plateforme diffère de celle produite par d'autres outils tels que la commande arch. Les combinaisons de noms de système d'exploitation et d'architecture valides sont listées comme valeurs pour $GOOS et $GOARCH sur https://golang.org/doc/install/source#environment, et peuvent également être trouvées en exécutant go tool dist list.

Bien que podman build soit heureux d'utiliser des images de base et de construire des images pour n'importe quelle plateforme existante, les instructions RUN ne peuvent pas réussir sans l'aide de l'émulation fournie par des paquets comme qemu-user-static.

--pull=policy

Politique de récupération d'image. La valeur par défaut est missing.

  • always: Récupérez toujours l'image et générez une erreur si la récupération échoue.
  • missing: Récupérez l'image uniquement lorsqu'elle n'existe pas dans le stockage local des conteneurs. Générez une erreur si aucune image n'est trouvée et que la récupération échoue.
  • never: Ne récupérez jamais l'image, mais utilisez celle du stockage local des conteneurs. Générez une erreur lorsqu'aucune image n'est trouvée.
  • newer: Récupérez si l'image dans le registre est plus récente que celle du stockage local des conteneurs. Une image est considérée comme plus récente lorsque les digests sont différents. La comparaison des horodatages est sujette à erreur. Les erreurs de récupération sont supprimées si une image locale a été trouvée.

--source-date-epoch=secondes

Définir l'horodatage de "création" pour l'image construite à ce nombre de secondes depuis l'époque (heure Unix 0, c'est-à-dire 00:00:00 UTC le 1er janvier 1970) (par défaut, utiliser la valeur définie dans la variable d'environnement SOURCE_DATE_EPOCH, ou l'heure actuelle si elle n'est pas définie).

L'horodatage de "création" est écrit dans la configuration et le manifeste de l'image lors de la validation de l'image, de sorte que l'exécution de la même construction à deux moments différents produira normalement des images avec des hachages sha256 différents, même si aucun autre changement n'a été apporté au Containerfile et au contexte de construction.

Lorsque cet indicateur est défini, un argument de construction SOURCE_DATE_EPOCH fournira sa valeur à une étape où il est déclaré.

Lorsque cet indicateur est défini, l'horodatage de "création" de la configuration de l'image est toujours défini à l'heure spécifiée, ce qui devrait permettre de construire des images identiques à des moments différents en utilisant le même ensemble d'entrées.

Lorsque cet indicateur est défini, la sortie écrite comme spécifié dans l'indicateur --output portera exactement l'horodatage spécifié.

h also définit son heure spécifiée sur le contenu des nouvelles couches.

Vous pouvez ajouter le suffixe :ro ou :rw à un volume pour le monter en lecture seule ou en lecture-écriture, respectivement. Par défaut, les volumes sont montés en lecture-écriture. Voir les exemples.

Changement de propriétaire des montages de volume

Par défaut, Podman ne modifie pas le propriétaire et le groupe des répertoires sources montés. Lors de l'exécution avec des espaces de noms utilisateur, l'UID et le GID à l'intérieur de l'espace de noms peuvent corres

pondre à un autre UID et GID sur l'hôte.

Le suffixe :U indique à Podman d'utiliser l'UID et le GID corrects de l'hôte basés sur l'UID et le GID dans l'espace de noms, pour changer récursivement le propriétaire et le groupe du volume source.

Attention à utiliser avec prudence car cela modifie le système de fichiers de l'hôte.

Labellisation des montages de volumes

Les systèmes de labellisation comme SELinux exigent que des labels corrects soient placés sur le contenu des volumes montés dans un conteneur. Sans label, le système de sécurité peut empêcher les processus s'exécutant dans le conteneur d'utiliser le contenu. Par défaut, Podman ne modifie pas les labels définis par le système d'exploitation.

Pour changer un label dans le contexte du conteneur, ajoutez l'un de ces deux suffixes :z ou :Z au montage du volume. Ces suffixes indiquent à Podman de relabéliser les objets de fichiers sur les volumes partagés. L'option z indique à Podman que deux conteneurs partagent le contenu du volume. Par conséquent, Podman labellise le contenu avec un label de contenu partagé. Les labels de volumes partagés permettent à tous les conteneurs de lire/écrire le contenu. L'option Z indique à Podman de labelliser le contenu avec un label privé non partagé. Seul le conteneur actuel peut utiliser un volume privé.

Remarque : Ne relabélisez pas les fichiers et répertoires systèmes. Relabéliser le contenu système peut entraîner l'échec d'autres services confinés sur la machine hôte. Pour ces types de conteneurs, il est recommandé de désactiver la séparation SELinux. L'option --security-opt label=disable désactive la séparation SELinux pour le conteneur. Par exemple, si un utilisateur souhaite monter son répertoire personnel entier dans les conteneurs de build, il doit désactiver la séparation SELinux.

$ podman build --security-opt label=disable -v $HOME:/home/user .

Montages de volumes en superposition

Le drapeau :O indique à Podman de monter le répertoire de l'hôte comme un stockage temporaire en utilisant le système de fichiers Overlay. Les conteneurs de commande RUN sont autorisés à modifier le contenu dans le point de montage et celui-ci est stocké dans le stockage du conteneur dans un répertoire séparé. En termes de Overlay FS, le répertoire source est le niveau inférieur (lower) et le répertoire de stockage du conteneur est le niveau supérieur (upper). Les modifications du point de montage sont détruites lorsque la commande RUN se termine, de manière similaire à un point de montage tmpfs.

Toute exécution ultérieure des commandes RUN verra le contenu original du répertoire source, toute modification des commandes RUN précédentes n'existera plus.

Un cas d'utilisation du montage overlay est le partage du cache de paquets de l'hôte dans le conteneur pour accélérer les builds.

Remarque :

  • Les montages Overlay ne sont actuellement pas pris en charge en mode sans root.
  • Le drapeau O n'est pas autorisé à être spécifié avec les drapeaux Z ou z. Le contenu monté dans le conteneur est étiqueté avec le label privé. Sur les systèmes SELinux, les labels du répertoire source doivent être lisibles par le label du conteneur. Sinon, la séparation des conteneurs SELinux doit être désactivée pour que le conteneur fonctionne.
  • La modification du volume de répertoire monté dans le conteneur avec un montage overlay peut entraîner des échecs inattendus. Ne modifiez pas le répertoire tant que le conteneur n'a pas fini de s'exécuter.

Par défaut, les volumes montés en bind sont privés. Cela signifie que tout montage effectué à l'intérieur des conteneurs n'est pas visible sur l'hôte et vice versa. Ce comportement peut être modifié en spécifiant une propriété de propagation de montage de volume.

Lorsque la politique de propagation de montage est définie sur shared, tout montage effectué à l'intérieur du conteneur sur ce volume est visible par l'hôte et le conteneur. Lorsque la politique de propagation de montage est définie sur slave, une propagation de montage unidirectionnelle est activée et tout montage effectué sur l'hôte pour ce volume n'est visible qu'à l'intérieur du conteneur. Pour contrôler la propriété de propagation de montage d'un volume, utilisez le drapeau de propagation :[r]shared, :[r]slave ou :[r]private. Pour que la propagation de montage fonctionne sur le point de montage source (point de montage où le répertoire source est monté), celui-ci doit avoir les bonnes propriétés de propagation. Pour les volumes partagés, le point de montage source doit être partagé. Et pour les volumes esclaves, le montage source doit être soit partagé, soit esclave. [1] ⟨#Footnote1⟩

Utilisez df <source-dir> pour déterminer le montage source, puis utilisez findmnt -o TARGET,PROPAGATION <source-mount-dir> pour déterminer les propriétés de propagation du montage source. Si l'utilitaire findmnt n'est pas disponible, le point de montage source peut être déterminé en examinant l'entrée de montage dans /proc/self/mountinfo. Regardez les champs optionnels et voyez si des propriétés de propagation sont spécifiées. shared:X signifie que le montage est partagé, master:X signifie que le montage est esclave et si rien n'est présent, cela signifie que le montage est privé. [1] ⟨#Footnote1⟩

Pour changer les propriétés de propagation d'un point de montage, utilisez la commande mount. Par exemple, pour monter en bind le répertoire source /foo, exécutez mount --bind /foo /foo et mount --make-private --make-shared /foo. Cela transforme /foo en un point de montage partagé. Les propriétés de propagation du montage source peuvent être modifiées directement. Par exemple, si / est le montage source pour /foo, utilisez alors mount --make-shared / pour transformer / en un montage partagé.

EXEMPLES

Construire une image en utilisant des Containerfiles locaux

Construire une image en utilisant un Containerfile avec le contenu du répertoire courant :

$ podman build .

Construire une image en utilisant un Containerfile spécifié avec le contenu du répertoire courant :

$ podman build -f Containerfile.simple .

Construire une image en utilisant un Containerfile depuis stdin avec le contenu du répertoire courant :

$ cat $HOME/Containerfile | podman build -f - .

Construire une image en utilisant plusieurs Containerfiles avec le contenu du répertoire courant :

$ podman build -f Containerfile.simple -f Containerfile.notsosimple .

Construire une image en utilisant un Containerfile spécifié avec le contenu du répertoire $HOME. Notez que cpp est appliqué à Containerfile.in avant son traitement en tant que Containerfile :

$ podman build -f Containerfile.in $HOME

Construire une image avec le tag spécifié, un Containerfile et le contenu du répertoire courant :

$ podman build -t imageName .

Construire une image en ignorant la vérification des registres pour les images tirées via le Containerfile :

$ podman build --tls-verify=false -t imageName .

Construire une image avec le format de journalisation spécifié :

$ podman build --runtime-flag log-format=json .

Construire une image en utilisant le mode de débogage pour la journalisation :

$ podman build --runtime-flag debug .

Construire une image en utilisant les attributs de registre spécifiés lors du tirage des images du Containerfile sélectionné :

$ podman build --authfile /tmp/auths/myauths.json --cert-dir $HOME/auth --tls-verify=true --creds=username:password -t imageName -f Containerfile.simple .

Construire une image en utilisant les contrôles de ressources spécifiés lors de l'exécution des conteneurs pendant la construction :

$ podman build --memory 40m --cpu-period 10000 --cpu-quota 50000 --ulimit nofile=1024:1028 -t imageName .

Construire une image en utilisant les labels SELinux et la configuration cgroup spécifiés pour les conteneurs en cours d'exécution pendant la construction :

$ podman build --security-opt label=level:s0:c100,c200 --cgroup-parent /path/to/cgroup/parent -t imageName .

Construire une image avec un volume monté en lecture seule et relabélisé SELinux depuis l'hôte dans les conteneurs en cours d'exécution pendant la construction :

$ podman build --volume /home/test:/myvol:ro,Z -t imageName .

Construire une image avec un volume overlay monté depuis l'hôte dans les conteneurs en cours d'exécution pendant la construction :

$ podman build -v /var/lib/yum:/var/lib/yum:O -t imageName .

Construire une image en utilisant des couches, puis en supprimant les conteneurs intermédiaires même si la construction échoue.

$ podman build --layers --force-rm -t imageName .

Construire une image en ignorant le cache et sans supprimer les conteneurs intermédiaires même si la construction réussit :

$ podman build --no-cache --rm=false -t imageName .

Construire une image en utilisant le réseau spécifié lors de l'exécution des conteneurs pendant la construction :

$ podman build --network mynet .

Construire une image en utilisant un secret stocké dans une variable d'environnement ou un fichier nommé mysecret à utiliser avec l'instruction RUN --mount=type=secret,id=mysecret cat /run/secrets/mysecret :

$ podman build --secret=id=mysecret .

Construire une image en utilisant un secret stocké dans une variable d'environnement nommée MYSECRET à utiliser avec l'instruction RUN --mount=type=secret,id=mysecret cat /run/secrets/mysecret :

$ podman build --secret=id=mysecret,env=MYSECRET .
$ podman build --secret=id=mysecret,src=MYSECRET,type=env .

Construire une image en utilisant un secret stocké dans un fichier nommé .mysecret à utiliser avec l'instruction RUN --mount=type=secret,id=mysecret cat /run/secrets/mysecret :

$ podman build --secret=id=mysecret,src=.mysecret .
$ podman build --secret=id=mysecret,src=.mysecret,type=file .

Construction dune image multi-architecture en utilisant l'option --manifest (nécessite un logiciel d'émulation)

Construire une image en utilisant les architectures spécifiées et les relier à un seul manifeste en cas de succès :

$ podman build --arch arm --manifest myimage /tmp/mysrc
$ podman build --arch amd64 --manifest myimage /tmp/mysrc
$ podman build --arch s390x --manifest myimage /tmp/mysrc

Construire de manière similaire en utilisant une seule commande

$ podman build --platform linux/s390x,linux/ppc64le,linux/amd64 --manifest myimage /tmp/mysrc

Construire une image en utilisant plusieurs architectures spécifiées et les relier à un seul manifeste en cas de succès :

$ podman build --platform linux/arm64 --platform linux/amd64 --manifest myimage /tmp/mysrc

Construction dune image en utilisant une URL, un dépôt Git, ou une archive

Le contexte de build peut être spécifié comme une URL vers un Containerfile, un dépôt Git, ou une URL vers une archive. Si l'URL est un Containerfile, il est téléchargé dans un emplacement temporaire et utilisé comme contexte. Lorsqu'un dépôt Git est défini comme URL, le dépôt est cloné localement dans un emplacement temporaire puis utilisé comme contexte. Enfin, si l'URL est une archive, elle est téléchargée dans un emplacement temporaire et extraite avant d'être utilisée comme contexte.

Construction dune image en utilisant une URL vers un Containerfile

'permalink' href='#Building_an_image_using_a_URL_to_a_Containerfile'>Construction d'une image à partir d'une URL vers un Containerfile

Construire une image à partir d'un Containerfile téléchargé dans un emplacement temporaire utilisé comme contexte de construction :

$ podman build https://10.10.10.1/podman/Containerfile

Construction d'une image à partir d'un dépôt Git

Podman clone le dépôt GitHub spécifié vers un emplacement temporaire et l'utilise comme contexte. Le Containerfile à la racine du dépôt est utilisé, et cela ne fonctionne que si le dépôt GitHub est un dépôt dédié.

Construire une image à partir du dépôt git spécifié téléchargé dans un emplacement temporaire utilisé comme contexte de construction :

$ podman build -t hello  https://github.com/containers/PodmanHello.git
$ podman run hello

Note : GitHub ne prend pas en charge l'utilisation de git:// pour effectuer une opération de clone en raison des changements récents dans leurs directives de sécurité (https://github.blog/2021-09-01-improving-git-protocol-security-github/). Utilisez une URL https:// si le dépôt source est hébergé sur GitHub.

Construction d'une image à partir d'une URL vers une archive

Podman récupère le fichier archive, le décompresse et utilise son contenu comme contexte de construction. Le Containerfile à la racine de l'archive et le reste de l'archive sont utilisés comme contexte de la construction. Le passage de l'option -f PATH/Containerfile indique également au système de rechercher ce fichier dans le contenu de l'archive.

$ podman build -f dev/Containerfile https://10.10.10.1/podman/context.tar.gz

Note : les formats de compression pris en charge sont 'xz', 'bzip2', 'gzip' et 'identity' (pas de compression).

Fichiers

.containerignore/.dockerignore

Si le fichier .containerignore ou .dockerignore existe dans le répertoire de contexte, podman build lit son contenu. Utilisez l'option --ignorefile pour remplacer l'emplacement du chemin .containerignore. Podman utilise le contenu pour exclure les fichiers et répertoires du répertoire de contexte, lors de l'exécution des directives COPY et ADD dans le Containerfile/Dockerfile.

Les fichiers .containerignore et .dockerignore utilisent la même syntaxe ; si les deux sont dans le répertoire de contexte, podman build utilise uniquement .containerignore.

Les utilisateurs peuvent spécifier une série de globes Unix shell dans un fichier .containerignore pour identifier les fichiers/répertoires à exclure.

Podman prend en charge la chaîne de caractères joker spéciale ** qui correspond à n'importe quel nombre de répertoires (y compris zéro). Par exemple, */.go exclut tous les fichiers se terminant par .go trouvés dans tous les répertoires.

Exemple de fichier .containerignore :

# exclude this content for image
*/*.c
**/output*
src

*/*.c Exclut les fichiers et répertoires dont le nom se termine par .c dans n'importe quel sous-répertoire de premier niveau. Par exemple, le fichier source include/rootless.c.

**/output* Exclut les fichiers et répertoires commençant par output de n'importe quel répertoire.

src Exclut les fichiers nommés src et le répertoire src ainsi que tout leur contenu.

Les lignes commençant par ! (point d'exclamation) peuvent être utilisées pour faire des exceptions aux exclusions. Voici un exemple de fichier .containerignore qui utilise ce mécanisme :

*.doc
!Help.doc

Exclure tous les fichiers doc sauf Help.doc de l'image.

Cette fonctionnalité est compatible avec la gestion des fichiers .containerignore décrite ici : containerignore(5)

registries.conf (/etc/containers/registries.conf)

registries.conf est le fichier de configuration qui spécifie quels registres de conteneurs sont consultés lors de la complétion des noms d'images qui n'incluent pas de partie registre ou domaine. Voir containers-registries.conf(5)

Dépannage

lastlog fichier épars

L'utilisation de la commande useradd dans un Containerfile avec un UID/GID important crée un grand fichier épars /var/log/lastlog. Cela peut faire que la construction se bloque indéfiniment. Le langage Go ne prend pas correctement en charge les fichiers épars, ce qui peut entraîner la création de fichiers très volumineux dans l'image du conteneur.

Lorsque vous utilisez la commande useradd dans le script de construction, passez l'option --no-log-init ou -l à la commande useradd. Cette option indique à useradd d'arrêter la création du fichier lastlog.
