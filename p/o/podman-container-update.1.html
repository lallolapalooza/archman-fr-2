podman-update(1) Manuel des commandes générales podman-update(1)

NOM

podman-update - Met à jour la configuration d'un conteneur donné

SYNTAXE

podman update [options] conteneur

podman container update [options] conteneur

DESCRIPTION

Met à jour la configuration d'un conteneur existant, permettant de modifier les limites de ressources et les vérifications de santé.

OPTIONS

--blkio-weight=poids

Poids relatif des E/S de bloc. Le poids est une valeur comprise entre 10 et 1000.

Cette option n'est pas supportée sur les systèmes rootless avec cgroups V1.

--blkio-weight-device=périphérique:poids

Poids relatif des E/S de bloc pour un périphérique.

--cpu-period=limite

Définit la période CPU pour le Completely Fair Scheduler (CFS), qui est une durée en microsecondes. Une fois le quota CPU du conteneur épuisé, il ne sera pas planifié pour s'exécuter avant la fin de la période en cours. La valeur par défaut est de 100000 microsecondes.

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non-root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas supportée sur les systèmes rootless avec cgroups V1.

--cpu-quota=limite

Limite le quota CPU Completely Fair Scheduler (CFS).

Limite l'utilisation du CPU par le conteneur. Par défaut, les conteneurs s'exécutent avec la totalité des ressources CPU. La limite est un nombre en microsecondes. Si un nombre est fourni, le conteneur est autorisé à utiliser ce temps CPU jusqu'à la fin de la période CPU (contrôlable via --cpu-period).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non-root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas supportée sur les systèmes rootless avec cgroups V1.

--cpu-rt-period=microsecondes

Limite la période temps réel CPU en microsecondes.

Limite l'utilisation du CPU en temps réel du conteneur. Cette option indique au noyau de restreindre l'utilisation du CPU en temps réel du conteneur à la période spécifiée.

Cette option n'est supportée que sur les systèmes rootful avec cgroups V1.

--cpu-rt-runtime=microsecondes

Limite le temps d'exécution temps réel CPU en microsecondes.

Limite l'utilisation du CPU en temps réel du conteneur. Cette option indique au noyau de limiter le temps que les tâches en temps réel peuvent consommer dans une période CPU donnée. Ex : une période de 1 000 000 µs et un temps d'exécution de 950 000 µs signifie que ce conteneur peut consommer 95% du CPU disponible et laisser les 5% restants aux tâches de priorité normale.

La somme de tous les temps d'exécution entre conteneurs ne peut pas dépasser la quantité allouée au cgroup parent.

Cette option n'est supportée que sur les systèmes rootful avec cgroups V1.

--cpu-shares, -c=parts

Parts CPU (poids relatif).

Par défaut, tous les conteneurs reçoivent la même proportion de cycles CPU. Cette proportion peut être modifiée en changeant le poids des parts CPU du conteneur par rapport au poids combiné de tous les conteneurs en cours d'exécution. Le poids par défaut est de 1024.

La proportion ne s'applique que lorsque des processus intensifs en CPU sont en cours d'exécution. Lorsque les tâches d'un conteneur sont inactives, les autres conteneurs peuvent utiliser le temps CPU restant. La quantité réelle de temps CPU varie en fonction du nombre de conteneurs en cours d'exécution sur le système.

Par exemple, considérez trois conteneurs, un avec une part CPU de 1024 et deux autres avec un réglage de part CPU de 512. Lorsque les processus de ces trois conteneurs tentent d'utiliser 100% du CPU, le premier conteneur reçoit 50% du temps CPU total. Si un quatrième conteneur est ajouté avec une part CPU de 1024, le premier conteneur ne reçoit plus que 33% du CPU. Les autres conteneurs reçoivent respectivement 16,5%, 16,5% et 33% du CPU.

Sur un système multi-cœurs, les parts de temps CPU sont distribuées sur tous les cœurs CPU. Même si un conteneur est limité à moins de 100% du temps CPU, il peut utiliser 100% de chaque cœur CPU individuel.

Par exemple, considérez un système avec plus de trois cœurs. Si le conteneur C0 est démarré avec --cpu-shares=512 et exécute un processus, et un autre conteneur C1 avec --cpu-shares=1024 exécutant deux processus, cela peut entraîner la répartition suivante des parts CPU :

PID conteneur CPU Part CPU
100 C0 0 100% du CPU0
101 C1 1 100% du CPU1
102 C1 2 100% du CPU2

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non-root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas supportée sur les systèmes rootless avec cgroups V1.

--cpus=nombre

Nombre de CPUs. La valeur par défaut est 0.0, ce qui signifie aucune limite. Ceci est un raccourci pour --cpu-period et --cpu-quota, par conséquent l'option ne peut pas être spécifiée avec --cpu-period ou --cpu-quota.

Sur certains systèmes, la modification des limites CPU peut ne pas être autorisée pour les utilisateurs non-root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas supportée sur les systèmes rootless avec cgroups V1.

--cpuset-cpus=nombre

CPUs dans lesquels autoriser l'exécution. Peut être spécifié comme une liste séparée par des virgules (par ex. 0,1), comme une plage (par ex. 0-3), ou toute combinaison de ceux-ci (par ex. 0-3,7,11-15).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non-root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas supportée sur les systèmes rootless avec cgroups V1.

--cpuset-mems=nœuds

Nœuds mémoire (MEMs) dans lesquels autoriser l'exécution (0-3, 0,1). Seulement effectif sur les systèmes NUMA.

S'il y a quatre nœuds mémoire sur le système (0-3), utiliser --cpuset-mems=0,1 alors les processus du conteneur n'utiliseront la mémoire que des deux premiers nœuds mémoire.

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non-root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas supportée sur les systèmes rootless avec cgroups V1.

--device-read-bps=chemin:débit

Limite le débit de lecture (en octets par seconde) d'un périphérique (par ex. --device-read-bps=/dev/sda:1mb).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non-root. Pour plus de détails, voir https://github.com/containers/podm

--device-read-bps=path:rate

Limiter le taux de lecture (en opérations d'E/S par seconde) à partir d'un périphérique (par exemple, --device-read-bps=/dev/sda:1mb).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes sans root cgroups V1.

--device-read-iops=path:rate

Limiter le taux de lecture (en opérations d'E/S par seconde) à partir d'un périphérique (par exemple, --device-read-iops=/dev/sda:1000).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes sans root cgroups V1.

--device-write-bps=path:rate

Limiter le taux d'écriture (en octets par seconde) vers un périphérique (par exemple, --device-write-bps=/dev/sda:1mb).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes sans root cgroups V1.

--device-write-iops=path:rate

Limiter le taux d'écriture (en opérations d'E/S par seconde) vers un périphérique (par exemple, --device-write-iops=/dev/sda:1000).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes sans root cgroups V1.

--env, -e=env

Ajouter une valeur (par exemple, env=valeur) au conteneur. Peut être utilisé plusieurs fois. Si la valeur existe déjà dans le conteneur, elle est remplacée. Pour supprimer une variable d'environnement du conteneur, utilisez l'option --unsetenv.

Notez que les mises à jour d'environnement n'affectent le processus principal du conteneur qu'après le prochain démarrage.

--health-cmd="commande" | '["commande", arg1 , ...]'

Définir ou modifier une commande de vérification de santé pour un conteneur. La commande est une commande à exécuter à l'intérieur du conteneur qui détermine la santé du conteneur. La commande est requise pour que les autres options de vérification de santé soient appliquées. Une valeur de none désactive les vérifications de santé existantes.

Plusieurs options peuvent être passées sous forme de tableau JSON ; sinon, la commande est interprétée comme un argument pour /bin/sh -c.

Note : Les valeurs par défaut sont utilisées même si la vérification de santé est configurée dans l'image.

--health-interval=intervalle

Définir un intervalle pour les vérifications de santé. Un intervalle de disable ne configure aucun minuteur automatique. La valeur par défaut est 30s.

Note : Ce paramètre remplacera la configuration de vérification de santé liée à l'image.

La modification de ce paramètre réinitialise le minuteur.

--health-log-destination=chemin_répertoire

Définir la destination du journal de la vérification de santé. Chemin du répertoire, local ou events_logger (utilisation locale du fichier d'état du conteneur) (Défaut : local)

  • local : (par défaut) Les journaux de vérification de santé sont stockés dans les conteneurs overlay. (Par exemple : $runroot/healthcheck.log)
  • directory : crée un fichier journal nommé <ID_conteneur>-healthcheck.log avec les journaux de vérification de santé dans le répertoire spécifié.
  • events_logger : le journal sera écrit avec le mécanisme de journalisation défini par events_logger. Il sauvegarde également le journal dans un répertoire par défaut, pour les performances sur un système avec un grand nombre de journaux.

Attention : La modification de ce paramètre peut entraîner la perte des journaux précédents.

--health-max-log-count=nombre de journaux stockés

Définir le nombre maximum de tentatives dans le fichier journal de vérification de santé ('0' signifie un nombre infini de tentatives dans le fichier journal) (Défaut : 5 tentatives)

--health-max-log-size=taille des journaux stockés

Définir la longueur maximale en caractères du journal de vérification de santé stocké. ("0" signifie une longueur de journal infinie) (Défaut : 500 caractères)

--health-on-failure=action

Action à entreprendre une fois que le conteneur passe à un état non sain. La valeur par défaut est none.

  • none : Aucune action.
  • kill : Arrêter le conteneur.
  • restart : Redémarrer le conteneur. Ne combinez pas l'action restart avec le drapeau --restart. Lors de l'exécution dans une unité systemd, envisagez d'utiliser plutôt l'action kill ou stop pour utiliser la politique de redémarrage de systemd.
  • stop : Arrêter le conteneur.

--health-retries=tentatives

Le nombre de tentatives autorisées avant qu'une vérification de santé ne soit considérée comme non saine. La valeur par défaut est 3.

Note : Ce paramètre peut remplacer la configuration de vérification de santé de l'image.

--health-start-period=période

Le temps d'initialisation nécessaire au démarrage d'un conteneur. La valeur peut être exprimée dans un format de temps tel que 2m3s. La valeur par défaut est 0s.

Note : La commande de vérification de santé est exécutée dès que le conteneur est démarré. Si la vérification de santé réussit, l'état de santé du conteneur sera mis à jour à healthy. Cependant, si la vérification de santé échoue, l'état de santé restera starting jusqu'à ce que la vérification de santé réussisse ou que la période de --health-start-period soit écoulée. Si la commande de vérification de santé échoue après la fin de la période --health-start-period, l'état de santé sera mis à jour à unhealthy. La commande de vérification de santé est exécutée périodiquement en fonction de la valeur de --health-interval.

Note : Ce paramètre remplacera la configuration de vérification de santé liée à l'image.

--health-startup-cmd="commande" | '["commande", arg1 , ...]'

Définir une commande de vérification de santé de démarrage pour un conteneur. Cette commande est exécutée à l'intérieur du conteneur et est utilisée pour contrôler la vérification de santé régulière. Lorsque la commande de démarrage réussit, la vérification de santé régulière commence et la vérification de santé de démarrage cesse. Facultativement, si la commande échoue pendant un nombre défini de tentatives, le conteneur est redémarré. Une vérification de santé de démarrage peut être utilisée pour s'assurer que les conteneurs avec une longue période de démarrage ne sont pas marqués comme non sains tant qu'ils ne sont pas complètement démarrés. Les vérifications de santé de démarrage ne peuvent être utilisées que lorsqu'une vérification de santé régulière (depuis l'image du conteneur ou l'option --health-cmd) est également définie.

--health-startup-interval=intervalle

Définir un intervalle pour la vérification de santé de démarrage. Un intervalle de disable ne configure aucun minuteur automatique. La valeur par défaut est 30s.

La modification de ce paramètre réinitialise le minuteur, en fonction de l'état du conteneur.

--health-startup-retries=tentatives

Le nombre de tentatives autorisées avant que la vérification de santé de démarrage ne redémarre le conteneur. S'il est réglé sur 0, le conteneur n'est jamais redémarré. La valeur par défaut est 0.

--health-startup-success=tentatives

Le nombre d'exécutions réussies requis avant que la vérification de santé de démarrage ne réussisse et que la vérification de santé régulière ne commence. Une valeur de 0 signifie que toute réussite lance la vérification de santé régulière. La valeur par défaut est 0.

--health-startup-timeout=délai

Le temps maximum dont dispose une commande de vérification de santé de démarrage pour se terminer avant d'être marquée comme échouée. La valeur peut être exprimée dans un format de temps tel que 2m3s. La valeur par défaut est 30s.

--health-timeout=délai

Le temps maximum autorisé pour terminer la vérification de santé avant qu'un intervalle ne soit considéré comme échoué. Comme pour start-period, la valeur peut être exprimée dans un format de temps tel que 1m22s. La valeur par défaut est 30s.

Note : Un délai marque la vérification de santé comme échouée. Si la commande de vérification de santé elle-même s'exécute plus longtemps que le délai spécifié, elle recevra un signal SIGKILL.

Note : Ce paramètre remplacera la configuration de vérification de santé liée à l'image.

--latest, -l

Au lieu de fournir le nom ou l'ID du conteneur, utilisez le dernier conteneur créé. Note : le dernier conteneur démarré peut provenir d'autres utilisateurs de Podman sur la machine hôte. (Cette option n'est pas disponible avec le client Podman distant, y compris les machines Mac et Windows (à l'exception de WSL2))

--memory, -m=nombre[unité]

Limite de mémoire. Une unité peut être b (octets), k (kilo-octets), m (méga-octets) ou g (giga-octets).

Permet de contraindre la mémoire disponible pour un conteneur. Si l'hôte prend en charge la mémoire swap, le réglage de mémoire -m peut être supérieur à la RAM physique. Si une limite de 0 est spécifiée (sans utiliser -m), la mémoire du conteneur n'est pas limitée. La limite réelle peut être arrondie à un multiple de la taille de page du système d'exploitation (la valeur est très grande, des millions de trillions).

Cette option n'est pas prise en charge sur les systèmes sans root cgroups V1.

--memory-reservation=nombre[unité]

Soft limit de mémoire. Une unité peut être b (octets), k (kilo-octets), m (méga-octets) ou g (giga-octets).

Après avoir défini la réservation de mémoire, lorsque le système détecte une contention de mémoire ou une faible mémoire, les conteneurs sont forcés de limiter leur consommation à leur réservation. Réglez donc toujours la valeur en dessous de --memory, sinon la limite dure prend le dessus. Par défaut, la réservation de mémoire est identique à la limite de mémoire.

Pp">Cette option n'est pas prise en charge sur les systèmes sans privilèges cgroups V1.

--memory-swap=nombre[unité]

Une valeur limite égale à la mémoire plus le swap. Une unité peut être b (octets), k (kilo-octets), m (méga-octets), ou g (giga-octets).

Doit être utilisé avec le drapeau -m (--memory). La valeur de l'argument doit être supérieure à celle de
-m (--memory). Par défaut, il est défini au double de la valeur de --memory.

Définissez nombre sur -1 pour activer le swap illimité.

Cette option n'est pas prise en charge sur les systèmes sans privilèges cgroups V1.

--memory-swappiness=nombre

Ajuster le comportement de swappiness de la mémoire d'un conteneur. Accepte un entier compris entre 0 et 100.

Ce drapeau n'est pris en charge que sur les systèmes avec privilèges cgroups V1.

--no-healthcheck

Désactiver tous les healthchecks définis pour le conteneur.

--pids-limit=limite

Ajuster la limite de pids du conteneur. Définir sur -1 pour avoir des pids illimités pour le conteneur. La valeur par défaut est 2048 sur les systèmes qui prennent en charge le contrôleur cgroup "pids".

--restart=politique

Politique de redémarrage à suivre lorsque les conteneurs se terminent. La politique de redémarrage ne prend pas effet si un conteneur est arrêté via les commandes podman kill ou podman stop.

Les valeurs valides de politique sont :

  • no : Ne pas redémarrer les conteneurs à la sortie
  • never : Synonyme de no ; ne pas redémarrer les conteneurs à la sortie
  • on-failure[:max_retries] : Redémarrer les conteneurs lorsqu'ils se terminent avec un code de sortie non nul, en réessayant indéfiniment ou jusqu'à ce que le nombre max_retries optionnel soit atteint
  • always : Redémarrer les conteneurs lorsqu'ils se terminent, quel que soit leur statut, en réessayant indéfiniment
  • unless-stopped : Identique à always

Podman fournit un fichier d'unité systemd, podman-restart.service, qui redémarre les conteneurs après un redémarrage du système.

Lors de l'exécution de conteneurs dans des services systemd, utilisez la fonctionnalité de redémarrage fournie par systemd. Autrement dit, n'utilisez pas cette option dans une unité de conteneur, mais définissez la directive systemd Restart= dans la section [Service]. Voir podman-systemd.unit(5) et systemd.service(5).

--unsetenv=env

Supprimer des variables d'environnement du conteneur.

Notez que les mises à jour de l'environnement n'affectent le processus principal du conteneur qu'après le prochain démarrage.

EXEMPLES

Mettre à jour un conteneur avec un nouveau quota et une nouvelle période CPU :

podman update --cpus=0.5 ctrID

Mettre à jour le dernier conteneur avec une nouvelle valeur CPU :

podman update --latest --cpus=1

Mettre à jour un conteneur avec plusieurs options à la fois :

podman update --cpus 5 --cpuset-cpus 0 --cpu-shares 123 --cpuset-mems 0 \
  --memory 1G --memory-swap 2G --memory-reservation 2G \
  --blkio-weight-device /dev/sda:123 --blkio-weight 123 \
  --device-read-bps /dev/sda:10mb --device-write-bps /dev/sda:10mb \
  --device-read-iops /dev/sda:1000 --device-write-iops /dev/sda:1000 \
  --pids-limit 123 ctrID
