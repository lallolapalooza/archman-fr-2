podman-kube-play(1) Manuel des commandes générales podman-kube-play(1)

NOM

podman-kube-play - Créer des conteneurs, des pods et des volumes basés sur du YAML Kubernetes

SYNTAXE

podman kube play [options] fichier.yml|-|https://website.io/file.yml

DESCRIPTION

podman kube play lit un fichier structuré de YAML Kubernetes. Il recrée les conteneurs, les pods ou les volumes décrits dans le YAML. Les conteneurs au sein d'un pod sont ensuite démarrés, et l'ID du nouveau Pod ou le nom du nouveau Volume est affiché. Si le fichier YAML est spécifié comme "-", alors podman kube play lit le fichier YAML depuis l'entrée standard. L'entrée peut également être une URL pointant vers un fichier YAML, telle que https://podman.io/demo.yml. podman kube play lit le YAML depuis l'URL et en crée des pods et des conteneurs.

En utilisant l'option de ligne de commande --down, il est également capable de démonter les pods créés lors d'une exécution précédente de podman kube play.

En utilisant l'option de ligne de commande --replace, il démonte les pods (s'il y en a) créés lors d'une exécution précédente de podman kube play et recrée les pods avec le fichier YAML Kubernetes.

Idéalement, le fichier d'entrée est créé par la commande Podman (voir podman-kube-generate(1)). Cela garantit une importation fluide et des résultats attendus.

Actuellement, les types Kubernetes pris en charge sont :

  • Pod
  • Déploiement
  • PersistentVolumeClaim
  • ConfigMap
  • Secret
  • DaemonSet
  • Job

Pods ou Déploiements Kubernetes

Seuls cinq types de volumes sont pris en charge par kube play : les types de volumes hostPath, emptyDir, configMap, persistentVolumeClaim et image.

  • Lors de l'utilisation du type de volume hostPath, seuls les sous-types défaut (vide), DirectoryOrCreate, Directory, FileOrCreate, File, Socket, CharDevice et BlockDevice sont pris en charge. Podman interprète la valeur du hostPath path comme un chemin de fichier si elle contient au moins une barre oblique (/), sinon Podman traite la valeur comme le nom d'un volume nommé.
  • Lors de l'utilisation d'un persistentVolumeClaim, la valeur de claimName est le nom du volume nommé Podman.
  • Lors de l'utilisation d'un volume emptyDir, Podman crée un volume anonyme qui est attaché aux conteneurs s'exécutant à l'intérieur du pod et qui est supprimé une fois le pod supprimé.
  • Lors de l'utilisation d'un volume configMap, Podman crée un volume anonyme qui est attaché aux conteneurs s'exécutant à l'intérieur du pod et qui est supprimé une fois le pod supprimé.
  • Lors de l'utilisation d'un volume image, Podman crée un volume d'image en lecture seule avec un sous-chemin vide (l'image entière est montée). L'image doit déjà exister localement. Elle est prise en charge en mode rootful uniquement.

Remarque : La politique de redémarrage par défaut pour les conteneurs est always. Vous pouvez modifier la valeur par défaut en définissant le champ restartPolicy dans le spec.

Remarque : Lors de la lecture d'un YAML kube contenant des conteneurs d'initialisation (init containers), le conteneur d'initialisation est créé avec la valeur du type d'initialisation once. Pour modifier le type par défaut, utilisez l'annotation io.podman.annotations.init.container.type pour définir le type sur always.

Remarque : Les types de volumes hostPath créés par kube play reçoivent un label partagé SELinux (z), les montages bind ne sont pas re-étiquetés (utilisez chcon -t container_file_t -R <répertoire>).

Remarque : Pour définir les espaces utilisateur (userns) d'un pod, utilisez l'annotation io.podman.annotations.userns dans la définition du pod/déploiement. Par exemple, l'annotation io.podman.annotations.userns=keep-id indique à Podman de créer un espace utilisateur où le UID:GID de l'utilisateur rootless actuel sont mappés aux mêmes valeurs dans le conteneur. Ceci peut être annulé avec l'indicateur --userns.

Remarque : Utilisez l'annotation io.podman.annotations.volumes-from pour monter les volumes d'un conteneur à un autre. Vous pouvez monter des volumes à partir de plusieurs conteneurs source vers un conteneur cible. Les conteneurs source appartenant au même pod doivent être définis avant le conteneur source dans le YAML kube. Le format de l'annotation est io.podman.annotations.volumes-from/conteneurCible: "conteneurSource1:optionsMontage1;conteneurSource2:optionsMontage2".

Remarque : Si le tag :latest est utilisé, Podman tente de télécharger l'image à partir d'un registre. Si l'image a été construite localement avec Podman ou Buildah, elle a localhost comme domaine, dans ce cas, Podman utilise l'image du stockage local même si elle a le tag :latest.

Remarque : La commande podman play kube est un alias de podman kube play et remplit la même fonction.

Remarque : La commande podman kube down peut être utilisée pour arrêter et supprimer des pods ou des conteneurs basés sur le même YAML Kubernetes utilisé par podman kube play pour les créer.

Remarque : Pour personnaliser le nom du conteneur d'infrastructure (infra container) créé lors de podman kube play, utilisez l'annotation io.podman.annotations.infra.name dans la définition du pod. Cette annotation est automatiquement définie lors de la génération d'un YAML kube à partir d'un pod créé avec l'option --infra-name définie.

Remarque : Utilisez l'annotation io.podman.annotations.pids-limit/$nom_conteneur pour configurer la limite de pids du pod.

Remarque : Utilisez l'annotation io.podman.annotations.cpuset/$nom_conteneur pour restreindre l'exécution d'un conteneur à un ensemble spécifique de cœurs CPU. Ceci est équivalent à l'option --cpuset-cpus=nombre dans podman-run(1).

Remarque : Utilisez l'annotation io.podman.annotations.memory-nodes/$nom_conteneur pour restreindre les allocations mémoire d'un conteneur à un ensemble spécifique de nœuds mémoire sur les systèmes NUMA. Ceci est équivalent à l'option --cpuset-mems=nœuds dans podman-run(1).

PersistentVolumeClaims Kubernetes

Un PersistentVolumeClaim Kubernetes représente un volume nommé Podman. Seul le nom du PersistentVolumeClaim est requis par Podman pour créer un volume. Les annotations Kubernetes peuvent être utilisées pour exploiter les options disponibles pour les volumes Podman.

  • volume.podman.io/driver
  • volume.podman.io/device
  • volume.podman.io/type
  • volume.podman.io/uid
  • volume.podman.io/gid
  • volume.podman.io/mount-options
  • volume.podman.io/import-source
  • volume.podman.io/image

Utilisez volume.podman.io/import-source pour importer le contenu de l'archive tar ( .tar, .tar.gz, .tgz, .bzip, .tar.xz, .txz, .tar.zst) spécifiée dans la valeur de l'annotation dans le volume Podman créé.

Kube play est capable de construire des images à la volée étant donné la structure de répertoire correcte et des Containerfiles. Cette option n'est pas encore disponible pour les clients distants, y compris les machines Mac et Windows (sauf WSL2). Considérez l'extrait suivant d'un fichier YAML :

apiVersion: v1
kind: Pod
metadata:
...
spec:
  containers:
  - name: container
    image: foobar
...

S'il existe un répertoire nommé foobar dans le répertoire de travail actuel avec un fichier nommé Containerfile ou Dockerfile, Podman kube play construit cette image et la nomme foobar. Une structure de répertoire d'exemple pour cet exemple ressemble à ceci :

|- mesfichierskube
    |- monfichierplay.yaml
    |- foobar
         |- Containerfile

La construction considère foobar comme le répertoire de contexte pour la construction. S'il existe une image dans le stockage local appelée foobar, l'image n'est pas construite à moins que l'indicateur --build ne soit utilisé. Utilisez --build=false pour désactiver complètement les constructions.

Kube play prend en charge les sélecteurs de périphériques CDI (Container Device Interface) pour partager des périphériques hôtes (par exemple, des GPU) avec des conteneurs. Le format de configuration suit la gestion des ressources étendues de Kubernetes :

apiVersion: v1
kind: Pod
spec:
  containers:
  - name: container
    resources:
      limits:
        nvidia.com/gpu=all: 1

Pour activer le partage de périphériques hôtes, analogue à l'utilisation de l'indicateur --device, Podman kube prend en charge un sélecteur CDI personnalisé : podman.io/device=<chemin_périphérique_hôte>.

ConfigMap Kubernetes

Les ConfigMaps Kubernetes peuvent être référencés comme source de variables d'environnement ou de volumes dans les Pods ou les Déploiements. Les ConfigMaps ne sont pas un objet autonome dans Podman ; au lieu de cela, lorsqu'un conteneur utilise un ConfigMap, Podman crée les variables d'environnement ou les volumes selon les besoins.

Par exemple, le document YAML suivant définit un ConfigMap puis l'utilise dans un Pod :

apiVersion: v1
kind: ConfigMap
metadata:
  name: foo
data:
    FOO: bar
---
apiVersion: v1
kind: Pod
metadata:
  name: foobar
spec:
  containers:
  - name: container-1
    image: fooba

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

r envFrom: - configMapRef: name: foo optional: false

et en conséquence, la variable d'environnement FOO est définie à bar pour le conteneur container-1.

Kubernetes Secret

Kubernetes Secret représente un secret nommé Podman. Le Secret Kubernetes est sauvegardé dans son intégralité et peut être référencé comme source de variables d'environnement ou de volumes dans les Pods ou les Deployments.

Par exemple, le document YAML suivant définit un Secret puis l'utilise dans un Pod :

kind: Secret
apiVersion: v1
metadata:
  name: foo
data:
  foo: YmFy # base64 pour bar
---
apiVersion: v1
kind: Pod
metadata:
  name: foobar
spec:
  containers:
  - name: container-1
    image: foobar
    env:
    - name: FOO
      valueFrom:
        secretKeyRef:
          name: foo
          key: foo

et en conséquence, la variable d'environnement FOO est définie à bar pour le conteneur container-1.

Montage automatique de volumes (obsolète)

Note : L'annotation de montage automatique est obsolète. Kubernetes prend en charge nativement les volumes d'images et il convient de les utiliser plutôt que cette annotation spécifique à Podman.

Une image peut être montée automatiquement dans un conteneur si l'annotation io.podman.annotations.kube.image.automount/$ctrname est fournie. Les règles suivantes s'appliquent :

  • L'image doit déjà exister localement.
  • L'image doit avoir au moins 1 directive de volume.
  • Le chemin donné par la directive de volume sera monté depuis l'image dans le conteneur. Par exemple, une image avec un volume à /test/test_dir aura /test/test_dir dans l'image monté sur /test/test_dir dans le conteneur.
  • Plusieurs images peuvent être spécifiées. Si plusieurs images ont un volume à un chemin spécifique, la dernière image spécifiée l'emporte.
  • Les images sont toujours montées en lecture seule.
  • Les images à monter sont définies dans l'annotation "io.podman.annotations.kube.image.automount/$ctrname" sous forme de liste séparée par des points-virgules. Elles sont montées dans un seul conteneur du pod, pas dans tout le pod. L'annotation peut être spécifiée pour des conteneurs supplémentaires si des montages supplémentaires sont requis.

OPTIONS

--annotation=clé=valeur

Ajoute une annotation au conteneur ou au pod. Cette option peut être définie plusieurs fois.

Note : Pour podman kube play, le drapeau --annotation ajoute des annotations spécifiques à Podman aux conteneurs et aux pods créés par Podman, et non au YAML Kubernetes lui-même. Ces annotations peuvent être utilisées pour configurer des fonctionnalités spécifiques à Podman telles que les espaces de noms utilisateur (io.podman.annotations.userns), volumes-from (io.podman.annotations.volumes-from), et d'autres comportements de conteneur.

--authfile=chemin

Chemin du fichier d'authentification. Par défaut, il s'agit de ${XDG_RUNTIME_DIR}/containers/auth.json sous Linux, et de $HOME/.config/containers/auth.json sous Windows/macOS. Le fichier est créé par podman login. Si l'état d'autorisation ne s'y trouve pas, $HOME/.docker/config.json est vérifié, qui est défini à l'aide de docker login.

Note : Il existe également la possibilité de remplacer le chemin par défaut du fichier d'authentification en définissant la variable d'environnement REGISTRY_AUTH_FILE. Cela peut être fait avec export REGISTRY_AUTH_FILE=chemin.

--build

Génère des images même si elles sont trouvées dans le stockage local. Utilisez --build=false pour désactiver complètement les générations. (Cette option n'est pas disponible avec le client Podman distant)

Note : Vous pouvez également remplacer le type d'isolation par défaut en définissant la variable d'environnement BUILDAH_ISOLATION. export BUILDAH_ISOLATION=oci. Voir podman-build.1.md pour plus d'informations.

--cert-dir=chemin

Utilise les certificats à l'emplacement chemin (*.crt, *.cert, *.key) pour se connecter au registre. (Défaut : /etc/containers/certs.d) Pour plus de détails, voir containers-certs.d(5). (Cette option n'est pas disponible avec le client Podman distant, y compris les machines Mac et Windows (sauf WSL2))

--configmap=chemin

Utilise le fichier YAML Kubernetes configmap à l'emplacement spécifié pour fournir une source de valeurs de variables d'environnement dans les conteneurs du pod. (Cette option n'est pas disponible avec le client Podman distant)

Note : L'option --configmap peut être utilisée plusieurs fois ou une liste de chemins séparés par des virgules peut être utilisée pour passer plusieurs fichiers YAML Kubernetes configmap. Le fichier YAML peut être dans un format YAML multi-documents. Mais il ne doit contenir que des configmaps.

--context-dir=chemin

Utilise le répertoire chemin comme répertoire de contexte de génération pour chaque image. Nécessite que l'option --build soit vraie. (Cette option n'est pas disponible avec le client Podman distant)

--creds=[nom d'utilisateur[:mot de passe]]

Le [nom d'utilisateur[:mot de passe]] à utiliser pour s'authentifier auprès du registre, si nécessaire. Si une ou deux valeurs ne sont pas fournies, une invite de commande apparaît et la valeur peut être saisie. Le mot de passe est saisi sans écho.

Notez que les identifiants spécifiés sont uniquement utilisés pour s'authentifier auprès des registres cibles. Ils ne sont pas utilisés pour les miroirs ou lorsque le registre est réécrit (voir containers-registries.conf(5)) ; pour s'authentifier auprès de ceux-ci, envisagez d'utiliser un fichier containers-auth.json(5).

--force

Détruit les volumes liés aux PersistentVolumeClaims dans le cadre de --down

--help, -h

Affiche le message d'utilisation

--ip=adresse IP

Attribue une adresse IP statique au pod. Cette option peut être spécifiée plusieurs fois lorsque kube play crée plus d'un pod. Note : Lors de la connexion à plusieurs réseaux, utilisez la syntaxe --network nom:ip=<ip>.

--log-driver=driver

Définit le pilote d'enregistrement pour tous les conteneurs créés.

--log-opt=nom=valeur

Options spécifiques au pilote d'enregistrement.

Configurez l'enregistrement personnalisé. Les *noms* suivants sont pris en charge :

path : spécifie un chemin vers le fichier journal
(par exemple, --log-opt path=/var/log/container/mycontainer.json) ;

max-size : spécifie une taille maximale pour le fichier journal
(par exemple, --log-opt max-size=10mb) ;

tag : spécifie une étiquette de journal personnalisée pour le conteneur
(par exemple, --log-opt tag="{{.ImageName}}". Il prend en charge les mêmes clés que podman inspect --format. Cette option n'est actuellement prise en charge que par le pilote de journalisation journald.

--mac-address=adresse MAC

Attribue une adresse MAC statique au pod. Cette option peut être spécifiée plusieurs fois lorsque kube play crée plus d'un pod. Note : Lors de la connexion à plusieurs réseaux, utilisez la syntaxe --network nom:mac=<mac>.

--network=mode, --net

Définit le mode réseau pour le pod.

Les valeurs valides pour mode sont :

•
bridge[:OPTIONS,...] : Crée une pile réseau sur le pont par défaut. C'est le mode par défaut pour les conteneurs rootful. Il est possible de spécifier les options supplémentaires suivantes :
  • alias=nom : Ajoute un alias à portée réseau pour le conteneur.
  • ip=IPv4 : Spécifie une adresse IPv4 statique pour ce conteneur.
  • ip6=IPv6 : Spécifie une adresse IPv6 statique pour ce conteneur.
  • mac=MAC : Spécifie une adresse MAC statique pour ce conteneur.
  • interface_name=nom : Spécifie un nom pour l'interface réseau créée à l'intérieur du conteneur.
  • host_interface_name=nom : Spécifie un nom pour l'interface réseau créée à l'extérieur du conteneur.
Toute autre option sera transmise à netavark sans validation. Cela peut être utile pour passer des arguments aux plugins netavark.

Par exemple, pour définir une adresse ipv4 statique et une adresse mac statique, utilisez --network bridge:ip=10.88.0.10,mac=44:33:22:11:00:99.

  • <nom ou ID du réseau>[:OPTIONS,...] : Se connecte à un réseau défini par l'utilisateur ; c'est le nom ou l'ID du réseau d'un réseau créé par podman network create. Il est possible de spécifier les mêmes options décrites sous le mode bridge ci-dessus. Utilisez l'option --network plusieurs fois pour spécifier des réseaux supplémentaires.
    Pour des raisons de compatibilité ascendante, il est également possible de spécifier des réseaux séparés par des virgules dans le premier argument --network, mais cela vous empêche d'utiliser les options décrites dans la section bridge ci-dessus.
  • none : Crée un espace de noms réseau pour le conteneur mais ne configure aucune interface réseau pour celui-ci, de sorte que le conteneur n'a aucune connectivité réseau.
  • container:id : Réutilise la pile réseau d'un autre conteneur.
  • host : Utilise l'espace de noms réseau de l'hôte pour le conteneur au lieu d'en créer un isolé. Attention : Cela donne au conteneur un accès complet aux sockets Unix abstraits et aux sockets TCP/UDP liés à localhost. Étant donné que ces mécanismes sont souvent utilisés pour empêcher l'accès aux services système sensibles, en les isolant de l'accès par des entités externes, l'utilisation de cette option peut être considérée comme une vulnérabilité de sécurité.
  • ns:chemin : Chemin vers un espace de noms réseau à rejoindre.
  • private : Crée un nouvel espace de noms pour le conteneur. Cela utilise le mode bridge pour les conteneurs rootful et slirp4netns pour les conteneurs rootless.
  • slirp4netns[:OPTIONS,...] : utilise slirp4netns(1) pour créer une pile réseau utilisateur. Il est possible de spécifier les options supplémentaires suivantes, elles peuvent également être définies avec network_cmd_options dans containers.conf :
  • allow_host_loopback=true|false : Permet à slirp4netns d'accéder à l'IP de bouclage de l'hôte (la valeur par défaut est 10.0.2.2 ou la deuxième IP du sous-réseau CIDR de slirp4netns lorsqu'elle est modifiée, voir l'option cidr ci-dessous). La valeur par défaut est false.
  • mtu=MTU : Spécifie l'MTU à utiliser pour ce réseau. (La valeur par défaut est 65520).
  • cidr=CIDR : Spécifie la plage d'adresses IP à utiliser pour l'a

    This is the default for rootless containers and only supported in rootless mode.
    By default, IPv4 and IPv6 addresses and routes, as well as the pod interface name, are copied from the host. Port forwarding preserves the original source IP address. Options described in pasta(1) can be specified as comma-separated arguments.
    In terms of pasta(1) options, --config-net is given by default, in order to configure networking when the container is started, and --no-map-gw is also assumed by default, to avoid direct access from container to host using the gateway address. The latter can be overridden by passing --map-gw in the pasta-specific options (despite not being an actual pasta(1) option).
    For better integration with DNS handling, --dns-forward 169.254.1.1 is passed, and this address is added to resolv.conf(5) as first resolver. It is possible to pass --dns-forward explicitly in case a different IP address should be used. To make the host.containers.internal /etc/hosts entry work and allow connections to the host, --map-guest-addr 169.254.1.2 is passed. Again, it can be set explicitly to choose a different IP address.
    Also, -t none and -u none are passed if, respectively, no TCP or UDP port forwarding from host to container is configured (via Podman's --publish or by passing the pasta -t/-u options directly), to disable automatic port forwarding based on bound ports. Similarly, -T none and -U none are given to disable the same functionality from container to host.
    All options can also be set in containers.conf(5); see the pasta_options key under the network section in that file.

    • pasta:--map-gw: Allow the container to directly reach the host using the gateway address.

NAME

podman-kube-play - Play Kubernetes YAML files in pods

SYNOPSIS

podman kube play [options]

podman kube play [options]

DESCRIPTION

The podman kube play command runs Kubernetes YAML files as containers on the local system.

The command reads the specified YAML file or files from the specified directory and creates pods, containers, volumes, and networks based on the definitions in the YAML file(s).

The supported resources are Pods, Deployments, DaemonSets, Jobs, ConfigMaps, and PersistentVolumeClaims.

The command supports a subset of the Kubernetes API. For a full list of supported fields, refer to the Podman-kube documentation.

OPTIONS

The podman kube play command supports a number of options to control the behavior of the command. Some of the common options include:

--build
Build images from Dockerfiles found in the same directory as the YAML file.
--dry-run
Print the generated Podman commands without executing them.
--network
Specify the network to use for the containers.
--replace
Replace existing resources if they are found.
--save
Save the generated Podman commands to a file.
--tls-verify
Verify the TLS certificates of the registry.
--volume-driver
Specify the volume driver to use for the volumes.

EXAMPLES

Run a Kubernetes YAML file:

podman kube play my-app.yaml

Run all YAML files in a directory:

podman kube play ./my-app-dir/

Build images and run a Kubernetes YAML file:

podman kube play --build my-app.yaml

Replace existing resources and run a Kubernetes YAML file:

podman kube play --replace my-app.yaml
