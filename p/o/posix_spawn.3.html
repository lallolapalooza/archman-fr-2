posix_spawn(3) Manuel des fonctions de bibliothèque posix_spawn(3)

NOM

posix_spawn, posix_spawnp - créer un nouveau processus

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <spawn.h>
int posix_spawn(pid_t *restrict pid, const char *restrict path,
                const posix_spawn_file_actions_t *restrict file_actions,
                const posix_spawnattr_t *restrict attrp,
                char *const argv[restrict],
                char *const envp[restrict]);
int posix_spawnp(pid_t *restrict pid, const char *restrict file,
                const posix_spawn_file_actions_t *restrict file_actions,
                const posix_spawnattr_t *restrict attrp,
                char *const argv[restrict],
                char *const envp[restrict]);

DESCRIPTION

Les fonctions posix_spawn() et posix_spawnp() sont utilisées pour créer un nouveau processus enfant qui exécute un fichier spécifié. Ces fonctions ont été spécifiées par POSIX pour fournir une méthode standardisée de création de nouveaux processus sur des machines qui ne supportent pas l'appel système fork(2). Ces machines sont généralement de petits systèmes embarqués sans support MMU.

Les fonctions posix_spawn() et posix_spawnp() fournissent la fonctionnalité d'une combinaison de fork(2) et exec(3), avec quelques étapes de maintenance optionnelles dans le processus enfant avant l'exec(3). Ces fonctions ne sont pas destinées à remplacer les appels système fork(2) et execve(2). En fait, elles ne fournissent qu'un sous-ensemble des fonctionnalités réalisables en utilisant les appels système.

La seule différence entre posix_spawn() et posix_spawnp() réside dans la manière dont elles spécifient le fichier à exécuter par le processus enfant. Avec posix_spawn(), le fichier exécutable est spécifié comme un chemin (qui peut être absolu ou relatif). Avec posix_spawnp(), le fichier exécutable est spécifié comme un nom de fichier simple ; le système recherche ce fichier dans la liste des répertoires spécifiés par PATH (de la même manière que pour execvp(3)). Pour le reste de cette page, la discussion est formulée en termes de posix_spawn(), étant entendu que posix_spawnp() ne diffère que sur le point décrit.

Les arguments restants de ces deux fonctions sont les suivants:

pid
pointe vers un tampon qui est utilisé pour retourner l'identifiant du processus du nouvel enfant. L'identifiant du processus enfant est retourné dans le tampon pointé par pid.
file_actions
pointe vers un objet d'actions de fichier spawn qui spécifie les actions relatives aux fichiers à effectuer dans l'enfant entre les étapes fork(2) et exec(3). Cet objet est initialisé et rempli avant l'appel posix_spawn() en utilisant posix_spawn_file_actions_init(3) et les fonctions posix_spawn_file_actions_*().
attrp
pointe vers un objet d'attributs qui spécifie divers attributs du processus enfant créé. Cet objet est initialisé et rempli avant l'appel posix_spawn() en utilisant posix_spawnattr_init(3) et les fonctions posix_spawnattr_*().
argv
envp
spécifient la liste des arguments et l'environnement pour le programme qui est exécuté dans le processus enfant, comme pour execve(2).

Ci-dessous, les fonctions sont décrites en termes d'un processus en trois étapes : l'étape fork(), l'étape pré-exec() (exécutée dans l'enfant), et l'étape exec() (exécutée dans l'enfant).

étape fork()

Depuis glibc 2.24, la fonction posix_spawn() commence par appeler clone(2) avec les drapeaux CLONE_VM et CLONE_VFORK. Les implémentations plus anciennes utilisent fork(2), ou éventuellement vfork(2) (voir ci-dessous).

Le PID du nouveau processus enfant est placé dans *pid. La fonction posix_spawn() retourne ensuite le contrôle au processus parent.

Par la suite, le parent peut utiliser l'un des appels système décrits dans wait(2) pour vérifier l'état du processus enfant. Si l'enfant échoue dans l'une des étapes de maintenance décrites ci-dessous, ou échoue à exécuter le fichier désiré, il se termine avec le statut 127.

Avant glibc 2.24, le processus enfant est créé en utilisant vfork(2) au lieu de fork(2) lorsque l'une des conditions suivantes est vraie :

•
l'élément spawn-flags de l'objet d'attributs pointé par attrp contient le drapeau spécifique GNU POSIX_SPAWN_USEVFORK ; ou
•
file_actions est NULL et l'élément spawn-flags de l'objet d'attributs pointé par attrp ne contient PAS POSIX_SPAWN_SETSIGMASK, POSIX_SPAWN_SETSIGDEF, POSIX_SPAWN_SETSCHEDPARAM, POSIX_SPAWN_SETSCHEDULER, POSIX_SPAWN_SETPGROUP, ou POSIX_SPAWN_RESETIDS.

En d'autres termes, vfork(2) est utilisé si l'appelant le demande, ou s'il n'y a pas de nettoyage attendu dans l'enfant avant qu'il n'exec(3) le fichier demandé.

étape pré-exec() : maintenance

Entre les étapes fork() et exec(), un processus enfant peut avoir besoin d'effectuer un ensemble d'actions de maintenance. Les fonctions posix_spawn() et posix_spawnp() supportent un ensemble petit et bien défini de tâches système que le processus enfant peut accomplir avant d'exécuter le fichier exécutable. Ces opérations sont contrôlées par l'objet d'attributs pointé par attrp et l'objet d'actions de fichier pointé par file_actions. Dans l'enfant, le traitement est effectué dans l'ordre suivant :

(1)
Les actions sur les attributs du processus : masque de signaux, gestionnaires par défaut de signaux, algorithme et paramètres de planification, groupe de processus, et identifiants utilisateur et groupe effectifs sont modifiés comme spécifié par l'objet d'attributs pointé par attrp.
(2)
Les actions de fichier, comme spécifié dans l'argument file_actions, sont effectuées dans l'ordre où elles ont été spécifiées en utilisant les appels aux fonctions posix_spawn_file_actions_add*().
(3)
Les descripteurs de fichiers avec le drapeau FD_CLOEXEC défini sont fermés.

Tous les attributs du processus dans l'enfant, autres que ceux affectés par les attributs spécifiés dans l'objet pointé par attrp et les actions de fichier dans l'objet pointé par file_actions, seront affectés comme si l'enfant avait été créé avec fork(2) et avait exécuté le programme avec execve(2).

Les actions sur les attributs du processus sont définies par l'objet d'attributs pointé par attrp. Le drapeau spawn-flags (défini en utilisant posix_spawnattr_setflags(3)) contrôle les actions générales qui se produisent, et d'autres attributs dans l'objet spécifient les valeurs à utiliser pendant ces actions.

Les effets des drapeaux qui peuvent être spécifiés dans spawn-flags sont les suivants :

POSIX_SPAWN_SETSIGMASK
Définit le masque de signaux à l'ensemble de signaux spécifié dans l'attribut spawn-sigmask de l'objet pointé par attrp. Si le drapeau POSIX_SPAWN_SETSIGMASK n'est pas défini, alors l'enfant hérite du masque de signaux du parent.
POSIX_SPAWN_SETSIGDEF
Réinitialise la disposition de tous les signaux de l'ensemble spécifié dans l'attribut spawn-sigdefault de l'objec
t pointé par attrp par défaut. Pour le traitement des dispositions des signaux non spécifiées dans l'attribut spawn-sigdefault, ou le traitement lorsque POSIX_SPAWN_SETSIGDEF n'est pas spécifié, voir execve(2).
POSIX_SPAWN_SETSCHEDPARAM
Si ce drapeau est défini, et que le drapeau POSIX_SPAWN_SETSCHEDULER n'est pas défini, alors les paramètres de planification sont définis sur les paramètres spécifiés dans l'attribut spawn-schedparam de l'objet pointé par attrp.
POSIX_SPAWN_SETSCHEDULER
Définit l'algorithme de politique de planification et les paramètres du processus fils, comme suit :
•
La politique de planification est définie sur la valeur spécifiée dans l'attribut spawn-schedpolicy de l'objet pointé par attrp.
•
Les paramètres de planification sont définis sur la valeur spécifiée dans l'attribut spawn-schedparam de l'objet pointé par attrp (mais voir BUGS).

Si les drapeaux POSIX_SPAWN_SETSCHEDPARAM et POSIX_SPAWN_SETSCHEDPOLICY ne sont pas spécifiés, le processus fils hérite des attributs de planification correspondants du processus parent.

POSIX_SPAWN_RESETIDS
Si ce drapeau est défini, réinitialise l'UID et le GID effectifs à l'UID et au GID réels du processus parent. Si ce drapeau n'est pas défini, le processus fils conserve l'UID et le GID effectifs du parent. Dans les deux cas, si les bits de permission set-user-ID et set-group-ID sont activés sur le fichier exécutable, leur effet remplacera la définition de l'UID et du GID effectifs (voir execve(2)).
POSIX_SPAWN_SETPGROUP
Définit le groupe de processus sur la valeur spécifiée dans l'attribut spawn-pgroup de l'objet pointé par attrp. Si l'attribut spawn-pgroup a la valeur 0, l'ID du groupe de processus du fils est rendu identique à son ID de processus. Si le drapeau POSIX_SPAWN_SETPGROUP n'est pas défini, le processus fils hérite de l'ID du groupe de processus du parent.
POSIX_SPAWN_USEVFORK
Depuis glibc 2.24, ce drapeau n'a aucun effet. Sur les implémentations plus anciennes, la définition de ce drapeau force l'étape fork() à utiliser vfork(2) au lieu de fork(2). Le macro de test de fonctionnalité _GNU_SOURCE doit être défini pour obtenir la définition de cette constante.
POSIX_SPAWN_SETSID (depuis glibc 2.26)
Si ce drapeau est défini, le processus fils crée une nouvelle session et devient le leader de session. Le processus fils devient également le leader du groupe de processus dans la nouvelle session (voir setsid(2)). Le macro de test de fonctionnalité _GNU_SOURCE doit être défini pour obtenir la définition de cette constante.

Si attrp est NULL, alors les comportements par défaut décrits ci-dessus pour chaque drapeau s'appliquent.

L'argument file_actions spécifie une séquence d'opérations de fichier qui sont effectuées dans le processus fils après le traitement général décrit ci-dessus, et avant qu'il n'exécute l'exec(3). Si file_actions est NULL, alors aucune action spéciale n'est effectuée, et les sémantiques standard de l'exec(3) s'appliquent : les descripteurs de fichier ouverts avant l'exec restent ouverts dans le nouveau processus, à l'exception de ceux pour lesquels le drapeau FD_CLOEXEC a été défini. Les verrous de fichier restent en place.

Si file_actions n'est pas NULL, alors il contient un ensemble ordonné de requêtes pour open(2), close(2), et dup2(2) des fichiers. Ces requêtes sont ajoutées à file_actions par posix_spawn_file_actions_addopen(3), posix_spawn_file_actions_addclose(3), et posix_spawn_file_actions_adddup2(3). Les opérations demandées sont effectuées dans l'ordre où elles ont été ajoutées à file_actions.

Si l'une des actions de maintenance échoue (en raison de valeurs invalides passées ou d'autres raisons pour lesquelles la gestion des signaux, la planification des processus, les fonctions d'ID de groupe de processus et les opérations sur les descripteurs de fichier peuvent échouer), le processus fils se termine avec la valeur de sortie 127.

Étape exec()

Une fois que le processus fils a correctement forké et effectué toutes les étapes de pré-exécution demandées, le processus fils exécute l'exécutable demandé.

Le processus fils prend son environnement de l'argument envp, qui est interprété comme s'il avait été passé à execve(2). Les arguments du processus créé proviennent de l'argument argv, qui est traité comme pour execve(2).

VALEUR DE RETOUR

En cas de succès, posix_spawn() et posix_spawnp() placent le PID du processus fils dans pid, et retournent 0. S'il y a une erreur pendant l'étape fork(), aucun processus fils n'est créé, le contenu de *pid est indéterminé, et ces fonctions retournent un numéro d'erreur comme décrit ci-dessous.

Même lorsque ces fonctions retournent un statut de succès, le processus fils peut toujours échouer pour une multitude de raisons liées à son initialisation pré-exec(). De plus, l'exec(3) peut échouer. Dans tous ces cas, le processus fils se terminera avec la valeur de sortie de 127.

ERREURS

Les fonctions posix_spawn() et posix_spawnp() échouent uniquement dans le cas où l'appel sous-jacent fork(2), vfork(2), ou clone(2) échoue ; dans ces cas, ces fonctions retournent un numéro d'erreur, qui sera l'une des erreurs décrites pour fork(2), vfork(2), ou clone(2).

De plus, ces fonctions échouent si :

ENOSYS
Fonction non supportée sur ce système.

NORMES

POSIX.1-2008.

HISTORIQUE

glibc 2.2. POSIX.1-2001.

NOTES

Les activités de maintenance dans le processus fils sont contrôlées par les objets pointés par attrp (pour les actions non-fichiers) et file_actions. Dans le jargon POSIX, les types de données posix_spawnattr_t et posix_spawn_file_actions_t sont appelés objets, et leurs éléments ne sont pas spécifiés par nom. Les programmes portables doivent initialiser ces objets en utilisant uniquement les fonctions spécifiées par POSIX. (En d'autres termes, bien que ces objets puissent être implémentés sous forme de structures contenant des champs, les programmes portables doivent éviter de dépendre de tels détails d'implémentation.)

Selon POSIX, il n'est pas spécifié si les gestionnaires de fork établis avec pthread_atfork(3) sont appelés lorsque posix_spawn() est invoqué. Depuis glibc 2.24, les gestionnaires de fork ne sont pas exécutés dans tous les cas. Sur les implémentations plus anciennes, les gestionnaires de fork sont appelés uniquement si le processus fils est créé en utilisant fork(2).

Il n'existe pas de fonction "posix_fspawn" (c'est-à-dire une fonction qui est à posix_spawn() ce que fexecve(3) est à execve(2)). Cependant, cette fonctionnalité peut être obtenue en spécifiant l'argument path comme l'un des fichiers dans le répertoire /proc/self/fd de l'appelant.

BOGUES

POSIX.1 stipule que lorsque POSIX_SPAWN_SETSCHEDULER est spécifié dans spawn-flags, alors POSIX_SPAWN_SETSCHEDPARAM (s'il est présent) est ignoré. Cependant, avant glibc 2.14, les appels à posix_spawn() échouaient avec une erreur si POSIX_SPAWN_SETSCHEDULER était spécifié sans également spécifier POSIX_SPAWN_SETSCHEDPARAM.

EXEMPLES

Le programme ci-dessous démontre l'utilisation de diverses fonctions de l'API POSIX spawn. Le programme accepte des attributs en ligne de commande qui peuvent être utilisés pour créer des objets d'actions de fichiers et d'attributs. Les arguments restants en ligne de commande sont utilisés comme nom d'exécutable et arguments de ligne de commande du programme qui est exécuté dans le processus fils.

Lors de la première exécution, la commande date(1) est exécutée dans le fils, et l'appel posix_spawn() n'utilise aucune action de fichier ni objet d'attributs.


$ ./a.out date;
PID du fils : 7634
Mar 01 Fév 19:47:50 CEST 2011
Statut du fils : terminé, statut=0

Lors de la prochaine exécution, l'option de ligne de commande -c est utilisée pour créer un objet d'actions de fichiers qui ferme la sortie standard dans le fils. Par conséquent, date(1) échoue en essayant d'écrire en sortie et se termine avec le statut 1.


$ ./a.out -c date;
PID du fils : 7636
date : erreur d'écriture : descripteur de fichier invalide
Statut du fils : terminé, statut=1

Lors de la prochaine exécution, l'option de ligne de commande -s est utilisée pour créer un objet d'attributs qui spécifie que tous les signaux (bloquables) dans le fils doivent être bloqués. Par conséquent, essayer de tuer le fils avec le signal par défaut envoyé par kill(1) (c'est-à-dire SIGTERM) échoue, car ce signal est bloqué. Par conséquent, pour tuer le fils, SIGKILL est nécessaire (SIGKILL ne peut pas être bloqué).


$ ./a.out -s sleep 60 &
[1] 7637
$ PID du fils : 7638
$ kill 7638;
$ kill -KILL 7638;
$ Statut du fils : tué par le signal 9
[1]+  Terminé                   ./a.out -s sleep 60

Lorsque nous essayons d'exécuter une commande inexistante dans le fils, l'exec(3) échoue et le fils se termine avec le statut 127.


$ ./a.out xxxxx;
PID du fils : 10190
Statut du fils : terminé, statut=127

Source du programme

#include <err.h>
#include <errno.h>
#include <spawn.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <wait.h>
char **environ;
int
main(int argc, char *argv[])
{
    pid_t child_pid;
    int s, opt, status;
    sigset_t mask;
    posix_spawnattr_t attr;
    posix_spawnattr_t *attrp;
    posix_spawn_file_actions_t file_actions;
    posix_spawn_file_actions_t *file_actionsp;
    /* Parse les options de la ligne de commande, qui peuvent être utilisées pour spécifier un
       objet d'attributs et un objet d'actions de fichier pour l'enfant.  */
    attrp = NULL;
    file_actionsp = NULL;
    while ((opt = getopt(argc, argv, "sc")) != -1) {
        switch (opt) {
        case 'c':       /* -c: ferme la sortie standard dans l'enfant */
            /* Crée un objet d'actions de fichier et y ajoute une action "fermer".  */
            s = posix_spawn_file_actions_init(&file_actions);
            if (s != 0)
                errc(EXIT_FAILURE, s, "posix_spawn_file_actions_init");
            s = posix_spawn_file_actions_addclose(&file_actions,
                                                  STDOUT_FILENO);
            if (s != 0)
                errc(EXIT_FAILURE, s, "posix_spawn_file_actions_addclose");
            file_actionsp = &file_actions;
            break;
        case 's':       /* -s: bloque tous les signaux dans l'enfant */
            /* Crée un objet d'attributs et y ajoute une action "définir le masque de signal".  */
            s = posix_spawnattr_init(&attr);
            if (s != 0)
                errc(EXIT_FAILURE, s, "posix_spawnattr_init");
            s = posix_spawnattr_setflags(&attr, POSIX_SPAWN_SETSIGMASK);
            if (s != 0)
                errc(EXIT_FAILURE, s, "posix_spawnattr_setflags");
            sigfillset(&mask);
            s = posix_spawnattr_setsigmask(&attr, &mask);
            if (s != 0)
                errc(EXIT_FAILURE, s, "posix_spawnattr_setsigmask");
            attrp = &attr;
            break;
        }
    }
    if (argv[optind] == NULL) {
        fprintf(stderr, "Usage: %s [-cs] executable [args]\n", argv[0]);
        exit(EXIT_FAILURE);
    }
    /* Lance l'enfant.  Le nom du programme à exécuter et les arguments de la ligne de commande
       sont pris des arguments de la ligne de commande de ce programme.  L'environnement
       du programme exécuté dans l'enfant est rendu identique à celui du parent.  */
    s = posix_spawnp(&child_pid, argv[optind], file_actionsp, attrp,
                     &argv[optind], environ);
    if (s != 0)
        errc(EXIT_FAILURE, s, "posix_spawn");
    /* Détruit tous les objets que nous avons créés précédemment.  */
    if (attrp != NULL) {
        s = posix_spawnattr_destroy(attrp);
        if (s != 0)
            errc(EXIT_FAILURE, s, "posix_spawnattr_destroy");
    }
    if (file_actionsp != NULL) {
        s = posix_spawn_file_actions_destroy(file_actionsp);
        if (s != 0)
            errc(EXIT_FAILURE, s, "posix_spawn_file_actions_destroy");
    }
    printf("PID de l'enfant : %jd\n", (intmax_t) child_pid);
    /* Surveille l'état de l'enfant jusqu'à ce qu'il se termine.  */
    do {
        s = waitpid(child_pid, &status, WUNTRACED | WCONTINUED);
        if (s == -1)
            err(EXIT_FAILURE, "waitpid");
        printf("Statut de l'enfant : ");
        if (WIFEXITED(status)) {
            printf("terminé, statut=%d\n", WEXITSTATUS(status));
        } else if (WIFSIGNALED(status)) {
            printf("tué par le signal %d\n", WTERMSIG(status));
        } else if (WIFSTOPPED(status)) {
            printf("arrêté par le signal %d\n", WSTOPSIG(status));
        } else if (WIFCONTINUED(status)) {
            printf("continué\n");
        }
    } while (!WIFEXITED(status) && !WIFSIGNALED(status));
    exit(EXIT_SUCCESS);
}
