NOM

podman-auto-update - Met à jour automatiquement les conteneurs selon leur politique de mise à jour automatique

SYNTAXE

podman auto-update [options]

DESCRIPTION

podman auto-update télécharge les nouvelles images de conteneurs et redémarre les conteneurs configurés pour les mises à jour automatiques. Pour utiliser les mises à jour automatiques, le conteneur ou les charges de travail Kubernetes doivent s'exécuter dans une unité systemd. Après une mise à jour réussie d'une image, les conteneurs utilisant l'image sont mis à jour en redémarrant les unités systemd dans lesquelles ils s'exécutent. Veuillez vous référer à podman-systemd.unit(5) pour savoir comment exécuter Podman sous systemd.

Pour configurer un conteneur pour les mises à jour automatiques, il doit être créé avec l'étiquette io.containers.autoupdate ou le champ AutoUpdate dans podman-systemd.unit(5) avec l'une des deux valeurs suivantes :

  • registry : Si l'étiquette est présente et définie sur registry, Podman contacte le registre correspondant pour vérifier si l'image a été mise à jour. L'étiquette image est une alternative à registry conservée pour des raisons de compatibilité ascendante. Une image est considérée comme mise à jour si le digest dans le stockage local est différent de celui de l'image distante. Si une image doit être mise à jour, Podman la télécharge et redémarre l'unité systemd qui exécute le conteneur. La politique du registre nécessite une référence d'image entièrement qualifiée (par exemple, quay.io/podman/stable:latest) pour créer le conteneur. Cette application est nécessaire pour savoir quelle image vérifier et télécharger. Si un ID d'image était utilisé, Podman ne saurait plus quelle image vérifier/télécharger.
  • local : Si l'étiquette autoupdate est définie sur local, Podman compare le digest de l'image du conteneur à celui du stockage de conteneurs local. S'ils diffèrent, l'image locale est considérée comme plus récente et l'unité systemd est redémarrée.

Mises à jour automatiques et Kubernetes YAML

Podman prend en charge les mises à jour automatiques pour les charges de travail Kubernetes. La politique de mise à jour automatique peut être configurée directement via podman-systemd.unit(5) ou à l'intérieur du YAML Kubernetes avec les annotations spécifiques à Podman mentionnées ci-dessous :

  • io.containers.autoupdate : "registry|local" pour appliquer la politique de mise à jour automatique à tous les conteneurs
  • io.containers.autoupdate/$container : "registry|local" pour appliquer la politique de mise à jour automatique à $container uniquement
  • io.containers.sdnotify : "conmon|container" pour appliquer la politique sdnotify à tous les conteneurs
  • io.containers.sdnotify/$container : "conmon|container" pour appliquer la politique sdnotify à $container uniquement

Par défaut, la politique d'autoupdate est définie sur "disabled", la politique sdnotify est définie sur "conmon".

Unité et timer systemd

Podman est livré avec une unité systemd podman-auto-update.service. Cette unité est déclenchée quotidiennement à minuit par le minuteur systemd podman-auto-update.timer. Le minuteur peut être modifié pour des mises à jour personnalisées basées sur le temps, si désiré. L'unité peut en outre être invoquée par d'autres unités systemd (par exemple, via l'arbre de dépendance) ou manuellement via systemctl start podman-auto-update.service.

OPTIONS

--authfile=chemin

Chemin du fichier d'authentification. Par défaut, il s'agit de ${XDG_RUNTIME_DIR}/containers/auth.json sous Linux, et $HOME/.config/containers/auth.json sous Windows/macOS. Le fichier est créé par podman login. Si l'état d'autorisation n'y est pas trouvé, $HOME/.docker/config.json est vérifié, qui est défini à l'aide de docker login.

Remarque : Il existe également l'option de remplacer le chemin par défaut du fichier d'authentification en définissant la variable d'environnement REGISTRY_AUTH_FILE. Cela peut être fait avec export REGISTRY_AUTH_FILE=chemin.

Alternativement, l'étiquette de conteneur io.containers.autoupdate.authfile peut être configurée. Dans ce cas, Podman utilisera la valeur spécifiée dans l'étiquette.

--dry-run

Vérifie la disponibilité de nouvelles images mais n'effectue aucune opération de téléchargement ni ne redémarre de service ou de conteneur. Le champ UPDATED indique la disponibilité d'une nouvelle image avec "pending".

--format=format

Modifie le format de sortie par défaut. Cela peut être de type supporté comme 'json' ou un modèle Go. Les espaces réservés valides pour le modèle Go sont listés ci-dessous :

Espace réservé Description
.Container ID et nom du conteneur
.ContainerID ID du conteneur
.ContainerName Nom du conteneur
.Image Nom de l'image
.Policy Politique de mise à jour automatique du conteneur
.Unit Nom de l'unité systemd
.Updated Statut de mise à jour : true, false, failed, pending

--rollback

Si le redémarrage d'une unité systemd après la mise à jour de l'image a échoué, revient à utiliser l'image précédente et redémarre l'unité une autre fois. Par défaut, il est activé (true).

Notez que la détection de l'échec d'une unité systemd est mieux effectuée lorsque le conteneur envoie le message READY via SDNOTIFY. Ainsi, le redémarrage de l'unité attend la réception du message ou l'expiration d'un délai. Sans cela, le redémarrage de l'unité systemd peut réussir même si le conteneur a échoué peu après.

Pour qu'un conteneur envoie le message READY via SDNOTIFY, il doit être créé avec l'option --sdnotify=container (voir podman-run(1)). L'application s'exécutant à l'intérieur du conteneur peut alors exécuter systemd-notify --ready lorsqu'elle est prête ou utiliser les liaisons sdnotify du langage de programmation spécifique (par exemple, sd_notify(3)).

--tls-verify

Exiger HTTPS et vérifier les certificats lors du contact avec les registres (par défaut : true). Si explicitement défini sur true, la vérification TLS est utilisée. Si défini sur false, la vérification TLS n'est pas utilisée. Si non spécifié, la vérification TLS est utilisée à moins que le registre cible ne soit listé comme un registre non sécurisé dans containers-registries.conf(5)

EXEMPLES

Créez un fichier Quadlet configuré pour les mises à jour automatiques :

$ cat ~/.config/containers/systemd/sleep.container
[Container]
Image=registry.fedoraproject.org/fedora:latest
Exec=sleep infinity
AutoUpdate=registry

Générez un service systemd à partir du fichier Quadlet en rechargeant le démon utilisateur systemd :

$ systemctl --user daemon-reload

Démarrez le service systemd et assurez-vous que le conteneur est en cours d'exécution

$ systemctl --user start sleep.service
$ podman ps
CONTAINER ID  IMAGE                                     COMMAND         CREATED        STATUS        PORTS       NAMES
f8e4759798d4  registry.fedoraproject.org/fedora:latest  sleep infinity  2 seconds ago  Up 2 seconds              systemd-sleep

Vérifiez si une nouvelle image est disponible via --dry-run :

$ podman auto-update --dry-run --format "{{.Image}} {{.Updated}}"
registry.fedoraproject.org/fedora:latest   pending

Mettez à jour le service :

$ podman auto-update
UNIT           CONTAINER                     IMAGE                                     POLICY      UPDATED
sleep.service  f8e4759798d4 (systemd-sleep)  registry.fedoraproject.org/fedora:latest  registry    true
