potrace(1) Manuel des commandes générales potrace(1)

NOM

potrace - transformer des bitmaps en graphiques vectoriels.

SYNOPSIS

potrace [options] [nom_fichier...]

DESCRIPTION

potrace est un outil pour tracer des bitmaps, c'est-à-dire, transformer une bitmap en une image vectorielle lisse et redimensionnable. L'entrée est une bitmap, c'est-à-dire une image basée sur des pixels composée uniquement des deux couleurs noir et blanc. La sortie est au format SVG, PDF, EPS, ou l'un des nombreux autres formats vectoriels. Une utilisation typique est la création de graphiques vectoriels à partir de données numérisées, tels que des logos d'entreprises ou d'universités, des notes manuscrites, etc. L'image résultante n'est pas "crénelée" comme une bitmap, mais lisse. Elle peut ensuite être rendue à n'importe quelle résolution.

potrace peut lire des bitmaps dans les formats suivants : PBM, PGM, PPM (collectivement connus sous le nom de PNM, voir pnm(5)), ainsi que BMP (formats bitmap Windows et OS/2). L'image d'entrée ne devrait utiliser que les deux couleurs noir et blanc. Si d'autres valeurs de pixels apparaissent dans l'entrée, elles seront converties en noir et blanc à l'aide d'une méthode de seuillage simple.

potrace peut actuellement produire les formats de sortie suivants : SVG, PDF, EPS, PostScript, DXF, GeoJSON, PGM, Gimppath et XFig. D'autres backends pourraient être ajoutés à l'avenir.

OPTIONS

Les options suivantes sont prises en charge. Les dimensions (arguments de type dim) peuvent avoir des unités optionnelles, par exemple 6.5in, 15cm, 100pt. L'unité par défaut est le pouce (ou le centimètre, si cela a été configuré lors de la compilation, voir CONFIGURATION AU MOMENT DE LA COMPILATION ci-dessous). Pour les formats de sortie basés sur des pixels tels que PGM, DXF, GeoJSON et Gimppath, l'unité par défaut est le pixel.

Options générales :

-h, --help
afficher le message d'aide et quitter.
-v, --version
afficher les informations de version et quitter. Ceci montre également les valeurs par défaut qui ont été compilées dans cette version de potrace.
-l, --license
afficher les informations de licence et quitter.

Options d'entrée/sortie :

nom_fichier
Chaque fichier peut contenir une image d'entrée, ou plusieurs images d'entrée concaténées. Si des arguments de nom de fichier sont donnés, alors potrace créera par défaut un fichier de sortie pour chaque nom de fichier d'entrée donné. Le nom du fichier de sortie est obtenu à partir du nom du fichier d'entrée en changeant son extension conformément au backend choisi. Si changer l'extension est impossible car les noms des fichiers d'entrée et de sortie seraient identiques, alors le nom du fichier de sortie est créé en ajoutant le suffixe "-out" au nom du fichier d'entrée. Si aucun argument de nom de fichier n'est donné, alors potrace agit comme un filtre, lisant depuis l'entrée standard et écrivant vers la sortie standard. Un nom de fichier égal à "-" peut être donné pour spécifier la lecture depuis l'entrée standard.
-o nom_fichier, --output nom_fichier
écrire la sortie dans ce fichier. Toute la sortie est dirigée vers le fichier spécifié. Si cette option est utilisée, alors plusieurs noms de fichiers d'entrée ne sont autorisés que pour les backends multi-pages (voir TYPES DE BACKENDS ci-dessous). Dans ce cas, chaque fichier d'entrée peut contenir une ou plusieurs bitmaps, et toutes les bitmaps de tous les fichiers d'entrée sont traitées et la sortie est concaténée en un seul fichier. Un nom de fichier égal à "-" peut être donné pour spécifier l'écriture vers la sortie standard.
--
Fin des options. Tous les arguments restants sont interprétés comme des noms de fichiers. Ceci désactive également le mode filtre, même si aucun nom de fichier n'est donné. Ceci est utile pour les scripts shell, car potrace -- $NOM_FICHIERS se comportera correctement même pour une liste vide de noms de fichiers. Cependant, -- avec une liste vide de noms de fichiers n'est pas autorisé en conjonction avec l'option -o, car cela générerait un document de zéro page, ce que aucun des backends ne permet.

Sélection du backend :

Pour des informations générales, voir également TYPES DE BACKENDS ci-dessous.

-b nom, --backend nom
Sélectionner le backend par nom, où nom est l'un de eps, postscript, ps, pdf, pdfpage, svg, dxf, geojson, pgm, gimppath, xfig. Les noms de backends peuvent être abrégés par un préfixe tant qu'il n'y a pas d'ambiguïté. Les noms de backends ne sont pas sensibles à la casse.
-s, --svg, -b svg, --backend svg
Backend SVG. La sortie est un fichier Scalable Vector Graphics (SVG). C'est un backend à page unique, de taille variable, basé sur des dimensions. Notez que sauf si l'option -r est donnée, la résolution de la bitmap d'entrée est supposée être de 72dpi.
-b pdf, --backend pdf
Backend PDF. La sortie est un fichier au format Portable Document Format. Si l'entrée consiste en plusieurs bitmaps, elles sont chacune rendues sur une page séparée. C'est un backend multi-pages, de taille variable, basé sur des dimensions.
-b pdfpage, --backend pdfpage
Le backend PDFPage est similaire au backend PDF, sauf qu'il est de taille fixe comme le backend PostScript.
-e, --eps, -b eps, --backend eps
Backend EPS (par défaut). La sortie est un fichier encapsulé PostScript. C'est un backend à page unique, de taille variable, basé sur des dimensions.
-p, --postscript, -b ps, --backend ps
Backend PostScript. La sortie est un fichier PostScript. C'est un backend multi-pages, de taille fixe, basé sur des dimensions. Si l'entrée consiste en plusieurs bitmaps, elles sont chacune rendues sur une page séparée.
-b dxf, --backend dxf
Backend DXF. La sortie est un fichier au format Drawing Interchange Format (DXF). Dans ce backend, toutes les courbes de Bézier sont approximées par des arcs circulaires par morceaux ; ceci convient au traitement dans des logiciels de CAO ou pour des applications d'usinage utilisant des outils CNC. C'est un backend à page unique, de taille variable, basé sur des pixels. L'option -u n'a aucun effet pour ce backend.
-b geojson, --backend geojson
Backend GeoJSON. La sortie est un fichier dans le format utilisé par certaines applications traitant des données géographiques. Dans ce backend, toutes les courbes de Bézier sont approximées par 8 segments de ligne droite. C'est un backend à page unique, de taille variable, basé sur des pixels. L'option -u n'a aucun effet pour ce backend.
-g, --pgm, -b pgm, --backend pgm
Backend PGM. La sortie est un fichier portable greymap (PGM). C'est un backend pratique pour l'anti-crénelage d'une image bitmap. C'est un backend multi-pages, de taille variable, basé sur des pixels. Si l'entrée consiste en plus d'une image, les images sont concaténées dans la sortie.
-b gimppath, --backend gimppath
Backend Gimppath. Ce backend produit une sortie adaptée à être importée comme un chemin par le GNU Image Manipulation Program (Gimp) (dans le dialogue Calques, Canaux & Chemins, sélectionner Chemins, puis faire un clic droit et sélectionner Importer Chemin). La sortie est en fait un fichier SVG. Les différences avec le backend SVG sont : l'option --opaque n'a aucun effet, l'option --flat est toujours activée, et les dimensions sont basées sur des pixels. C'est un backend à page unique, de taille variable, basé sur des pixels.
-b xfig, --backend xfig
Backend XFig. C'est un backend à page unique, de taille fixe, basé sur des dimensions. La sortie est un fichier au format XFig. Notez que XFig utilise des X-splines au lieu de courbes de Bézier, il n'est donc pas possible de traduire la sortie de potrace en format XFig avec une précision absolue. Ce backend fait une approximation raisonnable en utilisant deux points de contrôle pour chaque segment de courbe de Bézier. L'option -u n'a aucun effet pour ce backend, car les points de contrôle sont toujours arrondis au plus proche 1/1200 de pouce dans XFig. L'optimisation des courbes est désactivée. Implique --opaque.

-z politique, --turnpolicy politique
spécifie comment résoudre les ambiguïtés dans la décomposition des chemins. Doit être l'un des suivants : noir, blanc, droite, gauche, minorité, majorité ou aléatoire. La valeur par défaut est minorité. Les politiques de virage peuvent être abrégées par un préfixe non ambigu, par exemple, on peut spécifier min au lieu de minorité.
-t n, --turdsize n
supprime les points de détail jusqu'à ce nombre de pixels.
-a n, --alphamax n
définit le paramètre de seuil de coin. La valeur par défaut est 1. Plus cette valeur est petite, plus les coins seront nets. Si ce paramètre est de 0, alors aucun lissage ne sera effectué et la sortie est un polygone. Si ce paramètre est supérieur à 4/3, alors tous les coins sont supprimés et la sortie est complètement lisse.
-n, --longcurve
désactive l'optimisation des courbes. Normalement, potrace essaie de joindre les segments de courbe de Bézier adjacents lorsque cela est possible. Cette option désactive ce comportement, ce qui entraîne une taille de fichier plus grande.
-O n, --opttolerance n
définit la tolérance d'optimisation des courbes. La valeur par défaut est 0.2. Des valeurs plus grandes permettent de joindre plus de segments de courbe de Bézier consécutifs en un seul segment, au détriment de la précision.
-u n, --unit n
définit la quantification de la sortie. Les coordonnées en sortie sont arrondies à 1/unité de pixels. La valeur par défaut de 10 donne généralement de bons résultats. Pour certains modes de débogage, une valeur de 100 donne une sortie plus précise. Cette option n'a aucun effet pour le backend XFig, qui rasterise toujours à 1/1200 pouce, ni pour le backend DXF. Pour le backend GeoJSON, cette option est seulement une indication ; l'arrondi réel peut être plus, mais pas moins, précis que spécifié.
-d n, --debug n
produit une sortie de débogage de type n. Cela a des effets différents selon les backends. Pour les backends PostScript/EPS, les valeurs n=1,2,3 illustrent les étapes intermédiaires de l'algorithme de potrace.

Options de mise à l\'échelle et de placement :

-P format, --pagesize format
pour les backends de taille fixe, définit la taille de la page. Les formats suivants peuvent être spécifiés : A4, A3, A5, B5, Letter, Legal, Tabloid, Statement, Executive, Folio, Quarto, 10x14. Les noms de format ne sont pas sensibles à la casse. De plus, un argument de la forme dimxdim est accepté pour spécifier des dimensions arbitraires. La taille de page par défaut est Letter (ou A4, si cela a été configuré à la compilation, voir CONFIGURATION À LA COMPILATION ci-dessous). Les noms de format de page peuvent être abrégés par un préfixe tant qu'il est non ambigu. Cette option n'a aucun effet pour les backends de taille variable.
-W dim, --width dim
définit la largeur de l'image de sortie (avant toute rotation et marges). Si une seule des dimensions largeur et hauteur est spécifiée, l'autre est ajustée en conséquence afin de préserver le rapport d'aspect.
-H dim, --height dim
définit la hauteur de l'image de sortie. Voir -W pour les détails.
-r n[xn], --resolution n[xn]
pour les backends basés sur les dimensions, définit la résolution (en dpi). Un pouce dans l'image de sortie correspond à ce nombre de pixels dans l'entrée. Notez qu'une valeur plus grande entraîne une image de sortie plus petite. Il est possible de spécifier des résolutions distinctes dans les directions x et y en donnant un argument de la forme nxn. Pour les backends de taille variable, la résolution par défaut est 72 dpi. Pour les backends de taille fixe, il n'y a pas de résolution par défaut ; l'image est par défaut mise à l'échelle pour tenir sur la page. Cette option n'a aucun effet pour les backends basés sur les pixels. Si -W ou -H sont spécifiés, ils ont la priorité.
-x n[xn], --scale n[xn]
pour les backends basés sur les pixels, définit le facteur de mise à l'échelle. Une valeur supérieure à 1 agrandit la sortie, une valeur comprise entre 0 et 1 réduit la sortie. La valeur par défaut est 1. Il est possible de spécifier des facteurs de mise à l'échelle distincts pour les directions x et y en donnant un argument de la forme nxn. Cette option n'a aucun effet pour les backends basés sur les dimensions. Si -W ou -H sont spécifiés, ils ont la priorité.
-S n, --stretch n
définit le rapport d'aspect. Une valeur supérieure à 1 signifie que l'image sera étirée dans la direction y. Une valeur comprise entre 0 et 1 signifie que l'image sera compressée dans la direction y.
-A angle, --rotate angle
définit l'angle de rotation (en degrés). La sortie sera tournée dans le sens antihoraire de cet angle. Ceci est utile pour compenser les images qui ont été numérisées de manière pas tout à fait droite.
-M dim, --margin dim
définit les quatre marges. L'effet et la valeur par défaut de cette option dépendent du backend. Pour les backends de taille variable, les marges seront simplement ajoutées autour de l'image de sortie (ou soustraites, en cas de marges négatives). La marge par défaut pour ces backends est 0. Pour les backends de taille fixe, les paramètres de marge peuvent être utilisés pour contrôler le placement de l'image sur la page. Si une seule des marges gauche et droite est donnée, l'image sera placée à cette distance du bord respectif de la page, et de même pour le haut et le bas. Si des marges sont données sur des côtés opposés, l'image est mise à l'échelle pour tenir entre ces marges, sauf si la mise à l'échelle est déjà déterminée explicitement par une ou plusieurs des options -W, -H, -r ou -x. Par défaut, les backends de taille fixe utilisent une marge non nulle dont la largeur dépend de la taille de la page.
-L dim, --leftmargin dim
définit la marge gauche. Voir -M pour les détails.
-R dim, --rightmargin dim
définit la marge droite. Voir -M pour les détails.
-T dim, --topmargin dim
définit la marge supérieure. Voir -M pour les détails.
-B dim, --bottommargin dim
définit la marge inférieure. Voir -M pour les détails.
--tight
supprime l'espace blanc autour de l'image avant l'application de la mise à l'échelle et des marges. Si cette option est donnée, les calculs de la largeur, de la hauteur et des marges sont basés sur le contour vectoriel réel, plutôt que sur les dimensions extérieures de la pixmap d'entrée, ce qui est le comportement par défaut. En particulier, l'option --tight peut être utilisée pour supprimer toutes les marges existantes de l'image d'entrée. Voir le fichier placement.pdf pour une illustration plus détaillée.

Options de couleur :

Ces options ne sont prises en charge que par certains backends. Les backends DXF et GeoJSON ne prennent pas en charge la couleur.

-C #rrggbb, --color #rrggbb
définit la couleur de premier plan de l'image de sortie. La valeur par défaut est noir.
--fillcolor #rrggbb
définit la couleur de remplissage de l'image de sortie, c'est-à-dire la couleur des parties "blanches" qui sont délimitées par des parties "noires". La valeur par défaut est de laisser ces parties transparentes. Implique --opaque. Veuillez noter que cette option définit la couleur d'arrière-plan ; pour définir la couleur de premier plan, utilisez --color à la place.
--opaque
remplit les parties blanches de l'image de manière opaque, au lieu de les laisser transparentes. Ceci s'applique uniquement aux parties blanches intérieures, c'est-à-dire celles qui sont enfermées dans un contour noir. L'opacité est toujours appliquée pour le backend XFig.

Options SVG :

--group
pour la sortie SVG, essaie de regrouper les chemins connexes. Chaque chemin est regroupé avec tous les chemins qui sont contenus à l'intérieur, afin qu'ils puissent être déplacés comme une unité avec un éditeur SVG. Cela rend la coloration des composants individuels légèrement plus compliquée, et donc ce n'est pas la valeur par défaut.
--flat
pour la sortie SVG, place l'image entière dans un seul chemin. Cela rend impossible la coloration individuelle des composants, et donc ce n'est pas la valeur par défaut. Mais le fichier SVG résultant peut être plus facilement importé par certaines applications comme Gimp. En fait, le backend Gimppath est une variation du backend SVG avec l'option --flat et une mise à l'échelle basée sur les pixels. L'option --flat n'a aucun effet si --opaque a été sélectionné.

Options PostScript/EPS/PDF :

-c, --cleartext
ne compresse pas la sortie. Cette option désactive l'utilisation des filtres de compression dans la sortie PostScript et PDF. Dans le backend PostScript, si -c et -q sont utilisés ensemble, la sortie résultante peut être facilement lue par d'autres programmes ou même par des humains.
-2, --level2
utilise la compression PostScript niveau 2 (par défaut). La taille de fichier résultante est d'environ 40 % inférieure à celle obtenue avec l'option -c.
-3, --level3
utilise la compression PostScript niveau 3, si disponible. Cela permet d'obtenir des fichiers légèrement plus petits qu'avec -2, mais les fichiers résultants peuvent ne pas s'imprimer sur d'anciennes imprimantes PostScript niveau 2. Si la prise en charge de la compression PostScript niveau 3 a été désactivée à la compilation, un message d'avertissement est affiché et la compression niveau 2 est utilisée à la place.
-q, --longcoding
désactive le codage numérique optimisé dans la sortie PostScript. Normalement, potrace utilise un format numérique très compact pour représenter les courbes de Bézier en PostScript, en tirant parti de la redondance existante dans les paramètres des courbes. OPTIONS

The command line options are:

-c [color], --clip [color]
clip the output to the bounds of the largest path. If a color name (e.g. red) is specified, only paths of that color are included in the clip. The special color name all is ignored. This option is mainly useful for debugging and for making more readable output (particularly if the -c option is also used).

Options PGM :

-G n, --gamma n
définir la valeur gamma pour l'anti-aliasing (par défaut 2.2). La plupart des écrans d'ordinateur ne rendent pas les nuances de gris linéairement, c'est-à-dire qu'une valeur de gris de 0,5 n'est pas affichée comme étant exactement à mi-chemin entre le noir et le blanc. Le paramètre gamma corrige cela, et conduit donc à un rendu plus agréable. La valeur par défaut de 2,2 est appropriée pour la plupart des écrans CRT normaux.

Options Frontend :

-k n, --blacklevel n
définir le seuil pour la conversion des images d'entrée en bitmaps. L'algorithme potrace attend un bitmap, donc tous les pixels des images d'entrée sont convertis en noir ou blanc avant que le traitement ne commence. Les pixels dont la luminosité est inférieure à n sont convertis en noir, tous les autres pixels en blanc. Ici n est un nombre compris entre 0 et 1. Un cas est traité spécialement : si l'entrée est dans un format de couleur indexé avec exactement 2 couleurs, alors le niveau de noir est ignoré et la plus sombre des deux couleurs est mappée au noir.

Note : la méthode utilisée par potrace pour convertir les greyscales en bitmaps est très rudimentaire ; de bien meilleurs résultats peuvent être obtenus si un programme séparé, tel que mkbitmap(1), est utilisé à cette fin. En particulier, mkbitmap(1), qui est distribué avec potrace, a la capacité de mettre à l'échelle et d'interpoler l'image avant le seuillage, ce qui permet une bien meilleure préservation des détails.

-i, --invert
inverser le bitmap d'entrée avant le traitement.

Options Barre de progression :

--progress
afficher une barre de progression pour chaque bitmap traité. Ceci est utile pour une utilisation interactive. Le comportement par défaut est de ne pas afficher d'informations de progression.
--tty mode
définir le mode de terminal pour le rendu de la barre de progression. Les valeurs possibles sont "vt100", qui nécessite un terminal compatible vt100, et "dumb", qui n'utilise que des caractères ASCII. La valeur par défaut dépend du système.

TYPES DE BACKEND

Les backends peuvent être classés de plusieurs manières, ce qui affecte les options de ligne de commande disponibles et leur comportement :

Taille fixe ou taille variable :
Pour les backends de taille fixe, la taille de la page est toujours la même (par exemple Lettre ou A4, comme spécifié à la compilation ou par l'option -P). Par défaut, l'image sera centrée et mise à l'échelle pour s'adapter à la taille de la page. Pour les backends de taille variable, la taille de la page suit la taille de l'image. Actuellement, les backends PostScript (PS), PDFPage et XFig sont de taille fixe, et les backends restants sont de taille variable.
Basé sur les dimensions ou basé sur les pixels :
Dans les backends basés sur les dimensions, les distances sont mesurées en unités physiques telles que les pouces ou les centimètres. Dans les backends basés sur les pixels, les distances sont mesurées en unités de pixels. L'option -r ne fonctionne que pour les backends basés sur les dimensions, et l'option -x ne fonctionne que pour les backends basés sur les pixels. Actuellement, les backends DXF, PGM, Gimppath et GeoJSON sont basés sur les pixels, et les backends restants sont basés sur les dimensions. Actuellement, tous les backends basés sur les pixels sont de taille variable.
Page unique ou multipage :
Les backends à page unique ne peuvent accepter qu'une seule image. Les backends multipages peuvent accepter plusieurs images, généralement une par page de sortie. Actuellement, les backends PostScript (PS), PDF, PDFPage et PGM sont multipages, et les backends restants sont à page unique. Notez que plusieurs images d'entrée peuvent être lues de deux manières : à partir de plusieurs fichiers d'entrée (avec l'option -o), ou à partir d'un seul fichier d'entrée contenant plusieurs images concaténées.

CONFIGURATION A LA COMPILATION

Certains aspects du comportement de potrace peuvent être configurés à la compilation en passant les options suivantes au script ./configure.

--disable-zlib
compiler potrace sans la bibliothèque de compression zlib. Cela signifie que la compression de niveau 3 PostScript ne sera pas disponible.
--enable-metric
compiler potrace avec les centimètres comme unité par défaut au lieu des pouces.
--enable-a4
compiler potrace avec A4 comme taille de page par défaut.

ETAT DE SORTIE

L'état de sortie est 0 en cas de succès, 1 si la ligne de commande était invalide, et 2 en cas de toute autre erreur.
