L' ARCHITECTURE

Polly est un optimiseur de boucles pour LLVM. À partir de LLVM-IR, il détecte et extrait les noyaux de boucles intéressants. Pour chaque noyau, un modèle mathématique est dérivé, qui décrit précisément les calculs individuels et les accès mémoire dans les noyaux. Au sein de Polly, une variété d'analyses et de transformations de code sont effectuées sur ce modèle mathématique. Une fois toutes les optimisations dérivées et appliquées, un LLVM-IR optimisé est régénéré et inséré dans le module LLVM-IR. [image]

Polly dans le pipeline de passes LLVM

Le pipeline de passes LLVM standard tel qu'utilisé dans le mode -O1/-O2/-O3 de clang/opt consiste en une séquence de passes qui peuvent être regroupées en différentes phases conceptuelles. La première phase, que nous appelons ici Canonicalisation, est une phase de canonicalisation scalaire qui contient des passes telles que -mem2reg, -instcombine, -cfgsimplify, ou le déroulement précoce de boucles. Elle a pour but de supprimer et de simplifier l'IR donné autant que possible, en se concentrant principalement sur les optimisations scalaires. La deuxième phase consiste en trois groupes conceptuels exécutés dans le soi-disant cycle d'inlining. Il s'agit à nouveau d'un ensemble de passes de Simplification Scalaire, d'un ensemble d'Optimisations de Boucles Simples, et de l'Inliner lui-même. Bien que ces passes constituent la majorité du pipeline de passes LLVM, l'objectif principal de ces passes reste la canonicalisation sans perte d'informations sémantiques qui compliquent les analyses ultérieures. Dans le cadre du cycle d'inlining, l'étape d'inlining de LLVM tente étape par étape d'inliner des fonctions, exécute des passes de canonicalisation pour exploiter les nouvelles opportunités de simplification exposées, puis tente d'inliner les fonctions davantage simplifiées. Certaines optimisations de boucles simples sont exécutées dans le cadre du cycle d'inlining. Bien qu'elles effectuent certaines optimisations, leur objectif principal reste la simplification du code du programme. Le mouvement de code invariant de boucle est une telle optimisation qui, en plus d'être bénéfique pour les performances du programme, nous permet de déplacer les calculs hors des boucles et, dans le meilleur des cas, d'éliminer complètement certaines boucles. Ce n'est qu'après la fin du cycle d'inlining qu'une dernière phase de Spécialisation de Cible est exécutée, où la complexité de l'IR est délibérément augmentée pour tirer parti des fonctionnalités spécifiques à la cible qui maximisent les performances d'exécution sur l'appareil visé. L'une des optimisations principales de cette phase est la vectorisation, mais aussi le déroulement de boucles spécifiques à la cible, ou certaines transformations de boucles (par exemple, la distribution) qui exposent davantage d'opportunités de vectorisation. [image]

Polly peut conceptuellement être exécuté à trois positions différentes dans le pipeline de passes. Comme optimiseur précoce avant le pipeline de passes LLVM standard, comme optimiseur tardif dans le cadre de la séquence de spécialisation de cible, et théoriquement aussi avec les optimisations de boucles dans le cycle d'inlining. Nous ne discutons que des deux premières options, car l'exécution de Polly dans la boucle d'inlining est susceptible de perturber l'inliner et n'est par conséquent pas une bonne idée. [image]

Exécuter Polly tôt avant le pipeline de passes standard présente l'avantage que le LLVM-IR traité par Polly est encore très proche du code d'origine. Par conséquent, il est moins probable que les transformations appliquées par LLVM modifient l'IR d'une manière facilement compréhensible par le programmeur. En conséquence, le feedback utilisateur est probablement meilleur et il est moins probable que des noyaux qui, en C, semblent parfaitement adaptés à Polly aient été transformés de telle sorte que Polly ne puisse plus les gérer. D'un autre côté, les codes qui nécessitent l'inlining pour être optimisés ne bénéficieront pas si Polly est planifié à cette position. L'ensemble supplémentaire de passes de canonicalisation requises entraînera une légère mais générale augmentation du temps de compilation et quelques changements aléatoires des performances d'exécution dus à un IR légèrement différent passant par les optimiseurs. Pour forcer Polly à s'exécuter tôt dans le pipeline de passes, utilisez l'option -polly-position=early (par défaut aujourd'hui). [image]

Exécuter Polly juste avant le vectoriseur présente l'avantage que tout le cycle d'inlining a été exécuté et, par conséquent, même le code C++ fortement templatisé pourrait théoriquement bénéficier de Polly (plus de travail est nécessaire pour rendre Polly réellement efficace ici). Comme l'IR qui est passé à Polly a déjà été canonicalisé, il n'est pas non plus nécessaire d'exécuter des passes de canonicalisation supplémentaires. Le temps de compilation général est presque pas affecté par Polly, car la détection des noyaux de boucles est généralement très rapide et les passes d'optimisation et de nettoyage réelles ne sont exécutées que sur les fonctions contenant des noyaux de boucles qui valent la peine d'être optimisés. Cependant, en raison des nombreuses optimisations qu'exécute LLVM avant Polly, l'IR qui atteint Polly a souvent des dépendances scalaires supplémentaires qui rendent Polly beaucoup moins efficace. Pour forcer Polly à s'exécuter avant le vectoriseur dans le pipeline de passes, utilisez l'option -polly-position=before-vectorizer. Cette position n'est pas encore le défaut pour Polly, mais des travaux sont en cours pour le rendre efficace même en présence de dépendances scalaires. Une fois ces travaux terminés, Polly utilisera probablement cette position par défaut. [image]

UTILISER POLLY AVEC CLANG

Cette documentation explique comment Polly peut être utilisé dans Clang pour optimiser automatiquement le code C/C++ lors de la compilation.

Attention :

Attention : clang/LLVM/Polly doivent être synchronisés (compilés à partir de la même révision).

Rendre Polly disponible depuis Clang

Polly est disponible via clang, opt et bugpoint, si Polly a été extrait dans tools/polly avant la compilation. Aucune configuration supplémentaire n'est nécessaire.

Optimisation avec Polly

Optimiser avec Polly est aussi simple que d'ajouter -O3 -mllvm -polly à vos indicateurs de compilateur (Polly n'est pas disponible à moins que les optimisations ne soient activées, comme -O1,-O2,-O3 ; l'optimisation pour la taille avec -Os ou -Oz n'est pas recommandée).

clang -O3 -mllvm -polly fichier.c

Génération automatique de code OpenMP

Pour détecter automatiquement les boucles parallèles et générer du code OpenMP pour elles, vous devez également ajouter -mllvm -polly-parallel -lgomp à vos CFLAGS.

clang -O3 -mllvm -polly -mllvm -polly-parallel -lgomp fichier.c

Changement du backend OpenMP

Le commutateur CL suivant permet de choisir le backend OpenMP de Polly :

-polly-omp-backend[=BACKEND]
choisir le backend OpenMP ; BACKEND peut être 'GNU' (par défaut) ou 'LLVM' ;

Les backends OpenMP peuvent être davantage influencés en utilisant les commutateurs CL suivants :

-polly-num-threads[=NUM]
définir le nombre de threads à utiliser ; NUM peut être n'importe quel entier positif (par défaut : 0, ce qui équivaut à automatique/runtime OMP) ;
-polly-scheduling[=SCHED]
définir le type de planification OpenMP ; SCHED peut être 'static', 'dynamic', 'guided' ou 'runtime' (par défaut) ;
-polly-scheduling-chunksize[=CHUNK]
définir la taille du bloc (pour le type de planification sélectionné) ; CHUNK peut être n'importe quel entier strictement positif (sinon, il sera par défaut à 1) ;

Notez qu'au moment de la rédaction, le backend GNU ne peut utiliser que les commutateurs polly-num-threads et polly-scheduling, ce dernier devant également être réglé sur "runtime".

Exemple : Utiliser un backend alternatif avec planification dynamique, quatre threads et une taille de bloc de un (commutateurs supplémentaires).

-mllvm -polly-omp-backend=LLVM -mllvm -polly-num-threads=4
-mllvm -polly-scheduling=dynamic -mllvm -polly-scheduling-chunksi

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

Génération automatique de code vectoriel

La génération automatique de code vectoriel peut être activée en ajoutant -mllvm -polly-vectorizer=stripmine à vos CFLAGS.

clang -O3 -mllvm -polly -mllvm -polly-vectorizer=stripmine file.c

Isoler les passes de Polly

Les passes d'analyse et de transformation de Polly sont exécutés avec de nombreux autres passes du pipeline du gestionnaire de passes. Certains des passes qui s'exécutent avant Polly sont essentiels à son fonctionnement, par exemple la canonisation de la boucle. Par conséquent, Polly est incapable d'optimiser le code directement à partir de la sortie -O0 de clang.

Pour obtenir l'IR LLVM que Polly voit dans le pipeline d'optimisation, utilisez la commande :

clang file.c -c -O3 -mllvm -polly -mllvm -polly-dump-before-file=before-polly.ll

Ceci écrit un fichier 'before-polly.ll' contenant l'IR LLVM tel que transmis à Polly, après la transformation SSA, la canonisation de la boucle, l'inlining et d'autres passes.

Ensuite, n'importe quel passe de Polly peut être exécuté sur 'before-polly.ll' en utilisant l'outil 'opt'. Pour savoir quels passes de Polly sont actifs dans le pipeline standard, voir la sortie de

clang file.c -c -O3 -mllvm -polly -mllvm -debug-pass=Arguments

Les passes de Polly sont ceux situés entre '-polly-detect' et '-polly-codegen'. Les passes d'analyse peuvent être omis. Au moment de la rédaction, le pipeline de passes par défaut de Polly est :

opt before-polly.ll -polly-simplify -polly-optree -polly-delicm -polly-simplify -polly-prune-unprofitable -polly-opt-isl -polly-codegen

Notez que cela utilise l'ancien gestionnaire de passes de LLVM.

Pour plus de complétude, voici d'autres méthodes qui génèrent de l'IR adapté au traitement par Polly à partir de code source C/C++/Objective C. La méthode précédente est celle recommandée.

La commande suivante génère une IR LLVM non optimisée ('-O0', qui est la valeur par défaut) et exécute les passes de canonisation dessus ('-polly-canonicalize'). Cela n'inclut pas tous les passes qui s'exécutent avant Polly dans le pipeline de passes par défaut. L'option '-disable-O0-optnone' est requise car sinon clang ajoute un attribut 'optnone' à toutes les fonctions de sorte qu'elles soient ignorées par la plupart des passes d'optimisation. Ceci est destiné à empêcher LTO de compiler ces fonctions lors de la phase de liaison.

clang file.c -c -O0 -Xclang -disable-O0-optnone -emit-llvm -S -o - | opt -polly-canonicalize -S

L'option '-disable-llvm-passes' désactive tous les passes LLVM, même ceux qui s'exécutent à -O0. Passer -O1 (ou tout niveau d'optimisation autre que -O0) évite que l'attribut 'optnone' soit ajouté.

clang file.c -c -O1 -Xclang -disable-llvm-passes -emit-llvm -S -o - | opt -polly-canonicalize -S

Comme autre alternative, Polly peut être placé en tête du pipeline de passes, puis sa sortie déversée. Cela exécute implicitement les passes '-polly-canonicalize'.

clang file.c -c -O3 -mllvm -polly -mllvm -polly-position=early -mllvm -polly-dump-before-file=before-polly.ll

Autres options

Polly prend en charge des options supplémentaires qui sont principalement utiles pour le développement ou l'analyse de Polly. Les options pertinentes peuvent être ajoutées à clang en ajoutant -mllvm -option-name aux CFLAGS ou à la ligne de commande clang.

Limiter Polly à une seule fonction

Pour limiter l'exécution de Polly à une seule fonction, utilisez l'option -polly-only-func=nom_fonction.

Désactiver la génération d'IR LLVM

Polly régénère normalement l'IR LLVM à partir de la représentation polyédrique. Pour voir uniquement les effets des transformations préparatoires, mais pour désactiver la génération de code de Polly, ajoutez l'option polly-no-codegen.

Vue graphique des SCoPs

Polly peut utiliser graphviz pour afficher les SCoPs qu'il détecte dans un programme. Les options pertinentes sont -polly-show, -polly-show-only, -polly-dot et -polly-dot-only. Les options 'show' exécutent automatiquement dotty ou un autre visualiseur graphviz pour montrer les scops graphiquement. Les options 'dot' stockent pour chaque fonction un fichier dot qui met en évidence les SCoPs détectés. Si 'only' est ajouté à la fin de l'option, les blocs de base sont affichés sans les instructions qu'ils contiennent.

Changer/Désactiver l'Optimiseur

Polly utilise par défaut l'optimiseur de planification isl. L'optimiseur isl optimise la localité des données et le parallélisme en utilisant l'algorithme Pluto. Pour désactiver complètement l'optimiseur, utilisez l'option -polly-optimizer=none.

Désactiver le tiling dans l'optimiseur

Par défaut, les deux optimiseurs effectuent du tiling, si possible. Si ce n'est pas souhaité, l'option -polly-tiling=false peut être utilisée pour le désactiver. (Cette option désactive le tiling pour les deux optimiseurs).

Import / Export

Les indicateurs -polly-import et -polly-export permettent l'exportation et la réimportation de la représentation polyédrique. En exportant, modifiant et réimportant la représentation polyédrique, des transformations calculées en externe peuvent être appliquées. Cela permet des optimiseurs externes ou l'optimisation manuelle de SCoPs spécifiques.

Visualiser les diagnostics de Polly avec opt-viewer

L'indicateur -fsave-optimization-record générera des fichiers .opt.yaml lors de la compilation de votre programme. Ces fichiers yaml contiennent des informations sur chaque remarque émise. Assurez-vous d'avoir Python 2.7 avec les packages Python PyYaml et Pygments. Pour exécuter opt-viewer :

llvm/tools/opt_viewer/opt_viewer.py -source-dir /chemin/vers/programme/src/ \
   /chemin/vers/programme/src/foo.opt.yaml \
   /chemin/vers/programme/src/bar.opt.yaml \
   -o ./output

Incluez tous les fichiers yaml (utilisez *.opt.yaml lors de la spécification des fichiers yaml à visualiser) pour voir tous les diagnostics de votre programme dans opt-viewer. Compilez avec PGO https://clang.llvm.org/docs/UsersManual.html#profiling-with-instrumentation pour visualiser les informations de Hotness dans opt-viewer. Les fichiers html résultants peuvent être visualisés dans un navigateur Internet.

Exécuter manuellement les passes individuels de Polly

Cet exemple présente les passes individuels impliqués lors de l'optimisation de code avec Polly. Nous montrons comment les exécuter individuellement et expliquons pour chacun quelle analyse est effectuée ou quelle transformation est appliquée. Dans cet exemple, la transformation polyédrique est fournie par l'utilisateur pour montrer l'amélioration des performances attendue par un optimiseur automatique optimal.

1. Créer l'IR_LLVM à partir du code C

Polly travaille sur l'IR LLVM. Il est donc nécessaire de traduire les fichiers source en IR LLVM. Si plus d'un fichier doit être optimisé, les fichiers peuvent être combinés en un seul fichier avec llvm-link. 
clang -S -emit-llvm matmul.c -Xclang -disable-O0-optnone -o matmul.ll

2. Préparer l'IR_LLVM pour Polly

Polly ne peut travailler qu'avec du code qui correspond à une forme canonique. Pour traduire l'IR LLVM dans cette forme, nous utilisons un ensemble de passes de canonisation. Ils sont programmés en utilisant '-polly-canonicalize'. 
opt -S -polly-canonicalize matmul.ll -o matmul.preopt.ll

3. Afficher les SCoPs détectés par Polly (optionnel)

Pour comprendre si Polly a réussi à détecter des SCoPs, nous imprimons la structure des SCoPs détectés. Dans notre exemple, deux SCoPs sont détectés. L'un dans 'init_array' et l'autre dans 'main'. 
$ opt -basic-aa -polly-ast -analyze matmul.preopt.ll -polly-process-unprofitable -polly-use-llvm-names

4. Surligner les SCoPs détectés dans les CFG du programme (nécessite graphviz/dotty)

Polly peut utiliser graphviz pour montrer graphiquement un CFG dans lequel les SCoPs détectés sont mis en évidence. Il peut également créer des fichiers '.dot' qui peuvent être traduits par l'utilitaire 'dot' dans divers formats graphiques. 
$ opt -polly-use-llvm-names -basic-aa -view-scops -disable-output matmul.preopt.ll
$ opt -polly-use-llvm-names -basic-aa -view-scops-only -disable-output matmul.preopt.ll

8. Importer les fichiers jscop modifiés et afficher la structure SCoP mise à jour (optionnel)

Polly peut réimporter des fichiers jscop, dans lesquels les ordonnancements des instructions sont modifiés. Ces ordonnancements modifiés sont utilisés pour décrire des transformations. Il est possible d'importer différents fichiers jscop en fournissant le suffixe du fichier jscop qui est importé.

Nous appliquons trois transformations différentes sur le SCoP dans la fonction main. Les fichiers jscop décrivant ces transformations sont écrits à la main (et disponibles dans docs/experiments/matmul).

Aucun Polly

Comme référence, nous n'appelons aucun code de génération Polly, mais appliquons uniquement les optimisations -O3 normales.

NAME

polly - Automatic parallelization and optimization framework

RELEASE NOTES RELEASE NOTES

The user is expected to refer to the upstream release notes for details on the latest changes and features.

The user is also referred to the LLVM release notes, as Polly is part of LLVM.

THE ARCHITECTURE

Polly is a polyhedral optimization framework for the LLVM compiler infrastructure. It operates on the Static Single Assignment (SSA) form of programs and extracts programs from the Static Control Flow Graph (SCFG) representation of the program, and then analyzes and transforms the program in the polyhedral model. Polly is designed to support arbitrary loop nests, including do-while loops, that operate on static arrays. It is also capable of optimizing programs that contain arbitrary control flow constructs, such as if-then-else statements, or function calls.

The polyhedral model can represent computations that exhibit regular data access patterns and control flow. In the polyhedral model, iterations of loops are represented as integer points in a multi-dimensional space, and the dependencies between these iterations are captured by transformations on these integer points. This allows for powerful analysis and transformation techniques, such as loop interchange, loop tiling, and loop skewing, which can significantly improve memory access patterns and parallelism.

Polly implements the polyhedral model using a set of interconnected components:

•
Region Inflection: Polly identifies regions of code that can be represented in the polyhedral model. This involves analyzing the control flow graph and identifying loop nests and static array accesses.
•
SCFG Construction: The identified regions are converted into the Static Control Flow Graph (SCFG) representation, which captures the control flow and data dependencies within the region.
•
Polyhedral Representation: The SCFG is then transformed into a polyhedral representation, where loop iterations are represented as integer points in a multi-dimensional space, and dependencies are captured by affine transformations.
•
Schedule Generation: Polly generates a new schedule for the polyhedral representation, which can reorder loop iterations to improve locality and parallelism. This is done by applying various scheduling heuristics and optimization techniques.
•
Code Generation: Finally, Polly generates optimized LLVM intermediate representation (IR) code from the transformed polyhedral representation.

Polly's architecture allows it to be integrated seamlessly into the LLVM compiler infrastructure. It can be invoked as a compiler pass, and its optimizations can be combined with other LLVM optimization passes.

USING POLLY WITH CLANG

To use Polly with Clang, you need to compile LLVM and Clang with Polly enabled. This is typically done by passing the -enable-polly flag to the CMake configuration script when building LLVM.

Once LLVM and Clang are built with Polly support, you can use Polly by passing the -polly flag to the Clang compiler. For example:

$ clang -O3 -polly your_code.c -o your_program

The -O3 flag enables the default optimization level, which includes Polly optimizations. You can also explicitly enable Polly by adding -polly to the list of optimization flags.

Polly can be combined with other optimization passes. You can control the specific Polly passes that are enabled by using the -polly-* flags. For example, to enable the loop tiling pass, you can use -polly-tiling.

To see a list of all available Polly passes, you can use the -polly-help flag:

$ clang -polly-help

Polly can also be used to automatically parallelize code. To enable automatic parallelization, use the -polly-parallel flag:

$ clang -O3 -polly -polly-parallel your_code.c -o your_program

This flag instructs Polly to generate parallel code by exploiting loop-level parallelism. The generated code may use threading libraries like OpenMP or pthreads, depending on the underlying LLVM configuration.

HOW TO MANUALLY USE THE INDIVIDUAL PIECES OF POLLY

While clang -polly is the recommended way to use Polly, you can also invoke its individual components manually using the opt tool. This can be useful for debugging or for more fine-grained control over the optimization process.

The primary tool for running LLVM optimization passes is opt. You can use it to run Polly passes on LLVM IR files.

First, you need to compile your source code to LLVM IR. For example, using Clang:

$ clang -O3 -emit-llvm your_code.c -S -o your_code.ll

Then, you can use opt to apply Polly optimizations. To run all Polly passes, you can use:

$ opt -O3 -load /path/to/polly/libPolly.so -polly -S your_code.ll -o your_code.polly.ll

Replace /path/to/polly/libPolly.so with the actual path to the Polly shared library. The -load option loads the dynamic library containing Polly, and -polly enables the main Polly pass. The -S flag ensures the output is in LLVM IR assembly format.

You can also run individual Polly passes. For example, to only run the loop tiling pass:

$ opt -O3 -load /path/to/polly/libPolly.so -polly-tiling -S your_code.ll -o your_code.tiled.ll

To see a list of all available passes that can be run with opt, you can use:

$ opt -help

This will list all standard LLVM passes, including those provided by Polly (which usually start with polly-).

If you suspect a specific pass is causing an issue or incorrect optimization, you can use the bugpoint tool to help isolate the problematic pass. For instance, if a specific optimization flag causes a crash:

•
$ bugpoint -O3 file.ll -opt-args -polly will allow bugpoint to track down the pass which causes the crash.

To do this manually:

  • $ opt -O3 -polly -debug-pass=Arguments to get all passes that are run by default. -debug-pass=Arguments will list all passes that have run.
  • Bisect down to the pass that changes it.

Debugging regressions introduced at some unknown earlier point

In case of a regression in performance or correctness (e.g., an earlier version of Polly behaved as expected and a later version does not), bisecting over the version history is the standard approach to identify the commit that introduced the regression.

LLVM has a single repository that contains all projects. It can be cloned at: https://github.com/llvm/llvm-project. How to bisect on a git repository is explained here https://www.metaltoad.com/blog/beginners-guide-git-bisect-process-elimination. The bisect process can also be automated as explained here: https://www.metaltoad.com/blog/mechanizing-git-bisect-bug-hunting-lazy. An LLVM specific run script is available here: https://gist.github.com/dcci/891cd98d80b1b95352a407d80914f7cf.

High-Performance Generalized Matrix Multiplication

Polly automatically detects and optimizes generalized matrix multiplication, the computation C ← α ⊗ C ⊕ β ⊗ A ⊗ B, where A, B, and C are three appropriately sized matrices, ⊕ and ⊗ operations are originating from the corresponding matrix semiring, and α and β are constants, and beta is not equal to zero. It allows to obtain the highly optimized form structured similar to the expert implementation of GEMM that can be found in GotoBLAS and its successors.
