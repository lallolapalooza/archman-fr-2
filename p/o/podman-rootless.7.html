Limites de Podman sans privilèges

La liste suivante classe les problèmes et irrégularités connus lors de l'exécution de Podman en tant qu'utilisateur non-root. Bien que fonctionnel actuellement, il reste un certain nombre de tâches à considérer pour être ajoutées. Ces changements proposés sont à différents stades de conception et de développement.

Les contributeurs sont les bienvenus pour aider à ce travail. Si vous décidez de prendre une partie et de travailler dessus, veuillez créer une issue sur GitHub et vous l'assigner. Si vous trouvez d'autres comportements inattendus avec Podman sans privilèges et que vous estimez qu'ils méritent d'être signalés, n'hésitez pas à mettre à jour ce document.

•
Podman ne peut pas créer de conteneurs qui se lient à des ports < 1024.
  • Le noyau n'autorise pas les processus sans CAP_NET_BIND_SERVICE à se lier à des ports bas.
  • Vous pouvez modifier le sysctl net.ipv4.ip_unprivileged_port_start pour changer le port le plus bas. Par exemple, sysctl net.ipv4.ip_unprivileged_port_start=443 permet aux conteneurs Podman sans privilèges de se lier à des ports >= 443.
  • Un serveur proxy, une règle de pare-feu du noyau, ou un outil de redirection tel que redir peut être utilisé pour rediriger le trafic d'un port privilégié vers un port non privilégié (où un podman pod est lié) dans un scénario serveur - où un utilisateur a accès au compte root (ou que le setuid sur le binaire serait un risque acceptable), mais souhaite exécuter les conteneurs en tant qu'utilisateur non privilégié pour une sécurité accrue et pour un nombre limité de ports prédéfinis.
•
À partir de Podman 5.0, pasta est l'outil de mise en réseau par défaut. Comme pasta copie l'adresse IP de l'interface principale, les connexions à cette IP depuis les conteneurs ne fonctionnent pas. Cela signifie qu'à moins d'avoir plus d'une interface, les connexions inter-conteneurs ne peuvent pas être établies sans passer explicitement une configuration réseau pasta, soit dans containers.conf, soit au moment de l'exécution.
•
Si vous aviez auparavant des transferts de ports (par exemple, via -p 80:80) auxquels d'autres conteneurs pouvaient accéder, vous pouvez soit revenir à slirp4netns, soit utiliser la solution (définition des options pasta avec des IP 10.0.2.x) publiée ici.
  • La documentation "Comment faire" est au mieux inégale.
  • Si /etc/subuid et /etc/subgid ne sont pas configurés pour un utilisateur, alors les commandes podman peuvent échouer facilement
  • Cela peut être un problème majeur sur les machines utilisant des informations de mot de passe basées sur le réseau (FreeIPA, Active Directory, LDAP)
  • Nous travaillons à obtenir le support de NSSWITCH pour les fichiers /etc/subuid et /etc/subgid.
•
Pas de support pour cgroup V1
  • cgroup V1 ne prend pas en charge de manière sécurisée la délégation de cgroup.
  • Depuis Fedora 31, la valeur par défaut est cgroup V2, qui prend en charge intégralement la gestion des cgroups sans privilèges. Notez que cela nécessite l'utilisation de --cgroup-manager dans les conteneurs sans privilèges pour utiliser systemd, ce que les nouveaux conteneurs obtiendront par défaut.
•
Certaines options de configuration d'unité système ne fonctionnent pas dans le conteneur sans privilèges
  • systemd échoue à appliquer plusieurs options et les échecs sont ignorés silencieusement (par exemple, CPUShares, MemoryLimit). Devrait fonctionner avec cgroup V2.
  • L'utilisation de certaines options entraînera des échecs de démarrage de service (par exemple, PrivateNetwork). Les services systemd nécessitant PrivateNetwork peuvent fonctionner en passant --cap-add SYS_ADMIN, mais les implications de sécurité doivent être soigneusement évaluées. Dans la plupart des cas, il est préférable de créer un fichier de substitution (override.conf) qui définit PrivateNetwork=no. Cela s'applique également aux conteneurs exécutés par root.
  • Ne peut pas partager les images de conteneurs avec CRI-O ou d'autres utilisateurs rootful
  • Difficile d'utiliser des magasins supplémentaires pour le partage de contenu
  • Ne fonctionne pas sur les homedirs NFS ou de systèmes de fichiers parallèles (par exemple, GPFS)
  • NFS et les systèmes de fichiers parallèles appliquent la création de fichiers sur différents UID côté serveur et ne comprennent pas les espaces de noms utilisateurs.
  • Lorsqu'un processus root du conteneur comme YUM tente de créer un fichier appartenant à un UID différent, NFS Server/GPFS refuse la création.
•
Ne fonctionne pas avec les homedirs montés avec noexec/nodev
•
L'utilisateur peut configurer le stockage pour pointer vers d'autres répertoires auxquels il peut écrire et qui ne sont pas montés noexec/nodev
•
Le support de l'utilisation d'overlayfs natif en tant qu'utilisateur non privilégié n'est disponible que pour la version de Podman >= 3.1 sur une version du noyau Linux >= 5.12, sinon le plus lent fuse-overlayfs peut être utilisé.
•
Quelques distributions Linux (par exemple, Ubuntu) ont pris en charge des versions encore plus anciennes de Podman et du noyau Linux en modifiant le comportement normal du noyau Linux.
  • Le seul autre pilote pris en charge est VFS.
  • Ne peut pas utiliser ping immédiatement.
•
(Peut être corrigé en configurant le sysctl sur l'hôte)
  • Nécessite un nouveau shadow-utils (non trouvé dans les anciennes distributions (RHEL7/Centos7) Devrait être corrigé dans la sortie RHEL7.7)
  • Quelques commandes ne fonctionnent pas.
•
mount/unmount (sur fuse-overlay)
•
Fonctionne uniquement si vous entrez dans l'espace de noms de montage avec podman unshare
  • podman stats (Fonctionne avec le support cgroup V2)
  • Checkpoint et Restore (CRIU nécessite root)
  • Pause et Unpause (Fonctionne avec le support cgroup V2)
•
Des problèmes avec des UID plus élevés peuvent entraîner l'échec des builds
•
Si un build tente d'utiliser un UID qui n'est pas mappé dans le mappage de l'espace de noms utilisateur pour un conteneur, les builds ne pourront pas placer l'UID dans une image.
•
La création de nœuds de périphériques dans un conteneur échoue, même en exécutant --privileged.
•
Le noyau ne permet pas aux processus non root (processus sans CAP_MKNOD) de créer des nœuds de périphériques. Si un conteneur doit créer des nœuds de périphériques, il doit être exécuté en tant que root.
•
Lors de l'utilisation de --net=host avec des conteneurs sans privilèges, les exécutions `podman exec` ultérieures vers ce conteneur ne rejoindront pas l'espace de noms réseau de l'hôte car il est détenu par root.
