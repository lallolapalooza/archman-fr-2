podman-container-clone(1) Manuel des commandes générales podman-container-clone(1)

NOM

podman-container-clone - Crée une copie d'un conteneur existant

SYNTAXE

podman container clone [options] conteneur nom image

DESCRIPTION

podman container clone crée une copie d'un conteneur, recréant l'original avec une configuration identique. Cette commande prend trois arguments : le premier étant l'ID ou le nom du conteneur à cloner, le second argument de cette commande peut changer le nom du clone par rapport au nom par défaut $NOM_ORIGINAL-clone, et le troisième est une nouvelle image à utiliser dans le conteneur cloné.

OPTIONS

--blkio-weight=poids

Poids relatif de l'IO bloc. Le poids est une valeur comprise entre 10 et 1000.

Cette option n'est pas supportée sur les systèmes rootless cgroups V1.

--blkio-weight-device=périphérique:poids

Poids relatif du périphérique pour l'IO bloc.

--cpu-period=limite

Définit la période CPU pour le Completely Fair Scheduler (CFS), qui est une durée en microsecondes. Une fois le quota CPU du conteneur épuisé, il ne sera pas planifié pour s'exécuter avant la fin de la période en cours. Par défaut, il est de 100000 microsecondes.

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas supportée sur les systèmes rootless cgroups V1.

Si aucune n'est spécifiée, la période CPU du conteneur original est utilisée.

--cpu-quota=limite

Limite le quota CPU du Completely Fair Scheduler (CFS).

Limite l'utilisation du CPU du conteneur. Par défaut, les conteneurs s'exécutent avec la totalité des ressources CPU. La limite est un nombre en microsecondes. Si un nombre est fourni, le conteneur est autorisé à utiliser cette quantité de temps CPU jusqu'à la fin de la période CPU (contrôlable via --cpu-period).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas supportée sur les systèmes rootless cgroups V1.

Si aucune n'est spécifiée, le quota CPU du conteneur original est utilisé.

--cpu-rt-period=microsecondes

Limite la période temps réel CPU en microsecondes.

Limite l'utilisation du CPU en temps réel du conteneur. Cette option indique au noyau de restreindre l'utilisation du CPU en temps réel du conteneur à la période spécifiée.

Cette option n'est supportée que sur les systèmes rootful cgroups V1.

Si aucune n'est spécifiée, la période d'exécution CPU du conteneur original est utilisée.

--cpu-rt-runtime=microsecondes

Limite le temps d'exécution temps réel CPU en microsecondes.

Limite l'utilisation du CPU en temps réel du conteneur. Cette option indique au noyau de limiter la quantité de temps qu'une tâche en temps réel peut consommer pendant une période CPU donnée. Par exemple : une période de 1 000 000µs et un temps d'exécution de 950 000µs signifie que ce conteneur peut consommer 95% du CPU disponible et laisser les 5% restants aux tâches de priorité normale.

La somme de tous les temps d'exécution entre les conteneurs ne peut pas dépasser la quantité allouée au groupe cgroup parent.

Cette option n'est supportée que sur les systèmes rootful cgroups V1.

--cpu-shares, -c=parts

Parts CPU (poids relatif).

Par défaut, tous les conteneurs reçoivent la même proportion de cycles CPU. Cette proportion peut être modifiée en changeant le poids des parts CPU du conteneur par rapport au poids combiné de tous les conteneurs en exécution. Le poids par défaut est 1024.

La proportion ne s'applique que lorsque des processus intensifs en CPU s'exécutent. Lorsque les tâches d'un conteneur sont inactives, les autres conteneurs peuvent utiliser le temps CPU restant. La quantité réelle de temps CPU varie en fonction du nombre de conteneurs en cours d'exécution sur le système.

Par exemple, considérez trois conteneurs, l'un avec une part CPU de 1024 et deux autres avec une part CPU de 512. Lorsque les processus dans les trois conteneurs tentent d'utiliser 100% du CPU, le premier conteneur reçoit 50% du temps CPU total. Si un quatrième conteneur est ajouté avec une part CPU de 1024, le premier conteneur ne reçoit que 33% du CPU. Les conteneurs restants reçoivent respectivement 16,5%, 16,5% et 33% du CPU.

Sur un système multi-cœurs, les parts de temps CPU sont distribuées sur tous les cœurs CPU. Même si un conteneur est limité à moins de 100% du temps CPU, il peut utiliser 100% de chaque cœur CPU individuel.

Par exemple, considérez un système avec plus de trois cœurs. Si le conteneur C0 est démarré avec --cpu-shares=512 exécutant un processus, et un autre conteneur C1 avec --cpu-shares=1024 exécutant deux processus, cela peut entraîner la répartition suivante des parts CPU :

PID conteneur CPU Part CPU
100 C0 0 100% du CPU0
101 C1 1 100% du CPU1
102 C1 2 100% du CPU2

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas supportée sur les systèmes rootless cgroups V1.

Si aucune n'est spécifiée, les parts CPU du conteneur original sont utilisées.

--cpus

Définit un nombre de CPU pour le conteneur qui remplace les limites CPU du conteneur original. Si aucune n'est spécifiée, les nano-CPU du conteneur original sont utilisés.

C'est un raccourci pour --cpu-period et --cpu-quota, donc seule l'option --cpus ou les deux options --cpu-period et --cpu-quota peuvent être définies.

Cette option n'est pas supportée sur les systèmes rootless cgroups V1.

--cpuset-cpus=nombre

CPU dans lesquels autoriser l'exécution. Peut être spécifié sous forme de liste séparée par des virgules (par ex. 0,1), de plage (par ex. 0-3), ou toute combinaison de ceux-ci (par ex. 0-3,7,11-15).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas supportée sur les systèmes rootless cgroups V1.

Si aucune n'est spécifiée, le cpuset CPU du conteneur original est utilisé.

--cpuset-mems=nœuds

Nœuds mémoire (MEMs) dans lesquels autoriser l'exécution (0-3, 0,1). Uniquement efficace sur les systèmes NUMA.

S'il y a quatre nœuds mémoire sur le système (0-3), utilisez --cpuset-mems=0,1, alors les processus du conteneur n'utiliseront la mémoire que des deux premiers nœuds mémoire.

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas supportée sur les systèmes rootless cgroups V1.

Si aucune n'est spécifiée, les nœuds mémoire CPU du conteneur original sont utilisés.

podman-container-clone(1) — podman — Arch Linux man pages

NAME

podman-container-clone - Clone a container

SYNOPSIS

podman container clone [OPTIONS] CONTAINER [CONTAINER...]

DESCRIPTION

The podman container clone command duplicates an existing container. This command can be used to create a copy of a container that is in a specific state, or to create a new container with resource constraints or a new image based on the original container.

OPTIONS

--destroy

Supprimer le conteneur d'origine que nous clonons une fois utilisé pour imiter la configuration.

--device-read-bps=path:rate

Limiter le débit de lecture (en octets par seconde) d'un périphérique (par exemple, --device-read-bps=/dev/sda:1mb).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes sans root utilisant cgroups V1.

--device-write-bps=path:rate

Limiter le débit d'écriture (en octets par seconde) vers un périphérique (par exemple, --device-write-bps=/dev/sda:1mb).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes sans root utilisant cgroups V1.

--force, -f

Forcer la suppression du conteneur d'origine que nous clonons. Ne peut être utilisé qu'en conjonction avec --destroy.

--memory, -m=nombre[unité]

Limite de mémoire. Une unité peut être b (octets), k (kibioctets), m (mébioctets) ou g (gibioctets).

Permet de contraindre la mémoire disponible pour un conteneur. Si l'hôte prend en charge la mémoire swap, alors le réglage de mémoire -m peut être supérieur à la RAM physique. Si une limite de 0 est spécifiée (sans utiliser -m), la mémoire du conteneur n'est pas limitée. La limite réelle peut être arrondie à un multiple de la taille de page du système d'exploitation (la valeur est très grande, c'est des millions de trillions).

Cette option n'est pas prise en charge sur les systèmes sans root utilisant cgroups V1.

Si aucune limite de mémoire n'est spécifiée, les limites de mémoire du conteneur d'origine sont utilisées.

--memory-reservation=nombre[unité]

Limite de mémoire souple. Une unité peut être b (octets), k (kibioctets), m (mébioctets) ou g (gibioctets).

Après avoir défini la réservation de mémoire, lorsque le système détecte une contention de mémoire ou une faible mémoire, les conteneurs sont forcés de restreindre leur consommation à leur réservation. Définissez donc toujours la valeur en dessous de --memory, sinon la limite dure prend le dessus. Par défaut, la réservation de mémoire est identique à la limite de mémoire.

Cette option n'est pas prise en charge sur les systèmes sans root utilisant cgroups V1.

Si non spécifiée, la réservation de mémoire est identique à la limite de mémoire du conteneur cloné.

--memory-swap=nombre[unité]

Une valeur limite égale à la mémoire plus le swap. Une unité peut être b (octets), k (kibioctets), m (mébioctets) ou g (gibioctets).

Doit être utilisé avec le drapeau -m (--memory). La valeur de l'argument doit être supérieure à celle de
-m (--memory). Par défaut, elle est définie au double de la valeur de --memory.

Définissez nombre sur -1 pour activer le swap illimité.

Cette option n'est pas prise en charge sur les systèmes sans root utilisant cgroups V1.

Si non spécifiée, le conteneur cloné est utilisé pour dériver la valeur du swap.

--memory-swappiness=nombre

Ajuster le comportement de swappiness de la mémoire d'un conteneur. Accepte un entier compris entre 0 et 100.

Ce drapeau n'est pris en charge que sur les systèmes rootful utilisant cgroups V1.

--name

Définir un nom personnalisé pour le conteneur cloné. Par défaut, s'il n'est pas spécifié, le nom est de la syntaxe : <NOM_ORIGINAL>-clone

--pod=nom

Cloner le conteneur dans un pod existant. Il est utile de déplacer un conteneur vers un pod existant. Le conteneur rejoint les espaces de noms partagés du pod, perdant sa configuration qui entre en conflit avec les espaces de noms partagés.

--run

Lorsque ce drapeau est défini sur true, il exécute le conteneur nouvellement créé après la fin du processus de clonage. Ceci spécifie un mode d'exécution détaché.

EXEMPLES

Cloner un conteneur spécifié dans un nouveau conteneur :

# podman container clone d0cf1f782e2ed67e8c0050ff92df865a039186237a4df24d7acba5b1fa8cc6e7
6b2c73ff8a1982828c9ae2092954bcd59836a131960f7e05221af9df5939c584

Cloner un conteneur spécifié dans un conteneur nouvellement nommé :

# podman container clone --name=clone d0cf1f782e2ed67e8c0050ff92df865a039186237a4df24d7acba5b1fa8cc6e7
6b2c73ff8a1982828c9ae2092954bcd59836a131960f7e05221af9df5939c584

Remplacer un conteneur spécifié avec des contraintes de ressources sélectionnées dans un nouveau conteneur, en supprimant le conteneur d'origine :

# podman container clone --destroy --cpus=5 d0cf1f782e2ed67e8c0050ff92df865a039186237a4df24d7acba5b1fa8cc6e7
6b2c73ff8a1982828c9ae2092954bcd59836a131960f7e05221af9df5939c584

Cloner un conteneur spécifié en lui donnant un nouveau nom, puis en remplaçant l'image du conteneur d'origine par le nom d'image spécifié :
